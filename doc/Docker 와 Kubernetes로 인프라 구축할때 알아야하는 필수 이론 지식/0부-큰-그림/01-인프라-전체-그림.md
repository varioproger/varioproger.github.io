# 1장. 인프라 전체 그림 — Docker, Kubernetes, Terraform, EKS의 역할과 배포 흐름

> **🎮 게임 서버 개발자에게** — 지금까지는 빌드한 서버 실행 파일을 IDC나 클라우드 머신에 복사하고, 런처 스크립트나 감시 프로세스로 채널 서버 N개를 띄워 왔을 것이다. 이 장은 그 일을 네 도구가 나눠 맡는 **지도**다. Docker는 "실행 파일 패키지"를, Terraform은 "머신과 네트워크 발주"를, Kubernetes는 "서버 N개를 늘 살아 있게 유지하는 감시자"를 맡는다. 결정적 차이는 Kubernetes가 "지금 3개 더 띄워라"라는 명령을 실행하는 스크립트가 아니라 **"늘 N개여야 한다"는 의도를 저장하고 계속 맞추는 제어 루프**라는 점, 그리고 그 루프가 머신(EC2)까지 만들어 주지는 않는다는 점이다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 이벤트 오픈 직전 서버 수를 3개에서 8개로 올렸는데 일부가 `Pending`으로 멈춰 있고, 누군가 "`terraform apply` 한 번 돌려 보자"고 말한다.
> - 패치 배포 후 버그가 나서 이전 이미지로 롤백했는데, 새 버전이 바꿔 둔 DB 스키마 때문에 이전 버전이 오류를 낸다.
> - "EKS를 쓰니까 서버 운영은 AWS가 해 주겠지"라는 말을 듣고 운영 계획을 세워야 한다.

> **이 장을 맨 처음 읽는 독자에게** — 이 장은 책 전체의 지도다. Pod, Deployment, Service 같은 낯선 이름이 쏟아지지만 지금은 **"누가 무엇을 맡는가"와 "배포가 어떤 순서로 흐르는가"**만 잡으면 충분하다. 처음 나오는 용어마다 짧은 풀이와 자세히 다루는 장을 붙여 두었으니, 그 장을 읽은 뒤 이 장으로 돌아와 다시 보면 지도가 훨씬 선명해진다.

> 이 장의 예시는 원문과 같이 **일반 EKS + EC2 Managed Node Group** 구성을 기준으로 한 학습용 설명이다. 수량은 원리를 보이기 위한 가정이다.

## 코어 — 이것만은 100%

> **한 문장:** Docker는 이미지를 만들고 Terraform은 AWS 자원을 코드로 선언하며 Kubernetes(EKS 제어부)는 원하는 실행 상태를 계속 맞추는데, "어디서 실행되는가"와 "누가 그 설정을 소유하는가"는 다른 질문이므로 Pod가 늘어도 EC2·Terraform이 자동으로 따라오지 않는다.

1. **네 도구, 네 역할** — Docker = 이미지 빌드, Kubernetes = 실행 의도 저장·유지, EKS = AWS가 관리하는 Kubernetes 제어부, Terraform = AWS 자원·정책을 코드로 선언(실행 후 종료). Node는 머신, Pod는 배치 단위, 컨테이너 안의 앱은 프로세스다.
2. **Git에서 EKS까지 — 이미지는 주소로 전달된다** — 배포 흐름은 Git → CI → Docker 빌드 → ECR → CD → EKS API이며, Kubernetes에는 이미지 자체가 아니라 이미지 주소(digest)가 전달되고 노드가 ECR에서 pull한다. 새 버전은 컨테이너를 덮어쓰지 않고 새 Pod로 교체한다.
3. **수요(replicas)와 공급(노드)은 별개, apply는 소유자일 때만** — 앱 복제 수와 머신 수는 다른 숫자다. Terraform은 그 설정의 소유자일 때만 변경·apply가 필요하고, Pending을 보면 먼저 무엇이 부족한지부터 확인한다.
4. **매니지드여도 내 책임** — EKS가 대신하는 것은 컨트롤 플레인 운영이다. RBAC·NetworkPolicy·업그레이드 결정·관측성·백업은 여전히 사용자의 몫이다.

|---|---|---|---|
| 빌드 머신이 만든 서버 실행 파일 + 리소스 패키지 | Docker **이미지** | 다시 실행할 수 있게 저장한 빌드 산출물이다. 실행 중인 서버가 아니다 | 실행에 필요한 라이브러리·OS 사용자 공간 파일까지 함께 담고, 레지스트리(ECR)에 올려 **주소(digest)로 가리킨다**. 배포 때 파일을 머신에 복사해 넣지 않고 노드가 스스로 pull한다 |
| 죽은 채널 서버를 다시 띄우는 감시 프로세스·런처 스크립트 | Kubernetes **Deployment / ReplicaSet controller** | 정해 둔 개수를 유지하고 죽으면 다시 띄운다 | "띄워라"를 한 번 실행하는 명령형 스크립트가 아니라 **원하는 상태를 저장하고 계속 맞추는 제어 루프**다. 어느 머신에 띄울지도 scheduler가 고른다. 그러나 **머신이 모자라면 만들지 않고 Pending으로 기다린다** |
| 서버 머신 한 대에 채널 서버 프로세스 여러 개 | **Node**와 **Pod** | 한 머신에 여러 실행 단위가 올라간다 | Pod는 하나 이상의 컨테이너를 묶은 배치 단위이고, 한 Pod가 여러 머신에 나뉘어 실행되지 않는다. Pod가 늘어도 머신(EC2)은 늘지 않는다 |
| IDC 장비 발주·네트워크 세팅 작업 | **Terraform** | 서버가 돌 머신과 네트워크를 준비한다 | 코드(HCL)로 선언하고 `plan`으로 확인 후 `apply`로 반영한다. 실행이 끝나면 종료되므로 **부하가 늘어도 스스로 다시 돌지 않는다** |
| 점검 시간에 서버를 내리고 실행 파일을 덮어쓴 뒤 다시 올리기 | **rolling update** | 새 버전으로 교체한다 | 실행 중인 컨테이너의 파일을 덮어쓰지 않는다. 새 ReplicaSet의 새 Pod를 늘리며 기존 Pod를 줄인다. 롤백해도 DB 데이터·스키마는 자동으로 돌아오지 않는다 |

## 코어 1. 네 도구, 네 역할

### 1.1 먼저 용어 정리: 머신, 실행 단위, 관리 프로그램

**한 줄 요약:** Node는 실행 장소, Pod는 배치 단위, 컨테이너 안의 앱은 실제 프로세스다.

- **Node**(→ [13장](../3부-쿠버네티스-핵심/13-왜-쿠버네티스인가.md)): Kubernetes 클러스터에 연결되어 앱 실행에 쓰이는 머신. 이 예시에서는 EC2 한 대가 worker Node 하나에 대응한다. Node 객체는 그 머신의 주소·용량·상태를 나타내는 기록이다. Node YAML을 등록하는 것만으로 EC2가 만들어지지는 않는다.
- **Pod**(→ [15장](../3부-쿠버네티스-핵심/15-Pod.md)): 같은 노드에 함께 배치할 컨테이너를 묶는 단위. 한 Node에 여러 Pod가 실행될 수 있고, 한 Pod가 여러 EC2에 나뉘어 실행되지는 않는다.
- Node는 **실행 장소**, Pod는 **배치 단위**, 컨테이너 안의 앱은 **실제 프로세스**다.

```
EC2 Node A                       EC2 Node B
├─ Linux 커널                    ├─ Linux 커널
├─ kubelet / containerd          ├─ kubelet / containerd
├─ Pod 1 → 주문 앱 컨테이너       ├─ Pod 3 → 주문 앱 컨테이너
└─ Pod 2 → 주문 앱 컨테이너       └─ 추가 Pod를 실행할 여유
```

Pod가 하나 더 생겨도 EC2가 한 대 더 생긴 것은 아니다. IP는 네트워크 주소이고 EC2는 머신이다.

### 1.2 네 가지 도구의 역할

**한 줄 요약:** Docker는 이미지를, Kubernetes는 실행 의도를, EKS는 제어부를, Terraform은 AWS 자원을 맡는다.

| 도구 | 하는 일 |
|---|---|
| **Docker** | 소스와 Dockerfile로 **이미지**를 만들고(빌드), 로컬에서 컨테이너를 실행해 확인한다. 이미지는 실행 중인 서버가 아니라 다시 실행할 수 있도록 저장한 산출물이다. |
| **Kubernetes** | "이미지 A의 앱을 3개 유지하라"는 **실행 의도를 저장하고 계속 맞춘다**. Deployment는 설정을 저장하는 객체이며, Deployment controller → ReplicaSet controller → Pod 객체 생성 → Scheduler가 노드 선택 → 노드의 kubelet이 runtime에 실행 요청 순으로 현실이 만들어진다. |
| **EKS** | AWS가 관리하는 **Kubernetes 제어부**(컨트롤 플레인: API Server, controller, scheduler, etcd)를 제공한다. 'EKS 스케줄러'가 따로 있는 것이 아니라 EKS가 제공하는 Kubernetes의 scheduler가 배치를 담당한다. |
| **Terraform** | HCL로 VPC, subnet, EKS cluster, Node Group, IAM, ECR 같은 **AWS 자원과 정책을 코드로 선언**하고 provider로 API를 호출한다. `plan`으로 계획을 보고 `apply`로 반영한다. 일반 CLI 실행은 끝나면 종료되며 Pod가 늘어날 때마다 자동으로 다시 실행되지 않는다. |

Docker 이미지와 빌드는 [5장](../2부-컨테이너와-Docker/05-가상머신-vs-컨테이너-Docker-전체-구조.md) [8장](../2부-컨테이너와-Docker/08-이미지-레이어-레지스트리-OCI.md) [9장](../2부-컨테이너와-Docker/09-Dockerfile과-이미지-빌드.md), Deployment·ReplicaSet은 [18장](../3부-쿠버네티스-핵심/18-워크로드-컨트롤러.md), 제어부와 scheduler의 구조는 [13장](../3부-쿠버네티스-핵심/13-왜-쿠버네티스인가.md) [19장](../3부-쿠버네티스-핵심/19-리소스-요청-제한과-스케줄링-기초.md)에서 자세히 다룬다.

**Kubernetes의 기본 scheduler는 EC2 생성 도구가 아니다.** Pod를 배치할 곳이 없으면 배치가 진행되지 않는다. 앱 개수 조정과 머신 공급은 연결할 수 있는 **별개의 일**이다.

### 1.3 누가 어디서 실행되는가

**한 줄 요약:** 빌드·Terraform은 실행 후 끝나지만, 제어부와 노드의 프로그램은 계속 돈다.

| 주체 | 주로 실행되는 곳 | 직접 바꾸는 것 | 작업 이후 남는 것 |
|---|---|---|---|
| Docker 빌드 도구 | 개발 머신 또는 CI runner | 이미지 산출물 | 레지스트리의 이미지 |
| Terraform | 운영자 머신 또는 인프라 CI runner | 담당 API의 자원·설정 | AWS 자원, 적용한 정책, state |
| Kubernetes 제어부 | EKS에서는 AWS 관리 영역 | Pod 등 객체, 배치·상태 | 지속적인 제어 루프 |
| kubelet / containerd | 각 worker Node | 로컬 실행 환경과 프로세스 | 실행 중 컨테이너와 상태 보고 |

운영자 머신의 Terraform이 종료돼도 EKS 제어부와 노드의 프로그램은 계속 실행된다. 빌드 머신을 꺼도 ECR의 이미지는 사라지지 않는다.

### 1.4 같은 말, 다른 의미

**한 줄 요약:** 두 개의 `apply`, 두 종류의 "늘린다"를 구분한다.

| 표현 | 의미 | 의미하지 않는 것 |
|---|---|---|
| `terraform apply` | Terraform이 관리하는 자원·설정 변경 반영 | 모든 Pod가 준비됐다는 보장 |
| `kubectl apply` | Kubernetes API에 객체 생성·변경 요청 | EC2를 반드시 새로 생성 |
| Pod replicas 증가 | 실행할 앱 복제본 수요 증가 | Pod 수만큼 EC2 증가 |
| Node 수 증가 | 앱을 배치할 머신 공급 증가 | 앱 replicas도 자동 증가 |

`kubectl`과 객체·매니페스트의 개념은 [14장](../3부-쿠버네티스-핵심/14-API-오브젝트-kubectl-YAML.md)에서 다룬다.

## 코어 2. Git에서 EKS까지 — 이미지는 주소로 전달된다

### 2.1 배포 흐름: 세 흐름이 EKS에서 만난다

**한 줄 요약:** 기반 준비는 환경이 바뀔 때, 앱 배포는 버전이 바뀔 때 돌고, 둘은 준비된 EKS 클러스터에서 만난다.

기반 준비는 **환경을 처음 만들거나 바꿀 때**, 앱 배포는 **버전이 바뀔 때** 수행한다. 두 흐름은 준비된 EKS 클러스터에서 만난다.

```
[A. 기반 준비 — 환경 생성·변경 시]
 Terraform 구성 → plan 확인 후 apply → AWS API가 VPC·EKS·Node Group·IAM·ECR 생성
                                    → 클러스터 준비(노드·CNI·DNS·LB controller·배포 권한)

[B. 앱 배포 — 앱 버전 변경 시]
 1 앱 개발(코드·테스트·Dockerfile·배포 설정)
 2 Git 원격 저장소 (commit / push / merge)
 3 CI runner: 코드 checkout · 테스트
 4 Docker 빌드: 이미지 생성
 5 ECR(레지스트리): 이미지 push · digest 확보
 6 CD: 배포할 이미지 digest와 환경 설정 선택
 7 Deployment · Service · Ingress 설정을 EKS API에 적용 (kubectl apply 등)

[C. EKS 안에서]
 8 API Server: 권한·설정 검증 후 객체 반영
 9 Controllers: ReplicaSet · Pod 객체 생성
10 Scheduler: 새 Pod의 실행 노드 결정
11 노드의 kubelet / containerd: 이미지를 ECR에서 pull하여 실행
12 앱 Pod: readiness 확인 · 상태 보고
13 사용자: 도메인으로 접속 → ALB → 건강한 Pod
```

C 구간(8~12단계)의 각 컴포넌트는 [13장](../3부-쿠버네티스-핵심/13-왜-쿠버네티스인가.md), readiness는 [16장](../3부-쿠버네티스-핵심/16-Pod-생명주기와-헬스체크.md), ALB를 만드는 Ingress는 [23장](../4부-노출-데이터-운영/23-Ingress와-외부-트래픽.md)에서 다룬다. CNI·DNS는 [21장](../4부-노출-데이터-운영/21-네트워크-모델과-Service.md) [22장](../4부-노출-데이터-운영/22-DNS와-서비스-디스커버리.md)의 주제다.

**중요한 갈림길**: Git에는 소스와 설정이 들어가고, ECR에는 빌드한 이미지가 들어간다. 배포 도구는 이미지 파일 자체를 Kubernetes API에 올리지 않고 **이미지 주소(digest)를 설정에 넣는다.** 노드의 runtime이 그 주소로 ECR에서 이미지를 가져온다. (이미지·레지스트리·digest → [8장](../2부-컨테이너와-Docker/08-이미지-레이어-레지스트리-OCI.md))

Git에 push한다고 이 전부가 기본으로 실행되지는 않는다. 어떤 push/merge가 workflow를 시작할지, 테스트 실패 시 어디서 멈출지를 **CI/CD 설정으로 연결해야 한다.**

### 2.2 파일마다 답하는 질문

**한 줄 요약:** 파일 다섯 종류가 각각 하나의 질문에 답한다.

- **Dockerfile**(→ [9장](../2부-컨테이너와-Docker/09-Dockerfile과-이미지-빌드.md)): 이미지 안에 어떤 실행 파일을 넣고 무엇을 실행할까?
- **Deployment**(→ [18장](../3부-쿠버네티스-핵심/18-워크로드-컨트롤러.md)): 그 이미지를 몇 개, 어떤 자원으로 실행할까?
- **Service**(→ [21장](../4부-노출-데이터-운영/21-네트워크-모델과-Service.md)): 어느 Pod 집합을 안정된 이름과 포트로 찾을까?
- **Ingress**(→ [23장](../4부-노출-데이터-운영/23-Ingress와-외부-트래픽.md)): 외부 HTTP 요청을 어느 Service에 연결할까?
- **Terraform 구성**: 이 일을 할 AWS 환경과 권한을 어떻게 만들까?

비밀번호나 장기 자격 증명은 이미지나 일반 Git 소스에 넣지 않고, 접근 제어가 있는 별도 경로로 주입한다. (Secret → [17장](../3부-쿠버네티스-핵심/17-ConfigMap과-Secret.md))

### 2.3 권한 세 가지

**한 줄 요약:** push(CI→ECR), 배포(CD→EKS API), pull(노드→ECR) 세 경로마다 권한과 네트워크가 필요하다.

| 누가 접근하는가? | 필요한 권한·경로 |
|---|---|
| CI가 ECR에 이미지 push | ECR 쓰기 권한 |
| CD가 EKS API에 배포 | 클러스터 인증·인가와 API endpoint 네트워크 접근 |
| 노드 runtime이 ECR에서 이미지 pull | 노드 구성에 맞는 이미지 읽기 권한과 네트워크 접근 |

클러스터 인증·인가(RBAC)는 [25장](../4부-노출-데이터-운영/25-인증-인가-보안-오토스케일링.md)에서 다룬다.

### 2.4 새 버전 배포

**한 줄 요약:** 새 버전은 덮어쓰기가 아니라 새 ReplicaSet으로의 교체이며, 롤백은 DB를 되돌리지 않는다.

Deployment의 이미지를 A에서 B로 바꾸면 Deployment controller가 새 ReplicaSet을 만들고, rolling update 전략에 맞춰 새 Pod를 늘리며 기존 Pod를 줄인다. **기존 컨테이너 안의 파일을 덮어쓰는 방식이 아니다.** 롤백도 이전 이미지로 돌릴 수 있지만, 이미 바뀐 DB 데이터와 스키마가 자동 복구되는 것은 아니다. (rolling update의 세부 → [18장](../3부-쿠버네티스-핵심/18-워크로드-컨트롤러.md))

### 2.5 매니페스트를 배포하는 도구 (개요)

**한 줄 요약:** 서드파티 앱은 Helm, 우리 앱의 환경별 설정은 Kustomize, Git 기준 자동 반영은 GitOps.

배포 흐름의 7단계(설정을 EKS API에 적용)에서 매니페스트를 클러스터에 적용하는 방법은 `kubectl apply` 하나만 있는 것이 아니다. 환경(dev/prod)이 늘고 서드파티 앱을 설치하게 되면 다음 도구를 만나게 된다. (Helm·Kustomize 개요는 [14장](../3부-쿠버네티스-핵심/14-API-오브젝트-kubectl-YAML.md), 설정 변경과 함께 쓰는 기법은 [17장](../3부-쿠버네티스-핵심/17-ConfigMap과-Secret.md)에서도 다룬다)

| 도구 | 방식 | 주로 쓰는 곳 |
|---|---|---|
| **Helm** | **차트**(매니페스트 템플릿 묶음)에 **값**(values)을 주입해 렌더링하고, 결과를 **릴리스**로 설치·추적한다. `helm history`/`helm rollback`으로 이력과 롤백을 관리한다 | 서드파티 앱 설치(Prometheus, cert-manager 등) |
| **Kustomize** | 유효한 YAML(base)에 환경별 패치(overlay)를 덧씌운다. `kubectl apply -k`로 내장 지원 | 우리 애플리케이션의 환경별 설정 |
| **GitOps**(Argo CD, Flux) | 클러스터 안의 에이전트가 Git 저장소를 지켜보다가 선언된 상태로 맞추고, 누가 손으로 바꾼 것(드리프트)도 되돌린다 | 배포 자동화와 감사 |

원문은 실무에서 Helm과 Kustomize를 **둘 다** 쓴다고 정리한다. GitOps는 CI가 `kubectl apply`를 하는 전통적인 push 방식과 달리 클러스터 자격 증명을 CI 시스템에 두지 않아도 된다는 보안 이점이 있다.

```bash
helm upgrade --install my-api ./chart -n prod --create-namespace -f values.prod.yaml   # 설치 또는 업그레이드
helm history my-api -n prod                                                            # 릴리스 이력
helm rollback my-api 2 -n prod                                                         # 2번 리비전으로 롤백
```

`-n prod`의 namespace는 [20장](../3부-쿠버네티스-핵심/20-네임스페이스.md)에서 다룬다.

## 코어 3. 수요(replicas)와 공급(노드)은 별개, apply는 소유자일 때만

### 3.1 먼저 세 숫자를 분리한다

**한 줄 요약:** replicas는 앱 수요, desired_size는 머신 목표, min·max_size는 허용 범위다.

| 숫자 | 예시 | 읽는 주체 |
|---|---|---|
| 앱의 원하는 Pod 수 | Deployment replicas = 6 | Deployment / ReplicaSet controller |
| 노드 그룹의 목표 머신 수 | desired_size = 2 | EC2 Auto Scaling 등 그룹 관리 기능 |
| 노드 그룹의 허용 범위 | min_size = 2, max_size = 5 | 그룹 관리 기능과 Cluster Autoscaler |

`max_size = 5`는 5대까지 **늘릴 수 있다는 상한**이지 5대를 당장 만들라는 명령이 아니다.

### 3.2 상황별 판단표

**한 줄 요약:** 자동 조정 주체가 있거나 여유가 있으면 apply가 필요 없고, Terraform이 그 수량을 소유할 때만 필요하다.

| 상황 | Terraform 변경 / apply 판단 |
|---|---|
| 앱 코드만 새 버전으로 배포 | 기존 기반을 쓰면 보통 불필요 |
| 기존 노드에 **여유가 있고** Pod 수만 증가 (예: 3 → 5) | 불필요 (replicas만 변경, EC2는 그대로) |
| HPA가 부하에 따라 replicas 변경 | 매 확장마다 불필요 |
| Cluster Autoscaler가 허용 범위 안에서 노드 추가 | 수량을 CA에 위임했다면 불필요 |
| 자동 확장이 없고 노드가 부족 (Pod 6 → 8, 노드 가득 참) | Terraform이 그룹 수량을 소유한다면 HCL 변경 → plan → apply |
| max=5인데 더 많은 용량이 필요 | Terraform 소유 max라면 변경 필요 |
| Pod 삭제 후 새 Pod 생성 | 불필요 (ReplicaSet controller가 복구) |
| Ingress에 따라 ALB 생성 | controller에 맡긴 ALB마다 별도 선언 불필요 |
| PVC에 따라 EBS 동적 생성 | 동적 디스크마다 별도 선언 불필요 |

HPA·Cluster Autoscaler는 [25장](../4부-노출-데이터-운영/25-인증-인가-보안-오토스케일링.md), Ingress와 ALB는 [23장](../4부-노출-데이터-운영/23-Ingress와-외부-트래픽.md), PVC와 동적 생성은 [24장](../4부-노출-데이터-운영/24-스토리지.md)에서 다룬다.

노드가 가득 차 있는데 Pod를 늘리면 Kubernetes는 원하는 상태(8개)를 기록하지만 EC2를 만들어 주지는 않는다. 배치하지 못한 Pod는 **Pending**으로 남는다. (Pending과 스케줄링 → [19장](../3부-쿠버네티스-핵심/19-리소스-요청-제한과-스케줄링-기초.md))

### 3.3 Terraform 실행 전의 네 질문

**한 줄 요약:** 부족한 것 → 조정 프로그램 → 정책 범위 → 설정 소유자 순서로 묻는다.

1. **무엇이 부족한가?** 앱 복제 수, 배치 용량, Pod IP, 권한, 이미지, 저장소 중 Events가 가리키는 것을 확인한다.
2. **그것을 조정할 프로그램이 있는가?** HPA, Cluster Autoscaler, Karpenter, AWS 그룹 기능 등.
3. **현재 정책 안에서 해결 가능한가?** 최대 수, zone, subnet, IAM, 할당량.
4. **바꿀 설정의 소유자는 누구인가?** Terraform이면 HCL·plan·apply, GitOps이면 저장소 변경, controller에 맡긴 동적 수량이면 해당 controller.

이미 노드에 배정된 Pod가 `ImagePullBackOff`라면 이미지·pull 권한·네트워크 문제다. **Pending이라는 표시만 보고 노드를 늘리거나 Terraform을 재실행하지 않는다.** (Events를 읽고 Pending·`ImagePullBackOff`를 진단하는 순서 → [26장](../4부-노출-데이터-운영/26-장애-진단-첫걸음.md))

> **[보충]** 이 장의 핵심 문장을 한 줄로 줄이면 "어디에서 실행되는가"와 "누가 그 설정을 관리하는가"는 서로 다른 질문이라는 것이다(원문의 표현을 풀어 쓴 것).

## 코어 4. 매니지드여도 내 책임

### 4.1 매니지드 쿠버네티스에서도 내 책임인 것

**한 줄 요약:** 클라우드는 컨트롤 플레인을 운영하고, 워커 노드는 공유 책임, 클러스터 설정과 워크로드는 전적으로 내 책임이다.

EKS 같은 매니지드 서비스가 대신해 주는 것은 주로 **컨트롤 플레인**(API 서버, etcd, 스케줄러, 컨트롤러 매니저)의 운영이다. 고가용성 구성, etcd 백업, 보안 패치와 버전 업그레이드 실행이 여기에 속한다. 나머지는 여전히 사용자의 몫이다.

| 영역 | 책임 |
|---|---|
| 컨트롤 플레인 | 클라우드가 운영 |
| 워커 노드 | 공유 책임. 클라우드는 노드 이미지·자동 복구 옵션을 제공하고, 업그레이드 시점·노드 크기와 수량·드레인은 내가 결정 |
| 클러스터 설정 | 전적으로 내 책임: RBAC, NetworkPolicy, ResourceQuota/LimitRange, Pod Security Admission, 애드온 선택과 운영 |
| 워크로드 | 전적으로 내 책임: 매니페스트, 리소스 설정, 프로브, 이미지 보안, 시크릿 관리, 관측성, 백업 |

원문은 매니지드에서도 반드시 해야 할 일로 노드 그룹 설계, 업그레이드 정책과 실행, RBAC과 클라우드 IAM 연동, NetworkPolicy(CNI 지원 여부 확인), 워크로드 아이덴티티 구성, 로깅·모니터링, 백업(etcd 백업만으로는 부족), 비용 관리를 꼽는다. **"매니지드를 쓰면 쿠버네티스를 몰라도 된다"는 것은 오해다.**

클러스터 설정 항목은 RBAC·NetworkPolicy·Pod Security Admission이 [25장](../4부-노출-데이터-운영/25-인증-인가-보안-오토스케일링.md), ResourceQuota·LimitRange가 [19장](../3부-쿠버네티스-핵심/19-리소스-요청-제한과-스케줄링-기초.md) [20장](../3부-쿠버네티스-핵심/20-네임스페이스.md), 프로브가 [16장](../3부-쿠버네티스-핵심/16-Pod-생명주기와-헬스체크.md), 시크릿 관리가 [17장](../3부-쿠버네티스-핵심/17-ConfigMap과-Secret.md)에서 이어진다. 이 책의 나머지가 바로 이 "내 책임" 목록을 채우는 내용이다.

## 실무 적용

### 체크리스트

- [ ] 네 도구의 역할을 구분한다: **Docker**는 이미지를 만들고, **Kubernetes**는 원하는 실행 상태를 유지하며, **EKS**는 AWS가 관리하는 Kubernetes 제어부이고, **Terraform**은 AWS 자원·정책을 코드로 관리한다.
- [ ] Node는 머신, Pod는 배치 단위, 컨테이너 안의 앱은 프로세스다. Pod가 늘어도 EC2가 자동으로 늘지는 않는다. 이를 전제로 용량을 계획한다.
- [ ] 배포 흐름: 코드 → Git → CI(테스트) → Docker 빌드 → 레지스트리(ECR) → CD가 이미지 주소를 Deployment에 반영 → Kubernetes가 노드에서 실행.
- [ ] 이미지 자체가 아니라 **이미지 주소**가 Kubernetes API로 전달된다. 노드가 ECR에서 pull할 권한과 네트워크가 있는지 확인한다.
- [ ] 어떤 push/merge가 workflow를 시작하고 테스트 실패 시 어디서 멈출지 CI/CD 설정으로 연결했는가?
- [ ] 비밀번호·장기 자격 증명을 이미지나 일반 Git 소스에 넣지 않았는가?
- [ ] Terraform은 Pod가 늘 때마다 실행하는 도구가 아니다. 설정의 **소유자**가 Terraform일 때만 변경·apply가 필요하다.
- [ ] 롤백 계획에 DB 데이터·스키마 복구가 포함되어 있는가? (이미지 롤백은 DB를 되돌리지 않는다)
- [ ] 매니지드 서비스는 컨트롤 플레인 운영을 대신할 뿐, RBAC·NetworkPolicy·업그레이드 결정·관측성·백업은 여전히 사용자의 책임이다.
- [ ] 서드파티 앱은 Helm 차트로, 우리 앱의 환경별 설정은 Kustomize로 관리하는 경우가 많고, GitOps는 Git에 선언된 상태로 클러스터를 계속 맞춘다.

### 시나리오로 확인하기

1. **상황:** 이벤트 오픈 30분 전, 게임 API 서버 Deployment의 replicas를 6에서 8로 올렸다. 2개가 `Pending`이다. C++ 서버 시절처럼 "서버가 부족하면 머신을 더 받으면 된다"는 생각에 팀원이 곧바로 `terraform apply`를 돌리자고 한다.
   **질문:** 먼저 무엇을 확인해야 하고, 언제 Terraform이 맞는 답인가?

   <details markdown="1"><summary>답 확인</summary>

   Kubernetes는 원하는 상태(8개)를 기록했지만 scheduler는 EC2를 만들지 않으므로 배치할 곳이 없으면 Pending으로 남는다. 먼저 네 질문을 확인한다. ① Events가 가리키는 부족한 것(배치 용량인지, Pod IP·권한·저장소인지) ② Cluster Autoscaler·Karpenter 같은 조정 프로그램이 있는가 ③ max_size·zone·subnet·IAM·할당량 안에서 해결되는가 ④ 그룹 수량의 소유자가 누구인가. 자동 확장이 없고 Terraform이 수량을 소유할 때만 HCL 변경 → plan → apply다. → 코어 3

   </details>

2. **상황:** 패치 배포 후 버그가 발견되어 이전 이미지로 롤백했다. 그런데 이전 버전 서버가 "알 수 없는 컬럼" 오류를 내기 시작했다.
   **질문:** 왜 롤백으로 해결되지 않았나?

   <details markdown="1"><summary>답 확인</summary>

   rolling update와 롤백은 Deployment의 이미지를 바꿔 새 ReplicaSet으로 Pod를 교체하는 일이다. 이전 이미지로는 돌아가지만 새 버전이 이미 바꾼 DB 데이터와 스키마는 자동 복구되지 않는다. 롤백 계획에 DB 변경의 호환성이나 복구 절차를 따로 넣어야 한다. → 코어 2

   </details>

3. **상황:** 새 이미지를 배포했더니 노드에 이미 배정된 Pod가 `ImagePullBackOff` 상태다. 누군가 "노드가 부족한가 보다, 노드를 늘리자"고 한다.
   **질문:** 노드 추가가 답인가?

   <details markdown="1"><summary>답 확인</summary>

   아니다. 이미 노드에 배정됐다면 배치 용량 문제가 아니라 이미지·pull 권한·네트워크 문제다. 이미지 주소(digest)가 맞는지, 노드 runtime에 ECR 이미지 읽기 권한과 네트워크 접근이 있는지(권한 세 가지 중 세 번째)를 확인한다. → 코어 2, 코어 3

   </details>

4. **상황:** "EKS를 쓰면 AWS가 클러스터를 관리하니 운영 인력은 필요 없다"는 계획서가 올라왔다.
   **질문:** 무엇이 빠졌나?

   <details markdown="1"><summary>답 확인</summary>

   EKS가 맡는 것은 컨트롤 플레인 운영(고가용성, etcd 백업, 보안 패치·업그레이드 실행)이다. 워커 노드는 공유 책임(업그레이드 시점·크기·수량·드레인은 내가 결정)이고, RBAC·NetworkPolicy·ResourceQuota/LimitRange·PSA·애드온 같은 클러스터 설정과 매니페스트·리소스·프로브·이미지 보안·시크릿·관측성·백업 같은 워크로드는 전적으로 내 책임이다. etcd 백업만으로 백업이 끝나지도 않는다. → 코어 4

   </details>

5. **상황:** 보안 감사에서 "CI 서버에 운영 클러스터 자격 증명이 있다"는 지적을 받았다.
   **질문:** 배포 방식을 어떻게 바꿀 수 있나?

   <details markdown="1"><summary>답 확인</summary>

   CI가 `kubectl apply`를 하는 전통적인 push 방식 대신 GitOps(Argo CD, Flux)를 쓰면, 클러스터 안의 에이전트가 Git 저장소를 지켜보며 선언된 상태로 맞추므로 클러스터 자격 증명을 CI 시스템에 두지 않아도 된다. 손으로 바꾼 드리프트도 되돌린다. → 코어 2

   </details>

### 2. 인출 질문

1. EC2 2대에 Pod 4개가 있고 Pod 2개를 더 넣을 여유가 있다. 같은 이미지로 6개를 실행하려면 Docker 재빌드나 EC2 추가가 필요한가?

   <details markdown="1"><summary>답 확인</summary>

   둘 다 필요 없다. 같은 이미지이므로 재빌드할 이유가 없고, 기존 노드에 여유가 있으므로 Deployment replicas만 6으로 바꾸면 된다(EC2는 그대로, Terraform도 불필요). → 코어 3 상황별 판단표

   </details>

2. 배포 도구는 이미지 파일 자체를 Kubernetes에 전달하는가? 노드는 이미지를 어디서 가져오는가?

   <details markdown="1"><summary>답 확인</summary>

   아니다. 배포 도구는 이미지 주소(digest)를 Deployment 설정에 넣을 뿐이고, 노드의 runtime(kubelet/containerd)이 그 주소로 ECR(레지스트리)에서 이미지를 pull한다. Git에는 소스와 설정, ECR에는 빌드한 이미지가 들어간다. → 코어 2

   </details>

3. Pod가 Pending이다. 곧바로 `terraform apply`를 하기 전에 먼저 확인할 것은 무엇인가?

   <details markdown="1"><summary>답 확인</summary>

   네 질문을 확인한다. ① Events가 가리키는 부족한 것이 무엇인가(복제 수·배치 용량·Pod IP·권한·이미지·저장소) ② 그것을 조정할 프로그램(HPA, Cluster Autoscaler, Karpenter 등)이 있는가 ③ 현재 정책(max 수·zone·subnet·IAM·할당량) 안에서 해결되는가 ④ 바꿀 설정의 소유자가 누구인가. Terraform이 소유할 때만 HCL → plan → apply다. → 코어 3

   </details>

4. Node, Pod, 컨테이너 안의 앱은 각각 무엇이며, Pod가 하나 늘면 EC2도 늘어나는가?

   <details markdown="1"><summary>답 확인</summary>

   Node는 실행 장소(이 예시에서 EC2 한 대), Pod는 같은 노드에 함께 배치할 컨테이너를 묶는 배치 단위, 컨테이너 안의 앱은 실제 프로세스다. 한 Node에 여러 Pod가 실행될 수 있고 한 Pod가 여러 EC2에 나뉘지는 않으며, Pod가 늘어도 EC2가 자동으로 늘지는 않는다. → 코어 1

   </details>

5. Kubernetes의 기본 scheduler는 노드가 가득 찼을 때 무엇을 하나? Terraform은 왜 Pod가 늘 때 자동으로 반응하지 않나?

   <details markdown="1"><summary>답 확인</summary>

   scheduler는 EC2 생성 도구가 아니므로 배치할 곳이 없으면 배치가 진행되지 않고 Pod는 Pending으로 남는다(원하는 상태만 기록). Terraform은 일반 CLI 실행이 끝나면 종료되므로 Pod가 늘 때마다 다시 실행되지 않는다. → 코어 1, 코어 3

   </details>

6. 노드 그룹의 `max_size = 5`는 무엇을 뜻하나? HPA나 Cluster Autoscaler가 확장할 때마다 Terraform apply가 필요한가?

   <details markdown="1"><summary>답 확인</summary>

   5대까지 늘릴 수 있다는 상한이지 당장 5대를 만들라는 명령이 아니다. HPA의 replicas 변경이나 허용 범위 안의 CA 노드 추가는 매번 Terraform이 필요 없다. 다만 max를 넘는 용량이 필요하고 그 max를 Terraform이 소유한다면 변경해야 한다. → 코어 3

   </details>

7. 새 버전 배포는 어떻게 이루어지며, 롤백하면 DB도 되돌아가나?

   <details markdown="1"><summary>답 확인</summary>

   Deployment의 이미지를 바꾸면 Deployment controller가 새 ReplicaSet을 만들고 rolling update로 새 Pod를 늘리며 기존 Pod를 줄인다. 기존 컨테이너 파일을 덮어쓰는 방식이 아니다. 롤백으로 이전 이미지로 돌릴 수 있지만 이미 바뀐 DB 데이터와 스키마는 자동 복구되지 않는다. → 코어 2 새 버전 배포

   </details>

8. 매니지드 쿠버네티스(EKS)에서 클라우드가 대신하는 것과 여전히 내 책임인 것은?

   <details markdown="1"><summary>답 확인</summary>

   클라우드는 컨트롤 플레인(API 서버·etcd·스케줄러·컨트롤러 매니저)의 고가용성, etcd 백업, 보안 패치·업그레이드 실행을 맡는다. 워커 노드는 공유 책임(업그레이드 시점·크기·수량·드레인은 내가 결정)이고, RBAC·NetworkPolicy·ResourceQuota·PSA 같은 클러스터 설정과 매니페스트·프로브·시크릿·관측성·백업 같은 워크로드는 전적으로 내 책임이다. → 코어 4

   </details>

9. Helm, Kustomize, GitOps는 각각 어떤 방식이며 GitOps의 보안 이점은?

   <details markdown="1"><summary>답 확인</summary>

   Helm은 차트(템플릿)에 values를 주입해 릴리스로 설치·추적하고 history/rollback을 제공하며 서드파티 앱 설치에 주로 쓴다. Kustomize는 base YAML에 환경별 overlay 패치를 덧씌워 우리 앱의 환경별 설정에 쓴다. GitOps(Argo CD, Flux)는 클러스터 안 에이전트가 Git을 지켜보며 선언된 상태로 맞추고 드리프트도 되돌리며, CI에 클러스터 자격 증명을 두지 않아도 된다. → 코어 2

   </details>

### 3. 기억 고리

- **C++ 유추:** Kubernetes Deployment ≈ 죽은 채널 서버를 다시 띄우는 감시 프로세스. ⚠️ 깨지는 곳: 감시 스크립트는 "띄워라" 명령을 실행하고 끝나지만 Kubernetes는 원하는 상태를 저장하고 계속 맞추는 루프이며, 머신이 모자라면 머신을 사 오지 않고 Pending으로 기다린다.
- **C++ 유추:** 패치 = 실행 파일 덮어쓰기. ⚠️ 깨지는 곳: rolling update는 덮어쓰지 않고 새 Pod로 교체하며, 롤백이 DB까지 되돌리지는 않는다.
- **비유:** Docker = 도시락 공장(이미지 생산), ECR = 창고, Kubernetes = "도시락 6개를 늘 진열해 두라"는 지시를 계속 지키는 매장 관리자, Terraform = 매장 건물과 진열대를 짓는 시공사. ⚠️ 비유가 깨지는 지점: 관리자(scheduler)는 진열대가 꽉 차도 진열대를 새로 짓지 않고 대기(Pending)만 한다. 시공사(Terraform)는 공사를 마치면 떠나므로 다시 부르지 않으면 오지 않는다. 진열하는 것도 도시락 실물이 아니라 창고 주소(digest)를 받은 각 매장(노드)이 직접 가져온다.
- **묶음(3의 법칙):** 실행 계층 3(Node=장소 / Pod=배치 단위 / 컨테이너 앱=프로세스), 배포 흐름 3구간(기반 준비 / 앱 배포 / EKS 안), 권한 3(CI push / CD 배포 / 노드 pull), 세 숫자(replicas / desired_size / min·max), 배포 도구 3(Helm / Kustomize / GitOps).
- **대칭·순서:** `terraform apply` vs `kubectl apply`, replicas 증가(수요) vs Node 증가(공급), Git(소스·설정) vs ECR(이미지), push 방식 CI vs pull 방식 GitOps.
