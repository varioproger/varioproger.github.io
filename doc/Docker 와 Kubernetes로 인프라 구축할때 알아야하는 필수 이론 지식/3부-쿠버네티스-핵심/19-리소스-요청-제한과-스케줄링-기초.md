# 19장. 리소스 요청·제한과 스케줄링 기초

> **🎮 게임 서버 개발자에게** — 서버 머신 사양을 보고 "이 머신에 채널 서버 몇 개를 올릴까"를 정하던 일, 메모리 상한에 걸려 서버가 죽던 일, 스레드 우선순위를 조정하던 일이 여기서 requests·limits·QoS로 바뀐다. 결정적 차이는 둘이다. 첫째, 배치는 **실제 사용량이 아니라 선언한 requests의 합**으로 결정된다. 둘째, 메모리 한도를 넘으면 C++에서처럼 `malloc`이 실패를 돌려주는 대신 커널이 프로세스를 **그 자리에서 죽인다**(OOMKilled, 137). CPU는 한도를 넘어도 기다리게 할 뿐이다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 노드는 한가해 보이는데 새로 띄운 게임 서버 Pod가 `Pending`에서 움직이지 않는다.
> - CPU 사용률은 60%인데 피크 시간에 응답 지연이 100ms 이상 튄다.
> - 서버가 `exitCode 137`로 계속 재시작된다.

## 코어 — 이것만은 100%

> **한 문장:** requests는 스케줄러가 배치에, limits는 커널이 실행 중에 쓰고, 그 조합이 QoS 클래스와 축출 순서를 정하며, CPU는 초과하면 기다리게 하고 메모리는 죽인다는 비대칭이 값 산정의 근거이고, 스케줄러는 필터링·스코어링으로 노드를 고르되 어피니티(Pod가 고름)와 테인트(노드가 거부)로 위치를 제어한다.

1. **requests vs limits** — requests는 스케줄러(requests 합만 보고 실제 사용량은 안 봄), limits는 커널 cgroup(CPU 스로틀링 / OOM Kill).
2. **QoS와 축출** — 모든 컨테이너 requests == limits → Guaranteed, 아무것도 없음 → BestEffort, 나머지 → Burstable. 노드 압박 시 BestEffort → Burstable → Guaranteed 순(약속보다 많이 쓰는 놈부터).
3. **CPU는 대기, 메모리는 죽음** — CPU는 압축 가능해 스로틀링(매 100ms 주기 적용), 메모리는 압축 불가라 OOMKilled(137). 그래서 CPU requests는 평균 근처, 메모리 requests는 피크 근처로 잡는다.
4. **스케줄러와 배치 제어** — 필터링 → 스코어링 → 바인딩. nodeSelector·어피니티는 Pod가 노드를 고르고, 테인트는 노드가 Pod를 거부한다. 전용 노드는 둘을 함께 쓴다.

**이 장의 학습 목표**
- requests와 limits가 각각 스케줄링과 런타임에 미치는 영향을 구분한다. (→ 코어 1)
- 세 가지 QoS 클래스가 어떻게 결정되고 축출 순서에 어떤 영향을 주는지 안다. (→ 코어 2)
- CPU 스로틀링과 메모리 OOMKilled의 비대칭성을 설명할 수 있다. (→ 코어 3)
- 스케줄러가 노드를 고르는 방식과 nodeSelector, affinity, taint/toleration의 기본 개념을 안다. (→ 코어 4)

리소스 값을 **너무 높게** 잡으면 노드가 텅 비어 있는데도 스케줄되지 않아 비용이 낭비되고, **너무 낮게** 잡으면 노드가 과부하되어 Pod들이 서로를 죽인다. 이 장은 그 값을 근거 있게 정하는 이론이다.

## 코어 1. requests는 스케줄러가, limits는 커널이 쓴다

### 1.1 requests와 limits: 완전히 다른 두 값

**한 줄 요약:** requests는 배치 시점에 스케줄러가, limits는 실행 내내 커널(cgroup)이 쓴다.

가장 흔한 오해가 이 둘을 비슷한 것으로 보는 것이다. **전혀 다른 시점에, 전혀 다른 주체가 사용한다.**

| | requests | limits |
|---|---|---|
| 누가 쓰는가 | **스케줄러** | **커널(cgroup)** ([7장](../2부-컨테이너와-Docker/07-자원-제어-cgroups.md)) |
| 언제 쓰는가 | Pod 배치 결정 시 | 실행 내내 |
| 의미 | "이만큼은 보장해 주세요" | "이 이상은 못 씁니다" |
| 초과 가능? | 가능(여유가 있으면) | 불가 |
| 영향 | 어느 노드에 갈지 | CPU 스로틀링 / OOM Kill |

```yaml
resources:
  requests:
    cpu: 100m          # 스케줄러: "이 노드에 100m 여유가 있나?"
    memory: 128Mi
  limits:
    cpu: 500m          # 커널: "이 컨테이너는 최대 0.5 코어"
    memory: 512Mi      # 커널: "512Mi 넘으면 죽인다"
```

### 1.2 스케줄러의 계산과 Allocatable

**한 줄 요약:** 스케줄러는 Allocatable에서 requests 합을 뺀 여유만 보며, 실제 사용률은 보지 않는다.

스케줄러는 **requests의 합**만 본다. 실제 사용량은 보지 않는다.

```
노드 할당 가능(Allocatable): CPU 3.8코어, 메모리 7.2Gi   ← 시스템 예약분 제외
현재 배치된 Pod들의 requests 합: CPU 3.0, 메모리 5Gi
남은 여유: CPU 0.8, 메모리 2.2Gi

새 Pod가 requests.cpu: 1을 요구 → 배치 불가 (0.8 < 1)
```

**실제 CPU 사용률이 5%여도 마찬가지다.** `kubectl describe node`의 "Allocated resources"에서 **Requests의 백분율이 100%에 가까우면 더 이상 스케줄되지 않는다.** Limits는 100%를 넘어도 된다(오버커밋).

노드의 전체 용량(Capacity)에서 `kube-reserved`(kubelet, 런타임용), `system-reserved`(OS용), 축출 임계값 여유분을 뺀 것이 **Allocatable**, 즉 워크로드가 쓸 수 있는 양이다. 예약을 너무 적게 잡으면 워크로드가 노드를 압박해 kubelet이나 런타임이 죽고 노드 전체가 `NotReady`가 될 수 있다.

### 1.3 단위

**한 줄 요약:** CPU는 millicore(`m`), 메모리는 항상 2진 접두사(`Mi`, `Gi`)를 쓴다.

```yaml
cpu: 1        # 1 코어 (= 1000m)
cpu: 100m     # 0.1 코어 (millicore)
memory: 128Mi # 128 * 1024^2 bytes  (권장)
memory: 128M  # 128 * 1000^2 bytes
```

> **`Mi`와 `M`을 혼동하지 말 것.** `1000Mi`는 약 1.05GB, `1000M`은 정확히 1GB다. 항상 `Mi`, `Gi`(2진 접두사)를 쓴다. 임시 스토리지(`ephemeral-storage`)도 제한할 수 있고, 초과하면 Pod가 축출된다.

## 코어 2. QoS 클래스와 축출 — 약속보다 많이 쓰는 놈부터

### 2.1 QoS 클래스

**한 줄 요약:** QoS는 requests/limits 설정으로 자동 결정되며, 모든 컨테이너가 조건을 만족해야 Guaranteed다.

requests/limits 설정에 따라 Pod는 세 등급으로 분류된다. **직접 지정할 수 없고 자동으로 결정된다.**

```
Guaranteed : 모든 컨테이너에 requests와 limits가 있고, CPU·메모리 모두 requests == limits
Burstable  : Guaranteed는 아니지만 최소 하나의 컨테이너에 requests나 limits가 있음
BestEffort : 모든 컨테이너에 requests도 limits도 없음
```

```bash
kubectl get pods -o custom-columns=NAME:.metadata.name,QOS:.status.qosClass
```

> **멀티 컨테이너의 함정** — Pod 안의 **모든** 컨테이너가 조건을 만족해야 Guaranteed다. 사이드카 하나에 resources를 안 쓰면 **Pod 전체가 Burstable**이 된다.

QoS가 결정하는 것:

1. **축출 우선순위**: BestEffort가 가장 먼저, 다음이 Burstable(requests를 초과한 정도가 클수록 먼저), Guaranteed가 마지막.
2. **OOM Score 조정값** (`oom_score_adj`): Guaranteed -997(거의 죽지 않음), Burstable 2&#126;999, BestEffort 1000(가장 먼저 죽음).
3. **CPU 가중치**: cgroup의 CPU 가중치가 requests에 비례한다. CPU 경합 시 requests가 큰 컨테이너가 더 많은 시간을 받는다(100m와 500m는 대략 1:5).

### 2.2 노드 압박과 축출

**한 줄 요약:** 노드 자원이 부족하면 kubelet이 QoS → requests 초과량 → Priority 순으로 Pod를 축출하며, PDB는 이를 막지 못한다.

노드의 자원이 부족해지면 kubelet이 **Pod를 축출(evict)** 해서 노드를 보호한다. 노드 전체가 죽는 것보다 낫기 때문이다. `memory.available`, `nodefs.available`, `pid.available` 등을 감시하며, Hard(즉시 축출)와 Soft(유예 기간 후 축출) 임계값이 있다.

**축출 순서**: ① QoS 클래스(BestEffort → Burstable → Guaranteed) ② 같은 QoS 안에서는 requests를 얼마나 초과했는가 ③ Pod Priority. 원칙은 "**약속(requests)보다 많이 쓰는 놈부터**"다.

```
Reason:  Evicted
Message: The node was low on resource: memory.
         Container app was using 892Mi, which exceeds its request of 128Mi.
```

압박 상태는 노드 컨디션(`MemoryPressure`, `DiskPressure`, `PIDPressure`)으로도 표시된다. `MemoryPressure=True`가 되면 새 BestEffort Pod는 그 노드에 스케줄되지 않는다.

축출을 예방하려면 ① requests를 실제 사용량에 가깝게 설정하고 ② 중요한 워크로드는 Guaranteed로 만들고 ③ 시스템 예약을 넉넉히 잡고 ④ 모니터링과 알림을 건다. 참고로 **PodDisruptionBudget은 노드 압박 축출을 막지 못한다.** PDB는 `kubectl drain` 같은 자발적 중단만 제어하고, kubelet의 자원 부족 축출은 비자발적 중단이기 때문이다.

## 코어 3. CPU는 대기, 메모리는 죽음 — 비대칭이 값 산정의 근거

### 3.1 CPU 스로틀링과 메모리 OOMKilled: 비대칭성

**한 줄 요약:** CPU는 압축 가능해 초과 시 대기시키고, 메모리는 압축 불가라 초과 시 죽인다.

**이 절이 이 장에서 가장 중요하다.** CPU와 메모리는 근본적으로 다르게 동작한다.

| | CPU | 메모리 |
|---|---|---|
| 성질 | **압축 가능**(compressible) | **압축 불가능**(incompressible) |
| 초과 시 | 대기시킨다(스로틀링) | **죽인다**(OOM Kill) |
| 회복 | 자동 | 재시작 필요 |
| 증상 | 응답 지연 | `exitCode 137`, `OOMKilled` |

CPU는 "잠깐 기다려"가 가능하지만, 메모리는 이미 할당된 것을 뺏을 수 없으므로 프로세스를 죽이는 수밖에 없다.

### 3.2 CPU 스로틀링

**한 줄 요약:** `limits.cpu`는 평균이 아니라 매 100ms 주기마다 적용되어, 사용률 100%가 아니어도 지연 스파이크를 만든다.

cgroup은 CFS 대역폭 제어로 CPU를 제한한다. `limits.cpu: 500m`은 **매 100ms 주기마다** 50ms만 CPU를 쓸 수 있다는 뜻이다. 평균이 아니라 매 주기에 적용된다는 것이 함정이다.

```
limits.cpu: 500m → 매 100ms 중 50ms
요청 처리에 30ms CPU가 필요한 앱:
  · 요청 1개 → 30ms → 문제없음
  · 동시 요청 2개 → 60ms 필요 → 50ms에서 스로틀 → 다음 주기까지 대기
  · 결과: 지연 시간이 갑자기 100ms 이상 튄다
```

멀티스레드 앱에서 특히 심각해서, **CPU 사용률이 100%가 아닌데도 지연이 발생**할 수 있다. 컨테이너 안의 `/sys/fs/cgroup/cpu.stat`에서 `nr_throttled / nr_periods`가 스로틀링 비율이고, 이 값이 높으면(원문 기준 5&#126;10% 초과) limits를 올려야 한다.

> **CPU limits를 아예 설정하지 않는 선택** — 일부 조직은 의도적으로 생략한다. CPU는 압축 가능해 초과해도 다른 Pod를 죽이지 않고, 여유 CPU를 활용하며, 스로틀링 지연 스파이크를 없앨 수 있기 때문이다. 반대로 예측 가능성이 떨어지고 한 Pod가 노드의 CPU를 다 쓰면 이웃이 느려진다. 절충안은 지연에 민감한 서비스는 limits 없이(또는 넉넉하게), 배치 워크로드는 limits를 거는 것이다. ResourceQuota가 있는 환경에서는 limits가 필수이므로 넉넉한 limits가 현실적이다([20장](20-네임스페이스.md)).

### 3.3 메모리 OOMKilled

**한 줄 요약:** 메모리 한도를 넘으면 커널이 죽이며(137), 노드 OOM은 훨씬 위험하고, 런타임 힙 설정은 한도보다 작게 둬야 한다.

메모리를 limits 이상 쓰면 커널이 프로세스를 죽인다. `lastState.terminated`에 `exitCode: 137`, `reason: OOMKilled`가 남는다([16장](16-Pod-생명주기와-헬스체크.md)).

| 종류 | 원인 | 영향 범위 |
|---|---|---|
| cgroup OOM | 컨테이너가 자기 `limits.memory` 초과 | 그 컨테이너만 |
| 노드 OOM | 노드 전체 메모리 고갈 | 여러 Pod, 심하면 kubelet까지 |

노드 OOM이 훨씬 위험하며, 코어 2의 축출이 이를 예방하기 위해 존재한다.

**JVM의 함정.** 힙만 limits와 같게(`-Xmx2g`, limits 2Gi) 잡으면 JVM은 힙 외에 메타스페이스, 코드 캐시, 스레드 스택, 다이렉트 버퍼, GC 오버헤드 등도 쓰므로 실제로는 limits를 넘어 OOMKilled 된다. `-XX:MaxRAMPercentage=70.0`처럼 컨테이너 한도 비율로 힙을 설정하거나, [17장](17-ConfigMap과-Secret.md)의 Downward API(`resourceFieldRef`)로 한도를 전달한다. Node.js도 `--max-old-space-size`를 limits보다 작게 둬야 한다.

### 3.4 실습으로 확인하는 비대칭

**한 줄 요약:** CPU 초과는 `nr_throttled`만 늘리고, 메모리 초과는 한도 근처에서 `OOMKilled`로 끝난다.

실습으로 재현할 수 있다. 4개의 무한 루프 프로세스를 `limits.cpu: 200m` Pod에서 돌리면 `nr_throttled`가 거의 모든 주기에서 증가하지만 **컨테이너는 죽지 않는다.** 10MB씩 메모리를 할당하는 프로그램을 `limits.memory: 128Mi` Pod에서 돌리면 110MB 근처에서 `OOMKilled`로 죽는다. **CPU는 대기시키고 메모리는 죽인다.**

### 3.5 적정값 산정

**한 줄 요약:** 관측 → 산정 → 검증으로 정하며, CPU requests는 평균 근처, 메모리 requests는 피크 근처로 잡는다.

**데이터 없이 감으로 정하지 말 것.** 절차는 관측 → 산정 → 검증이다.

- **관측**: `kubectl top pods --containers`(metrics-server 필요), 장기 데이터는 Prometheus.
- **산정 공식**(원문 제시)

  ```
  requests.cpu    = P50 ~ P70 사용량
  limits.cpu      = P95 ~ P99 x 1.5 (또는 설정하지 않음)
  requests.memory = P95 사용량 x 1.1
  limits.memory   = 최대 사용량 x 1.2 ~ 1.5
  ```

  CPU는 초과해도 스로틀링만 되므로 requests를 평균 근처로 잡아 밀도를 높이고, 메모리는 초과하면 죽으므로 requests를 피크에 가깝게 잡아 안전하게 간다.

| 워크로드 유형 | requests | limits | QoS 목표 |
|---|---|---|---|
| 지연 민감 API | 평균의 1.2배 | CPU 없음/넉넉히, 메모리 피크x1.3 | Burstable |
| 핵심 상태 저장(DB) | 피크 수준 | requests와 동일 | **Guaranteed** |
| 배치/워커 | 평균 | 넉넉히 | Burstable |

- **VPA(Vertical Pod Autoscaler)를 `updateMode: "Off"`(추천만)로 돌리면** 적용하지 않고 추천값만 받는 좋은 산정 도구가 된다.
- **오버커밋**: CPU 오버커밋은 안전하다(경합해도 스로틀링뿐, 2&#126;4배도 흔함). **메모리 오버커밋은 위험하다**(모든 Pod가 limits까지 쓰면 노드 OOM). 원문은 1.2&#126;1.5배 이내를 권한다.

## 코어 4. 스케줄러와 배치 제어 — Pod가 고르고, 노드가 거부한다

### 4.1 스케줄러가 노드를 고르는 방식

**한 줄 요약:** 필터링(가능한가) → 스코어링(어디가 좋은가) → 바인딩이며, 실패하면 `FailedScheduling`이 노드별 제외 이유를 알려 준다.

kube-scheduler는 `spec.nodeName`이 비어 있는 Pod를 발견하면 두 단계를 거친다.

```
① 필터링: "이 노드에 배치 가능한가?" (requests 만족, 어피니티, 테인트, 볼륨 등) — 예/아니오
② 스코어링: "어느 노드가 더 좋은가?" (자원 균형, 이미지가 이미 있나 등) — 0~100점
③ 바인딩: 최고 점수 노드를 골라 spec.nodeName 설정
```

필터링에서 아무 노드도 남지 않으면 Pod는 `Pending`이 되고 이벤트에 이유가 남는다.

```
Warning  FailedScheduling  0/5 nodes are available:
  2 Insufficient cpu,
  1 node(s) had untolerated taint {gpu: true},
  2 node(s) didn't match Pod's node affinity/selector.
```

각 숫자가 어떤 이유로 몇 개 노드가 제외됐는지 알려 주므로, 이 메시지를 읽는 법이 진단의 핵심이다. (실제로는 모든 노드를 평가하지 않고 충분히 좋은 노드를 빠르게 찾는다.)

### 4.2 nodeSelector

**한 줄 요약:** 노드 라벨과 정확히 일치(모두 AND)하는 노드에만 배치하는 가장 단순한 방법이다.

가장 단순한 방법이다. 노드에 라벨을 붙이고 Pod에서 일치를 요구한다. 모든 조건이 AND이고 정확히 일치해야 한다.

```bash
kubectl label node k8s-guide-worker disktype=ssd
```
```yaml
spec:
  nodeSelector:
    disktype: ssd
```

클라우드 환경에서는 `kubernetes.io/hostname`, `kubernetes.io/os`, `kubernetes.io/arch`, `topology.kubernetes.io/zone` 같은 내장 노드 라벨이 자동으로 붙는다.

### 4.3 노드 어피니티와 Pod 어피니티

**한 줄 요약:** 노드 어피니티는 required/preferred와 연산자를 갖춘 nodeSelector 확장판이고, Pod (안티)어피니티는 다른 Pod의 위치를 기준으로 한다.

**노드 어피니티**는 nodeSelector의 확장판이다. `required...`(필수, 만족하지 않으면 스케줄 안 됨)와 `preferred...`(선호, 만족하면 좋지만 아니어도 됨) 두 종류가 있고, `In`, `NotIn`, `Exists` 같은 연산자를 쓴다. 이름 끝의 `IgnoredDuringExecution`은 **스케줄링 시점에만 검사하고 실행 중에는 무시한다**는 뜻이다. 노드 라벨이 나중에 바뀌어도 실행 중인 Pod는 쫓겨나지 않는다.

**Pod 어피니티/안티어피니티**는 노드 속성이 아니라 **다른 Pod의 위치**를 기준으로 한다. `topologyKey`가 "같은 곳"의 정의(같은 노드 `kubernetes.io/hostname`, 같은 AZ `topology.kubernetes.io/zone` 등)를 결정한다.

- 고가용성을 위한 분산은 `preferred` 안티어피니티를 쓴다. `required`로 하면 노드 수보다 많은 replica를 만들 수 없다(노드 3개에 replica 5개면 2개가 영원히 Pending).
- 데이터베이스 복제본처럼 같은 노드에 있으면 안 되는 경우는 `required`가 맞다.
- Pod 어피니티는 계산 비용이 커서, 수백 노드 이상 클러스터에서는 주의가 필요하다.

### 4.4 테인트와 톨러레이션

**한 줄 요약:** 테인트는 노드가 Pod를 거부하는 것이고, 톨러레이션은 "허가"일 뿐 "지시"가 아니다.

어피니티가 **Pod가 노드를 고르는** 것이라면, 테인트는 **노드가 Pod를 거부하는** 것이다.

```
테인트(Taint)         : 노드에 붙인다. "나는 이런 Pod만 받는다"
톨러레이션(Toleration): Pod에 붙인다. "나는 그 조건을 견딜 수 있다"
```

```bash
kubectl taint nodes node-1 gpu=true:NoSchedule      # 추가
kubectl taint nodes node-1 gpu=true:NoSchedule-     # 제거 (끝에 하이픈)
```

| effect | 동작 |
|---|---|
| `NoSchedule` | 톨러레이션 없는 Pod는 새로 배치되지 않음. 기존 Pod는 유지 |
| `PreferNoSchedule` | 가능하면 피하지만 다른 곳이 없으면 배치 |
| `NoExecute` | 기존 Pod도 축출 |

```yaml
spec:
  tolerations:
    - key: gpu
      operator: Equal
      value: "true"
      effect: NoSchedule
```

> **톨러레이션은 "허가"이지 "지시"가 아니다.** GPU 노드에 테인트를 걸고 GPU Pod에 톨러레이션을 줘도, 그 Pod는 일반 노드에도 갈 수 있다. 전용 노드 풀에는 **테인트(다른 Pod를 막는다) + 노드 어피니티(이 Pod를 유도한다)를 함께** 써야 한다.

쿠버네티스가 자동으로 붙이는 내장 테인트도 있다(`not-ready`, `unreachable`, `memory-pressure`, `unschedulable`(`kubectl cordon`) 등). 모든 Pod에는 `not-ready`/`unreachable` 테인트에 대한 `tolerationSeconds: 300` 톨러레이션이 자동 추가되므로, **노드 장애 시 Pod가 5분 후에 옮겨진다.** 일시적 네트워크 문제로 성급히 옮기지 않기 위한 설계다. 컨트롤 플레인 노드에 일반 Pod가 배치되지 않는 것도 `node-role.kubernetes.io/control-plane:NoSchedule` 테인트 때문이다. [18장](18-워크로드-컨트롤러.md)에서 본 DaemonSet이 모든 노드에 뜨려면 이 톨러레이션이 필요하다.

### 4.5 스케줄링 문제 진단

**한 줄 요약:** `FailedScheduling` 메시지의 문구마다 원인과 대응이 정해져 있다.

| 메시지 | 원인 | 대응 |
|---|---|---|
| `Insufficient cpu/memory` | requests를 만족할 여유 없음 | requests 낮추기, 노드 추가 |
| `had untolerated taint` | 테인트에 막힘 | toleration 추가 |
| `didn't match Pod's node affinity/selector` | 어피니티 불만족 | 노드 라벨 확인 |
| `had volume node affinity conflict` | 볼륨과 노드의 AZ 불일치 | 스토리지 설정 확인 |
| `didn't match pod anti-affinity rules` | 안티어피니티 충돌 | `required` → `preferred` |
| `unschedulable` | cordon 상태 | `kubectl uncordon` |
| `Too many pods` | 노드의 Pod 수 상한(기본 110) | 노드 추가 |

## 실무 적용

### 체크리스트

- [ ] **requests는 스케줄러가, limits는 커널이 쓴다.** 스케줄러는 requests 합만 보고 실제 사용량은 보지 않는다. Pending이면 `kubectl describe node`의 Allocated resources(Requests 백분율)부터 본다. (→ 코어 1)
- [ ] 메모리 단위는 항상 `Mi`/`Gi`를 쓴다. (→ 코어 1)
- [ ] **QoS 클래스는 자동 결정된다.** 모든 컨테이너에서 requests == limits면 Guaranteed, 아무것도 없으면 BestEffort, 나머지는 Burstable. 사이드카 하나가 resources를 빠뜨리면 Pod 전체가 Burstable이 된다. (→ 코어 2)
- [ ] 노드 압박 시 축출 순서는 **BestEffort → Burstable → Guaranteed**. PDB는 이를 막지 못한다. 중요한 워크로드는 Guaranteed로, 시스템 예약은 넉넉히. (→ 코어 2)
- [ ] **CPU는 압축 가능(스로틀링), 메모리는 압축 불가능(OOMKilled).** 이 비대칭성이 설계 판단의 근거다. 지연 스파이크가 있으면 `cpu.stat`의 `nr_throttled / nr_periods`를 확인한다. (→ 코어 3)
- [ ] 힙을 가진 런타임(JVM, Node.js)은 힙 상한을 limits보다 작게(비율 또는 Downward API) 둔다. (→ 코어 3)
- [ ] 적정값은 관측 → 산정 → 검증으로 정하며, CPU 오버커밋은 안전하고 메모리 오버커밋은 위험하다. (→ 코어 3)
- [ ] 스케줄러는 **필터링 → 스코어링 → 바인딩**. `FailedScheduling` 메시지를 읽으면 원인을 안다. (→ 코어 4)
- [ ] nodeSelector/어피니티는 **Pod가 노드를 고르는** 도구, 테인트/톨러레이션은 **노드가 Pod를 거부하는** 도구이며, 전용 노드에는 둘을 함께 쓴다. 고가용성 분산은 `preferred` 안티어피니티로. (→ 코어 4)

1. **상황:** 이벤트 오픈 전에 게임 서버 Pod를 늘렸는데 새 Pod가 `Pending`이다. 모니터링상 노드 CPU 사용률은 10%도 안 된다. C++ 시절 습관대로 "머신이 놀고 있으니 더 올릴 수 있다"고 판단했었다.
   **질문:** 왜 배치되지 않나?

   <details markdown="1"><summary>답 확인</summary>

   스케줄러는 실제 사용량이 아니라 Allocatable에서 이미 배치된 Pod들의 requests 합을 뺀 여유만 본다. requests가 실사용보다 크게 잡혀 있으면 사용률이 낮아도 `Insufficient cpu`로 필터링된다. `kubectl describe pod`의 `FailedScheduling` 메시지와 `kubectl describe node`의 Allocated resources를 확인하고, 관측 데이터로 requests를 실제 사용량(CPU는 P50~P70)에 맞추거나 노드를 추가한다. → 코어 1, 코어 3

   </details>

2. **상황:** 멀티스레드 게임 서버에 `limits.cpu: 500m`을 걸었다. 평균 CPU 사용률은 낮은데 전투가 몰리는 순간 응답이 100ms 이상 튄다.
   **질문:** 원인과 확인 방법, 대응은?

   <details markdown="1"><summary>답 확인</summary>

   CFS 대역폭 제어는 매 100ms 주기마다 50ms만 쓰게 한다. 여러 스레드가 동시에 일하면 주기 초반에 할당량을 소진해 다음 주기까지 대기하므로, 평균 사용률이 낮아도 지연 스파이크가 난다. 컨테이너 안 `/sys/fs/cgroup/cpu.stat`의 `nr_throttled / nr_periods`가 높으면(원문 기준 5~10% 초과) limits를 올리거나, 지연 민감 서비스라면 CPU limits를 없애거나 넉넉하게 둔다(ResourceQuota 환경이면 넉넉한 limits). → 코어 3

   </details>

3. **상황:** 서버가 부하 테스트 중 `exitCode 137`, `OOMKilled`로 재시작을 반복한다. 코드에는 할당 실패(`nullptr`, `std::bad_alloc`) 처리 로직이 다 있는데 로그에 아무것도 남지 않았다.
   **질문:** 왜 할당 실패 처리가 동작하지 않았나? 무엇을 봐야 하나?

   <details markdown="1"><summary>답 확인</summary>

   메모리는 압축 불가능한 자원이라, 컨테이너가 `limits.memory`를 넘으면 커널이 프로세스를 죽인다(cgroup OOM). 실패를 돌려받아 처리할 기회 없이 종료되므로 앱 로그가 남지 않고 `lastState.terminated`에 `exitCode: 137`, `reason: OOMKilled`만 남는다. 관측한 최대 사용량 기준으로 `limits.memory`(최대 x 1.2~1.5)와 requests(P95 x 1.1)를 다시 잡고, 런타임이 있는 언어라면 힙 상한을 limits보다 작게 둔다. 실제 누수라면 코드를 고쳐야 한다. → 코어 3

   </details>

4. **상황:** 핵심 서버의 메인 컨테이너는 requests == limits로 맞췄는데, 노드 메모리가 부족해질 때 이 Pod가 다른 Pod보다 먼저 축출된다. Pod에는 resources를 쓰지 않은 로그 사이드카가 붙어 있다.
   **질문:** 왜인가?

   <details markdown="1"><summary>답 확인</summary>

   모든 컨테이너가 조건을 만족해야 Guaranteed다. 사이드카 하나에 resources가 없으면 Pod 전체가 Burstable이 되어, 축출 순서(BestEffort → Burstable → Guaranteed)와 `oom_score_adj`에서 불리해진다. 사이드카에도 requests == limits를 지정한다. PDB로는 이 축출을 막을 수 없다. → 코어 2

   </details>

5. **상황:** GPU 노드에 `gpu=true:NoSchedule` 테인트를 걸고 매치메이킹 AI Pod에 톨러레이션을 줬다. 그런데 AI Pod 일부가 일반 노드에 떠 있다. 또, 같은 서버 5개를 3노드에 분산하려고 `required` 안티어피니티를 걸었더니 2개가 계속 Pending이다.
   **질문:** 각각 무엇이 잘못됐나?

   <details markdown="1"><summary>답 확인</summary>

   톨러레이션은 "허가"이지 "지시"가 아니어서 AI Pod는 일반 노드에도 갈 수 있다. 테인트(다른 Pod를 막음) + 노드 어피니티 또는 nodeSelector(이 Pod를 GPU 노드로 유도)를 함께 써야 한다. `required` 안티어피니티는 노드 수보다 많은 replica를 만들 수 없게 하므로(노드 3개에 replica 5개면 2개가 영원히 Pending), 고가용성 분산에는 `preferred`를 쓴다. → 코어 4

   </details>

### 2. 인출 질문

1. 노드 CPU 사용률이 5%밖에 안 되는데 새 Pod가 `Pending`인 이유를 requests 관점에서 설명해 보라. (확인 질문 1)

   <details markdown="1"><summary>답 확인</summary>

   스케줄러는 실제 사용량이 아니라 노드 Allocatable에서 이미 배치된 Pod들의 **requests 합**을 뺀 여유만 본다. requests 합이 Allocatable에 가까우면(Allocated resources의 Requests 백분율이 100%에 근접) 실제 사용률이 5%여도 새 Pod의 requests를 만족할 수 없어 `Insufficient cpu`로 Pending이 된다. → 코어 1

   </details>

2. 같은 limits를 초과했을 때 CPU와 메모리는 각각 어떻게 되며, 왜 다르게 동작하는가? (확인 질문 2)

   <details markdown="1"><summary>답 확인</summary>

   CPU는 압축 가능한 자원이라 "잠깐 기다려"가 가능해 스로틀링(지연)만 되고 컨테이너는 죽지 않는다. 메모리는 압축 불가능해 이미 할당된 것을 뺏을 수 없으므로 커널이 프로세스를 죽인다(`exitCode 137`, `OOMKilled`). → 코어 3

   </details>

3. GPU 노드에 테인트를 걸고 GPU Pod에 톨러레이션만 줬을 때 부족한 점은 무엇이며 어떻게 보완하는가? (확인 질문 3)

   <details markdown="1"><summary>답 확인</summary>

   톨러레이션은 "허가"이지 "지시"가 아니므로 GPU Pod가 일반 노드에도 배치될 수 있다. 테인트로 다른 Pod를 막고, 노드 어피니티(또는 nodeSelector)로 이 Pod를 GPU 노드로 유도하는 것을 함께 써야 전용 노드 풀이 된다. → 코어 4

   </details>

4. QoS 클래스 세 가지의 결정 조건과, 사이드카 하나에 resources를 빠뜨리면 생기는 일은?

   <details markdown="1"><summary>답 확인</summary>

   모든 컨테이너에 requests와 limits가 있고 CPU·메모리 모두 requests == limits면 Guaranteed, 모든 컨테이너에 아무것도 없으면 BestEffort, 그 외는 Burstable이다. 직접 지정할 수 없고 자동 결정되며, 모든 컨테이너가 조건을 만족해야 하므로 사이드카 하나에 resources가 없으면 Pod 전체가 Burstable이 된다. → 코어 2

   </details>

5. `limits.cpu: 500m`인 앱이 CPU 사용률 100%가 아닌데도 지연 스파이크를 겪는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   CFS 대역폭 제어는 평균이 아니라 매 100ms 주기마다 50ms만 쓰게 한다. 요청당 30ms가 필요한 앱에 동시 요청 2개가 오면 60ms가 필요해 50ms에서 스로틀되고 다음 주기까지 대기해 지연이 100ms 이상 튄다. 멀티스레드 앱에서 특히 심하며 `cpu.stat`의 `nr_throttled / nr_periods`로 확인한다. → 코어 3

   </details>

6. JVM 앱에서 `-Xmx2g`, limits 2Gi로 두면 왜 OOMKilled 되며 어떻게 고치나?

   <details markdown="1"><summary>답 확인</summary>

   JVM은 힙 외에도 메타스페이스, 코드 캐시, 스레드 스택, 다이렉트 버퍼, GC 오버헤드 등을 쓰므로 실제 사용량이 limits를 넘는다. `-XX:MaxRAMPercentage=70.0`처럼 컨테이너 한도 비율로 힙을 정하거나 Downward API(`resourceFieldRef`)로 한도를 전달한다. → 코어 3

   </details>

7. 노드 압박 시 축출 순서와, PDB가 이를 막지 못하는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   ① QoS(BestEffort → Burstable → Guaranteed) ② 같은 QoS 안에서는 requests를 얼마나 초과했는가 ③ Pod Priority 순이다("약속보다 많이 쓰는 놈부터"). PDB는 `kubectl drain` 같은 자발적 중단만 제어하고, kubelet의 자원 부족 축출은 비자발적 중단이라 막지 못한다. → 코어 2

   </details>

8. CPU와 메모리의 requests 산정 방식이 다른 이유와, 오버커밋의 안전성 차이는?

   <details markdown="1"><summary>답 확인</summary>

   CPU는 초과해도 스로틀링뿐이라 requests를 P50&#126;P70 근처로 잡아 밀도를 높이고, 메모리는 초과하면 죽으므로 requests를 P95 x 1.1처럼 피크 가까이 잡는다. 같은 이유로 CPU 오버커밋은 안전하고(2&#126;4배도 흔함), 메모리 오버커밋은 모든 Pod가 limits까지 쓰면 노드 OOM이 나므로 위험하다(1.2&#126;1.5배 이내). → 코어 3

   </details>

9. 스케줄러가 노드를 고르는 단계와, `FailedScheduling` 메시지를 읽는 법은?

   <details markdown="1"><summary>답 확인</summary>

   ① 필터링(배치 가능한가: requests, 어피니티, 테인트, 볼륨 등) ② 스코어링(어느 노드가 더 좋은가: 자원 균형, 이미지 존재 등) ③ 바인딩(최고 점수 노드의 이름을 `spec.nodeName`에 설정). 필터링에서 남는 노드가 없으면 Pending이 되고, `0/5 nodes are available: 2 Insufficient cpu, 1 ... untolerated taint ...`처럼 이유별로 몇 개 노드가 제외됐는지 알려 준다. → 코어 4

   </details>

10. Pod 안티어피니티를 `required`로 걸면 생길 수 있는 문제는?

    <details markdown="1"><summary>답 확인</summary>

    노드 수보다 많은 replica를 만들 수 없다. 노드 3개에 replica 5개면 2개가 영원히 Pending이다. 고가용성 분산에는 `preferred`를 쓰고, DB 복제본처럼 같은 노드에 있으면 안 되는 경우에만 `required`를 쓴다. → 코어 4

    </details>

11. 노드가 장애 나도 Pod가 바로 옮겨지지 않고 5분 뒤 옮겨지는 이유는?

    <details markdown="1"><summary>답 확인</summary>

    모든 Pod에 `not-ready`/`unreachable` 내장 테인트에 대한 `tolerationSeconds: 300` 톨러레이션이 자동 추가되기 때문이다. 일시적 네트워크 문제로 성급히 옮기지 않기 위한 설계다. → 코어 4

    </details>

### 3. 기억 고리

- **C++ 유추:** `limits.memory` ≈ `setrlimit` 메모리 상한, `limits.cpu` ≈ 스레드 우선순위 조정. ⚠️ 깨지는 곳: 메모리 한도를 넘으면 `malloc` 실패가 아니라 커널이 즉시 죽이고(137), `limits.cpu`는 우선순위가 아니라 매 100ms 주기의 시간 상한이라 여유 CPU가 있어도 멈춘다.
- **비유:** requests = 식당 좌석 예약, limits = 1인 최대 주문량. 지배인(스케줄러)은 예약 장부만 보고 자리를 배정하므로 홀이 텅 비어 보여도 예약이 꽉 차면 손님을 못 받는다. ⚠️ 비유가 깨지는 지점: CPU 한도를 넘으면 "잠시 기다리게" 하지만, 메모리 한도를 넘으면 손님을 내보내는 정도가 아니라 프로세스를 그 자리에서 죽인다(OOMKilled). 또 예약(requests)은 초과해서 쓸 수 있지만 한도(limits)는 넘을 수 없다.
- **묶음(3의 법칙):** QoS 3등급(Guaranteed·Burstable·BestEffort) / 스케줄러 3단계(필터링·스코어링·바인딩) / 테인트 effect 3종(NoSchedule·PreferNoSchedule·NoExecute) / 축출 기준 3개(QoS·requests 초과량·Priority).
- **대칭·순서:** requests(스케줄러·배치 시) ↔ limits(커널·실행 내내), CPU(압축 가능·대기) ↔ 메모리(압축 불가·죽음), 어피니티(Pod가 노드를 고름) ↔ 테인트(노드가 Pod를 거부), required(필수) ↔ preferred(선호).
