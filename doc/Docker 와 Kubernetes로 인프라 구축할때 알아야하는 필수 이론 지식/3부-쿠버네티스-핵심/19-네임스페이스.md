# 19장. 네임스페이스 — 역할, 한계, ResourceQuota, LimitRange

## 이 장에서 배우는 것

- 네임스페이스가 제공하는 것과 제공하지 못하는 것을 정확히 구분한다.
- ResourceQuota로 네임스페이스의 자원 총량을 통제하는 방법을 안다.
- LimitRange로 컨테이너별 기본값과 상하한을 강제하는 방법을 안다.
- 같은 조직 팀 분리(소프트)와 신뢰할 수 없는 테넌트 분리(하드)의 차이를 이해한다.

여러 팀이 하나의 클러스터를 나눠 쓰면 "A팀의 실수가 B팀을 죽이지 않게", "한 팀이 자원을 독차지하지 못하게" 같은 질문이 생긴다. 네임스페이스는 그 출발점이다.

---

## 1. 네임스페이스의 역할

```bash
kubectl get namespaces
```

| 네임스페이스 | 용도 |
|---|---|
| `default` | 지정하지 않았을 때의 기본 |
| `kube-system` | 시스템 컴포넌트(건드리지 말 것) |
| `kube-public` | 인증 없이 읽을 수 있는 리소스(거의 안 씀) |
| `kube-node-lease` | 노드 하트비트용 Lease 오브젝트 |

네임스페이스가 제공하는 것은 네 가지다.

1. **이름 스코프** — 같은 이름의 리소스를 여러 네임스페이스에 만들 수 있다(`dev/web-service`, `prod/web-service`).
2. **DNS 스코프** — DNS 이름에 네임스페이스가 들어간다(`web.dev.svc.cluster.local`). 같은 네임스페이스 안에서는 짧은 이름으로 부를 수 있다.
3. **RBAC 경계** — Role과 RoleBinding은 네임스페이스에 속한다. "dev에서만 Pod를 만들 수 있는" 역할을 정의할 수 있다.
4. **리소스 쿼터의 단위** — ResourceQuota는 네임스페이스마다 적용된다.

(13장에서 본 대로 Node, PersistentVolume, StorageClass, ClusterRole 등은 네임스페이스에 속하지 않는 클러스터 전역 리소스다.)

## 2. 네임스페이스가 하지 못하는 일

> **네임스페이스는 보안 경계가 아니다.** 이름 정리와 권한 그룹화를 위한 것이지 격리를 위한 것이 아니다.

- **네트워크는 기본적으로 열려 있다.** `dev`의 Pod에서 `curl http://web.prod.svc.cluster.local`이 **연결된다.** 모든 Pod는 모든 Pod와 통신할 수 있다. 막으려면 NetworkPolicy가 필요하다.
- **노드는 공유된다.** 여러 네임스페이스의 Pod가 같은 노드에서 돈다. 같은 커널을 공유하고, CPU/메모리를 경쟁하며, `hostPath`가 있으면 다른 Pod의 데이터까지 볼 수 있다.
- **클러스터 전역 리소스는 공유된다.** CRD를 설치하면 모든 네임스페이스에 영향을 준다.
- **컨트롤 플레인은 하나다.** 한 팀이 API 서버에 부하를 주면 모두가 느려지고, etcd가 가득 차면 클러스터 전체가 멈춘다.

```
네임스페이스가 주는 것:  이름 정리, RBAC 그룹, 쿼터 단위, DNS 스코프
추가로 필요한 것:
  · 네트워크 격리 → NetworkPolicy
  · 자원 격리     → ResourceQuota + LimitRange (이 장)
  · 노드 격리     → 테인트 + 어피니티 (18장)
  · 커널 격리     → 샌드박스 런타임
  · 권한 격리     → RBAC
```

### 관리 명령

```bash
kubectl create namespace team-a
kubectl config set-context --current --namespace=team-a   # 기본 네임스페이스 변경
kubectl delete namespace team-a                           # 안의 모든 리소스가 함께 삭제
```

> **네임스페이스 삭제는 되돌릴 수 없다.** 안의 모든 리소스(Deployment, Service, PVC, Secret 등)가 사라진다. PVC에 연결된 볼륨의 `reclaimPolicy`가 `Delete`라면(PV/StorageClass에 지정, 23장) 데이터까지 사라진다. `Terminating`에서 멈추는 경우는 13장에서 본 파이널라이저 문제다.

## 3. ResourceQuota: 네임스페이스 총량 제한

네임스페이스 전체가 소비할 수 있는 자원의 총량을 정한다.

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-a-quota
  namespace: team-a
spec:
  hard:
    requests.cpu: "20"
    requests.memory: 40Gi
    limits.cpu: "40"
    limits.memory: 80Gi
    requests.storage: 500Gi
    persistentvolumeclaims: "20"
    pods: "100"
    services: "20"
    services.loadbalancers: "2"      # 비용 통제에 중요
    services.nodeports: "5"
    configmaps: "50"
    secrets: "50"
    count/deployments.apps: "30"
```

`services.loadbalancers`를 제한하는 이유는 LoadBalancer Service 하나당 클라우드 LB 하나가 생기고 요금이 부과되기 때문이다. `count/<resource>.<group>` 형식으로 임의 리소스의 개수도 제한할 수 있다.

```bash
kubectl describe resourcequota team-a-quota -n team-a
# Resource   Used   Hard
# pods       18     100
# requests.cpu  6   20
```

### 가장 중요한 규칙

> **컴퓨트 쿼터가 있으면 모든 컨테이너가 requests/limits를 명시해야 한다.** ResourceQuota에 `requests.cpu`나 `limits.memory`가 있으면 해당 값을 지정하지 않은 Pod는 **생성이 거부된다.**
>
> ```
> Error from server (Forbidden): pods "web" is forbidden: failed quota: team-a-quota:
> must specify limits.cpu for: app; limits.memory for: app; ...
> ```
>
> 이것은 버그가 아니라 의도된 동작이다(쿼터를 계산하려면 각 Pod가 얼마를 쓸지 알아야 하므로). **해결책은 LimitRange로 기본값을 주는 것이다.** 이 둘은 거의 항상 함께 쓴다.

### scopeSelector, 쿼터 초과 시 동작

`scopes`(`BestEffort`, `NotBestEffort`, `Terminating`, `PriorityClass` 등)를 지정하면 특정 조건의 Pod에만 쿼터를 적용할 수 있다. 예를 들어 `PriorityClass`가 `high-priority`인 Pod에만 쿼터를 걸면 팀이 높은 우선순위를 남발하는 것을 막는다.

**쿼터 초과 시 Pod 생성이 거부된다.** 이미 실행 중인 Pod는 영향받지 않는다. 주의할 점은 Deployment/ReplicaSet이 **계속 재시도**한다는 것이다. 이벤트를 보지 않으면 "왜 스케일이 안 되지?"라고 한참 헤맬 수 있다.

```bash
kubectl describe replicaset <name>
# Warning  FailedCreate  Error creating: pods "web-abc" is forbidden:
#   exceeded quota: team-a-quota, requested: requests.cpu=2, used: requests.cpu=19, limited: requests.cpu=20
```

## 4. LimitRange: 개별 컨테이너 기본값과 범위

ResourceQuota가 총량이라면, LimitRange는 **개별 컨테이너/Pod/PVC** 수준에서 동작한다.

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: team-a-limits
  namespace: team-a
spec:
  limits:
    - type: Container
      default:                  # ① limits 기본값
        cpu: 500m
        memory: 512Mi
      defaultRequest:           # ② requests 기본값
        cpu: 100m
        memory: 128Mi
      min:                      # ③ 최솟값 (이보다 작으면 거부)
        cpu: 10m
        memory: 32Mi
      max:                      # ④ 최댓값 (이보다 크면 거부)
        cpu: "4"
        memory: 8Gi
      maxLimitRequestRatio:     # ⑤ limits/requests 비율 상한
        memory: "4"
```

- **`default` / `defaultRequest`**: 컨테이너에 `resources`를 안 쓰면 어드미션 단계에서 이 값이 자동 주입된다. 개발자가 아무것도 쓰지 않아도 requests와 limits가 채워지므로, **ResourceQuota와 함께 쓸 때 필수적이다.**
- **`min` / `max`**: 범위를 강제한다(예: `maximum memory usage per Container is 8Gi, but limit is 16Gi`). 한 컨테이너가 노드 전체를 차지하는 것을 막는다.
- **`maxLimitRequestRatio`**: 오버커밋을 제한한다. `memory: "4"`이면 `requests: 1Gi, limits: 8Gi`(비율 8)는 거부된다. requests가 낮고 limits가 높으면 스케줄러는 "조금만 쓴다"고 판단해 많이 배치하는데 실제로는 limits까지 쓸 수 있어 노드가 과부하되기 때문이다(18장).

## 5. 실습 시나리오: 쿼터와 리밋

네임스페이스에 LimitRange(기본값 200m/256Mi, 최댓값 1 CPU/1Gi)와 ResourceQuota(`requests.cpu: "1"`, `pods: "10"`, `services.loadbalancers: "0"`)를 적용하면 다음을 확인할 수 있다.

| 행동 | 결과 |
|---|---|
| `kubectl run nginx -n team-a`(resources 미지정) | LimitRange가 requests/limits를 자동 주입 |
| limits.memory 4Gi를 요구하는 Pod | `maximum memory usage per Container is 1Gi, but limit is 4Gi`로 거부 |
| replicas 15짜리 Deployment | Pod 10개에서 멈추고 ReplicaSet에 `FailedCreate`(exceeded quota) 이벤트 |
| `--type=LoadBalancer`로 Service 노출 | `exceeded quota ... services.loadbalancers`로 거부 |

## 6. 멀티테넌시: 소프트와 하드

설계는 **"테넌트가 누구인가"** 에 따라 달라진다.

| | 소프트 멀티테넌시 | 하드 멀티테넌시 |
|---|---|---|
| 테넌트 | 같은 조직의 다른 팀 | 서로 신뢰하지 않는 고객, 외부 사용자 |
| 위협 모델 | 실수로 인한 영향 | **의도적 공격** |
| 커널 공유 | 허용 | 위험 |
| 구현 | 네임스페이스 + 쿼터 + NetworkPolicy + RBAC | 별도 클러스터 또는 샌드박스 런타임 |

> **핵심 판단 기준: 테넌트가 임의의 코드를 실행할 수 있는가?** 그렇다면 네임스페이스 격리로는 부족하다. 컨테이너의 격리 경계는 커널(5장)이고 커널 취약점은 계속 발견되기 때문이다. SaaS에서 고객이 자기 코드를 올리는 구조라면 클러스터를 분리하거나 gVisor/Kata 같은 샌드박스 런타임을 써야 한다.

같은 조직 안의 팀 분리(소프트)는 네임스페이스 + 라벨, ResourceQuota, LimitRange, NetworkPolicy(기본 거부 + 같은 네임스페이스 허용 + DNS 허용), RBAC의 조합으로 구현하고, 필요하면 전용 노드 풀(테인트 + 어피니티)을 더한다. 네임스페이스를 나누는 기준은 팀별, 환경별, 팀+환경별, 애플리케이션별 등이 있는데, 원문은 **환경(dev/staging/prod)은 클러스터로 나누는 것이 일반적**이라고 한다. 프로덕션과 개발이 같은 클러스터에 있으면 컨트롤 플레인 장애가 프로덕션에 전파되고 업그레이드를 먼저 테스트할 수도 없기 때문이다. 작은 조직은 클러스터 하나에 `dev`/`prod` 네임스페이스로 시작해 성장하며 분리해도 된다.

> **[보충]** 네임스페이스가 수십&#126;수백 개로 늘면 각각의 쿼터·네트워크 정책·권한을 일관되게 관리하는 일이 새 문제가 되는데, 원문은 이를 위한 도구로 계층적 네임스페이스(HNC)와 가상 클러스터(vCluster)를 소개한다. 입문 단계에서는 "이런 도구가 있다"는 정도만 알아 두면 충분하다.

## 핵심 요약

- **네임스페이스는 보안 경계가 아니다.** 이름 스코프, DNS 스코프, RBAC 그룹, 쿼터 단위를 제공할 뿐이며, 네트워크는 기본적으로 열려 있고 노드·커널·컨트롤 플레인은 공유된다.
- **ResourceQuota**는 네임스페이스 총량을, **LimitRange**는 개별 컨테이너를 제어한다.
- 컴퓨트 쿼터가 있으면 모든 컨테이너가 requests/limits를 명시해야 하므로 **LimitRange의 기본값과 함께 쓰는 것이 사실상 필수**다.
- `services.loadbalancers` 쿼터로 LB 비용 폭주를, `maxLimitRequestRatio`로 과도한 오버커밋을 막는다. 쿼터 초과 시 컨트롤러는 계속 재시도하므로 이벤트를 확인한다.
- **소프트 멀티테넌시**(같은 조직의 팀)는 네임스페이스 + 쿼터 + NetworkPolicy + RBAC, **하드 멀티테넌시**(신뢰할 수 없는 테넌트)는 별도 클러스터나 샌드박스 런타임이 필요하다.
- 네임스페이스 삭제는 안의 모든 리소스(PVC 포함)를 지운다.

## 확인 질문

2. ResourceQuota만 만들고 LimitRange 없이 `resources`를 안 쓴 Pod를 만들면 어떻게 되는가? 어떻게 해결하는가?
3. 외부 고객이 자기 코드를 올려 실행하는 서비스를 네임스페이스만으로 분리해도 안전하지 않은 이유는 무엇인가?
