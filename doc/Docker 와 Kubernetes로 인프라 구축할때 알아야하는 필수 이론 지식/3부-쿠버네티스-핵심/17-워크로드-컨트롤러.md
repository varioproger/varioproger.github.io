# 17장. 워크로드 컨트롤러 — Deployment, StatefulSet, DaemonSet, Job

## 이 장에서 배우는 것

- ReplicaSet이 Pod를 어떻게 관리하는지, 왜 직접 쓰지 않는지 설명할 수 있다.
- Deployment의 롤링 업데이트 파라미터를 이해하고 롤백할 수 있다.
- StatefulSet이 제공하는 세 가지 보장과 한계를 설명할 수 있다.
- DaemonSet, Job, CronJob의 용도를 구분하고, 워크로드 성격에 맞는 컨트롤러를 고를 수 있다.

---

14장에서 Pod를 직접 만들면 노드가 죽을 때 그대로 사라진다고 했다. 이 장의 컨트롤러들이 그 문제를 해결한다. 각 컨트롤러는 12장의 **조정 루프**를 돌리며, 다른 점은 "무엇을 원하는 상태로 삼는가"뿐이다.

```
ReplicaSet   : "이 라벨을 가진 Pod가 N개"
Deployment   : "이 템플릿의 ReplicaSet이 원하는 버전으로"
StatefulSet  : "고유 ID를 가진 Pod가 0..N-1까지 순서대로"
DaemonSet    : "조건에 맞는 모든 노드에 정확히 하나씩"
Job          : "성공적으로 완료된 Pod가 N개"
CronJob      : "스케줄에 맞춰 Job을 생성"
```

## 1. ReplicaSet: 개수를 지키는 컨트롤러

ReplicaSet은 **셀렉터에 매칭되는 Pod의 개수를 `replicas`로 유지**하는 단 하나의 일을 한다.

```yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: web-rs
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:                      # Pod 템플릿
    metadata:
      labels:
        app: web                 # selector와 일치해야 한다
    spec:
      containers:
        - name: web
          image: hello:1.0
```

조정 루프는 ① 셀렉터에 맞는 Pod를 센다(2개) ② 원하는 수(3개)와 비교한다(1개 부족) ③ template으로 Pod를 1개 생성한다. 초과하면 삭제하는데, Pending 상태, Ready가 아닌 것, 재시작이 많은 것 등 **문제 있는 것을 먼저** 지운다.

**셀렉터가 소유권을 결정한다.** ReplicaSet은 자기가 만들지 않은 Pod도 셀렉터에 맞으면 자기 것으로 간주한다. 그래서 셀렉터가 겹치는 컨트롤러 두 개를 만들면 서로 상대의 Pod를 지우려 드는 참사가 일어난다.

**왜 직접 쓰지 않는가.** ReplicaSet은 개수만 관리할 뿐 버전 관리를 하지 않는다. 템플릿의 이미지를 바꿔도 **기존 Pod는 그대로**이고 새로 만들어지는 Pod부터 적용된다. 롤링 업데이트도, 롤백도 없다. 그래서 실무에서는 **Deployment**를 쓴다.

```
Deployment  (버전 관리, 롤아웃 전략)
    ├─ ReplicaSet v1  (replicas: 0)   ← 롤백용으로 보관
    └─ ReplicaSet v2  (replicas: 3)   ← 현재 활성
           └─ Pod, Pod, Pod
```

## 2. Deployment: 무상태 애플리케이션

### 기본 구조

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  annotations:
    kubernetes.io/change-cause: "initial deploy v1.0"
spec:
  replicas: 4
  revisionHistoryLimit: 10          # 보관할 이전 ReplicaSet 수 (기본 10)
  minReadySeconds: 10               # Ready 후 이만큼 지나야 "사용 가능"으로 인정
  progressDeadlineSeconds: 600      # 이 시간 안에 진전이 없으면 실패 처리
  selector:
    matchLabels:
      app: web
  strategy:
    type: RollingUpdate             # 또는 Recreate
    rollingUpdate:
      maxSurge: 25%                 # 원하는 수보다 얼마나 더 만들 수 있나
      maxUnavailable: 25%           # 얼마나 부족해도 되나
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: hello:1.0
          readinessProbe:           # 롤링 업데이트의 안전장치
            httpGet: { path: /healthz, port: 8080 }
```

### 두 가지 전략

- **`Recreate`**: 전부 죽이고 전부 만든다. 다운타임이 생긴다. 두 버전이 동시에 존재하면 안 될 때(DB 스키마 호환성 문제, 파일 락 등) 쓴다.
- **`RollingUpdate`**(기본): 조금씩 교체한다.

```
[v1 v1 v1 v1]
[v1 v1 v1 v1 v2]     ← maxSurge만큼 추가
[v1 v1 v1 v2]        ← v2가 Ready되면 v1 하나 제거
...
[v2 v2 v2 v2]
```

### maxSurge와 maxUnavailable

`replicas: 4`, 둘 다 25%이면 `maxSurge = ceil(4 x 0.25) = 1`(최대 5개 존재), `maxUnavailable = floor(4 x 0.25) = 1`(최소 3개는 사용 가능). 올림/내림이 다르며 안전한 쪽으로 계산한다.

| 설정 | 동작 | 적합한 상황 |
|---|---|---|
| `25% / 25%` (기본) | 균형 | 대부분 |
| `maxSurge: 1`, `maxUnavailable: 0` | **용량을 절대 줄이지 않음.** 새 Pod가 Ready된 뒤에만 기존 것 제거 | 프로덕션 권장 |
| `maxSurge: 0`, `maxUnavailable: 1` | 총 Pod 수가 늘지 않음 | 리소스가 빠듯할 때 |
| `maxSurge: 100%`, `maxUnavailable: 0` | 새 버전 전체를 먼저 띄운 뒤 교체 | 빠른 배포, 리소스 여유 |

> **`maxUnavailable: 0`과 리소스 부족의 충돌** — 새 Pod가 뜰 자리가 있어야 진행된다. 클러스터에 여유가 없으면 새 Pod가 `Pending`에 머물러 롤아웃이 영원히 멈춘다.

**readiness가 롤아웃을 통제한다.** 새 Pod가 `Ready`가 되어야 다음 단계로 넘어간다. `minReadySeconds`를 주면 Ready 후 그 시간 동안 크래시하지 않아야 "사용 가능"으로 인정하므로, 시작 직후에 죽는 버그를 롤아웃 중에 잡을 수 있다. 잘못된 이미지로 업데이트해도 기존 Pod는 유지되어 **서비스는 멈추지 않고 롤아웃만 멈춘다.**

### 리비전과 롤백

```bash
kubectl set image deployment/web web=hello:2.0     # 업데이트
kubectl rollout status deployment/web              # 진행 확인
kubectl rollout history deployment/web             # 이력 (CHANGE-CAUSE는 애노테이션에서)
kubectl rollout undo deployment/web                # 직전으로 롤백
kubectl rollout undo deployment/web --to-revision=2
kubectl rollout pause deployment/web               # 진행 중 롤아웃 일시 중지 (resume으로 재개)
```

**롤백이 빠른 이유**는 이전 ReplicaSet이 `replicas: 0`으로 남아 있기 때문이다. 그것을 다시 스케일 업하고 현재 것을 스케일 다운하면 끝이다(이미지도 노드에 캐시되어 있다). `kubectl get rs -l app=web`으로 보면 리비전마다 ReplicaSet이 하나씩 있고 현재 것만 DESIRED가 0이 아니다. `revisionHistoryLimit`을 넘으면 오래된 것부터 삭제된다.

> **롤백이 복구하지 못하는 것** — Deployment 롤백은 **Pod 템플릿만** 되돌린다. DB 스키마 마이그레이션, ConfigMap/Secret의 내용, 외부 시스템에 미친 부수 효과는 되돌아가지 않는다. 마이그레이션은 하위 호환되게 설계한다.

### 롤링 업데이트 실전 흐름

`replicas: 4`, `maxSurge: 1`, `maxUnavailable: 0`, `minReadySeconds: 5`, readinessProbe가 있는 Deployment를 업데이트한다고 하자. 터미널 하나에서 `kubectl get pods -l app=web -w`로 지켜보고, 다른 터미널에서 업데이트한다.

```bash
kubectl set image deployment/web web=hello:2.0
kubectl annotate deployment/web kubernetes.io/change-cause="v2 - hello 2.0" --overwrite
kubectl rollout status deployment/web
```

관찰되는 패턴은 다음과 같다.

```
새 Pod 생성 (총 5개)          ← maxSurge: 1
새 Pod가 Ready
5초 대기                      ← minReadySeconds
기존 Pod 하나 Terminating (총 4개)
새 Pod 생성 (총 5개)
... 반복 ...
```

**사용 가능한 Pod가 4개 미만으로 떨어지지 않는다.** `maxUnavailable: 0`의 효과다. 존재하지 않는 이미지 태그로 업데이트하면 새 Pod 하나만 `ImagePullBackOff`에 빠지고 기존 4개는 `Running`으로 남는다. `kubectl rollout status --timeout=30s`가 시간 초과로 끝나면 `kubectl rollout undo`로 되돌린다.

> **[보충]** 위 예는 관찰하기 쉽도록 명령형 `kubectl set image`를 썼다. 실제 운영에서는 매니페스트 파일의 `image` 값을 바꾸고 `kubectl apply -f`로 적용하는 선언형 방식(13장)이 일반적이다. 그래야 파일과 클러스터 상태가 어긋나지 않는다.

### 블루-그린과 카나리

- **블루-그린**: 두 버전을 별도 Deployment로 완전히 띄우고, Service 셀렉터(`slot: blue` → `slot: green`)를 바꿔 한 번에 전환한다. 즉시 전환·즉시 복귀가 가능하지만 리소스가 2배 필요하다.
- **카나리**: 같은 Service 셀렉터를 공유하는 stable(9개)과 canary(1개) 같은 식으로 replica 수로 비율(10%)을 조절한다. 한계는 비율이 Pod 수에 묶이고, 분배가 정확하지 않고, 세션 고정이 안 되며, 자동 롤백이 없다는 것이다. 정밀한 카나리는 인그레스 컨트롤러의 가중치 기능이나 Argo Rollouts / Flagger 같은 도구로 구현한다.

### Deployment 모범 사례

- `replicas`는 최소 2 이상(단일 장애점 제거).
- `maxSurge: 1`, `maxUnavailable: 0`으로 용량 유지, `minReadySeconds`, `progressDeadlineSeconds` 설정.
- 이미지는 `latest` 금지, 명시적 태그 사용.
- readinessProbe는 필수, `preStop: sleep`(15장), `resources.requests/limits`(18장) 설정.
- **PodDisruptionBudget**을 함께 정의한다(아래). 없으면 노드 드레인 시 모든 Pod가 동시에 축출될 수 있다.

### PodDisruptionBudget: 노드 유지보수 중에도 최소 개수 지키기

노드를 업그레이드하거나 교체할 때는 `kubectl drain <node> --ignore-daemonsets`로 그 노드의 Pod를 비운다. drain은 노드에 스케줄 금지 표시를 하고, 각 Pod에 Eviction API를 호출한다. 이때 API 서버가 **PodDisruptionBudget(PDB)** 을 확인해, 허용 범위 안이면 Pod를 정상 종료(15장)시키고 위반이면 거절한다(kubectl은 재시도한다).

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-pdb
spec:
  maxUnavailable: 1          # 또는 minAvailable: 2
  selector:
    matchLabels: { app: web }
```

> **`minAvailable`을 replicas와 같게 두면 drain이 영원히 멈춘다.** `replicas: 3`에 `minAvailable: 3`이면 하나도 축출할 수 없다. `minAvailable: 2` 또는 `maxUnavailable: 1`로 둔다. HPA로 replicas가 오르내린다면 `maxUnavailable`이 의미가 유지되어 더 낫다.

`kubectl get pdb -A`의 `ALLOWED DISRUPTIONS`가 0이면 drain이 막힌 상태다. 그리고 **PDB는 drain 같은 자발적 중단만 제어한다.** 노드 자원 부족으로 kubelet이 Pod를 축출하는 비자발적 중단은 막지 못한다(18장).

## 3. StatefulSet: 상태 저장 애플리케이션

### Deployment로는 안 되는 것

데이터베이스 클러스터를 Deployment로 배포하면 문제가 줄줄이 나온다.

1. Pod 이름이 무작위다. 재시작하면 이름이 바뀌어 "1번 노드가 프라이머리" 같은 규칙을 만들 수 없다.
2. 모든 Pod가 같은 볼륨을 공유한다. 각자 자기 데이터 디렉터리가 필요한데 불가능하다.
3. 시작 순서가 없다. 첫 노드가 뜬 뒤 나머지가 조인해야 하는데 동시에 뜬다.
4. 안정적인 네트워크 ID가 없다. Pod IP가 바뀌면 클러스터 멤버십이 깨진다.

### 세 가지 보장

**① 안정적이고 고유한 네트워크 ID** — `web-0`, `web-1`, `web-2`처럼 이름이 순서를 갖고 재시작해도 같다. 각 Pod는 `web-0.web-headless.default.svc.cluster.local` 같은 고유 DNS 이름을 얻는데, 이를 위해 **헤드리스 서비스**(`clusterIP: None`)가 필요하다(20장).

**② 안정적인 스토리지** — `volumeClaimTemplates`로 각 Pod마다 자기만의 PVC가 생성된다(`web-0` → `data-web-0`). Pod가 다시 만들어져도 **같은 이름의 PVC에 다시 붙어** 데이터가 유지된다.

**③ 순서 보장** — 생성은 `web-0` → (Ready 대기) → `web-1` → `web-2`, 삭제는 역순이다.

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
spec:
  serviceName: db-headless          # 헤드리스 서비스 이름
  replicas: 3
  podManagementPolicy: OrderedReady # 또는 Parallel
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      partition: 0                  # 이 인덱스 이상만 업데이트
  selector:
    matchLabels: { app: db }
  template:
    metadata:
      labels: { app: db }
    spec:
      containers:
        - name: postgres
          image: postgres:16-alpine
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:             # Pod마다 PVC 생성
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 5Gi
```

- `podManagementPolicy`: `OrderedReady`(기본, 하나씩 순서대로)와 `Parallel`(동시에 생성/삭제하되 이름과 스토리지는 여전히 안정적).
- **롤링 업데이트는 높은 인덱스부터 역순**(`web-2` → `web-1` → `web-0`)이다. `partition: 2`를 주면 인덱스 2 이상만 업데이트되므로, partition을 단계적으로 낮추며 한 인스턴스씩 검증하는 **스테이지드 롤아웃(카나리)** 이 가능하다.

> **스케일 다운해도 PVC는 삭제되지 않는다.** 실수로 스케일 다운해도 데이터를 잃지 않게 하려는 의도된 동작이며, 다시 스케일 업하면 같은 PVC에 재연결된다. 정말 지우려면 수동으로 `kubectl delete pvc`를 한다(`persistentVolumeClaimRetentionPolicy`로 정책 지정도 가능).

### StatefulSet의 한계

StatefulSet이 해 주는 것은 **이름, 스토리지, 순서**뿐이다. 리더 선출, 복제 설정, 페일오버, 백업, 스키마 마이그레이션은 해 주지 않는다. 이는 애플리케이션이나 오퍼레이터의 일이어서, 실무에서는 StatefulSet을 직접 쓰기보다 DB별 오퍼레이터(CloudNativePG, Strimzi 등)를 쓴다.

> **더 근본적인 질문** — 프로덕션 DB를 쿠버네티스에서 운영해야 하는가? 관리형 서비스(RDS, Cloud SQL)가 나은 경우가 많다. StatefulSet은 "쿠버네티스에서 상태를 다룰 수 있다"는 것이지 "다뤄야 한다"는 뜻은 아니다.

## 4. DaemonSet: 노드마다 하나씩

**모든(또는 조건에 맞는) 노드에 정확히 하나의 Pod**를 배치한다. 노드가 추가되면 Pod가 자동 생기고, 노드가 제거되면 사라진다. `kube-proxy`와 CNI 플러그인(kindnet 등)이 DaemonSet이다(`kubectl get daemonset -n kube-system`).

전형적 용도는 로그 수집기(Fluent Bit 등), 모니터링 에이전트(node-exporter), 네트워크 플러그인, CSI 노드 플러그인, 보안 에이전트(Falco)다.

DaemonSet 특유의 설정:

- **`tolerations`**: 기본적으로 테인트가 걸린 노드(컨트롤 플레인 등)에는 배치되지 않는다. 시스템 에이전트는 모든 노드에 필요하므로 `operator: Exists`로 테인트를 감내하게 하는 것이 흔하다.
- **`nodeSelector`**: 특정 노드에만 배치.
- **`hostNetwork: true`, `hostPath` 볼륨**: 노드의 네트워크/파일시스템에 직접 접근. 보안 검토 대상이다.
- DaemonSet Pod도 일반 스케줄러를 거치므로 리소스 부족으로 Pending에 머물 수 있다.

노드당 여러 개가 필요하면 DaemonSet은 불가능하고(Deployment + anti-affinity), Pod마다 다른 설정이 필요하면 사이드카를 쓴다.

## 5. Job과 CronJob: 배치 워크로드

### Job: 완료를 목표로 하는 워크로드

Deployment는 "계속 돌아야 하는" 것을, Job은 "끝나야 하는" 것을 관리한다.

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: data-migration
spec:
  completions: 1              # 성공해야 할 Pod 수
  parallelism: 1              # 동시 실행 수
  backoffLimit: 4             # 실패 재시도 횟수 (기본 6)
  activeDeadlineSeconds: 600  # 전체 제한 시간
  ttlSecondsAfterFinished: 3600   # 완료 후 자동 삭제
  template:
    spec:
      restartPolicy: OnFailure    # Always는 사용 불가
      containers:
        - name: migrate
          image: myapp:1.2
          command: ["python", "manage.py", "migrate"]
```

`restartPolicy`는 `OnFailure`(같은 Pod 안에서 컨테이너 재시작) 또는 `Never`(실패한 Pod를 남기고 새 Pod 생성, 로그를 보기 쉬움)만 가능하다. `Always`면 영원히 끝나지 않기 때문이다.

병렬 패턴: 단일 작업(`completions: 1`), 고정 완료 수(`completions: 10, parallelism: 3`), 작업 큐(`completions` 미지정, 하나라도 성공하면 마무리), 인덱스 지정(`completionMode: Indexed`, 각 Pod가 `JOB_COMPLETION_INDEX` 환경변수를 받아 샤딩 처리).

흔한 문제: `BackoffLimitExceeded`(재시도 소진), `DeadlineExceeded`(`activeDeadlineSeconds` 초과), 그리고 **사이드카가 계속 실행되어 Job이 완료되지 않는 경우**(14장의 `initContainers` + `restartPolicy: Always` 사이드카로 해결).

### CronJob: 스케줄된 Job

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-backup
spec:
  schedule: "0 3 * * *"
  timeZone: "Asia/Seoul"               # v1.27+ 에서 타임존 지정 가능
  concurrencyPolicy: Forbid            # Allow | Forbid | Replace
  startingDeadlineSeconds: 300
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 3
  jobTemplate:
    spec:
      backoffLimit: 2
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: backup
              image: backup-tool:1.0
```

> **타임존 함정** — `timeZone` 필드가 없으면 컨트롤러 매니저의 시간대(보통 UTC)를 따른다. "매일 새벽 3시"라고 적었는데 한국 시각 정오에 실행되는 사고가 흔하다.

| `concurrencyPolicy` | 동작 |
|---|---|
| `Allow`(기본) | 이전 Job이 안 끝나도 새로 시작 |
| `Forbid` | 이전 Job이 실행 중이면 건너뜀 (백업처럼 동시 실행이 위험한 작업) |
| `Replace` | 이전 Job을 죽이고 새로 시작 |

테스트용 수동 실행은 `kubectl create job manual-backup --from=cronjob/nightly-backup`, 일시 중지는 `suspend: true`로 한다.

## 6. 컨트롤러 선택

```
워크로드가 끝나는가?
├─ 예 → 정해진 시각에 반복? ── 예: CronJob / 아니오: Job
└─ 아니오 (계속 실행)
    └─ 모든 노드에 하나씩 필요? ── 예: DaemonSet
        └─ 아니오 → 각 인스턴스가 고유 ID나 스토리지를 갖는가?
            ├─ 예 → StatefulSet (오퍼레이터가 있다면 먼저 검토)
            └─ 아니오 → Deployment  ← 90%의 경우
```

| | Deployment | StatefulSet | DaemonSet | Job | CronJob |
|---|---|---|---|---|---|
| Pod 이름 | 무작위 | `name-0`, `name-1` | 무작위 | 무작위 | 무작위 |
| 시작 순서 | 동시 | 순차(기본) | 동시 | 병렬 설정 가능 | - |
| 스토리지 | 공유 또는 없음 | Pod마다 고유 PVC | hostPath 주로 | 임시 | 임시 |
| 업데이트 | 롤링 | 롤링(역순) | 롤링 | - | - |
| 대표 용도 | 웹, API, 워커 | DB, 큐, 분산 스토리지 | 로그·모니터링·네트워크 | 마이그레이션, 배치 | 백업, 리포트 |

## 핵심 요약

- **ReplicaSet**은 개수만 지킨다. 템플릿을 바꿔도 기존 Pod는 그대로이므로 직접 쓰지 않고 Deployment가 감싼다.
- **Deployment의 롤링 업데이트**는 `maxSurge`/`maxUnavailable`로 속도와 안전성을 조절한다. 프로덕션 권장은 `maxSurge: 1, maxUnavailable: 0`이며 **readiness 프로브가 안전장치**다.
- 롤백은 이전 ReplicaSet을 다시 스케일 업하는 것이라 빠르다. 단 **DB 스키마와 ConfigMap 내용은 되돌아가지 않는다.**
- **PodDisruptionBudget**은 drain 같은 자발적 중단 중에도 최소 개수를 지킨다. `minAvailable`을 replicas와 같게 두면 drain이 멈춘다.
- **StatefulSet**은 안정적 이름·스토리지·순서를 보장하지만 리더 선출·페일오버는 해 주지 않는다. 스케일 다운해도 PVC는 남는다.
- **DaemonSet**은 노드마다 하나씩(시스템 에이전트), **Job**은 완료가 목표, **CronJob**은 `timeZone`과 `concurrencyPolicy`를 챙긴다.
- 대부분의 무상태 앱은 **Deployment**다.

## 확인 질문

1. ReplicaSet만 쓰면 이미지를 바꿔도 기존 Pod가 교체되지 않는 이유는 무엇이며, Deployment는 이를 어떻게 해결하는가?
2. `maxSurge: 1`, `maxUnavailable: 0`으로 롤링 업데이트할 때 클러스터에 여유 용량이 없으면 어떻게 되는가?
3. 데이터베이스 인스턴스 3개를 띄워야 한다. Deployment 대신 StatefulSet이 필요한 이유 세 가지를 말해 보라.
