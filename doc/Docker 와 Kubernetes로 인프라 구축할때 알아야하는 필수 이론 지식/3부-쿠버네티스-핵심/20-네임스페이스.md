# 20장. 네임스페이스 — 역할, 한계, ResourceQuota, LimitRange

> **🎮 게임 서버 개발자에게** — 쿠버네티스 네임스페이스는 C++의 `namespace`와 성격이 거의 같다. 이름 충돌을 막고 묶어 줄 뿐, 접근을 막는 벽이 아니다. 한 머신에 여러 서버 프로세스를 띄우면 같은 커널과 네트워크를 공유하듯, 여러 네임스페이스의 Pod도 노드·커널·네트워크·컨트롤 플레인을 공유한다. 결정적으로 새로운 것은 **ResourceQuota(팀 전체 예산)와 LimitRange(컨테이너별 기본값·상한)** 로 자원을 통제하는 장치이고, 둘은 한 쌍으로 써야 한다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - dev 환경의 서버가 실수로 prod 서비스에 붙어 실데이터를 건드렸다.
> - 쿼터를 건 뒤로 배포가 `forbidden: failed quota`로 실패하거나, 스케일이 10개에서 멈춘다.
> - 유저가 올린 스크립트(모드)를 서버에서 실행하는 기능을 같은 클러스터에서 돌려도 되는지 결정해야 한다.

## 코어 — 이것만은 100%

> **한 문장:** 네임스페이스는 이름·DNS·RBAC·쿼터의 단위일 뿐 보안 경계가 아니므로, 자원은 ResourceQuota(총량)와 LimitRange(개별 기본값·범위)를 함께 써서 통제하고, 네트워크·노드·커널 격리는 따로 더해야 하며, 신뢰할 수 없는 테넌트는 클러스터나 샌드박스 런타임으로 나눈다.

1. **네임스페이스가 주는 것 4가지** — 이름 스코프, DNS 스코프, RBAC 경계, 쿼터 단위. 삭제하면 안의 모든 것이 사라진다.
2. **네임스페이스는 보안 경계가 아니다** — 네트워크는 기본 열림, 노드·커널·클러스터 전역 리소스·컨트롤 플레인은 공유. 격리는 NetworkPolicy·쿼터·테인트·샌드박스·RBAC로 따로 더한다.
3. **ResourceQuota + LimitRange는 한 쌍** — 컴퓨트 쿼터가 있으면 requests/limits 없는 Pod는 거부되므로 LimitRange의 `default`/`defaultRequest`로 기본값을 주입한다. 쿼터 초과 시 컨트롤러는 계속 재시도하므로 이벤트를 확인한다.
4. **멀티테넌시 판단 기준** — "테넌트가 임의의 코드를 실행할 수 있는가?" 같은 조직 팀(소프트)은 네임스페이스 + 쿼터 + NetworkPolicy + RBAC, 신뢰할 수 없는 테넌트(하드)는 별도 클러스터나 샌드박스 런타임.

**이 장의 학습 목표**
- 네임스페이스가 제공하는 것과 제공하지 못하는 것을 정확히 구분한다. (→ 코어 1, 2)
- ResourceQuota로 네임스페이스의 자원 총량을 통제하는 방법을 안다. (→ 코어 3)
- LimitRange로 컨테이너별 기본값과 상하한을 강제하는 방법을 안다. (→ 코어 3)
- 같은 조직 팀 분리(소프트)와 신뢰할 수 없는 테넌트 분리(하드)의 차이를 이해한다. (→ 코어 4)

여러 팀이 하나의 클러스터를 나눠 쓰면 "A팀의 실수가 B팀을 죽이지 않게", "한 팀이 자원을 독차지하지 못하게" 같은 질문이 생긴다. 네임스페이스는 그 출발점이다.

## 코어 1. 네임스페이스가 주는 것

### 1.1 기본 네임스페이스와 네 가지 역할

**한 줄 요약:** 네임스페이스는 이름 스코프·DNS 스코프·RBAC 경계·쿼터 단위를 제공한다.

```bash
kubectl get namespaces
```

| 네임스페이스 | 용도 |
|---|---|
| `default` | 지정하지 않았을 때의 기본 |
| `kube-system` | 시스템 컴포넌트(건드리지 말 것) |
| `kube-public` | 인증 없이 읽을 수 있는 리소스(거의 안 씀) |
| `kube-node-lease` | 노드 하트비트용 Lease 오브젝트 |

네임스페이스가 제공하는 것은 네 가지다.

1. **이름 스코프** — 같은 이름의 리소스를 여러 네임스페이스에 만들 수 있다(`dev/web-service`, `prod/web-service`).
2. **DNS 스코프** — DNS 이름에 네임스페이스가 들어간다(`web.dev.svc.cluster.local`). 같은 네임스페이스 안에서는 짧은 이름으로 부를 수 있다.
3. **RBAC 경계** — Role과 RoleBinding은 네임스페이스에 속한다. "dev에서만 Pod를 만들 수 있는" 역할을 정의할 수 있다.
4. **리소스 쿼터의 단위** — ResourceQuota는 네임스페이스마다 적용된다.

([14장](14-API-오브젝트-kubectl-YAML.md)에서 본 대로 Node, PersistentVolume, StorageClass, ClusterRole 등은 네임스페이스에 속하지 않는 클러스터 전역 리소스다.)

### 1.2 관리 명령과 삭제의 위험

**한 줄 요약:** 네임스페이스 삭제는 안의 모든 리소스를 지우며 되돌릴 수 없다.

```bash
kubectl create namespace team-a
kubectl config set-context --current --namespace=team-a   # 기본 네임스페이스 변경
kubectl delete namespace team-a                           # 안의 모든 리소스가 함께 삭제
```

> **네임스페이스 삭제는 되돌릴 수 없다.** 안의 모든 리소스(Deployment, Service, PVC, Secret 등)가 사라진다. PVC에 연결된 볼륨의 `reclaimPolicy`가 `Delete`라면(PV/StorageClass에 지정, [24장](../4부-노출-데이터-운영/24-스토리지.md)) 데이터까지 사라진다. `Terminating`에서 멈추는 경우는 [14장](14-API-오브젝트-kubectl-YAML.md)에서 본 파이널라이저 문제다.

## 코어 2. 네임스페이스는 보안 경계가 아니다

### 2.1 네임스페이스가 하지 못하는 일

**한 줄 요약:** 네트워크는 열려 있고 노드·커널·전역 리소스·컨트롤 플레인은 공유되므로, 격리는 따로 더해야 한다.

> **네임스페이스는 보안 경계가 아니다.** 이름 정리와 권한 그룹화를 위한 것이지 격리를 위한 것이 아니다.

- **네트워크는 기본적으로 열려 있다.** `dev`의 Pod에서 `curl http://web.prod.svc.cluster.local`이 **연결된다.** 모든 Pod는 모든 Pod와 통신할 수 있다. 막으려면 NetworkPolicy가 필요하다.
- **노드는 공유된다.** 여러 네임스페이스의 Pod가 같은 노드에서 돈다. 같은 커널을 공유하고, CPU/메모리를 경쟁하며, `hostPath`가 있으면 다른 Pod의 데이터까지 볼 수 있다.
- **클러스터 전역 리소스는 공유된다.** CRD를 설치하면 모든 네임스페이스에 영향을 준다.
- **컨트롤 플레인은 하나다.** 한 팀이 API 서버에 부하를 주면 모두가 느려지고, etcd가 가득 차면 클러스터 전체가 멈춘다.

```
네임스페이스가 주는 것:  이름 정리, RBAC 그룹, 쿼터 단위, DNS 스코프
추가로 필요한 것:
  · 네트워크 격리 → NetworkPolicy
  · 자원 격리     → ResourceQuota + LimitRange (이 장)
  · 노드 격리     → 테인트 + 어피니티 (19장)
  · 커널 격리     → 샌드박스 런타임
  · 권한 격리     → RBAC
```

## 코어 3. ResourceQuota + LimitRange는 한 쌍

### 3.1 ResourceQuota: 네임스페이스 총량 제한

**한 줄 요약:** 네임스페이스 전체의 컴퓨트·스토리지·오브젝트 개수 총량을 정하며, `services.loadbalancers`는 비용 통제에 중요하다.

네임스페이스 전체가 소비할 수 있는 자원의 총량을 정한다.

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-a-quota
  namespace: team-a
spec:
  hard:
    requests.cpu: "20"
    requests.memory: 40Gi
    limits.cpu: "40"
    limits.memory: 80Gi
    requests.storage: 500Gi
    persistentvolumeclaims: "20"
    pods: "100"
    services: "20"
    services.loadbalancers: "2"      # 비용 통제에 중요
    services.nodeports: "5"
    configmaps: "50"
    secrets: "50"
    count/deployments.apps: "30"
```

`services.loadbalancers`를 제한하는 이유는 LoadBalancer Service 하나당 클라우드 LB 하나가 생기고 요금이 부과되기 때문이다. `count/<resource>.<group>` 형식으로 임의 리소스의 개수도 제한할 수 있다.

```bash
kubectl describe resourcequota team-a-quota -n team-a
# Resource   Used   Hard
# pods       18     100
# requests.cpu  6   20
```

### 3.2 가장 중요한 규칙

**한 줄 요약:** 컴퓨트 쿼터가 있으면 requests/limits를 명시하지 않은 Pod는 거부되며, 해결책은 LimitRange 기본값이다.

> **컴퓨트 쿼터가 있으면 모든 컨테이너가 requests/limits를 명시해야 한다.** ResourceQuota에 `requests.cpu`나 `limits.memory`가 있으면 해당 값을 지정하지 않은 Pod는 **생성이 거부된다.**
>
> ```
> Error from server (Forbidden): pods "web" is forbidden: failed quota: team-a-quota:
> must specify limits.cpu for: app; limits.memory for: app; ...
> ```
>
> 이것은 버그가 아니라 의도된 동작이다(쿼터를 계산하려면 각 Pod가 얼마를 쓸지 알아야 하므로). **해결책은 LimitRange로 기본값을 주는 것이다.** 이 둘은 거의 항상 함께 쓴다.

### 3.3 scopeSelector, 쿼터 초과 시 동작

**한 줄 요약:** `scopes`로 특정 Pod에만 쿼터를 걸 수 있고, 초과 시 새 Pod만 거부되며 컨트롤러는 조용히 재시도한다.

`scopes`(`BestEffort`, `NotBestEffort`, `Terminating`, `PriorityClass` 등)를 지정하면 특정 조건의 Pod에만 쿼터를 적용할 수 있다. 예를 들어 `PriorityClass`가 `high-priority`인 Pod에만 쿼터를 걸면 팀이 높은 우선순위를 남발하는 것을 막는다.

**쿼터 초과 시 Pod 생성이 거부된다.** 이미 실행 중인 Pod는 영향받지 않는다. 주의할 점은 Deployment/ReplicaSet이 **계속 재시도**한다는 것이다. 이벤트를 보지 않으면 "왜 스케일이 안 되지?"라고 한참 헤맬 수 있다.

```bash
kubectl describe replicaset <name>
# Warning  FailedCreate  Error creating: pods "web-abc" is forbidden:
#   exceeded quota: team-a-quota, requested: requests.cpu=2, used: requests.cpu=19, limited: requests.cpu=20
```

### 3.4 LimitRange: 개별 컨테이너 기본값과 범위

**한 줄 요약:** LimitRange는 컨테이너/Pod/PVC 단위로 기본값 주입·최소/최대 강제·limits/requests 비율 상한을 건다.

ResourceQuota가 총량이라면, LimitRange는 **개별 컨테이너/Pod/PVC** 수준에서 동작한다.

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: team-a-limits
  namespace: team-a
spec:
  limits:
    - type: Container
      default:                  # ① limits 기본값
        cpu: 500m
        memory: 512Mi
      defaultRequest:           # ② requests 기본값
        cpu: 100m
        memory: 128Mi
      min:                      # ③ 최솟값 (이보다 작으면 거부)
        cpu: 10m
        memory: 32Mi
      max:                      # ④ 최댓값 (이보다 크면 거부)
        cpu: "4"
        memory: 8Gi
      maxLimitRequestRatio:     # ⑤ limits/requests 비율 상한
        memory: "4"
```

- **`default` / `defaultRequest`**: 컨테이너에 `resources`를 안 쓰면 어드미션 단계에서 이 값이 자동 주입된다. 개발자가 아무것도 쓰지 않아도 requests와 limits가 채워지므로, **ResourceQuota와 함께 쓸 때 필수적이다.**
- **`min` / `max`**: 범위를 강제한다(예: `maximum memory usage per Container is 8Gi, but limit is 16Gi`). 한 컨테이너가 노드 전체를 차지하는 것을 막는다.
- **`maxLimitRequestRatio`**: 오버커밋을 제한한다. `memory: "4"`이면 `requests: 1Gi, limits: 8Gi`(비율 8)는 거부된다. requests가 낮고 limits가 높으면 스케줄러는 "조금만 쓴다"고 판단해 많이 배치하는데 실제로는 limits까지 쓸 수 있어 노드가 과부하되기 때문이다([19장](19-리소스-요청-제한과-스케줄링-기초.md)).

### 3.5 실습 시나리오: 쿼터와 리밋

**한 줄 요약:** 기본값 주입, 최댓값 거부, 개수 쿼터에서 멈춤, LB 쿼터 거부를 직접 확인한다.

네임스페이스에 LimitRange(기본값 200m/256Mi, 최댓값 1 CPU/1Gi)와 ResourceQuota(`requests.cpu: "1"`, `pods: "10"`, `services.loadbalancers: "0"`)를 적용하면 다음을 확인할 수 있다.

| 행동 | 결과 |
|---|---|
| `kubectl run nginx -n team-a`(resources 미지정) | LimitRange가 requests/limits를 자동 주입 |
| limits.memory 4Gi를 요구하는 Pod | `maximum memory usage per Container is 1Gi, but limit is 4Gi`로 거부 |
| replicas 15짜리 Deployment | Pod 10개에서 멈추고 ReplicaSet에 `FailedCreate`(exceeded quota) 이벤트 |
| `--type=LoadBalancer`로 Service 노출 | `exceeded quota ... services.loadbalancers`로 거부 |

## 코어 4. 멀티테넌시 — 테넌트가 누구인가

### 4.1 소프트와 하드

**한 줄 요약:** 테넌트가 임의의 코드를 실행할 수 있으면 하드 멀티테넌시이며, 네임스페이스로는 부족하다.

설계는 **"테넌트가 누구인가"** 에 따라 달라진다.

| | 소프트 멀티테넌시 | 하드 멀티테넌시 |
|---|---|---|
| 테넌트 | 같은 조직의 다른 팀 | 서로 신뢰하지 않는 고객, 외부 사용자 |
| 위협 모델 | 실수로 인한 영향 | **의도적 공격** |
| 커널 공유 | 허용 | 위험 |
| 구현 | 네임스페이스 + 쿼터 + NetworkPolicy + RBAC | 별도 클러스터 또는 샌드박스 런타임 |

> **핵심 판단 기준: 테넌트가 임의의 코드를 실행할 수 있는가?** 그렇다면 네임스페이스 격리로는 부족하다. 컨테이너의 격리 경계는 커널([6장](../2부-컨테이너와-Docker/06-컨테이너-격리-네임스페이스.md))이고 커널 취약점은 계속 발견되기 때문이다. SaaS에서 고객이 자기 코드를 올리는 구조라면 클러스터를 분리하거나 gVisor/Kata 같은 샌드박스 런타임을 써야 한다.

### 4.2 소프트 멀티테넌시 구현과 네임스페이스 구분 기준

**한 줄 요약:** 팀 분리는 네임스페이스 + 쿼터 + NetworkPolicy + RBAC로 하고, 환경(dev/staging/prod)은 보통 클러스터로 나눈다.

같은 조직 안의 팀 분리(소프트)는 네임스페이스 + 라벨, ResourceQuota, LimitRange, NetworkPolicy(기본 거부 + 같은 네임스페이스 허용 + DNS 허용), RBAC의 조합으로 구현하고, 필요하면 전용 노드 풀(테인트 + 어피니티)을 더한다. 네임스페이스를 나누는 기준은 팀별, 환경별, 팀+환경별, 애플리케이션별 등이 있는데, 원문은 **환경(dev/staging/prod)은 클러스터로 나누는 것이 일반적**이라고 한다. 프로덕션과 개발이 같은 클러스터에 있으면 컨트롤 플레인 장애가 프로덕션에 전파되고 업그레이드를 먼저 테스트할 수도 없기 때문이다. 작은 조직은 클러스터 하나에 `dev`/`prod` 네임스페이스로 시작해 성장하며 분리해도 된다.

> **[보충]** 네임스페이스가 수십&#126;수백 개로 늘면 각각의 쿼터·네트워크 정책·권한을 일관되게 관리하는 일이 새 문제가 되는데, 원문은 이를 위한 도구로 계층적 네임스페이스(HNC)와 가상 클러스터(vCluster)를 소개한다. 입문 단계에서는 "이런 도구가 있다"는 정도만 알아 두면 충분하다.

## 실무 적용

### 체크리스트

- [ ] **네임스페이스는 보안 경계가 아니다.** 이름 스코프, DNS 스코프, RBAC 그룹, 쿼터 단위를 제공할 뿐이며, 네트워크는 기본적으로 열려 있고 노드·커널·컨트롤 플레인은 공유된다. (→ 코어 1, 2)
- [ ] 네트워크 격리는 NetworkPolicy, 노드 격리는 테인트 + 어피니티, 커널 격리는 샌드박스 런타임, 권한 격리는 RBAC로 따로 더한다. (→ 코어 2)
- [ ] **ResourceQuota**는 네임스페이스 총량을, **LimitRange**는 개별 컨테이너를 제어한다. (→ 코어 3)
- [ ] 컴퓨트 쿼터가 있으면 모든 컨테이너가 requests/limits를 명시해야 하므로 **LimitRange의 기본값과 함께 쓰는 것이 사실상 필수**다. (→ 코어 3)
- [ ] `services.loadbalancers` 쿼터로 LB 비용 폭주를, `maxLimitRequestRatio`로 과도한 오버커밋을 막는다. 쿼터 초과 시 컨트롤러는 계속 재시도하므로 이벤트(`describe replicaset`)를 확인한다. (→ 코어 3)
- [ ] **소프트 멀티테넌시**(같은 조직의 팀)는 네임스페이스 + 쿼터 + NetworkPolicy + RBAC, **하드 멀티테넌시**(신뢰할 수 없는 테넌트)는 별도 클러스터나 샌드박스 런타임이 필요하다. (→ 코어 4)
- [ ] 네임스페이스 삭제는 안의 모든 리소스(PVC 포함)를 지운다. 삭제 전에 PV의 `reclaimPolicy`를 확인한다. (→ 코어 1)

### 시나리오로 확인하기

1. **상황:** dev 네임스페이스의 테스트 서버 설정에 실수로 `db.prod.svc.cluster.local`이 들어갔고, 테스트 트래픽이 prod DB에 그대로 쓰였다. "네임스페이스를 나눴으니 접속은 안 될 줄 알았다."
   **질문:** 왜 연결됐고, 무엇을 더해야 하나?

   <details markdown="1"><summary>답 확인</summary>

   네임스페이스는 이름 정리와 권한 그룹화를 위한 것이지 보안 경계가 아니다. 네트워크는 기본적으로 열려 있어 모든 Pod가 모든 Pod와 통신할 수 있고, 다른 네임스페이스의 Service도 DNS 이름으로 찾아간다. NetworkPolicy(기본 거부 + 같은 네임스페이스 허용 + DNS 허용)를 더한다. 원문은 환경(dev/prod) 자체를 클러스터로 나누는 것이 일반적이라고 한다. → 코어 2, 코어 4

   </details>

2. **상황:** 팀 네임스페이스에 ResourceQuota(`requests.cpu`, `limits.memory`)를 건 다음 날, 기존 매니페스트로 배포하던 서버가 `forbidden: failed quota ... must specify limits.cpu`로 생성되지 않는다.
   **질문:** 버그인가? 어떻게 해결하나?

   <details markdown="1"><summary>답 확인</summary>

   의도된 동작이다. 쿼터를 계산하려면 각 Pod가 얼마를 쓸지 알아야 하므로, 컴퓨트 쿼터가 있으면 해당 값을 지정하지 않은 Pod는 거부된다. LimitRange의 `default`/`defaultRequest`로 어드미션 단계에서 기본값이 주입되게 하고, 가능하면 매니페스트에도 resources를 명시한다. → 코어 3

   </details>

3. **상황:** 이벤트 대비로 replicas를 15로 올렸는데 Pod가 10개에서 멈췄다. Deployment에는 에러가 보이지 않는다.
   **질문:** 어디를 봐야 하고, 원인은 무엇일 가능성이 큰가?

   <details markdown="1"><summary>답 확인</summary>

   쿼터 초과 시 새 Pod 생성이 거부되고(실행 중인 Pod는 영향 없음) ReplicaSet이 계속 재시도하므로 겉으로는 조용하다. `kubectl describe replicaset <name>`에서 `FailedCreate ... exceeded quota` 이벤트를 확인하고, `kubectl describe resourcequota`로 Used/Hard(예: `pods: "10"`, `requests.cpu`)를 본다. 쿼터를 조정하거나 Pod당 requests를 줄인다. → 코어 3

   </details>

4. **상황:** 부하 테스트용 네임스페이스를 정리하려고 `kubectl delete namespace loadtest`를 실행했다. 그런데 그 안의 PVC에 다음 테스트에 쓸 측정 데이터가 있었고, 네임스페이스는 몇 시간째 `Terminating`이다.
   **질문:** 데이터는 어떻게 됐을 수 있고, `Terminating`은 무슨 문제인가?

   <details markdown="1"><summary>답 확인</summary>

   네임스페이스 삭제는 되돌릴 수 없고 안의 모든 리소스(PVC 포함)가 지워진다. 볼륨의 `reclaimPolicy`가 `Delete`면 데이터까지 사라진다. `Terminating`에서 멈추는 것은 파이널라이저 문제다. → 코어 1

   </details>

5. **상황:** 유저가 직접 만든 서버 사이드 스크립트(모드)를 업로드해 실행해 주는 기능을 기획 중이다. "유저마다 네임스페이스를 하나씩 주고 쿼터·NetworkPolicy·RBAC를 걸면 되지 않나?"
   **질문:** 충분한가?

   <details markdown="1"><summary>답 확인</summary>

   충분하지 않다. 테넌트가 임의의 코드를 실행할 수 있으므로 위협 모델이 실수가 아니라 의도적 공격인 하드 멀티테넌시다. 여러 네임스페이스의 Pod는 같은 노드에서 같은 커널을 공유하고, 컨테이너의 격리 경계는 커널인데 커널 취약점은 계속 발견된다. 클러스터를 분리하거나 gVisor/Kata 같은 샌드박스 런타임을 써야 한다. → 코어 4

   </details>

### 2. 인출 질문

1. `dev` 네임스페이스의 Pod가 `prod` 네임스페이스의 Service에 접속할 수 있는 이유는 무엇이며, 이를 막으려면 무엇이 필요한가? (확인 질문 1)

   <details markdown="1"><summary>답 확인</summary>

   네임스페이스는 이름 정리와 권한 그룹화를 위한 것이지 보안 경계가 아니며, 네트워크는 기본적으로 열려 있어 모든 Pod가 모든 Pod와 통신할 수 있다(`curl http://web.prod.svc.cluster.local`이 연결된다). 막으려면 NetworkPolicy가 필요하다. → 코어 2

   </details>

2. ResourceQuota만 만들고 LimitRange 없이 `resources`를 안 쓴 Pod를 만들면 어떻게 되는가? 어떻게 해결하는가? (확인 질문 2)

   <details markdown="1"><summary>답 확인</summary>

   쿼터에 `requests.cpu`나 `limits.memory` 같은 컴퓨트 항목이 있으면, 쿼터를 계산하려면 각 Pod가 얼마를 쓸지 알아야 하므로 해당 값을 지정하지 않은 Pod는 `failed quota ... must specify ...`로 생성이 거부된다(의도된 동작). LimitRange의 `default`/`defaultRequest`로 기본값이 어드미션 단계에서 자동 주입되게 해 해결하며, 둘은 거의 항상 함께 쓴다. → 코어 3

   </details>

3. 외부 고객이 자기 코드를 올려 실행하는 서비스를 네임스페이스만으로 분리해도 안전하지 않은 이유는 무엇인가? (확인 질문 3)

   <details markdown="1"><summary>답 확인</summary>

   여러 네임스페이스의 Pod가 같은 노드에서 같은 커널을 공유하고, 컨테이너의 격리 경계는 커널인데 커널 취약점은 계속 발견되기 때문이다. 위협 모델이 실수가 아니라 의도적 공격인 하드 멀티테넌시이므로 클러스터를 분리하거나 gVisor/Kata 같은 샌드박스 런타임을 써야 한다. → 코어 4

   </details>

4. 네임스페이스가 제공하는 네 가지는 무엇인가?

   <details markdown="1"><summary>답 확인</summary>

   ① 이름 스코프(같은 이름 리소스를 여러 네임스페이스에) ② DNS 스코프(`web.dev.svc.cluster.local`, 같은 네임스페이스에선 짧은 이름) ③ RBAC 경계(Role과 RoleBinding이 네임스페이스에 속함) ④ 리소스 쿼터의 단위. → 코어 1

   </details>

5. `services.loadbalancers` 쿼터를 제한하는 이유와, 쿼터를 초과했을 때 Deployment에서 보이는 현상은?

   <details markdown="1"><summary>답 확인</summary>

   LoadBalancer Service 하나당 클라우드 LB가 하나 생기고 요금이 부과되므로 비용 통제를 위해서다. 쿼터를 초과하면 새 Pod 생성이 거부되고(실행 중인 Pod는 영향 없음), Deployment/ReplicaSet은 계속 재시도한다. 예를 들어 `pods: "10"`에서 replicas 15면 10개에서 멈추고 ReplicaSet에 `FailedCreate`(exceeded quota) 이벤트가 남으므로 `describe replicaset`을 확인한다. → 코어 3

   </details>

6. LimitRange의 `maxLimitRequestRatio`는 무엇을 막는가?

   <details markdown="1"><summary>답 확인</summary>

   과도한 오버커밋을 막는다. `memory: "4"`이면 `requests: 1Gi, limits: 8Gi`(비율 8)는 거부된다. requests가 낮고 limits가 높으면 스케줄러는 조금만 쓴다고 판단해 많이 배치하는데, 실제로는 limits까지 쓸 수 있어 노드가 과부하되기 때문이다. → 코어 3

   </details>

7. 네임스페이스 삭제가 위험한 이유는?

   <details markdown="1"><summary>답 확인</summary>

   되돌릴 수 없고 안의 모든 리소스(Deployment, Service, PVC, Secret 등)가 함께 삭제된다. PVC에 연결된 볼륨의 `reclaimPolicy`가 `Delete`면 데이터까지 사라진다. Terminating에서 멈추면 파이널라이저 문제다. → 코어 1

   </details>

8. dev/staging/prod 환경은 네임스페이스와 클러스터 중 무엇으로 나누는 것이 일반적이며, 그 이유는?

   <details markdown="1"><summary>답 확인</summary>

   원문은 클러스터로 나누는 것이 일반적이라고 한다. 프로덕션과 개발이 같은 클러스터에 있으면 컨트롤 플레인 장애가 프로덕션에 전파되고, 업그레이드를 먼저 테스트할 수도 없기 때문이다. 작은 조직은 클러스터 하나에 `dev`/`prod` 네임스페이스로 시작해 성장하며 분리해도 된다. → 코어 4

   </details>

### 3. 기억 고리

- **C++ 유추:** 쿠버네티스 네임스페이스 ≈ C++ `namespace` — 이름 충돌만 막을 뿐 접근을 막지 않는다. ⚠️ 깨지는 곳: 쿠버네티스 네임스페이스는 RBAC·쿼터의 단위이기도 하고, 삭제하면 안의 리소스와 (reclaimPolicy에 따라) 데이터까지 실제로 사라진다.
- **비유:** 네임스페이스 = 한 사무실의 팀별 칸막이. 팀 이름표(이름 스코프), 출입 권한(RBAC), 팀 예산(쿼터)은 나뉘지만 통로(네트워크)는 열려 있고 건물 전기·배관(노드·커널·컨트롤 플레인)은 공유한다. ⚠️ 비유가 깨지는 지점: 칸막이 철거(네임스페이스 삭제)는 팀 물건(PVC 데이터 포함)까지 전부 버리는 것이고, 외부 손님이 들어오는 상황(하드 멀티테넌시)이면 칸막이가 아니라 건물 자체(클러스터)를 나눠야 한다.
- **묶음(3의 법칙):** 쿼터 쌍 = ResourceQuota(총량)·LimitRange(개별)·이벤트 확인(재시도 함정) / LimitRange 핵심 3기능 = 기본값 주입·범위 강제(min/max)·비율 상한 / 멀티테넌시 질문 3개 = 테넌트가 누구인가·위협 모델은·임의 코드를 실행하는가.
- **대칭·순서:** ResourceQuota(네임스페이스 총량) ↔ LimitRange(컨테이너 개별), 소프트(실수 방지·커널 공유 허용) ↔ 하드(공격 방어·커널 공유 위험).
