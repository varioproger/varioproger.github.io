# 18장. 워크로드 컨트롤러 — Deployment, StatefulSet, DaemonSet, Job

> **🎮 게임 서버 개발자에게** — 죽은 서버 프로세스를 다시 띄우는 감시 스크립트, LB 뒤에서 서버를 한 대씩 내려 패치하는 무중단 배포, 채널 서버마다 고정 번호와 전용 데이터 디렉터리, 머신마다 깔린 로그 수집 데몬, 새벽 랭킹 정산 cron — 이것들을 직접 짜던 일을 쿠버네티스에서는 **컨트롤러**가 한다. 결정적으로 다른 점은 명령("서버 2번을 재시작해")이 아니라 **원하는 상태("이 템플릿의 Pod가 4개")를 선언**하면 컨트롤러가 조정 루프로 맞춘다는 것이고, 컨트롤러 종류는 "무엇을 원하는 상태로 삼는가"로만 갈린다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 접속 중인 유저가 있는 상태에서 새 버전을 배포해야 하는데, 배포가 중간에 멈춰 진행되지 않는다.
> - 버그 난 버전을 롤백했더니 이번엔 DB 스키마가 안 맞아 구버전이 에러를 낸다.
> - "새벽 3시" 정산 배치가 한국 시각 정오에 돌았다.

## 코어 — 이것만은 100%

> **한 문장:** 모든 워크로드 컨트롤러는 같은 조정 루프를 돌고 "무엇을 원하는 상태로 삼는가"만 다르며, 무상태 앱은 ReplicaSet을 버전별로 감싸 롤링 업데이트·롤백하는 Deployment로, 고유 이름·스토리지·순서가 필요하면 StatefulSet으로, 노드마다 하나는 DaemonSet으로, 끝나야 하는 일은 Job/CronJob으로 돌린다.

1. **같은 조정 루프, 다른 원하는 상태** — ReplicaSet은 "셀렉터에 맞는 Pod N개"만 지킨다. 셀렉터가 소유권을 정하고, 버전 관리는 하지 않는다.
2. **Deployment = 버전별 ReplicaSet** — 리비전마다 ReplicaSet을 만들어 `maxSurge`/`maxUnavailable`과 readiness로 교체하고, 이전 ReplicaSet(replicas 0)을 다시 키워 빠르게 롤백한다(Pod 템플릿만 되돌린다). PDB로 drain 중에도 최소 개수를 지킨다.
3. **StatefulSet의 세 가지 보장** — 안정적 네트워크 ID(헤드리스 서비스), Pod마다 고유 PVC(`volumeClaimTemplates`), 순서 보장. 리더 선출·페일오버는 해 주지 않는다.
4. **DaemonSet·Job·CronJob** — 노드마다 정확히 하나(시스템 에이전트), 끝나야 하는 일(`restartPolicy`는 `OnFailure`/`Never`), 스케줄된 Job(`timeZone`·`concurrencyPolicy`).
5. **선택 트리** — 끝나는가?(Job/CronJob) → 노드마다 하나?(DaemonSet) → 고유 ID·스토리지?(StatefulSet) → 아니면 Deployment(90%).

**이 장의 학습 목표**
- ReplicaSet이 Pod를 어떻게 관리하는지, 왜 직접 쓰지 않는지 설명할 수 있다. (→ 코어 1)
- Deployment의 롤링 업데이트 파라미터를 이해하고 롤백할 수 있다. (→ 코어 2)
- StatefulSet이 제공하는 세 가지 보장과 한계를 설명할 수 있다. (→ 코어 3)
- DaemonSet, Job, CronJob의 용도를 구분하고, 워크로드 성격에 맞는 컨트롤러를 고를 수 있다. (→ 코어 4, 5)

## 코어 1. 같은 조정 루프, 다른 원하는 상태

### 1.1 컨트롤러들의 공통점

**한 줄 요약:** 모든 워크로드 컨트롤러는 조정 루프를 돌며, 다른 점은 "무엇을 원하는 상태로 삼는가"뿐이다.

[15장](15-Pod.md)에서 Pod를 직접 만들면 노드가 죽을 때 그대로 사라진다고 했다. 이 장의 컨트롤러들이 그 문제를 해결한다. 각 컨트롤러는 [13장](13-왜-쿠버네티스인가.md)의 **조정 루프**를 돌리며, 다른 점은 "무엇을 원하는 상태로 삼는가"뿐이다.

```
ReplicaSet   : "이 라벨을 가진 Pod가 N개"
Deployment   : "이 템플릿의 ReplicaSet이 원하는 버전으로"
StatefulSet  : "고유 ID를 가진 Pod가 0..N-1까지 순서대로"
DaemonSet    : "조건에 맞는 모든 노드에 정확히 하나씩"
Job          : "성공적으로 완료된 Pod가 N개"
CronJob      : "스케줄에 맞춰 Job을 생성"
```

### 1.2 ReplicaSet: 개수를 지키는 컨트롤러

**한 줄 요약:** ReplicaSet은 셀렉터에 매칭되는 Pod 수를 `replicas`로 유지할 뿐이고, 셀렉터가 소유권을 정한다.

ReplicaSet은 **셀렉터에 매칭되는 Pod의 개수를 `replicas`로 유지**하는 단 하나의 일을 한다.

```yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: web-rs
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:                      # Pod 템플릿
    metadata:
      labels:
        app: web                 # selector와 일치해야 한다
    spec:
      containers:
        - name: web
          image: hello:1.0
```

조정 루프는 ① 셀렉터에 맞는 Pod를 센다(2개) ② 원하는 수(3개)와 비교한다(1개 부족) ③ template으로 Pod를 1개 생성한다. 초과하면 삭제하는데, Pending 상태, Ready가 아닌 것, 재시작이 많은 것 등 **문제 있는 것을 먼저** 지운다.

**셀렉터가 소유권을 결정한다.** ReplicaSet은 자기가 만들지 않은 Pod도 셀렉터에 맞으면 자기 것으로 간주한다. 그래서 셀렉터가 겹치는 컨트롤러 두 개를 만들면 서로 상대의 Pod를 지우려 드는 참사가 일어난다.

### 1.3 왜 ReplicaSet을 직접 쓰지 않는가

**한 줄 요약:** ReplicaSet은 버전 관리를 하지 않아 템플릿을 바꿔도 기존 Pod가 그대로이므로, Deployment가 감싼다.

ReplicaSet은 개수만 관리할 뿐 버전 관리를 하지 않는다. 템플릿의 이미지를 바꿔도 **기존 Pod는 그대로**이고 새로 만들어지는 Pod부터 적용된다. 롤링 업데이트도, 롤백도 없다. 그래서 실무에서는 **Deployment**를 쓴다.

```
Deployment  (버전 관리, 롤아웃 전략)
    ├─ ReplicaSet v1  (replicas: 0)   ← 롤백용으로 보관
    └─ ReplicaSet v2  (replicas: 3)   ← 현재 활성
           └─ Pod, Pod, Pod
```

## 코어 2. Deployment — 버전별 ReplicaSet으로 교체하고 되돌린다

### 2.1 기본 구조

**한 줄 요약:** Deployment는 replicas·전략·리비전 보관 수·안전장치(readiness, minReadySeconds, progressDeadlineSeconds)를 한 곳에 선언한다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  annotations:
    kubernetes.io/change-cause: "initial deploy v1.0"
spec:
  replicas: 4
  revisionHistoryLimit: 10          # 보관할 이전 ReplicaSet 수 (기본 10)
  minReadySeconds: 10               # Ready 후 이만큼 지나야 "사용 가능"으로 인정
  progressDeadlineSeconds: 600      # 이 시간 안에 진전이 없으면 실패 처리
  selector:
    matchLabels:
      app: web
  strategy:
    type: RollingUpdate             # 또는 Recreate
    rollingUpdate:
      maxSurge: 25%                 # 원하는 수보다 얼마나 더 만들 수 있나
      maxUnavailable: 25%           # 얼마나 부족해도 되나
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: hello:1.0
          readinessProbe:           # 롤링 업데이트의 안전장치
            httpGet: { path: /healthz, port: 8080 }
```

### 2.2 두 가지 전략

**한 줄 요약:** `Recreate`는 전부 내리고 올리며(다운타임), `RollingUpdate`(기본)는 조금씩 교체한다.

- **`Recreate`**: 전부 죽이고 전부 만든다. 다운타임이 생긴다. 두 버전이 동시에 존재하면 안 될 때(DB 스키마 호환성 문제, 파일 락 등) 쓴다.
- **`RollingUpdate`**(기본): 조금씩 교체한다.

```
[v1 v1 v1 v1]
[v1 v1 v1 v1 v2]     ← maxSurge만큼 추가
[v1 v1 v1 v2]        ← v2가 Ready되면 v1 하나 제거
...
[v2 v2 v2 v2]
```

### 2.3 maxSurge와 maxUnavailable

**한 줄 요약:** maxSurge는 올림, maxUnavailable은 내림으로 안전하게 계산하며, 프로덕션 권장은 `1 / 0`이지만 여유 용량이 없으면 롤아웃이 멈춘다.

`replicas: 4`, 둘 다 25%이면 `maxSurge = ceil(4 x 0.25) = 1`(최대 5개 존재), `maxUnavailable = floor(4 x 0.25) = 1`(최소 3개는 사용 가능). 올림/내림이 다르며 안전한 쪽으로 계산한다.

| 설정 | 동작 | 적합한 상황 |
|---|---|---|
| `25% / 25%` (기본) | 균형 | 대부분 |
| `maxSurge: 1`, `maxUnavailable: 0` | **용량을 절대 줄이지 않음.** 새 Pod가 Ready된 뒤에만 기존 것 제거 | 프로덕션 권장 |
| `maxSurge: 0`, `maxUnavailable: 1` | 총 Pod 수가 늘지 않음 | 리소스가 빠듯할 때 |
| `maxSurge: 100%`, `maxUnavailable: 0` | 새 버전 전체를 먼저 띄운 뒤 교체 | 빠른 배포, 리소스 여유 |

> **`maxUnavailable: 0`과 리소스 부족의 충돌** — 새 Pod가 뜰 자리가 있어야 진행된다. 클러스터에 여유가 없으면 새 Pod가 `Pending`에 머물러 롤아웃이 영원히 멈춘다.

**readiness가 롤아웃을 통제한다.** 새 Pod가 `Ready`가 되어야 다음 단계로 넘어간다. `minReadySeconds`를 주면 Ready 후 그 시간 동안 크래시하지 않아야 "사용 가능"으로 인정하므로, 시작 직후에 죽는 버그를 롤아웃 중에 잡을 수 있다. 잘못된 이미지로 업데이트해도 기존 Pod는 유지되어 **서비스는 멈추지 않고 롤아웃만 멈춘다.**

### 2.4 리비전과 롤백

**한 줄 요약:** 롤백은 replicas 0으로 남은 이전 ReplicaSet을 다시 키우는 것이라 빠르지만, Pod 템플릿만 되돌린다.

```bash
kubectl set image deployment/web web=hello:2.0     # 업데이트
kubectl rollout status deployment/web              # 진행 확인
kubectl rollout history deployment/web             # 이력 (CHANGE-CAUSE는 애노테이션에서)
kubectl rollout undo deployment/web                # 직전으로 롤백
kubectl rollout undo deployment/web --to-revision=2
kubectl rollout pause deployment/web               # 진행 중 롤아웃 일시 중지 (resume으로 재개)
```

**롤백이 빠른 이유**는 이전 ReplicaSet이 `replicas: 0`으로 남아 있기 때문이다. 그것을 다시 스케일 업하고 현재 것을 스케일 다운하면 끝이다(이미지도 노드에 캐시되어 있다). `kubectl get rs -l app=web`으로 보면 리비전마다 ReplicaSet이 하나씩 있고 현재 것만 DESIRED가 0이 아니다. `revisionHistoryLimit`을 넘으면 오래된 것부터 삭제된다.

> **롤백이 복구하지 못하는 것** — Deployment 롤백은 **Pod 템플릿만** 되돌린다. DB 스키마 마이그레이션, ConfigMap/Secret의 내용, 외부 시스템에 미친 부수 효과는 되돌아가지 않는다. 마이그레이션은 하위 호환되게 설계한다.

### 2.5 롤링 업데이트 실전 흐름

**한 줄 요약:** `1 / 0` 설정에서는 사용 가능한 Pod가 원하는 수 아래로 떨어지지 않고, 잘못된 이미지는 새 Pod 하나만 실패시킨다.

`replicas: 4`, `maxSurge: 1`, `maxUnavailable: 0`, `minReadySeconds: 5`, readinessProbe가 있는 Deployment를 업데이트한다고 하자. 터미널 하나에서 `kubectl get pods -l app=web -w`로 지켜보고, 다른 터미널에서 업데이트한다.

```bash
kubectl set image deployment/web web=hello:2.0
kubectl annotate deployment/web kubernetes.io/change-cause="v2 - hello 2.0" --overwrite
kubectl rollout status deployment/web
```

관찰되는 패턴은 다음과 같다.

```
새 Pod 생성 (총 5개)          ← maxSurge: 1
새 Pod가 Ready
5초 대기                      ← minReadySeconds
기존 Pod 하나 Terminating (총 4개)
새 Pod 생성 (총 5개)
... 반복 ...
```

**사용 가능한 Pod가 4개 미만으로 떨어지지 않는다.** `maxUnavailable: 0`의 효과다. 존재하지 않는 이미지 태그로 업데이트하면 새 Pod 하나만 `ImagePullBackOff`에 빠지고 기존 4개는 `Running`으로 남는다. `kubectl rollout status --timeout=30s`가 시간 초과로 끝나면 `kubectl rollout undo`로 되돌린다.

> **[보충]** 위 예는 관찰하기 쉽도록 명령형 `kubectl set image`를 썼다. 실제 운영에서는 매니페스트 파일의 `image` 값을 바꾸고 `kubectl apply -f`로 적용하는 선언형 방식([14장](14-API-오브젝트-kubectl-YAML.md))이 일반적이다. 그래야 파일과 클러스터 상태가 어긋나지 않는다.

### 2.6 블루-그린과 카나리

**한 줄 요약:** 블루-그린은 Service 셀렉터를 한 번에 바꾸고(리소스 2배), 카나리는 replica 수로 비율을 조절한다(정밀하지 않음).

- **블루-그린**: 두 버전을 별도 Deployment로 완전히 띄우고, Service 셀렉터(`slot: blue` → `slot: green`)를 바꿔 한 번에 전환한다. 즉시 전환·즉시 복귀가 가능하지만 리소스가 2배 필요하다.
- **카나리**: 같은 Service 셀렉터를 공유하는 stable(9개)과 canary(1개) 같은 식으로 replica 수로 비율(10%)을 조절한다. 한계는 비율이 Pod 수에 묶이고, 분배가 정확하지 않고, 세션 고정이 안 되며, 자동 롤백이 없다는 것이다. 정밀한 카나리는 인그레스 컨트롤러의 가중치 기능이나 Argo Rollouts / Flagger 같은 도구로 구현한다.

### 2.7 Deployment 모범 사례

**한 줄 요약:** replicas 2 이상, 용량 유지 롤아웃, 명시적 태그, 프로브·종료 훅·리소스, 그리고 PDB.

- `replicas`는 최소 2 이상(단일 장애점 제거).
- `maxSurge: 1`, `maxUnavailable: 0`으로 용량 유지, `minReadySeconds`, `progressDeadlineSeconds` 설정.
- 이미지는 `latest` 금지, 명시적 태그 사용.
- readinessProbe는 필수, `preStop: sleep`([16장](16-Pod-생명주기와-헬스체크.md)), `resources.requests/limits`([19장](19-리소스-요청-제한과-스케줄링-기초.md)) 설정.
- **PodDisruptionBudget**을 함께 정의한다(아래). 없으면 노드 드레인 시 모든 Pod가 동시에 축출될 수 있다.

### 2.8 PodDisruptionBudget: 노드 유지보수 중에도 최소 개수 지키기

**한 줄 요약:** drain의 Eviction 요청을 API 서버가 PDB로 걸러 최소 개수를 지키지만, 자발적 중단만 막는다.

노드를 업그레이드하거나 교체할 때는 `kubectl drain <node> --ignore-daemonsets`로 그 노드의 Pod를 비운다. drain은 노드에 스케줄 금지 표시를 하고, 각 Pod에 Eviction API를 호출한다. 이때 API 서버가 **PodDisruptionBudget(PDB)** 을 확인해, 허용 범위 안이면 Pod를 정상 종료([16장](16-Pod-생명주기와-헬스체크.md))시키고 위반이면 거절한다(kubectl은 재시도한다).

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-pdb
spec:
  maxUnavailable: 1          # 또는 minAvailable: 2
  selector:
    matchLabels: { app: web }
```

> **`minAvailable`을 replicas와 같게 두면 drain이 영원히 멈춘다.** `replicas: 3`에 `minAvailable: 3`이면 하나도 축출할 수 없다. `minAvailable: 2` 또는 `maxUnavailable: 1`로 둔다. HPA로 replicas가 오르내린다면 `maxUnavailable`이 의미가 유지되어 더 낫다.

`kubectl get pdb -A`의 `ALLOWED DISRUPTIONS`가 0이면 drain이 막힌 상태다. 그리고 **PDB는 drain 같은 자발적 중단만 제어한다.** 노드 자원 부족으로 kubelet이 Pod를 축출하는 비자발적 중단은 막지 못한다([19장](19-리소스-요청-제한과-스케줄링-기초.md)).

## 코어 3. StatefulSet — 이름·스토리지·순서의 세 가지 보장

### 3.1 Deployment로는 안 되는 것

**한 줄 요약:** 무작위 이름, 공유 볼륨, 순서 없음, 불안정한 네트워크 ID 때문에 DB 클러스터는 Deployment로 못 돌린다.

데이터베이스 클러스터를 Deployment로 배포하면 문제가 줄줄이 나온다.

1. Pod 이름이 무작위다. 재시작하면 이름이 바뀌어 "1번 노드가 프라이머리" 같은 규칙을 만들 수 없다.
2. 모든 Pod가 같은 볼륨을 공유한다. 각자 자기 데이터 디렉터리가 필요한데 불가능하다.
3. 시작 순서가 없다. 첫 노드가 뜬 뒤 나머지가 조인해야 하는데 동시에 뜬다.
4. 안정적인 네트워크 ID가 없다. Pod IP가 바뀌면 클러스터 멤버십이 깨진다.

### 3.2 세 가지 보장

**한 줄 요약:** ① 고유 네트워크 ID(헤드리스 서비스) ② Pod별 PVC(`volumeClaimTemplates`) ③ 순서(생성 0→N, 삭제 역순).

**① 안정적이고 고유한 네트워크 ID** — `web-0`, `web-1`, `web-2`처럼 이름이 순서를 갖고 재시작해도 같다. 각 Pod는 `web-0.web-headless.default.svc.cluster.local` 같은 고유 DNS 이름을 얻는데, 이를 위해 **헤드리스 서비스**(`clusterIP: None`)가 필요하다([21장](../4부-노출-데이터-운영/21-네트워크-모델과-Service.md)).

**② 안정적인 스토리지** — `volumeClaimTemplates`로 각 Pod마다 자기만의 PVC가 생성된다(`web-0` → `data-web-0`). Pod가 다시 만들어져도 **같은 이름의 PVC에 다시 붙어** 데이터가 유지된다.

**③ 순서 보장** — 생성은 `web-0` → (Ready 대기) → `web-1` → `web-2`, 삭제는 역순이다.

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
spec:
  serviceName: db-headless          # 헤드리스 서비스 이름
  replicas: 3
  podManagementPolicy: OrderedReady # 또는 Parallel
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      partition: 0                  # 이 인덱스 이상만 업데이트
  selector:
    matchLabels: { app: db }
  template:
    metadata:
      labels: { app: db }
    spec:
      containers:
        - name: postgres
          image: postgres:16-alpine
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:             # Pod마다 PVC 생성
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 5Gi
```

### 3.3 관리 정책, 업데이트 순서, PVC 보존

**한 줄 요약:** 업데이트는 높은 인덱스부터 역순이고 `partition`으로 단계적 롤아웃이 가능하며, 스케일 다운해도 PVC는 남는다.

- `podManagementPolicy`: `OrderedReady`(기본, 하나씩 순서대로)와 `Parallel`(동시에 생성/삭제하되 이름과 스토리지는 여전히 안정적).
- **롤링 업데이트는 높은 인덱스부터 역순**(`web-2` → `web-1` → `web-0`)이다. `partition: 2`를 주면 인덱스 2 이상만 업데이트되므로, partition을 단계적으로 낮추며 한 인스턴스씩 검증하는 **스테이지드 롤아웃(카나리)** 이 가능하다.

> **스케일 다운해도 PVC는 삭제되지 않는다.** 실수로 스케일 다운해도 데이터를 잃지 않게 하려는 의도된 동작이며, 다시 스케일 업하면 같은 PVC에 재연결된다. 정말 지우려면 수동으로 `kubectl delete pvc`를 한다(`persistentVolumeClaimRetentionPolicy`로 정책 지정도 가능).

### 3.4 StatefulSet의 한계

**한 줄 요약:** 리더 선출·복제·페일오버·백업은 해 주지 않으므로 실무는 오퍼레이터나 관리형 DB를 먼저 검토한다.

StatefulSet이 해 주는 것은 **이름, 스토리지, 순서**뿐이다. 리더 선출, 복제 설정, 페일오버, 백업, 스키마 마이그레이션은 해 주지 않는다. 이는 애플리케이션이나 오퍼레이터의 일이어서, 실무에서는 StatefulSet을 직접 쓰기보다 DB별 오퍼레이터(CloudNativePG, Strimzi 등)를 쓴다.

> **더 근본적인 질문** — 프로덕션 DB를 쿠버네티스에서 운영해야 하는가? 관리형 서비스(RDS, Cloud SQL)가 나은 경우가 많다. StatefulSet은 "쿠버네티스에서 상태를 다룰 수 있다"는 것이지 "다뤄야 한다"는 뜻은 아니다.

## 코어 4. DaemonSet·Job·CronJob — 노드마다 하나, 끝나는 일

### 4.1 DaemonSet: 노드마다 하나씩

**한 줄 요약:** 모든(또는 조건에 맞는) 노드에 정확히 하나의 Pod를 두며, 시스템 에이전트용이고 테인트 노드에는 톨러레이션이 필요하다.

**모든(또는 조건에 맞는) 노드에 정확히 하나의 Pod**를 배치한다. 노드가 추가되면 Pod가 자동 생기고, 노드가 제거되면 사라진다. `kube-proxy`와 CNI 플러그인(kindnet 등)이 DaemonSet이다(`kubectl get daemonset -n kube-system`).

전형적 용도는 로그 수집기(Fluent Bit 등), 모니터링 에이전트(node-exporter), 네트워크 플러그인, CSI 노드 플러그인, 보안 에이전트(Falco)다.

DaemonSet 특유의 설정:

- **`tolerations`**: 기본적으로 테인트가 걸린 노드(컨트롤 플레인 등)에는 배치되지 않는다. 시스템 에이전트는 모든 노드에 필요하므로 `operator: Exists`로 테인트를 감내하게 하는 것이 흔하다.
- **`nodeSelector`**: 특정 노드에만 배치.
- **`hostNetwork: true`, `hostPath` 볼륨**: 노드의 네트워크/파일시스템에 직접 접근. 보안 검토 대상이다.
- DaemonSet Pod도 일반 스케줄러를 거치므로 리소스 부족으로 Pending에 머물 수 있다.

노드당 여러 개가 필요하면 DaemonSet은 불가능하고(Deployment + anti-affinity), Pod마다 다른 설정이 필요하면 사이드카를 쓴다.

### 4.2 Job: 완료를 목표로 하는 워크로드

**한 줄 요약:** Job은 "끝나야 하는" 일을 관리하므로 `restartPolicy`는 `OnFailure`/`Never`만 가능하다.

Deployment는 "계속 돌아야 하는" 것을, Job은 "끝나야 하는" 것을 관리한다.

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: data-migration
spec:
  completions: 1              # 성공해야 할 Pod 수
  parallelism: 1              # 동시 실행 수
  backoffLimit: 4             # 실패 재시도 횟수 (기본 6)
  activeDeadlineSeconds: 600  # 전체 제한 시간
  ttlSecondsAfterFinished: 3600   # 완료 후 자동 삭제
  template:
    spec:
      restartPolicy: OnFailure    # Always는 사용 불가
      containers:
        - name: migrate
          image: myapp:1.2
          command: ["python", "manage.py", "migrate"]
```

`restartPolicy`는 `OnFailure`(같은 Pod 안에서 컨테이너 재시작) 또는 `Never`(실패한 Pod를 남기고 새 Pod 생성, 로그를 보기 쉬움)만 가능하다. `Always`면 영원히 끝나지 않기 때문이다.

병렬 패턴: 단일 작업(`completions: 1`), 고정 완료 수(`completions: 10, parallelism: 3`), 작업 큐(`completions` 미지정, 하나라도 성공하면 마무리), 인덱스 지정(`completionMode: Indexed`, 각 Pod가 `JOB_COMPLETION_INDEX` 환경변수를 받아 샤딩 처리).

흔한 문제: `BackoffLimitExceeded`(재시도 소진), `DeadlineExceeded`(`activeDeadlineSeconds` 초과), 그리고 **사이드카가 계속 실행되어 Job이 완료되지 않는 경우**([15장](15-Pod.md)의 `initContainers` + `restartPolicy: Always` 사이드카로 해결).

### 4.3 CronJob: 스케줄된 Job

**한 줄 요약:** CronJob은 `timeZone`이 없으면 UTC 기준이 되기 쉽고, 겹치는 실행은 `concurrencyPolicy`로 정한다.

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-backup
spec:
  schedule: "0 3 * * *"
  timeZone: "Asia/Seoul"               # v1.27+ 에서 타임존 지정 가능
  concurrencyPolicy: Forbid            # Allow | Forbid | Replace
  startingDeadlineSeconds: 300
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 3
  jobTemplate:
    spec:
      backoffLimit: 2
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: backup
              image: backup-tool:1.0
```

> **타임존 함정** — `timeZone` 필드가 없으면 컨트롤러 매니저의 시간대(보통 UTC)를 따른다. "매일 새벽 3시"라고 적었는데 한국 시각 정오에 실행되는 사고가 흔하다.

| `concurrencyPolicy` | 동작 |
|---|---|
| `Allow`(기본) | 이전 Job이 안 끝나도 새로 시작 |
| `Forbid` | 이전 Job이 실행 중이면 건너뜀 (백업처럼 동시 실행이 위험한 작업) |
| `Replace` | 이전 Job을 죽이고 새로 시작 |

테스트용 수동 실행은 `kubectl create job manual-backup --from=cronjob/nightly-backup`, 일시 중지는 `suspend: true`로 한다.

## 코어 5. 컨트롤러 선택 트리

### 5.1 결정 트리와 비교표

**한 줄 요약:** 끝나는가 → 노드마다 하나인가 → 고유 ID·스토리지가 있는가 순으로 묻고, 나머지는 Deployment다.

```
워크로드가 끝나는가?
├─ 예 → 정해진 시각에 반복? ── 예: CronJob / 아니오: Job
└─ 아니오 (계속 실행)
    └─ 모든 노드에 하나씩 필요? ── 예: DaemonSet
        └─ 아니오 → 각 인스턴스가 고유 ID나 스토리지를 갖는가?
            ├─ 예 → StatefulSet (오퍼레이터가 있다면 먼저 검토)
            └─ 아니오 → Deployment  ← 90%의 경우
```

| | Deployment | StatefulSet | DaemonSet | Job | CronJob |
|---|---|---|---|---|---|
| Pod 이름 | 무작위 | `name-0`, `name-1` | 무작위 | 무작위 | 무작위 |
| 시작 순서 | 동시 | 순차(기본) | 동시 | 병렬 설정 가능 | - |
| 스토리지 | 공유 또는 없음 | Pod마다 고유 PVC | hostPath 주로 | 임시 | 임시 |
| 업데이트 | 롤링 | 롤링(역순) | 롤링 | - | - |
| 대표 용도 | 웹, API, 워커 | DB, 큐, 분산 스토리지 | 로그·모니터링·네트워크 | 마이그레이션, 배치 | 백업, 리포트 |

## 실무 적용

### 체크리스트

- [ ] **ReplicaSet**은 개수만 지킨다. 템플릿을 바꿔도 기존 Pod는 그대로이므로 직접 쓰지 않고 Deployment가 감싼다. 셀렉터가 겹치는 컨트롤러를 만들지 않는다. (→ 코어 1)
- [ ] **Deployment의 롤링 업데이트**는 `maxSurge`/`maxUnavailable`로 속도와 안전성을 조절한다. 프로덕션 권장은 `maxSurge: 1, maxUnavailable: 0`이며 **readiness 프로브가 안전장치**다. 이때 클러스터에 새 Pod 한 개분의 여유가 있는지 확인한다. (→ 코어 2)
- [ ] `replicas` 2 이상, `minReadySeconds`·`progressDeadlineSeconds` 설정, `latest` 금지, readinessProbe·`preStop: sleep`·`resources` 설정. (→ 코어 2)
- [ ] 롤백은 이전 ReplicaSet을 다시 스케일 업하는 것이라 빠르다. 단 **DB 스키마와 ConfigMap 내용은 되돌아가지 않으므로** 마이그레이션은 하위 호환되게 설계한다. (→ 코어 2)
- [ ] **PodDisruptionBudget**은 drain 같은 자발적 중단 중에도 최소 개수를 지킨다. `minAvailable`을 replicas와 같게 두면 drain이 멈춘다. `ALLOWED DISRUPTIONS`를 확인한다. (→ 코어 2)
- [ ] **StatefulSet**은 안정적 이름·스토리지·순서를 보장하지만 리더 선출·페일오버는 해 주지 않는다. 스케일 다운해도 PVC는 남는다. 오퍼레이터나 관리형 서비스를 먼저 검토한다. (→ 코어 3)
- [ ] **DaemonSet**은 노드마다 하나씩(시스템 에이전트), **Job**은 완료가 목표, **CronJob**은 `timeZone`과 `concurrencyPolicy`를 챙긴다. (→ 코어 4)
- [ ] 대부분의 무상태 앱은 **Deployment**다. (→ 코어 5)

### 시나리오로 확인하기

1. **상황:** 유저가 접속 중이라 용량을 줄이면 안 된다고 판단해 `maxSurge: 1`, `maxUnavailable: 0`으로 배포했다. 그런데 `rollout status`가 끝나지 않고, 새 Pod 하나가 계속 `Pending`이다.
   **질문:** 원인과 대응은?

   <details markdown="1"><summary>답 확인</summary>

   `maxUnavailable: 0`이면 기존 Pod를 먼저 줄일 수 없으므로 새 Pod가 뜰 자리가 있어야 진행된다. 클러스터에 여유가 없어 새 Pod가 Pending에 머물러 롤아웃이 영원히 멈춘 것이다(기존 Pod는 유지되어 서비스는 계속된다). 노드를 추가하거나 다른 워크로드의 requests를 조정하고, 리소스가 빠듯한 환경이라면 `maxSurge: 0`, `maxUnavailable: 1`처럼 총 Pod 수가 늘지 않는 설정을 검토한다. → 코어 2

   </details>

2. **상황:** v2 배포에 컬럼 삭제 마이그레이션이 포함되어 있었다. v2에 버그가 있어 `kubectl rollout undo`로 v1으로 되돌렸는데, v1이 "컬럼이 없다"는 에러를 쏟아 낸다.
   **질문:** 롤백이 왜 문제를 해결하지 못했나?

   <details markdown="1"><summary>답 확인</summary>

   Deployment 롤백은 Pod 템플릿만 되돌린다. DB 스키마 마이그레이션, ConfigMap/Secret 내용, 외부 시스템의 부수 효과는 되돌아가지 않는다. 마이그레이션은 구버전과 신버전이 모두 동작하도록 하위 호환되게 설계해야 한다(예: 컬럼 삭제는 구버전이 더 이상 쓰지 않게 된 뒤로 미룬다). 두 버전이 동시에 존재하면 안 되는 경우라면 `Recreate` 전략을 쓴다. → 코어 2

   </details>

3. **상황:** 노드 OS 업그레이드를 위해 `kubectl drain`을 했는데 끝나지 않는다. 게임 API Deployment는 `replicas: 3`, PDB는 `minAvailable: 3`이다.
   **질문:** 무엇이 막고 있고 어떻게 고치나?

   <details markdown="1"><summary>답 확인</summary>

   `minAvailable`이 replicas와 같아 하나도 축출할 수 없다(`kubectl get pdb -A`의 `ALLOWED DISRUPTIONS`가 0). API 서버가 Eviction을 거절하고 kubectl은 재시도만 한다. `minAvailable: 2` 또는 `maxUnavailable: 1`로 바꾼다. HPA로 replicas가 변한다면 `maxUnavailable`이 낫다. → 코어 2

   </details>

4. **상황:** 채널 서버들이 각자 번호(`ch-0`, `ch-1`…)로 매칭 서버에 등록되고, 자기 로컬 데이터를 디스크에 쓴다. 이를 Deployment로 올렸더니 재시작 후 매칭 서버에 낯선 이름이 등록되고 데이터가 섞였다.
   **질문:** 어떤 컨트롤러가 맞고, 그것이 해 주지 않는 것은?

   <details markdown="1"><summary>답 확인</summary>

   Deployment는 Pod 이름이 무작위이고 모든 Pod가 같은 볼륨을 공유한다. StatefulSet은 재시작해도 같은 이름(`ch-0`…)과 헤드리스 서비스를 통한 고유 DNS, `volumeClaimTemplates`로 Pod별 PVC, 순서 있는 생성·삭제를 보장한다. 단 리더 선출·복제·페일오버는 해 주지 않으므로 애플리케이션(또는 오퍼레이터)이 맡아야 한다. → 코어 3

   </details>

5. **상황:** 랭킹 정산 CronJob을 `schedule: "0 5 * * *"`로 만들었는데 한국 시각 오후 2시에 돌았다. 게다가 정산이 1시간 넘게 걸리는 날에는 다음 회차가 겹쳐 실행된다고 한다(매시 정각 스케줄로 바꾼 뒤).
   **질문:** 각각 무엇을 설정해야 하나?

   <details markdown="1"><summary>답 확인</summary>

   `timeZone` 필드가 없으면 컨트롤러 매니저 시간대(보통 UTC)를 따르므로 `timeZone: "Asia/Seoul"`(v1.27+)을 지정한다. 겹침은 `concurrencyPolicy` 기본값 `Allow` 때문이므로, 동시 실행이 위험한 작업이면 `Forbid`(실행 중이면 건너뜀)를 쓴다. 테스트는 `kubectl create job ... --from=cronjob/...`로 수동 실행한다. → 코어 4

   </details>

### 2. 인출 질문

1. ReplicaSet만 쓰면 이미지를 바꿔도 기존 Pod가 교체되지 않는 이유는 무엇이며, Deployment는 이를 어떻게 해결하는가? (확인 질문 1)

   <details markdown="1"><summary>답 확인</summary>

   ReplicaSet은 셀렉터에 맞는 Pod의 개수만 지킬 뿐 버전 관리를 하지 않으므로, 템플릿을 바꿔도 개수가 맞으면 기존 Pod는 그대로이고 새로 만들어지는 Pod부터 적용된다. Deployment는 템플릿이 바뀔 때마다 새 ReplicaSet을 만들고 새 것을 늘리고 옛 것을 줄이는 롤링 업데이트를 하며, 이전 ReplicaSet을 replicas 0으로 보관해 롤백도 제공한다. → 코어 1, 코어 2

   </details>

2. `maxSurge: 1`, `maxUnavailable: 0`으로 롤링 업데이트할 때 클러스터에 여유 용량이 없으면 어떻게 되는가? (확인 질문 2)

   <details markdown="1"><summary>답 확인</summary>

   기존 Pod를 먼저 줄일 수 없으므로 새 Pod가 뜰 자리가 있어야 진행된다. 여유가 없으면 새 Pod가 `Pending`에 머물러 롤아웃이 영원히 멈춘다(기존 Pod는 유지되어 서비스는 계속된다). → 코어 2

   </details>

3. 데이터베이스 인스턴스 3개를 띄워야 한다. Deployment 대신 StatefulSet이 필요한 이유 세 가지를 말해 보라. (확인 질문 3)

   <details markdown="1"><summary>답 확인</summary>

   ① 안정적이고 고유한 네트워크 ID: `db-0`, `db-1`처럼 재시작해도 같은 이름과 헤드리스 서비스를 통한 고유 DNS를 얻어 "0번이 프라이머리" 같은 규칙과 클러스터 멤버십을 유지한다. ② 안정적인 스토리지: `volumeClaimTemplates`로 Pod마다 자기 PVC가 생기고 재생성돼도 같은 PVC에 붙는다. ③ 순서 보장: `db-0`이 Ready된 뒤 다음이 뜨고 삭제는 역순이다. → 코어 3

   </details>

4. `replicas: 4`, `maxSurge: 25%`, `maxUnavailable: 25%`일 때 동시에 존재할 수 있는 최대 Pod 수와 최소 사용 가능 Pod 수는?

   <details markdown="1"><summary>답 확인</summary>

   maxSurge는 올림(ceil(4 x 0.25) = 1)이라 최대 5개, maxUnavailable은 내림(floor(4 x 0.25) = 1)이라 최소 3개가 사용 가능하다. 올림/내림이 다른 것은 안전한 쪽으로 계산하기 때문이다. → 코어 2

   </details>

5. Deployment 롤백이 빠른 이유와, 롤백이 되돌리지 못하는 것은?

   <details markdown="1"><summary>답 확인</summary>

   이전 ReplicaSet이 `replicas: 0`으로 남아 있어 그것을 다시 스케일 업하고 현재 것을 줄이기만 하면 되고, 이미지도 노드에 캐시되어 있다. 하지만 롤백은 Pod 템플릿만 되돌리므로 DB 스키마 마이그레이션, ConfigMap/Secret 내용, 외부 시스템에 미친 부수 효과는 되돌아가지 않는다. 마이그레이션은 하위 호환되게 설계한다. → 코어 2

   </details>

6. 잘못된 이미지 태그로 업데이트하면 서비스는 어떻게 되며, `minReadySeconds`는 어떤 역할을 하나?

   <details markdown="1"><summary>답 확인</summary>

   새 Pod 하나만 `ImagePullBackOff`에 빠지고 기존 Pod는 Running으로 남아 서비스는 멈추지 않고 롤아웃만 멈춘다(readiness가 롤아웃을 통제). `minReadySeconds`는 Ready 후 그 시간 동안 크래시하지 않아야 "사용 가능"으로 인정해, 시작 직후 죽는 버그를 롤아웃 중에 잡게 한다. → 코어 2

   </details>

7. PodDisruptionBudget은 무엇을 막고, 어떤 설정이 drain을 영원히 멈추게 하나? 막지 못하는 것은?

   <details markdown="1"><summary>답 확인</summary>

   drain 시 Eviction API 호출에 대해 API 서버가 PDB를 확인해 허용 범위를 넘는 축출을 거절하므로, 노드 유지보수 중에도 최소 개수를 지킨다. `replicas: 3`에 `minAvailable: 3`처럼 replicas와 같게 두면 하나도 축출할 수 없어 drain이 멈춘다(`maxUnavailable: 1` 권장). PDB는 자발적 중단만 제어하고, 노드 자원 부족으로 kubelet이 축출하는 비자발적 중단은 막지 못한다. → 코어 2

   </details>

8. StatefulSet의 롤링 업데이트 순서와 `partition`의 용도, 스케일 다운 시 PVC는?

   <details markdown="1"><summary>답 확인</summary>

   높은 인덱스부터 역순(`web-2` → `web-1` → `web-0`)으로 업데이트한다. `partition: N`이면 인덱스 N 이상만 업데이트되므로 partition을 단계적으로 낮추며 한 인스턴스씩 검증하는 스테이지드 롤아웃(카나리)이 가능하다. 스케일 다운해도 데이터 보호를 위해 PVC는 삭제되지 않고, 다시 스케일 업하면 같은 PVC에 재연결된다. → 코어 3

   </details>

9. Job에서 `restartPolicy: Always`를 쓸 수 없는 이유와, `OnFailure`와 `Never`의 차이는?

   <details markdown="1"><summary>답 확인</summary>

   Job은 "끝나야 하는" 워크로드인데 Always면 영원히 끝나지 않기 때문이다. `OnFailure`는 같은 Pod 안에서 컨테이너를 재시작하고, `Never`는 실패한 Pod를 남기고 새 Pod를 만들어 로그를 보기 쉽다. → 코어 4

   </details>

10. CronJob의 타임존 함정과 `concurrencyPolicy: Forbid`가 맞는 작업은?

    <details markdown="1"><summary>답 확인</summary>

    `timeZone` 필드가 없으면 컨트롤러 매니저의 시간대(보통 UTC)를 따라 "새벽 3시"가 한국 시각 정오에 실행되는 사고가 흔하다(v1.27+에서 `timeZone: "Asia/Seoul"` 지정 가능). `Forbid`는 이전 Job이 실행 중이면 건너뛰므로 백업처럼 동시 실행이 위험한 작업에 맞다. → 코어 4

    </details>

11. DaemonSet은 어떤 워크로드에 쓰며, 컨트롤 플레인 노드에도 배치하려면?

    <details markdown="1"><summary>답 확인</summary>

    모든(또는 조건에 맞는) 노드에 정확히 하나씩 필요한 시스템 에이전트(로그 수집기, node-exporter, CNI 플러그인, kube-proxy, CSI 노드 플러그인, 보안 에이전트)에 쓴다. 테인트가 걸린 노드에는 기본적으로 배치되지 않으므로 `tolerations`에 `operator: Exists`를 준다. → 코어 4

    </details>

### 3. 기억 고리

- **C++ 유추:** ReplicaSet ≈ 죽은 서버 프로세스를 다시 띄우는 감시 스크립트, Deployment 롤백 ≈ 이전 빌드 폴더로 실행 경로 되돌리기. ⚠️ 깨지는 곳: ReplicaSet은 PID가 아니라 라벨 셀렉터로 소유권을 판단해 남의 Pod까지 자기 것으로 셀 수 있고, 롤백은 바이너리(Pod 템플릿)만 되돌릴 뿐 DB 스키마·ConfigMap은 그대로다.
- **비유:** Deployment = 버전별 팀장(ReplicaSet)을 두는 본부장. 새 버전 팀장을 세워 인원을 조금씩 옮기고, 옛 팀장은 인원 0명으로 대기시켜 두었다가 문제가 생기면 다시 인원을 돌려준다(롤백). ⚠️ 비유가 깨지는 지점: 본부장이 되돌리는 것은 Pod 템플릿뿐이라, 그 사이 바뀐 DB 스키마나 ConfigMap 내용은 되돌아오지 않는다.
- **묶음(3의 법칙):** StatefulSet 보장 3가지(이름·스토리지·순서) / Deployment 안전장치 3가지(readinessProbe·minReadySeconds·progressDeadlineSeconds) / CronJob concurrencyPolicy 3가지(Allow·Forbid·Replace).
- **대칭·순서:** Recreate(다운타임) ↔ RollingUpdate, maxSurge(올림) ↔ maxUnavailable(내림), 블루-그린(셀렉터 전환·리소스 2배) ↔ 카나리(replica 비율), StatefulSet 생성(0→N) ↔ 삭제·업데이트(N→0). 선택 순서: 끝나는가 → 노드마다 → 고유 ID → Deployment.
