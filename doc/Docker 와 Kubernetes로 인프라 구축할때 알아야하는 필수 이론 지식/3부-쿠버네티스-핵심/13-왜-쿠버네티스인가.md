# 13장. 왜 쿠버네티스인가 — 선언적 상태와 아키텍처

> **🎮 게임 서버 개발자에게** — 서버 프로세스를 머신마다 직접 띄우고, 워치독 스크립트로 죽은 프로세스를 되살리고, 배포 스크립트로 점검 배포를 하던 일을 쿠버네티스는 "원하는 상태를 적어 두면 컨트롤러가 계속 맞춘다"는 한 가지 방식으로 대신한다. 결정적으로 다른 점은 **명령을 보내는 것이 아니라 상태를 적어 둔다**는 것, 그리고 컴포넌트끼리 직접 RPC를 주고받지 않고 **모두 API 서버를 통해서만** 협업한다는 것이다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 새벽에 서버 한 대가 죽었는데, 아무도 손대지 않았는데도 서비스가 복구되어 있다. 무엇이 무엇을 했는지 설명해야 한다.
> - 컨트롤 플레인(또는 매니지드 클러스터의 API 서버)이 잠시 응답하지 않는다. 지금 접속 중인 유저가 끊기는지, 배포만 멈추는지 판단해야 한다.
> - 팀이 "우리도 쿠버네티스로 가자"고 한다. 서비스 수·운영 인력·지연 요구를 놓고 도입이 정당한지 판단해야 한다.

## 코어 — 이것만은 100%

> **한 문장:** 컨테이너로 서비스가 잘게 쪼개지자 배치·복구·배포 결정이 사람 손을 넘어섰고, 쿠버네티스는 spec에 원하는 상태를 선언하면 API 서버를 중심으로 한 컨트롤러들이 관찰-비교-조치 루프로 그 상태를 계속 유지하게 해 준다.

1. **문제의 진화: 드리프트 → 배포 복잡도 → 오케스트레이터** — 컨테이너는 실행 단위의 재현성(드리프트)을 풀었지만, 서비스가 늘자 배치·복구·디스커버리·배포·스케일링이 사람이 감당할 수 없는 조합 문제가 되었다. 이를 대신 결정하는 것이 오케스트레이터다.
2. **선언적 상태 + 조정 루프(레벨 트리거)** — spec(사람이 씀)과 status(시스템이 씀)의 차이를 관찰→비교→조치로 줄인다. "무엇이 바뀌었나"가 아니라 "지금 어떤가"로 판단하므로 이벤트를 놓쳐도 다음 루프에서 바로잡힌다.
3. **컨트롤 플레인(결정) / 워커 노드(실행), 모든 통신은 API 서버 경유** — apiserver·etcd·scheduler·controller-manager vs kubelet·kube-proxy·컨테이너 런타임. kubelet은 pull 모델이라 컨트롤 플레인이 죽어도 실행 중인 Pod는 계속 돈다.
4. **도입 판단: "사람이 손으로 하는 반복 결정"이 많은가** — 서비스가 적거나 운영 인력이 없으면 다른 선택지를 먼저 본다.

## C++·TCP 서버 경험에서 출발하기

| 이미 아는 것 (C++/소켓 서버) | 이 장의 개념 | 같은 점 | ⚠️ 다른 점 (유추가 깨지는 곳) |
|---|---|---|---|
| epoll의 edge-triggered(EPOLLET) vs level-triggered | 엣지 트리거 vs 레벨 트리거 조정 | ET는 "변화"에만 알려 주므로 한 번 덜 읽으면 놓치고, LT는 "아직 읽을 게 남은 상태"면 계속 알려 준다. 쿠버네티스 컨트롤러는 LT처럼 "지금 상태"를 본다 | epoll은 한 커널의 fd 준비 상태이고, 쿠버네티스는 etcd에 저장된 분산 오브젝트의 상태다. "준비됨" 비트가 아니라 원하는 개수·이미지 같은 목표와의 차이를 계산한다 |
| 델타 패킷 동기화 vs 주기적 전체 스냅샷 동기화 | 이벤트 기반 vs 상태 기반 판단 | 델타 하나가 유실되면 클라이언트 상태가 영영 어긋나지만, 스냅샷을 다시 비교하면 복구된다 | 쿠버네티스에서 "스냅샷과 비교해 맞추는" 주체는 클라이언트가 아니라 컨트롤러이고, 맞추는 방법은 상태 덮어쓰기가 아니라 Pod 생성·삭제 같은 조치다 |
| 프로세스 워치독(죽으면 같은 머신에서 재실행) | 조정 루프(ReplicaSet 컨트롤러 등) | 죽은 것을 사람 없이 되살린다 | 워치독은 "이 머신의 이 프로세스"를 살리지만, 조정 루프는 "클러스터 전체에 N개"를 유지한다. 노드가 죽으면 **다른 노드에 새 Pod**를 만든다 |
| 마스터(로비) 서버가 채널 서버 배치를 결정하고, 각 머신의 에이전트에 명령 패킷을 보냄 | 컨트롤 플레인 / 워커 노드 | 결정하는 쪽과 실행하는 쪽이 나뉜다 | 스케줄러는 kubelet에 명령을 보내지 않는다. API 서버에 "이 Pod는 이 노드"라고 기록만 하고, kubelet이 watch로 **스스로 가져간다**(pull). 그래서 결정하는 쪽이 죽어도 실행 중인 것은 멈추지 않는다 |
| ssh로 서버마다 실행하는 배포 스크립트 | 명령형 방식 | 절차를 순서대로 지시한다 | 쿠버네티스의 기본은 선언형이다. 어느 서버에, 어떤 순서로, 죽으면 어떻게 할지는 적지 않는다 |

> **🧭 읽기 전에 (2분)** — 아래 질문에 추측으로 답을 적고 정독하며 고쳐 쓰세요.
> 1. 컨테이너가 재현성 문제를 풀었는데, 왜 또 다른 도구(오케스트레이터)가 필요해졌을까?
> 2. 서버가 죽었을 때 `docker run`을 서버마다 실행한 방식과 Deployment YAML 방식은 각각 무슨 일이 생길까?
> 3. "Pod 삭제됨" 이벤트를 컨트롤러가 놓치면 어떻게 될까?
> 4. 컨트롤 플레인이 잠시 죽으면 이미 실행 중인 Pod는 멈출까, 계속 돌까?
>
> **처리법:** 🛠 실습 `kubectl create deployment demo ... --replicas=3` → `kubectl delete pod -l app=demo` → `kubectl get pods -w` 로 자동 복구 관찰 · 🗺 관계도 선언(spec) ↔ 관찰(status) ↔ 조정 루프 / 컨트롤 플레인(결정) ↔ 워커 노드(실행) ↔ API 서버(유일한 통로) · 📦 카드로 컴포넌트 이름(apiserver, etcd, scheduler, controller-manager, kubelet, kube-proxy), Pod 생성 11단계

**이 장에서 배우는 것**

- 컨테이너만으로는 왜 부족해지는지, 쿠버네티스가 어떤 문제를 풀려고 나왔는지 설명할 수 있다.
- "선언적 상태"와 "조정 루프(reconciliation loop)"가 쿠버네티스의 핵심 아이디어임을 이해한다.
- 컨트롤 플레인과 워커 노드를 구성하는 컴포넌트의 역할을 한 줄씩 말할 수 있다.
- 쿠버네티스를 쓰지 말아야 하는 상황을 판단할 수 있다.

## 코어 1. 문제의 진화: 드리프트 → 배포 복잡도 → 오케스트레이터

### 1.1 인프라 드리프트: 같아야 할 서버가 달라진다

**한 줄 요약:** 수작업으로 관리한 서버들은 시간이 지나며 달라지고, 그러면 재현도 복구도 불가능해진다.

새 서비스를 서버 한 대에 배포한다고 하자. 운영자가 OS를 설치하고, 런타임을 올리고, 방화벽을 열고, 모니터링 에이전트를 붙인다. 6개월 뒤 서버를 한 대 더 늘릴 때 다른 담당자가 작업하면, OS 버전이나 패치 버전이 다르고 방화벽 규칙 하나가 빠질 수 있다. 두 서버는 "같은 서버"라 불리지만 실제로는 다르다.

이렇게 **동일해야 할 시스템들이 시간이 지나며 조금씩 벌어지는 현상**을 **인프라 드리프트(infrastructure drift)** 라고 한다. 위험한 이유는 두 가지다.

- **재현이 불가능하다.** 개발·스테이징·프로덕션의 상태가 다르면 테스트를 통과한 코드가 프로덕션에서 실패한다.
- **복구가 불가능하다.** 서버가 죽었을 때 "원래대로" 되돌리려면 원래 상태를 알아야 하는데, 수작업 이력은 어디에도 남아 있지 않다.

업계는 이 문제를 단계적으로 풀어 왔다.

| 단계 | 방법 | 한계 |
|---|---|---|
| 1 | 설정 관리 도구(Puppet, Chef, Ansible) | 이미 존재하는 서버를 원하는 상태로 *수렴*시키므로, 기반 OS 차이나 이전 작업의 잔여물은 못 없앤다 |
| 2 | 불변 인프라 — 고치지 말고 새 이미지로 갈아엎기 | VM 이미지는 무겁고 빌드가 느리다 |
| 3 | 컨테이너 — 앱과 의존성만 담은 가벼운 패키지 | 실행 단위의 재현성은 해결했지만, 새로운 문제를 낳았다 |

### 1.2 컨테이너가 낳은 새 문제: 배포 복잡도

**한 줄 요약:** 서비스가 수십 개로 쪼개지면 운영 질문이 "어떻게 올리지"에서 "어디에, 어떻게 옮기고 찾고 바꾸지"로 바뀌고, 그 조합은 사람이 감당할 수 없다.

컨테이너 덕분에 서비스를 잘게 쪼개기 쉬워졌다. 모놀리스 하나를 배포하던 조직이 40개 서비스를 배포하게 되면 운영자가 답해야 할 질문이 바뀐다.

| 모놀리스 시절의 질문 | 마이크로서비스 시대의 질문 |
|---|---|
| 이 서버에 앱을 어떻게 올리지? | 40개 서비스, 200개 인스턴스를 15대 서버에 **어떻게 배치**하지? |
| 서버가 죽으면 어떻게 살리지? | 그 위에 있던 인스턴스를 **어디로 옮기지**? |
| 앱 주소가 뭐지? | 인스턴스가 계속 옮겨 다니는데 서비스 간 **주소를 어떻게 찾지**? |
| 배포 시 서버를 내리면 되나? | 40개 서비스를 각각 **무중단으로** 어떻게 업데이트하지? |
| CPU가 부족하면 서버를 늘리자 | 어떤 서비스가 병목인지 **어떻게 알고** 그것만 늘리지? |

이 질문들은 사람이 손으로 답하기에는 조합의 수가 너무 많다. 필요한 것은 **결정을 대신 내려 주는 시스템**, 즉 **오케스트레이터**다. 쿠버네티스가 그 역할을 한다.

## 코어 2. 선언적 상태 + 조정 루프(레벨 트리거)

### 2.1 명령형 vs 선언적

**한 줄 요약:** 절차가 아니라 "결과로서의 상태"를 적는다.

쿠버네티스의 핵심 아이디어는 한 문장이다.

> **"무엇을 원하는지 적어 두면, 시스템이 알아서 그 상태를 유지한다."**

이것이 **선언적(declarative)** 접근이다. 명령형과 비교해 보자.

**명령형 — 절차를 지시한다**

```bash
ssh server-01 'docker run -d --name web-1 myapp:1.2'
ssh server-02 'docker run -d --name web-2 myapp:1.2'
ssh server-03 'docker run -d --name web-3 myapp:1.2'
# server-02가 죽으면? → 사람이 알아채고, 사람이 다시 실행
```

**선언적 — 목표 상태를 기술한다**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3              # "3개가 떠 있어야 한다"
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: web
        image: myapp:1.2   # "이 이미지여야 한다"
```

이 YAML에는 어느 서버에 띄울지, 어떤 순서로 띄울지, 죽으면 어떻게 할지가 적혀 있지 않다. **결과로서의 상태**만 적혀 있다.

### 2.2 조정 루프: 관찰 → 비교 → 조치

**한 줄 요약:** 모든 컨트롤러는 spec과 status의 차이를 줄이는 루프를 끝없이 돈다. 장애 복구와 롤링 업데이트가 같은 원리다.

이 상태를 실제로 만들어 내는 것이 **조정 루프**다. 쿠버네티스의 모든 컨트롤러는 다음 세 단계를 끝없이 반복한다.

```
     ┌───────────────────────────────────┐
     ▼                                   │
 ① 관찰(observe)  현재 상태는?  "web Pod가 2개 떠 있음"
     ▼                                   │
 ② 비교(diff)     원하는 상태는? "3개" → 차이: "1개 부족"
     ▼                                   │
 ③ 조치(act)      Pod 1개 생성 요청       │
     └───────────────────────────────────┘
```

서버 한 대가 죽으면 그 위의 Pod가 사라지고, 다음 루프에서 "2개뿐"이라는 차이가 관측되어 다른 노드에 하나가 자동 생성된다. **사람의 개입이 필요한 지점이 없다.** 같은 원리가 배포에도 적용된다. 이미지를 `myapp:1.3`으로 바꿔 적용하면 컨트롤러가 "현재 1.2인 Pod 3개, 원하는 것은 1.3인 Pod 3개"라는 차이를 발견하고 정해진 전략(기본은 롤링 업데이트)대로 하나씩 교체한다.

이 모델에서 `spec`은 "원하는 상태"(사람이 씀), `status`는 "현재 관찰된 상태"(시스템이 씀)다. 컨트롤러는 둘의 차이를 줄이는 방향으로 움직인다.

### 2.3 레벨 트리거: 이벤트를 놓쳐도 복구된다

**한 줄 요약:** "무엇이 바뀌었나"가 아니라 "지금 상태가 어떤가"로 판단하고, 멱등하게 동작한다.

조정 루프는 "무엇이 바뀌었나"가 아니라 "지금 상태가 어떤가"로 판단한다.

```
엣지 트리거:  "Pod가 삭제됨"이라는 이벤트에 반응
             → 이벤트를 놓치면 영영 처리하지 못한다
레벨 트리거:  "지금 2개인데 3개여야 한다"는 상태를 본다
             → 이벤트를 놓쳐도 다음 조정에서 바로잡힌다
```

쿠버네티스의 내장 컨트롤러는 모두 레벨 트리거 방식이다. 같은 컨트롤러가 같은 입력으로 여러 번 실행되어도 결과가 달라지지 않아야 한다(멱등성). 이것이 분산 시스템에서 견고성의 원천이다.

직접 확인해 볼 수 있다.

```bash
kubectl create deployment demo --image=nginx:alpine --replicas=3
kubectl delete pod -l app=demo --wait=false
kubectl get pods -l app=demo -w
```

아무도 지시하지 않았는데 새 Pod가 생긴다. ReplicaSet 컨트롤러가 차이를 관측하고 조치한 것이다.

## 코어 3. 컨트롤 플레인(결정) / 워커 노드(실행), 모든 통신은 API 서버 경유

### 3.1 아키텍처 한눈에 보기

**한 줄 요약:** 결정하는 쪽(컨트롤 플레인)과 실행하는 쪽(워커 노드)으로 나뉜다.

쿠버네티스 클러스터는 **결정하는 쪽(컨트롤 플레인)** 과 **실행하는 쪽(워커 노드)** 으로 나뉜다.

```
┌──────────────── 컨트롤 플레인 (Control Plane) ────────────────┐
│  kube-apiserver        ← 클러스터의 정문. 모든 요청이 통과      │
│  etcd                  ← 모든 오브젝트 상태를 저장하는 KV 스토어 │
│  kube-scheduler        ← 새 Pod를 어느 노드에 둘지 결정         │
│  kube-controller-manager ← Deployment, ReplicaSet 등의 조정 루프│
└──────────────────────────────────────────────────────────────┘
                              ▲ (kubelet이 API 서버에 접속)
     ┌────────────────────────┼────────────────────────┐
┌────▼───────────┐     ┌──────▼─────────┐     ┌────────▼───────┐
│ 워커 노드 1      │     │ 워커 노드 2     │     │ 워커 노드 3     │
│ kubelet        │     │ kubelet        │     │ kubelet        │
│ kube-proxy     │     │ kube-proxy     │     │ kube-proxy     │
│ 컨테이너 런타임   │     │ 컨테이너 런타임   │     │ 컨테이너 런타임   │
│ [Pod] [Pod]    │     │ [Pod]          │     │ [Pod] [Pod]    │
└────────────────┘     └────────────────┘     └────────────────┘
```

| | 컨트롤 플레인 | 워커 노드 |
|---|---|---|
| 역할 | 무엇을 어디에 둘지 **결정** | 실제로 컨테이너를 **실행** |
| 구성 | apiserver, etcd, scheduler, controller-manager | kubelet, kube-proxy, 컨테이너 런타임 |
| 죽으면 | 새 변경이 반영되지 않는다 | 그 노드의 Pod가 다른 노드로 옮겨간다(정확히는 컨트롤러가 다른 노드에 새 Pod를 만든다) |

### 3.2 컴포넌트 한 줄 요약

**한 줄 요약:** API 서버는 유일한 정문, etcd는 진실의 저장소, 스케줄러는 배치, 컨트롤러 매니저는 조정 루프, kubelet은 노드 에이전트, kube-proxy는 Service 트래픽 규칙.

| 컴포넌트 | 한 줄 설명 |
|---|---|
| **kube-apiserver** | 클러스터의 유일한 진입점. `kubectl`, 컨트롤러, kubelet 모두 이 API를 통해서만 대화한다. 인증·인가·감사를 한 곳에서 처리할 수 있다 |
| **etcd** | 클러스터의 모든 상태를 저장하는 분산 키-값 스토어. "클러스터의 진실"이며 이것을 잃으면 클러스터를 잃는다 |
| **kube-scheduler** | 노드가 정해지지 않은 Pod를 발견하면 리소스 요구량·어피니티·테인트 등을 고려해 노드를 결정한다 |
| **kube-controller-manager** | 수십 개의 내장 컨트롤러를 한 프로세스에서 실행한다. 각 컨트롤러가 조정 루프를 돈다 |
| **cloud-controller-manager** | (클라우드 환경) 로드밸런서 생성 등 클라우드 API 연동을 담당한다 |
| **kubelet** | 노드의 에이전트. "이 노드에서 이 Pod를 실행하라"는 지시를 받아 컨테이너를 띄우고 상태를 보고한다 |
| **컨테이너 런타임** | containerd, CRI-O 등. kubelet이 CRI라는 표준 인터페이스로 호출한다 |
| **kube-proxy** | Service의 가상 IP로 오는 트래픽을 실제 Pod로 전달하는 규칙(iptables나 IPVS)을 노드에서 관리한다 |

### 3.3 통신 규칙 두 가지

**한 줄 요약:** 모든 통신은 API 서버를 경유하고, kubelet은 pull 모델이다. 그래서 컨트롤 플레인이 죽어도 실행 중인 Pod는 계속 서비스한다.

1. **모든 통신은 API 서버를 경유한다.** 스케줄러가 kubelet에게 직접 명령하지 않고, 컨트롤러끼리도 직접 대화하지 않는다. 컴포넌트를 독립적으로 교체할 수 있는 이유다.
2. **kubelet은 pull 모델이다.** API 서버가 "이 Pod를 띄워라"라고 명령하지 않고, kubelet이 API 서버를 watch하다가 자기 노드에 할당된 Pod를 발견해 스스로 가져간다. 그래서 컨트롤 플레인이 잠시 죽어도 **이미 실행 중인 Pod는 계속 서비스한다.** 새 배포나 스케일링만 멈춘다.

### 3.4 요청 하나가 컨테이너가 되기까지

**한 줄 요약:** `kubectl apply` 한 번은 API 서버 → 스케줄러 → kubelet의 세 구간을 거치며, 각 구간은 서로를 기다리지 않는다.

`kubectl apply -f pod.yaml` 한 번이 실제 컨테이너가 되기까지는 다음 11단계를 거친다.

```
 1. kubectl apply        YAML → HTTPS POST 요청
 2. kube-apiserver       인증 → 인가 → 어드미션(기본값 주입·정책 검증)
 3. etcd 저장            이 시점에 spec.nodeName은 아직 비어 있다
 4. kube-scheduler       필터링 → 스코어링 → 노드 선택, spec.nodeName을 채운다
 5. kubelet              자기 노드에 할당된 Pod를 watch로 감지해 스스로 가져간다
 6. cgroup 계층 생성      QoS 클래스에 따라 위치가 정해진다
 7. 볼륨 마운트
 8. 이미지 pull           imagePullPolicy, imagePullSecrets
 9. 샌드박스(pause) 생성   CRI → CNI, 네트워크 네임스페이스 생성·IP 할당
10. init 컨테이너 순차 실행 → 앱 컨테이너 시작
11. 프로브 시작 → Ready=True → Service 엔드포인트에 등록
```

이 흐름은 성격이 다른 세 구간으로 나뉜다.

```
[1~3] 요청이 저장되기까지        — API 서버의 일
[4]   배치가 결정되기까지         — 스케줄러의 일
[5~11] 실제 컨테이너가 되기까지    — kubelet의 일
```

각 구간은 서로를 기다리지 않는다. 스케줄러는 nodeName이 빈 Pod를 찾아 채울 뿐이고, kubelet은 자기 노드 이름이 적힌 Pod를 찾아 실행할 뿐이다. 중앙 오케스트레이터가 전체를 지휘하는 구조가 아니다. 어느 단계에서 막혔는지는 `kubectl describe pod`의 Events 섹션에서 알 수 있다.

### 3.5 매니지드 쿠버네티스

**한 줄 요약:** 클라우드가 대신 운영하는 것은 컨트롤 플레인뿐이다.

클라우드 사업자(GKE, EKS, AKS)가 컨트롤 플레인을 대신 운영해 주는 서비스다. 다만 원문은 "매니지드를 쓰면 쿠버네티스를 몰라도 된다"는 것은 오해라고 지적한다. 컨트롤 플레인 운영 부담만 줄 뿐, 워크로드·네트워크 정책·RBAC·리소스 튜닝은 여전히 내 책임이다.

```
컨트롤 플레인 (apiserver, etcd, scheduler, cm)   ← 클라우드가 운영
워커 노드 (OS 패치, 노드 스케일링, 문제 노드 교체)  ← 여전히 내 책임
워크로드, 네트워크 정책, RBAC, 리소스 튜닝         ← 전적으로 내 책임
```

## 코어 4. 도입 판단: "사람이 손으로 하는 반복 결정"이 많은가

### 4.1 쿠버네티스를 쓰지 말아야 할 때

**한 줄 요약:** 자동화할 반복 결정이 적은데 자동화 기계를 들이지 않는다.

쿠버네티스는 만능이 아니다. 도입을 재고해야 하는 신호는 다음과 같다.

1. **서비스가 하나뿐이고 트래픽이 예측 가능하다.** 웹 서버 2대로 충분하다면 매니지드 PaaS나 단순한 VM + 로드밸런서가 총소유비용 면에서 낫다.
2. **상태를 가진 레거시가 핵심이다.** 파일 락, 로컬 디스크 세션, 고정 IP에 의존하는 앱은 "언제든 죽고 다시 뜬다"는 전제와 충돌한다.
3. **클러스터를 운영할 사람이 없다.** 매니지드여도 네트워크 정책·RBAC·리소스 튜닝·업그레이드는 팀의 몫이다.
4. **지연 시간이 마이크로초 단위로 중요하다.** 고빈도 트레이딩, 실시간 신호 처리 등.
5. **"요즘 다 쓴다니까"가 유일한 이유다.** 도입 이유를 한 문장으로 적을 수 없다면 아직 때가 아니다.

반대로 **도입이 정당화되는 신호**는 서비스가 열 개를 넘고 계속 늘어남, 배포 빈도가 높고 무중단 배포가 필요함, 트래픽 변동이 커서 자동 스케일링 이득이 큼, 여러 팀이 인프라를 공유함, 이식성이 필요함 등이다.

건강한 판단 기준은 이것이다. **"지금 사람이 손으로 하고 있는 반복 결정이 무엇인가?"** 그 목록이 길고 자주 반복된다면 쿠버네티스가 자동화해 줄 수 있고, 짧다면 자동화할 것이 없는데 자동화 기계를 들이는 셈이다.

## 실무 적용

### 체크리스트

- [ ] **인프라 드리프트**는 동일해야 할 시스템이 시간이 지나며 벌어지는 현상이다. 컨테이너는 실행 단위의 재현성을 해결했다.
- [ ] 서비스가 늘면 배치·복구·디스커버리·배포·스케일링이 사람이 감당할 수 없는 조합 문제가 되고, 이를 대신 결정하는 것이 오케스트레이터다.
- [ ] 쿠버네티스의 핵심은 **선언적 상태**(spec에 원하는 결과를 적는다)와 **조정 루프**(관찰-비교-조치를 반복한다)다. 상태를 기준으로 판단하므로 이벤트를 놓쳐도 복구된다.
- [ ] 클러스터는 **컨트롤 플레인**(apiserver, etcd, scheduler, controller-manager)과 **워커 노드**(kubelet, 런타임, kube-proxy)로 나뉘며, 모든 통신은 API 서버를 경유한다.
- [ ] 컨트롤 플레인이 멈춰도 실행 중인 Pod는 계속 동작한다.
- [ ] Pod가 어느 단계에서 막혔는지는 `kubectl describe pod`의 Events로 본다.
- [ ] 매니지드를 써도 워커 노드·워크로드·네트워크 정책·RBAC·리소스 튜닝은 내 책임이다.
- [ ] 자동화할 반복 결정이 많을 때 도입하고, 서비스가 소수이거나 운영 인력이 없다면 다른 선택지를 먼저 본다.

### 시나리오로 확인하기

1. **상황:** 새벽에 워커 노드 한 대가 하드웨어 장애로 죽었다. 예전 C++ 서버 시절처럼 온콜 담당자가 일어나 남은 서버에 ssh로 접속해 프로세스를 다시 띄우려고 했는데, 들어가 보니 이미 인스턴스 수가 원래대로 돌아와 있다.
   **질문:** 누가 무엇을 했고, 담당자가 손으로 프로세스를 더 띄우면 어떤 문제가 생길 수 있나?

   <details markdown="1"><summary>답 확인</summary>

   ReplicaSet 컨트롤러의 조정 루프가 "원하는 상태 3개, 현재 2개"라는 차이를 관측하고 다른 노드에 Pod를 새로 만들었다(관찰→비교→조치). 사람의 개입이 필요한 지점이 없다. 쿠버네티스 밖에서 손으로 띄운 프로세스는 spec에 없으므로 컨트롤러가 관리하지 않고, "같아야 할 것이 달라지는" 드리프트를 다시 만드는 셈이다. 바꾸고 싶은 것이 있으면 spec(예: `replicas`)을 고친다. → 코어 2

   </details>

2. **상황:** 매니지드 클러스터의 컨트롤 플레인이 10분간 응답하지 않는다는 공지가 떴다. 기획팀은 "지금 접속한 유저가 다 끊기느냐"고 묻는다.
   **질문:** 어떻게 답해야 하나? 그 사이 무엇이 안 되나?

   <details markdown="1"><summary>답 확인</summary>

   kubelet은 pull 모델이라 API 서버를 watch하다가 자기 Pod를 가져가 실행할 뿐, 실행을 계속하는 데 컨트롤 플레인의 명령이 필요하지 않다. 그래서 이미 실행 중인 Pod는 계속 서비스한다. 멈추는 것은 새 배포와 스케일링, 즉 "새 변경의 반영"이다. → 코어 3

   </details>

3. **상황:** 운영 자동화 스크립트를 직접 만들면서, "Pod 삭제됨" 이벤트를 받을 때마다 알림과 후속 작업을 하도록 짰다. 스크립트가 재시작되는 동안 들어온 이벤트는 처리되지 않았다.
   **질문:** 쿠버네티스 내장 컨트롤러는 이 문제를 어떤 방식으로 피하나?

   <details markdown="1"><summary>답 확인</summary>

   이벤트에 반응하는 엣지 트리거는 이벤트를 놓치면 영영 처리하지 못한다. 내장 컨트롤러는 모두 레벨 트리거라 "지금 2개인데 3개여야 한다"는 **현재 상태**를 보고 판단하므로, 이벤트를 놓쳐도 다음 조정에서 바로잡힌다. 같은 입력으로 여러 번 실행해도 결과가 같아야 한다(멱등성). epoll의 LT 모드가 "아직 읽을 데이터가 남은 상태"를 계속 알려 주는 것과 같은 발상이다. → 코어 2

   </details>

4. **상황:** 유저 세션 상태를 프로세스 메모리와 로컬 디스크에 들고 있고, 클라이언트가 고정 IP로 접속하는 서버 한 종류만 운영하는 팀에서 "요즘 다 쓰니까 쿠버네티스로 옮기자"는 제안이 나왔다.
   **질문:** 원문의 기준으로 어떤 신호들이 보이며, 무엇부터 따져야 하나?

   <details markdown="1"><summary>답 확인</summary>

   재고 신호가 여럿 겹친다. 서비스가 하나뿐임, 로컬 디스크 세션·고정 IP에 의존하는 상태 보유 앱("언제든 죽고 다시 뜬다"는 전제와 충돌), "요즘 다 쓴다"가 유일한 이유. 판단 기준인 "지금 사람이 손으로 하고 있는 반복 결정이 무엇인가?"의 목록을 먼저 적어 보고, 그 목록이 짧다면 VM + 로드밸런서나 매니지드 PaaS를 먼저 본다. → 코어 4

   </details>

5. **상황:** Pod를 `apply`했는데 몇 분째 컨테이너가 뜨지 않는다.
   **질문:** 어디까지 진행됐는지 무엇으로 알 수 있고, 어느 컴포넌트의 구간인지 어떻게 나누나?

   <details markdown="1"><summary>답 확인</summary>

   `kubectl describe pod`의 Events 섹션을 본다. [1~3] 요청 저장은 API 서버, [4] 노드 결정(spec.nodeName 채우기)은 스케줄러, [5~11] cgroup·볼륨·이미지 pull·샌드박스·init 컨테이너·프로브는 kubelet의 일이다. nodeName이 비어 있다면 스케줄러 구간에서 막힌 것이다. → 코어 3

   </details>

### 2. 인출 질문

1. 인프라 드리프트란 무엇이고, 왜 위험한가?

   <details markdown="1"><summary>답 확인</summary>

   동일해야 할 시스템들이 시간이 지나며 조금씩 벌어지는 현상이다. 환경 간 상태가 달라 테스트를 통과한 코드가 프로덕션에서 실패하는 **재현 불가능** 문제와, 원래 상태를 몰라 서버가 죽었을 때 되돌릴 수 없는 **복구 불가능** 문제를 낳는다. → 코어 1

   </details>

2. (확인 질문 1) 명령형 방식(`docker run`을 서버마다 실행)과 선언적 방식(Deployment YAML)의 가장 큰 차이는 무엇이며, 서버가 죽었을 때 각각 어떻게 되는가?

   <details markdown="1"><summary>답 확인</summary>

   명령형은 절차를 지시하고, 선언형은 결과로서의 목표 상태만 기술한다. 명령형은 서버가 죽으면 사람이 알아채고 다시 실행해야 한다. 선언형은 컨트롤러가 "2개뿐인데 3개여야 한다"는 차이를 관측해 다른 노드에 Pod를 자동으로 만든다. → 코어 2

   </details>

3. (확인 질문 2) 조정 루프의 세 단계는 무엇이고, 왜 "이벤트"가 아니라 "현재 상태"를 기준으로 판단하는 것이 견고한가?

   <details markdown="1"><summary>답 확인</summary>

   관찰(observe) → 비교(diff) → 조치(act)를 끝없이 반복한다. 엣지 트리거는 이벤트를 놓치면 영영 처리하지 못하지만, 레벨 트리거는 지금 상태를 보므로 이벤트를 놓쳐도 다음 조정에서 바로잡힌다. 같은 입력으로 여러 번 실행해도 결과가 같은 멱등성이 분산 시스템 견고성의 원천이다. → 코어 2

   </details>

4. (확인 질문 3) etcd, kube-scheduler, kubelet, kube-proxy는 각각 무엇을 하는가? 컨트롤 플레인이 잠시 죽으면 실행 중인 Pod는 어떻게 되는가?

   <details markdown="1"><summary>답 확인</summary>

   etcd는 클러스터의 모든 상태를 저장하는 분산 KV 스토어, scheduler는 노드가 정해지지 않은 Pod의 노드를 결정, kubelet은 노드 에이전트로 Pod를 실행하고 상태를 보고, kube-proxy는 Service 가상 IP 트래픽을 실제 Pod로 전달하는 규칙을 관리한다. kubelet이 pull 모델이므로 컨트롤 플레인이 죽어도 실행 중인 Pod는 계속 서비스하고, 새 배포·스케일링만 멈춘다. → 코어 3

   </details>

5. 스케줄러가 kubelet에게 직접 "이 Pod를 띄워라"라고 명령하지 않는 이유와 그 이점은?

   <details markdown="1"><summary>답 확인</summary>

   모든 통신은 API 서버를 경유하기 때문이다. 스케줄러는 nodeName이 빈 Pod를 찾아 채울 뿐이고, kubelet은 API 서버를 watch하다가 자기 노드에 할당된 Pod를 가져간다. 덕분에 컴포넌트를 독립적으로 교체할 수 있고, 중앙에서 전체를 지휘하는 구조가 아니게 된다. → 코어 3

   </details>

6. `kubectl apply -f pod.yaml` 이 컨테이너가 되기까지의 흐름을 세 구간으로 나누면? 막힌 단계는 어디서 확인하나?

   <details markdown="1"><summary>답 확인</summary>

   [1~3] 요청 저장(인증·인가·어드미션 후 etcd 저장, nodeName은 빈 상태) — API 서버의 일, [4] 배치 결정 — 스케줄러의 일, [5~11] cgroup·볼륨·이미지 pull·샌드박스·init 컨테이너·프로브까지 — kubelet의 일. 막힌 단계는 `kubectl describe pod`의 Events 섹션에서 본다. → 코어 3

   </details>

7. 매니지드 쿠버네티스(GKE, EKS, AKS)를 쓰면 무엇이 여전히 내 책임인가?

   <details markdown="1"><summary>답 확인</summary>

   클라우드는 컨트롤 플레인만 운영한다. 워커 노드(OS 패치, 노드 스케일링, 문제 노드 교체)는 여전히 내 책임이고, 워크로드·네트워크 정책·RBAC·리소스 튜닝은 전적으로 내 책임이다. "매니지드면 몰라도 된다"는 오해다. → 코어 3

   </details>

8. 쿠버네티스 도입을 재고해야 하는 신호와 건강한 판단 기준은?

   <details markdown="1"><summary>답 확인</summary>

   서비스가 하나뿐이고 트래픽이 예측 가능, 상태를 가진 레거시가 핵심, 운영할 사람이 없음, 마이크로초 지연이 중요, "요즘 다 쓴다"가 유일한 이유일 때다. 판단 기준은 "지금 사람이 손으로 하고 있는 반복 결정이 무엇인가?" — 그 목록이 길고 자주 반복될 때 도입한다. → 코어 4

   </details>

### 3. 기억 고리

- **C++ 유추:** 조정 루프 = epoll의 level-triggered 모드. "변화"가 아니라 "아직 처리할 게 남은 상태"를 보므로 한 번 놓쳐도 다음에 다시 잡힌다. ⚠️ 깨지는 곳: epoll은 한 커널의 fd 준비 상태이고, 쿠버네티스는 etcd에 저장된 클러스터 전체의 목표와 현재의 차이를 컨트롤러가 조치(생성·삭제)로 메운다.
- **C++ 유추:** 컨트롤 플레인/워커 = 마스터 서버/머신별 에이전트. ⚠️ 깨지는 곳: 명령 패킷을 push하지 않는다. 스케줄러는 API 서버에 기록만 하고 kubelet이 가져간다(pull).
- **비유:** 조정 루프 = 목표 온도를 맞추는 온도조절기. "온도가 몇 도 바뀌었다"는 사건이 아니라 "지금 몇 도인가"를 보고 켜고 끈다(레벨 트리거). ⚠️ 비유가 깨지는 지점: 쿠버네티스에는 컨트롤러가 수십 개이고, 서로 직접 대화하지 않고 API 서버(etcd에 저장된 상태)를 통해서만 협업한다.
- **묶음(3의 법칙):** 조정 루프 3단계 = 관찰·비교·조치 / Pod 생성 3구간 = API 서버·스케줄러·kubelet / 해결의 역사 3단계 = 설정 관리·불변 인프라·컨테이너.
- **대칭·순서:** spec(사람이 씀) ↔ status(시스템이 씀), 컨트롤 플레인(결정) ↔ 워커 노드(실행), 엣지 트리거(사건) ↔ 레벨 트리거(상태).
