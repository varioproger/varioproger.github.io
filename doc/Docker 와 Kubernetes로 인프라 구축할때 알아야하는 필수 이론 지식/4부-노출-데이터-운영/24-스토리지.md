# 24장. 스토리지 — Volume, PV, PVC, StorageClass

> **🎮 게임 서버 개발자에게** — 게임 서버를 물리 서버에 띄우던 시절에는 로그·덤프·리플레이 파일을 그 서버의 로컬 디스크에 쓰면 됐다. 쿠버네티스에서는 Pod가 언제든 다른 노드로 옮겨 다시 만들어지므로 **로컬 디스크에 쓴 데이터는 따라오지 않는다.** Pod보다 오래 살아야 하는 데이터는 PVC로 "요청"하고, 실제 디스크는 클러스터가 붙여 준다. 그 디스크는 특정 노드·AZ에 물리적으로 묶여 있다는 점이 메모리 할당과 결정적으로 다르다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 랭킹 DB나 매치 리플레이를 컨테이너 안에 저장했더니 재배포 후 다 사라졌다 → emptyDir/컨테이너 파일 시스템은 영구가 아니다.
> - 정리 작업 중 `kubectl delete pvc` 한 번에 클라우드 디스크까지 삭제됐다 → 회수 정책 `Delete`.
> - 노드 장애 후 DB Pod가 다른 노드에서 `Multi-Attach error`로 뜨지 않거나, 멀티 AZ에서 Pod가 영원히 `Pending`이다.

## 코어 — 이것만은 100%

> **한 문장:** Pod보다 오래 남아야 할 데이터는 개발자가 PVC로 요청하고, 맞는 PV가 없으면 StorageClass의 프로비저너(CSI 드라이버)가 동적으로 만들어 1:1로 바인딩하며, 멀티 AZ에선 WaitForFirstConsumer, 중요한 데이터엔 Retain을 쓴다.

1. **수명으로 볼륨을 고른다** — 스토리지 요구는 임시(emptyDir) / 설정 주입(configMap·secret 등) / 영구(PVC) 세 유형이다. hostPath는 일반 앱에서 쓰지 않는다.
2. **요구(PVC)와 제공(PV·StorageClass)의 분리** — PVC(요청, 네임스페이스) ↔ PV(실제 스토리지, 클러스터) ↔ StorageClass(종류 정의). 바인딩은 1:1 배타적이고, 맞는 PV가 없으면 프로비저너(CSI 드라이버)가 동적으로 만든다.
3. **볼륨은 물리적 위치(노드·AZ)에 묶인다** — 멀티 AZ에선 `WaitForFirstConsumer`, RWO는 "하나의 노드"다. Multi-Attach error·volume node affinity conflict도 여기서 나온다.
4. **데이터를 지키는 것은 정책과 백업이다** — 회수 정책 `Delete`는 PVC 삭제 시 실제 디스크까지 지우므로 프로덕션은 `Retain`. 백업은 앱·볼륨·클러스터 세 계층으로 나누고 복원 테스트로 검증한다.

**이 장에서 배우는 것 (원래 목차)**

- 스토리지 요구의 세 가지 유형과 알맞은 볼륨 타입(emptyDir, hostPath, PVC) → 코어 1
- PV / PVC / StorageClass의 관계와 바인딩 과정 → 코어 2
- 동적 프로비저닝과 `volumeBindingMode` → 코어 2, 코어 3
- 접근 모드(RWO/RWX 등)와 회수 정책(Delete/Retain) → 코어 3, 코어 4
- CSI가 무엇인지(개요) → 코어 2
- 백업의 세 계층과 스토리지 문제 진단의 첫 단계 → 코어 4, 코어 3

## 코어 1. 수명으로 볼륨을 고른다

### 1.1 왜 스토리지가 문제인가

**한 줄 요약:** 컨테이너 파일 시스템과 emptyDir은 휘발성이다. 이 장은 Pod가 사라져도 데이터가 남게 하는 방법을 다룬다.

컨테이너의 파일 시스템 변경은 휘발성이다. 컨테이너가 사라지면 함께 사라진다. 컨테이너 간에 파일을 공유하는 `emptyDir`도 Pod가 삭제되면 없어진다. 이 장은 **Pod가 사라져도 데이터가 남게 하는 방법**을 다룬다.

### 1.2 스토리지 요구의 세 가지 유형

**한 줄 요약:** 임시 스크래치(emptyDir) / 설정·시크릿 주입(configMap 등) / 영구 데이터(PVC) — 수명과 공유 범위로 고른다.

| 유형 | 수명 | 공유 범위 | 볼륨 타입 |
|---|---|---|---|
| **① 임시 스크래치** | Pod와 동일 | 같은 Pod 내 컨테이너 | `emptyDir` |
| **② 설정·시크릿 주입** | Pod와 동일 (내용은 외부에서 관리) | 같은 Pod | `configMap`, `secret`, `downwardAPI`, `projected` |
| **③ 영구 데이터** | Pod보다 오래 | Pod를 넘어 유지 | `persistentVolumeClaim` |

### 1.3 emptyDir

**한 줄 요약:** 컨테이너 재시작에는 살아남고 Pod 삭제에는 사라진다. `medium: Memory`는 메모리 한도를 소비한다.

```yaml
volumes:
  - name: scratch
    emptyDir:
      sizeLimit: 1Gi
  - name: cache
    emptyDir:
      medium: Memory       # tmpfs. 빠르지만 컨테이너 메모리 한도를 소비한다
      sizeLimit: 256Mi
```

`emptyDir`은 **컨테이너 재시작에는 살아남지만 Pod 삭제에는 사라진다.** `medium: Memory`로 쓴 데이터는 메모리 사용량에 포함되어, 초과하면 `OOMKilled`가 될 수 있다.

### 1.4 hostPath — 쓰지 말아야 할 이유

**한 줄 요약:** 노드 이동 시 데이터 없음, 노드 장악 가능한 보안 위험, 노드와 운명 공동체 — 정당한 용도는 시스템 컴포넌트뿐이다.

```yaml
volumes:
  - name: host-data
    hostPath:
      path: /var/lib/mydata
```

노드의 파일 시스템을 직접 마운트한다. **일반 애플리케이션에서는 쓰면 안 된다.**

- Pod가 다른 노드로 옮겨가면 **데이터가 없다.**
- 노드의 파일 시스템 접근은 **심각한 보안 위험**이다(`/`를 마운트하면 노드를 장악할 수 있다).
- 노드가 죽으면 데이터도 죽는다.

정당한 용도는 시스템 컴포넌트(예: DaemonSet 로그 수집기가 `/var/log/pods`를 읽는 경우)뿐이다. 로컬 디스크 성능이 필요하면 hostPath 대신 Local PersistentVolume을 쓴다.

## 코어 2. 요구(PVC)와 제공(PV·StorageClass)의 분리

### 2.1 PV / PVC / StorageClass

**한 줄 요약:** 개발자는 PVC로 요청만 하고, PV(실제 스토리지)와 StorageClass(종류 정의)는 운영자·프로비저너의 몫이다.

쿠버네티스는 스토리지를 **요구하는 쪽**과 **제공하는 쪽**을 분리한다.

```
   개발자                          클러스터 운영자
     │                                  │
     ▼                                  ▼
┌──────────┐                    ┌──────────────┐
│   PVC    │  "10Gi 짜리         │ StorageClass │  "이런 종류의
│          │   빠른 디스크 주세요" │              │   스토리지를 제공한다"
└────┬─────┘                    └──────┬───────┘
     │         ┌──────────┐            │
     └────────►│    PV    │◄───────────┘
       바인딩   │          │  프로비저너가 생성
               └────┬─────┘
              실제 스토리지 (EBS, 디스크, NFS ...)
```

| 리소스 | 스코프 | 누가 만드는가 | 의미 |
|---|---|---|---|
| **PersistentVolume (PV)** | 클러스터 | 운영자 또는 프로비저너 | 실제 스토리지 조각 |
| **PersistentVolumeClaim (PVC)** | 네임스페이스 | 개발자 | 스토리지 요청 |
| **StorageClass (SC)** | 클러스터 | 운영자 | 스토리지 "종류"의 정의 |

개발자는 PV를 직접 다루지 않는다. PVC로 요청하면 시스템이 PV를 붙여 준다.

### 2.2 PVC와 Pod에서의 사용

**한 줄 요약:** PVC에 접근 모드·StorageClass·용량을 적고, Pod는 `claimName`으로 그 PVC를 마운트한다.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: standard        # 생략하면 기본 StorageClass
  resources:
    requests:
      storage: 10Gi
---
# Pod
spec:
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: data
  containers:
    - name: app
      volumeMounts:
        - name: data
          mountPath: /var/lib/data
```

### 2.3 StorageClass

**한 줄 요약:** 프로비저너·파라미터·회수 정책·확장 허용·바인딩 모드를 묶은 "스토리지 종류"이며, 여러 클래스로 티어를 만든다.

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
provisioner: ebs.csi.aws.com
parameters:                         # 프로비저너별로 다름
  type: gp3
reclaimPolicy: Delete               # 또는 Retain
allowVolumeExpansion: true          # 나중에 늘릴 수 있는가
volumeBindingMode: WaitForFirstConsumer
```

여러 클래스를 정의해 티어를 만든다(예: `fast-ssd`는 데이터베이스, `standard`는 일반 앱, `cold-hdd`는 아카이브, `shared-nfs`는 여러 Pod 공유용).

### 2.4 바인딩과 동적 프로비저닝

**한 줄 요약:** 매칭 PV가 있으면 정적 바인딩, 없으면 프로비저너가 만들어 동적 바인딩한다. 바인딩은 1:1 배타적이다.

```
① PVC 생성
     │
② PV 컨트롤러가 매칭되는 PV를 찾는다
     │  (용량 ≥ 요청, accessMode 호환, storageClass 일치)
     ├─ 있음 → 바인딩 (정적 프로비저닝)
     └─ 없음 → StorageClass의 프로비저너 호출
                    │
              ③ 실제 스토리지 생성 (EBS 볼륨 등)
              ④ PV 오브젝트 생성 후 바인딩 (동적 프로비저닝)
```

**바인딩은 1:1이며 배타적이다.** 10Gi를 요청했는데 100Gi PV가 매칭되면 100Gi 전체를 차지한다.

| PVC STATUS | 의미 |
|---|---|
| `Pending` | 매칭되는 PV가 없거나 프로비저닝 대기 중 |
| `Bound` | PV와 연결됨 |
| `Lost` | 바인딩된 PV가 사라짐 |

### 2.5 CSI — 스토리지 드라이버 표준 (개요)

**한 줄 요약:** 드라이버를 쿠버네티스 본체 밖으로 분리해 gRPC로 통신하게 한 표준. 컨트롤러 플러그인(Deployment)과 노드 플러그인(DaemonSet)으로 배포된다.

과거에는 모든 스토리지 드라이버 코드가 쿠버네티스 본체 안(in-tree)에 있었다. 벤더가 버그를 고치려면 쿠버네티스 릴리스를 기다려야 했고, 드라이버 버그가 핵심 컴포넌트를 죽일 수 있었다. **CSI**(Container Storage Interface)는 스토리지 드라이버를 **클러스터 밖의 별도 컴포넌트**로 분리하고 gRPC 인터페이스로 통신하게 한 표준이다. in-tree 플러그인은 모두 CSI로 마이그레이션됐다.

CSI 드라이버는 두 부분으로 배포된다.

- **컨트롤러 플러그인**(Deployment): PVC를 보고 클라우드 API로 볼륨 생성/삭제/연결 (사이드카 `external-provisioner`, `external-attacher` 등과 함께)
- **노드 플러그인**(DaemonSet, 모든 노드): 실제로 노드에 마운트

PVC 생성부터 컨테이너에서 보이기까지의 큰 흐름은 다음과 같다.

```
PVC 생성 → (provisioner) 실제 볼륨 생성 → PV 생성·바인딩
→ Pod가 노드에 스케줄됨 → 볼륨을 노드에 연결 → 노드에 마운트
→ Pod의 볼륨 디렉터리에 바인드 마운트 → 컨테이너 시작
```

(StorageClass의 `provisioner: ebs.csi.aws.com` 같은 값이 어느 CSI 드라이버를 쓸지 가리킨다.)

## 코어 3. 볼륨은 물리적 위치(노드·AZ)에 묶인다

### 3.1 volumeBindingMode

**한 줄 요약:** `Immediate`는 Pod 위치를 모른 채 볼륨을 만들어 AZ 불일치를 낳고, `WaitForFirstConsumer`는 노드가 정해진 뒤 그에 맞춰 만든다.

- **`Immediate`**: PVC 생성 즉시 PV를 만든다. 멀티 AZ에서 볼륨이 AZ-a에 생겼는데 스케줄러가 Pod를 AZ-c 노드에 배치하려 하면 **Pod가 영원히 스케줄되지 않는다.**
- **`WaitForFirstConsumer`(권장)**: Pod가 스케줄될 때까지 기다렸다가 **결정된 노드에 맞춰** 볼륨을 만든다. 대부분의 클라우드 StorageClass는 이것이 기본값이다.

### 3.2 접근 모드

**한 줄 요약:** RWO는 "하나의 노드", RWOP가 "하나의 Pod"다. 블록 스토리지는 대부분 RWX를 지원하지 않는다.

| 모드 | 약칭 | 의미 |
|---|---|---|
| `ReadWriteOnce` | RWO | **하나의 노드**에서 읽기/쓰기 |
| `ReadOnlyMany` | ROX | 여러 노드에서 읽기 전용 |
| `ReadWriteMany` | RWX | **여러 노드**에서 읽기/쓰기 |
| `ReadWriteOncePod` | RWOP | **하나의 Pod**에서만 |

RWO는 "하나의 Pod"가 아니라 **하나의 노드**다. 같은 노드의 여러 Pod는 RWO 볼륨을 동시에 마운트할 수 있다. 정말 단일 Pod만 접근시키려면 RWOP를 쓴다.

| 스토리지 | RWO | RWX |
|---|---|---|
| AWS EBS, GCP PD, Azure Disk | O | X |
| AWS EFS, Azure Files, NFS | O | O |
| 로컬 디스크 | O | X |

블록 스토리지는 대부분 RWX를 지원하지 않는다. "여러 Pod가 같은 파일에 접근해야 한다"는 요구는 대개 아키텍처 문제의 신호이므로, 업로드 파일은 오브젝트 스토리지(S3), 캐시는 Redis 등의 대안을 먼저 검토하라는 것이 원문의 조언이다.

### 3.3 스토리지 문제 진단 (기본)

**한 줄 요약:** `kubectl describe pvc`의 Events가 핵심이다. Pending(코어 2)과 AZ·노드 연결 문제(코어 3)를 증상표로 가른다.

```bash
kubectl get pvc
kubectl describe pvc <name>          # Events가 핵심
kubectl get pv
kubectl get storageclass
kubectl get volumeattachment         # 볼륨이 어느 노드에 연결됐는가
```

| 증상 | 원인 | 대응 |
|---|---|---|
| PVC가 `Pending` + `WaitForFirstConsumer` | 정상. Pod를 만들면 바인딩된다 | - |
| PVC가 `Pending` + 이벤트 없음 | StorageClass 없음, 기본 클래스 미지정 | `kubectl get sc` |
| PVC가 `Pending` + `ProvisioningFailed` | CSI 드라이버 오류, 권한 부족, 쿼터 초과 | CSI 컨트롤러 로그 |
| Pod가 `Pending` + `volume node affinity conflict` | 볼륨 AZ와 노드 AZ 불일치 | `WaitForFirstConsumer` 사용 |
| `Multi-Attach error` | RWO 볼륨을 여러 노드에서 마운트 시도 | 이전 Pod가 완전히 종료되길 대기 |
| PVC 삭제가 `Terminating`에서 멈춤 | 파이널라이저 `pvc-protection` — 사용 중인 Pod 존재 | Pod를 먼저 삭제 |

`Multi-Attach error`는 노드가 갑자기 죽어 볼륨 연결이 해제되지 않은 채 남았을 때 흔히 생긴다. 대개 몇 분 뒤 자동으로 풀린다.

## 코어 4. 데이터를 지키는 것은 정책과 백업이다

### 4.1 회수 정책 (reclaimPolicy)

**한 줄 요약:** `Delete`는 PVC 삭제 시 실제 스토리지까지 지운다. 프로덕션 데이터는 `Retain`으로 바꾼다.

PVC가 삭제됐을 때 PV와 실제 데이터를 어떻게 할지 정한다.

| 정책 | 동작 |
|---|---|
| `Delete` | PV와 **실제 스토리지를 삭제**한다. 데이터가 사라진다 |
| `Retain` | PV를 `Released` 상태로 두고 **데이터를 보존**한다. 수동 정리 필요 |

대부분의 동적 프로비저닝 StorageClass는 `Delete`가 기본이므로 `kubectl delete pvc data` 한 번에 실제 디스크까지 삭제될 수 있다. 프로덕션 데이터에는 `Retain`을 쓰자. 이미 만들어진 PV는 다음처럼 바꿀 수 있다.

```bash
kubectl patch pv <pv-name> -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'
```

### 4.2 볼륨 확장

**한 줄 요약:** `allowVolumeExpansion: true`면 늘릴 수 있지만, 줄일 수는 없다.

StorageClass에 `allowVolumeExpansion: true`가 있으면 PVC의 `requests.storage`를 늘려 확장할 수 있다. **확장은 늘리는 것만 가능하고 줄일 수 없다.**

### 4.3 백업은 계층을 나눠 생각한다 (개요)

**한 줄 요약:** 앱(논리) · 볼륨(스냅샷) · 클러스터(Velero) 세 계층으로 나누고, 복원 테스트로 RTO·RPO를 검증한다. DB 직접 운영 여부도 이 관점에서 판단한다.

PV가 남아 있다고 백업이 된 것은 아니다. 원문은 백업을 세 계층으로 나눈다.

| 계층 | 방법 | 특징 |
|---|---|---|
| ① 애플리케이션 수준(논리적 백업) | `pg_dump`, `mysqldump` 등 | 일관성 보장, 다른 버전·환경으로 복원 가능. 대용량에서 느림 |
| ② 볼륨 수준(물리적 스냅샷) | VolumeSnapshot, 클라우드 스냅샷 | 빠름. 일관성은 앱 협조가 필요하고 같은 스토리지 시스템에 종속 |
| ③ 클러스터 수준(오브젝트 + 볼륨) | Velero | 네임스페이스 전체를 복원 가능. 클러스터 마이그레이션·재해 복구(DR)에 필수 |

**테스트하지 않은 백업은 백업이 아니다.** 정기적으로 별도 네임스페이스에 복원해 보고, 데이터 무결성과 복구에 걸리는 시간(RTO)·잃어도 되는 데이터 범위(RPO)를 측정하고, 절차를 문서화해 두어야 한다.

데이터베이스를 쿠버네티스 안에서 직접 운영할지도 이 관점에서 판단한다. 매니지드 DB(RDS, Cloud SQL)는 자동 백업과 시점 복구(PITR), 자동 페일오버, 읽기 복제본, 버전 업그레이드를 대신해 준다. 쿠버네티스에서 직접 운영하면 이것들을 오퍼레이터나 사람이 구현해야 하므로, 멀티 클라우드·온프레미스 이식성이 필수이거나 성숙한 오퍼레이터와 운영 역량이 있을 때 정당화된다는 것이 원문의 정리다.

## 실무 적용

### 체크리스트

- [ ] 스토리지 요구는 **임시(emptyDir) / 설정 주입 / 영구(PVC)** 세 유형이다. emptyDir은 Pod 삭제 시 사라지고, hostPath는 일반 앱에서 쓰지 않는다.
- [ ] **PVC**(개발자의 요청) ↔ **PV**(실제 스토리지) ↔ **StorageClass**(종류 정의). 맞는 PV가 없으면 StorageClass의 프로비저너가 **동적으로** 만든다.
- [ ] 멀티 AZ에서는 `WaitForFirstConsumer`가 사실상 필수다.
- [ ] RWO는 "하나의 노드"이며, 여러 노드 공유(RWX)는 파일 스토리지(NFS 계열)가 필요하다. 그 전에 오브젝트 스토리지·Redis 같은 대안을 검토한다.
- [ ] 회수 정책 `Delete`는 PVC 삭제 시 데이터까지 지운다. 중요한 데이터에는 `Retain`을 쓴다.
- [ ] 볼륨은 늘릴 수만 있고 줄일 수 없다(`allowVolumeExpansion: true` 필요).
- [ ] CSI는 스토리지 드라이버를 클러스터 밖 컴포넌트로 분리한 표준이다.
- [ ] 백업은 애플리케이션·볼륨·클러스터 세 계층으로 나눠 생각하고, 복원 테스트로 검증한다.
- [ ] PVC가 Pending이면 `kubectl describe pvc`의 Events부터 본다. `WaitForFirstConsumer`라면 정상일 수 있다.

### 시나리오로 확인하기

1. **상황:** 매치 리플레이 파일을 C++ 서버 시절처럼 "서버 로컬 디렉터리"에 쓰려고 hostPath로 `/var/lib/replays`를 마운트했다. 롤링 업데이트 후 일부 리플레이가 보이지 않는다.
   **질문:** 왜 그렇고, 무엇을 써야 하나?

   <details markdown="1"><summary>답 확인</summary>

   새 Pod가 다른 노드에 스케줄되면 그 노드의 hostPath에는 이전 데이터가 없다. hostPath는 보안 위험이고 노드가 죽으면 데이터도 사라진다. Pod보다 오래 남아야 하는 데이터는 PVC로 요청해야 하며, 여러 Pod가 같은 파일을 공유해야 한다면 S3 같은 오브젝트 스토리지를 먼저 검토한다. → 코어 1, 코어 3

   </details>

2. **상황:** 테스트 네임스페이스를 정리하다 `kubectl delete pvc`를 실행했는데, 운영 랭킹 DB가 쓰던 클라우드 디스크까지 사라졌다.
   **질문:** 원인과 예방책은?

   <details markdown="1"><summary>답 확인</summary>

   동적 프로비저닝 StorageClass의 기본 회수 정책이 `Delete`라서 PVC 삭제가 PV와 실제 스토리지 삭제로 이어졌다. 프로덕션 데이터에는 `Retain`을 쓰고, 이미 만든 PV는 `kubectl patch pv`로 바꾼다. 백업 3계층과 복원 테스트도 갖춰 둔다. → 코어 4

   </details>

3. **상황:** 멀티 AZ 클러스터에서 DB Pod가 `Pending`이고 Events에 `volume node affinity conflict`가 보인다.
   **질문:** 원인과 해결은?

   <details markdown="1"><summary>답 확인</summary>

   볼륨이 Pod 위치를 모른 채(`Immediate`) 한 AZ에 먼저 만들어졌고, Pod가 들어갈 노드는 다른 AZ에 있다. StorageClass를 `volumeBindingMode: WaitForFirstConsumer`로 해서 노드가 정해진 뒤 그 AZ에 볼륨을 만들게 한다. → 코어 3

   </details>

4. **상황:** 노드 하나가 갑자기 죽은 뒤 DB Pod가 다른 노드로 옮겨졌는데 `Multi-Attach error`로 시작하지 못한다.
   **질문:** 무슨 일이며 어떻게 대응하나?

   <details markdown="1"><summary>답 확인</summary>

   RWO 볼륨은 하나의 노드에만 연결되는데, 죽은 노드의 볼륨 연결이 해제되지 않은 채 남아 새 노드에서 마운트할 수 없다. `kubectl get volumeattachment`로 연결 상태를 확인하고, 이전 Pod가 완전히 종료되길 기다린다. 대개 몇 분 뒤 자동으로 풀린다. → 코어 3

   </details>

### 2. 인출 질문

1. Pod를 삭제해도 데이터가 남아야 한다면 emptyDir과 PVC 중 무엇을 써야 하는가? (원래 확인 질문 1)

   <details markdown="1"><summary>답 확인</summary>

   PVC를 쓴다. emptyDir은 컨테이너 재시작에는 살아남지만 Pod가 삭제되면 사라지는 임시 스크래치다. Pod보다 오래 유지되어야 하는 영구 데이터는 `persistentVolumeClaim`이다. → 코어 1

   </details>

2. PVC를 삭제했더니 클라우드 디스크까지 사라졌다. 어떤 설정 때문이며 어떻게 예방하는가? (원래 확인 질문 2)

   <details markdown="1"><summary>답 확인</summary>

   회수 정책(reclaimPolicy)이 `Delete`였기 때문이다. 대부분의 동적 프로비저닝 StorageClass는 `Delete`가 기본이라 PV와 실제 스토리지를 함께 지운다. 프로덕션 데이터에는 `Retain`을 쓰고, 이미 만든 PV는 `kubectl patch pv`로 `persistentVolumeReclaimPolicy`를 `Retain`으로 바꾼다. → 코어 4 (4.1)

   </details>

3. 멀티 AZ 클러스터에서 `WaitForFirstConsumer`가 권장되는 이유는 무엇인가? (원래 확인 질문 3)

   <details markdown="1"><summary>답 확인</summary>

   `Immediate`는 PVC 생성 즉시 볼륨을 만들어, 볼륨이 AZ-a에 생겼는데 스케줄러가 Pod를 AZ-c 노드에 두려 하면 Pod가 영원히 스케줄되지 않는다. `WaitForFirstConsumer`는 Pod가 스케줄된 뒤 결정된 노드에 맞춰 볼륨을 만든다. → 코어 3 (3.1)

   </details>

4. hostPath를 일반 애플리케이션에서 쓰면 안 되는 이유와 정당한 용도는?

   <details markdown="1"><summary>답 확인</summary>

   Pod가 다른 노드로 옮기면 데이터가 없고, 노드 파일 시스템 접근은 심각한 보안 위험이며(`/` 마운트 시 노드 장악), 노드가 죽으면 데이터도 죽는다. 정당한 용도는 DaemonSet 로그 수집기가 `/var/log/pods`를 읽는 것 같은 시스템 컴포넌트뿐이고, 로컬 디스크 성능이 필요하면 Local PersistentVolume을 쓴다. → 코어 1 (1.4)

   </details>

5. PVC를 만들었을 때 PV가 붙는 과정(정적/동적 프로비저닝)을 설명하라. 10Gi 요청에 100Gi PV가 매칭되면?

   <details markdown="1"><summary>답 확인</summary>

   PV 컨트롤러가 용량·accessMode·storageClass가 맞는 PV를 찾아 있으면 바인딩(정적), 없으면 StorageClass의 프로비저너를 호출해 실제 스토리지와 PV를 만든 뒤 바인딩(동적)한다. 바인딩은 1:1 배타적이라 100Gi 전체를 차지한다. → 코어 2 (2.4)

   </details>

6. RWO와 RWOP의 차이는? 여러 Pod가 같은 파일을 써야 한다는 요구에 원문은 무엇을 권하나?

   <details markdown="1"><summary>답 확인</summary>

   RWO는 하나의 노드에서 읽기/쓰기라 같은 노드의 여러 Pod가 동시에 마운트할 수 있고, RWOP는 하나의 Pod만 허용한다. EBS 같은 블록 스토리지는 대부분 RWX를 지원하지 않으며, 그런 요구는 아키텍처 문제의 신호이므로 업로드 파일은 S3 같은 오브젝트 스토리지, 캐시는 Redis 등을 먼저 검토하라고 한다. → 코어 3 (3.2)

   </details>

7. CSI는 왜 등장했고 어떤 두 부분으로 배포되나?

   <details markdown="1"><summary>답 확인</summary>

   드라이버 코드가 쿠버네티스 본체(in-tree)에 있어 벤더가 릴리스를 기다려야 했고 드라이버 버그가 핵심 컴포넌트를 죽일 수 있었다. CSI는 드라이버를 클러스터 밖 별도 컴포넌트로 분리해 gRPC로 통신한다. 컨트롤러 플러그인(Deployment, 볼륨 생성·삭제·연결)과 노드 플러그인(DaemonSet, 실제 마운트)으로 배포된다. → 코어 2 (2.5)

   </details>

8. 백업의 세 계층은 무엇이며, "백업이 된다"고 말하려면 무엇이 더 필요한가?

   <details markdown="1"><summary>답 확인</summary>

   애플리케이션 수준(`pg_dump` 등 논리적 백업), 볼륨 수준(VolumeSnapshot·클라우드 스냅샷), 클러스터 수준(Velero)이다. 테스트하지 않은 백업은 백업이 아니므로 정기적으로 별도 네임스페이스에 복원해 무결성과 RTO·RPO를 측정하고 절차를 문서화해야 한다. → 코어 4 (4.3)

   </details>

9. PVC가 Pending일 때와 `Multi-Attach error`가 날 때 각각 무엇을 보나?

   <details markdown="1"><summary>답 확인</summary>

   PVC Pending이면 `kubectl describe pvc`의 Events부터 본다. `WaitForFirstConsumer`면 Pod를 만들 때까지 정상이고, 이벤트가 없으면 StorageClass·기본 클래스 부재, `ProvisioningFailed`면 CSI 드라이버·권한·쿼터 문제다. `Multi-Attach error`는 RWO 볼륨을 여러 노드에서 마운트하려는 것으로, 흔히 노드가 갑자기 죽어 연결이 남은 경우이며 이전 Pod가 완전히 종료되길 기다린다. → 코어 3 (3.3)

   </details>

### 3. 기억 고리

- **C++ 유추:** 회수 정책 = 스마트 포인터의 소유권. `Delete` ≈ `unique_ptr` 소멸 시 자원 해제, `Retain` ≈ `release()`로 소유만 놓고 자원은 남김. ⚠️ 깨지는 곳: 기본값이 대개 `Delete`라 "핸들(PVC)만 지웠는데 실제 디스크까지 해제"되고, `Retain`으로 남은 PV는 사람이 직접 정리해야 한다(누수처럼 비용이 쌓인다).
- **비유:** PVC = 주문서("10Gi 빠른 디스크"), StorageClass = 상품 카탈로그와 그 공장(프로비저너), PV = 실제로 배송된 물건. 재고(PV)가 없으면 공장이 즉석에서 만든다. ⚠️ 비유가 깨지는 지점: 주문보다 큰 물건(100Gi)이 오면 그 전체를 내가 독점하고(1:1 배타), 주문서를 버리면(`Delete` 정책) 받은 물건까지 함께 폐기될 수 있다.
- **묶음(3의 법칙):** 스토리지 3유형(임시 / 설정 / 영구), 3리소스(PVC / PV / StorageClass), 백업 3계층(앱 / 볼륨 / 클러스터), hostPath 금지 3이유(노드 이동 / 보안 / 노드 사망).
- **대칭·순서:** Immediate vs WaitForFirstConsumer, Delete vs Retain, RWO(노드) vs RWOP(Pod), 정적 vs 동적 프로비저닝. 마운트 순서: PVC → 볼륨 생성 → PV 바인딩 → Pod 스케줄 → 노드 연결 → 노드 마운트 → 바인드 마운트 → 컨테이너 시작.
