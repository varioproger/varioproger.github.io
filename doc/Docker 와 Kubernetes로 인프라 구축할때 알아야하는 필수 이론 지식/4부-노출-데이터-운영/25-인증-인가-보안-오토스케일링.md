# 25장. 인증·인가(RBAC)·보안·오토스케일링 기초

> **🎮 게임 서버 개발자에게** — 게임 서버에서 "로그인 토큰 검증 → GM 권한 레벨 확인 → 명령 실행"을 구현해 봤다면, 쿠버네티스 API 서버도 같은 순서로 요청을 거른다(인증 → 인가 → 어드미션). 차이는 쿠버네티스에 **사용자 DB가 없다**는 점, 그리고 보안의 대상이 API 호출만이 아니라 **실행 중인 컨테이너가 침해됐을 때 어디까지 번지는가**라는 점이다. 동접이 늘면 채널 서버를 손으로 증설하던 일은 HPA가 하되, 기준은 노드 CPU가 아니라 Pod의 `requests`다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 신입 개발자에게 dev 네임스페이스 배포 권한만 주고 싶은데 `cluster-admin`을 줄 뻔했다 → RoleBinding + ClusterRole `edit`.
> - 보안 강화로 default-deny NetworkPolicy를 걸었더니 모든 서버가 서로를 못 찾는다 → DNS(53번) 허용 누락.
> - 이벤트 시작과 함께 트래픽이 몰렸는데 HPA가 늘지 않거나, 늘었는데 Pod가 `Pending`이다 → requests 기준·노드 오토스케일러.

## 코어 — 이것만은 100%

> **한 문장:** API 요청은 인증(401) → 인가(RBAC, 403) → 어드미션을 거쳐 통과하고, 실행된 워크로드는 securityContext·PSA·NetworkPolicy·SA 토큰 끄기로 침해 시 폭발 반경을 층마다 줄이며, 부하는 requests 기준의 HPA·VPA·노드 오토스케일러 세 축으로 맞춘다.

1. **API 요청은 세 관문을 지난다** — 인증(실패 401) → 인가(실패 403) → 어드미션 → etcd. 사용자 오브젝트는 없고 ServiceAccount만 API 오브젝트다.
2. **RBAC = 무엇을(Role) + 누구에게(Binding)** — RoleBinding이 ClusterRole을 참조하면 그 네임스페이스에만 적용된다. 최소 권한·그룹 기반·네임스페이스 스코프 우선.
3. **블래스트 레이디어스를 층마다 줄인다** — securityContext(컨테이너 안) / PSA(노드 탈출) / NetworkPolicy(Pod 간 통신) / SA 토큰 끄기·RBAC(API 호출). PSA는 단계적으로, NetworkPolicy는 기본 거부 + DNS 허용.
4. **오토스케일링은 세 축, 기준은 requests** — HPA(Pod 수) / VPA(Pod 크기) / 노드 오토스케일러(노드 수). HPA Utilization은 노드 용량이 아니라 `requests` 대비다.

**이 장에서 배우는 것 (원래 목차)**

- API 서버가 요청을 처리하는 3개의 관문(인증 → 인가 → 어드미션) → 코어 1
- RBAC의 네 가지 리소스(Role, ClusterRole, RoleBinding, ClusterRoleBinding) → 코어 2
- 워크로드 보안의 기본 사고방식(블래스트 레이디어스)과 `securityContext`, Pod Security Admission, NetworkPolicy의 역할 → 코어 3
- 오토스케일링의 세 축(HPA, VPA, 노드 오토스케일러)과 HPA의 계산 방식 → 코어 4

|---|---|---|---|
| 로그인 시 계정 DB 조회 + 세션 토큰 검증 | 인증(Authentication) | 요청자가 누구인지 먼저 확인하고, 실패하면 이후 처리를 하지 않는다 | 쿠버네티스에는 계정 DB가 없다. 인증서·토큰에서 이름과 그룹 문자열만 뽑고, 사용자 관리는 외부(CA, OIDC, IAM)가 한다 |
| GM 권한 레벨 테이블(레벨별 허용 명령) | RBAC | "어떤 명령을 쓸 수 있나"를 테이블로 정한다 | 권한 묶음(Role)과 부여(Binding)가 별개 리소스이고, 네임스페이스 스코프가 있다. 거부 규칙 없이 허용만 쌓인다 |

| 동접이 늘면 채널 서버를 손으로 증설 | HPA | 부하에 따라 인스턴스 수를 바꾼다 | 기준은 노드 CPU가 아니라 Pod `requests` 대비 사용률이고, 비율이 0.9&#126;1.1이면 움직이지 않는다. 노드가 모자라면 노드 오토스케일러가 1~5분 걸려 노드를 붙인다 |

## 코어 1. API 요청은 세 관문을 지난다

### 1.1 요청 처리 파이프라인

**한 줄 요약:** 인증(누구냐, 실패 401) → 인가(할 수 있냐, 실패 403) → 어드미션(수정·검증) → etcd. 401/403만 구분해도 진단이 빨라진다.

API 서버는 클러스터의 유일한 진입점이므로 접근 통제도 한 곳에서 이루어진다.

```
kubectl / Pod / 컨트롤러
        │  HTTPS 요청
        ▼
  ① 인증 (Authentication)  "당신은 누구입니까?"      → 실패 시 401
  ② 인가 (Authorization)   "그 행동을 할 권한이 있습니까?" → 실패 시 403
  ③ 어드미션 제어 (Admission Control)  요청 수정(Mutating) / 정책 검증(Validating)
  ④ etcd에 저장
```

**401과 403의 차이**를 알면 진단이 빨라진다. 401은 신원을 확인하지 못한 것(인증서·토큰·kubeconfig 문제), 403은 신원은 확인됐지만 권한이 없는 것(RBAC 문제)이다.

```bash
kubectl auth whoami                       # 나는 누구인가
kubectl auth can-i create pods            # 내가 이것을 할 수 있는가
kubectl auth can-i delete deployments -n prod
kubectl auth can-i --list -n default      # 내가 할 수 있는 모든 것
```

### 1.2 인증 — 쿠버네티스에는 사용자 오브젝트가 없다

**한 줄 요약:** 쿠버네티스는 사용자를 저장하지 않고 증거에서 이름·그룹 문자열만 뽑는다. ServiceAccount만 실제 API 오브젝트이며, 필요 없으면 토큰 자동 마운트를 끈다.

`kubectl get users`는 동작하지 않는다. 쿠버네티스는 사용자를 저장하지 않고, 요청에 담긴 증거(인증서, 토큰)를 검증해 **문자열로 된 사용자 이름과 그룹 목록**을 추출할 뿐이다. 사용자 생성·삭제는 외부 시스템(인증서 CA, OIDC 제공자, 클라우드 IAM)의 일이다. 예외는 **ServiceAccount**로, 실제 API 오브젝트다.

| | 일반 사용자 | ServiceAccount |
|---|---|---|
| 대상 | 사람, 외부 시스템 | 클러스터 내 워크로드 |
| API 오브젝트 | 없음 | 있음 |
| 관리 | 외부 (CA, OIDC, IAM) | 쿠버네티스 |

모든 Pod는 ServiceAccount를 갖는다(지정하지 않으면 네임스페이스의 `default`). 대부분의 애플리케이션은 쿠버네티스 API를 호출하지 않으므로, 토큰이 자동 마운트되어 Pod가 침해될 때 악용되지 않도록 필요 없으면 끈다.

```yaml
spec:
  serviceAccountName: my-app
  automountServiceAccountToken: false
```

> `system:masters` 그룹은 RBAC 검사를 건너뛰고 모든 것을 할 수 있다. kubeadm이 만드는 `admin.conf`의 인증서가 이 그룹이므로 일상적으로 쓰지 말고 보관해야 한다.

## 코어 2. RBAC = 무엇을(Role) + 누구에게(Binding)

### 2.1 네 가지 리소스와 조합

**한 줄 요약:** Role/ClusterRole은 권한 묶음, RoleBinding/ClusterRoleBinding은 부여. RoleBinding이 ClusterRole을 참조하는 조합이 실무의 핵심이다.

```
        네임스페이스 스코프          클러스터 스코프
권한   │      Role        │      │   ClusterRole    │
연결   │   RoleBinding    │      │ClusterRoleBinding│
```

- **Role / ClusterRole**: "무엇을 할 수 있는가"(권한 묶음)
- **RoleBinding / ClusterRoleBinding**: 그 권한을 "누구에게" 줄 것인가

| Binding | Role 참조 | 적용 범위 |
|---|---|---|
| RoleBinding | Role | 그 네임스페이스 |
| RoleBinding | **ClusterRole** | **그 네임스페이스에만** |
| ClusterRoleBinding | ClusterRole | 클러스터 전체 |

두 번째 조합(RoleBinding이 ClusterRole 참조)이 실무의 핵심이다. ClusterRole 하나를 정의하고 여러 네임스페이스에서 재사용한다.

### 2.2 Role 작성과 주체

**한 줄 요약:** `apiGroups: [""]`는 코어 그룹이고, 주체는 User·Group·ServiceAccount 세 종류다. 그룹 기반 바인딩을 권장한다.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: developer
  namespace: dev
rules:
  - apiGroups: ["", "apps"]
    resources: ["pods", "deployments"]
    verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
  - apiGroups: [""]
    resources: ["pods/log"]
    verbs: ["get"]
```

`apiGroups`의 빈 문자열 `""`은 코어 그룹(Pod, Service, ConfigMap, Secret 등)이다. 주체(Subject)는 User, Group, ServiceAccount 세 종류이며, 사람이 들어오고 나갈 때마다 RBAC을 고치지 않도록 **그룹 기반 바인딩**을 권장한다.

### 2.3 내장 ClusterRole과 설계 원칙

**한 줄 요약:** cluster-admin / admin / edit / view. 최소 권한·그룹 기반·네임스페이스 우선이며, secrets `list`·`pods/exec`·`pods` 생성은 위험 권한이다.

내장 ClusterRole은 다음과 같다.

| 이름 | 권한 |
|---|---|
| `cluster-admin` | 모든 것. ClusterRoleBinding으로 주면 슈퍼유저 |
| `admin` | 네임스페이스 안의 모든 것 + RBAC 관리 |
| `edit` | 네임스페이스 안의 리소스 읽기/쓰기. RBAC 관리는 제외 |
| `view` | 읽기 전용. Secret 제외 |

**RBAC 설계 원칙**: 최소 권한, 그룹 기반, 네임스페이스 스코프 우선(`cluster-admin`은 극소수에게만). 특히 `get`과 `list`는 다르다. secrets에 `list` 권한이 있으면 그 네임스페이스의 모든 시크릿을 덤프할 수 있다. `pods/exec`, `pods` 생성(hostPath·특권 컨테이너로 노드 장악 가능) 같은 권한도 신중하게 다룬다.

## 코어 3. 블래스트 레이디어스를 층마다 줄인다

### 3.1 워크로드 보안 기본 — 블래스트 레이디어스

**한 줄 요약:** "이것이 침해되면 피해가 어디까지 번지나?"를 컨테이너 안 / 노드 탈출 / Pod 간 통신 / API 호출 네 층에서 좁힌다.

RBAC이 "누가 API를 호출할 수 있는가"라면, 워크로드 보안은 "**그 워크로드가 실행된 뒤에 무엇을 할 수 있는가**"다. 유용한 질문은 "이것이 침해되면 피해가 어디까지 번지는가?" 곧 **블래스트 레이디어스**(blast radius, 폭발 반경)이다. 각 층에서 반경을 좁힌다.

| 침해 시 질문 | 막는 것 |
|---|---|
| 컨테이너 안에서 무엇을 할 수 있나? (root? 쓰기 가능한 FS?) | `securityContext` |
| 노드로 탈출할 수 있나? (hostPath, privileged) | Pod Security Admission |
| 다른 Pod와 통신할 수 있나? (기본은 전부 가능) | NetworkPolicy |
| API 서버를 호출할 수 있나? | `automountServiceAccountToken: false`, RBAC |

### 3.2 securityContext — 컨테이너 안에서 할 수 있는 일

**한 줄 요약:** non-root, 권한 상승 차단, 읽기 전용 루트 FS, capability 전부 제거, seccomp. `privileged: true`가 가장 위험하다.

```yaml
containers:
  - name: app
    securityContext:
      runAsNonRoot: true                # root면 컨테이너 시작 거부
      allowPrivilegeEscalation: false   # setuid로 권한 상승 차단
      readOnlyRootFilesystem: true      # 루트 FS 쓰기 금지
      privileged: false
      capabilities:
        drop: ["ALL"]                   # 모든 capability 제거
      seccompProfile:
        type: RuntimeDefault            # 시스템콜 필터링
```

`privileged: true`가 가장 위험하다. 사실상 노드의 root와 같다.

> **[보충]** 원문은 이 필드들이 앞서 다룬 리눅스 기본 요소([5장](../2부-컨테이너와-Docker/05-가상머신-vs-컨테이너-Docker-전체-구조.md)·[6장](../2부-컨테이너와-Docker/06-컨테이너-격리-네임스페이스.md)의 격리 기능 등)를 쓴다고 설명한다. 이 책에서 capability는 [5장](../2부-컨테이너와-Docker/05-가상머신-vs-컨테이너-Docker-전체-구조.md)·[6장](../2부-컨테이너와-Docker/06-컨테이너-격리-네임스페이스.md)와 [15장](../3부-쿠버네티스-핵심/15-Pod.md)에서 다뤘지만, 각 필드의 커널 수준 동작까지 다루지는 않았다.

### 3.3 Pod Security Admission (PSA) — 노드 탈출 막기

**한 줄 요약:** 네임스페이스 라벨 하나로 privileged / baseline / restricted 프로파일을 enforce / warn / audit 모드로 건다. warn·audit부터 단계적으로 올린다.

**네임스페이스 라벨 하나**로 보안 프로파일을 지정한다.

| 프로파일 | 내용 |
|---|---|
| `privileged` | 제한 없음 (시스템 컴포넌트용) |
| `baseline` | 알려진 권한 상승을 차단. 대부분의 앱이 수정 없이 통과 |
| `restricted` | 강력한 하드닝. 모범 사례 강제 |

`baseline`은 `privileged: true`, hostNetwork/hostPID/hostIPC, hostPath 볼륨 등을 금지한다. `restricted`는 여기에 더해 `runAsNonRoot: true`, `allowPrivilegeEscalation: false`, `capabilities.drop: ["ALL"]`, `seccompProfile.type: RuntimeDefault` 등을 요구한다.

라벨은 모드별로 붙인다. `enforce`는 위반 Pod 생성을 거부하고, `warn`은 kubectl 응답에 경고만 표시하며(생성은 됨), `audit`는 감사 로그에만 기록한다.

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: production
  labels:
    pod-security.kubernetes.io/enforce: baseline    # 위반하면 생성 거부
    pod-security.kubernetes.io/warn: restricted     # 경고만 표시
    pod-security.kubernetes.io/audit: restricted    # 감사 로그에만 기록
```

**한 번에 `restricted`를 강제하면 배포가 전부 실패할 수 있다.** 먼저 `warn`/`audit`로 위반 워크로드를 파악해 고친 뒤 `enforce: baseline` → `enforce: restricted` 순으로 단계적으로 올린다.

### 3.4 NetworkPolicy — Pod 간 통신 막기

**한 줄 요약:** 기본은 전부 허용, 정책이 적용된 Pod부터 명시된 것 외 거부. 허용만 누적되고, CNI가 지원해야 동작한다.

쿠버네티스의 기본 네트워크 모델은 **모든 Pod가 모든 Pod와 통신 가능**이고, NetworkPolicy가 이를 제한한다. 핵심 규칙은 다음과 같다.

- 적용되는 정책이 없는 Pod는 전부 허용된다. Ingress 정책이 하나라도 적용된 Pod는 명시된 것 외의 들어오는 트래픽이 전부 거부된다(Egress도 같다).
- 정책은 누적된다(허용 규칙의 합집합). 거부 규칙은 없고 허용 규칙만 있다.
- **CNI가 지원해야 동작한다.** 지원하지 않는 CNI(예: Flannel, kind 기본 CNI인 kindnet)에서는 NetworkPolicy를 만들어도 조용히 무시된다. Calico, Cilium, AWS VPC CNI(v1.14+) 등은 지원한다.

가장 흔한 출발점은 네임스페이스에 **기본 거부** 정책을 깔고 필요한 통신만 여는 것이다.

```yaml
# 모든 Ingress 거부 (ingress 규칙이 없으면 전부 거부)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: production
spec:
  podSelector: {}                    # 네임스페이스의 모든 Pod
  policyTypes: [Ingress]
---
# app=api Pod는 app=frontend Pod에서 오는 8080 포트만 허용
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-allow-frontend
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: api
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: frontend
      ports:
        - protocol: TCP
          port: 8080
```

### 3.5 Egress 기본 거부와 DNS, 그리고 OR/AND 함정

**한 줄 요약:** Egress를 막으면 DNS도 막히므로 kube-dns로 가는 53번을 열고, selector를 별도 항목(-)으로 쓰면 OR, 한 항목에 쓰면 AND다.

> **Egress를 막으면 DNS도 막힌다.** NetworkPolicy 적용 후 모든 것이 깨지는 사고의 대부분이 이것이다. Egress 기본 거부를 쓴다면 `kube-system`의 `k8s-app: kube-dns` Pod로 가는 UDP/TCP 53번 포트를 반드시 허용한다.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns
  namespace: production
spec:
  podSelector: {}
  policyTypes: [Egress]
  egress:
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: kube-system
          podSelector:
            matchLabels:
              k8s-app: kube-dns
      ports:
        - { protocol: UDP, port: 53 }
        - { protocol: TCP, port: 53 }
```

`from`/`to` 목록에서 하이픈(`-`)의 위치도 주의한다. `namespaceSelector`와 `podSelector`를 **각각 별도 항목(`-`)으로 쓰면 OR**(둘 중 하나), 위 DNS 예시처럼 **한 항목 안에 함께 쓰면 AND**(그 네임스페이스의 그 Pod만)다. 실무에서 가장 흔한 실수다.

## 코어 4. 오토스케일링은 세 축, 기준은 requests

### 4.1 오토스케일링의 세 축

**한 줄 요약:** 가로(HPA, Pod 수) / 세로(VPA, Pod 크기) / 노드(Cluster Autoscaler·Karpenter, 노드 수)는 맞물려 움직인다.

오토스케일링에는 세 축이 있다.

| 축 | 질문 | 도구 |
|---|---|---|
| 가로 | "Pod를 몇 개 띄울까?" | HPA (Horizontal Pod Autoscaler) |
| 세로 | "Pod 하나에 얼마를 줄까?" | VPA (Vertical Pod Autoscaler) |
| 노드 | "노드를 몇 개 둘까?" | Cluster Autoscaler / Karpenter |

세 축은 맞물려 있다. HPA가 Pod를 늘리면 노드가 부족해지고, Cluster Autoscaler가 노드를 추가한다.

### 4.2 전제: metrics-server

**한 줄 요약:** HPA·VPA는 metrics-server가 kubelet에서 모은 최근 CPU·메모리 값을 쓴다. Prometheus를 대체하지 않는다.

HPA와 VPA는 메트릭이 있어야 한다. **metrics-server**가 kubelet에서 CPU·메모리 사용량을 수집해 `kubectl top nodes/pods`와 HPA에 제공한다. 최근 값만 보관하므로 모니터링 시스템(Prometheus)을 대체하지 않는다.

### 4.3 HPA — 계산 방식과 requests 기준

**한 줄 요약:** `desired = ceil(current × 현재값/목표값)`, 비율 0.9~1.1이면 그대로. Utilization은 `requests` 대비라 requests가 틀리면 HPA도 틀린다.

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70      # requests 대비 70%
```

```
desiredReplicas = ceil( currentReplicas × ( currentMetric / desiredMetric ) )
예) 현재 4개, 평균 CPU 90%, 목표 70% → ceil(4 × 90/70) = 6
```

비율이 0.9&#126;1.1 사이면 스케일하지 않는다(미세한 변동 방지).

> **Utilization의 기준은 노드 용량이 아니라 `requests`다.** `requests.cpu: 200m`에 목표 70%면 140m를 넘을 때 스케일 아웃한다. requests를 바꾸면 HPA의 동작이 달라지므로, requests가 틀리면 HPA도 틀린다([19장](../3부-쿠버네티스-핵심/19-리소스-요청-제한과-스케줄링-기초.md)).

### 4.4 VPA와 노드 오토스케일링

**한 줄 요약:** VPA는 `Off` 모드로 권고값만 받는 것이 가장 안전하고, Cluster Autoscaler는 Pending Pod를 보고 노드를 늘리는 데 1~5분이 걸린다.

- **VPA**는 Pod의 requests/limits를 조절한다. `Off` 모드는 추천만 계산하고, `Recreate`/`Auto` 모드는 Pod를 삭제하고 재생성해 적용한다. 원문은 `Off` 모드로 권고값만 받아 매니페스트에 반영하는 방식을 가장 안전한 실무 방법으로 권한다.
- **Cluster Autoscaler**는 리소스 부족으로 Pending인 Pod를 발견하면 노드 그룹을 키우고, 사용률이 낮은 노드는 Pod를 옮긴 뒤 제거한다. 노드가 부팅되어 Pod가 스케줄되기까지 보통 1&#126;5분이 걸린다.

## 실무 적용

### 체크리스트

- [ ] API 요청은 **인증(401) → 인가(403) → 어드미션** 순으로 통과한다. 401이면 인증서·토큰·kubeconfig, 403이면 RBAC(`kubectl auth can-i`)를 본다.
- [ ] 쿠버네티스에는 사용자 오브젝트가 없고 ServiceAccount만 API 오브젝트다. API를 호출하지 않는 앱은 `automountServiceAccountToken: false`. `system:masters`(admin.conf)는 일상적으로 쓰지 않는다.
- [ ] RBAC은 Role(권한)과 Binding(연결)의 조합이다. 최소 권한·그룹 기반·네임스페이스 스코프를 우선하고, secrets `list`·`pods/exec`·`pods` 생성 권한은 신중히 준다.
- [ ] 워크로드 보안은 "침해되면 어디까지 번지는가"를 층마다 줄이는 일이다: securityContext, PSA, NetworkPolicy, ServiceAccount 토큰 끄기. `privileged: true`는 쓰지 않는다.
- [ ] PSA는 `warn`/`audit`로 시작해 `enforce`로 단계적으로 올린다(baseline → restricted).
- [ ] NetworkPolicy는 기본 거부 후 필요한 통신만 열되, Egress를 막을 때는 DNS를 반드시 허용한다. CNI가 NetworkPolicy를 지원하는지 먼저 확인하고, selector의 OR(별도 항목)/AND(한 항목)를 구분한다.
- [ ] 오토스케일링은 HPA(Pod 수), VPA(Pod 크기), 노드 오토스케일러(노드 수)의 세 축이다. HPA의 Utilization은 **requests 기준**이며 metrics-server가 전제다.
- [ ] VPA는 `Off` 모드로 권고값만 받아 반영하고, 노드 증설에는 1~5분이 걸린다는 점을 피크 대비에 반영한다.

   </details>

   **질문:** 각각 무엇을 고쳐야 하나?

   <details markdown="1"><summary>답 확인</summary>

   </details>

3. **상황:** 로컬 kind 클러스터에서 "api Pod는 frontend에서만 받는다" NetworkPolicy를 만들었는데, 다른 Pod에서도 여전히 api에 접속된다. C++ 서버의 iptables처럼 "규칙을 넣었으니 막혔다"고 생각했다.

   </details>

4. **상황:** 이벤트 시작으로 서버 CPU가 확실히 올랐는데 HPA(목표 CPU 70%)가 Pod를 늘리지 않는다. 확인해 보니 `requests.cpu`를 넉넉하게 2000m로 잡아 두었고 실제 사용량은 Pod당 800m 정도다.
   **질문:** 왜 늘지 않으며, 늘어난 뒤 Pod가 `Pending`이면 무엇이 일어나나?

   <details markdown="1"><summary>답 확인</summary>

   Utilization은 노드 용량이 아니라 `requests` 대비다. 800m / 2000m = 40%로 목표 70%에 못 미쳐 스케일 아웃하지 않는다. requests가 틀리면 HPA도 틀린다. HPA가 Pod를 늘렸는데 노드가 부족해 `Pending`이면 Cluster Autoscaler가 노드를 추가하며, 부팅·스케줄까지 보통 1~5분이 걸린다. → 코어 4

   </details>

5. **상황:** 운영툴 웹 서버 Pod가 취약점으로 침해됐다. 이 Pod는 쿠버네티스 API를 쓰지 않는데 기본 설정 그대로 배포돼 있었다.
   **질문:** 피해 반경을 줄이려면 어떤 층에서 무엇을 해 뒀어야 하나?

   <details markdown="1"><summary>답 확인</summary>

   API 호출 층: `automountServiceAccountToken: false`로 토큰을 끄고 SA 권한을 최소화한다. 컨테이너 층: `runAsNonRoot`, `allowPrivilegeEscalation: false`, `readOnlyRootFilesystem`, `capabilities.drop: ["ALL"]`. 노드 탈출 층: PSA baseline 이상으로 privileged·hostPath를 금지한다. 통신 층: NetworkPolicy 기본 거부 후 필요한 통신만 연다. → 코어 3

   </details>

   140m이다. Utilization의 기준은 노드 용량이 아니라 `requests`이므로 200m × 70% = 140m다. 단, 비율이 0.9~1.1 사이면 스케일하지 않는 허용 범위가 있어 미세한 초과에는 반응하지 않는다. → 코어 4 (4.3)

   </details>

4. "쿠버네티스에는 사용자 오브젝트가 없다"는 말의 의미와 ServiceAccount의 차이는? SA 토큰은 왜 끄는가?

   <details markdown="1"><summary>답 확인</summary>

   쿠버네티스는 사용자를 저장하지 않고 요청의 인증서·토큰을 검증해 사용자 이름 문자열과 그룹 목록만 추출한다. 사용자 관리는 CA·OIDC·IAM 같은 외부 시스템의 일이다. ServiceAccount는 클러스터 내 워크로드용 실제 API 오브젝트다. 대부분의 앱은 API를 호출하지 않으므로, Pod 침해 시 토큰이 악용되지 않게 `automountServiceAccountToken: false`로 끈다. → 코어 1 (1.2)

   </details>

5. RBAC에서 `get`과 `list`를 구분해야 하는 이유와 조심해야 할 다른 권한은?

   <details markdown="1"><summary>답 확인</summary>

   secrets에 `list` 권한이 있으면 그 네임스페이스의 모든 시크릿을 덤프할 수 있다. 또 `pods/exec`, 그리고 hostPath·특권 컨테이너로 노드를 장악할 수 있는 `pods` 생성 권한도 신중히 다룬다. `system:masters` 그룹은 RBAC 검사를 건너뛰므로 `admin.conf`는 일상적으로 쓰지 않고 보관한다. → 코어 1 (1.2), 코어 2 (2.3)

   </details>

6. 블래스트 레이디어스 관점에서 각 층을 막는 도구를 짝지어 보라. 가장 위험한 securityContext 설정은?

   <details markdown="1"><summary>답 확인</summary>

   컨테이너 안에서 할 수 있는 일은 `securityContext`, 노드 탈출은 Pod Security Admission, 다른 Pod와의 통신은 NetworkPolicy, API 서버 호출은 SA 토큰 끄기와 RBAC이 막는다. 가장 위험한 것은 사실상 노드 root와 같은 `privileged: true`다. → 코어 3 (3.1, 3.2)

   </details>

7. PSA를 적용할 때 왜 단계적으로 올려야 하나? 세 모드의 차이는?

   <details markdown="1"><summary>답 확인</summary>

   한 번에 `restricted`를 강제하면 배포가 전부 실패할 수 있다. `enforce`는 위반 Pod 생성을 거부, `warn`은 kubectl 응답에 경고만(생성됨), `audit`는 감사 로그에만 기록한다. 먼저 warn/audit로 위반을 파악해 고친 뒤 `enforce: baseline` → `enforce: restricted` 순으로 올린다. → 코어 3 (3.3)

   </details>

8. NetworkPolicy의 핵심 규칙과, Egress 기본 거부 시 반드시 해야 할 일은?

   <details markdown="1"><summary>답 확인</summary>

   정책이 없는 Pod는 전부 허용, 정책이 하나라도 적용되면 명시된 것 외 거부다. 정책은 허용 규칙의 합집합으로 누적되고 거부 규칙은 없으며, CNI가 지원해야 동작한다(Flannel·kindnet에선 조용히 무시). Egress를 막으면 DNS도 막히므로 `kube-system`의 `k8s-app: kube-dns` Pod로 가는 UDP/TCP 53을 허용한다. → 코어 3 (3.4, 3.5)

   </details>

9. NetworkPolicy의 `from`/`to`에서 `namespaceSelector`와 `podSelector`를 별도 항목으로 쓸 때와 한 항목에 쓸 때의 차이는?

   <details markdown="1"><summary>답 확인</summary>

   각각 별도 항목(`-`)으로 쓰면 OR(둘 중 하나)이고, 한 항목 안에 함께 쓰면 AND(그 네임스페이스의 그 Pod만)다. 실무에서 가장 흔한 실수다. → 코어 3 (3.5)

   </details>

10. 오토스케일링의 세 축과 서로의 관계, 그리고 VPA의 가장 안전한 사용법은?

    <details markdown="1"><summary>답 확인</summary>

    HPA(Pod 수), VPA(Pod 크기), Cluster Autoscaler/Karpenter(노드 수)다. HPA가 Pod를 늘려 노드가 부족해지면 Pending Pod를 본 Cluster Autoscaler가 노드를 추가한다(보통 1~5분). 모두 metrics-server의 메트릭이 전제다. VPA는 `Off` 모드로 권고값만 받아 매니페스트에 반영하는 것이 가장 안전하다. → 코어 4

    </details>

### 3. 기억 고리

- **C++ 유추:** 인증·인가 = 게임 서버의 "세션 토큰 검증 → GM 권한 레벨 확인". ⚠️ 깨지는 곳: 쿠버네티스에는 계정 DB가 없어 토큰에 적힌 이름·그룹만 믿고, 권한은 Role(무엇)과 Binding(누구)으로 쪼개져 네임스페이스 스코프를 가진다. NetworkPolicy도 iptables처럼 보이지만 기본이 전부 허용이고 CNI가 구현하지 않으면 그냥 무시된다.
- **비유:** 인증·인가 = 건물 출입. 로비에서 신분증을 확인하고(인증, 실패 시 401), 그다음 그 층에 들어갈 권한을 확인한다(인가, 실패 시 403). ⚠️ 비유가 깨지는 지점: 건물은 직원 명부를 갖고 있지만 쿠버네티스는 사용자 명부가 없다. 신분증(인증서·토큰)에 적힌 이름과 그룹만 믿는다. 또 출입 후에도 어드미션이 요청 내용을 고치거나 거부할 수 있다.
- **묶음(3의 법칙):** 관문 3개(인증 / 인가 / 어드미션), PSA 프로파일 3개(privileged / baseline / restricted)와 모드 3개(enforce / warn / audit), 오토스케일링 3축(HPA / VPA / 노드).
- **대칭·순서:** 401 vs 403, Role vs Binding(무엇 vs 누구), 네임스페이스 vs 클러스터 스코프, OR(별도 항목) vs AND(한 항목), 가로(HPA) vs 세로(VPA). PSA 도입 순서: warn/audit → enforce baseline → enforce restricted.
