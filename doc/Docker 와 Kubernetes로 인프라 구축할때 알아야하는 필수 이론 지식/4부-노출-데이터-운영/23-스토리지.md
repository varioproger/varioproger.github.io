# 23장. 스토리지 — Volume, PV, PVC, StorageClass

## 이 장에서 배우는 것

- 스토리지 요구의 세 가지 유형과 알맞은 볼륨 타입(emptyDir, hostPath, PVC)
- PV / PVC / StorageClass의 관계와 바인딩 과정
- 동적 프로비저닝과 `volumeBindingMode`
- 접근 모드(RWO/RWX 등)와 회수 정책(Delete/Retain)
- CSI가 무엇인지(개요)
- 백업의 세 계층과 스토리지 문제 진단의 첫 단계

## 1. 왜 스토리지가 문제인가

컨테이너의 파일 시스템 변경은 휘발성이다. 컨테이너가 사라지면 함께 사라진다. 컨테이너 간에 파일을 공유하는 `emptyDir`도 Pod가 삭제되면 없어진다. 이 장은 **Pod가 사라져도 데이터가 남게 하는 방법**을 다룬다.

## 2. 스토리지 요구의 세 가지 유형

| 유형 | 수명 | 공유 범위 | 볼륨 타입 |
|---|---|---|---|
| **① 임시 스크래치** | Pod와 동일 | 같은 Pod 내 컨테이너 | `emptyDir` |
| **② 설정·시크릿 주입** | Pod와 동일 (내용은 외부에서 관리) | 같은 Pod | `configMap`, `secret`, `downwardAPI`, `projected` |
| **③ 영구 데이터** | Pod보다 오래 | Pod를 넘어 유지 | `persistentVolumeClaim` |

### emptyDir

```yaml
volumes:
  - name: scratch
    emptyDir:
      sizeLimit: 1Gi
  - name: cache
    emptyDir:
      medium: Memory       # tmpfs. 빠르지만 컨테이너 메모리 한도를 소비한다
      sizeLimit: 256Mi
```

`emptyDir`은 **컨테이너 재시작에는 살아남지만 Pod 삭제에는 사라진다.** `medium: Memory`로 쓴 데이터는 메모리 사용량에 포함되어, 초과하면 `OOMKilled`가 될 수 있다.

### hostPath — 쓰지 말아야 할 이유

```yaml
volumes:
  - name: host-data
    hostPath:
      path: /var/lib/mydata
```

노드의 파일 시스템을 직접 마운트한다. **일반 애플리케이션에서는 쓰면 안 된다.**

- Pod가 다른 노드로 옮겨가면 **데이터가 없다.**
- 노드의 파일 시스템 접근은 **심각한 보안 위험**이다(`/`를 마운트하면 노드를 장악할 수 있다).
- 노드가 죽으면 데이터도 죽는다.

정당한 용도는 시스템 컴포넌트(예: DaemonSet 로그 수집기가 `/var/log/pods`를 읽는 경우)뿐이다. 로컬 디스크 성능이 필요하면 hostPath 대신 Local PersistentVolume을 쓴다.

## 3. PV / PVC / StorageClass

쿠버네티스는 스토리지를 **요구하는 쪽**과 **제공하는 쪽**을 분리한다.

```
   개발자                          클러스터 운영자
     │                                  │
     ▼                                  ▼
┌──────────┐                    ┌──────────────┐
│   PVC    │  "10Gi 짜리         │ StorageClass │  "이런 종류의
│          │   빠른 디스크 주세요" │              │   스토리지를 제공한다"
└────┬─────┘                    └──────┬───────┘
     │         ┌──────────┐            │
     └────────►│    PV    │◄───────────┘
       바인딩   │          │  프로비저너가 생성
               └────┬─────┘
              실제 스토리지 (EBS, 디스크, NFS ...)
```

| 리소스 | 스코프 | 누가 만드는가 | 의미 |
|---|---|---|---|
| **PersistentVolume (PV)** | 클러스터 | 운영자 또는 프로비저너 | 실제 스토리지 조각 |
| **PersistentVolumeClaim (PVC)** | 네임스페이스 | 개발자 | 스토리지 요청 |
| **StorageClass (SC)** | 클러스터 | 운영자 | 스토리지 "종류"의 정의 |

개발자는 PV를 직접 다루지 않는다. PVC로 요청하면 시스템이 PV를 붙여 준다.

### PVC와 Pod에서의 사용

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: standard        # 생략하면 기본 StorageClass
  resources:
    requests:
      storage: 10Gi
---
# Pod
spec:
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: data
  containers:
    - name: app
      volumeMounts:
        - name: data
          mountPath: /var/lib/data
```

### StorageClass

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
provisioner: ebs.csi.aws.com
parameters:                         # 프로비저너별로 다름
  type: gp3
reclaimPolicy: Delete               # 또는 Retain
allowVolumeExpansion: true          # 나중에 늘릴 수 있는가
volumeBindingMode: WaitForFirstConsumer
```

여러 클래스를 정의해 티어를 만든다(예: `fast-ssd`는 데이터베이스, `standard`는 일반 앱, `cold-hdd`는 아카이브, `shared-nfs`는 여러 Pod 공유용).

### 바인딩과 동적 프로비저닝

```
① PVC 생성
     │
② PV 컨트롤러가 매칭되는 PV를 찾는다
     │  (용량 ≥ 요청, accessMode 호환, storageClass 일치)
     ├─ 있음 → 바인딩 (정적 프로비저닝)
     └─ 없음 → StorageClass의 프로비저너 호출
                    │
              ③ 실제 스토리지 생성 (EBS 볼륨 등)
              ④ PV 오브젝트 생성 후 바인딩 (동적 프로비저닝)
```

**바인딩은 1:1이며 배타적이다.** 10Gi를 요청했는데 100Gi PV가 매칭되면 100Gi 전체를 차지한다.

| PVC STATUS | 의미 |
|---|---|
| `Pending` | 매칭되는 PV가 없거나 프로비저닝 대기 중 |
| `Bound` | PV와 연결됨 |
| `Lost` | 바인딩된 PV가 사라짐 |

### volumeBindingMode

- **`Immediate`**: PVC 생성 즉시 PV를 만든다. 멀티 AZ에서 볼륨이 AZ-a에 생겼는데 스케줄러가 Pod를 AZ-c 노드에 배치하려 하면 **Pod가 영원히 스케줄되지 않는다.**
- **`WaitForFirstConsumer`(권장)**: Pod가 스케줄될 때까지 기다렸다가 **결정된 노드에 맞춰** 볼륨을 만든다. 대부분의 클라우드 StorageClass는 이것이 기본값이다.

## 4. 접근 모드, 회수 정책

### 접근 모드

| 모드 | 약칭 | 의미 |
|---|---|---|
| `ReadWriteOnce` | RWO | **하나의 노드**에서 읽기/쓰기 |
| `ReadOnlyMany` | ROX | 여러 노드에서 읽기 전용 |
| `ReadWriteMany` | RWX | **여러 노드**에서 읽기/쓰기 |
| `ReadWriteOncePod` | RWOP | **하나의 Pod**에서만 |

RWO는 "하나의 Pod"가 아니라 **하나의 노드**다. 같은 노드의 여러 Pod는 RWO 볼륨을 동시에 마운트할 수 있다. 정말 단일 Pod만 접근시키려면 RWOP를 쓴다.

| 스토리지 | RWO | RWX |
|---|---|---|
| AWS EBS, GCP PD, Azure Disk | O | X |
| AWS EFS, Azure Files, NFS | O | O |
| 로컬 디스크 | O | X |

블록 스토리지는 대부분 RWX를 지원하지 않는다. "여러 Pod가 같은 파일에 접근해야 한다"는 요구는 대개 아키텍처 문제의 신호이므로, 업로드 파일은 오브젝트 스토리지(S3), 캐시는 Redis 등의 대안을 먼저 검토하라는 것이 원문의 조언이다.

### 회수 정책 (reclaimPolicy)

PVC가 삭제됐을 때 PV와 실제 데이터를 어떻게 할지 정한다.

| 정책 | 동작 |
|---|---|
| `Delete` | PV와 **실제 스토리지를 삭제**한다. 데이터가 사라진다 |
| `Retain` | PV를 `Released` 상태로 두고 **데이터를 보존**한다. 수동 정리 필요 |

대부분의 동적 프로비저닝 StorageClass는 `Delete`가 기본이므로 `kubectl delete pvc data` 한 번에 실제 디스크까지 삭제될 수 있다. 프로덕션 데이터에는 `Retain`을 쓰자. 이미 만들어진 PV는 다음처럼 바꿀 수 있다.

```bash
kubectl patch pv <pv-name> -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'
```

### 볼륨 확장

StorageClass에 `allowVolumeExpansion: true`가 있으면 PVC의 `requests.storage`를 늘려 확장할 수 있다. **확장은 늘리는 것만 가능하고 줄일 수 없다.**

## 5. CSI — 스토리지 드라이버 표준 (개요)

과거에는 모든 스토리지 드라이버 코드가 쿠버네티스 본체 안(in-tree)에 있었다. 벤더가 버그를 고치려면 쿠버네티스 릴리스를 기다려야 했고, 드라이버 버그가 핵심 컴포넌트를 죽일 수 있었다. **CSI**(Container Storage Interface)는 스토리지 드라이버를 **클러스터 밖의 별도 컴포넌트**로 분리하고 gRPC 인터페이스로 통신하게 한 표준이다. in-tree 플러그인은 모두 CSI로 마이그레이션됐다.

CSI 드라이버는 두 부분으로 배포된다.

- **컨트롤러 플러그인**(Deployment): PVC를 보고 클라우드 API로 볼륨 생성/삭제/연결 (사이드카 `external-provisioner`, `external-attacher` 등과 함께)
- **노드 플러그인**(DaemonSet, 모든 노드): 실제로 노드에 마운트

PVC 생성부터 컨테이너에서 보이기까지의 큰 흐름은 다음과 같다.

```
PVC 생성 → (provisioner) 실제 볼륨 생성 → PV 생성·바인딩
→ Pod가 노드에 스케줄됨 → 볼륨을 노드에 연결 → 노드에 마운트
→ Pod의 볼륨 디렉터리에 바인드 마운트 → 컨테이너 시작
```

(StorageClass의 `provisioner: ebs.csi.aws.com` 같은 값이 어느 CSI 드라이버를 쓸지 가리킨다.)

## 6. 백업은 계층을 나눠 생각한다 (개요)

PV가 남아 있다고 백업이 된 것은 아니다. 원문은 백업을 세 계층으로 나눈다.

| 계층 | 방법 | 특징 |
|---|---|---|
| ① 애플리케이션 수준(논리적 백업) | `pg_dump`, `mysqldump` 등 | 일관성 보장, 다른 버전·환경으로 복원 가능. 대용량에서 느림 |
| ② 볼륨 수준(물리적 스냅샷) | VolumeSnapshot, 클라우드 스냅샷 | 빠름. 일관성은 앱 협조가 필요하고 같은 스토리지 시스템에 종속 |
| ③ 클러스터 수준(오브젝트 + 볼륨) | Velero | 네임스페이스 전체를 복원 가능. 클러스터 마이그레이션·재해 복구(DR)에 필수 |

**테스트하지 않은 백업은 백업이 아니다.** 정기적으로 별도 네임스페이스에 복원해 보고, 데이터 무결성과 복구에 걸리는 시간(RTO)·잃어도 되는 데이터 범위(RPO)를 측정하고, 절차를 문서화해 두어야 한다.

데이터베이스를 쿠버네티스 안에서 직접 운영할지도 이 관점에서 판단한다. 매니지드 DB(RDS, Cloud SQL)는 자동 백업과 시점 복구(PITR), 자동 페일오버, 읽기 복제본, 버전 업그레이드를 대신해 준다. 쿠버네티스에서 직접 운영하면 이것들을 오퍼레이터나 사람이 구현해야 하므로, 멀티 클라우드·온프레미스 이식성이 필수이거나 성숙한 오퍼레이터와 운영 역량이 있을 때 정당화된다는 것이 원문의 정리다.

## 7. 스토리지 문제 진단 (기본)

```bash
kubectl get pvc
kubectl describe pvc <name>          # Events가 핵심
kubectl get pv
kubectl get storageclass
kubectl get volumeattachment         # 볼륨이 어느 노드에 연결됐는가
```

| 증상 | 원인 | 대응 |
|---|---|---|
| PVC가 `Pending` + `WaitForFirstConsumer` | 정상. Pod를 만들면 바인딩된다 | - |
| PVC가 `Pending` + 이벤트 없음 | StorageClass 없음, 기본 클래스 미지정 | `kubectl get sc` |
| PVC가 `Pending` + `ProvisioningFailed` | CSI 드라이버 오류, 권한 부족, 쿼터 초과 | CSI 컨트롤러 로그 |
| Pod가 `Pending` + `volume node affinity conflict` | 볼륨 AZ와 노드 AZ 불일치 | `WaitForFirstConsumer` 사용 |
| `Multi-Attach error` | RWO 볼륨을 여러 노드에서 마운트 시도 | 이전 Pod가 완전히 종료되길 대기 |
| PVC 삭제가 `Terminating`에서 멈춤 | 파이널라이저 `pvc-protection` — 사용 중인 Pod 존재 | Pod를 먼저 삭제 |

`Multi-Attach error`는 노드가 갑자기 죽어 볼륨 연결이 해제되지 않은 채 남았을 때 흔히 생긴다. 대개 몇 분 뒤 자동으로 풀린다.

## 핵심 요약

- 스토리지 요구는 **임시(emptyDir) / 설정 주입 / 영구(PVC)** 세 유형이다. emptyDir은 Pod 삭제 시 사라지고, hostPath는 일반 앱에서 쓰지 않는다.
- **PVC**(개발자의 요청) ↔ **PV**(실제 스토리지) ↔ **StorageClass**(종류 정의). 맞는 PV가 없으면 StorageClass의 프로비저너가 **동적으로** 만든다.
- 멀티 AZ에서는 `WaitForFirstConsumer`가 사실상 필수다.
- RWO는 "하나의 노드"이며, 여러 노드 공유(RWX)는 파일 스토리지(NFS 계열)가 필요하다.
- 회수 정책 `Delete`는 PVC 삭제 시 데이터까지 지운다. 중요한 데이터에는 `Retain`을 쓴다.
- CSI는 스토리지 드라이버를 클러스터 밖 컴포넌트로 분리한 표준이다.
- 백업은 애플리케이션·볼륨·클러스터 세 계층으로 나눠 생각하고, 복원 테스트로 검증한다.
- PVC가 Pending이면 `kubectl describe pvc`의 Events부터 본다. `WaitForFirstConsumer`라면 정상일 수 있다.
