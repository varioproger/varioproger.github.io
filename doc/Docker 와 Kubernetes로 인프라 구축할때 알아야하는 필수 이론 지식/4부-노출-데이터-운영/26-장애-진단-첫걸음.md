# 26장. 장애 진단 첫걸음

## 이 장에서 배우는 것

- 장애 진단은 "증상 → 가설 → 확인할 증거 → 변경 → 재검증"의 순서로 한다는 점
- `kubectl get / describe / logs / events`로 증거를 모으는 법
- 흔한 실패 패턴(Pending, ImagePullBackOff, CrashLoopBackOff 등)과 시작 가설
- 어느 계층을 볼지 정하는 방법
- 로그·메트릭을 미리 모아 두는 관측성의 기초와 업그레이드·복구 목표의 개념

## 1. 증거의 종류

장애 대응의 목표는 **사용자의 요청이 성공하는지** 확인하는 것이다. CPU나 Ready Pod 수는 원인을 설명하는 보조 지표다.

- **Metrics**: 지연·오류율·포화도
- **Logs**: 특정 사건의 맥락
- **Traces**: 여러 서비스에 걸친 한 요청의 경로
- **Kubernetes Events**: 스케줄링·이미지·마운트 등 변화의 원인을 찾는 데 유용하지만, 장기 감사 기록이나 모든 앱 로그를 대신하지는 않는다.

`kubectl top`(metrics-server)은 최근 자원 측정에 유용하지만 장기 모니터링·알림 시스템은 아니다.

## 2. 가장 먼저 확인할 것

먼저 **어느 cluster, 어느 Namespace, 어느 앱 버전, 어느 시간대**인지 고정한다. 잘못된 context에서 정상 앱을 조사하거나 새 버전 문제에 이전 Pod 로그를 읽는 실수를 줄인다. 아래 명령은 조회만 하며 자원을 바꾸지 않는다.

```bash
kubectl config current-context
kubectl get nodes -o wide
kubectl get deploy,rs,pods,svc,endpointslices -n <ns> -o wide
kubectl get events -n <ns> --sort-by=.metadata.creationTimestamp
kubectl describe pod <pod> -n <ns>
kubectl logs <pod> -n <ns> -c <container> --tail=100
kubectl logs <pod> -n <ns> -c <container> --previous --tail=100
```

| 명령 | 무엇을 알려 주는가 |
|---|---|
| `kubectl get` | 상태 한눈에 보기 (`-o wide`로 노드·IP, `-w`로 실시간 감시) |
| `kubectl describe` | **1순위.** 상세 상태와 하단의 Events(스케줄 실패, 이미지 pull 실패 등) |
| `kubectl logs` | 앱 로그. `--previous`는 직전에 종료된 컨테이너의 로그(크래시 원인) |
| `kubectl get events` | 시간순 이벤트. 최근 사건 확인 |

`--previous`는 직전 종료 컨테이너 로그가 남아 있을 때만 유용하다. Pod 객체가 없어졌거나 로그가 수거된 뒤까지 항상 조회되지는 않으므로 중앙 수집이 필요하다.

그 밖에 자주 쓰는 도구:

```bash
kubectl exec -it <pod> -- sh                       # 컨테이너 안으로 들어가 확인
kubectl port-forward svc/web 8080:80               # 로컬에서 서비스 접근 테스트
kubectl run t --rm -it --image=busybox --restart=Never -- wget -qO- http://web   # 임시 진단 Pod
kubectl get pods -A --field-selector status.phase!=Running,status.phase!=Succeeded  # 정상이 아닌 Pod
```

## 3. 증상별 분기표 (시작 가설)

| 증상 | 먼저 세울 가설 | 확인할 증거 |
|---|---|---|
| Pod가 생성되지 않음 | ReplicaSet 생성 실패·Quota·admission | Deployment/RS Events, quota |
| **Pending**, nodeName 없음 | requests·taint·affinity·volume 조건 | `FailedScheduling` 메시지, Node 용량 |
| `FailedCreatePodSandBox` | CNI/IP 공급 문제 | Pod Events, CNI Pod 상태·로그 |
| **ImagePullBackOff** | 이미지 이름·pull 권한·외부 연결 | 정확한 image 참조, 노드의 접근 경로 |
| **CrashLoopBackOff** | 앱 종료·설정 누락·probe | 이전 로그(`--previous`), exit code, probe Events |
| **OOMKilled** | 메모리 한계·사용 패턴 | lastState, limit, 메모리 추이 |
| Running이지만 **Ready 아님** | readiness 실패·의존성 | conditions, probe 응답 |
| 내부 Service 실패 | selector·포트·DNS·정책 | EndpointSlice, 호출 위치별 테스트 |
| 외부에서만 실패 | LB·DNS·TLS·보안 그룹 | listener, target 등록·health |
| PVC Pending | StorageClass·driver·권한·바인딩 대기 | PVC Events, StorageClass |
| API **403** Forbidden | 허용 작업 부족 | 현재 신원, RBAC |

표는 **시작 가설이지 확정 진단이 아니다.** 예를 들어 exit code 137만으로 항상 메모리 초과라고 단정하지 않는다. 종료 reason과 함께 판단한다. 또한 `Pending`만 보고 무조건 노드를 늘리지 않고, 먼저 Pod가 이미 노드에 배정되었는지와 Events를 본다.

## 4. 어느 계층을 볼지 정하기

| 관찰한 현상 | 먼저 분리할 질문 |
|---|---|
| `kubectl`이 연결되지 않음 | 앱 장애인가, 관리 API 접근 문제인가? (kubeconfig, 인증·인가, endpoint 경로) |
| Pod가 Pending | 노드가 정해졌는가? (Events, requests, taints, affinity, 노드 용량, PVC) |
| 노드 배정 후 ContainerCreating에서 멈춤 | 실행 준비 중 무엇이 실패했는가? (CNI/IP, 볼륨 마운트) |
| CrashLoopBackOff | 왜 프로세스가 종료되는가? (이전 컨테이너 로그, 종료 코드, 설정, OOMKilled) |
| 앱은 Ready인데 외부 요청 실패 | LB까지와 LB 이후 중 어디인가? (DNS, listener, target health, 보안 그룹, 포트) |
| 내부 Service 연결 실패 | 대상 발견과 전달 중 어디인가? (selector, EndpointSlice, DNS, NetworkPolicy) |

## 5. 예제: "배포 후 오류가 늘었는데 Pod는 Running"

1. rollout과 Ready 수를 본다. 새 Pod의 Ready가 false라면 새 버전이 요청을 받을 준비를 못 한 것이다.
2. 컨테이너 로그와 readiness 응답을 본다. `/ready`가 404라면 앱 경로와 probe 설정이 안 맞는 것이다.
3. EndpointSlice에 기존 Ready 대상이 남아 있는지, 로드밸런서의 target health와 비교한다.
4. 모든 health가 정상인데 업무만 실패한다면 앱 로그·DB·외부 API로 이동한다. "Kubernetes 정상"과 "업무 정상"은 다른 증거로 평가한다.

장애 중 변경을 여러 개 한꺼번에 하면 원인과 효과를 분리하기 어렵다. 복구 조치(이전 이미지로 되돌리기, 설정 수정)는 증거에 따라 고른다.

## 6. 네트워크 문제의 순서

서비스 연결이 안 될 때는 아래 순서로 좁힌다.

```
Pod A → Service/Pod B 연결 실패
  ├─ DNS 문제인가?
  ├─ 같은 노드인가, 다른 노드인가? (다른 노드면 CNI 확인)
  ├─ Service 경유인가? → EndpointSlice / kube-proxy 확인
  ├─ NetworkPolicy가 걸려 있는가? → kubectl get networkpolicy -A
  └─ conntrack/포트 고갈인가?
```

```bash
kubectl get endpointslices -o wide
kubectl exec -it <pod> -- cat /etc/resolv.conf
kubectl exec -it <pod> -- dig <service>.<namespace>.svc.cluster.local
kubectl logs -n kube-system -l k8s-app=kube-dns --tail=50
```

## 7. 관측성 기초 — 증거를 미리 모아 두기

`kubectl logs`와 `kubectl get events`는 지금 남아 있는 것만 보여 준다. 장애가 난 뒤에 증거를 찾으려면 **처음 인프라를 만들 때부터** 로그와 메트릭을 중앙으로 모아 두어야 한다.

### 세 기둥의 역할

| 기둥 | 성격 | 알려 주는 것 |
|---|---|---|
| 메트릭 | 시계열 수치. 집계에 최적화, 저비용·장기 보관 | **무엇이** 잘못됐는가 ("지금 에러율이 얼마인가?") |
| 로그 | 시점별 상세 기록. 고비용, 보관 기간 제한 | **왜** 잘못됐는가 ("그 요청에서 무슨 일이 있었나?") |
| 트레이스 | 요청이 서비스 사이를 지나간 경로. 샘플링으로 비용 통제 | **어디서** 잘못됐는가 ("어느 서비스에서 시간을 쓰나?") |

전형적인 진단 흐름은 알림(메트릭: 에러율 5% 초과) → 대시보드(메트릭: checkout 서비스) → 트레이스(payment 호출에서 타임아웃) → 로그(connection pool exhausted) 순이다.

### 로그 수집 경로

```
컨테이너 stdout/stderr
    ↓ 컨테이너 런타임
노드의 /var/log/pods/...
    ↓ 로그 수집기 (DaemonSet)
    ↓ 파싱, 메타데이터 추가(네임스페이스, Pod, 라벨)
중앙 로그 시스템 (Loki, Elasticsearch, CloudWatch Logs 등)
```

앱은 **파일이 아니라 stdout/stderr로** 로그를 쓴다. 파일에 쓰면 수집기가 읽지 못하고 볼륨이 필요해진다. 가능하면 구조화된 JSON으로 남기고, 요청마다 INFO 로그를 남기지 않는다(로그 비용이 인프라 비용을 넘어서는 흔한 원인이다).

### 메트릭 수집

| 소스 | 제공하는 것 |
|---|---|
| cAdvisor (kubelet 내장) | 컨테이너의 **실제 사용량**(CPU·메모리·IO) |
| kube-state-metrics | 오브젝트의 **선언된 상태**(원하는 replicas, Pod phase 등) |
| node-exporter | 노드 **하드웨어/OS**(디스크 여유, 부하 등) |

Prometheus가 이 소스들을 주기적으로 수집(스크레이프)해 저장하고, Grafana로 대시보드를, Alertmanager로 알림을 만든다. **metrics-server와 혼동하지 말자.** metrics-server는 HPA와 `kubectl top`용으로 최근 값만 제공하고, Prometheus는 장기 저장과 쿼리를 담당한다. 둘 다 필요하다.

> **알림은 증상에 걸고, 원인에 걸지 않는다.** "CPU 사용률 > 80%" 같은 원인 지표는 사용자에게 문제가 없어도 울려 알림 피로를 만든다. "에러율 > 1%", "P99 지연 > 500ms"처럼 사용자가 실제로 겪는 증상에 알림을 걸고, 원인 지표는 대시보드에 둔다.

EKS라면 Control Plane 로그를 CloudWatch Logs로 보내도록 따로 구성할 수 있다. 다만 이것만으로 앱의 stdout 전체가 자동으로 수집되는 것은 아니다.

## 8. 업그레이드와 복구 목표 (개요)

- **업그레이드는 호환성 프로젝트다.** Control Plane 버전 올리기와 노드·add-on·controller·client 버전 변경을 나눠 계획한다. 일반적인 흐름은 사전 조건 확인 → 다음 minor 버전의 Control Plane → 노드 → 필요한 add-on·client 조정이지만, 해당 버전의 공식 순서를 따른다. Control Plane 업그레이드는 `rollout undo`처럼 쉽게 되돌릴 수 있는 작업이 아니므로 검증 환경에서 먼저 확인한다.
- **RTO**는 허용 가능한 복구 시간, **RPO**는 허용 가능한 데이터 손실 시간 범위다. "매일 백업"과 "최근 5분 이내로 복구"는 같은 요구가 아니다. 백업 주기뿐 아니라 새 환경 준비, IAM·DNS·인증서, 데이터 복원과 검증에 걸리는 시간까지 측정한다(백업 계층은 23장).

## 핵심 요약

- 진단은 **증상 → 가설 → 증거 → 변경 → 재검증**의 순서다. 먼저 context·namespace·버전을 고정한다.
- 기본 도구는 `kubectl get`(상태), `describe`(상세와 Events), `logs`(`--previous` 포함), `events`다.
- Pending은 스케줄 조건, ImagePullBackOff는 이미지·권한·네트워크, CrashLoopBackOff는 이전 로그, Running이지만 Ready가 아니면 readiness를 먼저 본다.
- 표는 시작 가설일 뿐이므로 증거로 확인하고, 변경은 한 번에 하나씩 한다.
- 네트워크 문제는 DNS → EndpointSlice/Service → NetworkPolicy 순서로 좁힌다.
- 증거는 장애 전에 모아 두어야 한다. 로그는 stdout → 노드 → 수집기(DaemonSet) → 중앙 저장소로, 메트릭은 Prometheus로 모으고, 알림은 사용자가 겪는 증상에 건다.
- 업그레이드는 버전 호환성을 확인하며 단계적으로 진행하고, 복구 목표(RTO/RPO)는 실제 복원 시간으로 검증한다.
