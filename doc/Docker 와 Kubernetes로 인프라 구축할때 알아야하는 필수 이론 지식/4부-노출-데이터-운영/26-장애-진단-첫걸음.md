# 26장. 장애 진단 첫걸음

> **🎮 게임 서버 개발자에게** — 게임 서버가 죽으면 서버 머신에 들어가 코어 덤프를 열고 로그 파일을 뒤졌을 것이다. 쿠버네티스에서는 그 "서버 머신"이 수시로 바뀌고, 크래시한 컨테이너와 그 로그는 **Pod가 사라지면 함께 사라진다.** 그래서 진단 도구가 `ssh`와 `gdb`가 아니라 `kubectl describe`(Events)와 `logs --previous`이고, 진짜 증거는 장애 전에 중앙으로 모아 둔 로그·메트릭이다. 방법론(증상 → 가설 → 증거 → 변경 → 재검증)은 서버 버그를 잡던 방식과 같다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 점검 배포 직후 에러가 늘었는데 Pod는 전부 `Running`이다.
> - 서버 Pod가 `CrashLoopBackOff`인데 이미 재시작돼서 크래시 원인 로그가 안 보인다.
> - "CPU 80% 초과" 알림이 밤마다 울리는데 정작 유저 장애는 알림 없이 커뮤니티 제보로 알게 된다.

## 코어 — 이것만은 100%

> **한 문장:** 장애 진단은 context·namespace·버전을 고정한 뒤 증상 → 가설 → 증거(`get`/`describe`/`logs --previous`/`events`) → 한 번에 하나씩 변경 → 재검증 순으로 하고, 그 증거는 장애 전에 로그·메트릭을 중앙으로 모아 두어야 존재한다.

1. **고정하고, 가설은 증거로 확인한다** — 먼저 cluster·namespace·버전·시간대를 고정한다. 진단 순서는 증상 → 가설 → 증거 → 변경 → 재검증이고, 변경은 한 번에 하나씩 한다.
2. **증상이 시작 가설과 계층을 정한다** — 1순위 도구는 `kubectl describe`의 Events. Pending은 스케줄 조건, ImagePullBackOff는 이미지·권한·네트워크, CrashLoopBackOff는 `--previous` 로그, Running인데 Ready 아니면 readiness. 네트워크는 DNS → EndpointSlice/Service → NetworkPolicy 순. 분기표는 시작 가설일 뿐이다.
3. **증거는 장애 전에 모아야 존재한다** — 관측성은 메트릭(무엇) / 로그(왜) / 트레이스(어디서). 로그는 stdout → 노드 → DaemonSet 수집기 → 중앙 저장소, 메트릭은 Prometheus로 모으고, 알림은 증상에 건다.
4. **업그레이드와 복구도 검증으로 끝난다** — 업그레이드는 호환성 프로젝트이고, RTO·RPO는 실제 복원 시간으로 측정한다.

**이 장에서 배우는 것 (원래 목차)**

- 장애 진단은 "증상 → 가설 → 확인할 증거 → 변경 → 재검증"의 순서로 한다는 점 → 코어 1
- `kubectl get / describe / logs / events`로 증거를 모으는 법 → 코어 1
- 흔한 실패 패턴(Pending, ImagePullBackOff, CrashLoopBackOff 등)과 시작 가설 → 코어 2
- 어느 계층을 볼지 정하는 방법 → 코어 2
- 로그·메트릭을 미리 모아 두는 관측성의 기초와 업그레이드·복구 목표의 개념 → 코어 3, 코어 4

## 코어 1. 고정하고, 가설은 증거로 확인한다

### 1.1 증거의 종류

**한 줄 요약:** 목표는 사용자 요청의 성공 여부이고, 메트릭·로그·트레이스·Events는 각각 다른 증거다. `kubectl top`은 장기 모니터링이 아니다.

장애 대응의 목표는 **사용자의 요청이 성공하는지** 확인하는 것이다. CPU나 Ready Pod 수는 원인을 설명하는 보조 지표다.

- **Metrics**: 지연·오류율·포화도
- **Logs**: 특정 사건의 맥락
- **Traces**: 여러 서비스에 걸친 한 요청의 경로
- **Kubernetes Events**: 스케줄링·이미지·마운트 등 변화의 원인을 찾는 데 유용하지만, 장기 감사 기록이나 모든 앱 로그를 대신하지는 않는다.

`kubectl top`(metrics-server)은 최근 자원 측정에 유용하지만 장기 모니터링·알림 시스템은 아니다.

### 1.2 가장 먼저 확인할 것 — 맥락 고정과 조회 명령

**한 줄 요약:** cluster·Namespace·앱 버전·시간대를 고정한 뒤, 자원을 바꾸지 않는 조회 명령(get / describe / logs / events)으로 증거를 모은다.

먼저 **어느 cluster, 어느 Namespace, 어느 앱 버전, 어느 시간대**인지 고정한다. 잘못된 context에서 정상 앱을 조사하거나 새 버전 문제에 이전 Pod 로그를 읽는 실수를 줄인다. 아래 명령은 조회만 하며 자원을 바꾸지 않는다.

```bash
kubectl config current-context
kubectl get nodes -o wide
kubectl get deploy,rs,pods,svc,endpointslices -n <ns> -o wide
kubectl get events -n <ns> --sort-by=.metadata.creationTimestamp
kubectl describe pod <pod> -n <ns>
kubectl logs <pod> -n <ns> -c <container> --tail=100
kubectl logs <pod> -n <ns> -c <container> --previous --tail=100
```

| 명령 | 무엇을 알려 주는가 |
|---|---|
| `kubectl get` | 상태 한눈에 보기 (`-o wide`로 노드·IP, `-w`로 실시간 감시) |
| `kubectl describe` | **1순위.** 상세 상태와 하단의 Events(스케줄 실패, 이미지 pull 실패 등) |
| `kubectl logs` | 앱 로그. `--previous`는 직전에 종료된 컨테이너의 로그(크래시 원인) |
| `kubectl get events` | 시간순 이벤트. 최근 사건 확인 |

`--previous`는 직전 종료 컨테이너 로그가 남아 있을 때만 유용하다. Pod 객체가 없어졌거나 로그가 수거된 뒤까지 항상 조회되지는 않으므로 중앙 수집이 필요하다.

그 밖에 자주 쓰는 도구:

```bash
kubectl exec -it <pod> -- sh                       # 컨테이너 안으로 들어가 확인
kubectl port-forward svc/web 8080:80               # 로컬에서 서비스 접근 테스트
kubectl run t --rm -it --image=busybox --restart=Never -- wget -qO- http://web   # 임시 진단 Pod
kubectl get pods -A --field-selector status.phase!=Running,status.phase!=Succeeded  # 정상이 아닌 Pod
```

### 1.3 예제: "배포 후 오류가 늘었는데 Pod는 Running"

**한 줄 요약:** Ready 수 → readiness 응답 → EndpointSlice·LB target health → 앱·DB·외부 API 순으로 좁히고, 변경은 증거에 따라 하나씩 한다.

1. rollout과 Ready 수를 본다. 새 Pod의 Ready가 false라면 새 버전이 요청을 받을 준비를 못 한 것이다.
2. 컨테이너 로그와 readiness 응답을 본다. `/ready`가 404라면 앱 경로와 probe 설정이 안 맞는 것이다.
3. EndpointSlice에 기존 Ready 대상이 남아 있는지, 로드밸런서의 target health와 비교한다.
4. 모든 health가 정상인데 업무만 실패한다면 앱 로그·DB·외부 API로 이동한다. "Kubernetes 정상"과 "업무 정상"은 다른 증거로 평가한다.

장애 중 변경을 여러 개 한꺼번에 하면 원인과 효과를 분리하기 어렵다. 복구 조치(이전 이미지로 되돌리기, 설정 수정)는 증거에 따라 고른다.

## 코어 2. 증상이 시작 가설과 계층을 정한다

### 2.1 증상별 분기표 (시작 가설)

**한 줄 요약:** 증상마다 먼저 세울 가설과 볼 증거가 정해져 있다. 단, 표는 시작 가설이지 확정 진단이 아니다.

| 증상 | 먼저 세울 가설 | 확인할 증거 |
|---|---|---|
| Pod가 생성되지 않음 | ReplicaSet 생성 실패·Quota·admission | Deployment/RS Events, quota |
| **Pending**, nodeName 없음 | requests·taint·affinity·volume 조건 | `FailedScheduling` 메시지, Node 용량 |
| `FailedCreatePodSandBox` | CNI/IP 공급 문제 | Pod Events, CNI Pod 상태·로그 |
| **ImagePullBackOff** | 이미지 이름·pull 권한·외부 연결 | 정확한 image 참조, 노드의 접근 경로 |
| **CrashLoopBackOff** | 앱 종료·설정 누락·probe | 이전 로그(`--previous`), exit code, probe Events |
| **OOMKilled** | 메모리 한계·사용 패턴 | lastState, limit, 메모리 추이 |
| Running이지만 **Ready 아님** | readiness 실패·의존성 | conditions, probe 응답 |
| 내부 Service 실패 | selector·포트·DNS·정책 | EndpointSlice, 호출 위치별 테스트 |
| 외부에서만 실패 | LB·DNS·TLS·보안 그룹 | listener, target 등록·health |
| PVC Pending | StorageClass·driver·권한·바인딩 대기 | PVC Events, StorageClass |
| API **403** Forbidden | 허용 작업 부족 | 현재 신원, RBAC |

표는 **시작 가설이지 확정 진단이 아니다.** 예를 들어 exit code 137만으로 항상 메모리 초과라고 단정하지 않는다. 종료 reason과 함께 판단한다. 또한 `Pending`만 보고 무조건 노드를 늘리지 않고, 먼저 Pod가 이미 노드에 배정되었는지와 Events를 본다.

### 2.2 어느 계층을 볼지 정하기

**한 줄 요약:** 현상마다 "어느 경계의 이쪽인가 저쪽인가"를 먼저 묻는다 — 관리 API인가 앱인가, 노드 배정 전인가 후인가, LB 앞인가 뒤인가.

| 관찰한 현상 | 먼저 분리할 질문 |
|---|---|
| `kubectl`이 연결되지 않음 | 앱 장애인가, 관리 API 접근 문제인가? (kubeconfig, 인증·인가, endpoint 경로) |
| Pod가 Pending | 노드가 정해졌는가? (Events, requests, taints, affinity, 노드 용량, PVC) |
| 노드 배정 후 ContainerCreating에서 멈춤 | 실행 준비 중 무엇이 실패했는가? (CNI/IP, 볼륨 마운트) |
| CrashLoopBackOff | 왜 프로세스가 종료되는가? (이전 컨테이너 로그, 종료 코드, 설정, OOMKilled) |
| 앱은 Ready인데 외부 요청 실패 | LB까지와 LB 이후 중 어디인가? (DNS, listener, target health, 보안 그룹, 포트) |
| 내부 Service 연결 실패 | 대상 발견과 전달 중 어디인가? (selector, EndpointSlice, DNS, NetworkPolicy) |

### 2.3 네트워크 문제의 순서

**한 줄 요약:** DNS → 같은/다른 노드(CNI) → Service 경유(EndpointSlice·kube-proxy) → NetworkPolicy → conntrack/포트 고갈 순으로 좁힌다.

서비스 연결이 안 될 때는 아래 순서로 좁힌다.

```
Pod A → Service/Pod B 연결 실패
  ├─ DNS 문제인가?
  ├─ 같은 노드인가, 다른 노드인가? (다른 노드면 CNI 확인)
  ├─ Service 경유인가? → EndpointSlice / kube-proxy 확인
  ├─ NetworkPolicy가 걸려 있는가? → kubectl get networkpolicy -A
  └─ conntrack/포트 고갈인가?
```

```bash
kubectl get endpointslices -o wide
kubectl exec -it <pod> -- cat /etc/resolv.conf
kubectl exec -it <pod> -- dig <service>.<namespace>.svc.cluster.local
kubectl logs -n kube-system -l k8s-app=kube-dns --tail=50
```

## 코어 3. 증거는 장애 전에 모아야 존재한다

### 3.1 관측성 기초 — 왜 미리 모으나

**한 줄 요약:** `kubectl logs`와 `events`는 지금 남은 것만 보여 주므로, 처음 인프라를 만들 때부터 로그·메트릭을 중앙으로 모은다.

`kubectl logs`와 `kubectl get events`는 지금 남아 있는 것만 보여 준다. 장애가 난 뒤에 증거를 찾으려면 **처음 인프라를 만들 때부터** 로그와 메트릭을 중앙으로 모아 두어야 한다.

### 3.2 세 기둥의 역할

**한 줄 요약:** 메트릭 = 무엇이, 로그 = 왜, 트레이스 = 어디서. 진단은 알림 → 대시보드 → 트레이스 → 로그로 흐른다.

| 기둥 | 성격 | 알려 주는 것 |
|---|---|---|
| 메트릭 | 시계열 수치. 집계에 최적화, 저비용·장기 보관 | **무엇이** 잘못됐는가 ("지금 에러율이 얼마인가?") |
| 로그 | 시점별 상세 기록. 고비용, 보관 기간 제한 | **왜** 잘못됐는가 ("그 요청에서 무슨 일이 있었나?") |
| 트레이스 | 요청이 서비스 사이를 지나간 경로. 샘플링으로 비용 통제 | **어디서** 잘못됐는가 ("어느 서비스에서 시간을 쓰나?") |

전형적인 진단 흐름은 알림(메트릭: 에러율 5% 초과) → 대시보드(메트릭: checkout 서비스) → 트레이스(payment 호출에서 타임아웃) → 로그(connection pool exhausted) 순이다.

### 3.3 로그 수집 경로

**한 줄 요약:** stdout/stderr → 노드 `/var/log/pods` → DaemonSet 수집기 → 중앙 로그 시스템. 앱은 파일이 아니라 stdout에 쓴다.

```
컨테이너 stdout/stderr
    ↓ 컨테이너 런타임
노드의 /var/log/pods/...
    ↓ 로그 수집기 (DaemonSet)
    ↓ 파싱, 메타데이터 추가(네임스페이스, Pod, 라벨)
중앙 로그 시스템 (Loki, Elasticsearch, CloudWatch Logs 등)
```

앱은 **파일이 아니라 stdout/stderr로** 로그를 쓴다. 파일에 쓰면 수집기가 읽지 못하고 볼륨이 필요해진다. 가능하면 구조화된 JSON으로 남기고, 요청마다 INFO 로그를 남기지 않는다(로그 비용이 인프라 비용을 넘어서는 흔한 원인이다).

EKS라면 Control Plane 로그를 CloudWatch Logs로 보내도록 따로 구성할 수 있다. 다만 이것만으로 앱의 stdout 전체가 자동으로 수집되는 것은 아니다.

### 3.4 메트릭 수집

**한 줄 요약:** cAdvisor(실제 사용량) / kube-state-metrics(선언 상태) / node-exporter(노드 OS)를 Prometheus가 모은다. metrics-server와는 역할이 다르다.

| 소스 | 제공하는 것 |
|---|---|
| cAdvisor (kubelet 내장) | 컨테이너의 **실제 사용량**(CPU·메모리·IO) |
| kube-state-metrics | 오브젝트의 **선언된 상태**(원하는 replicas, Pod phase 등) |
| node-exporter | 노드 **하드웨어/OS**(디스크 여유, 부하 등) |

Prometheus가 이 소스들을 주기적으로 수집(스크레이프)해 저장하고, Grafana로 대시보드를, Alertmanager로 알림을 만든다. **metrics-server와 혼동하지 말자.** metrics-server는 HPA와 `kubectl top`용으로 최근 값만 제공하고, Prometheus는 장기 저장과 쿼리를 담당한다. 둘 다 필요하다.

### 3.5 알림 설계

**한 줄 요약:** 알림은 사용자가 겪는 증상(에러율, P99 지연)에 걸고, 원인 지표(CPU 등)는 대시보드에 둔다.

> **알림은 증상에 걸고, 원인에 걸지 않는다.** "CPU 사용률 > 80%" 같은 원인 지표는 사용자에게 문제가 없어도 울려 알림 피로를 만든다. "에러율 > 1%", "P99 지연 > 500ms"처럼 사용자가 실제로 겪는 증상에 알림을 걸고, 원인 지표는 대시보드에 둔다.

## 코어 4. 업그레이드와 복구도 검증으로 끝난다

### 4.1 업그레이드와 복구 목표 (개요)

**한 줄 요약:** 업그레이드는 Control Plane → 노드 → add-on·client 순의 호환성 프로젝트이고, RTO·RPO는 복원에 걸리는 실제 시간으로 측정한다.

- **업그레이드는 호환성 프로젝트다.** Control Plane 버전 올리기와 노드·add-on·controller·client 버전 변경을 나눠 계획한다. 일반적인 흐름은 사전 조건 확인 → 다음 minor 버전의 Control Plane → 노드 → 필요한 add-on·client 조정이지만, 해당 버전의 공식 순서를 따른다. Control Plane 업그레이드는 `rollout undo`처럼 쉽게 되돌릴 수 있는 작업이 아니므로 검증 환경에서 먼저 확인한다.
- **RTO**는 허용 가능한 복구 시간, **RPO**는 허용 가능한 데이터 손실 시간 범위다. "매일 백업"과 "최근 5분 이내로 복구"는 같은 요구가 아니다. 백업 주기뿐 아니라 새 환경 준비, IAM·DNS·인증서, 데이터 복원과 검증에 걸리는 시간까지 측정한다(백업 계층은 [24장](24-스토리지.md)).

## 실무 적용

### 체크리스트

- [ ] 진단은 **증상 → 가설 → 증거 → 변경 → 재검증**의 순서다. 먼저 context·namespace·버전·시간대를 고정한다.
- [ ] 기본 도구는 `kubectl get`(상태), `describe`(상세와 Events), `logs`(`--previous` 포함), `events`다.
- [ ] Pending은 스케줄 조건, ImagePullBackOff는 이미지·권한·네트워크, CrashLoopBackOff는 이전 로그, Running이지만 Ready가 아니면 readiness를 먼저 본다.
- [ ] 표는 시작 가설일 뿐이므로 증거로 확인하고(exit 137 단정 금지, Pending에 곧바로 노드 증설 금지), 변경은 한 번에 하나씩 한다.
- [ ] "Kubernetes 정상"과 "업무 정상"은 다른 증거로 평가한다.
- [ ] 네트워크 문제는 DNS → EndpointSlice/Service → NetworkPolicy 순서로 좁힌다.
- [ ] 증거는 장애 전에 모아 두어야 한다. 로그는 stdout → 노드 → 수집기(DaemonSet) → 중앙 저장소로, 메트릭은 Prometheus로 모으고, 알림은 사용자가 겪는 증상에 건다.
- [ ] 업그레이드는 버전 호환성을 확인하며 단계적으로 진행하고, 복구 목표(RTO/RPO)는 실제 복원 시간으로 검증한다.

### 시나리오로 확인하기

1. **상황:** 게임 서버 Pod가 `CrashLoopBackOff`다. C++ 서버 시절 습관대로 "서버에 들어가 로그 파일을 보자"며 `kubectl exec`를 시도했지만 컨테이너가 계속 재시작돼 들어가지지 않고, `kubectl logs`에는 새로 뜬 컨테이너의 시작 로그만 보인다.
   **질문:** 크래시 원인을 어떻게 보나?

   <details markdown="1"><summary>답 확인</summary>

   `kubectl logs <pod> -c <container> --previous`로 직전에 종료된 컨테이너의 로그를 보고, `kubectl describe pod`로 lastState의 exit code·종료 reason과 probe 관련 Events를 확인한다. 시작 가설은 앱 종료·설정 누락·probe 문제다. Pod가 지워지면 이 로그도 사라지므로 평소에 stdout 로그를 중앙으로 모아 둬야 한다. → 코어 1, 코어 2, 코어 3

   </details>

2. **상황:** 서버 Pod가 exit code 137로 재시작됐다. 팀원이 "메모리 누수다, limit을 두 배로 올리자"고 한다.
   **질문:** 바로 올려도 되나?

   <details markdown="1"><summary>답 확인</summary>

   137만으로 메모리 초과라고 단정하지 않는다. `describe`의 종료 reason이 `OOMKilled`인지, limit과 메모리 추이가 어떤지 증거로 확인한 뒤 판단한다. 장애 중에 여러 설정을 한꺼번에 바꾸면 원인과 효과를 분리할 수 없으니 변경은 하나씩 한다. → 코어 1, 코어 2

   </details>

3. **상황:** 점검 배포 후 에러가 늘었는데 모든 Pod가 `Running`이다.
   **질문:** 어떤 순서로 좁히나?

   <details markdown="1"><summary>답 확인</summary>

   ① rollout과 Ready 수(새 Pod Ready가 false인가) ② 컨테이너 로그와 readiness 응답(`/ready`가 404면 경로와 probe 불일치) ③ EndpointSlice의 Ready 대상과 LB target health 비교 ④ 모든 health가 정상인데 업무만 실패하면 앱 로그·DB·외부 API. 복구(이전 이미지로 되돌리기 등)는 증거에 따라 고른다. → 코어 1

   </details>

4. **상황:** 새벽마다 "노드 CPU 80% 초과" 알림이 울리지만 유저 불편은 없다. 반대로 지난주 로그인 장애는 알림 없이 커뮤니티 제보로 알았다.
   **질문:** 알림 설계를 어떻게 바꿔야 하나?

   <details markdown="1"><summary>답 확인</summary>

   CPU 같은 원인 지표 알림은 사용자 문제가 없어도 울려 알림 피로를 만든다. 로그인 API의 에러율(> 1%)이나 P99 지연(> 500ms)처럼 사용자가 겪는 증상에 알림을 걸고, CPU는 대시보드에 둔다. 장기 메트릭은 metrics-server가 아니라 Prometheus로 수집한다. → 코어 3

   </details>

5. **상황:** Pod가 `Pending`이 되자 바로 노드 그룹 크기를 늘리려 한다.
   **질문:** 그 전에 무엇을 확인하나?

   <details markdown="1"><summary>답 확인</summary>

   Pod가 이미 노드에 배정되었는지(nodeName)와 Events를 먼저 본다. 배정 전이라면 `FailedScheduling` 메시지로 requests·taint·affinity·volume(PVC) 조건과 노드 용량을 확인한다. 노드 부족이 아닌 원인이 많아 노드를 늘려도 해결되지 않을 수 있다. → 코어 2

   </details>

   </details>

8. 앱은 왜 로그를 파일이 아니라 stdout/stderr로 써야 하나?

   <details markdown="1"><summary>답 확인</summary>

   로그는 컨테이너 stdout/stderr → 런타임 → 노드의 `/var/log/pods` → DaemonSet 수집기 → 중앙 로그 시스템으로 흐른다. 파일에 쓰면 수집기가 읽지 못하고 볼륨이 필요해진다. 가능하면 구조화된 JSON으로 남기고 요청마다 INFO 로그를 남기지 않는다. → 코어 3 (3.3)

   </details>

9. metrics-server와 Prometheus는 어떻게 다르며, 메트릭 소스 세 가지는?

   <details markdown="1"><summary>답 확인</summary>

   metrics-server는 HPA와 `kubectl top`용으로 최근 값만 제공하고, Prometheus는 소스를 주기적으로 스크레이프해 장기 저장·쿼리를 담당하므로 둘 다 필요하다. 소스는 cAdvisor(컨테이너 실제 사용량), kube-state-metrics(오브젝트 선언 상태), node-exporter(노드 하드웨어/OS)다. → 코어 3 (3.4)

   </details>

10. 알림은 무엇에 걸어야 하며, RTO와 RPO는 무엇인가?

    <details markdown="1"><summary>답 확인</summary>

    알림은 원인(CPU 80% 등)이 아니라 사용자가 겪는 증상(에러율 > 1%, P99 지연 > 500ms)에 건다. 원인 지표 알림은 알림 피로를 만든다. RTO는 허용 가능한 복구 시간, RPO는 허용 가능한 데이터 손실 시간 범위이며, 백업 주기뿐 아니라 새 환경 준비·IAM·DNS·인증서·복원·검증 시간까지 측정해야 한다. → 코어 3 (3.5), 코어 4

    </details>

### 3. 기억 고리

- **C++ 유추:** `logs --previous` + `describe`의 lastState = 코어 덤프와 마지막 로그. ⚠️ 깨지는 곳: Pod가 지워지면 흔적도 함께 사라지고, exit 137은 "SIGKILL로 죽었다"일 뿐 OOM이라는 증거가 아니다. 사후 분석의 유일한 기반은 미리 모아 둔 중앙 로그·메트릭이다.
- **비유:** 장애 진단 = 의사의 진료. 증상을 듣고(증상), 의심 질환을 세우고(가설), 검사로 확인하고(증거), 처방하고(변경), 다시 검사한다(재검증). 증상별 분기표는 "열이 나면 감기부터 의심"하는 초진 목록이다. ⚠️ 비유가 깨지는 지점: 환자는 병원에서 바로 검사할 수 있지만, 클러스터의 증거(로그·이벤트)는 Pod가 사라지면 함께 사라지므로 장애 **전에** 중앙 수집해 둔 것만 쓸 수 있다.
- **묶음(3의 법칙):** 관측성 3기둥(메트릭=무엇 / 로그=왜 / 트레이스=어디서), 메트릭 소스 3(cAdvisor / kube-state-metrics / node-exporter), 첫 3도구(get / describe / logs --previous).
- **대칭·순서:** 증상 → 가설 → 증거 → 변경 → 재검증. 네트워크는 DNS → 노드 위치(CNI) → Service(EndpointSlice·kube-proxy) → NetworkPolicy → conntrack. 대비 쌍: 증상 알림 vs 원인 알림, metrics-server vs Prometheus, RTO vs RPO, "Kubernetes 정상" vs "업무 정상".
