# 24장. 인증·인가(RBAC)·보안·오토스케일링 기초

## 이 장에서 배우는 것

- API 서버가 요청을 처리하는 3개의 관문(인증 → 인가 → 어드미션)
- RBAC의 네 가지 리소스(Role, ClusterRole, RoleBinding, ClusterRoleBinding)
- 워크로드 보안의 기본 사고방식(블래스트 레이디어스)과 `securityContext`, Pod Security Admission, NetworkPolicy의 역할
- 오토스케일링의 세 축(HPA, VPA, 노드 오토스케일러)과 HPA의 계산 방식

## 1. 요청 처리 파이프라인

API 서버는 클러스터의 유일한 진입점이므로 접근 통제도 한 곳에서 이루어진다.

```
kubectl / Pod / 컨트롤러
        │  HTTPS 요청
        ▼
  ① 인증 (Authentication)  "당신은 누구입니까?"      → 실패 시 401
  ② 인가 (Authorization)   "그 행동을 할 권한이 있습니까?" → 실패 시 403
  ③ 어드미션 제어 (Admission Control)  요청 수정(Mutating) / 정책 검증(Validating)
  ④ etcd에 저장
```

**401과 403의 차이**를 알면 진단이 빨라진다. 401은 신원을 확인하지 못한 것(인증서·토큰·kubeconfig 문제), 403은 신원은 확인됐지만 권한이 없는 것(RBAC 문제)이다.

```bash
kubectl auth whoami                       # 나는 누구인가
kubectl auth can-i create pods            # 내가 이것을 할 수 있는가
kubectl auth can-i delete deployments -n prod
kubectl auth can-i --list -n default      # 내가 할 수 있는 모든 것
```

## 2. 인증 — 쿠버네티스에는 사용자 오브젝트가 없다

`kubectl get users`는 동작하지 않는다. 쿠버네티스는 사용자를 저장하지 않고, 요청에 담긴 증거(인증서, 토큰)를 검증해 **문자열로 된 사용자 이름과 그룹 목록**을 추출할 뿐이다. 사용자 생성·삭제는 외부 시스템(인증서 CA, OIDC 제공자, 클라우드 IAM)의 일이다. 예외는 **ServiceAccount**로, 실제 API 오브젝트다.

| | 일반 사용자 | ServiceAccount |
|---|---|---|
| 대상 | 사람, 외부 시스템 | 클러스터 내 워크로드 |
| API 오브젝트 | 없음 | 있음 |
| 관리 | 외부 (CA, OIDC, IAM) | 쿠버네티스 |

모든 Pod는 ServiceAccount를 갖는다(지정하지 않으면 네임스페이스의 `default`). 대부분의 애플리케이션은 쿠버네티스 API를 호출하지 않으므로, 토큰이 자동 마운트되어 Pod가 침해될 때 악용되지 않도록 필요 없으면 끈다.

```yaml
spec:
  serviceAccountName: my-app
  automountServiceAccountToken: false
```

> `system:masters` 그룹은 RBAC 검사를 건너뛰고 모든 것을 할 수 있다. kubeadm이 만드는 `admin.conf`의 인증서가 이 그룹이므로 일상적으로 쓰지 말고 보관해야 한다.

## 3. 인가 — RBAC

```
        네임스페이스 스코프          클러스터 스코프
권한   │      Role        │      │   ClusterRole    │
연결   │   RoleBinding    │      │ClusterRoleBinding│
```

- **Role / ClusterRole**: "무엇을 할 수 있는가"(권한 묶음)
- **RoleBinding / ClusterRoleBinding**: 그 권한을 "누구에게" 줄 것인가

| Binding | Role 참조 | 적용 범위 |
|---|---|---|
| RoleBinding | Role | 그 네임스페이스 |
| RoleBinding | **ClusterRole** | **그 네임스페이스에만** |
| ClusterRoleBinding | ClusterRole | 클러스터 전체 |

두 번째 조합(RoleBinding이 ClusterRole 참조)이 실무의 핵심이다. ClusterRole 하나를 정의하고 여러 네임스페이스에서 재사용한다.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: developer
  namespace: dev
rules:
  - apiGroups: ["", "apps"]
    resources: ["pods", "deployments"]
    verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
  - apiGroups: [""]
    resources: ["pods/log"]
    verbs: ["get"]
```

`apiGroups`의 빈 문자열 `""`은 코어 그룹(Pod, Service, ConfigMap, Secret 등)이다. 주체(Subject)는 User, Group, ServiceAccount 세 종류이며, 사람이 들어오고 나갈 때마다 RBAC을 고치지 않도록 **그룹 기반 바인딩**을 권장한다.

내장 ClusterRole은 다음과 같다.

| 이름 | 권한 |
|---|---|
| `cluster-admin` | 모든 것. ClusterRoleBinding으로 주면 슈퍼유저 |
| `admin` | 네임스페이스 안의 모든 것 + RBAC 관리 |
| `edit` | 네임스페이스 안의 리소스 읽기/쓰기. RBAC 관리는 제외 |
| `view` | 읽기 전용. Secret 제외 |

**RBAC 설계 원칙**: 최소 권한, 그룹 기반, 네임스페이스 스코프 우선(`cluster-admin`은 극소수에게만). 특히 `get`과 `list`는 다르다. secrets에 `list` 권한이 있으면 그 네임스페이스의 모든 시크릿을 덤프할 수 있다. `pods/exec`, `pods` 생성(hostPath·특권 컨테이너로 노드 장악 가능) 같은 권한도 신중하게 다룬다.

## 4. 워크로드 보안 기본

RBAC이 "누가 API를 호출할 수 있는가"라면, 워크로드 보안은 "**그 워크로드가 실행된 뒤에 무엇을 할 수 있는가**"다. 유용한 질문은 "이것이 침해되면 피해가 어디까지 번지는가?" 곧 **블래스트 레이디어스**(blast radius, 폭발 반경)이다. 각 층에서 반경을 좁힌다.

| 침해 시 질문 | 막는 것 |
|---|---|
| 컨테이너 안에서 무엇을 할 수 있나? (root? 쓰기 가능한 FS?) | `securityContext` |
| 노드로 탈출할 수 있나? (hostPath, privileged) | Pod Security Admission |
| 다른 Pod와 통신할 수 있나? (기본은 전부 가능) | NetworkPolicy |
| API 서버를 호출할 수 있나? | `automountServiceAccountToken: false`, RBAC |

### securityContext

```yaml
containers:
  - name: app
    securityContext:
      runAsNonRoot: true                # root면 컨테이너 시작 거부
      allowPrivilegeEscalation: false   # setuid로 권한 상승 차단
      readOnlyRootFilesystem: true      # 루트 FS 쓰기 금지
      privileged: false
      capabilities:
        drop: ["ALL"]                   # 모든 capability 제거
      seccompProfile:
        type: RuntimeDefault            # 시스템콜 필터링
```

`privileged: true`가 가장 위험하다. 사실상 노드의 root와 같다.

> **[보충]** 원문은 이 필드들이 앞서 다룬 리눅스 기본 요소(2부의 격리 기능 등)를 쓴다고 설명한다. 이 책에서 capability는 2부(4·5장)와 14장에서 다뤘지만, 각 필드의 커널 수준 동작까지 다루지는 않았다.

### Pod Security Admission (PSA)

**네임스페이스 라벨 하나**로 보안 프로파일을 지정한다.

| 프로파일 | 내용 |
|---|---|
| `privileged` | 제한 없음 (시스템 컴포넌트용) |
| `baseline` | 알려진 권한 상승을 차단. 대부분의 앱이 수정 없이 통과 |
| `restricted` | 강력한 하드닝. 모범 사례 강제 |

`baseline`은 `privileged: true`, hostNetwork/hostPID/hostIPC, hostPath 볼륨 등을 금지한다. `restricted`는 여기에 더해 `runAsNonRoot: true`, `allowPrivilegeEscalation: false`, `capabilities.drop: ["ALL"]`, `seccompProfile.type: RuntimeDefault` 등을 요구한다.

라벨은 모드별로 붙인다. `enforce`는 위반 Pod 생성을 거부하고, `warn`은 kubectl 응답에 경고만 표시하며(생성은 됨), `audit`는 감사 로그에만 기록한다.

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: production
  labels:
    pod-security.kubernetes.io/enforce: baseline    # 위반하면 생성 거부
    pod-security.kubernetes.io/warn: restricted     # 경고만 표시
    pod-security.kubernetes.io/audit: restricted    # 감사 로그에만 기록
```

**한 번에 `restricted`를 강제하면 배포가 전부 실패할 수 있다.** 먼저 `warn`/`audit`로 위반 워크로드를 파악해 고친 뒤 `enforce: baseline` → `enforce: restricted` 순으로 단계적으로 올린다.

### NetworkPolicy

쿠버네티스의 기본 네트워크 모델은 **모든 Pod가 모든 Pod와 통신 가능**이고, NetworkPolicy가 이를 제한한다. 핵심 규칙은 다음과 같다.

- 적용되는 정책이 없는 Pod는 전부 허용된다. Ingress 정책이 하나라도 적용된 Pod는 명시된 것 외의 들어오는 트래픽이 전부 거부된다(Egress도 같다).
- 정책은 누적된다(허용 규칙의 합집합). 거부 규칙은 없고 허용 규칙만 있다.
- **CNI가 지원해야 동작한다.** 지원하지 않는 CNI(예: Flannel, kind 기본 CNI인 kindnet)에서는 NetworkPolicy를 만들어도 조용히 무시된다. Calico, Cilium, AWS VPC CNI(v1.14+) 등은 지원한다.

가장 흔한 출발점은 네임스페이스에 **기본 거부** 정책을 깔고 필요한 통신만 여는 것이다.

```yaml
# 모든 Ingress 거부 (ingress 규칙이 없으면 전부 거부)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: production
spec:
  podSelector: {}                    # 네임스페이스의 모든 Pod
  policyTypes: [Ingress]
---
# app=api Pod는 app=frontend Pod에서 오는 8080 포트만 허용
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-allow-frontend
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: api
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: frontend
      ports:
        - protocol: TCP
          port: 8080
```

> **Egress를 막으면 DNS도 막힌다.** NetworkPolicy 적용 후 모든 것이 깨지는 사고의 대부분이 이것이다. Egress 기본 거부를 쓴다면 `kube-system`의 `k8s-app: kube-dns` Pod로 가는 UDP/TCP 53번 포트를 반드시 허용한다.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns
  namespace: production
spec:
  podSelector: {}
  policyTypes: [Egress]
  egress:
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: kube-system
          podSelector:
            matchLabels:
              k8s-app: kube-dns
      ports:
        - { protocol: UDP, port: 53 }
        - { protocol: TCP, port: 53 }
```

`from`/`to` 목록에서 하이픈(`-`)의 위치도 주의한다. `namespaceSelector`와 `podSelector`를 **각각 별도 항목(`-`)으로 쓰면 OR**(둘 중 하나), 위 DNS 예시처럼 **한 항목 안에 함께 쓰면 AND**(그 네임스페이스의 그 Pod만)다. 실무에서 가장 흔한 실수다.

## 5. 오토스케일링 기초

오토스케일링에는 세 축이 있다.

| 축 | 질문 | 도구 |
|---|---|---|
| 가로 | "Pod를 몇 개 띄울까?" | HPA (Horizontal Pod Autoscaler) |
| 세로 | "Pod 하나에 얼마를 줄까?" | VPA (Vertical Pod Autoscaler) |
| 노드 | "노드를 몇 개 둘까?" | Cluster Autoscaler / Karpenter |

세 축은 맞물려 있다. HPA가 Pod를 늘리면 노드가 부족해지고, Cluster Autoscaler가 노드를 추가한다.

### 전제: metrics-server

HPA와 VPA는 메트릭이 있어야 한다. **metrics-server**가 kubelet에서 CPU·메모리 사용량을 수집해 `kubectl top nodes/pods`와 HPA에 제공한다. 최근 값만 보관하므로 모니터링 시스템(Prometheus)을 대체하지 않는다.

### HPA

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70      # requests 대비 70%
```

```
desiredReplicas = ceil( currentReplicas × ( currentMetric / desiredMetric ) )
예) 현재 4개, 평균 CPU 90%, 목표 70% → ceil(4 × 90/70) = 6
```

비율이 0.9&#126;1.1 사이면 스케일하지 않는다(미세한 변동 방지).

> **Utilization의 기준은 노드 용량이 아니라 `requests`다.** `requests.cpu: 200m`에 목표 70%면 140m를 넘을 때 스케일 아웃한다. requests를 바꾸면 HPA의 동작이 달라지므로, requests가 틀리면 HPA도 틀린다(18장).

### VPA와 노드 오토스케일링

- **VPA**는 Pod의 requests/limits를 조절한다. `Off` 모드는 추천만 계산하고, `Recreate`/`Auto` 모드는 Pod를 삭제하고 재생성해 적용한다. 원문은 `Off` 모드로 권고값만 받아 매니페스트에 반영하는 방식을 가장 안전한 실무 방법으로 권한다.
- **Cluster Autoscaler**는 리소스 부족으로 Pending인 Pod를 발견하면 노드 그룹을 키우고, 사용률이 낮은 노드는 Pod를 옮긴 뒤 제거한다. 노드가 부팅되어 Pod가 스케줄되기까지 보통 1&#126;5분이 걸린다.

## 핵심 요약

- API 요청은 **인증(401) → 인가(403) → 어드미션** 순으로 통과한다. 쿠버네티스에는 사용자 오브젝트가 없고 ServiceAccount만 API 오브젝트다.
- RBAC은 Role(권한)과 Binding(연결)의 조합이다. 최소 권한·그룹 기반·네임스페이스 스코프를 우선한다.
- 워크로드 보안은 "침해되면 어디까지 번지는가"를 층마다 줄이는 일이다: securityContext, PSA, NetworkPolicy, ServiceAccount 토큰 끄기.
- PSA는 `warn`/`audit`로 시작해 `enforce`로 단계적으로 올린다. NetworkPolicy는 기본 거부 후 필요한 통신만 열되, Egress를 막을 때는 DNS를 반드시 허용한다.
- 오토스케일링은 HPA(Pod 수), VPA(Pod 크기), 노드 오토스케일러(노드 수)의 세 축이다. HPA의 Utilization은 **requests 기준**이다.

## 확인 질문

1. `kubectl` 호출이 401로 실패했을 때와 403으로 실패했을 때, 각각 무엇을 의심해야 하는가?
2. 특정 네임스페이스에서만 `edit` 권한을 주고 싶다면 어떤 리소스 조합을 쓰는가?
3. HPA 목표가 CPU 70%이고 requests가 200m일 때, Pod당 평균 사용량이 몇 m를 넘으면 스케일 아웃이 시작되는가?
