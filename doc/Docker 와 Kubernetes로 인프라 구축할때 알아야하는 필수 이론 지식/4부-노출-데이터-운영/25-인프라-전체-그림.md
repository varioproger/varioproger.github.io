# 25장. 인프라 전체 그림 — Docker, Kubernetes, Terraform, EKS의 역할과 배포 흐름

> 이 장의 예시는 원문과 같이 **일반 EKS + EC2 Managed Node Group** 구성을 기준으로 한 학습용 설명이다. 수량은 원리를 보이기 위한 가정이다.

## 이 장에서 배우는 것

- Docker, Kubernetes, EKS, Terraform이 각각 무엇을 맡는지
- Node, Pod, 컨테이너, 이미지가 서로 어떤 관계인지
- Git → 이미지 빌드 → 레지스트리 → 배포로 이어지는 흐름
- Pod나 Node가 늘어날 때 `terraform apply`가 필요한지 판단하는 방법
- 매니지드 쿠버네티스에서도 사용자가 책임지는 범위
- 매니페스트 배포 도구(Helm, Kustomize, GitOps)의 역할(개요)

## 1. 먼저 용어 정리: 머신, 실행 단위, 관리 프로그램

- **Node**: Kubernetes 클러스터에 연결되어 앱 실행에 쓰이는 머신. 이 예시에서는 EC2 한 대가 worker Node 하나에 대응한다. Node 객체는 그 머신의 주소·용량·상태를 나타내는 기록이다. Node YAML을 등록하는 것만으로 EC2가 만들어지지는 않는다.
- **Pod**: 같은 노드에 함께 배치할 컨테이너를 묶는 단위. 한 Node에 여러 Pod가 실행될 수 있고, 한 Pod가 여러 EC2에 나뉘어 실행되지는 않는다.
- Node는 **실행 장소**, Pod는 **배치 단위**, 컨테이너 안의 앱은 **실제 프로세스**다.

```
EC2 Node A                       EC2 Node B
├─ Linux 커널                    ├─ Linux 커널
├─ kubelet / containerd          ├─ kubelet / containerd
├─ Pod 1 → 주문 앱 컨테이너       ├─ Pod 3 → 주문 앱 컨테이너
└─ Pod 2 → 주문 앱 컨테이너       └─ 추가 Pod를 실행할 여유
```

Pod가 하나 더 생겨도 EC2가 한 대 더 생긴 것은 아니다. IP는 네트워크 주소이고 EC2는 머신이다.

## 2. 네 가지 도구의 역할

| 도구 | 하는 일 |
|---|---|
| **Docker** | 소스와 Dockerfile로 **이미지**를 만들고(빌드), 로컬에서 컨테이너를 실행해 확인한다. 이미지는 실행 중인 서버가 아니라 다시 실행할 수 있도록 저장한 산출물이다. |
| **Kubernetes** | "이미지 A의 앱을 3개 유지하라"는 **실행 의도를 저장하고 계속 맞춘다**. Deployment는 설정을 저장하는 객체이며, Deployment controller → ReplicaSet controller → Pod 객체 생성 → Scheduler가 노드 선택 → 노드의 kubelet이 runtime에 실행 요청 순으로 현실이 만들어진다. |
| **EKS** | AWS가 관리하는 **Kubernetes 제어부**(컨트롤 플레인: API Server, controller, scheduler, etcd)를 제공한다. 'EKS 스케줄러'가 따로 있는 것이 아니라 EKS가 제공하는 Kubernetes의 scheduler가 배치를 담당한다. |
| **Terraform** | HCL로 VPC, subnet, EKS cluster, Node Group, IAM, ECR 같은 **AWS 자원과 정책을 코드로 선언**하고 provider로 API를 호출한다. `plan`으로 계획을 보고 `apply`로 반영한다. 일반 CLI 실행은 끝나면 종료되며 Pod가 늘어날 때마다 자동으로 다시 실행되지 않는다. |

**Kubernetes의 기본 scheduler는 EC2 생성 도구가 아니다.** Pod를 배치할 곳이 없으면 배치가 진행되지 않는다. 앱 개수 조정과 머신 공급은 연결할 수 있는 **별개의 일**이다.

### 누가 어디서 실행되는가

| 주체 | 주로 실행되는 곳 | 직접 바꾸는 것 | 작업 이후 남는 것 |
|---|---|---|---|
| Docker 빌드 도구 | 개발 머신 또는 CI runner | 이미지 산출물 | 레지스트리의 이미지 |
| Terraform | 운영자 머신 또는 인프라 CI runner | 담당 API의 자원·설정 | AWS 자원, 적용한 정책, state |
| Kubernetes 제어부 | EKS에서는 AWS 관리 영역 | Pod 등 객체, 배치·상태 | 지속적인 제어 루프 |
| kubelet / containerd | 각 worker Node | 로컬 실행 환경과 프로세스 | 실행 중 컨테이너와 상태 보고 |

운영자 머신의 Terraform이 종료돼도 EKS 제어부와 노드의 프로그램은 계속 실행된다. 빌드 머신을 꺼도 ECR의 이미지는 사라지지 않는다.

### 같은 말, 다른 의미

| 표현 | 의미 | 의미하지 않는 것 |
|---|---|---|
| `terraform apply` | Terraform이 관리하는 자원·설정 변경 반영 | 모든 Pod가 준비됐다는 보장 |
| `kubectl apply` | Kubernetes API에 객체 생성·변경 요청 | EC2를 반드시 새로 생성 |
| Pod replicas 증가 | 실행할 앱 복제본 수요 증가 | Pod 수만큼 EC2 증가 |
| Node 수 증가 | 앱을 배치할 머신 공급 증가 | 앱 replicas도 자동 증가 |

## 3. Git에서 EKS까지: 배포 흐름

기반 준비는 **환경을 처음 만들거나 바꿀 때**, 앱 배포는 **버전이 바뀔 때** 수행한다. 두 흐름은 준비된 EKS 클러스터에서 만난다.

```
[A. 기반 준비 — 환경 생성·변경 시]
 Terraform 구성 → plan 확인 후 apply → AWS API가 VPC·EKS·Node Group·IAM·ECR 생성
                                    → 클러스터 준비(노드·CNI·DNS·LB controller·배포 권한)

[B. 앱 배포 — 앱 버전 변경 시]
 1 앱 개발(코드·테스트·Dockerfile·배포 설정)
 2 Git 원격 저장소 (commit / push / merge)
 3 CI runner: 코드 checkout · 테스트
 4 Docker 빌드: 이미지 생성
 5 ECR(레지스트리): 이미지 push · digest 확보
 6 CD: 배포할 이미지 digest와 환경 설정 선택
 7 Deployment · Service · Ingress 설정을 EKS API에 적용 (kubectl apply 등)

[C. EKS 안에서]
 8 API Server: 권한·설정 검증 후 객체 반영
 9 Controllers: ReplicaSet · Pod 객체 생성
10 Scheduler: 새 Pod의 실행 노드 결정
11 노드의 kubelet / containerd: 이미지를 ECR에서 pull하여 실행
12 앱 Pod: readiness 확인 · 상태 보고
13 사용자: 도메인으로 접속 → ALB → 건강한 Pod
```

**중요한 갈림길**: Git에는 소스와 설정이 들어가고, ECR에는 빌드한 이미지가 들어간다. 배포 도구는 이미지 파일 자체를 Kubernetes API에 올리지 않고 **이미지 주소(digest)를 설정에 넣는다.** 노드의 runtime이 그 주소로 ECR에서 이미지를 가져온다.

Git에 push한다고 이 전부가 기본으로 실행되지는 않는다. 어떤 push/merge가 workflow를 시작할지, 테스트 실패 시 어디서 멈출지를 **CI/CD 설정으로 연결해야 한다.**

### 파일마다 답하는 질문

- **Dockerfile**: 이미지 안에 어떤 실행 파일을 넣고 무엇을 실행할까?
- **Deployment**: 그 이미지를 몇 개, 어떤 자원으로 실행할까?
- **Service**: 어느 Pod 집합을 안정된 이름과 포트로 찾을까?
- **Ingress**: 외부 HTTP 요청을 어느 Service에 연결할까?
- **Terraform 구성**: 이 일을 할 AWS 환경과 권한을 어떻게 만들까?

비밀번호나 장기 자격 증명은 이미지나 일반 Git 소스에 넣지 않고, 접근 제어가 있는 별도 경로로 주입한다.

### 권한 세 가지

| 누가 접근하는가? | 필요한 권한·경로 |
|---|---|
| CI가 ECR에 이미지 push | ECR 쓰기 권한 |
| CD가 EKS API에 배포 | 클러스터 인증·인가와 API endpoint 네트워크 접근 |
| 노드 runtime이 ECR에서 이미지 pull | 노드 구성에 맞는 이미지 읽기 권한과 네트워크 접근 |

### 새 버전 배포

Deployment의 이미지를 A에서 B로 바꾸면 Deployment controller가 새 ReplicaSet을 만들고, rolling update 전략에 맞춰 새 Pod를 늘리며 기존 Pod를 줄인다. **기존 컨테이너 안의 파일을 덮어쓰는 방식이 아니다.** 롤백도 이전 이미지로 돌릴 수 있지만, 이미 바뀐 DB 데이터와 스키마가 자동 복구되는 것은 아니다.

## 4. Pod·Node가 늘어나면 Terraform이 필요한가

먼저 세 숫자를 분리한다.

| 숫자 | 예시 | 읽는 주체 |
|---|---|---|
| 앱의 원하는 Pod 수 | Deployment replicas = 6 | Deployment / ReplicaSet controller |
| 노드 그룹의 목표 머신 수 | desired_size = 2 | EC2 Auto Scaling 등 그룹 관리 기능 |
| 노드 그룹의 허용 범위 | min_size = 2, max_size = 5 | 그룹 관리 기능과 Cluster Autoscaler |

`max_size = 5`는 5대까지 **늘릴 수 있다는 상한**이지 5대를 당장 만들라는 명령이 아니다.

### 상황별 판단표

| 상황 | Terraform 변경 / apply 판단 |
|---|---|
| 앱 코드만 새 버전으로 배포 | 기존 기반을 쓰면 보통 불필요 |
| 기존 노드에 **여유가 있고** Pod 수만 증가 (예: 3 → 5) | 불필요 (replicas만 변경, EC2는 그대로) |
| HPA가 부하에 따라 replicas 변경 | 매 확장마다 불필요 |
| Cluster Autoscaler가 허용 범위 안에서 노드 추가 | 수량을 CA에 위임했다면 불필요 |
| 자동 확장이 없고 노드가 부족 (Pod 6 → 8, 노드 가득 참) | Terraform이 그룹 수량을 소유한다면 HCL 변경 → plan → apply |
| max=5인데 더 많은 용량이 필요 | Terraform 소유 max라면 변경 필요 |
| Pod 삭제 후 새 Pod 생성 | 불필요 (ReplicaSet controller가 복구) |
| Ingress에 따라 ALB 생성 | controller에 맡긴 ALB마다 별도 선언 불필요 |
| PVC에 따라 EBS 동적 생성 | 동적 디스크마다 별도 선언 불필요 |

노드가 가득 차 있는데 Pod를 늘리면 Kubernetes는 원하는 상태(8개)를 기록하지만 EC2를 만들어 주지는 않는다. 배치하지 못한 Pod는 **Pending**으로 남는다.

### Terraform 실행 전의 네 질문

1. **무엇이 부족한가?** 앱 복제 수, 배치 용량, Pod IP, 권한, 이미지, 저장소 중 Events가 가리키는 것을 확인한다.
2. **그것을 조정할 프로그램이 있는가?** HPA, Cluster Autoscaler, Karpenter, AWS 그룹 기능 등.
3. **현재 정책 안에서 해결 가능한가?** 최대 수, zone, subnet, IAM, 할당량.
4. **바꿀 설정의 소유자는 누구인가?** Terraform이면 HCL·plan·apply, GitOps이면 저장소 변경, controller에 맡긴 동적 수량이면 해당 controller.

이미 노드에 배정된 Pod가 `ImagePullBackOff`라면 이미지·pull 권한·네트워크 문제다. **Pending이라는 표시만 보고 노드를 늘리거나 Terraform을 재실행하지 않는다.**

> **[보충]** 이 장의 핵심 문장을 한 줄로 줄이면 "어디에서 실행되는가"와 "누가 그 설정을 관리하는가"는 서로 다른 질문이라는 것이다(원문의 표현을 풀어 쓴 것).

## 5. 매니지드 쿠버네티스에서도 내 책임인 것

EKS 같은 매니지드 서비스가 대신해 주는 것은 주로 **컨트롤 플레인**(API 서버, etcd, 스케줄러, 컨트롤러 매니저)의 운영이다. 고가용성 구성, etcd 백업, 보안 패치와 버전 업그레이드 실행이 여기에 속한다. 나머지는 여전히 사용자의 몫이다.

| 영역 | 책임 |
|---|---|
| 컨트롤 플레인 | 클라우드가 운영 |
| 워커 노드 | 공유 책임. 클라우드는 노드 이미지·자동 복구 옵션을 제공하고, 업그레이드 시점·노드 크기와 수량·드레인은 내가 결정 |
| 클러스터 설정 | 전적으로 내 책임: RBAC, NetworkPolicy, ResourceQuota/LimitRange, Pod Security Admission, 애드온 선택과 운영 |
| 워크로드 | 전적으로 내 책임: 매니페스트, 리소스 설정, 프로브, 이미지 보안, 시크릿 관리, 관측성, 백업 |

원문은 매니지드에서도 반드시 해야 할 일로 노드 그룹 설계, 업그레이드 정책과 실행, RBAC과 클라우드 IAM 연동, NetworkPolicy(CNI 지원 여부 확인), 워크로드 아이덴티티 구성, 로깅·모니터링, 백업(etcd 백업만으로는 부족), 비용 관리를 꼽는다. **"매니지드를 쓰면 쿠버네티스를 몰라도 된다"는 것은 오해다.**

## 6. 매니페스트를 배포하는 도구 (개요)

3절의 7단계에서 매니페스트를 클러스터에 적용하는 방법은 `kubectl apply` 하나만 있는 것이 아니다. 환경(dev/prod)이 늘고 서드파티 앱을 설치하게 되면 다음 도구를 만나게 된다.

| 도구 | 방식 | 주로 쓰는 곳 |
|---|---|---|
| **Helm** | **차트**(매니페스트 템플릿 묶음)에 **값**(values)을 주입해 렌더링하고, 결과를 **릴리스**로 설치·추적한다. `helm history`/`helm rollback`으로 이력과 롤백을 관리한다 | 서드파티 앱 설치(Prometheus, cert-manager 등) |
| **Kustomize** | 유효한 YAML(base)에 환경별 패치(overlay)를 덧씌운다. `kubectl apply -k`로 내장 지원 | 우리 애플리케이션의 환경별 설정 |
| **GitOps**(Argo CD, Flux) | 클러스터 안의 에이전트가 Git 저장소를 지켜보다가 선언된 상태로 맞추고, 누가 손으로 바꾼 것(드리프트)도 되돌린다 | 배포 자동화와 감사 |

원문은 실무에서 Helm과 Kustomize를 **둘 다** 쓴다고 정리한다. GitOps는 CI가 `kubectl apply`를 하는 전통적인 push 방식과 달리 클러스터 자격 증명을 CI 시스템에 두지 않아도 된다는 보안 이점이 있다.

```bash
helm upgrade --install my-api ./chart -n prod --create-namespace -f values.prod.yaml   # 설치 또는 업그레이드
helm history my-api -n prod                                                            # 릴리스 이력
helm rollback my-api 2 -n prod                                                         # 2번 리비전으로 롤백
```

## 핵심 요약

- **Docker**는 이미지를 만들고, **Kubernetes**는 원하는 실행 상태를 유지하며, **EKS**는 AWS가 관리하는 Kubernetes 제어부이고, **Terraform**은 AWS 자원·정책을 코드로 관리한다.
- Node는 머신, Pod는 배치 단위, 컨테이너 안의 앱은 프로세스다. Pod가 늘어도 EC2가 자동으로 늘지는 않는다.
- 배포 흐름: 코드 → Git → CI(테스트) → Docker 빌드 → 레지스트리(ECR) → CD가 이미지 주소를 Deployment에 반영 → Kubernetes가 노드에서 실행.
- 이미지 자체가 아니라 **이미지 주소**가 Kubernetes API로 전달된다.
- Terraform은 Pod가 늘 때마다 실행하는 도구가 아니다. 설정의 **소유자**가 Terraform일 때만 변경·apply가 필요하다.
- 매니지드 서비스는 컨트롤 플레인 운영을 대신할 뿐, RBAC·NetworkPolicy·업그레이드 결정·관측성·백업은 여전히 사용자의 책임이다.
- 서드파티 앱은 Helm 차트로, 우리 앱의 환경별 설정은 Kustomize로 관리하는 경우가 많고, GitOps는 Git에 선언된 상태로 클러스터를 계속 맞춘다.
