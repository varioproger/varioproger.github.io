## 1장. 인프라 전체 그림 — Docker, Kubernetes, Terraform, EKS의 역할과 배포 흐름

본문: [1장. 인프라 전체 그림 — Docker, Kubernetes, Terraform, EKS의 역할과 배포 흐름](../0부-큰-그림/01-인프라-전체-그림.md)

1. Docker, Kubernetes, EKS, Terraform의 역할은?

   <details markdown="1"><summary>답 확인</summary>

   Docker는 이미지 빌드, Kubernetes는 실행 의도 저장·유지, EKS는 AWS 관리 Kubernetes 제어부, Terraform은 AWS 자원·정책을 코드로 선언.

   </details>

2. Node, Pod, 컨테이너 앱의 관계는?

   <details markdown="1"><summary>답 확인</summary>

   Node는 실행 장소(머신), Pod는 배치 단위, 컨테이너 안 앱은 실제 프로세스. 한 Pod가 여러 EC2에 나뉘지 않는다.

   </details>

3. Node YAML을 등록하면 EC2가 만들어지나?

   <details markdown="1"><summary>답 확인</summary>

   아니다. Node 객체는 머신의 주소·용량·상태 기록일 뿐이다.

   </details>

4. Kubernetes 기본 scheduler는 노드가 가득 차면?

   <details markdown="1"><summary>답 확인</summary>

   EC2를 만들지 않는다. 배치 못 한 Pod는 Pending으로 남는다.

   </details>

5. 배포 시 Kubernetes API에 전달되는 것은?

   <details markdown="1"><summary>답 확인</summary>

   이미지 파일이 아니라 이미지 주소(digest). 노드 runtime이 ECR에서 pull한다.

   </details>

6. Git과 ECR에는 각각 무엇이 들어가나?

   <details markdown="1"><summary>답 확인</summary>

   Git에는 소스와 설정, ECR에는 빌드한 이미지.

   </details>

7. 배포 흐름의 권한 3가지는?

   <details markdown="1"><summary>답 확인</summary>

   CI의 ECR 쓰기, CD의 클러스터 인증·인가와 API 접근, 노드의 ECR 이미지 읽기·네트워크 접근.

   </details>

8. 노드 그룹 max_size = 5의 의미는?

   <details markdown="1"><summary>답 확인</summary>

   5대까지 늘릴 수 있다는 상한이지 5대를 만들라는 명령이 아니다.

   </details>

9. 기존 노드에 여유가 있고 Pod만 3→5로 늘릴 때 Terraform이 필요한가?

   <details markdown="1"><summary>답 확인</summary>

   불필요. replicas만 바꾸면 되고 EC2는 그대로다.

   </details>

10. Pod Pending 시 Terraform 실행 전 4질문은?

   <details markdown="1"><summary>답 확인</summary>

   무엇이 부족한가 / 조정할 프로그램이 있는가 / 현재 정책 안에서 해결되는가 / 설정 소유자는 누구인가.

   </details>

11. 배포 롤백하면 DB도 되돌아가나?

   <details markdown="1"><summary>답 확인</summary>

   아니다. 이전 이미지로는 돌아가지만 바뀐 DB 데이터·스키마는 자동 복구되지 않는다.

   </details>

12. 매니지드 쿠버네티스에서 클라우드가 맡는 것은?

   <details markdown="1"><summary>답 확인</summary>

   컨트롤 플레인 운영(고가용성, etcd 백업, 보안 패치·업그레이드 실행). 나머지(RBAC, NetworkPolicy, 워크로드, 백업 등)는 사용자 책임.

   </details>

13. Helm과 Kustomize의 차이는?

   <details markdown="1"><summary>답 확인</summary>

   Helm은 차트에 values를 주입해 릴리스로 관리(서드파티 앱), Kustomize는 base에 환경별 overlay 패치(우리 앱 환경 설정).

   </details>

14. GitOps의 동작과 보안 이점은?

   <details markdown="1"><summary>답 확인</summary>

   클러스터 안 에이전트가 Git 선언 상태로 맞추고 드리프트를 되돌린다. CI에 클러스터 자격 증명을 두지 않아도 된다.

   </details>

15. 이미 노드에 배정된 Pod가 ImagePullBackOff다. 노드를 늘려야 하나?

   <details markdown="1"><summary>답 확인</summary>

   아니다. 배치 용량이 아니라 이미지·pull 권한·네트워크 문제다. Pending 표시만 보고 노드를 늘리거나 Terraform을 재실행하지 않는다.

   </details>

## 2장. 리눅스 OS 큰 그림

본문: [2장. 리눅스 OS 큰 그림](../1부-리눅스-기초/02-리눅스-OS-큰그림.md)

1. 유저 모드가 커널 모드로 들어가는 세 가지 경로는?

   <details markdown="1"><summary>답 확인</summary>

   시스템 콜, 인터럽트, 예외/폴트.

   </details>

2. x86-64에서 커널과 유저의 특권 수준(ring)은?

   <details markdown="1"><summary>답 확인</summary>

   커널 ring 0, 유저 ring 3.

   </details>

3. 시스템 콜이 실패하면 무엇을 반환하는가?

   <details markdown="1"><summary>답 확인</summary>

   -1을 반환하고 errno에 이유를 넣는다.

   </details>

4. EINTR의 의미와 대응은?

   <details markdown="1"><summary>답 확인</summary>

   블로킹 시스템 콜이 시그널로 중단됨. 재시도해야 한다.

   </details>

5. EMFILE은 언제 나는가?

   <details markdown="1"><summary>답 확인</summary>

   프로세스의 fd 한도(ulimit -n 기본 1024)를 초과했을 때.

   </details>

6. 태스크 상태 D의 특징은?

   <details markdown="1"><summary>답 확인</summary>

   인터럽트 불가능한 대기(주로 디스크 I/O, NFS). kill -9로도 안 죽고 load average에 포함된다.

   </details>

7. CPU는 한가한데 load average가 높다면 무엇을 의심하나?

   <details markdown="1"><summary>답 확인</summary>

   D 상태 태스크가 많은 I/O 병목.

   </details>

8. 리눅스 6.6부터 CFS를 대체한 스케줄러는?

   <details markdown="1"><summary>답 확인</summary>

   EEVDF.

   </details>

9. nice 값의 범위와 의미는?

   <details markdown="1"><summary>답 확인</summary>

   -20~+19. 낮을수록 더 많은 CPU를 받는 가중치다.

   </details>

10. --cpus=2의 cgroup 쿼터 방식은?

   <details markdown="1"><summary>답 확인</summary>

   100ms 주기마다 200ms의 CPU 시간을 주고, 다 쓰면 다음 주기까지 스로틀링한다.

   </details>

11. 컨테이너 스로틀링 횟수를 확인하는 파일은?

   <details markdown="1"><summary>답 확인</summary>

   /sys/fs/cgroup/cpu.stat (nr_throttled, throttled_usec).

   </details>

12. 컨텍스트 스위칭의 진짜 비용은?

   <details markdown="1"><summary>답 확인</summary>

   CPU 캐시 오염과 TLB 플러시 같은 간접 비용.

   </details>

13. 컨테이너 안에서 hardware_concurrency()나 nproc으로 스레드 수를 정하면 무엇이 문제인가?

   <details markdown="1"><summary>답 확인</summary>

   쿼터가 아니라 호스트 코어 수를 얻어 스레드가 쿼터보다 많아지고, 쿼터를 빨리 소진해 스로틀링(지연 스파이크)이 생긴다.

   </details>

14. 16스레드 + --cpus=2 컨테이너에서 한 주기에 일어나는 일은?

   <details markdown="1"><summary>답 확인</summary>

   12.5ms 만에 200ms 쿼터를 소진하고 나머지 87.5ms 동안 컨테이너 전체가 멈춘다.

   </details>

15. ps·top이 없는 최소 컨테이너에서 프로세스 상태와 열린 fd를 보는 법은?

   <details markdown="1"><summary>답 확인</summary>

   cat /proc/&lt;pid&gt;/status, ls -l /proc/&lt;pid&gt;/fd. 모니터링 도구도 /proc을 읽을 뿐이다.

   </details>

## 3장. 프로세스와 시그널

본문: [3장. 프로세스와 시그널](../1부-리눅스-기초/03-프로세스와-시그널.md)

1. 좀비 프로세스는 어떻게 제거하나?

   <details markdown="1"><summary>답 확인</summary>

   kill -9로는 안 된다. 부모가 wait()/waitpid()로 회수해야 하므로 부모를 고친다.

   </details>

2. 고아 프로세스는 누구에게 재입양되나?

   <details markdown="1"><summary>답 확인</summary>

   PID 1(init/systemd) 또는 subreaper.

   </details>

3. fork가 저렴한 이유는?

   <details markdown="1"><summary>답 확인</summary>

   페이지를 바로 복사하지 않고 쓰기가 일어날 때만 복사하는 Copy-on-Write 방식이라서.

   </details>

4. exec 후에도 유지되는 것은?

   <details markdown="1"><summary>답 확인</summary>

   PID와 (기본적으로) 열린 fd.

   </details>

5. 잡을 수도 무시할 수도 없는 시그널 두 개는?

   <details markdown="1"><summary>답 확인</summary>

   SIGKILL(9)과 SIGSTOP.

   </details>

6. 컨테이너 PID 1에서 핸들러 없는 SIGTERM은 어떻게 되나?

   <details markdown="1"><summary>답 확인</summary>

   커널이 무시한다. docker stop은 10초 뒤 SIGKILL로 강제 종료한다.

   </details>

7. 종료 코드 137의 의미는?

   <details markdown="1"><summary>답 확인</summary>

   128+9 = SIGKILL. OOM killer, kill -9, docker stop 타임아웃.

   </details>

8. 종료 코드 143의 의미는?

   <details markdown="1"><summary>답 확인</summary>

   128+15 = SIGTERM, 정상 종료 요청.

   </details>

9. 종료 코드 139의 의미는?

   <details markdown="1"><summary>답 확인</summary>

   128+11 = SIGSEGV, 세그폴트.

   </details>

10. docker stop과 쿠버네티스의 기본 유예 시간은?

   <details markdown="1"><summary>답 확인</summary>

   도커 10초, 쿠버네티스 30초 뒤 SIGKILL.

   </details>

11. sh -c로 감싼 CMD의 문제와 해결은?

   <details markdown="1"><summary>답 확인</summary>

   셸이 PID 1이 되어 자식에게 시그널을 전달하지 않는다. exec 또는 exec 형식 CMD를 쓴다.

   </details>

12. SIGCHLD 핸들러를 루프로 작성하는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   표준 시그널은 큐잉되지 않아 여러 자식이 죽어도 한 번만 올 수 있어서.

   </details>

13. PID 1인 C++ 서버가 docker stop마다 정확히 10초 뒤 137로 끝난다. 원인은?

   <details markdown="1"><summary>답 확인</summary>

   SIGTERM 핸들러가 없어 PID 1에서 커널이 SIGTERM을 무시하고, 10초 유예 뒤 SIGKILL로 죽었다. SigCgt가 0인지 확인한다.

   </details>

14. SIGTERM 핸들러의 표준 패턴은?

   <details markdown="1"><summary>답 확인</summary>

   핸들러는 sig_atomic_t 플래그만 세우고 즉시 반환하고, 실제 정리는 메인 루프에서 한다.

   </details>

15. SIGPIPE를 무시하지 않은 네트워크 서버에 생기는 일은?

   <details markdown="1"><summary>답 확인</summary>

   상대가 닫은 소켓에 쓰는 순간 기본 동작(종료)으로 로그 없이 사라진다.

   </details>

## 4장. 메모리·파일시스템·네트워크 기초

본문: [4장. 메모리·파일시스템·네트워크 기초](../1부-리눅스-기초/04-메모리-파일시스템-네트워크-기초.md)

1. VSZ와 RSS의 차이는?

   <details markdown="1"><summary>답 확인</summary>

   VSZ는 예약한 가상 주소 공간, RSS는 실제 물리 메모리에 올라와 있는 페이지.

   </details>

2. 리눅스에서 ENOMEM이 잘 안 나는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   기본적으로 오버커밋하기 때문. 문제는 실제로 쓸 때 OOM으로 터진다.

   </details>

3. OOM killer의 흔적은 어디서 보나?

   <details markdown="1"><summary>답 확인</summary>

   dmesg | grep -i 'killed process'. 프로그램에는 경고가 없다.

   </details>

4. 컨테이너 메모리 사용량을 보는 cgroup v2 파일은?

   <details markdown="1"><summary>답 확인</summary>

   memory.current(RSS+페이지 캐시+커널 메모리)와 한도 memory.max.

   </details>

5. free가 적을 때 봐야 할 숫자는?

   <details markdown="1"><summary>답 확인</summary>

   available. buff/cache는 필요하면 회수되는 페이지 캐시다.

   </details>

6. 파일 이름은 inode에 있는가?

   <details markdown="1"><summary>답 확인</summary>

   아니다. 이름은 디렉터리 항목이 가진다.

   </details>

7. rm 후 용량이 안 돌아오면?

   <details markdown="1"><summary>답 확인</summary>

   열고 있는 프로세스가 있다. lsof | grep deleted 또는 lsof +L1로 찾는다.

   </details>

8. 컨테이너에서 파이썬 로그가 늦게 보이는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   stdout이 파이프/파일이면 전체 버퍼링이라서. PYTHONUNBUFFERED=1.

   </details>

9. TCP 메시지 경계를 만드는 세 방법은?

   <details markdown="1"><summary>답 확인</summary>

   길이 접두어, 구분자, 고정 길이.

   </details>

10. TIME_WAIT은 어느 쪽에 얼마나 머무나?

   <details markdown="1"><summary>답 확인</summary>

   먼저 연결을 닫은 쪽에 60초.

   </details>

11. 재시작 시 Address already in use의 해결 옵션은?

   <details markdown="1"><summary>답 확인</summary>

   bind 전에 SO_REUSEADDR을 켠다.

   </details>

12. 클라이언트의 에페머럴 포트 고갈 해결책은?

   <details markdown="1"><summary>답 확인</summary>

   커넥션 풀/keep-alive.

   </details>

13. bad_alloc 처리 코드가 있는데 컨테이너가 로그 없이 137로 죽는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   오버커밋으로 할당은 성공하고, 실제 사용 시 cgroup memory.max에 닿아 OOM killer가 잡을 수 없는 SIGKILL을 보냈기 때문. dmesg와 OOMKilled로 확인한다.

   </details>

14. 컨테이너 서버가 127.0.0.1에 bind하면?

   <details markdown="1"><summary>답 확인</summary>

   컨테이너 자신의 루프백이라 호스트·다른 Pod에서 접근할 수 없다. 0.0.0.0에 listen하고 ss -tlnp로 확인한다.

   </details>

15. TIME_WAIT 소켓이 수만 개면 문제인가?

   <details markdown="1"><summary>답 확인</summary>

   그 자체는 정상. 문제는 클라이언트 쪽 에페머럴 포트(약 28,000개) 고갈이며 커넥션 풀/keep-alive로 해결한다.

   </details>

## 5장. 가상 머신 vs 컨테이너, Docker의 전체 구조

본문: [5장. 가상 머신 vs 컨테이너, Docker의 전체 구조](../2부-컨테이너와-Docker/05-가상머신-vs-컨테이너-Docker-전체-구조.md)

1. VM과 컨테이너의 격리 위치 차이는?

   <details markdown="1"><summary>답 확인</summary>

   VM은 하드웨어 가상화(각자 커널), 컨테이너는 호스트 커널을 공유하는 프로세스 격리.

   </details>

2. "컨테이너는 격리가 약하다"의 의미는?

   <details markdown="1"><summary>답 확인</summary>

   격리를 커널이 제공하므로 커널 취약점으로 탈출하면 호스트 전체가 노출된다.

   </details>

3. 샌드박스 런타임 세 가지는?

   <details markdown="1"><summary>답 확인</summary>

   gVisor(사용자 공간 시스템콜 구현), Kata Containers(경량 VM), Firecracker(마이크로 VM).

   </details>

4. docker run의 전달 순서는?

   <details markdown="1"><summary>답 확인</summary>

   CLI → dockerd → containerd → containerd-shim-runc-v2 → runc → 커널.

   </details>

5. docker CLI와 dockerd는 어떻게 통신하나?

   <details markdown="1"><summary>답 확인</summary>

   REST API over Unix 소켓 /var/run/docker.sock.

   </details>

6. dockerd와 containerd는 어떻게 통신하나?

   <details markdown="1"><summary>답 확인</summary>

   gRPC (/run/containerd/containerd.sock).

   </details>

7. 실행 중인 컨테이너의 ps에 runc가 없는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   runc는 환경 준비 후 execve()로 컨테이너 명령으로 바뀌고 사라지는 일회성 프로세스라서.

   </details>

8. shim의 역할은?

   <details markdown="1"><summary>답 확인</summary>

   컨테이너 프로세스의 부모로 남아 입출력을 유지하고 종료 코드를 회수해 containerd에 전달한다.

   </details>

9. 데몬 무중단 업그레이드를 위한 daemon.json 옵션은?

   <details markdown="1"><summary>답 확인</summary>

   "live-restore": true.

   </details>

10. 브리지·포트 매핑·볼륨·빌드 위임은 누구의 몫인가?

   <details markdown="1"><summary>답 확인</summary>

   dockerd. containerd와 runc는 이를 모른다.

   </details>

11. 쿠버네티스 노드의 컨테이너 실행 경로는?

   <details markdown="1"><summary>답 확인</summary>

   kubelet → CRI → containerd → shim/runc.

   </details>

12. Dockerfile의 CMD는 무엇을 하나?

   <details markdown="1"><summary>답 확인</summary>

   빌드 시 실행이 아니라 컨테이너 시작 시 쓸 기본 명령을 기록한다.

   </details>

13. C++ 유추: runc와 fork/execve의 공통점과 차이는?

   <details markdown="1"><summary>답 확인</summary>

   둘 다 execve()로 PID를 유지한 채 프로그램을 바꾼다. runc는 그 전에 네임스페이스·cgroup·루트 파일시스템·권한을 먼저 설정한다.

   </details>

14. 시나리오: 라이브 중 dockerd 보안 패치로 재시작해야 한다. 게임 서버 컨테이너도 죽는가?

   <details markdown="1"><summary>답 확인</summary>

   죽지 않는다. 부모는 shim이라 데몬 재시작과 분리된다. 계획된 업그레이드는 daemon.json "live-restore": true로 더 확실히.

   </details>

15. 시나리오: 컨테이너로 옮기면 모든 패킷이 containerd·runc를 거쳐 느려지는가?

   <details markdown="1"><summary>답 확인</summary>

   아니다. containerd·runc는 실행 준비 제어 경로이고, 실행된 앱은 호스트 커널과 직접 시스템 호출을 주고받는다.

   </details>

## 6장. 컨테이너 격리 — 네임스페이스

본문: [6장. 컨테이너 격리 — 네임스페이스](../2부-컨테이너와-Docker/06-컨테이너-격리-네임스페이스.md)

1. 네임스페이스는 자원을 복제하는가?

   <details markdown="1"><summary>답 확인</summary>

   아니다. 커널 전역 자원을 프로세스 그룹별로 다르게 보이게 하는 렌즈다.

   </details>

2. 리눅스 네임스페이스는 몇 가지이며 어떤 시스템 콜로 다루나?

   <details markdown="1"><summary>답 확인</summary>

   8가지. clone(), unshare(), setns().

   </details>

3. PID 네임스페이스에서 첫 프로세스의 PID는?

   <details markdown="1"><summary>답 확인</summary>

   PID 1. 호스트에서는 다른 PID로 보인다.

   </details>

4. 컨테이너마다 0.0.0.0:80을 bind할 수 있는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   네트워크 네임스페이스마다 포트 공간과 lo, veth 인터페이스가 분리되어서.

   </details>

5. UTS 네임스페이스가 격리하는 것은?

   <details markdown="1"><summary>답 확인</summary>

   호스트 이름(과 NIS 도메인).

   </details>

6. 두 프로세스가 같은 네임스페이스인지 확인하는 방법은?

   <details markdown="1"><summary>답 확인</summary>

   /proc/&lt;pid&gt;/ns/ 링크의 대괄호 번호가 같은지 비교.

   </details>

7. 셸 없는 컨테이너를 호스트 도구로 디버깅하는 명령은?

   <details markdown="1"><summary>답 확인</summary>

   nsenter --target &lt;PID&gt; --net(--mount 등) -- &lt;명령&gt;.

   </details>

8. docker run이 기본적으로 호스트와 공유하는 네임스페이스는?

   <details markdown="1"><summary>답 확인</summary>

   사용자(user)와 타임(time) 네임스페이스.

   </details>

9. --net=container:app은 쿠버네티스의 무엇과 같은 원리인가?

   <details markdown="1"><summary>답 확인</summary>

   Pod의 pause 컨테이너가 만든 네트워크 네임스페이스에 나머지 컨테이너가 합류하는 구조.

   </details>

10. 격리의 세 축과 담당은?

   <details markdown="1"><summary>답 확인</summary>

   가시성=네임스페이스, 권한=capabilities·seccomp, 자원=cgroups.

   </details>

11. capability란?

   <details markdown="1"><summary>답 확인</summary>

   root 권한을 40여 개 조각으로 나눈 단위.

   </details>

12. --privileged를 프로덕션에서 쓰면 안 되는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   모든 capability를 주어 격리를 포기하는 것과 같기 때문.

   </details>

13. C++ 유추: 컨테이너 세 개가 모두 7777을 bind해도 EADDRINUSE가 안 나는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   네트워크 네임스페이스마다 포트 공간과 lo·veth 인터페이스가 분리되어 있어서. 외부 노출은 별도(Docker 네트워크) 문제다.

   </details>

14. 시나리오: 서버 엔트리포인트가 자식 프로세스를 여럿 띄워 좀비가 쌓인다. 대처는?

   <details markdown="1"><summary>답 확인</summary>

   컨테이너 첫 프로세스는 PID 1이라 좀비 회수·시그널 책임이 있다. tini를 PID 1로 두거나 docker run --init.

   </details>

15. 시나리오: 디버깅 편의로 --privileged --pid=host 배포를 제안받았다. 대안은?

   <details markdown="1"><summary>답 확인</summary>

   격리를 포기하는 것이므로 거절하고, 호스트에서 nsenter로 들어가 디버깅하며 필요한 권한만 --cap-add로 더한다.

   </details>

## 7장. 자원 제어 — cgroups

본문: [7장. 자원 제어 — cgroups](../2부-컨테이너와-Docker/07-자원-제어-cgroups.md)

1. cgroups의 역할은?

   <details markdown="1"><summary>답 확인</summary>

   프로세스 그룹의 자원 사용량을 제한하고 측정한다.

   </details>

2. cgroups v2의 핵심 아이디어는?

   <details markdown="1"><summary>답 확인</summary>

   모든 컨트롤러가 하나의 통합 계층을 공유하고 프로세스는 단 하나의 경로에만 속한다.

   </details>

3. v2에서 하위에 켤 컨트롤러를 지정하는 파일은?

   <details markdown="1"><summary>답 확인</summary>

   상위 cgroup의 cgroup.subtree_control.

   </details>

4. cgroup 드라이버 두 가지는?

   <details markdown="1"><summary>답 확인</summary>

   cgroupfs(직접 디렉터리·파일 작성)와 systemd(scope/slice 생성 요청).

   </details>

5. 쿠버네티스에서 cgroup 드라이버의 주의점은?

   <details markdown="1"><summary>답 확인</summary>

   kubelet과 컨테이너 런타임의 드라이버가 일치해야 한다.

   </details>

6. --cpus와 --memory가 쓰는 v2 제어 파일은?

   <details markdown="1"><summary>답 확인</summary>

   cpu.max와 memory.max.

   </details>

7. --cpu-shares의 의미는?

   <details markdown="1"><summary>답 확인</summary>

   경쟁 시 상대적 가중치(cpu.weight). 절대 상한이 아니다.

   </details>

8. --pids-limit이 막는 것은?

   <details markdown="1"><summary>답 확인</summary>

   포크 폭탄처럼 프로세스를 무한히 만들어 호스트를 고갈시키는 상황(pids.max).

   </details>

9. cpu.max 값 "20000 100000"의 의미는?

   <details markdown="1"><summary>답 확인</summary>

   100ms 주기 중 20ms만 사용 = 0.2 CPU.

   </details>

10. CPU 한도와 메모리 한도 초과 시 동작 차이는?

   <details markdown="1"><summary>답 확인</summary>

   CPU는 스로틀링(느려짐), 메모리는 OOM kill(죽음).

   </details>

11. OOM으로 죽었는지 확인하는 docker 필드는?

   <details markdown="1"><summary>답 확인</summary>

   docker inspect의 State.OOMKilled.

   </details>

12. --oom-kill-disable 사용 시 주의점은?

   <details markdown="1"><summary>답 확인</summary>

   반드시 --memory 상한을 함께 지정해야 한다. 없으면 호스트 메모리 고갈 위험.

   </details>

13. C++ 유추: 메모리 한도 초과가 bad_alloc과 다른 점은?

   <details markdown="1"><summary>답 확인</summary>

   앱이 처리할 예외·NULL이 아니라 커널이 cgroup 안의 프로세스를 SIGKILL로 종료한다. 로그 없이 사라진다.

   </details>

14. 시나리오: 서버 컨테이너가 크래시 로그 없이 피크마다 재시작된다. 먼저 볼 것은?

   <details markdown="1"><summary>답 확인</summary>

   docker inspect --format '{{.State.OOMKilled}}' — memory.max 초과로 cgroup OOM killer가 SIGKILL했는지 확인.

   </details>

15. 시나리오: --cpu-shares를 낮게 줬는데 한가할 때 CPU를 다 쓴다. 왜?

   <details markdown="1"><summary>답 확인</summary>

   --cpu-shares(cpu.weight)는 경쟁 시 상대 가중치일 뿐 절대 상한이 아니다. 상한은 --cpus(cpu.max).

   </details>

## 8장. 이미지, 레이어, 레지스트리, OCI 표준

본문: [8장. 이미지, 레이어, 레지스트리, OCI 표준](../2부-컨테이너와-Docker/08-이미지-레이어-레지스트리-OCI.md)

1. 이미지 레이어란?

   <details markdown="1"><summary>답 확인</summary>

   Dockerfile 명령마다 기록되는 파일시스템 변경분(diff). 읽기 전용이다.

   </details>

2. 레이어 구조의 두 이점은?

   <details markdown="1"><summary>답 확인</summary>

   레이어 공유(디스크 절약)와 빌드 캐시.

   </details>

3. overlayfs의 lowerdir, upperdir, merged는?

   <details markdown="1"><summary>답 확인</summary>

   lowerdir=읽기 전용 이미지 레이어, upperdir=쓰기 레이어, merged=컨테이너가 보는 / 통합 뷰.

   </details>

4. 컨테이너에서 이미지 파일을 수정하면?

   <details markdown="1"><summary>답 확인</summary>

   upperdir로 복사한 뒤 사본을 수정한다(copy-on-write). 원본 레이어는 그대로.

   </details>

5. 컨테이너에서 이미지 파일을 삭제하면?

   <details markdown="1"><summary>답 확인</summary>

   upperdir에 whiteout 표시를 남길 뿐 lowerdir 파일은 지워지지 않는다.

   </details>

6. 컨테이너를 삭제하면 쓰기 레이어는?

   <details markdown="1"><summary>답 확인</summary>

   upperdir이 사라져 변경이 모두 소실된다. 데이터는 볼륨으로.

   </details>

7. pull 시 "Already exists"의 의미는?

   <details markdown="1"><summary>답 확인</summary>

   같은 다이제스트의 레이어가 이미 로컬에 있어 다운로드를 건너뛴 것.

   </details>

8. 레지스트리와 태그를 생략하면?

   <details markdown="1"><summary>답 확인</summary>

   레지스트리는 docker.io, 태그는 latest.

   </details>

9. 프로덕션에서 latest를 피하는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   latest는 그냥 기본 태그 이름이라 같은 이름으로 다른 이미지가 실행될 수 있어 재현성이 깨진다.

   </details>

10. OCI의 세 스펙은?

   <details markdown="1"><summary>답 확인</summary>

   Image Spec, Runtime Spec, Distribution Spec.

   </details>

11. 이미지 인덱스의 역할은?

   <details markdown="1"><summary>답 확인</summary>

   여러 아키텍처의 매니페스트를 가리켜 클라이언트가 자기 아키텍처 것만 받게 한다.

   </details>

12. runc가 실행하는 번들의 구성은?

   <details markdown="1"><summary>답 확인</summary>

   config.json(실행 설정) + rootfs/(루트 파일시스템).

   </details>

13. C++ 유추: overlayfs CoW와 fork()의 CoW는 무엇이 다른가?

   <details markdown="1"><summary>답 확인</summary>

   복사 단위가 페이지가 아니라 파일이라 큰 파일을 조금만 고쳐도 통째로 복사되고, 사본은 컨테이너 삭제 시 사라진다.

   </details>

14. 시나리오: 핫픽스를 myserver:latest로 재배포했는데 일부 노드가 옛 버전을 돌린다. 어떻게 배포해야 하나?

   <details markdown="1"><summary>답 확인</summary>

   latest는 약속이 아니라 기본 태그 이름이다. 명시적 태그, 더 강하게는 myserver@sha256:... 다이제스트로 고정한다.

   </details>

15. 시나리오: 컨테이너 안에 저장하던 리플레이 파일이 재배포 후 사라졌다. 왜?

   <details markdown="1"><summary>답 확인</summary>

   쓰기는 upperdir에만 기록되고 컨테이너 삭제 시 upperdir이 사라진다. 남길 데이터는 볼륨으로 뺀다.

   </details>

## 9장. Dockerfile과 이미지 빌드

본문: [9장. Dockerfile과 이미지 빌드](../2부-컨테이너와-Docker/09-Dockerfile과-이미지-빌드.md)

1. 빌드 캐시가 무효화되는 범위는?

   <details markdown="1"><summary>답 확인</summary>

   바뀐 레이어와 그 뒤의 모든 레이어.

   </details>

2. 캐시를 살리는 명령 순서의 원칙은?

   <details markdown="1"><summary>답 확인</summary>

   자주 바뀌는 것을 뒤에 둔다(의존성 파일 복사·설치 → 코드 복사).

   </details>

3. .dockerignore의 역할은?

   <details markdown="1"><summary>답 확인</summary>

   .git, node_modules, .env 등을 빌드 컨텍스트에서 빼 불필요한 전송과 해시 계산을 줄인다.

   </details>

4. 멀티스테이지에서 다른 스테이지 산출물을 가져오는 문법은?

   <details markdown="1"><summary>답 확인</summary>

   FROM ... AS &lt;이름&gt; 후 COPY --from=&lt;이름&gt;.

   </details>

5. distroless 이미지의 보안 이점은?

   <details markdown="1"><summary>답 확인</summary>

   셸조차 없어 침투 시 할 수 있는 일이 거의 없다.

   </details>

6. 멀티플랫폼 빌드 결과물의 구조는?

   <details markdown="1"><summary>답 확인</summary>

   아키텍처별 이미지들과 이를 가리키는 이미지 인덱스(매니페스트 리스트).

   </details>

7. 멀티플랫폼 빌드에서 --load를 못 쓰는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   로컬 데몬은 단일 아키텍처 이미지만 받을 수 있어서. --push해야 한다.

   </details>

8. exec format error의 의심 원인은?

   <details markdown="1"><summary>답 확인</summary>

   이미지 실행 파일의 아키텍처가 노드와 맞지 않음.

   </details>

9. 빌드용 토큰을 ARG로 넘기면 안 되는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   이미지 히스토리에 남는다. RUN --mount=type=secret을 쓴다.

   </details>

10. 푸시 전 린트와 취약점 스캔 도구는?

   <details markdown="1"><summary>답 확인</summary>

   hadolint(Dockerfile 린트), trivy(이미지 취약점 스캔).

   </details>

11. --restart 정책 값 네 가지는?

   <details markdown="1"><summary>답 확인</summary>

   no(기본), on-failure, always, unless-stopped.

   </details>

12. json-file 로그가 무한히 커지는 것을 막는 설정은?

   <details markdown="1"><summary>답 확인</summary>

   daemon.json log-opts에 max-size, max-file 지정.

   </details>

13. C++ make 증분 빌드와 Docker 빌드 캐시의 결정적 차이는?

   <details markdown="1"><summary>답 확인</summary>

   make는 의존 그래프를 따라 영향받는 것만 다시 빌드하지만, Docker는 바뀐 레이어부터 끝까지 모든 명령을 다시 실행한다.

   </details>

14. 이미지 pull은 됐는데 exec format error, pull 실패는 ImagePullBackOff — 각각 무슨 단계 문제인가?

   <details markdown="1"><summary>답 확인</summary>

   ImagePullBackOff는 가져오는 단계, exec format error는 받은 뒤 실행 파일 아키텍처가 노드와 맞지 않는 문제.

   </details>

15. Node 앱 런타임 스테이지에 dumb-init과 USER node를 쓰는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   Node가 PID 1이면 시그널 처리가 잘 안 되므로 dumb-init/tini를 ENTRYPOINT로 두고, USER node로 비루트 실행한다.

   </details>

## 10장. 컨테이너 데이터 — 볼륨, 바인드 마운트, tmpfs

본문: [10장. 컨테이너 데이터 — 볼륨, 바인드 마운트, tmpfs](../2부-컨테이너와-Docker/10-컨테이너-데이터-볼륨-바인드마운트-tmpfs.md)

1. 컨테이너를 지우면 쓰기 레이어 데이터는?

   <details markdown="1"><summary>답 확인</summary>

   함께 사라진다. 쓰기 레이어는 컨테이너 생명주기와 함께한다.

   </details>

2. named volume의 기본 저장 위치는?

   <details markdown="1"><summary>답 확인</summary>

   /var/lib/docker/volumes/&lt;이름&gt;/_data (또는 볼륨 드라이버가 관리하는 위치).

   </details>

3. named volume은 언제까지 유지되나?

   <details markdown="1"><summary>답 확인</summary>

   docker volume rm할 때까지. 컨테이너 삭제와 무관하다.

   </details>

4. DB 데이터 디렉터리에 적합한 마운트는?

   <details markdown="1"><summary>답 확인</summary>

   named volume.

   </details>

5. 소스 코드를 실시간 반영할 때 쓰는 마운트는?

   <details markdown="1"><summary>답 확인</summary>

   바인드 마운트.

   </details>

6. 바인드 마운트의 주의점은?

   <details markdown="1"><summary>답 확인</summary>

   호스트 쪽 권한·SELinux 라벨 문제를 그대로 물려받고 Docker가 생명주기에 관여하지 않는다.

   </details>

7. tmpfs 마운트의 특징과 용도는?

   <details markdown="1"><summary>답 확인</summary>

   메모리 기반이라 컨테이너가 멈추면 즉시 사라진다. 디스크에 남기면 안 되는 비밀값용.

   </details>

8. -v에서 볼륨과 바인드 마운트를 구분하는 기준은?

   <details markdown="1"><summary>답 확인</summary>

   콜론 왼쪽이 이름이면 named volume, 경로(/, ./, $(pwd))면 바인드 마운트.

   </details>

9. 마운트 종류를 확인하는 방법은?

   <details markdown="1"><summary>답 확인</summary>

   docker inspect의 Mounts 항목 Type(volume/bind).

   </details>

10. 볼륨 드라이버 플러그인이 구현하는 표준 동작은?

   <details markdown="1"><summary>답 확인</summary>

   Create, Mount, Path, Unmount, Remove.

   </details>

11. 볼륨 드라이버 사용 시 컨테이너가 아는 것은?

   <details markdown="1"><summary>답 확인</summary>

   마운트 지점뿐. 데이터 위치는 드라이버가 책임진다.

   </details>

12. -v data:/app/data로 호스트 ./data를 공유하려 했는데 빈 폴더가 보인다. 원인은?

   <details markdown="1"><summary>답 확인</summary>

   콜론 왼쪽이 경로가 아니라 이름이라 data라는 빈 named volume이 새로 만들어졌다. ./data처럼 경로로 써야 바인드 마운트다.

   </details>

13. 볼륨 데이터까지 지우는 정리 명령의 예는?

   <details markdown="1"><summary>답 확인</summary>

   docker compose down -v, docker volume prune, docker system prune --volumes.

   </details>

14. DB 컨테이너를 마운트 없이 띄웠다가 docker rm 후 재생성하면 데이터는?

   <details markdown="1"><summary>답 확인</summary>

   쓰기 레이어에 있던 데이터가 컨테이너와 함께 사라진다. named volume에 두어야 한다.

   </details>

## 11장. Docker 네트워크

본문: [11장. Docker 네트워크](../2부-컨테이너와-Docker/11-Docker-네트워크.md)

1. 기본 브리지와 사용자 정의 브리지의 핵심 차이는?

   <details markdown="1"><summary>답 확인</summary>

   사용자 정의 브리지는 이름/별칭 자동 DNS와 네트워크 간 격리를 제공한다. 기본 브리지는 없다.

   </details>

2. veth pair란?

   <details markdown="1"><summary>답 확인</summary>

   항상 쌍으로 생성되어 한쪽에 들어간 패킷이 다른 쪽으로 나오는 가상 케이블. 한쪽은 컨테이너 eth0, 다른 쪽은 호스트 브리지.

   </details>

3. 같은 브리지 컨테이너 간 통신 방식은?

   <details markdown="1"><summary>답 확인</summary>

   브리지가 MAC 주소 테이블(FDB)로 전달하는 L2 스위칭. NAT 없음.

   </details>

4. 컨테이너가 외부로 나갈 때 NAT는?

   <details markdown="1"><summary>답 확인</summary>

   출발지 IP를 호스트 IP로 바꾸는 MASQUERADE(nat 테이블 POSTROUTING).

   </details>

5. -p 8080:80의 DNAT는 어느 단계에서 일어나나?

   <details markdown="1"><summary>답 확인</summary>

   라우팅 결정 전 nat 테이블 PREROUTING(DOCKER 체인).

   </details>

6. 포트 매핑 응답 패킷의 주소는 누가 되돌리나?

   <details markdown="1"><summary>답 확인</summary>

   conntrack이 기억한 연결 정보로 자동으로 되돌린다.

   </details>

7. docker-proxy를 끄는 설정은?

   <details markdown="1"><summary>답 확인</summary>

   daemon.json의 "userland-proxy": false.

   </details>

8. Docker Engine 28부터 바뀐 미게시 포트 동작은?

   <details markdown="1"><summary>답 확인</summary>

   -p로 게시하지 않은 포트로의 인바운드 트래픽을 기본 차단한다(리눅스 iptables 기반).

   </details>

9. 개발용 DB 포트를 내 PC에서만 열려면?

   <details markdown="1"><summary>답 확인</summary>

   -p 127.0.0.1:5432:5432처럼 루프백에만 게시한다.

   </details>

10. 컨테이너의 nameserver 127.0.0.11은?

   <details markdown="1"><summary>답 확인</summary>

   dockerd가 각 컨테이너 네트워크 네임스페이스에서 가로채 응답하는 내장 DNS 서버.

   </details>

11. 내장 DNS가 외부 도메인을 처리하는 방법은?

   <details markdown="1"><summary>답 확인</summary>

   호스트에 설정된 업스트림 DNS로 포워딩한다.

   </details>

12. --link가 레거시인 이유는?

   <details markdown="1"><summary>답 확인</summary>

   IP를 /etc/hosts에 정적으로 써서 IP 변경 갱신이 어렵고 동적 서비스 그룹을 표현하지 못한다.

   </details>

13. -p 5432:5432로 게시하고 ufw로 막았는데 외부에서 접속된다. 이유는?

   <details markdown="1"><summary>답 확인</summary>

   호스트 주소 생략 시 0.0.0.0에 게시되고, 게시된 포트에는 ufw보다 Docker 규칙이 먼저 적용된다.

   </details>

14. DNS 문제 진단 체크리스트 4단계는?

   <details markdown="1"><summary>답 확인</summary>

   같은 사용자 정의 네트워크인가 → 기본 브리지에 붙지 않았나 → ndots/검색 도메인 → 앱(일부 JVM)의 DNS 캐싱.

   </details>

15. docker-proxy의 역할은?

   <details markdown="1"><summary>답 확인</summary>

   dockerd가 게시 포트를 listen하며 컨테이너로 중계하는 사용자 공간 프로세스. hairpin NAT 등 DNAT만으로 부족한 경우를 보완한다(기본 경로는 커널 DNAT).

   </details>

## 12장. Docker Compose와 컨테이너 런타임 계보

본문: [12장. Docker Compose와 컨테이너 런타임 계보](../2부-컨테이너와-Docker/12-Docker-Compose와-컨테이너-런타임-계보.md)

1. Compose 파일의 최상위 키는?

   <details markdown="1"><summary>답 확인</summary>

   services, volumes, networks, configs, secrets.

   </details>

2. Compose에서 다른 서비스에 접근할 때 쓰는 호스트 이름은?

   <details markdown="1"><summary>답 확인</summary>

   서비스 이름(예: db). localhost가 아니다.

   </details>

3. Compose에서 DB 준비 후 API를 시작하는 방법은?

   <details markdown="1"><summary>답 확인</summary>

   DB에 healthcheck를 두고 depends_on에 condition: service_healthy를 지정한다.

   </details>

4. docker compose down -v의 위험은?

   <details markdown="1"><summary>답 확인</summary>

   볼륨까지 삭제해 DB 데이터도 사라진다.

   </details>

5. Compose v1과 v2의 차이는?

   <details markdown="1"><summary>답 확인</summary>

   v1은 Python, docker-compose. v2는 Go로 재작성된 CLI 플러그인, docker compose.

   </details>

6. Moby 프로젝트란?

   <details markdown="1"><summary>답 확인</summary>

   2017년 Docker 사가 오픈소스 코드베이스를 상업 제품과 분리한 프로젝트. 컴포넌트를 조립하는 키트.

   </details>

7. containerd와 runc의 현재 소속은?

   <details markdown="1"><summary>답 확인</summary>

   containerd는 CNCF 졸업 프로젝트, runc는 OCI 산하 레퍼런스 런타임.

   </details>

8. containerd의 컨테이너와 태스크의 차이는?

   <details markdown="1"><summary>답 확인</summary>

   컨테이너는 정적 메타데이터, 태스크는 실제로 실행 중인 프로세스.

   </details>

9. Docker와 쿠버네티스가 쓰는 containerd 네임스페이스는?

   <details markdown="1"><summary>답 확인</summary>

   Docker는 moby, 쿠버네티스는 k8s.io.

   </details>

10. containerd 네임스페이스는 커널 네임스페이스와 같은가?

   <details markdown="1"><summary>답 확인</summary>

   아니다. 한 containerd 안에서 상위 시스템별 메타데이터를 구분하는 멀티테넌시 장치다.

   </details>

11. dockershim은 무엇이고 언제 제거되었나?

   <details markdown="1"><summary>답 확인</summary>

   CRI를 구현하지 않은 Docker를 위한 kubelet 내장 어댑터. 쿠버네티스 1.24에서 제거.

   </details>

12. dockershim 제거 후 Docker Engine을 쿠버네티스 런타임으로 쓰려면?

   <details markdown="1"><summary>답 확인</summary>

   cri-dockerd 어댑터가 필요하다.

   </details>

13. Compose API가 DB 호스트를 localhost로 쓰면 왜 실패하나?

   <details markdown="1"><summary>답 확인</summary>

   컨테이너 안 localhost는 자기 자신의 네트워크 네임스페이스다. 서비스 이름(예: postgres)을 써야 한다.

   </details>

14. 쿠버네티스 노드에서 docker ps에 Pod 컨테이너가 안 보이는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   kubelet은 dockerd를 거치지 않고 CRI로 containerd를 직접 쓰며, 그 컨테이너는 k8s.io 네임스페이스에 있다.

   </details>

15. 노드가 쓰는 컨테이너 런타임을 확인하는 명령은?

   <details markdown="1"><summary>답 확인</summary>

   kubectl get nodes -o wide의 CONTAINER-RUNTIME 열(예: containerd://1.7.x).

   </details>

## 13장. 왜 쿠버네티스인가 — 선언적 상태와 아키텍처

본문: [13장. 왜 쿠버네티스인가 — 선언적 상태와 아키텍처](../3부-쿠버네티스-핵심/13-왜-쿠버네티스인가.md)

1. 인프라 드리프트란?

   <details markdown="1"><summary>답 확인</summary>

   동일해야 할 시스템들이 시간이 지나며 조금씩 달라지는 현상. 재현과 복구를 불가능하게 만든다.

   </details>

2. 명령형과 선언형 방식의 차이는?

   <details markdown="1"><summary>답 확인</summary>

   명령형은 절차를 지시하고, 선언형은 결과로서의 목표 상태만 기술한다.

   </details>

3. 조정 루프의 세 단계는?

   <details markdown="1"><summary>답 확인</summary>

   관찰(observe) → 비교(diff) → 조치(act)의 무한 반복.

   </details>

4. 레벨 트리거가 엣지 트리거보다 견고한 이유는?

   <details markdown="1"><summary>답 확인</summary>

   이벤트가 아니라 현재 상태를 보므로 이벤트를 놓쳐도 다음 조정에서 바로잡힌다.

   </details>

5. spec과 status는 각각 누가 쓰나?

   <details markdown="1"><summary>답 확인</summary>

   spec은 사람이 쓰는 원하는 상태, status는 시스템이 쓰는 현재 관찰된 상태.

   </details>

6. etcd의 역할은?

   <details markdown="1"><summary>답 확인</summary>

   클러스터의 모든 오브젝트 상태를 저장하는 분산 키-값 스토어. 잃으면 클러스터를 잃는다.

   </details>

7. kube-scheduler의 역할은?

   <details markdown="1"><summary>답 확인</summary>

   노드가 정해지지 않은 Pod에 대해 리소스·어피니티·테인트 등을 고려해 노드를 정하고 spec.nodeName을 채운다.

   </details>

8. kubelet의 역할과 동작 모델은?

   <details markdown="1"><summary>답 확인</summary>

   노드 에이전트로 Pod를 실행하고 상태를 보고하며, API 서버를 watch해 자기 노드 Pod를 가져가는 pull 모델이다.

   </details>

9. 컨트롤 플레인이 잠시 죽으면 실행 중인 Pod는?

   <details markdown="1"><summary>답 확인</summary>

   계속 서비스한다. 새 배포와 스케일링만 멈춘다.

   </details>

10. Pod 생성 흐름의 세 구간과 담당은?

   <details markdown="1"><summary>답 확인</summary>

   [1~3] 요청 저장=API 서버, [4] 배치 결정=스케줄러, [5~11] 컨테이너 실행=kubelet.

   </details>

11. 매니지드 쿠버네티스가 대신 운영하는 것은?

   <details markdown="1"><summary>답 확인</summary>

   컨트롤 플레인만. 워커 노드·워크로드·네트워크 정책·RBAC·리소스 튜닝은 여전히 내 책임.

   </details>

12. 쿠버네티스 도입의 건강한 판단 기준은?

   <details markdown="1"><summary>답 확인</summary>

   "지금 사람이 손으로 하고 있는 반복 결정이 무엇인가?" 그 목록이 길고 자주 반복되면 도입한다.

   </details>

13. C++ 유추: 조정 루프는 epoll의 어느 모드와 닮았고 어디서 다른가?

   <details markdown="1"><summary>답 확인</summary>

   level-triggered처럼 "지금 상태"를 보고 판단한다. 다만 대상이 fd가 아니라 etcd의 클러스터 상태이고, 차이를 Pod 생성·삭제 같은 조치로 메운다.

   </details>

14. C++ 유추: 스케줄러는 kubelet에 명령 패킷을 보내나?

   <details markdown="1"><summary>답 확인</summary>

   아니다. API 서버에 spec.nodeName을 기록할 뿐이고 kubelet이 watch로 스스로 가져간다(pull).

   </details>

15. 시나리오: 노드 하나가 죽었는데 아무도 손대지 않았는데 인스턴스 수가 복구됐다. 누가 했나?

   <details markdown="1"><summary>답 확인</summary>

   ReplicaSet 컨트롤러의 조정 루프가 "3개여야 하는데 2개"라는 차이를 관측해 다른 노드에 새 Pod를 만들었다.

   </details>

## 14장. API 오브젝트 모델, kubectl, YAML, 라벨

1. 오브젝트 공통 구조 5가지는?

   <details markdown="1"><summary>답 확인</summary>

   apiVersion, kind, metadata, spec(원하는 상태), status(현재 상태).

2. v1alpha1 API의 실무 지침은?

   <details markdown="1"><summary>답 확인</summary>

   실험적이라 예고 없이 바뀔 수 있으므로 프로덕션 금지.

   </details>

3. ownerReferences의 역할은?

   <details markdown="1"><summary>답 확인</summary>

   소유 관계를 기록해 소유자 삭제 시 가비지 컬렉터가 소유된 오브젝트도 삭제한다.

4. finalizers가 붙은 오브젝트를 삭제하면?

   <details markdown="1"><summary>답 확인</summary>

   </details>

5. Event의 기본 보관 기간은?

   <details markdown="1"><summary>답 확인</summary>

6. 라벨과 애노테이션의 차이는?

   라벨은 선택·그룹화용(셀렉터 가능, 값 63자), 애노테이션은 부가 정보용(셀렉터 불가, 총 256KB).

7. Deployment 셀렉터에 넣을 라벨 원칙은?

   <details markdown="1"><summary>답 확인</summary>

   생성 후 변경 불가이므로 변하지 않을 최소 라벨만 넣고 version 등은 template 라벨에만 둔다.

   </details>

8. 장애 Pod를 용량 손실 없이 격리하는 방법은?

   <details markdown="1"><summary>답 확인</summary>

   Pod 라벨을 바꿔 Service에서 빼면 ReplicaSet이 새 Pod를 만든다.

   </details>

9. kubeconfig의 컨텍스트란?

   <details markdown="1"><summary>답 확인</summary>

   (클러스터, 사용자, 기본 네임스페이스)의 조합. kubectl은 current-context로 간다.

   </details>

10. create와 apply의 차이는?

   <details markdown="1"><summary>답 확인</summary>

   create는 이미 있으면 에러, apply는 없으면 만들고 있으면 차이만 반영한다.

   </details>

11. YAML에서 country: NO를 따옴표 없이 쓰면?

   <details markdown="1"><summary>답 확인</summary>

   불리언 false로 해석될 수 있다.

   </details>

12. Helm과 Kustomize의 방식 차이는?

   <details markdown="1"><summary>답 확인</summary>

   Helm은 템플릿 렌더링+릴리스 관리, Kustomize는 base에 overlay를 덧씌우는 YAML 패치.

   </details>

13. C++ 유추: ownerReferences는 unique_ptr 소유 트리와 어디서 다른가?

   <details markdown="1"><summary>답 확인</summary>

   소멸자처럼 즉시 동기 호출되지 않는다. 가비지 컬렉터가 정리하고 finalizers가 삭제를 지연시킬 수 있다.

   </details>

14. 시나리오: kubectl apply가 성공했는데 새 버전이 서비스되지 않는다. 무엇을 오해했나?

   <details markdown="1"><summary>답 확인</summary>

   apply 성공은 API 서버가 저장했다는 뜻일 뿐이다. get pods/rollout status로 확인하고 describe의 Events(예: ImagePullBackOff)를 본다.

   </details>

15. 시나리오: 개발용 명령이 라이브 클러스터에서 실행됐다. 원인과 예방은?

   <details markdown="1"><summary>답 확인</summary>

   kubectl은 항상 current-context로 간다. kube-ps1로 프롬프트에 컨텍스트를 표시하고 kubectx/kubens를 쓴다.

   </details>

## 15장. Pod — 최소 배포 단위

본문: [15장. Pod — 최소 배포 단위](../3부-쿠버네티스-핵심/15-Pod.md)

1. Pod가 공유하는 리눅스 네임스페이스는?

   <details markdown="1"><summary>답 확인</summary>

   NET, IPC, UTS. MNT와 PID는 각자 갖는다(PID는 기본값).

   </details>

2. 같은 Pod의 두 컨테이너가 모두 8080을 열면?

   <details markdown="1"><summary>답 확인</summary>

   IP와 포트 공간을 공유하므로 뒤에 시작한 쪽이 Address already in use로 실패한다.

   </details>

3. 같은 Pod 컨테이너끼리 파일을 공유하려면?

   <details markdown="1"><summary>답 확인</summary>

   Pod 수준에 볼륨을 정의하고 각 컨테이너에 명시적으로 마운트한다.

   </details>

4. pause 컨테이너의 역할은?

   <details markdown="1"><summary>답 확인</summary>

   NET·IPC·UTS 네임스페이스를 소유해 메인 컨테이너가 재시작해도 Pod IP를 유지한다.

   </details>

5. Pod가 일회용이라 필요한 세 가지는?

   <details markdown="1"><summary>답 확인</summary>

   IP 대신 Service, 로컬 파일 대신 볼륨, 직접 생성 대신 컨트롤러.

   </details>

6. latest 태그 이미지의 imagePullPolicy 기본값은?

   <details markdown="1"><summary>답 확인</summary>

   Always. 명시적 태그면 IfNotPresent.

   </details>

7. CrashLoopBackOff 원인을 볼 로그 명령은?

   <details markdown="1"><summary>답 확인</summary>

   kubectl logs &lt;pod&gt; --previous (직전에 죽은 컨테이너의 로그).

   </details>

8. 셸 없는 이미지를 디버깅하는 표준 방법은?

   <details markdown="1"><summary>답 확인</summary>

   kubectl debug -it &lt;pod&gt; --image=... --target=&lt;컨테이너&gt;로 임시 디버그 컨테이너를 붙인다.

   </details>

9. Init 컨테이너의 실행 방식은?

   <details markdown="1"><summary>답 확인</summary>

   메인보다 먼저, 정의 순서대로 하나씩, 성공적으로 완료될 때까지 실행된다.

   </details>

10. 정식 사이드카를 만드는 설정은?

   <details markdown="1"><summary>답 확인</summary>

   initContainers 항목에 restartPolicy: Always를 준다.

   </details>

11. 앰배서더 패턴이란?

   <details markdown="1"><summary>답 확인</summary>

   메인이 외부 서비스로 나갈 때 복잡성을 감추는 프록시. 앱은 localhost만 본다(예: Cloud SQL Proxy).

   </details>

12. 멀티 컨테이너 Pod로 묶을지 판단 기준은?

   <details markdown="1"><summary>답 확인</summary>

   항상 1:1로, 같은 개수만큼, 함께 스케일되어야 하는가.

   </details>

13. C++ 유추: 같은 Pod의 컨테이너는 같은 머신의 두 프로세스와 어디서 다른가?

   <details markdown="1"><summary>답 확인</summary>

   네트워크(localhost·포트)는 공유하지만 파일 시스템과 프로세스 목록은 분리되어, 파일은 볼륨으로만 나눌 수 있다.

   </details>

14. 시나리오: 재배포 후 다른 서버가 하드코딩한 Pod IP로 접속이 실패한다. 왜?

   <details markdown="1"><summary>답 확인</summary>

   Pod는 일회용이라 교체되면 IP가 바뀐다. Pod IP 대신 Service로 접근해야 한다.

   </details>

15. 시나리오: 매칭 서버가 Redis 준비 전에 떠서 크래시를 반복한다. Pod 수준 해결책은?

   <details markdown="1"><summary>답 확인</summary>

   Init 컨테이너로 의존성 대기(until nc -z ...)를 건다. 반드시 완료 후 종료해야 한다.

   </details>

## 16장. Pod 생명주기와 헬스 체크

본문: [16장. Pod 생명주기와 헬스 체크](../3부-쿠버네티스-핵심/16-Pod-생명주기와-헬스체크.md)

1. 0/1 Running Pod는 Service 트래픽을 받나?

   <details markdown="1"><summary>답 확인</summary>

   받지 않는다. Ready=True인 Pod만 엔드포인트에 등록된다.

   </details>

2. exitCode 137의 두 가지 원인은?

   <details markdown="1"><summary>답 확인</summary>

   OOMKilled(메모리 초과) 또는 grace period 초과로 인한 SIGKILL.

   </details>

3. liveness와 readiness 실패 시 동작 차이는?

   <details markdown="1"><summary>답 확인</summary>

   liveness는 컨테이너 재시작, readiness는 재시작 없이 엔드포인트에서 제거.

   </details>

4. liveness에 DB 연결 체크를 넣으면?

   <details markdown="1"><summary>답 확인</summary>

   DB가 느려질 때 모든 Pod가 동시에 재시작하는 장애 증폭이 생긴다. 의존성은 readiness에 둔다.

   </details>

5. 프로브 최대 감지 시간 공식은?

   <details markdown="1"><summary>답 확인</summary>

   initialDelaySeconds + (periodSeconds x failureThreshold) + timeoutSeconds.

   </details>

6. timeoutSeconds 기본값과 권장값은?

   <details markdown="1"><summary>답 확인</summary>

   기본 1초는 너무 짧아 연쇄 붕괴를 부른다. 최소 3~5초.

   </details>

7. startupProbe의 역할은?

   <details markdown="1"><summary>답 확인</summary>

   성공할 때까지 liveness/readiness를 보류해 느리게 뜨는 앱을 보호한다(시작은 관대, 운영은 엄격).

   </details>

8. CrashLoopBackOff의 정체는?

   <details markdown="1"><summary>답 확인</summary>

   반복 크래시에 대한 지수 백오프(10초→최대 300초) 대기 상태로, 원인이 아니라 증상이다.

   </details>

9. restartPolicy 재시작은 무엇을 다시 시작하나?

   <details markdown="1"><summary>답 확인</summary>

   같은 노드에서 컨테이너만. IP와 emptyDir는 유지되고 restartCount만 증가한다.

   </details>

10. 배포 중 502의 근본 원인은?

   <details markdown="1"><summary>답 확인</summary>

   preStop 실행과 엔드포인트 제거가 병렬이라, 규칙 갱신 전 죽은 Pod로 트래픽이 간다.

   </details>

11. sh -c "python app.py"의 문제는?

   <details markdown="1"><summary>답 확인</summary>

   셸이 PID 1이 되어 SIGTERM을 앱에 전달하지 않는다. exec을 쓰거나 셸 없이 실행한다.

   </details>

12. terminationGracePeriodSeconds에 preStop 시간이 포함되나?

   <details markdown="1"><summary>답 확인</summary>

   포함된다. 기본 30초.

   </details>

13. C++ 유추: SIGTERM 받자마자 exit()하던 서버가 쿠버네티스에서 502를 만드는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   엔드포인트 제거·노드 규칙 갱신이 SIGTERM과 병렬이라, 즉시 죽으면 아직 규칙이 남은 노드에서 트래픽이 죽은 Pod로 간다.

   </details>

14. 시나리오: 데이터 로딩에 2분 걸리는 서버가 liveness에 걸려 계속 재시작된다. 해결은?

   <details markdown="1"><summary>답 확인</summary>

   initialDelaySeconds를 늘리지 말고 startupProbe(예: 10초 x 30)를 둔다. 성공 전까지 liveness가 보류된다.

   </details>

15. 시나리오: Pod 삭제가 매번 정확히 30초 걸리고 SIGTERM 핸들러가 안 돈다. 원인은?

   <details markdown="1"><summary>답 확인</summary>

   sh -c로 띄워 셸이 PID 1이 되어 시그널을 전달하지 않았다. exec 또는 셸 없이 실행한다.

   </details>

## 17장. ConfigMap과 Secret

본문: [17장. ConfigMap과 Secret](../3부-쿠버네티스-핵심/17-ConfigMap과-Secret.md)

1. 설정을 이미지에 넣으면 안 되는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   환경별로 다른 이미지가 되어 스테이징에서 테스트한 이미지와 프로덕션 이미지가 달라진다.

   </details>

2. ConfigMap data 값에 100이나 true를 따옴표 없이 쓰면?

   <details markdown="1"><summary>답 확인</summary>

   에러다. data 값은 모두 문자열이어야 한다.

   </details>

3. ConfigMap을 수정하면 실행 중 Pod의 환경변수는?

   <details markdown="1"><summary>답 확인</summary>

   절대 갱신되지 않는다. Pod를 재생성해야 한다.

   </details>

4. 볼륨으로 마운트한 ConfigMap은 갱신되나?

   <details markdown="1"><summary>답 확인</summary>

   된다. ..data 심볼릭 링크를 원자적으로 교체하며 최대 2분 정도 지연된다.

   </details>

5. subPath로 마운트한 ConfigMap 파일은 갱신되나?

   <details markdown="1"><summary>답 확인</summary>

   되지 않는다.

   </details>

6. envFrom에서 환경변수로 유효하지 않은 키는?

   <details markdown="1"><summary>답 확인</summary>

   조용히 건너뛴다.

   </details>

7. base64가 보호 수단이 아닌 이유는?

   <details markdown="1"><summary>답 확인</summary>

   인코딩일 뿐이라 누구나 base64 -d로 디코딩할 수 있다.

   </details>

8. Secret이 ConfigMap보다 실제로 나은 두 가지는?

   <details markdown="1"><summary>답 확인</summary>

   노드에서 tmpfs(메모리)에 저장되고, RBAC로 권한을 분리할 수 있다.

   </details>

9. 시크릿을 환경변수보다 볼륨으로 주입하는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   환경변수는 에러 리포팅·자식 프로세스 상속·/proc environ 등 유출 경로가 많고, 볼륨은 파일 권한 제어와 갱신이 된다.

   </details>

10. etcd 저장 시 암호화의 프로덕션 권장 프로바이더는?

   <details markdown="1"><summary>답 확인</summary>

   kms v2. 기존 Secret은 다시 써야(replace) 암호화된다.

   </details>

11. 설정 변경 시 롤아웃을 자동 유도하는 권장 방법은?

   <details markdown="1"><summary>답 확인</summary>

   ConfigMap 해시를 Pod 템플릿 애노테이션에 넣는 체크섬 애노테이션.

   </details>

12. immutable ConfigMap + 버전 이름의 장점은?

   <details markdown="1"><summary>답 확인</summary>

   실수로 설정을 바꾸는 사고 방지, kubelet 감시 불필요로 API 서버 부하 감소, 쉬운 롤백.

   </details>

13. C++ 유추: getenv()처럼 env로 주입한 ConfigMap 값을 바꾸려면?

   <details markdown="1"><summary>답 확인</summary>

   시작 시 고정되므로 Pod를 재생성해야 한다(rollout restart, 체크섬 애노테이션 등). ConfigMap 수정만으로는 반영되지 않는다.

   </details>

14. 시나리오: subPath로 넣은 nginx.conf가 ConfigMap 수정 후에도 그대로인 이유는?

   <details markdown="1"><summary>답 확인</summary>

   subPath 마운트는 자동 갱신되지 않는다. 디렉터리 마운트나 롤아웃 유도를 쓴다.

   </details>

15. 시나리오: 크래시 리포트에 DB 비밀번호가 실려 나갔다. 무엇을 바꾸나?

   <details markdown="1"><summary>답 확인</summary>

   환경변수 주입을 secret 볼륨(defaultMode 0400)으로 바꾼다. 환경변수는 에러 리포팅·자식 프로세스 상속·/proc environ으로 샌다.

   </details>

## 18장. 워크로드 컨트롤러 — Deployment, StatefulSet, DaemonSet, Job

본문: [18장. 워크로드 컨트롤러 — Deployment, StatefulSet, DaemonSet, Job](../3부-쿠버네티스-핵심/18-워크로드-컨트롤러.md)

1. ReplicaSet 템플릿 이미지를 바꾸면 기존 Pod는?

   <details markdown="1"><summary>답 확인</summary>

   그대로다. 새로 만들어지는 Pod부터 적용된다.

   </details>

2. ReplicaSet이 Pod 소유권을 판단하는 기준은?

   <details markdown="1"><summary>답 확인</summary>

   셀렉터. 자기가 만들지 않은 Pod도 셀렉터에 맞으면 자기 것으로 간주한다.

   </details>

3. Recreate 전략은 언제 쓰나?

   <details markdown="1"><summary>답 확인</summary>

   두 버전이 동시에 존재하면 안 될 때(DB 스키마 호환성, 파일 락 등). 다운타임이 생긴다.

   </details>

4. replicas 4, 25%/25%일 때 maxSurge와 maxUnavailable은?

   <details markdown="1"><summary>답 확인</summary>

   maxSurge는 올림해 1(최대 5개), maxUnavailable은 내림해 1(최소 3개 가용).

   </details>

5. 프로덕션 권장 롤링 업데이트 설정과 함정은?

   <details markdown="1"><summary>답 확인</summary>

   maxSurge 1, maxUnavailable 0. 클러스터 여유가 없으면 새 Pod가 Pending이라 롤아웃이 멈춘다.

   </details>

6. Deployment 롤백이 빠른 이유는?

   <details markdown="1"><summary>답 확인</summary>

   이전 ReplicaSet이 replicas 0으로 남아 있어 다시 스케일 업만 하면 된다.

   </details>

7. Deployment 롤백이 되돌리지 못하는 것은?

   <details markdown="1"><summary>답 확인</summary>

   DB 스키마 마이그레이션, ConfigMap/Secret 내용, 외부 부수 효과. Pod 템플릿만 되돌린다.

   </details>

8. PDB의 minAvailable을 replicas와 같게 두면?

   <details markdown="1"><summary>답 확인</summary>

   하나도 축출할 수 없어 drain이 영원히 멈춘다.

   </details>

9. StatefulSet의 세 가지 보장은?

   <details markdown="1"><summary>답 확인</summary>

   안정적 네트워크 ID, Pod별 안정적 스토리지(PVC), 순서 보장.

   </details>

10. StatefulSet을 스케일 다운하면 PVC는?

   <details markdown="1"><summary>답 확인</summary>

   삭제되지 않는다. 다시 스케일 업하면 같은 PVC에 재연결된다.

   </details>

11. Job에서 restartPolicy Always를 못 쓰는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   Job은 끝나야 하는데 Always면 영원히 끝나지 않는다. OnFailure 또는 Never만 가능.

   </details>

12. CronJob에 timeZone이 없으면?

   <details markdown="1"><summary>답 확인</summary>

   컨트롤러 매니저 시간대(보통 UTC)를 따라 의도와 다른 시각에 실행된다.

   </details>

13. C++ 유추: watchdog 스크립트와 ReplicaSet의 결정적 차이는?

   <details markdown="1"><summary>답 확인</summary>

   ReplicaSet은 PID가 아니라 라벨 셀렉터로 소유권을 판단해, 셀렉터가 겹치면 남의 Pod까지 지우려 든다.

   </details>

14. 시나리오: 컬럼 삭제 마이그레이션이 든 v2를 rollout undo했더니 v1이 에러를 낸다. 왜?

   <details markdown="1"><summary>답 확인</summary>

   롤백은 Pod 템플릿만 되돌리고 DB 스키마는 그대로다. 마이그레이션은 하위 호환되게 설계한다.

   </details>

15. 시나리오: maxSurge 1, maxUnavailable 0 배포에서 새 Pod가 Pending이고 롤아웃이 안 끝난다. 원인은?

   <details markdown="1"><summary>답 확인</summary>

   클러스터에 새 Pod 한 개분 여유가 없다. 기존 Pod는 유지되어 서비스는 계속되지만 롤아웃은 멈춘다.

   </details>

## 19장. 리소스 요청·제한과 스케줄링 기초

본문: [19장. 리소스 요청·제한과 스케줄링 기초](../3부-쿠버네티스-핵심/19-리소스-요청-제한과-스케줄링-기초.md)

1. requests와 limits는 각각 누가 쓰나?

   <details markdown="1"><summary>답 확인</summary>

   requests는 스케줄러(배치 결정), limits는 커널 cgroup(실행 내내 강제).

   </details>

2. 노드 사용률 5%인데 Pod가 Pending인 이유는?

   <details markdown="1"><summary>답 확인</summary>

   스케줄러는 실제 사용량이 아니라 requests 합만 보므로 requests 여유가 없으면 배치하지 않는다.

   </details>

3. 1000Mi와 1000M의 차이는?

   <details markdown="1"><summary>답 확인</summary>

   1000Mi는 약 1.05GB(2진), 1000M은 정확히 1GB. 항상 Mi/Gi를 쓴다.

   </details>

4. Guaranteed QoS의 조건은?

   <details markdown="1"><summary>답 확인</summary>

   모든 컨테이너에 requests와 limits가 있고 CPU·메모리 모두 requests == limits.

   </details>

5. 사이드카 하나에 resources가 없으면 Pod의 QoS는?

   <details markdown="1"><summary>답 확인</summary>

   Pod 전체가 Burstable이 된다.

   </details>

6. CPU와 메모리가 limits를 초과하면?

   <details markdown="1"><summary>답 확인</summary>

   CPU는 스로틀링(대기), 메모리는 OOMKilled(exitCode 137).

   </details>

7. limits.cpu 500m의 실제 의미는?

   <details markdown="1"><summary>답 확인</summary>

   매 100ms 주기마다 50ms만 CPU를 쓸 수 있다(평균이 아니라 매 주기).

   </details>

8. 노드 압박 시 축출 순서는?

   <details markdown="1"><summary>답 확인</summary>

   QoS(BestEffort → Burstable → Guaranteed) → requests 초과량 → Pod Priority.

   </details>

9. CPU와 메모리 오버커밋의 안전성은?

   <details markdown="1"><summary>답 확인</summary>

   CPU는 스로틀링뿐이라 안전, 메모리는 노드 OOM 위험이 있어 1.2~1.5배 이내.

   </details>

10. 스케줄러의 노드 선택 단계는?

   <details markdown="1"><summary>답 확인</summary>

   필터링 → 스코어링 → 바인딩(spec.nodeName 설정).

   </details>

11. 톨러레이션만 주면 전용 노드가 되지 않는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   톨러레이션은 허가이지 지시가 아니다. 노드 어피니티로 유도까지 해야 한다.

   </details>

12. 노드 장애 시 Pod가 5분 뒤 옮겨지는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   not-ready/unreachable 테인트에 tolerationSeconds 300 톨러레이션이 자동 추가되기 때문이다.

   </details>

13. C++ 유추: bad_alloc 처리를 다 해 뒀는데 로그 없이 137로 죽는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   cgroup 메모리 한도를 넘으면 할당 실패를 돌려주는 대신 커널이 프로세스를 죽인다(OOMKilled).

   </details>

14. 시나리오: 평균 CPU는 낮은데 limits.cpu 500m 멀티스레드 서버가 피크에 100ms 이상 튄다. 확인할 것은?

   <details markdown="1"><summary>답 확인</summary>

   cpu.stat의 nr_throttled / nr_periods. 높으면 limits를 올리거나, 지연 민감 서비스는 CPU limits를 없애거나 넉넉히 둔다.

   </details>

15. 시나리오: 메인 컨테이너는 requests==limits인데 Pod가 먼저 축출된다. 왜?

   <details markdown="1"><summary>답 확인</summary>

   resources 없는 사이드카 때문에 Pod 전체가 Burstable이 됐다. 모든 컨테이너가 조건을 만족해야 Guaranteed다.

   </details>

## 20장. 네임스페이스 — 역할, 한계, ResourceQuota, LimitRange

본문: [20장. 네임스페이스 — 역할, 한계, ResourceQuota, LimitRange](../3부-쿠버네티스-핵심/20-네임스페이스.md)

1. 네임스페이스가 제공하는 네 가지는?

   <details markdown="1"><summary>답 확인</summary>

   이름 스코프, DNS 스코프, RBAC 경계, 리소스 쿼터 단위.

   </details>

2. 네임스페이스는 보안 경계인가?

   <details markdown="1"><summary>답 확인</summary>

   아니다. 네트워크는 기본적으로 열려 있고 노드·커널·컨트롤 플레인을 공유한다.

   </details>

3. 다른 네임스페이스 Pod 간 통신을 막으려면?

   <details markdown="1"><summary>답 확인</summary>

   NetworkPolicy가 필요하다.

   </details>

4. kube-node-lease 네임스페이스의 용도는?

   <details markdown="1"><summary>답 확인</summary>

   노드 하트비트용 Lease 오브젝트를 둔다.

   </details>

5. 네임스페이스를 삭제하면?

   <details markdown="1"><summary>답 확인</summary>

   안의 모든 리소스가 삭제되며 되돌릴 수 없다. reclaimPolicy Delete면 볼륨 데이터까지 사라진다.

   </details>

6. services.loadbalancers 쿼터를 거는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   LoadBalancer Service 하나당 클라우드 LB가 생겨 요금이 부과되므로 비용 통제용이다.

   </details>

7. 컴퓨트 쿼터가 있는데 resources 없는 Pod를 만들면?

   <details markdown="1"><summary>답 확인</summary>

   생성이 거부된다(failed quota: must specify ...). LimitRange 기본값으로 해결한다.

   </details>

8. 쿼터 초과 시 Deployment의 동작은?

   <details markdown="1"><summary>답 확인</summary>

   새 Pod 생성이 거부되고 ReplicaSet이 계속 재시도하며 FailedCreate 이벤트를 남긴다.

   </details>

9. ResourceQuota와 LimitRange의 차이는?

   <details markdown="1"><summary>답 확인</summary>

   ResourceQuota는 네임스페이스 총량, LimitRange는 개별 컨테이너/Pod/PVC의 기본값·범위.

   </details>

10. LimitRange maxLimitRequestRatio의 목적은?

   <details markdown="1"><summary>답 확인</summary>

   requests 대비 limits 비율을 제한해 과도한 오버커밋으로 인한 노드 과부하를 막는다.

   </details>

11. 하드 멀티테넌시 판단 기준과 구현은?

   <details markdown="1"><summary>답 확인</summary>

   테넌트가 임의 코드를 실행하면 하드. 별도 클러스터 또는 gVisor/Kata 같은 샌드박스 런타임.

   </details>

12. dev/staging/prod 환경은 보통 무엇으로 나누나?

   <details markdown="1"><summary>답 확인</summary>

   클러스터. 컨트롤 플레인 장애 전파를 막고 업그레이드를 먼저 테스트하기 위해서다.

   </details>

13. C++ 유추: 쿠버네티스 네임스페이스는 C++ namespace와 무엇이 같고 다른가?

   <details markdown="1"><summary>답 확인</summary>

   둘 다 이름 충돌만 막을 뿐 접근을 막지 않는다. 다만 쿠버네티스 네임스페이스는 RBAC·쿼터 단위이고 삭제하면 안의 리소스가 실제로 사라진다.

   </details>

14. 시나리오: replicas 15로 올렸는데 10개에서 멈추고 Deployment엔 에러가 없다. 어디를 보나?

   <details markdown="1"><summary>답 확인</summary>

   kubectl describe replicaset의 FailedCreate(exceeded quota) 이벤트와 describe resourcequota의 Used/Hard.

   </details>

15. 시나리오: 유저 업로드 스크립트를 유저별 네임스페이스로만 격리해 실행해도 되나?

   <details markdown="1"><summary>답 확인</summary>

   안 된다. 임의 코드 실행은 하드 멀티테넌시라 커널 공유가 위험하므로 클러스터 분리나 gVisor/Kata 샌드박스 런타임이 필요하다.

   </details>

## 21장. 쿠버네티스 네트워크 모델과 Service

본문: [21장. 쿠버네티스 네트워크 모델과 Service](../4부-노출-데이터-운영/21-네트워크-모델과-Service.md)

1. 쿠버네티스 네트워크 모델 이름과 핵심 규칙은?

   <details markdown="1"><summary>답 확인</summary>

   IP-per-Pod. 모든 Pod는 고유 IP를 갖고 NAT 없이 다른 Pod·노드와 통신하며, 자기 IP와 남이 보는 IP가 같다.

   </details>

2. ClusterIP로 ping이 응답하지 않는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   어떤 인터페이스에도 붙지 않은 가상 IP라서 응답할 장비가 없다. 노드의 iptables/IPVS가 Pod IP로 바꿔칠 뿐이다.

   </details>

3. 클러스터의 IP 대역 3가지는?

   <details markdown="1"><summary>답 확인</summary>

   노드 CIDR(실재), Pod CIDR(CNI가 라우팅), Service CIDR(가상 IP).

   </details>

4. Service 타입의 포함 관계는?

   <details markdown="1"><summary>답 확인</summary>

   LoadBalancer ⊃ NodePort ⊃ ClusterIP. ExternalName은 DNS CNAME만 만든다(프록시 없음).

   </details>

5. NodePort 포트 범위와 프로덕션에 부적합한 이유는?

   <details markdown="1"><summary>답 확인</summary>

   30000~32767. 80/443을 못 쓰고 클라이언트가 노드 IP를 알아야 하며 앞단 LB가 따로 필요하다.

   </details>

6. externalTrafficPolicy Cluster vs Local?

   <details markdown="1"><summary>답 확인</summary>

   Cluster는 균등 분산이지만 SNAT로 클라이언트 IP 소실. Local은 IP 보존·홉 없음이지만 Pod 없는 노드는 응답 안 해 부하 불균등.

   </details>

7. LoadBalancer EXTERNAL-IP가 pending인 이유는?

   <details markdown="1"><summary>답 확인</summary>

   cloud-controller-manager가 없거나 권한 부족. 베어메탈·kind는 기본 pending이며 MetalLB 같은 구현이 필요하다.

   </details>

8. LoadBalancer Service를 많이 만들면 생기는 문제는?

   <details markdown="1"><summary>답 확인</summary>

   Service마다 클라우드 LB가 하나씩 생겨 비용이 늘어난다. 그래서 Ingress로 진입점을 모은다.

   </details>

9. EndpointSlice에서 트래픽을 받는 엔드포인트 조건은?

   <details markdown="1"><summary>답 확인</summary>

   conditions.ready: true. readiness 실패 중이면 false로 트래픽에서 빠진다.

   </details>

10. EndpointSlice가 Endpoints보다 나은 점은?

   <details markdown="1"><summary>답 확인</summary>

   100개 단위로 쪼개 변경된 슬라이스만 kube-proxy로 보내 대규모 클러스터 부하를 줄인다.

   </details>

11. 헤드리스 서비스란?

   <details markdown="1"><summary>답 확인</summary>

   clusterIP: None. 가상 IP 없이 DNS가 모든 Pod IP 목록을 반환하고 클라이언트가 직접 로드밸런싱한다.

   </details>

12. kube-proxy가 죽으면 기존 연결은?

   <details markdown="1"><summary>답 확인</summary>

   유지된다. kube-proxy는 규칙만 만들고 실제 변환은 커널이 하므로, 새 Service 변경만 반영되지 않는다.

   </details>

13. iptables vs IPVS 모드?

   <details markdown="1"><summary>답 확인</summary>

   iptables는 선형 O(n)·랜덤, IPVS는 해시 O(1)·rr/lc 등 알고리즘 선택. Service 1,000개 이상이면 IPVS 고려.

   </details>

14. 게임룸 서버 Pod IP를 설정 파일에 하드코딩했더니 롤링 업데이트 뒤 접속이 실패한다. 왜이고 어떻게 고치나?

   <details markdown="1"><summary>답 확인</summary>

   Pod IP는 일회용이라 교체 시 바뀐다. Service를 두고 ClusterIP(또는 Service 이름)로 접속한다.

   </details>

15. C++ 중계 서버와 kube-proxy의 결정적 차이는?

   <details markdown="1"><summary>답 확인</summary>

   kube-proxy는 recv/send로 중계하지 않고 iptables/IPVS 규칙만 만든다. 패킷은 커널이 DNAT 처리한다.

   </details>

## 22장. DNS와 서비스 디스커버리

본문: [22장. DNS와 서비스 디스커버리](../4부-노출-데이터-운영/22-DNS와-서비스-디스커버리.md)

1. 서비스 디스커버리에서 DNS가 환경변수보다 나은 이유는?

   <details markdown="1"><summary>답 확인</summary>

   DNS는 요청 시점에 해석된다. 환경변수는 Pod 시작 시점의 스냅샷이라 나중에 만든 Service는 빠진다.

   </details>

2. 클러스터 DNS 구현과 그 Service 이름은?

   <details markdown="1"><summary>답 확인</summary>

   CoreDNS. kube-system의 kube-dns Service(옛 구현 이름이 남은 것)이며 그 IP가 모든 Pod resolv.conf에 들어간다.

   </details>

3. Service의 FQDN 형식은?

   <details markdown="1"><summary>답 확인</summary>

   &lt;service&gt;.&lt;namespace&gt;.svc.cluster.local

   </details>

4. 일반·헤드리스·ExternalName Service의 DNS 응답은?

   <details markdown="1"><summary>답 확인</summary>

   일반은 ClusterIP 하나(A/AAAA), 헤드리스는 모든 Ready Pod IP, ExternalName은 CNAME.

   </details>

5. StatefulSet Pod의 DNS 이름 형식은?

   <details markdown="1"><summary>답 확인</summary>

   &lt;pod-name&gt;.&lt;headless-service&gt;.&lt;namespace&gt;.svc.cluster.local. Pod가 재생성돼도 이름은 유지된다.

   </details>

6. CoreDNS kubernetes 플러그인과 forward 플러그인의 역할은?

   <details markdown="1"><summary>답 확인</summary>

   kubernetes는 API를 watch해 Service/Pod 레코드 응답, forward는 처리 못 한 질의를 상위 DNS(노드 resolv.conf)로 전달.

   </details>

7. ndots 설정의 의미와 쿠버네티스 기본값은?

   <details markdown="1"><summary>답 확인</summary>

   이름의 점이 이 개수 미만이면 search 도메인을 먼저 붙여 본다. 기본값은 5.

   </details>

8. ndots:5에서 google.com 1회 조회 시 쿼리 수는?

   <details markdown="1"><summary>답 확인</summary>

   search 3번 실패 후 4번째 성공, A/AAAA 각각이라 최대 8개.

   </details>

9. ndots 함정의 가장 간단한 해결책은?

   <details markdown="1"><summary>답 확인</summary>

   FQDN 끝에 마침표를 붙인다(예: api.example.com.). search 도메인을 건너뛴다.

   </details>

10. hostNetwork: true Pod가 Service 이름을 해석하려면?

   <details markdown="1"><summary>답 확인</summary>

   dnsPolicy: ClusterFirstWithHostNet을 명시한다.

   </details>

11. dnsPolicy Default의 실제 의미는?

   <details markdown="1"><summary>답 확인</summary>

   노드의 /etc/resolv.conf를 그대로 사용해 클러스터 DNS를 안 쓴다. 기본값은 ClusterFirst다.

   </details>

12. DNS 조회가 정확히 5초 걸리거나 간헐 SERVFAIL이면?

   <details markdown="1"><summary>답 확인</summary>

   conntrack 경합에 의한 UDP 패킷 유실을 의심하고 NodeLocal DNSCache를 검토한다.

   </details>

13. default-deny NetworkPolicy 후 모든 게 안 되는 흔한 원인은?

   <details markdown="1"><summary>답 확인</summary>

   DNS(53번 포트) 예외를 빠뜨려 DNS 질의도 차단된 것.

   </details>

14. 외부 결제 API 호출이 쿠버네티스에서만 느리고 CoreDNS CPU가 높다. 원인과 가장 간단한 해결은?

   <details markdown="1"><summary>답 확인</summary>

   ndots:5 때문에 search 접미사 3개를 먼저 붙여 최대 8쿼리. 설정값 끝에 마침표를 붙인 FQDN을 쓴다.

   </details>

15. game 네임스페이스에서 database 네임스페이스의 postgres를 짧은 이름 postgres로 못 찾는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   search 첫 항목이 자기 네임스페이스라 postgres.game.svc...로 해석된다. postgres.database나 FQDN을 쓴다.

   </details>

## 23장. Ingress와 외부 트래픽

본문: [23장. Ingress와 외부 트래픽](../4부-노출-데이터-운영/23-Ingress와-외부-트래픽.md)

1. LoadBalancer Service로 서비스마다 노출할 때의 한계 두 가지는?

   <details markdown="1"><summary>답 확인</summary>

   서비스마다 LB·IP·인증서가 늘어 비용·관리 부담이 커지고, L4라 HTTP 경로/호스트 판단을 못 한다.

   </details>

2. Ingress와 IngressController의 차이는?

   <details markdown="1"><summary>답 확인</summary>

   Ingress는 라우팅 규칙을 선언한 API 리소스, IngressController는 그것을 watch해 실제로 프록시하는 프로그램.

   </details>

3. kubectl get ingress에서 ADDRESS가 비어 있으면?

   <details markdown="1"><summary>답 확인</summary>

   컨트롤러가 처리하지 않았다. 컨트롤러 존재와 ingressClassName/IngressClass 일치를 확인한다.

   </details>

4. 여러 Ingress 컨트롤러가 있을 때 처리 주체를 정하는 필드는?

   <details markdown="1"><summary>답 확인</summary>

   ingressClassName

   </details>

5. pathType 3가지는?

   <details markdown="1"><summary>답 확인</summary>

   Exact(정확히 일치), Prefix(경로 세그먼트 단위 접두사), ImplementationSpecific(컨트롤러 재량).

   </details>

6. pathType Prefix에서 /api는 /apifoo와 매칭되나?

   <details markdown="1"><summary>답 확인</summary>

   아니다. 세그먼트 단위라 /api/users와만 매칭된다.

   </details>

7. 경로 기반보다 호스트 기반 분리가 권장되는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   경로를 제거해 전달하는 rewrite가 상대 경로와 충돌할 수 있어서 서브도메인 분리가 더 안전하다.

   </details>

8. Ingress 규칙에 맞지 않는 요청은 누가 처리하나?

   <details markdown="1"><summary>답 확인</summary>

   defaultBackend

   </details>

9. Ingress에서 TLS는 어디서 종료되나?

   <details markdown="1"><summary>답 확인</summary>

   컨트롤러에서. 컨트롤러→백엔드 Pod 구간은 기본 평문 HTTP다.

   </details>

10. Ingress 인증서 발급·갱신 자동화 도구는?

   <details markdown="1"><summary>답 확인</summary>

   cert-manager. 애노테이션 한 줄(cert-manager.io/cluster-issuer)로 처리한다.

   </details>

11. Ingress 502 / 503 / 504의 의미는?

   <details markdown="1"><summary>답 확인</summary>

   502 백엔드 무응답(포트 불일치·크래시), 503 엔드포인트 없음, 504 백엔드가 느림.

   </details>

12. Ingress 404의 원인은?

   <details markdown="1"><summary>답 확인</summary>

   호스트/경로 매칭 실패. Host 헤더를 확인한다.

   </details>

13. Gateway API의 세 리소스와 담당자는?

   <details markdown="1"><summary>답 확인</summary>

   GatewayClass(인프라 제공자), Gateway(클러스터 운영자: 포트·인증서), HTTPRoute(앱 개발자: 라우팅).

   </details>

14. 게임 서버의 자체 TCP 프로토콜을 Ingress 규칙으로 라우팅할 수 있나?

   <details markdown="1"><summary>답 확인</summary>

   아니다. Ingress는 HTTP/HTTPS 요청을 호스트·경로로 나누는 L7 라우터다.

   </details>

15. 대부분의 IngressController는 Service ClusterIP를 거쳐 프록시하나?

   <details markdown="1"><summary>답 확인</summary>

   아니다. 대부분 ClusterIP를 거치지 않고 EndpointSlice의 Pod IP로 직접 프록시한다.

   </details>

## 24장. 스토리지 — Volume, PV, PVC, StorageClass

본문: [24장. 스토리지 — Volume, PV, PVC, StorageClass](../4부-노출-데이터-운영/24-스토리지.md)

1. 스토리지 요구의 세 유형과 볼륨 타입은?

   <details markdown="1"><summary>답 확인</summary>

   임시 스크래치=emptyDir, 설정·시크릿 주입=configMap/secret/downwardAPI/projected, 영구 데이터=persistentVolumeClaim.

   </details>

2. emptyDir의 수명은?

   <details markdown="1"><summary>답 확인</summary>

   컨테이너 재시작에는 살아남고 Pod 삭제에는 사라진다. medium: Memory면 메모리 한도를 소비해 OOMKilled 위험.

   </details>

3. hostPath를 일반 앱에 쓰면 안 되는 이유 3가지는?

   <details markdown="1"><summary>답 확인</summary>

   다른 노드로 옮기면 데이터 없음, 노드 장악 가능한 보안 위험, 노드가 죽으면 데이터도 죽음.

   </details>

4. PV / PVC / StorageClass의 스코프와 작성자는?

   <details markdown="1"><summary>답 확인</summary>

   PV=클러스터(운영자·프로비저너), PVC=네임스페이스(개발자), StorageClass=클러스터(운영자).

   </details>

5. 동적 프로비저닝이란?

   <details markdown="1"><summary>답 확인</summary>

   PVC에 맞는 PV가 없을 때 StorageClass의 프로비저너가 실제 스토리지와 PV를 만들어 바인딩하는 것.

   </details>

6. 10Gi PVC에 100Gi PV가 매칭되면?

   <details markdown="1"><summary>답 확인</summary>

   바인딩은 1:1 배타적이라 100Gi 전체를 차지한다.

   </details>

7. volumeBindingMode Immediate의 멀티 AZ 문제는?

   <details markdown="1"><summary>답 확인</summary>

   볼륨이 다른 AZ에 먼저 생겨 Pod가 영원히 스케줄되지 않을 수 있다. WaitForFirstConsumer로 노드 결정 후 생성한다.

   </details>

8. RWO와 RWOP의 차이는?

   <details markdown="1"><summary>답 확인</summary>

   RWO는 하나의 노드(같은 노드의 여러 Pod 가능), RWOP는 하나의 Pod만.

   </details>

9. EBS/GCP PD/Azure Disk는 RWX를 지원하나?

   <details markdown="1"><summary>답 확인</summary>

   아니다. RWX는 EFS, Azure Files, NFS 같은 파일 스토리지가 필요하다.

   </details>

10. reclaimPolicy Delete와 Retain의 차이는?

   <details markdown="1"><summary>답 확인</summary>

   Delete는 PVC 삭제 시 PV와 실제 스토리지 삭제, Retain은 PV를 Released로 두고 데이터 보존(수동 정리).

   </details>

11. 볼륨 확장의 조건과 제약은?

   <details markdown="1"><summary>답 확인</summary>

   StorageClass에 allowVolumeExpansion: true가 필요하고, 늘리기만 가능하며 줄일 수 없다.

   </details>

12. CSI란 무엇이며 배포 구성은?

   <details markdown="1"><summary>답 확인</summary>

   드라이버를 클러스터 밖으로 분리한 gRPC 표준. 컨트롤러 플러그인(Deployment)과 노드 플러그인(DaemonSet).

   </details>

13. 백업 3계층은?

   <details markdown="1"><summary>답 확인</summary>

   애플리케이션(pg_dump 등), 볼륨(VolumeSnapshot·클라우드 스냅샷), 클러스터(Velero).

   </details>

14. PVC 삭제가 Terminating에서 멈추면?

   <details markdown="1"><summary>답 확인</summary>

   pvc-protection 파이널라이저 때문으로, 사용 중인 Pod를 먼저 삭제한다.

   </details>

15. Multi-Attach error의 원인은?

   <details markdown="1"><summary>답 확인</summary>

   RWO 볼륨을 여러 노드에서 마운트하려 함. 노드 급사로 연결이 남은 경우가 흔하며 대개 몇 분 뒤 풀린다.

   </details>

## 25장. 인증·인가(RBAC)·보안·오토스케일링 기초

본문: [25장. 인증·인가(RBAC)·보안·오토스케일링 기초](../4부-노출-데이터-운영/25-인증-인가-보안-오토스케일링.md)

1. API 서버 요청 처리 3관문 순서는?

   <details markdown="1"><summary>답 확인</summary>

   인증(Authentication) → 인가(Authorization) → 어드미션 제어, 이후 etcd 저장.

   </details>

2. 401과 403의 차이는?

   <details markdown="1"><summary>답 확인</summary>

   401은 인증 실패(인증서·토큰·kubeconfig), 403은 신원 확인 후 권한 없음(RBAC).

   </details>

3. kubectl get users가 동작하지 않는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   쿠버네티스는 사용자를 저장하지 않고 인증서·토큰에서 이름과 그룹 문자열만 추출한다. 예외는 ServiceAccount.

   </details>

4. API를 호출하지 않는 앱의 SA 토큰 처리는?

   <details markdown="1"><summary>답 확인</summary>

   automountServiceAccountToken: false로 꺼서 Pod 침해 시 악용을 막는다.

   </details>

5. system:masters 그룹의 특징은?

   <details markdown="1"><summary>답 확인</summary>

   RBAC 검사를 건너뛰어 모든 것을 할 수 있다. kubeadm admin.conf 인증서가 이 그룹이라 보관만 한다.

   </details>

6. RoleBinding이 ClusterRole을 참조하면 적용 범위는?

   <details markdown="1"><summary>답 확인</summary>

   그 RoleBinding의 네임스페이스에만. ClusterRole 재사용의 핵심 조합이다.

   </details>

7. RBAC 주체 3종류와 권장 방식은?

   <details markdown="1"><summary>답 확인</summary>

   User, Group, ServiceAccount. 그룹 기반 바인딩을 권장한다.

   </details>

8. 내장 ClusterRole 4개는?

   <details markdown="1"><summary>답 확인</summary>

   cluster-admin(전부), admin(네임스페이스 전부+RBAC), edit(읽기/쓰기, RBAC 제외), view(읽기 전용, Secret 제외).

   </details>

9. secrets에 list 권한이 위험한 이유는?

   <details markdown="1"><summary>답 확인</summary>

   그 네임스페이스의 모든 시크릿을 덤프할 수 있다.

   </details>

10. 블래스트 레이디어스 층별 방어 도구는?

   <details markdown="1"><summary>답 확인</summary>

   컨테이너 안=securityContext, 노드 탈출=PSA, Pod 간 통신=NetworkPolicy, API 호출=SA 토큰 끄기·RBAC.

   </details>

11. PSA 프로파일 3개는?

   <details markdown="1"><summary>답 확인</summary>

   privileged(제한 없음), baseline(알려진 권한 상승 차단), restricted(강력한 하드닝).

   </details>

12. PSA 모드 enforce / warn / audit의 차이는?

   <details markdown="1"><summary>답 확인</summary>

   enforce는 생성 거부, warn은 경고만(생성됨), audit는 감사 로그에만 기록.

   </details>

13. NetworkPolicy가 조용히 무시되는 경우는?

   <details markdown="1"><summary>답 확인</summary>

   CNI가 지원하지 않을 때(Flannel, kindnet). Calico, Cilium 등은 지원한다.

   </details>

14. NetworkPolicy에서 namespaceSelector와 podSelector를 별도 항목 vs 한 항목에 쓰면?

   <details markdown="1"><summary>답 확인</summary>

   별도 항목(-)은 OR, 한 항목 안은 AND.

   </details>

15. Egress 기본 거부 시 반드시 허용할 것은?

   </details>

   <details markdown="1"><summary>답 확인</summary>

   <details markdown="1"><summary>답 확인</summary>

   </details>

15. 알림은 무엇에 걸어야 하나?

   <details markdown="1"><summary>답 확인</summary>

   </details>

   <details markdown="1"><summary>답 확인</summary>

   </details>

배포 중 502의 근본 원인은?	preStop 실행과 엔드포인트 제거가 병렬이라, 규칙 갱신 전 죽은 Pod로 트래픽이 간다.	Docker·K8s::16

base64가 보호 수단이 아닌 이유는?	인코딩일 뿐이라 누구나 base64 -d로 디코딩할 수 있다.	Docker·K8s::17

etcd 저장 시 암호화의 프로덕션 권장 프로바이더는?	kms v2. 기존 Secret은 다시 써야(replace) 암호화된다.	Docker·K8s::17

immutable ConfigMap + 버전 이름의 장점은?	실수로 설정을 바꾸는 사고 방지, kubelet 감시 불필요로 API 서버 부하 감소, 쉬운 롤백.	Docker·K8s::17

시나리오: subPath로 넣은 nginx.conf가 ConfigMap 수정 후에도 그대로인 이유는?	subPath 마운트는 자동 갱신되지 않는다. 디렉터리 마운트나 롤아웃 유도를 쓴다.	Docker·K8s::17
시나리오: 크래시 리포트에 DB 비밀번호가 실려 나갔다. 무엇을 바꾸나?	환경변수 주입을 secret 볼륨(defaultMode 0400)으로 바꾼다. 환경변수는 에러 리포팅·자식 프로세스 상속·/proc environ으로 샌다.	Docker·K8s::17
ReplicaSet 템플릿 이미지를 바꾸면 기존 Pod는?	그대로다. 새로 만들어지는 Pod부터 적용된다.	Docker·K8s::18
ReplicaSet이 Pod 소유권을 판단하는 기준은?	셀렉터. 자기가 만들지 않은 Pod도 셀렉터에 맞으면 자기 것으로 간주한다.	Docker·K8s::18
Recreate 전략은 언제 쓰나?	두 버전이 동시에 존재하면 안 될 때(DB 스키마 호환성, 파일 락 등). 다운타임이 생긴다.	Docker·K8s::18

시나리오: 컬럼 삭제 마이그레이션이 든 v2를 rollout undo했더니 v1이 에러를 낸다. 왜?	롤백은 Pod 템플릿만 되돌리고 DB 스키마는 그대로다. 마이그레이션은 하위 호환되게 설계한다.	Docker·K8s::18

CPU와 메모리 오버커밋의 안전성은?	CPU는 스로틀링뿐이라 안전, 메모리는 노드 OOM 위험이 있어 1.2~1.5배 이내.	Docker·K8s::19
스케줄러의 노드 선택 단계는?	필터링 → 스코어링 → 바인딩(spec.nodeName 설정).	Docker·K8s::19
