## 결정적 지식 3개

### ① 컨테이너는 커널 기능으로 둘러싼 보통 프로세스다

> 컨테이너 = 호스트 커널을 공유하는 리눅스 프로세스 + **네임스페이스(무엇이 보이나)** + **cgroups(얼마나 쓰나)** + **레이어 파일시스템(무엇을 디스크로 보나)**.

| 이 원리에서 나오는 것 | 장 |
|---|---|
| PID 1이 init 책임(좀비 회수·시그널)을 떠안음 → `docker stop` 지연, `tini` | 3장 |
| 종료 코드 = 128 + 시그널 번호 → 137(SIGKILL·OOM), 143(SIGTERM) | 3·7·26장 |
| 할당 ≠ 실제 사용(오버커밋) → 지연된 OOM Kill | 4·7장 |
| VM보다 빠르고 가볍지만 커널 공유로 격리가 약함 | 5·6장 |
| 네임스페이스는 렌즈일 뿐 → 컨테이너마다 0.0.0.0:80 가능, nsenter | 6장 |
| 메모리는 넘으면 죽고 CPU는 넘으면 느려진다 | 7·19장 |
| 불변 레이어 + 휘발성 쓰기 레이어 → 볼륨이 필요한 이유, 빌드 캐시 | 8·9·10장 |
| Pod = NET·IPC·UTS 네임스페이스를 공유한 컨테이너 묶음 → localhost 통신 | 15장 |

**스스로 확인:** "컨테이너가 137로 죽었다"와 "Pod 안 두 컨테이너가 localhost로 통신한다"를 ①만으로 설명할 수 있나요?

### ② 쿠버네티스는 원하는 상태를 선언하면 컨트롤러가 계속 맞춘다

> 사용자는 `spec`(원하는 상태)을 API 서버에 기록하고, 각 컨트롤러는 `status`(현재 상태)와의 차이를 **반복해서(레벨 트리거)** 좁힌다. 모든 통신은 API 서버를 거친다.

| 이 원리에서 나오는 것 | 장 |
|---|---|
| Pod 자동 재생성, 노드 장애 복구, 이벤트 유실 내성 | 13장 |
| 모든 리소스가 `apiVersion/kind/metadata/spec/status` 같은 구조 | 14장 |
| 프로브 결과로 재시작(liveness) / 트래픽 차단(readiness) | 16장 |
| Deployment → 버전별 ReplicaSet → 롤링 업데이트·롤백 | 18장 |
| 스케줄러는 `requests`만 보고 배치 → 사용률 낮아도 Pending | 19장 |
| Ingress 리소스는 선언일 뿐, 실행은 Ingress 컨트롤러 | 23장 |
| API 서버 3관문(인증 → 인가 → 어드미션), HPA도 하나의 컨트롤러 | 25장 |
| 누가 무엇을 바꾸나: Terraform(인프라) vs 컨트롤러(Pod 수) | 1장 |

**스스로 확인:** "Pod를 `kubectl delete`했는데 다시 생긴다"와 "Ingress를 만들었는데 ADDRESS가 비어 있다"를 ②로 설명할 수 있나요?

### ③ 일회용 실체 위에 안정된 간접층을 둔다

> Pod와 Pod IP, 노드, 디스크는 언제든 바뀐다. 그래서 쿠버네티스는 **이름·라벨·요구**로 느슨하게 연결하는 간접층을 둔다.

| 간접층 | 무엇을 감추나 | 장 |
|---|---|---|
| 라벨 셀렉터 | 어떤 Pod들인지 | 14장 |
| Service(ClusterIP) → EndpointSlice(ready) | 바뀌는 Pod IP | 21장 |
| DNS(`svc.namespace.svc.cluster.local`) | Service IP | 22장 |
| ConfigMap·Secret | 이미지에 굳은 설정 | 17장 |
| PVC(요구) ↔ PV·StorageClass(제공) | 실제 디스크 위치 | 24장 |
| Ingress(호스트·경로 규칙) | 여러 Service의 진입점 | 23장 |
| 네임스페이스·ResourceQuota | 팀·환경 경계 (보안 경계는 아님) | 20장 |

**스스로 확인:** "Pod는 Running인데 Service로 트래픽이 안 간다"를 ③의 사슬(라벨 → EndpointSlice ready → kube-proxy)로 따라갈 수 있나요?

## 장별 코어

### 1장. 인프라 전체 그림 — Docker, Kubernetes, Terraform, EKS의 역할과 배포 흐름

> Docker는 이미지를 만들고 Terraform은 AWS 자원을 코드로 선언하며 Kubernetes(EKS 제어부)는 원하는 실행 상태를 계속 맞추는데, "어디서 실행되는가"와 "누가 그 설정을 소유하는가"는 다른 질문이므로 Pod가 늘어도 EC2·Terraform이 자동으로 따라오지 않는다.

- 네 도구, 네 역할 — Docker=이미지 빌드, Kubernetes=실행 의도 저장·유지, EKS=AWS 관리 Kubernetes 제어부, Terraform=AWS 자원·정책 코드 선언(실행 후 종료). Node=머신, Pod=배치 단위, 컨테이너 앱=프로세스.
- Git에서 EKS까지 — 이미지는 주소로 전달된다: Git → CI → Docker 빌드 → ECR → CD → EKS API이며, 이미지 주소(digest)가 전달되고 노드가 ECR에서 pull한다. 새 버전은 새 Pod로 교체한다.
- 수요(replicas)와 공급(노드)은 별개, apply는 소유자일 때만 — Pending이면 무엇이 부족한지부터 확인하고, Terraform이 그 설정을 소유할 때만 apply한다.
- 매니지드여도 내 책임 — EKS는 컨트롤 플레인 운영만 대신하고 RBAC·NetworkPolicy·업그레이드 결정·관측성·백업은 사용자 몫이다.

**C++·TCP 서버에서 출발하기**

- 감시 프로세스·런처 스크립트 → Deployment/ReplicaSet controller: 명령형 스크립트가 아니라 원하는 상태를 계속 맞추는 루프이며, 머신이 모자라면 만들지 않고 Pending으로 기다린다.
- 서버 실행 파일 패키지 → Docker 이미지: 레지스트리에 올려 digest로 가리키고, 노드가 스스로 pull한다.
- IDC 장비 발주 → Terraform: 코드로 선언하고 plan/apply 후 종료되어 부하에 스스로 반응하지 않는다.
- 실행 파일 덮어쓰기 패치 → rolling update: 덮어쓰지 않고 새 Pod로 교체하며, 롤백이 DB를 되돌리지 않는다.

### 2장. 리눅스 OS 큰 그림

> 내 프로그램은 유저 모드에 갇혀 시스템 콜·인터럽트·예외로만 커널에 들어가고, 커널은 태스크(R/S/D/Z)를 스케줄링하며 컨테이너의 CPU 제한조차 cgroup 쿼터라는 커널 기능일 뿐이다.

- 커널 = 하드웨어를 흉내 내는 라이브러리 — 시분할·메모리 가상화·자원 중재·격리를 대신하고, 모든 것은 파일(fd)이며, 내부 상태는 /proc·/sys로 본다.
- 유저 → 커널의 문은 세 개뿐 — 시스템 콜, 인터럽트, 예외/폴트. 시스템 콜은 비싸고 실패 시 -1과 errno를 남긴다.
- 스케줄러와 태스크 상태 R/S/D/Z — D(인터럽트 불가 대기)는 kill -9로도 안 죽고 load average에 포함된다.
- 컨테이너 CPU 제한 = cgroup 쿼터 — --cpus=N은 100ms 주기 쿼터이고, 다 쓰면 컨테이너 전체가 다음 주기까지 스로틀링된다.

**C++·TCP 서버에서 출발하기**

- recv/send/epoll_wait 호출 → 시스템 콜: 컨테이너도 호스트와 같은 커널에 직접 시스템 콜을 한다(컨테이너 전용 커널은 없다).
- 워커 스레드 수 = hardware_concurrency() → cgroup CPU 쿼터: 코어 수를 직접 읽으면 호스트 코어 수가 나와 쿼터를 금방 소진하고 스로틀링된다.
- 틱 지연 스파이크 → 스로틀링: 원인이 내 코드가 아니라 쿼터 소진으로 컨테이너 전체가 멈춘 것일 수 있다(cpu.stat의 nr_throttled).

### 3장. 프로세스와 시그널

> 프로세스는 fork로 복제되고 exec로 교체되며 부모의 wait로 회수되는데, 컨테이너에서 PID 1이 된 내 서버는 이 회수(좀비)와 시그널 처리(SIGTERM)를 스스로 책임져야 하고, 못 하면 유예 시간 뒤 SIGKILL(137)로 끝난다.

- 프로세스 = 그릇, fork → exec → wait — 주소 공간·fd 테이블·스레드를 묶은 그릇이며 fork(COW) 후 exec(PID·fd 유지)로 실행되고 wait로 회수된다.
- 좀비·고아와 PID 1의 책임 — 좀비는 kill -9로 못 없애고 부모가 wait해야 하며, 컨테이너의 PID 1인 서버는 고아 회수와 시그널 처리를 떠안으므로 tini/--init 또는 직접 구현한다.
- 시그널 = 번호 하나짜리 비동기 통지, 종료 코드 = 128 + N — SIGKILL·SIGSTOP은 잡을 수 없고, 137(SIGKILL: OOM 등)·143(SIGTERM)으로 원인을 읽는다.
- 우아한 종료: SIGTERM → 유예 → SIGKILL — 새 요청 중단 → 진행 중 마무리 → 연결 닫기 → 종료를 도커 10초·쿠버네티스 30초 안에 끝내고, 셸이 PID 1이 되지 않게 exec 형식 CMD를 쓴다.

**C++·TCP 서버에서 출발하기**

- 점검 종료 절차(신규 접속 차단 → 세션 저장 → 종료) → SIGTERM 우아한 종료: 종료 시점과 마감(10초/30초)을 오케스트레이터가 정하고 넘기면 SIGKILL이다.
- 세그폴트 크래시(139) → 종료 코드 137: 137은 크래시가 아니라 바깥에서 SIGKILL로 죽인 것(OOM, kill -9, 타임아웃)이다.
- 끊긴 소켓에 send → 에러 반환 → SIGPIPE: 리눅스에서는 SIGPIPE 기본 동작으로 프로세스가 종료되므로 서버는 시작 시 무시한다.

### 4장. 메모리·파일시스템·네트워크 기초

> 커널은 메모리·파일·소켓 모두를 "예약과 실제 사용", "이름과 실체"를 분리한 간접 계층으로 다루기 때문에, 경고 없는 OOM kill(137), rm해도 안 돌아오는 용량, 늦게 보이는 로그, 127.0.0.1 listen 장애 같은 컨테이너 현상이 생긴다.

- 메모리: 예약 ≠ 실제 사용 — VSZ와 RSS는 다르고, 오버커밋 때문에 진짜 바닥나면 OOM killer가 경고 없이 SIGKILL을 보낸다. 컨테이너는 cgroup memory.max에서 OOM이 나고 종료 코드는 137이다.
- 파일: 이름 ≠ 실체, write ≠ 디스크 — fd → open file table → inode이며 이름은 디렉터리 항목에 있다. 열린 파일은 rm해도 공간이 안 돌아오고, overlayfs는 첫 쓰기 때 파일 전체를 복사하며, write 성공은 디스크 기록이 아니다.
- 네트워크: 소켓도 fd, bind 주소가 범위 — TCP는 경계 없는 바이트 스트림이고, 127.0.0.1 vs 0.0.0.0이 접근 범위를 정하며, 먼저 닫은 쪽은 60초 TIME_WAIT에 머문다.

**C++·TCP 서버에서 출발하기**

- new 실패 시 std::bad_alloc → 오버커밋과 OOM killer: 할당은 성공하고 쓰는 순간 SIGKILL(137)로 죽어 예외도 로그도 없다.
- 개발 PC의 127.0.0.1 bind → 네트워크 네임스페이스: 컨테이너마다 루프백이 따로라 밖에서 안 보이므로 0.0.0.0에 listen한다.
- 길이 헤더 패킷 조립 → TCP 바이트 스트림: 완전히 같다. 게임 서버의 패킷 조립이 곧 길이 접두어 방식이다.

### 5장. 가상 머신 vs 컨테이너, Docker의 전체 구조

> 컨테이너는 호스트 커널을 공유하는 격리된 프로세스이고, docker run은 CLI → dockerd → containerd → shim → runc → 커널로 전달되는 "실행 준비 경로"일 뿐이며, runc는 사라지고 shim이 부모로 남기에 데몬이 재시작돼도 컨테이너는 산다.

- 커널을 공유하는 프로세스 — VM은 하드웨어를 가상화해 각자 커널을 갖고, 컨테이너는 호스트 커널 하나를 공유해 가볍지만 격리 경계가 커널이다.
- 역할이 나뉜 제어 경로 — CLI → dockerd → containerd → shim → runc → 커널로 넘어가며, 네트워크·포트 매핑·볼륨·빌드 위임은 dockerd 몫이다.
- runc는 사라지고 shim이 남는다 — runc는 execve()로 컨테이너 명령이 되어 사라지고 shim이 부모로 남아, 데몬 재시작에도 컨테이너가 산다(live-restore로 더 확실히).
- 이미지는 파일과 설정, CPU에서 도는 것은 앱 — OCI 규격 덕분에 빌드·실행 도구가 달라도 되고, 실행 후 앱은 커널과 직접 시스템 호출을 주고받는다.

**C++·TCP 서버에서 출발하기**

- 한 머신에 서버 프로세스 여러 개 → 컨테이너: 같은 커널을 쓰지만 프로세스마다 다른 PID·네트워크·파일시스템 뷰와 자원 한도가 씌워진다.
- fork() 후 execve()로 서버 실행 → runc의 execve(): runc는 exec 전에 네임스페이스·cgroup·루트 파일시스템을 먼저 준비한다.
- waitpid()로 자식 종료 코드를 회수하는 감시 프로세스 → shim: 관리 데몬과 분리된 별도 프로세스라 dockerd가 재시작돼도 워크로드는 산다.
- 실행 파일 + 설정 배포 패키지 → 이미지: OS 유저랜드 파일까지 들어 있지만 커널은 없다.

### 6장. 컨테이너 격리 — 네임스페이스

> 컨테이너는 일반 프로세스에 네임스페이스라는 "렌즈"를 씌워 보이는 것만 다르게 만든 것이고, Docker 옵션은 그 렌즈를 공유하라는 지시이며, 격리는 가시성(네임스페이스)·권한(capabilities/seccomp)·자원(cgroups) 세 축이 함께여야 완성된다.

- 네임스페이스는 렌즈다 — 자원을 복제·분할하지 않고 프로세스 그룹별로 다르게 보이게 하며, 같은 커널·CPU·물리 NIC를 공유한다.
- 여덟 가지 렌즈 — PID(첫 프로세스가 PID 1), net(lo·eth0·포트 공간), mnt(이미지 레이어가 /), UTS, IPC, user(UID 매핑), cgroup, time.
- 만들고, 들어가고, 공유한다 — unshare로 만들고 nsenter로 들어가며 /proc/&lt;pid&gt;/ns/ 번호로 확인한다. --net=host, --net=container:X는 공유 지시이고 Pod의 pause 컨테이너가 같은 원리다.
- 격리 3축 — 네임스페이스는 가시성만 담당하고 권한은 capabilities/seccomp, 자원은 cgroups가 맡는다. --privileged는 격리 포기다.

**C++·TCP 서버에서 출발하기**

- 같은 포트 두 번 bind() → EADDRINUSE → 네트워크 네임스페이스: 네임스페이스마다 포트 공간이 따로라 컨테이너마다 0.0.0.0:80을 bind할 수 있다.
- getpid()의 프로세스 ID → PID 네임스페이스: 같은 프로세스가 안에서는 PID 1, 호스트에서는 다른 PID이며 PID 1은 좀비 회수·시그널 책임을 진다.
- chroot로 서버 가두기 → 마운트 네임스페이스 + pivot_root: 마운트 테이블 자체가 분리되고 /는 이미지 레이어 파일시스템이 된다.
- 1024 미만 포트용 root 실행 → capabilities: root 전체 대신 필요한 조각(CAP_NET_BIND_SERVICE)만 주며 런타임은 기본으로 대부분을 제거한다.

### 7장. 자원 제어 — cgroups

> 네임스페이스가 못 막는 자원 사용량은 cgroups가 제한·측정하며, Docker의 --cpus/--memory/--pids-limit은 결국 cgroup 제어 파일에 값을 쓰는 것이고, 한도를 넘으면 CPU는 느려지고(스로틀링) 메모리는 죽는다(OOM kill, OOMKilled).

- 보이는 것과 쓰는 양은 별개 — 네임스페이스는 가시성만 정하고, 자원 사용량을 제한·측정하는 것은 cgroups다.
- v2는 하나의 계층, 드라이버는 둘 — 모든 컨트롤러가 하나의 계층을 공유하고 프로세스는 한 경로에만 속한다. 드라이버는 cgroupfs/systemd이며 kubelet과 런타임의 드라이버가 일치해야 한다.
- Docker 옵션 = 제어 파일에 값 쓰기 — --cpus→cpu.max, --cpu-shares→cpu.weight, --memory→memory.max, --pids-limit→pids.max.
- CPU는 느려지고 메모리는 죽는다 — CPU 한도 초과는 스로틀링, 메모리 한도 초과는 cgroup OOM killer의 SIGKILL이며 State.OOMKilled가 true가 된다.

**C++·TCP 서버에서 출발하기**

- setrlimit()로 프로세스 자원 상한 → cgroups: 프로세스 그룹(컨테이너) 단위이고 측정까지 하며 계층으로 관리된다.
- new의 std::bad_alloc / malloc의 NULL → memory.max 초과: 처리할 실패 값이 아니라 cgroup OOM killer의 SIGKILL이라 핸들러도 로그도 남지 않는다.
- CPU 경쟁으로 틱이 밀림 → cpu.max 스로틀링: 경쟁이 없어도 주기 쿼터를 다 쓰면 다음 주기까지 강제로 대기한다.
- 스레드 무한 생성 버그·포크 폭탄 → pids.max: PID 네임스페이스는 개수를 막지 못하고 cgroup이 막는다.

### 8장. 이미지, 레이어, 레지스트리, OCI 표준

> 이미지는 내용 해시로 식별되는 읽기 전용 레이어의 스택이고, 컨테이너는 overlayfs로 그 위에 휘발성 쓰기 레이어 하나를 얹어 copy-on-write로 실행되며, OCI 세 스펙이 이 포맷·실행·배포 방식을 표준화해 도구를 자유롭게 바꿔 끼울 수 있다.

- 불변 레이어 스택과 내용 주소화 — 이미지는 순서 있는 읽기 전용 레이어 스택이고, 블롭은 다이제스트로 저장되어 같은 내용은 한 벌만 존재한다.
- 휘발성 쓰기 레이어(overlayfs CoW) — lowerdir + upperdir → merged. 수정은 CoW, 삭제는 whiteout이며 컨테이너를 지우면 upperdir도 사라지므로 데이터는 볼륨으로 뺀다.
- 태그는 이름표, 다이제스트는 내용 — 참조는 호스트/리포지토리:태그이고 latest는 기본 이름일 뿐이므로 프로덕션은 명시적 태그나 다이제스트로 고정한다.
- OCI: 포맷·실행·배포의 표준 — Image·Runtime(runc 참조 구현)·Distribution 세 스펙이 인터페이스만 정하고, 런타임은 번들(config.json + rootfs)을 실행한다.

**C++·TCP 서버에서 출발하기**

- 증분 빌드의 오브젝트 파일 재사용 → 레이어 빌드 캐시: 레이어는 순서 있는 스택이라 앞 레이어가 바뀌면 뒤 레이어도 다시 만든다.
- fork() 후 메모리 페이지 copy-on-write → overlayfs CoW: 복사 단위가 파일이고, 사본(upperdir)은 컨테이너를 지우면 사라진다.
- 버전 태그 vs 커밋 해시 → 이미지 태그 vs 다이제스트: 태그(latest)는 옮겨 붙을 수 있고 다이제스트는 내용 해시라 변하지 않는다.
- 패킷 프로토콜 명세 → OCI 스펙: 하나가 아니라 Image·Runtime·Distribution 세 스펙이라 빌드·실행·배포 도구를 각각 바꿔 끼울 수 있다.

### 9장. Dockerfile과 이미지 빌드

> Dockerfile은 레이어로 쌓이는 빌드 입력이므로 자주 바뀌는 것을 뒤에 두어 캐시를 살리고, 멀티스테이지로 빌드 도구와 실행물을 분리해 작고 안전한 이미지를 만들며, 버전 태그·멀티플랫폼 인덱스로 배포 단위를 식별하고, 비밀값은 이미지 밖으로 빼고 스캔·운영 설정으로 실행 준비를 마친다.

- 레이어 레시피와 캐시 — 바뀐 레이어와 그 뒤의 레이어를 전부 다시 만들므로 자주 바뀌는 것을 뒤에 두고 .dockerignore로 컨텍스트를 줄인다.
- 빌드와 실행의 분리(멀티스테이지) — FROM ... AS builder + COPY --from으로 산출물만 옮겨 크기(800MB → 10MB 남짓)와 공격 표면(distroless, 비루트 USER)을 줄인다.
- 배포 단위로서의 이미지 — latest 대신 버전/커밋 태그, build → tag → login → push, 멀티플랫폼은 아키텍처별 이미지를 가리키는 인덱스로 --push한다.
- 이미지 밖에 둘 것과 실행 운영 — ARG/ENV는 히스토리에 남으므로 secret 마운트·--env-file, 푸시 전 hadolint·trivy, 실행 중 --restart·log-opts·HEALTHCHECK.

**C++·TCP 서버에서 출발하기**

- make/CMake 증분 빌드 → 빌드 캐시: make는 의존 그래프로 영향받는 것만 다시 만들지만 Dockerfile은 한 줄 사슬이라 바뀐 줄 뒤가 전부 재실행된다.
- 빌드 머신 vs 배포 패키지 → 멀티스테이지: 최종 이미지에 넣을 파일은 COPY --from으로 직접 골라야 하고 빠진 동적 라이브러리는 실행 시에야 드러난다.
- x86/ARM 크로스 컴파일 배포 → 멀티플랫폼 이미지 인덱스: 한 태그 아래 여러 아키텍처를 묶고 pull하는 쪽이 자기 플랫폼을 자동 선택한다.
- 소스·설정에 비밀번호 하드코딩 → ARG/ENV 비밀값: docker history/inspect로 그대로 읽힌다. secret 마운트는 RUN 단계 동안만 존재한다.

### 10장. 컨테이너 데이터 — 볼륨, 바인드 마운트, tmpfs

> 컨테이너의 쓰기 레이어는 컨테이너와 함께 사라지므로, 남겨야 할 데이터는 레이어 밖에 마운트하며, 생명주기에 따라 볼륨(Docker 관리, 컨테이너와 독립)·바인드 마운트(호스트 경로 그대로)·tmpfs(메모리, 종료 시 소멸)를 고르고, 데이터가 실제로 어디 있는지는 볼륨 드라이버가 책임진다.

- 쓰기 레이어는 휘발성 — 컨테이너가 쓴 내용은 쓰기 레이어(upperdir)에 남고 컨테이너 삭제 시 함께 사라지므로 지속 데이터는 레이어 밖에 마운트한다.
- 마운트 3종 = 생명주기 선택 — 볼륨(Docker 관리, docker volume rm까지, DB 데이터), 바인드 마운트(호스트 경로, 권한·SELinux 상속, 소스 반영), tmpfs(메모리, 종료 즉시 소멸, 비밀값).
- 컨테이너는 마운트 지점만 안다 — 볼륨 드라이버 플러그인으로 NFS·클라우드 스토리지도 같은 -v 문법으로 쓰고 데이터 위치는 드라이버가 책임진다. 쿠버네티스도 같은 원리.

**C++·TCP 서버에서 출발하기**

- 서버 설치 폴더에 직접 쓰는 로그·세이브 → 쓰기 레이어: 컨테이너 교체(삭제·재생성)가 일상이라 교체 때마다 통째로 사라진다.
- DB 전용 디스크 → named volume: 경로는 Docker가 관리하고, compose down -v·volume prune 같은 정리 명령으로 함께 지워질 수 있다.
- 추상 저장소 인터페이스와 구현 교체 → 볼륨 드라이버 플러그인: 가상 함수가 아니라 별도 설치 플러그인이고, 드라이버는 볼륨 생성 시 정한다.

### 11장. Docker 네트워크

> 컨테이너는 veth pair로 호스트 브리지에 꽂혀 같은 브리지 안에서는 L2 스위칭으로, 밖으로는 라우팅 + MASQUERADE로 통신하고, 밖에서 들어오는 -p 트래픽은 PREROUTING의 DNAT로 컨테이너에 전달되며, 사용자 정의 브리지에서는 내장 DNS(127.0.0.11)로 네트워크 단위 이름 통신을 한다.

- 사용자 정의 브리지를 쓴다 — 기본 브리지(docker0)는 이름 기반 자동 DNS가 없고 평평한 공간이다. 사용자 정의 브리지는 이름/별칭 통신과 네트워크 간 격리를 준다.
- veth로 꽂고, 안은 스위칭·밖은 NAT — veth pair 한쪽은 컨테이너 eth0, 다른 쪽은 호스트 브리지. 컨테이너 간은 L2 스위칭, 외부로는 라우팅 + MASQUERADE(POSTROUTING).
- 들어오는 길은 PREROUTING DNAT — -p는 DOCKER 체인 DNAT가 라우팅 전에 목적지를 바꾸고 conntrack이 응답을 되돌린다. docker-proxy는 보완용, 게시 포트는 호스트 방화벽보다 Docker 규칙이 먼저.
- 이름은 127.0.0.11이 네트워크 단위로 푼다 — dockerd 내장 DNS가 같은 네트워크의 컨테이너 이름·별칭·Compose 서비스 이름을 풀고 외부 도메인은 업스트림으로 포워딩한다. --link는 레거시.

**C++·TCP 서버에서 출발하기**

- 공유기 포트포워딩 → -p의 iptables DNAT: 별도 장비가 아니라 같은 호스트 커널의 PREROUTING에서 라우팅 전에 바뀌고, 컨테이너 안 앱은 호스트 포트를 열지 않는다.
- bind(0.0.0.0) vs bind(127.0.0.1) → -p 8080:80 vs -p 127.0.0.1:5432:5432: 게시 주소는 앱이 아니라 Docker가 정한다.
- 설정 파일의 서버 IP → 컨테이너 이름(내장 DNS): IP는 재시작 때 바뀔 수 있고 이름 해석은 같은 사용자 정의 네트워크 안에서만 된다.
- 호스트 방화벽(ufw) → Docker iptables 규칙: 게시된 포트에는 Docker 규칙이 먼저 적용되어 ufw로 막았다고 안전하지 않다.

### 12장. Docker Compose와 컨테이너 런타임 계보

> Compose는 여러 서비스를 하나의 YAML로 묶어 전용 네트워크와 서비스 이름으로 잇는 개발 도구이고, Docker는 Moby에서 분리된 containerd·runc 등의 조합이며, kubelet은 dockerd를 거치지 않고 CRI로 같은 containerd를 직접 쓰므로 dockershim 제거 후에도 OCI 이미지는 그대로 쓸 수 있다.

- Compose = 한 파일 + 전용 네트워크 + 서비스 이름 — 서비스 이름(localhost 아님)으로 접근, 준비 보장은 healthcheck + condition: service_healthy, down -v는 볼륨 삭제, v2는 Go CLI 플러그인과 Compose Specification.
- 런타임 계층과 Moby 계보 — CLI/dockerd → containerd(고수준, CNCF) → runc(저수준, OCI 참조 구현) → 커널. Moby(2017)에서 부품이 분리되어 재사용된다.
- containerd는 공용 런타임, 두 경로 — dockerd → containerd(moby)와 kubelet ─CRI→ containerd(k8s.io)가 같은 containerd·shim으로 수렴한다. containerd 네임스페이스는 커널 네임스페이스와 다르다.
- dockershim 제거 ≠ Docker 이미지 폐기 — 1.24에서 kubelet이 Docker Engine을 건너뛰도록 단순화했을 뿐 OCI 이미지와 로컬 Docker 사용은 그대로다(Docker Engine을 런타임으로 쓰려면 cri-dockerd).

**C++·TCP 서버에서 출발하기**

- 서버들을 순서대로 띄우는 실행 스크립트 → Compose depends_on: 시작 순서만 정하고 listen 준비는 보장하지 않는다(healthcheck 필요).
- 같은 머신 다른 서버에 127.0.0.1로 접속 → 서비스 이름 접속: 컨테이너마다 네트워크 네임스페이스가 달라 localhost는 자기 자신이다.
- 순수 가상 인터페이스 + 어댑터 → CRI + dockershim: 인터페이스는 gRPC이고 1.24에서 어댑터를 kubelet에서 뺐다.
- C++ namespace(논리적 이름 구분) → containerd 네임스페이스: 이름이 같은 커널 네임스페이스(격리)와 전혀 다른 개념이다.

### 13장. 왜 쿠버네티스인가 — 선언적 상태와 아키텍처

> 컨테이너로 서비스가 잘게 쪼개지자 배치·복구·배포 결정이 사람 손을 넘어섰고, 쿠버네티스는 spec에 원하는 상태를 선언하면 API 서버를 중심으로 한 컨트롤러들이 관찰-비교-조치 루프로 그 상태를 계속 유지하게 해 준다.

- 문제의 진화: 드리프트 → 배포 복잡도 → 오케스트레이터 — 컨테이너는 실행 단위의 재현성을 풀었지만, 서비스가 늘자 배치·복구·디스커버리·배포·스케일링이 사람이 감당할 수 없는 조합 문제가 되었다.
- 선언적 상태 + 조정 루프(레벨 트리거) — spec(사람)과 status(시스템)의 차이를 관찰→비교→조치로 줄이며, 현재 상태로 판단하므로 이벤트를 놓쳐도 복구된다.
- 컨트롤 플레인(결정) / 워커 노드(실행), 모든 통신은 API 서버 경유 — kubelet은 pull 모델이라 컨트롤 플레인이 죽어도 실행 중인 Pod는 계속 돈다.
- 도입 판단 — "사람이 손으로 하는 반복 결정"이 많을 때 쓰고, 서비스가 적거나 운영 인력이 없으면 다른 선택지를 먼저 본다.

**C++·TCP 서버에서 출발하기**

- epoll level-triggered vs edge-triggered → 레벨 트리거 조정 루프: epoll은 한 커널의 fd 준비 상태, 쿠버네티스는 etcd에 저장된 클러스터 목표와 현재의 차이를 조치로 메운다.
- 프로세스 워치독 → 조정 루프: 워치독은 한 머신의 프로세스를 살리지만, 조정 루프는 클러스터 전체 N개를 유지하며 다른 노드에 새 Pod를 만든다.
- 마스터 서버가 에이전트에 명령 패킷 push → 컨트롤 플레인/kubelet: 스케줄러는 API 서버에 기록만 하고 kubelet이 watch로 가져간다(pull).

### 14장. API 오브젝트 모델, kubectl, YAML, 라벨

> 모든 쿠버네티스 리소스는 apiVersion·kind·metadata·spec·status라는 같은 구조의 API 오브젝트이고, 오브젝트끼리는 라벨·셀렉터로 느슨하게 묶이며, 우리는 kubeconfig의 현재 컨텍스트로 접속한 kubectl로 YAML 매니페스트를 apply해 원하는 상태를 선언한다.

- 모든 것은 같은 구조의 API 오브젝트 — REST URL을 가진 리소스이고 apiVersion+kind(스키마), metadata(이름·라벨·uid·ownerReferences·finalizers), spec(사람), status(시스템)로 구성된다.
- 라벨은 선택, 애노테이션은 부가 정보 — Service·ReplicaSet·NetworkPolicy는 라벨 셀렉터로 대상을 찾으며, Deployment 셀렉터는 생성 후 변경 불가다.
- kubectl은 현재 컨텍스트로 가고, 선언형 apply가 기본 — apply 성공은 저장됨일 뿐이므로 get pods → describe → get events로 실제 상태를 확인한다.
- YAML은 따옴표·들여쓰기 함정을 피하고, 많아지면 도구로 관리 — 뼈대 생성 → 수정 → 서버 검증 → diff → apply, 환경별 차이는 Helm(템플릿)·Kustomize(패치).

**C++·TCP 서버에서 출발하기**

- 패킷 ID + 프로토콜 버전 → apiVersion + kind: 패킷은 처리하고 버리지만 오브젝트는 etcd에 저장되어 계속 조정되고, 버전에 안정성 등급이 붙는다.
- unique_ptr 소유 트리 → ownerReferences: 소멸자처럼 즉시 호출되지 않고 가비지 컬렉터가 정리하며 finalizers가 삭제를 붙잡을 수 있다.
- 조건으로 세션을 골라 브로드캐스트 → 라벨 셀렉터: 대상 집합이 계속 재평가되어 라벨만 바꾸면 즉시 빠지고, 셀렉터가 겹치면 컨트롤러끼리 Pod를 빼앗는다.
- QA/라이브 접속 프로필 → kubeconfig context: 별도 확인 없이 current-context로 바로 가므로 라이브 컨텍스트 실수가 가장 흔한 사고다.

### 15장. Pod — 최소 배포 단위

> Pod는 pause 컨테이너가 소유한 NET·IPC·UTS 네임스페이스를 함께 쓰고 MNT·PID는 따로 갖는 일회용 컨테이너 묶음이므로, IP·로컬 파일·직접 생성에 기대지 말고 Service·볼륨·컨트롤러를 쓰며, 함께 스케일되어야 할 때만 Init·사이드카 등으로 컨테이너를 묶는다.

- 공유 vs 분리 + pause — NET·IPC·UTS 공유(같은 IP·localhost·포트 공간), MNT·PID 분리(파일은 볼륨으로만), pause가 네임스페이스를 소유해 재시작에도 IP 유지.
- Pod는 일회용 — 죽으면 이름·IP·uid가 다른 새 Pod가 생기므로 Service·볼륨·컨트롤러가 필요하고, 삭제는 Terminating → SIGTERM → 유예 → SIGKILL.
- 매니페스트 읽기와 Pod 다루기 — ports는 선언일 뿐, latest는 Always pull, describe는 Conditions → State → Events, 크래시는 logs --previous, 셸 없는 이미지는 kubectl debug --target.
- 멀티 컨테이너: Init·사이드카·패턴 — Init(먼저·순서대로·완료까지), 사이드카(init + restartPolicy: Always), 사이드카·앰배서더·어댑터, 기준은 "항상 1:1로 함께 스케일되는가".

**C++·TCP 서버에서 출발하기**

- 한 머신의 서버 + 에이전트 프로세스 → 멀티 컨테이너 Pod: localhost 통신과 bind() 포트 충돌은 같지만 파일 시스템(MNT)과 프로세스 목록(PID)은 분리된다.
- 리스닝 소켓을 쥔 부모 프로세스 → pause 컨테이너: 쥐는 것은 소켓이 아니라 네임스페이스(IP) 자체이고, pause는 일을 하지 않는다.
- 같은 머신에서 크래시 후 재실행 → Pod 교체: 컨테이너 재시작은 IP 유지, Pod 교체는 이름·IP·uid가 모두 바뀐다.

본문: [15장. Pod — 최소 배포 단위](../3부-쿠버네티스-핵심/15-Pod.md)

### 16장. Pod 생명주기와 헬스 체크

> Pod 상태는 거친 phase가 아니라 conditions의 Ready와 컨테이너의 lastState로 읽고, 프로브로 재시작(liveness)·트래픽 차단(readiness)·시작 보호(startup)를 나눠 설계하며, 종료 시 엔드포인트 제거와 SIGTERM이 병렬이라는 점을 preStop과 SIGTERM 처리로 메워야 요청이 유실되지 않는다.

- 상태 읽기: phase는 거칠고 Ready와 lastState가 정확하다 — Ready=True인 Pod만 엔드포인트에 등록되고(0/1 Running은 트래픽 없음), 왜 죽었는지는 lastState.terminated에 있다.
- 프로브 3종: 재시작 vs 트래픽 차단 vs 시작 보호 — liveness에 외부 의존성 금지, /healthz와 /readyz 분리, timeoutSeconds 기본 1초는 짧다.
- 재시작은 컨테이너 단위, CrashLoopBackOff는 증상 — 같은 노드에서 컨테이너만 다시 띄우고, 원인은 logs --previous → lastState → describe로 찾는다.
- 종료: 엔드포인트 제거와 SIGTERM은 병렬 — 배포 중 502의 근본 원인이므로 preStop sleep + 앱의 SIGTERM 처리로 막고, sh -c로 셸이 PID 1이 되지 않게 한다.

**C++·TCP 서버에서 출발하기**

- 서버 매니저 하트비트 → livenessProbe: 하트비트에 DB 체크를 넣던 습관은 모든 Pod 동시 재시작(장애 증폭)이 된다.
- 채널 "입장 불가" 표시 → readinessProbe: 쿠버네티스가 프로브 결과로 자동으로 엔드포인트에서 빼고 넣는다.
- 셸 종료 코드 128+시그널 → exitCode 137/139/143: 137은 OOM과 grace 초과가 같은 숫자라 reason으로 구분한다.
- 점검 종료 절차(신규 차단 → 세션 마무리 → 종료) → preStop + SIGTERM: 트래픽 차단과 SIGTERM이 병렬이고 유예 후 SIGKILL이다.

### 17장. ConfigMap과 Secret

> 같은 이미지를 모든 환경에 배포하고 설정은 ConfigMap·Secret으로 주입하되, 환경변수는 절대 갱신되지 않고 볼륨은 갱신되며(subPath 제외), base64는 암호화가 아니므로 Secret은 etcd 암호화(KMS)와 외부 시크릿 관리로 보호하고, 설정 변경은 Pod를 새로 만드는 롤아웃 유도로 반영한다.

- 이미지와 설정 분리 — 같은 이미지 + 환경별 설정 주입. ConfigMap(일반 설정)과 Secret(민감 정보)은 구조가 거의 같고 data 값은 모두 문자열이다.
- 주입 방식이 갱신을 결정한다 — 환경변수는 절대 안 됨(시작 시 고정), 볼륨 마운트는 됨(최대 ~2분, 앱이 다시 읽어야 함), subPath는 안 됨. Downward API도 같은 방식으로 주입한다.
- Secret의 진실: base64는 인코딩 — 실질 이점은 tmpfs 저장과 RBAC 분리뿐이고, 보호는 etcd 암호화(KMS v2)와 외부 시크릿 관리로 하며 주입은 볼륨을 권장한다.
- 설정 변경은 Pod를 새로 만들어 반영한다 — Deployment spec이 그대로면 컨트롤러가 반응하지 않으므로 체크섬 애노테이션·해시 이름·rollout restart·Reloader·불변 ConfigMap으로 롤아웃을 유도한다.

**C++·TCP 서버에서 출발하기**

- getenv()로 읽는 프로세스 환경변수 → env 주입: 반영하려면 컨테이너 재시작이 아니라 Pod 재생성이 필요하고, ConfigMap을 고쳐도 자동으로 일어나지 않는다.
- 설정 파일 hot reload → ConfigMap 볼륨 갱신: 파일 덮어쓰기가 아니라 ..data 심볼릭 링크 원자 교체이고 최대 2분 늦으며 subPath는 갱신되지 않는다.
- 설정 파일 비밀번호 XOR/Base64 난독화 → Secret data(base64): 보호 수단이 아니며 진짜 보호는 etcd 암호화·RBAC·외부 시크릿 관리라는 별도 계층이다.
- 패치 후 서버 재기동 → 롤아웃 유도: 사람이 재기동하는 대신 Pod 템플릿을 바꿔 Deployment가 롤링 업데이트하게 만든다.

### 18장. 워크로드 컨트롤러 — Deployment, StatefulSet, DaemonSet, Job

> 모든 워크로드 컨트롤러는 같은 조정 루프를 돌고 "무엇을 원하는 상태로 삼는가"만 다르며, 무상태 앱은 ReplicaSet을 버전별로 감싸 롤링 업데이트·롤백하는 Deployment로, 고유 이름·스토리지·순서가 필요하면 StatefulSet으로, 노드마다 하나는 DaemonSet으로, 끝나야 하는 일은 Job/CronJob으로 돌린다.

- 같은 조정 루프, 다른 원하는 상태 — ReplicaSet은 셀렉터에 맞는 Pod N개만 지키고, 셀렉터가 소유권을 정하며, 버전 관리는 하지 않는다.
- Deployment = 버전별 ReplicaSet — maxSurge/maxUnavailable과 readiness로 교체하고 replicas 0으로 남긴 이전 ReplicaSet으로 빠르게 롤백한다(Pod 템플릿만 되돌림). PDB로 drain 중 최소 개수를 지킨다.
- StatefulSet의 세 가지 보장 — 안정적 네트워크 ID(헤드리스 서비스)·Pod별 PVC·순서를 보장하지만 리더 선출·페일오버는 하지 않는다.
- DaemonSet·Job·CronJob — 노드마다 정확히 하나, 끝나야 하는 일(restartPolicy OnFailure/Never), 스케줄된 Job(timeZone·concurrencyPolicy).
- 선택 트리 — 끝나는가(Job/CronJob) → 노드마다 하나(DaemonSet) → 고유 ID·스토리지(StatefulSet) → Deployment(90%).

**C++·TCP 서버에서 출발하기**

- 죽은 프로세스를 다시 띄우는 watchdog → ReplicaSet: PID가 아니라 라벨 셀렉터로 소유권을 판단해 자기가 만들지 않은 Pod도 자기 것으로 센다.
- LB에서 한 대씩 빼고 패치 → RollingUpdate: maxSurge/maxUnavailable이 속도를, readiness가 진행을 자동으로 통제하고 실패하면 롤아웃만 멈춘다.
- 이전 빌드 폴더로 되돌리기 → Deployment 롤백: Pod 템플릿만 되돌리며 DB 스키마·ConfigMap·외부 부수 효과는 그대로다.
- 채널 서버 고정 번호 + 전용 데이터 디렉터리 → StatefulSet: 이름·스토리지·순서만 보장하고 마스터 선출·페일오버는 앱/오퍼레이터 몫이다.

### 19장. 리소스 요청·제한과 스케줄링 기초

> requests는 스케줄러가 배치에, limits는 커널이 실행 중에 쓰고, 그 조합이 QoS 클래스와 축출 순서를 정하며, CPU는 초과하면 기다리게 하고 메모리는 죽인다는 비대칭이 값 산정의 근거이고, 스케줄러는 필터링·스코어링으로 노드를 고르되 어피니티(Pod가 고름)와 테인트(노드가 거부)로 위치를 제어한다.

- requests vs limits — requests는 스케줄러(requests 합만 보고 실제 사용량은 안 봄), limits는 커널 cgroup(CPU 스로틀링 / OOM Kill).
- QoS와 축출 — 모든 컨테이너 requests==limits면 Guaranteed, 아무것도 없으면 BestEffort, 나머지 Burstable. 노드 압박 시 BestEffort → Burstable → Guaranteed 순(약속보다 많이 쓰는 놈부터)이며 PDB로 못 막는다.
- CPU는 대기, 메모리는 죽음 — CPU는 압축 가능해 스로틀링(매 100ms 주기), 메모리는 압축 불가라 OOMKilled(137). 그래서 CPU requests는 평균 근처, 메모리 requests는 피크 근처로 잡는다.
- 스케줄러와 배치 제어 — 필터링 → 스코어링 → 바인딩. nodeSelector·어피니티는 Pod가 노드를 고르고 테인트는 노드가 Pod를 거부하며, 전용 노드는 둘을 함께 쓴다.

**C++·TCP 서버에서 출발하기**

- 수동 용량 계획(머신당 서버 N개) → requests와 스케줄러: 실제 사용량이 아니라 선언된 requests 합으로 배치해 사용률 5%여도 Pending이 될 수 있다.
- setrlimit 후 malloc 실패/bad_alloc → limits.memory: 실패를 돌려받지 못하고 커널 OOM killer가 즉시 죽인다(exitCode 137).
- 스레드 우선순위·nice → CPU requests 가중치 / limits.cpu: limits.cpu는 우선순위가 아니라 매 100ms 주기의 시간 상한이라 여유 CPU가 있어도 멈춘다.
- GPU 머신에만 수동 배치 → 테인트 + 어피니티: 톨러레이션은 허가일 뿐 그 노드로 보내지 않는다.

### 20장. 네임스페이스 — 역할, 한계, ResourceQuota, LimitRange

> 네임스페이스는 이름·DNS·RBAC·쿼터의 단위일 뿐 보안 경계가 아니므로, 자원은 ResourceQuota(총량)와 LimitRange(개별 기본값·범위)를 함께 써서 통제하고, 네트워크·노드·커널 격리는 따로 더해야 하며, 신뢰할 수 없는 테넌트는 클러스터나 샌드박스 런타임으로 나눈다.

- 네임스페이스가 주는 것 4가지 — 이름 스코프·DNS 스코프·RBAC 경계·쿼터 단위. 삭제하면 안의 모든 리소스(PVC 포함)가 되돌릴 수 없이 사라진다.
- 네임스페이스는 보안 경계가 아니다 — 네트워크는 기본 열림, 노드·커널·클러스터 전역 리소스·컨트롤 플레인은 공유. NetworkPolicy·쿼터·테인트·샌드박스·RBAC를 따로 더한다.
- ResourceQuota + LimitRange는 한 쌍 — 컴퓨트 쿼터가 있으면 requests/limits 없는 Pod는 거부되므로 LimitRange 기본값을 주입한다. 쿼터 초과 시 컨트롤러는 조용히 재시도한다.
- 멀티테넌시 판단 기준 — 테넌트가 임의 코드를 실행하는가. 소프트는 네임스페이스+쿼터+NetworkPolicy+RBAC, 하드는 별도 클러스터나 샌드박스 런타임.

**C++·TCP 서버에서 출발하기**

- C++ namespace → 쿠버네티스 네임스페이스: 둘 다 이름 충돌만 막지만, 쿠버네티스 쪽은 RBAC·쿼터 단위이고 삭제하면 리소스가 실제로 지워진다.
- 한 머신의 여러 서버 프로세스 → 여러 네임스페이스의 Pod: 커널·노드를 공유하며 네트워크도 기본으로 서로 열려 있어 NetworkPolicy가 필요하다.
- 프로세스 전체 메모리 예산 + 객체별 풀 상한 → ResourceQuota + LimitRange: 양을 선언하지 않은 Pod는 생성 자체가 거부된다.
- 유저 스크립트 샌드박스 → 하드 멀티테넌시: 컨테이너 격리 경계는 커널이라 네임스페이스로는 부족하다.

### 21장. 쿠버네티스 네트워크 모델과 Service

> IP-per-Pod 모델에서 일회용인 Pod IP 대신 Service가 변하지 않는 가상 IP(ClusterIP)를 주고, EndpointSlice가 ready인 Pod 목록을 관리하며, kube-proxy가 만든 iptables/IPVS 규칙대로 커널이 그 가상 IP를 실제 Pod IP로 바꿔 준다.

- IP-per-Pod와 가상 IP — 모든 Pod는 고유 IP를 갖고 NAT 없이 통신하며, Pod IP는 일회용이고 ClusterIP는 어떤 인터페이스에도 없는 가상 IP다.
- Service 타입은 바깥으로 한 겹씩 감싼다 — LoadBalancer ⊃ NodePort ⊃ ClusterIP, ExternalName은 DNS CNAME만 만든다.
- EndpointSlice: ready인 Pod에만 보낸다 — selector에 맞는 Pod 목록 중 ready: true인 엔드포인트에만 트래픽이 간다.
- kube-proxy는 규칙만, 변환은 커널이 — kube-proxy는 iptables/IPVS 규칙을 만들 뿐 데이터 경로에 없다.

**C++·TCP 서버에서 출발하기**

- 로그인 서버가 내려주는 채널 서버 주소 → Service(ClusterIP): ClusterIP에는 accept()하는 프로세스가 없고 노드 커널이 DNAT로 목적지를 바꿀 뿐이다.
- 유저 공간 L4 중계 서버 → kube-proxy: 패킷을 받지 않고 규칙만 깔므로 죽어도 기존 연결이 유지된다.
- 하트비트로 죽은 서버를 목록에서 빼는 서버 매니저 → EndpointSlice ready: 판정은 readiness 프로브, 목록은 모든 노드에 전파된다.
- 프로세스마다 다른 포트로 bind → IP-per-Pod: Pod마다 자기 IP가 있어 모두 같은 포트를 써도 충돌이 없다.

### 22장. DNS와 서비스 디스커버리

> Pod는 resolv.conf에 박힌 CoreDNS(kube-dns Service)에 &lt;service&gt;.&lt;namespace&gt;.svc.cluster.local 이름으로 Service를 묻고, search 덕에 짧은 이름이 통하지만 ndots:5 때문에 외부 조회가 여러 질의로 불어나므로 끝에 점을 붙인 FQDN으로 막는다.

- 이름으로 찾고, 답은 CoreDNS가 한다 — DNS는 요청 시점 해석(환경변수는 시작 시점 스냅샷)이고, 모든 Pod resolv.conf에 kube-dns IP가 들어가 CoreDNS 플러그인 체인이 응답한다.
- 이름 규칙이 곧 응답 규칙 — &lt;service&gt;.&lt;namespace&gt;.svc.cluster.local, 일반=ClusterIP 하나, 헤드리스=모든 Ready Pod IP, ExternalName=CNAME.
- search + ndots가 질의 수를 정한다 — 점이 ndots(기본 5)개 미만이면 search 접미사부터 붙여 외부 조회 1회가 최대 8쿼리가 되며, 끝 마침표 FQDN이 가장 간단한 해결책이다.
- DNS 장애는 순서대로 좁힌다 — CoreDNS → kube-dns EndpointSlice → resolv.conf → NetworkPolicy(53번) → conntrack 경합(NodeLocal DNSCache).

**C++·TCP 서버에서 출발하기**

- 시작 시 설정 파일에서 서버 주소 읽기 → 환경변수 디스커버리: 시작 후 생긴 Service는 영영 모르므로 요청 시점 DNS를 쓴다.
- getaddrinfo() 호출 → Pod 안 DNS 조회: 코드는 같아도 Pod resolv.conf의 ndots:5·search 때문에 질의가 최대 8개로 불어난다.
- 사람이 관리하는 사내 DNS/hosts → CoreDNS: kubernetes 플러그인이 API를 watch해 레코드를 자동 응답한다.

### 23장. Ingress와 외부 트래픽

> Ingress는 하나의 진입점에서 HTTP 트래픽을 호스트·경로로 나누는 설정 데이터이고, 실제 라우팅과 TLS 종료는 그것을 watch하는 IngressController가 하므로 컨트롤러가 없으면 아무 일도 일어나지 않는다.

- 하나의 진입점, L7 라우팅 — LoadBalancer Service는 서비스마다 LB가 생기고 L4라 HTTP 판단을 못 하므로, Ingress가 LB 하나로 호스트·경로 기반 라우팅을 한다.
- 선언(Ingress)과 실행(Controller)은 다르다 — Ingress는 API 리소스, IngressController는 리버스 프록시 프로그램이며 컨트롤러가 없으면 ADDRESS가 비어 있다.
- TLS는 컨트롤러에서 끝난다 — 컨트롤러→백엔드 구간은 기본 평문이고 cert-manager로 인증서를 자동 갱신한다.
- 컨트롤러 선택과 후계 — 클라우드 네이티브(관리 부담↓) vs ingress-nginx(이식성↑), Gateway API는 애노테이션 난립·역할 분리 문제를 푸는 후계다.

**C++·TCP 서버에서 출발하기**

- 게이트웨이 서버의 opcode 기반 분배 → Ingress 라우팅: 기준이 HTTP 호스트·경로라 자체 TCP 프로토콜은 나눌 수 없다.
- 라우팅 설정 파일 vs 게이트웨이 프로세스 → Ingress vs IngressController: 규칙은 API 서버 리소스이고 컨트롤러가 watch로 계속 재생성한다.
- 게이트웨이에서 OpenSSL로 TLS를 풀고 내부 평문 → TLS 종료: 인증서는 Secret으로 넘기고 cert-manager가 90일 갱신을 자동화한다.

### 24장. 스토리지 — Volume, PV, PVC, StorageClass

> Pod보다 오래 남아야 할 데이터는 개발자가 PVC로 요청하고, 맞는 PV가 없으면 StorageClass의 프로비저너(CSI 드라이버)가 동적으로 만들어 1:1로 바인딩하며, 멀티 AZ에선 WaitForFirstConsumer, 중요한 데이터엔 Retain을 쓴다.

- 수명으로 볼륨을 고른다 — 임시(emptyDir) / 설정 주입(configMap·secret 등) / 영구(PVC) 세 유형이며 hostPath는 일반 앱에서 쓰지 않는다.
- 요구(PVC)와 제공(PV·StorageClass)의 분리 — 바인딩은 1:1 배타적이고, 맞는 PV가 없으면 프로비저너(CSI 드라이버)가 동적으로 만든다.
- 볼륨은 물리적 위치(노드·AZ)에 묶인다 — 멀티 AZ에선 WaitForFirstConsumer, RWO는 하나의 노드이며 Multi-Attach error·volume node affinity conflict가 여기서 나온다.
- 데이터를 지키는 것은 정책과 백업이다 — Delete는 PVC 삭제 시 디스크까지 지우므로 프로덕션은 Retain, 백업은 앱·볼륨·클러스터 3계층 + 복원 테스트.

**C++·TCP 서버에서 출발하기**

- 서버 머신 로컬 디스크에 세이브 쓰기 → hostPath: Pod는 다른 노드로 옮겨지므로 데이터가 따라오지 않는다.
- malloc 요청과 할당자 → PVC와 PV/StorageClass: 바인딩은 1:1 배타적이고 디스크는 노드·AZ에 묶인다.
- unique_ptr 소멸 vs release() → reclaimPolicy Delete vs Retain: 기본값이 대개 Delete라 PVC 삭제가 실제 디스크 삭제로 이어진다.
- 한 파일을 여러 프로세스가 쓰기 → 접근 모드: RWO의 단위는 프로세스가 아니라 노드다.

### 25장. 인증·인가(RBAC)·보안·오토스케일링 기초

> API 요청은 인증(401) → 인가(RBAC, 403) → 어드미션을 거쳐 통과하고, 실행된 워크로드는 securityContext·PSA·NetworkPolicy·SA 토큰 끄기로 침해 시 폭발 반경을 층마다 줄이며, 부하는 requests 기준의 HPA·VPA·노드 오토스케일러 세 축으로 맞춘다.

- API 요청은 세 관문을 지난다 — 인증(401) → 인가(403) → 어드미션 → etcd, 사용자 오브젝트는 없고 ServiceAccount만 API 오브젝트다.
- RBAC = 무엇을(Role) + 누구에게(Binding) — RoleBinding이 ClusterRole을 참조하면 그 네임스페이스에만 적용되며 최소 권한·그룹 기반·네임스페이스 우선이다.
- 블래스트 레이디어스를 층마다 줄인다 — securityContext / PSA / NetworkPolicy / SA 토큰 끄기, PSA는 단계적으로, NetworkPolicy는 기본 거부 + DNS 허용.
- 오토스케일링은 세 축, 기준은 requests — HPA(Pod 수) / VPA(Pod 크기) / 노드 오토스케일러(노드 수), HPA Utilization은 requests 대비다.

**C++·TCP 서버에서 출발하기**

- 로그인 계정 DB + 세션 토큰 검증 → 인증: 계정 DB가 없고 인증서·토큰의 이름·그룹 문자열만 믿는다.
- GM 권한 레벨 테이블 → RBAC: 권한 묶음(Role)과 부여(Binding)가 분리되고 네임스페이스 스코프가 있다.
- 서버 간 iptables 방화벽 → NetworkPolicy: 기본은 전부 허용이고 CNI가 지원하지 않으면 조용히 무시된다.
- 동접 증가 시 채널 서버 수동 증설 → HPA: 기준은 노드 CPU가 아니라 requests 대비 사용률이다.

### 26장. 장애 진단 첫걸음

> 장애 진단은 context·namespace·버전을 고정한 뒤 증상 → 가설 → 증거(get/describe/logs --previous/events) → 한 번에 하나씩 변경 → 재검증 순으로 하고, 그 증거는 장애 전에 로그·메트릭을 중앙으로 모아 두어야 존재한다.

- 고정하고, 가설은 증거로 확인한다 — cluster·namespace·버전·시간대를 고정하고 증상 → 가설 → 증거 → 변경 → 재검증, 변경은 한 번에 하나씩.
- 증상이 시작 가설과 계층을 정한다 — 1순위는 describe의 Events, Pending=스케줄 조건, ImagePullBackOff=이미지·권한·네트워크, CrashLoopBackOff=--previous 로그, Ready 아님=readiness, 네트워크는 DNS → EndpointSlice → NetworkPolicy.
- 증거는 장애 전에 모아야 존재한다 — 메트릭(무엇)/로그(왜)/트레이스(어디서), 로그는 stdout → 노드 → DaemonSet 수집기 → 중앙, 메트릭은 Prometheus, 알림은 증상에.
- 업그레이드와 복구도 검증으로 끝난다 — 업그레이드는 호환성 프로젝트, RTO·RPO는 실제 복원 시간으로 측정한다.

**C++·TCP 서버에서 출발하기**

- 코어 덤프·마지막 로그 분석 → logs --previous·describe lastState: Pod가 지워지면 흔적도 사라지므로 중앙 수집이 필요하다.
- 종료 시그널 해석(137 = 128+9 SIGKILL) → exit code 137: SIGKILL일 뿐 OOM 단정 근거가 아니며 종료 reason을 본다.
- 서버 로컬 로그 파일 → stdout 로깅: 파일은 수집기가 못 읽으므로 stdout에 구조화 JSON으로 쓴다.
