# 10장. 컨테이너 데이터 — 볼륨, 바인드 마운트, tmpfs

> **🎮 게임 서버 개발자에게** — 게임 DB 파일, 서버 로그, 세이브 데이터를 "어느 디스크 어느 경로에 둘지" 정하던 결정이 이 장의 주제입니다. 결정적으로 다른 점은 컨테이너 안의 파일시스템은 **컨테이너를 지우는 순간 통째로 사라지는 임시 공간**이라는 것입니다. 남겨야 할 데이터는 반드시 컨테이너 바깥(마운트)에 두어야 하고, 어떤 마운트를 고르느냐가 곧 "그 데이터가 언제 사라지는가"를 결정합니다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 개발 서버에서 MySQL/PostgreSQL 컨테이너를 새 버전으로 교체했더니 캐릭터·계정 데이터가 전부 사라졌다.
> - 개발 중 소스를 고쳐도 컨테이너 안 서버에 반영되지 않거나, 반대로 바인드 마운트한 폴더에서 권한 오류가 난다.
> - 인증서·토큰처럼 디스크에 흔적을 남기면 안 되는 파일을 컨테이너에 잠깐 줘야 한다.

## 코어 — 이것만은 100%

> **한 문장:** 컨테이너의 쓰기 레이어는 컨테이너와 함께 사라지므로, 남겨야 할 데이터는 레이어 밖에 마운트하며, 생명주기에 따라 볼륨(Docker 관리, 컨테이너와 독립)·바인드 마운트(호스트 경로 그대로)·tmpfs(메모리, 종료 시 소멸)를 고르고, 데이터가 실제로 어디 있는지는 볼륨 드라이버가 책임진다.

1. **쓰기 레이어는 휘발성** — 이미지 레이어는 읽기 전용, 컨테이너가 쓴 내용은 쓰기 레이어(upperdir)에 남고 컨테이너 삭제 시 함께 사라진다. 지속 데이터는 레이어 **밖**에 마운트한다.
2. **마운트 3종 = 생명주기 선택** — 볼륨(Docker 관리, `docker volume rm`까지 유지, DB 데이터), 바인드 마운트(호스트 경로 그대로, 호스트 권한·SELinux 문제 상속, 소스 실시간 반영), tmpfs(메모리, 종료 즉시 소멸, 비밀값).
3. **컨테이너는 마운트 지점만 안다** — 볼륨 드라이버 플러그인으로 NFS·클라우드 스토리지도 같은 `-v` 문법으로 쓰고, 데이터 위치는 드라이버가 책임진다. 쿠버네티스도 같은 원리다.

**이 장의 학습 목표** (원래 "이 장에서 배우는 것")

- 컨테이너 파일시스템 변경이 왜 사라지는지, 그래서 왜 별도 마운트가 필요한지 이해한다.
- 볼륨(named volume), 바인드 마운트, tmpfs의 차이와 용도를 구분한다.
- 볼륨 드라이버 플러그인이 무엇인지 개념을 안다.
- 세 가지 방식을 직접 실행해 저장 위치 차이를 확인한다.

## 코어 1. 쓰기 레이어는 휘발성이다

### 1.1 왜 별도 마운트가 필요한가

**한 줄 요약:** 쓰기 레이어는 컨테이너의 생명주기와 함께하므로, 재시작·교체에도 살아남아야 할 데이터는 레이어 구조 밖에 둔다.

[8장](08-이미지-레이어-레지스트리-OCI.md)에서 본 것처럼 이미지 레이어는 읽기 전용이고, 컨테이너의 쓰기 레이어(upperdir)는 **컨테이너의 생명주기와 함께한다.** 컨테이너를 지우면 쓰기 레이어도 함께 사라진다.

```
컨테이너 안에서 쓴 파일 ──→ 쓰기 레이어 ──→ 컨테이너 삭제 시 함께 사라짐
컨테이너 안에서 쓴 파일 ──→ 마운트된 위치 ──→ 컨테이너와 무관하게 남음 (볼륨/바인드)
```

컨테이너를 재시작하거나 교체해도 살아남아야 하는 데이터(예: 데이터베이스 파일)는 이 레이어 구조 **밖**에 두어야 한다. Docker는 세 가지 마운트 방식을 제공한다.

## 코어 2. 마운트 3종 = 생명주기 선택

### 2.1 세 가지 방식 비교

**한 줄 요약:** 누가 관리하나(Docker·호스트·메모리)와 언제 사라지나(`rm`할 때·호스트를 따라·종료 즉시)로 고른다.

| 방식 | 저장 위치 | 생명주기 | 주 용도 |
|---|---|---|---|
| named volume (볼륨) | `/var/lib/docker/volumes/<이름>/_data` (또는 볼륨 드라이버가 관리하는 위치) | `docker volume rm`할 때까지 유지, 컨테이너 삭제와 무관 | 데이터베이스 파일 등 컨테이너와 독립적으로 지속되어야 하는 데이터 |
| bind mount | 호스트의 임의 경로(사용자가 직접 지정) | 호스트 파일시스템의 생명주기를 그대로 따름 | 소스 코드 실시간 반영, 호스트 설정 파일 주입 |
| tmpfs mount | 호스트 디스크가 아닌 메모리 | 컨테이너가 멈추면 즉시 소멸 | 비밀값 등 디스크에 남기면 안 되는 임시 데이터 |

#### 볼륨 (named volume)

Docker(또는 containerd)가 직접 생명주기를 관리하는 저장 단위다. 컨테이너를 삭제해도 남아 있다(명시적으로 `docker volume rm`할 때까지 유지). 볼륨 드라이버 플러그인을 통해 로컬 디스크뿐 아니라 NFS, 클라우드 블록 스토리지 같은 외부 스토리지와도 연결할 수 있다(3.1).

#### 바인드 마운트

호스트의 특정 경로를 그대로 컨테이너 안에 노출한다. Docker가 그 내용의 생명주기에 관여하지 않으며, **호스트 쪽 권한·SELinux 라벨 문제를 그대로 물려받는다**는 점에 주의해야 한다. 개발 중 소스 코드를 컨테이너에 즉시 반영할 때 편리하다.

#### tmpfs 마운트

디스크에 쓰이지 않는 메모리 기반이어서 컨테이너가 종료되는 순간 내용이 완전히 사라진다. 런타임에만 필요한 토큰 파일 같은 민감 정보를 짧게 다룰 때 쓴다.

### 2.2 직접 비교해 보기

**한 줄 요약:** 세 방식을 한 컨테이너에 동시에 마운트해 파일을 쓰고, 컨테이너가 사라진 뒤 어디에 남는지 확인한다.

```bash
# 1. 현재 저장 드라이버 확인
docker info --format 'Driver: {{.Driver}}'

# 2. 세 방식을 한 번에 마운트하고 각각 파일을 써 보기
docker volume create demo-vol
docker run --rm \
  -v demo-vol:/data/volume \
  -v "$(pwd)":/data/bind \
  --tmpfs /data/tmpfs \
  alpine sh -c 'echo vol > /data/volume/f.txt; echo bind > /data/bind/f.txt; echo tmp > /data/tmpfs/f.txt'

# 3. 컨테이너가 이미 사라진 뒤 호스트에서 확인
ls "$(docker volume inspect demo-vol --format '{{.Mountpoint}}')"   # f.txt 있음 (볼륨)
ls ./f.txt                                                          # 있음 (바인드 마운트)
# tmpfs에 쓴 파일은 어디에도 없음
```

결과를 정리하면 다음과 같다.

| 쓴 위치 | 컨테이너 종료 후 |
|---|---|
| named volume | 볼륨 마운트포인트에 남음 |
| bind mount | 호스트의 지정 경로(현재 디렉터리)에 남음 |
| tmpfs | 완전히 사라짐 |

### 2.3 `-v` 문법의 함정과 정리 명령

**한 줄 요약:** 콜론 왼쪽이 이름이면 볼륨, 경로면 바인드 마운트이고, 볼륨은 정리 명령으로 함께 지워질 수 있다.

> **[보충]** 위 예시처럼 `-v`의 콜론 왼쪽이 이름(`demo-vol`)이면 named volume, 경로(`/`나 `./`, `$(pwd)`로 시작)이면 바인드 마운트로 해석된다. 이름을 잘못 쓰면 의도와 달리 빈 볼륨이 새로 만들어질 수 있으므로, 헷갈리면 `docker inspect <컨테이너>`의 `Mounts` 항목에서 `Type`(`volume`/`bind`)을 확인한다. 데이터를 남기는 볼륨은 `docker compose down -v`, `docker volume prune` 같은 정리 명령으로 함께 지워질 수 있다는 점도 기억해 두자([9장](09-Dockerfile과-이미지-빌드.md), [12장](12-Docker-Compose와-컨테이너-런타임-계보.md)).

## 코어 3. 컨테이너는 마운트 지점만 안다

### 3.1 볼륨 드라이버 플러그인

**한 줄 요약:** 기본 `local` 드라이버 대신 플러그인을 쓰면 원격·클라우드 스토리지도 같은 `-v` 마운트로 쓸 수 있다.

기본 `local` 드라이버는 호스트 디스크에 볼륨 데이터를 저장한다. 여러 호스트가 같은 데이터를 공유하거나 클라우드 블록 스토리지를 쓰려면 **볼륨 드라이버 플러그인**을 설치해 쓴다. 플러그인은 `Create`, `Mount`, `Path`, `Unmount`, `Remove` 같은 표준 동작을 구현하며, `docker plugin install`로 설치한 뒤 `docker volume create --driver <플러그인 이름>`으로 사용한다.

```bash
docker plugin install --grant-all-permissions vieux/sshfs
docker volume create --driver vieux/sshfs \
  --opt sshcmd=user@remote-host:/data \
  --opt password=... \
  remote-vol
```

컨테이너 입장에서는 여전히 평범한 `-v remote-vol:/data` 마운트이고, 실제 데이터는 원격 호스트나 외부 스토리지에 놓인다. 원칙은 같다. **컨테이너는 마운트 지점만 알고, 그 뒤에 데이터가 어디 있는지는 드라이버가 책임진다.**

> **[보충]** 위 예시의 `password=...`처럼 비밀번호를 명령에 직접 쓰는 방식은 개념을 보이기 위한 예시일 뿐이다.

### 3.2 쿠버네티스와의 연결

**한 줄 요약:** 쿠버네티스도 "컨테이너 파일시스템은 휘발성, 데이터는 밖의 저장소를 마운트"라는 같은 원리를 따른다.

> **[보충]** 쿠버네티스에서도 "컨테이너 파일시스템은 휘발성이고, 데이터를 남기려면 그 밖의 저장소를 마운트한다"는 같은 원리가 적용된다. 구체적인 방법은 이 책의 [24장](../4부-노출-데이터-운영/24-스토리지.md)에서 다룬다.

## 실무 적용

### 체크리스트

- [ ] 컨테이너의 쓰기 레이어는 컨테이너와 함께 사라지므로, 지속해야 하는 데이터는 레이어 밖에 마운트한다.
- [ ] 볼륨은 Docker가 관리하며 컨테이너와 독립적으로 유지되고, 바인드 마운트는 호스트 경로를 그대로 노출하며, tmpfs는 메모리에만 존재해 컨테이너 종료 시 사라진다는 차이로 방식을 고른다.
- [ ] DB 데이터 디렉터리는 named volume, 개발 중 소스 실시간 반영·설정 파일 주입은 바인드 마운트, 디스크에 남기면 안 되는 토큰은 tmpfs.
- [ ] 바인드 마운트는 호스트 권한/SELinux 문제를 물려받는다는 것을 기억한다.
- [ ] `-v` 왼쪽이 이름인지 경로인지 확인하고, 애매하면 `docker inspect`의 `Mounts.Type`을 본다.
- [ ] `docker compose down -v`, `docker volume prune`, `docker system prune --volumes`는 볼륨 데이터까지 지운다.
- [ ] 볼륨 드라이버 플러그인으로 NFS, 클라우드 스토리지 같은 외부 저장소도 같은 `-v` 문법으로 쓸 수 있다. 플러그인 옵션에 비밀번호를 직접 쓰는 것은 예시일 뿐이다.

### 시나리오로 확인하기

1. **상황:** 개발 서버에서 `docker run -d --name db postgres:16`으로 띄운 DB를 쓰다가, 이미지 버전을 올리려고 `docker rm -f db` 후 새로 띄웠더니 테스트 계정·캐릭터 데이터가 전부 사라졌다.
   **질문:** 데이터는 어디에 있었고, 어떻게 했어야 하나?

   <details markdown="1"><summary>답 확인</summary>

   마운트 없이 띄웠으므로 DB 파일은 컨테이너의 쓰기 레이어(upperdir)에 있었고, 쓰기 레이어는 컨테이너 삭제 시 함께 사라진다. DB 데이터 디렉터리를 named volume(예: `-v db-data:/var/lib/postgresql/data`)으로 마운트하면 컨테이너를 지우고 다시 만들어도 `docker volume rm`할 때까지 데이터가 남는다. → 코어 1, 코어 2

   </details>

2. **상황:** `docker run -v data:/app/data ...`로 호스트의 `./data` 폴더를 공유하려 했는데, 호스트의 `./data`에 아무 파일도 생기지 않고 컨테이너 안은 빈 폴더로 시작한다.
   **질문:** 무슨 일이 일어났나?

   <details markdown="1"><summary>답 확인</summary>

   콜론 왼쪽이 경로(`./data`, `/...`, `$(pwd)`)가 아니라 이름(`data`)이라 named volume으로 해석되었고, `data`라는 빈 볼륨이 새로 만들어졌다. 바인드 마운트를 원하면 `-v ./data:/app/data` 또는 `-v "$(pwd)/data":/app/data`처럼 경로로 쓰고, `docker inspect`의 `Mounts` 항목 `Type`이 `bind`인지 확인한다. → 코어 2 (2.3)

   </details>

3. **상황:** 개발 환경 정리 스크립트에 `docker compose down -v`와 `docker volume prune`을 넣었더니, 팀원이 며칠 걸려 넣어 둔 로컬 DB 테스트 데이터가 날아갔다.
   **질문:** 볼륨이 "컨테이너와 독립적으로 유지된다"는데 왜 사라졌나?

   <details markdown="1"><summary>답 확인</summary>

   볼륨은 컨테이너 삭제와는 무관하지만, `docker compose down -v`, `docker volume prune` 같은 정리 명령은 볼륨까지 지운다. "영구 보관"이 아니라 "명시적으로 지울 때까지 유지"다. 정리 스크립트에서는 `-v`/`prune`을 분리하거나 신중히 쓴다. → 코어 2 (2.3)

   </details>

4. **상황:** 게임 서버 두 대(서로 다른 호스트)가 같은 맵 리소스 데이터를 공유해야 한다. 기본 `-v resources:/data`로는 각 호스트에 따로 볼륨이 생긴다.
   **질문:** 컨테이너 쪽 설정을 크게 바꾸지 않고 공유하려면?

   <details markdown="1"><summary>답 확인</summary>

   기본 `local` 드라이버는 호스트 디스크에 저장하므로 호스트마다 따로다. 볼륨 드라이버 플러그인(예: `docker plugin install vieux/sshfs` 후 `docker volume create --driver vieux/sshfs ...`)으로 NFS·원격 호스트·클라우드 스토리지에 연결하면, 컨테이너는 여전히 평범한 `-v remote-vol:/data` 마운트를 쓰고 데이터 위치는 드라이버가 책임진다. → 코어 3 (3.1)

   </details>

### 2. 인출 질문

1. 데이터베이스 컨테이너의 데이터 디렉터리에는 볼륨, 바인드 마운트, tmpfs 중 무엇이 적합하고 그 이유는?

   <details markdown="1"><summary>답 확인</summary>

   볼륨(named volume)이다. Docker가 생명주기를 관리하고 컨테이너를 삭제·교체해도 `docker volume rm`할 때까지 유지되므로, 컨테이너와 독립적으로 지속되어야 하는 DB 파일에 맞다. tmpfs는 종료 시 사라지고, 바인드 마운트는 호스트 권한·SELinux 문제를 물려받는다. → 코어 2 (2.1)

   </details>

2. 호스트 소스 코드를 컨테이너에 실시간 반영하고 싶을 때 쓰는 방식은?

   <details markdown="1"><summary>답 확인</summary>

   바인드 마운트다. 호스트의 특정 경로를 그대로 컨테이너 안에 노출하므로 호스트에서 고친 코드가 즉시 보인다. 단, Docker가 그 내용의 생명주기에 관여하지 않고 호스트 쪽 권한·SELinux 라벨 문제를 그대로 물려받는다. → 코어 2 (2.1)

   </details>

3. tmpfs에 쓴 파일은 컨테이너가 멈추면 어떻게 되는가?

   <details markdown="1"><summary>답 확인</summary>

   즉시 완전히 사라진다. 호스트 디스크가 아니라 메모리에만 존재하므로, 런타임에만 필요한 토큰 파일처럼 디스크에 남기면 안 되는 민감 정보를 짧게 다룰 때 쓴다. 2.2 실습에서도 tmpfs에 쓴 파일은 어디에도 남지 않는다. → 코어 2 (2.1, 2.2)

   </details>

4. 왜 컨테이너 안에서 쓴 데이터는 컨테이너를 지우면 사라지는가?

   <details markdown="1"><summary>답 확인</summary>

   이미지 레이어는 읽기 전용이고, 컨테이너가 쓴 내용은 쓰기 레이어(upperdir)에 기록되는데 이 레이어는 컨테이너의 생명주기와 함께하기 때문이다. 살아남아야 하는 데이터는 레이어 구조 **밖**(마운트된 위치)에 두어야 한다. → 코어 1 ([8장](08-이미지-레이어-레지스트리-OCI.md) overlayfs와 연결)

   </details>

5. `-v` 옵션에서 named volume과 바인드 마운트는 어떻게 구분되며, 실수하면 어떤 일이 생기는가?

   <details markdown="1"><summary>답 확인</summary>

   콜론 왼쪽이 이름(`demo-vol`)이면 named volume, 경로(`/`, `./`, `$(pwd)`로 시작)이면 바인드 마운트로 해석된다. 이름을 잘못 쓰면 의도와 달리 빈 볼륨이 새로 만들어질 수 있으므로, `docker inspect`의 `Mounts` 항목에서 `Type`(`volume`/`bind`)을 확인한다. → 코어 2 (2.3 [보충])

   </details>

6. 볼륨 드라이버 플러그인을 쓰면 컨테이너 입장에서 무엇이 달라지는가?

   <details markdown="1"><summary>답 확인</summary>

   달라지는 것이 없다. 컨테이너에는 여전히 평범한 `-v remote-vol:/data` 마운트이고, 실제 데이터는 원격 호스트나 NFS·클라우드 블록 스토리지에 놓인다. 플러그인이 `Create`, `Mount`, `Path`, `Unmount`, `Remove` 같은 표준 동작을 구현해 데이터 위치를 책임진다. → 코어 3 (3.1)

   </details>

### 3. 기억 고리

- **C++ 유추:** 쓰기 레이어 ≈ 서버 설치 폴더에 직접 쓰는 로그·세이브 파일. ⚠️ 컨테이너 세계에서는 "재설치(컨테이너 교체)"가 일상이라, 그 폴더는 교체 때마다 통째로 사라진다.
- **C++ 유추:** 볼륨 드라이버 ≈ 추상 인터페이스 뒤의 저장소 구현 교체. ⚠️ 가상 함수가 아니라 별도로 설치하는 플러그인이고, 드라이버는 볼륨 생성 시 정한다.
- **비유:** 세 가지 마운트 = 호텔 투숙객의 짐 보관. 볼륨 = 호텔 보관소(호텔이 관리, 퇴실해도 맡긴 짐은 남음), 바인드 마운트 = 내 집 창고 열쇠를 방에 가져온 것(내 창고 그대로, 창고의 자물쇠 규칙도 그대로), tmpfs = 방 안 금고(체크아웃하면 비워짐). ⚠️ 비유가 깨지는 지점: tmpfs는 "비워지는" 것이 아니라 메모리라서 처음부터 디스크에 존재하지 않고, 볼륨은 `prune` 같은 정리 명령으로 함께 지워질 수 있어 "영구 보관"은 아니다.
- **묶음(3의 법칙):** 마운트 3종(볼륨·바인드·tmpfs)을 "누가 관리하나(Docker·호스트·메모리)"와 "언제 사라지나(rm할 때·호스트 따라·종료 즉시)" 두 기준으로 묶기.
- **대칭·순서:** 레이어 안(휘발) ↔ 레이어 밖(지속). 볼륨(Docker가 생명주기 관리) ↔ 바인드(Docker가 관여 안 함). 사라지는 시점 순: tmpfs(컨테이너가 멈출 때) → 쓰기 레이어(컨테이너를 삭제할 때) → 볼륨(`docker volume rm`할 때), 바인드는 호스트 파일시스템을 따른다.
