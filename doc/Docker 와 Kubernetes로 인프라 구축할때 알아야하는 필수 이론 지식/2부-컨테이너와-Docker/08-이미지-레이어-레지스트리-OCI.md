# 8장. 이미지, 레이어, 레지스트리, OCI 표준

> **🎮 게임 서버 개발자에게** — 서버 빌드 산출물(실행 파일 + 설정 + 리소스)을 패키지로 묶어 배포하던 일을 이미지가 대신한다. 다른 점은 이미지가 통짜 파일이 아니라 **변경분 레이어를 쌓은 것**이라 공통 부분은 한 벌만 저장·전송되고, 실행 중인 컨테이너의 파일 변경은 `fork()` 후 메모리 페이지처럼 copy-on-write로 따로 기록됐다가 컨테이너를 지우면 사라진다는 점이다. 이미지·실행·배포 방식은 패킷 프로토콜 명세처럼 OCI 표준으로 정해져 있어서, 만드는 도구와 돌리는 도구가 달라도 된다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 핫픽스를 `myserver:latest`로 다시 올렸는데 일부 노드는 옛 버전을 돌리고 있을 때
> - 컨테이너 안에 저장하던 리플레이·로그 파일이 재배포 후 통째로 사라졌을 때
> - Docker로 빌드한 이미지를 Docker가 없는 쿠버네티스 노드나 ARM 노드에서 돌려야 할 때

## 코어 — 이것만은 100%

> **한 문장:** 이미지는 내용 해시로 식별되는 읽기 전용 레이어의 스택이고, 컨테이너는 overlayfs로 그 위에 휘발성 쓰기 레이어 하나를 얹어 copy-on-write로 실행되며, OCI 세 스펙이 이 포맷·실행·배포 방식을 표준화해 도구를 자유롭게 바꿔 끼울 수 있다.

1. **불변 레이어 스택과 내용 주소화** — 이미지는 순서 있는 읽기 전용 레이어(변경분) 스택이다. 레이어 공유와 빌드 캐시가 가능하고, 블롭은 다이제스트(내용 해시)로 저장되어 같은 내용은 한 벌만 존재한다.
2. **휘발성 쓰기 레이어(overlayfs CoW)** — lowerdir(이미지) + upperdir(쓰기 레이어) → merged(`/`). 수정은 upperdir로 복사 후 수정(CoW), 삭제는 whiteout. 컨테이너를 지우면 upperdir도 사라지므로 데이터는 볼륨으로 뺀다.
3. **태그는 이름표, 다이제스트는 내용** — 이미지 참조는 `호스트/리포지토리:태그`이고, `latest`는 약속이 아니라 기본 이름일 뿐이다. 프로덕션에서는 명시적 태그나 다이제스트로 고정한다.
4. **OCI: 포맷·실행·배포의 표준** — Image(구조), Runtime(실행 방법, runc가 참조 구현), Distribution(레지스트리 HTTP API) 세 스펙이 구현이 아니라 인터페이스만 정한다. 런타임은 이미지가 아니라 번들(`config.json` + `rootfs`)을 실행한다.

**이 장에서 배우는 것**

- 컨테이너 이미지가 "읽기 전용 레이어의 스택"이라는 것과 그 이점(공유, 캐시)을 이해한다. → 코어 1
- overlayfs의 lowerdir/upperdir/merged와 copy-on-write를 개념적으로 이해한다. → 코어 2
- 레지스트리와 이미지 이름 형식(호스트/리포지토리:태그, 다이제스트)을 읽을 수 있다. → 코어 3
- OCI의 세 가지 스펙(Image, Runtime, Distribution)이 무엇이고 왜 중요한지 안다. → 코어 4

|---|---|---|---|
| 증분 빌드에서 바뀌지 않은 오브젝트 파일 재사용 | 레이어 빌드 캐시 | 변하지 않은 결과물은 다시 만들지 않는다 | 레이어는 순서대로 쌓인 스택이라, 앞쪽 레이어가 바뀌면 그 뒤 레이어도 다시 만든다. 자주 바뀌는 것을 뒤에 둔다 |

| 버전 태그(`v1.2.3`) vs 빌드에 박힌 커밋 해시 | 이미지 태그 vs 다이제스트 | 사람이 읽는 이름과 내용을 고정하는 식별자를 구분한다 | 태그(특히 `latest`)는 다른 이미지로 옮겨 붙을 수 있다. 다이제스트는 내용의 해시라 변하지 않고, 내용이 같으면 서로 다른 이미지의 레이어도 같은 값이 된다 |
| 클라이언트와 서버가 지키는 패킷 프로토콜 명세 | OCI 스펙 | 포맷과 인터페이스만 맞으면 구현(언어·벤더)이 달라도 서로 통한다 | 하나가 아니라 Image·Runtime·Distribution 세 스펙으로 나뉘어, 빌드·실행·배포 도구를 각각 바꿔 끼울 수 있다 |

## 코어 1. 불변 레이어 스택과 내용 주소화

### 1.1 이미지는 읽기 전용 레이어의 스택

**한 줄 요약:** 이미지는 Dockerfile 명령마다 기록된 변경분 레이어의 스택이고, 원본 레이어는 절대 수정되지 않는다.

컨테이너 이미지는 하나의 거대한 스냅샷이 아니라, **순서가 있는 여러 겹의 변경분(diff)** 이다. Dockerfile 명령을 거칠 때마다 직전 상태와 비교한 파일시스템 변경 사항이 새 레이어로 기록된다.

```dockerfile
FROM python:3.12-slim                  # 레이어 1: 베이스 이미지
WORKDIR /app                           # (메타데이터만, 레이어 없음)
COPY requirements.txt .                # 레이어 2: 의존성 목록
RUN pip install -r requirements.txt    # 레이어 3: 설치된 패키지들
COPY . .                               # 레이어 4: 애플리케이션 코드
CMD ["python", "app.py"]               # (메타데이터만)
```

```
        ┌──────────────────────────────┐
쓰기 →  │  컨테이너 레이어 (읽기/쓰기)     │  ← 컨테이너 실행 시에만 생성
        ├──────────────────────────────┤
        │  레이어 4: 앱 코드             │ ┐
        │  레이어 3: pip 패키지          │ │ 이미지 (읽기 전용, 불변)
        │  레이어 2: requirements.txt   │ │
        │  레이어 1: python:3.12-slim   │ ┘
        └──────────────────────────────┘
```

이 구조의 이점은 두 가지다.

1. **레이어 공유**: 같은 베이스 이미지를 쓰는 서비스가 20개여도 `python:3.12-slim` 레이어는 호스트에 한 벌만 저장된다. 각 이미지는 자기 고유 레이어만 추가로 차지한다.
2. **빌드 캐시**: 앱 코드만 바뀌면 레이어 1&#126;3은 캐시를 재사용하고 레이어 4만 다시 만든다. ([9장](09-Dockerfile과-이미지-빌드.md)에서 자세히 다룬다.)

그리고 컨테이너가 실행 중 파일을 바꿔도 그 변경은 별도의 **쓰기 가능한 레이어**에만 기록되고 원본 이미지 레이어는 절대 수정되지 않는다. 컨테이너를 지워도 이미지가 멀쩡하고, 같은 이미지로 컨테이너를 여러 개 띄워도 서로 간섭하지 않는 이유다. (→ 코어 2)

### 1.2 내용 주소화 저장과 레이어 공유

**한 줄 요약:** 블롭은 내용의 해시(다이제스트)로 저장되므로 같은 내용은 이름이 달라도 디스크에 한 벌만 있다.

containerd는 모든 블롭(레이어 tar, 이미지 config 등)을 파일 이름이 아니라 **내용의 해시(다이제스트, 예: `sha256:abcdef...`)** 로 식별하고 저장한다. 내용이 같으면 다이제스트도 같으므로, 서로 다른 이미지 이름이라도 레이어 내용이 같다면 디스크에는 한 벌만 저장된다.

- 이미지를 pull할 때 로그에 `Already exists`가 찍히는 레이어는 이미 로컬에 있어 다운로드를 건너뛴 것이다.
- 같은 베이스를 쓰는 이미지를 여러 개 받아도 디스크 사용량이 이미지 개수만큼 선형으로 늘지 않는다.
- 이미지를 지워도 다른 이미지가 참조하는 블롭은 남는다. 그래서 `docker image prune`이나 `docker system prune` 때 즉시 지워지는 레이어와 그렇지 않은 레이어가 갈린다.

```bash
docker system df      # 이미지/컨테이너/볼륨/빌드 캐시별 디스크 사용량 요약
```

## 코어 2. 휘발성 쓰기 레이어 (overlayfs CoW)

### 2.1 레이어를 하나로 보이게 하는 overlayfs

**한 줄 요약:** overlayfs는 lowerdir(이미지)과 upperdir(쓰기 레이어)를 merged로 합쳐 보여 주고, 수정은 copy-on-write, 삭제는 whiteout으로 처리한다.

여러 레이어를 하나의 파일시스템처럼 보이게 하는 기술이 **유니온 파일시스템**이며, 리눅스에서는 `overlayfs`가 사실상 표준이다. overlayfs 마운트는 네 디렉터리로 구성된다.

| 디렉터리 | 역할 |
|---|---|
| lowerdir | 읽기 전용 레이어 (이미지 레이어들) |
| upperdir | 쓰기 가능한 단일 레이어 (컨테이너가 만든 변경이 기록됨) |
| merged | 컨테이너가 `/`로 보는 통합 뷰 |
| workdir | overlayfs 내부 연산용 작업 디렉터리 (직접 다룰 일 없음) |

```
┌─────────────────────────────────────┐
│  merged (컨테이너가 보는 /)           │
└─────────────────────────────────────┘
        ▲                  ▲
┌───────┴────────┐  ┌──────┴──────────────────┐
│ upperdir       │  │ lowerdir (읽기 전용)      │
│ (쓰기 가능)     │  │ 레이어 1 + 2 + 3 ...     │
└────────────────┘  └─────────────────────────┘
```

이미지 레이어에 있던 파일을 컨테이너 안에서 수정하면, overlayfs는 먼저 그 파일을 upperdir로 **복사한 뒤** 사본을 수정한다. 이를 **copy-on-write(CoW)** 라고 하며, 같은 lowerdir을 공유하는 다른 컨테이너에는 영향이 없다. 파일을 삭제해도 lowerdir의 파일이 지워지는 것이 아니라 upperdir에 "지워졌다"는 표시(whiteout)를 남긴다.

**그래서 컨테이너의 파일시스템 변경은 휘발성이다.** 컨테이너를 삭제하면 upperdir이 사라진다. 데이터를 남기려면 이 구조 밖으로 나가야 하며, 이것이 [10장](10-컨테이너-데이터-볼륨-바인드마운트-tmpfs.md)의 볼륨이 필요한 이유다.

### 2.2 직접 확인하기와 Docker Engine v29의 기본값 전환

**한 줄 요약:** 컨테이너에서 만든 파일은 호스트의 `diff`(upperdir) 디렉터리에 나타난다. 단, v29 신규 설치는 containerd 이미지 스토어를 써서 경로가 다르다.

직접 확인해 볼 수 있다(전통적인 overlay2 저장 방식 기준).

```bash
docker run -d --name overlay-demo nginx:alpine
docker inspect --format '{{json .GraphDriver.Data}}' overlay-demo | python3 -m json.tool
# LowerDir, UpperDir, MergedDir, WorkDir 경로가 출력됨

docker exec overlay-demo sh -c 'echo hello > /tmp/marker.txt'
sudo cat /var/lib/docker/overlay2/$(docker inspect --format '{{.Id}}' overlay-demo)/diff/tmp/marker.txt
docker rm -f overlay-demo
```

컨테이너 안에서 만든 파일이 호스트의 평범한 디렉터리(`diff`, 곧 upperdir)에 나타나는 것을 보면 "컨테이너의 쓰기 레이어"라는 말이 추상적이지 않게 느껴진다.

단, **Docker Engine v29부터 신규 설치는 기본적으로 레거시 overlay2 그래프 드라이버 대신 containerd 이미지 스토어(스냅샷터)를 쓴다.** 이 경우 위 `/var/lib/docker/overlay2/...` 경로가 없고 `docker inspect`의 `GraphDriver` 항목 형식도 다르다. 기존 설치는 업그레이드해도 자동으로 전환되지 않는다. 어느 쪽인지는 먼저 확인한다.

```bash
docker info | grep -A2 'Storage Driver'
```

## 코어 3. 태그는 이름표, 다이제스트는 내용

### 3.1 레지스트리와 이미지 이름

**한 줄 요약:** 참조는 `호스트/리포지토리:태그`. 생략하면 `docker.io`와 `latest`이며, 프로덕션은 `latest` 대신 다이제스트 고정이 가장 강하다.

이미지는 **레지스트리**에 저장하고 주고받는다. 이미지 참조 형식은 다음과 같다.

```
registry.example.com:5000/team/myapp:1.2.3
└──────── 호스트 ────────┘└─ 리포지토리 ─┘└ 태그 ┘
```

- 레지스트리를 생략하면 Docker Hub(`docker.io`), 태그를 생략하면 `latest`로 간주된다.
- **프로덕션에서 `latest`를 쓰지 말 것.** `latest`는 "최신"이라는 약속이 아니라 그냥 기본 태그 이름이다. 같은 이름을 두 번 배포해도 다른 이미지가 실행될 수 있어 재현성이 깨진다.
- 더 강한 방법은 **다이제스트 고정**이다. 다이제스트는 내용의 해시라서 변하지 않는다.

```
myapp@sha256:5f2c9e...a31b
```

## 코어 4. OCI: 포맷·실행·배포의 표준

### 4.1 OCI 표준과 세 가지 스펙

**한 줄 요약:** 2015년 표준을 한 기업에서 떼어 내 만든 OCI가 Image·Runtime·Distribution 세 스펙으로 인터페이스와 포맷만 규정한다.

초기에는 "Docker 이미지"가 사실상의 표준이었지만, 표준이 한 기업의 프로젝트에 묶여 있으면 다른 벤더가 호환 도구를 만들거나 오케스트레이터가 런타임을 자유롭게 고르기 어렵다. 그래서 2015년 리눅스 파운데이션 산하에 **OCI(Open Container Initiative)** 가 만들어졌고, 컨테이너 실행 엔진의 핵심이던 코드가 분리·기부되어 오늘날의 `runc`가 되었다. OCI는 세 가지 스펙을 관리한다.

| 스펙 | 정하는 것 | 누가 구현·사용하나 |
|---|---|---|
| Image Spec | 이미지의 구조(레이어, 설정, 매니페스트) | 빌드·이미지 처리 도구 |
| Runtime Spec | 컨테이너를 생성·실행·종료하는 방법 (runc가 참조 구현) | runc 같은 저수준 런타임 |
| Distribution Spec | 레지스트리에 올리고 받는 HTTP API | 레지스트리, push/pull 클라이언트 |

세 스펙은 구현을 하나로 강제하지 않고 **인터페이스와 포맷만 규정**한다. 그래서 runc 대신 crun을, Docker Hub 대신 사설 레지스트리를, containerd 대신 CRI-O를 써도 이미지와 실행 방식의 근본 구조는 같다. Docker로 빌드한 이미지를 containerd로 실행하고, Podman으로 검사하고, 다른 레지스트리에 저장해도 문제가 없는 이유다.

### 4.2 OCI 이미지의 구성

**한 줄 요약:** 인덱스(아키텍처별) → 매니페스트 → config + 레이어. 클라이언트는 자기 아키텍처의 매니페스트만 골라 받는다.

| 객체 | 설명 |
|---|---|
| 이미지 매니페스트 | 이미지 config 참조 + 레이어들의 다이제스트 목록을 담은 JSON |
| 이미지 config | 기본 `Cmd`, `Entrypoint`, `Env`, `WorkingDir`, 노출 포트 등 실행 설정 |
| 레이어 | 파일시스템 변경분을 담은 tar 아카이브 (순서대로 겹쳐야 완전한 rootfs가 됨) |
| 이미지 인덱스 | 여러 아키텍처(amd64, arm64 등)의 매니페스트를 가리키는 상위 문서 |

```
이미지 인덱스 (선택)  : OS/CPU 아키텍처별 매니페스트 참조
  └─ 이미지 매니페스트
      ├─ config 참조 : 기본 실행 명령, 환경 변수, 작업 디렉터리 등
      └─ 레이어 참조들 : 파일시스템 변경분
```

멀티 아키텍처 이미지를 받으면 클라이언트는 먼저 인덱스를 읽고 **자기 아키텍처에 맞는 매니페스트**를 골라 그 레이어만 내려받는다. (구조를 이해하기 위한 논리적 그림이며 레지스트리에 이런 폴더가 있다는 뜻은 아니다.)

### 4.3 Docker 이미지 포맷과의 관계

**한 줄 요약:** OCI Image Spec은 Docker Image Manifest V2 Schema 2를 기반으로 해 구조가 거의 같고, 차이는 미디어 타입과 일부 확장 필드다.

과거 Docker는 자체 포맷(Docker Image Manifest V2, Schema 2)을 썼고, OCI Image Spec은 이를 기반으로 설계되어 구조가 거의 같다. 차이는 주로 미디어 타입 문자열과 일부 확장 필드에 있고, 최신 레지스트리와 빌드 도구는 둘을 사실상 동등하게 취급한다. 아주 오래된 도구가 OCI 미디어 타입을 인식하지 못해 문제가 생기면 이 차이를 먼저 의심해 볼 만하다.

### 4.4 Distribution Spec — 레지스트리 API (참고)

**한 줄 요약:** push/pull은 `/v2/` 아래 매니페스트·블롭 HTTP API다.

```text
GET  /v2/                              # API 버전 확인
GET  /v2/<name>/manifests/<reference>  # 매니페스트 조회 (태그 또는 다이제스트)
GET  /v2/<name>/blobs/<digest>         # 레이어·config 등 블롭 다운로드
POST /v2/<name>/blobs/uploads/         # 블롭 업로드 시작 (push)
PUT  /v2/<name>/manifests/<reference>  # 매니페스트 업로드 (push 마무리)
```

### 4.5 런타임은 이미지를 직접 읽지 못한다

**한 줄 요약:** runc는 번들(`config.json` + `rootfs/`)만 알고, containerd가 이미지를 번들로 바꿔 준다. 실제 실행 설정은 이미지 기본값에 Pod 명세가 더해져 만들어진다.

runc 같은 저수준 런타임은 이미지를 이해하지 못하고 **번들(bundle)** 만 안다. 번들은 `config.json`(실행 설정)과 루트 파일시스템(`rootfs/`)으로 이루어진 디렉터리다. containerd가 이미지를 받아 레이어를 풀고 rootfs를 준비하며 설정을 `config.json`으로 만든 뒤에야 runc를 호출한다. `config.json`의 `linux.namespaces`와 `linux.resources`가 [6장](06-컨테이너-격리-네임스페이스.md)의 네임스페이스와 [7장](07-자원-제어-cgroups.md)의 cgroup 한도를 선언하는 자리이고, runc는 이를 커널 호출로 옮기는 얇은 계층이다. 따라서 이미지 포맷이 바뀌어도 runc는 손댈 필요가 없다.

이미지 하나만으로 모든 운영 설정이 정해지지는 않는다. 쿠버네티스에서는 이미지의 기본값에 Pod 명세(환경 변수, 실행 명령, 메모리 제한, 마운트 등)를 더해 실제 실행 설정이 만들어진다(`kubernetes-qustion-book/01_기초/03_Docker_이미지에서_실행까지.md` 5절).

## 실무 적용

### 체크리스트

- [ ] 이미지는 읽기 전용 레이어의 스택이고, 컨테이너는 그 위에 쓰기 가능한 레이어 하나를 얹는다. 레이어 덕분에 디스크 공유와 빌드 캐시가 가능하다.
- [ ] overlayfs는 lowerdir(이미지)과 upperdir(쓰기 레이어)를 merged로 합쳐 보여 주며, 수정 시 copy-on-write가 일어난다. 컨테이너를 지우면 쓰기 레이어도 사라진다. 남겨야 할 데이터(로그, 리플레이, 세이브)는 볼륨으로 뺐는가?
- [ ] 블롭은 내용 해시(다이제스트)로 저장되어 같은 내용은 한 벌만 존재한다. 디스크 사용량은 `docker system df`로 확인한다.
- [ ] 이미지 참조는 `호스트/리포지토리:태그`이며, 프로덕션에서는 `latest` 대신 명시적 태그나 다이제스트를 쓴다.
- [ ] OCI는 Image, Runtime, Distribution 세 스펙으로 벤더 종속 없이 도구를 조합할 수 있게 한다. 런타임은 이미지가 아니라 번들(`config.json` + `rootfs`)을 실행한다.
- [ ] 실습 경로가 안 보이면 `docker info | grep -A2 'Storage Driver'`로 overlay2인지 containerd 이미지 스토어인지 먼저 확인했는가?

### 시나리오로 확인하기

1. **상황:** 접속 장애 핫픽스를 빌드해 `myserver:latest`로 다시 push하고 재배포했다. 그런데 일부 노드는 여전히 이전 빌드를 돌리고, 롤백하려 해도 "이전 latest"가 무엇이었는지 알 수 없다.
   **질문:** 무엇이 잘못됐고, 어떻게 배포해야 하나?

   <details markdown="1"><summary>답 확인</summary>

   `latest`는 "최신"이라는 약속이 아니라 그냥 기본 태그 이름이라, 같은 이름으로 배포해도 다른 이미지가 실행될 수 있어 재현성이 깨진다. 프로덕션에서는 `1.2.3` 같은 명시적 태그를 쓰고, 더 강하게는 `myserver@sha256:...`처럼 다이제스트로 고정한다. 다이제스트는 내용의 해시라 변하지 않는다. → 코어 3

   </details>

2. **상황:** 게임 서버가 컨테이너 안 `/app/replays`에 리플레이 파일을 저장해 왔다. 새 버전 배포로 컨테이너를 교체했더니 리플레이가 모두 사라졌다.
   **질문:** 왜 사라졌고, 어떻게 해야 했나?

   <details markdown="1"><summary>답 확인</summary>

   컨테이너가 쓴 파일은 overlayfs의 upperdir(쓰기 레이어)에만 기록되고, 컨테이너를 삭제하면 upperdir도 사라진다. 컨테이너의 파일시스템 변경은 휘발성이다. 남겨야 할 데이터는 이 구조 밖, 즉 볼륨([10장](10-컨테이너-데이터-볼륨-바인드마운트-tmpfs.md))으로 빼야 한다. → 코어 2

   </details>

3. **상황:** 같은 베이스 이미지 위에 로비·매치·채팅 등 서버 이미지 20개를 만들었다. 노드 디스크가 이미지 20벌만큼 필요할까 걱정이다.
   **질문:** 실제로는 어떤가?

   <details markdown="1"><summary>답 확인</summary>

   이미지는 레이어 스택이고 블롭은 내용 해시(다이제스트)로 저장된다. 같은 베이스 레이어는 호스트에 한 벌만 저장되고, 각 이미지는 자기 고유 레이어만 추가로 차지한다. pull 로그의 `Already exists`가 그 표시이며, 디스크 사용량은 이미지 개수만큼 선형으로 늘지 않는다. `docker system df`로 확인한다. → 코어 1

   </details>

4. **상황:** 비용 절감을 위해 arm64 노드를 섞었다. 같은 이미지 이름으로 배포했는데 amd64 노드와 arm64 노드 모두에서 잘 뜬다.
   **질문:** 이름 하나로 어떻게 아키텍처별 바이너리를 받는가?

   <details markdown="1"><summary>답 확인</summary>

   멀티 아키텍처 이미지는 이미지 인덱스가 아키텍처(amd64, arm64 등)별 매니페스트를 가리킨다. 클라이언트는 먼저 인덱스를 읽고 자기 아키텍처에 맞는 매니페스트를 골라 그 config와 레이어만 내려받는다. → 코어 4

   </details>

5. **상황:** 책의 overlayfs 실습을 따라 했는데 `/var/lib/docker/overlay2/.../diff` 경로가 없다.
   **질문:** 무엇을 의심해야 하나?

   <details markdown="1"><summary>답 확인</summary>

   Docker Engine v29부터 신규 설치는 레거시 overlay2 그래프 드라이버 대신 containerd 이미지 스토어(스냅샷터)를 기본으로 쓴다. 이 경우 해당 경로가 없고 `GraphDriver` 형식도 다르다. 기존 설치는 업그레이드해도 자동 전환되지 않는다. `docker info | grep -A2 'Storage Driver'`로 먼저 확인한다. → 코어 2

   </details>

### 2. 인출 질문

1. 같은 베이스 이미지를 쓰는 이미지 20개를 받아도 디스크가 20배 늘지 않는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   이미지는 레이어 스택이고, 블롭은 내용의 해시(다이제스트)로 저장된다. 내용이 같으면 다이제스트도 같아 베이스 레이어는 호스트에 한 벌만 저장되고, 각 이미지는 자기 고유 레이어만 추가로 차지한다. pull 로그의 `Already exists`가 그 표시다. → 코어 1 (1.1, 1.2)

   </details>

2. 컨테이너 안에서 파일을 수정한 뒤 컨테이너를 삭제하면 그 변경은 어떻게 되는가?

   <details markdown="1"><summary>답 확인</summary>

   수정은 overlayfs가 파일을 upperdir(쓰기 레이어)로 복사한 뒤 사본을 고치는 copy-on-write로 기록되고, 원본 이미지 레이어는 바뀌지 않는다. 컨테이너를 삭제하면 upperdir이 사라지므로 변경도 사라진다. 데이터를 남기려면 [10장](10-컨테이너-데이터-볼륨-바인드마운트-tmpfs.md)의 볼륨을 쓴다. → 코어 2 (2.1)

   </details>

3. `nginx`와 `nginx@sha256:...` 두 참조 중 재현성이 더 높은 것은 무엇이고, 이유는?

   <details markdown="1"><summary>답 확인</summary>

   `nginx@sha256:...`이다. `nginx`는 `docker.io`의 `latest` 태그로 해석되는데, `latest`는 "최신"이라는 약속이 아니라 그냥 기본 태그 이름이라 같은 이름으로 다른 이미지가 실행될 수 있다. 다이제스트는 내용의 해시라 변하지 않는다. → 코어 3 (3.1)

   </details>

4. 컨테이너에서 이미지에 있던 파일을 삭제하면 lowerdir의 파일은 어떻게 되는가?

   <details markdown="1"><summary>답 확인</summary>

   lowerdir의 파일은 지워지지 않는다. upperdir에 "지워졌다"는 표시(whiteout)를 남겨 merged 뷰에서 안 보이게 할 뿐이다. 그래서 같은 lowerdir을 공유하는 다른 컨테이너에는 영향이 없다. → 코어 2 (2.1)

   </details>

5. OCI는 왜 만들어졌고, 세 가지 스펙은 각각 무엇을 정하는가?

   <details markdown="1"><summary>답 확인</summary>

   표준이 한 기업 프로젝트(Docker)에 묶이면 다른 벤더가 호환 도구를 만들거나 오케스트레이터가 런타임을 고르기 어렵기 때문에 2015년 리눅스 파운데이션 산하에 만들어졌다. Image Spec은 이미지 구조, Runtime Spec은 컨테이너 생성·실행·종료 방법(runc가 참조 구현), Distribution Spec은 레지스트리 push/pull HTTP API를 정한다. 구현이 아니라 인터페이스와 포맷만 규정하므로 runc↔crun, containerd↔CRI-O 등을 바꿔 써도 된다. → 코어 4 (4.1)

   </details>

6. 멀티 아키텍처 이미지를 pull할 때 클라이언트는 어떤 순서로 무엇을 받는가?

   <details markdown="1"><summary>답 확인</summary>

   먼저 이미지 인덱스를 읽어 자기 아키텍처(amd64, arm64 등)에 맞는 매니페스트를 고르고, 그 매니페스트가 가리키는 config와 레이어만 내려받는다. → 코어 4 (4.2)

   </details>

7. runc가 이미지 포맷이 바뀌어도 손댈 필요가 없는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   runc는 이미지를 이해하지 못하고 번들(`config.json` + `rootfs/`)만 안다. containerd가 이미지를 받아 레이어를 풀고 rootfs와 `config.json`을 준비한 뒤 runc를 호출한다. `config.json`의 `linux.namespaces`와 `linux.resources`가 네임스페이스와 cgroup 한도를 선언하고, runc는 이를 커널 호출로 옮기는 얇은 계층이다. → 코어 4 (4.5)

   </details>

8. `/var/lib/docker/overlay2/.../diff` 경로로 실습했는데 경로가 없다면 무엇을 의심해야 하는가?

   <details markdown="1"><summary>답 확인</summary>

   Docker Engine v29부터 신규 설치는 레거시 overlay2 그래프 드라이버 대신 containerd 이미지 스토어(스냅샷터)를 기본으로 쓴다. 이 경우 해당 경로가 없고 `GraphDriver` 형식도 다르다. `docker info | grep -A2 'Storage Driver'`로 먼저 확인한다. → 코어 2 (2.2)

   </details>

### 3. 기억 고리

- **C++ 유추:** overlayfs CoW = `fork()` 뒤 공유 페이지에 쓰는 순간 사본을 만드는 copy-on-write. ⚠️ 깨지는 곳: 복사 단위가 페이지가 아니라 파일이라 큰 파일을 조금만 고쳐도 통째로 복사되고, 사본은 컨테이너를 지우면 함께 사라진다.
- **C++ 유추:** OCI = 클라이언트와 서버가 함께 지키는 패킷 프로토콜 명세. ⚠️ 깨지는 곳: 하나의 명세가 아니라 Image·Runtime·Distribution 세 스펙이라, 빌드·실행·배포 도구를 각각 바꿔 끼울 수 있다.
- **비유:** 이미지 레이어 + 컨테이너 레이어 = 원본 도면 위에 겹친 투명 트레이싱지. 원본 도면(이미지)은 모두가 함께 보고, 각자 자기 트레이싱지(upperdir)에만 그린다. 고치고 싶은 선은 트레이싱지에 옮겨 그린 뒤 고치고(CoW), 지우고 싶은 선은 위에 흰색으로 덮는다(whiteout). ⚠️ 비유가 깨지는 지점: overlayfs의 복사 단위는 선 하나가 아니라 **파일 전체**라서 큰 파일 수정은 비싸고, 트레이싱지는 컨테이너를 지우면 함께 버려진다.
- **비유:** 다이제스트 = 지문, 태그 = 이름표. 이름표(`latest`)는 다른 사람에게 옮겨 붙일 수 있지만 지문은 내용이 같아야만 같다. ⚠️ 비유가 깨지는 지점: 지문은 사람마다 고유하지만, 다이제스트는 내용이 같으면 서로 다른 이미지의 레이어라도 같아진다(그래서 한 벌만 저장).
- **묶음(3의 법칙):** OCI 3스펙(Image·Runtime·Distribution) / overlayfs 핵심 3디렉터리(lowerdir·upperdir·merged) / 이미지 참조 3부분(호스트·리포지토리·태그).
- **대칭·순서:** 읽기 전용(이미지, 불변) ↔ 쓰기 가능(컨테이너 레이어, 휘발). 태그(변할 수 있음) ↔ 다이제스트(불변). 순서: 인덱스 → 매니페스트 → config + 레이어 → (containerd) 번들 → runc.

- **거울 설명 (1분, 원고 없이):** "컨테이너를 지우면 안에서 만든 파일이 왜 사라지는가"를 overlayfs로 설명해 보세요. 말이 막히는 지점 = 지식의 구멍.
