# 5장. 컨테이너 격리 — 네임스페이스

## 이 장에서 배우는 것

- 네임스페이스가 "자원을 나누는 것"이 아니라 "다르게 보이게 하는 것"임을 이해한다.
- 주요 네임스페이스(PID, 네트워크, 마운트, UTS, IPC, 사용자)가 각각 무엇을 격리하는지 안다.
- `unshare`, `nsenter`, `/proc/<pid>/ns`로 네임스페이스를 직접 확인한다.
- `--net=host`, `--net=container:X` 같은 Docker 옵션이 "네임스페이스 공유"임을 이해한다.

---

## 5.1 네임스페이스란 무엇인가

컨테이너라는 특별한 커널 객체가 있는 것이 아니다. 컨테이너는 **일반 프로세스에 여러 네임스페이스를 조합해 씌운 것**이다.

리눅스 네임스페이스는 커널이 관리하는 전역 자원(프로세스 ID, 네트워크 인터페이스, 마운트 테이블 등)을 프로세스 그룹별로 **서로 다르게 "보이게"** 만드는 기능이다.

- 자원을 실제로 복제하거나 물리적으로 분할하는 것이 아니다. 컨테이너 10개는 여전히 같은 커널, 같은 CPU, 같은 물리 네트워크 인터페이스를 공유한다.
- 다만 컨테이너 안의 프로세스가 `ps`를 실행하면 자기 네임스페이스 안의 프로세스만, `ip addr`을 실행하면 자기 네트워크 네임스페이스의 인터페이스만 보인다.
- 네임스페이스는 커널에 질의한 결과를 걸러 주는 **렌즈**에 가깝다.

리눅스는 총 8가지 네임스페이스를 제공하며, `clone()`, `unshare()`, `setns()` 시스템 콜로 새로 만들거나 기존 것에 합류한다.

---

## 5.2 주요 네임스페이스

| 네임스페이스 | 격리 대상 | 컨테이너에서 보이는 모습 |
|---|---|---|
| PID | 프로세스 ID 공간 | 컨테이너의 첫 프로세스가 PID 1 |
| Network (net) | 네트워크 인터페이스, 라우팅, 방화벽 규칙, 포트 공간 | 자기만의 `lo`와 `eth0`(veth 한쪽 끝) |
| Mount (mnt) | 마운트 테이블 | `/`가 이미지 레이어를 합친 파일시스템으로 보임 |
| UTS | 호스트 이름, NIS 도메인 | `hostname`이 컨테이너 ID 앞자리(또는 `--hostname` 값) |
| IPC | System V IPC, POSIX 메시지 큐 | 컨테이너 간 IPC 키 충돌 없음 |
| User | UID/GID 매핑 | 컨테이너의 root가 호스트에서는 비특권 UID일 수 있음 |
| cgroup | cgroup 계층 뷰 | 자기 cgroup 하위 트리를 루트처럼 봄 |
| Time | 부팅 이후 경과 시간 클록 | 실무에서 가장 존재감이 적음 |

### PID 네임스페이스

새 PID 네임스페이스에서 처음 실행되는 프로세스는 그 안에서 **PID 1**이 된다. 컨테이너 안에서 `ps -ef`를 하면 엔트리포인트가 PID 1로 보이지만, 호스트에서는 같은 프로세스가 다른 PID를 가진다. PID는 네임스페이스마다 다르게 매핑되는 "뷰"다.

PID 1은 좀비 프로세스 회수와 시그널 처리에서 특별한 책임이 있다. 엔트리포인트가 자식 프로세스를 여럿 띄우면 좀비가 쌓일 수 있어, `tini` 같은 최소 init 프로그램을 PID 1로 두는 패턴이 쓰인다. Docker는 `docker run --init` 옵션으로 이를 켤 수 있다.

### 네트워크 네임스페이스

네트워크 인터페이스, 라우팅 테이블, 방화벽 규칙, 포트 바인딩 공간이 분리된다. 각 컨테이너는 기본적으로 자신만의 loopback(`lo`)과 가상 이더넷 인터페이스(veth pair의 한쪽 끝)를 가지며, 그래서 컨테이너마다 독립적으로 `0.0.0.0:80`을 바인딩할 수 있다. (10장에서 Docker 네트워크를 다룬다.)

### 마운트 네임스페이스

프로세스별로 독립적인 마운트 테이블을 제공한다. 컨테이너 안에서 `/`를 봤을 때 호스트의 루트가 아니라 이미지 레이어를 합친 파일시스템이 보이는 것은 이 네임스페이스와 `pivot_root`(또는 구형 `chroot`)의 조합으로 만들어진다.

### UTS, IPC 네임스페이스

- UTS는 호스트 이름을 격리한다. 컨테이너 안의 `hostname`이 호스트와 다른 이유다.
- IPC는 공유 메모리·세마포어·메시지 큐를 격리한다. 서로 다른 컨테이너가 같은 IPC 키를 써도 충돌하지 않는다.

### 사용자 네임스페이스

UID/GID 공간을 격리한다. 컨테이너 안에서 UID 0(root)인 프로세스가 호스트에서는 임의의 비특권 UID(예: 100000)로 매핑되게 할 수 있다. 컨테이너 탈출 취약점이 있더라도 호스트의 실제 root 권한을 얻지 못하게 하는 추가 방어선이 되고, rootless 컨테이너의 기반이 된다. 기본 `docker run`은 사용자 네임스페이스를 새로 만들지 않으며, `userns-remap` 설정이나 `--userns=` 옵션으로 활성화한다.

## 5.3 `/proc/<pid>/ns/`로 확인하기

각 프로세스의 네임스페이스는 `/proc/<pid>/ns/` 아래 심볼릭 링크로 보인다.

```bash
ls -l /proc/$$/ns/
```

```
cgroup -> 'cgroup:[4026531835]'
ipc    -> 'ipc:[4026531839]'
mnt    -> 'mnt:[4026531840]'
net    -> 'net:[4026531992]'
pid    -> 'pid:[4026531836]'
time   -> 'time:[4026531834]'
user   -> 'user:[4026531837]'
uts    -> 'uts:[4026531838]'
```

대괄호 안 숫자는 네임스페이스의 고유 식별자다. **두 프로세스의 번호가 같으면 같은 네임스페이스에 속한 것**이다.

## 5.4 직접 해 보기 (root 권한 필요)

### 새 PID 네임스페이스 만들기

```bash
sudo unshare --mount --pid --fork --mount-proc bash
ps -ef          # 자기 자신과 극소수 프로세스만 보임, bash가 PID 1
exit
```

`--mount-proc`는 새 PID 네임스페이스 기준으로 `/proc`를 다시 마운트해, `ps`가 정확한 결과를 보여 준다.

### 실행 중인 컨테이너의 네임스페이스에 들어가기 (`nsenter`)

```bash
docker run -d --name web nginx:latest
PID=$(docker inspect -f '{{.State.Pid}}' web)

sudo nsenter --target $PID --net -- ip addr     # 컨테이너의 네트워크 네임스페이스에서 실행
sudo nsenter --target $PID --mount -- ls /      # 컨테이너의 마운트 네임스페이스에서 실행
```

`nsenter`는 셸이 없는 이미지(예: distroless)처럼 컨테이너 안에 디버깅 도구가 없을 때, **호스트의 도구로 컨테이너의 네임스페이스 안을 살펴볼 수 있어** 실용적이다.

### 네트워크 네임스페이스 단독 관리

```bash
sudo ip netns add testns
sudo ip netns exec testns ip addr
sudo ip netns list
sudo ip netns delete testns
```

## 5.5 Docker가 네임스페이스를 조합하는 방식

`docker run`은 기본적으로 PID, 마운트, UTS, IPC, 네트워크(와 조건부로 cgroup) 네임스페이스를 새로 만든다. 사용자 네임스페이스와 타임 네임스페이스는 기본적으로 호스트와 공유한다.

Docker의 여러 옵션은 "이 네임스페이스는 새로 만들지 말고 다른 대상과 **공유**하라"는 지시로 이해하면 쉽다.

```bash
docker run --rm --net=host nginx:latest                  # 호스트와 네트워크 네임스페이스 공유
docker run -d --name app myapp:latest
docker run --rm --net=container:app busybox ip addr     # 다른 컨테이너 app과 네트워크 공유
docker run --rm --pid=host busybox ps -ef                # 호스트의 모든 프로세스가 보임 (디버깅용)
docker run --rm --ipc=host busybox ipcs                  # 호스트와 IPC 공유
```

`--net=container:app` 패턴은 **쿠버네티스 Pod 안에서 여러 컨테이너가 네트워크를 공유하는 구조와 같은 원리**다. Pod는 먼저 "pause 컨테이너"로 네트워크 네임스페이스를 만들어 두고, 같은 Pod의 나머지 컨테이너가 그 네임스페이스에 합류한다. 그래서 같은 Pod의 컨테이너끼리 `localhost`로 통신할 수 있다. (3부에서 다시 만난다.)

## 5.6 네임스페이스만으로는 부족하다

네임스페이스는 격리의 세 축 중 **가시성(무엇이 보이는가)** 만 담당한다.

| 축 | 담당 | 핵심 질문 |
|---|---|---|
| 가시성 | 네임스페이스 | 무엇이 보이는가 |
| 권한 | capabilities, seccomp | 무엇을 할 수 있는가 |
| 자원 | cgroups | 얼마나 쓸 수 있는가 |

- 네임스페이스는 커널 자체를 분리하지 않으므로 커널 취약점은 경계를 넘을 수 있다.
- "무엇이 보이는지"만 제한하고 "무엇을 할 수 있는지"는 제한하지 않는다. 위험한 동작을 막는 것은 capabilities(root 권한을 잘게 쪼갠 단위)와 seccomp(허용할 시스템 콜을 제한하는 필터)다.
- 자원 독점(noisy neighbor)을 막는 것은 다음 장의 cgroups다.
- 세 축이 함께 작동해야 격리가 완성되고, `--privileged`처럼 하나를 풀면 가장 약한 축이 전체 수준을 결정한다.

### capabilities — "무엇을 할 수 있는가"

전통적인 리눅스의 권한은 이분법이었다. root(UID 0)는 모든 것을 할 수 있고, 나머지는 거의 아무것도 못 한다. **capability**는 root의 권한을 40여 개 조각으로 나눈 것이다.

| capability | 허용하는 동작 |
|---|---|
| `CAP_NET_BIND_SERVICE` | 1024 미만 포트 바인딩 |
| `CAP_NET_ADMIN` | 네트워크 인터페이스·라우팅 설정 |
| `CAP_SYS_ADMIN` | 마운트 등 광범위한 관리 작업 (사실상 root와 유사, 위험) |
| `CAP_CHOWN` | 파일 소유자 변경 |
| `CAP_SYS_PTRACE` | 다른 프로세스 디버깅 |

컨테이너 런타임은 기본적으로 대부분의 capability를 **제거**한 채 컨테이너를 실행한다. 꼭 필요한 것만 골라 추가하고, 모든 capability를 주는 `--privileged`는 격리를 포기하는 것과 같으므로 프로덕션에서 쓰지 않는다.

```bash
docker run --rm --cap-add=NET_ADMIN alpine ip link set lo down && echo "성공"   # 특정 capability만 추가
docker run --rm --privileged alpine ...   # 모든 capability 부여 = 격리 포기 (프로덕션 금지)
```

쿠버네티스의 `securityContext.capabilities.drop: ["ALL"]`도 같은 메커니즘을 쓴다(24장). 컨테이너 안에서 root로 실행하지 않는 것(Dockerfile의 `USER`, 8장)과 함께 컨테이너 보안의 기본기다.

## 핵심 요약

- 네임스페이스는 커널 자원을 나누는 것이 아니라 프로세스마다 다른 "뷰"를 보여 주는 기능이며, 컨테이너는 프로세스에 네임스페이스를 씌운 것이다.
- 주요 네임스페이스: PID(프로세스), net(네트워크), mnt(마운트), UTS(호스트명), IPC, user(UID/GID).
- `/proc/<pid>/ns/`의 번호를 비교하면 같은 네임스페이스인지 알 수 있고, `unshare`로 만들고 `nsenter`로 들어간다.
- `--net=host`, `--net=container:X`, `--pid=host`, `--ipc=host`는 새로 만들지 않고 공유하라는 의미이며, 쿠버네티스 Pod의 네트워크 공유와 같은 원리다.
- 네임스페이스는 가시성만 담당하고, 권한은 capabilities/seccomp, 자원은 cgroups가 담당한다.
- 런타임은 대부분의 capability를 제거한 채 컨테이너를 실행한다. 필요한 것만 `--cap-add`로 더하고, `--privileged`는 쓰지 않는다.
