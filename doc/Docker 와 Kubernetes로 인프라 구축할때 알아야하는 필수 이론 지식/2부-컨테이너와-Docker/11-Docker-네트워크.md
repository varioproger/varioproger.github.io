# 11장. Docker 네트워크

> **🎮 게임 서버 개발자에게** — 게임 서버가 `bind()`/`listen()`한 포트로 클라이언트가 붙고, 서버끼리는 설정 파일의 IP로 접속하던 구조가 컨테이너 세계에서는 "컨테이너마다 독립된 네트워크 스택 + 가상 케이블(veth) + 가상 스위치(브리지) + 커널 NAT"로 바뀝니다. 결정적으로 다른 점은 컨테이너 안에서 80번을 `listen`해도 **호스트에서는 아무도 그 포트를 열지 않은 상태**라는 것입니다. 외부 접속은 `-p`가 만든 iptables DNAT 규칙이 목적지를 바꿔 줘야 들어오고, 서버끼리는 IP 대신 **컨테이너 이름**으로 찾습니다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 게임 서버 컨테이너가 같은 호스트의 Redis 컨테이너를 이름으로 못 찾는다(`--network` 없이 띄움).
> - 개발용 DB를 `-p 5432:5432`로 열고 `ufw`로 막았다고 믿었는데 외부에서 접속된다.
> - 클라이언트 접속이 `호스트IP:8080`으로 들어와 컨테이너의 80번까지 어떤 경로로 가는지 따져야 하는 장애 분석.

## 코어 — 이것만은 100%

> **한 문장:** 컨테이너는 veth pair로 호스트 브리지에 꽂혀 같은 브리지 안에서는 L2 스위칭으로, 밖으로는 라우팅 + MASQUERADE로 통신하고, 밖에서 들어오는 `-p` 트래픽은 PREROUTING의 DNAT로 컨테이너에 전달되며, 사용자 정의 브리지에서는 내장 DNS(127.0.0.11)로 네트워크 단위 이름 통신을 한다.

1. **사용자 정의 브리지를 쓴다** — 기본 브리지(`docker0`)는 이름 기반 자동 DNS가 없고 모든 컨테이너가 한 평평한 공간이다. 사용자 정의 브리지는 이름/별칭 통신과 네트워크 간 격리를 준다(Compose도 자동 생성).
2. **veth로 꽂고, 안은 스위칭·밖은 NAT** — veth pair 한쪽은 컨테이너 `eth0`, 다른 쪽은 호스트 브리지에 연결된다. 컨테이너 간은 L2 스위칭(NAT 없음), 외부로는 라우팅 + 아웃바운드 NAT(MASQUERADE, `POSTROUTING`).
3. **들어오는 길은 PREROUTING DNAT** — `-p`는 `DOCKER` 체인의 DNAT가 라우팅 결정 전에 목적지를 컨테이너 IP:포트로 바꾸고, 응답은 conntrack이 되돌린다. `docker-proxy`는 보완용이고, 게시 포트는 호스트 방화벽보다 Docker 규칙이 먼저다.
4. **이름은 127.0.0.11이 네트워크 단위로 푼다** — dockerd의 내장 DNS가 같은 네트워크의 컨테이너 이름·별칭·Compose 서비스 이름을 풀고, 외부 도메인은 업스트림으로 포워딩한다. `--link`는 레거시다.

**이 장의 학습 목표** (원래 "이 장에서 배우는 것")

- 기본 브리지(`docker0`)와 사용자 정의 브리지의 차이를 이해한다.
- veth pair가 컨테이너와 호스트 브리지를 어떻게 연결하는지 개념을 안다.
- 컨테이너 간 통신(스위칭)과 외부 통신(라우팅 + NAT)이 다르다는 것을 안다.
- 포트 매핑(`-p`)이 어떤 경로로 동작하는지 큰 그림을 이해한다.
- 내장 DNS(127.0.0.11)로 컨테이너 이름으로 통신하는 원리를 이해한다.

## 코어 1. 사용자 정의 브리지를 쓴다

### 1.1 기본 브리지와 사용자 정의 브리지

**한 줄 요약:** 겉보기엔 같은 리눅스 브리지지만, 사용자 정의 브리지만 이름 통신(자동 DNS)과 네트워크 간 격리를 준다.

Docker를 설치하면 `docker0`이라는 리눅스 브리지가 하나 만들어진다. `--network`를 지정하지 않은 컨테이너는 이 기본 브리지(`bridge`라는 이름의 기본 네트워크)에 연결된다. 반면 `docker network create`로 직접 만든 브리지를 **사용자 정의 브리지**라고 부른다. 겉보기엔 같은 리눅스 브리지지만 실무에 영향을 주는 차이가 있다.

| 구분 | 기본 브리지 (`docker0`) | 사용자 정의 브리지 |
|---|---|---|
| 이름으로 통신(자동 DNS) | 지원하지 않음 (`--link` 같은 레거시 방식이나 IP 직접 사용) | 컨테이너 이름/별칭으로 서로를 찾음 |
| 네트워크 간 격리 | 연결된 컨테이너가 모두 한 평평한 공간 | 서로 다른 네트워크의 컨테이너는 기본적으로 격리 (필요 시 `docker network connect`) |

그래서 실무에서는 **기본 브리지를 그대로 쓰지 말고 프로젝트마다 사용자 정의 브리지를 만들어 쓰라**고 권한다. Docker Compose가 프로젝트마다 전용 네트워크를 자동으로 만들어 주는 것도 같은 이유다([12장](12-Docker-Compose와-컨테이너-런타임-계보.md)).

```bash
docker network create mynet
docker run -d --name api --network mynet myapp:latest
docker run --rm --network mynet alpine ping -c1 api    # 컨테이너 이름 api로 통신
```

> **[보충]** 위 `ping` 줄은 이름 통신을 보여 주기 위해 이 책에서 구성한 예시이며, 원문에 있는 명령은 아니다.

## 코어 2. veth로 꽂고, 안은 스위칭·밖은 NAT

### 2.1 veth pair — 컨테이너와 호스트를 잇는 가상 케이블

**한 줄 요약:** veth pair의 한쪽 끝은 컨테이너 네임스페이스의 `eth0`, 다른 쪽은 호스트에 남아 브리지에 연결된다.

브리지 네트워크에서 컨테이너가 연결될 때 핵심은 **veth(virtual ethernet) pair**다. veth는 항상 쌍으로 생성되는 가상 인터페이스로, 한쪽 끝으로 들어간 패킷이 다른 끝으로 그대로 나온다. 마치 케이블로 연결된 것과 같다.

Docker는 veth pair를 만들어 **한쪽 끝은 컨테이너의 네트워크 네임스페이스로 옮기고**(컨테이너 안에서 `eth0`으로 보임), **다른 쪽 끝은 호스트에 남겨 브리지에 연결**한다.

```
[ 호스트 네트워크 네임스페이스 ]                [ 컨테이너 네트워크 네임스페이스 ]

   docker0 (브리지)
       │
       ├── vethXXXXXXX@if5  ◄──── veth pair ────►  eth0@if6      (컨테이너 1)
       │
       └── vethYYYYYYY@if7  ◄──── veth pair ────►  eth0@if8      (컨테이너 2)
```

직접 확인할 수 있다(앞 장처럼 `web`이라는 컨테이너가 떠 있다고 가정한다).

```bash
docker exec web ip link show eth0     # 예: 6: eth0@if7 ...  ← @if 뒤 숫자는 반대편 끝의 인덱스
ip link show type veth                # 호스트의 veth 목록
bridge link show                      # 브리지에 연결된 인터페이스
```

컨테이너 안 `eth0@ifN`의 N과 같은 인덱스를 가진 호스트 쪽 인터페이스가 그 컨테이너의 짝이다. (과거의 `brctl show`는 `bridge-utils` 패키지 소속이라 최근 배포판엔 기본 설치되지 않는 경우가 많고, 요즘은 `bridge link show`를 쓴다.)

> **[보충]** 이미지에 `ip` 명령이 없어 `docker exec web ip ...`가 실패하면, [6장](06-컨테이너-격리-네임스페이스.md)의 `nsenter --target $PID --net -- ip link show eth0`처럼 호스트의 도구로 컨테이너 네트워크 네임스페이스 안을 확인하면 된다.

### 2.2 통신 경로: 컨테이너 간 vs 외부

**한 줄 요약:** 같은 브리지 안은 L2 스위칭(라우팅·NAT 없음), 외부로 나갈 때는 라우팅 + 출발지를 호스트 IP로 바꾸는 MASQUERADE.

| 통신 | 경로 | 계층 |
|---|---|---|
| 같은 브리지 안의 컨테이너 ↔ 컨테이너 | veth → 브리지가 MAC 주소 테이블(FDB)로 전달 → 상대 veth | L2 스위칭 (라우팅·NAT 없음) |
| 컨테이너 → 외부(인터넷 등) | 컨테이너의 기본 게이트웨이(브리지 IP, 예: 172.17.0.1) → 호스트 커널 IP 포워딩 → 출발지 IP를 호스트 IP로 치환(MASQUERADE) | 라우팅 + NAT |

외부로 나가는 패킷의 출발지가 호스트 IP로 바뀌는 것이 **아웃바운드 NAT**다. Docker가 만들어 둔 `iptables`의 `nat` 테이블 `POSTROUTING` 체인에 이 규칙이 있다.

```bash
iptables -t nat -L POSTROUTING -n -v | grep -i MASQUERADE
```

## 코어 3. 들어오는 길은 PREROUTING DNAT

### 3.1 포트 매핑(`-p`)의 두 메커니즘

**한 줄 요약:** 기본 경로는 커널의 iptables DNAT이고, `docker-proxy`는 hairpin 같은 경우를 보완하는 사용자 공간 프로세스다.

`docker run -p 8080:80 nginx`는 호스트의 8080번으로 들어온 트래픽을 컨테이너의 80번으로 전달한다. 이 뒤에는 두 가지 메커니즘이 있다.

1. **iptables DNAT 규칙**: Docker가 `nat` 테이블에 `DOCKER` 체인을 두고 "호스트 8080으로 들어온 패킷의 목적지를 컨테이너 IP:80으로 바꿔라"는 규칙을 추가한다. 별도의 사용자 공간 프로세스 없이 커널에서만 처리된다.
2. **`docker-proxy`**: 포트를 게시할 때 dockerd가 호스트의 게시 포트를 직접 listen하며 컨테이너 IP:포트로 중계하도록 띄우는 사용자 공간 프로세스. 원문(Docker 내부구조 책 12장)은 호스트 자신이 루프백(`127.0.0.1`)으로 자기가 게시한 포트에 접속하는 경우(hairpin NAT) 등 DNAT만으로 왕복 경로가 깔끔하게 완성되지 않는 경우를 보완하는 안전판이라고 설명하며, 기본값은 활성화(`true`)이고 `daemon.json`의 `"userland-proxy": false`로 끌 수 있다고 한다. 끄면 포트 게시는 커널 NAT 경로만으로 처리되므로 끄기 전에 필요한 접근 경로(특히 호스트 루프백 접근)를 점검해야 한다.

한편 같은 책의 15장은 기본 경로가 커널 DNAT이며, 과거에는 `docker-proxy`가 hairpin 트래픽을 대신 중계하기도 했으나 최근 배포판에서는 hairpin 트래픽도 대부분 커널 DNAT만으로 처리된다고 설명한다. 두 설명을 합치면 "포트 게시의 기본 경로는 커널 DNAT이고, `docker-proxy`는 보완용"이라는 점은 일치하지만, 현재 환경에서 `docker-proxy`가 실제로 얼마나 관여하는지는 두 장의 서술이 완전히 같지 않다. 자신의 환경에서는 아래 `ps` 명령으로 직접 확인한다.

### 3.2 인바운드 패킷 경로

**한 줄 요약:** PREROUTING(DNAT) → 라우팅 결정 → FORWARD → docker0 → veth → eth0, 응답은 conntrack이 되돌린다.

패킷 경로를 요약하면 다음과 같다.

```
(외부에서 온 패킷, 목적지 = 호스트IP:8080)
        │
PREROUTING (nat) ── DOCKER 체인으로 점프
        │
DNAT: 목적지를 컨테이너IP:80 으로 변경
        │
라우팅 결정 (목적지가 컨테이너 IP이므로 docker0 방향)
        │
FORWARD 체인 (filter) → docker0 브리지 → veth → 컨테이너 eth0:80
```

DNAT가 라우팅 결정보다 앞선 `PREROUTING` 단계에서 일어난다는 점이 중요하다. 응답 패킷은 conntrack이 기억한 연결 정보로 자동으로 주소가 되돌려지므로, 클라이언트는 자신이 접속한 `호스트IP:8080`만 보게 된다.

```bash
docker run -d --name web -p 8080:80 nginx:latest
iptables-save -t nat | grep -i docker         # DNAT --to-destination <컨테이너IP>:80 규칙 확인
ps -ef | grep docker-proxy | grep -v grep     # -host-port 8080 -container-port 80
```

### 3.3 게시하지 않은 포트와 게시 주소

**한 줄 요약:** Engine 28부터 미게시 포트 인바운드는 기본 차단되지만, 게시된 포트는 호스트 방화벽보다 Docker 규칙이 먼저이므로 필요하면 루프백에만 묶는다.

Docker Engine 28부터는 `-p`로 게시하지 않은 컨테이너 포트로 들어오는 인바운드 트래픽을 기본 차단해, "호스트 방화벽(`ufw` 등)을 Docker가 우회한다"는 오래된 문제가 크게 완화되었다(Linux의 iptables 기반 동작이며 Docker Desktop에는 해당하지 않음). 다만 게시된 포트에는 여전히 Docker 규칙이 우선 적용된다.

> **[보충]** `-p 8080:80`처럼 호스트 주소를 생략하면 호스트의 모든 인터페이스(0.0.0.0)에 게시되어 외부에서도 접속할 수 있다. 개발용 DB처럼 내 PC에서만 쓰면 되는 포트는 `-p 127.0.0.1:5432:5432`처럼 루프백에만 묶어 두는 편이 안전하다. 게시된 포트는 위 설명처럼 `ufw` 같은 호스트 방화벽 규칙보다 Docker 규칙이 먼저 적용되므로, "방화벽에서 막았으니 괜찮다"고 가정하지 않는다.

## 코어 4. 이름은 127.0.0.11이 네트워크 단위로 푼다

### 4.1 내장 DNS와 컨테이너 이름으로 통신

**한 줄 요약:** `127.0.0.11`은 dockerd가 각 컨테이너 네임스페이스에서 가로채 응답하는 내장 DNS로, 같은 네트워크의 이름은 직접 풀고 외부 도메인은 업스트림으로 넘긴다.

사용자 정의 브리지에 연결된 컨테이너의 `/etc/resolv.conf`를 보면 낯선 주소가 있다.

```bash
docker network create mynet
docker run --rm --network mynet alpine:latest cat /etc/resolv.conf
```

```
nameserver 127.0.0.11
options ndots:0
```

`127.0.0.11`은 컨테이너 안의 실제 프로세스가 아니라, dockerd가 각 컨테이너의 네트워크 네임스페이스 안에서 가로채도록 설정한 **내장 DNS 서버**다. 실제 응답은 호스트의 dockerd가 그 네트워크에 속한 컨테이너들의 이름-IP 테이블을 조회해 만든다.

- 같은 네트워크 안에서는 **컨테이너 이름, `--network-alias` 별칭, Compose 서비스 이름**으로 조회된다.
- 컨테이너가 재시작되어 IP가 바뀌어도 매핑이 갱신되므로 **이름으로 접근하는 한 문제없다.**
- 외부 도메인(예: `api.example.com`)은 내장 DNS가 호스트에 설정된 업스트림 DNS로 포워딩한다. 그래서 컨테이너는 내부 이름과 외부 도메인을 모두 하나의 네임서버(127.0.0.11)에 물어보면 된다.

### 4.2 기본 브리지에 DNS가 없는 이유와 `--link`

**한 줄 요약:** 기본 브리지는 서비스 디스커버리 이전 시대의 기본값이고, 그 시절의 `--link`(정적 `/etc/hosts`)는 레거시다.

기본 브리지는 서비스 디스커버리 개념이 없던 초창기부터 존재해 온 기본값이다. 그 시절 이름 통신용 기능이 `--link`였는데, 대상 컨테이너의 IP를 `/etc/hosts`에 정적으로 한 줄 써 주는 방식이라 IP가 바뀌어도 갱신하기 어렵고 동적인 서비스 그룹을 표현하지 못했다. 사용자 정의 네트워크가 이를 해결했으므로 `--link`는 레거시로 간주되며 새 구성에서는 쓰지 않는다.

### 4.3 DNS 문제 진단 체크리스트

**한 줄 요약:** 같은 네트워크인가 → 기본 브리지인가 → `ndots`/검색 도메인 → 앱의 DNS 캐싱 순서로 본다.

1. 조회하는 컨테이너와 대상 컨테이너가 **같은 사용자 정의 네트워크**에 있는가? (이름 해석 범위는 네트워크 단위다. 서로 다른 네트워크라면 둘 다 127.0.0.11을 써도 서로를 찾지 못한다.)
2. 컨테이너가 **기본 브리지**에 붙어 있지는 않은가? (`--network`를 지정하지 않으면 기본 브리지에 붙는다.)
3. `ndots`/검색 도메인 설정이 예상과 다른 이름으로 조회하게 만들고 있지 않은가?
4. 애플리케이션(특히 일부 JVM 계열)이 DNS 응답을 오래 캐싱해 예전 IP로 접속하고 있지 않은가? (Docker 내장 DNS가 아니라 애플리케이션 캐싱 문제다.)

> **[보충]** 쿠버네티스에서는 Service 이름으로 Pod에 접근하는 서비스 디스커버리를 별도의 기능(클러스터 DNS)이 맡는다. Docker의 "이름으로 통신"과 개념은 비슷하지만 구현은 다르며, [22장](../4부-노출-데이터-운영/22-DNS와-서비스-디스커버리.md)에서 다룬다.

## 실무 적용

### 체크리스트

- [ ] 기본 브리지(`docker0`)는 이름 기반 자동 DNS가 없고, 사용자 정의 브리지는 내장 DNS로 컨테이너 이름/별칭 통신이 가능하다. 실무에서는 프로젝트마다 사용자 정의 브리지를 쓴다.
- [ ] veth pair는 컨테이너 쪽 `eth0`과 호스트 쪽 `vethXXXX`(브리지에 연결)가 짝을 이루는 가상 케이블이다. 짝은 `eth0@ifN`의 N으로 찾는다.
- [ ] 같은 브리지 안의 통신은 L2 스위칭, 외부 통신은 라우팅 + MASQUERADE(NAT)이다.
- [ ] `-p`는 iptables `DOCKER` 체인의 DNAT 규칙(`PREROUTING`에서 목적지 변환)과 보완용 `docker-proxy`로 동작한다. `"userland-proxy": false`로 끄기 전에 호스트 루프백 접근 경로를 점검한다.
- [ ] 내 PC에서만 쓸 포트는 `-p 127.0.0.1:포트:포트`로 루프백에만 게시하고, 게시된 포트에는 `ufw`보다 Docker 규칙이 먼저라는 것을 기억한다(Engine 28+는 미게시 포트 인바운드만 기본 차단).
- [ ] 컨테이너의 `127.0.0.11`은 dockerd의 내장 DNS이며, 이름 해석 범위는 네트워크 단위다. 새 구성에서 `--link`는 쓰지 않는다.
- [ ] DNS 장애는 같은 네트워크 → 기본 브리지 여부 → `ndots`/검색 도메인 → 앱 DNS 캐싱 순으로 진단한다.

### 시나리오로 확인하기

1. **상황:** 게임 서버(`game`)와 Redis(`redis`) 컨테이너를 `docker run -d --name ...`으로 각각 띄웠다. 게임 서버 설정에 `redis:6379`를 넣었더니 이름 해석 실패가 난다. 예전 습관대로 `docker inspect`로 Redis IP를 찾아 설정에 박으면 일단 되긴 한다.
   **질문:** 왜 이름이 안 풀리고, IP 하드코딩은 왜 나쁜가? 올바른 구성은?

   <details markdown="1"><summary>답 확인</summary>

   `--network`를 지정하지 않으면 기본 브리지(`docker0`)에 붙고, 기본 브리지에는 이름 기반 자동 DNS가 없다. IP는 컨테이너가 재시작되면 바뀔 수 있어 하드코딩하면 깨진다. `docker network create gamenet` 후 두 컨테이너를 `--network gamenet`으로 띄우면 내장 DNS(127.0.0.11)가 이름을 풀고, IP가 바뀌어도 매핑이 갱신된다. `--link`는 레거시라 쓰지 않는다. → 코어 1, 코어 4

   </details>

2. **상황:** 개발용 PostgreSQL을 `-p 5432:5432`로 띄우고 호스트에서 `ufw deny 5432`를 걸었다. 그런데 사내망의 다른 PC에서 접속이 된다.
   **질문:** 왜 막히지 않았고, 어떻게 했어야 하나?

   <details markdown="1"><summary>답 확인</summary>

   호스트 주소를 생략하면 0.0.0.0(모든 인터페이스)에 게시되고, 게시된 포트에는 `ufw` 같은 호스트 방화벽보다 Docker 규칙이 먼저 적용된다. Engine 28의 기본 차단은 **게시하지 않은** 포트에만 해당한다. 내 PC에서만 쓸 포트는 `-p 127.0.0.1:5432:5432`처럼 루프백에만 묶는다. → 코어 3 (3.3)

   </details>

3. **상황:** 외부 클라이언트가 `호스트IP:8080`으로 접속하는 nginx 컨테이너(`-p 8080:80`)의 패킷 경로를 장애 보고서에 적어야 한다. 동료는 "dockerd가 8080을 listen해서 받아 넘겨 준다"고 쓴다.
   **질문:** 정확한 경로는?

   <details markdown="1"><summary>답 확인</summary>

   기본 경로는 커널이다. `nat` 테이블 `PREROUTING`에서 `DOCKER` 체인으로 점프 → DNAT로 목적지를 `컨테이너IP:80`으로 변경 → 라우팅 결정(docker0 방향) → `FORWARD`(filter) → docker0 브리지 → veth → 컨테이너 `eth0:80`. 응답은 conntrack이 주소를 되돌려 클라이언트는 `호스트IP:8080`만 본다. `docker-proxy`(사용자 공간 중계)는 hairpin NAT 같은 경우를 위한 보완용이며, 실제 관여 여부는 `ps -ef | grep docker-proxy`로 확인한다. → 코어 3 (3.1, 3.2)

   </details>

4. **상황:** 두 컨테이너 모두 `/etc/resolv.conf`에 `nameserver 127.0.0.11`이 있는데도 서로의 이름을 찾지 못한다.
   **질문:** 가장 먼저 무엇을 확인하나?

   <details markdown="1"><summary>답 확인</summary>

   이름 해석 범위는 네트워크 단위이므로 두 컨테이너가 **같은 사용자 정의 네트워크**에 있는지 먼저 본다(다르면 `docker network connect`). 이어서 기본 브리지에 붙어 있지 않은지, `ndots`/검색 도메인 설정, 애플리케이션(일부 JVM 등)의 DNS 캐싱으로 예전 IP에 접속하는지 확인한다. → 코어 4 (4.3)

   </details>

### 2. 인출 질문

1. 기본 브리지에서는 컨테이너 이름으로 통신이 안 되는데 사용자 정의 브리지에서는 되는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   사용자 정의 브리지에 연결된 컨테이너는 dockerd의 내장 DNS 서버(`127.0.0.11`)를 쓰고, dockerd가 그 네트워크 컨테이너들의 이름-IP 테이블로 응답한다. 기본 브리지는 서비스 디스커버리 개념이 없던 초창기부터의 기본값이라 이 기능이 없고, 당시의 `--link`나 IP 직접 사용만 가능하다. → 코어 1 (1.1), 코어 4 (4.1, 4.2)

   </details>

2. 같은 브리지 안의 두 컨테이너 통신에는 NAT가 개입하는가? 외부로 나갈 때는 어떤가?

   <details markdown="1"><summary>답 확인</summary>

   같은 브리지 안에서는 NAT가 없다. veth → 브리지가 MAC 주소 테이블(FDB)로 전달 → 상대 veth로 가는 L2 스위칭이다. 외부로 나갈 때는 기본 게이트웨이(브리지 IP) → 호스트 IP 포워딩 → 출발지 IP를 호스트 IP로 바꾸는 MASQUERADE(아웃바운드 NAT, `nat` 테이블 `POSTROUTING`)를 거친다. → 코어 2 (2.2)

   </details>

3. `docker run -p 8080:80` 후 호스트 8080으로 온 패킷의 목적지는 어느 단계에서 컨테이너 IP로 바뀌는가?

   <details markdown="1"><summary>답 확인</summary>

   라우팅 결정보다 앞선 `nat` 테이블의 `PREROUTING` 단계에서 `DOCKER` 체인의 DNAT 규칙이 목적지를 `컨테이너IP:80`으로 바꾼다. 그 뒤 라우팅 결정(docker0 방향) → `FORWARD` 체인 → 브리지 → veth → 컨테이너 `eth0:80`으로 간다. 응답은 conntrack이 주소를 되돌려 클라이언트는 `호스트IP:8080`만 본다. → 코어 3 (3.2)

   </details>

4. 컨테이너 안 `eth0@if7`의 `@if7`은 무엇을 뜻하며, 호스트 쪽 짝은 어떻게 찾는가?

   <details markdown="1"><summary>답 확인</summary>

   veth pair 반대편 끝의 인터페이스 인덱스다. 호스트에서 `ip link show type veth`로 그 인덱스를 가진 `vethXXXX`를 찾으면 그 컨테이너의 짝이고, `bridge link show`로 브리지 연결을 본다. 컨테이너에 `ip` 명령이 없으면 `nsenter`로 확인한다. → 코어 2 (2.1)

   </details>

5. `docker-proxy`는 무엇이고, `"userland-proxy": false`로 끄기 전에 무엇을 점검해야 하는가?

   <details markdown="1"><summary>답 확인</summary>

   포트를 게시할 때 dockerd가 호스트 게시 포트를 listen하며 컨테이너로 중계하도록 띄우는 사용자 공간 프로세스로, 호스트가 루프백으로 자기가 게시한 포트에 접속하는 경우(hairpin NAT)처럼 DNAT만으로 경로가 깔끔하지 않은 경우를 보완한다. 기본 경로는 커널 DNAT다. 끄면 커널 NAT 경로만 남으므로 호스트 루프백 접근 같은 필요한 경로를 먼저 점검한다. → 코어 3 (3.1)

   </details>

6. `-p 5432:5432`로 개발용 DB를 띄우고 `ufw`로 막았으니 안전하다고 생각해도 되는가?

   <details markdown="1"><summary>답 확인</summary>

   아니다. 호스트 주소를 생략하면 0.0.0.0(모든 인터페이스)에 게시되고, 게시된 포트에는 `ufw` 같은 호스트 방화벽보다 Docker 규칙이 먼저 적용된다. 내 PC에서만 쓸 포트는 `-p 127.0.0.1:5432:5432`처럼 루프백에만 묶는다. (Engine 28부터 **게시하지 않은** 포트의 인바운드는 기본 차단된다.) → 코어 3 (3.3)

   </details>

7. 같은 `127.0.0.11`을 쓰는 두 컨테이너가 서로 이름을 찾지 못한다면 무엇부터 확인하는가?

   <details markdown="1"><summary>답 확인</summary>

   이름 해석 범위는 네트워크 단위이므로 두 컨테이너가 **같은 사용자 정의 네트워크**에 있는지 먼저 본다. 이어서 기본 브리지에 붙어 있지 않은지, `ndots`/검색 도메인 설정, 애플리케이션(일부 JVM 등)의 DNS 캐싱으로 예전 IP에 접속하는지 확인한다. → 코어 4 (4.3)

   </details>

8. `--link`가 레거시로 취급되는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   대상 컨테이너의 IP를 `/etc/hosts`에 정적으로 한 줄 써 주는 방식이라 IP가 바뀌어도 갱신하기 어렵고 동적인 서비스 그룹을 표현하지 못했다. 사용자 정의 네트워크의 내장 DNS가 이를 해결했다(재시작으로 IP가 바뀌어도 매핑 갱신). → 코어 4 (4.2)

   </details>

### 3. 기억 고리

- **C++ 유추:** `-p 8080:80` ≈ 공유기 포트포워딩. ⚠️ 별도 장비가 아니라 같은 호스트 커널의 `PREROUTING`에서 라우팅 결정 **전**에 목적지가 바뀌고, 컨테이너 안 앱은 자기 네임스페이스에서 80을 listen할 뿐 호스트 8080은 열지 않는다.
- **C++ 유추:** 컨테이너 이름 통신 ≈ 설정 파일의 서버 IP를 DNS 이름으로 바꾸기. ⚠️ 이름 해석은 같은 사용자 정의 네트워크 안에서만 되고, 응답자는 dockerd다.
- **비유:** Docker 네트워크 = 아파트 단지 인터넷. 각 세대(컨테이너)의 랜 케이블(veth) 한쪽은 세대 안 콘센트(`eth0`), 다른 쪽은 단지 스위치(브리지)에 꽂혀 있다. 단지 안 통화는 스위치만 거치고(L2), 밖으로 나갈 때는 단지 대표 번호(호스트 IP)로 바뀌며(MASQUERADE), 밖에서 대표 번호의 내선(8080)으로 오면 관리실이 세대 번호로 바꿔 연결한다(DNAT). ⚠️ 비유가 깨지는 지점: "관리실"은 사람(프로세스)이 아니라 커널의 iptables 규칙이고, 번호 변경은 라우팅 결정 **전**(PREROUTING)에 일어나며, 응답은 conntrack이 자동으로 되돌린다.
- **비유:** 내장 DNS 127.0.0.11 = 단지 관리실 안내 데스크. 같은 단지(네트워크) 주민 이름만 알고, 바깥 주소는 외부 안내(업스트림 DNS)에 물어 대신 알려 준다. ⚠️ 비유가 깨지는 지점: 데스크는 컨테이너 안의 실제 프로세스가 아니라 dockerd가 각 네임스페이스에서 가로채 응답하는 것이고, 다른 단지(다른 네트워크) 주민은 모른다.
- **묶음(3의 법칙):** 통신 3방향(컨테이너 간 = 스위칭 / 밖으로 = MASQUERADE / 안으로 = DNAT) / 브리지 차이 2축 + 권고 1(DNS·격리 → 사용자 정의 브리지) / 이름 3종(컨테이너 이름·`--network-alias`·Compose 서비스 이름).
- **대칭·순서:** 아웃바운드 NAT(출발지 변경, POSTROUTING) ↔ 인바운드 DNAT(목적지 변경, PREROUTING). 순서: PREROUTING → DNAT → 라우팅 결정 → FORWARD → docker0 → veth → eth0.
