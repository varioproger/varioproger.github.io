# 10장. Docker 네트워크

## 이 장에서 배우는 것

- 기본 브리지(`docker0`)와 사용자 정의 브리지의 차이를 이해한다.
- veth pair가 컨테이너와 호스트 브리지를 어떻게 연결하는지 개념을 안다.
- 컨테이너 간 통신(스위칭)과 외부 통신(라우팅 + NAT)이 다르다는 것을 안다.
- 포트 매핑(`-p`)이 어떤 경로로 동작하는지 큰 그림을 이해한다.
- 내장 DNS(127.0.0.11)로 컨테이너 이름으로 통신하는 원리를 이해한다.

---

## 10.1 기본 브리지와 사용자 정의 브리지

Docker를 설치하면 `docker0`이라는 리눅스 브리지가 하나 만들어진다. `--network`를 지정하지 않은 컨테이너는 이 기본 브리지(`bridge`라는 이름의 기본 네트워크)에 연결된다. 반면 `docker network create`로 직접 만든 브리지를 **사용자 정의 브리지**라고 부른다. 겉보기엔 같은 리눅스 브리지지만 실무에 영향을 주는 차이가 있다.

| 구분 | 기본 브리지 (`docker0`) | 사용자 정의 브리지 |
|---|---|---|
| 이름으로 통신(자동 DNS) | 지원하지 않음 (`--link` 같은 레거시 방식이나 IP 직접 사용) | 컨테이너 이름/별칭으로 서로를 찾음 |
| 네트워크 간 격리 | 연결된 컨테이너가 모두 한 평평한 공간 | 서로 다른 네트워크의 컨테이너는 기본적으로 격리 (필요 시 `docker network connect`) |

그래서 실무에서는 **기본 브리지를 그대로 쓰지 말고 프로젝트마다 사용자 정의 브리지를 만들어 쓰라**고 권한다. Docker Compose가 프로젝트마다 전용 네트워크를 자동으로 만들어 주는 것도 같은 이유다(11장).

```bash
docker network create mynet
docker run -d --name api --network mynet myapp:latest
docker run --rm --network mynet alpine ping -c1 api    # 컨테이너 이름 api로 통신
```

> **[보충]** 위 `ping` 줄은 이름 통신을 보여 주기 위해 이 책에서 구성한 예시이며, 원문에 있는 명령은 아니다.

## 10.2 veth pair — 컨테이너와 호스트를 잇는 가상 케이블

브리지 네트워크에서 컨테이너가 연결될 때 핵심은 **veth(virtual ethernet) pair**다. veth는 항상 쌍으로 생성되는 가상 인터페이스로, 한쪽 끝으로 들어간 패킷이 다른 끝으로 그대로 나온다. 마치 케이블로 연결된 것과 같다.

Docker는 veth pair를 만들어 **한쪽 끝은 컨테이너의 네트워크 네임스페이스로 옮기고**(컨테이너 안에서 `eth0`으로 보임), **다른 쪽 끝은 호스트에 남겨 브리지에 연결**한다.

```
[ 호스트 네트워크 네임스페이스 ]                [ 컨테이너 네트워크 네임스페이스 ]

   docker0 (브리지)
       │
       ├── vethXXXXXXX@if5  ◄──── veth pair ────►  eth0@if6      (컨테이너 1)
       │
       └── vethYYYYYYY@if7  ◄──── veth pair ────►  eth0@if8      (컨테이너 2)
```

직접 확인할 수 있다(앞 장처럼 `web`이라는 컨테이너가 떠 있다고 가정한다).

```bash
docker exec web ip link show eth0     # 예: 6: eth0@if7 ...  ← @if 뒤 숫자는 반대편 끝의 인덱스
ip link show type veth                # 호스트의 veth 목록
bridge link show                      # 브리지에 연결된 인터페이스
```

컨테이너 안 `eth0@ifN`의 N과 같은 인덱스를 가진 호스트 쪽 인터페이스가 그 컨테이너의 짝이다. (과거의 `brctl show`는 `bridge-utils` 패키지 소속이라 최근 배포판엔 기본 설치되지 않는 경우가 많고, 요즘은 `bridge link show`를 쓴다.)

> **[보충]** 이미지에 `ip` 명령이 없어 `docker exec web ip ...`가 실패하면, 5장의 `nsenter --target $PID --net -- ip link show eth0`처럼 호스트의 도구로 컨테이너 네트워크 네임스페이스 안을 확인하면 된다.

## 10.3 통신 경로: 컨테이너 간 vs 외부

| 통신 | 경로 | 계층 |
|---|---|---|
| 같은 브리지 안의 컨테이너 ↔ 컨테이너 | veth → 브리지가 MAC 주소 테이블(FDB)로 전달 → 상대 veth | L2 스위칭 (라우팅·NAT 없음) |
| 컨테이너 → 외부(인터넷 등) | 컨테이너의 기본 게이트웨이(브리지 IP, 예: 172.17.0.1) → 호스트 커널 IP 포워딩 → 출발지 IP를 호스트 IP로 치환(MASQUERADE) | 라우팅 + NAT |

외부로 나가는 패킷의 출발지가 호스트 IP로 바뀌는 것이 **아웃바운드 NAT**다. Docker가 만들어 둔 `iptables`의 `nat` 테이블 `POSTROUTING` 체인에 이 규칙이 있다.

```bash
iptables -t nat -L POSTROUTING -n -v | grep -i MASQUERADE
```

## 10.4 포트 매핑(`-p`)의 동작

`docker run -p 8080:80 nginx`는 호스트의 8080번으로 들어온 트래픽을 컨테이너의 80번으로 전달한다. 이 뒤에는 두 가지 메커니즘이 있다.

1. **iptables DNAT 규칙**: Docker가 `nat` 테이블에 `DOCKER` 체인을 두고 "호스트 8080으로 들어온 패킷의 목적지를 컨테이너 IP:80으로 바꿔라"는 규칙을 추가한다. 별도의 사용자 공간 프로세스 없이 커널에서만 처리된다.
2. **`docker-proxy`**: 포트를 게시할 때 dockerd가 호스트의 게시 포트를 직접 listen하며 컨테이너 IP:포트로 중계하도록 띄우는 사용자 공간 프로세스. 원문(Docker 내부구조 책 12장)은 호스트 자신이 루프백(`127.0.0.1`)으로 자기가 게시한 포트에 접속하는 경우(hairpin NAT) 등 DNAT만으로 왕복 경로가 깔끔하게 완성되지 않는 경우를 보완하는 안전판이라고 설명하며, 기본값은 활성화(`true`)이고 `daemon.json`의 `"userland-proxy": false`로 끌 수 있다고 한다. 끄면 포트 게시는 커널 NAT 경로만으로 처리되므로 끄기 전에 필요한 접근 경로(특히 호스트 루프백 접근)를 점검해야 한다.

한편 같은 책의 15장은 기본 경로가 커널 DNAT이며, 과거에는 `docker-proxy`가 hairpin 트래픽을 대신 중계하기도 했으나 최근 배포판에서는 hairpin 트래픽도 대부분 커널 DNAT만으로 처리된다고 설명한다. 두 설명을 합치면 "포트 게시의 기본 경로는 커널 DNAT이고, `docker-proxy`는 보완용"이라는 점은 일치하지만, 현재 환경에서 `docker-proxy`가 실제로 얼마나 관여하는지는 두 장의 서술이 완전히 같지 않다. 자신의 환경에서는 아래 `ps` 명령으로 직접 확인한다.

패킷 경로를 요약하면 다음과 같다.

```
(외부에서 온 패킷, 목적지 = 호스트IP:8080)
        │
PREROUTING (nat) ── DOCKER 체인으로 점프
        │
DNAT: 목적지를 컨테이너IP:80 으로 변경
        │
라우팅 결정 (목적지가 컨테이너 IP이므로 docker0 방향)
        │
FORWARD 체인 (filter) → docker0 브리지 → veth → 컨테이너 eth0:80
```

DNAT가 라우팅 결정보다 앞선 `PREROUTING` 단계에서 일어난다는 점이 중요하다. 응답 패킷은 conntrack이 기억한 연결 정보로 자동으로 주소가 되돌려지므로, 클라이언트는 자신이 접속한 `호스트IP:8080`만 보게 된다.

```bash
docker run -d --name web -p 8080:80 nginx:latest
iptables-save -t nat | grep -i docker         # DNAT --to-destination <컨테이너IP>:80 규칙 확인
ps -ef | grep docker-proxy | grep -v grep     # -host-port 8080 -container-port 80
```

### 참고: 게시하지 않은 포트

Docker Engine 28부터는 `-p`로 게시하지 않은 컨테이너 포트로 들어오는 인바운드 트래픽을 기본 차단해, "호스트 방화벽(`ufw` 등)을 Docker가 우회한다"는 오래된 문제가 크게 완화되었다(Linux의 iptables 기반 동작이며 Docker Desktop에는 해당하지 않음). 다만 게시된 포트에는 여전히 Docker 규칙이 우선 적용된다.

> **[보충]** `-p 8080:80`처럼 호스트 주소를 생략하면 호스트의 모든 인터페이스(0.0.0.0)에 게시되어 외부에서도 접속할 수 있다. 개발용 DB처럼 내 PC에서만 쓰면 되는 포트는 `-p 127.0.0.1:5432:5432`처럼 루프백에만 묶어 두는 편이 안전하다. 게시된 포트는 위 설명처럼 `ufw` 같은 호스트 방화벽 규칙보다 Docker 규칙이 먼저 적용되므로, "방화벽에서 막았으니 괜찮다"고 가정하지 않는다.

## 10.5 내장 DNS와 컨테이너 이름으로 통신

사용자 정의 브리지에 연결된 컨테이너의 `/etc/resolv.conf`를 보면 낯선 주소가 있다.

```bash
docker network create mynet
docker run --rm --network mynet alpine:latest cat /etc/resolv.conf
```

```
nameserver 127.0.0.11
options ndots:0
```

`127.0.0.11`은 컨테이너 안의 실제 프로세스가 아니라, dockerd가 각 컨테이너의 네트워크 네임스페이스 안에서 가로채도록 설정한 **내장 DNS 서버**다. 실제 응답은 호스트의 dockerd가 그 네트워크에 속한 컨테이너들의 이름-IP 테이블을 조회해 만든다.

- 같은 네트워크 안에서는 **컨테이너 이름, `--network-alias` 별칭, Compose 서비스 이름**으로 조회된다.
- 컨테이너가 재시작되어 IP가 바뀌어도 매핑이 갱신되므로 **이름으로 접근하는 한 문제없다.**
- 외부 도메인(예: `api.example.com`)은 내장 DNS가 호스트에 설정된 업스트림 DNS로 포워딩한다. 그래서 컨테이너는 내부 이름과 외부 도메인을 모두 하나의 네임서버(127.0.0.11)에 물어보면 된다.

### 기본 브리지에 DNS가 없는 이유와 `--link`

기본 브리지는 서비스 디스커버리 개념이 없던 초창기부터 존재해 온 기본값이다. 그 시절 이름 통신용 기능이 `--link`였는데, 대상 컨테이너의 IP를 `/etc/hosts`에 정적으로 한 줄 써 주는 방식이라 IP가 바뀌어도 갱신하기 어렵고 동적인 서비스 그룹을 표현하지 못했다. 사용자 정의 네트워크가 이를 해결했으므로 `--link`는 레거시로 간주되며 새 구성에서는 쓰지 않는다.

### DNS 문제 진단 체크리스트

1. 조회하는 컨테이너와 대상 컨테이너가 **같은 사용자 정의 네트워크**에 있는가? (이름 해석 범위는 네트워크 단위다. 서로 다른 네트워크라면 둘 다 127.0.0.11을 써도 서로를 찾지 못한다.)
2. 컨테이너가 **기본 브리지**에 붙어 있지는 않은가? (`--network`를 지정하지 않으면 기본 브리지에 붙는다.)
3. `ndots`/검색 도메인 설정이 예상과 다른 이름으로 조회하게 만들고 있지 않은가?
4. 애플리케이션(특히 일부 JVM 계열)이 DNS 응답을 오래 캐싱해 예전 IP로 접속하고 있지 않은가? (Docker 내장 DNS가 아니라 애플리케이션 캐싱 문제다.)

> **[보충]** 쿠버네티스에서는 Service 이름으로 Pod에 접근하는 서비스 디스커버리를 별도의 기능(클러스터 DNS)이 맡는다. Docker의 "이름으로 통신"과 개념은 비슷하지만 구현은 다르며, 4부에서 다룬다.

---

## 핵심 요약

- 기본 브리지(`docker0`)는 이름 기반 자동 DNS가 없고, 사용자 정의 브리지는 내장 DNS로 컨테이너 이름/별칭 통신이 가능하다. 실무에서는 사용자 정의 브리지를 쓴다.
- veth pair는 컨테이너 쪽 `eth0`과 호스트 쪽 `vethXXXX`(브리지에 연결)가 짝을 이루는 가상 케이블이다.
- 같은 브리지 안의 통신은 L2 스위칭, 외부 통신은 라우팅 + MASQUERADE(NAT)이다.
- `-p`는 iptables `DOCKER` 체인의 DNAT 규칙(`PREROUTING`에서 목적지 변환)과 보완용 `docker-proxy`로 동작한다.
- 컨테이너의 `127.0.0.11`은 dockerd의 내장 DNS이며, 이름 해석 범위는 네트워크 단위다.
