# 5장. 가상 머신 vs 컨테이너, Docker의 전체 구조

> **🎮 게임 서버 개발자에게** — 컨테이너는 "가벼운 VM"이 아니라, 한 리눅스 머신에서 게임 서버 프로세스 여러 개를 띄우던 것과 같은 **보통 프로세스**다. 차이는 커널이 각 프로세스에 서로 다른 "보이는 세상"과 자원 한도를 씌워 준다는 점뿐이다. `docker run`은 서버를 직접 실행하는 명령이 아니라, 여러 데몬을 거쳐 실행을 **준비**한 뒤 빠지는 제어 경로다. 마치 런처가 서버 프로세스를 `fork`/`exec`로 띄우고 감시만 하는 구조와 닮았다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 점검 시간에 Docker 엔진을 업그레이드해야 하는데, 접속 중인 유저가 있는 게임 서버 컨테이너가 같이 죽을지 판단해야 할 때
> - 유저가 올린 스크립트(모드·커스텀 맵 로직)를 컨테이너에서 돌리려는데 "컨테이너면 안전하다"고 믿어도 되는지 결정할 때
> - 포트 매핑이 안 먹어서 containerd/runc 로그를 뒤지고 있는데, 사실은 dockerd 쪽 문제일 때

## 코어 — 이것만은 100%

> **한 문장:** 컨테이너는 호스트 커널을 공유하는 격리된 프로세스이고, `docker run`은 CLI → dockerd → containerd → shim → runc → 커널로 전달되는 "실행 준비 경로"일 뿐이며, runc는 사라지고 shim이 부모로 남기에 데몬이 재시작돼도 컨테이너는 산다.

1. **커널을 공유하는 프로세스** — VM은 하드웨어를 가상화해 각자 커널을 갖고, 컨테이너는 호스트 커널 하나를 공유한다. 그래서 가볍고 빠르지만 격리 경계가 커널이라 커널 취약점에 약하다.
2. **역할이 나뉜 제어 경로** — "Docker"는 한 프로그램이 아니다. CLI → dockerd → containerd → shim → runc → 커널로 요청이 넘어가며, 계층마다 프로세스 경계와 책임(네트워크·볼륨·빌드는 dockerd 몫)이 나뉜다.
3. **runc는 사라지고 shim이 남는다** — runc는 네임스페이스·cgroup·루트 파일시스템을 준비한 뒤 `execve()`로 컨테이너 명령이 되어 사라지고, shim이 부모로 남아 입출력과 종료 코드를 맡는다. 그래서 dockerd/containerd 재시작에도 컨테이너가 살아 있다(`live-restore`로 더 확실히).
4. **이미지는 파일과 설정, CPU에서 도는 것은 앱** — 이미지는 실행 중인 컴퓨터가 아니라 파일과 설정이고, OCI 규격 덕분에 빌드 도구(BuildKit)와 실행 도구(Docker, kubelet+containerd)가 달라도 된다. 실행된 뒤에는 앱 프로세스가 호스트 커널과 직접 시스템 호출을 주고받는다.

**이 장에서 배우는 것**

- 가상 머신(VM)과 컨테이너가 격리하는 위치가 어떻게 다른지 설명한다. → 코어 1
- 컨테이너 격리가 "상대적으로 약하다"는 말의 의미를 이해한다. → 코어 1
- `docker run` 한 줄이 CLI → dockerd → containerd → shim → runc → 커널로 이어지는 흐름을 따라간다. → 코어 2, 3
- 이미지(파일과 설정)와 실행 중인 컨테이너(프로세스)가 어떻게 다른지 구분한다. → 코어 4

## 코어 1. 커널을 공유하는 프로세스

### 1.1 컨테이너 vs 가상 머신

**한 줄 요약:** 둘 다 격리된 실행 환경이지만, VM은 하드웨어 수준에서, 컨테이너는 커널을 공유한 채 프로세스 수준에서 격리한다.

두 기술 모두 "격리된 실행 환경"을 제공하지만, **격리가 일어나는 위치가 다르다.**

```
┌──── 가상 머신 ────────────────┐   ┌──── 컨테이너 ─────────────────┐
│  앱 A     앱 B     앱 C       │   │  앱 A     앱 B     앱 C        │
│  라이브러리 라이브러리 라이브러리 │   │  라이브러리 라이브러리 라이브러리 │
│  게스트OS  게스트OS  게스트OS   │   │                              │
│  (커널)    (커널)    (커널)    │   │      ← 커널을 공유 →           │
│  ─────────────────────────   │   │  ─────────────────────────    │
│      하이퍼바이저             │   │      컨테이너 런타임            │
│  ─────────────────────────   │   │  ─────────────────────────    │
│      호스트 OS (커널)          │   │      호스트 OS (커널)          │
│      물리 하드웨어             │   │      물리 하드웨어             │
└──────────────────────────────┘   └──────────────────────────────┘
```

- **가상 머신**은 하드웨어를 가상화한다. 각 VM은 자기만의 커널을 갖고, 하이퍼바이저가 CPU·메모리·디바이스를 나눠 준다. 격리 경계가 하드웨어 수준이라 매우 강하다.
- **컨테이너**는 프로세스를 격리한다. 모든 컨테이너가 호스트의 커널 하나를 공유하고, 커널이 제공하는 격리 기능으로 서로를 보이지 않게 만든다. 컨테이너 안에서 `ps`를 실행하면 자기 프로세스만 보이지만, 호스트에서 보면 그냥 하나의 프로세스일 뿐이다.

| 비교 항목 | 가상 머신 | 컨테이너 |
|---|---|---|
| 격리 수준 | 하드웨어 (강함) | 커널 네임스페이스 (상대적으로 약함) |
| 부팅 시간 | 수십 초 &#126; 수 분 | 수십 밀리초 &#126; 수 초 |
| 이미지 크기 | 수 GB | 수 MB &#126; 수백 MB |
| 오버헤드 | 게스트 커널 + 하이퍼바이저 | 거의 없음 |
| 밀도 (호스트당) | 수십 개 | 수백 &#126; 수천 개 |
| 커널 | 각자 다른 커널·OS 가능 | 호스트 커널 공유 (리눅스만) |

### 1.2 "컨테이너는 격리가 약하다"의 의미

**한 줄 요약:** 격리를 커널이 제공하므로 커널이 뚫리면 호스트 전체가 뚫린다. 신뢰할 수 없는 코드에는 샌드박스 런타임을 고려한다.

컨테이너의 격리는 커널이 제공한다. 따라서 **커널에 취약점이 있으면 격리가 뚫릴 수 있다.** 커널 취약점으로 컨테이너를 탈출(container escape)하면 호스트 전체가 노출된다. VM은 하이퍼바이저까지 뚫어야 하므로 한 단계 더 어렵다.

그래서 신뢰할 수 없는 코드를 실행하는 환경에서는 **샌드박스 런타임**을 쓰기도 한다.

- **gVisor**: 사용자 공간에서 커널 시스템콜을 가로채 구현해 호스트 커널 노출 면적을 줄인다.
- **Kata Containers**: 컨테이너마다 경량 VM을 띄운다. VM 수준 격리 + 컨테이너 사용성.
- **Firecracker**: AWS Lambda·Fargate가 쓰는 마이크로 VM.

> **[보충]** 처음에는 "일반 컨테이너 = 호스트 커널을 함께 쓰는 보통 프로세스"라는 점만 기억해도 충분하다. 샌드박스 런타임은 보안 요구가 높을 때 고려하는 선택지다.

## 코어 2. 역할이 나뉜 제어 경로

### 2.1 "Docker"라는 말 안에는 여러 역할이 있다

**한 줄 요약:** 빌드·관리·실행을 서로 다른 구성 요소가 나눠 맡는다.

`docker build`와 `docker run`이 같은 명령어로 시작하기 때문에 "Docker라는 한 프로그램이 만들고 끝까지 실행한다"고 이해하기 쉽다. 실제로는 여러 구성 요소가 협력한다.

| 이름 | 무엇인가 | 역할 |
|---|---|---|
| Docker CLI | 사용자가 호출하는 클라이언트 | `docker build`, `docker run` 등 요청 전달 |
| Buildx / BuildKit | 빌드 클라이언트 / 빌드 엔진 | Dockerfile과 소스로 이미지 생성 |
| Docker Engine (`dockerd`) | Docker API와 관리 기능을 제공하는 데몬 | 이미지·네트워크·볼륨 등 Docker 방식으로 관리 |
| containerd | 컨테이너 런타임 데몬 | 이미지와 컨테이너 수명 관리 |
| runc | OCI Runtime 규격의 구현체 | 준비된 환경에서 컨테이너 프로세스를 시작 |
| kubelet | 쿠버네티스의 노드 에이전트 | 자기 노드의 Pod 실행을 런타임에 요청 |

### 2.2 `docker run` 한 줄의 여정

**한 줄 요약:** CLI → dockerd → containerd → shim → runc → 커널, 계층마다 프로세스 경계가 실제로 나뉘어 있다.

`docker run -d --name web nginx:latest`를 실행하면 아래 순서로 요청이 전달된다.

```
docker CLI
   │  REST API 호출 (Unix 소켓 /var/run/docker.sock)
   ▼
dockerd (Docker Engine 데몬)
   │  gRPC (/run/containerd/containerd.sock)
   ▼
containerd
   │  컨테이너마다 shim 프로세스를 띄움
   ▼
containerd-shim-runc-v2
   │  OCI Runtime Spec에 따라 runc를 실행
   ▼
runc
   │  네임스페이스 생성, cgroup 설정, 루트 파일시스템 교체, 권한 적용 후
   │  컨테이너의 시작 명령을 execve()로 실행하고 runc 자신은 종료
   ▼
Linux 커널 (namespaces, cgroups, seccomp, capabilities, overlayfs 등)
```

각 계층의 책임을 표로 정리하면 다음과 같다.

| 컴포넌트 | 주요 책임 | 통신 방식 |
|---|---|---|
| `docker` CLI | 사용자 명령을 REST API 호출로 변환 | HTTP over Unix 소켓 |
| `dockerd` | 이미지 관리, 네트워크, 볼륨, 빌드(BuildKit 위임), 컨테이너 수명의 상위 조정 | REST API 서버 + containerd gRPC 클라이언트 |
| `containerd` | 이미지 pull/저장, 레이어(스냅샷) 관리, 컨테이너·태스크 관리, CRI 제공 | gRPC 서버 |
| `containerd-shim-runc-v2` | 컨테이너 프로세스의 부모 역할, 입출력·종료 상태 처리 | shim API |
| `runc` | 네임스페이스/cgroup/마운트를 구성하고 컨테이너 프로세스를 실행 | CLI 인자 + `config.json` |

핵심은 **계층마다 프로세스 경계가 실제로 나뉘어 있다**는 점이다.

- `docker` CLI는 요청을 보내고 응답을 받으면 끝난다. 컨테이너가 도는 동안 CLI가 살아 있을 필요는 없다.
- dockerd와 containerd는 서로 다른 독립 데몬이다.
- containerd가 컨테이너를 만들 때마다 그 컨테이너를 전담하는 shim 프로세스가 생긴다. (Docker의 일반적인 경로 기준이며, 구현에 따라 shim 하나가 여러 컨테이너를 맡도록 묶일 수도 있다.)
- **runc는 컨테이너를 "시작하는 순간"에만 존재하는 일회성 프로세스**다. 환경을 준비한 뒤 `execve()`로 자기 자리를 컨테이너의 시작 명령(예: nginx)으로 통째로 바꾸므로, 컨테이너가 실행되는 동안에는 runc가 남아 있지 않다. (→ 코어 3)

### 2.3 dockerd가 하는 일, containerd·runc가 하지 않는 일

**한 줄 요약:** 네트워크·포트 매핑·볼륨·빌드 위임은 dockerd의 몫이다.

네트워크 브리지 생성, 포트 매핑을 위한 방화벽 규칙 삽입, 볼륨 관리, 빌드 요청을 BuildKit에 넘기는 일은 **dockerd의 몫**이다. containerd와 runc는 이런 것을 알지 못하고 "이미지를 컨테이너로 만들어 실행한다"는 역할에 집중한다.

## 코어 3. runc는 사라지고 shim이 남는다

### 3.1 shim은 왜 있는가

**한 줄 요약:** runc가 사라진 뒤 컨테이너의 부모로 남아 입출력과 종료 코드를 맡는 것이 shim이고, 그 덕분에 데몬의 생사와 워크로드의 생사가 분리된다.

runc가 실행 직후 사라진다면, 컨테이너의 출력(stdout/stderr)은 누가 붙잡고, 컨테이너가 종료됐을 때 종료 코드는 누가 회수할까? 이 일을 하는 것이 `containerd-shim-runc-v2`다. shim은 컨테이너 프로세스의 **부모**로 남아 입출력을 유지하고, 종료되면 종료 코드를 회수해 containerd에 전달한다.

이 구조의 결과가 중요하다. **dockerd나 containerd가 재시작되어도 shim과 컨테이너 프로세스는 영향을 받지 않는다.** 그래서 Docker 데몬을 업그레이드하려고 재시작해도 실행 중이던 컨테이너가 죽지 않는다. 데몬이 다시 뜨면 기존 컨테이너 상태를 다시 연결한다. "상위 데몬의 생사가 실행 중인 워크로드의 생사와 분리되어 있다"는 의미다.

### 3.2 계획된 업그레이드에는 `live-restore`

**한 줄 요약:** dockerd 무중단 업그레이드를 고려한다면 `daemon.json`에서 `live-restore`를 켠다.

다만 "데몬을 내리고 새 버전으로 올리는" 계획된 업그레이드에서 컨테이너 중단을 더 확실하게 막으려면 `/etc/docker/daemon.json`에서 `live-restore` 옵션을 켜 둔다. 이 옵션을 켜면 dockerd가 정상 종료될 때 실행 중인 컨테이너를 멈추지 않고 그대로 둔 채 종료하고, 재시작 후 containerd에 남아 있는 태스크 목록으로 상태를 다시 구성한다. 운영 환경에서 무중단 dockerd 업그레이드를 고려한다면 활성화가 일반적으로 권장된다.

```json
{
  "live-restore": true
}
```

### 3.3 프로세스 트리로 직접 확인하기

**한 줄 요약:** 실행 중인 컨테이너의 프로세스 트리에는 shim 아래 nginx가 보이고 runc는 보이지 않는다.

직접 확인해 볼 수 있다.

```bash
docker run -d --name web nginx:latest
ps -ef --forest | grep -E "dockerd|containerd|nginx"
```

```
root   1000  ... /usr/bin/dockerd -H fd://
root   1050  ... \_ /usr/bin/containerd
root   2101  ...     \_ /usr/bin/containerd-shim-runc-v2 -namespace moby -id <container-id>
root   2130  ...         \_ nginx: master process nginx -g daemon off;
www    2170  ...             \_ nginx: worker process
```

(PID는 예시이다.) 출력에서 `runc`가 보이지 않는 점을 눈여겨보자. 이미 사라졌기 때문이다.

## 코어 4. 이미지는 파일과 설정, CPU에서 도는 것은 앱

### 4.1 이미지는 "실행 중인 컴퓨터"가 아니라 파일과 설정

**한 줄 요약:** 이미지는 실행 파일·라이브러리·앱 파일·시작 명령 정보이고, 게스트 커널을 부팅하지 않는다.

Python 앱을 예로 들면 Dockerfile은 이런 모양이다(개념 예시).

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY app.py /app/app.py
CMD ["python", "/app/app.py"]
```

- 빌드 결과(이미지)에는 Python 실행 파일, 라이브러리, 앱 파일, 시작 명령 등의 정보가 들어간다.
- `CMD`는 "빌드할 때 서버를 실행하라"가 아니라 **나중에 컨테이너를 시작할 때 쓸 기본 명령을 기록**하는 것이다.
- Dockerfile은 빌드의 입력일 뿐이고, 런타임은 이미 만들어진 이미지를 읽어 실행한다.
- 이미지에 Debian·Ubuntu 계열 파일이 들어 있어도 **별도의 게스트 커널을 부팅하지 않는다.** 앱의 시스템 호출은 호스트 커널이 처리한다.
- 같은 이미지를 쓴다는 것은 실행 중 메모리 상태를 복사한다는 뜻이 아니다. 각 머신이 이미지의 파일·설정으로 **새 프로세스**를 시작한다.

### 4.2 이미지를 만든 도구와 실행하는 도구는 달라도 된다

**한 줄 요약:** 빌드는 BuildKit, 실행은 containerd+runc. 같은 OCI 규격 이미지를 읽으므로 쿠버네티스 노드는 Docker 없이도 실행한다.

빌드는 BuildKit이 맡고, 일반적인 Docker Engine 실행 경로는 containerd와 runc를 사용한다. 쿠버네티스 노드는 Docker CLI/dockerd를 거치지 않고 kubelet이 CRI로 containerd에 요청하며, containerd가 runc로 컨테이너를 시작한다. 둘 다 같은 규격(OCI)의 이미지를 읽기 때문에 가능하다.

```
Docker CLI → dockerd → containerd → shim/runc → 앱 프로세스 → 커널   (개발 머신)
kubelet  ──CRI──→ containerd → shim/runc → 앱 프로세스 → 커널         (쿠버네티스 노드)
```

(위 도식은 호출 관계를 단순화한 것이며 프로세스의 부모·자식 관계를 정확히 그린 것은 아니다.)

### 4.3 실제로 CPU에서 도는 것은 무엇인가

**한 줄 요약:** CPU에서 도는 것은 앱 프로세스이고, containerd·runc는 실행을 준비하는 제어 경로일 뿐이다.

최종적으로 리눅스가 실행하는 것은 Python, Java, Go 바이너리 같은 **앱 프로세스**다. 컨테이너는 그 프로세스에 격리된 환경과 제약을 적용한 실행 방식이다.

| 커널 기능 | 컨테이너에 주는 효과 |
|---|---|
| PID namespace | 프로세스가 보는 PID 범위를 분리 (안과 밖의 PID가 다름) |
| Network namespace | 인터페이스·IP·포트 공간 분리 |
| Mount namespace 등 | 보이는 파일시스템 구성 분리 |
| cgroups | CPU·메모리 등의 사용을 측정·제한 |
| capabilities·seccomp 등 | 허용할 특권·시스템 호출 범위 제한 |

`앱 → containerd → runc → 커널`을 모든 CPU 연산이나 네트워크 패킷이 통과하는 경로로 읽으면 안 된다. containerd와 runc는 **실행을 준비하는 제어 경로**이고, 실행된 앱은 그 뒤로 호스트 커널과 직접 시스템 호출을 주고받는다. 이어지는 [6장](06-컨테이너-격리-네임스페이스.md)·[7장](07-자원-제어-cgroups.md)에서 네임스페이스와 cgroups를 자세히 본다.

4. **상황:** "컨테이너로 옮기면 모든 패킷이 dockerd → containerd → runc를 거쳐 커널로 가니까 레이턴시가 늘 것"이라는 우려가 나왔다.

### 2. 인출 질문

1. VM과 컨테이너는 각각 무엇을 가상화/격리하며, 커널은 어떻게 다른가?

   <details markdown="1"><summary>답 확인</summary>

   VM은 하드웨어를 가상화하고, 각 VM이 자기만의 게스트 커널을 가지며 하이퍼바이저가 자원을 나눈다. 컨테이너는 프로세스를 격리하고, 모든 컨테이너가 호스트 커널 하나를 공유한다(그래서 리눅스만, 다른 OS 불가). → 코어 1 (1.1)

   </details>

2. `docker run` 후 컨테이너가 실행 중일 때 `ps`에서 runc가 보이지 않는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   runc는 컨테이너를 시작하는 순간에만 존재하는 일회성 프로세스다. 네임스페이스·cgroup·마운트를 구성한 뒤 `execve()`로 자기 자리를 컨테이너의 시작 명령(예: nginx)으로 통째로 바꾸므로 실행 중에는 남아 있지 않다. → 코어 2 (2.2), 코어 3 (3.3)

   </details>

3. dockerd를 재시작해도 컨테이너가 죽지 않는 것은 어떤 구성 요소 덕분인가?

   <details markdown="1"><summary>답 확인</summary>

   `containerd-shim-runc-v2`(shim) 덕분이다. shim이 컨테이너 프로세스의 부모로 남아 입출력을 유지하고 종료 코드를 회수하므로, 상위 데몬의 생사와 워크로드의 생사가 분리된다. 계획된 업그레이드에는 `daemon.json`에서 `live-restore`를 켜 두면 더 확실하다. → 코어 3 (3.1, 3.2)

   </details>

4. "컨테이너는 격리가 약하다"는 말은 정확히 무슨 뜻이며, 이를 보완하는 선택지는?

   <details markdown="1"><summary>답 확인</summary>

   격리를 커널이 제공하므로 커널 취약점으로 컨테이너를 탈출하면 호스트 전체가 노출된다. VM은 하이퍼바이저까지 뚫어야 해 한 단계 더 어렵다. 신뢰할 수 없는 코드에는 gVisor(사용자 공간에서 시스템콜 구현), Kata Containers(컨테이너마다 경량 VM), Firecracker(마이크로 VM) 같은 샌드박스 런타임을 쓴다. → 코어 1 (1.2)

   </details>

5. 브리지 네트워크 생성이나 포트 매핑 방화벽 규칙은 dockerd, containerd, runc 중 누구의 몫인가?

   <details markdown="1"><summary>답 확인</summary>

   dockerd의 몫이다. 네트워크 브리지, 포트 매핑 방화벽 규칙, 볼륨 관리, 빌드 요청을 BuildKit에 넘기는 일은 dockerd가 하고, containerd와 runc는 "이미지를 컨테이너로 만들어 실행"하는 역할에 집중한다. → 코어 2 (2.3)

   </details>

6. Dockerfile의 `CMD`는 빌드 중에 서버를 실행하는가? 그리고 Debian 기반 이미지를 실행하면 Debian 커널이 부팅되는가?

   <details markdown="1"><summary>답 확인</summary>

   둘 다 아니다. `CMD`는 나중에 컨테이너를 시작할 때 쓸 기본 명령을 기록할 뿐이다. 이미지에 Debian 계열 파일이 있어도 별도 게스트 커널을 부팅하지 않고, 앱의 시스템 호출은 호스트 커널이 처리한다. → 코어 4 (4.1)

   </details>

7. 쿠버네티스 노드에서 Docker CLI/dockerd 없이 Docker로 빌드한 이미지를 실행할 수 있는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   kubelet이 CRI로 containerd에 요청하고 containerd가 runc로 컨테이너를 시작하는데, 빌드 도구와 실행 도구가 모두 같은 OCI 규격의 이미지를 읽기 때문이다. → 코어 4 (4.2)

   </details>

8. "앱 → containerd → runc → 커널"을 모든 CPU 연산과 패킷이 지나가는 경로로 이해하면 왜 틀린가?

   <details markdown="1"><summary>답 확인</summary>

   containerd와 runc는 실행을 준비하는 제어 경로일 뿐이다. 실행된 앱은 그 뒤로 호스트 커널과 직접 시스템 호출을 주고받는다. CPU에서 실제로 도는 것은 앱 프로세스이고, 컨테이너는 그 프로세스에 격리와 제약(네임스페이스, cgroups, capabilities·seccomp)을 적용한 실행 방식이다. → 코어 4 (4.3)

   </details>

### 3. 기억 고리

- **C++ 유추:** runc = 서버 런처가 `fork()` 뒤 호출하는 `execve()`, shim = 자식의 종료 코드를 `waitpid()`로 회수하는 감시 프로세스. ⚠️ 깨지는 곳: runc는 `execve()` 전에 네임스페이스·cgroup·루트 파일시스템을 먼저 바꿔 두고, shim은 관리 데몬과 분리된 별도 프로세스라서 관리 데몬(dockerd·containerd)이 죽어도 워크로드는 산다.
- **C++ 유추:** 컨테이너 여러 개 = 한 머신에 채널 서버 프로세스 여러 개. ⚠️ 깨지는 곳: 컨테이너마다 커널이 다른 PID·네트워크·파일시스템 뷰와 자원 한도를 씌운다. 같은 커널을 쓰므로 Windows용 바이너리 같은 다른 OS 커널용 프로그램은 리눅스 컨테이너에서 그대로 돌지 않는다.
- **비유:** runc = 로켓 발사대, shim = 관제소. 발사대(runc)는 발사 준비만 하고 로켓(앱)이 뜨면 역할이 끝나 사라지고, 관제소(shim)가 남아 교신(입출력)과 귀환 신호(종료 코드)를 받는다. 본사(dockerd)가 문을 닫았다 열어도 비행 중인 로켓은 계속 난다. ⚠️ 비유가 깨지는 지점: runc는 옆에 남는 시설이 아니라 `execve()`로 자기 자신이 앱으로 "변신"한다. 로켓과 발사대가 같은 프로세스(PID)다.
- **비유:** VM vs 컨테이너 = 단독주택 vs 아파트. 단독주택은 각자 기초(커널)를 갖고, 아파트 세대는 건물 골조(호스트 커널)를 공유하며 벽(네임스페이스)으로 나뉜다. ⚠️ 비유가 깨지는 지점: 골조에 결함(커널 취약점)이 있으면 모든 세대가 뚫릴 수 있고, 아파트는 다른 종류의 골조(다른 OS 커널)를 섞을 수 없다.
- **묶음(3의 법칙):** 데몬 3단(dockerd·containerd·shim) + 일회성 1(runc) / 샌드박스 3종(gVisor·Kata·Firecracker) / 이미지 3진실(파일과 설정·게스트 커널 없음·실행 시 새 프로세스).
- **대칭·순서:** 제어 경로(CLI→dockerd→containerd→shim→runc) ↔ 실행 경로(앱 ↔ 커널 직접 시스템 호출). 개발 머신 경로 ↔ 쿠버네티스 노드 경로(kubelet→CRI→containerd).
