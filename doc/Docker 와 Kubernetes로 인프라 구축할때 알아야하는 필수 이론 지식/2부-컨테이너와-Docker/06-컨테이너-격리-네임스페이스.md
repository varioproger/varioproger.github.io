# 6장. 컨테이너 격리 — 네임스페이스

> **🎮 게임 서버 개발자에게** — 한 머신에 채널 서버를 여러 개 띄울 때 포트를 7777, 7778, 7779로 나누고 공유 메모리 키가 겹치지 않게 관리했을 것이다. 네임스페이스는 커널이 "프로세스마다 다른 포트 공간·PID·호스트 이름·파일시스템이 보이게" 해 주는 기능이라, 그런 수작업 분리가 필요 없어진다. 결정적 차이는 이것이 **보이는 것만** 바꾼다는 점이다. 무엇을 할 수 있는지(권한)와 얼마나 쓰는지(자원)는 다른 장치가 막는다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 같은 호스트에서 서버 컨테이너 여러 개가 모두 `0.0.0.0:7777`을 bind하는데 왜 충돌이 안 나는지, 또는 왜 밖에서 접속이 안 되는지 따져야 할 때
> - 셸도 없는 distroless 서버 이미지에서 네트워크 상태를 확인해야 할 때
> - "디버깅이 편하니까" `--privileged`나 `--pid=host`로 배포하자는 제안을 막아야 할 때

## 코어 — 이것만은 100%

> **한 문장:** 컨테이너는 일반 프로세스에 네임스페이스라는 "렌즈"를 씌워 보이는 것만 다르게 만든 것이고, Docker 옵션은 그 렌즈를 공유하라는 지시이며, 격리는 가시성(네임스페이스)·권한(capabilities/seccomp)·자원(cgroups) 세 축이 함께여야 완성된다.

1. **네임스페이스는 렌즈다** — 자원을 복제·분할하지 않고 프로세스 그룹별로 다르게 "보이게" 한다. 컨테이너 10개도 같은 커널·CPU·물리 NIC를 공유한다.
2. **여덟 가지 렌즈** — PID(컨테이너 첫 프로세스가 PID 1), net(자기 `lo`·`eth0`, 포트 공간), mnt(이미지 레이어가 `/`), UTS(호스트명), IPC, user(UID 매핑), cgroup, time.
3. **만들고, 들어가고, 공유한다** — `unshare`로 만들고 `nsenter`로 들어가며 `/proc/<pid>/ns/` 번호로 확인한다. `--net=host`, `--net=container:X` 등 Docker 옵션은 "새로 만들지 말고 공유하라"이며, Pod의 pause 컨테이너가 같은 원리다.
4. **격리 3축** — 네임스페이스는 가시성만 담당한다. 권한은 capabilities/seccomp, 자원은 cgroups가 맡고, 런타임은 대부분의 capability를 제거한 채 실행하며 `--privileged`는 격리 포기다.

**이 장에서 배우는 것**

- 네임스페이스가 "자원을 나누는 것"이 아니라 "다르게 보이게 하는 것"임을 이해한다. → 코어 1
- 주요 네임스페이스(PID, 네트워크, 마운트, UTS, IPC, 사용자)가 각각 무엇을 격리하는지 안다. → 코어 2
- `unshare`, `nsenter`, `/proc/<pid>/ns`로 네임스페이스를 직접 확인한다. → 코어 3
- `--net=host`, `--net=container:X` 같은 Docker 옵션이 "네임스페이스 공유"임을 이해한다. → 코어 3

| `shmget()` 키가 다른 서버와 겹치는 문제 | IPC 네임스페이스 | System V IPC 키는 원래 전역이다 | 컨테이너끼리는 같은 IPC 키를 써도 충돌하지 않는다 |
| 1024 미만 포트를 쓰려고 서버를 root로 실행 | capabilities (`CAP_NET_BIND_SERVICE`) | 특권 동작에 권한이 필요하다 | root 전체가 아니라 필요한 조각(capability)만 줄 수 있다. 컨테이너 런타임은 기본으로 대부분을 제거한다 |

## 코어 1. 네임스페이스는 렌즈다

### 1.1 네임스페이스란 무엇인가

**한 줄 요약:** 컨테이너는 특별한 커널 객체가 아니라, 일반 프로세스에 커널 자원을 "다르게 보이게" 하는 네임스페이스를 여러 개 씌운 것이다.

컨테이너라는 특별한 커널 객체가 있는 것이 아니다. 컨테이너는 **일반 프로세스에 여러 네임스페이스를 조합해 씌운 것**이다.

리눅스 네임스페이스는 커널이 관리하는 전역 자원(프로세스 ID, 네트워크 인터페이스, 마운트 테이블 등)을 프로세스 그룹별로 **서로 다르게 "보이게"** 만드는 기능이다.

- 자원을 실제로 복제하거나 물리적으로 분할하는 것이 아니다. 컨테이너 10개는 여전히 같은 커널, 같은 CPU, 같은 물리 네트워크 인터페이스를 공유한다.
- 다만 컨테이너 안의 프로세스가 `ps`를 실행하면 자기 네임스페이스 안의 프로세스만, `ip addr`을 실행하면 자기 네트워크 네임스페이스의 인터페이스만 보인다.
- 네임스페이스는 커널에 질의한 결과를 걸러 주는 **렌즈**에 가깝다.

리눅스는 총 8가지 네임스페이스를 제공하며, `clone()`, `unshare()`, `setns()` 시스템 콜로 새로 만들거나 기존 것에 합류한다.

## 코어 2. 여덟 가지 렌즈

### 2.1 주요 네임스페이스 한눈에 보기

**한 줄 요약:** PID·net·mnt·UTS·IPC·user·cgroup·time, 각각 무엇이 다르게 보이는지가 핵심이다.

| 네임스페이스 | 격리 대상 | 컨테이너에서 보이는 모습 |
|---|---|---|
| PID | 프로세스 ID 공간 | 컨테이너의 첫 프로세스가 PID 1 |
| Network (net) | 네트워크 인터페이스, 라우팅, 방화벽 규칙, 포트 공간 | 자기만의 `lo`와 `eth0`(veth 한쪽 끝) |
| Mount (mnt) | 마운트 테이블 | `/`가 이미지 레이어를 합친 파일시스템으로 보임 |
| UTS | 호스트 이름, NIS 도메인 | `hostname`이 컨테이너 ID 앞자리(또는 `--hostname` 값) |
| IPC | System V IPC, POSIX 메시지 큐 | 컨테이너 간 IPC 키 충돌 없음 |
| User | UID/GID 매핑 | 컨테이너의 root가 호스트에서는 비특권 UID일 수 있음 |
| cgroup | cgroup 계층 뷰 | 자기 cgroup 하위 트리를 루트처럼 봄 |
| Time | 부팅 이후 경과 시간 클록 | 실무에서 가장 존재감이 적음 |

### 2.2 PID 네임스페이스

**한 줄 요약:** 컨테이너 안의 PID 1은 호스트에서는 다른 PID이고, PID 1은 좀비 회수·시그널 처리 책임을 진다.

새 PID 네임스페이스에서 처음 실행되는 프로세스는 그 안에서 **PID 1**이 된다. 컨테이너 안에서 `ps -ef`를 하면 엔트리포인트가 PID 1로 보이지만, 호스트에서는 같은 프로세스가 다른 PID를 가진다. PID는 네임스페이스마다 다르게 매핑되는 "뷰"다.

PID 1은 좀비 프로세스 회수와 시그널 처리에서 특별한 책임이 있다. 엔트리포인트가 자식 프로세스를 여럿 띄우면 좀비가 쌓일 수 있어, `tini` 같은 최소 init 프로그램을 PID 1로 두는 패턴이 쓰인다. Docker는 `docker run --init` 옵션으로 이를 켤 수 있다.

### 2.3 네트워크 네임스페이스

**한 줄 요약:** 인터페이스·라우팅·방화벽·포트 공간이 분리되어 컨테이너마다 `0.0.0.0:80`을 bind할 수 있다.

네트워크 인터페이스, 라우팅 테이블, 방화벽 규칙, 포트 바인딩 공간이 분리된다. 각 컨테이너는 기본적으로 자신만의 loopback(`lo`)과 가상 이더넷 인터페이스(veth pair의 한쪽 끝)를 가지며, 그래서 컨테이너마다 독립적으로 `0.0.0.0:80`을 바인딩할 수 있다. ([11장](11-Docker-네트워크.md)에서 Docker 네트워크를 다룬다.)

### 2.4 마운트 네임스페이스

**한 줄 요약:** 프로세스별 마운트 테이블 + `pivot_root`로 컨테이너의 `/`가 이미지 파일시스템이 된다.

프로세스별로 독립적인 마운트 테이블을 제공한다. 컨테이너 안에서 `/`를 봤을 때 호스트의 루트가 아니라 이미지 레이어를 합친 파일시스템이 보이는 것은 이 네임스페이스와 `pivot_root`(또는 구형 `chroot`)의 조합으로 만들어진다.

### 2.5 UTS, IPC 네임스페이스

**한 줄 요약:** UTS는 호스트 이름, IPC는 공유 메모리·세마포어·메시지 큐를 격리한다.

- UTS는 호스트 이름을 격리한다. 컨테이너 안의 `hostname`이 호스트와 다른 이유다.
- IPC는 공유 메모리·세마포어·메시지 큐를 격리한다. 서로 다른 컨테이너가 같은 IPC 키를 써도 충돌하지 않는다.

### 2.6 사용자 네임스페이스

**한 줄 요약:** 컨테이너의 root를 호스트의 비특권 UID로 매핑하는 추가 방어선이며, 기본 `docker run`에서는 꺼져 있다.

UID/GID 공간을 격리한다. 컨테이너 안에서 UID 0(root)인 프로세스가 호스트에서는 임의의 비특권 UID(예: 100000)로 매핑되게 할 수 있다. 컨테이너 탈출 취약점이 있더라도 호스트의 실제 root 권한을 얻지 못하게 하는 추가 방어선이 되고, rootless 컨테이너의 기반이 된다. 기본 `docker run`은 사용자 네임스페이스를 새로 만들지 않으며, `userns-remap` 설정이나 `--userns=` 옵션으로 활성화한다.

## 코어 3. 만들고, 들어가고, 공유한다

### 3.1 `/proc/<pid>/ns/`로 확인하기

**한 줄 요약:** `/proc/<pid>/ns/` 링크의 번호가 같으면 같은 네임스페이스다.

각 프로세스의 네임스페이스는 `/proc/<pid>/ns/` 아래 심볼릭 링크로 보인다.

```bash
ls -l /proc/$$/ns/
```

```
cgroup -> 'cgroup:[4026531835]'
ipc    -> 'ipc:[4026531839]'
mnt    -> 'mnt:[4026531840]'
net    -> 'net:[4026531992]'
pid    -> 'pid:[4026531836]'
time   -> 'time:[4026531834]'
user   -> 'user:[4026531837]'
uts    -> 'uts:[4026531838]'
```

대괄호 안 숫자는 네임스페이스의 고유 식별자다. **두 프로세스의 번호가 같으면 같은 네임스페이스에 속한 것**이다.

### 3.2 직접 해 보기 (root 권한 필요)

**한 줄 요약:** `unshare`로 만들고, `nsenter`로 들어가고, `ip netns`로 네트워크 네임스페이스만 따로 다룬다.

#### 새 PID 네임스페이스 만들기

```bash
sudo unshare --mount --pid --fork --mount-proc bash
ps -ef          # 자기 자신과 극소수 프로세스만 보임, bash가 PID 1
exit
```

`--mount-proc`는 새 PID 네임스페이스 기준으로 `/proc`를 다시 마운트해, `ps`가 정확한 결과를 보여 준다.

#### 실행 중인 컨테이너의 네임스페이스에 들어가기 (`nsenter`)

```bash
docker run -d --name web nginx:latest
PID=$(docker inspect -f '{{.State.Pid}}' web)

sudo nsenter --target $PID --net -- ip addr     # 컨테이너의 네트워크 네임스페이스에서 실행
sudo nsenter --target $PID --mount -- ls /      # 컨테이너의 마운트 네임스페이스에서 실행
```

`nsenter`는 셸이 없는 이미지(예: distroless)처럼 컨테이너 안에 디버깅 도구가 없을 때, **호스트의 도구로 컨테이너의 네임스페이스 안을 살펴볼 수 있어** 실용적이다.

#### 네트워크 네임스페이스 단독 관리

```bash
sudo ip netns add testns
sudo ip netns exec testns ip addr
sudo ip netns list
sudo ip netns delete testns
```

### 3.3 Docker가 네임스페이스를 조합하는 방식

**한 줄 요약:** `docker run`은 PID·mnt·UTS·IPC·net을 새로 만들고, `--net=host` 같은 옵션은 "새로 만들지 말고 공유하라"는 지시다.

`docker run`은 기본적으로 PID, 마운트, UTS, IPC, 네트워크(와 조건부로 cgroup) 네임스페이스를 새로 만든다. 사용자 네임스페이스와 타임 네임스페이스는 기본적으로 호스트와 공유한다.

Docker의 여러 옵션은 "이 네임스페이스는 새로 만들지 말고 다른 대상과 **공유**하라"는 지시로 이해하면 쉽다.

```bash
docker run --rm --net=host nginx:latest                  # 호스트와 네트워크 네임스페이스 공유
docker run -d --name app myapp:latest
docker run --rm --net=container:app busybox ip addr     # 다른 컨테이너 app과 네트워크 공유
docker run --rm --pid=host busybox ps -ef                # 호스트의 모든 프로세스가 보임 (디버깅용)
docker run --rm --ipc=host busybox ipcs                  # 호스트와 IPC 공유
```

`--net=container:app` 패턴은 **쿠버네티스 Pod 안에서 여러 컨테이너가 네트워크를 공유하는 구조와 같은 원리**다. Pod는 먼저 "pause 컨테이너"로 네트워크 네임스페이스를 만들어 두고, 같은 Pod의 나머지 컨테이너가 그 네임스페이스에 합류한다. 그래서 같은 Pod의 컨테이너끼리 `localhost`로 통신할 수 있다. ([15장](../3부-쿠버네티스-핵심/15-Pod.md)에서 다시 만난다.)

## 코어 4. 격리 3축

### 4.1 네임스페이스만으로는 부족하다

**한 줄 요약:** 네임스페이스는 가시성만 담당한다. 권한(capabilities·seccomp)과 자원(cgroups)이 함께여야 격리가 완성되고, 가장 약한 축이 전체 수준을 정한다.

네임스페이스는 격리의 세 축 중 **가시성(무엇이 보이는가)** 만 담당한다.

| 축 | 담당 | 핵심 질문 |
|---|---|---|
| 가시성 | 네임스페이스 | 무엇이 보이는가 |
| 권한 | capabilities, seccomp | 무엇을 할 수 있는가 |
| 자원 | cgroups | 얼마나 쓸 수 있는가 |

- 네임스페이스는 커널 자체를 분리하지 않으므로 커널 취약점은 경계를 넘을 수 있다.
- "무엇이 보이는지"만 제한하고 "무엇을 할 수 있는지"는 제한하지 않는다. 위험한 동작을 막는 것은 capabilities(root 권한을 잘게 쪼갠 단위)와 seccomp(허용할 시스템 콜을 제한하는 필터)다.
- 자원 독점(noisy neighbor)을 막는 것은 다음 장의 cgroups다.
- 세 축이 함께 작동해야 격리가 완성되고, `--privileged`처럼 하나를 풀면 가장 약한 축이 전체 수준을 결정한다.

### 4.2 capabilities — "무엇을 할 수 있는가"

**한 줄 요약:** root 권한을 40여 개 조각으로 나눈 것이며, 런타임은 대부분을 제거한 채 실행한다. 필요한 것만 `--cap-add`, `--privileged`는 금지.

전통적인 리눅스의 권한은 이분법이었다. root(UID 0)는 모든 것을 할 수 있고, 나머지는 거의 아무것도 못 한다. **capability**는 root의 권한을 40여 개 조각으로 나눈 것이다.

| capability | 허용하는 동작 |
|---|---|
| `CAP_NET_BIND_SERVICE` | 1024 미만 포트 바인딩 |
| `CAP_NET_ADMIN` | 네트워크 인터페이스·라우팅 설정 |
| `CAP_SYS_ADMIN` | 마운트 등 광범위한 관리 작업 (사실상 root와 유사, 위험) |
| `CAP_CHOWN` | 파일 소유자 변경 |
| `CAP_SYS_PTRACE` | 다른 프로세스 디버깅 |

컨테이너 런타임은 기본적으로 대부분의 capability를 **제거**한 채 컨테이너를 실행한다. 꼭 필요한 것만 골라 추가하고, 모든 capability를 주는 `--privileged`는 격리를 포기하는 것과 같으므로 프로덕션에서 쓰지 않는다.

```bash
docker run --rm --cap-add=NET_ADMIN alpine ip link set lo down && echo "성공"   # 특정 capability만 추가
docker run --rm --privileged alpine ...   # 모든 capability 부여 = 격리 포기 (프로덕션 금지)
```

쿠버네티스의 `securityContext.capabilities.drop: ["ALL"]`도 같은 메커니즘을 쓴다([25장](../4부-노출-데이터-운영/25-인증-인가-보안-오토스케일링.md)). 컨테이너 안에서 root로 실행하지 않는 것(Dockerfile의 `USER`, [9장](09-Dockerfile과-이미지-빌드.md))과 함께 컨테이너 보안의 기본기다.

### 체크리스트

- [ ] 네임스페이스는 커널 자원을 나누는 것이 아니라 프로세스마다 다른 "뷰"를 보여 주는 기능이며, 컨테이너는 프로세스에 네임스페이스를 씌운 것이다.
- [ ] 주요 네임스페이스: PID(프로세스), net(네트워크), mnt(마운트), UTS(호스트명), IPC, user(UID/GID).
- [ ] `/proc/<pid>/ns/`의 번호를 비교하면 같은 네임스페이스인지 알 수 있고, `unshare`로 만들고 `nsenter`로 들어간다. 셸 없는 이미지를 디버깅할 때 `nsenter`를 먼저 떠올리는가?
- [ ] `--net=host`, `--net=container:X`, `--pid=host`, `--ipc=host`는 새로 만들지 않고 공유하라는 의미이며, 쿠버네티스 Pod의 네트워크 공유와 같은 원리다.
- [ ] 엔트리포인트가 자식 프로세스를 여럿 띄운다면 `tini`나 `docker run --init`으로 PID 1 책임(좀비 회수·시그널 처리)을 처리했는가?
- [ ] 네임스페이스는 가시성만 담당하고, 권한은 capabilities/seccomp, 자원은 cgroups가 담당한다.
- [ ] 런타임은 대부분의 capability를 제거한 채 컨테이너를 실행한다. 필요한 것만 `--cap-add`로 더하고, `--privileged`는 쓰지 않는다.

### 시나리오로 확인하기

1. **상황:** 한 호스트에 채널 서버 컨테이너 세 개를 띄우는데, 셋 다 코드 수정 없이 `0.0.0.0:7777`을 bind한다. C++ 서버 시절 습관대로 "포트가 겹치니 7777/7778/7779로 서버 설정을 바꿔야 한다"고 생각했다.
   **질문:** 꼭 바꿔야 하나?

   <details markdown="1"><summary>답 확인</summary>

   아니다. 네트워크 네임스페이스는 인터페이스·라우팅 테이블·방화벽 규칙·포트 바인딩 공간을 분리한다. 컨테이너마다 자기만의 `lo`와 veth 한쪽 끝을 가지므로 각자 독립적으로 `0.0.0.0:7777`을 bind할 수 있다. 외부에 어떻게 노출할지는 Docker 네트워크([11장](11-Docker-네트워크.md))의 영역이다. → 코어 2

   </details>

2. **상황:** 서버 이미지를 distroless로 바꿨더니 컨테이너 안에 셸도 `ip`도 없다. 접속 장애가 나서 컨테이너의 네트워크 인터페이스를 봐야 한다.
   **질문:** 디버깅 도구를 이미지에 다시 넣어야 하나?

   <details markdown="1"><summary>답 확인</summary>

   그럴 필요 없다. `docker inspect -f '{{.State.Pid}}' <이름>`으로 호스트 기준 PID를 얻고, `sudo nsenter --target $PID --net -- ip addr`처럼 호스트의 도구를 컨테이너의 네트워크 네임스페이스 안에서 실행한다. → 코어 3

   </details>

3. **상황:** 서버 엔트리포인트 스크립트가 로그 수집 프로세스 등 자식을 여럿 띄운다. 시간이 지나자 컨테이너 안에 좀비 프로세스가 쌓였다.
   **질문:** 원인과 대처는?

   <details markdown="1"><summary>답 확인</summary>

   새 PID 네임스페이스의 첫 프로세스는 그 안에서 PID 1이 되고, PID 1은 좀비 프로세스 회수와 시그널 처리에서 특별한 책임이 있다. 엔트리포인트가 이 책임을 다하지 못하면 좀비가 쌓인다. `tini` 같은 최소 init 프로그램을 PID 1로 두거나 `docker run --init`을 켠다. → 코어 2

   </details>

4. **상황:** "운영 중 문제 생기면 바로 들여다볼 수 있게" 서버 컨테이너를 `--privileged --pid=host`로 배포하자는 의견이 나왔다.
   **질문:** 무엇이 문제인가?

   <details markdown="1"><summary>답 확인</summary>

   `--pid=host`는 PID 네임스페이스를 호스트와 공유해 호스트의 모든 프로세스가 보이게 하고, `--privileged`는 모든 capability를 주어 권한 축을 풀어 버린다. 격리는 가시성·권한·자원 세 축이 함께여야 완성되고 하나를 풀면 가장 약한 축이 전체 수준을 결정하므로, 이는 격리를 포기하는 것과 같다. 디버깅은 호스트에서 `nsenter`로 하고, 꼭 필요한 권한만 `--cap-add`로 더한다. → 코어 3, 코어 4

   </details>

5. **상황:** 쿠버네티스 Pod에 게임 서버 컨테이너와 메트릭 수집 사이드카를 함께 넣었다. 사이드카가 `localhost:9100`으로 서버의 메트릭 포트에 접근한다.
   **질문:** 다른 컨테이너인데 왜 `localhost`가 통하나?

   <details markdown="1"><summary>답 확인</summary>

   Pod는 먼저 pause 컨테이너로 네트워크 네임스페이스를 만들고, 같은 Pod의 나머지 컨테이너가 그 네임스페이스에 합류한다. `docker run --net=container:app`과 같은 원리로 네트워크 네임스페이스를 공유하므로 `localhost`가 같다. → 코어 3

   </details>

### 2. 인출 질문

1. 네임스페이스가 VM처럼 자원을 복제하는 것이 아니라고 하는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   네임스페이스는 커널 전역 자원을 프로세스 그룹별로 서로 다르게 "보이게" 할 뿐, 실제로 복제하거나 물리적으로 분할하지 않는다. 컨테이너 10개도 같은 커널, 같은 CPU, 같은 물리 네트워크 인터페이스를 공유한다. 커널 질의 결과를 걸러 주는 렌즈에 가깝다. → 코어 1 (1.1)

   </details>

2. 컨테이너 안에서 PID 1로 보이는 프로세스는 호스트에서는 어떻게 보이는가?

   <details markdown="1"><summary>답 확인</summary>

   호스트에서는 같은 프로세스가 다른 PID를 가진 보통 프로세스로 보인다. PID는 네임스페이스마다 다르게 매핑되는 "뷰"다. 단, 컨테이너 안에서 PID 1이므로 좀비 회수와 시그널 처리 책임이 있어 `tini`/`--init` 패턴이 쓰인다. → 코어 2 (2.2)

   </details>

3. `docker run --net=container:app ...`은 쿠버네티스의 어떤 동작과 같은 원리인가?

   <details markdown="1"><summary>답 확인</summary>

   Pod 안의 여러 컨테이너가 네트워크를 공유하는 구조와 같다. Pod는 먼저 pause 컨테이너로 네트워크 네임스페이스를 만들고, 나머지 컨테이너가 그 네임스페이스에 합류한다. 그래서 같은 Pod의 컨테이너끼리 `localhost`로 통신할 수 있다. → 코어 3 (3.3)

   </details>

4. 두 프로세스가 같은 네트워크 네임스페이스에 있는지 어떻게 확인하는가?

   <details markdown="1"><summary>답 확인</summary>

   `/proc/<pid>/ns/` 아래 심볼릭 링크(예: `net -> 'net:[4026531992]'`)의 대괄호 안 번호를 비교한다. 번호가 같으면 같은 네임스페이스에 속한 것이다. → 코어 3 (3.1)

   </details>

5. 셸도 디버깅 도구도 없는 distroless 컨테이너의 네트워크 상태를 보려면 어떻게 하는가?

   <details markdown="1"><summary>답 확인</summary>

   `docker inspect`로 컨테이너의 `.State.Pid` 값(호스트 기준 PID)을 얻고, `nsenter --target $PID --net -- ip addr`처럼 호스트의 도구를 컨테이너의 네임스페이스 안에서 실행한다. → 코어 3 (3.2)

   </details>

6. 사용자 네임스페이스는 어떤 보안 이점을 주며, 기본 `docker run`에서 켜져 있는가?

   <details markdown="1"><summary>답 확인</summary>

   컨테이너 안의 UID 0(root)을 호스트의 비특권 UID(예: 100000)로 매핑해, 탈출 취약점이 있어도 호스트의 실제 root 권한을 얻지 못하게 하는 추가 방어선이 되고 rootless 컨테이너의 기반이 된다. 기본 `docker run`은 새로 만들지 않으며 `userns-remap`이나 `--userns=`로 활성화한다. → 코어 2 (2.6), 코어 3 (3.3)

   </details>

7. 네임스페이스만으로 격리가 부족한 이유와, `--privileged`를 프로덕션에서 쓰면 안 되는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   네임스페이스는 "무엇이 보이는가"만 제한하고, "무엇을 할 수 있는가"(capabilities, seccomp)와 "얼마나 쓸 수 있는가"(cgroups)는 다른 축이 맡는다. 또 커널 자체를 분리하지 않아 커널 취약점은 경계를 넘을 수 있다. `--privileged`는 모든 capability를 주어 권한 축을 풀어 버리므로, 가장 약한 축이 전체 수준을 결정해 격리를 포기하는 것과 같다. → 코어 4 (4.1, 4.2)

   </details>

### 3. 기억 고리

- **C++ 유추:** 네트워크 네임스페이스 = 프로세스마다 따로 주어지는 포트 테이블. 같은 포트를 두 번 `bind()`해도 `EADDRINUSE`가 안 나는 이유. ⚠️ 깨지는 곳: 포트가 분리될 뿐 물리 NIC와 커널은 하나이고, 컨테이너 안에서 연 포트는 그대로 호스트 포트가 되지 않는다.
- **C++ 유추:** capability = "root로 띄우기" 대신 필요한 권한 조각만 주기(예: `CAP_NET_BIND_SERVICE`로 1024 미만 포트). ⚠️ 깨지는 곳: 컨테이너에서는 기본이 "대부분 제거"이고, `--privileged`는 그 조각을 전부 되돌려 격리를 포기한다.
- **비유:** 네임스페이스 = 같은 건물(커널)에서 세대마다 다른 색 창문 필름. 각 세대는 자기 필름을 통해 보이는 것(자기 프로세스, 자기 인터페이스)만 본다. ⚠️ 비유가 깨지는 지점: 필름은 보는 것만 바꿀 뿐 무엇을 할 수 있는지(capabilities)와 전기·수도를 얼마나 쓰는지(cgroups)는 막지 못한다. 또 `--net=container:X`처럼 두 세대가 같은 필름을 함께 쓸 수도 있다.
- **묶음(3의 법칙):** 격리 3축(가시성·권한·자원) / 네임스페이스 도구 3개(`unshare` 만들기·`nsenter` 들어가기·`ip netns` 관리) / 시스템 콜 3개(`clone`·`unshare`·`setns`).
- **대칭·순서:** 새로 만들기(기본: PID·mnt·UTS·IPC·net) ↔ 공유하기(`--net=host`, `--pid=host`, `--ipc=host`, `--net=container:X`, 기본 공유: user·time). `--cap-add`(필요한 것만) ↔ `--privileged`(전부 = 격리 포기).

- **거울 설명 (1분, 원고 없이):** "컨테이너는 특별한 커널 객체가 아니라 무엇인가"를 처음 듣는 사람에게 설명해 보세요. 말이 막히는 지점 = 지식의 구멍.
