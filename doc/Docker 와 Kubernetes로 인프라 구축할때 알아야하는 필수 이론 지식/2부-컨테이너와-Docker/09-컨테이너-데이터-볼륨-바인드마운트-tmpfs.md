# 9장. 컨테이너 데이터 — 볼륨, 바인드 마운트, tmpfs

## 이 장에서 배우는 것

- 컨테이너 파일시스템 변경이 왜 사라지는지, 그래서 왜 별도 마운트가 필요한지 이해한다.
- 볼륨(named volume), 바인드 마운트, tmpfs의 차이와 용도를 구분한다.
- 볼륨 드라이버 플러그인이 무엇인지 개념을 안다.
- 세 가지 방식을 직접 실행해 저장 위치 차이를 확인한다.

---

## 9.1 왜 별도 마운트가 필요한가

7장에서 본 것처럼 이미지 레이어는 읽기 전용이고, 컨테이너의 쓰기 레이어(upperdir)는 **컨테이너의 생명주기와 함께한다.** 컨테이너를 지우면 쓰기 레이어도 함께 사라진다.

```
컨테이너 안에서 쓴 파일 ──→ 쓰기 레이어 ──→ 컨테이너 삭제 시 함께 사라짐
컨테이너 안에서 쓴 파일 ──→ 마운트된 위치 ──→ 컨테이너와 무관하게 남음 (볼륨/바인드)
```

컨테이너를 재시작하거나 교체해도 살아남아야 하는 데이터(예: 데이터베이스 파일)는 이 레이어 구조 **밖**에 두어야 한다. Docker는 세 가지 마운트 방식을 제공한다.

---

## 9.2 세 가지 방식 비교

| 방식 | 저장 위치 | 생명주기 | 주 용도 |
|---|---|---|---|
| named volume (볼륨) | `/var/lib/docker/volumes/<이름>/_data` (또는 볼륨 드라이버가 관리하는 위치) | `docker volume rm`할 때까지 유지, 컨테이너 삭제와 무관 | 데이터베이스 파일 등 컨테이너와 독립적으로 지속되어야 하는 데이터 |
| bind mount | 호스트의 임의 경로(사용자가 직접 지정) | 호스트 파일시스템의 생명주기를 그대로 따름 | 소스 코드 실시간 반영, 호스트 설정 파일 주입 |
| tmpfs mount | 호스트 디스크가 아닌 메모리 | 컨테이너가 멈추면 즉시 소멸 | 비밀값 등 디스크에 남기면 안 되는 임시 데이터 |

### 볼륨 (named volume)

Docker(또는 containerd)가 직접 생명주기를 관리하는 저장 단위다. 컨테이너를 삭제해도 남아 있다(명시적으로 `docker volume rm`할 때까지 유지). 볼륨 드라이버 플러그인을 통해 로컬 디스크뿐 아니라 NFS, 클라우드 블록 스토리지 같은 외부 스토리지와도 연결할 수 있다(9.3).

### 바인드 마운트

호스트의 특정 경로를 그대로 컨테이너 안에 노출한다. Docker가 그 내용의 생명주기에 관여하지 않으며, **호스트 쪽 권한·SELinux 라벨 문제를 그대로 물려받는다**는 점에 주의해야 한다. 개발 중 소스 코드를 컨테이너에 즉시 반영할 때 편리하다.

### tmpfs 마운트

디스크에 쓰이지 않는 메모리 기반이어서 컨테이너가 종료되는 순간 내용이 완전히 사라진다. 런타임에만 필요한 토큰 파일 같은 민감 정보를 짧게 다룰 때 쓴다.

---

## 9.3 볼륨 드라이버 플러그인

기본 `local` 드라이버는 호스트 디스크에 볼륨 데이터를 저장한다. 여러 호스트가 같은 데이터를 공유하거나 클라우드 블록 스토리지를 쓰려면 **볼륨 드라이버 플러그인**을 설치해 쓴다. 플러그인은 `Create`, `Mount`, `Path`, `Unmount`, `Remove` 같은 표준 동작을 구현하며, `docker plugin install`로 설치한 뒤 `docker volume create --driver <플러그인 이름>`으로 사용한다.

```bash
docker plugin install --grant-all-permissions vieux/sshfs
docker volume create --driver vieux/sshfs \
  --opt sshcmd=user@remote-host:/data \
  --opt password=... \
  remote-vol
```

컨테이너 입장에서는 여전히 평범한 `-v remote-vol:/data` 마운트이고, 실제 데이터는 원격 호스트나 외부 스토리지에 놓인다. 원칙은 같다. **컨테이너는 마운트 지점만 알고, 그 뒤에 데이터가 어디 있는지는 드라이버가 책임진다.**

> **[보충]** 위 예시의 `password=...`처럼 비밀번호를 명령에 직접 쓰는 방식은 개념을 보이기 위한 예시일 뿐이다.

---

## 9.4 직접 비교해 보기

```bash
# 1. 현재 저장 드라이버 확인
docker info --format 'Driver: {{.Driver}}'

# 2. 세 방식을 한 번에 마운트하고 각각 파일을 써 보기
docker volume create demo-vol
docker run --rm \
  -v demo-vol:/data/volume \
  -v "$(pwd)":/data/bind \
  --tmpfs /data/tmpfs \
  alpine sh -c 'echo vol > /data/volume/f.txt; echo bind > /data/bind/f.txt; echo tmp > /data/tmpfs/f.txt'

# 3. 컨테이너가 이미 사라진 뒤 호스트에서 확인
ls "$(docker volume inspect demo-vol --format '{{.Mountpoint}}')"   # f.txt 있음 (볼륨)
ls ./f.txt                                                          # 있음 (바인드 마운트)
# tmpfs에 쓴 파일은 어디에도 없음
```

결과를 정리하면 다음과 같다.

| 쓴 위치 | 컨테이너 종료 후 |
|---|---|
| named volume | 볼륨 마운트포인트에 남음 |
| bind mount | 호스트의 지정 경로(현재 디렉터리)에 남음 |
| tmpfs | 완전히 사라짐 |

> **[보충]** 위 예시처럼 `-v`의 콜론 왼쪽이 이름(`demo-vol`)이면 named volume, 경로(`/`나 `./`, `$(pwd)`로 시작)이면 바인드 마운트로 해석된다. 이름을 잘못 쓰면 의도와 달리 빈 볼륨이 새로 만들어질 수 있으므로, 헷갈리면 `docker inspect <컨테이너>`의 `Mounts` 항목에서 `Type`(`volume`/`bind`)을 확인한다. 데이터를 남기는 볼륨은 `docker compose down -v`, `docker volume prune` 같은 정리 명령으로 함께 지워질 수 있다는 점도 기억해 두자(8장, 11장).

> **[보충]** 쿠버네티스에서도 "컨테이너 파일시스템은 휘발성이고, 데이터를 남기려면 그 밖의 저장소를 마운트한다"는 같은 원리가 적용된다. 구체적인 방법은 이 책의 4부에서 다룬다.

## 핵심 요약

- 컨테이너의 쓰기 레이어는 컨테이너와 함께 사라지므로, 지속해야 하는 데이터는 레이어 밖에 마운트한다.
- 볼륨은 Docker가 관리하며 컨테이너와 독립적으로 유지되고, 바인드 마운트는 호스트 경로를 그대로 노출하며, tmpfs는 메모리에만 존재해 컨테이너 종료 시 사라진다.
- 바인드 마운트는 호스트 권한/SELinux 문제를 물려받는다.
- 볼륨 드라이버 플러그인으로 NFS, 클라우드 스토리지 같은 외부 저장소도 같은 `-v` 문법으로 쓸 수 있다.
