# 4장. 메모리·파일시스템·네트워크 기초

> **🎮 게임 서버 개발자에게** — 네트워크 파트(소켓, 패킷 경계, TIME_WAIT, `SO_REUSEADDR`)는 이미 몸으로 아는 내용이니 복습으로 빠르게 넘겨도 된다. 이 장에서 새로 챙길 것은 두 가지다. 첫째, `new`/`malloc`이 성공해도 메모리가 확보된 것이 아니며, 컨테이너에서는 메모리 한도에 닿는 순간 **예외(`std::bad_alloc`)도 로그도 없이 SIGKILL(137)**로 죽는다. 둘째, 컨테이너는 자기만의 네트워크 공간을 가지므로 늘 하던 `127.0.0.1` bind가 **밖에서 안 보이는 서버**를 만든다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 게임 서버 컨테이너가 새벽마다 종료 코드 137로 재시작되는데 서버 로그에는 아무 흔적이 없다.
> - 로그 파일을 지웠는데 디스크 사용량 알림이 그대로다.
> - 잘 돌던 서버를 컨테이너로 옮겼더니 클라이언트도 다른 Pod도 접속하지 못한다.

## 코어 — 이것만은 100%

> **한 문장:** 커널은 메모리·파일·소켓 모두를 "예약과 실제 사용", "이름과 실체"를 분리한 간접 계층으로 다루기 때문에, 경고 없는 OOM kill(137), `rm`해도 안 돌아오는 용량, 늦게 보이는 로그, `127.0.0.1` listen 장애 같은 컨테이너 현상이 생긴다.

1. **메모리: 예약 ≠ 실제 사용** — 할당(VSZ)과 실제 사용(RSS)은 다르고, 리눅스는 오버커밋하므로 진짜 바닥나면 OOM killer가 경고 없이 SIGKILL을 보낸다. 컨테이너는 cgroup `memory.max`에서 OOM이 나고 종료 코드는 137이다.
2. **파일: 이름 ≠ 실체, write ≠ 디스크** — fd → open file table → inode 3계층이며 이름은 디렉터리 항목에 있다. 열린 파일은 `rm`해도 공간이 안 돌아오고, overlayfs는 첫 쓰기 때 파일 전체를 복사하며, `write` 성공은 디스크 기록이 아니다.
3. **네트워크: 소켓도 fd, bind 주소가 범위** — TCP는 메시지 경계 없는 바이트 스트림이다. bind 주소가 접근 범위를 정하며(`127.0.0.1` vs `0.0.0.0`), 먼저 닫은 쪽은 60초 TIME_WAIT에 머문다.

|---|---|---|---|
| `new` 실패 시 `std::bad_alloc` 처리 | 오버커밋과 OOM killer | 메모리가 부족하면 문제가 생긴다 | 리눅스는 오버커밋하므로 큰 할당도 대부분 성공한다. 진짜 부족은 **실제로 쓰는 순간** 오고, 그때는 예외가 아니라 OOM killer의 **SIGKILL**이라 잡을 수도 로그를 남길 수도 없다 |

## 코어 1. 메모리: 예약 ≠ 실제 사용

### 1.1 가상 메모리

**한 줄 요약:** 프로세스는 페이지 테이블을 거친 가상 주소만 보고, 매핑 없는 곳을 건드리면 SIGSEGV다.

프로세스가 보는 주소는 **실제 물리 메모리 주소가 아니다.** CPU가 **페이지 테이블**로 가상 주소를 물리 주소로 변환한다. 단위는 **페이지**(기본 4KB)다.

```
가상 주소 공간 (프로세스별 독립)               물리 메모리 (시스템 공유)
┌──────────────┐                               ┌──────────────┐
│ 페이지 0x1000  │ ──────────────────────────────▶│ 물리 프레임 A   │
│ 페이지 0x2000  │ ──────────────────────────────▶│ 물리 프레임 B   │
│ 페이지 0x3000  │ ─(매핑 없음: 접근 시 페이지 폴트)   │               │
└──────────────┘                               └──────────────┘
```

이렇게 하는 이유는 다음과 같다.

1. **격리**: 다른 프로세스의 메모리는 페이지 테이블에 없으니 접근 자체가 불가능하다.
2. **지연 할당**: 실제로 접근할 때까지 물리 메모리를 배정하지 않는다.
3. **공유**: libc 코드처럼 같은 물리 페이지를 여러 프로세스가 매핑할 수 있다.
4. **파일 매핑**: 파일을 메모리처럼 접근할 수 있다(`mmap`).

매핑이 없는 곳을 정당한 이유 없이 접근하면 `SIGSEGV`, 즉 "Segmentation fault"다.

### 1.2 "할당했다"와 "실제로 쓴다"는 다르다

**한 줄 요약:** `malloc`은 예약만 하고 물리 페이지는 처음 쓸 때 배정된다. VSZ ≠ RSS.

```c
char *p = malloc(1 << 30);        // 1GB. 성공. 그런데 RSS는 거의 안 늘어남
memset(p, 0, 1 << 30);            // 이제야 물리 페이지가 실제로 배정됨
```

`malloc`은 큰 요청에 대해 가상 주소 공간에 **예약만** 한다. 물리 페이지는 처음 쓰는 페이지마다 배정된다. 그래서 "메모리 사용량"에는 여러 의미가 섞여 있다.

| 지표 | 의미 |
|---|---|
| **VSZ** | 예약한 가상 주소 공간. 의미 없는 숫자인 경우가 많다 |
| **RSS** | 현재 물리 메모리에 올라와 있는 페이지. 공유 라이브러리 페이지도 포함해서 프로세스별 합이 실제보다 클 수 있다 |
| **PSS** | 공유 페이지를 공유 프로세스 수로 나눠 배분한 값 |
| **USS** | 이 프로세스만 쓰는 페이지. 죽이면 돌아오는 메모리 |

컨테이너가 메모리 제한에 걸리는지 보려면 cgroup의 `memory.current`를 본다. 이 값은 RSS + 페이지 캐시 + 커널 메모리다. 메모리 누수인지 판단할 때는 숫자 하나가 아니라 RSS(또는 USS)의 **시간에 따른 추세**를 본다.

또 하나, **`free()`해도 RSS가 안 줄어들 수 있다.** 할당자가 재사용을 위해 들고 있기 때문이다. 장기 실행 서버가 "누수는 없는데 RSS가 서서히 늘어나는" 흔한 원인(단편화)이다.

### 1.3 오버커밋과 OOM killer

**한 줄 요약:** 오버커밋 때문에 실패는 할당이 아니라 사용 시점에 오고, OOM killer는 경고 없이 SIGKILL을 보낸다.

리눅스는 기본적으로 **오버커밋**한다. 물리 메모리 16GB 머신에서 `malloc(100GB)`가 성공할 수 있다. 그래서 `ENOMEM`이 잘 안 나온다. 문제는 실제로 쓰기 시작할 때 터진다.

물리 메모리가 진짜로 바닥나면 커널은 **OOM killer**를 발동해 `oom_score`가 가장 높은(대략 RSS가 가장 큰) 프로세스를 **`SIGKILL`로** 죽인다. **프로그램에는 아무 경고도 없다.** `dmesg | grep -i 'killed process'`에만 흔적이 남는다.

**컨테이너와의 관계**: cgroup 메모리 제한(`memory.max`)에 닿으면 **그 컨테이너 안에서** OOM kill이 일어난다. 도커는 `OOMKilled: true`, 쿠버네티스는 exit code 137(128 + SIGKILL 9)로 보고한다. (종료 코드 읽는 법 → [3장](03-프로세스와-시그널.md), cgroup 메모리 제한 → [7장](../2부-컨테이너와-Docker/07-자원-제어-cgroups.md), 쿠버네티스 메모리 limit → [19장](../3부-쿠버네티스-핵심/19-리소스-요청-제한과-스케줄링-기초.md))

런타임 힙 설정(JVM `-Xmx`, Go `GOMEMLIMIT`)이 컨테이너 메모리 제한과 일관되는지도 확인 대상이다.

### 1.4 페이지 캐시: "free가 적다"는 착각

**한 줄 요약:** 봐야 할 숫자는 `available`이고, 컨테이너의 `memory.current`에는 페이지 캐시도 들어간다.

```
$ free -h
               total   used   free   shared  buff/cache  available
Mem:            31Gi   8.0Gi  1.2Gi   0.5Gi    22Gi       22Gi
```

`free`가 1.2GB뿐이지만 문제없다. 22GB는 **페이지 캐시**다. 커널은 디스크에서 읽은 파일 내용을 남는 RAM에 최대한 캐시하고, 프로세스가 필요로 하면 내준다. **봐야 할 숫자는 `available`이다.**

컨테이너의 `memory.current`에도 그 컨테이너가 만든 페이지 캐시가 포함된다. 로그를 많이 쓰는 컨테이너에서 "메모리 사용량"이 높게 보이는 원인이다. 압박이 오면 회수되므로 대부분 OOM까지는 안 간다.

### 1.5 스왑

**한 줄 요약:** 문제는 스왑 사용이 아니라 thrashing이고, 쿠버네티스는 예측성을 위해 전통적으로 스왑을 끈다.

물리 메모리가 부족하면 커널은 익명 페이지(힙, 스택)를 스왑 공간에 내보낸다. 스왑이 조금 쓰이는 것은 정상이고, **스왑 in/out이 계속 일어나는 것**(thrashing)이 문제다. 쿠버네티스는 전통적으로 스왑을 끈다. 스왑이 있으면 메모리 제한과 스케줄링 예측이 어려워지기 때문이다.

```bash
cat /proc/<pid>/status | grep -E 'Vm(Size|RSS|Swap)'
free -h
dmesg -T | grep -i -E 'oom|killed process'
cat /sys/fs/cgroup/memory.current /sys/fs/cgroup/memory.max   # 컨테이너 메모리 (cgroup v2)
```

## 코어 2. 파일: 이름 ≠ 실체, write ≠ 디스크

### 2.1 파일 디스크립터의 세 계층

**한 줄 요약:** fd → open file table → inode. 이름은 inode가 아니라 디렉터리 항목에 있다.

`open()`이 반환하는 정수 하나(fd) 뒤에는 세 개의 커널 테이블이 있다.

```
프로세스의 fd 테이블 ──▶ 시스템 전체 open file table ──▶ inode
 (정수 → 항목)           (오프셋, 열기 플래그)            (크기, 권한, 데이터 블록 위치)
```

- **fd 테이블(프로세스별)**: 정수 → open file 항목.
- **open file table(시스템 전체)**: 파일 오프셋, 열기 플래그. 
- **inode**: 파일의 실체. 크기, 권한, 소유자, 데이터 블록 위치. **파일 이름은 여기 없다.** 이름은 디렉터리 항목이 가진다.

이 구조가 설명하는 대표적인 현상: **열린 파일을 `rm`해도 디스크 용량이 안 줄어든다.** `rm`은 디렉터리 항목만 지운다. inode는 링크 수가 0이고 열고 있는 fd도 0일 때 해제된다. 로그를 지웠는데 용량이 안 돌아오면 `lsof | grep deleted`로 아직 열고 있는 프로세스를 찾는다.

fd를 닫지 않으면 쌓여서 `EMFILE`(Too many open files)로 죽는다. `ls /proc/<pid>/fd | wc -l`로 추세를 볼 수 있다. 프로세스당 기본 fd 한도는 1024(soft)라 서버는 올려야 한다. `ulimit -a`로 현재 한도를 볼 수 있고, systemd 서비스는 `LimitNOFILE=65536` 식으로 지정하며, 컨테이너는 도커 데몬의 기본값을 상속한다.

### 2.2 "모든 것은 파일이다"

**한 줄 요약:** 파일·파이프·소켓·디바이스·커널 상태가 모두 fd로 다뤄진다.

| 것 | 어떻게 fd가 되나 |
|---|---|
| 일반 파일 | `open` |
| 파이프/FIFO | `pipe` |
| 소켓 | `socket`, `accept` |
| 디바이스 (`/dev/null` 등) | `open` |
| 커널 내부 상태 | `/proc`, `/sys` |

### 2.3 VFS, 마운트, overlayfs

**한 줄 요약:** VFS가 인터페이스를 통일하고, overlayfs는 첫 쓰기 때 파일 전체를 복사한다.

`read()`는 ext4, xfs, tmpfs, NFS, overlayfs(도커 이미지 레이어), procfs 어디에서나 같다. 커널의 **VFS(Virtual File System)** 계층이 공통 인터페이스를 정의하고 각 파일시스템이 구현하기 때문이다.

- `mount`로 트리 어디든 다른 파일시스템을 붙일 수 있다. `/proc`, `/sys`, `/dev/shm`(tmpfs)이 그렇다.
- tmpfs는 RAM이고, NFS는 네트워크다.
- **overlayfs는 첫 쓰기 시 파일 전체를 상위 레이어로 복사한다.** 도커 컨테이너 안에서 큰 파일을 수정하면 느린 이유이고, 이럴 때는 볼륨을 쓰라고 원문은 권한다. (이미지 레이어 → [8장](../2부-컨테이너와-Docker/08-이미지-레이어-레지스트리-OCI.md), 볼륨 → [10장](../2부-컨테이너와-Docker/10-컨테이너-데이터-볼륨-바인드마운트-tmpfs.md))
- `df`는 마운트 지점별 용량이고, `du`는 디렉터리 트리 합계다. 둘이 다르면 삭제된 열린 파일이나 마운트로 가려진 디렉터리를 의심한다.

### 2.4 write()는 디스크에 쓰지 않는다

**한 줄 요약:** `write` 성공은 "커널이 받았다"일 뿐이고, 파이프로 나가는 stdout은 전체 버퍼링이다.

```
printf("log line\n")   ← 1. stdio 버퍼 (유저 공간)
   ▼
write(fd, ...)         ← 2. 페이지 캐시 (커널 메모리). 여기서 write()는 성공 반환
   ▼ (수 초 후 또는 fsync)
디스크                  ← 3. 진짜 영속
```

- `write` 성공은 "커널이 받았다"는 뜻이다. 정전이면 사라질 수 있고, 디스크에 확실히 내리려면 `fsync`가 필요하다.
- **컨테이너 로그 함정**: stdout이 터미널이면 줄 단위 버퍼링이지만 **파일이나 파이프면 전체 버퍼링**이다. 컨테이너에서 `docker logs`에 파이썬 출력이 안 나오는 고전적 문제가 이것이다(`PYTHONUNBUFFERED=1` 또는 stderr 사용). 시그널로 죽으면 stdio 버퍼는 플러시되지 않는다.
- 안전한 파일 덮어쓰기는 "임시 파일에 쓰고 `fsync` 후 `rename`"이다. `rename`이 원자적이기 때문이다.

```bash
ls -l /proc/<pid>/fd             # 열린 fd
lsof +L1                         # 삭제됐지만 열려 있는 파일
df -h; du -sh /var/log           # 마운트별 용량 vs 디렉터리 합계
```

## 코어 3. 네트워크: 소켓도 fd, bind 주소가 범위

### 3.1 소켓은 파일 디스크립터다

**한 줄 요약:** 핸드셰이크는 커널이 하고, 어느 주소에 bind했는지가 접근 가능 범위를 정한다.

```c
int fd = socket(AF_INET, SOCK_STREAM, 0);   // TCP 소켓. 반환값은 그냥 fd
```

소켓도 fd라서 `read`/`write`/`close`가 파일과 똑같이 동작한다. TCP 서버의 생애는 다음과 같다.

```
서버                                       클라이언트
socket()                                   socket()
bind(0.0.0.0:8080)                          
listen(backlog)          ◀── SYN ───────── connect()
accept() → 새 fd         ─── SYN+ACK ──▶
                         ◀── ACK ────────
read(new_fd)             ◀── 데이터 ─────  write()
write(new_fd)            ─── 데이터 ────▶  read()
close(new_fd)            ─── FIN ───────▶
                         ◀── FIN ────────  close()
```

- `bind`는 IP와 **포트**에 소켓을 묶는다. `listen`으로 연결을 받을 준비를 한다.
- **핸드셰이크(SYN, SYN+ACK, ACK)는 커널이 한다.** `accept()`는 이미 연결이 완성된 소켓을 큐에서 꺼내는 것뿐이다.
- 서버가 80번 포트를 바인딩하려면 root 또는 `CAP_NET_BIND_SERVICE` 권한이 필요하다고 원문은 설명한다. 컨테이너에서는 `docker run --user 1000` 등으로 root를 쓰지 않는 것이 좋다.
- **어느 주소에 bind했는지가 접근 가능 범위를 정한다.** 쿠버네티스 통신 장애를 좁힐 때 원문이 첫 단계로 꼽는 것이 "앱이 Pod 안에서 실제 주소와 포트에 listen하는가"다. 앱이 `127.0.0.1`에만 listen하면 Pod IP로의 접근은 실패할 수 있다. `ss -tlnp`의 Local Address 컬럼으로 확인한다.

> **[보충]** `0.0.0.0`에 bind하면 그 머신(또는 컨테이너)의 모든 네트워크 인터페이스로 들어오는 연결을 받고, `127.0.0.1`(루프백)에 bind하면 같은 네트워크 공간 안에서 오는 연결만 받는다. 컨테이너는 자기만의 네트워크 네임스페이스와 루프백을 가지므로([6장](../2부-컨테이너와-Docker/06-컨테이너-격리-네임스페이스.md)), 컨테이너 안의 `127.0.0.1`은 호스트나 다른 컨테이너·Pod에서 보이지 않는다. 그래서 컨테이너로 띄울 서버는 보통 `0.0.0.0`에 listen하도록 설정한다.

### 3.2 TCP는 스트림이다: 메시지 경계가 없다

**한 줄 요약:** `write` 횟수와 `read` 횟수는 무관하므로 경계는 앱이 만든다.

```c
// 클라이언트
write(fd, "HELLO", 5);
write(fd, "WORLD", 5);

// 서버
n = read(fd, buf, 1024);   // "HELLOWORLD" 10바이트가 한 번에 올 수도,
                           // "HEL" 3바이트만 올 수도 있다
```

TCP는 **바이트 스트림**이다. 보낸 쪽의 `write` 횟수와 받는 쪽의 `read` 횟수는 무관하다. **메시지 경계는 애플리케이션이 만들어야 한다.**

1. **길이 접두어**: `[4바이트 길이][본문]` (gRPC 등 대부분의 바이너리 프로토콜)
2. **구분자**: `\r\n` (HTTP 헤더, Redis 프로토콜)
3. **고정 길이**

`read`가 0을 반환하면 상대가 연결을 닫았다는 뜻(EOF)이다.

### 3.3 TIME_WAIT과 "Address already in use"

**한 줄 요약:** 먼저 닫은 쪽이 60초 TIME_WAIT. 서버는 `SO_REUSEADDR`, 클라이언트는 커넥션 풀.

서버를 재시작하면 `bind: Address already in use`가 나는 이유다.

TCP 연결을 **먼저 닫은 쪽**은 **TIME_WAIT** 상태로 60초 동안 머문다. 늦게 도착하는 패킷이 새 연결과 섞이지 않게 하기 위해서다. 그 소켓이 점유한 포트에는 `bind`가 안 될 수 있다. 해결은 `bind` 전에 **`SO_REUSEADDR`** 옵션을 켜는 것이다.

```c
int on = 1;
setsockopt(fd, SOL_SOCKET, SO_REUSEADDR, &on, sizeof(on));
bind(fd, ...);
```

추가로 알아둘 점이다.

- TIME_WAIT 소켓 수만 개는 **정상**이다. 문제는 클라이언트 쪽에서 **에페머럴 포트**(기본 32768&#126;60999, 약 28,000개)가 고갈되는 것이다. 짧은 연결을 초당 500개쯤 만들면(예: DB에 커넥션 풀 없이 매번 연결) 60초 안에 포트를 다 쓴다. 해결은 **커넥션 풀/keep-alive**다.
- `SO_REUSEPORT`는 다른 것으로, 여러 프로세스가 같은 포트에 각자 bind해 커널이 연결을 분배하게 한다.
- 상대 머신이 케이블이 뽑히거나 꺼지면 FIN도 RST도 오지 않아 소켓이 `ESTABLISHED`로 남는다. 장기 연결은 keepalive나 heartbeat가 필요하다.

### 3.4 같은 머신의 통신: Unix 도메인 소켓

**한 줄 요약:** `AF_UNIX`는 TCP 스택을 건너뛰고 파일 권한으로 접근을 제어한다.

같은 머신 안에서는 `AF_UNIX`를 쓴다. TCP 스택(체크섬, 순서 제어, 혼잡 제어)을 건너뛰어 더 빠르고, 파일시스템 경로(예: `/var/run/docker.sock`)에 바인딩되어 파일 권한으로 접근을 제어한다. (`docker.sock`을 쓰는 Docker 구조 → [5장](../2부-컨테이너와-Docker/05-가상머신-vs-컨테이너-Docker-전체-구조.md))

### 3.5 DNS는 블로킹이다

**한 줄 요약:** `getaddrinfo()`는 동기 블로킹이고 기본 타임아웃 5초 × 재시도다.

`getaddrinfo()`는 `/etc/hosts`를 읽고 `/etc/resolv.conf`의 네임서버에 UDP로 묻고 응답을 기다린다. 동기 블로킹이고 타임아웃은 기본 5초 × 재시도다. 컨테이너에서 DNS가 느린 것은 흔한 장애 원인이다(`ndots:5` 문제, [22장](../4부-노출-데이터-운영/22-DNS와-서비스-디스커버리.md)에서 다룬다).

```bash
ss -tlnp                        # 리스닝 소켓과 프로세스
ss -tan state time-wait | wc -l # TIME_WAIT 수
cat /proc/sys/net/ipv4/ip_local_port_range
```

## 실무 적용

### 체크리스트

- [ ] 가상 메모리: 프로세스는 독립된 주소 공간을 보고, 물리 메모리는 쓸 때 배정된다. VSZ는 예약, RSS는 실제 상주량이다. 누수 판단은 RSS(또는 USS)의 시간에 따른 추세로 한다.
- [ ] 리눅스는 오버커밋하기 때문에 메모리가 바닥나면 경고 없이 OOM killer가 SIGKILL을 보낸다. 컨테이너는 cgroup 한도에서 OOM이 나고 종료 코드는 137이다. 런타임 힙 설정(JVM `-Xmx`, Go `GOMEMLIMIT`)이 컨테이너 메모리 제한과 일관되는가?
- [ ] `free`는 적어 보여도 페이지 캐시가 크면 정상이다. `available`을 본다.
- [ ] fd는 프로세스 테이블, open file table, inode로 이어지고, 파일 이름은 inode가 아니라 디렉터리 항목에 있다. 열린 파일은 `rm`해도 공간이 안 돌아온다. (`lsof +L1`로 확인)
- [ ] 서버의 fd 한도(기본 1024 soft)를 올렸는가?
- [ ] 파일시스템은 VFS로 통일되고 마운트로 붙는다. overlayfs는 첫 쓰기 때 파일을 복사하므로 큰 파일 수정은 볼륨을 쓴다.
- [ ] `write` 성공은 디스크 기록이 아니며, 파이프/파일로 나가는 stdout은 전체 버퍼링이라 컨테이너 로그가 늦게 보일 수 있다. (영속이 필요하면 `fsync`)
- [ ] 소켓도 fd이고, TCP는 메시지 경계 없는 바이트 스트림이다. 앱이 `127.0.0.1`에만 listen하면 Pod IP로의 접근은 실패할 수 있다. (`ss -tlnp`로 확인)
- [ ] 먼저 연결을 닫은 쪽은 60초 TIME_WAIT에 머문다. 서버는 `SO_REUSEADDR`, 클라이언트는 커넥션 풀로 대응한다.

### 시나리오로 확인하기

1. **상황:** 게임 서버 컨테이너가 새벽 이벤트 정산 시간마다 종료 코드 137로 재시작된다. 서버 코드에는 `new` 실패 시 `std::bad_alloc`을 잡아 로그를 남기는 처리가 있는데 로그가 하나도 없다.
   **질문:** 무슨 일이 일어났고 어디서 확인하나?

   <details markdown="1"><summary>답 확인</summary>

   리눅스는 오버커밋하므로 할당은 성공하고, 실제로 페이지를 쓰는 순간 cgroup 메모리 제한(`memory.max`)에 닿아 그 컨테이너 안에서 OOM killer가 SIGKILL을 보낸 것이다(128 + 9 = 137). 예외가 아니라 잡을 수 없는 시그널이라 프로그램에는 아무 경고도 없다. `dmesg | grep -i 'killed process'`, 도커의 `OOMKilled: true`, `/sys/fs/cgroup/memory.current`·`memory.max`로 확인하고, RSS 추세를 보며 한도를 조정하거나 메모리 사용을 줄인다. → 코어 1

   </details>

2. **상황:** 디스크 사용량 경보가 와서 큰 로그 파일을 `rm`했는데 `df`는 그대로다. `du`로는 디렉터리가 거의 비어 있다.
   **질문:** 원인과 해결은?

   <details markdown="1"><summary>답 확인</summary>

   `rm`은 디렉터리 항목(이름)만 지우고, inode는 링크 수와 열린 fd가 모두 0일 때 해제된다. 서버가 아직 그 로그 파일을 열고 있다. `lsof | grep deleted` 또는 `lsof +L1`로 찾고, 그 프로세스가 파일을 닫게(재오픈·재시작) 한다. `df`와 `du`가 다르면 이것이나 마운트로 가려진 디렉터리를 의심한다. → 코어 2

   </details>

3. **상황:** 개발 PC에서 잘 되던 서버를 컨테이너로 옮겼다. 서버는 설정 기본값대로 `127.0.0.1:7777`에 bind한다. 컨테이너 안에서 `ss -tlnp`를 보면 listen 중인데 다른 Pod에서도, 포트를 연결한 호스트에서도 접속이 안 된다.
   **질문:** 왜인가?

   <details markdown="1"><summary>답 확인</summary>

   어느 주소에 bind했는지가 접근 가능 범위를 정한다. 컨테이너는 자기만의 네트워크 네임스페이스와 루프백을 가지므로 컨테이너 안의 `127.0.0.1`은 호스트나 다른 컨테이너·Pod에서 보이지 않는다. `0.0.0.0`에 listen하도록 바꾼다. `ss -tlnp`의 Local Address 컬럼이 `127.0.0.1:7777`이면 이 문제다. → 코어 3

   </details>

4. **상황:** 로그인 API 서버가 요청마다 DB에 새 TCP 연결을 열고 닫는다. 트래픽이 몰리면 DB 연결이 간헐적으로 실패하고, 서버 쪽 TIME_WAIT 소켓이 수만 개다.
   **질문:** TIME_WAIT 자체가 문제인가? 해결은?

   <details markdown="1"><summary>답 확인</summary>

   TIME_WAIT 소켓 수만 개는 정상이다. 문제는 클라이언트(여기서는 API 서버) 쪽 에페머럴 포트(기본 32768&#126;60999, 약 28,000개) 고갈이다. 짧은 연결을 초당 500개쯤 만들면 60초 안에 포트를 다 쓴다. 해결은 커넥션 풀/keep-alive다. → 코어 3

   </details>

5. **상황:** 컨테이너 안에서 수 GB짜리 맵 데이터 파일 일부를 수정하는 작업이 유난히 느리다.
   **질문:** 왜이고 어떻게 바꾸나?

   <details markdown="1"><summary>답 확인</summary>

   overlayfs는 첫 쓰기 시 파일 전체를 상위 레이어로 복사한다. 이미지 레이어에 있는 큰 파일을 수정하면 그 복사 비용이 든다. 이런 데이터는 볼륨에 둔다([10장](../2부-컨테이너와-Docker/10-컨테이너-데이터-볼륨-바인드마운트-tmpfs.md)). → 코어 2

   </details>

### 2. 인출 질문

1. `malloc(1GB)` 직후 RSS가 거의 늘지 않는 이유는 무엇이고, RSS와 VSZ는 어떻게 다른가?

   <details markdown="1"><summary>답 확인</summary>

   큰 `malloc`은 가상 주소 공간에 예약만 하고, 물리 페이지는 처음 쓰는 페이지마다 배정되기 때문이다(지연 할당). VSZ는 예약한 가상 주소 공간이고, RSS는 현재 물리 메모리에 올라와 있는 페이지다. → 코어 1

   </details>

2. 로그 파일을 `rm`했는데 디스크 사용량이 줄지 않는다면 무엇을 확인해야 하는가?

   <details markdown="1"><summary>답 확인</summary>

   `rm`은 디렉터리 항목만 지우고, inode는 링크 수와 열린 fd가 모두 0일 때 해제된다. 아직 그 파일을 열고 있는 프로세스를 `lsof | grep deleted` 또는 `lsof +L1`로 찾는다. `df`와 `du`가 다를 때도 이를 의심한다. → 코어 2

   </details>

3. 서버를 재시작했더니 `Address already in use`가 났다. 원인과 해결 옵션은 무엇인가?

   <details markdown="1"><summary>답 확인</summary>

   연결을 먼저 닫은 쪽(이전 서버)의 소켓이 TIME_WAIT 상태로 60초 머물며 포트를 점유하기 때문이다. `bind` 전에 `SO_REUSEADDR` 옵션을 켜서 해결한다. → 코어 3

   </details>

4. 쿠버네티스에서 exit code 137로 죽은 컨테이너는 메모리 관점에서 무슨 일을 겪은 것인가?

   <details markdown="1"><summary>답 확인</summary>

   cgroup 메모리 제한(`memory.max`)에 닿아 그 컨테이너 안에서 OOM killer가 SIGKILL을 보낸 것이다(128 + 9 = 137). 프로그램에는 경고가 없고 `dmesg`에만 흔적이 남는다. 도커는 `OOMKilled: true`로 보고한다. JVM `-Xmx`, Go `GOMEMLIMIT` 같은 런타임 힙 설정이 제한과 일관되는지 확인한다. → 코어 1

   </details>

5. `free -h`에서 free가 1.2GB뿐이고 buff/cache가 22GB라면 메모리 부족인가? 컨테이너에서는 어떤 영향이 있는가?

   <details markdown="1"><summary>답 확인</summary>

   부족이 아니다. 22GB는 페이지 캐시로, 프로세스가 필요하면 내준다. 봐야 할 숫자는 `available`이다. 컨테이너의 `memory.current`에도 그 컨테이너가 만든 페이지 캐시가 포함되어 로그를 많이 쓰면 사용량이 높게 보이지만, 압박 시 회수되므로 대부분 OOM까지는 가지 않는다. → 코어 1

   </details>

6. 컨테이너에서 파이썬 프로그램의 출력이 `docker logs`에 늦게 나오거나 안 나오는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   stdout이 터미널이면 줄 단위 버퍼링이지만, 파일이나 파이프면 전체 버퍼링이라 버퍼가 찰 때까지 나가지 않는다. `PYTHONUNBUFFERED=1`을 쓰거나 stderr를 쓴다. 시그널로 죽으면 stdio 버퍼는 플러시되지도 않는다. → 코어 2

   </details>

7. 앱이 컨테이너 안에서 `127.0.0.1`에만 listen하면 어떤 문제가 생기고, 어떻게 확인하는가?

   <details markdown="1"><summary>답 확인</summary>

   컨테이너는 자기만의 네트워크 네임스페이스와 루프백을 가지므로 그 `127.0.0.1`은 호스트나 다른 컨테이너·Pod에서 보이지 않는다. Pod IP로의 접근이 실패할 수 있으니 보통 `0.0.0.0`에 listen하게 한다. `ss -tlnp`의 Local Address 컬럼으로 확인한다. → 코어 3

   </details>

8. TCP로 "HELLO"와 "WORLD"를 두 번 `write`했을 때 받는 쪽은 어떻게 받으며, 애플리케이션은 무엇을 해야 하는가?

   <details markdown="1"><summary>답 확인</summary>

   TCP는 바이트 스트림이라 `write` 횟수와 `read` 횟수는 무관하다. "HELLOWORLD"가 한 번에 올 수도, "HEL"만 올 수도 있다. 메시지 경계는 앱이 길이 접두어, 구분자(`\r\n`), 고정 길이 중 하나로 만들어야 한다. → 코어 3

   </details>

### 3. 기억 고리

- **C++ 유추:** 메모리 부족 = `std::bad_alloc`. ⚠️ 깨지는 곳: 오버커밋 때문에 할당은 성공하고, 진짜 부족은 쓰는 순간 OOM killer의 SIGKILL(137)로 온다. 잡을 수 없으니 로그도 없다.
- **C++ 유추:** 개발 PC의 `127.0.0.1` bind. ⚠️ 깨지는 곳: 컨테이너마다 루프백이 따로 있어 밖에서 안 보인다. 컨테이너 서버는 `0.0.0.0`.
- **비유:** 오버커밋 = 항공사 초과 예약. 좌석보다 많이 팔아도(`malloc` 성공) 대부분 문제없지만, 모두 탑승하는 날(실제로 쓰는 순간) 누군가는 강제로 내린다(OOM killer). ⚠️ 비유가 깨지는 지점: 항공사는 미리 공지하고 보상하지만, OOM killer는 아무 경고 없이 `SIGKILL`로 가장 큰(oom_score 높은) 프로세스를 죽인다.
- **비유:** inode와 이름 = 책(실체)과 도서관 목록 카드(디렉터리 항목). `rm`은 목록 카드만 찢는다. 누군가 아직 책을 빌려 읽고(fd 열림) 있으면 책은 서가 공간을 계속 차지한다. ⚠️ 비유가 깨지는 지점: 하드 링크처럼 카드가 여러 장일 수 있고, 링크 수와 열린 fd가 모두 0이 되는 순간 커널이 즉시 해제한다.
- **묶음(3의 법칙):** 장 구조 3파트(메모리·파일시스템·네트워크) / fd 3계층(fd 테이블·open file table·inode) / 메시지 경계 3방법(길이 접두어·구분자·고정 길이).
- **대칭·순서:** VSZ(예약) ↔ RSS(상주), `rm`(이름 삭제) ↔ inode 해제, `127.0.0.1`(같은 네트워크 공간만) ↔ `0.0.0.0`(모든 인터페이스), `SO_REUSEADDR`(TIME_WAIT 포트 재bind) ↔ `SO_REUSEPORT`(여러 프로세스가 같은 포트 분배). 순서: printf → stdio 버퍼 → 페이지 캐시 → (fsync) → 디스크.
