# 2장. 리눅스 OS 큰 그림

> **🎮 게임 서버 개발자에게** — `recv`/`send`, epoll, 워커 스레드 풀을 다뤄 봤다면 이 장의 대부분은 이미 손에 익은 내용이다. 시스템 콜 비용, errno, 스레드 수와 코어 수의 관계가 그대로 나온다. 결정적으로 새로운 것은 **컨테이너도 결국 같은 커널 위의 프로세스**라는 관점이다. 게임 서버를 컨테이너에 넣으면 커널이 따로 생기는 것이 아니라, 같은 커널이 cgroup 쿼터로 CPU 시간을 잘라 줄 뿐이고, 그 때문에 "코어 수만큼 워커 스레드" 같은 익숙한 공식이 깨진다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 게임 서버를 `--cpus=2` 컨테이너로 옮겼더니 평균 CPU는 낮은데 틱(tick) 지연이 주기적으로 튄다.
> - 서버 머신의 CPU는 한가한데 load average가 계속 높다는 알림이 온다.
> - `ps`도 `top`도 없는 최소 이미지 컨테이너 안에서 프로세스 상태와 열린 소켓 수를 확인해야 한다.

## 코어 — 이것만은 100%

> **한 문장:** 내 프로그램은 유저 모드에 갇혀 시스템 콜·인터럽트·예외로만 커널에 들어가고, 커널은 태스크(R/S/D/Z)를 스케줄링하며 컨테이너의 CPU 제한조차 cgroup 쿼터라는 커널 기능일 뿐이다.

1. **커널 = 하드웨어를 흉내 내는 라이브러리** — 커널은 CPU 시분할·메모리 가상화·자원 중재·격리를 대신하고, "모든 것은 파일(fd)"이며, 그 내부 상태는 `/proc`·`/sys`로 들여다본다. 컨테이너는 이 커널 기능 위의 프로세스다.
2. **유저 → 커널의 문은 세 개뿐** — 시스템 콜, 인터럽트, 예외/폴트. 시스템 콜은 비싸고 실패 시 -1과 `errno`를 남긴다.
3. **스케줄러와 태스크 상태 R/S/D/Z** — 커널은 프로세스·스레드를 모두 태스크로 스케줄링한다. D(인터럽트 불가 대기)는 `kill -9`로도 안 죽고 load average에 포함된다.
4. **컨테이너 CPU 제한 = cgroup 쿼터** — `--cpus=N`은 100ms 주기의 cgroup CPU 쿼터이고, 쿼터를 다 쓰면 컨테이너 전체가 다음 주기까지 스로틀링된다.

## C++·TCP 서버 경험에서 출발하기

| 이미 아는 것 (C++/소켓 서버) | 이 장의 개념 | 같은 점 | ⚠️ 다른 점 (유추가 깨지는 곳) |
|---|---|---|---|
| `recv`/`send`/`epoll_wait` 호출 | 시스템 콜 | 유저 모드에서 커널로 들어가는 명시적 요청이고, 호출마다 비용이 든다 | 컨테이너 안 프로세스도 **호스트와 같은 커널**에 직접 시스템 콜을 한다. 컨테이너마다 커널이 따로 있는 것이 아니다 |
| 논블로킹 소켓의 `EAGAIN`/`EWOULDBLOCK`, `EINTR` 재시도 | `errno` 규약 | 실패는 -1 + `errno`, `EAGAIN`은 에러가 아니라 "지금은 없음" | 거의 그대로 적용된다. 컨테이너의 fd 한도(`EMFILE`의 기준)는 도커 데몬의 기본값을 상속한다는 점만 새롭다([4장](04-메모리-파일시스템-네트워크-기초.md)) |
| 워커 스레드 수 = 코어 수 (`std::thread::hardware_concurrency()`) | cgroup CPU 쿼터 (`--cpus`) | CPU 바운드 스레드 수는 코어 수가 상한이라는 원리는 같다 | 코어 수를 직접 읽는 코드는 쿼터가 아니라 **호스트의 코어 수**를 얻는다. 32코어 호스트에서 `--cpus=2`면 32개 스레드가 쿼터를 몇 ms 만에 소진하고 나머지 시간을 통째로 멈춘다 |
| 프레임/틱 지연 스파이크 프로파일링 | 스로틀링 | 평균은 멀쩡한데 순간 지연이 튄다 | 원인이 내 코드나 락이 아니라 **쿼터 소진으로 컨테이너 전체가 정지**한 것일 수 있다. `cpu.stat`의 `nr_throttled`로 확인한다 |
| `top`/`ps`로 서버 프로세스 상태 보기 | 태스크 상태 R/S/D/Z, `/proc` | STAT 컬럼을 읽는다 | 커널은 스레드도 태스크로 같게 다룬다. D 상태는 `kill -9`로 안 죽고 CPU가 놀아도 load를 올린다 |

> **🧭 읽기 전에 (2분)** — 아래 질문에 추측으로 답을 적고 정독하며 고쳐 쓰세요.
> 1. 내 프로그램이 디스크나 네트워크 카드에 직접 명령하지 못하고 커널을 거쳐야 하는 이유는 무엇일까?
> 2. `read()`를 1바이트씩 반복 호출하는 코드는 왜 느릴까?
> 3. CPU는 한가한데 load average가 높다면 무슨 일이 벌어지고 있는 걸까?
> 4. 스레드 16개짜리 프로그램을 `--cpus=2` 컨테이너에서 돌리면 무슨 일이 생길까?
>
> **처리법:** 🛠 실습 `strace -c ./myprog`, `cat /proc/self/status`, `ls -l /proc/self/fd`, `vmstat 1`, `cat /sys/fs/cgroup/cpu.stat` → 바로 실행 · 🗺 관계도 유저 모드 → (시스템 콜·인터럽트·예외) → 커널 모드, 태스크 상태 R/S/D/Z 전이, 스케줄러 ↔ cgroup CPU 쿼터 · 📦 카드로 errno 표(`EINTR`, `EAGAIN`, `EMFILE`, `ENOMEM`, `EPIPE`, `EADDRINUSE`), nice 범위 -20&#126;+19, CFS→EEVDF(6.6), 쿼터 주기 100ms

### 이 장에서 배우는 것

- 왜 Docker와 Kubernetes를 배우기 전에 리눅스 OS를 알아야 하는지
- 커널 모드와 유저 모드가 무엇이고, 프로그램이 커널에 요청하는 길(시스템 콜)이 무엇인지
- 프로세스(태스크)의 상태(R, S, D, Z)와 스케줄러가 CPU를 나누는 방식의 기초
- `/proc`으로 커널 내부를 들여다보는 방법
- 컨테이너의 CPU 제한(cgroup)이 어떻게 동작하는지

## 코어 1. 커널 = 하드웨어를 흉내 내는 라이브러리

### 1.1 왜 OS를 알아야 하는가

**한 줄 요약:** 컨테이너의 이상한 동작은 프레임워크가 아니라 커널 동작으로 설명된다.

컨테이너를 처음 다루면 이런 질문에 부딪힌다.

- 스레드 8개짜리 프로그램이 컨테이너에서 `--cpus=1`로 돌면 왜 이상하게 느려지는가?
- 컨테이너에서 PID 1로 뜬 내 서버가 `docker stop`에 10초 동안 안 죽고 강제 종료되는 이유는?
- 로그 파일을 `rm`했는데 왜 디스크 사용량이 줄지 않는가?

이 질문의 답은 프레임워크 문서가 아니라 **커널이 그 뒤에서 무엇을 하고 있는지**에 있다. 그리고 원문은 이렇게 말한다. 도커 컨테이너는 사실상 "리눅스 커널 기능(namespace, cgroup) 위의 프로세스"다. 즉 컨테이너를 이해하려면 먼저 리눅스 프로세스를 이해해야 한다. (첫 질문은 이 장 코어 4, 둘째는 [3장](03-프로세스와-시그널.md), 셋째는 [4장](04-메모리-파일시스템-네트워크-기초.md)에서 답한다)

### 1.2 커널이 대신 해주는 일

**한 줄 요약:** 시분할·가상화·중재·격리 네 축, 그리고 "모든 것은 파일".

프로그래머 입장에서 OS는 **하드웨어를 흉내 내는 거대한 라이브러리**다. 커널은 다음을 대신 해준다.

| 축 | 설명 |
|---|---|
| CPU 시분할 | 코어보다 많은 프로세스/스레드를 동시에 실행하는 것처럼 보이게 한다 |
| 메모리 가상화 | 모든 프로세스가 독립된 주소 공간을 가진 것처럼 착각하게 한다 |
| 자원 중재 | 여러 프로그램이 같은 디스크, 같은 네트워크 카드를 써도 안전하게 만든다 |
| 격리와 보호 | 한 프로그램의 버그가 다른 프로그램이나 커널을 건드리지 못하게 막는다 |

여기에 리눅스 고유의 철학이 하나 더 있다. **"모든 것은 파일이다"**. 디스크 파일, 소켓, 파이프, 디바이스, 타이머, 시그널까지 **파일 디스크립터(fd)** 하나로 다룬다. 이 책에서도 계속 등장한다.

### 1.3 /proc과 /sys: 커널 속을 들여다보는 창

**한 줄 요약:** 커널 상태는 가상 파일로 노출되고, 모니터링 도구는 모두 그것을 읽는다.

리눅스는 커널 내부 상태를 **파일처럼 읽을 수 있게** 노출한다. `/proc`은 디스크에 없는 가상 파일시스템이다.

```bash
cat /proc/self/status        # 지금 이 셸 프로세스의 상태 (VmRSS, Threads, State...)
ls -l /proc/self/fd          # 열린 파일 디스크립터 목록
cat /proc/self/maps          # 가상 주소 공간 레이아웃
cat /proc/cpuinfo            # CPU 정보
cat /proc/meminfo            # 시스템 메모리 통계
cat /proc/loadavg            # load average
```

`ps`, `top`, `free`, `lsof` 같은 도구는 전부 `/proc`을 읽어서 보여주는 것이다. 도구가 없는 최소 컨테이너 환경에서도 `cat /proc/...`만은 항상 된다.

## 코어 2. 유저 → 커널의 문은 세 개뿐

### 2.1 커널 모드와 유저 모드

**한 줄 요약:** 유저 코드는 세 경로로만 커널에 들어가고, 커널은 언제든 유저 코드를 끊을 수 있다.

CPU에는 최소 두 가지 특권 수준이 있다. x86-64에서는 ring 0(커널)과 ring 3(유저)이다.

- **유저 모드**: 내 프로그램이 도는 곳. 자기 가상 주소 공간의 메모리만 접근할 수 있고, 하드웨어에 직접 명령을 내릴 수 없다.
- **커널 모드**: 커널이 도는 곳. 모든 메모리와 하드웨어에 접근할 수 있다.

유저 모드 코드가 커널 모드로 들어가는 길은 정확히 세 가지뿐이다.

1. **시스템 콜**: 프로그램이 명시적으로 커널에 요청 (`read`, `write`, `mmap`...)
2. **인터럽트**: 하드웨어가 알림 (네트워크 패킷 도착, 타이머 틱, 디스크 I/O 완료)
3. **예외/폴트**: CPU가 명령 실행 중 문제를 감지 (페이지 폴트, 0으로 나누기, 잘못된 주소 접근)

반대로 커널은 언제든(인터럽트로) 유저 코드를 중단시키고 다른 일을 할 수 있다. 이 비대칭이 "격리와 보호"의 근간이다.

### 2.2 시스템 콜: 프로그램이 커널에 말하는 유일한 방법

**한 줄 요약:** 시스템 콜은 비싸고, glibc는 래퍼이며, `strace`로 다 보인다.

```c
ssize_t n = read(fd, buf, 4096);
```

이 한 줄에서 벌어지는 일을 단순화하면 다음과 같다.

```
유저 모드                              커널 모드
────────────────────────────────────────────────────────────
read(fd, buf, 4096)   ← glibc 래퍼 함수
  │ syscall 명령         ────────────▶  entry_SYSCALL_64
  │                                      ├ 인자 검증
  │                                      ├ fd → 파일 객체 조회
  │                                      ├ 파일시스템/소켓/파이프의 read 구현 호출
  │                                      │   (데이터가 없으면 여기서 프로세스를 잠재움)
  │                                      └ 결과를 담아 복귀
  │ ◀──────────────────────────────────  sysret
  ▼
n
```

기억할 것은 세 가지다.

- **비용**: 시스템 콜 하나는 함수 호출보다 훨씬 비싸다. 그래서 `read`를 1바이트씩 호출하는 코드는 느리고, stdio가 버퍼링을 한다.
- **glibc는 래퍼일 뿐**: `read()`, `malloc()`, `printf()`는 라이브러리 함수다. `malloc`은 내부적으로 가끔만 `brk`/`mmap`을 부르고, `printf`는 버퍼가 찰 때만 `write`를 부른다.
- **`strace`로 보면 다 나온다**: `strace -c ./myprog`는 프로그램이 부른 시스템 콜을 종류별로 집계해준다.

### 2.3 errno: 커널의 실패 통보 규약

**한 줄 요약:** 실패는 -1 + `errno`, 컨테이너 운영에서 자주 보는 여섯 개를 기억한다.

시스템 콜이 실패하면 -1을 반환하고 `errno`에 이유를 넣는다. 컨테이너 운영 중 자주 보게 될 것들만 추리면 다음과 같다.

| errno | 의미 | 실무에서 만나는 상황 |
|---|---|---|
| `EINTR` | 시그널에 의해 시스템 콜이 중단됨 | 블로킹 `read`/`accept` 중 시그널 도착. 재시도해야 한다 |
| `EAGAIN` | 지금은 데이터가 없음(논블로킹) | 에러가 아니라 정상적인 상황 |
| `EMFILE` | 프로세스의 fd 한도 초과 | `ulimit -n` 기본 1024. 커넥션 많은 서버에서 흔함 |
| `ENOMEM` | 메모리 부족 | 오버커밋 때문에 실제로는 거의 안 나온다 ([4장](04-메모리-파일시스템-네트워크-기초.md)) |
| `EPIPE` | 닫힌 파이프/소켓에 쓰기 | 상대가 끊었는데 `write` |
| `EADDRINUSE` | 주소가 이미 사용 중 | `TIME_WAIT` 소켓 ([4장](04-메모리-파일시스템-네트워크-기초.md)) |

### 2.4 인터럽트: 커널이 내 CPU 시간을 쓰는 순간

**한 줄 요약:** `%si`/`%hi`가 높으면 내 코드가 아니라 커널이 인터럽트 처리에 CPU를 쓰는 중이다.

네트워크 카드에 패킷이 도착하면 CPU에 인터럽트가 걸린다. 그 순간 어떤 프로세스가 돌고 있었건 CPU는 커널의 핸들러로 점프한다. 핸들러가 패킷을 큐에 넣고 복귀하면 원래 프로세스가 재개된다.

`top`의 `%si`(softirq), `%hi`(hardirq)가 높다면 내 코드가 아니라 커널이 인터럽트 처리에 CPU를 쓰고 있다는 뜻이다. 내 코드가 "아무것도 안 했는데" 지연이 튄다면 인터럽트나 다른 프로세스에 CPU를 빼앗긴 것일 수 있다.

## 코어 3. 스케줄러와 태스크 상태 R/S/D/Z

### 3.1 스케줄러: 코어보다 많은 태스크를 돌리는 법

**한 줄 요약:** 커널은 프로세스와 스레드를 모두 `task_struct` 하나로 다루며 runnable 태스크 사이에서 CPU를 나눈다.

리눅스 스케줄러의 단위는 **태스크**(task)다. 커널은 프로세스와 스레드를 구분하지 않고 모두 `task_struct` 하나로 다룬다. 스케줄러는 "실행 가능한(runnable)" 태스크들 사이에서 CPU 시간을 나눈다.

### 3.2 태스크의 상태

**한 줄 요약:** R(실행·대기), S(깨울 수 있는 대기), D(깨울 수 없는 대기), Z(좀비). D는 load에 포함된다.

```
          fork/clone
              │
              ▼
   ┌──────▶ Runnable (R) ──── 스케줄러가 선택 ────▶ Running
   │            ▲                                     │
   │            │ 이벤트 발생(데이터 도착, 락 해제 등)    │ I/O 대기, sleep, 락 대기
   │            │                                     ▼
   │        Sleeping ◀────────────────────────────────┘
   │         (S: interruptible / D: uninterruptible)
   │
   └──── 타임슬라이스 소진 또는 더 급한 태스크 등장(preemption)

   종료 → Zombie (Z) → 부모가 wait() → 소멸
```

`ps`/`top`의 STAT 컬럼이 이것이다.

| 상태 | 의미 |
|---|---|
| **R** | 실행 중이거나 실행 대기 중. CPU를 원하는 태스크가 코어 수보다 많으면 `load average`가 올라간다 |
| **S** | 인터럽트 가능한 대기. 서버 프로세스의 대부분은 평소에 이 상태 |
| **D** | 인터럽트 불가능한 대기(주로 디스크 I/O, NFS). **`kill -9`로도 안 죽는다**. 많으면 I/O 병목 |
| **Z** | 좀비. 종료했지만 부모가 회수하지 않음 ([3장](03-프로세스와-시그널.md)) |

D 상태는 load average에도 포함된다. CPU는 놀고 있는데 load가 높은 이유다.

### 3.3 공평한 분배의 기본 아이디어

**한 줄 요약:** vruntime이 가장 적은 태스크를 고르고, nice는 가중치이며, CPU 바운드 스레드 수의 상한은 코어 수다.

리눅스는 오랫동안 CFS(Completely Fair Scheduler)를 썼고, 6.6부터 EEVDF로 교체됐다. 입문자는 핵심 아이디어만 알면 된다.

- 각 태스크의 **가상 실행 시간**(vruntime)을 추적하고, 가장 적게 실행된 태스크를 다음에 고른다. "공평하게 나눈다"가 기본값이다.
- **nice 값**(-20 &#126; +19)은 가중치다. nice가 낮을수록 더 많은 CPU를 받는다. `nice -n 10 ./batch_job`은 "다른 것들에 양보하라"는 뜻이다.
- I/O 바운드 태스크는 자주 잠들어서 자연히 우선권을 얻는다.
- CPU 바운드 작업이라면 스레드 수 = 코어 수가 상한이다. 그 이상은 컨텍스트 스위칭 비용만 늘린다.

**컨텍스트 스위칭**의 진짜 비용은 레지스터 저장이 아니라 간접 비용(CPU 캐시 오염, TLB 플러시)이다. `vmstat 1`의 `cs` 컬럼이 수만&#126;수십만이면 "스레드가 너무 많거나 락 경합이 심하다"는 신호다.

## 코어 4. 컨테이너 CPU 제한 = cgroup 쿼터

### 4.1 컨테이너 시대의 스케줄러: cgroup CPU 제한

**한 줄 요약:** `--cpus=2`는 100ms마다 200ms 쿼터이고, 다 쓰면 컨테이너 안 모든 태스크가 다음 주기까지 멈춘다.

도커의 `--cpus=2`는 **cgroup의 CPU 대역폭 제어**다. 100ms 주기마다 200ms의 CPU 시간(2코어분)을 쿼터로 준다. 쿼터를 다 쓰면 다음 주기까지 컨테이너 안의 모든 태스크가 **스로틀링**된다.

함정: 컨테이너에 스레드가 16개인데 `--cpus=2`라면, 16개가 동시에 뛰어들어 12.5ms 만에 쿼터를 소진하고 나머지 87.5ms를 통째로 멈춘다. 지연 시간이 들쭉날쭉해지는 전형적인 원인이다.

```bash
cat /sys/fs/cgroup/cpu.stat    # nr_throttled, throttled_usec 확인
```

대응은 스레드 풀 크기를 실제 쿼터에 맞추는 것이다. 많은 런타임(Java 10+, .NET 등)이 cgroup 한도를 자동 인식하지만, `nproc` 등으로 코어 수를 직접 읽는 코드는 **호스트의 코어 수**를 얻는다.

> **[보충]** 쿠버네티스의 CPU limit 설정(`resources.limits.cpu`)도 위 cgroup 쿼터 방식과 연결된다. 이는 [19장](../3부-쿠버네티스-핵심/19-리소스-요청-제한과-스케줄링-기초.md)(리소스 요청·제한)에서 다시 다룬다. 지금은 "컨테이너 CPU 제한 = 커널 cgroup 기능"이라고만 기억하면 충분하다.

cgroup 자체의 구조는 [7장](../2부-컨테이너와-Docker/07-자원-제어-cgroups.md)에서 다룬다.

## 실무 적용

### 체크리스트

- [ ] 커널은 CPU 시분할, 메모리 가상화, 자원 중재, 격리를 대신해주고, 리눅스는 "모든 것은 파일(fd)"이라는 철학을 따른다.
- [ ] 유저 모드는 제한된 모드이고, 커널로 들어가는 길은 시스템 콜, 인터럽트, 예외 세 가지뿐이다.
- [ ] 시스템 콜은 비싸고, 실패하면 -1과 `errno`로 알려준다. 1바이트 단위 `read`/`write` 같은 잦은 호출을 버퍼링으로 줄였는가? (`EINTR`은 재시도, `EAGAIN`은 정상)
- [ ] 커넥션이 많은 서버라면 fd 한도(`ulimit -n` 기본 1024)를 올렸는가?
- [ ] 태스크 상태 R/S/D/Z를 구분하면 `ps`/`top` 출력이 읽힌다. D 상태는 `kill -9`로도 안 죽는다. CPU가 한가한데 load가 높으면 D를 먼저 본다.
- [ ] 컨테이너의 `--cpus` 제한은 cgroup CPU 쿼터이고, 초과하면 스로틀링된다. 스레드 풀 크기를 호스트 코어 수가 아니라 쿼터에 맞췄는가? `cpu.stat`의 `nr_throttled`를 확인했는가?
- [ ] `/proc`은 커널 상태를 파일처럼 보여주며, 대부분의 모니터링 도구가 이를 읽는다. 도구가 없는 컨테이너에서는 `/proc`을 직접 읽는다.

### 3. 기억 고리

- **C++ 유추:** 워커 스레드 수 = `hardware_concurrency()` ⚠️ 컨테이너에서는 호스트 코어 수가 나오므로 cgroup 쿼터와 어긋나고, 남는 스레드는 처리량이 아니라 스로틀링을 만든다.
- **C++ 유추:** `recv`/`send` = 시스템 콜 ⚠️ 컨테이너도 같은 호스트 커널을 쓰므로 "컨테이너 안 커널"은 없다. 컨테이너 제한은 그 커널의 cgroup 기능이다.
- **비유:** 시스템 콜 = 관공서 창구. 직접 금고(하드웨어)에 손대지 못하고 창구 직원(커널)에게 서류를 내야 하며, 한 번 갈 때마다 번호표 비용이 든다(그래서 모아서 간다 = 버퍼링). ⚠️ 비유가 깨지는 지점: 창구는 손님이 부를 때만 일하지만, 커널은 인터럽트로 언제든 내 실행을 끊고 끼어든다.
- **비유:** cgroup CPU 쿼터 = 100ms마다 충전되는 교통카드 잔액. 16명이 한꺼번에 쓰면 금방 바닥나고 다음 충전까지 모두 못 탄다. ⚠️ 비유가 깨지는 지점: "못 탄다"는 것은 요청 거부나 에러가 아니라 다음 주기까지의 일시 정지(스로틀링)이고, 카드 한 장을 컨테이너 안 모든 태스크가 함께 쓴다.
- **묶음(3의 법칙):** 커널 진입 3경로(시스템 콜·인터럽트·예외) / 시스템 콜 기억 3가지(비용·glibc 래퍼·strace) / 이 장 첫머리의 컨테이너 질문 3개(`--cpus` 지연·PID 1 종료·`rm` 후 용량).
- **대칭·순서:** S(깨울 수 있음) ↔ D(깨울 수 없음, `kill -9` 불가). 상태 흐름: fork → R → Running → S/D → R … → Z → wait → 소멸.

### 4. 가르치기 · 반대편 서기

- **거울 설명 (1분, 원고 없이):** "`read()` 한 줄이 커널에서 무슨 일을 하는가"를 처음 듣는 사람에게 설명해 보세요. 말이 막히는 지점 = 지식의 구멍.
- **C++ 서버 동료에게 설명하기:** "우리 서버를 `--cpus=2` 컨테이너에 넣으면 왜 워커 스레드 수를 다시 정해야 하는가"를 cgroup 쿼터와 스로틀링으로 1분 안에 설명해 보세요.
- **랜덤 논리 게임:** A "스레드를 많이 만들수록 처리량이 늘어난다" vs B "CPU 바운드라면 스레드 수는 코어(쿼터) 수가 상한이다" — 양쪽을 번갈아 변호해 보세요. (컨텍스트 스위칭 비용, cgroup 스로틀링, I/O 바운드 태스크를 근거로)
