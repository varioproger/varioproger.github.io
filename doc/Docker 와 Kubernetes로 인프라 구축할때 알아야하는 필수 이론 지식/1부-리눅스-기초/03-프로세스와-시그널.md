# 3장. 프로세스와 시그널

> **🎮 게임 서버 개발자에게** — 점검 공지 → 신규 접속 차단 → 접속 중인 유저 세션 저장 → 서버 종료. 게임 서버가 늘 해 온 이 종료 절차가 리눅스에서는 **SIGTERM 핸들러**로 시작된다. 결정적으로 다른 점은 두 가지다. 첫째, 이제 종료 명령은 운영자가 아니라 `docker stop`·쿠버네티스가 보내고 **정해진 유예 시간(10초/30초)이 지나면 SIGKILL로 강제 종료**한다. 둘째, 컨테이너 안에서 내 서버가 **PID 1**이 되면 init 프로세스의 책임(고아 회수, 시그널 처리)까지 떠안는다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 점검 배포 중 접속 중인 유저의 요청이 끊기고 마지막 세션 저장이 누락된다.
> - `docker stop`이 매번 정확히 10초 걸린 뒤에야 끝나고, 종료 코드는 137이다.
> - 쿠버네티스 Pod 상태에 `Exit Code: 137`이 찍혀 원인을 좁혀야 한다.

## 코어 — 이것만은 100%

> **한 문장:** 프로세스는 fork로 복제되고 exec로 교체되며 부모의 wait로 회수되는데, 컨테이너에서 PID 1이 된 내 서버는 이 회수(좀비)와 시그널 처리(SIGTERM)를 스스로 책임져야 하고, 못 하면 유예 시간 뒤 SIGKILL(137)로 끝난다.

1. **프로세스 = 그릇, fork → exec → wait** — 프로세스는 주소 공간·fd 테이블·스레드 등을 묶은 그릇이고, 새 프로그램은 fork(COW 복제) 후 exec(교체, PID·fd 유지)로 실행되며 부모의 wait로 회수된다.
2. **좀비·고아와 PID 1의 책임** — 종료한 자식은 부모가 `wait`할 때까지 좀비로 남고 `kill -9`로 못 없앤다. 고아는 PID 1이 입양한다. 컨테이너에서 PID 1인 내 서버는 회수와 시그널 처리를 직접 책임져야 하므로 `tini`/`--init`을 쓰거나 직접 구현한다.
3. **시그널 = 번호 하나짜리 비동기 통지, 종료 코드 = 128 + N** — SIGKILL(9)·SIGSTOP은 잡을 수 없다. 137(SIGKILL: OOM 등), 143(SIGTERM)으로 죽은 이유를 읽는다.
4. **우아한 종료: SIGTERM → 유예 → SIGKILL** — SIGTERM에 새 요청 중단 → 진행 중 요청 마무리 → 연결 닫기 → 종료를 수행한다. 도커 10초, 쿠버네티스 30초가 지나면 SIGKILL이며, 셸이 PID 1이 되지 않게 exec 형식 CMD를 쓴다.

## 코어 1. 프로세스 = 그릇, fork → exec → wait

### 1.1 프로세스란 무엇인가

**한 줄 요약:** 프로세스는 "그릇"이고, 실제 실행은 스레드가 한다.

프로세스는 "실행 중인 프로그램 하나에 대한 커널의 관리 단위"다. 실제로는 다음의 묶음이다.

- **가상 주소 공간**: 이 프로세스만 보는 독립된 메모리 뷰
- **파일 디스크립터 테이블**: 열린 파일, 소켓, 파이프 등에 대한 참조
- **최소 1개의 스레드(태스크)**: 실제로 코드를 실행하는 주체
- **자격 증명**: UID/GID, capabilities
- **환경**: 인자, 환경변수, 현재 디렉터리, 시그널 처리 방식, 자원 한도(`ulimit`)

핵심은 **프로세스는 "그릇"이고, 실제 실행은 스레드가 한다**는 점이다.

프로세스의 메모리는 대략 다음과 같이 배치된다. `cat /proc/self/maps`로 직접 볼 수 있다.

```
높은 주소  ┌──────────────────────┐
          │ 스택                  │ ↓ 지역 변수, 리턴 주소
          │ 메모리 매핑 영역        │ 공유 라이브러리, mmap()한 파일
          │ 힙 (brk)              │ ↑ malloc이 관리
          ├──────────────────────┤
          │ .bss / .data          │ 전역 변수
          │ .text (코드)           │ 읽기 전용
낮은 주소  └──────────────────────┘
```

### 1.2 프로세스 생성: fork, exec, wait

**한 줄 요약:** fork(COW 복제) → exec(교체, PID·fd 유지) → wait(종료 코드 회수).

리눅스는 "새 프로그램 실행"을 두 단계로 나눈다.

```c
pid_t pid = fork();              // 1. 현재 프로세스를 복제
if (pid == 0) {                  // 자식
    execve("/bin/ls", argv, envp);   // 2. 자신을 다른 프로그램으로 교체
    _exit(127);                      //    exec이 반환했다면 실패
} else {                         // 부모
    int status;
    waitpid(pid, &status, 0);        // 3. 자식 종료 대기 + 종료 코드 회수
}
```

- **fork**: 부모를 복제한다. 실제로는 페이지를 복사하지 않고, 쓰기가 일어날 때 그 페이지만 복사하는 **Copy-on-Write(COW)** 방식이라 저렴하다.
- **exec**: 현재 프로세스의 코드, 데이터, 힙, 스택을 모두 버리고 새 실행 파일을 적재한다. **PID는 그대로**이고, 열린 fd도 기본적으로 유지된다. 셸의 `ls > out.txt` 리다이렉션이 이 원리다.
- **wait**: 부모가 자식의 종료 코드를 회수한다.

원문이 지적하는 주의점 한 가지만 기억하자. 멀티스레드 프로세스에서는 fork 직후 exec만 하라.

## 코어 2. 좀비·고아와 PID 1의 책임

### 2.1 프로세스 종료, 좀비, 고아

**한 줄 요약:** 좀비는 부모가 고쳐야 사라지고, 고아는 PID 1이 입양해 회수한다.

프로세스가 종료하면 커널이 fd를 닫고 메모리를 해제한 뒤, 종료 코드를 보관하고 **부모에게 `SIGCHLD`를 보낸다**.

이 시점에서 프로세스는 **좀비**(Z)가 된다(태스크 상태 Z → [2장](02-리눅스-OS-큰그림.md)). 메모리도 fd도 없지만, 종료 코드를 담은 정보와 PID만 남아 있다. 부모가 `wait()`/`waitpid()`로 회수하면 완전히 사라진다.

- **좀비가 쌓이면** PID를 낭비해서 결국 `fork: Resource temporarily unavailable`이 난다. 좀비는 `kill -9`로 죽일 수 없다. 이미 죽었기 때문이다. **부모를 고쳐야 한다.**
- **고아(Orphan)**: 부모가 먼저 죽은 자식. **PID 1(init/systemd)** 또는 "subreaper"에 재입양되고, init은 주기적으로 `wait`하여 고아가 좀비로 남지 않게 한다.

```bash
ps -eo stat,pid,cmd | awk '$1 ~ /Z/'    # 좀비 찾기
ps -eo pid,ppid,pgid,sid,stat,cmd --forest   # 프로세스 트리
```

### 2.2 컨테이너의 PID 1 문제

**한 줄 요약:** PID 1이 된 내 서버는 고아를 떠안고, 핸들러 없는 시그널은 커널이 무시한다.

도커 컨테이너 안에서는 **내 서버 프로세스가 PID 1**이 되는 경우가 많다. 그러면 두 가지 문제가 생긴다.

1. 컨테이너 내 모든 고아 프로세스가 내 서버에 재입양되는데, 내 서버가 `wait`할 줄 모르면 **좀비가 누적**된다.
2. PID 1은 시그널 처리가 특별하다. 핸들러를 등록하지 않은 시그널은 **커널이 무시**한다. 그래서 `docker stop`(SIGTERM)에 반응하지 않고 10초 뒤 SIGKILL로 강제 종료된다.

해결책은 `tini`나 `dumb-init`을 ENTRYPOINT로 쓰거나(`docker run --init`), 직접 SIGTERM 핸들러와 SIGCHLD 회수 로직을 구현하는 것이다. (PID 네임스페이스는 [6장](../2부-컨테이너와-Docker/06-컨테이너-격리-네임스페이스.md), Dockerfile의 ENTRYPOINT와 init 구성은 [9장](../2부-컨테이너와-Docker/09-Dockerfile과-이미지-빌드.md)에서 다룬다)

### 2.3 데몬으로 만들지 말고 포그라운드로 실행한다

**한 줄 요약:** 데몬화는 systemd·컨테이너가 대신하므로 서버는 포그라운드 + stdout 로그로 실행한다.

전통적인 서버는 스스로 터미널과 분리된 백그라운드 프로세스(데몬)가 되도록 만들었다. `fork` 후 `setsid()`로 새 세션을 만들고, stdin/out/err을 `/dev/null`로 돌리는 식이다. 터미널(SSH)이 끊기면 그 세션에 `SIGHUP`이 전파되어 백그라운드 서버까지 죽을 수 있기 때문이다. 요즘은 systemd가 이 일을 대신 해주므로, 서버는 **포그라운드로 실행하고 로그를 stdout에 쓰는** 것이 권장된다. 컨테이너도 같은 원칙이다.

## 코어 3. 시그널 = 번호 하나짜리 비동기 통지, 종료 코드 = 128 + N

### 3.1 시그널이란

**한 줄 요약:** 시그널마다 기본 동작이 있고, SIGKILL과 SIGSTOP만은 잡을 수도 무시할 수도 없다.

시그널은 커널이 프로세스에 보내는 **번호 하나짜리 비동기 통지**다. 도착하면 프로세스가 무엇을 하고 있었든 중단되고 미리 정해진 동작이 실행된다. `Ctrl+C`, `kill`, `docker stop`, OOM killer, 세그폴트, 자식 종료 통지가 모두 시그널로 도착한다.

시그널마다 **기본 동작**이 있다.

| 기본 동작 | 시그널 |
|---|---|
| 종료 | `SIGTERM`(15), `SIGINT`(2, Ctrl+C), `SIGHUP`(1), `SIGPIPE`(13) |
| 종료 + 코어 덤프 | `SIGSEGV`(11), `SIGABRT`(6), `SIGQUIT`(3) |
| 무시 | `SIGCHLD`(17) |
| 정지 / 재개 | `SIGSTOP`, `SIGTSTP`(Ctrl+Z) / `SIGCONT` |

프로세스는 대부분의 시그널에 대해 **핸들러를 등록**하거나 **무시**하거나 **블록**(나중에 받기)할 수 있다. 예외는 **`SIGKILL`(9)과 `SIGSTOP`이다.** 이 둘은 잡을 수도 무시할 수도 없다. 그래서 `kill -9`는 최후의 수단이다. 정리 코드를 실행할 기회가 없어 임시 파일, 락 파일, 절반 쓴 데이터가 남는다.

### 3.2 시그널은 누가 보내는가

**한 줄 요약:** 커널, 다른 프로세스(도커·systemd·쿠버네티스 포함), 터미널.

- 커널: 하드웨어 예외(`SIGSEGV`), 이벤트(`SIGCHLD`, `SIGPIPE`, `SIGHUP`)
- 다른 프로세스: `kill(pid, sig)`. 같은 UID거나 root여야 한다. `docker stop`(SIGTERM 후 10초 뒤 SIGKILL), systemd, 쿠버네티스(SIGTERM 후 `terminationGracePeriodSeconds`)도 여기에 속한다.
- 터미널: Ctrl+C는 SIGINT를 전경 프로세스 그룹 전체에 보낸다.

### 3.3 종료 코드로 시그널 읽기

**한 줄 요약:** 종료 코드 = 128 + 시그널 번호. 137이면 첫 의심은 메모리 제한이다.

시그널로 죽은 프로세스의 종료 상태는 셸에서 `128 + 시그널 번호`로 보인다.

| 종료 코드 | 의미 |
|---|---|
| 130 | SIGINT (Ctrl+C) |
| 137 | SIGKILL: **OOM killer**, `kill -9`, `docker stop` 타임아웃 |
| 139 | SIGSEGV: 세그폴트 |
| 143 | SIGTERM: 정상 종료 요청 |
| 134 | SIGABRT: `abort()`, assert 실패 등 |

쿠버네티스 파드의 `Exit Code: 137`을 보면 첫 의심은 메모리 제한이다([4장](04-메모리-파일시스템-네트워크-기초.md)).

## 코어 4. 우아한 종료: SIGTERM → 유예 → SIGKILL

### 4.1 SIGTERM: 우아한 종료(graceful shutdown)

**한 줄 요약:** 유예 시간 안에 정리를 끝내야 하고, 핸들러는 플래그만 세운다.

`docker stop`, `kubectl delete pod`, `systemctl stop`이 보내는 신호다. 받으면 다음을 해야 한다.

```
SIGTERM 수신
   → 새 요청 수락 중단
   → 진행 중인 요청 마무리
   → 연결 닫기, 상태 저장
   → 종료
```

기본 동작(즉시 종료)에 맡기면 진행 중인 요청이 끊긴다. **유예 시간(도커 10초, 쿠버네티스 30초 기본) 안에 못 끝내면 SIGKILL**이다. 쿠버네티스의 종료 절차와 유예 시간은 [16장](../3부-쿠버네티스-핵심/16-Pod-생명주기와-헬스체크.md)(Pod 생명주기)에서 다시 다룬다.

핸들러에서는 할 수 있는 일이 거의 없으므로, 표준 패턴은 **핸들러가 플래그 하나만 세우고 즉시 반환**, 실제 정리는 메인 루프에서 하는 것이다.

```c
static volatile sig_atomic_t got_term = 0;
static void on_term(int sig) { got_term = 1; }   // 플래그만 세운다

// sigaction(SIGTERM, ...)로 등록
while (!got_term) { do_work(); }
cleanup_and_exit();
```

### 4.2 셸 스크립트 함정

**한 줄 요약:** 셸이 PID 1이면 시그널이 자식에게 가지 않는다. `exec` 또는 exec 형식 CMD.

`CMD ["sh", "-c", "node server.js"]`처럼 셸이 PID 1이면 셸은 자식에게 시그널을 **전달하지 않는다.** `exec node server.js`로 셸을 교체하거나 exec 형식 `CMD ["node", "server.js"]`를 써야 한다.

### 4.3 SIGCHLD: 좀비 방지

**한 줄 요약:** 표준 시그널은 큐잉되지 않으므로 `waitpid(-1, ..., WNOHANG)`를 루프로 돈다.

자식이 종료하면 온다. 기본 동작은 무시지만, 무시된다고 좀비가 회수되는 것은 아니다. `waitpid(-1, ..., WNOHANG)` 루프로 회수하거나, 종료 코드가 필요 없으면 `SIG_IGN`으로 명시적으로 설정해 커널이 자동 회수하게 한다. 표준 시그널은 큐잉되지 않아서 여러 자식이 동시에 죽어도 한 번만 올 수 있으므로 핸들러는 루프로 회수해야 한다.

```c
void on_sigchld(int sig) {
    int saved = errno;
    while (waitpid(-1, NULL, WNOHANG) > 0) { }
    errno = saved;
}
```

### 4.4 SIGHUP, SIGPIPE

**한 줄 요약:** SIGHUP은 "설정 다시 읽기"로 재정의하고, SIGPIPE는 네트워크 서버가 시작 시 무시한다.

- `SIGHUP`: 터미널이 끊길 때 오지만, 데몬은 "설정 다시 읽어라"로 재정의하는 것이 관례다(nginx 등). 
- `SIGPIPE`: 상대가 닫은 소켓/파이프에 쓰면 와서 기본 동작이 종료다. 서버가 로그 없이 사라지므로 네트워크 서버는 시작 시 무시하는 것이 일반적이다.

### 4.5 직접 확인해보기

**한 줄 요약:** `SigCgt`가 0인 PID 1은 `docker stop`이 안 먹는다고 예측할 수 있다.

```bash
kill -l                                   # 시그널 번호 목록
kill -TERM <pid>; echo $?                 # 종료 코드 확인 (128+N)
grep -E 'Sig(Pnd|Blk|Ign|Cgt)' /proc/<pid>/status   # 시그널 마스크
strace -e trace=signal -p <pid>           # 시그널 전달 관찰
timeout 5 ./prog                          # 5초 후 SIGTERM 보내기
```

`/proc/<pid>/status`의 `SigCgt`(caught)가 0이면 그 프로세스는 아무 핸들러도 등록하지 않은 것이다. PID 1인 컨테이너 프로세스라면 `docker stop`이 안 먹을 것이라 예측할 수 있다.

## 실무 적용

### 체크리스트

컨테이너 운영 체크리스트:

- [ ] SIGTERM에 우아한 종료 핸들러가 있는가? 유예 시간 안에 끝나는가?
- [ ] 컨테이너에서 PID 1로 뜬다면 init 프로세스(`tini`, `--init`)를 쓰는가?
- [ ] 셸이 PID 1이 되어 시그널을 삼키고 있지 않은가? (`exec`, exec 형식 CMD)
- [ ] 서버를 데몬화하지 않고 포그라운드로 실행하며 로그를 stdout에 쓰는가?
- [ ] 자식을 만든다면 SIGCHLD를 처리하는가?
- [ ] 컨테이너 안에서 root 대신 일반 사용자로 실행하는가? (`docker run --user 1000` 등. 컨테이너의 root는 기본적으로 capabilities가 제한된 root다.)

핵심 요약:

- [ ] 프로세스는 주소 공간, fd 테이블, 스레드 등을 묶은 "그릇"이고, 새 프로그램은 fork(복제) 후 exec(교체)로 실행된다.
- [ ] 종료한 자식은 부모가 `wait`하기 전까지 좀비로 남고, 좀비는 `kill -9`로 못 없앤다. 부모가 먼저 죽으면 PID 1이 입양한다.
- [ ] 컨테이너에서 서버가 PID 1이면 좀비 회수와 시그널 처리를 직접 책임져야 한다. 핸들러 없는 SIGTERM은 PID 1에서 무시된다.
- [ ] SIGTERM은 "정리하고 끝내라"는 요청이고, SIGKILL은 잡을 수 없는 강제 종료다. `docker stop`은 SIGTERM, 10초 후 SIGKILL이며 쿠버네티스는 기본 30초다.
- [ ] 종료 코드 `128 + N`으로 시그널을 읽는다. 137은 SIGKILL(OOM 등), 143은 SIGTERM이다.
- [ ] `sh -c`로 감싼 CMD는 시그널을 자식에게 전달하지 않을 수 있으므로 exec 형식을 쓴다.

### 시나리오로 확인하기

1. **상황:** 점검 배포 때마다 접속 중인 유저의 마지막 요청이 끊기고 세션 저장이 누락된다. 서버는 C++로 짠 단일 바이너리이고 컨테이너의 PID 1로 뜨며, `docker stop`은 늘 정확히 10초 뒤에 끝나고 종료 코드는 137이다. Windows 시절엔 운영 툴의 "종료" 버튼이 서버에 종료 패킷을 보냈기 때문에 시그널 처리는 따로 짜지 않았다.
   **질문:** 무슨 일이 벌어졌고 무엇을 고쳐야 하나?

   <details markdown="1"><summary>답 확인</summary>

   PID 1은 핸들러를 등록하지 않은 시그널을 커널이 무시하므로 SIGTERM이 무시되고, 10초 유예 뒤 SIGKILL(128 + 9 = 137)로 죽는다. 정리 코드를 실행할 기회가 없으니 요청이 끊기고 저장이 누락된다. `sigaction`으로 SIGTERM 핸들러를 등록해 플래그만 세우고, 메인 루프가 새 요청 중단 → 진행 중 요청 마무리 → 연결 닫기·상태 저장 → 종료를 유예 시간 안에 수행하게 한다. 자식을 만든다면 `tini`/`--init`도 고려한다. `/proc/<pid>/status`의 `SigCgt`가 0이면 이 상황을 미리 예측할 수 있다. → 코어 2, 코어 4

   </details>

2. **상황:** Dockerfile에 `CMD ["sh", "-c", "./gameserver --config /etc/game.conf"]`라고 썼다. 서버 코드에는 SIGTERM 핸들러가 있는데도 `docker stop`이 10초 걸린다.
   **질문:** 왜인가?

   <details markdown="1"><summary>답 확인</summary>

   셸이 PID 1이 되고, 셸은 자식(gameserver)에게 시그널을 전달하지 않는다. 핸들러가 있는 서버는 SIGTERM을 받지도 못한다. `exec ./gameserver ...`로 셸을 교체하거나 exec 형식 `CMD ["./gameserver", "--config", "/etc/game.conf"]`를 쓴다. → 코어 4

   </details>

3. **상황:** 쿠버네티스에서 게임 API 서버 Pod가 `Exit Code: 137`로 재시작을 반복한다. 코어 덤프는 없다.
   **질문:** 어떤 시그널이고 무엇부터 의심하나?

   <details markdown="1"><summary>답 확인</summary>

   137 = 128 + 9, 즉 SIGKILL이다. 세그폴트(139)처럼 서버 내부에서 터진 것이 아니라 바깥에서 죽인 것이며, 원인은 OOM killer, `kill -9`, 유예 시간 초과 등이다. 쿠버네티스에서는 첫 의심이 메모리 제한이다([4장](04-메모리-파일시스템-네트워크-기초.md)). → 코어 3

   </details>

4. **상황:** 클라이언트가 갑자기 끊긴 뒤 서버가 로그 한 줄 없이 사라졌다.
   **질문:** 의심할 시그널과 대응은?

   <details markdown="1"><summary>답 확인</summary>

   상대가 닫은 소켓에 쓰면 SIGPIPE가 오고 기본 동작이 종료라서 서버가 로그 없이 사라진다. 네트워크 서버는 시작 시 SIGPIPE를 무시하도록 설정하는 것이 일반적이다(닫힌 소켓에 쓰기를 뜻하는 `EPIPE`는 [2장](02-리눅스-OS-큰그림.md)의 errno 표 참고). → 코어 4

   </details>

5. **상황:** 서버가 외부 툴을 자식 프로세스로 자주 실행하는데, 며칠 지나면 `fork: Resource temporarily unavailable`이 난다.
   **질문:** 원인과 해결은?

   <details markdown="1"><summary>답 확인</summary>

   종료한 자식을 `wait`로 회수하지 않아 좀비가 PID를 낭비하고 있다. 좀비는 `kill -9`로 지울 수 없으므로 부모(서버)를 고친다. SIGCHLD 핸들러에서 `waitpid(-1, NULL, WNOHANG)`를 루프로 돌리거나, 종료 코드가 필요 없으면 `SIG_IGN`으로 설정해 커널이 자동 회수하게 한다. `ps -eo stat,pid,cmd | awk '$1 ~ /Z/'`로 확인한다. → 코어 2, 코어 4

   </details>

   </details>

### 3. 기억 고리

- **C++ 유추:** SIGTERM 우아한 종료 ≈ 점검 종료 절차(신규 접속 차단 → 세션 저장 → 종료). ⚠️ 깨지는 곳: 종료 시점과 마감 시간(10초/30초)을 서버가 아니라 오케스트레이터가 정하고, 넘기면 SIGKILL로 정리 없이 끝난다.
- **C++ 유추:** 크래시 = 세그폴트(139). ⚠️ 깨지는 곳: 137은 크래시가 아니라 바깥에서 SIGKILL로 죽인 것(OOM, kill -9, 타임아웃)이라 코어 덤프도 없다.
- **비유:** 좀비 = 퇴사했지만 인사과(부모)가 퇴직 서류(종료 코드)를 처리하지 않아 사번(PID)만 남은 직원. 본인에게 아무리 나가라고(`kill -9`) 해도 소용없고 인사과가 서류를 처리(`wait`)해야 사번이 반납된다. ⚠️ 비유가 깨지는 지점: 실제로는 메모리·fd도 이미 해제되어 남은 것은 PID와 종료 정보뿐이며, 쌓이면 PID 고갈로 `fork`가 실패한다.
- **비유:** PID 1 = 컨테이너라는 작은 회사의 사장. 고아 직원을 모두 떠맡고(재입양), 규정(핸들러)을 정해 두지 않은 공문(시그널)은 아예 접수되지 않는다. ⚠️ 비유가 깨지는 지점: SIGKILL은 PID 1이 잡을 수 없는 시그널이라, 외부에서 보낸 SIGKILL로는 결국 끝난다(그래서 10초 뒤 강제 종료).
- **묶음(3의 법칙):** 생성 3단계(fork·exec·wait) / PID 1 해결 3가지(tini·`--init`, 직접 핸들러, exec 형식 CMD) / 종료 코드 3대장(130 SIGINT·137 SIGKILL·143 SIGTERM).
- **대칭·순서:** SIGTERM(잡을 수 있음, 정리 후 종료) ↔ SIGKILL(잡을 수 없음, 정리 기회 없음). 순서: SIGTERM → 유예(10초/30초) → SIGKILL.
