# Part 11. 운영 안정성 패턴 (출처: Release It!)

> 이 부의 한 줄 요약: **"장애는 반드시 온다. 막을 수는 없으니, 번지지 않게 설계하라."**
> SaaS는 24시간 켜져 있고, 외부 결제/이메일/DB/다른 서비스에 기대어 동작한다. 그래서 "잘 돌아가는 코드"보다 "망가져도 덜 망가지는 코드"가 더 중요하다.

---

### 1. 안정성이란 무엇인가

#### 1.1 안정성(Stability)의 정의
- 서버 프로세스가 살아 있는 것이 아니라, **충격이나 부품 고장이 있어도 사용자가 계속 일을 처리할 수 있는 것**이 안정성이다.
- 시스템이 받는 힘은 두 종류다.
  - **충격(Impulse)**: 짧고 갑작스러운 폭주. 예) 유명인이 서비스를 언급해 1분 만에 만 명 접속, 새벽에 큐에 메시지 1,000만 건 투입.
  - **스트레스(Stress)**: 오래 지속되는 압박. 예) 결제사 응답이 계속 느림. 그 영향(변형)이 엉뚱한 곳(메모리 증가, DB I/O 증가)에서 나타난다.
- 오래 살아남는 시스템(Longevity)의 적은 **메모리 누수**와 **데이터 증가**다. 둘 다 개발/QA 환경(금방 껐다 켜므로)에서는 거의 안 드러난다.

왜 중요한가: 배포 주기 사이에 며칠씩 버텨야 하는데, 며칠 뒤에만 나타나는 버그는 테스트로 잡기 어렵다. 장시간 부하 테스트(soak test)와 메모리 모니터링이 필요한 이유다.

> 📖 원문: 3장 Defining Stability, Extending Your Life Span

#### 1.2 장애의 사슬: Fault → Error → Failure
| 단계 | 뜻 | 예시 |
|---|---|---|
| Fault (결함) | 내부 상태가 잘못된 조건 (잠복 버그가 터지거나, 경계에서 확인하지 않은 조건) | (보충) 처리 안 한 예외, DB 커넥션 누수 |
| Error (오류) | 눈에 보이는 잘못된 동작 | (보충) 500 응답, 잘못된 금액 |
| Failure (실패) | 시스템이 응답하지 않음 | (보충) 요청이 전부 타임아웃 |

- 결함이 열리면 균열이 시작되고, 결함은 오류로, 오류는 실패로 번진다. 결합이 강할수록 균열이 빨리 퍼진다.

- 균열(crack)은 한 곳에서 시작해 **결합도가 높은 곳을 따라 빠르게 번진다.** 사슬을 뒤에서 보면 필연 같지만, 각 사건은 서로 독립이 아니다. DB가 느려지면 앱 메모리도 위험해진다.
- 결함을 완전히 없애는 것은 불가능하다. 목표는 **결함이 오류로, 오류가 실패로 번지는 것을 끊는 것**이다.
- 자동차의 <strong>충격 흡수 구역(crumple zone)</strong>처럼, 먼저 부서져서 나머지를 지키는 "안전한 실패 모드"를 직접 설계해야 한다. 설계하지 않으면 예측 불가능하고 위험한 방식으로 무너진다.

모든 외부 호출/IO마다 스스로 물어보자.
- 연결이 아예 안 되면? 연결에 10분이 걸리면?
- 연결 후 끊기면? 연결됐는데 응답이 안 오면?
- 응답이 2분 걸리면? 요청이 1만 개 동시에 오면?

왜 중요한가: 이 질문 목록이 곧 이 부 전체의 목차다. 아래 패턴들은 모두 이 질문에 대한 답이다.

> 📖 원문: 3장 Failure Modes, Stopping Crack Propagation, Chain of Failure

### 2. 사고를 부르는 안티패턴 (미리 알아두는 위험 신호)

먼저 "무엇이 시스템을 죽이는가"를 알아야 패턴이 이해된다.

#### 2.1 통합 지점(Integration Points) — 1순위 위험
- DB, 결제 API, 이메일, 다른 마이크로서비스 등 **밖으로 나가는 모든 호출**이 통합 지점이다.
- 통합 지점은 예쁘게 에러를 돌려주지 않는다. 대개 **연결 거부, 무한 대기, 깨진 응답, 아주 느린 응답**으로 실패한다.
- 상대의 장애가 곧 **내 장애**가 된다. 방어하지 않으면 그대로 전염된다.
- 대응: 타임아웃, 서킷 브레이커, 비동기 분리(큐), 핸드셰이킹.

> 📖 원문: 4장 Integration Points

#### 2.2 연쇄 반응(Chain Reactions)과 연쇄 장애(Cascading Failures)
- **연쇄 반응**: 같은 계층의 서버 하나가 죽으면 남은 서버가 그 부하를 떠안고, 더 빨리 죽는다. 대개 메모리 누수, 숨은 경쟁 조건이 원인이다.
- **연쇄 장애**: 한 계층/시스템의 문제가 다른 계층으로 **건너뛰는** 것. 보통 커넥션 풀 고갈에서 시작한다.
  - 호출이 안 돌아오니 스레드(요청)가 커넥션을 쥔 채 대기 → 풀 고갈 → 다른 요청들도 커넥션을 기다리며 정지 → 서비스 전체 정지.
- 대응: 풀에서 자원을 얻을 때 **대기 시간 제한**, 타임아웃, 서킷 브레이커, 상태 확인에 따른 자동 교체(오토스케일링 + 헬스체크).

> 📖 원문: 4장 Chain Reactions, Cascading Failures

#### 2.3 막힌 스레드(Blocked Threads) → Node.js에서의 해석
- 책은 자바 스레드 기준이지만 본질은 같다. **요청을 처리할 자원이 무언가를 기다리며 묶여 있는 것**이 대부분 사고의 직접 원인이다.
- 책은 프로세스가 살아 있어도 모든 스레드가 불가능한 결과를 기다리며 멈춘 "행(hang)"을 대부분 장애의 직접 원인으로 본다. 특히 커넥션 풀, 캐시, 외부 호출 주변에서 잘 생긴다.
- (보충) Node.js에서의 해석: 스레드 대신 "끝나지 않는 Promise"와 "고갈된 커넥션 풀"이 같은 역할을 한다.
  - `await`한 외부 호출이 영원히 안 끝나면, 그 요청이 잡은 DB 커넥션·메모리가 계속 붙잡힌다.
  - 이벤트 루프를 오래 점유하는 동기 작업(큰 JSON 파싱, 무거운 반복문)은 **모든 요청**을 막는다.
- 직접 만든 커넥션 풀이나 생산자/소비자 큐보다 **검증된 라이브러리**를 쓰자. 책은 직접 만들기가 생각보다 훨씬 어렵다고 경고한다.
- 서드파티/벤더 클라이언트 라이브러리는 내부에서 무한 대기하는 경우가 많으니, 타임아웃 설정이 되는지 직접 확인한다.
- 프로세스 감시만으로는 부족하다. 가짜 사용자가 주기적으로 실제 거래를 흉내 내는 **외부 모니터링**이 필요하다.
- 대응: 모든 대기에 타임아웃.

> 📖 원문: 4장 Blocked Threads

#### 2.4 느린 응답(Slow Responses)
- **느린 응답은 빠른 에러보다 나쁘다.** 빠른 실패는 호출자가 바로 다음 일을 할 수 있지만, 느린 응답은 호출자의 자원을 잡아두고, 호출자도 느려져서 연쇄 장애로 이어진다.
- 웹사이트에서는 사용자가 새로고침을 눌러 **트래픽이 오히려 늘어난다.**
- 원인은 대개 DB 커넥션 경합, 메모리 누수(GC 부담), 비효율적 통신.
- 대응: Fail Fast, 서킷 브레이커, 타임아웃.

> 📖 원문: 4장 Slow Responses

#### 2.5 제한 없는 결과 집합(Unbounded Result Sets)
- 개발 DB에는 100행이지만 운영에서는 1,000만 행이 될 수 있다. `SELECT * FROM orders`를 전부 메모리에 올리면 서버가 죽는다.
- **"0개, 1개, 많이" 세 가지만 존재한다**고 생각하자. 정확히 1개가 아니라면 "많이"를 대비해야 한다.
- 대응: 모든 목록 API에 `limit`(최대치 강제)와 `offset/cursor` 페이지네이션. 응답에도 총 개수 힌트 포함. 운영 규모의 테스트 데이터로 검증.

```ts
// (보충: 원서 외 예시 코드)
// 나쁨: 전부 로드
const all = await repo.find();
// 좋음: 상한 강제 + 페이지네이션
const take = Math.min(dto.limit ?? 20, 100);
const rows = await repo.find({ take, skip: dto.offset ?? 0, order: { id: 'ASC' } });
```

> 🔗 NestJS 연결: 목록 조회 DTO에 `class-validator`의 `@Max(100)`을 걸고 ValidationPipe로 상한을 강제한다.

> 📖 원문: 4장 Unbounded Result Sets

#### 2.6 그 밖의 트래픽/규모 안티패턴 요약
| 안티패턴 | 한 줄 설명 | 핵심 대응 |
|---|---|---|
| 사용자(Users) | 사용자는 세션 메모리를 먹고, 예상 못 한 행동을 하고, 떼로 몰려온다 | 세션에 많이 담지 않기, 퍼징/속성 기반 테스트, 인기 URL 부하 테스트 |
| 자기 부정 공격(Self-Denial) | 마케팅 메일·이벤트가 스스로 트래픽 폭주를 만든다 | 마케팅팀과 소통, 메일을 나눠 발송, 정적 랜딩 페이지 |
| 규모 효과(Scaling Effects) | 소규모에서 되던 구조가 운영 규모에서 무너진다 (서버 간 점대점 통신 등) | 운영과 비슷한 규모로 테스트, 공유 자원 경계 |
| 불균형 용량(Unbalanced Capacities) | 앞단은 크게, 뒷단은 작게 확장되어 뒷단이 폭격당한다 | 앞/뒤 비율 점검, 양쪽 스트레스 테스트 |
| 도그파일(Dogpile) | 많은 서버/클라이언트가 동시에 같은 일을 한다 (정각 cron, 동시 재시작, 설정 일괄 배포, 고정 간격 재시도) | 실행 시각 분산(랜덤 지연), 점점 늘어나는 재시도 간격(백오프) |
| 힘 배수기(Force Multiplier) | 자동화(오토스케일러, 배포 도구)가 실수를 순식간에 거대화 | Governor 패턴(아래), 안전장치 |

- **도그파일**은 SaaS에서 매우 흔하다. 원서의 예: 서버가 재시작되면 빈 캐시 때문에 모든 요청이 DB 조회로 바뀌어 DB에 일시적으로 몰리는 경우, 고정 간격 재시도가 그 주기에 요청을 집중시키는 경우. (보충) 같은 시각에 캐시가 만료되는 "캐시 스탬피드"도 같은 종류다.
- 부하 테스트 스크립트에 고정 대기 시간을 넣으면 인위적인 맥박(pulse)이 생긴다. 대기마다 작은 무작위 편차를 준다.
- **힘 배수기**: 자동화는 판단력이 없어서 잘못되면 매우 빠르게 잘못된다.

> 📖 원문: 4장 Users, Self-Denial Attacks, Scaling Effects, Unbalanced Capacities, Dogpile, Force Multiplier

### 3. 타임아웃(Timeouts)

#### 3.1 핵심 개념
- 네트워크는 항상 실패할 수 있다. 응답이 영원히 안 올 수도 있다. **"희망은 설계 방법이 아니다."**
- 타임아웃은 "이 정도 기다렸으면 더 이상 안 기다린다"고 정하는 것이다. 상대의 문제가 **내 문제로 번지는 것을 막는 격리 장치**다.
- 어디에나 필요하다.
  - HTTP 호출, DB 쿼리, 외부 SDK 호출
  - 커넥션 풀에서 커넥션을 **빌리기 위해 기다리는 시간**
  - 락/뮤텍스 획득 대기
- 어떤 라이브러리는 "타임아웃 있는 함수"와 "무한 대기 함수"를 같이 제공한다. 기본값이 무한 대기라면 반드시 직접 설정하라. 기본값을 믿지 말 것.
- 웹 API 뒤의 서비스라면 "충분히 빠름"은 대략 10~100ms다. 그 이상은 용량과 고객을 잃는다.
- 반복되는 "커넥션 얻기 → 쿼리 → 결과 변환 → 반납" 같은 흐름은 한 곳(게이트웨이/공통 함수)에 모아 타임아웃 처리를 한 번만 제대로 만든다. 서킷 브레이커 적용도 쉬워진다.

```ts
// (보충: 원서 외 예시 코드) Node.js 18+: fetch에 타임아웃
const res = await fetch('https://pay.example.com/charge', {
  method: 'POST',
  body: JSON.stringify(payload),
  signal: AbortSignal.timeout(3000), // 3초 넘으면 AbortError
});
```

왜 중요한가: 타임아웃 없는 외부 호출 하나가 커넥션·메모리를 붙잡아 서비스 전체를 멈추게 하는 것이 가장 흔한 운영 사고 시나리오다.

> 🔗 NestJS 연결: `HttpModule`(axios) 설정에 `timeout`을 항상 지정. 요청 전체에는 Interceptor에서 `rxjs`의 `timeout()` 연산자로 상한을 걸 수 있다.

#### 3.2 타임아웃과 재시도(Retry)
- **즉시 재시도는 대체로 같은 이유로 또 실패한다.** 데이터센터 안에서의 실패는 상대가 한동안 문제인 경우가 많기 때문이다.
- 재시도하는 동안 호출자는 더 오래 기다리고, 그 사이 자원은 더 오래 점유된다.
- 더 나은 선택:
  1. 사용자에게 **빨리 결과를 준다** (실패, 성공, 또는 "접수했고 나중에 처리" 중 하나).
  2. 나중에 다시 시도할 일은 **큐에 넣어 느리게 재시도**한다 (이메일의 저장 후 전달 방식처럼).
- 재시도를 할 때는 고정 간격 대신 **간격을 점점 늘리는 백오프**를 써서 호출자마다 서로 다른 시점에 재시도하게 한다 (원서 4장 Dogpile의 권고). (보충) 여기에 무작위 편차(지터)를 더하는 것이 실무에서 흔하다.
- (보충) 재시도가 있으면 <strong>멱등성(Idempotency)</strong>이 필수다. 같은 결제 요청이 두 번 실행되면 안 된다. (멱등성 키 사용) 원서 Timeouts 절에는 이 설명이 없다.

```ts
// (보충: 원서 외 예시 코드)
async function retry<T>(fn: () => Promise<T>, max = 3, base = 200): Promise<T> {
  for (let i = 0; ; i++) {
    try { return await fn(); }
    catch (e) {
      if (i >= max) throw e;
      const wait = base * 2 ** i * (0.5 + Math.random()); // 백오프 + 지터
      await new Promise((r) => setTimeout(r, wait));
    }
  }
}
```

- 타임아웃은 서킷 브레이커와 짝이다. 타임아웃이 "문제 있음"을 알려주고, 서킷 브레이커가 "그럼 그만 호출하자"를 결정한다.

> 📖 원문: 5장 Timeouts (재시도/백오프 논의는 5장 Timeouts, 4장 Dogpile)

**정리**
- 통합 지점, 막힌 대기, 느린 응답에는 항상 타임아웃.
- 예상 못 한 실패에서 회복하는 가장 단순한 방법이 타임아웃.
- 재시도는 즉시 하지 말고, 늦추거나 큐로 미룬다.

### 4. 서킷 브레이커(Circuit Breaker)

#### 4.1 아이디어
- 집의 차단기처럼, **문제가 있는 호출을 아예 하지 않게 막는** 장치다. (재시도는 "다시 실행", 서킷 브레이커는 "실행 자체를 막음")
- 상태 3가지:

| 상태 | 동작 |
|---|---|
| Closed (닫힘) | 정상. 호출을 그대로 통과시키고 실패 횟수를 센다 |
| Open (열림) | 실패가 임계치를 넘음. 호출하지 않고 **즉시 실패**시킨다 |
| Half-Open (반열림) | 일정 시간 뒤 시험 호출 1건 허용. 성공하면 Closed, 실패하면 다시 Open |

- 열려 있을 때의 처리(폴백)를 미리 정해야 한다.
  - 즉시 에러(타임아웃과는 다른 종류의 에러로 구분)
  - 캐시된 마지막 정상 값, 일반적인 기본 응답, 보조 서비스 호출 등
  - **이것은 기술 결정이 아니라 비즈니스 결정**이다. 예) 재고 확인이 안 될 때 주문을 받을 것인가? 결제 검증이 안 될 때는? 이해관계자와 미리 합의한다.
- "실패 횟수"는 총량보다 **밀도**가 중요하다. 5시간에 5번과 30초에 5번은 다르다. 시간이 지나면 카운터가 줄어드는 방식(leaky bucket)이 실용적이다.
- 상태 변화는 반드시 **로그와 모니터링**으로 노출한다. 열림은 항상 "이상 신호"이며, 열린 횟수 추이는 다른 곳 문제의 선행 지표다. 운영자가 수동으로 열고 닫는 수단도 있으면 좋다.
- 서킷 브레이커는 **프로세스(인스턴스) 단위**로 둔다. 인스턴스끼리 상태를 공유하면 그 공유 자체가 새 실패 지점이 된다.
- 직접 구현하기보다 검증된 오픈소스 라이브러리를 쓰자 (책의 조언). (보충) Node.js에서는 `opossum` 등이 있다.
- 서킷 브레이커는 통합 지점, 연쇄 장애, 불균형 용량, 느린 응답에 효과적이다. 타임아웃 실패를 실행 실패와 따로 세기도 한다.
- 서킷 브레이커 안에서 호출이 한 줄로 직렬화(싱글 스레드화)되지 않도록 주의한다.

```ts
// (보충: 원서 외 예시 코드)
import CircuitBreaker from 'opossum';

const breaker = new CircuitBreaker(callPaymentApi, {
  timeout: 3000,                // 타임아웃과 함께 사용
  errorThresholdPercentage: 50, // 실패율 50% 초과 시 Open
  resetTimeout: 10_000,         // 10초 뒤 Half-Open 시도
});
breaker.fallback(() => ({ status: 'PENDING' })); // 폴백: 나중에 처리
breaker.on('open', () => logger.error('payment breaker OPEN')); // 상태 변화 로깅
```

왜 중요한가: 죽은 의존성을 계속 두드리면 자원만 낭비하고 상대의 복구도 방해한다. 빨리 포기하고 시스템을 지키는 것이 낫다.

> 🔗 NestJS 연결: 외부 API 호출을 감싼 Provider(서비스 클래스) 안에 브레이커를 두고 DI로 주입한다.

> 📖 원문: 5장 Circuit Breaker

**정리**
- "아프면 하지 마라": 문제 있는 통합 지점 호출을 중단.
- 타임아웃과 함께 쓴다 (타임아웃이 실패를 알려주고, 브레이커가 차단).
- 상태 변화는 반드시 기록·노출.

### 5. 벌크헤드(Bulkheads): 격벽으로 나누기

- 배의 방수 격벽처럼, **자원을 칸으로 나누어 한 곳의 침수가 배 전체를 가라앉히지 않게** 한다.
- 나누는 수준은 다양하다.
  - 서버/인스턴스 여러 대 (물리적 중복)
  - 서로 다른 가용 영역
  - 한 프로세스 안에서 **기능별로 풀(스레드, 커넥션)을 분리**
  - 중요 고객/기능 전용 용량 (원서 예: 항공사 체크인 전용 서버를 항공편 조회용 서버와 분리)
  - CPU 코어에 프로세스를 묶어(process binding) 폭주한 프로세스가 호스트 전체를 잡아먹지 못하게 하기
- 공유 서비스에 여러 클라이언트가 붙으면 서로가 서로에게 숨은 영향을 준다. 중요한 클라이언트에게 **전용 풀**을 주면 영향이 사라진다.
- 관리자용 요청 처리 용량을 따로 남겨두면, 서버가 꽉 차도 진단/종료 요청은 받을 수 있다.
- 클라우드와 소프트웨어 로드밸런서에서는 격벽을 영구적으로 둘 필요 없이 필요할 때 만들고 없앨 수도 있다.

(보충) SaaS에서의 예:
- 외부 API별로 동시 호출 수 제한을 따로 둔다 (A사 API가 느려져도 B사 호출은 영향 없음).
- 무거운 리포트 생성은 별도 큐/워커로 분리해 일반 API에 영향을 주지 않는다.
- 요금제가 높은 (중요) 테넌트를 위한 용량을 분리하거나, 테넌트당 사용량 제한을 둔다.

```ts
// (보충: 원서 외 예시 코드)
// 간단한 동시성 제한(세마포어) = 소형 벌크헤드
class Bulkhead {
  private active = 0;
  constructor(private max: number) {}
  async run<T>(fn: () => Promise<T>): Promise<T> {
    if (this.active >= this.max) throw new Error('BULKHEAD_FULL'); // 대기 대신 즉시 거절
    this.active++;
    try { return await fn(); } finally { this.active--; }
  }
}
const emailBulkhead = new Bulkhead(20);
const reportBulkhead = new Bulkhead(3);
```

> 🔗 NestJS 연결: 큐(BullMQ 등)를 용도별로 분리하고 각각 `concurrency`를 다르게 준다. 모듈별로 별도 HTTP 클라이언트/풀을 구성하는 것도 벌크헤드다.

> 📖 원문: 5장 Bulkheads

**정리**
- 배의 일부를 지킨다: 부분 기능이라도 살린다.
- 적절한 크기로 나눈다(스레드 풀 → CPU → 서버 → 클러스터/가용 영역).
- 공유 서비스 구조에서 특히 중요하다.

### 6. 정상 상태 유지(Steady State)

#### 6.1 개념
- 사람이 서버에 들어가 만지는 순간이 사고의 기회다. 사람 손을 최대한 줄이자.
- 시스템은 **최소한 한 번의 배포 주기 동안 사람 개입 없이** 돌아가야 한다. (디스크 정리를 위한 접속, 밤마다 재시작 같은 일이 필요하면 설계 결함)
- 원칙: **무언가를 쌓는 메커니즘이 있으면, 같은 속도 이상으로 비우는 메커니즘도 있어야 한다.** 양동이에 물이 들어오는 만큼 빠져야 넘치지 않는다.

#### 6.2 쌓이는 것들과 대응
| 쌓이는 것 | 문제 | 대응 |
|---|---|---|
| DB 데이터 | 시간이 갈수록 I/O·지연 증가 | **데이터 보관/삭제 정책**을 처음부터 설계. 삭제는 참조 무결성을 아는 애플리케이션 로직으로 |
| 로그 파일 | 디스크가 차서 서비스 중단. 로그 실패가 또 로그를 만들어 폭주하기도 함 | 로그 로테이션, 크기 제한, 중앙 로그 시스템으로 즉시 전송 |
| 메모리 캐시 | 무한 증가하면 메모리 누수의 주범 | 캐시 크기 상한 + 만료(TTL/LRU) |

- "삭제는 나중에 하자"는 거의 항상 지켜지지 않고, 어느 날 폭탄이 된다. 첫 릴리스부터 계획하라.
- 법적 로그 보관 요구가 있어도 **운영 서버가 아니라 중앙 저장소**에 보관하라. (서버 자체는 사라질 수 있다.)
- 컨테이너 환경에서는 로그를 파일 대신 표준 출력(stdout)으로 내보내는 경우가 많다 (원서 8장 Logging).
- 캐시를 만들 때는 (1) 키의 종류가 유한한가, (2) 캐시된 값이 바뀌는가를 먼저 묻는다. 키가 무한하면 크기 제한과 무효화가 필수이고, 가장 단순한 방법은 주기적 전체 비우기(시간 기반)다. LRU도 선택지다.

```ts
// (보충: 원서 외 예시 코드)
// 키 공간이 무한한 캐시는 반드시 크기/수명 제한
import { LRUCache } from 'lru-cache';
const cache = new LRUCache<string, object>({ max: 5000, ttl: 60_000 });
```

- (보충) 세션이나 토큰 저장소, 임시 파일, 업로드 임시본, 소프트 삭제된 행, 아웃박스 테이블 등도 모두 "쌓이는 양동이"다. 원서가 다루는 것은 DB 데이터, 로그 파일, 메모리 캐시 세 가지다.

왜 중요한가: 운영 시작 몇 달 뒤 "갑자기" 느려지는 시스템의 원인은 대부분 여기에 있다.

> 🔗 NestJS 연결 (보충): `@nestjs/schedule`(`@Cron`)으로 정기 정리 작업을 만든다. 여러 인스턴스에서 중복 실행되지 않도록 락을 고려하고, 실행 시각은 정각에 몰리지 않게 분산한다.

> 📖 원문: 5장 Steady State (컨테이너 stdout은 8장 Logging)

**정리**
- 사람 손이 필요 없게 만든다.
- 데이터는 애플리케이션 로직으로 정리한다.
- 캐시는 크기를 제한한다. 로그는 굴리고(rotate) 밖으로 보낸다.

### 7. 빠른 실패(Fail Fast)

- 어차피 실패할 일이라면 **일을 시작하기 전에** 실패시키는 것이 낫다. 느린 실패가 가장 나쁘다.
- 방법:
  - **입력 검증을 가장 앞에서**: DB 연결 확보나 객체 로딩 전에 파라미터부터 확인.
  - **필요한 자원을 미리 확인**: 트랜잭션에 필요한 DB 커넥션, 서킷 브레이커 상태를 시작 시점에 확인 (요리 전 재료 준비와 같다).
  - 로드밸런서가 살아 있는 서버가 없을 때 대기시키지 말고 즉시 거절.
- **시스템 오류와 애플리케이션 오류를 구분**해서 응답해야 한다. 사용자 입력 오류를 "서버 오류"로 돌려주면, 상위 시스템이 서킷 브레이커를 잘못 열 수 있다.
  - (보충) 예: 400/422(잘못된 요청) ≠ 503(일시적 사용 불가) ≠ 500(내부 오류). 원서는 구체적인 코드 대신 "구분해서 보고하라"고만 말한다.
- 타임아웃은 **나가는 요청**을 보호하고, Fail Fast는 **들어오는 요청**을 보호한다. 같은 동전의 양면이다.

```ts
// (보충: 원서 외 예시 코드)
// 요청 초입에서 검증 → 자원 확인 → 본 작업
if (breaker.opened) throw new ServiceUnavailableException('payment temporarily unavailable'); // 503
```

> 🔗 NestJS 연결: `ValidationPipe`와 Guard가 바로 Fail Fast 지점이다. 컨트롤러 진입 전에 잘못된 요청을 걸러낸다. 예외 매핑은 `ExceptionFilter`에서 일관되게.

> 📖 원문: 5장 Fail Fast

### 8. 죽게 두기(Let It Crash)

- 오류 복구 코드는 복잡하고 신뢰하기 어렵다. **가장 깨끗한 상태는 방금 시작한 직후**다. 그래서 상태가 의심스러우면 복구를 시도하기보다 **프로세스를 종료하고 새로 시작**하는 편이 안전할 때가 있다.
- 성립 조건 4가지:
  1. **좁은 범위**: 한 컴포넌트가 죽어도 나머지가 영향받지 않는다.
  2. **빠른 교체**: 다시 뜨는 시간이 짧다. Node.js 프로세스는 밀리초~초 단위라 적합하다. (VM 전체가 몇 분 걸린다면 부적합)
  3. **감독(Supervision)**: 누군가 재시작해야 한다. 단, 문제가 계속되면 죽고 뜨기를 반복하며 서버를 괴롭히므로 재시작 빈도를 추적해야 한다. 감독자와 요청을 보내는 소비자는 다른 존재다. (보충: PM2, 쿠버네티스, ECS 같은 도구가 이 역할을 한다. 다만 원서는 PaaS/오토스케일러는 "무조건 재시작"만 하므로 진짜 감독자와 다르다고 짚는다.)
  4. **재통합(Reintegration)**: 다시 뜬 인스턴스가 자동으로 트래픽을 받는다. (헬스체크 통과 시 로드밸런서에 편입, 직접 호출이면 호출자 쪽 서킷 브레이커가 재통합)
- 큰 모놀리스나 시작이 느린 프로세스, 여러 기능이 한 프로세스에 엉킨 앱에는 맞지 않는다.
- 원서 예시: NodeJS 프로세스는 밀리초 만에 시작하지만 VM은 몇 분이 걸리므로, VM 위에서는 VM 전체가 아니라 NodeJS 프로세스만 죽이는 것이 맞다.

(보충) Node.js에서의 실전 적용:
- 처리되지 않은 예외(`uncaughtException`)나 처리되지 않은 Promise 거부(`unhandledRejection`) 후에는 상태를 믿을 수 없다. **로그를 남기고, 진행 중 요청을 정리(graceful)한 뒤 종료**하고 감독자가 재시작하게 하자.
- 반대로 **정상 요청 하나의 예외**로 프로세스를 죽이지는 말자. 그런 예외는 잡아서 4xx/5xx 응답으로 처리하는 것이 맞다. 구분이 중요하다.

```ts
// (보충: 원서 외 예시 코드)
process.on('unhandledRejection', (err) => {
  logger.error({ err }, 'unhandledRejection - shutting down');
  gracefulShutdown().finally(() => process.exit(1)); // 감독자가 재시작
});
```

> 📖 원문: 5장 Let It Crash

### 9. 핸드셰이킹, 부하 차단, 배압, 거버너

#### 9.1 핸드셰이킹(Handshaking)과 헬스체크
- 서버가 "지금 바빠서 못 받아요"라고 클라이언트/로드밸런서에게 알려 **스스로를 보호**하는 협상이다.
- HTTP는 이 기능이 약하다. 현실적인 방법이 **헬스체크 엔드포인트**다. 로드밸런서가 주기적으로 조회해서 실패하면(예: 503) 해당 인스턴스로 트래픽을 보내지 않는다.
- 핸드셰이킹이 불가능한 상대에게는 서킷 브레이커가 차선책이다 ("물어보는 대신 그냥 호출해 보고 결과를 추적").

#### 9.2 부하 차단(Shed Load)
- 서비스는 **수요를 통제할 수 없다.** 아무리 확장해도 세상은 더 많은 요청을 보낼 수 있다.
- 과부하 상태의 서비스는 "매우 느림"과 "다운"이 밖에서는 구별되지 않는다. 그래서 TCP처럼 **한계를 넘으면 새 요청을 거절**해야 한다.
- 기준: 응답시간이 SLA를 넘거나(가장 이상적), 동시 처리 수가 상한(세마포어)을 넘을 때. 로드밸런서가 있다면 헬스체크 페이지에서 503을 돌려 잠시 물러나게 할 수 있다. (보충) 거절 응답에 `Retry-After` 헤더를 붙이는 것이 관례다.
- 외부(인터넷) 경계에서는 부하 차단과 비동기 응답을, 시스템/조직 내부 경계에서는 배압을 우선하고 부하 차단은 보조로 쓴다. (보충) 외부 경계의 속도 제한(rate limit)도 같은 맥락이다.

#### 9.3 배압(Back Pressure)
- 성능 문제의 시작은 어딘가의 **큐가 쌓이는 것**이다. 큐가 무한하면 메모리가 다 차고 대기 시간도 무한히 늘어난다. **큐는 반드시 유한해야 한다.**
- 큐가 가득 찼을 때 선택지는 넷뿐이다: 새 항목 버리기, 오래된 항목 버리기, 거절하기, 생산자 멈추기(배압).
- 배압은 소비자가 못 따라갈 때 **생산자를 늦추는** 것이다. 시스템 경계 **안쪽**에서 잘 맞는다. 경계 바깥(인터넷)에서는 부하 차단과 비동기 응답(`202 Accepted`)을 쓴다.
- 배압이 걸리는 상황은 성능 문제의 신호이므로 반드시 모니터링에 노출한다.

- 원서 예: 저장소가 감당하는 속도를 넘으면 API 서버가 스토리지 호출 슬롯(예: 서버당 100개)을 제한해 배압을 만들고, 경계에서는 스레드를 막아두는 대신 503으로 응답하거나 큐에 넣고 202로 응답한다.

(보충) Node.js 예시:
- 스트림의 `highWaterMark`, `pipeline()`은 배압을 지원한다.
- BullMQ 큐에 상한을 두고, 작업이 쌓이는 속도와 처리 속도를 모니터링한다.

#### 9.4 거버너(Governor)
- 자동화는 판단력이 없다. 오스케일러가 설정 오류로 서버를 대량 종료하거나, 반대로 인스턴스를 무한히 늘려 비용 폭탄이 날 수 있다.
- **위험한 방향(삭제, 종료, 차단)의 속도를 제한**한다. 예) 한 번에 전체의 10%까지만 종료, 배치 삭제는 시간당 N건까지만.
- 거버너는 상태와 시간을 기억하고, 안전한 방향과 위험한 방향을 다르게 취급한다(비대칭). 안전 범위 안에서는 빠르게, 범위를 벗어날수록 점점 더 큰 "저항"(속도 감소)을 준다.
- 제한에 걸리면 사람이 개입할 시간을 벌도록 모니터링과 연결해 알림을 보낸다.
- 자동화 제어 소프트웨어의 안전장치(원서 4장 Force Multiplier): 시스템의 80% 이상이 죽었다고 관측되면 관측자가 틀렸을 가능성을 먼저 의심하고, 기대 상태와 관측 상태의 차이가 크면 확인을 요청하며, 인스턴스를 켜는 것은 빠르게 끄는 것은 천천히 한다.
- (보충) SaaS 예: 대량 삭제/대량 이메일 발송/대량 결제 작업에 속도 제한과 "N건 초과 시 승인 필요" 규칙.

> 🔗 NestJS 연결 (보충): `@nestjs/throttler`(Guard)로 요청 속도 제한, `@nestjs/terminus`로 헬스체크 엔드포인트 구성.

> 📖 원문: 5장 Handshaking, Shed Load, Create Back Pressure, Governor (4장 Force Multiplier의 Controls and Safeguards 포함)

### 10. 결합 낮추기(Decoupling Middleware)와 테스트 하네스

#### 10.1 동기 호출의 위험, 큐의 이점
- 요청/응답(HTTP, RPC)은 **양쪽이 동시에 살아 있어야** 하는 결합이다. 동기 호출은 연쇄 장애를 전달하는 증폭기다. JSON over HTTP도 마찬가지다.
- 메시지 큐/발행-구독은 **시간과 장소 모두에서 결합을 끊는다.** 받는 쪽이 잠시 죽어도 보내는 쪽은 계속 일한다.
- 단점: 설계가 어렵다. 예외 큐, 늦게 오는 응답, 콜백, 각종 가정을 다뤄야 하고, 재정적 위험을 어디까지 감수할지 비즈니스 담당자와 협의해야 한다. (보충: 실무에서는 데드 레터 큐, 메시지 순서, 중복 처리도 함께 고민한다.)
- 동기 호출의 장점은 논리가 단순하다는 것이다. 예를 들어 카드 승인 결과를 바로 받아 다음 단계로 갈지 결정하기 쉽다.
- 이 결정은 아키텍처 전반에 퍼지므로 **일찍 결정해야 하는 몇 안 되는 사안**이다.

SaaS 예: 회원 가입 → 환영 메일/분석 이벤트/CRM 동기화는 동기 호출 대신 이벤트/큐로 분리. 결제 승인처럼 결과가 즉시 필요한 것만 동기.

> 🔗 NestJS 연결: `@nestjs/bullmq`, `@nestjs/microservices`, `EventEmitter2` 등으로 비동기 분리.

> 📖 원문: 5장 Decoupling Middleware

#### 10.2 테스트 하네스(Test Harness)
- 통합 테스트 환경은 **상대가 명세대로 잘 동작할 때**만 검증한다. 실제 장애는 명세를 벗어난 방식(응답 지연, 연결만 되고 무응답, 쓰레기 응답, 1바이트씩 느리게 전송)으로 온다.
- 모킹(Mock)은 정의된 인터페이스 안의 행동만 흉내 낸다. 그래서 **일부러 악의적으로 구는 가짜 서버**(테스트 하네스)가 필요하다.
  - 연결 거부, 연결 후 무응답, 절반만 응답, 형식이 틀린 응답, 너무 큰 응답, 매우 느린 응답 등
  - 포트별로 다른 나쁜 행동을 하게 만들면 하나의 도구로 여러 시나리오를 시험할 수 있다.
- 목적: 우리 시스템의 타임아웃/서킷 브레이커/폴백이 진짜 작동하는지 확인.

```ts
// (보충: 원서 외 예시 코드)
// 응답을 절대 안 주는 가짜 서버 (타임아웃 검증용)
import http from 'node:http';
http.createServer(() => { /* 응답하지 않음 */ }).listen(10200);
```

- 다른 테스트를 대체하지 않고 보완한다 (비기능 요구를 검증).

> 📖 원문: 5장 Test Harnesses

### 11. 운영 관점의 설계: 설정, 가시성, 배포

#### 11.1 설정(Configuration) 관리
- 설정은 시스템의 "사용자 인터페이스"다. 개발자와 운영자가 쓰는 화면이고, 잘못되면 시스템이 깨진다.
- 규칙:
  - **코드(빌드 결과물)는 환경에 상관없이 동일**, 달라지는 것은 설정뿐이다. (12-Factor: 설정은 환경에 저장)
  - 환경별 설정은 **소스 코드 저장소 밖**에 두거나 별도의 접근 제한 저장소에 둔다. 운영 DB 비밀번호가 Git에 올라가는 사고는 반복된다.
  - 작은 팀은 **환경 변수 주입**이 가장 단순하고 충분하다. 설정 서버(ZooKeeper 등)는 그 자체가 새 장애 지점이라 조직 전체 전략이 있을 때만 쓴다.
  - 속성 이름은 <strong>기능(역할)</strong>을 드러내게 짓는다: `hostname`이 아니라 `authenticationProvider`처럼 (원서 예).
  - 설정 파일은 가장 민감한 정보(운영 DB 비밀번호)를 담으므로 변조와 유출로부터 보호한다. 설정을 버전 관리에서 완전히 빼라는 뜻은 아니고, 소스와 다른 저장소에 두고 접근을 통제하라는 뜻이다.
  - 컨테이너 이미지에는 운영 자격 증명이나 호스트명/포트를 넣지 않는다. 시작 시 주입하고, 비밀번호 보관소(vault)를 활용한다.
  - (보충) 시작 시점에 설정을 검증해서 잘못되면 **바로 실패**한다(Fail Fast 적용).

```ts
// (보충: 원서 외 예시 코드) 시작 시 환경 변수 검증 (Zod/Joi 등)
const env = z.object({
  DATABASE_URL: z.string().url(),
  PAYMENT_TIMEOUT_MS: z.coerce.number().default(3000),
}).parse(process.env); // 없으면 부팅 자체가 실패
```

> 🔗 NestJS 연결 (보충): `@nestjs/config`의 `ConfigModule.forRoot({ validate })` 또는 Joi 스키마로 시작 시 검증. 시크릿은 코드 저장소가 아니라 시크릿 매니저에서 주입.

> 📖 원문: 8장 Configuration (Configuration Files, Configuration with Disposable Infrastructure, Naming Configuration Properties), 7장 The 12-Factor App

#### 11.2 투명성(Transparency): 로깅, 메트릭, 헬스체크
운영 중인 시스템은 눈에 보이지 않는다. 볼 수 있게 **설계 단계부터** 만들어야 한다.

**로깅 규칙**
- 로그의 주 독자는 **개발자가 아니라 운영자**다.
- 레벨을 엄격히 구분한다.
  - `ERROR`: 사람이 조치해야 하는 진짜 문제 (서킷 브레이커 열림, DB 연결 실패)
  - `WARN`: 사용자 입력 오류, 예상 가능한 업무 예외
  - 잘못된 카드 번호 하나까지 ERROR로 남기면 진짜 오류가 묻힌다.
- 운영에서 `debug`/`trace` 레벨을 켜두지 않는다 (배포 파이프라인에서 검사).
- **거래를 추적하는 식별자**(사용자 ID, 세션 ID, 트랜잭션 ID 등)를 로그에 넣는다. 수만 줄에서 grep할 실마리가 된다. (보충: SaaS라면 요청 ID, 테넌트 ID도 넣는다.)
- 애매한 로그 문구는 미신과 오해를 낳는다. 원서 예: "Reset required"라는 모호한 디버그 메시지를 운영자가 DB 장애 전조로 오해해, 6개월간 매주 DB 페일오버를 했다. 누가 무엇을 해야 하는지가 분명한 문장으로 쓴다.
- 상태 전이(예: 브레이커 상태 변화)는 반드시 기록한다.
- 로그 파일은 애플리케이션 설치 디렉터리와 분리하고, 위치를 설정으로 바꿀 수 있게 한다. 컨테이너에서는 표준 출력으로 내보내는 경우가 많다. (보충: 구조화 JSON 형식과 중앙 수집 시스템에서의 검색·경보는 실무 권장이다.)
- 로그는 가장 느슨하게 결합된 관측 수단이라 어떤 도구로도 수집할 수 있다.

**메트릭**
- 각 인스턴스가 지표를 내보내고, **중앙에서 수집·시각화·경보**한다. 가장 단순하게는 주기적으로 통계 한 줄을 로그에 남기는 방식도 된다. 작은 팀은 New Relic, Datadog 같은 외부 서비스로 빨리 시작하는 편이 낫다고 원서는 말한다. (보충: 요청 수, 응답시간, 에러율, 풀 사용량, 큐 길이 같은 구체 지표와 Prometheus는 원서 예시가 아니다.)
- 경보 임계치, 정책, 전체 상태를 어떻게 종합할지는 인스턴스 밖에서 결정한다 (자주 바뀌는 정책이라서). 모니터링은 시스템을 감싸는 외골격이어야 한다.

**헬스체크**
- 단순한 "살아 있음(200)"만이 아니라 다음을 보여주면 좋다.
  - 호스트 IP, 런타임(인터프리터) 버전
  - 앱 버전/커밋 ID
  - 지금 요청을 받을 수 있는 상태인가 (준비 상태)
  - DB 연결 풀, 캐시, 서킷 브레이커 상태
- 클라이언트가 헬스체크를 직접 보지 않고 로드밸런서를 통해 접근한다. 로드밸런서는 새 인스턴스의 헬스체크가 실패 → 성공으로 바뀌는 순간을 "시작 완료"로 보고 트래픽을 넣는다.
- (보충) <strong>생존(liveness)</strong>과 <strong>준비(readiness)</strong>를 구분하는 것이 좋다. 이 용어는 쿠버네티스 개념이며 원서에는 없다.
  - liveness 실패 → 프로세스를 재시작
  - readiness 실패 → 재시작 없이 트래픽만 잠시 빼기 (예: 외부 의존성 장애, 시작 중, 종료 중)
  - 주의: 외부 의존성 하나가 죽었다고 liveness까지 실패시키면 전체가 재시작 루프에 빠질 수 있다.

> 🔗 NestJS 연결 (보충): `@nestjs/terminus`로 `/health/live`, `/health/ready` 구성(`TypeOrmHealthIndicator`, `HttpHealthIndicator` 등). 로그는 `nestjs-pino` 같은 구조화 로거 + 요청 ID 미들웨어.

> 📖 원문: 8장 Transparency (Logging, Instance Metrics, Health Checks)

#### 11.3 배포와 그레이스풀 셧다운
- 배포는 "한 순간"이 아니라 **시간에 걸친 과정**이다. 인스턴스 하나에서도 네 구간이 있다.
  1. **준비(Prep)**: 새 버전을 미리 깔아둔다 (불변 인프라라면 새 이미지 배포).
  2. **배수(Drain)**: 새 요청을 받지 않고, **진행 중 요청이 끝나길 기다린다.** 막힌 요청 때문에 배수가 늦어질 수 있으므로 "충분히 됐다" 싶은 시간 제한을 둔다. 규모가 클수록 시간 제한이 과정을 예측 가능하게 만든다.
  3. **교체(Update)**
  4. **시작(Startup)**: 프로세스가 떴다고 곧바로 요청을 받으면 안 된다. 캐시 로딩, DB 연결 준비가 끝난 뒤 트래픽을 받는다. 서비스는 "사용 가능" 플래그를 false로 시작하고 준비되면 true로 바꾼다.
- 원서의 롤아웃 절차: 그룹(예: Alpha~Foxtrot)별로 새 요청 중단 → 배수 → 코드/설정 갱신 → 헬스체크 통과 확인 → 요청 재개를 반복한다. 첫 그룹은 **카나리** 그룹으로 삼아 지표(에러, 지연, RAM)를 지켜본 뒤 확대한다.
- 롤아웃 중에는 구 버전과 신 버전이 동시에 돈다. 인메모리 세션은 사라지므로 사용자에게 투명해야 하고, 세션은 다른 곳에 있는 정보의 로컬 캐시로만 취급한다.
- (보충) 이것이 <strong>그레이스풀 셧다운(Graceful Shutdown)</strong>의 구현 흐름이다: 종료 신호(SIGTERM) → 헬스체크 실패로 전환(새 트래픽 차단) → 진행 중 요청 완료 → DB/큐 연결 정리 → 종료. 제한 시간이 지나면 강제 종료. 원서는 "SIGTERM"이라는 말 대신 배수/헬스체크 플래그 방식으로 설명한다.
- 원서에서 **블루-그린**(두 풀 중 하나에 새 배포 후 트래픽 전환)은 16장 Adaptation의 Continuous Delivery 패턴 소개에 나온다. 롤링과 카나리는 13장에 나온다.
- **DB 스키마 변경은 무중단의 핵심 난관이다.** 신·구 버전 코드가 잠시 함께 돌기 때문이다. 원서는 두 단계로 나눈다.
  - **확장(Expansion) 단계**: 테이블/뷰/널 허용 컬럼 **추가**, 데이터 복사 등. 현재 앱이 쓰지 않는 것만 더한다. 코드 배포 전에 먼저 적용. 필요하면 트리거 같은 "심(shim)"으로 신구 구조를 잇는다.
  - 새 코드 배포
  - **정리(Cleanup, 수축/Contraction) 단계**: 구 테이블/컬럼 **삭제**, 새 컬럼의 NOT NULL·외래키 제약 추가. 모든 인스턴스가 새 코드가 된 뒤, 잠시 지켜보고 나서 적용.
  - 컬럼 이름 변경이나 삭제를 한 번의 배포에 넣으면 롤링 도중 구 버전이 깨진다.
- 마이그레이션은 도구(예: Liquibase 같은 프레임워크)로 관리하되, 도구가 호환성까지 보장해 주지는 않으므로 확장/정리로 나눠야 한다. 운영 데이터 복사본처럼 "지저분한" 데이터로도 테스트한다.
- 큰 데이터 마이그레이션은 요청이 문서/행을 건드릴 때마다 조금씩 옮기고(trickle), 나중에 남은 것을 일괄(batch) 처리하는 방식이 무중단에 유리하다 (원서의 "trickle, then batch").
- 배포는 자주, 작게 하는 편이 위험이 적다. 원서 표현: "고통스러우면 더 자주 하라" (Continuous Deployment).
- 12-Factor의 "Disposability": **빠른 시작과 깔끔한 종료**로 언제든 프로세스를 버리고 새로 띄울 수 있어야 한다.

```ts
// (보충: 원서 외 예시 코드)
// main.ts: NestJS 그레이스풀 셧다운
const app = await NestFactory.create(AppModule);
app.enableShutdownHooks(); // SIGTERM 수신 시 OnModuleDestroy 등 훅 실행
await app.listen(3000);

// 서비스에서 정리
@Injectable()
export class QueueService implements OnApplicationShutdown {
  async onApplicationShutdown(signal?: string) {
    await this.worker.close(); // 진행 중 작업 마무리 후 연결 종료
  }
}
```

> 🔗 NestJS 연결 (보충): `enableShutdownHooks()`, `OnModuleDestroy`/`OnApplicationShutdown` 라이프사이클 훅. 쿠버네티스에서는 `terminationGracePeriodSeconds`와 readiness probe를 함께 맞춘다.

### 12. 용량과 부하에 대한 기본 감각

- **리틀의 법칙(Little's Law)**: 원서는 큐가 길어질수록 대기 시간도 늘어난다는 맥락에서 이 법칙을 이름만 언급한다 (Create Back Pressure). 아래 공식과 해석은 (보충)이다.
  - (보충) 동시에 처리 중인 요청 수 ≈ 초당 요청 수 × 평균 처리 시간. 처리 시간이 2배로 느려지면 같은 요청률에서 동시 점유 자원도 2배가 된다.
  - (보충) 그래서 부하가 높아질수록 느려지고, 느려질수록 자원(소켓, 커넥션)이 더 필요해지는 악순환이 생긴다. 원서도 느린 응답과 풀 경합이 서로를 키우는 순환 고리를 짚는다.
- **큐가 길어지면 지연도 무한히 늘어난다.** 그래서 유한한 큐 + 배압 + 부하 차단이 필요하다.
- **앞단과 뒷단 용량의 균형**을 본다. 원서 예: 앞단 3,000 스레드가 뒷단 75~450 스레드를 향하면 균형이 안 맞는다. (보충) 이를 커넥션 풀에 적용하면, 앱 인스턴스 수 × 풀 크기가 DB의 최대 커넥션을 넘을 때 확장할수록 DB가 먼저 죽는다.
- 소수의 값비싼 거래(예: 결제)를 평소 비율의 2~5배로 늘려 시험한다. 원서는 전환율 2%를 4, 6, 10%로 올려 테스트하라고 예시한다.
- 운영과 같은 규모의 데이터와 비율로 테스트한다 (소규모에서 잘 되는 것은 증거가 아니다).
- 부하 테스트는 짧은 시간만 하지 말고, **몇 시간~며칠 지속하는 soak 테스트**로 메모리 누수와 리소스 고갈을 찾는다. 유휴 시간대(새벽)를 흉내 내면 커넥션 유휴 타임아웃 문제도 찾을 수 있다.
- 인기 기능·특정 URL에 트래픽이 몰리는 시나리오를 별도로 테스트한다.

> 📖 원문: 3장 Extending Your Life Span, 4장 Users(Expensive to Serve)/Scaling Effects/Unbalanced Capacities, 5장 Create Back Pressure

### 13. 안티패턴과 대응 패턴 한눈에 보기

| 위험(안티패턴) | 대표 증상 | 주요 대응 패턴 |
|---|---|---|
| Integration Points | 외부 API 장애가 내 장애로 | Timeouts, Circuit Breaker, Decoupling Middleware, Handshaking |
| Chain Reactions | 서버 하나 죽자 나머지도 연달아 | 누수 제거, 오토스케일 + 헬스체크, Bulkheads |
| Cascading Failures | 한 계층의 장애가 다른 계층으로 | Timeouts, Circuit Breaker, 풀 대기 제한 |
| Blocked Threads/대기 | 요청이 멈추고 서버가 "행(hang)" | Timeouts, 검증된 라이브러리 사용 |
| Slow Responses | 느려지고 사용자가 새로고침 | Fail Fast, Shed Load, Circuit Breaker |
| Unbounded Result Sets | 대량 조회 시 OOM | 페이지네이션, 상한 강제 |
| Users / Self-Denial / Dogpile | 트래픽 폭주, 동시 재시도, 캐시 스탬피드 | 부하 차단, 백오프+지터, 스케줄 분산 |
| Scaling Effects / Unbalanced Capacities | 운영 규모에서 갑자기 무너짐 | 운영 규모 테스트, 앞·뒤 용량 균형 |
| Force Multiplier | 자동화가 실수를 폭발적으로 확대 | Governor |
| 무한 증가(데이터·로그·캐시) | 몇 달 뒤 서서히 느려짐/디스크 풀 | Steady State |

**핵심 패턴 요약**
- Timeouts: 기다림에 상한을 둔다.
- Circuit Breaker: 아픈 곳은 건드리지 않는다.
- Bulkheads: 칸을 나눠 일부만 잃는다.
- Steady State: 쌓이는 것은 반드시 비운다.
- Fail Fast: 실패할 일은 빨리 실패한다.
- Let It Crash: 복구가 어려우면 깨끗하게 재시작한다.
- Handshaking / Shed Load / Back Pressure: 과부하를 알리고, 거절하고, 상류를 늦춘다.
- Governor: 자동화의 위험한 속도를 제한한다.
- Decoupling / Test Harness: 결합을 낮추고, 나쁜 상대로 미리 훈련한다.

### ✅ 이 부 핵심 체크리스트

- [ ] **모든 외부 호출**(HTTP, DB, 큐, SDK)에 타임아웃이 명시되어 있다. 기본값(무한)에 의존하지 않는다.
- [ ] 커넥션 풀에서 자원을 빌릴 때의 **대기 시간도 제한**되어 있다.
- [ ] 재시도는 **지수 백오프 + 지터**를 쓰고, 재시도되는 작업은 **멱등**하다. 오래 걸릴 일은 큐로 넘긴다.
- [ ] 중요한 외부 의존성에는 <strong>서킷 브레이커 + 폴백(비즈니스가 합의한)</strong>이 있고, 상태 변화가 로그/메트릭으로 보인다.
- [ ] 자원과 워커를 <strong>용도별로 분리(벌크헤드)</strong>해서, 한 기능/한 외부 서비스의 문제가 전체로 번지지 않는다.
- [ ] 모든 목록 조회에 **상한이 있는 페이지네이션**이 적용되어 있다. 큐와 캐시도 크기가 제한된다.
- [ ] 데이터 정리, 로그 로테이션(또는 stdout 수집), 캐시 만료 등 **쌓이는 것을 비우는 장치**가 처음부터 설계되어 있다.
- [ ] 요청 초입에서 **빠르게 실패**한다(입력 검증, 자원 확인). 4xx(클라이언트 오류)와 5xx/503(시스템 문제)을 구분해 응답한다.
- [ ] `/health/live`와 `/health/ready`가 있고, **그레이스풀 셧다운**(SIGTERM → 새 트래픽 차단 → 진행 요청 완료 → 연결 정리)이 구현되어 있다.
- [ ] 설정은 코드 밖(환경 변수/시크릿 매니저)에 있고 **시작 시 검증**된다. 로그에는 요청 ID가 있고, ERROR 레벨은 실제 조치가 필요한 일에만 쓴다.
- [ ] 스키마 변경은 **확장 → 코드 배포 → 정리**의 순서로 나누어 무중단으로 적용한다.
- [ ] 운영 규모의 데이터·비율로 테스트하고, 장시간 부하(soak) 테스트와 **장애 주입**(응답 없는 가짜 서버 등)으로 방어 장치가 실제로 작동하는지 확인한다.
