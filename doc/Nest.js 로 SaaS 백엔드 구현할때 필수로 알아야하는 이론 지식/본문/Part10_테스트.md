# Part 10. 테스트 전략과 원칙 (출처: Unit Testing Principles, Practices, and Patterns)

> **🎮 게임 서버 개발자에게** — 게임 서버에서는 봇 클라이언트를 붙여 보거나 QA가 직접 플레이해 확인하는 일이 많고, 단위 테스트는 수학·판정 함수 정도에만 쓰기 쉽다. 이 장은 GoogleTest/gMock으로 테스트를 써 본 경험이 있다면 그 위에, "무엇을 검증하고 무엇을 가짜로 바꿀 것인가"의 기준을 세워 준다. 결정적으로 다른 점은, 웹 백엔드는 몇 년 동안 계속 리팩터링되므로 구현에 붙은 테스트는 안전망이 아니라 짐이 된다는 것, 그리고 내 DB는 가짜로 바꾸지 않고 실제로 띄워 테스트한다는 것이다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 쿼리 두 번을 한 번으로 합치는 리팩터링만 했는데 테스트 수십 개가 빨갛게 변했다. 기능은 멀쩡하다.
> - 인메모리 DB로 돌린 통합 테스트는 전부 통과했는데, 운영 PostgreSQL에서 JSON 연산·제약 조건 차이로 장애가 났다.
> - 구독 갱신 테스트가 월말이나 특정 시각에만 실패한다.

## 코어 — 이것만은 100%

> **한 문장:** 테스트는 프로젝트를 오래 지속 가능하게 만드는 안전망이므로, 리팩터링 내성을 양보하지 않고 관찰 가능한 동작(WHAT)만 검증하며, 도메인 로직은 많은 단위 테스트로·오케스트레이션은 실제 DB와 비관리형 의존성 목을 쓰는 소수의 통합 테스트로 덮는다.

1. **테스트의 가치 = 4기둥의 곱** — 회귀 방지 × 리팩터링 내성 × 빠른 피드백 × 유지보수성. 리팩터링 내성은 양보할 수 없으므로 실제 절충은 회귀 방지 vs 속도에서 일어난다. 커버리지는 낮을 때만 의미 있는 지표다.
2. **관찰 가능한 동작(WHAT)만 검증한다** — 오탐의 원인은 구현 세부 사항(HOW)에 결합한 것 하나뿐이다. 단위는 클래스가 아니라 동작이고, 스텁은 검증하지 않으며, 구현은 private으로 숨긴다.
3. **출력 기반 > 상태 기반 > 통신 기반, 시간은 값으로** — 로직을 입력 → 반환값의 순수 함수로 뽑을수록 테스트가 쉬워지고, 시간도 전역에서 꺼내지 말고 값으로 넘긴다.
4. **Humble Object: 로직과 조율을 나눈다** — 복잡한 로직은 협력 객체가 적은 도메인으로 빼서 단위 테스트하고, 서비스는 "읽기 → 판단 → 쓰기"만 하는 얇은 조율자로 남긴다.
5. **관리형 vs 비관리형 의존성이 목의 자리를 정한다** — 관리형(내 앱 전용 DB)은 운영과 같은 종류의 실제 DB로, 비관리형(SMTP, 메시지 큐, 결제 API)만 가장 바깥 경계에서 목으로 대체한다. 통합 테스트는 시나리오당 가장 긴 성공 경로 하나 + 단위로 못 잡는 엣지 케이스.

## 코어 1. 테스트의 가치: 지속 가능한 성장과 4기둥

### 1.1 단위 테스트의 목적: 지속 가능한 성장

**한 줄 요약:** 테스트의 목적은 버그 잡기만이 아니라 프로젝트가 오래 유지되면서도 개발 속도가 떨어지지 않게 하는 것이며, 나쁜 테스트는 안전망이 아니라 짐이다.

#### 핵심 개념
- 테스트의 진짜 목적은 "버그 잡기"만이 아니라 **프로젝트가 오래 유지되면서도 개발 속도가 떨어지지 않게 하는 것**입니다.
- 테스트가 없으면 초반엔 빠르지만, 코드가 쌓일수록 한 곳을 고치면 다른 곳이 깨지는 "소프트웨어 엔트로피"가 커져 속도가 급락합니다.
- 테스트는 이 하락을 막는 **안전망**입니다. 리팩터링해도 기능이 그대로인지 바로 알려 줍니다.
- 하지만 **나쁜 테스트는 안전망이 아니라 짐**입니다. 오류 경보를 남발하고, 유지비만 들며, 결국 프로젝트는 똑같이 정체됩니다.
- 테스트도 코드이므로 "적을수록 좋은 부채"입니다. 가치 없는 테스트는 안 쓰는 것이 낫습니다.

#### 테스트의 비용

| 비용 항목 | 설명 |
|---|---|
| 리팩터링 비용 | 프로덕션 코드를 고칠 때 테스트도 고쳐야 함 |
| 실행 비용 | 변경할 때마다 돌려야 함 |
| 오탐(false alarm) 대응 | 기능은 멀쩡한데 빨간불이 켜짐 |
| 읽는 비용 | 코드 동작을 이해하려고 테스트를 읽음 |

- 테스트하기 어려운 코드는 대개 결합도가 높다는 신호입니다(나쁜 코드를 알려 주는 지표). 하지만 테스트가 쉽다고 좋은 코드라는 보장은 없습니다.
- 성공적인 테스트 묶음의 조건: ① 개발 주기에 통합되어 매 변경마다 실행된다 ② 가장 중요한 부분(도메인 모델)에 집중한다 ③ 최소 유지비로 최대 가치를 낸다.

#### 왜 SaaS 백엔드에서 중요한가
> 💡 보충(원서 외): SaaS는 몇 년간 계속 기능을 추가하고 고칩니다. 결제, 권한, 요금제 같은 코드가 회귀(regression) 버그로 깨지면 고객 돈과 데이터 문제로 이어집니다. "장기 생존용 안전망"이 테스트의 존재 이유입니다.

> 📖 원문: 1.1 ~ 1.2, 1.4

### 1.2 커버리지 수치에 속지 않기

**한 줄 요약:** 커버리지는 낮을 때만 의미 있는 "나쁜 쪽 지표"다. 낮으면 위험 신호지만 높아도 아무것도 보장하지 않으므로 숫자를 강제하지 않는다.

- 커버리지(코드 커버리지, 분기 커버리지)는 **"테스트되지 않은 부분"을 찾는 데는 좋은 지표**입니다. 수치가 낮으면 문제가 있다는 신호입니다.
- 하지만 **수치가 높다고 테스트가 좋다는 뜻은 아닙니다.** 코드를 실행만 하고 검증(assert)을 안 해도 커버리지는 오릅니다.
- 커버리지에는 근본적 한계가 있습니다.
  - 검증(assert)이 의미 있는지 알려 주지 못함
  - 외부 라이브러리, 다른 서비스 호출 결과까지는 보지 못함
- **100% 커버리지를 목표로 삼으면** 사소한 코드까지 테스트하게 되고, 수치를 채우려고 나쁜 테스트가 늘어납니다.
- 원서의 결론: 커버리지는 <strong>낮을 때만 의미 있는 "나쁜 쪽 지표"</strong>입니다. 낮은 수치(예: 60% 미만)는 확실한 위험 신호지만, 높은 수치는 아무것도 보장하지 않습니다.
- 핵심 코드에서 높은 커버리지를 갖는 것은 좋지만, 특정 숫자(100%, 90%, 70% 등)를 **필수 요건으로 강제하면 안 됩니다.** 목표는 <strong>"각 테스트가 의미 있는 가치를 주는가"</strong>입니다.
- 커버리지에는 두 종류가 있습니다. 코드 커버리지(실행된 줄 비율)는 코드를 압축하기만 해도 수치가 오르는 식으로 쉽게 조작됩니다. 분기 커버리지(if/switch 같은 분기 통과 비율)는 그보다 정확하지만 위 한계는 여전합니다.

### 1.3 좋은 테스트의 4기둥

**한 줄 요약:** 테스트의 가치는 회귀 방지 × 리팩터링 내성 × 빠른 피드백 × 유지보수성의 곱이며, 리팩터링 내성은 양보할 수 없으므로 실제 절충은 회귀 방지 vs 속도에서 일어난다.

모든 자동화 테스트(단위, 통합, E2E)는 아래 4가지 속성으로 평가할 수 있습니다.

| 기둥 | 뜻 | 높이려면 |
|---|---|---|
| ① 회귀 방지(Protection against regressions) | 버그를 얼마나 잘 잡는가 | 더 많은 코드를 실행, 복잡/핵심 로직을 포함 |
| ② 리팩터링 내성(Resistance to refactoring) | 동작이 그대로인데 리팩터링만 했을 때 안 깨지는가 | **구현이 아니라 결과**를 검증 |
| ③ 빠른 피드백(Fast feedback) | 얼마나 빨리 도는가 | 외부 프로세스에 의존하지 않기 |
| ④ 유지보수성(Maintainability) | 읽고 실행하기 쉬운가 | 짧게, 외부 의존성 적게 |

#### 기둥 ①: 회귀 방지
- 실행하는 코드량, 코드의 복잡도, 도메인 중요도가 클수록 높아집니다.
- 한 줄짜리 getter 같은 **사소한 코드는 테스트 가치가 거의 없습니다.**
- 서드파티 라이브러리, 프레임워크, DB까지 포함해 실행하면 더 강한 보호를 얻습니다.

#### 기둥 ②: 리팩터링 내성 (가장 중요)
- 기능은 그대로인데 테스트가 깨지는 것을 <strong>오탐(false positive)</strong>이라 합니다.
- 오탐이 잦으면 팀은 "또 그 테스트가 울었네" 하며 실패를 무시하게 되고, 결국 **진짜 버그도 놓칩니다.** 나아가 테스트가 무서워서 리팩터링을 하지 않게 됩니다.
- 원인은 하나입니다. **테스트가 구현 세부 사항(HOW)에 결합**되어 있기 때문입니다.
- 해법도 하나입니다. **최종 결과(WHAT), 즉 관찰 가능한 동작만 검증**합니다. (→ 코어 2 전체가 이 해법을 구체화한 것입니다.)

```ts
// 나쁨: 내부 구성(어떤 하위 렌더러를 쓰는가)을 검증 → 구현을 바꾸면 깨짐
expect(sut.subRenderers[0]).toBeInstanceOf(HeaderRenderer);

// 좋음: 최종 결과물만 검증
expect(sut.render({ header: 'h', body: 'b', footer: 'f' }))
  .toBe('<h1>h</h1><b>b</b><i>f</i>');
```

```ts
// 나쁨: 실행된 SQL 문자열을 검증 → 같은 결과를 내는 SQL로 바꾸면 깨짐
expect(repo.lastExecutedSql).toBe('SELECT * FROM users WHERE id = 5');
```

#### 정확도 = 신호 / 잡음
- 테스트 정확도는 "찾아낸 버그(신호)" 대비 "오탐(잡음)"의 비율입니다.
- 프로젝트 초반엔 오탐 비용이 작지만, **프로젝트가 커질수록 오탐이 미탐(놓친 버그)만큼 치명적**이 됩니다.

#### 이상적인 테스트는 없다
- 4기둥 점수를 **곱한 값**이 테스트의 가치입니다. 하나라도 0이면 전체가 0입니다.
- ①, ②, ③은 서로 상충해서 셋을 동시에 최대로 만들 수 없습니다.

| 극단 사례 | ① 회귀방지 | ② 내성 | ③ 속도 | 결과 |
|---|---|---|---|---|
| E2E 테스트 | 최고 | 최고 | **낮음** | 느려서 전부를 이것으로 덮을 수 없음 |
| 사소한 테스트 | 낮음 | 높음 | 높음 | 버그를 못 잡음, 가치 0 |
| 깨지기 쉬운 테스트 | 높음 | **낮음** | 높음 | 오탐 폭탄 |

- 리팩터링 내성은 "있거나 없거나"에 가까워 **양보할 수 없는 항목**입니다. 그러므로 실제 절충은 **①회귀방지 vs ③속도** 사이에서 일어납니다.
- 소수의 고가치 테스트가 다수의 어중간한 테스트보다 낫습니다.
- 유지보수성(④)은 ①②③과 대체로 무관하지만, E2E 테스트는 덩치가 크고 외부 의존성을 살려 두어야 해서 유지비가 큽니다.

#### 블랙박스 vs 화이트박스
- 블랙박스: 명세/요구사항 기준으로 "무엇을 하는가"를 검증 → 리팩터링 내성이 좋음. 화이트박스: 소스 구조 기준 → 회귀 방지는 좋지만 깨지기 쉬움.
- **테스트를 쓸 때는 블랙박스**로, 비즈니스 요구사항으로 거슬러 올라갈 수 없는 테스트는 깨지기 쉽다는 신호입니다. 커버리지 도구로 빠진 분기를 찾는 **분석 단계에서만** 화이트박스 시각을 씁니다.

> 📖 원문: 4.1 ~ 4.5

## 코어 2. 관찰 가능한 동작(WHAT)만 검증한다

이 묶음의 원리는 하나입니다: **테스트는 호출자가 보는 결과만 확인하고, 그 결과를 어떻게 만들었는지(HOW)는 묻지 않는다.** 단위의 정의(2.1), 테스트 구조(2.2)와 이름(2.3), 스텁 검증 금지(2.4), 캡슐화(2.5), private 관련 안티패턴(2.6~2.8)이 모두 이 원리에서 나옵니다.

### 2.1 단위 테스트란 무엇인가

**한 줄 요약:** 단위 테스트는 한 단위의 "동작"을 빠르게, 다른 테스트와 격리해 검증하는 테스트이며, 단위는 클래스가 아니라 비즈니스적으로 의미 있는 동작 하나다.

#### 정의
단위 테스트는 다음 세 가지를 모두 만족하는 테스트입니다.
1. <strong>한 단위의 동작(unit of behavior)</strong>을 검증한다.
2. **빠르게** 실행된다.
3. **다른 테스트와 격리**되어 실행된다 (순서나 병렬 실행에 영향받지 않음).

이 중 하나라도 어기면 통합 테스트(integration test)로 분류됩니다.

#### "단위"는 클래스가 아니라 동작
- 초보자는 "클래스 하나 = 단위"라고 생각하기 쉽습니다. 그러나 **단위는 비즈니스 관점에서 의미 있는 동작 하나**입니다.
- 그 동작을 구현하는 데 클래스가 1개든 3개든 상관없습니다.
- 좋은 테스트는 "고객이 주문하면 재고가 줄어든다"처럼 **비개발자에게도 이야기가 되는** 시나리오를 검증합니다. "다리 왼쪽 앞발, 오른쪽 앞발이 움직인다"처럼 내부 동작을 쪼개 검증하면 의미가 사라집니다.

#### 두 가지 학파

| | 고전파(Classical) | 런던파(London / Mockist) |
|---|---|---|
| 격리의 대상 | 테스트끼리 서로 격리 | 대상 클래스를 협력 객체로부터 격리 |
| 단위의 크기 | 클래스 하나 또는 여러 개 | 클래스 하나 |
| 테스트 더블 사용 | **공유 의존성**(DB, 외부 API 등)만 대체 | 불변 값 객체 외 **거의 모든 협력 객체** 대체 |

- 이 책은 **고전파**를 권장합니다. 런던파처럼 협력 객체를 다 목(mock)으로 바꾸면 테스트가 구현 세부 사항에 묶여 깨지기 쉬워지기 때문입니다.
- 런던파의 장점(세밀한 원인 파악, 복잡한 객체 그래프 테스트 용이)은 실제로는 "설계 문제를 목으로 덮는 것"인 경우가 많습니다. 테스트하기 어려운 객체 그래프는 설계를 고쳐야 할 신호입니다.

#### 의존성 분류 (용어 정리)
- **공유 의존성(shared)**: 테스트끼리 상태를 공유할 수 있는 것 (DB, 파일, 정적 변수)
- **프로세스 외부 의존성(out-of-process)**: 내 프로세스 밖에 있는 것 (DB, 메시지 브로커, SMTP, 외부 API)
- **값 객체(value object)**: 불변이고 내용으로만 구분되는 것 (숫자, 금액, 날짜). 그냥 그대로 써도 됨.
- 공유 의존성과 프로세스 외부 의존성은 거의 겹치지만 완전히 같지는 않습니다. 읽기 전용 외부 API는 프로세스 밖에 있어도 테스트끼리 상태를 바꿀 수 없으므로 "공유"는 아닙니다.
- 협력 객체(collaborator) = 공유되었거나 상태가 변하는 의존성. 값 객체는 협력 객체가 아닙니다.

#### 통합 테스트와 E2E
- 통합 테스트 = 단위 테스트의 세 조건 중 하나라도 못 지키는 테스트(공유 의존성 접근, 느림, 여러 동작을 한꺼번에 검증 등).
- E2E 테스트는 통합 테스트의 부분집합으로, 프로세스 외부 의존성을 대부분 포함해 최종 사용자 관점에서 검증합니다. 유지비가 가장 커서 빌드 후반에 돌립니다.

> 📖 원문: 2.1 ~ 2.4

### 2.2 테스트 구조: AAA 패턴

**한 줄 요약:** Arrange → Act → Assert로 쓰되 Act는 한 줄이어야 하며, Act가 두 줄 이상이면 테스트가 아니라 코드의 캡슐화를 고치라는 신호다.

#### AAA
- **Arrange(준비)**: 대상 객체(SUT: System Under Test)와 의존성을 원하는 상태로 만든다.
- **Act(실행)**: 대상의 메서드를 호출한다.
- **Assert(검증)**: 결과를 확인한다.
- BDD 스타일의 Given-When-Then과 같은 구조입니다 (비개발자와 공유할 때 더 읽기 좋음).

```ts
describe('PriceEngine', () => {  // 원서 6.1의 예제를 TS로 바꾼 것
  it('할인율은 상품 개수에 비례하되 20%를 넘지 않는다', () => {
    // Arrange
    const sut = new PriceEngine();
    const products = [new Product('핸드워시'), new Product('샴푸')];

    // Act
    const discount = sut.calculateDiscount(products);

    // Assert
    expect(discount).toBe(0.02);
  });
});
```

#### 작성 규칙

| 규칙 | 이유 |
|---|---|
| 테스트 대상 변수 이름을 `sut`로 통일 | 대상과 의존성을 한눈에 구분 |
| **Act는 한 줄** | 두 줄 이상이면 API가 캡슐화되지 않았다는 신호 (아래 참고) |
| 테스트 하나에 Act/Assert 묶음은 **하나** | 여러 개면 여러 동작을 한 번에 검증하는 것 → 단위 테스트라면 쪼갬 (원서: 느린 통합 테스트에서만 예외적으로 허용) |
| 테스트 안에 `if` 금지 | 분기는 여러 시나리오를 섞었다는 뜻 (통합 테스트에도 예외 없음) |
| 한 동작의 결과가 여러 개면 assert가 여러 개여도 OK | "assert 하나만" 규칙은 잘못된 통념. 단, assert가 너무 길면 값 객체 동등 비교 같은 빠진 추상화 신호일 수 있음 |
| Arrange가 가장 커도 됨 | 너무 크면 헬퍼 함수나 Object Mother / Test Data Builder로 추출 |
| 구역은 `// Arrange` 주석 또는 빈 줄로 구분 | 짧은 단위 테스트는 빈 줄만으로도 충분 |
| 유닛 테스트엔 보통 teardown이 필요 없음 | 프로세스 외부와 통신하지 않으니 정리할 부작용이 없음 |

#### Act가 두 줄이면 왜 문제인가
```ts
// 나쁜 API: 호출자가 두 번째 호출을 잊으면 불변식(invariant)이 깨진다
const success = customer.purchase(store, 'shampoo', 5);
store.removeInventory(success, 'shampoo', 5);   // ← 잊으면 재고가 줄지 않음

// 좋은 API: 한 번 호출로 두 결과가 함께 보장된다
const success = customer.purchase(store, 'shampoo', 5);
```
- 구매 성공과 재고 감소는 **함께 일어나야** 합니다. 이를 지키지 못하면 데이터 불일치가 DB까지 들어가고, 고객 대응이 필요한 사고가 됩니다.
- 테스트가 아니라 **코드의 캡슐화**를 고치라는 신호입니다.

#### Jest 참고
- 원서: 공통 준비를 생성자(`beforeEach` 에 해당)에 몰아넣으면 테스트끼리 결합되고(한 곳을 고치면 전부 영향) 테스트만 봐서는 상황이 안 보입니다. 대신 **팩토리 함수**(`createStore(...)`처럼 테스트가 원하는 값을 인자로 지정)로 매번 새로 만드세요. 예외: 거의 모든 테스트가 쓰는 DB 연결 같은 것은 공통 부모 클래스에서 준비해도 됩니다.
- 같은 동작을 여러 입력으로 검증할 땐 `it.each`(원서의 파라미터화 테스트)를 사용합니다. 단, 케이스가 많아질수록 테스트 이름이 흐려지므로 성공 케이스는 따로 떼어 이름을 붙이는 절충이 좋고, 동작이 복잡하면 파라미터화를 쓰지 않습니다.
- 가독성을 위해 assertion 라이브러리(원서는 Fluent Assertions 소개)를 쓸 수 있습니다. (Jest의 `expect(...).toBe(...)`도 이미 같은 형태입니다. — 보충)

```ts
it.each([
  ['mycorp.com', 'a@mycorp.com', true],
  ['mycorp.com', 'a@gmail.com', false],
])('회사 %s 에서 %s 는 사내 이메일 여부: %s', (domain, email, expected) => {
  const sut = new Company(domain, 0);
  expect(sut.isEmailCorporate(email)).toBe(expected);
});
```

> 🔗 NestJS 연결: `Test.createTestingModule()`로 모듈을 만드는 것은 Arrange 단계입니다. 도메인 로직 테스트는 이것 없이 `new`만으로 충분한 것이 이상적입니다. (`Test.createTestingModule()` 자체는 [Part 3](Part03_NestJS핵심.md)에서 다룹니다.)

> 📖 원문: 3.1 ～ 3.3, 3.5 ～ 3.6

### 2.3 테스트 이름 짓기

**한 줄 요약:** 테스트 이름은 메서드 이름(구현)이 아니라, 도메인 전문가에게 설명하듯 사실을 말하는 평서문으로 짓는다.

- `메서드명_시나리오_기대결과` 같은 규칙은 **구현(메서드 이름)에 묶이므로 비추천**입니다. 메서드 이름을 바꾸면 테스트 이름도 바뀌어야 합니다.
- **비개발자(도메인 전문가)에게 설명하듯 평서문으로** 씁니다.
- `should be ~`(바람) 대신 `is ~`(사실)로 씁니다. 테스트는 "이 시스템은 이렇다"라는 사실 진술이기 때문입니다.

```ts
// 나쁨
it('isDeliveryValid_InvalidDate_ReturnsFalse', ...)
// 좋음
it('과거 날짜로는 배송을 예약할 수 없다', ...)
it('delivery with a past date is invalid', ...)
```
- 유틸리티 코드(비즈니스 의미가 없는 코드)는 예외적으로 메서드 이름을 써도 됩니다.
- 원서는 영어 단어를 밑줄로 구분하라고 권합니다(C# 메서드명 제약). Jest는 문자열 이름을 쓰므로 그냥 문장으로 적으면 됩니다.
- (보충) Jest에서는 `describe`에 대상 이름, `it`에 동작을 문장으로 적으면 자연스럽게 읽힙니다. 원서도 `[클래스명]Tests`는 진입점일 뿐이라고 설명합니다.

> 📖 원문: 3.4

### 2.4 목(Mock)과 스텁(Stub) 구분

**한 줄 요약:** 스텁은 들어오는 상호작용(쿼리)을 흉내 낼 뿐 검증하지 않고, 목은 나가는 상호작용(커맨드, 부수 효과)을 흉내 내고 검증한다. 스텁 호출 검증은 과잉 명세다.

#### 테스트 더블(Test Double)
가짜 의존성을 통틀어 부르는 말입니다 (dummy, stub, spy, mock, fake). 실무에서는 두 종류로 정리하면 충분합니다.

| | 스텁(Stub) | 목(Mock) |
|---|---|---|
| 역할 | **들어오는** 상호작용을 흉내: 대상이 데이터를 **받아 오는** 호출 | **나가는** 상호작용을 흉내하고 검증: 대상이 **부수 효과를 일으키는** 호출 |
| 예 | DB 조회 결과를 미리 정해 돌려줌 | 이메일 전송 함수가 호출됐는지 확인 |
| 검증 여부 | **호출 자체를 검증하지 않는다** | 호출 여부/인자/횟수를 검증한다 |
| CQS 대응 | 쿼리(값 반환, 부수 효과 없음) | 커맨드(부수 효과, 반환 없음) |

> "mock"은 도구(jest.fn, jest.mock)를 뜻하기도 합니다. 도구인 `jest.fn()`으로 목도 스텁도 만들 수 있으니, **역할로 구분**하세요.

```ts
// 스텁: 입력 데이터를 준비할 뿐 → 호출 검증 금지
const userRepo = { countUsers: jest.fn().mockResolvedValue(10) };
const report = await new ReportService(userRepo).create();
expect(report.numberOfUsers).toBe(10);
// expect(userRepo.countUsers).toHaveBeenCalledTimes(1);  ← 안티패턴! 조회 방식은 구현 세부 사항

// 목: 외부로 나가는 부수 효과 → 검증 대상
const mailer = { sendWelcome: jest.fn() };
await new SignupService(mailer).greet('user@email.com');
expect(mailer.sendWelcome).toHaveBeenCalledWith('user@email.com');
expect(mailer.sendWelcome).toHaveBeenCalledTimes(1);
```

- **스텁 호출을 검증하는 것은 흔한 안티패턴**입니다. 대상이 데이터를 어떻게 모으는지는 결과가 아니라 과정(구현)이기 때문입니다. 이를 "과잉 명세(over-specification)"라 부릅니다.
- 한 테스트 더블이 스텁과 목 역할을 동시에 한다면 그냥 목이라 부릅니다 (다른 메서드를 각각 스텁/목으로 쓰는 것은 문제 없음).
- 원서의 분류: 스파이(직접 손으로 쓴 목)는 목 쪽, 더미(자리만 채우는 값)/페이크(아직 없는 의존성 대체)는 스텁 쪽으로 묶입니다.
- 원서에 따르면 CQS(명령-쿼리 분리) 원칙상 메서드는 명령(부수 효과, 반환 없음)이거나 쿼리(값 반환, 부수 효과 없음)여야 하며, 명령을 대체하면 목, 쿼리를 대체하면 스텁입니다.
- 단, "나가는" 호출이라도 시스템 내부(클래스 간) 통신이면 목으로 검증하지 않습니다. 목이 어디에 쓰이는지는 → 코어 5에서 정리합니다.

> 📖 원문: 5.1

### 2.5 관찰 가능한 동작 vs 구현 세부 사항

**한 줄 요약:** 관찰 가능한 동작은 호출자가 목표를 이루는 데 쓰는 연산과 상태이고 나머지는 모두 구현 세부 사항이며, 구현을 private으로 숨기면 테스트는 자동으로 좋아진다.

#### 구분 기준
코드는 다음 둘 중 하나입니다.
- **관찰 가능한 동작(observable behavior)**: 호출자(클라이언트)가 **자기 목표를 이루기 위해** 사용하는 것
  - 계산이나 부수 효과를 일으키는 **연산(operation)**
  - 결과를 확인하는 **상태(state)**
- **구현 세부 사항(implementation detail)**: 위에 해당하지 않는 나머지

> "공개(public) API"와 "관찰 가능한 동작"은 다릅니다. 이상적으로는 둘이 일치해야 하고, 구현 세부 사항은 전부 `private`이어야 합니다. 구현이 public으로 새어 나오면 테스트도 거기에 붙게 됩니다.

#### 예: 구현이 새는 API
```ts
// 나쁨: 호출자가 normalize를 직접 호출해야 함 → 두 번 호출해야 목표 달성 → 불변식이 깨질 수 있음
class User {
  name = '';
  normalizeName(name: string) { return name.trim().slice(0, 50); }
}
user.name = user.normalizeName(input);   // 잊으면 50자 제한 위반

// 좋음: 규칙을 안쪽에 숨김(캡슐화). 호출자는 한 번만 호출
class User {
  #name = '';
  get name() { return this.#name; }
  set name(v: string) { this.#name = this.#normalize(v); }
  #normalize(v: string) { return v.trim().slice(0, 50); }
}
user.name = input;
```

#### 경험 법칙
- **하나의 목표를 위해 호출자가 클래스의 연산을 2번 이상 호출해야 한다면**, 구현이 새고 있을 가능성이 높습니다.
- 캡슐화 = 불변식(invariant, 항상 참이어야 하는 조건)을 지키는 것. 잘못된 사용을 애초에 불가능하게 만드세요.
- **API를 잘 설계하면 테스트가 자동으로 좋아집니다.** 구현을 다 숨기면, 테스트는 관찰 가능한 동작만 검증할 수밖에 없기 때문입니다.
- Tell, Don't Ask: 데이터를 꺼내 밖에서 판단하지 말고, 데이터와 그 데이터를 다루는 동작을 한 곳에 묶으세요.

> 📖 원문: 5.2

### 2.6 안티패턴: private 메서드를 테스트하기 위해 공개하지 않기

**한 줄 요약:** private 메서드는 public 동작으로 간접 검증하고, 그게 어려울 만큼 복잡하면 빠진 추상화를 별도 클래스로 추출한다.

- private 메서드는 구현 세부 사항입니다. 공개해서 테스트하면 리팩터링 내성이 무너집니다.
- 대신 **public 동작을 통해 간접 검증**합니다.
- private 메서드가 너무 복잡해 간접 검증이 어렵다면, (a) 죽은 코드이거나 (b) **빠져 있는 추상화**입니다. 별도 클래스로 추출해 그 클래스를 직접 테스트하세요.
- 드문 예외(원서 11.1.3): private이면서 사실상 관찰 가능한 동작인 경우(예: ORM이 복원할 때만 쓰는 private 생성자)는 공개하거나 리플렉션으로 인스턴스를 만들어도 됩니다. 이때 생성자에 불변식 검사를 넣어 캡슐화를 유지합니다.

```ts
class Order {
  describe() { return `... 총액: ${new PriceCalculator().calculate(this.customer, this.products)}`; }
}
class PriceCalculator {                 // 복잡한 로직을 추출 → 출력 기반으로 쉽게 테스트
  calculate(customer: Customer, products: Product[]): number { /* 기본가 - 할인 + 세금 */ }
}
```

> 📖 원문: 11.1 (원서 11장 안티패턴 11.1 ~ 11.6 중. 나머지는 2.7~2.8, 3.2, 4.2~4.3)

### 2.7 안티패턴: private 상태를 테스트용으로 노출하지 않기

**한 줄 요약:** 테스트도 프로덕션과 같은 권한으로 대상을 쓰며, 내부 필드 대신 프로덕션이 실제로 쓰는 결과를 검증한다.

- 테스트도 프로덕션 코드와 **같은 권한**으로 대상을 사용해야 합니다.
- 예: `customer.promote()` 후 내부 `status` 필드를 열어서 확인하지 말고, 프로덕션이 실제로 쓰는 결과인 **`getDiscount()`가 5%가 되는지**를 검증하세요(새 고객은 할인 없음, 승격 후 5%). 나중에 프로덕션이 status를 쓰기 시작하면 그때는 그 필드도 관찰 가능한 동작이 됩니다.

> 📖 원문: 11.2

### 2.8 안티패턴: 테스트에 도메인 지식(알고리즘) 누수

**한 줄 요약:** 프로덕션 계산식을 테스트에 복사하면 알고리즘이 틀려도 같이 틀려 통과하므로, 기대값은 미리 계산한 값을 하드코딩한다.

```ts
// 나쁨: 프로덕션 계산식을 테스트에 복사 → 알고리즘이 틀려도 같이 틀려서 통과
const expected = a + b;
expect(add(a, b)).toBe(expected);

// 좋음: 미리 계산한 값을 하드코딩 (가능하면 SUT가 아닌 다른 방법/도메인 전문가가 계산)
it.each([[1, 3, 4], [11, 33, 44], [100, 500, 600]])('%d + %d = %d', (a, b, expected) => {
  expect(add(a, b)).toBe(expected);
});
```

> 📖 원문: 11.3

## 코어 3. 출력 기반 > 상태 기반 > 통신 기반, 시간은 값으로

이 묶음의 원리: **입력이 같으면 결과가 같은 코드(순수 함수)가 가장 테스트하기 쉽다.** 그래서 스타일은 출력 기반을 우선하고(3.1), 결과를 흔드는 숨은 입력인 "현재 시각"도 값으로 넘긴다(3.2).

### 3.1 세 가지 테스트 스타일

**한 줄 요약:** 출력 기반(입력 → 반환값)이 리팩터링 내성·유지보수성 모두 최고이고, 통신 기반은 시스템 경계를 넘는 부수 효과에만 쓴다. 함수형 코어와 가변 셸로 나누면 출력 기반을 늘릴 수 있다.

| 스타일 | 무엇을 검증하나 | 예 |
|---|---|---|
| **출력 기반(Output-based)** | 입력 → 반환값 | 할인 계산 함수의 리턴값 |
| **상태 기반(State-based)** | 실행 후 대상(또는 협력 객체, DB)의 상태 | 주문에 상품이 추가되었는가 |
| **통신 기반(Communication-based)** | 협력 객체와의 호출(목 사용) | 이메일 전송 함수가 호출되었는가 |

```ts
// 출력 기반: 가장 짧고 깨지지 않음
expect(priceEngine.calculateDiscount([p1, p2])).toBe(0.02);

// 상태 기반
order.addProduct(product);
expect(order.products).toEqual([product]);

// 통신 기반
expect(mailer.send).toHaveBeenCalledWith('user@email.com');
```

#### 비교 결과

| | 리팩터링 내성 | 유지보수성 | 비고 |
|---|---|---|---|
| 출력 기반 | **최고** | **최고** | 부수 효과 없는 순수 함수에만 적용 가능 |
| 상태 기반 | 보통 | 보통 | 검증할 상태가 많으면 테스트가 길어짐 |
| 통신 기반 | 가장 위험 | 가장 낮음 | 목 설정과 검증이 길고, 잘못 쓰면 깨지기 쉬움 |

- **가능하면 출력 기반을 우선**하세요. 로직을 "입력 받아 값 반환"하는 순수 함수(부수 효과 없는 함수)로 뽑아낼수록 테스트가 쉬워집니다.
- 통신 기반은 위에서 본 대로 **시스템 경계를 넘는 부수 효과에만** 씁니다.
- 세 스타일은 한 테스트에서 섞어 써도 됩니다.
- 회귀 방지와 속도는 스타일과 크게 상관없습니다.
- 원서는 고전파가 상태 기반을, 런던파가 통신 기반을 선호하고 둘 다 출력 기반은 쓴다고 정리합니다.

#### 출력 기반으로 옮기기: 함수형 아키텍처
- 원서 6.3~6.5: 비즈니스 로직(결정을 내리는 함수형 코어)과 부수 효과(그 결정을 DB/메시지로 반영하는 가변 셸)를 분리하면 코어를 출력 기반으로 테스트할 수 있습니다. 셸은 입력을 모으고 코어의 결정을 실행하기만 합니다(읽기 → 결정 → 실행).
- 단점: 미리 모든 입력을 읽어야 해서 성능이 떨어질 수 있고, 코드가 늘어납니다. 그래서 전부 옮기려 하지 말고 "가능한 만큼" 옮기며, 실제로는 출력 기반과 상태 기반을 섞고 통신 기반은 조금만 씁니다.

> 📖 원문: 6.1 ~ 6.5

### 3.2 시간(Time) 다루기

**한 줄 요약:** 시간은 전역 컨텍스트(안티패턴) < 명시적 주입(Clock) < 값으로 전달(가장 좋음) 순이며, 실무에서는 서비스가 Clock으로 시간을 얻어 도메인에 Date 값으로 넘긴다.

- 만료일, 구독 갱신, 토큰 유효 기간, 청구 주기 등 SaaS에는 시간 로직이 넘쳐납니다. `new Date()`를 로직 속에서 직접 호출하면 테스트가 실행 시점에 따라 달라집니다.
- 세 가지 방법:
  1. **전역 컨텍스트**(원서: 정적 필드 `DateTimeServer.Now`): 안티패턴. 테스트 간 상태를 공유하고 프로덕션을 오염시킴
  2. **명시적 의존성으로 주입** (Clock 서비스): 괜찮음
  3. **값으로 전달** (`inquiry.approve(now)`): **가장 좋음**
- 절충안(원서 권장): DI 프레임워크가 값 주입을 잘 지원하지 않으므로, 업무 시작점(서비스/컨트롤러)에서 Clock 서비스로 현재 시간을 얻고, 도메인에는 <strong>값(Date)</strong>으로 넘깁니다.

```ts
// 서비스(조율): 시간을 얻어 값으로 전달
async renew(subId: number) {
  const sub = await this.repo.findById(subId);
  sub.renew(this.clock.now());            // 도메인: 값으로 받음
  await this.repo.save(sub);
}

// (보충: 구독 갱신은 원서 예제가 아니라 이 원고의 SaaS 예시) 도메인 단위 테스트: 시간 고정이 필요 없음
const sub = new Subscription({ expiresAt: new Date('2026-01-31') });
sub.renew(new Date('2026-01-30'));
expect(sub.expiresAt).toEqual(new Date('2026-02-28'));
```

> 🔗 NestJS 연결(보충): `Clock`을 Provider로 등록하고 서비스에 주입하세요. 도메인 클래스는 시간을 파라미터로 받습니다. (Jest의 `jest.useFakeTimers().setSystemTime(...)`도 가능하지만, 전역 상태를 건드리므로 원서의 권고 취지상 명시적 주입/값 전달이 더 견고합니다.)

> 📖 원문: 11.6

## 코어 4. Humble Object: 도메인 로직과 오케스트레이션 분리

이 묶음의 원리: **"깊이(복잡도)와 너비(협력 객체 수)를 동시에 가지지 말라."** 복잡한 로직은 협력 객체가 없는 곳으로 빼서 단위 테스트하고, 외부와 닿는 부분은 로직 없는 얇은 껍데기로 남긴다(4.1). 테스트용 스위치 코드(4.2)나 부분 목킹(4.3)이 필요해지는 것도 이 분리가 안 된 신호다.

### 4.1 코드 4분류와 Humble Object 패턴

**한 줄 요약:** 복잡도/도메인 중요도 × 협력 객체 수로 코드를 4분류하고, 과복잡 코드는 도메인(판단, 단위 테스트)과 얇은 서비스(읽기 → 판단 → 쓰기, 소수 통합 테스트)로 쪼갠다.

#### 코드를 4분류하기
두 축으로 나눕니다: **복잡도/도메인 중요도**(세로) x **협력 객체 수**(가로).

| | 협력 객체 적음 | 협력 객체 많음 |
|---|---|---|
| **복잡/중요** | **도메인 모델, 알고리즘** → 단위 테스트 (가성비 최고) | **과복잡 코드** → 분리해야 함 (fat controller) |
| **단순/덜 중요** | 사소한 코드 → **테스트하지 않음** | **컨트롤러(오케스트레이션)** → 통합 테스트로 소수만 |

- 복잡하고 중요한 코드는 **협력 객체가 적어야** 합니다. "깊이(복잡도)와 너비(협력 객체 수)를 동시에 가지지 말라"는 뜻입니다.
- 사소한 코드(생성자, getter)는 테스트하지 않습니다. 나쁜 테스트를 쓰느니 안 쓰는 것이 낫습니다.
- 복잡도는 분기점 수(순환 복잡도 = 1 + 분기점 수)로 셉니다. 분기가 없어도 결제 금액 계산처럼 도메인 중요도가 높으면 테스트할 가치가 있습니다(복잡도와 도메인 중요도는 서로 독립).
- 도메인 클래스의 협력 객체는 프로세스 외부와 통신하지 않는 한 한두 개는 괜찮습니다. 이런 내부 협력에 목을 쓰지는 않습니다.

#### Humble Object 패턴
- 문제: 로직이 테스트하기 어려운 것(DB, 외부 API, 프레임워크, UI)과 뒤섞여 있다.
- 해법: **로직을 별도 클래스/함수로 빼내고**, 원래 코드는 그 둘을 이어 주는 **얇은(humble) 껍데기**만 남긴다. 얇은 껍데기는 로직이 없으므로 굳이 단위 테스트하지 않는다.
- 헥사고날, MVC, DDD Aggregate 등 유명한 구조들도 결국 같은 원리(로직과 조율의 분리)입니다.

#### 예: 서비스 메서드를 나누기
```ts
// (보충: 원서 7.2의 이메일 변경 예제를 NestJS 스타일 TS로 바꾼 예시)
// Before: 한 곳에 판단, DB, 메시지 발행이 뒤섞임 (테스트하기 힘든 과복잡 코드)
async changeEmail(userId: number, newEmail: string) {
  const user = await this.db.findUser(userId);
  const company = await this.db.findCompany();
  if (user.isEmailConfirmed) return '이미 확정된 이메일';
  const isCorporate = newEmail.endsWith('@' + company.domain);
  if (isCorporate && user.type !== 'employee') company.employees++;
  // ... 계속 분기하며 저장하고 메시지 발행
}

// After: 도메인(판단)과 서비스(조율)를 분리
class User {                       // 도메인: 단위 테스트 대상
  changeEmail(newEmail: string, company: Company) { /* 규칙만, 외부 호출 없음 */ }
}
class UserService {                // 조율: 얇게, 통합 테스트로 커버
  async changeEmail(userId: number, newEmail: string) {
    const user = await this.userRepo.findById(userId);     // 읽기
    const company = await this.companyRepo.get();
    user.changeEmail(newEmail, company);                   // 판단(도메인)
    await this.userRepo.save(user);                        // 쓰기
    await this.companyRepo.save(company);
    await this.bus.publish(new EmailChanged(userId, newEmail));
    return 'OK';
  }
}
```
- "읽기 → 판단 → 쓰기" 세 단계로 나누는 것이 기본 형태입니다.
- 업무 도중 DB 조회가 더 필요한 경우가 있는데, 이때는 세 가지 중 하나로 타협합니다: (1) 미리 다 읽어 오기(성능 손해), (2) 도메인에 의존성 주입(테스트성 손해), (3) 판단을 더 작은 단계로 쪼개 서비스가 단계별로 처리(서비스가 복잡해짐). **도메인 테스트 용이성, 서비스 단순함, 성능** 셋 중 둘만 잡을 수 있습니다. 원서의 권장: 성능이 대개 중요하므로 (1)은 어렵고, (2)는 도메인이 과복잡 코드로 돌아가므로 피하며, (3)을 택하되 서비스가 복잡해지는 것을 아래 두 기법으로 줄입니다.
- **CanExecute/Execute 패턴**: 도메인에 `canChangeEmail()` 같은 검사 메서드를 두고, 실제 `changeEmail()` 안에서도 그 검사를 전제 조건으로 다시 확인합니다. 서비스는 판단 규칙을 몰라도 되고, 검사를 빠뜨려도 잘못된 변경이 일어나지 않습니다.
- **도메인 이벤트**: 도메인이 자신의 변화(예: 이메일이 실제로 바뀜)를 이벤트로 기록해 두고, 서비스가 작업이 끝난 뒤 이를 외부 호출(메시지 발행 등)로 바꿉니다. 그러면 위 예제처럼 "이메일이 안 바뀌었는데도 메시지를 보내는" 문제를 서비스에 if를 넣지 않고 막을 수 있습니다.
- 그래도 이메일 중복 확인처럼 서비스에 남는 판단은 있으며, 이런 부분은 통합 테스트로 덮습니다.

#### 무엇을 테스트할까
- 도메인 모델/알고리즘: 분기(엣지 케이스)를 **단위 테스트로 많이** 검증합니다.
- 도메인 중요도가 있는 전제 조건(precondition)은 테스트합니다 (예: 직원 수는 음수가 될 수 없다). 도메인 의미가 없는 방어 코드는 테스트하지 않습니다.
- 컨트롤러/서비스: 통합 테스트로 소수만 검증합니다 (→ 코어 5).

> 🔗 NestJS 연결: 얇은 Controller와 Service가 오케스트레이션을 맡고, 순수 도메인 클래스(엔티티, 값 객체, 정책 함수)는 프레임워크 데코레이터 없이 만드세요. 그러면 `new`만으로 단위 테스트할 수 있습니다.

> 📖 원문: 7.1 ~ 7.5 (원서는 DB 접근을 팩토리/ORM 매핑으로 분리하는 과정도 다룸)

### 4.2 안티패턴: 코드 오염 (Code Pollution)

**한 줄 요약:** 테스트만을 위한 스위치 코드를 프로덕션에 넣지 말고, 인터페이스(토큰)로 프로덕션 구현과 테스트용 구현을 분리한다.

- 테스트를 위해서만 존재하는 코드를 프로덕션에 넣는 것 (`if (isTestEnv) return;` 같은 스위치).
- 프로덕션 코드가 복잡해지고, 테스트용 경로가 실수로 운영에서 실행될 위험이 있습니다.
- 대안: 인터페이스(또는 토큰)를 두고 **프로덕션 구현 / 테스트용 구현을 분리**합니다. 인터페이스는 코드가 없으므로 버그 위험이 훨씬 작습니다.

> 📖 원문: 11.4

### 4.3 안티패턴: 구체 클래스의 일부만 목킹하기 (`spyOn` 부분 대체)

**한 줄 요약:** 일부 메서드만 가짜로 바꾸고 싶다면 그 클래스가 책임을 둘 이상 가진 것이므로, 외부 통신(목)과 계산(실제)으로 쪼갠다.

- "클래스의 일부 메서드만 가짜로 바꾸고 나머지는 진짜로" 쓰는 방식은 그 클래스가 **책임을 둘 이상 가졌다**는 신호입니다 (예: 외부 API 호출 + 통계 계산).
- 해법: 책임을 둘로 쪼갭니다. 외부 통신은 `DeliveryGateway`(인터페이스 + 목), 계산은 `StatisticsCalculator`(순수 로직, 실제 사용). 이것도 Humble Object 패턴입니다. (원서 예제: 배송 통계 계산기가 외부 서비스에서 배송 목록을 가져오는 클래스)

> 📖 원문: 11.5

## 코어 5. 관리형 vs 비관리형 의존성: 목의 자리와 통합 테스트

이 묶음의 원리: **"외부에서 보이는 부수 효과인가?"** 이 질문 하나로 무엇을 목으로 검증할지(5.1), 통합 테스트에서 무엇을 실제로 띄울지(5.2), 목을 어디에 어떻게 둘지(5.3)가 정해집니다. 실제로 띄우는 관리형 의존성(DB)을 잘 다루는 법이 5.4~5.5입니다.

### 5.1 시스템 내부 통신 vs 시스템 간 통신, 목의 올바른 자리

**한 줄 요약:** 클래스 간 호출(시스템 내부 통신)은 구현 세부 사항이라 목으로 검증하지 않고, 외부 시스템과의 통신 중 외부에 보이는 것(비관리형)만 목으로 검증한다. 내 앱 전용 DB(관리형)는 실제 것을 쓴다.

#### 헥사고날 아키텍처 (Hexagonal Architecture)
애플리케이션은 두 층으로 나뉩니다.
- **도메인 계층**: 비즈니스 로직(규칙, 계산, 판단). 외부 세계를 모릅니다.
- **애플리케이션 서비스 계층(컨트롤러 역할)**: DB에서 읽고, 도메인을 호출하고, 저장하고, 외부 시스템과 통신하는 **조율자**. 비즈니스 로직은 없습니다.
- 의존 방향은 **서비스 → 도메인** 한 방향입니다.
- 각 층마다 "관찰 가능한 동작"이 있고, 테스트는 층별로 그 동작을 검증합니다 (도메인 테스트는 세부 목표, 서비스 테스트는 유스케이스 전체).

#### 두 종류의 통신

| | 시스템 내부(intra-system) | 시스템 간(inter-system) |
|---|---|---|
| 예 | 클래스 사이의 호출 (Customer → Store) | 앱 → SMTP, 메시지 큐, 외부 API |
| 성격 | **구현 세부 사항** | **관찰 가능한 동작(계약)** |
| 목으로 검증? | **하지 않는다** (깨지기 쉬움) | **한다** (하위 호환을 지켜야 하므로) |

- 외부 시스템은 내가 마음대로 바꿀 수 없기 때문에, 메시지 구조나 호출 방식이 **리팩터링 후에도 그대로**여야 합니다. 이를 지키는 도구가 목입니다.
- 반대로 내부 클래스끼리의 호출을 목으로 검증하면, 내부를 고칠 때마다 테스트가 깨집니다.

#### 모든 프로세스 외부 의존성을 목으로 바꾸는 건 아니다
- 프로세스 외부 의존성은 두 종류입니다.
  - **관리형(managed)**: 내 앱만 접근하는 것. 예: **내 애플리케이션 전용 DB**. 외부에 보이지 않으므로 통신 방식은 구현 세부 사항. → **실제 것을 그대로** 쓴다.
  - **비관리형(unmanaged)**: 외부에서도 보이는 부수 효과. 예: SMTP, 메시지 큐(Kafka, RabbitMQ), 결제 API. → **목으로 대체**한다.
- 이 규칙은 아래 통합 테스트에서 다시 사용됩니다.
- (참고) 관리형/비관리형이라는 용어는 원서 8.2.1에서 정리됩니다. 5.4.1에서는 "앱만 접근하는 DB와의 통신은 구현 세부 사항"이라고 설명합니다.
- 내부 클래스 간에 목을 쓰면 테스트가 구현에 묶인다는 점이 런던파가 취약한 이유입니다. 목이 "동작을 검증한다"는 말은 애플리케이션 경계를 넘고 그 부수 효과가 외부에 보일 때만 맞습니다.

> 📖 원문: 5.3 ~ 5.4 (관리형/비관리형 용어는 8.2.1)

### 5.2 통합 테스트

**한 줄 요약:** 통합 테스트는 시나리오당 가장 긴 성공 경로 하나 + 단위로 못 잡는 엣지 케이스만 검증하고, 관리형 의존성은 실제로·비관리형은 목으로 쓰며, 인터페이스는 목이 필요한 비관리형 의존성에만 둔다.

#### 역할과 테스트 피라미드
- 통합 테스트는 **단위 테스트가 아닌 모든 테스트**입니다 (E2E 포함). 실제로는 컨트롤러(서비스 계층)가 DB, 메시지 큐 등과 잘 붙는지 검증합니다.
- 통합 테스트는 더 많은 코드를 실행하므로 **회귀 방지와 리팩터링 내성이 높지만, 느리고 유지비가 큽니다.**
- 그래서 피라미드 모양이 됩니다.
  - 아래(많이): 단위 테스트 — 비즈니스 시나리오의 **엣지 케이스를 최대한 여기서** 검증
  - 위(적게): 통합 테스트 — 시나리오당 **가장 긴 성공 경로(happy path) 하나** + 단위로 못 잡는 엣지 케이스
- 로직이 적은 단순 앱이라면 피라미드가 아니라 직사각형(단위=통합 비슷)이 됩니다.
- **Fail Fast**: 잘못된 사용이 첫 실행에 바로 예외로 터지고 데이터가 오염되지 않는다면, 그 엣지 케이스는 통합 테스트로 굳이 검증하지 않아도 됩니다. (운영 관점의 Fail Fast는 [Part 9](Part09_운영안정성.md)에서 다룹니다.)

#### 어떤 외부 의존성을 실제로 쓰나

| 종류 | 예 | 통합 테스트에서 |
|---|---|---|
| 관리형 (내 앱 전용) | 내 서비스 전용 DB (PostgreSQL) | **실제 인스턴스 사용**, 최종 상태를 검증 |
| 비관리형 (외부 노출) | SMTP, 메시지 큐, 결제 API | **목으로 대체**, 호출 계약을 검증 |

- 내 DB 테이블을 다른 서비스가 직접 읽고 있다면, 그 부분은 **비관리형처럼 취급**(계약 보존)해야 합니다. 하지만 DB를 통한 시스템 간 통합은 결합이 커지므로 API나 메시지로 바꾸는 것이 좋습니다.
- 실제 DB를 쓸 수 없는 상황이라면 어중간하게 DB를 목으로 바꾸지 말고, **통합 테스트를 포기하고 도메인 단위 테스트에 집중**하세요. 가치가 낮은 테스트는 없느니만 못합니다.

#### 인터페이스 남용 주의 (NestJS 개발자에게 중요)
- "모든 서비스/리포지토리에 인터페이스를 만든다"는 관습은 대부분 **잘못된 이유**입니다.
  - 구현이 하나뿐인 인터페이스는 진짜 추상화가 아니며, 느슨한 결합도 주지 않습니다 (진짜 추상화는 구현이 2개 이상일 때 "발견"됩니다).
  - "나중에 확장하려고"는 YAGNI(필요할 때 만들자) 위반입니다.
- 인터페이스를 만드는 현실적 이유는 **목을 만들기 위해서**입니다. 그러니 **비관리형 의존성(메일, 메시지 큐, 결제)에만** 인터페이스(TypeScript에서는 interface나 abstract class/토큰)를 두고, 관리형 의존성(내 DB/ORM)은 구체 클래스로 주입합니다.
- 도메인 클래스에 `IUser` 같은 인터페이스를 만들면 위험 신호입니다. 도메인 간 상호작용을 목으로 검증하게 되기 때문입니다.

#### 통합 테스트 모범 사례
1. **도메인 모델의 경계를 명확히**: 도메인 코드가 한곳(폴더/모듈)에 모여 있어야 단위/통합 테스트 대상을 나누기 쉽습니다.
2. **계층 수 줄이기**: 대부분 백엔드는 도메인, 애플리케이션 서비스, 인프라 3계층이면 충분합니다. 계층이 많아지면 계층별로 목을 끼워 테스트하게 되어 가치가 떨어집니다.
3. **순환 의존 제거**: A가 B를, B가 A를 호출하는 구조는 읽기도 테스트도 어렵습니다. 인터페이스로 컴파일 순환만 숨기지 말고, B가 값을 반환하도록 바꿔 순환 자체를 없애세요.
4. **통합 테스트도 Act는 가급적 하나**: "등록 → 삭제"를 한 테스트에 이어 붙이지 마세요. 예외는 호출 제한이 있는 느린 외부 샌드박스 같은 경우뿐입니다.

> 🔗 NestJS 연결: 순환 의존이 생기면 `forwardRef()`로 임시 회피하기 쉬운데, 이는 위에서 말한 "숨기기"입니다. 설계로 순환을 없애는 것이 정답입니다. 또한 NestJS의 DI 토큰/Provider 덕분에 비관리형 의존성(예: `MAILER`)만 mock provider로 교체하는 통합 테스트가 자연스럽게 가능합니다. (`forwardRef()`와 DI 토큰/Provider는 [Part 3](Part03_NestJS핵심.md)에서 다룹니다.)

> 📖 원문: 8.1 ~ 8.5 (8.6 로깅 테스트는 이 원고에서 생략)

### 5.3 목 사용 모범 사례

**한 줄 요약:** 목은 비관리형 의존성에만, 시스템 가장 바깥 경계의 마지막 타입에, 통합 테스트에서만, 내가 소유한 타입(어댑터)에만 쓰고, 기대값은 리터럴로 적는다.

1. **비관리형 의존성에만 목을 쓴다.** (DB 같은 관리형은 실제를 씀)
2. **시스템의 가장 바깥 경계에서 검증한다.** 컨트롤러와 외부 시스템 사이 **마지막 타입**을 목으로 만듭니다. 원서 예: 메시지 버스 SDK를 감싼 `IBus`(문자열 메시지를 보냄)가 마지막 타입이고, 그 위의 도메인 메시지 래퍼 `MessageBus`는 중간 단계라서 `IBus`를 목킹하고 `MessageBus`는 실제로 씁니다. 그러면 실제로 외부에 나가는 메시지 문자열까지 검증되어 회귀 방지와 리팩터링 내성이 함께 높아집니다.
3. **목은 통합 테스트에서만 쓴다.** 도메인(단위 테스트)에는 외부 협력 객체가 없어야 하므로 목이 필요 없습니다. 필요하다면 설계가 잘못된 것입니다.
4. **목이 몇 개든 상관없다.** 한 테스트에 목이 여러 개인 건, 그 시나리오가 외부 시스템을 여러 개 쓰기 때문입니다.
5. **호출이 있었는지 + 예상 밖의 호출이 없었는지 둘 다 확인한다.** 외부 시스템 입장에서는 "빠진 메시지"와 "엉뚱한 메시지" 모두 계약 위반입니다.
6. **내가 소유한 타입만 목으로 만든다.** 서드파티 SDK를 직접 목킹하지 말고, 내가 만든 <strong>어댑터(래퍼)</strong>를 만들어 그것을 목킹하세요(원서는 이를 부패 방지 계층 역할이라 설명). SDK 업그레이드 영향이 어댑터 한 곳에 갇힙니다. 단, 프로세스 내부/관리형 의존성(날짜 API, 내 DB용 ORM)은 굳이 감쌀 필요가 없습니다. (Stripe, AWS SDK는 보충 예시)
7. 테스트의 기대값은 프로덕션 코드의 상수를 재사용하지 말고 **테스트에 리터럴로 직접 적습니다.** 프로덕션 값과 같은 것을 참조하면 무엇이 틀려도 통과하는 동어반복 테스트가 됩니다. 테스트가 프로덕션과 독립된 "감사자" 역할을 해야 합니다.
8. **직접 만든 스파이(spy)** 는 시스템 경계 클래스에 목보다 유리할 수 있습니다. 보낸 메시지를 저장해 두고 `shouldSendNumberOfMessages(1).withEmailChangedMessage(...)`처럼 체이닝으로 검증하면 단언 코드를 재사용하고 짧고 읽기 좋아집니다.
9. 예외: **로그**처럼 정확한 문자열 구조보다 "기록이 남는가"가 중요한 비관리형 의존성은 가장 바깥이 아니라 도메인 로거 수준에서 목킹해도 충분합니다.

```ts
// (보충: 원서의 IBus 예제를 응용한 통합 테스트 예시) 결제 어댑터(PaymentGateway)만 목, DB는 실제
it('구독을 시작하면 결제가 정확히 한 번 요청된다', async () => {
  const gateway = { charge: jest.fn().mockResolvedValue({ ok: true }) };
  const sut = await createApp({ overrides: [{ token: PAYMENT_GATEWAY, value: gateway }] });

  const res = await sut.post('/subscriptions', { plan: 'pro' });

  expect(res.status).toBe(201);
  expect(gateway.charge).toHaveBeenCalledTimes(1);
  expect(gateway.charge).toHaveBeenCalledWith({ amount: 29000, currency: 'KRW' });  // 리터럴로 직접 명시
  // 실제 DB에서 구독 행이 생성되었는지 별도 조회로 확인
});
```

### 5.4 데이터베이스를 활용한 통합 테스트

**한 줄 요약:** 스키마는 명시적 마이그레이션으로 소스 관리하고, 한 업무의 변경은 한 트랜잭션/Unit of Work로 묶으며, 테스트의 Arrange·Act·Assert는 각각 별도 컨텍스트를 쓴다.

#### 준비 사항

| 항목 | 원칙 |
|---|---|
| 스키마를 소스 관리 | DB 구조는 코드처럼 Git에서 관리. "기준 DB 인스턴스"를 따로 두는 방식은 이력도 없고 진실의 원천도 둘로 갈라져 나쁨 |
| 참조 데이터도 스키마의 일부 | 앱이 수정하지 않는 필수 초기 데이터(원서 예: 사용자 유형 테이블. 보충 예: 요금제/역할 목록)는 마이그레이션에 SQL INSERT로 포함. 앱이 수정하면 일반 데이터 |
| 개발자마다 별도 DB | 공유 DB는 테스트끼리 간섭하고, 호환 안 되는 변경이 다른 개발자를 막음. 가능하면 본인 머신에 개인 DB를 사용 (Docker로 띄우는 것도 가능) |
| **마이그레이션 기반 배포** | 상태 기반(비교 도구가 자동 생성)이 아니라 **명시적 마이그레이션 스크립트**로 관리 |

- 마이그레이션 방식이 중요한 이유는 **데이터 이동(data motion)** 때문입니다. 예를 들어 `name` 컬럼을 `first_name`, `last_name`으로 쪼갤 때는 기존 데이터를 변환하는 스크립트가 필요한데, 자동 비교 도구는 이를 못 합니다. 출시 후에는 버릴 수 없는 데이터가 있으므로 마이그레이션이 필수입니다.
- 커밋된 마이그레이션은 **수정하지 않습니다.** 틀렸다면 새 마이그레이션을 추가하세요 (데이터 손실 위험이 있을 때만 예외).

- 원서: 상태 기반 방식(비교 도구가 자동 생성)은 출시 전 임시로만 쓸 수 있고, 첫 출시 이후에는 마이그레이션 기반으로 바꿔야 합니다. 마이그레이션에는 되돌리는(down) 스크립트를 두면 옛 버전 재현에 유용합니다.

> 🔗 NestJS 연결(보충): TypeORM/Prisma/MikroORM/Knex의 migration 기능이 이 역할입니다. `synchronize: true`(자동 스키마 동기화)는 상태 기반 방식에 해당하며 개발 초기 임시용일 뿐 운영에서 쓰면 안 됩니다.

#### 트랜잭션 관리와 Unit of Work
- 한 업무(비즈니스 오퍼레이션)에서 <strong>데이터를 바꾸는 작업은 모두 원자적(atomic, 전부 성공 or 전부 취소)</strong>이어야 합니다.
- 예: 회사의 직원 수를 저장한 뒤 사용자 저장이 실패하면 "직원 수는 늘었는데 직원은 없는" 불일치가 DB에 남습니다.
- 두 결정을 분리하세요.
  - **무엇을 바꿀지** → 리포지토리(호출마다 짧게 쓰고 버려도 됨)
  - **반영할지 취소할지** → 트랜잭션(업무 전체 동안 유지, 성공 시에만 commit)
- **Unit of Work**: 변경된 객체를 모아 두었다가 업무 끝에 한 번에 저장(원서: EF의 `SaveChanges`). 트랜잭션이 짧아져 DB 경합도 줄고 DB 호출 수도 줄어듭니다. 원서는 NHibernate/Entity Framework를 예로 듭니다. (보충: Node 쪽에서는 MikroORM의 `em.flush()`가 같은 개념이고, TypeORM의 `dataSource.transaction()`이나 Prisma의 `$transaction`은 업무 단위 트랜잭션을 만들어 주는 도구로 이해하면 안전합니다.)
- 읽기 전용 작업은 트랜잭션을 여러 번 써도 문제없습니다.
- 문서형 DB(MongoDB 등)는 한 문서 안에서만 원자성이 보장되므로, 한 업무가 한 문서(Aggregate)만 바꾸도록 설계합니다.

```ts
// (보충: TypeORM 기반 예시) 서비스에서 한 업무 = 한 트랜잭션
async changeEmail(userId: number, newEmail: string) {
  return this.dataSource.transaction(async (em) => {
    const user = await em.findOneByOrFail(User, { id: userId });
    const company = await em.findOneByOrFail(Company, {});
    user.changeEmail(newEmail, company);      // 도메인 판단
    await em.save([user, company]);           // 성공하면 함께 commit, 예외면 함께 rollback
    return 'OK';
  });
}
```

#### 테스트에서의 트랜잭션 규칙
- 프로덕션은 업무 하나마다 <strong>새 컨텍스트(연결/세션)</strong>를 씁니다. 테스트도 이를 그대로 재현해야 합니다.
- 테스트의 <strong>Arrange / Act / Assert 각각 별도의 트랜잭션(또는 컨텍스트)</strong>을 사용하세요(원서: 최소 3개). 같은 컨텍스트를 재사용하면 ORM이 데이터를 캐시해 DB 상태를 독립적으로 확인하지 못하는 착시가 생깁니다.
- 준비/실행/검증 코드를 헬퍼(팩토리 메서드, 서비스를 실행하는 래퍼, 체이닝 검증)로 빼서 통합 테스트를 짧게 유지합니다. 그 결과 DB 컨텍스트가 늘어 조금 느려지지만, 이는 속도를 유지보수성과 맞바꾸는 것이며 감수할 만합니다(원서 10.4).

> 📖 원문: 10.1, 10.2, 10.4

### 5.5 테스트 데이터 생명주기

**한 줄 요약:** 통합 테스트는 순차 실행하고, 데이터는 테스트 "시작 시" 손으로 쓴 SQL로 일반 데이터만 정리하며, 인메모리 DB 대신 운영과 같은 DBMS를 쓴다. 쓰기는 꼼꼼히, 읽기는 중요한 것만, 리포지토리는 단독 테스트하지 않는다.

#### 격리 방법
- 통합 테스트는 **순차 실행**이 현실적입니다. 병렬로 돌리려면 데이터 유일성 보장과 정리가 어려워져 비용이 큽니다. 원서는 단위/통합 테스트 컬렉션을 나누고 통합 쪽만 병렬을 끄라고 합니다. (보충: Jest에서는 `--runInBand` 또는 프로젝트 분리)
- 테스트마다 컨테이너를 새로 띄워 병렬화하는 방법은 이미지·컨테이너 관리 부담이 커서 꼭 필요할 때만 권합니다. 개발자당 DB 하나를 Docker로 띄우는 것은 괜찮습니다("성급한 병렬화"를 반대).
- 테스트 사이 데이터를 정리하는 방법 4가지 비교:

| 방법 | 평가 |
|---|---|
| 매번 백업 복원 / 컨테이너 재생성 | 느림 |
| **테스트 끝에** 정리 | 빠르지만 중간에 죽으면 정리가 생략되어 다음 테스트 오염 |
| 테스트 전체를 롤백되는 트랜잭션으로 감싸기 | 프로덕션과 다른 트랜잭션 구조가 되어 결과가 왜곡됨 |
| **테스트 시작 시** 정리 | **최선**: 빠르고, 생략될 위험 없고, 프로덕션과 동일한 동작 |

- 정리 SQL은 **직접 손으로** 쓰세요 (FK 순서 고려). 자동 생성 알고리즘이나 제약 조건 해제는 불필요하게 복잡합니다. 원서는 모든 통합 테스트의 공통 부모 클래스에 넣어 매 테스트 시작 때 실행합니다. (별도 teardown 단계는 필요 없고 Arrange의 일부로 봅니다.)
- 정리는 **일반 데이터만** 지우고, 참조 데이터(마이그레이션이 관리하는 것)는 지우지 않습니다.

```ts
// (보충: Postgres/TypeORM 기준 예시. 원서 예제는 DELETE 문)
beforeEach(async () => {
  await dataSource.query('TRUNCATE TABLE subscriptions, users, companies RESTART IDENTITY CASCADE');
});
```

#### 인메모리 DB(SQLite 등) 쓰지 않기
- 인메모리 DB는 빠르고 정리도 쉬워 보이지만, **운영 DB와 기능이 달라** 오탐/미탐이 생기고 결국 수동 회귀 테스트가 남습니다. (보충: JSON 연산, 락, 인덱스, 제약 조건, 타입 차이 등이 흔한 차이점)
- **운영과 같은 DBMS**를 테스트에서 쓰세요 (버전·에디션은 달라도 되지만 제품은 같아야 함). (보충: Docker의 PostgreSQL 컨테이너가 실용적인 방법)

#### 무엇을 테스트할까: 읽기 vs 쓰기, 리포지토리
- **쓰기는 꼼꼼히**: 실수하면 데이터 오염으로 이어져 피해가 큽니다.
- **읽기는 가장 복잡하거나 중요한 것만**: 읽기 버그의 피해는 상대적으로 작습니다. 읽기에는 도메인 모델이나 무거운 ORM 추상화가 필요 없고, 단순 SQL/쿼리 빌더로 충분합니다.
- **리포지토리를 단독으로 테스트하지 않습니다.** 비용은 통합 테스트 수준인데 얻는 보호는 전체 통합 테스트와 겹칩니다. 전체 시나리오 통합 테스트의 일부로만 검증하세요. (원서: 매핑 로직을 협력 객체 없는 팩토리로 뺄 수 있으면 그것만 테스트하되, ORM을 쓰면 DB 없이는 매핑을 테스트할 수 없음)
- 마찬가지로 도메인 이벤트를 외부 호출로 바꾸는 디스패처도 단독 테스트하지 않습니다(복잡한 목 설정 비용 대비 이득이 적음).

> 📖 원문: 10.3 ~ 10.5

### 체크리스트
- [ ] 테스트의 목적은 커버리지 수치가 아니라 **프로젝트를 오래 지속 가능하게** 만드는 것이다. 가치 없는 테스트는 쓰지 않는다.
- [ ] 테스트의 단위는 "클래스"가 아니라 **비즈니스적으로 의미 있는 동작 하나**다. 테스트는 `AAA` 구조, Act는 한 줄, `if` 없음, 이름은 도메인 언어 평서문.
- [ ] 좋은 테스트는 **회귀 방지 / 리팩터링 내성 / 빠른 피드백 / 유지보수성**을 모두 갖춘다. 그중 **리팩터링 내성은 양보하지 않는다.**
- [ ] 테스트는 <strong>관찰 가능한 동작(WHAT)</strong>만 검증하고 구현 세부 사항(HOW)은 검증하지 않는다. 구현은 private으로 숨기고 API를 캡슐화한다.
- [ ] **스텁은 검증하지 않는다.** 목은 **시스템 경계를 넘는 부수 효과**(메일, 메시지 큐, 결제)에만, 그리고 통합 테스트에서만 쓴다.
- [ ] 비즈니스 로직(도메인, 순수 함수)과 오케스트레이션(서비스)을 **Humble Object로 분리**한다. 도메인은 단위 테스트, 서비스는 소수의 통합 테스트로 검증한다.
- [ ] 스타일 선택은 **출력 기반 > 상태 기반 > 통신 기반** 순으로 우선한다.
- [ ] 내 앱 전용 DB(관리형)는 **운영과 같은 종류의 실제 DB**로 테스트하고, 외부 노출 의존성(비관리형)만 목으로 대체한다. **인메모리 DB는 피한다.**
- [ ] 한 업무의 데이터 변경은 **하나의 트랜잭션/Unit of Work**로 묶고, 마이그레이션으로 스키마를 관리한다. 테스트 데이터는 **테스트 시작 시** 정리한다.
- [ ] 안티패턴 회피: private 노출, 테스트 안에 알고리즘 복사, 테스트용 스위치 코드, 구체 클래스 부분 목킹, `new Date()` 직접 호출. **시간은 값으로 전달**한다.
- [ ] 인터페이스는 목이 필요한 비관리형 의존성에만 둔다. 구현이 하나뿐인 인터페이스를 습관적으로 만들지 않는다.

### 시나리오로 확인하기

1. **상황:** `ReportService`가 사용자 수와 활성 사용자 수를 쿼리 두 번으로 가져오던 것을 쿼리 한 번으로 합쳤다. 리포트 결과는 똑같은데 테스트 30개가 빨갛게 변했다. 테스트를 열어 보니 gMock에서 하던 습관대로 모든 리포지토리 호출에 `toHaveBeenCalledTimes`를 걸어 두었다.
   **질문:** 무엇이 잘못됐고, 테스트를 어떻게 고쳐야 하나?

   <details markdown="1"><summary>답 확인</summary>

   오탐(false positive)이다. 리포지토리 조회는 데이터를 "받아 오는" 들어오는 상호작용이므로 스텁이고, 스텁의 호출 여부·횟수를 검증하는 것은 과잉 명세다. 데이터를 어떻게 모으는지는 구현 세부 사항(HOW)이다. 스텁 호출 검증을 지우고, 최종 결과(리포트 값), 즉 관찰 가능한 동작(WHAT)만 검증한다. 오탐이 잦으면 팀이 실패를 무시해 진짜 버그도 놓치고 리팩터링을 두려워하게 된다. 더 근본적으로는 내 앱 전용 DB(관리형)는 목으로 바꾸지 말고 실제 DB로 통합 테스트하는 편이 낫다. → 코어 2, 코어 5

   </details>

2. **상황:** 통합 테스트를 빠르게 하려고 SQLite 인메모리 DB를 썼다. 테스트는 전부 통과했는데, 운영 PostgreSQL에서 JSON 컬럼 조회와 제약 조건 위반 처리 때문에 장애가 났다.
   **질문:** 무엇을 바꿔야 하나?

   <details markdown="1"><summary>답 확인</summary>

   인메모리 DB는 운영 DB와 기능이 달라 오탐/미탐이 생기고 결국 수동 회귀 테스트가 남는다((보충) JSON 연산, 락, 인덱스, 제약 조건, 타입 차이). 운영과 같은 DBMS(버전·에디션은 달라도 제품은 같게)를 테스트에 쓰고, 개발자마다 Docker로 개인 PostgreSQL을 띄운다. 스키마는 마이그레이션으로 관리하고, 통합 테스트는 순차 실행(Jest `--runInBand`)하며 데이터는 테스트 시작 시 정리한다. → 코어 5

   </details>

3. **상황:** 구독 갱신 테스트가 평소엔 통과하다가 월말이나 자정 근처에만 실패한다. 도메인 클래스 `Subscription.renew()` 안에서 `new Date()`를 직접 호출하고 있다. 게임 서버에서 틱 함수 안에서 `GetTickCount()`를 직접 불러 리플레이가 안 되던 것과 같은 문제다.
   **질문:** 어떻게 고치나?

   <details markdown="1"><summary>답 확인</summary>

   시간을 도메인 안에서 직접 얻으면 테스트가 실행 시점에 따라 달라진다. 세 방법 중 전역 컨텍스트(정적 필드, `jest.useFakeTimers()`로 전역 시간 바꾸기도 전역 상태를 건드림)는 피하고, 서비스(업무 시작점)에서 Provider로 주입한 `Clock`으로 현재 시간을 얻어 도메인에는 `sub.renew(now)`처럼 Date 값으로 넘긴다. 그러면 도메인 단위 테스트는 시간 고정 없이 `new Date('2026-01-30')` 같은 값만 넘기면 되는 출력 기반·상태 기반 테스트가 된다. → 코어 3

   </details>

4. **상황:** 통합 테스트가 중간에 예외로 죽은 뒤부터, 다음 실행에서 "duplicate key" 에러로 다른 테스트들이 줄줄이 실패한다. 데이터 정리는 `afterEach`에서 하고 있다.
   **질문:** 원인과 해법은?

   <details markdown="1"><summary>답 확인</summary>

   테스트 끝에 정리하면 중간에 죽었을 때 정리가 생략되어 다음 테스트가 오염된다. 정리는 테스트 "시작 시"(`beforeEach`, Arrange의 일부) 손으로 쓴 SQL(FK 순서 고려, 예: `TRUNCATE ... RESTART IDENTITY CASCADE`)로 하고, 마이그레이션이 관리하는 참조 데이터는 지우지 않는다. 테스트 전체를 롤백 트랜잭션으로 감싸는 방법은 프로덕션과 다른 트랜잭션 구조가 되어 결과가 왜곡되므로 피한다. → 코어 5

   </details>

5. **상황:** 결제 테스트에서 Stripe SDK를 `jest.mock('stripe')`로 통째로 목킹했다. SDK 메이저 버전을 올리자 메서드 시그니처가 바뀌어 테스트 수십 개를 고쳐야 했다. 한편 팀원은 "나중에 확장할 수도 있으니" 모든 서비스·리포지토리에 `IUserService` 같은 인터페이스를 만들자고 한다.
   **질문:** 두 문제를 이 장의 기준으로 정리하면?

   <details markdown="1"><summary>답 확인</summary>

   목은 내가 소유한 타입만 만든다. 서드파티 SDK는 내가 만든 어댑터(예: `PaymentGateway`, 부패 방지 계층 역할)로 감싸고 그 어댑터를 목킹하면 SDK 업그레이드 영향이 어댑터 한 곳에 갇힌다. 목은 비관리형 의존성의 가장 바깥 경계에서, 통합 테스트에서만 쓰고, 기대값(`{ amount: 29000, currency: 'KRW' }`)은 리터럴로 적는다. 인터페이스는 목이 필요한 비관리형 의존성(메일, 메시지 큐, 결제)에만 둔다. 구현이 하나뿐인 인터페이스는 진짜 추상화가 아니고 "나중에 확장"은 YAGNI 위반이다. NestJS에서는 DI 토큰으로 비관리형 의존성만 mock provider로 바꾸면 된다. → 코어 5

   </details>

### 2. 인출 질문

1. 단위 테스트의 진짜 목적은 무엇이고, 왜 "나쁜 테스트는 짐"이라고 하나요?

   <details markdown="1"><summary>답 확인</summary>

   목적은 버그 잡기만이 아니라 프로젝트가 오래 유지되면서도 개발 속도가 떨어지지 않게 하는 것(지속 가능한 성장)입니다. 나쁜 테스트는 오탐을 남발하고 유지비(리팩터링·실행·오탐 대응·읽기 비용)만 들어 결국 프로젝트를 똑같이 정체시킵니다. 테스트도 코드이므로 "적을수록 좋은 부채"이고, 가치 없는 테스트는 안 쓰는 편이 낫습니다. → 코어 1 (1.1)

   </details>

2. 커버리지가 "낮을 때만 의미 있는 나쁜 쪽 지표"인 이유는?

   <details markdown="1"><summary>답 확인</summary>

   낮은 수치는 테스트되지 않은 부분이 있다는 확실한 위험 신호지만, 높은 수치는 아무것도 보장하지 않습니다. 검증(assert) 없이 실행만 해도 수치가 오르고, 검증이 의미 있는지·외부 라이브러리 결과까지는 알려 주지 못하기 때문입니다. 특정 숫자를 강제하면 수치를 채우려는 나쁜 테스트가 늘어납니다. 코드 커버리지는 코드를 압축만 해도 오르고, 분기 커버리지가 더 정확하지만 한계는 같습니다. → 코어 1 (1.2)

   </details>

3. 단위 테스트의 세 조건은 무엇이고, "단위"는 무엇을 뜻하나요?

   <details markdown="1"><summary>답 확인</summary>

   ① 한 단위의 동작을 검증하고 ② 빠르게 실행되며 ③ 다른 테스트와 격리되어 실행되는 테스트입니다. 하나라도 어기면 통합 테스트입니다. "단위"는 클래스 하나가 아니라 비즈니스 관점에서 의미 있는 동작 하나이며, 그 동작을 구현하는 클래스 수는 상관없습니다. → 코어 2 (2.1)

   </details>

4. 고전파와 런던파는 무엇이 다르고, 이 책은 왜 고전파를 권하나요?

   <details markdown="1"><summary>답 확인</summary>

   고전파는 테스트끼리 격리하고 공유 의존성(DB, 외부 API 등)만 대체합니다. 런던파는 대상 클래스를 협력 객체로부터 격리해 불변 값 객체 외 거의 모든 협력 객체를 목으로 바꿉니다. 협력 객체를 다 목으로 바꾸면 테스트가 구현 세부 사항에 묶여 깨지기 쉬워지고, 런던파의 장점은 실제로 "설계 문제를 목으로 덮는 것"인 경우가 많기 때문입니다. → 코어 2 (2.1)

   </details>

5. Act가 두 줄 이상이면 무엇의 신호이고, 무엇을 고쳐야 하나요?

   <details markdown="1"><summary>답 확인</summary>

   API가 캡슐화되지 않았다는 신호입니다. 예: `customer.purchase()` 뒤에 `store.removeInventory()`를 따로 호출해야 하면 호출자가 두 번째 호출을 잊을 때 "구매 성공 + 재고 감소"라는 불변식이 깨집니다. 테스트가 아니라 한 번의 호출로 두 결과가 함께 보장되도록 코드의 캡슐화를 고칩니다. → 코어 2 (2.2)

   </details>

6. `메서드명_시나리오_기대결과` 같은 테스트 이름 규칙을 피하라는 이유와 권장 방식은?

   <details markdown="1"><summary>답 확인</summary>

   메서드 이름(구현)에 묶여 메서드 이름을 바꾸면 테스트 이름도 바꿔야 하기 때문입니다. 비개발자(도메인 전문가)에게 설명하듯 평서문으로 쓰고, `should be ~`(바람) 대신 `is ~`(사실)로 씁니다. 예: "과거 날짜로는 배송을 예약할 수 없다". 비즈니스 의미가 없는 유틸리티 코드는 예외적으로 메서드 이름을 써도 됩니다. → 코어 2 (2.3)

   </details>

7. 좋은 테스트의 4기둥은 무엇이고, 왜 실제 절충은 "회귀 방지 vs 속도"에서만 일어나나요?

   <details markdown="1"><summary>답 확인</summary>

   회귀 방지, 리팩터링 내성, 빠른 피드백, 유지보수성입니다. 테스트의 가치는 네 점수를 곱한 값이라 하나라도 0이면 전체가 0입니다. ①②③은 동시에 최대가 될 수 없는데, 리팩터링 내성은 "있거나 없거나"에 가까워 양보할 수 없으므로 남은 회귀 방지와 속도 사이에서 절충합니다(예: E2E는 회귀 방지·내성 최고지만 느림). → 코어 1 (1.3)

   </details>

8. 오탐(false positive)은 왜 위험하고, 원인과 해법은 무엇인가요?

   <details markdown="1"><summary>답 확인</summary>

   기능은 멀쩡한데 테스트가 깨지는 것이 오탐입니다. 잦으면 팀이 실패를 무시해 진짜 버그도 놓치고, 테스트가 무서워 리팩터링을 하지 않게 됩니다. 프로젝트가 커질수록 오탐은 미탐만큼 치명적입니다. 원인은 테스트가 구현 세부 사항(HOW)에 결합한 것 하나이고, 해법은 최종 결과(WHAT), 즉 관찰 가능한 동작만 검증하는 것입니다. → 코어 1 (1.3), 코어 2

   </details>

9. 스텁과 목의 차이는 무엇이고, 스텁 호출을 검증하면 왜 안티패턴인가요?

   <details markdown="1"><summary>답 확인</summary>

   스텁은 대상이 데이터를 받아 오는 "들어오는" 상호작용(쿼리)을 흉내 내며 호출 자체를 검증하지 않습니다. 목은 부수 효과를 일으키는 "나가는" 상호작용(커맨드)을 흉내 내고 호출 여부·인자·횟수를 검증합니다. 대상이 데이터를 어떻게 모으는지는 결과가 아니라 과정(구현)이므로, 스텁 호출 검증은 과잉 명세가 되어 깨지기 쉽습니다. `jest.fn()`은 도구일 뿐이니 역할로 구분합니다. → 코어 2 (2.4)

   </details>

10. "관찰 가능한 동작"의 정의와, 구현이 새고 있다는 경험 법칙은?

    <details markdown="1"><summary>답 확인</summary>

    호출자가 자기 목표를 이루기 위해 사용하는 연산(계산·부수 효과)과 상태입니다. 나머지는 구현 세부 사항이며 이상적으로는 전부 private이어야 합니다. 하나의 목표를 위해 호출자가 클래스의 연산을 2번 이상 호출해야 한다면 구현이 새고 있을 가능성이 높습니다(예: `normalizeName()`을 직접 불러야 하는 `User`). API를 잘 설계하면 테스트가 자동으로 좋아집니다. → 코어 2 (2.5)

    </details>

11. 시스템 내부 통신과 시스템 간 통신 중 어느 쪽을 목으로 검증하나요? 프로세스 외부 의존성은 모두 목인가요?

    <details markdown="1"><summary>답 확인</summary>

    시스템 내부 통신(클래스 간 호출)은 구현 세부 사항이라 목으로 검증하지 않고, 시스템 간 통신(SMTP, 메시지 큐, 외부 API)은 하위 호환을 지켜야 하는 관찰 가능한 동작이라 목으로 검증합니다. 프로세스 외부 의존성 중 관리형(내 앱 전용 DB)은 외부에 보이지 않으므로 실제 것을 쓰고, 비관리형(외부에서도 보이는 부수 효과)만 목으로 대체합니다. → 코어 5 (5.1)

    </details>

12. 세 가지 테스트 스타일을 리팩터링 내성·유지보수성으로 비교하고, 출력 기반을 늘리는 방법을 말해 보세요.

    <details markdown="1"><summary>답 확인</summary>

    출력 기반(입력 → 반환값)이 둘 다 최고, 상태 기반이 보통, 통신 기반(목 사용)이 가장 위험·가장 낮습니다. 회귀 방지와 속도는 스타일과 크게 상관없습니다. 비즈니스 로직(결정을 내리는 함수형 코어)과 부수 효과(가변 셸)를 분리해 "읽기 → 결정 → 실행"으로 만들면 코어를 출력 기반으로 테스트할 수 있습니다. 단 성능·코드량 비용이 있어 가능한 만큼만 옮깁니다. → 코어 3 (3.1)

    </details>

13. 코드를 4분류하는 두 축과 각 칸의 테스트 전략, Humble Object 패턴을 설명해 보세요.

    <details markdown="1"><summary>답 확인</summary>

    축은 복잡도/도메인 중요도와 협력 객체 수입니다. 복잡·협력 적음(도메인 모델, 알고리즘) → 단위 테스트, 단순·협력 많음(컨트롤러) → 통합 테스트로 소수, 단순·협력 적음(사소한 코드) → 테스트 안 함, 복잡·협력 많음(과복잡 코드) → 분리해야 함. Humble Object는 로직을 별도 클래스/함수로 빼고 원래 코드에는 둘을 잇는 얇은 껍데기만 남기는 패턴이며, 헥사고날·MVC·DDD Aggregate도 같은 원리입니다. → 코어 4 (4.1)

    </details>

14. 업무 도중 DB 조회가 더 필요할 때의 세 가지 타협과 원서의 권장은?

    <details markdown="1"><summary>답 확인</summary>

    (1) 미리 다 읽어 오기(성능 손해), (2) 도메인에 의존성 주입(테스트성 손해), (3) 판단을 더 작은 단계로 쪼개 서비스가 단계별로 처리(서비스가 복잡해짐)입니다. 도메인 테스트 용이성·서비스 단순함·성능 중 둘만 잡을 수 있습니다. 원서는 (3)을 택하고, 서비스 복잡도를 CanExecute/Execute 패턴과 도메인 이벤트로 줄이라고 권합니다. → 코어 4 (4.1)

    </details>

15. 통합 테스트는 무엇을 얼마나 검증하나요? 그리고 NestJS 개발자가 주의할 "인터페이스 남용"이란?

    <details markdown="1"><summary>답 확인</summary>

    단위 테스트에서 엣지 케이스를 최대한 검증하고, 통합 테스트는 시나리오당 가장 긴 성공 경로 하나 + 단위로 못 잡는 엣지 케이스만 검증합니다(피라미드). 잘못된 사용이 첫 실행에 바로 예외로 터지면(Fail Fast) 통합 테스트로 굳이 검증하지 않습니다. 구현이 하나뿐인 인터페이스는 진짜 추상화가 아니므로, 인터페이스는 목이 필요한 비관리형 의존성(메일, 메시지 큐, 결제)에만 두고 관리형(내 DB/ORM)은 구체 클래스로 주입합니다. → 코어 5 (5.2)

    </details>

16. 목 사용 모범 사례 중 "가장 바깥 경계의 마지막 타입", "내가 소유한 타입만", "기대값은 리터럴로"의 의미는?

    </details>

17. 마이그레이션 기반 배포가 필요한 이유와, 테스트에서 Arrange·Act·Assert마다 별도 컨텍스트를 쓰는 이유는?

    <details markdown="1"><summary>답 확인</summary>

    </details>

18. 테스트 데이터 정리 방법 4가지 중 최선은 무엇이고, 인메모리 DB를 쓰지 말라는 이유는?

20. private 메서드를 테스트하고 싶을 때, 구체 클래스의 일부만 `spyOn`으로 바꾸고 싶을 때 각각 무엇의 신호이고 어떻게 고치나요?

    </details>

### 3. 기억 고리

- **C++ 유추:** gMock `EXPECT_CALL` → Jest 목. ⚠️ C++에서는 목을 만들려고 가상 인터페이스를 습관처럼 만들고 모든 호출에 `EXPECT_CALL`을 걸기 쉽지만, 이 책은 인터페이스·목을 비관리형 의존성에만 두고 조회(스텁) 호출은 검증하지 않는다.
- **C++ 유추:** 클라이언트-서버 패킷 포맷(하위 호환 필수) vs 서버 내부 클래스 호출(자유롭게 변경) → 시스템 간 통신(목으로 검증) vs 시스템 내부 통신(검증하지 않음). ⚠️ 같은 프로세스 밖이라도 내 앱 전용 DB는 "패킷 포맷"이 아니라 내부 구현에 가깝다(관리형 → 실제 DB 사용).
- **C++ 유추:** 틱 함수에 시간 delta를 넘겨 리플레이를 결정적으로 만들기 → 시간은 값으로 전달. ⚠️ JS `Date`는 가변 객체이므로 넘긴 값을 도메인이 수정하지 않게 주의한다(보충).
- **비유:** 리팩터링 내성이 없는 테스트 = 오작동이 잦은 화재경보기. 자주 울리면 모두가 무시해 진짜 불(버그)이 나도 놓친다. ⚠️ 비유가 깨지는 지점: 경보기는 감도만 낮추면 되지만, 테스트의 오탐은 감도 문제가 아니라 "구현(HOW)에 결합"이라는 구조 문제라서 검증 대상을 결과(WHAT)로 바꿔야 고쳐진다.
- **비유:** 스텁/목 = 들어오는 택배(받아 쓰기만 하고 확인하지 않음) / 내보내는 등기우편(보냈는지 증빙을 확인). ⚠️ 비유가 깨지는 지점: 사내 부서끼리 주고받는 메모(시스템 내부 통신)는 "나가는" 호출이어도 구현 세부 사항이라 목으로 검증하지 않는다. 증빙이 필요한 것은 회사 밖으로 나가는 우편(비관리형 의존성)뿐이다.
- **묶음(3의 법칙):** 목의 자리 3원칙 = ① 비관리형 의존성에만 ② 가장 바깥 경계의 마지막 타입에서 ③ 통합 테스트에서만. 기준은 "외부에 보이는 부수 효과인가".
- **묶음(3의 법칙):** 테스트 스타일 3종(출력 > 상태 > 통신) / 의존성 3종(공유·프로세스 외부·값 객체) / 시간 처리 3종(전역 < 주입 < 값).
- **대칭·순서:** 스텁 ↔ 목 = 쿼리 ↔ 커맨드 = 들어오는 ↔ 나가는 / 관리형 ↔ 비관리형 = 실제 DB ↔ 목 / 서비스 흐름: 읽기 → 판단(도메인) → 쓰기 / 통합 테스트 흐름: 시작 시 정리 → Arrange → Act → Assert(각각 별도 컨텍스트).
