# Part 8. 멀티테넌트 SaaS 아키텍처 (출처: Building Multi-Tenant SaaS Architectures, Tod Golding)
> 이 부는 이 책 전체의 중심이다. 앞부분에서 배운 Node.js, NestJS, DB, 인증 지식이 "한 서비스를 여러 고객이 함께 쓴다"는 조건에서 어떻게 달라지는지를 다룬다.
> 원서는 AWS 예제가 많지만, 여기서는 **개념 위주**로 정리하고 예시는 TypeScript/NestJS로 새로 썼다. (`보충` 표시가 있는 예시는 원서의 개념을 NestJS/PostgreSQL 환경에 옮긴 것이다.)

### 1. SaaS란 무엇인가 — 기술 이전에 "운영 방식"
#### 1.1 설치형에서 통합형으로
- **설치형(Installed software)**: 고객마다 별도 환경, 별도 버전, 별도 커스터마이징. 고객이 늘수록 지원팀·인프라·버전이 같이 늘어난다.
- 문제점
  - 새 기능 배포가 느리다 (고객마다 업그레이드 시점이 다름)
  - 고객 1명 추가 = 운영 비용도 거의 1명분 추가 → 마진이 깎임
  - 시장 변화에 반응이 느림
- **SaaS**: 하나의 서비스를 모든 고객이 함께 쓰고, 한 번 배포하면 **모두 같은 버전**이 된다.

> **왜 중요한가?** "모든 테넌트가 같은 버전을 쓰는가?"가 SaaS인지 아닌지 가르는 가장 실용적인 판별 기준이다. 고객 요청으로 코드를 갈라(fork)주기 시작하면 SaaS의 장점(속도, 효율)이 사라진다.

> 📖 원문: 1장 Where We Started, The Move to a Unified Model

#### 1.2 SaaS는 비즈니스 모델이다
책이 말하는 SaaS 비즈니스의 핵심 목표는 다음 5가지다. (세 번째 열 "시사점"은 (보충) 저자 해석이다.)

| 축 | 의미 | 백엔드 개발자에게 주는 시사점 (보충) |
|---|---|---|
| 민첩성(Agility) | 빨리 배포하고 시장 변화·가격 정책 변경에 빨리 반응한다 | 배포 자동화, 기능 플래그, 무중단 배포 |
| 운영 효율(Operational efficiency) | 고객이 1,000명 늘어도 특별한 인력·팀을 늘리지 않는다 | 온보딩·모니터링·과금 자동화 |
| 혁신(Innovation) | 민첩성과 효율 덕분에 새 시장·새 요금제를 실험할 여유가 생긴다 | 티어/요금제 변경이 쉬운 구조 |
| 마찰 없는 온보딩(Frictionless onboarding) | 가입 → 사용까지 시간(Time to value)을 줄인다 | 온보딩 파이프라인 |
| 성장(Growth) | 고객 확보·온보딩·운영 전체를 성장에 맞춰 효율화한다 | 자동화된 확장 가능한 구조 |
- 책의 SaaS 정의(재구성): "고객에게 낮은 마찰로, **서비스 중심**으로 소프트웨어를 제공하는 비즈니스이자 전달 방식. 민첩성과 운영 효율이 성장의 기둥."
- **제품(Product)이 아닌 서비스(Service)**: 기능뿐 아니라 가입 속도, 장애 빈도, 새 기능 출시 속도까지 "서비스 품질"이다. 식당의 음식(제품)과 응대(서비스) 비유가 대표적이다.
- "다수의 필요가 소수의 필요보다 우선한다." → 한 고객만을 위한 일회성 코드는 원칙적으로 피한다.

> 📖 원문: 1장 At Its Core, SaaS Is a Business Model; Building a Service—Not a Product; Defining SaaS

#### 1.3 멀티테넌시의 재정의: "공유"가 아니라 "통합 운영"
- 전통적 정의: 여러 고객이 **인프라를 공유**하면 멀티테넌트.
- 책의 정의: **온보딩·배포·관리·운영을 하나의 통합된 경험으로 처리**하면 멀티테넌트. 인프라를 공유하는지는 상관없다.
- 예를 들어 고객마다 서버와 DB를 따로 줘도, 같은 버전을 같은 도구로 한꺼번에 배포·관리한다면 멀티테넌트다.
- 그래서 책은 "single-tenant"라는 말을 쓰지 않고 **사일로(Silo)/풀(Pool)** 이라는 용어를 쓴다 (3장에서 자세히).
- **테넌트(Tenant)**: 서비스를 쓰는 고객 단위. 아파트 건물(공유 인프라)에 입주한 세입자에 비유한다(2장). B2B에서는 "회사", B2C에서는 "사용자 개인"이 테넌트가 되기도 한다.
- **MSP(Managed Service Provider)는 SaaS가 아니다**: 고객마다 다른 버전을 돌리게 두고 운영만 한곳에서 대행하면, 고객별 예외 대응이 남기 때문에 SaaS와 구분된다(1장).
- **서비스 표면만 노출**: 테넌트에게는 서비스의 겉면만 보여야 한다. 테넌트가 쓰는 DB 같은 자원을 직접 들여다보게 하면 고객별 예외가 생기기 쉽다(1장 "Where Are the Boundaries of SaaS?").

> **왜 중요한가?** "테넌트 = 회사(조직)"라는 모델링이 이후 모든 테이블/토큰/권한 설계의 출발점이다. 책도 앱을 먼저 만들고 테넌시를 나중에 덧붙이는(bolt-on) 방식은 대개 큰 리팩터링과 타협으로 이어진다고 경고한다(4장). 그래서 **첫날부터 테넌트를 1급 개념**으로 넣는다.

> 📖 원문: 1장 Redefining Multi-Tenancy, The Managed Service Provider Model; 2장 Adding Tenancy to Your Architecture; 4장 도입부/Conclusion

### 2. 두 개의 반쪽: 컨트롤 플레인 vs 애플리케이션 플레인
#### 2.1 개념
모든 SaaS 아키텍처는 두 부분으로 나눌 수 있다.

```
┌───────────────────────── 컨트롤 플레인 (Control Plane) ─────────────────────────┐
│  온보딩 · 아이덴티티 · 테넌트 관리 · 과금/미터링 · 메트릭 · 관리자 콘솔          │
│  "SaaS 사업을 굴리는 공통 서비스" — 테넌트 자체를 대상으로 하지 않음               │
└──────────────────────────────────────┬───────────────────────────────────────────┘
                                       │ 프로비저닝 / 설정 / 메트릭 수집
┌──────────────────────────────────────▼───────────────────────────────────────────┐
│                       애플리케이션 플레인 (Application Plane)                     │
│  주문, 상품, 결제 등 "실제 제품 기능" — 테넌트 컨텍스트가 모든 곳에 스며듦         │
└───────────────────────────────────────────────────────────────────────────────────┘
```

| 구분 | 컨트롤 플레인 | 애플리케이션 플레인 |
|---|---|---|
| 역할 | 테넌트를 만들고 관리·운영 | 테넌트가 쓰는 제품 기능 제공 |
| 멀티테넌트 여부 | 그 자체는 멀티테넌트 서비스가 **아님** (테넌트 전체를 위한 서비스) | 테넌트 컨텍스트를 인지해야 함 |
| 사용자 | SaaS 제공사의 시스템 관리자 | 테넌트의 관리자/일반 사용자 |
| 배포 주기 | 독자적 버전 관리 | 기능·티어 요구에 따라 변경 |
- 컨트롤 플레인을 **먼저** 만들어야 한다. 그러면 개발이 처음부터 "테넌트가 있다"는 전제로 진행된다 (강제 함수 역할).
- 앱 플레인에는 정해진 하나의 청사진이 없다. 도메인, 규제, 레거시에 따라 자유롭게 구성한다.
- 어떤 앱 플레인(공유든 전용이든)이라도 **하나의 컨트롤 플레인이 통합 관리**하면 멀티테넌트다.

> **왜 중요한가?** 신입 개발자가 가장 많이 하는 실수는 "일단 앱부터 만들고 나중에 로그인/과금/테넌트를 붙이자"이다. 컨트롤 플레인 개념이 있으면 무엇을 별도 서비스(모듈)로 분리할지 판단하기 쉽다.

> 🔗 NestJS 연결: 하나의 모노레포에서 `ControlPlaneModule`(테넌트, 온보딩, 과금)과 `AppPlaneModule`(도메인 기능)을 분리해 시작하면 좋다. 규모가 커지면 별도 서비스로 쪼갤 수 있다.

> 📖 원문: 2장 The Two Halves of Every SaaS Architecture

#### 2.2 컨트롤 플레인의 5가지 구성요소
1. **온보딩(Onboarding)** – 새 테넌트를 만들고 필요한 설정·자원을 준비하는 흐름 전체를 오케스트레이션한다. 테넌트 ID 생성, 사용자·인증 구성, 앱 자원 프로비저닝이 여기에 포함된다.
2. **아이덴티티(Identity)** – 사용자를 테넌트에 **묶는** 것(SaaS Identity). 인증만이 아니라 "이 사용자는 어느 테넌트 소속인가"가 핵심이다.
3. **메트릭(Metrics)** – 공유 자원에서 "누가 얼마나 쓰는지"를 파악하려면 테넌트 단위의 계측이 필요하다.
4. **과금(Billing)** – 온보딩 때 과금 시스템에 테넌트(고객)를 등록하고, 사용량 기반이면 사용 이벤트를 수집해 전달한다.
5. **테넌트 관리(Tenant Management)** – 테넌트 ID, 티어, 상태(활성/비활성), 설정을 저장하는 **단일 진실 원천(Single source of truth)**.

> 📖 원문: 2장 Inside the Control Plane

#### 2.3 애플리케이션 플레인에서 테넌시가 스며드는 5곳

| 지점 | 질문 |
|---|---|
| 테넌트 컨텍스트(Tenant context) | 이 요청은 어느 테넌트(어느 티어)의 것인가? |
| 테넌트 격리(Tenant isolation) | 이 코드가 다른 테넌트의 자원을 못 건드리게 막았는가? |
| 데이터 파티셔닝(Data partitioning) | 테넌트 데이터를 어떻게 나눠 저장하는가? |
| 테넌트 라우팅(Tenant routing) | 이 요청을 어느 전용/공유 서비스로 보낼까? |
| 배포(Deployment) | 전용 자원이 있으면 어디에 어떻게 새 버전을 배포할까? |

이 다섯 가지가 이 부의 나머지 내용이다.

> 📖 원문: 2장 Inside the Application Plane

#### 2.4 회색 지대: 티어링, 그리고 3종류의 사용자
- **티어링(Tiering)**: Basic/Advanced/Premium처럼 요금제별로 다른 경험을 제공하는 것. 가격표가 아니라 **아키텍처에 영향**을 준다(스로틀링, 라우팅, 기능 등). 티어는 컨트롤 플레인에서 관리하고, 토큰(테넌트 컨텍스트)에 실어 앱 플레인에서 사용하는 것이 자연스럽다.
- 사용자 역할은 3종류로 구분한다.

| 역할 | 소속 | 하는 일 |
|---|---|---|
| 테넌트 사용자(Tenant user) | 테넌트 | 일반 기능 사용 |
| 테넌트 관리자(Tenant admin) | 테넌트 | 온보딩 때 만들어지는 첫 사용자. 같은 테넌트의 사용자 추가 등 앱 관리 |
| 시스템 관리자(System admin) | SaaS 제공사 | 컨트롤 플레인 관리 콘솔로 테넌트 운영 |
- 시스템 관리자는 컨트롤 플레인의 관리 콘솔에 접근하므로 별도의 인증 경험이 필요하고, 그 계정을 만들고 관리하는 절차도 반복 가능하고 안전하게 설계해야 한다. (많은 팀이 소홀히 하는 부분) 4장에서는 시스템 관리자 아이덴티티가 테넌트 아이덴티티와 별개로 생성된다고 설명한다.
- 사용자 관리는 컨트롤 플레인이냐 앱 플레인이냐 논란이 있지만, 저자는 "테넌트와 사용자를 잇는 아이덴티티는 컨트롤 플레인"을 선호한다.
- <strong>테넌트 프로비저닝(Tenant Provisioning)</strong>도 회색 지대다. 온보딩은 컨트롤 플레인이 오케스트레이션하되, 실제 자원 준비를 앱 플레인 쪽에서 실행할지 컨트롤 플레인이 직접 할지 선택할 수 있다. 저자는 프로비저닝을 대상 자원에 가까운 쪽에 두는 편을 선호하며, 어느 쪽이든 온보딩의 독립된 한 단계로 분리해 두라고 한다.
- 두 플레인은 반드시 별도 네트워크·인프라로 나눠야 하는 것은 아니다. 다만 논리적으로는 항상 나눠야 하고, 플레인별로 기술 스택도 다르게 골라도 된다. ("Avoiding the Absolutes": 이 모델을 절대 규칙으로 보지 말 것.)

> 📖 원문: 2장 The Gray Area (Tiering; Tenant, Tenant Admin, and System Admin Users; Tenant Provisioning; Integrating the Control and Application Planes; Avoiding the Absolutes)

### 3. 배포 모델: 사일로(Silo)와 풀(Pool)
#### 3.1 두 개의 핵심 용어
- **사일로(Silo)**: 자원이 **한 테넌트 전용**
- **풀(Pool)**: 자원을 **여러 테넌트가 공유**
- 컴퓨트(서버), DB, 큐, 스토리지 등 **자원 하나하나 단위**로 정할 수 있다. 서비스마다 다르게 조합해도 된다.

```
예) 주문 서비스: 컴퓨트=사일로, 스토리지=사일로, 큐=사일로
    상품 서비스: 컴퓨트=풀,   스토리지=풀
    청구 서비스: 컴퓨트=풀,   스토리지=사일로
```

> 📖 원문: 3장 Introducing the Silo and Pool Models

#### 3.2 배포 모델 종류

| 모델 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **Full Stack Silo** | 테넌트마다 전체 스택(서버·DB·큐…)을 따로 | 격리·규제 대응 쉬움, 장애 영향 범위(blast radius) 작음, 비용 귀속(테넌트별 비용 계산) 쉬움 | 비용 높음, 컨트롤 플레인·배포 복잡, 테넌트 수백 개 이상이면 관리 한계 |
| **Full Stack Pool** | 모든 자원을 모든 테넌트가 공유 | 규모의 경제, 단순한 배포·운영, 비용 효율 | 격리 구현 난이도 높음, 노이지 네이버(noisy neighbor), 장애 시 전체 영향, 비용 귀속 어려움 |
| **Hybrid (Silo+Pool)** | 대부분 풀, 일부 프리미엄 고객만 풀 스택 사일로 | 큰 고객·규제 고객 대응 | 사일로 테넌트 비율이 커지면 SaaS 장점 훼손 → 수를 제한해야 함 |
| **Mixed Mode** | 서비스·자원 단위로 사일로/풀을 골라 섞음 | 가장 유연, 필요한 곳만 사일로 | 온보딩·배포·라우팅이 더 복잡 |
| **Pod** | 테넌트 그룹을 하나의 배포 단위(pod)로 묶음 (예: 리전별, 규모 한계 회피) | 확장 한계·지역 요건·영향 범위 제한 | 컨트롤 플레인이 pod를 인지해야 함, 유휴 자원 중복 |

> **쿠버네티스의 pod와는 다른 개념**이다. 여기서는 "테넌트 묶음 배포 단위"를 뜻한다.

#### 3.3 꼭 기억할 원칙
1. **풀 모델은 컨텍스트 해석이 매 요청마다 필요**하다. 사일로는 배포할 때 이미 테넌트가 정해져 있어(환경변수로 충분) 단순하다. 풀에서는 "모든 요청이 테넌트 컨텍스트를 가지고 들어온다".
2. **사일로에서도 개별 커스터마이징은 금지**다. 사일로는 규제/티어/성능 때문에 쓰는 것이지, 특정 고객에게 코드를 따로 주려는 게 아니다. 모든 사일로는 같은 버전, 같은 설정, 같은 자동화로 관리한다.
3. 저자의 조언: **사일로로 시작하더라도 "풀로 만들고, 사일로는 테넌트가 하나뿐인 풀 인스턴스"라고 생각하고 만들어라.** 그러면 나중에 풀로 옮기거나 티어를 바꾸기 쉽다.
4. 배포 모델은 **진화**한다. 처음에 완벽히 정하려 하지 말고, 데이터(메트릭)를 보고 사일로↔풀을 바꿀 수 있게 열어 둔다.
5. 기본은 풀, 사일로는 "이유를 대야만" 허용한다 (8장의 "Defaulting to a Pooled Model").

> **왜 중요한가?** (보충: 저자 해석) 초기 SaaS의 현실적 출발점은 대개 "풀(단일 DB, tenant_id) + 필요시 프리미엄만 사일로"이다. 이 선택이 스키마, 마이그레이션, 관측, 과금 전부에 영향을 준다. 원서는 "정답이 하나 없고 진화한다"는 점을 강조한다.

> 📖 원문: 3장 Full Stack Silo/Pool, Hybrid, Mixed Mode, Pod Deployment Model, Picking a Deployment Model

### 4. 온보딩(Onboarding): 테넌트를 만드는 자동화 파이프라인
#### 4.1 왜 온보딩이 중요한가
- 온보딩은 "가입 폼 처리"가 아니라 **사일로/풀, 인증, 라우팅, 티어 전략이 실제로 구현되는 자리**다.
- 첫인상이며, 실패는 곧 고객 이탈이다. 가입에서 실제 가치를 얻기까지의 시간 = **Time to value**.
- 셀프서비스(가입 페이지) 방식이든 내부 운영자가 처리하든, **완전 자동화·반복 가능**해야 한다. 수작업이 끼면 확장이 안 된다.

#### 4.2 온보딩 흐름의 기본 순서
```
[셀프 가입 or 관리자 콘솔]
        │
        ▼
  1) Onboarding Service (오케스트레이터) 호출
        │
        ├─ 2) Tenant Management: 테넌트 생성 (ID 발급, status=inactive)
        ├─ 3) Provisioning: 테넌트 자원 준비 (티어에 따라 다름)
        ├─ 4) Billing: 과금 시스템에 고객/플랜 등록
        ├─ 5) Identity: 테넌트 관리자 사용자 생성 (+ 커스텀 claim 채움)
        └─ 6) 모두 성공 → Tenant Management에 status=active
```

핵심 포인트:
- **오케스트레이션 서비스 1개**가 전 단계를 소유한다. 일부 단계는 비동기·외부 시스템 의존이기 때문이다.
- 테넌트 ID는 **온보딩 맨 앞**에서 만든다. 처음에는 `active=false`로 두고, 모든 단계가 끝나야 `true`로 바꾼다.
- 사용자 초대 메일·임시 비밀번호·비밀번호 재설정은 **인증 제공자(IdP)의 기능에 위임**한다. 직접 만들지 않는다.

- **온보딩 전에 기본 환경(baseline environment)이 먼저 있어야 한다**: 네트워크, 컨트롤 플레인 서비스, 풀 자원, 시스템 관리자 아이덴티티와 관리 콘솔을 온보딩 이전에 한 번 자동화 스크립트로 준비한다. 내부 운영자가 관리 콘솔에서 온보딩을 실행하는 경로도 이 콘솔에 둘 수 있다.
- 온보딩은 "가입 폼"이 아니라 서비스의 일부로 다뤄야 하며, 원서는 처음부터 온보딩·아이덴티티·컨트롤 플레인부터 만들라고 권한다(4장).

#### 4.3 온보딩 상태 추적
각 단계를 상태로 기록해 관리 콘솔에서 볼 수 있게 한다. 원서의 예시 상태: `TENANT_CREATED` → `TENANT_PROVISIONED` → `BILLING_INITIALIZED` → `USER_CREATED` → `TENANT_ACTIVATED`.

- "어느 단계에서 멈췄는가"를 알면 재시도·장애 분석이 쉬워진다.

#### 4.4 티어 기반 온보딩
- 프로비저닝 서비스는 **티어에 따라 다르게 동작**한다.
  - Basic(풀): 공유 자원은 이미 있음 → 설정·라우팅 정도만 추가 (가벼움)
  - Premium(사일로): 전용 스택을 새로 생성 (무거움)
- Mixed Mode에서는 자원별로 "사일로면 새로 만들고, 풀이면 기존 것에 등록"을 판단해야 한다.
- **풀 자원은 처음 환경을 만들 때 미리 준비(pre-provision)** 하는 것이 자연스럽다 (첫 테넌트에게 몰아서 지연을 주지 않도록).
- 티어별 차이는 허용하되, **테넌트 개별 맞춤은 안 된다.**

#### 4.5 생성한 자원 추적
- 테넌트 전용 자원(사일로)을 만들면, 나중에 배포·운영 때 찾을 수 있도록 **테넌트별 자원 위치를 기록**해야 한다. (예: 테넌트→전용 DB 주소/서비스 URL 테이블)
- 표준 해법은 없고, 보통 테넌트 관리 서비스의 테이블이나 DevOps 도구에 저장한다.

#### 4.6 실패 처리와 테스트
- 외부 시스템(결제/과금 서비스) 장애가 온보딩 전체를 막으면 안 된다 → **비동기 큐 + 재시도**로 결합도를 낮춘다.
- 온보딩은 부하 테스트, 실패 복구 테스트, 소요 시간 측정을 **티어별로** 돌려 봐야 한다. 고객이 대신 테스트해 주지 않게 한다.

```ts
// 보충: NestJS로 표현한 온보딩 오케스트레이션 골격
@Injectable()
export class OnboardingService {
  constructor(
    private tenants: TenantService,
    private provisioning: ProvisioningService,
    private billing: BillingQueue,       // 큐로 비동기 처리
    private identity: IdentityService,
  ) {}

  async onboard(dto: OnboardDto) {
    const tenant = await this.tenants.create({ ...dto, active: false }); // 1) ID 발급
    try {
      await this.provisioning.provision(tenant.id, tenant.tier);          // 2) 티어별 자원
      await this.billing.enqueueCreateCustomer(tenant.id, tenant.tier);   // 3) 비동기
      await this.identity.createTenantAdmin(tenant.id, dto.adminEmail);   // 4) 커스텀 claim 포함
      await this.tenants.activate(tenant.id);                             // 5) 마지막에 활성화
    } catch (e) {
      await this.tenants.markOnboardingFailed(tenant.id, e);             // 상태 기록 + 재시도 대상
      throw e;
    }
  }
}
```

> **왜 중요한가?** 온보딩이 수작업이거나 불안정하면 "고객 100명 추가"가 곧 "인력 추가"가 된다. SaaS가 확장 가능한지의 첫 시험대다.

> 🔗 NestJS 연결: 다단계 비동기 처리는 BullMQ(큐) + 상태 머신으로 구현한다. 각 단계는 멱등(idempotent)하게 만들어 재시도해도 안전해야 한다.

### 5. SaaS 아이덴티티와 테넌트 컨텍스트: 토큰에 테넌트를 싣는다
#### 5.1 SaaS Identity = 사용자 + 테넌트
- 멀티테넌트에서는 "로그인 성공"만으로 부족하다. **모든 로그인 사용자는 반드시 어떤 테넌트에 속해야** 한다.
- 사용자 정보(이름, 이메일…)와 테넌트 정보(tenantId, 티어…)를 합친 것을 **SaaS Identity**라 부르고, 이것이 곧 **테넌트 컨텍스트(Tenant context)** 다.
- B2B: 회사가 테넌트, 사용자는 그 회사 소속. B2C: 사용자 자체가 테넌트일 수 있어 매핑이 불필요.
- 이 정보는 인증 직후 **가장 앞단에서** 확정하고, 이후 모든 곳에 전달한다.

#### 5.2 JWT 커스텀 클레임(Custom Claims)
OIDC/OAuth가 발급하는 JWT에 우리가 정한 필드를 추가할 수 있다.

```json
// 보충: 원서는 tenant ID, role, tier를 커스텀 claim으로 넣는다고만 설명한다. 아래 키 이름은 예시다.
{
  "sub": "user-123",
  "email": "kim@acme.com",
  "custom:tenantId": "b5a9…-guid",
  "custom:tier": "premium",
  "custom:role": "tenant_admin"
}
```

- 사용 흐름: 로그인 → IdP가 테넌트 정보가 든 토큰 발급 → 클라이언트가 `Authorization: Bearer <JWT>`로 전송 → 서비스가 토큰에서 테넌트 컨텍스트 추출 → 서비스 간 호출 시 **같은 토큰을 그대로 전달**.
- 이 토큰 하나가 로깅, 메트릭, 과금, 격리, 데이터 접근, 티어링, 스로틀링, 라우팅에 전부 쓰인다.
- 커스텀 클레임은 두 단계로 채운다: (1) 온보딩 이전에 IdP에 "이런 속성을 쓰겠다"고 정의, (2) 사용자를 만들 때마다 tenantId/role/tier 값을 채움. **이후 추가되는 사용자에게도 반드시 채워야 한다.**

#### 5.3 커스텀 클레임은 "절제해서" 쓴다
- 넣어도 되는 것: **자주 바뀌지 않는, 테넌트 컨텍스트를 이루는 값** (tenantId, tier, 역할 정도)
- 넣지 말 것: 기능이 추가될 때마다 바뀌는 세밀한 권한(앱 접근 제어). 토큰이 비대해지고 자주 재발급해야 한다.
- 판단 기준: "앱 기능이 변하면 이 값도 바뀌는가?" → 그렇다면 앱의 RBAC/권한 시스템에서 관리.

#### 5.4 중앙 조회 서비스에 의존하지 마라
- 안티패턴: 토큰에 테넌트 정보가 없어서 요청마다 "Tenant Mapping Service"를 호출해 tenantId를 찾는 구조.
- 모든 서비스, 모든 요청이 한 곳을 거치므로 **병목이자 단일 장애점**이 된다. 게다가 그 서비스는 비즈니스 가치가 없다.
- 원칙: **서비스가 테넌트 컨텍스트를 얻기 위해 다른 서비스를 호출할 필요가 없어야 한다.** 필요한 정보는 토큰에 넣는다.

#### 5.5 페더레이션(Federated) 로그인
- 큰 고객이 자사 SSO(사내 IdP)로 로그인하게 해 달라고 요구할 수 있다.
- 문제: 외부 IdP가 발급한 토큰에는 우리의 tenantId claim이 **없다**.
- 해법: 우리가 중간에서 토큰을 **보강(enrichment)** 해서 tenantId, tier를 붙인다(IdP가 제공하는 훅이나 연합 기능을 쓰거나, 안 되면 직접 구현). 인증 흐름 중간에 끼어드는 만큼 보안·확장성·단일 장애점 부담이 생기므로 신중히 결정한다.
- 내부 IdP 사용자와 외부 IdP 사용자를 **나란히** 지원해야 하는 경우가 흔하다.

- **IdP 구조와 다중 소속**: IdP의 사용자 묶음 단위(풀/그룹/조직)를 테넌트마다 따로 둘지 하나로 합칠지는 확장성과 정책 유연성(예: 티어별 MFA)의 트레이드오프다. 같은 이메일이 여러 테넌트에 속하는 경우는 표준 해법이 없고, 서브도메인으로 테넌트를 먼저 특정한 뒤 인증하는 방식이 깔끔하다(테넌트 선택 화면은 소속 정보 노출 위험).

#### 5.6 인증(Authentication) ≠ 테넌트 격리(Isolation)
> **가장 흔한 착각:** "로그인한 사용자의 토큰에 tenantId가 있으니 다른 테넌트는 못 본다."

- 인증은 격리의 **출발점**일 뿐이다(컨텍스트를 준다).
- 그 컨텍스트를 받은 서비스 코드에 버그가 있으면(예: `WHERE tenant_id`를 빠뜨림) 인증된 사용자도 다른 테넌트 데이터를 볼 수 있다.
- 격리는 인증과 **별개의 방어 계층**으로 구현해야 한다 (원서 9장, 이 문서 10절에서 다룬다).

```ts
// 보충: JWT에서 테넌트 컨텍스트를 꺼내는 Guard (NestJS)
@Injectable()
export class TenantAuthGuard implements CanActivate {
  constructor(private jwt: JwtService, private tenants: TenantCache) {}

  async canActivate(ctx: ExecutionContext): Promise<boolean> {
    const req = ctx.switchToHttp().getRequest();
    const token = req.headers.authorization?.replace('Bearer ', '');
    if (!token) throw new UnauthorizedException();

    const claims = await this.jwt.verifyAsync(token);        // 서명 검증 필수
    if (!claims.tenantId) throw new UnauthorizedException(); // 테넌트 없는 토큰은 거부

    const active = await this.tenants.isActive(claims.tenantId); // 비활성 테넌트 차단
    if (!active) throw new ForbiddenException('Tenant is inactive');

    req.tenant = { id: claims.tenantId, tier: claims.tier, role: claims.role };
    return true;
  }
}
```

> **왜 중요한가?** 토큰 기반 테넌트 컨텍스트는 이 부의 모든 기능(격리, 로깅, 스로틀링, 라우팅, 과금)의 입력값이다. (보충: 원서 외 일반 보안 상식) 서명을 검증하지 않거나 클라이언트가 보낸 tenantId를 믿으면 다른 방어가 무의미해진다. **tenantId는 요청 바디/헤더의 사용자 입력을 신뢰하지 말고, 검증된 토큰에서만 얻는다.**

> 🔗 NestJS 연결: `@nestjs/passport` + JWT Strategy 또는 커스텀 Guard로 구현. 커스텀 데코레이터 `@CurrentTenant()`로 컨트롤러에서 안전하게 꺼내 쓴다.

> 📖 원문: 4장 Creating a SaaS Identity (Attaching a Tenant Identity, Populating Custom Claims, Using Custom Claims Judiciously, No Centralized Services for Resolving Tenant Context, Federated SaaS Identity, Tenant Grouping/Mapping Constructs, Sharing User IDs Across Tenants, Tenant Authentication Is Not Tenant Isolation)

### 6. 테넌트 관리(Tenant Management)와 수명주기
#### 6.1 테넌트 관리 서비스의 역할
컨트롤 플레인의 작고 단순한 서비스지만 **모든 것의 중심**이다.

- 저장하는 것: 테넌트 ID, 이름, 티어, 활성 상태, 온보딩 상태, 마지막 활동일, 서브도메인, ID 관련 설정(MFA·비밀번호 정책, IdP 매핑), 라우팅 설정(전용 자원 URL 등), 필요하면 테넌트별 키/시크릿
- 사용자 관리와 테넌트 관리는 구분한다. B2C처럼 테넌트=사용자여도 테넌트 속성·정책은 따로 있고, 사용자의 역할 같은 앱 설정은 테넌트 설정과 분리해 두는 편이 좋다.
- **단일 진실 원천**: 테넌트 상태는 여기서만 바꾸고, 변경이 필요한 다른 곳(인증, 과금, 라우팅)에 전파한다.
- 주의: 앱 서비스가 요청마다 이 서비스를 호출하면 병목이 된다. 그래서 핵심 속성은 JWT에 실어 두고, 이 서비스는 **관리·설정용**으로 쓴다. (원서: 자주 접근되면 다른 접근 전략을 고려. 캐시는 (보충) 일반적 대안)

- 관리 콘솔은 테넌트 목록·상태·티어 변경·내부 온보딩을 제공한다. 콘솔에서 되는 기능은 보통 이 서비스의 API로도 가능하다(콘솔만/API만/혼합 모두 가능). 콘솔은 시스템 관리자 전용 인증으로 보호한다. 원서는 이 관리 콘솔을 직접 만들 가치가 있다고 본다.

#### 6.2 테넌트 ID 생성 규칙
- **GUID/UUID 사용**: 전역 유일, 테넌트 이름 등 다른 속성에 의존하지 않음, 외부인이 ID로 테넌트를 추측하지 못함.
- ID는 **불변**이어야 한다.
- 서브도메인(`acme.myapp.com`), 회사명 같은 "친화적 이름"은 별도로 두고 내부 ID로 **매핑**한다. 이름은 바뀔 수 있지만 ID는 바뀌면 안 된다.

#### 6.3 수명주기 이벤트
**(1) 비활성화(Deactivate) / 재활성화**
- 접근만 막는다. 데이터와 자원은 그대로 둔다 (복귀 가능).
- 예: 결제 연체 → 과금 시스템 이벤트 → Billing Service → Tenant Management에 deactivate 요청 → 해당 테넌트 사용자의 인증 차단.
- 실무 결정 사항: 이미 로그인한 세션을 즉시 끊을 것인가, 만료까지 두는가? (많은 곳이 부드럽게 두는 쪽)
- 유예 기간(grace period), 안내 메일 등 정책이 필요하다.
- 상태는 **Tenant Management만** 바꾸고 나머지가 따라오게 한다.

**(2) 폐기(Decommission)**
- 비활성화 이후 일정 기간이 지나면 자원을 실제로 제거한다. 별도의 **Decommissioning 서비스**로 분리하는 것이 자연스럽다.
- 삭제할지, **아카이브**(보관)할지, 나중에 복원(rehydrate)할 여지를 남길지 정책을 정한다.
- **풀 데이터 삭제가 까다롭다**: 공유 테이블에서 해당 tenant_id 행만 골라 삭제해야 하고, 서비스마다 저장소 기술이 달라 코드가 각각 필요하다.
- 삭제 작업이 다른 테넌트 성능을 해치지 않게 **비동기·저강도**로 수행한다.
- 온보딩보다 더 복잡한 경우도 많다.

**(3) 티어 변경(Upgrade/Downgrade)**
- 풀 안에서의 변경은 쉽다: 티어 값을 바꾸면 기능 플래그와 스로틀링 정책이 자동 적용된다.
- 풀 → 사일로 이동(예: Basic→Premium 전용 스택)은 어렵다: 전용 자원 프로비저닝(온보딩 코드 재활용) + **데이터 이전** + 무중단 여부 결정. 다른 테넌트에 부하를 주지 않아야 한다.
- 다운그레이드는 그 반대 작업이다.

> **왜 중요한가?** 테넌트는 "만들고 끝"이 아니다. 연체, 해지, 재가입, 업그레이드가 반드시 발생하며, 특히 **삭제(데이터 파기, 개인정보 규정)** 와 **풀 → 사일로 이전**은 나중에 붙이기 매우 어렵다.

> 🔗 NestJS 연결: 테넌트 상태 변경은 도메인 이벤트(`@nestjs/event-emitter`)나 메시지 큐로 발행하고, 인증·과금·캐시 모듈이 구독해 동기화한다.

> 📖 원문: 5장 Tenant Management Fundamentals, Generating a Tenant Identifier, Storing Infrastructure Configuration, Managing Tenant Configuration, Managing Tenant Lifecycle (Activating and Deactivating, Decommissioning, Changing Tenant Tiers)

### 7. 테넌트 식별과 요청 라우팅 (Front Door)
#### 7.1 진입 경로에 따른 테넌트 식별
요청이 들어올 때 "어느 테넌트인가"를 어디서 알아내느냐의 문제다.

| 방식 | 예 | 특징 |
|---|---|---|
| **서브도메인** | `acme.myapp.com` | 가장 흔함. 도메인 하나로 테넌트별 진입점 제공. 온보딩 때 DNS/인증서 설정 |
| **벤더(커스텀) 도메인** | `shop.acme-store.com` | 테넌트 브랜딩/화이트라벨. 도메인 검증·등록 자동화가 큰 작업 |
| **단일 도메인** | `www.myapp.com` | B2C에서 흔함. 로그인 후 토큰의 claim으로 테넌트를 알게 됨 |
- 도메인은 **친화적 이름**일 뿐이고, 내부에서는 도메인 → 테넌트 ID로 매핑해서 쓴다 (이름이 바뀌어도 ID는 유지).
- 도메인 매핑이 쓰이는 두 곳: (1) 로그인 시 어떤 IdP/사용자 풀로 인증할지 결정 (2) 전용 자원으로의 라우팅.
- 단일 도메인에서 사용자별 IdP가 다르면: 이메일 도메인으로 테넌트 추정, 또는 사용자 ID → 테넌트 매핑 테이블 조회. 둘 다 "1 사용자 = 1 테넌트"를 가정한다.

#### 7.2 "중간 삽입(Man in the Middle)" 문제
- 표준 OAuth/OIDC 흐름은 IdP가 다 알아서 처리한다.
- 그러나 테넌트별로 다른 IdP로 보내려면 **중간에 매핑 로직**을 끼워야 하고, 이것이 새로운 병목·장애점이 된다. 이 대가를 감수할 만한지 판단해야 한다.

#### 7.3 멀티테넌트 인증 흐름 (서브도메인 예)
1. 사용자가 `tenant1.myapp.com` 접속
2. 앱이 미인증 상태임을 감지 → 로그인 화면
3. 서브도메인으로 Tenant Management에서 해당 테넌트의 IdP 설정 조회
4. 그 IdP로 표준 OAuth 코드 흐름 진행
5. IdP가 tenantId claim이 든 JWT 발급
6. 이 JWT를 Bearer 토큰으로 서비스에 전달

"OIDC/OAuth 표준은 지키되, **표준 흐름 앞에 테넌트 매핑 단계를 얹는 것**"이 멀티테넌트 인증의 본질이다.

#### 7.4 라우팅(Routing)
- 모든 자원이 풀이면 라우팅은 단순하다.
- 사일로와 풀이 섞이면, 요청마다 **테넌트 컨텍스트로 목적지를 결정**해야 한다.
  - 최상단 라우터: 테넌트 → 어느 서비스 인스턴스/그룹으로 보낼지
  - 서비스 간 라우터: 풀 서비스가 전용(사일로) 서비스를 호출할 때도 테넌트 기준으로 분기
- 라우팅 정보(테넌트 → 목적지)는 온보딩 때 등록되고, 매 요청 조회하면 지연이 생기므로 **캐싱**한다.
- 사일로가 많아질수록 라우팅 구성이 커져 확장 한계가 온다 → 사일로 테넌트 수를 제한. (원서 예: 서버리스에서 테넌트별 API Gateway를 두면 대규모에서 확장이 어렵다.)
- 원서는 매핑 조회를 서비스 코드에 넣기보다, 게이트웨이·프록시·서비스 메시(예: 쿠버네티스의 Istio) 같은 **기존 라우팅 인프라에 위임**하는 편이 더 깔끔하다고 본다.
- 단일 도메인에서 클라이언트가 직접 테넌트 URL을 조회해 붙이게 하는 방식은 클라이언트에 부담을 넘기므로, 매핑 계층의 캐싱이 더 일반적이다.

> 🔗 NestJS 연결: 서브도메인 파싱은 Middleware에서(`req.hostname`), 이후 토큰 검증은 Guard에서 수행. 전용 서비스 호출은 `HttpService`/마이크로서비스 클라이언트 앞에 테넌트→URL 조회를 캡슐화한다.

> 📖 원문: 6장 Entering the Front Door (tenant domain / single domain), The Man in the Middle Challenge, The Multi-Tenant Authentication Flow, Federated Authentication, Routing Authenticated Tenants (Serverless/Container Tenant Routing); 2장 Tenant Routing

### 8. 멀티테넌트 서비스 만들기
#### 8.1 서비스 설계 시 테넌시가 바꾸는 것
- 설치형에서는 서비스가 **한 고객 부하**만 고려하면 됐다. 풀에서는 **크기가 제각각인 수많은 테넌트가 동시에** 같은 서비스를 쓴다.
- 새 테넌트는 언제든 들어오고, 부하 패턴은 예측 불가하며, 티어별 SLA도 다르다.
- 따라서 서비스 분해 시 기존 원칙(단일 책임 등)에 **다음 관점을 추가**한다.

**(a) 노이지 네이버(Noisy Neighbor)**
- 한 테넌트의 과도한 사용이 다른 테넌트의 성능을 떨어뜨리는 현상.
- 예: 카탈로그 서비스에서 이미지 썸네일 생성 API만 무거워 병목 → 서비스 전체를 늘리는 대신 **썸네일 처리를 별도 서비스로 분리**해 그것만 확장.
- 원칙: 병목이 되는 연산을 식별해 **작게 쪼개면** 필요한 곳만 확장해 낭비(과잉 프로비저닝)를 줄인다.
- 초기부터 완벽히 나누려 하지 말고 **메트릭을 보며 진화**시킨다.

**(b) 사일로 대상 서비스 최소화**
- 규제·격리·성능·티어 때문에 일부 서비스만 사일로가 필요하다면, 서비스 전체를 사일로화하지 말고 **필요한 부분만 쪼개서** 사일로로 둔다.
  - 예: 주문 서비스 → "주문 처리(사일로)" + "주문 이행(풀)"
- 사일로는 운영·비용 부담이 크므로 신중히.

**(c) 컴퓨트/스토리지의 영향** – 컨테이너는 서비스 전체가 확장 단위이고 서버리스는 함수 단위라 세분화에 유리하다. 공유 DB에 테넌트가 몰리면 DB가 새 노이지 네이버 지점이 된다.

**(d) 메트릭으로 설계 검증**
- 서비스에 테넌트 ID·티어가 포함된 메트릭을 심어야 "어떤 티어가 어떤 서비스를 압박하는지" 분석할 수 있다.

#### 8.2 서비스 내부: 테넌트 컨텍스트 추출 → 적용
저자의 규칙: **서비스 개발자가 멀티테넌시를 최대한 의식하지 않고 비즈니스 로직에 집중하게 하라.**

**Step 1. 컨텍스트 추출** – Bearer 토큰(JWT)을 검증·해석해 tenantId, tier를 꺼낸다. 위치는 서비스 내부이든 API 게이트웨이이든 상관없지만 **모든 요청 맨 앞에서 한 번** 해야 한다.

**Step 2. 로깅에 적용** – 로그마다 tenantId/tier를 포함시킨다. 그렇지 않으면 "테넌트 A만 오류가 난다"는 제보를 받아도 로그에서 A의 활동을 골라낼 수 없다.

**Step 3. 메트릭에 적용** – 처리 시간, 사용량 등을 `{tenantId, tier, service, operation, duration}` 형태로 발행한다.

**Step 4. 데이터 접근에 적용** – 풀 저장소에서는 조회 조건에 tenantId를 반드시 포함한다. 티어에 따라 저장소가 다르면(풀 테이블 vs 전용 테이블) 매핑 로직도 필요하다.

**Step 5. 격리 적용** – 쿼리 조건에 tenantId를 넣는 것만으로는 **격리가 아니다**. 개발자가 실수해도 다른 테넌트 데이터에 접근하지 못하도록 별도 방어 계층이 필요하다(9장).

#### 8.3 테넌트 세부사항을 숨기고 중앙화하기
- 위 코드를 서비스마다 복붙하면 코드가 3배로 부풀고 정책을 바꾸기 어렵다.
- 해법: 라이브러리/헬퍼로 뽑는다.
  - `getTenantContext(request)` — 토큰 해석
  - 로깅·메트릭 래퍼 — 컨텍스트 자동 주입
  - 데이터 접근 계층(DAL/Repository) — 테넌트 필터, 티어별 테이블 매핑, 격리 적용을 캡슐화
- 결과적으로 서비스 코드는 원래처럼 깔끔하게 유지된다.
- 이런 관심사 분리는 **인터셉션(가로채기)** 기법으로 더 자동화할 수 있다: 애스펙트(Aspect), 사이드카(Sidecar), **미들웨어(Middleware, Node.js/Express에서 흔함)**. 개발자가 호출하지 않아도 요청 진입/종료 시점에 테넌트 컨텍스트 초기화와 정책이 적용되도록 한다.

```ts
// 보충: AsyncLocalStorage로 요청 단위 테넌트 컨텍스트 전파 (Node.js)
import { AsyncLocalStorage } from 'node:async_hooks';

export interface TenantContext { tenantId: string; tier: string; requestId: string }
export const tenantStore = new AsyncLocalStorage<TenantContext>();

// NestJS 미들웨어: 요청 진입 시 컨텍스트를 설정
@Injectable()
export class TenantContextMiddleware implements NestMiddleware {
  use(req: any, _res: any, next: () => void) {
    // 주의: NestJS에서는 미들웨어가 Guard보다 먼저 실행되므로 req.tenant가 아직 없다.
    // 그래서 여기서 토큰을 직접 검증해 꺼내거나(아래), Guard 이후에 도는 Interceptor에서 run()을 호출한다.
    const claims = verifyAndDecode(req.headers.authorization); // 서명 검증 헬퍼(가정)
    tenantStore.run(
      { tenantId: claims.tenantId, tier: claims.tier, requestId: req.id },
      next,
    );
  }
}

// 어디서든 꺼내 쓰기: 로거, 리포지토리, 메트릭에서 매개변수 전달 없이 사용
export const currentTenant = () => {
  const ctx = tenantStore.getStore();
  if (!ctx) throw new Error('No tenant context'); // 컨텍스트 없이 DB 접근 시 즉시 실패
  return ctx;
};
```

> **왜 중요한가?** "매번 개발자가 tenantId를 넘겨야 한다"는 구조는 반드시 누군가 빠뜨린다. **컨텍스트 전파와 필터를 프레임워크 레벨에서 자동화**하는 것이 사고를 막는다.

> 🔗 NestJS 연결: Middleware(요청 진입), Guard(인증/활성 테넌트 확인), Interceptor(로그/메트릭/응답 처리), 커스텀 Provider(`REQUEST` 스코프 또는 AsyncLocalStorage 기반 `nestjs-cls`)를 조합한다. Request-scoped provider는 성능 비용이 있으므로 AsyncLocalStorage 방식을 우선 고려한다.

### 9. 데이터 파티셔닝(Data Partitioning): 테넌트 데이터를 어떻게 나눌까
#### 9.1 핵심 개념
- **데이터 파티셔닝**: 테넌트 데이터를 어떤 저장 구조에 어떻게 나눠 담을지의 전략. 사일로/풀 용어를 그대로 쓴다.
  - **Pooled(풀)**: 한 테이블/저장소에 모든 테넌트 데이터를 섞고, 각 행에 `tenant_id`를 붙여 구분
  - **Siloed(사일로)**: 테넌트마다 별도 저장소(전용 DB/스키마/테이블)
- 두 방식은 배타적이지 않다. **티어별로 섞을 수 있고**(Basic=풀, Premium=사일로), **서비스마다 다르게** 정해도 된다. 즉 "테넌트 전체 데이터를 무조건 사일로"가 아니라 **데이터 종류별로** 필요한 것만 사일로화한다.
- 사일로일 때는 저장소 이름에 테넌트 식별자를 붙여 매핑한다. 이때 dev/staging/prod 환경 구분도 이름 규칙에 포함해야 할 수 있다.

#### 9.2 선택 기준

| 고려 요소 | 질문 |
|---|---|
| 워크로드·SLA | 부하 변동은? 큰 테넌트 하나가 DB를 독점할 수 있는가? 테넌트별 데이터 크기는? |
| 노이지 네이버 | 풀 DB에서 한 테넌트 쿼리가 다른 테넌트를 느리게 하나? |
| 장애 영향 범위(Blast radius) | DB가 죽으면 전체 테넌트가 죽는가? 중요한 데이터는 분리할까? |
| 격리 요구 | 규제·고객 계약상 데이터를 물리적으로 분리해야 하나? |
| 운영·관리 | 스키마 마이그레이션, 백업/복원, 모니터링을 테넌트 수만큼 반복하는 부담은? |
| 규모 한계 | 테넌트당 DB/스키마를 수천 개 만들어도 되는가? (DB 엔진의 한계) |
| 비용 | 유휴 상태에서도 테넌트당 고정비가 드는가? |
- **기본값은 풀.** 사일로는 "명확한 이유가 있을 때만" 도입하도록 하면 불필요한 사일로를 막는다. 사일로는 자기 자리를 증명해야 한다.
- 서비스별로 "이 데이터에 가장 맞는 저장소"를 고르는 것이 좋다(기술 하나로 통일 강요 X).

#### 9.3 관계형 DB(PostgreSQL 등)에서의 파티셔닝
**풀(Pooled)**
- 모든 테이블에 `tenant_id` 컬럼을 추가한다.
- 원서: TenantId가 테이블 접근의 기본 키 역할을 하고, 원래의 키(예: CustomerId)는 보조 키/필터가 된다. 그래서 **모든 쿼리에 tenant 조건**이 들어간다. (보충: 인덱스에서 tenant_id를 앞에 두는 복합 키가 일반적)
- 장점: 가장 단순, 마이그레이션 한 번에 전체 적용
- 단점: 잘못된 쿼리 하나가 유출로 이어짐(→ 격리 계층 필수). 데이터가 과도하거나 고르지 않으면 한 저장소의 확장 한계에 부딪힌다. 큰 테넌트 하나가 좌우할 수 있다.
- 관계형은 스키마가 있어서 모든 테넌트를 새 스키마로 옮기는 마이그레이션 부담이 있어 민첩성 면에서 불리하다. 그래도 관계형이 잘 맞는 워크로드가 있다.

**사일로(Siloed)** — 세 가지 단위
1. 테넌트당 DB **인스턴스** (가장 강한 분리, 가장 비쌈)
2. 테넌트당 **데이터베이스**(같은 인스턴스 공유)
3. 테넌트당 **테이블 세트**(같은 DB 안). (보충: PostgreSQL에서는 schema-per-tenant로 구현하는 방식이 흔하다. 원서는 RDS 기준 인스턴스/데이터베이스/테이블 세 단위를 설명한다.)
- 스키마가 있는 RDB는 **모든 사일로에 마이그레이션을 각각 적용**해야 해서 민첩성이 떨어진다 (예: 새 컬럼 추가를 수천 스키마에 롤아웃).
- 구조를 나눠도 **DB 사용자 권한 등으로 접근 제한이 가능한지**를 확인해야 한다. 나눴는데 접근 제어가 안 되면 격리가 안 되는 것과 같다.
- 엔진의 한계(DB 수, 테이블 수)를 사전에 계산한다.

#### 9.4 NoSQL 파티셔닝 (개념)
- 스키마리스라 기능 출시 시 대규모 마이그레이션 부담이 적어 민첩성에 유리하다. 풀은 한 테이블에 `tenantId`를 파티션 키로(원래 키는 정렬 키), 사일로는 테넌트당 테이블로 나눈다(원서는 DynamoDB 기준). 사일로 테이블 이름은 전역에서 유일해야 한다.
- 원서 저자는 "NoSQL로 시작하고, 사업 요구가 관계형을 가리키면 그때 옮기라"고 조언한다. (보충: 이 문서의 스택은 PostgreSQL이므로, 관계형 데이터가 핵심이면 풀 + tenant_id + RLS로 시작하는 것이 합리적이다.)
- 원서는 객체 저장소(S3: 접두어로 테넌트 구분, 버킷당 테넌트는 개수 한도 주의)와 검색 엔진(OpenSearch: 테넌트별 인덱스 또는 공용 인덱스)의 사일로/풀도 다룬다. 개념은 같다.

#### 9.5 그 밖의 고려사항
- **스토리지 컴퓨트 크기 산정(Rightsizing)**: 서비스는 수평 확장으로 부하를 따라가지만, DB 서버는 미리 크기를 정하는 경우가 많다. 풀 DB는 피크에 맞춰 **과잉 프로비저닝**이 되기 쉽다. 서버리스 DB 계열은 이 문제를 줄여 준다.
- **처리량 제어(Throughput/Throttling)**: DB 수준 설정과 애플리케이션 수준 스로틀링으로 노이지 네이버를 완화한다.
- **샤딩(Sharding)**: 풀을 유지하되 하나의 DB로는 감당이 안 될 때, 테넌트 그룹을 여러 DB에 나눠 배치하는 방식(Pod 배포 모델의 데이터 버전). 데이터 접근 계층이 "테넌트→샤드" 조회를 해야 하므로 복잡하지만, 영향 범위 축소와 확장에 도움이 된다.
- **혼합 모드**: 한 저장소 안에서 Premium은 전용 인덱스/테이블, Basic은 공유 구조를 쓰는 식으로 섞을 수 있다.

#### 9.6 데이터 수명주기와 보안
- **티어 업그레이드**: 풀 → 사일로로 데이터 이동 자동화가 필요. 이동 중 부하가 다른 테넌트에 영향을 주면 안 된다.
- **삭제(Decommission)**: 풀에서 특정 테넌트 행만 지우려면 서비스별로 코드를 작성해야 한다.
- **백업/복원**: 풀에서는 "특정 테넌트만 복원"이 까다롭다. 처음부터 테넌트 단위 백업/복원이 필요한지 결정해 두어야 한다.
- **암호화**: 전송 중/저장 시 암호화는 기본. 고객이 자신의 **암호화 키를 직접 관리**하길 원하면(BYOK) 대체로 그 테넌트 데이터를 사일로로 둬야 한다.
- **분리 ≠ 격리**: 데이터를 사일로에 둔다고 격리가 되는 것은 아니다(다음 절).

> **왜 중요한가?** 이 선택은 나중에 바꾸기 가장 어렵다. 처음엔 "풀 + tenant_id + 강한 격리 계층"으로 시작하고, 사일로는 예외로 두는 것이 현실적인 출발점이다. 단, 사일로로 옮길 수 있게 **데이터 접근을 리포지토리 계층에 캡슐화**해 두어야 한다.

> 🔗 NestJS 연결: TypeORM/Prisma/MikroORM에서 요청마다 다른 DataSource나 스키마를 선택해야 한다면 커스텀 Provider(`useFactory`) + 컨텍스트로 구성. 풀 모델에서는 Repository 베이스 클래스에서 tenantId 조건을 강제하거나 ORM subscriber/filter를 이용한다.

### 10. 테넌트 격리(Tenant Isolation): "실수해도 새지 않게" 막는 방어선
#### 10.1 핵심 메시지
1. **배포 방식(사일로/풀)과 격리는 다른 것**이다. DB를 테넌트별로 나눠도, 서비스 코드가 테넌트 A 요청 처리 중 B의 DB 연결을 쓰는 실수를 하면 막을 장치가 없다.
2. 격리는 코드와 자원 **사이에 끼는 게이트키퍼**다. 테넌트 컨텍스트를 기준으로 자원 접근 범위를 제한하고, 코드가 뭘 요청하든 그 범위 밖은 거부한다.
3. "우리 개발자는 실수 안 해요"라는 가정은 위험하다. 업계에는 한 테넌트의 데이터가 다른 테넌트에 노출된 사고가 수없이 많고, **한 번의 유출**이 사업에 치명적이다.
4. 테넌트 관점에서는 자원이 공유든 전용이든 **똑같이 격리되어 있다고 기대**한다.
5. 격리는 **의도적으로 설계하고 구현**해야 한다(자연스럽게 되지 않는다).

#### 10.2 격리의 세 가지 수준

| 수준 | 의미 | 예시 | 난이도 |
|---|---|---|---|
| **Full Stack 격리** | 테넌트 전용 스택 전체가 경계 | 테넌트별 클라우드 계정/네트워크/클러스터 | 쉬움 (기존 경계 도구 활용) |
| **Resource 수준** | 자원 하나가 경계 (DB, 큐, 버킷) | 테넌트 전용 DB에 접근 권한을 그 테넌트로 한정 | 중간 |
| **Item 수준** | 공유 자원 **안의 행/문서** 단위 | 공유 테이블에서 내 tenant_id 행만 접근 | 가장 어려움 (지원하는 도구가 적음) |
- 풀 모델을 많이 쓸수록 Item 수준 격리가 중요해지는데, 이 수준을 강제할 도구가 부족하면 **직접 만든다**(ABAC, OPA 같은 정책 도구, 앱 레벨 강제 등).

#### 10.3 RBAC와 격리는 다르다
- **RBAC(역할 기반 접근 제어)**: 사용자의 **역할**에 따라 기능 접근을 제한 (관리자는 삭제 가능, 일반 사용자는 불가)
- **격리**: 사용자 역할과 무관하게 **오직 테넌트 컨텍스트**로 자원 범위를 제한
- 같은 테넌트 안에서 역할이 달라도 격리 정책은 같다. 두 개념을 섞으면 설계와 테스트가 뒤엉킨다. 같은 도구를 쓰더라도 **의도는 분리**해서 생각한다.

#### 10.4 격리는 애플리케이션이 정의한다
- 인프라(클라우드)는 자기 수준의 격리를 제공하지만, "어디가 테넌트 경계인가"는 **우리 앱만 안다**. 공유 테이블의 어느 행이 어느 테넌트 것인지 인프라는 모르기 때문이다.
- 따라서 앱 레벨에서 경계를 정의하고 코드/라이브러리로 강제하는 것이 SaaS의 기본 책임(shared responsibility)이다.

#### 10.5 격리는 계층적으로 적용한다
- **API 계층**: 요청의 테넌트 컨텍스트로 접근 가능한 경로/서비스인지 확인 (예: 테넌트 A 요청이 테넌트 B 전용 서비스로 못 가게)
- **컴퓨트 → 자원 계층**: 서비스가 DB/큐/스토리지에 접근할 때 그 테넌트 범위로 제한
- 여러 겹으로 방어(defense in depth)한다.

#### 10.6 배포 시점 격리 vs 런타임 격리
**배포 시점(Deployment-time) 격리**
- 서비스가 **테넌트 전용(사일로)** 으로 배포된다면, 배포할 때 "이 서비스는 테넌트 X 자원에만 접근 가능"이라는 정책을 부여해 버린다.
- 코드가 어떤 실수를 해도 배포 정책이 막아 주므로 **개발자의 준수에 의존하지 않는다.** (컴플라이언스가 DevOps 프로세스로 이동)
- 단, 사일로 배포가 전제이므로 모든 자원을 사일로화하는 것은 비현실적.

**런타임(Runtime) 격리**
- 서비스가 **풀(공유)** 이면 배포 시점에는 모든 테넌트에 접근 가능해야 한다.
- 따라서 **요청마다** 테넌트 컨텍스트로 "범위가 제한된 자격/세션"을 얻어 그 범위 안에서만 자원을 사용한다.
- 이 과정을 서비스 개발자가 몰라도 되게 **미들웨어/래퍼/사이드카/프록시** 같은 가로채기 계층에 넣는다(개발자를 격리 흐름에서 최대한 제외).
- 성능 이슈: 매 요청마다 범위 제한 자격을 발급하면 지연이 커진다 → **TTL 캐시**로 완화하고, 발급 로직은 별도 네트워크 호출 서비스보다 **같은 프로세스 안 라이브러리**로 두는 편이 낫다. 정책 개수 같은 서비스 한도도 고려해, 테넌트마다 정책을 만들지 말고 **정책 템플릿**에 테넌트 값을 채워 쓴다.
- 원서의 구체 예(AWS)는 STS로 테넌트 범위가 제한된 임시 자격을 받아 DynamoDB에 접근하는 방식이다. 아래 RLS는 이를 PostgreSQL 환경에 옮긴 (보충) 대응 사례다.

#### 10.7 격리 정책 관리와 테스트
- 격리 정책은 **서비스와 함께 버전 관리**(각 서비스 저장소에 포함)하거나 **중앙 저장소**에서 관리하는 방식이 있다. 저자는 서비스 소유팀이 자기 정책을 함께 관리하는 편을 선호. 어느 쪽이든 배포·버전·소유가 정해져야 한다.
- **격리 테스트가 반드시 필요**: 테넌트 1 컨텍스트에서 테넌트 2의 ID로 조회했을 때 **빈 결과 또는 오류**가 나와야 한다. 이런 "교차 테넌트 접근" 시도는 로그/알람으로도 남긴다. (카오스 엔지니어링 기법도 활용 가능)
- 테스트가 어렵다는 이유로 생략하면 안 된다.

```ts
// 보충 1: 앱 레벨 강제 — 모든 쿼리에 tenant 조건을 자동으로 붙이는 기반 리포지토리
export abstract class TenantScopedRepository<T extends { tenantId: string }> {
  constructor(protected readonly repo: Repository<T>) {}

  find(where: FindOptionsWhere<T> = {}) {
    return this.repo.find({ where: { ...where, tenantId: currentTenant().tenantId } as any });
  }

  save(entity: Omit<T, 'tenantId'> & Partial<T>) {
    return this.repo.save({ ...entity, tenantId: currentTenant().tenantId } as T);
  }
  // 조건 없는 raw query/QueryBuilder는 별도 승인 경로로만 허용 (코드 리뷰/린트 규칙)
}
```

```sql
-- 보충 2: PostgreSQL Row-Level Security (DB가 직접 Item 수준 격리를 강제)
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
ALTER TABLE orders FORCE ROW LEVEL SECURITY;  -- 테이블 소유자에게도 적용 (앱이 소유자 계정이면 필수)
CREATE POLICY tenant_isolation ON orders
  USING (tenant_id = current_setting('app.tenant_id')::uuid);
-- 요청 시작 시 트랜잭션에서 (바인드 파라미터 사용, 문자열 이어붙이기 금지):
--   SELECT set_config('app.tenant_id', $1, true);   -- $1 = 검증된 tenantId, true = 트랜잭션 로컬
-- 앱 코드에서 WHERE tenant_id를 빠뜨려도 다른 테넌트 행은 반환되지 않는다.
-- 주의: 앱 접속 계정이 superuser 이거나 BYPASSRLS 권한이면 RLS가 무시된다.
```

> **왜 중요한가?** 멀티테넌트 SaaS에서 가장 치명적인 사고는 "다른 고객 데이터가 보이는 것"이다. 격리는 **버그가 있어도 유출되지 않게 하는 구조**이며, 사일로냐 풀이냐와 무관하게 필수다.

> 🔗 NestJS 연결: 격리 로직은 Guard(요청 진입 전 확인) + Interceptor/Middleware(컨텍스트 설정) + 기반 Repository/ORM 훅(쿼리 스코프) + DB RLS의 다층 방어로 구성한다. 격리 회귀 테스트는 e2e 테스트(`supertest`)에 포함시킨다.

### 11. 노이지 네이버와 스로틀링, 티어링
#### 11.1 노이지 네이버 대응 도구 상자

| 수단 | 설명 |
|---|---|
| **스로틀링(Throttling)/Rate limit** | 테넌트(또는 티어)별로 초당 요청 수, 버스트, 일일 쿼터 제한 |
| **서비스 분해** | 무거운 연산을 별도 서비스/워커로 분리해 독립 확장 |
| **큐 기반 비동기화** (보충) | 무거운 작업을 큐에 넣고, 테넌트별 공정성 있게 처리 (원서에 직접 항목은 없고 일반 상식) |
| **사일로화** | 지속적으로 문제가 되는 자원/테넌트만 전용으로 |
| **동시성/자원 상한** | 티어별 동시 실행 수, CPU/메모리 쿼터 |
| **DB 처리량 제어** | 저장소 수준 처리량 설정, 풀 안의 티어 구분 |
| **메트릭과 알림** | 테넌트별 사용량을 보고 이상 징후 감지 |
- **무제한을 허용하면 과잉 프로비저닝**으로 이어져 비용 효율 목표를 무너뜨린다.
- 심지어 "사용량 기반 과금이니 제한 필요 없다"는 접근도 함정이다. **과금 대상이 아닌 API를 마구 호출**하는 테넌트가 다른 테넌트를 해칠 수 있으므로 과금 여부와 별개로 보호 장치가 필요하다.
- 서버리스에서 함수 동시성을 티어별로 나눠 한 티어가 전체 동시성을 고갈시키지 못하게 하는 접근이 예시로 소개된다(개념: **티어별 자원 상한**). 쿠버네티스에서는 네임스페이스별 리소스 쿼터로 같은 개념을 구현한다.

#### 11.2 티어별 스로틀링의 원칙
- 정책을 한 곳(게이트웨이/미들웨어)에서 설정하고, **클라이언트에게 티어 개념을 알리거나 키를 관리하게 하지 않는다.**
- 이전에 소개했듯 **토큰 안의 tier**로 정책을 선택하는 방식이 깔끔하다.
- 티어별 제한 예시: 요청/초, 버스트, 일일 쿼터, 동시 작업 수, 저장 용량, 데이터 보관 기간, 사용자 수, 기능 접근.
- "제한이 나쁜 경험이 아니냐"는 질문에 대한 답: 제한은 **전체 가용성·비용을 보호**하는 것이며, 티어별 제한이 **명확히 공지**되어야 한다. 한도에 다가가면 **경고(soft limit)** 를 먼저 주고 **하드 리밋**에서 실제 차단하는 단계형 방식도 유용하다.

> 🔗 NestJS 연결: `@nestjs/throttler`를 커스텀 Guard로 확장(트래커=tenantId, 한도=티어별), 저장소는 Redis. 백그라운드 작업은 BullMQ에서 테넌트별 rate limiter/그룹 큐로 공정성을 확보한다.

> 📖 원문: 7장 Addressing Noisy Neighbor; 8장 Throughput and Throttling; 11장 Concurrency and Noisy Neighbor(개념); 14장 Throttling and Tenant Experience, API/Compute/Storage Tiering

### 12. 티어링(Tiering)과 과금(Billing)/미터링(Metering)
#### 12.1 티어링은 "가격표"가 아니라 아키텍처 결정
- 티어는 **가치 경계(Value boundary)** 를 만든다. 성능, 비용, 기능, 격리 등에서 경계를 찾고, 이를 요금제와 연결한다.
- 티어 정보는 컨트롤 플레인이 관리하고, 토큰에 실려 앱 전반에서 활용된다.

#### 12.2 티어링 패턴 3가지

| 패턴 | 아이디어 | 예 |
|---|---|---|
| **소비(Consumption) 중심** | 사용 가능한 자원량을 티어로 제한, **티어별 매출이 비용을 넘도록** | 월 $50 Basic은 월 $5,000 Platinum과 같은 속도로 자원을 못 쓰게 |
| **가치(Value) 중심** | 기능/성능/SLA/사용자 수 등 체감 가치를 차등 | 상위 티어만 고급 기능, 빠른 처리(비디오 인코딩 즉시 vs 배치 큐) |
| **배포(Deployment) 중심** | 격리/전용 자원을 상위 티어에서 제공 | Basic=전체 풀, Advanced=일부 서비스 전용, Premium=전체 스택 사일로 |
- 위 패턴은 **조합 가능**(Composite). 도메인 특화 티어도 가능. 테넌트가 옵션을 골라 구성하는 "빌드 유어 오운 티어"도 있지만 운영 복잡도가 커진다.
- 기능 접근 제어는 RBAC 또는 **기능 플래그(Feature flag)** 로 구현하되, 사용자 역할과 테넌트 티어가 모두 영향을 준다.

- 무료 티어는 획득 채널이지만 비용이 드는 만큼 소비 제한이 특히 중요하고, 유료 전환 시 데이터 이관과 비활성 무료 테넌트 정리 정책을 미리 정한다.

#### 12.3 티어 구현 지점

| 계층 | 티어를 구현하는 방식 (개념) |
|---|---|
| **API** | 티어별 사용량 계획(초당 요청 수/버스트/일 쿼터). 게이트웨이나 미들웨어에서 적용 |
| **컴퓨트** | 티어별 동시성/스케일링/자원 쿼터, 티어별 별도 배포 |
| **스토리지** | 풀에서 티어별 처리량/용량/보관기간 제한, 또는 상위 티어만 사일로. 데이터 종류별로 필요한 것만 사일로화 |
| **서비스 배포** | Premium만 특정 서비스를 테넌트 전용으로, 나머지는 공유 |
- 개별 테넌트용 정책(one-off)은 지양하고 **티어 단위 정책**으로 관리한다.
- 티어 목록은 컨트롤 플레인의 작은 서비스로 관리하고, **과금 시스템의 플랜/티어와 동기화**한다.
- 운영 관점: 티어 정책이 제대로 작동하는지(너무 빡빡/느슨하지 않은지) 메트릭으로 지속 점검한다.

#### 12.4 과금과 미터링
- **메트릭(Metrics)**: 운영·비즈니스 의사결정용 데이터. **미터링(Metering)**: 청구서 계산에 쓰는 사용량 데이터. 두 목적은 다르지만 데이터가 겹칠 수 있다.
- 과금 연동 지점: (1) 온보딩 시 고객/플랜 등록 (2) 사용량 기반이면 사용 이벤트(요청 수, 저장량, 대역폭 등)를 수집해 과금 시스템으로 전송 (3) 연체 등 과금 상태 변화 이벤트를 받아 테넌트 비활성화 등에 반영
- 과금 시스템 장애가 서비스 장애로 번지지 않도록 **비동기·재시도·멱등성**을 적용한다.
- (보충: 원서 외 일반 설계 조언) 미터링 이벤트는 정확성이 중요하므로 중복 방지(멱등 키)와 누락 방지(영속 큐) 설계를 한다. 원서는 소비·과금 데이터를 API/서비스/인프라 자원 어느 층에서 수집할지를 다룬다.
- 원서에서 티어는 과금 시스템의 플랜/티어와 연결되어 컨트롤 플레인에서 스로틀링·사용량 측정·기능 on/off에 쓰인다(14장 Billing and Tiering).

> **왜 중요한가?** 티어를 초기에 고려하지 않고 나중에 붙이면 스로틀링, 기능 플래그, 라우팅, 과금 식별자를 전부 뜯어고쳐야 한다. 처음부터 "tier가 토큰과 설정 테이블에 있다" 정도만 준비해도 크게 유리하다.

> 🔗 NestJS 연결: 기능 접근 제어는 커스텀 데코레이터(`@RequireTier('premium')`)와 Guard 조합으로 구현. 미터링은 Interceptor + 큐(BullMQ/Kafka)로 비동기 발행.

> 📖 원문: 14장 Tiering Patterns (Consumption/Value/Deployment-Focused, Free Tiers, Composite), Billing and Tiering, Implementing Tiering, Tier Management, Operations and Tiering; 2장 Billing; 12장 Multi-Tenant Operational Metrics

### 13. 테넌트 인지 운영(Tenant-Aware Operations): 관측과 배포
#### 13.1 SaaS 운영 마인드셋
- 운영은 개발팀 밖의 일이 아니다. 제품, 고객 성공, 경영진까지 **테넌트의 서비스 경험**에 관심을 갖는다.
- 공유 환경은 "누가 시스템을 쓰고, 누가 문제를 일으키는가"가 잘 안 보이므로 **테넌트별 가시성**이 없으면 운영이 불가능하다.
- 문제를 사후 대응이 아니라 **선제적(proactive)** 으로 찾는다 (예: 온보딩이 막힌 테넌트, 사용량이 줄어 이탈 위험이 있는 테넌트).
- 운영 도구는 한 번 만들고 끝이 아니라 계속 진화시킨다. 저자는 기능 개발을 일부 미루더라도 운영 기반에 우선 투자하라고까지 말한다.

#### 13.2 어떤 메트릭을 모을까

| 분류 | 예시 | 용도 |
|---|---|---|
| **테넌트 활동** | 온보딩 소요 시간·단계별 이탈, Time to value, 기능 사용, 활동 감소(이탈 신호) | 온보딩 개선, 고객 성공 관리 |
| **민첩성(Agility)** | 가용성, 배포 빈도, 배포 실패율, 리드타임, MTTD/MTTR, 결함 유출률 | 배포/운영 성숙도 |
| **소비(Consumption)** | 테넌트·티어별 자원 사용량 (API 호출 수, 서비스별 처리량, DB/큐 사용) | 스케일링, 티어링, 스로틀링 정책 |
| **테넌트당 비용(Cost per tenant)** | 인프라 청구액을 소비 비율로 안분해 테넌트/티어별 비용 계산 | 요금제/마진 검증 |
| **비즈니스 건강** | MRR, 이탈률(Churn), CAC, CLTV | 경영 판단 (기술 외부 데이터 다수) |
| **기본(Baseline) 인프라** | CPU, 메모리 | 이상 징후와 테넌트 활동을 상관 분석 |

핵심 통찰:
- **풀 자원은 소비 귀속이 어렵다.** 자원 수준 사용량은 알아도 "각 테넌트가 몇 %를 썼는가"는 도구가 알려주지 않으므로 **직접 계측**해야 한다. API 진입점(가볍지만 거침) → 서비스 수준 → 인프라 자원 수준 순으로 정밀도를 높일 수 있고, 처음에는 가장 값진 곳만 계측하고 점차 확대한다.
- **테넌트당 비용의 예**: 최하위 티어가 매출은 가장 적은데 인프라 비용은 가장 크게 잡히는 경우가 실제로 발생한다. 티어/가격 정책이 소비와 맞는지 이 지표로 검증한다. (정확한 회계가 아닌 **근사치**로 충분)
- 로그·메트릭에는 최소한 **tenantId와 tier**를 넣는다. 이 하나가 분석 가능성을 크게 좌우한다.

#### 13.3 배포 자동화와 표적 릴리스
- 배포 자동화는 세 부분이다: (1) 기본 환경 + 공유 풀 자원 준비 (2) **테넌트 온보딩 시** 필요한 자원 프로비저닝 (3) **업데이트 배포**(전용 자원이 있으면 풀과 각 사일로에 **모두** 배포해야 하므로 온보딩 때 기록한 자원 정보를 사용).
- **기능 플래그(Feature flag)**: 티어 단위로 기능을 켜고 끈다. 특정 테넌트 전용 플래그를 남발하면 개별 맞춤화로 미끄러져 SaaS 이점이 사라진다 → **티어 단위 원칙**, 예외는 최소화.
- **카나리 릴리스(Canary)/웨이브 릴리스**: 테넌트를 그룹으로 나눠(예: 내부 테스트 테넌트 → 우호적 고객 → 나머지) 단계적으로 배포. 풀에서는 "일부 테넌트에게만 새 코드 경로를 켜는 기능 플래그"로 흉내 낼 수 있다.
- 풀 모델은 모든 테넌트가 동시에 새 버전을 받으므로, 롤백 능력과 테스트가 그만큼 중요하다.

#### 13.4 테넌트 인지 운영 콘솔·로그·대시보드 (원서 12장 Building a Tenant-Aware Operations Console 이후)

- **기성 모니터링 도구는 테넌트·티어 개념이 없다.** 그래서 전체 지표는 초록색인데 "특정 테넌트만 느리다"는 제보가 오면 원인을 찾을 수단이 없다. 도구를 커스터마이징하거나 콘솔을 직접 만들어 **전체 / 티어 / 개별 테넌트**로 범위를 바꿔 가며 볼 수 있게 해야 한다.
- 원서 예: 마이크로서비스 상태 히트맵(초록→노랑→빨강)에서 "가장 활발한 서비스"와 "전체 테넌트/특정 티어/특정 테넌트" 필터를 고르면 그 범위의 건강 상태가 보인다. 그 밖에 가장 활동이 많은(=문제가 나기 쉬운) 테넌트 목록과 상태, 테넌트별 인프라 서비스 소비 분포(특정 테넌트가 비정상적으로 많이 쓰는지), 테넌트별 마이크로서비스 사용량 막대 등.
- **티어는 과금 개념만이 아니다.** 티어마다 운영상 경험이 다르므로 "고급 티어가 노이지 네이버 영향을 받지 않는지"처럼 티어 관점으로도 본다.
- **기술 지표와 경험(비즈니스) 지표를 함께 보여 주면** 상관관계를 찾을 수 있다. 예: 새 기능 배포가 성능 문제를 일으켜 온보딩 시간이 늘어난 것을 발견. 운영팀의 일은 단순한 헬스 모니터링을 넘어선다.
- **테넌트 인지 로그**: 서비스가 로그에 테넌트 컨텍스트(테넌트 ID, 티어)를 반드시 남겨야 하고, 그 로그를 테넌트·티어로 필터링해 볼 수 있어야 한다. 콘솔에 로그 뷰를 넣거나 기성 로그 분석 도구를 쓰거나 둘 다 유효하다.
- **선제적(proactive) 전략**: 사람이 개입해야 할 조건은 알림으로, 성능 저하는 자동으로 감지해 스케일링을 조정하는 식으로 자동화·정책으로 문제를 미리 잡는다. 방식은 기술 스택과 배포 모델에 따라 다르다.
- **역할별 대시보드**: 메트릭을 하나의 공유 웨어하우스에 모으고, 각 직군(운영, 제품, 영업 등)이 자기 관점의 대시보드를 만들어 쓰게 한다. 그럴수록 새 지표 요구도 늘어난다.
- **배포 자동화의 세 요소**(13.3절과 연결): (1) 환경 초기 설정과 풀 자원, (2) 온보딩 때 실행되는 테넌트별 프로비저닝, (3) 테넌트별 자원이 있을 때 **업데이트를 각 환경에 매핑해 배포**하는 과정. 런타임에 테넌트 인프라가 계속 생기므로 이 자동화 코드는 높은 품질·신뢰성이 필요하다.

> **왜 중요한가?** 운영 지표가 없으면 티어 정책, 스케일링, 노이지 네이버 대응이 전부 "감"이 된다. 또한 테넌트별 비용을 모르면 성장할수록 적자가 커지는 요금제를 유지할 수 있다.

> 🔗 NestJS 연결: OpenTelemetry로 span/attribute에 `tenant.id`, `tenant.tier`를 넣고, 로거는 pino 등 JSON 로거로 통일한다. 배포 시 DB 마이그레이션은 "풀 1회 + 사일로 N회"로 실행되도록 마이그레이션 도구를 설계한다.

> 📖 원문: 12장 The SaaS Operations Mindset, Multi-Tenant Operational Metrics (Tenant Activity, Agility, Consumption, Cost-per-Tenant, Business Health, Composite, Baseline), Multi-Tenant Deployment Automation (Scoping Deployments, Targeted Releases)

### 14. 기술 스택별 멀티테넌트 배포: 컨테이너(Kubernetes)와 서버리스

> 원서 10장(EKS), 11장(서버리스/Lambda)은 AWS 서비스를 예로 들지만, 핵심은 "3절의 사일로/풀 모델을 각 컴퓨트 스택이 어떤 단위로 구현하는가"다. 이 절은 **개념만** 옮긴다. NestJS 앱은 컨테이너로 배포되는 경우가 많으므로 Kubernetes 쪽이 더 가깝고, 서버리스는 비교용이다.

#### 14.1 왜 Kubernetes(EKS)와 SaaS가 잘 맞는가 (원서 10장 The EKS–SaaS Fit)

- **프로그래밍 모델이 그대로**다. 언어·도구·라이브러리를 유지한 채 컨테이너로 옮길 수 있어, 기존 시스템을 SaaS로 이전할 때 멀티테넌시 핵심에 에너지를 쓸 수 있다.
- **스케일링**: 스파이크에 빠르게 늘리고 효율적으로 줄일 수 있다(다만 노드 증감이 필요하므로 과잉 프로비저닝이 완전히 사라지지는 않는다).
- **묶음 단위(namespace)** 로 컴퓨트를 사일로/풀로 나눌 수 있고, **배포 도구 생태계**(Helm, Argo, Flux 등)가 티어별 온보딩·배포에 잘 맞는다.
- **격리 수단**(사이드카, 서비스 메시)이 늘어나 격리 정책을 중앙으로 밀어 개발자 부담을 줄일 수 있다.
- 단점: 도구와 패턴이 계속 바뀌어 처음 고른 전략이 새 도구 때문에 낡을 수 있다.

#### 14.2 Kubernetes 배포 패턴 (원서 10장 Deployment Patterns)

핵심 용어: **클러스터**(전체 컴퓨트), **노드**(클러스터 안에서 탄력적으로 늘고 주는 서버), **파드(pod)**(실행 최소 단위), **네임스페이스**(클러스터 안의 자원 그룹, "하위 클러스터"처럼 생각).

| 패턴 | 설명 | 특징 |
|---|---|---|
| 풀(Pooled) | 모든 테넌트가 한 클러스터·한 네임스페이스 공유 | 가장 단순. 클러스터 자동 확장에 의존. 복제본 수·메모리 설정으로 튜닝 |
| 네임스페이스별 사일로 | 테넌트마다 네임스페이스를 만들고 서비스 복사본을 배포 | 가장 흔한 사일로. 테넌트별 관리·설정이 쉽고 네임스페이스 간 접근 정책을 붙일 수 있음. 노드는 공유하며 전체가 함께 확장 |
| 노드별 사일로 | 네임스페이스 + 전용 노드까지 테넌트에 묶음 | 컴퓨트를 아예 공유하지 않아 규정 준수 요구에 맞음 |
| 테넌트별 클러스터 | 테넌트마다 클러스터 | 저자는 대체로 과하다고 봄(운영·비용 부담, 규모 확장 어려움) |
| 파드(pod) 배포 모델 | 테넌트 그룹을 여러 클러스터에 분산(예: 프리미엄 몇 개는 별도 클러스터, 나머지는 공유) | 변형 다수. 3절의 "pod"와 쿠버네티스 pod는 다른 개념 |
| 가상 클러스터 | 클러스터 수준 격리 느낌 + 노드는 공유 | 주목할 만한 대안 |

- **혼합(mixed mode)**: 사일로 테넌트는 각자의 네임스페이스에, 나머지는 하나의 "풀" 네임스페이스에 두면 복잡도가 크게 늘지 않는다. 한 네임스페이스 정의를 다른 곳에 재사용하기 쉽다.
- **컨트롤 플레인 위치**: 정답은 없다. 애플리케이션 플레인과 **별도로 관리·버전·배포**해야 한다는 것만 확실하다. (a) 완전히 별도 클러스터: 독립 운영·스케일 가능, 클러스터 간 통신 허용 필요. (b) 같은 클러스터의 별도 네임스페이스: 자동화·비용 효율이 좋지만 분리를 원하는 팀도 있음.

#### 14.3 라우팅 (원서 10장 Routing Considerations)

- 테넌트별 자원이 흩어져 있으면 요청을 알맞은 곳으로 보내는 **테넌트 인지 라우팅**이 필요하다(7절).
- **Ingress 컨트롤러**(NGINX, Contour, Kong)가 인바운드 로드 밸런서로 테넌트 경로·서브도메인에 따라 테넌트 네임스페이스의 서비스로 보낸다. **서비스 메시**(Istio, Linkerd 등)는 더 세밀한 라우팅을 제공한다.
- 앞단에서 테넌트 컨텍스트를 뽑아 **라우팅과 인증**에 쓴다. 예: 서브도메인으로 어느 아이덴티티 제공자로 인증할지 결정(프리미엄은 전용 사용자 풀, 기본 티어는 공용 풀). 이런 매핑 정책을 서비스 코드 밖의 프록시로 옮긴다.

#### 14.4 온보딩·배포 자동화 (원서 10장 Onboarding and Deployment Automation)

- 온보딩 코드는 티어에 따라 필요한 자원이 다르다. 사일로 온보딩은 네임스페이스 생성·서비스 배포·저장소 프로비저닝, 풀은 대부분 설정만 하고 필요한 테넌트 전용 자원만 만든다.
- 개발 CI/CD는 **새 버전을 모든 테넌트 네임스페이스에 배포**해야 하며, 개발자가 이 복잡성을 몰라도 되게 한다.
- 원서 예시 조합: **Helm**으로 공통 기본 템플릿 + 티어별 값(chart)을 정의, **Argo Workflows**로 온보딩 워크플로 오케스트레이션(비 쿠버네티스 자원은 Terraform/CDK 등으로 프로비저닝), **Flux**가 저장소의 chart 변경을 감지해 클러스터에 적용. 서비스 v3.1→v4.0 배포도 chart 버전을 올리면 Flux가 모든 네임스페이스에 반영한다.
- 쿠버네티스 밖 자원(DB 등)은 Helm으로 못 다루므로 다른 인프라 자동화 도구를 함께 쓴다. 도구 선택은 팀에 맞게 평가하라고 한다.

#### 14.5 격리 (원서 10장 Tenant Isolation)

- **네임스페이스 간**: 온보딩 때 각 테넌트 네임스페이스에 **NetworkPolicy**를 붙여 다른 네임스페이스에서의 접근을 막는다(쿠버네티스 기본 수단).
- **사일로 저장소(배포 시점 격리)**: 테넌트별 테이블에 대한 접근 정책을 네임스페이스의 서비스 계정에 붙여(IRSA) 테넌트 서비스가 자기 테이블만 접근하게 한다. 개발자가 몰라도 적용된다.
- **풀 저장소(런타임 격리)**: 한 테이블에 여러 테넌트 데이터가 섞여 있으므로 요청마다 테넌트 컨텍스트를 확인해 **테넌트로 범위가 제한된 자격 증명**을 얻어 항목 수준 접근을 제한한다. 공유 라이브러리로 컨텍스트→정책→자격 획득을 개발자 시야 밖에서 처리하는 것이 이상적이다.
- **사이드카**(서비스 옆에서 트래픽을 가로채는 프록시 프로세스)로 격리를 중앙화할 수 있지만, 저장소 호출을 사이드카가 해야 하거나 자격 증명을 되돌려줘야 해서 아직 적용 방법을 더 다듬어야 한다고 저자는 말한다.
- 컨테이너 탈출(escape) 위험은 컨테이너 기반 전반의 보안 관심사이며 이 장 범위 밖이다.
- **노드 유형 선택**: CPU/메모리 집약, GPU 등 워크로드에 맞는 노드 그룹을 나눠 서비스를 매핑할 수 있다.

#### 14.6 서버리스(Lambda) 스택의 특징 (원서 11장)

- **적합성**: 테넌트 활동은 예측이 어려워 오토스케일링 정책을 짜고 과잉 프로비저닝하기 쉽다. 서버리스는 스케일링을 관리형 서비스에 맡기고 **실행한 만큼만 과금**해 소비를 활동에 가깝게 맞춘다. 배포 단위가 함수라 **영향 범위(blast radius)가 작고**, 함수 호출은 한 번에 한 테넌트라서 **테넌트별 소비 귀속과 텔레메트리**가 쉽다. 단, 장시간 작업 등에는 컨테이너가 나을 수 있어 모든 것을 서버리스로 할 필요는 없다.
- **논리적 마이크로서비스**: 서비스의 각 연산이 별도 함수이고, 서비스는 함수 묶음이다(함께 버전·배포·테스트).
- **사일로/풀**: 함수를 묶는 그룹 구조가 없어, 테넌트별로 함수 묶음을 **별도 배포**하고 **라우팅**으로 연결한다. 함수는 원래 호출마다 분리되지만 사일로 배포를 하는 이유는 (1) 동시성 한도 때문에 생기는 **노이지 네이버**를 티어별 동시성 정책으로 통제, (2) 배포 시점 격리 정책 부착이 쉬워짐 때문이다.
- **주의점 두 가지**: **콜드 스타트**(오래 안 쓴 함수의 첫 호출 지연; 풀에서는 미미하지만 한 테넌트만 쓰는 사일로에서는 두드러져 프리미엄 티어에 사전 초기화 동시성을 두기도 함) / **상태 잔존(state residue)**(재사용되는 함수 인스턴스에 이전 테넌트 상태가 남아 다음 테넌트 요청에 노출될 수 있으니 전역 상태를 쓰지 말고 종료 시 정리).
- **컨트롤 플레인 위치**: 대체로 계정 수준으로 결정. 별도 계정이면 경계가 확실하고 동시성 영향을 줄이지만 계정 간 접근 설정이 필요하고, 같은 계정이면 배포가 단순하지만 보안·동시성·격리를 감수한다.
- **운영 복잡도**: 함수·테넌트 복사본이 늘어 관리 단위가 잘게 쪼개지므로 서비스가 아닌 **함수 단위의 관측**이 필요하다.
- **라우팅**: API 게이트웨이 하나에 모든 테넌트 경로를 매핑(단순, 규모가 커지면 복잡) vs 배포별 게이트웨이(정책 세분화, 테넌트↔게이트웨이 매핑 필요·수천 테넌트에서는 비용/운영 부담).
- **온보딩·배포 자동화**: 서버리스용 도구(SAM 등)로 기본 템플릿 + 티어별 설정(예: 기본 티어는 사전 초기화 동시성 0, 프리미엄은 사용)을 정의. <strong>"테넌트↔스택 매핑 테이블"</strong>을 두고 풀은 첫 테넌트 때만 스택을 만들고 이후에는 설정만 추가, 사일로는 테넌트별 행을 둔다. 업데이트 때는 이 테이블을 순회해 모든 환경에 적용하며, 이 기록은 카나리/웨이브 배포에도 쓸 수 있다. 이런 추적을 직접 만들어야 한다고 원서는 지적한다.
- **풀 격리(동적 주입)**: API 게이트웨이의 authorizer가 요청에서 테넌트 컨텍스트를 뽑아 격리 정책으로 자격 증명을 만들고 헤더로 서비스에 주입한다. 서비스는 받은 자격 증명만 적용하면 되고, 게이트웨이에서 캐시해 지연을 줄일 수 있다. 단점은 정책이 서비스와 분리되어 소유·버전 관리가 어렵다고 느끼는 팀도 있다는 점이다. **사일로 함수**는 배포 시점에 격리 정책을 붙이면 되어 훨씬 쉽다.

> 🔗 NestJS 연결: NestJS를 컨테이너로 배포하는 경우 14.2~14.5가 그대로 적용된다(테넌트별 네임스페이스/설정, Ingress 서브도메인 라우팅). 서버리스 관점의 "요청 단위 테넌트 컨텍스트, 전역 상태 금지"는 NestJS에서도 `AsyncLocalStorage`/요청 스코프로 테넌트 컨텍스트를 관리하고 싱글턴에 테넌트 상태를 두지 않는 원칙과 통한다. (보충)
