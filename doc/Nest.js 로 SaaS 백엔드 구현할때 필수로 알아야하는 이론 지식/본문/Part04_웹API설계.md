# Part 4. 웹 API 설계 (REST) (출처: The Design of Web APIs, 2nd)

> **🎮 게임 서버 개발자에게** — REST API는 게임 서버의 "패킷 프로토콜 명세"에 해당합니다. 다만 opcode마다 구조체를 새로 정의하던 방식과 달리, REST는 **명사 URL(리소스) × 소수의 표준 메서드(GET/POST/PUT/PATCH/DELETE)** 조합으로 모든 기능을 표현하고, 메서드·상태코드의 의미가 표준이라 프록시·캐시·클라이언트 라이브러리가 그 의미를 보고 움직입니다. 결정적으로 **연결에 세션 상태가 붙지 않습니다(무상태)** — 매 요청이 토큰을 들고 오고 어느 서버가 받아도 처리해야 합니다. 또 게임 클라이언트처럼 강제 업데이트를 걸 수 없는 외부 고객이 붙으므로, 한 번 공개한 API는 "바꿀 수 없는 계약"이 됩니다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 결제 API의 응답이 네트워크에서 사라져 클라이언트가 재시도했더니 **이중 결제**가 났다.
> - 운영자 두 명이 같은 구독 정보를 동시에 수정했는데 **먼저 저장한 변경이 사라졌다**.
> - 응답 enum에 값 하나를 추가해 배포했을 뿐인데 **파트너사 연동이 깨졌다**는 문의가 들어온다.

## 코어 — 이것만은 100%

> **한 문장:** 공개한 API는 바꾸기 어려운 계약이므로, "리소스(명사) + 표준 메서드(동사)"의 균일한 규칙과 올바른 데이터 위치·상태코드·목적별 DTO로 처음부터 설계하고, 재시도·동시 수정·권한·긴 작업·이벤트 통지를 설계 단계에서 방어하며, 하위 호환 규칙과 OpenAPI 가이드라인으로 진화시킨다.

1. **균일한 인터페이스** — URL은 명사 컬렉션 + 식별자, 메서드의 의미(GET 안전, PUT/DELETE 멱등, POST/PATCH 비멱등)를 지키고, 식별자는 path·수정자는 query·내용은 body, 생성은 201 + Location. (REST 원칙, URL, 메서드, 데이터 위치, 상태코드, 행위 연산)
2. **계약으로서의 데이터** — 요청/응답 DTO를 목적별로 분리하고(서버 관리 값은 요청에서 받지 않음), 응답은 항상 객체로 감싸며, 에러는 Problem Details로 통일, 목록에는 필터·정렬·페이징(상한)을 처음부터. (DTO, Postel의 법칙, 목록, 에러)
3. **실패와 권한을 전제한 설계** — 재시도에 대비해 Idempotency-Key, 갱신 유실에 대비해 ETag + If-Match(412), 권한은 토큰의 사용자·테넌트와 입력을 항상 대조하고 존재를 숨길 땐 404. (멱등·동시성, 보안 설계)
4. **효율·긴 작업·통지** — 캐시와 데이터량 최적화로 호출 비용을 줄이고, 대량 작업은 오류 정책부터, 긴 작업은 202 Accepted + 작업 리소스(폴링/콜백), 외부 통지는 서명·재시도·멱등 수신을 갖춘 웹훅. (캐시, 데이터량, 대량, 비동기, 웹훅, 다른 통신 방식)
5. **진화** — 응답과 요청은 호환 판정 방향이 반대다. 버전 방식(`/v1`)을 처음부터 정하고, 깨는 변경은 OpenAPI diff를 CI에 넣어 막으며, 폐기는 `deprecated`와 `Sunset`으로 알린다. (하위 호환·버전, OpenAPI·가이드라인)

| 결과 패킷의 에러 코드 enum (`RESULT_NOT_ENOUGH_GOLD`) | HTTP 상태코드(2XX/4XX/5XX) + Problem Details 본문 | 성공/실패와 사유를 알린다 | 상태코드는 **표준 번호**라 첫 자리만으로 성격(누구 책임인지)을 알고, 클라이언트·게이트웨이가 재시도/로그아웃/캐시를 결정한다. 우리만의 번호를 만들지 않고 세부 사유는 본문(RFC 9457)에 담는다 → 코어 1·2 |
| 패킷 시퀀스 번호 / 중복 패킷 무시 | 멱등성 + `Idempotency-Key` | 재전송 때문에 같은 처리가 두 번 되는 것을 막는다 | TCP는 **한 연결 안**의 중복 세그먼트만 걸러 준다. 응답이 유실돼 클라이언트가 **새 연결로 같은 HTTP 요청을 다시 보내면** TCP는 그것이 중복인지 모른다. 그래서 애플리케이션이 키를 공유 저장소(DB·Redis)에 남겨 서버·연결을 넘어 중복을 판정해야 한다 → 코어 3 |
| 프로토콜 버전 체크 (클라 버전이 다르면 접속 거부 → 강제 업데이트) | API 버전(`/v1`)·하위 호환 규칙·`Sunset` | 클라이언트와 서버 사이의 계약이다 | 게임은 구버전 클라이언트를 강제 업데이트로 끊을 수 있지만, 공개 API의 소비자(파트너 서버)는 우리가 업데이트시킬 수 없다. 그래서 "깨지지 않게 바꾸는 규칙"과 폐기 예고가 필요하다 → 코어 5 |
| 서버 → 클라 푸시 패킷 (Notify) | 웹훅 / SSE / WebSocket | 서버가 먼저 알린다 | HTTP REST는 요청-응답뿐이라 서버가 먼저 말할 수 없다. 외부 고객에게는 **우리가 고객 서버 URL을 HTTP로 호출(웹훅)** 하고, 실패·중복 도착을 전제로 설계한다 → 코어 4 |

## 코어 1. 균일한 인터페이스 — 리소스 + 표준 메서드 + 표준 상태코드

> 게임 서버 프로토콜이 "opcode 표 + 패킷 구조체 정의서"라면, REST API의 프로토콜은 **"어떤 명사(URL)에 어떤 표준 동사(메서드)를 쓰고, 데이터는 어디(path/query/header/body)에 담고, 결과는 어떤 표준 번호(상태코드)로 알리는가"** 라는 하나의 균일한 규칙이다. 이 코어의 여섯 절은 모두 그 규칙의 한 조각이다.

### 1.1 REST 원칙과 API 설계의 기본 마음가짐

**한 줄 요약:** REST의 핵심은 "리소스(명사) + 표준 HTTP 메서드(동사)"라는 균일한 규칙과 무상태이고, 목표는 교과서적 REST가 아니라 쓰기 쉽고 안전하고 오래 유지되는 API다.

#### 1.1.1 REST는 "HTTP를 제대로 쓰는 스타일"

REST는 2000년 Roy Fielding이 정리한 아키텍처 스타일이다. 여섯 가지 제약이 있다.

| 제약 | 뜻 | API 설계에서의 의미 |
|---|---|---|
| 클라이언트/서버 분리 | 역할을 나눈다 | 서버 내부 구조(DB 테이블 등)를 밖에 노출하지 않는다 |
| 무상태(Stateless) | 요청마다 필요한 정보를 다 담는다 | 서버가 세션을 기억하지 않는다. 서버를 늘려도(스케일 아웃) 문제 없다 |
| 캐시(Cache) | 응답이 재사용 가능한지 알려준다 | `Cache-Control`, `ETag` 사용 |
| 계층형 시스템 | 클라이언트는 중간 장치(게이트웨이 등)를 모른다 | API 게이트웨이, 로드밸런서 뒤에 숨길 수 있다 |
| 균일한 인터페이스 | 리소스 + 표준 메서드로 다룬다 | `GET /users/1`, `DELETE /users/1` 같은 규칙 |
| 코드 온 디맨드(선택) | 서버가 코드를 내려줌 | REST API에서는 거의 안 씀 |

핵심은 **"리소스(명사) + 표준 HTTP 메서드(동사)"** 라는 균일한 규칙이다.

> 왜 중요한가: 규칙이 균일하면 개발자가 문서를 안 봐도 API를 "추측"해서 쓸 수 있다.
> 무상태는 SaaS의 수평 확장(서버 여러 대)의 전제 조건이다.

#### 1.1.2 "이게 진짜 REST냐" 논쟁은 피하자

- `POST /check-out` 같은 동사 경로도 HTTP 관점에서는 유효하다(아래 1.6절).
- 복수/단수 이름 논쟁은 REST 여부와 무관하다. **팀 안에서 하나로 통일**하는 게 중요하다.
- 목표는 "교과서적 REST"가 아니라 **쓰기 쉽고, 안전하고, 오래 유지되는 API**다.

#### 1.1.3 API 설계는 네 겹으로 나눠 생각한다 (원서 1.7)

한 번에 모든 걸 풀려 하지 말고 층별로 한 문제씩 다룬다.

| 층 | 핵심 질문 | 이 문서의 해당 부분 |
|---|---|---|
| 1. 다목적으로 "제 일을 하는" API | 화면·앱이 달라도 재사용되는가? 내부 구현(마이크로서비스 등)을 숨기는가? | 1.2~1.3절 (특정 UI에 묶지 않기) |
| 2. 쓰기 쉽고 상호운용되는 API | 이름이 명확한가? 오류 메시지가 조치 가능한가? 서비스마다 사용자 ID 종류가 다르지 않은가? | 2.1~2.4절 |
| 3. 제약을 반영한 API | 보안, 효율, 맥락(긴 작업 등), 변경(하위 호환) | 3.1~5.1절 |
| 4. 계속 개선되는 설계 과정 | 이름·페이징 같은 반복 결정을 가이드라인으로 일관되게 | 5.2절 |

- 원서 예시: 사용자 A가 B로 로그인했을 때 A의 DM이 보인 사고는 설계 때 "누가 무엇을 볼 수 있나"를 정하지 않아서 생기는 흔한 보안 결함이다. 한 번에 모든 데이터를 돌려주다 느려지거나 메모리 부족이 나는 것은 효율 설계 문제다. 영상에서 친구를 찾는 작업이 100ms 안에 못 끝나면 "작업 시작 → 상태 확인 → 결과 조회" 세 번 호출 구조(4.4절)로 바꾼다. `sts`를 `status`로 이름만 바꿔도 기존 앱이 깨진다(5.1절).
- 명명 규칙(`fromDate` vs `from_date`)이나 페이징 방식은 반복해서 나오는 결정이므로, 정해 두고 **가이드라인과 자동 검사**(5.2절)로 일관성을 지킨다.

> 🔗 NestJS 연결: 무상태 원칙 덕분에 Guard에서 JWT 같은 토큰으로 매 요청 인증하는 방식이 자연스럽다.

### 1.2 리소스와 URL(경로) 설계

**한 줄 요약:** 경로 하나는 사용자가 이해하는 개념(리소스) 하나를 가리키며, "컬렉션 + 요소" 패턴과 부모/자식 계층으로 짓고, 화면이 아니라 기능을 기준으로 설계한다.

#### 1.2.1 경로는 "무엇"을 가리키는 주소

- 경로(path) 하나는 리소스 하나를 식별한다.
- 경로는 DB 테이블 이름이 아니라 **사용자가 이해하는 개념**을 나타낸다.
- 약어·암호 같은 이름(`/xyz`, `/cat`)은 6개월 뒤 본인도 못 읽는다. 뜻이 분명한 이름을 쓴다.

#### 1.2.2 컬렉션 + 요소 패턴 (가장 널리 쓰이는 규칙)

```
GET    /products            상품 목록 (컬렉션)
POST   /products            상품 생성
GET    /products/{id}       상품 1건 조회 (요소)
PUT    /products/{id}       상품 교체
PATCH  /products/{id}       상품 일부 수정
DELETE /products/{id}       상품 삭제
```

- 컬렉션은 **요소 종류를 나타내는 명사**(보통 복수형)로 짓는다.
- 요소 경로 = 컬렉션 경로 + `/` + 식별자. 파일 시스템처럼 이어 붙이면 된다.
- 식별자는 **경로 매개변수(path parameter)** 로 둔다.

#### 1.2.3 계층으로 관계 표현

```
/merchants/{merchantId}/products/{productId}   → 특정 판매자의 상품
/accounts/{accountId}/transactions             → 특정 계좌의 거래 목록
```

- 앞쪽이 부모, 뒤쪽이 자식이다. **마지막 세그먼트가 그 리소스의 정체**다.
- 부모/자식 순서를 뒤집으면(`/{id}/catalog`) 읽기 어렵다.
- 짧은 경로가 읽기 좋다. 자식 ID가 전역 유일하면 상위 경로 없이 `/transactions/{id}`로 바로 접근하게 줄일 수 있다(원서 9.3.3). 반대로 `home`처럼 전역 유일하지 않은 ID(`/customers/{customerId}/addresses/{addressId}`)는 줄일 수 없다.
- (보충) "보통 2단계 정도"라는 깊이 기준은 원서에 없는 저자의 경험칙이다.

#### 1.2.4 경로 작성 팁

- 끝에 슬래시를 붙이지 않는다(`/products` O, `/products/` X). 라우팅 버그의 원인이다.
- (보충) 소문자와 하이픈(`kebab-case`)으로 통일한다(`/account-applications`). 원서 예시가 이런 형태이지만 명시적 규칙은 아니며, 복수/단수 중 하나로 일관되게 쓰라는 것이 원서의 핵심이다.
- 필수 정보(리소스 식별)는 경로, 선택 정보(필터)는 쿼리로 둔다(1.4절 참고).
- 경로 안에 필터를 넣지 않는다. `/products/book/design` 대신 `/products?type=book&q=design`.
- 필수 필터가 계속 붙는다면 경로에 넣어야 할 식별자일 수 있다. `GET /transactions?accountId=1` 대신 `GET /accounts/1/transactions`.

#### 1.2.5 UI 화면을 그대로 API로 만들지 말 것

"카테고리 화면"이 있다고 `/categories/{id}/products`를 만들 필요는 없다.
`GET /products?category=...` 하나로 충분할 때가 많다. **화면이 아니라 기능(capability)** 을 기준으로 설계한다.

> 왜 중요한가: URL은 한번 공개하면 바꾸기 매우 어렵다(클라이언트가 전부 깨진다). 처음 이름이 이후 몇 년을 좌우한다.

> 🔗 NestJS 연결: `@Controller('products')` + `@Get(':id')`. 모듈별로 컬렉션 하나를 담당하는 컨트롤러를 두면 URL 구조와 코드 구조가 일치한다.

> 📖 원문: 4.1~4.2, 9.3

### 1.3 HTTP 메서드로 행위 표현

**한 줄 요약:** 다섯 메서드는 각각 안전·멱등이라는 표준 의미를 갖고, 이 의미를 지켜야 재시도·캐시·프록시가 올바르게 동작한다(생성은 POST, 클라이언트가 ID를 정하면 PUT, 부분 수정은 PATCH + Merge Patch).

> C++ 서버에서 opcode의 의미는 우리 서버 코드만 알았다. HTTP 메서드의 의미는 **중간에 있는 남(브라우저, 크롤러, 프록시, 캐시, HTTP 클라이언트 라이브러리)도 안다.** 그래서 GET에 상태 변경을 넣으면 우리가 호출하지 않았는데도 그 연산이 반복 실행될 수 있다.

#### 1.3.1 다섯 가지 메서드

| 메서드 | 의미 | 대표 용도 | 안전(Safe) | 멱등(Idempotent) |
|---|---|---|---|---|
| GET | 읽기 | 조회, 검색, 다운로드 | O | O |
| POST | 처리/생성 | 생성, "그 외 모든 것" | X | X |
| PUT | 교체(전체) | 전체 수정, ID를 클라이언트가 정하는 생성 | X | O |
| PATCH | 부분 수정 | 일부 필드 수정 | X | X (구현에 따라) |
| DELETE | 삭제 | 삭제, 취소 | X | O |

- **안전(Safe)**: 서버 상태를 바꾸지 않는다. GET은 안전해야 한다. (로그 남기는 정도는 OK)
- **멱등(Idempotent)**: 같은 요청을 여러 번 보내도 서버 결과가 한 번 보낸 것과 같다.

> GET으로 데이터를 지우거나 바꾸는 API는 절대 만들지 않는다. 크롤러, 프리페치, 캐시가 GET을 마음대로 반복 호출한다.

#### 1.3.2 전형적인 CRUD 매핑

| 하고 싶은 일 | 요청 |
|---|---|
| 요소 생성 | `POST /elements` (기본 선택) |
| 목록/검색 | `GET /elements` |
| 1건 조회 | `GET /elements/{id}` |
| 수정 | `PUT` 또는 `PATCH /elements/{id}` |
| 삭제 | `DELETE /elements/{id}` |

#### 1.3.3 POST vs PUT (생성)

- `POST /products` : 서버가 ID를 만든다. 대부분의 생성은 이걸 쓴다.
- `PUT /products/{isbn}` : 클라이언트가 ID를 정한다(ISBN처럼 이미 전역 유일한 값일 때). 없으면 생성, 있으면 교체.
- `PUT /products`(컬렉션에 PUT)은 "전체 목록 교체"가 되어 버리므로 쓰지 않는다.

#### 1.3.4 PUT vs PATCH (수정)

- PUT은 리소스 **전체**를 보낸다. 빠진 필드는 "없는 값"이 된다. 구현이 단순하다.
- PATCH는 **바뀐 필드만** 보낸다. 네트워크와 실수 면에서 유리하다.
- PATCH 본문 형식은 **JSON Merge Patch(RFC 7396)** 가 가장 흔하고 이해하기 쉽다. 예: `{"price": 59.99}`
  - JSON Patch(RFC 6902)도 있지만 복잡하고 문서화가 어려워 권장하지 않는다.
- 주의: Merge Patch에서 배열은 통째로 교체된다. 배열이 크면 별도 하위 리소스로 분리하는 게 좋다.

```ts
// NestJS 예: 위 규칙을 그대로 옮긴 컨트롤러 뼈대
@Controller('products')
export class ProductsController {
  @Get()              list(@Query() q: ListProductsQuery) {}
  @Post()             create(@Body() dto: CreateProductDto) {}
  @Get(':id')         get(@Param('id') id: string) {}
  @Put(':id')         replace(@Param('id') id: string, @Body() dto: ReplaceProductDto) {}
  @Patch(':id')       update(@Param('id') id: string, @Body() dto: UpdateProductDto) {}
  @Delete(':id') @HttpCode(204) remove(@Param('id') id: string) {}
}
```

> 왜 중요한가: 메서드의 의미(안전/멱등)를 지켜야 재시도, 캐시, 프록시가 올바르게 동작한다.
> 특히 "멱등한 메서드는 실패 시 안전하게 재시도할 수 있다"는 점이 장애 대응의 기반이다.

> 🔗 NestJS 연결: `@Get/@Post/@Put/@Patch/@Delete` 데코레이터. `@nestjs/mapped-types`의 `PartialType`으로 PATCH용 DTO를 쉽게 만든다.

> 📖 원문: 4.3, 5.3.4, 13.5.6

### 1.4 입력 데이터는 어디에 담을까 (path / query / header / body)

**한 줄 요약:** 식별자는 경로, 표현(생성/수정 내용)은 본문, 수정자(필터·정렬·페이징)는 쿼리, 메타데이터(인증·형식·캐시)는 헤더에 둔다.

> 바이너리 패킷에서는 헤더(길이·opcode)와 페이로드 두 칸뿐이었다. HTTP 요청은 데이터를 둘 칸이 네 개이고, 칸마다 캐시·로그·프록시가 다르게 취급하므로 **어디에 두느냐 자체가 설계**다.

HTTP 요청에는 데이터를 담을 곳이 네 군데 있다.

| 위치 | 예 | 특징 |
|---|---|---|
| 경로 매개변수 | `/products/123` | 리소스 식별, 필수, 계층적 |
| 쿼리 매개변수 | `?type=BD&sort=price` | 비계층적 옵션, 순서 무관, 선택적 |
| 헤더 | `Accept: text/csv` | 메타데이터(인증, 형식, 캐시 등) |
| 본문(body) | `{ "name": "..." }` | POST/PUT/PATCH에서만. 리소스 내용 |

데이터의 성격별 규칙은 단순하다.

| 데이터 성격 | 위치 |
|---|---|
| 리소스 식별자 (어떤 리소스인가) | **경로** |
| 리소스 표현 (생성/수정할 내용) | **본문** |
| 리소스 수정자 (필터, 정렬, 페이징, 옵션) | **쿼리** (표준 헤더로 표현 가능하면 헤더) |

- GET / DELETE에는 본문을 쓰지 않는다(일부 서버·프록시가 무시한다).
- 인증 토큰은 `Authorization` 헤더에 둔다. **URL에 넣지 않는다**(3.2절 참고).

> 왜 중요한가: 위치를 잘못 잡으면 캐시가 안 되거나(GET 본문), 로그에 민감정보가 남거나, 필수/선택 구분이 무너진다.

> 🔗 NestJS 연결: `@Param()`, `@Query()`, `@Headers()`, `@Body()`. 각각 DTO + ValidationPipe로 검증한다.

> 📖 원문: 4.4

### 1.5 HTTP 상태코드 올바르게 쓰기

**한 줄 요약:** 상태코드는 첫 자리로 책임(2XX 성공 / 4XX 소비자 / 5XX 우리)을 알리는 표준 번호이며, 클라이언트는 이것으로 재시도·알림·로그아웃을 결정하므로 나만의 코드를 만들지 않고 상황별 표준 코드를 쓴다.

#### 1.5.1 상태코드 클래스

| 클래스 | 뜻 | 누구 책임? |
|---|---|---|
| 2XX | 성공 | - |
| 4XX | 클라이언트(소비자) 오류 | 요청한 쪽 |
| 5XX | 서버 오류 | 우리 쪽 |

모르는 코드가 와도 첫 자리만 보면 성격을 알 수 있다. 정의되지 않은 번호로 **나만의 상태코드를 만들지 않는다**.

#### 1.5.2 성공 코드

| 상황 | 코드 |
|---|---|
| 조회/검색 성공 | 200 OK (검색 결과가 0건이어도 **200 + 빈 목록**) |
| 생성 성공 | **201 Created** + `Location` 헤더 |
| 수정 성공 (수정된 리소스 반환) | 200 OK |
| 수정/삭제 성공 (반환할 것 없음) | 204 No Content |
| 나중에 처리할 작업을 접수 | 202 Accepted |

#### 1.5.3 오류 코드

| 상황 | 코드 |
|---|---|
| 잘못된 JSON, 필드 누락, 검증 실패 | 400 Bad Request (또는 422 Unprocessable Content) |
| 인증 실패 (토큰 없음/만료/틀림) | 401 Unauthorized |
| 인증됐지만 권한 없음 | 403 Forbidden |
| 리소스 없음 | 404 Not Found |
| 허용하지 않는 메서드 | 405 Method Not Allowed |
| 지원하지 않는 응답 형식(Accept) | 406 Not Acceptable |
| 충돌 (중복 요청, 상태 충돌) | 409 Conflict |
| 요청 본문 형식 미지원(Content-Type) | 415 Unsupported Media Type |
| 조건 불일치 (`If-Match` 실패) | 412 Precondition Failed |
| 요청 과다 (Rate limit) | 429 Too Many Requests |
| 예상 못한 서버 오류 | 500 Internal Server Error |
| 점검/과부하 | 503 Service Unavailable (`Retry-After` 헤더) |

실전 규칙:

- 입력을 받는 모든 연산은 **400 처리**를 갖춘다.
- 경로 매개변수가 있는 모든 연산은 **404 처리**를 갖춘다.
- 모든 연산은 **500 처리**를 갖춘다(단, 내부 정보는 숨긴다).
- `POST /transfers`에서 "출금 계좌가 없다"는 오류에 404를 쓰면 안 된다. 404는 `/transfers` 자체가 없다는 뜻이 된다. 400(또는 422)을 쓴다.
- 400 vs 422: 둘 다 괜찮다. 팀에서 하나로 통일한다.

> 왜 중요한가: 클라이언트는 상태코드로 재시도할지, 사용자에게 알릴지, 로그아웃할지를 결정한다. 잘못된 코드는 잘못된 동작으로 이어진다.

> 🔗 NestJS 연결: `@HttpCode(204)`, `HttpException`의 하위 클래스들(`NotFoundException`, `ConflictException` 등), `ValidationPipe`의 기본 400.

> 📖 원문: 4.5, 9.8.2

### 1.6 응답 데이터 위치와 "행위(do)" 연산 표현

**한 줄 요약:** 응답은 헤더 + 본문 두 곳뿐이며(생성은 201 + Location + 생성된 리소스), CRUD로 안 되는 행위는 행위 리소스·명사화·결과 리소스 세 방식 중 골라 표현한다.

#### 1.6.1 응답에서 데이터를 두는 곳

- 응답도 **헤더 + 본문** 두 곳뿐이다.
- 생성 성공(201)이면 본문에 **생성된 리소스**를, 헤더에 **`Location: /products/123`** 을 넣는다.
- 수정 성공(200)이면 본문에 수정된 리소스를 돌려준다.
- 삭제 성공은 보통 본문이 없다(204).
- 오류는 **항상 본문에 오류 정보**를 담는다(2.4절). HTTP 상태코드만으로는 오류 원인을 알려 주기에 부족하기 때문이다.
- 검색(GET)은 결과가 없어도 200과 **빈 목록**을 본문에 담아 돌려준다.
- 수정에서 200을 쓰기로 했다면 수정된 리소스를 본문에 담아야 하고, 본문 없이 끝내려면 204를 쓴다.
- 201 Created는 **Location 헤더에 생성된 리소스의 URL**을 담아야 한다. 본문에 데이터를 안 돌려주더라도 이 URL로 나중에 GET 할 수 있다.

**전형적 연산의 응답 위치 요약(원서 4.6.4)**

| 연산 | 성공 시 응답 |
|---|---|
| 조회(GET) | 본문에 요청한 리소스 |
| 검색(GET) | 본문에 찾은 목록 또는 빈 목록 |
| 생성(POST/PUT) | 본문에 생성된 리소스 + Location 헤더에 URL |
| 수정(PUT/PATCH) | 본문에 수정된 리소스 |
| 삭제(DELETE) | 아무것도 돌려주지 않음 |
| 오류 | 본문에 오류 정보 |

(생성·수정 응답에 무엇을 얼마나 돌려줄지 네트워크 효율 관점의 조정은 원서 13.5.2에서 다룬다 — 이 문서 4.2절.)

```
POST /products
→ 201 Created
  Location: /products/12345
  { "id": 12345, "name": "Cowboy Bebop", ... }
```

#### 1.6.2 CRUD로 안 되는 "행위" 연산

"체크아웃", "결제 승인", "메일 재발송"처럼 동사에 가까운 기능은 세 가지 방식이 있다.

| 방식 | 예 | 설명 |
|---|---|---|
| 행위 리소스 | `POST /carts/{id}/check-out` | 함수 호출처럼 POST. HTTP상 유효함 |
| 행위를 명사로 | `POST /checkouts` | "체크아웃"을 하나의 개념으로 승격. 조회·검색·이력도 가능 |
| 결과를 리소스로 | `POST /orders` | 결과물(주문)을 만드는 것으로 표현 |

- 행위 리소스가 "비REST"라는 오해가 있지만, 원서는 RFC 9110을 근거로 HTTP 리소스가 업무 개념이든 프로세스든 행위든 될 수 있다고 설명한다. 그래서 `POST /check-out`도 REST API에서 유효하다. 행위 리소스는 무언가를 생성하지 않는 일시적 처리(예: 숫자 두 개를 받아 합을 200으로 돌려주는 `POST /sum`)에도 쓸 수 있다.
- 저자 본인은 행위 리소스도 도구 상자에 두되, 확장 여지가 커서 대체로 명사형 리소스로 바꿔 설계한다고 한다. 긴 처리(장기 작업)는 명사로 바꾸면 다루기 좋다(4.4절, 원서 14.7).
- 행위 리소스는 경로에 업무 개념과의 관계를 드러내는 편이 좋다(메서드와 클래스의 관계처럼). 카트가 여러 개라면 `POST /carts/{id}/check-out`.
- 동사를 명사로 바꾸기 어렵다면 `-ing`, `-ment`, `-tion` 등을 붙여 본다(execute → executions).
- 명사로 승격하면 나중에 "목록 조회", "상태 확인", "비동기 처리"(4.4절)로 확장하기 쉽다.
- 실무에서는 `POST /payments/{id}/refund` 같은 행위 리소스도 자주 쓴다. 팀 규칙으로 통일하면 된다.

> 왜 중요한가: SaaS에는 결제, 초대, 구독 해지 같은 "행위"가 많다. 억지로 PUT으로 상태만 바꾸게 하면 의미가 흐려진다.

> 📖 원문: 4.6, 4.7

## 코어 2. 계약으로서의 데이터 — DTO, 목록, 에러

> 게임 서버에서는 패킷 구조체를 바꾸면 클라이언트와 서버를 같이 빌드해 배포했다. 공개 API의 요청·응답 JSON은 **우리가 다시 빌드시킬 수 없는 외부 코드가 파싱하는 구조체**다. 그래서 모델을 목적별로 나누고, 처음부터 확장 가능한 모양(객체로 감싸기, `{ data, metadata }`, 표준 에러 형식)으로 정한다.

### 2.1 요청/응답 데이터 모델(DTO) 설계

**한 줄 요약:** 같은 리소스라도 요청용 모델과 응답용 모델은 다르므로 목적별 모델(7종)을 두고, 서버 관리 값은 요청에서 받지 않으며, 값은 표준 형식(ISO 8601, 값+통화, 읽을 수 있는 코드)으로 표현한다.

같은 리소스라도 **요청용 모델과 응답용 모델은 다르다**. 하나를 억지로 재사용하지 말고, 목적별 모델을 둔다.

#### 2.1.1 일곱 가지 전형적 모델

| 모델 | 용도 | 내용 |
|---|---|---|
| Complete (완전) | 생성/조회/수정의 응답, 목록 요소 | 리소스의 모든 속성 + ID |
| Summarized (요약) | 목록 응답(선택), 다른 리소스에 포함 | 의미 있는 핵심 속성만 |
| Minimal (최소) | 다른 리소스에 포함, 생성 응답(옵션) | ID만 |
| Identifier (식별자) | 경로 매개변수 | ID 값 |
| Creation (생성) | POST 본문 | 클라이언트가 줘야 하는 속성만 (ID, 생성일 등 서버 관리 값 제외) |
| Replacement (교체) | PUT 본문 | 보통 Creation과 같음 |
| Modification (수정) | PATCH 본문 | Creation과 같지만 **모든 속성이 선택** |

- 원서(9.5.2)는 목록에서도 소비자가 결국 필요로 하는 정보가 많으면 요약이나 최소 모델보다 **완전 모델**이 낫다고 하고, 생성·수정 응답은 서버가 채운 값(실행일 등)을 소비자가 알아야 하므로 ID만이 아니라 **완전한 리소스**를 돌려주길 권한다. 최소 모델 응답은 13.5.2의 `Prefer` 옵션으로 고르게 한다(이 문서 4.2절).
- 원서 5.4.1은 Complete/Summarized/Minimal/Identifier 4종과 Creation/Replacement/Modification 3종을 소개한다.

```ts
// Complete → Creation → Modification 파생 예
class ProductDto {            // 응답용(Complete)
  id: number; name: string; price: number; createdAt: string; supplier: { code: string; name: string };
}
class CreateProductDto {      // 서버가 만드는 id, createdAt, supplier.name 제외
  name: string; price: number; supplierCode: string;
}
class UpdateProductDto extends PartialType(CreateProductDto) {} // 모두 선택
```

- 수정 후 바꿀 수 없는 필드(예: 공급자)가 있다면 수정 모델에서 뺀다.
- **서버 관리 값(id, createdAt, role 등)을 요청에서 받지 않는다.** 클라이언트가 임의로 넣으면 권한 상승(mass assignment) 사고가 난다.

> 게임 서버에서 "클라이언트가 보낸 골드량·레벨을 그대로 믿지 않는다"는 원칙과 같다. 요청 DTO에 `role` 필드가 있으면 클라이언트가 자기 권한을 써 넣을 수 있다.

#### 2.1.2 응답 본문은 항상 객체로 감싼다

- 응답이 배열(`[...]`)이면 나중에 페이지 정보를 추가할 때 **계약이 깨진다**.
- 처음부터 `{ "data": [...], "metadata": {...} }` 형태로 시작한다(2.3절 참고).

#### 2.1.3 값 표현 규칙 (자주 나는 실수)

| 항목 | 권장 | 피할 것 |
|---|---|---|
| 날짜/시간 | ISO 8601 문자열, UTC (`2024-03-10T14:10:00Z`), 날짜만이면 `2024-03-10` | 단위가 헷갈리는 Unix timestamp (초 vs 밀리초) |
| 금액 | 숫자 + 통화 분리 (`{ "value": 1234.5, "currency": "EUR" }`) | `"1,234.5"`처럼 포맷된 문자열 |
| 코드값 | 사람이 읽을 수 있는 값 (`"checking"`) 또는 코드 + 라벨 | 의미 모를 `1`, `7`, `xbt` |
| 식별자 | 짧고 안정적인 표준 ID | 변경 가능한 값, 민감 정보(주민번호 등) |
| 기간 | ISO 8601 duration (`P1M`) | `"MONTHLY"` 같은 확장 어려운 고정값 |
| 그룹 | 관련 값은 객체로 묶기 (`overdraft: { active, limit }`) | 접두어 붙은 평평한 속성 나열 |

- (보충) **돈은 부동소수점 계산에 주의**한다. 서버 내부는 정수(센트 단위)나 Decimal을 쓰고, API에는 단위를 명확히 문서화한다. 원서에는 없는 일반 관행이며, 원서는 단위 혼동(센트 vs 달러가 15.2.2에서 사고로 이어짐)만 경고한다.
- 이름은 팀 전체에서 일관되게(`createdAt`으로 정했으면 어디서나 `createdAt`).
- 응답 속성명은 번역하지 않는다. 번역은 **사람이 읽는 값**(라벨)에만 적용한다.

#### 2.1.4 연산별 입력·출력 모델 잡는 요령 (원서 5.3)

- **출력 모델을 먼저 정하고 입력을 뒤에 정한다.** 대부분 입력 데이터는 출력의 일부와 같기 때문이다.
- **조회(GET /products/{productReference})**: 경로 변수 이름을 모델 속성 이름(`productReference`)과 맞춘다. 문서에 그대로 보이므로 소비자가 데이터 조각을 쉽게 연결한다. 응답에서 `required`인 속성은 **항상 반환**, 아닌 속성은 없을 수도 있다는 뜻이다. 이를 구현·테스트가 알고 있어야 하고 소비자도 알아야 한다.
- **검색(GET /products)**: 목록 요소는 리소스의 **요약 모델**(목록에서 필요한 핵심만)을 쓴다. 목록에 데이터가 너무 적거나 많으면 호출 수 증가·데이터량 증가로 효율이 떨어진다. 필터(`?keywords=anime&category=BD`)는 반환 모델의 속성에 맞춰 설계하고, 모델에 없는 값(예: 원산지)으로는 필터할 수 없으므로 필요하면 속성을 추가한다. 입출력이 반드시 대칭일 필요는 없지만 대칭이면 쓰기 쉽다.
- **생성(POST /products)**: 입력은 **생성 모델**(서버가 만드는 `productReference`, `dateAdded` 등은 제외), 응답의 URL은 표준 `Location` 헤더. 성능을 위해 응답에 ID만 담은 최소 모델을 쓸 수도 있다.

#### 2.1.5 "바로 쓸 수 있는" 데이터로 만들기 (원서 8.4)

- **단순하되 유용하게**: 은행 계좌에 잔액이 여러 종류라면 전부 노출하면 다재다능하지만 소비자가 골라야 한다. 소비자가 비전문가이거나 다중 잔액 유스케이스가 없으면 가장 흔한 하나만 두거나, 전부 두되 기본값 플래그(`default`)를 준다. 단, 단순함을 위해 필요한 능력까지 잘라내진 않는다.
- **해석용 보조 데이터를 함께**: `balance: 123`만으로는 무슨 통화인지 알 수 없다. `currency`를 곁들인다.
- **가공된 데이터로 소비자 일을 줄인다**: "쓸 수 있는 금액(safe to spend)" 같은 값을 서버가 계산해 주면 소비자가 마이너스 통장 한도를 더할지 뺄지 등 **우리 비즈니스 규칙을 직접 구현하다 틀리는 것**을 막는다.
- **표준 식별자·값을 우선**: 내부 UUID보다 널리 알려진 계좌번호, 그보다 국제 표준(IBAN)이 외부 시스템 연동에 유리하다(보안 이유가 없다면). 통화도 내부 코드(`UD`) 대신 ISO 4217(`USD`). 대상이 넓을수록 좋고, 표준이 없으면 공유되는 정보를 쓴다.
- **문자열로 만들지 말 것 / 만들 것**: 계산에 쓰는 숫자는 포맷하지 않는다(`"1,234.5"` 금지). 반대로 앞자리 0이 의미 있는 계좌번호 `"0001234567"` 같은 참조·코드는 문자열이 낫다. 화면 표시용 로케일 포맷(프랑스는 `1 234,5`)은 소비자 몫이다.
- **암호 같은 코드값 금지**: `1`, `7`, `xbt` 대신 `"checking"`, `"savings"`. 여러 시스템이 쓰는 코드라 못 바꾸면 `typeLabel` 같은 라벨을 옆에 두거나 `{code, label}` 객체로 만든다.
- **날짜는 ISO 8601**: 타임스탬프는 초/밀리초 단위가 헷갈린다(Unix time은 초, JavaScript `Date.now()`는 밀리초). 시간대 오프셋(`+01:00`)도 표현되지만 기본은 UTC를 권장(서머타임 영향 없음), 규제·감사 등 특별한 이유가 있을 때만 오프셋을 쓴다. 기간은 `P2Y3M5DT11H30M5S` 형식.

#### 2.1.6 데이터를 정리해서 보여 주기 (원서 8.6)

- **객체로 묶기**: `overdraftFacility: true`와 `limit: 100`이 흩어져 있으면 관계를 알기 어렵다. `overdraftFacility: { active, limit }`로 묶는다. 금액도 `{ amount, currency }` 객체로 만들어 통화 짝을 명확히 한다.
- 지나치게 하위 객체로 쪼개지 않는다. 하위 객체는 **업무 개념**을 나타내야 하고 재사용 가능한 것이 좋다. UI 구성을 그대로 따라 하지 않는다(1.2.5절).
- **배열로 묶기**: `value1..valueN`, `line1..line4` 같은 이름은 `values`, `lines` 배열로. 종류가 다른 두 잔액은 `balances` 배열에 `type`을 붙여 담는다.
- **정렬**: 배열의 순서는 JSON Schema로 표현할 수 없으므로 `description`에 "type 순으로: value-date, expected"처럼 적는다. 객체 속성 순서는 코드엔 영향이 없지만 문서·확인 편의를 위해 관련된 것끼리 붙이고 중요한 것을 앞에 둔다.

> 왜 중요한가: DTO는 API 계약 그 자체다. 잘못 설계한 모델은 나중에 "하위 호환을 깨야만 고칠 수 있는 버그"가 된다.

> 🔗 NestJS 연결: 요청 DTO는 `class-validator` + `ValidationPipe({ whitelist: true, forbidNonWhitelisted: false })`로 검증하고 모르는 필드는 무시(whitelist)한다. 응답 DTO는 `ClassSerializerInterceptor` + `@Exclude()`/`@Expose()`로 내부 필드를 차단한다.

> 📖 원문: 5.3, 5.4, 8.4~8.5, 15.6.3

### 2.2 응답 설계 원칙: 관대하게 받고, 보수적으로 돌려주기

**한 줄 요약:** Postel의 법칙 — 받을 때는 너그럽게(모르는 필드 무시, 여러 날짜 형식 수용), 줄 때는 엄격하게(UTC 통일, 0건도 200 + 빈 목록).

Postel의 법칙: **받을 때는 너그럽게, 줄 때는 엄격하게.**

- 수정 요청에 읽기 응답을 그대로 돌려 보냈다면(`id`, `createdAt` 포함) 400을 내지 말고 **모르는/수정 불가 필드는 무시**한다.
- 날짜는 여러 형식(`+09:00`, 날짜만)을 받아 주고, 응답은 항상 UTC로 통일한다.
- 검색 결과가 없는 것은 오류가 아니다. `200 + 빈 목록`이 클라이언트 코드를 더 단순하게 만든다.
- 필수 입력은 최소화한다. 기본값을 줄 수 있으면 선택 입력으로 만든다.
- 성공 응답에는 클라이언트가 바로 쓸 수 있는 정보를 충분히 담는다(생성 결과의 ID, 상태 등).

> 📖 원문: 9.5, 9.8.1

### 2.3 목록 API: 필터링·정렬·페이징

**한 줄 요약:** 목록 API에는 처음부터 필터·정렬·페이징(크기 상한 필수)을 갖추고, 응답은 `{ data, metadata }`로 감싸 적용된 기본값까지 알려 준다.

목록 API는 SaaS에서 가장 많이 호출되는 API 중 하나다. **처음부터 세 가지를 모두 준비**한다.

#### 2.3.1 필터링

```
GET /accounts/12345/transactions?category=restaurant&amount.gte=100&amount.lt=400
```

- 필터 이름은 **응답 데이터의 속성 이름과 맞춘다**. 응답에 없는 값으로는 필터링하지 않는다.
- 필터는 모두 **선택**이다. 안 주면 "전체"다.
- 유연하게 만든다.
  - 여러 값: `category=restaurant,bar`
  - 범위: `amount.gte=100&amount.lt=400`, 또는 `from/to`
  - 자유 검색: `q=...` (복잡한 문법은 발명하지 말고 검색엔진 문법을 쓴다)
- 필터를 너무 많이 만들지 않는다. 실제 필요한 것만.
- 민감한 값은 쿼리에 넣지 않는다(3.2절).

#### 2.3.2 정렬

```
GET /transactions?sort=date:desc,amount:asc
```

- 정렬도 선택으로 두고, **쓸모 있는 기본값**을 정한다(예: 최신순).
- 방향을 생략하면 오름차순(asc)으로 간주하면 쓰기 쉽다.

#### 2.3.3 페이징

| 방식 | 요청 예 | 장점 | 단점 |
|---|---|---|---|
| 오프셋/인덱스 | `?page=3&size=10` | 구현 간단, 특정 페이지로 점프 가능 | 뒤 페이지일수록 느림, 도중에 데이터가 바뀌면 중복/누락 |
| 커서 | `?after=cursor123&size=25` | 대용량에서 빠름, 데이터 변경에 강함 | 다음/이전만 가능, 정렬 기준이 고유·순차 값이어야 함 |

- **페이지 크기 상한을 반드시 둔다**(예: 최대 100). 전체를 한 번에 주면 서버 메모리·비용이 폭발한다.
- 기본 크기와 최소 크기(1)도 정한다.
- 대용량이거나 무한 스크롤이면 커서 방식을, 관리자 화면처럼 페이지 번호 점프가 필요하면 오프셋 방식을 쓴다.
- 커서는 클라이언트가 해석하지 않는 **불투명 문자열**로 준다.

> 게임 서버에서 랭킹·우편함 목록을 패킷 하나에 통째로 실어 보내지 않고 나눠 보내던 것과 같은 이유다. 다만 HTTP에서는 서버가 연결에 "현재 몇 번째 페이지인지"를 기억하지 않으므로(무상태), 다음 위치(페이지 번호나 커서)를 **클라이언트가 매 요청에 들고 와야** 한다.

#### 2.3.4 목록 응답 형태와 메타데이터

```json
{
  "data": [ { "id": 1, "..." : "..." } ],
  "metadata": {
    "pagination": { "page": 1, "size": 40, "last": 10, "elements": 398 },
    "sort": [ { "name": "date", "direction": "desc" } ],
    "filters": [ { "name": "category", "enum": ["restaurant", "bar"] } ]
  }
}
```

- 실제 데이터(`data`)와 목록에 대한 정보(`metadata`)를 분리한다.
- 사용자가 값을 안 줬을 때 **어떤 기본값이 적용됐는지** 응답에 알려준다.
- 쿼리 URL이 너무 길어질 만큼 조건이 복잡하면 `POST /.../search`를 쓴다(3.2절).

```ts
// NestJS 예: 페이징 쿼리 DTO
class ListQuery {
  @IsOptional() @Type(() => Number) @Min(1) page = 1;
  @IsOptional() @Type(() => Number) @Min(1) @Max(100) size = 20;
  @IsOptional() @IsString() sort?: string;      // 예: "createdAt:desc"
}
```

> 왜 중요한가: 페이징 상한이 없는 목록 API는 곧 장애 원인이 된다. 또한 정렬 기준과 페이징 방식은 DB 인덱스 설계와 맞물려 있다.

> 🔗 NestJS 연결: `@Query()` + DTO(`class-transformer`의 `@Type`)로 숫자 변환·범위 검증. 응답 포맷은 Interceptor로 `{ data, metadata }`를 일괄 적용할 수 있다.

> 📖 원문: 9.6, 13.6

### 2.4 에러 응답 표준화

**한 줄 요약:** 에러는 알맞은 상태코드 + 사람이 조치할 수 있는 메시지 + 기계 판독 정보를 모든 오류 한 번에, 표준 형식(Problem Details, RFC 9457)으로 주고, 500에는 내부 정보를 숨긴다.

#### 2.4.1 좋은 에러 응답의 조건

1. 알맞은 **HTTP 상태코드**를 쓴다.
2. 사람이 읽고 **문제를 해결할 수 있는 메시지**를 준다. ("Unsupported JPY currency"보다 "Unsupported JPY currency; amount currency must be EUR or USD")
3. 프로그램이 처리할 수 있는 **기계 판독용 정보**(오류 유형, 위치, 허용 값)를 준다.
4. **가능한 모든 오류를 한 번에** 알려준다(하나 고치면 다음 오류가 나오는 경험은 최악이다).
5. 표준 형식을 쓴다.

#### 2.4.2 표준: Problem Details for HTTP APIs (RFC 9457)

`Content-Type: application/problem+json`

```json
{
  "status": 422,
  "type": "https://api.example.com/errors/validation",
  "title": "The request is not valid",
  "detail": "Missing destination and unsupported currency",
  "instance": "/errors/8f3a1c",
  "errors": [
    { "type": "https://api.example.com/errors/required",
      "detail": "Destination account is missing",
      "source": { "location": "body", "name": "destination", "pointer": "#/destination" } },
    { "type": "https://api.example.com/errors/invalid-value",
      "detail": "Currency must be EUR or USD",
      "source": { "location": "body", "name": "currency", "pointer": "#/amount/currency" },
      "values": ["EUR", "USD"] }
  ]
}
```

| 필드 | 의미 |
|---|---|
| `status` | HTTP 상태코드 |
| `type` | 오류 종류를 식별하는 URI (같은 종류는 항상 같은 값) |
| `title` | 오류 종류의 짧은 설명 (항상 동일) |
| `detail` | 이번 발생 건의 구체적 설명 |
| `instance` | 이번 발생 건의 참조 식별자 (로그 추적용) |
| `errors` (확장) | 필드별 상세 오류 목록 |

#### 2.4.3 보안과 에러

- **500 에러에 내부 정보(DB 종류, IP, 스택트레이스)를 넣지 않는다.** 대신 추적용 참조 번호만 준다.
- 401: 토큰 없음/만료/잘못됨. 403: 인증은 됐지만 권한 없음(권한을 요청하면 해결 가능한 경우).
- **리소스 존재 자체를 숨기고 싶으면 403 대신 404**를 준다. (다른 테넌트의 주문 ID로 조회했을 때 "없음"으로 응답)
- 400 vs 422, 에러 코드 이름 등은 한 번 정해서 모든 API에서 동일하게 쓴다.

> 왜 중요한가: 에러 형식이 제각각이면 프론트엔드가 모든 API마다 다른 에러 처리 코드를 짜야 한다. 그리고 500에 내부 정보가 새면 공격 단서가 된다.

> 🔗 NestJS 연결: 전역 **Exception Filter**(`@Catch()`)에서 모든 예외를 Problem Details 형태로 변환한다. `ValidationPipe`의 `exceptionFactory`로 필드별 오류 목록을 만든다. 500은 Filter에서 로깅만 하고 일반 메시지로 바꾼다.

> 📖 원문: 9.8, 12.10

## 코어 3. 실패와 권한을 전제한 설계 — 멱등·동시성·보안

> 게임 서버에서는 한 유저의 요청이 보통 한 세션(한 연결)을 통해 순서대로 들어왔고, TCP가 연결 안의 재전송·중복을 처리해 줬다. HTTP API에서는 **같은 요청이 다른 연결, 다른 서버 인스턴스로 다시 들어올 수 있고**, 여러 사용자가 같은 리소스를 동시에 고친다. 또 "로그인한 세션이니 이 유저 데이터"라는 연결 단위 신뢰가 없으므로, 매 요청마다 토큰의 사용자·테넌트와 입력을 대조해야 한다.

### 3.1 멱등성·안전성·동시 수정 방어 (데이터 정합성)

**한 줄 요약:** 네트워크는 끊기고 클라이언트는 재시도하므로, 중복 요청은 Idempotency-Key(→ 409 또는 이전 응답 재생)로, 갱신 유실은 ETag + If-Match(→ 412)로 설계 단계에서 막는다.

#### 3.1.1 왜 문제인가

네트워크는 끊긴다. 클라이언트는 응답을 못 받으면 **재시도**한다. 이때 서버는 이미 처리했을 수 있다.

- 결제 POST를 재시도 → **이중 결제**
- 두 사용자가 같은 데이터를 읽고 각각 수정 → **나중 저장이 먼저 저장을 덮어씀**(갱신 유실)

> (보충) TCP의 시퀀스 번호와 재전송은 **한 연결 안에서** 바이트가 빠짐없이 순서대로 한 번씩 전달되게 할 뿐이다. 요청은 서버에 도착해 처리됐는데 응답이 오는 길에 연결이 끊기면, 클라이언트(또는 HTTP 클라이언트 라이브러리·게이트웨이)는 **새 연결을 열어 같은 요청을 다시 보낸다.** 이 두 번째 요청은 TCP 입장에서 완전히 새 데이터이므로, 중복 여부는 애플리케이션이 판정해야 한다.

#### 3.1.2 메서드별 재시도 안전성

| 메서드 | 안전 | 멱등 | 재시도 |
|---|---|---|---|
| GET | O | O | 안전 |
| DELETE | X | O | 결과 상태는 같다(두 번째는 404일 수 있음) |
| PUT | X | O | 상태는 같지만, 그 사이 다른 수정이 있었다면 덮어쓸 위험 |
| POST | X | X | **위험** (중복 생성) |
| PATCH | X | 보통 X | **위험** |

구현도 이 성질을 지켜야 한다. "DELETE인데 실행할 때마다 카운터를 증가"시키면 멱등이 깨진다.

#### 3.1.3 중복 요청 방지: Idempotency-Key

클라이언트가 요청마다 고유한 키(UUID)를 헤더에 담아 보낸다.

```
POST /payments
Idempotency-Key: 3b5c8f1e-9a2d-4f6b-8c70-1d2e3f4a5b6c
```

원서가 설명하는 서버 동작은 단순하다. 같은 식별자로 이미 요청이 온 적이 있는지 확인하고, 있으면 **다시 처리하지 않고 409 Conflict**를 돌려준다. 헤더 이름은 IETF 초안이 `Idempotency-Key`를 제안하며, `Transaction-Id`나 `Request-Unique-Id` 같은 이름도 가능하다고 본다. POST뿐 아니라 PATCH, PUT에도 쓸 수 있다.

> 💡 보충(원서 외): 아래 내용은 원서가 아니라 실무 관행이다. 원서는 "키가 이미 있으면 409"까지만 말한다.
> - 이미 처리한 키에는 409 대신 **저장해 둔 이전 응답을 그대로 재생**하는 방식도 많이 쓴다(재시도한 클라이언트가 성공 응답을 받을 수 있다).
> - 처리 중인 키는 409로 거절하거나 대기시킨다.
> - 키는 일정 기간(예: 24시간) 뒤 만료시킨다.

```ts
// (보충) 개념 코드. 원서에는 없는 예시 (NestJS Interceptor 또는 서비스 계층에서)
const key = req.header('Idempotency-Key');
if (!key) throw new BadRequestException('Idempotency-Key required');
const saved = await store.get(key);                 // Redis 등, TTL 24h
if (saved) return saved.response;                   // 재처리 없이 이전 결과 반환
const result = await this.payments.create(dto);
await store.set(key, { response: result }, 86400);  // 성공 결과 저장
return result;
```

추가로 **업무 규칙 기반 중복 감지**도 가능하다(원서 12.5.3). 재시도할 때마다 새 키를 만들면 서버는 별개 요청으로 본다. 그래서 최근 1분 안에 금액·출금·입금이 같은 이체가 오면 409로 막고, 정말 의도한 반복이면 `Confirm-Duplicate: true` 헤더로 강제하게 한다. 차단 기간은 상황에 따라 다르다.

> 💡 보충(원서 외): 위 코드는 "조회 후 저장" 순서라서 동시 요청 두 개가 모두 통과할 수 있다. 키 확인과 저장은 **원자적으로** 이뤄져야 한다(DB 유니크 제약, Redis `SET NX` 등). 이 원자성 이야기는 원서에 없는 저자 보충이다.

> 멀티스레드 C++ 서버의 "check-then-act" 경쟁 조건과 똑같은 버그다. 다만 여기서는 같은 프로세스의 mutex로 막을 수 없다. 두 요청이 **서로 다른 서버 인스턴스**에서 처리될 수 있으므로, 원자성은 모든 인스턴스가 공유하는 저장소(DB 유니크 제약, Redis `SET NX`)에서 확보해야 한다.

#### 3.1.4 갱신 유실 방지: ETag + If-Match (낙관적 잠금)

```
GET /owners/123
→ 200 OK
  ETag: "z567dff"
  { ... }

PUT /owners/123
If-Match: "z567dff"           ← "내가 읽은 버전 그대로일 때만 수정해라"
→ 200 OK                       (버전 일치)
→ 412 Precondition Failed      (그 사이 누가 바꿨음 → 다시 읽고 재시도)
```

- ETag는 리소스 버전을 나타내는 값이다(해시, 버전 번호, 수정 시각 기반 등 구현 자유).
- (보충) DB에서는 `version` 컬럼(낙관적 잠금)과 자연스럽게 연결된다.
- 모든 PUT/PATCH를 조건부로 강제하려면 `If-Match`를 필수로 정의한다(도입 시 기존 클라이언트가 깨지므로 처음부터 정하는 편이 좋다).
- 원서는 대안으로 `Last-Modified` 헤더와 `If-Unmodified-Since` 요청 헤더(날짜 기반)도 언급한다. 모든 PUT/PATCH를 안전하게 하려면 OpenAPI에서 `If-Match`(또는 `If-Unmodified-Since`)를 필수 헤더로 표시하는 것을 고려하라고 한다.
- 조건부 갱신을 뒤늦게 필수로 바꾸면 기존 클라이언트가 수정을 전혀 못 하게 된다(원서 15.2.2).

> 💡 보충(원서 외): `If-Match`가 빠진 요청을 **428 Precondition Required**로 거절하는 것은 원서에 나오지 않는 HTTP 관행이다. 원서는 필수 헤더로 표시하는 것까지만 말하고 428은 언급하지 않는다.

> 비유하자면 compare-and-swap(CAS)이다. "내가 읽은 값(버전)이 아직 그대로면 바꿔라, 아니면 실패". 차이점은 기대값(ETag)을 **클라이언트가 들고 다니다가** 요청에 실어 보낸다는 것, 그리고 실패(412)하면 서버가 대신 재시도하지 않고 클라이언트가 다시 읽어 사용자에게 충돌을 보여 줄지 판단한다는 것이다.

> 왜 중요한가: 결제, 주문, 구독 변경 같은 SaaS 핵심 기능에서 중복 처리와 갱신 유실은 곧 **돈과 데이터 손실**이다. 방어책은 설계 단계에서 넣어야 한다.

> 🔗 NestJS 연결: Idempotency-Key는 **Interceptor**나 Guard + Redis로 공통 처리, 낙관적 잠금은 TypeORM `@VersionColumn` / Prisma 버전 필드와 `If-Match` 헤더를 조합한다.

> 📖 원문: 12.5, 4.3.1

### 3.2 보안 관점의 API 설계 (간단히)

**한 줄 요약:** URL에는 민감정보를 넣지 않고, 목록·조회는 항상 토큰의 사용자·테넌트와 입력을 대조하며(IDOR 방지), 스코프로 앱의 호출 범위를 최소화하고, 401/403/404/500을 존재 은닉까지 고려해 구분한다.

인증(Authentication)과 인가(Authorization) 구현은 [Part 5](Part05_API보안기본.md)·[Part 6](Part06_API보안심화.md)에서 다루고, 여기서는 **API 설계 차원**에서 꼭 지킬 것만 정리한다.

#### 3.2.1 URL에는 민감정보를 넣지 않는다

URL(경로+쿼리)은 브라우저 기록, 프록시, API 게이트웨이, 서버 로그 등 곳곳에 남는다. HTTPS도 이것을 막아주지 않는다.

- 비밀번호, 토큰, 주민번호, 이름·이메일 같은 개인정보로 `GET ?email=...` 검색을 하지 않는다.
- 민감한 검색은 **`POST /holders/search`** 처럼 본문에 담는다. (검색 결과 조회이므로 "REST 아니다"라는 반론은 무시해도 된다.)
- 민감 값을 리소스 ID로 쓰지 않는다. 내부 ID를 쓰고, 민감 값은 검색 엔드포인트로 찾게 한다.

#### 3.2.2 "누가 무엇을 볼 수 있나"를 설계에 반영

- 목록 API는 호출자에 따라 **자기 권한 범위의 데이터만** 돌려줘야 한다. (사용자는 자기 테넌트/자기 계좌만)
- ID가 UUID처럼 추측하기 어려워도 보안이 아니다. 항상 **토큰의 사용자·테넌트 정보와 요청 입력을 대조**한다. (IDOR 방지)
- 권한별로 응답 필드가 다르다면(예: 일부 사용자에게는 특정 필드 제거) 문서에 명시한다.
- 경로에 소유자를 넣으면 실수를 줄인다. (`/owners/{ownerId}/sources`, 또는 `/owners/me/sources`)

#### 3.2.3 스코프(Scope)로 접근 범위 제한

- 토큰에 `orders:read`, `orders:write` 같은 **스코프**를 담아 "이 클라이언트(앱)는 이 연산만 호출 가능"을 제한한다. 최소 권한 원칙의 적용이다. (스코프는 주로 OAuth/OIDC 용어이며 RBAC의 역할과 비슷한 역할을 한다.)
- 연산 하나마다 필요한 스코프를 정하고 문서에 적는다.
- **스코프가 있다고 실행이 보장되는 건 아니다.** 스코프는 "앱이 이 연산을 부를 자격이 있는가"이고, 비즈니스 규칙과 **최종 사용자 권한**은 구현 쪽에서 별도로 검사한다. 원서 예: 송금 스코프가 있는 모바일 앱이 호출해도, 그 사용자에게 "고액 송금" 권한이 없으면 구현이 거절한다. 스코프 검사는 보통 API 게이트웨이가, 사용자 권한 검사는 구현이 맡는다.
- 스코프를 아예 안 정하면 인증된 앱은 모든 연산을 호출할 수 있다. 반대로 `write` 같은 통짜 스코프를 만들면 "거래 표시 갱신"만 필요한 앱에도 "송금" 권한이 딸려 간다.
- 스코프 이름과 설명은 API 제공자, 클라이언트 개발자, **최종 사용자(동의 화면에서 읽는 사람)** 모두가 이해할 수 있어야 한다.
- 스코프를 나중에 바꾸면 기존 클라이언트가 깨지거나 권한 구멍이 생기므로 신중히 설계한다.

**스코프 설계 방식 6가지 (원서 12.8)**

| 방식 | 예 | 특징 |
|---|---|---|
| 연산 기반 | `transfer:list`, `transfer:create` | 가장 정밀하지만 개수가 많아 고르기 힘들고 사용자를 압도할 수 있음 |
| 리소스/개념 기반 | `transfer:all` | 리소스 관련 모든 연산. 단순하나 한 리소스로는 유스케이스가 안 끝날 수 있음 |
| 유스케이스 기반 | `money_transfer` | 한 유스케이스에 필요한 연산 묶음(예: 송금에 필요한 출금/입금 계좌 목록 조회 포함) |
| 읽기/쓰기 기반 | `account:read_only`, `account:write_only` | 변경성 연산(생성·삭제)을 분리. 전역 read/write 하나는 보통 너무 넓음 |
| 사용자/클라이언트 기반 | `owner:transfer:all` | 특정 사용자 유형이 필요한 연산. 넓으면 무엇이 허용되는지 가려지므로 리소스·읽기/쓰기로 좁힘 |
| 동작 조정 | `transaction:sensitive_data` | 연산의 응답 내용(민감 데이터 포함 여부)을 바꾸는 스코프. 게이트웨이가 아닌 구현이 처리 |

- 민감도가 다른 연산(예: 은행 직원 전용 "특이 송금 검증")을 같은 스코프에 섞지 않는다.
- 한 API 안에서 여러 방식을 섞어 써도 되고, 한 연산을 여러 스코프가 커버해도 된다. 이름 규칙은 자유지만 일관되고 사용자 친화적이어야 한다(원서 예: `{사용자|클라이언트}:{리소스|유스케이스}:{행동}`).
- 접근을 제한하는 스코프 변경은 게이트웨이 설정(OpenAPI 기반)으로 비교적 쉽지만, 동작을 바꾸는 스코프는 구현을 고쳐야 한다. 배포 후 스코프 변경은 이미 쓰는 클라이언트에 영향을 준다(5.1절).

#### 3.2.4 오류 코드 선택 규칙 (재정리)

| 상황 | 응답 |
|---|---|
| 토큰이 없거나, 만료됐거나, 잘못됨 | 401 |
| 토큰은 유효하나 스코프/권한 부족 (존재 사실 공개 가능) | 403 |
| 존재 사실 자체를 숨겨야 함 (남의 테넌트 리소스) | 404 |
| 서버 내부 오류 | 500 (내부 정보 은닉) |

> 왜 중요한가: 멀티테넌트 SaaS에서 "다른 고객 데이터가 보이는" 사고는 가장 치명적이다. 이 규칙은 설계 초기부터 체크리스트로 잡아야 한다.

> 🔗 NestJS 연결: **Guard**(`AuthGuard`, 커스텀 `RolesGuard`/`ScopesGuard`)로 토큰·스코프를 검사하고, `@Roles()`/`@Scopes()` 같은 커스텀 데코레이터 + `Reflector`로 연산별 요구 스코프를 선언한다. 테넌트 조건은 서비스/리포지토리 계층에서 항상 함께 걸어야 한다.

> 📖 원문: 12.4, 12.6, 12.7, 12.10

## 코어 4. 효율·긴 작업·통지 — 캐시, 데이터량, 대량, 비동기, 웹훅

> 게임 서버는 연결이 늘 열려 있어 서버가 언제든 Notify 패킷을 밀어 넣을 수 있었고, 오래 걸리는 처리도 나중에 결과 패킷을 보내면 됐다. HTTP 요청-응답 모델에서는 **응답 하나가 요청 하나에 묶여 있고 서버가 먼저 말할 수 없다.** 그래서 호출 자체를 줄이고(캐시·데이터량·대량), 오래 걸리는 일은 "작업 리소스"로 바꾸고(202), 서버발 통지는 반대 방향 HTTP 호출(웹훅)이나 다른 프로토콜(SSE·WebSocket)로 푼다.

### 4.1 캐시와 조건부 조회

**한 줄 요약:** 가장 빠른 호출은 하지 않는 호출이므로, 서버가 데이터 성격에 맞춘 캐시 정책(`Cache-Control`, `ETag`, `Vary`)을 응답에 명시하고, 조건부 조회(`If-None-Match` → 304)로 변경이 없으면 본문을 생략한다.

가장 빠른 API 호출은 **호출하지 않는 것**이다. 서버가 캐시 정책을 응답에 명시해 준다. (클라이언트가 임의로 캐시 정책을 정하게 두지 않는다.)

| 응답 헤더 | 의미 |
|---|---|
| `Cache-Control: no-store` | 저장 금지 (민감/실시간 데이터) |
| `Cache-Control: max-age=600` | 600초 동안 재사용 가능 |
| `Cache-Control: no-cache` | 저장은 가능하나 **사용 전 재검증 필수** (이름과 달리 캐시 불가가 아님) |
| `ETag: "abc"` | 이 응답의 버전 식별자 |
| `Vary: Accept, Accept-Language` | 형식/언어에 따라 응답이 다르므로 캐시 키에 포함 |

#### 4.1.1 조건부 조회

```
GET /accounts/123
If-None-Match: "z567dff"    ← "내가 가진 버전과 다르면 줘"

→ 304 Not Modified          (본문 없음, 캐시 그대로 사용)
→ 200 OK + 새 ETag + 새 본문 (변경됨)
```

- 캐시 정책은 **데이터 성격**으로 정한다. 카드 상품 가격표(월 1회 변경)와 계좌 잔액(실시간)은 다르다.
- 보안·규제상 캐시하면 안 되는 데이터는 `no-store`.
- 캐시 정책은 OpenAPI 문서에 적어서 구현자와 소비자가 함께 본다.

> 게임 클라이언트가 패치 서버에서 리소스 파일의 해시를 비교해 바뀐 것만 내려받는 것과 같은 발상이다. 같은 ETag가 조회 쪽에서는 `If-None-Match`(→ 304), 수정 쪽에서는 `If-Match`(→ 412, 3.1.4절)로 쓰인다.

> 왜 중요한가: 캐시는 서버 비용과 응답 속도를 동시에 줄인다. 반대로 잘못된 캐시는 "오래된 잔액이 보이는" 사고를 만든다.

> 🔗 NestJS 연결: `@Header('Cache-Control', 'max-age=600')`, `CacheInterceptor`(`@nestjs/cache-manager`), Express의 기본 ETag 생성 기능.

> 📖 원문: 13.4

### 4.2 데이터량 최적화: 필드 선택, Prefer, 부분 수정

**한 줄 요약:** 필드 선택·`Prefer` 헤더·PATCH·HTTP 압축·반복 데이터 분리로 주고받는 양을 줄이되, 최적화는 필요가 확인된 뒤에 한다.

- **필드 선택(Sparse fieldset)**: `GET /accounts/123?fields=balance` 처럼 필요한 필드만 요청한다. (JSON:API는 `fields[account]=balance`)
- **모델 선택**: `Prefer: model=summarized` / `model=complete`처럼 `Prefer` 헤더로 응답 상세도를 고르게 한다. 기본값을 명확히 둔다. 커스텀 미디어 타입(`application/vnd.x.summarized+json`)도 가능하지만 놀랄 수 있으니 신중히.
- **생성/수정 응답 생략**: 필요 없는 클라이언트는 `Prefer: model=none`(또는 `return-no-content`)으로 본문 없이 `201 Created` + `Location`만 받게 할 수 있다. 원서는 "무언가 생성됐다"는 정보를 남기려고 204 대신 201을 유지하길 권한다. `model=minimal`이면 ID만, `model=summarized`면 요약 모델을 준다. (원서 13.5.2)
- **PATCH(Merge Patch)** 로 바뀐 필드만 전송한다. 수백만 사용자 규모에서는 차이가 커진다.
- **HTTP 압축**을 켠다. 원서는 JSON 같은 텍스트가 평균 최대 75%까지 줄어든다고 하며(13.2.1), HTTP/2 이상을 쓰면 더 효율적이라고 한다. 다만 압축이 켜져 있어도 반환 데이터 자체를 줄이는 최적화(13.5)는 여전히 의미가 있다.
- **반복 데이터는 별도 API**로 분리한다. (코드-라벨 사전은 `GET /codes/{name}/values`로 두고 캐시)
- 최적화는 **필요가 확인된 뒤에** 한다. 먼저 사용자 요구와 사용하기 쉬움이 우선이다.

> 🔗 NestJS 연결: `compression` 미들웨어, `@Query('fields')` 파싱, `ClassSerializerInterceptor`의 `groups` 옵션으로 응답 필드 세트를 고르는 방식.

> 📖 원문: 13.3, 13.5

### 4.3 대량(Bulk/Batch) 작업

**한 줄 요약:** 100번 호출 대신 컬렉션 수준의 대량 연산을 제공하되, 먼저 오류 정책(All-or-nothing vs 부분 성공 → 207 Multi-Status)과 건수 상한을 정한다.

100건을 처리하려고 API를 100번 호출하는 것은 비효율적이다. **컬렉션 수준의 대량 연산**을 제공한다.

```
POST   /account-applications      { "data": [ {...}, {...} ] }     여러 건 생성
PATCH  /account-applications      { "data": [ {"id":1,...}, ... ] }  여러 건 수정 (본문에 id 포함)
DELETE /account-applications?id=1,2,3                              여러 건 삭제
GET    /products?id=1,2,3                                          여러 건 조회
```

#### 4.3.1 오류 정책을 먼저 결정

| 정책 | 설명 | 적합한 경우 |
|---|---|---|
| All-or-nothing | 하나라도 실패하면 전체 롤백 | 서로 의존하는 이체 묶음, 정합성이 중요 |
| Mixed (부분 성공) | 성공한 건은 반영, 실패한 건만 보고 | 독립적인 등록 다건, 재전송 최소화 |

부분 성공이면 **207 Multi-Status** 를 쓰고, 건별 결과를 담는다.

```json
{ "data": [
  { "status": 201, "headers": { "Location": "/account-applications/123" }, "body": { "id": 123 } },
  { "status": 400, "body": { "errors": [ { "detail": "card is invalid", "pointer": "#/data/1/card" } ] } }
] }
```

- 한 번에 받을 건수 상한을 정한다(예: 최대 100).
- 처리 시간이 길어질 수 있으면 다음 절의 비동기 방식으로 전환한다.

> 🔗 NestJS 연결: 배열 본문 검증은 `@ValidateNested({ each: true })` + `@Type(() => Item)`. 트랜잭션이 필요한 all-or-nothing 처리는 서비스 계층의 트랜잭션으로 묶는다.

> 📖 원문: 13.7

### 4.4 긴 작업(비동기 API)

**한 줄 요약:** 수초 이상 걸리는 작업은 202 Accepted + `Location`으로 "작업 리소스"를 만들어 돌려주고, 결과는 폴링·콜백(또는 `Prefer`로 동기 선택)으로 받게 한다.

수초 이상 걸리는 작업(보고서 생성, 대량 임포트, 영상 처리)을 요청-응답 한 번에 기다리게 하면 문제가 생긴다. 연결 타임아웃, 서버 커넥션 고갈, 재시작 시 작업 유실 등이다.

> 게임 서버라면 오래 걸리는 처리를 워커 스레드에 넘기고 끝나면 결과 패킷을 보냈을 것이다. HTTP에서는 결과를 밀어 줄 열린 연결이 없으므로, **작업 자체를 조회 가능한 리소스**로 만들어 클라이언트가 찾아오게 한다.

#### 4.4.1 접수 후 폴링

```
POST /reports
→ 202 Accepted
  Location: /reports/789
  { "id": 789, "status": "IN_PROGRESS", "progressPercentage": 0 }

GET /reports/789
→ 200 OK
  { "id": 789, "status": "DONE", "resultUrl": "/reports/789/file" }
```

- 접수는 **202 Accepted** + `Location`으로 작업 리소스 위치를 알려준다.
- 원서 예시는 `IN_PROGRESS`/`DONE` 상태를 조회하는 시뮬레이션 리소스다. 폴링을 줄이도록 **진행률(`progressPercentage`), 진행 속도, 예상 종료 시각(`estimatedEnd`)** 을 함께 주고, 예상 종료일을 담은 `Retry-After` 헤더도 쓸 수 있다(성공한 GET에서는 흔하지 않다).
- (보충) 작업 자체를 리소스(`/reports/{id}`, `/jobs/{id}`)로 모델링하면 취소(`DELETE`)와 이력 조회도 자연스럽다. `PENDING`/`FAILED` 같은 추가 상태값과 실패 원인을 담는 방식은 원서에 없는 일반적 확장이다.

#### 4.4.2 콜백(Callback)으로 폴링 없애기

작업 종료 시 서버가 소비자가 등록한 URL을 호출한다(다음 절 웹훅과 같은 방식). 원서는 둘을 구분한다. 콜백은 소비자가 시작한 작업의 결과(예: 시뮬레이션 종료)이고, 웹훅은 제공자 쪽에서 발생한 이벤트(예: 새 거래)다. OpenAPI에서는 콜백을 해당 연산의 `callbacks`에 정의한다. (보충) 폴링과 병행 제공하는 것이 안전하다.

#### 4.4.3 동기/비동기 선택 (`Prefer`)

`Prefer: response=synchronous`(생략하거나 `response=asynchronous`면 즉시 202)처럼 `Prefer` 헤더로 소비자가 실행 방식을 고르게 할 수 있다. 원서는 최선의 방법은 아니며 주의해서 써야 한다고 한다. 소비자 구현이 단순해지는 이점이 있지만 동기 모드는 매우 오래 걸릴 수 있으니, 특정 스코프(예: `simulation:run:synchronous`)를 가진 소비자에게만 허용하는 방식을 제시한다. (원서 14.7.4)

> 왜 중요한가: SaaS는 리포트, 내보내기, 일괄 처리가 반드시 생긴다. 처음부터 "작업 리소스" 패턴을 쓰면 나중에 큐/워커 구조로 바꿔도 API가 변하지 않는다.

> 🔗 NestJS 연결: 접수 컨트롤러가 202를 반환하고 실제 작업은 **BullMQ(`@nestjs/bullmq`) 큐 + Processor**가 처리한다. 작업 상태는 DB에 저장하고 `GET /jobs/{id}`로 노출한다.

> 📖 원문: 14.7

### 4.5 웹훅(Webhook): 서버가 먼저 알려주기

**한 줄 요약:** 웹훅은 이벤트 발생 시 우리 서버가 고객 서버 URL을 POST로 호출하는 "반대 방향 API"로, CloudEvents 형식·Thin/Thick 선택·서명 등 보안·실패 시 재시도/빈틈 채우기를 설계하고, 선택 사항으로 둔다.

#### 4.5.1 웹훅이란

**"반대 방향 API"**. 이벤트(결제 완료, 구독 갱신 등)가 발생하면 **우리 서버가 고객 서버의 URL을 호출**한다.

- 고객이 계속 우리 API를 폴링할 필요가 없다(서버 부하 감소, 실시간성 향상).
- 웹훅 인터페이스는 **우리(제공자)가 정의**하고 고객이 구현한다. 항상 `POST`다.
- 웹훅은 **선택 사항**으로 둔다. 웹훅을 못 받는 고객도 일반 API 조회로 같은 정보를 얻을 수 있어야 한다.

#### 4.5.2 이벤트 형식: CloudEvents 표준 권장

```json
POST https://customer.com/hooks
Content-Type: application/cloudevents+json

{
  "specversion": "1.0",
  "type": "com.example.invoice.paid",
  "source": "/invoices",
  "id": "evt_123",
  "data": { "invoiceId": "inv_9", "amount": 4900, "currency": "USD" }
}
```

- `source`와 `id`를 이어 붙인 값이 이벤트를 유일하게 식별한다(원서 14.6.4). `type`은 `com.회사.도메인.행위` 같은 역도메인 형태의 이름이다.
- 원서는 `application/cloudevents-batch+json`으로 여러 이벤트를 배열로 보내는 방식도 소개하지만, 실시간 통지에는 한 건씩 보낸다.
- CloudEvents는 이벤트 전체 크기를 64KB 이하로 권장한다.
- (보충) 소비자가 이 `id`로 중복 수신을 걸러낼 수 있다. 원서가 직접 그렇게 말하지는 않지만 자연스러운 활용이다.

#### 4.5.3 이벤트 데이터: 얇게 vs 두껍게

| 종류 | 내용 | 적합한 경우 |
|---|---|---|
| Thin (얇은 이벤트) | ID/링크만 (`{ "href": "/invoices/inv_9" }`) | 데이터가 자주 변하거나 큼, 민감함 |
| Thick (두꺼운 이벤트) | 사용할 수 있는 데이터를 함께 | 데이터가 작고 변하지 않으며 소비자가 바로 쓰고 싶어함 |

민감한 정보는 두꺼운 이벤트에 넣지 않거나, 권한에 따라 필드를 제거한다.

#### 4.5.4 웹훅 보안

수신 측이 "정말 우리가 보낸 것인지" 검증할 수 있어야 한다.

원서(14.6.6)는 웹훅도 일반 API처럼 보안을 고려해야 하고, 실제 방식은 보안 전문가와 상의해 정하라고 한다. 원서가 나열하는 선택지는 다음과 같다.

- **공유 비밀키로 메시지 서명**: 수신자가 "변조되지 않았고 우리 플랫폼이 보낸 것"임을 확인할 수 있다.
- 발송 서버 IP 허용 목록(allowlist)
- 상호 TLS(mutual TLS)
- OAuth 2.0
- 여러 방식을 조합할 수 있고, 어떤 방식이 있느냐에 따라 민감한 데이터를 이벤트에 넣어도 될지 판단한다.
- 서명 같은 방식은 OpenAPI에서 형식(커스텀 헤더 등)이나 텍스트 설명으로 문서화한다.

> 💡 보충(원서 외): 원서는 "공유 비밀키로 서명" 수준까지만 말한다. 아래는 저자가 덧붙인 일반 관행이다.
> - 서명에 HMAC-SHA256을 쓰고 `X-Signature` 같은 헤더에 담는 구체 형식
> - 타임스탬프를 서명에 포함해 재전송 공격을 막는 방법
> - 수신 URL을 HTTPS만 허용하는 정책
> 원서에서 해당 서명 헤더 이름이나 타임스탬프 방식은 확인되지 않는다.

#### 4.5.5 수신 측 기대 동작과 실패 처리

- 웹훅 수신 측은 아무 2XX 상태로 응답하면 된다(200 또는 204). 응답 본문은 제공자가 읽지 않는다. 원서는 응답이 수 밀리초 안에 나가는 것이 이상적이라고 하고, 문서 예시로 "200ms 이내 응답"을 든다.
- 수신 구현은 최대한 단순해야 한다. 보안과 데이터 형식만 확인하고 이벤트를 DB나 큐에 넣은 뒤, **실제 처리는 다른 시스템이 나중에** 한다.
- 발송이 실패(타임아웃, 2XX 아님)했을 때 원서가 드는 선택지는 다음과 같다.
  1. 소비자가 일반 API로 빈틈을 채운다(예: 새 거래를 조회하는 `GET /transactions`).
  2. 빈틈을 채우도록 돕는 전용 연산을 준다(예: 지난 알림을 필터로 조회하는 "알림 목록" 연산).
  3. 개발자 포털이나 "알림 재전송" 연산으로 과거 이벤트를 요청 시 다시 보낸다(같은 웹훅 경로로 들어오게 된다).
  4. **자동 재시도**. 원서 예시는 24시간 동안 최대 5회로 제한한다. 수신자가 응답에 Retry 헤더를 넣어 재시도를 최적화하게 할 수도 있다.
- 한도를 넘으면 소비자는 재전송 기능을 쓴다. 이벤트 이력과 재시도의 복잡도는 이해관계자와 논의해 정하라고 하며, GitHub와 PayPal의 웹훅 문서를 참고하라고 권한다.
- 웹훅 설명(description)에 호출 측 동작("실패 시 24시간 동안 5회 재전송")과 수신 구현이 지켜야 할 동작을 적는다.
- (보충) 재시도 간격을 지수 백오프로 하는 것, 재시도 때문에 **수신자가 멱등하게** 처리해야 한다는 점, 순서 보장이 안 될 수 있으니 문서에 적는 것은 원서에 직접 나오지 않는 일반 관행이다.
- (보충) 재전송 API 경로 `POST /webhook-deliveries/{id}/redeliver`와 `GET /events?since=...`는 예시 이름일 뿐이며 원서 표기가 아니다.

```ts
// (보충) 발송 측 서명 예 (Node.js). 원서에 없는 일반 관행 예시이며, 실제 서명 방식은 보안 전문가와 확정한다.
import { createHmac } from 'node:crypto';
const ts = Math.floor(Date.now() / 1000);
const sig = createHmac('sha256', secret).update(`${ts}.${rawBody}`).digest('hex');
headers['X-Signature'] = `t=${ts},v1=${sig}`;
```

> 왜 중요한가: SaaS 통합의 표준 수단이 웹훅이다(결제 서비스, Git 서비스 등이 모두 그렇다). 고객에게 웹훅을 제공하든, 외부 웹훅을 받든 서명·재시도·멱등 처리는 필수다.

> 🔗 NestJS 연결: 발송은 큐(BullMQ)의 재시도·백오프 기능으로 구현한다. 수신 엔드포인트는 서명 검증용 Guard를 만들고, 서명 계산을 위해 **원본 본문(raw body)** 보존 설정이 필요하다.

> 📖 원문: 14.6

### 4.6 다른 통신 방식 (선택 판단용 개요)

**한 줄 요약:** REST는 공개·파트너·브라우저 API의 기본이지만, 스트리밍은 SSE, 양방향은 WebSocket, 내부 이벤트는 EDA, BFF는 GraphQL, 내부 고성능 통신은 gRPC를 고려한다.

REST가 항상 정답은 아니다. 알아 두고 상황에 맞게 고른다.

| 방식 | 잘 맞는 상황 |
|---|---|
| REST (HTTP JSON) | 일반적인 CRUD, 외부 공개 API, 캐시·도구 생태계 활용 |
| 웹훅 | 외부에 이벤트 통지 |
| 이벤트 기반 (메시지 브로커) | 내부 서비스 간 비동기 통신 |
| SSE (Server-Sent Events) | 서버 → 클라이언트 단방향 실시간 (알림, 진행률) |
| WebSocket | 양방향 실시간 (채팅, 협업 편집) |
| GraphQL | 클라이언트가 필요한 필드를 유연하게 조합해야 할 때 |
| gRPC | 내부 서비스 간 고성능 통신 |

**원서가 짚는 각 방식의 주의점 (14.8)**

- **이벤트 기반(EDA)**: 웹훅은 인터넷 너머 외부에, EDA는 **내부** 통신에 맞다. 제공자가 채널에 이벤트를 발행하고 소비자가 구독한다. 웹훅 알림을 EDA가 뒷받침할 수도 있다.
- **SSE**: HTTP로 텍스트 데이터를 서버→클라이언트로 스트리밍한다(진행률, 실시간 시세, AI 응답 스트리밍). 보통 REST API와 함께 쓴다. 단, 연결을 계속 열어 두므로 **자원 소모가 클 수 있다**.
- **WebSocket**: 양방향(텍스트·바이너리) 실시간 통신. 연결이 많으면 자원 소모가 크고, 방화벽·프록시가 막을 수 있어 추가 설정이 필요하다.
- **GraphQL**: 여러 API 데이터를 모으고 필요한 요소만 정밀하게 고르는 데 좋아 BFF(backend-for-frontend)에 어울린다. 다만 **캐싱, 무거운 복잡 쿼리 방지, 보안**이 과제이며, 이런 기능이 꼭 필요 없다면 HTTP/2 위의 잘 설계된 REST로 충분할 수 있다.
- **gRPC**: 컴포넌트가 많은 마이크로서비스에서 고려. HTTP/2와 양방향 스트리밍을 활용하고 Protobuf 바이너리가 JSON보다 작고 직렬화가 빠르다. **브라우저는 gRPC를 지원하지 않는다.**

> 게임 서버 개발자에게 가장 익숙한 모델은 WebSocket(연결 유지 + 양방향 메시지)과 gRPC(스키마로 정의한 바이너리 메시지, opcode 대신 서비스·메서드 이름)다. 그렇다고 공개 SaaS API를 이 방식으로 만들 이유는 되지 않는다. 연결 유지형은 서버마다 연결 상태를 들고 있어야 하므로, 무상태 REST가 주는 "아무 인스턴스나 받아도 된다"는 확장성과 캐시·게이트웨이 생태계를 포기하게 된다.

**언제 REST 말고 다른 것을 고려하나 (원서 14.8.2)**

| 요구 | 후보 |
|---|---|
| 소비자에게 데이터를 스트리밍해야 함 | SSE |
| 양방향 통신 필요 | WebSocket |
| 내부 시스템에 이벤트를 보내야 함 | EDA |
| BFF를 만드는데 REST로 안 되는 기능이 필요 | GraphQL |

반대로 기본 스택이 REST가 아니더라도, **공개/파트너 API**(대부분 REST), 나중에 공개될 수 있는 사설 API, **브라우저가 소비하는 API**(gRPC 부적합), 인터넷 너머 제공자→소비자 통신(웹훅·콜백)이면 REST(또는 HTTP 웹훅)를 고려하라고 한다. "도구가 망치뿐이면 모든 게 못으로 보인다"는 경계도 덧붙인다.

> 🔗 NestJS 연결: `@nestjs/graphql`, `@nestjs/websockets`, `@nestjs/microservices`(gRPC/큐), SSE는 `@Sse()` 데코레이터.

> 📖 원문: 14.8

## 코어 5. 진화 — 하위 호환·버전·OpenAPI

> 게임 서버는 프로토콜 버전이 다르면 접속을 거부하고 클라이언트를 강제 업데이트시킬 수 있었다. 공개 API의 소비자는 우리가 배포할 수 없는 외부 코드이므로, **"깨지지 않게 바꾸는 규칙"(하위 호환 판정표)**, 버전 정책, 폐기 예고, 그리고 그 규칙을 기계가 검사할 수 있게 하는 **OpenAPI 명세**가 필요하다.

### 5.1 API 진화: 하위 호환과 버전 관리

**한 줄 요약:** API는 공개 순간부터 계약이므로, 응답(출력)과 요청(입력)에서 방향이 반대인 하위 호환 판정 규칙을 지키고, OpenAPI diff를 CI에 넣고, 버전 방식(경로 `/v1`)을 처음부터 정하며, 폐기는 `deprecated`와 `Sunset`으로 알린다.

API는 공개되는 순간부터 **계약**이다. 바꿀 때 소비자의 코드를 깨지 않는 것이 핵심이다.

#### 5.1.1 하위 호환되는 변경 vs 깨지는 변경

**응답(출력) 데이터**

| 변경 | 호환? |
|---|---|
| 새 속성 추가 | 호환 |
| 선택 속성 제거 | 호환 |
| 선택을 필수로(항상 반환) | 호환 |
| 문자열 최대 길이 줄이기 | 호환 |
| 문자열 최대 길이 늘리기 | **깨짐** (소비자 DB 컬럼 길이 초과 등) |
| 필수 속성 제거/이름 변경/이동 | **깨짐** |
| 타입·형식·의미 변경 (숫자 → 문자열, 초 → 밀리초) | **깨짐** |
| enum에 값 추가 | **깨짐** (소비자가 모르는 값 처리 못함) |
| 필수를 선택으로 변경 | **깨짐** |

**요청(입력) 데이터** — 방향이 반대다.

| 변경 | 호환? |
|---|---|
| 선택 입력 추가 | 호환 |
| 필수 입력을 선택으로 완화 | 호환 |
| 허용 범위·길이·enum 값 확대 | 호환 |
| 필수 입력 추가 | **깨짐** |
| 이름 변경/타입 변경/제약 강화/enum 값 제거 | **깨짐** |

> 판정 요령: 응답은 소비자가 **읽는** 쪽이라 "소비자가 예상하는 범위 안에 머무는가", 요청은 소비자가 **쓰는** 쪽이라 "예전에 보내던 요청이 여전히 받아들여지는가"를 본다. C++에서 패킷 구조체에 필드를 끼워 넣으면 오프셋이 밀려 구버전이 깨지던 것과 달리, JSON은 이름으로 필드를 찾으므로 **응답에 속성 추가**는 안전하다. 반대로 enum 값 추가는 소비자 코드의 `switch`에 없는 값이 들어오는 것이라 깨진다.

**그 외**

- 경로(URL) 변경 → 404로 깨짐. (리다이렉트 308을 두어도 클라이언트가 따라가지 않는 경우가 많다.)
- 연산(메서드) 제거/변경 → 405/404.
- 상태코드 변경 (200 → 201도 엄격한 클라이언트는 깨질 수 있음).
- 에러 응답 형식 변경 → 오류 처리 코드가 깨진다.
- 새 필수 단계(예: 이체 후 OTP 확인 추가)로 **흐름이 바뀌면** 조용히 깨진다.
- **암묵적 계약**: 문서에 없어도 소비자는 관찰한 동작(정렬 순서, 응답 속도)에 의존한다. (Hyrum의 법칙)

#### 5.1.2 실수 방지: 자동 검사

- 변경 전/후 OpenAPI 문서를 비교해야 한다. 일반 텍스트 diff는 인터페이스가 그대로인데도 구조 변화를 잔뜩 보여주므로 부족하다. 안전한 변경과 깨지는 변경을 구분해 주는 **OpenAPI 전용 비교 도구**를 CI/CD에 넣어, 마지막 배포 때 검증한 문서와 새 문서를 비교하고 의도치 않은 변경이 보이면 배포를 막는다(원서 15.2.8).
- 이런 도구는 명세 밖의 동작(응답 상태·동작 변화, 암묵적 계약)을 잡지 못한다. 구현을 기대 OpenAPI에 맞춰 충분히 테스트해 보완한다.
- 원서는 특정 도구 이름을 추천하지 않고, "OpenAPI diff" 분야는 계속 변하니 tools.openapis.org 등에서 "oas diff", "openapi diff"로 찾고 각 도구가 깨지는 변경을 어떻게 판정하는지 문서를 확인하라고만 한다.
- (보충) `oasdiff`는 그런 도구 중 하나로 저자가 예로 든 이름이며 원서에는 나오지 않는다.

#### 5.1.3 버전 관리

- API 버전은 **인터페이스(소비자에게 보이는 계약)** 의 버전이다. 구현 코드 버전과 다르다.
- 체계: **시맨틱 버저닝**(MAJOR.MINOR — 깨지는 변경은 MAJOR, 호환 변경은 MINOR)이 가장 흔하다. 릴리스가 정기적이면 날짜 기반(`2024-03-04`)도 가능하다.
- 요청에 버전을 표현하는 방법 비교:

| 방식 | 예 | 평가 |
|---|---|---|
| 경로 | `/v1/accounts` | **기본 권장**. 단순하고 가장 흔함 |
| 커스텀 헤더 | `Version: 2` | 가능. 다만 자주 빼먹음 |
| 미디어 타입 | `Accept: application/vnd.x.v2+json` | 가능하나 구현·사용이 까다로움 |
| 쿼리 | `?version=2` | 비권장 (데이터와 메타데이터가 섞임) |
| 도메인 | `api-v2.example.com` | 드묾 |

- **버전 방식은 처음부터 정한다.** 지금 `/v1`을 경로에 넣어 두고 오래 유지해도 된다.
- **리소스/연산별로 따로 버전을 매기지 않는다.** (`/v2/orders`와 `/v3/customers`가 섞이면 어떤 조합이 되는지 아무도 모른다.)
- 가능한 한 오래 v1을 유지하고, 정말 가치가 있을 때만 v2로 올린다.

#### 5.1.4 깨는 변경을 하기 전에 물어볼 것

1. 영향받는 소비자는 누구이며 몇 명인가? (내부 앱, 파트너, 공개)
2. 소비자가 실제로 깨질 기능을 쓰는가? (게이트웨이 로그, 스코프로 확인)
3. 여러 버전을 동시에 운영할 수 있는가? (한 인스턴스 + 요청/응답 어댑터가 권장)
4. 버전 정책이 있는가? (지원 기간, 최근 N개 버전 지원)
5. 깨는 가치가 비용보다 큰가?

#### 5.1.5 확장 가능한 설계 습관 (애초에 안 깨지게)

- 요청/응답 본문은 **항상 객체**로 (배열·원시값 금지).
- 문자열 배열보다 **객체 배열**을 (나중에 속성 추가 가능): `owners: [{ id }]`
- **불리언보다 enum/status**: `executed: true/false` 대신 `status: "EXECUTED" | "DELAYED"`
- 자주 바뀌는 enum(카테고리 등)은 **값 조회 API**(`GET /categories`)로 분리한다.
- 모르는 입력 필드는 **에러 대신 무시**해서 나중에 제거할 여지를 남긴다.
- 지나친 범용화는 금지. "상상 속 미래"까지 다 대비한 복잡한 설계는 오히려 해롭다.

#### 5.1.6 폐기(Deprecation)를 알리기

- OpenAPI에 `deprecated: true`로 표시한다.
- 여러 버전을 각각 제한된 기간만 지원할 때, 폐기 예정 버전의 모든 응답에 **`Sunset: Wed, 31 Aug 2024 23:59:59 GMT`** 헤더(RFC 8594)를 붙여 폐기 시점을 프로그램이 알 수 있게 한다. 다만 소비자나 인프라가 이 헤더를 실제로 확인해야 쓸모가 있다. 제공자가 만든 SDK가 이 헤더를 보고 로그에 경고를 남기는 식으로 쓴다(원서 15.6.4).
- 원서는 `Deprecation` 헤더를 언급하지 않는다.

> 💡 보충(원서 외): 폐기 사실 자체를 알리는 `Deprecation` 응답 헤더를 `Sunset`과 함께 쓰는 팀도 있지만, 이는 원서 근거가 없는 일반 관행이다. 원서에서 확인된 것은 `Sunset`과 OpenAPI `deprecated` 표시뿐이다.

- 변경 이력(changelog)을 OpenAPI 문서에 남긴다(원서 15.7.3). 충분한 공지 기간을 두는 것은 원서의 "버전 정책(지원 기간)" 논의와 이어진다.
- 스코프·보안 방식을 바꾸는 변경도 깨지는 변경이다. 새/구 방식을 잠시 **병행 지원**한 뒤 옛 방식을 제거한다.

> 왜 중요한가: SaaS 고객은 한 번 붙인 연동을 좀처럼 바꾸지 않는다. 하위 호환을 깨면 곧바로 고객 장애와 이탈이다.

> 🔗 NestJS 연결: `app.enableVersioning({ type: VersioningType.URI })` + `@Controller({ path: 'orders', version: '1' })`. 폐기 헤더는 Interceptor로 붙이면 편하다.

> 📖 원문: 15.1~15.7

### 5.2 OpenAPI 명세와 문서화

**한 줄 요약:** OpenAPI는 REST API를 기계가 읽는 형식으로 기술한 "프로토콜 정의서"로, 문서·SDK·모킹·변경 감지·린트를 자동화하며, 명세 우선/코드 우선 중 택하고 팀 가이드라인 + API 린터로 일관성을 지킨다.

> 게임 서버 팀이 패킷 정의 파일(IDL)에서 C++ 구조체와 직렬화 코드를 생성하던 것과 비슷한 위치다. 차이는 OpenAPI가 필드 구조뿐 아니라 경로·메서드·상태코드별 응답·인증 스코프·웹훅까지 기술하고, 외부 소비자가 읽는 **공개 문서**가 된다는 점이다.

#### 5.2.1 OpenAPI란

REST API를 **기계가 읽을 수 있는 형식(YAML/JSON)** 으로 기술하는 표준이다.
하나의 문서로 다음을 자동화할 수 있다.

- 사람용 API 문서(Swagger UI, Redoc)
- 클라이언트 SDK / 서버 스텁 코드 생성
- 모킹(가짜 서버), 계약 테스트
- 변경 감지(breaking change diff), 린트

#### 5.2.2 기본 구조

```yaml
openapi: 3.1.0
info:
  title: Shop API
  version: "1.2"          # 숫자가 아니라 문자열로 (따옴표!)
paths:
  /products/{productId}:
    get:
      summary: 상품 상세 조회
      parameters:
        - name: productId
          in: path
          required: true
          schema: { type: string }
      responses:
        "200":
          description: 상품을 찾음
          content:
            application/json:
              schema: { $ref: "#/components/schemas/Product" }
        "404":
          description: 상품이 없음 (또는 이 사용자에게 접근 권한이 없음)
          content:
            application/problem+json:
              schema: { $ref: "#/components/schemas/Problem" }
components:
  schemas:
    Product:
      type: object
      required: [id, name]
      properties:
        id: { type: string }
        name: { type: string }
webhooks: {}      # 웹훅 정의는 여기 (경로 대신 식별자 사용)
```

- `paths`: 연산 정의 (경로 + 메서드).
- `parameters`: path/query/header 입력.
- `requestBody`, `responses`: 본문과 상태코드별 응답.
- `components`: 공용 스키마/파라미터/응답/보안 스킴을 정의하고 `$ref`로 재사용한다.
- `webhooks`, `callbacks`: 웹훅과 콜백 정의.
- `security`, `securitySchemes`: 인증 방식과 스코프.

#### 5.2.3 문서를 잘 쓰는 법

- 상태코드 설명에 "Forbidden" 같은 HTTP 이유 문구만 적지 말고 **언제 발생하는지**를 적는다. (예: "토큰에 스코프가 없거나, 요청자가 이 계좌의 관리자가 아닐 때")
- 캐시 정책, 조건부 요청 헤더(`ETag`, `If-Match`), 멱등 키 규칙, 재시도 정책, 접근 제한 등을 **설명 필드**에 반드시 적는다.
- 설명(`description`)은 Markdown을 지원한다.
- 요청·응답 **예시**를 넣으면 이해가 빠르다.
- 공통 부분(에러 응답, 페이징 파라미터)은 `components`에 한 번만 정의해 일관성을 지킨다.

#### 5.2.4 명세 우선(Design-first) vs 코드 우선(Code-first)

| 방식 | 설명 | 장점 | 단점 |
|---|---|---|---|
| 명세 우선 | 먼저 OpenAPI 작성 → 합의 → 구현 | 구현 전 리뷰 가능, 프론트/백 병렬 작업, 계약이 진실의 원천 | 명세와 코드가 어긋나지 않게 관리 필요 |
| 코드 우선 | 코드에 데코레이터를 달고 명세를 자동 생성 | 코드와 문서가 동기화되기 쉬움 | 구현 세부가 계약에 새어 들어가기 쉬움, 설계 리뷰가 늦어짐 |

- 원서(6.2.2)는 명세를 독립된 진실의 원천으로 삼을 수 있는 **명세 우선을 대체로 권장**하되, 구현 세부와 문서가 섞여도 괜찮고 구현이 몰래 변하지 않는다면 코드 우선도 적합하다고 본다. 언제든 방식을 바꿀 수 있다.
- 코드 우선이라도 **생성된 문서를 리뷰**하고, `info.version`이 구현 버전이 아니라 API 버전인지 확인한다.
- 문서는 CI에서 **린트**(Spectral 등)로 일관성 규칙을 자동 검사하면 좋다. 규칙은 팀 **API 가이드라인**(URL 규칙, 에러 형식, 페이징 방식, 버전 정책 등)으로 정해 두면 의사결정 논쟁이 줄어든다.

#### 5.2.5 API 설계 가이드라인과 린터 (원서 16.3~16.4, 18.1)

- **ADR(결정 기록)만으로는 설계할 때 쓰기 불편하다.** "거래 검색" 연산 하나를 설계하려 해도 경로, 상태코드, 응답 형식, 페이징, 필터, 에러를 여러 ADR에서 찾아야 하고 빠뜨리기 쉽다. **가이드라인**은 "목록·검색 API는 이렇게 만든다"처럼 한곳에 실행 가능한 형태로 모으고 관련 ADR 링크를 단다.
- 덕분에 "결과가 없으면 200 빈 목록이냐 404냐"를 백 번째 토론하지 않고, 데이터 모델이 필요한 정보를 주는지 같은 본질에 집중할 수 있다. 혼자 만드는 프로젝트든 팀이든 유용하고, 팀이라면 설계 방식이 서로 다를 수 있어 공유 가이드가 필수다. 사람이 바뀌어도 신입이 빨리 적응한다.
- 원서는 거버넌스를 "규칙을 어기면 야단치는 API 경찰"이 아니라 가이드라인·도구·교육·지원으로 만드는 사람을 돕는 **조력자**로 보라고 한다.
- 가이드라인에 넣을 것: 원칙과 규칙(허용 HTTP 메서드/상태코드, 복수형 경로 규칙, 기본 페이징 방식, 에러는 Problem Details 사용 등. 필수/권장/선택은 RFC 2119의 MUST/SHOULD/MAY로 표기), **실행 가능한 레시피**(규칙을 흩어 두지 말고 "목록 조회 방법", "에러 처리 방법" 같은 작업 단위로 묶어 경로·파라미터·응답 전체를 설명), OpenAPI 템플릿·공용 컴포넌트, 자동 검사 도구(린터).
- **API 린터**는 코드 린터의 OpenAPI 버전이다. 설계 문제(속성 이름 규칙 불일치, 검색 연산의 페이징 파라미터 누락, 보안 스코프 미정의)와 OpenAPI 작성 문제(경로 파라미터 중복 정의, 인라인 스키마)를 IDE·CLI·CI/CD에서 자동으로 찾아 가이드라인을 무리 없이 적용하게 해 준다. OpenAPI 파일이 어떻게 만들어졌든 상관없이 검사한다.

> 🔗 NestJS 연결: `@nestjs/swagger`로 코드 우선 방식 사용. 
> - 설정: `DocumentBuilder` + `SwaggerModule.setup('docs', app, document)`.
> - DTO 문서화: `@ApiProperty()` (또는 CLI 플러그인 자동화), 컨트롤러: `@ApiTags`, `@ApiOperation`, `@ApiResponse`, `@ApiBearerAuth`, `@ApiQuery`.
> - 생성된 JSON을 파일로 내보내 CI에서 breaking-change diff에 사용한다.

> 📖 원문: 6.1~6.3, 15.7, 16.3, 18.1

## 실무 적용

### NestJS에 적용하는 종합 예시

**한 줄 요약:** 다섯 코어의 규칙이 `main.ts` 전역 설정과 컨트롤러 하나에 함께 녹아 있다.

```ts
// main.ts
app.setGlobalPrefix('api');
app.enableVersioning({ type: VersioningType.URI, defaultVersion: '1' });   // /api/v1/...
app.useGlobalPipes(new ValidationPipe({ whitelist: true, transform: true })); // 검증 + 모르는 필드 무시
app.useGlobalFilters(new ProblemDetailsFilter());                            // 에러 표준화 (RFC 9457)
app.useGlobalInterceptors(new ClassSerializerInterceptor(app.get(Reflector)));

// orders.controller.ts
@ApiTags('orders')
@Controller({ path: 'orders', version: '1' })
export class OrdersController {
  @Post()
  @HttpCode(201)
  @ApiCreatedResponse({ type: OrderDto })
  async create(@Body() dto: CreateOrderDto,
               @Headers('idempotency-key') key: string,
               @Res({ passthrough: true }) res: Response) {
    const order = await this.orders.create(dto, key);       // 멱등 처리 포함
    res.location(`/api/v1/orders/${order.id}`);              // Location 헤더
    return order;
  }

  @Get()
  list(@Query() q: ListOrdersQuery) {                        // page/size/sort/filters
    return this.orders.list(q);                              // { data, metadata }
  }

  @Patch(':id')
  update(@Param('id') id: string,
         @Headers('if-match') ifMatch: string,
         @Body() dto: UpdateOrderDto) {
    return this.orders.update(id, dto, ifMatch);             // 불일치 시 412
  }
}
```

### 시나리오로 확인하기

1. **상황:** 결제 API(`POST /payments`)에서 가끔 같은 주문이 두 번 결제된다. 로그를 보면 첫 요청은 정상 처리됐고, 몇 초 뒤 같은 본문의 요청이 **다른 서버 인스턴스**로 한 번 더 들어왔다. 팀원은 "TCP가 재전송·중복을 처리해 주니 중복 패킷은 있을 수 없다"고 말한다.
   **질문:** 무엇이 원인이고 어떻게 막아야 하나?

   <details markdown="1"><summary>답 확인</summary>

   첫 요청은 처리됐지만 응답이 돌아오는 길에 연결이 끊겨, 클라이언트(또는 HTTP 라이브러리·게이트웨이)가 **새 연결로 같은 요청을 재시도**한 것입니다. TCP의 중복 제거는 한 연결 안에서만 동작하므로 이 재시도는 TCP 입장에서 새 데이터입니다. POST는 비멱등이라 재시도가 위험합니다. 클라이언트가 `Idempotency-Key`를 보내고, 서버는 같은 키가 이미 왔으면 다시 처리하지 않고 409(원서) 또는 저장해 둔 이전 응답을 재생(보충, 실무 관행)합니다. 키 확인과 저장은 모든 인스턴스가 공유하는 저장소에서 **원자적으로**(DB 유니크 제약, Redis `SET NX`) 해야 동시 요청 두 개가 모두 통과하지 않습니다. 재시도마다 새 키를 만드는 클라이언트에 대비해 업무 규칙 기반 중복 감지(최근 1분 내 같은 금액·계좌 → 409, `Confirm-Duplicate: true`로 강제)도 고려합니다. → 코어 3

   </details>

2. **상황:** 관리자 화면에서 운영자 A와 B가 같은 고객사의 구독 정보를 열어 두고, A는 좌석 수를, B는 결제 이메일을 고쳐 `PUT /subscriptions/{id}`로 저장했다. 나중에 보니 A의 변경이 사라졌다. 게임 서버에서는 한 객체의 변경이 단일 로직 스레드에서 순서대로 처리돼 이런 일이 없었다.
   **질문:** 원인과 API 설계 차원의 해결책은?

   <details markdown="1"><summary>답 확인</summary>

   두 사람이 같은 버전을 읽고 각각 전체를 보내는 PUT으로 저장해 **나중 저장이 먼저 저장을 덮어쓴 갱신 유실**입니다. 요청 처리 순서를 서버가 직렬화해도, 각자 "읽은 시점의 옛 값"을 통째로 보내므로 막히지 않습니다. GET 응답에 `ETag`를 주고, 수정 요청에 `If-Match`로 읽은 버전을 실어 보내게 해서, 그 사이 바뀌었으면 **412 Precondition Failed**로 거절하고 클라이언트가 다시 읽게 합니다(DB `version` 컬럼과 연결). 조건부 갱신은 뒤늦게 필수로 바꾸면 기존 클라이언트가 수정을 못 하게 되므로 처음부터 정합니다. 바뀐 필드만 보내는 PATCH(Merge Patch)도 덮어쓰기 범위를 줄입니다. → 코어 3 (3.1.4절), 코어 1 (1.3.4절)

   </details>

3. **상황:** 보안 점검에서 "`GET /orders/{id}`에 다른 테넌트의 주문 ID를 넣으면 403이 온다. ID가 UUID라 괜찮다고 생각했다"는 지적을 받았다.
   **질문:** 무엇이 문제이고 어떻게 고쳐야 하나?

   <details markdown="1"><summary>답 확인</summary>

   403은 "그 리소스가 존재하지만 너는 권한이 없다"는 뜻이라 **다른 고객의 주문이 존재한다는 사실**을 알려 줍니다. 존재 자체를 숨겨야 하는 남의 테넌트 리소스는 404로 응답합니다. 또 UUID처럼 추측하기 어려운 ID도 보안이 아니므로, 서비스/리포지토리 계층에서 항상 **토큰의 사용자·테넌트 정보와 요청 입력을 대조**해야 합니다(IDOR 방지). 게임 서버에서 "로그인한 세션이니 이 유저 것"이라고 믿던 연결 단위 신뢰가 HTTP에는 없다는 점을 기억합니다. → 코어 3 (3.2절), 코어 2 (2.4.3절)

   </details>

4. **상황:** 주문 응답의 `status` enum에 `"PARTIALLY_SHIPPED"`를 추가해 배포했다. 속성을 "추가"만 했으니 안전하다고 판단했는데, 다음 날 파트너사 연동이 오류를 내기 시작했다. 게임이었다면 클라이언트 강제 업데이트로 해결했을 것이다.
   **질문:** 왜 깨졌고, 앞으로 어떻게 해야 하나?

   <details markdown="1"><summary>답 확인</summary>

   응답에서 **enum 값 추가는 깨지는 변경**입니다. 소비자 코드가 모르는 값을 처리하지 못하기 때문입니다(응답에 새 속성 추가는 호환이지만 enum 값 추가는 다릅니다). 공개 API 소비자는 강제 업데이트할 수 없으므로, 배포 전에 OpenAPI 전용 diff 도구를 CI에 넣어 깨지는 변경을 막고, 정말 필요하면 새 버전(`/v2`)이나 깨는 변경 전 질문 5개(영향 소비자, 실제 사용 여부, 병행 운영, 버전 정책, 가치 대비 비용)를 거칩니다. 자주 바뀌는 enum은 값 조회 API로 분리하는 습관도 있습니다. 옛 버전 폐기는 `deprecated: true`와 `Sunset` 헤더로 알립니다. → 코어 5

   </details>

5. **상황:** 고객사가 연 단위 매출 보고서를 요청하는 `GET /reports/annual`이 30초 넘게 걸려, 게이트웨이 타임아웃이 나고 서버 재시작(배포) 때마다 생성 중이던 보고서가 사라진다.
   **질문:** API를 어떻게 다시 설계해야 하나?

   <details markdown="1"><summary>답 확인</summary>

   긴 작업을 요청-응답 한 번에 기다리게 하면 연결 타임아웃, 커넥션 고갈, 재시작 시 작업 유실이 생깁니다. 작업을 리소스로 만들어 `POST /reports` → **202 Accepted + `Location: /reports/{id}`** 로 접수하고, 클라이언트는 `GET /reports/{id}`를 폴링해 `IN_PROGRESS`/`DONE`과 결과 URL을 확인합니다(진행률·예상 종료 시각·`Retry-After`로 폴링 감소). 원하면 콜백으로 완료를 알립니다. NestJS에서는 접수 컨트롤러가 202를 반환하고 BullMQ 큐 + Processor가 실제 작업을 하며 상태를 DB에 저장하므로, 재시작해도 작업이 큐에 남습니다. 처음부터 이 패턴을 쓰면 내부 구조가 바뀌어도 API는 변하지 않습니다. → 코어 4 (4.4절)

   </details>

### 2. 인출 질문

1. REST의 여섯 가지 제약 중 무상태와 균일한 인터페이스가 API 설계에서 갖는 의미는?

   <details markdown="1"><summary>답 확인</summary>

   제약은 클라이언트/서버 분리, 무상태, 캐시, 계층형 시스템, 균일한 인터페이스, 코드 온 디맨드(선택)입니다. 무상태는 요청마다 필요한 정보를 다 담아 서버가 세션을 기억하지 않으므로 서버를 늘려도 문제없는, SaaS 수평 확장의 전제입니다. 균일한 인터페이스는 "리소스(명사) + 표준 메서드(동사)" 규칙으로, 문서를 안 봐도 API를 추측해 쓸 수 있게 합니다. → 코어 1 (1.1절)

   </details>

2. 요청 데이터를 담는 네 위치와 성격별 배치 규칙은? 이 규칙으로 보면 필터를 경로에 넣지 말아야 하는 이유와, 반대로 필수 필터를 경로로 옮겨야 하는 경우는?

   <details markdown="1"><summary>답 확인</summary>

   위치는 경로·쿼리·헤더·본문이며, 리소스 식별자는 경로, 리소스 표현(생성/수정 내용)은 본문, 리소스 수정자(필터·정렬·페이징·옵션)는 쿼리(표준 헤더로 표현 가능하면 헤더)에 둡니다. GET/DELETE에는 본문을 쓰지 않고 인증 토큰은 `Authorization` 헤더에 둡니다. 필터는 선택적 수정자이므로 `/products/book/design` 대신 `/products?type=book&q=design`처럼 쿼리에 두지만, 필수 필터가 계속 붙는다면 식별자일 수 있으므로 `GET /transactions?accountId=1` 대신 `GET /accounts/1/transactions`로 경로에 넣습니다. → 코어 1 (1.2절, 1.4절)

   </details>

3. 안전(Safe)과 멱등(Idempotent)의 차이를 말하고, 다섯 메서드를 분류해 보세요. GET으로 데이터를 바꾸면 안 되는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   안전은 서버 상태를 바꾸지 않는 것, 멱등은 여러 번 보내도 결과가 한 번 보낸 것과 같은 것입니다. GET은 안전·멱등, PUT·DELETE는 멱등만, POST는 둘 다 아님, PATCH는 보통 비멱등(구현에 따라)입니다. 크롤러·프리페치·캐시가 GET을 마음대로 반복 호출하므로 GET으로 데이터를 바꾸면 안 됩니다. → 코어 1 (1.3절)

   </details>

4. POST vs PUT(생성), PUT vs PATCH(수정)를 구분하고 PATCH 본문 형식 권장안을 말해 보세요.

   <details markdown="1"><summary>답 확인</summary>

   `POST /products`는 서버가 ID를 만들고(대부분의 생성), `PUT /products/{isbn}`은 클라이언트가 전역 유일한 ID를 정할 때 씁니다(없으면 생성, 있으면 교체). 컬렉션에 PUT은 전체 교체가 되므로 쓰지 않습니다. PUT은 전체를 보내 빠진 필드는 없는 값이 되고, PATCH는 바뀐 필드만 보냅니다. PATCH는 JSON Merge Patch(RFC 7396)가 흔하고 쉬우며(배열은 통째로 교체), JSON Patch(RFC 6902)는 복잡해 권장하지 않습니다. → 코어 1 (1.3절)

   </details>

5. 생성 성공, 반환할 것 없는 수정/삭제, 나중에 처리할 작업 접수, 검색 결과 0건은 각각 어떤 상태코드로 응답하나요? `POST /transfers`에서 출금 계좌가 없을 때 404가 틀린 이유는?

   <details markdown="1"><summary>답 확인</summary>

   생성은 201 Created + `Location` 헤더, 반환할 것 없는 수정/삭제는 204, 접수는 202 Accepted, 검색 0건은 200 + 빈 목록입니다. 404는 `/transfers` 자체가 없다는 뜻이 되므로, 본문 내용의 문제는 400(또는 422)을 씁니다. → 코어 1 (1.5절)

   </details>

6. CRUD로 표현하기 어려운 "행위" 연산을 설계하는 세 가지 방식은? 명사화의 이점은?

   <details markdown="1"><summary>답 확인</summary>

   행위 리소스(`POST /carts/{id}/check-out`, RFC 9110상 유효), 행위를 명사로(`POST /checkouts`), 결과를 리소스로(`POST /orders`)입니다. 명사로 승격하면 목록 조회, 상태 확인, 비동기 처리로 확장하기 쉽습니다. 동사를 명사로 바꾸기 어려우면 `-ing/-ment/-tion`을 붙여 봅니다(execute → executions). → 코어 1 (1.6절)

   </details>

7. DTO 7종을 말하고, 서버 관리 값을 요청에서 받으면 안 되는 이유와 응답을 항상 객체로 감싸야 하는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   Complete, Summarized, Minimal, Identifier와 Creation, Replacement, Modification(모든 속성 선택)입니다. id·createdAt·role 같은 서버 관리 값을 클라이언트가 넣게 하면 권한 상승(mass assignment) 사고가 납니다. 응답이 배열이면 나중에 페이지 정보를 추가할 때 계약이 깨지므로 처음부터 `{ data, metadata }`로 시작합니다. → 코어 2 (2.1절)

   </details>

8. 날짜, 금액, 코드값은 어떻게 표현해야 하나요? 또 Postel의 법칙은 입력과 응답에 어떻게 적용되나요?

   <details markdown="1"><summary>답 확인</summary>

   날짜는 ISO 8601 문자열에 기본 UTC(`2024-03-10T14:10:00Z`)로, 초/밀리초가 헷갈리는 Unix timestamp는 피합니다. 금액은 숫자와 통화를 분리한 객체(`{ value, currency }`)로, `"1,234.5"` 같은 포맷 문자열은 피합니다. 코드값은 `1`, `7` 대신 사람이 읽을 수 있는 값(`"checking"`)이나 코드 + 라벨로 줍니다. Postel의 법칙("받을 때는 너그럽게, 줄 때는 엄격하게")에 따라 날짜는 여러 형식을 받아 주되 응답은 항상 UTC로 통일하고, 수정 요청에 섞인 모르는/수정 불가 필드는 400 대신 무시하며, 필수 입력은 최소화합니다. → 코어 2 (2.1절, 2.2절)

   </details>

9. 오프셋 페이징과 커서 페이징을 비교하고, 목록 API에 반드시 둬야 할 안전장치는?

   <details markdown="1"><summary>답 확인</summary>

   오프셋(`?page=3&size=10`)은 구현이 간단하고 특정 페이지 점프가 가능하지만 뒤 페이지일수록 느리고 도중에 데이터가 바뀌면 중복/누락됩니다. 커서(`?after=...`)는 대용량에서 빠르고 변경에 강하지만 다음/이전만 가능하며 정렬 기준이 고유·순차 값이어야 하고, 커서는 불투명 문자열로 줍니다. 페이지 크기 상한(예: 최대 100)을 반드시 두고 기본·최소 크기도 정하며, 적용된 기본값을 metadata로 알려 줍니다. → 코어 2 (2.3절)

   </details>

10. 좋은 에러 응답의 조건과 Problem Details(RFC 9457)의 주요 필드는?

    <details markdown="1"><summary>답 확인</summary>

    알맞은 상태코드, 사람이 읽고 해결할 수 있는 메시지, 기계 판독용 정보, 가능한 모든 오류를 한 번에, 표준 형식입니다. 필드는 `status`, `type`(오류 종류 URI), `title`(종류의 짧은 설명), `detail`(이번 건 설명), `instance`(이번 건 참조 식별자), 확장 `errors`(필드별 상세)이며 `Content-Type: application/problem+json`을 씁니다. 500에는 내부 정보 대신 추적용 참조 번호만 줍니다. → 코어 2 (2.4절)

    </details>

11. Idempotency-Key는 어떻게 동작하나요? 원서 설명과 실무 보충의 차이, 그리고 업무 규칙 기반 중복 감지는?

    <details markdown="1"><summary>답 확인</summary>

    클라이언트가 요청마다 고유 키를 헤더에 담고, 원서 기준으로 서버는 같은 키가 이미 왔으면 다시 처리하지 않고 409를 돌려줍니다. 실무 보충으로는 저장해 둔 이전 응답을 재생하거나 키를 일정 기간 뒤 만료시키며, 키 확인과 저장은 원자적이어야 합니다(유니크 제약, `SET NX`). 재시도마다 새 키를 만드는 경우를 위해, 최근 1분 내 같은 금액·계좌의 이체를 409로 막고 의도한 반복은 `Confirm-Duplicate: true`로 강제하게 하는 업무 규칙 기반 감지도 있습니다. → 코어 3 (3.1절)

    </details>

12. 갱신 유실을 ETag + If-Match로 막는 흐름과, 조건부 갱신을 뒤늦게 필수로 바꾸면 생기는 문제는?

    <details markdown="1"><summary>답 확인</summary>

    GET 응답의 ETag(리소스 버전)를 받아 두고, PUT/PATCH 때 `If-Match`에 담아 "내가 읽은 버전일 때만 수정"을 요청합니다. 일치하면 200, 그 사이 누가 바꿨으면 412 Precondition Failed를 받고 다시 읽어 재시도합니다. 뒤늦게 필수로 바꾸면 기존 클라이언트가 수정을 전혀 못 하게 되므로 처음부터 정하는 편이 좋습니다. 대안으로 `Last-Modified` + `If-Unmodified-Since`도 있습니다. → 코어 3 (3.1절)

    </details>

13. 401, 403, 404, 500을 보안 관점에서 어떻게 구분해 쓰나요? UUID를 쓰거나 토큰에 스코프가 있으면 권한 검사를 생략해도 될까요?

    <details markdown="1"><summary>답 확인</summary>

    토큰이 없거나 만료·잘못됨은 401, 토큰은 유효하나 스코프/권한 부족(존재 사실 공개 가능)은 403, 존재 사실 자체를 숨겨야 할 때(남의 테넌트 리소스)는 404, 서버 내부 오류는 500(내부 정보 은닉)입니다. UUID처럼 추측하기 어려운 ID도 보안이 아니므로, 항상 토큰의 사용자·테넌트 정보와 요청 입력을 대조해야 합니다(IDOR 방지). 또 스코프가 있다고 실행이 보장되지도 않습니다. 스코프는 "앱이 이 연산을 부를 자격이 있는가"이고, 비즈니스 규칙과 최종 사용자 권한은 구현이 별도로 검사합니다(송금 스코프가 있어도 고액 송금 권한이 없으면 거절). 스코프 검사는 보통 게이트웨이가, 사용자 권한은 구현이 맡습니다. 스코프가 없으면 인증된 앱이 모든 연산을 호출할 수 있고, `write` 같은 통짜 스코프는 필요 없는 앱에도 송금 권한이 딸려 갑니다. → 코어 2 (2.4절), 코어 3 (3.2절)

    </details>

14. `Cache-Control`의 `no-store`와 `no-cache`는 어떻게 다르며, 조건부 조회는 어떻게 동작하나요?

    <details markdown="1"><summary>답 확인</summary>

    `no-store`는 저장 금지(민감/실시간 데이터), `no-cache`는 저장은 가능하지만 사용 전 재검증이 필수입니다(이름과 달리 캐시 불가가 아님). 조건부 조회는 `If-None-Match`에 가진 ETag를 보내 바뀌지 않았으면 304 Not Modified(본문 없음), 바뀌었으면 200 + 새 ETag + 새 본문을 받습니다. 캐시 정책은 데이터 성격으로 정하고 서버가 응답에 명시합니다. → 코어 4 (4.1절)

    </details>

15. 대량 작업의 두 가지 오류 정책과 부분 성공 시 응답 방식은?

    <details markdown="1"><summary>답 확인</summary>

    All-or-nothing은 하나라도 실패하면 전체 롤백(서로 의존하는 이체 묶음 등 정합성 중요), Mixed는 성공한 건은 반영하고 실패한 건만 보고합니다(독립적인 다건 등록). 부분 성공이면 207 Multi-Status로 건별 status·headers·body를 담습니다. 한 번에 받을 건수 상한을 두고, 오래 걸리면 비동기로 전환합니다. → 코어 4 (4.3절)

    </details>

16. 긴 작업을 비동기 API로 설계하는 방법과, 콜백과 웹훅의 차이는?

    <details markdown="1"><summary>답 확인</summary>

    접수 시 202 Accepted + `Location`으로 작업 리소스 위치를 알려 주고, 클라이언트는 그 리소스를 폴링해 `IN_PROGRESS`/`DONE`을 확인합니다. 폴링을 줄이도록 진행률, 예상 종료 시각, `Retry-After`를 줄 수 있습니다. 콜백은 소비자가 시작한 작업의 결과를 알리는 것이고(`callbacks`에 정의), 웹훅은 제공자 쪽에서 발생한 이벤트를 알리는 것입니다. `Prefer: response=synchronous`로 실행 방식을 고르게 할 수도 있지만 주의해서 씁니다. → 코어 4 (4.4절)

    </details>

17. 웹훅 설계에서 이벤트 형식, Thin vs Thick, 보안 선택지, 수신 측 동작, 실패 처리 선택지를 정리해 보세요.

    <details markdown="1"><summary>답 확인</summary>

    형식은 CloudEvents(`source` + `id`로 유일 식별, 64KB 이하 권장)입니다. Thin은 ID/링크만(데이터가 자주 변하거나 크거나 민감할 때), Thick은 데이터를 함께(작고 변하지 않을 때)입니다. 보안은 공유 비밀키 서명, IP 허용 목록, 상호 TLS, OAuth 2.0을 조합합니다. 수신 측은 아무 2XX로 빨리 응답하고 이벤트를 DB/큐에 넣은 뒤 나중에 처리합니다. 실패 시 일반 API로 빈틈 채우기, 전용 조회 연산, 재전송 연산, 자동 재시도(예: 24시간 최대 5회)를 둡니다. 웹훅은 선택 사항이어야 합니다. → 코어 4 (4.5절)

    </details>

18. 응답 데이터와 요청 데이터에서 하위 호환 판정이 어떻게 반대인지 예를 들어 설명해 보세요.

    <details markdown="1"><summary>답 확인</summary>

    응답에 새 속성 추가는 호환이지만, enum 값 추가·필수를 선택으로 변경·문자열 최대 길이 늘리기는 깨집니다(소비자가 모르는 값·누락·길이 초과를 처리 못 함). 요청은 반대로 선택 입력 추가·필수를 선택으로 완화·허용 범위/enum 확대가 호환이고, 필수 입력 추가·제약 강화·enum 값 제거가 깨집니다. 그 밖에 경로·메서드·상태코드·에러 형식·흐름 변경도 깨지며, 문서에 없는 관찰된 동작에도 소비자는 의존합니다(Hyrum의 법칙). → 코어 5 (5.1절)

    </details>

19. 버전 표현 방식 중 기본 권장은 무엇이고, 피해야 할 버전 관리 습관과 폐기 알림 방법은?

    <details markdown="1"><summary>답 확인</summary>

    경로(`/v1/accounts`)가 단순하고 흔해 기본 권장이며, 쿼리(`?version=2`)는 데이터와 메타데이터가 섞여 비권장입니다. 버전 방식은 처음부터 정하고, 리소스/연산별로 따로 버전을 매기지 않습니다. 폐기는 OpenAPI에 `deprecated: true`를 표시하고 폐기 예정 버전의 모든 응답에 `Sunset` 헤더(RFC 8594)로 폐기 시점을 알립니다. 깨는 변경 방지는 OpenAPI 전용 diff 도구를 CI에 넣어 자동 검사합니다. → 코어 5 (5.1절)

    </details>

20. 명세 우선과 코드 우선을 비교하고, ADR만으로 부족해 가이드라인과 린터가 필요한 이유는?

    <details markdown="1"><summary>답 확인</summary>

    명세 우선은 OpenAPI를 먼저 쓰고 합의 후 구현해 구현 전 리뷰·병렬 작업이 가능하고 계약이 진실의 원천이 되며(원서가 대체로 권장), 코드 우선은 코드와 문서 동기화가 쉽지만 구현 세부가 계약에 새고 설계 리뷰가 늦어집니다. ADR은 연산 하나를 설계할 때 경로·상태코드·페이징·에러 규칙을 여러 문서에서 찾아야 해 불편하므로, 작업 단위의 실행 가능한 레시피로 모은 가이드라인과 이를 자동 검사하는 API 린터가 필요합니다. → 코어 5 (5.2절)

    </details>

21. TCP가 시퀀스 번호로 재전송·중복을 처리해 주는데도 HTTP API에 Idempotency-Key가 필요한 이유는? 그리고 키 확인을 프로세스 안의 mutex로 보호하면 왜 부족한가?

    <details markdown="1"><summary>답 확인</summary>

    TCP의 중복 제거는 **한 연결 안**의 세그먼트에만 적용됩니다. 응답이 유실된 뒤 클라이언트가 새 연결로 같은 요청을 다시 보내면 TCP는 그것을 새 데이터로 보므로, 애플리케이션이 키로 중복을 판정해야 합니다. 그 재시도는 다른 서버 인스턴스로 갈 수 있으므로 한 프로세스의 mutex로는 막을 수 없고, 모든 인스턴스가 공유하는 저장소에서 원자적으로(DB 유니크 제약, Redis `SET NX`) 확인·저장해야 합니다. → 코어 3 (3.1절)

    </details>

22. opcode 기반 패킷 프로토콜과 REST의 "리소스 + 메서드" 방식은 무엇이 다르고, 그 차이 때문에 GET에 상태 변경을 넣으면 왜 위험한가?

    <details markdown="1"><summary>답 확인</summary>

    opcode는 기능마다 번호를 새로 만드는 방식이고 그 의미는 우리 서버 코드만 압니다. REST는 명사 URL과 소수의 표준 메서드를 조합하며, 메서드의 안전·멱등 의미가 표준이라 크롤러·프리페치·캐시·프록시 같은 제3자가 그 의미대로 행동합니다. 그래서 GET에 상태 변경을 넣으면 우리가 의도하지 않은 반복 호출로 데이터가 바뀔 수 있습니다. → 코어 1 (1.3절)

### 3. 기억 고리

- **C++ 유추 — 패킷 시퀀스 번호 → Idempotency-Key:** 둘 다 재전송 때문에 같은 처리가 두 번 되는 것을 막는다. ⚠️ 시퀀스 번호는 한 연결 안에서만 유효하지만, HTTP 재시도는 새 연결·다른 서버로 오므로 키를 공유 저장소에 원자적으로 남겨야 한다.
- **C++ 유추 — CAS(compare-and-swap) → ETag + If-Match:** "읽은 값이 그대로일 때만 바꿔라". ⚠️ 기대값(ETag)을 클라이언트가 들고 다니고, 실패(412) 시 서버가 아니라 클라이언트가 다시 읽고 판단한다.
- **C++ 유추 — 세션 객체 → 무상태 + 토큰:** 요청 처리에 "누구인가"가 필요한 점은 같다. ⚠️ 연결에 컨텍스트가 붙지 않으므로 매 요청이 토큰을 들고 오고, 권한·테넌트 검사도 매 요청 다시 한다(연결 단위 신뢰 없음).
- **C++ 유추 — 프로토콜 버전 체크/강제 업데이트 → API 버전·하위 호환:** 둘 다 클라·서버 계약을 관리한다. ⚠️ 공개 API 소비자는 강제 업데이트할 수 없으므로 "깨지지 않게 바꾸는 규칙"과 `Sunset` 예고가 필요하다.
- **비유:** 공개 API = 이미 인쇄해 배포한 계약서. 한 글자(`sts` → `status`)만 바꿔도 서명한 모든 상대(클라이언트)가 깨진다. ⚠️ 비유가 깨지는 지점: 계약서는 조항을 추가하면 모두 다시 동의해야 하지만, API는 응답에 새 속성을 추가하는 것처럼 상대 동의 없이도 안전한 변경이 있고, 반대로 enum 값 추가처럼 "추가"인데도 깨지는 변경이 있다.
- **비유:** 웹훅 = 반대 방향 API(택배 도착 문자). 고객이 계속 확인(폴링)할 필요 없이 우리가 먼저 알린다. ⚠️ 비유가 깨지는 지점: 문자는 한 번 보내면 끝이지만, 웹훅은 실패 재시도로 중복 도착할 수 있어 수신자가 멱등하게 처리해야 하고, 웹훅을 못 받아도 일반 API로 같은 정보를 얻을 수 있어야 한다.
- **묶음(3의 법칙):** 데이터 위치 3원칙(식별자 = 경로 / 표현 = 본문 / 수정자 = 쿼리), 상태코드 3클래스(2XX 성공 / 4XX 소비자 / 5XX 우리), 목록 3종 세트(필터 / 정렬 / 페이징), 행위 연산 3방식(행위 리소스 / 명사화 / 결과 리소스), 권한 응답 3종(401 인증 / 403 권한 / 404 존재 은닉).
- **대칭·순서:** 정합성 방어 쌍 — Idempotency-Key(중복 요청 → 409) ↔ ETag + If-Match(갱신 유실 → 412). 조회 쪽 짝 — If-None-Match → 304. 하위 호환 판정은 응답(출력)과 요청(입력)이 서로 반대. 긴 작업 흐름: 작업 시작(202) → 상태 확인 → 결과 조회.
