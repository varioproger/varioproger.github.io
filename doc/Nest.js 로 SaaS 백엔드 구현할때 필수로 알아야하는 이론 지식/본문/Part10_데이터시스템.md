# Part 10. 데이터 시스템 기초 (출처: Designing Data-Intensive Applications, 2nd ed.)

SaaS 백엔드는 결국 "데이터를 안전하게 저장하고, 빠르게 꺼내 주고, 여러 서버가 동시에 만져도 망가지지 않게 하는 일"이다. 이 부는 그 밑바닥에 깔린 원리를 쉬운 말로 정리한다. 특정 DB 제품 사용법이 아니라, **어떤 DB·큐·캐시를 쓰든 통하는 사고방식**이 목표다.

> 핵심 한 줄: 데이터 시스템에는 정답이 없고 **트레이드오프**만 있다. 무엇을 얻고 무엇을 내주는지 말할 수 있어야 한다.

---

### 1. 큰 그림: 운영 시스템, 분석 시스템, 원본과 파생 데이터

#### 1.1 운영(OLTP) vs 분석(OLAP)

| 구분 | OLTP (운영) | OLAP (분석) |
|---|---|---|
| 읽기 패턴 | 키로 몇 건 조회 (point query) | 수백만 행을 훑어 합계·평균 |
| 쓰기 패턴 | 한 건씩 생성·수정·삭제 | 대량 적재(ETL) 또는 이벤트 스트림 |
| 쿼리 | 애플리케이션 코드에 고정 | 분석가가 자유롭게 작성 |
| 데이터 의미 | 지금의 최신 상태 | 시간에 따른 이력 |
| 규모 | GB ～ TB | TB ～ PB |

- 서비스 DB에서 무거운 집계 쿼리를 돌리면 **다른 고객의 응답이 같이 느려진다.**
- 그래서 보통 분석은 별도 DB(데이터 웨어하우스)로 복사해서 한다. 복사 과정을 ETL(추출-변환-적재)이라 부른다.
- 웨어하우스는 원본 서비스 DB와 스키마도 다르다(별 모양 스키마, 넓은 팩트 테이블 등).

**왜 SaaS에서 중요한가:** "관리자 대시보드 통계 쿼리 때문에 서비스가 느려졌다"는 흔한 사고의 근본 원인이다. (보충) 초기엔 읽기 복제본으로, 커지면 분석 전용 저장소로 분리하는 순서가 무난하다. 원서는 분석용 웨어하우스를 별도로 두는 이유(서비스 성능 영향, 스키마 차이, 여러 시스템 데이터 결합)를 설명한다.

> 📖 원문: 1장 "Operational Versus Analytical Systems"

#### 1.2 원본(System of Record)과 파생 데이터(Derived Data)

- **원본(진실의 원천):** 새 데이터가 가장 먼저 기록되는 곳. 다른 곳과 값이 다르면 원본이 맞다.
- **파생 데이터:** 원본에서 가공해 만든 사본. 잃어도 원본에서 다시 만들 수 있다.
  - 예: 캐시, 검색 인덱스, 비정규화 컬럼, 머티리얼라이즈드 뷰, 집계 테이블
- 어떤 DB든 도구일 뿐이고, **"이 데이터는 원본인가 파생인가"는 쓰는 방식**이 정한다.
- 파생 데이터는 원본이 바뀔 때마다 갱신해야 한다. 이 "동기화"가 나중에 나올 정합성 문제의 뿌리다.

**왜 중요한가:** 캐시나 검색 인덱스의 값이 이상할 때 "원본이 맞다, 파생은 다시 만들면 된다"는 기준이 있으면 복구 절차가 단순해진다.

> 📖 원문: 1장 "Systems of Record and Derived Data"

#### 1.3 분산은 비용이다: 단일 노드로 충분하면 단순하게

서버를 여러 대로 나누는 이유는 분명하다: 장애 대비(이중화), 성능 확장, 지리적 가까움, 규제(데이터 국외 반출 금지) 등. 하지만 대가가 있다.

- 네트워크 호출은 언제든 실패하거나 시간 초과가 날 수 있고, **요청이 처리됐는지조차 모를 수 있다.**
- 프로세스 내 함수 호출보다 훨씬 느리고, 지연 시간이 들쭉날쭉하다.
- 디버깅이 어렵다 → 로그·메트릭·분산 추적(OpenTelemetry 등)이 필요하다.
- 서비스마다 DB를 따로 두면 서비스 간 정합성은 **애플리케이션 몫**이 된다.

마이크로서비스는 기술 문제보다 "여러 팀이 서로 기다리지 않게 하려는 조직 문제"의 해법에 가깝다. 팀이 작으면 오히려 오버헤드다. 요즘 단일 서버도 매우 강력하므로, **한 대로 되는 일은 한 대로 하는 게 가장 싸고 안전하다.**

> 🔗 NestJS 연결: 처음에는 하나의 NestJS 앱을 Module로 잘 나누는 모듈러 모놀리스로 시작하고, 나중에 분리 가능한 경계를 남겨 두면 된다.

> 📖 원문: 1장 "Distributed Versus Single-Node Systems", "Microservices and Serverless"

### 2. 성능·신뢰성·확장성·유지보수성

#### 2.1 성능 지표: 응답 시간, 처리량, 백분위수

- **응답 시간(response time):** 클라이언트가 요청을 보내고 답을 받을 때까지 전부. (처리 시간 + 대기열 + 네트워크)
- **처리량(throughput):** 초당 처리하는 요청 수. 필요한 서버 수(비용)를 결정한다.
- 부하가 한계에 가까워지면 **대기열 때문에 응답 시간이 급격히 늘어난다.**
- 응답 시간은 숫자 하나가 아니라 **분포**다. 평균은 "대부분 사용자가 겪는 값"을 알려 주지 못한다.

| 지표 | 의미 |
|---|---|
| p50 (중앙값) | 절반의 요청이 이보다 빠름. "보통 사용자" 경험 |
| p95 / p99 | 느린 5% / 1% 요청의 경계. **꼬리 지연(tail latency)** |
| p99.9 | 대형 서비스에서 핵심 고객 경험을 볼 때 |

- 느린 요청은 종종 **데이터가 많은 고객(가장 중요한 고객)** 에게 일어난다.
- **꼬리 지연 증폭:** 한 화면이 백엔드 호출 10개를 필요로 하면, 그중 하나만 느려도 화면이 느려진다. 호출이 많을수록 "느린 것에 걸릴 확률"이 커진다.
- 서버 대기열 지연은 서버 안에서는 안 보이므로 **클라이언트 관점에서도 측정**해야 한다.
- 백분위수는 평균내면 의미가 없다. 여러 서버 값을 합칠 때는 **히스토그램을 합친다.**
- **SLO**(목표: "p99 < 1초, 성공률 99.9%")와 **SLA**(못 지키면 보상하는 계약)를 구분한다.

**과부하의 악순환(재시도 폭풍):** 서버가 느려지면 클라이언트가 시간 초과 후 재시도 → 요청이 더 늘어남 → 더 느려짐. 대응책:
- 재시도 간격을 점점 늘리고 무작위로 흩뜨린다 (지수 백오프 + 지터)
- 계속 실패하는 대상은 잠시 호출을 끊는다 (서킷 브레이커)
- 서버는 한계에 다다르면 일부 요청을 미리 거절한다 (로드 셰딩), 클라이언트에 속도를 늦추라 신호한다 (백프레셔)

```ts
// (보충: 원서에 없는 예시 코드) 지수 백오프 + 지터 (재시도 폭풍 방지)
async function retry<T>(fn: () => Promise<T>, max = 5): Promise<T> {
  for (let i = 0; ; i++) {
    try { return await fn(); }
    catch (e) {
      if (i >= max) throw e;
      const base = Math.min(1000 * 2 ** i, 30_000);
      await new Promise(r => setTimeout(r, Math.random() * base)); // 지터
    }
  }
}
```

**왜 중요한가:** "평균 응답 200ms"만 보고 안심하면 상위 1% 고객의 불만을 놓친다. 모니터링 대시보드는 p50/p95/p99를 기본으로 잡는다.

> 🔗 NestJS 연결: Interceptor로 요청별 소요 시간을 측정해 히스토그램 메트릭(Prometheus 등)으로 내보내는 것이 전형적인 방식이다.

> 📖 원문: 2장 "Describing Performance"

#### 2.2 사례로 배우는 트레이드오프: 타임라인 팬아웃

SNS 홈 타임라인을 두 방식으로 만든다고 하자.

1. **읽을 때 계산:** 조회 시 팔로우한 사람들의 글을 조인해서 모은다 → 쓰기는 가볍지만 읽기가 매우 비싸다.
2. **쓸 때 미리 계산(머티리얼라이즈):** 글을 쓰는 순간 모든 팔로워의 타임라인에 복사해 둔다 → 읽기는 캐시처럼 빠르지만 **쓰기 한 번이 팔로워 수만큼 증폭(fan-out)** 된다.

팔로워가 수백만인 계정은 예외로 두고 조회 시 합치는 식으로 **섞어서** 푼다. 교훈: 미리 계산해 둔 결과는 **읽기를 싸게 하는 대신 쓰기와 동기화 비용을 낸다.** 이는 캐시·집계 테이블·비정규화 전부에 적용되는 원리다.

> 📖 원문: 2장 "Case Study: Social Network Home Timelines"

#### 2.3 신뢰성 (Reliability)

- **결함(fault):** 시스템 일부의 고장 (디스크 하나, 외부 API 장애).
- **실패(failure):** 시스템 전체가 서비스를 못 함. 좋은 설계는 **결함이 실패로 번지지 않게** 한다.
- 하드웨어 고장은 대체로 서로 독립적이라 이중화로 막기 쉽다(다만 같은 랙·데이터센터 단위로 함께 죽는 상관관계는 있다). **소프트웨어 버그는 모든 서버에 동시에 터져** 훨씬 위험하다 (같은 코드, 같은 입력). 예: 2012년 윤초 때 리눅스 커널 버그로 많은 Java 앱이 동시에 멈췄다.
- 연쇄 장애: 한 곳의 느려짐이 다음 곳을 과부하 시키며 번진다.
- 운영 사고의 주된 원인은 **사람의 설정 변경**이다. 대응: 롤백 수단, 점진 배포, 좋은 모니터링, 테스트.
- 사고 후에는 개인 탓이 아니라 **시스템/프로세스 원인**을 찾는 무비난(blameless) 사후분석을 한다.
- 일시적 중단은 견딜 수 있어도 **데이터 유실·손상은 치명적**이다. (보충) 그래서 백업과 복구 연습이 필수다.

> 📖 원문: 2장 "Reliability and Fault Tolerance"

#### 2.4 확장성 (Scalability)와 유지보수성

- "이 시스템은 확장 가능하다"는 말은 무의미하다. **"어떤 부하가 어떻게 늘면 무엇을 할 것인가"** 로 말해야 한다.
- 부하를 숫자로 파악한다: 초당 요청 수, 읽기/쓰기 비율, 캐시 적중률, 사용자당 데이터량 등.
- **수직 확장(scale up):** 더 큰 서버. 단순하지만 비용이 가파르게 오르고 한계가 있다.
- **수평 확장(scale out):** 서버를 여러 대. 이론상 선형 확장이지만 분산 시스템의 복잡도를 떠안는다(샤딩 등).
- 규모가 10배 커지면 구조를 다시 생각하게 된다. 그러나 **미리 10배 이상 대비하는 것은 낭비**인 경우가 많다. 초기 스타트업의 최우선은 단순함과 유연함이다.

유지보수성 3요소:
- **운영 용이성(Operability):** 모니터링, 문서화, 예측 가능한 동작, 서버 한 대 빼도 무방한 구조
- **단순성(Simplicity):** 복잡도를 줄이는 최고의 도구는 좋은 추상화 (SQL·트랜잭션 자체가 추상화)
- **진화 가능성(Evolvability):** 요구사항 변화에 맞춰 바꾸기 쉬움. 되돌릴 수 없는 결정(데이터 마이그레이션 등)은 신중히

**왜 중요한가:** 소프트웨어 비용의 대부분은 만든 뒤 유지에 든다. "지금 빠르게"보다 "나중에 바꾸기 쉽게"를 기준으로 삼자.

> 📖 원문: 2장 "Scalability", "Maintainability"

### 3. 데이터 모델: 관계형 vs 문서

#### 3.1 두 모델의 차이

| | 관계형 (테이블) | 문서 (JSON) |
|---|---|---|
| 강점 | 조인, 다대일·다대다 관계, 제약조건 | 트리 구조 데이터를 한 번에 읽기(지역성), 객체와 비슷한 모양 |
| 약점 | 객체 ↔ 테이블 변환(임피던스 불일치) | 조인이 약함, 관계가 많아질수록 불편 |
| 스키마 | 쓸 때 검증 (schema-on-write) | 읽을 때 해석 (schema-on-read) |

- 데이터가 "한 덩어리 문서"(예: 이력서, 설정 묶음)이고 통째로 읽고 쓰면 문서 모델이 잘 맞는다.
- (보충) 여러 엔티티가 서로 참조하는 SaaS 도메인(조직-사용자-구독-청구서 등)은 다대일·다대다 관계가 많아 관계형이 대부분 유리하다.
- 요즘은 둘이 수렴한다: 관계형 DB도 JSON 타입과 문서 내부 속성 인덱스를 지원하고, 문서 DB도 조인·보조 인덱스를 지원한다. (보충) "관계형 + 일부 JSONB 컬럼"이 실용적인 절충이다.

"스키마가 없다"는 말은 오해다. **스키마가 코드 속에 암묵적으로 있을 뿐**이다. 형식이 서로 다른 데이터가 섞여 있거나, 외부 시스템이 정한 구조일 때는 유연한 게 이득이고, 모든 레코드가 같은 구조라면 DB가 검증해 주는 스키마가 이득이다.

**문서 하나를 너무 크게 만들지 말 것:** 문서는 통째로 읽고 다시 쓰는 경우가 많다. 자주 조금씩 갱신되거나 무한히 늘어나는 배열(댓글 수천 개 등)은 별도 테이블이 낫다.

```ts
// (원서 예제를 TS로 옮김) 문서 모델에서 스키마 변경: 읽는 쪽이 옛날 형식도 처리해야 한다
function normalize(user: any) {
  if (user.name && !user.firstName) user.firstName = user.name.split(' ')[0];
  return user;
}
// 관계형: 기본값 NULL 컬럼 추가는 빠르지만, 대량 UPDATE 백필은 모든 행을 다시 쓰므로 오래 걸릴 수 있다
// ALTER TABLE users ADD COLUMN first_name text DEFAULT NULL;
```

> 📖 원문: 3장 "Relational Versus Document Models"

#### 3.2 정규화 vs 비정규화, 그리고 N+1

- **정규화:** 한 사실을 한 곳에만 저장하고 ID로 참조. 수정이 쉽고 일관성이 좋다. 읽을 때 조인이 필요하다.
- **비정규화:** 같은 정보를 여러 곳에 복사. 읽기가 빠르지만 **모든 사본을 갱신**해야 하고 어긋날 위험이 있다.
- 비정규화는 사실상 "파생 데이터"다. 갱신 절차와 실패 시 처리 계획이 있어야 한다.
- OLTP는 대체로 정규화, 분석은 비정규화(읽기 전용 이력이므로 문제 적음)가 맞다.
- 자주 바뀌는 값(좋아요 수, 사용자 이름)은 복사하지 않고 **ID만 저장한 뒤 조회 때 채우는 것(hydration)** 이 낫다.
- 확실하지 않다면 **정규화로 시작**하고 실제 병목이 확인될 때 부분적으로 비정규화한다.

**N+1 문제(ORM의 함정):** 댓글 N개를 가져온 뒤, 댓글마다 작성자를 따로 조회하면 쿼리가 N+1번 나간다. 조인이나 미리 로딩(eager loading)으로 한 번에 가져와야 한다.

```ts
// 나쁨: 댓글마다 작성자 쿼리 (N+1)
const comments = await repo.find();
for (const c of comments) c.author = await users.findOne(c.authorId);

// 좋음: 관계를 함께 로딩 (보충: TypeORM 예)
const comments = await repo.find({ relations: { author: true } });
```

**왜 중요한가:** ORM은 편하지만 느린 쿼리와 동시성 버그를 쉽게 숨긴다. 생성되는 SQL을 볼 줄 알아야 한다.

> 📖 원문: 3장 "Normalization, Denormalization, and Joins", "The Object-Relational Mismatch"

#### 3.3 이벤트 소싱과 CQRS 개요

- **이벤트 소싱:** 현재 상태를 덮어쓰는 대신, "무슨 일이 일어났는가"를 **과거형 이벤트**("좌석이 예약됨")로 순서대로 추가만 한다. 현재 상태는 이벤트를 재생해서 얻는다.
- **CQRS:** 쓰기용 모델(이벤트 로그)과 읽기용 모델(조회에 최적화된 뷰)을 분리한다. 읽기 뷰는 언제든 이벤트를 다시 재생해 재구축할 수 있다.
- 장점: 변경 이유가 남는 감사 로그, 새 조회 화면을 이벤트로 새로 만들 수 있음, 잘못된 처리는 "정정 이벤트"로 되돌림
- 단점/주의:
  - 이벤트는 수정·삭제하지 않으므로 **개인정보 삭제 요구(GDPR)** 와 충돌한다 → 개인정보는 이벤트 밖에 두거나 암호화 후 키를 지우는 방식(crypto-shredding)
  - 환율처럼 외부 값을 참조하면 재생 결과가 달라진다 → 이벤트에 값을 함께 기록
  - 재생 시 이메일 재발송 같은 부작용 주의
- 원서는 감사 로그가 필요한 규제 산업에서 유용하다고 언급한다. (보충) 모든 CRUD 앱에 필요한 것은 아니며, 결제·정산처럼 이력이 핵심인 도메인에서 고려한다.

> 🔗 NestJS 연결: `@nestjs/cqrs` 모듈이 Command/Query/Event 분리를 제공한다. 다만 패턴 도입 비용을 감안해 필요한 모듈에만 적용한다.

> 📖 원문: 3장 "Event Sourcing and CQRS"

### 4. 저장소 엔진 기초: 인덱스, B-Tree, LSM, 컬럼 저장

#### 4.1 인덱스는 "읽기 이득 vs 쓰기 비용"의 거래

- 가장 단순한 DB는 파일 끝에 추가만 하는 로그다. 쓰기는 매우 빠르지만 읽기는 처음부터 훑어야 한다.
- **인덱스**는 원본에서 파생한 추가 구조로, 읽기를 빠르게 한다. 대신 **쓰기마다 인덱스도 갱신**해야 하고 디스크도 쓴다.
- 그래서 DB는 인덱스를 자동으로 다 만들지 않는다. **실제 쿼리 패턴을 보고 필요한 것만** 만든다.

#### 4.2 두 가지 큰 계열

**(1) 로그 구조 저장 – LSM-Tree** (RocksDB, Cassandra 등)
1. 쓰기는 먼저 메모리의 정렬된 구조(memtable)에 넣고, 장애 대비로 로그에도 기록한다.
2. 메모리가 차면 정렬된 불변 파일(SSTable)로 디스크에 쓴다.
3. 읽기는 메모리 → 최신 파일 → 오래된 파일 순으로 찾는다. 블룸 필터로 "이 파일엔 없다"를 빨리 판단한다.
4. 백그라운드에서 파일을 합치며(compaction) 오래된 값과 삭제 표식(tombstone)을 정리한다.

**(2) B-Tree** (PostgreSQL, MySQL 등 대부분 관계형 DB)
- 고정 크기 페이지(4~16KB)의 트리. 제자리 덮어쓰기.
- 깊이가 3~4단계에 불과해 조회가 안정적으로 빠르다. 범위 검색도 쉽다.
- 페이지 분할 중 죽어도 복구할 수 있게 **WAL(write-ahead log)** 을 먼저 쓴다.

| | B-Tree | LSM-Tree |
|---|---|---|
| 잘하는 것 | 읽기, 범위 조회, 예측 가능한 성능 | 쓰기 처리량, 압축 |
| 주의점 | 페이지 단위 쓰기, 조각화(vacuum 필요) | 컴팩션이 쓰기 대역폭을 나눠 씀, 읽기가 여러 파일을 뒤짐 |
| 대표 | 일반적인 SaaS 관계형 DB | 쓰기 폭주(로그, 시계열, 메시지) |

원서의 경험칙은 "LSM은 쓰기 위주에, B-Tree는 읽기에 유리하지만 벤치마크는 워크로드에 민감하므로 내 데이터로 측정하라"이다. (보충) 일반 SaaS 업무 데이터는 B-Tree 기반 관계형 DB로 충분한 경우가 많다.

#### 4.3 인덱스 종류 몇 가지

- **기본 키 인덱스 / 보조(secondary) 인덱스:** 보조 인덱스는 값이 중복될 수 있다. `user_id`, `tenant_id`처럼 자주 검색하는 컬럼에 만든다.
- **클러스터드 인덱스:** 행 자체가 인덱스 안에 저장됨 (MySQL InnoDB의 기본 키).
- **커버링 인덱스:** 쿼리에 필요한 컬럼까지 인덱스에 포함시켜 테이블을 안 읽고 답한다. 읽기는 빨라지고 쓰기·용량 비용이 늘어난다.
- **인메모리 DB(Redis 등):** 디스크가 아니라 메모리에서 서비스. 디스크 로그·스냅샷으로 내구성을 얻기도 하고(설정에 따라 약한 내구성), 우선순위 큐·집합 같은 자료구조를 그대로 제공하는 장점도 있다.

```sql
-- (보충: 원서에 없는 예시) 멀티테넌트에서 흔한 복합 인덱스: 테넌트 → 생성일 순으로 조회
CREATE INDEX idx_orders_tenant_created ON orders (tenant_id, created_at DESC);
```

#### 4.4 분석용 저장: 컬럼 지향

- 웨어하우스의 표는 컬럼이 100개 넘게 넓은데, 쿼리는 그중 4~5개만 읽는다.
- **행 지향:** 한 행의 모든 값이 붙어 있다 → 조회/수정 한 건에 유리(OLTP).
- **컬럼 지향:** 같은 컬럼 값끼리 붙어 있다 → 필요한 컬럼만 읽고 압축이 잘 된다(OLAP). Parquet이 대표적 파일 포맷.

**왜 중요한가:** "인덱스를 걸면 빨라진다"만 아는 것과 "쓰기가 느려지고 용량이 는다"까지 아는 것은 다르다. 슬로우 쿼리를 고칠 때 인덱스 추가의 비용을 함께 따진다.

> 📖 원문: 4장 "Storage and Indexing for OLTP" (로그 구조 저장, B-Trees, 비교, 보조·커버링 인덱스, 인메모리), "Column-Oriented Storage"

### 5. 인코딩과 스키마 진화: 배포 중에는 옛 버전과 새 버전이 공존한다

#### 5.1 왜 호환성이 중요한가

- 서버는 **롤링 배포**(한 대씩 교체)를 한다. 잠시 동안 옛 코드와 새 코드가 함께 돈다.
- 모바일 앱·외부 API 클라이언트는 우리가 강제로 업데이트할 수 없다.
- DB 안의 데이터는 5년 전 것도 남아 있다 ("데이터는 코드보다 오래 산다").

그래서 두 방향 호환성이 모두 필요하다.
- **하위(backward) 호환:** 새 코드가 옛 데이터를 읽을 수 있음. (비교적 쉽다)
- **상위(forward) 호환:** 옛 코드가 새 데이터를 읽을 수 있음(모르는 필드는 무시). (더 까다롭다)

함정: 옛 코드가 새 필드를 모른 채 객체를 읽고 → 수정하고 → 저장하면 **새 필드가 사라진다.** 모르는 필드를 보존하도록 주의한다.

#### 5.2 API·이벤트 변경 시 실전 규칙 (REST/JSON 기준)

| 변경 | 안전한가 |
|---|---|
| 응답에 필드 **추가** | 안전 (클라이언트가 모르는 필드를 무시하면) |
| 요청에 **선택** 파라미터 추가 | 안전 |
| 필드 삭제, 이름 변경, 타입 변경, 필수 필드 추가 | (보충: 위 원칙에서 유추) **호환성 깨짐** → 새 버전 필요 |

- 서버를 먼저 올리므로 요청은 하위 호환, 응답은 상위 호환이 필요하다. 외부 클라이언트는 강제 업데이트가 안 되어 호환성을 오래 유지해야 한다.
- 깨지는 변경이 필요하면 **URL이나 Accept 헤더로 버전을 나누고 옛 버전을 한동안 함께 유지**한다(원서: 표준 방식은 없다).
- (보충) DB 스키마는 "확장 → 이전 → 축소" 순으로 나눠 배포한다: (1) 컬럼 추가(nullable) → (2) 코드가 양쪽을 다 처리 → (3) 백필 → (4) 옛 컬럼 제거. 원서는 NULL 기본값 컬럼 추가는 빠르고 큰 백필은 느리다는 점만 언급한다.

#### 5.3 인코딩 형식 선택

- **언어 전용 직렬화(Java Serializable, pickle 등):** 다른 언어와 호환 안 됨, 임의 클래스 생성으로 **보안 취약점**이 되기 쉬워 임시 용도 외 금지.
- **JSON:** 사실상 표준. 단, 함정이 있다.
  - 숫자는 정수/실수 구분이 없다. **2^53보다 큰 정수는 JavaScript에서 부정확**해진다 → 64비트 ID는 **문자열**로 주고받는다.
  - 바이너리 데이터는 Base64로 (용량 약 33% 증가).
  - JSON Schema/OpenAPI로 형식을 문서화·검증할 수 있다.
- **Protobuf / Avro:** 스키마 기반 바이너리. 필드 이름을 데이터에 넣지 않아 "바이너리 JSON"보다 훨씬 작다(원서 예: 81바이트 JSON이 Protobuf 33바이트). 스키마가 곧 문서이며, 스키마 저장소로 호환성을 배포 전에 검사할 수 있고 코드 생성도 된다. gRPC는 Protobuf를 쓴다.
  - Protobuf는 필드 **번호(태그)** 로 필드를 식별한다. 규칙: 필드 이름은 바꿔도 되지만 번호는 바꾸지 않는다. 새 필드는 새 번호로 추가한다. 삭제한 번호는 재사용하지 않는다(reserved).
  - Avro는 태그 번호가 없고 쓰는 쪽·읽는 쪽 스키마를 **필드 이름으로** 맞춘다. DB 스냅샷을 스키마 자동 생성으로 덤프하는 용도에 유리하다.

```ts
// (보충: 원서 설명을 코드로 옮긴 예) JS에서 큰 ID 함정. 원서: X(트위터)는 ID를 숫자와 문자열로 둘 다 내려준다
JSON.parse('{"id": 9007199254740993}').id;  // 9007199254740992 (틀림!)
// 해결: API에서 ID는 문자열로
// { "id": "9007199254740993" }
```

> 🔗 NestJS 연결: `class-validator` + DTO는 요청 스키마를 검증하고, `@nestjs/swagger`는 OpenAPI 문서를 생성한다. 응답 DTO를 명시해 두면 필드 추가/삭제를 의도적으로 관리할 수 있다.

> 📖 원문: 5장 "Formats for Encoding Data", "The Merits of Schemas", 도입부(호환성)

#### 5.4 데이터가 흐르는 길: DB, 서비스 호출, 워크플로, 이벤트

**(1) DB를 통한 흐름:** 쓰는 쪽이 인코딩, 읽는 쪽이 디코딩. 여러 버전이 같은 DB를 만지므로 상·하위 호환이 모두 필요하다.

**(2) 서비스 호출(REST/RPC):**
- 원격 호출을 로컬 함수처럼 다루려는 시도(RPC의 "위치 투명성")는 근본적으로 결함이 있다.
  - 네트워크 요청은 **성공 / 실패 / 시간 초과(모름)** 세 결과가 있다.
  - 재시도하면 이미 처리된 요청이 **중복 실행**될 수 있다 → **멱등성 설계**가 필요하다.
  - 지연이 들쭉날쭉하고, 인자를 직렬화해야 한다.
- 보통 서버를 먼저, 클라이언트를 나중에 업데이트하므로 요청은 하위 호환, 응답은 상위 호환이 필요하다.
- 여러 서버 앞에는 로드 밸런서, 서비스 디스커버리가 필요하다.

**(3) 내구성 있는 워크플로(Durable Execution):**
- 결제 처리처럼 "사기 검사 → 카드 결제 → 계좌 입금" 여러 서비스 호출을 하나의 흐름으로 묶고 싶을 때, 단일 DB 트랜잭션으로 감쌀 수 없다.
- Temporal 같은 엔진은 각 단계의 결과를 로그로 남겨 두고, 중간에 죽으면 **이미 성공한 단계는 다시 하지 않고** 이어서 재개한다.
- 조건: 외부 API가 멱등이어야 하고(고유 ID 전달), 워크플로 코드는 결정적(deterministic)이어야 한다(무작위·현재시각 직접 사용 금지, 코드 순서 변경 주의).

**(4) 이벤트 기반(메시지 브로커):** 보내는 쪽은 응답을 기다리지 않고, 브로커가 중간에서 저장·전달한다.
- 장점: 받는 쪽이 죽어 있어도 완충, 자동 재전달, 여러 소비자에게 전달, 송수신 분리
- 메시지 스키마도 진화하므로 스키마 레지스트리나 명시적 버전 관리가 필요하다.

> 🔗 NestJS 연결: `@nestjs/microservices`(TCP, Redis, NATS, Kafka, RabbitMQ 등)와 BullMQ 기반 큐 모듈이 이 패턴의 구현 수단이다.

> 📖 원문: 5장 "Modes of Dataflow" (Dataflow Through Databases, REST and RPC, Durable Execution and Workflows, Event-Driven Architectures)

### 6. 복제 (Replication)

같은 데이터를 여러 서버에 복사해 두는 것. 목적은 셋: **지연 감소(가까운 복사본), 가용성(하나 죽어도 계속), 읽기 처리량 확장.**

> (보충) 복제는 백업이 아니다. 실수로 지운 데이터도 복제본에 똑같이 전파된다. 과거 시점으로 돌아갈 백업이 별도로 필요하다. (원서는 복제 로그를 스냅샷과 함께 오브젝트 스토어에 보관하는 방식을 백업·재해복구 방법으로 소개한다.)

#### 6.1 리더-팔로워 복제 (가장 흔한 방식)

- **리더(primary):** 모든 쓰기를 받는다. 변경 내용을 복제 로그로 팔로워에게 전달한다.
- **팔로워(replica):** 로그를 같은 순서로 적용. 읽기 요청은 리더나 팔로워 어디든 가능.
- PostgreSQL, MySQL, MongoDB 등 대부분이 이 방식을 기본 제공한다.

**동기 vs 비동기 복제**

| | 동기 | 비동기 |
|---|---|---|
| 리더가 응답하는 시점 | 팔로워가 받은 뒤 | 팔로워를 기다리지 않고 |
| 내구성 | 팔로워에도 확실히 있음 | 리더가 죽으면 **최근 쓰기 유실 가능** |
| 가용성 | 팔로워가 멎으면 쓰기가 멈춤 | 쓰기 계속 가능 |

- 모든 팔로워를 동기로 하면 하나만 죽어도 전체가 멈춘다. 그래서 **팔로워 1개만 동기(반동기), 나머지는 비동기**가 흔한 타협이다.

**장애 처리**
- 팔로워 장애: 재시작 후 자기 로그 위치 이후의 변경을 리더에게서 받아 따라잡는다.
- 리더 장애 = **페일오버**: (1) 죽었다고 판단(보통 타임아웃) → (2) 가장 최신인 팔로워를 새 리더로 선출 → (3) 클라이언트가 새 리더로 쓰도록 재설정.
- 페일오버의 위험:
  - 비동기 복제면 새 리더에 없는 쓰기가 유실된다. (예: 뒤처진 새 리더가 자동 증가 ID를 재사용해 Redis와 어긋나 다른 사용자에게 데이터가 노출된 실제 사고가 있다.)
  - **스플릿 브레인:** 두 노드가 모두 자기가 리더라고 믿고 쓰기를 받음 → 데이터 손상
  - 타임아웃이 너무 짧으면 일시 과부하에도 불필요한 페일오버가 일어나 상황이 악화된다.
- 이런 위험 때문에 일부 운영팀은 자동 페일오버가 있어도 수동으로 한다(원서). (보충) 관리형 DB(RDS, Cloud SQL 등)를 쓰더라도 페일오버 시 짧은 쓰기 실패와 재연결이 일어날 수 있으니 앱에서 처리한다.

**복제 로그 방식(참고)**: 구문(SQL) 그대로 전달 → `NOW()`, `RAND()` 때문에 어긋날 수 있음 / WAL 바이트 전달 → 버전 결합이 강해 업그레이드가 어려움 / **논리(행 단위) 로그** → 저장 엔진과 분리되어 버전이 달라도 되고 **외부 시스템(CDC)** 으로 내보내기 쉽다.

> 📖 원문: 6장 "Single-Leader Replication" (동기/비동기, Setting Up New Followers, Handling Node Outages, Implementation of Replication Logs)

#### 6.2 복제 지연(Replication Lag)이 만드는 버그

읽기 복제본에서 읽으면 **아직 복제가 안 된 오래된 값**을 볼 수 있다. 결국은 맞아지므로 **최종적 일관성(eventual consistency)** 이라 부르지만, "결국"이 얼마인지는 보장이 없다(평소 1초 미만이지만 과부하나 네트워크 문제 시 수 초~수 분).

세 가지 대표 이상 현상:

1. **자기 쓰기 못 읽기 (read-your-writes 위반):** 프로필 저장 후 새로고침하니 옛 값이 보인다 → 사용자는 "저장이 안 됐다"고 느낀다.
   - 대책: 방금 수정한 사용자의 읽기는 리더로 보낸다 / 마지막 쓰기 후 N초간은 리더 읽기 / 마지막 쓰기 위치(LSN·타임스탬프)를 기억해 그 이상 최신인 복제본에서만 읽는다.
   - 여러 기기(웹+모바일)에서도 지켜지려면 그 정보가 중앙에 있어야 한다.
2. **시간이 거꾸로 감 (monotonic reads 위반):** 새로고침하니 방금 보인 댓글이 사라진다(더 뒤처진 복제본에 연결).
   - 대책: 같은 사용자는 항상 같은 복제본에서 읽게 한다(사용자 ID 해시로 고정).
3. **인과 순서 뒤집힘 (consistent prefix 위반):** 답변이 질문보다 먼저 보인다(샤드마다 지연이 다를 때).
   - 대책: 인과 관계 있는 쓰기를 같은 샤드에 모은다.

원칙: **"복제가 동기인 척"하면 문제가 생긴다.** 복제 지연이 몇 분이 되어도 괜찮은지 자문하고, 안 괜찮다면 위 대책을 설계에 넣거나 강한 일관성을 주는 DB를 쓴다.

```ts
// (보충: 원서 아이디어 "마지막 쓰기 후 일정 시간 리더 읽기"의 예시 구현) 쓰기 직후 일정 시간은 리더에서 읽기
const recentlyWritten = await redis.get(`wrote:${userId}`);
const db = recentlyWritten ? leaderConn : replicaConn;
// (쓰기 성공 시: await redis.set(`wrote:${userId}`, '1', 'EX', 10))
```

> 🔗 NestJS 연결: TypeORM/Prisma의 읽기 복제본 설정(replication 옵션)을 쓸 때 어떤 조회를 리더로 보낼지 Repository 계층에서 명시하는 것이 안전하다.

> 📖 원문: 6장 "Problems with Replication Lag", "Solutions for Replication Lag"

#### 6.3 다중 리더와 리더 없는 복제 (개요만)

- **다중 리더:** 여러 지역에 각각 리더를 두어 지역별로 빠르게 쓰기. 오프라인 편집 앱도 같은 구조. 문제는 **같은 데이터를 동시에 수정하면 충돌**한다는 점이다.
  - 충돌 회피(한 레코드의 쓰기는 항상 같은 리더로), **LWW(마지막 쓰기 승리)**, 값들을 보관 후 병합, CRDT 등.
  - **LWW는 동시 쓰기 중 하나를 조용히 버린다.** 시계 오차가 있으면 나중 쓰기가 버려지기도 한다.
- **리더 없는 복제(Dynamo 스타일: Cassandra 등):** 쓰기를 n개 복제본 중 w개에, 읽기를 r개에 요청하고 `w + r > n`이면 최신 값이 겹친다(쿼럼). 노드 몇 개가 죽어도 동작하지만, 그래도 엣지 케이스가 있어 "강한 일관성"은 아니다.
- 다중 리더에서는 "계좌가 음수가 되지 않기", "사용자명 유일" 같은 제약을 보장할 수 없다(원서). 그래서 제약이 필요하면 단일 리더가 낫고, 다중 리더는 설정 함정이 많아 "가능하면 피하라"는 평이 있다.
- (보충) 일반 SaaS는 **단일 리더 + 읽기 복제본**으로 대부분 충분하다.

> 📖 원문: 6장 "Multi-Leader Replication", "Dealing with Conflicting Writes", "Leaderless Replication" (Using quorums)

### 7. 파티셔닝 (샤딩) 기초

데이터가 한 대에 안 들어가거나 쓰기가 한 대로 감당이 안 될 때, 데이터를 **조각(샤드)으로 나눠 여러 노드에 분산**한다. 각 레코드는 정확히 한 샤드에 속하고, 각 샤드는 다시 복제된다.

> 샤딩은 무거운 해법이다. 읽기가 문제면 읽기 복제본으로, 한 대가 감당 가능하면 샤딩하지 않는 것이 좋다. 나눈 기준(파티션 키)을 나중에 바꾸기 매우 어렵다.

#### 7.1 어떻게 나누나

| 방식 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **키 범위** | 키 구간별로 샤드 (백과사전 권처럼) | 범위 조회 쉬움 | 시간순 키면 **최신 샤드에 쓰기가 몰림(핫스팟)** |
| **키 해시** | 해시값으로 분배 | 고르게 분산 | 범위 조회가 모든 샤드에 흩어짐 |

- 해시 % 노드수 방식은 노드 수가 바뀌면 **대부분의 키가 이동**한다. 그래서 샤드를 노드 수보다 훨씬 많이 만들어 두고 샤드 단위로 옮기거나, 해시 범위 분할 / 일관 해시를 쓴다.
- 복합 키의 첫 부분으로만 분산하면 (예: `tenant_id`로 분산, 그 안에서 시간순) **같은 파티션 키 안의 범위 조회는 효율적**이다.

#### 7.2 핫스팟

균등하게 나눠도 **부하는 균등하지 않을 수 있다.** 인기 계정 하나, 초대형 테넌트 하나가 한 샤드를 태운다.
- 아주 뜨거운 키에는 키 뒤에 난수를 붙여 쓰기를 분산시킬 수 있다. 대신 읽을 때 모두 모아야 한다.
- 뜨거운 키를 전용 샤드로 빼는 방식도 있다.
- 자동 리밸런싱은 편하지만, 과부하 노드를 죽은 것으로 오판해 **연쇄 장애**를 만들 수도 있어 사람이 개입하는 편이 안전한 경우도 있다.

#### 7.3 보조 인덱스와 샤딩

- **로컬 인덱스:** 각 샤드가 자기 데이터만 색인. 쓰기는 간단하지만 조건 검색은 **모든 샤드에 질의(scatter-gather)** 해야 하고 꼬리 지연이 커진다.
- **글로벌 인덱스:** 인덱스 자체를 검색어 기준으로 샤딩. 읽기는 빠르지만 쓰기가 여러 샤드에 걸쳐 일관성 유지가 어렵다.

#### 7.4 멀티테넌시와 샤딩 (SaaS 핵심)

SaaS에서 "고객(테넌트) 단위로 데이터를 나누는 것"은 자연스러운 샤딩 기준이다. 원서는 테넌트별 샤드(또는 작은 테넌트 묶음 샤드)를 이야기한다. 아래 표는 (보충) 실무에서 흔한 세 가지 구현 방식의 격리 수준 비교로, 원서에는 없다.

| 방식 | 격리 수준 | 비고 |
|---|---|---|
| 공유 테이블 + `tenant_id` 컬럼 | 낮음 (쿼리 실수 시 노출 위험) | 가장 단순, 초기 SaaS의 기본 |
| 테넌트별 스키마 | 중간 | 마이그레이션 수가 늘어남 |
| 테넌트별 DB(샤드) | 높음 | 운영 비용 증가 |

테넌트 단위 분리의 이점: **자원 격리**(시끄러운 이웃 방지), **권한 격리**(접근 제어 버그가 나도 남의 데이터 접근 가능성 감소), 장애 범위 축소(셀 기반 구조), **테넌트별 백업·복구**, 데이터 삭제·이전(GDPR, 데이터 거주지) 용이, 스키마 마이그레이션을 테넌트별로 점진 적용.
단점: 아주 큰 테넌트 하나는 한 노드에 안 들어갈 수 있고, 아주 작은 테넌트가 많으면 오버헤드가 크며, 테넌트를 가로지르는 기능(전체 통계 등)이 어려워진다.

```ts
// (보충) 공유 테이블 방식: 모든 쿼리에 tenant_id 조건을 강제하는 것이 핵심 (누락 = 데이터 노출 사고)
await repo.find({ where: { tenantId: ctx.tenantId, status: 'active' } });
// PostgreSQL RLS(행 수준 보안)로 DB 차원에서도 강제하면 더 안전 (원서 외 내용)
```

> 🔗 NestJS 연결: 요청 스코프 Provider나 Guard/Interceptor에서 테넌트 ID를 한 번 결정해 모든 Repository 호출에 주입하면 조건 누락을 줄일 수 있다.

> 📖 원문: 7장 "Pros and Cons of Sharding", "Sharding for Multitenancy", "Sharding of Key-Value Data", "Skewed Workloads and Relieving Hot Spots", "Sharding and Secondary Indexes"

### 8. 트랜잭션

트랜잭션 = 여러 읽기·쓰기를 **하나의 논리 단위**로 묶는 것. 성공하면 전부 반영(commit), 실패하면 전부 취소(rollback/abort). 덕분에 앱은 "일부만 성공한 상태"를 걱정하지 않고, **안전하게 재시도**할 수 있다.

#### 8.1 ACID의 진짜 의미

- **원자성(Atomicity):** 도중에 장애가 나면 지금까지의 쓰기를 모두 취소. (동시성이 아니라 "중단 가능성"이 핵심)
- **일관성(Consistency):** "계좌 합계는 항상 맞아야 한다" 같은 **앱이 정한 불변 조건**이 유지됨. 이것은 DB만으로 보장되지 않고, **제약조건(UNIQUE, FK, CHECK)을 선언**하고 트랜잭션을 올바르게 짜야 한다.
- **격리(Isolation):** 동시에 실행되는 트랜잭션이 서로 간섭하지 않음. 실제로는 성능 때문에 완전한 격리를 안 쓰는 경우가 많다(다음 절).
- **내구성(Durability):** 커밋된 데이터는 장애가 나도 남음(디스크 fsync + WAL, 복제). 절대적 보장은 없으므로 복제·백업을 함께 쓴다.

"ACID 호환"이라는 말은 제품마다 의미가 달라 **마케팅 용어에 가깝다.** 격리 수준이 구체적으로 무엇인지 확인해야 한다.

#### 8.2 단일 객체 vs 다중 객체

- 한 행/문서 수준의 원자성·격리는 거의 모든 DB가 보장한다. 원자적 증가(`value = value + 1`), 비교 후 쓰기(CAS) 같은 연산도 제공한다.
- **여러 행을 함께 바꿔야 하는 경우**(주문+재고, 이메일 저장+안읽은 개수 갱신, 인덱스와 데이터)에 다중 객체 트랜잭션이 필요하다. 없으면 중간 상태가 다른 사용자에게 보이거나, 실패 시 짝이 안 맞는 데이터가 남는다.

**재시도 시 주의:**
- 일시적 오류(교착, 직렬화 실패, 페일오버)만 재시도하고, 제약조건 위반 같은 영구 오류는 재시도해도 소용없다.
- 재시도에는 지수 백오프와 횟수 제한을 둔다.
- **커밋은 됐는데 응답만 유실된 경우** 재시도하면 중복 실행된다 → 멱등성/중복 제거가 필요하다.
- 트랜잭션 밖의 부작용(이메일 발송)은 롤백되지 않는다.
- 트랜잭션은 **짧게** 유지한다. 사용자 입력을 기다리는 동안 열어 두지 않는다(HTTP 요청 하나 안에서 끝낸다).

```ts
// (보충: 원서에 없는 예시) TypeORM: 이체를 하나의 트랜잭션으로
await dataSource.transaction(async (m) => {
  await m.decrement(Account, { id: from }, 'balance', amount);
  await m.increment(Account, { id: to }, 'balance', amount);
  // 도중 예외 → 자동 롤백
});
```

> 🔗 NestJS 연결: 서비스 메서드 단위로 트랜잭션 경계를 정하고, 필요하면 Interceptor나 `nestjs-cls` 등으로 트랜잭션 컨텍스트를 전달한다. 트랜잭션 안에서 외부 API 호출은 피한다.

> 📖 원문: 8장 "What Exactly Is a Transaction?" (The Meaning of ACID, Single-Object and Multi-Object Operations, Handling errors and aborts)

#### 8.3 격리 수준과 동시성 이상 현상

완전한 격리(직렬화 가능)는 성능 비용이 커서 대부분 DB의 기본값은 **약한 격리**다. 그래서 어떤 이상 현상이 어느 수준에서 막히는지 알아야 한다.

**이상 현상 정리**

| 현상 | 설명 | 예 |
|---|---|---|
| 더티 리드 | 커밋 안 된 값을 읽음 | 취소될 값을 보고 판단 |
| 더티 라이트 | 커밋 안 된 값을 덮어씀 | 두 구매자에게 물건과 송장이 엇갈려 배정 |
| 읽기 왜곡(read skew) | 한 트랜잭션 안에서 읽는 시점마다 상태가 다름 | 이체 중간에 조회해서 잔액 합계가 100 모자라 보임 |
| **갱신 손실(lost update)** | 읽고→수정→쓰기를 동시에 하면 한쪽이 사라짐 | 카운터 2번 증가가 1번만 반영 |
| **쓰기 왜곡(write skew)** | 같은 전제를 읽고 서로 다른 행을 수정해 불변 조건 위반 | 당직 의사 2명이 동시에 "나 빠질게" → 당직 0명 |
| **팬텀(phantom)** | 내 검색 조건에 맞는 새 행이 다른 트랜잭션에 의해 생김 | 회의실 이중 예약, 닉네임 중복 |

**주요 격리 수준**

1. **Read Committed** (PostgreSQL 등 기본값): 더티 리드/라이트를 막는다. 읽기 왜곡, 갱신 손실, 쓰기 왜곡은 **막지 못한다.**
2. **Snapshot Isolation** (PostgreSQL의 REPEATABLE READ, 여러 DB의 "repeatable read"): 트랜잭션 시작 시점의 일관된 스냅샷을 본다(MVCC: 행의 여러 버전을 보관). **읽기가 쓰기를, 쓰기가 읽기를 막지 않는다.** 백업·긴 분석 쿼리에 좋다. 읽기 왜곡은 막지만 **쓰기 왜곡과 팬텀은 여전히 가능**하다. (MySQL InnoDB의 repeatable read는 제품별 차이로 갱신 손실 탐지가 되지 않는다는 점도 주의)
3. **Serializable** (직렬화 가능): 마치 한 번에 하나씩 실행한 것과 같은 결과를 보장해 모든 이상 현상을 막는다. 구현은 (a) 실제 직렬 실행, (b) 2단계 잠금(2PL, 읽기·쓰기가 서로 막아 성능 저하와 교착 위험), (c) SSI(낙관적으로 진행하고 충돌하면 abort → 재시도) 중 하나다. 요즘 PostgreSQL의 SERIALIZABLE은 SSI다.

> 격리 수준의 이름은 DB마다 뜻이 다르다. 사용하는 DB 문서로 실제 동작을 확인한다.

**갱신 손실 막는 법 (실무 우선순위)**

1. **원자적 연산 사용** — 가장 간단하다.
   ```sql
   UPDATE counters SET value = value + 1 WHERE key = 'foo';
   ```
2. **명시적 잠금** — 읽으면서 행을 잠근다. 교착 가능하니 짧게, 순서를 일관되게.
   ```sql
   BEGIN;
   SELECT * FROM accounts WHERE id = 1 FOR UPDATE;
   -- 검증 후 UPDATE
   COMMIT;
   ```
3. **낙관적 잠금(버전 번호 CAS)** — 충돌이 드문 경우에 적합. 0행 갱신이면 재시도.
   ```sql
   UPDATE wiki SET content = $1, version = version + 1
   WHERE id = $2 AND version = $3;   -- 영향받은 행이 0이면 충돌
   ```
4. **DB의 자동 탐지** (PostgreSQL repeatable read 이상): 충돌 시 abort → 앱에서 재시도.

> ORM의 "읽어서 값 바꾸고 저장"은 대표적인 갱신 손실 함정이다. 카운터·잔액은 원자적 UPDATE로 쓴다.

**쓰기 왜곡/팬텀 막는 법**
- 가능하면 **UNIQUE 제약**으로 해결한다 (닉네임 중복, 이중 예약 슬롯 중복 등). 두 번째 트랜잭션이 위반으로 실패한다.
- 전제로 삼은 행이 존재한다면 `SELECT ... FOR UPDATE`로 잠근다.
- "없음"을 전제로 삽입하는 경우(팬텀)는 잠글 행이 없다 → **SERIALIZABLE 사용 + 재시도**, 또는 미리 만들어 둔 슬롯 행을 잠그는 방식(충돌의 물질화, 최후 수단).
- (보충: 원서에 없음) PostgreSQL에는 시간 범위 겹침을 막는 **EXCLUDE 제약**도 있다.

```sql
-- (보충) 회의실 이중 예약 방지를 DB 제약으로 (PostgreSQL)
ALTER TABLE bookings ADD CONSTRAINT no_overlap
  EXCLUDE USING gist (room_id WITH =, tstzrange(start_time, end_time) WITH &&);
```

**왜 SaaS에서 중요한가:** 이중 결제, 재고 초과 판매, 좌석·자원 중복 예약, 크레딧 초과 사용은 모두 이 동시성 이상 현상의 결과이며, 악의적 사용자가 요청을 동시에 쏘아 일부러 유발할 수도 있다. 낮은 확률의 버그도 보안 문제가 된다.

> 🔗 NestJS 연결: 격리 수준은 TypeORM `manager.transaction('SERIALIZABLE', ...)`처럼 지정한다. 직렬화 실패(예: PostgreSQL 40001)와 교착(40P01) 오류를 잡아 재시도하는 공용 래퍼를 만들어 두면 좋다.

> 📖 원문: 8장 "Weak Isolation Levels" (Read Committed, Snapshot Isolation and Repeatable Read, Preventing Lost Updates, Write Skew and Phantoms), "Serializability"

#### 8.4 분산 트랜잭션은 되도록 피한다

- 여러 노드/시스템에 걸친 트랜잭션은 **모두 커밋 또는 모두 중단**해야 한다(원자적 커밋). 대표 알고리즘이 **2단계 커밋(2PC)**: 코디네이터가 (1) "커밋할 수 있나?" 투표를 받고, (2) 모두 예라면 커밋을 지시.
- 문제: 투표 후 코디네이터가 죽으면 참여자는 **불확실 상태로 락을 잡은 채 대기**한다. 사람이 수동으로 풀어야 하는 일이 생긴다. 성능도 나쁘다.
- 같은 종류의 DB 내부(예: Spanner, CockroachDB)의 분산 트랜잭션은 잘 동작하지만, **서로 다른 시스템(DB+메시지 큐+외부 API)을 묶는 XA 트랜잭션은 운영이 어렵다.**
- 그래서 마이크로서비스에서는 보통 분산 트랜잭션 대신 **멱등성 + 재시도, 아웃박스** 로 정합성을 맞춘다(이 부의 12절, 원서 12장). (보충) 사가(보상 트랜잭션)도 흔한 대안이지만 원서 본문에서는 다루지 않는다. 서로 다른 시스템을 묶는 워크플로는 5.4절의 durable execution도 대안이다.

> 📖 원문: 8장 "Distributed Transactions" (Two-Phase Commit, Distributed Transactions Across Different Systems)

### 9. 분산 시스템의 문제 기초

#### 9.1 부분 실패와 네트워크

단일 컴퓨터는 대체로 "되거나 완전히 안 되거나"지만, 분산 시스템은 **일부만 고장**나고 그 상태가 **비결정적**이다. 무엇이 성공했는지조차 모를 수 있다.

요청을 보냈는데 응답이 없을 때 가능한 원인은 구별이 안 된다:
- 요청이 유실됨 / 상대가 죽음 / 상대가 느림 / **처리는 됐는데 응답이 유실됨**

TCP도 전달을 "신뢰"하는 것이지 **상대 앱이 처리했음**을 보장하지 않는다. 진짜 성공은 애플리케이션 응답으로만 확인된다.

- 타임아웃은 장애 감지의 유일한 수단이지만, **너무 짧으면 멀쩡한 노드를 죽은 것으로 오판**하고, 너무 길면 복구가 늦다. 오판하면 그 노드가 하던 일이 두 번 실행될 수 있다.
- 네트워크 지연은 상한이 없다. 분 단위 지연도 실제로 관찰된다.

**실무 규칙**
- 모든 외부 호출에 **타임아웃**을 건다 (기본값이 무제한인 라이브러리가 많다).
- 타임아웃 = "실패"가 아니라 "**모름**"으로 취급하고, 재시도 가능하게 **멱등**하게 설계한다.
- 재시도에는 백오프+지터를 쓴다.

```ts
// (보충: 원서에 없는 예시) Node.js: fetch에 타임아웃
const res = await fetch(url, { signal: AbortSignal.timeout(3000) });
// 타임아웃은 "서버가 처리 안 함"을 뜻하지 않는다 → 멱등 키와 함께 재시도
```

> 🔗 NestJS 연결: HttpModule(axios) 설정의 `timeout`, RxJS `timeout`/`retry` 연산자, 헬스체크(Terminus)로 방어선을 만든다.

> 📖 원문: 9장 "Faults and Partial Failures", "Unreliable Networks" (The Limitations of TCP, Fault Detection, Timeouts and Unbounded Delays)

#### 9.2 시계는 믿을 수 없다

| 시계 | 용도 | 주의 |
|---|---|---|
| **시각 시계(time-of-day)** | "몇 시 몇 분" (Date.now) | NTP 보정으로 **뒤로 점프**할 수 있음. 서버마다 오차. 경과 시간 측정에 부적합 |
| **단조 시계(monotonic)** | 경과 시간, 타임아웃 (`performance.now()`, `process.hrtime`) | 항상 앞으로만 감. 서로 다른 서버 간 비교는 무의미 |

- 서버 시계 오차는 조용히 벌어진다. 원서 예: 인터넷 NTP 동기화는 수십 ms 오차가 보통이고 네트워크가 막히면 100ms~1초 튀며, 방화벽으로 NTP가 막히면 오차가 크게 쌓인다.
- **여러 서버의 타임스탬프로 "누가 먼저 썼는가"를 정하면 위험**하다. 인과적으로 나중인 쓰기가 더 이른 타임스탬프를 받아 **LWW에서 조용히 버려질** 수 있다.
- 시간 순서가 중요하면 DB가 부여하는 순번(시퀀스, LSN), 논리 시계, 버전 번호를 쓴다.

```ts
// (보충: JS API 예시) 경과 시간은 단조 시계로
const t0 = performance.now();
await work();
const elapsedMs = performance.now() - t0;   // Date.now() 차이는 시계 조정에 취약
```

> 📖 원문: 9장 "Unreliable Clocks" (Monotonic Versus Time-of-Day Clocks, Clock Synchronization and Accuracy, Relying on Synchronized Clocks)

#### 9.3 프로세스 멈춤, 분산 락, 펜싱 토큰

프로세스는 **언제든 오래 멈출 수 있다**(GC, VM 정지, 부하). 멈추기 전에 "락을 갖고 있다"고 확인했어도, 깨어났을 때는 이미 락이 만료되어 다른 노드가 가져갔을 수 있다. 이때 옛 락 소유자("좀비")가 계속 쓰면 데이터가 깨진다. 지연된 네트워크 패킷이 뒤늦게 도착해도 같은 일이 생긴다.

**펜싱 토큰(fencing token):** 락/리스를 줄 때마다 **증가하는 번호**를 함께 발급하고, 저장소는 "이미 더 큰 번호의 쓰기를 받았으면 작은 번호 요청을 거절"한다.

```
클라이언트1: 락 획득(token=33) → 멈춤 … 락 만료
클라이언트2: 락 획득(token=34) → 쓰기 요청(34) 성공
클라이언트1: 깨어남 → 쓰기 요청(33) → 저장소가 거절 ✔
```

- 같은 효과를 **조건부 쓰기(CAS, 버전 컬럼)** 로도 얻을 수 있다. 그래서 가능하면 락보다 **DB의 조건부 UPDATE/유니크 제약**에 의존한다.
- 원서: 리스(만료되는 락)는 프로세스가 멈추거나 요청이 지연되면 두 노드가 동시에 락을 갖고 있다고 믿는 상황이 생긴다. 결과가 낭비된 계산 정도라면 괜찮지만, 데이터 손상으로 이어지면 펜싱이 필요하다. 원서는 ZooKeeper의 zxid, etcd의 revision 등을 펜싱 토큰으로 쓸 수 있다고 한다.
- (보충) Redis 등 단순 TTL 락도 같은 이유로 정합성 목적(이중 결제 방지)에는 펜싱/조건부 쓰기가 필요하고, 중복 작업 줄이기 같은 효율 목적에는 충분하다.

> 🔗 NestJS 연결: 스케줄러(`@nestjs/schedule`)가 여러 인스턴스에서 동시에 돌 때 "한 번만 실행"을 위해 락을 쓴다면, 락이 깨져도 결과가 망가지지 않도록 작업 자체를 멱등하게 만든다.

> 📖 원문: 9장 "Process Pauses", "Knowledge, Truth, and Lies" (Distributed Locks and Leases, Fencing off zombies and delayed requests)

### 10. 일관성 모델 개요

#### 10.1 일관성 강도의 스펙트럼

| 모델 | 뜻 | 비용 |
|---|---|---|
| **최종적 일관성** | 쓰기를 멈추면 언젠가 복제본이 같아짐 | 가장 약함, 가장 빠름/가용 |
| read-your-writes, monotonic reads, consistent prefix | 복제 지연 이상 현상 일부를 막는 중간 보장 (6.2절) | 중간 |
| **선형화 가능성(Linearizability)** | 데이터 사본이 **하나뿐인 것처럼** 동작. 쓰기가 끝나면 그 이후 모든 읽기는 최신 값 | 강함, 지연↑, 네트워크 분리 시 가용성↓ |

**선형화 가능성이 꼭 필요한 곳**
- 리더/락 선출 (동시에 두 명이 성공하면 안 됨)
- **유일성 제약** (닉네임/이메일 중복 방지, 재고가 0 아래로 안 내려가기, 같은 좌석 두 명 예약 불가)
- 서로 다른 통신 경로 간 경쟁 조건 (파일 저장소에 쓰고 큐로 "처리하라" 신호를 보냈는데 저장소 복제가 늦어 옛 파일을 읽음)

반대로 대부분의 화면 조회(피드, 통계)는 몇 초 오래돼도 괜찮다. **어디에 강한 일관성이 필요한지 골라서** 그 부분만 리더/강한 DB로 처리하는 것이 실전 전략이다.

**CAP 정리, 한 줄 요약:** 네트워크가 갈라졌을 때 선형화 가능성을 지키려면 일부 노드는 응답을 포기(불가용)해야 한다. "3개 중 2개 선택"이라는 통속적 설명은 오해이고, 실무에서는 "일관성 vs 지연·가용성의 트레이드오프" 정도로 이해하면 충분하다. 많은 시스템이 선형화를 포기하는 진짜 이유는 분리 대응보다 **성능**이다.

**복제 방식별 선형화 가능성**: 단일 리더(리더에서만 읽으면 대체로 가능) / 합의 기반 시스템(etcd 등, 대체로 가능) / 다중 리더(불가) / 리더 없음+시각 LWW(사실상 불가).

> 📖 원문: 10장 "Linearizability" (What Makes a System Linearizable?, Relying on Linearizability, The Cost of Linearizability)

#### 10.2 분산 환경의 ID 생성

| 방식 | 장점 | 단점 |
|---|---|---|
| 자동 증가 정수 (단일 DB) | 작고 순서가 있음 | 단일 장애점, 병목, 다중 리전에 불리, 추측 가능(보안) |
| 샤드별 번호 대역/홀짝 | 분산 가능 | 시간 순서 보장 안 됨 |
| **UUID v4** | 어디서나 충돌 없이 생성 | 128비트, 무작위라 순서 없음 ((보충) 인덱스 삽입이 흩어져 성능이 떨어질 수 있음) |
| **시간 기반 ID (UUID v7, ULID, Snowflake)** | 대략 시간순 정렬, 분산 생성 | 시계 오차 때문에 **엄밀한 순서는 아님** |

- 원서: 인과 순서와 맞는 ID가 필요하면 램포트 타임스탬프(카운터+노드ID)나 하이브리드 논리 시계를 쓴다. 이들은 인과 순서와는 일치하지만 "최신 값인지"(선형화)를 보장하지는 않는다. 단일 노드 자동 증가는 순서가 정확하지만 단일 장애점·병목이다. (보충) 채팅 메시지 순서처럼 실무에선 DB 시퀀스로 충분한 경우가 많다.
- 대략적 정렬이면 충분하고 분산 생성이 필요하면 UUID v7/ULID가 실용적이다.
- (보충) 외부에 노출하는 ID는 순차 정수보다 UUID가 열거 공격(IDOR 탐색)에 덜 취약하다(단, 권한 검사는 별도로 필수).

> 📖 원문: 10장 "ID Generators and Logical Clocks"

### 11. 캐시와 파생 데이터의 정합성

캐시는 대표적인 **파생 데이터**다. 원본(DB)이 정답이고 캐시는 언제든 버리고 다시 만들 수 있어야 한다.

**캐시가 어긋나는 흔한 이유: 이중 쓰기(dual write)**
- 앱이 "DB에 쓰고, 그다음 캐시/검색 인덱스도 갱신"하면,
  1. **경쟁 조건:** 두 요청이 A, B를 거의 동시에 쓰면 DB엔 B, 캐시엔 A가 남을 수 있다 (오류 없이 영구히 어긋남).
  2. **부분 실패:** DB 쓰기는 성공, 캐시 갱신은 실패 → 불일치.
- 두 시스템을 원자적으로 묶으려면 분산 트랜잭션이 필요해 비싸다.

**안전한 접근**
- 원서 근거: 이중 쓰기는 경쟁 조건·부분 실패 문제가 있고, 해법은 DB를 리더로 두고 변경 로그를 순서대로 소비하는 **CDC/아웃박스** 방식이다 (12.3절). 파생 데이터(캐시 포함)는 원본에서 다시 만들 수 있어야 한다는 점도 원서 1장 내용이다.
- 아래 항목은 (보충) 원서에 없는 캐시 실무 관행이다.
  - **캐시를 갱신하지 말고 무효화(삭제)한다.** 다음 읽기가 DB에서 최신 값을 채운다 (cache-aside). 삭제는 멱등이라 재시도하기 쉽다.
  - 무효화 실패에 대비해 **TTL(만료 시간)** 을 항상 둔다.
  - 정확성이 중요한 값(잔액, 재고)은 캐시에서 읽어 판단하지 말고 원본에서 확인한다.
  - 캐시 미스가 동시에 몰리면(스탬피드) DB가 폭주한다 → 잠금/요청 병합, TTL 무작위화.

```ts
// (보충: 원서에 없는 예시) cache-aside + 쓰기 시 무효화
async function getUser(id: string) {
  const cached = await redis.get(`user:${id}`);
  if (cached) return JSON.parse(cached);
  const user = await repo.findOneByOrFail({ id });
  await redis.set(`user:${id}`, JSON.stringify(user), 'EX', 300); // TTL 필수
  return user;
}
async function updateUser(id: string, patch: Partial<User>) {
  await repo.update(id, patch);   // 원본 먼저
  await redis.del(`user:${id}`);  // 그다음 무효화 (실패해도 TTL이 구제)
}
```

> 🔗 NestJS 연결: `CacheModule`(cache-manager)의 `ttl` 설정과 `CacheInterceptor`를 쓸 때, 사용자별/테넌트별 데이터가 섞이지 않도록 캐시 키에 `tenantId`, `userId`를 반드시 포함한다.

### 12. 메시지 브로커와 이벤트 스트림 기초

#### 12.1 왜 브로커를 쓰나

이메일 발송, 리포트 생성, 웹훅 전달, 결제 후처리 같은 일을 요청 안에서 다 하면 느리고 취약하다. 브로커(큐)에 "할 일"을 넣고 **워커가 비동기로 처리**한다.
- 소비자가 다운/과부하여도 메시지가 쌓여 **완충**한다.
- 소비자가 죽으면 **재전달**한다.
- 보내는 쪽과 받는 쪽이 분리된다. 하나의 이벤트를 여러 소비자가 받을 수 있다.

**보낼 때 던져야 할 질문 두 가지**
1. 생산자가 소비자보다 빠르면? → 버린다 / 큐에 쌓는다 / 백프레셔로 생산자를 막는다.
2. 노드가 죽으면 메시지를 잃어도 되나? → 디스크 저장과 복제 필요 여부(비용 있음).

**소비 패턴**
- **로드 밸런싱:** 메시지 하나는 소비자 중 한 명에게 → 작업 병렬 처리
- **팬아웃:** 메시지 하나가 모든 구독자에게 → 여러 독립 시스템에 알림
- 둘을 조합: Kafka의 컨슈머 그룹 (그룹 내에서는 분담, 그룹 간에는 각각 수신)

**Ack와 재전달**
- 소비자는 처리를 마친 뒤 **ack**를 보낸다. ack가 없으면 브로커는 미처리로 보고 다시 보낸다.
- 처리는 끝났는데 ack만 유실되면 **같은 메시지가 두 번** 온다 → 기본적으로 **최소 1회(at-least-once)** 전달이므로 소비자는 **중복에 안전해야 한다(멱등).**
- 로드 밸런싱+재전달 조합에서는 **순서가 뒤바뀔 수 있다.**
- **독약 메시지(poison message):** 항상 소비자를 죽이는 메시지가 무한 재시도 되면 큐 전체가 막힌다 → 시도 횟수 제한 후 **DLQ(dead letter queue)** 로 옮기고 알림을 건다.

#### 12.2 로그 기반 브로커 (Kafka류)

- 메시지를 **삭제하지 않고 추가만 하는 로그**에 쌓는다. 소비자는 자신의 **오프셋(위치)** 만 기억하며 순서대로 읽는다.
- 처리한 메시지도 남아 있어 **다시 읽기(재처리), 새 소비자 추가**가 쉽다.
- 로그를 여러 **파티션**으로 나눠 확장한다. **순서는 파티션 안에서만 보장**된다. 순서가 필요한 메시지(같은 사용자의 이벤트 등)는 **같은 파티션 키**(예: userId, tenantId)로 보낸다.
- 한 파티션은 한 소비자만 읽으므로 병렬도는 파티션 수 이하이다. 한 메시지가 느리면 그 뒤가 밀린다(head-of-line blocking).

| | 전통 큐 (RabbitMQ 등) | 로그 기반 (Kafka 등) |
|---|---|---|
| 메시지 | 처리 후 삭제 | 보존, 재읽기 가능 |
| 순서 | 재전달 시 뒤섞일 수 있음 | 파티션 내 보장 |
| 적합 | 무거운 작업을 건별로 분산 | 높은 처리량, 순서·재처리 중요 |

> 🔗 NestJS 연결: 작업 큐는 BullMQ(`@nestjs/bullmq`, Redis 기반), 이벤트 스트림은 `@nestjs/microservices`의 Kafka/RabbitMQ 트랜스포터가 흔한 선택이다. 실패 재시도·DLQ 정책을 큐 옵션으로 명시한다.

> 📖 원문: 12장 "Transmitting Event Streams" (Messaging Systems, Log-Based Message Brokers)

#### 12.3 DB와 다른 시스템의 동기화: 이중 쓰기 문제, CDC, 아웃박스

**이중 쓰기 금지 (11장에서 본 문제):** "DB 커밋 후 메시지 발행"을 앱 코드에서 따로 하면, DB만 성공하고 메시지 발행이 실패(또는 그 반대)해 영구 불일치가 생긴다.

**해법 1 – 아웃박스 패턴** (원서 12장의 CDC 절 사이드바에서 소개: 내부 스키마와 공개 스키마를 분리하는 용도)
1. 비즈니스 데이터와 "보낼 이벤트"를 **같은 DB 트랜잭션**으로 `outbox` 테이블에 함께 기록한다. (원자적)
2. 별도 릴레이(폴링 또는 CDC)가 outbox를 읽어 브로커로 발행하고 발행됨으로 표시한다.
3. (보충) 릴레이가 중복 발행할 수 있으므로 소비자는 멱등하게 처리한다.

원서 설명: 겉보기엔 이중 쓰기지만 두 쓰기가 같은 DB 안에 있어 한 트랜잭션에 묶이므로 문제가 없다. 단점은 내부 스키마와 outbox 스키마 사이 변환을 유지해야 하고, DB 쓰기량이 늘어난다는 점이다.

```ts
// (보충: 원서에 없는 예시 코드)
await dataSource.transaction(async (m) => {
  const order = await m.save(Order, { tenantId, total });
  await m.save(Outbox, {
    aggregateId: order.id,
    type: 'order.created',
    payload: { orderId: order.id, total },   // 이벤트 = 공개 계약. 내부 스키마와 분리
  });
});
// 별도 워커: SELECT ... FROM outbox WHERE published = false ORDER BY id → 브로커 발행 → 표시
```

**해법 2 – CDC(Change Data Capture)**
- DB의 복제 로그(논리 로그)를 읽어 변경을 **커밋된 순서 그대로** 스트림으로 내보낸다 (예: Debezium). 검색 인덱스·캐시·웨어하우스는 이 스트림의 소비자가 된다.
- 앱 코드를 거의 바꾸지 않고 붙일 수 있다. 단, DB 테이블 스키마가 사실상 **공개 API**가 되므로 컬럼 삭제가 소비자를 깰 수 있다. 이 때문에 아웃박스 테이블로 내부/외부 스키마를 분리하는 방식을 함께 쓴다.
- CDC도 비동기이므로 복제 지연이 존재한다.

**이벤트 소싱과의 차이:** CDC는 일반 DB의 변경을 저수준에서 뽑아내고, 이벤트 소싱은 앱이 처음부터 불변 이벤트를 원본으로 삼는다.

> 📖 원문: 12장 "Databases and Streams" (Keeping Systems in Sync, Change Data Capture, CDC versus event sourcing)

#### 12.4 멱등성(Idempotence)과 정확히 한 번(Exactly-once)

- **멱등 연산:** 여러 번 실행해도 한 번 실행한 것과 결과가 같다.
  - 멱등: "상태를 PAID로 설정", "키 삭제", "PUT으로 전체 교체"
  - 비멱등: "잔액에 +100", "이메일 발송", "주문 생성"
- 네트워크·브로커는 재시도/재전달을 하므로 "정확히 한 번 전송"은 현실적으로 불가능하다. 대신 **"최소 한 번 전달 + 멱등한 처리 = 효과상 정확히 한 번(effectively-once)"** 을 목표로 한다.
- 분산 트랜잭션으로 메시지 ack와 DB 변경을 원자적으로 묶는 방법도 있지만 특정 환경(Kafka 내부, 스트림 프레임워크)에서만 효율적이다. 일반 앱에서는 **멱등 키**가 훨씬 현실적이다.

원서의 예: Kafka 메시지의 오프셋을 값과 함께 DB에 저장해 "이미 적용했는가"를 판단한다(재생 순서 동일, 결정적 처리, 동시 갱신 없음이 전제).

**멱등 키(Idempotency Key) 설계** ((보충) 아래는 실무 관행이며 원서는 일반 원리만 다룬다)
1. 클라이언트(또는 메시지 생산자)가 요청마다 **고유 키**를 만든다 (UUID).
2. 서버는 처리 전에 키를 **유니크 제약이 있는 테이블**에 기록한다. 이미 있으면 저장해 둔 결과를 그대로 반환한다.
3. 키 기록과 비즈니스 처리를 **같은 트랜잭션**에 넣는다.

```ts
// (보충: 원서에 없는 예시) 멱등 처리: (idempotency_key UNIQUE) 제약으로 중복 차단
async function charge(key: string, dto: ChargeDto) {
  return dataSource.transaction(async (m) => {
    const inserted = await m.createQueryBuilder()
      .insert().into(IdemRecord).values({ key, status: 'processing' })
      .orIgnore().execute();                        // ON CONFLICT DO NOTHING
    if (inserted.identifiers.length === 0) {
      return (await m.findOneByOrFail(IdemRecord, { key })).response;  // 이미 처리됨
    }
    const result = await paymentService.charge(dto); // 외부 결제 API에도 같은 key 전달!
    await m.update(IdemRecord, { key }, { status: 'done', response: result });
    return result;
  });
}
```

- **메시지 소비자:** 메시지 ID(또는 로그 오프셋)를 처리 기록과 함께 저장해 "이미 처리했는가"를 확인한다. 처리 결과와 기록이 **같은 트랜잭션**이어야 한다.
- 외부 API는 멱등 API여야 하고 고유 ID를 넘겨야 한다(원서 5장 Durable Execution). (보충) 예: Stripe의 `Idempotency-Key` 헤더.

**왜 SaaS에서 중요한가:** 결제·웹훅·이메일·큐 작업은 반드시 재시도되고 중복 도착한다. 멱등성 없는 설계는 "이중 청구", "알림 두 번 발송"으로 직결된다.

> 🔗 NestJS 연결: 멱등 키 헤더를 읽어 중복을 판별하는 Interceptor/Guard를 만들어 결제·주문 생성 엔드포인트에 적용하는 방식이 깔끔하다.

> 📖 원문: 12장 "Fault Tolerance" 중 Atomic commit revisited, Idempotence; 8장 "Distributed Transactions" 중 "Exactly-Once Message Processing Revisited"; 5장 "Durable Execution and Workflows". 아웃박스는 12장 "Change Data Capture" 절의 사이드바.

### ✅ 이 부 핵심 체크리스트

- [ ] 서비스 DB(OLTP)에서 무거운 분석 쿼리를 돌리지 않는다. 읽기 복제본이나 별도 분석 저장소로 분리한다.
- [ ] 데이터마다 "원본인지 파생(캐시·인덱스·집계)인지" 구분하고, 파생 데이터는 언제든 원본에서 재생성 가능하게 둔다.
- [ ] 성능은 평균이 아니라 **p50/p95/p99**로 본다. 모든 외부 호출에 타임아웃을 걸고, 재시도는 지수 백오프+지터로 한다.
- [ ] 인덱스는 쿼리 패턴에 맞춰 선택한다. 읽기 이득과 쓰기·용량 비용을 함께 따진다.
- [ ] 배포 중 옛/새 버전이 공존함을 전제로 API·이벤트·DB 스키마를 **하위·상위 호환**으로 바꾼다 (필드 추가는 OK, 삭제·이름/타입 변경은 단계적으로). 64비트 ID는 JSON에서 문자열로 준다.
- [ ] 읽기 복제본을 쓸 때 복제 지연을 전제로 한다. 방금 쓴 데이터는 리더에서 읽는 등 read-your-writes를 보장한다.
- [ ] 샤딩은 정말 필요할 때까지 미룬다. 멀티테넌트 쿼리에는 `tenant_id` 조건을 강제하고, 큰 테넌트/핫 키 문제를 염두에 둔다.
- [ ] 다중 행 변경은 짧은 트랜잭션으로 묶고, 카운터·잔액은 **원자적 UPDATE**로 갱신하며, 동시성 검사는 UNIQUE/EXCLUDE 제약·`FOR UPDATE`·낙관적 버전 컬럼·SERIALIZABLE(+재시도)로 막는다.
- [ ] 서로 다른 시스템(DB+큐+외부 API)을 분산 트랜잭션으로 묶지 않는다. 대신 **아웃박스 + 멱등 소비자 + 재시도**를 쓴다. DB와 캐시/큐에 "각각 따로 쓰기(이중 쓰기)"를 하지 않는다.
- [ ] 시계에 의존해 순서를 정하지 않는다(경과 시간은 단조 시계, 순서는 시퀀스/버전). 분산 락을 정합성에 쓸 때는 펜싱 토큰이나 조건부 쓰기를 함께 쓴다.
- [ ] 브로커 메시지는 최소 1회 전달이라 중복·순서 뒤바뀜이 생긴다고 가정한다. 멱등 키, 재시도 상한, DLQ 알림을 설계한다.
- [ ] 캐시는 TTL을 두고, 쓰기 시 갱신보다 무효화를 우선하며, 캐시 키에 테넌트/사용자 식별자를 포함한다.
