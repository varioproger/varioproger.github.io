# Node.js + NestJS SaaS 백엔드 필수 이론서 — 통합 목차 리스트

> 13권의 책과 doc 폴더 교재(NestJS·Node.js 런타임·웹 보안·Docker)에서 SaaS 백엔드 개발에 필수인 항목만 골라 쉽게 다시 정리했습니다. 본문은 Part별 파일로 나뉘어 있고, 이 문서가 전체 목차 겸 색인입니다.
> - `(보충)`/`보충(원서 외)` 표시는 원서에 없고 이해를 돕기 위해 추가한 내용입니다. 표시 없는 내용은 원서 본문과 대조했습니다(기록: `_work/verify_*.md`).
> - NestJS 프레임워크 자체는 Part 13에서 다룹니다(출처: doc/Nestjs 교재). 다른 Part에는 `🔗 NestJS 연결`로 접점을 표시합니다.
> - Part 2의 15～25절(Node.js 런타임)과 Part 7의 24～32절(웹 보안)은 doc 폴더 교재로 보강한 내용이며, 목차에 `[보충: ...]`으로 표시했습니다.
> - 코드 예시는 실행해 검증하지 않았습니다.

**읽는 순서**: TypeScript(Part 1) → Node.js(Part 2) → **NestJS(Part 13)** → 아키텍처·DDD(Part 3～4) → API 설계·보안(Part 5～7) → 멀티테넌트 SaaS(Part 8) → 데이터(Part 9～10) → 안정성(Part 11) → 테스트(Part 12)
> - Part 13은 번호는 마지막이지만 Part 2 다음에 읽습니다. Part 3~12의 `🔗 NestJS 연결`이 Guard·Pipe·Interceptor·Module·DI 같은 NestJS 용어를 전제로 하기 때문입니다.
> - Part 13 안의 `→ Part N 참조`는 "더 깊은 이론은 그 Part에서"라는 안내이므로, 처음 읽을 때는 건너뛰고 해당 Part를 읽을 때 다시 연결하면 됩니다. Part 2 15～25절의 `Part11` 참조도 같습니다.

## [Part 1. TypeScript 타입 시스템 (NestJS의 언어) (출처: Effective TypeScript)](본문/Part01_TypeScript.md)
- [Item 1] TypeScript와 JavaScript의 관계 — 모든 JS는 유효한 TS, 타입은 JS 런타임 동작을 모델링함을 이해해야 NestJS 코드가 읽힘
- [Item 2] 사용 중인 TypeScript 옵션 알기 (strict, noImplicitAny, strictNullChecks) — tsconfig가 안전망의 두께를 결정
- [Item 3] 코드 생성은 타입과 독립적 — 타입은 런타임에 사라지므로 요청 검증(DTO)이 필요한 근본 이유
- [Item 4] 구조적 타이핑 — 클래스도 모양만 맞으면 통과. 테스트 더블·DI 설계와 직결
- [Item 5] any 사용 제한 — 타입 안전망을 통째로 끄는 주범
- [Item 7] 타입은 값의 집합 — 유니온/교차/never를 이해하는 기초 사고법
- [Item 9] 타입 단언보다 타입 선언 — as 남용은 런타임 사고의 원인
- [Item 11] 잉여 속성 검사 vs 타입 검사 — 객체 리터럴에서만 잉여 키를 잡는다는 함정
- [Item 13] type과 interface의 차이 — 매일 쓰는 선택지, 선택 기준 필요
- [Item 14] readonly로 변경 오류 방지 — 공유 객체/설정 값의 우발적 변형 방지
- [Item 15] 타입 연산과 제네릭으로 중복 제거 (Pick/Omit/Partial 등) — DTO·엔티티 변형 타입(NestJS mapped types)의 기반
- [Item 22] 타입 좁히기(Narrowing) — 유니온을 안전하게 다루는 핵심 도구
- [Item 27] 콜백 대신 async 함수 — Node.js 비동기 코드의 표준 형태
- [Item 29] 항상 유효한 상태만 표현하는 타입 — 상태 버그를 설계로 제거
- [Item 32] 타입 별칭에 null/undefined 포함 금지 — null 경계 설계
- [Item 33] null을 타입 경계(perimeter)로 밀어내기 — strictNullChecks 하에서 코드 단순화
- [Item 34] 유니온을 가진 인터페이스보다 인터페이스의 유니온 — 판별 유니온(Discriminated Union)
- [Item 35] string보다 정밀한 타입 — 상태/역할/플랜 등 리터럴 유니온
- [Item 36] 특수 값에는 별도 타입 사용 — 'none', -1 같은 센티널 값 오용 방지
- [Item 37] 선택적 프로퍼티 사용 제한 — `?` 남발이 만드는 불명확한 상태
- [Item 45] 안전하지 않은 단언은 잘 타입된 함수 안에 숨기기 — 검증 경계를 한 곳에 모으기
- [Item 46] any 대신 unknown — 외부 입력(요청 바디, JSON.parse) 처리의 기본 타입
- [Item 48] 건전성(Soundness) 함정 피하기 — TS 타입이 런타임과 어긋나는 대표 지점
- [Item 59] never로 완전성 검사 — 새 케이스 추가 시 누락을 컴파일 오류로 전환
- [Item 61] Record 타입으로 값 동기화 유지 — 권한/플랜 매핑 테이블 누락 방지
- [Item 64] 브랜드로 명목적 타이핑 — UserId/TenantId 혼동 방지(멀티테넌시)
- [Item 72] ECMAScript 기능 우선 (enum, 파라미터 프로퍼티, 데코레이터) — NestJS가 쓰는 experimentalDecorators/파라미터 프로퍼티를 이해하기 위함
- [Item 74] 런타임에 타입 복원하기 — DTO 검증(class-validator/Zod)과 직접 연결

## [Part 3. 소프트웨어 아키텍처 기초 (출처: Fundamentals of Software Architecture)](본문/Part03_소프트웨어아키텍처.md)
- [1장] Introduction (아키텍처 정의, 두 가지 법칙 요약) — "모든 것은 트레이드오프, 왜가 어떻게보다 중요"라는 사고의 출발점
- [2장] Architectural Thinking: 아키텍처 vs 설계, 전략/전술, 트레이드오프 분석 — 기술 선택마다 장단점을 따지는 습관의 기초
- [3장] Modularity: 모듈화 vs 입도, 응집도, 결합도(구심/원심), 불안정성·추상성, Connascence — 모듈 경계 설계의 핵심 언어
- [4장] Architectural Characteristics Defined: 아키텍처 특성(-ilities), 운영/구조/횡단 특성, "가장 덜 나쁜 아키텍처" — SaaS의 확장성·가용성·보안 요구를 구조로 옮기는 기준
- [5장] Identifying Architectural Characteristics (명시적/암시적 특성, 우선순위 제한) — 핵심 특성 3개 내외로 좁히는 방법
- [6장] Measuring and Governing (순환복잡도, 피트니스 함수) — 아키텍처를 코드/CI로 지키는 방법(의존성 규칙 테스트)
- [7장] Scope of Architectural Characteristics (아키텍처 퀀텀, 정적/동적 결합) — 모놀리스 vs 분산 판단 기준
- [8장] Component-Based Thinking (논리 컴포넌트, 워크플로/액터-액션 방식, Entity Trap, 데메테르 법칙) — 모듈러 모놀리스의 모듈을 나누는 실전 방법
- [9장] Foundations (스타일 vs 패턴, Big Ball of Mud, 기술/도메인 파티셔닝, 분산 컴퓨팅의 오류들, 콘웨이 법칙) — 스타일 선택의 기본 어휘와 분산의 대가
- [10장] Layered Architecture Style — NestJS 기본 컨트롤러-서비스-리포지토리 구조의 이론적 배경
- [11장] Modular Monolith Architecture Style — NestJS SaaS의 권장 출발점
- [13장] Microkernel Architecture Style — 테넌트별 커스터마이징/플러그인 구조
- [14장] Service-Based Architecture Style — 마이크로서비스 전 단계의 실용적 분산 스타일
- [15장] Event-Driven Architecture Style (이벤트 vs 메시지, 페이로드, 비동기 트레이드오프, 중재자) — 큐/이벤트 사용 판단과 함정
- [18장] Microservices Architecture (바운디드 컨텍스트, 데이터 격리, 사가) — 언제 쓰고 언제 피할지 판단
- [19장] Choosing the Appropriate Architecture Style — 스타일 선택 의사결정 기준
- [21장] Architectural Decisions (ADR, 결정 안티패턴, 아키텍처적 중요성) — 결정을 기록하고 근거를 남기는 실무 관행

## [Part 4. 도메인 주도 설계(DDD) 핵심 (출처: Learning Domain-Driven Design)](본문/Part04_DDD.md)
- [1] 서브도메인 분석 (Core/Supporting/Generic) — 어디에 공들이고 어디에 사서 쓸지 판단하는 출발점
- [2] 유비쿼터스 언어 — 코드·대화·문서의 용어를 통일해 오해 비용 제거 (모델 개념 포함)
- [3] 바운디드 컨텍스트 — 같은 단어가 다른 뜻일 때 모델 경계를 나누는 핵심 도구, NestJS 모듈 경계와 직결
- [4] 컨텍스트 통합/컨텍스트 맵 (Partnership, Shared Kernel, Conformist, ACL, OHS, Separate Ways) — 모듈·서비스 간 계약 설계, 외부 API 연동(ACL)에 필수
