### ① 경계에서 검증하고, 안쪽은 구조로 보장한다

> TypeScript 타입은 런타임에 사라지고, 공격자는 로그인한 정상 사용자처럼 보인다. 그러므로 **들어오는 경계에서 한 번 검증**하고(인증·DTO 검증·테넌트 추출), 그 안쪽은 "조심하기"가 아니라 **실수가 불가능한 구조**로 만든다.

| 이 원리에서 나오는 것 | Part |
|---|---|
| `as`는 변환이 아니다, DTO가 class인 이유, ValidationPipe·Zod가 필요한 이유 | 1·3 |
| 공개 API는 계약: 응답을 객체로 감싸기, enum, 버전 방식을 처음부터 | 4 |
| 인증은 "누구인가"만 채우고 거절은 인가가 한다 → 401 vs 403, Guard 분리 | 5 |
| BOLA/BFLA 검사, 입출력 DTO 분리, 페이지네이션 상한, 기본 거부 | 6 |
| 테넌트 컨텍스트는 검증된 토큰에서 맨 앞에서 한 번 추출 → 자동 전파, RLS | 13 |
| 요청 파이프라인 순서: Middleware → Guard → Interceptor → Pipe → Handler | 3 |

**스스로 확인:** "`/orders/:id`에서 남의 주문이 보이는 버그"를 막는 위치와 방법을 ①로 설명할 수 있나요?

### ② 네트워크 결과는 성공·실패·**모름** 세 가지다

> 요청은 실패하고, 응답이 안 오면 성공했는지 알 수 없다. 그래서 **타임아웃으로 기다림을 끊고, 재시도하며, 재시도가 안전하도록 멱등하게** 만든다. 기다림은 자원을 붙잡는다.

| 이 원리에서 나오는 것 | Part |
|---|---|
| 이벤트 루프를 막지 않기, await 사이 끼어들기(race) | 2 |
| 한 트랜잭션에 Aggregate 하나 → 결과적 일관성, Outbox, Saga | 12 |
| 메서드의 안전·멱등 의미, Idempotency-Key, ETag + If-Match, 202 비동기 작업 | 4 |

## Part별 코어

### Part 1. TypeScript 타입 시스템 (NestJS의 언어)

> TypeScript의 타입은 컴파일 후 사라지는 "값의 집합"에 대한 정적 약속이므로, strict로 검사 구멍을 막고 판별 유니온·리터럴 유니온·브랜드로 불가능한 상태를 표현할 수 없게 만들되, 외부 입력은 unknown으로 받아 경계에서 한 번 런타임 검증(NestJS: DTO 클래스 + ValidationPipe)해야 한다.

- 타입은 컴파일 후 사라진다 — as는 변환이 아니고 인터페이스는 instanceof·DI 토큰이 될 수 없다. 런타임에 남는 것은 in, 꼬리표 값, class뿐이며 "타입이 맞다"가 "런타임에도 맞다"를 보장하지 않는다
- 검사 스위치는 켜고, 끄는 장치는 좁게 — 처음부터 "strict": true. any·as·!·타입 가드(is)는 최소 범위로, 검증 함수 안에 숨기고, 모르는 값은 unknown
- 타입 = 값의 집합, 비교는 구조(모양)로 — 대입 가능 = 부분집합, 타입은 열려 있다. 잉여 속성 검사는 별도 장치, userId/tenantId 혼동은 브랜드 타입으로 막는다
- 유효한 상태만 표현한다 — 판별 유니온, 리터럴 유니온, 특수 값 대신 | null, null은 경계로, 누락은 never 완전성 검사와 Record&lt;Union, V&gt;로 컴파일 단계에서 잡는다
- 경계에서 한 번 검증하고 NestJS 런타임 장치를 안다 — unknown → 경계에서 한 번 검증(단일 진실 원천) → 안쪽은 신뢰. NestJS DI는 experimentalDecorators + emitDecoratorMetadata + 파라미터 프로퍼티 + 런타임에 존재하는 class에 의존한다

**C++·TCP 서버에서 출발하기**

- C++ RTTI(dynamic_cast, typeid) → 타입 소멸: TS의 interface/type은 JS 출력에 아무것도 남지 않아 instanceof 인터페이스가 불가하다
- C++ static_cast → TS as 단언: as는 변환 코드를 하나도 만들지 않는다(진짜 변환은 Number(val))
- C++ 템플릿 → TS 제네릭: 템플릿은 타입별 코드 인스턴스화, 제네릭은 검사 후 지워져 런타임에 T를 모른다
- C++ 명목적 타이핑/strong typedef → 구조적 타이핑 + 브랜드: 모양만 같으면 호환되므로 같은 string ID가 섞이고, 브랜드는 래퍼 없이 타입에만 존재하는 실수 방지 장치다

### Part 2. Node.js 핵심 원리와 디자인 패턴

> Node.js는 스레드 하나의 이벤트 루프가 I/O 대기 시간을 다른 요청 처리에 쓰는 리액터이므로 루프를 막지 말고 비동기를 규율 있게 다루며 바깥 세계와의 경계에서 실패·취소·컨텍스트를 관리해야 하고, NestJS는 그 위의 Node 디자인 패턴을 포장한 것이며, 확장·운영할 때는 상태를 공유 저장소로 빼고 중복 전달·시그널·메모리 한도에 대비해야 한다.

- 이벤트 루프를 막지 마라 — JS는 libuv 루프 한 스레드에서 단계별로 돈다. I/O 대기는 공짜, 동기 CPU 작업은 모든 요청을 멈춘다(p99 폭증) → setImmediate 쪼개기, 프로세스/Worker 풀, 큐로 분리하고 루프 지연을 메트릭으로 본다
- 비동기 규율 — Zalgo 금지, 순차/병렬/제한된 병렬 구분, forEach+async 금지, EventEmitter 리스너 정리, 대용량은 스트림 + pipeline()으로 백프레셔, 진행 중 Promise 공유(배칭)
- 경계에서의 실패·취소·컨텍스트 — 운영 에러는 처리, 프로그래머 에러는 기록 후 종료, floating promise 금지, 외부 호출엔 AbortSignal.timeout(), 요청 ID·테넌트 ID는 AsyncLocalStorage, 바이트는 인코딩·HMAC·timingSafeEqual로 정확히
- 디자인 패턴이 NestJS의 뿌리 — 모듈 캐시 싱글턴의 결합을 DI·IoC로 풀고(@Injectable, useFactory), Adapter·Proxy(Interceptor)·Strategy(PassportStrategy)·Middleware(NestMiddleware, Guard/Interceptor)·Observer(@OnEvent)
- 확장과 운영 — 상태를 공유 저장소로 빼 복제, at-least-once 소비자는 멱등, process.env는 문자열, node를 PID 1로 직접 실행 + SIGTERM 처리, 힙 상한 70~75%, lockfile + npm ci

**C++·TCP 서버에서 출발하기**

- epoll 리액터 루프 + 로직 스레드 1개 → Node 이벤트 루프: 로직 스레드를 늘릴 수 없고 콜백이 선점되지 않아 한 핸들러가 길면 전체가 멈춘다(Windows libuv는 IOCP지만 JS엔 같은 콜백 모양)
- I/O 워커 스레드 풀 → libuv 스레드 풀/Worker Threads: 풀은 파일·DNS·일부 crypto·zlib만 돌리고 내 JS는 안 돌린다. Worker는 별도 V8 힙이라 메시지(복사)로만 통신
- 세션별 송신 큐 상한 → 스트림 백프레셔: Node 신호(write() false, drain)는 권고일 뿐 강제하지 않아 무시하면 메모리만 늘어난다
- thread_local/OVERLAPPED 세션 컨텍스트 → AsyncLocalStorage: 스레드가 아니라 비동기 흐름에 붙는다. Node에서 thread_local은 전역 변수와 같다

### Part 3. NestJS 프레임워크 핵심

> NestJS는 DI 컨테이너(모듈·프로바이더·토큰·스코프)와 고정된 요청 파이프라인, 플랫폼 어댑터로 "어디에 무엇을 넣을지"를 고정해 주는 프레임워크이며, SaaS에서는 기본 잠금(전역 Guard)·입력 화이트리스트·출력 직렬화·다중 인스턴스 안전성으로 그 구조를 운영 수준까지 끌어올린다.

- 세 층과 요청의 전 생애 — DI 컨테이너 + 고정된 요청 파이프라인 + 플랫폼 어댑터(Express/Fastify). 부팅은 create()(그래프·DI) → listen() 안의 init()(라우트 → onModuleInit → onApplicationBootstrap) → 포트.
- DI 컨테이너: 모듈 경계·토큰·스코프 — 모듈은 자기 providers와 import한 모듈의 exports만 주입받고(중복 등록 = 인스턴스 두 개), 프로바이더는 기본 싱글턴·토큰(인터페이스 불가)으로 찾으며, 요청 데이터는 인자나 AsyncLocalStorage로(REQUEST 스코프는 버블링).
- 요청 파이프라인: 어디에 무엇을 넣나 — Middleware → Guard → Interceptor → Pipe → Handler → Interceptor → Filter. 인증·인가 Guard, 검증 Pipe, 응답 가공·직렬화 Interceptor, 에러 모양 Filter, 전역 등록은 APP_* 토큰.
- 보안 기본값: 기본 잠금 — 전역 AuthGuard + @Public(), ValidationPipe whitelist, 직렬화/응답 DTO, 전역 예외 필터로 500 내부 숨김, 소유권 검사는 서비스, 설정은 부팅 시 검증.
- 다중 인스턴스와 운영 — 크론 중복, 인메모리 rate limit·캐시 불일치, 큐 at-least-once → 멱등, enableShutdownHooks + readiness 먼저 내리기, liveness/readiness 분리, synchronize 운영 금지.

**C++·TCP 서버에서 출발하기**

- 패킷 처리 파이프라인(수신→세션 인증→디코딩/검증→디스패치→응답 직렬화) → Middleware→Guard→Pipe→Handler→Interceptor/Filter: 순서가 프레임워크에 고정되고 Middleware는 핸들러를 모르며, Guard 거부는 Interceptor가 못 본다.
- main()에서 매니저 싱글턴을 new하고 포인터를 꽂는 초기화 → DI 컨테이너: 생성 순서를 컨테이너가 런타임 메타데이터로 정하므로 TS 인터페이스는 토큰이 될 수 없다(추상 클래스 사용).
- thread_local 세션 정보 → AsyncLocalStorage: 스레드가 아니라 비동기 흐름에 붙고 큐 워커로는 넘어가지 않는다. 싱글턴 필드 오염은 스레드가 하나여도 await 인터리빙으로 생긴다.
- 서버 점검 종료 절차 → enableShutdownHooks + 종료 훅 3단계: 기본값이 꺼져 있고, K8s는 SIGTERM과 LB 제거를 동시에 하므로 readiness를 먼저 내려야 한다.

### Part 4. 웹 API 설계 (REST)

> 공개한 API는 바꾸기 어려운 계약이므로, "리소스(명사) + 표준 메서드(동사)"의 균일한 규칙과 올바른 데이터 위치·상태코드·목적별 DTO로 처음부터 설계하고, 재시도·동시 수정·권한·긴 작업·이벤트 통지를 설계 단계에서 방어하며, 하위 호환 규칙과 OpenAPI 가이드라인으로 진화시킨다.

- 균일한 인터페이스 — URL은 명사 컬렉션 + 식별자, 메서드 의미(GET 안전, PUT/DELETE 멱등, POST/PATCH 비멱등)를 지키고, 식별자는 path·수정자는 query·내용은 body, 생성은 201 + Location.
- 계약으로서의 데이터 — 요청/응답 DTO를 목적별로 분리(서버 관리 값은 요청에서 받지 않음), 응답은 항상 객체로, 에러는 Problem Details(RFC 9457), 목록은 필터·정렬·페이징(상한)을 처음부터.
- 실패와 권한을 전제한 설계 — 재시도에는 Idempotency-Key, 갱신 유실에는 ETag + If-Match(412), 권한은 토큰의 사용자·테넌트와 입력을 항상 대조(존재 은닉은 404).
- 효율·긴 작업·통지 — 캐시·데이터량·대량 연산으로 호출 비용을 줄이고, 긴 작업은 202 Accepted + 작업 리소스(폴링/콜백), 외부 통지는 서명·재시도·멱등 수신을 갖춘 웹훅.
- 진화 — 하위 호환 판정은 응답과 요청이 반대다. 버전 방식(/v1)을 처음부터 정하고, OpenAPI diff를 CI에 넣고, 폐기는 deprecated + Sunset으로 알린다.

**C++·TCP 서버에서 출발하기**

- opcode + 패킷 구조체 → HTTP 메서드 + 리소스 URL: 메서드의 안전·멱등 의미가 표준이라 프록시·캐시·크롤러 같은 제3자도 그 의미대로 행동한다.
- 세션 상태(소켓에 붙은 유저 컨텍스트) → 무상태 + 매 요청 토큰: 연결에 상태가 없어 어느 인스턴스든 처리하고, 권한 검사도 매 요청 한다.
- 패킷 시퀀스 번호/중복 패킷 무시 → Idempotency-Key: TCP 중복 제거는 한 연결 안뿐이라, 새 연결로 온 재시도는 공유 저장소의 키로 원자적으로 판정한다.
- 프로토콜 버전 체크·강제 업데이트 → API 버전·하위 호환: 외부 소비자는 강제 업데이트할 수 없어 깨지지 않는 변경 규칙과 Sunset 예고가 필요하다.

### Part 5. API 보안 기본 (인증·인가·공격 방어)

> API 보안은 HTTPS 위에서 "속도 제한 → 인증(누구인지만 채움) → 감사 로그 → 인가(기본 거부)" 순서의 관문을 다층으로 세우고, 입력은 allowlist로 받고 출력은 올바른 Content-Type으로 내보내며, "브라우저가 자격 증명을 자동으로 붙인다"는 사실을 기준으로 쿠키·토큰을 고르고, 비밀번호·토큰·키는 해시·짧은 수명·폐기 가능한 형태로 다루는 것이다.

- 관문의 순서와 다층 방어 — HTTPS → 속도 제한(인증도 CPU를 쓰므로 가장 먼저) → 인증(거절 없이 신원만) → 감사 로그 → 인가(여기서 거절). 게이트웨이가 있어도 앱에 한 겹 더 둔다.
- 입력은 allowlist, 출력은 Content-Type — "무엇이 유효한가"를 정의해 검증하고 SQL은 파라미터 바인딩, 모든 응답(에러 포함)에 올바른 Content-Type과 보안 헤더.
- 브라우저가 자격 증명을 자동으로 붙이는가 — 세션 쿠키는 CSRF 방어(SameSite·CSRF 토큰)가 필요하고, Bearer 헤더는 CSRF에 강하지만 저장 위치에 따라 XSS로 탈취된다. CORS는 브라우저 규칙일 뿐 인증·인가를 대체하지 않는다.
- 비밀과 토큰은 해시·짧은 수명·폐기 가능하게 — 비밀번호는 느린 해시+솔트, 고엔트로피 토큰·키는 SHA-256 해시, 시크릿은 코드 밖. JWT는 alg 서버 고정·iss/aud/exp 검증·폐기 수단 필요. OAuth2는 위임 인가(Code + PKCE), 로그인은 OIDC.
- 인가는 기본 거부, 그리고 기록 — 최종 판단은 권한 ∩ scope, 모든 조회에 테넌트 경계, RBAC로 시작해 ABAC 추가, 거부·권한 변경은 감사 로그로.

**C++·TCP 서버에서 출발하기**

- 접속 시 로그인 후 세션을 소켓에 귀속 → 세션 쿠키/Bearer 토큰 인증: 연결이 없어 요청마다 다시 증명하고, 값을 훔치면 어디서든 그 유저가 되며, 로그아웃은 소켓 닫기가 아니라 서버 측 레코드 폐기다.
- 로그인 서버가 발급한 인증 키를 게임 서버가 확인 → JWT/OAuth2 액세스 토큰(AS 발급, RS 검증): JWT는 발급처에 묻지 않고 서명만 보므로 빠르지만 즉시 폐기가 어렵고, 토큰 안의 alg는 믿으면 안 된다.
- 패킷 검증·서버 권한 검사(이 아이템이 이 캐릭터 것인가) → allowlist 입력 검증·객체 수준 인가(BOLA 방지): JSON은 필드를 마음대로 추가할 수 있고(Mass Assignment), 판단 재료가 역할·scope·테넌트로 여러 겹이다.
- 게임 클라이언트(전용 실행 파일) → 브라우저(CSRF·XSS·CORS): 유추 불가, 완전히 새 개념. 브라우저는 여러 사이트 코드를 실행하고 쿠키를 자동으로 붙인다.

### Part 6. 안전한 API 설계·구현 (보안 심화 실무)

> 공격자는 로그인한 정상 사용자처럼 보이므로, 설계·구조로 취약점을 불가능하게 만들고(위협 모델링·스펙 제약·기본 거부), 어디서 온 데이터든 믿지 않고 검증하며, 매 요청·매 리소스마다 소유자·테넌트·역할을 확인하고, 정상 요청의 남용(플로우 건너뛰기·동시 요청·자원 폭탄)을 원자적 처리와 속도 제한으로 막고, 그 모든 것을 보이게 운영(인벤토리·관측·자동 테스트·공급망)한다.

- 설계·구조로 불가능하게 — 위협 모델링(분해 → 식별·순위 → 대응 → 검증, STRIDE)과 스펙 제약(enum·상한·UUID·추가 속성 금지), 기본 거부(fail-safe)·검증 순서(출처→크기→어휘→구문→의미)·도메인 프리미티브로 실수를 구조적으로 막는다.
- 아무것도 믿지 않는다 — 인증 ≠ 인가, "내부 API"는 없다, 요청·응답·서드파티·내부 서비스·DB 5흐름 검증, 사용자 입력이 URL(SSRF)·객체 키(프로토타입 오염)·명령·경로·리다이렉트·헤더로 해석되지 않게 한다.
- 매 요청·매 리소스마다 인가 — BOLA(소유자·테넌트 조건), BFLA(역할 기본 거부, 숨김은 보안 아님), BOPLA(입력/출력 DTO 분리), 깨진 인증(IdP·재인증·열거 방지), JWT 전 항목 검증, 계정 복구·MFA·WebSocket도 같은 기준.
- 정상 요청이 무기가 된다 — 비즈니스 플로우 남용은 단계·간격 추적과 플로우 트래커로, check-then-act는 조건부 원자적 갱신·유니크 제약으로, 자원 소비는 엔드포인트별 속도 제한(IP+계정+세션)으로.
- 보이게, 안전하게 운영한다 — OpenAPI·카탈로그·버전 폐기 자동화, 게이트웨이·네트워크 분리·WAF(한계), 스택 없는 에러·로그 마스킹, CI의 접근 제어 테스트 4종, npm ci --ignore-scripts와 최소 권한 실행.

**C++·TCP 서버에서 출발하기**

- 서버 권위(클라이언트 수치 재계산) → 제로 트러스트·대량 할당 방지: 전용 클라이언트·안티치트가 없고 누구나 curl로 JSON을 보내며, 응답·서드파티·DB 데이터도 검증 대상이다.
- 변조 패킷의 남의 인벤토리 슬롯 ID → BOLA: 연결에 묶인 플레이어 객체가 없으니 매 요청 토큰에서 주체를 꺼내 매 쿼리에 userId·tenantId 조건을 건다.
- 아이템 복사(동시 패킷 race) + 플레이어 lock → check-then-act 경쟁 상태: Node는 await 사이에 끼어들고 인스턴스가 여러 대라 메모리 mutex가 아니라 DB 원자적 갱신으로 막는다.
- 매크로 입력 간격 탐지 → 비즈니스 플로우 남용 탐지: API는 UI 순서를 강제하지 않으므로 서버가 플로우 트래커로 단계·간격을 직접 기록해야 한다.

### Part 7. SQL 인덱스와 쿼리 성능

> 인덱스는 테이블과 별개인 "정렬된 복사본 + B-Tree"이고, 쿼리 속도는 트리 깊이가 아니라 "리프를 얼마나 넓게 훑고 테이블을 몇 번 다녀오느냐"로 정해지므로, 쿼리 패턴(등호 → 범위 → 정렬)에 맞춘 최소한의 인덱스를 설계하고, 인덱스를 무력화하는 쿼리를 피하며, EXPLAIN으로 접근/필터 조건과 쓰기 비용까지 확인한다.

- 인덱스 = 정렬된 복사본 + 트리 — 조회는 트리 탐색(항상 빠름) → 리프 체인 → 테이블 접근이며, "인덱스를 탔는데 느림"은 넓은 범위 스캔과 테이블 접근 반복 때문이고 하드웨어 증설로는 응답 시간이 줄지 않는다.
- 복합 인덱스는 왼쪽부터, 등호 먼저·범위 나중 — tenant_id 선두, 등호 → 범위 → ORDER BY 순으로 설계하고, 접근 조건은 범위를 좁히고 필터 조건은 읽고 버린다. 인덱스는 적을수록 좋다(부분 인덱스, 기존 인덱스 확장).
- 인덱스를 못 쓰게 만드는 쿼리를 피한다 — 컬럼에 함수·연산 금지(날짜는 반열린 구간), LIKE는 접두사만, 값은 항상 바인드 파라미터, 선택 조건은 동적으로 조립한다.
- 인덱스로 일을 덜어 낸다 — 커버링(테이블 접근 생략), 파이프라인 ORDER BY(정렬 생략), Top-N + Keyset 페이징(버리는 행 없음), 조인 컬럼 인덱스 + N+1 제거(왕복 감소).
- EXPLAIN으로 진단하고 쓰기 비용을 따진다 — 진단은 EXPLAIN (ANALYZE)부터 운영 규모 데이터로, INSERT는 인덱스 개수만큼 곱셈 비용이므로 꼭 필요한 인덱스만, UPDATE는 바뀐 컬럼만, 대량 작업은 배치로.

**C++·TCP 서버에서 출발하기**

- std::map&lt;std::tuple&lt;A,B,C&gt;, V&gt;의 lower_bound → 복합 인덱스 (a, b, c): 접두사로만 찾는 점은 같지만, B-Tree는 디스크 페이지(수백 항목) 트리라 깊이 4~5이고 찾은 뒤 테이블에 가는 랜덤 I/O가 진짜 비용이다.
- 메인 컨테이너 + 보조 조회 맵 여러 개 → 테이블 + 인덱스 여러 개: 삽입 때 모두 갱신해야 하는 점은 같지만, 인덱스 갱신은 디스크 쓰기·페이지 분할·락을 동반해 INSERT 비용이 인덱스 개수만큼 곱해진다.
- 연결 리스트 std::advance(n) vs lower_bound(lastKey) → OFFSET vs Keyset 페이징: Keyset은 정렬 키가 유일해야 하며(마지막에 id), 데이터가 바뀌어도 결과가 안정적이다.
- 아이템마다 패킷 하나씩 보내기 → ORM N+1 쿼리: 왕복 횟수가 비용을 지배하는 점은 같지만, 지연 로딩은 그 왕복을 코드에서 보이지 않게 숨긴다(SQL 로그를 켜야 보인다).

### Part 8. 데이터 시스템 기초

> 데이터 시스템에는 정답 없이 트레이드오프만 있으며, 원본과 파생 데이터를 구분하고, 복제·버전 공존·동시성·네트워크가 만드는 "지연", "모름", "중복"을 전제로 DB 제약·짧은 트랜잭션·아웃박스·멱등성으로 정합성을 지킨다.

- 트레이드오프로 말하기 — 분산은 비용, 성능은 분포: 한 대로 되면 한 대로, OLTP와 분석을 분리하고, 성능은 p50/p95/p99로 보며 재시도는 지수 백오프 + 지터로 한다.
- 원본 vs 파생 — 미리 계산하면 읽기는 싸고 동기화는 비싸다: 캐시·인덱스·비정규화·집계·읽기 뷰는 원본에서 다시 만들 수 있는 파생이며, 이중 쓰기 대신 무효화+TTL·CDC·아웃박스로 동기화한다.
- 복사본과 버전은 어긋난다 — 스키마 진화·복제·샤딩: 배포 중 옛/새 버전이 공존하므로 하위·상위 호환, 복제본은 늦으므로 read-your-writes 등을 설계, 샤딩 기준은 바꾸기 어려우니 최후에.
- 동시성은 DB에 맡긴다 — 트랜잭션과 격리 수준: 기본 격리는 약하므로 갱신 손실·쓰기 왜곡·팬텀을 원자적 UPDATE, UNIQUE/EXCLUDE 제약, FOR UPDATE, 버전 컬럼, SERIALIZABLE + 재시도로 막는다.
- 네트워크는 "모름"을 돌려준다 — 최소 1회 + 멱등 = 효과상 정확히 한 번: 분산 트랜잭션 대신 타임아웃·단조 시계·펜싱·아웃박스·멱등 키로 중복과 불확실성을 흡수한다.

**C++·TCP 서버에서 출발하기**

- std::mutex로 감싼 gold -= cost → 원자적 UPDATE·FOR UPDATE·버전 컬럼: 여러 서버·커넥션이 같은 DB를 만지므로 앱 메모리 락은 무력하고 잠금의 주인은 DB다.
- send() 성공·소켓 타임아웃 → 성공/실패/모름: send() 성공은 커널 버퍼 적재일 뿐, TCP도 상대 앱 처리를 보장하지 않아 재시도는 중복 실행을 낳는다.
- 패킷 시퀀스 번호로 중복·역순 버리기 → 펜싱 토큰·멱등 키·오프셋: 번호 검사가 저장소(DB)에서, 재시작과 여러 서버를 넘어 유지돼야 한다.
- steady_clock / system_clock → 단조 시계 / 시각 시계: 대응은 거의 그대로지만, 여러 서버의 시각 타임스탬프로 순서를 정하면 LWW에서 나중 쓰기가 조용히 버려질 수 있다.

### Part 9. 운영 안정성 패턴

> 장애(결함)는 막을 수 없으므로, 모든 통합 지점의 기다림에 상한을 두고(타임아웃), 아픈 곳은 끊고(서킷 브레이커), 칸을 나누고(벌크헤드), 쌓이는 것은 비우고(정상 상태), 과부하는 거절하거나 늦춰서 결함이 실패로 번지는 사슬을 끊는다.

- 장애 사슬 끊기 — 결함 → 오류 → 실패는 결합도가 높은 곳을 따라 번지므로, 결함 제거가 아니라 번짐을 끊는 안전한 실패 모드를 설계한다.
- 기다림은 자원을 붙잡는다 — 통합 지점이 1순위 위험이고 느린 응답은 빠른 에러보다 나쁘다. 타임아웃 + 서킷 브레이커가 기본 짝, 재시도는 백오프·큐로 미루고, 들어오는 요청은 Fail Fast.
- 격리와 상한 — 벌크헤드, 페이지 상한(무제한 결과 집합 금지), 유한한 큐 + 배압 + 부하 차단, 자동화에는 거버너, 용량 균형과 soak 테스트.
- 쌓이면 비우고, 의심스러우면 재시작 — 쌓는 메커니즘마다 비우는 메커니즘(정상 상태), 상태를 믿을 수 없으면 Let It Crash(4조건).
- 운영을 위한 설계 — 큐로 결합 끊기와 테스트 하네스, 설정은 코드 밖 + 시작 시 검증, 로깅·메트릭·헬스체크, 배수·카나리 배포, 스키마는 확장 → 코드 배포 → 정리.

**C++·TCP 서버에서 출발하기**

- 블로킹 recv()에 거는 수신 타임아웃 → 모든 await에 거는 타임아웃: Node의 await는 스레드를 막지 않지만 그 요청이 쥔 커넥션·메모리는 계속 붙잡히고, 라이브러리 기본값이 무한일 수 있다
- 세션 송신 큐 상한(넘치면 끊기) → 유한한 큐 + 배압/부하 차단: HTTP 외부 경계에서는 연결을 끊지 않고 503(+Retry-After)이나 202로 응답하고, 배압은 내부 경계에서만 쓴다
- 크래시 후 워치독 재시작 → Let It Crash: 세션 상태를 메모리에 품은 게임 서버는 '좁은 범위'를 만족하지 못한다. 상태가 밖에 있는 빠른 무상태 인스턴스여야 성립한다
- 점검 공지 후 서버 내림·패치 → 무중단 롤링 배포: 점검 시간 없이 신·구 버전이 함께 돌므로 스키마도 확장 → 코드 배포 → 정리로 나눠야 한다

### Part 10. 테스트 전략과 원칙

> 테스트는 프로젝트를 오래 지속 가능하게 만드는 안전망이므로, 리팩터링 내성을 양보하지 않고 관찰 가능한 동작(WHAT)만 검증하며, 도메인 로직은 많은 단위 테스트로·오케스트레이션은 실제 DB와 비관리형 의존성 목을 쓰는 소수의 통합 테스트로 덮는다.

- 테스트의 가치 = 4기둥의 곱 — 회귀 방지 × 리팩터링 내성 × 빠른 피드백 × 유지보수성. 리팩터링 내성은 양보 불가라 실제 절충은 회귀 방지 vs 속도, 커버리지는 낮을 때만 의미 있다.
- 관찰 가능한 동작(WHAT)만 검증한다 — 오탐의 원인은 구현(HOW) 결합 하나. 단위는 클래스가 아니라 동작, 스텁은 검증하지 않고, 구현은 private으로 숨긴다.
- 출력 기반 &gt; 상태 기반 &gt; 통신 기반, 시간은 값으로 — 로직을 순수 함수로 뽑을수록 테스트가 쉬워지고, 현재 시각도 값으로 넘긴다.
- Humble Object — 복잡한 로직은 협력 객체가 적은 도메인으로 빼 단위 테스트하고, 서비스는 읽기 → 판단 → 쓰기만 하는 얇은 조율자로 남긴다.
- 관리형 vs 비관리형 의존성 — 내 앱 전용 DB는 운영과 같은 실제 DB로, SMTP·큐·결제만 가장 바깥 경계에서 목으로. 통합 테스트는 시나리오당 가장 긴 성공 경로 하나 + 단위로 못 잡는 엣지 케이스.

**C++·TCP 서버에서 출발하기**

- gMock EXPECT_CALL(가상 인터페이스 주입) → Jest 목/스텁: 인터페이스·목은 비관리형 의존성에만 두고, 조회(스텁) 호출은 검증하지 않는다
- 패킷 포맷 하위 호환 vs 서버 내부 클래스 호출 → 시스템 간 통신(목으로 검증) vs 시스템 내부 통신(검증 안 함): 내 앱 전용 DB는 프로세스 밖이어도 내부 구현 취급(실제 DB 사용)
- 틱에 시간 delta를 넘겨 결정적 리플레이 → 시간은 값으로 전달: 원리는 같지만 JS Date는 가변 객체라 도메인이 수정하지 않게 주의
- 봇 클라이언트로 서버 전체 검증 → E2E/통합 테스트: 회귀 방지는 강하지만 느려서 전부를 덮을 수 없고, 엣지 케이스는 단위 테스트에서 잡는다

### Part 11. 소프트웨어 아키텍처 기초

> 아키텍처는 정답이 아니라 트레이드오프이므로, 구조에 영향을 주는 특성 상위 3개를 골라 퀀텀·파티셔닝·스타일을 정하고(SaaS 기본값은 모듈러 모놀리스), 모듈 경계는 피트니스 함수로 지키며, 결정의 '왜'는 ADR로 남긴다.

- 모든 것은 트레이드오프 — 정답 대신 장단점을 함께 적어 "가장 덜 나쁜" 선택을 고르고(제1법칙), '어떻게'보다 '왜'를 남긴다(제2법칙).
- 특성과 퀀텀 — 구조에 영향을 주는 특성을 상위 3개 정도로 고르고, 특성은 퀀텀 단위로 적용되며 공유 DB·동기 호출은 서비스를 한 퀀텀으로 묶는다.
- 모듈 경계: 높은 응집·낮은 결합 — 경계를 넘는 결합은 약하게(Connascence), 순환 의존 금지, 엔티티 트랩 대신 업무 흐름/역할 기준, 공개 API만 노출한다.
- 스타일 선택: 모놀리스에서 분산까지 — 단순성·비용은 모놀리스, 확장성·탄력성·장애 내성은 분산(대가: 분산 컴퓨팅의 오류). SaaS는 모듈러 모놀리스 → 서비스 기반 → 마이크로서비스, 통신은 기본 동기.
- 통제와 기록 — 구조 규칙은 CI의 피트니스 함수로 자동 검사하고, 중요한 결정은 ADR로 한 곳에 남긴다.

**C++·TCP 서버에서 출발하기**

- 월드/로비/채팅 서버 분리 → 분산 아키텍처·마이크로서비스: 서버 간 동기 RPC와 공유 계정 DB로 묶이면 프로세스가 여러 개여도 한 퀀텀이며, 마이크로서비스는 서비스별 DB·share nothing이 전제다.
- UserManager/ItemManager 싱글톤 → 엔티티 트랩: 게임 서버의 흔한 관행이 여기서는 쓰레기통 클래스로 가는 안티패턴이다.
- 순환 include → 모듈 순환 의존: C++은 대개 컴파일 단계에서 드러나지만 Node/NestJS는 런타임에 드러나 CI 피트니스 함수로 막아야 한다.
- 서버 간 동기 RPC vs 메시지 큐 → 동적 퀀텀 얽힘 vs 이벤트 기반: 비동기는 응답성만 높이고 전체 처리 시간은 그대로이며 사후 오류 처리·최종적 일관성이 새로 생긴다.

### Part 12. 도메인 주도 설계(DDD) 핵심

> DDD는 서브도메인 유형(핵심/일반/지원)에 따라 공들일 곳을 정하고, 유비쿼터스 언어가 일관되게 통하는 바운디드 컨텍스트로 모델을 나눈 뒤, 그 안의 로직은 복잡도에 맞는 패턴(Transaction Script → Active Record → Domain Model → Event Sourcing)으로 구현하되 핵심 규칙은 Aggregate라는 일관성·트랜잭션 경계에 가두고, 경계 사이는 ACL·Outbox·Saga로 유실과 중복을 전제해 잇는 "중요한 곳은 정교하게, 단순한 곳은 단순하게"의 방법이다.

- 서브도메인과 유비쿼터스 언어 — 서브도메인은 발견한다(핵심=직접·고급 설계, 일반=사서 씀, 지원=단순 CRUD). 기획자와 코드가 같은 말을 쓰고, 한 용어는 한 뜻만 갖는다.
- 바운디드 컨텍스트와 컨텍스트 통합 — 언어가 일관되게 통하는 범위로 설계하고 한 팀이 소유하며, 팀 관계에 따라 파트너십/공유 커널/순응자/ACL/OHS/결별을 고르고, 마이크로서비스는 서브도메인 경계로 자른다.
- 복잡도에 맞는 패턴 사다리 — 돈·감사 → Event-sourced, 복잡한 규칙 → Domain Model, 복잡한 데이터 → Active Record, 그 외 → Transaction Script. 아키텍처(Layered / Ports & Adapters / CQRS)와 테스트 전략이 이 선택을 따라간다.
- Aggregate = 일관성·트랜잭션 경계 — 공개 메서드로만 상태 변경, 트랜잭션당 하나만 수정, 작게 유지하고 다른 Aggregate는 ID로 참조, 버전으로 낙관적 락, 과거형 Domain Event 발행. 이벤트 소싱은 그 상태를 이벤트 목록으로 저장하는 선택지다.
- 경계 너머는 유실·중복을 전제한다 — Outbox로 상태와 이벤트를 같은 트랜잭션에 저장(at-least-once → 멱등 소비자), 여러 Aggregate에 걸친 흐름은 Saga/Process Manager와 보상 행위로, 내부 이벤트는 공개 이벤트로 번역한다.

**C++·TCP 서버에서 출발하기**

- 유저 단위로 묶어 한 번에 처리하는 트랜잭션 경계(인벤토리·재화) → Aggregate: 메모리·스레드 소유 대신 매 요청 DB 로드 + version 조건부 저장(낙관적 락)으로 지키며, 두 유저를 한 트랜잭션에서 고치는 거래는 규칙 위반이라 경계 재검토나 Saga 대상이다.
- DB 커밋과 지급 대기 기록을 같은 트랜잭션에 남기고 워커가 지급 → Outbox: 보장은 at-least-once라 받는 쪽이 event-id로 중복을 걸러야 한다(멱등 소비자).
- 로그인 서버의 계정 vs 게임 서버의 캐릭터 → 바운디드 컨텍스트: 프로세스 분리가 아니라 언어·모델 경계이며, 한 프로세스 안의 NestJS 모듈(모듈러 모놀리스)로도 충분하다.
- std::atomic compare_exchange → 낙관적 동시성 제어(WHERE version = ?): 실패 신호는 0행 갱신이고, 재시도 시 다시 로드해 규칙을 재검증해야 한다.

### Part 13. 멀티테넌트 SaaS 아키텍처

> 멀티테넌시는 인프라 공유가 아니라 모든 테넌트를 같은 버전으로 통합 운영하는 것이며, 사일로/풀은 자원 단위로 고르되(기본은 풀), 검증된 토큰의 테넌트 컨텍스트를 맨 앞에서 한 번 뽑아 모든 곳에 자동으로 흘려보내고, 공유가 낳는 두 위험(유출·간섭)은 인증과 별개의 격리 계층과 티어별 상한으로 막으며, 테넌트의 일생(온보딩·관리·티어·과금·운영)은 컨트롤 플레인이 자동화한다.

- 멀티테넌시 = 통합 운영 (두 플레인) — 판별 기준은 "모든 테넌트가 같은 버전인가"이며, 컨트롤 플레인(온보딩·아이덴티티·메트릭·과금·테넌트 관리)을 먼저 세우고 앱 플레인 5지점(컨텍스트·격리·데이터 파티셔닝·라우팅·배포)에 테넌시가 스며든다.
- 사일로/풀은 자원 단위 선택 — 컴퓨트·DB·큐마다 전용/공유를 고르고 기본은 풀·사일로는 이유가 있을 때만이며, 데이터 파티셔닝과 Kubernetes/서버리스 배포 패턴도 이 선택의 구현이다.
- 테넌트 컨텍스트는 토큰에 실려 자동 전파 — SaaS Identity = 사용자 + 테넌트로, tenantId·tier·role만 JWT 커스텀 claim에 싣고 중앙 조회 없이 맨 앞에서 한 번 추출해 AsyncLocalStorage 등으로 로깅·메트릭·데이터 접근·라우팅에 흘린다.
- 공유의 두 위험: 유출은 격리로, 간섭은 상한으로 — 인증 ≠ 격리 ≠ RBAC, 격리 3수준·배포 시점/런타임 격리·기반 Repository + RLS·교차 테넌트 테스트, 노이지 네이버는 티어별 스로틀링·쿼터·동시성 상한과 작업 분리.
- 컨트롤 플레인이 테넌트의 일생을 자동화 — 온보딩(inactive 생성 → 프로비저닝 → 과금 → 관리자 → 활성화, 상태 추적·멱등·비동기), 테넌트 관리(UUID·불변, 비활성화·폐기·티어 변경), 티어링·과금/미터링, 테넌트 인지 운영(메트릭 6분류·표적 릴리스).

**C++·TCP 서버에서 출발하기**

- 게임 월드/서버군(샤드) → 테넌트: 부하 분산 단위가 아니라 계약한 고객사(조직) 단위이며 데이터 교차는 곧 사고다.
- 서버군별 전용 DB vs 통합 DB(월드 ID 컬럼) → 사일로 vs 풀: 자원 하나하나 단위로 섞고 기본은 풀, 사일로는 개별 고객 맞춤이 아니라 티어 상품으로만 준다.
- 세션 객체에 저장한 worldId → 테넌트 컨텍스트(JWT claim): HTTP는 무상태라 매 요청 토큰으로 실려 오고, 한 Node 스레드가 여러 테넌트 요청을 섞어 처리하므로 AsyncLocalStorage로 전파한다.
- 패킷 핸들러의 소유권 검증 → 테넌트 격리: 핸들러별 수동 체크가 아니라 기반 Repository·RLS처럼 잊어도 걸리는 구조로 강제한다.
