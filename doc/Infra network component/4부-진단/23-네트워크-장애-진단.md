# 23장. 네트워크 장애 진단 — 계층별 플로차트

> **🎮 게임 서버 개발자에게** — 클라이언트가 "접속이 안 돼요"라고 하면 우리는 서버 프로세스가 `listen` 중인지, 방화벽이 막는지, 라우팅이 맞는지를 위에서 아래로 하나씩 지워 가며 찾았다. 쿠버네티스 장애 진단도 같은 일이다. 결정적으로 다른 점은 **길 한가운데에 눈에 보이지 않는 가상 부품이 여러 개 더 끼어 있다**는 것이다. 네임스페이스 안의 가상 인터페이스, DNAT로 주소를 바꾸는 규칙, 이름을 IP로 바꾸는 CoreDNS, 트래픽을 조용히 버리는 NetworkPolicy가 그렇다. 게다가 도구도 속인다. ClusterIP는 ping에 응답하지 않는 것이 정상이고, 운영 이미지에는 `tcpdump`조차 없다. 그래서 "어디서부터, 어떤 순서로 지울 것인가"를 미리 정해 두어야 한다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - "Pod A가 Service C에 닿지 않는다"는 신고를 받았는데, DNS·CNI·Service·정책 중 어디부터 봐야 할지 막막할 때
> - ping과 작은 요청은 되는데 큰 응답이나 TLS 핸드셰이크에서만 멈추는 증상, 또는 부하가 몰릴 때만 간헐적으로 실패하는 증상을 만났을 때
> - NetworkPolicy를 적용한 직후 갑자기 모든 통신이 끊겼을 때

## 코어 — 이것만은 100%

> **한 문장:** 네트워크 장애는 DNS → 노드 간 연결 → Service → NetworkPolicy → 노드 자원 순으로, 더 흔하고 상위인 계층부터 하나씩 확실히 배제하며 내려가고, 증상(큰 전송만 실패, 정확히 5초 지연, 특정 정책 직후 전부 실패 등)이 어느 계층을 의심할지 알려 준다.

1. **계층별 배제 순서** — "Pod A가 B에 안 닿는다"는 여러 질문의 뭉치다. 이름(DNS) → Pod 간 경로(CNI) → Service(EndpointSlice·kube-proxy) → NetworkPolicy → 노드 자원 고갈 순으로, 상위 계층을 먼저 배제한다. Pod IP·ClusterIP·DNS 이름으로 차례로 호출해 보면 경계가 갈린다.
2. **증상은 계층을 가리킨다** — 큰 전송만 실패하면 MTU, 정확히 5초 지연이면 conntrack 경쟁(DNS), 정책 적용 직후 전부 실패하면 DNS 예외 누락, 부하 때만 간헐 실패하면 conntrack·임시 포트 고갈을 먼저 의심한다.
3. **관찰 위치를 고른다** — 같은 문제도 Pod 네임스페이스 안, 호스트의 veth, 양쪽 노드, 흐름 단위(Hubble)에서 보이는 것이 다르다. 양쪽 노드에서 동시에 캡처하면 패킷이 사라지는 지점이 드러난다.

**이 장의 학습 목표**

- 5단계 진단 플로차트를 순서와 이유까지 설명하고, 실제 장애에 적용할 수 있다.
- Pod IP → ClusterIP → DNS 이름 세 점 호출로 CNI·kube-proxy·DNS 영역을 구분할 수 있다.
- 증상표를 보고 의심 계층을 고르고, MTU·conntrack·임시 포트·IP 고갈의 확인 명령을 안다.
- `kubectl debug`, `nsenter`, 호스트 veth 캡처, Hubble 중 상황에 맞는 관찰 위치를 고를 수 있다.

## 코어 1. 계층별 플로차트 — 위에서 아래로 배제한다

### 1.1 5단계 플로차트

**한 줄 요약:** "Pod A가 B나 Service C에 닿지 않는다"는 질문을 이름 → 노드 간 연결 → Service → 정책 → 노드 자원의 순서로 좁힌다.

이 질문은 사실 서로 다른 여러 질문이 뭉쳐 있다. 아래 순서로 좁혀 가면 대부분의 원인에 도달한다(원천: Kubernetes_Internals_Network_Guide 19.3).

```
Pod A → 목적지에 연결 안 됨
  │
  ▼
① 목적지가 이름(FQDN)인가, IP인가?
  │
  ├─ 이름이다 → DNS 문제 가능성 (18장)
  │             kubectl exec A -- nslookup <목적지>
  │             해석 실패 → CoreDNS Pod 상태, ndots 설정, NetworkPolicy의 DNS 허용 확인
  │             해석 성공 → 아래로 계속
  │
  ▼
② IP는 얻었다. 같은 노드인가, 다른 노드인가?
  │
  ├─ 같은 노드 → CNI의 로컬 브리지/veth 연결 확인 (13장)
  │             다른 노드 → CNI의 오버레이/네이티브 라우팅 확인 (13장)
  │             예: VXLAN 캡슐화가 방화벽에 막히는가, BGP 라우팅이 전파됐는가
  │
  ▼
③ 목적지가 Pod IP인가, Service(ClusterIP 등)인가?
  │
  ├─ Service다 → EndpointSlice에 준비된(ready) 백엔드가 있는가? (16장)
  │             kube-proxy 모드라면 iptables/IPVS 규칙이 반영됐는가 (17장)
  │             eBPF 모드라면 cilium service map에 반영됐는가 (22장)
  │             cilium service list / iptables-save | grep <서비스>
  │
  ▼
④ 연결 자체는 되는데 특정 포트/프로토콜에서만 실패하는가?
  │
  ├─ NetworkPolicy가 해당 방향을 거부하고 있지 않은가 (21장)
  │  · CNI가 NetworkPolicy를 시행하는 CNI인지부터 재확인
  │  · podSelector/namespaceSelector 조합이 의도와 다르게 AND/OR 되어 있지 않은가
  │
  ▼
⑤ 정책도 통과하는데 간헐적으로/고부하 상황에서만 실패하는가?
  │
  └─ 노드 레벨 자원 고갈 가능성
     · conntrack 테이블 가득 참 (연결이 몰릴 때 새 연결이 거부됨)
     · 임시 포트(ephemeral port) 고갈 (아웃바운드 연결이 많은 워크로드)
     · nf_conntrack: table full, dropping packet 같은 커널 로그 확인
```

> **[보충]** 괄호 속 장 번호는 원천의 장 번호를 이 책의 장 번호로 바꿔 적은 것이다(CNI 13&#126;15장, Service 16장, kube-proxy 17장, DNS 18장, NetworkPolicy 21장, eBPF 22장).

### 1.2 왜 이 순서인가

**한 줄 요약:** 더 상위 계층에서 확실히 배제한 뒤에만 하위 원인을 의심한다. 반대로 하면 흔한 원인(DNS 설정 오류)을 지나치고 시간을 낭비한다.

플로차트의 순서는 임의적이지 않다. **DNS → 노드 간 연결성 → Service 레벨 → 정책 레벨 → 노드 자원 레벨** 순으로, **더 상위 계층에서 확실히 배제한 뒤에만 하위 원인을 의심하는** 구조다. 반대 순서로 접근하면(예: conntrack부터 의심) 훨씬 흔한 원인(DNS 설정 오류)을 지나치고 시간을 낭비하기 쉽다.

### 1.3 세 점 호출 — Pod IP, ClusterIP, 이름

**한 줄 요약:** 같은 대상을 Pod IP, ClusterIP, DNS 이름으로 차례로 호출하면 어디에서 끊겼는지 경계가 갈린다.

textbook의 진단은 반대 방향에서 시작한다. 같은 대상에 세 가지 방법으로 접근해 보는 것이다(원천: kubernetes-textbook-main 9.7, 23.6).

```bash
# ⑥ Pod에 직접 접근되는가 (Service를 건너뛰고)
kubectl run t --rm -it --image=nicolaka/netshoot --restart=Never -- curl -s <POD_IP>:8080

# ⑦ ClusterIP로 접근되는가
kubectl run t --rm -it --image=nicolaka/netshoot --restart=Never -- curl -s <CLUSTER_IP>:80

# ⑧ DNS 이름으로 접근되는가
kubectl run t --rm -it --image=nicolaka/netshoot --restart=Never -- curl -s web
```

⑥과 ⑦ 사이가 kube-proxy의 영역이고, ⑦과 ⑧ 사이가 DNS의 영역이다. **이 구분이 진단의 핵심이다.**

| 결과 | 의미 |
|---|---|
| ⑥ 실패 | CNI 또는 NetworkPolicy 문제 (Pod 네트워크 자체) |
| ⑥은 되는데 ⑦이 안 됨 | kube-proxy 문제, iptables 규칙 미생성 |
| ⑦은 되는데 ⑧이 안 됨 | DNS 문제 (18장) |

> **[보충]** 두 원천은 진단의 출발점이 다르다. Kubernetes_Internals_Network_Guide는 "이름이냐 IP냐"에서 위(DNS)부터 내려가고, textbook의 23.6 플로차트는 "같은 Pod → 같은 노드 → 다른 노드 → Service → DNS → NetworkPolicy"로 아래(Pod 네트워크)부터 훑는다. 둘은 모순이 아니라 같은 경로를 보는 방향 차이다. 충돌 시 더 최신·상세한 원천을 따른다는 규칙에 따라 이 책의 기본 플로차트(1.1)는 Internals Guide를 따르고, 세 점 호출은 그 안에서 경계를 빠르게 가르는 보조 기법으로 쓴다.

### 1.4 Service 단계 8점 점검

**한 줄 요약:** Service가 동작하지 않을 때는 Service → 엔드포인트 → 셀렉터 → Ready → 포트 → Pod → ClusterIP → DNS 순으로 위에서 아래로 확인한다.

```bash
# ① Service가 존재하고 ClusterIP가 할당됐는가
kubectl get svc web

# ② 엔드포인트가 있는가  ★ 가장 흔한 실패 지점
kubectl get endpointslice -l kubernetes.io/service-name=web
# 비어 있다면 → 셀렉터 불일치 또는 Pod가 Ready가 아님

# ③ 셀렉터가 Pod와 맞는가
kubectl get svc web -o jsonpath='{.spec.selector}'
kubectl get pods --show-labels

# ④ Pod가 Ready인가
kubectl get pods -l app=web

# ⑤ 포트가 맞는가
kubectl get svc web -o jsonpath='{.spec.ports}'
kubectl get pod <pod> -o jsonpath='{.spec.containers[*].ports}'

# ⑥~⑧ 은 1.3의 세 점 호출 (Pod IP / ClusterIP / DNS 이름)
```

증상별로는 엔드포인트가 비어 있으면 셀렉터 오타·Pod가 Ready 아님·네임스페이스 불일치, 일부 요청만 실패하면 일부 Pod의 `ready` 이상, 간헐적 연결 리셋이면 종료 중인 Pod로 가는 트래픽(preStop 확인), 외부에서만 안 되면 NetworkPolicy·방화벽·LB 헬스체크를 의심한다.

⑥은 되는데 ⑦이 안 될 때 kube-proxy의 규칙이 실제로 만들어졌는지는 모드별로 이렇게 본다(원천: 부록 A.9).

```bash
# iptables 모드
iptables-save -t nat | grep KUBE-SVC
iptables -t nat -nL KUBE-SVC-<hash> -v
conntrack -L | grep <service-ip>

# IPVS 모드
ipvsadm -Ln
ip addr show kube-ipvs0

# nftables 모드
nft list table ip kube-proxy
```

## 코어 2. 증상이 가리키는 계층

### 2.1 증상별 원인표

**한 줄 요약:** 증상 하나가 의심 계층 하나를 가리킨다. 표를 외워 두면 플로차트의 어느 단계로 점프할지 정해진다.

| 증상 | 유력 원인 | 확인 |
|---|---|---|
| 같은 노드는 되고 다른 노드는 안 됨 | 오버레이/라우팅, MTU | `ip route`, tcpdump |
| ping은 되는데 큰 전송이 안 됨 | **MTU** | `ping -M do -s` |
| 간헐적 타임아웃 | conntrack 고갈, MTU | `conntrack -C`, `dmesg` |
| DNS만 안 됨 | CoreDNS, NetworkPolicy | 2.3절 |
| 정책 적용 후 전부 안 됨 | **DNS 예외 누락** | 2.3절의 allow-dns |
| Pod가 `ContainerCreating`에서 멈춤 | CNI 플러그인 실패 | containerd 로그, `/etc/cni/net.d` |
| Pod에 IP가 없음 | IPAM 고갈, CNI 설정 | `describe pod` 이벤트 |
| 서비스는 되는데 특정 Pod만 안 됨 | 그 Pod의 readiness | 1.4절 |
| 외부에서만 안 됨 | SNAT, 방화벽, LB 헬스체크 | `externalTrafficPolicy` |
| 노드 재부팅 후 안 됨 | iptables 규칙 유실, CNI 상태 | kube-proxy/CNI Pod 재시작 |

### 2.2 MTU 불일치 — 가장 악명 높은 문제

**한 줄 요약:** ping과 작은 요청은 되는데 큰 응답·TLS 핸드셰이크에서만 멈추면 MTU다. 오버레이 캡슐화 헤더만큼 Pod MTU가 줄어야 한다.

**증상이 특이하다.**

```
· ping은 잘 된다
· 작은 HTTP 요청도 잘 된다
· 큰 응답이나 파일 전송에서 멈춘다
· TLS 핸드셰이크가 실패한다
· "간헐적으로" 느리다
```

**원인**

```
물리 네트워크 MTU: 1500
VXLAN 오버헤드:    -50
Pod 인터페이스 MTU: 1450 이어야 한다

만약 Pod MTU가 1500으로 설정되어 있으면:
  1500바이트 패킷 → VXLAN 캡슐화 → 1550바이트
  → 물리 MTU 초과 → 단편화 또는 드롭
```

**진단**

```bash
# ① MTU 확인
kubectl run t --rm -it --image=nicolaka/netshoot --restart=Never -- ip link show eth0
docker exec k8s-guide-worker ip link show | grep mtu

# ② 단편화 금지 ping으로 실제 MTU 찾기
kubectl run t --rm -it --image=nicolaka/netshoot --restart=Never -- \
  sh -c 'for size in 1500 1450 1400 1350; do
           echo -n "$size: "
           ping -c1 -M do -s $((size-28)) <TARGET_POD_IP> >/dev/null 2>&1 && echo OK || echo FAIL
         done'
```

첫 번째로 성공하는 크기가 실제 사용 가능한 MTU다.

| 환경 | 물리 MTU | 오버헤드 | Pod MTU |
|---|---|---|---|
| 일반 이더넷 + VXLAN | 1500 | 50 | **1450** |
| 일반 이더넷 + IPIP | 1500 | 20 | **1480** |
| 일반 이더넷 + WireGuard | 1500 | 60 | **1440** |
| AWS (점보 프레임) | 9001 | 50 | 8951 |
| GCP | 1460 | 50 | 1410 |

설정은 Calico에서 `calico-config` ConfigMap의 `veth_mtu: "1450"`, Cilium에서 `helm upgrade cilium cilium/cilium --set MTU=1450`이다.

> **⚠️ 클라우드 VPC 피어링과 VPN** — VPC 피어링이나 VPN을 거치면 MTU가 더 줄어든다. 온프레미스 연결이 있는 클러스터에서 **일부 대상만 통신이 안 되는** 증상이 나오면 MTU를 의심한다. (오버레이와 MTU의 원리는 [6장](../1부-리눅스-네트워크-기초/06-오버레이-VXLAN-MTU.md), CNI별 설정은 [15장](../3부-쿠버네티스-네트워크/15-CNI-플러그인과-패킷-경로.md))

> **[보충]** `ping -M do -s N`에서 `size-28`을 쓰는 것은 원천 스크립트 그대로다. 28은 ICMP 에코 요청의 페이로드 크기에 더해지는 IP 헤더(20바이트)와 ICMP 헤더(8바이트)의 합으로, 전체 패킷 크기를 MTU 후보와 맞추기 위한 것이다(원천에는 설명이 없다).

### 2.3 DNS 진단과 NetworkPolicy의 DNS 차단

**한 줄 요약:** 진단용 Pod에서 resolv.conf → CoreDNS 도달 → 내부 이름 → 외부 이름 → CoreDNS 상태 순으로 확인한다. NetworkPolicy 직후의 전면 장애는 DNS 차단이 대부분이다.

진단용 Pod(`kubectl run dns-debug --rm -it --image=nicolaka/netshoot --restart=Never -- bash`)에서 차례로 확인한다.

```bash
cat /etc/resolv.conf                                           # ① nameserver가 10.96.0.10인지, search가 올바른지
dig @10.96.0.10 kubernetes.default.svc.cluster.local           # ② kube-dns Service IP로 직접
dig @<coredns-pod-ip> kubernetes.default.svc.cluster.local     #    CoreDNS Pod IP로 직접 (Service를 건너뛰고)
nslookup kubernetes.default                                    # ③ 클러스터 내부 이름
nslookup web.default.svc.cluster.local
nslookup google.com                                            # ④ 외부 이름
kubectl get pods -n kube-system -l k8s-app=kube-dns            # ⑤ CoreDNS 자체 상태
kubectl logs -n kube-system -l k8s-app=kube-dns --tail=50
kubectl get endpointslice -n kube-system -l kubernetes.io/service-name=kube-dns
```

Service IP로는 안 되는데 Pod IP로는 되면 **kube-proxy 문제**(17장)다. 내부는 되는데 외부가 안 되면 CoreDNS의 `forward` 설정 또는 노드의 DNS 문제다.

| 증상 | 가능한 원인 | 확인 |
|---|---|---|
| **모든 DNS 실패** | CoreDNS Pod 다운, 엔드포인트 없음 | `kubectl get pods -n kube-system -l k8s-app=kube-dns` |
| **간헐적 실패** | CoreDNS 부하, conntrack 경합 | CoreDNS replica 늘리기, NodeLocal DNSCache |
| **정확히 5초 지연** | conntrack race condition | NodeLocal DNSCache, `single-request-reopen` |
| **외부만 실패** | `forward` 설정, 노드 DNS | Corefile의 forward, 노드 `/etc/resolv.conf` |
| **내부만 실패** | `kubernetes` 플러그인, RBAC | CoreDNS 로그, ServiceAccount 권한 |
| **특정 네임스페이스만** | NetworkPolicy가 DNS 차단 | 21장 |
| **`i/o timeout`** | UDP 패킷 유실, MTU 문제 | 2.2절 |
| **CoreDNS 로그에 `loop detected`** | 노드 resolv.conf가 자기 자신을 가리킴 | systemd-resolved 스텁 문제 |

기본 거부(default-deny) NetworkPolicy를 적용하면 **DNS도 차단된다.** 반드시 예외를 만들어야 한다.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns
spec:
  podSelector: {}
  policyTypes: [Egress]
  egress:
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: kube-system
          podSelector:
            matchLabels:
              k8s-app: kube-dns
      ports:
        - protocol: UDP
          port: 53
        - protocol: TCP
          port: 53
```

**NetworkPolicy를 적용한 뒤 갑자기 모든 것이 안 되는** 사고의 90%가 DNS 차단이다. (DNS 구조는 [18장](../3부-쿠버네티스-네트워크/18-DNS와-서비스-디스커버리.md), 정책은 [21장](../3부-쿠버네티스-네트워크/21-NetworkPolicy와-네트워크-보안.md))

**Docker 단일 호스트의 DNS 점검.** 내장 DNS(127.0.0.11) 장애는 대개 네 가지로 좁혀진다(원천: docker-fundamental 15.7). 첫째, 두 컨테이너가 **같은 사용자 정의 네트워크**에 있는가(이름 해석 범위는 네트워크 단위). 둘째, **기본 브리지**에 붙어 있지 않은가(내장 DNS가 적용되지 않는다). 셋째, `ndots`와 검색 도메인 조합이 예상 밖의 이름을 조회하게 만들지 않는가. 넷째, 앱의 **DNS 캐싱**(특히 JVM 계열은 오래 캐싱해 IP가 바뀐 뒤에도 옛 IP로 접속할 수 있다. dockerd가 아니라 앱 문제다). (Docker DNS는 [9장](../2부-Docker-네트워크/09-Docker-DNS와-서비스-디스커버리.md))

### 2.4 Ingress 진단

**한 줄 요약:** Ingress는 ADDRESS → IngressClass → 컨트롤러 인식 → 백엔드 엔드포인트 → 생성 설정 → 컨트롤러에서 백엔드 직접 호출 순으로 확인하고, HTTP 상태 코드가 위치를 알려 준다.

확인 순서는 `kubectl get ingress`(ADDRESS가 비어 있으면 컨트롤러가 처리하지 않음) → `kubectl get ingressclass`(`spec.ingressClassName`과 대조) → `kubectl describe ingress <name>`의 Events와 컨트롤러 로그(`kubectl logs -n ingress-nginx -l app.kubernetes.io/component=controller --tail=50`) → `kubectl get svc,endpointslice`(★ 1.4절의 진단) → 생성된 nginx 설정 확인(`kubectl exec -n ingress-nginx <controller-pod> -- cat /etc/nginx/nginx.conf | grep -A20 "server_name shop"`) → 컨트롤러 Pod에서 `curl -s http://web.default.svc.cluster.local`로 백엔드 직접 호출이다.

| 증상 | 원인 |
|---|---|
| `404 Not Found` (nginx 기본 페이지) | 호스트/경로 매칭 실패. `Host` 헤더 확인 |
| `503 Service Unavailable` | 백엔드 엔드포인트 없음 → 1.4절 진단 |
| `502 Bad Gateway` | 백엔드가 응답 안 함. 포트 불일치, 앱 크래시 |
| `504 Gateway Timeout` | 백엔드가 느림. `proxy-read-timeout` 조정 |
| TLS 인증서 오류 | Secret 이름·네임스페이스 확인. **Secret은 Ingress와 같은 네임스페이스에 있어야 한다** |
| ADDRESS 비어 있음 | `ingressClassName` 불일치, 컨트롤러 미설치 |
| 리다이렉트 루프 | `ssl-redirect` + 앞단 LB가 이미 TLS 종료. `force-ssl-redirect: false` |

마지막 항목이 클라우드 환경에서 흔하다. ALB가 TLS를 종료하고 HTTP로 컨트롤러에 전달하는데, 컨트롤러가 "HTTP네? HTTPS로 리다이렉트!"를 반복한다. `X-Forwarded-Proto` 헤더를 신뢰하도록 설정해야 한다. (Ingress 구조는 [19장](../3부-쿠버네티스-네트워크/19-Ingress와-Gateway-API.md))

### 2.5 노드 레벨 자원 고갈 — 연결이 몰릴 때만 나타나는 장애

**한 줄 요약:** conntrack 테이블, 임시 포트, Pod IP, iptables 규칙 수는 한계가 있고, 한계에 닿으면 코드는 멀쩡한데 새 연결만 조용히 실패한다.

**conntrack 고갈.** DNAT된 연결은 커널의 연결 추적 테이블에 기록되고, 응답 패킷은 이 테이블을 보고 역변환된다. **테이블이 가득 차면 새 연결이 거부된다.**

```bash
docker exec k8s-guide-worker sh -c 'echo "current: $(conntrack -C), max: $(sysctl -n net.netfilter.nf_conntrack_max)"'
dmesg | grep -i conntrack      # nf_conntrack: table full, dropping packet
```

**80%를 넘으면 위험하다.** 원인은 짧은 연결이 매우 많은 워크로드, 타임아웃이 긴 UDP 연결, 연결 누수다. 대책(원천 값 그대로):

```bash
sysctl -w net.netfilter.nf_conntrack_max=2097152
sysctl -w net.netfilter.nf_conntrack_tcp_timeout_time_wait=30
sysctl -w net.netfilter.nf_conntrack_udp_timeout=30
```

값을 무작정 올리는 것이 능사는 아니다. 항목 하나가 커널 메모리를 소비하므로 동시 연결 수 추세를 관측하며 조정한다. eBPF 소켓 레벨 로드밸런싱을 쓰면 Service 경유 트래픽의 conntrack 의존이 줄지만, 일반 Pod 간 연결이나 외부로 나가는 연결은 여전히 conntrack을 거친다. (conntrack은 [5장](../1부-리눅스-네트워크-기초/05-netfilter-iptables-NAT-conntrack.md), eBPF는 [22장](../3부-쿠버네티스-네트워크/22-eBPF-데이터플레인과-Cilium.md))

> **[보충]** textbook(23.5)은 "Cilium의 eBPF 데이터 플레인은 자체 연결 추적을 쓰므로 이 문제에서 자유롭다"고 쓰고, Internals Guide(19.3)는 "완전히 사라지지는 않는다"고 쓴다. 더 상세한 후자를 따랐다.

**임시 포트(ephemeral port) 고갈.** 같은 목적지로 짧은 연결을 매우 많이 여는 아웃바운드 워크로드에서 신규 연결이 실패할 수 있다.

```bash
sysctl net.ipv4.ip_local_port_range
ss -s
```

앱 쪽에서 keep-alive나 커넥션 풀링으로 완화하거나 포트 범위 확장을 검토한다. 리눅스의 에페머럴 포트 기본 범위는 32768&#126;60999(약 28,000개)이며, 초당 500개 짧은 연결을 만드는 클라이언트는 60초 안에 다 쓴다(원천: linux/06 6.3). (소켓·포트는 [2장](../1부-리눅스-네트워크-기초/02-소켓-TCP-포트-DNS-기초.md))

**Pod IP 고갈.** 노드당 Pod CIDR은 `kubectl get nodes -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.podCIDR}{"\n"}{end}'`로 본다. 클러스터 CIDR이 `10.244.0.0/16`(65,536개)이고 노드당 `/24`(254개, 실제로는 maxPods 110에 제한)면 최대 노드 수는 2^(24-16) = 256개다. 노드가 256개를 넘으면 IP를 할당할 수 없으므로 클러스터 생성 시점에 규모를 예측해야 한다. AWS VPC CNI는 VPC 서브넷의 IP를 직접 쓰므로 서브넷이 작으면 금방 소진되고, `kubectl set env daemonset aws-node -n kube-system ENABLE_PREFIX_DELEGATION=true`(접두사 위임)로 완화한다.

**iptables 규칙 폭증.** 규칙 수는 `iptables -t nat -S | wc -l`로 센다. 서비스 1,000개 × 엔드포인트 평균 10개면 규칙 수 ≈ 1,000 × (2 + 10 × 2) = 22,000이고, 서비스 5,000개면 10만 개를 넘는다. 증상은 서비스 변경 반영의 수 초~수십 초 지연, kube-proxy CPU 상승, `iptables-restore` 실행 시간 증가다. 대책은 IPVS 모드, Cilium의 kube-proxy 대체(eBPF), 서비스 수 자체 줄이기(헤드리스 활용)다. 동기화 시간은 `kubectl get --raw /metrics 2>/dev/null | grep kubeproxy_sync_proxy_rules_duration`으로 본다.

> **[보충]** 두 원천은 IPVS의 위상이 다르다. textbook(9.5, 23.5)은 IPVS 전환을 대책으로 제시하고, Kubernetes_Internals_Network_Guide(15장 요약)는 IPVS 모드가 KEP-5495에 따라 공식 폐기 경로에 들어섰다고 쓴다(v1.35 경고 로그, v1.37 기능 게이트, v1.40 기본 비활성, v1.43 코드 제거). 더 상세한 후자를 따라, 규칙 폭증의 장기 대책으로는 nftables 모드나 eBPF 대체도 함께 고려해야 한다. 자세한 비교는 [17장](../3부-쿠버네티스-네트워크/17-kube-proxy-데이터플레인.md).

## 코어 3. 어디에서 볼 것인가 — 관찰 위치와 도구

### 3.1 Pod 네트워크 네임스페이스 안에서 캡처

**한 줄 요약:** 가장 정확한 방법은 문제 Pod의 네트워크 네임스페이스 안에서 캡처하는 것이다. 운영 이미지에는 `tcpdump`가 없으므로 디버그 컨테이너나 `nsenter`로 도구를 빌려 쓴다.

```bash
# 방법 ① kubectl debug로 대상 Pod에 임시 디버그 컨테이너 붙이기
# (같은 네트워크 네임스페이스를 공유 — --target으로 프로세스 네임스페이스까지 공유 가능)
kubectl debug -it <pod-name> \
  --image=nicolaka/netshoot \
  --target=<container-name> \
  -- tcpdump -i any -n port 80
```

```bash
# 방법 ② nsenter로 노드에서 직접 Pod의 네트워크 네임스페이스 진입
# (Pod의 PID를 먼저 확인해야 한다)
docker exec k8s-guide-worker crictl inspect <container-id> \
  | grep -i pid

docker exec k8s-guide-worker nsenter -t <pid> -n tcpdump -i eth0 -n
```

Pod 안의 네트워크 설정은 다음으로 확인한다.

```bash
kubectl exec pod-a -- ip addr
kubectl exec pod-a -- ip route
kubectl exec pod-a -- cat /etc/resolv.conf
```

(네임스페이스·veth 구조는 [3장](../1부-리눅스-네트워크-기초/03-네트워크-네임스페이스.md), [4장](../1부-리눅스-네트워크-기초/04-veth-브리지-라우팅-ARP.md))

### 3.2 호스트 쪽 veth에서 캡처

**한 줄 요약:** 이미지가 너무 미니멀해 디버그 컨테이너조차 부담스러우면 Pod 안이 아니라 호스트 쪽 veth 끝에서 캡처한다.

Pod의 네트워크 네임스페이스는 veth 쌍의 한쪽 끝이고, 다른 쪽 끝은 호스트 네임스페이스(또는 CNI 브리지)에 있다. Docker 컨테이너에서는 `eth0@if7`의 `@if` 뒤 숫자가 반대쪽 끝의 인덱스다(`ip link show type veth`, `bridge link show`).

```bash
# Pod에 연결된 veth 인터페이스 이름 찾기
docker exec k8s-guide-worker sh -c   'ethtool -S <pod-내부-eth0-ifindex> 2>/dev/null; ip link | grep veth'

# 호스트에서 해당 veth로 캡처 — Pod 내부에 아무것도 설치하지 않고도 확인 가능
docker exec k8s-guide-worker tcpdump -i <veth이름> -n
```

### 3.3 노드 간 경로와 양쪽 동시 캡처

**한 줄 요약:** 노드의 라우팅 테이블·오버레이 인터페이스·이웃 테이블을 보고, 양쪽 노드에서 동시에 캡처해 패킷이 사라지는 지점을 특정한다.

```bash
docker exec k8s-guide-worker ip route | grep 10.244                                      # 라우팅 테이블
docker exec k8s-guide-worker ip -d link show | grep -A2 -E 'vxlan|ipip|flannel'          # 오버레이 인터페이스
docker exec k8s-guide-worker ip neigh                                                    # ARP/이웃 테이블
```

```bash
docker exec k8s-guide-worker tcpdump -i any -nn "host 10.244.2.7" -c 20    # 노드에서 특정 Pod IP 트래픽
docker exec k8s-guide-worker tcpdump -i any -nn "udp port 8472" -c 10      # 오버레이(VXLAN) 패킷
```

**양쪽 노드에서 동시에 캡처하면** 어디서 패킷이 사라지는지 정확히 알 수 있다.

> **[보충]** 위 명령의 VXLAN 필터는 원천(textbook 23.6)이 `udp port 8472`로 쓴 값이다. Docker 오버레이 실습(docker-fundamental 13장)에서는 VXLAN 목적지 포트를 4789(RFC 7348 표준)로 확인하라고 한다. 두 값이 다른 것은 원천끼리 다른 환경을 다루기 때문이며, 실제 포트는 `ip -d link show type vxlan`의 `dstport` 항목으로 확인하는 것이 안전하다.

### 3.4 흐름 단위 관측 — Hubble과 cilium monitor

**한 줄 요약:** Cilium 환경이면 패킷을 캡처하지 않고도 허용·거부된 흐름과 정책 판정이 곧바로 보인다. tcpdump는 "바이트", Hubble은 "정책 판단"에 답한다.

```bash
# 특정 네임스페이스를 오가는 모든 흐름
hubble observe --namespace shop

# 정책에 의해 거부(DROPPED)된 흐름만
hubble observe --namespace shop --verdict DROPPED

# 특정 Pod를 목적지로 하는 흐름만, 실시간 팔로우
hubble observe --to-pod shop/backend-abc123 --follow
```

거부된 흐름은 `DROPPED (Policy denied)`처럼 출력된다. Hubble보다 저수준으로, BPF 프로그램이 내는 개별 이벤트(드롭, 정책 판정)는 `cilium monitor`로 본다.

```bash
cilium status
cilium monitor --type drop
cilium monitor --type policy-verdict
```

> **[보충]** 원천끼리 Hubble 판정값 표기가 다르다. Kubernetes_Internals_Network_Guide 본문(19.4)과 textbook 과제는 `--verdict DROPPED`를, 같은 책의 부록 A.11은 `--verdict DENIED`와 `--pod <namespace>/<pod>`를 쓴다. 더 상세한 본문 표기(`DROPPED`)를 따랐다. 어느 쪽이든 실제 환경의 `hubble observe --help`로 확인하는 것이 안전하다.

### 3.5 Docker 단일 호스트에서 규칙 눈으로 확인하기

**한 줄 요약:** 포트를 게시한 컨테이너가 안 되면 `iptables-save`로 DOCKER 체인의 DNAT 규칙과 docker-proxy 프로세스를 직접 본다.

```bash
docker run -d --name web -p 8080:80 nginx:latest

# nat 테이블 전체를 텍스트로 덤프
iptables-save -t nat | grep -i docker
```

출력에는 `DOCKER` 체인이 있고, 그 안에 `-p tcp --dport 8080 -j DNAT --to-destination 172.17.0.2:80`과 비슷한 규칙이 보인다. `PREROUTING`과 `OUTPUT` 체인에서 `DOCKER` 체인으로 점프하는 규칙도 함께 확인된다. iptables-nft 배포판이라면 `nft list ruleset | grep -A 5 -i docker`로도 볼 수 있다. 외부 통신용 마스커레이딩 규칙은 `iptables -t nat -L POSTROUTING -n -v | grep -i MASQUERADE`, 게시 포트와 `docker-proxy`의 대응은 `ps -ef | grep docker-proxy | grep -v grep`으로 본다.

(포트 게시는 [8장](../2부-Docker-네트워크/08-브리지-네트워크와-포트-게시.md), 방화벽 백엔드는 [11장](../2부-Docker-네트워크/11-Docker-방화벽-iptables에서-nftables로.md))

## 실무 적용

### 체크리스트

- [ ] 장애 신고를 받으면 "이름인가 IP인가"부터 묻고, DNS → 노드 간 연결 → Service → NetworkPolicy → 노드 자원 순으로 배제한다.
- [ ] 같은 대상을 Pod IP, ClusterIP, DNS 이름으로 차례로 호출해 CNI·kube-proxy·DNS 영역을 가른다. ClusterIP에 ping을 보내 판단하지 않는다.
- [ ] Service 문제는 엔드포인트(EndpointSlice) 비어 있음과 `ready`를 먼저 본다. 가장 흔한 실패 지점이다.
- [ ] 큰 전송에서만 멈추면 `ping -M do -s`로 MTU를 찾고, 오버레이 오버헤드(VXLAN 50, IPIP 20)를 반영했는지 확인한다.
- [ ] 정책을 적용하는 순간 DNS(UDP/TCP 53) 예외를 함께 넣었는지 확인한다. 사용 중인 CNI가 NetworkPolicy를 시행하는 CNI인지도 확인한다(kindnet·Flannel은 시행하지 않는다).
- [ ] 부하 때 간헐 실패하면 `conntrack -C`와 상한을 비교(80% 위험)하고 `dmesg`에서 `table full`을 찾는다. 임시 포트 범위와 `ss -s`도 본다.
- [ ] 캡처가 필요하면 위치를 고른다. Pod 안(`kubectl debug`/`nsenter`), 호스트 veth, 양쪽 노드 동시, Cilium이면 Hubble.
- [ ] 새 클러스터를 만들었거나 CNI를 교체했다면 Sonobuoy 같은 적합성 테스트로 확인한다(`sonobuoy run --mode=quick --wait`, 네트워크만은 `--e2e-focus="\[sig-network\].*Conformance"`).

### 시나리오로 확인하기

1. **증상:** 새로 배포한 서버 Pod에서 `backend` 서비스를 이름으로 호출하는데 3초 뒤 타임아웃. 다른 요청은 정상이다. 방금 `default-deny-ingress` NetworkPolicy를 `shop` 네임스페이스(backend가 있는 곳)에 적용했다.
   **의심 부품 → 확인 방법 → 해결:**

   <details markdown="1"><summary>답 확인</summary>

   이름은 해석되어 연결 시도까지 갔으니 ① DNS는 통과했고, 다른 요청이 되니 ② CNI 연결성도 정상이다. EndpointSlice에 ready 백엔드가 있으면 ③ Service도 통과다. 남는 것은 ④ NetworkPolicy다. Cilium이면 `hubble observe --namespace shop --verdict DROPPED --last 5`로 거부된 흐름이 바로 보이고, 아니면 `kubectl get networkpolicy -A`와 `kubectl describe networkpolicy`로 확인한다. 정책에 해당 방향의 허용 규칙을 추가한다. (CNI가 정책을 시행하지 않는 kindnet이면 차단 자체가 재현되지 않는다.) → 코어 1

   </details>

2. **증상:** 다른 노드의 Pod와는 ping은 되고 작은 요청도 되는데, 큰 파일 다운로드와 TLS 핸드셰이크가 멈춘다. 같은 노드의 Pod와는 문제가 없다.
   **의심 부품 → 확인 방법 → 해결:**

   <details markdown="1"><summary>답 확인</summary>

   증상표의 "같은 노드는 되고 다른 노드는 안 됨" + "ping은 되는데 큰 전송이 안 됨"이므로 오버레이의 MTU다. Pod 인터페이스 MTU를 `ip link show eth0`로 보고, `ping -c1 -M do -s $((size-28))`로 1500, 1450, 1400, 1350을 시험해 처음 성공하는 크기를 찾는다. VXLAN이면 Pod MTU를 1450으로(Calico `veth_mtu: "1450"`, Cilium `--set MTU=1450`) 맞춘다. VPC 피어링이나 VPN을 거치면 더 줄어든다. → 코어 2

   </details>

3. **증상:** 트래픽이 몰리는 시간대에만 새 연결이 간헐적으로 실패하고, 재시작하면 잠깐 괜찮아진다. 코드 변경은 없었다.
   **의심 부품 → 확인 방법 → 해결:**

   <details markdown="1"><summary>답 확인</summary>

   플로차트 ① DNS ~ ④ 정책을 배제했다면 ⑤ 노드 자원 고갈이다. `conntrack -C`와 `nf_conntrack_max`를 비교(80% 초과면 위험)하고 `dmesg | grep -i conntrack`으로 `nf_conntrack: table full, dropping packet`을 찾는다. 아웃바운드가 많다면 `ip_local_port_range`와 `ss -s`도 본다. 원인이 짧은 연결 폭주면 keep-alive·커넥션 풀로 앱을 고치고, 필요하면 `nf_conntrack_max`와 타임아웃을 튜닝한다. → 코어 2

   </details>

### 3. 기억 고리

- **C++ 유추:** 장애 진단 = 접속 안 되는 서버를 "프로세스 → 방화벽 → 라우팅 → DNS" 순으로 지워 가는 일. ⚠️ 깨지는 곳: 사이에 가상 부품이 많고, ping과 `tcpdump` 같은 익숙한 도구가 그대로 통하지 않는다(ClusterIP ping 무응답, 이미지에 도구 없음).
- **비유:** 진단 = 병원 접수에서 검사실까지 "이름 확인 → 이동 경로 → 대표번호 연결 → 출입 허가 → 건물 수용량" 순서로 막힌 곳을 찾는 것. ⚠️ 비유가 깨지는 지점: 환자는 한 번만 막히지만 네트워크는 계층 여러 곳이 동시에 문제일 수 있고, 한 증상이 여러 계층에서 나올 수 있다.
- **묶음(3의 법칙):** 세 점 호출(Pod IP / ClusterIP / DNS 이름), 관찰 위치 세 곳(Pod 안 / 호스트 veth / 양쪽 노드), 노드 자원 고갈 세 가지(conntrack / 임시 포트 / IP·규칙 수).
- **대칭·순서:** 위 → 아래(DNS → CNI → Service → 정책 → 자원)와 흔함 → 드묾. 대비 쌍: tcpdump(바이트) vs Hubble(판정), Pod 안 캡처 vs 호스트 veth 캡처.
