## 결정적 지식 3개

23개 장의 거의 모든 현상은 아래 세 원리 중 하나로 설명됩니다. 접속이 안 되거나 낯선 규칙·옵션을 만나면 "이건 셋 중 무엇의 결과인가?"부터 물어보세요.

### ① 컨테이너·Pod의 네트워크는 네임스페이스 안의 독립된 스택이고, veth·브리지·터널로 이어 붙인다

> 네트워크 네임스페이스가 인터페이스·라우팅 테이블·방화벽 규칙·포트 공간을 **프로세스 그룹별로 다르게 보이게** 하고, veth pair(가상 케이블)가 그 경계를 넘으며, 브리지(같은 대역 L2 스위칭)·라우팅·캡슐화(VXLAN)가 스택들을 이어 준다.

| 이 원리에서 나오는 것 | 장 |
|---|---|
| 새 네임스페이스에는 `lo` 하나뿐(DOWN) — 네임스페이스는 복제가 아니라 "뷰" | 3장 |
| 컨테이너 안 `listen(80)`은 호스트 포트를 열지 않음 → `-p`의 DNAT가 필요 | 1·8장 |
| veth는 항상 쌍, 브리지는 FDB로 L2 스위칭, 대역 밖은 `ip route`가 정함 | 4장 |
| Docker의 Sandbox = 네임스페이스, Endpoint = 가상 인터페이스, Network = 논리 그룹 | 7장 |
| 같은 브리지 안은 NAT 없는 스위칭, 밖으로는 라우팅 + MASQUERADE | 8장 |
| macvlan/ipvlan은 NAT 없이 물리망에, host는 netns 분리 포기, none은 `lo`만 | 10장 |
| Rootless는 veth·브리지를 못 만져 TAP + 유저스페이스 스택으로 대신 통신 | 12장 |
| Pod = pause가 소유한 네임스페이스에 컨테이너들이 `setns`로 합류 → 앱이 죽어도 IP 유지 | 3·13장 |
| 네임스페이스는 가시성 축일 뿐 — 권한은 capability 비트마스크와 seccomp가 따로 막음 | 3장 |
| 브리지는 호스트를 못 넘는다 → VXLAN 캡슐화(UDP 4789)와 MTU 약 50바이트 손실 | 6·15장 |
| 노드 사이는 오버레이 / 네이티브 라우팅 / 클라우드 네이티브 IP 중 하나로 운반 | 15장 |

**스스로 확인:** "ping·작은 요청은 되는데 큰 전송만 실패한다"와 "Pod 안 두 컨테이너가 localhost로 통신한다"를 ①만으로 설명할 수 있나요?

### ② 가상 주소는 커널 netfilter가 패킷의 주소를 바꿔서 실현한다

> 접속한 주소에 그 주소를 가진 장비가 없어도 된다. 라우팅 결정 **앞**(PREROUTING)에서 목적지를 바꾸고(DNAT), 나가는 길(POSTROUTING)에서 출발지를 바꾸며(MASQUERADE), 되돌아오는 패킷은 **conntrack**이 기억한 변환 정보로 복원한다.

| 이 원리에서 나오는 것 | 장 |
|---|---|
| DNAT는 PREROUTING, MASQUERADE는 POSTROUTING, DNAT는 연결의 첫 패킷에만 적용 | 5장 |
| 같은 호스트의 방화벽 도구들은 서로 다른 훅(INPUT·FORWARD)에 걸려 서로를 우회할 수 있다 | 5·8·11장 |
| `-p`는 `DOCKER` 체인의 DNAT 규칙 + `docker-proxy` 두 메커니즘의 결과 | 8장 |
| 컨테이너의 `127.0.0.11:53`은 netns 안의 DNAT가 dockerd 내장 리졸버로 넘김 | 9장 |
| 게시된 포트에는 Docker 규칙이 호스트 방화벽보다 먼저 평가됨 (Engine 28은 미게시 포트만 기본 차단, Engine 29의 실험적 `docker-bridges` 테이블은 규칙 공간을 분리) | 8·11장 |
| ClusterIP는 어떤 인터페이스에도 붙지 않은 "약속", 노드 규칙이 Pod IP로 DNAT | 1·16장 |
| `KUBE-SERVICES → KUBE-SVC-* → KUBE-SEP-*`, 확률 `1/(N−i+1)`, `0x4000` 마크가 노드를 건너는 트래픽의 SNAT를 정함 | 1·5·17장 |
| 사이드카 메시는 init 컨테이너가 심은 iptables로 모든 트래픽을 프록시로 보냄 | 20장 |
| NetworkPolicy의 iptables 시행은 규칙 수에 비례, eBPF는 맵 룩업·`connect()` 시점 변환 | 21·22장 |
| conntrack 테이블이 차면 새 연결 거부, 정확히 5초 지연은 conntrack 경쟁(DNS) 의심 | 5·18·23장 |

**스스로 확인:** "kube-proxy가 죽어도 이미 맺은 연결은 계속 된다"와 "응답 패킷이 ClusterIP 출발지로 돌아온다"를 ②만으로 설명할 수 있나요?

### ③ 선언된 의도는 컨트롤러·플러그인이 노드 커널의 규칙으로 번역해야 실행된다

> Service·Ingress·NetworkPolicy·CNI 설정은 모두 **API 서버에 기록된 데이터(약속)**일 뿐이다. 실행은 그것을 watch하는 구현 컴포넌트(CNI 플러그인, kube-proxy, CoreDNS, Ingress 컨트롤러, cilium-agent)가 커널 규칙·프록시 설정·BPF 맵으로 바꿔서 한다.

| 이 원리에서 나오는 것 | 장 |
|---|---|
| IP-per-Pod는 규칙만 정하고 배선은 CNI에 위임 | 13장 |
| CNI = 런타임이 실행 파일을 호출하는 계약(ADD/DEL/CHECK/VERSION), IP 할당은 두 층 | 14장 |
| Docker도 같은 구조: dockerd의 libnetwork가 정책, 드라이버가 패킷 처리 | 7·9장 |
| Service(의도) → EndpointSlice 컨트롤러(현재 대상, `ready`) → kube-proxy(노드 규칙) | 16·17장 |
| CoreDNS는 평범한 워크로드, `kubernetes` 플러그인이 API 서버를 watch (search/ndots 확장은 Pod 안 리졸버 몫이라 비용이 CoreDNS 로그·메트릭에 남음) | 18장 |
| Ingress = 데이터, IngressController = 조정 루프(ingress-nginx는 데이터 경로에 있고 ALB 컨트롤러는 없음), Gateway API는 세 역할로 분리 | 19장 |
| 사이드카는 뮤테이팅 어드미션 웹훅이 주입 | 20장 |
| NetworkPolicy의 시행자는 CNI — 미지원 CNI에서는 효과 없음, 한 연결은 출발 egress와 도착 ingress 양쪽 허용이 필요 | 21장 |
| cilium-agent가 BPF 맵을 쓰고 커널 프로그램이 읽음, 에이전트가 죽어도 트래픽 유지 | 22장 |
| 진단: 오브젝트 모델(의도)이 정상인지 먼저, 정상이면 구현(데이터플레인)을 본다 | 17·23장 |

**스스로 확인:** "NetworkPolicy를 만들었는데 효과가 없다"와 "Ingress를 만들었는데 동작하지 않는다"를 ③으로 설명할 수 있나요?

## 패킷 여정 한 줄 지도

```
앱 ─ 이름 조회(127.0.0.11 또는 CoreDNS, 9·18장) → ClusterIP로 connect
   → 컨테이너/Pod netns의 eth0 → veth → 호스트 브리지·라우팅 (3·4장)
   → PREROUTING DNAT: ClusterIP → Pod IP (5·16·17장, 응답은 conntrack이 복원)
   → 같은 노드면 veth로, 다른 노드면 VXLAN 캡슐화/네이티브 라우팅 (6·15장) → 상대 Pod
   나갈 때: POSTROUTING MASQUERADE (5·8장)  ·  밖에서 들어올 때: LoadBalancer → NodePort → Ingress (16·19장)
   통과 여부: NetworkPolicy (21장)  ·  안 닿으면: 계층별로 잘라 진단 (23장)
```

**C++ 게임 서버로 번역하면:** 공유기의 포트포워딩·NAT 라우터가 같은 커널 안의 iptables 규칙이 되고(②), 설정 파일에 박아 둔 서버 IP 대신 변하지 않는 가상 좌표(Service)와 이름(DNS)을 쓰며(③), `bind(0.0.0.0:80)`이 호스트 포트를 점유하지 않는 이유는 포트 공간이 네임스페이스별로 분리되기 때문이다(①). 출처는 1장이다.

## 장별 코어

### 1장. 패킷 한 개의 여정

> 패킷은 컨테이너의 격리된 네트워크 스택에서 출발해 veth와 브리지로 호스트에 올라오고, 경계마다 NAT(출발지 변경 MASQUERADE, 목적지 변경 DNAT)나 캡슐화를 거치며, 쿠버네티스에서는 Pod 간 NAT 없는 평평한 네트워크 위에 "이름(DNS) → 가상 주소(Service) → 실제 Pod(DNAT) → 외부 진입(Ingress)"의 네 문제가 층층이 얹혀 있다.

- **컨테이너는 자기만의 네트워크 스택을 갖고, veth와 브리지로 호스트에 꽂힌다** — 네트워크 네임스페이스가 인터페이스·라우팅·방화벽·포트 공간을 격리하고, veth pair의 한쪽 끝이 호스트 브리지에 연결된다. 같은 브리지 안은 L2 스위칭, 밖으로는 라우팅 + NAT다.
- **주소 바꿔치기는 NAT와 conntrack이 한다** — 나갈 때는 출발지를 바꾸고(MASQUERADE, POSTROUTING), 들어올 때는 라우팅 결정 전에 목적지를 바꾸며(DNAT, PREROUTING), 응답은 conntrack이 기억한 변환 정보로 되돌린다.
- **쿠버네티스는 "Pod마다 IP, NAT 없는 평평한 네트워크"를 요구하고, 그 구현(CNI)이 노드 간 이동을 맡는다** — 노드 사이는 캡슐화(VXLAN)나 네이티브 라우팅(BGP) 중 하나로 옮기고, 캡슐화에는 MTU 손실이 따른다.
- **Service는 약속이고 실행은 노드 커널이 한다** — kube-proxy가 만든 `KUBE-SERVICES → KUBE-SVC-* → KUBE-SEP-*` 규칙이 연결 단위로(첫 SYN에서 한 번) 백엔드를 확률로 고르고 DNAT하며, 응답은 conntrack이 되돌린다. 같은 규칙망 안의 `0x4000` 마크가 노드를 건너는 트래픽의 SNAT(클라이언트 IP 소실)를 만들고, Ingress 컨트롤러는 Service를 건너뛰어 자기 프록시 상태로 Pod IP에 직접 보낸다.

### 2장. 소켓·TCP·포트·DNS 기초

> 소켓은 fd이고 핸드셰이크와 accept 큐는 커널이 쥐며, TCP는 메시지 경계 없는 바이트 스트림이고, 동시 연결의 한계는 포트(에페머럴 범위)와 I/O 모델(블로킹 스레드 대 `epoll`)이 정하며, 이름 해석(`getaddrinfo`)은 동기 블로킹이라 이벤트 루프를 멈추고 컨테이너에서는 `resolv.conf`가 누구를 가리키는지가 장애 원인이 된다.

- **소켓은 fd이고 핸드셰이크·accept 큐는 커널이 쥔다** — `accept()`는 이미 완성된 연결을 큐에서 꺼낼 뿐이어서, 서버가 `accept`를 안 불러도 `connect`는 성공한다. 큐(backlog)가 차면 그때부터 SYN이 무시되고 `ss -ltn`의 Recv-Q/Send-Q와 `nstat`으로 진단한다. fd이므로 이벤트 루프 하나가 소켓·파이프·타이머·시그널을 함께 기다리고, 같은 머신에서는 `AF_UNIX` 소켓이 fd 자체를 다른 프로세스에 넘길 수 있다.
- **TCP는 바이트 스트림이고 커널 옵션이 동작을 바꾼다** — `read`는 1바이트만 돌려줘도 정상이고(0은 EOF, `ECONNRESET`은 RST), `TCP_NODELAY`·keepalive·`SIGPIPE`·half-open이 장애의 단골이다. 파일을 보낼 때 `sendfile`은 유저 공간 복사를 건너뛴다.
- **동시 연결의 한계는 포트와 I/O 모델이 정한다** — 포트는 에페머럴 범위(기본 32768&#126;60999)와 `TIME_WAIT`가 고갈시키고, 스레드-per-연결은 수천에서 한계가 오며(C10K), `epoll`은 fd를 한 번 등록해 O(준비된 수)로 답한다. Edge-triggered는 `EAGAIN`까지 읽어야 하고, `io_uring`은 준비 모델이 아니라 완료 모델이다.
- **DNS 조회는 동기 블로킹이다** — `getaddrinfo()`는 `/etc/hosts`와 `/etc/resolv.conf`의 네임서버를 보고 응답을 기다리므로 이벤트 루프 안에서 부르면 모든 커넥션이 멈추며, 컨테이너의 DNS 지연은 흔한 장애 원인이다.

### 3장. 네트워크 네임스페이스

> 네트워크 네임스페이스는 인터페이스·라우팅 테이블·방화벽 규칙·소켓·포트 공간을 프로세스 그룹별로 다르게 "보이게" 하는 커널 기능(막 만든 것은 `lo` 하나뿐인 빈 껍데기)이고, `/proc/[pid]/ns/`의 inode 번호로 식별하고 `setns`로 합류하며, 쿠버네티스 Pod는 pause가 소유한 네임스페이스에 앱 컨테이너가 합류한 구조라 `ip netns`+`unshare`로 손으로 재현되고, 네임스페이스는 격리의 한 축일 뿐이라 권한은 capability 비트마스크와 seccomp 프로파일이 따로 막는다.

- **네임스페이스는 복제가 아니라 "뷰"이고, 네트워크 네임스페이스는 가장 구현이 복잡한 축이다** — 같은 커널·CPU·물리 NIC를 공유하되 라우팅 테이블뿐 아니라 방화벽 규칙·소켓·`/proc/net` 통계까지 네임스페이스별로 독립 유지된다(2.6.29 전후로 점진적 완성). 새 네임스페이스에는 `lo` 하나만 있고 DOWN 상태다.
- **`/proc/[pid]/ns/`의 inode 번호로 같은 네임스페이스인지 판별하고, `setns`로 합류한다** — 새로 만들기(`clone`/`unshare`)와 합류하기(`setns`)는 다른 시스템콜이고, 링크는 실제로 열 수 있는 fd라서 `nsenter`가 호스트의 도구를 가지고 들어간다. `ip netns`와 Docker는 서로 다른 경로에 네임스페이스를 등록한다.
- **격리보다 "공유"가 설계다** — Pod는 pause가 네임스페이스를 소유하고 나머지가 합류하는 구조이고, 손으로 만든 `ip netns` Pod에서 같은 IP·포트 공간(`net`)과 분리된 `pid`/`mnt`가 검증된다. 컨테이너 런타임은 이 과정을 OCI 스펙에 따라 자동화할 뿐이다.
- **네임스페이스는 가시성 한 축일 뿐이다** — "무엇을 할 수 있는가"는 capability(유효 capability는 `/proc/self/status`의 비트마스크)와 seccomp(허용 시스템 콜 필터)가 따로 막으며, `NET_ADMIN` 없이는 `ip link set lo down`도 실패한다.

### 4장. veth·브리지·라우팅·ARP

> veth pair는 두 끝이 서로 다른 네임스페이스에 놓일 수 있는 가상 케이블이라 "어느 끝에서 보느냐"가 관찰 지점을 정하고(짝은 `@ifN` 인덱스로 이어진다), 같은 브리지 안은 MAC 주소 테이블(FDB)로 L2 스위칭되며, 대역 밖은 라우팅 테이블이 다음 홉을 정하고(노드마다 Pod 대역 경로 한 줄), ARP/NDP가 그 다음 홉의 IP를 MAC으로 풀어 준다.

- **veth는 두 개의 끝점이고, 어느 끝에서 보느냐가 관점이다** — 한쪽에 들어간 패킷이 다른 쪽으로 그대로 나오므로, 컨테이너 안 `eth0`·호스트 쪽 veth·노드 `eth0`에서 `tcpdump`를 걸면 같은 흐름을 다른 지점에서 본다. 이미지에 도구가 없어도 호스트 쪽 veth에서 캡처할 수 있고, 손으로 `ip link add ... type veth peer name ...` → `ip link set ... netns` 순서로 CNI가 하는 일을 재현한다.
- **브리지 = 가상 스위치** — 같은 브리지 안의 통신은 FDB를 보고 프레임을 전달하는 L2 스위칭이며 라우팅도 NAT도 없다. `bridge link show`와 `bridge fdb show br docker0`으로 본다.
- **대역 밖은 라우팅이 정한다** — 컨테이너는 기본 게이트웨이(브리지 IP)로 보내고 호스트가 IP 포워딩 + MASQUERADE로 내보낸다. 노드 간 경로는 `10.244.2.0/24 via 192.168.1.11 dev eth0` 같은 노드당 한 줄이며, 캡슐화 인터페이스가 보이면 오버레이이고 클러스터/노드 마스크가 최대 노드 수를 정한다.
- **ARP는 같은 L2 세그먼트 안에서 IP를 MAC으로 푼다** — IPv4는 ARP, IPv6는 NDP가 맡고 `ip neigh`로 이웃 테이블을 본다. 여러 노드가 같은 IP를 ARP로 광고하면 충돌이 생긴다(IPVS `kube-ipvs0`, MetalLB L2).

### 5장. netfilter·iptables·NAT·conntrack

> netfilter는 커널의 패킷 경로에 걸린 훅(PREROUTING·INPUT·FORWARD·OUTPUT·POSTROUTING)이고 iptables/nftables는 그 훅에 규칙을 거는 도구이며, 목적지를 바꾸는 DNAT는 라우팅 결정 앞(PREROUTING)에서, 출발지를 바꾸는 MASQUERADE는 나가는 길(POSTROUTING)에서 일어나고, 되돌아오는 패킷은 conntrack이 기억한 변환 정보로 자동 복원된다.

- **패킷은 훅을 지나고, 규칙은 거기에 걸려 있다** — 훅 위치가 곧 "무엇을 할 수 있는가"를 정한다. 호스트 자신으로 가는 패킷은 INPUT, 컨테이너로 가는 패킷은 FORWARD를 지나므로, 어느 훅에 규칙을 거느냐에 따라 같은 호스트의 두 방화벽 도구가 서로의 트래픽을 못 보거나 우회한다.
- **NAT는 체인 사슬이고, SNAT는 마크가 정한다** — DNAT(PREROUTING)↔MASQUERADE(POSTROUTING)의 시점 대칭은 입문 책에서 배웠다. 심화 지점은 쿠버네티스가 이를 `KUBE-SERVICES → KUBE-SVC-*(확률) → KUBE-SEP-*(DNAT)`로 풀고, 출발지 변환은 `KUBE-MARK-MASQ`가 남긴 `0x4000` 마크를 `KUBE-POSTROUTING`이 보고 적용한다는 것이다.
- **conntrack이 연결 단위로 기억하고, 그 비용이 한계다** — DNAT 규칙은 연결의 첫 패킷에만 적용되고, 같은 흐름의 나머지 패킷과 응답 방향은 conntrack 테이블이 처리한다. 그래서 확률 분배도 "연결 단위"이고, 테이블이 가득 차면 새 연결이 조용히 드롭된다. NAT 자체가 conntrack이라는 추가 단계이고, 임시 포트 고갈이라는 별개의 벽이 같은 증상을 낸다.
- **규칙은 순서대로 읽히고, 백엔드는 둘이다** — iptables 규칙은 위에서부터 선형 탐색이라 규칙이 폭증하면 느려진다. 요즘 `iptables` 명령은 대개 nftables 위의 호환 레이어(`iptables-nft`)이고, 같은 시스템에 legacy와 nft가 섞이면 서로의 규칙을 못 본다.

본문: [5장. netfilter·iptables·NAT·conntrack](../1부-리눅스-네트워크-기초/05-netfilter-iptables-NAT-conntrack.md)

### 6장. 오버레이·VXLAN·MTU

> 브리지는 한 호스트 안의 L2일 뿐이라 오버레이(VXLAN: VNI·UDP 4789)가 L3 위에 원본 프레임을 감싸 가상 L2를 얹고, 그 대가로 약 50바이트 오버헤드가 생겨 Pod·컨테이너 MTU를 1450 안팎으로 낮춰야 한다.

- **브리지는 호스트를 못 넘는다** — 호스트 A의 `docker0`과 호스트 B의 `docker0`은 아무 조치 없이는 서로 다른 사설 대역에 속한 남남이다. 정적 라우트로 이을 수는 있어도 호스트 수와 재스케줄링이 늘수록 감당이 안 된다.
- **VXLAN = VNI + UDP 캡슐화 + VTEP** — 24비트 VNI가 논리 네트워크를 구분하고(약 1,600만 개), 원본 프레임 전체를 UDP 페이로드로 감싸 보내며(표준 목적지 포트 4789), 캡슐화·역캡슐화하는 끝점이 VTEP다. 물리 네트워크는 평범한 UDP 트래픽으로만 본다.
- **캡슐화의 대가는 MTU다** — 외부 IP·UDP·VXLAN 헤더로 50바이트 안팎이 붙는다. 물리 MTU 1500에서 Pod MTU도 1500이면 캡슐화 후 1550바이트가 되어 단편화되거나 드롭된다. 증상은 "ping·작은 요청 OK, 큰 전송 NG".
- **오버레이는 선택지 중 하나다** — 대안은 물리 네트워크에 Pod 대역 경로를 알려 주는 네이티브 라우팅(BGP 등)과 VPC IP를 직접 받는 네이티브 IP다. 오버레이는 어디서나 되지만 MTU 손실·CPU 비용·진단 난이도를 치른다.

### 7장. Docker 네트워크 모델

> Docker 네트워킹은 dockerd에 링크된 libnetwork가 담당하며 Sandbox·Endpoint·Network 세 객체(CNM)로 추상화하고, 모든 드라이버는 이 모델의 다른 구현이며 IPAM은 별도의 교체 가능한 축이다.

- **libnetwork는 네트워킹을 dockerd 코어에서 뽑아낸 플러그형 라이브러리다** — 별도 데몬이 아니라 dockerd 프로세스에 링크되어 동작하고, 정책·모델은 libnetwork가, 실제 패킷 처리는 드라이버가 맡는다.
- **CNM은 Sandbox·Endpoint·Network 세 객체다** — Sandbox 1개는 여러 Network에 붙을 수 있고(Endpoint가 그만큼 생김), Endpoint는 정확히 하나의 Network·하나의 Sandbox에만 속한다.
- **드라이버는 갈아 끼우는 부품이고 IPAM은 독립된 축이다** — `bridge`·`overlay`·`macvlan`·`ipvlan`·`host`·`none` 모두 같은 CNM을 구현한다. 연결 방식(드라이버)과 주소 할당(IPAM)은 서로 독립적으로 교체된다.
- **`docker network` 명령은 CNM 오퍼레이션이다** — create=Network 생성, connect=Endpoint 생성+join, disconnect=leave+삭제. Endpoint 생성이 컨테이너 생명주기와 독립이라 실행 중에도 네트워크를 붙이고 뗄 수 있다. CNI(쿠버네티스)는 ADD/DEL 두 훅이 핵심인 훨씬 단순한 별개의 모델이다.

### 8장. 브리지 네트워크와 포트 게시

> 컨테이너는 veth pair로 호스트 브리지에 꽂혀 같은 브리지 안에서는 L2 스위칭(NAT 없음)으로, 밖으로는 라우팅 + MASQUERADE로 통신하고, 밖에서 들어오는 `-p` 트래픽은 PREROUTING의 DNAT로 라우팅 결정 전에 목적지가 바뀌어 컨테이너에 도착하며(응답은 conntrack이 되돌림), 게시된 포트에는 호스트 방화벽보다 Docker 규칙이 먼저 적용된다.

- **사용자 정의 브리지는 DNS와 격리의 단위다** — 기본 브리지(`docker0`)는 자동 DNS가 없는 평평한 한 공간이고, 사용자 정의 브리지는 네트워크마다 내장 DNS와 격리 도메인을 갖는다. 그 네트워크에 줄 대역은 IPAM이 풀에서 할당하며 풀은 `daemon.json`의 `default-address-pools`로 정한다.
- **veth는 CNM의 Endpoint, 안은 스위칭·밖은 NAT** — veth 한 쌍의 컨테이너 쪽 끝이 Endpoint이고 호스트 쪽 끝이 브리지에 꽂힌다. 같은 브리지 안은 FDB 기반 L2 스위칭, 밖으로는 게이트웨이 → IP 포워딩 → MASQUERADE다. (veth·브리지·라우팅 자체는 4장)
- **`-p`는 커널 DNAT와 사용자 공간 `docker-proxy`의 이중 구조다** — 기본 경로는 PREROUTING의 DNAT(규칙 읽기는 5장)이고, `docker-proxy`는 포트마다 뜨는 보완 프로세스다. 경계 사례(hairpin, 루프백 접근, 바인딩 주소)와 `userland-proxy: false`의 영향이 이 장의 심화 지점이다.
- **게시된 포트에서는 Docker 규칙이 호스트 방화벽보다 먼저다** — Engine 28부터 미게시 포트 인바운드는 기본 차단되지만, 게시 포트의 우선순위는 netfilter 체인 삽입 순서의 문제다(5장 1.3절, 11장).

### 9장. Docker DNS와 서비스 디스커버리

> 사용자 정의 네트워크의 컨테이너는 `nameserver 127.0.0.11`을 갖고, 그 주소는 dockerd(libnetwork)의 내장 리졸버가 **네트워크 단위** 이름 장부로 응답하며(없는 이름은 호스트의 업스트림 DNS로 포워딩), 기본 브리지에는 이 서버가 없다.

- **127.0.0.11은 컨테이너 안의 프로세스가 아니라 dockerd다** — 컨테이너 네임스페이스 *안*의 DNAT 규칙이 `127.0.0.11:53` 질의를 가로채 dockerd 내부의 리졸버로 넘기고, 리졸버는 드라이버가 연결/해제 때마다 갱신하는 장부에서 컨테이너 이름·`--network-alias`·Compose 서비스 이름을 조회한다. 모르는 이름(외부 도메인)은 업스트림 서버에 순서대로 포워딩한다.
- **해석 범위는 네트워크 단위다** — 장부가 네트워크별로 분리되어 있고(Endpoint는 정확히 하나의 Network에 속한다), 기본 브리지(`docker0`)는 아예 대상이 아니다. 장애 진단의 첫 질문은 늘 "같은 네트워크인가?"이고, 해결은 `docker network connect`로 상대 장부에 등재시키는 것이다.
- **DNS 옵션은 파일에 한 번 박히는 정적 설정이고, `search`·`ndots`는 질의 횟수를 바꾼다** — `--dns`, `--dns-search`, `--dns-option`, `--add-host`는 `/etc/resolv.conf`·`/etc/hosts`에 컨테이너 생성 시점에 기록된다. 점 개수가 `ndots`보다 적은 이름은 `search` 접미사 확장이 절대 이름보다 먼저다. 바꾸려면 컨테이너를 재생성한다.
- **Swarm의 서비스 이름은 VIP 또는 DNSRR로 풀린다** — 기본 VIP는 서비스 이름 하나가 고정 가상 IP 하나로 풀리고 부하 분산은 커널 IPVS가, DNSRR은 살아 있는 모든 태스크 IP를 돌려주고 분산은 클라이언트가 한다.

### 10장. macvlan·ipvlan·host·none·오버레이

> 브리지·오버레이는 격리된 netns에서 NAT를 거치지만 macvlan/ipvlan은 NAT 없이 물리망에 직접 붙고, host는 netns 분리를 포기하며, none은 lo만 남기고, 오버레이는 VXLAN으로 멀티호스트 가상 L2를 얹는다.

- **macvlan/ipvlan은 NAT를 우회해 물리망에 직접 붙는다** — macvlan은 부모 인터페이스 위에 컨테이너마다 고유 MAC의 서브인터페이스를, ipvlan은 부모의 MAC을 공유하고 IP로 분배한다. 둘 다 호스트의 IP 스택(라우팅, iptables/nftables)을 거치지 않는다. MAC 개수를 제한하는 스위치·클라우드 NIC에서는 macvlan이 막히고 ipvlan이 대안이다.
- **macvlan/ipvlan 컨테이너는 같은 호스트와 직접 통신할 수 없다** — 커널 구조상의 제약이며, 호스트에 같은 부모를 쓰는 서브인터페이스(`mv-shim`)를 하나 더 만들어 우회한다.
- **host와 none은 netns의 양 극단이다** — host는 `CLONE_NEWNET`을 쓰지 않아 호스트의 인터페이스·라우팅·포트를 그대로 공유한다(NAT 없음, 포트 충돌, 격리 약화). none은 독립 netns에 `lo`만 있다.
- **오버레이는 L3 위에 가상 L2를 얹는다** — Swarm의 오버레이는 컨트롤 플레인(gossip)과 데이터 플레인(VXLAN)이 분리되어 있고, ingress 라우팅 메시는 IPVS로 모든 노드에서 게시 포트를 받는다. 2026년 현재 Swarm은 deprecated가 아니지만 nftables 백엔드와는 함께 쓸 수 없다.

### 11장. Docker 방화벽 — iptables에서 nftables로

> Docker는 오랫동안 iptables(대부분 `iptables-nft` 호환 레이어) 체인을 호스트 표준 체인에 끼워 넣는 방식으로 방화벽을 구성했고, 그 공유 구조가 낳은 보안 허점을 Engine 28이 "게시하지 않은 포트 인바운드 기본 차단"으로 막았으며, Engine 29는 전용 테이블(`docker-bridges`)로 규칙을 분리하는 **실험적** 네이티브 nftables 백엔드를 도입했다.

- **iptables의 구조적 한계와 호환 레이어** — 선형 규칙 순회, IPv4/IPv6/브리지/ARP 도구 파편화. 현대 배포판의 `iptables`는 대개 nftables 위의 호환 바이너리 `iptables-nft`이고, `iptables-legacy`와 섞이면 서로의 규칙을 못 본다.
- **Engine 28.0.0 — 게시하지 않은 포트를 막다** — Docker가 관대한 기본 정책(ACCEPT)에 기대고 `FORWARD`에 자기 규칙을 앞쪽에 끼워 넣던 구조 때문에, 게시하지 않은 포트도 컨테이너 IP로 직접 라우팅되거나 `ufw` 규칙을 우회했다. 28.0.0부터 `DOCKER` 체인에서 기본 차단한다(Linux 전용).
- **Engine 29.0.0 — 실험적 네이티브 nftables 백엔드** — `--firewall-backend=nftables`. Docker 전용 테이블(`ip docker-bridges`, `ip6 docker-bridges`)로 네임스페이스를 분리한다. `DOCKER-USER`는 그대로 존재하지 않고 별도 테이블 + 우선순위로 대체된다.
- **제약을 알고 쓴다** — 실험적(구성·동작·구현이 바뀔 수 있음), Swarm 모드에서는 활성화 불가, macvlan/ipvlan은 이 전환과 무관(영향은 브리지 네트워크의 포트 게시 경로에 국한).

### 12장. IPv6 듀얼스택과 Rootless 네트워킹

> Docker의 IPv6는 opt-in이고 방화벽 규칙은 IPv4와 별도로 확인해야 하며, Rootless Docker는 veth·브리지를 못 만지므로 RootlessKit이 TAP 디바이스로 패킷을 유저스페이스 네트워크 스택에 넘겨 대신 통신시킨다.

- **IPv6는 켜야 쓴다** — 새로 설치해도 IPv4 전용이다. 데몬 전체(`daemon.json`의 `ipv6: true` + `fixed-cidr-v6`)나 네트워크 단위(`docker network create --ipv6 --subnet ...`)로 활성화해 dual-stack을 만든다.
- **dual-stack은 ARP 대신 NDP, 방화벽은 IPv4와 별도** — 컨테이너는 두 주소를 함께 받고, 이웃 탐색은 ICMPv6 기반 NDP가 맡으며, 내부망에는 흔히 ULA(`fd00::/8`)를 쓴다. nftables 전환은 문법 통일일 뿐 IPv4/IPv6 정책을 자동 통합하지 않는다.
- **Rootless는 "커널 권한 없이" 네트워크를 만든다** — dockerd를 user namespace 안에서 일반 사용자로 실행한다. 비루트는 veth를 다른 netns로 옮기거나 브리지·라우팅·방화벽을 조작할 수 없어, RootlessKit이 자식 netns에 TAP 디바이스를 만들고 유저스페이스 스택이 비특권 소켓 API로 대신 통신한다.
- **백엔드와 제약** — 기본 백엔드가 Docker v29.5부터 slirp4netns(C)에서 gvisor-tap-vsock(Go)으로 바뀌었다(보안 이유). 1024 미만 포트, ICMP, macvlan/ipvlan에 제약이 있다.

### 13장. 쿠버네티스 네트워크 모델과 Pod 네트워크

> 쿠버네티스는 "모든 Pod는 고유 IP를 갖고 NAT 없이 서로 통신한다"는 규칙(IP-per-Pod)만 정하고, 그 규칙을 지키는 실제 배선은 CNI 플러그인이 하며, Pod 하나의 네트워크 네임스페이스는 pause 컨테이너가 소유해 그 안의 컨테이너들이 IP와 포트 공간을 함께 쓴다.

- **IP-per-Pod는 "포트를 전역 자원에서 해방"하는 계약이다** — 모든 Pod가 NAT 없이 서로·노드와 통신하고, 자기가 보는 자기 IP와 남이 보는 IP가 같다. 대가는 클러스터 규모의 평평한 네트워크를 누군가 만들어야 한다는 것이고, 그 일을 쿠버네티스가 아닌 CNI 플러그인에 위임한다.
- **Pod는 pause가 만든 네임스페이스에 컨테이너들이 `setns`로 합류하는 것이다** — "공유"의 실체는 `/proc/<pid>/ns/*`의 inode 번호가 같다는 것이고(net·ipc·uts 공유, mnt·pid 분리), pause는 PID 1로 좀비를 수거하며 CRI `RunPodSandbox` 안에서 만들어진다. 앱이 죽어도 IP가 유지된다. `hostNetwork: true` Pod만 예외다.
- **IP 대역은 셋(노드·Pod·Service)이고, "네트워크 문제"는 네 가지 문제의 합이다** — Pod 네트워크, 이름, Service 전달, 외부 진입은 담당 부품이 다르다. 이 책 3부는 이 지도를 한 층씩 연다.

### 14장. CNI 스펙과 IPAM

> CNI는 런타임이 플러그인 실행 파일을 환경변수와 stdin JSON으로 호출해 ADD/DEL/CHECK/VERSION을 수행하는 계약이고, /etc/cni/net.d/의 설정이 플러그인 체인을 정하며, Pod IP는 노드에 서브넷을 나누는 층과 그 안에서 Pod에 한 개씩 주는 층의 두 단계로 할당된다.

- **CNI는 실행 파일 호출 계약이다** — 동작은 `ADD`·`DEL`·`CHECK`·`VERSION` 넷이고, 입력은 환경변수와 stdin JSON, 출력은 stdout JSON이다. 호출하는 것은 kubelet이 아니라 컨테이너 런타임(libcni)이다.
- **설정은 사전순으로 하나만 채택되고, 그 안의 `plugins` 배열이 체인이다** — 주 플러그인 → (IPAM 위임) → portmap·bandwidth 같은 메타 플러그인 순으로 `prevResult`를 넘기며 호출된다.
- **IP 할당은 두 층이다** — 클러스터 전역 층(node-ipam-controller가 `Node.spec.podCIDR`을 배분)과 노드 로컬 층(host-local 같은 IPAM 플러그인이 Pod마다 IP 배분). 빈번한 작업을 API 서버 왕복 없이 노드에서 끝내는 설계다.

### 15장. CNI 플러그인과 패킷 경로

> 물리 네트워크는 Pod 대역을 모르므로 CNI 플러그인은 노드 간 패킷을 캡슐화(오버레이)하거나, 경로를 알리거나(네이티브 라우팅), VPC의 실제 IP를 주는(클라우드 네이티브 IP) 세 방식 중 하나로 운반하며, 오버레이는 캡슐화 헤더만큼 MTU가 줄어든다.

- **근본 문제는 "물리 네트워크가 Pod CIDR을 모른다"이고, 해법은 세 가지다** — 오버레이(어디서나 동작, MTU·CPU 비용), 네이티브 라우팅(오버헤드 없음, 물리 네트워크가 경로를 받아야 함), 클라우드 네이티브 IP(VPC IP 직접 사용, IP 고갈 위험).
- **패킷 경로는 "veth → 루트 netns 라우팅 → (VXLAN 캡슐화 또는 그대로) → 상대 노드 → veth"다** — 라우팅 테이블이 `dev vxlan.*`면 오버레이, `via <노드IP> dev eth0`이면 네이티브 라우팅이며, tcpdump로 캡슐화 유무가 바로 드러난다.
- **오버레이의 대가는 MTU다** — VXLAN 50바이트, IPIP 20바이트. Pod MTU를 그만큼 낮추지 않으면 ping은 되고 큰 전송만 실패한다.
- **플러그인은 이 스펙트럼 위의 선택이다** — Flannel(단순), Calico(BGP·성숙한 정책), Cilium(eBPF), Antrea(OVS), 클라우드 CNI(VPC IP).

### 16장. Service와 EndpointSlice

> Service는 "이 라벨의 Pod를 이 포트로 제공한다"는 의도와 변하지 않는 가상 IP(ClusterIP)를 정의하고, EndpointSlice 컨트롤러가 selector에 맞는 Pod의 현재 IP·포트·상태를 EndpointSlice로 기록하며, `ready: true`인 대상에게만 트래픽이 간다.

- **ClusterIP는 주소가 아니라 "약속"이고, Service 타입은 안쪽에서 바깥으로 한 겹씩 감싼다** — `LoadBalancer ⊃ NodePort ⊃ ClusterIP`. ExternalName은 DNS CNAME일 뿐이고, 헤드리스(`clusterIP: None`)는 가상 IP를 없앤다.
- **EndpointSlice는 "지금 이 주소들이 대상"이라는 구체 목록이다** — 약 100개 단위로 샤딩해 바뀐 슬라이스만 전송하며, `conditions`(ready·serving·terminating)가 트래픽 대상 여부를 정한다.
- **서비스 디스커버리는 DNS가 정답이고, 환경변수에는 순서 의존 함정이 있다** — 환경변수는 Pod 시작 시점의 스냅샷이다. 헤드리스는 DNS가 Pod IP 목록을 직접 돌려줘 클라이언트가 고르게 한다.
- **트래픽 정책·세션 어피니티·드레이닝이 "어디로, 어떻게 끊김 없이"를 정한다** — `Cluster`/`Local`, `sessionAffinity: ClientIP`, 종료 중 엔드포인트의 `ready=false` + `terminating=true`.

### 17장. kube-proxy 데이터플레인

> kube-proxy는 Service/EndpointSlice를 watch해 노드 커널의 규칙(iptables·IPVS·nftables)을 다시 써 주는 컨트롤러일 뿐이고, 패킷 처리(DNAT와 conntrack 되돌림)는 커널이 하며, 모드에 따라 규칙 조회가 선형 O(n)(iptables)이거나 해시 O(1)(IPVS, nftables 맵)이다.

- **kube-proxy는 규칙의 작성자일 뿐 데이터 경로에 없다** — 패킷은 `PREROUTING`/`OUTPUT` 훅에서 netfilter 규칙을 만나 DNAT되고, 그 변환 정보를 conntrack이 기억한다. DNAT는 연결의 첫 패킷에만 적용되고 응답·후속 패킷은 conntrack이 역변환하므로, kube-proxy가 죽으면 새 변경이 반영되지 않을 뿐 기존 연결은 그대로다. `docker-proxy`와 달리 패킷을 받아 넘기는 중계 프로세스가 아니다.
- **iptables 모드는 체인 사슬이다** — `KUBE-SERVICES → KUBE-SVC-* → KUBE-SEP-*`에서 i번째 엔드포인트에 `1/(N−i+1)` 확률을 걸어 균등 분배하고, 마지막에 DNAT한다. 갱신은 증분이 아니라 `iptables-restore`로 전체 교체한다.
- **모드는 조회 구조의 선택이다** — iptables(선형 O(n)), IPVS(`kube-ipvs0` + 해시 O(1), 하지만 공식 폐기 경로), nftables(집합/맵, GA), eBPF(Cilium은 netfilter 자체를 우회).

본문: [17장. kube-proxy 데이터플레인](../3부-쿠버네티스-네트워크/17-kube-proxy-데이터플레인.md)

### 18장. DNS와 서비스 디스커버리

> 클러스터 DNS는 CoreDNS(플러그인 체인 + `kubernetes` 플러그인)가 Service/EndpointSlice를 watch해 `<service>.<namespace>.svc.cluster.local` 레코드로 답해 주고, Pod의 `/etc/resolv.conf`(search 목록 + `ndots:5`)가 짧은 이름을 그 형태로 확장하며, 그 DNS 트래픽 자체도 일반 Service 경로를 탄다.

- **CoreDNS = 플러그인 체인이자 평범한 워크로드** — `kubernetes` 플러그인이 API 서버를 watch해 메모리에 레코드를 유지하고, 모르는 이름은 `forward`가 노드의 DNS로 넘긴다. CoreDNS 앞의 `kube-dns` Service는 ClusterIP이며 이 주소가 모든 Pod의 `nameserver`다.
- **search/ndots는 리졸버 규칙이고, 그 비용은 CoreDNS 쪽에 흔적으로 남는다** — 짧은 이름 확장은 Pod 안의 리졸버가 `resolv.conf`만 보고 하므로 후보마다 실제 쿼리가 나가고, `NXDOMAIN`이 확정된 쿼리도 CoreDNS까지 간다. 그래서 tcpdump·CoreDNS `log`·`coredns_dns_requests_total`로 직접 세고, 완화책은 `ndots`를 낮출수록 내부 짧은 이름이 깨지는 경계 조건과 함께 고른다. 이름 규칙(FQDN, 레코드 종류)은 입문 책과 같고 SRV·`hostname`/`subdomain`만 더한다.
- **캐시, NodeLocal DNSCache, 진단 순서** — 대량 UDP 쿼리가 만드는 conntrack 경쟁 조건(5초 지연/SERVFAIL)을 노드마다 놓은 캐시로 피한다. DNS 장애는 CoreDNS Pod → Service/EndpointSlice → resolv.conf → ClusterIP 직접 질의 → 간헐성 순으로 좁힌다.

### 19장. Ingress와 Gateway API

> Ingress(또는 Gateway API 리소스)는 라우팅 규칙을 선언한 **데이터**일 뿐이고, 컨트롤러가 그것을 watch해 자기 리버스 프록시 설정으로 바꿔 L7(호스트·경로) 요청을 Pod IP로 직접 프록시하며, Gateway API는 이 선언을 GatewayClass/Gateway/Route 세 역할로 쪼개 애노테이션 난립을 표준 필드로 대체한다.

- **컨트롤러는 조정 루프이고, 데이터 경로에 있는지는 구현마다 다르다** — ingress-nginx류는 Ingress/Service/EndpointSlice/Secret을 watch해 `nginx.conf` 같은 프록시 설정을 만들고 리로드(엔드포인트 변경은 동적 갱신)하며, 자기 프록시가 요청을 받아 ClusterIP를 거치지 않고 Pod IP로 직접 프록시한다. AWS Load Balancer Controller 같은 클라우드 네이티브 컨트롤러는 ALB 설정만 유지하고 요청 경로에는 없다.
- **라우팅 규칙과 TLS 종료** — 호스트/경로 기반 라우팅, `pathType`, TLS는 컨트롤러에서 종료(컨트롤러 → Pod는 평문), cert-manager로 발급·갱신 자동화.
- **Gateway API: 역할을 세 리소스로 분리** — GatewayClass(인프라 제공자) → Gateway(클러스터 운영자, 리스너·TLS·`allowedRoutes`) → HTTPRoute 등(앱 팀). 헤더 매칭·가중치 분할·URL 재작성이 애노테이션이 아닌 타입 검증되는 표준 필드가 된다.

본문: [19장. Ingress와 Gateway API](../3부-쿠버네티스-네트워크/19-Ingress와-Gateway-API.md)

### 20장. 서비스 메시 데이터플레인

> 서비스 메시는 서비스 간 트래픽을 프록시 계층(사이드카 또는 ztunnel/waypoint)이 가로채 mTLS·재시도·트래픽 분할·관측을 앱 수정 없이 제공하는 구조이며, 그 대가는 리소스·지연·복잡도다.

- **프록시가 앱 옆에서 트래픽을 강제로 가로챈다** — 사이드카는 뮤테이팅 어드미션 웹훅이 Pod 생성 시 주입하고, init 컨테이너가 심은 iptables 규칙으로 모든 인/아웃바운드가 프록시를 거친다. 앱은 모른다.
- **프록시 계층이 대신 해 주는 일** — 사이드카 사이 구간의 mTLS(워크로드 신원은 단기 인증서), 재시도·타임아웃·서킷 브레이커·카나리 가중치, 균일한 관측 데이터.
- **사이드카 vs 앰비언트: 격리 대 효율, 그리고 도입 판단** — 앰비언트는 노드당 공유 ztunnel(L4/mTLS)과 선택적 waypoint(L7)로 Pod당 오버헤드를 없애는 대신 격리를 노드 단위로 완화한다. 메시는 서비스가 많고 규제·일관된 트래픽 제어가 필요할 때 정당화된다.

본문: [20장. 서비스 메시 데이터플레인](../3부-쿠버네티스-네트워크/20-서비스-메시-데이터플레인.md)

### 21장. NetworkPolicy와 네트워크 보안

> 격리는 정책이 선택한 Pod의 `policyTypes` 방향별로 일어나고 한 연결은 출발 Pod의 egress와 도착 Pod의 ingress 양쪽이 모두 허용해야 통과하며, 이 판정의 시행은 kube-proxy가 아니라 CNI가 하므로 CNI가 지원해야만 효과가 있고, 표준 NetworkPolicy가 못 하는 일(deny·우선순위·클러스터 전역·L7·FQDN)은 CNI 확장이나 AdminNetworkPolicy가 맡는다.

- **격리는 Pod·방향 단위이고, 연결은 양쪽 판정이다** — 정책이 선택한 Pod의 `policyTypes`에 쓴 방향만 격리되고, 출발 Pod의 egress와 도착 Pod의 ingress가 모두 허용해야 한다. 허용은 합집합으로 누적되며 한 정책이 다른 정책의 허용을 부정하지 못한다.
- **셀렉터 조합의 의미는 구조가 정한다** — 별도 항목은 OR, 한 항목 안은 AND. 빈 `podSelector`는 같은 네임스페이스 전체, `ipBlock`은 CIDR 기준이라 NAT와 실제 경로의 영향을 받는다.
- **시행자는 CNI이고, 표준에는 한계가 있다** — Calico/Cilium/Antrea는 시행하고 Flannel·kindnet은 미지원이다. iptables 기반은 규칙 수에 비례해 순회 비용이 늘고 eBPF 기반은 맵 룩업이다. 표준의 한계 4가지는 CNI별 확장으로 메운다.
- **제로 트러스트 설계는 "기본 거부 → 최소 허용 → DNS 확인 → 자동 배포 → 관리자 가드레일"이다** — 클러스터 전역 규칙은 AdminNetworkPolicy(아직 v1alpha1)가 맡는다.

### 22장. eBPF 데이터플레인과 Cilium

> eBPF는 verifier가 검증한 프로그램을 커널 훅에서 실행하는 기술이고, Cilium은 cilium-agent가 BPF 맵을 갱신하고 커널 프로그램이 맵을 룩업해 Service 로드밸런싱과 NetworkPolicy를 처리하여 iptables 체인 순회와 패킷마다의 DNAT·conntrack을 대체한다.

- **eBPF = 검증된 프로그램 + 훅 + 맵** — verifier(검증)·샌드박스·JIT. XDP는 NIC 직후 가장 이른 훅(빨리 버리기), TC는 `sk_buff`가 있는 늦은 훅(더 많은 컨텍스트). 상태는 BPF 맵으로만 주고받는다.
- **Cilium: 에이전트(유저스페이스)가 맵을 쓰고, 커널 프로그램이 맵을 읽는다** — 에이전트가 죽어도 이미 적재된 프로그램과 맵이 계속 트래픽을 처리한다. 체인 순회 대신 해시 맵 룩업이다.
- **소켓 레벨 로드밸런싱과 같은 경로의 정책** — `connect()` 시점에 목적지를 Pod IP로 써 넣어 패킷 단위 DNAT/conntrack이 필요 없고, NetworkPolicy도 같은 TC 훅 프로그램·맵을 쓴다. 단 verifier의 복잡도 예산이라는 실제 한계가 있다.

### 23장. 네트워크 장애 진단 — 계층별 플로차트

> 네트워크 장애는 DNS → 노드 간 연결 → Service → NetworkPolicy → 노드 자원 순으로, 더 흔하고 상위인 계층부터 하나씩 확실히 배제하며 내려가고, 증상(큰 전송만 실패, 정확히 5초 지연, 특정 정책 직후 전부 실패 등)이 어느 계층을 의심할지 알려 준다.

- **계층별 배제 순서** — "Pod A가 B에 안 닿는다"는 여러 질문의 뭉치다. 이름(DNS) → Pod 간 경로(CNI) → Service(EndpointSlice·kube-proxy) → NetworkPolicy → 노드 자원 고갈 순으로, 상위 계층을 먼저 배제한다. Pod IP·ClusterIP·DNS 이름으로 차례로 호출해 보면 경계가 갈린다.
- **증상은 계층을 가리킨다** — 큰 전송만 실패하면 MTU, 정확히 5초 지연이면 conntrack 경쟁(DNS), 정책 적용 직후 전부 실패하면 DNS 예외 누락, 부하 때만 간헐 실패하면 conntrack·임시 포트 고갈을 먼저 의심한다.
- **관찰 위치를 고른다** — 같은 문제도 Pod 네임스페이스 안, 호스트의 veth, 양쪽 노드, 흐름 단위(Hubble)에서 보이는 것이 다르다. 양쪽 노드에서 동시에 캡처하면 패킷이 사라지는 지점이 드러난다.
