# 9장. Docker DNS와 서비스 디스커버리

> **🎮 게임 서버 개발자에게** — 게임 서버가 DB·Redis·매치메이커에 붙을 때 설정 파일에 IP를 적거나, 기껏해야 사내 DNS 이름을 `getaddrinfo()`로 풀어 `connect()`하던 구조가 컨테이너 세계에서는 "컨테이너마다 `/etc/resolv.conf`에 `127.0.0.11`이 박혀 있고, 그 주소를 받아 주는 것이 호스트의 dockerd"로 바뀝니다. 결정적으로 다른 점은 이 DNS가 **네트워크 단위로 이름 장부를 따로 들고 있다**는 것입니다. 같은 `127.0.0.11`을 써도 다른 네트워크의 컨테이너는 모르고, 기본 브리지에 붙은 컨테이너는 아예 이 서버를 쓰지 않습니다. 이름 해석은 소켓 API가 아니라 **파일(`/etc/resolv.conf`, `/etc/hosts`)에 컨테이너 생성 시점에 한 번 기록된 설정**에서 출발한다는 점도 기억하세요.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - `redis:6379`처럼 이름으로 붙는 설정을 넣었는데 게임 서버 컨테이너가 이름 해석에 실패한다.
> - 컨테이너를 재시작해 IP가 바뀌었는데 JVM 기반 서비스가 계속 예전 IP로 접속하려 한다.
> - 컨테이너 안에서 호스트의 개발용 서버를 불러야 해서 `host.docker.internal` 같은 이름이 필요하다.

## 코어 — 이것만은 100%

> **한 문장:** 사용자 정의 네트워크의 컨테이너는 `nameserver 127.0.0.11`을 갖고, 그 주소는 dockerd(libnetwork)의 내장 리졸버가 **네트워크 단위** 이름 장부로 응답하며(없는 이름은 호스트의 업스트림 DNS로 포워딩), 기본 브리지에는 이 서버가 없다.

1. **127.0.0.11은 컨테이너 안의 프로세스가 아니라 dockerd다** — 컨테이너 네임스페이스 *안*의 DNAT 규칙이 `127.0.0.11:53` 질의를 가로채 dockerd 내부의 리졸버로 넘기고, 리졸버는 드라이버가 연결/해제 때마다 갱신하는 장부에서 컨테이너 이름·`--network-alias`·Compose 서비스 이름을 조회한다. 모르는 이름(외부 도메인)은 업스트림 서버에 순서대로 포워딩한다.
2. **해석 범위는 네트워크 단위다** — 장부가 네트워크별로 분리되어 있고(Endpoint는 정확히 하나의 Network에 속한다), 기본 브리지(`docker0`)는 아예 대상이 아니다. 장애 진단의 첫 질문은 늘 "같은 네트워크인가?"이고, 해결은 `docker network connect`로 상대 장부에 등재시키는 것이다.
3. **DNS 옵션은 파일에 한 번 박히는 정적 설정이고, `search`·`ndots`는 질의 횟수를 바꾼다** — `--dns`, `--dns-search`, `--dns-option`, `--add-host`는 `/etc/resolv.conf`·`/etc/hosts`에 컨테이너 생성 시점에 기록된다. 점 개수가 `ndots`보다 적은 이름은 `search` 접미사 확장이 절대 이름보다 먼저다. 바꾸려면 컨테이너를 재생성한다.
4. **Swarm의 서비스 이름은 VIP 또는 DNSRR로 풀린다** — 기본 VIP는 서비스 이름 하나가 고정 가상 IP 하나로 풀리고 부하 분산은 커널 IPVS가, DNSRR은 살아 있는 모든 태스크 IP를 돌려주고 분산은 클라이언트가 한다.

**이 장의 학습 목표**

- 컨테이너의 `/etc/resolv.conf`에 있는 `127.0.0.11`의 정체와 질의 처리 경로를 설명한다.
- 이름 장부가 네트워크별인 이유를 CNM의 Sandbox·Endpoint·Network 관계로 설명하고, `docker network connect`가 왜 해결책인지 말한다.
- `--dns`·`--dns-search`·`--dns-option`·`--add-host`가 어느 파일에 어떻게 반영되는지 안다.
- 점 개수·`ndots`·`search` 목록으로 질의 이름이 확장되는 순서를 손으로 따라가고, 완화책과 과도한 `ndots` 인하의 함정을 안다.
- Swarm 서비스 디스커버리의 VIP와 DNSRR 차이, DNSRR의 제약을 안다.
- DNS 장애를 4단계 순서(같은 네트워크 → 기본 브리지 → ndots/검색 도메인 → 앱 캐싱)로 진단한다.

## 코어 1. 127.0.0.11은 컨테이너 안의 프로세스가 아니라 dockerd다

### 1.1 내장 DNS 서버의 정체

**한 줄 요약:** `127.0.0.11`은 컨테이너 네임스페이스 안에서 가로채지는 가상의 DNS 리스너이고, 실제 응답은 호스트의 dockerd(libnetwork) 내장 리졸버가 만든다.

> **입문 책에서 배운 것:** 사용자 정의 네트워크 컨테이너의 `/etc/resolv.conf`는 `nameserver 127.0.0.11`과 `options ndots:0`을 갖고, 그 주소의 정체는 컨테이너 안 프로세스가 아니라 dockerd의 내장 DNS다([입문 11장](../../Docker%20와%20Kubernetes로%20인프라%20구축할때%20알아야하는%20필수%20이론%20지식/2부-컨테이너와-Docker/11-Docker-네트워크.md) 코어 4). 여기서는 그 안쪽 구조만 본다.

원천이 설명하는 구조는 세 겹이다.

- **가로채기는 컨테이너 netns 안에서 일어난다.** dockerd는 컨테이너의 네트워크 네임스페이스 *내부*에 `127.0.0.11:53`(UDP/TCP) 질의를 가로채는 iptables/nftables DNAT 규칙을 심어 둔다. 규칙이 호스트 쪽이 아니라 각 컨테이너 안에 있다는 점은 nftables 백엔드에서도 같다([11장](11-Docker-방화벽-iptables에서-nftables로.md) 코어 3).
- **처리는 컨테이너별 네트워크 컨텍스트를 아는 리졸버가 한다.** dockerd(정확히는 libnetwork) 안의 내장 리졸버(embedded DNS server)가 맡는다.
- **장부는 드라이버가 갱신한다.** 응답의 근거는 그 네트워크에 속한 컨테이너들의 이름-IP 매핑 테이블이며, 각 네트워크 드라이버가 컨테이너 연결/해제 시점마다 갱신하는 내부 서비스 디스커버리 데이터베이스다.

```
 컨테이너 netns                                   호스트
┌──────────────────────────┐
│ 앱: getaddrinfo("api")   │
│   │ 질의                 │
│   ▼                      │
│ 127.0.0.11:53            │
│   │ (netns 안 DNAT 규칙)  │──────▶  dockerd (libnetwork) 내장 리졸버
└──────────────────────────┘             │ 같은 네트워크의 이름-IP 장부 조회
                                         │ 못 찾으면 → 업스트림 DNS로 포워딩
                                         ▲
                                         └ 드라이버가 연결/해제 때마다 장부 갱신
```

### 1.2 외부 도메인은 어떻게 포워딩되는가

**한 줄 요약:** 로컬 장부에서 못 찾은 이름은 실패시키지 않고 호스트의 업스트림 DNS에 **순서대로** 물어, 성공이나 NXDOMAIN을 받는 즉시 멈춘다.

조회 대상(컨테이너 이름·별칭·Compose 서비스 이름)은 입문 책에서 배웠다. 심화 포인트는 장부에 없는 이름의 처리 규칙이다.

- 업스트림 서버 목록은 기본적으로 호스트의 `/etc/resolv.conf`에 설정된 네임서버(또는 `--dns`로 명시한 서버)다.
- 사용자 정의 네트워크에서는 업스트림 서버들에 **순서대로** 질의해 성공 응답이나 NXDOMAIN을 받는 즉시 중단한다. 원천은 이것이 여러 서버에 무작위로 흩어 쿼리하던 예전 방식보다 예측 가능하다고 설명한다.
- 그래서 컨테이너는 내부 이름과 외부 도메인을 구분하지 않고 `127.0.0.11` 하나에만 물으면 된다.

## 코어 2. 해석 범위는 네트워크 단위다 — 기본 브리지와 `--link`

### 2.1 기본 브리지: `resolv.conf`가 복사본이다

**한 줄 요약:** 기본 브리지는 서비스 디스커버리 개념이 없던 초창기의 기본값이라 내장 DNS 대상이 아니다 — 그래서 `127.0.0.11` 대신 호스트의 네임서버 설정이 그대로 복사되어 있다.

> **입문 책에서 배운 것:** 기본 브리지(`docker0`)에는 이름 기반 자동 DNS가 없고, 옛 `--link`는 대상 IP를 `/etc/hosts`에 정적으로 한 줄 써 주던 레거시이므로 새 구성에서는 쓰지 않는다([입문 11장](../../Docker%20와%20Kubernetes로%20인프라%20구축할때%20알아야하는%20필수%20이론%20지식/2부-컨테이너와-Docker/11-Docker-네트워크.md) 4.2). 사용자 정의 브리지와 기본 브리지의 차이는 [8장](08-브리지-네트워크와-포트-게시.md)에서도 본다.

진단에서 쓸모 있는 관찰 포인트는 파일에 남은 흔적이다. 기본 브리지 컨테이너의 `/etc/resolv.conf`에는 `127.0.0.11`이 없고 호스트의 네임서버 설정이 복사되어 있다. 원천은 이것이 설계상 누락이 아니라 역사적 이유(설계 시점에 지금 같은 서비스 디스커버리 개념이 없었다)라고 설명한다. `--link`의 한계(IP 변경을 따라가지 못하는 정적 한 줄, 동적 서비스 그룹 표현 불가)는 사용자 정의 네트워크의 "연결/해제 때마다 갱신되는 장부"가 해결했다.

### 2.2 범위는 "네트워크별 장부" — CNM 객체로 읽기

**한 줄 요약:** 서로 다른 네트워크의 컨테이너는 둘 다 `127.0.0.11`을 써도 서로를 찾지 못한다 — DNS 서버가 따로 있는 것이 아니라 같은 dockerd가 네트워크별로 분리해 관리하는 조회 테이블이기 때문이다.

원천은 "별도의 DNS 서버 인스턴스가 아니라, 같은 dockerd가 네트워크별로 분리해서 관리하는 조회 테이블"이라고 못 박는다. 이 구조는 [7장](07-Docker-네트워크-모델.md)의 CNM 객체 관계와 겹쳐 보면 선명하다. `/etc/resolv.conf`는 Sandbox(컨테이너 하나의 네트워크 스택 전체)에 속하는 설정이고, Endpoint는 정확히 하나의 Network에만 속하며 컨테이너가 네트워크 둘에 붙으면 Endpoint가 둘(`eth0`, `eth1`)이 된다.

```
Sandbox (컨테이너 netns)  ── resolv.conf: nameserver 127.0.0.11
   ├─ Endpoint A1 (eth0) ── Network cnm-lab      ← 이 네트워크의 장부
   └─ Endpoint A2 (eth1) ── Network second-net   ← 다른 네트워크의 장부
```

> **[보충]** 위 그림은 CNM의 객체 관계(원천 11장)와 "네트워크별 조회 테이블"(원천 15장)이라는 두 서술을 겹쳐 그린 것이다. 두 네트워크에 동시에 붙은 컨테이너의 질의가 두 장부를 어떻게 합쳐 조회하는지는 원천에 서술이 없다.

해결 수단도 이 구조에서 나온다. 실행 중인 컨테이너에 `docker network connect <net> <컨테이너>`를 하면 재시작 없이 Endpoint(`eth1`)가 추가된다(원천 11장 실습). 드라이버가 연결 시점에 장부를 갱신한다는 1.1과 합치면 "상대 네트워크 장부에도 등재시키는 것"으로 읽힌다 — 두 서술을 잇는 [보충] 추론이다.

### 2.3 DNS 문제 진단 4단계 — 무엇을 보고 판정하는가

**한 줄 요약:** 같은 네트워크인가 → 기본 브리지인가 → `ndots`/검색 도메인 → 앱의 DNS 캐싱, 순서는 입문 책과 같고 여기서는 각 단계의 **관찰 대상**을 붙인다.

> **입문 책에서 배운 것:** 진단 4단계의 순서와 이유는 [입문 11장](../../Docker%20와%20Kubernetes로%20인프라%20구축할때%20알아야하는%20필수%20이론%20지식/2부-컨테이너와-Docker/11-Docker-네트워크.md) 4.3의 체크리스트와 같다.

| 순서 | 관찰 | 판정 |
|---|---|---|
| 1 | `docker network inspect <네트워크>`의 `Containers` 섹션(Endpoint 목록)에 두 컨테이너가 모두 있는가 | 한쪽이 없으면 다른 장부다. `docker network connect`로 등재(2.2) |
| 2 | 컨테이너 안 `cat /etc/resolv.conf`의 `nameserver` | `127.0.0.11`이 아니라 호스트 네임서버 복사본이면 기본 브리지(2.1). `--network`를 빼먹은 경우가 흔하다 |
| 3 | 같은 파일의 `search`·`options` 줄 | 질의가 실제로 어떤 이름들로 확장되는지 3.2의 규칙으로 따져 본다. 사용자 정의 브리지 기본값은 `ndots:0` |
| 4 | 컨테이너 안 `nslookup`/`getent hosts`는 새 IP를 주는데 앱만 옛 IP를 쓰는가 | 일부 런타임(특히 JVM 계열)의 긴 DNS 캐싱이다. dockerd를 파지 않는다 |

> **[보충]** 쿠버네티스는 Service 이름으로 Pod에 접근하는 서비스 디스커버리를 클러스터 DNS가 맡는다. 개념은 비슷하지만 구현이 다르며, [18장](../3부-쿠버네티스-네트워크/18-DNS와-서비스-디스커버리.md)에서 다룬다. 진단 명령 모음은 [23장](../4부-진단/23-네트워크-장애-진단.md)에 있다. 1단계의 `docker network inspect` 확인법은 원천 11장 실습에서 가져왔다.

## 코어 3. DNS 옵션은 파일에 한 번 박히는 정적 설정이다

### 3.1 네 가지 런타임 옵션

**한 줄 요약:** `--dns`·`--dns-search`·`--dns-option`은 `/etc/resolv.conf`에, `--add-host`는 `/etc/hosts`에 컨테이너 생성 시점에 기록된다.

| 옵션 | 반영되는 곳 | 의미 |
|---|---|---|
| `--dns` | `/etc/resolv.conf`의 `nameserver` | 컨테이너가 쓸 네임서버를 명시. 사용자 정의 네트워크에서는 이미 `127.0.0.11`이 들어 있으므로, 추가로 지정하면 내장 DNS가 외부 이름을 포워딩할 때 참조하는 업스트림 목록에 영향을 주는 방식으로 동작 |
| `--dns-search` | `/etc/resolv.conf`의 `search` | 검색 도메인. 짧은 이름(FQDN이 아닌 이름)에 이 도메인을 자동으로 덧붙여 조회 |
| `--dns-option` | `/etc/resolv.conf`의 `options` | `ndots`, `timeout`, `attempts` 같은 resolver 세부 옵션. 사용자 정의 네트워크의 기본값은 `ndots:0` |
| `--add-host` | `/etc/hosts` | `host:ip` 정적 매핑. 옛 `--link`가 하던 일을 훨씬 명시적·예측 가능하게 대신하며, DNS 질의 없이 파일 조회만으로 즉시 해석된다 |

`--add-host`의 IP 자리에 특수값 `host-gateway`를 쓰면 호스트 자신을 가리키는 내부 IP로 자동 치환된다. 컨테이너 안에서 호스트로 접근해야 하는 개발 환경 등에서 쓰인다.

```bash
docker run --rm \
  --dns=1.1.1.1 \
  --dns-search=example.internal \
  --add-host=host.docker.internal:host-gateway \
  alpine:latest sh -c "cat /etc/resolv.conf; echo ---; cat /etc/hosts"
```

### 3.2 검색 도메인과 `ndots` — 이름이 확장되는 순서

**한 줄 요약:** 점(`.`) 개수가 `ndots`보다 적은 이름은 절대 이름으로 묻기 *전에* `search` 목록의 접미사를 하나씩 붙여 먼저 시도한다 — `ndots`와 `--dns-search`는 질의의 **횟수와 순서**를 바꾸는 값이다.

> **입문 책에서 배운 것:** `getaddrinfo()`는 `/etc/hosts`와 `resolv.conf` 네임서버(UDP)를 거치는 동기 블로킹 호출이고([입문 4장](../../Docker%20와%20Kubernetes로%20인프라%20구축할때%20알아야하는%20필수%20이론%20지식/1부-리눅스-기초/04-메모리-파일시스템-네트워크-기초.md) 3.5)이며 `ndots:5` 문제가 컨테이너 DNS 지연의 흔한 원인으로 언급된다. 입문 11장 4.3은 진단 3단계로 `ndots`/검색 도메인 점검만 한다([입문 11장](../../Docker%20와%20Kubernetes로%20인프라%20구축할때%20알아야하는%20필수%20이론%20지식/2부-컨테이너와-Docker/11-Docker-네트워크.md) 4.3). 여기서는 짧은 이름이 여러 번 질의되는 규칙을 푼다.

규칙(리졸버 일반 규칙을 쿠버네티스 원천이 `search` 목록으로 설명한 것)은 이렇다. 아래는 쿠버네티스 Pod의 `resolv.conf`가 `ndots:5`와 다음 `search` 목록을 갖는 경우의 예다.

```
search default.svc.cluster.local svc.cluster.local cluster.local

쿼리: www.example.com   (점 2개, 여전히 ndots=5보다 작음)
① www.example.com.default.svc.cluster.local   ← 실패(존재하지 않음)
② www.example.com.svc.cluster.local           ← 실패
③ www.example.com.cluster.local               ← 실패
④ www.example.com                              ← 여기서야 성공
```

외부 도메인을 조회할 때마다 실패가 확정된 질의 3개를 먼저 보내는 셈이다. 같은 규칙이 Docker에도 적용된다. `--dns-search`가 `search` 줄을, `--dns-option`이 `ndots` 같은 `options` 줄을 채우고(3.1), 사용자 정의 네트워크의 기본값 `ndots:0`은 짧은 이름도 검색 도메인 없이 **우선 그대로** 조회하게 한다(원천 15장 15.6). 쿠버네티스에서 가져온 `ndots:5`를 그대로 옮기면 위 예와 같은 낭비와 예상 못한 외부 도메인 매칭이 생긴다(15.7).

완화책과 반대편 함정도 같은 규칙에서 나온다.

| 방법 | 효과 / 주의 |
|---|---|
| 끝에 점을 붙여 절대 이름으로 쓴다(`www.example.com.`) | `search` 목록을 건너뛰고 곧바로 조회 |
| 처음부터 완전한 FQDN을 설정에 쓴다 | `search` 목록이 필요 없어진다 |
| `ndots`를 낮춘다 | 너무 낮추면 내부 짧은 이름이 실패할 수 있다. 예: `ndots:1`이면 점이 1개 이상인 이름은 곧바로 절대 이름으로 취급되어 `search`를 거치지 않는다. 워크로드의 실제 조회 패턴(내부 짧은 이름 위주인지, 외부 FQDN 위주인지)을 먼저 파악한다 |

> **[보충]** 위 예의 `search` 목록과 `ndots:5`는 쿠버네티스 원천(Kubernetes_Internals_Network_Guide 16.2)의 것이고, Docker 원천에는 이 확장 순서를 보여 주는 예가 없다. Docker에서 같은 규칙이 적용된다는 연결은 15.6·15.7의 `search`·`ndots` 설명과 위 규칙을 이은 것이다. 쿠버네티스 쪽 상세(`dnsPolicy`, `dnsConfig`, 5초 지연)는 [18장](../3부-쿠버네티스-네트워크/18-DNS와-서비스-디스커버리.md)에서 본다.

### 3.3 "정적"의 의미

**한 줄 요약:** 이 옵션들은 생성 시점에 한 번 기록되므로, 실행 중 호스트의 DNS 설정이 바뀌어도 컨테이너 파일은 (일반적으로) 갱신되지 않아 재생성해야 반영된다.

원천은 일부 예외(dockerd가 특정 조건에서 관리하는 파일을 갱신하는 경우)가 있으나 일반적으로는 정적이라고 설명한다. 게임 서버 설정 파일을 서버 기동 시 한 번 읽는 것과 같다. 설정 파일을 고쳐도 떠 있는 프로세스는 모르듯, 파일을 고쳐도 떠 있는 컨테이너 설정은 바뀌지 않는다는 감각으로 기억하면 된다.

> **[보충]** 이 비유는 이해를 돕는 장치이며, 컨테이너 `/etc/resolv.conf`가 실제로 어떤 방식으로 만들어지는지에 대한 원천 설명은 위 문장이 전부다.

실습은 아래 순서로 진행한다(원천 15장 실습에서 가져온 명령이며, 이 책을 쓴 환경에서 실행해 검증한 것은 아니다).

```bash
docker network create dns-lab
docker run -d --name svc-a --network dns-lab alpine:latest sleep infinity
docker run --rm --network dns-lab alpine:latest cat /etc/resolv.conf     # nameserver 127.0.0.11
docker run --rm --network dns-lab alpine:latest sh -c "nslookup svc-a || getent hosts svc-a"
docker run --rm alpine:latest cat /etc/resolv.conf                       # 기본 브리지: 호스트 네임서버 설정
docker rm -f svc-a
docker network rm dns-lab
```

## 코어 4. Swarm의 서비스 이름은 VIP 또는 DNSRR로 풀린다

### 4.1 VIP 모드 — 이름 하나가 고정 IP 하나

**한 줄 요약:** `docker service create`의 기본값인 VIP 모드는 서비스에 고정 가상 IP를 하나 할당하고, 이름 질의에는 항상 그 VIP만 답하며 부하 분산은 커널 IPVS가 한다.

Swarm 모드에서 같은 역할의 태스크(컨테이너)가 여러 개 떠 있으면 "서비스 이름으로 조회했을 때 어느 태스크로 가는가"라는 문제가 생긴다. 서비스 디스커버리는 Swarm 오버레이가 gossip으로 전파한 멤버십·라우팅 정보([10장](10-macvlan-ipvlan-host-none-오버레이.md) 코어 4)를 바탕으로 클라이언트에 어떤 주소를 돌려줄지 정한다.

VIP 모드에서는 서비스 이름 질의에 항상 VIP 하나만 돌아온다. 실제로 어느 태스크로 가는지는 이 VIP를 대상으로 한 **IPVS(IP Virtual Server) 기반 로드밸런싱 규칙**이 커널 레벨에서 처리한다. 클라이언트는 IP 하나만 알면 되고, 태스크가 늘거나 줄어도 IP가 바뀌지 않으므로 애플리케이션이 캐시한 DNS 응답이 낡아 생기는 문제가 거의 없다.

### 4.2 DNSRR 모드 — 이름 하나가 태스크 IP 여러 개

**한 줄 요약:** DNSRR은 VIP 없이 질의 시점에 살아 있는 모든 태스크 IP 목록을 돌려주고 선택은 클라이언트에 맡기며, 라우팅 메시와는 함께 쓸 수 없다.

- 로드밸런싱 책임이 커널의 IPVS에서 클라이언트(또는 클라이언트의 DNS 캐싱 계층)로 넘어간다.
- `endpoint_mode: dnsrr`로 **명시적으로** 지정해야 활성화된다.
- 라우팅 메시(ingress 모드의 핵심 기능)와는 함께 쓸 수 없다. 라우팅 메시가 VIP를 전제로 노드로 들어온 트래픽을 태스크로 전달하는 방식이기 때문이다.

```yaml
# Compose 파일에서 DNSRR 모드를 지정하는 예
services:
  worker:
    image: myapp:latest
    deploy:
      endpoint_mode: dnsrr
```

| 구분 | VIP (기본) | DNSRR |
|---|---|---|
| 이름 질의 응답 | 고정 VIP 하나 | 질의 시점의 모든 태스크 IP 목록 |
| 부하 분산 주체 | 커널 IPVS | 클라이언트 / 클라이언트 DNS 캐싱 계층 |
| 라우팅 메시 | 함께 사용 가능 | 함께 사용 불가 |
| 캐시 낡음 문제 | 거의 없음(IP 불변) | 응답이 태스크 IP 목록이라 클라이언트 DNS 캐싱의 영향을 받는다(원천의 VIP 설명에서 유추한 [보충]) |
| 주 용도 | 대부분의 실무 | 클라이언트가 정교한 부하 분산 로직(특정 IP 우선 접속, 커넥션 풀링 전략 등)을 이미 갖춘 경우, 또는 UDP 기반처럼 IPVS의 연결 추적과 궁합이 맞지 않는 워크로드에서 선택적으로 고려 |

> **[보충]** 이 책은 Swarm 자체를 쓰는 것이 목적이 아니라 "서비스 이름 → 고정 가상 IP + 커널 부하 분산" 대 "이름 → 여러 IP"라는 두 패턴을 이해하는 데 목적이 있다. 쿠버네티스 Service(ClusterIP)와 헤드리스 Service가 같은 두 패턴에 대응한다는 점은 원천에 있는 설명이 아니므로 [16장](../3부-쿠버네티스-네트워크/16-Service와-EndpointSlice.md)에서 확인하자.

## 실무 적용

### 체크리스트

- [ ] 서버끼리 이름으로 통신하려면 **같은 사용자 정의 네트워크**에 붙인다(`--network`를 빼먹으면 기본 브리지에 붙어 내장 DNS를 못 쓴다).
- [ ] 컨테이너 안 `/etc/resolv.conf`가 `nameserver 127.0.0.11`인지(사용자 정의 네트워크), 호스트 네임서버 복사본인지(기본 브리지) 먼저 본다.
- [ ] 다른 네트워크의 컨테이너를 이름으로 불러야 하면 `docker network connect`로 등재한다(재시작 불필요). 정적 매핑이 필요하면 `--add-host`.
- [ ] 호스트로 접근해야 하는 개발 환경에는 `--add-host=host.docker.internal:host-gateway`를 쓴다.
- [ ] `ndots`를 바꿀 때는 의미를 알고 바꾼다(`ndots:5`는 짧은 이름 조회마다 검색 도메인을 덧붙여 여러 번 질의).
- [ ] DNS 옵션을 바꾸면 컨테이너를 재생성해야 반영된다는 것을 기억한다.
- [ ] 이름이 풀리는데 접속이 엉뚱하면 앱의 DNS 캐싱(JVM 등)을 의심한다.
- [ ] Swarm에서 DNSRR은 라우팅 메시와 함께 쓸 수 없다.

### 시나리오로 확인하기

1. **상황:** 쿠버네티스 설정을 옮기며 컨테이너에 `--dns-option ndots:5`와 `--dns-search`를 그대로 넣었다. 이후 외부 도메인(`api.example.com`) 호출이 느려졌고 내부 이름도 가끔 엉뚱한 곳으로 풀린다.
   **질문:** 왜 느려지고, 어떻게 줄이나?

   <details markdown="1"><summary>답 확인</summary>

   점이 2개인 `api.example.com`은 `ndots:5`보다 점이 적어 절대 이름으로 곧바로 묻지 않는다. `search` 목록의 접미사를 하나씩 붙인 이름을 먼저 시도하고, 모두 실패한 뒤에야 원래 이름이 질의된다. 실패가 확정된 질의가 앞에 붙어 지연이 늘고, 예상치 못한 이름 매칭이 생길 수 있다. 줄이는 법은 끝에 점을 붙인 절대 이름(`api.example.com.`) 사용, 완전한 FQDN 설정, 또는 사용자 정의 네트워크 기본값 `ndots:0`으로 되돌리는 것이다. 단 `ndots`를 낮추면 내부 짧은 이름 조회가 깨질 수 있어 조회 패턴을 먼저 본다. → 코어 3 (3.2)

   </details>

2. **상황:** `frontnet`의 `web`과 `backnet`의 `cache`가 모두 `nameserver 127.0.0.11`을 갖는데 `web`이 `cache`를 이름으로 못 찾는다. `cache`를 재시작하지 않고 풀고 싶다.
   **질문:** 의심 부품과 해결은?

   <details markdown="1"><summary>답 확인</summary>

   서로 다른 네트워크라서 장부가 다르다(진단 1단계: `docker network inspect`의 `Containers` 섹션에 둘이 함께 있는지). `docker network connect frontnet cache`로 `cache`를 `frontnet`에도 연결하면 재시작 없이 Endpoint(`eth1`)가 추가된다. 드라이버가 연결 시점에 장부를 갱신하므로 `web`이 그 장부에서 `cache`를 찾게 된다고 읽는 것이 이 책의 해석이다(원천은 연결·장부 갱신을 각각 서술하며, 이 조합의 결과를 직접 보여 주지는 않는다). → 코어 2 (2.2, 2.3)

   </details>

### 2. 인출 질문

1. `127.0.0.11`에 DNS 서버 프로세스가 있는가? 질의는 어떻게 처리되는가?

   <details markdown="1"><summary>답 확인</summary>

   없다. dockerd가 컨테이너 netns 안에 심은 DNAT 규칙이 `127.0.0.11:53` 질의를 가로채고, 호스트의 dockerd(libnetwork) 내장 리졸버가 그 네트워크의 장부(드라이버가 연결/해제 때마다 갱신)를 조회해 응답한다. → 코어 1 (1.1)

   </details>

2. 컨테이너가 외부 도메인 `api.example.com`을 조회하면 무슨 일이 일어나는가?

   <details markdown="1"><summary>답 확인</summary>

   내장 DNS가 로컬 장부에서 못 찾으면 실패시키지 않고 호스트에 설정된 업스트림 DNS(기본은 호스트 `/etc/resolv.conf`의 네임서버, 또는 `--dns`로 지정한 서버)로 포워딩한다. 사용자 정의 네트워크에서는 업스트림에 순서대로 질의해 성공이나 NXDOMAIN을 받는 즉시 중단한다. → 코어 1 (1.2)

   </details>

3. 컨테이너를 네트워크 둘에 연결하면 CNM의 Sandbox·Endpoint는 각각 몇 개가 되고, 이름 장부 범위와 어떻게 맞물리는가?

   <details markdown="1"><summary>답 확인</summary>

   Sandbox(컨테이너의 네트워크 스택, `/etc/resolv.conf` 포함)는 하나이고 Endpoint는 네트워크마다 하나씩 둘(`eth0`, `eth1`)이다. Endpoint는 정확히 하나의 Network에만 속하고, 이름 조회 테이블은 네트워크별로 분리되어 있다. 실행 중에도 `docker network connect`로 재시작 없이 Endpoint를 추가할 수 있다. → 코어 2 (2.2)

   </details>

4. 서로 다른 두 네트워크의 컨테이너가 둘 다 `127.0.0.11`을 쓰는데 서로를 못 찾는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   DNS 서버 인스턴스가 따로 있는 것이 아니라 같은 dockerd가 네트워크별로 분리해서 관리하는 조회 테이블이기 때문이다. 해석 범위가 네트워크 단위다. → 코어 2 (2.2)

   </details>

5. `ndots:5`, `search`가 세 개일 때 점 2개짜리 외부 이름 하나는 어떤 순서로 질의되는가? `ndots`를 1로 낮추면 무엇이 달라지고 무엇이 위험한가?

   <details markdown="1"><summary>답 확인</summary>

   점 개수가 `ndots`보다 적으므로 `search` 접미사를 하나씩 붙인 이름 3개를 먼저 시도하고(모두 실패), 마지막에 원래 이름을 절대 이름으로 질의한다. `ndots:1`이면 점이 1개 이상인 이름은 곧바로 절대 이름으로 취급되어 `search`를 거치지 않으므로 외부 이름은 빨라지지만, 점이 없는 내부 짧은 이름만 확장 대상이 되어 점 있는 내부 이름은 실패할 수 있다. 사용자 정의 브리지의 기본값 `ndots:0`은 짧은 이름도 우선 그대로 조회한다. → 코어 3 (3.2)

   </details>

6. `--add-host=host.docker.internal:host-gateway`는 무엇을 하는가? DNS 질의를 거치는가?

   <details markdown="1"><summary>답 확인</summary>

   `/etc/hosts`에 `host.docker.internal` 항목을 추가하고 `host-gateway`를 호스트 자신을 가리키는 내부 IP로 치환한다. DNS 질의를 거치지 않고 파일 조회만으로 해석되므로 내장 DNS나 외부 네임서버 상태와 무관하게 즉시 해석된다. → 코어 3 (3.1)

   </details>

7. Swarm VIP 모드와 DNSRR 모드를 부하 분산 주체와 제약 중심으로 비교하라.

   <details markdown="1"><summary>답 확인</summary>

   VIP(기본): 서비스당 고정 가상 IP 하나, 이름 질의에는 항상 VIP만 응답, 분산은 커널 IPVS. DNSRR: VIP 없이 질의 시점의 모든 태스크 IP를 응답, 분산은 클라이언트가 담당, `endpoint_mode: dnsrr`로 명시해야 하며 라우팅 메시와 함께 쓸 수 없다. → 코어 4

   </details>

8. 컨테이너를 재시작했는데 이름 조회는 새 IP를 주지만 앱이 옛 IP로 접속한다. 어디를 보나?

   <details markdown="1"><summary>답 확인</summary>

   앱 레벨 DNS 캐싱(특히 JVM 계열의 긴 캐싱)이다. Docker 내장 DNS는 매핑이 갱신되므로 dockerd 쪽을 파지 않는다. → 코어 2 (2.3)

   </details>

### 3. 기억 고리

- **C++ 유추:** 컨테이너의 이름 해석 ≈ `getaddrinfo()` 호출. ⚠️ 응답자는 컨테이너 안 프로세스가 아니라 호스트의 dockerd이고, 같은 네트워크의 장부만 안다.
- **C++ 유추:** `--add-host`/`--link` ≈ `/etc/hosts` 편집. ⚠️ `--add-host`는 명시적이고 예측 가능하지만 둘 다 생성 시점에 한 번 기록되므로 실행 중 갱신을 기대할 수 없다.
- **비유:** 내장 DNS = 아파트 단지 관리실 안내 데스크. 같은 단지(네트워크) 주민 이름만 알고 바깥 번호는 외부 안내(업스트림)에 물어 준다. ⚠️ 비유가 깨지는 지점: 데스크는 컨테이너 안에 있는 사람이 아니라 dockerd가 각 컨테이너 네임스페이스에서 가로채 응답하는 것이고, 다른 단지(다른 네트워크)와는 장부가 분리되어 있다.
- **묶음(3의 법칙):** 이름 3종(컨테이너 이름 / `--network-alias` / Compose 서비스 이름) · 응답 3경로(로컬 장부 / 업스트림 포워딩 / 파일 `/etc/hosts`) · 진단 4단계의 앞 3개(같은 네트워크 → 기본 브리지 → ndots)를 한 호흡으로, 4번째(앱 캐싱)는 "Docker 탓이 아님" 꼬리표로.
- **대칭·순서:** VIP(이름→1개 고정 IP, 커널이 분산) ↔ DNSRR(이름→N개 IP, 클라이언트가 분산). 진단 순서는 범위(같은 네트워크) → 종류(기본 브리지) → 설정(ndots) → 앱(캐시)으로 "Docker에서 앱 쪽으로" 이동. 이름 확장 순서는 search 접미사 먼저 → 절대 이름 마지막(점 개수 < ndots일 때).
