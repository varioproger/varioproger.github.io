# 9장. Docker DNS와 서비스 디스커버리

> **🎮 게임 서버 개발자에게** — 게임 서버가 DB·Redis·매치메이커에 붙을 때 설정 파일에 IP를 적거나, 기껏해야 사내 DNS 이름을 `getaddrinfo()`로 풀어 `connect()`하던 구조가 컨테이너 세계에서는 "컨테이너마다 `/etc/resolv.conf`에 `127.0.0.11`이 박혀 있고, 그 주소를 받아 주는 것이 호스트의 dockerd"로 바뀝니다. 결정적으로 다른 점은 이 DNS가 **네트워크 단위로 이름 장부를 따로 들고 있다**는 것입니다. 같은 `127.0.0.11`을 써도 다른 네트워크의 컨테이너는 모르고, 기본 브리지에 붙은 컨테이너는 아예 이 서버를 쓰지 않습니다. 이름 해석은 소켓 API가 아니라 **파일(`/etc/resolv.conf`, `/etc/hosts`)에 컨테이너 생성 시점에 한 번 기록된 설정**에서 출발한다는 점도 기억하세요.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - `redis:6379`처럼 이름으로 붙는 설정을 넣었는데 게임 서버 컨테이너가 이름 해석에 실패한다.
> - 컨테이너를 재시작해 IP가 바뀌었는데 JVM 기반 서비스가 계속 예전 IP로 접속하려 한다.
> - 컨테이너 안에서 호스트의 개발용 서버를 불러야 해서 `host.docker.internal` 같은 이름이 필요하다.

## 코어 — 이것만은 100%

> **한 문장:** 사용자 정의 네트워크의 컨테이너는 `nameserver 127.0.0.11`을 갖고, 그 주소는 dockerd(libnetwork)의 내장 리졸버가 **네트워크 단위** 이름 장부로 응답하며(없는 이름은 호스트의 업스트림 DNS로 포워딩), 기본 브리지에는 이 서버가 없다.

1. **127.0.0.11은 컨테이너 안의 프로세스가 아니라 dockerd다** — 컨테이너 네임스페이스 안의 DNAT 규칙이 `127.0.0.11:53` 질의를 가로채 dockerd 내부의 리졸버로 넘기고, 리졸버는 컨테이너 이름·`--network-alias`·Compose 서비스 이름을 조회한다. 모르는 이름(외부 도메인)은 업스트림으로 포워딩한다.
2. **해석 범위는 네트워크 단위다** — 같은 사용자 정의 네트워크에서만 서로를 찾는다. 기본 브리지(`docker0`)는 내장 DNS 대상이 아니고, 옛 `--link`는 레거시다. 장애 진단의 첫 질문은 늘 "같은 네트워크인가?"다.
3. **DNS 옵션은 파일에 한 번 박히는 정적 설정이다** — `--dns`, `--dns-search`, `--dns-option`, `--add-host`는 `/etc/resolv.conf`·`/etc/hosts`에 컨테이너 생성 시점에 기록된다. 바꾸려면 컨테이너를 재생성한다.
4. **Swarm의 서비스 이름은 VIP 또는 DNSRR로 풀린다** — 기본 VIP는 서비스 이름 하나가 고정 가상 IP 하나로 풀리고 부하 분산은 커널 IPVS가, DNSRR은 살아 있는 모든 태스크 IP를 돌려주고 분산은 클라이언트가 한다.

**이 장의 학습 목표**

- 컨테이너의 `/etc/resolv.conf`에 있는 `127.0.0.11`의 정체와 질의 처리 경로를 설명한다.
- 기본 브리지에 DNS가 없는 이유와 `--link`가 레거시인 이유를 말한다.
- `--dns`·`--dns-search`·`--dns-option`·`--add-host`가 어느 파일에 어떻게 반영되는지 안다.
- Swarm 서비스 디스커버리의 VIP와 DNSRR 차이, DNSRR의 제약을 안다.
- DNS 장애를 4단계 순서(같은 네트워크 → 기본 브리지 → ndots/검색 도메인 → 앱 캐싱)로 진단한다.

|---|---|---|---|
| `getaddrinfo("redis", ...)` 후 `connect()` | 컨테이너 이름 → 127.0.0.11 → IP | 이름 해석 결과 IP로 연결한다는 흐름은 동일 | 응답자가 사내 DNS 서버가 아니라 **호스트의 dockerd**이고, 같은 네트워크의 컨테이너 장부만 안다 |
| `/etc/resolv.conf`의 `nameserver` 줄 | 컨테이너 `/etc/resolv.conf`의 `127.0.0.11` | 리졸버가 읽는 설정 파일 | 루프백 주소처럼 보이지만 컨테이너 안에 DNS 프로세스는 없다. 네임스페이스 안 DNAT가 dockerd로 넘긴다 |

| DNS 라운드로빈(여러 A 레코드) | Swarm DNSRR 모드 | 조회 때마다 여러 IP를 돌려주고 클라이언트가 고른다 | 라우팅 메시와 함께 쓸 수 없고, 분산 책임이 커널이 아니라 클라이언트(또는 그 DNS 캐싱 계층)로 넘어간다 |
| 게임 클라이언트의 DNS 캐시/재접속 로직 | JVM 등 앱 레벨 DNS 캐싱 | 이름을 한 번 풀고 오래 쓰면 IP 변경을 못 따라간다 | Docker 내장 DNS는 갱신되는데 **앱이 캐시**해서 생기는 문제다. dockerd만 의심하면 시간을 허비한다 |

## 코어 1. 127.0.0.11은 컨테이너 안의 프로세스가 아니라 dockerd다

### 1.1 내장 DNS 서버의 정체

**한 줄 요약:** `127.0.0.11`은 컨테이너 네임스페이스 안에서 가로채지는 가상의 DNS 리스너이고, 실제 응답은 호스트의 dockerd(libnetwork) 내장 리졸버가 만든다.

사용자 정의 브리지(또는 오버레이) 네트워크에 연결된 컨테이너에서 `/etc/resolv.conf`를 열면 낯선 주소가 나온다.

```bash
docker network create mynet
docker run --rm --network mynet alpine:latest cat /etc/resolv.conf
```

```
nameserver 127.0.0.11
options ndots:0
```

`127.0.0.11`은 루프백 대역(`127.0.0.0/8`) 안의 주소지만 컨테이너 자신의 로컬 프로세스를 가리키지 않는다. 원천이 설명하는 구조는 이렇다.

- dockerd는 컨테이너의 네트워크 네임스페이스 안에서 `127.0.0.11:53`(UDP/TCP)으로 오는 쿼리를 **가로채도록** iptables/nftables DNAT 규칙을 그 네임스페이스 내부에 심어 둔다.
- 실제 쿼리 처리는 dockerd(정확히는 libnetwork) 프로세스 안의, 컨테이너별 네트워크 컨텍스트를 아는 **내장 리졸버(embedded DNS server)**가 맡는다.
- 응답은 호스트의 dockerd가 그 네트워크에 속한 컨테이너들의 이름-IP 매핑 테이블(각 네트워크 드라이버가 컨테이너 연결/해제 시점마다 갱신하는 내부 서비스 디스커버리 데이터베이스)을 조회해 만든다.

```
 컨테이너 netns                                   호스트
┌──────────────────────────┐
│ 앱: getaddrinfo("api")   │
│   │ 질의                 │
│   ▼                      │
│ 127.0.0.11:53            │
│   │ (netns 안 DNAT 규칙)  │──────▶  dockerd (libnetwork) 내장 리졸버
└──────────────────────────┘             │ 같은 네트워크의 이름-IP 장부 조회
                                         │ 못 찾으면 → 업스트림 DNS로 포워딩
```

> **[보충]** 유추: C++ 서버에서 라이브러리 함수 호출처럼 보이지만 실제로는 다른 프로세스가 처리하는 RPC와 닮았다. 다만 이 유추는 "컨테이너 안에 DNS 프로세스가 없다"는 점에서 깨진다. 앱이 보는 것은 루프백 주소 하나뿐이고 처리는 컨테이너 밖에서 일어난다.

### 1.2 무엇이 이름으로 조회되는가, 외부 도메인은?

**한 줄 요약:** 컨테이너 이름·`--network-alias` 별칭·Compose 서비스 이름(과 Compose가 붙이는 별칭)은 로컬 장부에서, 그 밖의 이름은 호스트의 업스트림 DNS로 넘어간다.

같은 네트워크 안에서는 컨테이너 이름뿐 아니라 `docker run --network-alias`로 지정한 별칭, Compose의 서비스 이름, Compose가 자동으로 붙여 주는 별칭들도 같은 방식으로 조회된다. 컨테이너가 재시작되어 IP가 바뀌어도 내장 DNS의 매핑이 함께 갱신되므로 이름으로 조회하는 한 문제가 없다.

`api.example.com` 같은 외부 도메인은 어떻게 될까. 내장 DNS는 자기 장부에서 찾지 못하면 쿼리를 실패시키지 않고 **호스트에 설정된 업스트림 DNS 서버로 그대로 포워딩**한다.

- 업스트림 서버 목록은 기본적으로 호스트의 `/etc/resolv.conf`에 설정된 네임서버(또는 `--dns`로 명시한 서버)다.
- 사용자 정의 네트워크에서는 내장 DNS가 업스트림 서버들에 **순서대로** 질의해 성공 응답이나 NXDOMAIN을 받는 즉시 중단한다. 원천은 이것이 여러 서버에 무작위로 흩어 쿼리하던 예전 방식보다 예측 가능하다고 설명한다.
- 그래서 컨테이너는 사내 서비스 이름과 외부 도메인을 구분하지 않고 하나의 네임서버(`127.0.0.11`)에만 물으면 된다.

## 코어 2. 해석 범위는 네트워크 단위다 — 기본 브리지와 `--link`

### 2.1 기본 브리지에 DNS가 없는 역사적 이유

**한 줄 요약:** 기본 브리지는 서비스 디스커버리 개념이 없던 초창기의 기본값이라 내장 DNS 대상이 아니고, 그 시절의 이름 통신 수단이 `--link`(정적 `/etc/hosts`)였다.

`docker0`(`docker network ls`에서 `bridge`라는 이름)에 연결된 컨테이너들 사이에는 내장 DNS 기반 이름 해석이 동작하지 않는다. 이 네트워크의 컨테이너 `/etc/resolv.conf`에는 `127.0.0.11` 대신 **호스트의 네임서버 설정이 그대로 복사**되어 있다. 원천은 이것이 설계상 누락이 아니라 역사적 이유라고 설명한다. 기본 브리지는 "네트워크를 지정하지 않았을 때 붙는 기본값"으로 Docker 초창기부터 있었고, 설계 시점에 지금 같은 서비스 디스커버리 개념이 없었다.

당시의 이름 통신 기능이 `--link`다. `docker run --link api:api-alias`처럼 지정하면 Docker가 대상 컨테이너의 IP를 확인해 새 컨테이너의 `/etc/hosts`에 **정적으로 한 줄** 추가했다. 한계는 두 가지였다.

- 컨테이너가 재시작되어 IP가 바뀌면 `/etc/hosts`를 갱신할 방법이 마땅치 않았다.
- 링크는 생성 시점에 한 번 기록되는 관계라, 동적으로 늘어나는 서비스 그룹(같은 역할의 컨테이너 여러 개를 부하 분산 대상으로 묶는 것)을 표현할 수 없었다.

사용자 정의 브리지가 이를 근본적으로 해결했다. 연결된 컨테이너는 자동으로 내장 DNS 대상이 되고 IP가 바뀌어도 장부가 갱신된다. 그래서 `--link`는 레거시로 간주되어 새 구성에서는 쓰지 않으며, 실무에서는 기본 브리지 대신 전용 사용자 정의 브리지를 만드는 것이 사실상 표준이다. Docker Compose가 별도 설정 없이도 프로젝트별 전용 네트워크를 자동 생성하고 서비스 이름으로 서로를 찾게 해 주는 것도 이 "사용자 정의 브리지 + 내장 DNS" 조합 위에서 동작한다. (기본 브리지와 사용자 정의 브리지의 차이는 [8장](08-브리지-네트워크와-포트-게시.md)에서 본다.)

### 2.2 범위는 "네트워크별 장부"

**한 줄 요약:** 서로 다른 네트워크의 컨테이너는 둘 다 `127.0.0.11`을 써도 서로를 찾지 못한다 — DNS 서버가 따로 있는 것이 아니라 같은 dockerd가 네트워크별로 분리해 관리하는 조회 테이블이기 때문이다.

이 사실이 장애 진단의 출발점이다. 원천은 "별도의 DNS 서버 인스턴스가 아니라, 같은 dockerd가 네트워크별로 분리해서 관리하는 조회 테이블"이라고 못 박는다. 두 컨테이너가 서로 다른 브리지 네트워크에 각각 붙어 있다면 이름이 풀리지 않는다.

### 2.3 DNS 문제 진단 4단계

**한 줄 요약:** 같은 네트워크인가 → 기본 브리지인가 → `ndots`/검색 도메인 → 앱의 DNS 캐싱, 이 순서로 좁힌다.

| 순서 | 확인 | 이유 |
|---|---|---|
| 1 | 조회하는 쪽과 대상이 **같은 사용자 정의 네트워크**인가 | 해석 범위가 네트워크 단위. 다르면 서로 못 찾는다 |
| 2 | 컨테이너가 **기본 브리지**에 붙어 있지 않은가 | `--network`를 지정하지 않으면 기본 브리지에 붙을 수 있고, 이때 내장 DNS는 적용되지 않는다 |
| 3 | `ndots`/검색 도메인이 **예상과 다른 이름**으로 조회하게 만들지 않는가 | 쿠버네티스에서 가져온 `ndots:5` 같은 값은 짧은 이름 하나에 검색 도메인을 하나씩 덧붙여 여러 번 질의하게 만들어 지연이나 예상 못한 외부 도메인 매칭을 낳을 수 있다. 사용자 정의 브리지 기본값은 `ndots:0` |
| 4 | 앱이 **DNS 응답을 자체 캐싱**하지 않는가 | 일부 런타임(특히 JVM 계열)은 기본적으로 DNS 응답을 매우 길게 캐싱해, 컨테이너가 재시작되어 IP가 바뀌었는데 예전 IP로 계속 접속할 수 있다. Docker 내장 DNS 문제가 아니라 앱 캐싱 정책 문제다 |

> **[보충]** 쿠버네티스는 Service 이름으로 Pod에 접근하는 서비스 디스커버리를 클러스터 DNS가 맡는다. 개념은 비슷하지만 구현이 다르며, [18장](../3부-쿠버네티스-네트워크/18-DNS와-서비스-디스커버리.md)에서 다룬다. 진단 명령 모음은 [23장](../4부-진단/23-네트워크-장애-진단.md)에 있다.

## 코어 3. DNS 옵션은 파일에 한 번 박히는 정적 설정이다

### 3.1 네 가지 런타임 옵션

**한 줄 요약:** `--dns`·`--dns-search`·`--dns-option`은 `/etc/resolv.conf`에, `--add-host`는 `/etc/hosts`에 컨테이너 생성 시점에 기록된다.

| 옵션 | 반영되는 곳 | 의미 |
|---|---|---|
| `--dns` | `/etc/resolv.conf`의 `nameserver` | 컨테이너가 쓸 네임서버를 명시. 사용자 정의 네트워크에서는 이미 `127.0.0.11`이 들어 있으므로, 추가로 지정하면 내장 DNS가 외부 이름을 포워딩할 때 참조하는 업스트림 목록에 영향을 주는 방식으로 동작 |
| `--dns-search` | `/etc/resolv.conf`의 `search` | 검색 도메인. 짧은 이름(FQDN이 아닌 이름)에 이 도메인을 자동으로 덧붙여 조회 |
| `--dns-option` | `/etc/resolv.conf`의 `options` | `ndots`, `timeout`, `attempts` 같은 resolver 세부 옵션. 사용자 정의 네트워크의 기본값은 `ndots:0` |
| `--add-host` | `/etc/hosts` | `host:ip` 정적 매핑. 옛 `--link`가 하던 일을 훨씬 명시적·예측 가능하게 대신하며, DNS 질의 없이 파일 조회만으로 즉시 해석된다 |

`--add-host`의 IP 자리에 특수값 `host-gateway`를 쓰면 호스트 자신을 가리키는 내부 IP로 자동 치환된다. 컨테이너 안에서 호스트로 접근해야 하는 개발 환경 등에서 쓰인다.

```bash
docker run --rm \
  --dns=1.1.1.1 \
  --dns-search=example.internal \
  --add-host=host.docker.internal:host-gateway \
  alpine:latest sh -c "cat /etc/resolv.conf; echo ---; cat /etc/hosts"
```

### 3.2 "정적"의 의미

**한 줄 요약:** 이 옵션들은 생성 시점에 한 번 기록되므로, 실행 중 호스트의 DNS 설정이 바뀌어도 컨테이너 파일은 (일반적으로) 갱신되지 않아 재생성해야 반영된다.

원천은 일부 예외(dockerd가 특정 조건에서 관리하는 파일을 갱신하는 경우)가 있으나 일반적으로는 정적이라고 설명한다. 게임 서버 설정 파일을 서버 기동 시 한 번 읽는 것과 같다. 설정 파일을 고쳐도 떠 있는 프로세스는 모르듯, 파일을 고쳐도 떠 있는 컨테이너 설정은 바뀌지 않는다는 감각으로 기억하면 된다.

> **[보충]** 이 비유는 이해를 돕는 장치이며, 컨테이너 `/etc/resolv.conf`가 실제로 어떤 방식으로 만들어지는지에 대한 원천 설명은 위 문장이 전부다.

실습은 아래 순서로 진행한다(원천 15장 실습에서 가져온 명령이며, 이 책을 쓴 환경에서 실행해 검증한 것은 아니다).

```bash
docker network create dns-lab
docker run -d --name svc-a --network dns-lab alpine:latest sleep infinity
docker run --rm --network dns-lab alpine:latest cat /etc/resolv.conf     # nameserver 127.0.0.11
docker run --rm --network dns-lab alpine:latest sh -c "nslookup svc-a || getent hosts svc-a"
docker run --rm alpine:latest cat /etc/resolv.conf                       # 기본 브리지: 호스트 네임서버 설정
docker rm -f svc-a
docker network rm dns-lab
```

## 코어 4. Swarm의 서비스 이름은 VIP 또는 DNSRR로 풀린다

### 4.1 VIP 모드 — 이름 하나가 고정 IP 하나

**한 줄 요약:** `docker service create`의 기본값인 VIP 모드는 서비스에 고정 가상 IP를 하나 할당하고, 이름 질의에는 항상 그 VIP만 답하며 부하 분산은 커널 IPVS가 한다.

Swarm 모드에서 같은 역할의 태스크(컨테이너)가 여러 개 떠 있으면 "서비스 이름으로 조회했을 때 어느 태스크로 가는가"라는 문제가 생긴다. 서비스 디스커버리는 Swarm 오버레이가 gossip으로 전파한 멤버십·라우팅 정보([10장](10-macvlan-ipvlan-host-none-오버레이.md) 코어 4)를 바탕으로 클라이언트에 어떤 주소를 돌려줄지 정한다.

VIP 모드에서는 서비스 이름 질의에 항상 VIP 하나만 돌아온다. 실제로 어느 태스크로 가는지는 이 VIP를 대상으로 한 **IPVS(IP Virtual Server) 기반 로드밸런싱 규칙**이 커널 레벨에서 처리한다. 클라이언트는 IP 하나만 알면 되고, 태스크가 늘거나 줄어도 IP가 바뀌지 않으므로 애플리케이션이 캐시한 DNS 응답이 낡아 생기는 문제가 거의 없다.

### 4.2 DNSRR 모드 — 이름 하나가 태스크 IP 여러 개

**한 줄 요약:** DNSRR은 VIP 없이 질의 시점에 살아 있는 모든 태스크 IP 목록을 돌려주고 선택은 클라이언트에 맡기며, 라우팅 메시와는 함께 쓸 수 없다.

- 로드밸런싱 책임이 커널의 IPVS에서 클라이언트(또는 클라이언트의 DNS 캐싱 계층)로 넘어간다.
- `endpoint_mode: dnsrr`로 **명시적으로** 지정해야 활성화된다.
- 라우팅 메시(ingress 모드의 핵심 기능)와는 함께 쓸 수 없다. 라우팅 메시가 VIP를 전제로 노드로 들어온 트래픽을 태스크로 전달하는 방식이기 때문이다.

```yaml
# Compose 파일에서 DNSRR 모드를 지정하는 예
services:
  worker:
    image: myapp:latest
    deploy:
      endpoint_mode: dnsrr
```

| 구분 | VIP (기본) | DNSRR |
|---|---|---|
| 이름 질의 응답 | 고정 VIP 하나 | 질의 시점의 모든 태스크 IP 목록 |
| 부하 분산 주체 | 커널 IPVS | 클라이언트 / 클라이언트 DNS 캐싱 계층 |
| 라우팅 메시 | 함께 사용 가능 | 함께 사용 불가 |
| 캐시 낡음 문제 | 거의 없음(IP 불변) | 응답이 태스크 IP 목록이라 클라이언트 DNS 캐싱의 영향을 받는다(원천의 VIP 설명에서 유추한 [보충]) |
| 주 용도 | 대부분의 실무 | 클라이언트가 정교한 부하 분산 로직(특정 IP 우선 접속, 커넥션 풀링 전략 등)을 이미 갖춘 경우, 또는 UDP 기반처럼 IPVS의 연결 추적과 궁합이 맞지 않는 워크로드에서 선택적으로 고려 |

> **[보충]** 이 책은 Swarm 자체를 쓰는 것이 목적이 아니라 "서비스 이름 → 고정 가상 IP + 커널 부하 분산" 대 "이름 → 여러 IP"라는 두 패턴을 이해하는 데 목적이 있다. 쿠버네티스 Service(ClusterIP)와 헤드리스 Service가 같은 두 패턴에 대응한다는 점은 원천에 있는 설명이 아니므로 [16장](../3부-쿠버네티스-네트워크/16-Service와-EndpointSlice.md)에서 확인하자.

## 실무 적용

### 체크리스트

- [ ] 서버끼리 이름으로 통신하려면 **같은 사용자 정의 네트워크**에 붙인다(`--network`를 빼먹으면 기본 브리지에 붙어 내장 DNS를 못 쓴다).
- [ ] 컨테이너 안 `/etc/resolv.conf`가 `nameserver 127.0.0.11`인지(사용자 정의 네트워크), 호스트 네임서버 복사본인지(기본 브리지) 먼저 본다.
- [ ] IP를 설정 파일에 하드코딩하지 않는다. 재시작으로 IP가 바뀌어도 장부는 갱신되지만 하드코딩은 깨진다.
- [ ] `--link`는 새 구성에서 쓰지 않는다. 정적 매핑이 필요하면 `--add-host`.
- [ ] 호스트로 접근해야 하는 개발 환경에는 `--add-host=host.docker.internal:host-gateway`를 쓴다.
- [ ] `ndots`를 바꿀 때는 의미를 알고 바꾼다(`ndots:5`는 짧은 이름 조회마다 검색 도메인을 덧붙여 여러 번 질의).
- [ ] DNS 옵션을 바꾸면 컨테이너를 재생성해야 반영된다는 것을 기억한다.
- [ ] 이름이 풀리는데 접속이 엉뚱하면 앱의 DNS 캐싱(JVM 등)을 의심한다.
- [ ] Swarm에서 DNSRR은 라우팅 메시와 함께 쓸 수 없다.

### 시나리오로 확인하기

1. **상황:** `docker run -d --name game ...`과 `docker run -d --name redis ...`로 각각 띄웠다. `game` 설정의 `redis:6379`가 이름 해석에 실패한다. `game`의 `/etc/resolv.conf`에는 호스트와 같은 네임서버가 적혀 있다.
   **질문:** 의심 부품, 확인, 해결은?

   <details markdown="1"><summary>답 확인</summary>

   의심 부품은 기본 브리지다. `--network`를 지정하지 않으면 기본 브리지에 붙고, 이 네트워크는 내장 DNS 대상이 아니라서 `resolv.conf`에 `127.0.0.11` 대신 호스트의 네임서버 설정이 복사되어 있다(진단 2단계). 해결은 `docker network create gamenet` 후 두 컨테이너를 `--network gamenet`으로 다시 띄우는 것이다. `--link`는 레거시라 쓰지 않는다. → 코어 2

   </details>

2. **상황:** 두 컨테이너 모두 `nameserver 127.0.0.11`을 가졌는데 서로를 찾지 못한다.
   **질문:** 가장 먼저 무엇을 확인하나?

   <details markdown="1"><summary>답 확인</summary>

   두 컨테이너가 **같은 사용자 정의 네트워크**에 있는지 본다. 내장 DNS는 별도 서버가 아니라 같은 dockerd가 네트워크별로 분리 관리하는 조회 테이블이므로, 서로 다른 네트워크라면 둘 다 `127.0.0.11`을 써도 서로를 찾을 수 없다. 이어서 `ndots`/검색 도메인, 앱 캐싱 순으로 본다. → 코어 2 (2.2, 2.3)

   </details>

3. **상황:** 컨테이너를 재시작했더니 JVM 기반 서비스가 예전 IP로 계속 접속을 시도한다. `nslookup`으로 컨테이너 안에서 풀면 새 IP가 나온다.
   **질문:** 원인과 대응은?

   <details markdown="1"><summary>답 확인</summary>

   내장 DNS는 갱신되어 새 IP를 주는데 앱이 DNS 응답을 길게 캐싱하는 것이다(일부 런타임, 특히 JVM 계열은 기본적으로 매우 길게 캐싱하도록 설정). Docker 쪽이 아니라 애플리케이션 캐싱 정책 문제이므로 dockerd에서 원인을 찾느라 시간을 쓰지 말고 앱의 DNS 캐시 설정을 점검한다. → 코어 2 (2.3 4단계)

   </details>

3. 기본 브리지에 내장 DNS가 없는 이유와 그 시절 대안은?

   <details markdown="1"><summary>답 확인</summary>

   기본 브리지는 Docker 초창기부터의 "네트워크 미지정 시 기본값"이고 설계 시점에 서비스 디스커버리 개념이 없었다. 대안은 `--link`로, 대상 컨테이너 IP를 `/etc/hosts`에 정적으로 한 줄 추가했다. → 코어 2 (2.1)

   </details>

4. `--link`가 레거시가 된 두 가지 한계는?

   <details markdown="1"><summary>답 확인</summary>

   (1) 컨테이너 재시작으로 IP가 바뀌어도 `/etc/hosts`를 갱신할 방법이 마땅치 않았다. (2) 생성 시점에 한 번 기록되는 관계라 동적으로 늘어나는 서비스 그룹을 표현할 수 없었다. 사용자 정의 네트워크의 내장 DNS가 이를 해결했다. → 코어 2 (2.1)

   </details>

5. 서로 다른 두 네트워크의 컨테이너가 둘 다 `127.0.0.11`을 쓰는데 서로를 못 찾는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   DNS 서버 인스턴스가 따로 있는 것이 아니라 같은 dockerd가 네트워크별로 분리해서 관리하는 조회 테이블이기 때문이다. 해석 범위가 네트워크 단위다. → 코어 2 (2.2)

   </details>

6. `--dns-option`으로 `ndots`를 크게 줄 때의 위험은?

   <details markdown="1"><summary>답 확인</summary>

   짧은 이름 하나를 조회할 때마다 검색 도메인을 하나씩 덧붙여 여러 번 질의하게 되어 불필요한 지연이나 예상치 못한 외부 도메인 매칭이 생길 수 있다. 사용자 정의 브리지 기본값은 `ndots:0`이므로 의미를 이해하고 바꾼다. → 코어 2 (2.3), 코어 3

   </details>

7. `--add-host=host.docker.internal:host-gateway`는 무엇을 하는가? DNS 질의를 거치는가?

   <details markdown="1"><summary>답 확인</summary>

   `/etc/hosts`에 `host.docker.internal` 항목을 추가하고 `host-gateway`를 호스트 자신을 가리키는 내부 IP로 치환한다. DNS 질의를 거치지 않고 파일 조회만으로 해석되므로 내장 DNS나 외부 네임서버 상태와 무관하게 즉시 해석된다. → 코어 3 (3.1)

   </details>

8. Swarm VIP 모드와 DNSRR 모드를 부하 분산 주체와 제약 중심으로 비교하라.

   <details markdown="1"><summary>답 확인</summary>

   VIP(기본): 서비스당 고정 가상 IP 하나, 이름 질의에는 항상 VIP만 응답, 분산은 커널 IPVS. DNSRR: VIP 없이 질의 시점의 모든 태스크 IP를 응답, 분산은 클라이언트가 담당, `endpoint_mode: dnsrr`로 명시해야 하며 라우팅 메시와 함께 쓸 수 없다. → 코어 4

   </details>

9. 컨테이너를 재시작했는데 이름 조회는 새 IP를 주지만 앱이 옛 IP로 접속한다. 어디를 보나?

   <details markdown="1"><summary>답 확인</summary>

   앱 레벨 DNS 캐싱(특히 JVM 계열의 긴 캐싱)이다. Docker 내장 DNS는 매핑이 갱신되므로 dockerd 쪽을 파지 않는다. → 코어 2 (2.3)

   </details>

### 3. 기억 고리

- **C++ 유추:** 컨테이너의 이름 해석 ≈ `getaddrinfo()` 호출. ⚠️ 응답자는 컨테이너 안 프로세스가 아니라 호스트의 dockerd이고, 같은 네트워크의 장부만 안다.
- **C++ 유추:** `--add-host`/`--link` ≈ `/etc/hosts` 편집. ⚠️ `--add-host`는 명시적이고 예측 가능하지만 둘 다 생성 시점에 한 번 기록되므로 실행 중 갱신을 기대할 수 없다.
- **비유:** 내장 DNS = 아파트 단지 관리실 안내 데스크. 같은 단지(네트워크) 주민 이름만 알고 바깥 번호는 외부 안내(업스트림)에 물어 준다. ⚠️ 비유가 깨지는 지점: 데스크는 컨테이너 안에 있는 사람이 아니라 dockerd가 각 컨테이너 네임스페이스에서 가로채 응답하는 것이고, 다른 단지(다른 네트워크)와는 장부가 분리되어 있다.
- **묶음(3의 법칙):** 이름 3종(컨테이너 이름 / `--network-alias` / Compose 서비스 이름) · 응답 3경로(로컬 장부 / 업스트림 포워딩 / 파일 `/etc/hosts`) · 진단 4단계의 앞 3개(같은 네트워크 → 기본 브리지 → ndots)를 한 호흡으로, 4번째(앱 캐싱)는 "Docker 탓이 아님" 꼬리표로.
- **대칭·순서:** VIP(이름→1개 고정 IP, 커널이 분산) ↔ DNSRR(이름→N개 IP, 클라이언트가 분산). 진단 순서는 범위(같은 네트워크) → 종류(기본 브리지) → 설정(ndots) → 앱(캐시)으로 "Docker에서 앱 쪽으로" 이동.
