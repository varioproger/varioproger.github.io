# 10장. macvlan·ipvlan·host·none·오버레이

> **🎮 게임 서버 개발자에게** — 지금까지의 브리지 네트워크는 "컨테이너는 사설 IP, 밖으로는 호스트 IP로 NAT, 안으로는 `-p` 포트 매핑"이었습니다. 게임 서버를 물리 서버에 직접 올리면 서버 한 대가 자기 IP와 표준 포트를 가졌는데, 이 장의 드라이버들은 그 감각을 **컨테이너에 되돌려 주는 쪽**(macvlan/ipvlan: 컨테이너가 물리망의 독립 장비처럼 보임, host: 아예 호스트의 소켓 공간을 공유)과 **정반대로 끊어 버리는 쪽**(none)과 **여러 호스트를 한 L2처럼 묶는 쪽**(오버레이)으로 갈라집니다. 결정적으로 다른 점은 macvlan/ipvlan 컨테이너가 외부의 다른 서버와는 잘 통신하는데 **정작 같은 호스트와는 ping조차 안 된다**는 것입니다. 설정 실수가 아니라 커널의 구조적 제약입니다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 라이선스·클러스터 멤버십이 IP/MAC에 묶인 레거시 서버를 NAT 없이 물리망에 그대로 올려야 한다.
> - macvlan으로 올린 컨테이너에 다른 서버는 접속되는데 호스트의 헬스체크·모니터링 에이전트는 접속이 안 된다.
> - 지연에 민감한 프록시를 `--network host`로 띄웠더니 같은 호스트의 다른 컨테이너와 포트가 충돌한다.

## 코어 — 이것만은 100%

> **한 문장:** 브리지·오버레이는 컨테이너마다 격리된 netns에 NAT를 거쳐 나가지만, macvlan/ipvlan은 NAT 없이 물리망에 직접 붙고(macvlan = 컨테이너별 고유 MAC, ipvlan = 부모 MAC 공유 + IP로 분배), host는 netns 분리를 포기하며, none은 `lo`만 남기고, 오버레이는 L3 위에 VXLAN으로 가상 L2를 얹는 멀티호스트 방식이다.

1. **macvlan/ipvlan은 NAT를 우회해 물리망에 직접 붙는다** — macvlan은 부모 인터페이스 위에 컨테이너마다 고유 MAC의 서브인터페이스를, ipvlan은 부모의 MAC을 공유하고 IP로 분배한다. 둘 다 호스트의 IP 스택(라우팅, iptables/nftables)을 거치지 않는다. MAC 개수를 제한하는 스위치·클라우드 NIC에서는 macvlan이 막히고 ipvlan이 대안이다.
2. **macvlan/ipvlan 컨테이너는 같은 호스트와 직접 통신할 수 없다** — 커널 구조상의 제약이며, 호스트에 같은 부모를 쓰는 서브인터페이스(`mv-shim`)를 하나 더 만들어 우회한다.
3. **host와 none은 netns의 양 극단이다** — host는 `CLONE_NEWNET`을 쓰지 않아 호스트의 인터페이스·라우팅·포트를 그대로 공유한다(NAT 없음, 포트 충돌, 격리 약화). none은 독립 netns에 `lo`만 있다.
4. **오버레이는 L3 위에 가상 L2를 얹는다** — Swarm의 오버레이는 컨트롤 플레인(gossip)과 데이터 플레인(VXLAN)이 분리되어 있고, ingress 라우팅 메시는 IPVS로 모든 노드에서 게시 포트를 받는다. 2026년 현재 Swarm은 deprecated가 아니지만 nftables 백엔드와는 함께 쓸 수 없다.

**이 장의 학습 목표**

- NAT를 우회해야 하는 이유 세 가지와 macvlan/ipvlan의 동작 원리 차이를 설명한다.
- macvlan 4모드, ipvlan L2/L3, 802.1Q 서브인터페이스(`eth0.20`)를 구분한다.
- macvlan에서 promiscuous mode가 왜 문제가 되고 ipvlan이 왜 대안인지 안다.
- 호스트-컨테이너 직접 통신 불가의 원인과 `mv-shim` 우회법을 안다.
- host/none 모드의 장단점과 6가지 모드 비교표를 채운다.
- Swarm 오버레이의 컨트롤/데이터 플레인 분리, ingress 라우팅 메시, 현재 위상을 설명한다.

## 코어 1. macvlan/ipvlan은 NAT를 우회해 물리망에 직접 붙는다

### 1.1 왜 NAT를 우회해야 하는가

**한 줄 요약:** 브리지 + 포트 매핑은 편리하지만, IP/MAC에 의존하는 레거시, "서비스마다 자기 IP + 표준 포트" 전제의 환경, 고성능 워크로드에서는 NAT 계층이 걸림돌이 된다.

브리지·오버레이 컨테이너는 공통적으로 NAT를 거친다. 사설 대역(예: `172.17.0.0/16`) IP를 받고, 나갈 때는 호스트 IP로 매스커레이딩, 들어올 때는 포트 매핑 DNAT다. 대부분 충분하지만 세 가지 상황에서 한계가 나타난다.

1. **IP/MAC 의존 레거시** — 자신의 IP나 MAC을 라이선스 검증, 클러스터 멤버십 판단, 멀티캐스트 기반 디스커버리 등의 근거로 쓰는 소프트웨어는 NAT 뒤에서 컨테이너 내부의 IP와 외부에서 도달하는 경로의 IP가 달라 오동작할 수 있다. 물리/가상 네트워크 어플라이언스를 컨테이너로 옮기는 마이그레이션에서 자주 만난다.
2. **포트 구분 대신 IP 구분** — 포트 매핑은 컨테이너마다 호스트 포트를 따로 할당해야 한다. 네트워크 장비·방화벽 정책이 "각 서비스는 자기 IP로 표준 포트에 응답한다"를 전제로 설계된 환경에서는 컨테이너마다 고유 IP를 주는 편이 운영이 단순하다.
3. **conntrack 오버헤드** — DNAT/SNAT 자체가 커널 conntrack을 거치는 추가 단계다. 초당 연결 수가 매우 많은 고성능 워크로드(NFV 등)에서는 NAT 계층을 걷어내고 싶어진다.

macvlan과 ipvlan은 컨테이너의 인터페이스를 호스트의 물리 인터페이스에 직접 연결해 컨테이너가 물리망에서 "보통의 호스트"처럼 보이게 한다. (NAT/conntrack 자체는 [5장](../1부-리눅스-네트워크-기초/05-netfilter-iptables-NAT-conntrack.md)에서, 브리지 경로는 [8장](08-브리지-네트워크와-포트-게시.md)에서 다뤘다.)

### 1.2 macvlan — 컨테이너마다 고유 MAC

**한 줄 요약:** 하나의 부모 인터페이스 위에 각자 고유 MAC을 가진 서브인터페이스를 만들고, 프레임을 MAC 기준으로 분배한다 — veth·브리지(`docker0`)를 거치지 않는다.

호스트의 `eth0`를 부모(parent)로 지정하면 컨테이너마다 `eth0` 기반 macvlan 서브인터페이스가 생성되어, 커널이 새로 발급한 고유 MAC과 함께 컨테이너 네임스페이스 안으로 이동한다. 트래픽은 `eth0`가 직접 수신하는 이더넷 프레임 레벨에서 MAC 기준으로 각 서브인터페이스에 분배되며, **호스트의 IP 스택(라우팅 테이블, iptables/nftables 체인)을 거치지 않고** 물리 네트워크로 직접 나간다. 스위치에는 같은 물리 포트 뒤의 또 다른 독립 장비로 보이고, DHCP로 IP를 받거나 고정 IP를 쓸 수 있다.

```
[브리지]   컨테이너 eth0 ─ veth ─ docker0(브리지) ─ 호스트 IP 스택(NAT) ─ eth0 ─ 물리망
[macvlan]  컨테이너 eth0(고유 MAC) ─────────── 부모 eth0 가 MAC으로 분배 ─────── 물리망
```

> **[보충]** 위 그림은 원천 서술(veth·docker0·호스트 IP 스택을 거치지 않음)을 한눈에 비교하도록 정리한 것이다.

**macvlan 4모드** (`-o macvlan_mode`, 기본값 `bridge`)

| 모드 | 동작 | 주요 용도 |
|---|---|---|
| `bridge` (기본값) | 같은 부모를 공유하는 서브인터페이스끼리 커널 내부에서 직접 스위칭, 물리 스위치를 거치지 않음 | 대부분의 요구, 가장 널리 쓰임 |
| `vepa` | 같은 부모의 서브인터페이스 간 트래픽도 반드시 외부 스위치로 내보냈다가 되돌아오게 강제 | 802.1Qbg 지원 스위치에서 모든 트래픽에 중앙 정책/모니터링 적용 |
| `private` | 같은 부모의 서브인터페이스끼리 통신 자체를 차단 | 컨테이너 간 격리가 필수인 멀티테넌시 |
| `passthru` | 부모 인터페이스 하나를 컨테이너 하나에 통째로 전달(서브인터페이스 여러 개 안 만듦) | 컨테이너가 물리 NIC를 배타적으로 점유해야 하는 특수 경우 |

`vepa`를 "802.1Q 트렁크 모드"로 오해하기 쉽다. 원천은 vepa가 스위치의 반사(reflective relay) 지원이 필요한 표준 프로토콜 확장이고, 802.1Q VLAN 트렁킹은 부모 인터페이스를 VLAN 서브인터페이스로 구성하는 별개의 축이라고 정정한다.

```bash
docker network create -d macvlan \
  --subnet=192.168.10.0/24 \
  --gateway=192.168.10.1 \
  -o parent=eth0 \
  mv-net
```

스위치 포트가 트렁크(여러 VLAN의 태그 프레임)라면 부모를 `eth0.20`처럼 `.` + VLAN ID로 지정한다. Docker는 이 이름 규칙을 인식해 VLAN 서브인터페이스가 없으면 자동 생성한다.

```bash
docker network create -d macvlan \
  --subnet=192.168.20.0/24 \
  --gateway=192.168.20.1 \
  -o parent=eth0.20 \
  mv-net-vlan20
```

스위치 트렁크 설정과 Docker 네트워크의 VLAN ID가 어긋나면 컨테이너가 통신하지 못하는데도 Docker는 별다른 오류를 내지 않는 경우가 많다. 트러블슈팅은 **스위치 쪽 설정부터** 확인한다.

**promiscuous mode 주의.** macvlan은 한 물리 인터페이스로 서로 다른 MAC의 트래픽을 송수신한다. 그런데 일부 물리 NIC나 가상화 환경(퍼블릭 클라우드의 가상 NIC, 일부 하이퍼바이저 vSwitch)은 자신에게 할당된 MAC의 프레임만 통과시킨다. macvlan이 동작하려면 NIC가 promiscuous mode로 자기 MAC이 아닌 프레임도 상위로 전달해야 하고, 경우에 따라 스위치 포트가 포트당 여러 MAC 학습을 허용해야 한다. 원천은 AWS EC2·GCP Compute Engine 등이 소스/목적지 MAC 검사를 엄격히 적용해 별도의 "소스/목적지 확인 비활성화" 등 설정 없이는 macvlan 트래픽이 **조용히 드롭**된다고 설명한다. 온프레미스에서는 스위치 포트 보안(port security)이나 802.1X가 MAC 개수를 제한하고 있지 않은지 네트워크 팀과 사전 확인한다.

### 1.3 ipvlan — MAC을 공유하는 대안

**한 줄 요약:** ipvlan은 모든 컨테이너가 부모의 MAC을 공유하고 커널이 IP 기준으로 분배하므로 MAC 개수 제한 문제에서 자유롭다.

스위치 입장에서는 "MAC 하나 뒤에 여러 IP를 쓰는 하나의 장비"로 보인다. 포트 보안으로 학습 MAC 수를 엄격히 제한하는 스위치나 가상 NIC가 자기 MAC 외 트래픽을 통과시키지 않는 클라우드 인스턴스에서 macvlan보다 훨씬 안정적이다.

- **L2 모드(기본값):** macvlan bridge와 유사. 같은 부모의 컨테이너는 같은 브로드캐스트 도메인(같은 서브넷)으로 취급되어 ARP·브로드캐스트·멀티캐스트가 오간다. 다른 서브넷은 물리 게이트웨이를 거친다.
- **L3 모드:** 부모 인터페이스가 사실상 라우터처럼 동작한다. 브로드캐스트·멀티캐스트는 전달되지 않고, 커널이 서브인터페이스로 향하는 패킷을 IP 기준으로 직접 라우팅한다. 같은 부모의 L3 컨테이너끼리는 **서로 다른 서브넷이어도 외부 라우터 없이** 커널 내부에서 통신한다. 대신 DHCP처럼 브로드캐스트에 의존하는 워크로드는 맞지 않아 고정 IP를 할당하는 것이 일반적이며, 게이트웨이를 지정하지 않는 경우가 많다.

```bash
# L2 모드(기본값)
docker network create -d ipvlan \
  --subnet=192.168.30.0/24 \
  --gateway=192.168.30.1 \
  -o parent=eth0 \
  -o ipvlan_mode=l2 \
  ipv-l2-net

# L3 모드
docker network create -d ipvlan \
  --subnet=192.168.40.0/24 \
  -o parent=eth0 \
  -o ipvlan_mode=l3 \
  ipv-l3-net
```

**선택 기준.** 컨테이너가 자체 MAC을 가진 완전 독립 장비처럼 보여야 하고 스위치에 MAC 개수 제한이 없다면 macvlan이 직관적이다. 스위치·클라우드가 인터페이스당 MAC 수를 제한하거나, 수백&#126;수천 개 컨테이너에 물리망 IP를 부여해 MAC 주소 테이블(CAM) 부담을 줄이고 싶다면 ipvlan이 유리하다. 두 드라이버 모두 Docker Engine 29에서도 libnetwork의 기존 드라이버 구조를 유지하며, 호스트의 NAT/포트 매핑 계층을 거치지 않으므로 [11장](11-Docker-방화벽-iptables에서-nftables로.md)의 nftables 백엔드 전환과 사실상 무관하게 동작한다.

| 구분 | macvlan | ipvlan |
|---|---|---|
| 컨테이너 MAC | 컨테이너마다 고유 | 부모 MAC 공유 |
| 분배 기준 | MAC | IP |
| 스위치/클라우드 MAC 제한 환경 | 취약(promiscuous·다중 MAC 필요) | 안정적 |
| 모드 | bridge / vepa / private / passthru | L2 / L3 |
| 공통 | NAT 불필요, 물리망 IP, 호스트와 직접 통신 불가 | 동일 |

## 코어 2. macvlan/ipvlan 컨테이너는 같은 호스트와 직접 통신할 수 없다

### 2.1 호스트와 컨테이너가 통신하지 못하는 이유

**한 줄 요약:** 부모와 서브인터페이스는 "물리 매체를 공유"하는 관계일 뿐 서로 자유롭게 통신하는 링크가 아니며, 서브인터페이스에서 나간 패킷이 같은 물리 인터페이스로 돌아 들어오는 경로가 커널에 만들어지지 않는다.

macvlan/ipvlan을 처음 쓰면 거의 예외 없이 만나는 증상이다. 컨테이너는 물리망의 다른 장비와는 잘 통신하는데, 컨테이너를 실행 중인 호스트와는 ping조차 안 된다. 원천은 이것이 설정 실수가 아니라 리눅스 커널의 구조적 제약이며 macvlan bridge 모드든 ipvlan L2 모드든 동일한 드라이버 설계상의 한계라고 설명한다.

### 2.2 우회: 호스트도 macvlan 서브인터페이스가 된다

**한 줄 요약:** 호스트에 같은 부모를 쓰는 macvlan 서브인터페이스(`mv-shim`)를 하나 더 만들어 호스트가 "또 하나의 macvlan 장비"인 척하면 통신된다.

```bash
# 호스트에 macvlan 서브인터페이스를 하나 만들어 컨테이너와 같은 대역에 배치
sudo ip link add mv-shim link eth0 type macvlan mode bridge
sudo ip addr add 192.168.10.200/24 dev mv-shim
sudo ip link set mv-shim up

# 이제 호스트의 mv-shim을 통해 macvlan 네트워크의 컨테이너와 통신 가능
ping 192.168.10.101
```

호스트의 `eth0` 자체가 아니라 `eth0`을 부모로 하는 또 다른 macvlan 자식(`mv-shim`)을 통해 통신하기 때문에 제약을 피한다. Docker CLI가 자동으로 만들어 주지는 않으며 사용자가 `ip link`로 직접 구성해야 한다. ipvlan도 같은 원리로 부모 위에 호스트용 ipvlan 서브인터페이스를 추가해 우회한다. 삭제는 `sudo ip link delete mv-shim`.

실무에서 중요한 이유는 설계 단계에서 이 제약을 감안해야 하기 때문이다. macvlan/ipvlan 컨테이너에 대해 **호스트에서** 헬스체크하거나 모니터링 에이전트가 호스트에서 컨테이너 IP로 접속하려는 설계를 세우면 "다른 서버에서는 되는데 정작 호스트에서는 안 된다"는 당혹스러운 증상이 나온다.

> **[보충]** 이 실습은 원천이 "물리 스위치에 접근할 수 있는 온프레미스 리눅스 호스트"를 전제로 하며, 클라우드 인스턴스에서는 가상 NIC의 MAC 필터링 때문에 macvlan 부분이 그대로 동작하지 않을 수 있다고 안내한다. 이 책을 쓴 환경은 Windows라 직접 실행 검증은 하지 못했다.

## 코어 3. host와 none은 네트워크 네임스페이스의 양 극단이다

### 3.1 host 모드 — 네임스페이스 분리를 포기

**한 줄 요약:** `--network host` 컨테이너는 `CLONE_NEWNET`을 쓰지 않아 호스트의 인터페이스·라우팅·iptables/nftables·포트를 그대로 공유한다 — NAT도 `-p`도 필요 없다.

브리지·오버레이·macvlan·ipvlan은 모두 컨테이너마다 독립 netns를 만들고 그 안에 인터페이스를 구성해 넣는다. host 모드는 이 전제를 뒤집는다. 리눅스는 `clone()`/`unshare()`에 `CLONE_NEWNET`을 주어 새 netns를 만드는데([3장](../1부-리눅스-네트워크-기초/03-네트워크-네임스페이스.md)), host 모드는 이 플래그를 쓰지 않는다. 컨테이너 프로세스는 호스트의 초기 netns를 그대로 공유한다.

```bash
docker run -d --network host --name web-host nginx:latest
```

이 컨테이너 안의 nginx는 컨테이너 전용 IP 없이 **호스트의 IP로 직접 80번을 listen**한다. `-p` 옵션을 줘도 무시된다(매핑할 대상 netns가 없다).

- **이점(성능):** veth 페어·브리지·conntrack NAT 단계가 사라진다. 브리지에서는 NIC → 커널 스택 → docker0 → veth → 컨테이너 netns로 여러 단계를 거치지만, host에서는 애플리케이션이 호스트 소켓 계층에 사실상 직접 접근한다. 초당 수만&#126;수십만 연결을 처리하는 프록시·로드밸런서·패킷 캡처 도구처럼 지연·처리량에 민감한 워크로드에서 선호된다.
- **대가 1 — 포트 충돌:** netns를 공유하면 포트 공간도 공유한다. host 모드 컨테이너 두 개가 같은 포트를 listen하면 평범한 리눅스 프로세스 두 개가 충돌하듯 실패한다.
- **대가 2 — 격리 약화:** 컨테이너 프로세스가 호스트의 모든 인터페이스·라우팅 정보에 접근하므로 침해 시 노출 표면이 넓다. `NET_ADMIN` capability와 결합되면 컨테이너에서 `iptables`/`nft`로 **호스트의 방화벽 규칙까지** 조작할 수 있다. 그래서 신뢰할 수 있는 워크로드이면서 성능이 명확한 우선순위일 때로 한정하는 것이 일반적 권고다.

> **[보충]** 🎮 유추: host 모드는 게임 서버를 물리 서버에서 그냥 실행하는 것과 같다. `bind(0.0.0.0:7777)`이 곧 호스트의 7777이고, 두 번째 인스턴스가 같은 포트를 `bind`하면 `EADDRINUSE`가 난다. ⚠️ 다만 컨테이너라서 파일 시스템·프로세스 등 다른 네임스페이스 격리는 유지되고, 공유되는 것은 **네트워크**뿐이다. (이 문장은 원천 서술의 "netns만 공유"를 풀어 쓴 것이다.)

### 3.2 none 모드 — `lo`만 남기고 완전 격리

**한 줄 요약:** `--network none` 컨테이너는 독립 netns를 가지지만 루프백(`lo`) 외에는 veth도 브리지 연결도 IP도 없고, `lo`조차 UP이 아닐 때가 많다.

```bash
docker run -it --network none alpine:latest ip addr
```

쓰임은 두 가지다. 첫째, 네트워크가 필요 없는 순수 배치 작업(파일 변환, 로컬 데이터 처리)에서 공격 표면을 줄이려고 의도적으로 차단한다. 둘째, Docker 기본 드라이버가 아닌 다른 네트워킹(별도 CNI 플러그인, SR-IOV 직접 연결, 특수 하드웨어 오프로드 경로)을 수동으로 붙일 때다. Docker가 아무 인터페이스도 만들지 않도록 none으로 띄운 뒤 컨테이너 netns(`/var/run/docker/netns/` 아래 또는 `nsenter`로 접근 가능한 netns)에 외부 도구가 직접 인터페이스를 붙인다. 이때 Docker는 netns만 만들어 줄 뿐 네트워킹 구성의 책임은 완전히 외부 도구로 넘어간다.

### 3.3 모드 6종 한눈에 비교

**한 줄 요약:** netns 분리 여부 → 컨테이너 IP → NAT 필요 → 호스트와 통신 가능 여부, 네 축으로 외운다.

| 모드 | 네트워크 네임스페이스 | 컨테이너 IP | NAT 필요 여부 | 호스트-컨테이너 통신 | 주 용도 |
|---|---|---|---|---|---|
| bridge(사용자 정의) | 분리 | 사설 대역, docker0 등 경유 | 필요(포트 매핑) | 가능 | 범용 단일 호스트 |
| overlay | 분리 | VXLAN 오버레이 대역 | 필요(ingress 등) | 가능(호스트도 참여 시) | Swarm 멀티호스트 |
| macvlan | 분리 | 물리망 대역, 고유 MAC | 불필요 | 기본 불가(우회 필요) | 레거시 IP/MAC 요구 |
| ipvlan | 분리 | 물리망 대역, MAC 공유 | 불필요 | 기본 불가(우회 필요) | MAC 제한 환경 |
| host | 미분리(호스트 공유) | 호스트 IP 그대로 | 불필요 | 구분 자체가 없음 | 고성능, 신뢰 워크로드 |
| none | 분리(루프백만) | 없음 | 해당 없음 | 불가 | 완전 격리, 수동 구성 |

## 코어 4. 오버레이는 L3 위에 가상 L2를 얹는다

### 4.1 오버레이의 필요와 VXLAN 한 컷

**한 줄 요약:** 브리지는 커널 하나의 범위를 못 벗어나므로, 여러 호스트의 컨테이너를 같은 스위치처럼 묶으려면 IP 연결성 위에 VXLAN(UDP 4789)으로 가상 L2를 얹는다.

호스트 A의 `docker0` 컨테이너와 호스트 B의 `docker0` 컨테이너는 아무 조치 없이는 서로 다른 사설 대역에서 서로의 존재를 모른다. 수동 라우팅은 호스트가 늘수록 복잡도가 급증하고 컨테이너 재스케줄링마다 라우팅을 갱신해야 해 확장성이 없다. 오버레이는 L3 위에 캡슐화로 가상 L2를 얹는 방식이다.

VXLAN의 세 요소(상세는 [6장](../1부-리눅스-네트워크-기초/06-오버레이-VXLAN-MTU.md))는 이렇다. 24비트 VNI로 논리 L2를 구분해(약 1,600만 개) 오버레이 네트워크 하나가 VNI 하나에 대응하고, 원본 이더넷 프레임 전체를 UDP **4789번**(RFC 7348 표준)으로 감싸며, 이 때문에 50바이트 안팎의 MTU 오버헤드가 붙어 컨테이너 쪽 MTU를 1450바이트 안팎으로 낮추는 것이 권장된다. VXLAN을 종단하는 지점이 VTEP이고 Swarm에서는 각 노드의 커널이 VTEP 역할을 한다.

### 4.2 컨트롤 플레인과 데이터 플레인의 분리

**한 줄 요약:** gossip(Serf·memberlist 계열)으로 "누가 어느 노드에 있는가"를 퍼뜨리고, 실제 패킷은 그 정보를 보고 VXLAN UDP 4789로 캡슐화해 보낸다.

- **컨트롤 플레인:** Swarm 노드들은 중앙 조정자 없이 gossip으로 서로의 존재·상태를 알린다. 어떤 태스크가 어느 노드에 있는지, 오버레이 Endpoint의 IP·MAC·그 노드의 실제 IP(VTEP 주소)가 클러스터에 전파된다. 이 정보가 있어야 커널이 "이 MAC으로 가는 프레임은 저 물리 IP의 노드로 캡슐화"하는 판단을 한다.
- **데이터 플레인:** 컨테이너 A → 다른 노드의 컨테이너 B 패킷은 로컬 오버레이 인터페이스로 들어가고, 전파된 정보를 참고해 목적지 노드 IP로 VXLAN 캡슐화되어 UDP 4789로 나간다. 상대 노드가 캡슐을 벗겨 원본 프레임을 오버레이 브리지를 통해 B의 veth로 전달한다. 애플리케이션 데이터는 gossip 메시지와 완전히 분리된 경로(VXLAN UDP)를 타므로 클러스터 규모가 커져도 패킷 전달 성능은 별도로 확장될 수 있다.

### 4.3 ingress 네트워크와 라우팅 메시

**한 줄 요약:** `--publish`된 포트는 태스크가 없는 노드를 포함해 **모든 노드**에서 열리고, 각 노드의 IPVS가 ingress 오버레이를 통해 실제 태스크가 있는 노드로 넘긴다 — 대가로 SNAT 때문에 원본 클라이언트 IP가 보존되기 어렵다.

Swarm에서 `docker service create --publish`(또는 `-p`)로 포트를 게시하면 클러스터의 모든 노드에서 리스닝한다. 이 라우팅 메시를 구현하는 특수 오버레이가 `ingress`이고 Swarm 초기화 시 자동 생성된다. 핵심은 각 노드 커널의 IPVS(IP Virtual Server, 리눅스 커널 내장 L4 로드밸런서)다. 노드 X의 8080으로 요청이 왔는데 태스크가 노드 Y에만 있다면, X는 IPVS 규칙에 따라 ingress 오버레이를 통해 Y의 컨테이너로 전달한다. 이때 출발지 주소는 ingress 내부 주소로 SNAT되므로 서비스 컨테이너는 어느 노드를 거쳤든 ingress 주소에서 온 것으로 본다. 따라서 **원본 클라이언트 IP 보존이 중요한 서비스**라면 이 제약을 감안해 설계한다.

| 구분 | 단일 컨테이너 `-p` | Swarm 라우팅 메시 |
|---|---|---|
| 요청을 받을 수 있는 노드 | 컨테이너가 실제 떠 있는 호스트뿐 | 클러스터의 모든 노드 |
| 로드밸런싱 | 없음 | IPVS 기반 VIP 로드밸런싱 |
| 사용 네트워크 | 로컬 브리지 | `ingress` 오버레이(VXLAN 캡슐화) |
| 노드 장애/스케일 대응 | 컨테이너가 죽으면 포트도 사라짐 | 태스크가 재스케줄되어도 게시 포트는 클러스터 전체에서 유효 |

핵심 차이는 "포트가 게시된 곳"과 "실제 처리하는 곳"의 분리 여부다. 라우팅 메시는 포트 매핑 + 오버레이 라우팅을 합친 상위 개념이다. (서비스 이름이 VIP/DNSRR로 풀리는 방식은 [9장](09-Docker-DNS와-서비스-디스커버리.md) 코어 4.)

### 4.4 2026년 현재 위상과 Swarm 없이 실습

**한 줄 요약:** Swarm은 deprecated가 아니고 유지보수 중이지만, Docker Engine 29의 실험적 nftables 백엔드는 Swarm 모드에서 켤 수 없다.

원천 서술(2026년 9월 기준)은 이렇다. Docker Swarm 모드는 deprecated가 아니며 공식 문서 어디에도 폐지 예정 표시가 없다. Mirantis가 엔터프라이즈 고객 대상 Swarm 장기 지원을 2030년까지 약속했다. 운영 복잡도를 낮게 유지하고 싶은 중소규모 환경에서는 여전히 실용적 선택지다. 다만 Swarm 오버레이가 필요로 하는 방화벽 규칙 세트가 아직 nftables로 마이그레이션되지 않아, **Swarm 모드가 활성화된 노드에서는 `--firewall-backend=nftables`를 켤 수 없다**. 당분간 Swarm 노드는 기존 iptables 기반 경로를 써야 한다([11장](11-Docker-방화벽-iptables에서-nftables로.md) 참조).

오버레이는 Swarm의 전유물이 아니다. libnetwork의 overlay 드라이버는 Swarm 클러스터 상태 관리와 별개 계층이라, `--attachable` 옵션을 붙이면 Swarm 서비스가 아닌 일반 `docker run` 컨테이너도 연결할 수 있다.

```bash
docker network create -d overlay --attachable demo-overlay
```

단일 호스트에서는 VXLAN 인터페이스가 생성되는 것까지만 볼 수 있고, 실제 호스트 간 캡슐화를 보려면 Swarm을 초기화하고 노드 두 대 이상을 조인해야 한다. 원천 실습 요지는 `docker swarm init`, `docker network create -d overlay --attachable demo-overlay`, 각 노드에서 컨테이너 실행 후 `docker exec c1 ping -c 3 c2`, `ip -d link show type vxlan`(`dstport 4789` 확인), `sudo tcpdump -i eth0 udp port 4789 -n -c 10`이다.

## 실무 적용

### 체크리스트

- [ ] NAT를 우회해야 하는 이유가 IP/MAC 의존 레거시·IP 단위 정책·conntrack 오버헤드 중 무엇인지 먼저 확인한다.
- [ ] macvlan 전: NIC/스위치/클라우드가 promiscuous·포트당 다중 MAC을 허용하는가? 아니면 ipvlan을 검토한다.
- [ ] 트렁크 환경: 부모를 `eth0.20`처럼 VLAN 서브인터페이스로 지정하고 스위치의 VLAN 설정과 일치시킨다(어긋나도 Docker는 오류를 안 낼 수 있으므로 스위치부터 확인).
- [ ] macvlan/ipvlan 컨테이너에 호스트에서 접근해야 한다면 `mv-shim` 같은 호스트용 서브인터페이스를 설계에 포함한다.
- [ ] host 모드는 포트 충돌과 호스트 방화벽 조작 가능성(`NET_ADMIN`)을 감수할 수 있는 신뢰 워크로드에만 쓴다.
- [ ] none 모드는 netns만 만들어 주고 구성은 외부 도구 몫임을 기억한다.
- [ ] Swarm 라우팅 메시는 원본 클라이언트 IP가 SNAT로 가려질 수 있다. 필요하면 설계에 반영한다.
- [ ] Swarm 노드에서는 nftables 백엔드를 켤 수 없다.

### 시나리오로 확인하기

1. **상황:** macvlan 네트워크(`192.168.10.0/24`)에 컨테이너 `192.168.10.101`을 띄웠다. 다른 PC에서는 접속되는데, 컨테이너가 도는 호스트에서 ping하면 응답이 없다.
   **질문:** 의심 부품, 확인, 해결은?

   <details markdown="1"><summary>답 확인</summary>

   설정 오류가 아니라 macvlan/ipvlan의 커널 구조적 제약이다(호스트 `eth0`와 서브인터페이스 사이에 분배 경로가 없다). 호스트에 같은 부모를 쓰는 macvlan 서브인터페이스를 만들어 우회한다: `ip link add mv-shim link eth0 type macvlan mode bridge`, `ip addr add 192.168.10.200/24 dev mv-shim`, `ip link set mv-shim up`. 삭제는 `ip link delete mv-shim`. → 코어 2

   </details>

2. **상황:** 퍼블릭 클라우드 인스턴스에서 macvlan 컨테이너를 만들었는데 아무 통신도 안 된다. Docker 쪽에는 오류가 없다.
   **질문:** 원인과 대안은?

   <details markdown="1"><summary>답 확인</summary>

   클라우드 가상 NIC가 소스/목적지 MAC 검사를 엄격히 적용해 macvlan의 여러 MAC 트래픽을 조용히 드롭한다(별도로 "소스/목적지 확인 비활성화" 등의 설정이 필요). MAC을 공유하는 ipvlan이 대안이며 이런 환경에서 훨씬 안정적이다. 온프레미스라면 스위치의 포트 보안/802.1X가 MAC 개수를 제한하는지 확인한다. → 코어 1 (1.2, 1.3)

   </details>

3. **상황:** 프록시 두 개를 `--network host`로 띄웠는데 두 번째가 실패한다. `-p 8080:80`도 줬는데 매핑이 안 보인다.
   **질문:** 원인은?

   <details markdown="1"><summary>답 확인</summary>

   host 모드는 netns를 공유하므로 포트 공간도 공유한다. 같은 포트를 listen하면 평범한 프로세스 두 개가 충돌하는 것과 같다. `-p`는 매핑할 대상 netns가 없어 무시되며 `docker ps`의 PORTS 칼럼도 비어 있다. 포트를 서로 다르게 설정하거나 브리지 모드로 돌아간다. → 코어 3 (3.1)

   </details>

### 2. 인출 질문

1. macvlan의 컨테이너 트래픽은 브리지 네트워크와 비교해 어떤 경로를 안 거치는가?

   <details markdown="1"><summary>답 확인</summary>

   veth 페어와 `docker0` 브리지를 거치지 않고, 호스트의 IP 스택(라우팅 테이블, iptables/nftables 체인)도 거치지 않는다. 부모 `eth0`가 수신하는 이더넷 프레임을 MAC 기준으로 각 서브인터페이스에 분배해 물리 네트워크로 직접 나간다. → 코어 1 (1.2)

   </details>

2. macvlan의 `vepa`와 802.1Q VLAN 트렁킹은 같은 것인가?

   <details markdown="1"><summary>답 확인</summary>

   아니다. vepa는 스위치의 반사(reflective relay) 지원이 필요한 표준 프로토콜 확장으로 같은 부모의 서브인터페이스 간 트래픽도 외부 스위치로 내보냈다가 되돌리게 한다. VLAN 트렁킹은 부모를 `eth0.20` 같은 VLAN 서브인터페이스로 구성하는 별개의 축이다. → 코어 1 (1.2)

   </details>

3. macvlan이 퍼블릭 클라우드에서 조용히 실패하는 이유와 ipvlan이 대안인 이유는?

   <details markdown="1"><summary>답 확인</summary>

   macvlan은 컨테이너마다 다른 MAC의 프레임을 보내는데, 클라우드 가상 NIC는 소스/목적지 MAC 검사로 자신에게 할당된 MAC 외 트래픽을 드롭한다. ipvlan은 부모 MAC을 공유하고 IP로 분배하므로 이 제약에서 자유롭다. → 코어 1 (1.2, 1.3)

   </details>

4. ipvlan L3 모드의 특징 세 가지는?

   <details markdown="1"><summary>답 확인</summary>

   (1) 부모 인터페이스가 사실상 라우터처럼 동작해 IP 기준으로 직접 라우팅한다. (2) 브로드캐스트·멀티캐스트가 전달되지 않아 DHCP 같은 브로드캐스트 의존 워크로드에 맞지 않고 고정 IP를 쓴다. (3) 같은 부모의 L3 컨테이너끼리는 서로 다른 서브넷이어도 외부 라우터 없이 통신하며, 게이트웨이를 지정하지 않는 경우가 많다. → 코어 1 (1.3)

   </details>

5. 호스트에서 macvlan 컨테이너로 ping이 안 되는 이유와 해결책은?

   <details markdown="1"><summary>답 확인</summary>

   서브인터페이스에서 나간 패킷이 같은 물리 인터페이스로 되돌아 들어오는 경로가 커널에 만들어지지 않기 때문이다(bridge 모드든 L2 모드든 동일한 설계상 한계). 호스트에 같은 부모의 macvlan 서브인터페이스(`mv-shim`)를 만들고 컨테이너와 같은 대역 IP를 주면 통신된다. ipvlan도 같은 원리다. → 코어 2

   </details>

6. host 모드의 이점과 대가 두 가지는?

   <details markdown="1"><summary>답 확인</summary>

   이점: veth·브리지·conntrack NAT 단계가 사라져 지연·처리량이 좋다. 대가: (1) 포트 공간 공유로 같은 포트를 listen하면 충돌한다. (2) 격리 약화 — 호스트의 모든 인터페이스·라우팅에 접근하고 `NET_ADMIN`과 결합되면 호스트 방화벽 규칙까지 조작할 수 있다. → 코어 3 (3.1)

   </details>

7. none 모드의 두 가지 쓰임은?

   <details markdown="1"><summary>답 확인</summary>

   (1) 네트워크가 필요 없는 순수 배치 작업의 공격 표면 축소. (2) Docker 기본 드라이버가 아닌 네트워킹(CNI 플러그인, SR-IOV 등)을 외부 도구가 컨테이너 netns에 수동으로 붙이는 패턴. 이때 Docker는 netns만 만든다. → 코어 3 (3.2)

   </details>

8. VXLAN의 VNI, 포트, MTU 관련 숫자를 말하라.

   <details markdown="1"><summary>답 확인</summary>

   VNI는 24비트(약 1,600만 개 논리 네트워크), 캡슐화 UDP 목적지 포트 4789(RFC 7348), 캡슐화 오버헤드는 50바이트 안팎이라 컨테이너 쪽 MTU를 1450바이트 안팎으로 낮추는 것이 권장된다. → 코어 4 (4.1)

   </details>

9. 라우팅 메시에서 태스크가 없는 노드로 온 요청이 처리되는 과정과 부작용은?

   <details markdown="1"><summary>답 확인</summary>

   게시된 포트는 모든 노드에서 listen하고, 그 노드의 IPVS 규칙이 ingress 오버레이를 통해 실제 태스크가 있는 노드의 컨테이너로 전달한다. 이때 출발지가 ingress 내부 주소로 SNAT되어 서비스 컨테이너가 원본 클라이언트 IP를 보존하기 어렵다. → 코어 4 (4.3)

   </details>

10. 2026년 현재 Swarm의 상태와 nftables 백엔드와의 관계는?

    <details markdown="1"><summary>답 확인</summary>

    deprecated가 아니고 유지보수 중이며 Mirantis가 엔터프라이즈 지원을 2030년까지 약속했다. 그러나 Swarm 오버레이 규칙이 아직 nftables로 마이그레이션되지 않아 Swarm 모드 노드에서는 `--firewall-backend=nftables`를 켤 수 없다. → 코어 4 (4.4)

    </details>

### 3. 기억 고리

- **C++ 유추:** macvlan = NIC를 하나 더 꽂은 서버(고유 MAC), ipvlan = NIC 하나에 별칭 IP를 여러 개 단 서버. ⚠️ 둘 다 같은 호스트와는 직접 통신 불가라는, 일반 NIC 별칭에는 없는 제약이 있다.
- **C++ 유추:** host 모드 = 서버를 물리 서버에서 직접 실행. ⚠️ 네트워크만 공유할 뿐 나머지 격리는 유지된다.
- **비유:** 아파트 단지. 브리지 = 단지 대표 번호(NAT)로 통화, macvlan = 세대마다 직통 번호와 별도 회선, ipvlan = 한 회선에 내선 번호 여러 개, host = 관리실 전화기를 세대가 같이 쓰기, none = 전화선 철거. ⚠️ 비유가 깨지는 지점: macvlan/ipvlan 세대는 바로 옆 관리실(호스트)과는 직통이 안 되어 "관리실 전용 직통 회선"(`mv-shim`)을 하나 더 깔아야 한다.
- **묶음(3의 법칙):** NAT 우회 이유 3(IP/MAC 의존 · IP 단위 정책 · conntrack 오버헤드) / 네임스페이스 3유형(분리+NAT: bridge·overlay, 분리+NAT 없음: macvlan·ipvlan, 비분리/루프백만: host·none) / 오버레이 3요소(VNI · UDP 4789 · MTU 오버헤드).
- **대칭·순서:** macvlan(MAC으로 분배, MAC 개수 제한에 취약) ↔ ipvlan(IP로 분배, MAC 공유). host(netns 포기) ↔ none(netns만 남기고 전부 제거). 오버레이는 컨트롤(gossip) → 데이터(VXLAN) 순서.

### 4. 가르치기 · 반대편 서기

- **거울 설명 (1분, 원고 없이):** "macvlan 컨테이너는 외부와는 통신되는데 호스트와는 안 되는 이유와 우회법"을 처음 듣는 사람에게 설명해 보세요. 말이 막히는 지점 = 지식의 구멍.
- **C++ 서버 동료에게 설명하기:** "host 모드에서 두 번째 서버가 `bind`에 실패하는 것"을 `EADDRINUSE`와 연결해 설명해 보세요.
- **랜덤 논리 게임:** A "클라우드에서도 macvlan을 쓰자" vs B "ipvlan이 안전하다" — 번갈아 변호하세요. (MAC 검사, promiscuous, CAM 테이블, 브로드캐스트/DHCP를 근거로)
