# 8장. 브리지 네트워크와 포트 게시

> **🎮 게임 서버 개발자에게** — 게임 서버가 `bind()`/`listen()`한 포트로 클라이언트가 붙던 구조가, 컨테이너 세계에서는 "컨테이너마다 독립된 네트워크 스택 + 가상 케이블(veth) + 가상 스위치(브리지) + 커널 NAT"로 바뀐다. 결정적으로 다른 점은 컨테이너 안에서 80번을 `listen`한 소켓은 **컨테이너 자기 네임스페이스 안의 소켓일 뿐**이라는 것이다. 외부 접속은 `-p`가 만든 iptables DNAT 규칙이 목적지를 바꿔 줘야 들어오고(기본 경로), 그 사이에는 어떤 프로세스도 없을 수 있다(보완용 `docker-proxy`가 호스트 포트를 대신 bind하는 경우는 코어 3). 서버끼리는 IP 대신 **컨테이너 이름**으로 찾는다. 이 장은 [4장](../1부-리눅스-네트워크-기초/04-veth-브리지-라우팅-ARP.md)의 veth·브리지와 [5장](../1부-리눅스-네트워크-기초/05-netfilter-iptables-NAT-conntrack.md)의 NAT가 Docker에서 합쳐지는 지점이다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 개발용 DB를 `-p 5432:5432`로 열고 `ufw`로 막았다고 믿었는데 외부에서 접속된다.
> - 클라이언트 접속이 `호스트IP:8080`으로 들어와 컨테이너의 80번까지 어떤 경로로 가는지 따져야 하는 장애 분석.
> - 두 컨테이너가 이름으로 서로를 못 찾는데 `--network` 없이 띄워 기본 브리지에 붙은 상황.

## 코어 — 이것만은 100%

> **한 문장:** 컨테이너는 veth pair로 호스트 브리지에 꽂혀 같은 브리지 안에서는 L2 스위칭(NAT 없음)으로, 밖으로는 라우팅 + MASQUERADE로 통신하고, 밖에서 들어오는 `-p` 트래픽은 PREROUTING의 DNAT로 라우팅 결정 전에 목적지가 바뀌어 컨테이너에 도착하며(응답은 conntrack이 되돌림), 게시된 포트에는 호스트 방화벽보다 Docker 규칙이 먼저 적용된다.

1. **사용자 정의 브리지를 쓴다** — 기본 브리지(`docker0`)는 자동 DNS가 없고 모든 컨테이너가 평평한 한 공간이다. 사용자 정의 브리지는 이름·별칭 통신과 네트워크 간 격리를 준다.
2. **veth로 꽂고, 안은 스위칭·밖은 NAT** — veth pair 한쪽은 컨테이너 `eth0`, 다른 쪽은 호스트에 남아 브리지에 연결된다. 같은 브리지 안은 MAC 주소 테이블(FDB)로 L2 전달, 외부로는 게이트웨이 → IP 포워딩 → MASQUERADE(`POSTROUTING`).
3. **들어오는 길은 PREROUTING DNAT** — `-p`는 `DOCKER` 체인의 DNAT 규칙(커널)과 `docker-proxy`(사용자 공간 보완 프로세스) 두 메커니즘의 결과다. 경로는 PREROUTING → DNAT → 라우팅 결정 → FORWARD → docker0 → veth → eth0.
4. **방화벽과의 상호작용을 안다** — Engine 28부터 게시하지 않은 포트로의 인바운드는 기본 차단되지만, 게시된 포트에는 여전히 Docker 규칙이 호스트 방화벽보다 먼저다.

**이 장의 학습 목표**

- 기본 브리지와 사용자 정의 브리지의 차이(DNS·격리)와 실무 권고를 설명할 수 있다.
- veth pair로 컨테이너와 호스트 브리지가 이어지는 구조를 그리고, `eth0@ifN`으로 짝을 찾을 수 있다.
- 컨테이너 간 통신(스위칭)과 외부 통신(라우팅 + NAT)이 다른 계층의 동작임을 설명할 수 있다.
- `-p 8080:80`의 인바운드 경로를 PREROUTING부터 컨테이너까지 순서대로 말할 수 있다.
- `docker-proxy`와 `userland-proxy: false`의 의미, hairpin NAT, Engine 28의 방화벽 동작을 안다.

## 코어 1. 사용자 정의 브리지를 쓴다

### 1.1 기본 브리지와 사용자 정의 브리지

**한 줄 요약:** 겉보기엔 같은 리눅스 브리지지만, 사용자 정의 브리지만 이름 통신(자동 DNS)과 네트워크 간 격리를 준다.

Docker를 설치하면 별다른 설정 없이도 `docker0`이라는 리눅스 브리지 디바이스가 하나 만들어져 있다. `docker run`에서 `--network`를 지정하지 않은 컨테이너는 기본적으로 이 `docker0`, 즉 CNM 상의 `bridge`라는 이름의 기본 Network에 연결된다([7장](07-Docker-네트워크-모델.md)). 반면 `docker network create -d bridge my-net`처럼 직접 만든 브리지를 **사용자 정의 브리지**라고 부른다.

| 구분 | 기본 브리지 (`docker0`) | 사용자 정의 브리지 |
|---|---|---|
| 이름으로 통신(자동 DNS) | 지원하지 않음. `--link` 같은 레거시 옵션이나 IP 직접 사용 | 컨테이너 이름 또는 `--network-alias` 별칭을 호스트 이름처럼 사용 |
| 네트워크 간 격리 | 연결된 컨테이너가 모두 서로 통신 가능한 평평한(flat) 공간 | 서로 다른 사용자 정의 브리지의 컨테이너는 `docker network connect`로 명시 연결하지 않는 한 격리 |

사용자 정의 네트워크마다 Docker가 내장 DNS 서버(embedded DNS)를 자동으로 구동하고 각 컨테이너의 `/etc/resolv.conf`가 그것을 가리키도록 구성하기 때문이다(상세는 [9장](09-Docker-DNS와-서비스-디스커버리.md)). 이 장에서는 "기본 브리지는 DNS 기반 자동 탐색이 없고 사용자 정의 브리지는 있다"는 실무적 차이만 기억하면 충분하다. 그래서 실무 가이드는 거의 예외 없이 **기본 브리지를 그대로 쓰지 말고 프로젝트마다 사용자 정의 브리지를 만들라**고 권하고, Docker Compose가 프로젝트마다 전용 네트워크를 자동 생성하는 것도 같은 이유다.

```bash
docker network create mynet
docker run -d --name api --network mynet myapp:latest
docker run --rm --network mynet alpine ping -c1 api    # 컨테이너 이름 api로 통신
```

> **[보충]** 위 `ping` 예시는 이름 통신을 보여 주려고 이 책이 구성한 예이며 원천(docker 12)에 있는 명령은 아니다. 원천은 `docker network create -d bridge my-net` 형태만 보여 준다.

## 코어 2. veth로 꽂고, 안은 스위칭·밖은 NAT

### 2.1 veth pair — 컨테이너와 호스트를 잇는 가상 케이블

**한 줄 요약:** veth pair의 한쪽 끝은 컨테이너 네임스페이스의 `eth0`(CNM의 Endpoint), 다른 쪽은 호스트에 남아 브리지에 연결된다.

veth(virtual ethernet) pair는 항상 쌍으로 생성되는 가상 인터페이스로, 한쪽 끝으로 들어간 패킷이 물리 케이블로 연결된 것처럼 다른 끝으로 그대로 나온다. Docker는 컨테이너를 브리지 네트워크에 연결할 때 veth pair를 만들어 **한쪽 끝은 컨테이너의 네트워크 네임스페이스로 옮기고**(컨테이너 안에서 `eth0`), **다른 쪽은 호스트의 기본 네임스페이스에 남겨 브리지 디바이스에 연결**한다.

```
[ 호스트 네트워크 네임스페이스 ]                [ 컨테이너 네트워크 네임스페이스 ]

   docker0 (브리지)
       │
       ├── vethXXXXXXX@if5  ◄──── veth pair ────►  eth0@if6
       │   (호스트 쪽 끝, 브리지에 연결)               (컨테이너 쪽 끝, CNM의 Endpoint)
       │
       └── vethYYYYYYY@if7  ◄──── veth pair ────►  eth0@if8  (다른 컨테이너)
```

CNM 용어로 컨테이너 쪽 끝(`eth0`)이 Endpoint이고, 호스트 쪽 끝(`vethXXXXXXX`)이 브리지라는 Network 실체에 연결되는 접점이다. 직접 확인할 수 있다.

```bash
# 컨테이너 안에서 인터페이스 번호 확인
docker exec web ip link show eth0
# 예: 6: eth0@if7: <BROADCAST,MULTICAST,UP,LOWER_UP> ...

# 호스트에서 브리지에 연결된 veth 목록 확인
ip link show type veth
bridge link show
```

`eth0@if7`의 `@if` 뒤 숫자는 veth pair의 반대쪽 끝이 호스트 네임스페이스에서 갖는 **인터페이스 인덱스**다. 호스트에서 `ip link show`로 같은 인덱스를 가진 인터페이스가 이 컨테이너와 짝을 이루는 veth의 호스트 쪽 끝이다. 전통적으로는 `brctl show docker0`을 썼지만 `brctl`은 오래된 `bridge-utils` 패키지 소속이라 최근 배포판에는 기본 설치되지 않는 경우가 많고, 요즘은 iproute2의 `bridge link show` 또는 `bridge fdb show br docker0`을 쓴다.

> **[보충]** 이미지에 `ip` 명령이 없어 `docker exec web ip ...`가 실패하는 경우의 대안(호스트 도구로 컨테이너 네트워크 네임스페이스 안을 보는 `nsenter`)은 원천 docker 12가 아니라 [3장](../1부-리눅스-네트워크-기초/03-네트워크-네임스페이스.md)의 네임스페이스 개념에서 이어 붙인 이 책의 설명이다.

### 2.2 통신 경로: 컨테이너 간 vs 외부

**한 줄 요약:** 같은 브리지 안은 L2 스위칭(라우팅·NAT 없음), 외부로는 라우팅 + 출발지를 호스트 IP로 바꾸는 MASQUERADE.

| 통신 | 경로 | 계층 |
|---|---|---|
| 같은 브리지 안의 컨테이너 ↔ 컨테이너 | veth → 브리지가 MAC 주소 테이블(FDB, Forwarding Database)로 전달 → 상대 veth | L2 스위칭 (라우팅·NAT 없음) |
| 컨테이너 → 외부(인터넷 등) | 컨테이너 라우팅 테이블의 기본 게이트웨이(브리지 IP, 예: `docker0`의 172.17.0.1) → 커널 IP 포워딩 → 출발지 IP를 호스트의 외부 인터페이스 IP로 치환(MASQUERADE) | 라우팅 + NAT |

컨테이너 A가 컨테이너 B의 IP로 패킷을 보내면 veth pair를 통해 브리지로 들어오고, 브리지는 학습한 MAC 주소 테이블(FDB)을 참고해 해당 프레임을 B의 veth 쪽으로 그대로 전달한다. 리눅스 브리지가 하는 일은 물리 이더넷 스위치와 개념적으로 같고, 같은 네트워크 안에서는 IP 계층보다 아래인 L2에서 통신이 끝난다. 반면 목적지가 같은 브리지 대역 밖이면 패킷은 브리지가 아니라 컨테이너의 기본 게이트웨이를 거쳐 커널의 IP 포워딩 경로로 올라가고, `nat` 테이블 `POSTROUTING` 체인의 MASQUERADE 규칙이 출발지를 호스트 IP로 바꾼다. 이것이 **아웃바운드 NAT**다. 정리하면 같은 브리지 내부는 "스위칭", 외부로 나가는 통신은 "라우팅 + NAT"이다.

```bash
# Docker가 만들어 둔 마스커레이딩 규칙 확인
iptables -t nat -L POSTROUTING -n -v | grep -i MASQUERADE
```

## 코어 3. 들어오는 길은 PREROUTING DNAT

### 3.1 포트 게시(`-p`)의 두 메커니즘

**한 줄 요약:** 기본 경로는 커널의 iptables DNAT이고, `docker-proxy`는 hairpin 같은 경우를 보완하는 사용자 공간 프로세스다.

`docker run -p 8080:80 nginx`는 호스트의 8080으로 들어온 트래픽을 컨테이너의 80으로 전달한다. 두 개의 서로 다른 메커니즘이 함께 작동한 결과다.

**① iptables DNAT 규칙.** Docker는 컨테이너를 포트 게시와 함께 실행할 때 `nat` 테이블에 `DOCKER` 체인을 만들고(정확히는 최초 실행 시 만들어 둔 체인을 재사용), "호스트 8080으로 들어오는 패킷의 목적지를 컨테이너 IP:80으로 바꿔라"는 DNAT 규칙을 추가한다. `PREROUTING`(호스트 자신에서 접속하는 경우를 위해 `OUTPUT`에서도)이 `DOCKER` 체인으로 점프하도록 연결되어 있어서, 호스트로 들어오는 모든 패킷은 라우팅 결정 전에 이 DNAT 규칙을 거친다. 이렇게 도착한 패킷은 목적지가 컨테이너 IP로 바뀐 채 `FORWARD` 체인을 거쳐 브리지로 들어간다. **별도의 사용자 공간 프로세스가 개입하지 않는 순수한 커널 NAT 경로**다.

**② `docker-proxy`.** 포트를 게시할 때마다 dockerd는 호스트의 게시 포트를 직접 bind해 리스닝하는 `docker-proxy` 프로세스를 하나씩 띄운다(원천 12.4). 호스트 포트로 들어온 연결을 받아 컨테이너의 IP:포트로 그대로 중계(relay)하는 단순한 TCP/UDP 프록시다. 순수 커널 NAT 경로만으로는 깔끔하게 처리되지 않는 상황, 대표적으로 호스트 자신이 루프백(`127.0.0.1`)으로 자기가 게시한 포트에 접속하는 경우(hairpin NAT라 부르는 상황)나 특정 네트워크 구성에서 IPv6 처리가 얽히는 경우를 보완하는 안전판이다.

이 이중 구조는 `--userland-proxy` 데몬 옵션으로 제어한다. 기본값은 활성화(`true`)이며, `/etc/docker/daemon.json`으로 끈다.

```json
{
  "userland-proxy": false
}
```

```bash
# 설정 반영 후 데몬 재시작
sudo systemctl restart docker
```

끄면 `docker-proxy` 프로세스가 뜨지 않고 포트 게시는 오직 iptables(또는 nftables) 기반 커널 NAT 경로로만 처리된다. 대부분의 표준 사용 패턴에서는 문제없고 호스트당 게시 포트가 많은 환경에서는 프로세스 수를 줄여 리소스를 절약할 수 있지만, hairpin NAT류의 특수 시나리오에서 차이가 날 수 있다. **끄기 전에 실제로 필요한 접근 경로(특히 호스트 자신의 루프백을 통한 접근)를 점검**한다.

```bash
# 현재 떠 있는 docker-proxy 프로세스와 게시 포트의 대응 확인
ps -ef | grep docker-proxy | grep -v grep
# 예: docker-proxy -proto tcp -host-ip 0.0.0.0 -host-port 8080 -container-ip 172.17.0.2 -container-port 80
```

> **[보충]** 원천 두 장의 서술이 완전히 같지 않다. docker 12.4는 포트를 게시할 때마다 `docker-proxy`가 하나씩 뜨고 기본값이 활성화라고 설명하는 반면, docker 15.4는 기본 경로가 커널 DNAT이며 과거에는 `docker-proxy`가 hairpin 등 일부를 대신 중계했지만 최근 배포판에서는 hairpin도 대부분 커널 DNAT만으로 처리된다고 쓴다. 이 책은 두 설명을 합쳐 "기본 경로는 커널 DNAT, `docker-proxy`는 보완용"까지만 확정하고, 현재 환경에서 `docker-proxy`가 얼마나 관여하는지는 위 `ps` 명령으로 직접 확인하게 한다. 또 hairpin의 정의도 12.4는 "호스트가 루프백으로 자기 게시 포트에 접속", 15.4는 "컨테이너가 자기가 게시한 포트를 호스트 주소로 되돌아 접속"으로 쓰는 등 초점이 다르다(3.3절). 서술이 다른 부분은 더 상세한 15장 쪽을 기준으로 삼았다.

### 3.2 인바운드 패킷 경로

**한 줄 요약:** PREROUTING(DNAT) → 라우팅 결정 → FORWARD → docker0 → veth → eth0, 응답은 conntrack이 되돌린다.

```
(외부에서 온 패킷, dst=host_ip:8080)
        │
        ▼
PREROUTING (nat 테이블) ── DOCKER 체인으로 점프
        │
        ▼
DNAT: dst를 container_ip:80 으로 변경
        │
        ▼
라우팅 결정 (목적지가 이제 컨테이너 IP이므로 docker0 브리지 방향으로)
        │
        ▼
FORWARD 체인 (filter 테이블) ── 정책에 따라 ACCEPT/DROP 판단
        │
        ▼
docker0 브리지 → veth(호스트 쪽) → veth(컨테이너 쪽)
        │
        ▼
컨테이너 네트워크 네임스페이스 안의 eth0:80 (nginx 프로세스가 accept)
```

DNAT가 이루어지는 시점이 라우팅 결정보다 앞선 `PREROUTING` 단계라는 점이 중요하다. 커널은 목적지를 컨테이너 IP로 바꾼 **뒤에** "이 패킷을 어디로 보낼지"를 다시 판단하고, 그 결과 docker0 쪽으로 라우팅된다. 응답 패킷은 conntrack이 기억한 연결 정보로 자동으로 주소가 되돌려지므로(un-DNAT), 클라이언트는 항상 자신이 접속한 `host_ip:8080`만 본다([5장](../1부-리눅스-네트워크-기초/05-netfilter-iptables-NAT-conntrack.md)).

실제 규칙을 눈으로 확인한다. 포트를 게시한 컨테이너를 띄운 뒤 `iptables-save`로 `nat` 테이블을 덤프한다.

```bash
docker run -d --name web -p 8080:80 nginx:latest

# nat 테이블 전체를 텍스트로 덤프
iptables-save -t nat | grep -i docker
```

출력에는 `DOCKER` 체인이 정의되어 있고 그 안에 `-p tcp --dport 8080 -j DNAT --to-destination 172.17.0.2:80`과 비슷한 규칙이 보일 것이다. `PREROUTING`과 (호스트 자신에서 접속하는 경우를 위한) `OUTPUT` 양쪽에서 이 `DOCKER` 체인으로 점프하는 규칙도 함께 확인된다. iptables가 nftables 백엔드(`iptables-nft`)로 동작하는 배포판이라면 같은 규칙을 `nft list ruleset | grep -A 5 -i docker`로도 볼 수 있다. `--firewall-backend=nftables`로 Docker 자체의 실험적 nftables 백엔드를 켠 환경에서는 규칙 구조 자체가 `iptables`/`DOCKER` 체인 방식과 다른 형태(Docker 전용 네임스페이스로 분리된 테이블)로 나타난다([11장](11-Docker-방화벽-iptables에서-nftables로.md)).

### 3.3 hairpin NAT — 자기 자신의 게시 포트로 접속할 때

**한 줄 요약:** 나갔던 인터페이스로 되돌아 들어오는 경로는 커널 NAT가 항상 매끄럽게 처리하지 못했고, 지금은 대부분 처리되지만 오래된 커널·브리지 netfilter 비활성화 환경에서는 어긋날 수 있다.

컨테이너 A가 자기가 게시한 포트를 호스트의 공인 IP나 게시 주소로 되돌아 들어오는 경로로 접속하려는 경우다. 예를 들어 컨테이너 안 스크립트가 설정 파일의 `http://<호스트의_외부_IP>:18080`을 그대로 써서 자기 자신에게 요청을 보내는 상황이다. 요청은 컨테이너의 veth로 나가 docker0를 거쳐 DNAT를 받고 다시 같은 컨테이너로 돌아와야 한다. 이렇게 나갔던 인터페이스로 되돌아 들어오는 경로를 hairpin(헤어핀) NAT라고 한다.

- 과거에는 `docker-proxy`가 커널 DNAT를 우회해 사용자 공간에서 루프백 트래픽을 직접 중계하는 방식으로 해결하기도 했다.
- 오늘날에는 커널의 브리지 netfilter 훅과 conntrack이 개선되어 대부분의 최신 배포판에서 hairpin 트래픽도 커널 DNAT만으로 정상 처리된다.
- 아주 오래된 커널이거나 브리지 netfilter가 비활성화된 환경에서는 여전히 어긋날 수 있다.
- 가장 간단하고 확실한 회피책은 컨테이너가 자기 자신을 호출해야 하는 상황 자체를 피하고, 컨테이너 이름이나 `localhost`로 접근하도록 설계를 바꾸는 것이다.

### 3.4 단일 호스트 `-p` vs Swarm 라우팅 메시

**한 줄 요약:** 포트가 게시된 곳과 요청을 처리하는 곳이 항상 같은 호스트인가(단일 호스트) 분리되는가(라우팅 메시)가 핵심 차이다.

Swarm에서 `docker service create --publish published=8080,target=80`으로 서비스를 게시하면 명령은 비슷해 보여도 내부는 상당히 다르다. 특수한 `ingress` 오버레이 네트워크(VXLAN 캡슐화)와 라우팅 메시가 관여하기 때문이다([6장](../1부-리눅스-네트워크-기초/06-오버레이-VXLAN-MTU.md), [10장](10-macvlan-ipvlan-host-none-오버레이.md)).

| 구분 | 단일 컨테이너 포트 매핑 (`docker run -p`) | Swarm ingress 라우팅 메시 (`docker service --publish`) |
|---|---|---|
| 요청을 받을 수 있는 노드 | 해당 컨테이너가 실제로 떠 있는 호스트뿐 | 클러스터의 모든 노드(태스크가 그 노드에 없어도 가능) |
| DNAT 대상 결정 | 항상 그 호스트의 특정 컨테이너 IP로 고정 | 어느 노드로 들어오든 ingress 네트워크를 통해 실제 태스크가 떠 있는 노드로 재전달 |
| 로드밸런싱 | 없음 | IPVS 기반 VIP 로드밸런싱으로 여러 태스크에 분산 |
| 사용되는 네트워크 | 로컬 브리지(docker0 또는 사용자 정의 브리지) | 특수한 `ingress` 오버레이 네트워크 |
| 노드 장애/스케일 변화 | 컨테이너가 죽으면 포트도 사라짐 | 태스크가 다른 노드로 재스케줄되어도 게시 포트는 클러스터 전체에서 유효 |

라우팅 메시는 "포트 매핑 + 오버레이 네트워크 라우팅"을 합친 상위 개념이라고 볼 수 있다.

## 코어 4. 방화벽과의 상호작용을 안다

### 4.1 Engine 28 — 게시하지 않은 포트의 기본 차단

**한 줄 요약:** Engine 28부터 미게시 포트 인바운드는 기본 차단되지만, 게시된 포트에는 여전히 Docker 규칙이 호스트 방화벽보다 먼저 적용된다.

오랫동안 유명한 문제가 있었다. Docker가 포트를 게시하면서 iptables의 `FORWARD` 체인에 직접 규칙을 끼워 넣다 보니 관리자가 `ufw`나 `firewalld`로 인바운드 규칙을 걸어 두어도 Docker 규칙이 먼저 평가되어 방화벽 정책을 사실상 우회하는 것이다. `ufw deny`로 막은 포트가 컨테이너가 게시하는 순간 외부에서 접근 가능해지는 직관에 어긋나는 상황이 반복 보고되었다.

Docker Engine 28부터는 이 문제를 상당 부분 완화하도록 기본 동작이 바뀌었다. `-p`/`--publish`로 열지 않은 컨테이너 포트로 들어오는 인바운드 트래픽을 컨테이너 IP 기준으로 기본 차단한다. iptables 기반이며 리눅스 환경에 한정되고, VM 계층을 쓰는 Docker Desktop(macOS/Windows)에는 해당하지 않는다. 이전에는 게시하지 않은 포트라도 같은 브리지 대역에 도달할 수 있는 경로(같은 LAN, 컨테이너 IP를 아는 내부 사용자)만 있으면 사실상 열려 있는 것과 마찬가지인 경우가 많았는데, 이제는 게시 여부가 방화벽 수준에서도 의미를 갖는다.

다만 문제 전체가 해소된 것은 아니다. Docker가 `FORWARD` 체인 등 호스트 방화벽 도구가 관리하는 것과 같은 iptables 테이블에 자신의 규칙을 직접 삽입하는 구조는 유지되고, **게시된 포트에는 여전히 Docker의 규칙이 우선 적용된다.** "게시하지 않은 포트가 기본적으로 안전해졌다"는 것이지 "Docker가 호스트 방화벽 규칙 체계에 완전히 순응한다"는 뜻이 아니다. 이 구조를 다시 설계하려는 시도가 Docker Engine 29의 실험적 nftables 백엔드이며 [11장](11-Docker-방화벽-iptables에서-nftables로.md)에서 다룬다.

> **[보충]** `-p 8080:80`처럼 호스트 주소를 생략하면 호스트의 모든 인터페이스(0.0.0.0)에 게시되어 외부에서도 접속된다. 내 PC에서만 쓸 포트는 `-p 127.0.0.1:5432:5432`처럼 루프백에만 묶는 편이 안전하다는 설명은 원천(docker 12)에 없고 이 책이 덧붙인 실무 조언이다. 원천이 보여 주는 `docker-proxy` 예시의 `-host-ip 0.0.0.0`은 호스트 쪽 게시 주소 개념이 있다는 간접 근거일 뿐이다.

## 실무 적용

### 체크리스트

- [ ] 기본 브리지(`docker0`)는 이름 기반 자동 DNS가 없고 평평한 한 공간이다. 프로젝트마다 사용자 정의 브리지를 쓴다.
- [ ] veth pair: 컨테이너 쪽 `eth0@ifN` ↔ 호스트 쪽 `vethXXXX`(브리지에 연결). 짝은 `ip link show type veth`·`bridge link show`로 찾는다(구 `brctl show`).
- [ ] 같은 브리지 안은 L2 스위칭(FDB, NAT 없음), 외부는 기본 게이트웨이 → IP 포워딩 → MASQUERADE(`POSTROUTING`).
- [ ] `-p`는 `DOCKER` 체인 DNAT(PREROUTING, 라우팅 결정 전)와 보완용 `docker-proxy`다. 경로: PREROUTING → DNAT → 라우팅 → FORWARD → docker0 → veth → eth0.
- [ ] `iptables-save -t nat | grep -i docker`로 `DNAT --to-destination <컨테이너IP>:<포트>`를 확인하고 `ps -ef | grep docker-proxy`로 프록시 관여 여부를 확인한다.
- [ ] `"userland-proxy": false`로 끄기 전에 호스트 루프백 접근 등 필요한 경로를 점검한다.
- [ ] 게시된 포트에는 호스트 방화벽보다 Docker 규칙이 먼저다. Engine 28+의 기본 차단은 **미게시** 포트에만 해당한다.
- [ ] 컨테이너가 자기 게시 포트를 호스트 주소로 호출하는 설계를 피하고 컨테이너 이름이나 `localhost`를 쓴다.

   **질문:** 왜 막히지 않았고 어떻게 했어야 하나?

   <details markdown="1"><summary>답 확인</summary>

   게시된 포트에는 `ufw` 같은 호스트 방화벽 규칙보다 Docker가 `FORWARD` 등에 넣은 규칙이 먼저 평가된다. Engine 28의 기본 차단은 **게시하지 않은** 포트에만 해당한다. 외부 접근이 필요 없다면 게시 자체를 하지 않는다. 방화벽만 믿지 않는다. (게시 주소를 루프백으로 제한하는 `-p 127.0.0.1:5432:5432` 형태는 코어 4의 [보충]에서 밝혔듯 원천에 없는 이 책의 실무 조언이다.) → 코어 4 (4.1)

   </details>

2. **상황:** 외부 클라이언트가 `호스트IP:8080`으로 접속하는 nginx 컨테이너(`-p 8080:80`)의 패킷 경로를 장애 보고서에 적어야 한다. 동료는 "dockerd가 8080을 listen해서 받아 넘겨 준다"고 쓴다.
   **질문:** 정확한 경로는?

   <details markdown="1"><summary>답 확인</summary>

   기본 경로는 커널이다. `nat` 테이블 `PREROUTING` → `DOCKER` 체인 점프 → DNAT로 목적지를 `컨테이너IP:80`으로 변경 → 라우팅 결정(docker0 방향) → `FORWARD`(filter) → docker0 → veth → 컨테이너 `eth0:80`. 응답은 conntrack이 주소를 되돌려 클라이언트는 `호스트IP:8080`만 본다. `docker-proxy`는 hairpin NAT 같은 경우의 보완용이며 실제 관여 여부는 `ps -ef | grep docker-proxy`로 확인한다. → 코어 3 (3.1, 3.2)

   </details>

3. **상황:** 컨테이너 안 스크립트가 설정 파일의 `http://<호스트_외부_IP>:18080`(자기 자신이 게시한 포트)으로 요청을 보내는데 오래된 호스트에서만 응답이 없다.
   **질문:** 의심 부품과 해결은?

   <details markdown="1"><summary>답 확인</summary>

   hairpin NAT 경로다. 패킷이 나갔던 인터페이스로 되돌아 들어와야 하는데, 아주 오래된 커널이거나 브리지 netfilter가 비활성화된 환경에서는 커널 DNAT만으로 어긋날 수 있다. 가장 확실한 해결은 자기 자신을 호스트 주소로 호출하는 설계를 없애고 컨테이너 이름이나 `localhost`로 접근하게 바꾸는 것이다. → 코어 3 (3.3)

   </details>

4. **상황:** 컨테이너 두 개를 `--network` 없이 띄웠더니 서로 이름으로 접속이 안 된다.
   **질문:** 원인과 올바른 구성은?

   <details markdown="1"><summary>답 확인</summary>

   `--network`를 지정하지 않으면 기본 브리지(`docker0`)에 붙고, 기본 브리지에는 자동 DNS가 없다. `docker network create`로 사용자 정의 브리지를 만들고 두 컨테이너를 같은 네트워크에 붙이면 컨테이너 이름이나 `--network-alias`로 접속할 수 있다. Compose는 프로젝트마다 전용 네트워크를 자동 생성한다. → 코어 1 (1.1)

   </details>

### 2. 인출 질문

1. 기본 브리지에서는 컨테이너 이름으로 통신이 안 되는데 사용자 정의 브리지에서는 되는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   Docker가 사용자 정의 네트워크마다 내장 DNS 서버를 구동하고 각 컨테이너의 `/etc/resolv.conf`가 그것을 가리키게 하기 때문이다. 기본 브리지는 그런 자동 DNS가 없어 `--link` 같은 레거시 옵션이나 IP 직접 사용만 가능했다. → 코어 1 (1.1)

   </details>

2. 같은 브리지 안의 두 컨테이너 통신에 NAT가 개입하는가? 외부로 나갈 때는?

   <details markdown="1"><summary>답 확인</summary>

   같은 브리지 안은 NAT도 라우팅도 없다. veth → 브리지가 MAC 주소 테이블(FDB)로 전달 → 상대 veth인 L2 스위칭이다. 외부로 나갈 때는 기본 게이트웨이(브리지 IP) → 호스트 IP 포워딩 → 출발지를 호스트 IP로 바꾸는 MASQUERADE(`nat` `POSTROUTING`)를 거친다. → 코어 2 (2.2)

   </details>

3. 컨테이너 안 `eth0@if7`의 `@if7`은 무엇이고 호스트 쪽 짝은 어떻게 찾는가?

   <details markdown="1"><summary>답 확인</summary>

   veth pair 반대쪽 끝이 호스트 네임스페이스에서 가진 인터페이스 인덱스다. 호스트에서 `ip link show`로 같은 인덱스를 가진 인터페이스를 찾으면 그것이 짝이고, `bridge link show`로 브리지 연결을 본다. → 코어 2 (2.1)

   </details>

4. 호스트 8080으로 온 패킷의 목적지는 어느 단계에서 컨테이너 IP로 바뀌는가? 이 시점이 중요한 이유는?

   <details markdown="1"><summary>답 확인</summary>

   라우팅 결정보다 앞선 `nat` 테이블 `PREROUTING` 단계의 `DOCKER` 체인 DNAT 규칙에서 바뀐다. 목적지를 바꾼 뒤에 라우팅을 판단하므로 패킷이 docker0 방향으로 가서 FORWARD → 브리지 → veth → `eth0:80`에 도착한다. 응답은 conntrack이 되돌린다. → 코어 3 (3.2)

   </details>

5. `docker-proxy`는 무엇이고, 끄기 전에 무엇을 점검하는가?

   <details markdown="1"><summary>답 확인</summary>

   포트를 게시할 때 dockerd가 호스트 게시 포트를 listen하며 컨테이너로 중계하도록 띄우는 사용자 공간 프로세스로, 호스트가 루프백으로 자기 게시 포트에 접속하는 경우(hairpin NAT) 등 DNAT만으로 경로가 깔끔하지 않은 경우를 보완한다. `"userland-proxy": false`로 끄면 커널 NAT 경로만 남으므로 필요한 접근 경로(특히 호스트 루프백)를 먼저 점검한다. → 코어 3 (3.1)

   </details>

6. hairpin NAT란 무엇이고 어떻게 피하는가?

   <details markdown="1"><summary>답 확인</summary>

   컨테이너가 자기가 게시한 포트를 호스트의 외부/게시 주소로 접속하면 패킷이 나갔다가 DNAT를 거쳐 나갔던 인터페이스로 되돌아 들어오는데, 이 경로를 hairpin NAT라 한다. 최신 배포판에서는 대부분 커널 DNAT로 처리되지만 오래된 커널·브리지 netfilter 비활성 환경에서는 어긋날 수 있다. 컨테이너 이름이나 `localhost`로 접근하도록 설계를 바꾸는 것이 가장 확실하다. → 코어 3 (3.3)

   </details>

7. `-p`로 게시한 포트를 `ufw`로 막았는데 열려 있는 이유와 Engine 28이 바꾼 것은?

   <details markdown="1"><summary>답 확인</summary>

   Docker가 `FORWARD` 등 호스트 방화벽이 관리하는 것과 같은 iptables 테이블에 직접 규칙을 넣고, 게시된 포트에는 Docker 규칙이 우선 적용되기 때문이다. Engine 28은 **게시하지 않은** 포트로의 인바운드를 컨테이너 IP 기준으로 기본 차단하도록 바꿨다(Docker Desktop은 해당 없음). 게시된 포트 문제는 남아 있다. → 코어 4 (4.1)

   </details>

8. 단일 호스트 `-p`와 Swarm 라우팅 메시의 핵심 차이는?

   <details markdown="1"><summary>답 확인</summary>

   단일 호스트 `-p`는 컨테이너가 떠 있는 호스트만 요청을 받고 DNAT 대상이 그 호스트의 특정 컨테이너 IP로 고정된다. 라우팅 메시는 클러스터 어느 노드로 들어와도 `ingress` 오버레이(VXLAN)를 통해 실제 태스크가 있는 노드로 재전달하고 IPVS 기반 VIP로 로드밸런싱한다. 즉 포트가 게시된 곳과 요청을 처리하는 곳이 분리된다. → 코어 3 (3.4)

   </details>

### 3. 기억 고리

- **C++ 유추:** `-p 8080:80` ≈ 공유기 포트포워딩. ⚠️ 별도 장비가 아니라 같은 호스트 커널의 `PREROUTING`에서 라우팅 결정 **전**에 목적지가 바뀌고, 컨테이너 안 앱은 자기 네임스페이스에서 80을 `listen`할 뿐이고, 호스트 8080으로 오는 패킷은 기본적으로 커널 DNAT가 넘긴다(`docker-proxy`는 보완용).
- **C++ 유추:** 컨테이너 이름 통신 ≈ 설정 파일의 서버 IP를 DNS 이름으로 바꾸기. ⚠️ 기본 브리지에서는 안 되고 사용자 정의 브리지에서만 된다.
- **비유:** Docker 네트워크 = 아파트 단지 인터넷. 각 세대(컨테이너)의 랜 케이블(veth) 한쪽은 세대 안 콘센트(`eth0`), 다른 쪽은 단지 스위치(브리지)에 꽂혀 있다. 단지 안 통화는 스위치만 거치고(L2), 밖으로 나갈 때는 단지 대표 번호(호스트 IP)로 바뀌며(MASQUERADE), 밖에서 대표 번호의 내선(8080)으로 오면 관리실이 세대 번호로 바꿔 연결한다(DNAT). ⚠️ 비유가 깨지는 지점: "관리실"은 사람(프로세스)이 아니라 커널의 iptables 규칙이고, 번호 변경은 라우팅 결정 **전**(PREROUTING)에 일어나며, 응답은 conntrack이 자동으로 되돌린다.
- **묶음(3의 법칙):** 통신 3방향(컨테이너 간 = 스위칭 / 밖으로 = MASQUERADE / 안으로 = DNAT) · 포트 게시 보조 3(DNAT 규칙·docker-proxy·`userland-proxy` 옵션) · 방화벽 사실 3(미게시 포트 기본 차단·게시 포트는 Docker 우선·Desktop 제외).
- **대칭·순서:** 아웃바운드 NAT(출발지 변경, POSTROUTING) ↔ 인바운드 DNAT(목적지 변경, PREROUTING). 순서: PREROUTING → DNAT → 라우팅 결정 → FORWARD → docker0 → veth → eth0.

### 4. 가르치기 · 반대편 서기

- **거울 설명 (1분, 원고 없이):** "외부 요청이 `-p 8080:80`을 통해 nginx 컨테이너에 도착하는 경로"를 처음 듣는 사람에게 설명해 보세요. 말이 막히는 지점 = 지식의 구멍.

- **랜덤 논리 게임:** A "`docker-proxy`(userland-proxy)는 켜 두는 게 안전하다" vs B "커널 DNAT만으로 충분하니 끄자" — 양쪽을 번갈아 변호해 보세요(hairpin NAT, 원천 두 장의 서술 차이, 직접 `ps`로 확인, 프로세스 수 절약을 근거로).
