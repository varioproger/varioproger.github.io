# 8장. 브리지 네트워크와 포트 게시

> **🎮 게임 서버 개발자에게** — 게임 서버가 `bind()`/`listen()`한 포트로 클라이언트가 붙던 구조가, 컨테이너 세계에서는 "컨테이너마다 독립된 네트워크 스택 + 가상 케이블(veth) + 가상 스위치(브리지) + 커널 NAT"로 바뀐다. 결정적으로 다른 점은 컨테이너 안에서 80번을 `listen`한 소켓은 **컨테이너 자기 네임스페이스 안의 소켓일 뿐**이라는 것이다. 외부 접속은 `-p`가 만든 iptables DNAT 규칙이 목적지를 바꿔 줘야 들어오고(기본 경로), 그 사이에는 어떤 프로세스도 없을 수 있다(보완용 `docker-proxy`가 호스트 포트를 대신 bind하는 경우는 코어 3). 서버끼리는 IP 대신 **컨테이너 이름**으로 찾는다. 이 장은 [4장](../1부-리눅스-네트워크-기초/04-veth-브리지-라우팅-ARP.md)의 veth·브리지와 [5장](../1부-리눅스-네트워크-기초/05-netfilter-iptables-NAT-conntrack.md)의 NAT가 Docker에서 합쳐지는 지점이다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 개발용 DB를 `-p 5432:5432`로 열고 `ufw`로 막았다고 믿었는데 외부에서 접속된다.
> - 클라이언트 접속이 `호스트IP:8080`으로 들어와 컨테이너의 80번까지 어떤 경로로 가는지 따져야 하는 장애 분석.
> - 두 컨테이너가 이름으로 서로를 못 찾는데 `--network` 없이 띄워 기본 브리지에 붙은 상황.

## 코어 — 이것만은 100%

> **한 문장:** 컨테이너는 veth pair로 호스트 브리지에 꽂혀 같은 브리지 안에서는 L2 스위칭(NAT 없음)으로, 밖으로는 라우팅 + MASQUERADE로 통신하고, 밖에서 들어오는 `-p` 트래픽은 PREROUTING의 DNAT로 라우팅 결정 전에 목적지가 바뀌어 컨테이너에 도착하며(응답은 conntrack이 되돌림), 게시된 포트에는 호스트 방화벽보다 Docker 규칙이 먼저 적용된다.

1. **사용자 정의 브리지는 DNS와 격리의 단위다** — 기본 브리지(`docker0`)는 자동 DNS가 없는 평평한 한 공간이고, 사용자 정의 브리지는 네트워크마다 내장 DNS와 격리 도메인을 갖는다. 그 네트워크에 줄 대역은 IPAM이 풀에서 할당하며 풀은 `daemon.json`의 `default-address-pools`로 정한다.
2. **veth는 CNM의 Endpoint, 안은 스위칭·밖은 NAT** — veth 한 쌍의 컨테이너 쪽 끝이 Endpoint이고 호스트 쪽 끝이 브리지에 꽂힌다. 같은 브리지 안은 FDB 기반 L2 스위칭, 밖으로는 게이트웨이 → IP 포워딩 → MASQUERADE다. (veth·브리지·라우팅 자체는 [4장](../1부-리눅스-네트워크-기초/04-veth-브리지-라우팅-ARP.md))
3. **`-p`는 커널 DNAT와 사용자 공간 `docker-proxy`의 이중 구조다** — 기본 경로는 PREROUTING의 DNAT(규칙 읽기는 [5장](../1부-리눅스-네트워크-기초/05-netfilter-iptables-NAT-conntrack.md))이고, `docker-proxy`는 포트마다 뜨는 보완 프로세스다. 경계 사례(hairpin, 루프백 접근, 바인딩 주소)와 `userland-proxy: false`의 영향이 이 장의 심화 지점이다.
4. **게시된 포트에서는 Docker 규칙이 호스트 방화벽보다 먼저다** — Engine 28부터 미게시 포트 인바운드는 기본 차단되지만, 게시 포트의 우선순위는 netfilter 체인 삽입 순서의 문제다([5장](../1부-리눅스-네트워크-기초/05-netfilter-iptables-NAT-conntrack.md) 1.3절, [11장](11-Docker-방화벽-iptables에서-nftables로.md)).

**이 장의 학습 목표**

- 사용자 정의 네트워크의 대역이 어디서 정해지는지(`default-address-pools`)와 DNS·격리 범위를 설명할 수 있다.
- veth·브리지 구조를 CNM의 Endpoint·Network에 대응시킬 수 있다.
- `docker-proxy` 프로세스의 인자를 읽고, `userland-proxy: false`로 바뀌는 것과 끄기 전 점검 항목을 말할 수 있다.
- hairpin NAT가 왜 까다로운 경로인지, 원천 두 장의 서술 차이를 포함해 설명할 수 있다.
- 단일 호스트 `-p`와 Swarm 라우팅 메시의 차이, 게시 포트와 호스트 방화벽의 우선순위 문제를 안다.

## 코어 1. 사용자 정의 브리지는 DNS와 격리의 단위다

### 1.1 기본 브리지와 사용자 정의 브리지

**한 줄 요약:** 이름 통신(자동 DNS)과 네트워크 간 격리는 사용자 정의 브리지의 몫이고, 그 네트워크의 대역은 IPAM이 풀에서 할당한다.

> **입문 책에서 배운 것:** 기본 브리지 `docker0`는 이름 통신이 없는 평평한 공간이고, `docker network create`로 만든 사용자 정의 브리지는 컨테이너 이름·별칭으로 통신하며 서로 다른 네트워크끼리 격리된다. 그래서 프로젝트마다 사용자 정의 브리지를 쓴다. ([입문 책 11장](../../Docker%20와%20Kubernetes로%20인프라%20구축할때%20알아야하는%20필수%20이론%20지식/2부-컨테이너와-Docker/11-Docker-네트워크.md))

- 이름 통신이 되는 이유는 Docker가 사용자 정의 네트워크마다 내장 DNS를 구동하고 각 컨테이너의 `/etc/resolv.conf`가 그것을 가리키게 하기 때문이다. 해석 범위는 네트워크 단위이며 상세는 [9장](09-Docker-DNS와-서비스-디스커버리.md)이다.
- 기본 브리지는 CNM 상에서 `bridge`라는 이름의 기본 Network이고([7장](07-Docker-네트워크-모델.md)), 사용자 정의 네트워크에 줄 서브넷은 IPAM이 고른다. `daemon.json`의 `default-address-pools`가 **사용자 정의 브리지·오버레이 네트워크에 할당할 IP 대역 풀**이다. 사내 대역과 겹치면 7장의 `--subnet`으로 직접 지정하거나 이 풀을 조정한다.

> **[보충]** `default-address-pools`는 원천(docker 07)이 `daemon.json` 키 표에서 "사용자 정의 브리지/오버레이 네트워크에 할당할 IP 대역 풀"이라고 한 한 줄 설명만 있고, 값의 형식과 충돌 시 동작은 원천에 없어 적지 않는다. "사내 대역과 겹치면 풀을 조정한다"는 활용 방식은 이 책의 추론이다.

## 코어 2. veth로 꽂고, 안은 스위칭·밖은 NAT

### 2.1 veth pair — Endpoint와 브리지의 접점

**한 줄 요약:** veth 한 쌍의 컨테이너 쪽 끝(`eth0`)이 CNM의 Endpoint이고, 호스트 쪽 끝(`vethXXXXXXX`)이 브리지에 꽂힌다.

> **입문 책에서 배운 것:** Docker는 veth pair의 한쪽을 컨테이너 네임스페이스로 옮겨 `eth0`으로 보이게 하고 다른 쪽을 호스트 브리지에 연결한다. `eth0@ifN`의 N으로 호스트 쪽 짝을 찾고, `ip link show type veth`·`bridge link show`로 확인한다. ([입문 책 11장](../../Docker%20와%20Kubernetes로%20인프라%20구축할때%20알아야하는%20필수%20이론%20지식/2부-컨테이너와-Docker/11-Docker-네트워크.md), 손으로 조립하는 과정은 [4장](../1부-리눅스-네트워크-기초/04-veth-브리지-라우팅-ARP.md))

이 장의 몫은 CNM 용어와의 대응이다. 컨테이너 쪽 끝이 Endpoint이고 브리지 디바이스가 Network의 실체이므로([7장](07-Docker-네트워크-모델.md)), 컨테이너를 네트워크 두 개에 붙이면 veth 쌍도 두 개가 생긴다. 브리지의 MAC 주소 테이블(FDB)은 구 `brctl` 대신 iproute2의 `bridge fdb show br docker0`로 본다.

### 2.2 통신 경로: 컨테이너 간 vs 외부

**한 줄 요약:** 같은 브리지 안은 FDB 기반 L2 스위칭(라우팅·NAT 없음), 외부로는 라우팅 + MASQUERADE다.

> **입문 책에서 배운 것:** 같은 브리지의 컨테이너끼리는 MAC 주소 테이블(FDB)로 전달되는 L2 스위칭이고, 대역 밖으로는 기본 게이트웨이(예: 172.17.0.1) → 커널 IP 포워딩 → `POSTROUTING`의 MASQUERADE로 출발지를 호스트 IP로 바꾼다. ([입문 책 11장](../../Docker%20와%20Kubernetes로%20인프라%20구축할때%20알아야하는%20필수%20이론%20지식/2부-컨테이너와-Docker/11-Docker-네트워크.md))

두 경로가 다른 계층의 동작이라는 점이 핵심이며, 포워딩·MASQUERADE의 구성 요소는 [4장](../1부-리눅스-네트워크-기초/04-veth-브리지-라우팅-ARP.md) 3.1절, 규칙은 `iptables -t nat -L POSTROUTING -n -v | grep -i MASQUERADE`로 본다.

## 코어 3. 들어오는 길은 DNAT, 보완은 docker-proxy

### 3.1 포트 게시(`-p`)의 두 메커니즘 — 프로세스는 포트마다 하나

**한 줄 요약:** 기본 경로는 커널 DNAT이고, `docker-proxy`는 포트마다 하나씩 뜨는 사용자 공간 보완 프로세스이며 `userland-proxy: false`로 끌 수 있다.

> **입문 책에서 배운 것:** `-p 8080:80`은 `nat` 테이블 `DOCKER` 체인의 DNAT(별도 프로세스 없이 커널만으로 처리)와 `docker-proxy`라는 보완 프로세스 두 메커니즘의 결과이고, `"userland-proxy": false`로 끄기 전에 호스트 루프백 접근 경로를 점검한다. ([입문 책 11장](../../Docker%20와%20Kubernetes로%20인프라%20구축할때%20알아야하는%20필수%20이론%20지식/2부-컨테이너와-Docker/11-Docker-네트워크.md))

**`docker-proxy`의 모양.** dockerd는 포트를 게시할 때마다 호스트의 게시 포트를 직접 bind해 리스닝하는 `docker-proxy` 프로세스를 **하나씩** 띄운다(원천 12.4). 호스트 포트로 들어온 연결을 컨테이너 IP:포트로 그대로 중계하는 단순한 TCP/UDP 프록시이고, 인자에 게시 정보가 그대로 담긴다.

```bash
ps -ef | grep docker-proxy | grep -v grep
# 예: docker-proxy -proto tcp -host-ip 0.0.0.0 -host-port 8080 -container-ip 172.17.0.2 -container-port 80
```

**보완하는 경계 사례.** 원천은 순수 커널 NAT 경로로 왕복이 깔끔하게 완성되지 않는 경우로 호스트 자신이 루프백(`127.0.0.1`)으로 자기 게시 포트에 접속하는 경우(hairpin NAT), 특정 네트워크 구성에서 IPv6 처리가 얽히는 경우를 든다. 15.4절은 과거 버전에서 바인딩 주소가 `0.0.0.0`이 아니거나 hairpin이 필요한 특수한 경우를 `docker-proxy`가 대신 중계했다고 덧붙인다.

**끄기와 확인.** `/etc/docker/daemon.json`에 `{"userland-proxy": false}`를 넣고 `sudo systemctl restart docker`를 하면 `docker-proxy`가 뜨지 않고 포트 게시는 iptables(또는 nftables) 기반 커널 NAT 경로만으로 처리된다. 호스트당 게시 포트가 많은 환경에서는 프로세스 수를 줄여 리소스를 절약할 수 있다. 원천 실습의 확인 절차는 다음과 같다(이 책이 실행해 본 것은 아니다).

```bash
docker run -d --name web2 -p 8081:80 nginx:latest
ps -ef | grep docker-proxy | grep -v grep   # web2에 대한 docker-proxy가 뜨지 않는지 확인
curl -sI http://localhost:8081 | head -1     # 그래도 접속이 정상인지 확인
```

> **[보충]** 원천 두 장의 서술이 완전히 같지 않다. docker 12.4는 포트를 게시할 때마다 `docker-proxy`가 하나씩 뜨고 기본값이 활성화라고 설명하는 반면, docker 15.4는 기본 경로가 커널 DNAT이며 과거에는 `docker-proxy`가 hairpin 등 일부를 대신 중계했지만 최근 배포판에서는 hairpin도 대부분 커널 DNAT만으로 처리된다고 쓴다. 이 책은 "기본 경로는 커널 DNAT, `docker-proxy`는 보완용"까지만 확정하고, 현재 환경에서의 관여 정도는 위 `ps` 명령으로 직접 확인하게 한다. hairpin의 정의도 12.4는 "호스트가 루프백으로 자기 게시 포트에 접속", 15.4는 "컨테이너가 자기 게시 포트를 호스트 주소로 되돌아 접속"으로 초점이 다르다(3.3절). 서술이 다른 부분은 더 상세한 15장을 기준으로 삼았다.

### 3.2 인바운드 경로와 규칙 확인

**한 줄 요약:** 경로는 PREROUTING(DNAT) → 라우팅 결정 → FORWARD → docker0 → veth → eth0이고, 규칙은 백엔드에 맞는 명령으로 본다.

> **입문 책에서 배운 것:** DNAT는 라우팅 결정보다 앞선 PREROUTING에서 일어나고, 응답은 conntrack이 되돌려 클라이언트는 `호스트IP:8080`만 본다. ([입문 책 11장](../../Docker%20와%20Kubernetes로%20인프라%20구축할때%20알아야하는%20필수%20이론%20지식/2부-컨테이너와-Docker/11-Docker-네트워크.md))

훅과 체인(`PREROUTING`·`OUTPUT`·`FORWARD` 등)의 위치와 응답 복원의 원리는 [5장](../1부-리눅스-네트워크-기초/05-netfilter-iptables-NAT-conntrack.md)(1.2·3.1절)이, `DOCKER` 체인을 줄 번호로 읽는 방법은 5장 2.2절이 다룬다. 이 장에서 더하는 것은 **호스트 자신에서 접속하는 경우의 진입점**이다. 호스트의 로컬 프로세스가 보낸 패킷은 `PREROUTING`이 아니라 `OUTPUT`에서 `DOCKER` 체인으로 점프한다.

규칙을 보는 명령은 백엔드에 따라 다르다.

```bash
iptables-save -t nat | grep -i docker           # DNAT --to-destination <컨테이너IP>:80
nft list ruleset | grep -A 5 -i docker          # iptables-nft 배포판에서 같은 규칙
```

`--firewall-backend=nftables`로 Docker 자체의 실험적 nftables 백엔드를 켠 환경에서는 규칙 구조가 `iptables`/`DOCKER` 체인 방식과 다른 형태(Docker 전용 네임스페이스로 분리된 테이블)로 나타난다([11장](11-Docker-방화벽-iptables에서-nftables로.md)).

### 3.3 hairpin NAT — 자기 자신의 게시 포트로 접속할 때

**한 줄 요약:** 나갔던 인터페이스로 되돌아 들어오는 경로는 커널 NAT가 항상 매끄럽게 처리하지 못했고, 지금은 대부분 처리되지만 오래된 커널·브리지 netfilter 비활성화 환경에서는 어긋날 수 있다.

컨테이너 A가 자기가 게시한 포트를 호스트의 공인 IP나 게시 주소로 되돌아 들어오는 경로로 접속하려는 경우다. 예를 들어 컨테이너 안 스크립트가 설정 파일의 `http://<호스트의_외부_IP>:18080`을 그대로 써서 자기 자신에게 요청을 보내는 상황이다. 요청은 컨테이너의 veth로 나가 docker0를 거쳐 DNAT를 받고 다시 같은 컨테이너로 돌아와야 한다. 이렇게 나갔던 인터페이스로 되돌아 들어오는 경로를 hairpin(헤어핀) NAT라고 한다.

- 과거에는 `docker-proxy`가 커널 DNAT를 우회해 사용자 공간에서 루프백 트래픽을 직접 중계하는 방식으로 해결하기도 했다.
- 오늘날에는 커널의 브리지 netfilter 훅과 conntrack이 개선되어 대부분의 최신 배포판에서 hairpin 트래픽도 커널 DNAT만으로 정상 처리된다.
- 아주 오래된 커널이거나 브리지 netfilter가 비활성화된 환경에서는 여전히 어긋날 수 있다.
- 가장 간단하고 확실한 회피책은 컨테이너가 자기 자신을 호출해야 하는 상황 자체를 피하고, 컨테이너 이름이나 `localhost`로 접근하도록 설계를 바꾸는 것이다.

### 3.4 단일 호스트 `-p` vs Swarm 라우팅 메시

**한 줄 요약:** 포트가 게시된 곳과 요청을 처리하는 곳이 항상 같은 호스트인가(단일 호스트) 분리되는가(라우팅 메시)가 핵심 차이다.

Swarm에서 `docker service create --publish published=8080,target=80`으로 서비스를 게시하면 명령은 비슷해 보여도 내부는 상당히 다르다. 특수한 `ingress` 오버레이 네트워크(VXLAN 캡슐화)와 라우팅 메시가 관여하기 때문이다([6장](../1부-리눅스-네트워크-기초/06-오버레이-VXLAN-MTU.md), [10장](10-macvlan-ipvlan-host-none-오버레이.md)).

| 구분 | 단일 컨테이너 포트 매핑 (`docker run -p`) | Swarm ingress 라우팅 메시 (`docker service --publish`) |
|---|---|---|
| 요청을 받을 수 있는 노드 | 해당 컨테이너가 실제로 떠 있는 호스트뿐 | 클러스터의 모든 노드(태스크가 그 노드에 없어도 가능) |
| DNAT 대상 결정 | 항상 그 호스트의 특정 컨테이너 IP로 고정 | 어느 노드로 들어오든 ingress 네트워크를 통해 실제 태스크가 떠 있는 노드로 재전달 |
| 로드밸런싱 | 없음 | IPVS 기반 VIP 로드밸런싱으로 여러 태스크에 분산 |
| 사용되는 네트워크 | 로컬 브리지(docker0 또는 사용자 정의 브리지) | 특수한 `ingress` 오버레이 네트워크 |
| 노드 장애/스케일 변화 | 컨테이너가 죽으면 포트도 사라짐 | 태스크가 다른 노드로 재스케줄되어도 게시 포트는 클러스터 전체에서 유효 |

라우팅 메시는 "포트 매핑 + 오버레이 네트워크 라우팅"을 합친 상위 개념이라고 볼 수 있다.

## 코어 4. 게시 포트의 우선순위는 체인 삽입 순서의 문제다

### 4.1 Engine 28 — 미게시 포트는 막혔고, 게시 포트는 그대로다

**한 줄 요약:** Engine 28부터 미게시 포트 인바운드는 기본 차단되지만, 게시된 포트에는 여전히 Docker 규칙이 호스트 방화벽보다 먼저 적용된다.

> **입문 책에서 배운 것:** Engine 28부터 `-p`로 게시하지 않은 포트로 들어오는 인바운드를 기본 차단해 "Docker가 호스트 방화벽을 우회한다"는 문제가 크게 완화됐고(Linux 전용, Docker Desktop 제외), 게시된 포트에는 Docker 규칙이 우선한다. ([입문 책 11장](../../Docker%20와%20Kubernetes로%20인프라%20구축할때%20알아야하는%20필수%20이론%20지식/2부-컨테이너와-Docker/11-Docker-네트워크.md))

왜 게시 포트가 여전히 우선인지는 netfilter 구조의 문제다. `ufw` 규칙은 흔히 `INPUT`에 있고 컨테이너행 트래픽은 `FORWARD`를 지나며 Docker 규칙은 그 앞쪽에 끼어 있다([5장](../1부-리눅스-네트워크-기초/05-netfilter-iptables-NAT-conntrack.md) 1.3·2.2절). Engine 28의 변경 내용(`gateway_mode_ipv4`/`gateway_mode_ipv6`의 `nat-unprotected` 복원 옵션 포함)과 이를 구조적으로 다시 설계한 Engine 29의 실험적 nftables 백엔드는 [11장](11-Docker-방화벽-iptables에서-nftables로.md)이 다룬다.

> **[보충]** 호스트 주소를 생략한 `-p 8080:80`은 모든 인터페이스(0.0.0.0)에 게시되므로 내 PC에서만 쓸 포트는 `-p 127.0.0.1:5432:5432`처럼 루프백에 묶는 편이 안전하다는 조언은 원천(docker 12)에 없고 이 책이 덧붙인 실무 조언이다. 원천 `docker-proxy` 예시의 `-host-ip 0.0.0.0`은 호스트 쪽 게시 주소 개념이 있다는 간접 근거일 뿐이다.

## 실무 적용

### 체크리스트

- [ ] 사용자 정의 브리지는 내장 DNS와 격리의 단위이고, 그 대역은 IPAM이 풀(`daemon.json`의 `default-address-pools`)에서 할당한다. 기본 브리지는 이름 통신이 없는 평평한 공간이다.
- [ ] veth 쌍의 컨테이너 쪽 끝이 CNM의 Endpoint, 호스트 쪽 끝이 브리지의 접점이다. 같은 브리지 안은 FDB 기반 L2 스위칭, 밖은 게이트웨이 → IP 포워딩 → MASQUERADE다.
- [ ] `-p`는 `DOCKER` 체인 DNAT(커널)와 포트마다 하나씩 뜨는 `docker-proxy`(보완)의 이중 구조이고, `ps -ef | grep docker-proxy`의 인자(`-host-port`, `-container-ip` 등)로 게시 정보를 읽는다.
- [ ] 호스트 자신에서의 접속은 `PREROUTING`이 아니라 `OUTPUT`이 `DOCKER` 체인으로 점프한다. 규칙은 `iptables-save -t nat | grep -i docker`(또는 `nft list ruleset | grep -A 5 -i docker`)로 본다.
- [ ] `"userland-proxy": false`로 끄면 커널 NAT 경로만 남는다. 끈 뒤 `docker-proxy`가 뜨지 않는지와 접속이 정상인지 확인하고, 끄기 전에 호스트 루프백 접근 경로를 점검한다.
- [ ] 게시된 포트에는 호스트 방화벽보다 Docker 규칙이 먼저다(`ufw`는 `INPUT`, 컨테이너행은 `FORWARD`, Docker 규칙은 그 앞쪽). Engine 28+의 기본 차단은 **미게시** 포트에만 해당한다.
- [ ] 컨테이너가 자기 게시 포트를 호스트 주소로 호출하는 설계를 피하고 컨테이너 이름이나 `localhost`를 쓴다.

### 시나리오로 확인하기

1. **상황:** 개발용 PostgreSQL을 `-p 5432:5432`로 띄우고 호스트에서 `ufw deny 5432`를 걸었는데 사내망의 다른 PC에서 접속이 된다.
   **질문:** 왜 막히지 않았고 어떻게 했어야 하나?

   <details markdown="1"><summary>답 확인</summary>

   `ufw` 같은 도구는 규칙을 흔히 `INPUT`에 두지만 컨테이너로 향하는 트래픽은 `FORWARD`를 지나고, Docker가 `FORWARD` 앞쪽에 `DOCKER` 체인 점프 규칙을 끼워 두어 게시된 포트에는 Docker 규칙이 먼저 평가된다([5장](../1부-리눅스-네트워크-기초/05-netfilter-iptables-NAT-conntrack.md) 1.3절). Engine 28의 기본 차단은 **게시하지 않은** 포트에만 해당한다. 외부 접근이 필요 없다면 게시 자체를 하지 않는다. 방화벽만 믿지 않는다. (게시 주소를 루프백으로 제한하는 `-p 127.0.0.1:5432:5432` 형태는 코어 4의 [보충]에서 밝혔듯 원천에 없는 이 책의 실무 조언이다.) → 코어 4 (4.1)

   </details>

2. **상황:** 외부 클라이언트가 `호스트IP:8080`으로 접속하는 nginx 컨테이너(`-p 8080:80`)의 패킷 경로를 장애 보고서에 적어야 한다. 동료는 "dockerd가 8080을 listen해서 받아 넘겨 준다"고 쓴다.
   **질문:** 정확한 경로는?

   <details markdown="1"><summary>답 확인</summary>

   기본 경로는 커널이다. `nat` 테이블 `PREROUTING` → `DOCKER` 체인 점프 → DNAT로 목적지를 `컨테이너IP:80`으로 변경 → 라우팅 결정(docker0 방향) → `FORWARD`(filter) → docker0 → veth → 컨테이너 `eth0:80`. 응답은 conntrack이 주소를 되돌려 클라이언트는 `호스트IP:8080`만 본다. `docker-proxy`는 포트마다 하나씩 뜨는 보완용이며 실제 관여 여부는 `ps -ef | grep docker-proxy`로 확인한다. → 코어 3 (3.1, 3.2)

   </details>

3. **상황:** 컨테이너 안 스크립트가 설정 파일의 `http://<호스트_외부_IP>:18080`(자기 자신이 게시한 포트)으로 요청을 보내는데 오래된 호스트에서만 응답이 없다.
   **질문:** 의심 부품과 해결은?

   <details markdown="1"><summary>답 확인</summary>

   hairpin NAT 경로다. 패킷이 나갔던 인터페이스로 되돌아 들어와야 하는데, 아주 오래된 커널이거나 브리지 netfilter가 비활성화된 환경에서는 커널 DNAT만으로 어긋날 수 있다. 가장 확실한 해결은 자기 자신을 호스트 주소로 호출하는 설계를 없애고 컨테이너 이름이나 `localhost`로 접근하게 바꾸는 것이다. → 코어 3 (3.3)

   </details>

4. **상황:** 게시 포트가 수십 개인 호스트에서 `docker-proxy` 프로세스가 너무 많아 보인다. `daemon.json`에 `"userland-proxy": false`를 넣어 줄이려 한다.
   **질문:** 어떤 순서로 적용하고 무엇을 점검하는가?

   <details markdown="1"><summary>답 확인</summary>

   끄기 전에 이 호스트에서 실제로 쓰는 접근 경로(특히 호스트 자신의 루프백을 통한 접근)가 있는지 점검한다. 설정 후 `sudo systemctl restart docker`로 재시작하고, 새 컨테이너를 `-p`로 게시해 `ps -ef | grep docker-proxy`에 그 포트의 프로세스가 뜨지 않는지, `curl -sI http://localhost:<포트>`로 접속이 여전히 정상인지 확인한다. 끄면 포트 게시는 커널 NAT 경로만으로 처리되며 hairpin 같은 특수 시나리오에서 차이가 날 수 있다. → 코어 3 (3.1)

   </details>

### 2. 인출 질문

1. 기본 브리지에서는 컨테이너 이름으로 통신이 안 되는데 사용자 정의 브리지에서는 되는 이유는? 사용자 정의 네트워크에 줄 대역 풀은 어디서 정하는가?

   <details markdown="1"><summary>답 확인</summary>

   Docker가 사용자 정의 네트워크마다 내장 DNS 서버를 구동하고 각 컨테이너의 `/etc/resolv.conf`가 그것을 가리키게 하기 때문이다. 기본 브리지는 그런 자동 DNS가 없어 `--link` 같은 레거시 옵션이나 IP 직접 사용만 가능했다. 사용자 정의 브리지·오버레이 네트워크에 할당할 IP 대역 풀은 `daemon.json`의 `default-address-pools`다. → 코어 1 (1.1)

   </details>

2. iptables-nft 배포판에서 Docker의 포트 게시 규칙을 볼 수 있는 명령 두 가지와, Docker 자체 nftables 백엔드를 켜면 달라지는 점은?

   <details markdown="1"><summary>답 확인</summary>

   `iptables-save -t nat | grep -i docker`와 `nft list ruleset | grep -A 5 -i docker`다. `--firewall-backend=nftables`로 Docker의 실험적 nftables 백엔드를 켠 환경에서는 규칙 구조가 `DOCKER` 체인 방식과 다른 형태(Docker 전용 네임스페이스로 분리된 테이블)로 나타난다. → 코어 3 (3.2)

   </details>

3. `ps -ef | grep docker-proxy`의 출력 한 줄에서 무엇을 읽을 수 있는가?

   <details markdown="1"><summary>답 확인</summary>

   게시 정보다. 예를 들어 `docker-proxy -proto tcp -host-ip 0.0.0.0 -host-port 8080 -container-ip 172.17.0.2 -container-port 80`에서 프로토콜, 호스트 쪽 게시 주소·포트, 컨테이너 IP·포트의 대응을 읽는다. dockerd는 포트를 게시할 때마다 이런 프로세스를 하나씩 띄운다. → 코어 3 (3.1)

   </details>

4. 원천 두 장(docker 12.4와 15.4)이 `docker-proxy`의 관여에 대해 다르게 쓰는 점은 무엇이고, 이 책은 어떻게 정리했는가?

   <details markdown="1"><summary>답 확인</summary>

   12.4는 게시할 때마다 `docker-proxy`가 하나씩 뜨고 기본 활성화라고 쓰고, 15.4는 기본 경로가 커널 DNAT이며 과거에는 hairpin 등을 `docker-proxy`가 대신 중계했지만 최근 배포판에서는 대부분 커널 DNAT만으로 처리된다고 쓴다. 이 책은 "기본 경로는 커널 DNAT, `docker-proxy`는 보완용"까지만 확정하고 실제 관여는 `ps`로 직접 확인하게 한다. → 코어 3 (3.1)

   </details>

5. `docker-proxy`를 끄기 전에 무엇을 점검하고, 끈 뒤 무엇을 확인하는가?

   <details markdown="1"><summary>답 확인</summary>

   끄기 전에 실제로 필요한 접근 경로(특히 호스트 자신의 루프백을 통한 접근)를 점검한다. 끈 뒤에는 새로 게시한 포트에 대한 `docker-proxy` 프로세스가 `ps`에 뜨지 않는지, `curl -sI http://localhost:<포트>`로 접속이 정상인지 확인한다. 끄면 포트 게시는 커널 NAT 경로만으로 처리된다. → 코어 3 (3.1)

   </details>

6. hairpin NAT란 무엇이고 어떻게 피하는가?

   <details markdown="1"><summary>답 확인</summary>

   컨테이너가 자기가 게시한 포트를 호스트의 외부/게시 주소로 접속하면 패킷이 나갔다가 DNAT를 거쳐 나갔던 인터페이스로 되돌아 들어오는데, 이 경로를 hairpin NAT라 한다. 최신 배포판에서는 대부분 커널 DNAT로 처리되지만 오래된 커널·브리지 netfilter 비활성 환경에서는 어긋날 수 있다. 컨테이너 이름이나 `localhost`로 접근하도록 설계를 바꾸는 것이 가장 확실하다. → 코어 3 (3.3)

   </details>

7. `-p`로 게시한 포트를 `ufw`로 막았는데 열려 있는 이유와 Engine 28이 바꾼 것은?

   <details markdown="1"><summary>답 확인</summary>

   `ufw`는 규칙을 흔히 `INPUT`에 두지만 컨테이너행 트래픽은 `FORWARD`를 지나고, Docker가 `FORWARD` 앞쪽에 `DOCKER` 체인 점프 규칙을 끼워 두며 게시된 포트에는 Docker 규칙이 우선 적용되기 때문이다. Engine 28은 **게시하지 않은** 포트로의 인바운드를 컨테이너 IP 기준으로 기본 차단하도록 바꿨다(Docker Desktop은 해당 없음). 게시된 포트 문제는 남아 있다. → 코어 4 (4.1)

   </details>

8. 단일 호스트 `-p`와 Swarm 라우팅 메시의 핵심 차이는?

   <details markdown="1"><summary>답 확인</summary>

   단일 호스트 `-p`는 컨테이너가 떠 있는 호스트만 요청을 받고 DNAT 대상이 그 호스트의 특정 컨테이너 IP로 고정된다. 라우팅 메시는 클러스터 어느 노드로 들어와도 `ingress` 오버레이(VXLAN)를 통해 실제 태스크가 있는 노드로 재전달하고 IPVS 기반 VIP로 로드밸런싱한다. 즉 포트가 게시된 곳과 요청을 처리하는 곳이 분리된다. → 코어 3 (3.4)

   </details>

9. 컨테이너를 네트워크 두 개에 붙이면 veth 쌍은 몇 개이며, CNM과 어떻게 대응하는가? 브리지의 MAC 테이블은 어떤 명령으로 보는가?

   <details markdown="1"><summary>답 확인</summary>

   네트워크 수만큼, 즉 두 쌍이 생긴다. 컨테이너 쪽 끝(`eth0`, `eth1`)이 각각 Endpoint이고 브리지 디바이스가 Network의 실체이며 호스트 쪽 끝이 브리지에 꽂힌다. MAC 주소 테이블(FDB)은 구 `brctl` 대신 `bridge fdb show br docker0`로 본다. → 코어 2 (2.1)

   </details>

### 3. 기억 고리

- **C++ 유추:** `-p 8080:80` ≈ 공유기 포트포워딩. ⚠️ 별도 장비가 아니라 같은 호스트 커널의 `PREROUTING`에서 라우팅 결정 **전**에 목적지가 바뀌고, 컨테이너 안 앱은 자기 네임스페이스에서 80을 `listen`할 뿐이고, 호스트 8080으로 오는 패킷은 기본적으로 커널 DNAT가 넘긴다(`docker-proxy`는 보완용).
- **C++ 유추:** 컨테이너 이름 통신 ≈ 설정 파일의 서버 IP를 DNS 이름으로 바꾸기. ⚠️ 기본 브리지에서는 안 되고 사용자 정의 브리지에서만 된다.
- **비유:** Docker 네트워크 = 아파트 단지 인터넷. 각 세대(컨테이너)의 랜 케이블(veth) 한쪽은 세대 안 콘센트(`eth0`), 다른 쪽은 단지 스위치(브리지)에 꽂혀 있다. 단지 안 통화는 스위치만 거치고(L2), 밖으로 나갈 때는 단지 대표 번호(호스트 IP)로 바뀌며(MASQUERADE), 밖에서 대표 번호의 내선(8080)으로 오면 관리실이 세대 번호로 바꿔 연결한다(DNAT). ⚠️ 비유가 깨지는 지점: "관리실"은 사람(프로세스)이 아니라 커널의 iptables 규칙이고, 번호 변경은 라우팅 결정 **전**(PREROUTING)에 일어나며, 응답은 conntrack이 자동으로 되돌린다.
- **묶음(3의 법칙):** 통신 3방향(컨테이너 간 = 스위칭 / 밖으로 = MASQUERADE / 안으로 = DNAT) · 포트 게시 보조 3(DNAT 규칙·docker-proxy·`userland-proxy` 옵션) · 방화벽 사실 3(미게시 포트 기본 차단·게시 포트는 Docker 우선·Desktop 제외).
- **대칭·순서:** 아웃바운드 NAT(출발지 변경, POSTROUTING) ↔ 인바운드 DNAT(목적지 변경, PREROUTING; 호스트 자신발은 OUTPUT). 커널 경로(DNAT) ↔ 보완 경로(포트마다 하나씩 `docker-proxy`). 순서: PREROUTING → DNAT → 라우팅 결정 → FORWARD → docker0 → veth → eth0.
