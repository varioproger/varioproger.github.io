# 1장. 패킷 한 개의 여정

> **🎮 게임 서버 개발자에게** — 지금까지 `connect(서버IP, 포트)`로 보낸 패킷은 "내 소켓 → 상대 소켓"으로 곧장 간다고 생각해도 대부분 문제가 없었다. 컨테이너와 쿠버네티스에서는 같은 패킷이 **경계를 지날 때마다 주소가 바뀌거나, 겉에 헤더가 한 겹 더 씌워지거나, 전혀 다른 네임스페이스로 넘어간다.** 결정적으로 다른 점은 "내가 접속한 주소"에 그 주소를 가진 장비가 **실제로는 없을 수 있다**는 것이다(Service의 ClusterIP는 어떤 인터페이스에도 붙어 있지 않다). 이 장은 패킷 하나를 따라가며 어디에서 무엇이 바뀌는지 책 전체의 지도를 먼저 그린다. 세부는 각 장에서 채운다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 접속이 안 될 때 "컨테이너 안 앱이 죽었나, 포트 게시가 틀렸나, Service가 틀렸나, DNS인가"를 **경계 단위로 잘라서** 의심해야 하는 장애 분석.
> - 게임 서버가 보는 접속자 IP가 클라이언트 IP가 아니라 노드 IP로 찍히는 이유를 설명해야 할 때.
> - 이후 장(netns, veth, iptables, CNI, kube-proxy, Ingress)이 "어느 구간의 부품"인지 위치를 잡지 못하고 용어만 쌓여 갈 때.

## 코어 — 이것만은 100%

> **한 문장:** 패킷은 컨테이너의 격리된 네트워크 스택에서 출발해 veth와 브리지로 호스트에 올라오고, 경계마다 NAT(출발지 변경 MASQUERADE, 목적지 변경 DNAT)나 캡슐화를 거치며, 쿠버네티스에서는 Pod 간 NAT 없는 평평한 네트워크 위에 "이름(DNS) → 가상 주소(Service) → 실제 Pod(DNAT) → 외부 진입(Ingress)"의 네 문제가 층층이 얹혀 있다.

1. **컨테이너는 자기만의 네트워크 스택을 갖고, veth와 브리지로 호스트에 꽂힌다** — 네트워크 네임스페이스가 인터페이스·라우팅·방화벽·포트 공간을 격리하고, veth pair의 한쪽 끝이 호스트 브리지에 연결된다. 같은 브리지 안은 L2 스위칭, 밖으로는 라우팅 + NAT다.
2. **주소 바꿔치기는 NAT와 conntrack이 한다** — 나갈 때는 출발지를 바꾸고(MASQUERADE, POSTROUTING), 들어올 때는 라우팅 결정 전에 목적지를 바꾸며(DNAT, PREROUTING), 응답은 conntrack이 기억한 변환 정보로 되돌린다.
3. **쿠버네티스는 "Pod마다 IP, NAT 없는 평평한 네트워크"를 요구하고, 그 구현(CNI)이 노드 간 이동을 맡는다** — 노드 사이는 캡슐화(VXLAN)나 네이티브 라우팅(BGP) 중 하나로 옮기고, 캡슐화에는 MTU 손실이 따른다.
4. **Service는 약속이고 실행은 노드 커널이 한다** — DNS가 이름을 ClusterIP로 풀고, kube-proxy가 만든 노드의 규칙이 ClusterIP를 실제 Pod IP로 DNAT한다. 밖에서 들어오는 요청은 LoadBalancer → NodePort → ClusterIP 계층이나 Ingress 컨트롤러가 받아 Pod로 넘긴다.

**이 장의 학습 목표**

- 컨테이너에서 외부로, 외부에서 컨테이너로, Pod에서 Service로, 인터넷에서 Pod로 가는 네 가지 경로를 한 장의 지도로 그릴 수 있다.
- 각 경계에서 "주소가 바뀌는가, 캡슐화되는가, 그대로인가"를 구분한다.
- 이 책의 각 장이 어느 구간을 설명하는지 위치를 안다.
- 통신 문제를 주소·발견·전달·진입의 네 가지로 나누어 장애 원인을 좁히는 사고방식을 갖는다.

## C++·TCP 서버 경험에서 출발하기

| 이미 아는 것 (C++/소켓 서버) | 이 장의 개념 | 같은 점 | ⚠️ 다른 점 (유추가 깨지는 곳) |
|---|---|---|---|
| `connect(서버IP, 포트)`의 목적지는 곧 서버 장비 | Service의 ClusterIP로 접속 | 클라이언트는 하나의 안정된 좌표만 안다 | ClusterIP는 **어떤 네트워크 인터페이스에도 바인딩되어 있지 않다.** 그 IP로 `ping`을 보내도 응답이 없고, 노드 커널의 규칙이 목적지를 실제 Pod IP로 바꿔치기한다 |
| 설정 파일의 서버 IP(고정) | Pod IP는 일회용, 이름은 DNS | 이름 해석 후 IP로 `connect()`한다 | Pod가 재시작되면 IP가 바뀌므로 IP를 박아 둘 수 없다. Service가 "변하지 않는 가상 좌표"를 대신 제공한다 |
| `bind(0.0.0.0:80)`은 호스트 포트 80을 점유 | 컨테이너 안 `listen(80)`은 호스트 포트를 열지 않음 | 둘 다 `listen`일 뿐이다 | 네트워크 네임스페이스가 포트 바인딩 공간을 분리한다. 호스트에서 열리려면 `-p`가 만든 DNAT 규칙이 필요하다 |
| 공유기 포트포워딩·NAT 라우터 | 호스트 커널의 iptables NAT | 주소를 바꿔 내부로 넘긴다 | 별도 장비가 아니라 **같은 커널**의 PREROUTING/POSTROUTING 규칙이고, 응답은 conntrack이 되돌린다 |
| 로드밸런서 장비(L4) 뒤의 서버 풀 | kube-proxy가 만든 규칙(iptables 등) | 연결 단위로 백엔드를 고른다 | kube-proxy 프로세스는 **데이터 경로에 없다.** 규칙은 커널에 있고, 선택된 목적지는 conntrack이 그 연결 동안 유지한다 |
| 접속자 IP를 로그에 남김 | `externalTrafficPolicy` | 클라이언트 IP가 앱까지 오길 기대한다 | 기본값 `Cluster`에서는 외부 트래픽이 SNAT되어 **원본 클라이언트 IP가 소실**될 수 있다 |

## 코어 1. 컨테이너 안에서 노드 밖으로, 노드 밖에서 컨테이너 안으로

### 1.1 전체 지도 한 장

**한 줄 요약:** 단일 호스트에서 컨테이너의 패킷은 "자기 네트워크 네임스페이스 → veth → 호스트 브리지 → 라우팅/NAT → 호스트 NIC"로 흐른다.

먼저 이 책 전체의 뼈대를 한 장에 그린다. 아래 지도의 각 구간이 이후 장의 주제다.

```
[컨테이너 netns]     [호스트 netns]                                   [바깥]
 앱 (listen 80)
   │ eth0 ◄── veth pair ──► vethXXXX ─┐
   │                                   ├─ docker0 (브리지, L2 스위칭)
 앱2  eth0 ◄── veth pair ──► vethYYYY ─┘        │
                                                 │ 라우팅 + NAT
                                                 ▼
                                           호스트 eth0 ───────────────► 외부
   나갈 때:  출발지 컨테이너IP → 호스트IP  (POSTROUTING, MASQUERADE)
   들어올 때: 목적지 호스트IP:8080 → 컨테이너IP:80 (PREROUTING, DNAT)
```

> **[보충]** 위 그림은 `docker-fundamental` 12장의 veth 구조 그림과 통신 경로 설명을 한 장으로 합쳐 이 책에서 구성한 요약이며, 원문에 이 형태의 그림이 있는 것은 아니다.

### 1.2 컨테이너 안: 격리된 네트워크 스택

**한 줄 요약:** 네트워크 네임스페이스가 인터페이스, 라우팅 테이블, iptables/nftables 규칙, 포트 바인딩 공간을 분리하므로 컨테이너마다 독립적으로 `0.0.0.0:80`을 바인딩할 수 있다.

네임스페이스는 자원을 복제하는 것이 아니라 프로세스가 커널에 질의할 때 보이는 "뷰"를 바꾸는 기능이다. 컨테이너 10개도 같은 커널, 같은 물리 NIC를 공유하지만, 각 컨테이너 안에서 `ip addr`을 하면 자기 네임스페이스의 인터페이스만 보인다. 컨테이너는 기본적으로 자기만의 loopback(`lo`)과 veth pair의 한쪽 끝을 가진다. 상세는 [3장](../1부-리눅스-네트워크-기초/03-네트워크-네임스페이스.md)에서 다룬다.

### 1.3 나가는 길과 같은 브리지 안의 길

**한 줄 요약:** 같은 브리지 안은 MAC 주소 테이블로 스위칭(라우팅·NAT 없음), 대역 밖으로 나갈 때는 게이트웨이 → IP 포워딩 → 출발지를 호스트 IP로 바꾸는 MASQUERADE다.

| 통신 | 경로 | 바뀌는 것 |
|---|---|---|
| 같은 브리지의 컨테이너 ↔ 컨테이너 | veth → 브리지(FDB 조회) → 상대 veth | 없음 (L2 스위칭) |
| 컨테이너 → 외부 | 컨테이너의 기본 게이트웨이(브리지 IP, 예: 172.17.0.1) → 호스트 커널 IP 포워딩 → `POSTROUTING`의 MASQUERADE | 출발지 IP가 호스트 외부 인터페이스 IP로 |

브리지와 veth는 [4장](../1부-리눅스-네트워크-기초/04-veth-브리지-라우팅-ARP.md), NAT 규칙은 [5장](../1부-리눅스-네트워크-기초/05-netfilter-iptables-NAT-conntrack.md), Docker 브리지의 전체 모습은 [8장](../2부-Docker-네트워크/08-브리지-네트워크와-포트-게시.md)에서 다룬다.

### 1.4 들어오는 길: 포트 게시의 DNAT

**한 줄 요약:** `-p 8080:80`은 `PREROUTING`에서 라우팅 결정 전에 목적지를 `컨테이너IP:80`으로 바꾸고, 응답은 conntrack이 되돌린다.

```
(외부 → 호스트IP:8080)
 PREROUTING (nat) → DOCKER 체인 → DNAT: 목적지를 컨테이너IP:80 으로 변경
   → 라우팅 결정(docker0 방향) → FORWARD(filter) → docker0 → veth → 컨테이너 eth0:80
```

클라이언트는 자신이 접속한 `호스트IP:8080`만 보게 된다. 컨테이너 안에서 80번을 `listen`했다고 호스트의 8080이 열리는 것이 아니다. 이 규칙이 만들어 주는 것이다.

> 기본 경로는 위의 커널 DNAT이고, `docker-proxy`라는 사용자 공간 프로세스가 hairpin(호스트 자신이 루프백으로 게시 포트에 접속) 같은 경우를 보완하는 안전판으로 따로 있다. 상세는 [8장](../2부-Docker-네트워크/08-브리지-네트워크와-포트-게시.md)에서 다룬다.

## 코어 2. Pod에서 다른 노드의 Pod로: 평평한 네트워크

### 2.1 쿠버네티스가 요구하는 네 가지

**한 줄 요약:** 쿠버네티스는 네트워크를 직접 구현하지 않고 "Pod마다 IP, NAT 없는 Pod 간 통신"이라는 요구사항만 정하며, 구현은 CNI 플러그인에 위임한다.

1. 모든 Pod는 NAT 없이 다른 모든 Pod와 통신할 수 있다(노드가 같든 다르든).
2. 모든 노드는 NAT 없이 모든 Pod와 통신할 수 있다(kubelet 헬스체크 등).
3. Pod가 스스로 인식하는 자신의 IP는 다른 Pod가 그 Pod를 볼 때의 IP와 같다.
4. `hostNetwork: true`인 Pod는 예외다. 별도 네트워크 네임스페이스 없이 노드의 것을 공유하므로 Pod IP가 곧 노드 IP이고 포트도 노드와 공유한다.

이 모델을 **IP-per-Pod**라고 부른다. 포트 매핑 방식에서는 포트가 노드 단위 전역 자원이 되어 nginx 세 개가 8080·8081·8082를 나눠 써야 했지만, IP-per-Pod에서는 Pod마다 표준 포트(예: 80)를 그대로 쓰므로 포트 충돌 자체가 없다. 상세는 [13장](../3부-쿠버네티스-네트워크/13-쿠버네티스-네트워크-모델과-Pod-네트워크.md)에서 다룬다.

### 2.2 세 가지 IP 대역

**한 줄 요약:** 노드 CIDR은 실제 네트워크에 있고, Pod CIDR은 CNI가 라우팅하며, Service CIDR은 실재하지 않는 가상 IP다.

| 대역 | 예시 | 할당 대상 | 라우팅 가능? |
|---|---|---|---|
| 노드 CIDR | `192.168.1.0/24` | 물리/가상 머신 | 실제 네트워크에 존재 |
| Pod CIDR | `10.244.0.0/16` | Pod | CNI가 라우팅 (오버레이 또는 실제 라우팅) |
| Service CIDR | `10.96.0.0/12` | Service의 ClusterIP | 실재하지 않는 가상 IP |

클러스터 Pod CIDR은 노드별 서브넷으로 쪼개진다(예: 클러스터 `/16`을 노드별 `/24`로). 이 값은 클러스터를 만들 때 정해야 하며 운영 중에 넓히기는 번거롭다.

### 2.3 Pod 하나가 만들어질 때

**한 줄 요약:** 런타임이 네트워크 네임스페이스를 만들고 CNI 플러그인을 호출해 그 안에 인터페이스와 IP를 채우며, Pod의 컨테이너들은 pause 컨테이너가 만든 네임스페이스에 합류한다.

```
kubelet ─ CRI(RunPodSandbox) ─► 컨테이너 런타임(containerd / CRI-O)
        네트워크 네임스페이스 생성, libcni로 CNI 설정 로드
        ─► CNI 플러그인 바이너리 실행 (/opt/cni/bin/<plugin>)
        ─► 플러그인이 netns 안에 인터페이스 생성 → 결과 JSON 반환
```

CNI를 실제로 호출하는 것은 kubelet이 아니라 런타임에 내장된 libcni 클라이언트다. Pod 안의 컨테이너들이 같은 IP·같은 포트 공간을 쓰는 이유는 같은 네트워크 네임스페이스에 합류하기 때문이고, 그 네임스페이스를 소유하는 빈 프로세스가 pause 컨테이너다. (3장, [14장](../3부-쿠버네티스-네트워크/14-CNI-스펙과-IPAM.md))

### 2.4 노드를 건너가는 두 가지 방식

**한 줄 요약:** 노드 A의 Pod가 노드 B의 Pod로 갈 때, 오버레이는 패킷을 UDP로 감싸 옮기고 네이티브 라우팅은 감싸지 않고 노드 라우팅 테이블로 옮긴다.

```
오버레이(VXLAN)                                   네이티브 라우팅(BGP)
① Pod netns에서 패킷 생성(목적지 10.244.2.7)      ① Pod netns에서 패킷 생성
② veth로 노드 A의 루트 netns로                    ② 노드 A 라우팅 테이블:
③ 라우팅: 10.244.2.0/24 → dev vxlan.calico           10.244.2.0/24 via 192.168.1.11 dev eth0
   (또는 flannel.1)                               ③ 캡슐화 없이 물리 네트워크로 전송
④ VXLAN이 캡슐화: FDB에서 노드 B의 실제 IP 조회,   ④ 노드 B가 수신 → 로컬 라우팅 → Pod netns
   UDP(4789 또는 8472)로 노드 B에 전송
⑤ 노드 B가 역캡슐화 → 로컬 라우팅 → veth → Pod
```

캡슐화는 오버헤드만큼 MTU를 깎는다.

| 캡슐화 | 오버헤드 | 물리 MTU 1500일 때 Pod MTU |
|---|---|---|
| 없음 (네이티브 라우팅) | 0 | 1500 |
| IPIP | 20 bytes | 1480 |
| VXLAN | 50 bytes | 1450 |

Pod MTU가 이보다 크게 설정되면 큰 패킷이 단편화되거나 드롭되며, 증상은 "ping과 작은 요청은 되는데 큰 응답이나 TLS 핸드셰이크만 실패"하는 형태로 나타난다. 오버레이·VXLAN·MTU는 [6장](../1부-리눅스-네트워크-기초/06-오버레이-VXLAN-MTU.md), 플러그인별 경로는 [15장](../3부-쿠버네티스-네트워크/15-CNI-플러그인과-패킷-경로.md)에서 다룬다.

## 코어 3. Service로 가는 길: 이름 → 가상 주소 → 실제 Pod

### 3.1 통신은 네 가지 문제로 나뉜다

**한 줄 요약:** 주소(Pod 네트워크), 발견(Service·DNS), 전달(Service→Pod), 진입(Ingress/Gateway)은 서로 다른 문제이고 구현 주체도 다르므로 합쳐서 "쿠버네티스 네트워크가 알아서 한다"고 생각하면 원인 추적이 어렵다.

| 문제 | 의도 또는 대상 | 실제 구현 주체 | 이 책 |
|---|---|---|---|
| Pod가 통신할 인터페이스와 IP 필요 | Pod 네트워크 | CNI 플러그인과 노드 네트워크 구성 | 13&#126;15장 |
| 교체되는 Pod를 안정적인 이름으로 찾기 | Service와 DNS 이름 | CoreDNS와 API 대상 정보 | 16·18장 |
| Service 주소로 들어온 패킷을 Pod로 보내기 | Service, EndpointSlice | kube-proxy 또는 대체 데이터 경로 구현 | 16·17·22장 |
| 외부 HTTP를 앱으로 연결하기 | Ingress 또는 Gateway API | 해당 controller와 실제 LB·프록시 | 19장 |

DNS 응답이 맞아도 Pod까지 패킷이 못 갈 수 있고, Pod IP로 접속돼도 Service selector가 틀릴 수 있다.

### 3.2 클러스터 내부 요청 한 번

**한 줄 요약:** DNS가 이름을 ClusterIP로 풀고, 노드의 규칙이 ClusterIP:80을 Pod IP:8080으로 바꿔치기하며, DNS는 이름 해석만 할 뿐 매 패킷을 중계하지 않는다.

```
호출 Pod ── orders.study.svc.cluster.local 조회 ──► CoreDNS
         ◄── Service의 ClusterIP ──────────────────
호출 Pod ── ClusterIP:80 으로 TCP 연결 ──► 노드 데이터 경로(Service·EndpointSlice에 맞춘 규칙)
                                          ── 선택한 Pod IP:8080 으로 전달 ──► orders Pod
호출 Pod ◄── 연결 경로를 통한 응답 ─────────────────────────────────────────
```

Service에 `port: 80`, `targetPort: 8080`, `selector`가 있으면 "이 label의 앱을 80이라는 서비스 포트로 제공하라"는 의도이고, EndpointSlice controller가 selector와 Pod 상태를 보고 구체적인 대상 IP·포트·준비 상태를 기록한다. kube-proxy 등이 그 기록을 전달 경로에 반영한다. 이름 해석은 [18장](../3부-쿠버네티스-네트워크/18-DNS와-서비스-디스커버리.md), Service와 EndpointSlice는 [16장](../3부-쿠버네티스-네트워크/16-Service와-EndpointSlice.md)에서 다룬다.

### 3.3 ClusterIP의 정체와 kube-proxy

**한 줄 요약:** ClusterIP는 주소가 아니라 약속이며, kube-proxy가 노드 커널에 심어 둔 규칙이 목적지를 실제 Pod IP로 DNAT한다.

ClusterIP(`10.96.x.y`)는 어떤 네트워크 인터페이스에도 바인딩되어 있지 않고 라우팅 테이블에도 그 주소로 가는 물리적 경로가 없다. 그래서 `ping`에는 응답이 없다. 대신 각 노드의 규칙이 그 IP로 향하는 패킷을 가로채 실제 Pod IP로 바꾼다. kube-proxy는 각 노드에서 다음 세 단계를 한다.

```
① API 서버를 watch — Service와 EndpointSlice 변경 감지
② 노드의 데이터플레인(iptables / IPVS / nftables) 규칙 갱신
③ 실제 패킷 처리는 커널이 한다 — kube-proxy는 데이터 경로에 없다
```

iptables 모드에서는 체인이 다음 계층으로 구성된다.

```
PREROUTING / OUTPUT ─► KUBE-SERVICES ─► KUBE-SVC-<서비스 해시> ─► KUBE-SEP-<엔드포인트> ─► DNAT → Pod IP:Port
```

`KUBE-SVC-*`에서 엔드포인트를 확률적으로 고르고, `KUBE-SEP-*`에서 실제 DNAT가 일어난다. 이 분배는 연결 단위이며, conntrack이 최초 SYN에서 결정한 목적지를 연결이 끝날 때까지 유지한다.

```
요청: 클라이언트(10.244.1.9:34567) → ClusterIP(10.96.142.88:80)
        │ DNAT 적용, conntrack에 변환 정보 기록 → 실제 목적지(10.244.1.3:8080)
응답: 10.244.1.3:8080 → 10.244.1.9:34567
        │ conntrack이 "위 요청의 응답"으로 인식 → 역변환
      클라이언트가 보기엔 여전히 10.96.142.88:80에서 온 응답
```

kube-proxy 프로세스가 죽어도 이미 프로그래밍된 규칙은 커널에 남아 기존 연결은 끊기지 않는다. 다만 이후의 Service/EndpointSlice 변경은 반영되지 않는다. 자세한 규칙 읽기는 [17장](../3부-쿠버네티스-네트워크/17-kube-proxy-데이터플레인.md)에서 한다.

> kube-proxy 대신 eBPF 기반 구현이 이 역할을 맡는 경우 담당 구성요소가 달라질 수 있다([22장](../3부-쿠버네티스-네트워크/22-eBPF-데이터플레인과-Cilium.md)).

## 코어 4. 밖에서 Pod로: LoadBalancer, NodePort, Ingress

### 4.1 Service 타입은 진입점을 하나씩 더한다

**한 줄 요약:** `LoadBalancer ⊃ NodePort ⊃ ClusterIP`로, 위 타입은 아래 타입을 포함하며 새 로드밸런싱 로직이 아니라 같은 엔드포인트 목록으로 들어가는 진입점을 하나 더 추가한다.

- **ClusterIP**: 클러스터 내부 가상 주소(기본).
- **NodePort**: 모든 노드의 지정 포트(기본 범위 30000&#126;32767)가 열려, `노드IP:30080`으로 들어온 트래픽도 같은 엔드포인트로 라우팅된다. ClusterIP도 함께 할당된다.
- **LoadBalancer**: cloud-controller-manager가 클라우드 API로 로드밸런서를 만들고 각 노드의 NodePort를 백엔드로 등록한다. `EXTERNAL-IP`가 `<pending>`에 머물면 cloud-controller-manager가 없거나(베어메탈·kind 기본 환경) 권한이 부족한 것이다.
- **ExternalName**: 셀렉터·엔드포인트·ClusterIP가 없는 DNS 별칭(CNAME)이며 트래픽을 프록시하지 않는다.

### 4.2 접속자 IP는 어디서 사라지는가

**한 줄 요약:** `externalTrafficPolicy: Cluster`(기본)에서는 노드를 건너가는 외부 트래픽이 SNAT되어 원본 클라이언트 IP가 사라지고, `Local`은 SNAT가 필요 없어 보존된다.

```
Cluster(기본): 외부 클라이언트 → 노드A(Pod 없음) → [SNAT] → 노드B의 Pod
                                             └ 클라이언트 IP가 노드A의 IP로 치환됨
Local:         외부 클라이언트 → 노드B(Pod 있음) → 노드B의 Pod (원본 IP 그대로)
               외부 클라이언트 → 노드A(Pod 없음) → 응답 없음 ✗
```

`Local`은 그 노드에 백엔드 Pod가 없으면 응답이 없고, Pod 분포가 고르지 않으면 부하가 불균등해진다. 클라우드 LB의 헬스체크가 Pod 없는 노드를 제외해 주는 구성에서 권장된다. 접속자 IP를 서버가 알아야 하는 게임 서버에서 특히 확인해야 할 설정이다.

### 4.3 Ingress: 규칙과 실행자는 다르다

**한 줄 요약:** Ingress는 선언(데이터)일 뿐이고, 컨트롤러가 그 선언을 읽어 리버스 프록시를 설정해 실제 요청을 받으며, 대부분의 컨트롤러는 ClusterIP를 거치지 않고 Pod IP로 직접 프록시한다.

```
인터넷 → LB(1개) → Ingress Controller ─ shop.example.com/ → web, /api → api ... ─► Pod IP (직접)
```

Ingress 리소스만 만들고 컨트롤러가 없으면 `ADDRESS`가 비어 있는 채 아무 일도 일어나지 않는다. TLS는 컨트롤러에서 종료되고 컨트롤러 → Pod 구간은 기본적으로 평문이다. AWS의 IP target 방식에서는 ALB가 Pod IP로 직접 전달해 ClusterIP나 NodePort를 반드시 경유하지 않고, instance target 방식에서는 ALB → 노드 NodePort → Pod 경로가 된다. Ingress와 Gateway API는 [19장](../3부-쿠버네티스-네트워크/19-Ingress와-Gateway-API.md), 진입 뒤 서비스 간 통신의 암호화·제어는 [20장](../3부-쿠버네티스-네트워크/20-서비스-메시-데이터플레인.md)에서 다룬다.

### 4.4 책 전체 지도: 어디서 무엇이 바뀌는가

**한 줄 요약:** 경계마다 "주소 변경 / 캡슐화 / 변경 없음"을 구분해 두면 패킷을 tcpdump로 어느 구간에서 봐야 할지 감이 잡힌다.

| 구간 | 일어나는 일 | 담당 부품 | 장 |
|---|---|---|---|
| 컨테이너 ↔ 호스트 | 네임스페이스 경계를 veth로 넘음 | netns, veth, 브리지 | 3·4 |
| 컨테이너 → 외부 | 출발지 IP를 호스트 IP로 변경 | iptables MASQUERADE | 5·8 |
| 외부 → 컨테이너 (`-p`) | 목적지를 컨테이너 IP:포트로 변경 | iptables DNAT, conntrack | 5·8 |
| 이름 → IP | 이름 해석 | Docker 내장 DNS / CoreDNS | 9·18 |
| Pod ↔ Pod | NAT 없음 (노드 간은 캡슐화 또는 라우팅) | CNI, VXLAN/BGP | 6·13&#126;15 |
| Pod → Service | 목적지 ClusterIP를 Pod IP로 변경 | kube-proxy 규칙, conntrack | 16·17 |
| 외부 → Pod | LB·NodePort·Ingress 컨트롤러 경유 | cloud LB, kube-proxy, Ingress | 16·19 |
| 통신 허용/차단 | 트래픽 필터링 | NetworkPolicy | 21 |
| 장애 | 계층별로 잘라 진단 | 명령 모음 | 23, 부록 |

Pod A → Pod B 통신 실패를 자를 때는 ① 같은 Pod 안인가(localhost, 포트 충돌) ② 같은 노드의 다른 Pod인가(로컬 브리지/veth) ③ 다른 노드의 Pod인가(노드 간 라우팅·오버레이·MTU) ④ Service를 통하는가(엔드포인트, iptables/IPVS 규칙) ⑤ DNS 이름을 쓰는가 ⑥ NetworkPolicy가 있는가 순으로 좁힌다. 이 순서는 [23장](../4부-진단/23-네트워크-장애-진단.md)에서 완성한다.

## 실무 적용

### 체크리스트

- [ ] 컨테이너의 네트워크는 netns + veth + 호스트 브리지이며, 컨테이너 안 `listen`은 호스트 포트를 열지 않는다는 점을 안다.
- [ ] 나갈 때 출발지 변경(MASQUERADE, POSTROUTING), 들어올 때 목적지 변경(DNAT, PREROUTING), 응답 복원(conntrack)의 세 가지 짝을 말할 수 있다.
- [ ] Pod CIDR / 노드 CIDR / Service CIDR을 구분하고, Service CIDR(ClusterIP)은 어떤 인터페이스에도 붙어 있지 않다는 것을 안다.
- [ ] 노드 간 이동이 오버레이인지 네이티브 라우팅인지 확인하고, 오버레이면 MTU(VXLAN이면 1500 → 1450)를 점검한다.
- [ ] 게임 서버가 접속자 IP를 써야 한다면 `externalTrafficPolicy`와 SNAT 여부를 확인한다.
- [ ] Ingress를 만들었다면 컨트롤러가 설치되어 있는지(`ADDRESS`가 비어 있지 않은지) 확인한다.
- [ ] 장애는 같은 Pod → 같은 노드 → 다른 노드 → Service → DNS → NetworkPolicy 순으로 경계를 잘라 본다.

### 시나리오로 확인하기

1. **상황:** Pod A에서 Pod B의 Pod IP로 `curl`하면 되는데, Service 이름으로 하면 연결이 안 된다.
   **질문:** 의심 부품과 확인 순서는?

   <details markdown="1"><summary>답 확인</summary>

   Pod IP 직접 접속이 성공하면 CNI(Pod 네트워크)는 정상이므로 Service나 DNS 문제다. Service 쪽에서는 EndpointSlice에 대상과 포트가 있는지(selector·Pod Ready 불일치가 가장 흔한 원인), 이어서 호출 Pod에서 이름이 해석되는지(DNS), ClusterIP로 시험했을 때 어느 경계에서 달라지는지를 본다. → 코어 3, 코어 4 (4.4)

   </details>

2. **상황:** 게임 서버를 LoadBalancer Service 뒤에 올렸더니 서버 로그의 접속자 IP가 전부 노드 IP다.
   **질문:** 왜 그런가?

   <details markdown="1"><summary>답 확인</summary>

   `externalTrafficPolicy: Cluster`(기본)에서는 요청이 도착한 노드가 다른 노드의 Pod로 넘길 때 소스 주소를 해당 노드 IP로 치환(SNAT)하므로 Pod 입장에서는 모든 요청이 노드에서 온 것처럼 보인다. `Local`은 노드를 건너가는 재전달이 없어 SNAT가 필요 없고 클라이언트 IP가 보존되지만, Pod가 없는 노드는 응답이 없고 부하가 불균등해질 수 있으므로 LB 헬스체크와 함께 쓴다. → 코어 4 (4.2)

   </details>

3. **상황:** 새로 `Ingress`를 만들고 `kubectl get ingress`를 했는데 `ADDRESS`가 비어 있고 접속이 안 된다.
   **질문:** 먼저 의심할 것은?

   <details markdown="1"><summary>답 확인</summary>

   Ingress는 선언일 뿐이므로 이를 처리하는 IngressController가 없거나 `ingressClassName`이 맞지 않아 아무 컨트롤러도 이 오브젝트를 처리하지 않은 상태가 가장 먼저 의심된다. 컨트롤러 설치와 IngressClass 연결을 확인한다. → 코어 4 (4.3)

   </details>

### 2. 인출 질문

1. 컨테이너 안 `eth0`은 호스트와 어떻게 연결되는가?

   <details markdown="1"><summary>답 확인</summary>

   veth pair의 한쪽 끝이 컨테이너 네트워크 네임스페이스 안의 `eth0`이고, 다른 끝은 호스트에 남아 브리지(`docker0` 등)에 연결된다. 한쪽으로 들어간 패킷이 다른 쪽으로 그대로 나온다. → 코어 1 (1.1&#126;1.3)

   </details>

2. 같은 브리지 안의 통신과 외부로 나가는 통신은 무엇이 다른가?

   <details markdown="1"><summary>답 확인</summary>

   같은 브리지 안은 브리지의 MAC 주소 테이블(FDB)로 전달되는 L2 스위칭이라 라우팅도 NAT도 없다. 외부로는 게이트웨이(브리지 IP) → 호스트 IP 포워딩 → POSTROUTING의 MASQUERADE로 출발지가 호스트 IP로 바뀐다. → 코어 1 (1.3)

   </details>

3. `-p 8080:80`일 때 목적지는 어느 단계에서 바뀌고, 응답은 어떻게 돌아가는가?

   <details markdown="1"><summary>답 확인</summary>

   라우팅 결정보다 앞선 PREROUTING 단계의 DOCKER 체인 DNAT가 목적지를 컨테이너IP:80으로 바꾼다. 응답은 conntrack이 기억한 연결 정보로 되돌려져 클라이언트는 호스트IP:8080만 본다. → 코어 1 (1.4)

   </details>

4. 서로 다른 노드의 Pod가 NAT 없이 통신하는 두 방식은?

   <details markdown="1"><summary>답 확인</summary>

   오버레이(VXLAN 등)는 원본 패킷을 UDP(4789 또는 8472)로 캡슐화해 노드 B 물리 IP로 보내고 역캡슐화한다. 네이티브 라우팅(BGP 등)은 캡슐화 없이 `10.244.2.0/24 via 192.168.1.11` 같은 라우팅 테이블 경로로 보낸다. 캡슐화에는 MTU 손실이 따른다(VXLAN 50 bytes → 1450). → 코어 2 (2.4)

   </details>

5. ClusterIP에 `ping`을 보내면 왜 응답이 없는가?

   <details markdown="1"><summary>답 확인</summary>

   ClusterIP는 어떤 네트워크 인터페이스에도 바인딩되어 있지 않고 그 주소로 가는 라우팅 경로도 없다. 각 노드의 데이터플레인 규칙이 그 IP로 향하는 패킷을 실제 Pod IP로 바꿔치기하는 "약속"일 뿐이다. → 코어 3 (3.3)

   </details>

6. kube-proxy는 패킷 경로에 있는가? 죽으면 어떻게 되는가?

   <details markdown="1"><summary>답 확인</summary>

   없다. API 서버를 watch해 노드 규칙(iptables/IPVS/nftables)을 갱신할 뿐 실제 패킷 처리는 커널이 한다. 프로세스가 죽어도 이미 프로그래밍된 규칙은 남아 기존 연결은 끊기지 않지만, 이후의 Service/EndpointSlice 변경은 반영되지 않는다. → 코어 3 (3.3)

   </details>

7. 통신 문제를 네 가지로 나누면?

   <details markdown="1"><summary>답 확인</summary>

   Pod 네트워크(CNI), 이름 발견(Service·DNS), 전달(Service·EndpointSlice → kube-proxy), 진입(Ingress·Gateway)이다. DNS가 맞아도 패킷이 못 갈 수 있고, Pod IP 접속이 돼도 selector가 틀릴 수 있어 합쳐서 보면 원인 추적이 어렵다. → 코어 3 (3.1)

   </details>

8. 외부 트래픽에서 접속자 IP가 사라지는 조건과 대안은?

   <details markdown="1"><summary>답 확인</summary>

   `externalTrafficPolicy: Cluster`(기본)에서 노드를 건너 다른 노드의 Pod로 갈 때 소스가 노드 IP로 SNAT된다. `Local`은 보존하지만 Pod 없는 노드는 응답이 없고 부하가 불균등할 수 있어 LB 헬스체크와 함께 쓴다. → 코어 4 (4.2)

   </details>

9. 외부 요청이 Ingress를 거쳐 Pod에 닿을 때 ClusterIP를 꼭 거치는가?

   <details markdown="1"><summary>답 확인</summary>

   아니다. 대부분의 IngressController는 ClusterIP를 거치지 않고 Pod IP로 직접 프록시한다(kube-proxy 홉을 건너뛰어 지연이 줄고 L7 로드밸런싱을 컨트롤러가 직접 구현). AWS ALB의 IP target 방식도 ClusterIP·NodePort를 반드시 경유하지 않는다. → 코어 4 (4.3)

   </details>

### 3. 기억 고리

- **C++ 유추:** `connect(ClusterIP)` ≈ 로드밸런서 VIP로 접속. ⚠️ 그 VIP를 가진 장비가 없고, 노드 커널의 DNAT 규칙이 목적지를 실제 Pod IP로 바꾸며, kube-proxy 프로세스는 데이터 경로에 없다.
- **C++ 유추:** 공유기 포트포워딩 ≈ `-p`. ⚠️ 별도 장비가 아니라 같은 커널의 PREROUTING에서 라우팅 결정 전에 바뀌고 응답은 conntrack이 되돌린다.
- **비유:** 패킷 = 택배. 아파트 단지(호스트)로 들어갈 때 대표 번호(호스트IP:8080)가 세대 번호(컨테이너IP:80)로 바뀌어 배달되고(DNAT), 나갈 때는 보내는 사람 주소가 단지 대표 주소로 바뀐다(MASQUERADE). 단지 사이를 이동하는 큰 화물은 겉 상자(VXLAN)에 한 번 더 담겨 가므로 상자 두께만큼 적재량(MTU)이 줄어든다. ⚠️ 비유가 깨지는 지점: 변환을 하는 "관리실"은 사람이 아니라 커널 규칙이고, 변환 정보를 기억해 응답을 되돌리는 것은 conntrack이다.
- **묶음(3의 법칙):** 주소가 바뀌는 곳 3 (나갈 때 MASQUERADE / 들어올 때 `-p` DNAT / Service DNAT) · 노드 건너는 방식 3 (오버레이 / 네이티브 라우팅 / 클라우드 네이티브 IP) · Service 진입 계층 `LoadBalancer ⊃ NodePort ⊃ ClusterIP`.
- **대칭·순서:** 출발지 변경(POSTROUTING) ↔ 목적지 변경(PREROUTING). 문제 4분해 순서: 주소 → 발견 → 전달 → 진입. 장애를 자르는 순서: 같은 Pod → 같은 노드 → 다른 노드 → Service → DNS → NetworkPolicy.

> **묶음 설명:** "클라우드 네이티브 IP"는 `kubernetes-textbook-main` 23장(23.2)이 오버레이·네이티브 라우팅에 이어 세 번째로 드는 방식이다. Pod가 VPC의 실제 IP를 받아(예: AWS VPC CNI는 ENI 보조 IP) 오버레이도 라우팅 설정도 필요 없지만, IP 고갈과 노드당 Pod 수 제한이 단점이다. 이 책에서는 [15장](../3부-쿠버네티스-네트워크/15-CNI-플러그인과-패킷-경로.md)에서 다룬다.
