# 20장. 서비스 메시 데이터플레인

> **🎮 게임 서버 개발자에게** — 게임 서버 사이(매치메이킹 ↔ 게임룸 ↔ DB 프록시)의 통신에 재시도, 타임아웃, 암호화, 호출 로그를 넣으려면 보통 각 서버 코드에 라이브러리로 심었다. 언어가 여러 개면 언어마다 다시 구현해야 하고 정책도 어긋난다. 서비스 메시는 이것을 **앱 옆에 붙은 프록시(사이드카)** 로 옮긴다. 앱은 평소처럼 `connect()`/`send()`를 하지만, 그 패킷은 커널 규칙으로 옆의 프록시를 먼저 거친다. 결정적으로 다른 점은, 앱이 이 사실을 **전혀 모른다**는 것이다(네트워크 네임스페이스 수준에서 강제로 우회된다). 이 장은 구현법이 아니라 **데이터플레인이 어디에 놓이고 무엇을 대가로 치르는가**를 개념 수준에서 다룬다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 서비스 간 호출을 모두 mTLS로 암호화하라는 규제 요구가 왔는데 앱을 일일이 고칠 수 없다 → 메시가 후보다. 하지만 정말 필요한지부터 판단한다.
> - 서비스 메시를 켰더니 Pod마다 컨테이너가 하나씩 늘고 메모리가 불어난다 → 사이드카 모델의 비용, 앰비언트 모드를 검토한다.
> - "요청이 실패하는데 앱 로그에는 아무것도 없다" → 사이드카 프록시가 앞에서 막고 있을 가능성(디버깅 대상이 하나 더 생겼다).

## 코어 — 이것만은 100%

> **한 문장:** 서비스 메시는 서비스 간(동서) 트래픽을 프록시 계층(사이드카 또는 노드 공유 ztunnel/waypoint)이 가로채 mTLS·재시도·트래픽 분할·관측을 앱 코드 수정 없이 제공하는 구조이며, 그 대가는 리소스·지연·복잡도라서 문제를 이미 겪을 때 도입해도 늦지 않다.

1. **프록시가 앱 옆에서 트래픽을 강제로 가로챈다** — 사이드카는 뮤테이팅 어드미션 웹훅이 Pod 생성 시 주입하고, init 컨테이너가 심은 iptables 규칙으로 모든 인/아웃바운드가 프록시를 거친다. 앱은 모른다.
2. **프록시 계층이 대신 해 주는 일** — 사이드카 사이 구간의 mTLS(워크로드 신원은 단기 인증서), 재시도·타임아웃·서킷 브레이커·카나리 가중치, 균일한 관측 데이터.
3. **사이드카 vs 앰비언트: 격리 대 효율, 그리고 도입 판단** — 앰비언트는 노드당 공유 ztunnel(L4/mTLS)과 선택적 waypoint(L7)로 Pod당 오버헤드를 없애는 대신 격리를 노드 단위로 완화한다. 메시는 서비스가 많고 규제·일관된 트래픽 제어가 필요할 때 정당화된다.

**이 장의 학습 목표**

- 남북 트래픽(Ingress/Gateway)과 동서 트래픽(서비스 메시)을 구분한다.
- 사이드카 주입 흐름(웹훅 → 사이드카 + iptables init 컨테이너)과 트래픽 강제 우회를 설명한다.
- mTLS, L7 트래픽 제어, 관측성을 프록시 계층이 대신하는 방식을 설명한다.
- 사이드카 모델과 앰비언트 모델의 트레이드오프를 비교한다.
- 메시가 정당화되는 신호와 과한 신호를 구분한다.

| 모든 서버 프로세스에 붙는 에이전트 | 사이드카의 Pod당 1개 비용 vs 노드당 1개 ztunnel | 에이전트가 늘수록 자원을 먹는다 | 앰비언트는 Pod당 프록시를 없애고 노드 공유로 바꾸는 대신 격리가 약해진다 |

## 코어 1. 프록시가 앱 옆에서 트래픽을 강제로 가로챈다

### 1.1 남북 vs 동서

**한 줄 요약:** Ingress/Gateway는 외부 ↔ 클러스터(남북), 서비스 메시는 서비스 ↔ 서비스(동서)를 다룬다. 둘 다 "리버스 프록시를 어디에 둘 것인가"에서 출발한다.

```
        Ingress/Gateway (남북) ← 19장
             │
    ┌────────▼────────┐
    │   서비스 A       │
    └───┬─────────┬───┘
        │         │      서비스 메시 (동서) ← 이 장
    ┌───▼───┐ ┌───▼───┐
    │서비스B │ │서비스C │
    └───────┘ └───────┘
```

[19장](19-Ingress와-Gateway-API.md)의 진입점을 통과한 뒤, 서비스 사이의 통신을 어떻게 암호화하고 제어하고 관측하는가가 이 장의 질문이다. 위치로 보면 [16장](16-Service와-EndpointSlice.md)·[17장](17-kube-proxy-데이터플레인.md)의 L4 Service 위, L7 계층이다.

### 1.2 사이드카 주입: 웹훅이 프록시를 끼워 넣는다

**한 줄 요약:** 뮤테이팅 어드미션 웹훅이 Pod 생성 직전에 사이드카 프록시와 iptables 설정용 init 컨테이너를 스펙에 추가한다.

```
Pod 생성 요청
     │
     ▼
MutatingAdmissionWebhook  (istiod, linkerd-proxy-injector 등)
  namespaceSelector로 주입 대상 판단 (예: istio-injection=enabled 라벨)
  spec.containers에 사이드카 프록시 추가
  spec.initContainers에 iptables 규칙 설정용 initContainer 추가
     │
     ▼
Pod (2개 이상의 컨테이너)
  app 컨테이너 ──▶ sidecar (Envoy) ──▶ 외부
  모든 인/아웃바운드 트래픽이 iptables(또는 eBPF)로 사이드카를 거치도록 강제 리다이렉트된다
```

핵심은 **init 컨테이너가 iptables 규칙을 심는다**는 것이다. 앱 컨테이너는 자신이 사이드카를 거친다는 사실을 모르고, 네트워크 네임스페이스 수준에서 트래픽이 우회된다. [17장](17-kube-proxy-데이터플레인.md)에서 본 iptables 리다이렉트 메커니즘(`REDIRECT`/`DNAT` 타깃)이 kube-proxy와 무관하게 여기서도 쓰인다. 네임스페이스와 iptables의 기초는 [3장](../1부-리눅스-네트워크-기초/03-네트워크-네임스페이스.md), [5장](../1부-리눅스-네트워크-기초/05-netfilter-iptables-NAT-conntrack.md)이다.

> **[보충]** 어드미션 웹훅은 API 서버가 객체를 저장하기 전에 외부 서버에 호출해 객체를 수정·검증하게 하는 확장 지점이다. 이 책에서 따로 다루지 않으므로, "Pod 생성 요청을 중간에서 가로채 스펙을 고쳐 주는 훅" 정도로 이해하면 충분하다. 원천은 이 웹훅이 응답하지 않으면 Pod 생성이 지연되거나 실패할 수 있다는 가용성 위험을 지적한다.

### 1.3 네이티브 사이드카 컨테이너

**한 줄 요약:** `restartPolicy: Always`를 가진 `initContainer`로 사이드카를 정의하면 kubelet이 시작·종료 순서를 직접 보장한다.

과거에는 사이드카를 `spec.containers`에 평범한 컨테이너로 넣었기 때문에, app보다 먼저 준비되고 app이 끝난 뒤에도 로그·트레이스 flush가 끝날 때까지 살아 있어야 한다는 요구를 충족하기 어려웠다. **네이티브 사이드카 컨테이너**(`restartPolicy: Always`인 `initContainer`)는 kubelet이 순서를 보장하는 정식 기능이다. 원천에 따르면 1.29에서 베타로 기본 활성화됐고 1.33 무렵에는 안정적인 실무 관행이며, Istio·Linkerd 등 최신 메시 구현체는 대부분 이 방식으로 프록시를 주입한다.

## 코어 2. 프록시 계층이 대신 해 주는 일

### 2.1 mTLS: 앱이 모르는 사이에 양방향 인증

**한 줄 요약:** 일반 Pod 간 통신은 평문이지만, 사이드카가 주입되면 두 사이드카 사이가 mTLS로 암호화되고 앱 코드는 그대로다.

```
서비스 A                                          서비스 B
app ─평문 HTTP(localhost)→ sidecar A ══mTLS══▶ sidecar B ─평문 HTTP(localhost)→ app
                                      (양방향 상호 인증)
```

각 사이드카는 워크로드마다 발급된 **단기(short-lived) 인증서**를 갖고, 컨트롤 플레인(Istiod 등)이 자동으로 로테이션한다. "제로 트러스트"라 불리는 이유는 둘이다.

1. **양방향 인증**이므로 클라이언트도 서버도 서로의 신원을 확인한다. 네트워크 위치(같은 서브넷, 같은 클러스터)를 신뢰의 근거로 삼지 않는다.
2. 워크로드 신원이 **SPIFFE/SPIRE 계열의 짧은 수명 인증서**로 표현되므로, IP나 노드가 아니라 **워크로드 자체의 신원**으로 "누가 누구를 호출할 수 있는가"를 정책으로 쓸 수 있다.

> **🎮 연결** — 게임 서버 간에 "이 IP 대역이면 믿는다"는 식의 신뢰를 했다면, 메시는 그 가정을 버리고 서버 하나하나가 신분증(인증서)을 들고 다닌다고 보면 된다.

### 2.2 L7 트래픽 제어를 프록시로

**한 줄 요약:** 재시도·타임아웃·서킷 브레이커·카나리·폴트 인젝션을 앱이 아니라 프록시 레이어의 공통 기능으로 옮긴다.

| 기능 | 프록시가 하는 일 |
|---|---|
| 재시도 | 특정 상태 코드(예: 5xx)에서 자동 재시도, 백오프 정책 |
| 타임아웃 | 업스트림 응답이 늦으면 강제 종료 |
| 서킷 브레이커 | 연속 실패가 임계치를 넘으면 해당 백엔드로의 요청을 일시 차단 |
| 카나리 가중치 | 여러 백엔드로 정확한 비율로 분배(Gateway API의 `weight`와 같은 개념이 동서 트래픽에도 적용) |
| 폴트 인젝션 | 의도적으로 지연·오류를 주입해 장애 내성 테스트 |

앱을 Go로 짜든 Java든 Python이든 사이드카가 앞을 가로막고 있으므로 같은 정책이 적용된다.

### 2.3 관측성: 모든 홉이 프록시라서 균일하다

**한 줄 요약:** 모든 호출이 사이드카를 거치므로 요청량·지연 분포(p50/p90/p99)·오류율·분산 트레이스 스팬을 앱 수정 없이 같은 형식으로 얻는다.

```
service-a ──▶ service-b ──▶ service-c
   │envoy        │envoy        │envoy
   ▼             ▼             ▼
동일한 형식의 요청량, 지연 분포(p50/p90/p99), 오류율, 분산 트레이스 스팬
```

한계도 분명하다. 이것은 **네트워크 계층의 관측**이다. 애플리케이션 내부 로직(DB 쿼리 지연 등)까지 보려면 OpenTelemetry 같은 앱 계측이 여전히 필요하다.

## 코어 3. 사이드카 vs 앰비언트, 그리고 도입 판단

### 3.1 사이드카 모델의 비용

**한 줄 요약:** Pod마다 프록시 하나라서 자원이 Pod 수에 비례하고, 주입이 Pod 시작에 영향을 주며, 디버깅 대상이 늘어난다.

- **Pod마다 프록시 컨테이너 하나.** Pod가 1,000개면 프록시도 1,000개다. 원천은 메모리 수십&#126;수백 MB × 1,000(internals), 프록시당 메모리 50&#126;100MB와 CPU 오버헤드(textbook)라고 적는다.
- **지연.** 요청마다 프록시를 두 번 통과해 보통 1&#126;3ms가 추가된다(textbook).
- **주입 실패가 Pod 시작을 막을 수 있다.** 웹훅이 응답하지 않으면 Pod 생성이 지연되거나 실패한다.
- **시작 순서 문제.** app보다 사이드카가 먼저 준비되어야 트래픽을 놓치지 않는다. 네이티브 사이드카가 이 문제는 해결했지만 Pod마다 프록시가 하나씩 떠 있어야 한다는 사실은 그대로다.
- **복잡도·학습 곡선.** "요청이 실패하는데 앱 로그에는 아무것도 없다" 같은 상황이 늘고, Istio의 개념(VirtualService, DestinationRule, PeerAuthentication 등)을 팀이 알아야 한다.

> **[보충]** 메모리 수치가 두 원천에서 다르다(수십&#126;수백 MB vs 50&#126;100MB). 구현체와 설정에 따라 달라지는 값이므로 "Pod당 수십 MB 이상, 수가 곱해진다"는 규모감으로만 기억한다.

### 3.2 앰비언트 모드: ztunnel + waypoint

**한 줄 요약:** Pod마다 프록시를 붙이지 않고, 노드당 하나의 공유 ztunnel(L4/mTLS)과 필요한 곳에만 두는 waypoint(L7)로 기능을 두 계층으로 나눈다.

```
노드 A
  Pod 1(사이드카 없음)  Pod 2(사이드카 없음)
        │                   │
        └────────▶ ztunnel (노드당 1개)
                     · mTLS 종료/시작
                     · L4 라우팅
                     · 기본 L4 정책 강제
                        │ mTLS로 암호화된 L4 터널
                        ▼
              waypoint proxy (네임스페이스 또는 서비스 어카운트 단위, 선택적)
                     · L7 라우팅, 재시도, 서킷 브레이커, 헤더 기반 정책
                     · L7 기능이 실제로 필요한 워크로드에만 배치
```

ztunnel은 노드마다 하나만 존재하는 공유 프록시로 해당 노드의 모든 Pod를 대신해 mTLS와 L4 라우팅·기본 정책을 처리한다. Pod에는 프록시 컨테이너가 없고, 커널 수준 리다이렉트(예: eBPF 또는 노드 네트워크 네임스페이스 설정)로 Pod 트래픽이 ztunnel을 거치게 한다. waypoint는 L7 기능(헤더 매칭, 재시도, 트래픽 분할)이 필요한 네임스페이스·서비스 어카운트에만 배치하고, L4 mTLS만 필요한 대다수 워크로드는 ztunnel만으로 충분하다.

### 3.3 트레이드오프: 격리 대 효율

**한 줄 요약:** 사이드카는 Pod 단위 격리가 강하고 자원 오버헤드가 Pod 수에 비례하며, 앰비언트는 노드 공유로 오버헤드를 줄이는 대신 L4 계층 격리가 노드 단위로 약해진다.

| | 사이드카 모드 | 앰비언트 모드 |
|---|---|---|
| Pod당 오버헤드 | 프록시 컨테이너 1개씩(메모리·CPU) | 없음(ztunnel이 노드당 공유) |
| L7 기능 적용 범위 | 모든 Pod에 항상 존재 | waypoint를 배치한 곳에만 |
| 격리 수준 | Pod 단위로 강함(프록시가 전용) | ztunnel은 노드 내 워크로드가 공유 |
| 주입 실패의 영향 범위 | 해당 Pod만 | ztunnel 장애 시 그 노드의 모든 Pod 영향 |
| 도입 복잡도 | Pod 재시작(주입)이 필요 | 상대적으로 낮음, 사이드카 재주입 불필요 |
| 적합한 상황 | 워크로드마다 세밀한 L7 제어가 상시 필요 | 대다수는 mTLS만 필요하고 일부만 L7 제어 필요 |

**Cilium과의 접점:** Cilium도 서비스 메시 기능(mTLS, L7 가시성)을 eBPF 데이터플레인 위에서 사이드카 없이 제공하는 방향으로 발전해 왔다. 앰비언트의 "노드 단위 공유 처리"를 커널 레벨에서 구현한다고 보면 [22장](22-eBPF-데이터플레인과-Cilium.md)과 연결된다.

| 구현 | 아키텍처 | 특징 |
|---|---|---|
| **Istio** | 사이드카(+ Ambient 모드) | 기능 최다, 복잡도 최고 |
| **Linkerd** | 사이드카(경량 Rust 프록시) | 단순함 지향, 리소스 적게 씀 |
| **Cilium Service Mesh** | eBPF(사이드카 없음) | 커널 레벨, 오버헤드 적음 |
| **Istio Ambient** | ztunnel(노드 단위) + waypoint | 사이드카 제거로 비용 절감 |

### 3.4 도입 판단: 필요한 문제를 이미 겪고 있는가

**한 줄 요약:** 서비스가 많고 규제·일관된 제어가 필요하면 정당화되고, 필요한 게 관측·분할·격리 하나뿐이면 더 가벼운 도구로 충분하다.

| 메시가 정당화되는 신호 | 메시가 과한 신호 |
|---|---|
| 서비스가 20개를 넘고 서로 복잡하게 호출한다 | 서비스가 10개 미만이다 |
| 모든 서비스 간 통신에 mTLS가 규제상 요구된다(금융, 의료) | 팀이 작고 쿠버네티스 자체도 아직 익숙하지 않다 |
| 서비스 간 호출의 분산 트레이싱이 필요한데 앱을 일일이 수정할 수 없다 | 필요한 것이 관측성뿐 → OpenTelemetry 라이브러리로 충분 |
| 정교한 트래픽 제어(서킷 브레이커, 재시도)가 여러 서비스에 일관되게 필요하다 | 필요한 것이 트래픽 분할뿐 → 인그레스 카나리나 Argo Rollouts로 충분 |
| | 필요한 것이 네트워크 격리뿐 → NetworkPolicy([21장](21-NetworkPolicy와-네트워크-보안.md))로 충분 |

원천의 결론은 "메시를 도입하기 전에, 그것이 해결할 문제를 이미 겪고 있는지 확인하라. 필요해진 뒤에 도입해도 늦지 않다"이다.

> **[보충]** 위 20개/10개 같은 숫자는 textbook이 제시한 판단 기준의 예시이며 절대 기준은 아니다. 두 숫자 사이(10&#126;20개)는 원천이 규정하지 않은 회색 지대다.

## 실무 적용

### 체크리스트

- [ ] 메시를 도입하기 전에 해결하려는 문제(mTLS, 일관된 재시도/타임아웃, 분산 트레이싱)를 이미 겪고 있는지 적어 본다. 관측성만이면 OpenTelemetry, 분할만이면 인그레스 카나리, 격리만이면 NetworkPolicy를 먼저 고려한다.
- [ ] 사이드카 모델을 쓴다면 Pod당 프록시 비용(메모리·CPU, 요청당 1&#126;3ms)과 웹훅 가용성 위험을 감안한다.
- [ ] 사이드카는 네이티브 사이드카 방식(`restartPolicy: Always` init 컨테이너)으로 주입되는지 구현체 설정을 확인한다.
- [ ] 대규모 클러스터에서 "mTLS만 필요한데 사이드카 오버헤드가 크다"면 앰비언트(ztunnel + 필요한 곳에만 waypoint)를 검토하되, ztunnel 장애가 노드 전체에 영향을 준다는 점을 감안한다.
- [ ] 메시가 주는 관측은 네트워크 계층 한정임을 기억하고, 앱 내부 지연은 앱 계측으로 본다.
- [ ] Ingress → 컨트롤러 → Pod 구간이 평문이므로, 그 구간 암호화가 필요하면 메시(또는 백엔드 프로토콜 설정)를 쓴다.

### 시나리오로 확인하기

1. **상황:** 금융 규제로 모든 서비스 간 통신에 mTLS가 필요해졌다. 서비스는 30개이고 언어가 섞여 있다. 앱 팀은 코드를 못 고친다.
   **질문:** 메시가 적합한가? 어떤 구조인가?

   <details markdown="1"><summary>답 확인</summary>

   적합하다. 서비스가 20개를 넘고 mTLS가 규제상 요구되며 앱을 수정할 수 없다는 정당화 신호에 모두 해당한다. 사이드카가 두 사이드카 사이 구간을 mTLS로 암호화하고 앱↔사이드카는 localhost 평문이므로 앱 코드는 그대로다. 인증서는 컨트롤 플레인이 자동 로테이션한다. → 코어 2, 코어 3 (3.4)

   </details>

2. **상황:** 메시 도입 후 Pod 1,000개 클러스터의 메모리가 크게 늘었다. 대부분 워크로드는 L4 mTLS만 필요하다.
   **질문:** 구조를 어떻게 바꿀 수 있고 무엇을 포기하는가?

   <details markdown="1"><summary>답 확인</summary>

   앰비언트 모드로 바꿔 Pod당 사이드카를 없애고 노드당 ztunnel(mTLS/L4)을 공유하며, L7이 필요한 곳에만 waypoint를 둔다. 포기하는 것은 Pod 단위 격리다(ztunnel은 노드 내 워크로드가 공유하고, 장애 시 그 노드의 모든 Pod가 영향을 받는다). 또 L7 기능은 waypoint를 배치한 곳에만 적용된다. → 코어 3 (3.2, 3.3)

   </details>

3. **상황:** 팀이 서비스 8개를 운영하는데 "카나리 배포를 정확한 비율로 하고 싶다"는 이유로 메시 도입을 제안한다.
   **질문:** 어떻게 판단하는가?

   <details markdown="1"><summary>답 확인</summary>

   서비스가 10개 미만이고 필요한 것이 트래픽 분할뿐이므로 과한 신호다. 인그레스 카나리(가중치 애노테이션)나 Gateway API의 `backendRefs[].weight`, Argo Rollouts로 충분하다. → 코어 3 (3.4), [19장](19-Ingress와-Gateway-API.md)

   </details>

1. 서비스 메시와 Ingress/Gateway는 어떤 트래픽을 각각 다루는가?

   <details markdown="1"><summary>답 확인</summary>

   Ingress/Gateway는 외부 → 클러스터(남북), 서비스 메시는 서비스 ↔ 서비스(동서) 트래픽이다. → 코어 1 (1.1)

   </details>

2. 앱이 모르게 사이드카를 거치게 만드는 두 부품은?

   <details markdown="1"><summary>답 확인</summary>

   ① 뮤테이팅 어드미션 웹훅이 Pod 생성 시 사이드카 프록시와 init 컨테이너를 스펙에 주입 ② init 컨테이너가 심은 iptables(또는 eBPF) 리다이렉트 규칙이 모든 인/아웃바운드를 사이드카로 보낸다. → 코어 1 (1.2)

   <details markdown="1"><summary>답 확인</summary>

   두 사이드카 사이 구간이 mTLS이고 앱↔사이드카는 localhost 평문이다. 이유: ① 양방향 인증이라 네트워크 위치를 신뢰 근거로 삼지 않는다 ② 워크로드 신원이 SPIFFE/SPIRE 계열 단기 인증서로 표현되어 IP·노드가 아니라 워크로드 신원으로 정책을 쓴다. → 코어 2 (2.1)

   </details>

4. 서킷 브레이커와 재시도를 앱이 아니라 프록시에 두면 무엇이 좋은가?

   언어마다 라이브러리로 재구현할 필요 없이 일관된 정책을 적용한다. 앱은 정책의 존재를 알 필요가 없다. → 코어 2 (2.2)

   </details>

   </details>

   <details markdown="1"><summary>답 확인</summary>

   ztunnel: 노드당 하나의 공유 프록시로 mTLS, L4 라우팅, 기본 L4 정책. waypoint: L7 기능(헤더 매칭, 재시도, 트래픽 분할)이 필요한 네임스페이스·서비스 어카운트에만 선택적으로 배치. → 코어 3 (3.2)

   "격리 대 효율". 사이드카는 Pod 전용 프록시라 격리가 강하지만 오버헤드가 Pod 수에 비례한다. 앰비언트는 노드 공유로 오버헤드를 줄이지만 L4 계층에서 노드 내 워크로드가 프록시를 공유하고, ztunnel 장애 시 그 노드의 모든 Pod가 영향을 받는다. → 코어 3 (3.3)

   </details>

8. 서비스 메시가 과한 경우 세 가지 대안은?

   <details markdown="1"><summary>답 확인</summary>

   </details>

### 3. 기억 고리

- **C++ 유추:** 사이드카 = 서버 옆에 붙은 로컬 프록시(localhost 중계). ⚠️ 깨지는 곳: 로컬 프록시는 앱이 주소를 알고 연결하지만, 사이드카는 init 컨테이너의 iptables 규칙이 앱 모르게 **강제로** 트래픽을 돌린다. 또 앱↔사이드카는 평문, 사이드카끼리만 mTLS다.
- **비유:** 사이드카 = 모든 직원에게 붙은 개인 비서(번역·보안·기록). 앰비언트 = 층마다 공용 비서실(ztunnel)과 특별 업무만 맡는 전담 팀(waypoint). ⚠️ 비유가 깨지는 지점: 개인 비서는 격리되어 있지만 공용 비서실은 한 곳이 멈추면 그 층 전체가 영향을 받는다. 또 비서(프록시)가 일을 잘해도 직원(앱) 내부의 일(쿼리 지연)은 못 본다.
- **묶음(3의 법칙):** 코어 3개(강제 우회 / 프록시가 대신 / 사이드카 vs 앰비언트·판단), 프록시가 주는 가치 3개(mTLS 보안 / 트래픽 제어 / 관측성), 비용 3개(리소스·지연·복잡도).
- **대칭·순서:** 남북(Ingress) ↔ 동서(메시), 사이드카(Pod당) ↔ 앰비언트(노드당 + 선택적 waypoint), 정당화 신호 ↔ 과한 신호.
