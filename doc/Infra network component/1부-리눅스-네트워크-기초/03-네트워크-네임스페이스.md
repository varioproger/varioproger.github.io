# 3장. 네트워크 네임스페이스

> **🎮 게임 서버 개발자에게** — 같은 머신에 게임 서버 프로세스를 여러 개 띄우면 포트가 겹치지 않게 서버마다 `7001`, `7002`, ...를 나눠 쓰던 기억이 있을 것이다. 컨테이너는 이 문제를 **프로세스마다 "네트워크 스택 한 벌"을 따로 보게 만들어서** 푼다. 인터페이스, 라우팅 테이블, 방화벽 규칙, 포트 바인딩 공간이 통째로 분리되므로 서버마다 `0.0.0.0:80`을 그대로 쓴다. 결정적으로 다른 점은, 이것은 가상 머신처럼 자원을 복제하는 것이 아니라 **같은 커널이 프로세스에게 보여 주는 뷰만 바꾸는 것**이라는 점이다. 그래서 "컨테이너"라는 커널 객체는 존재하지 않고, 네임스페이스가 붙은 평범한 프로세스가 있을 뿐이다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 이미지에 `ip`·`ss`·셸이 없어서(distroless) 컨테이너 안 네트워크를 볼 수 없을 때, 호스트에서 `nsenter`로 그 컨테이너의 네트워크 네임스페이스에 들어가 확인해야 한다.
> - Pod 안 컨테이너 A가 죽어도 Pod IP가 유지되는 이유, 같은 Pod 컨테이너끼리 `localhost`로 통신되는 이유를 설명해야 한다.
> - `--net=host`로 띄운 컨테이너가 정말 호스트 네트워크를 쓰는지 inode 번호로 증명해야 한다.

## 코어 — 이것만은 100%

> **한 문장:** 네트워크 네임스페이스는 인터페이스·라우팅 테이블·방화벽 규칙·소켓·포트 공간을 프로세스 그룹별로 다르게 "보이게" 하는 커널 기능(막 만든 것은 `lo` 하나뿐인 빈 껍데기)이고, `/proc/[pid]/ns/`의 inode 번호로 식별하고 `setns`로 합류하며, 쿠버네티스 Pod는 pause가 소유한 네임스페이스에 앱 컨테이너가 합류한 구조라 `ip netns`+`unshare`로 손으로 재현되고, 네임스페이스는 격리의 한 축일 뿐이라 권한은 capability 비트마스크와 seccomp 프로파일이 따로 막는다.

1. **네임스페이스는 복제가 아니라 "뷰"이고, 네트워크 네임스페이스는 가장 구현이 복잡한 축이다** — 같은 커널·CPU·물리 NIC를 공유하되 라우팅 테이블뿐 아니라 방화벽 규칙·소켓·`/proc/net` 통계까지 네임스페이스별로 독립 유지된다(2.6.29 전후로 점진적 완성). 새 네임스페이스에는 `lo` 하나만 있고 DOWN 상태다.
2. **`/proc/[pid]/ns/`의 inode 번호로 같은 네임스페이스인지 판별하고, `setns`로 합류한다** — 새로 만들기(`clone`/`unshare`)와 합류하기(`setns`)는 다른 시스템콜이고, 링크는 실제로 열 수 있는 fd라서 `nsenter`가 호스트의 도구를 가지고 들어간다. `ip netns`와 Docker는 서로 다른 경로에 네임스페이스를 등록한다.
3. **격리보다 "공유"가 설계다** — Pod는 pause가 네임스페이스를 소유하고 나머지가 합류하는 구조이고, 손으로 만든 `ip netns` Pod에서 같은 IP·포트 공간(`net`)과 분리된 `pid`/`mnt`가 검증된다. 컨테이너 런타임은 이 과정을 OCI 스펙에 따라 자동화할 뿐이다.
4. **네임스페이스는 가시성 한 축일 뿐이다** — "무엇을 할 수 있는가"는 capability(유효 capability는 `/proc/self/status`의 비트마스크)와 seccomp(허용 시스템 콜 필터)가 따로 막으며, `NET_ADMIN` 없이는 `ip link set lo down`도 실패한다.

**이 장의 학습 목표**

- 네트워크 네임스페이스가 왜 가장 복잡한 네임스페이스인지, 격리하는 것과 격리하지 않는 것을 구분한다.
- `ls -l /proc/<pid>/ns/`, `lsns -t net`, `nsenter`, `ip netns`로 네임스페이스를 보고 들어가며, `--net=host` 컨테이너의 inode가 호스트와 같음을 확인한다.
- pause 컨테이너가 하는 두 가지 일과 `pause.c`가 시그널 핸들러를 직접 등록하는 이유를 설명한다.
- 빈 네임스페이스를 만들어 Pod처럼 쓰는 절차와 런타임이 하는 일을 대응시킨다.
- capability 비트마스크를 읽고 `capsh`로 제거 실험을 하며, seccomp 프로파일의 기본 동작(`SCMP_ACT_ERRNO`)을 안다.

## 코어 1. 네임스페이스는 복제가 아니라 "뷰"다

### 1.1 네임스페이스란 무엇인가

**한 줄 요약:** 네임스페이스는 커널의 전역 자원을 프로세스 그룹별로 다르게 "보이게" 할 뿐이며, "컨테이너"라는 커널 객체는 없고 다섯 축을 조합한 프로세스가 있을 뿐이다.

> **입문 책에서 배운 것:** 네임스페이스는 커널 질의 결과를 걸러 주는 렌즈이고, 컨테이너 10개도 같은 커널·CPU·물리 NIC를 공유하며, 8가지 중 네트워크가 인터페이스·라우팅·방화벽·포트 공간을 분리한다([입문 책 6장](../../Docker%20와%20Kubernetes로%20인프라%20구축할때%20알아야하는%20필수%20이론%20지식/2부-컨테이너와-Docker/06-컨테이너-격리-네임스페이스.md)).

"컨테이너"를 이루는 것은 다음 다섯 축이다.

```
namespaces    무엇을 볼 수 있는가           PID, NET, MNT, UTS, IPC, USER, CGROUP, TIME
cgroups       얼마나 쓸 수 있는가           cpu, memory, io, pids, hugetlb
capabilities  무엇을 할 수 있는가           CAP_NET_ADMIN, CAP_SYS_ADMIN, ...
union FS      파일 시스템을 어떻게 쌓는가    overlayfs (lowerdir + upperdir → merged)
seccomp/LSM   어떤 시스템콜을 호출할 수 있는가  seccomp-bpf, AppArmor, SELinux
```

호스트에서 `ps aux`로 보면 그냥 프로세스다. 이 책은 그중 네트워크 네임스페이스(이 코어와 코어 2·3)와 권한 축의 capability·seccomp(코어 4)를 다룬다.

### 1.2 네트워크 네임스페이스가 가장 복잡한 이유

**한 줄 요약:** 네트워크 네임스페이스(`CLONE_NEWNET`)는 라우팅 테이블뿐 아니라 방화벽 규칙, 소켓, `/proc/net` 하위 통계까지 네임스페이스별로 독립 유지해야 해서 8개 중 구현이 가장 복잡한 축에 속한다.

그 때문에 도입도 점진적이었다. 아래는 원천의 도입 시점 표다(배포판에 따라 백포트 여부가 다를 수 있어 실제 사용 가능 여부는 각 배포판의 커널 설정으로 확인한다).

| 네임스페이스 | 플래그 | 커널 버전 | 격리 대상 |
|---|---|---|---|
| Mount | `CLONE_NEWNS` | 2.4.19 | 마운트 테이블 |
| UTS | `CLONE_NEWUTS` | 2.6.19 | 호스트 이름, NIS 도메인 |
| IPC | `CLONE_NEWIPC` | 2.6.19 | System V IPC, POSIX 메시지 큐 |
| PID | `CLONE_NEWPID` | 2.6.24 | 프로세스 ID 공간 |
| **Network** | **`CLONE_NEWNET`** | **2.6.29 전후** | **네트워크 인터페이스, 라우팅, 방화벽** |
| User | `CLONE_NEWUSER` | 3.8 | UID/GID 매핑 |
| cgroup | `CLONE_NEWCGROUP` | 4.6 | cgroup 계층 뷰 |
| Time | `CLONE_NEWTIME` | 5.6 | 부팅 이후 경과 시각 클록 |

각 컨테이너는 기본적으로 자기만의 loopback(`lo`)과 veth pair의 한쪽 끝을 가진다. 이것이 컨테이너마다 독립적으로 `0.0.0.0:80`을 바인딩할 수 있는 이유이며, 이 네임스페이스는 이후 브리지·오버레이·nftables 논의의 근간이다.

### 1.3 새 네임스페이스는 비어 있다

**한 줄 요약:** 막 만든 네트워크 네임스페이스에는 `lo` 하나만 있고 DOWN 상태다.

```bash
ip netns add pod-lab
ip netns exec pod-lab ip addr
```

```
1: lo: <LOOPBACK> mtu 65536 state DOWN
    link/loopback 00:00:00:00:00:00
```

> 위 출력은 `kubernetes-textbook-main` 19.3의 예시 출력을 옮긴 것이며, 이 책을 쓴 환경(Windows)에서 직접 실행해 확인한 것은 아니다.

이 빈 네임스페이스를 채우는 일(인터페이스 생성, IP 할당, 라우팅 설정)이 바로 쿠버네티스에서 CNI 플러그인이 하는 일이다([14장](../3부-쿠버네티스-네트워크/14-CNI-스펙과-IPAM.md)). 채우는 절차는 [4장](04-veth-브리지-라우팅-ARP.md)에서 veth와 함께 다룬다.

## 코어 2. inode 번호로 보고, setns로 합류한다

### 2.1 /proc/[pid]/ns/ 확인

**한 줄 요약:** 프로세스가 속한 네임스페이스는 `/proc/[pid]/ns/` 아래의 심볼릭 링크로 노출되고, 대괄호 안 숫자(inode)가 같으면 같은 네임스페이스다.

> **입문 책에서 배운 것:** `ls -l /proc/$$/ns/`의 `net:[4026531992]` 같은 번호를 비교한다([입문 책 6장](../../Docker%20와%20Kubernetes로%20인프라%20구축할때%20알아야하는%20필수%20이론%20지식/2부-컨테이너와-Docker/06-컨테이너-격리-네임스페이스.md)).

컨테이너와 `--net=host` 컨테이너를 호스트와 비교하는 실험이 원천에 있다.

```bash
docker run -d --name web nginx:latest
CPID=$(docker inspect -f '{{.State.Pid}}' web)
sudo ls -l /proc/$CPID/ns/net /proc/self/ns/net      # 번호가 다르면 독립된 네트워크 네임스페이스

docker run -d --name web-host --net=host nginx:latest
HPID=$(docker inspect -f '{{.State.Pid}}' web-host)
sudo ls -l /proc/$HPID/ns/net /proc/self/ns/net      # 이번에는 번호가 같아야 한다

lsns                    # 시스템의 모든 네임스페이스 목록
lsns -t net             # 네트워크 네임스페이스만
```

### 2.2 세 개의 시스템콜

**한 줄 요약:** 새로 만들기는 `clone`/`unshare`, 기존 네임스페이스에 합류는 `setns`이며, 이 마지막이 Pod의 핵심이다.

| 시스템콜 | 하는 일 | 명령행 도구 |
|---|---|---|
| `clone(CLONE_NEW*)` | 새 네임스페이스와 함께 프로세스 생성 | `unshare --fork` |
| `unshare(CLONE_NEW*)` | 현재 프로세스를 새 네임스페이스로 분리 | `unshare` |
| `setns(fd, type)` | **기존 네임스페이스에 합류** | `nsenter` |

`/proc/[pid]/ns/` 링크는 읽기용 정보일 뿐 아니라 실제로 열 수 있는 파일 디스크립터이기도 하다. `setns()`에 이 경로를 열어 얻은 fd를 넘기면 호출한 프로세스가 그 네임스페이스에 합류한다. `nsenter`는 이 메커니즘을 CLI로 감싼 도구다.

### 2.3 nsenter와 ip netns

**한 줄 요약:** `nsenter`는 실행 중인 프로세스의 네임스페이스에 들어가고, `ip netns`는 이름 붙은 네트워크 네임스페이스를 컨테이너와 무관하게 독립적으로 관리한다.

```bash
# 실행 중인 컨테이너의 네임스페이스에 호스트에서 진입하기
docker run -d --name web nginx:latest
PID=$(docker inspect -f '{{.State.Pid}}' web)

# 해당 컨테이너의 네트워크 네임스페이스에 들어가서 인터페이스 확인
sudo nsenter --target $PID --net -- ip addr
```

`nsenter`는 컨테이너 이미지 안에 셸이나 디버깅 도구가 전혀 없는 distroless 이미지라 해도, 호스트에 설치된 도구로 그 컨테이너의 네임스페이스 안을 확인할 수 있어 디버깅에 대단히 실용적이다.

```bash
# ip netns를 이용한 네트워크 네임스페이스 관리
sudo ip netns add testns
sudo ip netns exec testns ip addr
sudo ip netns list
sudo ip netns delete testns
```

`ip netns`가 만드는 네임스페이스는 기본적으로 `/var/run/netns/` 아래에 이름이 붙은 형태로 등록된다. 반면 Docker가 만드는 네트워크 네임스페이스는 `/var/run/docker/netns/`(또는 유사 경로) 아래에 별도로 관리되므로, 두 등록 체계가 완전히 같지는 않다. 그래서 컨테이너의 네트워크 네임스페이스는 `ip netns list`에 바로 보이지 않을 수 있다.

> **[보충]** 마지막 문장("바로 보이지 않을 수 있다")은 위 등록 경로 차이에서 추론해 이 책이 덧붙인 설명이며 원천에 명시된 것은 아니다. 컨테이너 안은 `nsenter --target $PID --net`으로 들어가는 방법이 원천에 있는 확실한 방법이다.

`docker inspect -f '{{.State.Pid}}'`가 돌려주는 PID가 호스트 기준인 이유는 PID가 네임스페이스마다 다르게 매핑되는 "뷰"이기 때문이다. 컨테이너 안에서 PID 1인 프로세스는 호스트의 PID 공간에서는 다른 번호를 가지며, PID 네임스페이스는 중첩될 수 있어 프로세스는 자기 네임스페이스와 조상 네임스페이스에서는 보이지만 형제나 자식 네임스페이스에서는 보이지 않는다. 그래서 호스트에서는 컨테이너 프로세스가 보이고 컨테이너에서는 호스트 프로세스가 보이지 않는다(`--pid=host` 제외). `nsenter --mount`도 같은 방식으로 컨테이너의 마운트 네임스페이스에 들어간다(`sudo nsenter --target $PID --mount -- ls /`).

## 코어 3. 격리보다 "공유"가 설계다

### 3.1 Docker 옵션은 공유 지시다

**한 줄 요약:** `docker run`은 PID·마운트·UTS·IPC·네트워크(조건부 cgroup) 네임스페이스를 새로 만들고, `--net=host`·`--net=container:X`는 "새로 만들지 말고 공유하라"는 지시다.

> **입문 책에서 배운 것:** `--net=host`, `--net=container:X`, `--pid=host`, `--ipc=host`는 모두 네임스페이스를 새로 만들지 않고 공유하라는 뜻이고, 쿠버네티스 Pod의 네트워크 공유와 같은 원리다([입문 책 6장](../../Docker%20와%20Kubernetes로%20인프라%20구축할때%20알아야하는%20필수%20이론%20지식/2부-컨테이너와-Docker/06-컨테이너-격리-네임스페이스.md)). 사용자·타임 네임스페이스는 기본적으로 호스트와 공유한다.

`--net=host`로 띄운 컨테이너의 `net` inode가 호스트와 같다는 것은 2.1의 실험으로 증명한다. `--net=host`·`none`·macvlan 등 드라이버 선택은 [10장](../2부-Docker-네트워크/10-macvlan-ipvlan-host-none-오버레이.md)에서 이어진다.

### 3.2 pause 컨테이너: Pod의 네임스페이스 소유자

**한 줄 요약:** Pod의 네트워크 네임스페이스는 앱 컨테이너가 아니라 빈 프로세스(pause)가 소유하고, 나머지 컨테이너는 `--net=container:pause`에 준하는 방식으로 합류한다.

`--net=container:app` 패턴은 쿠버네티스 Pod 안에서 여러 컨테이너가 네트워크 네임스페이스를 공유하는 구조와 같은 원리다. Pod에 컨테이너 A와 B가 있고 네트워크를 공유해야 할 때, 누가 네임스페이스를 소유해야 할까?

```
[방안 1] A가 소유하고 B가 합류
  → A가 크래시하면 네임스페이스가 사라진다
  → B의 네트워크도 끊기고, Pod IP가 바뀐다  ✗

[방안 2] 별도의 "빈" 프로세스가 소유
  → A, B가 모두 죽었다 살아나도 네임스페이스는 유지
  → Pod IP가 보존된다  ✓
```

방안 2의 그 빈 프로세스가 pause(인프라 컨테이너, 샌드박스)다. 소스는 놀랍도록 짧다.

```c
/* pause.c — 핵심만 */
static void sigdown(int signo) { _exit(0); }
static void sigreap(int signo) {
    while (waitpid(-1, NULL, WNOHANG) > 0);   /* 좀비 수거 */
}

int main() {
    signal(SIGINT,  sigdown);
    signal(SIGTERM, sigdown);
    signal(SIGCHLD, sigreap);
    for (;;) pause();          /* 시그널이 올 때까지 잠든다 */
}
```

pause는 두 가지 일을 한다. 첫째, 프로세스가 살아 있어야 네임스페이스가 유지되므로 네임스페이스를 살아 있게 유지한다. 둘째, PID 1로서 좀비 프로세스를 수거한다(`shareProcessNamespace: true`인 Pod에서 pause가 PID 1이 되는 이유). PID 네임스페이스에서 PID 1은 고아 프로세스를 입양해 `wait()`으로 정리할 의무가 있고, 이를 하지 않으면 좀비가 쌓인다. 이 짧은 코드가 `SIGINT`/`SIGTERM`/`SIGCHLD` 핸들러를 직접 등록하는 것도 같은 맥락이다.

> **[보충]** 원천(`docker-fundamental` 2장)은 PID 1이 "핸들러를 명시적으로 등록하지 않은 시그널에 대해 커널 기본 동작을 따르지 않고 무시하는 경우가 많다"고 설명한다. 위 `pause.c`가 핸들러를 등록하는 이유를 이 사실과 연결한 것은 이 책의 해석이며, 원천이 두 사실을 직접 잇지는 않는다. 입문 책의 pause 설명([입문 책 15장](../../Docker%20와%20Kubernetes로%20인프라%20구축할때%20알아야하는%20필수%20이론%20지식/3부-쿠버네티스-핵심/15-Pod.md))은 IP 유지 이유까지이고, 여기서는 소스와 PID 1의 책임까지 내려간다.

Pod와 앱 컨테이너를 비교하면 다음과 같다.

| 네임스페이스 | Pod 안 pause vs 앱 컨테이너 |
|---|---|
| `net`, `ipc`, `uts` | inode 번호가 같다 (공유) |
| `mnt`, `pid` | 다르다 (분리) |

```bash
# 노드에서 확인
crictl pods
crictl inspectp <POD_ID> | jq '.status.metadata, .info.pid'
POD_PID=$(crictl inspectp <POD_ID> | jq -r '.info.pid')
ls -l /proc/$POD_PID/ns/
crictl ps --pod <POD_ID>
APP_PID=$(crictl inspect <CONTAINER_ID> | jq -r '.info.pid')
ls -l /proc/$APP_PID/ns/
```

Pod 네트워크의 전체 그림은 [13장](../3부-쿠버네티스-네트워크/13-쿠버네티스-네트워크-모델과-Pod-네트워크.md)에서 이어진다.

### 3.3 손으로 만든 Pod (네트워크 네임스페이스 부분)

**한 줄 요약:** `ip netns`로 네임스페이스를 만들면 pause의 역할을 대신하고, 그 안에 합류한 프로세스들은 같은 IP와 포트 공간을 쓰며, 프로세스가 죽어도 네임스페이스와 IP는 유지된다.

`kubernetes-textbook-main` 19.3은 `kubectl`도 컨테이너 런타임도 없이 리눅스 명령만으로 Pod를 만든다(루트 권한의 리눅스 머신, kind 노드 안에서 하는 것이 안전하다고 한다). 네트워크 네임스페이스 관련 단계만 추린다. veth를 만들어 인터페이스를 채우는 단계는 [4장](04-veth-브리지-라우팅-ARP.md)에서 다룬다.

```bash
# 단계 1: "pod-lab"이라는 네트워크 네임스페이스 = 우리의 pause
ip netns add pod-lab
ip netns list
ls -l /var/run/netns/pod-lab

# 단계 2의 ①: 루프백 활성화 — localhost 통신에 필수
ip netns exec pod-lab ip link set lo up
```

(단계 2의 veth 연결 후) 컨테이너 A와 B를 같은 네트워크 네임스페이스에 합류시키되 MNT/PID는 새로 만든다. A는 8080에서 HTTP 서버를 띄운다(원천은 `nc` 대체로 아래 python 형태도 보여 준다. cgroup 등록 줄은 이 장 범위 밖이라 생략했다).

```bash
# 컨테이너 A: 네트워크는 pod-lab에 합류, MNT/PID는 새로 만든다
ip netns exec pod-lab unshare --mount --pid --fork --mount-proc \
  bash -c 'python3 -m http.server 8080' &

# 컨테이너 B: 네트워크는 pod-lab에 합류, MNT/PID는 새로 만든다
ip netns exec pod-lab \
  unshare --mount --pid --fork --mount-proc \
  bash -c '
    echo "PID: $$"                              # 1
    curl -s localhost:8080 | head -5            # container-a의 응답
    ps aux                                      # container-a의 프로세스는 안 보임
  '
```

결과의 의미는 다음과 같다.

- 두 프로세스가 **같은 IP, 같은 포트 공간**을 쓴다 → `localhost` 통신 성공
- 각자 **다른 PID 네임스페이스**를 갖는다 → 서로의 프로세스가 안 보임
- 각자 **다른 MNT 네임스페이스**를 갖는다 → 파일시스템 분리

```bash
# 단계 6: 네임스페이스 공유 검증
PIDS=$(ip netns pids pod-lab)
for p in $PIDS; do
  echo "=== PID $p ==="
  readlink /proc/$p/ns/net    # 같아야 한다
  readlink /proc/$p/ns/pid    # 달라야 한다
  readlink /proc/$p/ns/mnt    # 달라야 한다
done
```

net은 같고 pid/mnt는 다르다. 이것이 Pod의 정의다. 마지막으로 컨테이너(프로세스)를 죽여도 네임스페이스는 남는다.

```bash
# 단계 8: container-a를 죽인다
kill %1
# 네임스페이스와 IP는 그대로 살아 있다
ip netns exec pod-lab ip addr show eth0 | grep inet
# inet 10.99.0.2/24 ...                    ← 유지됨!
```

pause 컨테이너(여기서는 `ip netns`가 만든 네임스페이스 파일)가 있기 때문에 IP가 보존된다. 정리는 `ip netns delete pod-lab`로 한다.

> 위 절차는 원천 `kubernetes-textbook-main` 19.3의 명령과 설명을 책 맥락에 맞게 일부만 발췌한 것이다. 이 책의 필자는 이 환경(Windows)에서 이 명령을 실행해 보지 못했으므로 "실행 검증"된 절차가 아니다. 실습은 Linux 노드(kind 노드 등)에서 직접 해 보기 바란다.

### 3.4 손으로 만든 것과 런타임의 대응

**한 줄 요약:** 컨테이너 런타임(containerd/runc)이 하는 일은 우리가 손으로 한 일을 OCI 스펙에 따라 자동화하는 것이며, `config.json`에서 그 네임스페이스 목록을 볼 수 있다.

| 우리가 만든 것 | 쿠버네티스에서 |
|---|---|
| `ip netns add pod-lab` | pause 컨테이너 생성 |
| veth 페어 + IP 할당 | CNI 플러그인 `ADD` |
| `unshare --mount --pid` | 각 컨테이너의 격리 |
| cgroup `memory.max` | `limits.memory` |
| OOM으로 인한 종료(137) | `OOMKilled` |
| `capsh --drop` | `securityContext.capabilities.drop` |
| seccomp 프로파일 | `seccompProfile` |

```bash
# runc가 받는 config.json을 구경해 보자
docker exec k8s-guide-worker sh -c \
  'find /run/containerd -name config.json 2>/dev/null | head -1 | xargs cat' | jq '.linux.namespaces, .linux.resources.memory'
```

## 코어 4. 네임스페이스만으로는 부족하다

### 4.1 가시성 / 권한 / 자원 세 축

**한 줄 요약:** 네임스페이스는 "무엇이 보이는가"만 제한하고, 권한은 capabilities/seccomp, 자원은 cgroups가 맡으며, 격리 수준은 가장 약한 축을 따른다.

> **입문 책에서 배운 것:** 커널을 분리하지 않으므로 커널 취약점은 경계를 넘을 수 있고, 가시성(네임스페이스)·권한(capabilities/seccomp)·자원(cgroups) 세 축이 함께여야 하며 `--privileged`는 격리를 포기하는 것이다([입문 책 6장](../../Docker%20와%20Kubernetes로%20인프라%20구축할때%20알아야하는%20필수%20이론%20지식/2부-컨테이너와-Docker/06-컨테이너-격리-네임스페이스.md)).

여기서는 권한 축을 입문 책이 다루지 않은 수준(비트마스크와 시스템 콜 필터)까지 내려가 본다.

### 4.2 capability는 비트마스크다

**한 줄 요약:** 프로세스의 유효 capability는 `/proc/self/status`의 `CapEff` 비트마스크로 읽고, `capsh`로 해독·제거 실험을 하며, 런타임은 기본적으로 14개 정도만 남기고 제거한다.

```bash
# 현재 프로세스의 capability
grep Cap /proc/self/status
# CapInh: 0000000000000000
# CapPrm: 000001ffffffffff
# CapEff: 000001ffffffffff        ← 유효 capability 비트마스크
# CapBnd: 000001ffffffffff

capsh --decode=000001ffffffffff | tr ',' '\n' | head

# NET_ADMIN 없이 인터페이스 조작 시도 → 실패
capsh --drop=cap_net_admin -- -c 'ip link set lo down' 2>&1
# RTNETLINK answers: Operation not permitted
```

인터페이스를 조작하는 권한을 막는 것은 네임스페이스가 아니라 capability다. 컨테이너 런타임은 기본적으로 14개 정도만 남기고 나머지를 제거하며, 쿠버네티스에서는 이렇게 설정한다.

```yaml
securityContext:
  capabilities:
    drop: ["ALL"]
    add: ["NET_BIND_SERVICE"]     # 1024 미만 포트만 필요하다면
```

### 4.3 seccomp는 호출 가능한 시스템 콜을 거른다

**한 줄 요약:** seccomp 프로파일은 허용할 시스템 콜 목록과 기본 동작을 정하며, 허용되지 않은 호출은 `EPERM`이 반환되고 `SCMP_ACT_KILL`로 하면 프로세스가 즉시 죽는다.

```json
{
  "defaultAction": "SCMP_ACT_ERRNO",
  "architectures": ["SCMP_ARCH_X86_64"],
  "syscalls": [
    {
      "names": ["read", "write", "exit", "exit_group", "rt_sigreturn",
                "brk", "mmap", "munmap", "openat", "close", "fstat"],
      "action": "SCMP_ACT_ALLOW"
    }
  ]
}
```

```yaml
# 노드의 /var/lib/kubelet/seccomp/profiles/ 에 배치 후
securityContext:
  seccompProfile:
    type: Localhost
    localhostProfile: profiles/minimal.json
```

실무에서는 Security Profiles Operator로 앱을 실행하며 사용하는 시스템 콜을 기록해 프로파일을 자동 생성한다고 원천은 소개한다. 네임스페이스·capability·seccomp 어느 하나라도 느슨하면 가장 약한 축이 전체 수준을 결정한다.

## 실무 적용

### 체크리스트

- [ ] 네임스페이스는 뷰의 분리이며 VM이 아니다. 네트워크 네임스페이스는 라우팅뿐 아니라 방화벽 규칙·소켓·`/proc/net` 통계까지 독립 유지한다.
- [ ] 같은 네트워크 네임스페이스인지는 `readlink /proc/<pid>/ns/net`의 inode 번호로 비교하고, `--net=host` 컨테이너는 호스트와 번호가 같다.
- [ ] 호스트의 도구로 컨테이너 안을 볼 때는 `docker inspect -f '{{.State.Pid}}'`(호스트 기준 PID)로 `nsenter --target $PID --net`에 들어간다. `ip netns list`에는 컨테이너가 바로 보이지 않을 수 있다.
- [ ] Pod 안 컨테이너는 pause가 소유한 네임스페이스에 합류한다. `net`/`ipc`/`uts`는 공유, `mnt`/`pid`는 분리다.
- [ ] 막 만든 네임스페이스는 `lo`만 있고 DOWN이므로 `lo`를 올리고 인터페이스·IP·기본 게이트웨이를 채워야 한다.
- [ ] 인터페이스 조작이 `Operation not permitted`로 실패하면 네임스페이스가 아니라 capability(`CapEff`, `NET_ADMIN`)를 본다. 필요한 capability만 `add`하고 `drop: ["ALL"]`을 기본으로 한다.

### 시나리오로 확인하기

1. **상황:** 컨테이너 안에서 `ip link set lo down`을 시도하면 `RTNETLINK answers: Operation not permitted`가 난다. 네트워크 네임스페이스는 컨테이너 전용인데 왜 막히는가?
   **질문:** 무엇이 막고, 어떻게 확인하나?

   <details markdown="1"><summary>답 확인</summary>

   네임스페이스는 무엇이 보이는지만 정하고 무엇을 할 수 있는지는 capability가 정한다. `NET_ADMIN`이 없으면 인터페이스 조작이 실패한다. `grep Cap /proc/self/status`의 `CapEff` 비트마스크를 `capsh --decode=<값>`으로 해독해 확인하고, 컨테이너 런타임은 기본적으로 14개 정도만 남기고 제거한다. 꼭 필요하면 `securityContext.capabilities.add`로 해당 capability만 더한다. → 코어 4 (4.2)

   </details>

2. **상황:** 손으로 만든 `pod-lab`에서 컨테이너 B가 `curl localhost:8080`으로 컨테이너 A를 호출하는데 연결이 안 된다. `ps aux`에서는 A의 프로세스가 안 보인다.
   **질문:** 무엇을 점검하나? `ps`에서 안 보이는 것은 문제인가?

   <details markdown="1"><summary>답 확인</summary>

   `ps`에서 안 보이는 것은 정상이다. A와 B는 각자 다른 PID·MNT 네임스페이스를 갖는다. `localhost` 통신은 같은 `net` 네임스페이스와 `lo`가 UP이어야 하므로 `ip netns exec pod-lab ip link set lo up`을 했는지, 두 프로세스의 `readlink /proc/$p/ns/net`이 같은지(pid/mnt는 달라야 한다) 확인한다. → 코어 1 (1.3), 코어 3 (3.3)

   </details>

3. **상황:** `--net=host`로 띄웠다고 생각한 컨테이너가 호스트 네트워크를 쓰는지 의심스럽다.
   **질문:** 무엇으로 증명하나?

   <details markdown="1"><summary>답 확인</summary>

   컨테이너 PID(`docker inspect -f '{{.State.Pid}}'`)의 `/proc/$PID/ns/net`과 호스트의 `/proc/self/ns/net` inode 번호를 비교한다. 같으면 `--net=host`이고, 다르면 독립된 네트워크 네임스페이스다. → 코어 2 (2.1)

   </details>

### 2. 인출 질문

1. 네트워크 네임스페이스가 8개 중 구현이 가장 복잡한 이유는?

   <details markdown="1"><summary>답 확인</summary>

   라우팅 테이블뿐 아니라 방화벽 규칙, 소켓, `/proc/net` 하위의 각종 통계까지 네임스페이스별로 독립적으로 유지되어야 하기 때문이다(커널 2.6.29 전후로 점진적 완성). 막 만든 것에는 `lo` 하나만 있고 DOWN이며, 이 빈 네임스페이스를 채우는 일이 CNI 플러그인의 일이다. → 코어 1 (1.2, 1.3)

   </details>

2. 컨테이너가 호스트 네트워크 네임스페이스를 쓰는지 어떻게 증명하는가? `docker inspect`의 PID는 누구 기준인가?

   <details markdown="1"><summary>답 확인</summary>

   컨테이너의 `/proc/$CPID/ns/net`과 호스트의 `/proc/self/ns/net` inode 번호를 비교한다. `--net=host`면 같고 일반 컨테이너면 다르다. `.State.Pid`는 호스트의 PID 공간 기준 번호다(PID는 네임스페이스마다 다르게 매핑되는 뷰이므로 컨테이너 안에서는 PID 1이다). → 코어 2 (2.1, 2.3)

   </details>

3. `unshare`·`nsenter`·`ip netns`의 차이와, `ip netns`와 Docker의 등록 경로는?

   <details markdown="1"><summary>답 확인</summary>

   `unshare`는 `unshare(CLONE_NEW*)`/`clone`을 감싸 새 네임스페이스로 분리하고, `nsenter`는 `setns(fd, type)`를 감싸 기존 네임스페이스에 합류하며(`/proc/<pid>/ns/` 링크를 연 fd를 사용), `ip netns`는 이름 붙은 네트워크 네임스페이스를 독립적으로 관리한다. `ip netns`는 `/var/run/netns/`, Docker는 `/var/run/docker/netns/`(또는 유사 경로)에 등록한다. → 코어 2 (2.2, 2.3)

   </details>

4. pause가 네임스페이스를 소유하지 않고 앱 컨테이너 A가 소유하면 무슨 일이 생기는가? pause는 무엇을 하는가?

   <details markdown="1"><summary>답 확인</summary>

   A가 크래시하면 네임스페이스가 사라져 B의 네트워크도 끊기고 Pod IP가 바뀐다. 빈 프로세스 pause가 소유하면 A·B가 죽었다 살아나도 유지된다. pause는 네임스페이스를 살아 있게 유지하고, PID 1로서 좀비를 수거한다(`pause.c`가 `SIGINT`/`SIGTERM`/`SIGCHLD` 핸들러를 등록하고 `pause()`로 잠든다). → 코어 3 (3.2)

   </details>

5. Pod 안 pause와 앱 컨테이너의 네임스페이스 중 공유되는 것과 분리되는 것은? 노드에서 어떻게 확인하는가?

   <details markdown="1"><summary>답 확인</summary>

   `net`, `ipc`, `uts`는 inode 번호가 같아 공유되고 `mnt`, `pid`는 다르다. `crictl pods` → `crictl inspectp <POD_ID>`로 pause의 `.info.pid`를 얻고 `crictl inspect <CONTAINER_ID>`로 앱 컨테이너 PID를 얻어 각각 `ls -l /proc/<PID>/ns/`를 비교한다. → 코어 3 (3.2)

   </details>

6. 손으로 만든 Pod에서 "Pod의 정의"가 검증되는 방식은?

   <details markdown="1"><summary>답 확인</summary>

   `ip netns pids pod-lab`로 얻은 PID들에 대해 `readlink /proc/$p/ns/net`은 같고(같은 IP·포트 공간, `localhost` 통신 성공) `pid`/`mnt`는 달라야 한다(서로의 프로세스가 안 보임). 컨테이너를 죽여도 네임스페이스 파일(pause 역할) 덕분에 IP가 유지된다. → 코어 3 (3.3)

   </details>

7. 손으로 한 `ip netns add`·veth·`capsh --drop`은 쿠버네티스의 무엇에 대응하고, 런타임은 어디서 그 설정을 보는가?

   <details markdown="1"><summary>답 확인</summary>

   각각 pause 컨테이너 생성, CNI 플러그인 `ADD`, `securityContext.capabilities.drop`에 대응한다. 런타임(containerd/runc)이 같은 일을 OCI 스펙에 따라 자동화하며, `find /run/containerd -name config.json`의 `.linux.namespaces`로 구경할 수 있다. → 코어 3 (3.4)

   </details>

8. 유효 capability는 어디서 읽고, 제거 실험은 어떻게 하는가? seccomp는 위반 시 무엇을 하는가?

   <details markdown="1"><summary>답 확인</summary>

   `grep Cap /proc/self/status`의 `CapEff` 비트마스크를 `capsh --decode=<값>`으로 해독하고, `capsh --drop=cap_net_admin -- -c 'ip link set lo down'`은 `Operation not permitted`로 실패한다. 런타임은 기본적으로 14개 정도만 남긴다. seccomp는 `defaultAction`이 `SCMP_ACT_ERRNO`이고 허용 목록 밖의 호출은 `EPERM`을 반환하며 `SCMP_ACT_KILL`이면 프로세스가 즉시 죽는다. → 코어 4 (4.2, 4.3)

   </details>

### 3. 기억 고리

- **C++ 유추:** `nsenter --target $PID --net` ≈ 다른 프로세스에 attach해서 그 관점으로 상태를 보는 것. ⚠️ 대상을 건드리지 않고 호스트의 도구를 그대로 쓰며, 보이는 것은 그 프로세스의 네트워크 스택 전체다.
- **C++ 유추:** 컨테이너 포트 = 서버 인스턴스마다 포트 나누기. ⚠️ 포트를 나누는 게 아니라 스택 전체를 따로 본다. 호스트 포트를 열려면 별도 규칙(`-p`)이 필요하다.
- **비유:** 네트워크 네임스페이스 = 사무실 칸막이가 쳐진 독립된 전화 교환실. 각 칸마다 자기 전화기(인터페이스), 연결표(라우팅), 보안 규칙, 내선 번호(포트)가 따로 있다. 칸막이 두 개가 하나의 교환실을 공유하게 하면 같은 번호 체계를 쓴다(Pod). ⚠️ 비유가 깨지는 지점: 건물(커널)은 하나라서 건물 자체에 구멍이 있으면(커널 취약점) 칸막이가 소용없고, 칸막이는 "들어올 수 있는 사람"(권한)이나 "전기 사용량"(자원)을 막지 못한다.
- **묶음(3의 법칙):** 시스템콜 3 (`clone`/`unshare`/`setns`) · 도구 3 (`unshare`/`nsenter`/`ip netns`) · Pod 공유 3 (`net`/`ipc`/`uts`) · 격리 축 3 (가시성 네임스페이스 / 권한 capabilities·seccomp / 자원 cgroups).
- **대칭·순서:** 만들기(`unshare`·`clone`) ↔ 합류하기(`setns`·`nsenter`). 빈 netns → `lo` up → (인터페이스·IP·게이트웨이 채움, 4장) → 컨테이너 합류 순.
