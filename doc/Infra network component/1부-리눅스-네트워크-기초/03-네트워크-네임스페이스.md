# 3장. 네트워크 네임스페이스

> **🎮 게임 서버 개발자에게** — 같은 머신에 게임 서버 프로세스를 여러 개 띄우면 포트가 겹치지 않게 서버마다 `7001`, `7002`, ...를 나눠 쓰던 기억이 있을 것이다. 컨테이너는 이 문제를 **프로세스마다 "네트워크 스택 한 벌"을 따로 보게 만들어서** 푼다. 인터페이스, 라우팅 테이블, 방화벽 규칙, 포트 바인딩 공간이 통째로 분리되므로 서버마다 `0.0.0.0:80`을 그대로 쓴다. 결정적으로 다른 점은, 이것은 가상 머신처럼 자원을 복제하는 것이 아니라 **같은 커널이 프로세스에게 보여 주는 뷰만 바꾸는 것**이라는 점이다. 그래서 "컨테이너"라는 커널 객체는 존재하지 않고, 네임스페이스가 붙은 평범한 프로세스가 있을 뿐이다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 이미지에 `ip`·`ss`·셸이 없어서(distroless) 컨테이너 안 네트워크를 볼 수 없을 때, 호스트에서 `nsenter`로 그 컨테이너의 네트워크 네임스페이스에 들어가 확인해야 한다.
> - Pod 안 컨테이너 A가 죽어도 Pod IP가 유지되는 이유, 같은 Pod 컨테이너끼리 `localhost`로 통신되는 이유를 설명해야 한다.
> - `--net=host`로 띄운 컨테이너가 정말 호스트 네트워크를 쓰는지 inode 번호로 증명해야 한다.

## 코어 — 이것만은 100%

> **한 문장:** 네트워크 네임스페이스는 인터페이스·라우팅 테이블·방화벽 규칙·포트 바인딩 공간을 프로세스 그룹별로 다르게 "보이게" 하는 커널 기능이고, 컨테이너는 이것을 새로 만들거나 다른 대상과 **공유**해서 조합하며, 쿠버네티스 Pod는 pause 컨테이너가 만든 네임스페이스에 앱 컨테이너들이 합류한 것이다.

1. **네임스페이스는 복제가 아니라 "뷰"다** — 같은 커널·CPU·물리 NIC를 공유하지만, 프로세스는 자기 네임스페이스 안의 인터페이스·라우팅·규칙·소켓만 본다. 새 네임스페이스에는 `lo` 하나만 있고 DOWN 상태다.
2. **`/proc/[pid]/ns/`의 inode 번호로 같은 네임스페이스인지 판별하고, `setns`로 합류한다** — 새로 만들기(`clone`/`unshare`)와 합류하기(`setns`)는 다른 시스템콜이며, `unshare`/`nsenter`/`ip netns`가 이를 감싼 도구다.
3. **격리보다 "공유"가 설계다** — Docker의 `--net=host`, `--net=container:X`는 "새로 만들지 말고 공유하라"는 지시이고, 쿠버네티스 Pod는 pause 컨테이너가 네임스페이스를 소유하고 나머지가 합류하는 같은 원리다. 그래서 컨테이너가 죽어도 Pod IP가 유지된다.
4. **네임스페이스는 가시성 축일 뿐이다** — 권한(capabilities/seccomp)과 자원(cgroups)은 다른 축이며, 네임스페이스만으로는 보안 경계가 되지 못한다.

**이 장의 학습 목표**

- 네트워크 네임스페이스가 격리하는 것과 격리하지 않는 것을 구분한다.
- `ls -l /proc/<pid>/ns/`, `lsns -t net`, `nsenter`, `ip netns`로 네임스페이스를 보고 들어간다.
- `--net=host`, `--net=container:X`, pause 컨테이너가 같은 메커니즘(공유)임을 설명한다.
- 빈 네임스페이스를 만들어 Pod처럼 쓰는 절차에서 "네임스페이스 만들기"가 CNI의 어느 부분과 대응하는지 안다.

## 코어 1. 네임스페이스는 복제가 아니라 "뷰"다

### 1.1 네임스페이스란 무엇인가

**한 줄 요약:** 커널이 관리하는 전역 자원을 프로세스 그룹별로 다르게 "보이게" 만드는 기능이며, 자원을 실제로 복제하거나 분할하지 않는다.

같은 물리 서버 위의 컨테이너 10개는 같은 커널, 같은 CPU, 같은 물리 네트워크 인터페이스를 공유한다. 다만 각 컨테이너 프로세스가 `ps`를 하면 자기 네임스페이스 안의 프로세스만, `ip addr`을 하면 자기 네트워크 네임스페이스 안의 인터페이스만 보인다. 네임스페이스는 프로세스가 커널에 질의할 때 결과를 필터링·치환해 주는 렌즈에 가깝다.

**"컨테이너"라는 커널 객체는 존재하지 않는다.** 네임스페이스(무엇을 볼 수 있는가), cgroups(얼마나 쓸 수 있는가), capabilities(무엇을 할 수 있는가), union FS(파일시스템을 어떻게 쌓는가), seccomp/LSM(어떤 시스템콜을 호출할 수 있는가)을 조합한 프로세스를 컨테이너라고 부를 뿐이며, 호스트에서 `ps aux`로 보면 그냥 프로세스다. 이 책은 그중 네트워크 네임스페이스만 다룬다.

### 1.2 여덟 가지 중 네트워크 네임스페이스

**한 줄 요약:** 네트워크 네임스페이스(`CLONE_NEWNET`)는 인터페이스, 라우팅 테이블, iptables/nftables 규칙, 포트 바인딩 공간을 분리한다.

리눅스는 mount, UTS, IPC, PID, network, user, cgroup, time의 8가지 네임스페이스를 제공한다. 그중 네트워크 네임스페이스는 구현이 가장 복잡한 축에 속한다. 라우팅 테이블뿐 아니라 방화벽 규칙, 소켓, `/proc/net` 하위의 각종 통계까지 네임스페이스별로 독립적으로 유지되어야 하기 때문이다.

| 네임스페이스 | 플래그 | 격리 대상 |
|---|---|---|
| Mount | `CLONE_NEWNS` | 마운트 테이블 |
| UTS | `CLONE_NEWUTS` | 호스트 이름, NIS 도메인 |
| IPC | `CLONE_NEWIPC` | System V IPC, POSIX 메시지 큐 |
| PID | `CLONE_NEWPID` | 프로세스 ID 공간 |
| **Network** | **`CLONE_NEWNET`** | **네트워크 인터페이스, 라우팅, 방화벽** |
| User | `CLONE_NEWUSER` | UID/GID 매핑 |
| cgroup | `CLONE_NEWCGROUP` | cgroup 계층 뷰 |
| Time | `CLONE_NEWTIME` | 부팅 이후 경과 시각 클록 |

각 컨테이너는 기본적으로 자기만의 loopback(`lo`)과 veth pair의 한쪽 끝을 가진다. 이것이 컨테이너마다 독립적으로 `0.0.0.0:80`을 바인딩할 수 있는 이유다. 이 네임스페이스는 이후 브리지·오버레이·nftables 논의의 근간이다.

### 1.3 새 네임스페이스는 비어 있다

**한 줄 요약:** 막 만든 네트워크 네임스페이스에는 `lo` 하나만 있고 DOWN 상태다.

```bash
ip netns add pod-lab
ip netns exec pod-lab ip addr
```

```
1: lo: <LOOPBACK> mtu 65536 state DOWN
    link/loopback 00:00:00:00:00:00
```

> 위 출력은 `kubernetes-textbook-main` 19.3의 예시 출력을 옮긴 것이며, 이 책을 쓴 환경(Windows)에서 직접 실행해 확인한 것은 아니다.

이 빈 네임스페이스를 채우는 일(인터페이스 생성, IP 할당, 라우팅 설정)이 바로 쿠버네티스에서 CNI 플러그인이 하는 일이다([14장](../3부-쿠버네티스-네트워크/14-CNI-스펙과-IPAM.md)). 채우는 절차는 [4장](04-veth-브리지-라우팅-ARP.md)에서 veth와 함께 다룬다.

## 코어 2. inode 번호로 보고, setns로 합류한다

### 2.1 /proc/[pid]/ns/ 확인

**한 줄 요약:** 프로세스가 속한 네임스페이스는 `/proc/[pid]/ns/` 아래의 심볼릭 링크로 노출되고, 대괄호 안 숫자(inode)가 같으면 같은 네임스페이스다.

```bash
ls -l /proc/$$/ns/
```

```
lrwxrwxrwx 1 root root 0 ... cgroup -> 'cgroup:[4026531835]'
lrwxrwxrwx 1 root root 0 ... ipc -> 'ipc:[4026531839]'
lrwxrwxrwx 1 root root 0 ... mnt -> 'mnt:[4026531840]'
lrwxrwxrwx 1 root root 0 ... net -> 'net:[4026531992]'
lrwxrwxrwx 1 root root 0 ... pid -> 'pid:[4026531836]'
...
```

두 프로세스가 같은 네임스페이스에 속하는지 확인하려면 이 번호를 비교한다. 컨테이너 프로세스와 호스트 프로세스가 네트워크 네임스페이스를 공유하는지(`--net=host`) 확인하려면 두 프로세스의 `net -> net:[...]` 번호가 같은지 본다.

```bash
lsns                    # 시스템의 모든 네임스페이스 목록
lsns -t net             # 네트워크 네임스페이스만
```

### 2.2 세 개의 시스템콜

**한 줄 요약:** 새로 만들기는 `clone`/`unshare`, 기존 네임스페이스에 합류는 `setns`이며, 이 마지막이 Pod의 핵심이다.

| 시스템콜 | 하는 일 | 명령행 도구 |
|---|---|---|
| `clone(CLONE_NEW*)` | 새 네임스페이스와 함께 프로세스 생성 | `unshare --fork` |
| `unshare(CLONE_NEW*)` | 현재 프로세스를 새 네임스페이스로 분리 | `unshare` |
| `setns(fd, type)` | **기존 네임스페이스에 합류** | `nsenter` |

`/proc/[pid]/ns/` 링크는 읽기용 정보일 뿐 아니라 실제로 열 수 있는 파일 디스크립터이기도 하다. `setns()`에 이 경로를 열어 얻은 fd를 넘기면 호출한 프로세스가 그 네임스페이스에 합류한다. `nsenter`는 이 메커니즘을 CLI로 감싼 도구다.

### 2.3 nsenter와 ip netns

**한 줄 요약:** `nsenter`는 실행 중인 프로세스의 네임스페이스에 들어가고, `ip netns`는 이름 붙은 네트워크 네임스페이스를 컨테이너와 무관하게 독립적으로 관리한다.

```bash
# 실행 중인 컨테이너의 네임스페이스에 호스트에서 진입하기
docker run -d --name web nginx:latest
PID=$(docker inspect -f '{{.State.Pid}}' web)

# 해당 컨테이너의 네트워크 네임스페이스에 들어가서 인터페이스 확인
sudo nsenter --target $PID --net -- ip addr
```

`nsenter`는 컨테이너 이미지 안에 셸이나 디버깅 도구가 전혀 없는 distroless 이미지라 해도, 호스트에 설치된 도구로 그 컨테이너의 네임스페이스 안을 확인할 수 있어 디버깅에 대단히 실용적이다.

```bash
# ip netns를 이용한 네트워크 네임스페이스 관리
sudo ip netns add testns
sudo ip netns exec testns ip addr
sudo ip netns list
sudo ip netns delete testns
```

`ip netns`가 만드는 네임스페이스는 기본적으로 `/var/run/netns/` 아래에 이름이 붙은 형태로 등록된다. 반면 Docker가 만드는 네트워크 네임스페이스는 `/var/run/docker/netns/`(또는 유사 경로) 아래에 별도로 관리되므로, 두 등록 체계가 완전히 같지는 않다. 그래서 컨테이너의 네트워크 네임스페이스는 `ip netns list`에 바로 보이지 않을 수 있다.

> **[보충]** 마지막 문장("바로 보이지 않을 수 있다")은 위 등록 경로 차이에서 추론해 이 책이 덧붙인 설명이며 원천에 명시된 것은 아니다. 컨테이너 안은 `nsenter --target $PID --net`으로 들어가는 방법이 원천에 있는 확실한 방법이다.

## 코어 3. 격리보다 "공유"가 설계다

### 3.1 Docker 옵션은 공유 지시다

**한 줄 요약:** `docker run`은 기본적으로 PID·마운트·UTS·IPC·네트워크(조건부 cgroup) 네임스페이스를 새로 만들고, 여러 옵션은 "새로 만들지 말고 공유하라"는 지시로 이해하면 명확하다.

```bash
# 네트워크 네임스페이스를 호스트와 공유 (새 net 네임스페이스를 만들지 않음)
docker run --rm --net=host nginx:latest

# 네트워크 네임스페이스를 다른 컨테이너 X와 공유 (사이드카 패턴의 기반)
docker run -d --name app myapp:latest
docker run --rm --net=container:app busybox ip addr
```

사용자 네임스페이스는 기본적으로 새로 만들지 않고 호스트 것을 쓰며, 타임 네임스페이스도 기본은 호스트와 공유한다. `--net=host`로 띄운 컨테이너는 호스트와 `net` inode 번호가 같고, 일반 컨테이너는 다르다. `--net=host`·`none`·macvlan 등 드라이버 선택은 [10장](../2부-Docker-네트워크/10-macvlan-ipvlan-host-none-오버레이.md)에서 이어진다.

### 3.2 pause 컨테이너: Pod의 네임스페이스 소유자

**한 줄 요약:** Pod의 네트워크 네임스페이스는 앱 컨테이너가 아니라 빈 프로세스(pause)가 소유하고, 나머지 컨테이너는 `--net=container:pause`에 준하는 방식으로 합류한다.

`--net=container:app` 패턴은 쿠버네티스 Pod 안에서 여러 컨테이너가 네트워크 네임스페이스를 공유하는 구조와 같은 원리다. Pod에 컨테이너 A와 B가 있고 네트워크를 공유해야 할 때, 누가 네임스페이스를 소유해야 할까?

```
[방안 1] A가 소유하고 B가 합류
  → A가 크래시하면 네임스페이스가 사라진다
  → B의 네트워크도 끊기고, Pod IP가 바뀐다  ✗

[방안 2] 별도의 "빈" 프로세스가 소유
  → A, B가 모두 죽었다 살아나도 네임스페이스는 유지
  → Pod IP가 보존된다  ✓
```

방안 2의 그 빈 프로세스가 pause(인프라 컨테이너, 샌드박스)다. 소스는 놀랍도록 짧다.

```c
/* pause.c — 핵심만 */
static void sigdown(int signo) { _exit(0); }
static void sigreap(int signo) {
    while (waitpid(-1, NULL, WNOHANG) > 0);   /* 좀비 수거 */
}

int main() {
    signal(SIGINT,  sigdown);
    signal(SIGTERM, sigdown);
    signal(SIGCHLD, sigreap);
    for (;;) pause();          /* 시그널이 올 때까지 잠든다 */
}
```

pause는 두 가지 일을 한다. 첫째, 프로세스가 살아 있어야 네임스페이스가 유지되므로 네임스페이스를 살아 있게 유지한다. 둘째, PID 1로서 좀비 프로세스를 수거한다(`shareProcessNamespace: true`인 Pod에서 pause가 PID 1이 되는 이유). Pod와 앱 컨테이너를 비교하면 다음과 같다.

| 네임스페이스 | Pod 안 pause vs 앱 컨테이너 |
|---|---|
| `net`, `ipc`, `uts` | inode 번호가 같다 (공유) |
| `mnt`, `pid` | 다르다 (분리) |

```bash
# 노드에서 확인
crictl pods
crictl inspectp <POD_ID> | jq '.status.metadata, .info.pid'
POD_PID=$(crictl inspectp <POD_ID> | jq -r '.info.pid')
ls -l /proc/$POD_PID/ns/
crictl ps --pod <POD_ID>
APP_PID=$(crictl inspect <CONTAINER_ID> | jq -r '.info.pid')
ls -l /proc/$APP_PID/ns/
```

Pod 네트워크의 전체 그림은 [13장](../3부-쿠버네티스-네트워크/13-쿠버네티스-네트워크-모델과-Pod-네트워크.md)에서 이어진다.

### 3.3 손으로 만든 Pod (네트워크 네임스페이스 부분)

**한 줄 요약:** `ip netns`로 네임스페이스를 만들면 pause의 역할을 대신하고, 그 안에 합류한 프로세스들은 같은 IP와 포트 공간을 쓰며, 프로세스가 죽어도 네임스페이스와 IP는 유지된다.

`kubernetes-textbook-main` 19.3은 `kubectl`도 컨테이너 런타임도 없이 리눅스 명령만으로 Pod를 만든다(루트 권한의 리눅스 머신, kind 노드 안에서 하는 것이 안전하다고 한다). 네트워크 네임스페이스 관련 단계만 추린다. veth를 만들어 인터페이스를 채우는 단계는 [4장](04-veth-브리지-라우팅-ARP.md)에서 다룬다.

```bash
# 단계 1: "pod-lab"이라는 네트워크 네임스페이스 = 우리의 pause
ip netns add pod-lab
ip netns list
ls -l /var/run/netns/pod-lab

# 단계 2의 ①: 루프백 활성화 — localhost 통신에 필수
ip netns exec pod-lab ip link set lo up
```

(단계 2의 veth 연결 후) 컨테이너 A와 B를 같은 네트워크 네임스페이스에 합류시키되 MNT/PID는 새로 만든다.

```bash
# 컨테이너 B: 네트워크는 pod-lab에 합류, MNT/PID는 새로 만든다
ip netns exec pod-lab \
  unshare --mount --pid --fork --mount-proc \
  bash -c '
    echo "PID: $$"                              # 1
    curl -s localhost:8080 | head -5            # container-a의 응답
    ps aux                                      # container-a의 프로세스는 안 보임
  '
```

결과의 의미는 다음과 같다.

- 두 프로세스가 **같은 IP, 같은 포트 공간**을 쓴다 → `localhost` 통신 성공
- 각자 **다른 PID 네임스페이스**를 갖는다 → 서로의 프로세스가 안 보임
- 각자 **다른 MNT 네임스페이스**를 갖는다 → 파일시스템 분리

```bash
# 단계 6: 네임스페이스 공유 검증
PIDS=$(ip netns pids pod-lab)
for p in $PIDS; do
  echo "=== PID $p ==="
  readlink /proc/$p/ns/net    # 같아야 한다
  readlink /proc/$p/ns/pid    # 달라야 한다
  readlink /proc/$p/ns/mnt    # 달라야 한다
done
```

net은 같고 pid/mnt는 다르다. 이것이 Pod의 정의다. 마지막으로 컨테이너(프로세스)를 죽여도 네임스페이스는 남는다.

```bash
# 단계 8: container-a를 죽인다
kill %1
# 네임스페이스와 IP는 그대로 살아 있다
ip netns exec pod-lab ip addr show eth0 | grep inet
# inet 10.99.0.2/24 ...                    ← 유지됨!
```

pause 컨테이너(여기서는 `ip netns`가 만든 네임스페이스 파일)가 있기 때문에 IP가 보존된다. 정리는 `ip netns delete pod-lab`로 한다.

> 위 절차는 원천 `kubernetes-textbook-main` 19.3의 명령과 설명을 책 맥락에 맞게 일부만 발췌한 것이다. 이 책의 필자는 이 환경(Windows)에서 이 명령을 실행해 보지 못했으므로 "실행 검증"된 절차가 아니다. 실습은 Linux 노드(kind 노드 등)에서 직접 해 보기 바란다.

## 코어 4. 네임스페이스만으로는 부족하다

### 4.1 가시성 / 권한 / 자원 세 축

**한 줄 요약:** 네임스페이스는 "무엇이 보이는가"만 제한하고, 권한은 capabilities/seccomp, 자원은 cgroups가 맡으며, 격리 수준은 가장 약한 축을 따른다.

- 네임스페이스는 **커널 자체를 분리하지 않는다.** 모든 컨테이너가 같은 커널 코드를 실행하므로 커널 취약점(예: 네임스페이스 처리 로직 버그)이 있으면 경계를 넘을 수 있다.
- 네임스페이스는 "무엇을 할 수 있는지"가 아니라 "무엇이 보이는지"만 제한한다. 위험한 행위를 막는 것은 **capabilities**(root 권한을 잘게 쪼갠 단위)와 **seccomp**(허용된 시스템콜만 호출하게 하는 필터)의 몫이다.
- 자원 사용량 제한은 **cgroups**의 몫이다.

`--privileged`로 capabilities와 seccomp를 사실상 무력화하면 나머지 축이 엄격해도 전체 격리 수준은 가장 약한 축을 따른다. 네트워크 맥락에서도 같다. 원천의 실험에서는 `NET_ADMIN` capability를 제거한 프로세스가 `ip link set lo down`을 시도하면 `RTNETLINK answers: Operation not permitted`로 실패한다. 인터페이스를 조작하는 권한을 막는 것은 네임스페이스가 아니라 capability다.

> 위 `NET_ADMIN` 실험은 `kubernetes-textbook-main` 19.6에서 가져온 한 줄이며, 이 장에서 19.6 전체를 다루지는 않는다.

## 실무 적용

### 체크리스트

- [ ] 네임스페이스는 뷰의 분리이며 VM이 아니다. 같은 커널을 공유하므로 단독으로는 보안 경계가 아니다.
- [ ] 같은 네트워크 네임스페이스인지는 `readlink /proc/<pid>/ns/net` 또는 `ls -l /proc/<pid>/ns/`의 inode 번호를 비교한다.
- [ ] 이미지에 도구가 없는 컨테이너는 `docker inspect -f '{{.State.Pid}}'`로 PID를 얻어 `nsenter --target $PID --net -- ip addr`로 본다.
- [ ] `--net=host`는 새 네임스페이스를 만들지 않으므로 호스트와 포트를 공유한다. `--net=container:X`는 X와 IP·포트 공간을 공유한다.
- [ ] Pod 안 컨테이너는 pause가 소유한 네임스페이스에 합류한다. `net`/`ipc`/`uts`는 공유, `mnt`/`pid`는 분리다.
- [ ] 막 만든 네임스페이스는 `lo`만 있고 DOWN이므로 `lo`를 올리고 인터페이스·IP·기본 게이트웨이를 채워야 한다.
- [ ] 격리를 말할 때는 네임스페이스(보이는 것), capabilities/seccomp(할 수 있는 것), cgroups(쓸 수 있는 양) 세 축을 함께 본다.

### 시나리오로 확인하기

1. **상황:** 운영 중인 distroless 컨테이너가 외부로 나가지 못한다. 컨테이너 안에는 셸도 `ip`도 없다.
   **질문:** 컨테이너 안 라우팅과 인터페이스를 어떻게 확인하나?

   <details markdown="1"><summary>답 확인</summary>

   호스트에서 `PID=$(docker inspect -f '{{.State.Pid}}' <컨테이너>)`로 PID를 얻고 `sudo nsenter --target $PID --net -- ip addr`(또는 `ip route`)로 그 컨테이너의 네트워크 네임스페이스 안에 호스트의 도구로 들어간다. `nsenter`는 `/proc/<pid>/ns/net`을 열어 `setns()`로 합류하는 도구다. → 코어 2 (2.2, 2.3)

   </details>

2. **상황:** Pod 안의 컨테이너 A가 크래시 후 재시작되었다. Pod IP가 바뀌지 않았다고 팀원이 신기해한다.
   **질문:** 왜 IP가 유지되는가?

   <details markdown="1"><summary>답 확인</summary>

   네트워크 네임스페이스를 앱 컨테이너 A가 아니라 pause 컨테이너가 소유하기 때문이다. A가 크래시해도 pause가 네임스페이스를 살려 두므로 IP와 네임스페이스가 유지되고, 재시작된 A는 같은 네임스페이스에 다시 합류한다. A가 소유했다면 네임스페이스가 사라져 Pod IP가 바뀌었을 것이다. → 코어 3 (3.2, 3.3)

   </details>

3. **상황:** `--net=host`로 띄웠다고 생각한 컨테이너가 호스트 네트워크를 쓰는지 의심스럽다.
   **질문:** 무엇으로 증명하나?

   <details markdown="1"><summary>답 확인</summary>

   컨테이너 PID(`docker inspect -f '{{.State.Pid}}'`)의 `/proc/$PID/ns/net`과 호스트의 `/proc/self/ns/net` inode 번호를 비교한다. 번호가 같으면 같은 네임스페이스(`--net=host`)이고, 다르면 독립된 네트워크 네임스페이스를 쓰는 것이다. → 코어 2 (2.1), 코어 3 (3.1)

   </details>

### 2. 인출 질문

1. 네임스페이스는 VM과 무엇이 다른가?

   <details markdown="1"><summary>답 확인</summary>

   자원을 복제하거나 분할하지 않는다. 같은 커널·CPU·물리 NIC를 공유하고, 프로세스가 커널에 질의할 때 보이는 결과만 필터링·치환한다. 그리고 커널을 공유하므로 네임스페이스만으로는 완전한 보안 경계가 되지 못한다. → 코어 1 (1.1), 코어 4

   </details>

2. 네트워크 네임스페이스가 격리하는 것은?

   <details markdown="1"><summary>답 확인</summary>

   네트워크 인터페이스, 라우팅 테이블, iptables/nftables 규칙, 포트 바인딩 공간이다(소켓과 `/proc/net` 하위 통계도 네임스페이스별로 독립 유지). 그래서 컨테이너마다 `0.0.0.0:80`을 독립적으로 바인딩할 수 있다. → 코어 1 (1.2)

   </details>

3. 두 프로세스가 같은 네트워크 네임스페이스인지 어떻게 확인하나?

   <details markdown="1"><summary>답 확인</summary>

   `/proc/<pid>/ns/net` 심볼릭 링크(`net:[번호]`)의 inode 번호를 비교한다. `ls -l /proc/<pid>/ns/` 또는 `readlink`를 쓰며, `lsns -t net`로 시스템 전체 목록도 본다. → 코어 2 (2.1)

   </details>

4. `unshare`와 `nsenter`의 차이는?

   <details markdown="1"><summary>답 확인</summary>

   `unshare`는 `unshare(CLONE_NEW*)`/`clone`을 감싼 도구로 새 네임스페이스를 만들어 분리한다. `nsenter`는 `setns(fd, type)`를 감싼 도구로 기존 프로세스의 네임스페이스에 합류한다. `ip netns`는 이름 붙은 네트워크 네임스페이스를 독립적으로 관리한다. → 코어 2 (2.2, 2.3)

   </details>

5. 새로 만든 네트워크 네임스페이스에는 무엇이 있는가? CNI가 하는 일은 이와 어떻게 연결되는가?

   <details markdown="1"><summary>답 확인</summary>

   `lo` 하나만 있고 DOWN 상태다. CNI 플러그인이 하는 일이 바로 이 빈 네임스페이스를 인터페이스·IP·라우팅으로 채우는 것이다. → 코어 1 (1.3)

   </details>

6. `--net=container:app`은 무엇을 하며 쿠버네티스에서 어디에 대응하는가?

   <details markdown="1"><summary>답 확인</summary>

   새 네트워크 네임스페이스를 만들지 않고 컨테이너 `app`의 것을 공유한다(같은 IP·포트 공간). 쿠버네티스 Pod에서 앱 컨테이너들이 pause 컨테이너가 만든 네임스페이스에 합류하는 구조(`--net=container:pause`와 동등한 방식)와 같은 원리다. → 코어 3 (3.1, 3.2)

   </details>

7. pause 컨테이너가 하는 일 두 가지는?

   <details markdown="1"><summary>답 확인</summary>

   네임스페이스를 살아 있게 유지하는 것(프로세스가 살아 있어야 네임스페이스가 유지됨), 그리고 PID 1로서 좀비 프로세스를 수거하는 것이다. 앱 컨테이너가 죽어도 Pod IP가 유지되는 이유다. → 코어 3 (3.2)

   </details>

8. Pod 안 pause와 앱 컨테이너의 네임스페이스 중 공유되는 것과 분리되는 것은?

   <details markdown="1"><summary>답 확인</summary>

   `net`, `ipc`, `uts`는 inode 번호가 같아 공유되고, `mnt`, `pid`는 다르다(분리). → 코어 3 (3.2)

   </details>

9. 네임스페이스만으로 컨테이너가 안전하지 않은 이유는?

   <details markdown="1"><summary>답 확인</summary>

   커널을 분리하지 않으므로 커널 취약점이 경계를 넘을 수 있고, "무엇이 보이는지"만 제한할 뿐 "무엇을 할 수 있는지"(capabilities/seccomp)와 "얼마나 쓸 수 있는지"(cgroups)는 별개 축이기 때문이다. `--privileged`처럼 한 축이 느슨하면 전체 격리 수준은 가장 약한 축을 따른다. → 코어 4

   </details>

### 3. 기억 고리

- **C++ 유추:** `nsenter --target $PID --net` ≈ 다른 프로세스에 attach해서 그 관점으로 상태를 보는 것. ⚠️ 대상을 건드리지 않고 호스트의 도구를 그대로 쓰며, 보이는 것은 그 프로세스의 네트워크 스택 전체다.
- **C++ 유추:** 컨테이너 포트 = 서버 인스턴스마다 포트 나누기. ⚠️ 포트를 나누는 게 아니라 스택 전체를 따로 본다. 호스트 포트를 열려면 별도 규칙(`-p`)이 필요하다.
- **비유:** 네트워크 네임스페이스 = 사무실 칸막이가 쳐진 독립된 전화 교환실. 각 칸마다 자기 전화기(인터페이스), 연결표(라우팅), 보안 규칙, 내선 번호(포트)가 따로 있다. 칸막이 두 개가 하나의 교환실을 공유하게 하면 같은 번호 체계를 쓴다(Pod). ⚠️ 비유가 깨지는 지점: 건물(커널)은 하나라서 건물 자체에 구멍이 있으면(커널 취약점) 칸막이가 소용없고, 칸막이는 "들어올 수 있는 사람"(권한)이나 "전기 사용량"(자원)을 막지 못한다.
- **묶음(3의 법칙):** 시스템콜 3 (`clone`/`unshare`/`setns`) · 도구 3 (`unshare`/`nsenter`/`ip netns`) · Pod 공유 3 (`net`/`ipc`/`uts`) · 격리 축 3 (가시성 네임스페이스 / 권한 capabilities·seccomp / 자원 cgroups).
- **대칭·순서:** 만들기(`unshare`·`clone`) ↔ 합류하기(`setns`·`nsenter`). 빈 netns → `lo` up → (인터페이스·IP·게이트웨이 채움, 4장) → 컨테이너 합류 순.
