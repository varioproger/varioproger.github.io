# 6장. 오버레이·VXLAN·MTU

> **🎮 게임 서버 개발자에게** — 게임 서버가 여러 대로 늘면 서버끼리는 "같은 내부망"에 있다고 가정하고 사설 IP로 서로 붙는다. 컨테이너를 여러 호스트에 흩어 놓으면 이 가정이 깨진다. 호스트마다 자기 브리지와 자기 사설 대역을 갖기 때문이다. 오버레이는 **실제 네트워크 위에 가상 네트워크를 한 겹 더 얹어** 이 문제를 푼다. 결정적으로 다른 점은 비용이다. 패킷을 UDP로 한 번 더 감싸므로 **MTU가 줄어들고**, 이것을 모르면 "ping은 되는데 큰 응답만 멈추는" 이상한 장애를 만난다. TCP 서버 개발자가 가장 낯설어하는 종류의 버그다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 다른 노드의 Pod와는 통신이 안 되고 같은 노드 Pod와는 되는 상황에서 오버레이 경로를 따져야 할 때.
> - 로그인(작은 요청)은 되는데 큰 패킷(리소스 다운로드, TLS 핸드셰이크)에서만 멈추는 증상.
> - CNI를 고를 때 "오버레이냐 네이티브 라우팅이냐"의 성능·진단 trade-off를 설명해야 할 때.

## 코어 — 이것만은 100%

> **한 문장:** 브리지는 한 호스트 안의 L2일 뿐이라 호스트 사이는 이어지지 않으므로, 오버레이는 이미 있는 L3(IP) 위에 원본 이더넷 프레임을 UDP로 감싸(VXLAN, VNI로 네트워크 구분, 4789번 포트) 가상 L2를 얹고, 그 대가로 약 50바이트의 오버헤드가 생겨 컨테이너·Pod 인터페이스의 MTU를 1450 안팎으로 낮춰야 한다.

1. **브리지는 호스트를 못 넘는다** — 호스트 A의 `docker0`과 호스트 B의 `docker0`은 아무 조치 없이는 서로 다른 사설 대역에 속한 남남이다. 정적 라우트로 이을 수는 있어도 호스트 수와 재스케줄링이 늘수록 감당이 안 된다.
2. **VXLAN = VNI + UDP 캡슐화 + VTEP** — 24비트 VNI가 논리 네트워크를 구분하고(약 1,600만 개), 원본 프레임 전체를 UDP 페이로드로 감싸 보내며(표준 목적지 포트 4789), 캡슐화·역캡슐화하는 끝점이 VTEP다. 물리 네트워크는 평범한 UDP 트래픽으로만 본다.
3. **캡슐화의 대가는 MTU다** — 외부 IP·UDP·VXLAN 헤더로 50바이트 안팎이 붙는다. 물리 MTU 1500에서 Pod MTU도 1500이면 캡슐화 후 1550바이트가 되어 단편화되거나 드롭된다. 증상은 "ping·작은 요청 OK, 큰 전송 NG".
4. **오버레이는 선택지 중 하나다** — 대안은 물리 네트워크에 Pod 대역 경로를 알려 주는 네이티브 라우팅(BGP 등)과 VPC IP를 직접 받는 네이티브 IP다. 오버레이는 어디서나 되지만 MTU 손실·CPU 비용·진단 난이도를 치른다.

**이 장의 학습 목표**

- 단일 호스트 브리지가 멀티호스트에서 한계를 갖는 이유를 설명할 수 있다.
- VNI·UDP 4789·VTEP·FDB가 각각 무엇인지, 오버레이 패킷이 어떤 순서로 이동하는지 말할 수 있다.
- 캡슐화 오버헤드가 MTU 손실이 되는 계산을 하고, MTU 불일치의 전형적 증상을 안다.
- `ping -M do -s`로 실제 사용 가능한 MTU를 찾는 방법을 안다.
- 오버레이 / 네이티브 라우팅 / 네이티브 IP를 비교해 선택 기준을 설명할 수 있다.

## 코어 1. 브리지는 호스트를 못 넘는다

### 1.1 단일 호스트 브리지의 한계

**한 줄 요약:** 리눅스 브리지는 하나의 커널 안에 있는 소프트웨어 L2 스위치라서 다른 호스트의 브리지와 자동으로 이어지지 않는다.

리눅스 브리지는 브리지에 연결된 인터페이스들을 같은 물리 스위치에 꽂힌 것처럼 취급하고 이더넷 프레임을 MAC 주소 기준으로 전달한다. 그런데 브리지는 하나의 리눅스 커널 안에 존재하는 디바이스이므로, 호스트 A의 `docker0`에 붙은 컨테이너와 호스트 B의 `docker0`에 붙은 컨테이너는 아무 조치도 하지 않으면 **서로 완전히 다른 사설 IP 대역에 속한 채 서로의 존재조차 모르는** 상태가 된다([4장](04-veth-브리지-라우팅-ARP.md)의 브리지와 라우팅 개념이 전제다).

호스트 간 라우팅을 수동 구성하거나, 각 호스트의 브리지 대역이 겹치지 않게 관리하며 정적 라우트를 깔 수도 있다. 하지만 호스트 수가 늘수록 설정 복잡도가 기하급수적으로 늘고, 컨테이너가 재스케줄링되어 다른 호스트로 옮겨갈 때마다 라우팅 정보를 갱신해야 한다. 컨테이너를 여러 호스트에 자유롭게 배치하려면 물리 토폴로지와 무관하게 "논리적으로 같은 L2"인 것처럼 통신할 방법이 필요하다.

### 1.2 오버레이의 핵심 아이디어

**한 줄 요약:** 이미 존재하는 L3(IP) 연결성 위에, 캡슐화로 가상 L2 네트워크를 하나 더 얹는다.

호스트 A와 B가 평범한 IP 라우팅으로만 연결되어 있어도, 그 위에 캡슐화된 터널을 두면 같은 스위치에 연결된 것처럼 이더넷 프레임을 주고받을 수 있다. "L3 위에 가상 L2를 얹는다"는 표현이 이 구조다.

> **[보충]** 쿠버네티스 쪽 설명(textbook 23.2)은 같은 문제를 "노드 A의 Pod(10.244.1.5)가 노드 B의 Pod(10.244.2.7)에 패킷을 보낸다. **물리 네트워크는 10.244.0.0/16을 모른다.** 어떻게 전달할까?"로 제기한다. 오버레이가 이 질문에 대한 세 가지 답(코어 4) 중 첫 번째다.

## 코어 2. VXLAN = VNI + UDP 캡슐화 + VTEP

### 2.1 VXLAN의 세 요소

**한 줄 요약:** VNI가 "어느 가상 네트워크인가"를, UDP 4789 캡슐화가 "어떻게 실어 나르는가"를, VTEP이 "누가 감싸고 푸는가"를 맡는다.

VXLAN(Virtual eXtensible Local Area Network)은 RFC 7348로 표준화된 캡슐화 프로토콜이며, 원래 대규모 데이터센터에서 가상 머신용 멀티테넌트 L2 네트워크를 대량으로 만들어야 하는 요구에서 출발했다. 컨테이너 오버레이는 이 기술을 그대로 쓴다.

- **VNI(VXLAN Network Identifier):** 24비트 식별자로 논리적인 L2 네트워크를 구분한다. 24비트이므로 이론상 약 1,600만 개의 오버레이 네트워크를 동시에 운용할 수 있다. `docker network create -d overlay`로 만든 오버레이 네트워크 하나가 하나의 VNI에 대응된다. 같은 VNI를 공유하는 Endpoint끼리는 같은 논리 L2 네트워크로 취급되고, 다른 VNI의 트래픽과는 완전히 격리된다.
- **UDP 캡슐화:** 원본 이더넷 프레임 전체(안의 IP 패킷 포함)를 UDP 데이터그램의 페이로드로 감싸 보낸다. 목적지 포트로 IANA가 VXLAN 전용으로 할당한 **4789번**을 쓰는 것이 표준 동작이다(과거 일부 벤더 구현이 다른 포트를 기본값으로 쓰던 시절이 있었지만 RFC 7348 이후 4789가 사실상 표준으로 정착했다). 물리 네트워크 입장에서는 평범한 UDP 트래픽일 뿐이고, 장비는 안에 어떤 L2 프레임이 들었는지 알 필요가 없다.
- **VTEP(VXLAN Tunnel Endpoint):** VXLAN을 종단하는 지점. Swarm 환경에서는 각 노드의 커널이 VTEP 역할을 한다.

```
┌─────────────────────────────────────────────────┐
│ 외부 IP 헤더  (노드A IP → 노드B IP)               │
│ ┌─────────────────────────────────────────────┐ │
│ │ VXLAN/IPIP 헤더                              │ │
│ │ ┌─────────────────────────────────────────┐ │ │
│ │ │ 내부 IP 헤더 (Pod A IP → Pod B IP)       │ │ │
│ │ │ 페이로드                                  │ │ │
│ │ └─────────────────────────────────────────┘ │ │
│ └─────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────┘
```

### 2.2 쿠버네티스에서 오버레이 패킷의 실제 경로

**한 줄 요약:** Pod → veth → 루트 netns 라우팅 테이블이 VXLAN 인터페이스로 → FDB로 상대 노드 IP를 찾아 캡슐화 → 물리 전송 → 역캡슐화 → 로컬 라우팅 → Pod.

```
노드 A: Pod(10.244.1.5) → ping → Pod(10.244.2.7, 노드 B)

① Pod netns에서 패킷 생성, 목적지 10.244.2.7
② veth를 통해 노드 A의 루트 netns로
③ 라우팅 테이블 조회: 10.244.2.0/24 → dev vxlan.calico (또는 flannel.1)
④ VXLAN 인터페이스가 캡슐화
     - FDB(Forwarding Database)에서 10.244.2.0/24를 담당하는 노드 B의 실제 IP를 조회
     - 외부 UDP/VXLAN 헤더를 씌워 노드 B의 물리 IP로 전송 (UDP 포트 4789 또는 8472)
⑤ 노드 B의 물리 NIC가 수신 → VXLAN 헤더 확인 → 역캡슐화
⑥ 내부 패킷의 목적지(10.244.2.7)로 로컬 라우팅 → veth → Pod netns
```

```bash
# VXLAN 인터페이스와 FDB 확인 (오버레이 CNI일 때)
ip -d link show | grep -A2 vxlan
bridge fdb show dev vxlan.calico   # 또는 flannel.1
```

원천은 VXLAN 패킷 캡처에도 UDP 포트 8472를 쓴다(`tcpdump -i any -nn "udp port 8472" -c 10`). 4789가 IANA 표준 포트이고 구현·환경에 따라 8472가 쓰이는 경우가 있음을 같이 기억해 둔다.

> **[보충]** 원천(Docker 13.2)은 4789를 표준으로, 쿠버네티스 쪽(k8s-internals 13.5)은 "4789 또는 8472"로 쓴다. 두 원천이 어떤 구현이 어느 포트를 쓰는지까지는 설명하지 않으므로 이 책도 그 대응은 적지 않는다. 방화벽에서 오버레이 트래픽을 열어야 한다면 사용 중인 CNI의 실제 포트를 확인해야 한다는 점만 유의한다.

### 2.3 Docker 오버레이와의 관계

**한 줄 요약:** Docker 오버레이 드라이버는 CNM의 Network를 VXLAN VNI 하나로 구현한 것이고, Sandbox·Endpoint 개념은 브리지 드라이버와 같다.

달라지는 것은 "같은 Network에 속한다"는 멤버십을 물리적으로 다른 호스트 사이에서 어떻게 실현하느냐뿐이다. Docker 오버레이 드라이버의 세부 동작(Swarm 모드, ingress, 현재 위상)은 [10장](../2부-Docker-네트워크/10-macvlan-ipvlan-host-none-오버레이.md)에서 다룬다. CNM 모델 자체는 [7장](../2부-Docker-네트워크/07-Docker-네트워크-모델.md)에서 본다.

## 코어 3. 캡슐화의 대가는 MTU다

### 3.1 오버헤드 계산

**한 줄 요약:** 물리 MTU에서 캡슐화 오버헤드를 뺀 값이 Pod의 최대 MTU다. VXLAN이면 1500 − 50 = 1450.

원본 프레임을 통째로 UDP로 한 번 더 감싸므로 외부 IP 헤더, UDP 헤더, VXLAN 헤더가 차례로 덧붙어 VXLAN 캡슐화는 원본에 **50바이트 안팎**의 오버헤드를 더한다. 물리 MTU가 이더넷 표준 1500으로 고정된 환경에서 컨테이너 내부 MTU도 1500이면, 캡슐화 후 실제 패킷 크기가 물리 MTU를 넘는다. 결과는 단편화이거나, 단편화가 허용되지 않는 조건에서는 폐기다.

```
물리 네트워크 MTU: 1500
VXLAN 오버헤드:    -50
Pod 인터페이스 MTU: 1450 이어야 한다

만약 Pod MTU가 1500으로 설정되어 있으면:
  1500바이트 패킷 → VXLAN 캡슐화 → 1550바이트
  → 물리 MTU 초과 → 단편화 또는 드롭
```

| 환경 | 물리 MTU | 오버헤드 | Pod MTU |
|---|---|---|---|
| 일반 이더넷 + VXLAN | 1500 | 50 | **1450** |
| 일반 이더넷 + IPIP | 1500 | 20 | **1480** |
| 일반 이더넷 + WireGuard | 1500 | 60 | **1440** |
| AWS (점보 프레임) | 9001 | 50 | 8951 |
| GCP | 1460 | 50 | 1410 |

네이티브 라우팅(캡슐화 없음)이면 오버헤드 0, Pod MTU는 1500이다. Geneve는 오버헤드가 가변(기본 8 + 옵션)이라 대략 1450 내외로 본다. Docker의 오버레이 드라이버는 대체로 MTU 조정을 자동 처리하지만, 물리 네트워크의 MTU가 표준보다 작은 환경(일부 클라우드 VPC, 특정 터널 구간 등)에서는 수동으로 재확인해야 할 수 있다.

### 3.2 증상과 진단

**한 줄 요약:** ping과 작은 요청은 통과하고 큰 응답·TLS 핸드셰이크만 실패하며, 간헐적으로 느리다.

```
· ping은 잘 된다
· 작은 HTTP 요청도 잘 된다
· 큰 응답이나 파일 전송에서 멈춘다
· TLS 핸드셰이크가 실패한다
· "간헐적으로" 느리다
```

VPC 피어링이나 VPN을 거치면 MTU가 더 줄어든다. 온프레미스 연결이 있는 클러스터에서 **일부 대상만 통신이 안 되는** 증상이 나오면 MTU를 의심한다.

```bash
# ① MTU 확인
kubectl run t --rm -it --image=nicolaka/netshoot --restart=Never -- ip link show eth0
docker exec k8s-guide-worker ip link show | grep mtu

# ② 단편화 금지 ping으로 실제 MTU 찾기
kubectl run t --rm -it --image=nicolaka/netshoot --restart=Never -- \
  sh -c 'for size in 1500 1450 1400 1350; do
           echo -n "$size: "
           ping -c1 -M do -s $((size-28)) <TARGET_POD_IP> >/dev/null 2>&1 && echo OK || echo FAIL
         done'
```

첫 번째로 성공하는 크기가 실제 사용 가능한 MTU다.

> **[보충]** 위 스크립트의 `size-28`은 원천에 이유가 적혀 있지 않다. ICMP echo의 페이로드(`-s`)에는 IP 헤더 20바이트와 ICMP 헤더 8바이트가 더해져 전체 패킷 크기가 되므로 28을 뺀다는 일반 지식으로 이 책이 덧붙인 설명이다. `-M do`는 단편화 금지(Don't Fragment) 옵션이다.

설정 예(원천):

```yaml
# Calico
kind: ConfigMap
metadata:
  name: calico-config
data:
  veth_mtu: "1450"
```

```bash
# Cilium
helm upgrade cilium cilium/cilium --set MTU=1450
```

> **[보충]** 같은 원천(k8s-internals 13.5)은 MTU 진단을 "19장에서 본격적으로" 다룬다고 하고 textbook 23.5가 구체적인 명령을 준다. 이 책에서는 [23장](../4부-진단/23-네트워크-장애-진단.md)이 그 역할을 이어받는다.

## 코어 4. 오버레이는 선택지 중 하나다

### 4.1 세 가지 방식

**한 줄 요약:** 물리 네트워크가 Pod 대역을 모를 때, 캡슐화(오버레이) / 경로 광고(네이티브 라우팅) / VPC IP 직접 할당(네이티브 IP) 중 하나로 푼다.

| 구분 | 오버레이 | 네이티브 라우팅 | 네이티브 IP (클라우드 통합) |
|---|---|---|---|
| 방식 | Pod 패킷을 노드 간 패킷 안에 넣어 전송 | 물리 네트워크에 Pod CIDR 경로를 알려 줌 | Pod가 VPC의 실제 IP를 받음 |
| 구현 | VXLAN, IPIP, Geneve, WireGuard | BGP, 클라우드 라우트 테이블, 동일 L2 세그먼트 | AWS VPC CNI(ENI 보조 IP), Azure CNI, GKE(별칭 IP 범위) |
| 장점 | 물리 설정 불필요, 어디서나 동작 | 캡슐화 오버헤드·MTU 문제 없음, 진단 쉬움 | 보안 그룹·플로우 로그를 Pod에 적용, 외부에서 Pod 직접 접근 |
| 단점 | CPU 비용, MTU 감소, 물리 장비가 안을 몰라 진단 어려움 | 물리 네트워크 설정 필요, 클라우드 라우트 항목 수 제한(AWS 기본 50) | IP 고갈, 노드당 Pod 수가 인스턴스 타입에 묶임 |

| 프로토콜 | 오버헤드 | 특징 |
|---|---|---|
| VXLAN | 50 bytes | UDP 캡슐화, 가장 널리 쓰임 |
| IPIP | 20 bytes | IP-in-IP, 더 가벼움 |
| Geneve | 가변 | 확장 가능한 메타데이터 |
| WireGuard | &#126;60 bytes | 암호화 포함 |

### 4.2 네이티브 라우팅의 패킷 경로 (BGP)

```
① Pod netns에서 패킷 생성, 목적지 10.244.2.7
② 노드 A의 라우팅 테이블 조회: 10.244.2.0/24 via 192.168.1.11 dev eth0
   (이 경로는 BIRD가 BGP로 노드 B로부터 받아 커널에 주입한 것)
③ 캡슐화 없이 그대로 물리 네트워크로 전송 (목적지 IP는 여전히 10.244.2.7이지만,
   L2 프레임의 다음 홉은 노드 B)
④ 노드 B가 직접 수신 → 로컬 라우팅 → Pod netns
```

```bash
ip route | grep 10.244
# 10.244.2.0/24 via 192.168.1.11 dev eth0 proto bird
```

`proto bird`가 이 경로가 **BGP로 학습된 경로**임을 알려 준다. 캡슐화 계층이 없으므로 `tcpdump`로 봐도 평범한 IP 패킷이라 진단하기 쉽다.

### 4.3 선택 가이드

```
물리 네트워크를 제어할 수 있는가?
├─ 예 → 네이티브 라우팅 (BGP)          성능 최선
└─ 아니오
    └─ 클라우드인가?
        ├─ 예 → 클라우드 CNI 또는 클라우드 라우트
        │        IP 여유가 없다면 → 오버레이
        └─ 아니오 → 오버레이 (VXLAN)   가장 범용적
```

네이티브 IP의 노드당 최대 Pod 수는 원천의 EKS 예에서 `(ENI 수 × ENI당 IP 수) - 1`, m5.large는 3 × 10 − 1 = 29다. 클러스터 CIDR과 노드별 서브넷(Pod CIDR 할당)은 [14장](../3부-쿠버네티스-네트워크/14-CNI-스펙과-IPAM.md), CNI별 패킷 경로의 상세는 [15장](../3부-쿠버네티스-네트워크/15-CNI-플러그인과-패킷-경로.md)에서 이어진다.

## 실무 적용

### 체크리스트

- [ ] 브리지는 한 호스트 안의 L2다. 멀티호스트에는 오버레이 또는 라우팅이 필요하다.
- [ ] VXLAN은 VNI(24비트)로 네트워크를 구분하고, 원본 프레임을 UDP로 감싼다(표준 4789, 환경에 따라 8472도 사용). 방화벽에서 이 UDP 포트를 열어야 하는지 CNI 문서로 확인한다.
- [ ] 오버레이를 쓰면 Pod MTU를 반드시 물리 MTU − 오버헤드로 맞춘다(VXLAN이면 1450).
- [ ] "ping OK + 큰 전송 NG + TLS 실패 + 간헐적 느림"이면 MTU를 의심하고 `ping -M do -s`로 찾는다.
- [ ] 같은 노드는 되고 다른 노드는 안 되면 `ip route`, `ip -d link show | grep -E 'vxlan|ipip|flannel'`, `bridge fdb`, `tcpdump`(양쪽 노드 동시)를 본다.
- [ ] VPC 피어링·VPN 구간이 있으면 MTU가 더 줄어든다는 것을 기억한다.
- [ ] 네이티브 라우팅의 BGP 경로는 `ip route`에서 `proto bird`로 알아본다.

### 시나리오로 확인하기

1. **상황:** 게임 클라이언트가 접속은 되고 채팅 같은 작은 패킷은 오가는데, 접속 직후 내려받는 큰 리소스 응답에서만 멈춘다. Pod 간 `ping`은 정상이다. 클러스터는 VXLAN 오버레이이고 Pod 인터페이스 MTU가 1500이다.
   **질문:** 의심 부품, 확인, 해결은?

   <details markdown="1"><summary>답 확인</summary>

   의심 부품은 Pod MTU 불일치다. 1500바이트 패킷이 VXLAN 캡슐화로 1550바이트가 되어 물리 MTU 1500을 넘고 단편화되거나 드롭된다. `ip link show eth0`와 노드의 `ip link show | grep mtu`로 MTU를 확인하고, `ping -c1 -M do -s $((size-28)) <TARGET_POD_IP>`를 1500/1450/1400/1350으로 돌려 처음 성공하는 크기를 찾는다. 해결은 CNI의 MTU 설정(Calico `veth_mtu: "1450"`, Cilium `MTU=1450`)을 물리 MTU − 오버헤드로 맞추는 것이다. → 코어 3

   </details>

2. **상황:** 같은 노드의 Pod끼리는 통신되는데 다른 노드의 Pod와는 안 된다. MTU 문제는 아닌 것 같다.
   **질문:** 어디를 어떤 순서로 보는가?

   <details markdown="1"><summary>답 확인</summary>

   노드 간 경로(오버레이 또는 라우팅)를 본다. 오버레이라면 `ip route | grep 10.244`로 상대 노드 Pod 대역이 VXLAN 인터페이스를 가리키는지, `ip -d link show | grep -A2 vxlan`와 `bridge fdb show dev vxlan.calico`(또는 `flannel.1`)로 상대 노드 IP가 FDB에 있는지 확인한다. `tcpdump -i any -nn "udp port 8472"`로 양쪽 노드에서 동시에 캡처하면 패킷이 어디서 사라지는지 안다. 네이티브 라우팅이면 `ip route`에 `via <노드IP> ... proto bird` 경로가 있는지 본다. → 코어 2 (2.2), 코어 4 (4.2)

   </details>

3. **상황:** 온프레미스에 사설 네트워크 장비를 직접 관리하는 팀이 "캡슐화 오버헤드가 아깝다"며 오버레이 대신 다른 방식을 쓰자고 한다.
   **질문:** 어떤 선택지가 있고 trade-off는?

   <details markdown="1"><summary>답 확인</summary>

   물리 네트워크를 제어할 수 있다면 네이티브 라우팅(BGP)이 성능 최선이다. 캡슐화 오버헤드와 MTU 문제가 없고 `tcpdump`로 평범한 IP 패킷이 보여 진단이 쉽다. 대신 물리 네트워크에 Pod CIDR 경로 설정이 필요하다. 오버레이는 물리 설정 없이 어디서나 동작하지만 MTU 손실·CPU 비용·진단 난이도를 감수해야 한다. → 코어 4 (4.1, 4.3)

   </details>

### 2. 인출 질문

1. 호스트 A와 B의 `docker0` 컨테이너가 별도 설정 없이 통신되지 않는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   브리지는 하나의 커널 안에 있는 디바이스라 다른 호스트의 브리지와 자동으로 이어지지 않는다. 각각 다른 사설 IP 대역에 속해 서로의 존재를 모른다. 정적 라우트로 이을 수는 있지만 호스트 수와 재스케줄링이 늘면 감당하기 어렵다. → 코어 1 (1.1)

   </details>

2. "L3 위에 가상 L2를 얹는다"는 말을 한 문장으로 풀면?

   <details markdown="1"><summary>답 확인</summary>

   호스트들이 평범한 IP 라우팅으로만 연결되어 있어도, 이더넷 프레임을 캡슐화해 터널로 실어 보내면 마치 같은 스위치에 연결된 것처럼 통신할 수 있다는 뜻이다. → 코어 1 (1.2)

   </details>

3. VNI, UDP 4789, VTEP는 각각 무엇인가?

   <details markdown="1"><summary>답 확인</summary>

   VNI는 논리 L2 네트워크를 구분하는 24비트 식별자(약 1,600만 개), UDP 4789는 원본 프레임을 감싸 보내는 VXLAN 표준 목적지 포트, VTEP은 캡슐화·역캡슐화하는 터널 끝점(Swarm에서는 각 노드의 커널)이다. → 코어 2 (2.1)

   </details>

4. 오버레이에서 다른 노드의 Pod로 가는 패킷의 경로를 6단계로 말하라.

   <details markdown="1"><summary>답 확인</summary>

   ① Pod netns에서 패킷 생성 → ② veth로 노드 루트 netns → ③ 라우팅 테이블이 `10.244.2.0/24 → vxlan 인터페이스` → ④ FDB에서 상대 노드 IP를 찾아 UDP/VXLAN 캡슐화 후 전송 → ⑤ 상대 노드 NIC가 수신해 역캡슐화 → ⑥ 로컬 라우팅 → veth → Pod netns. → 코어 2 (2.2)

   </details>

5. 물리 MTU 1500에서 VXLAN 오버레이의 Pod MTU는 얼마여야 하고, 1500이면 어떻게 되는가?

   <details markdown="1"><summary>답 확인</summary>

   1450(오버헤드 50). 1500이면 1500바이트 패킷이 캡슐화로 1550바이트가 되어 물리 MTU를 넘고 단편화 또는 드롭된다. → 코어 3 (3.1)

   </details>

6. MTU 불일치의 전형적 증상 3가지와, 실제 MTU를 찾는 명령은?

   <details markdown="1"><summary>답 확인</summary>

   ping은 되고 작은 요청도 되지만 큰 응답/파일 전송에서 멈추고, TLS 핸드셰이크가 실패하고, 간헐적으로 느리다. `ping -c1 -M do -s $((size-28)) <TARGET_POD_IP>`를 1500·1450·1400·1350으로 돌려 처음 성공하는 크기가 사용 가능한 MTU다. → 코어 3 (3.2)

   </details>

7. 네이티브 라우팅이 오버레이보다 진단하기 쉬운 이유는?

   <details markdown="1"><summary>답 확인</summary>

   캡슐화 계층이 없어 `tcpdump`로 봐도 평범한 IP 패킷이고, BGP로 학습된 경로는 `ip route`에서 `proto bird`로 확인된다. MTU 문제도 없다. 대신 물리 네트워크 설정이 필요하다. → 코어 4 (4.2)

   </details>

8. 어떤 환경에서 어떤 방식을 고르는가?

   <details markdown="1"><summary>답 확인</summary>

   물리 네트워크를 제어할 수 있으면 네이티브 라우팅(BGP), 아니고 클라우드면 클라우드 CNI/라우트(IP 여유가 없으면 오버레이), 클라우드도 아니면 가장 범용적인 오버레이(VXLAN). → 코어 4 (4.3)

   </details>

### 3. 기억 고리

- **C++ 유추:** 캡슐화 ≈ 게임 패킷에 바깥 헤더를 하나 더 씌우는 것. ⚠️ 씌우는 대상이 이더넷 프레임 전체이고 바깥은 UDP/IP라, 포장 크기만큼 실을 수 있는 데이터가 줄어든다(MTU).
- **C++ 유추:** "ping 되니까 정상" ≈ 작은 테스트 패킷만 보내 보고 안심하는 것. ⚠️ 큰 패킷만 막히는 장애가 있다.
- **비유:** 오버레이 = 택배 상자 안의 택배 상자. 안쪽 상자(Pod 패킷)를 바깥 상자(UDP/IP)에 담아 지역 간 운송망(물리 네트워크)에 맡기고, 도착 지점(VTEP)에서 바깥 상자를 뜯는다. 운송망은 안쪽 상자의 내용을 모른다. ⚠️ 깨지는 지점: 상자가 겹치면 부피(헤더 50바이트)가 늘어서 규격(MTU)을 넘기면 쪼개지거나 반송(드롭)된다.
- **묶음(3의 법칙):** VXLAN 3요소(VNI·UDP 캡슐화·VTEP) · 해결 3방식(오버레이·네이티브 라우팅·네이티브 IP) · MTU 증상 3(ping OK·큰 전송 NG·TLS NG).
- **대칭·순서:** 캡슐화(송신 노드) ↔ 역캡슐화(수신 노드). 오버레이 6단계 ↔ 네이티브 라우팅 4단계(캡슐화·역캡슐화 단계 제거). MTU = 물리 MTU − 오버헤드.
