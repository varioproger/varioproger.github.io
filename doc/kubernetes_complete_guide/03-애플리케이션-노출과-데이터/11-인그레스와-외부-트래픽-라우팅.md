# 11장. 인그레스와 외부 트래픽 라우팅

> **학습목표**
> - Ingress 리소스와 IngressController의 관계를 설명할 수 있다.
> - 호스트·경로 기반 라우팅과 TLS 종료를 설정할 수 있다.
> - cert-manager로 인증서 발급과 갱신을 자동화할 수 있다.
> - 클라우드별 인그레스 통합 방식의 차이를 안다.
> - Gateway API가 Ingress의 어떤 한계를 해결하는지 설명할 수 있다.
> - 서비스 메시가 필요한 시점과 과한 시점을 판단할 수 있다.

---

## 들어가며

9장에서 본 것처럼, LoadBalancer 타입 Service는 하나당 클라우드 로드밸런서 하나를 만든다. 서비스가 30개면 LB도 30개, IP도 30개, 인증서도 30개다. 비용과 관리 부담이 곱셈으로 늘어난다.

게다가 Service는 **L4(TCP/UDP)** 에서 동작한다. "`/api`로 오는 요청은 백엔드로, `/`는 프론트엔드로" 같은 HTTP 수준의 판단을 할 수 없다.

**Ingress**는 이 둘을 해결한다. 하나의 진입점에서 HTTP/HTTPS 트래픽을 받아 호스트와 경로에 따라 여러 서비스로 나눈다.

```
                     ┌─────────────────────────────┐
                     │      Ingress Controller     │
인터넷 → LB (1개) →  │  shop.example.com/     → web│
                     │  shop.example.com/api  → api│
                     │  admin.example.com/    → adm│
                     └─────────────────────────────┘
```

## 11.1 Ingress와 IngressController

### 둘은 다른 것이다

이 구분이 가장 중요하다.

| | Ingress | IngressController |
|---|---|---|
| 정체 | **API 리소스**(설정 데이터) | **실행되는 프로그램**(리버스 프록시) |
| 하는 일 | "이렇게 라우팅해 달라"고 선언 | 그 선언을 읽어 실제로 라우팅 |
| 배포 형태 | YAML 매니페스트 | Deployment/DaemonSet + Service |

**Ingress 리소스만 만들면 아무 일도 일어나지 않는다.** 컨트롤러가 없으면 그저 etcd에 저장된 데이터일 뿐이다. 이것이 초보자가 가장 자주 겪는 혼란이다.

```bash
kubectl get ingress
# NAME   CLASS   HOSTS              ADDRESS   PORTS   AGE
# web    nginx   shop.example.com             80      5m
#                                   ^^^^^^^
#                                   ADDRESS가 비어 있다 = 컨트롤러가 처리하지 않았다
```

### 컨트롤러의 동작

```
① API 서버 watch → Ingress, Service, EndpointSlice, Secret 변경 감지
② 자신의 설정 파일(nginx.conf 등)을 재생성
③ 프로세스 리로드
④ 들어오는 요청을 규칙에 따라 백엔드 Pod로 프록시
```

**중요**: 대부분의 컨트롤러는 Service의 ClusterIP를 거치지 않고 **Pod IP로 직접** 프록시한다. kube-proxy를 우회하므로 홉이 하나 줄고, 세션 고정이나 가중치 같은 L7 기능을 컨트롤러가 직접 구현할 수 있다.

### 주요 IngressController

| 컨트롤러 | 특징 |
|---|---|
| **ingress-nginx** | 쿠버네티스 프로젝트가 관리. 가장 널리 쓰임. 애노테이션으로 세밀한 제어 |
| **NGINX Ingress Controller** (F5) | NGINX Inc.의 상용/오픈소스 버전. 위와 **다른 프로젝트다** |
| **Traefik** | 자동 서비스 디스커버리, Let's Encrypt 내장, 대시보드 |
| **HAProxy Ingress** | 고성능, 세밀한 로드밸런싱 |
| **Envoy 기반** (Contour, Emissary) | Gateway API 지원, gRPC 친화적 |
| **클라우드 네이티브** (AWS LBC, GKE Ingress, AGIC) | 클라우드 LB를 직접 제어 |

> **⚠️ 이름이 비슷한 두 프로젝트**
> `ingress-nginx`(커뮤니티, `kubernetes/ingress-nginx`)와 `nginx-ingress`(F5/NGINX Inc.)는 **다른 프로젝트**이며 애노테이션 접두사도 다르다.
> - ingress-nginx: `nginx.ingress.kubernetes.io/...`
> - NGINX Inc.: `nginx.org/...`
>
> 문서를 찾을 때 어느 쪽인지 확인해야 한다. 이 장에서는 ingress-nginx를 기준으로 한다.

### IngressClass

여러 컨트롤러를 함께 쓸 때 어느 것이 처리할지 지정한다.

```yaml
apiVersion: networking.k8s.io/v1
kind: IngressClass
metadata:
  name: nginx
  annotations:
    ingressclass.kubernetes.io/is-default-class: "true"    # 기본값 지정
spec:
  controller: k8s.io/ingress-nginx
```

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web
spec:
  ingressClassName: nginx        # ★ 어느 컨트롤러가 처리할지
```

과거에는 `kubernetes.io/ingress.class` 애노테이션을 썼지만 **폐기됐다.** `ingressClassName` 필드를 쓴다.

## 11.2 실습: NGINX Ingress Controller

3장에서 만든 kind 클러스터에는 `extraPortMappings`로 80번 포트를 열어 두었다. 이제 그것을 쓴다.

**① 컨트롤러 설치**

```bash
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/main/deploy/static/provider/kind/deploy.yaml

kubectl wait --namespace ingress-nginx \
  --for=condition=ready pod \
  --selector=app.kubernetes.io/component=controller \
  --timeout=120s
```

kind용 매니페스트는 `hostPort`로 80/443을 노드에 바인딩하고, `nodeSelector: ingress-ready=true`로 컨트롤 플레인 노드에 배치한다. 3장의 클러스터 설정에서 그 라벨을 미리 붙여 두었다.

```bash
kubectl get pods -n ingress-nginx
kubectl get ingressclass
```

**② 백엔드 서비스 두 개 준비**

```yaml
# backends.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 2
  selector: { matchLabels: { app: web } }
  template:
    metadata: { labels: { app: web } }
    spec:
      containers:
        - name: app
          image: hashicorp/http-echo:1.0
          args: ["-text=I am WEB", "-listen=:5678"]
          ports: [{ containerPort: 5678 }]
---
apiVersion: v1
kind: Service
metadata: { name: web }
spec:
  selector: { app: web }
  ports: [{ port: 80, targetPort: 5678 }]
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 2
  selector: { matchLabels: { app: api } }
  template:
    metadata: { labels: { app: api } }
    spec:
      containers:
        - name: app
          image: hashicorp/http-echo:1.0
          args: ["-text=I am API", "-listen=:5678"]
          ports: [{ containerPort: 5678 }]
---
apiVersion: v1
kind: Service
metadata: { name: api }
spec:
  selector: { app: api }
  ports: [{ port: 80, targetPort: 5678 }]
```

```bash
kubectl apply -f backends.yaml
```

**③ 경로 기반 라우팅**

```yaml
# ingress-path.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /$2
spec:
  ingressClassName: nginx
  rules:
    - host: shop.localdev.me            # *.localdev.me → 127.0.0.1 로 해석된다
      http:
        paths:
          - path: /api(/|$)(.*)
            pathType: ImplementationSpecific
            backend:
              service:
                name: api
                port:
                  number: 80
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web
                port:
                  number: 80
```

```bash
kubectl apply -f ingress-path.yaml
kubectl get ingress shop
```

**④ 테스트**

```bash
curl -H "Host: shop.localdev.me" http://localhost/
# I am WEB

curl -H "Host: shop.localdev.me" http://localhost/api/users
# I am API
```

`localdev.me`는 모든 하위 도메인이 `127.0.0.1`로 해석되는 공개 도메인이라 로컬 실습에 편리하다. `/etc/hosts`를 수정할 필요가 없다.

### pathType 이해하기

이 필드가 매칭 방식을 결정한다.

| pathType | 동작 |
|---|---|
| `Exact` | 경로가 정확히 일치 |
| `Prefix` | **경로 세그먼트 단위** 접두사 일치 |
| `ImplementationSpecific` | 컨트롤러가 알아서 (nginx는 정규식 지원) |

**`Prefix`의 세그먼트 단위 매칭**이 헷갈리기 쉽다.

```
path: /api  (Prefix)
  /api        ✓ 매칭
  /api/       ✓ 매칭
  /api/users  ✓ 매칭
  /apifoo     ✗ 매칭 안 됨! (세그먼트가 다르다)
```

**우선순위**: 더 긴 경로가 우선한다. `/api/v2`가 `/api`보다 먼저 매칭된다.

### rewrite-target

백엔드 앱이 `/api` 접두사를 모른다면 제거해서 전달해야 한다.

```yaml
metadata:
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /$2
spec:
  rules:
    - http:
        paths:
          - path: /api(/|$)(.*)      # $2 = 캡처 그룹 2번
            pathType: ImplementationSpecific
```

```
요청: /api/users/1
백엔드가 받는 경로: /users/1
```

> **⚠️ rewrite와 상대 경로의 함정**
> HTML 안의 상대 경로(`<img src="logo.png">`)는 브라우저가 `/api/logo.png`로 요청한다. 백엔드는 `/logo.png`를 기대하는데 rewrite가 적용되어 다시 `/logo.png`가 되므로 우연히 동작하기도 하고 안 하기도 한다.
>
> **경로 기반 분리보다 서브도메인 분리가 안전하다.**
> ```
> api.example.com  → api 서비스
> www.example.com  → web 서비스
> ```

### 호스트 기반 라우팅

```yaml
spec:
  ingressClassName: nginx
  rules:
    - host: web.localdev.me
      http:
        paths:
          - path: /
            pathType: Prefix
            backend: { service: { name: web, port: { number: 80 } } }
    - host: api.localdev.me
      http:
        paths:
          - path: /
            pathType: Prefix
            backend: { service: { name: api, port: { number: 80 } } }
    - host: "*.dev.localdev.me"        # 와일드카드 (한 단계만)
      http:
        paths:
          - path: /
            pathType: Prefix
            backend: { service: { name: web, port: { number: 80 } } }
```

```bash
curl -H "Host: web.localdev.me" http://localhost/
curl -H "Host: api.localdev.me" http://localhost/
```

### 기본 백엔드

어느 규칙에도 매칭되지 않는 요청을 처리한다.

```yaml
spec:
  defaultBackend:
    service:
      name: fallback
      port: { number: 80 }
```

## 11.3 TLS 종료와 cert-manager

### Ingress에서 TLS 설정

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - shop.example.com
      secretName: shop-tls          # ★ kubernetes.io/tls 타입 Secret
  rules:
    - host: shop.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend: { service: { name: web, port: { number: 80 } } }
```

Secret은 7장에서 본 TLS 타입이다.

```bash
kubectl create secret tls shop-tls --cert=tls.crt --key=tls.key
```

**TLS는 컨트롤러에서 종료된다.** 컨트롤러 → 백엔드 Pod 구간은 기본적으로 평문 HTTP다. 이 구간도 암호화하려면 서비스 메시(11.6절)나 백엔드 프로토콜 설정이 필요하다.

```yaml
annotations:
  nginx.ingress.kubernetes.io/backend-protocol: "HTTPS"
```

### cert-manager로 자동화

인증서를 수동으로 발급·갱신하는 것은 지속 가능하지 않다. Let's Encrypt 인증서는 90일마다 만료된다.

**cert-manager**는 인증서 발급·갱신을 CRD로 자동화한다. 6부에서 배울 오퍼레이터 패턴의 대표적 사례다.

**① 설치**

```bash
helm repo add jetstack https://charts.jetstack.io
helm install cert-manager jetstack/cert-manager \
  --namespace cert-manager --create-namespace \
  --set crds.enabled=true
```

**② Issuer 정의**

```yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: admin@example.com
    privateKeySecretRef:
      name: letsencrypt-prod-account-key
    solvers:
      # HTTP-01 챌린지 (가장 간단)
      - http01:
          ingress:
            ingressClassName: nginx
      # DNS-01 챌린지 (와일드카드 인증서에 필수)
      - dns01:
          route53:
            region: ap-northeast-2
        selector:
          dnsZones: ["example.com"]
```

**HTTP-01 vs DNS-01**

| | HTTP-01 | DNS-01 |
|---|---|---|
| 검증 방식 | `/.well-known/acme-challenge/` 경로에 파일 배치 | DNS TXT 레코드 생성 |
| 요구사항 | 외부에서 80번 포트 접근 가능 | DNS 제공자 API 자격증명 |
| 와일드카드 | ❌ 불가 | ✅ 가능 |
| 내부망 서비스 | ❌ 불가 | ✅ 가능 |

**③ Ingress에 애노테이션 하나 추가**

```yaml
metadata:
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod
spec:
  tls:
    - hosts: [shop.example.com]
      secretName: shop-tls        # cert-manager가 이 Secret을 만들어 준다
```

**이것으로 끝이다.** cert-manager가 Ingress를 감시하다가:
1. `Certificate` 리소스를 자동 생성
2. ACME 챌린지 수행 (임시 Ingress/DNS 레코드 생성)
3. 인증서 발급 후 Secret에 저장
4. **만료 30일 전 자동 갱신**

**④ 상태 확인**

```bash
kubectl get certificate
kubectl describe certificate shop-tls
kubectl get certificaterequest,order,challenge      # 발급 과정 추적
```

발급이 안 될 때는 이 순서로 따라가면 어디서 막혔는지 알 수 있다.

> **테스트할 때는 staging Issuer를 쓰자**
> Let's Encrypt 프로덕션 환경에는 **주당 5회**의 중복 인증서 발급 제한이 있다. 설정을 시험하는 동안에는 staging을 쓴다.
> ```yaml
> server: https://acme-staging-v02.api.letsencrypt.org/directory
> ```
> staging 인증서는 브라우저가 신뢰하지 않지만 발급 과정은 동일하게 검증할 수 있다.

## 11.4 유용한 애노테이션 (ingress-nginx)

Ingress 리소스는 표준화된 필드가 적어서, 실무 기능은 대부분 애노테이션으로 제공된다.

```yaml
metadata:
  annotations:
    # --- 리다이렉트 ---
    nginx.ingress.kubernetes.io/ssl-redirect: "true"          # HTTP → HTTPS
    nginx.ingress.kubernetes.io/force-ssl-redirect: "true"
    nginx.ingress.kubernetes.io/permanent-redirect: "https://new.example.com"

    # --- 요청 제한 ---
    nginx.ingress.kubernetes.io/proxy-body-size: "50m"        # 업로드 크기
    nginx.ingress.kubernetes.io/proxy-read-timeout: "300"
    nginx.ingress.kubernetes.io/proxy-connect-timeout: "10"

    # --- 레이트 리밋 ---
    nginx.ingress.kubernetes.io/limit-rps: "10"               # 초당 요청
    nginx.ingress.kubernetes.io/limit-connections: "20"

    # --- 세션 고정 ---
    nginx.ingress.kubernetes.io/affinity: "cookie"
    nginx.ingress.kubernetes.io/session-cookie-name: "SRVID"
    nginx.ingress.kubernetes.io/session-cookie-max-age: "3600"

    # --- CORS ---
    nginx.ingress.kubernetes.io/enable-cors: "true"
    nginx.ingress.kubernetes.io/cors-allow-origin: "https://app.example.com"

    # --- 인증 ---
    nginx.ingress.kubernetes.io/auth-type: basic
    nginx.ingress.kubernetes.io/auth-secret: basic-auth
    # 외부 인증 서비스 위임 (OAuth2 Proxy 등)
    nginx.ingress.kubernetes.io/auth-url: "https://auth.example.com/oauth2/auth"
    nginx.ingress.kubernetes.io/auth-signin: "https://auth.example.com/oauth2/start"

    # --- 접근 제어 ---
    nginx.ingress.kubernetes.io/whitelist-source-range: "203.0.113.0/24"

    # --- 백엔드 프로토콜 ---
    nginx.ingress.kubernetes.io/backend-protocol: "GRPC"      # HTTP | HTTPS | GRPC | AJP
```

### 애노테이션 기반 카나리

8장에서 replica 비율로 카나리를 했지만, 인그레스는 **정확한 비율**을 지원한다.

```yaml
# 안정 버전 Ingress (기존)
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-stable
spec:
  ingressClassName: nginx
  rules:
    - host: shop.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend: { service: { name: web-v1, port: { number: 80 } } }
---
# 카나리 Ingress (같은 host, 같은 path)
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-canary
  annotations:
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "10"           # 10%
    # 또는 헤더 기반
    # nginx.ingress.kubernetes.io/canary-by-header: "X-Canary"
    # nginx.ingress.kubernetes.io/canary-by-header-value: "always"
    # 또는 쿠키 기반
    # nginx.ingress.kubernetes.io/canary-by-cookie: "canary"
spec:
  ingressClassName: nginx
  rules:
    - host: shop.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend: { service: { name: web-v2, port: { number: 80 } } }
```

**Pod 수와 무관하게 정확히 10%를 보낸다.** 게다가 헤더나 쿠키로 특정 사용자만 새 버전에 노출시킬 수 있다. 8.2절에서 말한 replica 비율 방식의 한계를 넘어선다.

```bash
# 가중치 조절
kubectl annotate ingress web-canary \
  nginx.ingress.kubernetes.io/canary-weight=50 --overwrite
```

> **⚠️ 애노테이션의 근본 문제**
> 지금까지 본 기능들은 **모두 비표준이다.** ingress-nginx에서 Traefik으로 바꾸면 애노테이션을 전부 다시 써야 한다. 타입 검증도 없어서 오타가 나면 조용히 무시된다.
>
> 이 문제를 해결하려는 것이 다음 절의 **Gateway API**다.

## 11.5 Gateway API — Ingress의 후계

### Ingress의 한계

Ingress는 2015년에 만들어져 2020년 `networking.k8s.io/v1`로 GA됐지만, 설계상 한계가 명확하다.

1. **표현력 부족.** 헤더 기반 라우팅, 트래픽 분할, 재시도, 타임아웃 — 표준 필드가 없다.
2. **애노테이션 난립.** 컨트롤러마다 다르고 이식성이 없다.
3. **역할 분리 불가.** 인프라 팀(LB, 인증서)과 앱 팀(라우팅 규칙)이 같은 리소스를 편집해야 한다.
4. **HTTP 전용.** TCP/UDP/gRPC를 제대로 표현하지 못한다.

### Gateway API의 구조

**역할별로 리소스를 분리한 것**이 핵심이다.

```
┌──────────────────────────────────────────────────┐
│ GatewayClass          ← 인프라 제공자가 정의        │
│   "이 클러스터에서 쓸 수 있는 게이트웨이 종류"       │
└──────────────────────────────────────────────────┘
                    ▲
┌───────────────────┴──────────────────────────────┐
│ Gateway               ← 클러스터 운영자가 관리      │
│   "80/443 포트를 열고, 이 인증서를 쓴다"            │
│   "어떤 네임스페이스의 Route를 붙일 수 있다"         │
└──────────────────────────────────────────────────┘
                    ▲
┌───────────────────┴──────────────────────────────┐
│ HTTPRoute / GRPCRoute / TCPRoute                 │
│                       ← 애플리케이션 개발자가 관리  │
│   "이 호스트, 이 경로는 내 서비스로"                │
└──────────────────────────────────────────────────┘
```

**각 팀이 자기 리소스만 관리하면 된다.** RBAC로 권한을 자연스럽게 나눌 수 있다.

### 예제

```yaml
# ① 인프라 팀: Gateway
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: prod-gateway
  namespace: infra
spec:
  gatewayClassName: nginx
  listeners:
    - name: https
      protocol: HTTPS
      port: 443
      hostname: "*.example.com"
      tls:
        mode: Terminate
        certificateRefs:
          - name: wildcard-example-com
      allowedRoutes:
        namespaces:
          from: Selector
          selector:
            matchLabels:
              gateway-access: "true"     # 이 라벨이 있는 NS만 연결 허용
---
# ② 앱 팀: HTTPRoute
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: shop
  namespace: shop
spec:
  parentRefs:
    - name: prod-gateway
      namespace: infra
  hostnames:
    - shop.example.com
  rules:
    # 헤더 기반 라우팅 — 표준 기능!
    - matches:
        - path: { type: PathPrefix, value: /api }
          headers:
            - name: X-Version
              value: v2
      backendRefs:
        - name: api-v2
          port: 80

    # 트래픽 분할 — 표준 기능!
    - matches:
        - path: { type: PathPrefix, value: / }
      backendRefs:
        - name: web-v1
          port: 80
          weight: 90
        - name: web-v2
          port: 80
          weight: 10

    # 요청 변형 — 표준 기능!
    - matches:
        - path: { type: PathPrefix, value: /old }
      filters:
        - type: RequestRedirect
          requestRedirect:
            path:
              type: ReplacePrefixMatch
              replacePrefixMatch: /new
            statusCode: 301
      backendRefs:
        - name: web
          port: 80
```

**애노테이션 없이 모든 것이 스펙 필드다.** 타입 검증이 되고, 컨트롤러를 바꿔도 그대로 동작한다.

### 지원 상태와 도입 시점

```bash
# CRD 설치 (표준 채널)
kubectl apply -f https://github.com/kubernetes-sigs/gateway-api/releases/download/v1.2.0/standard-install.yaml
```

- **v1.0 GA**(2023년 10월): `Gateway`, `GatewayClass`, `HTTPRoute`
- 지원 구현: Envoy Gateway, Istio, Contour, Traefik, Cilium, NGINX Gateway Fabric, GKE Gateway, AWS Gateway API Controller

**언제 도입할 것인가?**

- **신규 프로젝트**: Gateway API를 우선 검토할 만하다.
- **기존 Ingress 운영 중**: 서두를 필요 없다. Ingress는 계속 지원된다. 애노테이션 지옥에 시달리거나 팀 간 권한 분리가 필요해질 때 마이그레이션한다.
- **`ingress2gateway`** 라는 변환 도구가 있다.

## 11.5b 클라우드별 인그레스 통합

29장에서 상세히 다루지만, 여기서 개요를 잡아 둔다.

| | **AWS** | **GCP** | **Azure** |
|---|---|---|---|
| 컨트롤러 | AWS Load Balancer Controller | GKE Ingress | Application Gateway Ingress Controller (AGIC) |
| 만드는 것 | ALB (L7) / NLB (L4) | Cloud Load Balancing | Application Gateway |
| 특징 | Target Group에 Pod IP 직접 등록 가능 | 글로벌 애니캐스트 IP, Cloud CDN 통합 | WAF 통합 |
| 인증서 | ACM 연동 | Google-managed certificates | Key Vault 연동 |
| 대안 | ingress-nginx + NLB | ingress-nginx + LB | ingress-nginx + LB |

**클라우드 네이티브 컨트롤러 vs ingress-nginx**

| | 클라우드 네이티브 | ingress-nginx |
|---|---|---|
| 관리 부담 | 낮음 (LB는 클라우드가 운영) | 컨트롤러 Pod를 직접 운영 |
| 클라우드 기능 | WAF, CDN, ACM 등 완전 통합 | 별도 구성 필요 |
| 이식성 | ❌ 클라우드 종속 | ✅ 어디서나 동일 |
| 설정 유연성 | 클라우드 LB의 제약 안에서 | NGINX 설정 전체 |
| 지연 | 프로비저닝에 수 분 | 즉시 반영 |
| 비용 | LB 요금 | 노드 리소스 + LB 1개 |

**멀티 클라우드나 온프레미스가 섞여 있다면 ingress-nginx로 통일**하는 편이 운영이 단순하다. 단일 클라우드에 집중한다면 네이티브 컨트롤러의 통합 이점이 크다.

## 11.6 서비스 메시 — 언제 필요하고 언제 과한가

### 무엇을 해 주는가

인그레스가 **남북(north-south) 트래픽**(외부 ↔ 클러스터)을 다룬다면, 서비스 메시는 **동서(east-west) 트래픽**(서비스 ↔ 서비스)을 다룬다.

```
        인그레스 (남북)
             │
    ┌────────▼────────┐
    │   서비스 A       │
    └───┬─────────┬───┘
        │         │      서비스 메시 (동서)
    ┌───▼───┐ ┌───▼───┐
    │서비스B │ │서비스C │
    └───────┘ └───────┘
```

**제공하는 것**

| 영역 | 기능 |
|---|---|
| **보안** | 서비스 간 mTLS 자동 적용, 인증서 자동 로테이션, 세밀한 인가 정책 |
| **트래픽 관리** | 재시도, 타임아웃, 서킷 브레이커, 트래픽 분할, 폴트 인젝션 |
| **관측성** | 모든 서비스 간 호출의 메트릭·트레이스·로그를 **코드 수정 없이** 수집 |

**어떻게 하는가**: 각 Pod에 사이드카 프록시(Envoy)를 주입해 모든 트래픽을 가로챈다. 5.6절의 사이드카 패턴이 대규모로 적용된 것이다.

### 주요 구현

| | 아키텍처 | 특징 |
|---|---|---|
| **Istio** | 사이드카 (+ Ambient 모드) | 기능 최다, 복잡도 최고 |
| **Linkerd** | 사이드카 (경량 Rust 프록시) | 단순함 지향, 리소스 적게 씀 |
| **Cilium Service Mesh** | eBPF (사이드카 없음) | 커널 레벨, 오버헤드 적음 |
| **Istio Ambient** | ztunnel(노드 단위) + waypoint | 사이드카 제거로 비용 절감 |

### 비용

메시는 공짜가 아니다.

- **리소스**: Pod마다 프록시 컨테이너 하나 추가. 메모리 50~100MB, CPU 오버헤드.
- **지연**: 요청마다 프록시 두 번 통과. 보통 1~3ms 추가.
- **복잡도**: 디버깅 대상이 하나 더 생긴다. "요청이 실패하는데 앱 로그에는 아무것도 없다" 같은 상황이 늘어난다.
- **학습 곡선**: Istio의 개념(VirtualService, DestinationRule, PeerAuthentication...)을 팀 전체가 알아야 한다.

### 판단 기준

**메시가 정당화되는 신호**

- 서비스가 **20개를 넘고** 서로 복잡하게 호출한다
- **모든 서비스 간 통신에 mTLS**가 규제상 요구된다(금융, 의료)
- 서비스 간 호출의 **분산 트레이싱**이 필요한데 앱을 일일이 수정할 수 없다
- **정교한 트래픽 제어**(서킷 브레이커, 재시도 정책)가 여러 서비스에 일관되게 필요하다

**메시가 과한 신호**

- 서비스가 10개 미만이다
- 팀이 작고 쿠버네티스 자체도 아직 익숙하지 않다
- 필요한 것이 **관측성뿐**이다 → OpenTelemetry 라이브러리(31장)로 충분하다
- 필요한 것이 **트래픽 분할뿐**이다 → 인그레스 카나리나 Argo Rollouts(30장)로 충분하다
- 필요한 것이 **네트워크 격리뿐**이다 → NetworkPolicy(18장)로 충분하다

> **"메시를 도입하기 전에, 그것이 해결할 문제를 이미 겪고 있는지 확인하라."**
>
> 많은 팀이 문제를 겪기 전에 메시를 도입했다가 복잡도만 떠안는다. 반대로 정말 필요한 규모에 도달하면 메시 없이는 관리가 불가능해진다. **필요해진 뒤에 도입해도 늦지 않다.**

## 11.7 인그레스 문제 진단

```bash
# ① Ingress에 ADDRESS가 할당됐는가
kubectl get ingress
# ADDRESS가 비어 있으면 → 컨트롤러가 처리하지 않음

# ② IngressClass가 맞는가
kubectl get ingressclass
kubectl get ingress <name> -o jsonpath='{.spec.ingressClassName}'

# ③ 컨트롤러가 이 Ingress를 인식했는가
kubectl describe ingress <name>        # Events 확인
kubectl logs -n ingress-nginx -l app.kubernetes.io/component=controller --tail=50

# ④ 백엔드 서비스와 엔드포인트가 있는가  ★ 9장의 진단
kubectl get svc,endpointslice

# ⑤ 생성된 nginx 설정 직접 확인
kubectl exec -n ingress-nginx <controller-pod> -- cat /etc/nginx/nginx.conf | grep -A20 "server_name shop"

# ⑥ 컨트롤러 Pod에서 백엔드로 직접 접근
kubectl exec -n ingress-nginx <controller-pod> -- curl -s http://web.default.svc.cluster.local
```

**증상별 원인표**

| 증상 | 원인 |
|---|---|
| `404 Not Found` (nginx 기본 페이지) | 호스트/경로 매칭 실패. `Host` 헤더 확인 |
| `503 Service Unavailable` | 백엔드 엔드포인트 없음 → 9장 진단 |
| `502 Bad Gateway` | 백엔드가 응답 안 함. 포트 불일치, 앱 크래시 |
| `504 Gateway Timeout` | 백엔드가 느림. `proxy-read-timeout` 조정 |
| TLS 인증서 오류 | Secret 이름·네임스페이스 확인. **Secret은 Ingress와 같은 네임스페이스에 있어야 한다** |
| ADDRESS 비어 있음 | `ingressClassName` 불일치, 컨트롤러 미설치 |
| 리다이렉트 루프 | `ssl-redirect` + 앞단 LB가 이미 TLS 종료. `force-ssl-redirect: false` |

**마지막 항목이 클라우드 환경에서 흔하다.** ALB가 TLS를 종료하고 HTTP로 컨트롤러에 전달하는데, 컨트롤러가 "HTTP네? HTTPS로 리다이렉트!"를 반복한다. `X-Forwarded-Proto` 헤더를 신뢰하도록 설정해야 한다.

**과제 1 — 세 가지 라우팅 방식 비교**
같은 두 서비스를 ① 경로 기반(`/api`, `/`), ② 호스트 기반(`api.localdev.me`, `web.localdev.me`), ③ 둘의 조합으로 각각 노출한다. `rewrite-target`이 필요한 경우와 아닌 경우를 확인하고, 상대 경로 리소스가 어떻게 되는지 관찰한다.

**과제 2 — 정확한 카나리 배포**
`canary-weight`를 10 → 25 → 50 → 100으로 단계적으로 올리며 각 단계에서 100번씩 요청해 실제 분배 비율을 측정한다. 8장의 replica 비율 방식과 정확도를 비교한다. 그다음 `canary-by-header`로 바꿔 특정 헤더가 있을 때만 새 버전으로 가는 것을 확인한다.

**과제 3 — cert-manager로 자체 서명 인증서 발급**
Let's Encrypt 대신 자체 서명 Issuer를 만들어 실습한다.

apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata: { name: selfsigned }
spec: { selfSigned: {} }

Ingress에 애노테이션을 붙여 Secret이 자동 생성되는 것을 확인하고, `kubectl get certificate,certificaterequest`로 발급 과정을 추적한다.

**과제 4 — Gateway API 체험**
Gateway API CRD를 설치하고, NGINX Gateway Fabric 또는 Envoy Gateway로 같은 라우팅을 구현한다. 11.2절의 Ingress와 비교해 어떤 부분이 애노테이션에서 스펙 필드로 옮겨졌는지 정리한다.

## 요약

- **Ingress는 데이터, IngressController는 프로그램**이다. 컨트롤러가 없으면 Ingress를 만들어도 아무 일도 일어나지 않는다. `ADDRESS`가 비어 있는 것이 그 신호다.
- 라우팅은 **호스트 기반**과 **경로 기반**이 있다. `pathType: Prefix`는 세그먼트 단위로 매칭되며, `rewrite-target`은 상대 경로 문제를 일으킬 수 있어 **서브도메인 분리가 더 안전하다.**
- TLS는 컨트롤러에서 종료된다. **cert-manager**를 쓰면 애노테이션 한 줄로 인증서 발급과 갱신이 자동화된다. 와일드카드 인증서나 내부망 서비스에는 DNS-01 챌린지가 필요하다.
- ingress-nginx의 **카나리 애노테이션**은 Pod 수와 무관한 정확한 가중치 분배, 헤더·쿠키 기반 분기를 제공한다. 8장의 replica 비율 방식보다 정밀하다.
- 애노테이션은 **컨트롤러마다 다르고 검증되지 않는다.** **Gateway API**가 이를 표준 스펙 필드로 옮기고, GatewayClass/Gateway/HTTPRoute로 **역할별 권한 분리**를 가능하게 한다. 신규 프로젝트라면 검토할 만하다.
- **서비스 메시는 동서 트래픽을 다룬다.** mTLS, 재시도, 분산 트레이싱을 코드 수정 없이 제공하지만 리소스·지연·복잡도 비용이 있다. **필요한 것이 관측성뿐이면 OpenTelemetry로, 트래픽 분할뿐이면 인그레스 카나리로, 격리뿐이면 NetworkPolicy로 충분하다.**
- 진단은 **ADDRESS 할당 → IngressClass → 컨트롤러 로그 → 백엔드 엔드포인트** 순으로 좁힌다. 503은 엔드포인트 문제, 502는 백엔드 응답 문제, 404는 매칭 문제다.

**다음 장에서는** 3부의 마지막 주제인 스토리지를 다룬다. Pod가 사라져도 데이터가 남게 하는 방법, 그리고 그 뒤에서 동작하는 CSI 아키텍처를 살펴본다.
