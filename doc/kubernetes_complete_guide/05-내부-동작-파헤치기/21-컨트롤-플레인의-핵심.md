# 21장. 컨트롤 플레인의 핵심

> **학습목표**
> - API 서버가 요청을 처리하는 내부 단계를 순서대로 설명할 수 있다.
> - watch가 어떻게 구현되어 있는지(watch cache, resourceVersion) 이해한다.
> - 컨트롤러의 공통 패턴(Informer → 워크큐 → 조정)을 설명할 수 있다.
> - 리더 선출의 동작과 설정을 안다.
> - API 우선순위·공정성(APF)으로 과부하를 제어할 수 있다.
> - 컨트롤 플레인 문제를 메트릭과 로그로 진단할 수 있다.

---

## 들어가며

20장에서 kubelet이 "API 서버를 watch한다"고 여러 번 말했다. 이 장은 그 상대편을 연다.

컨트롤 플레인은 네 컴포넌트로 이루어진다(1.4절).

```
kube-apiserver           모든 요청의 관문이자 유일한 etcd 접근 경로
etcd                     상태 저장소 (22장)
kube-scheduler           배치 결정 (15장)
kube-controller-manager  수십 개 컨트롤러의 집합
cloud-controller-manager 클라우드 연동
```

이 장에서는 API 서버와 컨트롤러 매니저를 다룬다.

## 21.1 kube-apiserver 내부

### 요청 처리 경로

17.1절에서 인증·인가·어드미션을 봤다. 실제 경로는 더 길다.

```
HTTP 요청
    ↓
┌──────────────────────────────────────────────┐
│ ① 필터 체인 (핸들러 래핑)                       │
│    · panic 복구                               │
│    · 요청 타임아웃 (기본 60초)                   │
│    · 인증 (Authentication)                    │
│    · 감사 (Audit) 시작                         │
│    · Impersonation 처리                       │
│    · API Priority & Fairness (큐잉)           │
│    · 인가 (Authorization)                     │
└────────────────────┬─────────────────────────┘
                     ▼
┌──────────────────────────────────────────────┐
│ ② 라우팅                                      │
│    /api/v1/namespaces/default/pods/web        │
│    → 그룹/버전/리소스/이름 파싱                  │
│    → 해당 REST 핸들러로                         │
└────────────────────┬─────────────────────────┘
                     ▼
┌──────────────────────────────────────────────┐
│ ③ 역직렬화 + 버전 변환                          │
│    외부 버전(v1) → 내부 버전(__internal)        │
└────────────────────┬─────────────────────────┘
                     ▼
┌──────────────────────────────────────────────┐
│ ④ 어드미션 체인                                 │
│    Mutating → 스키마 검증 → Validating         │
└────────────────────┬─────────────────────────┘
                     ▼
┌──────────────────────────────────────────────┐
│ ⑤ 스토리지 계층                                 │
│    내부 버전 → 스토리지 버전                     │
│    → protobuf 직렬화                          │
│    → 암호화 (설정 시, 7.4절)                    │
│    → etcd 쓰기                                │
└────────────────────┬─────────────────────────┘
                     ▼
┌──────────────────────────────────────────────┐
│ ⑥ 응답                                        │
│    스토리지 버전 → 내부 → 요청한 외부 버전         │
│    → JSON/protobuf 직렬화                      │
└──────────────────────────────────────────────┘
```

### 버전 변환의 허브 모델

4.1절에서 "같은 리소스가 여러 버전으로 제공된다"고 했다. 구현이 흥미롭다.

```
        v1beta1 ──┐
                  ├──→ __internal ──→ 스토리지 버전(v1) ──→ etcd
        v1 ────────┘
                     (허브)

읽을 때는 반대 방향
```

**모든 버전이 서로 변환되는 것이 아니라, 내부 버전을 허브로 삼는다.** N개 버전이 있을 때 변환 함수가 N²이 아니라 2N개면 된다.

**결과**: `v1beta1`으로 만든 오브젝트를 `v1`으로 읽을 수 있다. 26장에서 CRD에 버저닝을 적용할 때 같은 원리를 쓴다.

```bash
# 스토리지 버전 확인
kubectl get --raw /apis/apps/v1 | jq '.resources[] | select(.name=="deployments") | .storageVersionHash'
```

### 어그리게이션 계층

API 서버가 모든 API를 직접 제공하는 것은 아니다.

```
                    kube-apiserver
                          │
        ┌─────────────────┼──────────────────┐
        ▼                 ▼                  ▼
   내장 API          CRD 기반 API      어그리게이션 API
   /api/v1          apiextensions로    별도 서버로 프록시
   /apis/apps/v1    등록된 CRD         metrics.k8s.io 등
```

```bash
kubectl get apiservices | grep -v Local
```
```
NAME                     SERVICE                      AVAILABLE
v1beta1.metrics.k8s.io   kube-system/metrics-server   True
```

**`metrics.k8s.io`는 내장 API가 아니다.** metrics-server가 별도 서버로 구현하고, API 서버가 그쪽으로 프록시한다(16.1절). 28장에서 직접 만든다.

### watch의 구현

**모든 컨트롤러가 watch에 의존한다**(4.5절). 수천 개의 watch 연결을 어떻게 감당할까?

```
etcd
  │ (etcd watch, 리소스 종류마다 하나)
  ▼
┌────────────────────────────────────┐
│  watch cache (API 서버 메모리)       │
│  · 최근 이벤트를 순환 버퍼에 보관       │
│  · 현재 오브젝트 상태를 저장           │
└────────────────┬───────────────────┘
                 │ (fan-out)
     ┌───────────┼───────────┬──────────┐
     ▼           ▼           ▼          ▼
 kubelet1    kubelet2   controller   Informer
```

**핵심**: API 서버는 etcd에 **리소스 종류마다 watch를 하나만** 건다. 클라이언트 수천 개가 붙어도 etcd 부하는 늘지 않는다.

**`resourceVersion` 파라미터의 동작**

```
watch?resourceVersion=""       → 현재 상태를 모두 보낸 뒤(bookmark) 이후 변경
watch?resourceVersion="0"      → 캐시의 아무 시점에서나 시작 (가장 빠름)
watch?resourceVersion="12345"  → 그 시점 이후의 변경만
```

**연결이 끊겼다가 재접속할 때** 마지막 resourceVersion으로 이어받는다. 그런데 캐시의 순환 버퍼에서 밀려났다면?

```
410 Gone: too old resource version
```

클라이언트는 **전체 목록을 다시 받아(relist)** 재시작해야 한다. Informer가 이것을 자동으로 처리한다(25장).

**Bookmark 이벤트**가 이 문제를 완화한다.

```bash
curl -s "localhost:8001/api/v1/pods?watch=true&allowWatchBookmarks=true" | jq -c 'select(.type=="BOOKMARK")'
```

변경이 없어도 주기적으로 "지금 resourceVersion은 여기까지"라고 알려 준다. 클라이언트가 최신 위치를 유지하므로 410이 줄어든다.

### 페이지네이션과 목록 부하

```bash
kubectl get pods -A --chunk-size=500
```

**대규모 클러스터에서 `list`는 위험하다.** Pod가 5만 개인 클러스터에서 전체 목록을 요청하면 수백 MB가 직렬화되어 **API 서버 메모리가 폭증한다.**

**Streaming List**(v1.32+)는 이것을 개선한다. 전체를 메모리에 모으지 않고 스트리밍한다.

## 21.2 API 우선순위와 공정성 (APF)

### 문제

과거에는 `--max-requests-inflight` 하나로 전체 동시 요청 수만 제한했다. 그래서 잘못 만든 컨트롤러 하나가 요청을 폭주시키면 **kubelet의 노드 상태 보고까지 밀려나** 클러스터가 무너졌다.

### 해결

APF는 요청을 **분류하고 큐를 나눈다.**

```
요청 → FlowSchema(분류) → PriorityLevelConfiguration(큐 + 동시성 배분)
```

```bash
kubectl get flowschemas
kubectl get prioritylevelconfigurations
```

```
NAME                          PRIORITYLEVEL     MATCHINGPRECEDENCE
exempt                        exempt            1
system-leader-election        leader-election   100
node-high                     node-high         400
system-node-high              node-high         400
kube-system-service-accounts  workload-high     900
service-accounts              workload-low      9000
global-default                global-default    9900
catch-all                     catch-all         10000
```

**우선순위 레벨**

| 레벨 | 대상 |
|---|---|
| `exempt` | system:masters — 제한 없음 |
| `system` | 시스템 컴포넌트 |
| `node-high` | kubelet의 노드 상태 보고 ★ |
| `leader-election` | 리더 선출 (기아 방지) |
| `workload-high` | kube-system의 컨트롤러 |
| `workload-low` | 일반 ServiceAccount |
| `global-default` | 나머지 |
| `catch-all` | 분류되지 않은 것 |

**핵심 효과**: 어떤 워크로드가 요청을 폭주시켜도 **`node-high`와 `leader-election`의 몫은 보장된다.** 클러스터가 무너지지 않는다.

**커스텀 FlowSchema**

```yaml
apiVersion: flowcontrol.apiserver.k8s.io/v1
kind: FlowSchema
metadata:
  name: limit-noisy-controller
spec:
  priorityLevelConfiguration:
    name: workload-low
  matchingPrecedence: 500
  distinguisherMethod:
    type: ByUser
  rules:
    - subjects:
        - kind: ServiceAccount
          serviceAccount:
            name: noisy-operator
            namespace: default
      resourceRules:
        - verbs: ["*"]
          apiGroups: ["*"]
          resources: ["*"]
          clusterScope: true
          namespaces: ["*"]
```

**모니터링**

```bash
kubectl get --raw /metrics | grep -E 'apiserver_flowcontrol_(rejected|current_inqueue)' | head
```

`apiserver_flowcontrol_rejected_requests_total`이 증가하면 어떤 클라이언트가 과도한 요청을 보내고 있다는 뜻이다. **429 응답**을 받은 클라이언트는 백오프해야 한다.

## 21.3 컨트롤러의 공통 패턴

### 조정 루프의 실제 구현

1장에서 "관찰-비교-조치"라고 했다. 실제 구현은 이렇다.

```
   API 서버
      │ watch + list
      ▼
┌──────────────────────────────────────────┐
│  Informer                                │
│    ┌────────────┐                        │
│    │ Reflector  │ list & watch → DeltaFIFO│
│    └─────┬──────┘                        │
│          ▼                               │
│    ┌────────────┐   ┌──────────────┐     │
│    │ Controller │ → │ Indexer/Store│     │  ← 로컬 캐시
│    └─────┬──────┘   └──────────────┘     │
│          │ 이벤트 핸들러                   │
└──────────┼───────────────────────────────┘
           ▼
    ┌─────────────┐
    │  워크큐       │  ← 키(namespace/name)만 넣는다
    │  (rate limit)│
    └──────┬──────┘
           ▼
    ┌─────────────────────────────┐
    │  워커 고루틴 (N개)             │
    │    key = queue.Get()         │
    │    obj = lister.Get(key)     │  ← 캐시에서 읽는다 (API 호출 아님)
    │    reconcile(obj)            │
    │    if err: queue.AddRateLimited(key)  │
    └─────────────────────────────┘
```

### 왜 이 구조인가

**① Informer의 로컬 캐시**
컨트롤러가 오브젝트를 읽을 때마다 API 서버를 호출하면 부하가 감당되지 않는다. Informer는 watch로 받은 상태를 **메모리에 유지**하고, 읽기는 캐시에서 처리한다.

**② 워크큐에 키만 넣는 이유**
오브젝트 자체를 넣으면 오래된 데이터로 작업할 수 있다. **키만 넣고 처리 시점에 캐시에서 최신 상태를 읽는다.**

**③ 중복 제거**
같은 키가 이미 큐에 있으면 추가하지 않는다. 1초에 100번 변경돼도 조정은 한 번만 일어난다.

**④ 레이트 리미터**
실패한 항목은 지수 백오프로 재시도한다. 영구 실패하는 항목이 CPU를 태우지 않는다.

```go
// 기본 레이트 리미터: 5ms에서 시작해 1000초까지
workqueue.DefaultControllerRateLimiter()
```

**이 패턴을 25~27장에서 직접 구현한다.**

### 조정 함수의 원칙

```go
func (c *Controller) reconcile(key string) error {
    // ① 현재 상태를 캐시에서 읽는다
    obj, err := c.lister.Get(key)
    if errors.IsNotFound(err) {
        return nil    // 삭제됨 — 정리는 GC가 한다
    }

    // ② 원하는 상태와 비교

    // ③ 차이를 줄이는 조치

    return nil
}
```

**반드시 지켜야 할 것들**

| 원칙 | 이유 |
|---|---|
| **멱등성** | 같은 조정이 여러 번 실행될 수 있다. 두 번 해도 결과가 같아야 한다 |
| **레벨 트리거** | "무엇이 바뀌었나"가 아니라 **"지금 상태가 어떤가"** 로 판단한다 |
| **이벤트에 의존하지 않기** | 이벤트는 유실될 수 있다. 주기적 재동기화가 안전망이다 |
| **API 호출 최소화** | 읽기는 캐시에서. 쓰기는 정말 바뀔 때만 |
| **status만 쓰기** | spec은 사용자의 것이다 (4.2절) |

> **엣지 트리거 vs 레벨 트리거**
>
> **엣지 트리거**는 "Pod가 삭제됨"이라는 **이벤트**에 반응한다. 이벤트를 놓치면 영영 처리하지 못한다.
>
> **레벨 트리거**는 "지금 Pod가 2개인데 3개여야 한다"는 **상태**를 본다. 이벤트를 놓쳐도 다음 조정에서 바로잡힌다.
>
> **쿠버네티스의 모든 컨트롤러는 레벨 트리거다.** 이것이 분산 시스템에서 견고성의 원천이다.

**모든 컨트롤러가 같은 프로세스에서 각자의 고루틴으로 돈다.** 하나가 느려져도 다른 것은 계속 동작하지만, 프로세스가 죽으면 모두 멈춘다.

### 가비지 컬렉터 상세

4.2절에서 본 `ownerReferences` 기반 삭제의 구현이다.

```
① 모든 리소스의 ownerReferences를 추적해 **의존 그래프**를 만든다
② 소유자가 삭제되면 자식들을 큐에 넣는다
③ 삭제 방식에 따라:
   · Background: 소유자를 먼저 지우고 자식은 비동기로
   · Foreground: 소유자에 finalizer를 붙이고 자식을 먼저 지운다
   · Orphan: ownerReferences만 제거하고 자식은 남긴다
```

**고아 감지**: 소유자가 이미 없는데 자식이 남아 있으면 GC가 정리한다.

```bash
# GC 관련 메트릭
kubectl get --raw /metrics | grep garbage_collector | head
```

## 21.4 리더 선출

### 왜 필요한가

컨트롤 플레인을 HA로 구성하면 controller-manager와 scheduler가 3개씩 돈다. **모두가 동시에 조정하면 충돌한다.** ReplicaSet 컨트롤러 3개가 각자 "1개 부족하네"라며 Pod를 만들면 3개가 생긴다.

**해결**: 한 번에 하나만 활성(active)이고 나머지는 대기(standby)한다.

```yaml
  holderIdentity: k8s-guide-control-plane_d4e5f6
  leaseDurationSeconds: 15
  acquireTime: "2026-09-01T10:00:00Z"
  renewTime: "2026-09-01T10:23:45Z"
  leaseTransitions: 3
```

**동작**

```
리더:
  · renewDeadline(10초)마다 renewTime 갱신
  · 갱신 실패 시 즉시 리더십 포기하고 종료

대기자:
  · retryPeriod(2초)마다 Lease 확인
  · renewTime + leaseDurationSeconds(15초)가 지났으면
    → 자신을 holderIdentity로 설정 시도 (낙관적 동시성, 4.2절)
    → 성공하면 리더가 된다
```

**낙관적 동시성 제어**(4.2절의 `resourceVersion`)가 여기서 쓰인다. 여러 대기자가 동시에 시도해도 하나만 성공한다.

**설정**

```yaml
--leader-elect=true
--leader-elect-lease-duration=15s
--leader-elect-renew-deadline=10s
--leader-elect-retry-period=2s
```

> **⚠️ 리더 전환 중의 공백**
> 리더가 죽으면 최대 15초 동안 아무도 조정하지 않는다. **이것은 정상이다.** 레벨 트리거 방식이므로 새 리더가 현재 상태를 보고 이어서 처리한다.
>
> 값을 너무 짧게 하면 일시적 네트워크 지연에도 리더가 바뀌어 오히려 불안정해진다. `leaseTransitions`가 자주 증가하면 이 문제를 의심한다.

**직접 만든 오퍼레이터에도 필요하다.** 27장에서 controller-runtime의 리더 선출을 설정한다.

## 21.5 cloud-controller-manager

### 왜 분리했는가

클라우드 연동 코드가 쿠버네티스 본체에 있으면 CSI 이전의 스토리지와 같은 문제가 생긴다(12.4절). 그래서 별도 컴포넌트로 분리했다.

**포함된 컨트롤러**

| 컨트롤러 | 하는 일 |
|---|---|
| `node` | 클라우드 API로 노드 정보 보강(인스턴스 타입, AZ 라벨), 삭제된 인스턴스의 Node 오브젝트 제거 |
| `route` | Pod CIDR을 위한 클라우드 라우트 설정 |
| `service` | LoadBalancer 타입 Service → 실제 클라우드 LB 생성 (9.2절) |

**노드 초기화 흐름**

```
① kubelet이 노드를 등록
   → 테인트 부착: node.cloudprovider.kubernetes.io/uninitialized:NoSchedule
   → 이 테인트 때문에 Pod가 스케줄되지 않는다
        ↓
② CCM이 클라우드 API 조회
   → topology.kubernetes.io/zone, region 라벨 추가
   → node.kubernetes.io/instance-type 추가
   → ProviderID 설정
        ↓
③ 테인트 제거 → 스케줄링 가능
```

**15.2절에서 본 내장 노드 라벨들이 이때 붙는다.**

### 핵심 메트릭

```bash
kubectl get --raw /metrics > /tmp/apiserver-metrics.txt
```

| 메트릭 | 의미 | 경보 기준 |
|---|---|---|
| `apiserver_request_duration_seconds` | 요청 지연 | P99 > 1초 |
| `apiserver_request_total{code=~"5.."}` | 서버 에러 | 비율 > 1% |
| `apiserver_current_inflight_requests` | 처리 중 요청 | 한도에 근접 |
| `apiserver_flowcontrol_rejected_requests_total` | APF 거부 | 증가 중 |
| `etcd_request_duration_seconds` | etcd 지연 ★ | P99 > 500ms |
| `apiserver_storage_objects` | 리소스별 오브젝트 수 | 급증 |
| `workqueue_depth` | 컨트롤러 큐 깊이 | 계속 증가 |
| `workqueue_queue_duration_seconds` | 큐 대기 시간 | 증가 |
| `leader_election_master_status` | 리더 여부 (1/0) | - |
| `rest_client_requests_total{code="429"}` | 레이트 리밋 | 증가 |

**`etcd_request_duration_seconds`가 가장 중요한 선행 지표다.** etcd가 느려지면 모든 것이 느려진다(22장).

### 증상별 진단

| 증상 | 원인 | 확인 |
|---|---|---|
| `kubectl`이 전반적으로 느림 | etcd 지연, API 서버 과부하 | `etcd_request_duration`, `inflight_requests` |
| `429 Too Many Requests` | APF 제한 | `flowcontrol_rejected_requests_total`, FlowSchema |
| `etcdserver: request timed out` | etcd 문제 | 22장 |
| 특정 컨트롤러만 반응 없음 | 리더 선출 문제, 워크큐 포화 | `leader_election_master_status`, `workqueue_depth` |
| `Unable to connect to the server` | API 서버 다운, 인증서 만료 | static Pod 로그, 인증서 만료일 |
| `x509: certificate has expired` | 인증서 만료 | `kubeadm certs check-expiration` |
| 오브젝트가 계속 늘어남 | 컨트롤러 버그, 파이널라이저 | `apiserver_storage_objects` |

## 실습 과제

**과제 1 — 버전 변환 확인**
CRD를 두 버전(v1alpha1, v1beta1)으로 정의하고, 한 버전으로 만든 오브젝트를 다른 버전으로 조회해 변환이 일어나는 것을 확인한다. (26장의 예습)

**과제 2 — 410 Gone 재현**
watch를 오래된 resourceVersion으로 시작해 `410 Gone`을 받아 본다.
```bash
curl -s "localhost:8001/api/v1/pods?watch=true&resourceVersion=1" | head -3
```
Informer가 이 상황을 어떻게 처리하는지 조사한다.

**과제 3 — 워크큐 메트릭 관찰**
Deployment를 대량으로 생성·삭제하면서 `workqueue_depth`와 `workqueue_queue_duration_seconds`가 어떻게 변하는지 기록한다. 컨트롤러가 부하를 어떻게 흡수하는지 관찰한다.

**과제 4 — 커스텀 FlowSchema**
특정 ServiceAccount의 요청을 `workload-low`로 분류하는 FlowSchema를 만들고, 그 SA로 대량 요청을 보내 다른 요청이 영향받지 않는 것을 확인한다.

**과제 5 — 레벨 트리거 검증**
컨트롤러 매니저를 30초간 정지시킨 뒤 그동안 Pod를 여러 개 삭제한다. 컨트롤러가 돌아왔을 때 **이벤트를 놓쳤음에도** 올바른 개수로 복구되는 것을 확인한다. 이것이 레벨 트리거의 힘이다.

## 요약

- API 서버의 요청 경로는 **필터 체인(인증·감사·APF·인가) → 라우팅 → 역직렬화/버전 변환 → 어드미션 → 스토리지 → 응답**이다.
- 버전 변환은 **내부 버전을 허브로 삼는다.** N개 버전에 2N개 변환 함수만 있으면 된다.
- **watch cache**가 etcd watch 하나를 수천 클라이언트에 fan-out한다. 오래된 `resourceVersion`으로 재접속하면 `410 Gone`이 나고 클라이언트는 relist해야 한다. **Bookmark 이벤트**가 이를 완화한다.
- **APF**는 요청을 FlowSchema로 분류해 우선순위별 큐에 넣는다. 어떤 워크로드가 폭주해도 **kubelet의 노드 보고와 리더 선출의 몫은 보장된다.**
- 모든 컨트롤러는 **Informer(로컬 캐시) → 워크큐(키만, 중복 제거, 레이트 리밋) → 조정 함수** 패턴을 따른다. 조정은 **멱등**해야 하고 **레벨 트리거**여야 한다.
- **레벨 트리거**이기 때문에 이벤트를 놓쳐도 다음 조정에서 바로잡힌다. 이것이 쿠버네티스 견고성의 원천이다.
- **리더 선출**은 Lease 오브젝트와 낙관적 동시성 제어로 구현된다. 리더가 죽으면 최대 15초의 공백이 있지만, 레벨 트리거이므로 문제되지 않는다.
- **cloud-controller-manager**는 노드에 클라우드 정보를 보강하고 LoadBalancer Service를 실제 LB로 만든다. 초기화 전에는 `uninitialized` 테인트가 스케줄링을 막는다.
- 진단의 핵심 지표는 **`etcd_request_duration_seconds`** 다. etcd가 느려지면 모든 것이 느려진다. **kubeadm 클러스터의 인증서는 1년 만료**이므로 정기 업그레이드가 가용성 문제이기도 하다.

**다음 장에서는** 그 etcd를 연다. 모든 상태가 저장되는 곳이자, 클러스터에서 가장 취약한 지점이다.
