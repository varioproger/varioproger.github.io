# 15장. 고급 스케줄링

> **학습목표**
> - 스케줄러의 필터링·스코어링 두 단계를 설명할 수 있다.
> - nodeSelector, 노드 어피니티, Pod 어피니티/안티어피니티를 구분해 사용할 수 있다.
> - 테인트와 톨러레이션으로 노드를 전용화할 수 있다.
> - 토폴로지 분산 제약으로 AZ 간 균등 배치를 구현할 수 있다.
> - PriorityClass와 선점의 동작을 이해하고 안전하게 설계할 수 있다.

---

## 들어가며

14장에서 스케줄러가 requests를 본다고 했다. 하지만 실무의 요구는 그보다 복잡하다.

- "이 워크로드는 GPU 노드에만"
- "같은 서비스의 Pod들은 서로 다른 AZ에"
- "캐시 Pod는 앱 Pod와 같은 노드에"
- "이 노드는 특정 팀 전용"
- "긴급 배치는 다른 Pod를 밀어내고라도 실행"

이 장은 이런 요구를 표현하는 도구들을 다룬다.

## 15.1 스케줄러의 동작

### 두 단계

kube-scheduler는 `spec.nodeName`이 비어 있는 Pod를 발견하면 두 단계를 거친다.

```
┌─────────────────────────────────────────────────┐
│  ① 필터링 (Filtering / Predicates)               │
│     "이 노드에 배치 가능한가?" — 예/아니오          │
│                                                 │
│     전체 노드 100개                               │
│         ↓ NodeResourcesFit (requests 만족?)      │
│         ↓ NodeAffinity                          │
│         ↓ TaintToleration                       │
│         ↓ PodTopologySpread                     │
│         ↓ VolumeBinding (12장)                   │
│         ↓ NodePorts                             │
│     가능한 노드 12개                              │
└─────────────────────────────────────────────────┘
                      ↓
┌─────────────────────────────────────────────────┐
│  ② 스코어링 (Scoring / Priorities)               │
│     "어느 노드가 더 좋은가?" — 0~100점            │
│                                                 │
│         ↓ NodeResourcesBalancedAllocation       │
│         ↓ ImageLocality (이미지가 이미 있나)       │
│         ↓ InterPodAffinity                      │
│         ↓ TaintToleration (PreferNoSchedule)    │
│         ↓ PodTopologySpread                     │
│     최고 점수 노드 선택 (동점이면 랜덤)             │
└─────────────────────────────────────────────────┘
                      ↓
              ③ 바인딩: spec.nodeName 설정
```

**필터링에서 아무 노드도 남지 않으면** Pod는 `Pending`이 되고 이벤트에 이유가 기록된다.

```bash
kubectl describe pod <pending-pod>
```
```
Warning  FailedScheduling  0/5 nodes are available:
  2 Insufficient cpu,
  1 node(s) had untolerated taint {gpu: true},
  2 node(s) didn't match Pod's node affinity/selector.
```

**이 메시지를 읽는 법이 진단의 핵심이다.** 각 숫자가 어떤 이유로 몇 개 노드가 제외됐는지 알려 준다.

### 성능 최적화

노드가 수천 개인 클러스터에서 모든 노드를 평가하면 느리다. 스케줄러는 **`percentageOfNodesToScore`** 만큼만 검사한다.

```yaml
# KubeSchedulerConfiguration
apiVersion: kubescheduler.config.k8s.io/v1
kind: KubeSchedulerConfiguration
percentageOfNodesToScore: 50      # 기본: 노드 수에 따라 자동(50~100%)
```

즉 **최적의 노드를 항상 찾는 것이 아니라, 충분히 좋은 노드를 빠르게 찾는다.**

## 15.2 nodeSelector와 노드 어피니티

### nodeSelector — 가장 단순한 방법

```yaml
spec:
  nodeSelector:
    disktype: ssd
    kubernetes.io/os: linux
```

노드에 라벨을 붙인다.

```bash
kubectl label node k8s-guide-worker disktype=ssd
kubectl get nodes -L disktype
```

**모든 조건이 AND**이고, **정확히 일치**해야 한다. 표현력이 낮아 실무에서는 어피니티를 더 많이 쓴다.

### 내장 노드 라벨

클라우드 환경에서 자동으로 붙는 라벨들이 있다.

```bash
kubectl get node <node> --show-labels
```

| 라벨 | 예시 |
|---|---|
| `kubernetes.io/hostname` | `node-1` |
| `kubernetes.io/os` | `linux` |
| `kubernetes.io/arch` | `amd64`, `arm64` |
| `topology.kubernetes.io/region` | `ap-northeast-2` |
| `topology.kubernetes.io/zone` | `ap-northeast-2a` |
| `node.kubernetes.io/instance-type` | `m5.xlarge` |
| `node-role.kubernetes.io/control-plane` | `""` |

**`topology.kubernetes.io/zone`이 특히 중요하다.** 15.5절의 토폴로지 분산과 12장의 볼륨 어피니티가 이 라벨을 쓴다.

### 노드 어피니티

nodeSelector의 확장판이다. 두 종류가 있다.

```yaml
spec:
  affinity:
    nodeAffinity:
      # ① 필수 조건 — 만족하지 않으면 스케줄 안 됨 (필터링 단계)
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:            # ← term 안의 조건들은 AND
              - key: kubernetes.io/arch
                operator: In
                values: [amd64, arm64]
              - key: node.kubernetes.io/instance-type
                operator: NotIn
                values: [t3.micro, t3.small]
          - matchExpressions:            # ← term끼리는 OR
              - key: special-hardware
                operator: Exists

      # ② 선호 조건 — 만족하면 좋지만 아니어도 됨 (스코어링 단계)
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 80                     # 1~100
          preference:
            matchExpressions:
              - key: disktype
                operator: In
                values: [ssd]
        - weight: 20
          preference:
            matchExpressions:
              - key: topology.kubernetes.io/zone
                operator: In
                values: [ap-northeast-2a]
```

**연산자**

| operator | 의미 |
|---|---|
| `In` | 값 목록에 포함 |
| `NotIn` | 포함되지 않음 |
| `Exists` | 라벨 키가 존재 |
| `DoesNotExist` | 키가 없음 |
| `Gt` / `Lt` | 정수 비교 (값이 숫자여야 함) |

**AND / OR 규칙이 헷갈리기 쉽다.**
```
nodeSelectorTerms:     ← 이 리스트의 항목들은 OR
  - matchExpressions:  ← 이 안의 조건들은 AND
      - 조건1
      - 조건2
  - matchExpressions:
      - 조건3
      
결과: (조건1 AND 조건2) OR (조건3)
```

### IgnoredDuringExecution의 의미

이름이 길지만 의미는 단순하다. **"스케줄링 시점에만 검사하고, 실행 중에는 무시한다."**

노드의 라벨이 나중에 바뀌어도 이미 실행 중인 Pod는 쫓겨나지 않는다.

`RequiredDuringExecution`(라벨이 바뀌면 축출) 기능은 오랫동안 계획만 있고 구현되지 않았다. 필요하다면 **Descheduler**라는 별도 컴포넌트를 쓴다.

## 15.3 Pod 어피니티와 안티어피니티

노드의 속성이 아니라 **다른 Pod의 위치**를 기준으로 배치한다.

```yaml
spec:
  affinity:
    # ① 같이 두기
    podAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        - labelSelector:
            matchLabels:
              app: cache
          topologyKey: kubernetes.io/hostname      # ★ 같은 "노드"에

    # ② 떨어뜨리기
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        - labelSelector:
            matchLabels:
              app: web
          topologyKey: kubernetes.io/hostname      # ★ 다른 노드에
```

### topologyKey가 핵심이다

"같은 곳"의 정의를 결정한다.

| topologyKey | "같은 곳"의 의미 |
|---|---|
| `kubernetes.io/hostname` | 같은 노드 |
| `topology.kubernetes.io/zone` | 같은 가용 영역 |
| `topology.kubernetes.io/region` | 같은 리전 |
| 커스텀 라벨 (`rack`, `datacenter`) | 직접 정의한 장애 도메인 |

```
podAntiAffinity + topologyKey: kubernetes.io/hostname
  → 한 노드에 이 앱의 Pod가 하나씩만

podAntiAffinity + topologyKey: topology.kubernetes.io/zone
  → 한 AZ에 이 앱의 Pod가 하나씩만  (매우 강한 제약!)
```

### 전형적 사용 예

**고가용성 — 노드 분산 (선호)**

```yaml
podAntiAffinity:
  preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 100
      podAffinityTerm:
        labelSelector:
          matchLabels:
            app: web
        topologyKey: kubernetes.io/hostname
```

`preferred`를 쓰는 이유: `required`로 하면 노드 수보다 많은 replica를 만들 수 없다. replicas 5, 노드 3개면 2개가 영원히 Pending이다.

**엄격한 분산 (필수)**

```yaml
podAntiAffinity:
  requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchExpressions:
          - key: app
            operator: In
            values: [database]
      topologyKey: kubernetes.io/hostname
```

데이터베이스 복제본이 같은 노드에 있으면 노드 하나가 죽을 때 데이터를 잃는다. 이 경우 `required`가 맞다.

**지역성 — 캐시와 앱을 같은 노드에**

```yaml
podAffinity:
  preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 100
      podAffinityTerm:
        labelSelector:
          matchLabels:
            app: redis-cache
        topologyKey: kubernetes.io/hostname
```

네트워크 홉을 줄여 지연을 낮춘다.

**같은 AZ에 두기 — 데이터 전송 비용 절감**

```yaml
podAffinity:
  preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 100
      podAffinityTerm:
        labelSelector:
          matchLabels:
            app: backend
        topologyKey: topology.kubernetes.io/zone
```

AZ 간 트래픽은 유료다. 관련 서비스를 같은 AZ에 모으면 비용이 줄어든다.

> **⚠️ Pod 어피니티는 계산 비용이 크다**
>
> 노드 어피니티는 노드 라벨만 보면 되지만, Pod 어피니티는 **모든 노드에 대해 그 노드의 모든 Pod를 검사**해야 한다. 노드가 수백 개면 스케줄링이 눈에 띄게 느려진다.
>
> 쿠버네티스 문서도 "수백 노드 이상의 클러스터에서는 주의하라"고 경고한다.
>
> **단순 분산이 목적이라면 다음 절의 `topologySpreadConstraints`가 훨씬 효율적이다.**

**`namespaceSelector`** 로 다른 네임스페이스의 Pod를 참조할 수도 있다.

```yaml
podAffinity:
  requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchLabels: { app: shared-cache }
      namespaceSelector:
        matchLabels: { team: platform }
      topologyKey: kubernetes.io/hostname
```

## 15.4 테인트와 톨러레이션

### 방향이 반대다

어피니티가 **Pod가 노드를 고르는** 것이라면, 테인트는 **노드가 Pod를 거부하는** 것이다.

```
테인트(Taint)      : 노드에 붙인다. "나는 이런 Pod만 받는다"
톨러레이션(Toleration): Pod에 붙인다. "나는 그 조건을 견딜 수 있다"
```

**테인트가 있는 노드는 톨러레이션이 없는 Pod를 받지 않는다.**

### 테인트 관리

```bash
# 추가
kubectl taint nodes node-1 gpu=true:NoSchedule

# 제거 (끝에 하이픈)
kubectl taint nodes node-1 gpu=true:NoSchedule-

# 확인
kubectl describe node node-1 | grep -A3 Taints
```

**effect 세 가지**

| effect | 동작 |
|---|---|
| `NoSchedule` | 톨러레이션 없는 Pod는 **새로 배치되지 않음**. 기존 Pod는 유지 |
| `PreferNoSchedule` | 가능하면 피하지만, 다른 곳이 없으면 배치 (스코어링 단계) |
| `NoExecute` | **기존 Pod도 축출**한다 |

### 톨러레이션

```yaml
spec:
  tolerations:
    # 정확한 키-값 매칭
    - key: gpu
      operator: Equal
      value: "true"
      effect: NoSchedule

    # 키만 있으면 됨 (값 무관)
    - key: dedicated
      operator: Exists
      effect: NoSchedule

    # 모든 테인트 감내 (DaemonSet에서 흔함)
    - operator: Exists

    # NoExecute + 유예 시간
    - key: node.kubernetes.io/unreachable
      operator: Exists
      effect: NoExecute
      tolerationSeconds: 300      # 5분 후 축출
```

> **⚠️ 톨러레이션은 "허가"이지 "지시"가 아니다**
>
> GPU 노드에 테인트를 걸고 GPU Pod에 톨러레이션을 주면, **그 Pod가 GPU 노드에 갈 수 있게** 된다. 하지만 **일반 노드에도 갈 수 있다.**
>
> ```yaml
> # ❌ 이것만으로는 부족하다
> tolerations:
>   - key: gpu
>     operator: Exists
> ```
>
> **반드시 어피니티와 함께 써야 한다.**
> ```yaml
> tolerations:
>   - key: gpu
>     operator: Exists
> affinity:
>   nodeAffinity:
>     requiredDuringSchedulingIgnoredDuringExecution:
>       nodeSelectorTerms:
>         - matchExpressions:
>             - key: gpu
>               operator: Exists
> ```
>
> **테인트 = 다른 Pod를 막는다 / 어피니티 = 이 Pod를 유도한다.** 둘 다 필요하다.

### 내장 테인트

쿠버네티스가 자동으로 붙이는 테인트들이 있다.

| 테인트 | 언제 |
|---|---|
| `node.kubernetes.io/not-ready` | 노드가 Ready가 아님 |
| `node.kubernetes.io/unreachable` | 노드 컨트롤러가 노드에 도달 못 함 |
| `node.kubernetes.io/memory-pressure` | 메모리 압박 (14.4절) |
| `node.kubernetes.io/disk-pressure` | 디스크 압박 |
| `node.kubernetes.io/pid-pressure` | PID 고갈 |
| `node.kubernetes.io/unschedulable` | `kubectl cordon` 실행됨 |
| `node.cloudprovider.kubernetes.io/uninitialized` | CCM 초기화 대기 |
| `node-role.kubernetes.io/control-plane` | 컨트롤 플레인 노드 |

**모든 Pod에 자동으로 추가되는 톨러레이션**이 있다.

```yaml
tolerations:
  - key: node.kubernetes.io/not-ready
    operator: Exists
    effect: NoExecute
    tolerationSeconds: 300
  - key: node.kubernetes.io/unreachable
    operator: Exists
    effect: NoExecute
    tolerationSeconds: 300
```

**이것이 노드 장애 시 Pod가 5분 후에 옮겨지는 이유다.** 일시적 네트워크 문제로 Pod를 성급히 옮기지 않기 위한 설계다.

빠른 페일오버가 필요하면 이 값을 줄인다.

```yaml
tolerations:
  - key: node.kubernetes.io/unreachable
    operator: Exists
    effect: NoExecute
    tolerationSeconds: 30
```

**단, 짧게 하면 일시적 문제에도 Pod가 대량 이동해 오히려 불안정해질 수 있다.**

### 전용 노드 풀 구성

실무에서 가장 흔한 패턴이다.

```bash
# ① 노드에 테인트와 라벨을 함께
kubectl taint nodes gpu-node-1 workload=gpu:NoSchedule
kubectl label nodes gpu-node-1 workload=gpu
```

```yaml
# ② Pod에 톨러레이션 + 어피니티
spec:
  tolerations:
    - key: workload
      operator: Equal
      value: gpu
      effect: NoSchedule
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: workload
                operator: In
                values: [gpu]
```

13장의 멀티테넌시에서 팀별 노드 분리도 같은 패턴이다.

## 15.5 토폴로지 분산 제약

### Pod 안티어피니티의 한계

안티어피니티로는 "**균등하게**" 분산시킬 수 없다. `required`는 전부 다르게, `preferred`는 애매하게 분산될 뿐이다.

```
AZ-a: 4개, AZ-b: 1개, AZ-c: 1개    ← preferred로도 이럴 수 있다
```

**`topologySpreadConstraints`** 는 편차를 명시적으로 제어한다.

```yaml
spec:
  topologySpreadConstraints:
    - maxSkew: 1                                  # 최대 편차
      topologyKey: topology.kubernetes.io/zone
      whenUnsatisfiable: DoNotSchedule            # 또는 ScheduleAnyway
      labelSelector:
        matchLabels:
          app: web
      # 선택적 필드들
      minDomains: 3                               # 최소 도메인 수 (v1.30 GA)
      nodeAffinityPolicy: Honor                   # 어피니티 필터를 계산에 반영
      nodeTaintsPolicy: Honor
      matchLabelKeys: [pod-template-hash]         # ★ 롤아웃 시 중요
```

### maxSkew의 의미

**가장 많은 도메인의 Pod 수 − 가장 적은 도메인의 Pod 수 ≤ maxSkew**

```
maxSkew: 1, replicas: 6, AZ 3개
  → 2, 2, 2  ✓  (편차 0)
  → 3, 2, 1  ✗  (편차 2)

maxSkew: 1, replicas: 4, AZ 3개
  → 2, 1, 1  ✓  (편차 1)
```

### whenUnsatisfiable

| 값 | 동작 |
|---|---|
| `DoNotSchedule` | 제약을 만족할 수 없으면 **Pending** (필터링) |
| `ScheduleAnyway` | 최선을 다하되 안 되면 그냥 배치 (스코어링) |

**프로덕션 권장**: 노드/AZ 수준 분산은 `ScheduleAnyway`가 안전하다. `DoNotSchedule`은 AZ 하나가 장애일 때 새 Pod가 아예 안 뜨는 상황을 만들 수 있다.

### 다중 제약 조합

```yaml
topologySpreadConstraints:
  # AZ 간 균등 (엄격)
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels: { app: web }

  # 노드 간 균등 (느슨)
  - maxSkew: 2
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: ScheduleAnyway
    labelSelector:
      matchLabels: { app: web }
```

**두 제약이 모두 만족되어야 한다(AND).**

### matchLabelKeys — 롤아웃 시의 함정

```yaml
    matchLabelKeys: [pod-template-hash]
```

이 필드가 없으면 롤링 업데이트 중 문제가 생긴다.

```
현재: v1 Pod 3개 (AZ-a: 1, AZ-b: 1, AZ-c: 1)
새 v2 Pod를 만들려는데...
  → labelSelector가 app=web이므로 v1 Pod들도 계산에 포함
  → "이미 균등하니 어디든 괜찮다" 또는 잘못된 계산
```

`matchLabelKeys: [pod-template-hash]`를 주면 **같은 리비전의 Pod끼리만** 계산한다. v2는 v2끼리 균등하게 분산된다.

### 클러스터 기본 제약

모든 Pod에 자동 적용할 수도 있다.

```yaml
# KubeSchedulerConfiguration
profiles:
  - pluginConfig:
      - name: PodTopologySpread
        args:
          defaultConstraints:
            - maxSkew: 3
              topologyKey: topology.kubernetes.io/zone
              whenUnsatisfiable: ScheduleAnyway
          defaultingType: List
```

## 15.6 PriorityClass와 선점

### 우선순위 정의

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high-priority
value: 1000000
globalDefault: false
preemptionPolicy: PreemptLowerPriority     # 또는 Never
description: "결제 등 미션 크리티컬 워크로드"
---
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: low-priority
value: 100
globalDefault: false
preemptionPolicy: Never                     # 선점하지 않음
description: "배치, 재시도 가능한 작업"
```

```yaml
# Pod에 적용
spec:
  priorityClassName: high-priority
```

**내장 PriorityClass**
```bash
kubectl get priorityclass
```
```
NAME                      VALUE        GLOBAL-DEFAULT
system-cluster-critical   2000000000   false
system-node-critical      2000001000   false
```

CoreDNS, kube-proxy 같은 시스템 컴포넌트가 이것을 쓴다. **일반 워크로드에는 이 값을 쓰면 안 된다.**

### 선점의 동작

```
① 고우선순위 Pod가 Pending (배치할 노드 없음)
        ↓
② 스케줄러가 선점 후보 노드를 찾는다
   "이 노드의 저우선순위 Pod들을 지우면 배치 가능한가?"
        ↓
③ 가장 적은 희생으로 가능한 노드 선택
        ↓
④ 대상 Pod들에게 graceful termination
   (terminationGracePeriodSeconds 존중)
        ↓
⑤ 고우선순위 Pod 배치
```

**선점된 Pod의 상태**
```bash
kubectl get events --field-selector reason=Preempted
kubectl describe pod <preempted-pod>
```
```
Status:  Failed
Reason:  Preempted
Message: Preempted in order to accommodate a higher priority pod
```

**컨트롤러가 다시 만들어 준다.** Deployment의 Pod라면 다른 노드에 재배치를 시도한다. 배치할 곳이 없으면 계속 Pending이다.

### 위험과 대책

> **⚠️ PriorityClass 남용의 위험**
>
> "우리 팀 서비스가 제일 중요하니까"라며 모두가 high-priority를 쓰면 우선순위가 무의미해진다. 더 나쁘게는, 저우선순위 워크로드가 계속 선점당해 **영원히 실행되지 못하는 기아(starvation)** 상태에 빠진다.
>
> **대책**
> 1. **PriorityClass 생성 권한을 제한한다** (RBAC, 17장)
> 2. **ResourceQuota의 scopeSelector로 제한한다** (13.2절)
>    ```yaml
>    spec:
>      hard:
>        requests.cpu: "10"
>      scopeSelector:
>        matchExpressions:
>          - scopeName: PriorityClass
>            operator: In
>            values: ["high-priority"]
>    ```
> 3. **`preemptionPolicy: Never`** — 우선순위는 높지만 선점은 안 하게. 스케줄 큐에서 먼저 시도되기만 한다.
> 4. **PodDisruptionBudget** — 선점도 PDB를 **최선 노력으로** 존중한다(보장은 아니다).

### 실용적 우선순위 체계

```
2000001000  system-node-critical      (시스템)
2000000000  system-cluster-critical   (시스템)
────────────────────────────────────────
   1000000  critical      결제, 인증 등 장애 시 서비스 중단
    100000  high          주요 API
     10000  normal        일반 서비스        ← globalDefault
      1000  low           내부 도구
       100  batch         배치, 재시도 가능   (preemptionPolicy: Never)
```

**`globalDefault: true`** 인 클래스를 하나 만들어 두면, 지정하지 않은 Pod가 그 값을 받는다. 없으면 우선순위 0이다.

# tolerating.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: special
spec:
  replicas: 2
  selector: { matchLabels: { app: special } }
  template:
    metadata: { labels: { app: special } }
    spec:

          operator: Equal
          value: special
          effect: NoSchedule

## 15.8 스케줄링 프로파일과 커스텀 스케줄러

### 프로파일 — 여러 스케줄링 정책

하나의 kube-scheduler가 여러 프로파일을 가질 수 있다.

```yaml
apiVersion: kubescheduler.config.k8s.io/v1
kind: KubeSchedulerConfiguration
profiles:
  - schedulerName: default-scheduler

  - schedulerName: bin-packing        # 밀집 배치 (비용 절감)
    pluginConfig:
      - name: NodeResourcesFit
        args:
          scoringStrategy:
            type: MostAllocated       # 이미 많이 찬 노드를 선호

  - schedulerName: spread-scheduler   # 분산 배치 (안정성)
    pluginConfig:
      - name: NodeResourcesFit
        args:
          scoringStrategy:
            type: LeastAllocated
```

```yaml
# Pod에서 지정
spec:
  schedulerName: bin-packing
```

**`MostAllocated`** 는 노드를 꽉 채워 빈 노드를 만든다. Cluster Autoscaler(16장)가 그 노드를 제거해 **비용을 줄인다.**

### 커스텀 스케줄러

특수한 요구가 있다면 자체 스케줄러를 실행할 수 있다.

- **Volcano**: 배치·AI 워크로드용. 갱 스케줄링(모든 Pod가 함께 시작), 큐 관리
- **Yunikorn**: 계층적 큐, 공정 배분
- **직접 구현**: 스케줄러 프레임워크의 플러그인으로 확장

**갱 스케줄링**이 필요한 예: 분산 학습 작업에서 워커 8개가 **모두** 배치되어야 의미가 있다. 6개만 뜨면 자원만 낭비한다. 기본 스케줄러는 이것을 표현하지 못한다.

### Descheduler

시간이 지나면 배치가 최적에서 멀어진다. 노드가 추가되거나, Pod가 축출·재배치되거나, 라벨이 바뀌기 때문이다.

**Descheduler**는 주기적으로 실행되어 조건에 맞지 않는 Pod를 축출한다. 그러면 스케줄러가 다시 배치한다.

```yaml
apiVersion: "descheduler/v1alpha2"
kind: "DeschedulerPolicy"
profiles:
  - name: default
    pluginConfig:
      - name: RemoveDuplicates
      - name: LowNodeUtilization
        args:
          thresholds: { cpu: 20, memory: 20, pods: 20 }
          targetThresholds: { cpu: 50, memory: 50, pods: 50 }
      - name: RemovePodsViolatingTopologySpreadConstraint
      - name: RemovePodsViolatingNodeAffinity
```

**주의**: Descheduler는 Pod를 죽인다. PDB를 반드시 설정하고, 프로덕션에서는 신중하게 도입한다.

## 15.9 스케줄링 문제 진단

```bash
# ① Pending 이유 확인
kubectl describe pod <pod> | grep -A10 Events

# ② 노드 상태와 여유
kubectl get nodes
kubectl describe node <node> | grep -A15 "Allocated resources"

# ③ 테인트 확인
kubectl get nodes -o json | jq -r '.items[] | "\(.metadata.name): \(.spec.taints // "none")"'

# ④ 노드 라벨 확인
kubectl get nodes --show-labels

# ⑤ 스케줄러 로그
kubectl logs -n kube-system -l component=kube-scheduler --tail=100
```

**FailedScheduling 메시지 해독**

| 메시지 | 원인 | 대응 |
|---|---|---|
| `Insufficient cpu/memory` | requests를 만족할 여유 없음 | requests 낮추기, 노드 추가 (14, 16장) |
| `had untolerated taint {k: v}` | 테인트에 막힘 | toleration 추가 |
| `didn't match Pod's node affinity/selector` | 어피니티 불만족 | 노드 라벨 확인 |
| `had volume node affinity conflict` | 볼륨 AZ 불일치 | `WaitForFirstConsumer` (12.2절) |
| `didn't match pod anti-affinity rules` | 안티어피니티 충돌 | `required` → `preferred` |
| `node(s) didn't satisfy existing pods anti-affinity` | 기존 Pod의 안티어피니티 | 위와 동일 |
| `unschedulable` | cordon 상태 | `kubectl uncordon` |
| `node(s) had unready condition` | 노드 NotReady | 노드 진단 (20장) |
| `Too many pods` | 노드의 Pod 수 상한(기본 110) | 노드 추가, `maxPods` 조정 |

## 실습 과제

**과제 1 — 어피니티 AND/OR 검증**
`nodeSelectorTerms`에 term을 두 개 두고, 각 term 안에 조건을 두 개씩 넣는다. 노드 라벨을 조합해 가며 어떤 경우에 스케줄되는지 확인해 OR/AND 규칙을 검증한다.

**과제 2 — required vs preferred 안티어피니티**
replicas를 노드 수보다 많게(예: 노드 2개, replicas 5) 설정하고, `required`와 `preferred` 안티어피니티를 각각 적용해 결과를 비교한다. `required`에서 몇 개가 Pending이 되는지 확인한다.

**과제 3 — 테인트만으로는 부족함을 확인**
GPU 노드 시나리오를 만들되 **톨러레이션만** 주고 어피니티는 주지 않는다. Pod가 일반 노드에도 배치되는 것을 확인한 뒤, 어피니티를 추가해 해결한다.

**과제 4 — matchLabelKeys의 효과**
`topologySpreadConstraints`에서 `matchLabelKeys`를 뺀 상태로 롤링 업데이트를 하고, 새 Pod들의 분산이 어떻게 되는지 관찰한다. 그다음 `matchLabelKeys: [pod-template-hash]`를 추가해 비교한다.

**과제 5 — 선점과 기아 상태**
저우선순위 Job을 여러 개 띄우고, 고우선순위 Pod를 반복해서 생성한다. 저우선순위 Job이 계속 선점당해 완료되지 못하는 것을 확인한 뒤, ResourceQuota의 scopeSelector로 고우선순위 사용을 제한해 해결한다.

## 요약

- 스케줄러는 **필터링**(가능한 노드 추리기)과 **스코어링**(최선 고르기) 두 단계로 동작한다. `FailedScheduling` 메시지의 숫자가 각 이유로 제외된 노드 수를 알려 준다.
- **노드 어피니티**는 노드 라벨을, **Pod 어피니티/안티어피니티**는 다른 Pod의 위치를 기준으로 한다. `topologyKey`가 "같은 곳"의 정의를 결정한다.
- **Pod 어피니티는 계산 비용이 크다.** 단순 분산이 목적이면 `topologySpreadConstraints`가 훨씬 효율적이다.
- **테인트는 노드가 Pod를 거부하는 것**이고, **톨러레이션은 그 거부를 견디는 허가**다. 톨러레이션만으로는 Pod가 그 노드로 **가지 않으므로**, 전용 노드에는 **테인트 + 어피니티를 함께** 써야 한다.
- 노드 장애 시 Pod가 5분 후 이동하는 것은 자동 추가되는 `unreachable` 톨러레이션의 `tolerationSeconds: 300` 때문이다.
- **`topologySpreadConstraints`의 `maxSkew`** 는 도메인 간 Pod 수 편차를 제한한다. 롤링 업데이트에서는 **`matchLabelKeys: [pod-template-hash]`** 가 있어야 리비전별로 올바르게 계산된다. 프로덕션에서는 `ScheduleAnyway`가 안전하다.
- **PriorityClass는 남용되면 우선순위가 무의미해지고 저우선순위 워크로드가 기아에 빠진다.** RBAC로 생성을 제한하고, ResourceQuota의 `scopeSelector`로 사용을 제한하며, 선점이 불필요하면 `preemptionPolicy: Never`를 쓴다.
- **스케줄링 프로파일**로 밀집 배치(`MostAllocated`, 비용 절감)와 분산 배치(`LeastAllocated`, 안정성)를 선택할 수 있고, **Descheduler**로 시간이 지나 최적에서 멀어진 배치를 교정할 수 있다.

**다음 장에서는** 배치가 아니라 **개수**를 자동으로 조절하는 방법을 다룬다. Pod 수(HPA), Pod 크기(VPA), 노드 수(Cluster Autoscaler)를 함께 설계하는 법을 살펴본다.
