# 16장. 오토스케일링

> **학습목표**
> - HPA의 스케일링 알고리즘을 계산할 수 있고 안정화 윈도를 튜닝할 수 있다.
> - VPA의 세 가지 모드와 HPA와의 충돌 지점을 안다.
> - Cluster Autoscaler와 Karpenter의 차이를 설명할 수 있다.
> - 커스텀·외부 메트릭으로 스케일링하는 방법을 안다.
> - 세 축의 오토스케일링을 함께 설계할 때의 함정을 피할 수 있다.

---

## 들어가며

오토스케일링에는 세 축이 있다.

```
        ┌─────────────────────────────────────────┐
        │  HPA (Horizontal Pod Autoscaler)        │
   가로 │  "Pod를 몇 개 띄울까?"                    │
        └─────────────────────────────────────────┘

        ┌─────────────────────────────────────────┐
        │  VPA (Vertical Pod Autoscaler)          │
   세로 │  "Pod 하나에 얼마를 줄까?"                 │
        └─────────────────────────────────────────┘

        ┌─────────────────────────────────────────┐
        │  Cluster Autoscaler / Karpenter         │
   노드 │  "노드를 몇 개 둘까?"                      │
        └─────────────────────────────────────────┘
```

세 축은 서로 맞물려 있다. HPA가 Pod를 늘리면 노드가 부족해지고, Cluster Autoscaler가 노드를 추가한다. 이 연쇄가 잘 동작하려면 14장의 requests가 정확해야 한다.

## 16.1 metrics-server — 모든 것의 전제

HPA와 VPA는 메트릭 없이는 아무것도 못 한다.

```bash
# 설치 (kind에서는 TLS 우회 필요)
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml

kubectl patch -n kube-system deployment metrics-server --type=json \
  -p '[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'

kubectl wait -n kube-system --for=condition=Available deployment/metrics-server --timeout=120s
```

```bash
kubectl top nodes
kubectl top pods --containers
```

**metrics-server는 kubelet의 요약 API에서 CPU·메모리 사용량을 수집**해 Metrics API(`metrics.k8s.io`)로 제공한다.

```bash
kubectl get --raw /apis/metrics.k8s.io/v1beta1/pods | jq '.items[0]'
```

> **⚠️ metrics-server는 모니터링 시스템이 아니다**
> - 최근 값만 메모리에 보관한다(약 15초 해상도, 이력 없음)
> - 고가용성 구성이 아니다
> - **Prometheus를 대체하지 않는다.** 31장의 관측성은 별개다.

## 16.2 HorizontalPodAutoscaler

### 기본 형태

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70      # requests 대비 70%
```

**`autoscaling/v2`를 쓰자.** v1은 CPU 하나만 지원한다.

```bash
kubectl get hpa
# NAME   REFERENCE        TARGETS   MINPODS   MAXPODS   REPLICAS
# web    Deployment/web   45%/70%   3         20        5
```

### 스케일링 공식

```
desiredReplicas = ceil( currentReplicas × ( currentMetric / desiredMetric ) )
```

**예제**
```
현재 replicas: 4
현재 평균 CPU 사용률: 90%
목표: 70%

desired = ceil(4 × (90 / 70)) = ceil(5.14) = 6
```

**허용 오차(tolerance)**: 비율이 **0.9 ~ 1.1** 사이면 스케일하지 않는다. 미세한 변동으로 계속 스케일되는 것을 막기 위해서다.

```
90/70 = 1.286  → 1.1 초과 → 스케일 아웃
72/70 = 1.029  → 허용 범위 → 변화 없음
```

### `Utilization`의 기준은 requests다 — 매우 중요

```yaml
target:
  type: Utilization
  averageUtilization: 70
```

**이것은 노드 용량의 70%가 아니라 `requests.cpu`의 70%다.**

```
requests.cpu: 200m
목표 70% → 140m를 넘으면 스케일 아웃
```

**따라서 requests를 바꾸면 HPA의 동작이 완전히 달라진다.**

```
requests: 200m, 실제 사용 140m → 70% → 목표 도달
requests: 500m, 실제 사용 140m → 28% → 스케일 인!
```

14장에서 requests를 정확히 설정하라고 한 이유가 여기에도 있다. **requests가 틀리면 HPA도 틀린다.**

절대값 기준도 쓸 수 있다.

```yaml
target:
  type: AverageValue
  averageValue: 300m        # requests와 무관한 절대값
```

### 여러 메트릭

```yaml
metrics:
  - type: Resource
    resource:
      name: cpu
      target: { type: Utilization, averageUtilization: 70 }
  - type: Resource
    resource:
      name: memory
      target: { type: Utilization, averageUtilization: 80 }
```

**각 메트릭으로 계산한 값 중 가장 큰 것을 선택한다.** 하나라도 임계를 넘으면 스케일 아웃된다.

> **⚠️ 메모리 기반 HPA는 대개 부적절하다**
>
> 메모리는 CPU와 달리 **부하가 줄어도 자동으로 반환되지 않는다.** JVM 힙, 커넥션 풀, 캐시는 한 번 늘어나면 유지된다.
>
> 결과: 스케일 아웃은 되지만 **스케일 인이 되지 않는다.** Pod 수가 계속 늘기만 한다.
>
> 메모리 기반 스케일링이 의미 있는 경우는 워크로드가 명확히 메모리 바운드이고 사용량이 실제로 오르내릴 때뿐이다. 대부분은 **CPU나 커스텀 메트릭(큐 길이, RPS)이 낫다.**

### behavior — 스케일 속도 제어

기본 동작은 보수적이다. 이것을 세밀하게 조정할 수 있다.

```yaml
spec:
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0        # 즉시 반응 (기본 0)
      selectPolicy: Max                     # 여러 정책 중 가장 큰 값
      policies:
        - type: Percent
          value: 100                        # 100% 증가 (2배)
          periodSeconds: 15
        - type: Pods
          value: 4                          # 또는 4개 추가
          periodSeconds: 15

    scaleDown:
      stabilizationWindowSeconds: 300       # ★ 5분간 관찰 (기본 300)
      selectPolicy: Min
      policies:
        - type: Percent
          value: 50                         # 한 번에 최대 50% 감소
          periodSeconds: 60
        - type: Pods
          value: 2
          periodSeconds: 60
```

**`stabilizationWindowSeconds`** 가 가장 중요한 파라미터다.

- **scaleUp의 기본값은 0**: 부하가 오르면 즉시 대응
- **scaleDown의 기본값은 300**: 5분간의 **최댓값**을 기준으로 판단

```
scaleDown 안정화 윈도 300초의 동작:
  최근 5분간 계산된 desiredReplicas: [10, 8, 6, 5, 5, 4]
  → 최댓값 10을 선택 → 스케일 인 안 함

이렇게 해서 "부하가 잠깐 줄었다가 다시 오르는" 상황에서
Pod를 줄였다 늘렸다 하는 플래핑(flapping)을 막는다.
```

**튜닝 지침**

| 상황 | scaleUp 안정화 | scaleDown 안정화 |
|---|---|---|
| 트래픽 급증이 잦음 | 0 (즉시) | 600~900초 (보수적) |
| 비용에 민감 | 0~30초 | 180~300초 |
| Pod 시작이 느림(JVM) | 0, Percent 크게 | 600초 이상 |
| 배치 워크로드 | 30~60초 | 60~120초 |

### 실습: HPA 동작 관찰

**① 대상 배포**

```yaml
# hpa-demo.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: hpa-demo
spec:
  replicas: 1
  selector:
    matchLabels: { app: hpa-demo }
  template:
    metadata:
      labels: { app: hpa-demo }
    spec:
      containers:
        - name: app
          image: registry.k8s.io/hpa-example      # CPU를 많이 쓰는 데모 앱
          ports: [{ containerPort: 80 }]
          resources:
            requests: { cpu: 100m, memory: 64Mi }
            limits:   { cpu: 300m, memory: 128Mi }
---
apiVersion: v1
kind: Service
metadata: { name: hpa-demo }
spec:
  selector: { app: hpa-demo }
  ports: [{ port: 80 }]
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: hpa-demo
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: hpa-demo
  minReplicas: 1
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 50 }
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0
      policies:
        - type: Percent
          value: 100
          periodSeconds: 15
    scaleDown:
      stabilizationWindowSeconds: 60      # 실습을 빠르게 보기 위해 짧게

```

## 16.3 커스텀 메트릭과 KEDA

### CPU만으로는 부족한 경우

큐를 소비하는 워커를 생각해 보자. CPU 사용률은 낮은데 큐에 작업이 10만 개 쌓여 있다. CPU 기반 HPA는 아무것도 하지 않는다.

**필요한 것은 "큐 길이 기반 스케일링"이다.**

### 세 가지 메트릭 소스

```yaml
metrics:
  # ① Resource — CPU/메모리 (metrics-server)
  - type: Resource
    resource:
      name: cpu
      target: { type: Utilization, averageUtilization: 70 }

  # ② Pods — Pod당 커스텀 메트릭 (custom.metrics.k8s.io)
  - type: Pods
    pods:
      metric:
        name: http_requests_per_second
      target:
        type: AverageValue
        averageValue: "100"       # Pod당 100 RPS

  # ③ Object — 특정 오브젝트의 메트릭
  - type: Object
    object:
      describedObject:
        apiVersion: networking.k8s.io/v1
        kind: Ingress
        name: web
      metric:
        name: requests_per_second
      target:
        type: Value
        value: "10k"

  # ④ External — 클러스터 외부 메트릭 (external.metrics.k8s.io)
  - type: External
    external:
      metric:
        name: sqs_queue_length
        selector:
          matchLabels:
            queue: orders
      target:
        type: AverageValue
        averageValue: "30"        # Pod당 30개 메시지
```

②③④를 쓰려면 **메트릭 어댑터**가 필요하다. 대표적으로 `prometheus-adapter`다.

```yaml
# prometheus-adapter 설정 예
rules:
  - seriesQuery: 'http_requests_total{namespace!="",pod!=""}'
    resources:
      overrides:
        namespace: { resource: namespace }
        pod: { resource: pod }
    name:
      matches: "^(.*)_total$"
      as: "${1}_per_second"
    metricsQuery: 'sum(rate(<<.Series>>{<<.LabelMatchers>>}[2m])) by (<<.GroupBy>>)'
```

### KEDA — 이벤트 기반 오토스케일링

메트릭 어댑터 설정은 번거롭다. **KEDA**(Kubernetes Event-Driven Autoscaling)는 이것을 훨씬 단순하게 만든다.

```bash
helm repo add kedacore https://kedacore.github.io/charts
helm install keda kedacore/keda --namespace keda --create-namespace
```

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: order-worker
spec:
  scaleTargetRef:
    name: order-worker
  minReplicaCount: 0              # ★ 0까지 줄일 수 있다!
  maxReplicaCount: 50
  pollingInterval: 15
  cooldownPeriod: 300
  triggers:
    - type: aws-sqs-queue
      metadata:
        queueURL: https://sqs.ap-northeast-2.amazonaws.com/123/orders
        queueLength: "10"          # Pod당 메시지 10개
        awsRegion: ap-northeast-2
      authenticationRef:
        name: aws-credentials
```

**KEDA의 강점**

**① Scale to Zero**
표준 HPA는 `minReplicas: 1`이 최소다. KEDA는 **0까지 줄인다.** 큐가 비면 Pod가 하나도 없다가, 메시지가 오면 자동으로 깨어난다. 배치 워크로드의 비용을 크게 줄인다.

**② 60개 이상의 스케일러 내장**
Kafka, RabbitMQ, SQS, Azure Service Bus, Prometheus, PostgreSQL, Redis, Cron, GCP Pub/Sub...

```yaml
# Prometheus 쿼리로 스케일
triggers:
  - type: prometheus
    metadata:
      serverAddress: http://prometheus.monitoring:9090
      metricName: http_requests_rate
      query: sum(rate(http_requests_total{app="web"}[2m]))
      threshold: "100"

# 시간 기반 (예측 가능한 패턴)
  - type: cron
    metadata:
      timezone: Asia/Seoul
      start: "0 8 * * 1-5"        # 평일 오전 8시
      end: "0 20 * * 1-5"          # 오후 8시
      desiredReplicas: "10"
```

**③ 내부적으로는 HPA를 만든다**
KEDA는 HPA를 대체하는 것이 아니라 **HPA를 자동 생성·관리**한다. 그래서 HPA의 모든 동작(behavior 등)이 그대로 적용된다.

```bash
kubectl get hpa
# keda-hpa-order-worker  ← KEDA가 만든 것
```

**시간 기반 스케일링의 가치**: 트래픽 패턴이 예측 가능하다면, 반응형 스케일링보다 **선제적 스케일링**이 낫다. 오전 9시에 트래픽이 몰린다면 8시 50분에 미리 늘려 두는 것이 사용자 경험에 좋다.

## 16.4 VerticalPodAutoscaler

### 세 가지 모드

VPA는 **Pod의 크기**(requests/limits)를 조절한다.

```yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: web-vpa
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web
  updatePolicy:
    updateMode: "Auto"        # Off | Initial | Recreate | Auto
  resourcePolicy:
    containerPolicies:
      - containerName: app
        minAllowed: { cpu: 50m, memory: 64Mi }
        maxAllowed: { cpu: "2",  memory: 4Gi }
        controlledResources: [cpu, memory]
        controlledValues: RequestsAndLimits    # 또는 RequestsOnly
      - containerName: sidecar
        mode: "Off"                            # 이 컨테이너는 제외
```

| 모드 | 동작 |
|---|---|
| `Off` | **추천만 계산.** 적용하지 않음 → 14.5절의 산정 도구 |
| `Initial` | Pod 생성 시에만 적용. 실행 중 변경 없음 |
| `Recreate` | Pod를 **삭제하고 재생성**해 적용 |
| `Auto` | 현재는 `Recreate`와 동일 (인플레이스 리사이즈는 발전 중) |

### 세 컴포넌트

```
Recommender  : 사용량 이력을 분석해 추천값 계산
Updater      : 추천과 현재 값이 크게 다르면 Pod 축출
Admission Plugin : 새 Pod 생성 시 추천값을 주입
```

```bash
kubectl describe vpa web-vpa
```
```
Recommendation:
  Container Recommendations:
    Container Name: app
    Lower Bound:  cpu: 87m,   memory: 262144k
    Target:       cpu: 150m,  memory: 314572k    ← 권장값
    Uncapped Target: cpu: 150m, memory: 314572k
    Upper Bound:  cpu: 1250m, memory: 1073741824
```

### HPA와의 충돌

> **⚠️ VPA(Auto)와 HPA를 같은 리소스(CPU/메모리)에 동시에 쓰면 안 된다**
>
> **왜 충돌하는가?**
> 1. HPA는 `requests` 대비 사용률로 판단한다(16.2절).
> 2. VPA가 requests를 올리면 → 같은 사용량에서 **사용률이 떨어진다.**
> 3. HPA가 "여유가 있네"라고 판단해 **스케일 인**한다.
> 4. Pod가 줄어 남은 Pod의 부하가 늘고 → VPA가 requests를 더 올린다.
> 5. 진동(oscillation)이 발생한다.
>
> **안전한 조합**
>
> | 조합 | 가능? |
> |---|---|
> | HPA(CPU) + VPA(`updateMode: Off`) | ✅ 추천만 받아 수동 반영 |
> | HPA(**커스텀 메트릭**) + VPA(CPU/메모리 Auto) | ✅ 서로 다른 신호를 본다 |
> | HPA(CPU) + VPA(**메모리만** Auto) | ⚠️ 이론상 가능하나 주의 |
> | HPA(CPU) + VPA(CPU Auto) | ❌ **금지** |

**실무 권장**: VPA는 **`Off` 모드로 권고만 받고**, 그 값을 매니페스트에 반영해 Git에 커밋하는 방식이 가장 안전하다(30장의 GitOps와도 잘 맞는다).

### In-Place Pod Resize

VPA의 근본 문제는 **Pod를 재시작해야 한다**는 것이다. 이를 해결하려는 것이 인플레이스 리사이즈다.

```yaml
# v1.27 알파, v1.33 베타
spec:
  containers:
    - name: app
      resizePolicy:
        - resourceName: cpu
          restartPolicy: NotRequired      # 재시작 없이 변경
        - resourceName: memory
          restartPolicy: RestartContainer  # 메모리는 재시작 필요할 수 있음
```

```bash
kubectl patch pod web --subresource resize \
  -p '{"spec":{"containers":[{"name":"app","resources":{"requests":{"cpu":"800m"}}}]}}'
```

성숙하면 VPA의 사용성이 크게 개선될 것이다.

## 16.5 노드 오토스케일링

### Cluster Autoscaler

**동작**

```
스케일 아웃:
  Pending Pod 발견 (리소스 부족이 이유)
       ↓
  "어느 노드 그룹에 노드를 추가하면 이 Pod가 뜰까?" 시뮬레이션
       ↓
  해당 노드 그룹(ASG/MIG/VMSS)의 크기 증가
       ↓
  노드 부팅 → 조인 → Pod 스케줄 (보통 1~5분)

스케일 인:
  노드 사용률이 임계값 미만 (기본 50%)
       ↓
  10분간(기본) 지속되는지 확인
       ↓
  그 노드의 Pod들을 다른 노드로 재배치 가능한지 확인
       ↓
  드레인 후 노드 제거
```

```yaml
# 주요 설정
--scale-down-utilization-threshold=0.5
--scale-down-unneeded-time=10m
--scale-down-delay-after-add=10m
--expander=least-waste          # random | most-pods | least-waste | priority
--balance-similar-node-groups
--skip-nodes-with-local-storage=false
--skip-nodes-with-system-pods=false
```

**노드 제거를 막는 Pod들**

Cluster Autoscaler는 다음 Pod가 있는 노드를 제거하지 않는다.

| 조건 | 회피 방법 |
|---|---|
| PDB를 위반하게 되는 Pod | 적절한 PDB 설정 |
| 컨트롤러 없이 만든 Pod (kind: Pod) | 컨트롤러 사용 |
| `emptyDir`/`hostPath` 로컬 스토리지 사용 | `--skip-nodes-with-local-storage=false` |
| kube-system의 Pod (PDB 없는) | PDB 추가 |
| 다른 곳으로 옮길 수 없는 Pod | 어피니티 완화 |

**명시적 회피 애노테이션**
```yaml
metadata:
  annotations:
    cluster-autoscaler.kubernetes.io/safe-to-evict: "false"
```

### Karpenter

AWS가 만들었고 이제 CNCF 프로젝트다. Cluster Autoscaler와 접근이 다르다.

| | **Cluster Autoscaler** | **Karpenter** |
|---|---|---|
| 노드 관리 | 미리 정의된 **노드 그룹**의 크기 조절 | **필요한 인스턴스를 직접 프로비저닝** |
| 인스턴스 타입 | 노드 그룹에 고정 | Pod 요구에 맞춰 **동적 선택** |
| 프로비저닝 속도 | 1~5분 (ASG 경유) | **수십 초** (EC2 직접 호출) |
| 빈 패킹 | 제한적 | **적극적 통합(consolidation)** |
| 스팟 인스턴스 | 별도 노드 그룹 | 자동 폴백, 중단 처리 |
| 지원 | 멀티 클라우드 | AWS 중심 (Azure 지원 추가) |

```yaml
# Karpenter NodePool
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: default
spec:
  template:
    spec:
      requirements:
        - key: kubernetes.io/arch
          operator: In
          values: ["amd64", "arm64"]
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["spot", "on-demand"]      # 스팟 우선
        - key: karpenter.k8s.aws/instance-category
          operator: In
          values: ["c", "m", "r"]
        - key: karpenter.k8s.aws/instance-generation
          operator: Gt
          values: ["5"]
      nodeClassRef:
        name: default
      expireAfter: 720h                       # 30일 후 교체 (보안 패치)
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    consolidateAfter: 30s
  limits:
    cpu: "1000"
    memory: 1000Gi
```

**Karpenter의 통합(consolidation)** 이 강력하다. 주기적으로 "지금 배치를 더 적은/작은 노드로 재구성할 수 있나?"를 계산하고, 가능하면 Pod를 옮기고 노드를 제거한다. **비용 절감 효과가 크다.**

**주의**: 노드를 자주 교체하므로 PDB와 graceful shutdown(6장)이 제대로 되어 있어야 한다. 그렇지 않으면 서비스가 끊긴다.

## 16.6 세 축을 함께 설계하기

### 연쇄 반응의 타이밍

```
부하 증가
   ↓ (15~30초)  HPA가 감지하고 Pod 수 증가
   ↓ (즉시)     새 Pod가 Pending (노드 여유 없음)
   ↓ (10~30초)  Cluster Autoscaler가 감지
   ↓ (1~5분)    노드 프로비저닝
   ↓ (10~60초)  이미지 pull + Pod 시작
   ↓ (프로브)    readiness 통과 → 트래픽 수신

총 지연: 2~7분
```

**이 지연이 문제가 되는 경우**가 많다. 대책은 셋이다.

**① 오버프로비저닝 — 미리 여유 노드 확보**

낮은 우선순위의 "자리 채우기" Pod를 띄워 둔다. 진짜 워크로드가 오면 선점되어(15.6절) 즉시 자리를 내준다.

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata: { name: overprovisioning }
value: -10                       # ★ 음수! 모든 것보다 낮다
globalDefault: false
---
apiVersion: apps/v1
kind: Deployment
metadata: { name: overprovisioning }
spec:
  replicas: 3
  selector: { matchLabels: { app: overprovisioning } }
  template:
    metadata: { labels: { app: overprovisioning } }
    spec:
      priorityClassName: overprovisioning
      terminationGracePeriodSeconds: 0     # 즉시 비켜 준다
      containers:
        - name: pause
          image: registry.k8s.io/pause:3.9
          resources:
            requests: { cpu: "1", memory: 2Gi }    # 실제로는 안 쓴다
```

**노드는 미리 떠 있고, 필요할 때 1초 만에 자리가 난다.**

**② 선제적 스케일링**

트래픽 패턴이 예측 가능하면 KEDA의 cron 스케일러를 쓴다(16.3절).

**③ Pod 시작 시간 단축**
- 이미지 크기 줄이기 (2장의 멀티 스테이지 빌드)
- `imagePullPolicy: IfNotPresent`
- 이미지 프리풀 (DaemonSet으로 미리 받아 두기)
- startupProbe 튜닝 (6장)

### 흔한 함정

**① requests가 부정확하면 모든 것이 무너진다**

```
requests가 실제보다 낮음
  → HPA: 사용률이 높게 계산되어 과도하게 스케일 아웃
  → CA:  노드에 실제보다 많은 Pod를 배치 → 노드 과부하 → 축출

requests가 실제보다 높음
  → HPA: 사용률이 낮게 계산되어 스케일 아웃 안 됨 → 응답 지연
  → CA:  불필요한 노드 추가 → 비용 낭비
```

**14장이 이 장의 전제조건이다.**

**② HPA와 replicas의 충돌**

```yaml
# Deployment
spec:
  replicas: 3        # ← HPA가 관리하는데 이 값이 있으면?
```

GitOps로 매니페스트를 다시 적용할 때마다 replicas가 3으로 되돌아가고, HPA가 다시 늘리는 **플래핑**이 발생한다.

**해결책**: HPA가 관리하는 Deployment에서는 `replicas` 필드를 **제거**한다.

Argo CD라면:
```yaml
spec:
  ignoreDifferences:
    - group: apps
      kind: Deployment
      jsonPointers: ["/spec/replicas"]
```

**③ PDB 없이 노드 오토스케일링**

Cluster Autoscaler가 노드를 제거할 때 PDB가 없으면 **한 서비스의 모든 Pod가 동시에 축출**될 수 있다.

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: web-pdb }
spec:
  minAvailable: 2         # 또는 maxUnavailable: 1
  selector:
    matchLabels: { app: web }
```

> **⚠️ PDB의 데드락**
> `minAvailable`을 `replicas`와 같게 하면 **노드 드레인이 영원히 진행되지 않는다.** 하나도 죽일 수 없기 때문이다.
> ```yaml
> replicas: 3
> minAvailable: 3      # ❌ 드레인 불가
> minAvailable: 2      # ✅
> maxUnavailable: 1    # ✅ (replicas가 변해도 안전)
> ```
> **`maxUnavailable`을 쓰는 편이 HPA와 함께 쓸 때 안전하다.**

**④ 스케일 인 시 요청 유실**

6장의 graceful shutdown이 되어 있지 않으면 스케일 인마다 502가 발생한다. `preStop` + SIGTERM 처리는 오토스케일링의 전제조건이다.

### 체크리스트

```
□ requests가 실측 기반으로 설정되어 있다 (14장)
□ readiness 프로브가 정확하다 (6장)
□ preStop + SIGTERM 처리가 되어 있다 (6장)
□ PDB가 설정되어 있다 (maxUnavailable 권장)
□ HPA 대상 Deployment에 replicas 필드가 없다
□ HPA의 minReplicas ≥ 2 (단일 장애점 제거)
□ scaleDown 안정화 윈도가 워크로드 특성에 맞다
□ 노드 프로비저닝 지연을 고려했다 (오버프로비저닝 등)
□ VPA는 Off 모드이거나 HPA와 다른 메트릭을 쓴다
□ 스케일링 이벤트에 알림이 걸려 있다 (31장)
```

## 실습 과제

**과제 1 — HPA 계산 검증**
`averageUtilization: 50`, replicas 2인 상태에서 부하를 걸어 사용률을 120%로 만든다. 공식 `ceil(2 × 120/50) = 5`대로 스케일되는지 확인한다. `behavior`의 `Percent` 정책이 이 값을 어떻게 제한하는지도 관찰한다.

**과제 2 — requests 변경이 HPA에 미치는 영향**
같은 부하에서 `requests.cpu`를 100m → 300m로 바꾸고 HPA의 TARGETS 값이 어떻게 변하는지 기록한다. Pod 수가 어떻게 달라지는가?

**과제 3 — 안정화 윈도 비교**
`scaleDown.stabilizationWindowSeconds`를 0과 600으로 각각 설정하고, 부하를 주기적으로 올렸다 내렸다 하며 Pod 수의 변화를 그래프로 그려 본다. 플래핑이 어떻게 억제되는지 확인한다.

**과제 4 — VPA 권고 vs 실제 설정**
14장 과제 4에서 얻은 VPA 추천값을 실제로 적용하고, 적용 전후의 노드 할당률과 Pod 축출 빈도를 비교한다.

**과제 5 — 오버프로비저닝 효과 측정**
16.6절의 오버프로비저닝 Deployment를 배포한 상태와 아닌 상태에서, HPA로 Pod를 급증시켰을 때 **첫 Pod가 Ready가 되기까지의 시간**을 각각 측정한다.

## 요약

- 오토스케일링은 **Pod 수(HPA)**, **Pod 크기(VPA)**, **노드 수(CA/Karpenter)** 세 축이며 서로 맞물려 동작한다. **모든 축이 requests의 정확성에 의존한다**(14장).
- HPA 공식은 `ceil(replicas × 현재/목표)`이고, **`Utilization`의 기준은 노드 용량이 아니라 `requests`** 다. requests를 바꾸면 HPA 동작이 완전히 달라진다.
- **메모리 기반 HPA는 대개 부적절하다.** 메모리는 부하가 줄어도 반환되지 않아 스케일 인이 일어나지 않는다.
- `behavior.scaleDown.stabilizationWindowSeconds`(기본 300)는 **최근 N초의 최댓값**을 기준으로 삼아 플래핑을 막는다. 스케일 아웃은 즉시(0), 스케일 인은 보수적으로가 기본 원칙이다.
- 큐 길이나 RPS 기반 스케일링에는 **KEDA**가 실용적이다. 60여 개 스케일러를 내장하고, **Scale to Zero**와 **시간 기반 선제 스케일링**을 지원하며, 내부적으로는 HPA를 만든다.
- **VPA(Auto)와 HPA를 같은 리소스에 동시에 쓰면 진동이 발생한다.** VPA는 `updateMode: Off`로 권고만 받아 매니페스트에 반영하는 방식이 가장 안전하다.
- **Karpenter**는 노드 그룹 없이 Pod 요구에 맞는 인스턴스를 직접 프로비저닝하고 적극적으로 통합해 비용을 줄인다. 대신 노드 교체가 잦으므로 PDB와 graceful shutdown이 필수다.
- 부하 급증부터 새 Pod가 트래픽을 받기까지 **2~7분**이 걸린다. 음수 우선순위의 **오버프로비저닝 Pod**로 여유 노드를 미리 확보하면 이 지연을 없앨 수 있다.
- HPA가 관리하는 Deployment에서는 **`replicas` 필드를 제거**해야 GitOps와 충돌하지 않는다.

**다음 장에서는** 지금까지 다룬 모든 리소스에 대한 접근을 통제하는 방법을 다룬다. API 요청이 통과하는 세 관문(인증·인가·어드미션)을 살펴보고, 최소 권한 RBAC를 설계한다.
