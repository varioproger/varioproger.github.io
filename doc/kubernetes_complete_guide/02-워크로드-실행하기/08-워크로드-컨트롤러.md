# 8장. 워크로드 컨트롤러

> **학습목표**
> - ReplicaSet이 Pod를 어떻게 관리하는지, 그리고 왜 직접 쓰지 않는지 설명할 수 있다.
> - Deployment의 롤링 업데이트 파라미터를 계산하고 롤백할 수 있다.
> - 블루-그린과 카나리 배포를 쿠버네티스 기본 기능으로 구현할 수 있다.
> - StatefulSet이 제공하는 세 가지 보장을 설명하고 적절히 사용할 수 있다.
> - DaemonSet, Job, CronJob의 용도를 구분한다.
> - 워크로드 성격에 맞는 컨트롤러를 결정 트리로 선택할 수 있다.

---

## 들어가며

5장에서 Pod를 직접 만들었지만, 노드가 죽으면 그대로 사라진다고 했다. 이 장에서 다루는 컨트롤러들이 그 문제를 해결한다.

각 컨트롤러는 1장에서 본 **조정 루프**를 돌린다. 다른 점은 "무엇을 원하는 상태로 삼는가"뿐이다.

```
ReplicaSet   : "이 라벨을 가진 Pod가 N개"
Deployment   : "이 템플릿의 ReplicaSet이 원하는 버전으로"
StatefulSet  : "고유 ID를 가진 Pod가 0..N-1까지 순서대로"
DaemonSet    : "조건에 맞는 모든 노드에 정확히 하나씩"
Job          : "성공적으로 완료된 Pod가 N개"
CronJob      : "스케줄에 맞춰 Job을 생성"
```

## 8.1 ReplicaSet — 개수를 지키는 컨트롤러

### 동작 원리

ReplicaSet은 단 하나의 일을 한다. **셀렉터에 매칭되는 Pod의 개수를 `replicas`로 유지한다.**

```yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: web-rs
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:                      # Pod 템플릿
    metadata:
      labels:
        app: web                 # ★ selector와 일치해야 한다
    spec:
      containers:
        - name: web
          image: hello:1.0
```

조정 루프는 이렇다.

```
① 셀렉터(app=web)에 맞는 Pod를 센다 → 2개
② 원하는 수(3개)와 비교 → 1개 부족
③ template으로 Pod를 1개 생성
```

반대로 4개면 하나를 **삭제한다.** 삭제 대상 선택에는 우선순위가 있다.

1. Pending 상태 (아직 스케줄 안 된 것)
2. Ready가 아닌 것
3. 재시작 횟수가 많은 것
4. 더 최근에 생성된 것
5. 같은 노드에 Pod가 많이 몰린 쪽

**"이미 잘 도는 것보다 문제 있는 것을 먼저 지운다"** 는 합리적 순서다.

### 셀렉터가 소유권을 결정한다

여기서 중요한 성질이 나온다. **ReplicaSet은 자기가 만들지 않은 Pod도 셀렉터에 맞으면 자기 것으로 간주한다.**

```bash
# ReplicaSet과 같은 라벨의 Pod를 직접 만들면
kubectl run rogue --image=nginx --labels="app=web"

# ReplicaSet이 이것을 자기 Pod로 세고, 초과분을 삭제한다
kubectl get pods -l app=web
```

4장에서 배운 `ownerReferences`가 이때 붙는다. 이 성질 때문에 **셀렉터가 겹치는 컨트롤러 두 개를 만들면 서로 상대의 Pod를 지우려 드는 참사**가 일어난다. 라벨 설계에 주의해야 하는 이유다.

### 왜 직접 쓰지 않는가

ReplicaSet은 개수만 관리할 뿐 **버전 관리를 하지 않는다.** 이미지를 바꾸면?

```bash
kubectl set image rs/web-rs web=hello:2.0
kubectl get pods -o jsonpath='{.items[*].spec.containers[0].image}'
# hello:1.0 hello:1.0 hello:1.0    ← 기존 Pod는 그대로!
```

**템플릿 변경은 기존 Pod에 영향을 주지 않는다.** 새로 만들어지는 Pod부터 적용된다. 롤링 업데이트도, 롤백도 없다.

그래서 실무에서는 **Deployment를 쓴다.** Deployment가 ReplicaSet을 관리하고, ReplicaSet이 Pod를 관리하는 3단 구조다.

```
Deployment  (버전 관리, 롤아웃 전략)
    └─ ReplicaSet v1  (replicas: 0)     ← 롤백용으로 보관
    └─ ReplicaSet v2  (replicas: 3)     ← 현재 활성
           └─ Pod, Pod, Pod
```

> **ReplicationController는 무엇인가?**
> ReplicaSet의 전신이다. 차이는 셀렉터뿐이다. RC는 등가 기반 셀렉터만 지원하고, RS는 `matchExpressions`(집합 기반)를 지원한다(4.3절). **새로 쓸 이유가 없다.**

## 8.2 Deployment — 무상태 애플리케이션

### 기본 구조

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  annotations:
    kubernetes.io/change-cause: "initial deploy v1.0"
spec:
  replicas: 4
  revisionHistoryLimit: 10          # 보관할 이전 ReplicaSet 수 (기본 10)
  minReadySeconds: 10               # Ready 후 이만큼 지나야 "사용 가능"으로 인정
  progressDeadlineSeconds: 600      # 이 시간 안에 진전이 없으면 실패 처리

  selector:
    matchLabels:
      app: web

  strategy:
    type: RollingUpdate             # 또는 Recreate
    rollingUpdate:
      maxSurge: 25%                 # 원하는 수보다 얼마나 더 만들 수 있나
      maxUnavailable: 25%           # 얼마나 부족해도 되나

  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: hello:1.0
          readinessProbe:           # ★ 롤링 업데이트의 안전장치
            httpGet: { path: /healthz, port: 8080 }
```

### 두 가지 전략

**`Recreate`** — 전부 죽이고 전부 만든다.

```
[v1 v1 v1] → [       ] → [v2 v2 v2]
             다운타임 발생
```

쓰는 경우: 두 버전이 동시에 존재하면 안 될 때(DB 스키마 호환성 문제, 파일 락 등).

**`RollingUpdate`** (기본) — 조금씩 교체한다.

```
[v1 v1 v1 v1]
[v1 v1 v1 v1 v2]        ← maxSurge만큼 추가
[v1 v1 v1 v2]           ← v2가 Ready되면 v1 하나 제거
[v1 v1 v1 v2 v2]
[v1 v1 v2 v2]
...
[v2 v2 v2 v2]
```

### maxSurge와 maxUnavailable 계산

`replicas: 4`, `maxSurge: 25%`, `maxUnavailable: 25%` 일 때:

```
maxSurge       = ceil(4 × 0.25)  = 1   → 최대 5개까지 존재 가능
maxUnavailable = floor(4 × 0.25) = 1   → 최소 3개는 사용 가능해야 함
```

올림/내림이 다르다는 점에 주의하자. 안전한 쪽으로 계산한다.

**조합에 따른 성격**

| 설정 | 동작 | 적합한 상황 |
|---|---|---|
| `maxSurge: 25%`, `maxUnavailable: 25%` (기본) | 균형 | 대부분의 경우 |
| `maxSurge: 1`, `maxUnavailable: 0` | **용량을 절대 줄이지 않음.** 새 Pod가 Ready된 뒤에만 기존 것 제거 | 프로덕션 권장 |
| `maxSurge: 0`, `maxUnavailable: 1` | **총 Pod 수가 늘지 않음.** 하나 지우고 하나 만듦 | 리소스가 빠듯할 때, 라이선스 제한 |
| `maxSurge: 100%`, `maxUnavailable: 0` | 새 버전 전체를 먼저 띄운 뒤 교체 | 빠른 배포, 리소스 여유 있을 때 |

> **⚠️ `maxUnavailable: 0`과 리소스 부족의 충돌**
> `maxUnavailable: 0`은 새 Pod가 뜰 자리가 있어야 진행된다. 클러스터에 여유가 없으면 새 Pod가 `Pending`에 머물러 **롤아웃이 영원히 멈춘다.** Cluster Autoscaler(16장)가 없다면 이 조합을 쓰기 전에 여유 용량을 확인해야 한다.

### readiness가 롤아웃을 통제한다

6장에서 확인했듯, **새 Pod가 `Ready`가 되어야 다음 단계로 넘어간다.** 이것이 롤링 업데이트의 핵심 안전장치다.

`minReadySeconds`를 추가하면 더 보수적이 된다.

```yaml
minReadySeconds: 30
```

Ready가 된 후 30초 동안 크래시하지 않아야 "사용 가능"으로 인정한다. **시작 직후에 죽는 버그**를 롤아웃 중에 잡아낼 수 있다.

### 리비전과 롤백

```bash
# 이력 확인
kubectl rollout history deployment/web
```
```
REVISION  CHANGE-CAUSE
1         initial deploy v1.0
2         update to v1.1
3         update to v1.2
```

`CHANGE-CAUSE`는 `kubernetes.io/change-cause` 애노테이션에서 온다. 매니페스트에 적어 두면 이력이 읽기 쉬워진다.

```bash
# 특정 리비전 상세
kubectl rollout history deployment/web --revision=2

# 직전으로 롤백
kubectl rollout undo deployment/web

# 특정 리비전으로
kubectl rollout undo deployment/web --to-revision=2

# 진행 중인 롤아웃 제어
kubectl rollout pause deployment/web
kubectl rollout resume deployment/web
kubectl rollout status deployment/web --timeout=5m
```

**롤백은 어떻게 그렇게 빠른가?** 이전 ReplicaSet이 `replicas: 0`으로 남아 있기 때문이다. 롤백은 그것을 다시 스케일 업하고 현재 것을 스케일 다운하는 것뿐이다. 이미지를 다시 받을 필요도 없다(노드에 캐시되어 있으므로).

```bash
kubectl get rs -l app=web
```
```
NAME             DESIRED   CURRENT   READY   AGE
web-6c8b4f9d7c   0         0         0       10m    ← v1.0 (롤백용)
web-7d8e9f5c8b   0         0         0       5m     ← v1.1
web-8e9f0a6d9c   4         4         4       1m     ← v1.2 (현재)
```

`revisionHistoryLimit`을 넘으면 오래된 것부터 삭제된다.

> **⚠️ 롤백이 복구하지 못하는 것**
> Deployment 롤백은 **Pod 템플릿만** 되돌린다. 다음은 되돌아가지 않는다.
> - DB 스키마 마이그레이션
> - ConfigMap/Secret의 내용 (7장의 불변 ConfigMap + 버전 이름이 이 문제를 해결한다)
> - 외부 시스템에 미친 부수 효과
>
> "롤백하면 되니까"라는 생각으로 마이그레이션을 설계하면 안 된다. **하위 호환되는 마이그레이션**(컬럼 추가는 되지만 삭제는 두 단계로)이 원칙이다.

### 실습: 롤링 업데이트 관찰하기

```yaml
# rollout-demo.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: rollout-demo
  annotations:
    kubernetes.io/change-cause: "v1"
spec:
  replicas: 4
  minReadySeconds: 5
  strategy:
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  selector:
    matchLabels: { app: rollout-demo }
  template:
    metadata:
      labels: { app: rollout-demo }
    spec:
      containers:
        - name: app
          image: nginx:1.25-alpine
          readinessProbe:
            httpGet: { path: /, port: 80 }
            initialDelaySeconds: 3
            periodSeconds: 2
```

```bash
kubectl apply -f rollout-demo.yaml
kubectl rollout status deployment/rollout-demo
```

이제 두 터미널을 준비한다.

**터미널 1** — Pod 변화 관찰
```bash
kubectl get pods -l app=rollout-demo -w
```

**터미널 2** — 업데이트 실행
```bash
kubectl set image deployment/rollout-demo app=nginx:1.27-alpine
kubectl annotate deployment/rollout-demo kubernetes.io/change-cause="v2 - nginx 1.27" --overwrite
```

터미널 1에서 관찰되는 패턴:
```
새 Pod 생성 (총 5개)      ← maxSurge: 1
새 Pod가 Ready
5초 대기                  ← minReadySeconds
기존 Pod 하나 Terminating (총 4개)
새 Pod 생성 (총 5개)
...
```

**용량이 절대 4개 미만으로 떨어지지 않는다.** `maxUnavailable: 0`의 효과다.

**롤백 실험**
```bash
# 잘못된 이미지로 업데이트
kubectl set image deployment/rollout-demo app=nginx:does-not-exist
kubectl get pods -l app=rollout-demo
```
```
NAME                            READY   STATUS             AGE
rollout-demo-6c8b4f9d7c-2xk4p   1/1     Running            5m    ← 기존 4개 유지
rollout-demo-6c8b4f9d7c-8mnvz   1/1     Running            5m
rollout-demo-6c8b4f9d7c-klmno   1/1     Running            5m
rollout-demo-6c8b4f9d7c-qw7lr   1/1     Running            5m
rollout-demo-9f0a1b7e0d-pqrst   0/1     ImagePullBackOff   30s   ← 새 Pod만 실패
```

**서비스는 멈추지 않았다.** 롤아웃만 멈췄을 뿐이다.

```bash
kubectl rollout status deployment/rollout-demo --timeout=30s
# error: timed out waiting for the condition

kubectl rollout undo deployment/rollout-demo
kubectl rollout status deployment/rollout-demo
```

```bash
kubectl delete -f rollout-demo.yaml
```

### 배포 전략: 블루-그린과 카나리

롤링 업데이트 외에도 두 가지 전략을 쿠버네티스 기본 기능만으로 구현할 수 있다.

**블루-그린 배포**

두 버전을 완전히 별도로 띄우고, Service의 셀렉터를 바꿔 한 번에 전환한다.

```yaml
# blue (현재 운영)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-blue
spec:
  replicas: 4
  selector:
    matchLabels: { app: web, slot: blue }
  template:
    metadata:
      labels: { app: web, slot: blue }
    spec:
      containers: [{ name: web, image: hello:1.0 }]
---
# green (새 버전)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-green
spec:
  replicas: 4
  selector:
    matchLabels: { app: web, slot: green }
  template:
    metadata:
      labels: { app: web, slot: green }
    spec:
      containers: [{ name: web, image: hello:2.0 }]
---
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web
    slot: blue           # ★ 이 한 줄이 트래픽 방향을 결정한다
  ports: [{ port: 80, targetPort: 8080 }]
```

**전환**
```bash
# green을 먼저 검증 (별도 Service로 접근)
kubectl patch service web -p '{"spec":{"selector":{"app":"web","slot":"green"}}}'
```

**즉시 전환되고, 문제가 있으면 즉시 되돌릴 수 있다.** 대가는 리소스가 2배 필요하다는 것이다.

**카나리 배포**

같은 Service 셀렉터를 공유하되, replica 수로 비율을 조절한다.

```yaml
# stable: replicas 9
# canary: replicas 1
# → 둘 다 app=web 라벨 → 10% 트래픽이 canary로
```

```bash
kubectl scale deployment web-canary --replicas=1     # 10%
kubectl scale deployment web-canary --replicas=3     # 25%
kubectl scale deployment web-stable --replicas=0     # 100% 전환
```

4장의 실습 과제 2에서 이미 해 본 방식이다.

> **이 방식의 한계**
> - **비율이 Pod 수에 묶인다.** 1%를 보내려면 stable을 99개 띄워야 한다.
> - **트래픽 분배가 정확하지 않다.** kube-proxy의 iptables 라운드로빈은 근사치다.
> - **세션 고정이 안 된다.** 같은 사용자가 요청마다 다른 버전을 받을 수 있다.
> - **자동 롤백이 없다.** 에러율이 올라도 사람이 봐야 한다.
>
> 정밀한 카나리는 **인그레스 컨트롤러의 가중치 기능**(11장)이나 **Argo Rollouts / Flagger** 같은 프로그레시브 딜리버리 도구(30장)로 구현한다. 이들은 메트릭을 보고 자동으로 승격하거나 롤백한다.

### Deployment 모범 사례

```yaml
spec:
  replicas: 3                          # 최소 2 이상 (단일 장애점 제거)
  revisionHistoryLimit: 5              # 기본 10은 대개 과하다
  minReadySeconds: 10
  progressDeadlineSeconds: 600
  strategy:
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0                # 용량 유지
  template:
    spec:
      terminationGracePeriodSeconds: 45
      topologySpreadConstraints:       # 노드/AZ 분산 (15장)
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: ScheduleAnyway
          labelSelector:
            matchLabels: { app: web }
      containers:
        - name: web
          image: registry.example.com/web:1.2.3   # latest 금지
          readinessProbe: { ... }                  # 필수
          lifecycle:
            preStop:
              exec: { command: ["sleep", "10"] }   # 6장
          resources:
            requests: { cpu: 100m, memory: 128Mi }
            limits:   { memory: 512Mi }
```

여기에 **PodDisruptionBudget**을 함께 정의한다(32장에서 상세히).

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-pdb
spec:
  minAvailable: 2            # 또는 maxUnavailable: 1
  selector:
    matchLabels: { app: web }
```

이것이 없으면 노드 드레인 시 모든 Pod가 동시에 축출될 수 있다.

## 8.3 StatefulSet — 상태 저장 애플리케이션

### Deployment로는 안 되는 것

데이터베이스 클러스터를 Deployment로 배포한다고 생각해 보자. 문제가 줄줄이 나온다.

1. **Pod 이름이 무작위다.** `db-6c8b4f9d7c-2xk4p`. 재시작하면 다른 이름이 된다. "1번 노드가 프라이머리"라는 규칙을 만들 수 없다.
2. **모든 Pod가 같은 볼륨을 공유한다.** 각 인스턴스가 자기만의 데이터 디렉터리를 가져야 하는데 불가능하다.
3. **시작 순서가 없다.** 클러스터를 구성하려면 첫 노드가 뜬 뒤 나머지가 조인해야 하는데, 동시에 뜬다.
4. **안정적인 네트워크 ID가 없다.** Pod IP가 바뀌면 클러스터 멤버십이 깨진다.

StatefulSet은 이 넷을 모두 해결한다.

### 세 가지 보장

**① 안정적이고 고유한 네트워크 ID**

```
web-0, web-1, web-2      ← 이름이 순서를 갖는다. 재시작해도 같은 이름
```

각 Pod는 고유한 DNS 이름을 얻는다.
```
web-0.web-headless.default.svc.cluster.local
web-1.web-headless.default.svc.cluster.local
```

이를 위해 **헤드리스 서비스**가 필요하다(9장에서 상세히).

**② 안정적인 스토리지**

`volumeClaimTemplates`로 각 Pod마다 **자기만의 PVC**가 생성된다.

```
web-0 → data-web-0 (PVC)
web-1 → data-web-1 (PVC)
web-2 → data-web-2 (PVC)
```

Pod가 죽고 다시 만들어져도 **같은 이름의 PVC에 다시 붙는다.** 데이터가 유지된다.

**③ 순서 보장**

```
생성: web-0 → (Ready 대기) → web-1 → (Ready 대기) → web-2
삭제: web-2 → web-1 → web-0        (역순)
스케일 다운 3→1: web-2 삭제 → web-1 삭제
```

### 매니페스트

```yaml
# 헤드리스 서비스 (필수)
apiVersion: v1
kind: Service
metadata:
  name: db-headless
spec:
  clusterIP: None                  # ★ 헤드리스
  selector:
    app: db
  ports:
    - port: 5432
      name: pg
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
spec:
  serviceName: db-headless         # ★ 위 헤드리스 서비스 이름
  replicas: 3
  podManagementPolicy: OrderedReady  # 또는 Parallel
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      partition: 0                 # 이 인덱스 이상만 업데이트

  selector:
    matchLabels: { app: db }

  template:
    metadata:
      labels: { app: db }
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: postgres
          image: postgres:16-alpine
          env:
            - name: POSTGRES_PASSWORD
              valueFrom:
                secretKeyRef: { name: db-secret, key: password }
            - name: PGDATA
              value: /var/lib/postgresql/data/pgdata
          ports:
            - containerPort: 5432
              name: pg
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data
          readinessProbe:
            exec:
              command: ["pg_isready", "-U", "postgres"]
            initialDelaySeconds: 5

  volumeClaimTemplates:            # ★ Pod마다 PVC 생성
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        storageClassName: standard
        resources:
          requests:
            storage: 5Gi
```

### podManagementPolicy

| 값 | 동작 | 쓰는 경우 |
|---|---|---|
| `OrderedReady` (기본) | 하나씩 순서대로, Ready 확인 후 다음 | 클러스터 조인 순서가 중요한 DB |
| `Parallel` | 동시에 생성/삭제 (이름과 스토리지는 여전히 안정적) | 순서가 상관없는 샤딩된 시스템 |

`Parallel`은 시작이 훨씬 빠르다. 순서가 필요 없다면 선택할 만하다.

### 롤링 업데이트와 partition

StatefulSet의 롤링 업데이트는 **높은 인덱스부터 역순**으로 진행된다.

```
web-2 업데이트 → Ready 대기 → web-1 → Ready 대기 → web-0
```

`partition`을 쓰면 **단계적 업데이트(스테이지드 롤아웃)** 가 가능하다.

```yaml
updateStrategy:
  rollingUpdate:
    partition: 2      # 인덱스 2 이상만 업데이트 → web-2만 교체
```

**카나리 배포에 활용하는 방법**

```bash
# ① partition을 replicas와 같게 설정 (아무것도 업데이트 안 됨)
kubectl patch statefulset db -p '{"spec":{"updateStrategy":{"rollingUpdate":{"partition":3}}}}'

# ② 이미지 변경 (아직 적용 안 됨)
kubectl set image statefulset/db postgres=postgres:17-alpine

# ③ partition을 2로 → web-2만 새 버전
kubectl patch statefulset db -p '{"spec":{"updateStrategy":{"rollingUpdate":{"partition":2}}}}'
# 검증...

# ④ 문제없으면 계속 낮춘다
kubectl patch statefulset db -p '{"spec":{"updateStrategy":{"rollingUpdate":{"partition":0}}}}'
```

**한 인스턴스씩 검증하며 진행할 수 있다.** 데이터베이스 업그레이드처럼 되돌리기 어려운 작업에 유용하다.

### 스케일 다운과 PVC

> **⚠️ StatefulSet을 스케일 다운해도 PVC는 삭제되지 않는다**
> ```bash
> kubectl scale statefulset db --replicas=1
> kubectl get pvc
> # data-db-0   Bound   (사용 중)
> # data-db-1   Bound   ← 남아 있다
> # data-db-2   Bound   ← 남아 있다
> ```
> **의도된 동작이다.** 실수로 스케일 다운했을 때 데이터를 잃지 않도록. 다시 스케일 업하면 같은 PVC에 재연결된다.
>
> 정말 삭제하려면 수동으로 지워야 한다.
> ```bash
> kubectl delete pvc data-db-1 data-db-2
> ```
>
> v1.27+ 에서는 정책을 지정할 수 있다.
> ```yaml
> spec:
>   persistentVolumeClaimRetentionPolicy:
>     whenScaled: Delete       # 스케일 다운 시 삭제
>     whenDeleted: Retain      # StatefulSet 삭제 시 보존
> ```

### 실습: StatefulSet의 세 보장 확인

```yaml
# sts-demo.yaml
apiVersion: v1
kind: Service
metadata:
  name: sts-headless
spec:
  clusterIP: None
  selector: { app: sts-demo }
  ports: [{ port: 80 }]
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: web
spec:
  serviceName: sts-headless
  replicas: 3
  selector:
    matchLabels: { app: sts-demo }
  template:
    metadata:
      labels: { app: sts-demo }
    spec:
      containers:
        - name: app
          image: busybox
          command:
            - sh
            - -c
            - |
              # 자기 이름을 데이터 파일에 기록 (최초 1회)
              [ -f /data/id ] || echo "$(hostname) created at $(date)" > /data/id
              cat /data/id
              sleep 3600
          volumeMounts:
            - name: data

```


**② 이름 안정성 확인**


**③ 스토리지 안정성 확인**

```bash
# web-1 created at Mon Sep  1 10:23:11 UTC 2026   ← 같은 시각! 데이터가 유지됐다
```

**④ PVC 확인**



**⑥ 정리**
```bash

```

### StatefulSet의 한계

StatefulSet이 해 주는 것은 **이름, 스토리지, 순서**뿐이다. 다음은 **해 주지 않는다.**

- 리더 선출
- 복제 설정
- 페일오버
- 백업
- 스키마 마이그레이션

이것들은 애플리케이션이나 오퍼레이터의 일이다. 그래서 실무에서는 **StatefulSet을 직접 쓰기보다 오퍼레이터를 쓴다.**

- PostgreSQL → CloudNativePG, Zalando Postgres Operator
- MySQL → Vitess, Percona Operator
- Kafka → Strimzi
- Redis → Redis Operator
- Elasticsearch → ECK

6부에서 이런 오퍼레이터를 직접 만든다.

> **더 근본적인 질문**
> 프로덕션 데이터베이스를 쿠버네티스에서 운영해야 하는가? 관리형 서비스(RDS, Cloud SQL)를 쓰는 편이 나은 경우가 많다. 운영 부담, 백업·복구, 성능 튜닝의 난이도를 고려해야 한다. StatefulSet은 "쿠버네티스에서 상태를 다룰 수 있다"는 것이지 "다뤄야 한다"는 뜻은 아니다.

## 8.4 DaemonSet — 노드마다 하나씩

### 용도

**모든(또는 조건에 맞는) 노드에 정확히 하나의 Pod**를 배치한다. 노드가 추가되면 자동으로 Pod가 생기고, 노드가 제거되면 Pod도 사라진다.

3장에서 본 `kube-proxy`와 `kindnet`이 DaemonSet이었다.

```bash
kubectl get daemonset -n kube-system
```

전형적 용도:
- **로그 수집기**: Fluent Bit, Filebeat, Promtail — 노드의 로그 디렉터리를 읽는다
- **모니터링 에이전트**: node-exporter, Datadog Agent
- **네트워크 플러그인**: Calico, Cilium (23장)
- **스토리지 데몬**: CSI 노드 플러그인 (12장)
- **보안 에이전트**: Falco

### 매니페스트

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-exporter
  namespace: monitoring
spec:
  selector:
    matchLabels: { app: node-exporter }
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1        # 동시에 업데이트할 노드 수
      # maxSurge: 0            (v1.25+ 에서 지원)
  template:
    metadata:
      labels: { app: node-exporter }
    spec:
      # ★ 컨트롤 플레인 노드에도 배치하려면 toleration 필요 (15장)
      tolerations:
        - key: node-role.kubernetes.io/control-plane
          operator: Exists
          effect: NoSchedule
        - operator: Exists      # 모든 테인트 무시 (에이전트에 흔한 설정)

      # ★ 특정 노드에만 배치하려면
      nodeSelector:
        kubernetes.io/os: linux

      hostNetwork: true         # 노드의 네트워크 네임스페이스 사용
      hostPID: true

      containers:
        - name: node-exporter
          image: prom/node-exporter:v1.8.0
          args:
            - --path.rootfs=/host
          ports:
            - containerPort: 9100
              hostPort: 9100    # 노드 포트에 직접 바인딩
          volumeMounts:
            - name: rootfs
              mountPath: /host
              readOnly: true
          securityContext:
            runAsUser: 65534
            readOnlyRootFilesystem: true

      volumes:
        - name: rootfs
          hostPath:
            path: /
```

**DaemonSet 특유의 설정들**

- **`tolerations`**: 기본적으로 테인트가 걸린 노드(컨트롤 플레인 등)에는 배치되지 않는다. 시스템 에이전트는 모든 노드에 필요하므로 `operator: Exists`로 모든 테인트를 감내하게 하는 것이 흔하다.
- **`hostNetwork: true`**: 노드의 네트워크를 직접 쓴다. 노드 수준 메트릭 수집이나 CNI 플러그인에 필요하다. **보안상 주의**가 필요하다(18장).
- **`hostPath` 볼륨**: 노드의 파일 시스템에 접근한다. 로그 수집기가 `/var/log/pods`를 읽는 방식이다. 역시 보안 검토 대상이다.

**DaemonSet은 스케줄러를 거친다.** 예전에는 DaemonSet 컨트롤러가 `nodeName`을 직접 지정했지만, 현재는 노드 어피니티로 표현되어 일반 스케줄러가 처리한다. 그래서 리소스 부족으로 DaemonSet Pod가 Pending에 머물 수 있다.

### DaemonSet의 대안

DaemonSet이 항상 답은 아니다.

| 상황 | 대안 |
|---|---|
| Pod마다 다른 설정이 필요 | 사이드카 (5.6절) |
| 일부 노드에만 필요 | `nodeSelector`가 붙은 DaemonSet, 또는 Deployment + 어피니티 |
| 노드당 여러 개 필요 | DaemonSet은 불가. Deployment + anti-affinity (15장) |
| 클라우드 매니지드 에이전트 | 클라우드가 제공하는 애드온을 쓰는 편이 낫다 |

## 8.5 Job과 CronJob — 배치 워크로드

### Job — 완료를 목표로 하는 워크로드

Deployment는 "계속 돌아야 하는" 것을, Job은 "끝나야 하는" 것을 관리한다.

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: data-migration
spec:
  completions: 1              # 성공해야 할 Pod 수
  parallelism: 1              # 동시 실행 수
  backoffLimit: 4             # 실패 재시도 횟수 (기본 6)
  activeDeadlineSeconds: 600  # 전체 제한 시간
  ttlSecondsAfterFinished: 3600   # 완료 후 자동 삭제 (기본은 남아 있음)

  template:
    spec:
      restartPolicy: OnFailure    # ★ Always는 사용 불가
      containers:
        - name: migrate
          image: myapp:1.2
          command: ["python", "manage.py", "migrate"]
```

**`restartPolicy`는 `OnFailure` 또는 `Never`만 가능하다.** `Always`면 영원히 끝나지 않으므로.

두 값의 차이:
- `OnFailure`: **같은 Pod 안에서 컨테이너를 재시작**한다. `restartCount`가 증가.
- `Never`: Pod를 실패로 두고 **새 Pod를 만든다.** 실패한 Pod가 남아 로그를 볼 수 있다.

디버깅에는 `Never`가 유리하다.

### 병렬 처리 패턴

**① 단일 작업**
```yaml
completions: 1
parallelism: 1
```

**② 고정 완료 수 (병렬)**
```yaml
completions: 10       # 10개가 성공해야 함
parallelism: 3        # 동시에 3개씩
```
"10개 파일을 처리하되 3개씩 동시에" 같은 경우.

**③ 작업 큐**
```yaml
completions: null     # 지정 안 함
parallelism: 5
```
5개 Pod가 동시에 돌며 외부 큐에서 작업을 가져간다. **하나라도 성공적으로 종료하면 나머지도 마무리**되고 Job이 완료된다.

**④ 인덱스 지정 (Indexed Job, v1.24+ GA)**
```yaml
completionMode: Indexed
completions: 5
parallelism: 5
```
각 Pod가 `JOB_COMPLETION_INDEX` 환경변수로 0~4의 인덱스를 받는다. 데이터를 샤딩해 처리할 때 유용하다.

```yaml
containers:
  - name: worker
    command: ["sh", "-c", "process-shard.sh $JOB_COMPLETION_INDEX"]
```

### Job 진단

```bash
kubectl get jobs
kubectl describe job data-migration
kubectl logs job/data-migration                # 첫 Pod의 로그
kubectl get pods -l job-name=data-migration    # 모든 Pod
kubectl logs -l job-name=data-migration --tail=-1
```

**흔한 문제**

| 증상 | 원인 |
|---|---|
| Job이 계속 재시도 | 앱 오류. `backoffLimit` 도달까지 반복 |
| `BackoffLimitExceeded` | 재시도 횟수 소진 |
| `DeadlineExceeded` | `activeDeadlineSeconds` 초과 |
| Job이 완료되지 않음 | 사이드카가 계속 실행 중 → **5.5절의 정식 사이드카**로 해결 |

마지막 항목이 중요하다. 5장에서 말한 대로 사이드카를 `initContainers` + `restartPolicy: Always`로 정의하면 메인 컨테이너가 끝날 때 자동 종료되어 Job이 정상 완료된다.

### CronJob — 스케줄된 Job

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-backup
spec:
  schedule: "0 3 * * *"                # 매일 03:00 (UTC 기준!)
  timeZone: "Asia/Seoul"               # v1.27+ 에서 타임존 지정 가능
  concurrencyPolicy: Forbid            # Allow | Forbid | Replace
  startingDeadlineSeconds: 300         # 이 시간 안에 시작 못하면 건너뜀
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 3
  suspend: false                       # true면 일시 중지

  jobTemplate:
    spec:
      backoffLimit: 2
      activeDeadlineSeconds: 3600
      ttlSecondsAfterFinished: 86400
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: backup
              image: backup-tool:1.0
              command: ["/backup.sh"]
```

> **⚠️ 타임존 함정**
> `timeZone` 필드가 없으면 **컨트롤러 매니저의 시간대**(보통 UTC)를 따른다. "매일 새벽 3시"라고 적었는데 한국 시각 정오에 실행되는 사고가 흔하다. v1.27+ 에서는 `timeZone`을 명시하자.

**`concurrencyPolicy`**

| 값 | 동작 |
|---|---|
| `Allow` (기본) | 이전 Job이 안 끝나도 새로 시작 |
| `Forbid` | 이전 Job이 실행 중이면 **건너뛴다** |
| `Replace` | 이전 Job을 죽이고 새로 시작 |

백업처럼 동시 실행이 위험한 작업은 반드시 `Forbid`를 쓴다.

**수동 실행 (테스트용)**
```bash
kubectl create job manual-backup --from=cronjob/nightly-backup
```

**일시 중지**
```bash
kubectl patch cronjob nightly-backup -p '{"spec":{"suspend":true}}'
```

## 8.6 컨트롤러 선택 결정 트리

```
워크로드가 끝나는가?
├─ 예 (완료를 목표로 함)
│   └─ 정해진 시각에 반복하는가?
│       ├─ 예 → CronJob
│       └─ 아니오 → Job
│
└─ 아니오 (계속 실행되어야 함)
    └─ 모든 노드에 하나씩 필요한가?
        ├─ 예 → DaemonSet
        └─ 아니오
            └─ 각 인스턴스가 고유한 ID나 스토리지를 갖는가?
                ├─ 예 → StatefulSet
                │        (단, 오퍼레이터가 있다면 그것을 먼저 검토)
                └─ 아니오 → Deployment  ← 90%의 경우
```

### 비교표

| | Deployment | StatefulSet | DaemonSet | Job | CronJob |
|---|---|---|---|---|---|
| Pod 이름 | 무작위 | `name-0`, `name-1` | 무작위 | 무작위 | 무작위 |
| 시작 순서 | 동시 | 순차 (기본) | 동시 | 병렬 설정 가능 | - |
| 스토리지 | 공유 또는 없음 | Pod마다 고유 PVC | hostPath 주로 | 임시 | 임시 |
| 스케일 | `replicas` | `replicas` | 노드 수에 종속 | `completions` | - |
| 업데이트 | 롤링 (앞에서부터) | 롤링 (역순) | 롤링 | - | - |
| 대표 용도 | 웹, API, 워커 | DB, 큐, 분산 스토리지 | 로그·모니터링·네트워크 | 마이그레이션, 배치 | 백업, 리포트 |

## 실습 과제

**과제 1 — 세 가지 롤아웃 전략 비교**
같은 앱을 세 가지 설정으로 배포하고, 업데이트 중 `curl` 반복 요청의 실패율과 총 소요 시간을 비교한다.
- `maxSurge: 1, maxUnavailable: 0`
- `maxSurge: 0, maxUnavailable: 1`
- `strategy: Recreate`

`hey -z 60s -c 10 http://...` 같은 부하 도구를 쓰면 측정이 쉽다.

**과제 2 — 블루-그린 전환 구현**
8.2절의 매니페스트로 blue/green을 배포하고, green을 검증할 별도 Service(`web-preview`)를 만든다. 검증 후 메인 Service의 셀렉터를 바꿔 전환하고, 문제 발생을 가정해 즉시 되돌린다. 전환에 걸린 시간을 측정한다.

**과제 3 — StatefulSet partition으로 카나리**
3개짜리 StatefulSet을 만들고, `partition`을 이용해 `web-2`만 새 이미지로 업데이트한다. 각 Pod의 이미지를 확인해 하나만 바뀌었는지 검증한 뒤, 단계적으로 partition을 낮춰 전체를 업데이트한다.

**과제 4 — Indexed Job으로 샤딩 처리**
`completionMode: Indexed`, `completions: 5`, `parallelism: 2`인 Job을 만들어 각 Pod가 `JOB_COMPLETION_INDEX`를 출력하도록 한다. 5개 인덱스가 모두 정확히 한 번씩 처리되는지 로그로 확인한다.

**과제 5 — 사이드카가 Job을 막는 문제 재현**
Job에 `containers`로 정의한 무한 루프 사이드카를 넣고 Job이 완료되지 않는 것을 확인한다. 그다음 그 사이드카를 `initContainers` + `restartPolicy: Always`로 옮겨 Job이 정상 완료되는 것을 비교한다.

## 요약

- **ReplicaSet**은 개수만 지킨다. 템플릿을 바꿔도 기존 Pod는 그대로이므로 직접 쓰지 않고, Deployment가 여러 ReplicaSet을 오가며 버전을 관리한다.
- **Deployment의 롤링 업데이트**는 `maxSurge`/`maxUnavailable`로 속도와 안전성을 조절한다. 프로덕션 권장은 `maxSurge: 1, maxUnavailable: 0`이며, 이때 클러스터에 여유 용량이 있어야 롤아웃이 멈추지 않는다. **readiness 프로브가 롤아웃의 안전장치**다.
- 롤백은 이전 ReplicaSet을 다시 스케일 업하는 것이라 빠르다. 다만 **DB 스키마와 ConfigMap 내용은 되돌아가지 않는다.**
- **블루-그린**은 Service 셀렉터 전환으로, **카나리**는 replica 비율로 구현할 수 있다. 정밀한 제어가 필요하면 인그레스 가중치나 Argo Rollouts를 쓴다.
- **StatefulSet**은 안정적 이름·스토리지·순서 세 가지를 보장한다. `partition`으로 단계적 업데이트가 가능하고, 스케일 다운해도 PVC는 남는다. 하지만 리더 선출이나 페일오버는 해 주지 않으므로 실무에서는 **오퍼레이터를 먼저 검토**한다.
- **DaemonSet**은 노드마다 하나씩 배치하며, 시스템 에이전트에 쓴다. 테인트를 감내할 toleration이 대개 필요하다.
- **Job**은 완료를 목표로 하고 `restartPolicy`가 `OnFailure`/`Never`만 가능하다. 사이드카는 반드시 `initContainers` + `Always`로 정의해야 Job이 완료된다. **CronJob**은 `timeZone`을 명시하고, 동시 실행이 위험하면 `concurrencyPolicy: Forbid`를 쓴다.

**2부를 마치며** — 여기까지가 쿠버네티스에서 워크로드를 실행하는 데 필요한 전부다. API 오브젝트 모델(4장), Pod의 구조(5장)와 생명주기(6장), 설정 주입(7장), 그리고 다섯 가지 컨트롤러(8장). 3부에서는 이렇게 띄운 워크로드를 **바깥과 연결한다.** 서비스 디스커버리, DNS, 인그레스, 그리고 데이터를 영구히 보관하는 스토리지를 다룬다.
