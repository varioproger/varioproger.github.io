# 7장. 설정과 시크릿

> **학습목표**
> - 이미지와 설정을 분리해야 하는 이유를 설명하고 ConfigMap으로 구현할 수 있다.
> - 환경변수 주입과 볼륨 마운트의 차이, 특히 **갱신 동작의 차이**를 안다.
> - Secret의 한계(base64는 암호화가 아니다)를 이해하고 실제 보호 수단을 적용할 수 있다.
> - Downward API로 Pod 자신의 메타데이터를 주입할 수 있다.
> - 설정이 바뀌었을 때 안전하게 롤아웃을 유도하는 패턴을 구현할 수 있다.

---

## 들어가며: 왜 분리하는가

2장에서 이미지가 불변이라고 했다. 그런데 같은 애플리케이션을 개발·스테이징·프로덕션에 배포하려면 DB 주소, 로그 레벨, 기능 플래그가 달라야 한다.

**설정을 이미지에 넣으면** 환경마다 다른 이미지를 빌드해야 한다. 그러면 "스테이징에서 테스트한 이미지"와 "프로덕션에 배포한 이미지"가 다른 산출물이 되어, 테스트의 의미가 사라진다.

그래서 원칙은 이렇다.

> **같은 이미지를 모든 환경에 배포하고, 설정만 환경별로 주입한다.**

이것은 [Twelve-Factor App](https://12factor.net/)의 3번째 원칙이기도 하다. 쿠버네티스는 이를 위해 **ConfigMap**(일반 설정)과 **Secret**(민감 정보) 두 리소스를 제공한다.

## 7.1 ConfigMap

### 만드는 방법

**명령형으로**

```bash
# 리터럴 값
kubectl create configmap app-config \
  --from-literal=LOG_LEVEL=info \
  --from-literal=MAX_CONNECTIONS=100

# 파일에서 (키 = 파일명)
kubectl create configmap app-config --from-file=./app.properties

# 파일에서 (키 지정)
kubectl create configmap app-config --from-file=config=./app.properties

# 디렉터리 전체 (각 파일이 하나의 키)
kubectl create configmap app-config --from-file=./config-dir/

# .env 파일에서 (각 줄이 키=값)
kubectl create configmap app-config --from-env-file=./app.env
```

**선언형으로**

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  # ① 단순 키-값
  LOG_LEVEL: "info"
  MAX_CONNECTIONS: "100"
  FEATURE_NEW_UI: "true"

  # ② 파일 전체를 하나의 값으로
  app.yaml: |
    server:
      port: 8080
      timeout: 30s
    database:
      host: postgres.default.svc.cluster.local
      pool_size: 20

  nginx.conf: |
    upstream backend {
      server localhost:8080;
    }
    server {
      listen 80;
      location / {
        proxy_pass http://backend;
      }
    }

binaryData:
  # 바이너리는 base64로 (인증서, 이미지 등)
  cert.der: MIIBkTCB+wIJAJ...
```

> **⚠️ `data`의 값은 모두 문자열이어야 한다**
> ```yaml
> data:
>   MAX_CONNECTIONS: 100        # ❌ 숫자 → 에러
>   MAX_CONNECTIONS: "100"      # ✅
>   DEBUG: true                 # ❌
>   DEBUG: "true"               # ✅
> ```
> 3장에서 본 YAML 함정이 여기서 실제 에러로 나타난다.

### 주입 방법 1: 환경변수

**개별 키 주입**

```yaml
spec:
  containers:
    - name: app
      image: hello:1.0
      env:
        - name: LOG_LEVEL
          valueFrom:
            configMapKeyRef:
              name: app-config
              key: LOG_LEVEL
        - name: DB_POOL
          valueFrom:
            configMapKeyRef:
              name: app-config
              key: MAX_CONNECTIONS
              optional: true          # 키가 없어도 Pod가 시작됨
```

**전체 키를 한 번에**

```yaml
      envFrom:
        - configMapRef:
            name: app-config
        - configMapRef:
            name: shared-config
            optional: true
        - secretRef:
            name: app-secret
        - prefix: APP_               # 모든 키에 접두사
          configMapRef:
            name: app-config
```

`envFrom`은 간편하지만 주의할 점이 있다.

- ConfigMap의 **모든 키**가 환경변수가 된다. 나중에 키를 추가하면 의도치 않은 변수가 생길 수 있다.
- 키 이름이 환경변수로 유효하지 않으면(예: `app.yaml`) **조용히 건너뛴다.** 이벤트에 경고가 남지만 놓치기 쉽다.
- 여러 소스에 같은 키가 있으면 **나중 것이 이긴다.** `env`가 `envFrom`보다 우선한다.

> **⚠️ 환경변수는 절대 갱신되지 않는다**
> ConfigMap을 수정해도 **이미 실행 중인 Pod의 환경변수는 바뀌지 않는다.** 리눅스에서 프로세스의 환경변수는 시작 시점에 고정되기 때문이다. 반영하려면 Pod를 재생성해야 한다(7.6절에서 방법을 다룬다).

### 주입 방법 2: 볼륨 마운트

```yaml
spec:
  volumes:
    - name: config
      configMap:
        name: app-config
        # 특정 키만 선택하고 경로 지정
        items:
          - key: app.yaml
            path: application.yaml       # /etc/app/application.yaml 로 마운트
          - key: nginx.conf
            path: nginx/nginx.conf       # 하위 디렉터리도 가능
        defaultMode: 0444                # 읽기 전용

  containers:
    - name: app
      volumeMounts:
        - name: config
          mountPath: /etc/app
          readOnly: true
```

`items`를 생략하면 **모든 키가 파일**이 된다.

```
/etc/app/
├── LOG_LEVEL          (내용: info)
├── MAX_CONNECTIONS    (내용: 100)
├── app.yaml
└── nginx.conf
```

**`subPath`의 함정**

특정 파일 하나만 기존 디렉터리에 끼워 넣고 싶을 때 `subPath`를 쓴다.

```yaml
      volumeMounts:
        - name: config
          mountPath: /etc/nginx/nginx.conf
          subPath: nginx.conf
```

이렇게 하면 `/etc/nginx/` 디렉터리의 다른 파일들이 유지된다. 하지만 **`subPath`로 마운트한 파일은 ConfigMap이 변경되어도 자동 갱신되지 않는다.** 이것은 알려진 제약이며, 갱신이 필요하면 디렉터리 마운트를 써야 한다.

### 볼륨 마운트의 자동 갱신 — 어떻게 동작하는가

환경변수와 달리 **볼륨으로 마운트한 ConfigMap은 자동으로 갱신된다.**

메커니즘이 흥미롭다. kubelet은 심볼릭 링크를 이용한 원자적 교체를 한다.

```bash
kubectl exec <pod> -- ls -la /etc/app/
```

```
lrwxrwxrwx  app.yaml -> ..data/app.yaml
drwxr-xr-x  ..2026_09_01_10_23_45.123456789/
lrwxrwxrwx  ..data -> ..2026_09_01_10_23_45.123456789
```

갱신 시 새 타임스탬프 디렉터리를 만들고, `..data` 심볼릭 링크를 원자적으로 교체한다. 그래서 **부분적으로 갱신된 파일을 읽는 일이 없다.**

**갱신 지연**은 kubelet의 동기화 주기(기본 1분) + 캐시 TTL을 합쳐 **최대 2분 정도**다. 즉시 반영되지 않는다.

**중요한 것은, 파일이 바뀌어도 앱이 그것을 다시 읽지 않으면 소용없다는 점이다.** 앱이 파일 변경을 감지하는 로직(inotify, 주기적 재로드)을 갖고 있거나, 7.6절의 롤아웃 유도 패턴을 써야 한다.

### 세 방식 비교

| | 환경변수 (`env`/`envFrom`) | 볼륨 마운트 | 볼륨 + `subPath` |
|---|---|---|---|
| 자동 갱신 | ❌ 절대 안 됨 | ✅ (최대 ~2분 지연) | ❌ |
| 앱 수정 필요 | 없음 | 파일 읽기 로직 | 파일 읽기 로직 |
| 큰 설정 파일 | 부적합 | ✅ 적합 | ✅ 적합 |
| 디버깅 | `kubectl exec -- env` | `kubectl exec -- cat` | 동일 |
| 대표 용도 | 단순 값, 12-factor 스타일 | 설정 파일, 인증서 | 기존 디렉터리에 파일 하나 추가 |

### 실습: ConfigMap의 두 방식 비교

```yaml
# configmap-demo.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: demo-config
data:
  GREETING: "hello"
  app.conf: |
    mode=development
    verbose=true
---
apiVersion: v1
kind: Pod
metadata:
  name: config-demo
spec:
  volumes:
    - name: config
      configMap:
        name: demo-config
  containers:
    - name: app
      image: busybox
      command:
        - sh
        - -c
        - |
          while true; do
            echo "=== $(date '+%H:%M:%S')"
            echo "ENV : $GREETING"
            echo "FILE: $(grep mode /etc/config/app.conf)"
            sleep 10
          done
      env:
        - name: GREETING
          valueFrom:
            configMapKeyRef: { name: demo-config, key: GREETING }
      volumeMounts:
        - name: config
          mountPath: /etc/config
```

```bash
kubectl apply -f configmap-demo.yaml
kubectl logs config-demo -f
```

```
=== 10:23:11
ENV : hello
FILE: mode=development
```

이제 ConfigMap을 수정한다.

```bash
kubectl patch configmap demo-config --type=merge \
  -p '{"data":{"GREETING":"CHANGED","app.conf":"mode=production\nverbose=false\n"}}'
```

1~2분 기다린 뒤 로그를 다시 본다.

```
=== 10:25:41
ENV : hello              ← 안 바뀜! (환경변수는 고정)
FILE: mode=production    ← 바뀜! (볼륨은 갱신됨)
```

**이 차이를 눈으로 확인하는 것이 이 실습의 목적이다.**

```bash
kubectl delete -f configmap-demo.yaml
```

## 7.2 Secret

### ConfigMap과의 차이

Secret은 구조적으로 ConfigMap과 거의 같다. 차이는 이렇다.

| | ConfigMap | Secret |
|---|---|---|
| 데이터 필드 | `data` (평문) | `data` (base64) 또는 `stringData` (평문 입력) |
| etcd 저장 | 평문 | 평문 (**암호화 설정 안 하면**) |
| kubelet 캐싱 | 노드 디스크 | **tmpfs (메모리)** |
| `kubectl get -o yaml` | 값이 보임 | base64 인코딩되어 보임 |
| RBAC | 별도 리소스로 권한 분리 가능 | 동일 |
| 최대 크기 | 1MiB | 1MiB |

> **⚠️ base64는 암호화가 아니다**
> ```bash
> kubectl get secret db-secret -o jsonpath='{.data.password}' | base64 -d
> # supersecret123
> ```
> 누구나 디코딩할 수 있다. base64는 바이너리 데이터를 안전하게 전송하기 위한 **인코딩**이지 보호 수단이 아니다.
>
> **Secret이 ConfigMap보다 실제로 나은 점은 두 가지뿐이다.**
> 1. 노드에서 **tmpfs(메모리)** 에 저장되어 디스크에 남지 않는다.
> 2. **RBAC로 권한을 분리**할 수 있고, 로그·이벤트에 값이 노출되지 않도록 시스템이 더 조심한다.
>
> 실제 보호는 7.4절(저장 시 암호화)과 7.5절(외부 시크릿 관리)에서 만들어야 한다.

### 만드는 방법

```bash
# 리터럴
kubectl create secret generic db-secret \
  --from-literal=username=admin \
  --from-literal=password='S3cur3P@ss'

# 파일에서
kubectl create secret generic tls-key --from-file=./server.key

# TLS 전용 타입
kubectl create secret tls my-tls \
  --cert=./tls.crt --key=./tls.key

# 레지스트리 인증
kubectl create secret docker-registry regcred \
  --docker-server=registry.example.com \
  --docker-username=user \
  --docker-password=pass \
  --docker-email=me@example.com
```

**선언형**

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
stringData:              # ★ 평문으로 쓰면 API 서버가 인코딩해 준다
  username: admin
  password: S3cur3P@ss
  config.json: |
    {"apiKey": "abc123"}
```

`stringData`를 쓰면 base64를 직접 계산할 필요가 없다. 저장 시 `data`로 변환된다.

**Secret 타입**

| type | 용도 | 필수 키 |
|---|---|---|
| `Opaque` | 임의 데이터 (기본) | - |
| `kubernetes.io/tls` | TLS 인증서 | `tls.crt`, `tls.key` |
| `kubernetes.io/dockerconfigjson` | 레지스트리 인증 | `.dockerconfigjson` |
| `kubernetes.io/basic-auth` | 기본 인증 | `username`, `password` |
| `kubernetes.io/ssh-auth` | SSH 키 | `ssh-privatekey` |
| `kubernetes.io/service-account-token` | SA 토큰 | (시스템 생성) |

타입을 지정하면 API 서버가 필수 키를 검증해 주고, 컨트롤러들이 용도를 인식한다.

### 주입 방법

ConfigMap과 동일하다.

```yaml
spec:
  volumes:
    - name: secret-vol
      secret:
        secretName: db-secret
        defaultMode: 0400        # 소유자만 읽기

  containers:
    - name: app
      env:
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: db-secret
              key: password
      volumeMounts:
        - name: secret-vol
          mountPath: /etc/secrets
          readOnly: true
```

> **환경변수보다 볼륨을 권장하는 이유**
>
> 환경변수로 주입한 시크릿은 여러 경로로 유출될 수 있다.
> - `kubectl describe pod`에는 안 보이지만, `kubectl get pod -o yaml`의 env 정의에는 키 참조가 남는다
> - 앱이 크래시할 때 스택 트레이스나 에러 리포팅 도구가 환경변수를 통째로 전송하는 경우가 있다
> - `/proc/<pid>/environ`으로 같은 Pod의 다른 컨테이너에서 읽힐 수 있다(PID 공유 시)
> - 자식 프로세스에 자동으로 상속된다
>
> 볼륨은 파일 권한으로 제어할 수 있고, 갱신도 된다.

### Secret 확인과 편집

```bash
# 값 보기
kubectl get secret db-secret -o jsonpath='{.data.password}' | base64 -d

# 전체를 평문으로
kubectl get secret db-secret -o go-template='{{range $k,$v := .data}}{{$k}}: {{$v | base64decode}}{{"\n"}}{{end}}'

# 편집 (base64를 직접 다뤄야 해서 불편)
kubectl edit secret db-secret
```

## 7.3 Downward API — Pod 자신의 정보 주입

앱이 자기 Pod 이름, 네임스페이스, 노드, IP를 알아야 할 때가 있다. 로그에 출처를 남기거나, 메트릭에 라벨을 붙이거나, 리더 선출에 쓸 때다.

### 환경변수로

```yaml
env:
  # 메타데이터
  - name: POD_NAME
    valueFrom:
      fieldRef:
        fieldPath: metadata.name
  - name: POD_NAMESPACE
    valueFrom:
      fieldRef:
        fieldPath: metadata.namespace
  - name: POD_UID
    valueFrom:
      fieldRef:
        fieldPath: metadata.uid
  - name: POD_IP
    valueFrom:
      fieldRef:
        fieldPath: status.podIP
  - name: NODE_NAME
    valueFrom:
      fieldRef:
        fieldPath: spec.nodeName
  - name: SERVICE_ACCOUNT
    valueFrom:
      fieldRef:
        fieldPath: spec.serviceAccountName

  # 라벨/애노테이션의 특정 키
  - name: APP_VERSION
    valueFrom:
      fieldRef:
        fieldPath: metadata.labels['version']

  # 리소스 정보 ★ 매우 유용
  - name: CPU_LIMIT
    valueFrom:
      resourceFieldRef:
        containerName: app
        resource: limits.cpu
        divisor: "1"          # 코어 단위
  - name: MEMORY_LIMIT_MB
    valueFrom:
      resourceFieldRef:
        containerName: app
        resource: limits.memory
        divisor: 1Mi          # MiB 단위
```

**`resourceFieldRef`의 실용적 가치**가 크다. JVM이나 Node.js 앱은 컨테이너의 메모리 한도를 알아야 힙 크기를 정할 수 있다.

```yaml
env:
  - name: MEMORY_LIMIT_MB
    valueFrom:
      resourceFieldRef:
        resource: limits.memory
        divisor: 1Mi
  - name: JAVA_OPTS
    value: "-XX:MaxRAMPercentage=75.0"
```

14장에서 이 설정이 왜 중요한지(그리고 왜 `-Xmx`를 하드코딩하면 안 되는지) 다룬다.

### 볼륨으로

라벨과 애노테이션 **전체**를 파일로 받을 수 있다. 이것은 환경변수로는 불가능하다.

```yaml
volumes:
  - name: podinfo
    downwardAPI:
      items:
        - path: labels
          fieldRef:
            fieldPath: metadata.labels
        - path: annotations
          fieldRef:
            fieldPath: metadata.annotations
```

```bash
kubectl exec <pod> -- cat /etc/podinfo/labels
```
```
app="hello"
pod-template-hash="6c8b4f9d7c"
version="1.0"
```

**볼륨 방식은 갱신된다.** 라벨을 바꾸면 파일이 반영된다. 4.3절에서 본 "라벨을 바꿔 Pod를 Service에서 떼어내는" 기법과 조합하면, 앱이 자기가 격리됐음을 감지할 수도 있다.

### 실습: 자기 정보를 출력하는 Pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: downward-demo
  labels:
    app: downward
    tier: backend
spec:
  volumes:
    - name: podinfo
      downwardAPI:
        items:
          - path: labels
            fieldRef: { fieldPath: metadata.labels }
  containers:
    - name: app
      image: busybox
      command:
        - sh
        - -c
        - |
          echo "=== Downward API ==="
          echo "Pod    : $POD_NAME"
          echo "NS     : $POD_NAMESPACE"
          echo "Node   : $NODE_NAME"
          echo "IP     : $POD_IP"
          echo "MemLim : ${MEM_LIMIT}Mi"
          echo "--- labels file ---"
          cat /etc/podinfo/labels
          sleep 3600
      env:
        - name: POD_NAME
          valueFrom: { fieldRef: { fieldPath: metadata.name } }
        - name: POD_NAMESPACE
          valueFrom: { fieldRef: { fieldPath: metadata.namespace } }
        - name: NODE_NAME
          valueFrom: { fieldRef: { fieldPath: spec.nodeName } }
        - name: POD_IP
          valueFrom: { fieldRef: { fieldPath: status.podIP } }
        - name: MEM_LIMIT
          valueFrom:
            resourceFieldRef: { resource: limits.memory, divisor: 1Mi }
      resources:
        limits:
          memory: 128Mi
      volumeMounts:
        - name: podinfo
          mountPath: /etc/podinfo
```

```bash
kubectl apply -f downward-demo.yaml
kubectl logs downward-demo
```

## 7.4 저장 시 암호화 (Encryption at Rest)

기본 설정에서 **Secret은 etcd에 평문으로 저장된다.** etcd 백업 파일을 얻은 사람은 모든 시크릿을 읽을 수 있다.

확인해 보자(kind 클러스터).

```bash
docker exec k8s-guide-control-plane sh -c \
  'ETCDCTL_API=3 etcdctl \
   --cacert=/etc/kubernetes/pki/etcd/ca.crt \
   --cert=/etc/kubernetes/pki/etcd/server.crt \
   --key=/etc/kubernetes/pki/etcd/server.key \
   get /registry/secrets/default/db-secret' | strings | grep -i pass
```

암호화가 없으면 비밀번호가 그대로 보인다.

### EncryptionConfiguration 설정

API 서버에 암호화 설정을 준다.

`/etc/kubernetes/enc/encryption-config.yaml`:
```yaml
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
      - secrets
      - configmaps                    # 원한다면 ConfigMap도
    providers:
      # ★ 순서가 중요하다. 첫 번째가 암호화에 쓰인다
      - aescbc:
          keys:
            - name: key1
              secret: <base64로 인코딩한 32바이트 키>
      - identity: {}                  # 평문 (기존 데이터 읽기용)
```

API 서버에 플래그를 추가한다.

```yaml
# /etc/kubernetes/manifests/kube-apiserver.yaml
spec:
  containers:
    - command:
        - kube-apiserver
        - --encryption-provider-config=/etc/kubernetes/enc/encryption-config.yaml
```

**프로바이더 종류**

| 프로바이더 | 특징 |
|---|---|
| `identity` | 암호화 안 함 (기본) |
| `aescbc` | AES-CBC. 널리 쓰였으나 `aesgcm` 권장 |
| `aesgcm` | AES-GCM. 빠르지만 키 교체가 잦아야 함 |
| `secretbox` | XSalsa20+Poly1305 |
| `kms` v2 | **외부 KMS 연동. 프로덕션 권장** |

**KMS v2**가 실질적인 정답이다. 데이터 암호화 키(DEK)를 클라우드 KMS(AWS KMS, GCP Cloud KMS, Azure Key Vault)로 보호하므로, 키가 etcd나 API 서버 디스크에 남지 않는다.

### 기존 Secret 재암호화

암호화 설정은 **새로 쓰이는 데이터에만** 적용된다. 기존 Secret을 암호화하려면 다시 쓰게 만들어야 한다.

```bash
kubectl get secrets -A -o json | kubectl replace -f -
```

22장에서 etcd 백업을 다룰 때 이 주제가 다시 나온다.

## 7.5 외부 시크릿 관리

etcd 암호화를 해도 남는 문제가 있다.

- **시크릿이 Git에 커밋된다.** GitOps(30장)를 하려면 매니페스트가 저장소에 있어야 하는데, Secret을 그대로 넣을 수는 없다.
- **로테이션이 수동이다.** 비밀번호를 90일마다 바꿔야 하는데 사람이 손으로 한다.
- **감사 추적이 없다.** 누가 언제 어떤 시크릿을 읽었는지 알 수 없다.

실무에서 쓰는 해법은 셋이다.

### ① External Secrets Operator (ESO)

외부 시크릿 저장소를 소스로 삼아 쿠버네티스 Secret을 **자동 생성·동기화**한다.

```yaml
apiVersion: external-secrets.io/v1beta1
kind: SecretStore
metadata:
  name: aws-secrets
spec:
  provider:
    aws:
      service: SecretsManager
      region: ap-northeast-2
      auth:
        jwt:
          serviceAccountRef:
            name: external-secrets-sa      # IRSA로 인증 (17장)
---
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: db-credentials
spec:
  refreshInterval: 1h                       # 자동 갱신 주기
  secretStoreRef:
    name: aws-secrets
    kind: SecretStore
  target:
    name: db-secret                         # 생성될 K8s Secret 이름
    creationPolicy: Owner
  data:
    - secretKey: password                   # K8s Secret의 키
      remoteRef:
        key: prod/database                  # AWS Secrets Manager의 시크릿
        property: password
```

**장점**: 매니페스트에 실제 값이 없으므로 Git에 안전하게 커밋할 수 있다. 외부에서 값을 바꾸면 자동으로 동기화된다.

지원 백엔드: AWS Secrets Manager, GCP Secret Manager, Azure Key Vault, HashiCorp Vault, 1Password 등.

### ② Sealed Secrets

값을 **클러스터의 공개키로 암호화**해 Git에 커밋한다. 클러스터 안의 컨트롤러만 복호화할 수 있다.

```bash
# 암호화
kubectl create secret generic db-secret \
  --from-literal=password=S3cur3 --dry-run=client -o yaml \
  | kubeseal -o yaml > sealed-secret.yaml

# 결과물은 Git에 커밋 가능
cat sealed-secret.yaml
```

```yaml
apiVersion: bitnami.com/v1alpha1
kind: SealedSecret
metadata:
  name: db-secret
spec:
  encryptedData:
    password: AgBv3xK9m2...    # 이 클러스터에서만 복호화 가능
```

**장점**: 외부 시스템이 필요 없다. 소규모 팀에 적합.
**단점**: 로테이션이 여전히 수동. 클러스터를 재구축하면 키를 복원해야 한다.

### ③ 시크릿을 아예 만들지 않기 — Workload Identity

가장 나은 접근이다. **정적 자격 증명 자체를 없앤다.**

```yaml
# EKS의 IRSA 예
apiVersion: v1
kind: ServiceAccount
metadata:
  name: app-sa
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::123456789:role/app-role
---
apiVersion: apps/v1
kind: Deployment
spec:
  template:
    spec:
      serviceAccountName: app-sa       # 이것만으로 AWS API 호출 가능
```

앱은 AWS 액세스 키를 갖지 않는다. ServiceAccount 토큰이 IAM 역할로 교환되고, 그 토큰은 자동 로테이션된다. 17장에서 자세히 다룬다.

**선택 가이드**

| 상황 | 권장 |
|---|---|
| 클라우드 리소스 접근 (S3, RDS, ...) | **Workload Identity** — 시크릿이 아예 없음 |
| 외부 SaaS API 키 등 | **External Secrets Operator** |
| 소규모 팀, 외부 시스템 없음 | **Sealed Secrets** |
| 어떤 경우든 | + **etcd 암호화(KMS)** 는 기본으로 |

## 7.6 설정 변경 시 롤아웃 유도하기

7.1절에서 확인했듯, ConfigMap을 바꿔도 환경변수는 갱신되지 않고 볼륨은 앱이 다시 읽어야 반영된다. 그래서 **설정이 바뀌면 Pod를 새로 만드는** 것이 가장 확실하다.

### 문제 상황

```bash
kubectl edit configmap app-config      # 설정 변경
kubectl get pods                       # ... 아무 일도 안 일어난다
```

Deployment의 spec이 바뀌지 않았으므로 컨트롤러는 조치할 이유가 없다. 4.2절의 `generation`이 그대로다.

### 해결책 1: 체크섬 애노테이션 (권장)

ConfigMap의 해시를 Pod 템플릿의 애노테이션에 넣는다. 설정이 바뀌면 해시가 바뀌고, 그러면 Pod 템플릿이 바뀌므로 롤링 업데이트가 자동으로 일어난다.

**Helm에서** (30장):
```yaml
spec:
  template:
    metadata:
      annotations:
        checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}
        checksum/secret: {{ include (print $.Template.BasePath "/secret.yaml") . | sha256sum }}
```

**Kustomize에서**는 자동으로 처리된다.
```yaml
# kustomization.yaml
configMapGenerator:
  - name: app-config
    literals:
      - LOG_LEVEL=info
```
Kustomize는 `app-config-7d9f8b2c4k` 처럼 **내용 해시를 이름에 붙인다.** 내용이 바뀌면 새 ConfigMap이 생기고, Deployment의 참조도 자동으로 갱신되어 롤아웃이 일어난다. 게다가 **이전 버전이 남아 있어 롤백도 가능하다.**

**직접 관리한다면** 스크립트로:
```bash
HASH=$(kubectl get configmap app-config -o yaml | sha256sum | cut -c1-16)
kubectl patch deployment app -p \
  "{\"spec\":{\"template\":{\"metadata\":{\"annotations\":{\"config-hash\":\"$HASH\"}}}}}"
```

### 해결책 2: 수동 재시작

```bash
kubectl rollout restart deployment/app
```

Pod 템플릿에 `kubectl.kubernetes.io/restartedAt` 애노테이션을 현재 시각으로 넣어 롤링 업데이트를 유발한다. 간단하지만 **자동화되지 않는다.**

### 해결책 3: Reloader

ConfigMap/Secret 변경을 감시해 관련 Deployment를 자동 재시작하는 오퍼레이터다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app
  annotations:
    reloader.stakater.com/auto: "true"        # 참조하는 모든 CM/Secret 감시
    # 또는 특정 대상만
    configmap.reloader.stakater.com/reload: "app-config"
```

### 해결책 4: 불변 ConfigMap + 버전 이름

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config-v2        # 버전을 이름에 넣는다
immutable: true              # ★ 변경 불가로 선언
data:
  LOG_LEVEL: debug
```

`immutable: true`의 이점:
- **실수로 프로덕션 설정을 바꾸는 사고를 막는다.**
- kubelet이 변경을 감시할 필요가 없어져 **API 서버 부하가 크게 준다.** 대규모 클러스터에서 의미 있는 최적화다.

설정을 바꾸려면 새 이름의 ConfigMap을 만들고 Deployment의 참조를 바꾼다. 이것은 자연스럽게 롤링 업데이트를 유발하고, 이전 ConfigMap이 남아 있어 롤백도 쉽다.

### 실습: 체크섬으로 자동 롤아웃 구현

```yaml
# checksum-demo.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: web-config
data:
  index.html: |
    <h1>Version 1</h1>
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 2
  selector:
    matchLabels: { app: web }
  template:
    metadata:
      labels: { app: web }
      annotations:
        config-hash: "PLACEHOLDER"
    spec:
      volumes:
        - name: html
          configMap: { name: web-config }
      containers:
        - name: nginx
          image: nginx:alpine
          volumeMounts:
            - name: html
              mountPath: /usr/share/nginx/html
```

```bash
kubectl apply -f checksum-demo.yaml

# 해시 계산 후 주입하는 스크립트
apply_with_hash() {
  HASH=$(kubectl get configmap web-config -o jsonpath='{.data}' | sha256sum | cut -c1-16)
  kubectl patch deployment web -p \
    "{\"spec\":{\"template\":{\"metadata\":{\"annotations\":{\"config-hash\":\"$HASH\"}}}}}"
}

apply_with_hash
kubectl rollout status deployment/web
```

이제 설정을 바꾸고 스크립트를 다시 실행한다.

```bash
kubectl patch configmap web-config --type=merge \
  -p '{"data":{"index.html":"<h1>Version 2</h1>\n"}}'

apply_with_hash
kubectl rollout status deployment/web       # ★ 롤아웃이 일어난다!

kubectl get pods -l app=web                 # 새 Pod로 교체됨
```

```bash
kubectl delete -f checksum-demo.yaml
```

## 실습 과제

**과제 1 — 환경별 설정 분리**
같은 Deployment 매니페스트에 `dev`와 `prod` 두 ConfigMap을 준비하고, 네임스페이스만 바꿔 배포한다. 이미지는 동일하되 로그 레벨과 replica 수가 다르게 만든다. "같은 이미지, 다른 설정" 원칙을 실제로 구현해 본다.

**과제 2 — Secret 유출 경로 확인**
Secret을 환경변수로 주입한 Pod에서 다음을 실행해 값이 노출되는 경로를 확인한다.
```bash
kubectl exec <pod> -- env | grep -i pass
kubectl exec <pod> -- cat /proc/1/environ | tr '\0' '\n' | grep -i pass
```
그다음 볼륨 마운트로 바꾸고 같은 명령이 아무것도 찾지 못하는 것을 확인한다.

**과제 3 — etcd에서 Secret 확인**
7.4절의 etcdctl 명령으로 Secret이 평문으로 저장되어 있는지 확인한다. (kind 클러스터에서 안전하게 실험할 수 있다.) 이 실험이 왜 "Secret은 암호화가 아니다"라는 말의 근거인지 설명해 본다.

**과제 4 — 불변 ConfigMap 실험**
`immutable: true`인 ConfigMap을 만들고 수정을 시도해 어떤 에러가 나는지 확인한다. 그다음 `app-config-v1` → `app-config-v2`로 이름을 바꿔 가며 배포하는 워크플로를 만들고, `kubectl rollout undo`로 이전 설정으로 롤백되는 것을 확인한다.

## 요약

- **같은 이미지를 모든 환경에 배포하고 설정만 주입한다.** ConfigMap은 일반 설정, Secret은 민감 정보용이지만 구조는 거의 같다.
- **환경변수는 절대 갱신되지 않고, 볼륨 마운트는 갱신된다**(최대 2분 지연). 단 `subPath`로 마운트하면 갱신되지 않는다.
- **base64는 암호화가 아니다.** Secret의 실질적 이점은 노드에서 tmpfs에 저장된다는 것과 RBAC 분리뿐이다. 실제 보호는 **etcd 암호화(KMS v2)** 와 **외부 시크릿 관리**로 만든다.
- 시크릿을 환경변수보다 **볼륨으로** 주입하는 편이 안전하다. 환경변수는 `/proc/*/environ`, 에러 리포팅, 자식 프로세스 상속 등 유출 경로가 많다.
- **Downward API**로 Pod 이름·노드·IP·리소스 한도를 주입할 수 있다. `resourceFieldRef`로 메모리 한도를 받아 JVM 힙을 설정하는 것이 대표적 용도다.
- 실무 시크릿 관리의 정답 순서: **① Workload Identity로 시크릿 자체를 없애기 → ② External Secrets Operator → ③ Sealed Secrets**. 어떤 경우든 etcd 암호화는 기본.
- 설정 변경 시 롤아웃을 유도하려면 **체크섬 애노테이션**(Helm) 또는 **내용 해시 이름**(Kustomize)을 쓴다. `immutable: true`는 사고를 막고 API 서버 부하도 줄인다.

**다음 장에서는** 지금까지 다룬 Pod를 실제로 관리하는 다섯 가지 컨트롤러를 살펴본다. Deployment의 롤링 업데이트가 어떻게 동작하는지, StatefulSet이 왜 필요한지, 그리고 어떤 상황에 어떤 컨트롤러를 골라야 하는지 정리한다.
