# 31장. 관측성

> **학습목표**
> - 관측성의 세 기둥과 쿠버네티스에서의 수집 경로를 설명할 수 있다.
> - Prometheus 스택을 구성하고 ServiceMonitor로 앱 메트릭을 수집할 수 있다.
> - 로그 수집 파이프라인을 설계하고 비용을 통제할 수 있다.
> - OpenTelemetry로 분산 트레이싱을 도입할 수 있다.
> - SLI/SLO를 정의하고 번 레이트 기반 알림을 만들 수 있다.
> - 이벤트와 감사 로그를 장기 보관해 분석할 수 있다.

## 31.1 관측성의 세 기둥

### 무엇이 다른가

```
┌─────────────────────────────────────────────────────┐
│  메트릭 (Metrics)                                     │
│  · 시계열 수치. 집계에 최적화                           │
│  · "지금 에러율이 얼마인가?"                            │
│  · 저비용, 장기 보관 가능                              │
│  → 무엇이 잘못됐는지 알려 준다                          │
├─────────────────────────────────────────────────────┤
│  로그 (Logs)                                          │
│  · 시점별 이벤트 기록. 상세                             │
│  · "그 요청에서 무슨 일이 있었나?"                       │
│  · 고비용, 보관 기간 제한                              │
│  → 왜 잘못됐는지 알려 준다                             │
├─────────────────────────────────────────────────────┤
│  트레이스 (Traces)                                    │
│  · 요청의 서비스 간 전파 경로                           │
│  · "어느 서비스에서 시간을 쓰고 있나?"                    │
│  · 샘플링으로 비용 통제                                │
│  → 어디서 잘못됐는지 알려 준다                          │
└─────────────────────────────────────────────────────┘
```

**진단 흐름**

```
알림: "에러율이 5%를 넘었다"          ← 메트릭
   ↓
대시보드: "checkout 서비스에서 발생"    ← 메트릭
   ↓
트레이스: "payment 호출에서 타임아웃"   ← 트레이스
   ↓
로그: "connection pool exhausted"     ← 로그
```

**세 가지가 상관관계로 연결되어야 이 흐름이 매끄럽다.** 트레이스 ID를 로그에 넣고, 메트릭에 exemplar를 붙이는 것이 그 방법이다.

### 쿠버네티스에서의 수집 경로

```
┌──────────────────── 노드 ────────────────────┐
│                                              │
│  Pod ──stdout/stderr──→ /var/log/pods/       │
│   │                          │               │
│   │ /metrics 엔드포인트        │ DaemonSet     │
│   │                          ▼               │
│   │                    [로그 수집기]           │
│   │                          │               │
│  kubelet ──→ cAdvisor 메트릭  │               │
│   │  (컨테이너 CPU/메모리/IO)   │               │
│   ▼                          ▼               │
│  /metrics/resource       중앙 로그 시스템       │
│  /metrics/cadvisor                           │
└──────────────────────────────────────────────┘
         │
         │ 스크레이프
         ▼
   [Prometheus]  ←─── kube-state-metrics (오브젝트 상태)
         │        ←─── node-exporter (노드 하드웨어)
         │        ←─── 컨트롤 플레인 메트릭
         ▼
   [Grafana] [Alertmanager]
```

**세 가지 메트릭 소스를 구분해야 한다.**

| 소스 | 제공하는 것 | 예 |
|---|---|---|
| **cAdvisor** (kubelet 내장) | 컨테이너 **실제 사용량** | `container_cpu_usage_seconds_total`, `container_memory_working_set_bytes` |
| **kube-state-metrics** | 오브젝트의 **선언된 상태** | `kube_deployment_spec_replicas`, `kube_pod_status_phase` |
| **node-exporter** | 노드 **하드웨어/OS** | `node_filesystem_avail_bytes`, `node_load1` |

**16.1절의 metrics-server와 혼동하지 말자.** metrics-server는 HPA용으로 최근 값만 제공하고, Prometheus는 장기 저장과 쿼리를 담당한다. **둘 다 필요하다.**

## 31.2 Prometheus 스택

### 설치

```bash
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm install kube-prom prometheus-community/kube-prometheus-stack \
  -n monitoring --create-namespace \
  --values prom-values.yaml
```

**포함되는 것**
- Prometheus Operator (24.5절의 사례)
- Prometheus
- Alertmanager
- Grafana (대시보드 사전 구성)
- node-exporter (DaemonSet)
- kube-state-metrics

```yaml
# prom-values.yaml
prometheus:
  prometheusSpec:
    retention: 15d
    retentionSize: 45GB
    replicas: 2                          # HA
    storageSpec:
      volumeClaimTemplate:
        spec:
          storageClassName: fast-ssd     # 12장
          resources:
            requests:
              storage: 50Gi
    resources:                           # 14장
      requests: { cpu: 500m, memory: 4Gi }
      limits:   { memory: 8Gi }

    # ★ 모든 네임스페이스의 ServiceMonitor를 찾도록
    serviceMonitorSelectorNilUsesHelmValues: false
    podMonitorSelectorNilUsesHelmValues: false
    ruleSelectorNilUsesHelmValues: false

    # 원격 저장소 (장기 보관)
    remoteWrite:
      - url: http://thanos-receive.monitoring:19291/api/v1/receive

grafana:
  adminPassword: changeme
  persistence:
    enabled: true
    size: 10Gi
  sidecar:
    dashboards:
      enabled: true                      # ConfigMap으로 대시보드 추가 가능

alertmanager:
  alertmanagerSpec:
    replicas: 3
    storage:
      volumeClaimTemplate:
        spec:
          resources: { requests: { storage: 10Gi } }
```

> **⚠️ `serviceMonitorSelectorNilUsesHelmValues: false`를 빠뜨리면**
> Prometheus가 Helm 릴리스 라벨이 붙은 ServiceMonitor만 찾는다. 다른 네임스페이스에서 만든 것을 무시해 **"메트릭이 안 잡힌다"는 가장 흔한 문제**가 생긴다.

### 앱 메트릭 노출

**애플리케이션 코드**

```go
import (
    "github.com/prometheus/client_golang/prometheus"
    "github.com/prometheus/client_golang/prometheus/promauto"
    "github.com/prometheus/client_golang/prometheus/promhttp"
)

var (
    httpRequests = promauto.NewCounterVec(
        prometheus.CounterOpts{
            Name: "http_requests_total",
            Help: "Total HTTP requests",
        },
        []string{"method", "path", "status"},
    )
    httpDuration = promauto.NewHistogramVec(
        prometheus.HistogramOpts{
            Name:    "http_request_duration_seconds",
            Help:    "HTTP request latency",
            Buckets: []float64{.005, .01, .025, .05, .1, .25, .5, 1, 2.5, 5, 10},
        },
        []string{"method", "path"},
    )
)

func main() {
    http.Handle("/metrics", promhttp.Handler())
    // ...
}
```

> **⚠️ 라벨 카디널리티**
> 라벨 값의 조합마다 별도 시계열이 생긴다.
> ```go
> // ❌ 카디널리티 폭발
> httpRequests.WithLabelValues(method, r.URL.Path, status)   // /users/12345
>
> // ✅ 경로 템플릿 사용
> httpRequests.WithLabelValues(method, "/users/{id}", status)
> ```
> 사용자 ID, 요청 ID, 타임스탬프를 라벨로 쓰면 Prometheus가 메모리 부족으로 죽는다. **이것이 Prometheus 장애의 1순위 원인이다.**

**히스토그램 버킷**은 SLO 임계값을 포함해야 한다. SLO가 "P99 < 500ms"라면 0.5 버킷이 반드시 있어야 정확히 계산된다.

### ServiceMonitor

24.5절에서 본 Prometheus Operator의 핵심 CRD다.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: webapp
  labels:
    app: webapp
spec:
  selector: { app: webapp }
  ports:
    - name: http
      port: 80
      targetPort: 8080
    - name: metrics          # ★ 이름이 있어야 ServiceMonitor가 참조한다
      port: 9090
      targetPort: 9090
---
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: webapp
  namespace: prod
  labels:
    release: kube-prom       # Prometheus의 selector와 맞춰야 할 수도 있다
spec:
  selector:
    matchLabels: { app: webapp }
  namespaceSelector:
    matchNames: [prod]
  endpoints:
    - port: metrics          # ★ Service의 포트 이름
      path: /metrics
      interval: 30s
      scrapeTimeout: 10s
      # 불필요한 시계열 드롭 (비용 절감)
      metricRelabelings:
        - sourceLabels: [__name__]
          regex: 'go_gc_.*|go_memstats_.*'
          action: drop
```

**PodMonitor**는 Service 없이 Pod를 직접 스크레이프한다. DaemonSet이나 Job에 유용하다.

### 확인

```bash
# 타깃 상태
kubectl port-forward -n monitoring svc/kube-prom-kube-prometheus-prometheus 9090
# http://localhost:9090/targets

# 설정 리로드 확인
kubectl logs -n monitoring prometheus-kube-prom-kube-prometheus-prometheus-0 -c prometheus | tail
```

**타깃이 안 보일 때 확인 순서**

```
① ServiceMonitor가 존재하는가
② Prometheus의 serviceMonitorSelector와 라벨이 맞는가
③ ServiceMonitor의 selector가 Service와 맞는가
④ Service의 포트 이름과 endpoints.port가 일치하는가
⑤ Pod가 실제로 /metrics를 노출하는가
   kubectl exec <pod> -- curl -s localhost:9090/metrics | head
⑥ NetworkPolicy가 Prometheus의 접근을 막고 있는가 (18.4절)
```

### 핵심 쿼리

```promql
# ── 워크로드 ──
# 재시작이 잦은 Pod (6.3절)
increase(kube_pod_container_status_restarts_total[1h]) > 3

# OOMKilled (14.3절)
increase(kube_pod_container_status_last_terminated_reason{reason="OOMKilled"}[1h]) > 0

# 준비되지 않은 Pod (6.1절)
kube_pod_status_ready{condition="false"} == 1

# ── 리소스 (14장) ──
# CPU 사용량 vs requests
sum(rate(container_cpu_usage_seconds_total{container!=""}[5m])) by (namespace, pod)
  / sum(kube_pod_container_resource_requests{resource="cpu"}) by (namespace, pod)

# CPU 스로틀링 비율 (14.3절)
rate(container_cpu_cfs_throttled_periods_total[5m])
  / rate(container_cpu_cfs_periods_total[5m]) > 0.05

# 메모리 사용량 vs limits
container_memory_working_set_bytes{container!=""}
  / on(namespace,pod,container) kube_pod_container_resource_limits{resource="memory"} > 0.9

# 노드 할당률 (14.1절)
sum(kube_pod_container_resource_requests{resource="cpu"}) by (node)
  / sum(kube_node_status_allocatable{resource="cpu"}) by (node)

# ── 컨트롤 플레인 (21.6절) ──
histogram_quantile(0.99, sum(rate(apiserver_request_duration_seconds_bucket[5m])) by (le, verb))
histogram_quantile(0.99, sum(rate(etcd_disk_wal_fsync_duration_seconds_bucket[5m])) by (le))
sum(rate(apiserver_request_total{code=~"5.."}[5m])) / sum(rate(apiserver_request_total[5m]))

# ── 스토리지 (12.7절) ──
kubelet_volume_stats_available_bytes / kubelet_volume_stats_capacity_bytes < 0.15

# ── 오퍼레이터 (27.4절) ──
rate(controller_runtime_reconcile_errors_total[5m]) > 0.1
workqueue_depth > 50
```

### 장기 보관

Prometheus는 로컬 디스크에 저장하고 확장이 제한적이다. 장기 보관과 글로벌 뷰가 필요하면:

| 도구 | 특징 |
|---|---|
| **Thanos** | 사이드카가 오브젝트 스토리지에 블록 업로드. 글로벌 쿼리 |
| **Mimir** (Grafana) | 수평 확장, 멀티 테넌시 |
| **VictoriaMetrics** | 리소스 효율이 높다. 단일 바이너리도 가능 |
| 클라우드 관리형 | AMP(AWS), Google Managed Prometheus, Azure Monitor |

## 31.3 로깅

### 수집 경로

5.3절에서 본 것을 다시 정리한다.

```
컨테이너 stdout/stderr
    ↓ 컨테이너 런타임
/var/log/pods/<ns>_<pod>_<uid>/<container>/0.log
    ↓ 로그 수집기 (DaemonSet, 8.4절)
    ↓ 파싱, 메타데이터 추가(네임스페이스, Pod, 라벨)
중앙 로그 시스템
```

**로그 로테이션**(20.6절)

```yaml
# kubelet 설정
containerLogMaxSize: 10Mi
containerLogMaxFiles: 5
```

**노드 디스크 용량을 계산해야 한다.** 110 Pod × 컨테이너 2개 × 10Mi × 5 = 약 11GB.

### 애플리케이션 로깅 원칙

**① 파일이 아니라 stdout/stderr로**

```go
// ✅ 표준 출력
log.Println("...")

// ❌ 파일 (수집기가 못 읽는다, 볼륨이 필요하다)
f, _ := os.Create("/var/log/app.log")
```

**파일에 써야 하는 레거시 앱**은 5.6절의 사이드카 패턴으로 stdout에 흘려보낸다.

**② 구조화된 JSON**

```json
{
  "ts": "2026-09-01T10:23:11.123Z",
  "level": "error",
  "msg": "payment failed",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "user_id": "u-12345",
  "order_id": "o-98765",
  "error": "connection timeout"
}
```

**`trace_id`가 있으면 트레이스와 로그를 연결할 수 있다**(31.4절).

**③ 적절한 레벨**

```
ERROR  즉시 조치가 필요한 것만
WARN   비정상이지만 처리된 것
INFO   중요한 상태 변화 (시작, 종료, 설정 변경)
DEBUG  개발용 (프로덕션에서는 끈다)
```

> **⚠️ INFO를 요청마다 남기지 마라**
> 초당 1000 요청 × 로그 500바이트 = **일 43GB**. 로그 비용이 인프라 비용을 넘어서는 흔한 원인이다.
>
> 요청 단위 정보는 **메트릭**(집계)과 **트레이스**(샘플링)로 다루고, 로그는 예외 상황에 집중한다.

### 로그 스택 선택

| 스택 | 특징 |
|---|---|
| **Loki** (Grafana) | **라벨만 인덱싱**, 본문은 압축 저장 → 저렴. Grafana 통합 |
| **Elasticsearch (EFK)** | 전문 검색. 강력하지만 운영 부담과 비용이 크다 |
| **OpenSearch** | ES 포크 |
| 클라우드 관리형 | CloudWatch Logs, Cloud Logging, Azure Monitor |

**Loki의 접근이 쿠버네티스와 잘 맞는다.** 라벨(네임스페이스, Pod, 앱)로 좁힌 뒤 본문을 grep하는 방식이라, 전체 텍스트 인덱싱 비용이 없다.

### Loki + Promtail 구성

```bash
helm repo add grafana https://grafana.github.io/helm-charts
helm install loki grafana/loki-stack -n monitoring \
  --set grafana.enabled=false \
  --set promtail.enabled=true
```

**LogQL 예시**

```logql
# 특정 앱의 에러
{namespace="prod", app="webapp"} |= "error"

# JSON 파싱 후 필터
{namespace="prod"} | json | level="error" | user_id="u-12345"

# 에러율 계산 (메트릭으로 변환)
sum(rate({namespace="prod", app="webapp"} | json | level="error" [5m]))

# 트레이스 ID로 전체 서비스의 로그 추적
{namespace="prod"} | json | trace_id="4bf92f3577b34da6a3ce929d0e0e4736"
```

**마지막 쿼리가 강력하다.** 하나의 요청이 여러 서비스를 거친 로그를 한 번에 모은다.

### 비용 통제

```yaml
# Promtail에서 불필요한 로그 드롭
pipeline_stages:
  - json:
      expressions:
        level: level
  - match:
      selector: '{namespace="dev"}'
      stages:
        - drop:
            expression: '.*health.*'      # 헬스체크 로그 제외

  - match:
      selector: '{app="noisy"}'
      stages:
        - drop:
            older_than: 24h
```

**보관 정책**

```
prod 에러/감사:  90일 ~ 1년
prod 일반:      14~30일
staging:        7일
dev:            3일
```

## 31.4 분산 트레이싱

### 왜 필요한가

마이크로서비스에서 "이 요청이 왜 느린가"는 로그만으로 답하기 어렵다.

```
사용자 요청 (총 2.3초)
├─ gateway         (5ms)
│  └─ auth         (12ms)
├─ order-api       (2.2초)  ← 여기가 문제
│  ├─ inventory    (30ms)
│  ├─ payment      (2.1초)  ← 진짜 문제
│  │  └─ external-pg-api (2.0초)  ← 근본 원인
│  └─ db-write     (15ms)
└─ notification    (async)
```

**트레이스가 이 구조를 그대로 보여 준다.**

### OpenTelemetry

**벤더 중립 표준**이다. 계측은 한 번, 백엔드는 자유롭게 교체한다.

```
앱 (OTel SDK)
    ↓ OTLP
OTel Collector (DaemonSet 또는 Deployment)
    ↓ 처리, 배치, 샘플링
백엔드: Jaeger / Tempo / Zipkin / 클라우드 APM
```

**설치**

```bash
helm repo add open-telemetry https://open-telemetry.github.io/opentelemetry-helm-charts
helm install otel-collector open-telemetry/opentelemetry-collector \
  -n monitoring --set mode=daemonset
```

**Collector 설정**

```yaml

  tail_sampling:
    decision_wait: 10s

      - name: errors

        status_code: { status_codes: [ERROR] }
```

> **꼬리 샘플링이 실용의 핵심이다**
> 모든 트레이스를 저장하면 비용이 감당되지 않는다. 앞머리 샘플링(1%)은 문제가 있는 요청을 놓친다.
>
> **꼬리 샘플링은 트레이스가 완료된 뒤 판단한다.** 에러나 느린 요청은 100% 보관하고, 정상 요청은 1%만 남긴다. 문제 진단에 필요한 것을 놓치지 않으면서 비용을 통제한다.

```go
import (
    "go.opentelemetry.io/otel"
    "go.opentelemetry.io/otel/attribute"
    "go.opentelemetry.io/otel/trace"
)

func handleOrder(ctx context.Context, orderID string) error {
    tracer := otel.Tracer("order-service")
    ctx, span := tracer.Start(ctx, "handleOrder",
        trace.WithAttributes(attribute.String("order.id", orderID)))
    defer span.End()

    if err := chargePayment(ctx, orderID); err != nil {
        span.RecordError(err)
        span.SetStatus(codes.Error, err.Error())
        return err
    }
    return nil
}
```

**컨텍스트를 전파하는 것이 핵심이다.** `ctx`를 하위 호출에 계속 넘겨야 스팬이 연결된다.

## 31.5 SLI/SLO와 알림

### 알림 설계의 원칙

> **증상에 알림을 걸고, 원인에 걸지 마라.**

```
❌ 원인 기반
   "CPU 사용률 > 80%"
   → CPU가 높아도 사용자는 아무 문제 없을 수 있다
   → 알림 피로를 만들고, 진짜 문제를 놓치게 한다

✅ 증상 기반
   "에러율 > 1%" 또는 "P99 지연 > 500ms"
   → 사용자가 실제로 겪는 문제
```

**원인 지표는 대시보드에 두고, 알림은 증상에만 건다.**

### SLI 정의

```
가용성 SLI = 성공 요청 수 / 전체 요청 수
지연 SLI   = 500ms 이내 응답 수 / 전체 요청 수
```

```promql
# 가용성
sum(rate(http_requests_total{app="webapp",status!~"5.."}[5m]))
  / sum(rate(http_requests_total{app="webapp"}[5m]))

# 지연 (히스토그램 버킷 활용)
sum(rate(http_request_duration_seconds_bucket{app="webapp",le="0.5"}[5m]))
  / sum(rate(http_request_duration_seconds_count{app="webapp"}[5m]))
```

**레코딩 룰로 미리 계산해 두면** 쿼리가 빨라지고 대시보드가 가벼워진다.

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: webapp-sli
spec:
  groups:
    - name: sli
      interval: 30s
      rules:
        - record: sli:availability:ratio_rate5m
          expr: |
            sum(rate(http_requests_total{app="webapp",status!~"5.."}[5m]))
              / sum(rate(http_requests_total{app="webapp"}[5m]))
        - record: sli:latency:ratio_rate5m
          expr: |
            sum(rate(http_request_duration_seconds_bucket{app="webapp",le="0.5"}[5m]))
              / sum(rate(http_request_duration_seconds_count{app="webapp"}[5m]))
```

### 에러 예산과 번 레이트

```
SLO: 30일간 가용성 99.9%
에러 예산 = 0.1% = 30일 × 0.001 = 43.2분
```

**번 레이트(burn rate)** = 에러 예산을 소진하는 속도

```
번 레이트 1  → 30일에 정확히 예산을 다 쓴다
번 레이트 14.4 → 2일 만에 다 쓴다 (긴급)
번 레이트 6   → 5일 만에 다 쓴다
```

**다중 윈도 번 레이트 알림**이 구글 SRE 북의 권장 방식이다.

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: webapp-slo
spec:
  groups:
    - name: slo
      rules:
        # 빠른 소진 — 즉시 대응 (2% 예산을 1시간에)
        - alert: WebAppErrorBudgetBurnFast
          expr: |
            (1 - sli:availability:ratio_rate5m) > (14.4 * 0.001)
            and
            (1 - sli:availability:ratio_rate1h) > (14.4 * 0.001)
          for: 2m
          labels:
            severity: critical
          annotations:
            summary: "webapp 에러 예산이 빠르게 소진되고 있습니다"
            description: "현재 속도면 2일 안에 30일 예산을 소진합니다"
            runbook_url: "https://wiki.example.com/runbooks/webapp-errors"

        # 느린 소진 — 근무 시간에 대응
        - alert: WebAppErrorBudgetBurnSlow
          expr: |
            (1 - sli:availability:ratio_rate6h) > (6 * 0.001)
            and
            (1 - sli:availability:ratio_rate3d) > (6 * 0.001)
          for: 15m
          labels:
            severity: warning
```

**두 윈도를 `and`로 묶는 이유**: 짧은 윈도만 보면 일시적 스파이크에 알림이 울리고, 긴 윈도만 보면 반응이 느리다. **둘 다 만족할 때만 알림**을 보내 오탐을 줄인다.

### 인프라 알림

증상 기반 원칙을 지키되, 인프라에도 최소한의 알림이 필요하다.

```yaml
groups:
  - name: kubernetes-critical
    rules:
      - alert: NodeNotReady
        expr: kube_node_status_condition{condition="Ready",status="true"} == 0
        for: 10m
        labels: { severity: critical }

      - alert: PodCrashLooping
        expr: |
          rate(kube_pod_container_status_restarts_total[10m]) * 600 > 3
        for: 10m
        labels: { severity: warning }
        annotations:
          summary: "{{$labels.namespace}}/{{$labels.pod}}가 반복 재시작 중"

      - alert: PersistentVolumeFillingUp
        expr: |
          kubelet_volume_stats_available_bytes / kubelet_volume_stats_capacity_bytes < 0.10
        for: 15m
        labels: { severity: critical }

      - alert: EtcdHighFsyncDuration            # 22.5절
        expr: |
          histogram_quantile(0.99,
            rate(etcd_disk_wal_fsync_duration_seconds_bucket[5m])) > 0.5
        for: 10m
        labels: { severity: critical }

      - alert: APIServerHighLatency             # 21.6절
        expr: |
          histogram_quantile(0.99,
            sum(rate(apiserver_request_duration_seconds_bucket{verb!~"WATCH|CONNECT"}[5m]))
            by (le, verb)) > 1
        for: 10m
        labels: { severity: warning }

      - alert: CertificateExpiringSoon          # 21.6절
        expr: |
          (apiserver_client_certificate_expiration_seconds_count > 0)
          and on(job)
          histogram_quantile(0.01,
            sum(rate(apiserver_client_certificate_expiration_seconds_bucket[5m]))
            by (job, le)) < 7*24*3600
        labels: { severity: warning }
```

```yaml
route:
  group_by: [alertname, namespace]
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h

    - matchers: [severity = critical]

      receiver: slack-dev
      repeat_interval: 24h

inhibit_rules:
  # ★ 노드가 죽었으면 그 위의 Pod 알림은 억제
  - source_matchers: [alertname = NodeNotReady]
    target_matchers: [alertname =~ "Pod.*"]
    equal: [node]

receivers:
  - name: pagerduty
    pagerduty_configs:
      - service_key: <key>
  - name: slack-oncall
    slack_configs:
      - api_url: <webhook>
        channel: '#oncall'
        title: '{{ .CommonAnnotations.summary }}'
        text: |
          {{ range .Alerts }}
          *{{ .Labels.alertname }}* ({{ .Labels.severity }})
```

## 31.7 대시보드 설계

### 계층 구조

```
① 서비스 개요 (SLO)          ← 경영진, 온콜의 첫 화면
   가용성, 지연, 에러 예산 잔량, 트래픽

② 서비스 상세 (RED)          ← 온콜의 두 번째 화면
   Rate:     요청률
   Errors:   에러율
   Duration: 지연 분포

③ 리소스 (USE)               ← 원인 분석
   Utilization: 사용률
   Saturation:  포화도 (큐 길이, 스로틀링)
   Errors:      하드웨어/시스템 에러

④ 인프라                     ← 플랫폼 팀
   노드, 컨트롤 플레인, etcd, 네트워크
```

**RED는 서비스(요청 처리)에, USE는 리소스(CPU, 디스크)에 적용한다.**

### 즉시 쓸 수 있는 대시보드

kube-prometheus-stack이 설치하는 것들:

```
Kubernetes / Compute Resources / Cluster
Kubernetes / Compute Resources / Namespace (Workloads)
Kubernetes / Compute Resources / Pod
Kubernetes / Networking / Cluster
Kubernetes / API server
Kubernetes / Kubelet
etcd
Node Exporter / Nodes
```

**14.5절의 리소스 산정**에 `Compute Resources / Pod` 대시보드가 직접 쓰인다.

### 대시보드 작성 팁

- **한 화면에 들어오게** — 스크롤이 필요하면 나눈다
- **단위를 명시** — bytes, seconds, percent
- **임계선 표시** — SLO 목표선을 그래프에 그린다
- **변수 활용** — namespace, pod를 드롭다운으로
- **주석(annotation)** — 배포 시점을 그래프에 표시하면 상관관계가 보인다

```yaml
# Grafana annotation을 배포 시 추가 (30장의 CD 파이프라인에서)
curl -X POST http://grafana/api/annotations \
  -H "Content-Type: application/json" \
  -d '{"text":"deploy webapp v2.4.1","tags":["deploy","webapp"]}'
```

**과제 1 — 라벨 카디널리티 폭발 재현**
요청 경로를 그대로 라벨로 쓰는 앱을 만들고, 랜덤 경로로 요청을 대량 발생시킨다. Prometheus의 `prometheus_tsdb_head_series` 메트릭이 급증하는 것을 관찰하고, 메모리 사용량 변화를 기록한다.

**과제 2 — SLO 알림 구현**
31.5절의 다중 윈도 번 레이트 알림을 실제로 구성한다. 의도적으로 에러를 발생시켜 빠른 소진 알림이 울리는 것을 확인하고, 짧은 스파이크에는 울리지 않는 것도 검증한다.

**과제 3 — 세 신호 연결**
간단한 두 서비스(A → B)를 만들고 OpenTelemetry로 계측한다. 로그에 `trace_id`를 남기고, Grafana에서 트레이스 → 로그로 이동하는 것을 구성한다.

**과제 4 — 감사 로그 분석**
로컬 클러스터에 감사 정책을 적용하고, `kubectl exec`을 실행한 뒤 감사 로그에서 그 기록을 찾는다. 어떤 정보가 남는지(사용자, 시각, 대상, 명령) 확인한다.

**과제 5 — 리소스 산정에 활용**
14.5절의 방법론대로, Prometheus 쿼리로 실제 워크로드의 P50/P95/최대 사용량을 구하고 현재 requests와 비교한다. 조정 후 노드 할당률이 어떻게 변하는지 측정한다.

## 요약

- **메트릭은 무엇이, 트레이스는 어디서, 로그는 왜 잘못됐는지** 알려 준다. 세 신호를 `trace_id`와 exemplar로 연결해야 진단 흐름이 매끄럽다.
- 메트릭 소스는 셋이다. **cAdvisor**(실제 사용량), **kube-state-metrics**(선언된 상태), **node-exporter**(하드웨어). metrics-server(HPA용)와는 별개다.
- **라벨 카디널리티 폭발이 Prometheus 장애의 1순위 원인**이다. 사용자 ID, 요청 ID, 원본 경로를 라벨로 쓰면 안 된다.
- `serviceMonitorSelectorNilUsesHelmValues: false`를 빠뜨리면 다른 네임스페이스의 ServiceMonitor를 무시한다. **"메트릭이 안 잡힌다"의 가장 흔한 원인**이다.
- **로그는 stdout/stderr로, 구조화된 JSON으로, 적절한 레벨로.** 요청마다 INFO를 남기면 로그 비용이 인프라 비용을 넘는다. 요청 단위 정보는 메트릭과 트레이스로 다룬다.
- **Loki는 라벨만 인덱싱**해 전문 검색 비용 없이 쿠버네티스 로그를 다룬다.
- **꼬리 샘플링**이 트레이싱의 실용 열쇠다. 에러와 느린 요청은 100%, 정상은 1%만 보관해 비용과 진단 가치를 함께 확보한다.
- **알림은 증상에, 대시보드는 원인에.** CPU 사용률이 아니라 에러율과 지연에 알림을 건다. **다중 윈도 번 레이트**로 오탐을 줄이고, `inhibit_rules`로 알림 폭풍을 막으며, 모든 알림에 **런북 링크**를 붙인다.
- **이벤트는 1시간만 보관된다.** 이벤트 익스포터로 내보내야 장애 후 분석이 가능하다. **감사 로그**는 규제 대응과 침해 탐지에 필수다.

**다음 장에서는** 이 관측성 위에서 클러스터를 운영한다. 고가용성 설계, 무중단 업그레이드, 백업과 재해 복구, 그리고 이 책 전체를 관통하는 트러블슈팅 플레이북을 정리한다.
