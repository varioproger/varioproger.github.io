# 48장. 동기화와 잠금

> **이 장의 위치** — Part IX「동시성과 비동기」의 네 번째 장이다. 45장에서 "공유 상태는 위험하다"고 경고하고, 46·47장에서 `Task`와 `async`/`await`로 **스레드를 막지 않는 법**을 배웠다. 그런데 아무리 잘 설계해도 둘 이상의 실행 흐름이 같은 메모리를 만지는 지점은 남는다. 이 장은 그 지점에서 무슨 일이 벌어지는지 — 원자성·가시성·재배치라는 세 가지 축으로 — 끝까지 파고, .NET이 제공하는 동기화 도구 전부를 비용 순서로 배치한다.
>
> **선수 지식** — 45장(스레드의 기초), 46장(스레드 풀과 태스크), 15장(`object` 타입과 박싱), 27장(이벤트)
>
> **이 장에서 다루지 않는 것** — `Task`의 생성·합성·취소는 46장에서, `async`/`await`의 상태 기계와 `ConfigureAwait`는 47장에서 이미 다뤘다. 신호(`AutoResetEvent`·`ManualResetEvent`·`CountdownEvent`·`Barrier`)와 조건 변수 패턴, 스레드 로컬 상태는 49장에서, `Parallel`·PLINQ와 동시성 컬렉션의 사용법은 50장에서, `ConcurrentDictionary`의 내부 구조는 24.12절에서 다룬다. 캐시 라인과 거짓 공유(false sharing)의 최적화 심화는 61.4절과 70.6절에 있다.

## 48.1 동기화 개요 — 무엇을 왜 동기화하는가

### 동기화가 필요한 정확한 조건

스레드 동기화(thread synchronization)는 **여러 스레드가 같은 데이터를 동시에 건드릴 때 데이터가 깨지는 것을 막는 일**이다. 여기서 "동시에"가 핵심이다. 두 스레드가 같은 데이터를 만지더라도 물리적으로 같은 시점에 만질 수 없다면 동기화는 전혀 필요 없다.

동기화가 필요한 조건은 정확히 두 가지가 **모두** 성립할 때다.

1. **둘 이상의 실행 흐름이 같은 상태에 접근한다.**
2. **그중 최소 하나가 그 상태에 쓴다.**

둘 중 하나라도 빠지면 동기화는 불필요하다. 상태가 스레드마다 따로 있으면(1번 탈락) 경합할 것이 없다. 모두가 읽기만 하면(2번 탈락) 값이 변하지 않으므로 누가 언제 읽든 같은 값을 본다. 이 두 문장이 이 장 전체의 뿌리다. 실무에서 동기화 문제를 푸는 가장 좋은 방법은 잠금을 잘 거는 것이 아니라 **1번이나 2번을 성립하지 않게 설계를 바꾸는 것**이다.

47장에서 본 `async` 메서드 안의 지역 상태가 좋은 예다. `async` 메서드의 서로 다른 구간을 서로 다른 스레드가 실행할 수 있지만(47.7절의 상태 기계), 그 구간들은 **절대 동시에 실행되지 않도록** 구현되어 있다. 따라서 `async` 메서드 안에 갇힌 데이터에는 동기화가 필요 없다.

### 데이터 경합과 경합 조건

용어를 구분하자.

| 용어 | 정의 | 예 |
|---|---|---|
| **데이터 경합(data race)** | 두 스레드가 동기화 없이 같은 메모리 위치에 접근하고, 최소 하나가 쓰기다 | 두 스레드가 `_counter++` 를 잠금 없이 실행 |
| **경합 조건(race condition)** | 결과가 스레드들의 상대적 타이밍에 의존한다 | 두 스레드가 각각 `if (!_done) { … ; _done = true; }` 실행 |
| **찢긴 읽기(torn read)** | 한 변수의 값을 절반만 갱신된 상태로 읽는다 | 32비트 프로세스에서 `long` 필드를 잠금 없이 읽기 |

데이터 경합은 언어·런타임 수준에서 **정의되지 않은 동작**에 가까운 사고다. 경합 조건은 개별 연산이 모두 원자적이더라도 **연산의 조합**이 원자적이지 않아서 생긴다. 데이터 경합을 다 없애도 경합 조건은 남을 수 있다 — 48.7절에서 이 구분이 다시 중요해진다.

가장 흔한 예를 보자.

```csharp
class ThreadUnsafe
{
    static bool _done;

    static void Go()
    {
        if (!_done) { Console.WriteLine("Done"); _done = true; }
    }
}
```

두 스레드가 `Go`를 동시에 부르면 `"Done"`이 두 번 출력될 수 있다. 한 스레드가 `if` 를 평가하는 바로 그 순간에 다른 스레드가 아직 `_done = true` 에 도달하지 않았을 수 있기 때문이다.

이보다 더 미묘한 예도 있다.

```csharp
class ThreadUnsafe
{
    static int _val1 = 1, _val2 = 1;

    static void Go()
    {
        if (_val2 != 0) Console.WriteLine(_val1 / _val2);
        _val2 = 0;
    }
}
```

두 스레드가 `Go`를 동시에 부르면 **0으로 나누기 오류**가 날 수 있다. 한 스레드가 `if (_val2 != 0)` 를 통과한 직후 `Console.WriteLine`에 진입하기 전에, 다른 스레드가 `_val2 = 0` 을 실행할 수 있다.

> **⚠️ 재현되지 않는 버그가 기본값이다**
>
> 이런 코드는 개발 환경에서 몇 달 동안 한 번도 안 터지고, 부하가 걸린 운영 서버에서 하루에 몇 번씩 터진다. CPU 코어가 많을수록, 부하가 클수록 확률이 올라간다. 그래서 동시성 코드는 **가능한 한 많은 코어를 가진 머신에서 스트레스 테스트**해야 한다. 디버거를 붙이면 JIT이 최적화를 끄고 타이밍이 완전히 달라지므로, 디버거 아래에서 재현되지 않는다는 사실은 아무 증거도 되지 못한다.

### 동기화가 비싼 세 가지 이유

동기화는 필요악이다. Richter가 정리한 세 가지 문제를 그대로 옮긴다.

**첫째, 지루하고 실수하기 쉽다.** 여러 스레드가 동시에 만질 수 있는 데이터를 **전부** 찾아내서 그 주변을 잠금으로 감싸야 한다. 한 군데라도 빠뜨리면 데이터가 깨진다. 그리고 잠금 코드를 전부 올바르게 넣었다는 것을 증명할 방법이 없다. 실행해 보고, 스트레스 테스트하고, 아무 일도 없기를 바라는 수밖에 없다.

**둘째, 성능을 해친다.** 잠금을 획득하고 해제하는 데 시간이 든다. 메서드 호출이 추가되고, 어느 스레드가 먼저 잠금을 얻을지 CPU들이 서로 조율해야 한다. 이 조율 자체가 비싸다.

```csharp
// 잠금이 없을 때 — 참조 대입 두 번, 극도로 빠르다
public sealed class LinkedList
{
    private Node _head;
    public void Add(Node newNode) { newNode.Next = _head; _head = newNode; }
}
```

여기에 잠금을 넣으면 스레드 안전해지지만 몇 배 느려진다. 어떤 잠금을 쓰든 그렇다.

**셋째, 한 번에 한 스레드만 들여보낸다.** 이건 잠금의 존재 이유지만 동시에 문제이기도 하다. 스레드가 막히면 스레드 풀은 CPU를 놀리지 않으려고 새 스레드를 만든다(46.2절의 스레드 주입). 스레드 생성은 메모리와 시간을 크게 쓴다(45.4절). 게다가 막혔던 스레드가 깨어나면 이제 코어 수보다 많은 스레드가 돌게 되어 컨텍스트 스위치가 늘어난다.

> **💡 동기화를 없애는 네 가지 설계**
>
> 잠금을 잘 쓰는 법보다 잠금이 필요 없게 만드는 법이 먼저다.
>
> 1. **공유하지 마라.** 정적 필드를 피한다. `new`로 만든 객체의 참조를 다른 스레드에 넘기지 않으면 그 객체에는 동기화가 필요 없다.
> 2. **값 타입을 써라.** 값 타입은 복사되므로 각 스레드가 자기 복사본을 다룬다(16장).
> 3. **읽기 전용으로 만들어라.** 초기화 후 아무도 쓰지 않는 데이터는 몇 개의 스레드가 동시에 읽어도 안전하다. `string`이 대표적이다 — 불변이므로 여러 스레드가 하나의 `String` 객체를 동시에 봐도 깨질 수가 없다.
> 4. **불변 객체로 상태를 묶어라.** 여러 필드를 하나의 불변 객체로 묶으면 참조 대입 한 번이 곧 원자적 갱신이 된다(48.14절).

### 동기화 도구 분류

.NET이 제공하는 도구는 네 갈래다.

| 갈래 | 하는 일 | 대표 도구 | 이 책의 위치 |
|---|---|---|---|
| **단순 블로킹** | 다른 스레드나 시간을 그냥 기다린다 | `Thread.Join`, `Thread.Sleep`, `Task.Wait` | 45.2절, 46장 |
| **잠금(배타·비배타)** | 임계 구역에 들어올 수 있는 스레드 수를 제한한다 | `lock`(`Monitor`), `Mutex`, `SpinLock`, `Semaphore(Slim)`, `ReaderWriterLockSlim` | 이 장 48.5~48.12 |
| **신호** | 한 스레드가 다른 스레드에게 "이제 됐다"고 알린다 | `ManualResetEvent(Slim)`, `AutoResetEvent`, `CountdownEvent`, `Barrier` | 49장 |
| **비블로킹** | 스레드를 절대 막지 않고 원자성·순서를 확보한다 | `Interlocked`, `volatile`, `Volatile`, `Thread.MemoryBarrier` | 이 장 48.2~48.4 |

잠금과 신호는 다시 **사용자 모드 / 커널 모드 / 하이브리드** 로 나뉜다. 이 구분이 성능의 거의 전부를 설명한다.

| 구분 | 구현 위치 | 무경합 비용 | 경합 시 동작 | 예 |
|---|---|---|---|---|
| **사용자 모드(primitive user-mode)** | 특수 CPU 명령 | 매우 낮음 | 스핀 — CPU를 태운다 | `Interlocked`, `Volatile`, `SpinLock` |
| **커널 모드(primitive kernel-mode)** | OS 커널 객체 | 매우 높음(모드 전환) | 블록 — CPU를 놓는다 | `Mutex`, `Semaphore`, `AutoResetEvent`, `ManualResetEvent` |
| **하이브리드(hybrid)** | 둘의 조합 | 낮음 | 잠깐 스핀 후 블록 | `Monitor`(`lock`), `SemaphoreSlim`, `ManualResetEventSlim`, `ReaderWriterLockSlim`, `CountdownEvent` |

하이브리드가 이기는 이유는 통계다. 대부분의 애플리케이션에서 **둘 이상의 스레드가 정확히 같은 시점에 같은 데이터를 만지려는 일은 드물다.** 그러니 경합이 없는 절대다수의 경우에는 사용자 모드처럼 빠르게 지나가고, 드물게 경합이 나면 커널에 들어가 블록한다. 어차피 그 스레드는 멈춰야 하므로 그때의 느림은 문제가 되지 않는다.

> **📌 라이브락과 데드락 중 무엇이 나은가**
>
> 잠금을 쥔 스레드가 영영 놓지 않으면 기다리는 스레드는 영영 못 간다. 그것이 **사용자 모드 구조**라면 그 스레드는 CPU를 계속 태우며 돈다 — 이것을 **라이브락(livelock)** 이라 부른다. **커널 모드 구조**라면 스레드는 블록된 채 멈춰 있다 — 이것이 **데드락(deadlock)** 이다.
>
> 둘 다 나쁘지만 **데드락이 항상 라이브락보다 낫다.** 라이브락은 CPU 시간과 메모리(스레드 스택)를 둘 다 낭비하고, 데드락은 메모리만 낭비한다. 게다가 데드락은 덤프에서 읽어내기가 훨씬 쉽다(48.8절).

### 이 장을 읽는 순서

48.2~48.4는 **잠금 없이** 정확성을 얻는 층이다. 여기를 이해하지 못하면 48.5 이후의 잠금이 왜 그렇게 생겼는지 설명이 되지 않는다. 48.5~48.9는 `lock`/`Monitor`를 문법에서 덤프 분석까지 관통하고, 48.10~48.12는 나머지 잠금 도구를 비용 순서로 배치한다. 48.13~48.15는 자주 틀리는 관용구 하나(이중 검사 잠금), 타입 수준의 계약(스레드 안전성), 그리고 .NET 9의 새 타입(`System.Threading.Lock`)이다.

## 48.2 원자성·가시성·재배치 — .NET 메모리 모델

동시성 버그의 원인은 세 가지밖에 없다. **원자성(atomicity)**, **가시성(visibility)**, **재배치(reordering)** 다. 이 절은 세 가지를 하나씩 정의하고, 그 위에 .NET의 메모리 모델을 얹는다.

### 원자성 — 어떤 연산이 쪼개지지 않는가

**원자적(atomic)** 이라는 말은 그 연산이 하드웨어에서 **나눌 수 없이** 실행된다는 뜻이다. 다른 스레드가 중간 상태를 볼 수 없다.

CLR은 다음 타입의 변수에 대한 **읽기와 쓰기가 원자적**임을 보장한다.

| 원자적 | 원자적이지 않음(32비트에서) |
|---|---|
| `bool`, `char`, `sbyte`/`byte`, `short`/`ushort` | `long`/`ulong` |
| `int`/`uint`, `nint`/`nuint`(`IntPtr`/`UIntPtr`) | `double` |
| `float`, 모든 참조 타입 | `decimal`(항상 아님 — 16바이트) |

정확한 규칙은 **"워드 크기 이하이고 자연 정렬된 읽기·쓰기는 원자적"** 이다. 32비트 프로세스에서 워드는 4바이트이므로 `long`은 여기서 벗어난다.

```csharp
static class SomeType
{
    public static int X;
}

// 이 대입은 원자적이다
SomeType.X = 0x01234567;
```

`X`는 `0x00000000`에서 `0x01234567`로 **한 번에** 바뀐다. 다른 스레드가 `0x01230000` 같은 중간 값을 볼 가능성은 없다.

`X`가 `long`이라면 이야기가 달라진다.

```csharp
static class SomeType
{
    public static long X;   // 32비트 프로세스에서는 원자적이지 않다
}

SomeType.X = 0x0123456789abcdef;
```

32비트 프로세스에서 이 대입은 4바이트 저장 두 번으로 컴파일된다. 다른 스레드가 그 사이에 읽으면 `0x0123456700000000` 이나 `0x0000000089abcdef` 를 얻을 수 있다. 이것이 **찢긴 읽기(torn read)** 다.

> **⚠️ "64비트니까 괜찮다"가 위험한 이유**
>
> x64 프로세스에서 정렬된 `long` 읽기·쓰기는 원자적이다. 그래서 x64에서만 테스트하면 이 버그는 절대 안 나온다. 그런데 같은 코드가 32비트 프로세스(레거시 데스크톱 앱, 32비트 IIS 워커, 일부 임베디드 타깃)에서 돌면 조용히 깨진다.
>
> 게다가 **정렬**이 깨지면 64비트에서도 원자성이 사라질 수 있다. `[StructLayout(LayoutKind.Explicit)]`로 필드를 8바이트 경계에서 어긋나게 배치하면(54.4절) 그 필드의 읽기·쓰기는 더 이상 원자적이라는 보장이 없다.
>
> **판단 기준은 간단하다.** `long`/`double`을 여러 스레드가 공유한다면 크기와 무관하게 `Interlocked`를 써라(48.4절).

### `i++`는 왜 원자적이 아닌가

가장 자주 오해받는 지점이다. `i++`는 한 글자짜리 연산처럼 생겼지만 **세 개의 연산**이다.

```csharp
static int _counter;

static void Increment() => _counter++;
```

컴파일 결과를 보면 명확하다.

```il
.method private hidebysig static void Increment() cil managed
{
  .maxstack  8
  IL_0000:  ldsfld     int32 Program::_counter   // 1. 읽는다
  IL_0005:  ldc.i4.1
  IL_0006:  add                                  // 2. 더한다
  IL_0007:  stsfld     int32 Program::_counter   // 3. 쓴다
  IL_000c:  ret
}
```

읽기와 쓰기가 각각 원자적이라 해도 **세 개를 묶은 것**은 원자적이지 않다. 두 스레드가 동시에 `_counter++`를 1,000,000번씩 실행하면 결과는 2,000,000이 아니라 그보다 작은, 실행할 때마다 달라지는 수가 나온다.

```text
  스레드 A                      _counter      스레드 B
  ─────────────                 ────────      ─────────────
  ldsfld  → 7                      7
                                   7          ldsfld  → 7
  add     → 8                      7
                                   7          add     → 8
  stsfld  ← 8                      8
                                   8          stsfld  ← 8
                                   ↑
                          증가 두 번이 한 번이 되었다
```

같은 이유로 `x += 1`, `x = x + 1`, `x *= 2`, `list.Count++`, `_flags |= Flag.A` 는 전부 원자적이지 않다.

> **📌 원자적 읽기·쓰기가 보장하는 것과 보장하지 않는 것**
>
> 원자성은 **값이 찢기지 않음**만 보장한다. 그 읽기·쓰기가 **언제** 일어나는지는 전혀 보장하지 않는다. 원자적인 `int` 쓰기도 CPU 레지스터에 캐시되어 다른 스레드에게 몇 밀리초 동안 안 보일 수 있고, 앞뒤 문장과 순서가 바뀔 수 있다. 이것이 다음 두 절의 주제다.

### 가시성 — 쓴 값이 언제 보이는가

한 스레드가 쓴 값이 다른 스레드에게 **언제** 보이는가? 답은 "보장이 없다"이다.

현대 CPU에서 코어는 메인 메모리를 직접 만지지 않는다. 각 코어는 자기 L1/L2 캐시를 갖고, 쓰기는 우선 **스토어 버퍼(store buffer)** 에 쌓였다가 나중에 캐시로, 캐시에서 다시 다른 코어로 전파된다(61.4절). 캐시 일관성 프로토콜이 결국은 값을 전파하지만 "결국"이 언제인지는 정해져 있지 않다.

그 위에 소프트웨어 계층이 하나 더 있다. C# 컴파일러와 JIT은 **필드를 CPU 레지스터에 캐시**할 수 있다. 이건 캐시 일관성 프로토콜이 도달하지 못하는 영역이다. 레지스터에 든 값은 다른 코어가 무슨 짓을 해도 갱신되지 않는다.

Richter의 고전적인 예다.

```csharp
static class StrangeBehavior
{
    // 나중에 볼 것처럼, 이 필드를 volatile로 표시하면 문제가 사라진다
    private static bool _stopWorker = false;

    public static void Main()
    {
        Thread t = new Thread(Worker);
        t.Start();
        Thread.Sleep(5000);
        _stopWorker = true;
        t.Join();                 // 워커가 멈추기를 기다린다
    }

    private static void Worker(object o)
    {
        int x = 0;
        while (!_stopWorker) x++;
        Console.WriteLine("Worker: x={0} 에서 멈췄다", x);
    }
}
```

`Worker`를 컴파일할 때 컴파일러는 이렇게 볼 수 있다. "`_stopWorker`는 이 메서드 안에서 절대 바뀌지 않는다. 그러니 루프 밖에서 한 번만 읽으면 된다." 그 결과 `_stopWorker`가 `false`면 **영원히 도는 루프**가 만들어진다. 루프의 매 반복에서 필드를 다시 읽지 않기 때문이다.

> **📌 이 예제가 실제로 멈추지 않게 하려면**
>
> Richter의 원문은 이 프로그램을 .NET Framework에서 `/platform:x86 /optimize+`로 컴파일하고 **디버거 없이** 실행하면 영원히 돈다고 적는다. x86 JIT이 x64 JIT보다 성숙해서 더 공격적으로 최적화했기 때문이다. 즉 **같은 소스가 플랫폼과 JIT 버전에 따라 다르게 동작한다.**
>
> 이건 안심의 근거가 아니라 공포의 근거다. "내 머신에서는 잘 돌았다"는 정보가 0에 수렴한다는 뜻이기 때문이다. 최신 RyuJIT에서 이 루프가 어떻게 처리되는지는 JIT 버전과 대상 아키텍처에 따라 다르며, **어느 쪽이든 언어 규칙상 허용된 최적화**다.

### 재배치 — 순서가 바뀐다

컴파일러, JIT, CPU 셋 다 명령의 순서를 바꿀 수 있다. 규칙은 하나뿐이다. **단일 스레드 관점에서 프로그램의 의도가 보존되면 된다.** 다중 스레드 관점은 이 규칙에 포함되지 않는다.

```csharp
sealed class ThreadsSharingData
{
    private int _flag = 0;
    private int _value = 0;

    // 한 스레드가 실행한다
    public void Thread1()
    {
        // 주의: 이 두 줄은 순서가 뒤바뀔 수 있다
        _value = 5;
        _flag = 1;
    }

    // 다른 스레드가 실행한다
    public void Thread2()
    {
        // 주의: _value가 _flag보다 먼저 읽힐 수 있다
        if (_flag == 1)
            Console.WriteLine(_value);
    }
}
```

`Thread2`가 `0`을 출력할 수 있다. 경로가 두 개다.

**경로 1 — 쓰기 재배치.** `Thread1`의 두 줄이 뒤집혀 `_flag = 1`이 먼저 실행된다. 단일 스레드 관점에서는 아무 차이가 없으므로 허용된다. 그 사이에 `Thread2`가 `_flag == 1`을 보고 아직 `0`인 `_value`를 출력한다.

**경로 2 — 읽기 재배치.** `Thread1`은 프로그램 순서대로 실행되었지만, `Thread2`를 컴파일할 때 `_value`를 `_flag`보다 먼저 레지스터로 읽어 두었다. 그 시점의 `_value`는 `0`이다. 그 뒤 `Thread1`이 두 필드를 모두 바꾸고, `Thread2`가 `_flag`를 읽어 `1`을 보고, 레지스터에 든 낡은 `0`을 출력한다.

```text
  ── 프로그램 순서 (소스가 말하는 것) ──────────────────
     Thread1:  _value = 5   →   _flag = 1
     Thread2:  read _flag   →   read _value

  ── 실제로 허용되는 실행 중 하나 ─────────────────────
     Thread1:  _flag = 1    →   _value = 5
     Thread2:  read _value(0) → read _flag(1) → print 0
                 ↑
       "단일 스레드 관점에서 의도가 보존됨"만 지키면 합법
```

> **⚠️ 릴리스 빌드에서만 터진다**
>
> 재배치로 인한 버그는 디버그 빌드에서 거의 안 나온다. 디버그 빌드는 최적화를 끄고, 디버거를 붙이면 JIT이 단계 실행하기 쉬운 코드를 만든다. **릴리스 빌드에서만, 부하가 있을 때만, 특정 CPU에서만** 터지는 것이 이 부류 버그의 특징이다.

### ECMA 메모리 모델 · x86 실제 동작 · ARM의 약한 모델

여기서 반드시 구분해야 할 세 층이 있다.

| 층 | 무엇을 정하는가 | 실무적 함의 |
|---|---|---|
| **ECMA-335 명세** | 이식 가능한 프로그램이 **의존해도 되는 최소 보장** | 여기에 없는 것에 기대면 다른 런타임·아키텍처에서 깨진다 |
| **특정 CLR 구현** | 그 런타임이 실제로 제공하는 보장(명세보다 강할 수 있다) | 지금 이 머신에서 통과하는 이유일 뿐, 계약이 아니다 |
| **CPU 아키텍처** | 하드웨어가 실제로 허용하는 재배치 | x86/x64와 ARM64가 극적으로 다르다 |

ECMA-335는 `volatile`로 표시된 접근에 **획득/해제 의미론**을 부여하고, 그 외의 일반 읽기·쓰기는 자유롭게 재배치될 수 있게 둔다. Microsoft CLR의 x86/x64 구현은 하드웨어 특성 때문에 명세보다 강한 보장을 실제로 제공해 왔다. 문제는 **그 강한 보장에 기대어 쓴 코드가 명세상으로는 틀린 코드**라는 것이다.

CPU 층의 차이는 결정적이다.

| 아키텍처 | 메모리 순서 모델 | 실무 결과 |
|---|---|---|
| **x86 / x64** | 강한 순서(TSO). 저장끼리, 적재끼리는 재배치되지 않는다. **저장 후 적재**만 재배치될 수 있다 | 재배치 버그의 상당수가 겉으로 드러나지 않는다 |
| **ARM64 / ARM32** | 약한 순서. 저장끼리도, 적재끼리도 재배치될 수 있다 | 같은 코드가 조용히 깨진다 |
| **역사적 예** | 2006년 Apple 컴퓨터의 PowerPC 등 일부 아키텍처는 x86이 제공하던 강한 순서 보장을 포기하고 명시적 메모리 배리어를 요구했다 | 이 문제는 새로운 것이 아니다 |

> **⚠️ x86에서만 테스트하면 버그가 숨는다**
>
> 이건 2020년대에 훨씬 중요해진 경고다. Apple Silicon(M 시리즈) 개발 머신, AWS Graviton·Azure Ampere 같은 ARM64 서버, Windows on ARM이 모두 일상이 되었다. **x64 개발 머신에서 몇 년간 멀쩡했던 코드가 ARM64 프로덕션으로 옮기는 순간 재현 불가능한 데이터 손상을 일으키는 사고**가 실제로 일어난다.
>
> 판단 기준은 이렇다. **"x86이 이 재배치를 막아 주니까"에 의존하는 코드는 틀린 코드다.** 정확한 코드는 배리어를 명시적으로 요구한다. 대상 아키텍처가 하나라도 ARM64를 포함한다면 이 원칙에 예외를 두지 마라.

### 획득/해제 의미론

메모리 배리어(memory barrier), 또는 펜스(fence)는 **재배치와 캐싱의 효과가 통과할 수 없는 담장**이다. 세 종류가 있다.

| 종류 | 의미 | .NET에서 |
|---|---|---|
| **획득 펜스(acquire fence)** | 펜스 **뒤**의 읽기·쓰기가 펜스 앞으로 옮겨 갈 수 없다 | `Volatile.Read`, `volatile` 필드 읽기, 잠금 획득 |
| **해제 펜스(release fence)** | 펜스 **앞**의 읽기·쓰기가 펜스 뒤로 옮겨 갈 수 없다 | `Volatile.Write`, `volatile` 필드 쓰기, 잠금 해제 |
| **전체 펜스(full fence)** | 양방향 모두 막는다 | `Thread.MemoryBarrier`, 모든 `Interlocked` 메서드, 모든 커널 모드 구조의 메서드 호출 |

두 개를 결합하면 규칙이 하나로 요약된다.

> **💡 스레드가 공유 메모리로 대화할 때의 한 줄 규칙**
>
> **마지막 값은 `Volatile.Write`로 쓰고, 첫 값은 `Volatile.Read`로 읽어라.**
>
> `Thread1`은 여러 필드를 쓴 뒤 마지막에 플래그를 `Volatile.Write`로 쓴다. 해제 펜스가 앞선 모든 쓰기를 먼저 완료시킨다. `Thread2`는 플래그를 `Volatile.Read`로 먼저 읽는다. 획득 펜스가 뒤따르는 모든 읽기를 그 뒤로 밀어낸다. 이 짝이 성립하면 `Thread2`가 플래그의 새 값을 봤을 때 앞선 쓰기들도 반드시 보인다.

앞의 `ThreadsSharingData`를 이 규칙으로 고치면 이렇게 된다.

```csharp
sealed class ThreadsSharingData
{
    private int _flag = 0;
    private int _value = 0;

    public void Thread1()
    {
        // _flag에 1이 쓰이기 전에 _value에 5가 반드시 쓰인다
        _value = 5;
        Volatile.Write(ref _flag, 1);
    }

    public void Thread2()
    {
        // _flag를 읽은 뒤에 _value를 읽는다
        if (Volatile.Read(ref _flag) == 1)
            Console.WriteLine(_value);
    }
}
```

이제 `0`이 출력될 수 없다. 왜 그런지 한 번 더 정리하자.

- `Thread1`의 `Volatile.Write` 호출은 **그 앞의 모든 쓰기가 완료된 뒤** `_flag`에 1이 쓰이도록 강제한다. `Volatile.Write` 앞에 쓰기가 열 개 있었다면 그 열 개끼리는 여전히 순서가 뒤바뀔 수 있다. 다만 **전부가 `_flag` 쓰기보다 먼저** 끝난다.
- `Thread2`의 `Volatile.Read` 호출은 **그 뒤의 모든 읽기가 `_flag` 읽기 이후에 시작**되도록 강제한다. `Volatile.Read` 뒤에 읽기가 열 개 있으면 그 열 개끼리는 순서가 뒤바뀔 수 있지만, **전부가 `_flag` 읽기 이후에** 시작된다.

> **📌 잠금은 왜 이 문제를 자동으로 해결하는가**
>
> `lock` 블록에 들어갈 때 획득 펜스가, 나올 때 해제 펜스가 생긴다. 그래서 **같은 잠금 안에서만 읽고 쓰는 데이터**에는 원자성·가시성·재배치 문제가 모두 사라진다. 이것이 잠금이 비싸도 압도적으로 많이 쓰이는 이유다. 세 가지 문제를 한 번에 없애 준다.
>
> 이 성질은 잠금만의 것이 아니다. **모든 동기화 구조**가 펜스를 만든다. 신호 구조로 한 시점에 한 스레드만 변수에 접근하도록 보장했다면 그 변수에는 잠금이 필요 없다.
>
> ```csharp
> var signal = new ManualResetEvent(false);
> int x = 0;
> new Thread(() => { x++; signal.Set(); }).Start();
> signal.WaitOne();
> Console.WriteLine(x);   // 항상 1
> ```

## 48.3 `volatile`, `Volatile` 클래스, 메모리 배리어

### 문법 — `volatile` 키워드

`Volatile.Read`/`Volatile.Write`를 매번 올바른 자리에 부르는 것은 사람에게 어려운 일이다. 그래서 C#은 필드 한정자 `volatile`을 제공한다.

```csharp
sealed class ThreadsSharingData
{
    private volatile int _flag = 0;   // 이 필드의 모든 접근이 volatile이 된다
    private int _value = 0;

    public void Thread1()
    {
        _value = 5;
        _flag = 1;        // 컴파일러가 Volatile.Write와 같은 코드를 만든다
    }

    public void Thread2()
    {
        if (_flag == 1)   // 컴파일러가 Volatile.Read와 같은 코드를 만든다
            Console.WriteLine(_value);
    }
}
```

`volatile`을 붙일 수 있는 타입은 제한적이다.

붙일 수 있는 것은 `bool`, `char`, `sbyte`/`byte`, `short`/`ushort`, `int`/`uint`, `nint`/`nuint`, `float`, 모든 참조 타입, 그리고 기반 타입이 위 정수형 중 하나인 `enum`이다. `class` 제약이 붙은 제네릭 타입 매개변수에도 붙일 수 있다. 반면 `long`/`ulong`, `double`, `decimal`, 구조체에는 붙일 수 없고, 지역 변수와 매개변수에도 붙일 수 없다.

원자성이 보장되지 않는 타입에는 `volatile`을 붙일 수 없다는 규칙이다. 즉 `volatile long`은 컴파일 오류다. 이건 언어가 **"`volatile`은 원자성을 만들어 주지 않는다"** 는 사실을 문법으로 강제하는 것이다.

### 컴파일 결과 — JIT이 무엇을 하는가

`volatile` 필드는 IL 메타데이터에 `modreq(System.Runtime.CompilerServices.IsVolatile)` 로 표시된다.

```il
.field private int32 modreq([System.Runtime]System.Runtime.CompilerServices.IsVolatile) _flag
```

그리고 그 필드를 읽고 쓰는 IL에는 `volatile.` 접두사가 붙는다.

```il
IL_0007:  ldarg.0
IL_0008:  ldc.i4.1
IL_0009:  volatile.
IL_000b:  stfld      int32 ThreadsSharingData::_flag
```

JIT은 `volatile.` 접두사를 보고 두 가지를 한다.

1. **그 필드를 CPU 레지스터에 캐시하지 않는다.** 읽을 때마다 실제로 메모리에서 읽고, 쓸 때마다 실제로 메모리에 쓴다.
2. **적절한 하드웨어 펜스를 삽입한다.** x86/x64에서는 하드웨어가 이미 대부분의 순서를 보장하므로 추가 명령이 거의 나오지 않는다. ARM64에서는 `ldar`/`stlr` 같은 획득/해제 명령이 실제로 나온다.

> **📌 x64에서 `volatile`이 "공짜"로 보이는 이유**
>
> x64 디스어셈블리를 보면 `volatile int` 읽기가 평범한 `mov`로 나온다. 그래서 "`volatile`은 x64에서 아무것도 안 한다"고 오해하기 쉽다. 틀렸다. `volatile`은 여전히 **JIT이 그 접근을 최적화로 제거하거나 레지스터로 승격하지 못하게** 막는다. 하드웨어 펜스가 필요 없을 뿐 컴파일러 펜스는 그대로 살아 있다.

### `volatile`이 보장하지 않는 세 가지

`volatile`을 둘러싼 오해가 유난히 많다. 하나씩 정리하자.

**첫째, `volatile`은 원자성을 만들지 않는다.**

```csharp
private volatile int _counter;

public void Bump() => _counter++;   // 여전히 스레드 안전하지 않다
```

`_counter++`는 여전히 읽기-수정-쓰기 세 연산이다. `volatile`은 그 세 연산이 각각 메모리에 도달하도록 만들 뿐, 하나로 묶어 주지 않는다. **증가는 `Interlocked.Increment`로만 안전해진다.**

**둘째, 두 `volatile` 연산 사이의 재배치는 여전히 가능하다.**

`volatile` 쓰기는 **해제** 펜스, `volatile` 읽기는 **획득** 펜스다. 각각 반쪽만 막는다. 그래서 다음은 여전히 뒤바뀔 수 있다.

```csharp
private volatile bool _a, _b;

void M()
{
    _a = true;              // volatile 쓰기 (해제 펜스: 앞의 것이 뒤로 못 감)
    bool local = _b;        // volatile 읽기 (획득 펜스: 뒤의 것이 앞으로 못 감)
    // ↑ 이 "쓰기 다음 읽기" 순서는 보장되지 않는다
}
```

해제 펜스는 뒤에 오는 읽기가 앞으로 넘어오는 것을 막지 않고, 획득 펜스는 앞에 있는 쓰기가 뒤로 밀리는 것을 막지 않는다. 저장-적재(store-load) 재배치는 x86/x64 하드웨어에서도 유일하게 허용되는 재배치다. 이 순서까지 막으려면 **전체 펜스**가 필요하다.

```csharp
void M()
{
    _a = true;
    Thread.MemoryBarrier();   // 전체 펜스
    bool local = _b;          // 이제 순서가 보장된다
}
```

이것이 Dekker 알고리즘 같은 고전적인 잠금 없는 상호 배제 알고리즘이 `volatile`만으로는 구현되지 않는 이유다.

**셋째, `volatile` 필드를 `ref`/`out`으로 넘기면 volatile성이 사라진다.**

```csharp
private volatile int _amount;

void M()
{
    // CS0420: volatile 필드에 대한 참조는 volatile로 취급되지 않는다
    bool ok = int.TryParse("123", out _amount);
}
```

C#은 `volatile` 필드를 `ref`/`out`으로 전달할 때 **경고 CS0420**을 낸다. 호출되는 메서드는 그 매개변수가 volatile 필드를 가리킨다는 사실을 모르므로, 그 안에서 이루어지는 접근에는 아무 펜스도 없다. 경고를 무시하고 넘기면 **volatile 표시가 조용히 무력화된다.**

> **⚠️ `Interlocked`도 `ref`를 받는다**
>
> `Interlocked.Increment(ref _amount)` 처럼 `volatile` 필드를 `Interlocked`에 넘기면 같은 CS0420 경고가 난다. 이 경우는 실질적 위험이 없다 — `Interlocked` 메서드 자체가 전체 펜스이기 때문이다. 하지만 경고를 없애려고 `volatile`을 떼는 것이 옳은 대응이지, 경고를 억제하는 것이 옳은 대응이 아니다. **`Interlocked`로만 접근하는 필드에는 `volatile`이 필요 없다.**

### `Volatile.Read` / `Volatile.Write`가 더 나은 이유

`volatile` 키워드는 **그 필드의 모든 접근**을 volatile로 만든다. 그런데 실제 알고리즘에서 volatile 접근이 필요한 지점은 대개 한두 곳이고, 나머지 접근은 평범해도 된다. 전부를 volatile로 만들면 그 나머지의 최적화 기회를 잃는다.

```csharp
// _amount가 volatile 필드라고 하자
_amount = _amount + _amount;
```

일반적으로 정수를 두 배로 만드는 것은 왼쪽 시프트 한 번이고, 컴파일러는 이 최적화를 안다. 그런데 `_amount`가 `volatile`이면 이 최적화가 금지된다. 컴파일러는 `_amount`를 레지스터로 한 번 읽고, 다시 다른 레지스터로 읽고, 두 레지스터를 더하고, 결과를 `_amount`에 써야 한다. 최적화되지 않은 코드는 더 크고 더 느리다. 이것이 루프 안에 있으면 손해가 커진다.

그래서 저자를 포함해 많은 사람이 `volatile` 키워드보다 `Volatile` 클래스를 선호한다.

```csharp
public static class Volatile
{
    public static void Write(ref int location, int value);
    public static int  Read(ref int location);
    // bool, sbyte/byte, short/ushort, int/uint, long/ulong,
    // nint/nuint, float, double, 그리고 T where T : class 오버로드가 있다
}
```

`Volatile`의 오버로드 집합은 `volatile` 키워드보다 넓다. **`long`과 `double`도 받는다.** 다만 여기서 오해하면 안 된다 — `Volatile.Read(ref long)`은 순서만 보장하고, 32비트 프로세스에서 원자성까지 보장하지는 않는다. 그 경우에는 `Interlocked.Read`를 써야 한다.

| 도구 | 원자성 | 순서 | 적용 범위 |
|---|---|---|---|
| `volatile` 키워드 | 대상 타입이 원래 원자적일 때만 | 획득(읽기) / 해제(쓰기) | 필드의 **모든** 접근 |
| `Volatile.Read`/`Write` | 위와 같음 | 획득 / 해제 | 그 **호출 지점**만 |
| `Thread.MemoryBarrier()` | 없음 | **전체 펜스** | 호출 지점 |
| `Interlocked.*` | **있음** | **전체 펜스** | 호출 지점 |
| `lock` 블록 | 블록 전체가 배타적 | 진입 획득 / 이탈 해제 | 블록 |

> **📌 `Thread.VolatileRead` / `Thread.VolatileWrite`**
>
> 오래된 코드에서 만날 수 있는, `Volatile` 클래스가 나오기 전의 API다. 의미는 비슷하지만 **전체 펜스**를 삽입해 필요 이상으로 비싸다. 새 코드에서는 `Volatile.Read`/`Volatile.Write`를 쓰고, 전체 펜스가 정말 필요하면 `Thread.MemoryBarrier()`를(또는 `Interlocked.MemoryBarrier()`를 ※.NET Core 이후) 명시적으로 부른다 — 의도가 코드에 드러난다.

### 성능 영향

x86/x64에서 `volatile` 읽기·쓰기의 하드웨어 비용은 사실상 0이다. 진짜 비용은 **최적화 기회의 상실**이다.

- 필드를 레지스터에 유지할 수 없다 → 루프마다 메모리 접근
- 그 필드를 포함한 식을 접거나 다시 쓸 수 없다
- 그 필드 주변의 명령을 재배치해 파이프라인을 채울 수 없다

ARM64에서는 여기에 실제 배리어 명령의 비용이 더해진다. `volatile` 읽기가 뜨거운 루프 안에 있으면 측정 가능한 차이가 난다.

> **💡 "`volatile`을 쓰고 싶다면 대개 잘못 생각하고 있는 것이다"**
>
> 실무 지침으로 이렇게 정리한다.
>
> - **99%의 경우**, 원하는 것은 `lock`이거나 `Interlocked`이거나 동시성 컬렉션(24.12절)이다.
> - `volatile`이 정말 맞는 경우는 거의 **"한 스레드가 쓰고 여러 스레드가 읽는 단순 플래그"** 하나뿐이다. 취소 플래그, 종료 신호, 초기화 완료 표시 같은 것.
> - 그 플래그마저도 `CancellationToken`(46.8절)이나 `Volatile.Read`/`Write` 짝으로 표현하는 편이 의도가 더 잘 드러난다.
> - 두 개 이상의 `volatile` 필드가 서로 관계를 맺는 순간, 그 코드는 거의 확실히 틀렸다. 그때 필요한 것은 **잠금**이다.
>
> `volatile`로 잠금 없는 알고리즘을 짜려는 충동이 들면, 먼저 그 알고리즘을 `lock`으로 작성하고 측정하라. 측정 결과 잠금이 병목이 아니면 — 대개 아니다 — 거기서 끝이다.

## 48.4 `Interlocked` — 사용자 모드 원자 연산

### 문법 — 메서드 목록

`Volatile`의 메서드는 원자적 읽기 **또는** 원자적 쓰기를 한다. `System.Threading.Interlocked`의 메서드는 원자적 읽기 **와** 쓰기를 하나의 나눌 수 없는 연산으로 수행한다. 그리고 **모든 `Interlocked` 메서드는 전체 펜스**다.

```csharp
public static class Interlocked
{
    // return (++location)
    public static int Increment(ref int location);

    // return (--location)
    public static int Decrement(ref int location);

    // return (location += value)   — value가 음수면 뺄셈
    public static int Add(ref int location, int value);

    // int old = location; location = value; return old;
    public static int Exchange(ref int location, int value);

    // int old = location;
    // if (location == comparand) location = value;
    // return old;
    public static int CompareExchange(ref int location, int value, int comparand);
}
```

반환값의 의미가 메서드마다 다르다는 점에 주의한다.

| 메서드 | 반환값 | 비고 |
|---|---|---|
| `Increment` / `Decrement` / `Add` | **연산 후**의 값 | `i++`가 아니라 `++i`에 대응 |
| `Exchange` | **연산 전**의 값 | 이전 값을 알아야 하므로 |
| `CompareExchange` | **연산 전**의 값 (교환 성공 여부와 무관) | 반환값을 `comparand`와 비교해 성공을 판정 |
| `Read` | 현재 값 | `long`을 32비트에서 찢기지 않고 읽기 위해 존재 |

오버로드는 `int` 외에 `long`, 그리고 `Exchange`/`CompareExchange`에 한해 `object`, `IntPtr`, `float`, `double`, 그리고 참조 타입으로 제약된 제네릭 버전 `T`가 있다.

```csharp
// long을 32비트 프로세스에서 안전하게 읽는 유일한 방법
long snapshot = Interlocked.Read(ref _bigCounter);
```

> **📌 `Interlocked.Read`는 왜 존재하는가**
>
> 64비트 프로세스에서 정렬된 `long` 읽기는 원자적이므로 `Interlocked.Read`가 필요 없어 보인다. 그러나 32비트 프로세스에서는 필요하다. 내부적으로 `Interlocked.Read(ref x)`는 `CompareExchange(ref x, 0, 0)` 과 같은 일을 한다 — 값이 0이면 0으로 바꾸고(즉 아무것도 안 바꾸고) 이전 값을 반환한다. 결과적으로 원자적 읽기가 된다. `int`에는 대응하는 `Interlocked.Read`가 없다. 필요 없기 때문이다.

### 컴파일 결과와 하드웨어

`Interlocked`의 메서드는 JIT이 인식하는 **내장 함수(intrinsic)** 다. 메서드 호출로 컴파일되지 않고 단일 CPU 명령으로 인라인된다.

```csharp
Interlocked.Increment(ref _counter);
```

x64에서 이 한 줄은 대략 다음과 같은 명령이 된다.

```asm
mov     eax, 1
lock xadd dword ptr [rcx], eax   ; 원자적 교환-덧셈
```

`Interlocked.CompareExchange`는 `lock cmpxchg`가 된다.

```asm
mov     eax, comparand
mov     edx, value
lock cmpxchg dword ptr [rcx], edx  ; [rcx]==eax 이면 edx 저장, 어느 쪽이든 이전 값을 eax에
```

`lock` 접두사가 핵심이다. 이 접두사가 해당 캐시 라인에 대한 배타적 소유권을 확보하고, 그 사이에 다른 코어가 끼어들지 못하게 한다. **운영체제는 이 일에 전혀 개입하지 않는다.** 그래서 빠르다. 그리고 그래서 이 명령으로 막힌 스레드는 OS가 "막혔다"고 인식하지 못한다 — 스레드 풀이 대체 스레드를 만들지도 않는다.

ARM64에는 `lock` 접두사가 없다. 대신 `ldaxr`/`stlxr`(적재-배타 / 저장-배타) 쌍으로 루프를 돌거나, ARMv8.1 이상이면 `ldadd`/`cas` 같은 원자 명령을 쓴다. **어느 쪽이든 의미론은 동일하다.**

### 런타임 동작 — CAS 루프 패턴

`Interlocked`에 `Multiply`, `Divide`, `Min`, `Max` 같은 메서드가 없는 것을 아쉬워하는 사람이 많다(비트 연산 `And`·`Or`는 ※.NET 5에서 추가되었다). 그런데 **`CompareExchange` 하나로 임의의 연산을 원자적으로 만들 수 있다.** 이 관용구를 **CAS(compare-and-swap) 루프** 라 부른다.

```csharp
public static int Maximum(ref int target, int value)
{
    int currentVal = target, startVal, desiredVal;

    // 루프 안에서는 target을 바꾸려는 시도 외에는 절대 건드리지 않는다
    // 다른 스레드가 지금 이 순간에도 만지고 있을 수 있기 때문이다
    do
    {
        // 이번 반복의 시작 값을 기록한다
        startVal = currentVal;

        // startVal과 value만으로 원하는 결과를 계산한다
        desiredVal = Math.Max(startVal, value);

        // 여기서 스레드가 선점될 수 있다!

        // if (target == startVal) target = desiredVal;
        // 어느 쪽이든 바뀌기 전의 값이 반환된다
        currentVal = Interlocked.CompareExchange(ref target, desiredVal, startVal);

        // 이번 반복 동안 시작 값이 바뀌었으면 다시 시도한다
    } while (startVal != currentVal);

    return desiredVal;
}
```

이 패턴의 구조를 뜯어보자.

1. **읽는다.** `startVal`에 현재 값을 스냅숏한다.
2. **계산한다.** `startVal`만 가지고 `desiredVal`을 만든다. 이 계산은 임의로 복잡해도 된다 — 수천 줄이어도 상관없다. 다만 **부작용이 없어야 한다.** 재시도되면 다시 실행되기 때문이다.
3. **원자적으로 교체를 시도한다.** `CompareExchange`가 "내가 읽은 그 값이 아직 그대로인가"를 확인하고 그럴 때만 바꾼다.
4. **실패하면 다시 시도한다.** 반환값이 `startVal`과 다르면 그사이 누군가 바꾼 것이므로, 새 값으로 처음부터 반복한다.

이 패턴은 데이터베이스의 **낙관적 동시성(optimistic concurrency)** 과 정확히 같은 발상이다. 잠그지 않고 진행하되, 커밋 시점에 "내가 본 것이 아직 유효한가"를 확인한다.

Richter는 이 패턴을 `Morph`라는 제네릭 메서드로 캡슐화하기도 했다. 계산 단계를 델리게이트로 받아 CAS 루프만 재사용하는 형태다. 다만 델리게이트 호출 비용이 붙으므로, 성능이 중요한 자리에서는 위 `Maximum`처럼 루프를 인라인으로 쓰는 편이 낫다.

> **📌 이미 본 CAS 루프 — 이벤트 접근자**
>
> 27.1절에서 컴파일러가 생성하는 이벤트 `add`/`remove` 접근자를 봤다. 그 본문이 정확히 이 패턴이다.
>
> ```csharp
> EventHandler<T> prevHandler;
> EventHandler<T> newMail = _newMail;
> do
> {
>     prevHandler = newMail;
>     EventHandler<T> combined = (EventHandler<T>)Delegate.Combine(prevHandler, value);
>     newMail = Interlocked.CompareExchange(ref _newMail, combined, prevHandler);
> } while (newMail != prevHandler);
> ```
>
> 델리게이트는 불변이므로(26.4절) `Delegate.Combine`은 새 체인을 만들어 반환한다. 즉 "읽고, 새 값을 만들고, 원자적으로 교체한다"가 그대로 성립한다. **이벤트 구독이 잠금 없이 스레드 안전한 것은 이 관용구 덕분이다.**

### CAS 루프를 잠금으로 쓰기

`Exchange` 하나로 가장 단순한 잠금을 만들 수 있다.

```csharp
struct SimpleSpinLock
{
    private int _resourceInUse;   // 0=사용 안 함(기본), 1=사용 중

    public void Enter()
    {
        // 항상 "사용 중"으로 바꾼다. 이 스레드가 "사용 안 함"에서 바꾼 것이면 잠금을 얻은 것이다
        while (Interlocked.Exchange(ref _resourceInUse, 1) != 0)
        {
            // 여기에 "흑마술"이 들어간다 (48.12절)
        }
    }

    public void Leave() => Volatile.Write(ref _resourceInUse, 0);
}
```

두 스레드가 동시에 `Enter`를 부르면 `Interlocked.Exchange`가 한 쪽만 `0 → 1`로 바꾼 것을 보게 만든다. 그 스레드가 잠금을 얻는다. 다른 스레드는 `1 → 1`로 바꾸고 `1`을 받으므로 계속 돈다.

문제는 명확하다. **경합이 나면 스레드가 CPU를 태우며 돈다.** 그래서 스핀락은 아주 짧은 임계 구역에만 쓸 수 있다. `while` 안의 "흑마술"이 무엇인지는 48.12절에서 본다.

### lock-free의 대가

`Interlocked` 기반 코드를 흔히 **lock-free**라고 부른다. 공짜가 아니다.

**첫째, ABA 문제.** `CompareExchange`는 "값이 여전히 `startVal`인가"만 확인한다. 그런데 그사이에 값이 `A → B → A`로 두 번 바뀌었다면? `CompareExchange`는 이 사실을 알 수 없고 성공한다. 값 하나만 보는 알고리즘에서는 대개 문제가 아니지만, 그 값이 **포인터**이고 그 포인터가 가리키는 구조가 그사이에 해제되고 같은 주소에 다시 할당되었다면 치명적이다.

.NET에서는 이 문제가 네이티브 코드보다 훨씬 덜 아프다. GC가 살아 있는 객체를 회수하지 않으므로 "해제되고 같은 주소에 재할당"이 일어나지 않기 때문이다. 그래도 **인덱스나 버전 번호를 CAS로 관리하는 알고리즘**에서는 여전히 나타난다. 표준 해법은 값에 **버전 카운터를 붙여** 함께 교체하는 것이다.

**둘째, 라이브락.** 경합이 심하면 모든 스레드가 계산하고, 실패하고, 다시 계산하기를 반복한다. 진행하는 스레드가 하나도 없지는 않으므로 엄밀히는 라이브락이 아니지만, 실질적으로는 **CPU를 100% 태우면서 처리량이 잠금보다 낮아지는** 상황이 생긴다.

**셋째, 재시도 비용.** CAS 루프의 계산 단계가 무거우면 재시도할 때마다 그 계산이 통째로 버려진다. 계산이 잠금 획득 비용보다 비싸다면 CAS 루프는 손해다.

> **⚠️ CAS 루프의 계산 단계에는 부작용이 있으면 안 된다**
>
> 재시도되면 그 계산이 다시 실행된다. 계산 단계에서 로그를 남기거나, 컬렉션에 항목을 넣거나, 다른 필드를 갱신하거나, 이벤트를 발생시키면 **그 부작용이 여러 번 일어난다.** CAS 루프 안에서는 순수 계산만 해라.

### 성능 영향 — `Interlocked`가 이기는 조건과 지는 조건

| 상황 | `Interlocked` | `lock` |
|---|---|---|
| 단일 `int`/`long` 카운터 증가, 경합 낮음 | **압승** | 불필요하게 무겁다 |
| 단일 필드 교체(플래그, 참조), 경합 낮음 | **압승** | 불필요 |
| 여러 필드를 한 묶음으로 갱신 | 불가능하거나 매우 복잡 | **적합** |
| 임계 구역 안의 작업이 길다 | CAS 루프가 계속 재시도 → 손해 | **적합** |
| 여러 코어가 **같은 캐시 라인**을 초당 수백만 번 두드린다 | 캐시 라인 핑퐁으로 급격히 느려진다 | 마찬가지로 느리다 |

마지막 행이 중요하다. `Interlocked`가 빠른 것은 **경합이 없을 때**다. 경합이 심해지면 `lock` 접두사가 요구하는 캐시 라인 배타 소유권 확보가 코어 간 통신을 유발하고, 이 비용이 지배적이 된다. 여러 코어가 같은 카운터를 두드리면 그 카운터가 있는 64바이트 캐시 라인이 코어 사이를 계속 왕복한다.

해법은 **분할**이다. 코어마다(또는 스레드마다) 별도의 카운터를 두고 나중에 합친다.

```csharp
// 나쁨 — 모든 스레드가 같은 캐시 라인을 두드린다
static long _total;
void Work() => Interlocked.Increment(ref _total);

// 나음 — 스레드 로컬로 세고 마지막에 한 번만 합친다
static long _total;
void Work(IEnumerable<Item> items)
{
    long local = 0;
    foreach (var item in items) local++;      // 잠금도 Interlocked도 없다
    Interlocked.Add(ref _total, local);       // 딱 한 번
}
```

이 패턴은 48.9절의 경합 감소 전략표에서 다시 나온다. 서로 다른 스레드의 카운터가 **같은 캐시 라인에 놓여** 생기는 거짓 공유(false sharing) 문제와 패딩으로 그것을 없애는 방법은 70.6절에서 다룬다.

> **💡 언제 `Interlocked`를 선택하는가**
>
> 판단 기준 하나로 요약한다. **"원자적으로 갱신해야 하는 상태가 워드 하나에 들어가는가?"**
>
> 들어가면 `Interlocked`가 거의 항상 옳다. 안 들어가면 — 필드가 두 개 이상이거나, 컬렉션이거나, 계산이 길면 — `lock`이 옳다. 억지로 여러 필드를 하나의 `long`에 비트로 욱여넣는 설계는 정말 뜨거운 경로에서만 정당화된다. Richter의 `OneManyLock`이 잠금 상태 전체를 하나의 정수 필드에 다섯 개의 비트 필드로 담고 CAS 루프로 조작하는 것이 그 예다.

## 48.5 배타적 잠금 — `lock` 문, `Monitor.Enter`/`Exit`

### 문법

`lock` 문은 C#에서 가장 많이 쓰이는 동기화 구조다.

```csharp
class ThreadSafe
{
    static readonly object _locker = new object();
    static int _val1 = 1, _val2 = 1;

    static void Go()
    {
        lock (_locker)
        {
            if (_val2 != 0) Console.WriteLine(_val1 / _val2);
            _val2 = 0;
        }
    }
}
```

한 번에 한 스레드만 `_locker`를 잠글 수 있다. 경합하는 스레드는 잠금이 풀릴 때까지 막힌다. 여러 스레드가 경합하면 **준비 큐(ready queue)** 에 줄을 서고 원칙적으로 선착순으로 잠금을 얻는다.

다만 "선착순"을 보장으로 받아들이면 안 된다. Windows와 CLR의 구현 세부 때문에 큐의 공정성이 깨져 늦게 온 스레드가 먼저 들어갈 수 있다. **잠금의 공정성에 알고리즘의 정확성을 의존하지 마라.**

배타적 잠금은 보호 대상에 대한 **직렬화된 접근(serialized access)** 을 강제한다고 말한다. 한 스레드의 접근 구간이 다른 스레드의 접근 구간과 겹칠 수 없다는 뜻이다. 위 예제에서 보호되는 것은 `Go` 메서드 안의 로직**과** `_val1`, `_val2` 필드다.

> **📌 잠금은 잠금 객체 자체를 보호하지 않는다**
>
> `lock(x)`가 걸려 있어도 다른 스레드가 `x.ToString()`을 부르는 것은 전혀 막히지 않는다. **두 스레드가 모두 `lock(x)`를 실행해야** 블로킹이 일어난다. 잠금 객체는 그냥 티켓이지, 보호막이 아니다.

### 컴파일 결과 — `Monitor.Enter`와 `Monitor.Exit`

`lock` 문은 `System.Threading.Monitor`의 메서드 호출에 대한 문법 설탕이다.

```csharp
lock (_locker)
{
    // 본문
}
```

C# 컴파일러는 이것을 다음으로 번역한다.

```csharp
bool lockTaken = false;
try
{
    Monitor.Enter(_locker, ref lockTaken);
    // 본문
}
finally
{
    if (lockTaken) Monitor.Exit(_locker);
}
```

IL로 보면 `try`/`finally` 구조가 그대로 드러난다.

```il
  IL_0000:  ldsfld     object Program::_locker
  IL_0005:  stloc.0
  IL_0006:  ldc.i4.0
  IL_0007:  stloc.1                                   // lockTaken = false
  .try
  {
    IL_0008:  ldloc.0
    IL_0009:  ldloca.s   lockTaken
    IL_000b:  call       void [System.Runtime]System.Threading.Monitor::Enter(object, bool&)
    // ... 본문 ...
    IL_001a:  leave.s    IL_0028
  }
  finally
  {
    IL_001c:  ldloc.1
    IL_001d:  brfalse.s  IL_0027
    IL_001f:  ldloc.0
    IL_0020:  call       void [System.Runtime]System.Threading.Monitor::Exit(object)
    IL_0027:  endfinally
  }
```

### C# 4에서 왜 바뀌었는가

C# 4 이전의 번역은 이랬다.

```csharp
// C# 3 이하의 lock 번역
Monitor.Enter(_locker);
try
{
    // 본문
}
finally { Monitor.Exit(_locker); }
```

여기에 미묘한 취약점이 있다. `Monitor.Enter`가 반환된 뒤 `try` 블록에 진입하기 **직전에** 예외가 발생하면 어떻게 되는가? `OutOfMemoryException`이나 (.NET Framework에서) 스레드 중단(`ThreadAbortException`)이 그 틈에 끼어들 수 있다. 그러면 잠금은 획득되었는데 `finally`가 실행되지 않아 **잠금이 영영 새어 나간다(leaked lock).**

.NET 4 / C# 4에서 이를 막기 위해 `Monitor.Enter`의 오버로드가 추가되었다.

```csharp
public static void Enter(object obj, ref bool lockTaken);
```

`lockTaken`은 **이 메서드가 예외를 던졌고 잠금을 얻지 못했을 때에만** `false`로 남는다. 잠금을 얻었으면 예외가 나든 말든 `true`가 된다. `Enter` 호출을 `try` 블록 **안**으로 넣고 `finally`에서 `lockTaken`을 검사하면, "잠금을 얻었는데 해제하지 않는" 창이 사라진다.

`Monitor.TryEnter`에도 같은 `lockTaken` 오버로드가 있다. 48.12절에서 볼 `SpinLock`도 같은 패턴을 쓴다.

> **⚠️ `Monitor.Exit`을 먼저 부르면 예외**
>
> 같은 객체에 대해 `Monitor.Enter`를 부르지 않은 채 `Monitor.Exit`을 부르면 `SynchronizationLockException`이 발생한다. 그리고 `Monitor.Enter`/`Exit`를 직접 쓸 때 개수를 맞추지 않으면 잠금이 영영 안 풀리거나 이 예외가 난다. **`lock` 문을 쓰면 컴파일러가 짝을 보장한다.** `Monitor`를 직접 쓰는 이유는 `TryEnter`나 `Wait`/`Pulse`가 필요할 때뿐이다.

### 런타임 동작 — 동기화 블록 인덱스와 잠금 팽창

`Monitor`는 정적 클래스이고 그 메서드는 **임의의 힙 객체 참조**를 받는다. 그렇다면 잠금 상태(소유 스레드 ID, 재귀 카운트, 대기 스레드 수, 커널 이벤트 핸들)는 어디에 저장되는가?

15.2절과 54.2절에서 본 것처럼 관리 힙의 모든 객체는 두 개의 부가 필드를 갖는다. **타입 객체 포인터**와 **동기화 블록 인덱스(sync block index)** 다. 후자가 이 질문의 답이다.

```text
   관리 힙                              CLR의 동기화 블록 배열
   ┌──────────────────────┐            ┌─────────────────────┐
   │ Object-A             │            │ 동기화 블록 #0      │◀──┐
   │  타입 객체 포인터    │            ├─────────────────────┤   │
   │  동기화 블록 인덱스 (0)│───────────▶│ 동기화 블록 #1      │   │
   │  인스턴스 필드…      │            ├─────────────────────┤   │
   ├──────────────────────┤            │ 동기화 블록 #2      │◀─┐│
   │ Object-B             │            ├─────────────────────┤  ││
   │  타입 객체 포인터    │            │ 동기화 블록 #3      │◀┐││
   │  동기화 블록 인덱스 (-1)│ (없음)   │        …            │ │││
   │  인스턴스 필드…      │            └─────────────────────┘ │││
   ├──────────────────────┤                                    │││
   │ Object-C             │────────────────────────────────────┘││
   │  동기화 블록 인덱스 (2)│─────────────────────────────────────┘│
   ├──────────────────────┤                                       │
   │ Type-T (타입 객체)   │───────────────────────────────────────┘
   │  동기화 블록 인덱스 (3)│
   │  타입의 정적 필드…   │
   └──────────────────────┘
```

*힙의 객체(타입 객체 포함)는 동기화 블록 인덱스로 CLR의 동기화 블록 배열의 한 항목을 가리킬 수 있다.*

동작 순서는 이렇다.

1. CLR이 초기화될 때 네이티브 힙에 **동기화 블록 배열**을 할당한다.
2. 객체가 생성되면 동기화 블록 인덱스는 **-1**로 초기화된다. 어떤 동기화 블록도 가리키지 않는다는 뜻이다.
3. 그 객체에 대해 `Monitor.Enter`가 처음 불리면 CLR이 배열에서 빈 동기화 블록을 찾아 객체의 인덱스를 그것에 맞춘다. **동기화 블록은 필요할 때 즉석에서 연결된다.**
4. `Monitor.Exit`이 불리면 CLR은 그 객체를 기다리는 스레드가 남았는지 본다. 없으면 동기화 블록을 해제하고 객체의 인덱스를 다시 -1로 돌린다. 해제된 블록은 나중에 다른 객체에 재사용된다.

배열이 모자라면 CLR이 더 만든다. 동시에 동기화되는 객체가 많다고 해서 고갈되지는 않는다.

### 씬 락과 팻 락

위 설명은 개념 모델이다. 실제 CLR은 한 단계를 더 최적화한다. **경합이 없는 대부분의 경우에는 동기화 블록조차 만들지 않는다.**

객체 헤더의 그 한 워드는 여러 용도로 나뉘어 쓰인다. 경합이 없는 잠금 획득에서는 CLR이 헤더 워드에 **소유 스레드 ID와 재귀 카운트를 직접 적어 넣는다.** 이것을 **씬 락(thin lock)** 이라 부른다. 별도의 할당이 전혀 없고, 원자 명령 하나로 획득이 끝난다.

씬 락으로 표현할 수 없는 상황이 되면 CLR은 실제 동기화 블록을 할당하고 잠금을 **팻 락(fat lock)** 으로 **팽창(inflation)** 시킨다. 팽창을 유발하는 대표적 조건은 다음과 같다.

| 조건 | 왜 팽창하는가 |
|---|---|
| 경합이 발생해 대기 스레드가 생겼다 | 대기 큐와 커널 이벤트를 담을 자리가 필요하다 |
| 재귀 카운트가 헤더의 비트 폭을 넘겼다 | 헤더의 비트 예산을 초과 |
| `Monitor.Wait`/`Pulse`가 쓰였다 | 조건 변수용 대기 큐가 별도로 필요하다 |
| 그 객체의 `GetHashCode()`가 호출되어 헤더에 해시가 저장되었다 | 헤더 워드를 해시가 이미 쓰고 있다 |

한 번 팽창한 잠금은 대개 그 객체가 회수될 때까지 팽창 상태를 유지한다.

> **⚠️ `GetHashCode()`가 잠금 성능을 바꿀 수 있다**
>
> 마지막 행이 실무에서 놀라움을 준다. `Object.GetHashCode()`의 기본 구현은 객체 수명 동안 변하지 않는 수를 반환해야 하므로 **그 값을 객체 헤더에 저장한다**(15.6절, 54.2절). 그런데 헤더 워드는 씬 락도 쓰는 자리다. 잠금 대상 객체를 `Dictionary`의 키로 쓰거나 `HashSet`에 넣으면 그 객체의 잠금이 팽창할 수 있다.
>
> 실무적 결론은 이렇다. **잠금 전용 객체를 따로 만들어라.** `private readonly object _locker = new object();`는 아무 데도 담기지 않으므로 해시 코드가 요구될 일이 없다. 48.6절의 권고가 성능 관점에서도 옳은 이유다.

### 재진입 — 같은 스레드는 다시 들어갈 수 있다

`Monitor`는 **재진입 가능(reentrant)** 하다. 잠금을 이미 쥔 스레드는 같은 잠금을 다시 획득할 수 있고, 내부적으로 재귀 카운트가 올라간다.

```csharp
lock (_locker)
    lock (_locker)
        lock (_locker)
        {
            // 여기까지 문제없이 들어온다
        }
```

`Monitor`로 직접 쓰면 이렇다.

```csharp
Monitor.Enter(_locker); Monitor.Enter(_locker); Monitor.Enter(_locker);
// 작업
Monitor.Exit(_locker);  Monitor.Exit(_locker);  Monitor.Exit(_locker);
```

**가장 바깥쪽 `lock` 블록을 빠져나가야만** — 즉 `Exit` 호출 개수가 `Enter` 호출 개수와 같아져야만 — 잠금이 실제로 풀린다. 스레드는 오직 **첫 번째(가장 바깥) 잠금**에서만 막힐 수 있다.

재진입이 필요한 전형적인 상황은 잠금을 쥔 메서드가 같은 잠금을 요구하는 다른 메서드를 부를 때다.

```csharp
object locker = new object();

lock (locker)
{
    AnotherMethod();
    // 여전히 잠금을 쥐고 있다 — 재진입 가능하기 때문이다
}

void AnotherMethod()
{
    lock (locker) { Console.WriteLine("Another method"); }
}
```

> **📌 재진입은 공짜가 아니다**
>
> 재진입을 지원하려면 잠금이 소유 스레드 ID와 재귀 카운트를 유지해야 한다. 이 필드를 갱신하는 비용이 잠금을 느리게 만든다. Richter가 측정한 하이브리드 잠금 비교에서, 소유권·재귀를 지원하지 않는 단순 하이브리드 잠금은 무경합 증가 연산에서 기준 대비 약 21배, 소유권·재귀를 지원하는 버전은 약 29배 느렸다. **기능 하나하나가 성능을 깎는다.**
>
> `Monitor`는 예외적으로 재귀를 지원하면서도 성능이 좋다. 부분적으로는 `Monitor`가 관리 코드가 아니라 네이티브 코드로 구현되어 있기 때문이다.

### `Monitor.TryEnter`와 타임아웃

`Monitor.Enter`는 잠금을 얻을 때까지 무한정 기다린다. `TryEnter`는 타임아웃을 지정할 수 있다.

```csharp
// 밀리초 또는 TimeSpan
if (Monitor.TryEnter(_locker, TimeSpan.FromSeconds(2)))
{
    try { /* 임계 구역 */ }
    finally { Monitor.Exit(_locker); }
}
else
{
    // 2초 안에 얻지 못했다 — 다른 일을 하거나 오류를 보고한다
}
```

인수 없이 `TryEnter(_locker)`를 부르면 **즉시 시도하고 즉시 포기한다.** 잠금 상태를 "떠보는" 용도다.

`TryEnter`에도 `lockTaken` 오버로드가 있다.

```csharp
bool lockTaken = false;
try
{
    Monitor.TryEnter(_locker, 2000, ref lockTaken);
    if (lockTaken) { /* 임계 구역 */ }
}
finally { if (lockTaken) Monitor.Exit(_locker); }
```

> **💡 `TryEnter`는 데드락 검출 도구다**
>
> `TryEnter`를 성능 최적화로 쓰려는 시도는 대개 실패한다. 진짜 가치는 **진단**에 있다. 절대 경합하지 않아야 할 잠금에 넉넉한 타임아웃(예: 30초)을 걸고, 타임아웃이 나면 스택 트레이스와 함께 로그를 남긴다. 프로덕션에서 데드락이 나면 프로세스가 멎는 대신 **로그가 남는다.** 48.8절에서 이 기법을 다시 본다.

### `Monitor.Wait` / `Pulse` / `PulseAll`

`Monitor`는 배타적 잠금 위에 **조건 변수(condition variable)** 도 제공한다.

```csharp
public static class Monitor
{
    public static bool Wait(object obj);
    public static bool Wait(object obj, int millisecondsTimeout);
    public static void Pulse(object obj);
    public static void PulseAll(object obj);
}
```

`Wait`은 잠금을 **일시적으로 놓고** 스레드를 막는다. `Pulse`는 대기 중인 스레드 하나를, `PulseAll`은 전부를 깨운다. 다만 깨어난 스레드는 즉시 실행되지 않고, 신호를 보낸 스레드가 `Monitor.Exit`으로 잠금을 놓아야 비로소 잠금을 얻고 진행한다.

```csharp
sealed class ConditionVariablePattern
{
    private readonly object _lock = new object();
    private bool _condition = false;

    public void Consumer()
    {
        Monitor.Enter(_lock);

        // 잠금을 쥔 채로 복잡한 조건을 "원자적으로" 검사한다
        while (!_condition)
            Monitor.Wait(_lock);      // 잠금을 잠시 놓고 기다린다

        // 조건이 성립했다 — 데이터를 처리한다
        Monitor.Exit(_lock);
    }

    public void Producer()
    {
        Monitor.Enter(_lock);
        _condition = true;
        Monitor.PulseAll(_lock);      // 잠금이 풀린 뒤 대기자들이 깨어난다
        Monitor.Exit(_lock);
    }
}
```

핵심은 **`if`가 아니라 `while`로 조건을 검사한다**는 것이다. 깨어난 시점에 조건이 다시 거짓이 되어 있을 수 있기 때문이다(가짜 깨어남과 다른 스레드의 선점). 이 패턴의 전체 논의와 생산자/소비자 큐 구현은 49.7절에 있다.

> **⚠️ `Wait`/`Pulse`는 해당 객체의 잠금을 쥔 상태에서만 부를 수 있다**
>
> 잠금을 쥐지 않고 `Monitor.Wait`이나 `Monitor.Pulse`를 부르면 `SynchronizationLockException`이 발생한다. 그리고 `Wait`/`Pulse`를 쓰는 순간 그 객체의 잠금은 반드시 팻 락으로 팽창한다.

## 48.6 잠금 객체 선택과 잠금 범위 결정

### 규칙은 하나 — 참조 타입이어야 한다

잠금 객체로 쓸 수 있는 것은 **참여하는 모든 스레드가 볼 수 있는 참조 타입 객체**다. 이 하드 룰 하나 외에는 문법적 제약이 없다. 그래서 잘못 고르기가 쉽다.

값 타입을 넘기면 어떻게 되는가?

```csharp
int counter = 0;
lock (counter) { … }   // 컴파일 오류 — CS0185 (lock 대상은 참조 타입이어야 한다)
```

C#은 값 타입에 `lock`을 거는 것을 컴파일 오류로 막는다. 그런데 `Monitor.Enter`를 직접 부르면 막히지 않는다.

```csharp
int counter = 0;
Monitor.Enter(counter);   // 컴파일된다 — 그리고 아무것도 동기화하지 않는다
```

`Monitor.Enter`는 `object`를 받으므로 값 타입이 **박싱**된다(15.2절). 호출할 때마다 **완전히 다른 박스 객체**가 만들어지므로, 매번 다른 객체를 잠그는 셈이다. 동기화 효과는 0이고, 대응하는 `Monitor.Exit(counter)`는 또 다른 박스를 대상으로 하므로 `SynchronizationLockException`을 던진다.

### 잠그면 안 되는 세 가지

**`this`를 잠그지 마라.**

```csharp
sealed class Transaction
{
    private DateTime _timeOfLastTrans;

    public void PerformTransaction()
    {
        Monitor.Enter(this);          // 나쁘다
        _timeOfLastTrans = DateTime.Now;
        Monitor.Exit(this);
    }

    public DateTime LastTransaction
    {
        get { Monitor.Enter(this); try { return _timeOfLastTrans; }   // 나쁘다
              finally { Monitor.Exit(this); } }
    }
}
```

문제는 **모든 객체의 동기화 블록 인덱스가 암묵적으로 public**이라는 것이다. 클래스 밖의 아무 코드나 그 잠금을 가져갈 수 있다.

```csharp
public static void SomeMethod()
{
    var t = new Transaction();
    Monitor.Enter(t);                 // 이 객체의 "public 잠금"을 가져갔다

    // 스레드 풀 스레드가 LastTransaction을 읽으려 한다
    // → SomeMethod가 Monitor.Exit을 부를 때까지 막힌다!
    ThreadPool.QueueUserWorkItem(o => Console.WriteLine(t.LastTransaction));

    // 다른 작업…
    Monitor.Exit(t);
}
```

디버거로 보면 스레드 풀 스레드가 `LastTransaction` 안에서 막혀 있다는 것까지는 알 수 있다. 그런데 **어느 스레드가 잠금을 쥐고 있는지**, 그리고 **왜 쥐게 되었는지** 알아내는 것은 훨씬 어렵다. 알아냈다 해도 그 코드가 내가 고칠 수 있는 코드가 아닐 수 있다.

**타입 객체(`typeof(T)`)를 잠그지 마라.** 타입 객체도 힙의 객체이므로 동기화 블록 인덱스가 있고, `lock(typeof(Widget))`은 컴파일된다. 문제는 그 타입 객체의 범위다. 어셈블리 안팎의 모든 코드가 같은 타입 객체를 얻을 수 있으므로 잠금의 범위가 사실상 프로세스 전역이 된다. .NET Framework에서는 도메인 중립(domain-neutral)으로 로드된 타입의 타입 객체를 잠그면 **프로세스의 모든 AppDomain에 걸쳐** 잠금이 걸리는 문제가 있었다. AppDomain이 제공해야 할 격리를 깨는 알려진 결함이었고, 고성능으로 고치기 어려워 끝내 수정되지 않았다.

**문자열 리터럴을 잠그지 마라.** 문자열은 인터닝(interning)될 수 있다(8장). 서로 아무 관계 없는 두 코드가 같은 리터럴을 쓰면 **메모리상 동일한 `String` 객체**를 얻게 되고, 두 코드가 서로를 모른 채 동기화된다. .NET Framework에서는 AppDomain 경계를 넘어 문자열이 참조로 전달되어 같은 문제가 AppDomain 사이에서도 일어났다.

### 그러면 무엇을 잠글 것인가

```csharp
sealed class Transaction
{
    // 트랜잭션마다 자기만의 private 잠금을 갖는다
    private readonly object _lock = new object();
    private DateTime _timeOfLastTrans;

    public void PerformTransaction()
    {
        lock (_lock) _timeOfLastTrans = DateTime.Now;
    }

    public DateTime LastTransaction
    {
        get { lock (_lock) return _timeOfLastTrans; }
    }
}
```

규칙은 이렇다.

| 보호 대상 | 잠금 객체 | 이유 |
|---|---|---|
| 인스턴스 필드 | `private readonly object` **인스턴스 필드** | 인스턴스마다 독립적인 잠금 |
| 정적 필드 | `private static readonly object` **정적 필드** | 타입 전체에 하나 |
| 서로 연관된 두 컬렉션 | 둘을 함께 보호하는 **하나의** 잠금 객체 | 부분적 잠금은 조합 원자성을 깬다 |
| 스레드 안전하지 않은 제3자 객체 | 그 객체를 감싸는 클래스의 private 잠금 | 모든 접근이 같은 잠금을 통과해야 한다 |

`readonly`가 중요하다. 잠금 필드가 도중에 다른 객체로 바뀌면 어떤 스레드는 옛 객체를, 어떤 스레드는 새 객체를 잠그게 되어 동기화가 통째로 사라진다.

> **📌 보호 대상 자체를 잠그는 관용구**
>
> 다음과 같은 코드도 흔하고, 대체로 문제가 없다.
>
> ```csharp
> class ThreadSafe
> {
>     List<string> _list = new List<string>();
>     void Test() { lock (_list) { _list.Add("Item 1"); … } }
> }
> ```
>
> `_list`가 private이고 클래스 밖으로 새어 나가지 않는다면 안전하다. 다만 그 참조를 반환하거나 이벤트 인수로 넘기는 순간 "public 잠금" 문제가 그대로 발생한다. 전용 잠금 필드를 두는 편이 항상 더 방어적이다.
>
> 람다나 익명 메서드가 캡처한 지역 변수를 잠글 수도 있다. 캡처된 지역 변수는 실제로는 힙 객체의 필드이므로(26장) 참조 타입 규칙을 만족한다.

> **⚠️ `[MethodImpl(MethodImplOptions.Synchronized)]`를 쓰지 마라**
>
> 이 특성을 메서드에 붙이면 JIT이 그 메서드의 네이티브 코드를 `Monitor.Enter`/`Monitor.Exit` 호출로 감싼다. 인스턴스 메서드면 `this`를, 정적 메서드면 **타입 객체**를 잠근다. 즉 위에서 "하지 마라"고 한 두 가지를 자동으로 해 준다. **쓰지 마라.**

### 잠금 범위 — 잠금 안에서 하지 말아야 할 것

잠금을 쥔 채로 하면 안 되는 일이 몇 가지 있다.

| 하지 말 것 | 무엇이 잘못되나 |
|---|---|
| **다른 잠금 획득** | 잠금 순서 역전 → 데드락(48.8절) |
| **외부 코드 호출**(가상 메서드, 인터페이스, 델리게이트, 콜백) | 그 코드가 어떤 잠금을 잡을지 알 수 없다 |
| **이벤트 발생** | 구독자가 누구인지, 무엇을 잡을지 알 수 없다 |
| **I/O 수행**(파일, 네트워크, DB) | 밀리초 단위의 잠금 보유 → 경합 폭증 |
| **`Dispatcher.Invoke` / `Control.Invoke`** | UI 스레드가 같은 잠금을 기다리면 즉시 데드락 |
| **`.Result` / `.Wait()`로 비동기 대기** | 47.14절의 데드락 + 잠금 보유 시간 폭증 |
| **긴 계산** | 잠금은 짧아야 한다 |
| **`await`** | 애초에 컴파일 오류다(48.11절) |

특히 두 번째와 세 번째가 미묘하다.

> **⚠️ 잠금을 쥔 채 외부 코드를 부르면 잠금의 캡슐화가 새어 나간다**
>
> 이걸 이렇게 볼 수 있다. 잠금을 쥔 채로 남의 코드를 부르면, **그 잠금의 캡슐화가 미묘하게 깨진다.** 내 클래스 `X` 안에서 private 필드 `a`를 잠갔는데, 나를 부른 쪽(또는 그 위)이 이미 클래스 `Y`의 필드 `b`를 잠근 상태일 수 있다. 동시에 다른 스레드가 반대 순서로 하고 있다면 데드락이다.
>
> 이것은 CLR의 결함이 아니라 **잠금이라는 개념 자체의 근본적 한계**다. 소프트웨어 트랜잭셔널 메모리 같은 연구가 이 문제를 다룬다.
>
> 역설적이게도 **좋은 객체지향 설계가 이 문제를 악화시킨다.** 다형성과 의존성 주입은 런타임에야 결정되는 호출 사슬을 만들고, 그러면 "내가 부르는 것이 무엇을 잠그는지"를 정적으로 알 수 없게 된다.

이벤트 발생도 같은 문제다. 이벤트를 발생시키는 것은 **모르는 코드를 부르는 것**이다(27.6절). 구독자가 무엇을 하는지, 어떤 잠금을 잡는지, 얼마나 오래 걸리는지 전혀 알 수 없다.

```csharp
// 나쁨 — 잠금을 쥔 채 이벤트를 발생시킨다
lock (_lock)
{
    _items.Add(item);
    ItemAdded?.Invoke(this, new ItemEventArgs(item));   // 여기서 무슨 일이든 일어날 수 있다
}

// 나음 — 상태 변경만 잠금 안에서, 알림은 밖에서
bool added;
lock (_lock)
{
    added = _items.Add(item);
}
if (added) ItemAdded?.Invoke(this, new ItemEventArgs(item));
```

### 잠금 세분성 — 넓게 잠글 것인가 좁게 잠글 것인가

**굵은 잠금(coarse-grained)** 은 객체 전체를 하나의 잠금으로 보호한다. 구현이 단순하고 데드락 위험이 낮으며 조합 원자성이 자동으로 성립하지만, 경합이 커지고 확장성이 나쁘다. **잔 잠금(fine-grained)** 은 필드·버킷·샤드마다 별도 잠금을 둔다. 경합이 작고 확장성이 좋은 대신, 여러 잠금을 함께 잡아야 하는 순간 데드락 위험이 생기고 조합 원자성을 지키기 어려워진다.

> **💡 굵게 시작하고, 측정한 뒤에만 잘게 쪼개라**
>
> 스레드 안전하지 않은 제3자 라이브러리를 여러 스레드에서 써야 한다면, **그 객체의 모든 프로퍼티·메서드·필드 접근을 같은 하나의 배타적 잠금으로 감싸는 것**이 정답이다. 그 객체의 메서드가 모두 빨리 끝난다면 이 전략은 아주 잘 동작한다.
>
> 잘게 쪼개는 것은 측정으로 경합을 확인한 뒤에 한다(48.9절). 잘게 쪼갠 잠금은 데드락과 조합 원자성 버그를 함께 데려온다.

## 48.7 잠금과 원자성, 중첩 잠금

### 잠금이 보장하는 것은 상호 배제뿐이다

한 그룹의 변수가 **항상 같은 잠금 안에서** 읽히고 쓰인다면, 그 변수들은 원자적으로 읽히고 쓰인다고 말할 수 있다.

```csharp
lock (locker) { if (x != 0) y /= x; }
```

`x`와 `y`가 **항상 이 동일한 배타적 잠금 안에서만** 접근된다면, 이 블록은 다른 스레드의 동작으로 쪼개지거나 선점되어 결과가 뒤바뀔 수 없다. 0으로 나누기 오류는 절대 나지 않는다.

여기서 "항상"이 조건의 전부다. 한 군데라도 잠금 없이 `x`를 쓰는 코드가 있으면 보장은 즉시 사라진다.

### 예외가 잠금의 원자성을 깬다

잠금이 제공하는 원자성은 **블록 안에서 예외가 던져지면 무너진다.** 다중 스레드와 무관하게 그렇다.

```csharp
decimal _savingsBalance, _checkBalance;

void Transfer(decimal amount)
{
    lock (_locker)
    {
        _savingsBalance += amount;
        _checkBalance   -= amount + GetBankFee();
    }
}
```

`GetBankFee()`가 예외를 던지면 저축 잔액은 늘었는데 당좌 잔액은 줄지 않았다. 은행이 돈을 잃는다. 여기서는 `GetBankFee`를 먼저 호출해 문제를 피할 수 있다. 더 복잡한 경우에는 `catch`나 `finally`에서 **롤백 로직**을 구현해야 한다.

> **⚠️ `finally`에서 잠금을 푸는 것이 늘 옳지는 않다**
>
> C# 컴파일러는 `lock` 문을 `try`/`finally`로 번역해서 어떤 경우에도 잠금이 풀리게 한다. 좋은 일처럼 보이지만 Richter는 반대 의견을 낸다. **상태를 변경하는 도중 예외가 나면 상태는 이미 깨져 있다.** 그런데 `finally`가 잠금을 풀어 버리면 다른 스레드가 그 깨진 상태를 만지기 시작한다. 예측 불가능한 동작과 보안 결함으로 이어질 수 있다. **애플리케이션이 멎는 편이 깨진 상태로 계속 도는 것보다 낫다**는 주장이다.
>
> 한편 `try` 블록이 상태를 **읽기만** 한다면 `finally`에서 잠금을 푸는 것은 안전하다.
>
> 실무적으로는 이렇게 정리한다. **잠금 안에서 예외가 날 수 있는 상태 변경을 한다면, 그 예외를 잡아 롤백하거나 프로세스를 내리는 결정을 명시적으로 하라.** `lock` 문에 맡기고 잊지 마라.

### 조합 연산의 원자성은 설계자의 몫이다

이것이 이 절의 핵심이다. **개별 연산이 모두 스레드 안전해도 그것들의 조합은 스레드 안전하지 않다.**

`List<T>`가 완전히 스레드 안전하다고 가정하자. 그래도 이 코드는 안전하지 않다.

```csharp
if (!_list.Contains(newItem)) _list.Add(newItem);
```

`Contains`와 `Add` 사이에 다른 스레드가 같은 항목을 추가할 수 있다. 안전하게 만들려면 `if` 문 **전체**를 잠금으로 감싸야 한다. 그리고 같은 리스트를 수정하는 **모든** 코드가 같은 잠금을 써야 한다.

```csharp
_list.Clear();   // 이것도 같은 잠금으로 감싸야 한다
```

결국 스레드 안전하지 않은 컬렉션을 다룰 때와 **정확히 같은 양의 잠금**이 필요하다. `List`의 가상의 스레드 안전성은 아무 도움도 되지 않았다.

> **⚠️ `ConcurrentDictionary`도 같은 함정을 갖는다**
>
> ```csharp
> if (!_dict.ContainsKey(key))
>     _dict.TryAdd(key, value);      // 여전히 경합이다
> ```
>
> `ConcurrentDictionary`의 각 메서드는 스레드 안전하지만, 두 호출 **사이**는 보호되지 않는다. 다른 스레드가 그 틈에 같은 키를 넣을 수 있다.
>
> 해법은 잠금을 씌우는 것이 아니라 **원자적인 조합 메서드를 쓰는 것**이다. `ConcurrentDictionary`는 이 목적으로 `TryAdd`, `GetOrAdd`, `AddOrUpdate`, `TryUpdate`, `TryRemove`를 제공한다.
>
> ```csharp
> _dict.GetOrAdd(key, k => CreateValue(k));   // 원자적
> ```
>
> 다만 `GetOrAdd`의 팩터리 델리게이트가 **여러 번 호출될 수 있다**는 점에 주의한다. 값 생성에 부작용이 있으면 안 된다. 자세한 내용은 24.12절과 50.10절에 있다.

### 중첩 잠금과 잠금 순서

48.5절에서 본 것처럼 같은 잠금의 중첩은 안전하다. **서로 다른 잠금**의 중첩이 위험하다.

```csharp
// 스레드 A
lock (_lockA)
{
    lock (_lockB) { … }
}

// 스레드 B
lock (_lockB)
{
    lock (_lockA) { … }   // 데드락
}
```

두 잠금을 동시에 잡아야 한다면 **모든 코드가 같은 순서로 잡아야 한다.** 이 규약과 그 한계는 다음 절에서 본다.

> **💡 두 잠금을 동시에 잡아야 한다면 설계를 의심하라**
>
> 두 잠금이 필요하다는 것은 대개 다음 중 하나를 뜻한다.
>
> - 두 자원이 사실은 하나의 불변식(invariant)을 공유한다 → **하나의 잠금으로 합쳐라.**
> - 잠금을 쥔 채 다른 컴포넌트를 부르고 있다 → **잠금 밖으로 호출을 빼라.**
> - 상태 변경과 알림이 섞여 있다 → **분리해라**(48.6절의 이벤트 예제).
>
> 정말로 두 잠금이 필요한 경우는 드물다. 있다면 그 순서를 코드 주석이 아니라 **문서와 코드 리뷰 체크리스트**에 명시하라.

## 48.8 데드락 · 라이브락 · 우선순위 역전 진단

### 데드락의 정의와 네 조건

**데드락(deadlock)** 은 두 스레드가 각각 상대가 쥔 자원을 기다려 둘 다 진행하지 못하는 상태다.

```csharp
object locker1 = new object();
object locker2 = new object();

new Thread(() =>
{
    lock (locker1)
    {
        Thread.Sleep(1000);
        lock (locker2) { }      // 데드락
    }
}).Start();

lock (locker2)
{
    Thread.Sleep(1000);
    lock (locker1) { }          // 데드락
}
```

세 개 이상의 스레드로 더 긴 사슬을 만들 수도 있다.

고전적으로 데드락은 다음 **네 조건이 모두 성립할 때에만** 발생한다.

| 조건 | 의미 | .NET에서 깨는 방법 |
|---|---|---|
| **상호 배제(mutual exclusion)** | 자원을 한 번에 한 스레드만 쓸 수 있다 | 불변 데이터·스레드 로컬·`Interlocked`로 잠금 자체를 없앤다 |
| **점유 대기(hold and wait)** | 자원을 쥔 채 다른 자원을 기다린다 | 잠금 안에서 다른 잠금을 잡지 않는다 |
| **비선점(no preemption)** | 남이 쥔 자원을 강제로 뺏을 수 없다 | `Monitor.TryEnter` 타임아웃으로 스스로 포기한다 |
| **순환 대기(circular wait)** | 대기 관계가 원을 이룬다 | **전역 잠금 순서 규약**으로 원을 끊는다 |

넷 중 **하나만 깨도** 데드락은 나지 않는다. 실무에서 가장 실용적인 것은 네 번째, 그다음이 두 번째다.

> **⚠️ CLR은 데드락을 검출하지도 해소하지도 않는다**
>
> 표준 호스팅 환경의 CLR은 SQL Server와 달리 데드락을 자동으로 감지해서 한쪽을 죽이지 않는다. 잠금 타임아웃을 지정하지 않았다면 참여 스레드는 **영원히** 막힌다.
>
> 예외가 하나 있다. SQL CLR 통합 호스트 아래에서는 데드락이 자동으로 감지되고 한쪽 스레드에 (잡을 수 있는) 예외가 던져진다. 이건 호스트가 제공하는 기능이지 CLR의 기본 동작이 아니다.

### .NET에서의 전형적인 데드락 세 가지

**전형 1 — 잠금 순서 역전.** 위 예제가 그것이다. 여러 잠금을 서로 다른 순서로 잡는다.

**전형 2 — UI 스레드 + `.Result`.** 47.14절에서 해부한 그 데드락이다. UI 스레드가 `Task`의 `.Result`나 `.Wait()`로 블로킹하고, 그 태스크의 연속이 동기화 컨텍스트를 통해 UI 스레드로 돌아오려 한다. UI 스레드는 블로킹 중이라 연속을 실행할 수 없고, 태스크는 연속이 실행되어야 완료된다.

같은 구조가 잠금과 UI 마샬링의 조합으로도 나온다.

```csharp
// 백그라운드 스레드
lock (_locker)
{
    Dispatcher.Invoke(() => UpdateUi());   // UI 스레드가 _locker를 기다리는 중이면 데드락
}

// UI 스레드
lock (_locker) { … }
```

`Invoke` 대신 `BeginInvoke`를 쓰면 대개 해결된다. 대기하지 않기 때문이다. 또는 `Invoke` 전에 잠금을 놓는다 — 다만 잠금을 잡은 쪽이 호출자라면 그럴 수 없다.

**전형 3 — 잠금 안에서의 이벤트 호출.** 48.6절에서 본 그 문제다. 구독자가 다른 잠금을 잡거나, 다른 스레드에 마샬링하거나, 그 스레드가 다시 원래 잠금을 요구할 수 있다.

### 예방 — 잠금 순서 규약

가장 널리 알려진 조언은 **"잠금을 항상 일관된 순서로 잡아라"** 다. 위 첫 예제 같은 단순한 경우에는 효과적이다.

```csharp
// 규약: 항상 lockA → lockB 순서로만 잡는다
static readonly object _lockA = new object();   // 순위 1
static readonly object _lockB = new object();   // 순위 2

void M1() { lock (_lockA) lock (_lockB) { … } }   // OK
void M2() { lock (_lockA) lock (_lockB) { … } }   // OK
// void M3() { lock (_lockB) lock (_lockA) { … } }  // 금지
```

문제는 이 조언이 **현실의 어려운 경우에 적용하기 어렵다**는 것이다. 근본적인 난점은 **내 호출자가 어떤 잠금을 이미 쥐고 있는지 알 수 없다**는 데 있다. 내 클래스 `X` 안에서 private 필드 `a`를 잠갔을 때, 호출자(또는 그 호출자)가 이미 클래스 `Y`의 필드 `b`를 잠갔을 수 있다. 그 사실을 알 방법이 없으니 순서를 정할 수도 없다.

그래서 더 나은 전략은 규약 이전에 **구조**를 바꾸는 것이다.

> **💡 데드락을 없애는 다섯 가지 전략 — 효과 순서**
>
> 1. **잠금을 하나로 줄여라.** 하나면 순서 문제가 없다.
> 2. **내 객체를 참조할 가능성이 있는 객체의 메서드를 잠금 안에서 부르지 마라.** 콜백은 잠금 밖에서.
> 3. **다른 클래스의 메서드를 잠금 안에서 부를 필요가 정말 있는지 다시 보라.** 대개 다른 방법이 있다.
> 4. **상위 수준 동기화로 대체하라.** 태스크 연속과 합성기(46.4·46.9절), 데이터 병렬성(50장), 불변 타입(48.14절)은 잠금 자체를 줄인다.
> 5. **그래도 두 잠금이 남으면 전역 순서를 문서화하고 코드 리뷰로 강제하라.**

### 검출 — `TryEnter` 타임아웃

프로덕션에서 데드락을 "예방"에 전부 걸 수는 없다. **검출 장치**를 넣어 두면 프로세스가 조용히 멎는 대신 로그가 남는다.

```csharp
static bool EnterOrLog(object locker, string name,
                       [CallerMemberName] string caller = null)
{
    // 정상 상황에서는 절대 걸리지 않을 만큼 넉넉하게
    if (Monitor.TryEnter(locker, TimeSpan.FromSeconds(30))) return true;

    Logger.Error($"잠금 '{name}' 획득 실패 (30초). 호출자={caller}, " +
                 $"스레드={Environment.CurrentManagedThreadId}\n" +
                 $"{new System.Diagnostics.StackTrace(true)}");
    return false;   // 호출자는 반드시 실패를 처리해야 한다
}
```

이 기법의 장점은 **어느 스레드가 어느 잠금을 기다리다 실패했는지**가 스택 트레이스와 함께 남는다는 것이다. 상대편 스레드가 무엇을 쥐고 있는지는 여전히 모르지만, 절반은 알아낸 셈이다.

> **⚠️ 타임아웃 후 "그냥 진행"하지 마라**
>
> `TryEnter`가 `false`를 반환했을 때 잠금 없이 임계 구역에 들어가는 것은 데드락을 데이터 손상으로 바꾸는 것일 뿐이다. 타임아웃 시의 올바른 대응은 **실패를 보고하고 그 작업을 포기하는 것**이다. 데드락이 프로세스 전체를 멎게 만들었다면 그 프로세스를 내리는 것이 가장 안전한 선택일 때도 많다.

### 라이브락과 우선순위 역전

**라이브락(livelock)** 은 스레드가 막히지 않고 계속 실행되면서도 진행이 없는 상태다. 데이터가 계속 바뀌어 CAS 루프가 끝없이 재시도하거나, 두 스레드가 서로 양보하다가 아무도 못 가는 경우다. 데드락보다 진단이 어렵다 — CPU가 100%이므로 "일하는 중"처럼 보이기 때문이다.

**우선순위 역전(priority inversion)** 은 낮은 우선순위 스레드가 잠금을 쥔 채로 CPU를 못 받고, 그 잠금을 기다리는 높은 우선순위 스레드가 대기하는 상태다. 스핀락에서 특히 치명적이다.

> **⚠️ 스핀락과 스레드 우선순위**
>
> 스핀락은 단일 CPU 머신에서 쓰면 안 된다. 잠금을 쥔 스레드가 CPU를 얻지 못하면 놓을 수도 없는데, 기다리는 스레드가 스핀하며 CPU를 계속 붙들고 있기 때문이다. 잠금을 쥔 쪽의 우선순위가 더 낮으면 상황은 훨씬 나빠진다 — **완전한 라이브락**이다.
>
> Windows는 오랫동안 실행되지 못한 스레드의 우선순위를 일시적으로 올려 주는 동적 부스팅을 한다. 그래서 스핀락을 쓰는 스레드에서는 이 부스팅을 **꺼야** 할 수 있다. `System.Diagnostics.Process`와 `System.Diagnostics.ProcessThread`의 `PriorityBoostEnabled` 속성이 그 스위치다(45.7절, 73.5절).
>
> 하이퍼스레딩 CPU에서도 스핀락 문제가 있다. 두 논리 코어가 물리 실행 자원을 공유하므로 한쪽의 스핀이 다른 쪽의 진행을 방해한다. 이 문제들에 대응하는 로직이 `SpinWait`에 들어 있다(48.12절).

프로덕션 데드락은 대개 메모리 덤프로 온다. WinDbg + SOS로 읽는 최소 절차는 이렇다.

| 열 | 의미 |
|---|---|
| `SyncBlock Owner` | 잠금 객체의 주소와 타입 — 어떤 객체가 잠겼는가 |
| `Owning Thread Info` | 그 잠금을 **쥔** 스레드(관리 스레드 번호와 OS 스레드 ID) |
| `MonitorHeld` | 홀수면 잠금이 잡혀 있다. 나머지 비트가 대기 스레드 수를 나타낸다 |
| `Recursion` | 소유 스레드의 재귀 획득 횟수 |

위 출력은 두 개의 `System.Object`가 각각 다른 스레드에게 잡혀 있고, 각각에 대기자가 있다는 뜻이다. 데드락의 전형적인 모습이다.

그다음 각 스레드가 **어디서** 막혔는지 본다.

```text
0:000> ~6s
0:000> !clrstack
OS Thread Id: 0x2b18 (6)
        Child SP   IP  Call Site
        …          …   System.Threading.Monitor.Enter(System.Object)
        …          …   MyApp.Repository.Save(MyApp.Entity)
        …          …   MyApp.Service.Process()
```

모든 관리 스레드의 스택을 한 번에 보려면 다음을 쓴다.

```text
0:000> ~*e !clrstack
```

읽는 순서를 정리하면 이렇다.

1. `!syncblk`으로 **잠긴 객체 → 소유 스레드** 매핑을 만든다.
2. 각 소유 스레드의 `!clrstack`을 보고 **그 스레드가 무엇을 기다리는지** 확인한다.
3. "스레드 A는 객체 X를 쥐고 객체 Y를 기다리고, 스레드 B는 객체 Y를 쥐고 객체 X를 기다린다"는 순환을 찾는다.

> **📌 도구의 상세는 다른 장에**
>
> 덤프 수집 방법(`dotnet-dump collect`, `procdump`)과 심볼 설정은 74.5·74.6절에, SOS 명령 전반과 힙 분석은 66.9절에 있다. 여기서 기억할 것은 **`!syncblk` + `~*e !clrstack` 두 명령이 관리 데드락 분석의 90%**라는 것이다.
>
> 데드락이 커널 모드 구조(`Mutex`, `Semaphore`, 이벤트)에서 났다면 `!syncblk`에는 안 나온다. 그때는 네이티브 스택(`~*k`)에서 `WaitForSingleObjectEx` / `WaitForMultipleObjectsEx` 프레임을 찾아야 한다.

> **⚠️ 스레드 풀 기아는 데드락처럼 보인다**
>
> 덤프에서 모든 스레드 풀 스레드가 `Monitor.Enter`나 `Task.Wait`에 걸려 있다면, 진짜 데드락이 아니라 46.2절의 **스레드 풀 기아**일 수 있다. 구분하는 방법은 시간을 두고 두 번 덤프를 뜨는 것이다. 스택이 조금씩 진행한다면 기아이고, 완전히 동일하면 데드락이다.

## 48.9 잠금 성능과 경합(contention) 측정

### 무경합 비용 — 실제 수치

먼저 감을 잡자. 잠금이 **경합하지 않을 때** 얼마나 드는가?

| 구조 | 무경합 획득+해제 비용 | 출처 |
|---|---|---|
| `lock` (`Monitor`) | 20나노초 미만 (2020년대 머신) | Nutshell |
| `Mutex` | 약 0.5마이크로초 — `lock`의 20배 이상 | Nutshell |
| `Semaphore` (커널) | `WaitOne`+`Release` 약 1마이크로초 | Nutshell |
| `SemaphoreSlim` | 위의 약 1/10 | Nutshell |
| `AutoResetEvent`/`ManualResetEvent` | 약 1마이크로초 | Nutshell |
| `ManualResetEventSlim`/`CountdownEvent` | 짧은 대기에서 위의 최대 50배 빠름 | Nutshell |

Richter의 상대 비교 실험은 다른 각도에서 같은 이야기를 한다. 지역 `int`를 1,000만 번 증가시키는 데 걸린 시간을 기준으로 각 잠금의 오버헤드를 잰 것이다.

```csharp
var sw = Stopwatch.StartNew();
for (int i = 0; i < iterations; i++) x++;              // 잠금 없음

sw.Restart();
for (int i = 0; i < iterations; i++) { M(); x++; M(); } // 빈 메서드 호출 두 번

var sl = new SpinLock(false);
sw.Restart();
for (int i = 0; i < iterations; i++)
{
    bool taken = false; sl.Enter(ref taken); x++; sl.Exit();
}
// … 이하 잠금 종류를 바꿔 가며 반복. M은 [MethodImpl(NoInlining)]이 붙은 빈 메서드다
```

Richter가 얻은 결과다.

| 방식 | 밀리초 | 배수 |
|---|---|---|
| 잠금 없이 증가 | 8 | 기준 |
| 빈 메서드 호출 두 번 + 증가 | 69 | 약 9배 |
| `SpinLock`(사용자 모드) 안에서 증가 | 164 | 약 21배 |
| 단순 하이브리드 잠금 안에서 증가 | 164 | 약 21배 |
| 소유권·재귀를 지원하는 하이브리드 잠금 | 230 | 약 29배 |
| `AutoResetEvent` 기반 커널 잠금 | 8,854 | **약 1,107배** |

> **⚠️ 이 수치는 절대값이 아니라 비율로만 읽어라**
>
> Richter의 측정은 2012년경 하드웨어에서 .NET Framework으로 잰 것이다. 오늘의 절대 시간은 훨씬 짧다. 그러나 **비율의 구조는 변하지 않았다.** 사용자 모드 구조가 수십 사이클, 커널 전환이 수천 사이클 규모라는 사실은 CPU와 OS의 물리적 구조에서 나오기 때문이다.
>
> 그리고 이 실험은 **완전 무경합**이다. 경합이 있으면 그림이 완전히 달라진다.

### 경합 시 비용

무경합 잠금 획득은 원자 명령 하나에 가깝다. 경합이 나면 이야기가 다르다.

```text
  무경합 경로 (대부분)
  ┌─────────────────────────────────────────┐
  │ lock cmpxchg 로 헤더 워드 획득 → 끝     │  수십 사이클
  └─────────────────────────────────────────┘

  경합 경로 (드물지만 비싸다)
  ┌─────────────────────────────────────────┐
  │ 1. 짧게 스핀한다 (사용자 모드)          │  수백 사이클
  │ 2. 여전히 못 얻으면 팻 락으로 팽창      │  할당 + 초기화
  │ 3. 커널 이벤트에서 대기 (모드 전환)     │  수천 사이클
  │ 4. 깨어나면 스케줄러가 다시 배치        │  + 컨텍스트 스위치
  │ 5. 캐시가 식어 있어 재시작이 느리다     │  + 캐시 미스
  └─────────────────────────────────────────┘
```

한 번의 경합이 무경합 획득 **수백 배**의 비용을 만든다. 그래서 잠금 최적화의 목표는 "잠금을 빠르게 만드는 것"이 아니라 **"경합을 없애는 것"** 이다.

### 측정 — `dotnet-counters`

경합을 짐작하지 말고 재라. 가장 접근하기 쉬운 도구는 `dotnet-counters`다.

```bash
# 프로세스 목록
dotnet-counters ps

# System.Runtime 카운터 실시간 모니터링
dotnet-counters monitor --process-id 12345 --counters System.Runtime
```

여기서 볼 카운터는 다음과 같다.

| 카운터 | 의미 | 경합 진단에서의 역할 |
|---|---|---|
| `monitor-lock-contention-count` | 갱신 주기 동안 모니터 잠금 경합이 발생한 횟수 | **직접 지표.** 이 값이 계속 크면 잠금이 병목이다 |
| `threadpool-thread-count` | 스레드 풀 스레드 수 | 계속 늘면 블로킹이 스레드 주입을 유발하는 중이다 |
| `threadpool-queue-length` | 스레드 풀 큐의 작업 항목 수 | 쌓이면 처리가 밀리고 있다 |
| `cpu-usage` | CPU 사용률 | 낮은데 처리량도 낮으면 대기 바운드다 |

읽는 법의 요령은 이렇다.

- **CPU는 낮은데 처리량이 안 나온다 + `monitor-lock-contention-count`가 크다** → 잠금 경합이 병목이다.
- **CPU는 낮은데 처리량이 안 나온다 + 경합은 작다 + `threadpool-queue-length`가 크다** → 블로킹 I/O나 sync-over-async다(47.14절).
- **CPU가 100%인데 처리량이 안 나온다** → 스핀 기반 라이브락이거나 CAS 재시도 폭주다.

더 정밀한 분석은 이벤트 추적으로 간다. CLR은 잠금 경합에 대해 `ContentionStart`/`ContentionStop` 이벤트를 방출한다. `dotnet-trace`(73.9절)나 PerfView(66.7절)로 수집하면 **어느 스택에서 경합이 났는지**까지 알 수 있다.

```bash
dotnet-trace collect --process-id 12345 \
  --providers Microsoft-Windows-DotNETRuntime:0x4000:5
```

> **💡 측정 없이 잠금을 최적화하지 마라**
>
> 경험상 "잠금이 느릴 것 같아서" 잘게 쪼갠 코드의 대다수는 (a) 경합이 애초에 없었고, (b) 대신 데드락 위험과 조합 원자성 버그를 얻었다. 67장의 원칙이 여기에도 그대로 적용된다. **`monitor-lock-contention-count`로 경합의 존재를 확인한 뒤에만** 구조를 바꿔라.

### 경합을 줄이는 전략

경합이 실제로 확인되었다면 쓸 수 있는 카드는 다음과 같다. 위쪽이 대체로 효과가 크고 안전하다.

| 전략 | 내용 | 대가 |
|---|---|---|
| **잠금 범위 축소** | 잠금 안의 코드를 최소화한다. I/O·계산·콜백을 밖으로 뺀다 | 거의 없음. 항상 먼저 시도할 것 |
| **불변성** | 상태를 불변 객체로 만들고 참조 교체로 갱신한다(48.14절) | 갱신마다 객체 할당 |
| **읽기 전용 데이터 복제** | 초기화 후 변하지 않는 데이터는 아예 잠금 없이 읽는다 | 갱신 경로의 복잡도 |
| **스레드 로컬 누적 후 병합** | 각 스레드가 자기 부분 결과를 만들고 마지막에 한 번만 합친다 | 병합 로직. 중간 결과를 실시간으로 못 본다 |
| **잠금 분할(splitting)** | 서로 독립적인 상태를 서로 다른 잠금으로 나눈다 | 두 잠금을 함께 잡아야 하면 데드락 위험 |
| **잠금 샤딩(striping)** | 키의 해시로 N개 잠금 중 하나를 고른다. `ConcurrentDictionary`의 방식 | 전체를 잠가야 하는 연산이 비싸진다 |
| **읽기/쓰기 잠금** | 읽기 비중이 압도적일 때 `ReaderWriterLockSlim`(48.11절) | 무경합 비용이 `lock`의 약 2배 |
| **잠금 없는 자료구조** | `Interlocked` 기반 CAS 알고리즘 | 구현 난이도가 급격히 오른다. 검증이 어렵다 |

잠금 샤딩의 최소 형태는 이렇다.

```csharp
sealed class ShardedCounter
{
    private const int ShardCount = 32;   // 대개 코어 수 이상의 2의 거듭제곱
    private readonly object[] _locks;
    private readonly long[] _values;

    public ShardedCounter()
    {
        _locks = new object[ShardCount];
        _values = new long[ShardCount];
        for (int i = 0; i < ShardCount; i++) _locks[i] = new object();
    }

    public void Add(int key, long amount)
    {
        int shard = (key & int.MaxValue) % ShardCount;
        lock (_locks[shard]) _values[shard] += amount;
    }

    // 주의: 이 값은 "어느 한 시점의 스냅숏"이 아니다
    public long ApproximateTotal()
    {
        long sum = 0;
        for (int i = 0; i < ShardCount; i++)
            lock (_locks[i]) sum += _values[i];
        return sum;
    }
}
```

> **⚠️ 샤딩은 전역 일관성을 포기한다**
>
> `ApproximateTotal`은 각 샤드를 차례로 잠그며 더한다. 첫 샤드를 읽은 뒤 마지막 샤드를 읽기 전에 첫 샤드가 다시 바뀔 수 있다. 즉 **어떤 시점에도 실제로 존재하지 않았던 합계**가 나올 수 있다. 이 정도의 부정확성을 받아들일 수 있는 자리에만 샤딩을 쓴다. 정확한 스냅숏이 필요하면 모든 샤드를 동시에 잠가야 하고, 그 순간 샤딩의 이점이 사라진다.
>
> 그리고 `_values` 배열의 인접 원소는 **같은 캐시 라인에 놓인다.** 서로 다른 코어가 인접 샤드를 두드리면 거짓 공유로 성능이 무너진다. 실제 구현에서는 원소 사이에 패딩을 넣거나 각 샤드를 자기 캐시 라인에 정렬한다(70.6절).

## 48.10 `Mutex` — 크로스 프로세스 잠금

### 문법과 위치

`System.Threading.Mutex`는 상호 배제(**mut**ual **ex**clusion) 잠금이다. `lock`과 하는 일은 같지만 **커널 객체**로 구현되어 있어서 프로세스 경계를 넘을 수 있다.

```csharp
public sealed class Mutex : WaitHandle
{
    public Mutex();
    public Mutex(bool initiallyOwned, string name, out bool createdNew);
    public void ReleaseMutex();
}
```

`Mutex`는 `WaitHandle`에서 파생되므로 `WaitOne`으로 잠그고 `ReleaseMutex`로 푼다.

```csharp
sealed class LockWithMutex
{
    private static readonly Mutex _mutex = new Mutex();

    public void DoWork()
    {
        _mutex.WaitOne();
        try { /* 임계 구역 */ }
        finally { _mutex.ReleaseMutex(); }
    }
}
```

`ReleaseMutex`는 반드시 `finally`에서 불러야 한다. 예외가 나면 뮤텍스가 잠긴 채 남는다.

### `WaitHandle` 계층

커널 모드 구조는 모두 `WaitHandle`을 상속한다.

```text
   WaitHandle  (내부에 SafeWaitHandle — Win32 커널 객체 핸들)
     ├── EventWaitHandle
     │     ├── AutoResetEvent       (49.2절)
     │     └── ManualResetEvent     (49.2절)
     ├── Semaphore                  (48.11절)
     └── Mutex                      (이 절)
```

`WaitHandle`의 주요 멤버는 다음과 같다.

| 멤버 | 내부적으로 부르는 Win32 함수 | 설명 |
|---|---|---|
| `WaitOne()` / `WaitOne(timeout)` | `WaitForSingleObjectEx` | 이 핸들이 신호될 때까지 대기. 타임아웃이면 `false` |
| `WaitAll(WaitHandle[])` | `WaitForMultipleObjectsEx` (`bWaitAll=TRUE`) | **전부** 신호될 때까지 대기 |
| `WaitAny(WaitHandle[])` | `WaitForMultipleObjectsEx` (`bWaitAll=FALSE`) | **하나라도** 신호되면 그 인덱스를 반환. 타임아웃이면 `WaitHandle.WaitTimeout`(258) |
| `Dispose()` | `CloseHandle` | 커널 객체 핸들을 닫는다 |

**모든 커널 모드 구조의 메서드 호출은 전체 메모리 펜스다.**

> **⚠️ `WaitAll`/`WaitAny`의 배열은 64개를 넘을 수 없다**
>
> 넘기면 `NotSupportedException`이 던져진다. Win32 `WaitForMultipleObjectsEx`의 제약이 그대로 드러난 것이다.
>
> 그리고 `WaitAll`과 `WaitHandle.SignalAndWait`는 호출 스레드가 **다중 스레드 아파트먼트(MTA)** 여야 한다. WPF나 Windows Forms의 주 스레드는 단일 스레드 아파트먼트(STA)이므로 이 메서드들을 쓸 수 없다. 대안은 49.5절에 있다.

> **📌 `WaitHandle.Dispose`를 굳이 부르지 않아도 되는 드문 경우**
>
> `Dispose`를 부르려면 다른 스레드가 그 커널 객체를 더 이상 쓰지 않는다는 것을 **확실히** 알아야 한다. 이 확신을 코드로 유지하고 테스트하는 부담이 크다. Richter는 대기 핸들에 한해서는 `Dispose`를 부르지 말고 GC에 맡기라고 권한다 — GC는 아무 스레드도 그 객체를 쓰지 않는 시점을 알기 때문이다. 대기 핸들의 OS 부담이 가볍다는 점도 근거다.
>
> 33장의 일반 원칙("`IDisposable`이면 `Dispose`하라")에 대한 드문 예외다. 다른 비관리 리소스에 이 논리를 확장하지 마라.

### 명명된 뮤텍스와 단일 인스턴스 애플리케이션

`Mutex`의 진짜 존재 이유는 **프로세스 간 배타**다. 이름을 주면 그 뮤텍스는 컴퓨터 전역이 된다.

```csharp
// 회사·제품 URL 등 충돌하지 않을 이름을 쓴다
using var mutex = new Mutex(true, @"Global\contoso.com OneAtATimeDemo");

// 이전 인스턴스가 종료 중일 수 있으니 몇 초 기다려 본다
if (!mutex.WaitOne(TimeSpan.FromSeconds(3), false))
{
    Console.WriteLine("이미 실행 중인 인스턴스가 있다. 종료한다.");
    return;
}

try { RunProgram(); }
finally { mutex.ReleaseMutex(); }
```

`Global\` 접두사가 중요하다. 이것이 없으면 터미널 서비스 세션이나 별도의 Unix 콘솔마다 **다른 이름 공간**에 뮤텍스가 만들어져, 같은 세션 안의 애플리케이션에만 보인다. 모든 세션에서 보이게 하려면 `Global\`을 붙인다.

명명된 커널 객체를 이용한 더 가벼운 관용구도 있다. **동기화 동작 자체는 쓰지 않고, "이 이름의 커널 객체를 만든 것이 나인가"만 묻는 것**이다.

```csharp
public static class Program
{
    public static void Main()
    {
        bool createdNew;
        using (new Semaphore(0, 1, "SomeUniqueStringIdentifyingMyApp", out createdNew))
        {
            if (createdNew)
            {
                // 이 스레드가 커널 객체를 만들었다 → 다른 인스턴스가 없다
                // 나머지 애플리케이션을 여기서 실행한다
            }
            else
            {
                // 같은 이름의 커널 객체가 이미 있었다 → 다른 인스턴스가 실행 중이다
                // 아무것도 하지 않고 Main에서 반환해 두 번째 인스턴스를 종료한다
            }
        }
    }
}
```

Windows 커널은 같은 이름의 커널 객체를 **오직 하나의 스레드만 만들 수 있게** 보장한다. 두 프로세스가 정확히 동시에 시작해도 `createdNew`가 `true`인 쪽은 하나뿐이다. 여기서 `Semaphore`를 썼지만 `EventWaitHandle`이나 `Mutex`도 똑같이 동작한다 — 동기화 동작이 아니라 **생성의 배타성**을 쓰는 것이기 때문이다.

`EventWaitHandle`, `Semaphore`, `Mutex`는 정적 `OpenExisting` 메서드도 제공한다. 이름으로 기존 커널 객체를 여는 것이고, 그 이름의 객체가 없으면 `WaitHandleCannotBeOpenedException`이 던져진다.

> **⚠️ 명명된 객체의 플랫폼 차이**
>
> 명명된 `Mutex`는 Windows와 Unix 계열 플랫폼 모두에서 동작하지만, **명명된 `Semaphore`와 명명된 `EventWaitHandle`은 Windows 전용**이다. 크로스 플랫폼 앱에서 단일 인스턴스 관용구를 쓴다면 `Mutex`를 골라야 한다.

### `Mutex`만의 추가 동작 — 소유권과 재귀

`Mutex`는 다른 커널 구조에 없는 두 가지 로직을 갖는다. 그리고 그 두 가지가 `Mutex`를 느리게 만든다.

**첫째, 소유 스레드를 기록한다.** `Mutex` 객체는 자신을 획득한 스레드의 정수 ID를 저장한다. `ReleaseMutex`가 불리면 호출 스레드가 획득한 그 스레드인지 확인하고, 아니면 상태를 바꾸지 않고 예외를 던진다(Richter의 기술로는 `ApplicationException`).

**둘째, 재귀 카운트를 유지한다.** 뮤텍스를 이미 소유한 스레드가 다시 `WaitOne`을 부르면 재귀 카운트가 올라가고 스레드는 그냥 진행한다. `ReleaseMutex`마다 카운트가 내려가고, **0이 되어야** 다른 스레드가 소유자가 될 수 있다.

```csharp
sealed class SomeClass : IDisposable
{
    private readonly Mutex _lock = new Mutex();

    public void Method1()
    {
        _lock.WaitOne();
        // 작업…
        Method2();              // Method2가 같은 잠금을 재귀적으로 획득한다
        _lock.ReleaseMutex();
    }

    public void Method2()
    {
        _lock.WaitOne();
        // 작업…
        _lock.ReleaseMutex();
    }

    public void Dispose() => _lock.Dispose();
}
```

`Mutex` 대신 `AutoResetEvent`를 썼다면 `Method2`의 `WaitOne`에서 자기 자신을 기다리며 영원히 막혔을 것이다.

> **📌 재귀가 필요하면 관리 코드로 만드는 편이 훨씬 빠르다**
>
> `Mutex`의 소유권·재귀 로직은 커널 안에 있다. 그래서 재귀 획득 한 번마다 커널 전환이 일어난다. 같은 동작을 `AutoResetEvent` 위에 관리 코드로 구현하면 — 소유 스레드 ID와 재귀 카운트를 관리 코드의 필드로 들고 있으면 — 재귀 획득이 **관리 코드 안에서 끝난다.** 커널에는 처음 획득할 때와 최종적으로 놓을 때만 들어간다.
>
> 물론 실무에서 프로세스 안의 재귀 잠금이 필요하면 그냥 `lock`을 쓴다. 이 대비가 말하는 것은 하나다 — **기능 하나를 추가하는 비용이 어느 층에 붙느냐가 성능을 결정한다.**

`Mutex`에만 있는 또 하나의 동작이다. **뮤텍스를 소유한 스레드가 어떤 이유로든 종료되면**, 그 뮤텍스를 기다리던 스레드 중 하나가 깨어나면서 `System.Threading.AbandonedMutexException`을 받는다.

이 예외는 대개 처리되지 않고 프로세스를 종료시킨다. **그리고 그게 옳다.** 어떤 스레드가 뮤텍스를 잡고 데이터를 갱신하다가 갱신을 끝내지 못하고 죽었다는 뜻이기 때문이다. 그 데이터는 깨져 있을 가능성이 높다. 이 예외를 잡아서 계속 진행하면 **깨진 데이터를 만지게 되어** 예측 불가능한 결과와 보안 문제로 이어진다.

> **⚠️ `ReleaseMutex`를 잊고 `Dispose`만 하면 다른 대기자가 예외를 받는다**
>
> ```csharp
> using var mutex = new Mutex(true, @"Global\MyApp");
> // ReleaseMutex를 부르지 않고 using 블록을 벗어난다
> ```
>
> `Dispose`(또는 `Close`)만 호출하고 `ReleaseMutex`를 부르지 않으면, 그 뮤텍스를 기다리던 다른 코드에 `AbandonedMutexException`이 던져진다. 단일 인스턴스 관용구를 쓸 때 자주 나오는 실수다. **획득했으면 반드시 `finally`에서 `ReleaseMutex`를 불러라.**

### 스레드 친화성 — async와 섞으면 안 되는 이유

`Mutex`는 **획득한 스레드만 해제할 수 있다.** 이 성질을 **스레드 친화성(thread affinity)** 이라 부른다(45.3절).

이것이 `async`/`await`와 근본적으로 충돌한다.

```csharp
// 절대 하면 안 되는 코드
async Task BadAsync()
{
    _mutex.WaitOne();                  // 스레드 A가 뮤텍스를 획득

    await SomethingAsync();            // 여기서 스레드가 바뀔 수 있다

    _mutex.ReleaseMutex();             // 스레드 B가 해제를 시도 → 예외
}
```

`await` 이후의 코드는 다른 스레드에서 실행될 수 있다(47.7절, 47.12절). 그러면 `ReleaseMutex`를 부르는 스레드가 획득한 스레드가 아니게 되고, 뮤텍스는 예외를 던진다. 설령 우연히 같은 스레드로 돌아왔더라도 그것은 우연일 뿐 보장이 아니다.

같은 이유로 **`lock` 블록 안에서는 `await`가 컴파일 오류**다. C# 컴파일러가 아예 막는다.

| 구조 | 스레드 친화성 | `async`와 함께 쓸 수 있나 |
|---|---|---|
| `lock` / `Monitor` | **있음** (소유) | 불가 — `await` 자체가 컴파일 오류 |
| `Mutex` | **있음** (소유) | 불가 — 컴파일은 되지만 런타임에 깨진다 |
| `ReaderWriterLockSlim` | **있음** (소유) | 불가 |
| `SpinLock` | 옵션에 따라 | 불가 |
| `Semaphore` / `SemaphoreSlim` | **없음** | **`SemaphoreSlim.WaitAsync`로 가능** (48.11절) |

> **💡 `Mutex`를 언제 쓰는가**
>
> 딱 하나의 경우다. **프로세스 경계를 넘어야 할 때.**
>
> - 단일 인스턴스 애플리케이션
> - 여러 프로세스가 공유하는 파일이나 하드웨어 자원의 보호
> - 설치 프로그램이나 업데이터가 본 애플리케이션과 조율해야 할 때
>
> 프로세스 안에서만 배타가 필요하다면 `Mutex`를 쓸 이유가 전혀 없다. `lock`이 20배 이상 빠르고, 소유권·재귀 동작도 갖고 있다.

## 48.11 비배타적 잠금 — `Semaphore`, `SemaphoreSlim`, 읽기/쓰기 잠금

배타적 잠금은 임계 구역에 한 스레드만 들여보낸다. **비배타적 잠금**은 동시성을 제한할 뿐 완전히 직렬화하지는 않는다.

### 세마포어의 개념

세마포어는 **정원이 정해진 나이트클럽**이다. 클럽이 꽉 차면 아무도 못 들어가고 밖에 줄이 선다. 누군가 나가면 한 명이 들어간다.

내부적으로 세마포어는 커널이 유지하는 **정수 카운트**다. 카운트가 0이면 대기 중인 스레드가 막히고, 0보다 크면 통과한다. 스레드가 통과할 때 카운트가 1 줄고, `Release`할 때 늘어난다. 최대 카운트를 넘어서 `Release`하면 `SemaphoreFullException`이 던져진다.

```csharp
public sealed class Semaphore : WaitHandle
{
    public Semaphore(int initialCount, int maximumCount);
    public int Release();                  // Release(1)과 같다. 이전 카운트를 반환
    public int Release(int releaseCount);  // 이전 카운트를 반환
}
```

**세마포어에는 소유자가 없다.** 이것이 `Mutex`·`lock`과의 결정적 차이다. 아무 스레드나 `Release`를 부를 수 있다. 스레드 A가 `Wait`하고 스레드 B가 `Release`해도 정상이다.

초기 카운트를 1로 준 세마포어는 배타적 잠금처럼 동작하지만, 소유권과 재귀가 없다는 점이 다르다.

> **📌 세 커널 프리미티브의 깨우기 동작 비교**
>
> 자동 리셋 이벤트(`AutoResetEvent`)에 신호를 보내면 대기 중인 스레드 **하나**만 깨어나고 커널이 자동으로 다시 `false`로 되돌린다. 수동 리셋 이벤트(`ManualResetEvent`)는 대기 중인 스레드 **전부**를 깨우고 `Reset`을 명시적으로 부를 때까지 열려 있다. 세마포어는 `Release(n)`의 `n`만큼 깨운다.
>
> 자동 리셋 이벤트는 최대 카운트 1인 세마포어와 매우 비슷하다. 차이는 `Set`을 연속으로 여러 번 불러도 여전히 하나만 깨어나는 반면(추가 티켓이 버려진다), 세마포어는 `Release`를 여러 번 부르면 카운트가 계속 올라가 여러 스레드를 깨울 수 있다는 점이다. 이 구조들의 상세는 49.1~49.2절에 있다.

### `Semaphore` vs `SemaphoreSlim`

기능적으로 유사한 두 클래스가 있다.

| | `Semaphore` | `SemaphoreSlim` |
|---|---|---|
| 구현 | 순수 커널 객체 | 하이브리드 — 사용자 모드에서 스핀 후 필요하면 커널 대기 |
| 무경합 비용 | `WaitOne`+`Release` 약 1마이크로초 | 그 약 1/10 |
| 이름 지정(프로세스 간) | 가능(**Windows 전용**) | **불가** |
| `CancellationToken` 지원 | 없음 | **있음** |
| 비동기 대기 | 없음 | **`WaitAsync`** |
| `WaitHandle` 파생 | 예 (`WaitAny`/`WaitAll` 참여 가능) | 아니오 (`AvailableWaitHandle` 속성으로 노출) |

특별한 이유가 없으면 `SemaphoreSlim`이다.

```csharp
class TheClub                      // 명단 없음!
{
    static SemaphoreSlim _sem = new SemaphoreSlim(3);   // 정원 3

    static void Main() { for (int i = 1; i <= 5; i++) new Thread(Enter).Start(i); }

    static void Enter(object id)
    {
        Console.WriteLine(id + " 입장 대기");
        _sem.Wait();
        Console.WriteLine(id + " 입장!");        // 동시에 최대 세 스레드만
        Thread.Sleep(1000 * (int)id);
        Console.WriteLine(id + " 퇴장");
        _sem.Release();
    }
}
```

출력을 보면 1·2·3이 차례로 들어간 뒤 4와 5는 대기하고, 1이 나가야 4가, 2가 나가야 5가 들어간다.

초기 카운트를 0으로 두고 나중에 `Release`로 늘리는 것도 합법이다. 다음 두 줄은 동등하다.

```csharp
var semaphore1 = new SemaphoreSlim(3);
var semaphore2 = new SemaphoreSlim(0); semaphore2.Release(3);
```

### `SemaphoreSlim.WaitAsync` — 유일하게 async와 함께 쓸 수 있는 잠금

`await` 위에 잠금을 거는 것은 불가능하다.

```csharp
lock (_locker)
{
    await Task.Delay(1000);   // 컴파일 오류
}
```

컴파일러가 막는 것은 옳다. 잠금은 스레드가 소유하는데 `await`에서 돌아올 때 스레드가 바뀔 수 있고(48.10절), 게다가 잠금은 블로킹인데 오래 블로킹하지 않으려는 것이 비동기의 목적이기 때문이다.

그럼에도 비동기 연산을 순차화하거나 동시 실행 수를 제한해야 할 때가 있다. **`SemaphoreSlim.WaitAsync`가 이 문제의 정답이다.**

```csharp
public Task<bool> WaitAsync(int millisecondsTimeout, CancellationToken cancellationToken);
```

세마포어에는 소유자가 없으므로 "획득한 스레드가 해제해야 한다"는 제약이 없다. 그래서 `await`를 가로질러도 문제가 없다.

가장 흔한 관용구는 **동시성 제한**이다. 웹 브라우저가 다운로드를 병렬로 하되 최대 10개로 제한하고 싶다면 이렇게 쓴다.

```csharp
SemaphoreSlim _semaphore = new SemaphoreSlim(10);

async Task<byte[]> DownloadWithSemaphoreAsync(string uri)
{
    await _semaphore.WaitAsync();
    try
    {
        return await _httpClient.GetByteArrayAsync(uri);
    }
    finally
    {
        _semaphore.Release();
    }
}
```

`initialCount`를 1로 줄이면 최대 병렬도가 1이 되고, 이것이 곧 **비동기 잠금**이다.

`try`/`finally`가 지저분하다면 확장 메서드로 감쌀 수 있다.

```csharp
public static async Task<IDisposable> EnterAsync(this SemaphoreSlim ss)
{
    await ss.WaitAsync().ConfigureAwait(false);
    return Disposable.Create(() => ss.Release());   // 익명 disposal (33.5절)
}

// 사용
async Task<byte[]> DownloadWithSemaphoreAsync(string uri)
{
    using (await _semaphore.EnterAsync())
        return await _httpClient.GetByteArrayAsync(uri);
}
```

> **⚠️ `Release`를 `finally`에서 부르지 않으면 세마포어가 영구히 줄어든다**
>
> 예외 경로에서 `Release`를 빠뜨리면 그 티켓은 영영 회수되지 않는다. 몇 번 반복되면 세마포어의 유효 정원이 0이 되고 **모든 호출이 영원히 대기**한다. 겉으로는 데드락과 구별되지 않는다. `Release`는 항상 `finally`에서, 또는 위 `using` 관용구로.

> **📌 .NET 6 이후의 대안 — `Parallel.ForEachAsync`**
>
> 비동기 동시성을 제한하는 방법이 하나 더 있다.
>
> ```csharp
> await Parallel.ForEachAsync(uris,
>     new ParallelOptions { MaxDegreeOfParallelism = 10 },
>     async (uri, cancelToken) =>
>     {
>         var download = await _httpClient.GetByteArrayAsync(uri, cancelToken);
>         Console.WriteLine($"{download.Length} 바이트 다운로드");
>     });
> ```
>
> 컬렉션 전체를 제한된 병렬도로 처리하는 것이 목적이라면 이쪽이 훨씬 읽기 쉽다. 자세한 내용은 50.7절에 있다. 반면 **개별 호출 지점마다** 제한을 걸어야 하거나 호출이 여러 진입점에서 들어온다면 `SemaphoreSlim`이 맞다.

### `ReaderWriterLockSlim`

타입의 인스턴스가 **동시 읽기에는 안전하지만 동시 갱신에는 안전하지 않은** 경우가 흔하다. 이럴 때 모든 접근을 하나의 배타적 잠금으로 감싸면 안전하기는 하지만, 읽기가 많고 갱신이 드문 상황에서 동시성을 지나치게 제한한다. 애플리케이션 서버가 자주 쓰는 데이터를 정적 필드에 캐시하는 상황이 대표적이다.

`System.Threading.ReaderWriterLockSlim`이 이 문제를 푼다. 잠금이 두 종류다.

- **쓰기 잠금(write lock)** 은 완전히 배타적이다.
- **읽기 잠금(read lock)** 은 다른 읽기 잠금과 호환된다.

즉 한 스레드가 쓰기 잠금을 쥐면 읽기·쓰기 모두 막히고, 아무도 쓰기 잠금을 쥐지 않았으면 읽기 잠금은 몇 개든 동시에 잡힌다.

```csharp
public class ReaderWriterLockSlim : IDisposable
{
    public ReaderWriterLockSlim(LockRecursionPolicy recursionPolicy);

    public void EnterReadLock();
    public bool TryEnterReadLock(int millisecondsTimeout);
    public void ExitReadLock();

    public void EnterWriteLock();
    public bool TryEnterWriteLock(int millisecondsTimeout);
    public void ExitWriteLock();

    public void EnterUpgradeableReadLock();
    public void ExitUpgradeableReadLock();
    // 모니터링용 속성 다수
}
```

세 스레드가 계속 리스트를 열거하고, 두 스레드가 100ms마다 난수를 추가하는 예다.

```csharp
class SlimDemo
{
    static ReaderWriterLockSlim _rw = new ReaderWriterLockSlim();
    static List<int> _items = new List<int>();
    static Random _rand = new Random();

    static void Main()
    {
        new Thread(Read).Start();  new Thread(Read).Start();  new Thread(Read).Start();
        new Thread(Write).Start("A");  new Thread(Write).Start("B");
    }

    static void Read()
    {
        while (true)
        {
            _rw.EnterReadLock();
            foreach (int i in _items) Thread.Sleep(10);
            _rw.ExitReadLock();
        }
    }

    static void Write(object threadID)
    {
        while (true)
        {
            int newNumber = GetRandNum(100);
            _rw.EnterWriteLock();
            _items.Add(newNumber);
            _rw.ExitWriteLock();
            Console.WriteLine("스레드 " + threadID + " 가 " + newNumber + " 추가");
            Thread.Sleep(100);
        }
    }

    static int GetRandNum(int max) { lock (_rand) return _rand.Next(max); }
}
```

`Write` 안에서 `Console.WriteLine(_rw.CurrentReadCount + " 명이 동시에 읽는 중")` 을 찍어 보면 거의 항상 3이 나온다 — 세 읽기 스레드가 실제로 동시에 들어가 있다는 뜻이다.

> **⚠️ 예제 코드에는 `try`/`finally`가 없다**
>
> 위 예제는 지면을 아끼려고 `try`/`finally`를 생략했다. 프로덕션 코드에서는 반드시 `_rw.EnterReadLock(); try { … } finally { _rw.ExitReadLock(); }` 형태로 써야 한다. `Enter…Lock`과 `Exit…Lock` 사이에서 예외가 나면 잠금이 영구히 잠긴 채 남는다.

### 업그레이드 가능 읽기 잠금

읽기 잠금을 쓰기 잠금으로 **원자적으로** 바꾸고 싶을 때가 있다. 리스트에 항목이 없을 때만 추가하는 경우다. 순진하게 하면 이렇게 된다.

1. 읽기 잠금을 얻는다.
2. 항목이 이미 있는지 검사한다. 있으면 잠금을 풀고 반환한다.
3. 읽기 잠금을 푼다.
4. 쓰기 잠금을 얻는다.
5. 항목을 추가한다.

문제는 3번과 4번 사이다. 다른 스레드가 그 틈에 같은 항목을 넣을 수 있다.

`ReaderWriterLockSlim`은 이를 위해 세 번째 종류의 잠금인 **업그레이드 가능 읽기 잠금(upgradeable read lock)** 을 제공한다.

```csharp
while (true)
{
    int newNumber = GetRandNum(100);

    _rw.EnterUpgradeableReadLock();
    if (!_items.Contains(newNumber))
    {
        _rw.EnterWriteLock();          // 원자적으로 쓰기 잠금으로 승격
        _items.Add(newNumber);
        _rw.ExitWriteLock();           // 다시 업그레이드 가능 읽기 잠금으로
        Console.WriteLine("스레드 " + threadID + " 가 " + newNumber + " 추가");
    }
    _rw.ExitUpgradeableReadLock();

    Thread.Sleep(100);
}
```

업그레이드 가능 잠금은 임의 개수의 읽기 잠금과 공존할 수 있지만, **한 번에 하나만** 잡힐 수 있다. 이 제약이 승격 경쟁을 직렬화해서 **변환 데드락**을 막는다. SQL Server의 잠금과 정확히 대응된다.

SQL Server의 공유 잠금(share lock)이 읽기 잠금에, 배타 잠금(exclusive lock)이 쓰기 잠금에, 업데이트 잠금(update lock)이 업그레이드 가능 읽기 잠금에 대응한다.

> **📌 승격은 "잠깐 놓았다가 다시 잡기"다**
>
> 승격이 마법은 아니다. 다른 읽기 스레드가 있으면 그들이 전부 잠금을 나갈 때까지 승격은 완료되지 않는다. 즉 승격은 **읽기 잠금을 놓고 즉시 쓰기 잠금을 잡는 것과 실질적으로 같다.** 다른 점은 그사이에 다른 업그레이드 가능 잠금이 끼어들 수 없다는 것뿐이고, 그것이 정확성의 핵심이다.

### 재귀 정책

기본적으로 `ReaderWriterLockSlim`은 중첩·재귀 잠금을 금지한다.

```csharp
var rw = new ReaderWriterLockSlim();
rw.EnterReadLock();
rw.EnterReadLock();     // LockRecursionException
```

생성자에 `LockRecursionPolicy.SupportsRecursion`을 주면 허용된다.

```csharp
var rw = new ReaderWriterLockSlim(LockRecursionPolicy.SupportsRecursion);
```

재귀를 허용하면 한 스레드가 두 종류의 잠금을 동시에 쥘 수 있게 되어 복잡해진다.

```csharp
rw.EnterWriteLock();
rw.EnterReadLock();
Console.WriteLine(rw.IsReadLockHeld);    // True
Console.WriteLine(rw.IsWriteLockHeld);   // True
rw.ExitReadLock();
rw.ExitWriteLock();
```

기본 규칙은 이렇다. **잠금을 얻은 뒤의 재귀 잠금은 다음 척도에서 더 낮거나 같을 수는 있어도 높을 수는 없다.**

```text
   읽기 잠금  →  업그레이드 가능 잠금  →  쓰기 잠금
```

업그레이드 가능 잠금을 쓰기 잠금으로 승격하는 요청만은 언제나 합법이다.

> **⚠️ 읽기/쓰기 잠금의 재귀는 특히 비싸다**
>
> Richter는 `ReaderWriterLockSlim`을 만들 때 항상 `LockRecursionPolicy.NoRecursion`을 넘기라고 권한다. 읽기/쓰기 잠금에서 스레드 소유권과 재귀를 지원하는 것은 **엄청나게 비싸다.** 잠금이 들여보낸 **모든 읽기 스레드**를 추적하고 각각에 대해 별도의 재귀 카운트를 유지해야 하기 때문이다. 그리고 그 정보 자체를 스레드 안전하게 관리하려고 `ReaderWriterLockSlim`은 내부적으로 **배타적 스핀락을 쓴다.** 농담이 아니다.

### 구형 `ReaderWriterLock`을 쓰지 마라

.NET Framework 1.0에 `ReaderWriterLock`이 있었다. 문제가 너무 많아서 .NET Framework 3.5에서 `ReaderWriterLockSlim`이 새로 만들어졌다. 기존 애플리케이션과의 호환성 때문에 구형 클래스를 고칠 수 없어 새로 시작한 것이다. 구형 클래스의 문제는 이랬다.

- 경합이 없어도 매우 느리다.
- 스레드 소유권·재귀 동작을 **끌 수 없어** 더 느리다.
- **읽기 스레드를 쓰기 스레드보다 우대**한다. 그 결과 쓰기 스레드가 줄만 서고 거의 서비스되지 못해 서비스 거부 상태가 될 수 있다.
- 잠금 변환(승격)을 지원하지만 업그레이드 가능 잠금 개념이 없어 **신뢰할 수 없다.**

`ReaderWriterLock`의 `AcquireXXX`/`ReleaseXXX` 메서드는 타임아웃 시 `false`를 반환하는 대신 `ApplicationException`을 던진다는 차이도 있다. **새 코드에서 쓸 이유는 없다.**

### 그래서 읽기/쓰기 잠금을 쓸 것인가

여기가 실무에서 가장 자주 잘못 판단되는 지점이다.

> **💡 읽기 비중이 압도적이지 않으면 그냥 `lock`이 빠르다**
>
> `ReaderWriterLockSlim`은 평범한 `lock`(`Monitor.Enter`/`Exit`)보다 **약 두 배 느리다.** 읽기와 쓰기를 구분하고, 읽기 카운트를 유지하고, 대기 큐를 세 갈래로 관리하는 비용이다.
>
> 즉 읽기/쓰기 잠금은 **"읽기가 압도적으로 많고, 각 읽기가 잠금을 상당한 시간 붙들고 있을 때"** 에만 이긴다. 짧은 읽기가 많은 경우에는 동시 읽기의 이득보다 잠금 자체의 오버헤드가 커서 `lock`이 이긴다.
>
> **판단 절차는 이렇다.**
>
> 1. `lock`으로 구현한다.
> 2. `monitor-lock-contention-count`로 경합을 확인한다(48.9절).
> 3. 경합이 실재하고, 읽기가 90% 이상이고, 읽기 구간이 짧지 않다면 `ReaderWriterLockSlim`을 시도한다.
> 4. **바꾼 뒤 다시 측정한다.** 느려졌다면 되돌린다.
>
> 그리고 4번 전에 한 가지를 더 고려하라. 읽기가 압도적이라면 **불변 스냅숏 교체**(48.14절)나 `ConcurrentDictionary`(24.12절)가 읽기 경로에서 잠금을 아예 없앨 수 있다. 그게 되면 읽기/쓰기 잠금보다 훨씬 빠르다.

## 48.12 스핀락, 스핀 대기, 스레드 소유권과 재귀

### `SpinLock` — 값 타입 잠금

48.4절에서 `Interlocked.Exchange`만으로 스핀락을 만들 수 있음을 봤다. .NET은 그것을 다듬은 `System.Threading.SpinLock`을 제공한다. 차이는 스핀 루프 안에서 `SpinWait`를 써서 백오프(back-off)를 한다는 것과 타임아웃을 지원한다는 것이다.

```csharp
var spinLock = new SpinLock(enableThreadOwnerTracking: false);

bool lockTaken = false;
try { spinLock.Enter(ref lockTaken); /* 아주 짧은 임계 구역 */ }
finally { if (lockTaken) spinLock.Exit(); }
```

`Monitor.Enter`와 같은 `lockTaken` 패턴을 쓴다(48.5절). 생성자 인수 `enableThreadOwnerTracking`은 소유 스레드를 추적할지 정한다. `true`면 잘못된 사용(같은 스레드의 재귀 진입, 다른 스레드의 `Exit`)을 예외로 잡아 주지만 느려진다. 프로덕션에서는 대개 `false`로 만든다.

> **⚠️ `SpinLock`은 값 타입이다 — 복사하면 동기화가 사라진다**
>
> `SpinLock`은 구조체다. 가볍고 메모리 친화적이라는 장점이 있다 — 컬렉션의 항목마다 잠금을 하나씩 붙여야 하는 상황에 적합하다. 대신 **값 의미론이 함정을 만든다.**
>
> - **`SpinLock`을 메서드에 값으로 전달하면 복사본이 만들어진다.** 그 복사본을 잠가 봐야 원본과 아무 관계가 없다. 넘겨야 한다면 `ref`로 넘긴다.
> - **`SpinLock` 필드를 `readonly`로 선언하지 마라.** `readonly` 필드에 대해 인스턴스 메서드를 부르면 컴파일러가 방어적 복사본을 만든다(16장). `Enter`는 그 복사본을 잠그고 사라진다. 잠금은 아무것도 하지 않은 것이 된다. 그리고 **조용히** 그렇게 된다.
> - `SpinLock`을 프로퍼티로 노출하거나 `object`에 담지 마라. 박싱되면 같은 문제가 생긴다.
>
> 이 함정이 `SpinLock`을 위험하게 만든다. 사용을 정당화할 만큼 빠르지도 않다.

> **💡 `SpinLock`을 쓰지 마라 — 거의 항상**
>
> Richter의 판단은 명확하다. **`SpinLock`은 `Monitor`보다 약간 빠를 뿐인데, CPU 시간을 낭비할 잠재적 위험이 있어서 그 정도 이득으로는 정당화되지 않는다.**
>
> `SpinLock`이 정당한 경우는 이렇게 좁다.
>
> - 임계 구역이 **수십 나노초** 규모로 확실히 짧다.
> - 다중 코어 머신에서만 돈다.
> - 잠금 객체가 아주 많아서 `Monitor`의 객체 헤더 경로조차 부담이다.
> - 그리고 **측정으로 이득을 확인했다.**
>
> Richter의 `AsyncOneManyLock` 구현이 좋은 예다. 그 안의 `SpinLock`은 정수 계산 몇 개와 큐 조작 한 번만을 감싼다 — 잠금 보유 시간이 확실히 유한하고 아주 짧다. 그런 경우에만 정당하다.

### `SpinWait` — 단계적 백오프

`SpinLock`의 스핀 루프 안에서 무엇을 해야 하는가? 그냥 계속 도는 것은 최악이다. `System.Threading.SpinWait` 구조체가 이 "흑마술"을 캡슐화한다.

```csharp
var spinwait = new SpinWait();
while (!TryDoSomething())
    spinwait.SpinOnce();
```

`SpinOnce`는 호출 횟수가 늘어남에 따라 점점 더 양보하는 쪽으로 전략을 바꾼다. 내부적으로 `Thread`의 세 정적 메서드를 조합한다.

| 단계 | 부르는 것 | 하는 일 |
|---|---|---|
| 초반 | `Thread.SpinWait(n)` | 특수 CPU 명령(x86의 `pause`, ARM의 `yield`)을 n번 실행. **OS에 아무것도 알리지 않는다.** 하이퍼스레딩 CPU에서 다른 논리 코어에 실행 자원을 넘긴다 |
| 중반 | `Thread.Yield()` | 같은 프로세서에서 실행 준비된 다른 스레드가 있으면 그쪽에 타임슬라이스를 넘긴다. 넘겼으면 `true` 반환 |
| 후반 | `Thread.Sleep(0)` / `Thread.Sleep(1)` | 스레드를 스케줄 대상에서 잠시 뺀다 |

세 가지의 차이를 정확히 알아 두면 스핀 코드를 읽을 때 도움이 된다.

- **`Thread.Sleep(0)`** — 현재 타임슬라이스의 나머지를 포기하고 다른 스레드를 스케줄하게 한다. 다만 **더 낮은 우선순위의 스레드는 실행되지 못한다.** 그리고 같은 우선순위 이상의 스케줄 가능한 스레드가 없으면 방금 `Sleep`을 부른 스레드가 다시 스케줄된다.
- **`Thread.Yield()`** — `Sleep(0)`과 `Sleep(1)`의 중간이다. 현재 프로세서에서 실행할 다른 스레드가 있으면 넘기고, 없으면 `false`를 반환하며 그냥 진행한다. 낮은 우선순위 스레드에도 기회를 준다.
- **`Thread.Sleep(1)`** — 항상 컨텍스트 스위치를 강제하고, 시스템 타이머 해상도 때문에 실제로는 1밀리초보다 오래 잔다.
- **`Thread.SpinWait(n)`** — 커널에 전혀 들어가지 않는다. 하이퍼스레딩이 아닌 CPU에서는 사실상 무시된다.

> **⚠️ `Thread.Sleep`의 두 가지 오해**
>
> `Timeout.Infinite`(-1)를 넘기면 그 스레드는 영원히 스케줄되지 않는다. 아무 쓸모가 없다 — 스레드를 끝내서 스택과 커널 객체를 회수하는 편이 항상 낫다. 그리고 `Thread.Sleep(100)`은 "정확히 100밀리초"가 아니라 "**대략** 100밀리초, 경우에 따라 수 초 이상"이다. Windows는 실시간 운영체제가 아니다.

### 스레드 소유권과 재귀 지원표

지금까지 나온 잠금들을 두 축으로 정리하자.

| 구조 | 스레드 소유권 | 재귀 | 다른 스레드가 해제 가능? | 구현 |
|---|---|---|---|---|
| `Monitor` (`lock`) | 있음 | **지원** | 불가 | 하이브리드 |
| `Mutex` | 있음 | **지원** | 불가 | 커널 |
| `SpinLock` | 옵션(`enableThreadOwnerTracking`) | 미지원 | 옵션에 따라 | 사용자 모드 |
| `ReaderWriterLockSlim` | 있음 | 정책에 따라(`LockRecursionPolicy`) | 불가 | 하이브리드 |
| `Semaphore` | **없음** | 해당 없음 | **가능** | 커널 |
| `SemaphoreSlim` | **없음** | 해당 없음 | **가능** | 하이브리드 |
| `AutoResetEvent` / `ManualResetEvent` | **없음** | 해당 없음 | **가능** | 커널 |
| `System.Threading.Lock` ※.NET 9 | 있음 | **지원** | 불가 | 하이브리드(전용) |

이 표에서 두 가지를 읽어야 한다.

**첫째, 소유권이 없는 구조만 `async`와 함께 쓸 수 있다.** 표의 "다른 스레드가 해제 가능?" 열이 곧 그 판정이다(48.10절).

**둘째, 기능마다 비용이 붙는다.** 소유권 추적은 스레드 ID 필드와 비교를, 재귀는 카운트 필드와 증감을 요구한다. Richter의 하이브리드 잠금 비교에서 소유권·재귀 없는 버전(기준 대비 21배)과 있는 버전(29배)의 차이가 그 비용이다.

> **📌 `Monitor`가 재귀를 지원하면서도 빠른 이유**
>
> 위 논리대로면 `Monitor`도 느려야 한다. 실제로는 매우 빠르다. 이유는 두 가지다. 첫째, `Monitor`는 관리 코드가 아니라 **네이티브 코드**로 구현되어 있다. 둘째, 경합 없는 경로에서는 객체 헤더의 씬 락만 건드리고 끝난다(48.5절). 소유 스레드 ID와 재귀 카운트가 그 한 워드 안에 이미 들어 있으므로 추가 필드 접근이 없다.

## 48.13 이중 검사 잠금(double-check locking)의 정확한 구현

### 문제 — 지연 초기화의 스레드 안전성

싱글턴 객체를 애플리케이션이 요구할 때까지 만들지 않고 미루고 싶다. 아무도 요구하지 않으면 아예 만들지 않아 시간과 메모리를 아낀다. 문제는 여러 스레드가 동시에 요구할 때 **정확히 한 번만** 만들어야 한다는 것이다.

가장 단순한 시도는 이렇다.

```csharp
Expensive _expensive;
readonly object _expenseLock = new object();

public Expensive Expensive
{
    // 잠금 없이 이렇게만 쓰면 스레드 안전하지 않다:
    //   if (_expensive == null) _expensive = new Expensive();
    //   return _expensive;
    get
    {
        lock (_expenseLock)
        {
            if (_expensive == null) _expensive = new Expensive();
            return _expensive;
        }
    }
}
```

주석 처리한 잠금 없는 버전에서는 두 스레드가 동시에 `if`를 통과해 각각 다른 `Expensive` 인스턴스를 만들 수 있고, 그중 어느 쪽이 필드에 남는지도 정해져 있지 않다. 잠금도 배리어도 없이 `_expensive`에 접근한다는 문제도 있다.

`lock`으로 감싼 위 버전은 정확하다. 다만 **이미 만들어진 뒤에도 매번 잠금을 잡는다.** 이 비용을 없애려는 것이 이중 검사 잠금이다.

### 이중 검사 잠금의 발상

```csharp
sealed class Singleton
{
    // 이 잠금이 필요한 것은 스레드 안전성 때문이다. 이 패턴은 "싱글턴을 만드는 비용이
    // System.Object 하나 만드는 비용보다 크고, 아예 안 만들 수도 있다"를 전제한다.
    // 그렇지 않다면 그냥 클래스 생성자에서 만드는 편이 더 효율적이고 쉽다.
    private static readonly object s_lock = new object();

    private static Singleton s_value = null;

    private Singleton() { /* 초기화 */ }

    public static Singleton GetSingleton()
    {
        // 이미 만들어졌으면 그냥 반환한다 (빠른 경로 — 잠금 없음)
        if (s_value != null) return s_value;

        Monitor.Enter(s_lock);          // 아직이면 한 스레드만 들여보낸다
        if (s_value == null)            // 여전히 없으면 만든다 (두 번째 검사)
        {
            Singleton temp = new Singleton();

            // 참조를 s_value에 게시한다 — 왜 Volatile.Write인지는 아래에서
            Volatile.Write(ref s_value, temp);
        }
        Monitor.Exit(s_lock);

        return s_value;
    }
}
```

이름의 "이중 검사"는 `if (s_value != null)`이 두 번 나오는 데서 왔다. 첫 번째는 잠금 밖에서 하는 빠른 경로 검사, 두 번째는 잠금 안에서 하는 확정 검사다.

### 왜 순진하게 쓰면 깨지는가

이 패턴은 Java에서 널리 쓰이다가 **모든 환경에서 동작하지 않는다**는 것이 밝혀지며 유명해졌다. Java 가상 머신은 `GetSingleton` 진입 시점에 `s_value`를 CPU 레지스터로 읽고, 두 번째 `if`에서 그 레지스터를 그대로 읽었다. 그래서 두 번째 검사가 항상 참이 되어 여러 스레드가 각각 객체를 만들었다.

CLR에서는 이 특정 문제가 없다. **잠금 메서드 호출은 전체 메모리 펜스**이므로 `Monitor.Enter` 이후에는 `s_value`를 반드시 다시 읽어야 한다. 레지스터에 캐시해 둘 수 없다.

그런데 **다른 문제가 남는다.** 두 번째 `if` 안에 다음과 같이 썼다고 하자.

```csharp
s_value = new Singleton();   // 이상적으로는 이렇게 쓰고 싶다
```

컴파일러가 다음 순서로 코드를 만들 것이라고 기대한다.

1. `Singleton`을 위한 메모리를 할당한다.
2. 생성자를 호출해 필드를 초기화한다.
3. 참조를 `s_value`에 대입한다.

값을 다른 스레드에게 보이게 만드는 것을 **게시(publishing)** 라 한다. 그런데 컴파일러·JIT·CPU는 이렇게 할 수도 있다.

1. 메모리를 할당한다.
2. **참조를 `s_value`에 게시한다.**
3. 생성자를 호출한다.

단일 스레드 관점에서는 아무 차이가 없다. 그러나 2번과 3번 사이에 다른 스레드가 `GetSingleton`을 부르면? 그 스레드는 `s_value != null`을 보고 **생성자가 아직 실행되지 않은 객체**를 반환한다. 필드가 전부 기본값인 반쯤 만들어진 싱글턴을 쓰게 된다.

```text
   스레드 A                                    스레드 B
   ────────────────────────────                ─────────────────────────
   메모리 할당
   s_value = ptr        ← 게시가 먼저!
                                               if (s_value != null) → true
                                               return s_value       ← 생성자 미실행 객체!
   ctor 실행 (필드 초기화)
```

**이 버그는 타이밍에만 의존하므로 추적이 극도로 어렵다.**

### 올바른 구현

`Volatile.Write`가 이 문제를 고친다. 해제 펜스이므로 **그 앞의 모든 쓰기(생성자가 수행한 필드 초기화 포함)가 완료된 뒤에만** `s_value`에 참조가 들어간다.

같은 효과를 필드 한정자로 얻을 수도 있다.

```csharp
private static volatile Singleton s_value = null;

// 이제 이렇게 써도 안전하다
if (s_value == null) s_value = new Singleton();
```

다만 이 방법은 **모든 읽기도 volatile로 만든다.** 이 시나리오에서 읽기 쪽에 획득 펜스가 필요한 것은 맞지만(첫 번째 검사에서 낡은 값을 보지 않기 위해), 뜨거운 경로의 모든 읽기가 최적화 대상에서 빠지는 대가를 치른다. `Volatile.Write` 쪽이 더 정밀하다.

| 구현 | 첫 검사 | 게시 | 정확한가 |
|---|---|---|---|
| 일반 필드 + 일반 대입 | 낡은 값을 볼 수 있다 | 재배치로 미완성 객체 게시 가능 | **아니오** |
| 일반 필드 + `Volatile.Write` 게시 | 낡은 값을 봐도 잠금 안에서 다시 검사한다 | 안전 | **예** |
| `volatile` 필드 | 안전 | 안전 | **예** (읽기 최적화 손실) |
| `Interlocked.CompareExchange` 게시 | 안전 | 안전(전체 펜스) | **예** (객체가 둘 이상 만들어질 수 있음) |

### `Interlocked.CompareExchange` 방식

잠금을 아예 쓰지 않는 세 번째 방법도 있다.

```csharp
sealed class Singleton
{
    private static Singleton s_value = null;

    private Singleton() { /* 초기화 */ }

    public static Singleton GetSingleton()
    {
        if (s_value != null) return s_value;

        // 새로 만들고, 다른 스레드가 먼저 하지 않았을 때만 뿌리내린다
        Singleton temp = new Singleton();
        Interlocked.CompareExchange(ref s_value, temp, null);

        // 경쟁에서 진 쪽이 만든 객체는 나중에 GC된다
        return s_value;
    }
}
```

여러 스레드가 동시에 부르면 `Singleton` 객체가 둘 이상 만들어질 수 있다. 그러나 `CompareExchange` 덕분에 **`s_value`에 게시되는 것은 하나뿐**이고, 나머지는 곧 회수된다.

장점이 뚜렷하다. **아주 빠르고, 스레드를 절대 막지 않는다.** 스레드 풀 스레드가 `Monitor`에서 막히면 스레드 풀이 새 스레드를 만들고(46.2절), 메모리가 더 할당되고, 모든 DLL이 스레드 연결 알림을 받는다. `CompareExchange`에는 그런 일이 전혀 없다.

단점도 뚜렷하다. **생성자에 부작용이 있으면 쓸 수 없다.** 파일을 열거나, 정적 상태를 갱신하거나, 등록을 수행하는 생성자라면 그 부작용이 여러 번 일어난다. 그리고 버려지는 객체가 `IDisposable`이면 정리되지 않는다.

### 결론 — 대개는 `Lazy<T>`나 정적 생성자를 써라

이중 검사 잠금은 "멋있어 보인다"는 이유로 필요 이상으로 자주 쓰인다. **대부분의 시나리오에서는 오히려 효율을 해친다.**

가장 단순한 대안은 이것이다.

```csharp
sealed class Singleton
{
    private static readonly Singleton s_value = new Singleton();

    private Singleton() { /* 초기화 */ }

    public static Singleton GetSingleton() => s_value;
}
```

CLR은 그 클래스의 멤버에 처음 접근할 때 **자동으로 타입 생성자를 호출**하고, 타입 생성자 호출이 스레드 안전함을 **이미 보장한다**(13.12절). 즉 CLR이 이중 검사 잠금과 같은 일을 대신 해 준다.

단점은 하나다. 타입 생성자는 그 클래스의 **어떤** 멤버에 처음 접근해도 실행된다. `Singleton`에 다른 정적 멤버가 있으면 그중 하나만 건드려도 싱글턴이 만들어진다. 이 문제를 피하려고 중첩 클래스를 쓰는 관용구가 있다.

그리고 BCL은 이 패턴들을 이미 타입으로 제공한다.

```csharp
public class Lazy<T>
{
    public Lazy(Func<T> valueFactory, LazyThreadSafetyMode mode);
    public bool IsValueCreated { get; }
    public T Value { get; }
}

public enum LazyThreadSafetyMode
{
    None,                       // 스레드 안전성 없음 (GUI 앱 등)
    ExecutionAndPublication,    // 이중 검사 잠금 기법
    PublicationOnly,            // Interlocked.CompareExchange 기법
}
```

`LazyThreadSafetyMode`의 세 값이 이 절에서 본 세 가지 구현과 정확히 대응한다는 점을 보라. **직접 구현할 이유가 거의 없다.**

메모리가 극도로 빠듯해 `Lazy<T>` 래퍼 객체조차 아깝다면 `System.Threading.LazyInitializer`의 정적 메서드가 있다. 필드에 직접 작용하므로 간접 참조가 한 단계 줄어든다.

```csharp
Expensive _expensive;

public Expensive Expensive
{
    get   // 내부적으로 이중 검사 잠금을 구현한다
    {
        LazyInitializer.EnsureInitialized(ref _expensive, () => new Expensive());
        return _expensive;
    }
}
```

> **💡 지연 초기화 결정 순서**
>
> 1. **정말 지연이 필요한가?** 생성이 싸면 그냥 필드 초기화자나 생성자에서 만들어라.
> 2. **정적 싱글턴인가?** `static readonly` 필드 + 타입 생성자. CLR이 보장한다.
> 3. **인스턴스 필드인가?** `Lazy<T>`(기본 모드 `ExecutionAndPublication`).
> 4. **래퍼 객체 하나가 문제가 될 만큼 뜨거운가?** `LazyInitializer.EnsureInitialized`.
> 5. **그래도 직접 써야 하는가?** 이중 검사 잠금을 쓰되 **게시를 `Volatile.Write`로** 하라.
>
> `Lazy<T>`의 상세와 팩터리 델리게이트가 캡처한 것들의 수명 문제는 34.7절에 있다.

## 48.14 스레드 안전성 — .NET 타입의 스레드 안전성, 애플리케이션 서버, 불변 객체

### 정의

프로그램이나 메서드가 **어떤 다중 스레드 시나리오에서도 올바르게 동작하면** 스레드 안전(thread-safe)하다고 말한다. 스레드 안전성은 주로 잠금과 **스레드 상호작용 가능성의 축소**로 달성된다.

중요한 오해를 먼저 걷어내자. **스레드 안전한 메서드가 반드시 내부적으로 잠금을 잡는다는 뜻은 아니다.**

```csharp
public static int Max(int val1, int val2)
{
    return (val1 < val2) ? val2 : val1;
}
```

`System.Math.Max`는 잠금을 전혀 잡지 않지만 완벽하게 스레드 안전하다. `int`는 값 타입이므로 두 인수가 복사되어 들어오고, 각 스레드는 **자기 데이터만** 다루기 때문이다. 스레드 안전이란 "두 스레드가 동시에 접근해도 데이터가 깨지지 않는다"는 성질이지 특정 구현 기법이 아니다.

### 범용 타입이 스레드 안전하지 않은 이유

범용 타입이 완전한 스레드 안전성을 갖는 경우는 드물다. 이유가 셋이다.

1. **개발 부담이 크다.** 필드가 많으면 각각이 임의의 다중 스레드 상황에서 상호작용할 여지가 된다.
2. **성능 비용이 든다.** 실제로 다중 스레드에서 쓰이든 아니든 일부는 지불된다.
3. **소용이 없을 때가 많다.** 스레드 안전한 타입이 그것을 쓰는 프로그램을 스레드 안전하게 만들어 주지 않고, 프로그램을 안전하게 만드는 작업이 타입의 안전성을 무의미하게 만드는 경우가 흔하다(48.7절의 `Contains`+`Add`).

그래서 스레드 안전성은 **특정 다중 스레드 시나리오를 다루기 위해 필요한 곳에만** 구현되는 것이 보통이다.

### .NET 타입의 스레드 안전성 규약

.NET의 규약은 다음 한 줄이다.

> **정적 멤버는 스레드 안전하다. 인스턴스 멤버는 그렇지 않다.**

이 규약이 존재하는 이유가 있다. 정적 멤버는 **범위가 지나치게 넓다.** 예를 들어 `DateTime.Now`가 스레드 안전하지 않다고 하자. 외부에서 이를 보호하는 유일한 방법은 `lock(typeof(DateTime))` 처럼 타입 자체를 잠그는 것뿐이다. 그러려면 세상의 모든 프로그래머가 그렇게 하기로 합의해야 하는데 불가능하다. 게다가 타입을 잠그는 것은 그 자체로 문제를 만든다(48.6절). 그래서 `DateTime`의 정적 멤버는 스레드 안전하도록 **의도적으로 작성되었다.**

Microsoft의 프레임워크 클래스 라이브러리도 같은 규약을 따른다. 이건 강제가 아니라 **약속**이다. 여러 회사가 만든 어셈블리들이 하나의 잠금에 합의하는 것이 불가능하므로, 라이브러리 쪽이 내부적으로 처리해 주는 수밖에 없었다.

> **⚠️ 정적 메서드의 스레드 안전성은 자동으로 생기지 않는다**
>
> `static`을 붙였다고 스레드 안전해지는 것이 아니다. **명시적으로 그렇게 작성해야 한다.** 자기 타입을 공개하는 라이브러리를 만든다면 이 규약을 따르는 것이 좋다 — 소비자가 해결할 수 없는 스레드 안전성 난제를 만들지 않기 위해서다.
>
> 규약에는 예외가 하나 있다. **인스턴스 메서드의 목적 자체가 스레드 조율이라면 그 인스턴스 메서드는 스레드 안전해야 한다.** 예를 들어 한 스레드가 `CancellationTokenSource.Cancel()`을 부르고 다른 스레드가 `CancellationToken.IsCancellationRequested`를 조회한다(46.8절). 이 두 인스턴스 멤버는 내부에 조율 코드를 갖고 있다 — 두 멤버가 접근하는 필드는 `volatile`로 표시되어 있다.

### 이 규약의 실제 신뢰도

규약을 얼마나 믿어야 하는가?

| 상황 | 신뢰도 | 근거 |
|---|---|---|
| BCL의 정적 멤버 | 높다 | 의도적으로 그렇게 작성되었고 문서화되어 있다 |
| BCL의 인스턴스 멤버 | **안전하지 않다고 가정하라** | 프리미티브를 제외하면 동시 읽기 전용 접근 이상은 보장되지 않는다 |
| BCL 컬렉션의 동시 읽기 | 안전 | 읽기 전용 동시 접근은 명시적으로 보장된다 |
| 제3자 라이브러리 | **문서를 읽어라. 없으면 안전하지 않다고 가정하라** | 규약을 따르지 않는 라이브러리가 많다 |
| 겉보기에 읽기 전용인 메서드 | **의심하라** | 아래 참조 |

마지막 행이 중요하다.

> **⚠️ `Random.Next()`는 읽기가 아니다**
>
> `Random.Next()`는 이름과 달리 내부 시드를 **갱신한다.** 즉 상태를 바꾸는 메서드다. 여러 스레드가 하나의 `Random` 인스턴스를 공유하면 결과가 망가지거나 같은 값이 반복될 수 있다.
>
> 해법은 두 가지다. `Random`을 잠금으로 감싸거나, **스레드마다 별도 인스턴스**를 갖는 것이다.
>
> ```csharp
> // 스레드마다 자기 Random을 갖는다 (49.8절)
> var localRandom = new ThreadLocal<Random>(
>     () => new Random(Guid.NewGuid().GetHashCode()));
> Console.WriteLine(localRandom.Value.Next());
> ```
>
> 매개변수 없는 `Random` 생성자는 시스템 시계를 시드로 쓰므로, 짧은 시간 안에 만든 두 인스턴스가 같은 수열을 낼 수 있다. 그래서 위 예제는 `Guid`의 해시를 시드로 준다.
>
> 문서가 없다면 **메서드가 정말 읽기 전용인지 함부로 단정하지 마라.** 컬렉션의 `ToArray()`가 내부 구조를 압축(compaction)하도록 구현되어 있다면, 그 컬렉션은 동시 읽기에 안전하지 않다.

### 잠금으로 스레드 안전하지 않은 타입 쓰기

.NET 타입 대부분이 인스턴스 수준에서 스레드 안전하지 않지만, **주어진 객체에 대한 모든 접근을 하나의 잠금으로 보호하면** 다중 스레드 코드에서 쓸 수 있다.

```csharp
class ThreadSafe
{
    static List<string> _list = new List<string>();

    static void Main()
    {
        new Thread(AddItem).Start();
        new Thread(AddItem).Start();
    }

    static void AddItem()
    {
        lock (_list) _list.Add("Item " + _list.Count);

        string[] items;
        lock (_list) items = _list.ToArray();
        foreach (string s in items) Console.WriteLine(s);
    }
}
```

두 가지가 눈여겨볼 만하다.

**첫째, 열거 중 수정은 예외를 던진다.** .NET 컬렉션은 열거 도중 컬렉션이 수정되면 `InvalidOperationException`을 던진다(24.1절). 다중 스레드에서는 다른 스레드가 수정할 수 있으므로 이 예외가 언제든 나올 수 있다.

**둘째, 그래서 위 예제는 항목을 배열로 복사한 뒤 열거한다.** 열거 전체 구간에 잠금을 거는 대신, 짧게 잠그고 스냅숏을 뜬 다음 잠금 밖에서 열거한다. **열거하면서 하는 일이 오래 걸릴 수 있다면** 이 편이 훨씬 낫다. 읽기/쓰기 잠금(48.11절)도 대안이다.

서로 연관된 두 리스트를 다룬다면 **공통의 잠금 객체 하나**를 골라야 한다. 리스트 중 하나를 잠금으로 삼을 수도 있지만, 독립된 잠금 필드를 쓰는 편이 낫다.

### 애플리케이션 서버에서의 상태 관리

애플리케이션 서버는 동시 클라이언트 요청을 처리하려면 다중 스레드여야 한다. ASP.NET Core와 Web API 애플리케이션은 **암묵적으로 다중 스레드**다. 서버 코드를 쓸 때 요청 처리 스레드들 사이에 상호작용 가능성이 있다면 스레드 안전성을 고려해야 한다.

다행히 그 가능성은 대개 낮다.

| 상태의 종류 | 스레드 안전성 부담 |
|---|---|
| 요청별 인스턴스(스코프 서비스, 컨트롤러) | 없음 — 요청마다 별도 객체 |
| 지역 변수, 메서드 매개변수 | 없음 |
| 무상태(stateless) 서비스 — 필드가 없다 | 없음 |
| **싱글턴 서비스의 인스턴스 필드** | **있음** — 모든 요청이 공유한다 |
| **정적 필드** | **있음** — 캐시가 대표적이다 |

전형적인 서버 클래스는 무상태이거나 클라이언트/요청마다 별도의 인스턴스를 만드는 활성화 모델을 갖는다. 상호작용은 보통 **정적 필드**를 통해서만 생긴다 — 데이터베이스 일부를 메모리에 캐시하거나, 인증·감사 같은 인프라 서비스를 제공할 때다.

> **⚠️ DI 컨테이너의 수명이 곧 스레드 안전성 요구다**
>
> ASP.NET Core에서 서비스를 `AddSingleton`으로 등록하면 그 인스턴스는 **모든 요청이 공유한다.** 그 타입에 가변 인스턴스 필드가 있다면 스레드 안전해야 한다. `AddScoped`면 요청마다 새 인스턴스이므로 부담이 없다.
>
> 가장 흔한 사고는 **싱글턴 서비스가 스코프 서비스를 필드로 붙드는 것**이다(captive dependency). 수명 문제인 동시에 스레드 안전성 문제다. 하나의 `DbContext`를 싱글턴이 붙들고 여러 요청이 동시에 쓰면 확실히 깨진다.

### 캐시 — 실제 예제

자주 호출되는 조회 메서드가 있다고 하자.

```csharp
// User는 사용자 데이터를 담은 사용자 정의 클래스다
internal User RetrieveUser(int id) { … }   // DB에서 읽어 온다
```

결과를 정적 `Dictionary`에 캐시해 성능을 올리고 싶다. 스레드 안전성을 고려한 개념적으로 단순한 해법은 이렇다.

```csharp
static class UserCache
{
    static Dictionary<int, User> _users = new Dictionary<int, User>();

    internal static User GetUser(int id)
    {
        lock (_users)
            if (_users.TryGetValue(id, out User cached)) return cached;

        User u = RetrieveUser(id);       // DB 조회 — 잠금 밖에서
        lock (_users) _users[id] = u;
        return u;
    }
}
```

여기에는 단순성과 성능 사이의 **의도적 타협**이 들어 있다. 두 스레드가 아직 캐시되지 않은 같은 `id`로 동시에 들어오면 `RetrieveUser`가 두 번 호출되고 딕셔너리가 불필요하게 두 번 갱신된다. 메서드 전체를 하나의 잠금으로 감싸면 이 낭비는 없어지지만 **훨씬 나쁜 비효율**이 생긴다 — `RetrieveUser`가 도는 동안 캐시 전체가 잠겨 다른 모든 사용자 조회가 막힌다.

더 나은 해법은 `User`가 아니라 **`Task<User>`를 캐시하는 것**이다.

```csharp
static class UserCache
{
    static Dictionary<int, Task<User>> _userTasks = new Dictionary<int, Task<User>>();

    internal static Task<User> GetUserAsync(int id)
    {
        lock (_userTasks)
            if (_userTasks.TryGetValue(id, out var userTask))
                return userTask;
            else
                return _userTasks[id] = Task.Run(() => RetrieveUser(id));
    }
}
```

이제 메서드 전체의 로직이 **하나의 잠금** 안에 있다. 그런데도 동시성이 나빠지지 않는다. 잠금 안에서 하는 일이 딕셔너리 접근과 (필요하면) 비동기 작업의 **시작**뿐이기 때문이다. 두 스레드가 같은 ID로 동시에 들어오면 둘 다 **같은 태스크**를 `await`하게 된다. 정확히 원하던 결과다.

> **💡 "잠금 안에서 오래 걸리는 일을 하지 마라"의 우아한 해법**
>
> 위 패턴의 핵심은 **오래 걸리는 작업 자체가 아니라 그 작업을 나타내는 객체(`Task`)를 캐시**한다는 것이다. 잠금 보유 시간이 마이크로초 단위로 줄고, 중복 실행도 사라지고, GC 부담도 준다.
>
> 이 발상은 캐시 외에도 널리 쓰인다. **"잠금 안에서는 상태 전이만, 실제 작업은 밖에서"** 로 일반화된다.

### 불변 객체가 동기화를 없애는 원리

**불변 객체(immutable object)** 는 외부에서든 내부에서든 상태를 바꿀 수 없는 객체다. 필드는 보통 `readonly`로 선언되고 생성 시점에 완전히 초기화된다(19장).

불변성이 다중 스레드에서 가치 있는 이유는 하나다. **48.1절의 두 조건 중 두 번째를 제거한다.** 아무도 쓰지 않으므로 동기화가 필요 없다.

관련된 필드 여러 개를 하나의 불변 객체로 묶으면 **잠금 보유 시간을 극단적으로 줄일 수 있다.** 두 필드가 있다고 하자.

```csharp
int _percentComplete;
string _statusMessage;
```

이 둘을 원자적으로 읽고 써야 한다. 두 필드를 각각 잠그는 대신 다음 불변 클래스를 정의한다.

```csharp
class ProgressStatus   // 어떤 작업의 진행 상황을 나타낸다
{
    public readonly int PercentComplete;
    public readonly string StatusMessage;
    // 필드가 훨씬 많을 수도 있다…

    public ProgressStatus(int percentComplete, string statusMessage)
    {
        PercentComplete = percentComplete;
        StatusMessage = statusMessage;
    }
}
```

그리고 그 타입의 필드 하나와 잠금 객체 하나만 둔다.

```csharp
readonly object _statusLocker = new object();
ProgressStatus _status;
```

이제 쓰기는 이렇게 된다.

```csharp
var status = new ProgressStatus(50, "작업 중");
// 필드가 아무리 많아도 여기까지는 잠금 밖에서 만든다
// …
lock (_statusLocker) _status = status;   // 아주 짧은 잠금
```

읽기는 이렇다.

```csharp
ProgressStatus status;
lock (_statusLocker) status = _status;   // 역시 아주 짧은 잠금

int pc = status.PercentComplete;         // 잠금 없이 읽는다
string msg = status.StatusMessage;
```

잠금은 **참조 대입 한 번**만 감싼다. 객체 자체는 불변이므로 참조를 얻은 뒤에는 잠금 없이 마음껏 읽어도 안전하다. 필드가 스무 개여도 잠금 보유 시간은 그대로다.

> **📌 참조 대입은 원자적이므로 잠금조차 없앨 수 있다**
>
> 참조 타입의 읽기·쓰기는 원자적이므로(48.2절), 위 예제의 `lock` 대신 `Volatile.Read`/`Volatile.Write` 짝으로도 된다.
>
> ```csharp
> Volatile.Write(ref _status, status);           // 게시
> ProgressStatus s = Volatile.Read(ref _status); // 읽기
> ```
>
> `Volatile.Write`가 해제 펜스이므로 `ProgressStatus`의 생성자가 완료된 뒤에만 참조가 게시된다 — 48.13절에서 본 그 문제가 여기서도 똑같이 적용된다. **불변 스냅숏 교체는 이 두 줄이 전부다.**
>
> 읽기가 압도적으로 많은 캐시라면 이 패턴이 `ReaderWriterLockSlim`보다 훨씬 빠르다. 읽기 경로에 잠금이 아예 없기 때문이다. 대신 갱신마다 전체 스냅숏을 새로 만드는 비용을 낸다. `System.Collections.Immutable`의 컬렉션들이 이 트레이드오프를 구조적으로 개선한다(24.10절).

### 스레드 안전성을 문서화하는 법

내가 만든 타입의 스레드 안전성 계약을 소비자에게 어떻게 알리는가? 형식적 장치가 없으므로 **문서화가 유일한 수단**이다.

권장하는 서술 방식은 다음 네 가지 등급 중 하나를 명시하는 것이다.

| 등급 | 의미 | 예 |
|---|---|---|
| **완전 스레드 안전** | 어떤 조합의 동시 호출도 안전하다 | `ConcurrentDictionary`, `HttpClient`(대부분의 사용) |
| **동시 읽기 안전** | 아무도 쓰지 않는 동안의 동시 읽기만 안전하다 | `List<T>`, `Dictionary<K,V>` |
| **스레드 안전하지 않음** | 외부에서 직렬화해야 한다 | 대부분의 가변 타입 |
| **스레드 친화적** | 특정 스레드에서만 쓸 수 있다 | UI 컨트롤, `DbContext`(사실상) |

XML 문서 주석에 명시하는 것이 좋다.

```csharp
/// <summary>사용자 조회 결과를 메모리에 캐시한다.</summary>
/// <remarks>
/// <para><b>스레드 안전성:</b> 이 타입의 모든 public 정적·인스턴스 멤버는
/// 동시 호출에 안전하다. 내부적으로 단일 배타 잠금으로 직렬화된다.</para>
/// </remarks>
public sealed class UserCache { … }
```

> **💡 "동시 읽기 안전"을 주장하려면 읽기 메서드가 진짜 읽기여야 한다**
>
> 타입을 "동시 읽기에 안전"하다고 문서화했다면, 소비자가 읽기라고 여길 만한 메서드 안에서 **필드에 쓰지 마라.** 컬렉션의 `ToArray()`를 구현하면서 내부 구조를 압축하고 싶은 유혹이 들 수 있다. 그러면 그 순간 계약이 깨진다. 꼭 해야 한다면 그 부분만 잠금으로 감싸라.
>
> 열거자(enumerator)가 열거 가능 객체(enumerable)와 분리된 이유 중 하나가 이것이다. 두 스레드가 같은 컬렉션을 동시에 열거할 수 있는 것은 각자 **별도의 열거자 객체**를 받기 때문이다(28장).

## 48.15 `System.Threading.Lock` 타입 ※C# 13 / .NET 9

### 왜 새 타입이 필요했는가

48.5절에서 본 대로 `lock` 문은 `Monitor.Enter`/`Exit`로 컴파일되고, `Monitor`는 **임의의 힙 객체의 헤더 워드**를 잠금 상태 저장소로 쓴다. 이 설계에는 오래된 문제가 있다.

| 문제 | 설명 |
|---|---|
| 잠금 대상이 지나치게 자유롭다 | `this`, `typeof(T)`, 문자열, 박싱된 값 타입 — 전부 컴파일된다(48.6절) |
| 객체 헤더 경로를 탄다 | `GetHashCode()` 호출 등 다른 용도와 헤더 워드를 공유해 팽창을 유발한다(48.5절) |
| 의도가 코드에 드러나지 않는다 | `private readonly object _lock`은 그냥 `object`다. 잘못 쓰는 것을 막을 장치가 없다 |
| 새 기능을 넣을 자리가 없다 | `Monitor`는 정적 클래스이고 `object`를 받으므로 API를 확장하기 어렵다 |

.NET 9와 C# 13은 **잠금 전용 타입** `System.Threading.Lock`을 도입해 이 문제들을 정리했다.

### 문법

```csharp
using System.Threading;

class Counter
{
    private readonly Lock _lock = new Lock();   // object가 아니라 Lock
    private int _value;

    public void Increment()
    {
        lock (_lock)      // lock 문이 이 타입을 특별히 인식한다
        {
            _value++;
        }
    }
}
```

`lock` 문의 사용법은 완전히 같다. 필드 타입만 `object`에서 `Lock`으로 바뀌었다.

`Lock`의 주요 멤버는 다음과 같다.

```csharp
public sealed class Lock
{
    public Lock();

    public void Enter();
    public void Exit();

    public bool TryEnter();                             // TimeSpan / int 오버로드도 있다
    public bool TryEnter(int millisecondsTimeout);

    public Scope EnterScope();
    public bool IsHeldByCurrentThread { get; }

    public ref struct Scope { public void Dispose(); }
}
```

`Monitor`와 대응이 명확하다.

| `Monitor` (정적) | `Lock` (인스턴스) |
|---|---|
| `Monitor.Enter(obj)` | `lockObj.Enter()` |
| `Monitor.Exit(obj)` | `lockObj.Exit()` |
| `Monitor.TryEnter(obj, ms)` | `lockObj.TryEnter(ms)` |
| `Monitor.IsEntered(obj)` | `lockObj.IsHeldByCurrentThread` |
| (없음) | `lockObj.EnterScope()` |

### `EnterScope()`와 `ref struct`

`Lock`의 새로운 API가 `EnterScope()`다. `Lock.Scope`라는 `ref struct`를 반환하고, 그 `Dispose()`가 잠금을 해제한다.

```csharp
using (_lock.EnterScope())
{
    // 임계 구역
}
```

또는 `using` 선언으로.

```csharp
void Increment()
{
    using var scope = _lock.EnterScope();
    _value++;
}
```

반환 타입이 `ref struct`인 것이 설계의 핵심이다. `ref struct`는 스택에만 존재할 수 있으므로(16장, 68장) 다음이 전부 컴파일 오류가 된다.

- 필드로 저장하기
- 힙에 박싱하기
- 람다나 반복자에 캡처하기
- `async` 메서드에서 `await`를 가로질러 살아남기

즉 **잠금 범위가 하나의 메서드 안, 하나의 스택 프레임 안에 갇히도록 언어가 강제한다.** 잠금 스코프가 실수로 새어 나가는 것을 타입 시스템이 막는 것이다.

> **📌 `lock` 문과 `EnterScope()`는 같은 코드로 컴파일된다**
>
> C# 13 컴파일러는 `lock` 문의 대상이 `System.Threading.Lock` 타입일 때 `Monitor.Enter`/`Exit` 대신 `EnterScope()`/`Scope.Dispose()`를 호출하는 코드를 만든다. 대략 다음과 같다.
>
> ```csharp
> // lock (_lock) { 본문 }  →
> Lock.Scope scope = _lock.EnterScope();
> try { 본문 }
> finally { scope.Dispose(); }
> ```
>
> 그러므로 `lock` 문과 `using var scope = _lock.EnterScope();` 는 **의미적으로 동일하다.** 어느 쪽을 쓸지는 스타일 문제다. 다만 `using` 선언 형태는 중괄호 중첩을 하나 줄여 준다.

### 런타임 동작 — 전용 경로

`Lock`은 객체 헤더의 동기화 블록 인덱스 경로를 **타지 않는다.** 잠금 상태를 자기 인스턴스 필드에 직접 갖는다. 여기서 오는 이점이 있다.

- 그 객체의 `GetHashCode()`가 호출되어도 잠금이 팽창하지 않는다(48.5절의 함정 제거).
- 잠금 상태에 접근하는 데 간접 참조가 한 단계 줄어든다.
- 런타임이 이 타입만을 위한 최적화를 자유롭게 넣을 수 있다.

의미론은 `Monitor`와 같다. **하이브리드 잠금**이고, **스레드 소유권과 재귀를 지원**한다.

```csharp
lock (_lock)
    lock (_lock)       // 재진입 가능 — Monitor와 같다
    { … }
```

> **⚠️ `Monitor.Wait`/`Pulse`에 대응하는 API는 없다**
>
> `Lock`에는 조건 변수 API(`Wait`/`Pulse`/`PulseAll`)가 없다. 조건 변수 패턴이 필요하면 여전히 `object`와 `Monitor`를 써야 한다(48.5절, 49.7절).
>
> 그리고 `Lock` 인스턴스를 `Monitor.Enter`에 넘기는 것은 **컴파일은 되지만 의미가 전혀 다르다.** 아래 함정을 보라.

### `object`로 캐스팅하면 조용히 `Monitor`로 돌아간다

이것이 이 타입의 가장 중요한 함정이다.

```csharp
Lock myLock = new Lock();

lock (myLock)          // Lock의 새 경로를 탄다
{
    … 
}

object asObject = myLock;

lock (asObject)        // Monitor 경로를 탄다! 완전히 다른 잠금이다
{
    … 
}
```

`Lock`도 결국 참조 타입이므로 `object`로 업캐스팅할 수 있고, `object`에 대한 `lock`은 `Monitor.Enter`로 컴파일된다. 그러면 **같은 인스턴스에 대해 서로 다른 두 개의 잠금 메커니즘**이 동작한다. `Lock`의 내부 상태와 그 객체의 헤더 워드는 서로를 전혀 모른다.

결과는 **상호 배제의 조용한 소실**이다. 한 스레드는 `Lock` 경로로, 다른 스레드는 `Monitor` 경로로 들어가 둘 다 임계 구역에 있게 된다. 예외도 경고도 런타임에는 없다.

같은 문제가 여러 형태로 나타난다.

```csharp
// 1. object 매개변수에 넘기기
void Helper(object o) { lock (o) { … } }
Helper(myLock);                         // Monitor 경로

// 2. object 필드에 담기
private object _locker = new Lock();    // 타입 정보가 사라진다
lock (_locker) { … }                    // Monitor 경로

// 3. object[] 나 List<object>에 담기
var locks = new object[] { new Lock() };
lock (locks[0]) { … }                   // Monitor 경로
```

> **⚠️ 컴파일러가 경고를 낸다 — 무시하지 마라**
>
> C# 13 컴파일러는 `System.Threading.Lock` 값이 다른 타입으로 변환될 때 **경고 CS9216**을 낸다. 메시지는 대략 "`System.Threading.Lock` 타입의 값을 다른 타입으로 변환하면 `lock` 문에서 의도하지 않은 모니터 기반 잠금이 사용될 가능성이 높다"는 내용이다.
>
> 이 경고를 억제하지 마라. 잠금 필드의 타입을 `Lock`으로 유지하고, `object`를 받는 헬퍼에 넘기지 마라. `Lock`을 받는 헬퍼가 필요하면 매개변수 타입을 `Lock`으로 선언한다.
>
> 그리고 이 경고는 **변환 지점**에서만 나온다. 변환이 다른 어셈블리나 리플렉션을 통해 일어나면 잡히지 않는다. `Lock` 인스턴스를 클래스 밖으로 내보내지 않는 것이 최선의 방어다 — `private readonly`가 그 답이다.

### 마이그레이션

기존 코드를 `Lock`으로 옮기는 절차는 단순하다.

```csharp
// 이전
private readonly object _lock = new object();

// 이후 ※.NET 9
private readonly Lock _lock = new Lock();
```

`lock (_lock) { … }` 코드는 **한 글자도 바꿀 필요가 없다.** 컴파일러가 새 경로를 자동으로 선택한다.

다만 다음 경우에는 마이그레이션이 불가능하거나 주의가 필요하다.

| 상황 | 대응 |
|---|---|
| `Monitor.Wait`/`Pulse`를 쓰고 있다 | **옮기지 마라.** `object`를 유지한다 |
| `Monitor.Enter`/`Exit`를 직접 부른다 | `_lock.Enter()`/`_lock.Exit()`로 바꾼다 |
| 잠금 객체를 `object` 타입 API에 넘긴다 | 그 API의 시그니처를 바꾸거나 옮기지 않는다 |
| 보호 대상 자체를 잠그고 있다(`lock (_list)`) | 전용 `Lock` 필드를 새로 만든다 |
| 대상이 .NET 8 이하도 포함한다 | **옮길 수 없다.** `Lock`은 .NET 9부터다 |
| 잠금 객체를 리플렉션이나 직렬화로 다룬다 | 옮기지 마라 |

> **💡 새 코드는 `Lock`으로, 기존 코드는 서두르지 마라**
>
> `Lock`은 명확한 개선이다. 의도가 타입에 드러나고, 오용 가능성이 줄고, 객체 헤더 경로를 피한다. **.NET 9 이상만 대상으로 하는 새 코드에서는 기본 선택으로 삼을 만하다.**
>
> 반면 기존 코드를 일괄 변환하는 작업의 이득은 대개 크지 않다. 성능 차이는 측정 가능한 수준이 아닐 때가 많고, 위 표의 예외 상황을 하나라도 놓치면 조용한 버그가 된다. **경합이 확인된 뜨거운 잠금부터, 하나씩, 측정하면서** 옮겨라.

## 이 장의 요약

- **동기화가 필요한 조건은 두 가지다.** 둘 이상의 실행 흐름이 같은 상태에 접근하고, 그중 최소 하나가 쓴다. 둘 중 하나만 깨면 동기화는 불필요해진다. 잠금을 잘 쓰는 것보다 잠금이 필요 없게 설계하는 것이 먼저다.
- **동시성 버그의 원인은 원자성·가시성·재배치 셋뿐이다.** 워드 크기 이하의 정렬된 읽기·쓰기만 원자적이고, `i++`는 세 연산이라 원자적이 아니다. 쓴 값이 언제 보이는지는 보장이 없고, 컴파일러·JIT·CPU는 단일 스레드 의미만 보존하면 순서를 바꿀 수 있다.
- **x86에서만 테스트하면 재배치 버그가 숨는다.** x86/x64는 강한 순서 모델이라 저장-적재 재배치만 허용하지만, ARM64는 약한 모델이라 같은 코드가 조용히 깨진다. Apple Silicon과 ARM 서버가 일상이 된 지금 이 경고는 이론이 아니다.
- **`volatile`은 반쪽 펜스이고 원자성을 만들지 않는다.** 두 volatile 연산 사이의 저장-적재 재배치는 여전히 가능하고, `ref`/`out`으로 넘기면(CS0420) volatile성이 사라진다. `volatile`을 쓰고 싶어지면 대개 필요한 것은 `lock`이나 `Interlocked`다.
- **`Interlocked`는 전체 펜스이면서 원자적이다.** `CompareExchange` 하나로 임의의 연산을 원자화하는 CAS 루프가 이 클래스의 진짜 능력이며, 이벤트 접근자가 그 예다. 대가는 ABA 문제, 재시도 비용, 그리고 경합 시의 캐시 라인 핑퐁이다.
- **`lock`은 `Monitor.Enter(obj, ref lockTaken)`/`try`/`finally Monitor.Exit`로 컴파일된다.** `lockTaken`은 C# 4에서 잠금 유출을 막으려고 도입되었다. `Monitor`는 객체 헤더의 씬 락에서 시작해 경합·`Wait`/`Pulse`·`GetHashCode` 등을 만나면 동기화 블록(팻 락)으로 팽창한다.
- **잠금 객체는 `private readonly object`여야 한다.** `this`·`typeof(T)`·문자열 리터럴을 잠그면 통제할 수 없는 코드와 잠금을 공유하게 된다. 잠금 안에서는 다른 잠금 획득, 외부 코드 호출, 이벤트 발생, I/O를 하지 마라.
- **잠금이 보장하는 것은 상호 배제뿐이다.** 개별 연산이 모두 스레드 안전해도 조합은 안전하지 않다. `ConcurrentDictionary`의 `ContainsKey` 후 `TryAdd`가 여전히 경합인 이유이고, 그래서 `GetOrAdd`·`AddOrUpdate` 같은 원자적 조합 메서드가 존재한다.
- **데드락은 네 조건이 모두 성립할 때만 난다.** 실무적으로 깨기 쉬운 것은 순환 대기(잠금 순서 규약)와 점유 대기(잠금 안에서 다른 잠금 금지)다. 덤프에서는 `!syncblk`으로 소유자를 찾고 `~*e !clrstack`으로 대기 지점을 찾는 두 명령이 분석의 대부분이다.
- **잠금 최적화의 목표는 잠금을 빠르게 만드는 것이 아니라 경합을 없애는 것이다.** 무경합 획득은 20나노초 미만이지만 경합 한 번은 그 수백 배다. `monitor-lock-contention-count`로 경합의 존재를 확인한 뒤에만 범위 축소·불변성·샤딩·읽기/쓰기 잠금을 시도하라.
- **`Mutex`는 프로세스 경계를 넘어야 할 때만 쓴다.** 커널 객체라 `lock`의 20배 이상 느리고, 소유 스레드가 죽으면 `AbandonedMutexException`이 나며, 스레드 친화성 때문에 `async`와 섞을 수 없다.
- **`SemaphoreSlim.WaitAsync`가 `async`와 함께 쓸 수 있는 유일한 잠금이다.** 세마포어에는 소유자가 없어 획득한 스레드와 해제하는 스레드가 달라도 되기 때문이다. 동시성 제한의 표준 관용구이고, `initialCount`를 1로 주면 비동기 잠금이 된다.
- **읽기/쓰기 잠금은 읽기가 압도적일 때만 이긴다.** `ReaderWriterLockSlim`은 평범한 `lock`보다 약 두 배 느리고, 재귀를 지원하게 하면 훨씬 더 느려진다. 구형 `ReaderWriterLock`은 쓰지 마라.
- **이중 검사 잠금은 게시를 `Volatile.Write`로 해야 정확하다.** 그러지 않으면 생성자가 끝나기 전에 참조가 게시되어 반쯤 만들어진 객체가 보일 수 있다. 그리고 대부분의 경우 `Lazy<T>`나 정적 생성자를 쓰는 편이 더 낫다.
- **.NET의 규약은 "정적 멤버는 안전, 인스턴스 멤버는 아님"이다.** 이 규약은 강제가 아니라 약속이며, `Random.Next()`처럼 이름이 읽기 같아도 상태를 바꾸는 메서드가 있다. 불변 객체로 상태를 묶고 참조를 교체하면 잠금 보유 시간을 참조 대입 한 번으로 줄일 수 있다.
- **`System.Threading.Lock`(.NET 9 / C# 13)은 전용 잠금 타입이다.** `lock` 문이 이 타입을 특별 인식해 `Monitor` 대신 `EnterScope()` 경로로 컴파일하고, 객체 헤더를 쓰지 않는다. `object`로 캐스팅하면 조용히 `Monitor`로 돌아가므로 경고 CS9216을 억제하지 마라.

## 연습 문제

1. **원자성 관찰.** 두 스레드가 각각 `_counter++`를 1,000,000번 실행하는 프로그램을 작성하고 결과를 10회 출력하라. 매번 다른 값이 나오는 것을 확인한 뒤 `Interlocked.Increment`로 바꿔 항상 2,000,000이 나오는 것을 확인하라. 두 버전의 실행 시간도 비교하라.

2. **찢긴 읽기 재현.** `long` 필드에 한 스레드가 `0x0000000000000000`과 `0x7FFFFFFFFFFFFFFF`를 번갈아 쓰고, 다른 스레드가 계속 읽으면서 두 값 중 어느 쪽도 아닌 값을 발견하면 출력하는 프로그램을 작성하라. 32비트 프로세스(`<PlatformTarget>x86</PlatformTarget>`)로 빌드해 실행한 결과와 x64로 실행한 결과를 비교하라. 그다음 `Interlocked.Read`/`Interlocked.Exchange`로 고쳐라.

3. **재배치 관찰.** 48.2절의 `ThreadsSharingData`를 반복 실행하는 하네스를 작성하라(두 스레드를 수십만 번 반복 시작). `0`이 출력되는 횟수를 세고, `Volatile.Read`/`Volatile.Write`를 넣은 뒤 그 횟수가 0이 되는지 확인하라. ARM64 머신(Apple Silicon, Ampere 등)을 구할 수 있다면 같은 프로그램을 그곳에서 돌려 결과를 비교하라.

4. **경합 측정.** 하나의 `lock`으로 보호되는 카운터를 코어 수만큼의 스레드가 두드리는 프로그램을 작성하고, `dotnet-counters monitor --counters System.Runtime`으로 `monitor-lock-contention-count`를 관찰하라. 그다음 48.9절의 샤딩 카운터로 바꾸고 같은 카운터를 다시 관찰해 수치가 어떻게 변하는지 기록하라.

5. **데드락 분석.** 48.8절의 두 잠금 데드락 예제를 실행해 프로세스를 멎게 만든 뒤 `dotnet-dump collect`로 덤프를 뜨고, `dotnet-dump analyze`에서 `!syncblk`과 `~*e !clrstack`을 실행하라. 어느 스레드가 어느 객체를 쥐고 무엇을 기다리는지 순환을 직접 그려 보라.

6. **비동기 동시성 제한.** 100개의 URL을 다운로드하되 동시에 최대 5개만 실행되도록 `SemaphoreSlim.WaitAsync`로 구현하라. 진행 중인 요청 수를 `Interlocked`로 세어 최댓값이 5를 넘지 않는지 검증하고, `Release`를 `finally`에서 빼면 어떤 일이 벌어지는지 확인하라. 같은 작업을 `Parallel.ForEachAsync`로도 작성해 비교하라.

7. **`Lock` 타입 함정 재현.** .NET 9 프로젝트에서 `System.Threading.Lock` 필드를 만들고, 한 스레드는 `lock (myLock)`으로, 다른 스레드는 `object asObject = myLock; lock (asObject)`로 같은 임계 구역에 들어가는 프로그램을 작성하라. 상호 배제가 깨지는 것을 확인하고, 컴파일 시 어떤 경고가 나오는지 기록하라.
