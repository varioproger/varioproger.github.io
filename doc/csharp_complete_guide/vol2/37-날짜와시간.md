# 37장. 날짜와 시간

> **이 장의 위치** — Part VII「BCL I — 텍스트·시간·숫자」의 세 번째 장이다. 35장과 36장이 문자열을 다뤘다면, 이 장은 실무에서 문자열 다음으로 사고가 잦은 영역인 **시간**을 다룬다. `DateTime`이 8바이트 안에 무엇을 담고 무엇을 담지 않는지, `DateTimeOffset`이 그 빈틈 중 어디까지를 메우는지, 서머타임이 왜 존재하지 않는 시각과 두 번 존재하는 시각을 만들어내는지를 판다. 날짜/시간 API는 문법이 쉬워서 다 안다고 착각하기 좋은 영역이고, 그래서 조용히 틀린 코드가 가장 오래 살아남는 영역이다.
>
> **선수 지식** — 16장(구조체와 값 타입), 21장(널 안정성), 25장(동등성과 순서 비교), 20장(열거형과 특성)
>
> **이 장에서 다루지 않는 것** — 날짜/시간 **서식 지정자**(`"yyyy-MM-dd"`, `"O"`, `"R"` 같은 표준·사용자 지정 형식 문자열)와 `DateTimeStyles` 파싱 플래그, `CultureInfo`·`DateTimeFormatInfo`의 동작은 전부 38장이다. 이 장은 "어느 타입을 고르고 그 타입이 무엇을 의미하는가"만 다루고, 그 값을 문자열로 만드는 문법은 38장으로 넘긴다. JSON·XML 직렬화기의 동작 상세는 41장(JSON)과 42장(XML)이며, 여기서는 **저장 전략**만 정한다. 경과 시간 측정용 `Stopwatch`와 벤치마킹은 67.2절이다.

## 37.1 `TimeSpan` — 기간의 표현

### 무엇을 표현하는 타입인가

`System.TimeSpan`은 **시간 간격**을 표현하는 불변 구조체다. 부수적으로 **하루 중의 시각**(time of the day)을 표현하는 데도 쓰이는데, 이때는 서머타임 전환이 없다고 가정한 "자정 이후 경과 시간"이라는 뜻이 된다.

세 가지 사실이 이 타입의 전부다.

- **해상도는 100나노초**다. 이 단위를 **틱(tick)** 이라 부른다.
- **최댓값은 약 1,000만 일**이다. 정확히는 `10675199.02:48:05.4775807`.
- **음수가 될 수 있다.** 이것이 `TimeSpan`을 "길이"가 아니라 "변위"로 만든다.

C#은 이 타입에 대응하는 별칭 키워드를 정의하지 않는다. `int`가 `System.Int32`의 별칭인 것과 달리 `TimeSpan`은 그냥 `TimeSpan`이다. 이 장에서 다루는 다섯 개 타입 — `TimeSpan`, `DateTime`, `DateTimeOffset`, `DateOnly`, `TimeOnly` — 모두 그렇다.

### 내부 표현 — 필드 하나

`TimeSpan`의 내부는 놀라울 만큼 단순하다. `long` 필드 하나가 전부다.

```csharp
// 개념적 레이아웃 (실제 BCL 소스와 동일한 구조)
public readonly struct TimeSpan
{
    private readonly long _ticks;   // 100ns 단위. 이게 전부다.
}
```

`sizeof(TimeSpan)`은 8이다. 다시 말해 `TimeSpan`을 주고받는 비용은 `long`을 주고받는 비용과 같다. 힙 할당이 없고, 복사가 레지스터 하나로 끝난다. `TimeSpan` 필드를 클래스에 백 개 넣어도 800바이트일 뿐이다.

그래서 `TimeSpan`의 모든 산술은 결국 `long` 산술이다. `a + b`는 `_ticks` 덧셈 하나로 컴파일되고, JIT은 이를 단일 `add` 명령으로 낮춘다.

> **📌 왜 하필 100나노초인가**
>
> 100ns 틱은 .NET이 만든 단위가 아니라 Windows에서 물려받은 단위다. Win32의 `FILETIME`이 1601년 1월 1일부터의 100ns 간격 수를 64비트로 세는 구조이고, .NET은 기점만 0001년 1월 1일로 바꾸어 그 관례를 이어받았다. 64비트에 100ns를 담으면 약 29,000년 범위가 나오는데, .NET은 그중 0001~9999년만 유효 범위로 쓴다.
>
> 이 선택의 부작용이 하나 있다. 대부분의 유닉스 계열 API와 데이터베이스는 밀리초 또는 마이크로초를 단위로 쓰기 때문에, 왕복 변환에서 하위 자릿수가 잘린다. PostgreSQL의 `timestamp`는 마이크로초 정밀도이므로 `DateTime`의 틱 하위 한 자리는 저장되지 않는다.

### 생성 방법 세 가지

`TimeSpan`을 만드는 방법은 정확히 세 가지다.

1. 생성자 중 하나를 호출한다
2. 정적 `From…` 메서드 중 하나를 호출한다
3. `DateTime` 하나에서 다른 `DateTime`을 뺀다

**생성자**는 다음과 같다.

```csharp
public TimeSpan (int hours, int minutes, int seconds);
public TimeSpan (int days, int hours, int minutes, int seconds);
public TimeSpan (int days, int hours, int minutes, int seconds,
                 int milliseconds);
public TimeSpan (int days, int hours, int minutes, int seconds,
                 int milliseconds, int microseconds);   // ※.NET 7
public TimeSpan (long ticks);   // 틱 하나 = 100ns
```

**`From…` 정적 메서드**는 단위 하나만으로 간격을 지정할 때 더 편하다.

```csharp
public static TimeSpan FromDays         (double value);
public static TimeSpan FromHours        (double value);
public static TimeSpan FromMinutes      (double value);
public static TimeSpan FromSeconds      (double value);
public static TimeSpan FromMilliseconds (double value);
public static TimeSpan FromMicroseconds (double value);   // ※.NET 7
public static TimeSpan FromTicks        (long value);
```

세 번째 방법 — 뺄셈 — 은 37.2절에서 `DateTime`을 다룰 때 나온다.

```csharp
Console.WriteLine (new TimeSpan (2, 30, 0));    // 02:30:00
Console.WriteLine (TimeSpan.FromHours (2.5));   // 02:30:00
Console.WriteLine (TimeSpan.FromHours (-2.5));  // -02:30:00
```

마지막 줄이 중요하다. **`TimeSpan`은 음수를 정상적인 값으로 취급한다.** 예외가 아니고, 절댓값으로 정규화되지도 않는다.

> **⚠️ `From…`의 `double` 오버로드는 밀리초 단위로 반올림한다**
>
> `FromSeconds`·`FromMinutes`·`FromHours`·`FromDays`는 인자를 밀리초로 환산한 뒤 **가장 가까운 밀리초로 반올림**해서 틱을 만든다. `TimeSpan`의 해상도가 100ns인데도 이 경로로는 밀리초보다 정밀한 값을 만들 수 없다.
>
> ```csharp
> Console.WriteLine (TimeSpan.FromSeconds (0.00005).Ticks);  // 0 — 사라진다
> Console.WriteLine (TimeSpan.FromTicks (500).Ticks);        // 500
> ```
>
> 마이크로초 이하를 다뤄야 하면 `FromTicks`나 `TimeSpan(long)` 생성자를 써라. `FromMicroseconds`(※.NET 7)도 같은 반올림 규칙을 적용하지만 단위가 마이크로초이므로 실용상 문제가 되지 않는다.

### 연산자

`TimeSpan`은 `<`, `>`, `<=`, `>=`, `==`, `!=`, `+`, `-`(이항·단항)를 오버로드한다.

```csharp
TimeSpan a = TimeSpan.FromHours (2) + TimeSpan.FromMinutes (30);   // 02:30:00
TimeSpan b = TimeSpan.FromDays (10) - TimeSpan.FromSeconds (1);    // 9.23:59:59
```

곱셈과 나눗셈 연산자도 있다. `TimeSpan * double`, `TimeSpan / double`, 그리고 `TimeSpan / TimeSpan`(결과는 `double`)이 지원된다.

```csharp
TimeSpan half = TimeSpan.FromHours (3) / 2;                     // 01:30:00
double ratio  = TimeSpan.FromHours (3) / TimeSpan.FromHours (2); // 1.5
```

`Negate()`는 부호를 뒤집고, `Duration()`은 절댓값을 돌려준다.

```csharp
TimeSpan neg = TimeSpan.FromHours (-2.5);
Console.WriteLine (neg.Negate());     // 02:30:00
Console.WriteLine (neg.Duration());   // 02:30:00
```

### 구성 요소 프로퍼티 vs `Total…` 프로퍼티

이 구분이 `TimeSpan`에서 가장 자주 틀리는 지점이다. 앞의 `b`(10일에서 1초 모자란 값)로 확인한다.

```csharp
TimeSpan nearlyTenDays = TimeSpan.FromDays (10) - TimeSpan.FromSeconds (1);

Console.WriteLine (nearlyTenDays.Days);           // 9
Console.WriteLine (nearlyTenDays.Hours);          // 23
Console.WriteLine (nearlyTenDays.Minutes);        // 59
Console.WriteLine (nearlyTenDays.Seconds);        // 59
Console.WriteLine (nearlyTenDays.Milliseconds);   // 0
```

`Days`, `Hours`, `Minutes`, `Seconds`, `Milliseconds`는 **정수 타입이고, 값을 "9일 23시간 59분 59초"로 분해했을 때의 각 자리**를 돌려준다. 시계 표시판의 각 칸이라고 생각하면 된다.

반면 `Total…` 프로퍼티는 **`double` 타입이고, 전체 간격을 그 단위 하나로 환산한 값**을 돌려준다.

```csharp
Console.WriteLine (nearlyTenDays.TotalDays);           // 9.99998842592593
Console.WriteLine (nearlyTenDays.TotalHours);          // 239.999722222222
Console.WriteLine (nearlyTenDays.TotalMinutes);        // 14399.9833333333
Console.WriteLine (nearlyTenDays.TotalSeconds);        // 863999
Console.WriteLine (nearlyTenDays.TotalMilliseconds);   // 863999000
```

| 프로퍼티 | 반환 타입 | 의미 | 위 예제 값 |
|---|---|---|---|
| `Days` | `int` | 분해한 값의 "일" 자리 | 9 |
| `Hours` | `int` | 분해한 값의 "시" 자리 (−23~23) | 23 |
| `Minutes` | `int` | 분해한 값의 "분" 자리 (−59~59) | 59 |
| `Seconds` | `int` | 분해한 값의 "초" 자리 (−59~59) | 59 |
| `Milliseconds` | `int` | 분해한 값의 "밀리초" 자리 | 0 |
| `Microseconds` ※.NET 7 | `int` | 분해한 값의 "마이크로초" 자리 | 0 |
| `Nanoseconds` ※.NET 7 | `int` | 분해한 값의 "나노초" 자리 (100 단위) | 0 |
| `Ticks` | `long` | 전체를 100ns 단위로 | 8639990000000 |
| `TotalDays` | `double` | 전체를 일 단위로 | 9.99998842592593 |
| `TotalHours` | `double` | 전체를 시 단위로 | 239.999722222222 |
| `TotalMinutes` | `double` | 전체를 분 단위로 | 14399.9833333333 |
| `TotalSeconds` | `double` | 전체를 초 단위로 | 863999 |
| `TotalMilliseconds` | `double` | 전체를 밀리초 단위로 | 863999000 |

> **⚠️ 타임아웃 계산에 `Seconds`를 쓰면 61초가 1초가 된다**
>
> 실무에서 가장 흔한 `TimeSpan` 버그가 이것이다.
>
> ```csharp
> TimeSpan elapsed = TimeSpan.FromSeconds (61);
> if (elapsed.Seconds > 60) { /* 절대 실행되지 않는다 */ }   // Seconds == 1
> if (elapsed.TotalSeconds > 60) { /* 이게 맞다 */ }         // TotalSeconds == 61
> ```
>
> 규칙은 간단하다. **"이 간격이 얼마나 긴가"를 물으면 `Total…`, "이 값을 어떻게 표시할까"를 물으면 구성 요소 프로퍼티**다. 조건문 안에서는 거의 항상 `Total…`이거나, 아예 `TimeSpan`끼리 직접 비교하는 것이 옳다.
>
> 사실 가장 좋은 답은 셋째다. `if (elapsed > TimeSpan.FromMinutes(1))` — 숫자로 내려가지 말고 `TimeSpan`을 `TimeSpan`과 비교하면 단위 실수 자체가 불가능해진다.

### 음수 `TimeSpan`의 구성 요소는 전부 음수다

음수 간격을 분해하면 **모든 자리가 음수**로 나온다. 부호가 최상위 자리에만 붙지 않는다.

```csharp
TimeSpan t = TimeSpan.FromHours (-2.5);

Console.WriteLine (t);                // -02:30:00
Console.WriteLine (t.Hours);          // -2
Console.WriteLine (t.Minutes);        // -30
Console.WriteLine (t.TotalMinutes);   // -150
```

`t.Hours`가 `-2`이고 `t.Minutes`가 `+30`이 아니라 `-30`이다. 사람에게 보여줄 문자열을 손으로 조립하는 코드에서 이 규칙을 잊으면 `-2시간 -30분` 같은 출력이 나온다. 부호를 따로 뽑고 `Duration()`으로 절댓값을 분해하는 것이 안전하다.

```csharp
string sign = t < TimeSpan.Zero ? "-" : "";
TimeSpan abs = t.Duration();
Console.WriteLine ($"{sign}{abs.Hours}시간 {abs.Minutes}분");   // -2시간 30분
```

### `TimeSpan.Zero`와 정적 필드들

`TimeSpan`의 **기본값은 `TimeSpan.Zero`** 다. 구조체이므로 `default(TimeSpan)`이 모든 필드가 0인 값이고, 그것이 곧 `TimeSpan.Zero`다. 이는 16.4절에서 본 "0이 유효한 상태여야 한다"는 원칙을 잘 지키는 설계다 — 길이 0인 간격은 완벽하게 의미 있는 값이다.

| 정적 멤버 | 값 | 용도 |
|---|---|---|
| `TimeSpan.Zero` | `00:00:00` | 기본값, 부호 판별 기준, "즉시" |
| `TimeSpan.MinValue` | `-10675199.02:48:05.4775808` | 하한 (`long.MinValue` 틱) |
| `TimeSpan.MaxValue` | `10675199.02:48:05.4775807` | 상한 (`long.MaxValue` 틱) |
| `TimeSpan.TicksPerDay` | 864,000,000,000 | 단위 환산 상수 |
| `TimeSpan.TicksPerHour` | 36,000,000,000 | 단위 환산 상수 |
| `TimeSpan.TicksPerMinute` | 600,000,000 | 단위 환산 상수 |
| `TimeSpan.TicksPerSecond` | 10,000,000 | 단위 환산 상수 |
| `TimeSpan.TicksPerMillisecond` | 10,000 | 단위 환산 상수 |
| `TimeSpan.TicksPerMicrosecond` ※.NET 7 | 10 | 단위 환산 상수 |

> **💡 `TimeSpan.Zero`와 `Timeout.InfiniteTimeSpan`을 구분해서 써라**
>
> BCL의 타임아웃 인자를 받는 API — `Task.Delay`, `CancellationTokenSource`, `SemaphoreSlim.WaitAsync`, `Timer` — 는 대개 두 개의 특별한 값을 인식한다. `TimeSpan.Zero`는 "기다리지 않고 즉시"이고, `Timeout.InfiniteTimeSpan`(내부적으로 −1 밀리초)은 "무한정"이다.
>
> 설정 파일에서 읽은 타임아웃이 파싱 실패로 `default(TimeSpan)`이 되면 그것은 `TimeSpan.Zero`, 즉 "즉시 포기"다. 무한 대기가 될 것이라고 기대했다면 정반대 동작이다. 설정에서 읽는 `TimeSpan`은 `TimeSpan?`으로 받고 `null`일 때의 기본값을 명시하는 편이 안전하다(21장).

### 파싱과 포매팅

`TimeSpan.Parse`는 `ToString`의 반대 동작이고, `TryParse`는 실패 시 예외 대신 `false`를 돌려준다. `System.Xml.XmlConvert` 클래스도 XML 표준 형식(ISO 8601 기간 표기)을 따르는 `TimeSpan`/문자열 변환 메서드를 제공한다.

```csharp
TimeSpan ts = TimeSpan.Parse ("1.02:03:04");   // 1일 2시간 3분 4초

if (TimeSpan.TryParse (userInput, out TimeSpan parsed))
    Console.WriteLine (parsed.TotalMinutes);
```

서식 지정자(`"c"`, `"g"`, `"G"`와 사용자 지정 패턴)의 상세와 문화권 영향은 38.5절에서 다룬다. `XmlConvert`는 38.9절이다.

### 하루 중의 시각으로서의 `TimeSpan`

`TimeSpan`은 자정 이후 경과 시간, 즉 "하루 중의 시각"을 표현하는 데도 쓸 수 있다. 현재 시각을 이 형태로 얻으려면 `DateTime.Now.TimeOfDay`를 호출한다.

```csharp
TimeSpan now = DateTime.Now.TimeOfDay;
Console.WriteLine (now);   // 예: 14:32:05.1234567
```

역사적으로 이것이 "시각만" 표현하는 유일한 방법이었다. 하지만 `TimeSpan`은 24시간을 넘거나 음수가 될 수 있으므로 타입이 불변 조건을 강제해 주지 못한다. `TimeSpan.FromHours(30)`은 완벽하게 유효한 `TimeSpan`이지만 "하루 중의 시각"으로서는 무의미하다. .NET 6이 `TimeOnly`를 도입한 이유가 이것이고, 37.3절에서 다룬다.

> **⚠️ 하루 중의 시각을 `TimeSpan`으로 표현할 때는 서머타임이 없다고 가정한다**
>
> "자정으로부터 경과한 시간"과 "벽시계가 가리키는 시각"은 서머타임 전환일에 어긋난다. 시계를 한 시간 앞당기는 날, 자정으로부터 9시간이 지난 순간의 벽시계는 10:00이다. `TimeSpan`으로 하루 중의 시각을 다루는 코드는 이 차이를 표현할 수 없다.
>
> 즉 `someDate.Date + someTimeSpan`으로 "그날 그 시각"을 조립하는 관용구는 전환일에 틀린 값을 만들거나, 아예 존재하지 않는 시각을 만든다. 37.7절에서 자세히 판다.

### 성능

`TimeSpan`은 8바이트 값 타입이므로 생성·전달·비교가 모두 할당 없이 끝난다. 주의할 지점은 두 군데다.

- **`ToString()`은 문자열을 할당한다.** 로그 한 줄마다 `TimeSpan.ToString()`을 부르는 코드는 GC 압력을 만든다. `ISpanFormattable`을 구현하므로 `TryFormat`으로 스택 버퍼에 직접 쓸 수 있다(38.8절).
- **`object`로 취급하면 박싱된다.** `Dictionary<string, object>`에 `TimeSpan`을 넣거나, 문자열 보간의 인자로 `object` 오버로드가 선택되면 힙 할당이 일어난다(15장). 최신 C#의 보간 문자열 핸들러는 대부분 이를 피하지만, `string.Format(…, ts)` 같은 경로는 여전히 박싱한다.

## 37.2 `DateTime`과 `DateTimeOffset` — 무엇이 다른가

### 두 타입의 공통 골격

`DateTime`과 `DateTimeOffset`은 **날짜와, 선택적으로 시각을 표현하는 불변 구조체**다. 둘 다 해상도는 100ns이고 범위는 0001년부터 9999년까지다.

`DateTimeOffset`은 기능적으로 `DateTime`과 비슷하되, **UTC로부터의 오프셋을 함께 저장한다**는 점이 다르다. 이 하나의 차이가 서로 다른 시간대의 값을 비교할 때 훨씬 의미 있는 결과를 만든다.

```text
DateTimeOffset이 표현하는 것:
    July 01 2019 03:00:00 -06:00
    └────────────────┘ └────┘
      벽시계 날짜/시각   UTC 오프셋
```

### 내부 표현 — 여기서 모든 것이 갈린다

두 타입의 차이는 결국 메모리 레이아웃의 차이다.

```text
DateTime — 8바이트 (ulong _dateData 하나)

  63 62 61                                                    0
 ┌──┬──┬────────────────────────────────────────────────────────┐
 │Kind │            0001-01-01 00:00:00 이후의 틱 수            │
 │(2bit)│                     (62 bit)                          │
 └──┴──┴────────────────────────────────────────────────────────┘
   ↑
   00 = Unspecified   01 = Utc   10 = Local

  → 비교는 아래 62비트만 본다. Kind는 무시된다.


DateTimeOffset — 16바이트 (DateTime + short, 패딩 포함)

 ┌──────────────────────────────┬──────────────────┬───────────┐
 │  DateTime _dateTime (8byte)  │ short _offset    │  padding  │
 │  값은 항상 UTC (불변)        │ Minutes (2byte)  │  (6byte)  │
 └──────────────────────────────┴──────────────────┴───────────┘

  → 비교는 왼쪽 UTC DateTime만 본다. 오프셋은 주로 포매팅용이다.
```

`DateTime`은 **62비트 틱 + 2비트 `DateTimeKind`** 로 구성된다. 틱은 0001년 1월 1일 자정 이후의 100ns 간격 수이고, `Kind`는 이 값이 무엇을 기준으로 하는지를 알려주는 3상태 플래그다.

`DateTimeOffset`은 **값이 항상 UTC인 `DateTime` 필드 하나와, UTC 오프셋을 분 단위로 담는 16비트 정수 필드**로 구성된다. 오프셋이 분 단위 `short`라는 것은 두 가지를 뜻한다 — 초 단위 오프셋을 표현할 수 없고, 어떤 지역인지도 알 수 없다.

> **📌 `DateTimeOffset`은 시간대를 모른다**
>
> `DateTimeOffset`은 UTC 오프셋을 **분 단위 정수**로만 저장한다. 지역 정보는 어디에도 없다. 따라서 `+08:00`이라는 오프셋이 싱가포르 시각인지 퍼스(서호주) 시각인지 구별할 방법이 존재하지 않는다. 두 지역은 표준시가 같지만 서머타임 이력이 다르므로, 이 구별이 필요한 상황이 실제로 있다.
>
> 이 한계가 37.10절의 "미래 일정은 `DateTimeOffset`으로 저장하면 안 된다"는 결론으로 이어진다.

### 동등 비교 의미론 — 선택의 진짜 기준

`DateTime`과 `DateTimeOffset` 중 무엇을 쓸지는 대부분 **동등 비교가 어떻게 동작하기를 원하는가**로 결정된다.

- **`DateTime`은 비교에서 3상태 플래그를 무시한다.** 연·월·일·시·분·초가 같으면 같은 값으로 본다.
- **`DateTimeOffset`은 같은 시점(point in time)을 가리키면 같은 값으로 본다.**

이 차이를 코드로 보면 즉시 이해된다.

```csharp
DateTime dt1 = new DateTime (2000, 1, 1, 10, 20, 30, DateTimeKind.Local);
DateTime dt2 = new DateTime (2000, 1, 1, 10, 20, 30, DateTimeKind.Utc);
Console.WriteLine (dt1 == dt2);        // True  ← Kind가 달라도 틱이 같으면 같다

DateTime local = DateTime.Now;
DateTime utc   = local.ToUniversalTime();
Console.WriteLine (local == utc);      // False ← 같은 시점인데 다르다고 한다
```

두 줄 다 직관에 반한다. 첫 줄은 **다른 시점인데 같다**고 하고, 둘째 줄은 **같은 시점인데 다르다**고 한다. `DateTime`의 `==`는 시점을 비교하는 연산자가 아니라 **달력 필드를 비교하는 연산자**이기 때문이다.

`DateTimeOffset`은 정반대다.

```csharp
DateTimeOffset local = DateTimeOffset.Now;
DateTimeOffset utc   = local.ToUniversalTime();

Console.WriteLine (local.Offset);        // -06:00:00 (중미 기준)
Console.WriteLine (utc.Offset);          // 00:00:00

Console.WriteLine (local == utc);            // True  ← 같은 시점이므로 같다
Console.WriteLine (local.EqualsExact (utc)); // False ← 오프셋까지 보면 다르다
```

**비교에 오프셋을 포함시키려면 `EqualsExact`를 명시적으로 불러야 한다.** `==`, `Equals`, `CompareTo`, 정렬, `Dictionary` 키 — 전부 UTC 값만 본다.

> **⚠️ 서머타임 하나만으로도 이 구별이 중요해진다**
>
> "우리 앱은 한국에서만 돌아가니까 시간대는 신경 안 써도 된다"는 판단은 절반만 맞다. 한국은 현재 서머타임을 쓰지 않지만, 서머타임을 쓰는 지역이라면 **단일 지역 애플리케이션에서도** 로컬 `DateTime` 비교가 깨진다. 가을에 시계를 되돌리는 날, 로컬 시각은 한 시간을 두 번 지나가므로 "나중에 기록된 값이 더 크다"는 가정이 무너진다.
>
> 여러 지역을 다루지 않더라도, 로그·감사·순서 판정처럼 "시간이 앞으로만 흐른다"를 전제하는 코드는 반드시 UTC나 `DateTimeOffset`을 써야 한다. 37.7절에서 이 규칙을 정리한다.

따라서 다음 두 값을 `DateTime`은 **다르다**고 보고 `DateTimeOffset`은 **같다**고 본다.

```text
July 01 2019 09:00:00 +00:00   (GMT)
July 01 2019 03:00:00 -06:00   (중미 지역 로컬 시각)
```

대부분의 경우 `DateTimeOffset`의 동등성 논리가 더 낫다. 국제 이벤트 둘 중 어느 쪽이 더 최근인지 계산할 때 `DateTimeOffset`은 별도 처리 없이 옳은 답을 준다. 같은 일을 `DateTime`으로 하려면 애플리케이션 전체를 하나의 시간대(보통 UTC)로 표준화해야 하는데, 여기에는 두 가지 문제가 있다.

- 사용자에게 친절하려면 UTC `DateTime`을 포매팅 전에 **명시적으로** 로컬 시각으로 변환해야 한다.
- 그걸 잊고 로컬 `DateTime`을 섞어 넣기가 너무 쉽다.

### 그런데도 `DateTime`이 나은 경우

`DateTime`이 더 적합한 자리가 분명히 있다. **런타임의 로컬 컴퓨터를 기준으로 한 상대적인 값**을 지정할 때다.

전형적인 예가 이것이다. 전 세계에 지사가 있고, 각 지사에서 **현지 시각 새벽 3시**에 아카이브 작업을 돌리고 싶다고 하자(그 시각에 활동이 가장 적으므로). 이때는 `DateTime`이 맞다. 각 사이트의 로컬 시각을 존중하기 때문이다.

```csharp
// 각 지사 서버에서 이 값은 "그 서버의 새벽 3시"를 뜻한다.
DateTime archiveTime = new DateTime (2025, 3, 9, 3, 0, 0);   // Unspecified
```

이 값을 `DateTimeOffset`으로 바꾸면 오프셋이 박혀 버리므로 "각자의 새벽 3시"라는 의미가 사라진다. `2025-03-09T03:00:00+09:00`은 서울의 새벽 3시일 뿐, 런던 지사에서는 새벽 3시가 아니다.

> **💡 판단 기준 한 문장**
>
> **"이 값은 지구상의 특정 순간인가, 아니면 어떤 벽시계가 가리키는 눈금인가?"**
>
> 특정 순간이면 `DateTimeOffset`(또는 UTC `DateTime`)이고, 벽시계 눈금이면 `DateTime`이다. 로그 타임스탬프·주문 시각·측정 시점은 전자, 알람 시각·영업시간·"매달 1일 자정"은 후자다. 후자를 `DateTimeOffset`으로 저장하는 순간 그것은 특정 순간으로 굳어 버려서 다른 시간대에서 재해석할 수 없게 된다.

### 두 타입 비교표

| 항목 | `DateTime` | `DateTimeOffset` |
|---|---|---|
| 크기 | 8바이트 | 16바이트 |
| 내부 | 62비트 틱 + 2비트 `Kind` | UTC `DateTime` + 16비트 분 오프셋 |
| 시간대 정보 | 3상태 플래그(`Unspecified`/`Utc`/`Local`) | UTC 오프셋(분). 지역 이름은 없음 |
| `==`가 보는 것 | 틱만. `Kind` 무시 | UTC 시점만. `Offset` 무시 |
| 오프셋까지 비교 | 해당 없음 | `EqualsExact` |
| 같은 시점, 다른 표현 | 다르다고 판정 | 같다고 판정 |
| 다른 시점, 같은 벽시계 | 같다고 판정 | 다르다고 판정 |
| `ToUniversalTime` | 틱을 바꾼다(조건부) | 틱은 그대로, 오프셋만 바꾼다 |
| BCL 지원 폭 | 넓다 (대부분의 API가 이쪽) | 상대적으로 좁다 |
| 적합한 용도 | 벽시계 시각, 로컬 상대 시각, 날짜 | 절대 시점, 로그, 감사, 국제 비교 |
| SQL Server 매핑 | `datetime2` | `datetimeoffset` |

> **📌 SQL Server 2008과 `datetimeoffset`**
>
> SQL Server 2008이 `datetimeoffset`이라는 동명의 데이터 타입으로 `DateTimeOffset`을 직접 지원하기 시작했다. 이전에는 오프셋을 별도 컬럼에 저장하거나 UTC로 정규화해서 넣는 수밖에 없었다. 저장 전략은 37.10절에서 정리한다.

### `DateTime` 생성

`DateTime`은 연·월·일 정수를 받는 생성자와, 여기에 시·분·초·밀리초(그리고 ※.NET 7부터 마이크로초)를 더 받는 생성자를 정의한다.

```csharp
public DateTime (int year, int month, int day);
public DateTime (int year, int month, int day,
                 int hour, int minute, int second, int millisecond);
```

날짜만 지정하면 시각은 암묵적으로 자정(0:00)이 된다.

생성자들은 `DateTimeKind`도 받을 수 있다. 이 열거형의 값은 셋이다.

```csharp
public enum DateTimeKind { Unspecified, Local, Utc }
```

앞 절에서 말한 3상태 플래그가 바로 이것이다. **`Unspecified`가 기본값**이고, "이 `DateTime`은 시간대에 대해 아무 말도 하지 않는다"는 뜻이다. `Local`은 현재 컴퓨터의 로컬 시간대 기준이라는 뜻이다. 다만 **로컬 `DateTime`은 그것이 어떤 시간대인지도, `DateTimeOffset`처럼 UTC로부터의 수치 오프셋도 담고 있지 않다.** 그저 "로컬"이라는 표지만 있다.

`DateTime`의 `Kind` 프로퍼티가 이 `DateTimeKind`를 돌려준다.

`DateTime` 생성자에는 `Calendar` 객체를 받는 오버로드도 있다. `System.Globalization`에 정의된 `Calendar` 하위 클래스 중 아무거나 써서 날짜를 지정할 수 있다.

```csharp
DateTime d = new DateTime (5767, 1, 1,
                           new System.Globalization.HebrewCalendar());
Console.WriteLine (d);     // 12/12/2006 12:00:00 AM
```

(이 예제의 날짜 표시 형식은 컴퓨터의 지역 설정에 따라 달라진다.) **`DateTime`은 언제나 기본 그레고리력을 쓴다.** 위 예제는 생성 시점에 일어나는 일회성 변환일 뿐이다. 다른 달력으로 계산을 하려면 `Calendar` 하위 클래스의 메서드를 직접 써야 한다.

`long` 틱 값 하나로 `DateTime`을 만들 수도 있다. 이때 틱은 0001년 1월 1일 자정 이후의 100ns 간격 수다.

상호 운용을 위해 `DateTime`은 Windows 파일 시각(`long`)을 변환하는 정적 `FromFileTime`·`FromFileTimeUtc` 메서드와, OLE 자동화 날짜/시각(`double`)을 변환하는 `FromOADate`를 제공한다.

문자열로부터 `DateTime`을 만들려면 정적 `Parse` 또는 `ParseExact`를 호출한다. 둘 다 선택적 플래그와 형식 공급자를 받고, `ParseExact`는 형식 문자열도 받는다. 파싱의 상세는 38.1절과 38.5절, 38.6절에서 다룬다.

### `DateTimeOffset` 생성

`DateTimeOffset`은 비슷한 생성자 집합을 갖되, UTC 오프셋을 `TimeSpan`으로 함께 지정한다.

```csharp
public DateTimeOffset (int year, int month, int day,
                       int hour, int minute, int second,
                       TimeSpan offset);
public DateTimeOffset (int year, int month, int day,
                       int hour, int minute, int second, int millisecond,
                       TimeSpan offset);
```

> **⚠️ 오프셋은 분 단위 정수여야 한다**
>
> 생성자에 넘기는 `TimeSpan`은 **정수 분**이어야 한다. 그렇지 않으면 예외가 던져진다. 내부 표현이 분 단위 `short`이므로 초 이하를 표현할 방법이 없기 때문이다.
>
> ```csharp
> // 초 성분이 있으면 던진다 (ArgumentException 계열)
> var bad  = new DateTimeOffset (2025, 1, 1, 0, 0, 0, TimeSpan.FromSeconds (30));
> // 오프셋 절댓값이 14시간을 넘어도 던진다 (ArgumentOutOfRangeException 계열)
> var bad2 = new DateTimeOffset (2025, 1, 1, 0, 0, 0, TimeSpan.FromHours (15));
> ```
>
> 역사적으로 실재했던 LMT(지방 평균시) 기반 오프셋 중에는 분 단위가 아닌 것들이 있다. 1908년 이전의 시각을 다루는 시스템이라면 이 제약에 걸린다.

`DateTimeOffset`도 `Calendar` 객체를 받는 생성자, `long` 틱 값을 받는 생성자, 문자열을 받는 정적 `Parse`/`ParseExact`를 갖는다.

기존 `DateTime`으로부터 `DateTimeOffset`을 만들 수도 있다. 생성자를 쓰거나,

```csharp
public DateTimeOffset (DateTime dateTime);
public DateTimeOffset (DateTime dateTime, TimeSpan offset);
```

암시적 캐스트를 쓴다.

```csharp
DateTimeOffset dt = new DateTime (2000, 2, 3);
```

> **📌 암시적 캐스트가 있는 이유**
>
> `DateTime` → `DateTimeOffset` 암시적 캐스트는 편의 기능처럼 보이지만 실은 현실적인 타협이다. **.NET BCL 대부분이 `DateTimeOffset`이 아니라 `DateTime`을 받기 때문이다.** `File.GetLastWriteTime`, `XmlConvert`, 상당수의 데이터 액세스 API가 여전히 `DateTime` 중심이다. 암시적 변환이 없으면 `DateTimeOffset`을 주력으로 쓰는 코드가 경계마다 명시적 변환으로 지저분해진다.

### 암시적 변환의 오프셋 추론 규칙

오프셋을 지정하지 않으면 `DateTime` 값으로부터 다음 규칙으로 추론된다.

| 원본 `DateTime`의 `Kind` | 추론되는 오프셋 |
|---|---|
| `Utc` | 0 (`+00:00`) |
| `Local` | 현재 로컬 시간대의 오프셋 |
| `Unspecified` (기본값) | 현재 로컬 시간대의 오프셋 |

**`Unspecified`가 `Local`과 똑같이 취급된다**는 점을 놓치지 마라. "시간대를 모른다"고 표시된 값이 조용히 "이 서버의 로컬 시각"으로 해석된다. 데이터베이스에서 읽어 온 `DateTime`은 대개 `Unspecified`이므로, 그 값을 무심코 `DateTimeOffset`에 대입하면 **DB에 UTC로 저장했더라도 서버 로컬 시간대로 해석된다.**

```csharp
// DB에서 읽은 값 — Kind는 Unspecified
DateTime fromDb = ReadUtcTimestampFromDatabase();

// 이 캐스트는 fromDb를 "서버 로컬 시각"으로 해석한다. UTC로 저장했다면 틀렸다.
DateTimeOffset wrong = fromDb;

// 올바른 방법: Kind를 먼저 확정한다
DateTimeOffset right = DateTime.SpecifyKind (fromDb, DateTimeKind.Utc);
```

> **⚠️ 이것이 UTC 저장 시스템에서 가장 흔한 8~9시간 오차의 원인이다**
>
> "DB에는 UTC로 넣었는데 화면에는 9시간 뒤 시각이 나온다"는 버그의 90%가 위 패턴이다. `Unspecified`는 "알 수 없음"이 아니라 실질적으로 "로컬로 간주"로 동작하는 자리가 많다. 데이터 액세스 계층 경계에서 `SpecifyKind`로 `Kind`를 못 박는 것을 규칙으로 만들어라. 37.4절에서 `Kind`별 동작을 표로 정리한다.

### `DateTimeOffset` → `DateTime` 변환 세 프로퍼티

반대 방향 변환을 위해 `DateTimeOffset`은 `DateTime` 타입을 돌려주는 프로퍼티 세 개를 제공한다.

| 프로퍼티 | 돌려주는 값 | 결과의 `Kind` |
|---|---|---|
| `UtcDateTime` | UTC 시각 | `Utc` |
| `LocalDateTime` | 현재 로컬 시간대 시각 (필요하면 변환) | `Local` |
| `DateTime` | 지정된 그대로의 시각 (= UTC + 오프셋) | `Unspecified` |

```csharp
DateTimeOffset dto = new DateTimeOffset (
    2025, 3, 9, 3, 0, 0, TimeSpan.FromHours (9));   // 서울 새벽 3시

Console.WriteLine (dto.UtcDateTime);     // 2025-03-08 18:00:00  (Kind=Utc)
Console.WriteLine (dto.DateTime);        // 2025-03-09 03:00:00  (Kind=Unspecified)
Console.WriteLine (dto.LocalDateTime);   // 실행 컴퓨터의 로컬 시각 (Kind=Local)
```

`DateTime` 프로퍼티는 **UTC 값에 오프셋을 더한 벽시계 시각**을 `Unspecified`로 돌려준다. 원래 값이 어느 지역이었는지에 대한 정보는 여기서 사라진다.

> **⚠️ `dto.DateTime`은 "그 지역의 벽시계"일 뿐 어떤 시간대인지 모른다**
>
> `LocalDateTime`은 실행 중인 컴퓨터의 시간대로 변환한 값이고, `DateTime`은 원래 오프셋 기준의 벽시계 값이다. 이 둘을 혼동하면 서버에서는 맞고 개발자 PC에서는 틀리는(또는 그 반대인) 코드가 나온다. 서버 시간대를 UTC로 맞춰 두면 두 값이 우연히 같아져서 버그가 더 오래 숨는다.

### 현재 시각 얻기

`DateTime`과 `DateTimeOffset` 모두 현재 날짜와 시각을 돌려주는 정적 `Now` 프로퍼티를 갖는다.

```csharp
Console.WriteLine (DateTime.Now);         // 11/11/2019 1:23:45 PM
Console.WriteLine (DateTimeOffset.Now);   // 11/11/2019 1:23:45 PM -06:00
```

`DateTime`은 날짜 부분만 돌려주는 `Today`도 제공한다.

```csharp
Console.WriteLine (DateTime.Today);       // 11/11/2019 12:00:00 AM
```

정적 `UtcNow` 프로퍼티는 현재 날짜와 시각을 UTC로 돌려준다.

```csharp
Console.WriteLine (DateTime.UtcNow);         // 11/11/2019 7:23:45 AM
Console.WriteLine (DateTimeOffset.UtcNow);   // 11/11/2019 7:23:45 AM +00:00
```

**이 메서드들의 정밀도는 운영체제에 따라 다르며 일반적으로 10~20밀리초 범위다.**

> **⚠️ 경과 시간 측정에 `DateTime.Now`를 쓰지 마라**
>
> 10~20ms 정밀도는 "이 메서드가 3ms 걸렸다"를 측정하기에 턱없이 거칠다. 게다가 `DateTime.Now`는 **단조(monotonic)가 아니다.** NTP 동기화, 사용자의 시계 변경, 서머타임 전환이 값을 뒤로 되돌릴 수 있고, 그러면 경과 시간이 음수가 된다.
>
> 경과 시간에는 `Stopwatch`(67.2절)나 `Environment.TickCount64`를 써라. 둘 다 벽시계가 아니라 단조 증가하는 고해상도 카운터를 읽는다. ※.NET 8부터는 `TimeProvider.GetTimestamp()`/`GetElapsedTime()`이 이 역할을 추상화한다(37.9절).

> **💡 `DateTime.Now`는 `DateTime.UtcNow`보다 비싸다**
>
> `Now`는 내부적으로 UTC 시각을 얻은 뒤 **현재 로컬 시간대의 오프셋을 계산해서 더한다.** 서머타임 조정 규칙 조회가 포함되므로 `UtcNow`보다 확실히 비싸다. 초당 수십만 번 타임스탬프를 찍는 로깅 경로에서는 차이가 측정된다.
>
> 실무 규칙: **내부적으로는 UTC로 다루고, 사람에게 보여주는 마지막 순간에만 로컬로 변환한다.** 이러면 성능과 정확성이 동시에 좋아진다.

### 날짜/시각 요소 읽기

`DateTime`과 `DateTimeOffset`은 날짜/시각의 각 요소를 돌려주는 비슷한 인스턴스 프로퍼티 집합을 제공한다.

```csharp
DateTime dt = new DateTime (2000, 2, 3, 10, 20, 30);

Console.WriteLine (dt.Year);           // 2000
Console.WriteLine (dt.Month);          // 2
Console.WriteLine (dt.Day);            // 3
Console.WriteLine (dt.DayOfWeek);      // Thursday
Console.WriteLine (dt.DayOfYear);      // 34

Console.WriteLine (dt.Hour);           // 10
Console.WriteLine (dt.Minute);         // 20
Console.WriteLine (dt.Second);         // 30
Console.WriteLine (dt.Millisecond);    // 0
Console.WriteLine (dt.Ticks);          // 630851700300000000
Console.WriteLine (dt.TimeOfDay);      // 10:20:30 (TimeSpan을 돌려준다)
```

`DateTimeOffset`은 여기에 `TimeSpan` 타입의 `Offset` 프로퍼티가 더 있다.

`Date` 프로퍼티는 시각을 자정으로 자른 `DateTime`을 돌려준다. `Microsecond`와 `Nanosecond` 프로퍼티가 ※.NET 7에 추가되었다.

### 산술

두 타입 모두 계산을 수행하는 인스턴스 메서드를 제공한다(대부분 `double` 또는 `int` 인자를 받는다).

| 메서드 | 인자 | 메서드 | 인자 |
|---|---|---|---|
| `AddYears` | `int` | `AddMinutes` | `double` |
| `AddMonths` | `int` | `AddSeconds` | `double` |
| `AddDays` | `double` | `AddMilliseconds` | `double` |
| `AddHours` | `double` | `AddTicks` | `long` |

이들은 모두 **새로운** `DateTime` 또는 `DateTimeOffset`을 돌려주며, 윤년 같은 것을 고려한다. 음수를 넘기면 뺄셈이 된다.

`Add` 메서드는 `TimeSpan`을 더한다. `+` 연산자도 같은 일을 하도록 오버로드되어 있다.

```csharp
TimeSpan ts = TimeSpan.FromMinutes (90);
Console.WriteLine (dt.Add (ts));
Console.WriteLine (dt + ts);          // 위와 같다
```

`DateTime`/`DateTimeOffset`에서 `TimeSpan`을 빼거나, 하나에서 다른 하나를 뺄 수도 있다. 후자의 결과는 `TimeSpan`이다 — 이것이 37.1절에서 말한 세 번째 `TimeSpan` 생성 방법이다.

```csharp
DateTime thisYear = new DateTime (2015, 1, 1);
DateTime nextYear = thisYear.AddYears (1);
TimeSpan oneYear  = nextYear - thisYear;    // 365.00:00:00
```

이 산술이 서머타임·월말·윤년에서 어떻게 어긋나는지는 37.8절에서 전부 판다.

### 포매팅과 파싱 — 요약만

`DateTime`에 `ToString`을 호출하면 짧은 날짜(전부 숫자) 뒤에 긴 시각(초 포함)이 붙은 형태로 서식화된다.

```text
11/11/2019 11:50:30 AM
```

일·월·연 순서, 앞자리 0 사용 여부, 12시간제/24시간제 같은 것은 기본적으로 운영체제의 지역 설정이 결정한다. `DateTimeOffset`의 `ToString`도 같되 오프셋이 함께 나온다.

```text
11/11/2019 11:50:30 AM -06:00
```

`ToShortDateString`/`ToLongDateString`은 날짜 부분만, `ToShortTimeString`/`ToLongTimeString`은 시각 부분만 돌려준다. 이 네 메서드는 실은 네 개의 서로 다른 형식 문자열에 대한 축약이다. `ToString`은 형식 문자열과 공급자를 받는 오버로드가 있어 다양한 옵션과 지역 설정 적용 방식을 제어할 수 있다. **상세는 전부 38장, 특히 38.5절이다.**

정적 `Parse`/`TryParse`와 `ParseExact`/`TryParseExact`가 `ToString`의 반대 동작을 한다. `Try*` 메서드는 `FormatException`을 던지는 대신 `false`를 돌려준다.

> **⚠️ 문화권이 다르면 오파싱된다**
>
> 서식화할 때와 파싱할 때의 문화권 설정이 다르면 `DateTime`과 `DateTimeOffset`이 **잘못 파싱될 수 있다.** `01/02/2019`는 미국 문화권에서 1월 2일이고 영국 문화권에서 2월 1일이다. 예외가 나지 않고 조용히 다른 날짜가 된다.
>
> 문화권 설정을 무시하는 형식 문자열(`"o"` 같은)과 함께 `ToString`을 쓰면 이 문제를 피할 수 있다.
>
> ```csharp
> DateTime dt1 = DateTime.Now;
> string cannotBeMisparsed = dt1.ToString ("o");
> DateTime dt2 = DateTime.Parse (cannotBeMisparsed);
> ```
>
> 기계가 읽을 문자열에는 언제나 불변 문화권과 왕복 형식을 써라. 37.10절과 38.11절에서 다시 다룬다.

### `null`이 될 수 없는 타입에 `null`이 필요할 때

`DateTime`과 `DateTimeOffset`은 구조체이므로 본질적으로 널 가능하지 않다. 널 가능성이 필요하면 두 가지 방법이 있다.

- **널 가능 타입을 쓴다** — `DateTime?` 또는 `DateTimeOffset?`
- **정적 필드 `DateTime.MinValue`나 `DateTimeOffset.MinValue`를 쓴다** — 이 타입들의 기본값이다

**널 가능 타입이 대개 더 낫다.** 컴파일러가 실수를 막아 주기 때문이다(21장). `DateTime.MinValue`는 널 가능 값 타입이 도입된 C# 2.0 이전에 작성된 코드와의 하위 호환을 위해 유용하다.

> **⚠️ `DateTime.MinValue`에 `ToUniversalTime`을 부르면 `MinValue`가 아니게 된다**
>
> `DateTime.MinValue`나 `MaxValue`에 `ToUniversalTime`/`ToLocalTime`을 호출하면, **GMT의 어느 쪽에 있느냐에 따라** 결과가 더 이상 `MinValue`가 아닐 수 있다. 한국(UTC+9)에서 `DateTime.MinValue.ToUniversalTime()`은 9시간을 빼려다 하한을 만나고, 반대로 `MinValue`를 로컬로 바꾸면 `0001-01-01 09:00:00`이 된다.
>
> 그래서 `if (value == DateTime.MinValue)`로 "값 없음"을 검사하는 코드는 중간에 시간대 변환이 한 번만 끼어들어도 조용히 실패한다. GMT 위(영국, 서머타임 밖)에서는 로컬과 UTC가 같으므로 문제 자체가 생기지 않는다 — 영국의 겨울에 대한 보상이라고 생각하자.
>
> **결론: 센티널 값 대신 `DateTime?`을 써라.** `null` 검사는 시간대 변환에 영향받지 않는다.

## 37.3 `DateOnly`와 `TimeOnly` ※.NET 6

### 왜 필요했나

`DateOnly`와 `TimeOnly` 구조체는 .NET 6에서 도입되었다. **날짜만, 또는 시각만 표현하고 싶을 때**를 위한 타입이다.

그전까지 "날짜만"을 표현하는 관행적 방법은 **시각을 0(자정)으로 둔 `DateTime`** 이었다. 이 방식의 문제는 명확하다 — 0이 아닌 시각 성분이 코드 어딘가에서 끼어들면 **동등 비교가 실패한다.**

```csharp
// 전통적인 방식의 함정
DateTime birthday    = new DateTime (1990, 5, 17);          // 00:00:00
DateTime fromInput   = DateTime.Parse ("1990-05-17 00:00:00.001");

Console.WriteLine (birthday == fromInput);   // False — 1밀리초 때문에
```

1밀리초짜리 잔여물은 UI 컨트롤, JSON 왕복, DB 컬럼의 정밀도 차이 등 온갖 경로로 흘러든다. 그리고 그때마다 "생일이 같은지" 판정이 조용히 실패한다.

`DateOnly`는 이 문제를 **타입 수준에서 제거한다.** 시각 성분을 담을 자리가 아예 없으므로 잔여물이 들어올 수 없다.

### `DateOnly`

`DateOnly`는 시각 성분이 없는 `DateTime`이라고 보면 된다. 중요한 것은 **`DateOnly`에는 `DateTimeKind`도 없다**는 점이다. 사실상 언제나 `Unspecified`이며, `Local`이나 `Utc`라는 개념 자체가 없다.

```csharp
DateOnly d = new DateOnly (2025, 3, 9);

Console.WriteLine (d);              // 2025-03-09 (지역 설정에 따름)
Console.WriteLine (d.Year);         // 2025
Console.WriteLine (d.DayOfWeek);    // Sunday
Console.WriteLine (d.DayOfYear);    // 68
Console.WriteLine (d.DayNumber);    // 0001-01-01부터의 일수
```

내부 표현은 **`int` 필드 하나**다. 0001년 1월 1일을 0으로 하는 일련번호를 담으며, 그래서 `sizeof(DateOnly)`는 4다. `DateTime`의 절반이다.

주요 멤버는 다음과 같다.

| 멤버 | 설명 |
|---|---|
| `DayNumber` | 0001-01-01부터의 일수 (`int`) |
| `DateOnly.FromDayNumber(int)` | 일련번호로부터 생성 |
| `DateOnly.FromDateTime(DateTime)` | `DateTime`의 날짜 부분만 취함 |
| `ToDateTime(TimeOnly)` | 시각을 결합해 `DateTime` 생성 |
| `AddDays` / `AddMonths` / `AddYears` | 날짜 산술 (`AddHours`는 없다) |
| `DateOnly.MinValue` / `MaxValue` | 0001-01-01 / 9999-12-31 |
| `Parse` / `TryParse` / `ParseExact` | 문자열 변환 |

`AddHours`나 `AddMinutes`가 없다는 것이 이 타입의 성격을 잘 보여준다. 날짜에 시간을 더한다는 연산은 정의되지 않는다.

### `TimeOnly`

`TimeOnly`는 날짜 성분이 없는 `DateTime`이다. **하루 중의 시각을 담기 위한** 타입이며, 알람 시각이나 영업시간을 기록하는 용도에 적합하다.

```csharp
TimeOnly open  = new TimeOnly (9, 0);
TimeOnly close = new TimeOnly (18, 30);

Console.WriteLine (open);            // 9:00 AM (지역 설정에 따름)
Console.WriteLine (close - open);    // 09:30:00 (TimeSpan)
```

내부는 `long _ticks` 하나이고, 값은 0(자정)부터 하루에서 1틱 모자란 값까지로 **제한된다.** 이것이 `TimeSpan`과의 결정적 차이다 — `TimeSpan.FromHours(30)`은 만들 수 있지만 `new TimeOnly(30, 0)`은 던진다.

`TimeOnly`의 산술은 **하루를 넘으면 되감긴다(wrap around).**

```csharp
TimeOnly t = new TimeOnly (23, 30);
Console.WriteLine (t.AddHours (2));                    // 01:30 — 되감겼다

TimeOnly r = t.Add (TimeSpan.FromHours (26), out int wrappedDays);
Console.WriteLine ($"{r}, {wrappedDays}일 넘어감");     // 01:30, 1일 넘어감
```

`out int wrappedDays` 오버로드가 며칠을 넘어갔는지 알려준다. 되감김을 놓치면 안 되는 계산에서는 이 오버로드를 써라.

`IsBetween`은 **자정을 가로지르는 구간**을 올바르게 처리한다.

```csharp
TimeOnly nightStart = new TimeOnly (22, 0);
TimeOnly nightEnd   = new TimeOnly (6, 0);
TimeOnly now        = new TimeOnly (2, 0);

Console.WriteLine (now.IsBetween (nightStart, nightEnd));   // True
```

직접 `now >= nightStart && now <= nightEnd`로 쓰면 이 경우 `False`가 나온다. 야간 할증, 심야 배치 창(window), 영업시간 판정에서 매번 손으로 짜던 조건문이 메서드 하나로 대체된다.

> **⚠️ `TimeOnly`도 서머타임을 모른다**
>
> `TimeOnly`는 "벽시계 눈금"일 뿐이다. 시계를 앞당기는 날 `02:30`이라는 `TimeOnly`는 만들 수 있지만, 그날 그 시각은 **존재하지 않는다.** `TimeOnly`는 이를 알려 주지 않는다.
>
> `DateOnly` + `TimeOnly` + 시간대 ID의 조합으로 미래 일정을 표현할 때, 실제 실행 시점을 계산하는 단계에서 반드시 `TimeZoneInfo.IsInvalidTime`으로 검증해야 한다(37.7절).

### 다섯 타입 정리

| 타입 | 크기 | 내부 | 날짜 | 시각 | 시간대 정보 | 도입 |
|---|---|---|---|---|---|---|
| `TimeSpan` | 8 | `long` 틱 | 없음 | 간격 (24h 초과·음수 가능) | 없음 | .NET 1.0 |
| `DateTime` | 8 | 62비트 틱 + 2비트 `Kind` | 있음 | 있음 | 3상태 플래그 | .NET 1.0 |
| `DateTimeOffset` | 16 | UTC `DateTime` + `short` 분 | 있음 | 있음 | UTC 오프셋(분) | .NET 2.0 |
| `DateOnly` | 4 | `int` 일련번호 | 있음 | 없음 | 없음 (항상 `Unspecified` 성격) | .NET 6 |
| `TimeOnly` | 8 | `long` 틱 (0~1일 미만) | 없음 | 있음 (하루 안으로 제한) | 없음 | .NET 6 |

> **💡 `DateOnly`를 쓸 자리 목록**
>
> **생일, 계약 시작일·만료일, 청구 기준일, 공휴일, 회계 기간 경계, 유효기간.** 이들의 공통점은 "시간대에 따라 달라지지 않아야 한다"는 것이다. 생일은 사용자가 어느 시간대에서 조회하든 같은 날짜여야 한다.
>
> 이런 값을 `DateTime`으로 저장하고 UTC 변환을 태우면 **날짜가 하루씩 밀리는** 고전적 버그가 나온다. 서울에서 자정에 저장한 `2025-03-09 00:00:00`을 UTC로 바꾸면 `2025-03-08 15:00:00`이 되고, 미국 사용자가 조회하면 3월 8일로 보인다. `DateOnly`는 변환 자체가 불가능하므로 이 버그가 생길 수 없다.

> **📌 도구 생태계의 지원 시점**
>
> `DateOnly`/`TimeOnly`는 .NET 6에 들어왔지만 주변 생태계는 조금 늦었다. `System.Text.Json`은 ※.NET 7부터 이 두 타입을 기본 지원한다. .NET 6에서 JSON으로 주고받으려면 커스텀 컨버터가 필요하다(41.5절). ORM과 데이터베이스 공급자도 버전에 따라 지원 여부가 갈리므로, 도입 전에 스택 전체를 확인해라.

## 37.4 `DateTime`과 시간대(`DateTimeKind`)

### `DateTime`은 시간대 처리에 대해 단순하다

`DateTime`은 시간대를 다루는 방식이 **단순하다(simplistic)**. 내부적으로 두 조각의 정보만 저장한다.

- **62비트 숫자** — 0001년 1월 1일 이후의 틱 수
- **2비트 열거형** — `DateTimeKind` (`Unspecified`, `Local`, `Utc`)

두 `DateTime` 인스턴스를 비교할 때는 **틱 값만 비교되고 `DateTimeKind`는 무시된다.**

```csharp
DateTime dt1 = new DateTime (2000, 1, 1, 10, 20, 30, DateTimeKind.Local);
DateTime dt2 = new DateTime (2000, 1, 1, 10, 20, 30, DateTimeKind.Utc);
Console.WriteLine (dt1 == dt2);      // True

DateTime local = DateTime.Now;
DateTime utc   = local.ToUniversalTime();
Console.WriteLine (local == utc);    // False
```

이 두 줄은 37.2절에서 이미 봤지만, 여기서 다시 보는 이유는 **`Kind`가 비교에 참여하지 않는다는 사실이 `DateTime`의 거의 모든 함정의 뿌리**이기 때문이다.

```text
DateTime의 비교 경로

  dt1 (Kind=Local, ticks=T)          dt2 (Kind=Utc, ticks=T)
        │                                   │
        └───────────┐           ┌───────────┘
                    ↓           ↓
              ┌──────────────────────┐
              │  ticks == ticks ?    │   ← Kind는 여기 들어오지 않는다
              └──────────────────────┘
                        │
                        ↓
                      True

  → "같은 시점인가"가 아니라 "같은 달력 눈금인가"를 답한다.
```

`GetHashCode`도 마찬가지로 틱만 본다. 따라서 `Kind`만 다른 두 값은 `Dictionary`에서 **같은 키**로 취급된다. `HashSet<DateTime>`에 UTC 값과 로컬 값을 섞어 넣으면 예상과 다른 중복 제거가 일어난다(25장).

### `ToUniversalTime`과 `ToLocalTime`의 조건부 동작

인스턴스 메서드 `ToUniversalTime`/`ToLocalTime`은 각각 세계시/지역시로 변환한다. 이들은 컴퓨터의 현재 시간대 설정을 적용하고, `Kind`가 `Utc` 또는 `Local`인 새 `DateTime`을 돌려준다.

**핵심은 이 변환이 조건부라는 것이다.**

- 이미 `Utc`인 `DateTime`에 `ToUniversalTime`을 부르면 **변환이 일어나지 않는다.**
- 이미 `Local`인 `DateTime`에 `ToLocalTime`을 부르면 **변환이 일어나지 않는다.**
- 하지만 `Unspecified`인 `DateTime`에 둘 중 아무거나 부르면 **변환이 일어난다.**

표로 정리하면 이렇다. 로컬 시간대를 UTC+9(서울)로 가정한다.

| 원본 `Kind` | 원본 값 | `.ToUniversalTime()` | `.ToLocalTime()` |
|---|---|---|---|
| `Utc` | 12:00 | 12:00 (`Utc`) — 변환 없음 | 21:00 (`Local`) |
| `Local` | 12:00 | 03:00 (`Utc`) | 12:00 (`Local`) — 변환 없음 |
| `Unspecified` | 12:00 | 03:00 (`Utc`) — **로컬로 간주** | 21:00 (`Local`) — **UTC로 간주** |

마지막 행이 위험하다. **`Unspecified`는 두 메서드에 대해 서로 다르게 해석된다.** `ToUniversalTime`은 `Unspecified`를 "로컬 시각"으로 보고 오프셋을 빼고, `ToLocalTime`은 "UTC 시각"으로 보고 오프셋을 더한다. 같은 값에 두 메서드를 부르면 18시간 차이가 나는 두 결과가 나온다.

> **⚠️ `Unspecified`에 시간대 변환을 걸지 마라**
>
> `Unspecified`는 "이 값이 어느 기준인지 나는 모른다"는 뜻이다. 모르는 값에 변환을 걸면 BCL이 대신 추측하는데, 그 추측이 메서드마다 다르다. 결과는 조용히 틀린 시각이다.
>
> 규칙: **`Unspecified` 값에는 먼저 `SpecifyKind`로 의미를 부여하고, 그다음에 변환한다.** 어느 쪽인지 정말 모른다면 그건 데이터 모델의 결함이지 API의 문제가 아니다.

### `SpecifyKind` — 틱은 그대로, 표지만 바꾼다

정적 `DateTime.SpecifyKind` 메서드로 `Kind`만 다른 `DateTime`을 만들 수 있다.

```csharp
DateTime d   = new DateTime (2015, 12, 12);                  // Unspecified
DateTime utc = DateTime.SpecifyKind (d, DateTimeKind.Utc);
Console.WriteLine (utc);      // 12/12/2015 12:00:00 AM
```

출력값이 같다는 데 주목해라. **`SpecifyKind`는 변환이 아니라 재해석이다.** 틱은 손대지 않고 2비트 표지만 갈아 끼운다.

| 메서드 | 틱을 바꾸나 | `Kind`를 바꾸나 | 의미 |
|---|---|---|---|
| `SpecifyKind` | 아니오 | 예 | "이 벽시계 값은 사실 UTC였다"고 선언 |
| `ToUniversalTime` | 예 (조건부) | 예 (`Utc`로) | 실제 시각을 UTC 기준으로 환산 |
| `ToLocalTime` | 예 (조건부) | 예 (`Local`로) | 실제 시각을 로컬 기준으로 환산 |

이 구별이 데이터 액세스 계층에서 결정적이다. DB에 UTC로 저장한 값을 읽어 오면 `Kind`는 `Unspecified`다. 여기서 필요한 것은 **재해석(`SpecifyKind`)이지 변환이 아니다.**

```csharp
// 데이터 액세스 계층의 올바른 관용구
DateTime raw = (DateTime) reader["CreatedAtUtc"];         // Kind = Unspecified
DateTime utc = DateTime.SpecifyKind (raw, DateTimeKind.Utc);
DateTime forDisplay = utc.ToLocalTime();                  // 이제 변환이 옳다
```

여기서 `SpecifyKind`를 빠뜨리고 바로 `ToLocalTime()`을 부르면 결과가 우연히 같아 보인다 — `Unspecified`를 UTC로 간주하기 때문이다. 하지만 같은 값에 `ToUniversalTime()`을 부르는 다른 코드 경로가 하나라도 있으면 그쪽은 틀린다. 우연히 맞는 코드는 리팩터링 한 번에 무너진다.

### `Kind`는 어디서 사라지는가

`Kind`는 2비트짜리 인메모리 정보다. 그래서 값이 프로세스 밖으로 나가는 거의 모든 경로에서 **소실되거나 왜곡된다.**

| 경로 | `Kind`는 어떻게 되나 |
|---|---|
| `ToString()` (기본 형식) | 사라진다. 오프셋 표기가 없다 |
| `ToString("O")` / `"o"` | 보존된다. `Utc`는 `Z`, `Local`은 `+09:00`, `Unspecified`는 접미사 없음 |
| `DateTime.Parse` (기본) | `Z`나 오프셋이 있으면 **로컬로 변환**되고 `Kind`는 `Local` |
| `DateTime.Parse` + `DateTimeStyles.RoundtripKind` | 문자열의 표기대로 `Kind` 복원 |
| SQL Server `datetime2` 왕복 | 사라진다. 읽으면 `Unspecified` |
| `System.Text.Json` 왕복 | 형식 문자열에 오프셋이 있으면 복원, 없으면 `Unspecified` |
| 이진 직렬화 (`ToBinary`/`FromBinary`) | 보존된다 |

`DateTime.ToBinary()`는 62비트 틱과 2비트 `Kind`를 그대로 담은 `long`을 돌려주고 `DateTime.FromBinary(long)`이 그것을 복원한다. `Ticks`만 저장하면 `Kind`가 날아가지만 `ToBinary`는 살린다.

> **⚠️ `DateTime.Parse`는 기본적으로 `Z`를 로컬로 바꾼다**
>
> ```csharp
> DateTime d = DateTime.Parse ("2025-03-09T12:00:00Z");
> Console.WriteLine (d.Kind);   // Local
> Console.WriteLine (d);        // 2025-03-09 21:00:00 (서울 기준)
> ```
>
> UTC 문자열을 파싱했는데 결과가 로컬 시각이다. 값 자체는 같은 시점이므로 "틀린" 것은 아니지만, UTC를 기대한 코드에서는 예상과 다르다. UTC로 받고 싶으면 `DateTimeStyles.AdjustToUniversal`을, 문자열에 적힌 그대로의 `Kind`를 원하면 `DateTimeStyles.RoundtripKind`를 넘겨라(38.6절).

### 성능 관점

`DateTime` 연산의 비용은 대체로 두 부류다.

- **순수 틱 산술** — `Add*`, `+`, `-`, 비교. `long` 연산 몇 개로 끝난다. 무할당, 인라인 가능.
- **시간대가 개입하는 연산** — `Now`, `ToLocalTime`, `ToUniversalTime`, `IsDaylightSavingTime`. 로컬 시간대 객체를 얻고 조정 규칙을 조회한다. 캐시가 있어도 순수 산술보다 훨씬 비싸다.

핫 루프 안에서 `ToLocalTime()`을 반복 호출하는 코드는 프로파일러에서 눈에 띄게 나타난다. 변환은 경계에서 한 번만 하고, 내부 계산은 UTC 틱으로 하는 것이 성능과 정확성을 동시에 얻는 길이다.

> **📌 `Kind`는 왜 3상태인가 — 하위 호환의 흔적**
>
> `DateTime`은 .NET 1.0에 있었고 `DateTimeKind`는 .NET 2.0에서 추가되었다. 1.0 시절의 `DateTime`에는 시간대 개념이 아예 없었으므로, 2.0이 62비트 틱 위에 남은 2비트에 플래그를 끼워 넣으면서도 **기존 값의 의미를 바꾸지 않아야** 했다. 그 결과가 "기본값은 `Unspecified`이고, `Unspecified`는 비교에서 무시된다"는 어정쩡한 설계다.
>
> `DateTimeOffset`이 .NET 2.0에서 함께 등장한 이유가 여기 있다. `DateTime`을 고칠 수 없으니 새 타입을 만든 것이다. 20년이 지난 지금도 BCL 대부분이 `DateTime` 중심인 이유 역시 같은 하위 호환 때문이다.

## 37.5 `DateTimeOffset`과 시간대

### 내부 구조가 곧 의미론이다

`DateTimeOffset`은 내부적으로 **값이 항상 UTC인 `DateTime` 필드 하나와, UTC 오프셋을 분 단위로 담는 16비트 정수 필드**로 구성된다. 비교는 **(UTC) `DateTime`만** 보고, `Offset`은 주로 포매팅에 쓰인다.

이 한 문장이 `DateTimeOffset`의 모든 동작을 설명한다.

```text
DateTimeOffset dto = 2025-03-09 03:00:00 +09:00

  실제로 메모리에 담긴 것:
  ┌────────────────────────────┬──────────────────┐
  │ _dateTime = 2025-03-08     │ _offsetMinutes   │
  │             18:00:00 (UTC) │      = 540       │
  └────────────────────────────┴──────────────────┘
             ↑                          ↑
      비교·정렬·해시가 보는 값      포매팅과 EqualsExact만 보는 값

  dto.UtcDateTime  → 2025-03-08 18:00:00 (Kind=Utc)
  dto.DateTime     → 2025-03-09 03:00:00 (Kind=Unspecified)  = UTC + offset
  dto.Offset       → 09:00:00
```

### `ToUniversalTime`/`ToLocalTime`은 시점을 바꾸지 않는다

`ToUniversalTime`/`ToLocalTime` 메서드는 **같은 시점을 가리키되 오프셋이 UTC 또는 로컬인** `DateTimeOffset`을 돌려준다. `DateTime`과 달리 이 메서드들은 **밑에 깔린 날짜/시각 값을 건드리지 않고 오프셋만 바꾼다.**

```csharp
DateTimeOffset local = DateTimeOffset.Now;
DateTimeOffset utc   = local.ToUniversalTime();

Console.WriteLine (local.Offset);   // -06:00:00 (중미 기준)
Console.WriteLine (utc.Offset);     // 00:00:00

Console.WriteLine (local == utc);   // True
```

비교에 `Offset`을 포함시키려면 `EqualsExact` 메서드를 써야 한다.

```csharp
Console.WriteLine (local.EqualsExact (utc));   // False
```

| 연산 | `DateTime` | `DateTimeOffset` |
|---|---|---|
| `ToUniversalTime` | 틱을 바꾼다 (조건부) | 틱은 그대로, 오프셋만 `00:00`으로 |
| `ToLocalTime` | 틱을 바꾼다 (조건부) | 틱은 그대로, 오프셋만 로컬로 |
| `==` / `Equals` | 틱 비교 | UTC 시점 비교 |
| `CompareTo` / 정렬 | 틱 비교 | UTC 시점 비교 |
| `GetHashCode` | 틱 기반 | UTC 시점 기반 |
| 오프셋 포함 비교 | 불가능 | `EqualsExact` |

> **💡 `DateTimeOffset`은 동등성 계약을 제대로 지킨다**
>
> 25.4절에서 본 규칙 — "`Equals`가 참이면 `GetHashCode`도 같아야 한다" — 을 `DateTimeOffset`은 UTC 값 기준으로 일관되게 지킨다. `+09:00`의 03:00과 `+00:00`의 18:00(전날)은 `Equals`도 참이고 해시도 같다. 그래서 `Dictionary<DateTimeOffset, T>`나 `HashSet<DateTimeOffset>`에 서로 다른 오프셋의 값을 섞어 넣어도 시점 기준으로 올바르게 동작한다.
>
> `DateTime`은 이 성질을 "달력 눈금 기준"으로 지킨다. 어느 쪽이 옳은지는 도메인이 결정하지만, **집합·사전 키로 쓸 때 직관과 일치하는 쪽은 대개 `DateTimeOffset`이다.**

### 오프셋은 지역이 아니다 — 결정적 한계

`DateTimeOffset`이 담은 것은 **"그 순간 그 지역의 시계가 UTC보다 몇 분 앞서 있었는가"** 뿐이다. 그 지역이 어디인지, 그 오프셋이 표준시인지 서머타임인지는 담기지 않는다.

```csharp
var a = new DateTimeOffset (2025, 6, 1, 12, 0, 0, TimeSpan.FromHours (8));
// 이 값은 싱가포르인가? 퍼스인가? 중국인가? 알 수 없다.
```

이 한계가 실무에서 문제가 되는 자리는 정확히 하나다 — **미래 시각.** 과거 시각은 오프셋이 이미 확정되었으므로 `DateTimeOffset`으로 완전하게 기록된다. 하지만 미래 시각은 그렇지 않다.

```csharp
// 2026년 3월 15일 서울 오전 9시 회의 — 지금 저장한다
var meeting = new DateTimeOffset (2026, 3, 15, 9, 0, 0, TimeSpan.FromHours (9));
```

한국이 그사이 서머타임을 도입하면 이 값은 틀린 시각을 가리키게 된다. 오프셋 `+09:00`이 박혀 있으므로 재해석할 방법이 없다. **미래 일정은 "로컬 벽시계 시각 + 시간대 ID"로 저장해야 한다.** 37.7절과 37.10절에서 이 결론을 완성한다.

> **⚠️ `DateTimeOffset`은 "시간대 인식 타입"이 아니다**
>
> 이름 때문에 `DateTimeOffset`이 시간대를 안다고 오해하기 쉽다. 아니다. 시간대(time zone)는 "오프셋이 시간에 따라 어떻게 변하는가에 대한 규칙 집합"이고, 오프셋은 그 규칙을 특정 순간에 적용한 **결과값 하나**다.
>
> 규칙을 담은 타입은 `TimeZoneInfo`다(37.6절). `DateTimeOffset`은 규칙의 스냅숏만 갖는다.

### `Now`의 오프셋은 서머타임을 반영한다

`DateTimeOffset.Now`가 돌려주는 오프셋은 **그 순간의 실제 오프셋**이다. 서머타임 중이면 표준 오프셋이 아니라 서머타임 오프셋이 들어온다.

```csharp
// 미국 태평양 시간대에서
// 1월:  DateTimeOffset.Now.Offset → -08:00 (PST)
// 7월:  DateTimeOffset.Now.Offset → -07:00 (PDT)
```

`TimeZoneInfo.Local.BaseUtcOffset`은 언제나 `-08:00`을 돌려준다. **`BaseUtcOffset`은 표준시 오프셋이고, `DateTimeOffset.Offset`은 실효 오프셋이다.** 둘을 혼동하면 여름 반년 동안 한 시간 어긋난다.

### 산술은 UTC 값에 대해서만 일어난다

`DateTimeOffset`의 `Add*` 메서드는 내부 UTC 값에 시간을 더하고 **오프셋은 그대로 둔다.** 절대 시간 기준의 산술이라는 뜻이고, 대부분의 경우 이것이 원하는 동작이다.

```csharp
var t = new DateTimeOffset (2025, 3, 8, 12, 0, 0, TimeSpan.FromHours (-8));
var t2 = t.AddDays (1);

Console.WriteLine (t2);   // 2025-03-09 12:00:00 -08:00
```

미국 태평양 시간대는 2025년 3월 9일에 서머타임이 시작된다. 즉 그날 실제 벽시계는 `-07:00`으로 바뀌어 있고, 현지인이 보는 시각은 13:00이다. 그런데 `AddDays(1)`의 결과는 오프셋 `-08:00`을 그대로 달고 있다. **정확히 24시간 뒤라는 점에서는 맞고, 그 지역의 벽시계 표현으로서는 틀렸다.**

> **⚠️ `DateTimeOffset` 산술은 오프셋을 갱신하지 않는다**
>
> `AddDays`, `AddHours`, `+ TimeSpan` 모두 오프셋을 유지한다. 서머타임 경계를 넘어가면 결과의 오프셋이 그 시점의 실제 오프셋과 달라진다. 시점 자체는 정확하지만, 그 값을 사용자에게 "3월 9일 12시"라고 보여주면 틀린 정보가 된다.
>
> 벽시계 기준으로 하루 뒤를 계산하려면 `TimeZoneInfo`를 거쳐야 한다. 37.8절에서 올바른 관용구를 보인다.

## 37.6 `TimeZoneInfo` — 변환, 조회, IANA vs Windows ID

### 레거시 `TimeZone`과의 관계

시간대를 다루는 타입은 역사적으로 둘이다. `System.TimeZone`이 먼저 있었고, `System.TimeZoneInfo`가 그것을 대체했다.

`TimeZone`은 **로컬 시간대 하나만** 다룰 수 있다. 정적 `TimeZone.CurrentTimeZone`이 `TimeZone` 인스턴스를 돌려준다.

```csharp
TimeZone zone = TimeZone.CurrentTimeZone;
Console.WriteLine (zone.StandardName);   // Pacific Standard Time
Console.WriteLine (zone.DaylightName);   // Pacific Daylight Time
```

`GetDaylightChanges` 메서드는 주어진 연도의 서머타임 정보를 돌려준다.

```csharp
DaylightTime day = zone.GetDaylightChanges (2019);
Console.WriteLine (day.Start.ToString ("M"));   // 10 March
Console.WriteLine (day.End.ToString ("M"));     // 03 November
Console.WriteLine (day.Delta);                  // 01:00:00
```

`TimeZoneInfo`는 이 한계를 전부 넘어선다.

| 항목 | `TimeZone` (레거시) | `TimeZoneInfo` |
|---|---|---|
| 다룰 수 있는 시간대 | 로컬 하나 | 시스템에 등록된 전부 + 커스텀 |
| 조정 규칙 | 지정 연도의 시작/종료만 | 연도 범위별 규칙 컬렉션 전체 |
| 임의 시간대 간 변환 | 불가 | `ConvertTime` |
| 모호한 시각 처리 | 없음 | `IsAmbiguousTime`, `GetAmbiguousTimeOffsets` |
| 존재하지 않는 시각 처리 | 없음 | `IsInvalidTime` |
| 직렬화 | 없음 | `ToSerializedString` / `FromSerializedString` |
| 커스텀 시간대 생성 | 없음 | `CreateCustomTimeZone` |

> **💡 새 코드에서 `TimeZone`을 쓸 이유는 없다**
>
> `TimeZone`은 `TimeZoneInfo`로 완전히 대체되었다. 위 표에서 `TimeZone`이 이길 수 있는 칸이 하나도 없다. 오래된 코드베이스에서 `TimeZone.CurrentTimeZone`을 만나면 `TimeZoneInfo.Local`로 바꾸는 것이 거의 언제나 옳다.
>
> 다만 `GetDaylightChanges(year)`에 정확히 대응하는 `TimeZoneInfo` 메서드는 없다. 같은 정보를 얻으려면 `GetAdjustmentRules`가 돌려주는 선언적 규칙을 해석해야 한다(37.7절). 이것이 `TimeZoneInfo`가 더 어려워 보이는 유일한 지점이다.

### `TimeZoneInfo.Local`과 기본 프로퍼티

정적 `TimeZoneInfo.Local` 프로퍼티는 현재 로컬 설정에 기반한 `TimeZoneInfo` 객체를 돌려준다. 캘리포니아에서 실행하면 다음과 같다.

```csharp
TimeZoneInfo zone = TimeZoneInfo.Local;
Console.WriteLine (zone.StandardName);   // Pacific Standard Time
Console.WriteLine (zone.DaylightName);   // Pacific Daylight Time
```

`IsDaylightSavingTime`과 `GetUtcOffset` 메서드는 다음처럼 동작한다.

```csharp
DateTime dt1 = new DateTime (2019, 1, 1);   // DateTimeOffset도 받는다
DateTime dt2 = new DateTime (2019, 6, 1);

Console.WriteLine (zone.IsDaylightSavingTime (dt1));   // False (1월 — 표준시)
Console.WriteLine (zone.IsDaylightSavingTime (dt2));   // True  (6월 — 서머타임)
Console.WriteLine (zone.GetUtcOffset (dt1));           // -08:00:00
Console.WriteLine (zone.GetUtcOffset (dt2));           // -07:00:00
```

두 메서드의 답이 서로를 확인해 준다. 1월은 서머타임이 아니므로 오프셋이 표준시 `-08:00`이고, 6월은 서머타임이므로 한 시간 앞당겨진 `-07:00`이다.

### 임의 시간대 얻기 — `FindSystemTimeZoneById`

세계의 어떤 시간대든 `FindSystemTimeZoneById`에 시간대 ID를 넘겨 얻을 수 있다. 곧 분명해질 이유로 서호주(Western Australia)로 바꿔 본다.

```csharp
TimeZoneInfo wa = TimeZoneInfo.FindSystemTimeZoneById
                    ("W. Australia Standard Time");

Console.WriteLine (wa.Id);                          // W. Australia Standard Time
Console.WriteLine (wa.DisplayName);                 // (GMT+08:00) Perth
Console.WriteLine (wa.BaseUtcOffset);               // 08:00:00
Console.WriteLine (wa.SupportsDaylightSavingTime);  // True
```

`Id` 프로퍼티는 `FindSystemTimeZoneById`에 넘긴 값과 일치한다. 정적 `GetSystemTimeZones` 메서드는 세계의 모든 시간대를 돌려주므로, 유효한 시간대 ID 문자열 전체를 다음처럼 나열할 수 있다.

```csharp
foreach (TimeZoneInfo z in TimeZoneInfo.GetSystemTimeZones())
    Console.WriteLine (z.Id);
```

> **⚠️ `FindSystemTimeZoneById`는 예외를 던진다 — 컨테이너에서 특히**
>
> 해당 ID의 시간대를 찾지 못하면 `TimeZoneNotFoundException`을, 시간대 데이터가 손상되었으면 `InvalidTimeZoneException`을 던진다. 리눅스 컨테이너에서 이것이 자주 터지는데, `alpine`이나 슬림 베이스 이미지에는 **tzdata 패키지가 아예 없기 때문**이다. `TimeZoneInfo.Local`은 UTC로 폴백되어 동작하는 것처럼 보이지만, 특정 ID를 조회하는 순간 던진다.
>
> 대응은 세 가지다. (1) 이미지에 tzdata를 설치한다. (2) `Microsoft.Extensions.TimeZoneInfo` 계열 대신 앱과 함께 배포되는 tzdata 패키지를 참조한다. (3) ※.NET 8부터는 `TimeZoneInfo.TryFindSystemTimeZoneById`로 예외 없이 실패를 감지한다.
>
> 이 문제는 로컬 Windows 개발 환경에서는 절대 재현되지 않는다. 배포 후 처음 터지는 종류의 버그다.

> **📌 커스텀 시간대와 직렬화**
>
> `TimeZoneInfo.CreateCustomTimeZone`으로 커스텀 시간대를 만들 수 있다. `TimeZoneInfo`는 불변이므로 관련 데이터를 전부 메서드 인자로 넘겨야 한다. 미리 정의된 시간대든 커스텀 시간대든 `ToSerializedString`을 호출하면 (반쯤) 사람이 읽을 수 있는 문자열로 직렬화되고, `TimeZoneInfo.FromSerializedString`으로 역직렬화된다.
>
> 이 기능의 실용적 용도 하나 — **서버와 클라이언트의 tzdata 버전이 다를 때** 서버가 쓰는 규칙을 직렬화해 함께 보내면 양쪽이 같은 규칙으로 계산한다. 다만 문자열이 길고 버전 간 형식 호환이 보장되지 않으므로 영구 저장에는 부적합하다.

### 시간대 간 변환

정적 `ConvertTime` 메서드는 `DateTime`이나 `DateTimeOffset`을 한 시간대에서 다른 시간대로 변환한다. 대상 `TimeZoneInfo`만 넘길 수도 있고, 원본과 대상 `TimeZoneInfo`를 모두 넘길 수도 있다. `ConvertTimeFromUtc`와 `ConvertTimeToUtc` 메서드로 UTC와 직접 변환할 수도 있다.

```csharp
TimeZoneInfo seoul = TimeZoneInfo.FindSystemTimeZoneById ("Korea Standard Time");
TimeZoneInfo perth = TimeZoneInfo.FindSystemTimeZoneById ("W. Australia Standard Time");

DateTime seoulTime = new DateTime (2025, 6, 1, 14, 0, 0, DateTimeKind.Unspecified);
DateTime perthTime = TimeZoneInfo.ConvertTime (seoulTime, seoul, perth);
Console.WriteLine (perthTime);      // 2025-06-01 13:00:00

// UTC와 직접
DateTime utc = TimeZoneInfo.ConvertTimeToUtc (seoulTime, seoul);
DateTime back = TimeZoneInfo.ConvertTimeFromUtc (utc, seoul);
```

`ConvertTimeBySystemTimeZoneId` 오버로드는 `TimeZoneInfo` 객체 대신 ID 문자열을 직접 받는다.

> **⚠️ `ConvertTimeToUtc`는 `Kind`와 시간대가 모순되면 던진다**
>
> `ConvertTimeToUtc(dateTime, sourceZone)`에서 `dateTime.Kind`가 `Utc`인데 `sourceZone`이 UTC가 아니거나, `Kind`가 `Local`인데 `sourceZone`이 `TimeZoneInfo.Local`이 아니면 `ArgumentException`이 던져진다. 또한 `dateTime`이 해당 시간대에서 **존재하지 않는 시각**이어도 `ArgumentException`이 던져진다(37.7절).
>
> 따라서 시간대 변환에 넘기는 `DateTime`은 대개 `Kind`가 `Unspecified`여야 한다. "이 벽시계 값을 저 시간대의 값으로 해석하라"는 요청에 `Kind` 표지는 방해만 된다.

### 주요 멤버 정리

| 멤버 | 종류 | 설명 |
|---|---|---|
| `Local` | 정적 프로퍼티 | 로컬 시간대 |
| `Utc` | 정적 프로퍼티 | UTC 시간대 |

| `ClearCachedData()` | 정적 메서드 | 캐시 무효화 (OS 시간대 변경 후) |
| `Id` | 프로퍼티 | 조회 키가 되는 문자열 |
| `DisplayName` / `StandardName` / `DaylightName` | 프로퍼티 | 표시용 이름들 |

| `ConvertTime` / `ConvertTimeFromUtc` / `ConvertTimeToUtc` | 정적 메서드 | 변환 |
| `CreateCustomTimeZone` | 정적 메서드 | 커스텀 시간대 생성 |
| `ToSerializedString()` / `FromSerializedString(string)` | 메서드 / 정적 메서드 | 문자열 왕복 |

### Windows ID vs IANA ID

시간대 ID 체계는 세상에 둘 있다.

- **Windows ID** — `"Korea Standard Time"`, `"W. Australia Standard Time"`. 영어 문장처럼 생겼고 Windows 레지스트리가 원본이다.
- **IANA ID** (tz database, Olson ID) — `"Asia/Seoul"`, `"Australia/Perth"`. `대륙/도시` 형태이고 리눅스·macOS·자바·자바스크립트·PostgreSQL 등 사실상 나머지 세계 전부가 쓴다.

| 지역 | Windows ID | IANA ID |
|---|---|---|
| 서울 | `Korea Standard Time` | `Asia/Seoul` |
| 퍼스 | `W. Australia Standard Time` | `Australia/Perth` |
| 로스앤젤레스 | `Pacific Standard Time` | `America/Los_Angeles` |
| 런던 | `GMT Standard Time` | `Europe/London` |
| 뉴욕 | `Eastern Standard Time` | `America/New_York` |
| UTC | `UTC` | `Etc/UTC` |

.NET Core 시절 이것은 실질적인 이식성 장벽이었다. Windows에서 `"Korea Standard Time"`으로 작성한 코드가 리눅스에서 `TimeZoneNotFoundException`으로 죽었다.

**※.NET 6부터 `FindSystemTimeZoneById`는 두 체계를 모두 받아들인다.** 플랫폼이 무엇이든, ID가 어느 체계든 내부적으로 변환해서 조회한다. 변환에는 CLDR(유니코드 공통 로케일 데이터 저장소)의 매핑 표가 쓰인다.

.NET 6은 명시적 변환 API도 함께 추가했다.

```csharp
// IANA → Windows
if (TimeZoneInfo.TryConvertIanaIdToWindowsId ("Asia/Seoul", out string? winId))
    Console.WriteLine (winId);        // Korea Standard Time

// Windows → IANA
if (TimeZoneInfo.TryConvertWindowsIdToIanaId ("Korea Standard Time", out string? ianaId))
    Console.WriteLine (ianaId);       // Asia/Seoul

// 지금 이 TimeZoneInfo의 Id가 어느 체계인가
Console.WriteLine (TimeZoneInfo.Local.HasIanaId);
```

> **⚠️ 양방향 매핑은 1:1이 아니다**
>
> Windows ID 하나가 여러 IANA ID에 대응한다. `"Eastern Standard Time"`은 `America/New_York`, `America/Toronto`, `America/Detroit` 등 수십 개를 포괄한다. `TryConvertWindowsIdToIanaId`는 그중 CLDR이 지정한 **대표 지역** 하나만 돌려준다.
>
> 따라서 **Windows ID → IANA ID → Windows ID 왕복은 안전하지만, IANA ID → Windows ID → IANA ID 왕복은 정보를 잃는다.** `America/Toronto`를 왕복시키면 `America/New_York`이 되어 돌아온다. 두 지역의 현재 규칙이 같으므로 당장은 문제가 없지만, 과거 데이터를 다루거나 두 지역의 규칙이 갈라지면 틀린다.
>
> **저장은 IANA ID로 해라.** 더 세밀하고, 더 이식성 있고, .NET 밖의 모든 시스템이 이해한다.

> **📌 .NET 5부터 문자열 처리의 기반이 ICU로 바뀌었다**
>
> .NET 5는 Windows에서도 문화권·정렬·시간대 데이터의 기본 원본을 OS의 NLS에서 ICU(International Components for Unicode)로 전환했다. 이 변화 덕분에 플랫폼 간 동작이 통일되었고, .NET 6의 IANA/Windows ID 양방향 수용도 여기에 얹혀 있다. 문화권 관련 파장은 35장과 38장에서 다룬다.

## 37.7 서머타임(DST)이 만드는 함정 — 존재하지 않는 시각, 중복되는 시각

### 시계가 튈 때 무슨 일이 일어나는가

서머타임 전환은 벽시계에 두 종류의 이상 구간을 만든다.

```text
봄 — 시계를 앞당긴다 (미국 태평양, 2025-03-09)

  01:58  01:59  [02:00 ────── 02:59]  03:00  03:01
                 └───────────────────┘
                  존재하지 않는 시각
                  IsInvalidTime → true

  이 구간의 벽시계 시각은 그날 한 번도 나타나지 않는다.
  02:30을 예약한 배치 작업은 실행되지 않거나 두 번 실행된다.


가을 — 시계를 되돌린다 (미국 태평양, 2025-11-02)

              ┌── 첫 번째 01:00~01:59 (PDT, -07:00)
  00:59 ─────┤
              └── 두 번째 01:00~01:59 (PST, -08:00) ── 02:00

  이 구간의 벽시계 시각은 그날 두 번 나타난다.
  IsAmbiguousTime → true
  GetAmbiguousTimeOffsets → [ -07:00, -08:00 ]

  로컬 시각만 보고 순서를 판정하는 코드는 여기서 깨진다.
```

이 두 구간을 판정하기 위해 `TimeZoneInfo`는 다음 메서드들을 제공한다.

- **`IsInvalidTime`** — `DateTime`이 시계를 앞당길 때 건너뛴 시간(또는 델타) 안에 있으면 `true`를 돌려준다.
- **`IsAmbiguousTime`** — `DateTime`이나 `DateTimeOffset`이 시계를 되돌릴 때 반복되는 시간(또는 델타) 안에 있으면 `true`를 돌려준다.
- **`GetAmbiguousTimeOffsets`** — 모호한 `DateTime`이나 `DateTimeOffset`에 대해 유효한 오프셋 선택지들을 `TimeSpan` 배열로 돌려준다.

```csharp
TimeZoneInfo pacific = TimeZoneInfo.FindSystemTimeZoneById ("America/Los_Angeles");

DateTime skipped   = new DateTime (2025, 3,  9, 2, 30, 0);
DateTime repeated  = new DateTime (2025, 11, 2, 1, 30, 0);

Console.WriteLine (pacific.IsInvalidTime   (skipped));    // True
Console.WriteLine (pacific.IsAmbiguousTime (repeated));   // True

foreach (TimeSpan off in pacific.GetAmbiguousTimeOffsets (repeated))
    Console.WriteLine (off);        // -07:00:00 그리고 -08:00:00
```

> **⚠️ 사용자 입력을 받는 모든 시각 필드에 이 검증이 필요하다**
>
> "매일 새벽 2시 30분에 백업"이라는 설정을 사용자가 저장했다고 하자. 대부분의 날에는 잘 돈다. 그리고 1년에 하루, 그 시각이 존재하지 않는 날 조용히 건너뛰거나, 1년에 하루, 그 시각이 두 번 있는 날 두 번 돈다.
>
> 두 번 도는 쪽이 더 위험하다. 멱등하지 않은 작업 — 정산, 청구, 알림 발송 — 이 중복 실행된다. 스케줄러를 직접 만든다면 **직전 실행 시각을 UTC로 기록하고 UTC 기준으로 다음 실행 시각을 계산**하는 것이 유일하게 안전한 설계다.

> **⚠️ 존재하지 않는 시각을 변환하면 예외가 난다**
>
> `TimeZoneInfo.ConvertTimeToUtc`에 `IsInvalidTime`이 참인 `DateTime`을 넘기면 `ArgumentException`이 던져진다. 반면 모호한(`IsAmbiguousTime`) 시각은 예외 없이 **표준시 오프셋을 선택해서** 변환된다. 즉 존재하지 않는 시각은 시끄럽게 실패하고, 중복되는 시각은 조용히 한쪽을 고른다.
>
> 조용한 쪽이 더 무섭다. 사용자가 의도한 것이 첫 번째 01:30이었는지 두 번째 01:30이었는지는 아무도 모른 채로 지나간다.

### 서머타임 규칙 읽기 — `GetAdjustmentRules`

`TimeZoneInfo`에서 서머타임의 시작과 끝을 나타내는 단순한 날짜를 얻을 수는 없다. 대신 `GetAdjustmentRules`를 호출해야 하고, 이것은 **모든 연도에 적용되는 모든 서머타임 규칙의 선언적 요약**을 돌려준다. 각 규칙은 그 규칙이 유효한 날짜 범위를 나타내는 `DateStart`와 `DateEnd`를 갖는다.

```csharp
foreach (TimeZoneInfo.AdjustmentRule rule in wa.GetAdjustmentRules())
    Console.WriteLine ("Rule: applies from " + rule.DateStart +
                       " to " + rule.DateEnd);
```

서호주는 2006년에 시즌 중간에 서머타임을 처음 도입했고(그리고 2009년에 폐지했다), 그래서 첫해에 대한 특별 규칙이 필요했다. 결과적으로 규칙이 두 개다.

```text
Rule: applies from 1/01/2006 12:00:00 AM to 31/12/2006 12:00:00 AM
Rule: applies from 1/01/2007 12:00:00 AM to 31/12/2009 12:00:00 AM
```

각 `AdjustmentRule`은 `TimeSpan` 타입의 `DaylightDelta` 프로퍼티(거의 모든 경우 한 시간이다)와, `DaylightTransitionStart`·`DaylightTransitionEnd` 프로퍼티를 갖는다. 뒤의 둘은 `TimeZoneInfo.TransitionTime` 타입이고, 다음 프로퍼티들을 갖는다.

```csharp
public bool      IsFixedDateRule { get; }
public DayOfWeek DayOfWeek       { get; }
public int       Week            { get; }
public int       Day             { get; }
public int       Month           { get; }
public DateTime  TimeOfDay       { get; }
```

### `TransitionTime` 해석 규칙 세 가지

전환 시각은 **고정 날짜와 부동 날짜를 모두 표현해야 하기 때문에** 다소 복잡하다. 부동 날짜의 예가 "3월의 마지막 일요일"이다. 전환 시각을 해석하는 규칙은 다음과 같다.

1. **종료 전환에 대해** `IsFixedDateRule`이 `true`이고, `Day`가 1, `Month`가 1, `TimeOfDay`가 `DateTime.MinValue`이면, **그해에는 서머타임의 종료가 없다.** (이는 남반구에서, 그 지역에 서머타임이 처음 도입될 때만 일어날 수 있다.)
2. 그렇지 않고 `IsFixedDateRule`이 `true`이면, **`Month`, `Day`, `TimeOfDay` 프로퍼티**가 조정 규칙의 시작 또는 끝을 결정한다.
3. 그렇지 않고 `IsFixedDateRule`이 `false`이면, **`Month`, `DayOfWeek`, `Week`, `TimeOfDay` 프로퍼티**가 조정 규칙의 시작 또는 끝을 결정한다.

마지막 경우에서 **`Week`는 그달의 몇 번째 주인지를 뜻하며, `5`는 "마지막 주"를 의미한다.**

| 규칙 | 조건 | 해석에 쓰는 프로퍼티 |
|---|---|---|
| 1 | 종료 전환 + `IsFixedDateRule` + `Day==1` + `Month==1` + `TimeOfDay==MinValue` | 그해 종료 없음 |
| 2 | `IsFixedDateRule == true` | `Month`, `Day`, `TimeOfDay` |
| 3 | `IsFixedDateRule == false` | `Month`, `DayOfWeek`, `Week`, `TimeOfDay` (`Week==5`는 마지막 주) |

앞의 `wa` 시간대에 대해 조정 규칙을 열거하면 이 규칙들을 눈으로 확인할 수 있다.

```csharp
foreach (TimeZoneInfo.AdjustmentRule rule in wa.GetAdjustmentRules())
{
    Console.WriteLine ("Rule: applies from " + rule.DateStart +
                       " to " + rule.DateEnd);

    Console.WriteLine ("   Delta: " + rule.DaylightDelta);

    Console.WriteLine ("   Start: " + FormatTransitionTime
                                      (rule.DaylightTransitionStart, false));

    Console.WriteLine ("   End:   " + FormatTransitionTime
                                      (rule.DaylightTransitionEnd, true));
    Console.WriteLine();
}
```

`FormatTransitionTime`에서 방금 설명한 규칙들을 그대로 구현한다.

```csharp
static string FormatTransitionTime (TimeZoneInfo.TransitionTime tt,
                                    bool endTime)
{
    // 규칙 1 — 그해에는 서머타임 종료가 없다
    if (endTime && tt.IsFixedDateRule
                && tt.Day == 1 && tt.Month == 1
                && tt.TimeOfDay == DateTime.MinValue)
        return "-";

    string s;
    if (tt.IsFixedDateRule)
        s = tt.Day.ToString();                          // 규칙 2
    else
        s = "The " +                                    // 규칙 3
            "first second third fourth last".Split() [tt.Week - 1] +
            " " + tt.DayOfWeek + " in";

    return s + " " + DateTimeFormatInfo.CurrentInfo.MonthNames [tt.Month-1]
             + " at " + tt.TimeOfDay.TimeOfDay;
}
```

`"first second third fourth last".Split()[tt.Week - 1]`이 `Week == 5`를 `"last"`로 매핑하는 부분이다. 규칙 3의 "5는 마지막 주"가 여기서 구현된다.

> **⚠️ `Week == 5`를 "다섯째 주"로 읽으면 틀린다**
>
> 어떤 달에는 특정 요일이 다섯 번 있고 어떤 달에는 네 번 있다. `Week == 5`를 문자 그대로 "5번째"로 해석하면 네 번뿐인 달에서 날짜를 못 찾는다. tz database의 관례를 따라 **`5`는 언제나 "그달의 마지막 해당 요일"** 이다.
>
> 같은 함정이 역방향에도 있다. "3월의 마지막 일요일"을 직접 계산할 때 `AddDays`로 5주를 더하면 4월로 넘어간다. 월말에서 거꾸로 찾는 것이 옳다.

> **📌 `TransitionTime.TimeOfDay`는 `DateTime`인데 날짜 부분을 무시한다**
>
> `TimeOfDay`의 타입이 `TimeSpan`이나 `TimeOnly`가 아니라 `DateTime`이다. `TimeOnly`가 .NET 6에나 등장했기 때문이고, 이 API는 .NET 3.5 시절 설계다. 날짜 부분은 무의미하며 시각 부분만 읽어야 한다 — 위 코드에서 `tt.TimeOfDay.TimeOfDay`라고 두 번 쓴 이유다.

### 서머타임과 `DateTime` — 세 가지 규칙

`DateTimeOffset`이나 UTC `DateTime`을 쓰면 동등 비교가 서머타임의 영향을 받지 않는다. 하지만 로컬 `DateTime`을 쓰면 서머타임이 문제를 만든다. 규칙은 이렇게 요약된다.

1. **서머타임은 로컬 시각에 영향을 주지만 UTC 시각에는 영향을 주지 않는다.**
2. **시계가 되돌아갈 때, "시간이 앞으로 흐른다"에 의존하는 비교는 로컬 `DateTime`을 쓰는 경우에 (그리고 오직 그 경우에만) 깨진다.**
3. **UTC와 로컬 시각 사이의 왕복은 (같은 컴퓨터에서) 언제나 안정적이다** — 시계가 되돌아가는 중이라도.

`IsDaylightSavingTime`은 주어진 로컬 `DateTime`이 서머타임의 적용을 받는지 알려준다. UTC 시각은 언제나 `false`를 돌려준다.

```csharp
Console.Write (DateTime.Now.IsDaylightSavingTime());      // True 또는 False
Console.Write (DateTime.UtcNow.IsDaylightSavingTime());   // 언제나 False
```

`dto`가 `DateTimeOffset`이라면 다음 식이 같은 일을 한다.

```csharp
dto.LocalDateTime.IsDaylightSavingTime()
```

서머타임의 **종료**는 로컬 시각을 쓰는 알고리즘에 특별한 문제를 만든다. 시계가 되돌아갈 때 같은 시간(더 정확히는 `Delta`)이 반복되기 때문이다.

> **⚠️ 두 `DateTime`을 비교하기 전에 각각 `ToUniversalTime`을 불러라 — 단, 조건이 있다**
>
> 아무 두 `DateTime`이든 **각각에 대해 먼저 `ToUniversalTime`을 호출하면** 안정적으로 비교할 수 있다. 이 전략은 **정확히 하나가 `DateTimeKind.Unspecified`일 때 (그리고 그때만) 실패한다.**
>
> ```csharp
> // 안전한 비교
> if (a.ToUniversalTime() < b.ToUniversalTime()) { ... }
> ```
>
> 왜 실패하는가. 37.4절의 표에서 봤듯 `ToUniversalTime`은 `Unspecified`를 "로컬"로 간주한다. 둘 다 `Unspecified`면 같은 가정이 적용되므로 상대 비교는 유지된다. 둘 다 `Kind`가 명확해도 문제없다. 하지만 **하나는 `Utc`이고 하나는 `Unspecified`인 경우**, 전자는 그대로 두고 후자에만 로컬 오프셋을 빼므로 오프셋만큼 어긋난 비교가 된다.
>
> 이 실패 가능성이 `DateTimeOffset`을 선호할 또 하나의 이유다. `DateTimeOffset`에는 `Unspecified`라는 상태가 없다.

### 미래 일정은 UTC로 저장하면 안 된다

여기까지의 내용에서 실무적으로 가장 중요한 결론이 나온다.

**"매주 화요일 오전 9시(서울)" 같은 미래 일정을 UTC로 변환해 저장하면 안 된다.**

이유는 단순하다. UTC로 변환하는 순간 **그 변환에 쓰인 서머타임 규칙이 값에 구워진다.** 그런데 시간대 규칙은 **정치적 결정으로 바뀐다.** 실제로 최근 몇 년만 봐도 규칙 변경이 계속 있었다 — 서머타임을 폐지한 나라, 도입한 나라, 전환 날짜를 옮긴 나라가 매년 나온다. tz database는 1년에 여러 번 갱신된다.

```text
잘못된 저장
  "매주 화 09:00 (Asia/Seoul)"  ──변환──→  "매주 화 00:00 UTC"  ──저장
                                                   │
                          한국이 서머타임을 도입    │
                                                   ↓
                                    실제 실행 시각: 현지 10:00 (틀림)

올바른 저장
  "매주 화 09:00" + "Asia/Seoul"  ──저장
                                     │
                    실행 직전에 변환  │  (그 시점의 최신 tzdata 사용)
                                     ↓
                          그때의 규칙으로 계산한 정확한 UTC 시각
```

| 값의 성격 | 저장 형태 | 이유 |
|---|---|---|
| 과거에 일어난 일 | UTC 또는 `DateTimeOffset` | 오프셋이 이미 확정됨. 규칙이 바뀌어도 사실은 안 바뀜 |
| 미래의 절대 시점 (로켓 발사 등) | UTC | 벽시계와 무관하게 그 순간이 중요 |
| 미래의 벽시계 약속 (회의, 알람) | 로컬 시각 + IANA 시간대 ID | 규칙이 바뀌면 재계산되어야 함 |
| 반복 일정 | 로컬 시각 + 시간대 ID + 반복 규칙 | 위와 같음 |
| 날짜만 (생일, 만기일) | `DateOnly` | 시간대 변환 자체가 부적절 |

> **💡 캘린더 애플리케이션은 전부 이 방식을 쓴다**
>
> iCalendar(RFC 5545) 표준의 `DTSTART;TZID=Asia/Seoul:20250311T090000`이 정확히 이 구조다 — 벽시계 시각과 시간대 ID를 함께 저장하고, UTC로 굳히지 않는다. 구글 캘린더, 아웃룩 모두 같다.
>
> 반대로 "언제나 UTC로 저장하라"는 조언은 **과거 이벤트에 대해서만** 옳다. 이 조언을 미래 일정에 적용하면 시간대 규칙이 바뀔 때마다 데이터를 마이그레이션해야 한다.

## 37.8 날짜 산술의 함정 — 윤년, 월말, 윤초

### `Add*` 메서드는 윤년을 안다. 그것이 문제의 시작이다

37.2절에서 본 `AddYears`·`AddMonths`·`AddDays` 등은 모두 새 값을 돌려주며 **윤년 같은 것을 고려한다.** 이 "고려한다"가 정확히 무엇을 뜻하는지가 이 절의 주제다.

달력 산술에는 물리적으로 옳은 답이 없는 질문이 존재한다. **"1월 31일의 한 달 뒤는 언제인가?"** 2월 31일은 없다. BCL은 이 질문에 **클램핑(clamping)** 으로 답한다.

```csharp
DateTime jan31 = new DateTime (2025, 1, 31);
Console.WriteLine (jan31.AddMonths (1));    // 2025-02-28  ← 잘렸다
Console.WriteLine (jan31.AddMonths (2));    // 2025-03-31  ← 다시 31일
```

`AddMonths`는 결과 월의 마지막 날을 넘어가면 **그 달의 마지막 날로 자른다.** 2월로 갈 때 잘리고, 3월로 갈 때는 원래 값이 살아 있으므로 31일이 나온다. 원본으로부터 계산하기 때문이다.

`AddYears`도 같은 규칙을 쓴다. 2월 29일에서만 드러난다.

```csharp
DateTime leap = new DateTime (2024, 2, 29);
Console.WriteLine (leap.AddYears (1));      // 2025-02-28
Console.WriteLine (leap.AddYears (4));      // 2028-02-29
```

### 클램핑이 만드는 비가환성

클램핑의 진짜 문제는 **연산이 가환적이지도, 결합적이지도, 가역적이지도 않다**는 것이다.

```csharp
DateTime d = new DateTime (2025, 1, 31);

Console.WriteLine (d.AddMonths (1).AddDays (1));   // 2025-03-01
Console.WriteLine (d.AddDays (1).AddMonths (1));   // 2025-03-01
```

이 경우는 우연히 같지만, 다른 값에서는 갈라진다.

```csharp
DateTime e = new DateTime (2025, 1, 30);

Console.WriteLine (e.AddMonths (1).AddDays (1));   // 2025-03-01  (2/28 + 1)
Console.WriteLine (e.AddDays (1).AddMonths (1));   // 2025-02-28  (1/31 → 2/28)
```

**연산 순서를 바꾸었을 뿐인데 하루 이상 벌어졌다.** 그리고 뺄셈으로 되돌아가지 않는다.

```csharp
Console.WriteLine (jan31.AddMonths (1).AddMonths (-1));   // 2025-01-28
```

`+1개월` 후 `-1개월`이 원래 값이 아니다. 1월 31일이 1월 28일이 되어 돌아온다.

| 표현식 | 결과 | 비고 |
|---|---|---|
| `2025-01-31.AddMonths(1)` | `2025-02-28` | 월말 클램핑 |
| `2025-01-31.AddMonths(1).AddMonths(-1)` | `2025-01-28` | 가역적이지 않음 |
| `2025-01-30.AddMonths(1).AddDays(1)` | `2025-03-01` | 순서 A |
| `2025-01-30.AddDays(1).AddMonths(1)` | `2025-02-28` | 순서 B — 다르다 |
| `2024-02-29.AddYears(1)` | `2025-02-28` | 윤일 클램핑 |
| `2024-02-29.AddYears(1).AddYears(-1)` | `2024-02-28` | 가역적이지 않음 |

> **⚠️ 구독 갱신일 계산에서 날짜가 앞당겨진다**
>
> 매달 갱신되는 구독의 다음 청구일을 `next = current.AddMonths(1)`로 계산하는 코드는 흔하다. 1월 31일에 시작한 구독은 2월에 28일로 잘리고, 그 값에서 다시 한 달을 더하면 3월 28일이 된다. **한 번 잘린 날짜는 영영 복구되지 않는다.** 1년 뒤에는 청구일이 28일로 굳어 있다.
>
> 올바른 방법은 **원래의 "청구 기준일(anchor day)"을 따로 보관하고 매번 그것으로부터 계산**하는 것이다.
>
> ```csharp
> static DateOnly NextBillingDate (DateOnly start, int monthsElapsed)
> {
>     DateOnly target = start.AddMonths (monthsElapsed);   // 원본에서 계산
>     int lastDay = DateTime.DaysInMonth (target.Year, target.Month);
>     return new DateOnly (target.Year, target.Month, Math.Min (start.Day, lastDay));
> }
> ```
>
> 이래야 1월 31일 → 2월 28일 → **3월 31일**이 된다.

### 윤년 유틸리티

```csharp
Console.WriteLine (DateTime.IsLeapYear (2024));          // True
Console.WriteLine (DateTime.IsLeapYear (1900));          // False — 100의 배수
Console.WriteLine (DateTime.IsLeapYear (2000));          // True  — 400의 배수
Console.WriteLine (DateTime.DaysInMonth (2024, 2));      // 29
Console.WriteLine (DateTime.DaysInMonth (2025, 2));      // 28
```

그레고리력의 윤년 규칙은 "4의 배수이되 100의 배수는 제외, 단 400의 배수는 포함"이다. `year % 4 == 0`만 검사하는 손수 만든 윤년 판정은 1900년과 2100년에서 틀린다.

> **⚠️ `TotalDays / 365`로 나이를 계산하지 마라**
>
> ```csharp
> // 틀림
> int age = (int) ((DateTime.Today - birthDate).TotalDays / 365);
> ```
>
> 윤년이 누적되면서 오차가 쌓이고, 생일 근처에서 하루 이틀씩 틀린다. `365.25`로 바꿔도 마찬가지다. 나이는 **간격이 아니라 달력 사건의 횟수**이므로 달력으로 세야 한다.
>
> ```csharp
> static int GetAge (DateOnly birth, DateOnly today)
> {
>     int age = today.Year - birth.Year;
>     if (today < birth.AddYears (age)) age--;    // 올해 생일이 안 지났으면 하나 뺀다
>     return age;
> }
> ```
>
> `AddYears`의 클램핑 덕분에 2월 29일생도 평년에는 2월 28일 기준으로 처리된다. 법적 정의가 다른 나라도 있으므로 도메인 요구사항을 먼저 확인해라.

### 윤초는 표현되지 않는다

**.NET의 시간 모델에 윤초(leap second)는 존재하지 않는다.** `DateTime`의 `Second` 프로퍼티가 가질 수 있는 값은 0~59뿐이고, 생성자에 60을 넘기면 `ArgumentOutOfRangeException`이 던져진다.

```csharp
// 던진다 — 실제 UTC에는 2016-12-31 23:59:60 이 존재했다
var t = new DateTime (2016, 12, 31, 23, 59, 60);
```

실제 UTC에는 윤초가 삽입된 적이 있다(1972년 이후 27회). 하지만 `DateTime`은 "하루는 정확히 864,000,000,000틱"이라는 전제 위에 서 있고, 이 전제를 깨면 모든 산술이 무너진다. 그래서 .NET은 물론 유닉스 시간, 대부분의 데이터베이스도 윤초를 표현하지 않는다.

실제로는 운영체제가 윤초를 **뭉개서(smear)** 처리한다. 윤초 전후 일정 시간에 걸쳐 시계를 아주 조금씩 느리게 돌려 1초를 흡수하는 방식이다. 애플리케이션 입장에서는 시각이 잠깐 부정확할 뿐 불연속은 보이지 않는다.

> **📌 윤초가 문제가 되는 도메인은 따로 있다**
>
> 천문학, 위성 궤도 계산, 초정밀 금융 타임스탬프 규제(MiFID II 등)에서는 윤초가 실제 문제다. 이런 도메인은 UTC 대신 TAI(국제원자시)나 GPS 시각을 쓰고, .NET의 `DateTime`을 그대로 쓰지 않는다.
>
> 참고로 국제도량형총회는 2035년까지 윤초를 폐지하기로 결의했다. 그때까지는 여전히 삽입될 수 있다.

### `Add`는 서머타임을 고려하지 않는다

이것이 날짜 산술 함정 중 가장 자주 사고를 내는 항목이다.

**`DateTime.Add*`는 순수한 틱 산술이다.** 서머타임 규칙을 조회하지 않는다. 로컬 `DateTime`에 하루를 더하면 벽시계 필드가 하루 늘어날 뿐, 실제 경과 시간이 24시간이라는 보장은 없다.

```csharp
// 미국 태평양 시간대. 3월 9일에 서머타임이 시작된다.
DateTime local = new DateTime (2025, 3, 8, 12, 0, 0, DateTimeKind.Local);
DateTime next  = local.AddDays (1);

Console.WriteLine (next);    // 2025-03-09 12:00:00 (Local)
// 벽시계로는 "다음 날 같은 시각"이 맞다.
// 그러나 실제 경과 시간은 23시간이다.
```

같은 계산을 `DateTimeOffset`으로 하면 정반대가 된다 — 37.5절에서 본 대로 절대 24시간이 흐르고 벽시계 시각이 어긋난다.

| 표현 | `AddDays(1)`의 의미 | 실제 경과 | 벽시계 |
|---|---|---|---|
| `DateTime` (Local) | 벽시계 필드 +1일 | 23시간 (봄) / 25시간 (가을) | 같은 시각 |
| `DateTime` (Utc) | 틱 +24시간 | 정확히 24시간 | UTC 기준 같은 시각 |
| `DateTimeOffset` | 틱 +24시간, 오프셋 유지 | 정확히 24시간 | 오프셋이 낡아 어긋남 |

두 의미가 다르므로 **무엇을 원하는지 먼저 정해야 한다.**

- "정확히 24시간 뒤" → UTC나 `DateTimeOffset`에서 `AddHours(24)`
- "내일 같은 벽시계 시각" → 로컬 벽시계로 계산한 뒤 시간대를 통해 UTC로 되돌린다

두 번째의 올바른 관용구는 이렇다.

```csharp
static DateTimeOffset AddCalendarDays (DateTimeOffset instant,
                                       int days, TimeZoneInfo zone)
{
    // 1) 대상 시간대의 벽시계로 옮긴다
    DateTime wall = TimeZoneInfo.ConvertTime (instant, zone).DateTime;

    // 2) 벽시계 위에서 날짜 산술을 한다
    wall = wall.AddDays (days);

    // 3) 그 시간대의 규칙으로 다시 절대 시점을 만든다
    if (zone.IsInvalidTime (wall))          // 건너뛴 시각이면 보정이 필요하다
        wall = wall.AddHours (1);

    TimeSpan offset = zone.GetUtcOffset (wall);
    return new DateTimeOffset (wall, offset);
}
```

핵심은 **벽시계 산술과 절대 시각 산술을 분리하고, 그 사이를 `TimeZoneInfo`가 잇는다**는 구조다. `IsInvalidTime` 보정을 빼먹으면 1년에 하루 예외가 난다.

> **⚠️ "1시간 뒤 재시도"를 벽시계로 계산하면 무한 루프가 될 수 있다**
>
> 가을 전환일, 로컬 시각 01:30에 실패한 작업을 "1시간 뒤" 재시도하도록 벽시계 기준으로 스케줄링하면 그 1시간 뒤가 다시 01:30이다. 시계가 되돌아갔기 때문이다.
>
> **재시도·백오프·타임아웃은 예외 없이 단조 시계나 UTC로 계산해야 한다.** `Task.Delay(TimeSpan)`처럼 상대 지연을 쓰는 API는 애초에 벽시계를 보지 않으므로 안전하다. 벽시계 시각을 계산해서 그 시각까지 기다리는 구조가 위험하다.

### 산술 함정 카탈로그

| 함정 | 증상 | 대응 |
|---|---|---|
| `AddMonths` 월말 클램핑 | 청구일이 28일로 굳음 | 기준일을 보관하고 원본에서 계산 |
| 덧셈 순서 의존성 | 같은 로직이 경로마다 다른 결과 | 연산 순서를 규약으로 고정 |
| 가역성 없음 | `+1개월 -1개월 ≠ 원본` | 뺄셈으로 되돌리지 말고 원본 보관 |
| `TotalDays/365` 나이 계산 | 생일 근처 하루 오차 | 달력 기준 계산 |
| 손수 만든 윤년 판정 | 1900·2100년에 틀림 | `DateTime.IsLeapYear` |
| 윤초 미표현 | `Second == 60` 파싱 실패 | 입력을 정규화하거나 거부 |
| 로컬 `Add`와 서머타임 | 경과 시간이 23/25시간 | 의미를 정하고 UTC와 벽시계를 분리 |
| `DateTimeOffset` 산술의 낡은 오프셋 | 표시 시각이 1시간 어긋남 | `TimeZoneInfo.ConvertTime`으로 재계산 |
| 로컬 시각으로 재시도 간격 계산 | 전환일에 중복·무한 대기 | 단조 시계 또는 UTC |

> **💡 날짜 산술을 도메인 서비스로 감싸라**
>
> "다음 청구일", "영업일 기준 N일 뒤", "회계 분기 시작일" 같은 계산은 `DateTime` 확장 메서드로 흩어 두면 각 호출 지점마다 미묘하게 다른 규칙이 자란다. 도메인 규칙을 담은 서비스 클래스 하나에 모으고 단위 테스트로 경계 케이스 — 월말, 윤일, 서머타임 전환일 — 를 고정해라. 이 계산은 "누구나 아는 상식"처럼 보여서 리뷰가 느슨해지는 대표적인 영역이다.

## 37.9 시간 의존성 제거 — `TimeProvider` ※.NET 8

### 문제 — `DateTime.Now`는 테스트할 수 없는 전역 상태다

다음 코드는 흔하고, 테스트할 수 없다.

```csharp
public class SubscriptionService
{
    public bool IsExpired (Subscription s)
        => s.ExpiresAt < DateTime.UtcNow;      // ← 숨은 의존성
}
```

"만료 하루 전", "만료 당일", "만료 직후"를 테스트하려면 시스템 시계를 바꾸는 수밖에 없다. `DateTime.UtcNow`는 정적 프로퍼티이므로 주입할 수도, 가로챌 수도 없다.

전통적 해법은 인터페이스를 하나 정의하는 것이었다.

```csharp
public interface IClock { DateTimeOffset UtcNow { get; } }
```

문제는 이 인터페이스가 팀마다, 라이브러리마다 다르게 정의되었다는 점이다. ASP.NET Core에는 `ISystemClock`이, NodaTime에는 `IClock`이, 각 사내 코드베이스에는 또 다른 것이 있었다. 서로 다른 라이브러리를 조합하면 시계가 여러 개 생겼고, `Task.Delay`나 `Timer` 같은 **BCL의 시간 의존 API는 어차피 가짜 시계를 모른다**는 근본적 한계가 남았다.

### `TimeProvider` — BCL이 제시한 표준 추상화

.NET 8은 `System.TimeProvider` 추상 클래스를 도입해 이 문제를 표준화했다.

```csharp
public abstract class TimeProvider
{
    public static TimeProvider System { get; }        // 실제 시계

    public virtual DateTimeOffset GetUtcNow();
    public DateTimeOffset GetLocalNow();              // GetUtcNow + LocalTimeZone
    public virtual TimeZoneInfo LocalTimeZone { get; }

    public virtual long GetTimestamp();               // 단조 카운터
    public virtual long TimestampFrequency { get; }
    public TimeSpan GetElapsedTime (long startingTimestamp);
    public TimeSpan GetElapsedTime (long startingTimestamp, long endingTimestamp);

    public virtual ITimer CreateTimer (TimerCallback callback, object? state,
                                       TimeSpan dueTime, TimeSpan period);
}
```

세 가지를 한 타입에 모은 것이 핵심이다.

| 기능 | 메서드 | 대체하는 것 |
|---|---|---|
| 벽시계 | `GetUtcNow()`, `GetLocalNow()` | `DateTime.UtcNow`, `DateTimeOffset.Now` |
| 단조 시계 | `GetTimestamp()`, `GetElapsedTime()` | `Stopwatch` |
| 타이머 | `CreateTimer()` | `System.Threading.Timer` |
| 시간대 | `LocalTimeZone` | `TimeZoneInfo.Local` |

**`GetUtcNow()`는 `DateTimeOffset`을 돌려준다.** `DateTime`이 아니다. BCL이 새 API에서 어느 타입을 표준으로 보는지 드러나는 대목이다.

### BCL의 시간 의존 API가 `TimeProvider`를 받는다

`TimeProvider`가 이전의 사설 `IClock` 인터페이스들과 결정적으로 다른 점은, **BCL 자신이 이 추상화를 받아들인다**는 것이다. .NET 8은 여러 API에 `TimeProvider` 오버로드를 추가했다.

```csharp
// 지연
await Task.Delay (TimeSpan.FromSeconds (30), timeProvider, ct);

// 타임아웃
using var cts = new CancellationTokenSource (TimeSpan.FromSeconds (5), timeProvider);

// 태스크 타임아웃
await someTask.WaitAsync (TimeSpan.FromSeconds (10), timeProvider, ct);

// 주기 타이머
var timer = new PeriodicTimer (TimeSpan.FromMinutes (1), timeProvider);
```

가짜 `TimeProvider`를 주입하면 **`Task.Delay`조차 즉시 완료시킬 수 있다.** 30초 대기를 포함한 재시도 로직의 테스트가 밀리초 단위로 끝난다. 이것이 사설 `IClock`으로는 불가능했던 부분이다.

### `FakeTimeProvider`로 테스트하기

`Microsoft.Extensions.TimeProvider.Testing` 패키지가 `FakeTimeProvider`를 제공한다.

```csharp
public class SubscriptionService (TimeProvider time)
{
    public bool IsExpired (Subscription s) => s.ExpiresAt < time.GetUtcNow();
}
```

```csharp
[Fact]
public void 만료일_당일에는_만료되지_않는다()
{
    var fake = new FakeTimeProvider (
        new DateTimeOffset (2025, 6, 1, 0, 0, 0, TimeSpan.Zero));

    var svc = new SubscriptionService (fake);
    var sub = new Subscription { ExpiresAt = new DateTimeOffset (
                                     2025, 6, 1, 12, 0, 0, TimeSpan.Zero) };

    Assert.False (svc.IsExpired (sub));

    fake.Advance (TimeSpan.FromHours (13));    // 시계를 앞으로 민다
    Assert.True (svc.IsExpired (sub));
}
```

| `FakeTimeProvider` 멤버 | 역할 |
|---|---|
| 생성자(`DateTimeOffset`) | 시작 시각 지정 |
| `SetUtcNow(DateTimeOffset)` | 특정 시각으로 점프 |
| `Advance(TimeSpan)` | 시계를 앞으로 밀고, 그 사이 만료되는 타이머·지연을 발동 |
| `AutoAdvanceAmount` | `GetUtcNow()`가 호출될 때마다 자동으로 전진시킬 양 |
| `LocalTimeZone` | 가짜 로컬 시간대 지정 — 서머타임 전환 테스트에 쓴다 |

`Advance`가 등록된 타이머와 `Task.Delay`를 함께 진행시킨다는 점이 중요하다. 시각만 바꾸는 것이 아니라 **시간에 묶인 모든 스케줄을 함께 굴린다.**

> **💡 `LocalTimeZone`을 바꿔 서머타임 전환을 테스트해라**
>
> 37.7절에서 본 함정들 — 존재하지 않는 시각, 중복되는 시각 — 은 1년에 두 번만 재현되므로 실환경에서 발견하기 어렵다. `FakeTimeProvider`의 `LocalTimeZone`을 서머타임을 쓰는 시간대로 설정하고 `SetUtcNow`로 전환 순간에 시계를 놓으면, **전환일 동작을 매 빌드마다 검증**할 수 있다.
>
> 이것이 시간 추상화의 진짜 가치다. 테스트를 빠르게 만드는 것보다 **재현 불가능한 시나리오를 재현 가능하게 만드는 것**이 더 크다.

### 리팩터링 — `DateTime.Now` 직접 호출 제거

기존 코드베이스를 옮기는 절차는 이렇다.

**1단계. 정적 호출을 찾는다.** `DateTime.Now`, `DateTime.UtcNow`, `DateTime.Today`, `DateTimeOffset.Now`, `DateTimeOffset.UtcNow`, `new Stopwatch()`, `new Timer(...)`를 전부 검색한다.

**2단계. 생성자로 주입한다.**

```csharp
// 전
public class OrderProcessor
{
    public void Process (Order o) { o.ProcessedAt = DateTime.UtcNow; }
}

// 후
public class OrderProcessor (TimeProvider time)
{
    public void Process (Order o) { o.ProcessedAt = time.GetUtcNow(); }
}
```

**3단계. DI 컨테이너에 실제 구현을 등록한다.**

```csharp
services.AddSingleton (TimeProvider.System);
```

**4단계. 남은 호출을 금지한다.** 분석기 규칙이나 코드 리뷰 체크리스트로 `DateTime.Now` 직접 호출을 막는다. 하나라도 남으면 그 경로만 테스트에서 실제 시계를 본다.

> **⚠️ 기본값 매개변수로 `TimeProvider.System`을 넣지 마라**
>
> ```csharp
> // 하지 마라
> public OrderProcessor (TimeProvider? time = null)
>     => _time = time ?? TimeProvider.System;
> ```
>
> 편해 보이지만, 주입을 깜빡한 곳이 컴파일 에러 없이 실제 시계를 쓰게 된다. 테스트에서는 통과하고 다른 경로에서만 실패하는 종류의 버그가 생긴다. **의존성은 필수로 만들어라.** 생성자가 길어지는 것이 조용한 실패보다 낫다.

> **⚠️ `TimeProvider`는 .NET 8 타입이지만 하위 타깃에서도 쓸 수 있다**
>
> `Microsoft.Bcl.TimeProvider` 패키지가 .NET Standard 2.0 이상에서 `TimeProvider`를 제공한다. .NET Framework나 .NET 6/7을 타깃하는 라이브러리도 같은 추상화를 쓸 수 있다.
>
> 다만 `Task.Delay(TimeSpan, TimeProvider)` 같은 **BCL 오버로드는 런타임이 .NET 8 이상일 때만 존재한다.** 하위 타깃에서는 확장 메서드 형태로 폴리필이 제공되지만 동작 특성이 완전히 같지는 않으므로, 멀티 타깃 라이브러리라면 이 차이를 테스트로 고정해라.

시간·난수·파일 시스템 의존성을 제거하는 설계 일반론은 80.4절에서 더 다룬다.

## 37.10 날짜/시간 저장과 직렬화 전략

### 두 개의 질문으로 결정한다

저장 형식은 취향이 아니라 값의 의미가 결정한다. 질문은 둘이다.

```text
                   ┌─────────────────────────────────┐
                   │ 이 값은 시각을 포함하는가?      │
                   └───────────┬─────────────────────┘
                  아니오       │       예
          ┌────────────────────┘       └──────────────┐
          ↓                                           ↓
    ┌───────────┐                    ┌────────────────────────────────┐
    │ DateOnly  │                    │ 지구상의 특정 순간인가,        │
    │ (date)    │                    │ 벽시계 눈금인가?               │
    └───────────┘                    └───────┬────────────────────────┘
                                    특정 순간 │ 벽시계
                          ┌──────────────────┘   └──────────────┐
                          ↓                                     ↓
              ┌───────────────────────┐         ┌──────────────────────────┐
              │ 과거인가 미래인가?    │         │ 로컬 시각 + IANA TZ ID   │
              └───┬───────────────────┘         │ (datetime2 + varchar)    │
           과거   │   미래(절대)                └──────────────────────────┘
        ┌─────────┘        └────────┐
        ↓                           ↓
┌───────────────────────┐  ┌─────────────────┐
│ DateTimeOffset        │  │ UTC             │
│ (오프셋까지 보존)     │  │ (datetime2)     │
│ 또는 UTC              │  └─────────────────┘
└───────────────────────┘
```

### 저장 전략 비교표

| 전략 | 저장 내용 | 장점 | 단점 | 언제 |
|---|---|---|---|---|
| UTC `DateTime` | UTC 벽시계 값 | 단순, 비교·정렬 정확, 인덱스 효율 | 표시 전 변환 필수, `Kind` 소실 | 로그, 감사, 생성/수정 시각 |
| `DateTimeOffset` | UTC + 오프셋 | 사용자가 본 시각 복원 가능 | 저장 공간 큼, 지역 미상 | 주문·결제 등 사용자 맥락이 중요한 과거 이벤트 |
| 로컬 시각 + TZ ID | 벽시계 값 + `Asia/Seoul` | 규칙 변경에 안전, 재해석 가능 | 정렬·비교에 계산 필요 | 미래 일정, 반복 일정, 알람 |
| `DateOnly` | 날짜만 | 시간대 변환 자체가 불가능 | 시각이 필요하면 못 씀 | 생일, 만기일, 회계일 |
| epoch 밀리초 | `long` | 언어 중립, 컴팩트 | 사람이 못 읽음, 정밀도 손실 | 외부 API 연동, 시계열 저장소 |

> **💡 세 컬럼 패턴**
>
> 실무에서 자주 쓰는 절충안이 있다. 하나의 논리적 시각을 **세 컬럼**으로 저장하는 것이다.
>
> | 컬럼 | 타입 | 용도 |
> |---|---|---|
> | `OccurredAtUtc` | `datetime2` | 정렬·범위 조회·인덱스 |
> | `LocalWallClock` | `datetime2` | 사용자가 본 그대로의 시각 |
> | `TimeZoneId` | `varchar(64)` | IANA ID. 재해석의 근거 |
>
> 중복 저장이지만, 인덱스는 UTC 컬럼에만 걸면 되고 표시와 재계산은 나머지 둘로 한다. 시간대 규칙이 바뀌어도 `LocalWallClock` + `TimeZoneId`로 `OccurredAtUtc`를 다시 계산할 수 있다는 것이 핵심 이점이다.

### SQL Server 타입 매핑

| SQL Server 타입 | 정밀도 | 범위 | .NET 타입 | 비고 |
|---|---|---|---|---|
| `date` | 1일 | 0001-01-01 ~ 9999-12-31 | `DateOnly` / `DateTime` | 3바이트 |
| `time` | 100ns | 00:00:00 ~ 23:59:59.9999999 | `TimeOnly` / `TimeSpan` | 3~5바이트 |
| `datetime2` | 100ns | 0001 ~ 9999 | `DateTime` | 6~8바이트. 기본 선택 |
| `datetimeoffset` | 100ns + 분 오프셋 | 0001 ~ 9999 | `DateTimeOffset` | 8~10바이트 |
| `datetime` (레거시) | 약 3.33ms | 1753 ~ 9999 | `DateTime` | 8바이트. 신규 사용 금지 |
| `smalldatetime` (레거시) | 1분 | 1900 ~ 2079 | `DateTime` | 4바이트 |

> **⚠️ 레거시 `datetime`은 값을 조용히 반올림한다**
>
> `datetime` 타입은 1/300초(약 3.33ms) 단위로만 값을 저장한다. `.NET`에서 `23:59:59.999`를 넣으면 **다음 날 00:00:00.000으로 반올림된다.** "하루의 마지막 순간"을 나타내려고 `.999`를 쓰는 관용구가 여기서 깨진다.
>
> 애초에 범위 조회는 `>= 시작 AND < 다음날`로 쓰는 것이 정답이다. 경계값을 손으로 만들면 정밀도가 다른 저장소를 만날 때마다 틀린다.

### ISO 8601 왕복 형식 `"O"`

기계가 읽을 문자열에는 예외 없이 **왕복(round-trip) 형식 `"O"`(또는 `"o"`)** 를 써라. 이 형식은 문화권 설정을 무시하고, 100ns 정밀도를 모두 담고, `DateTimeKind`를 보존한다.

```csharp
var utc   = new DateTime (2025, 3, 9, 12, 0, 0, DateTimeKind.Utc);
var local = new DateTime (2025, 3, 9, 12, 0, 0, DateTimeKind.Local);
var unspec= new DateTime (2025, 3, 9, 12, 0, 0, DateTimeKind.Unspecified);

Console.WriteLine (utc.ToString    ("O"));   // 2025-03-09T12:00:00.0000000Z
Console.WriteLine (local.ToString  ("O"));   // 2025-03-09T12:00:00.0000000+09:00
Console.WriteLine (unspec.ToString ("O"));   // 2025-03-09T12:00:00.0000000
```

**`Kind`가 접미사로 인코딩된다** — `Utc`는 `Z`, `Local`은 실제 오프셋, `Unspecified`는 아무것도 붙지 않는다. 되읽을 때 이 정보를 복원하려면 `DateTimeStyles.RoundtripKind`가 필요하다.

```csharp
DateTime back = DateTime.Parse (s, CultureInfo.InvariantCulture,
                                DateTimeStyles.RoundtripKind);
```

`DateTimeOffset`은 `Kind` 문제가 없으므로 `"O"` 왕복이 더 단순하다.

```csharp
var dto = new DateTimeOffset (2025, 3, 9, 12, 0, 0, TimeSpan.FromHours (9));
string s = dto.ToString ("O");                 // 2025-03-09T12:00:00.0000000+09:00
var back = DateTimeOffset.Parse (s, CultureInfo.InvariantCulture);
Console.WriteLine (back.EqualsExact (dto));    // True — 오프셋까지 복원된다
```

> **⚠️ `"O"` 없이 `ToString()`한 문자열은 되읽을 수 없다**
>
> 기본 `ToString()`은 실행 환경의 문화권을 따른다. 한국 서버에서 만든 `2025-03-09 오후 12:00:00`을 미국 서버에서 파싱하면 예외가 나거나 — 더 나쁘게는 — 다른 날짜로 조용히 읽힌다. 로그 파일, 캐시 키, 파일 이름, HTTP 헤더, 큐 메시지 어디든 마찬가지다.
>
> 사람이 읽을 문자열과 기계가 읽을 문자열을 분리해라. 전자는 `CultureInfo.CurrentCulture` + 표시용 형식, 후자는 `CultureInfo.InvariantCulture` + `"O"`다. 서식 지정자 목록과 문화권 규칙은 38.5절과 38.11절에서 다룬다.

### `XmlConvert`

XML 문맥에서는 `System.Xml.XmlConvert`가 표준 XSD 날짜/시각 형식을 따르는 변환을 제공한다.

```csharp
string s = XmlConvert.ToString (dt, XmlDateTimeSerializationMode.Utc);
DateTime d = XmlConvert.ToDateTime (s, XmlDateTimeSerializationMode.RoundtripKind);
```

`XmlDateTimeSerializationMode`는 `Local`, `Utc`, `Unspecified`, `RoundtripKind` 네 값을 갖는다. **`RoundtripKind`가 `Kind`를 보존하는 유일한 값**이므로 왕복이 목적이면 이것을 써라. `XmlConvert`의 다른 용도는 38.9절에서 다룬다.

### JSON과 epoch

`System.Text.Json`은 기본적으로 ISO 8601-1:2019 확장 프로파일로 `DateTime`과 `DateTimeOffset`을 처리한다. 즉 별도 설정 없이도 왕복 안전한 문자열이 나온다. 직렬화기의 옵션과 커스텀 컨버터는 41.2절과 41.5절이다.

유닉스 epoch를 쓰는 외부 시스템과 연동할 때는 `DateTimeOffset`의 전용 메서드를 쓴다.

```csharp
DateTimeOffset now = DateTimeOffset.UtcNow;

long secs   = now.ToUnixTimeSeconds();
long millis = now.ToUnixTimeMilliseconds();

DateTimeOffset a = DateTimeOffset.FromUnixTimeSeconds (secs);
DateTimeOffset b = DateTimeOffset.FromUnixTimeMilliseconds (millis);

Console.WriteLine (DateTimeOffset.UnixEpoch);   // 1970-01-01T00:00:00.0000000+00:00
```

| 표현 | 정밀도 | 범위 | 비고 |
|---|---|---|---|
| `ToUnixTimeSeconds` | 1초 | 넓음 (`long`) | 하위 자릿수 손실 |
| `ToUnixTimeMilliseconds` | 1ms | 넓음 (`long`) | 대부분의 웹 API가 이것 |
| ISO 8601 `"O"` | 100ns | 0001 ~ 9999 | 사람도 읽을 수 있음 |
| `DateTime.Ticks` | 100ns | 0001 ~ 9999 | .NET 전용. `Kind` 소실 |
| `DateTime.ToBinary()` | 100ns | 0001 ~ 9999 | .NET 전용. `Kind` 보존 |

> **⚠️ epoch 값을 `int`로 받지 마라**
>
> 32비트 부호 있는 정수로 표현한 유닉스 초는 **2038년 1월 19일에 넘친다.** 외부 API의 JSON 필드를 `int`로 선언한 코드가 아직도 많다. `long`으로 받아라.
>
> 밀리초 단위 epoch는 `int`로는 1970년 이후 25일도 담지 못하므로 이 실수가 즉시 드러나지만, 초 단위는 앞으로 십여 년 동안 조용히 동작한다.

> **📌 tzdata 버전은 데이터의 일부다**
>
> "로컬 시각 + 시간대 ID"로 저장하면 규칙 변경에 안전하다고 했지만, 정확히는 **"계산 시점의 tzdata로 재계산된다"** 는 뜻이다. 서버들의 tzdata 버전이 서로 다르면 같은 입력에 다른 UTC 시각이 나온다.
>
> 대응은 두 가지다. (1) 배포 파이프라인에서 tzdata 버전을 고정하고 일괄 갱신한다. (2) 계산 결과를 캐시할 때 사용한 tzdata 버전을 함께 기록해, 버전이 올라가면 재계산 대상을 식별할 수 있게 한다. 항공·물류처럼 미래 일정이 대량인 도메인에서는 후자가 필수다.

| 확인 항목 | 통과 기준 |
|---|---|
| 데이터베이스 컬럼 타입 | `datetime2` 또는 `datetimeoffset`. 레거시 `datetime` 없음 |
| `Kind` 확정 지점 | 데이터 액세스 계층 경계에서 `SpecifyKind` |
| 미래 일정 | 로컬 시각 + IANA 시간대 ID로 저장 |

| 기계용 문자열 | `InvariantCulture` + `"O"` |

## 이 장의 요약

- **`TimeSpan`은 `long` 틱 하나다.** 100ns 단위, 약 1,000만 일 범위, 음수 가능. 만드는 방법은 생성자·`From…`·`DateTime` 뺄셈 세 가지이며, `From…`의 `double` 오버로드는 밀리초로 반올림한다. 기본값은 `TimeSpan.Zero`다.
- **`Seconds`와 `TotalSeconds`는 다른 질문에 답한다.** 구성 요소 프로퍼티는 표시용 자릿수이고 `Total…`은 전체 환산값이다. 조건문에서는 `Total…`을 쓰거나, 더 좋게는 `TimeSpan`끼리 직접 비교한다.
- **`DateTime`은 62비트 틱 + 2비트 `Kind`이고, 비교는 틱만 본다.** `Kind`가 달라도 틱이 같으면 같다고 판정한다. 즉 `DateTime`의 `==`는 "같은 시점인가"가 아니라 "같은 달력 눈금인가"를 답한다.
- **`DateTimeOffset`은 UTC `DateTime` + 16비트 분 오프셋이고, 비교는 UTC 값만 본다.** 오프셋까지 포함해 비교하려면 `EqualsExact`를 명시적으로 불러야 한다. 오프셋은 저장하지만 **지역은 모른다** — `+08:00`이 싱가포르인지 퍼스인지 알 방법이 없다.
- **선택 기준은 "특정 순간인가, 벽시계 눈금인가"다.** 국제 이벤트의 선후 판정처럼 시점이 중요하면 `DateTimeOffset`, "각 지사 현지 새벽 3시"처럼 로컬 상대 시각이면 `DateTime`이다.
- **`DateOnly`/`TimeOnly`(.NET 6)는 타입 수준에서 함정을 제거한다.** 자정 `DateTime`으로 날짜를 표현할 때 생기던 "0이 아닌 시각 성분 때문에 동등 비교 실패"가 구조적으로 불가능해진다. `TimeOnly.IsBetween`은 자정을 가로지르는 구간도 처리한다.
- **`Unspecified`는 "알 수 없음"이 아니라 자리마다 다르게 해석되는 상태다.** `ToUniversalTime`은 로컬로 간주하고 `ToLocalTime`은 UTC로 간주한다. `DateTimeOffset`으로의 암시적 변환은 로컬로 간주한다. 데이터 경계에서 `SpecifyKind`로 못 박아라.
- **`DateTime.MinValue`를 "값 없음"의 센티널로 쓰지 마라.** 시간대 변환 한 번이면 더 이상 `MinValue`가 아니게 된다. `DateTime?`을 써라.
- **`TimeZoneInfo`가 규칙을 담고 `DateTimeOffset`은 규칙의 스냅숏만 담는다.** 시간대 간 변환은 `ConvertTime` 계열로 하고, 시간대 ID는 IANA 형식으로 저장한다. .NET 6부터 `FindSystemTimeZoneById`가 두 체계를 모두 받지만, IANA→Windows→IANA 왕복은 정보를 잃는다.
- **서머타임은 존재하지 않는 시각과 두 번 존재하는 시각을 만든다.** `IsInvalidTime`·`IsAmbiguousTime`·`GetAmbiguousTimeOffsets`로 검증해야 하며, 전자는 변환 시 예외를 던지고 후자는 조용히 한쪽을 고른다. 두 `DateTime` 비교 전에 각각 `ToUniversalTime`을 부르는 전략은 **정확히 하나가 `Unspecified`일 때** 실패한다.
- **미래 일정은 UTC가 아니라 "로컬 시각 + 시간대 ID"로 저장한다.** UTC로 굳히면 그 순간의 서머타임 규칙이 값에 구워지고, 규칙은 정치적 결정으로 바뀐다. 과거 이벤트에만 UTC가 정답이다.
- **날짜 산술은 가환적이지도 가역적이지도 않다.** `AddMonths`는 월말을 클램핑하고, 그래서 `+1개월 -1개월`이 원본이 아니다. 청구일 계산은 기준일을 보관하고 원본에서 계산해야 한다. 윤초는 .NET의 시간 모델에 존재하지 않는다.
- **`Add`는 서머타임을 고려하지 않는다.** 로컬 `DateTime`의 `AddDays(1)`은 벽시계 하루이고 실제로는 23시간일 수 있으며, `DateTimeOffset`의 `AddDays(1)`은 정확히 24시간이지만 오프셋이 낡는다. 벽시계 산술과 절대 시각 산술을 분리하고 `TimeZoneInfo`로 이어라.
- **`TimeProvider`(.NET 8)는 벽시계·단조 시계·타이머를 하나의 추상화로 묶는다.** BCL 자신이 `Task.Delay`·`CancellationTokenSource`·`PeriodicTimer`에서 이를 받으므로, `FakeTimeProvider`로 30초 대기 로직을 밀리초에 테스트하고 서머타임 전환일 동작을 매 빌드마다 검증할 수 있다.
- **기계가 읽을 문자열에는 `InvariantCulture` + `"O"`를 쓴다.** `"O"`는 `Kind`를 접미사로 인코딩하며, 되읽을 때 `DateTimeStyles.RoundtripKind`가 필요하다. epoch 필드는 반드시 `long`으로 받아라.

## 연습 문제

1. `TimeSpan.FromDays(10) - TimeSpan.FromSeconds(1)`을 만들고 `Days`/`Hours`/`Minutes`/`Seconds`와 `TotalDays`/`TotalHours`/`TotalMinutes`/`TotalSeconds`를 모두 출력해 값을 대조하라. 이어서 `TimeSpan.FromHours(-2.5)`의 `Hours`와 `Minutes`를 출력해 부호가 어떻게 붙는지 확인하고, `Duration()`을 쓴 버전과 비교하라.
2. `Kind`만 다른 두 `DateTime`이 `==`로 같게 나오는 것과, `DateTime.Now`와 그 `ToUniversalTime()`이 다르게 나오는 것을 각각 실행해 확인하라. 같은 실험을 `DateTimeOffset`으로 반복하고 `EqualsExact`의 결과까지 출력해, 두 타입의 동등성 의미론을 표로 정리하라.
3. `Unspecified`인 `DateTime` 하나를 만들어 `ToUniversalTime()`과 `ToLocalTime()`을 각각 호출하고 두 결과의 차이를 출력하라. 그 차이가 로컬 오프셋의 두 배임을 확인하고, `SpecifyKind`로 `Kind`를 확정한 뒤 같은 실험을 반복해 차이가 사라지는 것을 보여라.
4. `TimeZoneInfo.GetSystemTimeZones()`를 열거해 `Id`·`BaseUtcOffset`·`SupportsDaylightSavingTime`을 표로 출력하라. `HasIanaId`가 `true`인 항목 수를 세고, 리눅스 컨테이너와 Windows에서 각각 실행해 결과를 비교하라.
5. `America/Los_Angeles` 시간대에 대해 2025년의 서머타임 전환 시각 전후 3시간을 1분 간격으로 훑으면서 `IsInvalidTime`과 `IsAmbiguousTime`이 `true`인 구간을 출력하라. 모호한 시각 하나를 골라 `GetAmbiguousTimeOffsets`가 돌려주는 값을 확인하라.
6. 37.7절의 `FormatTransitionTime`을 그대로 옮겨 `Australia/Perth`와 자신의 로컬 시간대에 대해 `GetAdjustmentRules()`를 출력하라. `IsFixedDateRule`이 `false`인 규칙에서 `Week` 값이 무엇인지 확인하고, `Week == 5`인 규칙이 있으면 실제 달력에서 그 날짜를 계산해 검증하라.
7. `2025-01-31`에서 시작해 `AddMonths(1)`을 12번 연속 적용한 결과와, 기준일 31을 보관하고 매번 원본에서 계산한 결과를 나란히 출력하라. 두 수열이 갈라지는 지점을 찾고, 어느 쪽이 도메인 요구사항에 맞는지 판단 근거를 적어라.
8. 서머타임이 있는 시간대에서 로컬 `DateTime`에 `AddDays(1)`을 한 결과와, 같은 시점을 `DateTimeOffset`으로 만들어 `AddDays(1)`을 한 결과를 전환일 전날에 대해 각각 출력하라. 두 결과의 UTC 값과 벽시계 값을 모두 찍어 차이를 설명하라.
9. `Microsoft.Extensions.TimeProvider.Testing`을 참조해 `FakeTimeProvider`로 "3회 재시도, 매번 30초 대기" 로직의 테스트를 작성하라. 테스트 실행 시간이 1초 미만인지 확인하고, `Task.Delay`에 `TimeProvider` 오버로드를 넘기지 않았을 때 어떻게 되는지도 확인하라.
10. 같은 `DateTime` 값을 (a) `ToString()`, (b) `ToString("O")`, (c) `ToBinary()`, (d) `Ticks`로 각각 직렬화한 뒤 되읽어 `Kind`와 값이 보존되는지 표로 정리하라. `CultureInfo.CurrentCulture`를 `en-US`와 `de-DE`로 바꿔 가며 (a)의 왕복이 실패하는 것을 재현하라.
