# 부록 J. 추가 학습 자료 — 저장소, 블로그, 컨퍼런스

> **이 부록의 위치** — 부록 I가 **이 책이 어디서 왔는가**를 밝혔다면, 이 부록은 **이 책 다음에 어디로 가는가**를 가리킨다. 책은 여기서 끝나지만 C#은 끝나지 않는다. 앞으로 새로 나오는 것들에 대해서는 어떤 책도 답을 주지 못하고, 그때부터는 1차 출처를 직접 여는 습관만이 남는다.
>
> **선수 지식** — 83장(런타임 소스 읽기), 84장(자기 검증 체크리스트). 이 부록은 그 두 장의 자료 편이다.
>
> **이 부록에서 다루지 않는 것** — 런타임 저장소를 실제로 열어 들어가는 **절차의 세부**는 83장이, 진단 도구의 **명령 레퍼런스**는 부록 C가, 스스로를 시험하는 **질문 목록**은 84장이 담당한다. 여기서는 "무엇이 어디에 있고, 무엇을 배우러 가는가"만 정리한다.

## J.1 이 목록을 쓰는 법과 주의

### 왜 URL을 적지 않는가

이 부록에는 주소가 한 줄도 없다. 이름과 **찾는 방법**만 적는다. 이유는 두 가지다.

첫째, **주소는 자료보다 빨리 낡는다.** 문서가 옮겨지고, 블로그 플랫폼이 바뀌고, 저장소가 이관된다. `dotnet/coreclr`와 `dotnet/corefx`가 `dotnet/runtime` 하나로 합쳐진 것이 대표적인 예이고, 그때 수많은 책과 글의 링크가 한꺼번에 죽었다. 반면 **저장소 이름과 조직 이름은 훨씬 오래 산다.** "GitHub에서 `dotnet/runtime`을 찾아라"는 지시는 5년 뒤에도 유효할 가능성이 높다.

둘째, **찾는 행위 자체가 기술이다.** 링크를 클릭하는 것과 저장소를 검색해 구조를 파악하고 원하는 파일에 도달하는 것은 다른 능력이다. 후자만이 **처음 보는 저장소**에도 통한다. 이 부록은 전자를 일부러 막는다.

### 자료의 등급

모든 자료가 같은 무게를 갖지 않는다. 충돌할 때 무엇을 믿을지 미리 정해 두어야 한다.

| 등급 | 자료 | 무엇을 답하는가 | 신뢰도 |
|---|---|---|---|
| **1차** | 런타임·컴파일러 **소스** | 실제로 무엇이 실행되는가 | 최고. 단 그 커밋 시점의 사실 |
| **1차** | 언어·CLI **명세**(ECMA-334/335) | 무엇이 보증되는가 | 최고. 단 구현이 앞서갈 수 있다 |
| **1차** | 언어 **설계 저장소**의 제안서·회의록 | 왜 그렇게 정해졌는가 | 높음. 단 미채택 제안이 섞여 있다 |
| **1.5차** | 런타임 저장소의 `docs/design` | 서브시스템의 의도와 구조 | 높음. 단 갱신이 늦는 문서가 있다 |
| **2차** | 공식 문서(API 레퍼런스·가이드) | 어떻게 쓰는가 | 높음. 단 내부 동작은 답하지 않는다 |
| **2차** | 공식 블로그의 성능·릴리스 글 | 무엇이 바뀌었는가 | 높음. 특정 버전 기준임을 항상 확인 |
| **3차** | 책·강연·개인 글 | 어떻게 이해할 것인가 | 유용하나 **버전과 판을 반드시 확인** |
| **3차** | 질의응답 사이트의 답변 | 급할 때의 실마리 | 낮음. 오래된 답이 상위에 남는다 |

**이 책은 3차다.** 부록 I가 그 사실을 이미 밝혔다. 이 부록의 목적은 독자를 3차에서 1차로 이동시키는 것이다.

> **⚠️ 상위 검색 결과와 정확한 답은 다르다**
>
> C#은 20년 넘은 언어라 인터넷에 남은 글의 상당수가 .NET Framework 시절 것이다. "C# 문자열 성능", "C# 스레드 동기화" 같은 검색어의 상위 결과는 대체로 10년 전 답이며, 그 사이 런타임이 바뀌어 **정확히 반대 조언**이 된 것도 있다. 검색으로 얻은 답은 항상 **작성 시점과 대상 런타임**을 확인하고, 확인할 수 없으면 버려라.

> **💡 자료를 고르는 한 문장 기준**
>
> "이 자료는 **어느 버전**을 대상으로 하는가?"에 답할 수 없는 자료는 읽지 마라. 대상 버전이 명시되지 않은 성능 주장, 런타임 동작 서술, 최적화 조언은 전부 신뢰 등급이 한 단계 내려간다.

## J.2 1차 출처

### 런타임과 컴파일러 소스

| 저장소 | 조직 | 무엇이 들어 있는가 | 무엇을 배우러 가는가 |
|---|---|---|---|
| `dotnet/runtime` | GitHub `dotnet` | CLR(coreclr), GC, JIT, 코어 라이브러리 전부 | 런타임이 **실제로** 무엇을 하는가. 이 책 3권 전체의 최종 근거 |
| `dotnet/roslyn` | GitHub `dotnet` | C#·VB 컴파일러, 분석기 인프라 | 문법이 **무엇으로 컴파일되는가**, 진단 메시지의 정확한 조건 |
| `dotnet/csharplang` | GitHub `dotnet` | C# 언어 설계 — 제안서, 설계 회의록, 사양 초안 | 기능이 **왜 그 모양인가**, 그리고 다음에 무엇이 오는가 |
| `dotnet/csharpstandard` | GitHub `dotnet` | ECMA-334 표준화 작업본 | 언어의 **공식 문면** |
| `dotnet/sdk` | GitHub `dotnet` | `dotnet` CLI와 빌드 파이프라인 | `dotnet build`가 실제로 무엇을 하는가 |
| `dotnet/diagnostics` | GitHub `dotnet` | SOS, `dotnet-dump`·`dotnet-trace`·`dotnet-counters` | 진단 도구의 동작과 명령 목록(부록 C의 배경) |
| `dotnet/performance` | GitHub `dotnet` | 런타임 공식 벤치마크 스위트 | **벤치마크를 어떻게 쓰는지**의 모범 사례 |
| `dotnet/docs` | GitHub `dotnet` | 공식 문서의 소스 | 문서가 틀렸을 때 고칠 곳 |

찾는 법은 하나다 — GitHub에서 `dotnet` 조직을 열고 저장소 목록에서 이름으로 찾는다. 조직 이름이 `dotnet`인 것만 기억하면 나머지는 목록에서 보인다.

> **📌 `dotnet/coreclr`과 `dotnet/corefx`를 아직 참조하는 글**
>
> 이 두 저장소는 `dotnet/runtime`으로 통합됐다. 옛 글에서 이 이름이 나오면 경로를 `dotnet/runtime`의 `src/coreclr/`(전자)과 `src/libraries/`(후자)로 옮겨 읽으면 된다. 그 글의 **작성 시점이 통합 이전**이라는 신호이기도 하다.

### 언어 설계 저장소를 읽는 법

`dotnet/csharplang`은 이 목록에서 가장 저평가된 자료다. 구조는 단순하다.

| 디렉터리 | 내용 | 읽는 시점 |
|---|---|---|
| `proposals/` | 채택 전 제안서 | 새 문법의 **정확한 규칙**이 궁금할 때 |
| `proposals/csharp-NN.0/` | 버전별로 확정된 기능 명세 | 그 버전 기능의 세부 규칙 확인 |
| `meetings/` | 언어 설계 회의(LDM) 노트, 날짜별 | **왜 그렇게 정해졌는가**를 알고 싶을 때 |
| `spec/` | 언어 사양 초안 | 문면이 필요할 때 |

읽는 순서를 권한다. **기능 하나를 골라 제안서 → 회의록 순으로 읽어라.** 제안서는 "무엇"이고 회의록은 "왜"다. 예를 들어 컬렉션 식이나 기본 인터페이스 멤버 같은 논쟁적인 기능은 회의록에 채택되지 않은 대안이 함께 남아 있고, 그 대안들이 왜 버려졌는지를 읽는 것이 언어를 이해하는 가장 빠른 길이다.

> **⚠️ 제안서가 곧 기능은 아니다**
>
> `proposals/` 최상위에는 **아직 채택되지 않은** 제안이 많다. 논의 중이거나 무기한 보류된 것도 그대로 남아 있다. 어떤 문법을 제안서에서 보고 "C#에 이런 게 있다"고 결론 내리면 안 된다. 버전별 폴더(`proposals/csharp-NN.0/`)에 있고 릴리스 노트에 있는 것만 실제 기능이다.

### 명세 — ECMA-334와 ECMA-335

| 문서 | 내용 | 언제 필요한가 |
|---|---|---|
| **ECMA-334** | C# 언어 명세 | "이 동작이 보증되는가, 아니면 구현 세부인가"를 판별할 때 |
| **ECMA-335** | 공통 언어 기반(CLI) 명세 — 메타데이터, IL 명령 집합, 타입 시스템 | IL 옵코드의 정확한 의미론, 메타데이터 테이블 구조, 검증 규칙 |

ECMA 표준은 ECMA International이 무료로 배포한다. 검색어는 표준 번호 그대로다. **ECMA-335의 Partition III(CIL 명령 집합)은 이 책 56장과 부록 A의 최종 근거**이며, 옵코드의 스택 전이 동작을 한 줄씩 정의한다. 부록 A의 표에서 애매한 항목이 있으면 여기로 가면 된다.

> **📌 명세와 구현이 다를 때**
>
> 명세가 "구현 정의(implementation-defined)" 또는 "지정되지 않음(unspecified)"이라고 말하는 지점이 있다. 그런 곳에서 관찰한 동작은 **지금 이 런타임의 동작일 뿐**이고 다음 버전에 바뀌어도 버그가 아니다. 명세를 읽는 가장 큰 실익이 이것이다 — **의존해도 되는 것과 안 되는 것의 경계**를 아는 것.

### 공식 문서 — 무엇을 문서에서 찾고 무엇을 소스에서 찾나

경계를 미리 정해 두면 시간을 아낀다.

| 질문의 종류 | 어디로 | 예 |
|---|---|---|
| 이 메서드의 시그니처·오버로드·예외는? | 공식 API 레퍼런스 | `Dictionary<K,V>.TryGetValue`의 반환 규약 |
| 이 기능을 어떻게 켜는가? | 공식 가이드 문서 | 서버 GC 활성화, 트리밍 설정 |
| 런타임 구성 스위치의 이름은? | 공식 문서 + `dotnet/runtime`의 구성 문서 | `DOTNET_gcServer` 등(65장) |
| 이 API의 **시간 복잡도와 할당**은? | 소스 | `List<T>.Insert`가 언제 배열을 다시 잡는가 |
| 이 최적화가 **언제 적용되는가**? | JIT 소스 + 디스어셈블리 | 인라이닝 임계값, 경계 검사 제거(55장) |
| 이 동작이 **버전 간에 바뀌었는가**? | 저장소의 `git log`와 릴리스 노트 | LOH 임계값, GC 모드 기본값 |
| **왜** 이렇게 설계됐는가? | `csharplang` 회의록, `runtime`의 이슈·PR 논의 | `record struct`가 기본 가변인 이유 |

한 줄로 정리하면 이렇다. **공식 문서는 "무엇을·어떻게"에 답하고, 소스는 "실제로·왜·언제부터"에 답한다.** 이 책이 3권 내내 소스를 인용한 이유가 여기 있다.

### 릴리스와 변화 추적

| 자료 | 무엇을 배우러 가는가 |
|---|---|
| **.NET Blog**(마이크로소프트 공식 개발자 블로그의 .NET 섹션) | 릴리스마다 무엇이 바뀌었는가, 특히 **버전별 성능 개선 정리 글** |
| `dotnet/core` 저장소의 릴리스 노트 | 각 릴리스에 들어간 변경의 목록과 호환성 주의 |
| `dotnet/runtime`의 **주요 변경 사항(breaking changes)** 문서 | 올릴 때 깨질 것 |
| `dotnet/runtime`·`dotnet/roslyn`의 **이슈와 PR** | 지금 논의 중인 것. 검색은 저장소 안 검색으로 |

**버전별 성능 개선 정리 글**은 이 목록에서 가장 밀도가 높다. 매 릴리스마다 런타임 팀이 그 버전에서 바꾼 최적화를 벤치마크와 함께 정리하는 긴 글이 .NET Blog에 올라오고, 분량이 책 한 장을 넘는다. 이 책 부록 D의 성능 상수가 버전에 따라 달라진다고 경고한 지점을 실제로 추적하려면 이 글이 출발점이다.

> **💡 릴리스 노트는 읽는 것이 아니라 검색하는 것이다**
>
> 통독할 분량이 아니다. 자기 코드베이스에서 쓰는 타입 이름(`HttpClient`, `JsonSerializer`, `Dictionary`, `Regex` 등)으로 릴리스 노트와 성능 글을 **검색**하라. 열 개 중 한 개가 자기 코드에 해당하고, 그 한 개가 무료로 얻는 성능 개선이거나 조용한 동작 변경이다.

## J.3 소스를 읽는 기술

83장이 절차를 다뤘다. 여기서는 **자주 쓰는 진입 경로**만 압축한다.

### 저장소를 클론하기 전에

전체 클론은 무겁다. 세 단계로 나눠 쓴다.

| 단계 | 방법 | 언제 |
|---|---|---|
| 1 | GitHub **웹 검색**(저장소 안에서 파일명·기호명 검색) | 파일 하나만 보면 될 때. 대부분이 여기서 끝난다 |
| 2 | 얕은 클론 | 여러 파일을 오가며 읽을 때 |
| 3 | 전체 클론 + 빌드 | 실제로 고쳐 보거나 디버깅할 때 |

```bash
# 2단계: 히스토리 없이 최신 스냅숏만
# <저장소 주소>는 GitHub에서 dotnet/runtime을 찾아 복사한다
git clone --depth 1 <저장소 주소>

# 특정 릴리스 시점의 소스를 보고 싶을 때 (브랜치 이름은 저장소의 브랜치 목록에서 확인)
git clone --depth 1 --branch release/8.0 <저장소 주소>
```

**릴리스 브랜치를 지정하는 것이 중요하다.** 기본 브랜치는 아직 출시되지 않은 다음 버전이다. 자기가 쓰는 런타임의 동작을 확인하려면 그 버전의 브랜치를 봐야 한다.

### 실전 절차 — `Dictionary<K,V>`의 리사이즈 정책을 확인하고 싶을 때

절차를 그대로 따라가 보자. 이 흐름이 다른 모든 질문에도 그대로 적용된다.

```text
① 질문을 파일 이름으로 바꾼다
   "Dictionary의 리사이즈" → Dictionary.cs

② 코어 라이브러리에서 위치를 좁힌다
   src/libraries/System.Private.CoreLib/src/System/Collections/Generic/

③ 파일 안에서 기호로 찾는다
   Resize / Initialize / _buckets / _entries

④ 그 메서드가 호출하는 헬퍼로 한 단계 더 들어간다
   용량 계산이 별도 헬퍼로 빠져 있으면 그쪽이 진짜 정책이다

⑤ 결론을 코드로 재현해 확인한다
   Count를 늘려 가며 내부 용량이 언제 점프하는지 관찰
```

명령으로 쓰면 이렇다.

```bash
# ② 위치 좁히기 — 파일 찾기
find src/libraries -name "Dictionary.cs" -path "*Generic*"

# ③ 파일 안에서 리사이즈 경로 찾기
grep -n "Resize\|private void Initialize\|_buckets" \
  src/libraries/System.Private.CoreLib/src/System/Collections/Generic/Dictionary.cs

# ④ 용량 계산 헬퍼가 별도 파일로 빠져 있는지
grep -rn "static int GetPrime\|ExpandPrime" src/libraries/System.Private.CoreLib/src/System/Collections/
```

④에서 나오는 헬퍼 파일이 **정책의 실제 소재지**다. 컬렉션 본체는 "언제 늘릴지"만 정하고 "얼마나 늘릴지"는 공용 헬퍼가 정하는 구조가 흔하다. 이 구조를 한 번 보고 나면 `HashSet<T>`, `ConcurrentDictionary<K,V>`도 같은 방식으로 읽힌다.

⑤가 빠지면 안 된다. 소스를 읽어 얻은 결론은 **실행해서 확인**해야 완성이다.

```csharp
// 내부 용량 변화를 관찰한다 — 리플렉션으로 내부 배열 길이를 읽는 방식.
// 필드 이름은 런타임 구현 세부이므로 버전에 따라 달라질 수 있다.
// 그래서 "이 코드가 그대로 돌지 않으면 필드 이름부터 소스에서 다시 확인"이 정답이다.
using System.Reflection;

var d = new Dictionary<int, int>();
int last = -1;
for (int i = 0; i < 100; i++)
{
    d[i] = i;
    var f = typeof(Dictionary<int, int>)
        .GetField("_entries", BindingFlags.NonPublic | BindingFlags.Instance);
    var entries = (Array?)f?.GetValue(d);
    int cap = entries?.Length ?? -1;
    if (cap != last)
    {
        Console.WriteLine($"Count={d.Count,3}  내부 용량={cap}");
        last = cap;
    }
}
```

> **⚠️ 내부 필드에 의존하는 코드를 제품에 넣지 마라**
>
> 위 코드는 **학습용 관찰 도구**다. `_entries` 같은 private 필드 이름은 계약이 아니며 어느 릴리스에서든 사라질 수 있다. 관찰이 끝나면 버려라. 제품 코드에서 컬렉션 용량이 중요하다면 답은 하나다 — **생성자에 초기 용량을 넘겨서 리사이즈 자체를 없애는 것**(24장, 69장).

|---|---|
| GC 알고리즘의 실제 구현 | `src/coreclr/gc/gc.cpp` (거대하다 — 83.2절의 진입 순서를 따르라) |
| GC 구성 스위치의 전체 목록과 기본값 | `src/coreclr/gc/gcconfig.h` |

> **📌 소스보다 `docs/design`을 먼저 열어라**
>
> Book of the Runtime(BOTR)은 CLR 서브시스템별 개관 문서 모음이고, 구현보다 훨씬 안정적이다. GC나 타입 로더처럼 코드가 수만 줄인 영역은 BOTR 문서를 먼저 읽고 들어가야 길을 잃지 않는다. 다만 일부 문서는 .NET Framework 시절에 쓰여 갱신이 늦었으므로, 문서 파일의 `git log`로 마지막 수정 시점을 확인하는 습관을 붙여라(83.5절).

> **⚠️ C++ 소스를 완벽히 읽으려 하지 마라**
>
> `gc.cpp` 한 파일이 수만 줄이다. 처음부터 끝까지 읽는 것은 목표가 아니며 가능하지도 않다. **질문 하나를 들고 들어가 답만 찾고 나오는 것**이 정상적인 사용법이다. 83.2절이 그 진입 순서를 다룬다.

## J.4 도구

각 도구는 **다른 층위**를 본다. 어느 층을 보고 싶은지가 정해지면 도구는 자동으로 정해진다.

| 층위 | 질문 | 도구 |
|---|---|---|
| 소스 → IL | 컴파일러가 무엇을 생성했나 | SharpLab, ILSpy, `ildasm` |
| IL → 기계어 | JIT이 무엇을 냈나 | `DOTNET_JitDisasm`, 디스어셈블리 뷰 |
| 실행 시간 | 얼마나 걸리나 | BenchmarkDotNet |
| 프로세스 전체 | 어디서 시간·메모리를 쓰나 | PerfView, `dotnet-trace`, `dotnet-counters` |
| 죽은 프로세스 | 무슨 상태에서 멈췄나 | `dotnet-dump` + SOS, WinDbg |
| 코드 자체 | 쓰기 전에 잡을 수 있나 | 분석기(analyzer) |

### 디컴파일러와 IL 뷰어

| 도구 | 성격 | 무엇을 배우러 쓰나 |
|---|---|---|
| **SharpLab** | 브라우저에서 바로 쓰는 웹 도구(이름으로 검색) | **가장 먼저 열 도구.** C# 코드를 붙여 넣으면 IL, 디컴파일된 C#(컴파일러가 생성한 것을 다시 C#으로), 그리고 JIT 어셈블리까지 한 화면에서 본다 |
| **ILSpy** (`icsharpcode/ILSpy`) | 데스크톱 앱 + 확장 | 이미 빌드된 어셈블리를 열어 볼 때. NuGet 패키지 안을 들여다볼 때 |
| **dotPeek** (JetBrains, 무료) | 데스크톱 앱 | ILSpy의 대안. 심볼 서버 기능이 쓸 만하다 |
| **`ildasm`** | 명령줄 | 스크립트로 IL을 뽑아 비교(diff)할 때. 원문 형식 그대로 필요할 때 |

**SharpLab 하나만 익혀도 이 책 1·2권의 절반을 검증할 수 있다.** "이 문법이 무엇으로 바뀌는가"라는 질문은 전부 여기서 30초 만에 답이 나온다 — `foreach`가 무엇으로 풀리는지, `async` 메서드의 상태 기계가 어떻게 생겼는지, 문자열 보간이 `string.Format`이 되는지 보간 핸들러가 되는지, `record`가 생성한 멤버가 무엇인지.

> **💡 SharpLab을 여는 순간을 습관으로 만들어라**
>
> 이 책의 "컴파일 결과" 단계 서술을 읽을 때마다 SharpLab을 열어 같은 코드를 넣어 보라. 두세 번 하고 나면 **책을 믿는 대신 확인하는 습관**이 붙고, 그것이 84장이 요구하는 상태다. 다만 SharpLab이 쓰는 컴파일러·런타임 버전은 자기 프로젝트와 다를 수 있으니, 버전이 중요한 판단이면 로컬 빌드로 다시 확인하라.

### 벤치마크와 프로파일러

| 도구 | 무엇을 배우러 쓰나 | 주의 |
|---|---|---|
| **BenchmarkDotNet** (`dotnet/BenchmarkDotNet`) | 마이크로 벤치마크의 사실상 표준. 워밍업·이상치·통계·다중 런타임 비교를 알아서 처리 | 릴리스 구성에서만. 죽은 코드 제거에 주의(67.4절) |
| **PerfView** (`microsoft/perfview`) | Windows에서 ETW 기반 전체 추적. CPU 스택, GC 이벤트, 할당 추적 | 학습 곡선이 가파르다. 부록 C에 조리법이 있다 |
| **`dotnet-trace`** | 크로스 플랫폼 추적 수집 | 수집만 한다. 분석은 PerfView나 다른 뷰어에서 |
| **`dotnet-counters`** | 실시간 카운터 관찰. 가장 가벼운 첫 진단 | 오버헤드가 낮아 프로덕션에서도 쓸 수 있다 |
| **`dotnet-dump`** + **SOS** | 덤프를 떠서 사후 분석. 힙 내용, 스레드 스택 | 부록 C의 SOS 명령 표 |
| **`dotnet-gcdump`** | 힙의 객체 그래프만 가볍게 | 누수 추적의 첫걸음 |
| **`dotnet-monitor`** (`dotnet/monitor`) | 컨테이너 환경에서 진단 데이터를 원격 수집 | 쿠버네티스 환경의 표준 접근 |
| **`dotnet/performance`** | 런타임 팀의 공식 벤치마크 스위트 | **읽는 용도.** 벤치마크를 어떻게 짜는지의 모범 |

> **📌 성능 작업의 도구 순서는 항상 같다**
>
> `dotnet-counters`로 **어디가 문제인지** 좁히고 → `dotnet-trace`/PerfView로 **누가 그러는지** 찾고 → BenchmarkDotNet으로 **고친 게 나아졌는지** 증명한다. 이 순서를 건너뛰고 BenchmarkDotNet부터 여는 것이 가장 흔한 시간 낭비다. 벤치마크는 **이미 범인을 알 때** 쓰는 도구다(67장).

### 분석기 — 쓰기 전에 잡는 층

분석기(analyzer)는 Roslyn 위에서 도는 규칙 엔진이고, 컴파일할 때마다 코드를 검사한다. **이 책이 서술한 함정의 상당수가 이미 규칙으로 존재한다.**

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>net8.0</TargetFramework>
    <Nullable>enable</Nullable>

    <!-- .NET 기본 분석기 켜기 (기본값은 SDK 버전에 따라 다르다) -->
    <EnableNETAnalyzers>true</EnableNETAnalyzers>
    <!-- 권장 수준 이상의 규칙까지 켠다 -->
    <AnalysisMode>Recommended</AnalysisMode>
    <!-- 경고를 오류로 승격 — CI에서 강제하려면 -->
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
  </PropertyGroup>
</Project>
```

개별 규칙의 심각도는 `.editorconfig`에서 조정한다.

```text
# .editorconfig
[*.cs]
# 예: 인스턴스 상태를 쓰지 않는 멤버를 static으로 (호출 비용)
dotnet_diagnostic.CA1822.severity = warning

# 예: 라이브러리 코드에서 ConfigureAwait 누락 잡기
dotnet_diagnostic.CA2007.severity = warning
```

| 분석기 계열 | 무엇을 배우러 쓰나 |
|---|---|
| **.NET 기본 분석기**(SDK에 내장, `CA` 규칙) | 성능·신뢰성·보안·API 설계의 표준 규칙. 규칙 문서 자체가 좋은 학습 자료다 |
| **`dotnet/roslyn-analyzers`** | 위 규칙들의 **구현 소스**. 규칙이 정확히 어떤 조건에 걸리는지 확인할 때 |
| **코드 스타일 규칙**(`IDE` 규칙) | 팀 스타일을 `.editorconfig`로 강제 |
| **직접 만든 분석기** | 팀의 관용구를 규칙으로 고정 — 리뷰에서 반복해 지적하는 것이 있다면 그것이 후보다 |

> **💡 분석기 경고는 무료 학습 자료다**
>
> 새 규칙이 경고를 뿜으면 끄기 전에 **규칙 ID로 문서를 한 번 읽어라.** 대부분은 이 책의 어느 절과 정확히 대응하고, 왜 그것이 문제인지 짧게 설명돼 있다. 규칙을 끌 때는 프로젝트 전체가 아니라 그 줄에서만 끄고 이유를 주석으로 남겨라.

### 회복 탄력성과 실무 라이브러리

**Polly**(`App-vNext/Polly`)는 재시도·회로 차단기·타임아웃·격벽 같은 회복 탄력성 정책을 조합하는 라이브러리다. 여기서 배울 것은 라이브러리 사용법 자체보다 **정책을 조합 가능한 객체로 표현하는 API 설계**다 — 78장(API 설계)의 관점으로 이 라이브러리의 공개 표면을 읽어 보면, 조합 가능성을 어떻게 타입으로 표현하는지의 좋은 사례가 된다.

## J.6 스스로 검증하는 습관

### 이 책도 낡는다

정직하게 말한다. **이 책의 서술 중 일부는 몇 년 안에 틀린 것이 된다.** 특히 다음 범주가 그렇다.

| 범주 | 왜 낡는가 | 확인 주기 |
|---|---|---|
| 성능 수치(부록 D) | 하드웨어와 런타임 최적화가 바뀐다 | 런타임 메이저 버전마다 |
| GC 기본값과 임계값(65장) | 기본 모드·동적 조정 정책이 바뀐다 | 런타임 메이저 버전마다 |
| JIT 최적화의 적용 조건(55장) | 인라이닝·PGO 휴리스틱이 계속 바뀐다 | 런타임 메이저 버전마다 |
| 컴파일러가 생성하는 코드(부록 A) | 낮추기 전략이 개선된다 | SDK 메이저 버전마다 |
| 언어 기능 목록(부록 H) | 매년 늘어난다 | 언어 버전마다 |
| 도구의 명령·옵션(부록 C) | 도구 릴리스마다 | 도구를 쓸 때마다 |

반대로 **잘 낡지 않는 것**도 있다. 값 타입과 참조 타입의 차이, 박싱의 원리, GC의 세대 가설, `async`의 상태 기계 구조, 동등성 계약, API 설계 원칙. 이 책이 원리 서술에 지면을 많이 쓴 이유가 그것이다.

### 세 가지 검증 도구, 세 가지 질문

| 질문 | 도구 | 절차 |
|---|---|---|
| **컴파일러가 정말 그렇게 바꾸나?** | SharpLab (또는 ILSpy) | 코드를 붙여 넣고 IL·디컴파일 결과를 본다. 30초 |
| **정말 더 빠른가?** | BenchmarkDotNet | 두 구현을 같은 벤치마크에 넣고 `MemoryDiagnoser`를 켠다. 10분 |
| **런타임이 정말 그렇게 하나?** | 소스 + 실행 관찰 | 소스에서 정책을 확인하고, 그 정책이 관찰되는 실험 코드를 짠다. 한두 시간 |

세 번째가 가장 비싸고 가장 확실하다. 그리고 세 번째를 할 줄 아는 것이 이 책이 목표한 상태다.

### 검증 루프의 형태

```text
   ┌──────────────────────────────────────────────┐
   │  주장을 만난다 (책·블로그·동료·이 책)            │
   └──────────────────┬───────────────────────────┘
                      ↓
   ┌──────────────────────────────────────────────┐
   │  어떤 종류의 주장인가?                          │
   └───┬──────────────┬──────────────┬────────────┘
       ↓              ↓              ↓
   문법·컴파일     성능 수치      런타임 동작
       ↓              ↓              ↓
   SharpLab      BenchmarkDotNet   소스 + 실험
       ↓              ↓              ↓
   ┌──────────────────────────────────────────────┐
   │  확인됨 → 조건을 함께 기록                      │
   │  (런타임 버전 · TFM · 하드웨어 · 측정 조건)       │
   └──────────────────────────────────────────────┘
```

**"확인됨"으로 끝내지 말고 조건을 함께 기록하라.** ".NET 8, x64, 서버 GC에서 A가 B보다 1.4배 빨랐다"와 "A가 B보다 빠르다"는 전혀 다른 문장이고, 후자는 6개월 뒤 틀린 조언이 된다. 부록 D 전체가 이 원칙 위에 쓰였다.

> **⚠️ 자기가 만든 벤치마크를 가장 의심하라**
>
> 남의 주장보다 자기 벤치마크가 더 자주 틀린다. 죽은 코드 제거, 워밍업 부족, 상수 접힘, 계층형 컴파일의 단계 차이, 첫 호출의 JIT 비용 — 전부 67.4절이 다룬 함정이고 전부 "내 쪽이 10배 빠르다"는 결과로 나타난다. **결과가 너무 좋으면 벤치마크를 의심하라**가 유일하게 안전한 반응이다.

> **💡 확인한 것을 기록으로 남겨라**
>
> 저장소에 `experiments/` 폴더 하나를 두고 확인한 실험을 코드째 남겨라. 6개월 뒤 런타임을 올릴 때 **같은 실험을 다시 돌려 결과가 바뀌었는지 보는 것**이 최신 상태를 유지하는 가장 저렴한 방법이다. 이것이 83.6절과 84장이 요구하는 습관의 실물이다.

### 84장과의 연결

84장은 "무엇을 아는가"를 점검하는 목록이고, 이 부록은 "모르는 것을 어떻게 알아내는가"의 목록이다. 둘은 짝이다.

84.8절의 심층 질문 100선을 풀다가 막히는 항목이 나오면, 그 순간이 이 부록을 쓸 때다. **질문 → 자료 등급 판단(J.1) → 1차 출처(J.2) → 소스 진입(J.3) → 도구로 확인(J.4·J.6)** 순으로 내려가면 대부분의 질문이 하루 안에 닫힌다. 닫히지 않는 질문은 아직 아무도 답을 모르는 질문이고, 그때는 이슈를 열 차례다(J.5의 갈래 D).

## J.7 이 책을 마치며

이 책은 84개 장과 열 개의 부록으로 여덟 권을 하나의 서술로 합쳤다. 그 서술의 목표는 처음부터 하나였다 — **문법에서 멈추지 않는 것.** 어떤 문법이 무엇으로 컴파일되고, 런타임이 그것을 어떻게 실행하며, 그래서 언제 비싸지는가. 이 4단을 매 주제마다 반복한 이유는 그 순서로 생각하는 사람만이 처음 보는 문제 앞에서 스스로 답을 만들 수 있기 때문이다.

그런 사람에게 이 책의 마지막 쓸모는 **더 이상 이 책이 필요하지 않게 만드는 것**이다. 어떤 주장을 만났을 때 SharpLab을 열고, 벤치마크를 짜고, 소스에 들어가 확인하는 사람은 책의 서술을 기다릴 필요가 없다. 그 상태가 이 책이 84장과 이 부록으로 끝나는 이유다.

C#은 계속 바뀐다. 새 문법이 매년 들어오고, GC의 기본값이 바뀌고, JIT이 어제 못 하던 최적화를 오늘 한다. 그 변화를 따라가는 방법은 이 책을 다시 사는 것이 아니라, 릴리스 노트를 자기 타입 이름으로 검색하고 설계 회의록을 읽고 소스를 여는 것이다. 자료는 낡지만 **1차 출처를 여는 습관은 낡지 않는다.**

여기까지 온 것을 축하한다. 다음 장은 없다.

## 이 부록의 요약

- **자료는 등급이 있다.** 소스와 명세가 1차, 설계 저장소와 `docs/design`이 그다음, 공식 문서가 2차, 책과 강연이 3차다. 이 책도 3차이고, 충돌하면 위쪽이 이긴다.

- **URL 대신 이름을 외워라.** 주소는 자료보다 빨리 낡는다. `dotnet` 조직의 `runtime`·`roslyn`·`csharplang`·`diagnostics`·`performance` 다섯 저장소 이름이면 대부분의 질문에 도달할 수 있다.

- **`dotnet/csharplang`의 회의록이 가장 저평가된 자료다.** 제안서는 "무엇"을, 회의록은 "왜"를 말한다. 채택되지 않은 대안과 그 이유를 읽는 것이 언어를 이해하는 가장 빠른 길이다.

- **공식 문서는 "무엇을·어떻게", 소스는 "실제로·왜·언제부터"에 답한다.** 이 경계를 알면 검색 시간이 절반으로 준다.

- **소스는 질문 하나를 들고 들어가 답만 찾고 나온다.** 파일 이름으로 좁히고, 기호로 찾고, 헬퍼로 한 단계 더 들어가고, 실행해서 확인한다. `docs/design`을 먼저 읽는 것이 길을 잃지 않는 유일한 방법이다.

- **도구는 층위별로 하나씩이면 충분하다.** 컴파일 결과는 SharpLab, 시간은 BenchmarkDotNet, 프로세스는 `dotnet-counters`와 PerfView, 사후 분석은 `dotnet-dump`와 SOS, 예방은 분석기.

- **성능 도구의 순서는 항상 좁히기 → 찾기 → 증명하기다.** BenchmarkDotNet부터 여는 것이 가장 흔한 시간 낭비다.

- **다음 6개월은 한 갈래만 골라라.** 내부·성능·설계·기여 중 하나. 넷을 동시에 하면 아무것도 남지 않는다.

- **이 책의 일부는 몇 년 안에 틀린 것이 된다.** 성능 수치, GC 기본값, JIT 조건, 생성 코드가 그 범주다. 원리는 오래 가고 수치는 낡는다.

- **확인한 것은 조건과 함께 기록하라.** "A가 B보다 빠르다"는 6개월 뒤 틀린 조언이 되고, ".NET 8, x64, 서버 GC에서 1.4배"는 재검증 가능한 사실로 남는다.

## 연습 문제

1. GitHub에서 `dotnet` 조직을 열고 J.2절 표의 저장소 여덟 개를 전부 찾아 즐겨찾기하라. 각 저장소의 README 첫 화면에서 **이 저장소가 무엇을 담는지** 한 문장으로 요약해 적어라.

2. `dotnet/csharplang`에서 최근 언어 버전의 기능 하나를 골라 제안서를 읽고, `meetings/`에서 그 기능이 논의된 회의록을 찾아라. **채택되지 않은 대안 하나**와 버려진 이유를 정리하라.

3. J.3절의 다섯 단계 절차를 그대로 따라 `List<T>`의 성장 정책을 소스에서 확인하고, 관찰 코드를 짜서 실제 용량 변화를 출력하라. 소스에서 읽은 정책과 관찰 결과가 일치하는가?

4. `src/coreclr/gc/gcconfig.h`를 열어 자기가 이름을 아는 GC 구성 스위치를 다섯 개 찾아라. 그중 이 책 65장에서 다루지 않은 것이 있는지 확인하고, 하나를 골라 `docs/design`에서 설명을 찾아라.

5. SharpLab에서 다음 다섯 가지를 각각 확인하라 — `foreach`가 배열과 `List<T>`에서 서로 다르게 풀리는가, `record`가 어떤 멤버를 생성하는가, `async` 메서드의 상태 기계 클래스는 구조체인가 클래스인가, 문자열 보간이 `string.Format`이 되는가 핸들러가 되는가, `switch` 식의 패턴이 어떤 분기로 낮춰지는가.

6. 자기 프로젝트에 `<AnalysisMode>Recommended</AnalysisMode>`를 켜고 나온 경고를 규칙 ID별로 집계하라. 상위 다섯 개 규칙의 문서를 읽고, 각각이 이 책의 어느 절과 대응하는지 적어라.

7. 최근 세 개 릴리스의 버전별 성능 개선 글을 자기 코드베이스에서 쓰는 타입 이름으로 검색하라. 해당하는 항목이 나오면 그 개선이 실제로 자기 코드에 나타나는지 벤치마크로 확인하라.

8. `experiments/` 폴더를 만들고, 이 책을 읽으며 확인하고 싶었던 주장 세 개를 실험 코드로 남겨라. 각 실험에 **런타임 버전·TFM·하드웨어·측정 조건**을 주석으로 기록하라. 다음 런타임 업그레이드 때 그대로 다시 돌린다.
