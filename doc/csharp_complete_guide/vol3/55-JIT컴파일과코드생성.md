# 55장. JIT 컴파일과 코드 생성

## 55.1 IL이 네이티브가 되는 시점 — 프리스텁과 백패칭

### 아무도 IL을 실행하지 않는다

가장 먼저 정리해야 할 오해가 있다. **CLR은 IL을 인터프리트하지 않는다.** 메서드를 실행하려면 그 메서드의 IL이 **반드시** 먼저 대상 CPU의 기계어로 번역되어야 한다. 이 번역을 하는 것이 CLR의 **JIT(just-in-time, 적시) 컴파일러**이고, CoreCLR의 현행 JIT 엔진 이름은 **RyuJIT**이다.

"just-in-time"의 의미는 **미리 하지 않는다**는 것이다. 어셈블리를 로드할 때 그 안의 모든 메서드를 컴파일하지 않는다. 프로그램이 실제로 호출하는 메서드만, 그것도 **처음 호출되는 그 순간에** 컴파일한다. 호출되지 않는 메서드는 영원히 컴파일되지 않는다.

```csharp
static void Main()
{
    Console.WriteLine("Hello");
    Console.WriteLine("Goodbye");
}

// 이 메서드는 아무도 호출하지 않는다.
// IL은 어셈블리에 들어 있지만 기계어로는 영원히 번역되지 않는다.
static void NeverCalled() => Console.WriteLine("?");
```

> **📌 IL은 무엇인가**
>
> IL은 마이크로소프트가 여러 상용·학계 언어/컴파일러 저자와 협의해 만든 **CPU 독립적인 기계어**다. 대부분의 CPU 기계어보다 훨씬 높은 수준이라, 객체 타입에 접근하고 조작하는 명령, 객체를 만들고 초기화하는 명령, 객체의 가상 메서드를 호출하는 명령, 배열 원소를 직접 다루는 명령을 갖는다. 예외를 던지고 잡는 명령까지 있다. **객체지향 기계어**라고 생각하면 된다. 스택 기반이고 타입이 없는(typeless) 명령 집합이라는 특성은 56.2절에서 자세히 본다.

### Richter의 그림 — 타입의 내부 자료구조와 JITCompiler

『CLR via C#』이 그리는 모델부터 보자. 이 모델은 개념적으로 정확하고, 실제 구현을 이해하는 출발점이다.

`Main`이 실행되기 **직전에**, CLR은 `Main`의 코드가 참조하는 모든 타입을 탐지한다. 그리고 각 타입마다 내부 자료구조를 하나씩 할당한다(54.1절에서 본 `MethodTable`이 바로 이것이다). 이 자료구조에는 그 타입이 정의한 **메서드마다 항목이 하나씩** 있고, 각 항목은 그 메서드의 구현이 있는 **주소**를 담는다.

문제는 아직 아무것도 컴파일되지 않았다는 것이다. 그래서 CLR은 이 구조를 초기화할 때 **모든 항목을 CLR 내부의 문서화되지 않은 함수 하나로 채운다.** Richter는 이 함수를 `JITCompiler`라고 부른다.

```text
[첫 번째 호출]

  관리 EXE                      Console 타입의 내부 자료구조
┌────────────────────────┐    ┌──────────────────────────────┐
│ static void Main() {   │    │ WriteLine()          ● ──────┼──┐
│   Console.WriteLine(   │    │ WriteLine(string)    ● ──────┼──┤
│     "Hello");          │───▶│ (나머지 멤버들)       ● ──────┼──┤
│   Console.WriteLine(   │    │ ...                          │  │
│     "Goodbye");        │    └──────────────────────────────┘  │
│ }                      │                                      │
└────────────────────────┘                                      ▼
                                              ┌───────────────────────────────────┐
                                              │ JITCompiler 함수 {                 │
                                              │  1. 타입(Console)을 구현한 어셈블리 │
                                              │     메타데이터에서 호출된 메서드     │
                                              │     (WriteLine)을 찾는다            │
                                              │  2. 메타데이터에서 그 메서드의 IL을  │
                                              │     얻는다                          │
                                              │  3. 메모리 블록을 할당한다           │
                                              │  4. IL을 네이티브 CPU 명령으로       │
                                              │     컴파일해 3의 메모리에 저장한다   │
                                              │  5. 타입 테이블의 그 메서드 항목이    │
                                              │     3의 메모리 블록을 가리키도록      │
                                              │     수정한다  ← 백패칭               │
                                              │  6. 그 메모리 블록의 네이티브 코드로  │
                                              │     점프한다                         │
                                              │ }                                   │
                                              └───────────────────────────────────┘
```

`Main`이 `WriteLine`을 처음 호출하면 `JITCompiler`가 호출된다. `JITCompiler`는 **어떤 메서드가 호출되었고 어떤 타입이 그 메서드를 정의하는지** 알고 있다. 정의 어셈블리의 메타데이터에서 IL을 찾아 검증하고 기계어로 컴파일한 다음, 동적으로 할당한 메모리 블록에 저장한다. 그리고 **타입의 내부 자료구조로 돌아가서, 자기를 호출했던 그 항목을 방금 컴파일한 기계어의 주소로 덮어쓴다.** 마지막으로 그 코드로 점프한다.

이 덮어쓰기가 **백패칭(backpatching)** 이다.

```text
[두 번째 호출]

  관리 EXE                      Console 타입의 내부 자료구조
┌────────────────────────┐    ┌──────────────────────────────┐
│ static void Main() {   │    │ WriteLine()          ● ──────┼──▶ JITCompiler
│   Console.WriteLine(   │    │ WriteLine(string)    ● ──────┼──┐
│     "Hello");          │───▶│ (나머지 멤버들)       ● ──────┼──┼─▶ JITCompiler
│   Console.WriteLine(   │    │ ...                          │  │
│     "Goodbye");        │    └──────────────────────────────┘  │
│ }                      │                                      ▼
└────────────────────────┘                          ┌────────────────────────┐
                                                    │ 네이티브 CPU 명령        │
                                                    │ (WriteLine(string)의     │
                                                    │  컴파일 결과)            │
                                                    └────────────────────────┘
```

두 번째 호출은 `JITCompiler`를 **완전히 건너뛰고** 곧바로 기계어 블록으로 간다. **성능 손실은 첫 호출 한 번뿐이다.**

> **📌 아키텍처마다 다른 코드가 나온다**
>
> x86 Windows나 WoW64에서 실행되면 JIT은 x86 명령을 만든다. x64 Windows에서 64비트 애플리케이션으로 실행되면 x64 명령을, ARM에서 실행되면 ARM 명령을 만든다. **같은 어셈블리 파일이 세 가지 다른 기계어가 된다.** 이것이 IL이 존재하는 이유의 절반이다.

### 실제 CoreCLR — `MethodDesc`, 프리코드, 프리스텁

Richter의 그림은 "타입 테이블의 항목을 덮어쓴다"고 요약한다. 실제 CoreCLR 구현은 여기에 **간접 층 하나**를 더 둔다. 그 층이 왜 필요한지가 이 절의 핵심이다.

CoreCLR에서 각 메서드는 `MethodDesc`라는 자료구조로 표현된다(54.1절의 `MethodTable` 슬롯 테이블이 가리키는 것이 결국 이것이다). `MethodDesc`는 **진입점(entry point)** 주소를 하나 갖는다. 이 주소가 "이 메서드를 호출하려면 여기로 점프하라"는 안정적인 주소다.

메서드가 아직 컴파일되지 않았을 때, 진입점은 **프리코드(precode)** 라는 작은 스텁을 가리킨다. x64에서 `FixupPrecode`는 대략 이렇게 생겼다.

```text
; FixupPrecode (개념적 형태)
        jmp     qword ptr [rip + <타깃 셀>]     ; 간접 점프
        ; 타깃 셀의 초기값 = ThePreStub 주소
```

프로그램이 이 메서드를 호출하면 프리코드가 **프리스텁(prestub, `ThePreStub`)** 으로 점프한다. 프리스텁은 다음을 한다.

1. 어떤 `MethodDesc`를 통해 들어왔는지 알아낸다.
2. 필요하면 타입 로딩·정적 생성자 실행 등 선행 작업을 한다.
3. **JIT을 호출해 IL을 기계어로 컴파일한다.**
4. `MethodDesc`의 진입점(정확히는 프리코드의 타깃 셀)을 방금 만든 기계어 주소로 **덮어쓴다.**
5. 그 코드로 점프한다.

```text
[1] 첫 호출 전

  호출 지점                  MethodDesc              프리코드                 프리스텁
┌────────────┐          ┌──────────────┐        ┌──────────────┐      ┌─────────────┐
│ call ●─────┼─────────▶│ 진입점 ●─────┼───────▶│ jmp [cell]   │─────▶│ ThePreStub  │
└────────────┘          │ IL RVA       │        │ cell = 프리스텁│      │  → JIT 호출 │
                        │ 플래그       │        └──────────────┘      └──────┬──────┘
                        └──────────────┘                                     │
                                                                             │ JIT
[2] 컴파일 직후 (백패칭)                                                      ▼
                                                                     ┌──────────────┐
  호출 지점                  프리코드                                  │ 네이티브 코드 │
┌────────────┐          ┌──────────────┐                             │ push rbp     │
│ call ●─────┼─────────▶│ jmp [cell]   │────────────────────────────▶│ ...          │
└────────────┘          │ cell = 코드!  │  ← 이 한 워드만 덮어쓴다      │ ret          │
                        └──────────────┘                             └──────────────┘
```

**왜 간접 층을 두는가.** Richter의 그림대로 호출 지점(`call` 명령의 피연산자)을 직접 고치려면, 이 메서드를 호출하는 **모든 코드 위치**를 알고 있어야 한다. 그건 불가능하다. 대신 프리코드가 **불변의 안정 주소**를 제공하면, 호출 지점은 전부 그 주소를 가리키게 두고 **프리코드 안의 워드 하나만** 고치면 된다. 백패칭이 한 곳에서 끝난다.

이 설계는 뒤에서 볼 **계층형 컴파일**의 전제 조건이기도 하다. Tier-0 코드를 Tier-1 코드로 갈아끼우려면 "이미 컴파일된 수많은 호출 지점"을 다시 손대지 않고도 목적지를 바꿀 수 있어야 한다.

> **⚠️ 가상 호출은 백패칭 대상이 하나 더 있다**
>
> 가상 메서드는 `MethodTable`의 **슬롯**에도 진입점이 복사되어 있다(54.1절). 그래서 백패칭은 프리코드 셀뿐 아니라 파생 타입들의 슬롯까지 갱신해야 한다. CoreCLR은 이 작업을 "entry point backpatching"이라는 별도 메커니즘으로 처리하며, 슬롯 백패칭이 필요한 메서드는 그렇지 않은 메서드보다 계층 승격 비용이 조금 더 크다. 인터페이스 호출은 또 다른 경로 — **가상 스텁 디스패치(VSD)** — 를 쓰며, 여기서도 스텁이 단형(monomorphic) 캐시로 백패칭된다.

### 컴파일 결과는 프로세스와 함께 사라진다

JIT이 만든 기계어는 **동적 메모리**에 저장된다. 그 결과 세 가지가 따라온다.

- 애플리케이션이 끝나면 컴파일 결과는 **버려진다.**
- 같은 애플리케이션을 다시 실행하면 **처음부터 다시 컴파일한다.**
- 같은 애플리케이션을 두 개의 OS 프로세스로 동시에 실행하면 **각각 따로 컴파일한다.** 네이티브 애플리케이션이 읽기 전용 코드 페이지를 프로세스 간에 공유하는 것과 대비된다.

이것이 메모리 소비를 상당히 늘릴 수 있다. 55.7절에서 볼 ReadyToRun과 Native AOT가 존재하는 이유가 바로 이 세 줄이다.

> **📌 대부분의 애플리케이션에서 JIT 비용은 문제가 아니다**
>
> 대부분의 애플리케이션은 **같은 메서드를 반복해서 호출한다.** 그 메서드들은 실행 중 딱 한 번만 컴파일 비용을 치른다. 게다가 메서드를 호출하는 시간보다 메서드 **안에서** 보내는 시간이 더 긴 것이 보통이다. 서버 애플리케이션에서는 첫 요청만 느리고 이후 요청은 전속력으로 돈다.

### 관리 코드가 네이티브 코드보다 빠를 수 있는 이유

C/C++ 배경에서 오면 "실행 시점에 컴파일을 또 한다니 손해 아닌가" 하는 의심이 든다. 실제로 두 번째 컴파일 단계는 성능에 손해이고 동적 메모리를 할당한다. 하지만 JIT은 **네이티브 컴파일러가 알 수 없는 것을 안다.**

- JIT은 **실행 중인 CPU가 무엇인지 안다.** 그 CPU가 제공하는 특수 명령을 활용하는 코드를 낼 수 있다. 비관리 애플리케이션은 보통 최소 공통 분모 CPU를 대상으로 컴파일하고 특수 명령을 피한다.
- JIT은 **특정 검사가 이 머신에서 항상 거짓이라는 것을 안다.** 예를 들어 다음 코드는 CPU가 하나뿐인 머신에서 아무 명령도 생성하지 않을 수 있다.

  ```csharp
  if (numberOfCPUs > 1) {
      // ...
  }
  ```

- **런타임이 코드 실행을 프로파일링해서 실행 중에 IL을 다시 컴파일할 수 있다.** 관찰된 실행 패턴에 따라 분기 예측 실패를 줄이도록 재구성할 수 있다.

Richter가 2012년에 쓴 이 책에서 세 번째 항목에는 "현재 버전의 CLR은 이것을 하지 않지만 미래 버전은 할지도 모른다"는 단서가 붙어 있었다. **그 미래가 왔다.** 계층형 컴파일과 동적 PGO가 정확히 그것이고, 이 장의 55.2절부터 55.5절이 그 이야기다.

### 컴파일러 스위치와 코드 품질

C# 컴파일러 스위치 두 개가 코드 품질에 영향을 준다. `/optimize`(SDK 프로젝트의 `<Optimize>`)와 `/debug`(`<DebugType>`)다.

| 컴파일러 스위치 조합 | C# IL 코드 품질 | JIT 네이티브 코드 품질 |
|---|---|---|
| `/optimize-` `/debug-` (기본값) | 최적화 안 됨 | 최적화됨 |
| `/optimize-` `/debug(+/full/pdbonly)` | 최적화 안 됨 | **최적화 안 됨** |
| `/optimize+` `/debug(-/+/full/pdbonly)` | 최적화됨 | 최적화됨 |

`/optimize-`로 만든 IL에는 **`nop` 명령과 바로 다음 줄로 점프하는 분기**가 잔뜩 들어 있다. Visual Studio의 편집 후 계속하기 기능과, `for`·`while`·`do`·`if`·`else`·`try`·`catch`·`finally` 같은 제어 흐름 문장에 중단점을 걸 수 있게 하기 위한 것이다. `/optimize+`는 이 잉여 명령을 제거한다. IL이 작아져 EXE/DLL 파일이 작아지고, IL을 직접 읽기도 편해진다. 대신 디버거에서 한 줄씩 따라가기 어려워지고 일부 함수 평가가 동작하지 않는다.

두 번째 행이 중요하다. **`/debug:full`은 JIT에게 "이 어셈블리를 디버깅할 생각이다"라고 알리고, JIT은 최적화를 끄고 IL 명령과 네이티브 코드의 대응 관계를 추적한다.** 이 정보 덕분에 Visual Studio의 JIT 디버거로 이미 실행 중인 프로세스에 붙어 쉽게 디버깅할 수 있다.

> **⚠️ Debug 빌드에서 잰 성능 수치는 전부 무의미하다**
>
> SDK 스타일 프로젝트의 Debug 구성은 `<Optimize>false</Optimize>`이고, 컴파일러는 어셈블리에 `[assembly: Debuggable(DebuggableAttribute.DebuggingModes.DisableOptimizations | ...)]`를 방출한다. **JIT은 이 특성을 보고 그 모듈의 모든 메서드에 대해 최적화를 끈다.** 인라이닝도, 경계 검사 제거도, 레지스터 할당 최적화도 없다. Debug 빌드에서 잰 수치는 Release 빌드의 성능과 아무 관계가 없다. BenchmarkDotNet이 Debug 어셈블리를 감지하면 경고를 띄우고 실행을 거부하는 이유다(67.3절).
>
> Visual Studio 디버거로 프로세스를 시작하면 `/debug` 설정과 무관하게 JIT이 IL↔네이티브 매핑을 추적하도록 강제된다. **모듈 로드 시 JIT 최적화 비활성화(관리 전용)** 옵션을 꺼야 이 강제가 풀린다.

### 검증(verification)은 어디로 갔나

『CLR via C#』은 JIT이 IL을 기계어로 컴파일하는 동안 **검증(verification)** 을 수행한다고 설명한다. 모든 메서드가 올바른 개수의 매개변수로 호출되는지, 각 매개변수의 타입이 맞는지, 반환값이 제대로 쓰이는지 등을 확인하는 과정이다. 관리 모듈의 메타데이터가 이 검증에 쓰이는 모든 메서드·타입 정보를 담고 있다.

검증의 원래 목적은 **한 Windows 가상 주소 공간에서 여러 관리 애플리케이션을 안전하게 실행하는 것**이었다. 코드가 메모리를 부적절하게 건드리지 않는다는 것이 검증으로 보장되면, 프로세스를 분리하지 않아도 서로를 망가뜨리지 않는다. .NET Framework의 AppDomain과 부분 신뢰(partial trust) 모델이 이 위에 서 있었다.

> **⚠️ .NET Core / .NET 5+ 에는 IL 검증이 없다**
>
> 부분 신뢰와 코드 접근 보안(CAS)이 .NET Core에서 제거되면서 **런타임의 IL 검증도 함께 사라졌다.** 모든 코드가 완전 신뢰로 실행된다. `PEVerify.exe`는 .NET Framework 전용 도구이고, .NET에서는 별도 도구인 **`ILVerify`** 를 빌드 파이프라인에서 따로 돌려야 한다.
>
> 그렇다고 아무 IL이나 통과하는 것은 아니다. JIT은 여전히 구조적으로 말이 안 되는 IL(스택 깊이 불일치, 존재하지 않는 토큰 참조 등)을 만나면 **`InvalidProgramException`** 을 던진다. 58장에서 `Reflection.Emit`으로 IL을 직접 만들 때 가장 자주 보게 될 예외다. 반면 `VerificationException`은 타입에는 존재하지만 현대 CoreCLR의 JIT이 검증 실패를 이유로 던지는 일은 사실상 없다.
>
> .NET Framework에서는 달랐다. `unsafe` 코드를 JIT이 만나면 어셈블리에 `SecurityPermissionFlag.SkipVerification`이 부여되었는지 확인하고, 없으면 `InvalidProgramException` 또는 `VerificationException`을 던져 메서드 실행을 막았다.

### 시작 시 JIT 부하를 줄이는 오래된 무기

`System.Runtime.ProfileOptimization` 클래스는 애플리케이션 실행 중 **어떤 메서드가 JIT 컴파일되는지를 파일에 기록**한다. 다음번 시작 때 JIT은 멀티코어 머신에서 **다른 스레드를 써서 이 메서드들을 미리 병렬로 컴파일한다.** 사용자가 애플리케이션과 상호작용하는 동안 하나씩 컴파일하는 대신, 초기화 중에 여러 메서드를 동시에 컴파일하므로 시작이 빨라진다.

```csharp
// 애플리케이션 시작 지점의 아주 앞에서
System.Runtime.ProfileOptimization.SetProfileRoot(
    Path.Combine(AppContext.BaseDirectory, "profile"));
System.Runtime.ProfileOptimization.StartProfile("startup.profile");
```

이 기능은 흔히 **멀티코어 JIT**이라고 불린다. 호스트나 프레임워크가 이것을 대신 켜 주는지는 버전마다 다르므로, 쓸 생각이라면 해당 호스트 문서에서 확인해야 한다. 직접 쓸 일은 데스크톱 애플리케이션의 시작 시간을 다듬을 때 정도다.

> **💡 JIT 비용을 눈으로 확인하는 가장 빠른 방법**
>
> ```text
> dotnet-counters monitor --process-id <PID> --counters System.Runtime
> ```
>
> `Time spent in JIT (ms / 1 sec)`와 `IL Bytes Jitted`, `Number of Methods Jitted` 세 카운터를 보면 된다. 시작 직후 급등했다가 몇 초 안에 0 근처로 떨어지는 것이 정상이다. **정상 상태에서도 JIT 시간이 계속 높게 유지된다면** 어딘가에서 동적 코드 생성(식 트리 컴파일, `Reflection.Emit`, 정규식 `RegexOptions.Compiled`)을 반복 호출하고 있다는 뜻이다. 57.13절의 델리게이트 캐싱이 필요한 상황이다.

## 55.2 계층형 컴파일(Tiered Compilation)과 Tier-1 승격 조건

### 하나의 컴파일러가 두 가지 상반된 요구를 받는다

55.1절의 모델에는 근본적인 긴장이 있다. JIT은 메서드가 처음 호출되는 **바로 그 순간** 코드를 내놓아야 한다. 사용자가 기다리고 있다. 그런데 좋은 코드를 만들려면 시간이 든다 — 인라이닝 후보를 평가하고, 루프를 분석하고, 레지스터를 할당하고, 경계 검사를 지울 수 있는지 증명해야 한다.

- **시작 시간**을 위해서는 컴파일이 빨라야 한다 → 최적화를 적게 해야 한다.
- **정상 상태 처리량**을 위해서는 코드가 좋아야 한다 → 최적화를 많이 해야 한다.

한 번만 컴파일한다면 둘 중 하나를 포기해야 한다. .NET Core 3.0부터 기본으로 켜진 **계층형 컴파일(tiered compilation)** 은 이 딜레마를 **두 번 컴파일**해서 푼다. ※.NET Core 2.1에서 옵트인으로 도입되었고 .NET Core 3.0부터 기본값이다.

| | **Tier-0** | **Tier-1** |
|---|---|---|
| 다른 이름 | Quick JIT, MinOpts | Fully optimized, FullOpts |
| 언제 만들어지나 | 메서드 첫 호출 시 | 메서드가 "뜨겁다"고 판정된 후 백그라운드에서 |
| 컴파일 속도 | 매우 빠름 | 느림 |
| 인라이닝 | 사실상 하지 않음 | 적극적으로 함 |
| 경계 검사 제거 | 하지 않음 | 함 |
| 레지스터 할당 | 거의 안 함 (지역 변수는 스택) | 함 |
| 스택 프레임 | `rbp` 기반 | 대개 `rsp` 기반, 프레임 포인터 생략 |
| 프로파일 계측 | 상황에 따라 있음 | 없음 |
| 실행 속도 | 느림 (수 배까지) | 빠름 |

핵심 통찰은 이것이다. **대부분의 메서드는 몇 번밖에 호출되지 않는다.** 애플리케이션 시작 경로에서 한 번 돌고 마는 초기화 코드에 최적화 시간을 쓰는 것은 낭비다. 반면 뜨거운 루프 안에서 수백만 번 호출되는 메서드는 아무리 오래 걸려도 최적화할 가치가 있다. 계층형 컴파일은 **어느 쪽인지 실행해 보고 나서** 결정한다.

### 승격 흐름

```text
                        메서드 첫 호출
                              │
                              ▼
                ┌─────────────────────────────┐
                │  프리스텁 → JIT (Tier-0)      │
                │  빠르게, 최적화 없이 컴파일    │
                └──────────────┬──────────────┘
                               │
                               ▼
                ┌─────────────────────────────┐
                │  호출 계수 스텁(call counting │◀────┐
                │  stub)을 진입점에 설치        │     │
                │  카운터 = 30 (기본값)         │     │ 매 호출마다
                └──────────────┬──────────────┘     │ 카운터 감소
                               │                     │
                        카운터 == 0 ?  ──── 아니오 ───┘
                               │ 예
                               ▼
                ┌─────────────────────────────┐
                │  호출 계수 지연(delay) 중인가? │
                │  (기본 100ms, 새 Tier-0       │─── 예 ──▶ 타이머 재시작
                │   메서드가 나올 때마다 리셋)   │           (아직 시작 중이다)
                └──────────────┬──────────────┘
                               │ 아니오
                               ▼
                ┌─────────────────────────────┐
                │  계층화 백그라운드 워커 큐에    │
                │  등록                        │
                └──────────────┬──────────────┘
                               │
                               ▼           (별도 스레드. 호출자는 기다리지 않는다)
                ┌─────────────────────────────┐
                │  JIT (Tier-1) — 완전 최적화   │
                └──────────────┬──────────────┘
                               │
                               ▼
                ┌─────────────────────────────┐
                │  진입점 백패칭                │
                │  · 프리코드 셀 갱신           │
                │  · 가상 슬롯 갱신             │
                └──────────────┬──────────────┘
                               │
                               ▼
                    이후 호출은 Tier-1 코드로
```

세 가지를 짚어야 한다.

**첫째, 승격은 동기적이지 않다.** 카운터가 0이 되는 그 호출이 멈춰 서서 Tier-1 컴파일을 기다리지 않는다. 백그라운드 스레드가 컴파일하고, 끝나면 진입점을 갈아끼운다. 그 사이의 호출은 계속 Tier-0 코드로 간다.

**둘째, 이미 실행 중인 호출은 갈아끼워지지 않는다.** 백패칭은 **다음 호출**부터 효과가 있다. 이미 스택 프레임 위에서 돌고 있는 Tier-0 코드는 그대로 끝까지 Tier-0으로 실행된다. 이것이 55.3절 OSR이 존재해야 하는 이유다.

**셋째, "호출 30회"는 절반의 진실이다.** 임계값 자체는 `TC_CallCountThreshold`의 기본값 30이 맞다. 그러나 **호출 계수 지연(call counting delay)** 이 함께 작동한다. 새로운 Tier-0 메서드가 컴파일될 때마다 100밀리초짜리 타이머가 리셋되고, 그동안은 호출 계수 자체가 시작되지 않는다. "아직도 새 메서드가 계속 나오고 있다 = 아직 시작 단계다 = 지금 승격해 봐야 소용없다"는 판단이다. 애플리케이션이 안정되어 100ms 동안 새 Tier-0 메서드가 나오지 않으면 비로소 계수가 시작된다.

> **⚠️ "30번 호출하면 Tier-1이 된다"고 벤치마크를 짜면 틀린다**
>
> 위 지연 때문에 실제 승격 시점은 예측할 수 없다. 게다가 승격이 큐에 등록된 뒤 실제 컴파일이 끝나고 백패칭이 완료되는 시점도 비결정적이다. 워밍업 없이 잰 수치가 실행마다 크게 흔들리는 주된 이유가 이것이다. BenchmarkDotNet이 워밍업 반복을 자동으로 넣고 `[SimpleJob]`의 반복 수를 조정하는 것은 정확히 이 계층 전이를 밀어내기 위해서다(67.4절).

### 제어 스위치

계층형 컴파일과 관련된 설정은 세 경로로 줄 수 있다. 우선순위는 환경 변수 > `runtimeconfig.json` > 프로젝트 파일 순이 아니라, 프로젝트 파일 설정이 `runtimeconfig.json`으로 방출되고 환경 변수가 그것을 덮어쓰는 구조다.

**프로젝트 파일(`.csproj`)**

```xml
<PropertyGroup>
  <TieredCompilation>true</TieredCompilation>
  <TieredCompilationQuickJit>true</TieredCompilationQuickJit>
  <TieredCompilationQuickJitForLoops>true</TieredCompilationQuickJitForLoops>
  <TieredPGO>true</TieredPGO>
</PropertyGroup>
```

**`runtimeconfig.json`** (위 설정이 빌드 시 이렇게 방출된다)

```json
{
  "runtimeOptions": {
    "configProperties": {
      "System.Runtime.TieredCompilation": true,
      "System.Runtime.TieredCompilation.QuickJit": true,
      "System.Runtime.TieredCompilation.QuickJitForLoops": true,
      "System.Runtime.TieredPGO": true
    }
  }
}
```

**환경 변수**

| 환경 변수 | 기본값 | 효과 |
|---|---|---|
| `DOTNET_TieredCompilation` | `1` | `0`이면 계층화를 끄고 모든 메서드를 처음부터 완전 최적화로 컴파일 |
| `DOTNET_TC_QuickJit` | `1` | `0`이면 Tier-0(Quick JIT)을 쓰지 않는다 |
| `DOTNET_TC_QuickJitForLoops` | `1` (※.NET 7+) | 루프를 가진 메서드도 Tier-0으로 컴파일할지. .NET 6 이하 기본값은 `0` |
| `DOTNET_TC_CallCountThreshold` | `1E` (16진수, = 30) | Tier-1 승격 호출 횟수 |
| `DOTNET_TC_CallCountingDelayMs` | `64` (16진수, = 100) | 호출 계수 지연 밀리초 |
| `DOTNET_TieredPGO` | `1` (※.NET 8+) | 동적 PGO 계측. .NET 6/7에서는 기본 `0` |
| `DOTNET_ReadyToRun` | `1` | `0`이면 R2R 네이티브 코드를 무시하고 전부 JIT |
| `DOTNET_JitObjectStackAllocation` | 버전에 따라 다름 | 이스케이프 분석 기반 객체 스택 할당. **.NET 8 시점에는 기본 비활성화**이고 `1`로 켜야 했다. 이후 버전의 기본값은 해당 릴리스 문서에서 확인하라 |

> **⚠️ 접두사 — `DOTNET_`과 `COMPlus_`**
>
> 위 변수들은 원래 `COMPlus_` 접두사를 썼다(`COMPlus_TieredCompilation`). **.NET 6부터 `DOTNET_` 접두사가 공식이 되었고, `COMPlus_`도 여전히 인식된다.** 새 코드에는 `DOTNET_`을 쓰되, 인터넷의 오래된 문서·이슈·블로그는 대부분 `COMPlus_`로 되어 있으니 둘을 같은 것으로 읽어야 한다.
>
> **.NET Framework에서는 `COMPlus_`만 통한다.** `DOTNET_` 접두사는 .NET Framework의 CLR이 알지 못한다. 그리고 애초에 .NET Framework에는 계층형 컴파일 자체가 없다.
>
> 숫자 값은 **16진수로 해석된다.** `DOTNET_TC_CallCountThreshold=100`이라고 쓰면 100이 아니라 256이다.
>
> 그리고 더 중요한 것 — **이 변수들은 런타임 내부의 진단·실험용 스위치이지 공개 API가 아니다.** 이름도, 기본값도, 존재 여부도 릴리스마다 바뀔 수 있고 공식 문서에 전부 실려 있지도 않다. 조사와 실험에 쓰는 것은 좋지만 **운영 환경의 구성으로 굳히지 마라.** 제품 코드에서 동작을 고정해야 한다면 `runtimeconfig.json`이나 프로젝트 속성처럼 문서화된 경로를 쓰고, 쓰기 전에 자신이 쓰는 .NET 버전의 문서에서 이름과 의미를 확인하라.

```text
# Linux/macOS — 계층화를 끄고 실행
DOTNET_TieredCompilation=0 dotnet run -c Release

# Windows (cmd)
set DOTNET_TieredCompilation=0
dotnet run -c Release
```

### 같은 메서드, 두 개의 기계어

계층 차이를 눈으로 보는 것이 가장 빠르다. 다음 메서드를 보자.

```csharp
static int Sum(int[] data)
{
    int total = 0;
    for (int i = 0; i < data.Length; i++)
        total += data[i];
    return total;
}
```

Tier-0 코드다. `DOTNET_JitDisasm=Sum`으로 뽑은 출력의 **형태**를 옮겼다(뽑는 법은 55.8절에서 다룬다).

> **⚠️ 이 장의 디스어셈블리 리스팅은 전부 "예시"다**
>
> 이 장에 실린 x64 리스팅은 형태를 보여주기 위한 것이다. **레지스터 배정, 블록 이름(`G_M…_IG…`), 주소 상수, 명령 순서, 코드 크기는 .NET 버전·CPU·운영체제·PGO 프로파일에 따라 전부 달라진다.** 같은 코드를 자기 머신에서 뽑으면 다른 출력이 나오는 것이 정상이다. 읽어야 할 것은 개별 명령이 아니라 **패턴**이다 — 경계 검사가 있는가 없는가, `call`이 남았는가 사라졌는가, 지역 변수가 레지스터인가 스택인가.


```text
; Assembly listing for method Program:Sum(int[]):int (Tier0)
; Emitting BLENDED_CODE for X64 CPU with AVX2 - Windows
; Tier0 code
; rbp based frame
; partially interruptible

G_M000_IG01:
       push     rbp
       sub      rsp, 32
       lea      rbp, [rsp+0x20]
       mov      qword ptr [rbp+0x10], rcx      ; data 인수를 스택에 저장

G_M000_IG02:
       xor      eax, eax
       mov      dword ptr [rbp-0x04], eax      ; total = 0        ← 스택
       xor      eax, eax
       mov      dword ptr [rbp-0x08], eax      ; i = 0            ← 스택
       jmp      SHORT G_M000_IG04

G_M000_IG03:
       mov      rax, qword ptr [rbp+0x10]      ; data 다시 읽기
       mov      edx, dword ptr [rbp-0x08]      ; i 다시 읽기
       cmp      edx, dword ptr [rax+0x08]      ; i vs data.Length ← 경계 검사
       jae      SHORT G_M000_IG06
       mov      edx, dword ptr [rax+rdx*4+0x10]
       add      dword ptr [rbp-0x04], edx      ; total += ...     ← 스택 갱신
       mov      eax, dword ptr [rbp-0x08]
       inc      eax
       mov      dword ptr [rbp-0x08], eax      ; i++              ← 스택 갱신

G_M000_IG04:
       mov      eax, dword ptr [rbp-0x08]
       mov      rdx, qword ptr [rbp+0x10]
       cmp      eax, dword ptr [rdx+0x08]      ; Length 매 반복 재로드
       jl       SHORT G_M000_IG03

G_M000_IG05:
       mov      eax, dword ptr [rbp-0x04]
       add      rsp, 32
       pop      rbp
       ret

G_M000_IG06:
       call     CORINFO_HELP_RNGCHKFAIL        ; 범위 초과 → 예외
       int3
```

읽어야 할 것은 네 가지다.

1. **`total`과 `i`가 레지스터가 아니라 스택에 있다.** 반복마다 읽고 쓴다. Tier-0은 레지스터 할당을 거의 하지 않는다.
2. **`data.Length`를 반복마다 다시 읽는다** (`mov rdx, [rbp+0x10]` → `cmp eax, [rdx+8]`).
3. **경계 검사가 살아 있다** (`cmp` / `jae` / `CORINFO_HELP_RNGCHKFAIL`).
4. **`rbp` 기반 프레임**이다. 디버깅과 스택 워크는 쉽지만 명령이 늘어난다.

같은 메서드의 Tier-1 코드다.

```text
; Assembly listing for method Program:Sum(int[]):int (Tier1)
; Emitting BLENDED_CODE for X64 CPU with AVX2 - Windows
; Tier1 code
; optimized code
; rsp based frame
; fully interruptible

G_M000_IG01:

G_M000_IG02:
       xor      eax, eax                       ; total → eax
       xor      edx, edx                       ; i     → edx
       mov      r8d, dword ptr [rcx+0x08]      ; len = data.Length  ← 루프 밖으로
       test     r8d, r8d
       jle      SHORT G_M000_IG04

G_M000_IG03:
       mov      r10d, edx
       add      eax, dword ptr [rcx+r10*4+0x10]  ; 경계 검사 없음
       inc      edx
       cmp      r8d, edx
       jg       SHORT G_M000_IG03

G_M000_IG04:
       ret

; Total bytes of code 33
```

- 프롤로그·에필로그가 **사라졌다.** 스택 프레임을 만들 필요가 없다.
- `total`, `i`, `len`이 전부 **레지스터**에 있다.
- `data.Length`가 **루프 밖으로 끌어올려졌다**(loop hoisting).
- **경계 검사가 완전히 사라졌다.** `CORINFO_HELP_RNGCHKFAIL`로 가는 분기가 없다. 이유는 55.6절에서 판다.
- 루프가 **뒤집혀서**(loop inversion) 조건 검사가 루프 끝으로 갔다. 반복마다 점프 하나가 줄어든다.

> **📌 `; Total bytes of code`**
>
> JIT 디스어셈블리의 마지막 줄에 나오는 이 숫자가 그 메서드의 기계어 크기다. 같은 메서드의 Tier-0/Tier-1 크기를 비교하면 최적화 강도를 짐작할 수 있다. 위 Tier-1 리스팅의 33바이트가 그 예다(Tier-0 코드는 같은 메서드라도 훨씬 길다). **다만 Tier-1이 항상 더 작은 것은 아니다** — 인라이닝이 개입하면 훨씬 커지는 것이 보통이다.

### 계층화를 꺼야 하는 경우

기본값을 바꿀 이유는 많지 않지만, 세 가지 상황이 있다.

| 상황 | 조치 | 이유 |
|---|---|---|
| 마이크로벤치마크에서 안정된 수치가 필요 | BenchmarkDotNet에 맡긴다 | 워밍업으로 처리되므로 계층화를 끌 필요가 없다 |
| 짧게 실행되고 끝나는 계산 집약 CLI 도구 | `DOTNET_TieredCompilation=0` 검토 | Tier-1 승격 전에 프로그램이 끝나 버린다 |
| 지연 시간 스파이크가 SLA를 깬다 | R2R + 워밍업 요청(55.7절) | 계층 전이 자체가 아니라 첫 JIT이 원인인 경우가 많다 |
| 특정 메서드만 처음부터 최적화 | `[MethodImpl(MethodImplOptions.AggressiveOptimization)]` | 그 메서드만 계층화를 건너뛴다 |

> **⚠️ `AggressiveOptimization`은 동적 PGO를 포기하는 것이다**
>
> `[MethodImpl(MethodImplOptions.AggressiveOptimization)]`이 붙은 메서드는 **첫 호출부터 완전 최적화 계층으로 컴파일되고, 다시는 재컴파일되지 않는다.** 계층 전이를 기다리지 않아도 되니 좋아 보인다.
>
> 그런데 재컴파일되지 않는다는 것은 **동적 PGO의 프로파일 정보를 절대 받지 못한다**는 뜻이다(55.5절). 가드된 역가상화도, 프로파일 기반 블록 재배치도 적용되지 않는다. 게다가 이 메서드는 **ReadyToRun 이미지의 사전 컴파일 코드도 사용하지 않는다** — 항상 런타임에 JIT된다. 인터페이스 호출이 많은 코드에 이 특성을 붙이면 .NET 8 이후에는 오히려 **느려질 수 있다.**
>
> 정말 필요한 곳은 "호출 횟수는 적은데 한 번 들어가면 아주 오래 도는 순수 계산 루프"뿐이고, 그마저도 .NET 7의 OSR이 대부분 해결했다. **측정 없이 붙이지 마라.**

> **💡 계층화를 끄는 것과 `AggressiveOptimization`을 뿌리는 것은 다르다**
>
> `DOTNET_TieredCompilation=0`은 **여전히 R2R 코드를 사용하고**, 계층화만 끈다. 반면 `AggressiveOptimization`은 R2R까지 무시한다. 시작 시간에 민감한 애플리케이션에서 후자를 남발하면 시작이 눈에 띄게 느려진다.

## 55.3 OSR(On-Stack Replacement) — 긴 루프의 재컴파일 ※.NET 7+

### 계층형 컴파일이 남긴 구멍

55.2절의 승격 메커니즘에는 명백한 구멍이 있다. **승격은 "다음 호출"부터 효과가 있다.** 그렇다면 다음 호출이 없는 메서드는 어떻게 되는가?

```csharp
static long Sum()
{
    long total = 0;
    for (int i = 0; i < 2_000_000_000; i++)
        total += i;
    return total;         // 이 메서드는 딱 한 번 호출된다
}
```

이 메서드는 한 번 호출되고 20억 번 반복한다. 호출 횟수는 1이므로 임계값 30에 영원히 도달하지 못한다. 설령 도달한들 이미 스택 위에서 돌고 있는 Tier-0 프레임은 교체되지 않는다. **결과적으로 이 루프 전체가 Tier-0 코드로 실행된다** — 레지스터 할당도 없고 경계 검사도 그대로인 코드로.

.NET Core 3.0 ~ .NET 6은 이 문제를 **회피**로 해결했다. `TC_QuickJitForLoops`의 기본값을 `0`으로 두어, **루프(정확히는 역방향 분기)를 가진 메서드는 Tier-0을 건너뛰고 처음부터 완전 최적화로 컴파일**했다.

> **⚠️ 회피책의 대가 — .NET 6 이하에서 `foreach`가 든 메서드는 Tier-0을 못 받는다**
>
> "루프가 있으면 처음부터 최적화"는 안전하지만 비싸다. `foreach` 한 줄, `while` 한 줄이 들어간 초기화 메서드도 전부 느린 완전 최적화 경로로 컴파일된다. 실제로 애플리케이션의 상당수 메서드가 어떤 형태로든 루프를 포함하므로, 계층형 컴파일이 시작 시간을 줄여주는 폭이 그만큼 깎였다.
>
> .NET 6 이하를 유지보수하고 있고 시작 시간이 중요하다면 `DOTNET_TC_QuickJitForLoops=1`을 켜볼 수 있다. 단 위의 "긴 루프가 Tier-0에 갇히는" 문제가 그대로 돌아온다.

### OSR — 실행 중인 프레임을 갈아끼운다

.NET 7은 회피 대신 **정면 돌파**를 택했다. **OSR(on-stack replacement, 스택 상 교체)** 은 이미 실행 중인 메서드의 스택 프레임을, 실행 도중에 최적화된 버전의 프레임으로 바꿔치기하는 기술이다. ※.NET 6에 x64 한정 옵트인으로 들어왔고, .NET 7에서 기본 활성화되었다.

동작 방식은 이렇다.

1. Tier-0으로 컴파일할 때, JIT은 루프의 시작 지점(역방향 분기 대상)에 **패치포인트(patchpoint)** 를 심는다. 패치포인트는 카운터를 하나 감소시키고, 0이 되면 런타임 헬퍼를 호출하는 코드다.
2. 루프가 충분히 돌면 헬퍼가 호출된다. 이 초기 카운터는 `DOTNET_TC_OnStackReplacement_InitialCounter`로 조정할 수 있지만, **기본값 자체는 구현 세부이며 버전마다 다르다.** 실험용으로 값을 바꿔 보는 용도로만 쓰라.
3. 헬퍼는 **그 루프에 진입한 상태에서 시작하는 특별한 최적화 버전** — OSR 메서드 — 을 컴파일한다. 이 버전은 메서드 처음이 아니라 그 루프 헤더에서 시작하도록 만들어진다.
4. 런타임은 현재 Tier-0 프레임의 지역 변수 값을 읽어 OSR 코드가 기대하는 위치(레지스터 포함)로 **전이(transition)** 시키고, 실행을 OSR 코드로 넘긴다.
5. 루프 나머지는 최적화된 코드로 돈다.

```text
  [t=0] 메서드 진입, Tier-0 코드 실행

    스택
  ┌────────────────────────────┐
  │  Sum() Tier-0 프레임        │   for (i = 0; ...) {
  │   total : [rbp-0x08]        │       ...
  │   i     : [rbp-0x04]        │       ; 패치포인트: counter--
  │                            │       ; counter == 0 ? → 헬퍼 호출
  └────────────────────────────┘   }

  [t=1] 루프 1000회 → 패치포인트 헬퍼 호출 → OSR 버전 JIT 컴파일

                                  ┌──────────────────────────────┐
                                  │ Sum@0x1F (Tier1-OSR)          │
                                  │  · 루프 헤더에서 시작          │
                                  │  · total → rax, i → edx       │
                                  │  · 경계 검사 제거              │
                                  └──────────────────────────────┘

  [t=2] 프레임 전이 — 지역 변수 값을 그대로 옮긴다

    스택
  ┌────────────────────────────┐
  │  Sum() OSR 프레임            │   ← 같은 논리적 호출, 다른 기계어
  │   total : rax                │      i, total 값은 보존됨
  │   i     : edx                │
  └────────────────────────────┘

  [t=3] 나머지 1,999,999,000회 반복은 최적화된 코드로
```

OSR 덕분에 `TC_QuickJitForLoops`의 기본값을 `1`로 바꿀 수 있게 되었다. **루프가 있든 없든 모든 메서드가 Tier-0에서 출발하고**, 긴 루프는 OSR이 구해준다.

### 계층 이름이 늘어났다

OSR이 들어오면서 JIT 디스어셈블리 헤더에 나타나는 계층 이름이 다양해졌다.

| 헤더 표기 | 의미 |
|---|---|
| `(Tier0)` | 계층형 컴파일의 빠른 첫 컴파일 |
| `(Tier0-Instrumented)` | 프로파일 계측이 들어간 Tier-0 (55.5절) |
| `(Tier1)` | 완전 최적화, 호출 계수를 통해 승격됨 |
| `(Tier1-Instrumented)` | 최적화되었지만 프로파일 계측 프로브가 남아 있는 단계 |
| `(Tier1-OSR)` | OSR로 만들어진 최적화 코드. 메서드 중간에서 시작한다 |
| `(FullOpts)` | 계층화를 거치지 않고 처음부터 완전 최적화 (`AggressiveOptimization`, 계층화 비활성화, 일부 특수 메서드) |
| `(MinOpts)` | 최적화 없음. 계층화가 꺼진 상태에서 JIT이 최적화를 포기한 경우(메서드가 너무 크거나 `NoOptimization`) |

`DOTNET_JitDisasmSummary=1`을 켜면 각 메서드가 어느 계층으로 컴파일되었는지 한 줄씩 나온다. 어떤 메서드가 OSR을 거쳤는지 확인하는 가장 빠른 방법이다.

```text
   1: JIT compiled Program:Main(String[]):this [Tier0, IL size=54, code size=213]
   2: JIT compiled Program:Sum():long [Tier0, IL size=32, code size=118]
   3: JIT compiled Program:Sum():long [Tier1-OSR @0x1f, IL size=32, code size=41]
```

> **⚠️ OSR 코드는 완벽하지 않다**
>
> OSR 메서드는 "메서드 중간에서 시작한다"는 제약을 안고 컴파일된다. 진입 시점의 지역 변수 상태를 Tier-0 프레임에서 받아와야 하므로, **일부 변수는 스택에 남고 프레임 레이아웃도 Tier-0과 호환되도록 제약된다.** 그래서 OSR 코드의 품질은 같은 루프를 처음부터 Tier-1로 컴파일했을 때보다 **약간 떨어질 수 있다.**
>
> 실무에서 이것이 문제가 되는 경우는 드물지만, "루프 하나가 프로그램 실행 시간의 전부"인 계산 커널이라면 차이가 측정될 수 있다. 그럴 때의 선택지는 (1) 루프를 별도 메서드로 빼서 여러 번 호출되게 만들거나, (2) 그 메서드에 `AggressiveOptimization`을 붙이는 것이다. 다만 (2)의 부작용은 55.2절의 ⚠️를 다시 읽어야 한다.

> **📌 OSR은 JVM에서 온 개념이다**
>
> HotSpot JVM은 오래전부터 OSR을 갖고 있었다. .NET이 계층형 컴파일을 도입한 것이 2018년(.NET Core 2.1), OSR을 기본으로 켠 것이 2022년(.NET 7)이니 상당한 시차가 있다. 이 순서는 우연이 아니다 — OSR은 **런타임이 스택 프레임의 정확한 상태를 알아야** 가능하고, 그러려면 GC 정보와 디버그 정보 인프라가 성숙해 있어야 한다.

> **💡 OSR이 켜져 있는지 빠르게 확인하기**
>
> 다음 코드를 `dotnet run -c Release`로 돌리고, `DOTNET_JitDisasmSummary=1 DOTNET_JitStdOutFile=jit.txt`를 준 뒤 `jit.txt`에서 `OSR`을 grep하면 된다.
>
> ```csharp
> long total = 0;
> for (int i = 0; i < 500_000_000; i++) total += i;
> Console.WriteLine(total);
> ```
>
> .NET 7 이상이면 최상위 문의 `<Main>$`에 대해 `Tier1-OSR` 항목이 잡힌다. .NET 6에서는 잡히지 않고, 대신 `<Main>$`가 처음부터 `FullOpts`로 컴파일된 것이 보인다.

## 55.4 인라이닝 규칙과 `[MethodImpl(AggressiveInlining)]`

### 인라이닝은 다른 모든 최적화의 전제다

인라이닝은 호출을 없애는 최적화다. `call` 명령 하나와 프롤로그·에필로그를 절약한다. 그것만으로도 이득이지만, **인라이닝의 진짜 가치는 그 뒤에 열리는 문에 있다.**

```csharp
readonly struct Point
{
    public readonly int X, Y;
    public Point(int x, int y) { X = x; Y = y; }
    public int Manhattan() => Math.Abs(X) + Math.Abs(Y);
}

static int Distance(int x, int y) => new Point(x, y).Manhattan();
```

`Manhattan()`이 인라이닝되지 않으면 `Point` 구조체를 스택에 만들고 그 주소를 넘겨야 한다. 인라이닝되면 JIT은 `X`와 `Y`가 그냥 인수 `x`, `y`라는 것을 알게 되고, 구조체 자체를 없앨 수 있다(스칼라 대체, scalar replacement). `Math.Abs`도 내장 함수(intrinsic)로 펼쳐진다. 최종 코드에는 구조체도, 호출도 남지 않는다.

인라이닝이 열어주는 후속 최적화는 다음과 같다.

| 후속 최적화 | 인라이닝이 없으면 왜 불가능한가 |
|---|---|
| 상수 전파 | 호출 경계를 넘어 인수가 상수라는 것을 알 수 없다 |
| 죽은 코드 제거 | 호출된 메서드 안의 분기가 항상 거짓인지 알 수 없다 |
| 스칼라 대체 / 구조체 분해 | 구조체 주소가 다른 메서드로 넘어가면 메모리에 실체화해야 한다 |
| 이스케이프 분석 | 객체가 다른 메서드로 넘어가면 탈출한 것으로 보수적으로 판단한다(55.6절) |
| 경계 검사 제거 | 인덱스와 배열 길이의 관계가 호출 경계에서 끊긴다 |
| 공통 부분식 제거 | 서로 다른 메서드에 있는 같은 계산을 합칠 수 없다 |

**속성 접근자(`get`/`set`), 작은 래퍼 메서드, 확장 메서드는 인라이닝되지 않으면 존재 이유가 사라진다.** C#의 무비용 추상화는 대부분 인라이닝이 뒷받침한다.

### RyuJIT의 인라이닝 판단

JIT은 각 호출 지점마다 다음 순서로 판단한다.

```text
       호출 지점 발견
            │
            ▼
  ┌─────────────────────────────────┐
  │ 1. 하드 블로커가 있는가?          │── 있음 ──▶ 인라이닝 안 함 (판단 끝)
  │    (아래 표 참조)                │
  └────────────┬────────────────────┘
               │ 없음
               ▼
  ┌─────────────────────────────────┐
  │ 2. [AggressiveInlining]인가?     │── 예 ──▶ 크기·수익성 검사를 건너뛴다
  └────────────┬────────────────────┘
               │ 아니오
               ▼
  ┌─────────────────────────────────┐
  │ 3. IL 크기 ≤ 16바이트?           │── 예 ──▶ 거의 항상 인라이닝
  └────────────┬────────────────────┘
               │ 아니오
               ▼
  ┌─────────────────────────────────┐
  │ 4. IL 크기 ≤ 100바이트이고        │
  │    수익성 추정이 양수인가?        │── 예 ──▶ 인라이닝
  │    (관측: 인수가 상수인가,        │
  │     루프 안 호출인가, 반환값이     │
  │     바로 분기 조건인가 등)        │
  └────────────┬────────────────────┘
               │ 아니오
               ▼
        인라이닝 안 함
```

위 흐름도의 숫자는 RyuJIT 구현에 들어 있는 기본 상수를 옮긴 것이다. **다만 이 값들은 공개 API도 문서화된 계약도 아니고, 릴리스마다 조정된다.** "아주 작은 메서드는 사실상 무조건 후보이고, 어느 크기를 넘으면 수익성 추정이 양수여야 통과하며, 인라이닝 깊이에도 상한이 있다"는 **구조**만 기억하고, 특정 바이트 수를 기준선처럼 믿지 마라. 자기 코드가 인라이닝되는지는 수치를 외워 판정할 것이 아니라 생성 코드로 확인해야 한다(55.8절).

### 하드 블로커 — 특성을 붙여도 인라이닝되지 않는 경우

| 블로커 | 설명 |
|---|---|
| `[MethodImpl(MethodImplOptions.NoInlining)]` | 명시적 거부 |
| `[MethodImpl(MethodImplOptions.NoOptimization)]` | 최적화 자체를 끈다 |
| 예외 처리 블록을 포함 | `try`/`catch`/`finally`/`fault`가 있는 메서드는 인라이닝하지 않는다 |
| 명시적 `tail.` 접두사 호출 | 꼬리 호출 시맨틱을 보존해야 한다 |
| `localloc`(`stackalloc`)을 포함 | 호출자 프레임에 영향을 준다 |
| 재귀 깊이 초과 | 자기 자신을 무한히 펼칠 수 없다 |
| 가상/인터페이스 호출인데 역가상화 실패 | 어떤 구현을 부를지 모른다(55.5절) |
| 대상 타입의 정적 생성자가 `beforefieldinit`이 아님 | 초기화 순서 시맨틱이 깨질 수 있다 |
| Tier-0 컴파일 | Tier-0은 인라이닝을 사실상 수행하지 않는다 |

마지막 항목이 실무에서 자주 오해를 만든다.

> **⚠️ Tier-0 코드는 인라이닝을 하지 않는다**
>
> 프로퍼티 접근자를 잔뜩 쓴 코드가 시작 직후에 유난히 느린 이유가 이것이다. Tier-0에서는 `obj.X`가 진짜 `call`로 컴파일된다. Tier-1로 승격되고 나서야 사라진다.
>
> 그래서 **워밍업 없이 첫 몇 번의 실행을 측정하면 추상화 비용이 실제보다 몇 배 크게 나온다.** "구조체 래퍼를 썼더니 10배 느려졌다"는 마이크로벤치마크의 절반은 Tier-0을 측정한 것이다(67.4절).

### `[MethodImpl(MethodImplOptions.AggressiveInlining)]`이 실제로 하는 일

```csharp
using System.Runtime.CompilerServices;

[MethodImpl(MethodImplOptions.AggressiveInlining)]
static int Clamp(int v, int lo, int hi) => v < lo ? lo : (v > hi ? hi : v);
```

이 특성이 하는 일은 정확히 하나다. **크기 제한과 수익성 추정을 건너뛰게 한다.** 위 흐름도의 3·4단계를 우회한다.

하지 **않는** 일은 다음과 같다.

- **하드 블로커를 무시하지 않는다.** `try`/`catch`가 있으면 특성이 있어도 인라이닝되지 않는다.
- **인라이닝을 보장하지 않는다.** JIT은 여전히 거부할 수 있다. "요청"이지 "지시"가 아니다.
- **Tier-0에서 인라이닝하게 만들지 않는다.**
- **재귀 깊이 제한을 없애지 않는다.**

> **⚠️ `AggressiveInlining`은 자주 역효과를 낸다**
>
> 무해해 보이지만 세 가지 방식으로 코드를 느리게 만들 수 있다.
>
> 1. **명령어 캐시 압박.** 같은 메서드 본문이 호출 지점 수만큼 복제된다. 20곳에서 부르는 200바이트짜리 메서드에 이 특성을 붙이면 코드가 4KB 늘어난다. L1 명령어 캐시는 보통 32KB다. 뜨거운 루프가 캐시에서 밀려나면 `call` 하나를 아낀 것보다 훨씬 크게 잃는다.
> 2. **레지스터 압박.** 인라이닝된 본문의 지역 변수가 호출자의 레지스터를 놓고 경쟁한다. 레지스터가 모자라면 스택으로 넘치고(spill), 스택 접근이 늘어난다.
> 3. **호출자 자신이 인라이닝 후보에서 탈락한다.** 인라이닝 후 커진 호출자는 IL 크기 기준을 넘겨, 그 호출자를 부르는 상위 메서드에서 인라이닝되지 못한다. 최적화가 한 단계 위로 전파되지 못한다.
>
> 그리고 JIT 시간도 늘어난다. 시작 시간에 민감한 애플리케이션에서 라이브러리 전체에 이 특성을 뿌리면 시작이 느려진다.

> **💡 `AggressiveInlining`을 붙일 만한 곳**
>
> 다음 조건을 **전부** 만족할 때만 고려하라.
>
> - 뜨거운 경로에서 실제로 호출되고, 프로파일러가 그 사실을 보여준다.
> - 본문이 작다. 몇 줄짜리 표현식 본문 수준이어야 하고, 화면을 넘길 만큼 긴 메서드에 이 특성을 붙인다면 방향이 잘못되었다.
> - 인수가 호출 지점에서 상수이거나, 인라이닝 후 상수 폴딩·분기 제거가 일어날 것으로 기대된다.
> - **붙이기 전후를 BenchmarkDotNet으로 측정했다.**
>
> 대표적으로 잘 맞는 곳은 제네릭 타입 검사를 포함한 래퍼(`if (typeof(T) == typeof(int))` 형태), 비트 조작 헬퍼, `Span` 슬라이싱 래퍼다. 반대로 로깅 헬퍼나 유효성 검사 메서드에 붙이는 것은 거의 항상 손해다.

### 실전 패턴 — 느린 경로를 밖으로 빼기

인라이닝 관점에서 가장 효과가 큰 리팩터링은 **뜨거운 경로와 차가운 경로를 분리하는 것**이다. BCL 전체가 이 패턴을 쓴다.

```csharp
// 나쁜 형태 — 예외를 던지는 코드가 본문에 있어서 IL이 커지고,
// throw 헬퍼 호출 때문에 인라이닝 수익성 추정이 나빠진다
public T Get(int index)
{
    if ((uint)index >= (uint)_count)
        throw new ArgumentOutOfRangeException(
            nameof(index), index, "인덱스가 범위를 벗어났다.");
    return _items[index];
}
```

```csharp
// 좋은 형태 — 던지는 부분을 NoInlining 메서드로 분리한다
public T Get(int index)
{
    if ((uint)index >= (uint)_count)
        ThrowIndexOutOfRange(index);
    return _items[index];
}

[MethodImpl(MethodImplOptions.NoInlining)]
[DoesNotReturn]
private static void ThrowIndexOutOfRange(int index) =>
    throw new ArgumentOutOfRangeException(
        nameof(index), index, "인덱스가 범위를 벗어났다.");
```

두 번째 형태에서 `Get`의 IL은 훨씬 짧아지고 인라이닝 후보가 된다. 예외 메시지 문자열과 예외 객체 생성 코드는 **차가운 별도 메서드**로 밀려나서, 뜨거운 코드의 명령어 캐시를 차지하지 않는다. `[DoesNotReturn]`은 널 허용성 분석에 알려주는 용도이고 JIT 동작에는 영향을 주지 않지만, 컴파일러 경고를 정리해 준다.

> **📌 `(uint)index >= (uint)_count`라는 관용구**
>
> 위 코드의 캐스팅은 오타가 아니다. `index`가 음수이면 `(uint)`로 변환했을 때 아주 큰 수가 되므로, **한 번의 비교로 하한(`< 0`)과 상한(`>= _count`)을 동시에 검사한다.** 비교 명령이 두 개에서 하나로 줄어든다. BCL 전체에서 이 관용구를 볼 수 있고, JIT도 이 형태를 인식한다.

### 인라이닝 여부를 확인하는 법

가장 확실한 방법은 생성 코드를 보는 것이다.

```text
set DOTNET_JitDisasm=Distance
set DOTNET_TieredCompilation=0
dotnet run -c Release
```

`Distance`의 디스어셈블리에 `call` 명령이 남아 있는지 보면 된다. `Manhattan`으로 가는 호출이 없다면 인라이닝된 것이다.

`DOTNET_JitDisasmSummary=1`로 전체 목록을 뽑았을 때 **어떤 메서드가 목록에 아예 나타나지 않는다면**, 그 메서드는 (a) 호출된 적이 없거나 (b) 모든 호출 지점에서 인라이닝되어 독립 컴파일이 필요 없었던 것이다.

> **⚠️ ILSpy나 IL 뷰어로는 인라이닝을 볼 수 없다**
>
> 인라이닝은 **JIT의 결정**이다. C# 컴파일러는 인라이닝을 하지 않는다. `ildasm`이나 ILSpy(56.8절)로 IL을 봐도 `call` 명령은 그대로 있다. 인라이닝을 확인하려면 반드시 **네이티브 코드**를 봐야 한다. 55.8절이 그 방법이다.

## 55.5 역가상화(devirtualization)와 가드된 역가상화(GDV)

### 가상 호출은 인라이닝의 적이다

54.1절에서 본 것처럼 가상 호출은 객체 → `MethodTable` → 슬롯 → 코드로 이어지는 간접 참조 두 번이다. 인터페이스 호출은 여기에 가상 스텁 디스패치가 더해진다. 간접 참조 자체의 비용도 있지만, **더 큰 손해는 인라이닝이 불가능하다는 것**이다. 어떤 구현이 불릴지 모르면 무엇을 펼쳐 넣을지도 알 수 없다.

```csharp
interface IShape { double Area(); }

sealed class Circle : IShape
{
    public double R;
    public double Area() => Math.PI * R * R;
}

static double TotalArea(IShape[] shapes)
{
    double sum = 0;
    foreach (IShape s in shapes)
        sum += s.Area();      // 인터페이스 호출 — 무엇이 불릴까?
    return sum;
}
```

**역가상화(devirtualization)** 는 JIT이 "실제로 불릴 구현이 무엇인지" 알아내서 가상/인터페이스 호출을 직접 호출로 바꾸는 최적화다. 직접 호출이 되면 인라이닝 후보가 되고, 그러면 55.4절의 후속 최적화가 전부 열린다.

### 정적 역가상화 — 타입만 보고 알 수 있는 경우

JIT이 프로파일 없이도 역가상화할 수 있는 상황들이다.

| 상황 | 예 |
|---|---|
| 수신자의 정적 타입이 `sealed` 클래스 | `Circle c; c.Area()` — `Circle`은 `sealed`이므로 파생 타입이 없다 |
| 메서드가 `sealed override` | 그 아래로는 재정의가 불가능하다 |
| 수신자가 `new`로 방금 만든 정확한 타입 | `new Circle().Area()` |
| 타입 계층에 재정의가 하나도 없음 | 클래스가 `sealed`가 아니어도 로드된 타입 중 재정의가 없으면 가능(단 새 타입 로드 시 무효화 필요) |
| 제네릭 타입 인수가 값 타입 | `List<int>`의 `IEnumerator<int>`처럼 인스턴스화가 확정된 경우 |
| `Span<T>`/배열의 `foreach` | 구조체 열거자가 인터페이스를 거치지 않는다 |

> **💡 `sealed`는 성능 특성이다**
>
> 상속을 열어둘 이유가 없는 클래스에 `sealed`를 붙이는 것은 설계 의도의 표현일 뿐 아니라 **JIT에게 주는 정보**다. `sealed` 클래스의 인스턴스 메서드 호출은 정적으로 역가상화되고, 형변환 검사도 단순해진다(정확한 타입 비교 한 번이면 된다).
>
> BCL과 ASP.NET Core 코드베이스가 내부 클래스에 `sealed`를 광범위하게 붙이는 이유가 이것이다. 라이브러리를 만든다면 "상속을 지원할 것인가"를 의식적으로 결정하고, 아니라면 `sealed`를 붙여라. 나중에 `sealed`를 떼는 것은 호환되는 변경이지만 붙이는 것은 파괴적 변경이다.

### 동적 PGO — 실행을 관찰해서 알아낸다

정적 역가상화가 통하지 않는 경우가 훨씬 많다. `IShape[]`에는 무엇이든 들어올 수 있다. 하지만 **실제로 돌려보면** 99%가 `Circle`일 수도 있다. 이 사실을 알아내는 것이 **동적 PGO(dynamic profile-guided optimization)** 다.

계층형 컴파일이 이것을 가능하게 한다. 어차피 두 번 컴파일할 거라면, **첫 번째 컴파일 결과에 계측 코드를 심어두고 두 번째 컴파일에서 그 결과를 쓰면 된다.**

```text
  [일반 메서드]

   Tier-0            Tier-0-Instrumented              Tier-1
  ┌────────┐  30회  ┌──────────────────────┐  임계값  ┌────────────────┐
  │ 빠른    │──────▶│ 여전히 최적화 없음     │────────▶│ 완전 최적화     │
  │ 컴파일  │       │ + 블록 카운터          │         │ + 프로파일 활용  │
  └────────┘       │ + 클래스/메서드 프로파일 │         │ + GDV           │
                   └──────────────────────┘         └────────────────┘

  [R2R로 사전 컴파일된 메서드]

   R2R 코드          Tier-1-Instrumented              Tier-1
  ┌────────┐        ┌──────────────────────┐         ┌────────────────┐
  │ 사전    │──────▶│ 최적화 + 계측 프로브   │────────▶│ 완전 최적화     │
  │ 컴파일  │       │ (계측 비용을 줄이려고   │         │ + 프로파일 활용  │
  └────────┘       │  최적화된 코드에 심는다) │         └────────────────┘
                   └──────────────────────┘
```

계측이 수집하는 것은 크게 두 가지다.

- **블록 카운트** — 어느 기본 블록이 몇 번 실행되었는가. 뜨거운 블록과 차가운 블록을 나누고, 분기를 재배치하고, 루프를 어떻게 펼칠지 결정하는 데 쓰인다.
- **클래스 프로파일 / 메서드 프로파일** — 이 가상·인터페이스 호출 지점에서 실제로 관찰된 수신자의 타입이 무엇인가. 델리게이트 호출 지점에서 실제로 불린 메서드가 무엇인가.

> **📌 동적 PGO는 .NET 8부터 기본값이다**
>
> ※.NET 6에서 `DOTNET_TieredPGO=1` 옵트인으로 도입되었고, .NET 7에서 개선되었으며, **.NET 8에서 기본 활성화**되었다. .NET 6/7 프로젝트를 유지보수하고 있다면 `<TieredPGO>true</TieredPGO>`를 켜보는 것만으로 인터페이스 호출이 많은 코드에서 의미 있는 개선을 얻을 수 있다.
>
> 계측 계층이 하나 더 끼는 만큼 워밍업 구간이 조금 길어진다. 반대로 계측 자체는 "뜨거운 코드에만" 하도록 여러 차례 다듬어져서, .NET 8 시점의 오버헤드는 대부분의 애플리케이션에서 무시할 만하다.

### 가드된 역가상화(GDV)

프로파일이 "이 호출 지점의 수신자는 95%가 `Circle`이었다"고 말해도, JIT은 그것을 **단정할 수 없다.** 나머지 5%가 언제든 올 수 있다. 그래서 JIT은 **가드(guard)를 붙인 역가상화**를 한다.

```csharp
// JIT이 만들어내는 코드를 C#으로 옮기면 대략 이렇다
foreach (IShape s in shapes)
{
    if (s.GetType() == typeof(Circle))     // 가드: MethodTable 포인터 비교
    {
        // 빠른 경로 — 역가상화 + 인라이닝됨
        Circle c = (Circle)s;
        sum += Math.PI * c.R * c.R;
    }
    else
    {
        // 느린 경로 — 원래의 인터페이스 호출
        sum += s.Area();
    }
}
```

가드는 실제로는 **객체의 `MethodTable` 포인터와 `Circle`의 `MethodTable` 주소를 비교하는 `cmp` 한 줄**이다. x64 코드에서는 이렇게 나온다.

```text
       mov      rax, qword ptr [rsi]           ; 객체의 MethodTable 포인터
       mov      rdx, 0x7FFA1C3D2B28             ; Circle의 MethodTable 주소
       cmp      rax, rdx
       jne      SHORT G_M000_IG09              ; 다르면 느린 경로로
       ; --- 여기부터 인라이닝된 Circle.Area() ---
       vmovsd   xmm0, qword ptr [rsi+0x08]
       vmulsd   xmm0, xmm0, xmm0
       ...
```

비교 한 번과 잘 예측되는 분기 하나를 치르고, 그 대가로 **인터페이스 디스패치를 없애고 본문을 인라이닝한다.** 단형(monomorphic)에 가까운 호출 지점에서는 압도적으로 남는 장사다.

> **⚠️ GDV는 다형적인 호출 지점에서는 이득이 없다**
>
> 수신자 타입이 매번 달라지는 호출 지점에서는 가드가 계속 실패한다. 그러면 비교와 분기 비용만 추가되고 느린 경로로 간다. JIT은 프로파일이 충분히 편향되어 있을 때만 GDV를 적용하려 하지만, 프로파일이 수집된 구간과 실제 운영 구간의 타입 분포가 다르면 어긋날 수 있다.
>
> 이것이 **워밍업 단계와 정상 운영 단계의 부하 특성이 다른 서버**에서 드물게 성능 이상이 보고되는 이유다. 예를 들어 시작 시 특정 구현만 쓰다가 나중에 다른 구현이 섞이면, 시작 때 수집한 프로파일로 만든 Tier-1 코드가 계속 느린 경로를 타게 된다. 현재 구현은 이런 경우를 감지해 다시 계측하고 재컴파일하지는 않는다(가드가 빗나가도 결과는 여전히 올바르고, 느려질 뿐이다).

> **📌 GDV의 확장 — 델리게이트와 다중 가드**
>
> ※.NET 8은 GDV를 **델리게이트 호출**과 **`Func<>`/`Action<>` 기반 호출 지점**으로 확장했다. 델리게이트 프로파일이 특정 대상 메서드로 편향되어 있으면 그 메서드를 인라이닝하고 델리게이트 대상 비교를 가드로 쓴다. LINQ처럼 델리게이트를 대량으로 쓰는 코드가 .NET 8에서 개선된 이유 중 하나다.
>
> 가드를 여러 개(두 후보 타입) 다는 것도 가능하지만, 가드 개수가 늘수록 코드가 커지고 이득이 줄어들기 때문에 JIT은 보수적으로 적용한다.

### 제네릭과 역가상화

제네릭은 역가상화 관점에서 특별하다. 54장에서 본 것처럼 CLR은 제네릭 인스턴스화를 두 방식으로 다룬다.

| 타입 인수 | 네이티브 코드 | 역가상화 |
|---|---|---|
| **값 타입** (`List<int>`) | 인스턴스화마다 **별도 코드** 생성 | `T`가 정확히 `int`임을 JIT이 안다. `typeof(T) == typeof(int)`가 상수로 접힌다 |
| **참조 타입** (`List<string>`) | 모든 참조 타입이 **공유 코드**(`__Canon`) 사용 | `T`의 정확한 타입을 모른다. 타입 검사가 런타임 조회가 된다 |

이 차이가 실무에서 만드는 결과가 있다.

```csharp
[MethodImpl(MethodImplOptions.AggressiveInlining)]
static void Write<T>(Span<byte> dst, T value)
{
    if (typeof(T) == typeof(int))
    {
        BinaryPrimitives.WriteInt32LittleEndian(dst, (int)(object)value!);
    }
    else if (typeof(T) == typeof(long))
    {
        BinaryPrimitives.WriteInt64LittleEndian(dst, (long)(object)value!);
    }
    else
    {
        throw new NotSupportedException();
    }
}
```

`Write<int>`로 인스턴스화되면 JIT은 `typeof(T) == typeof(int)`를 **컴파일 타임 상수 `true`** 로 접고, 나머지 분기를 통째로 제거한다. `(int)(object)value`의 박싱·언박싱도 사라진다. 이 관용구는 BCL 전체에서 쓰인다. 다만 `T`가 참조 타입이면 공유 코드를 쓰므로 이 폴딩이 일어나지 않는다.

> **⚠️ 인터페이스 제약을 건 제네릭이 참조 타입이면 여전히 인터페이스 호출이다**
>
> ```csharp
> static long Sum<T>(T[] items) where T : IHasValue
> {
>     long s = 0;
>     foreach (T item in items) s += item.Value;
>     return s;
> }
> ```
>
> `T`가 **구조체**면 제약된 호출(`constrained.` 접두사, 56.3절)이 정확한 구현으로 해석되어 박싱 없이 직접 호출·인라이닝된다. `T`가 **클래스**면 공유 `__Canon` 코드가 만들어지고 인터페이스 호출이 그대로 남는다. 같은 소스에서 타입 인수에 따라 성능이 크게 갈린다. 동적 PGO가 붙으면 후자도 GDV로 개선될 수 있지만 전자만큼은 아니다.

> **💡 역가상화가 일어났는지 확인하는 법**
>
> 디스어셈블리에서 다음 세 가지를 찾으면 된다.
>
> - `call qword ptr [rax+0x??]` 형태의 **간접 호출**이 남아 있다 → 가상 호출이 그대로다.
> - `cmp rax, <상수>` + `jne` 뒤에 본문이 펼쳐져 있다 → **GDV**가 적용되었다.
> - 호출도 가드도 없이 본문만 있다 → **정적 역가상화 + 인라이닝**이 되었다.
>
> `DOTNET_TieredPGO=0`으로 한 번, `1`로 한 번 뽑아서 비교하면 GDV의 효과를 분리해 볼 수 있다.

## 55.6 경계 검사 제거, 루프 클로닝, 상수 폴딩, 이스케이프 분석

### 경계 검사는 공짜가 아니다

C#에서 `arr[i]`는 항상 안전하다. 인덱스가 범위를 벗어나면 `IndexOutOfRangeException`이 난다. 이 보장은 **모든 배열 접근마다 비교와 분기**로 구현된다.

```text
       cmp      edx, dword ptr [rcx+0x08]      ; i vs arr.Length
       jae      SHORT G_M000_IG06              ; i >= Length면 예외로
       mov      eax, dword ptr [rcx+rdx*4+0x10]
       ...
G_M000_IG06:
       call     CORINFO_HELP_RNGCHKFAIL
       int3
```

`jae`(unsigned 비교)를 쓰는 것에 주목하라. 55.4절의 `(uint)` 관용구와 같은 원리로, **음수 인덱스도 이 한 번의 비교로 걸러진다.** 배열 길이는 `MethodTable` 포인터 바로 뒤 오프셋 8에 있다(54.7절).

비용 자체는 크지 않다. 분기 예측이 거의 항상 맞고, 최신 CPU에서 예측된 분기는 거의 공짜다. 그러나 **뜨거운 루프에서는 다르다.** 검사가 명령 개수를 늘리고, 벡터화를 방해하고, 루프 펼치기를 어렵게 만든다.

### JIT이 검사를 지울 수 있는 조건

RyuJIT의 범위 검사 제거는 **인덱스 값의 범위를 증명**하는 방식으로 동작한다. 증명이 가장 쉬운 형태는 하나다.

```csharp
for (int i = 0; i < arr.Length; i++)
{
    // arr[i] — 검사 제거됨
}
```

JIT은 이렇게 추론한다.

1. `i`의 초기값은 0이다.
2. 루프 조건이 `i < arr.Length`이므로, 본문에 들어온 시점에서 `i < arr.Length`가 참이다.
3. `arr`는 루프 안에서 재할당되지 않으므로 `arr.Length`는 불변이다.
4. `i`는 단조 증가하고 오버플로하지 않는다.
5. 따라서 `0 <= i < arr.Length`가 증명된다. 검사 삭제.

**3번과 4번이 깨지면 증명이 무너진다.** 그래서 다음 형태들은 검사가 남을 수 있다.

| 형태 | 결과 | 이유 |
|---|---|---|
| `for (int i = 0; i < arr.Length; i++) arr[i]` | **제거됨** | 표준형 |
| `for (int i = 0; i < arr.Length; i++) other[i]` | **`other`의 검사는 남음** | `other.Length`와 `arr.Length`의 관계를 모른다 |
| `for (int i = 0; i < n; i++) arr[i]` | **남음** | `n`과 `arr.Length`의 관계를 모른다 |
| `int len = arr.Length; for (i=0;i<len;i++) arr[i]` | 대개 제거됨 (보장 아님) | `len`이 `arr.Length`의 복사본임을 추적해야 한다 |
| `for (int i = 0; i < arr.Length - 1; i++) arr[i]` | **남을 수 있음** | 상한이 `Length`가 아니라 파생식이다 |
| `for (int i = 0; i < arr.Length; i++) arr[i + 1]` | **남음** | `i+1 < Length`는 증명되지 않는다(실제로 거짓이다) |
| `for (int i = arr.Length - 1; i >= 0; i--) arr[i]` | 대개 제거됨 | 역방향 표준형도 인식한다 |
| `foreach (var x in arr)` | **제거됨** | 컴파일러가 표준형 `for`로 낮춘다 |
| `for (int i = 0; i < span.Length; i++) span[i]` | **제거됨** | `Span<T>` 인덱서도 같은 분석 대상 |

> **⚠️ 이 표를 외우지 말고 확인하는 법을 외워라**
>
> 경계 검사 제거는 JIT 버전마다 개선된다. 어떤 .NET 버전에서 검사가 남던 형태가 다음 버전에서는 사라진다. 표를 규칙처럼 믿으면 낡은 지식으로 코드를 비틀게 된다.
>
> **확인 방법은 하나다.** 디스어셈블리에서 `CORINFO_HELP_RNGCHKFAIL`을 찾아라.
>
> ```text
> set DOTNET_JitDisasm=Sum
> set DOTNET_TieredCompilation=0
> dotnet run -c Release > out.txt
> findstr RNGCHKFAIL out.txt
> ```
>
> 아무것도 안 나오면 그 메서드의 모든 배열 접근에서 검사가 제거된 것이다. 나온다면 몇 개인지 세고, 루프를 표준형으로 고친 뒤 다시 세라. **`arr.Length - 1` 같은 형태에서 검사가 남는지 아닌지를 논쟁하는 것보다 30초 걸려 직접 확인하는 것이 빠르고 정확하다.**

> **💡 검사를 확실히 지우는 방법 — 재슬라이싱**
>
> 상한이 `arr.Length`가 아니라 별도 변수 `n`이라면, 배열을 그 길이로 잘라내면 표준형이 복원된다.
>
> ```csharp
> // 검사가 남는다
> static int SumFirst(int[] arr, int n)
> {
>     int s = 0;
>     for (int i = 0; i < n; i++) s += arr[i];
>     return s;
> }
>
> // 검사가 사라진다 — 슬라이스를 한 번만 검사하고 루프는 표준형이 된다
> static int SumFirstSliced(int[] arr, int n)
> {
>     ReadOnlySpan<int> span = arr.AsSpan(0, n);   // 여기서 한 번 검증
>     int s = 0;
>     for (int i = 0; i < span.Length; i++) s += span[i];
>     return s;
> }
> ```
>
> `AsSpan(0, n)`이 범위를 한 번 검증하고, 이후 루프는 `span.Length`를 상한으로 쓰므로 표준형이 된다. **경계 검사를 N번에서 1번으로 줄이는 것**이 `Span<T>`의 성능 이점 중 상당 부분이다(68.4절).
>
> 반대로 `unsafe` 포인터나 `Unsafe.Add`로 검사를 지우는 것은 최후의 수단이다. 안전성을 잃고, 얻는 것은 슬라이싱과 비슷한 정도인 경우가 많다.

### 루프 클로닝 — 증명이 안 되면 두 벌을 만든다

증명이 안 되는 경우에도 JIT은 포기하지 않는다. **루프 클로닝(loop cloning)** 은 루프를 두 벌 만들고, 진입 시점에 한 번 검사해서 어느 쪽으로 갈지 정한다.

```csharp
static void Copy(int[] src, int[] dst, int n)
{
    for (int i = 0; i < n; i++)
        dst[i] = src[i];
}
```

JIT이 만드는 구조를 C#으로 옮기면 이렇다.

```csharp
static void Copy(int[] src, int[] dst, int n)
{
    if (src != null && dst != null && n <= src.Length && n <= dst.Length)
    {
        // 빠른 사본 — 경계 검사 없음
        for (int i = 0; i < n; i++)
            dst[i] = src[i];
    }
    else
    {
        // 느린 사본 — 검사 전부 유지
        for (int i = 0; i < n; i++)
            dst[i] = src[i];
    }
}
```

루프 앞의 조건이 **클로닝 조건(cloning condition)** 이다. 검사 N번을 진입 시 검사 몇 번으로 바꾼다.

디스어셈블리에서 루프 클로닝은 이렇게 보인다. 루프 본문이 **두 벌** 있고, 한쪽에만 `RNGCHKFAIL` 분기가 있다.

```text
G_M000_IG02:
       ; 클로닝 조건 검사
       test     rcx, rcx
       je       SHORT G_M000_IG07              ; src == null → 느린 경로
       cmp      r8d, dword ptr [rcx+0x08]
       ja       SHORT G_M000_IG07              ; n > src.Length → 느린 경로
       ...
G_M000_IG03:                                    ; 빠른 사본
       mov      r10d, dword ptr [rcx+rax*4+0x10]
       mov      dword ptr [rdx+rax*4+0x10], r10d
       inc      eax
       cmp      eax, r8d
       jl       SHORT G_M000_IG03
       jmp      SHORT G_M000_IG09
G_M000_IG07:                                    ; 느린 사본
       cmp      eax, dword ptr [rcx+0x08]
       jae      SHORT G_M000_IG10
       ...
```

> **⚠️ 루프 클로닝은 코드 크기를 두 배로 만든다**
>
> 이득만 있는 것은 아니다. 루프 본문이 복제되므로 코드가 커지고, 명령어 캐시 압박이 늘고, JIT 시간이 늘어난다. JIT은 루프 본문이 일정 크기 이하일 때만 클로닝하며, 중첩 루프에서는 안쪽만 클로닝하는 식으로 제한을 둔다.
>
> **코드가 갑자기 커졌는데 이유를 모르겠다면** 루프 클로닝을 의심하라. 그리고 앞의 💡처럼 슬라이스로 표준형을 만들어 주면 클로닝 자체가 필요 없어져서 코드가 다시 작아진다.

### 상수 폴딩과 죽은 분기 제거

JIT은 컴파일 타임에 값이 확정되는 식을 미리 계산한다. C# 컴파일러도 상수 폴딩을 하지만, **JIT은 C# 컴파일러가 알 수 없는 것들을 상수로 안다.**

| 식 | JIT이 아는 값 | 결과 |
|---|---|---|
| `IntPtr.Size` | 4 또는 8 | 32/64비트 분기 하나가 통째로 사라진다 |
| `Sse2.IsSupported`, `Avx2.IsSupported` 등 | 실행 CPU에 따라 `true`/`false` | 지원하지 않는 명령 집합용 코드가 전부 제거된다 |
| `Vector128.IsHardwareAccelerated` | `true`/`false` | 스칼라 폴백 경로가 사라진다 |
| `Vector<T>.Count` | `T`와 실행 CPU의 벡터 폭으로 정해지는 상수 | 루프 스텝이 상수가 된다 |
| `typeof(T) == typeof(int)` (값 타입 인스턴스화) | `true`/`false` | 55.5절의 제네릭 특수화 |
| `RuntimeHelpers.IsKnownConstant(x)` (BCL 내부 전용) | 호출 지점에서 `x`가 상수인지 | BCL이 특수 경로를 고르는 데 쓴다. public API가 아니므로 직접 쓸 수는 없다 |
| `static readonly` 기본형 필드 ※.NET 8 | 정적 생성자 실행 후의 값 | Tier-1에서 상수로 접힌다 |

마지막 항목이 ※.NET 8의 의미 있는 개선이다. 정적 생성자가 이미 실행되었다면, `static readonly int`나 `static readonly bool`의 값은 더 이상 바뀌지 않는다. Tier-1 컴파일 시점에는 그 값을 읽어서 **상수처럼 취급**할 수 있다.

```csharp
static readonly bool UseFastPath =
    Environment.GetEnvironmentVariable("FAST") == "1";

static int Compute(int x)
{
    if (UseFastPath) return x * 2;   // Tier-1에서는 분기가 통째로 사라진다
    return SlowCompute(x);
}
```

.NET 7 이하에서는 매 호출마다 정적 필드를 읽고 분기했다. .NET 8부터는 Tier-1 코드에서 `UseFastPath`가 상수로 접히고, 죽은 쪽 분기가 제거된다. **기능 스위치(feature switch) 패턴이 사실상 무비용이 되었다.**

> **📌 이것이 하드웨어 내장 함수 패턴이 성립하는 이유**
>
> ```csharp
> if (Avx2.IsSupported)      { /* AVX2 경로 */ }
> else if (Sse2.IsSupported) { /* SSE2 경로 */ }
> else                       { /* 스칼라 경로 */ }
> ```
>
> 이 코드는 세 경로를 전부 컴파일하는 것처럼 보이지만, **JIT은 실행 중인 CPU에 해당하는 한 경로만 남기고 나머지를 지운다.** 분기 검사조차 남지 않는다. 이 패턴이 없었다면 SIMD 코드를 쓸 때마다 런타임 검사 비용을 내야 했을 것이다.
>
> 반대로 **ReadyToRun 이미지에는 이 폴딩이 제대로 적용되지 않는다.** R2R은 기준(baseline) 명령어 집합을 가정해 컴파일되기 때문이다(55.7절).

### 이스케이프 분석과 스택 할당

참조 타입 인스턴스는 힙에 할당된다 — 이것이 교과서적 설명이다. 그러나 **어떤 객체가 자기가 만들어진 메서드 밖으로 절대 새어나가지 않는다는 것을 증명할 수 있다면**, 그 객체는 값 타입 지역 변수처럼 스택에 놓아도 된다. 이 증명을 **이스케이프 분석(escape analysis)** 이라 하고, 런타임 팀은 이 기능을 **객체 스택 할당(object stack allocation)** 이라고 부른다.

```csharp
sealed class Vector
{
    public int X, Y;
    public Vector(int x, int y) { X = x; Y = y; }
}

static Vector Add(Vector a, Vector b) => new Vector(a.X + b.X, a.Y + b.Y);

public int UseVectors()
{
    var p1 = new Vector(1, 2);
    var p2 = new Vector(3, 4);
    var result = Add(p1, p2);
    return result.X + result.Y;
}
```

이스케이프 분석이 꺼져 있으면 `p1`, `p2` 할당이 그대로 힙 할당 헬퍼 호출로 나온다.

```text
       sub      rsp, 32
       mov      rsi, 7FFC032D2B28h              ; MT: Vector
       mov      rcx, rsi
       call     coreclr!JIT_TrialAllocSFastMP_InlineGetThread
       mov      rdi, rax
       mov      dword ptr [rdi+0x08], 1
       mov      dword ptr [rdi+0x0C], 2
       mov      rcx, rsi
       call     coreclr!JIT_TrialAllocSFastMP_InlineGetThread
       mov      rbx, rax
       mov      dword ptr [rbx+0x08], 3
       mov      dword ptr [rbx+0x0C], 4
       ...
```

이스케이프 분석이 켜지면 두 객체가 **스택 프레임 안에서 만들어진다.** `rsp` 기준 오프셋에 `MethodTable` 포인터와 필드가 그대로 배치된다 — **메모리 레이아웃은 힙에 있을 때와 완전히 동일하다.**

```text
       mov      rax, 7FFBF83B2B28h              ; MT: Vector
       mov      qword ptr [rsp+0x28], rax       ; MethodTable 포인터
       mov      dword ptr [rsp+0x30], 1         ; X
       mov      dword ptr [rsp+0x34], 2         ; Y
       lea      rdx, [rsp+0x28]
       mov      qword ptr [rsp+0x18], rax
       mov      dword ptr [rsp+0x20], 3
       mov      dword ptr [rsp+0x24], 4
       ...
```

`call JIT_TrialAllocSFastMP_InlineGetThread`가 **사라졌다.** 할당이 없으니 GC 압력도 없다.

> **⚠️ 이스케이프 분석은 아직 매우 제한적이다**
>
> ※.NET 8 시점에는 **기본 비활성화**였고 `DOTNET_JitObjectStackAllocation=1`로 켜야 관찰할 수 있었다. 이후 릴리스에서 기본값과 적용 범위가 계속 바뀌고 있으므로, 자신이 쓰는 버전의 기본값은 릴리스 노트에서 확인하라. 어느 쪽이든 **다음 중 하나에 해당하면 스택 할당되지 않는다.**
>
> - 할당 대상이 **배열**이다
> - 할당 대상이 **문자열**이다
> - **박싱된 구조체**다
> - 클래스 크기가 8KB를 초과한다
> - ReadyToRun 하에서 클래스나 그 기반 클래스가 다른 **버전 버블**에 있다
> - **루프 안에서** 할당된다
>
> 그리고 결정적인 제약이 하나 더 있다. **JIT에는 프로시저 간(interprocedural) 이스케이프 분석이 없다.** 객체의 메서드를 호출하거나 객체를 인수로 넘기면, 그 호출이 **인라이닝되지 않는 한** 탈출한 것으로 간주된다. 위 예제에서 스택 할당이 일어나려면 `Add`가 반드시 인라이닝되어야 한다. 55.4절에서 "인라이닝이 다른 모든 최적화의 전제"라고 한 이유가 여기서도 반복된다.
>
> 실제 애플리케이션에서 이 최적화만으로 할당 수가 눈에 띄게 줄어드는 경우는 아직 흔하지 않다. **"JIT이 알아서 스택에 올려주겠지"라고 기대하고 클래스를 쓰지 마라.** 할당을 줄이려면 여전히 구조체, `Span<T>`, 풀링이 정공법이다(69장).

> **📌 스택 할당을 측정할 방법이 없다**
>
> 현재 이 최적화가 적용되었는지 알려주는 CLR 이벤트나 진단 도구가 없다. 확인하려면 디스어셈블리에서 `JIT_TrialAlloc...` 계열 헬퍼 호출이 사라졌는지 보는 수밖에 없다. BenchmarkDotNet의 `MemoryDiagnoser`는 할당 바이트 수가 줄어든 것으로 간접 확인해 준다(67.5절).

### JIT이 하지 않는 최적화

기대하면 안 되는 것들도 명확히 해두자.

| 최적화 | RyuJIT | 비고 |
|---|---|---|
| 일반 루프 자동 벡터화 | **하지 않는다** | SIMD를 원하면 `Vector<T>`/`Vector128<T>` 내장 함수를 직접 써야 한다 |
| 프로시저 간 이스케이프 분석 | 하지 않는다 | 인라이닝에 의존한다 |
| 전역 프로그램 최적화 | 하지 않는다 | 메서드 단위 컴파일이다 |
| 꼬리 재귀 최적화 | 제한적 | 명시적 `tail.` 접두사가 있거나 특정 조건에서만 |
| 루프 펼치기(unrolling) | 제한적 | 반복 횟수가 작고 상수일 때 주로 |
| 부동소수점 재결합 | **하지 않는다** | IEEE 754 시맨틱을 보존해야 한다. `a+b+c`의 순서를 바꾸지 않는다 |

> **⚠️ "JIT이 최적화해 주겠지"는 위험한 가정이다**
>
> C++ 컴파일러는 전체 프로그램을 몇 초~몇 분에 걸쳐 최적화한다. RyuJIT은 **밀리초 단위로** 메서드 하나를 컴파일해야 한다. 시간 예산 자체가 다르다.
>
> 그래서 RyuJIT은 "값이 큰 최적화를 싸게" 하는 데 집중하고, 비싼 전역 분석은 포기한다. 알고리즘 복잡도, 할당 횟수, 데이터 지역성(54.9절)은 **여전히 개발자의 책임**이다. JIT이 고쳐주는 것은 그 위에 얹힌 상수 배수뿐이다.

## 55.7 ReadyToRun과 Native AOT — 언제 무엇을 쓰나

### 먼저 역사 — NGen.exe

.NET Framework에는 **NGen.exe**(네이티브 코드 생성기)라는 도구가 있었다. 애플리케이션을 사용자 머신에 설치할 때 IL을 네이티브 코드로 컴파일해 디스크에 저장하는 도구다. 런타임에 어셈블리를 로드할 때 CLR은 대응하는 NGen 이미지가 있는지 확인하고, 있으면 그 코드를 쓴다. JIT 컴파일이 필요 없어진다.

NGen이 흥미로운 시나리오는 둘이었다.

- **시작 시간 개선** — 이미 네이티브 코드로 컴파일되어 있으므로 런타임 컴파일이 필요 없다.
- **작업 집합(working set) 감소** — 어셈블리가 여러 프로세스에 동시에 로드된다면, NGen 이미지는 별도 파일이므로 **여러 프로세스 주소 공간에 메모리 매핑되어 공유**될 수 있다. 프로세스마다 코드 사본을 가질 필요가 없다.

생성된 이미지는 `%SystemRoot%\Assembly\NativeImages_v4.0.#####_64` 같은 폴더에 놓였다. 폴더 이름에 CLR 버전과 32/64비트 정보가 들어간다.

그러나 문제가 많았다.

| 문제 | 내용 |
|---|---|
| **지적 재산 보호 안 됨** | NGen 이미지만 배포하고 IL을 감출 수 없다. 런타임이 리플렉션·직렬화를 위해 메타데이터를 필요로 하고, NGen 이미지를 쓸 수 없는 상황이면 IL로 폴백해야 한다 |
| **동기화가 깨짐** | CLR 버전(패치·서비스 팩), CPU 타입, Windows OS 버전, 어셈블리의 MVID(재컴파일 시 변경), 참조 어셈블리의 버전 ID, 보안 설정 중 **하나라도 달라지면 NGen 이미지를 쓸 수 없다.** 그러면 조용히 JIT 경로로 돌아간다 |
| **실행 성능 저하** | NGen은 실행 환경에 대해 JIT만큼 가정할 수 없다. 특정 CPU 명령을 최적화하지 못하고, 정적 필드 접근에 간접 참조를 넣고(실제 주소를 런타임까지 모른다), 클래스 생성자가 이미 실행되었는지 모르므로 **곳곳에 클래스 생성자 호출 코드를 삽입한다.** 일부 NGen 애플리케이션은 JIT 버전보다 약 5% 느렸다 |

> **📌 NGen은 .NET Framework 전용이다**
>
> `ngen.exe`는 .NET Framework SDK와 함께 배포되며 **.NET Core / .NET 5+ 에는 존재하지 않는다.** 현대 .NET의 대응물은 ReadyToRun(`crossgen2`)이고, 설계 전제가 다르다. `ngen install` 명령을 .NET 8 프로젝트에 쓰려는 시도는 시작부터 틀렸다.
>
> 서버 애플리케이션에서 NGen은 거의 의미가 없었다. 첫 클라이언트 요청만 손해를 보고 이후 요청은 전속력으로 돌기 때문이다. 게다가 대부분의 서버 애플리케이션은 코드 인스턴스가 하나뿐이어서 작업 집합 이득도 없다. 이 판단은 오늘날의 R2R에도 대체로 유효하다.
>
> 시작 시간이 아주 긴 대형 클라이언트 애플리케이션을 위해 **MPGO.exe**(Managed Profile Guided Optimization)라는 도구도 있었다. 애플리케이션을 MPGO로 실행하고 흔한 작업을 수행하면, 실행된 코드 정보가 프로파일로 어셈블리에 임베드되고 NGen이 그 프로파일로 더 나은 이미지를 만들었다. 이 도구 역시 .NET Framework 전용이다.

### ReadyToRun (R2R)

**ReadyToRun**은 게시(publish) 시점에 IL을 네이티브 코드로 미리 컴파일하되, **IL과 메타데이터도 함께 남겨두는** 방식이다. 도구는 `crossgen2`이고, 개발자는 MSBuild 속성으로만 쓴다.

```xml
<PropertyGroup>
  <PublishReadyToRun>true</PublishReadyToRun>
</PropertyGroup>
```

```text
dotnet publish -c Release -r linux-x64 --self-contained -p:PublishReadyToRun=true
```

R2R은 **RID(런타임 식별자)를 지정해야** 한다. 네이티브 코드는 특정 OS/아키텍처용이기 때문이다.

R2R 이미지는 하이브리드다.

```text
      일반 어셈블리                    R2R 어셈블리
  ┌─────────────────────┐        ┌─────────────────────────┐
  │ PE 헤더              │        │ PE 헤더                  │
  │ 메타데이터 테이블     │        │ 메타데이터 테이블         │
  │ IL 코드              │        │ IL 코드          ← 남아있다│
  │                     │        │ 네이티브 코드     ← 추가됨 │
  │                     │        │ R2R 헤더/픽스업 테이블     │
  └─────────────────────┘        └─────────────────────────┘
       파일 크기 1x                     파일 크기가 크게 늘어난다
```

IL이 남아 있는 이유는 두 가지다. **리플렉션과 메타데이터 접근이 여전히 필요하고**, 무엇보다 **네이티브 코드가 무효화될 때 JIT으로 폴백해야 하기 때문이다.**

### R2R 코드는 Tier-1 코드가 아니다

여기가 R2R을 이해하는 핵심이다. **R2R 코드는 계층형 컴파일 관점에서 "Tier-0 대체품"에 가깝다.**

| 항목 | R2R 코드 | Tier-1 JIT 코드 |
|---|---|---|
| 대상 CPU | **기준(baseline) 명령어 집합** | 실행 중인 CPU의 전체 기능 |
| `Avx2.IsSupported` | 기준 ISA를 넘는 검사는 접히지 않는다 | 실행 CPU 기준으로 접힌다 |
| 크로스 어셈블리 인라이닝 | **버전 버블 안에서만** | 제한 없음 |
| 정적 필드 접근 | 간접 참조 | 직접 주소 |
| 동적 PGO | 없음 | 있음 |
| 컴파일 시점 | 게시 시 | 실행 중 |

그래서 R2R 코드는 **호출 계수의 대상이 된다.** 뜨거워진 R2R 메서드는 55.5절의 그림대로 `Tier1-Instrumented`를 거쳐 `Tier1`으로 재컴파일된다. **R2R의 목적은 최고 성능이 아니라 최고 성능에 도달하기 전까지의 구간을 메우는 것이다.**

> **📌 버전 버블(version bubble)**
>
> R2R 컴파일러는 한 어셈블리의 코드를 컴파일하면서 **다른 어셈블리의 메서드를 인라이닝해도 되는가**라는 문제에 부딪힌다. 인라이닝했는데 나중에 그 어셈블리만 교체되면 낡은 코드가 남는다.
>
> **버전 버블**은 "함께 배포되고 함께 버전이 올라간다고 가정하는 어셈블리 묶음"이다. 버블 안에서는 인라이닝과 필드 오프셋 하드코딩이 허용된다. 버블 밖으로는 전부 간접 참조를 거친다.
>
> `<PublishReadyToRunComposite>true</PublishReadyToRunComposite>`는 자체 포함 배포에서 **모든 어셈블리를 하나의 버전 버블로 묶어** 단일 R2R 이미지를 만든다. 최적화 여지가 커지고 시작이 더 빨라지지만, 이미지가 커지고 어셈블리 하나만 교체하는 것이 불가능해진다.

> **⚠️ R2R을 켰는데 효과가 없다면**
>
> 다음을 순서대로 확인하라.
>
> 1. **RID를 지정했는가.** `-r` 없이 `PublishReadyToRun`만 켜면 아무 일도 일어나지 않는다.
> 2. **실제로 R2R 코드가 쓰이고 있는가.** `DOTNET_ReadyToRun=0`으로 한 번 돌려 시작 시간을 비교하라. 차이가 없으면 R2R 이미지가 로드되지 않고 있다.
> 3. **`Vector<T>`를 쓰는 메서드는 R2R 대상이 아니다.** `Vector<T>`의 크기가 CPU에 따라 달라지므로 `crossgen2`가 사전 컴파일을 건너뛴다. SIMD가 많은 코드에서는 R2R 커버리지가 낮게 나온다.
> 4. **`[MethodImpl(AggressiveOptimization)]`이 붙은 메서드도 제외된다.**
> 5. **제네릭 인스턴스화 대부분이 사전 컴파일되지 않는다.** `List<MyStruct>`처럼 다른 어셈블리의 제네릭을 내 값 타입으로 인스턴스화한 코드는 R2R 이미지에 없을 가능성이 높다.

### Native AOT

**Native AOT**는 접근이 근본적으로 다르다. 게시 시점에 **전체 프로그램을 네이티브 실행 파일로 컴파일하고, 결과물에는 JIT도 IL도 넣지 않는다.**

```xml
<PropertyGroup>
  <TargetFramework>net8.0</TargetFramework>
  <PublishAot>true</PublishAot>
  <InvariantGlobalization>true</InvariantGlobalization>
</PropertyGroup>
```

```text
dotnet publish -c Release -r win-x64
```

출력은 이렇게 된다.

```text
MSBuild version 17.8.0+4ce2ff1f8 for .NET
  Determining projects to restore...
  AotConsole -> ...\bin\Release\net8.0\win-x64\AotConsole.dll
  Generating native code
  AotConsole -> ...\bin\Release\net8.0\win-x64\publish\
```

`Generating native code`가 실제로 AOT 컴파일이 일어났다는 신호다. 결과 `AotConsole.exe`는 .NET 런타임이 설치되지 않은 시스템에서도 실행된다. 원서의 예제(간단한 콘솔 앱)에서는 약 1.2MB였다. 실제 크기는 코드와 쓰는 라이브러리에 따라 달라진다.

Native AOT가 주는 것은 다음과 같다.

- **자체 포함** — .NET 런타임이 설치되지 않은 시스템에서 실행된다.
- **가장 빠른 시작** — JIT이 없으므로 컴파일 대기가 아예 없다. 밀리초 단위 시작이 가능하다.
- **가장 작은 메모리 발자국** — JIT 작업 메모리도, 컴파일된 코드를 담을 동적 메모리도 필요 없다.
- **예측 가능한 지연 시간** — 계층 전이로 인한 성능 변동이 없다.

> **⚠️ 개발 중에는 AOT가 아니다**
>
> Native AOT는 **게시 시점에만** 일어난다. `<PublishAot>true</PublishAot>`를 켜고 F5로 디버깅하거나 `dotnet run`을 해도, 그때는 여전히 JIT으로 돌고 있다. AOT와 호환되지 않는 코드가 개발 중에는 멀쩡히 돌다가 게시 후에 깨지는 일이 흔하다.
>
> **게시를 해보기 전에는 AOT에서 동작한다고 가정하지 마라.** 다행히 게시 시 소스 분석기가 경고를 내주므로, **AOT 경고가 하나도 없는 게시**를 CI에서 강제하는 것이 실무적인 방어선이다.

### Native AOT가 못 하는 것

| 못 하는 것 | 왜 | 관련 절 |
|---|---|---|
| **동적 어셈블리 로딩** | 로드할 IL도, 컴파일할 JIT도 없다. `Assembly.LoadFrom`, 커스텀 ALC 플러그인 시스템이 동작하지 않는다 | 52.9절, 52.14절 |
| **런타임 코드 생성** | `System.Reflection.Emit`, `AssemblyBuilder`, `DynamicMethod`, 컴파일되는 식 트리(`Expression.Compile`) | 57.13절, 58장 |
| **`RegexOptions.Compiled`** | 내부적으로 `Reflection.Emit`을 쓴다. AOT에서는 인터프리터 방식으로 폴백된다 | — |
| **제약 없는 리플렉션** | 트리밍이 "리플렉션으로만 접근되는 멤버"를 정적으로 알 수 없어 제거해 버린다 | 57.14절 |
| **크로스 플랫폼 게시** | Linux에서 Windows용 AOT 바이너리를 만들 수 없다. **배포할 OS에서 게시해야 한다** | — |
| **일부 프레임워크** | ASP.NET Core MVC(컨트롤러 기반 Web API 포함)와 EF Core는 런타임 코드 생성을 쓴다. .NET 8은 **Minimal API에 대한 기본 지원**만 제공한다 | — |
| **C++/CLI** | 지원되지 않는다 | — |

> **⚠️ 리플렉션은 "안 되는" 것이 아니라 "덜 되는" 것이다**
>
> Native AOT도 리플렉션을 **어느 정도는** 지원한다. AOT 컴파일러가 정적으로 발견한 타입에 대해서는 `Type`, `MethodInfo`를 얻고 호출할 수 있다. 문제는 **트리밍**이다. AOT는 트리밍을 요구하고, 트리머는 "리플렉션으로만 접근되는 멤버"를 판별하지 못해 제거한다. 제거된 멤버에 리플렉션으로 접근하면 **런타임에 예외가 난다.**
>
> 해법은 트리머에게 알려주는 것이다.
>
> ```csharp
> static object Create(
>     [DynamicallyAccessedMembers(DynamicallyAccessedMemberTypes.PublicConstructors)]
>     Type t) => Activator.CreateInstance(t)!;
> ```
>
> 그리고 AOT에서 동작하지 않을 수 있는 API에는 `[RequiresDynamicCode]`가 붙어 있다. 이 특성이 붙은 멤버를 쓰면 게시 시 **IL3050** 경고가 난다.
>
> ```text
> warning IL3050: Using member 'System.Reflection.Emit.AssemblyBuilder.
> DefineDynamicAssembly(AssemblyName, AssemblyBuilderAccess)' which has
> 'RequiresDynamicCodeAttribute' can break functionality when AOT compiling.
> Defining a dynamic assembly requires dynamic code.
> ```
>
> 자세한 대응은 57.14절에서 다룬다. 근본 해법은 **소스 생성기**로 컴파일 타임에 코드를 만들어 리플렉션을 제거하는 것이다(57.15절).

> **📌 게시 전 준비물**
>
> Native AOT는 플랫폼 네이티브 링커를 쓴다. Windows에서는 Visual Studio 2022의 **C++를 사용한 데스크톱 개발** 워크로드가 기본 구성 요소와 함께 설치되어 있어야 한다. Ubuntu 18.04 이상 Linux에서는 다음이 필요하다.
>
> ```text
> sudo apt-get install clang zlib1g-dev
> ```

### 배포 방식 정리

셋을 비교하기 전에, 그와 직교하는 **배포 형태** 세 가지를 먼저 구분해야 한다.

| 형태 | 의미 | 명령 |
|---|---|---|
| **프레임워크 종속 배포(FDD)** | `.dll`을 배포하고 `dotnet` 명령으로 실행. 대상 머신에 런타임이 있어야 한다 | `dotnet publish -c Release` |
| **프레임워크 종속 실행 파일(FDE)** | `.exe`를 배포해 직접 실행. 여전히 런타임이 있어야 한다 | `dotnet publish -c Release -r win-x64 --no-self-contained` |
| **자체 포함(self-contained)** | 런타임까지 전부 포함. 런타임 설치가 필요 없다 | `dotnet publish -c Release -r win-x64 --self-contained` |

자체 포함 배포는 크다. 간단한 콘솔 앱 하나가 publish 폴더 기준 **68MB** 정도 나온다(실행 파일 자체는 154KB지만 나머지가 런타임이다). `PublishSingleFile`로 하나로 묶어도 62MB 안팎이다.

크기를 줄이는 것이 **트리밍**이다.

```xml
<!-- ① 타입·멤버 수준(full) 트리밍 — .NET 6 이후의 기본 모드이므로 켜기만 하면 된다 -->
<PublishTrimmed>true</PublishTrimmed>
```

```xml
<!-- ② 어셈블리 수준(partial) 트리밍 — 모드를 명시해야 한다 -->
<PublishTrimmed>true</PublishTrimmed>
<TrimMode>partial</TrimMode>
```

.NET Core 3에서 도입될 때는 사용되지 않는 어셈블리만 제거했고(`copyused`), .NET 5부터 개별 타입과 멤버까지 제거하게 되었으며(`link`), .NET 6부터 BCL에 트리밍 주석이 붙으면서 **타입·멤버 수준 트리밍이 기본값**이 되었다. .NET 7에서 이름이 각각 `full`과 `partial`로 바뀌었다.

> **⚠️ `.NET Framework`에는 이 선택지들이 아예 없다**
>
> .NET Framework 애플리케이션은 항상 머신에 설치된 프레임워크에 의존한다. 자체 포함 배포도, 트리밍도, R2R도, Native AOT도 없다. 있는 것은 NGen뿐이다. 마이그레이션 계획을 세울 때 이 차이가 배포 전략 전체를 바꾼다.

### JIT / R2R / Native AOT 비교

| 항목 | JIT (계층형) | ReadyToRun | Native AOT |
|---|---|---|---|
| 컴파일 시점 | 실행 중 | 게시 시 + 실행 중(Tier-1) | 게시 시 |
| **시작 시간** | 가장 느림 | 빠름 | **가장 빠름** |
| **워밍업 후 처리량** | **가장 높음** | 가장 높음(Tier-1 재컴파일 후) | 중간 |
| 동적 PGO / GDV | 있음 | 있음(Tier-1에서) | **없음** |
| CPU 고유 명령 | 실행 머신에 맞춤 | 기준 ISA(Tier-1 후 개선) | 게시 시 지정한 대상 |
| **배포 크기** | 가장 작음(FDD) | 중간(IL+네이티브) | 큼(단일 실행 파일) |
| 메모리 발자국 | 큼(JIT 작업 메모리) | 중간 | **가장 작음** |
| 런타임 설치 필요 | 예(FDD/FDE) | 예/아니오 | **아니오** |
| 리플렉션 | 전부 | 전부 | 제한적 |
| `Reflection.Emit` | 가능 | 가능 | **불가** |
| 동적 어셈블리 로드 | 가능 | 가능 | **불가** |
| 크로스 컴파일 게시 | 해당 없음 | **가능** | **불가** |
| 트리밍 필요 | 아니오 | 아니오 | **필수** |
| .NET Framework 대응물 | JIT | NGen(다른 설계) | 없음 |

> **💡 무엇을 언제 쓰나**
>
> - **장기 실행 서버(ASP.NET Core, 백그라운드 워커)** — 기본 JIT + 계층형 컴파일 + 동적 PGO. 시작 시간이 SLA에 걸린다면 R2R을 추가한다. 워밍업 요청을 몇 개 보내는 것이 더 효과적인 경우도 많다.
> - **컨테이너에서 자주 재시작되는 서비스, 자동 확장이 잦은 워크로드** — R2R. 콜드 스타트가 반복적으로 비용이 된다.
> - **서버리스 함수, CLI 도구, 사이드카** — Native AOT. 프로세스가 짧게 살고 시작 시간이 전부다.
> - **계산 집약적 장기 실행 작업** — **JIT을 쓰라.** Native AOT는 동적 PGO와 CPU 고유 명령 선택을 잃는다. 몇 시간 도는 계산 작업에서 시작 시간 몇십 밀리초는 무의미하고, 처리량 차이는 누적된다.
> - **플러그인 아키텍처, 직렬화 프레임워크, ORM** — Native AOT는 사실상 불가능하다. 소스 생성기로 전환할 계획이 없다면 시도하지 마라.
>
> 그리고 **셋 다 측정으로 결정하라.** "AOT가 빠르다"는 시작 시간에 대해서만 무조건 참이다. 처리량은 반대일 수 있다.

## 55.8 SharpLab / `DOTNET_JitDisasm`으로 생성 코드 읽기

앞의 여섯 절에서 계속 "디스어셈블리를 보라"고 했다. 이제 실제로 보는 방법이다. 도구는 셋이고, 용도가 다르다.

| 도구 | 얻는 것 | 언제 |
|---|---|---|
| **SharpLab** (sharplab.io) | 짧은 코드 조각의 IL / 최적화된 x64 / 컴파일러가 낮춘 C# | 빠른 실험, 문법이 무엇으로 바뀌는지 확인 |
| **`DOTNET_JitDisasm`** | 실제 애플리케이션에서 실제로 컴파일된 코드, 계층 포함 | 진짜 문제를 조사할 때 |
| **BenchmarkDotNet `[DisassemblyDiagnoser]`** | 벤치마크 대상 메서드의 디스어셈블리 | 성능 비교와 함께 볼 때 |

### SharpLab

브라우저만 있으면 된다. 왼쪽에 C# 코드를 붙여넣고, 상단에서 다음을 고른다.

- **Release** 구성 (Debug로 두면 최적화되지 않은 코드가 나온다)
- **Results: JIT Asm**

```csharp
public class C
{
    public int Sum(int[] data)
    {
        int total = 0;
        for (int i = 0; i < data.Length; i++)
            total += data[i];
        return total;
    }
}
```

오른쪽에 나오는 것은 대략 이런 형태다.

```text
C.Sum(Int32[])
    L0000: mov r8d, [rdx+8]     ; len = data.Length  (인스턴스 메서드라 this=rcx, data=rdx)
    L0004: xor eax, eax         ; total = 0
    L0006: xor ecx, ecx         ; i = 0
    L0008: test r8d, r8d
    L000b: jle short L001c
    ...
    L001c: ret
```

위 리스팅도 형태를 보인 예시다. 실제 출력은 버전·CPU·운영체제에 따라 달라진다(55.2절의 ⚠️).

> **⚠️ SharpLab에서 메서드가 사라지는 이유**
>
> SharpLab의 JIT Asm 출력에서 원하는 메서드가 안 보이거나 본문이 텅 비어 있다면 대개 다음 중 하나다.
>
> - **메서드가 인라이닝되었다.** 확인하려면 `[MethodImpl(MethodImplOptions.NoInlining)]`을 붙여라.
> - **인수가 상수라서 전부 접혔다.** 매개변수를 받도록 바꿔라.
> - **결과를 쓰지 않아 죽은 코드로 제거되었다.** 반환하거나 필드에 저장하라.
> - **`private`/`static`이라 도달 불가로 판정되었다.** `public`으로 바꿔라.
>
> 좋은 습관은 조사 대상을 **`public` 인스턴스 메서드로, 매개변수를 받고, 값을 반환하도록** 만드는 것이다.

> **📌 SharpLab이 보여주는 것은 완전 최적화 코드다**
>
> SharpLab의 JIT Asm은 Tier-0이 아니라 **완전 최적화 계층**의 코드다. 그래서 "실제 실행 중에 이 코드가 나온다"는 보장이 없다 — 그 메서드가 Tier-1까지 승격되어야 한다. 시작 경로의 성능을 조사할 때는 SharpLab만으로 부족하다.
>
> 또한 SharpLab은 **동적 PGO 프로파일이 없다.** 그래서 GDV(55.5절)가 적용된 코드는 SharpLab에서 볼 수 없다. GDV를 확인하려면 실제 애플리케이션에서 `DOTNET_JitDisasm`을 써야 한다.

SharpLab의 다른 출력 모드도 유용하다.

| Results 설정 | 보여주는 것 | 쓰임 |
|---|---|---|
| **C#** | 컴파일러가 낮춘(lowered) C# | `foreach`, `using`, `async`, 레코드, 패턴 매칭이 무엇으로 바뀌는지 (56.6절) |
| **IL** | 실제 IL | 56장 전체 |
| **JIT Asm** | 최적화된 x64/ARM64 | 이 장 |
| **Syntax Tree** | Roslyn 구문 트리 | 분석기·소스 생성기 작성 시 |

### `DOTNET_JitDisasm` — 실제 프로세스의 코드 보기

※.NET 7부터 JIT 디스어셈블리 관련 스위치가 **릴리스 런타임에서도** 동작한다. 그 이전에는 체크드(checked) 런타임 빌드가 필요했다. 이것은 실무에서 매우 큰 차이다 — 이제 아무 머신에서나 환경 변수 하나로 생성 코드를 볼 수 있다.

| 환경 변수 | 값 | 효과 |
|---|---|---|
| `DOTNET_JitDisasm` | 메서드 패턴 | 해당 메서드의 디스어셈블리를 출력 |
| `DOTNET_JitDisasmSummary` | `1` | 컴파일된 모든 메서드를 한 줄씩 요약(계층 포함) |
| `DOTNET_JitStdOutFile` | 파일 경로 | 출력을 파일로 보낸다(콘솔 출력과 섞이지 않는다) |
| `DOTNET_JitDisasmDiffable` (구 `DOTNET_JitDiffableDasm`) | `1` | 주소·상수를 지워 두 출력의 diff를 가능하게 한다 |
| `DOTNET_JitDisasmWithGC` | `1` | GC 정보를 함께 출력 |

메서드 패턴은 여러 형태를 받는다.

```text
DOTNET_JitDisasm=Sum                     메서드 이름이 Sum인 것 전부
DOTNET_JitDisasm=Program:Sum             Program 타입의 Sum
DOTNET_JitDisasm=Program:*               Program 타입의 모든 메서드
DOTNET_JitDisasm=*                       전부 (출력이 엄청나다)
DOTNET_JitDisasm="Sum Copy Clamp"        공백으로 여러 개
```

전형적인 조사 절차는 이렇다.

```text
# 1) 어떤 메서드가 어느 계층으로 컴파일되었는지 전체 지도부터
set DOTNET_JitDisasmSummary=1
set DOTNET_JitStdOutFile=C:\temp\summary.txt
dotnet run -c Release

# 2) 관심 메서드를 정해서 완전 최적화 코드만 뽑는다
set DOTNET_JitDisasmSummary=
set DOTNET_JitDisasm=Program:Sum
set DOTNET_TieredCompilation=0
set DOTNET_JitStdOutFile=C:\temp\sum-opt.txt
dotnet run -c Release

# 3) 옵션 하나만 바꿔서 다시 뽑고 비교한다
set DOTNET_TieredPGO=0
set DOTNET_JitStdOutFile=C:\temp\sum-nopgo.txt
dotnet run -c Release
```

Linux/macOS에서는 한 줄로 붙일 수 있다.

```text
DOTNET_JitDisasm='Program:Sum' DOTNET_TieredCompilation=0 \
  DOTNET_JitStdOutFile=/tmp/sum.txt dotnet run -c Release
```

### 출력 읽는 법

전형적인 `DOTNET_JitDisasm` 출력의 구조다.

```text

;

                                                ;; size=0 bbWeight=1 PerfScore 0.00

       mov      r8d, dword ptr [rcx+0x08]
       test     r8d, r8d

                                                ;; size=13 bbWeight=1 PerfScore 3.50
G_M12345_IG03:        ;; offset=0x000D
       mov      r10d, edx
       add      eax, dword ptr [rcx+r10*4+0x10]
       inc      edx
       cmp      r8d, edx
       jg       SHORT G_M12345_IG03
                                                ;; size=13 bbWeight=4 PerfScore 13.00

                                                ;; size=1 bbWeight=1 PerfScore 1.00

```

주석 헤더에서 읽어야 할 것들이다.

| 줄 | 의미 |
|---|---|
| `(Tier1)` | 계층. `Tier0`, `Tier1-OSR`, `FullOpts` 등 (55.3절 표) |
| `Emitting BLENDED_CODE for X64 CPU with AVX2` | JIT이 대상으로 삼은 명령어 집합. R2R이었다면 훨씬 낮은 기준이 나온다 |
| `rsp based frame` / `rbp based frame` | 프레임 포인터 생략 여부. Tier-0은 대개 `rbp` |
| `No PGO data` / `... inlinees with PGO data` | 동적 PGO 프로파일이 쓰였는지 |
| `Final local variable assignments` | 각 지역 변수가 어느 레지스터에 배정되었는지. `-> rax`면 레지스터, `->  [rbp-0x08]`이면 스택 |
| `bbWeight` | 그 블록의 상대 실행 빈도 추정. 루프 본문이 1보다 크다 |
| `PerfScore` | JIT의 내부 비용 추정치. 절대값은 의미 없고 **같은 메서드의 두 버전을 비교할 때** 쓴다 |

`G_M12345_IG02` 같은 레이블은 **기본 블록(basic block)** 경계다. `IG`는 insertion group을 뜻한다.

> **💡 두 버전을 diff하는 요령**
>
> `DOTNET_JitDisasmDiffable=1`을 주면 메모리 주소, 메서드 핸들 값, `G_M12345` 같은 메서드 번호가 안정적인 형태로 바뀐다. 그래야 diff가 의미 있게 나온다.
>
> ```text
> DOTNET_JitDisasmDiffable=1 DOTNET_JitDisasm='Program:Sum' \
>   DOTNET_JitStdOutFile=/tmp/a.txt dotnet run -c Release
>
> # 코드를 고친 뒤
> DOTNET_JitDisasmDiffable=1 DOTNET_JitDisasm='Program:Sum' \
>   DOTNET_JitStdOutFile=/tmp/b.txt dotnet run -c Release
>
> diff -u /tmp/a.txt /tmp/b.txt
> ```
>
> "이 리팩터링이 생성 코드를 바꿨는가"라는 질문에 30초 안에 답할 수 있다.

> **⚠️ 계층화를 끄지 않으면 같은 메서드가 두 번 나온다**
>
> `DOTNET_JitDisasm`은 **컴파일될 때마다** 출력한다. 계층화가 켜져 있으면 Tier-0, (계측 계층), Tier-1이 각각 나온다. 처음 보면 "같은 메서드가 왜 세 번 나오지" 하고 당황하게 된다.
>
> 최종 코드만 보고 싶으면 `DOTNET_TieredCompilation=0`을, 계층 전이를 관찰하고 싶으면 그대로 두면 된다. **다만 계층화를 끄면 동적 PGO도 함께 꺼진다** — Tier-1 코드가 프로파일 없이 만들어지므로 GDV가 사라진다. GDV를 보고 싶으면 계층화를 켠 채 뽑고 마지막 `(Tier1)` 블록을 읽어라.

### BenchmarkDotNet의 `[DisassemblyDiagnoser]`

성능 수치와 디스어셈블리를 함께 보고 싶을 때가 가장 많다. BenchmarkDotNet이 이것을 해준다.

```csharp
using BenchmarkDotNet.Attributes;
using BenchmarkDotNet.Running;

[DisassemblyDiagnoser(maxDepth: 3, printSource: true)]
[MemoryDiagnoser]
public class SumBench
{
    private int[] _data = null!;

    [GlobalSetup]
    public void Setup() => _data = Enumerable.Range(0, 10_000).ToArray();

    [Benchmark(Baseline = true)]
    public int Loop()
    {
        int total = 0;
        for (int i = 0; i < _data.Length; i++) total += _data[i];
        return total;
    }

    [Benchmark]
    public int Linq() => _data.Sum();
}

BenchmarkRunner.Run<SumBench>();
```

실행하면 `BenchmarkDotNet.Artifacts/results/` 아래에 `*-asm.md`와 `*-asm.html` 파일이 생긴다. `maxDepth`는 호출된 메서드를 몇 단계까지 따라 들어가 디스어셈블할지다 — 인라이닝되지 않은 호출을 추적할 때 올린다.

> **📌 BenchmarkDotNet은 워밍업을 통해 Tier-1 코드를 측정한다**
>
> BenchmarkDotNet의 디스어셈블리는 **실제로 측정에 쓰인 코드**다. 즉 계층 승격이 끝난 뒤의 코드이고, 동적 PGO 프로파일도 반영되어 있다. SharpLab과 `DOTNET_JitDisasm`의 중간쯤에 있으면서 성능 수치까지 붙어 나오므로, **"왜 이쪽이 빠른가"를 설명해야 할 때 가장 좋은 도구**다. 자세한 사용법은 67.3절에서 다룬다.

### 어셈블리를 읽을 때 알아둘 최소한

x64 어셈블리 전체를 배울 필요는 없다. 이 장의 목적에는 다음 정도면 충분하다.

| 패턴 | 의미 |
|---|---|
| `mov rax, [rcx+0x08]` | 객체 `rcx`의 오프셋 8을 읽는다. 배열이면 `Length`(54.7절) |
| `[rcx+rdx*4+0x10]` | 배열 원소 접근. `0x10`이 x64 배열의 데이터 시작 오프셋 |
| `cmp` + `jae` 뒤에 `RNGCHKFAIL` | **경계 검사** (55.6절) |
| `call CORINFO_HELP_...` | JIT 헬퍼 호출. `RNGCHKFAIL`(범위), `NEWSFAST`(할당), `CHKCASTCLASS`(형변환) 등 |
| `call qword ptr [rax+0x??]` | **간접 호출.** 가상 호출이 남아 있다 |
| `cmp rax, <큰 상수>` + `jne` | **GDV 가드** 또는 형변환 검사 (55.5절) |
| `test rcx, rcx` + `je` | **null 검사** |
| `vmovsd`, `vaddps`, `vpaddd` | SIMD 명령. AVX 계열이면 `v` 접두사가 붙는다 |
| 프롤로그 `push rbp` / `sub rsp, N` 없음 | 프레임리스 함수. 최적화된 작은 메서드의 표시 |

> **💡 null 검사는 대개 공짜다**
>
> `test rcx, rcx` + `je`가 항상 나오는 것은 아니다. JIT은 **어차피 그 객체의 필드를 읽는다면** 명시적 null 검사를 생략한다. 주소 0 근처 페이지는 매핑되어 있지 않으므로, null 참조 접근은 하드웨어 액세스 위반을 일으키고 런타임이 그것을 잡아 `NullReferenceException`으로 바꾼다. **null 검사가 메모리 접근에 흡수된 것**이다.
>
> 그래서 디스어셈블리에 명시적 null 검사가 안 보인다고 검사가 없는 것은 아니다. 반대로 명시적 `test`가 보인다면, 그 시점에 실제 메모리 접근이 뒤따르지 않는 경로(예: 필드 오프셋이 페이지 크기보다 큰 거대 구조체, 메서드 호출 전 수신자 검사)라는 뜻이다.

## 55.9 JIT을 도와주는 코드 vs 방해하는 코드

앞의 여덟 절을 실전 목록으로 압축한다. 원칙은 하나다. **JIT이 무언가를 증명할 수 있게 만들어라.** JIT의 모든 최적화는 증명 위에 서 있다 — 이 인덱스가 범위 안이라는 증명, 이 호출의 수신자가 이 타입이라는 증명, 이 객체가 탈출하지 않는다는 증명. 증명을 어렵게 만드는 코드가 곧 JIT을 방해하는 코드다.

### 반복문

| 도와주는 코드 | 방해하는 코드 | 이유 |
|---|---|---|
| `for (int i = 0; i < arr.Length; i++)` | `for (int i = 0; i < n; i++)` (`n`이 별도 매개변수) | 경계 검사 제거 표준형 (55.6절) |
| `foreach (var x in arr)` / `foreach (var x in span)` | `foreach (var x in (IEnumerable<T>)arr)` | 인터페이스로 올리면 구조체 열거자가 박싱되고 역가상화가 깨진다 |
| `arr.AsSpan(0, n)`으로 자른 뒤 순회 | 원본 배열에 `n`을 상한으로 인덱싱 | 검사 N번 → 1번 |
| 루프 안에서 배열 참조를 재할당하지 않음 | 루프 안에서 `arr = something` | 길이 불변 가정이 깨진다 |
| 루프 본문을 작게 유지 | 거대한 루프 본문 | 루프 클로닝·펼치기 임계값을 넘긴다 |

```csharp
// 방해: 인터페이스를 통해 배열을 순회한다
static int Count(IEnumerable<int> items)
{
    int c = 0;
    foreach (int x in items) c++;    // 인터페이스 호출 × 2 (MoveNext, Current)
    return c;
}

// 도움: 구조체 열거자가 그대로 쓰이고, 인라이닝되고, 경계 검사가 사라진다
static int Count(ReadOnlySpan<int> items)
{
    int c = 0;
    foreach (int x in items) c++;
    return c;
}
```

### 타입과 호출

| 도와주는 코드 | 방해하는 코드 | 이유 |
|---|---|---|
| `sealed class` | 불필요하게 열린 클래스 | 정적 역가상화 (55.5절) |
| `sealed override` | 재정의 가능한 채로 두기 | 같은 이유 |
| 구조체 제약 제네릭 (`where T : struct, IFoo`) | 참조 타입 제네릭 + 인터페이스 호출 | 값 타입은 인스턴스화별 코드가 생겨 역가상화·인라이닝이 된다 |
| 인터페이스를 정말 필요할 때만 | 모든 클래스에 인터페이스를 붙이는 습관 | 인터페이스 디스패치는 가상 호출보다 비싸다 (54.1절) |
| 델리게이트를 필드에 캐싱 | 호출 지점마다 람다 생성 | 델리게이트 GDV가 안정적으로 걸리고 할당도 줄어든다 |
| `static` 람다 (`static x => ...`) | 클로저를 캡처하는 람다 | 클로저 클래스 할당이 사라진다 |

> **⚠️ 인터페이스는 설계 도구이지 성능 도구가 아니다**
>
> "모든 것에 인터페이스를 붙인다"는 습관은 테스트 용이성이라는 이름으로 정당화되지만 대가가 있다. 인터페이스 호출은 가상 스텁 디스패치를 거치고, 인라이닝을 막고, 그 결과 55.4절 표의 후속 최적화 전부를 막는다.
>
> 동적 PGO의 GDV가 많은 경우를 구제하지만 **구제하지 못하는 경우도 있다** — 구현이 여러 개 섞여 도는 다형적 호출 지점, 워밍업 전 구간, `AggressiveOptimization`이 붙은 메서드, Native AOT.
>
> 뜨거운 경로에서는 인터페이스 대신 **구조체 제약 제네릭**을 고려하라.
>
> ```csharp
> // 인터페이스: 호출마다 디스패치
> static long Sum(IEnumerable<int> src) { ... }
>
> // 구조체 제약 제네릭: TEnum마다 전용 코드가 생기고 전부 인라이닝된다
> static long Sum<TEnum>(TEnum e) where TEnum : struct, IEnumerator<int> { ... }
> ```

### 메서드 구조

| 도와주는 코드 | 방해하는 코드 | 이유 |
|---|---|---|
| 뜨거운 경로를 작게, 예외 던지기를 별도 메서드로 | 뜨거운 메서드 본문에 `throw new ...(긴 메시지)` | IL 크기가 커져 인라이닝 후보에서 탈락 (55.4절) |
| `try`/`catch`를 뜨거운 메서드 밖에 배치 | 작은 헬퍼 안에 `try`/`catch` | 예외 처리 블록이 있으면 인라이닝 불가 |
| 인수 유효성 검사를 얇게 (`(uint)i >= (uint)n`) | 여러 조건과 문자열 보간이 섞인 검사 | 같은 이유 |
| 매개변수 개수를 적게 | 인수를 계속 늘리는 시그니처 | 레지스터로 전달되는 인수 개수가 정해져 있다(Windows x64는 정수 4개, System V x64는 6개). 그 수를 넘으면 나머지는 스택으로 간다 |
| 큰 구조체는 `in`/`ref`로 전달 | 큰 구조체를 값으로 전달 | 복사 비용. `in`은 읽기 전용 참조로 넘긴다 |

> **⚠️ `in` 매개변수에는 함정이 있다**
>
> `in`은 큰 구조체의 복사를 없애지만, **`readonly struct`가 아닌 구조체에 `in`을 쓰면 오히려 방어적 복사(defensive copy)가 생긴다.** 컴파일러는 그 구조체의 메서드 호출이 상태를 바꿀 수 있다고 보고, 안전을 위해 호출 전에 복사본을 만든다.
>
> ```csharp
> struct Big { public int A, B, C, D, E, F, G, H; public int Sum() => A + B + C + D + E + F + G + H; }
>
> static int Use(in Big b) => b.Sum();   // b의 복사본을 만든 뒤 Sum() 호출
> ```
>
> `readonly struct Big`으로 선언하면 복사가 사라진다. **`in`을 쓰려면 `readonly struct`가 함께 가야 한다.**

### 값과 상수

| 도와주는 코드 | 방해하는 코드 | 이유 |
|---|---|---|
| `const` / `static readonly` | `static` 가변 필드 | ※.NET 8부터 `static readonly` 기본형이 Tier-1에서 상수로 접힌다 |
| `Avx2.IsSupported` 분기 | 런타임 설정 값으로 SIMD 경로 선택 | JIT-타임 상수 폴딩 (55.6절) |
| `typeof(T) == typeof(int)` (값 타입 제네릭) | `T`를 `object`로 박싱해 타입 검사 | 상수로 접히고 박싱이 사라진다 |
| 배열 길이를 조건식에 직접 사용 | 길이를 미리 계산해 여러 변수에 나눠 보관 | 범위 분석이 추적할 수 있게 |

### 할당과 수명

| 도와주는 코드 | 방해하는 코드 | 이유 |
|---|---|---|
| 지역 변수로만 쓰이는 작은 객체 | 그 객체를 필드에 저장하거나 다른 메서드로 넘김 | 이스케이프 분석 (55.6절) |
| `Span<T>` / `stackalloc` | 임시 배열 할당 | 애초에 힙을 안 쓴다 (68.9절) |
| `ArrayPool<T>` 대여 | 반복적인 `new T[n]` | GC 압력 |
| `struct` 열거자 | 클래스 열거자 | 할당 없음 + 인라이닝 가능 |

> **💡 이스케이프 분석에 기대지 말고 구조를 바꿔라**
>
> 55.6절에서 본 것처럼 .NET 9의 객체 스택 할당은 제약이 매우 많다. **"작은 클래스를 지역 변수로만 쓰면 JIT이 스택에 올려주겠지"라고 기대하는 것은 위험하다.** 배열도, 문자열도, 박싱도, 루프 안 할당도 전부 제외된다.
>
> 할당을 확실히 없애려면 여전히 (1) 구조체로 바꾸거나, (2) `Span<T>`/`stackalloc`을 쓰거나, (3) 풀링해야 한다. 이스케이프 분석은 그 위에 얹히는 보너스로 취급하라.

### 계층형 컴파일과의 상호작용

| 도와주는 코드 | 방해하는 코드 | 이유 |
|---|---|---|
| 짧은 메서드를 여러 번 호출 | 하나의 거대한 메서드에 전부 몰아넣기 | 호출 계수가 쌓여야 Tier-1이 된다 |
| 뜨거운 루프를 별도 메서드로 분리 | `Main` 안에 모든 로직 | OSR에 의존하지 않아도 된다 (55.3절) |
| 아무것도 안 붙임 (기본값 신뢰) | `AggressiveOptimization` 남발 | 동적 PGO와 R2R을 잃는다 (55.2절) |
| 워밍업 후 측정 | 첫 실행 시간을 성능 지표로 사용 | Tier-0을 측정하게 된다 (67.4절) |

### 종합 예제 — 하나씩 고쳐나가기

세 번의 리팩터링으로 생성 코드가 어떻게 달라지는지 보자. 요구사항은 "정수 배열에서 임계값을 넘는 원소의 합"이다.

**1단계 — 흔한 첫 구현**

```csharp
public interface IFilter { bool Match(int value); }

public class ThresholdFilter : IFilter
{
    private readonly int _threshold;
    public ThresholdFilter(int t) => _threshold = t;
    public bool Match(int value) => value > _threshold;
}

public long SumMatching(List<int> data, IFilter filter)
{
    long sum = 0;
    for (int i = 0; i < data.Count; i++)
    {
        if (filter.Match(data[i]))
            sum += data[i];
    }
    return sum;
}
```

생성 코드에 남는 것: `List<int>` 인덱서 호출(인라이닝될 수는 있다), 인덱서 안의 경계 검사, **인터페이스 호출 `filter.Match`** (동적 PGO가 붙으면 GDV로 개선될 수 있다), `data[i]`의 중복 접근.

**2단계 — 클래스를 `sealed`로, 컬렉션을 `Span`으로**

```csharp
public sealed class ThresholdFilter : IFilter { /* 동일 */ }

public long SumMatching(int[] data, IFilter filter)
{
    ReadOnlySpan<int> span = data;
    long sum = 0;
    for (int i = 0; i < span.Length; i++)
    {
        int v = span[i];                 // 한 번만 읽는다
        if (filter.Match(v)) sum += v;
    }
    return sum;
}
```

경계 검사가 사라지고, 인덱서 호출이 사라지고, 중복 접근이 사라졌다. `filter.Match`는 여전히 인터페이스 호출이지만 `ThresholdFilter`가 `sealed`라서, **호출 지점에서 정적 타입이 `ThresholdFilter`인 경우에는** 역가상화된다. 매개변수 타입이 `IFilter`인 한 여전히 프로파일에 의존한다.

**3단계 — 구조체 제약 제네릭**

```csharp
public readonly struct ThresholdFilter : IFilter
{
    private readonly int _threshold;
    public ThresholdFilter(int t) => _threshold = t;
    public bool Match(int value) => value > _threshold;
}

public long SumMatching<TFilter>(ReadOnlySpan<int> span, TFilter filter)
    where TFilter : struct, IFilter
{
    long sum = 0;
    for (int i = 0; i < span.Length; i++)
    {
        int v = span[i];
        if (filter.Match(v)) sum += v;   // 제약된 호출 → 직접 호출 → 인라이닝
    }
    return sum;
}
```

`TFilter`가 값 타입이므로 `SumMatching<ThresholdFilter>`는 **전용 네이티브 코드**를 얻는다. `filter.Match`는 제약된 호출(`constrained.`)로 컴파일되고 JIT이 정확한 구현으로 해석해 인라이닝한다. 최종 루프 본문은 대략 이렇게 된다.

```text
G_M000_IG03:
       mov      r10d, dword ptr [rcx+rdx*4+0x10]   ; v = span[i]
       cmp      r10d, r9d                          ; v > _threshold   ← 인라이닝됨
       jle      SHORT G_M000_IG05
       movsxd   r10, r10d
       add      rax, r10                           ; sum += v
G_M000_IG05:
       inc      edx
       cmp      r8d, edx
       jl       SHORT G_M000_IG03
```

호출도, 경계 검사도, 인터페이스 디스패치도 남지 않았다. **이것이 "JIT이 증명할 수 있게 만든" 코드다.**

> **⚠️ 3단계를 모든 코드에 적용하지 마라**
>
> 구조체 제약 제네릭은 강력하지만 대가가 있다.
>
> - **코드 크기 폭증.** 타입 인수마다 별도 네이티브 코드가 생긴다. 필터 종류가 20개면 `SumMatching`이 20벌 컴파일된다.
> - **JIT 시간 증가.** 각 인스턴스화가 첫 호출 때 컴파일된다.
> - **가독성 저하.** 제네릭 매개변수가 시그니처에 번지고 호출부가 장황해진다.
>
> 이 기법은 **프로파일러가 그 호출 지점을 지목했을 때만** 쓴다. `System.Text.Json`, `System.Linq` 내부, `SearchValues` 같은 BCL의 뜨거운 경로가 정확히 이 패턴을 쓰는 이유이고, 그것은 그 코드가 수억 번 실행되기 때문이다.

## 이 장의 요약

- **CLR은 IL을 실행하지 않는다.** 메서드가 처음 호출되는 순간 JIT(RyuJIT)이 IL을 대상 CPU의 기계어로 번역한다. 호출되지 않는 메서드는 영원히 컴파일되지 않는다.
- **백패칭이 핵심 메커니즘이다.** `MethodDesc`의 진입점이 프리코드를 가리키고, 프리코드가 프리스텁으로 점프하고, 프리스텁이 JIT을 호출한 뒤 **프리코드 안의 워드 하나를 고쳐** 이후 호출이 곧바로 네이티브 코드로 가게 만든다. 안정적인 간접 층이 있기에 계층형 컴파일도 가능하다.
- **계층형 컴파일은 시작 시간과 처리량의 딜레마를 두 번 컴파일해서 푼다.** Tier-0은 빠르게·최적화 없이, Tier-1은 느리게·완전 최적화로. 승격 임계값은 호출 30회이지만 호출 계수 지연(100ms)이 함께 작동하므로 실제 시점은 비결정적이다.
- **OSR이 "긴 루프가 Tier-0에 갇히는" 문제를 해결했다** ※.NET 7. 패치포인트가 실행 중인 프레임을 최적화된 OSR 프레임으로 교체한다. 덕분에 루프가 있는 메서드도 Tier-0에서 출발할 수 있게 되었다.
- **인라이닝은 다른 모든 최적화의 전제다.** 상수 전파, 스칼라 대체, 이스케이프 분석, 경계 검사 제거가 전부 인라이닝 뒤에 열린다. `AggressiveInlining`은 크기·수익성 검사만 건너뛸 뿐 하드 블로커(예외 처리 블록 등)를 무시하지 않으며, 명령어 캐시 압박과 레지스터 압박으로 역효과를 낼 수 있다.
- **동적 PGO와 GDV가 인터페이스 호출의 비용을 지운다** ※.NET 8 기본값. 계측 계층이 클래스 프로파일을 모으고, Tier-1이 `MethodTable` 비교 한 줄을 가드로 삼아 역가상화 + 인라이닝한다. 단형에 가까운 호출 지점에서만 이득이다.
- **경계 검사 제거는 증명의 문제다.** `for (int i = 0; i < arr.Length; i++)`가 표준형이고, 상한이 다른 변수이거나 인덱스가 파생식이면 검사가 남는다. 확인 방법은 디스어셈블리에서 `CORINFO_HELP_RNGCHKFAIL`을 찾는 것이고, 확실한 해법은 `AsSpan(0, n)`으로 재슬라이싱하는 것이다.
- **RyuJIT이 하지 않는 것도 분명하다.** 일반 루프 자동 벡터화, 프로시저 간 이스케이프 분석, 전역 프로그램 최적화, 부동소수점 재결합은 하지 않는다. 밀리초 단위 시간 예산 안에서 값이 큰 최적화만 고른다.
- **R2R은 Tier-1의 대체가 아니라 Tier-0의 대체다.** 기준 명령어 집합으로 컴파일되고 버전 버블 밖으로는 인라이닝하지 못하므로, 뜨거워진 R2R 메서드는 결국 Tier-1으로 재컴파일된다. NGen은 .NET Framework 전용이고 R2R과 설계 전제가 다르다.
- **Native AOT는 JIT을 없애는 대신 동적성을 포기한다.** `Reflection.Emit`, 동적 어셈블리 로딩, 무제한 리플렉션, 크로스 플랫폼 게시가 불가능하고 트리밍이 필수다. 시작 시간이 전부인 워크로드에는 최선이고, 장기 실행 계산 작업에는 오히려 손해일 수 있다.
- **환경 변수는 `DOTNET_` 접두사를 쓰고 값은 16진수로 해석된다.** 레거시 `COMPlus_`도 인식되며, .NET Framework에서는 `COMPlus_`만 통한다.

## 연습 문제

1. 간단한 콘솔 앱에서 `DOTNET_JitDisasmSummary=1`과 `DOTNET_JitStdOutFile`을 설정하고 실행하라. 컴파일된 메서드 수를 세고, `Tier0`·`Tier1`·`FullOpts` 각각이 몇 개인지 세라. 그다음 `DOTNET_TieredCompilation=0`으로 다시 실행해 목록이 어떻게 달라지는지 비교하라.
2. 55.2절의 `Sum(int[])` 메서드를 그대로 만들고, 100만 원소 배열로 1회만 호출하는 프로그램과 100회 호출하는 프로그램을 각각 작성하라. `DOTNET_JitDisasm=Sum`으로 두 경우의 출력을 뽑아 계층이 어떻게 달라지는지 확인하라.
3. 20억 번 도는 단일 루프를 가진 메서드를 작성하고 `DOTNET_JitDisasmSummary=1`로 `Tier1-OSR` 항목이 나타나는지 확인하라. 그다음 `DOTNET_TC_OnStackReplacement=0`으로 끄고 실행 시간을 비교하라.
4. 55.6절 표의 여섯 가지 루프 형태를 각각 메서드로 만들고, `DOTNET_JitDisasm`으로 뽑아 `CORINFO_HELP_RNGCHKFAIL`이 몇 번 나오는지 세라. 자신이 쓰는 .NET 버전에서 표와 다른 결과가 나오는 항목이 있는가?
5. 인터페이스를 받는 메서드와 구조체 제약 제네릭 메서드(55.9절 종합 예제의 1단계와 3단계)를 BenchmarkDotNet으로 비교하라. `[DisassemblyDiagnoser]`를 붙여 두 코드의 루프 본문을 나란히 놓고, 처리량 차이를 생성 코드로 설명하라.
6. `[MethodImpl(MethodImplOptions.AggressiveInlining)]`을 붙인 버전과 안 붙인 버전, `[MethodImpl(MethodImplOptions.NoInlining)]`을 붙인 버전 세 가지로 같은 헬퍼 메서드를 만들고, 호출자의 `Total bytes of code`가 어떻게 달라지는지 기록하라. 코드가 커진 만큼 빨라졌는가?
7. 콘솔 앱 하나를 (a) 프레임워크 종속, (b) 자체 포함, (c) 자체 포함 + `PublishReadyToRun`, (d) `PublishAot` 네 가지로 게시하고, **publish 폴더 총 크기**와 **`Stopwatch`로 잰 프로세스 시작~첫 출력 시간**을 표로 정리하라. `DOTNET_ReadyToRun=0`을 준 (c)의 시작 시간도 함께 재서 R2R이 실제로 기여한 몫을 분리하라.
