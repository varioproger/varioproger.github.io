# 65장. GC 모드와 튜닝

> **이 장의 위치** — 64장은 **비동시 워크스테이션 GC 한 사이클**을 현미경으로 봤다. 힙이 하나이고, GC가 도는 동안 모든 관리 스레드가 멈춰 있는 가장 단순한 경우다. 이 장은 그 위에 나머지 조합을 얹는다. 힙이 여러 개면 무엇이 달라지는가, GC가 사용자 스레드와 **동시에** 돌면 무엇이 달라지는가, 그리고 그 선택을 어디서 어떻게 하는가. 알고리즘은 같다. 달라지는 것은 **누가 언제 멈추는가**다.
>
> **선수 지식** — 62장(.NET 힙의 구조, 특히 62.4·62.6절), 63장(할당, 특히 63.5·63.6절), 64장(GC 알고리즘 완전 해부 전체)
>
> **이 장에서 다루지 않는 것** — 실제로 GC 문제를 진단하는 도구 워크플로(PerfView, `dotnet-trace`, WinDbg)는 66장에서, 컨테이너 환경의 메모리 제한 전반은 72.8절에서, 파이널라이제이션 API의 의미론은 34장에서 다룬다. 이 장은 **어떤 모드가 있고 무엇을 어떻게 설정하는가**에 집중한다.

---

.NET GC의 설정 가능한 축은 놀라울 만큼 적다. JVM 세계에서 온 사람은 종종 당황한다. 거기서는 GC 동작의 거의 모든 측면을 조정할 수 있지만, 대신 그것을 아주 잘 이해하고 무엇을 왜 바꾸는지 확신해야 한다. Microsoft는 반대 길을 골랐다. **GC 중심이 아니라 애플리케이션 중심**이다. 어떤 종류의 애플리케이션을 만드는지만 알려주면 나머지는 GC가 알아서 한다.

그래서 이 장의 대부분은 "이 손잡이를 돌리면 어떻게 된다"가 아니라 "**이 손잡이는 왜 이렇게 생겼는가**"다. 손잡이 자체는 몇 개 안 된다.

---

## 65.1 워크스테이션 GC vs 서버 GC

### 두 개의 설정 묶음

가장 큰 분기는 **워크스테이션(Workstation)** 과 **서버(Server)** 다. .NET 런타임의 맨 처음부터 있었고, 이름은 각각이 의도한 전형적 애플리케이션에서 왔다. 그러나 이름에 갇히면 안 된다. 데스크톱 애플리케이션에 서버 GC를 쓰는 것도, 웹 애플리케이션에 워크스테이션 GC를 쓰는 것도 완벽하게 정상일 수 있다. **워크스테이션과 서버는 "두 개의 눈에 띄게 다른 GC 설정 묶음"으로 이해하는 것이 정확하다.**

### 워크스테이션 모드가 가정하는 것

워크스테이션 모드는 대화형 UI 애플리케이션에 필요한 **응답성**을 위해 설계됐다. 좋은 대화성은 애플리케이션의 일시 정지가 가능한 한 짧기를 요구한다. 긴 GC가 트리거됐다고 UI가 멈추면 안 된다. 그래서 다음 결정이 내려졌다.

- **GC가 더 자주 일어나고, 한 번에 할 일이 적다.** 객체가 덜 만들어졌으니 쓰레기도 덜 생긴다.
- **부수 효과로 메모리 사용량이 낮다.** 더 자주 회수하니 "매달려 있는" 쓰레기가 크게 쌓이지 않는다.
- **관리 힙이 하나다.** 데스크톱 애플리케이션은 대체로 한 번에 하나의 작업을 처리하므로 GC 작업을 병렬화할 필요가 없다. 게다가 이 모드는 **한 컴퓨터에서 여러 애플리케이션이 동시에 돌고 있다**고 가정한다. 각자가 CPU 코어와 메모리를 쓴다. 여러 힙을 동시에 처리하는 GC 스레드를 늘리는 것은 필요하지도, 특별히 바람직하지도 않다. 워크스테이션 모드는 처음부터 **한 번에 한 스레드가 처리하는 하나의 관리 힙**으로 설계됐다.
- **세그먼트가 더 작다.** 더 작은 메모리 영역 위에서 동작하기 위해서다. 단, **리전(region)에는 해당하지 않는다** — 62.6절에서 본 것처럼 .NET 7부터 기본이 된 리전은 크기가 모드에 의존하지 않는다.

### 서버 모드가 가정하는 것

서버 모드는 동시 요청을 처리하는 애플리케이션을 위해 설계됐다. 보통 높은 **처리량**이 기대된다 — 주어진 시간 안에 최대한 많은 데이터를 처리하는 것.

- **기본 세그먼트 크기가 크다.** 특히 64비트 시스템에서 그렇다. 필요하다면 GC가 트리거되기 전에 훨씬 많은 할당을 수용할 수 있다. 이것 역시 리전에서는 더 이상 해당하지 않는다.
- **GC가 덜 자주 일어난다.** 일반적으로 개별 일시 정지는 더 길어진다는 뜻이다. GC 사이에 더 많은 객체가 만들어졌기 때문이다. 그러나 여러 CPU 코어에서 병렬 처리되므로 실제 일시 정지는 워크스테이션보다 **짧을 수도** 있다. 게다가 여러 번의 작은 수집은 한 번의 큰 수집보다 비효율적이다 — 더 기다렸다면 죽었을 객체를 GC가 복사해 버릴 수 있기 때문이다. 오래 기다릴수록 생존율은 낮아진다. 결국 **누적 일시 정지 시간은 더 짧아진다.**
- **부수 효과로 메모리 사용량이 높다.** GC가 덜 자주 일어난다는 것은 "매달려 있는" 쓰레기가 더 많다는 뜻이고, 워크스테이션보다 큰 워킹 셋을 의미한다. 다만 "서버" 머신은 메모리가 넉넉하다고 가정하므로 큰 문제로 보지 않는다.
- **관리 힙이 여러 개다.** 머신의 코어 수에 기반한 확장성을 보장한다. 여러 힙을 병렬로 처리하는 것이 하나의 큰 힙을 다루는 것보다 빠르다. 게다가 서버 애플리케이션은 종종 전용 서버에 호스팅되므로 가용 코어를 마음껏 써도 된다. **컨테이너 시나리오에서는 CPU가 제한될 수 있으므로 이 가정이 깨진다** — 65.7절에서 다시 본다.

한 문장으로 줄이면 이렇다. **서버 모드는 메모리를 더 쓰고 총 중단 시간을 줄인다.**

> **📌 코어 수만큼 빨라지지는 않는다**
>
> 병목은 메모리 접근이다. CPU 코어 4개로 힙을 병렬 처리한다고 해서 같은 메모리 크기를 코어 하나로 처리할 때보다 4배 빨라지지는 않는다. 그래도 확실히 빨라지기는 한다. 서버 GC의 이득을 선형으로 기대하면 실망한다.

### 그림으로 보기

```text
┌──────────────────────── 워크스테이션 GC ────────────────────────┐
│                                                                 │
│   사용자 스레드   T1  T2  T3  T4   ...  (코어 수와 무관)          │
│                    \  |  /  /                                   │
│                     \ | / /                                     │
│                      ▼▼▼▼                                       │
│          ┌───────────────────────────┐                          │
│          │      관리 힙  #0  (하나)   │                          │
│          │  gen0 | gen1 | gen2 | LOH │                          │
│          └───────────────────────────┘                          │
│                      ▲                                          │
│                      │                                          │
│     비동시: 수집을 트리거한 사용자 스레드가 GC 코드를 직접 실행   │
│     백그라운드: 전용 BGC 스레드 1개가 추가로 존재                │
│     (전용 스레드는 CPU에 고정되지 않는다 — 어피니티 없음)         │
└─────────────────────────────────────────────────────────────────┘

┌────────────────── 서버 GC (논리 코어 4개 가정) ──────────────────┐
│                                                                 │
│   사용자 스레드   T1     T2     T3     T4  ...                   │
│                   │      │      │      │                        │
│         (63.5절 힙 밸런싱으로 할당 컨텍스트가 힙에 배정된다)      │
│                   ▼      ▼      ▼      ▼                        │
│      ┌───────┐ ┌───────┐ ┌───────┐ ┌───────┐                    │
│      │ 힙 #0 │ │ 힙 #1 │ │ 힙 #2 │ │ 힙 #3 │                    │
│      └───┬───┘ └───┬───┘ └───┬───┘ └───┬───┘                    │
│          ▲         ▲         ▲         ▲                        │
│      ┌───┴───┐ ┌───┴───┐ ┌───┴───┐ ┌───┴───┐                    │
│      │ SGC 0 │ │ SGC 1 │ │ SGC 2 │ │ SGC 3 │  서버 GC 스레드     │
│      └───────┘ └───────┘ └───────┘ └───────┘  (블로킹 GC 담당)   │
│      ┌───────┐ ┌───────┐ ┌───────┐ ┌───────┐                    │
│      │ BGC 0 │ │ BGC 1 │ │ BGC 2 │ │ BGC 3 │  백그라운드 GC      │
│      └───────┘ └───────┘ └───────┘ └───────┘  스레드 (동시 GC)   │
│          │         │         │         │                        │
│          ▼         ▼         ▼         ▼                        │
│       core0     core1     core2     core3   ← 스레드 어피니티     │
│       (서버 GC 스레드는 기본적으로 코어에 고정된다)               │
└─────────────────────────────────────────────────────────────────┘
```

이 그림에서 반드시 읽어야 할 세 가지가 있다.

1. **힙 개수** — 워크스테이션은 1개, 서버는 기본적으로 사용 가능한 논리 CPU 코어 수만큼이다.
2. **전용 GC 스레드** — 워크스테이션 비동시는 전용 스레드가 **아예 없다**. 수집을 트리거한 사용자 스레드가 GC 코드를 그대로 실행한다. 서버 모드는 힙마다 서버 GC 스레드 하나가 있고, 백그라운드까지 켜면 힙마다 하나가 더 붙는다. **16코어 머신에서 백그라운드 서버 GC는 GC 전용 스레드 32개를 만든다.**
3. **스레드 어피니티** — 서버 GC 스레드는 각각 하나의 CPU 코어에 고정(pin)된다. 이것이 캐시 지역성에는 좋지만, 같은 머신에 .NET 프로세스가 여럿이면 서로 앞쪽 코어를 두고 싸우게 된다. 65.5절에서 다시 본다.

### 비교표

| 항목 | 워크스테이션 | 서버 |
|---|---|---|
| 관리 힙 개수 | 1개 | 기본값 = 프로세스가 볼 수 있는 논리 CPU 코어 수 |
| 전용 GC 스레드 | 비동시 0개 / 백그라운드 1개 | 힙당 1개(서버 GC 스레드) + 백그라운드면 힙당 1개 추가 |
| GC 코드 실행 주체(비동시) | 수집을 트리거한 사용자 스레드 | 전용 서버 GC 스레드들 |
| 스레드 우선순위 | 사용자 스레드 그대로(보통 normal) | 전용 스레드 |
| CPU 어피니티 | 없음 | 기본적으로 코어에 고정 |
| 세그먼트 크기(세그먼트 구현) | 작다 | 크다, 특히 64비트 |
| 리전 크기(.NET 7+) | 모드와 무관 | 모드와 무관 |
| GC 빈도 | 잦다 | 드물다 |
| 개별 일시 정지 | 짧다 | 개별로는 길 수 있으나 병렬이라 짧아질 수도 |
| 누적 일시 정지 | 길다 | 짧다 |
| 메모리 사용량 | 낮다 | 높다 |
| 설계 의도 | 응답성 | 처리량 |

> **⚠️ 논리 코어가 1개면 `gcServer` 설정은 무시된다**
>
> 논리 CPU 코어가 하나뿐인 머신에서는 `gcServer` 설정과 무관하게 **항상 워크스테이션 GC가 쓰인다.** 이것은 문서화된 동작이지 버그가 아니다. 컨테이너에 CPU 1개를 할당해 놓고 "서버 GC를 켰는데 힙이 하나다"라며 헤매는 일이 실제로 자주 일어난다. `GCSettings.IsServerGC`로 실제 값을 확인하는 습관을 들이는 편이 낫다.

> **📌 소스 코드에서는 어떻게 나뉘어 있는가**
>
> 워크스테이션과 서버는 얼마나 많은 코드를 공유할까. 압도적 대부분이 같은 `.\src\coreclr\gc\gc.cpp` 파일 안에 있고, `#if` 전처리기 지시자로 갈린다. 이 파일은 서로 다른 네임스페이스와 정의 집합으로 **두 번 컴파일된다**.
>
> - `.\src\coreclr\gc\gcsvr.cpp` — `SERVER_GC` 상수를 정의하고 `SVR` 네임스페이스 안에서 `gc.cpp`를 포함한다.
> - `.\src\coreclr\gc\gcwks.cpp` — `WKS` 네임스페이스 안에서 같은 파일을 포함한다.
>
> 그래서 GC 관련 타입이나 메서드를 볼 때 `WKS::` 또는 `SVR::` 네임스페이스에서 온다. `SERVER_GC`를 정의하면 `MULTIPLE_HEAPS`를 비롯한 몇 개의 중요한 정의가 따라 켜지고, `gc.cpp` 안의 수많은 구간이 그 정의에 의존한다. 하나의 알고리즘, 두 개의 빌드다.

> **💡 "웹 앱이면 서버 GC"라는 반사 신경을 의심하라**
>
> 서버 GC가 좋은 것은 애플리케이션이 그 자원을 **독점**할 때다. 한 머신에 .NET 마이크로서비스 12개가 떠 있다면, 12개가 각자 코어 수만큼 힙과 GC 스레드를 만든다. 8코어 머신에서 백그라운드 서버 GC 12개면 GC 전용 스레드만 192개다. 이 경우 서버 GC는 처리량을 올리는 게 아니라 컨텍스트 스위칭과 메모리 사용량만 올린다. .NET 8 이전이라면 `GCHeapCount`로 힙 수를 줄이고, .NET 8 이후라면 DATAS를 검토하는 게 옳다(65.5·65.7절).

### 모드를 설정하는 세 갈래 길

워크스테이션/서버와 비동시/동시는 **직교하는 두 개의 설정**이고 각각 두 개의 값을 가진다. 곱하면 네 가지 모드가 나온다. GC에 관해 설정할 수 있는 것은 거의 이것이 전부다.

설정 방법은 런타임에 따라 다르다. **이 차이가 실무에서 가장 흔한 사고 원인이므로** 표로 먼저 정리한다.

| 설정 | .NET Framework `app.config`/`web.config` | .NET `runtimeconfig.json` | `.csproj` MSBuild 속성 | 환경 변수 |
|---|---|---|---|---|
| 서버 GC | `<gcServer enabled="true"/>` | `"System.GC.Server": true` | `<ServerGarbageCollection>` | `DOTNET_gcServer=1` |
| 동시(백그라운드) GC | `<gcConcurrent enabled="true"/>` | `"System.GC.Concurrent": true` | `<ConcurrentGarbageCollection>` | `DOTNET_gcConcurrent=1` |
| VM 유지 | `<GCRetainVM enabled="true"/>` | `"System.GC.RetainVM": true` | `<RetainVMGarbageCollection>` | `DOTNET_GCRetainVM=1` |
| 힙 개수 | `<GCHeapCount enabled="6"/>` | `"System.GC.HeapCount": 6` | — | `DOTNET_GCHeapCount=6` |

.NET Framework 애플리케이션에서 GC 모드를 바꾸는 주된 방법은 표준 구성 파일이다.

```xml
<?xml version="1.0" encoding="utf-8" ?>
<configuration>
  <startup>
    <supportedRuntime version="v4.0" sku=".NETFramework,Version=v4.7" />
  </startup>
  <runtime>
    <gcServer enabled="true"/>
    <gcConcurrent enabled="true"/>
  </runtime>
</configuration>
```

- **ASP.NET 웹 애플리케이션** — IIS에 호스팅되는 경우 `web.config`를 쓴다. 이 경우 ASP.NET 호스트가 **기본적으로 서버 GC를 켠다**(.NET 4.5 이후 런타임에서는 백그라운드 모드도 함께 켜진다).
- **콘솔 애플리케이션 또는 Windows 서비스** — 기본적으로 `[appName].exe.config`를 쓴다. 설정이 없으면 **동시 워크스테이션 모드가 켜진다.**

> **⚠️ .NET Framework Windows 서비스의 기본값 함정**
>
> 데이터를 요청 형태로 대량 처리하는 Windows 서비스는 동작상 **서버 애플리케이션에 가깝지 대화형 애플리케이션이 아니다.** 그런데 .NET Framework에서 아무 설정도 하지 않으면 동시 워크스테이션 GC로 뜬다. 힙 하나, GC 스레드 하나로 수 GB 힙을 감당하게 된다. 이런 상황에서 서버 GC 계열로 바꾸면 성능이 크게 좋아지는 경우가 많다. .NET(Core)에서도 콘솔 앱의 기본값은 동일하게 워크스테이션이다 — ASP.NET Core 템플릿이 `ServerGarbageCollection`을 켜 줄 뿐이다.

.NET Framework에서도 환경 변수와 레지스트리로 설정할 수 있다. `HKCU\Software\Microsoft\.NETFramework` 아래에 `gcServer` 또는 `gcConcurrent` 키를 0 또는 1로 두거나, `COMPlus_gcServer` / `COMPlus_gcConcurrent` 환경 변수를 쓴다.

.NET(Core)은 더 유연하다. 파일 기반 설정은 형식만 XML에서 JSON으로 바뀌었다.

```json
{
  "runtimeOptions": {
    "tfm": "net8.0",
    "framework": {
      "name": "Microsoft.NETCore.App",
      "version": "8.0.0"
    },
    "configProperties": {
      "System.GC.Server": true,
      "System.GC.Concurrent": true
    }
  }
}
```

이 파일을 손으로 쓸 일은 거의 없다. `.csproj`에 속성을 쓰면 빌드 시 `runtimeconfig.json`으로 옮겨 적힌다.

```xml
<PropertyGroup>
  <ServerGarbageCollection>true</ServerGarbageCollection>
  <ConcurrentGarbageCollection>false</ConcurrentGarbageCollection>
</PropertyGroup>
```

세 번째 길이 환경 변수다. 도커 이미지처럼 격리된 환경에서 특히 유용하다.

```text
DOTNET_gcServer=1
DOTNET_gcConcurrent=0
```

> **⚠️ 환경 변수는 JSON을 덮어쓰고, 숫자는 16진수다**
>
> 두 개가 모두 설정되면 `COMPlus_`/`DOTNET_` 환경 변수가 JSON 설정을 **이긴다.** 그리고 숫자 값은 `0x` 접두사가 없어도 **16진수로 해석된다.** `DOTNET_GCHeapCount=10`은 힙 10개가 아니라 **16개**다. 이 함정에 걸리면 "설정했는데 값이 이상하다"가 아니라 "설정이 먹긴 먹었는데 엉뚱하게 먹었다"가 되어 훨씬 찾기 어렵다.

> **📌 `COMPlus_`와 `DOTNET_`**
>
> .NET 6부터는 `COMPlus_` 대신 `DOTNET_` 접두사를 쓰는 것이 권장된다. `COMPlus_`도 .NET 8까지 여전히 동작한다. 두 개를 동시에 설정하지는 말 것. 새 코드와 새 컨테이너 이미지에서는 `DOTNET_`만 쓰는 편이 좋다.

전체 구성 손잡이 목록은 Microsoft 문서(`learn.microsoft.com/dotnet/core/runtime-config/garbage-collector`)에 있다. 이 장에서는 실제로 쓸 일이 있는 것만 다룬다.

## 65.2 비동시 vs 백그라운드(동시) GC — 동시 마크, 동시 스윕

### 두 번째 축

워크스테이션/서버와 직교하게, GC는 사용자 스레드와 협력하는 두 가지 방식을 가진다.

- **비동시(non-concurrent)** — GC가 일하는 동안 사용자 스레드가 중단된다.
- **동시(concurrent)** — GC 작업이 다른 스레드와 병렬로 일어난다.

비동시 버전은 .NET 초기부터 워크스테이션과 서버 양쪽에 있었다. 개념적으로 정말 단순하다. 모든 사용자 스레드를 세우고, GC가 일하고, 다시 재개한다. 64장 전체가 이 이야기였다.

동시 GC는 개념적으로도 구현상으로도 훨씬 복잡하다. 사용자 스레드와 수집기 사이에 추가 동기화가 있어야 한다. 양쪽이 일관된 현실 인식을 가지고, 수집 중인 객체를 수정하거나 살아 있는 객체를 수집하는 심각한 문제를 일으키지 않아야 한다. 그런 동기화를 **낮은 오버헤드를 유지하면서** 구현하는 것이 쉬울 리 없다.

동시 GC의 이름은 .NET 버전에 따라 다르다. 이 혼란이 문서를 읽을 때 계속 발목을 잡으므로 정리해 둔다.

| 모드 | 도입 | 이름 |
|---|---|---|
| 워크스테이션 동시 | .NET 1.0 | Concurrent Workstation GC |
| 워크스테이션 동시 | .NET Framework 4.0 | **Background Workstation GC**로 개명(중요한 개선 이후) |
| 서버 동시 | .NET Framework 4.5 | **Background Server GC**(그 전에는 서버 동시 GC가 없었다) |

> **📌 소스에서의 위치**
>
> 두 모드 모두 같은 `gc.cpp` 안에 있다. 동시 버전은 `#if BACKGROUND_GC` 전처리기 지시자로 감싸여 있다. 그런데 `BACKGROUND_GC`는 `SVR`과 `WKS` 양쪽 버전에서 **항상 정의된다.** 즉 컴파일된 바이너리에는 동시·비동시 코드가 모두 들어 있고, 어느 쪽을 쓸지는 런타임 시작 시점에 활성화/비활성화된다.

### 타임라인으로 보기

일시 정지 구간이 시각적으로 어디에 생기는지가 이 절의 핵심이다. 아래 그림에서 `████`는 사용자 스레드가 **정지한 구간**, `────`는 정상 실행, `====`는 GC 스레드가 일하는 구간이다.

```text
비동시 워크스테이션 GC — 전체 블로킹 GC(full-blocking GC)

시간 ──────────────────────────────────────────────────────────────▶

T1 ─────────────────█████████████████████████████████──────────────
                    ↑                               ↑
                 EE 중단                          EE 재개
T2 ─────────────────█████████████████████████████████──────────────

GC ..................========== Mark/Plan/Compact ==........

                    │←────────── 일시 정지 = 전체 GC 시간 ──────────→│
                    │  gen2 힙이 크면 여기가 수백 ms가 된다          │
```

```text
백그라운드 워크스테이션 GC — 같은 전체 GC

시간 ──────────────────────────────────────────────────────────────▶

T1 ──────█████──────────────────█████──█████───────█████────────────
         (A)                     (C)   (FG GC)
T2 ──────█████──────────────────█████──█████───────█████────────────

BGC ......=====▶===== 동시 마크 =====▶=====▶== 동시 스윕 ==▶.........
          (A)         (B)              (C)      (D)

FG  ...................▲..................▲.......▲..................
                    포그라운드 GC(gen0/1)가 배경 GC 도중 여러 번 가능

         │←(A)→│      │←──(B)──→│  │←(C)→│  │←──(D)──→│
         짧은 STW      동시 실행     짧은 STW   동시 실행
```

두 그림의 차이를 한 줄로 요약하면 이렇다. **비동시는 긴 정지 하나, 백그라운드는 짧은 정지 두 개와 그 사이의 동시 실행이다.** 총 CPU 사용량은 백그라운드가 더 크다. 대신 개별 정지가 짧다. 이것이 이 장 전체를 관통하는 트레이드오프다.

### 워크스테이션 비동시 — 가장 단순한 모드

64장에서 이미 철저히 봤다. 이 장에서는 "워크스테이션 비동시"를 그냥 **비동시 GC**라고 부르겠다. 특징은 다음과 같다.

- **관리 스레드가 GC 전체 기간 동안 중단된다.** 수집 대상이 gen0이든 gen1이든 gen2(전체 GC)든 마찬가지다. 단일 ephemeral GC는 시간이 아주 짧으므로 비동시로 해도 문제가 없다. 그러나 **전체 블로킹 GC(full-blocking GC)** 는 ephemeral GC보다 훨씬 오래 걸릴 수 있다. 그래서 훨씬 더 원치 않는 것이 된다.
- **GC 코드가 수집을 트리거한 사용자 스레드 위에서 실행된다.** 할당자 내부에서 호출된다. 그 스레드의 우선순위는 바뀌지 않으므로 보통 normal이고, **다른 애플리케이션의 다른 스레드들과 CPU를 두고 경쟁해야 한다.**
- **GC는 항상 "stop the world" 구간에서 실행되므로, 판단하기에 따라 압축(compacting)할 수 있다.**

CLR 이벤트로 추적하면 다음 순서로 나온다.

| 순서 | PerfView 표기 | GC 소스 코드 표기 | id |
|---|---|---|---|
| 1 | `GCSuspendEEStart` | `GCSuspendEEBegin` | 9 |
| 2 | `GCSuspendEEStop` | `GCSuspendEEEnd` | 8 |
| 3 | `GCStart` | `GCStart` | — |
| 4 | `GCStop` | `GCEnd` | — |
| 5 | `GCRestartEEStart` | `GCRestartEEBegin` | 7 |
| 6 | `GCRestartEEStop` | `GCRestartEEEnd` | 3 |

> **⚠️ PerfView의 이벤트 이름과 소스 코드의 이벤트 이름이 다르다**
>
> PerfView는 `Start`/`Stop`으로 표기하지만 GC 소스 코드는 `Begin`/`End`로 되어 있다. 위 표의 네 개가 대표적이다. 소스를 뒤지면서 PerfView 이름으로 `grep`하면 아무것도 안 나온다. 반대도 마찬가지다.

전형적 사용 시나리오는 다음 두 가지다.

- **CPU 자원이 제한되고 많은 애플리케이션이 경쟁하는 포화 환경.** 수집이 단일 스레드에서 돌므로 가용 코어에 주는 영향이 적다.
- **경량 웹 애플리케이션이 많은 환경**(도커화된 마이크로서비스 등). 가볍고 메모리 사용량이 작다면 비동시 GC로 충분하고, 스레드 수를 제한해 자원을 아낀다.

### 워크스테이션 동시 (.NET Framework 4.0 이전)

역사적 배경으로만 알아두면 된다. 후속인 백그라운드 워크스테이션이 이 모드를 거의 그대로 포함한다.

- GC 전용 스레드가 하나 추가된다. 대부분의 시간에는 할 일을 기다리며 중단돼 있다.
- **ephemeral 수집은 항상 비동시다.** 충분히 빠르므로 비동시로 해도 되고, 그래야 필요할 때 압축할 수 있다.
- 전체 GC는 두 가지 모드로 실행될 수 있다. 비동시(그래서 압축 가능)이거나, 동시(그래서 **압축하지 않는다**).
- 동시 전체 GC 중에 사용자 스레드가 객체를 할당할 수 있다. **다만 그런 할당은 ephemeral 세그먼트 크기로 제한된다.** 공간이 떨어지면 더 만들 방법이 없기 때문이다(동시 GC 중에는 다른 GC가 트리거될 수 없다). 그런 일이 생기면 사용자 스레드는 전체 GC가 끝날 때까지 중단된다.
- 짧은 "stop the world" 구간이 두 번 있다 — 시작과 중간.

> **📌 32비트 워크스테이션의 16 MB 벽**
>
> 이 모드의 치명적 한계가 바로 위의 할당 제한이었다. 워크스테이션 모드의 세그먼트는 크지 않았고, **32비트에서는 겨우 16 MB였다.** 그래서 "동시" GC인데도 ephemeral 세그먼트가 고갈되어 스레드가 예상보다 훨씬 자주 멈췄다. 이 한계를 넘어서는 것이 백그라운드 워크스테이션 GC의 주된 개선이었다.

### 백그라운드 워크스테이션

.NET Framework 4.0부터 워크스테이션 동시 GC를 대체했고 .NET(Core)에도 그대로 있다. 핵심 개선은 **동시 GC 중에도 필요하면 ephemeral GC를 트리거할 수 있다**는 것이다. 이로써 일반 스레드의 할당 제한이 사라졌다.

- GC 전용 스레드가 하나 있다. 대부분 중단돼 대기한다.
- ephemeral 수집은 비동시다. 그래서 필요하면 압축한다.
- 전체 GC는 비동시(압축 가능) 또는 백그라운드(**압축 안 함**) 두 가지로 실행된다.
- 백그라운드 전체 GC 도중 관리 스레드가 할당할 수 있고, **그 할당이 일반적인 ephemeral 수집을 트리거할 수 있다.** 이것을 백그라운드 GC와 대비해 **포그라운드 GC(foreground GC)** 라고 부른다.
- 포그라운드 GC는 백그라운드 GC 하나 동안 **여러 번** 일어날 수 있다. .NET 문서의 표현을 빌리면 "전용 백그라운드 GC 스레드는 잦은 안전 지점에서 포그라운드 GC 요청이 있는지 확인한다". 포그라운드 GC는 일반적인 비동시 GC이고, 그동안 백그라운드 GC는 일시적으로 중단된다. 모두가 정지해 있으므로 **압축할 수 있고, 세그먼트나 리전을 추가로 만들어 힙을 확장할 수도 있다.**
- 짧은 "stop the world" 구간이 두 번 있다 — 시작과 중간.

### 백그라운드 GC의 네 단계

백그라운드 GC의 해부학이 이 절의 심장이다. 네 단계로 쪼갤 수 있다.

```text
   (A) 초기 STW      (B) 동시 마크        (C) 최종 마크 STW   (D) 동시 스윕
 ┌─────────────┐  ┌──────────────────┐  ┌───────────────┐  ┌────────────────┐
 │ 스레드 정지  │  │ 스레드 실행 중    │  │ 스레드 정지    │  │ 스레드 실행 중  │
 │             │  │                  │  │               │  │                │
 │ 스택 스캔    │  │ 핸들 순회         │  │ 스택·큐·핸들   │  │ 마크 배열 기준  │
 │ 파이널라이   │  │ work list 소비    │  │ 재스캔         │  │ 프리 리스트     │
 │ 제이션 큐    │─▶│ (BGCDrainMark)   │─▶│ write watch   │─▶│ 항목 생성       │
 │ 스캔 →       │  │ write watch 반영  │  │ 최종 반영      │  │                │
 │ work list   │  │ (BGCRevisit)     │  │ 의존 핸들·     │  │ 빈 세그먼트     │
 │ 준비         │  │                  │  │ 약한 참조 처리 │  │ 해제(decommit) │
 │             │  │ 포그라운드 GC     │  │               │  │ 포그라운드 GC   │
 │ 필요하면     │  │ 0회 이상 가능     │  │               │  │ 가능(조건부)    │
 │ ephemeral GC│  │                  │  │               │  │                │
 └─────────────┘  └──────────────────┘  └───────────────┘  └────────────────┘
   짧다(수 ms)      길다(수십~수백 ms)      짧다(수 ms)         길다

   ※ 압축은 어느 단계에서도 하지 않는다. 백그라운드 GC는 비압축이다.
```

| 단계 | 이름 | 스레드 상태 | 하는 일 |
|---|---|---|---|
| A | 초기 STW | 정지 | 할당자가 GC를 트리거했고 백그라운드 GC를 시작하기로 결정한 지점. 필요하면 여기서 일반 ephemeral GC도 실행한다(할당 예산 초과 등). 객체의 초기 마킹을 수행하고 백그라운드 GC가 이를 소비한다 |
| B | 동시 마크 | 실행 | 사용자 스레드가 재개된 상태로 도달 가능성을 동시에 발견한다. 이 단계에서 포그라운드 GC가 0회 이상 트리거될 수 있다 |
| C | 최종 마크 STW | 정지 | 사용자 스레드를 정지시키고, 다음 단계에서 수집할 객체의 도달 가능성을 확정한다 |
| D | 동시 스윕 | 실행 | 사용자 스레드가 도는 상태로 C에서 확정된 죽은 객체를 안전하게 쓸어낸다. 이 단계에서도 포그라운드 GC가 일어날 수 있다 |

이 네 단계에서 나오는 ETW/EventPipe 이벤트는 비동시 GC보다 훨씬 많다. 일반적인 GC 이벤트 외에 BGC 접두사가 붙은 이벤트들이 백그라운드 GC를 상세히 기술한다.

| 이벤트 | 의미 |
|---|---|
| `BGCStart` | 백그라운드 GC 시작 |
| `BGC1stNonCondStop` / `BGC1stCondStop` | 1차(초기) 비동시/동시 구간 종료 |
| `BGCDrainMark` | work list 소비. 목록 안의 객체 수 정보를 담는다 |
| `BGCRevisit` | 재방문. 처음에 "더러웠던(dirty)" 페이지 수와 그로 인해 결국 마킹된 객체 수를 담는다 |
| `BGC2ndNonConStart` / `BGC2ndNonConStop` | 2차 비동시 구간(최종 마크 STW) |
| `BGC2ndConStart` / `BGC2ndConStop` | 2차 동시 구간(동시 스윕) |
| `GCCreateConcurrentThread` | 백그라운드 GC 스레드 생성 |
| `GCTerminateConcurrentThread` | 백그라운드 GC 스레드 소멸 |

> **⚠️ BGC 이벤트는 기본 공급자에 없다**
>
> 모든 `BGC` 접두사 이벤트는 `Microsoft-Windows-DotNETRuntimePrivate` 공급자가 낸다. **`dotnet-trace`가 기본으로 켜 주지 않는다.** 명령줄에서 명시해야 한다.
>
> ```text
> dotnet trace collect --providers "Microsoft-Windows-DotNETRuntimePrivate:1:5,Microsoft-Windows-DotNETRuntime:1:5" -p <process id>
> ```
>
> 공급자 목록 문법은 `공급자명:키워드:상세도`다. 여기서 `1`은 GC 키워드, `5`는 verbose다. "백그라운드 GC를 추적하는데 아무 이벤트도 안 보인다"의 90%는 이것이다.

> **📌 소스에서 백그라운드 GC 따라가기**
>
> 백그라운드 GC 코드의 대부분은 워크스테이션과 서버가 공유한다(주된 차이는 이 코드를 실행하는 스레드 수뿐이다). 조사할 때는 `gc_heap::garbage_collect` 메서드에서 시작해 `do_concurrent_p` 플래그의 사용처를 보면 된다. 백그라운드 GC가 시작되면 `gc_heap::do_background_gc`가 백그라운드 GC 스레드를 깨운다.
>
> 재미있는 것은 **포그라운드 GC와 백그라운드 GC가 같은 `gc_heap::gc1` 메서드로 표현된다**는 점이다. 차이는 전역 `settings.concurrent` 플래그 안에 있다. 포그라운드 GC는 이 플래그가 꺼진 상태로 실행되고(64장에서 본 그 변종이다), 백그라운드 GC는 분리된 스레드에서 플래그가 켜진 상태로 실행되어 `gc_heap::background_mark_phase`와 `gc_heap::background_sweep`을 호출한다.

전형적 사용 시나리오는 명확하다. **대부분의 UI 애플리케이션.** 백그라운드 워크스테이션 GC의 일시 정지를 최대한 짧게 만들려는 노력이 많이 들어갔고, 그래서 모든 종류의 대화형 애플리케이션에 완벽한 선택이다. 다만 **백그라운드 GC는 여전히 압축하지 않으므로** 단편화가 문제가 될 수 있고, 그것을 줄이기 위해 가끔 블로킹 전체 GC가 트리거된다. 그때 UI 반응성이 나빠진다.

### 동시 마크는 어떻게 가능한가

사용자 스레드가 도는 동안 도달 가능성을 어떻게 판정하는가. 스레드들은 끊임없이 객체를 수정하고, 객체 사이의 참조를 만들고 지운다. 이런 동적 조건에서 도달 가능성을 발견하는 것이 가능한가.

64.2절에서 본 것처럼 .NET의 추적 수집기는 루트에서 시작해 객체 그래프 전체를 순회하며 방문한 객체를 마킹한다. 이 접근을 사용자 스레드와 동시에 하려 할 때 두 가지 문제가 생긴다.

1. 사용자 스레드의 작업을 방해하지 않으면서 객체를 어떻게 마킹할 것인가.
2. 객체 사이 관계에 대한 일관된 시각을 사용자 스레드와 수집기 양쪽에서 어떻게 유지할 것인가.

#### 문제 1 — 마크 배열

64.2절에서 객체를 마킹한다는 것은 그 객체의 MethodTable 포인터에 비트 하나를 세우는 것이라고 했다. "stop the world" 접근에서는 완벽히 괜찮다. 그러나 스레드들이 사용 중일 수 있는 그런 핵심 포인터를 수정하는 것은 **안전성과 성능(캐시 무효화 포함) 양면에서 받아들일 수 없다.**

그래서 동시 마킹은 마킹 정보를 **전용의 분리된 마크 배열(mark array)** 에 저장한다. 조직은 62.7절의 카드 테이블과 비슷하다.

```text
관리 힙 (64비트)
 ┌────────┬────────┬────────┬────────┬────────┬────────┬────────┬────────┐
 │ 16바이트│ 16바이트│ 16바이트│ 16바이트│ 16바이트│ 16바이트│ 16바이트│ 16바이트│
 └────────┴────────┴────────┴────────┴────────┴────────┴────────┴────────┘
      │        │        │        │        │        │        │        │
      ▼        ▼        ▼        ▼        ▼        ▼        ▼        ▼
 ┌────────────────────────────────────────────────────────────────────────┐
 │ 마크 배열 — 1비트 = 힙의 16바이트 영역 (32비트 런타임에서는 8바이트)     │
 │ ┌──────────── 마크 워드 (4바이트 = 32비트) ─────────────┐               │
 │ │ 0 1 0 0 1 1 0 0 ... │ ... │ ... │ ...                │               │
 │ └───────────────────────────────────────────────────────┘               │
 └────────────────────────────────────────────────────────────────────────┘
```

- 각 비트가 관리 힙의 **16바이트 영역**에 대응한다(32비트 런타임에서는 8바이트).
- 마크 배열은 **4바이트 마크 워드**로 조직된다.
- GC가 객체를 방문하고 마킹하려 하면 대응하는 비트를 세운다. **마크 배열의 유일한 소유자가 GC이므로 접근 시 동기화 문제가 없다.**
- 게다가 동시 마킹 중에는 이 비트가 **세워지기만 하고 지워지지 않는다.** 여러 스레드가 병렬 동시 마킹을 할 때(백그라운드 서버 GC) 동기화가 훨씬 단순해진다.

16바이트 세분성으로 충분한 이유는 **최소 객체 크기가 24바이트**이기 때문이다(64.6절). 그런 영역 안에 객체가 둘 이상 놓일 수 없다. 나중에 마크 배열에서 세워진 비트를 훑으면 대응 객체의 도달 가능성 정보를 얻는다.

#### 문제 2 — 잃어버린 객체와 쓰기 감시

수집기가 그래프를 순회하는 동안 객체 사이 참조가 수정되면 무엇이 잘못될 수 있는가. 다섯 가지 경우가 있다.

| 경우 | 상황 | 위험한가 |
|---|---|---|
| 1 | **아직 방문하지 않은** 객체의 참조가 수정됨 | 안전. 아직 방문 전이니 GC가 방문할 때 변경이 반영된다 |
| 2 | **이미 방문한** 객체가 도달 불가능한 객체로의 참조를 지움 | 안전. 순간적으로 **부유 쓰레기(floating garbage)** 가 생길 뿐, 다음 GC에서 수집된다 |
| 3 | **이미 방문한** 객체가 도달 불가능한 객체로의 참조를 **추가**함 | **위험.** GC가 그 객체를 방문(마킹)할 기회가 없을 수 있다. 사용 중인데도 쓰레기로 간주되어 수집된다 — **"잃어버린 객체(lost object)" 문제** |
| 4 | 이미 방문한 객체가 **도달 가능한** 객체로의 참조를 수정함 | 다른 경로로 GC가 방문할 기회가 있는지 확인해야 판정 가능 |
| 5 | **현재 방문 중인** 객체가 자기 참조를 수정함 | 그 참조가 이미 방문됐는지에 따라 위 경우 중 하나로 귀착 |

```text
경우 2 — 부유 쓰레기                 경우 3 — 잃어버린 객체 (위험)

  [방문됨 A] ──X──▶ [B]                [방문됨 A] ─────▶ [B] (새로 연결)
                     ↑                                     ↑
              참조가 끊겨도 B는                    GC는 A를 이미 지나갔다.
              어차피 죽을 객체였다.                B는 마킹될 기회가 없다.
              잠시 살아 있는 것처럼                 살아 있는데 수집된다!
              보이다가 다음 GC에 죽는다.
```

해결책은 명백하다. **문제가 되는 객체를 다시 방문하면 된다.** 부유 쓰레기의 양, 재방문할 객체 수, 사용자 스레드와 수집기 사이 동기화 비용 사이에서 서로 다른 절충을 하는 여러 동시 마킹 기법이 존재한다.

.NET은 단순하면서 효과적인 **쓰기 장벽(write barrier)** 기법을 골랐다. 이미 방문했거나 지금 방문 중인 객체가 수정될 때마다 "재방문 대상"으로 취급한다. 수정 목록을 어떻게 관리하는지는 플랫폼과 버전에 따라 다르다.

| 환경 | 쓰기 감시(write watch) 구현 | 세분성 |
|---|---|---|
| Windows, ~.NET Framework / ~.NET 5 이전 | OS의 `WriteWatch` 메커니즘(62.7절의 카드 테이블도 이것을 썼다) | 페이지 단위(4 kB) |
| 비 Windows 런타임, 그리고 **Windows도 .NET 5부터** | CLR 자체 구현. JIT이 삽입한 쓰기 장벽이 전용 배열의 대응 바이트를 수정한다 | 소프트웨어 구현 |

> **⚠️ 페이지 세분성이 만드는 과잉 재방문**
>
> OS `WriteWatch`는 **페이지 단위(4 kB)** 세분성이다. 객체 하나만 수정되어도 4 kB 페이지 전체가 무효화된다. 즉 그 페이지 안의 객체 전부가 재방문 후보가 된다. 백그라운드 GC 도중 객체 사이 의존 관계를 자주 수정하는 워크로드는 **많은 페이지를 무효화해 GC가 많은 객체를 재방문하게 만든다.** 이것이 "백그라운드 GC를 켰는데 동시 마크 단계가 이상하게 오래 걸린다"의 원인일 수 있다. `BGCRevisit` 이벤트의 dirty page 수를 보면 확인된다.

이제 각 단계가 정확히 무엇을 하는지 다시 정리할 수 있다.

- **(A) 초기 STW** — 스레드가 정지한 동안 초기 목록을 준비한다. **스택과 파이널라이제이션 큐만** 스캔해 향후 동시 마킹을 위한 "work list"를 채운다. 이 목록에는 발견된 객체만 들어가고, **이 시점에는 그 객체의 나가는 참조를 따라가지 않는다.** 그래서 이 단계가 짧다.
- **(B) 동시 마크** — 사용자 스레드가 도는 동안 동시 마킹의 본체가 실행된다. 다음 루트에 대해 객체 그래프를 순회하며 마크 배열에 마킹한다.
  - 핸들
  - 이전 단계에서 준비한 work list — 스택에서 출발한 큰 객체 그래프가 여기서 고려된다. 이 단계에서 `BGCDrainMark` 이벤트가 work list 안의 객체 수와 함께 발행된다.
  - 쓰기 감시 목록 — 동시 마킹이 끝날 무렵, 이 단계 동안 일어난 모든 객체 수정이 고려된다. `BGCRevisit` 이벤트가 발행된다.
- **(C) 최종 마크 STW** — **"최종 진실"의 지점**이다. 모든 스레드가 정지하고 GC가 "따라잡을" 기회를 얻는다. 이 시점에 마크 배열은 실제 도달 가능성 상태를 꽤 잘 반영하고 있지만, 확실히 하기 위해 다시 확인해야 한다. 이것은 **증분 작업**이다. 그래프를 순회할 때 마크 배열의 마킹 플래그를 고려하므로 많은 객체는 다시 방문되지 않는다. 루트를 재방문하는 것은 새로 도달 가능해진 객체가 없는지 확인하기 위해서다. 물론 이 과정은 부유 쓰레기를 만든다(이미 마킹된 객체가 "언마킹"되지는 않으므로). 결과의 정확성 관점에서는 문제가 아니다. 이 최종 마킹에서 고려하는 루트는 다음과 같다.
  - 스택, 파이널라이제이션 큐, 핸들
  - 쓰기 감시 목록 — 이전 확인에서 GC가 따라잡지 못한 모든 수정을 포함하기 위해
  - 추가로 의존 핸들 스캔과 약한 참조 처리 같은 전형적 마킹 관련 작업(34.9절)

> **📌 소스에서 동시 마킹**
>
> .NET(Core)에서 동시 마킹의 주 코드는 `gc_heap::background_mark_phase`에 있다. 가장 중요한 두 자료구조는 `mark_array`(위 그림의 배열)와 `c_mark_list`(초기 단계에서 채워지는 "work list")다. `c_mark_list`는 스택과 파이널라이제이션 큐 스캔 중 `gc_heap::background_promote_callback`이 채우고 `gc_heap::background_drain_mark_list`가 소비한다.
>
> 쓰기 감시 목록은 `gc_heap::revisit_written_pages`가 읽는다. `gc_heap::get_write_watch_for_gc_heap`으로 갱신된 메모리 위치 목록을 얻어 객체 단위로 훑는다. 소프트웨어 쓰기 감시가 켜져 있으면 `JIT_WriteBarrier_WriteWatch_PreGrow64` 같은 쓰기 장벽에서 그 사용을 볼 수 있다.
>
> 모든 동시 마킹은 `gc_heap::background_promote`가 담당하고, `gc_heap::background_mark_simple`과 `background_mark_simple1`을 통해 그래프를 순회하며 `gc_heap::background_mark1`에서 `mark_array`의 대응 비트를 세운다.

정리하면 두 가지 대가가 있다.

- 동시 마킹은 부유 쓰레기를 만든다. 즉 **덜 공격적인 수집**이 된다 — 블로킹 마킹보다 더 많은 죽은 객체가 더 오래 공간을 차지한다.
- 백그라운드 GC 중 객체 의존 관계를 자주 수정하면 많은 페이지가 무효화되고 GC가 많은 객체를 재방문하게 된다.

### 동시 스윕

동시 스윕이 시작될 때 마크 배열에는 이미 모든 살아 있는 객체 정보가 있다. 64.9절의 비동시 Plan/Sweep 단계와 마찬가지로 이 정보로 죽은 객체를 쓸어낼 수 있다. 힙의 객체를 하나씩 훑으며 마크 배열과 대조하고, 도달 불가능한 객체에 대해 프리 리스트 항목을 만든다(64.9절과 정확히 같은 방식이며 세대 할당자 갱신도 포함한다).

SOH 할당이 동시 스윕 중에 일어날 수 있으므로 둘이 어떻게 상호작용하는지가 중요하다. 순서는 이렇다.

1. **런타임이 사용자 스레드 실행을 재개하기 전에, 모든 세대의 프리 리스트 항목이 지워진다.** 그래서 짧은 기간 동안 할당자들은 빈 공간을 인식하지 못한다 — 이미 소비된 세그먼트/리전 부분의 끝에서 할당하게 된다.
2. **동시 스윕이 ephemeral 세대에서 시작한다.** gen0과 gen1에 프리 리스트 항목을 만들되 **분리된 목록 위에서** 작업하고 끝에 할당자에게 게시한다(할당하는 사용자 스레드와 동시 GC가 프리 리스트에 동시 접근하는 것을 피하기 위해서다). 이 빠른 단계가 끝나자마자 ephemeral 세대의 할당자는 빈 공간을 소비할 수 있게 된다. 그리고 **이 단계에서는 포그라운드 GC가 허용되지 않는다** — 포그라운드 GC는 압축할 수 있고, 그것은 진행 중인 객체 단위 스캔과 충돌하기 때문이다.
3. **동시 스윕이 gen2, LOH, POH로 계속된다.** gen2·LOH·POH에 프리 리스트 항목을 만들고 즉시 할당자에게 게시한다. 이 단계에서는
   - 사용자 스레드가 할당할 때 이미 게시된 gen0 프리 리스트를 소비할 수 있다.
   - **포그라운드 GC가 허용된다.** gen1에서 gen2로 객체가 승격되면 이미 만들어진 gen2 프리 리스트 항목이 소비된다. 포그라운드 GC는 일반적인 비동시 GC이고 그동안 백그라운드 GC가 일시 중단되므로 목록에 동시 접근이 없어 안전하다.

> **⚠️ LOH 할당은 동시 스윕 도중 막힐 수 있다**
>
> 역사적으로 전체 과정 동안 LOH 할당이 허용되지 않았다. **.NET Core 3.1부터는 gen2 백그라운드 스윕 도중에는 LOH 할당이 가능해졌다.** 그러나 **LOH 자체를 스윕하는 동안에는 여전히 불가능하다.** GC가 프리 리스트를 수정하는 동안 LOH 할당자가 그 목록에 동시 접근해야 하기 때문이다. 동시 스윕 중 큰 객체를 할당하려는 사용자 스레드는 **LOH 스윕이 끝날 때까지 블록된다.** "백그라운드 GC를 쓰는데 왜 대형 배열 할당에서 스레드가 멈추는가"의 답이 이것이다. 65.10절의 배열 풀링이 이 문제까지 함께 없앤다.

동시 스윕 중에도 비동시 버전과 마찬가지로 세그먼트가 비면 삭제될 수 있다(메모리를 decommit 한다).

> **📌 소스에서 동시 스윕**
>
> `gc_heap::background_sweep`에 구현되어 있다. gen0·gen1 객체를 스캔하는 `gc_heap::background_ephemeral_sweep`를 호출한 뒤 gen2, LOH, POH의 객체를 스캔한다. 스캔 도중 **객체 256개마다** 잘 정의된 안전 지점에서 `gc_heap::allow_fgc`를 호출한다. 객체 스캔 중에는 이미 익숙한 `gc_heap::thread_gap`과 `gc_heap::make_unused_array`가 각각 프리 리스트 항목과 사용 불가능한 작은 빈 공간을 만든다.

### 서버 비동시

.NET 초기부터 .NET Framework 4.5까지, 서버(주로 웹) 애플리케이션을 위한 유일한 기본 모드였다. 사실 앞서 본 워크스테이션 비동시의 꽤 단순한 확장이다. 모든 GC가 블로킹이고, 어느 세대를 수집하든 마찬가지다. 다만 메모리 관리 관점에서 중요한 차이가 있다 — **기본적으로 논리 CPU 코어 수만큼의 관리 힙이 있다.**

- **GC 전용 추가 스레드가 있다.** 기본적으로 관리 힙 개수와 정확히 같다(그냥 **서버 GC 스레드**라고 부른다). 대부분 중단돼 대기한다. 모든 스레드가 하나의 관리 힙에 배정된다.
- **모든 수집이 비동시 GC다.** 여러 GC 스레드에서 병렬로 처리되므로 같은 힙 크기에 대해 워크스테이션 모드보다 도입되는 일시 정지가 짧다. "stop the world"이므로 **어느 수집이든 필요하면 압축할 수 있다.**
- **마크 스틸링(mark stealing)** 기법으로 여러 GC 스레드 사이의 마킹 작업을 분산한다. 살아 있는 나가는 참조를 담은 객체의 분포가 달라서 힙이 불균형해질 수 있기 때문이다. GC 스레드들은 이따금 서로에게서 방문할 객체 배치(batch)를 "훔친다".

전형적 사용 시나리오는 다음과 같다.

- **심하게 포화된 웹 서버.** 여러 애플리케이션의 많은 동시 스레드 때문에 CPU 코어 경합이 심하면, 자원을 더 많이 쓰는 백그라운드 서버 GC보다 이 모드가 나을 수 있다. `GCHeapCount`로 스레드 수를 추가로 제한할 수도 있다.
- **모든 GC(전체 GC 포함)가 압축할 수 있으므로** 동시 버전보다 단편화에 강하다. 워킹 셋이 작아진다.
- **모든 GC가 블로킹이므로** 동시 마킹 단계에서 부유 쓰레기가 생기지 않는다. 워킹 셋이 더 줄어든다.

### 백그라운드 서버

.NET Framework 4.5부터 서버 애플리케이션의 기본 모드다. 지금까지 나온 것 중 **단연 가장 복잡한 GC**지만, 비동시 서버와 백그라운드 워크스테이션을 모두 이해했다면 사실 그 둘의 조합임을 쉽게 알 수 있다.

- **관리 힙마다 GC 전용 스레드가 두 개** 있다. 대부분 중단돼 대기한다.
  - **서버 GC 스레드** — 비동시 서버 GC와 마찬가지로 모든 블로킹 GC(포그라운드 GC 포함)를 담당한다.
  - **백그라운드 GC 스레드** — 백그라운드 GC를 담당하는 힙당 추가 스레드다.
- **ephemeral 수집은 비동시 GC다.** 충분히 빠르고, 그래야 압축할 수 있다. **포그라운드 GC 스레드들이 병렬로 실행하며 각 스레드가 자기 관리 힙을 담당한다.**
- 전체 GC는 비동시(압축 가능, 모든 서버 GC 스레드가 병렬 작업) 또는 백그라운드(**압축 안 함**, 전용 백그라운드 GC 스레드들이 병렬 실행) 두 가지로 실행된다.
- 백그라운드 전체 GC 중 관리 스레드가 할당할 수 있고 그 할당이 ephemeral 수집(포그라운드 GC)을 트리거할 수 있다. 포그라운드 GC는 백그라운드 GC 하나 동안 여러 번 일어날 수 있다. 짧은 STW 구간이 시작과 중간에 두 번 있다.

백그라운드 서버 GC의 정확한 서술은 백그라운드 워크스테이션 서술의 대부분을 반복하는 일이 된다. **주된 차이는 추가 GC 스레드가 하나가 아니라 가용 CPU 코어 수만큼이라는 것뿐이다.**

이것은 백그라운드 워크스테이션 GC의 장점(짧은 일시 정지, 약한 스레드 할당 제한)과 비동시 서버 GC의 장점(병렬 수집에 따른 확장성)을 결합하기 위해 엄청난 복잡도를 도입한다. **스레드 활용 관점에서 가장 자원을 많이 쓰는 GC다. 16코어 머신에서 GC 전용 스레드가 32개 생긴다.**

전형적 사용 시나리오는 다음과 같다.

- **대부분의 서버 기반 애플리케이션의 기본 GC.** 다만 같은 서버 인스턴스에 .NET 애플리케이션이 수십 개 돌고 있다면 그것들 전부가 백그라운드 서버 GC를 쓰기를 바라지는 않을 것이다.
- **전용 머신에서 도는 자원 집약적 데스크톱 애플리케이션.** 의료 장비나 공장 제어 스테이션처럼 통제된 환경에서 오직 내 애플리케이션만 돈다면 이 모드를 고려할 만하다. 가장 정교한 GC가 가진 자원을 잘 활용할 것이다.

| 모드 | 힙 개수 | GC 전용 스레드 | 전체 GC 일시 정지 | 처리량 | 메모리 | 압축 | 적합 워크로드 |
|---|---|---|---|---|---|---|---|
| **워크스테이션 비동시** | 1 | 0 | **가장 길다** — 단일 스레드가 전부 블로킹 처리 | 낮음 | **가장 낮음** | 항상 가능 | CPU가 극도로 포화된 환경, 힙이 작은 경량 마이크로서비스 |

> **⚠️ "일시 정지가 짧다"는 평균이 아니라 백분위로 봐야 한다**
>
> 위 표의 "가장 짧음"은 백분위 기준이다. 실측 벤치마크에서 **평균** GC 일시 정지만 보면 모드 간 차이가 작아 보인다. 그러나 **99% 이상 백분위**를 보면 워크스테이션 비동시가 심각하게 나빠진다. 평균은 값진 정보의 환상을 주면서 중요한 사실을 놓치는 통계량이다. GC 일시 정지와 애플리케이션 응답 시간처럼 중요한 지표는 반드시 백분위로 보라. 65.3절에서 다시 다룬다.

## 65.3 GC 일시 중지 시간과 오버헤드의 트레이드오프

### 무엇을 오버헤드라고 부르는가

자동 메모리 관리는 본질적으로 자기가 도입하는 오버헤드와 얽혀 있다. GC는 결국 우리 애플리케이션의 일부로 도는 코드다. CPU 사이클을 쓰고, 나머지 애플리케이션이 아무것도 하지 않는 일시 정지를 만든다. 그런데 "오버헤드"를 정확히 무엇으로 정의하고 어떻게 재는가.

전체 .NET 애플리케이션 성능의 맥락에서 두 방향으로 볼 수 있다.

**GC 쪽 지표 — 두 개의 원치 않는 부작용**

- **GC 일시 정지(GC pauses).** 현재로서는 무정지(pauseless) GC라는 것이 존재하지 않는다. GC가 애플리케이션 스레드를 멈추는 것은 명백히 바람직하지 않고, 대화형 애플리케이션에서 특히 그렇다. 총합, 평균, 백분위 같은 값을 측정한다. 무엇이 허용 가능한 임계값인지는 애플리케이션 특성에 따라 다르다. 일반적으로 **개별 GC 일시 정지가 수십 밀리초를 넘고 그것이 자주 일어난다면 경고 신호로 봐야 한다.**
- **GC의 CPU 오버헤드.** GC 코드를 실행하는 것도 다른 코드와 마찬가지로 CPU 자원을 쓴다. GC가 오래 돌수록, 또는 더 많은 코어를 쓸수록 일반 코드 실행에서 더 많은 CPU 사이클을 훔친다. 이것은 동시 GC와 비동시 GC 양쪽 모두에 해당한다. 일반적인 웹 애플리케이션에서 **10%를 넘는 지속적 사용률은 경고 신호**로 보는 편이 좋다.

**애플리케이션 쪽 지표**

- **처리량(throughput)** — 애플리케이션이 얼마나 빨리 실행되는가. 예를 들어 주어진 시간에 몇 개의 HTTP 요청을 처리하는가.
- **지연(latency)** — 꼬리 지연(tail latency)을 보는 것이 일반적이다. 가장 느린 x%의 동작이 얼마나 오래 걸리는가.
- **메모리 소비** — 특히 최대 메모리 사용량이 얼마인가.

### 두 지표가 그림에서 어디인가

```text
        ┌── GC 일시 정지 시간 ──┐
        │                      │
T1 ─────█████████████████──────────────────────────────█████████────
        ↑                ↑                             ↑
     EE 중단 시작      EE 재개 완료                   다음 GC
        │                                              │
        │←──── Suspend MSec ────┤←─ Pause MSec ─┤      │
        │  (중단 + 재개에 쓴 시간) (GC 처리 시간)         │
        │                                              │
        │←─────────── 직전 GC 이후 경과 시간 ───────────→│

  % GC = (동시 부분을 포함한 GC 전체 시간) / (직전 GC 이후 경과 시간)
```

| 지표 | 정의 | 어디서 보는가 |
|---|---|---|
| **GC 일시 정지 시간** | GC의 비동시 구간의 지속 시간. 실행 엔진이 애플리케이션 스레드를 중단시키는 데 쓴 시간 + GC가 진행한 시간 + 스레드를 재개하는 데 쓴 시간 | PerfView GCStats의 "GC Events by Time" 표 — `Suspend MSec`(중단·재개)과 `Pause MSec`(GC 처리) 열 |
| **CPU에서 GC가 쓴 상대 시간** | 동시 부분을 포함한 GC 전체 시간과 직전 GC 이후 경과 시간의 비율 | 같은 표의 `% GC` 열 |

> **📌 `Suspend MSec`가 크면 GC 문제가 아닐 수 있다**
>
> 위 표의 두 열을 반드시 나눠서 보라. `Pause MSec`는 GC가 실제로 일한 시간이지만, `Suspend MSec`는 **모든 관리 스레드를 안전 지점으로 몰아 협조적 모드에서 선점 모드로 옮기는 데 걸린 시간**이다(64.12절). 이 값이 크다면 원인은 GC 처리 자체가 아니라 **어떤 스레드가 안전 지점에 도달하지 못하고 있는 것**이다. 긴 동기 I/O, 타이트한 비인터럽트 루프, 그리고 **`[SuppressGCTransition]`을 붙인 P/Invoke 호출**(60.10절)이 대표적 원인이다. `SuppressGCTransition`은 GC 전환을 없애 호출 오버헤드를 줄이지만, 그 호출이 도는 동안 스레드는 **협조적 모드에 머물러 GC를 기다리게 만든다.** 짧고 빠르게 반환하는 네이티브 함수에만 써야 하는 이유가 이것이다.

> **⚠️ "% Time in GC" 성능 카운터는 신뢰하지 마라**
>
> "% Time in the GC" 성능 카운터나 `time-in-gc` .NET 카운터로도 GC의 CPU 오버헤드를 측정할 수 있다. 그러나 **덜 정확하고**, .NET 팀은 CLR 이벤트 기반 측정을 권한다(백그라운드 GC 도입 이후 팀은 성능 카운터보다 ETW/EventPipe 이벤트에 투자하고 있다).
>
> 결정적 함정이 하나 더 있다. **GC가 없으면 이 성능 카운터는 갱신되지 않고 이전 값을 계속 표시한다.** 성능 모니터에 99%가 고정으로 그려져 있어도 놀라지 마라 — 그냥 마지막 GC 때의 측정값이 갱신되지 않은 것일 수 있다. **항상 새 GC가 실제로 일어났는지 확인하라.** "# Gen 0 Collections" 성능 카운터나 `gen-0-gc-count` .NET 카운터를 함께 보면 된다.

> **⚠️ "% Time in GC"는 GC 모드와 함께 해석해야 한다**
>
> 실측 벤치마크에서 이 카운터만 보면 **워크스테이션 모드의 오버헤드가 서버 모드보다 훨씬 큰 것처럼** 오해하기 쉽다. 이유는 정의에 있다. 이 값은 "직전 GC 이후 경과 시간 대비 GC 시간"이다. 서버 모드는 GC에 쓴 **시간**은 짧지만 그 처리가 여러 관리 힙에서 여러 코어에 걸쳐 병렬로 일어난다. 시간은 짧아도 **전체 CPU 사용량은 비슷하며**, 이 지표는 그것을 정확히 드러내지 못한다.
>
> 결론: **워크스테이션 모드에서는 이 값이 높아도 서버 모드보다 관대하게 해석해야 한다.** 두 모드의 % Time in GC 값을 나란히 놓고 비교하는 것은 의미가 없다.

### 무엇을 알람으로 걸 것인가

측정 지표를 정했으면 임계값이 필요하다. 절대적인 답은 없다 — 무엇이 허용 가능한지는 애플리케이션 특성에 달려 있다. 그래도 출발점이 될 만한 경험칙은 있다.

| 지표 | 경고 신호로 볼 만한 값 | 근거 |
|---|---|---|
| 개별 GC 일시 정지 | **수십 ms를 넘고 자주 반복** | 대화형 애플리케이션에서는 이미 체감된다. 요청 처리 애플리케이션에서는 꼬리 지연을 만든다 |
| GC의 CPU 사용률 | 일반적인 웹 애플리케이션에서 **10%를 넘는 지속적 사용** | 실무에서 관찰한 경계값. 이 이상이면 할당량 자체를 의심한다 |
| EE 중단 시간(`Suspend MSec`) | **1 ms 초과**(64장 Rule 17) | GC 처리가 아니라 스레드가 안전 지점에 도달하지 못하는 문제 |
| 일시 정지 99%/99.9% 백분위 | 평균의 몇 배 이상으로 벌어짐 | 평균만 보면 보이지 않는 꼬리. 모드 선택을 뒤집는 지표 |

> **💡 임계값은 GC가 아니라 비즈니스에서 온다**
>
> GC 오버헤드 자체는 비즈니스 지표가 아니다. "% Time in GC를 10% 미만으로 유지하라"고 요구하는 경영진을 상상할 수 있는가. 관찰해야 하는 것은 **GC 오버헤드가 다른 비즈니스 지표에 미치는 영향**이다. 백분위는 비즈니스 요구와 직접 연결된다 — "사용자의 99%가 2초 미만, 99.99%가 10초 미만의 응답 시간을 갖는다" 같은 형태로. GC 지표에 알람을 걸되, **에스컬레이션 기준은 응답 시간 백분위에 두는 것**이 건강하다.

### 실측 — 네 모드를 같은 워크로드로 재면

`nopCommerce` 웹 애플리케이션을 도커 환경에서 돌리고 JMeter로 부하를 걸어 네 가지 GC 구성을 비교한 결과의 요지는 다음과 같다.

| 측정 항목 | 관찰 |
|---|---|
| **CPU 사용량** | 서버 GC 계열이 워크스테이션 계열보다 **명백히 높다.** 서버 GC가 가용 자원을 훨씬 적극적으로 쓰기 때문이며 예상대로다 |
| **% Time in GC** | 위 함정 때문에 **워크스테이션이 더 나빠 보이는 오해를 유발한다** |
| **메모리 사용량** | 관리 힙이 서버 계열에서 **눈에 띄게 크다.** 반면 같은 모드의 비동시/백그라운드 사이 차이는 꽤 작다 |
| **평균 GC 일시 정지** | ephemeral 세대는 모드와 무관하게 정말 빨리 수집된다. **차이는 전체 GC에서 나온다.** 확실한 패자는 **워크스테이션 비동시** — 모든 쓰레기를 블로킹 모드의 단일 스레드로 수집한다. 서버 비동시는 여러 관리 힙에서 병렬로 하므로 더 빠르지만 두 동시 버전보다는 여전히 눈에 띄게 느리다 |
| **GC 일시 정지 백분위** | **백그라운드 서버가 가장 좋고 워크스테이션 비동시가 명백히 가장 나쁘다.** 특히 99%를 넘는 백분위에서 심각하게 악화된다 |
| **응답 시간** | 서버 GC 모드가 워크스테이션보다 눈에 띄게 좋다(동시 여부와 무관). 다만 **처리 시간이 긴 요청에서는** 비동시 모드의 긴 일시 정지가 최대 응답 시간에 크게 반영되지 않는다 — 처리 시간 자체가 가장 긴 GC 일시 정지보다 훨씬 길기 때문이다. **요청을 수십 ms 단위로 처리한다면 GC 일시 정지의 영향이 훨씬 커진다** |

> **💡 이 결론을 그대로 가져다 쓰지 마라**
>
> 위 결과는 **특정 애플리케이션의 특정 개발 시점**에 대한 것이다. 생성된 사용자 부하, 특정 환경(코어 수, 메모리 양, 함께 도는 다른 애플리케이션)이라는 가정 위에 서 있다. 그대로 자기 애플리케이션에 적용하지 마라. 의미 있는 것은 **결론이 아니라 방법론**이다 — CPU, 메모리, 일시 정지, 클라이언트 관점 응답 시간을 함께 보고, 핵심 지표는 백분위로 본다. 그리고 이런 테스트는 **개발용 데스크톱이 아니라 프로덕션에 가까운 환경에서** 해야 한다.

### 측정 도구 조합

프로덕션에서도 돌릴 수 있을 만큼 침습성이 낮은 조합은 다음과 같다. 자세한 워크플로는 66장에서 다룬다.

| 알고 싶은 것 | 도구 | 지표 |
|---|---|---|
| GC 오버헤드 | `dotnet-counters` (CSV로 수집) | `CPU Usage (%)`, `% Time in GC since last GC (%)` |
| 메모리 사용량 | `dotnet-counters` | `GC Heap Size (MB)` |
| 일시 정지 | `dotnet-trace`의 `gc-collect` 프로파일 | `PauseMSec` — PerfView GCStats의 "Individual GC Events / View in Excel"로 CSV 추출 |
| 클라이언트 관점 응답 시간 | 부하 도구(JMeter 등) | 백분위 응답 시간 |

> **⚠️ `% in GC` 지표를 얻으려면 무거운 세션이 필요하다**
>
> GCStats 보고서의 `% in GC` 열은 CPU 샘플링을 포함한 무거운 `dotnet-trace` 세션을 요구하고 상당한 오버헤드를 도입한다. 애플리케이션이 몇 배 느려질 수 있어 의미 있는 비교에 부적합해진다. 모드 비교 벤치마크에서는 이 지표를 아예 빼고 `dotnet-counters`의 가벼운 카운터로 대체하는 편이 낫다.

## 65.4 지연 시간 모드 — Batch / Interactive / LowLatency / SustainedLowLatency / NoGCRegion

### 세 번째 축, 그리고 유일하게 런타임에 바꿀 수 있는 축

네 가지 GC 모드와 직교하게, **지연(일시 정지) 동작을 제어하는 설정**이 하나 더 있다. 지연 시간 모드 설정 덕분에 GC의 **침습성** — 얼마나 기꺼이 블로킹 일시 정지를 도입할 것인가 — 을 제어할 수 있다.

지금까지 본 GC 모드 설정과 결정적으로 다른 점이 있다. **지연 시간 모드는 프로그램 동작 중에 동적으로 바꿀 수 있다.** 이것이 흥미로운 가능성을 연다.

환경 변수(`COMPlus_GCLatencyMode` / `DOTNET_GCLatencyMode`)로도 설정할 수 있지만, **지원되는 방법은 코드에서 `GCSettings.LatencyMode` 정적 속성으로 설정하는 것**이다.

```csharp
public enum GCLatencyMode
{
    Batch = 0,
    Interactive = 1,
    LowLatency = 2,
    SustainedLowLatency = 3,
    NoGCRegion = 4
}
```

### 다섯 모드가 실제로 무엇을 바꾸는가

"지연 시간 모드"라는 이름은 오해를 부른다. 이것은 GC에게 "빨라져라"라고 부탁하는 것이 아니다. **각 모드는 아주 구체적으로 "어떤 종류의 GC를 금지할 것인가"를 정한다.** 그것이 전부다.

| 모드 | 값 | 실제로 무엇을 바꾸는가 | 사용 가능한 GC 모드 | 기본값인 경우 |
|---|---|---|---|---|
| **Batch** | 0 | **백그라운드 GC를 끈다.** 일시 정지 길이에 관심이 없으므로 GC가 처리량이나 메모리 사용량 같은 다른 측면을 최적화할 수 있다 | 전부 | 모든 비동시 GC(`System.GC.Concurrent`/`gcConcurrent`를 끈 상태로 시작) |
| **Interactive** | 1 | **백그라운드 GC를 켠다.** 개별 일시 정지의 길이를 최소화하려 시도하며, 그 대가로 메모리를 더 쓴다 | 전부 | 모든 동시 GC. 즉 **.NET의 실질적 기본값** |
| **LowLatency** | 2 | **모든 일반 gen2 수집(동시·비동시 전부)을 금지한다** | **워크스테이션만** | 없음 |
| **SustainedLowLatency** | 3 | **비동시 전체 GC만 금지한다.** ephemeral GC와 백그라운드 GC는 허용된다 | 워크스테이션·서버(단, 시작 시 동시 설정이 켜져 있어야 함) | 없음 |
| **NoGCRegion** | 4 | GC를 통째로 끄려 시도한다. **속성 대입으로는 설정되지 않는다** — `GC.TryStartNoGCRegion` 전용 | 전부 | 없음 |

### Batch — 동적으로 백그라운드 GC 끄기

Batch 모드에서는 일시 정지 길이에 관심이 없다. 그래서 GC가 다른 측면(처리량이나 메모리 사용량)을 최적화할 수 있다. 실무적으로는 **백그라운드 GC 가능성을 없애는 옵션**이다. 다시 말해 애플리케이션 시작 시 동시 GC가 켜져 있었어도 **런타임에 동적으로 끌 수 있다.**

그러면 이미 만들어진 백그라운드 GC 스레드는 어떻게 되는가. GC 모드에 따라 다르다.

| GC 모드 | 백그라운드 GC 스레드의 운명 |
|---|---|
| 서버 GC | 지연 시간 모드가 되돌려질 때까지 **무기한 중단된다** |
| 워크스테이션 GC | 일정 시간(현재 **20초**) 후 타임아웃되어 **소멸된다.** `GCTerminateConcurrentThread` ETW/EventPipe 이벤트가 발행된다 |

### Interactive — 기본값이자 동적으로 백그라운드 GC 켜기

대화형 모드에서 GC는 개별 일시 정지의 지속 시간을 최소화하려 하며 그 대가로 메모리를 더 쓴다(대화형 UI 애플리케이션에서 바람직하다). 백그라운드 GC를 켜고, **모든 동시 GC의 기본 설정**이다. 워크스테이션과 서버 GC 모드가 모두 기본적으로 동시이므로 **.NET의 기본 설정이기도 하다.**

Batch의 보완으로, 동시 GC를 동적으로 켜는 데 쓸 수 있다. 이 경우 백그라운드 GC 스레드가 없으면 만들어지고 `GCCreateConcurrentThread` 이벤트가 발행된다.

추가로, **워크스테이션 GC + Interactive 모드**(즉 기본 조합)에서는 **GC 시간 튜닝이 활성화된다**(64.1절의 수집 튜닝).

### LowLatency — 가장 강한 요구, 그러나 워크스테이션 전용

GC 일시 정지 시간을 무슨 대가를 치르더라도 최소화하는 것이 필수적일 때 쓴다. **워크스테이션 GC 모드에서만 사용 가능하다.** LowLatency 모드는 **모든 일반적인, 동시·비동시를 막론한 gen2 가비지 컬렉션을 비활성화한다.** 꽤 강한 요구다. 전체 GC는 **저메모리 시스템 알림을 받았을 때** 또는 **명시적으로 트리거됐을 때**(`GC.Collect` 호출 등)만 일어난다.

말할 필요도 없이 애플리케이션 동작에 큰 영향을 미친다.

- 전체 일시 정지 시간이 정말 짧아진다. 빠른 ephemeral 수집만 일어나기 때문이다.
- **메모리 사용량이 크게 늘어날 가능성이 높다.** gen2나 LOH에 쌓이는 객체가 전혀 수집되지 않기 때문이다.

> **⚠️ LowLatency는 반드시 짧게, 반드시 되돌려라**
>
> 이런 강한 지연 시간 모드는 **지연 요구가 절대적으로 필수적인 짧은 기간에만** 써야 한다. 사용자와의 집중적 상호작용 구간 같은 것이다. 그리고 이 모드로 동작한 뒤에는 조만간 반드시 격렬한 가비지 컬렉션이 일어난다는 사실을 알고 있어야 한다. 대개는 **통제된 시점에 수동으로 GC를 트리거하는 것**이 최선이다.

.NET Framework에서 이 모드를 설정할 때는 특별한 주의가 필요하다.

```csharp
// .NET Framework 전용 패턴 — CER로 finally 실행을 보장한다
GCLatencyMode oldMode = GCSettings.LatencyMode;
RuntimeHelpers.PrepareConstrainedRegions();
try
{
    GCSettings.LatencyMode = GCLatencyMode.LowLatency;
    // 시간에 민감한 짧은 작업을 여기서 수행한다
}
finally
{
    GCSettings.LatencyMode = oldMode;
}
```

일반적인 `try`/`finally`만으로는 .NET Framework에서 충분하지 않을 수 있다. `finally` 블록이 실행되지 않는 드문 상황이 여전히 존재하기 때문이다. 추가 예방책으로 **제약 실행 영역(CER, Constrained Execution Regions)** 을 쓴다. .NET 문서의 표현으로 "CER은 신뢰할 수 있는 관리 코드 작성 메커니즘의 일부다. CER은 그 안의 코드가 전부 실행되는 것을 막을 대역 외 예외를 CLR이 던지지 못하도록 제약하는 영역을 정의한다". 예를 들어 CLR은 CER 안에서 실행 중인 코드에 대해 스레드 중단을 지연시킨다.

> **⚠️ .NET(Core)에서 CER은 폐기되었다**
>
> .NET(Core)에서 CER은 deprecated다. 런타임이 `finally` 블록 실행에 대해 더 강한 보장을 제공하기 때문이다(`Thread.Abort`도 AppDomain 언로드도 없다). `RuntimeHelpers.PrepareConstrainedRegions()`는 .NET(Core)에서 **아무 동작도 하지 않는 no-op**이다. 새 코드에서는 그냥 `try`/`finally`를 쓰면 된다. 반대로, 인터넷에서 찾은 .NET Framework 시절 예제를 그대로 옮겨 놓고 "CER로 보호했으니 안전하다"고 믿는 것도 곤란하다.

### SustainedLowLatency — 실무에서 실제로 쓰이는 것

LowLatency의 지연 요구가 너무 강하고 힙이 너무 빨리 자랄 수 있어서, .NET Framework 4.5에서 또 다른 버전이 도입됐다. **워크스테이션과 서버 GC 모드 모두에서 쓸 수 있다.** 짧은 일시 정지와 메모리 사용량 사이의 타협이다. 이 모드는 **비동시 전체 GC만 비활성화한다.** 다시 말해 ephemeral GC와 백그라운드 GC는 허용된다.

- **시작 시 동시 설정이 켜져 있어야만** 사용 가능하다(나중에 Batch/Interactive 지연 시간 모드로 바꾼 것과는 무관하다).
- LowLatency와 마찬가지로 전체 블로킹 GC는 저메모리 시스템 알림이나 명시적 트리거로만 가능하다.

SustainedLowLatency는 힙이 자라는 속도를 제한하면서 짧은 일시 정지를 제공하므로(LowLatency만큼 짧지는 않다 — 백그라운드 GC가 도입하는 일시 정지가 있다) **더 긴 시간 동안 저지연 모드에 머무를 수 있다.**

사용자 입력을 다룰 때 아주 좋은 타협일 수 있다. 이 정확한 시나리오를 Visual Studio가 쓰는 Roslyn 파서 소스에서 볼 수 있다. 사용자가 에디터에 무언가를 입력할 때 SustainedLowLatency가 켜지고, 지정된 타임아웃 후 원래 값으로 되돌아간다.

```csharp
/// <summary>
/// GC 모드를 SustainedLowLatency로 설정하는 것을 관리한다.
/// 어느 스레드에서 호출해도 안전하지만, 키보드나 마우스 입력을 받을 때
/// UI 스레드에서 호출하는 것을 의도한다.
/// </summary>
internal static class GCManager
{
    /// <summary>
    /// 높은 지연이 허용되지 않는 시나리오(예: 타이핑 입력 처리)에서
    /// 비싼 블로킹 gen2 GC를 억제하려면 이 메서드를 호출한다.
    ///
    /// UseLowLatencyModeForProcessingUserInput이 다시 호출되지 않으면
    /// 짧은 시간 뒤 블로킹 GC가 자동으로 다시 켜진다.
    /// </summary>
    internal static void UseLowLatencyModeForProcessingUserInput()
    {
        // ...
        var currentMode = GCSettings.LatencyMode;
        var currentDelay = s_delay;
        if (currentMode != GCLatencyMode.SustainedLowLatency)
        {
            GCSettings.LatencyMode = GCLatencyMode.SustainedLowLatency;
            // 마지막 요청으로부터 짧은 시간 뒤 LatencyMode를 복원한다.
            currentDelay = new ResettableDelay(s_delayMilliseconds);
            currentDelay.Task.SafeContinueWith(
                _ => RestoreGCLatencyMode(currentMode), TaskScheduler.Default);
            s_delay = currentDelay;
        }
        currentDelay?.Reset();
    }
}
```

이 패턴의 핵심은 **타이머로 자동 복귀한다**는 것이다. `try`/`finally`로는 "사용자가 타이핑하는 동안"이라는 구간을 표현할 수 없다. 마지막 입력 이후 N 밀리초가 지나면 원래 모드로 돌아간다.

> **💡 트레이딩 시스템의 SustainedLowLatency**
>
> 이 모드는 UI 전용이 아니다. 일부 서버 애플리케이션 — 특히 트레이딩 앱 — 은 **거래 시간 동안 전체 블로킹 GC의 방해를 받고 싶지 않다**는 것을 표현하기 위해 SustainedLowLatency를 쓴다. 동시에 그 시간 동안 충분한 메모리가 있음을 확인해 둔다. 장 마감 후 통제된 시점에 `GC.Collect`로 정리한다. 이런 식으로 "업무 시간 = 저지연, 업무 외 시간 = 정리"라는 리듬을 만드는 것이 현실적인 사용법이다.

### NoGCRegion — 설정할 수 있는 가장 강한 요구

.NET Framework 4.6에서 추가된, 단연 가장 강한 요구다. Microsoft 문서의 설명으로 이 모드는 "지정된 양의 메모리가 사용 가능하다면 임계 경로 실행 중 가비지 컬렉션을 허용하지 않으려 시도한다". 다시 말해 **GC를 완전히 끄려 하지만 무한정 그럴 수는 없다.**

그래서 `GCSettings.LatencyMode`에 `GCLatencyMode.NoGCRegion`을 대입하는 것으로는 켤 수 없다 — **이 속성으로는 진입할 수 없다**(런타임 버전에 따라 무시되거나 `ArgumentOutOfRangeException`이 난다). 대신 전용 메서드가 여러 오버로드로 도입됐다.

```csharp
bool GC.TryStartNoGCRegion(long totalSize);
bool GC.TryStartNoGCRegion(long totalSize, bool disallowFullBlockingGC);
bool GC.TryStartNoGCRegion(long totalSize, long lohSize);
bool GC.TryStartNoGCRegion(long totalSize, long lohSize, bool disallowFullBlockingGC);
void GC.EndNoGCRegion();
```

- `totalSize` — GC를 트리거하지 않고 할당할 수 있기를 바라는 메모리 양(바이트). 달리 말하면 **관리 힙당 미리 확보되어 있어야 하는 메모리 양**이다.
- `lohSize` — 그 할당 중 얼마나 LOH에 쓸 것인지. **지정하지 않으면 `totalSize` 제한이 SOH와 LOH 각각에 별도로 적용된다.** 즉 실질적으로 `totalSize`의 **두 배**를 할당할 수 있게 된다.
- `disallowFullBlockingGC` — 요청한 양보다 가용 메모리가 적을 때, `TryStartNoGCRegion` 구현 내부에서 최소 요청량을 찾기 위해 **전체 비동시 GC를 트리거한다.** 이 인자를 `true`로 주면 그 동작을 금지한다(그러면 메모리가 부족할 때 그냥 `false`를 반환한다).
- 반환값 `true`는 GC가 "충분한 메모리가 실제로 있다"고 인정했고 no GC 지연 시간 모드에 진입했다는 뜻이다.

### 완전한 사용 예제

```csharp
using System;
using System.Runtime;

public static class CriticalPath
{
    public static void Run()
    {
        // 이전 finally 블록이 실행되지 않았을 경우를 대비한다
        if (GCSettings.LatencyMode == GCLatencyMode.NoGCRegion)
        {
            GC.EndNoGCRegion();
        }

        // SOH 100 MB를 확보하고, 부족하면 전체 블로킹 GC는 하지 않는다
        if (GC.TryStartNoGCRegion(100 * 1024 * 1024, disallowFullBlockingGC: true))
        {
            try
            {
                // 지연에 민감한 임계 작업을 여기서 수행한다.
                // 할당 총량이 100 MB를 넘지 않는 한 GC는 트리거되지 않는다.
                DoLatencySensitiveWork();
            }
            finally
            {
                try
                {
                    GC.EndNoGCRegion();
                }
                catch (InvalidOperationException ex)
                {
                    // 할당 한도를 이미 넘겨 모드가 되돌려진 경우 여기로 온다.
                    // 로깅만 하고 삼킨다 — 이미 GC는 정상 동작 중이다.
                    Log(ex);
                }
            }
        }
        else
        {
            // 확보 실패. no GC 영역 없이 그냥 진행하거나, 작업을 미룬다.
            DoLatencySensitiveWork();
        }
    }
}
```

패턴의 세 가지 요소를 놓치지 마라.

1. **시작 전에 이전 영역이 남아 있는지 확인한다.**
2. **`finally` 안의 `EndNoGCRegion` 호출을 다시 `try`로 감싼다.** 이 호출은 던질 수 있다.
3. **`TryStartNoGCRegion`이 `false`를 반환한 경로를 반드시 처리한다.** 무시하고 진행하면 no GC 영역이 아닌 채로 임계 작업이 도는데, `finally`에서 `EndNoGCRegion`을 호출하면 예외가 난다.

### 실패 조건과 예외

| 상황 | 결과 |
|---|---|
| 요청량보다 가용 메모리가 적고 `disallowFullBlockingGC`가 기본값 | 내부에서 **전체 비동시 GC**를 트리거해 확보를 시도한다 |
| 요청량 확보에 실패 | `TryStartNoGCRegion`이 **`false` 반환** |
| **세그먼트 구현**에서 `totalSize`(또는 `totalSize - lohSize`)가 ephemeral 세그먼트 크기를 초과 | **`ArgumentOutOfRangeException`** |
| 이전 `TryStartNoGCRegion`에 대응하는 `EndNoGCRegion` 호출 없이 다시 `TryStartNoGCRegion` 호출 | **`InvalidOperationException`** — "The NoGCRegion mode was already in progress." |
| 할당이 `totalSize`를 초과해 모드가 자동 해제된 뒤 `EndNoGCRegion` 호출 | **`InvalidOperationException`** — "Allocated memory exceeds specified memory for NoGCRegion mode." |

> **⚠️ 세그먼트 크기 제한 — 리전 이전 구현의 함정**
>
> 레거시 세그먼트 기반 GC에서는 **지정한 크기가 모든 ephemeral 세그먼트의 총 크기 이하여야 한다**(서버 GC라면 ephemeral 세그먼트 크기에 힙 개수를 곱한 값). `lohSize`를 지정하면 `totalSize - lohSize`(즉 SOH 크기)가 ephemeral 세그먼트 크기 이하여야 하고, `totalSize`만 지정하면 SOH·LOH 어느 쪽을 의도했는지 알 수 없으므로 **안전한 쪽으로 가정해 `totalSize` 전체가 ephemeral 세그먼트 크기 이하**여야 한다. ephemeral 세그먼트 공간이 떨어지면 GC를 트리거할 수밖에 없기 때문이다. 초과하면 `ArgumentOutOfRangeException`이 던져진다. .NET 7+의 리전 구현에서는 이 제약의 성격이 달라지지만, **여전히 요청량이 무한정 클 수는 없다.**

> **⚠️ 짝을 맞추지 않으면 다음 호출이 무조건 실패한다**
>
> GC 관점에서는 `EndNoGCRegion`을 잊어도 크게 문제되지 않는다. `totalSize` 할당을 넘기면 지연 시간 모드가 원래대로 되돌아가는 것이 보장된다. **그러나 no GC API 관점에서는 `TryStartNoGCRegion` 호출마다 대응하는 `EndNoGCRegion` 호출이 있어야 한다.** 없으면 이후의 `TryStartNoGCRegion` 호출이 "The NoGCRegion mode was already in progress." 메시지와 함께 `InvalidOperationException`을 던진다. **할당 한도가 이미 위반되어 지연 시간 모드가 되돌려진 상태에서도 마찬가지다!** 그 경우에도 여전히 `EndNoGCRegion`을 호출해야 하고, 그 호출은 "Allocated memory exceeds specified memory for NoGCRegion mode." 메시지의 `InvalidOperationException`을 던진다는 것을 알고 있어야 한다.
>
> no GC 영역은 설계상 일정 할당량으로 제한되므로, 저지연 모드를 설정할 때만큼 CER로 보호할 필요는 없다. 최악의 경우 GC가 트리거될 뿐이다. 그래도 `TryStartNoGCRegion` 호출 전에 이전 영역을 끝내야 하는지 확인하는 것은 항상 좋다.

> **📌 `GC.RegisterNoGCRegionCallback`**
>
> `GC.RegisterNoGCRegionCallback(long totalSize, Action callback)`도 있다. no GC 영역에서 지정한 할당량에 도달했을 때 콜백을 받는다. "한도의 80% 지점에서 미리 작업을 마무리한다" 같은 패턴에 쓸 수 있다.

> **📌 소스에서 no GC 영역**
>
> `GC.TryStartNoGCRegion`의 구현인 `GCInterface_StartNoGCRegion`이 `GCHeap::StartNoGCRegion`을 호출한다. 여기서 `GCHeap::GarbageCollect`가 호출될 수 있고, `gc_heap::prepare_for_no_gc_region`이 ephemeral 세그먼트 크기 조건을 검사하고 no GC 모드에 허용된 한도를 설정한다. 이후 정상 실행 중 GC 조건이 충족되면 `gc_heap::should_proceed_for_no_gc`가 할당 한도 위반을 검사한다.

### 지연 시간 최적화 목표 — 앞으로의 방향

64.1절의 정적 데이터 이야기에서 또 하나의 지연 제어 층이 나왔다. **지연 시간 최적화 목표(latency optimization goals, 레벨)** 다. .NET 소스의 주석은 이렇게 말한다. "지연 시간 모드는 사용자에게 특정한 GC 지식(예: 예산, 전체 블로킹 GC)을 요구했다. 우리는 그것에서 벗어나려 한다. 사용자에게 의미 있는 성능 측면 중 무엇이 가장 중요한지 말하게 하는 것이 훨씬 합리적이기 때문이다." 그 측면이란 메모리 사용량, 처리량, 일시 정지 예측 가능성이다.

| 레벨 | 이름 | 특성 | 지원 여부(.NET Framework 4.8 / .NET 8 기준) |
|---|---|---|---|
| 0 | 메모리 사용량 | 일시 정지가 길고 잦을 수 있으나 힙 크기가 작게 유지된다 | 지원 |
| 1 | 일시 정지와 처리량의 균형 | 일시 정지가 더 예측 가능하고 더 잦다. 가장 긴 일시 정지가 레벨 0보다 짧다 | **지원(기본값)** |
| 2 | 처리량 | 일시 정지가 예측 불가능하지만 아주 잦지는 않다(그리고 길 수 있다) | 미지원 |
| 3 | 짧은 일시 정지 | 일시 정지가 더 예측 가능하고 더 잦다. 가장 긴 일시 정지가 레벨 1보다 짧다 | 미지원 |

지연 시간 레벨은 `GCLatencyLevel` 구성 손잡이로 접근한다. `COMPlus_GCLatencyLevel` / `DOTNET_GCLatencyLevel` 환경 변수에 0 또는 1(기본값)을 준다.

> **⚠️ 레벨 2와 3은 아직 구현되지 않았다**
>
> 계획된 네 레벨 중 **현재 지원되는 것은 0과 1뿐이고**, 그 둘조차 런타임과 GC 전반에서의 활용이 여전히 매우 제한적이다. 블로그 글에서 레벨 3("짧은 일시 정지")을 보고 설정해 봤자 아무 일도 일어나지 않는다. 앞으로의 방향을 알아두는 정도로 충분하다.

## 65.5 힙 하드 리밋, 힙 개수, GC 스레드 어피니티

여기서부터는 모드가 아니라 **구성 손잡이(configuration knob)** 다. 65.8절에서 볼 `GC.GetConfigurationVariables` 메서드가 반환하는 값들이 대체로 이것이고, 내부 변수는 `.\src\coreclr\gc\gcconfig.h`에 정의되어 있다.

이 절과 다음 절의 설정은 `DOTNET_xxx` 환경 변수(.NET 6 이전에는 `COMPlus_xxx`)로 켠다. 대부분은 `runtimeconfig.json`의 `configProperties`로도 설정할 수 있다. **숫자 값은 `0x` 접두사 없이 16진수로 해석된다**는 것을 다시 한번 기억하라.

### 힙 하드 리밋

컨테이너 안에서 돌 때 GC는 환경의 메모리 제한을 자동으로 감지한다. 그런데 GC는 애플리케이션이 쓰는 **관리 메모리의 양만** 제어한다 — 메서드를 JIT 하는 데 쓰는 메모리나 네이티브 코드의 할당은 제어하지 못한다. 그래서 **모든 힙의 누적 크기를 컨테이너에 할당된 총 메모리의 일정 비율로 제한한다. 기본값은 75%다.**

즉 1 GB 제한이 걸린 컨테이너에서 .NET 애플리케이션을 돌리면 **GC는 750 MB를 넘게 쓰지 않고, 그 이상 할당하려 하면 `OutOfMemoryException`을 던진다.** 나머지 250 MB는 다른 모든 것을 위해 남는다.

시나리오에 따라 이 제한이 너무 높을 수도(예제에서 네이티브 코드나 같은 컨테이너의 다른 프로세스가 250 MB보다 많이 써서 OOM 킬 당한다), 너무 낮을 수도 있다(프로세스가 800~900 MB까지 쓰기를 원한다). 그렇다면 직접 조정한다.

| 설정 | 의미 |
|---|---|
| `GCHeapHardLimit` | 모든 힙의 총 메모리 사용량에 대한 **절대 제한**(바이트) |
| `GCHeapHardLimitPercent` | 총 물리 메모리 대비 **비율 제한**. 기본 75%를 바꾼다 |
| `GCHeapHardLimitSOH` / `LOH` / `POH` | 각 힙 크기의 절대 제한 |
| `GCHeapHardLimitSOHPercent` / `LOHPercent` / `POHPercent` | 각 힙 크기의 비율 제한 |

```text
DOTNET_GCHeapHardLimit=32000000        # 16진수 → 838,860,800 바이트 (약 800 MB)
DOTNET_GCHeapHardLimitPercent=50       # 16진수 0x50 → 80 (%)
```

> **⚠️ 여기서 16진수 함정이 가장 아프게 작동한다**
>
> `DOTNET_GCHeapHardLimitPercent=50`은 50%가 아니라 **80%** 다(0x50 = 80). `DOTNET_GCHeapHardLimit=1000000`은 100만 바이트가 아니라 **16,777,216바이트**다. 힙 하드 리밋 설정에서 이 실수를 하면 프로덕션에서만 재현되는 OOM이 되거나, 반대로 아무 효과가 없는 설정이 된다. **설정 후에는 반드시 `GC.GetConfigurationVariables()`로 실제 반영된 값을 확인하라**(65.8절).

`GCHeapHardLimitSOH`/`LOH`/`POH` 조합은 더 세밀한 제어를 준다. **고급 시나리오에서만 써야 한다.**

**.NET 8부터는 이 값들을 런타임에 바꿀 수 있다.** `GC.RefreshMemoryLimit()`을 쓴다 — 65.8절에서 자세히 본다.

### 힙 개수

서버 GC 모드에서 GC는 가용 코어 수만큼 힙을 만든다. 어떤 경우에는 더 적은 힙을 쓰고 싶다(대개는 프로세스의 메모리 사용량을 줄이기 위해서다). `GCHeapCount` 설정으로 그렇게 한다.

- .NET Framework 4.6+ 와 .NET(Core)에서 사용 가능하다.
- **서버 GC 모드에서만 설정할 수 있다.**
- GC가 쓰는 **스레드 수와 관리 힙 수를 함께** 지정한다.
- 제공한 값은 **프로세스가 사용 가능한 논리 CPU 수보다 작아야 한다.** 그렇지 않으면 그 수로 잘린다.

```xml
<!-- .NET Framework: app.config / web.config -->
<configuration>
  <runtime>
    <gcServer enabled="true"/>
    <GCHeapCount enabled="6"/>
  </runtime>
</configuration>
```

```json
{
  "runtimeOptions": {
    "configProperties": {
      "System.GC.Server": true,
      "System.GC.HeapCount": 6
    }
  }
}
```

> **📌 `GCHeapCount` 이전에는 코어 수를 줄이는 방법밖에 없었다**
>
> 예전에는 이 제한을 걸려면 **프로세스가 쓸 수 있는 논리 코어 수 자체를 제한**해야 했다. 심각한 부작용이 있었다. 런타임 전체에 영향을 미쳐서 GC만 제한하려던 것이 **.NET 프로그램 전체의 동시성을 원치 않게 제한**해 버렸다. `GCHeapCount` 도입 이후로는 이쪽이 GC의 그 측면을 제어하는 선호 방법이다.

### GC 스레드 어피니티

서버 GC 모드에서 GC는 GC 힙 수만큼 GC 스레드를 만들고, **각 GC 스레드는 CPU 코어 하나에 고정(pin)된다.** 기본 어피니티를 바꾸고 싶은 경우가 몇 가지 있다.

**경우 1 — 힙 수를 줄였을 때.** 남은 GC 스레드는 **순서대로 앞쪽 코어에 고정된다.** 힙을 3개로 설정하면 GC 스레드 3개가 앞의 CPU 코어 3개에 고정된다. 같은 머신에 여러 .NET 프로세스가 돌고 있다면 이것은 원하는 결과가 아닐 것이다 — **전부가 앞쪽 코어를 두고 경쟁하고 나머지 코어는 놀게 된다.**

```text
8코어 머신, GCHeapCount=3인 .NET 프로세스 3개 (기본 어피니티)

  core0   core1   core2   core3   core4   core5   core6   core7
 ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐
 │ P1  │ │ P1  │ │ P1  │ │     │ │     │ │     │ │     │ │     │
 │ P2  │ │ P2  │ │ P2  │ │ 놀고│ │ 놀고│ │ 놀고│ │ 놀고│ │ 놀고│
 │ P3  │ │ P3  │ │ P3  │ │ 있음│ │ 있음│ │ 있음│ │ 있음│ │ 있음│
 └─────┘ └─────┘ └─────┘ └─────┘ └─────┘ └─────┘ └─────┘ └─────┘
   ↑ 3개 프로세스의 GC 스레드가 같은 3개 코어에서 싸운다
```

`GCHeapAffinitizeMask` 또는 `GCHeapAffinitizeRanges`로 바꾼다. 둘 다 GC 스레드를 어느 CPU 코어에 고정할지 지정하되 문법이 다르다.

**경우 2 — 어피니티 자체가 해로울 때.** 어떤 이유로든 프로세스마다 서로 다른 코어를 배정하는 것이 실용적이지 않을 수 있다. 어떤 프로세스는 자원을 주기적으로만 쓰기 때문에 코어 집합 전체를 전용으로 주는 것이 낭비일 수 있다. 그것 자체는 괜찮지만, 이 경우 **GC 스레드 고정이 해로워진다.** 동시에 도는 다른 프로세스가 일부 코어를 오래 독점할 수 있는데, GC 스레드는 고정되어 있어서 **OS 스케줄러가 다른 코어로 재배치할 수 없기** 때문이다. 이런 상황에서는 GC 스레드 고정을 아예 끄는 편이 낫다. `GCNoAffinitize`가 그것을 한다.

**경우 3 — Windows CPU 그룹.** Windows에서는 걱정거리가 하나 더 있다. 여러 CPU 그룹을 가진 시스템에서 돌고 있다면 **GC는 프로세스가 배정된 CPU 그룹의 코어만 쓴다.** 모든 코어를 쓰고 싶다면 `GCCpuGroup`을 설정해야 한다. **이 제약은 .NET 7 + Windows 11 / Windows Server 2022 조합에서 해소되었다.**

| 설정 | 용도 |
|---|---|
| `GCHeapCount` | 서버 GC의 힙(그리고 GC 스레드) 개수 |
| `GCHeapAffinitizeMask` | GC 스레드를 고정할 CPU 코어를 비트마스크로 지정 |
| `GCHeapAffinitizeRanges` | 같은 목적, 범위 문법(`0-3,8-11` 형태) |
| `GCNoAffinitize` | GC 스레드 고정을 완전히 끈다 |
| `GCCpuGroup` | 여러 CPU 그룹을 가진 Windows 시스템에서 모든 그룹의 코어를 쓴다 |

> **💡 다중 인스턴스 호스팅에서의 조합**
>
> 한 머신에 .NET 서비스를 여러 개 올린다면 선택지는 셋이다. (1) 각 프로세스에 `GCHeapCount` + `GCHeapAffinitizeRanges`로 겹치지 않는 코어를 배정한다 — 완전히 CPU를 인식하는 배치가 가능하지만 관리 비용이 크다. (2) `GCNoAffinitize`로 고정을 끄고 OS 스케줄러에 맡긴다 — 부하가 주기적이고 예측하기 어려울 때 낫다. (3) .NET 8 이후라면 **DATAS에 맡긴다**(65.7절). 새로 짓는 시스템이라면 (3)부터 검토하는 것이 합리적이다.

> **⚠️ 어피니티 설정은 컨테이너의 CPU 제한과 잘 맞지 않는다**
>
> 컨테이너에 CPU 할당량(quota)이 걸려 있으면 "코어 몇 개"라는 개념 자체가 흐려진다. cgroup의 CPU quota는 특정 코어를 주는 것이 아니라 **시간 슬라이스 비율**을 주는 것이기 때문이다. 이 상황에서 `GCHeapAffinitizeMask`를 지정하는 것은 대개 도움이 되지 않고 종종 해롭다. 컨테이너에서는 `GCHeapCount`(또는 DATAS)까지만 쓰고 어피니티는 건드리지 않는 편이 낫다. 컨테이너 전반은 72.8절에서 다룬다.

## 65.6 메모리 부하 임계값과 보수적 모드, 대용량 페이지

### 메모리 부하 임계값

시스템이 무거운 부하 아래 있으면 GC는 동작을 바꾼다. 더 공격적으로 메모리를 회수하고 메모리 사용량을 줄이려 한다. **기본적으로 이것은 총 물리 메모리 사용량(모든 프로세스 포함)이 90%에 도달할 때 일어난다.** RAM이 80 GB보다 많은 머신에서는 코어 수에 따라 기본값이 조정되지만 **항상 90%에서 97% 사이**다.

`GCHighMemPercent`로 이 임계값을 직접 조정한다.

```text
DOTNET_GCHighMemPercent=5F        # 16진수 0x5F → 95 (%)
```

> **💡 메모리를 조금만 쓰는 프로세스라면 임계값을 올려라**
>
> 이 설정이 유용한 대표적 경우는 **내 프로세스가 메모리를 많이 쓰지 않을 때**다. 해방시킬 메모리가 애초에 별로 없는데 GC를 더 공격적으로 만들어 성능에 영향을 주는 것은 의미가 없다. 이 경우 임계값을 올리는 편이 좋다. 반대로 같은 머신에서 메모리를 크게 쓰는 다른 프로세스와 공존한다면 임계값을 낮춰 더 일찍 양보하게 만들 수도 있다.

### GC 보수적 모드 — `GCConserveMemory`

64장에서 본 것처럼 가비지 컬렉션의 빈도는 세대 예산에 달려 있고(63.6절), 예산은 수집에서 살아남은 객체의 비율에 따라 조정된다. 결론적으로 **GC는 메모리 사용량이 아니라 오버헤드를 최소화하도록 튜닝되어 있다.** 어떤 경우에는 이것이 바람직하지 않다. 예를 들어 한 서버에서 많은 애플리케이션을 돌릴 때 그렇다.

오버헤드를 얼마간 내주고 메모리 사용량을 낮추고 싶은 상황을 위해 `GCConserveMemory` 설정이 도입됐다. **애플리케이션이 감내할 총 단편화 양의 한도를 설정한다.**

- **.NET Framework 4.8과 .NET 5부터 사용 가능하다.**
- .NET Framework 4.8+: `app.config`의 Configuration ▸ Runtime ▸ `GCConserveMemory` 키 또는 `COMPlus_GCConserveMemory` 환경 변수
- .NET 5+: `runtimeconfig.json`의 `configProperties`에 `System.GC.ConserveMemory` 키 또는 `DOTNET_GCConserveMemory` 환경 변수

값은 **0에서 9 사이**다. 0이면 비활성화다. **값이 클수록 GC가 공격적이다.** 단편화 한도는 다음과 같이 계산된다.

```text
최대 단편화 비율 = (10 - GCConserveMemory) / 10

GCConserveMemory = 5  →  (10-5)/10 = 0.5  →  단편화 50% 이하 유지
GCConserveMemory = 7  →  (10-7)/10 = 0.3  →  단편화 30% 이하 유지
GCConserveMemory = 9  →  (10-9)/10 = 0.1  →  단편화 10% 이하 유지
```

실제로는 **각 gen2 수집마다** GC가 gen2와 LOH의 누적 단편화 양을 계산한다. 그 양이 임계값을 넘으면 GC는 빈 공간을 회수하기 위해 **압축 수집**을 수행한다. 추가로, **LOH 단독의 단편화가 임계값 위라면 LOH도 압축된다.** 이것은 **LOH 압축이 자동으로 일어나는 드문 상황 중 하나**다(64.8절).

> **⚠️ LOH 압축 조건은 총 단편화가 먼저다**
>
> LOH 압축 조건은 **총 단편화가 임계값을 넘은 경우에만** 평가된다. 다시 말해 **LOH가 극도로 단편화되어 있어도 gen2에 유의미한 단편화가 없으면 LOH는 압축되지 않을 가능성이 높다.**
>
> 구체적인 예를 보자. gen2가 2 GB에 단편화 10%, LOH가 1 GB에 단편화 90%라고 하자. gen2가 LOH의 두 배 크기이므로 누적 단편화는 **약 36%** 밖에 안 된다. 그래서 **`GCConserveMemory`를 7 이상(단편화 한도 30% 이하)으로 설정해야만 LOH가 압축된다.** "LOH 단편화가 90%인데 왜 압축이 안 되는가"의 답이 여기 있다.

### 대용량 페이지

61장에서 잠깐 다룬 대용량 페이지(large pages, Linux에서는 huge pages)는 기본 4 kB보다 큰 페이지를 뜻한다. **x64는 2 MB와 1 GB 페이지 크기를 지원한다.** .NET은 `GCLargePages` 설정으로 **실험적 지원**을 제공한다. 활성화하면 두 가지 방식으로 성능이 개선될 수 있다.

- **TLB 미스 감소.** 페이지가 크면 페이지 수가 줄어들고, 가상 주소를 물리 주소로 변환하는 TLB(Translation Lookaside Buffer) 사용이 줄어든다.
- **페이지 폴트 감소.** 애플리케이션이 거대한 버퍼를 할당할 때 GC가 요청된 메모리를 커밋하고 0으로 채우는 데 시간이 걸릴 수 있다. 대용량 페이지를 쓰면 **처음부터 메모리가 커밋되어** 이 비용이 사라진다.

대용량 페이지를 쓰면 **메모리가 절대 페이지 아웃되지 않는다.** 같은 머신의 다른 애플리케이션에 영향을 줄 수 있어서 OS가 사용을 제한한다.

| OS | 요구 조건 |
|---|---|
| Windows | 프로세스를 실행하는 사용자에게 **`SeLockMemoryPrivilege`** 권한이 있어야 한다 |
| Linux | huge page가 풀에 미리 할당되어 있어야 하고, 그 풀 크기는 관리자가 관리한다 |

> **⚠️ `GCLargePages`는 힙 하드 리밋 없이는 시작조차 못 한다**
>
> `GCLargePages`를 켜려면 **반드시 힙 하드 리밋도 설정해야 한다.** 그러지 않으면 프로세스 초기화가 오류 코드 **`0x8013200E` (`CLR_E_GC_LARGE_PAGE_MISSING_HARD_LIMIT`)** 로 실패한다. GC가 시작 시점에 모든 대용량 페이지를 커밋하므로 얼마나 쓸 것인지 미리 알아야 하기 때문이다.
>
> 그런데 `GCHeapHardLimit`으로 리밋을 설정하면 **GC가 요청한 크기의 두 배를 커밋한다**(추가 메모리를 쓰지는 않는다). 이유는 불명확하며 버그일 가능성이 높다. 대신 **`GCHeapHardLimitSOH`, `GCHeapHardLimitLOH`, `GCHeapHardLimitPOH`로 힙별 리밋을 설정하는 것을 권한다.** 이 경우 GC는 세 힙에 필요한 메모리만 커밋한다. 단, **셋을 전부 설정해야 한다.** 하나라도 빠지면 초기화가 오류 코드 **`0x8013200D`** 로 실패한다.

> **📌 `GCConserveMemory`와 `GCHeapCount`는 다른 문제를 푼다**
>
> 둘 다 "메모리를 줄인다"로 요약되지만 작동 지점이 다르다. `GCHeapCount`는 **힙(그리고 GC 스레드)의 개수**를 줄여 힙마다 붙는 고정 비용과 예산을 줄인다. `GCConserveMemory`는 **단편화 한도**를 정해 압축을 더 자주 유발한다. 힙이 많아서 메모리를 쓰는 것인지, 단편화 때문에 쓰는 것인지를 먼저 `GC.GetGCMemoryInfo()`의 `FragmentedBytes`로 확인하고 골라야 한다. 둘 다 필요한 경우도 흔하고, .NET 8+라면 DATAS가 두 가지를 함께 다룬다(65.7절).

> **💡 대용량 페이지는 마지막에 시도하라**
>
> 실험적 기능이고, 권한 설정이 필요하고, 힙 하드 리밋을 강제하고, OS 수준에서 다른 프로세스에 영향을 준다. 얻는 것은 TLB 미스와 페이지 폴트 감소인데, 그것이 병목임을 **먼저 측정으로 입증한 경우에만** 값어치가 있다. 대부분의 애플리케이션에서는 65.7절의 DATAS나 65.10절의 배열 풀링이 훨씬 큰 이득을 준다.

### 이 절의 손잡이 요약

| 설정 | 값 | 무엇을 바꾸는가 | 언제 쓰는가 |
|---|---|---|---|
| `GCHighMemPercent` | 0~100(16진수) | 시스템 메모리 부하가 이 비율에 도달하면 GC가 공격적으로 바뀐다. 기본 90%(RAM 80 GB 초과 시 90~97% 사이로 자동 조정) | 프로세스가 메모리를 적게 쓸 때 올린다. 메모리를 크게 쓰는 다른 프로세스와 공존할 때 낮춘다 |
| `GCConserveMemory` | 0~9 | 감내할 단편화 한도 = (10 − 값)/10. gen2 수집마다 평가되며 초과 시 압축한다 | 한 서버에 애플리케이션이 많고 메모리가 병목일 때. LOH 자동 압축을 유도하고 싶을 때 |
| `GCLargePages` | 0/1 | 2 MB 또는 1 GB 페이지 사용. TLB 미스와 페이지 폴트를 줄인다 | 실험적. **힙 하드 리밋과 OS 권한이 선행 조건.** 측정으로 입증된 경우에만 |

## 65.7 DATAS(동적 적응 모드)와 컨테이너 환경 ※.NET 8+

### 문제부터

보수적 모드(`GCConserveMemory`)는 .NET 애플리케이션의 메모리 사용량을 줄이는 좋은 방법이다. 그러나 더 나아갈 방법이 있다. **동적 적응 모드, 줄여서 DATAS(Dynamically Adapting To Application Sizes)** 다. `GCDynamicAdaptationMode` 설정으로 켠다.

DATAS가 풀려는 문제는 서버 GC의 근본 가정에서 나온다. 서버 GC는 **가용 CPU 코어마다 힙 하나**를 만든다. 이 가정은 애플리케이션이 그 머신을 독점할 때 옳다. 그런데 현실은 이렇다.

```text
문제 상황 — 64코어 머신의 작은 서비스 (DATAS 이전)

 요청 없음 (새벽 3시)              피크 (오후 2시)
 ┌──────────────────────────┐    ┌──────────────────────────┐
 │ 힙 64개                  │    │ 힙 64개                  │
 │ 각각 gen0 예산 확보       │    │ 각각 gen0 예산 확보       │
 │ 실제 사용: 거의 없음      │    │ 실제 사용: 꽉 참          │
 │ 메모리: 수백 MB 낭비      │    │ 메모리: 적절             │
 └──────────────────────────┘    └──────────────────────────┘
        ↑ GCHeapCount를 낮게 잡으면          ↑ GCHeapCount를 높게 잡으면
          여기서 처리량이 죽는다               여기서 메모리가 낭비된다
```

`GCHeapCount`로 힙 수를 조정할 수 있지만 **정확한 값을 짐작하는 것은 어렵고**, 게다가 애플리케이션의 워크로드는 하루 중에도 변한다. 피크 부하에 맞춘 값은 유휴 상태에서 과대하고, 그 반대도 마찬가지다. **정적 설정으로는 원리적으로 풀 수 없는 문제다.**

### DATAS가 하는 두 가지

DATAS는 보수적 모드 위에 지어졌다. 그래서 **켜면 `GCConserveMemory`가 자동으로 5로 설정된다**(원한다면 다른 값으로 조정할 수 있다). 그 위에 두 가지 효과가 더해진다.

| 효과 | 무엇을 하는가 | 왜 중요한가 |
|---|---|---|
| **gen0 예산의 동적 조정** | gen0 예산을 **다른 세대의 크기에 따라** 조정한다 | 63.6절에서 본 것처럼 gen0 예산은 원래 **객체 생존율에만** 의존한다. DATAS에서는 프로세스가 메모리를 많이 쓰지 않으면 **생존율이 높아도 gen0을 작게 유지한다.** 총 메모리 사용량이 더 줄어든다 |
| **힙 개수의 동적 조정** | 서버 GC의 힙 개수를 **워크로드에 따라 런타임에 늘리고 줄인다** | 위 문제를 정확히 푼다. 유휴 시에는 힙 하나로 줄었다가 부하가 오면 늘어난다 |

힙 개수 조정에 쓰이는 휴리스틱은 **최근 세 번의 가비지 컬렉션에서 수집한 여러 지표**에 기반한다. 대표적인 두 가지는 다음과 같다.

- **GC에 쓴 시간**
- **할당 락(allocation lock)을 기다리는 데 쓴 시간** — **할당 락은 힙마다 하나씩 있다.** 너무 많은 스레드가 같은 할당 락을 얻으려 경쟁한다면 그것은 **힙 개수를 늘려야 한다는 신호**다.

```text
DATAS의 되먹임 루프

  ┌─────────────────────────────────────────────────────────┐
  │  최근 3회 GC의 지표 수집                                  │
  │   · GC에 쓴 시간                                         │
  │   · 할당 락 대기 시간 (힙당 락 1개)                        │
  └────────────────────────┬────────────────────────────────┘
                           ▼
         ┌─────────────────────────────────────┐
         │ 할당 락 경합이 높다  →  힙 개수 증가  │
         │ GC 시간이 낮고 유휴  →  힙 개수 감소  │
         └─────────────────────────────────────┘
                           ▼
              ┌─────────────────────────┐
              │ 힙 개수 변경 (다음 GC부터)│
              └─────────────────────────┘
```

### 왜 기본값이 되었는가

.NET 8에서 DATAS는 **옵트인**으로 도입됐다. **.NET 9부터는 서버 GC에서 기본으로 켜진다.** ※

이유는 .NET의 배포 형태 변화에 있다. 오늘날 대부분의 .NET 서버 애플리케이션은 **컨테이너 안에서, 여러 인스턴스로, CPU 할당량이 제한된 채** 돈다. 이 환경에서 "코어 수만큼 힙"이라는 기본값은 거의 항상 틀린 값이다.

- 컨테이너의 CPU 할당량은 코어 개수가 아니라 시간 슬라이스 비율이다. 코어 수 감지가 의도한 만큼의 병렬성을 의미하지 않는다.
- 인스턴스를 여러 개 띄우는 것이 표준이 되면서 **인스턴스당 메모리 사용량**이 직접적인 비용이 되었다.
- 워크로드가 하루 안에서도 크게 변한다. 정적 `GCHeapCount`는 두 극단 중 하나에서 손해를 본다.

DATAS는 이 세 가지에 대해 **설정 없이 대응한다.** 실제로 유휴 상태의 메모리 사용량이 크게 줄고, 부하가 오면 처리량을 위해 힙을 늘린다. "설정하지 않아도 합리적인 기본값"이라는 .NET GC의 애플리케이션 중심 철학과도 맞는다.

### 끄는 법

기본값이 되었다는 것은 **일부 워크로드에서는 꺼야 한다**는 뜻이기도 하다.

| 방법 | 설정 |
|---|---|
| `runtimeconfig.json` | `"System.GC.DynamicAdaptationMode": 0` |
| `.csproj` MSBuild 속성 ※ | `<GarbageCollectionAdaptationMode>0</GarbageCollectionAdaptationMode>` |
| 환경 변수 | `DOTNET_GCDynamicAdaptationMode=0` |

켤 때는 같은 자리에 `1`을 준다.

```xml
<PropertyGroup>
  <ServerGarbageCollection>true</ServerGarbageCollection>
  <!-- 처리량이 최우선인 배치 처리 서비스. DATAS를 끈다 -->
  <GarbageCollectionAdaptationMode>0</GarbageCollectionAdaptationMode>
</PropertyGroup>
```

> **⚠️ DATAS는 처리량을 희생해 메모리를 얻는다**
>
> DATAS를 켜면 GC는 힙을 적게 유지하려 하고, `GCConserveMemory=5`가 함께 켜지므로 **압축 수집이 더 자주 일어난다.** 처리량이 절대적으로 중요하고 메모리는 충분한 워크로드 — 전용 머신의 대용량 배치 처리, 인메모리 분석 — 에서는 **.NET 9로 올린 뒤 처리량이 떨어지는 원인**이 될 수 있다. .NET 9 마이그레이션에서 "아무것도 안 바꿨는데 느려졌다"면 DATAS를 먼저 의심하고, 껐다 켜서 비교하라.

> **⚠️ DATAS는 서버 GC 전용이다**
>
> 워크스테이션 GC에는 조정할 힙이 하나뿐이므로 DATAS의 두 번째 효과가 의미가 없다. 워크스테이션 GC에 `GCDynamicAdaptationMode`를 설정해 놓고 메모리가 줄기를 기대하지 마라. 워크스테이션에서 메모리를 줄이고 싶다면 `GCConserveMemory`를 직접 쓴다.

> **📌 `GCMaxHeapCount`**
>
> `GC.GetConfigurationVariables()` 출력에 `MaxHeapCount` 항목이 보인다(65.8절). DATAS가 힙 개수를 늘릴 수 있는 상한이다. `DOTNET_GCMaxHeapCount`로 설정한다. "DATAS는 쓰되 힙이 16개를 넘지는 않게 하라" 같은 요구를 표현할 수 있다.

### 컨테이너 환경에서의 조합

컨테이너 안의 .NET GC 설정은 이 장의 여러 조각이 만나는 지점이다. 자세한 것은 72.8절에서 다루지만, 이 장의 관점에서 요약하면 이렇다.

| 상황 | 권장 |
|---|---|
| CPU 1개짜리 컨테이너 | 서버 GC 설정이 **무시된다.** 워크스테이션 GC가 강제된다. `gcServer`를 켜 놓고 헷갈리지 마라 |
| 메모리 제한만 있는 컨테이너 | GC가 자동 감지해 **총 힙을 제한의 75%로 묶는다.** 네이티브 메모리를 많이 쓴다면 `GCHeapHardLimitPercent`를 낮추고, GC 힙이 대부분이라면 올린다 |
| .NET 8+ 다중 인스턴스 | **DATAS를 켠다**(.NET 9는 기본). `GCHeapCount` 수동 조정보다 거의 항상 낫다 |
| 처리량 우선 전용 컨테이너 | DATAS를 끄고 서버 GC + 백그라운드. 필요하면 `GCHeapCount`를 CPU 할당량에 맞게 고정 |
| 극단적으로 작은 사이드카 | **워크스테이션 비동시**를 검토한다. GC 전용 스레드가 0개다 |

## 65.8 GC API — `GC.Collect`, `GetGCMemoryInfo`, `AddMemoryPressure`, `TryStartNoGCRegion`, `GCSettings`, `GC.KeepAlive`

### 레퍼런스 표

정적 `GC` 클래스는 대부분 런타임 네이티브 구현을 감싸는 얇은 래퍼다. 여기서는 실제로 쓸 일이 있는 것을 기능별로 정리한다. **각 API마다 함정이 있고, 그 함정이 이 표의 존재 이유다.**

| API | 용도 | 도입 | 함정 |
|---|---|---|---|
| `GC.GetConfigurationVariables()` | 현재 GC 구성 값을 키/값 쌍으로 나열 | .NET 6 | 키는 **환경 변수 이름이 아니라 `GCConfig` 내부 필드 이름**이다. 설정 안 한 항목도 기본값으로 출력된다. `GCLOHThreshold`는 이유 불명으로 빠져 있다 |
| `GC.MaxGeneration` | 현재 구현된 세대 수 | 초기 | 값은 **2**다. gen2와 LOH가 전체 GC에서 함께 수집되어 하나로 취급되기 때문이다 |
| `GC.CollectionCount(int)` | 특정 세대의 누적 GC 횟수 | 초기 | **포함적(inclusive)** 이다. gen1이 수집되면 gen0 카운터도 증가한다 |
| `GC.GetGeneration(object)` | 객체가 속한 세대 | 초기 | **유효하지 않은 객체를 넘기면 결과가 정의되지 않는다.** 현재 구현은 `2147483647`을 반환하고, 예전 .NET은 2를 반환했다 |
| `GC.GetTotalMemory(bool)` | 모든 세대에서 사용 중인 총 바이트(**단편화 제외**) | 초기 | `forceFullCollection: true`는 **최악의 경우 전체 블로킹 GC를 20번까지** 트리거한다. 안정된 결과를 얻으려 반복하기 때문이다 |
| `GC.GetTotalAllocatedBytes(bool)` | 프로세스 시작 이후 모든 힙의 누적 할당 바이트 | .NET Core 3.0 | `precise: true`는 **스레드를 중단시킨다.** 성능 영향이 있다 |
| `GC.GetAllocatedBytesForCurrentThread()` | 현재 스레드가 지금까지 할당한 총 바이트 | .NET Core 2.1 / .NET Framework 4.8 | **다른 스레드는 물어볼 수 없다.** 생존 여부와 무관하게 모든 할당을 센다 |
| `GC.GetGCMemoryInfo(GCKind)` | 마지막 GC의 상세 통계 | .NET Core 3.0 (`GCKind`는 .NET 5) | `Index == 0`이면 아직 GC가 없었다는 뜻이고 **다른 필드를 쓰면 안 된다** |
| `GC.GetTotalPauseDuration()` | 프로세스 시작 이후 총 일시 정지 시간(ms) | .NET 8 | 누적값이다. 구간 측정은 두 번 읽어 빼야 한다 |
| `GC.KeepAlive(object)` | 스택 루트의 생존을 해당 줄까지 연장 | 초기 | 아무 일도 하지 않는 메서드처럼 보이지만 **GC Info를 바꾼다**(64.5절) |
| `GC.Collect(...)` | 명시적 수집 | 초기 | Rule 20. 정당한 경우가 극히 드물다 |
| `GC.AddMemoryPressure(long)` / `RemoveMemoryPressure(long)` | 비관리 메모리 압력을 GC에 알림 | 초기 | **짝을 맞추지 않으면 GC 튜닝이 영구히 왜곡된다** |
| `GC.TryStartNoGCRegion(...)` / `EndNoGCRegion()` | GC 없는 영역 | .NET Framework 4.6 | 65.4절의 예외 조건 전부 |
| `GC.RegisterNoGCRegionCallback(long, Action)` | no GC 영역의 할당량 도달 콜백 | .NET 8 | no GC 영역 안에서만 의미가 있다 |
| `GC.RefreshMemoryLimit()` | 힙 하드 리밋을 런타임에 재적용 | .NET 8 | **런타임을 중단시켰다가 재개한다.** 값은 반드시 `ulong` |
| `GC.ReRegisterForFinalize` / `SuppressFinalize` / `WaitForPendingFinalizers` | 파이널라이제이션 제어 | 초기 | 34장 참조 |
| `GC.RegisterForFullGCNotification(int, int)` 외 | GC 알림 | 초기 | 65.9절 참조. **블로킹 GC만 알림을 낸다** |
| `GCSettings.IsServerGC` | 서버 GC 여부 | 초기 | **읽기 전용.** 런타임 시작 후에는 GC 모드를 바꿀 수 없다 |
| `GCSettings.LatencyMode` | 지연 시간 모드 | 초기 | 65.4절. **런타임에 바꿀 수 있는 유일한 GC 모드 축** |
| `GCSettings.LargeObjectHeapCompactionMode` | 다음 블로킹 전체 GC에서 LOH 압축 | .NET Framework 4.5.1 | `CompactOnce`는 **한 번만** 적용된다. 대단히 비싸다 |
| `MemoryFailPoint` | 처리 시작 전 메모리 가용성 확인 | .NET Framework 2.0 | **Windows 런타임만 실제로 구현한다.** 다른 OS에서는 생성자가 항상 성공한다 |
| `GC._RegisterFrozenSegment` / `_UnregisterFrozenSegment` | NonGC 힙(고정 세그먼트) 등록 | — | `private`이고 리플렉션으로만 호출된다. **쓰지 마라** |

### 구성 확인 — `GC.GetConfigurationVariables`

프로덕션에서 "이 프로세스가 실제로 어떤 GC 설정으로 떠 있는가"를 확인하는 가장 직접적인 방법이다. 구성 파일을 보는 것으로는 100% 확신할 수 없다. 파일 기반 설정은 환경 변수나 레지스트리로 덮어써질 수 있고, 파일에 오타가 있을 수도 있다. **확실히 아는 유일한 방법은 .NET 프로세스 자신에게 물어보는 것이다.**

```csharp
foreach (var pair in GC.GetConfigurationVariables())
    Console.WriteLine($"{pair.Key} = {pair.Value}");
```

.NET 8 기준 출력은 다음과 같다.

```text

ConcurrentGC = True
RetainVM = False
NoAffinitize = False
GCCpuGroup = False
GCLargePages = False
HeapCount = 8
MaxHeapCount = 0
GCHeapAffinitizeMask = 0
GCHeapAffinitizeRanges =
GCHighMemPercent = 0
GCHeapHardLimit = 0
GCHeapHardLimitPercent = 0
GCHeapHardLimitSOH = 0
GCHeapHardLimitLOH = 0
GCHeapHardLimitPOH = 0
GCHeapHardLimitSOHPercent = 0

GCHeapHardLimitPOHPercent = 0

```

키의 정체는 `gcconfig.h` 파일에 있다.

```text
#define GC_CONFIGURATION_KEYS \
BOOL_CONFIG (ServerGC,     "gcServer",     "System.GC.Server",     false, "Whether we should be using Server GC")  \
BOOL_CONFIG (ConcurrentGC, "gcConcurrent", "System.GC.Concurrent", true,  "Whether we should be using Concurrent GC")  \
```

| 열 | 의미 |
|---|---|
| 1 | **키** — 이 메서드가 반환하는 이름 |
| 2 | 환경 변수 이름의 뒷부분(`DOTNET_` 접두사가 붙는다) |
| 3 | 런타임 설정에서 쓸 수 있는 GC 속성 이름 |
| 4 | 기본값 |
| 5 | 의미와 사용법 설명 |

> **⚠️ 반환된 키를 그대로 환경 변수 이름으로 쓰면 안 된다**
>
> 반환되는 키는 **`GCConfig` 클래스의 내부 필드 이름**이지 환경 변수 이름이 아니다. `ServerGC`가 키지만 환경 변수는 `DOTNET_gcServer`다. 매핑은 `gcconfig.h`의 두 번째 열에 있다. 그리고 **대응하는 GC 속성이 있는 구성 변수만 이 메서드가 나열한다** — `GCLOHThreshold`는 이유가 분명하지 않지만 빠져 있다.

> **📌 ETW 이벤트로 확인하는 대안**
>
> 프로세스에 코드를 넣지 않고 확인하려면 ETW/EventPipe를 쓴다. ETW/EventPipe 세션이 시작하고 끝날 때마다 .NET 런타임은 진단 도구용 추가 이벤트를 보낸다. `Microsoft-Windows-DotNETRuntimeRundown/Runtime/Start` 이벤트를 보면 된다. 런타임이 시작할 때뿐 아니라 **세션이 시작하고 끝날 때도** 발행되므로, 짧은 세션 하나만 열었다 닫으면 된다.
>
> ```text
> dotnet trace collect --providers Microsoft-Windows-DotNETRuntimeRundown:0x80000000001:5 -p <pid>
> ```
>
> 관심 있는 것은 `StartupFlags` 필드다.
>
> | 플래그 | 값 | 의미 |
> |---|---|---|
> | `CONCURRENT_GC` | `0x000001` | 동시 GC로 시작했다. 이 값이 없으면 비동시 GC다 |
> | `SERVER_GC` | `0x001000` | 서버 GC로 시작했다. 이 값이 없으면 워크스테이션 GC다 |
> | `HOARD_GC_VM` | `0x002000` | VM 유지(hoarding)가 켜져 있다 |
>
> 값들은 조합된다. 백그라운드 서버 GC는 `CONCURRENT_GC`와 `SERVER_GC`가 모두 나열되고, **비동시 워크스테이션 GC는 아무것도 나열되지 않는다.** IIS에 호스팅된 ASP.NET 웹 애플리케이션은 `StartupFlags`가 208919(16진수 33017)로 나오며 `CONCURRENT_GC`, `LOADER_OPTIMIZATION_SINGLE_DOMAIN`, `LOADER_OPTIMIZATION_MULTI_DOMAIN`, `LOADER_SAFEMODE`, `SERVER_GC`, `HOARD_GC_VM`, `LEGACY_IMPERSONATION`, `DISABLE_COMMITTHREADSTACK`에 해당한다.

가장 간단한 시작 시 진단 로그는 이런 형태가 된다.

```csharp
Console.WriteLine("{0} on {1}-bit with {2} CPUs",
                  (GCSettings.IsServerGC ? "Server" : "Workstation"),
                  ((IntPtr.Size == 8) ? 64 : 32),
                  Environment.ProcessorCount);
```

> **💡 시작 로그에 GC 설정을 남겨라**
>
> 이 세 줄은 비용이 사실상 0이고, 나중에 "이 인시던트 때 이 프로세스가 어떤 GC로 떠 있었나"에 답해 준다. 여기에 `GCSettings.LatencyMode`와 `GC.GetConfigurationVariables()`에서 `HeapCount`, `GCHeapHardLimit`, `GCDynamicAdaptationMode` 정도를 덧붙이면 충분하다. 컨테이너 환경이라면 특히 값어치가 크다.

### 통계 — `CollectionCount`, `GetTotalMemory`, 할당량

`GC.CollectionCount`가 **포함적**이라는 사실은 직접 확인하는 편이 빠르다.

```csharp
GC.Collect(0);
Console.WriteLine($"{GC.CollectionCount(0)} {GC.CollectionCount(1)} {GC.CollectionCount(2)}");
GC.Collect(1);
Console.WriteLine($"{GC.CollectionCount(0)} {GC.CollectionCount(1)} {GC.CollectionCount(2)}");
GC.Collect(2);
Console.WriteLine($"{GC.CollectionCount(0)} {GC.CollectionCount(1)} {GC.CollectionCount(2)}");
```

```text
1 0 0
2 1 0
3 2 1
```

각 어린 세대의 수집 카운터가 더 오래된 세대의 수집을 포함한다. 이 메서드의 가장 흔한 용도는 **"자동으로 일어나지 않았을 때만" 명시적 GC를 호출하는** 패턴이다.

```csharp
if (lastGen2CollectionCount == GC.CollectionCount(2))
{
    GC.Collect(2);
}
lastGen2CollectionCount = GC.CollectionCount(2);
```

각 세대 카운터를 주기적으로 확인해 새 수집을 감지하는 데 쓸 수도 있다. 확인 주기가 충분히 촘촘하면 "매 GC 후 실행되는 콜백" 비슷한 것을 만들 수 있다.

`GC.GetTotalMemory`는 **모든 세대에서 사용 중인 총 바이트 수를 단편화를 제외하고** 반환한다. 다시 말해 관리 힙 위 모든 관리 객체의 총 크기다. **명시적 GC를 먼저 트리거하지 않으면 이미 도달 불가능한 죽은 객체의 크기도 포함된다.**

```csharp
static void Main(string[] args)
{
    Console.WriteLine("Hello world!");

    var process = Process.GetCurrentProcess();
    Console.WriteLine($"{process.PrivateMemorySize64:N0}");
    Console.WriteLine($"{process.WorkingSet64:N0}");
    Console.WriteLine($"{process.VirtualMemorySize64:N0}");
    Console.WriteLine($"{GC.GetTotalMemory(true):N0}");
    Console.ReadLine();
}
```

```text
Hello world!
11,165,696
28,766,208
2,480,842,821,632
87,688
```

> **⚠️ `GetTotalMemory`로 메모리 기반 제어를 하지 마라**
>
> 위 출력을 보라. GC 힙의 객체는 **약 87 kB**인데 프로세스 개인 메모리는 **약 11 MB**다. `GetTotalMemory`는 단편화와 세그먼트/리전 관리의 전체 오버헤드(예: 세그먼트 페이지의 사전 커밋)를 세지 않으므로 **메모리에 대한 전체 압력을 정확히 반영하지 못한다.** "메모리 사용량이 임계값을 넘으면 웹 요청을 스로틀링" 같은 용도로 쓰면 안 된다. 그런 시나리오에는 `Process` 클래스의 전체 메모리 측정값(`WorkingSet64`, `PrivateMemorySize64`)을 쓰는 편이 낫다.
>
> 반대로 **누수를 알아채는 데는 훌륭하다.** 관리 힙 위 도달 가능한 객체가 계속 늘어나는 것이 그대로 보인다.

할당량을 측정할 때는 목적에 따라 메서드가 다르다.

| 측정 대상 | 메서드 | 특징 |
|---|---|---|
| 프로세스 전체 누적 할당 | `GC.GetTotalAllocatedBytes(precise)` | .NET Core 3.0+. `precise: true`는 각 스레드의 미사용 할당 컨텍스트를 빼서 더 정확하지만 **스레드를 중단시킨다** |
| 현재 스레드 누적 할당 | `GC.GetAllocatedBytesForCurrentThread()` | 구현이 빠르고 직관적이다. 이전 할당 컨텍스트에서 할당한 바이트 합 + 현재 할당 컨텍스트의 이미 소비한 부분 |
| AppDomain 누적 할당 (.NET Framework 전용) | `AppDomain.MonitoringTotalAllocatedMemorySize` | 할당 컨텍스트가 바뀔 때마다 갱신되므로 **몇 kB 수준의 세분성**만 있다. AppDomain 리소스 모니터링을 켜야 한다 |
| 마지막 GC 생존 바이트 (.NET Framework 전용) | `AppDomain.MonitoringSurvivedMemorySize` | **전체 GC 후에만 정확이 보장된다** |

단위 테스트에서 "이 코드가 할당을 하지 않는다"를 검증하는 표준 패턴은 이렇다.

```csharp
[Fact]
public void SampleTest()
{
    string input = "Hello world!";
    var startAllocations = GC.GetAllocatedBytesForCurrentThread();

    ReadOnlySpan<char> span = input.AsSpan().Slice(0, 5);

    var endAllocations = GC.GetAllocatedBytesForCurrentThread();
    Assert.Equal(startAllocations, endAllocations);
    Assert.Equal("Hello", span.ToString());
}
```

> **⚠️ 할당 측정에 `GetTotalMemory`를 쓰지 마라**
>
> 흔한 실수다. `GetTotalMemory`는 **누적 할당량이 아니라 현재 총 메모리 사용량**을 잰다. 테스트 도중 GC가 한 번 돌면 값이 줄어든다. 스레드 격리 덕분에 깨끗하고 재현 가능한 결과를 주는 `GetAllocatedBytesForCurrentThread`가 정답이다. BenchmarkDotNet의 `MemoryDiagnoser`가 정확히 이 문제를 다루며, 실행 환경에 따라 가장 정밀한 방법을 골라 쓴다.

### `GC.GetGCMemoryInfo` — 마지막 GC의 해부

앞의 메서드들에 빠져 있는 것은 **트리거되거나 유도된 GC가 얼마나 효율적이었는지**를 이해할 방법이다. GC는 각 GC 전후로 단편화 바이트, 승격 바이트, 일시 정지 시간 같은 많은 통계를 추적한다. **.NET Core 3.0부터 `GC.GetGCMemoryInfo`가 이 상세 정보에 접근하는 선호 방법이다.** .NET 5부터는 `GCKind` 열거형 매개변수로 마지막 ephemeral GC(gen0 또는 gen1), 전체 블로킹 GC(블로킹 gen2), 백그라운드 GC(항상 gen2) 중 어느 것의 상세를 원하는지 지정할 수 있다.

```csharp
GC.Collect(2, GCCollectionMode.Aggressive);
GCMemoryInfo info = GC.GetGCMemoryInfo(GCKind.Any);

if (info.Index != 0)
{
    Console.Write($"#{info.Index} is gen{info.Generation}");
    if (info.Compacted) Console.Write(" compacting");
    if (info.Concurrent) Console.Write(" concurrent");
    Console.WriteLine();

    Console.WriteLine($"High Mem threshold = {info.HighMemoryLoadThresholdBytes}");
    Console.WriteLine($"High Mem load      = {info.MemoryLoadBytes}");
    Console.WriteLine($"Heap Size bytes    = {info.HeapSizeBytes}");
    Console.WriteLine($"Promoted bytes     = {info.PromotedBytes}");
    Console.WriteLine($"Fragmented bytes   = {info.FragmentedBytes}");
    Console.WriteLine($"Committed bytes    = {info.TotalCommittedBytes}");
    Console.WriteLine($"Total Avail. bytes = {info.TotalAvailableMemoryBytes}");
    Console.WriteLine($"Pinned obj count   = {info.PinnedObjectsCount}");
    Console.WriteLine($"Finalization pend  = {info.FinalizationPendingCount}");
    Console.WriteLine($"Pause time %       = {info.PauseTimePercentage}");

    foreach (var pause in info.PauseDurations)
    {
        if (pause.TotalNanoseconds > 0)   // 일시 정지가 없는 단계는 표시하지 않는다
            Console.WriteLine($"  {pause.TotalMicroseconds} micro seconds");
    }

    for (int gen = 0; gen < info.GenerationInfo.Length; gen++)
    {
        var genInfo = info.GenerationInfo[gen];
        if (gen == 4)      Console.WriteLine("POH");
        else if (gen == 3) Console.WriteLine("LOH");
        else               Console.WriteLine($"Gen {gen}");

        Console.WriteLine($"   Fragmentation before = {genInfo.FragmentationBeforeBytes}");
        Console.WriteLine($"   Fragmentation after  = {genInfo.FragmentationAfterBytes}");
        Console.WriteLine($"            Size before = {genInfo.SizeBeforeBytes}");
        Console.WriteLine($"            Size after  = {genInfo.SizeAfterBytes}");
    }
}
```

| 필드 | 의미 | 주의 |
|---|---|---|
| `Index` | GC 일련번호 | **0이면 아직 GC가 없었다는 뜻이고 나머지 필드를 쓰면 안 된다** |
| `Generation` | 수집된 세대 | 0, 1, 2 중 하나 |
| `Compacted` / `Concurrent` | 압축했는지 / 동시였는지 | 백그라운드 GC 여부 판별에 쓴다 |
| `HeapSizeBytes` / `FragmentedBytes` | 힙 크기 / 단편화 바이트 | `GetTotalMemory`와 달리 **단편화를 볼 수 있다** |
| `PromotedBytes` | 승격 바이트 | 중년기 위기 진단의 핵심 수치(64장 Rule 18) |
| `TotalCommittedBytes` | 커밋된 총 바이트 | |
| `HighMemoryLoadThresholdBytes` / `MemoryLoadBytes` | 고메모리 임계값 / 현재 부하 | 65.6절 `GCHighMemPercent`의 실효값을 여기서 확인한다 |
| `PinnedObjectsCount` | 고정 객체 수 | 64.7절 |
| `PauseDurations` | 각 STW 구간의 지속 시간 | **항상 원소가 2개다.** 블로킹 GC는 1개만 유효하고 백그라운드 GC는 2개가 유효하다. **0 나노초인 것을 무시해야 한다** |
| `GenerationInfo[]` | 세대별 전후 크기·단편화 | 인덱스 **0~2가 gen0~2, 3이 LOH, 4가 POH**다. `Generation` 필드(0~2)와 인덱스 체계가 **다르다** |

> **⚠️ `PauseDurations`와 PerfView의 `Pause MSec`는 다른 값이다**
>
> PerfView GCStats의 `Pause MSec` 열은 **병합된 하나의 값**이다. 반면 `PauseDurations`는 애플리케이션 스레드가 중단된 **각 단계의 지속 시간**을 준다 — 블로킹 GC는 한 번, 백그라운드 GC는 두 번. 백그라운드 GC의 "일시 정지"를 하나의 숫자로 보고하면 실제 사용자 경험을 왜곡한다. **두 개의 짧은 정지가 하나의 긴 정지와 같지 않다.**

> **⚠️ `GenerationInfo` 인덱스와 `Generation` 필드를 헷갈리지 마라**
>
> `GCMemoryInfo.Generation`은 0, 1, 2 중 하나다(수집된 세대). `GenerationInfo` 배열의 인덱스는 0~4이며 3이 LOH, 4가 POH다. **두 체계가 다르다.** `info.GenerationInfo[info.Generation]`은 대개 의도한 것을 주지만, LOH나 POH를 보려면 인덱스를 직접 써야 한다.

.NET 8은 `GCMemoryInfo.PauseTimePercentage` 속성에 좋은 보완을 추가했다. **`GC.GetTotalPauseDuration()`** 은 프로세스 시작 이후의 **총 일시 정지 시간을 밀리초로** 준다. 두 시점에서 읽어 빼면 구간 일시 정지 총합을 얻는다.

```csharp
var before = GC.GetTotalPauseDuration();
DoWork();
var after = GC.GetTotalPauseDuration();
Console.WriteLine($"이 구간의 GC 일시 정지 합계: {(after - before).TotalMilliseconds:F2} ms");
```

### `AddMemoryPressure` / `RemoveMemoryPressure`

GC는 **관리 메모리만 본다.** 관리 객체 하나가 뒤에 거대한 비관리 메모리를 붙들고 있어도 GC 입장에서 그 객체는 그냥 작은 객체다. 결과적으로 **런타임이 자기 메모리 사용량에 대해 비현실적으로 낙관적인 인식**을 갖게 된다.

```csharp
public sealed class NativeImage : IDisposable
{
    private IntPtr _handle;
    private readonly long _nativeBytes;

    public NativeImage(string path)
    {
        _handle = NativeMethods.LoadImage(path, out _nativeBytes);

        // GC에게 "이 작은 객체 뒤에 이만큼의 비관리 메모리가 있다"고 알린다
        GC.AddMemoryPressure(_nativeBytes);
    }

    public void Dispose()
    {
        if (_handle != IntPtr.Zero)
        {
            NativeMethods.FreeImage(_handle);
            _handle = IntPtr.Zero;

            // 반드시 짝을 맞춘다
            GC.RemoveMemoryPressure(_nativeBytes);
        }
        GC.SuppressFinalize(this);
    }
}
```

동작 원리는 단순하다. **마지막 GC 이후의 순 메모리 압력(추가분 − 제거분)이 예산과 비교되어 GC를 트리거한다.** 이 예산은 **4 MB에서 시작하고**, 최근 세 번의 GC에 걸친 추가/제거된 메모리 압력과 현재 관리 힙 크기에 기반해 동적으로 조정된다.

**언제 필요한가.**

| 상황 | 필요한가 |
|---|---|
| 작은 관리 래퍼가 큰 비관리 버퍼(이미지, 오디오, GPU 리소스, 네이티브 모델)를 소유 | **필요하다.** 이것이 전형적 사례다 |
| 관리 객체가 비관리 메모리를 소유하지만 `Dispose`가 즉시 호출되는 것이 보장됨 | 대개 불필요하다. 압력을 알릴 이유는 GC가 그 객체를 **회수하도록 유도**하기 위해서다 |
| `SafeHandle`로 감싼 OS 핸들(파일, 소켓) | 대개 불필요하다. 메모리가 아니라 핸들이 자원이다 |
| 비관리 메모리 크기가 수십 kB 수준 | 불필요하다. 예산이 4 MB에서 시작하므로 노이즈가 된다 |
| 전체 크기를 미리 알 수 없는 경우 | **주의.** 잘못된 값이 잘못된 GC 리듬을 만든다 |

> **⚠️ 짝을 맞추지 않으면 GC 튜닝이 영구히 왜곡된다**
>
> `AddMemoryPressure`를 호출하고 `RemoveMemoryPressure`를 하지 않으면, GC는 존재하지 않는 비관리 메모리가 계속 있다고 믿는다. 결과는 **불필요하게 잦은 전체 GC**다. 파이널라이저 경로와 `Dispose` 경로 **양쪽에서** 제거가 일어나되 **두 번 제거되지는 않도록** 해야 한다. 위 예제처럼 `_handle`을 확인해 한 번만 실행되게 하는 것이 안전한 형태다.
>
> 반대로 `RemoveMemoryPressure`를 추가한 것보다 많이 호출하면 그것도 문제다. 값이 정확히 대칭이어야 한다.

> **💡 기본 구현이 안 맞으면 직접 만들어도 된다**
>
> 이 메커니즘의 동작이 자기 워크로드에 잘 맞지 않는다면, 비슷한 메커니즘을 직접 구현해도 된다 — 자기 회계 장부를 유지하다가 임계값을 넘으면 `GC.Collect`를 호출하는 식이다. 다만 Rule 20을 기억하라. 명시적 GC가 정당한 드문 경우 중 하나가 되려면 **측정으로 뒷받침되어야** 한다.

### 명시적 수집과 `GC.Collect` 오버로드

64장의 Rule 20에서 다뤘듯 명시적 GC는 대개 나쁜 생각이다. 완전성을 위해 오버로드를 나열한다.

```csharp
GC.Collect();
GC.Collect(int generation);
GC.Collect(int generation, GCCollectionMode mode);
GC.Collect(int generation, GCCollectionMode mode, bool blocking);
GC.Collect(int generation, GCCollectionMode mode, bool blocking, bool compacting);
```

정당한 경우가 아주 없지는 않다. 대표적인 것은 **애플리케이션이 한동안 잠드는 경우**다. 하루에 한 번 활동하는 Windows 서비스(업데이트 확인 등)를 생각해 보자. `System.Timers.Timer`로 24시간마다 활동을 시작한다. 활동이 끝나면 24시간 동안 아무 코드도 실행되지 않으므로 **메모리 할당이 전혀 없고 GC가 활성화될 기회가 없다.** 객체 그래프가 비어 있는데도 활동 중 소비한 메모리를 그대로 24시간 동안 붙들고 있게 된다. 이 경우 활동 직후 `GC.Collect`를 호출하는 것이 해법이다.

파이널라이저 때문에 수집이 지연되는 객체까지 확실히 수집하려면 한 단계를 더 넣는다.

```csharp
GC.Collect();
GC.WaitForPendingFinalizers();
GC.Collect();
```

파이널라이저를 실행하는 행위 자체가 파이널라이저를 가진 다른 객체를 해방할 수 있으므로 종종 루프로 감싼다. **파이널라이저를 가진 클래스를 테스트할 때**도 이 패턴이 필요하다(34장).

### 메모리 리밋을 런타임에 바꾸기 ※.NET 8

65.5절의 힙 하드 리밋은 **.NET 8부터 런타임에 조정할 수 있다.** 두 가지 용도가 있다.

1. **환경이 .NET 런타임이 이해하지 못하는 방식으로 제한을 지시할 때.** 예를 들어 AWS Lambda 실행 환경은 `AWS_LAMBDA_FUNCTION_MEMORY_SIZE` 환경 변수로 제한을 준다. 애플리케이션 시작 시 그 값을 읽어 .NET 런타임에 번역해 줄 수 있다.
2. **하루 중 메모리 제한을 조정하고 싶을 때.** 특정 시간대에 다른 프로그램에 메모리를 더 남겨 주기 위해 낮추는 식이다.

조정 가능한 리밋은 `GCHeapHardLimit`, `GCHeapHardLimitPercent`, `GCHeapHardLimitSOH`/`LOH`/`POH`, 그리고 그 `Percent` 변형들이다. 방법은 `AppContext`에 새 값을 설정한 뒤 `GC.RefreshMemoryLimit()`으로 GC에 변경을 알리는 것이다.

```csharp
AppContext.SetData("GCHeapHardLimitPercent", 50UL);
GC.RefreshMemoryLimit();
```

> **⚠️ `ulong`이 아니면 조용히 무시된다**
>
> 위 코드의 `50UL`에서 `UL` 접미사를 놓치지 마라. **값은 반드시 `ulong`으로 제공해야 한다.** 다른 데이터 타입을 쓰면 값이 **조용히 무시된다.** 예외도, 경고도 없다. `AppContext.SetData("GCHeapHardLimitPercent", 50)`은 `int`를 넘기므로 아무 일도 하지 않는다.

> **⚠️ `RefreshMemoryLimit`은 런타임을 중단시킨다**
>
> 이 메서드는 GC 상태를 갱신하는 동안 **런타임을 중단시켰다가 이후 재개한다.** 애플리케이션에 예상치 못한 영향을 준다. 요청 처리 도중 주기적으로 호출할 성질의 것이 아니다.
>
> 오류 처리도 일관되지 않다. **너무 낮은 리밋을 설정하면 `InvalidOperationException`이 던져진다.** 대부분의 잘못된 리밋 조합도 예외를 낸다(예: SOH·LOH·POH 비율 합이 100%를 넘는 경우). **그러나 잘못된 `GCHeapHardLimitPercent` 값은 조용히 무시된다.** 설정 후 `GC.GetConfigurationVariables()`로 실제 반영 여부를 확인하는 습관이 필요하다.

### `MemoryFailPoint` — 처리 전 메모리 확보 확인

`OutOfMemoryException` 처리는 성가시다. 중요한 처리 한복판에서 터지면 특히 그렇다. 그런 상황을 사전에 피하기 위해 `MemoryFailPoint` 클래스로 **중요한 처리를 시작하기 전에 충분한 메모리가 있는지 보장을 시도**할 수 있다.

```csharp
try
{
    using (MemoryFailPoint failPoint = new MemoryFailPoint(sizeInMegabytes: 1024))
    {
        // 계산 수행
    }
}
catch (InsufficientMemoryException e)
{
    Console.WriteLine(e);
    throw;
}
```

생성자는 요구한 것보다 가용 메모리가 적으면 **`InsufficientMemoryException`** 을 던진다. 다중 스레드 사용을 위한 내부 기록 때문에 **`IDisposable`이므로 `using`으로 감싸야 한다.**

Windows 구현에서 이 클래스가 검사하는 단계는 다음과 같다.

1. 일반적으로 충분한 가상 주소 공간이 있는지 — 64비트 프로그램이면 거대한 주소 공간 덕에 항상 참이어야 한다.
2. **전체·블로킹·압축 GC를 명시적으로 호출**해 미사용 세그먼트를 해방하고 관리 메모리 사용을 최대한 압축한다.
3. 충분한 여유 가상 메모리가 있는지.
4. 요구한 메모리 크기를 수용하기 위해 OS 페이지 파일을 키워야 하는지.
5. 필요하다면 GC 세그먼트를 만들 만한 연속된 여유 가상 메모리가 있는지.

> **⚠️ `MemoryFailPoint`는 Windows에서만 실제로 동작한다**
>
> 현재 **Windows 기반 런타임만 이 클래스의 기능을 구현한다.** 다른 시스템에서는 **`MemoryFailPoint` 생성자가 항상 성공한다.** 리눅스 컨테이너에서 이 클래스로 OOM을 막고 있다고 믿는다면 아무것도 막고 있지 않은 것이다.
>
> 그리고 Windows에서도 **보장은 없다.** 이 API로도 `OutOfMemoryException`이 나지 않는다는 보장은 없다. 최선의 노력일 뿐이다. 게다가 2단계에서 **전체 블로킹 압축 GC를 유발**하므로 그 자체로 비싸다.

### 고정 세그먼트 API — 알고만 있어라

완전성을 위해 언급하는, **쓰면 안 되는** API가 하나 있다.

```csharp
IntPtr GC._RegisterFrozenSegment(IntPtr sectionAddress, nint sectionSize);
void   GC._UnregisterFrozenSegment(IntPtr segmentHandle);
```

이것은 62.5절에서 **NonGC 힙(NGCH)** 이라는 이름으로 다룬 개념이다. 임의의 네이티브 메모리 덩어리를 NGCH의 일부로 등록해 **관리 객체를 비관리 메모리에 저장**할 수 있게 한다. NGCH는 GC가 무시한다. 그 힙의 객체는 GC 중 스캔되지 않으므로 **나가는 참조가 루트 역할을 하지 않고**, GC가 참조되지 않는 고정 객체를 해방하지도 않는다. 그 메모리 관리는 전적으로 자기 책임이다.

왜 이런 것이 필요한가. 수 GB의 정적 데이터(캐시나 머신러닝 모델)가 있고, 한 번에 로드되며 구조체로 저장할 수 없는(대개 데이터의 다른 부분을 가리키는 포인터를 담기 때문) 경우, 일반 관리 힙에 로드하면 두 가지가 성능을 해친다.

1. **gen2에 직접 할당하는 API가 없다.** 데이터 일부가 LOH에 갈 수 있어도(배열) 대부분은 gen0에 할당된다. 오래 사는 데이터이므로 GC가 수 GB를 gen1로, 다시 gen2로 옮기게 되고 상당한 오버헤드가 된다.
2. **gen2로 승격된 뒤에도 끝이 아니다.** 전체 압축 GC마다 그 수 GB를 다시 스캔해야 한다. 데이터가 바뀌지 않으므로 자원 낭비다.

> **⚠️ 이 API는 `private`이고 리플렉션으로만 호출할 수 있다**
>
> 이 API들은 외부 소비를 의도했지만 `private`으로 선언되어 있고 리플렉션을 통해 호출해야 한다. **이것은 실험적 상태를 반영하며, 무엇을 하는지 모르는 사람이 쓰지 못하게 하는 문지기 장치다.**
>
> .NET은 자동 메모리 관리를 위해 설계되었다. 임의 위치에 참조 객체를 할당하는 편의 시설이 없으므로 **전부 수동으로 해야 한다.** .NET 타입 시스템에 대한 강한 이해가 필요하고 깊은 unsafe 세계로 들어가게 된다. 객체 하나를 할당한 뒤 다음 객체를 할당하려면 그 타입 인스턴스의 메모리 크기를 알아야 하고, 그것은 MethodTable을 파싱한다는 뜻이다. 배열·문자열·복잡한 타입을 쓰려면 그 메모리 레이아웃을 완벽히 알아야 한다. **하지 마라.**

## 65.9 GC 알림과 프로그래밍적 제어

### 왜 이런 것이 있었나

GC API의 한 부분은 **전체 블로킹 GC가 다가오고 있음을 통지받는 것**과 관련이 있다. 이 필요는 주로 .NET 4.5 이전 시대에서 왔다. 그때 서버 GC에는 비동시 블로킹 버전밖에 없었다. 그런 GC는 꽤 오래 걸릴 수 있었으므로 **미리 예측할 수 있다는 것이 상당히 유용했다.**

전형적인 예는 **로드 밸런서에게 이 서버 인스턴스를 다가오는 전체 블로킹 GC가 끝날 때까지 사용 불가로 만들라고 알리는 것**이다.

```text
        전체 블로킹 GC 알림 기반 서버 팜 패턴

  요청 ─────▶ [로드 밸런서] ─────▶ [서버 A]  ← WaitForFullGCApproach 성공
                    │                  │
                    │                  ├── 1. LB에서 자신을 제외
                    │                  ├── 2. GC.Collect()로 즉시 수집
                    │                  ├── 3. WaitForFullGCComplete 대기
                    │                  └── 4. LB에 자신을 복귀
                    │
                    └──────────▶ [서버 B]  ← 그동안 요청을 받는다
```

### API

| 메서드 | 역할 |
|---|---|
| `GC.RegisterForFullGCNotification(int maxGenerationThreshold, int largeObjectHeapThreshold)` | 조건이 충족되면 발생할 GC 알림을 등록한다. 조건은 **gen2 또는 LOH 할당 예산 사용률**에 기반한다 — GC를 트리거할 수 있는 할당 이후 남은 공간의 비율 |
| `GC.CancelFullGCNotification()` | 알림 메커니즘을 취소한다 |
| `GC.WaitForFullGCApproach()` | GC 알림을 무기한 기다리는 **블로킹 호출**. 타임아웃을 지정하는 오버로드도 있다 |
| `GC.WaitForFullGCComplete()` | 전체 GC 완료를 무기한 기다리는 **블로킹 호출**. 역시 타임아웃 오버로드가 있다 |

```csharp
GC.RegisterForFullGCNotification(10, 10);

Thread startPolling = new Thread(() =>
{
    while (true)
    {
        GCNotificationStatus s = GC.WaitForFullGCApproach(1000);
        if (s == GCNotificationStatus.Succeeded)
        {
            Console.WriteLine("GC is about to begin");
        }
        else if (s == GCNotificationStatus.Timeout)
        {
            continue;
        }

        // ...
        // 전체 GC에 반응한다. 예를 들어 로드 밸런서에서 현재 서버를 제외하는 코드를 호출한다
        // ...

        s = GC.WaitForFullGCComplete(10_000);
        if (s == GCNotificationStatus.Succeeded)
        {
            Console.WriteLine("GC has ended");
        }
        else if (s == GCNotificationStatus.Timeout)
        {
            Console.WriteLine("GC took alarming amount of time");
        }
    }
});
startPolling.Start();

GC.CancelFullGCNotification();
```

> **⚠️ 백그라운드 GC에서는 알림이 오지 않는다**
>
> **오직 블로킹 가비지 컬렉션만 이 알림을 발생시킨다.** 동시 설정이 켜져 있으면 백그라운드 가비지 컬렉션은 알림되지 않는다. 오늘날 대부분의 웹 애플리케이션이 백그라운드 GC 모드로 돌고 일시 정지가 훨씬 덜 눈에 띄므로, **GC 알림은 중요성을 많이 잃었다.** 이 API를 새로 도입하려 한다면 먼저 자신에게 물어야 한다 — 정말 비동시 모드로 돌고 있는가?

> **⚠️ 임계값은 추측해야 하고, API는 설계상 부정확하다**
>
> Microsoft 문서의 표현으로 "알림은 전체 가비지 컬렉션이 일어날 것을 보장하지 않는다. 조건이 전체 가비지 컬렉션에 유리한 임계값에 도달했다는 것만 보장한다".
>
> - **값이 너무 높으면** 실제 GC 전에 트리거되지 않는 거짓 양성 알림을 많이 받는다.
> - **값이 너무 낮으면** 실제로 일어난 GC를 놓칠 수 있다.
>
> 이 API는 **미래를 예측해 달라고 GC에게 요구하는 것**이므로 설계상 정확할 수 없다. 자기 워크로드에 맞는 인자 값을 찾으려면 실험이 필요하다. 실제 애플리케이션의 워크로드는 계속 변하므로 정확한 예측은 어렵다. 언급한 임계값으로 미세 조정하는 것은 최소한 **자기의 전형적 워크로드에 적응**하게 해 준다.

> **💡 오늘날 이 API가 여전히 값어치 있는 곳**
>
> 세 가지 조건이 모두 맞을 때다. (1) 비동시 서버 GC를 의도적으로 쓰고 있고, (2) 요청을 다른 인스턴스로 넘길 수 있는 구조이며, (3) 전체 GC 일시 정지가 SLA를 실제로 위반한다. 셋 중 하나라도 아니면 **백그라운드 GC로 바꾸는 것이 거의 항상 더 나은 답**이다. GC 알림 스레드 하나를 상시 돌리는 비용이 공짜가 아니라는 점도 계산에 넣어라.

### 지금까지 나온 프로세스 내부 모니터링 수단 정리

프로세스 안에서 자기 메모리 사용을 관찰하는 방법을 여기서 한 번에 정리한다.

| 수단 | 무엇을 주는가 | 한계 |
|---|---|---|
| `GC.GetAllocatedBytesForCurrentThread()` | 각 스레드의 할당량. 여기에 프로세스 전역 통계를 쌓아 올릴 수 있다 | **할당 정보일 뿐 얼마나 살아남는지는 전혀 알려주지 않는다.** 프로세스의 전체 메모리 사용에 대해 아무것도 말하지 않는다 |
| `AppDomain.MonitoringTotalAllocatedMemorySize` | 같은 목적의 .NET Framework 대안 | .NET Framework 전용. 할당 컨텍스트 세분성 |
| `GC.GetTotalMemory()` | 모든 세대의 관리 객체가 차지한 총 크기(단편화 제외) | 단편화와 관리 힙 전체 메모리를 고려하지 않는다. **OS 관점의 프로세스 메모리 소비와 직접 상관관계가 없다.** 대신 **누수 탐지에는 훌륭하다** |
| `Process.WorkingSet64` / `PrivateMemorySize64` | OS 관점의 프로세스 메모리 | GC 힙과 그 외를 구분해 주지 않는다. `GetTotalMemory`를 보완하는 용도 |
| `GC.GetGCMemoryInfo()` | 마지막 GC의 상세 통계(단편화 포함) | .NET Core 3.0+. **.NET 5부터는 단편화를 포함한 전체 관리 힙 크기를 프로그래밍으로 얻을 수 있다** |
| .NET CLR Memory 성능 카운터 | 세대 크기, 가상 메모리 소비 등 깊은 통찰 | **Windows .NET Framework에서만 지원된다** |
| TraceEvent 라이브러리로 GC 이벤트 관찰 | 훨씬 정밀하고 깊은 통찰. CLR 이벤트는 엄청난 양의 정보를 준다 | ETW/EventPipe 오버헤드는 캡처하는 이벤트 수에 비례한다. **GC start/end/GCHeapStats 정도만 관찰하는 것이 고수준 메모리 정보를 얻는 합리적 접근** |

> **⚠️ 자기 프로세스에 ClrMD로 붙는 것은 위험하다**
>
> ClrMD(`Microsoft.Diagnostics.Runtime`)는 프로세스를 중단시키지 않고 붙을 수 있으므로 이론적으로는 **자기 자신에게** 붙어 자가 모니터링을 할 수 있다. 그러나 깊이 생각해 보면 많은 도전이 따른다 — 동적으로 변하는 프로세스 상태를 어떻게 다룰 것인가, GC와 할당이 일어나는 도중 힙을 어떻게 검사할 것인가. ClrMD 관리자도 자가 검사를 명시적으로 금지하지는 않았지만 **제대로 하는 것은 정말 어려운 일이며, 문제가 생기면 지원되지 않는 시나리오로 취급해야 한다.** 자가 검사가 필요하다면 **자식 프로세스에 위임하는 편이 낫다.** Debug 빌드의 진단 수단으로는 고려할 만하지만 Release 프로덕션 빌드에 포함하기 전에는 신중해야 한다. 진단 도구 전반은 66장에서 다룬다.

## 65.10 배열 풀링을 GC 관점에서 보기

### 왜 이 절이 이 장에 있는가

배열 풀링은 언뜻 GC 튜닝과 무관해 보인다. 그러나 **GC 설정을 바꾸는 것보다 훨씬 큰 효과를 내는 경우가 많고**, 무엇보다 이 장에서 본 함정 몇 개를 한 번에 없앤다. 지금까지 본 것을 되짚어 보자.

| 이 장에서 본 문제 | 배열 풀링이 하는 일 |
|---|---|
| 백그라운드 GC의 **동시 스윕 중 LOH 할당이 블록된다**(65.2절) | LOH에 새로 할당하지 않으므로 블록될 일이 없다 |
| 백그라운드 GC는 **압축하지 않아 LOH가 단편화된다** | 큰 배열을 재사용하므로 LOH에 구멍을 만들지 않는다 |
| `GCConserveMemory`로 LOH 압축을 유도해도 **gen2 단편화가 낮으면 압축되지 않는다**(65.6절) | 애초에 LOH 단편화를 만들지 않는다 |
| `GCSettings.LargeObjectHeapCompactionMode = CompactOnce`는 **대단히 비싸다** | 쓸 일이 없어진다 |
| 서버 GC로 바꿔 처리량을 얻으려 하면 **메모리가 늘어난다**(65.1절) | 할당 자체를 줄이므로 GC 빈도가 내려간다 |

62.3절에서 본 것처럼 **85,000바이트를 넘는 객체는 LOH로 간다.** LOH는 기본적으로 압축되지 않는다. 큰 블록의 메모리를 GC 중에 옮기는 비용이 지나치게 크기 때문이다. 그 결과 두 가지가 따라온다.

- **할당이 느려질 수 있다.** GC가 항상 힙 끝에서 할당할 수 없고 중간의 빈틈도 찾아봐야 하며, 그러려면 빈 메모리 블록의 연결 리스트를 유지해야 한다(63.2절).
- **LOH는 단편화된다.** 86,000바이트 객체가 남긴 구멍은 85,000~86,000바이트 객체로만 채울 수 있다(인접한 다른 구멍과 합쳐지지 않는 한).

LOH는 또한 **비세대적**이다. 모든 객체가 gen2로 취급된다. 즉 **전체 GC에서만 수집된다.**

### `ArrayPool<T>`

애플리케이션이 배열을 자주 만든다면 배열 풀링으로 대부분의 GC 오버헤드를 피할 수 있다. .NET Core 3에서 도입되었고, 배열을 "빌린" 뒤 나중에 풀에 반환해 재사용하는 방식으로 동작한다.

```csharp
using System.Buffers;

// 전역 공유 풀에서 최소 100개 원소를 담는 int 배열을 빌린다
int[] pooledArray = ArrayPool<int>.Shared.Rent(100);
try
{
    // pooledArray.Length는 100보다 클 수 있다
    Process(pooledArray.AsSpan(0, 100));
}
finally
{
    // 반드시 반환한다
    ArrayPool<int>.Shared.Return(pooledArray);
}
```

풀 관리자는 **요청한 것보다 큰 배열을 줄 수 있다**(일반적으로 2의 거듭제곱 단위로 할당한다). 배열을 다 쓰면 `Return`을 호출한다. 이것이 배열을 풀에 반환해 같은 배열을 다시 빌릴 수 있게 한다. 풀 관리자에게 **반환 전에 배열을 지우라고** 불리언 값으로 지시할 수도 있다.

공유 풀 대신 커스텀 풀을 만들어 거기서 빌릴 수도 있다.

```csharp
var myPool = ArrayPool<int>.Create();
int[] array = myPool.Rent(100);
// ...
myPool.Return(array);
```

> **⚠️ 반환한 배열을 계속 쓰는 것을 아무것도 막지 않는다**
>
> 배열 풀링의 한계다. **배열을 반환한 뒤에도 (불법적으로) 계속 사용하는 것을 막는 장치가 없다.** 이 시나리오를 피하려면 조심스럽게 코딩해야 한다. 그리고 명심할 것 — **자기 코드만 망가뜨리는 것이 아니라 배열 풀링을 쓰는 다른 API까지 망가뜨릴 수 있다.** ASP.NET Core가 그런 API 중 하나다.
>
> 커스텀 풀을 만들면 다른 API를 망가뜨릴 위험은 사라지지만, 재사용 기회가 줄어 **전체 메모리 사용량은 늘어난다.**

> **⚠️ `Rent`가 주는 배열의 길이를 믿지 마라**
>
> `Rent(100)`이 길이 128인 배열을 줄 수 있다. `pooledArray.Length`로 루프를 돌면 **초기화되지 않은(또는 이전 대여자가 남긴) 데이터를 읽게 된다.** 항상 자기가 요청한 길이를 별도로 들고 다니거나 `AsSpan(0, n)`으로 잘라 쓴다. 이것은 논리 버그일 뿐 아니라 **이전 대여자의 데이터가 새어 나가는 보안 문제**가 될 수 있다. 민감한 데이터를 담았다면 `Return(array, clearArray: true)`를 쓴다.

> **💡 GC 설정을 만지기 전에 할당을 줄여라**
>
> 이 장 전체가 GC 설정에 관한 것이지만, 실무에서 효과 순위를 매기면 이렇다. **(1) 할당을 줄인다(63.9절의 숨은 할당, 배열 풀링, `Span<T>`) → (2) 객체 수명을 고친다(중년기 위기, 64장 Rule 18) → (3) GC 모드를 바꾼다 → (4) 세부 손잡이를 돌린다.** 3번과 4번부터 시작하는 팀을 자주 본다. 1번에서 얻을 수 있는 것이 대개 훨씬 크고, 1번을 하고 나면 3번이 필요 없어지는 경우도 많다.

> **📌 POH가 있으면 세대 인식 풀은 필요 없다**
>
> `GC.GetGeneration`을 이용해 "오래된 세대의 객체를 우선 빌려주는" 풀을 만드는 기법이 있었다. 고정할 객체를 모아 두는 풀에서, gen2 전용 세그먼트에 사는 객체를 재사용하면 고정의 해악이 줄어들기 때문이다(짧은 시간 고정한다면 그 사이 전체 GC가 일어날 확률이 훨씬 낮다). .NET 5+에서는 **POH(고정 객체 힙)에 직접 할당하면 되므로 이 기법은 필요 없다**(62.5절). .NET 기본 라이브러리 내부의 `PinnableBufferCache` 클래스가 이런 풀의 실제 구현이며, 캐시 트리밍과 다중 스레드 접근 최적화까지 담고 있어 읽어 볼 값어치가 있다.

## 65.11 GC 모드 선택 판단 흐름도

### 가장 정직한 답부터

여기까지 GC가 동작할 수 있는 다양한 모드와 지연 시간 설정을 통한 침습성 제어를 배웠다. 그래서 **내 경우에 최선의 GC 선택은 무엇인가.**

**단순한 답은 기본 GC 모드를 쓰라는 것이다.** 많은 경우 이 답으로 충분하고, 대안 때문에 머리를 싸맬 필요가 없다. 기본 설정이 이렇게 잘 동작한다는 것은 .NET 팀의 대단한 성취이며, 실제로 보통은 그것을 바꿀 이유가 없다.

그럼에도 돌려 볼 만한 손잡이가 있고, 사용을 고려할 값어치가 있는 상황이 있다. 가장 흔한 예외는 두 가지다.

- **다른 애플리케이션이 많이 도는 서버에 호스팅된 웹 애플리케이션.** 기본 백그라운드 서버 GC가 자원을 너무 많이 쓸 수 있다. `GCHeapCount`로 조금 튜닝하거나 다른 모드로 바꾼다.
- **처리를 많이 하는 Windows 서비스.** 기본 백그라운드 워크스테이션 GC가 충분히 확장되지 않을 수 있다. 서버 모드로 바꾸는 것을 검토한다.

| `SustainedLowLatency` | 불가 | **가능** | 불가 | **가능** |
| `GCHeapCount` | 불가 | 불가 | **가능** | **가능** |
| **전형적 용도** | 한 머신에 경량 애플리케이션이 많고 더 긴 중단을 감수할 수 있는 경우(짧은 `LowLatency` 구간으로 통제 가능) | 엄격한 응답성 요구가 있는 대화형 애플리케이션(`LowLatency`·`SustainedLowLatency`로 추가 제어) | 현재는 꽤 드물다. 자원을 더 쓰는 백그라운드 서버와 백그라운드 워크스테이션 사이의 타협으로 쓸 수 있으나 더 긴 GC 일시 정지를 도입한다. 긴 블로킹 GC는 GC 알림으로 수용할 수 있다 | 요청 처리 기반의 대부분의 애플리케이션(IIS 호스팅 웹 애플리케이션, 처리형 Windows 서비스) |

> **⚠️ `LowLatency`는 서버 GC에서 쓸 수 없고, `SustainedLowLatency`는 비동시 워크스테이션에서 쓸 수 없다**
>
> 표의 지연 시간 모드 네 줄이 이 장에서 가장 자주 사고를 내는 부분이다. `GCSettings.LatencyMode`에 **현재 GC 모드가 지원하지 않는 조합**(서버 GC에 `LowLatency` 등)을 대입해도 **예외가 나지 않는다.** 그냥 원하는 효과가 없거나 다른 값으로 정착한다. 코드는 잘 도는데 의도한 튜닝이 전혀 적용되지 않는 상태가 된다. 설정 직후 `GCSettings.LatencyMode`를 **다시 읽어 확인하는 것**이 유일하게 확실한 방법이다.
>
> ```csharp
> GCSettings.LatencyMode = GCLatencyMode.SustainedLowLatency;
> if (GCSettings.LatencyMode != GCLatencyMode.SustainedLowLatency)
>     Log.Warn("SustainedLowLatency가 적용되지 않았다. 동시 GC로 시작했는지 확인하라.");
> ```
>
> 실무적으로 기억할 것은 단순하다. **대화형 앱 = 백그라운드 워크스테이션(기본), 요청 처리 앱 = 백그라운드 서버(기본), 자원이 극도로 부족한 환경 = 비동시 계열.** 나머지는 측정으로 정한다.

> **💡 판단을 뒤집는 세 가지 질문**
>
> 모드를 고르기 전에 이 세 가지를 먼저 물어라.
>
> 1. **이 프로세스는 이 머신의 CPU를 독점하는가?** 아니라면 서버 GC의 전제가 깨진다.
> 2. **요청 하나의 처리 시간이 GC 일시 정지보다 긴가?** 처리 시간이 수백 ms라면 수 ms의 GC 일시 정지 차이는 응답 시간에 거의 나타나지 않는다. 요청을 수십 ms에 처리한다면 정반대다.
> 3. **메모리와 처리량 중 무엇이 실제 비용인가?** 클라우드 청구서를 보면 대개 답이 나온다. 인스턴스 수를 늘려 처리량을 사는 것이 GC 모드를 바꾸는 것보다 싸고 확실한 경우가 많다.

### Rule 23 — GC 모드를 의식적으로 선택하라

**적용 범위** — 일반 코드: 보통 정도로 흔하다. 고성능 코드: **매우 중요하다.**

**근거** — 다양한 GC 모드와 설정이 있다. 힙 개수와 GC 스레드 수, 공격성 같은 핵심 GC 매개변수가 통제 아래 있다. 대부분의 경우 기본 설정으로 충분하다. **그러나 대안이 무엇인지, 그리고 그에 대해 어떻게 좋은 판단을 내리는지는 알고 있어야 한다.**

**적용 방법**

1. 애플리케이션의 특성을 올바르게 반영하는 주된 모드에서 시작한다. 서버 앱인가 워크스테이션 앱인가, 일시 정지 지속 시간에 신경 쓰는가 아닌가. **자기 앱의 일반적 특성은 이미 알고 있을 테니 이것은 거의 일이 아니다.**
2. 각 GC 모드는 CPU와 메모리 사용 측면에서 각자의 장단점이 있고, 전체 애플리케이션 성능에 서로 다른 방식으로 영향을 준다. **측정하지 않고서는 어느 모드가 자기 필요에 가장 맞는지 말하기 정말 어렵다.**
3. 성능에 정말 신경 쓴다면 확인하고 측정하라. Rule 5(GC를 일찍 측정하라)와 Rule 6(프로그램을 측정하라)이 특히 사전 프로덕션 환경(그리고 어느 정도는 프로덕션에서도) 도움이 된다.
4. **테스트 방법론에 주의하라 — 특히 가장 중요한 측정에 백분위를 쓰는 것.**

### Rule 24 — 지연 시간 모드를 기억하라

**적용 범위** — 일반 코드: 오히려 드물다. 고성능 코드: **중요하다.**

**근거** — 네 가지 .NET GC 모드 외에 **지연 시간 모드로 GC의 공격성에 영향을 줄 수 있다.** 지연 시간 모드는 GC가 얼마나 기꺼이 블로킹 가비지 컬렉션을 실행할지(그래서 원치 않는 일시 정지를 도입할지)를 제어한다. 이것은 **응답성**(짧은 블로킹 일시 정지만 있으므로)과 **메모리 사용량**(비압축 백그라운드 GC 때문에) 사이의 명확한 균형으로 이어진다.

짧은 지연에 집중하는 모드는 대화형 애플리케이션에서 UI 반응성에 추가 통제가 필요할 때, 전형적으로 **최대 부드러움이 필요한 짧은 기간**(키보드 타이핑 등)에 가장 자주 쓰인다. 트레이딩 앱 같은 일부 서버 앱은 **거래 시간 동안 전체 블로킹 GC의 방해를 원치 않는다**는 것을 표시하기 위해 `SustainedLowLatency`를 쓰면서, 동시에 그 시간 동안 충분한 메모리가 있는지 확인한다.

**적용 방법** — 지연 시간 모드는 애플리케이션 코드 안에서 바꾼다. 저지연 모드는 **항상 일정 시간 동안만** 설정한다. 기대가 강할수록 그 시간은 짧아야 한다.

- 한쪽 끝에 `SustainedLowLatency`가 있다. 블로킹 전체 GC만 비활성화하므로 오래 지속할 수 있다.
- 다른 쪽 끝에 no GC 영역이 있다. 가비지 컬렉션을 통째로 비활성화한다.
- 추가로 동시/비동시 GC 버전 사이를 **동적으로 전환**할 수 있다.

사용자가 애플리케이션을 어떻게 쓰는지 잘 이해하고 있다면 훨씬 잘 튜닝된 메모리·CPU 사용으로 이어질 수 있다. **그러나 이런 정밀한 튜닝은 전형적인 애플리케이션에는 필요 없다.** 성능 요구의 한계에 접근하고 있을 때만 지연 시간 모드를 관심 있게 보면 된다.

## 65.12 커스텀 GC(standalone GC)의 존재

### 플러그인이 된 GC

**.NET Core 2.1부터 가비지 컬렉터와 실행 엔진 사이의 결합이 크게 느슨해졌다.** 그 이전에는 GC 코드가 나머지 CLR 코드와 상당히 얽혀 있었다. .NET Core 2.1이 **로컬 GC(Local GC)**, 다른 이름으로 **독립 GC(standalone GC)** 개념을 도입하면서, 런타임이 **자기 DLL 안에 있는 GC를 쓸 수 있게** 되었다. 즉 GC가 플러그인이 되었다.

환경 변수 하나로 커스텀 GC를 끼워 넣는다.

```text
set DOTNET_GCName=ZeroGC.dll
```

`DOTNET_GCName`은 커스텀 GC를 담은 라이브러리의 **이름만** 받고 `coreclr.dll`과 같은 폴더에서 찾는다. **.NET 9부터는 절대 경로를 받는 `DOTNET_GCPath` 환경 변수를 대신 쓸 수 있다.**

런타임은 초기화할 때 이 환경 변수를 알아채고 기본 내장 GC 대신 지정된 라이브러리에서 커스텀 GC를 로드하려 시도한다. **커스텀 GC는 기본 GC와 완전히 다른 구현을 담을 수 있다. 세대, 세그먼트, 할당자, 파이널라이제이션 같은 개념이 커스텀 GC에는 아예 없을 수도 있다.**

### 무엇을 구현해야 하는가

가장 단순한 로컬 GC 구현은 그리 복잡하지 않다. 컴파일을 위해 CLR 코드에서 `debugmacros.h`, `gcenv.base.h`, `gcinterface.h` 세 파일만 직접 포함하면 된다.

커스텀 GC 라이브러리는 CLR이 초기화 중에 호출하는 **내보내기 함수 두 개**만 정의하면 된다.

```cpp
extern "C" DLLEXPORT HRESULT
GC_Initialize(
    /* In  */ IGCToCLR* clrToGC,
    /* Out */ IGCHeap** gcHeap,
    /* Out */ IGCHandleManager** gcHandleManager,
    /* Out */ GcDacVars* gcDacVars
)
{
    IGCHeap* heap = new ZeroGCHeap(clrToGC);
    IGCHandleManager* handleManager = new ZeroGCHandleManager();
    *gcHeap = heap;
    *gcHandleManager = handleManager;
    return S_OK;
}

extern "C" DLLEXPORT void
GC_VersionInfo(/* Out */ VersionInfo* result)
{
    result->MajorVersion = GC_INTERFACE_MAJOR_VERSION;
    result->MinorVersion = GC_INTERFACE_MINOR_VERSION;
    result->BuildVersion = 0;
    result->Name = "Zero GC";
}
```

- `GC_Initialize`는 두 핵심 인터페이스 `IGCHeap`과 `IGCHandleManager`의 커스텀 구현을 지정해야 한다.
- `GC_VersionInfo`는 하위 호환성 관리에 쓰인다. 커스텀 GC가 요구하는 런타임(더 정확히는 그 GC 인터페이스)의 버전을 지정한다.

제공된 `IGCToCLR` 인터페이스 주소도 저장해야 한다. GC 코드 안에서 CLR과 통신하는 데 쓴다. 메서드가 아주 많은데 흥미로운 것 몇 개는 다음과 같다.

| 메서드 | 역할 |
|---|---|
| `SuspendEE` / `RestartEE` | 주어진 이유로 관리 스레드를 중단·재개하도록 런타임에 요청한다(커스텀 GC의 비동시 부분 구현에 쓴다) |
| `GcScanRoots` | 모든 관리 스레드의 스택 워크를 수행하고, 스택에서 만난 모든 GC 루트에 주어진 `promote_func`를 호출한다(커스텀 Mark 단계 구현에 필요하다) |
| `GcStartWork` / `GcDone` | GC가 시작되고 완료되었음을 런타임에 알린다 |

> **⚠️ `IGCHeap`은 80개가 넘는 메서드를 요구한다**
>
> 커스텀 `IGCHeap` 구현은 핵심 가비지 컬렉션 기능을 대표하는 주 인터페이스다. **구현해야 할 메서드가 80개를 넘는다.** 다만 그중 대부분은 유효한 구현이 필요하지 않다. **내장 현재 GC의 설계를 염두에 두고 선언된 것들**이기 때문이다. 커스텀 GC에는 지연 시간 모드나 LOH 개념 자체가 없을 수 있으므로 `SetGcLatencyMode`나 `SetLOHCompactionMode` 같은 메서드에는 더미 구현을 제공하면 된다.

가장 단순한 이른바 **Zero GC**(객체를 할당하기만 하고 절대 회수하지 않는 GC)는 이렇게 구현할 수 있다.

```cpp
Object* ZeroGCHeap::Alloc(gc_alloc_context* acontext, size_t size, uint32_t flags)
{
    int sizeWithHeader = size + sizeof(ObjHeader);
    ObjHeader* address = (ObjHeader*)calloc(sizeWithHeader, sizeof(char*));
    return (Object*)(address + 1);
}

HRESULT ZeroGCHeap::GarbageCollect(int generation, bool low_memory_p, int mode)
{
    return NOERROR;
}
```

커스텀 GC는 "작은" 객체와 "큰" 객체(그래서 SOH와 LOH)를 구분할 필요조차 없다. 크기와 무관하게 원하는 대로 할당하면 된다 — 예를 들어 항상 `calloc` 호출로. **기본 .NET GC에서는 수천 줄의 코드를 실행하고 이 책 수백 페이지로 설명되는 `GarbageCollect` 메서드가 한 줄로 끝나는 것을 보는 것은 꽤 재미있는 일이다.**

### .NET 팀도 이 기능을 쓴다

이것이 실험용 장난감만은 아니다. **.NET 팀 자신이 로컬 GC 기능을 쓴다.**

| 라이브러리 | 정체 |
|---|---|
| `clrgc.dll` | .NET 8에서 **세그먼트를 쓰는 "옛 GC"** 가 이 이름으로 컴파일되어 런타임과 함께 배포된다. 어떤 이유로든 그 버전으로 되돌아가고 싶다면 `GCName` 환경 변수를 여기로 가리키면 된다 |
| `clrgcexp.dll` | **기본 GC의 실험 버전.** 아직 완전히 테스트되지 않은 다가오는 실험적 기능이 들어 있다. 리전 기반 GC가 기본이 되기 전에 이것으로 배포되었다 |

> **💡 리전 회귀를 의심할 때 `clrgc.dll`로 되돌려 보라**
>
> .NET 7에서 리전이 기본이 되면서 일부 워크로드에서 메모리 사용 패턴이 달라졌다(62.6절). 리전 도입 이후 특정 워크로드에서 회귀를 의심한다면 **`DOTNET_GCName=clrgc.dll`로 세그먼트 기반 GC로 되돌려 A/B 비교**를 해 볼 수 있다. 이것은 진단 수단이지 프로덕션 해법이 아니다 — 원인을 찾았으면 되돌려 놓아야 한다. 이 스위치는 런타임 버전에 따라 사라질 수 있다.

> **⚠️ 커스텀 GC는 "조금만 고치기"가 안 된다**
>
> 커스텀 GC를 쓰면 **기본 GC 기능 전체를 대체한다.** 기본 동작을 "조금만" 수정하는 것은 쉽지 않다. 다만 내장 GC 코드 전체를 가져다 독립 GC 라이브러리로 배포하면 그것을 출발점으로 삼아 완성하기는 훨씬 쉬워진다.
>
> 현실적으로 커스텀 GC를 실제로 쓰는 경우는 연구, 교육, 그리고 아주 특수한 임베디드·실시간 시나리오다. **프로덕션 서비스에서 커스텀 GC를 검토하고 있다면, 그 전에 이 장의 나머지 모든 손잡이를 다 돌려 봤는지 확인하라.**

## 이 장의 요약

- **GC 설정의 축은 세 개뿐이다.** 워크스테이션/서버, 비동시/백그라운드, 그리고 지연 시간 모드. 앞의 둘은 프로세스 시작 시 고정되고 **지연 시간 모드만 런타임에 바꿀 수 있다.** JVM식 세밀 조정이 없는 것은 결함이 아니라 애플리케이션 중심 설계의 결과다.
- **워크스테이션은 힙 1개·응답성, 서버는 코어 수만큼의 힙·처리량이다.** 서버 모드는 메모리를 더 쓰고 총 중단 시간을 줄인다. **논리 코어가 1개면 `gcServer` 설정이 무시된다.**
- **백그라운드 GC는 긴 정지 하나를 짧은 정지 두 개로 쪼갠다.** 초기 STW(A) → 동시 마크(B) → 최종 마크 STW(C) → 동시 스윕(D). 대가는 **비압축**이라 단편화가 쌓이고, 부유 쓰레기가 생기며, CPU를 더 쓴다는 것이다.
- **동시 마크는 마크 배열(64비트에서 1비트 = 힙 16바이트)과 쓰기 감시로 구현된다.** 쓰기 감시가 페이지(4 kB) 세분성이므로 객체 참조를 자주 수정하는 워크로드는 재방문 비용이 커진다. `BGCRevisit` 이벤트로 확인한다.
- **동시 스윕 중 LOH 스윕 구간에서는 대형 객체 할당이 블록된다.** gen2 백그라운드 스윕 중 LOH 할당은 .NET Core 3.1부터 허용되지만, LOH 자체를 스윕하는 동안은 여전히 막힌다.
- **지연 시간 모드는 "빨라져라"가 아니라 "무엇을 금지할 것인가"다.** Batch는 백그라운드 GC를 끄고, LowLatency는 모든 gen2 GC를 막고(워크스테이션 전용), SustainedLowLatency는 비동시 전체 GC만 막는다. NoGCRegion은 `TryStartNoGCRegion`으로만 진입한다.
- **`TryStartNoGCRegion`은 `EndNoGCRegion`과 반드시 짝을 이뤄야 한다.** 짝이 없으면 다음 호출이 `InvalidOperationException`으로 실패한다. 할당 한도를 넘겨 모드가 자동 해제된 뒤에도 `EndNoGCRegion` 호출은 필요하고, 그 호출도 던진다.
- **환경 변수의 숫자 값은 16진수다.** `DOTNET_GCHeapHardLimitPercent=50`은 50%가 아니라 80%다. 그리고 환경 변수는 `runtimeconfig.json`을 이긴다. 설정 후에는 **`GC.GetConfigurationVariables()`로 실제 값을 확인하라.**
- **컨테이너에서 GC는 메모리 제한의 75%를 힙 상한으로 잡는다.** `GCHeapHardLimitPercent`/`GCHeapHardLimit`으로 조정하고, .NET 8부터는 `AppContext.SetData` + `GC.RefreshMemoryLimit()`으로 런타임에 바꿀 수 있다(값은 반드시 `ulong`).
- **DATAS는 gen0 예산과 힙 개수를 워크로드에 맞춰 동적으로 조정한다.** .NET 8 옵트인, .NET 9 서버 GC 기본값. 켜면 `GCConserveMemory=5`가 따라온다. 처리량이 절대적인 워크로드에서는 `GarbageCollectionAdaptationMode=0`으로 끈다.
- **`GC.GetGCMemoryInfo`가 가장 정보가 많은 GC API다.** 단편화를 볼 수 있고, `PauseDurations`가 STW 구간을 **분리해서** 준다. `Index == 0`이면 나머지 필드를 쓰면 안 되고, `GenerationInfo` 인덱스(3=LOH, 4=POH)와 `Generation` 필드는 체계가 다르다.
- **`AddMemoryPressure`/`RemoveMemoryPressure`는 짝을 맞춰야 한다.** 순 압력이 예산(4 MB에서 시작, 최근 세 GC를 기준으로 동적 조정)과 비교되어 GC를 트리거한다. 짝이 어긋나면 GC 튜닝이 영구히 왜곡된다.
- **GC 설정을 만지기 전에 할당을 줄여라.** 배열 풀링은 LOH 단편화, 동시 스윕 중 블록, 압축 비용을 한 번에 없앤다. 다만 `Rent`가 요청보다 큰 배열을 줄 수 있고, 반환한 배열을 계속 쓰는 것을 아무도 막지 않는다.
- **커스텀 GC는 `DOTNET_GCName`(또는 .NET 9+의 `DOTNET_GCPath`)으로 끼운다.** .NET 팀 자신이 `clrgc.dll`(세그먼트 기반 옛 GC)과 `clrgcexp.dll`(실험 버전)로 이 기능을 쓴다.

| 규칙 | 요지 |
|---|---|

## 연습 문제

1. 같은 콘솔 프로그램을 `DOTNET_gcServer=0`과 `DOTNET_gcServer=1`로 각각 실행하고, `GCSettings.IsServerGC`와 `GC.GetConfigurationVariables()["HeapCount"]`를 출력해 확인하라. 그다음 컨테이너에 `--cpus=1`을 주고 다시 실행해 **서버 GC 설정이 무시되는 것**을 확인하라.
2. `DOTNET_GCHeapCount=10`으로 서버 GC 프로세스를 띄우고 `GC.GetConfigurationVariables()`의 `HeapCount` 값을 확인하라. 10이 아니라 16이 나오는 이유를 설명하고, 실제로 10개를 얻으려면 무엇을 설정해야 하는지 확인하라.
3. 대형 객체를 반복 할당하는 프로그램을 백그라운드 워크스테이션과 비동시 워크스테이션으로 각각 돌리고, `GC.GetTotalPauseDuration()`으로 총 일시 정지 시간을, `dotnet-counters`로 `GC Heap Size`를 비교하라. **총 일시 정지와 메모리 사용량이 반대 방향으로 움직이는 것**을 수치로 확인하라.
4. `dotnet-trace collect --providers "Microsoft-Windows-DotNETRuntimePrivate:1:5,Microsoft-Windows-DotNETRuntime:1:5"`로 세션을 열고 백그라운드 GC가 일어나는 워크로드를 실행하라. `BGCRevisit` 이벤트의 dirty page 수와 재방문 객체 수를 확인하고, 객체 그래프를 자주 수정하는 버전과 그렇지 않은 버전에서 값이 어떻게 달라지는지 비교하라.
5. `GC.TryStartNoGCRegion`을 호출한 뒤 `EndNoGCRegion` 없이 다시 `TryStartNoGCRegion`을 호출해 예외 메시지를 직접 확인하라. 이어서 요청한 `totalSize`보다 많이 할당한 뒤 `EndNoGCRegion`을 호출해 **다른 메시지의 같은 예외 타입**이 나오는 것을 확인하라.
6. `AppContext.SetData("GCHeapHardLimitPercent", 50)`(`int`)와 `50UL`(`ulong`)을 각각 설정하고 `GC.RefreshMemoryLimit()` 후 `GC.GetConfigurationVariables()`를 출력하라. **`int`가 조용히 무시되는 것**을 확인하라.
7. 85,000바이트를 넘는 배열을 반복 할당하는 프로그램과, 같은 일을 `ArrayPool<byte>.Shared`로 하는 프로그램을 만들어 `GC.GetGCMemoryInfo()`의 `GenerationInfo[3]`(LOH) 단편화와 `GC.CollectionCount(2)`를 비교하라.
8. .NET 8 이상에서 `DOTNET_GCDynamicAdaptationMode`를 0과 1로 바꿔가며 부하 변동이 큰 워크로드를 돌리고, 유휴 구간과 피크 구간의 `GC Heap Size`와 `HeapCount`를 관찰하라. DATAS가 힙 개수를 실제로 조정하는지 확인하라.
