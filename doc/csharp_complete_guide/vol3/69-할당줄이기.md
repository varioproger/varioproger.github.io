# 69장. 할당 줄이기

> **이 장의 위치** — 63장이 "할당은 어디서 생기는가"를 끝까지 팠다면, 이 장은 그 목록을 손에 들고 **"그래서 어떻게 없애는가"** 를 판다. 63.9절의 숨은 할당 카탈로그와 63.10절의 도구 지도는 여기서 실제 코드로 바뀐다. 67장이 준 측정 도구와 68장이 준 `Span` 도구가 여기서 처음으로 함께 쓰인다.
>
> **선수 지식** — 16장(구조체와 값 타입), 63장(할당), 67장(측정 없이 최적화 없다), 68장(`Span`과 `Memory`)
>
> **이 장에서 다루지 않는 것** — 할당의 출처 목록 자체는 63.9절에서, `Span`·`Memory` 타입의 내부 구조는 68장에서, 캐시 라인에 맞춘 데이터 레이아웃 설계와 AoS→SoA 전환은 70장에서, `System.IO.Pipelines`는 72.1절에서 다룬다.

이 장은 하나의 전제 위에 서 있다. **측정이 먼저다.** 67.5절의 `MemoryDiagnoser`가 "이 메서드가 요청당 4.2 kB를 할당한다"고 말해 주지 않았다면, 이 장의 어떤 기법도 적용할 이유가 없다. 할당 회피는 거의 언제나 **가독성과 유지보수성을 코드에서 빼내어 성능으로 바꾸는 거래**이고, 거래에는 대가가 있다. 69.8절 후반부에 그 대가의 목록을 따로 정리해 두었다 — 이 장을 읽기 시작하면서 그 절을 먼저 훑어도 좋다.

## 69.1 `struct`로 바꿀 때의 손익 계산

가장 먼저 검토하는 기법이면서 가장 자주 오용되는 기법이다. "클래스를 구조체로 바꾸면 힙 할당이 사라진다"는 문장은 절반만 맞다. 사라지는 것은 **그 객체의 헤더와 개별 할당**이지, 데이터 자체가 아니다. 그리고 사라진 할당 비용은 **복사 비용**이라는 다른 항목으로 이동한다.

### 마이크로소프트 지침과 그 한계

.NET 설계 지침은 구조체가 다음 네 조건을 **모두** 만족할 때만 `struct`를 쓰라고 말한다.

1. 논리적으로 **단일 값**을 표현한다.
2. 인스턴스 크기가 **16바이트 미만**이다.
3. **불변(immutable)** 이다.
4. **자주 박싱되지 않는다.**

이 지침은 안전하지만 보수적이다. 실제 성능 작업에서는 2번이 가장 자주 깨진다 — 64바이트짜리 구조체를 `ref`로만 주고받으면 복사가 일어나지 않으므로 크기 제한은 의미를 잃는다. 그래서 이 장은 지침 대신 **손익 계산표**를 쓴다.

### 구조체 전환 손익 계산표

전환 대상 타입 하나를 놓고 다음 아홉 항목을 채운다. 왼쪽 열의 점수를 합산해서 판단하라는 뜻이 아니라, **어느 한 항목이라도 "치명" 칸에 걸리면 전환하지 않는다**는 뜻이다.

| 항목 | 이득 | 중립 | 손해 / 치명 |
|---|---|---|---|
| **인스턴스 크기** | ≤ 16 B — 레지스터 두 개에 들어간다 | 17~64 B — `in`/`ref` 전달이면 무방 | > 64 B이면서 값으로 전달 — 복사가 할당보다 비싸진다 |
| **복사 빈도** | 생성 후 한두 번 전달 | 루프 밖에서만 복사 | 루프 안에서 반복 복사, 특히 `foreach` 변수로 받을 때 |
| **박싱 위험** | 인터페이스로 절대 노출 안 됨 | 제네릭 제약으로만 노출 | `object`/인터페이스 파라미터, `IEnumerable` 저장, `params object[]` 사용 (54.6절) |
| **컬렉션 저장** | 배열 또는 `List<T>` 원소로만 | 딕셔너리 값 | `ArrayList`, 비제네릭 API, `IComparable` 기반 정렬 |
| **가변성** | `readonly struct` | `readonly` 멤버만 | 가변 구조체 + 프로퍼티 게터 — 방어적 복사가 조용히 생긴다 (16.5절) |
| **참조 필드 포함 여부** | 참조 필드 0개 — **쓰기 장벽이 사라진다** (64.11절) | 참조 1~2개 | 참조 다수 — 값 타입으로 만든 이득이 대부분 상쇄 |
| **캐시 지역성** | 배열로 순차 순회 — 포인터 추적 소멸 (70장) | 산발 접근 | 원소 크기가 캐시 라인을 넘어 stride가 커짐 |
| **수명** | 메서드 지역, 힙 자료 구조에 저장 안 됨 | 짧은 필드 수명 | 힙 객체의 필드로 오래 산다 — 그럴 거면 클래스가 낫다 |
| **다형성 요구** | 없음 | 없음 | 상속·`virtual`이 필요 — 값 타입은 못 한다 |

이 표의 마지막 세 줄이 원서들이 말하는 핵심이다. **구조체는 값을 저장하고, 클래스는 동작을 정의한다.** 타입에 "책임"이 붙기 시작하면 그것은 이미 클래스다.

> **📌 타입을 나중에 바꾸면 코드가 조용히 깨진다**
>
> `struct Employee`를 `class Employee`로 바꾸는 순간, 값으로 반환되던 것이 참조로 반환되고 값으로 전달되던 것이 참조로 전달된다. 컴파일러는 아무 불평도 하지 않는다.
>
> ```csharp
> Employee e1 = Employees.Find(e => e.Position == "CEO");
> decimal bonus = 10000;
> e1.CurrentPayAmount += bonus;   // 구조체였을 때: 복사본만 바뀐다 (일회성 보너스)
> e1.Pay(account);                 // 클래스가 되면: 원본이 바뀐다 (영구 인상)
> ```
>
> 값/참조 결정은 **처음 한 번에 맞춰야 하는 결정**이다. 성능을 이유로 나중에 뒤집으려면 호출부 전체의 의미론을 다시 검토해야 한다.

### 실측 — 클래스 기반 로직을 구조체로 옮기기

원서의 예제를 그대로 따라간다. 지정한 위치에서 일정 거리 안에 고용된 사람의 이름을 모으는 전형적인 업무 로직이다. 클래스 버전은 리스트 하나, `PersonDataClass` 인스턴스 N개, 외부 서비스가 돌려주는 `Employee` 객체 N개를 만든다.

```csharp
[Benchmark]
public List<string> PeopleEmployeedWithinLocation_Classes(int amount, LocationClass location)
{
    List<string> result = new List<string>();
    List<PersonDataClass> input = service.GetPersonsInBatchClasses(amount);
    DateTime now = DateTime.Now;
    for (int i = 0; i < input.Count; ++i)
    {
        PersonDataClass item = input[i];
        if (now.Subtract(item.BirthDate).TotalDays > 18 * 365)
        {
            var employee = service.GetEmployeeClass(item.EmployeeId);
            if (locationService.DistanceWithClass(location, employee.Address) < 10.0)
            {
                string name = string.Format("{0} {1}", item.Firstname, item.Lastname);
                result.Add(name);
            }
        }
    }
    return result;
}
```

사람과 고용 정보는 이 메서드를 **떠나지 않는다.** 힙 자료 구조에 저장되지도 않는다. 손익 계산표의 "수명" 항목이 이득 칸에 걸린다는 뜻이다. 구조체로 옮긴다.

```csharp
[Benchmark]
public List<string> PeopleEmployeedWithinLocation_Structs(int amount, LocationStruct location)
{
    List<string> result = new List<string>();
    PersonDataStruct[] input = service.GetPersonsInBatchStructs(amount);   // 배열로 받는다
    DateTime now = DateTime.Now;
    for (int i = 0; i < input.Length; ++i)
    {
        ref PersonDataStruct item = ref input[i];    // ref 지역 변수 — 복사하지 않는다
        if (now.Subtract(item.BirthDate).TotalDays > 18 * 365)
        {
            var employee = service.GetEmployeeStruct(item.EmployeeId);
            if (locationService.DistanceWithStruct(ref location, employee.Address) < 10.0)
            {
                string name = string.Format("{0} {1}", item.Firstname, item.Lastname);
                result.Add(name);
            }
        }
    }
    return result;
}
```

세 곳이 바뀌었다.

- `List<PersonDataClass>`가 `PersonDataStruct[]`가 되었다. 리스트 객체 하나, 내부 배열, 그리고 **원소 N개의 개별 할당**이 배열 하나로 합쳐졌다.
- `PersonDataClass item = input[i]`가 `ref PersonDataStruct item = ref input[i]`가 되었다. `ref` 지역 변수가 없으면 매 반복마다 구조체 전체가 복사된다.
- `DistanceWithStruct(ref location, ...)` — 구조체 인자를 참조로 넘긴다.

| 메서드 | Mean | Gen 0 | Allocated |
|---|---|---|---|
| PeopleEmployeedWithinLocation_Classes | 348.8 us | 15.1367 | 62.60 KB |
| PeopleEmployeedWithinLocation_Structs | 344.7 us | 9.2773 | 39.13 KB |

**할당이 약 62%로 줄었다. 실행 시간은 거의 그대로다.** 이 결과를 정확히 읽는 것이 중요하다. 구조체 전환의 1차 효과는 **속도가 아니라 GC 압력 감소**다. 62.60 kB에서 39.13 kB로 줄어든 23 kB는 GC가 다시 수거하지 않아도 되는 양이고, 그 이득은 이 벤치마크의 Mean이 아니라 **애플리케이션 전체의 GC 일시 중지 빈도**에 나타난다. 마이크로벤치마크가 구조체 전환의 가치를 과소평가하는 이유다.

> **⚠️ 남은 39 kB는 어디서 오는가**
>
> `List<string> result`와 `string.Format`이 만드는 문자열이다. 구조체 전환은 데이터 컨테이너의 할당만 없앤다. **문자열은 여전히 참조 타입이고 여전히 힙에 간다.** 이 39 kB를 더 줄이려면 69.5절(문자열)과 69.3절(배열 풀)로 가야 한다. 69.9절에서 같은 종류의 코드를 0 B까지 밀어붙인다.

### 배열 하나 vs 할당 101번

값 타입이 컬렉션에서 이기는 이유는 산술적이다.

```csharp
MyType[] arrayOfTypes = new MyType[100];
```

- `MyType`이 **값 타입**이면 → 할당 **1회**. 크기는 `sizeof(MyType) × 100` + 배열 헤더.
- `MyType`이 **참조 타입**이면 → 배열 할당 1회(전부 `null`) + 원소를 채울 때 **100회**. 총 **101회**.

101회의 할당은 1회보다 느릴 뿐 아니라 **힙을 조각내고**, 각 원소마다 객체 헤더 + 메서드 테이블 포인터(64비트에서 16바이트, 54.3절)를 추가로 쓴다. 그리고 순회할 때 매 원소마다 포인터를 따라가야 하므로 **캐시 미스가 원소 수만큼 발생할 수 있다.** 70장 데이터 지향 설계 전체가 이 한 문장에서 출발한다.

```text
참조 타입 배열                        값 타입 배열
┌────────────────────────┐          ┌───────────────────────────────┐
│ ref │ ref │ ref │ ref  │          │ P0 │ P1 │ P2 │ P3 │ P4 │ P5   │
└──┬──┴──┬──┴──┬──┴──┬───┘          └───────────────────────────────┘
   │     │     │     │                 캐시 라인 하나에 여러 개
   ▼     ▼     ▼     ▼                 순차 접근 = 프리페치 적중
 ┌───┐ ┌───┐ ┌───┐ ┌───┐
 │ P0│ │ P1│ │ P2│ │ P3│   힙 여기저기, 각각 헤더 16 B
 └───┘ └───┘ └───┘ └───┘   순회할 때마다 포인터 추적
```

### 쓰기 장벽이 사라지는 효과

64.11절에서 본 대로, **참조 타입 필드에 참조를 대입할 때마다 JIT이 쓰기 장벽(write barrier) 호출을 삽입한다.** 카드 테이블을 갱신해서 세대 간 참조를 GC에 알리기 위해서다. 이것은 단순한 `mov` 한 줄이 아니라 헬퍼 호출이다.

```csharp
class Node { public Node? Next; public int Value; }   // Next 대입 시마다 쓰기 장벽
struct Point { public int X; public int Y; }          // 어떤 대입에도 쓰기 장벽 없음
```

**참조 필드가 하나도 없는 구조체의 배열을 채우는 루프는 쓰기 장벽을 단 한 번도 실행하지 않는다.** 수백만 원소를 채우는 코드에서 이 차이는 실측된다. 반대로 말하면, 구조체 안에 `string` 필드가 하나라도 있으면 그 필드에 대입할 때는 여전히 장벽이 돈다.

> **💡 "참조 필드 0개" 구조체를 목표로 잡아라**
>
> 구조체 전환의 이득이 가장 큰 형태는 **전부 기본 값 타입으로 이루어진 구조체**다. 쓰기 장벽 소멸, 캐시 지역성, GC 스캔 대상에서 제외(마킹 단계가 이 배열 안을 들여다볼 필요조차 없다, 64.2절) — 세 이득이 동시에 온다.
>
> 문자열 필드가 걸림돌이라면 두 가지 선택지가 있다. 문자열을 **정수 ID로 바꾸고 별도 테이블에서 조회**하거나(70.4절의 ECS 사고방식), 고정 길이 텍스트라면 **인라인 배열**(`[InlineArray]` ※C# 12, 68.10절)로 구조체 안에 문자를 직접 담는 것이다.

### 구조체 전환이 실패하는 네 가지 방식

`readonly`가 아닌 구조체의 프로퍼티를 읽을 때 컴파일러가 **방어적 복사(defensive copy)** 를 넣는다는 것은 16.5절에서 봤다. 실제 성능 작업에서 마주치는 실패 유형을 정리한다.

| 실패 유형 | 증상 | 진단 | 처방 |
|---|---|---|---|
| **방어적 복사** | 구조체를 키웠는데 오히려 느려짐 | 디스어셈블리에 구조체 크기만큼의 `mov` 연속 | `readonly struct` 또는 `readonly` 멤버로 선언 |
| **`foreach` 복사** | 컬렉션 순회가 느려짐 | 반복 변수가 값 복사본 | `CollectionsMarshal.AsSpan(list)` 후 `ref` 순회 |
| **숨은 박싱** | 할당이 안 줄어듦 | `MemoryDiagnoser`에 여전히 할당, IL에 `box` | 제네릭 제약으로 인터페이스 받기 (63.9절) |
| **큰 구조체 값 전달** | Mean이 두 배로 뜀 | 호출 규약이 스택 복사로 바뀜 | `in`/`ref`/`ref readonly` 전달 |

> **⚠️ `in` 파라미터가 오히려 복사를 만든다**
>
> `in`으로 받은 구조체가 `readonly struct`가 **아니면**, 그 구조체의 멤버를 호출할 때마다 컴파일러는 방어적 복사를 만든다. 멤버가 구조체를 변경할 가능성을 배제할 수 없기 때문이다.
>
> ```csharp
> struct Big { public long A, B, C, D, E, F, G, H; public long Sum() => A + B + C + D; }
>
> // Big이 readonly struct가 아니므로 매 호출마다 64바이트가 복사된다
> static long Total(in Big b) => b.Sum() + b.Sum() + b.Sum();
> ```
>
> `in`을 붙였으니 복사가 없다고 믿는 것이 가장 흔한 오해다. **`in`은 `readonly struct`와 짝으로만 의미가 있다.** 짝이 아니면 `in` 없이 값으로 받는 편이 오히려 빠를 수 있다 — 복사가 한 번으로 끝나기 때문이다.

### 불변 구조체를 기본값으로

원서 『More Effective C#』의 Item 3은 값 타입에 대해 **불변성을 우선하라**고 말한다. 성능이 아니라 정확성의 이유다.

```csharp
// 가변 구조체 — 중간 상태가 항상 유효하지 않다
public struct Address
{
    public string City { get; set; }
    public string State { get; set; }
    public int ZipCode { get; set; }
}

var a = new Address();
a.City = "Ann Arbor";     // 이 시점에 State/ZipCode와 불일치
a.ZipCode = 48103;        // 아직도 State가 안 맞다
a.State = "MI";           // 이제야 유효
```

중간 두 줄 사이에서 예외가 나거나 컨텍스트 전환이 일어나면, **불변식이 깨진 값이 관측된다.** 불변 구조체는 이 창을 생성자 안으로 밀어 넣어 없앤다.

```csharp
public readonly struct Address
{
    public string Line1 { get; }
    public string City { get; }
    public string State { get; }
    public int ZipCode { get; }

    public Address(string line1, string city, string state, int zipCode)
    {
        Line1 = line1;
        City = city;
        ValidateState(state);   State = state;
        ValidateZip(zipCode);   ZipCode = zipCode;
    }
}

// 변경은 "새로 만들기"다
var a2 = new Address(a1.Line1, "Ann Arbor", "MI", 48103);
```

C# 10의 `record struct`와 `with` 식을 쓰면 이 패턴이 훨씬 간결해진다.

```csharp
public readonly record struct Address(string Line1, string City, string State, int ZipCode);

var a2 = a1 with { City = "Ann Arbor", State = "MI", ZipCode = 48103 };
```

> **📌 `record struct`와 `struct`는 메모리 관점에서 같다**
>
> `record struct`는 그냥 구조체다. 컴파일러가 `Equals`/`GetHashCode`/`ToString`/`Deconstruct`를 대신 써 줄 뿐이고, 그 중 `Equals`와 `GetHashCode`는 **리플렉션 기반 기본 구현(16.7절)보다 훨씬 빠른 필드별 비교 코드**를 생성한다. 메모리 관리 관점에서 `record struct`와 `struct` 사이에는 차이가 없다. 반대로 `record`(클래스)는 그냥 클래스다 — 힙에 간다.

> **⚠️ 불변 구조체 안의 가변 참조는 불변이 아니다**
>
> ```csharp
> public readonly struct PhoneList
> {
>     private readonly Phone[] _phones;
>     public PhoneList(Phone[] ph) => _phones = ph;
>     public IEnumerable<Phone> Phones => _phones;
> }
>
> Phone[] phones = new Phone[10];
> var pl = new PhoneList(phones);
> phones[5] = Phone.Generate();     // "불변" 구조체의 내용이 바뀌었다
> ```
>
> `readonly` 필드가 막는 것은 **참조의 재대입**이지 **가리키는 대상의 변경**이 아니다. 진짜로 불변이어야 한다면 생성자에서 방어적 복사를 하거나 `ImmutableArray<T>` / `ImmutableList<T>`(`System.Collections.Immutable`)를 써야 한다. 다만 방어적 복사 자체가 할당이라는 점을 잊지 마라 — 할당을 줄이려고 시작한 작업이 여기서 되돌아온다.

### 반례 — 구조체가 항상 이기지는 않는다

『High Performance C#』이 제시하는 벤치마크는 흥미로운 반전을 담고 있다. 참조 필드 유무에 따라 승자가 뒤집힌다.

| 상황 | 더 빠른 쪽 |
|---|---|
| 참조 필드가 **없는** 타입을 만들고 버리기 | **클래스**가 구조체보다 빠를 수 있다 |
| 참조 필드가 **있는** 타입을 만들고 버리기 | **구조체**가 클래스보다 빠르다 |

첫 줄이 직관에 어긋난다. 이유는 두 가지다. 작고 참조 없는 클래스는 **할당 빠른 경로(63.1절)가 포인터 하나를 미는 것으로 끝나고**, 0 채우기도 이미 되어 있다. 반면 구조체는 그 자리에서 필드별 초기화 코드가 돌고, 반환·전달마다 복사된다. 벤치마크의 반복 횟수가 GC를 한 번도 트리거하지 않을 만큼 적으면, **할당의 진짜 비용인 GC가 계산에 들어가지 않는다.**

> **⚠️ "구조체가 더 빠르다"를 벤치마크로 증명했다면 GC를 뺀 것이 아닌지 의심하라**
>
> 마이크로벤치마크는 대개 짧게 돌고, 짧게 돌면 세대 0 GC 몇 번으로 끝난다. 실제 서비스의 이득은 **초당 수천 번의 요청이 누적한 할당을 GC가 치우는 시간**에서 나온다. 67.5절의 `Gen0`/`Gen1`/`Gen2` 컬럼과 `Allocated` 컬럼을 Mean보다 먼저 봐야 하는 이유다. Mean이 같은데 Allocated가 40% 줄었다면, 그것은 **성공한 최적화**다.

### 전환 체크리스트

실무에서 쓰는 순서다.

1. 67.5절로 **어느 타입이 할당량 상위인지** 확인한다. 상위 3개 밖은 손대지 않는다.
2. 그 타입이 손익 계산표의 "치명" 칸에 하나라도 걸리는지 본다. 걸리면 중단하고 다른 기법(69.3, 69.4)으로 간다.
3. `readonly record struct`로 선언한다. `readonly`부터 시작해서, 정말 못 하겠을 때만 푼다.
4. 전달을 전부 `in`으로 바꾸고, 순회를 `ref` 지역 변수로 바꾼다.
5. IL을 확인해 `box` 명령이 남았는지 본다 (56장). 남았으면 그 호출 지점을 제네릭으로 바꾼다.
6. 재측정한다. `Allocated`가 줄었는데 `Mean`이 늘었다면 복사 비용에 진 것이다 — 4번으로 돌아간다.

## 69.2 `ValueTuple`과 `ValueTask`

두 타입은 이름이 비슷하고 목적도 비슷하다 — **참조 타입 하나를 구조체로 바꿔서 할당을 없앤다.** 하지만 함정의 성격은 완전히 다르다. `ValueTuple`의 함정은 설계 품질이고, `ValueTask`의 함정은 **정의되지 않은 동작**이다.

### `ValueTuple` — 힙에 안 가는 다중 반환

`Tuple<T1, T2>`와 익명 타입은 참조 타입이므로 **항상 힙에 만들어진다.** C# 7.0의 값 튜플은 구조체다. 기본 비교와 벤치마크(할당 88 B → 0 B, 4배 이상 빨라짐)는 63.10절에 있으므로 반복하지 않는다. 여기서는 **실무에서 걸리는 지점**만 본다.

```csharp
// 전부 힙 할당
var t1 = new Tuple<int, double>(0, 0.0);
var t2 = Tuple.Create(0, 0.0);
var t3 = new { A = 1, B = 0.0 };

// 힙 할당 없음
var t4 = (0, 0.0);
var t5 = (A: 0, B: 0.0);
t5.A = 3;                       // 값 튜플은 가변이다
```

#### 요소 이름은 런타임에 존재하지 않는다

`(A: 0, B: 0.0)`의 `A`, `B`는 **컴파일러가 아는 이름일 뿐** `ValueTuple<int, double>`의 필드 이름이 아니다. 실제 필드는 언제나 `Item1`, `Item2`다. 메서드 시그니처에 나타나는 이름은 `TupleElementNamesAttribute`로 메타데이터에 기록된다.

```csharp
public (int Count, double Average) Compute() => (3, 1.5);
```

```il
.method public hidebysig instance valuetype [System.Runtime]System.ValueTuple`2<int32, float64>
        Compute() cil managed
{
  .param [0]
  .custom instance void [System.Runtime]System.Runtime.CompilerServices.TupleElementNamesAttribute::.ctor(string[])
           = ( 01 00 02 00 00 00 05 43 6F 75 6E 74 07 41 76 65 72 61 67 65 00 00 )
  // ...
}
```

이 사실의 실무적 귀결이 셋이다.

- **리플렉션으로 요소 이름을 읽을 수 없다.** `GetFields()`는 `Item1`, `Item2`만 준다. 직렬화 라이브러리가 값 튜플을 잘 다루지 못하는 이유다.
- **`dynamic`으로 접근하면 이름이 안 통한다.** `dynamic d = (A: 1, B: 2); d.A`는 런타임 바인딩 실패다 (59장).
- **오버로드 해석에서 이름은 무시된다.** `(int A, int B)`와 `(int X, int Y)`는 같은 타입이다.

#### 8개를 넘으면 중첩된다

`ValueTuple`은 `ValueTuple<T1>`부터 `ValueTuple<T1,...,T7, TRest>`까지만 있다. 여덟 번째부터는 `TRest`에 또 다른 `ValueTuple`이 들어가는 **중첩 구조**가 된다.

```csharp
var big = (1, 2, 3, 4, 5, 6, 7, 8, 9);
// 실제 타입: ValueTuple<int,int,int,int,int,int,int, ValueTuple<int,int>>
// big.Item8은 컴파일러가 big.Rest.Item1로 번역한다
```

여전히 값 타입이므로 힙 할당은 없다. 하지만 **크기가 커지고 복사가 비싸진다.** 요소가 여덟 개를 넘어가면 손익 계산표의 "인스턴스 크기" 항목이 손해 칸으로 이동한다 — 그 지점이 전용 `readonly record struct`를 정의할 시점이다.

> **⚠️ 값 튜플을 `readonly` 필드에 담으면 방어적 복사가 생긴다**
>
> `ValueTuple<...>`은 **가변 구조체**다. 필드가 public이고 `readonly`가 아니다. 따라서 `readonly` 필드나 `in` 파라미터로 받은 값 튜플의 요소를 읽을 때마다 방어적 복사가 발생할 수 있다 (69.1절).
>
> ```csharp
> private readonly (long A, long B, long C, long D) _state;   // 32바이트
> public long Sum => _state.A + _state.B + _state.C + _state.D;  // 접근마다 복사 가능성
> ```
>
> 필드로 오래 들고 있을 데이터라면 값 튜플이 아니라 `readonly record struct`를 쓴다. **값 튜플은 메서드 경계를 넘는 일회용 컨테이너다.**

#### 딕셔너리 키로 쓸 때

값 튜플은 복합 키로 아주 유용하다. `Dictionary<(int, string), T>`는 익명 타입 키나 문자열 연결 키(`$"{a}:{b}"` — 매번 문자열 할당!)보다 압도적으로 낫다.

```csharp
// 나쁨 — 조회마다 문자열 할당
var bad = new Dictionary<string, Rate>();
var r1 = bad[$"{currency}:{tenor}"];

// 좋음 — 할당 0
var good = new Dictionary<(string Currency, int Tenor), Rate>();
var r2 = good[(currency, tenor)];
```

`ValueTuple`의 `Equals`와 `GetHashCode`는 각 요소의 것을 호출하도록 **컴파일러가 아니라 BCL이 직접 구현**해 두었다. 요소가 값 타입이면 박싱 없이 `EqualityComparer<T>.Default`를 타므로 안전하다.

### `ValueTask` — 세 가지 절대 금기

`ValueTask<T>`가 왜 존재하는지(동기 완료 시 `Task` 할당 회피), 어떻게 구현되어 있는지(`_obj`와 `_result` 두 필드의 판별 공용체), 언제 `Task`가 더 나은지(두 필드 복사 비용, `WhenAll` 사용 시 `AsTask()` 할당)는 63.9절과 47.13절에서 다뤘다. 여기서는 **오용의 결과**를 정확히 본다.

`ValueTask`가 위험한 이유는 하나다. **`ValueTask`가 감싼 `IValueTaskSource`는 풀링될 수 있고, 풀에 반납된 뒤에는 다른 작업이 그 인스턴스를 쓴다.** 그래서 다음 세 가지는 예외를 던지지 않고 **조용히 틀린 값을 준다.**

#### 금기 1 — 두 번 `await`

```csharp
ValueTask<int> vt = ReadAsync();
int a = await vt;      // OK
int b = await vt;      // 금지 — 정의되지 않은 동작
```

첫 `await`가 완료되는 순간 소스 인스턴스는 풀로 돌아갈 수 있다. 두 번째 `await`는 **이미 다른 작업이 사용 중인 인스턴스**의 상태를 읽는다. `InvalidOperationException`이 날 수도 있고, 다른 요청의 결과를 받을 수도 있다. 어느 쪽인지는 타이밍이 정한다.

두 번 필요하면 첫 번째에서 값을 저장하거나, `AsTask()`로 변환한다(그 순간 할당이 생기지만 안전하다).

```csharp
Task<int> t = ReadAsync().AsTask();   // 이제 몇 번이든 await 가능
```

#### 금기 2 — 완료 전 동기 대기

```csharp
ValueTask<int> vt = ReadAsync();
int x = vt.Result;                          // 완료 전이면 금지
int y = vt.GetAwaiter().GetResult();        // 같은 이유로 금지
```

`Task.Result`는 완료될 때까지 **블로킹한다.** `ValueTask.Result`는 **블로킹하지 않는다.** 미완료 상태에서 읽으면 결과가 정의되지 않는다. 유일하게 허용되는 형태는 `IsCompletedSuccessfully`를 먼저 확인하는 것이다.

```csharp
ValueTask<int> vt = ReadAsync();
if (vt.IsCompletedSuccessfully)
    return vt.Result;          // 안전 — 동기 완료 경로
return await vt;               // 그 외에는 반드시 await
```

`IsCompleted`가 아니라 **`IsCompletedSuccessfully`** 를 쓰는 것에 주의하라. `IsCompleted`는 실패·취소 상태에서도 `true`이고, 그 상태에서 `.Result`를 읽으면 예외 처리 경로가 달라진다.

#### 금기 3 — 저장하거나 여러 곳에 넘기기

```csharp
private ValueTask<int> _pending;       // 필드에 저장 — 금지
_pending = ReadAsync();
// ...한참 뒤...
var v = await _pending;                // 소스는 이미 재사용됐을 수 있다

var all = new List<ValueTask<int>>();  // 컬렉션에 모으기 — 금지
await Task.WhenAll(all);               // 애초에 컴파일도 안 된다
```

`ValueTask`는 **생성 직후 정확히 한 번 소비되는 일회용 값**이다. 여러 소비자에게 전달되거나, 수명이 호출 프레임을 넘어가면 안 된다.

> **⚠️ `ValueTask` 오용은 부하가 걸릴 때만 드러난다**
>
> 위 세 가지는 **동기 완료 경로에서는 대개 잘 동작한다.** `_obj`가 `null`이고 `_result`에 값이 들어 있는 상태라면 두 번 읽어도 같은 값이 나온다. 문제는 부하가 올라가 실제로 비동기 경로를 타고 풀링된 소스가 재사용되기 시작할 때다. **개발 환경과 스테이징에서는 멀쩡하고 프로덕션 피크에서만 데이터가 섞이는** 최악의 버그 유형이다.
>
> 정적 분석으로 잡을 수 있다. .NET SDK의 분석기 **CA2012 ("ValueTask instances should be consumed correctly")** 가 정확히 이 패턴을 경고한다. 이 규칙을 `warning`이 아니라 **`error`로 승격**해 두는 것을 권한다.
>
> ```xml
> <PropertyGroup>
>   <EnableNETAnalyzers>true</EnableNETAnalyzers>
> </PropertyGroup>
> <ItemGroup>
>   <!-- ValueTask 오용을 빌드 실패로 만든다 -->
>   <None Include="..." />
> </ItemGroup>
> ```
>
> `.editorconfig`에서는 `dotnet_diagnostic.CA2012.severity = error`로 지정한다.

### `ValueTask` 채택 판단표

| 상황 | 반환 타입 | 이유 |
|---|---|---|
| 캐시 적중률이 높은 조회 (`TryGetValue` 후 I/O) | **`ValueTask<T>`** | 동기 완료가 지배적 — 할당이 통째로 사라진다 |
| 버퍼가 차 있으면 즉시 반환하는 스트림 읽기 | **`ValueTask<int>`** | `Stream.ReadAsync`가 이미 이 시그니처다 |
| 항상 네트워크·디스크를 타는 연산 | `Task<T>` | 어차피 `Task`가 할당된다. 두 필드 복사만 손해 |
| 결과를 `WhenAll`/`WhenAny`에 모아야 함 | `Task<T>` | `AsTask()` 변환이 할당을 되살린다 |
| 공개 라이브러리 API의 범용 진입점 | `Task<T>` | 소비자가 오용할 여지를 주지 않는다 |
| 인터페이스 메서드 (구현체가 동기일 수 있음) | **`ValueTask`** | 동기 구현체가 `Task.CompletedTask` 없이 `default`를 반환 |

마지막 줄이 실무에서 가장 유용하다. `ValueTask`(제네릭 아닌 쪽)의 기본값은 **이미 완료된 상태**이므로, 동기 구현체는 이렇게 쓴다.

```csharp
public interface IHandler
{
    ValueTask HandleAsync(Message m, CancellationToken ct);
}

public sealed class SyncHandler : IHandler
{
    public ValueTask HandleAsync(Message m, CancellationToken ct)
    {
        Process(m);
        return default;      // 할당 0. Task.CompletedTask도 필요 없다
    }
}
```

> **📌 `async ValueTask` 메서드의 상태 기계도 풀링할 수 있다 ※.NET 6**
>
> `ValueTask`를 반환해도 **비동기 경로를 타면** 상태 기계 객체는 여전히 힙에 간다(63.9절). `[AsyncMethodBuilder(typeof(PoolingAsyncValueTaskMethodBuilder<>))]`를 메서드에 붙이면 그 상태 기계 객체까지 풀링된다.
>
> ```csharp
> [AsyncMethodBuilder(typeof(PoolingAsyncValueTaskMethodBuilder<>))]
> public async ValueTask<int> ReadAsync() { /* ... */ }
> ```
>
> 다만 풀링은 공짜가 아니다 — 대여·반납의 동기화 비용이 생기고, **소비자가 위의 세 금기를 어기면 오염의 파급 범위가 훨씬 커진다.** 진짜로 할당 프로파일 상위에 그 상태 기계가 올라와 있을 때만 붙여라.

### `IValueTaskSource`를 직접 구현할 것인가

`ValueTask`의 세 번째 형태다. 이것을 구현하면 **비동기 경로의 `Task` 할당까지 없앨 수 있다.** 완전히 동작하고 스레드 안전한 구현은 사소하지 않다는 경고는 63.9절에 있다. 여기에 실무 판단 하나만 덧붙인다.

**직접 구현하지 말고 `ManualResetValueTaskSourceCore<T>`를 감싸라.** 이것은 `System.Threading.Tasks.Sources`의 구조체이며, 상태 전이·연속 저장·`ExecutionContext` 흐름을 이미 처리해 준다.

```csharp
using System.Threading.Tasks.Sources;

internal sealed class PooledOperation : IValueTaskSource<int>
{
    private ManualResetValueTaskSourceCore<int> _core;   // 구조체 — 필드로 담는다

    public ValueTask<int> Task => new ValueTask<int>(this, _core.Version);

    // IValueTaskSource<int> 구현은 전부 위임한다
    public int GetResult(short token)
    {
        int result = _core.GetResult(token);
        _core.Reset();          // 다음 사용을 위해 초기화 — 여기서 Version이 올라간다
        Pool.Return(this);      // 그리고 풀로 돌아간다
        return result;
    }
    public ValueTaskSourceStatus GetStatus(short token) => _core.GetStatus(token);
    public void OnCompleted(Action<object?> cont, object? state, short token,
                            ValueTaskSourceOnCompletedFlags flags)
        => _core.OnCompleted(cont, state, token, flags);

    // 연산 완료 시 호출한다
    internal void Complete(int value) => _core.SetResult(value);
    internal void Fail(Exception e) => _core.SetException(e);
}
```

`_core.Version`이 앞서 말한 세 금기의 방어선이다. `Reset()`이 버전을 올리므로, 옛 `ValueTask`가 들고 있던 토큰으로 접근하면 `InvalidOperationException`이 난다 — **운이 좋으면** 그렇다. 인스턴스가 이미 다른 작업에 배정되고 버전이 한 바퀴 돌았다면 그마저도 안 난다.

> **⚠️ `ManualResetValueTaskSourceCore<T>`는 구조체이므로 복사하면 안 된다**
>
> `readonly` 필드로 선언하거나 프로퍼티로 노출하면 복사본이 만들어지고, 그 복사본에 `SetResult`를 호출해도 원본은 완료되지 않는다. **반드시 `private` 가변 필드로 두고, 모든 접근을 `ref`로 하거나 같은 클래스 안에서 직접 한다.** 이 타입에 `[StructLayout(LayoutKind.Auto)]`가 붙어 있고 문서가 "복사하지 말 것"을 명시하는 이유다.

## 69.3 `ArrayPool<T>`와 `MemoryPool<T>`

버퍼는 할당 최적화의 주전장이다. 크고(수 kB~수 MB), 수명이 짧고, 내용은 매번 덮어쓰므로 **재사용의 조건을 완벽하게 만족한다.** `ArrayPool<T>`의 구조 — 27개 버킷, 16요소부터 두 배씩, 요청 시 생성, ※.NET 5 트리밍, `ArrayPoolEventSource` 진단 — 는 63.10절과 65.10절에서 다뤘다. 이 절은 **쓰는 법과 틀리는 법**이다.

### 풀링 도구 4종 비교

| | `ArrayPool<T>.Shared` | `ArrayPool<T>.Create(...)` | `MemoryPool<T>.Shared` | `ObjectPool<T>` |
|---|---|---|---|---|
| **네임스페이스** | `System.Buffers` | `System.Buffers` | `System.Buffers` | `Microsoft.Extensions.ObjectPool` |
| **패키지** | BCL 내장 | BCL 내장 | BCL 내장 | NuGet |
| **빌려 주는 것** | `T[]` (요청보다 클 수 있음) | `T[]` (요청보다 클 수 있음) | `IMemoryOwner<T>` | `T` (임의 클래스) |
| **구현체** | `SharedArrayPool` (TLS + 파티션) | `ConfigurableArrayPool` (버킷만) | `ArrayMemoryPool` (내부적으로 `ArrayPool.Shared` 위임) | `DefaultObjectPool<T>` |
| **반환 의무** | `Return` 누락 = **조용한 성능 저하** | 동일 | `Dispose` 누락 = 동일 | `Return` 누락 = 동일 |
| **반환 누락의 결과** | 예외 없음. 풀이 비고 이후 `Rent`가 새 배열 할당 | 동일 | 동일 | 동일 |
| **스레드 안전성** | 안전. 스레드 지역 캐시로 무경합 경로 있음 | 안전. 락 기반, 경합 시 더 느림 | 안전 | 안전 (기본 구현) |
| **최대 크기** | 기본 상한 초과 시 그냥 새로 할당 | `maxArrayLength` 지정 | `MaxBufferSize` 프로퍼티 | 개념 없음 |
| **초기화 보장** | **없음.** 이전 내용이 그대로 있다 | 없음 | 없음 | 정책/`IResettable`에 위임 |
| **주 용도** | 범용 버퍼 (I/O, 인코딩, 직렬화) | 격리된 풀이 필요할 때 | 소유권을 넘겨야 할 때, `Memory<T>` API | 초기화가 비싼 객체 |
| **대표 함정** | `buffer.Length ≠ 요청 길이` | 전역 공유 안 됨 — 정적 필드로 잡아야 함 | `Memory`는 `Dispose` 후 무효 | 상태 초기화 누락 = 데이터 유출 |

핵심 판단은 두 갈래다. **바이트/문자 버퍼면 `ArrayPool`, 그 버퍼의 소유권이 메서드를 떠나면 `MemoryPool`, 버퍼가 아닌 객체면 `ObjectPool`.**

### 정석 패턴

```csharp
using System.Buffers;

public static int ProcessLine(ReadOnlySpan<char> input)
{
    char[] rented = ArrayPool<char>.Shared.Rent(input.Length);
    try
    {
        // (1) 항상 요청 길이로 슬라이싱해서 쓴다. rented.Length를 신뢰하지 않는다
        Span<char> buffer = rented.AsSpan(0, input.Length);
        input.ToUpperInvariant(buffer);
        return Count(buffer);
    }
    finally
    {
        // (2) 반드시 finally. (3) 민감 데이터면 clearArray: true
        ArrayPool<char>.Shared.Return(rented, clearArray: false);
    }
    // (4) 이 지점 이후 rented를 다시 읽으면 안 된다
}
```

네 개의 규칙이 전부 이 여덟 줄에 들어 있다.

**(1) `Rent`는 요청보다 큰 배열을 준다.** 512를 요청하면 1024짜리가 온다. `buffer.Length`를 데이터 길이로 쓰면 **초기화되지 않은 뒷부분까지 처리하는 버그**가 된다. 항상 실제 길이를 별도로 들고 다니거나, 위처럼 즉시 슬라이싱해서 `Span`으로만 접근한다.

> **💡 큰 배열을 받았으면 그것을 활용하라**
>
> 512바이트를 요청해 1024바이트를 받았다면, 복사 작업을 512 청크가 아니라 1024 청크로 수행하는 편이 낫다. 원서의 조언 그대로다. 실제 길이 검증이 필요 없는 순수 버퍼 용도(예: `Stream.Read`의 대상)라면 `rented.Length`를 그대로 넘기는 것이 옳다.

**(2) `Return`은 `finally`에.** 예외 경로에서 반납을 빠뜨리면 풀이 서서히 비고, 이후 모든 `Rent`가 새 배열 할당으로 폴백한다. **오류가 아니라 성능 저하로만 나타나므로 발견이 늦다.**

**(3) `clearArray`.** 기본값은 `false`다 — 즉 **다음에 이 배열을 빌리는 코드가 당신의 데이터를 볼 수 있다.**

| `clearArray` | 언제 | 비용 |
|---|---|---|
| `false` (기본) | 일반 바이트/문자 버퍼 | 0 |
| `true` | 비밀번호·토큰·복호화된 평문·개인정보를 담았을 때 | `Array.Clear` 한 번 |
| **필수 `true`** | 배열 원소가 **참조 타입**일 때 | 참조를 끊지 않으면 GC가 그 객체들을 계속 살려 둔다 |

> **⚠️ 참조 타입 배열을 풀링하면서 `clearArray: false`로 반납하면 메모리 누수다**
>
> `ArrayPool<MyClass>.Shared`에서 빌린 배열에 객체 100개를 채우고 그대로 반납하면, 그 배열은 풀 안에서 **100개 객체를 강하게 참조한 채로 살아 있다.** 풀 자체가 정적 수명이므로 그 객체들은 세대 2까지 승격되고 절대 수거되지 않는다.
>
> 66장에서 다룬 "풀에 붙잡힌 객체" 누수 유형이 정확히 이것이다. **원소가 참조 타입인 배열은 반드시 `clearArray: true`로 반납한다.** 값 타입 배열이면 성능상 `false`가 맞다.
>
> 참고로 `ArrayPool<T>.Shared.Return`은 `T`가 참조를 포함하는 타입이면 **`clearArray`가 `false`여도 지우도록** 구현되어 있는 버전이 있지만, **이 동작에 의존하지 마라.** 명시적으로 `true`를 넘기는 것이 계약이다.

**(4) 반납 후 참조 금지.** 이것이 풀링의 유일한 진짜 위험이다.

### 반납 후 사용 — 풀링의 use-after-free

```csharp
// 절대 하면 안 되는 코드
public Span<byte> BadRead(Stream s, int len)
{
    byte[] buf = ArrayPool<byte>.Shared.Rent(len);
    try   { s.ReadExactly(buf, 0, len); return buf.AsSpan(0, len); }
    finally { ArrayPool<byte>.Shared.Return(buf); }   // 반환값이 이미 무효다
}
```

관리 언어에서는 dangling pointer가 없지만, **풀링은 그 개념을 되살린다.** 배열 자체는 살아 있으므로 `NullReferenceException`도 `AccessViolationException`도 나지 않는다. 그냥 **다른 스레드가 지금 쓰고 있는 데이터**가 읽힌다.

증상은 이렇게 나타난다.

| 증상 | 원인 |
|---|---|
| 응답에 다른 사용자의 데이터가 섞임 | 반납 후 읽기 — 다른 요청이 같은 배열을 빌림 |
| 간헐적으로 JSON 파싱 실패 | 반납 후 쓰기 — 남의 버퍼를 덮어씀 |
| 부하가 낮을 때는 재현 안 됨 | 풀에 여유가 있으면 같은 배열이 즉시 재배정되지 않음 |
| `IndexOutOfRangeException`이 무작위 위치에서 | 이중 반납으로 같은 배열이 풀에 두 번 등록됨 |

> **⚠️ 이중 반납(double return)은 가장 찾기 어려운 풀 버그다**
>
> ```csharp
> byte[] buf = pool.Rent(n);
> try { Helper(buf, pool); }        // Helper 안에서도 Return을 호출한다면?
> finally { pool.Return(buf); }     // 두 번째 반납
> ```
>
> 같은 배열이 풀 안에 **두 번 등록**되면, 서로 다른 두 코드가 같은 배열을 "각자 자기 것"으로 빌려 간다. `ArrayPool`은 이 상황을 검출하지 않는다.
>
> 규칙은 단순하다. **빌린 곳에서만 반납한다.** 버퍼를 다른 메서드에 넘길 때는 절대 반납 책임을 함께 넘기지 않는다. 소유권을 넘겨야 한다면 `ArrayPool`이 아니라 `MemoryPool<T>`와 `IMemoryOwner<T>`를 쓴다 — 그쪽은 소유권이 타입으로 표현된다.

> **💡 디버그 빌드에서 대여를 추적하는 래퍼**
>
> 누수와 이중 반납을 잡으려면 `#if DEBUG`에서만 도는 추적 풀을 하나 두는 것이 효과적이다.
>
> ```csharp
> internal static class TrackedPool
> {
> #if DEBUG
>     private static readonly ConcurrentDictionary<byte[], string> Outstanding = new(ReferenceEqualityComparer.Instance);
> #endif
>     public static byte[] Rent(int n)
>     {
>         byte[] b = ArrayPool<byte>.Shared.Rent(n);
> #if DEBUG
>         if (!Outstanding.TryAdd(b, Environment.StackTrace))
>             throw new InvalidOperationException("풀이 같은 배열을 두 번 대여했다 — 이중 반납 흔적");
> #endif
>         return b;
>     }
>     public static void Return(byte[] b, bool clear = false)
>     {
> #if DEBUG
>         if (!Outstanding.TryRemove(b, out _))
>             throw new InvalidOperationException("빌리지 않은 배열을 반납했다 (또는 이중 반납)");
> #endif
>         ArrayPool<byte>.Shared.Return(b, clear);
>     }
> }
> ```
>
> `ReferenceEqualityComparer.Instance` ※.NET 5는 배열 내용이 아니라 **참조 동일성**으로 비교한다. 이 구분이 여기서는 필수다.

### 언제 풀이 이득인가

풀링에도 비용이 있다. `Rent`는 버킷 인덱스 계산 + 스레드 지역 슬롯 확인 + 실패 시 파티션 락 순으로 진행되고, 이것은 수십 나노초다. **작고 자주 쓰는 버퍼는 그냥 할당하는 편이 빠르다.**

| 버퍼 크기 | 권장 | 이유 |
|---|---|---|
| ~ 1 kB | `stackalloc` (68.9절) | 풀 조회 비용 > 할당 비용. 스택은 공짜 |
| 1 kB ~ 85 kB | 빈도에 따라 판단 | 초당 수천 번이면 풀, 아니면 그냥 할당 |
| 85 kB 이상 (LOH) | **거의 항상 풀** | LOH 할당은 0 채우기가 지배하고 압축도 안 된다 (63.4절) |
| 크기 예측 불가 | 상한 분기 + 풀 | `size <= 256 ? stackalloc : Rent` |

```csharp
// 크기가 런타임 값일 때의 정석
const int StackLimit = 256;

public int Encode(ReadOnlySpan<char> src, Span<byte> dst)
{
    int needed = Encoding.UTF8.GetMaxByteCount(src.Length);

    byte[]? rented = null;
    Span<byte> tmp = needed <= StackLimit
        ? stackalloc byte[StackLimit]
        : (rented = ArrayPool<byte>.Shared.Rent(needed));
    try
    {
        int written = Encoding.UTF8.GetBytes(src, tmp);
        tmp[..written].CopyTo(dst);
        return written;
    }
    finally
    {
        if (rented is not null) ArrayPool<byte>.Shared.Return(rented);
    }
}
```

이 패턴을 눈에 익혀 두라. BCL 내부 코드 어디를 열어도 이 형태가 나온다. **`stackalloc`을 조건부로 쓰되 삼항 연산자의 두 가지가 모두 `Span<byte>`로 수렴하고, 풀에서 빌렸을 때만 반납한다.**

> **⚠️ `stackalloc`을 삼항 연산자 밖으로 빼면 조건이 무력해진다**
>
> ```csharp
> // 잘못된 형태 — stackalloc이 항상 실행된다
> Span<byte> tmp = stackalloc byte[StackLimit];
> if (needed > StackLimit) tmp = ArrayPool<byte>.Shared.Rent(needed);
> ```
>
> 이 코드는 큰 버퍼가 필요한 경우에도 **스택 256바이트를 낭비한다.** 그것만이면 사소하지만, `StackLimit`을 크게 잡은 코드에서는 스택 압박이 실제 문제가 된다. 그리고 `stackalloc`이 루프 안에 있으면 반복마다 스택이 자라 `StackOverflowException`으로 죽는다 — 잡을 수 없는 예외다 (63.7절).

### `GC.AllocateUninitializedArray<T>` — 풀의 대안 ※.NET 5

풀을 쓰지 않고도 할당 비용의 절반을 없앨 수 있는 경우가 있다. 배열을 만들자마자 전부 덮어쓸 것이라면 **0 채우기를 생략**한다.

```csharp
// 일반 할당 — 런타임이 전체를 0으로 채운다
byte[] a = new byte[1_000_000];

// 0 채우기 생략 — 내용은 쓰레기다
byte[] b = GC.AllocateUninitializedArray<byte>(1_000_000);
stream.ReadExactly(b);      // 즉시 전부 덮어쓴다
```

LOH에 가는 큰 배열일수록 이득이 크다. 63.4절에서 본 대로 **LOH 할당 비용의 대부분이 0 채우기**이기 때문이다.

| 크기 | `new byte[n]` | `AllocateUninitializedArray` | 비고 |
|---|---|---|---|
| 1 kB | 차이 거의 없음 | 차이 거의 없음 | 할당 컨텍스트가 이미 0 |
| 100 kB | 유의미 | 더 빠름 | LOH 진입 |
| 10 MB | 수 ms | 크게 빠름 | 0 채우기가 지배 |

> **⚠️ `AllocateUninitializedArray`는 `[SkipLocalsInit]`과 같은 위험을 가진다**
>
> 반환된 배열에는 **이전에 그 메모리를 쓴 코드의 데이터**가 남아 있다. 전부 덮어쓰지 않은 채 그 배열을 외부로 내보내면 정보 유출이다. 69.8절에서 같은 논의를 다시 한다.
>
> 참고로 이 API는 **요청 크기가 작으면 그냥 0으로 채워진 배열을 돌려줄 수도 있다.** 런타임이 임계값 아래에서는 일반 경로를 타기 때문이다. "쓰레기가 들어 있을 것"이라고 가정하는 것도, "0일 것"이라고 가정하는 것도 둘 다 틀렸다. **전부 덮어쓴다**는 것만이 유효한 계약이다.

### `MemoryPool<T>` — 소유권이 타입에 나타난다

`MemoryPool<T>.Shared`가 돌려주는 것은 배열이 아니라 `IMemoryOwner<T>`다. 68.6절에서 본 대로 `MemoryPool<T>.Shared`의 기본 구현은 내부적으로 `ArrayPool<T>.Shared`를 감싼 얇은 래퍼다. 그러면 왜 존재하는가.

```csharp
// ArrayPool — 반납 책임이 계약에 없다. 주석으로만 존재한다
byte[] GetBuffer(int n);          // 이걸 누가 반납하나?

// MemoryPool — 반납 책임이 타입에 있다
IMemoryOwner<byte> GetBuffer(int n);   // 받은 쪽이 Dispose 한다
```

**소유권을 메서드 경계 밖으로 넘겨야 할 때 `MemoryPool`을 쓴다.** `IMemoryOwner<T>`는 `IDisposable`이므로 `using`이 강제되고, 분석기가 미폐기를 경고하고, 소유권 이전이 코드 리뷰에서 보인다.

```csharp
public sealed class ResponseBuffer : IDisposable
{
    private readonly IMemoryOwner<byte> _owner;
    public Memory<byte> Data { get; }

    public ResponseBuffer(int size)
    {
        _owner = MemoryPool<byte>.Shared.Rent(size);
        Data = _owner.Memory[..size];      // 요청 크기로 슬라이싱 — ArrayPool과 같은 규칙
    }

    public void Dispose() => _owner.Dispose();
}
```

> **⚠️ `Dispose` 이후의 `Memory<T>`는 무효다 — 그런데 예외가 안 난다**
>
> `IMemoryOwner<T>`를 `Dispose`한 뒤에도 그 전에 얻어 둔 `Memory<byte>` 값은 **여전히 유효한 배열을 가리킨다.** 그 배열은 이미 풀에 반납되었을 뿐이다. `ArrayPool`의 반납 후 사용과 정확히 같은 버그이며, 타입으로도 막지 못한다.
>
> **`IMemoryOwner<T>`를 담는 타입은 자신도 `IDisposable`이어야 하고, `Memory<T>` 프로퍼티는 `Dispose` 이후 접근을 방어해야 한다.** 68.13절의 소유권 가이드라인이 이 이야기다.

> **📌 `MemoryPool<T>` 최대 크기는 `ArrayPool`과 다르다**
>
> `MemoryPool<T>.Shared.MaxBufferSize`는 기본 구현(`ArrayMemoryPool<T>`)에서 배열 길이 상한(`Array.MaxLength`, 옛 버전에서는 `int.MaxValue`)을 보고한다 — 사실상 제한이 없다는 뜻이고, 요청이 크면 그냥 새로 할당한다. 실제 풀링 이득이 있는 크기는 그 아래에 있는 `ArrayPool<T>.Shared`의 버킷 범위에 달려 있다. `MaxBufferSize`를 "여기까지는 풀링된다"로 읽으면 안 된다.

### 커스텀 풀은 언제 필요한가

세 가지 경우에만 `ArrayPool<T>.Create`나 직접 만든 풀을 검토한다.

1. **격리가 필요할 때.** 라이브러리가 `Shared`를 오염시키는 것을 막고 싶거나, 특정 서브시스템의 풀 사용량을 독립적으로 계측하고 싶을 때.
2. **크기 분포가 극단적일 때.** `Shared`의 2의 거듭제곱 버킷은 항상 최대 2배를 낭비한다. 항상 정확히 4,096바이트만 쓴다면 전용 풀이 메모리를 아낀다.
3. **고정 크기 + 초고빈도.** 락 없는 단일 크기 스택 하나가 `SharedArrayPool`의 범용 로직보다 빠를 수 있다. 단, 이 판단은 **반드시 측정으로 뒷받침해야 한다.**

```csharp
// 격리된 풀은 반드시 정적 필드로 잡는다 — 매번 Create하면 풀이 아니다
private static readonly ArrayPool<byte> FramePool =
    ArrayPool<byte>.Create(maxArrayLength: 64 * 1024, maxArraysPerBucket: 64);
```

> **⚠️ `ArrayPool<T>.Create()`를 메서드 안에서 호출하면 풀이 아니다**
>
> `Create`는 **새 풀 인스턴스를 만든다.** 지역 변수로 만들어 쓰고 버리면 그 안의 배열은 전부 GC 대상이 되고, 결국 매 호출마다 새 배열을 할당하는 것과 같다. 게다가 풀 객체 자체의 할당까지 추가된다. **원래 코드보다 느리고 더 많이 할당한다.** 정적 필드가 아닌 곳에 `ArrayPool.Create`가 있으면 리뷰에서 반드시 잡아야 한다.

## 69.4 오브젝트 풀과 `RecyclableMemoryStream`

배열이 아닌 객체를 재사용하는 이야기다. 풀링을 고려해야 하는 세 시나리오 — 핫 패스, 비싼 초기화, 중년기 위기(mid-life crisis) — 는 63.10절에 정리되어 있다. 여기서는 **풀을 어떻게 만들고 어떻게 망가뜨리는가**를 본다.

### 좋은 오브젝트 풀은 왜 어려운가

단일 스레드라면 `Stack<T>` 하나면 끝난다. 어려운 것은 **동기화 오버헤드 없이 스레드 안전을 얻는 것**이고, 많은 순진한 구현이 원래의 할당보다 느리다. Roslyn 컴파일러의 `ObjectPool<T>`가 좋은 참고 구현이며, 원서가 그 코드를 인용한다.

```csharp
public class ObjectPool<T> where T : class
{
    private T firstItem;                  // 핵심: 첫 슬롯을 필드로 뺀다
    private readonly T[] items;
    private readonly Func<T> generator;

    public ObjectPool(Func<T> generator, int size)
    {
        this.generator = generator ?? throw new ArgumentNullException(nameof(generator));
        this.items = new T[size - 1];
    }

    public T Rent()
    {
        // PERF: 첫 원소만 먼저 본다. 실패하면 RentSlow가 나머지를 본다.
        // 최초 읽기를 의도적으로 동기화하지 않는다. 후보를 찾았을 때만 인터록한다.
        // 최악의 경우 최근에 반납된 객체를 놓칠 뿐이다 — 큰 문제가 아니다.
        T inst = firstItem;
        if (inst == null || inst != Interlocked.CompareExchange(ref firstItem, null, inst))
            inst = RentSlow();
        return inst;
    }

    public void Return(T item)
    {
        if (firstItem == null)
            firstItem = item;    // 의도적으로 인터록을 쓰지 않는다.
                                 // 최악의 경우 두 객체가 같은 슬롯에 저장되고,
                                 // 그중 하나가 그냥 수거될 뿐이다.
        else
            ReturnSlow(item);
    }

    private T RentSlow()
    {
        for (int i = 0; i < items.Length; i++)
        {
            T inst = items[i];
            if (inst != null && inst == Interlocked.CompareExchange(ref items[i], null, inst))
                return inst;
        }
        return generator();      // 풀이 비었으면 그냥 만든다
    }

    private void ReturnSlow(T obj)
    {
        for (int i = 0; i < items.Length; i++)
            if (items[i] == null) { items[i] = obj; break; }
    }
}
```

이 코드에서 배울 것은 세 가지다.

- **`firstItem` 필드 분리.** 대부분의 대여·반납은 배열을 스캔하지 않고 필드 하나만 만진다. 캐시 라인 하나로 끝난다.
- **동기화를 의도적으로 생략한 지점이 있다.** `Return`의 빠른 경로는 인터록이 없다. 경합하면 객체 하나를 잃을 뿐이고, **잃은 객체는 GC가 정상적으로 수거한다.** 풀의 정확성 요구가 낮다는 사실을 성능으로 바꾼 설계다.
- **풀이 비면 그냥 만든다.** 대기하지 않는다. 풀은 **최적화이지 자원 관리 메커니즘이 아니다.**

> **⚠️ 풀을 자원 관리로 착각하면 데드락을 만든다**
>
> "풀이 비었으면 반납될 때까지 기다린다"는 설계는 오브젝트 풀이 아니라 **세마포어**다. 그리고 대여자가 반납 전에 다른 대여를 시도하는 순간 데드락이 된다. 오브젝트 풀은 언제나 **비면 새로 만들고, 넘치면 버린다.** 자원 개수를 제한해야 한다면 그것은 별개의 관심사이고 `SemaphoreSlim`으로 따로 표현해야 한다.

### `Microsoft.Extensions.ObjectPool`

직접 만들지 말고 이것을 쓰라는 것이 63.10절의 결론이었다. 사용법을 정확히 본다.

```csharp
using Microsoft.Extensions.ObjectPool;

public sealed class Buffers : IResettable        // Microsoft.Extensions.ObjectPool 패키지
{
    public byte[] Data { get; } = new byte[4096];
    public int Length;

    public bool TryReset()
    {
        Length = 0;
        return true;      // false를 반환하면 이 인스턴스는 풀에 들어가지 않고 버려진다
    }
}

private static readonly ObjectPool<Buffers> Pool = ObjectPool.Create<Buffers>();

public static void DoSomeWork()
{
    Buffers instance = Pool.Get();
    try     { /* 작업 */ }
    finally { Pool.Return(instance); }
}
```

| 구성 요소 | 역할 |
|---|---|
| `ObjectPool<T>` | 추상 클래스. `Get()`과 `Return(T)` 두 메서드 |
| `ObjectPool.Create<T>()` | 기본 정책으로 풀 생성. `T`는 `new()` 제약 필요 |
| `ObjectPoolProvider` / `DefaultObjectPoolProvider` | DI 컨테이너에 등록해서 여러 풀을 만들 때 |
| `IPooledObjectPolicy<T>` | 생성 방법(`Create`)과 반납 허용 조건(`Return`) 커스터마이즈 |
| `IResettable` | `TryReset()`이 반납 시점에 자동 호출된다. 패키지 최신 버전에서만 제공되므로 참조 버전을 확인하라 |
| `StringBuilderPooledObjectPolicy` | `StringBuilder` 전용 기성 정책 |

`StringBuilder` 풀링은 워낙 흔해서 전용 정책이 준비되어 있다.

```csharp
private static readonly ObjectPool<StringBuilder> SbPool =
    new DefaultObjectPoolProvider().CreateStringBuilderPool(
        initialCapacity: 256, maximumRetainedCapacity: 4 * 1024);

public string Render(IReadOnlyList<Item> items)
{
    StringBuilder sb = SbPool.Get();
    try
    {
        foreach (Item i in items) sb.Append(i.Name).Append(';');
        return sb.ToString();
    }
    finally { SbPool.Return(sb); }    // 정책이 Clear()와 용량 검사를 대신 해 준다
}
```

`maximumRetainedCapacity`가 중요하다. 어쩌다 한 번 10 MB짜리 문자열을 만든 `StringBuilder`가 풀에 남아 **그 10 MB를 영구히 붙잡는 것**을 막는다. 이 한 줄이 커스텀 풀에서 가장 자주 빠지는 안전장치다.

> **⚠️ 풀링 대상이 상태를 남기면 데이터가 섞인다**
>
> 오브젝트 풀의 사고는 거의 전부 **초기화 누락**이다.
>
> ```csharp
> public sealed class RequestContext          // IResettable을 구현하지 않았다
> {
>     public string? UserId;
>     public List<string> Roles = new();
> }
> ```
>
> 이 객체를 풀에서 빌려 `UserId`만 채우고 `Roles`를 건드리지 않으면, **이전 요청의 역할 목록이 그대로 남아 있다.** 권한 상승 취약점이다. 반납 후 사용(69.3절)과 달리 이쪽은 코드가 완벽히 정상으로 보인다.
>
> 규칙 세 가지를 강제하라. **(1) 풀링 대상 타입은 반드시 `IResettable`을 구현한다. (2) `TryReset`은 모든 필드를 건드린다 — 새 필드를 추가할 때 여기도 고쳐야 한다. (3) 그 규칙을 지키는지 검증하는 단위 테스트를 쓴다.**
>
> ```csharp
> [Fact]
> public void TryReset_ClearsEveryField()
> {
>     var c = new RequestContext { UserId = "u1" };
>     c.Roles.Add("admin");
>     Assert.True(c.TryReset());
>
>     // 리플렉션으로 모든 인스턴스 필드가 기본값인지 확인한다.
>     // 필드가 추가되면 이 테스트가 먼저 깨진다.
>     foreach (var f in typeof(RequestContext).GetFields(
>                  BindingFlags.Instance | BindingFlags.Public | BindingFlags.NonPublic))
>     {
>         object? v = f.GetValue(c);
>         if (v is System.Collections.ICollection col) Assert.Empty(col);
>         else Assert.Equal(f.FieldType.IsValueType ? Activator.CreateInstance(f.FieldType) : null, v);
>     }
> }
> ```

> **📌 `IDisposable` 객체를 풀링하면 `Dispose`가 자동 호출된다**
>
> `Microsoft.Extensions.ObjectPool`의 기본 구현은 **풀이 가득 차서 인스턴스를 버릴 때** 그 객체가 `IDisposable`이면 `Dispose`를 호출한다. 반대로 말하면 **정상적으로 풀에 들어간 객체는 `Dispose`되지 않는다.** 파일 핸들이나 소켓처럼 결정적 해제가 필요한 자원을 담은 객체는 풀링 대상이 아니다.

### 풀링이 손해인 네 가지 경우

| 상황 | 왜 손해인가 |
|---|---|
| 객체가 작고 초기화가 싸다 | `Get`/`Return`의 동기화 비용 > 세대 0 할당 비용. 63.1절의 빠른 경로는 명령 예닐곱 개다 |
| 대여 수명이 길다 | 풀이 계속 비어 새로 만든다. 풀 조회 비용만 추가로 낸다 |
| 동시 대여 수가 풀 크기보다 훨씬 크다 | 대부분의 `Get`이 폴백 경로. "최선의 경우" 벤치마크가 거짓말하는 지점(63.10절) |
| 반납이 보장되지 않는 코드 구조 | 예외·조기 반환·비동기 취소 경로가 많으면 누락이 필연 |

> **⚠️ 벤치마크 결과의 이면**
>
> 63.10절에서 인용한 풀링 벤치마크(141 KB → 86 KB → 39 KB)는 **단일 스레드 최선의 경우**다. 수백 개의 동일 연산이 동시에 진행 중이면 그중 일부만 풀링된 배열을 얻고 **나머지는 풀 조회 비용을 내고도 결국 할당한다.** 풀링의 효과는 반드시 **실제 동시성 수준을 재현한 부하 테스트**에서 확인해야 한다. `[SimpleJob]` 하나짜리 마이크로벤치마크는 여기서 쓸모가 없다.

### `RecyclableMemoryStream`

`MemoryStream`의 네 가지 부작용(메모리 낭비·LOH 할당·복사·단편화)과 `RecyclableMemoryStreamManager`의 기본 사용법은 63.10절에 있다. 이 절은 **내부 구조와 실무 함정**이다.

```text
RecyclableMemoryStream 의 메모리 구조

   스트림 객체 (풀링 대상 아님 — 가벼운 래퍼)
        │
        ├─▶ 블록 리스트  ┌────────┬────────┬────────┬────────┐
        │                │ block0 │ block1 │ block2 │ block3 │  ← 균일 크기 (기본 128 kB)
        │                └────────┴────────┴────────┴────────┘     이것이 풀링된다
        │
        └─▶ (GetBuffer 호출 시에만) 대형 연속 버퍼
                          ┌───────────────────────────────────┐
                          │  largeBufferMultiple 의 배수 크기  │  ← 별도 풀
                          └───────────────────────────────────┘
```

핵심은 원서가 인용한 클래스 주석 그대로다. **"풀링되는 것은 스트림 객체 자체가 아니라 블록들이다."** 그리고 `GetBuffer()`가 호출되면 연속된 단일 버퍼가 필요하므로, 블록이 여러 개면 **대형 버퍼를 따로 빌려 전부 복사한다.**

> **⚠️ `GetBuffer()`와 `ToArray()`가 이 클래스를 쓰는 이유를 없앤다**
>
> - **`ToArray()`** 는 **항상 새 배열을 할당하고 전체를 복사한다.** 풀링의 이득이 통째로 사라진다. 크기가 85 kB를 넘으면 그 배열은 LOH로 간다 — 정확히 이 라이브러리를 도입해서 피하려던 상황이다.
> - **`GetBuffer()`** 는 할당은 피하지만, 블록이 여러 개일 때 **대형 버퍼로의 전체 복사**를 유발한다. 그리고 그 버퍼는 요청 크기보다 클 수 있으므로 `Length`를 데이터 길이로 쓰면 안 된다.
>
> 최선은 둘 다 쓰지 않는 것이다. `GetReadOnlySequence()`가 블록들을 `ReadOnlySequence<byte>`로 노출하므로, 소비자가 세그먼트를 순회하며 처리하면 복사가 0이다. `System.IO.Pipelines`(72.1절)와 `Utf8JsonReader`가 이 타입을 그대로 받는다.
>
> ```csharp
> using var ms = manager.GetStream("serialize");
> Serialize(ms, payload);
> ms.Position = 0;
>
> // 나쁨 — 전체 복사 + 새 할당
> byte[] bytes = ms.ToArray();
>
> // 좋음 — 복사 없음
> ReadOnlySequence<byte> seq = ms.GetReadOnlySequence();
> var reader = new Utf8JsonReader(seq);
> ```

`GetStream`에 태그 문자열을 넘길 수 있다는 점도 실무에서 유용하다.

```csharp
static readonly RecyclableMemoryStreamManager Manager = new(
    new RecyclableMemoryStreamManager.Options(
        blockSize:                 128 * 1024,
        largeBufferMultiple:      1024 * 1024,
        maximumBufferSize:  128 * 1024 * 1024,
        maximumSmallPoolFreeBytes: 0,
        maximumLargePoolFreeBytes: 0));

using var ms = Manager.GetStream(tag: "OrderExport");   // ETW 이벤트에 이 태그가 실린다
```

태그는 `Microsoft-IO-RecyclableMemoryStream` ETW 이벤트에 실려서, **어느 코드 경로가 풀을 고갈시키는지**를 스택 추적 없이도 알려 준다. GUID(`B80CD4E4-890E-468D-9CBA-90EB7C82DFC7`)로 활성화해야 한다는 함정은 63.10절에 있다.

> **⚠️ `Dispose`를 빠뜨리면 메모리가 풀로 돌아가지 않는다**
>
> `RecyclableMemoryStream`은 `Dispose` 시점에 블록을 반납한다. `using`을 빠뜨리면 그 블록들은 **파이널라이저가 돌 때까지** 풀 밖에 있고, 파이널라이저는 언제 돌지 모른다. 그 사이 풀은 계속 새 블록을 만든다.
>
> 파이널라이저가 도는 스트림은 `MemoryStreamFinalized` 이벤트로 드러난다(이중 해제는 `MemoryStreamDoubleDispose`다). **개발 환경에서는 `RecyclableMemoryStreamManager.Options.GenerateCallStacks`를 켜서 생성 지점의 스택 추적과 함께 잡아 두는 것이 좋다.** 스택 수집 비용이 크므로 프로덕션에서는 끈다.

> **💡 `maximumSmallPoolFreeBytes: 0`이 뜻하는 것**
>
> 63.10절에 인용한 설정에서 `maximumSmallPoolFreeBytes`와 `maximumLargePoolFreeBytes`가 둘 다 `0`이다. 이것은 **풀 크기 무제한**을 뜻한다. 부하가 튀는 순간 풀이 그만큼 커지고, 그 메모리는 프로세스가 죽을 때까지 반환되지 않는다.
>
> 컨테이너에서 메모리 한도가 걸려 있다면(65.5절의 힙 하드 리밋) 이 값을 반드시 유한하게 잡아야 한다. 풀이 상한을 넘으면 초과분은 풀링되지 않고 GC에 맡겨진다 — 느려지지만 죽지는 않는다. **무제한 풀은 "OOM으로 죽는 대신 조금 느려진다"는 선택지를 포기하는 설정이다.**

## 69.5 문자열 할당 제거 — `string.Create`, 보간 핸들러, `Span` 슬라이싱

문자열은 웹 애플리케이션 할당 프로파일의 상위를 거의 항상 차지한다. UTF-16이므로 문자당 2바이트이고, 불변이므로 조작할 때마다 새로 만들어지고, 로깅·직렬화·키 생성 등 어디에나 있다.

63.9절의 벤치마크 표는 **같은 문자열을 만드는 여섯 가지 방법**의 비용을 비교했다(`StringConcatenation` 368 B → `StringCreate` 56 B). 그 표의 마지막 세 행이 전부 56 B였던 것을 기억하라. **56 B는 최종 문자열 자체의 크기이고, 그 밑으로는 내려갈 수 없다.**

이 절의 목표는 그 하한 자체를 없애는 것이다. 즉 **문자열을 아예 만들지 않는다.** 단계는 셋이다.

| 단계 | 기법 | 없애는 것 | 남는 것 | 난이도 |
|---|---|---|---|---|
| **1단계** | 보간 핸들러 | 중간 버퍼, `params object[]`, 박싱 | 최종 문자열 | 낮음 — 대개 코드 변경조차 없다 |
| **2단계** | `string.Create` | 중간 버퍼 전부 | 최종 문자열 | 중간 — 길이를 미리 알아야 한다 |
| **3단계** | `Span` 슬라이싱 | **최종 문자열까지** | 없음 (0 B) | 높음 — 문자열 타입을 API에서 걷어내야 한다 |

### 1단계 — 보간 핸들러

C# 10부터 `$"..."`는 `string.Format` 호출이 아니라 **`DefaultInterpolatedStringHandler` 사용으로 컴파일된다.** 그 변환 결과와 스택 버퍼를 직접 주는 기법은 63.9절에 있다. 여기서는 **자기 핸들러를 만드는 경우**를 본다.

가장 큰 실무 이득은 **조건부 포매팅**이다. 로그 레벨이 꺼져 있으면 문자열을 만들지 않는 로거가 대표 사례다.

```csharp
using System.Runtime.CompilerServices;

public sealed class FastLogger
{
    public LogLevel MinLevel { get; init; } = LogLevel.Information;

    public void LogDebug([InterpolatedStringHandlerArgument("")] ref DebugHandler handler)
    {
        // handler.IsEnabled가 false면 handler는 아무것도 만들지 않았다
        if (handler.IsEnabled) Write(handler.ToStringAndClear());
    }

    private void Write(string s) => Console.Out.WriteLine(s);

    [InterpolatedStringHandler]
    public ref struct DebugHandler
    {
        private DefaultInterpolatedStringHandler _inner;
        public bool IsEnabled { get; }

        // literalLength/formattedCount는 컴파일러가 채운다.
        // logger는 InterpolatedStringHandlerArgument("")가 지정한 this다.
        // shouldAppend를 false로 두면 컴파일러가 AppendXxx 호출 자체를 건너뛴다.
        public DebugHandler(int literalLength, int formattedCount,
                            FastLogger logger, out bool shouldAppend)
        {
            IsEnabled = logger.MinLevel <= LogLevel.Debug;
            shouldAppend = IsEnabled;
            _inner = IsEnabled
                ? new DefaultInterpolatedStringHandler(literalLength, formattedCount)
                : default;
        }

        public void AppendLiteral(string s) => _inner.AppendLiteral(s);
        public void AppendFormatted<T>(T value) => _inner.AppendFormatted(value);
        public void AppendFormatted<T>(T value, string? format) => _inner.AppendFormatted(value, format);

        public string ToStringAndClear() => _inner.ToStringAndClear();
    }
}
```

호출부는 평범하다.

```csharp
logger.LogDebug($"user={userId} elapsed={sw.ElapsedMilliseconds:D6}ms");
```

Debug가 꺼져 있으면 **`userId`의 `ToString()`도, `long`의 포매팅도, 문자열 연결도 전혀 일어나지 않는다.** 컴파일러가 `shouldAppend`가 `false`일 때 `AppendLiteral`/`AppendFormatted` 호출을 통째로 건너뛰는 코드를 만들기 때문이다. 이것은 조건부 컴파일이 아니라 **런타임 분기**이므로, 로그 레벨을 실행 중에 바꿔도 동작한다.

| 구현 | Debug 꺼짐 상태에서 요청당 할당 |
|---|---|
| `logger.LogDebug(string.Format("user={0} elapsed={1}", u, ms))` | 문자열 + 박싱 2회 + `object[]` |
| `logger.LogDebug("user={0} elapsed={1}", u, ms)` (`params object[]`) | 박싱 2회 + `object[]` |
| 커스텀 핸들러 (위 코드) | **0 B** |

> **⚠️ `AppendFormatted<T>` 제네릭 오버로드를 반드시 제공하라**
>
> 핸들러에 `AppendFormatted(object value)`만 정의하면 **모든 값 타입 인자가 박싱된다.** 할당을 없애려고 만든 핸들러가 정확히 그 할당을 만든다. 반드시 제네릭 오버로드를 두고, 그 안에서 `DefaultInterpolatedStringHandler`의 제네릭 오버로드로 위임해야 한다. `DefaultInterpolatedStringHandler.AppendFormatted<T>`는 `T`가 `ISpanFormattable`이면 **`TryFormat`으로 버퍼에 직접 쓴다** — 중간 문자열도 박싱도 없다.

> **📌 `Microsoft.Extensions.Logging`은 이미 이렇게 되어 있다 ※.NET 8**
>
> `LoggerMessage.Define`과 소스 생성기 기반 `[LoggerMessage]` 특성이 같은 문제를 컴파일 타임에 푼다. 자기 로거를 만들 이유가 없다면 그쪽을 쓰는 편이 낫다. 위 코드는 **보간 핸들러 패턴 자체를 이해하기 위한 예제**이며, 로깅 말고도 어서션·진단 메시지·조건부 예외 메시지에 그대로 적용된다.

### 2단계 — `string.Create`

문자열을 만들긴 해야 하되 **중간 버퍼를 하나도 만들고 싶지 않을 때** 쓴다. 최종 문자열의 버퍼를 그 자리에서 직접 채운다.

```csharp
public static string Create<TState>(int length, TState state,
                                    System.Buffers.SpanAction<char, TState> action);
```

63.9절의 예제(정수 네 개를 `D4`로 이어 붙이기, 80 ns / 56 B)를 봤으므로, 여기서는 **실무에서 자주 나오는 세 형태**를 본다.

```csharp
// (a) 고정 형식 식별자 — 길이를 정확히 안다
public static string FormatOrderId(int region, long seq)
    => string.Create(3 + 1 + 12, (region, seq), static (span, s) =>
    {
        s.region.TryFormat(span[..3], out _, "D3");
        span[3] = '-';
        s.seq.TryFormat(span[4..], out _, "D12");
    });

// (b) 반복 — new string(char, int)로 안 되는 경우
public static string Repeat(ReadOnlySpan<char> unit, int times)
{
    // ReadOnlySpan은 ref struct라 TState가 될 수 없다 → 배열/문자열로 넘긴다
    string u = unit.ToString();
    return string.Create(u.Length * times, u, static (span, s) =>
    {
        for (int i = 0; i < span.Length; i += s.Length) s.AsSpan().CopyTo(span[i..]);
    });
}

// (c) 마스킹 — 원본을 복사한 뒤 일부만 바꾼다
public static string MaskCard(string number)
    => string.Create(number.Length, number, static (span, src) =>
    {
        src.AsSpan().CopyTo(span);
        if (span.Length > 4) span[..^4].Fill('*');
    });
```

세 예제 모두 람다에 **`static`을 붙였다.** 붙이지 않으면 캡처가 생겨 클로저 할당이 발생할 수 있고(63.9절), 그러면 `string.Create`를 쓴 이유가 사라진다. **`string.Create`의 델리게이트는 반드시 `static` 람다여야 한다.** 필요한 값은 전부 `TState`로 넘긴다.

> **⚠️ `string.Create`는 채우지 않은 문자를 그대로 남긴다**
>
> 63.9절에서 경고한 그대로다. `length`만큼의 버퍼가 주어지고, **전부 채우는 것은 호출자 책임이다.** 채우지 않은 위치에는 무엇이 들어 있는지 정의되지 않는다 — 힙에서 방금 재사용된 메모리의 내용일 수 있다.
>
> 방어책은 두 가지다. **길이 계산을 별도 함수로 분리해서 단위 테스트를 붙이거나**, 채우기 전에 `span.Fill(' ')`로 초기화하는 것이다. 후자는 비용이 들지만 정보 유출보다는 낫다.
>
> 특히 위험한 형태는 `TryFormat`의 반환값을 무시하는 코드다. `s.seq.TryFormat(span[4..], out _, "D12")`에서 `seq`가 13자리라면 `TryFormat`은 `false`를 반환하고 **아무것도 쓰지 않는다.** 버퍼 12칸이 초기화되지 않은 채 문자열이 된다. `out _`이 아니라 실제 결과를 검사해야 한다.

`string.Create`에는 **보간 핸들러를 받는 오버로드**도 있다 ※.NET 6. 길이를 미리 계산하지 않아도 되므로 훨씬 쓰기 쉽다.

```csharp
// 스택 버퍼를 주고, 넘치면 자동으로 풀에서 빌린다
Span<char> initial = stackalloc char[128];
string s = string.Create(CultureInfo.InvariantCulture, initial,
                         $"{region:D3}-{seq:D12}-{DateTime.UtcNow:yyyyMMdd}");
```

이 오버로드는 `DefaultInterpolatedStringHandler`가 초기 버퍼를 다 쓰면 **내부적으로 `ArrayPool<char>.Shared`로 확장한다.** 즉 정확한 길이를 모르면서도 중간 문자열 할당은 없다. 실무에서 2단계의 기본형으로 삼을 만한 것은 `string.Create<TState>`가 아니라 이쪽이다.

| 방법 | 길이를 알아야 하나 | 중간 할당 | 실수 위험 |
|---|---|---|---|
| `string.Format` | 아니오 | `object[]` + 박싱 + 중간 문자열 | 낮음 |
| `$"..."` (기본 핸들러) | 아니오 | 없음 (핸들러 내부 버퍼는 풀) | 낮음 |
| `string.Create(provider, buffer, $"...")` ※.NET 6 | 아니오 | 없음 | 낮음 |
| `string.Create<TState>(len, state, action)` | **예** | 없음 | **높음** — 미충전 버퍼 |

> **💡 `string.Create<TState>`는 마지막 수단이다**
>
> 표의 세 번째 행이 네 번째 행과 거의 같은 성능을 내면서 위험이 훨씬 낮다. **`string.Create<TState>`를 직접 쓸 이유는 "길이 계산이 자명하고 형식이 고정되어 있으며 초당 수십만 번 실행된다"는 조건이 다 맞을 때뿐이다.** 그 외에는 보간 핸들러 오버로드로 충분하다.

### 3단계 — `Span` 슬라이싱으로 문자열을 아예 만들지 않기

가장 큰 이득이자 가장 침습적인 변경이다. **`Substring`을 전부 없앤다.**

```csharp
// 이전 — Split이 배열 하나 + 문자열 N개
public static Config Parse(string line)
{
    string[] parts = line.Split('=');
    return new Config(parts[0].Trim(), int.Parse(parts[1]));
}

// 이후 — 할당 0 (Config가 구조체라면)
public static Config Parse(ReadOnlySpan<char> line)
{
    int eq = line.IndexOf('=');
    if (eq < 0) throw new FormatException("'=' 없음");
    ReadOnlySpan<char> key = line[..eq].Trim();
    ReadOnlySpan<char> val = line[(eq + 1)..];
    return new Config(key, int.Parse(val));    // int.Parse는 ReadOnlySpan<char> 오버로드가 있다
}
```

세 가지가 동시에 사라졌다. `Split`이 만드는 `string[]`, 각 조각의 `string`, `Trim()`이 만드는 새 `string`. `ReadOnlySpan<char>.Trim()`은 **슬라이스만 조정하므로 할당하지 않는다.**

`MemoryExtensions.Split` ※.NET 8을 쓰면 다중 분리도 할당 없이 된다.

```csharp
Span<Range> ranges = stackalloc Range[8];
int n = line.Split(ranges, ',', StringSplitOptions.TrimEntries);
for (int i = 0; i < n; i++)
{
    ReadOnlySpan<char> field = line[ranges[i]];
    // ...
}
```

`Range`는 구조체이고 `Span<Range>`는 스택에 있으므로 **전체 과정에 힙 할당이 0이다.** 분리 개수가 버퍼보다 많으면 마지막 `Range`에 나머지 전체가 들어간다 — 잘리지 않고 조용히 뭉쳐진다는 점을 기억하라.

줄 단위 처리에는 `EnumerateLines` ※.NET 6가 있다.

```csharp
foreach (ReadOnlySpan<char> line in text.AsSpan().EnumerateLines())
{
    // line은 슬라이스다. \r\n, \n, \r, 유니코드 줄 구분자를 모두 처리한다
}
```

#### 사전 조회에서 문자열 만들지 않기 ※.NET 9

3단계에서 가장 자주 막히는 지점이 **딕셔너리 키**다. `Dictionary<string, T>`에 `ReadOnlySpan<char>`로 조회할 방법이 오랫동안 없었고, 그래서 `span.ToString()`으로 되돌아가곤 했다.

```csharp
// 이 한 줄이 3단계의 노력을 전부 무효로 만든다
var value = map[key.ToString()];
```

.NET 9의 **대체 조회(alternate lookup)** 가 이 문제를 푼다.

```csharp
private static readonly Dictionary<string, Handler> Map = new(StringComparer.Ordinal);

public static Handler Find(ReadOnlySpan<char> key)
{
    var lookup = Map.GetAlternateLookup<ReadOnlySpan<char>>();
    return lookup[key];      // 문자열 할당 없음
}
```

`StringComparer.Ordinal`과 `StringComparer.OrdinalIgnoreCase`가 `IAlternateEqualityComparer<ReadOnlySpan<char>, string>`을 구현하기 때문에 가능하다. `HashSet<string>`, `ConcurrentDictionary<string, T>`도 같은 방식을 지원한다.

> **⚠️ 기본 비교자로 만든 딕셔너리는 대체 조회를 지원하지 않는다**
>
> `GetAlternateLookup<TAlternate>()`는 사전의 비교자가 `IAlternateEqualityComparer<TAlternate, TKey>`를 구현하지 않으면 **`InvalidOperationException`을 던진다.** `StringComparer.Ordinal`과 `OrdinalIgnoreCase`는 이를 구현하므로 안전하다.
>
> ```csharp
> // 안전 — 비교자를 명시한다
> var d = new Dictionary<string, int>(StringComparer.Ordinal);
> var lookup = d.GetAlternateLookup<ReadOnlySpan<char>>();
> ```
>
> 기본 비교자로 만든 `Dictionary<string, T>`가 지원되는지는 런타임 구현에 달려 있고 버전에 따라 달라질 수 있다. **대체 조회를 쓸 사전은 생성 지점에서 비교자를 명시하라** — 실패가 컴파일 오류가 아니라 런타임 예외이기 때문이다.
>
> ※.NET 9 미만이라면 대안은 두 가지다. 키를 미리 `enum`이나 정수 ID로 변환해 두거나, 조회 경로에서만 쓰는 커스텀 해시 테이블을 두는 것이다. 후자는 대개 과잉이다.

### 세 단계의 실측 대비

같은 작업 — `"region=EU;seq=42;ts=1717000000"` 형태의 문자열을 파싱해 `(string Region, int Seq, long Ts)`를 얻고, 그것을 `"EU/000042"` 형식의 키로 다시 만드는 것 — 을 네 가지로 구현했다. **아래 표의 비율은 단계별 이득의 상대 크기를 보이기 위한 [예시]이며 원천 도서의 측정값이 아니다.** 절대값은 입력 형태와 기계에 따라 달라지므로 반드시 자기 환경에서 재라.

| 구현 | Mean | Allocated | 무엇이 남았나 |
|---|---|---|---|
| `Split` + `string.Format` (기준) | 100% | 100% | 배열, 조각 문자열 3개, 포맷 중간물, 결과 문자열 |
| 1단계: `Split` + 보간 핸들러 | 약 80% | 약 55% | 배열, 조각 문자열 3개, 결과 문자열 |
| 2단계: `Split` + `string.Create` | 약 75% | 약 50% | 배열, 조각 문자열 3개, 결과 문자열 |
| 3단계: `Span` 슬라이싱 + `string.Create` | 약 30% | 약 12% | **결과 문자열만** |

숫자보다 중요한 것은 **어느 단계가 무엇을 없앴는가**다. 1·2단계는 출력 쪽만 손대므로 이득이 제한적이다. **입력 쪽의 `Split`과 `Substring`을 없애는 3단계가 이 표의 대부분을 만든다.** 실무에서 문자열 최적화를 시작한다면 순서를 뒤집어서 3단계부터 검토하는 편이 낫다.

> **⚠️ 문자열 캐시와 `string.Intern`은 할당 최적화가 아니다**
>
> "같은 문자열을 반복 생성한다면 캐시하면 되지 않나"는 자연스러운 발상이지만 두 가지 함정이 있다.
>
> - **`string.Intern`이 넣는 인턴 풀은 프로세스 수명 동안 절대 비워지지 않는다.** 사용자 입력이나 요청 데이터를 인턴하면 그것은 **되돌릴 수 없는 메모리 누수**다. 66장의 진단 시나리오에 자주 등장한다.
> - 직접 만든 `ConcurrentDictionary<string, string>` 캐시도 상한이 없으면 같은 문제다. 상한을 두면 이번엔 축출 정책과 락이 필요해지고, 그 비용이 문자열 할당 비용을 넘길 수 있다.
>
> 진짜 해법은 캐시가 아니라 **애초에 문자열을 만들지 않는 것**(3단계)이거나, 값 집합이 유한하다면 **`enum`이나 사전 정의된 상수로 바꾸는 것**이다.

## 69.6 `SearchValues<T>`와 최적화된 검색 ※.NET 8

68.4절에서 `SearchValues<T>`의 기본 사용법을 봤다. `SearchValues.Create`가 값 집합을 분석해 최적 구현을 고르고, `static readonly` 필드로 캐싱해야 의미가 있다는 것까지다. 이 절은 **그 분석이 무엇을 고르는지, 이득이 얼마인지, 언제 이득이 없는지**다.

### 왜 이 타입이 할당 줄이기 장에 있는가

`SearchValues<T>` 자체는 할당을 줄이지 않는다. 오히려 인스턴스 하나를 할당한다. 이 타입이 여기 있는 이유는 **그것이 없앨 수 있는 것** 때문이다.

| 없어지는 것 | 어떻게 |
|---|---|
| `string.Split` 배열과 조각 문자열 | 구분자 위치를 찾아 슬라이싱만 한다 (69.5절 3단계) |
| `Regex` 객체와 매치 결과 객체 | 단순 문자 집합 검색은 정규식이 필요 없다 |
| `char[]` 구분자 배열 | `IndexOfAny(char[])`는 매 호출마다 배열 리터럴을 만들 수 있다 |
| 검증 실패 경로의 예외·메시지 | 빠른 스캔으로 조기 거부 |

세 번째 항목이 흔히 간과된다.

```csharp
ReadOnlySpan<char> s = text;   // 아래 셋 모두 스팬에 대한 MemoryExtensions 확장이다

// 매 호출마다 char[3] 배열이 할당될 수 있다
int i = s.IndexOfAny(new[] { ',', ';', '\t' });

// 컴파일러가 정적 데이터로 굳히는 경우도 있으나 보장은 없다
int j = s.IndexOfAny(',', ';', '\t');      // 이 오버로드는 최대 3개까지만

// 확실한 방법
private static readonly SearchValues<char> Seps = SearchValues.Create(",;\t");
int k = s.IndexOfAny(Seps);
```

※ `string.IndexOfAny`에는 값 세 개짜리 오버로드가 없다. 위 형태를 쓰려면 `text.AsSpan()`으로 스팬을 먼저 얻어야 한다.

### 생성 시점에 무엇이 결정되는가

`SearchValues.Create`는 값 집합을 분석해 **서로 다른 내부 구현 클래스 중 하나를 인스턴스화한다.** 어떤 것이 선택되는지는 구현 세부 사항이고 버전마다 바뀌지만, 판단 축은 안정적이다.

| 값 집합의 성질 | 대략적인 전략 |
|---|---|
| 값이 1~5개 | 값별 비교를 벡터화해 한 번에 여러 문자와 대조 |
| ASCII 범위(0~127) 안 | **비트맵** — 128비트 테이블 조회. SIMD 셔플로 한 번에 16~32문자 |
| 연속 범위 (`'0'`~`'9'`) | **범위 비교** — 뺄셈 한 번과 부호 없는 비교 한 번 |
| ASCII를 넘는 넓은 집합 | 확률적 맵(probabilistic map) + 확인 단계 |
| `byte` 집합 | 위와 유사하되 256비트 테이블 |

요점은 **이 분석 비용을 생성 시점에 한 번만 내고 검색마다 재사용한다**는 것이다. 그래서 캐싱이 선택이 아니라 필수다.

> **⚠️ 메서드 안에서 `SearchValues.Create`를 호출하면 순손해다**
>
> ```csharp
> // 나쁨 — 호출마다 분석 + 테이블 구축 + 객체 할당
> bool HasSep(ReadOnlySpan<char> s) => s.IndexOfAny(SearchValues.Create(",;\t")) >= 0;
> ```
>
> 이 코드는 `IndexOfAny(',', ';', '\t')`보다 **느리고 더 많이 할당한다.** 짧은 입력에서는 차이가 몇 배까지 벌어진다. `SearchValues`는 "생성 1회, 검색 N회"의 N이 클 때만 이긴다.
>
> `static readonly` 필드로 두면 정적 생성자에서 한 번 만들어지고 프로세스 수명 내내 재사용된다. 68.4절의 팁이 이 절에서도 그대로 유효하다.

### 이득의 크기

정확한 배수는 입력 길이, 집합 크기, CPU의 SIMD 폭에 따라 달라진다. 경향은 이렇다.

| 상황 | `IndexOfAny(char[])` 대비 |
|---|---|
| 짧은 입력(< 16자), 작은 집합 | 거의 차이 없음 — 벡터화 이득이 나오기 전에 끝난다 |
| 중간 입력(수백 자), ASCII 집합 | 수 배 |
| 긴 입력(수 kB), ASCII 집합 | 한 자릿수 배수 이상 — 벡터 폭만큼 병렬 처리 |
| 큰 집합(수십 개 문자) | 차이가 가장 크다 — 순진한 구현은 집합 크기에 비례하지만 비트맵은 O(1) |

마지막 줄이 실무에서 가장 자주 걸린다. **HTTP 헤더 검증, URL 인코딩 대상 문자 판별, JSON 이스케이프 필요 문자 탐지** — 전부 "수십 개의 문자 집합 안에 있는가"를 긴 문자열에 대해 묻는 작업이다.

```csharp
// URL에서 인코딩해야 하는 문자 집합
private static readonly SearchValues<char> NeedsEncoding =
    SearchValues.Create(" \"<>#%{}|\\^~[]`;/?:@=&$+,!*'()");

public static string EncodeIfNeeded(string url)
{
    int i = url.AsSpan().IndexOfAny(NeedsEncoding);
    if (i < 0) return url;          // 흔한 경로 — 할당 0, 스캔 한 번
    return SlowEncode(url, i);      // 드문 경로에서만 버퍼를 만든다
}
```

이 패턴이 `SearchValues`의 진짜 가치다. **"손댈 필요가 없다"를 아주 빠르게 판정해서, 대부분의 입력에 대해 할당 경로 자체를 건너뛴다.** 문자열 인코딩·이스케이프·검증 코드는 거의 전부 이 형태로 다시 쓸 수 있다.

### `SearchValues<string>` ※.NET 9

.NET 9에서 문자열 집합 검색이 추가되었다.

```csharp
private static readonly SearchValues<string> Keywords =
    SearchValues.Create(["SELECT", "INSERT", "UPDATE", "DELETE"], StringComparison.OrdinalIgnoreCase);

int idx = sql.AsSpan().IndexOfAny(Keywords);
```

여러 후보 문자열을 동시에 찾는 다중 패턴 매칭이며, 생성 시점에 후보 집합의 성질(개수, 길이 분포, 공통 접두)에 따라 적절한 알고리즘을 고른다. 이것이 대체하는 것은 다음 두 가지다.

```csharp
// 이전 (1) — 후보 수만큼 전체 스캔. O(n × m)
foreach (string kw in keywords)
    if (sql.Contains(kw, StringComparison.OrdinalIgnoreCase)) { /* ... */ }

// 이전 (2) — 정규식. Regex 객체 + 매치 객체 할당
private static readonly Regex Rx = new("SELECT|INSERT|UPDATE|DELETE", RegexOptions.IgnoreCase);
if (Rx.IsMatch(sql)) { /* ... */ }
```

> **⚠️ `StringComparison`은 Ordinal 계열만 지원한다**
>
> `SearchValues.Create(values, comparisonType)`가 지원하는 것은 `Ordinal`과 `OrdinalIgnoreCase`뿐이다. `CurrentCulture`나 `InvariantCulture`를 넘기면 생성 시점에 인자 검증 예외가 난다.
>
> 이것은 제약이 아니라 **설계 의도**다. 문화권 인식 비교는 정규화·대조 테이블을 거쳐야 하므로 벡터화된 바이트 스캔과 양립할 수 없다. 사용자에게 보여 줄 텍스트의 정렬·비교에는 여전히 `StringComparer`가 필요하고, 프로토콜 토큰·키워드·헤더 이름처럼 **기계가 읽는 텍스트**에만 이 타입을 쓴다.

### 선택 기준표

| 하려는 일 | 도구 | 이유 |
|---|---|---|
| 문자 하나 찾기 | `span.IndexOf(c)` | 이미 벡터화되어 있다. `SearchValues`는 과잉 |
| 문자 2~3개 중 아무거나 | `span.IndexOfAny(a, b, c)` | 전용 오버로드가 있다 |
| 문자 4개 이상, 반복 호출 | **`SearchValues<char>`** | 캐싱한 비트맵이 이긴다 |
| 값 범위(`'0'`~`'9'`) | `IndexOfAnyInRange` ※.NET 8 | 범위 전용 API가 더 직접적 |
| 집합에 **없는** 첫 문자 | `IndexOfAnyExcept(sv)` ※.NET 8 | 검증에 유용 — "전부 허용 문자인가" |
| 여러 문자열 중 아무거나 | **`SearchValues<string>`** ※.NET 9 | 다중 패턴 매칭 |
| 실제 패턴(반복·그룹·역참조) | `[GeneratedRegex]` ※.NET 7 | `SearchValues`로 표현 불가능. 소스 생성기가 할당도 줄인다 |

> **💡 정규식이 필요한지 다시 물어라**
>
> 실무 코드의 정규식 상당수는 "문자 집합 검사"와 "고정 문자열 포함 검사"의 조합이다. 그 둘은 `SearchValues`와 `Contains`로 표현할 수 있고, **정규식 엔진의 매치 객체 할당이 통째로 사라진다.**
>
> 정말로 정규식이 필요하다면 최소한 `[GeneratedRegex]` 소스 생성기 ※.NET 7를 쓴다. 런타임 파싱과 인터프리터 대신 컴파일 타임에 C# 코드를 생성하고, `EnumerateMatches`로 `Match` 객체 없이 순회할 수 있다.
>
> ```csharp
> [GeneratedRegex(@"\d{4}-\d{2}-\d{2}")]
> private static partial Regex DatePattern();
>
> foreach (ValueMatch m in DatePattern().EnumerateMatches(input))
> {
>     ReadOnlySpan<char> found = input.AsSpan(m.Index, m.Length);   // 할당 없음
> }
> ```
> `ValueMatch`는 구조체이고 `EnumerateMatches`는 `ref struct` 열거자를 돌려준다. `Matches()`가 만드는 `MatchCollection`과 `Match` 객체 사슬이 전부 사라진다.

## 69.7 UTF-8 직접 다루기로 인코딩 변환 제거

63.9절 7번 항목에서 `u8` 리터럴, `Utf8.TryWrite`, `Utf8.FromUtf16`/`ToUtf16`, `OperationStatus`, 그리고 "버퍼를 키워 재시도하면 그 재시도가 곧 추가 할당"이라는 함정을 다뤘다. 이 절은 그 도구들로 **파이프라인 전체에서 변환을 없애는 방법**이다.

### 문제의 형태

.NET 문자열은 UTF-16이다. 그런데 바깥 세상은 대부분 UTF-8이다.

```text
   [네트워크]      [애플리케이션]        [네트워크]
   UTF-8 바이트 ──▶ string (UTF-16) ──▶ UTF-8 바이트
                    ↑              ↑
              변환 1: 할당       변환 2: 할당
              + 문자당 2배 메모리
```

HTTP 요청 하나를 처리하면서 헤더 이름 비교, 경로 라우팅, JSON 필드 이름 대조를 전부 `string`으로 하면 **입구에서 한 번 늘리고 출구에서 한 번 줄이는** 왕복 변환을 낸다. 요청당 수십 회다.

목표는 이 그림을 이렇게 바꾸는 것이다.

```text
   [네트워크]              [애플리케이션]                  [네트워크]
   UTF-8 바이트 ─────▶ ReadOnlySpan<byte> 로 직접 처리 ─────▶ UTF-8 바이트
                        비교·슬라이싱·파싱 전부 바이트 상태에서
                        변환은 "사람이 볼 텍스트"에서만
```

### 도구 1 — `u8` 리터럴 ※C# 11

```csharp
ReadOnlySpan<byte> contentType = "application/json"u8;
```

이 리터럴은 **어셈블리의 데이터 섹션에 UTF-8 바이트로 박혀 있다.** 런타임 할당도, 인코딩 변환도, 정적 생성자도 없다. `Encoding.UTF8.GetBytes("application/json")`이 매번 하던 일이 컴파일 타임으로 이동했다.

```csharp
// 헤더 이름 비교 — 문자열을 전혀 만들지 않는다
public static bool IsJson(ReadOnlySpan<byte> headerValue)
    => headerValue.StartsWith("application/json"u8);
```

> **⚠️ `u8` 리터럴은 `ReadOnlySpan<byte>`이지 `byte[]`가 아니다**
>
> 배열이 필요한 API에 넘기려면 `.ToArray()`를 불러야 하고 **그것이 할당이다.** `u8` 리터럴의 이득은 그 스팬을 스팬으로 받는 API에 그대로 넘길 때만 나온다.
>
> 그리고 `ref struct`이므로 필드로 저장할 수 없다(68.1절). 상수처럼 여러 곳에서 쓰려면 정적 프로퍼티로 노출한다 — **매번 같은 데이터 섹션을 가리키므로 비용이 없다.**
>
> ```csharp
> private static ReadOnlySpan<byte> JsonContentType => "application/json"u8;   // OK
> private static readonly ReadOnlySpan<byte> Bad = "x"u8;                       // 컴파일 오류
> ```

### 도구 2 — `IUtf8SpanFormattable` ※.NET 8

`ToString()` → `Encoding.UTF8.GetBytes()`의 두 단계를 한 단계로 줄인다. 기본 숫자 타입, `Guid`, `Version`, 날짜 관련 타입이 이 인터페이스를 구현한다.

```csharp
public interface IUtf8SpanFormattable
{
    bool TryFormat(Span<byte> utf8Destination, out int bytesWritten,
                   ReadOnlySpan<char> format, IFormatProvider? provider);
}
```

```csharp
Span<byte> buf = stackalloc byte[32];
if (value.TryFormat(buf, out int written, "F2", CultureInfo.InvariantCulture))
    socket.Send(buf[..written]);
// 중간 string도, GetBytes 호출도 없다
```

반대 방향은 `IUtf8SpanParsable<TSelf>` ※.NET 8이다. C# 12의 정적 추상 인터페이스 멤버 위에 만들어져 있어서 제네릭 코드에서 쓸 수 있다.

```csharp
static T ParseField<T>(ReadOnlySpan<byte> utf8) where T : IUtf8SpanParsable<T>
    => T.Parse(utf8, CultureInfo.InvariantCulture);
```

`System.Buffers.Text`의 `Utf8Formatter.TryFormat`/`Utf8Parser.TryParse`도 같은 일을 한다. 이쪽이 더 오래되었고 형식 지정자 표현이 다르다(`StandardFormat` 구조체). 새 코드는 인터페이스 쪽을 쓴다.

### 도구 3 — `Utf8.TryWrite`와 보간

여러 조각을 조립할 때는 보간 문자열을 UTF-8 버퍼에 직접 쓴다. `Utf8.TryWrite`는 ※.NET 8이다.

```csharp
using System.Text.Unicode;

int i1 = 1, i2 = 2, i3 = 3, i4 = 4;
Span<byte> utf8 = stackalloc byte[64];
if (Utf8.TryWrite(utf8, CultureInfo.InvariantCulture,
                  $"{i1:X4}.{i2:X4}.{i3:X4}.{i4:X4}", out int bytesWritten))
{
    Send(utf8[..bytesWritten]);
}
```

`Utf8.TryWrite`는 `TryWriteInterpolatedStringHandler`를 사용한다. 즉 **69.5절의 보간 핸들러 기법이 UTF-8 대상에 그대로 적용된 것**이다. 각 인자는 `IUtf8SpanFormattable`이면 바이트로 직접 포매팅되고, 아니면 UTF-16 경유 후 변환된다.

### 변환이 불가피할 때의 정석

애플리케이션 경계에서는 결국 변환해야 한다. 그때의 정석 패턴이다.

```csharp
public static void WriteUtf8(Stream dest, ReadOnlySpan<char> text)
{
    // (1) 최대 크기를 먼저 계산한다 — 재시도 경로를 아예 없앤다
    int max = Encoding.UTF8.GetMaxByteCount(text.Length);

    // (2) 작으면 스택, 크면 풀
    byte[]? rented = null;
    Span<byte> buf = max <= 256 ? stackalloc byte[256]
                                : (rented = ArrayPool<byte>.Shared.Rent(max));
    try
    {
        // (3) 스팬 오버로드 — 중간 배열이 없다
        int n = Encoding.UTF8.GetBytes(text, buf);
        dest.Write(buf[..n]);
    }
    finally
    {
        if (rented is not null) ArrayPool<byte>.Shared.Return(rented);
    }
}
```

63.9절이 지적한 "버퍼를 키워 재시도하면 그 재시도가 곧 추가 할당"이라는 함정을, **`GetMaxByteCount`로 상한을 먼저 잡아 원천 차단**한 것이다.

| 방법 | 재시도 가능성 | 중간 할당 |
|---|---|---|
| `Encoding.UTF8.GetBytes(string)` | 없음 | **결과 배열 1개** — 매번 |
| `Utf8.FromUtf16` + `Length + 1` 버퍼 | 높음 (비 ASCII에서) | 재시도 시 버퍼 재할당 |
| `Utf8.FromUtf16` + `GetMaxByteCount` 버퍼 | 없음 | 없음 (풀/스택) |
| `Encoding.UTF8.GetBytes(span, span)` | 없음 | 없음 |
| `Encoding.UTF8.TryGetBytes(span, span, out n)` ※.NET 8 | 없음 | 없음. 실패를 예외 대신 `false`로 |

> **⚠️ `GetMaxByteCount`는 문자당 3바이트가 아니다**
>
> `Encoding.UTF8.GetMaxByteCount(n)`은 대략 `3n + 3`을 돌려준다. 상한이므로 **거의 항상 과대 추정**이고, ASCII 문자열이라면 실제 필요량의 세 배를 잡는다. 짧은 문자열에서는 무해하지만, 1 MB 텍스트에 3 MB 버퍼를 빌리면 그 자체가 LOH 압박이다.
>
> 큰 입력에서는 `GetByteCount(text)`로 **정확한 크기를 먼저 계산**하는 편이 낫다. 입력을 한 번 더 스캔하는 비용이 들지만, 3배 버퍼를 잡는 것보다 싸다. 경계는 대략 수십 kB다 — 측정해서 정하라.

> **⚠️ 청크 경계에서 서로게이트 쌍을 자르면 데이터가 깨진다**
>
> 큰 텍스트를 조각내어 인코딩할 때, UTF-16 서로게이트 쌍(이모지, 일부 한자 확장 영역)의 상위·하위 유닛이 서로 다른 청크로 갈리면 **각 조각이 독립적으로는 유효하지 않은 시퀀스**가 된다. `Encoding.UTF8.GetBytes`는 이를 대체 문자(`U+FFFD`)로 바꿔 버리고, 두 조각을 합쳐도 원본은 복구되지 않는다.
>
> 해법은 상태를 유지하는 `Encoder`를 쓰는 것이다.
>
> ```csharp
> Encoder enc = Encoding.UTF8.GetEncoder();   // 청크 사이의 상태를 기억한다
> foreach (var chunk in chunks)
>     enc.Convert(chunk, buf, flush: false, out int used, out int written, out _);
> enc.Convert(ReadOnlySpan<char>.Empty, buf, flush: true, out _, out int tail, out _);
> ```
>
> `flush: false`가 핵심이다. 마지막 청크에서만 `true`를 준다. 같은 함정이 `Utf8.FromUtf16`에서는 `OperationStatus.NeedMoreData`로 나타난다 — 이 값을 오류로 취급해 버리는 코드가 흔하다.

### 어디까지 밀어붙일 것인가

파이프라인 전체를 바이트로 유지하는 것은 강력하지만 대가가 크다.

| 이득 | 대가 |
|---|---|
| 변환 할당 0, 메모리 사용 절반(ASCII 기준) | 디버거에서 `Span<byte>`는 숫자 배열로 보인다 |
| 복사·검증 단계 소멸 | 문자열 API를 전부 잃는다 — 비교·정렬·정규화 |
| `Utf8JsonReader`/`Writer`와 직결 | 문화권 인식 연산 불가 |
| 캐시 효율 향상 | 팀 전체가 이 스타일을 이해해야 한다 |

**경계를 정하는 것이 실무의 핵심이다.** 권장하는 선은 이렇다.

- **프로토콜 계층**(헤더 파싱, 라우팅, JSON 필드 이름, 토큰 대조) — 바이트로 유지한다.
- **도메인 계층**(비즈니스 로직, 검증 메시지, 사용자 데이터) — `string`으로 변환한다.
- **변환은 계층 경계에서 정확히 한 번.** 왔다 갔다 하면 안 하느니만 못하다.

> **💡 `System.Text.Json`은 이미 이 설계를 따른다**
>
> `Utf8JsonReader`는 `ReadOnlySpan<byte>`(또는 `ReadOnlySequence<byte>`)를 직접 읽고, `ValueTextEquals("name"u8)`로 **문자열을 만들지 않고** 프로퍼티 이름을 비교한다. `Utf8JsonWriter`는 `JsonEncodedText`로 미리 인코딩·이스케이프된 이름을 재사용한다.
>
> ```csharp
> private static readonly JsonEncodedText NameProp = JsonEncodedText.Encode("name");
>
> writer.WriteString(NameProp, value);   // 이름 인코딩·이스케이프가 매번 반복되지 않는다
> ```
>
> 직렬화가 할당 프로파일 상위에 있다면, 커스텀 `JsonConverter`를 이 두 도구로 다시 쓰는 것이 69장의 다른 어떤 기법보다 큰 이득을 낼 때가 많다.

## 69.8 `[SkipLocalsInit]`과 미세 최적화의 경계

여기서 이 장의 성격이 바뀐다. 앞의 일곱 절은 "할당을 없애는 법"이었고, 이 절은 **"어디서 멈춰야 하는가"** 다.

### `.locals init`이 하는 일

56장에서 본 대로, C# 컴파일러는 메서드마다 IL 헤더에 `init` 플래그를 붙인다.

```il
.method public hidebysig instance int32 Compute() cil managed
{
  .maxstack 2
  .locals init ([0] int32 sum, [1] valuetype Big data)   // init 플래그
  // ...
}
```

이 플래그를 보면 **JIT이 메서드 진입 시 지역 변수 영역 전체를 0으로 채우는 코드를 방출한다.** C#의 명확한 대입(definite assignment) 규칙이 있으므로 언어 수준에서는 불필요해 보이지만, 두 가지 이유로 존재한다. **`stackalloc` 버퍼가 0으로 채워지는 것을 보장하고**, 검증 가능(verifiable) IL의 요건을 만족시킨다.

`[SkipLocalsInit]` ※C# 9는 이 플래그를 끈다.

```csharp
using System.Runtime.CompilerServices;

[SkipLocalsInit]
public int Compute()
{
    Span<byte> buf = stackalloc byte[512];   // 더 이상 0으로 채워지지 않는다
    // ...
}
```

`<AllowUnsafeBlocks>true</AllowUnsafeBlocks>`가 필요하다는 점(60장), 그리고 초기화되지 않은 스택에는 직전에 그 프레임을 쓴 코드의 데이터가 남는다는 점(68.9절)은 이미 다뤘다.

### 언제 실제로 이득인가

이득의 크기는 **0으로 채워야 하는 스택 바이트 수**에 정비례한다.

| 메서드의 지역 변수 상황 | `[SkipLocalsInit]`의 효과 |
|---|---|
| 지역 변수가 `int` 몇 개 | **없음.** 레지스터에 배정되어 스택 프레임에 안 나온다 |
| 작은 구조체 두세 개 (합 64 B) | 거의 없음. `xorps` 몇 줄 |
| `stackalloc byte[1024]` | 측정 가능. 1 kB 0 채우기가 사라진다 |
| 큰 값 타입 지역 변수 (수백 B) | 측정 가능 |
| 위의 것들이 **아주 자주 호출되는 메서드에** 있을 때 | 유의미 |
| 위의 것들이 **드물게 호출되는 메서드에** 있을 때 | 무의미 — 측정 노이즈에 묻힌다 |

정리하면 조건이 둘 다 만족될 때만 이득이 있다. **(1) 스택 프레임이 크다(≥ 수백 바이트). (2) 그 메서드가 핫 패스에 있다.** 둘 중 하나라도 아니면 붙이지 마라.

> **⚠️ `[SkipLocalsInit]`은 할당을 줄이지 않는다**
>
> 이 특성은 이 장에서 유일하게 **힙 할당과 무관한** 기법이다. 스택 초기화 명령을 없앨 뿐이고, `Allocated` 컬럼은 1바이트도 바뀌지 않는다. 할당 프로파일을 보고 이 특성을 붙이는 것은 진단과 처방이 어긋난 것이다. 이것이 겨냥하는 것은 **CPU 시간**이고, 확인해야 할 것은 `Mean`과 디스어셈블리다(67.4절).

### 위험 — 세 가지 유출 경로

```csharp
// 위험 1 — 부분만 채우고 전체를 내보낸다
[SkipLocalsInit]
public byte[] MakeToken()
{
    Span<byte> buf = stackalloc byte[32];
    RandomNumberGenerator.Fill(buf[..16]);   // 앞 16바이트만 채웠다
    return buf.ToArray();                     // 뒤 16바이트는 이전 프레임의 데이터
}
```

```csharp
// 위험 2 — TryFormat 실패를 무시한다
[SkipLocalsInit]
public string Format(long v)
{
    Span<char> buf = stackalloc char[8];
    v.TryFormat(buf, out int n);      // 실패해도 n은 0, buf는 그대로 쓰레기
    return new string(buf);            // n을 안 쓰고 전체를 문자열로 만든다
}
```

```csharp
// 위험 3 — 조건부로만 채운다
[SkipLocalsInit]
public void Handle(Request r)
{
    Span<byte> key = stackalloc byte[16];
    if (r.HasKey) r.CopyKeyTo(key);
    Cache.Store(key);                  // HasKey가 false면 이전 요청의 키가 저장된다
}
```

세 경우 모두 **컴파일 오류도 예외도 없다.** 그리고 세 경우 모두 `[SkipLocalsInit]`이 없으면 0이 들어가서 아무 일도 안 일어난다. **특성 하나를 붙이는 것으로 정상 코드가 취약점으로 바뀐다.**

> **⚠️ `[module: SkipLocalsInit]`은 거의 항상 잘못된 선택이다**
>
> 모듈 전체나 어셈블리 전체에 거는 형태는 "전 메서드에서 미세 이득"을 노리지만, 실제로는 **위 세 가지 실수가 어디에 있는지 아무도 모르는 상태**를 만든다. 그리고 이득의 대부분은 스택 프레임이 큰 소수의 메서드에서 나오므로, 전역 적용의 추가 이득은 거의 0이다.
>
> 규칙은 하나다. **측정으로 이득이 확인된 개별 메서드에만 붙인다.** 60장과 68.9절이 같은 결론에 도달했고, 이 절도 같다. 그리고 붙인 메서드에는 반드시 주석으로 이유와 측정값을 남긴다 — 6개월 뒤 그 메서드를 고칠 사람이 `stackalloc` 버퍼가 0이 아니라는 사실을 알아야 한다.
>
> ```csharp
> // [SkipLocalsInit]: 이 메서드는 요청당 4회 호출되고 stackalloc 4 kB를 쓴다.
> // 제거 시 처리량 -3.1% (2026-03 측정). buf는 아래에서 전체가 채워진다.
> [SkipLocalsInit]
> internal static int Encode(...)
> ```

### 할당 회피가 손해인 경우

이 장 전체에 대한 반대 신문이다. 다음 목록의 어느 하나에라도 해당하면 **최적화를 하지 않는 것이 옳은 결정**이다.

#### 1. 조기 최적화 — 측정이 그 코드를 지목하지 않았다

63.9절이 인용한 문장 그대로다. **1분에 한 번 실행되는 코드가 800바이트 대신 200바이트를 할당하는 것은 중요하지 않다.** 할당 프로파일 상위 몇 개 밖의 코드를 손대는 것은 순수한 손실이다 — 시간을 쓰고, 코드를 복잡하게 만들고, 버그 가능성을 늘리고, 얻는 것은 없다.

**판정 기준**: 67.5절의 `MemoryDiagnoser` 또는 프로파일러가 그 메서드를 상위 5개 안에 올려놓았는가. 아니면 손대지 않는다.

#### 2. 가독성 손실이 이득보다 크다

```csharp
// 이전 — 누구나 읽는다
public IEnumerable<string> ActiveNames(List<User> users)
    => users.Where(u => u.IsActive).Select(u => u.Name);

// 이후 — 할당 몇 백 바이트를 아꼈다
public int ActiveNames(ReadOnlySpan<User> users, Span<Range> outNames, ReadOnlySpan<char> pool)
{
    // ...40줄...
}
```

두 번째 코드가 정당화되는 유일한 상황은 **이 메서드가 초당 수십만 번 실행되고, 그것이 측정으로 확인되었을 때**다. 그 외의 경우 이것은 팀 전체의 유지보수 비용을 올리는 변경이다.

**판정 기준**: 이 변경을 리뷰하는 동료에게 5분 안에 설명할 수 있는가. 없다면 주석으로 벤치마크 결과를 남기거나, 하지 않는다.

#### 3. 풀 관리 버그의 기대 비용이 더 크다

69.3·69.4절의 함정 목록을 다시 보라. 반납 누락(조용한 성능 저하), 반납 후 사용(데이터 오염), 이중 반납(무작위 예외), 상태 초기화 누락(권한 상승). **이 중 세 개는 프로덕션 피크에서만 나타나고 재현이 어렵다.**

풀링으로 절약하는 것이 요청당 몇 kB인데 그 대가로 이런 버그 등급을 감수하는 것은 나쁜 거래다. 풀링은 **절약량이 크고(≥ 요청당 수십 kB, 또는 LOH 대상), 대여·반납 경로가 단순할 때** 도입한다.

**판정 기준**: 대여와 반납이 같은 메서드의 `try`/`finally` 안에 들어가는가. 그렇지 않다면 재검토한다.

#### 4. 수명 오류 — 스팬과 스택 메모리의 탈출

```csharp
// 컴파일러가 막아 주는 경우
Span<byte> Bad() { Span<byte> s = stackalloc byte[16]; return s; }   // CS8352

// 막아 주지 못하는 경우
unsafe void Worse()
{
    byte* p = stackalloc byte[16];
    _pending = p;            // 필드에 저장 — 프레임이 사라지면 dangling
}
```

`ref struct`의 규칙(68.1절)과 `scoped`(68.11절)가 안전한 경우를 크게 넓혔지만, `unsafe`를 섞거나 풀링된 버퍼를 비동기 경계 너머로 넘기면 **컴파일러의 보호를 벗어난다.**

가장 흔한 형태는 이것이다.

```csharp
// 위험 — await 이후에도 buf를 쓴다
async Task Handle(Stream s)
{
    byte[] buf = ArrayPool<byte>.Shared.Rent(4096);
    try
    {
        int n = await s.ReadAsync(buf);
        await Downstream(buf, n);       // 이 안에서 예외 → catch에서 buf 반납?
    }
    finally { ArrayPool<byte>.Shared.Return(buf); }
}
```

이 코드 자체는 옳다. 문제는 `Downstream`이 `buf`의 참조를 **저장하거나 다른 태스크에 넘길 때** 생긴다. `finally`가 반납한 뒤에도 그 태스크가 배열을 읽는다. 비동기 코드에서 풀링된 버퍼의 소유권은 **동기 코드보다 훨씬 추적하기 어렵다.**

**판정 기준**: 빌린 버퍼가 `await`를 넘어가는가. 넘어간다면 `IMemoryOwner<T>`로 소유권을 명시하거나(69.3절), 아예 풀링하지 않는다.

#### 5. 런타임이 이미 하고 있다

```csharp
// 이 "최적화"들은 대개 무의미하다
list.Capacity = list.Count;             // 배열을 새로 할당한다. 줄이려던 것을 늘렸다
GC.Collect();                            // 65.8절 — 거의 언제나 해롭다
var sb = new StringBuilder();            // 두세 조각 연결에는 + 가 낫다 (63.9절)
string.Intern(userInput);                // 되돌릴 수 없는 누수 (69.5절)
```

**판정 기준**: 이 최적화가 BCL의 내부 동작과 반대 방향인가. 그렇다면 BCL 소스를 먼저 읽는다.

## 69.9 핫 패스에서 힙 할당을 0으로 만들기 — 실전 케이스

지금까지의 기법을 **하나의 함수**에 순서대로 적용한다. 각 단계마다 무엇이 사라지는지 `Allocated` 컬럼으로 확인하고, 마지막에 0 B에 도달한다. 그다음 "그래서 여기까지 올 필요가 있었나"를 따진다.

### 대상 — 액세스 로그 집계

입력은 한 줄에 다섯 필드가 공백으로 구분된 텍스트다.

```text
2026-09-05T10:11:12Z GET /api/orders/42 200 137
2026-09-05T10:11:12Z GET /api/users/7 200 2481
2026-09-05T10:11:13Z POST /api/orders 201 64
2026-09-05T10:11:13Z GET /static/logo.png 304 0
```

요구 사항은 **경로의 첫 세그먼트별로, 상태 코드 계열(2xx/3xx/4xx/5xx)별 바이트 합계**를 구하는 것이다. 초당 수만 줄이 들어오는 수집기의 내부 루프이며, 67.5절의 프로파일이 이 함수를 할당 1위로 지목했다는 전제에서 시작한다.

### V0 — 평범한 구현

```csharp
public sealed record LogEntry(DateTime Ts, string Method, string Path, int Status, int Bytes);

public static Dictionary<string, long> AggregateV0(string[] lines)
{
    var result = new Dictionary<string, long>();
    foreach (string line in lines)
    {
        LogEntry? e = ParseV0(line);
        if (e is null) continue;

        string seg = e.Path.Split('/', StringSplitOptions.RemoveEmptyEntries)
                           .FirstOrDefault() ?? "";
        string key = string.Format("{0}/{1}xx", seg, e.Status / 100);
        result[key] = result.GetValueOrDefault(key) + e.Bytes;
    }
    return result;
}

private static LogEntry? ParseV0(string line)
{
    string[] parts = line.Split(' ');
    if (parts.Length != 5) return null;
    return new LogEntry(DateTime.Parse(parts[0]), parts[1], parts[2],
                        int.Parse(parts[3]), int.Parse(parts[4]));
}
```

읽기 쉽고, 정확하고, 관용적이다. **그리고 한 줄당 열 개 이상을 할당한다.**

### 할당 출처 분해

먼저 세는 것부터 한다. 최적화하기 전에 **어디서 몇 바이트가 나오는지** 목록으로 만든다.

| # | 출처 | 종류 | 줄당 개수 | 근거 |
|---|---|---|---|---|
| 1 | `line.Split(' ')` | `string[]` | 1 | 63.10절 — 배열 할당 |
| 2 | `Split`이 만든 조각 문자열 | `string` | 5 | 각 조각이 새 문자열 |
| 3 | `new LogEntry(...)` | `record` = 클래스 | 1 | 63.9절 — 명시적 할당 |
| 4 | `e.Path.Split('/')` | `string[]` | 1 | 두 번째 분리 |
| 5 | 경로 조각 문자열 | `string` | 2~3 | |
| 6 | `FirstOrDefault()` | 열거자 (배열이면 없음) | 0~1 | 63.10절 — LINQ 열거자 |
| 7 | `string.Format` | `object[]` + 박싱 | 2 | `params object[]`와 `int` 박싱 (63.9절) |
| 8 | `string.Format` 결과 | `string` | 1 | 최종 키 |
| 9 | `Dictionary` 성장 | 버킷 + 엔트리 배열 | 상각 | 63.10절 — 용량 미지정 |
| 10 | `DateTime.Parse` | 내부 임시 | 경우에 따라 | 실제로는 쓰지도 않는다 |

10번이 눈에 띈다. **`Ts` 필드는 어디서도 사용되지 않는다.** 파싱 자체가 불필요한 일이다. 할당 분해의 첫 이득은 대개 기법이 아니라 **"이거 왜 하고 있지"** 에서 나온다.

측정 환경은 이렇게 잡는다. **이하 V0~V4 표의 수치는 이 워크스루가 무엇을 없애는지를 보이기 위한 [예시]다** — 원천 도서에 있는 측정값이 아니므로 인용하지 말고, 같은 벤치마크를 자기 기계에서 돌려 자기 숫자를 얻어라.

### V1 — 파싱을 `Span` 슬라이싱으로

첫 번째 수술은 `Split` 두 개와 `record` 하나를 없애는 것이다(69.5절 3단계, 69.1절).

```csharp
// record(클래스) → readonly ref struct. 힙에 가지 않고 슬라이스만 들고 있다
public readonly ref struct LogView
{
    public readonly ReadOnlySpan<char> Method;
    public readonly ReadOnlySpan<char> Path;
    public readonly int Status;
    public readonly int Bytes;

    private LogView(ReadOnlySpan<char> m, ReadOnlySpan<char> p, int s, int b)
        { Method = m; Path = p; Status = s; Bytes = b; }

    public static bool TryParse(ReadOnlySpan<char> line, out LogView v)
    {
        v = default;
        Span<Range> f = stackalloc Range[6];               // ※.NET 8 — 할당 없는 분리
        if (line.Split(f, ' ') != 5) return false;

        // f[0]은 타임스탬프 — 쓰지 않으므로 파싱하지 않는다
        if (!int.TryParse(line[f[3]], out int status)) return false;
        if (!int.TryParse(line[f[4]], out int bytes))  return false;

        v = new LogView(line[f[1]], line[f[2]], status, bytes);
        return true;
    }

    // 경로의 첫 세그먼트 — 새 문자열을 만들지 않고 슬라이스로 돌려준다
    public ReadOnlySpan<char> FirstSegment
    {
        get
        {
            ReadOnlySpan<char> p = Path.TrimStart('/');
            int slash = p.IndexOf('/');
            return slash < 0 ? p : p[..slash];
        }
    }
}
```

집계 쪽은 아직 문자열 키를 쓴다.

```csharp
public static Dictionary<string, long> AggregateV1(string[] lines)
{
    var result = new Dictionary<string, long>(64, StringComparer.Ordinal);
    foreach (string line in lines)
    {
        if (!LogView.TryParse(line, out LogView e)) continue;
        string key = $"{e.FirstSegment}/{e.Status / 100}xx";     // 아직 문자열을 만든다
        result[key] = result.GetValueOrDefault(key) + e.Bytes;
    }
    return result;
}
```

사라진 것: 1, 2, 3, 4, 5, 6, 10번. 남은 것: 7·8번(키 문자열)과 9번(딕셔너리 — 이제 용량을 지정했으므로 상각).

보간 문자열이 `string.Format`을 대체하면서 `object[]`와 박싱도 함께 사라졌다(69.5절 1단계). `ReadOnlySpan<char>` 인자는 `DefaultInterpolatedStringHandler.AppendFormatted(ReadOnlySpan<char>)` 오버로드로 직접 복사된다.

| 메서드 | Mean | Gen0 | Gen1 | Allocated |
|---|---|---|---|---|
| V0 | 4.12 ms | 476.5625 | 46.8750 | 3,914 KB |
| **V1** | 1.31 ms | 74.2188 | 0 | **609 KB** |

**할당이 16%로, 시간이 32%로 줄었다.** Gen1이 0이 된 것에 주목하라 — 승격되는 객체가 사라졌다는 뜻이고, 이것은 `Mean`보다 훨씬 중요한 신호다(64장).

> **⚠️ `ref struct`를 반환하는 `TryParse`는 입력 스팬보다 오래 살 수 없다**
>
> `LogView`가 들고 있는 것은 `line`의 슬라이스다. `line`이 배열이나 풀링 버퍼를 가리키고 있고 그것이 반납되면, `LogView`의 필드는 남의 데이터를 가리킨다(69.3절). 컴파일러의 `ref safety` 규칙(68.11절)이 지역 변수 수준에서는 막아 주지만, **비동기 경계와 풀 반납은 막지 못한다.**
>
> 규칙: **`LogView`는 `TryParse`를 호출한 그 루프 반복 안에서만 산다.** 밖으로 나가야 할 값은 그 자리에서 값 타입으로 뽑아낸다.

### V2 — 키 문자열 제거

남은 609 KB는 전부 키 문자열이다. 줄마다 `"orders/2xx"` 같은 문자열을 만들고, 딕셔너리에서 조회한 뒤 버린다. **이미 사전에 있는 키를 조회하기 위해 문자열을 만드는 것**은 순수한 낭비다.

두 가지를 바꾼다. 상태 코드 계열을 문자열에서 빼서 **배열 인덱스**로 만들고, 세그먼트 조회에 **대체 조회**(69.5절, ※.NET 9)를 쓴다.

```csharp
public struct StatusBuckets            // 2xx/3xx/4xx/5xx + 그 외
{
    public long S2xx, S3xx, S4xx, S5xx, Other;

    public void Add(int status, int bytes)
    {
        switch (status / 100)
        {
            case 2: S2xx += bytes; break;
            case 3: S3xx += bytes; break;
            case 4: S4xx += bytes; break;
            case 5: S5xx += bytes; break;
            default: Other += bytes; break;
        }
    }
}

public static Dictionary<string, StatusBuckets> AggregateV2(
    string[] lines, Dictionary<string, StatusBuckets> result)
{
    var lookup = result.GetAlternateLookup<ReadOnlySpan<char>>();   // ※.NET 9

    foreach (string line in lines)
    {
        if (!LogView.TryParse(line, out LogView e)) continue;
        ReadOnlySpan<char> seg = e.FirstSegment;

        // 이미 있는 키면 문자열을 만들지 않는다
        if (lookup.TryGetValue(seg, out StatusBuckets b))
        {
            b.Add(e.Status, e.Bytes);
            lookup[seg] = b;
        }
        else
        {
            var nb = default(StatusBuckets);
            nb.Add(e.Status, e.Bytes);
            result[seg.ToString()] = nb;      // 최초 1회만 문자열 할당
        }
    }
    return result;
}
```

두 가지 설계 결정이 들어 있다.

- **`result`를 인자로 받는다.** 호출자가 사전을 재사용하므로 딕셔너리 할당이 루프 밖으로 나갔다. 값이 `StatusBuckets` 구조체이므로 사전 안에 인라인으로 저장된다 — 항목당 객체가 없다.
- **최초 등장 시에만 `seg.ToString()`.** 서로 다른 세그먼트가 유한개(수십~수백)이므로, 워밍업 이후에는 **문자열 할당이 0**이다.

| 메서드 | Mean | Gen0 | Gen1 | Allocated |
|---|---|---|---|---|
| V0 | 4.12 ms | 476.5625 | 46.8750 | 3,914 KB |
| V1 | 1.31 ms | 74.2188 | 0 | 609 KB |
| **V2** | 0.71 ms | 0 | 0 | **1.6 KB** |

**Gen0이 0이 되었다.** 남은 1.6 KB는 첫 실행에서 만들어지는 세그먼트 문자열들이다. 벤치마크가 같은 사전을 반복 사용하므로 실제로는 첫 번째 반복에서만 발생하고, BenchmarkDotNet이 그것을 반복 횟수로 나눠 보고한다.

> **⚠️ 구조체 값을 사전에서 꺼내 고치고 다시 넣는 것은 두 번의 해시 계산이다**
>
> ```csharp
> lookup.TryGetValue(seg, out StatusBuckets b);   // 해시 1회
> b.Add(...);                                      // 복사본을 수정
> lookup[seg] = b;                                 // 해시 2회
> ```
>
> 값 타입이므로 `b`는 복사본이다. 다시 넣지 않으면 갱신이 사라진다 — **조용히 틀린 결과**다.
>
> `Dictionary<TKey, TValue>`라면 `CollectionsMarshal.GetValueRefOrAddDefault` ※.NET 6로 해시 한 번에 참조를 얻을 수 있다.
>
> ```csharp
> ref StatusBuckets slot = ref CollectionsMarshal.GetValueRefOrAddDefault(result, key, out _);
> slot.Add(e.Status, e.Bytes);       // 제자리 수정. 해시 1회
> ```
>
> 다만 이 API는 `ReadOnlySpan<char>` 키를 받지 않으므로, **대체 조회와 조합할 수 없다.** V2에서는 문자열 할당 제거를 우선했다. 어느 쪽이 이기는지는 "새 키 비율"이 정한다 — 측정 없이 고르지 마라. 그리고 `ref`를 얻은 뒤 사전에 항목을 추가하면 그 `ref`가 무효가 된다는 점도 주의하라.

### V3 — 입력 자체를 통짜 버퍼로

아직 `string[] lines`가 남아 있다. 이 배열과 그 안의 1만 개 문자열은 **호출자가 만든 것**이고, 우리 함수의 `Allocated`에는 잡히지 않지만 시스템 전체로는 존재한다. 로그는 파일이나 소켓에서 오므로 애초에 통짜 버퍼로 받는 것이 자연스럽다.

```csharp
public static void AggregateV3(ReadOnlySpan<char> blob, Dictionary<string, StatusBuckets> result)
{
    var lookup = result.GetAlternateLookup<ReadOnlySpan<char>>();

    foreach (ReadOnlySpan<char> line in blob.EnumerateLines())     // ※.NET 6
    {
        if (!LogView.TryParse(line, out LogView e)) continue;
        ReadOnlySpan<char> seg = e.FirstSegment;

        if (lookup.TryGetValue(seg, out StatusBuckets b)) { b.Add(e.Status, e.Bytes); lookup[seg] = b; }
        else { var nb = default(StatusBuckets); nb.Add(e.Status, e.Bytes); result[seg.ToString()] = nb; }
    }
}
```

`EnumerateLines`는 `ref struct` 열거자를 돌려주므로 열거자 할당도 없다(68.7절의 전방 전용 열거자 패턴이 BCL에 들어간 형태다).

이제 호출 사슬 전체가 이렇게 된다.

```csharp
// 파일에서 읽어 그대로 넘긴다 — 중간 string[] 없음
char[] rented = ArrayPool<char>.Shared.Rent(charCount);
try
{
    int n = ReadIntoBuffer(rented);
    AggregateV3(rented.AsSpan(0, n), _result);
}
finally { ArrayPool<char>.Shared.Return(rented); }
```

### V4 — 출력도 할당 없이

마지막 남은 문자열은 결과를 렌더링할 때 생긴다.

```csharp
// 이전 — 항목마다 문자열 여러 개
foreach (var (k, v) in result)
    sb.AppendLine(string.Format("{0,-16} 2xx={1,10} 4xx={2,10}", k, v.S2xx, v.S4xx));

// 이후 — 중간 문자열 0, 최종 버퍼에 직접
public static int Render(Dictionary<string, StatusBuckets> result, Span<char> dest)
{
    int pos = 0;
    foreach (var (k, v) in result)
    {
        if (!dest[pos..].TryWrite(CultureInfo.InvariantCulture,
                $"{k,-16} 2xx={v.S2xx,10} 4xx={v.S4xx,10}\n", out int written))
            return -1;      // 버퍼 부족 — 호출자가 키워서 재시도
        pos += written;
    }
    return pos;
}
```

`MemoryExtensions.TryWrite` ※.NET 6는 `Utf8.TryWrite`(69.7절)의 UTF-16 판이며, 같은 보간 핸들러 메커니즘을 쓴다. 위 코드가 쓴 `IFormatProvider`를 함께 받는 오버로드는 ※.NET 8이다. 결과를 UTF-8로 바로 내보낼 것이라면 `Utf8.TryWrite`에 `Span<byte>`를 주면 되고, 그러면 인코딩 변환까지 사라진다.

### 최종 결과

| 메서드 | Mean | Gen0 | Gen1 | Allocated | 없앤 것 |
|---|---|---|---|---|---|
| V0 | 4.12 ms | 476.5625 | 46.8750 | 3,914 KB | — |
| V1 | 1.31 ms | 74.2188 | 0 | 609 KB | `Split` 배열·조각, `record`, LINQ, 불필요한 `DateTime.Parse` |
| V2 | 0.71 ms | 0 | 0 | 1.6 KB | 키 문자열, 딕셔너리 재할당 |
| V3 | 0.68 ms | 0 | 0 | **0 B** | 입력 `string[]`과 줄 문자열 |
| V3 + Render | 0.70 ms | 0 | 0 | **0 B** | 출력 문자열 |

**할당 3,914 KB → 0 B, 시간 4.12 ms → 0.70 ms.** 시간이 6배 빨라진 것의 상당 부분은 할당 그 자체가 아니라 **GC가 돌지 않게 된 것**과 **데이터 지역성**에서 온다. V0은 1만 개의 작은 객체를 힙 여기저기에 만들고 순회했고, V3은 연속된 `char` 버퍼 하나만 훑는다(70장).

### 0 B를 검증하는 테스트

벤치마크는 회귀를 막아 주지 않는다. **단위 테스트로 고정한다.**

```csharp
[Fact]
public void AggregateV3_AllocatesNothing_WhenKeysAreWarm()
{
    var result = new Dictionary<string, StatusBuckets>(64, StringComparer.Ordinal);
    string blob = TestData.Blob(1000);

    AggregateV3(blob, result);          // 워밍업 — 여기서 세그먼트 문자열이 만들어진다

    long before = GC.GetAllocatedBytesForCurrentThread();
    AggregateV3(blob, result);          // 두 번째 호출은 할당이 없어야 한다
    long after = GC.GetAllocatedBytesForCurrentThread();

    Assert.Equal(0, after - before);
}
```

`GC.GetAllocatedBytesForCurrentThread()`는 현재 스레드가 시작 이후 할당한 누적 바이트를 준다(63.10절). **정확한 값이며 샘플링이 아니다.** 이런 테스트를 CI에 넣어 두면(67.8절) 누군가 `Path.ToString()` 한 줄을 추가하는 순간 빌드가 깨진다.

> **⚠️ 이 테스트는 Release 빌드에서만 유효하다**
>
> Debug 빌드는 인라이닝을 하지 않고, 지역 변수를 스택에 유지하며, 일부 컴파일러 최적화가 꺼져 있다. 그리고 `ref struct` 관련 최적화도 달라질 수 있다. **할당 어서션 테스트는 반드시 Release 구성에서 돌려야 한다.** `[Fact(Skip = ...)]`로 Debug에서 건너뛰거나, CI의 Release 잡에서만 실행하도록 카테고리를 분리하라.
>
> 또 하나 — 다른 스레드가 이 스레드에 영향을 주지 않지만, **테스트 프레임워크가 같은 스레드에서 무언가를 할당하면** 값이 오염된다. 어서션 사이에는 측정 대상 호출만 두어야 한다.

### 여기까지 올 필요가 있었나

정직한 회고가 필요하다. 각 단계의 **이득 대비 비용**은 이렇다.

| 단계 | 할당 감소 | 코드 복잡도 증가 | 위험 | 판정 |
|---|---|---|---|---|
| V0 → V1 | 84% | 중간 (`ref struct` 도입) | 낮음 | **거의 항상 할 만하다** |
| V1 → V2 | 15%p (누적 99.96%) | 중간 (사전 재사용, 값 갱신 패턴) | 중간 (구조체 갱신 누락) | **핫 패스라면 할 만하다** |
| V2 → V3 | 나머지 (호출자 쪽 포함하면 큼) | 높음 (API 시그니처가 전파된다) | 중간 (버퍼 수명) | **입출력 경계까지 통제할 수 있을 때만** |
| V3 → Render | 0 (출력은 원래 드물다) | 높음 | 높음 (`TryWrite` 실패 처리) | **출력이 핫 패스일 때만** |

V0 → V1이 이득의 대부분을 만든다. **그 한 단계만 하고 멈추는 것이 대부분의 코드에서 옳은 결정이다.** V2 이후는 이 함수가 정말로 서비스의 병목일 때, 그리고 그 사실이 프로파일러로 확인되었을 때 간다.

> **💡 최적화를 어디서 멈출지는 숫자가 아니라 요구사항이 정한다**
>
> "할당 0"은 목표가 아니라 결과다. 목표는 언제나 67.1절에서 정한 것 — 처리량 목표, p99 지연 시간 목표, 메모리 상한 — 이고, 그 목표를 이미 만족했다면 V2에서 멈추는 것이 옳다. **남은 1.6 KB를 0으로 만드는 데 쓸 시간이 있다면, 그 시간에 다른 병목을 찾는 것이 거의 언제나 이득이 크다.**
>
> 반대로 목표를 만족하지 못했는데 이 장의 기법을 다 써도 안 된다면, 문제는 할당이 아니다. 알고리즘이거나(70장), 동시성이거나(65장), 애초에 아키텍처다. **할당 최적화가 답이 아닌 문제에 할당 최적화를 계속 적용하는 것**이 이 장의 가장 큰 실패 모드다.

## 이 장의 요약

- **구조체 전환은 "16바이트 미만"이 아니라 손익 계산표로 판단한다.** 크기·복사 빈도·박싱 위험·컬렉션 저장·가변성·참조 필드 유무·캐시 지역성·수명·다형성 요구 아홉 항목 중 하나라도 치명 칸에 걸리면 하지 않는다. 참조 필드가 0개인 구조체는 쓰기 장벽(64.11절)까지 없애므로 이득이 가장 크다.
- **구조체 전환의 1차 효과는 속도가 아니라 GC 압력 감소다.** 클래스 기반 로직을 구조체로 옮긴 실측에서 `Mean`은 348.8 us → 344.7 us로 거의 그대로였지만 `Allocated`는 62.60 KB → 39.13 KB로 줄었다. 마이크로벤치마크가 이 이득을 과소평가한다.
- **`ValueTask`의 세 금기는 두 번 `await`, 완료 전 동기 대기, 저장·공유다.** 셋 다 예외를 던지지 않고 조용히 틀린 값을 주며, 부하가 올라가 풀링된 소스가 재사용될 때만 드러난다. `CA2012`를 `error`로 승격하는 것이 유일한 실효적 방어다.
- **풀링 도구는 용도로 고른다** — 버퍼면 `ArrayPool`, 소유권을 넘기면 `MemoryPool`, 버퍼가 아닌 객체면 `ObjectPool`, 스트림이면 `RecyclableMemoryStream`. 공통 계약은 하나다: `try`/`finally`로 반납하고, 요청 길이로 슬라이싱하고, **반납 후에는 절대 참조하지 않는다.**
- **참조 타입 원소의 배열은 `clearArray: true`로 반납해야 한다.** 그러지 않으면 정적 수명의 풀이 그 객체들을 영구히 붙잡는다. 반대로 값 타입 배열에 `true`를 주는 것은 순수한 비용이다.
- **문자열 제거는 세 단계다** — 보간 핸들러(중간 버퍼·박싱 제거), `string.Create`(중간 버퍼 전부 제거), `Span` 슬라이싱(최종 문자열까지 제거). **이득의 대부분은 3단계, 즉 입력 쪽의 `Split`과 `Substring`을 없애는 데서 나온다.** ※.NET 9의 대체 조회가 3단계의 마지막 장벽이던 사전 키 문제를 푼다.
- **`SearchValues<T>`는 반드시 `static readonly` 필드로 캐싱한다.** 메서드 안에서 `Create`를 호출하면 `IndexOfAny(char[])`보다 느리고 더 많이 할당한다. 진짜 가치는 "손댈 필요 없음"을 빠르게 판정해서 **할당 경로 자체를 건너뛰는 것**이다.
- **인코딩 변환은 없애는 것이 최선이다.** `u8` 리터럴·`IUtf8SpanFormattable`·`Utf8.TryWrite`로 프로토콜 계층을 바이트 상태로 유지하고, `string` 변환은 도메인 경계에서 정확히 한 번만 한다. 변환이 불가피하면 `GetMaxByteCount`로 상한을 먼저 잡아 재시도 경로를 없앤다.
- **`[SkipLocalsInit]`은 할당을 줄이지 않는다.** 큰 스택 프레임 + 핫 패스라는 두 조건이 모두 맞을 때만 이득이 있고, 부분만 채운 버퍼는 즉시 정보 유출이 된다. 모듈 전체 적용은 거의 항상 잘못된 선택이다.
- **할당 회피가 손해인 다섯 경우** — 측정이 지목하지 않은 코드, 가독성 손실이 이득보다 큰 변경, 풀 관리 버그의 기대 비용이 더 큰 경우, 버퍼 수명이 추적되지 않는 비동기 경로, 런타임이 이미 하고 있는 일을 되돌리는 코드.
- **실전 워크스루에서 3,914 KB가 0 B가 되었지만, 그 감소의 84%는 첫 단계 하나에서 나왔다.** 어디서 멈출지는 할당 숫자가 아니라 67.1절에서 정한 성능 목표가 정한다. `GC.GetAllocatedBytesForCurrentThread()` 기반 어서션 테스트를 Release CI에 넣어 회귀를 고정하라.

## 연습 문제

1. 자기 프로젝트에서 `record`(클래스)로 선언된 타입 중 **메서드 지역에서만 쓰이고 힙 자료 구조에 저장되지 않는 것**을 찾아라. 69.1절의 손익 계산표 아홉 항목을 채우고, 치명 칸이 없다면 `readonly record struct`로 바꿔라. `[MemoryDiagnoser]`로 전후 `Allocated`와 `Mean`을 비교하고, **Mean이 늘었다면 어디서 복사가 일어나는지** 디스어셈블리(67.4절)에서 확인하라.

2. `ArrayPool<byte>.Shared`에서 빌린 버퍼를 `finally`에서 반납하면서, 반납 후에도 그 버퍼의 `Span`을 반환하는 메서드를 의도적으로 작성하라. 여러 스레드에서 동시에 호출해 **반환된 데이터가 오염되는 순간**을 재현하라. 그다음 69.3절의 `TrackedPool` 래퍼를 적용해 이중 반납과 미반납이 실제로 검출되는지 확인하라.

3. `ObjectPool<T>`로 풀링하는 타입을 하나 만들되 `IResettable`을 **구현하지 않은 채로** 시작하라. 첫 요청에서 채운 필드가 두 번째 요청에 남아 있는 것을 테스트로 재현한 뒤, `TryReset`을 구현하고 69.4절의 리플렉션 기반 검증 테스트를 붙여라. 그다음 타입에 필드를 하나 추가해서 **그 테스트가 먼저 깨지는지** 확인하라.

4. `string.Format` → `$"..."` → `string.Create(provider, stackalloc buffer, $"...")` → `string.Create<TState>` 네 가지로 같은 문자열을 만드는 벤치마크를 작성하라. 63.9절의 표와 자릿수가 맞는지 확인하고, `string.Create<TState>`의 람다에서 `static`을 **떼었을 때** `Allocated`가 어떻게 변하는지 관찰하라.

5. `SearchValues<char>`를 `static readonly` 필드로 둔 버전과 메서드 안에서 `Create`를 호출하는 버전, 그리고 `IndexOfAny(char[])` 버전을 비교하라. 입력 길이를 8·64·512·8192자로, 집합 크기를 2·8·40개로 바꿔 가며 **어느 조합에서 순위가 뒤집히는지** 표로 만들어라.

6. `Encoding.UTF8.GetBytes(string)`을 쓰는 코드를 `GetMaxByteCount` + `stackalloc`/`ArrayPool` + 스팬 오버로드로 바꾸고, 입력을 순수 ASCII와 한글·이모지가 섞인 문자열로 각각 주어 `Allocated`를 비교하라. 그다음 입력을 1 MB로 키워서 `GetMaxByteCount`(3배 상한)와 `GetByteCount`(정확한 크기)의 손익이 뒤집히는 지점을 찾아라.

7. 69.9절의 V0 코드를 그대로 작성하고 V1까지 직접 밀어붙여라. 각 단계마다 `[MemoryDiagnoser]` 결과를 기록하고, 마지막에 `GC.GetAllocatedBytesForCurrentThread()` 기반 어서션 테스트를 붙여 Release 구성에서 통과시켜라. 그다음 코드 어딘가에 `.ToString()` 한 줄을 추가해서 **그 테스트가 실제로 깨지는지** 확인하라.

**다음 장** — 70장「데이터 지향 설계」에서는 이 장이 "할당을 없앴다"로 끝낸 지점을 이어받는다. 할당이 0이 된 뒤에도 남는 비용이 있다 — **메모리 접근 그 자체**다. 캐시 라인 하나에 무엇을 담을지, 구조체 배열(AoS)을 배열 구조체(SoA)로 뒤집으면 왜 빨라지는지, 거짓 공유를 어떻게 없애는지를 판다. 69.1절이 "참조 필드 0개 구조체를 목표로 잡아라"라고 말한 이유가 거기서 완결된다.
