# 74장. 디버깅 기법

> **이 장의 위치** — 73장이 진단 **API 레퍼런스**였다면 이 장은 **워크플로**다. `Debugger` 클래스에 어떤 메서드가 있는지는 이미 알고 있다. 여기서 다루는 것은 "프로덕션 컨테이너에서 스레드가 다 멈췄다"는 신고를 받았을 때 무엇을 어떤 순서로 하는가다. 개발 머신에서 중단점을 거는 것부터, 덤프 하나만 손에 쥔 채 교착을 확정하는 것까지 이어진다.
>
> **선수 지식** — 32장(예외 처리), 47장(async/await 완전 해부), 48장(동기화와 잠금), 66장(메모리 문제 진단), 73장(진단 API)
>
> **이 장에서 다루지 않는 것** — 메모리 누수·힙 분석의 WinDbg/SOS 워크플로는 66장에서 이미 끝냈다. 이 장의 덤프 분석은 **교착·예외·행(hang)·스레드 고갈** 관점이며, 힙 쪽 명령이 필요해지는 지점마다 66장으로 넘긴다. `Debug`/`Trace`/`StackTrace` API 자체는 73장, 구조적 로깅과 분산 추적은 75장, 디버깅하기 쉬운 코드를 **설계하는** 습관은 80.7절에서 다룬다.

## 74.1 디버거 통합 — 연결(attach)과 중단(break)

애플리케이션이 디버거와 상호작용해야 할 때가 있다. 개발 중에는 디버거가 보통 IDE(Visual Studio, VS Code, Rider)지만, 배포 환경에서는 WinDbg나 lldb 같은 더 저수준 도구일 가능성이 높다. 이 차이를 인정하는 데서 시작해야 한다. **개발 머신에서 통하는 방법은 프로덕션에서 대부분 통하지 않는다.**

### 디버거는 어떻게 프로세스에 붙는가

관리 디버깅은 CLR이 노출하는 **디버깅 인터페이스**를 통해 이뤄진다. 디버거는 OS의 디버깅 기본 요소(Windows의 디버그 이벤트, Linux의 `ptrace`) 위에서 대상 프로세스를 제어하고, 그 위에서 CLR의 디버거 서비스가 "이 네이티브 주소는 어느 관리 메서드의 어느 IL 오프셋인가"를 번역해준다.

```text
       ┌────────────────────────┐
       │  IDE / WinDbg / lldb   │   ← 사용자가 보는 디버거
       └───────────┬────────────┘
                   │ 디버깅 프로토콜
       ┌───────────▼────────────┐
       │  관리 디버깅 계층       │   ← IL 오프셋 ↔ 네이티브 주소, 지역 변수, 스택
       │  (ICorDebug / SOS)     │
       └───────────┬────────────┘
                   │ OS 디버그 기본 요소
       ┌───────────▼────────────┐
       │  Windows 디버그 이벤트  │
       │  Linux ptrace(2)       │
       └───────────┬────────────┘
                   │
       ┌───────────▼────────────┐
       │   대상 .NET 프로세스    │
       └────────────────────────┘
```

이 그림에서 중요한 것은 **맨 아래 계층이 OS별로 다르다**는 사실이다. Linux 컨테이너에서 디버거가 붙지 않는 사고의 절반은 여기서 난다(뒤에서 다룬다).

### 연결 방식 다섯 가지

| 방식 | 어떻게 | 언제 쓰나 | 제약 |
|---|---|---|---|
| **시작과 동시에 디버깅(F5)** | IDE가 프로세스를 직접 띄운다 | 개발 중 기본. 프로그램 시작 지점부터 중단 가능 | 프로세스를 IDE가 소유한다. 호스팅 환경(서비스·IIS·컨테이너)을 재현하지 못한다 |
| **실행 중 프로세스에 연결(Attach to Process)** | IDE의 `디버그 > 프로세스에 연결` | 이미 떠 있는 프로세스, 다른 사람이 띄운 서비스, 로컬 컨테이너 | **연결 이전 코드에 중단점을 걸 수 없다.** 시작 시점 버그에 무력하다 |
| **`Debugger.Launch()` / `Debugger.Break()`** | 코드가 스스로 디버거를 부른다 | 시작 직후 버그, Windows 서비스, 디자이너, 빌드 태스크, MSBuild 태스크, 소스 생성기 | `Launch()`는 사실상 Windows 전용. 코드에 흔적이 남는다 |
| **원격 디버깅** | 대상 머신에 원격 디버거(`msvsmon.exe` / `vsdbg`)를 설치하고 IDE가 네트워크로 연결 | 테스트 서버, VM, 리눅스 호스트 | 방화벽·인증·심볼 배치 필요. **대상 프로세스를 정지시킨다** |
| **컨테이너 디버깅** | `docker exec`로 컨테이너 안 `vsdbg`를 파이프 전송(pipe transport)으로 구동 | 로컬/스테이징 컨테이너 | `SYS_PTRACE` 권한과 `vsdbg` 설치 필요. 이미지가 커진다 |

> **⚠️ 프로덕션에 디버거를 붙이는 것은 장애를 만드는 행위다**
>
> 디버거가 중단점에 걸리면 **프로세스 전체가 멈춘다.** 헬스 체크가 타임아웃되고 로드 밸런서가 인스턴스를 제거하며, 최악의 경우 오케스트레이터가 컨테이너를 죽여 조사 대상 자체를 잃는다. 프로덕션의 정답은 라이브 디버깅이 아니라 **덤프·추적·로그**다(74.5절, 74.8절). 굳이 붙여야 한다면 먼저 그 인스턴스를 트래픽에서 빼라.

### `Debugger` 클래스

`System.Diagnostics.Debugger`는 디버거와 상호작용하는 최소한의 표면을 제공한다. 73.2절에서 API 자체는 이미 봤으므로, 여기서는 **각 멤버가 실제로 어느 상황을 위해 존재하는지**를 정리한다.

| 멤버 | 하는 일 | 실전 용도 |
|---|---|---|
| `Debugger.IsAttached` | 디버거가 붙어 있는가 | 대기 루프의 종료 조건. 디버깅 중에만 다른 경로를 타게 할 때 |
| `Debugger.Launch()` | 디버거를 띄우고 연결한다. 실행은 **계속**된다. `bool` 반환 | Windows 서비스·디자이너·MSBuild 태스크처럼 IDE가 프로세스를 못 띄우는 경우 |
| `Debugger.Break()` | 디버거를 띄우고 연결한 뒤 **그 지점에서 중단**한다 | 원하는 실행 지점에 확실히 멈추고 싶을 때 |
| `Debugger.Log(level, category, message)` | 디버거 출력 창에 직접 기록 | 리스너 구성 없이 디버거에만 흘리고 싶은 메시지 |
| `Debugger.IsLogging()` | 디버거가 로그를 받고 있는가 | 비싼 로그 문자열 조립을 건너뛰기 |
| `Debugger.NotifyOfCrossThreadDependency()` | "이 코드를 평가하려면 다른 스레드가 돌아야 한다"고 디버거에 알린다 | 감시 창의 함수 평가(func-eval)가 교착하지 않게 만드는 라이브러리 쪽 장치 |

`Break`와 `Launch`의 차이는 **중단 여부 하나**다. 디버거를 붙이되 흐름은 계속 가게 하려면 `Launch`, 그 자리에서 멈추려면 `Break`다. 붙은 뒤에는 `Log`로 디버거 출력 창에 직접 메시지를 흘릴 수 있고, `IsAttached`로 연결 여부를 확인할 수 있다.

```csharp
using System.Diagnostics;

// 진입점 맨 앞. 시작 직후에 터지는 버그를 잡는 유일한 방법인 경우가 많다.
#if DEBUG
if (Environment.GetEnvironmentVariable("WAIT_FOR_DEBUGGER") == "1")
{
    Debugger.Launch();      // Windows: JIT 디버거 선택 대화상자를 띄운다
}
#endif
```

> **⚠️ `Debugger.Launch()`는 사실상 Windows 전용이다**
>
> `Launch()`는 OS에 등록된 **JIT 디버거**(Just-In-Time debugger)를 기동하는 메커니즘에 의존한다. Windows에는 이 레지스트리 등록(`AeDebug`)이 있지만 Linux·macOS에는 대응하는 개념이 없다. 그래서 Unix 계열에서 `Launch()`는 디버거를 띄우지 못하고 `false`를 반환하며 아무 일도 일어나지 않는다. **컨테이너 안에서 `Launch()`를 호출하고 "왜 안 멈추지"라고 묻는 것이 이 장에서 가장 흔한 오해다.**

### 컨테이너·서비스에서 시작 지점 디버깅하기

`Launch()`가 안 되는 환경에서 시작 지점을 잡는 표준 기법은 **대기 루프**다. 디버거를 붙일 시간을 벌어주는 것이 전부다.

```csharp
using System.Diagnostics;

static void WaitForDebuggerIfRequested()
{
    if (Environment.GetEnvironmentVariable("WAIT_FOR_DEBUGGER") != "1")
        return;

    Console.WriteLine($"PID {Environment.ProcessId} — 디버거 연결 대기 중...");

    // 타임아웃을 반드시 둔다. 안 그러면 디버깅용 환경 변수가 실수로 켜졌을 때
    // 컨테이너가 영원히 준비 상태가 되지 않는다.
    var deadline = DateTime.UtcNow.AddMinutes(2);
    while (!Debugger.IsAttached && DateTime.UtcNow < deadline)
        Thread.Sleep(200);

    if (Debugger.IsAttached)
        Debugger.Break();   // 붙었으면 여기서 멈춘다
}
```

컨테이너 쪽 준비는 세 가지다.

```bash
# 1) ptrace 권한을 준다 — 이게 없으면 vsdbg가 프로세스에 붙지 못한다
docker run --cap-add=SYS_PTRACE --security-opt seccomp=unconfined \
           -e WAIT_FOR_DEBUGGER=1 myapp:dev

# 2) 컨테이너 안에 vsdbg를 설치한다 (개발용 이미지에만)
curl -sSL https://aka.ms/getvsdbgsh | bash /dev/stdin -v latest -l /vsdbg

# 3) 호스트에서 프로세스 ID를 확인한다
docker exec -it <container> ps aux
```

VS Code라면 `launch.json`에 파이프 전송 구성을 넣는다.

```json
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Docker에 연결",
      "type": "coreclr",
      "request": "attach",
      "processId": "${command:pickRemoteProcess}",
      "pipeTransport": {
        "pipeProgram": "docker",
        "pipeArgs": [ "exec", "-i", "myapp-container" ],
        "debuggerPath": "/vsdbg/vsdbg",
        "pipeCwd": "${workspaceRoot}",
        "quoteArgs": false
      },
      "sourceFileMap": { "/src": "${workspaceFolder}" }
    }
  ]
}
```

`sourceFileMap`이 핵심이다. 컨테이너 안에서 빌드했다면 PDB에 박힌 소스 경로가 `/src/...`이고, 호스트의 실제 경로는 다르다. 이 매핑이 없으면 중단점이 비어 있는 원으로 바뀌며 `No symbols have been loaded for this document`를 띄운다. 근본 해법은 74.7절의 소스 링크다.

> **⚠️ `ptrace_scope`가 1이면 컨테이너 밖에서 붙을 수 없다**
>
> 대부분의 리눅스 배포판은 `/proc/sys/kernel/yama/ptrace_scope`를 `1`로 둔다. 이 값이 1이면 **부모 프로세스만** 다른 프로세스를 `ptrace`할 수 있다. 컨테이너에 `--cap-add=SYS_PTRACE`를 주는 것이 표준 해법이고, 개발 호스트라면 `sudo sysctl -w kernel.yama.ptrace_scope=0`으로 임시 완화할 수 있다. 이 설정은 **컨테이너별이 아니라 커널 전역**이므로 프로덕션 노드에서 건드리면 안 된다.

> **📌 진단 도구는 `ptrace`가 필요 없다**
>
> `dotnet-counters`·`dotnet-trace`·`dotnet-dump`는 EventPipe(유닉스 도메인 소켓/명명된 파이프)로 통신하므로 `ptrace`도 관리자 권한도 요구하지 않는다(73.9절). 디버거를 못 붙이는 환경에서 이 도구들이 여전히 동작하는 이유이며, 프로덕션 진단이 덤프·추적 중심이 되는 실질적 이유이기도 하다.

### 원격 디버깅

| 대상 | 도구 | 설치 | 비고 |
|---|---|---|---|
| Windows 서버·VM | Remote Debugger (`msvsmon.exe`) | Visual Studio 배포판에 포함. 대상 머신에 복사해 실행 | 기본 포트는 VS 버전마다 다르다(VS 2022는 4026). 인증 모드와 방화벽 규칙을 맞춰야 한다 |
| Linux 호스트 | `vsdbg` | `getvsdbgsh` 스크립트로 설치 | SSH 파이프 전송으로 붙는다. `pipeProgram`을 `ssh`로 둔다 |
| 컨테이너 | `vsdbg` | 이미지에 포함하거나 실행 중 설치 | `docker exec` 파이프 전송 |
| WSL | `vsdbg` | VS/VS Code가 자동 설치 | 파일 시스템 경로 매핑에 주의 |

원격 디버깅에서 가장 자주 깨지는 것은 **심볼과 소스 매칭**이다. 대상 머신의 바이너리는 빌드 서버에서 만든 것이고, 개발 머신의 소스는 그 사이 커밋이 몇 개 더 쌓여 있다. 이 문제를 구조적으로 없애는 방법이 결정론적 빌드와 소스 링크이며 74.6절·74.7절에서 다룬다.

### 중단한 뒤 — 스테핑의 실제

중단 모드에 들어가면 도구 모음(Visual Studio는 별도의 `디버그` 도구 모음, VS Code는 떠 있는 작은 막대)이 나타난다. 버튼 이름과 단축키는 도구가 달라도 거의 같다.

| 명령 | 단축키 | 하는 일 | 주의 |
|---|---|---|---|
| **시작/계속** | `F5` | 시작하거나, 다음 중단점 혹은 종료까지 진행 | 문맥에 따라 의미가 바뀐다 |
| **핫 리로드** | — | 재시작 없이 코드 변경을 적용 | 거친 편집이면 거부된다 |
| **모두 중단** | `Ctrl+Alt+Break` | 실행 중인 앱을 다음 가능한 줄에서 세운다 | **행(hang) 조사의 첫 수단** |
| **디버깅 중지** | `Shift+F5` | 세션 종료 | Attach였다면 프로세스도 같이 죽을 수 있다 |
| **다시 시작** | `Ctrl+Shift+F5` | 중지 후 즉시 재시작 | 재현해 놓은 상태를 잃는다 |
| **한 단계씩(Step Into)** | `F11` | 호출을 만나면 **안으로 들어간다** | 남의 코드로 빠지기 쉽다 |
| **프로시저 단위(Step Over)** | `F10` | 호출을 **한 번에 실행**하고 다음 줄로 | 건너뛰는 게 아니라 실행한다 |
| **프로시저 나가기(Step Out)** | `Shift+F11` | 현재 메서드가 반환할 때까지 | 잘못 들어갔을 때 탈출 |
| **다음 문 표시** | — | 커서를 다음 실행 문으로 이동 | 코드를 헤매다 돌아올 때 |
| **소스에 스레드 표시** | — | 편집기 여백에 각 스레드 위치 | 74.4절 |

`F11`과 `F10`의 차이는 **호출 문 위에 있을 때만** 드러난다. 단일 문을 실행할 때는 둘이 같다. `F11`은 그 메서드 안으로 들어가 한 줄씩 볼 수 있게 하고, `F10`은 메서드를 통째로 실행한 뒤 다음 줄에 선다. **`F10`이 메서드를 "건너뛴다"고 오해하는 경우가 많은데, 실행은 정상적으로 일어난다.**

전형적인 사용 흐름은 이렇다. 버그가 의심되는 계산을 담은 메서드 호출 앞에 서서 `F11`로 들어가고, 편집기에서 매개변수 위에 마우스를 올려 현재 값을 툴팁으로 확인하고, 의심되는 식(예: `a * b`)을 선택해 우클릭한 뒤 `조사식 추가`로 감시 창에 올린다. 감시 창이 그 식의 값을 보여주면 `+`여야 할 자리에 `*`가 있다는 사실이 즉시 드러난다. 고친 뒤 `Ctrl+Shift+F5`로 다시 시작해 `F10`으로 같은 줄을 지나며 값이 맞는지 확인하고 `F5`로 계속한다.

> **📌 커서까지 실행과 다음 문 설정**
>
> 중단점을 걸기 애매한 지점까지 빨리 가려면 그 줄에서 `Ctrl+F10`(**커서까지 실행**)을 쓴다. 임시 중단점을 걸었다 지우는 것보다 빠르다.
>
> 노란 화살표를 끌어다 다른 줄에 놓으면 **다음 실행 문을 바꿀 수 있다**(Set Next Statement, `Ctrl+Shift+F10`). 방금 지나온 줄을 다시 실행하거나 문제 있는 줄을 건너뛰는 데 쓴다.

> **⚠️ 다음 문 설정은 프로그램 상태를 망가뜨릴 수 있다**
>
> 실행 지점만 바뀔 뿐 **이미 실행된 부수 효과는 되돌아가지 않는다.** 변수는 그대로고, 열린 파일은 열려 있고, 증가한 카운터는 그대로다. 초기화를 건너뛰면 다음 줄에서 `NullReferenceException`이 나고, 그 예외는 진짜 버그가 아니라 디버깅 조작의 결과다. `try`/`catch` 블록이나 `await` 경계를 가로지르는 이동은 아예 거부되거나 정의되지 않은 결과를 낳는다. **"조사 중 우회"에만 쓰고, 여기서 관찰한 것을 버그 증거로 삼지 마라.**

> **📌 VS Code에서 콘솔 입력이 필요하다면 통합 터미널을 써라**
>
> VS Code는 기본적으로 디버깅 중 출력을 `디버그 콘솔`로 보낸다. 이 창은 `ReadLine` 같은 **입력 상호작용을 받지 못한다.** 콘솔 앱을 디버깅하는데 프롬프트가 나오지도, 입력을 기다리지도 않는 것처럼 보이는 이유가 이것이다. `launch.json`의 구성에서 `"console"`을 `"internalConsole"`에서 `"integratedTerminal"`로 바꾸면 터미널이 프로세스에 연결되어 정상적으로 입력을 받는다.
>
> ```json
> {
>   "name": ".NET Core Launch (console)",
>   "type": "coreclr",
>   "request": "launch",
>   "program": "${workspaceFolder}/Debugging/bin/Debug/net8.0/Debugging.dll",
>   "args": [],
>   "cwd": "${workspaceFolder}",
>   "stopAtEntry": false,
>   "console": "integratedTerminal"
> }
> ```

### 예외에서 중단하기

"예외가 났는데 어디서 났는지 모르겠다"는 문제의 답은 대부분 **예외 설정(Exception Settings) 창**이다.

- **처리되지 않은 예외에서 중단** — 기본 동작. 하지만 예외가 `catch`로 삼켜지면 중단되지 않는다.
- **던져질 때 중단(first-chance)** — 특정 예외 타입에 체크를 넣으면 `catch`가 있어도 **던져지는 순간** 멈춘다. 원래 스택이 살아 있는 유일한 시점이다.
- **"내 코드가 처리하지 않은 경우에만"** — "내 코드만(Just My Code)"이 켜져 있을 때, 라이브러리가 삼키는 예외는 무시하고 내 코드 밖으로 나온 것만 잡는다.

32.6절에서 본 2단계 예외 처리를 떠올리면 왜 first-chance가 특별한지 알 수 있다. 1단계(필터 실행)에서는 **스택이 아직 감기지 않았다.** 그래서 던져진 순간에 멈추면 예외를 일으킨 프레임의 지역 변수가 그대로 살아 있다. `catch` 블록에서 멈추면 이미 늦었다.

> **⚠️ 예외 필터(`when`)는 first-chance 중단의 의미를 바꾼다**
>
> `catch (E e) when (Filter(e))` 형태에서 필터는 **1단계**에 실행된다. 즉 디버거가 "던져질 때 중단"으로 멈추기 전에 이미 필터 코드가 돈다. 필터 안에 로깅이나 부수 효과를 넣어 뒀다면(32.8절), 디버거로 멈춰 놓고 보는 상태가 "예외가 던져진 직후"가 아니라 "필터가 한 번 돈 뒤"일 수 있다.

※.NET 9는 여기에 세밀한 제어를 추가했다. `[DebuggerDisableUserUnhandledExceptions]`를 메서드에 붙이면, 그 메서드에서 발생한 예외를 디버거가 "사용자가 처리하지 않은 예외"로 취급하지 않는다. 대신 라이브러리가 정말로 사용자에게 알려야 할 시점에 `Debugger.BreakForUserUnhandledException(ex)`를 명시적으로 호출한다. 프레임워크가 사용자 콜백을 감싸 호출할 때, 사용자 코드에서 난 예외를 프레임워크 프레임이 아니라 원래 자리에서 보여주기 위한 장치다.

### 편집하며 계속하기 — 핫 리로드

**핫 리로드(Hot Reload)** 는 실행 중인 앱에 코드 변경을 적용하고 즉시 효과를 보는 기능이다. 예전 이름은 **편집하며 계속하기(Edit and Continue)** 다. 버그를 빠르게 고칠 때 강력하다.

Visual Studio에서는 도구 모음의 핫 리로드 버튼이나 `디버그 > 코드 변경 내용 적용`으로 적용하고, 드롭다운의 **파일 저장 시 핫 리로드**를 켜면 저장만으로 반영된다. 명령줄에서는 `dotnet watch`가 같은 일을 한다.

```bash
$ dotnet watch
dotnet watch  Hot reload enabled. For a list of supported edits, see
              https://aka.ms/dotnet/hot-reload.
              Press "Ctrl + R" to restart.
dotnet watch  Building...
dotnet watch  Started
Hello, Hot Reload!
Hello, Hot Reload!
dotnet watch  File changed: .\Program.cs.
dotnet watch  Hot reload of changes succeeded.
Goodbye, Hot Reload!
```

> **📌 핫 리로드는 IDE 전용 기능이 아니다**
>
> .NET 6 출시 직전, 핫 리로드를 Visual Studio 전용으로 만들려는 시도가 있었고 논란 끝에 철회됐다. 그 결과 `dotnet watch`를 통한 명령줄 핫 리로드가 유지됐다. VS Code와 Rider 사용자가 같은 기능을 쓸 수 있는 것은 이 결정 덕분이다.

핵심은 **무엇이 되고 무엇이 안 되는가**다. 되는 줄 알고 편집했다가 "적용할 수 없는 편집이니 재시작하겠는가"라는 안내를 만나면 디버깅 세션과 재현해 놓은 상태를 통째로 잃는다.

| 변경 | 지원 | 비고 |
|---|---|---|
| 메서드 **본문** 수정 | 예 | 가장 흔한 경우. 조건식·계산식·문자열 수정 |
| 람다·지역 함수 **본문** 수정 | 예 | 클로저 구조를 바꾸지 않는 한 |
| 지역 변수 추가 | 대체로 예 | 활성 프레임이 아닐 때 안전하다 |
| 새 메서드·필드·속성·이벤트 추가 | 예 ※.NET 6+ | 런타임의 메타데이터 업데이트 지원이 필요하다 |
| 새 타입(클래스·구조체) 추가 | 예 ※.NET 6+ | |
| 메서드 **시그니처** 변경 | **아니오** | 매개변수 추가/제거/타입 변경 |
| 멤버 **이름 변경·삭제** | **아니오** | 메타데이터 토큰이 사라지는 편집은 불가 |
| 기반 타입·인터페이스 목록 변경 | **아니오** | 타입 레이아웃이 바뀐다 |
| `struct` 필드 레이아웃 변경 | **아니오** | 이미 만들어진 인스턴스와 어긋난다 |
| 제네릭 메서드·제네릭 타입 본문 편집 | 제한적 | 런타임 버전에 따라 다르다 |
| **현재 스택에 살아 있는 메서드**의 본문 편집 | 적용은 되지만 즉시 반영 안 됨 | 그 프레임은 이전 코드로 끝난다. 다음 호출부터 새 코드 |

지원되지 않는 편집을 **거친 편집(rude edit)** 이라고 부른다. 도구는 재시작을 제안하는 것 외에 할 수 있는 일이 없다.

> **📌 핫 리로드의 실체는 메타데이터 업데이트다**
>
> 내부적으로 핫 리로드는 컴파일러가 만든 델타(IL, 메타데이터, PDB)를 `System.Reflection.Metadata.MetadataUpdater.ApplyUpdate`로 런타임에 밀어 넣는다. 이 경로는 어셈블리가 **수정 가능(modifiable)** 으로 로드되어 있어야 열리며, 그 스위치가 환경 변수 `DOTNET_MODIFIABLE_ASSEMBLIES=debug`다. 도구가 알아서 설정해 주지만, 커스텀 런처를 쓴다면 직접 넣어야 한다. `MetadataUpdater.IsSupported`로 지원 여부를 확인할 수 있고, `[assembly: MetadataUpdateHandler(typeof(MyHandler))]`로 업데이트 시 캐시를 비우는 콜백을 등록할 수 있다 — 리플렉션 결과를 캐싱하는 라이브러리(57.12절)는 이걸 하지 않으면 핫 리로드 후 옛 메서드를 계속 호출한다.

> **⚠️ 핫 리로드가 아예 불가능한 배포 형태가 있다**
>
> Native AOT로 게시한 앱에는 IL도 메타데이터 업데이트 경로도 없다(55.7절, 57.14절). 단일 파일 게시나 최적화가 켜진 Release 구성도 마찬가지로 제외되거나 크게 제한된다. 핫 리로드는 **디버그 구성 + JIT 런타임**을 전제로 한 개발 시점 기능이며, 프로덕션 배포본에 적용할 수 있는 무엇이 아니다.

## 74.2 디버거 특성 — `DebuggerDisplay`, `DebuggerBrowsable`, `DebuggerStepThrough`, `DebuggerTypeProxy`

73.4절에서 디버거 특성의 목록과 각 특성의 효과를 표로 정리했다. 이 절은 그 표를 **실제로 쓰는 법**으로 바꾼다. 어떤 증상에 어떤 특성을 붙이는가, 표현식 문법이 정확히 어디까지 허용되는가, 내가 소유하지 않은 타입은 어떻게 하는가.

### 증상에서 특성으로

디버깅이 느려지거나 답답한 데는 몇 가지 전형이 있고, 각각에 대응하는 특성이 있다.

| 증상 | 붙일 것 | 효과 |
|---|---|---|
| 감시 창에 `{MyApp.Order}`만 보여서 어떤 객체인지 모른다 | `[DebuggerDisplay]` | 한 줄 요약을 직접 정한다 |
| 내부 필드·캐시·계산 속성이 감시 창을 가득 채운다 | `[DebuggerBrowsable(Never)]` | 그 멤버를 감시 창에서 지운다 |
| 컬렉션 래퍼를 펼치면 `_items`, `_size`, `_version`이 나온다 | `[DebuggerBrowsable(RootHidden)]` | 원소를 부모 자리에 바로 펼친다 |
| 내부 구조가 복잡해서 논리적 상태를 볼 수 없다 | `[DebuggerTypeProxy]` | 대리 타입이 만든 뷰를 대신 보여준다 |
| F11로 들어가면 매번 DI 컨테이너·검증 헬퍼에 빠진다 | `[DebuggerStepThrough]` | 그 메서드를 통과한다 |
| 호출 스택이 프록시·래퍼로 도배된다 | `[DebuggerHidden]` | 스택 창에서 감춘다. 내부 중단점도 무시된다 |
| 생성된 코드가 "내 코드"로 취급된다 | `[DebuggerNonUserCode]` | "내 코드만" 설정에서 제외된다 |
| 콜백에서 난 예외가 라이브러리 프레임에서 멈춘다 | `[DebuggerDisableUserUnhandledExceptions]` ※.NET 9 | 사용자 코드 자리에서 멈추게 돌린다 |

`[DebuggerHidden]`과 `[DebuggerStepThrough]`의 차이는 실무에서 계속 헷갈린다. **`StepThrough`는 "지나가라"이고 `Hidden`은 "없는 셈 쳐라"다.** `StepThrough`가 붙은 메서드 안에 중단점을 걸면 여전히 걸리지만, `Hidden`이 붙으면 그 중단점은 **무시된다.** 디버깅용 임시 중단점을 심어놓고 "왜 안 걸리지"라고 헤매는 원인이 대개 이것이다.

### `DebuggerDisplay` 표현식 문법

`[DebuggerDisplay]`의 인자는 **중괄호로 식을 끼워 넣는 템플릿 문자열**이다. 중괄호 밖은 리터럴, 안은 디버거가 평가하는 식이다.

```csharp
using System.Diagnostics;

[DebuggerDisplay("주문 #{Id} / {Lines.Count}줄 / {Total,nq} / {Status}")]
public sealed class Order
{
    public int Id { get; init; }
    public List<OrderLine> Lines { get; } = new();
    public decimal Total => Lines.Sum(l => l.Amount);
    public OrderStatus Status { get; set; }
}
```

식 뒤에 쉼표로 **형식 지정자(format specifier)** 를 붙일 수 있다. 자주 쓰는 것은 다음과 같다.

| 지정자 | 뜻 | 쓰는 이유 |
|---|---|---|
| `,nq` | no quotes — 문자열을 따옴표 없이 | 템플릿에 문자열을 섞을 때 `"활성"`이 `활성`으로 보인다. **가장 많이 쓴다** |
| `,d` | decimal — 정수를 10진수로 | 16진 표시 설정이 켜져 있어도 10진으로 강제 |
| `,h` | hex — 정수를 16진수로 | 플래그·마스크·핸들 값 |
| `,ac` | always calculate — 새로 고침을 기다리지 않고 즉시 평가 | 감시 창이 값을 아직 계산하지 않은 상태를 건너뛴다 |
| `,raw` | 사용자 정의 뷰를 무시하고 원시 값 | 프록시를 붙여 놓은 타입의 진짜 내부를 볼 때 |
| `,nse` | no side effects — 부수 효과를 전파하지 않고 평가 | 감시 식이 상태를 바꾸는 것을 막는다 |
| `,hidden` | 공개·비공개 멤버를 모두 표시 | 기본 뷰가 감춘 멤버까지 볼 때 |

식 안에서는 **속성·필드 접근, 인덱서, 산술·비교 연산, 조건 연산자, 문자열 리터럴**이 동작한다. 리터럴 중괄호가 필요하면 `\{`로 이스케이프한다.

```csharp
[DebuggerDisplay("{IsActive ? \"활성\" : \"중지\",nq} · 재시도 {RetryCount}/{MaxRetries}")]
```

이름 있는 인자로 **표시 요소 자체를 나눠 지정**할 수도 있다.

```csharp
[DebuggerDisplay("{_key}", Name = "{_key,nq}", Type = "캐시 항목")]
```

- `Value`(기본 위치 인자) — 값 열에 표시할 문자열
- `Name` — 이름 열에 표시할 문자열
- `Type` — 형식 열에 표시할 문자열

> **⚠️ `DebuggerDisplay` 식에서 메서드를 호출하지 마라**
>
> 문법적으로는 `{GetSummary()}` 같은 메서드 호출이 허용되고 Visual Studio는 대개 평가해 준다. 하지만 이것은 **함수 평가(func-eval)** 다. 디버거가 대상 프로세스의 스레드를 하나 골라 실제로 그 메서드를 실행시킨다. 그 메서드가 잠금을 잡거나, 다른 스레드를 기다리거나, I/O를 하면 감시 창이 통째로 멈추거나 타임아웃 오류로 채워진다. 더 나쁜 것은 **상태를 바꾸는 경우**다. 지연 초기화를 트리거하면 "디버거로 볼 때만 정상 동작하는" 하이젠버그가 만들어진다. 식은 순수한 속성·필드 접근으로 제한하라.

> **📌 `DebuggerDisplay`가 없으면 디버거는 `ToString()`을 부른다**
>
> 감시 창의 기본 요약은 `ToString()` 결과다. 그러므로 `ToString()`을 잘 만들어 두면 특성 없이도 대부분 해결된다. `record`가 디버깅하기 편한 이유가 여기 있다 — 컴파일러가 모든 속성을 나열하는 `ToString()`을 만들어 준다. `[DebuggerDisplay]`는 **`ToString()`이 사용자 대상 출력이라 디버깅용으로 바꿀 수 없을 때** 쓰는 두 번째 수단이다. 다만 `ToString()` 호출도 func-eval이므로, 무거운 `ToString()`은 그 자체로 디버깅을 느리게 만든다.

### 내가 소유하지 않은 타입에 붙이기

`[DebuggerDisplay]`와 `[DebuggerTypeProxy]`는 **어셈블리 수준**으로도 적용할 수 있다. 이때 `Target` 또는 `TargetTypeName`으로 대상 타입을 지정한다. NuGet 패키지의 타입이나 자동 생성된 타입처럼 소스를 고칠 수 없는 대상에 쓰는 방법이다.

```csharp
using System.Diagnostics;

// 소유하지 않은 타입에 표시 규칙을 붙인다
[assembly: DebuggerDisplay("{Value} ({Unit,nq})", Target = typeof(ThirdParty.Measurement))]

// 제네릭 타입은 어셈블리 정규화 이름 문자열로 지정한다
[assembly: DebuggerDisplay(
    "{Count}개 항목",
    TargetTypeName = "ThirdParty.Buffer`1, ThirdParty.Core")]
```

> **⚠️ `TargetTypeName`은 컴파일러가 검증하지 않는다**
>
> 오타가 나거나 대상 어셈블리 이름이 바뀌면 **아무 오류도 없이 그냥 무시된다.** 디버거에서 표시가 안 바뀌면 특성이 잘못된 것인지 디버거가 지원하지 않는 것인지 구분이 안 된다. `Target = typeof(...)`로 쓸 수 있는 경우에는 반드시 그쪽을 쓰고, 문자열을 써야 한다면 백틱 개수(`` `1 ``)와 어셈블리 단순 이름을 정확히 확인하라.

### `DebuggerTypeProxy` 완전 예제

`[DebuggerTypeProxy]`는 감시 창에서 **원래 타입 대신 보여줄 대리 타입**을 지정한다. BCL의 `Dictionary<TKey,TValue>`가 버킷 배열이 아니라 키-값 쌍 목록으로 보이는 것이 이 특성 덕분이다.

내부 표현과 논리적 표현이 크게 다른 타입일수록 효과가 크다. 이진 힙이 대표적이다. 저장은 배열이지만 사람이 알고 싶은 것은 "우선순위 순서"다.

```csharp
using System.Diagnostics;

[DebuggerDisplay("Count = {_count}, Min = {PeekForDebugger}")]
[DebuggerTypeProxy(typeof(MinHeapDebugView<>))]   // 열린 제네릭으로 지정한다
public sealed class MinHeap<T> where T : IComparable<T>
{
    // 대리 타입이 읽어야 하므로 internal로 둔다. private이면 프록시가 접근할 수 없다.
    internal T[] _items = new T[4];
    internal int _count;

    public int Count => _count;

    public void Push(T item)
    {
        if (_count == _items.Length) Array.Resize(ref _items, _count * 2);
        _items[_count] = item;
        int i = _count++;
        while (i > 0)
        {
            int parent = (i - 1) / 2;
            if (_items[parent].CompareTo(_items[i]) <= 0) break;
            (_items[parent], _items[i]) = (_items[i], _items[parent]);
            i = parent;
        }
    }

    public T Pop()
    {
        if (_count == 0) throw new InvalidOperationException("힙이 비어 있다.");
        T result = _items[0];
        _items[0] = _items[--_count];
        _items[_count] = default!;
        int i = 0;
        while (true)
        {
            int l = 2 * i + 1, r = l + 1, smallest = i;
            if (l < _count && _items[l].CompareTo(_items[smallest]) < 0) smallest = l;
            if (r < _count && _items[r].CompareTo(_items[smallest]) < 0) smallest = r;
            if (smallest == i) break;
            (_items[i], _items[smallest]) = (_items[smallest], _items[i]);
            i = smallest;
        }
        return result;
    }

    // DebuggerDisplay 전용 보조 속성. 예외를 던지지 않는다는 점이 중요하다.
    [DebuggerBrowsable(DebuggerBrowsableState.Never)]
    T? PeekForDebugger => _count == 0 ? default : _items[0];
}

// ── 대리 타입 ─────────────────────────────────────────────
internal sealed class MinHeapDebugView<T> where T : IComparable<T>
{
    readonly MinHeap<T> _heap;

    // 대상 인스턴스를 받는 생성자가 정확히 하나 필요하다.
    public MinHeapDebugView(MinHeap<T> heap) => _heap = heap;

    // 원소를 부모 노드 자리에 그대로 펼친다.
    [DebuggerBrowsable(DebuggerBrowsableState.RootHidden)]
    public T[] SortedItems
    {
        get
        {
            // 원본을 건드리지 않고 복사본에서 정렬한다 — 부수 효과 금지.
            var copy = new T[_heap._count];
            Array.Copy(_heap._items, copy, _heap._count);
            Array.Sort(copy);
            return copy;
        }
    }

    // 내부 구조도 필요하면 별도 노드로 남겨 둔다.
    public T[] RawBackingArray => _heap._items;
    public int Capacity => _heap._items.Length;
}
```

대리 타입의 규칙은 넷이다.

1. **대상 타입 인스턴스를 받는 public 생성자가 하나 있어야 한다.** 없으면 디버거가 프록시를 만들지 못하고 조용히 원래 뷰로 돌아간다.
2. **`internal`로 두면 공개 API 표면을 오염시키지 않는다.** 비제네릭 타입이라면 대상 타입 안의 중첩 private 클래스로 두어도 된다. 다만 제네릭 타입에서는 그럴 수 없다 — 다음 항목을 보라.
3. **제네릭 타입의 프록시는 별도의 제네릭 타입으로 만들고 열린 제네릭(`MinHeapDebugView<>`)으로 지정한다.** 디버거가 대상의 타입 인자로 닫아서 인스턴스화한다. 제네릭 타입 안에 중첩시킬 수 없는 이유는 문법이다 — 특성 인자의 `typeof`에는 **타입 매개변수를 쓸 수 없고**(CS0416), 중첩 타입을 이름만으로 참조하면 바깥 타입의 `T`가 딸려 들어간다. BCL이 `List<T>`·`Dictionary<TKey,TValue>`의 프록시를 별도 제네릭 타입으로 두는 이유가 이것이다.
4. **프록시의 속성은 순수해야 한다.** 위 예제가 원본 배열을 정렬하지 않고 복사본을 정렬하는 이유다. 프록시가 힙을 정렬해 버리면 디버깅하는 행위 자체가 프로그램을 고친다.

> **⚠️ `RootHidden`은 열거 가능한 것에만 의미가 있다**
>
> `DebuggerBrowsableState.RootHidden`은 "나를 감추고 **자식 원소를** 부모 자리에 펼쳐라"라는 뜻이다. 그래서 배열이나 `IEnumerable`이 아닌 스칼라 속성에 붙이면 디버거가 펼칠 자식이 없어 아무것도 표시되지 않거나 오류 노드가 나온다. 컬렉션이 아닌 멤버를 숨기고 싶으면 `Never`를 쓴다.

> **📌 프록시는 "원시 뷰"를 없애지 않는다**
>
> 프록시를 붙여도 감시 창에는 **Raw View**(원시 뷰) 노드가 남아 실제 필드를 볼 수 있다. 프록시가 뭔가를 잘못 계산하고 있다는 의심이 들면 여기를 펼치거나 식에 `,raw`를 붙인다. 프록시는 정보를 숨기는 것이 아니라 **기본 표시를 바꾸는 것**이다.

### 사용자 정의 시각화 도구

`[DebuggerVisualizer]`는 어셈블리 수준 특성으로, 감시 창의 돋보기 아이콘을 눌렀을 때 뜨는 **전용 창**을 등록한다. Visual Studio가 문자열을 텍스트/XML/JSON/HTML 뷰어로 보여주는 것, `DataSet`을 표로 보여주는 것이 모두 이 메커니즘이다.

직접 만들 가치가 있는 경우는 좁다. **텍스트 한 줄로 표현할 수 없는 자료 구조**여야 한다 — 이미지 버퍼, 공간 인덱스, 상태 기계 그래프, 큰 행렬 같은 것이다. 그 외에는 `[DebuggerDisplay]`와 `[DebuggerTypeProxy]`로 충분하고, 시각화 도구는 Visual Studio 전용이라 VS Code·Rider·WinDbg 사용자에게는 아무 효과가 없다.

> **⚠️ 시각화 도구는 대상 프로세스의 객체를 직렬화해서 가져온다**
>
> 시각화 도구는 별도 프로세스(디버거)에서 실행되므로, 대상 객체를 직렬화해 전달받아야 한다. 직렬화할 수 없는 타입이거나 그래프가 거대하면 실패하거나 아주 느려진다. 감시 창의 다른 특성들과 마찬가지로 **"보는 행위가 비싸질 수 있다"**는 원칙이 여기에도 적용된다.

### 성능과 배포 관점

디버거 특성은 런타임 동작을 바꾸지 않는다. 하지만 **공짜는 아니다.**

- 특성은 메타데이터로 어셈블리에 남는다. `[DebuggerDisplay]` 문자열도 그대로 들어간다. 수천 개 타입에 붙이면 어셈블리가 커진다.
- `[DebuggerDisplay]`·프록시가 참조하는 멤버는 **리플렉션으로 접근**된다. 트리밍이나 Native AOT에서 그 멤버가 잘려 나가면 감시 창이 깨진다(57.14절). 라이브러리라면 프록시 타입에 `[DynamicallyAccessedMembers]`를 고려하거나, 트리밍 대상 구성에서 프록시를 유지하도록 지정해야 한다.
- `[DebuggerStepThrough]`는 **JIT에 아무 영향이 없다.** 인라이닝이나 최적화와는 무관하다.

> **💡 라이브러리라면 `DebuggerDisplay`를 공개 계약처럼 다뤄라**
>
> 라이브러리 타입의 감시 창 표시는 사용자의 디버깅 경험을 직접 결정한다. 핵심 타입 열 개 정도에 `[DebuggerDisplay]`를, 컬렉션류에 `[DebuggerTypeProxy]`를 붙이는 투자는 문서 몇 페이지보다 효과가 크다. 반대로 애플리케이션 코드에 특성을 남발할 필요는 없다 — 대부분은 `record`로 만들거나 `ToString()`을 제대로 쓰는 것으로 충분하다.

## 74.3 조건부 중단점, 추적점, 데이터 중단점

중단점을 거는 것 자체는 배울 게 없다. 편집기 여백을 클릭하거나 `F9`를 누르면 빨간 원이 생기고, `F5`로 실행하면 그 줄에서 멈춘다. 멈춘 상태를 **중단 모드(break mode)** 라고 하며, 다음에 실행될 줄이 노랗게 강조된다.

배울 것은 그다음이다. **루프가 10만 번 도는데 문제는 87,342번째에서만 난다면 `F5`를 8만 번 누를 수는 없다.**

### 중단점 종류와 선택 기준

| 종류 | 걸리는 조건 | 언제 쓰나 | 대가 |
|---|---|---|---|
| **일반 중단점** | 그 줄에 도달할 때마다 | 기본 | 없음 |
| **조건부 중단점(condition)** | 식이 `true`일 때만 | "`order.Id == 4711`일 때만 보고 싶다" | **매우 비싸다.** 히트마다 식을 평가한다 |
| **히트 카운트(hit count)** | N번째 / N번마다 / N번 이후 | "3번째 재시도부터", "1000번마다 샘플링" | 조건식보다 훨씬 싸다 |
| **필터(filter)** | 특정 스레드·프로세스·머신에서만 | 멀티스레드 버그, 워커 하나만 관찰 | 낮음 |
| **추적점(tracepoint / logpoint)** | 걸리되 **멈추지 않고** 메시지만 출력 | 타이밍에 민감한 버그, 경쟁 조건 | 히트마다 순간 정지 |
| **함수 중단점** | 메서드 이름으로. 소스 없이도 | 라이브러리 내부, 어느 파일인지 모를 때 | 오버로드 전부에 걸릴 수 있음 |
| **데이터 중단점** | 특정 객체의 **필드 값이 바뀔 때** | "누가 이 값을 null로 만들었나" | 세션 한정. 개수 제한 |
| **종속 중단점** ※VS 2022 | 다른 중단점이 먼저 걸린 뒤에만 | "A 경로를 지나온 경우의 B만" | 낮음 |
| **임시 중단점** ※VS 2022 | 한 번 걸리고 스스로 사라짐 | 일회성 확인 | 없음 |
| **예외 중단점** | 예외가 던져질 때 / 처리되지 않을 때 | 74.1절 참조 | 예외가 잦으면 매우 느림 |

### 조건부 중단점

중단점을 우클릭해 **조건(Conditions)** 을 연다. Visual Studio는 `조건식`·`히트 카운트`·`필터` 세 종류를 한 중단점에 조합할 수 있고, VS Code는 `Edit Breakpoint...`에서 식과 히트 카운트를 지정한다.

```csharp
// 이 줄에 중단점을 걸고 조건을 answer < 9 로 지정한다
WriteLine($"{a} + {b} = {answer}");
```

조건식은 **평가 결과가 `true`여야 중단**하는 형태이거나, **값이 변경되었을 때** 중단하는 형태를 고를 수 있다. 후자는 감시 대상 식이 이전 히트와 달라진 경우에만 멈춘다 — 상태가 흔들리는 순간을 잡을 때 유용하다.

> **⚠️ 조건부 중단점은 프로그램을 100배 느리게 만들 수 있다**
>
> 조건식은 **대상 프로세스 안에서** 매 히트마다 평가된다. 디버거가 프로세스를 멈추고, 식을 해석하고, 필요하면 함수 평가를 하고, 다시 재개한다. 히트당 수십~수백 마이크로초가 든다. 초당 수만 번 도는 루프에 조건부 중단점을 걸면 프로그램은 사실상 정지한다. 더 나쁜 것은 **타이밍이 바뀌어 버그가 재현되지 않는 것**이다.
>
> 대안은 셋이다. (1) 히트 카운트로 대체할 수 있으면 그렇게 한다. (2) 조건을 코드로 내린다 — `if (order.Id == 4711) Debugger.Break();`는 조건 평가가 네이티브 코드로 컴파일되므로 비교가 안 될 만큼 빠르다. (3) 중단 대신 로그를 남긴다.

코드로 내리는 방식은 이렇게 쓴다.

```csharp
foreach (var order in orders)
{
    // 디버거가 붙어 있을 때만, 그리고 관심 있는 데이터일 때만 멈춘다.
    if (Debugger.IsAttached && order.Id == 4711)
        Debugger.Break();

    Process(order);
}
```

`Debugger.Break()`는 `[Conditional]`이 아니므로 Release 빌드에도 남는다(73.2절). 임시 조사용이라면 `#if DEBUG`로 감싸는 것이 안전하다.

### 히트 카운트와 필터

**히트 카운트**는 중단점이 몇 번째로 걸릴 때 실제로 멈출지를 정한다. 세 가지 모드가 있다.

- `= N` — 정확히 N번째 히트에만
- `≥ N` — N번째부터 계속
- `배수 N` — N, 2N, 3N... 번째마다 (샘플링)

조건식과 달리 **카운터를 하나 증가시키는 것이 전부**라 부담이 훨씬 적다. "루프 87,342번째"를 잡는 데는 조건식이 아니라 히트 카운트를 써야 한다.

**필터**는 어느 스레드·프로세스에서 걸릴지를 제한한다. 사용할 수 있는 항목은 다음과 같다.

| 필터 항목 | 예 |
|---|---|
| `ThreadName` | `ThreadName == "Worker-3"` |
| `ThreadId` | `ThreadId == 0x1a2c` |
| `ProcessName` | `ProcessName == "MyApp"` |
| `ProcessId` | `ProcessId == 12345` |
| `MachineName` | `MachineName == "BUILD-01"` |

`&`, `|`, `!`, 괄호로 조합할 수 있다. 스레드 여덟 개가 같은 코드를 도는데 하나만 관찰하고 싶을 때 유일하게 실용적인 수단이다. 이를 위해 **스레드에 이름을 붙여 두는 습관**이 결정적으로 유용해진다.

```csharp
var worker = new Thread(WorkerLoop) { Name = $"Worker-{index}", IsBackground = true };
worker.Start();
```

> **💡 스레드 이름은 디버깅 자산이다**
>
> `Thread.CurrentThread.Name`은 스레드 창, 병렬 스택 창, 중단점 필터, 그리고 덤프의 `!threads` 출력에서 전부 쓰인다. 이름 없는 스레드가 12개인 덤프와, `Worker-3`·`FlushTimer`·`RetryPump`로 이름 붙은 덤프는 분석 난이도가 다르다. 스레드 풀 스레드는 이름을 붙일 수 없지만(재사용되므로), 직접 만든 스레드에는 예외 없이 이름을 붙여라.

### 추적점(tracepoint) — 멈추지 않는 중단점

**추적점**은 중단점의 "적중 시 동작(When Hit)"을 "메시지를 출력하고 계속 실행"으로 설정한 것이다. VS Code에서는 **로그포인트(logpoint)** 라고 부른다. 코드를 고치지 않고 로그를 추가하는 셈이다.

메시지 안에는 중괄호로 식을 넣고, 달러 기호로 시작하는 의사 변수를 쓸 수 있다.

| 의사 변수 | 뜻 |
|---|---|
| `$FUNCTION` | 현재 함수 이름 |
| `$CALLER` | 호출한 함수 이름 |
| `$CALLSTACK` | 호출 스택 전체 |
| `$TID` | 스레드 ID |
| `$TNAME` | 스레드 이름 |
| `$PID` | 프로세스 ID |
| `$PNAME` | 프로세스 이름 |

```text
[{$TNAME}] {$FUNCTION} 진입: orderId={order.Id}, total={order.Total}
```

> **💡 경쟁 조건에는 중단점 대신 추적점을 써라**
>
> 멀티스레드 버그에 일반 중단점을 걸면 그 스레드만 멈추고 다른 스레드는 계속 달린다. 관찰 행위가 스레드 간 타이밍을 완전히 바꾸므로 버그는 사라진다. 추적점은 멈추지 않으므로 훨씬 덜 침습적이다. 그래도 히트마다 순간적인 정지는 발생하니, 마이크로초 단위 경쟁이라면 추적점조차 못 쓴다 — 그때는 코드에 링 버퍼 로깅을 넣거나 `dotnet-trace`(73.9절)로 이벤트를 수집하는 쪽으로 간다.

> **⚠️ 추적점 출력은 디버그 출력 창으로만 간다**
>
> 추적점 메시지는 디버거의 출력 창(Visual Studio의 `출력`, VS Code의 `디버그 콘솔`)에 나타난다. 표준 출력이 아니므로 리다이렉트되지 않고, 애플리케이션 로그에도 남지 않으며, 디버거를 떼면 사라진다. 남겨야 할 정보라면 추적점이 아니라 진짜 로깅(75장)으로 옮겨야 한다.

### 데이터 중단점 — "누가 이 값을 바꿨나"

`null`이 아니어야 할 필드가 어느 순간 `null`이 된다. 대입하는 곳이 스무 군데다. 이럴 때 쓰는 것이 **데이터 중단점**이다. Visual Studio 2019 16.4부터 .NET Core 3.0 이상 대상에서 관리 코드에도 쓸 수 있다.

사용법은 코드가 아니라 **런타임 객체에서 시작**한다.

1. 문제의 객체가 살아 있는 지점에서 중단한다.
2. `자동`·`지역`·`조사식` 창에서 그 객체를 펼친다.
3. 대상 **필드**를 우클릭하고 `값이 변경되면 중단`을 고른다.
4. 실행을 재개한다. 그 필드에 쓰기가 일어나는 순간 멈춘다.

```csharp
public sealed class SessionCache
{
    // 이 필드가 어느 순간 null이 된다. 대입 지점이 여러 곳이라 코드 검색으로는 못 찾는다.
    IReadOnlyDictionary<string, Session>? _snapshot;
    // ...
}
```

> **⚠️ 데이터 중단점의 제약을 알고 써라**
>
> - **특정 인스턴스의 특정 필드**에만 걸린다. "모든 `SessionCache`의 `_snapshot`"이 아니라 "이 객체의 `_snapshot`"이다.
> - **지역 변수에는 걸 수 없다.** 객체의 필드나 배열 원소여야 한다.
> - **개수 제한이 있다.** 하드웨어 감시 레지스터 수에 묶이는 네이티브 데이터 중단점만큼 빡빡하지는 않지만 무제한이 아니다.
> - **세션 간 유지되지 않는다.** 다음 디버깅 세션에서는 객체 주소가 달라지므로 다시 걸어야 한다.
> - **대상 객체가 GC되면 해제된다.**
> - GC가 객체를 **이동**시키면 디버거가 추적을 유지해야 한다. 관리 데이터 중단점이 성능에 영향을 주는 이유이며, 서버 GC + 큰 힙에서는 체감할 만큼 느려질 수 있다.

데이터 중단점을 못 쓰는 상황(지역 변수, .NET Framework, 여러 인스턴스 동시 감시)의 대안은 **속성으로 바꾸고 setter에 중단점을 거는 것**이다.

```csharp
IReadOnlyDictionary<string, Session>? _snapshot;

// 조사 기간에만 필드를 속성 뒤로 숨긴다.
IReadOnlyDictionary<string, Session>? Snapshot
{
    get => _snapshot;
    set
    {
        // 여기에 조건부 중단점을 건다: value == null
        _snapshot = value;
    }
}
```

### 함수 중단점과 종속 중단점

**함수 중단점**은 파일과 줄이 아니라 **이름으로** 건다. `디버그 > 새 중단점 > 함수 중단점`에서 `MyApp.Services.OrderService.Submit` 형태로 입력한다. 소스가 없는 라이브러리 메서드, 또는 "어느 파일에 있는지 모르지만 이름은 아는" 경우에 쓴다. 오버로드가 여러 개면 전부에 걸리므로, 매개변수 개수를 지정해 좁힐 수 있다.

**종속 중단점**(※Visual Studio 2022)은 "중단점 B는 중단점 A가 먼저 걸린 뒤에만 활성"이라는 관계를 만든다. 공유 헬퍼 메서드가 여러 경로에서 호출될 때, 관심 있는 경로를 지나온 호출만 잡는 데 쓴다. 조건식으로 같은 일을 하려면 호출 스택을 검사해야 하는데 그건 사실상 불가능하다.

**임시 중단점**(※Visual Studio 2022)은 한 번 걸린 뒤 스스로 사라진다. "여기 한 번만 와 보고 싶다"에 정확히 맞는다.

> **📌 중단점 창을 레이블로 관리하라**
>
> 중단점 창(`디버그 > 창 > 중단점`)에서 각 중단점에 **레이블**을 붙이고, 레이블 단위로 켜고 끌 수 있다. 조사 시나리오별로 중단점 세트를 만들어 두면 "결제 경로 세트"와 "재시도 경로 세트"를 전환하며 쓸 수 있다. 중단점 세트는 내보내기/가져오기(XML)로 팀과 공유할 수도 있다. 열 개 넘는 중단점을 매번 다시 거는 것은 낭비다.

### 중단 모드에서 쓰는 창

멈춘 뒤에 무엇을 보는가도 중요하다.

| 창 | 보는 것 | 특히 유용한 순간 |
|---|---|---|
| **지역(Locals)** | 현재 프레임의 지역 변수와 매개변수 | 항상 열어 둔다 |
| **자동(Autos)** | 현재 줄 주변에서 쓰인 변수 | 긴 메서드에서 잡음을 줄인다 |
| **조사식(Watch)** | 직접 입력한 식 | `list.Count(x => x.IsFailed)` 같은 즉석 집계 |
| **호출 스택(Call Stack)** | 프레임 목록 | 예외가 어디서 왔는지. **남의 코드에서 났을 때 특히** |
| **직접 실행(Immediate)** | 임의의 식·문 실행 | 상태를 바꿔 가며 가설을 검증 |
| **출력(Output)** | 모듈 로드, 추적점, `Debug.WriteLine` | 어떤 어셈블리가 언제 로드됐는지 |
| **예외 설정** | 어떤 예외에서 멈출지 | 74.1절 |
| **모듈(Modules)** | 로드된 어셈블리와 심볼 상태 | 74.6절 |
| **스레드 / 병렬 스택 / 작업** | 동시성 상태 | 74.4절 |

> **⚠️ 직접 실행 창의 식 평가는 프로그램 상태를 바꾼다**
>
> 직접 실행 창이나 조사식 창에서 메서드를 호출하면 그 메서드가 **진짜로 실행된다.** `list.Remove(x)`를 조사식에 넣으면 항목이 실제로 지워진다. 큐를 `Dequeue()`해 보면 항목이 사라진다. 디버깅 중에만 나타나는 이상 동작을 쫓다 보면 범인이 자기 조사식인 경우가 드물지 않다. 컬렉션을 볼 때는 `ToArray()`처럼 **읽기 전용 사본을 만드는 식**을 쓰는 습관이 안전하다.

## 74.4 병렬·비동기 코드 디버깅

동기 단일 스레드 코드의 디버깅은 잘 정의된 문제다. 프로그램 카운터가 하나고, 스택이 하나고, "다음 줄"이라는 개념이 명확하다. 스레드가 여덟 개가 되고 `await`가 끼어드는 순간 이 셋이 전부 무너진다.

### 무너지는 세 가지 전제

1. **"실행 위치가 하나"** — 이제 스레드마다 하나씩이다. `F10`을 누르면 현재 스레드만 한 줄 나아가고, 나머지 스레드는 그동안 자유롭게 달린다. 디버거로 관찰하는 순간 타이밍이 바뀌므로 경쟁 조건은 종종 사라진다.
2. **"스택이 호출 이력"** — `await` 뒤의 코드는 원래 호출자와 **다른 스레드의 스택 위에서** 실행된다. 물리적 스택에는 호출자가 없다.
3. **"멈추면 상태가 고정된다"** — 중단점에 걸리면 기본적으로 **모든 관리 스레드가 멈춘다.** 하지만 네이티브 스레드, 타이머, GC 파이널라이저, 그리고 원격 상대방은 멈추지 않는다. 멈춰 있는 동안 소켓이 타임아웃되고, 분산 잠금이 만료되고, 카프카 컨슈머가 그룹에서 쫓겨난다.

> **⚠️ 디버거에서 오래 멈춰 있으면 "디버깅 때문에 생긴 오류"가 나온다**
>
> 중단점에서 5분간 상태를 살펴본 뒤 `F5`를 누르면 HTTP 클라이언트 타임아웃, `CancellationTokenSource` 만료, DB 연결 끊김, 분산 잠금 손실이 한꺼번에 터진다. 이건 버그가 아니라 디버깅의 부작용이다. 오래 조사할 것 같으면 타임아웃을 개발 구성에서 크게 잡아 두거나, 애초에 덤프를 떠서 정지된 상태를 오프라인으로 보는 편이 낫다.

### 병렬 디버깅 창

| 창 | 보여주는 것 | 핵심 기능 |
|---|---|---|
| **스레드(Threads)** | 관리 스레드 목록: ID, 이름, 위치, 우선순위, 정지 상태 | 스레드 **고정(freeze)/해제(thaw)**, 특정 스레드로 전환 |
| **병렬 스택(Parallel Stacks)** | 모든 스레드/작업의 호출 스택을 **하나의 그래프로 병합** | 공통 프레임을 합쳐 보여준다. 어디에 몰려 있는지 한눈에 |
| **작업(Tasks)** | 살아 있는 `Task` 목록: ID, 상태, 시작 시각, 대기 대상, 할당된 스레드 | 교착·기아 상태에서 "누가 무엇을 기다리는가" |
| **병렬 조사식(Parallel Watch)** | 같은 식을 **모든 스레드에서** 평가해 표로 | 스레드마다 다른 지역 변수 값 비교 |
| **소스에 스레드 표시** | 편집기 여백에 각 스레드 위치 표시 | 어느 줄에 몇 개가 몰려 있는지 |

**병렬 스택 창의 스레드 뷰**가 병렬 디버깅의 출발점이다. 모든 스레드의 스택을 공통 접두사끼리 합쳐 그리므로, "18개 스레드가 전부 `SemaphoreSlim.WaitAsync`에 있다" 같은 사실이 즉시 보인다.

```text
              ┌──────────────────────────┐
              │  18 스레드                │
              │  ThreadPoolWorkQueue      │
              │   .Dispatch()             │
              └────────────┬─────────────┘
                           │
        ┌──────────────────┴───────────────────┐
        │                                      │
┌───────▼─────────┐                  ┌─────────▼────────┐
│  16 스레드       │                  │   2 스레드        │
│  OrderService    │                  │  HealthCheck      │
│   .SubmitAsync   │                  │   .PingAsync      │
│  SemaphoreSlim   │                  │  HttpClient       │
│   .Wait()  ←대기 │                  │   .SendAsync      │
└──────────────────┘                  └───────────────────┘
```

이 그림 하나가 "커넥션 풀 크기 16짜리 세마포어에 전부 걸려 있다"는 결론까지 데려간다.

> **💡 스레드 고정(freeze)으로 재현 순서를 강제하라**
>
> 스레드 창에서 스레드를 고정하면 그 스레드는 재개해도 실행되지 않는다. 경쟁 조건을 **의도적으로 만들 때** 쓴다. 스레드 A를 임계 구역 진입 직전에 세우고, 스레드 B만 풀어 끝까지 보낸 뒤, A를 녹여 어떤 일이 벌어지는지 본다. 코드에 `Thread.Sleep`을 심지 않고 인터리빙을 제어하는 유일한 방법이다. 다만 고정을 풀지 않은 채 세션을 끝내면 앱이 행에 걸리므로 반드시 해제하고 나와야 한다.

### 비동기 호출 스택이 끊기는 이유

47.7절에서 컴파일러가 `async` 메서드를 **상태 기계**로 바꾸는 과정을 봤다. 그 결과가 디버깅에 직접적인 영향을 준다.

```csharp
async Task<Report> BuildReportAsync(int id)
{
    var raw = await _repo.LoadAsync(id);      // ← 여기서 반환된다
    var enriched = await _enricher.RunAsync(raw);
    return Report.From(enriched);
}
```

첫 `await`에서 작업이 완료되지 않으면 `BuildReportAsync`는 **반환한다.** 스택 프레임은 사라진다. 나중에 `LoadAsync`가 완료되면 스레드 풀 스레드 하나가 상태 기계의 `MoveNext()`를 호출해 두 번째 줄부터 이어간다. 그 시점의 **물리적 스택**은 이렇다.

```text
[물리적 스택 — 재개 시점]           [사람이 기대하는 논리적 스택]
                                    
ThreadPoolWorkQueue.Dispatch()      Controller.GetReport()
  ↓                                   ↓
AwaitTaskContinuation.Run()         ReportService.CreateAsync()
  ↓                                   ↓
StateMachineBox.MoveNext()          BuildReportAsync()      ← 지금 여기
  ↓                                 
BuildReportAsync.MoveNext()         

   "누가 불렀는지" 정보가 없다        "누가 불렀는지"가 있다
```

물리적 스택 어디에도 `Controller.GetReport`가 없다. 호출자가 이미 반환했기 때문이다. 이것이 **비동기 스택이 끊긴다**는 말의 정확한 의미다.

Visual Studio는 이 간극을 **논리적 비동기 호출 스택**으로 메운다. 상태 기계 객체가 자신을 이어받을 연속(continuation)을 참조하고 있으므로, 디버거는 그 사슬을 거꾸로 따라가 논리적 호출자를 복원한다. 호출 스택 창의 `[비동기 메서드 다시 시작]`(`[Resuming Async Method]`) 구분선 아래가 그렇게 복원된 프레임이다.

문제는 **이 복원이 항상 되지는 않는다**는 것이다.

| 끊기는 원인 | 왜 | 대안 |
|---|---|---|
| `async void` | 연속을 담을 `Task`가 없다. 사슬이 시작부터 없다 | `async Task`로 바꾼다(47.14절). 이벤트 핸들러라면 즉시 `Task` 메서드로 위임 |
| 즉발-망각(fire-and-forget) | 반환 `Task`를 아무도 참조하지 않으므로 상류 링크가 끊긴다 | 반환 `Task`를 보관하거나 전용 실행기로 감싸 상관관계 ID를 붙인다 |
| `Task.Run(() => ...)` 경계 | 새 작업이 시작되며 논리적 부모가 바뀐다 | 경계 앞뒤로 로깅. `Activity`로 잇는다(75.4절) |
| `TaskCompletionSource` 브리지 | 완료를 외부에서 설정하므로 "누가 완료시켰는지"가 코드에 없다 | 완료 지점에 추적점/로그를 남긴다 |
| 콜백 기반 API(APM/EAP 래핑) | 델리게이트가 스택 관계를 대신하지 않는다 | 래퍼 진입/이탈 로깅 |
| 사용자 정의 awaitable | 디버거가 아는 상태 기계 패턴을 벗어난다 | `Task` 기반으로 감싼다 |
| 최적화된 릴리스 빌드 | 상태 기계 필드와 연속 참조가 최적화될 수 있다 | 조사 시점에는 최적화를 끄거나 덤프 분석으로 전환 |
| 동기 완료 경로 | 완료된 작업은 `await`가 그냥 통과하므로 상태 기계 자체가 만들어지지 않는다 | 이 경우는 오히려 물리 스택이 정확하다 |

> **⚠️ "내 코드만"이 켜져 있으면 상태 기계가 보이지 않는다**
>
> 기본 설정에서 Visual Studio는 컴파일러가 생성한 `MoveNext`와 `AsyncTaskMethodBuilder` 프레임을 감춘다. 편해 보이지만, 비동기 흐름이 이상할 때는 그 감춰진 프레임이 바로 답이다. `도구 > 옵션 > 디버깅`에서 **"내 코드만"을 끄고** 다시 보면 상태 기계 상자와 빌더가 드러난다. 반대로 평소 개발에서는 켜 두는 편이 낫다.

### 예외 스택 트레이스에서의 비동기

비동기 메서드에서 던져진 예외는 `Task`에 저장됐다가 `await` 지점에서 다시 던져진다. 이때 원본 스택을 잃지 않기 위해 런타임은 `ExceptionDispatchInfo`로 캡처·복원한다. 그 결과 스택 트레이스에 다음 구분선이 나타난다.

```text
System.InvalidOperationException: 재고가 부족하다.
   at Warehouse.Reserve(Int32 sku, Int32 qty) in /src/Warehouse.cs:line 88
   at Warehouse.ReserveAsync(Int32 sku, Int32 qty) in /src/Warehouse.cs:line 71
--- End of stack trace from previous location ---
   at OrderService.SubmitAsync(Order order) in /src/OrderService.cs:line 42
   at OrderController.Post(OrderDto dto) in /src/OrderController.cs:line 26
```

구분선 **위**가 예외가 실제로 발생한 곳, **아래**가 `await`로 이어받은 곳이다. .NET 5까지는 이 문구가 `--- End of stack trace from previous location where exception was thrown ---`으로 더 길었고, .NET 6에서 짧아졌다. 로그 파서를 쓰고 있다면 런타임 업그레이드 때 걸리는 지점이다.

.NET 6부터 BCL의 비동기 인프라 프레임 상당수에 `[StackTraceHidden]`(73.4절)이 붙어 트레이스가 훨씬 깨끗해졌다. `MoveNext`나 `<>c__DisplayClass` 프레임이 예전만큼 나오지 않는 이유다.

> **⚠️ `Task.Result`와 `.Wait()`는 스택 트레이스를 `AggregateException`으로 감싼다**
>
> `await`는 예외를 **원본 그대로** 다시 던지지만, `.Result`와 `.Wait()`는 `AggregateException`으로 감싼다. 로그에 `AggregateException`이 보이면 코드 어딘가에 동기 대기가 있다는 신호이며, 그 자체가 교착 위험 신호다(47.14절). `ex.Flatten().InnerExceptions`로 풀어야 진짜 원인이 보인다(32.13절).

### 덤프에서 비동기 상태 읽기 — `!dumpasync`

라이브 디버거가 없는 상황, 즉 프로덕션 덤프만 있는 상황에서는 병렬 스택 창도 작업 창도 쓸 수 없다. 이때 SOS의 `dumpasync`가 상태 기계를 힙에서 직접 찾아 준다.

```text
> dumpasync -stacks

STACK 1
0000023f8a1c4d90 0000023f8a1c4d68 (0) OrderService+<SubmitAsync>d__12
0000023f8a1c4e20 0000023f8a1c4df8 (1) ReportService+<CreateAsync>d__4
0000023f8a1c4f10 0000023f8a1c4ee8 (2) Controller+<PostAsync>d__7

STACK 2
0000023f8a1d1200 0000023f8a1d11d8 (0) PaymentGateway+<ChargeAsync>d__3
...
```

물리적 스택에는 존재하지 않는 **논리적 비동기 사슬**을 힙의 상태 기계 객체에서 복원한 것이다. 각 상태 기계 객체 주소를 `dumpobj`로 열면 `<>1__state`(현재 상태 번호)와 캡처된 지역 변수를 볼 수 있다.

```text
> dumpobj 0000023f8a1c4d68
Name:        OrderService+<SubmitAsync>d__12
Fields:
      MT    Field   Offset                 Type VT     Attr            Value Name
...              4000123        8         System.Int32  1 instance          1 <>1__state
...              4000124       10   ...OrderService  0 instance 0000023f8a1b0090 <>4__this
...              4000125       18       ...Order  0 instance 0000023f8a1c22c8 order
```

`<>1__state` 값의 의미는 47.7절에서 다룬 그대로다. `-1`은 시작 전 또는 실행 중, `-2`는 완료, `0` 이상은 **그 번호의 `await`에서 대기 중**이다. 즉 이 값 하나로 "어느 `await`에 멈춰 있는가"를 확정할 수 있다.

| 명령 | 하는 일 |
|---|---|
| `dumpasync` | 힙의 비동기 상태 기계 목록 |
| `dumpasync -stacks` | 상태 기계를 연속 사슬로 묶어 논리적 스택으로 |
| `dumpasync -completed` | 완료된 것까지 포함(기본은 미완료만) |
| `dumpasync -fields` | 각 상태 기계의 필드 값까지 |
| `dumpasync -roots` | 이 상태 기계를 살려두는 루트 |
| `dumpasync -type <이름>` | 타입 이름으로 필터 |

> **💡 `dumpasync -stacks`는 비동기 교착의 1차 진단 도구다**
>
> "요청이 응답하지 않는다"는 신고를 받고 덤프를 떴는데 `clrstack`에 보이는 스레드가 전부 유휴 상태라면, 일이 **스레드가 아니라 힙에 멈춰 있는** 것이다. 완료되지 않은 비동기 사슬 수백 개가 힙에 쌓여 있고 아무도 그것을 완료시키지 못하는 상태다. `dumpasync -stacks`로 어느 `await`에서 멈춰 있는지 세어 보면 원인 지점이 한두 곳으로 좁혀진다. 74.5절의 교착 워크스루가 `!syncblk`로 잡는 것은 **동기** 잠금 교착이고, 비동기 대기 교착은 이 명령의 영역이다.

### 스레드 풀 기아(starvation)

비동기 코드에서 가장 흔한 성능 사고는 교착이 아니라 **스레드 풀 기아**다. 증상이 교착과 비슷해서 혼동된다.

| 신호 | 어디서 보나 |
|---|---|
| `ThreadPool Queue Length`가 계속 증가 | `dotnet-counters monitor System.Runtime`(73.9절) |
| `ThreadPool Threads Count`가 천천히 증가 | 같은 곳. 풀이 초당 한두 개씩 주입하고 있다 |
| CPU는 낮은데 처리량이 떨어짐 | 메트릭 |
| 다수 스레드가 `Task.Result`·`Wait`·`GetAwaiter().GetResult()`에 있음 | `clrstack -all`, 병렬 스택 창 |
| `!threadpool` 출력의 큐 길이 | 덤프 분석 |

원인은 거의 항상 **sync-over-async**다. 비동기 메서드를 동기적으로 기다리는 코드가 스레드 풀 스레드를 붙잡고, 그 스레드가 부족해 완료 콜백이 실행되지 못하고, 그래서 대기가 끝나지 않는 악순환이다(47.14절). 디버깅 관점의 판별법은 간단하다. **`clrstack -all` 출력에서 `Wait`·`Result`·`GetResult`를 세어라.** 스레드 풀 스레드의 절반 이상이 거기 있으면 확정이다.

> **⚠️ 스레드 풀 기아는 "천천히 회복되는" 것처럼 보인다**
>
> 스레드 풀은 기아를 감지하면 스레드를 **주입**한다. 다만 주입 속도가 초당 1~2개로 매우 느리다. 그래서 부하가 걸리면 응답 시간이 몇 분에 걸쳐 서서히 나빠지다가, 스레드가 충분히 주입되면 갑자기 회복된다. 이 패턴 — **느린 악화와 급격한 회복** — 을 보면 잠금이 아니라 스레드 풀을 의심해야 한다. 잠금 교착은 회복되지 않는다.

## 74.5 메모리 덤프 생성과 사후 분석

### 세 가지 침습성

애플리케이션 상태를 분석하는 방법은 침습성(invasiveness) 기준으로 셋으로 나뉜다.

- **모니터링** — 애플리케이션이 스스로 내보내는 진단 정보를 밖에서 관찰한다. 추적이나 샘플링을 쓴다. 오버헤드가 충분히 낮으면 프로덕션에서 상시 사용할 수 있다.
- **코어 덤프(메모리 덤프)** — 특정 시점의 프로세스 메모리 상태를 파일로 저장한다. 대부분 메모리 전체를 저장하므로 수십 기가바이트가 될 수 있지만, 다른 머신에서도 분석할 수 있고 아주 상세한 정보를 준다. 다만 **한 시점의 스냅숏**이므로 시간에 따른 변화가 필요한 문제(누수 같은)에는 결론을 내기 어렵다. 그런 경우 둘 이상을 떠서 비교한다. 수집 자체는 침습적이다 — 프로세스가 수 초에서 수 분까지 멈춘다. 실패 후 자동 생성하는 용법이 특히 중요하며, 이를 **사후 분석(post-mortem analysis)** 이라 한다. 이 맥락에서 만들어진 덤프를 **크래시 덤프**라 부르지만, 실무에서 두 용어는 사실상 교환 가능하게 쓰인다.
- **라이브 디버깅** — 가장 침습적이다. 디버거를 붙여 한 단계씩 실행을 분석한다. 개발 머신에서는 기본이지만, 보안이 요구되거나 민감한 프로덕션 환경에서는 앞의 두 방법에 의존해야 한다.

이 장의 나머지는 대부분 두 번째에 관한 것이다. **프로덕션 디버깅은 덤프 디버깅이다.**

### 디버거냐 프로파일러냐 덤프냐

덤프 이야기를 시작하기 전에 갈림길을 정리해 둔다. 세 도구는 대체재가 아니라 **답할 수 있는 질문이 다르다.**

| 질문의 형태 | 도구 | 이유 |
|---|---|---|
| "이 줄에서 값이 왜 이런가" | **디버거** | 임의 시점에 멈춰 상태를 조작하며 가설을 검증할 수 있다 |
| "어디가 느린가 / 어디서 할당하는가" | **프로파일러** | 전체 실행에 대한 집계가 필요하다. 한 시점의 스냅숏으로는 알 수 없다 |
| "지금 이 프로세스가 왜 멈춰 있나" | **덤프** | 멈춘 상태 그 자체가 답이다. 재현할 필요가 없다 |
| "시간에 따라 무엇이 쌓이는가" | 프로파일러 또는 **덤프 2개 비교** | 변화량이 필요하다 (66.4절) |

프로파일링 쪽은 이미 다룬 장이 있다. Visual Studio 2022의 **성능 프로파일러**(`디버그 > 성능 프로파일러`)는 .NET 개체 할당 추적 도구로 시간에 따른 활성 개체 수, `할당`·`호출 트리`·`함수`·`컬렉션` 탭을 제공하고, 메서드 단위 할당 수와 바이트 수, 수집된 타입과 살아남은 타입의 비율까지 내려간다. JetBrains **dotMemory**는 총 사용량·비관리 메모리·세대별 힙·LOH를 시간축으로 그려 준다. **dotTrace**는 네 가지 프로파일링 모드를 제공한다 — **샘플링**(호출 시간의 정확한 측정, 대부분의 경우에 최적), **추적**(호출 **횟수**의 정확한 측정, 알고리즘 복잡도 분석에 적합), **한 줄씩**(고급 용도 전용), **타임라인**(시간적 성능 데이터 측정, 멀티스레드 분석 포함). 도구별 비교는 66.10절, 측정 방법론 전반은 67장에 있다.

> **⚠️ 프로파일러를 붙인 채 디버깅하지 마라**
>
> 프로파일러와 디버거는 둘 다 대상 프로세스를 침습적으로 계측한다. 동시에 붙이면 측정값이 무의미해지고(디버거의 정지 시간이 프로파일 결과에 섞인다), 도구에 따라 아예 붙지 않는다. **성능 문제는 프로파일러로 위치를 좁힌 뒤, 그 지점을 디버거로 들여다보는 순서**가 옳다. 반대로 하면 두 번 다 틀린 답을 얻는다.

### 덤프를 만드는 다섯 경로

| 경로 | 명령/조작 | 플랫폼 | 트리거 조건 | 언제 쓰나 |
|---|---|---|---|---|
| **작업 관리자** | 프로세스 우클릭 → `덤프 파일 만들기` | Windows | 수동만 | 급할 때. 도구가 아무것도 없을 때 |
| **Visual Studio** | 중단점/예외로 멈춘 상태에서 `디버그 > 다른 이름으로 덤프 저장` | Windows | 디버깅 중 수동 | 재현된 상태를 동료에게 보낼 때 |
| **ProcDump** | `procdump -ma <pid>` | Windows / Linux | **조건 지정 가능**(CPU·메모리·예외·시간·종료) | "5분 뒤가 아니라 문제가 난 순간"이 필요할 때 |
| **`dotnet-dump`** | `dotnet-dump collect -p <pid>` | 크로스 플랫폼 | 수동만 | .NET 프로세스의 표준 수단. 컨테이너 |
| **자동 크래시 덤프** | `DOTNET_DbgEnableMiniDump=1` 등 환경 변수 | 크로스 플랫폼 ※.NET 5+ | **처리되지 않은 예외로 종료할 때** | 재현 불가 크래시. 프로덕션 상시 설정 |

각각을 실제 명령으로 보자.

**작업 관리자.** `세부 정보` 탭에서 프로세스를 우클릭하고 `덤프 파일 만들기`를 고른다. 전체 메모리 덤프가 `%LOCALAPPDATA%\Temp`에 저장된다. 조건 지정도 자동화도 불가능하고, 32비트 프로세스를 64비트 작업 관리자로 뜨면 관리 스택이 제대로 안 읽히는 고전적 문제가 있다. **응급 수단 이상으로 쓰지 마라.**

**Visual Studio.** 디버깅 중 프로그램이 중단점이나 예외에서 멈추면 `디버그` 메뉴의 `다른 이름으로 덤프 저장`이 활성화된다. 저장되는 것은 **힙을 포함한 미니덤프**로, 그 시점의 메모리 스냅숏·실행 중이던 프로세스·로드된 모듈 목록을 담는다. 스택·스레드·변수를 그 순간 그대로 조사할 수 있다. 이 파일을 다시 열려면 `파일 > 열기 > 파일`로 `.dmp`를 고르면 되고, 요약 페이지에 마지막 갱신 시각, 프로세스 이름, 컴퓨터 아키텍처, 예외 코드와 정보, 힙 정보, 오류 정보, CLR·OS 버전, 그리고 이름·버전·경로가 붙은 모듈 목록이 나온다. 테스트 중 크래시를 만났을 때, 그리고 **고객 환경의 크래시를 내 컴퓨터에서 재현할 수 없을 때** 저장한다.

**ProcDump.** Sysinternals 도구다. 프로세스 ID만 알면 된다.

```bash
procdump -ma 12345                       # 전체 메모리 덤프 즉시
procdump -ma -e 12345                    # 처리되지 않은 예외 발생 시
procdump -ma -e 1 -f "OutOfMemory" 12345  # 1차 예외 중 필터에 걸리는 것
procdump -ma -c 90 -s 10 -n 3 12345      # CPU 90%가 10초 지속되면, 최대 3회
procdump -ma -m 2000 12345               # 커밋 메모리가 2GB를 넘으면
procdump -ma -t 12345                    # 프로세스 종료 시
procdump -ma -w MyApp.exe                # 아직 안 뜬 프로세스를 기다렸다가
```

메모리 사용량이나 CPU 소비가 임계치를 넘을 때, 기타 임의의 성능 카운터 값을 조건으로, 또는 주기적으로 덤프를 뜨는 등 트리거 옵션이 매우 많다. 전체 목록은 명령줄 도움말에 있다. **ProcDump는 Linux 버전도 있다.**

**`dotnet-dump`.** Microsoft가 제공하는 크로스 플랫폼 CLI 도구다. 실제로는 EventPipe로 명령을 보내 .NET 애플리케이션이 **스스로 덤프를 뜨게** 한다. 그 결과 런타임과 함께 설치된 `createdump` 바이너리가 실행되어 프로세스 메모리를 파일로 쓴다. 동작하지 않으면 `createdump` 파일의 권한을 확인해야 한다.

```bash
dotnet tool install -g dotnet-dump
dotnet-dump collect -p 12345
dotnet-dump collect -p 12345 --type Heap -o /dumps/app.dmp
```

`--type`은 `Full`·`Heap`·`Mini`·`Triage` 중 하나다. **ProcDump와 달리 트리거 조건을 걸 수 없다.**

`createdump`를 직접 부를 수도 있다. 컨테이너 안에 `dotnet-dump`를 설치할 수 없을 때 유용하다.

```bash
# 런타임과 함께 설치되어 있다
/usr/share/dotnet/shared/Microsoft.NETCore.App/8.0.11/createdump --full -f /dumps/core.%p 12345
```

**자동 크래시 덤프**(※.NET 5+). 재현 불가능한 크래시에 대한 유일한 실용적 답이다. 환경 변수만 설정하면 처리되지 않은 예외로 프로세스가 죽을 때 런타임이 알아서 덤프를 남긴다.

```bash
export DOTNET_DbgEnableMiniDump=1              # 크래시 시 덤프 생성 활성화
export DOTNET_DbgMiniDumpType=2                # 1=Mini 2=Heap 3=Triage 4=Full
export DOTNET_DbgMiniDumpName=/dumps/core.%p   # %p는 PID로 치환된다
export DOTNET_EnableCrashReport=1              # 추가로 .crashreport.json 생성
export DOTNET_CreateDumpDiagnostics=1          # createdump 자체의 진단 출력
```

쿠버네티스라면 `/dumps`에 볼륨을 마운트하고 파드 스펙의 `env`에 위 값을 넣는다. 컨테이너가 죽어도 덤프는 볼륨에 남는다.

> **⚠️ 컨테이너의 `core_pattern`은 호스트 전역이다**
>
> 리눅스에서 커널이 코어 파일을 어디에 쓸지는 `/proc/sys/kernel/core_pattern`이 정한다. 이 값은 **PID 네임스페이스별이 아니라 커널 전역**이다. 컨테이너 안에서 `sysctl`로 바꾸려 해도 안 되고, 바꿀 수 있다면 호스트와 다른 모든 컨테이너에 영향을 준다. 그래서 컨테이너에서는 커널 코어 덤프에 의존하지 말고 **`DOTNET_DbgEnableMiniDump` 경로를 쓰는 것이 정답이다.** 이 경로는 런타임이 `createdump`를 직접 실행하므로 `core_pattern`도 `ulimit -c`도 관여하지 않는다.

> **⚠️ 환경 변수 접두사는 런타임 버전에 따라 다르다**
>
> .NET 5 이전에는 `COMPlus_` 접두사를 썼다(`COMPlus_DbgEnableMiniDump`). .NET 5부터 `DOTNET_` 접두사가 도입됐고 현재 두 접두사가 모두 인식되지만, `DOTNET_`이 우선한다. 오래된 블로그 글을 보고 `COMPlus_`를 쓰면 동작은 하지만, 신규 설정에는 `DOTNET_`을 써라. 접두사를 섞어 쓰면 어느 쪽이 이겼는지 추적하기 어려워진다.

Windows에서 프로세스 전역 자동 덤프가 필요하면 WER(Windows Error Reporting)의 `LocalDumps` 레지스트리 키를 쓴다.

```text
HKLM\SOFTWARE\Microsoft\Windows\Windows Error Reporting\LocalDumps
    DumpFolder  (REG_EXPAND_SZ) = C:\dumps
    DumpCount   (REG_DWORD)     = 5
    DumpType    (REG_DWORD)     = 2      ; 0=커스텀 1=미니 2=전체
```

이쪽은 관리 런타임과 무관하게 OS가 처리하므로 네이티브 크래시(60장의 상호 운용 사고 등)에도 걸린다는 장점이 있다.

### 덤프 종류 — 무엇이 들어 있고 무엇이 없나

| 종류 | 크기 | 포함 | 할 수 있는 것 | 못 하는 것 |
|---|---|---|---|---|
| **Mini** | 수 MB | 스레드 스택, 모듈 목록, 예외 정보 | 스택 읽기, 예외 확인 | 힙 조사, 객체 필드 값 |
| **Triage** | 수 MB | Mini + 개인 정보 제거 시도 | 외부 공유용 1차 분석 | 힙 조사 |
| **Heap** | 관리 힙 크기 정도 | 관리 힙 + 스택 + 모듈 | **대부분의 관리 코드 분석** | 네이티브 힙 상세, 일부 매핑 |
| **Full** | 프로세스 주소 공간 전체 | 모든 커밋 메모리 | 네이티브까지 전부 | — (다만 매우 크다) |

> **💡 기본은 `Heap`이다**
>
> `Full`은 수십 기가바이트가 되어 전송·보관·분석이 전부 고통스럽다. 관리 코드 문제의 95%는 `Heap` 덤프로 충분하다. 네이티브 상호 운용(60장)이 얽혀 있거나 주소 공간 레이아웃 자체를 봐야 하는 경우에만 `Full`로 올려라. 반대로 `Mini`는 스택과 예외만 필요한 경우 — 예를 들어 교착 판정 — 에는 충분하고 훨씬 빠르다.

> **⚠️ 덤프는 프로세스 메모리 전체이고, 거기에는 비밀이 들어 있다**
>
> 전체·힙 덤프에는 연결 문자열, 액세스 토큰, 복호화된 개인 정보, 요청 본문, 세션 키가 **평문으로** 들어 있다. 티켓에 첨부하거나 외부 지원 채널에 올리기 전에 조직의 데이터 처리 정책을 확인해야 한다. 이것은 기술 문제가 아니라 규정 준수 문제다. `Triage` 덤프가 존재하는 이유가 정확히 이것이다.

### 덤프 분석 시작 절차

덤프 파일을 열었을 때 무엇부터 보는가. 순서가 있다. **가설을 세우기 전에 사실을 모은다.**

```text
① 무엇을 열었나        →  런타임 버전, 비트 수, OS, 수집 시각
② 왜 죽었나            →  예외 정보 (있다면)
③ 무엇이 로드되어 있나  →  모듈 목록, 버전, 심볼 상태
④ 스레드가 몇 개인가    →  스레드 목록, 상태, 이름
⑤ 스레드가 뭘 하나      →  전체 스레드의 관리 스택
⑥ 무엇을 기다리나       →  잠금·비동기 사슬
⑦ (필요 시) 힙          →  66장으로
```

Windows에서는 WinDbg, 크로스 플랫폼에서는 `dotnet-dump analyze`를 쓴다. **대부분의 SOS 명령은 이름이 같고 `!` 접두사 유무만 다르다** — WinDbg의 `!clrstack`은 `dotnet-dump analyze`에서 `clrstack`이다. 다만 **예외가 있다**: WinDbg의 `!threads`는 `dotnet-dump analyze`에서 `clrthreads`다(부록 C.4.4). 66.9절에서 SOS 로드와 확장 체인을 이미 다뤘으므로 여기서는 워크플로 명령만 정리한다.

```bash
# 크로스 플랫폼
dotnet-dump analyze /dumps/core.12345

# Linux에서 lldb로 (더 저수준이 필요할 때)
dotnet tool install -g dotnet-sos
dotnet sos install                     # ~/.lldbinit에 플러그인 로드 줄을 넣는다
lldb --core /dumps/core.12345 /usr/share/dotnet/dotnet
```

| 단계 | WinDbg | `dotnet-dump analyze` | 확인하는 것 |
|---|---|---|---|
| ① 런타임 확인 | `!eeversion` | `eeversion` | CLR 버전, 워크스테이션/서버 GC |
| ① 수집 시각·CPU | `.time` | — | 덤프 시각, 프로세스 가동 시간 |
| ② 예외 | `!pe -nested` | `pe -nested` | 현재 스레드의 관리 예외와 내부 예외 |
| ② 크래시 분석 | `!analyze -v` | — | 크래시 덤프의 자동 1차 분석 |
| ③ 모듈 | `lm`, `lmvm <이름>` | `modules`, `clrmodules` | 로드된 어셈블리와 버전 |
| ④ 스레드 | `!threads` | `clrthreads` | 관리 스레드 목록, 예외 보유 여부, 잠금 카운트 |
| ④ CPU 시간 | `!runaway` | — | 어느 스레드가 CPU를 태웠나 |
| ⑤ 스택(현재) | `!clrstack -a` | `clrstack -a` | 지역 변수·매개변수 포함 스택 |
| ⑤ 스택(전체) | `~*e !clrstack` | `clrstack -all` | 모든 스레드의 관리 스택 |
| ⑤ 스택 객체 | `!dso` | `dumpstackobjects` | 스택에서 참조되는 객체들 |
| ⑥ 잠금 | `!syncblk` | `syncblk` | 경합 중인 모니터와 소유 스레드 |
| ⑥ 비동기 | `!dumpasync -stacks` | `dumpasync -stacks` | 미완료 비동기 사슬 |
| ⑥ 스레드 풀 | `!threadpool` | `threadpool` | 큐 길이, 워커 수, CPU 사용률 |
| ⑦ 힙 | `!dumpheap -stat` | `dumpheap -stat` | **66.9절 참조** |

> **📌 스레드 전환 방법이 도구마다 다르다**
>
> WinDbg는 `~<n>s`로 n번 스레드로 전환하고 `~*e <명령>`으로 모든 스레드에서 명령을 실행한다. `dotnet-dump analyze`는 `setthread <n>`으로 전환하고, 전체 실행은 명령 자체의 `-all` 옵션에 의존한다. 손에 익은 쪽 하나만 쓰다가 다른 도구를 만나면 여기서 막힌다.

> **⚠️ 덤프의 비트 수·런타임 버전이 도구와 맞아야 한다**
>
> 64비트 프로세스의 덤프는 64비트 도구로 열어야 하고, SOS는 덤프를 만든 런타임 버전과 맞는 것이 로드돼야 한다. `dotnet-dump analyze`는 필요한 진단 라이브러리를 자동으로 찾으려 시도하지만, 오프라인 환경이나 자체 포함(self-contained) 배포에서는 실패한다. 이런 경우 **덤프와 함께 애플리케이션 디렉터리 전체를 보존**해 두면 `setclrpath`로 런타임 경로를 지정해 분석할 수 있다. 덤프만 달랑 받아서 못 여는 상황은 생각보다 흔하다.

> **📌 Linux 덤프를 Windows에서 열 수 있다**
>
> WinDbg는 Linux에서 생성된 코어 덤프도 로드할 수 있다. 다만 Linux 박스에서 바로 분석해야 한다면 `dotnet-dump analyze`가 답이다 — 크로스 플랫폼 CLI 도구이고 SOS와 같은 명령을 `!` 없이 쓴다.

### 교착 진단 완전 워크스루

이제 실제 사고를 처음부터 끝까지 따라간다.

**증상.** 결제 API가 응답하지 않는다. CPU는 3%. 메모리는 정상. 로그의 마지막 줄은 12분 전. 재시작하면 정상으로 돌아오고, 며칠 뒤 다시 발생한다. 재현 시나리오는 없다.

**1단계 — 덤프를 뜬다.** 재시작하기 전에. 이 순간을 놓치면 다음 발생까지 아무것도 할 수 없다.

```bash
kubectl exec -it payments-7d9f-abc -- /usr/share/dotnet/shared/Microsoft.NETCore.App/8.0.11/createdump \
    --withheap -f /dumps/hang-$(date +%s).core 1
kubectl cp payments-7d9f-abc:/dumps/hang-1730000000.core ./hang.core
```

**2단계 — 판을 확인한다.**

```text
> eeversion
8.0.1124.51707
Server mode with 8 heaps
concurrent
```

서버 GC 8힙. 이 정보는 나중에 스레드 목록에서 GC 스레드를 골라낼 때 쓴다.

**3단계 — 예외가 있나.**

```text
> pe -nested
There is no current managed exception on this thread
```

없다. **크래시가 아니라 행(hang)이다.** 크래시였다면 여기서 예외 타입과 스택이 나왔을 것이고 조사는 훨씬 짧게 끝난다.

- **`SyncBlock Owner`** — 잠금 대상 **객체의 주소와 타입**.

```csharp

{
    lock (this)              // 먼저 자기 자신을 잠근다
    {
        lock (other)         // ← 61행. 상대를 잠근다. 순서가 호출마다 다르다!
        {
            Balance -= amount;
            other.Balance += amount;
        }
    }
}
```

`A.TransferTo(B)`와 `B.TransferTo(A)`가 동시에 실행되면 잠금 획득 순서가 반대가 되어 교착한다. 48.8절의 교과서적 사례이며, 해법도 거기 있다 — **전역 순서를 정해 항상 같은 순서로 잠근다.**

```csharp
public void TransferTo(LedgerAccount other, decimal amount)
{
    // 안정적인 전역 순서(계좌 ID)로 잠금 순서를 고정한다.
    var (first, second) = Id < other.Id ? (this, other) : (other, this);
    lock (first)
    {
        lock (second)
        {
            Balance -= amount;
            other.Balance += amount;
        }
    }
}
```

> **⚠️ `!syncblk`는 `Monitor`만 본다**
>
> `!syncblk`가 보여주는 것은 **동기화 블록**, 즉 `lock` 문과 `Monitor.Enter`가 쓰는 메커니즘뿐이다. `SemaphoreSlim`, `ManualResetEventSlim`, `ReaderWriterLockSlim`, `Mutex`, 그리고 모든 비동기 잠금은 여기 나타나지 않는다. 이 도구로 아무것도 안 보인다고 "교착이 아니다"라고 결론 내면 안 된다. 그때는 `clrstack -all`에서 대기 함수 이름을 세고(`WaitOne`, `Wait`, `WaitAsync`, `GetResult`), 해당 동기화 객체를 `dumpheap -type SemaphoreSlim`으로 찾아 `dumpobj`로 내부 카운터를 읽는다. 비동기 대기 교착은 74.4절의 `dumpasync -stacks`가 담당한다.

> **💡 교착과 행을 구분하는 30초 판별법**
>
> 덤프를 열자마자 세 가지만 보면 방향이 정해진다. (1) `syncblk`에 항목이 있고 `MonitorHeld ≥ 3`이면 **모니터 교착**. (2) `threadpool` 큐 길이가 크고 스레드 다수가 `Wait`/`Result`에 있으면 **스레드 풀 기아**(74.4절). (3) 둘 다 비었는데 미완료 `dumpasync` 사슬이 쌓여 있으면 **비동기 대기 교착 또는 완료되지 않는 외부 I/O**. 이 분기를 먼저 하지 않고 스택을 하나씩 읽기 시작하면 26개 스레드에서 길을 잃는다.

## 74.6 로드된 모듈 확인과 심볼(PDB) 관리

### 왜 모듈 목록부터 보는가

과도한 메모리 사용 같은 성능 문제나 런타임 오류의 원인을 찾을 때, **어떤 모듈이 메모리에 로드되었는지**를 보는 것이 유용하다. 실무에서 이 목록이 답을 주는 경우는 구체적이다.

- 어셈블리 **버전이 예상과 다르다** — 배포된 것이 내가 빌드한 것이 아니다.
- **같은 이름의 어셈블리가 두 개** 로드되었다 — 서로 다른 경로에서. 52장의 로드 컨텍스트 문제다.
- 로드되어야 할 플러그인이 **아예 없다**.
- 심볼이 로드되지 않았다 — 그래서 스택에 줄 번호가 없다.
- 코드가 **최적화되어 있다** — 그래서 지역 변수 값을 못 본다.

### Visual Studio 모듈 창

디버깅 중 `디버그 > 창 > 모듈`을 열면 현재 프로세스가 로드한 모듈 목록이 나온다. 예를 들어 단순한 콘솔 앱이라면 다음 정도가 로드된다.

```text
System.Private.CoreLib.dll
MyApp.dll
System.Runtime.dll
System.Console.dll
```

각 행이 제공하는 필드는 다음과 같다.

| 필드 | 뜻 | 무엇을 판단하나 |
|---|---|---|
| **Name** | 로드된 어셈블리(모듈) 이름 | 무엇이 로드됐나 |
| **Path** | 모듈의 경로 | **어느 경로에서 왔나** — 중복 로드 판별의 핵심 |
| **Optimized** | 예/아니오 | 아니오인 사용자 코드는 최적화를 적용할 여지가 있다 |
| **User Code** | 예/아니오 | "내 코드만" 대상인가 |
| **Symbol Status** | 기호 로드됨 / 기호 로드 건너뜀 | **줄 번호를 볼 수 있는가** |
| **Symbol File** | 로드된 심볼 파일의 경로와 이름 | 어느 PDB가 매칭됐나 |
| **Order** | 어셈블리 로드 순서 | 로드 시점 문제 추적 |
| **Version** | 어셈블리 버전 | 예상 버전인가 |
| **Address** | 로드된 모듈의 메모리 주소 | 네이티브 디버깅과 대조 |
| **Process** | 모듈을 로드시킨 프로세스 ID와 실행 파일 | 다중 프로세스 디버깅 |
| **AppDomain** | 모듈이 속한 애플리케이션 도메인 이름 | — |

> **⚠️ 모듈 창의 `AppDomain` 열은 .NET(Core)에서 의미가 없다**
>
> .NET Core와 .NET 5 이상에는 사실상 앱 도메인이 하나뿐이며 격리 단위로서의 앱 도메인은 존재하지 않는다. 그럼에도 열이 표시되는 이유는 **디버거 UI가 .NET Framework와 .NET을 구분하지 않기 때문**이다. `clrhost` 같은 값이 보여도 의미를 부여하지 마라. .NET에서 격리 단위는 `AssemblyLoadContext`이며, 52장에서 다뤘다.

덤프 분석에서 같은 정보를 얻는 명령은 이렇다.

```text
> clrmodules -v
00007f3c3f120000 8.0.11    /app/MyApp.dll
00007f3c40a10000 8.0.1124  /usr/share/dotnet/shared/Microsoft.NETCore.App/8.0.11/System.Private.CoreLib.dll
...

> modules            # 네이티브 모듈까지 포함 (WinDbg에서는 lm)
```

### 같은 어셈블리가 두 번 로드될 때

모듈 창이 결정적인 답을 주는 대표 사례다. `Name` 열에 같은 이름이 두 번 나타나고 `Path`가 다르면, 서로 다른 두 어셈블리가 동시에 로드된 것이다. 이때 나타나는 증상은 논리적으로 설명되지 않는다.

```text
System.InvalidCastException: Unable to cast object of type
   'Contracts.OrderDto' to type 'Contracts.OrderDto'.
```

같은 이름의 타입인데 캐스팅이 실패한다. CLR에게 타입의 정체성은 **이름이 아니라 (어셈블리, 로드 컨텍스트, 타입) 조합**이기 때문이다(52장, 54장). 플러그인 호스트, 여러 버전이 섞인 의존성 그래프, `Assembly.LoadFrom`과 기본 컨텍스트의 혼용에서 발생한다.

판별은 모듈 창의 `Path`와 `Version`, 또는 덤프에서 `clrmodules -v`로 같은 이름이 두 줄 나오는지 확인하는 것으로 끝난다. 해결은 로드 컨텍스트 설계의 문제이며 52장의 영역이다.

> **💡 출력 창의 어셈블리 로드 메시지를 흘려보내지 마라**
>
> 디버깅을 시작하면 출력 창에 `Loaded '/app/MyApp.dll'. Symbols loaded.` 형태의 줄이 쭉 흐른다. 대부분 무시하지만, **예상하지 못한 경로나 예상하지 못한 버전**이 여기 먼저 나타난다. 배포 문제를 조사할 때는 이 로그를 처음부터 읽는 것이 모듈 창을 보는 것보다 빠르다. 로드 **순서**까지 알 수 있기 때문이다.

### PDB의 종류

PDB(program database)는 **IL 오프셋을 소스 파일과 줄 번호로 되돌리는 지도**다. 여기에 지역 변수 이름, 스코프, 람다·상태 기계와 원래 소스의 대응 관계가 들어 있다. `.csproj`의 `<DebugType>`이 어떤 종류를 만들지 결정한다.

| `<DebugType>` | 산출물 | 크로스 플랫폼 | 크기 | 특징 |
|---|---|---|---|---|
| `portable` | 별도 `.pdb` | **예** | 작다 | **.NET SDK 기본값.** 메타데이터 형식이 어셈블리와 동일해 읽기 쉽다 |
| `embedded` | 없음 (DLL 안에 포함) | 예 | DLL이 커진다 | **파일이 하나로 끝난다.** 배포·수집이 단순 |
| `full` | 별도 `.pdb` (Windows PDB) | 아니오 | 크다 | .NET Framework 시대 형식. Windows 도구 전용 |
| `pdbonly` | 별도 `.pdb` | 아니오 | 크다 | 레거시 값. `full`과 사실상 같게 처리된다 |
| `none` | 없음 | — | 0 | **줄 번호가 사라진다.** 예외 스택도, 덤프 분석도 |

```xml
<PropertyGroup>
  <!-- 심볼을 DLL에 넣어 배포 단위를 하나로 만든다 -->
  <DebugType>embedded</DebugType>
</PropertyGroup>
```

> **⚠️ Release 빌드에도 PDB는 생성된다**
>
> "Release니까 심볼이 없다"는 흔한 오해다. .NET SDK의 기본값에서 **Release 구성도 `portable` PDB를 만든다.** `<DebugType>`과 `<Optimize>`는 **독립된 설정**이다. 최적화된 코드에 완전한 심볼을 붙일 수 있고, 그게 프로덕션 디버깅의 표준 구성이다. 심볼을 정말 없애고 싶다면 `<DebugType>none</DebugType>`을 명시해야 하고, 그렇게 하면 **프로덕션 예외 로그에서 줄 번호가 사라진다.** 대부분의 경우 이건 나쁜 거래다.

> **⚠️ 최적화된 코드는 심볼이 있어도 변수가 안 보인다**
>
> PDB가 완벽해도 JIT이 지역 변수를 레지스터에 넣거나 아예 제거했다면 디버거는 `Cannot obtain value ... in the current context`류의 메시지를 표시한다. 메서드가 인라인되면 스택 프레임 자체가 사라진다(73.4절). 조사 중에 이게 방해가 된다면 `DOTNET_TieredCompilation=0`과 `DOTNET_TieredPGO=0`으로 계층형 컴파일을 끄거나(55.2절), 최후의 수단으로 `[MethodImpl(MethodImplOptions.NoOptimization | MethodImplOptions.NoInlining)]`을 임시로 붙인다. **관찰 대상을 바꾸는 행위**라는 것을 잊지 마라.

### 심볼 매칭 — 왜 "심볼이 일치하지 않는다"가 뜨는가

PE 파일의 디버그 디렉터리에는 **CodeView 항목**이 들어 있고, 거기에 대응하는 PDB의 **GUID와 age**가 박혀 있다. 디버거는 이 값이 정확히 일치하는 PDB만 받아들인다. 한 글자만 다르게 다시 컴파일해도 GUID가 달라진다.

여기서 **결정론적 빌드(deterministic build)** 가 결정적으로 중요해진다.

```xml
<PropertyGroup>
  <!-- SDK 프로젝트의 기본값이 이미 true다. 명시해 두면 의도가 드러난다. -->
  <Deterministic>true</Deterministic>
</PropertyGroup>
```

결정론적 빌드에서는 **같은 입력이 항상 바이트 단위로 같은 출력**을 만든다. 어셈블리의 MVID(module version id)와 PDB GUID도 동일하다. 결과적으로 다음이 가능해진다.

- 커밋 해시만 알면 **그 바이너리를 재현**할 수 있다. 빌드 산출물을 잃어버려도 심볼을 다시 만들 수 있다.
- 배포된 DLL과 내 로컬 빌드가 **정말 같은 소스인지** MVID 비교로 확인할 수 있다.
- 캐시·증분 빌드가 안전해진다.

MVID는 코드에서 바로 읽을 수 있다.

```csharp
Console.WriteLine(typeof(OrderService).Module.ModuleVersionId);
// 배포본에서 출력한 값과 로컬 빌드 값이 같으면 같은 바이너리다.
```

빌드 경로도 문제가 된다. PDB에는 **빌드 머신의 절대 경로**가 그대로 들어간다. `D:\a\_work\1\s\src\Payments\LedgerAccount.cs` 같은 CI 에이전트 경로다. CI 빌드에서는 다음 속성으로 경로를 정규화한다.

```xml
<PropertyGroup>
  <!-- CI에서만 true로 설정한다. 로컬 빌드에서는 켜지 않는다. -->
  <ContinuousIntegrationBuild Condition="'$(TF_BUILD)' == 'true' or '$(GITHUB_ACTIONS)' == 'true'">true</ContinuousIntegrationBuild>
</PropertyGroup>
```

이 설정은 소스 경로를 리포지터리 상대 경로로 매핑해 PDB에 넣는다. 소스 링크(74.7절)가 동작하기 위한 전제 조건이며, 동시에 **빌드 에이전트의 디렉터리 구조가 배포물에 유출되는 것을 막는다.**

> **⚠️ `ContinuousIntegrationBuild`를 로컬 빌드에서 켜지 마라**
>
> 이 속성이 켜지면 소스 경로가 정규화되어 **로컬 디버거가 소스를 찾지 못한다.** F5를 눌러도 중단점이 회색이 된다. 조건부로 CI 환경 변수에 묶어 두는 것이 표준 관행이다.

### 심볼 서버

PDB를 어디서 가져오는가. 디버거는 다음 순서로 찾는다.

1. 어셈블리 옆(같은 디렉터리)
2. PE에 기록된 원래 PDB 경로
3. 로컬 심볼 캐시
4. 구성된 심볼 서버

| 심볼 서버 | URL | 담고 있는 것 |
|---|---|---|
| **Microsoft 심볼 서버** | `https://msdl.microsoft.com/download/symbols` | Windows OS 및 .NET 런타임 바이너리의 PDB |
| **NuGet.org 심볼 서버** | `https://symbols.nuget.org/download/symbols` | `.snupkg`로 게시된 패키지 심볼 |
| **조직 내부 서버** | 임의 (Azure Artifacts 등) | 사내 빌드 산출물 |

WinDbg와 대부분의 도구는 `_NT_SYMBOL_PATH` 환경 변수를 읽는다.

```bash
export _NT_SYMBOL_PATH="SRV*C:\symbols*https://msdl.microsoft.com/download/symbols;SRV*C:\symbols*https://symbols.nuget.org/download/symbols"
```

`SRV*<로컬 캐시>*<서버 URL>` 형식이다. 로컬 캐시가 있어야 매번 내려받지 않는다. WinDbg 안에서는 `.symfix`(Microsoft 서버로 기본 설정)와 `.sympath+`(추가)를 쓴다.

`dotnet-dump`/lldb의 SOS에서는 전용 명령을 쓴다.

```text
> setsymbolserver -ms                    # Microsoft 심볼 서버 사용
> setsymbolserver -directory /symbols    # 로컬 디렉터리 추가
> setclrpath /app/runtime                # 자체 포함 배포의 런타임 경로 지정
> sethostruntime /usr/share/dotnet       # 분석 호스트가 쓸 런타임 지정
```

덤프 분석에 필요한 심볼과 모듈을 **미리 통째로 내려받는** 도구도 있다. 오프라인 분석 머신을 준비할 때 필수다.

```bash
dotnet tool install -g dotnet-symbol
dotnet-symbol --modules --debugging /dumps/hang.core -o /symbols
```

### 심볼 패키지 게시

라이브러리를 NuGet에 게시한다면 심볼도 함께 내보낸다.

```xml
<PropertyGroup>
  <IncludeSymbols>true</IncludeSymbols>
  <SymbolPackageFormat>snupkg</SymbolPackageFormat>
</PropertyGroup>
```

`.snupkg`는 `.nupkg`와 짝을 이루는 심볼 패키지이며 NuGet.org 심볼 서버가 이를 받아 서비스한다. 대안은 `<DebugType>embedded</DebugType>`로 **심볼을 DLL 안에 넣어 버리는 것**이다. 이쪽은 심볼 서버가 필요 없고 버전 불일치가 원천적으로 불가능하다는 큰 장점이 있다. 대신 패키지 크기가 늘고, 배포본에 소스 파일 경로 정보가 항상 따라간다.

| 배포 대상 | 권장 `<DebugType>` | 심볼 배포 | 이유 |
|---|---|---|---|
| 공개 NuGet 라이브러리 | `portable` | `.snupkg`로 심볼 서버에 | 패키지를 가볍게 유지하고 원하는 사람만 받는다 |
| 사내 공용 라이브러리 | `embedded` | 불필요 | 심볼 서버 운영 비용이 아깝다. 불일치 사고가 사라진다 |
| 컨테이너 서비스 | `embedded` 또는 `portable` + 이미지에 PDB 포함 | 이미지에 함께 | 덤프를 뜬 뒤 심볼을 찾아 헤매지 않는다 |
| 데스크톱 배포본 | `portable`, PDB는 별도 보관 | 사내 심볼 서버 | 배포 크기를 줄이되 분석 가능성은 유지 |
| 코드 유출이 극도로 민감 | `none` | — | **줄 번호와 사후 분석을 포기하는 대가를 감수** |

> **💡 컨테이너 이미지에는 PDB를 넣어라**
>
> `dotnet publish`는 기본적으로 PDB를 출력 디렉터리에 포함하는데, 이미지 크기를 줄이겠다고 이를 지우는 Dockerfile을 종종 본다. 절약되는 것은 보통 몇 메가바이트고, 잃는 것은 **프로덕션 예외 로그의 줄 번호와 덤프 분석의 소스 위치**다. 컨테이너 이미지는 이미 수백 메가바이트다. 지우지 마라.

> **⚠️ Native AOT에서는 관리 디버깅이 성립하지 않는다**
>
> Native AOT로 게시하면 IL도, 메타데이터도, CLR도 없다(55.7절, 57.14절). 결과물은 순수한 네이티브 실행 파일이므로 **SOS의 관리 명령이 동작하지 않고**, 디버깅은 네이티브 디버거(WinDbg/lldb)로 네이티브 PDB/DWARF를 써서 하게 된다. 스택 트레이스에 관리 메서드 이름이 나오는 것은 AOT 컴파일러가 별도의 스택 트레이스 메타데이터를 남기기 때문이며, 그마저도 트리밍 설정에 따라 줄어든다. **Native AOT를 채택하기 전에 "이 앱에 문제가 생기면 어떻게 조사할 것인가"에 답을 준비해 두어야 한다.** ReadyToRun(55.7절)은 사정이 다르다 — CLR이 그대로 있으므로 관리 디버깅이 정상 동작한다.

## 74.7 소스 링크와 프로덕션 디버깅

### 문제: 심볼이 있어도 소스가 없다

74.6절의 준비를 다 했다고 하자. 덤프를 열었고 심볼이 매칭됐다. 디버거는 이렇게 말한다.

```text
Source file not found:
  D:\a\_work\1\s\src\Payments\LedgerAccount.cs
```

줄 번호는 알지만 **그 줄에 무엇이 있는지 모른다.** 소스를 손으로 찾아 체크아웃하고 커밋을 맞추는 수동 작업이 남는다. 커밋을 잘못 맞추면 줄 번호가 한 칸씩 밀려 엉뚱한 코드를 읽으면서 몇 시간을 태운다.

**소스 링크(Source Link)** 는 이 문제를 없앤다. 빌드 시 "이 어셈블리의 소스는 이 리포지터리의 이 커밋에 있다"는 정보를 PDB에 넣어 두고, 디버거가 그 정보로 소스를 자동으로 내려받게 한다.

```text
[PDB]
 ├ 소스 파일 목록 + 각 파일의 콘텐츠 해시
 └ SourceLink JSON:
     { "documents": {
         "D:\\a\\_work\\1\\s\\*":
           "https://raw.githubusercontent.com/org/repo/9c1f4a2.../*" } }
                                              ↑ 커밋 SHA가 박혀 있다
        │
        ↓  디버거가 URL을 조합해 파일을 내려받고
           PDB의 콘텐츠 해시와 대조해 검증한다
[정확히 그 커밋의 소스]
```

핵심은 **해시 검증**이다. 내려받은 파일의 해시가 PDB에 기록된 것과 다르면 디버거는 그 소스를 쓰지 않는다. "줄 번호가 밀린 엉뚱한 소스"를 볼 가능성이 구조적으로 차단된다.

### 설정

```xml
<PropertyGroup>
  <!-- 리포지터리 URL을 패키지·PDB 메타데이터에 넣는다 -->
  <PublishRepositoryUrl>true</PublishRepositoryUrl>

  <!-- 소스 제어에 없는 생성 파일(소스 생성기 출력, AssemblyInfo 등)을 PDB에 직접 임베드 -->
  <EmbedUntrackedSources>true</EmbedUntrackedSources>

  <!-- 심볼 배포 방식: 별도 .snupkg -->
  <IncludeSymbols>true</IncludeSymbols>
  <SymbolPackageFormat>snupkg</SymbolPackageFormat>

  <!-- 또는 심볼을 DLL에 넣어 버린다 (둘 중 하나를 고른다) -->
  <!-- <DebugType>embedded</DebugType> -->

  <!-- CI에서만: 경로 정규화. 소스 링크의 전제 조건이다 -->
  <ContinuousIntegrationBuild Condition="'$(GITHUB_ACTIONS)' == 'true'">true</ContinuousIntegrationBuild>
</PropertyGroup>
```

호스트별 소스 링크 패키지는 ※.NET 8 SDK부터 **기본 포함**된다. 그 이전 SDK나 명시적 버전 고정이 필요하면 패키지를 직접 참조한다.

```xml
<ItemGroup>
  <PackageReference Include="Microsoft.SourceLink.GitHub" Version="8.0.0" PrivateAssets="All" />
  <!-- GitLab / AzureRepos.Git / Bitbucket.Git 용 패키지도 있다 -->
</ItemGroup>
```

`PrivateAssets="All"`이 중요하다. 이 패키지는 빌드 시점에만 필요하며 소비자에게 전이 의존성으로 흘러가면 안 된다.

극단적으로는 **소스 자체를 PDB에 넣을** 수도 있다.

```xml
<PropertyGroup>
  <EmbedAllSources>true</EmbedAllSources>
</PropertyGroup>
```

리포지터리에 접근할 수 없는 환경(에어갭 망, 외부 고객사 지원)에서 유일한 선택지다. 대신 **소스 전체가 배포물에 들어간다**는 것을 명확히 인지해야 한다.

| 옵션 | 소스가 어디 있나 | 리포지터리 접근 필요 | 유출 위험 |
|---|---|---|---|
| 소스 링크 + `.snupkg` | 리포지터리 | **필요** | 낮음 (인증된 사용자만) |
| 소스 링크 + `embedded` PDB | 리포지터리 | 필요 | 낮음 |
| `EmbedAllSources` | **PDB 안** | 불필요 | **높음** — 소스가 배포된다 |
| 심볼 없음(`none`) | — | — | 없음. 대신 조사가 불가능하다 |

### 디버거 쪽 설정

Visual Studio에서 `도구 > 옵션 > 디버깅 > 일반`에 다음이 있어야 한다.

- **소스 링크 지원 사용** — 켠다.
- **내 코드만(Just My Code)** — **끈다.** 켜져 있으면 라이브러리 코드로 들어가지 않는다.
- **원본 파일이 원래 버전과 정확히 일치해야 함** — 켜 둔다. 이게 해시 검증 스위치다.
- **.NET Framework 원본 스테핑** / **기호 서버 지원** — 필요에 따라.

`도구 > 옵션 > 디버깅 > 기호`에서 NuGet.org와 Microsoft 심볼 서버를 추가하고 로컬 캐시 경로를 지정한다.

소스 링크가 제대로 들어갔는지는 전용 도구로 검증할 수 있다.

```bash
dotnet tool install -g sourcelink
sourcelink test ./bin/Release/net8.0/Payments.pdb
```

이 명령은 PDB의 모든 문서에 대해 URL을 실제로 조회하고 해시를 대조한다. **CI 파이프라인에 넣어 두면 "배포하고 나서야 소스 링크가 깨진 걸 발견"하는 일이 없어진다.**

> **⚠️ 비공개 리포지터리는 인증이 필요하고, 그건 자동으로 되지 않는다**
>
> 소스 링크 URL이 비공개 GitHub/Azure DevOps 리포지터리를 가리키면 디버거가 인증 없이 내려받지 못한다. Visual Studio는 자격 증명 대화상자를 띄우지만, WinDbg나 CI 환경의 자동화된 분석에서는 그냥 실패한다. 조직 내부용이라면 `<DebugType>embedded</DebugType>` + `<EmbedAllSources>`가 오히려 더 신뢰할 만한 선택인 경우가 많다.

> **⚠️ 소스 링크는 결정론적 빌드와 경로 정규화 없이는 무의미하다**
>
> `ContinuousIntegrationBuild`가 꺼진 채 CI에서 빌드하면 PDB에 빌드 에이전트의 절대 경로가 들어가고, 소스 링크의 경로 매핑이 그 경로와 맞지 않아 조회가 실패한다. 세 설정 — `Deterministic`, `ContinuousIntegrationBuild`, `PublishRepositoryUrl` — 은 **한 세트**다. 하나만 빼면 나머지 둘이 조용히 무력해진다.

### 프로덕션 디버깅 전략

지금까지의 도구를 프로덕션 환경에 맞게 조합하면 다음 표가 된다. 원칙은 하나다. **사고가 나기 전에 준비된 것만 사고 때 쓸 수 있다.**

| 준비 항목 | 언제 설정하나 | 없으면 어떻게 되나 |
|---|---|---|
| `DebugType`(심볼 배포) | 빌드 구성 | 예외 로그에 줄 번호가 없다 |
| 결정론적 빌드 + 소스 링크 | 빌드 구성 | 덤프에서 소스를 못 찾아 몇 시간을 태운다 |
| 버전에 커밋 SHA 포함 | 빌드 구성 | 어느 코드가 돌고 있었는지 모른다 |
| `DOTNET_DbgEnableMiniDump` | 배포 매니페스트 | 크래시가 흔적 없이 사라진다 |
| 덤프 저장용 볼륨 | 배포 매니페스트 | 덤프를 뜨는 순간 디스크가 찬다 |
| `SYS_PTRACE`(개발/스테이징만) | 배포 매니페스트 | 붙일 수 없다 |
| 구조적 로그 + 상관관계 ID | 코드 | 사건의 순서를 재구성할 수 없다 (75장) |
| `dotnet-monitor` 사이드카 | 배포 매니페스트 | 문제가 난 순간에 도구가 없다 |
| 런북(어떤 신호에 무엇을 수집) | 운영 문서 | 당황해서 재시작부터 한다 |

버전에 커밋 SHA를 넣는 방법은 간단하다.

```xml
<PropertyGroup>
  <Version>2.7.3</Version>
  <!-- SDK가 InformationalVersion에 +<SourceRevisionId>를 붙인다 -->
  <SourceRevisionId Condition="'$(GITHUB_SHA)' != ''">$(GITHUB_SHA)</SourceRevisionId>
</PropertyGroup>
```

런타임에는 이렇게 읽는다.

```csharp
using System.Reflection;

var informational = Assembly.GetEntryAssembly()!
    .GetCustomAttribute<AssemblyInformationalVersionAttribute>()!
    .InformationalVersion;
// "2.7.3+9c1f4a2b8e7d6c5f4a3b2c1d0e9f8a7b6c5d4e3f"

logger.LogInformation("시작. 버전 {Version}, MVID {Mvid}",
    informational, typeof(Program).Module.ModuleVersionId);
```

**이 한 줄을 시작 로그에 남기는 것이 프로덕션 디버깅 준비 중 투자 대비 효과가 가장 크다.** 사고 조사의 첫 질문이 언제나 "어떤 빌드가 돌고 있었나"이기 때문이다.

### `dotnet-monitor` — 사고 순간에 도구가 있게 하기

컨테이너 환경에서는 문제가 생긴 순간 컨테이너에 셸로 들어가 도구를 설치할 시간이 없다. 그 컨테이너는 몇 초 뒤 오케스트레이터가 죽인다.

`dotnet-monitor`는 `dotnet-dump`/`dotnet-trace`/`dotnet-counters`의 기능을 **HTTP 엔드포인트로 노출하는 별도 프로세스**다. 쿠버네티스에서는 사이드카 컨테이너로 띄우고 진단 소켓 볼륨을 공유한다.

```yaml
# 파드 스펙 발췌
volumes:
  - name: diagnostics
    emptyDir: {}
  - name: dumps
    emptyDir: {}
containers:
  - name: app
    env:
      - name: DOTNET_DiagnosticPorts
        value: /diag/dotnet-monitor.sock
      - name: DOTNET_DbgEnableMiniDump
        value: "1"
      - name: DOTNET_DbgMiniDumpName
        value: /dumps/core.%p
    volumeMounts:
      - { name: diagnostics, mountPath: /diag }
      - { name: dumps,       mountPath: /dumps }
  - name: monitor
    image: mcr.microsoft.com/dotnet/monitor:8
    volumeMounts:
      - { name: diagnostics, mountPath: /diag }
```

진짜 가치는 **수집 규칙(collection rule)** 에 있다. "1분 안에 예외가 100개를 넘으면 자동으로 덤프를 뜬다", "GC 힙이 1GB를 넘으면 `gcdump`를 남긴다" 같은 규칙을 미리 정의해 두면, 사람이 없는 새벽 3시의 사고에도 증거가 남는다.

> **💡 "그때 덤프를 떴어야 했는데"를 없애는 유일한 방법**
>
> 프로덕션 사고 조사에서 가장 흔한 결말은 "재시작해서 복구했고 원인은 모른다"이다. 증거가 사라졌기 때문이다. 자동 크래시 덤프(`DOTNET_DbgEnableMiniDump`)와 규칙 기반 수집(`dotnet-monitor`)은 **사람의 판단을 기다리지 않는다.** 이 둘을 배포 매니페스트에 넣는 데 드는 시간은 30분이고, 없어서 잃는 시간은 사고 하나당 며칠이다.

> **⚠️ 진단 엔드포인트를 인증 없이 노출하지 마라**
>
> `dotnet-monitor`의 HTTP API는 프로세스 메모리를 덤프할 수 있다. 즉 **비밀 전체를 내주는 엔드포인트**다. 기본적으로 인증이 요구되며(API 키 또는 Azure AD), `--no-auth`는 로컬 개발용이다. 클러스터 안이라고 안전한 것이 아니다. 진단 포트는 별도 네트워크 정책으로 격리하고, 덤프 볼륨의 접근 권한도 애플리케이션 로그와 같은 등급으로 다뤄야 한다.

> **📌 스냅숏 디버깅이라는 상용 선택지도 있다**
>
> 일부 APM 제품(Azure Application Insights의 스냅숏 디버거 등)은 프로덕션에서 예외가 발생한 순간의 **경량 스냅숏**을 자동으로 수집해 IDE에서 지역 변수와 스택을 볼 수 있게 해준다. 전체 덤프보다 훨씬 가볍고 자동화되어 있다. 다만 벤더 종속과 추가 오버헤드가 따르고, 수집되는 데이터에 개인 정보가 포함될 수 있다는 점은 덤프와 동일하다. 이 장에서 다룬 표준 도구로 충분한 조직이 많지만, 선택지로 알아 둘 가치는 있다.

## 74.8 프로덕션 사고를 재현하는 법 — 덤프에서 시작하기

### 사용자 진술은 증거가 아니다

버그가 다 제거됐다고 믿고 릴리스를 빌드해 배포한다. 그러나 버그 없는 코드는 없고, 런타임에는 예상하지 못한 오류가 발생한다.

여기서 반드시 인정해야 할 사실이 하나 있다. **최종 사용자는 오류가 발생했을 때 자신이 무엇을 하고 있었는지 기억하지도, 인정하지도, 정확히 설명하지도 못한다.** 문제를 재현하고 원인을 이해해 고칠 수 있을 만큼의 유용한 정보를 사용자가 제공해 주리라고 기대해서는 안 된다. 그 대신 **코드를 계측(instrument)** 해야 한다 — 관심 있는 이벤트와 타이밍 같은 데이터를 기록해 두는 것이다.

이것이 이 장 전체의 결론이기도 하다. 재현 불가능한 프로덕션 버그를 잡는 능력은 사고가 난 뒤의 기술이 아니라 **사고 전에 남겨 둔 증거의 양**으로 결정된다.

> **💡 계측은 사고 대응 예산이다**
>
> 예외가 발생하는 지점을 포함해 애플리케이션 전반에 무슨 일이 일어나는지를 기록하는 코드를 넣어 두라. 그래야 로그를 검토해 문제를 추적하고 고칠 수 있다. 무엇을 어떻게 기록할지 — 구조적 로깅, 로그 수준, 스코프, 메트릭, 분산 추적 — 는 75장의 주제다. 여기서는 **이미 남아 있는 증거를 어떻게 사고 재구성으로 바꾸는가**만 다룬다.

### 표준 절차

```text
① 사실 고정      "언제, 어느 인스턴스, 어느 빌드, 어떤 증상"
       ↓
② 증거 수집      로그 · 메트릭 · 추적 · 덤프  (재시작 전에!)
       ↓
③ 타임라인 구성   시각 순으로 정렬. 최초 이상 징후 시점을 찾는다
       ↓
④ 가설 수립      "무엇이 원인인가"를 한 문장으로
       ↓
⑤ 반증 시도      가설과 모순되는 증거를 적극적으로 찾는다
       ↓
⑥ 국소 재현      최소 하네스로 같은 증상을 만든다
       ↓
⑦ 수정 + 회귀 테스트  같은 신호로 검증한다
```

④와 ⑤의 순서가 중요하다. 사람은 첫 가설을 확증하는 증거만 보게 되어 있다. **가설을 세운 직후 "이 가설이 틀렸다면 어떤 증거가 보여야 하는가"를 먼저 물어라.**

### ① 사실 고정 — 어느 빌드였나

조사의 첫 질문은 언제나 같다. **무엇이 돌고 있었나.**

| 알아야 할 것 | 살아 있는 프로세스 | 덤프에서 |
|---|---|---|
| 애플리케이션 버전·커밋 | 시작 로그의 `InformationalVersion` | `clrmodules -v`, 시작 로그 |
| 어셈블리 동일성 | `Module.ModuleVersionId` | `dumpmodule`, `clrmodules -v` |
| 런타임 버전·GC 모드 | `dotnet --info` | `eeversion` |
| OS·컨테이너 이미지 태그 | 오케스트레이터 | 덤프 헤더 |
| 구성 값 | 시작 로그 | `dumpheap -type Configuration...` |

74.7절에서 시작 로그에 버전과 MVID를 남기라고 한 이유가 여기서 회수된다. 이 값이 없으면 소스 링크도, 심볼 매칭도, "이 코드가 정말 그때 그 코드인가"라는 질문도 답이 없다.

### ② 증거 수집 — 재시작 전에

**재시작은 증거를 파괴한다.** 서비스를 살려야 한다는 압박은 정당하지만, 인스턴스가 여러 개라면 하나만 남겨 두고 나머지를 재시작하는 선택이 거의 항상 가능하다.

```bash
# 문제 인스턴스를 트래픽에서 뺀다 (죽이지 않는다)
kubectl label pod payments-7d9f-abc app-  # 서비스 셀렉터에서 제외

# 증거를 다 뜬다
kubectl exec payments-7d9f-abc -- .../createdump --withheap -f /dumps/a.core 1
kubectl exec payments-7d9f-abc -- dotnet-counters collect -p 1 --format json -o /dumps/counters.json
kubectl exec payments-7d9f-abc -- dotnet-trace collect -p 1 --duration 00:00:00:30 -o /dumps/t.nettrace
kubectl logs payments-7d9f-abc --since=1h > incident.log

# 그다음에 재시작
```

증상이 **시간에 따라 변하는 것**이라면 덤프를 **둘 이상** 떠서 비교한다. 스냅숏 하나로는 "쌓이고 있는가"를 알 수 없다. 메모리 관점의 스냅숏 비교는 66.4절에서 다뤘고, 스레드·잠금 관점에서도 같은 원리가 적용된다 — 5분 간격 덤프 두 개에서 같은 스레드가 **같은 줄**에 머물러 있으면 그 스레드는 진행하지 않고 있는 것이다.

### ③ 사고 유형별 신호와 도구

증상에서 도구로 가는 지도가 있으면 조사가 훨씬 빨라진다.

| 사고 유형 | 특징적 신호 | 첫 도구 | 확정 방법 |
|---|---|---|---|
| **모니터 교착** | CPU 낮음, 처리량 0, 회복 안 됨 | 덤프 | `syncblk` + `clrstack` 순환 대기 (74.5절) |
| **스레드 풀 기아** | 느린 악화, 급격한 회복, 큐 길이 증가 | `dotnet-counters` | `clrstack -all`에서 `Wait`/`Result` 계수 (74.4절) |
| **비동기 미완료** | 요청은 살아 있는데 응답 없음, 스레드는 유휴 | 덤프 | `dumpasync -stacks` (74.4절) |
| **예외 폭풍** | CPU 높음, `Exceptions/sec` 급증, 로그 급증 | `dotnet-counters` → `dotnet-trace` | 예외 타입 집계 (32.12절) |
| **CPU 스핀** | 특정 스레드가 CPU를 독점 | `dotnet-trace`(CPU 샘플링) | `!runaway` + 반복 스택 |
| **메모리 누수 / OOM** | 힙 증가, GC 시간 증가 | `dotnet-gcdump`, 덤프 | **66장 전체** |
| **LOH 단편화** | 힙은 크지 않은데 OOM | `dotnet-gcdump` | **66.11절** |
| **소켓·핸들 고갈** | `SocketException`, 연결 실패 | OS 도구 + 덤프 | `dumpheap -type Socket` 계수 |
| **시작 실패** | 프로세스가 즉시 종료 | 자동 크래시 덤프 | `pe -nested`, `clrstack` |

### 완전 워크스루 — 서서히 죽는 서비스

74.5절이 교착이었으니, 여기서는 **혼동하기 쉬운 다른 유형**을 끝까지 따라간다.

**증상.** 배포 후 40분쯤 지나면 p99 지연이 200ms에서 30초로 올라간다. CPU는 20%대로 낮다. 그러다 몇 분 뒤 갑자기 정상으로 돌아오고, 다시 나빠진다. 오류율은 타임아웃 때문에만 오른다.

**① 사실 고정.** 시작 로그에서 버전 `4.1.0+7ab39c1`. 이전 릴리스 `4.0.6`에서는 없던 증상. **변경 집합이 좁혀진다.**

**② 메트릭부터.** 덤프보다 싸다.

```text

    ThreadPool Completed Work Items / sec             61     ← 낮다
```

큐가 3,000개 넘게 쌓였는데 CPU는 20%, 완료율은 초당 61개. **일할 스레드가 없어서 큐가 쌓이는 것**이지 CPU가 부족한 게 아니다. 잠금 경합도 낮으므로 모니터 교착은 아니다. 74.4절의 판별 표대로 **스레드 풀 기아**가 1순위 가설이다.

**③ 덤프로 확정.**

이 스택이 **41개 스레드에서 반복된다.** 47개 워커 중 41개가 `Task.Result`에서 블로킹 중이다.

**④ 코드 확인.** 소스 링크(74.7절)가 설정되어 있으므로 디버거가 `RateProvider.cs`의 정확한 커밋 버전을 바로 열어 준다.

```csharp
// 4.1.0에서 추가된 코드
public Rate GetRate(string currency)
{
    // 기존 동기 인터페이스를 유지하려고 비동기 클라이언트를 동기로 감쌌다.
    return _client.GetRateAsync(currency).Result;   // ← 28행
}
```

전형적인 **sync-over-async**다(47.14절). 각 요청이 스레드 풀 스레드를 하나 잡고 HTTP 응답을 동기로 기다린다. 응답 완료 콜백도 스레드 풀에서 실행되어야 하는데, 스레드가 전부 대기 중이라 콜백이 실행되지 못한다. 스레드 풀은 이를 감지해 스레드를 **초당 1~2개씩** 주입하고, 충분히 주입되면 밀린 일이 한꺼번에 처리되며 갑자기 회복된다. **"느린 악화와 급격한 회복"이라는 특유의 패턴이 여기서 나온다.**

**⑤ 반증 시도.** 가설이 맞다면 다음이 참이어야 한다.

- 워커 스레드 수가 계속 증가해야 한다 → 47개, 기본 최소값보다 훨씬 크다. **부합.**
- 잠금 경합은 낮아야 한다 → 초당 4회. **부합.**
- 회복 직후에는 큐 길이가 급감해야 한다 → 메트릭 시계열에서 확인. **부합.**
- 부하가 낮으면 증상이 없어야 한다 → 스테이징 저부하에서 재현 안 됨. **부합.**

반증할 증거가 나오지 않는다. 확정.

**⑥ 국소 재현.** 프로덕션을 다시 망가뜨리지 않고 검증하려면 최소 하네스가 필요하다.

```csharp
using System.Diagnostics;

// 스레드 풀 기아를 의도적으로 재현하는 최소 하네스
ThreadPool.SetMinThreads(4, 4);            // 주입 속도의 영향을 극단화한다
var sw = Stopwatch.StartNew();
var completed = 0;

var tasks = Enumerable.Range(0, 200).Select(_ => Task.Run(() =>
{
    // 프로덕션 코드와 같은 형태: 비동기 작업을 동기로 기다린다
    var result = SimulateRemoteCallAsync().Result;
    Interlocked.Increment(ref completed);
    return result;
})).ToArray();

// 진행 상황을 초당 출력한다 — 큐가 어떻게 소진되는지 눈으로 본다
_ = Task.Run(async () =>
{
    while (completed < 200)
    {
        ThreadPool.GetAvailableThreads(out int worker, out _);
        Console.WriteLine($"{sw.ElapsedMilliseconds,6}ms  완료={completed,3}  가용워커={worker}");
        await Task.Delay(1000);
    }
});

Task.WaitAll(tasks);
Console.WriteLine($"총 {sw.ElapsedMilliseconds}ms");

static async Task<int> SimulateRemoteCallAsync()
{
    await Task.Delay(200);     // 원격 호출 지연을 흉내 낸다
    return 42;
}
```

`.Result`를 `await`로 바꾸고 람다를 `async`로 만들면 같은 200개 작업이 수백 밀리초에 끝난다. **차이가 두 자릿수 배수로 나타나는 것을 눈으로 확인한 뒤에** 수정을 배포한다.

**⑦ 수정과 회귀 방지.**

```csharp
// 인터페이스를 비동기로 올린다. 동기 래퍼를 남기지 않는다.
public Task<Rate> GetRateAsync(string currency) => _client.GetRateAsync(currency);
```

회귀를 막는 것은 코드 리뷰가 아니라 **자동화된 신호**다.

- 정적 분석 규칙으로 `.Result`/`.Wait()`/`GetAwaiter().GetResult()`를 금지한다(경고를 오류로 승격).
- 부하 테스트에 `ThreadPool Queue Length` 임계치를 넣는다.
- 회귀 테스트를 남긴다(80장).

> **⚠️ "재현이 안 되니 못 고친다"는 대부분 도구 부족이 아니라 신호 부족이다**
>
> 위 조사에서 결정적이었던 것은 특별한 기술이 아니라 (1) 버전이 찍힌 시작 로그, (2) 상시 수집되는 런타임 카운터, (3) 재시작 전에 뜬 덤프, (4) 동작하는 소스 링크였다. 넷 다 사고 **이전에** 준비되는 것들이다. 사고가 난 뒤에 준비할 수 있는 것은 아무것도 없다.

### 덤프에서 소스가 없을 때 — 디컴파일

소스 링크가 없거나 서드파티 라이브러리 내부에서 문제가 났다면, 스택이 알려준 메서드를 **디컴파일**해서 읽는 수밖에 없다. ILSpy, dotPeek, dnSpy 같은 도구가 컴파일된 IL을 C#처럼 보여준다(56.8절). dnSpy는 디컴파일된 코드를 **디버깅하고 수정**하는 것까지 가능해서, 소스 없는 어셈블리에 중단점을 걸어야 하는 극단적 상황에서 쓰인다.

JIT이 실제로 생성한 어셈블리 코드를 봐야 하는 수준까지 내려간다면 `DOTNET_JitDisasm`이나 SharpLab을 쓴다(55.8절). 디버깅에서 여기까지 내려오는 경우는 드물지만, "코드는 맞는데 결과가 틀리다"는 유형의 사고에서는 마지막 수단이 된다.

> **⚠️ 디컴파일 결과는 원본 소스가 아니다**
>
> 디컴파일러는 IL에서 C#을 **복원**한다. 컴파일러가 생성한 상태 기계, 클로저 클래스, `switch` 점프 테이블은 원래 소스와 다른 모습으로 나온다. 최적화가 적용된 릴리스 어셈블리라면 차이가 더 커진다. 디컴파일 결과에서 읽어낸 논리는 **가설**이지 사실이 아니며, 가능하면 실제 소스로 확인해야 한다. 라이선스 문제도 별개로 존재한다.

### 사후 체크리스트

사고가 끝나면 다음을 남긴다. 남기지 않으면 같은 사고를 두 번 조사하게 된다.

1. **타임라인** — 최초 이상 징후, 인지 시각, 완화 조치, 복구 시각.
2. **증거 아카이브** — 덤프·추적·로그를 사건 ID로 묶어 보관. 보존 기한과 접근 권한을 명시한다(덤프에는 비밀이 들어 있다).
3. **원인 문장 하나** — "무엇이 무엇을 유발했다" 형태. 여러 문장이면 아직 원인을 모르는 것이다.
4. **재현 하네스** — ⑥에서 만든 코드를 리포지터리에 남긴다.
5. **회귀 신호** — 테스트, 분석 규칙, 알림 임계치 중 최소 하나.
6. **부족했던 계측** — 이번에 "이 값이 있었으면 30분 만에 끝났을 텐데" 싶었던 것을 다음 릴리스에 넣는다.

> **💡 6번이 가장 가치 있다**
>
> 사고 대응의 진짜 산출물은 수정 커밋이 아니라 **다음 사고를 짧게 만드는 계측**이다. 조사 중에 "이걸 몰라서 막혔다"고 느낀 순간을 그때그때 메모해 두라. 그 목록이 관측 가능성 로드맵(75장)이 된다.

## 이 장의 요약

- **디버거 연결 방식은 다섯 가지이고 각각 가능한 것이 다르다.** F5는 시작 지점부터 잡을 수 있지만 호스팅 환경을 재현하지 못하고, Attach는 이미 실행 중인 것만 잡되 **연결 이전 코드에는 무력하다.** 시작 직후 버그에는 `Debugger.Launch()`나 환경 변수로 켜는 대기 루프가 답이다.
- **`Debugger.Launch()`는 사실상 Windows 전용이다.** Unix에는 JIT 디버거 등록 개념이 없어 아무 일도 하지 않고 `false`를 반환한다. 컨테이너에서는 `Debugger.IsAttached` 대기 루프 + `SYS_PTRACE` + `vsdbg` 조합을 쓴다. 반면 EventPipe 기반 진단 도구는 `ptrace`도 권한도 요구하지 않는다.
- **핫 리로드는 메타데이터 업데이트이지 마법이 아니다.** 메서드 본문과 멤버 추가는 되지만 시그니처 변경·이름 변경·삭제는 거친 편집이다. Native AOT와 최적화된 게시본에는 적용되지 않는다.
- **디버거 특성의 식은 디버거가 실제로 실행한다.** `[DebuggerDisplay]`에서 메서드를 호출하면 함수 평가가 일어나 잠금·I/O·지연 초기화를 유발할 수 있다. 식은 순수한 속성 접근으로 제한하고, 프록시 속성은 원본을 건드리지 않는 사본에서 계산하라.
- **`[DebuggerStepThrough]`는 "지나가라", `[DebuggerHidden]`은 "없는 셈 쳐라"다.** `Hidden`이 붙은 메서드 안의 중단점은 **무시된다.** 이 차이를 모르면 걸리지 않는 중단점을 붙잡고 시간을 태운다.
- **조건부 중단점은 히트마다 대상 프로세스 안에서 식을 평가한다.** 뜨거운 루프에서는 프로그램을 사실상 멈추고 타이밍을 바꿔 버그를 숨긴다. 히트 카운트·필터·코드 내 `Debugger.Break()`가 훨씬 싸다.
- **비동기 스택이 끊기는 것은 버그가 아니라 상태 기계의 구조적 결과다.** `await` 이후의 코드는 호출자가 사라진 스레드 풀 스택 위에서 돈다. 디버거가 연속 사슬로 논리적 스택을 복원하지만 `async void`·즉발-망각·`TaskCompletionSource` 브리지에서는 복원이 끊긴다. 그때 남는 수단이 `dumpasync -stacks`다.
- **덤프 생성 경로는 다섯 가지이고, 조건부 수집이 가능한 것은 ProcDump와 `dotnet-monitor`뿐이다.** `dotnet-dump`는 크로스 플랫폼이지만 트리거를 걸 수 없다. 재현 불가 크래시의 유일한 실용적 답은 `DOTNET_DbgEnableMiniDump` 자동 덤프다. 컨테이너에서는 `core_pattern`이 호스트 전역이므로 이 경로를 써야 한다.
- **덤프 분석은 순서가 있다.** 런타임 확인 → 예외 확인 → 모듈 → 스레드 목록 → 전체 스택 → 대기 관계. 이 순서를 건너뛰고 스택부터 읽으면 스레드 수십 개에서 길을 잃는다.
- **교착은 `syncblk`의 `MonitorHeld`로 확정한다.** 소유는 1, 대기자 하나당 2가 더해진다. 다만 이 명령은 `Monitor`만 본다 — `SemaphoreSlim`이나 비동기 대기는 여기 나타나지 않으므로 "안 보인다"를 "없다"로 읽으면 안 된다.
- **Release 빌드에도 PDB는 생성된다.** `<DebugType>`과 `<Optimize>`는 독립이다. 최적화된 코드 + 완전한 심볼이 프로덕션의 표준 구성이며, `none`을 고르는 것은 줄 번호와 사후 분석 능력을 포기하는 거래다.
- **결정론적 빌드·경로 정규화·소스 링크는 한 세트다.** 하나만 빠져도 나머지가 조용히 무력해진다. `sourcelink test`를 CI에 넣어 배포 전에 검증하라.
- **프로덕션 디버깅에서 사고 이후에 준비할 수 있는 것은 없다.** 버전이 찍힌 시작 로그, 상시 카운터, 자동 덤프, 동작하는 소스 링크 — 넷은 전부 사고 이전의 결정이다.

## 연습 문제

1. 콘솔 앱을 만들어 `Debugger.IsAttached` 대기 루프(타임아웃 포함)를 진입점에 넣고, 환경 변수로 켜지도록 하라. 이 앱을 컨테이너에서 실행하고 `--cap-add=SYS_PTRACE` 없이 붙여 보라. 어떤 오류가 나는가? 권한을 준 뒤 다시 시도해 차이를 확인하라.
2. `[DebuggerDisplay]`의 식에 `Interlocked.Increment(ref _counter)`를 호출하는 속성을 넣어라. 디버거로 중단해 감시 창을 열었다 닫았다 하면서 카운터가 얼마나 증가하는지 확인하라. 그다음 `,ac` 지정자를 붙이면 어떻게 달라지는가?
3. 74.2절의 `MinHeap<T>`를 구현하고 `[DebuggerTypeProxy]`를 붙여라. 프록시의 `SortedItems`에서 실수로 `Array.Sort(_heap._items)`처럼 **원본을** 정렬하도록 바꾼 뒤, 디버거로 관찰만 하고 실행을 계속했을 때 힙 불변식이 깨지는 것을 확인하라.
4. 100만 번 도는 루프 안에 조건부 중단점(`i == 999_999`)을 걸고 실행 시간을 측정하라. 같은 조건을 히트 카운트로, 그리고 `if (i == 999_999) Debugger.Break();`로 바꿔 각각 측정하고 세 값을 비교하라.
5. `async Task` 메서드 세 개를 중첩 호출하고 가장 안쪽에서 예외를 던져라. `await`로 받았을 때와 `.Result`로 받았을 때의 스택 트레이스 문자열을 나란히 출력해 `--- End of stack trace from previous location ---` 구분선과 `AggregateException` 래핑 차이를 확인하라. 중간 메서드를 `async void`로 바꾸면 어떻게 되는가?
6. 74.5절의 `TransferTo` 교착 코드를 그대로 재현하고, 두 스레드로 `A.TransferTo(B)`와 `B.TransferTo(A)`를 동시에 호출해 행에 걸리게 하라. `dotnet-dump collect`로 덤프를 뜬 뒤 `dotnet-dump analyze`에서 `clrthreads` → `syncblk` → `setthread` → `clrstack` 순으로 따라가 순환 대기를 확정하라.
7. 같은 프로젝트를 `<DebugType>portable</DebugType>`, `embedded`, `none`으로 각각 게시하고 출력 디렉터리 크기와 파일 목록을 비교하라. 각 경우에 예외를 던져 스택 트레이스에 줄 번호가 나오는지 확인하라.
8. `<Deterministic>true</Deterministic>` 상태에서 같은 소스를 두 번 빌드하고 두 DLL의 `Module.ModuleVersionId`를 비교하라. 소스에 공백 한 줄을 넣고 다시 빌드하면 값이 어떻게 바뀌는가? `<Deterministic>false</Deterministic>`로 두면?
9. `DOTNET_DbgEnableMiniDump=1`, `DOTNET_DbgMiniDumpType=2`, `DOTNET_DbgMiniDumpName=/tmp/core.%p`를 설정하고 처리되지 않은 예외로 죽는 앱을 실행하라. 생성된 덤프를 `dotnet-dump analyze`로 열어 `pe -nested`로 예외를, `clrstack`으로 스택을 확인하라.
10. 74.8절의 스레드 풀 기아 하네스를 실행하면서 `dotnet-counters monitor System.Runtime`을 함께 띄워라. `ThreadPool Queue Length`와 `ThreadPool Thread Count`의 시간에 따른 움직임을 기록하고, `.Result`를 `await`로 바꾼 뒤 같은 그래프를 다시 그려 비교하라.
