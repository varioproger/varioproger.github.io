## 61.1 스택 · 힙 · 레지스터 · 정적 영역

프로그램의 데이터가 놓일 수 있는 자리는 생각보다 적다. 네 곳뿐이다.

| 저장소 | 크기가 정해지는 시점 | 수명 | 접근 방법 | .NET에서 |
|---|---|---|---|---|
| **레지스터(register)** | 컴파일/JIT 시점 | 몇 개 명령어 | 명령어 피연산자 | JIT의 레지스터 할당 결과 |
| **정적 영역(static area)** | 컴파일 시점 | 프로그램 전체 | 고정 주소 | `static` 필드의 저장소 |
| **스택(stack)** | 컴파일 시점(프레임 크기) | 함수 스코프 | SP 기준 오프셋 | 지역 변수, 인자, 활성화 프레임 |
| **힙(heap)** | 실행 시점 | 명시적 또는 GC | 포인터 | 모든 참조 타입 인스턴스 |

아래에서는 역사적으로 등장한 순서 — 정적 영역, 레지스터, 스택, 힙 — 를 따라 하나씩 본다.

### 정적 할당 — 가장 오래된 방법

초기 프로그래밍 언어는 **정적 메모리 할당(static allocation)** 만 지원했다. 필요한 메모리의 양과 정확한 위치를 **컴파일 시점에, 프로그램을 실행하기도 전에** 알아야 했다. 크기가 고정되고 미리 정해져 있으니 메모리 관리는 사소한 문제였다. 기계어와 어셈블리부터 FORTRAN과 ALGOL 초기 버전까지, "고대"의 주요 언어가 모두 이랬다.

대가는 컸다. 정적 할당은 메모리를 비효율적으로 쓰기 쉽다. 얼마나 많은 데이터를 처리할지 미리 모르는데 얼마를 할당할지 어떻게 정하나? 더 큰 데이터를 처리하려면 **다시 컴파일해야 한다.**

최초의 컴퓨터에서는 모든 할당이 정적이었다. 사용하는 메모리 셀(누산기, 레지스터, RAM 셀)이 프로그램을 인코딩하는 시점에 결정됐기 때문이다. 그래서 정의된 "변수"는 프로그램의 전체 수명 동안 살아 있었다. 오늘날에도 정적 전역 변수를 만들 때 이 방식이 그대로 남아 있다 — 프로그램의 특별한 데이터 세그먼트에 저장된다.

> **📌 .NET의 static 필드는 어디에 있나**
>
> C#의 `static` 필드는 개념적으로 정적 영역에 속하지만, 실제 저장 위치는 훨씬 복잡하다. CLR은 타입별 정적 저장소를 고빈도 힙(High Frequency Heap) 위에 만들고, 참조 타입 정적 필드와 값 타입 정적 필드를 다르게 취급한다. 54.5절에서 본 것처럼.

### 레지스터 머신 — 우리가 쓰는 모든 CPU

컴퓨터는 산술 논리 장치(ALU)에서 연산하기 위해 **레지스터(register)** 를 쓴다. 이런 설계에 기반한 기계를 **레지스터 머신(register machine)** 이라 한다. 그런 컴퓨터에서 프로그램을 실행한다는 것은 사실상 **레지스터에 대해 계산한다**는 뜻이다. 더하거나 나누거나 무엇을 하든, 먼저 메모리에서 적절한 레지스터로 데이터를 실어와야 한다. 그다음 연산 명령을 부르고, 또 다른 명령으로 결과를 레지스터에서 메모리로 되돌려 저장한다.

`s = x + (2*y) + z`를 레지스터가 A, B 두 개뿐인 기계에서 계산한다고 하자.

```text
Load      A, y        // A = y
Multiply  A, 2        // A = A * 2 = 2 * y
Load      B, x        // B = x
Add       A, B        // A = A + B = x + 2 * y
Load      B, z        // B = z
Add       A, B        // A = A + B = x + 2 * y + z
Store     s, A        // s = A
```

이게 x86 어셈블리와 닮았다면 우연이 아니다. **현대 컴퓨터 대부분이 복잡한 레지스터 머신**이기 때문이다. 우리가 쓰는 모든 Intel과 AMD CPU가 이렇게 동작한다. x86/x64 어셈블리를 쓸 때 우리는 `eax`, `ebx`, `ecx` 같은 범용 레지스터를 다룬다. 명령어와 특수 레지스터가 훨씬 많을 뿐 개념은 같다.

레지스터 접근은 **데이터 조작 관점에서 즉시적**이다. 단일 프로세서 사이클 안에서 일어나고 추가 지연이 없다. **CPU에 데이터를 두는 자리 중 레지스터보다 가까운 곳은 없다.** 물론 레지스터는 현재 명령에 필요한 데이터만 담으므로 범용 메모리로 볼 수는 없다.

> **📌 메모리에서 직접 연산하는 기계는 없나**
>
> 레지스터로 싣지 않고 메모리에서 바로 연산하는 명령어 집합을 상상해볼 수 있다.
>
> ```text
> Multiply  s, y, 2     // s = 2 * y
> Add       s, x        // s = s + x
> Add       s, z        // s = s + z
> ```
>
> IBM System/360 같은 기계가 실제로 그랬다. 하지만 오늘날 상용으로 쓰이는 그런 컴퓨터는 알려진 바 없다.

### 스택 — LIFO에서 활성화 프레임까지

스택은 개념적으로 **후입선출(LIFO)** 리스트다. 맨 위에 데이터를 올리는 `push`와 맨 위에서 데이터를 빼내는 `pop`, 두 연산을 제공한다. 이 자료 구조 자체의 의미는 지금도 유효하다 — .NET에도 `Stack<T>` 컬렉션이 있다.

스택이 컴퓨터 프로그래밍과 떼려야 뗄 수 없게 된 것은 **서브루틴** 개념 때문이다. 다음 의사 코드를 보자.

```text
void main()
{
   ...
   fun1(2, 3);
   ...
}
int fun1(int a, int b)
{
   int x, y;
   ...
   fun2(a+b);
}
int fun2(int n)
{
   int z;
   ...
}
```

함수가 호출되면 스택은 SP(스택 포인터)를 움직여 확장되고, 다음 세 가지를 저장한다.

- **인자(arguments)** — 함수 인자 전부가 스택에 저장될 수 있다. 예제에서는 `a`(2)와 `b`(3).
- **반환 주소(return address)** — `fun1` 실행 후 `main`을 이어가려면 호출 직후 명령의 주소가 필요하다. 호출 명령이 주소 A1에 있었다면 A1+1을 저장한다.
- **지역 변수(local variables)** — 지역 변수 자리. 예제에서는 `x`와 `y`.

서브루틴이 호출될 때 스택에 놓이는 이 구조를 **활성화 프레임(activation frame)** 이라 한다. 전형적인 구현에서 스택 포인터는 새 활성화 프레임이 시작될 자리를 가리키도록 **적절한 오프셋만큼 감소한다.** 그래서 흔히 **"스택은 아래로 자란다"** 고 말한다. 활성화 프레임은 더 일반적으로 **스택 프레임(stack frame)** 이라고도 부른다 — 특정 목적으로 스택에 저장된 구조화된 데이터 전반을 가리킨다.

세 단계를 그림으로 보자. 주소가 위로 갈수록 커지도록 그렸다.

```text
[1] fun1 호출 직전                    [2] fun1 호출 후

 높은 주소                              높은 주소
 ┌────────────────────┐                ┌────────────────────┐
 │ ▒▒ 기존 프레임 ▒▒  │                │ ▒▒ 기존 프레임 ▒▒  │
 ├────────────────────┤ ← SP           ├────────────────────┤
 │                    │                │  a = 2             │┐
 │                    │                │  b = 3             │├ fun1의
 │      (미사용)      │                │  ret = A1+1        ││ 활성화
 │                    │                │  x                 ││ 프레임
 │                    │                │  y                 │┘
 └────────────────────┘                ├────────────────────┤ ← SP
 낮은 주소                              │      (미사용)      │
                                       └────────────────────┘
 PC ──→ main 안 A1 번지                 PC ──→ fun1 첫 명령
        (call fun1 직전)
```

```text
[3] fun1이 fun2를 호출한 후            [4] fun1에서 반환한 후

 높은 주소                              높은 주소
 ┌────────────────────┐                ┌────────────────────┐
 │ ▒▒ 기존 프레임 ▒▒  │                │ ▒▒ 기존 프레임 ▒▒  │
 ├────────────────────┤                ├────────────────────┤ ← SP
 │  a = 2             │┐               │  a = 2             │┐
 │  b = 3             │├ fun1          │  b = 3             ││
 │  ret = A1+1        ││ 프레임         │  ret = A1+1        ││
 │  x                 ││               │  x                 ││ 죽은 데이터
 │  y                 │┘               │  y                 ││ (덮어쓰기 전까지
 ├────────────────────┤                │  n = 5             ││  그대로 남는다)
 │  n = 5             │┐               │  ret = A2+1        ││
 │  ret = A2+1        │├ fun2          │  z                 │┘
 │  z                 │┘ 프레임         └────────────────────┘
 ├────────────────────┤ ← SP           낮은 주소
 │      (미사용)      │
 └────────────────────┘                PC ──→ main 안 A1+1 번지
 낮은 주소
 PC ──→ fun2 첫 명령
```

중첩 호출이 깊어질수록 활성화 프레임이 하나씩 쌓인다. 그래서 무한 중첩 호출은 불가능하다 — 무한한 개수의 활성화 프레임을 담을 메모리가 필요하기 때문이다. .NET에서 이 무한 루프는 `StackOverflowException`으로 끝난다. 스택 메모리 한계를 넘도록 서브루틴을 중첩 호출한 것이다.

서브루틴이 끝나면 활성화 프레임은 **스택 포인터를 현재 프레임 크기만큼 증가시키는 것만으로** 폐기된다. 저장된 반환 주소로 점프해 호출자로 돌아간다. 프레임 안에 있던 것(지역 변수, 매개변수)은 더 이상 필요 없으므로 SP를 올리는 것만으로 "해제"가 끝난다. 그 데이터는 **다음 함수 호출이 그 자리를 쓸 때 덮어써질 뿐이다.** 위 그림 [4]에서 `n`, `z` 같은 값이 여전히 물리적으로 남아 있는 것을 보라.

> **⚠️ 스택은 "지워지지" 않는다**
>
> 반환 시 스택 데이터가 0으로 초기화된다고 생각하면 안 된다. SP만 움직인다. 그래서 초기화하지 않은 지역 변수는 C 같은 언어에서 **이전 호출이 남긴 쓰레기 값**을 갖는다. C#이 지역 변수의 명확한 할당(definite assignment)을 컴파일 타임에 강제하는 이유가 여기 있다. `stackalloc`으로 얻은 버퍼도 `SkipLocalsInit`을 켜면 초기화되지 않은 채로 온다.

SP와 PC(프로그램 카운터, 명령 포인터라고도 한다)는 보통 전용 레지스터에 담긴다. 현대 컴퓨터에서 스택은 **하드웨어**(스택 포인터 전용 레지스터 제공)와 **소프트웨어**(스레드라는 운영체제 추상화와 그 메모리의 스택 지정 부분) 양쪽에서 지원된다.

> **📌 여기 그린 것은 예시일 뿐이다**
>
> 실제 구현은 아키텍처와 운영체제마다 다르다. x64 System V ABI와 Windows x64 호출 규약은 인자 전달 방식(어느 레지스터를 쓰는지, 섀도 공간이 있는지)부터 다르다. 인자 대부분이 레지스터로 전달되고 스택에는 아예 오르지 않는 경우도 흔하다. 여기서 중요한 건 "프레임이 쌓이고 SP가 움직인다"는 뼈대다.

### 스택 머신 — IL이 그렇게 생긴 이유

레지스터 머신과 대조되는 것이 **스택 머신(stack machine)** 이다. 여기서 모든 명령은 전용 **표현식 스택**(또는 **평가 스택**, evaluation stack)에서 동작한다. 이 스택이 앞에서 본 그 스택과 같을 필요는 없다는 점에 주의하라. 그래서 "표현식 스택"과 범용 스택을 둘 다 가진 기계도 가능하다. 레지스터가 아예 없을 수도 있다.

명령은 기본적으로 필요한 만큼 스택 맨 위에서 인자를 꺼내고, 결과도 스택 맨 위에 올린다. 스택 맨 위에서만 값을 꺼내면 **순수 스택 머신**, 더 깊은 곳에도 접근하면 **비순수 구현**이다.

앞과 같은 `s = x + (2*y) + z`를 스택 머신으로 쓰면 이렇게 된다.

```text
                    // 빈 스택
Push 2              // [2]
Push y              // [2][y]
Multiply            // [2*y]
Push x              // [2*y][x]
Add                 // [2*y+x]
Push z              // [2*y+x][z]
Add                 // [2*y+x+z]
Pop s               // []  (부수 효과로 s에 값을 쓴다)
```

장점은 두 가지다.

- **임시 값을 어디에 둘지 고민할 필요가 없다.** 레지스터냐 스택이냐 주 메모리냐를 최적으로 관리하려 애쓰는 것보다 개념적으로 훨씬 쉽다. 구현이 단순해진다.
- **옵코드가 짧아진다.** 무피연산자·단일 피연산자 명령이 많아 이진 인코딩이 효율적이고 코드가 조밀해진다. 로드/스토어 연산이 더 많이 필요해 명령어 수가 늘어날 수는 있지만, 그래도 이득이다.

메모리가 비싸고 부족하던 초기에 이건 중요한 장점이었다. 오늘날에도 스마트폰이나 웹 애플리케이션처럼 **코드를 내려받는** 상황에서 이득이다. 조밀한 이진 인코딩은 **CPU 명령어 캐시 사용에도 유리하다.**

스택 머신이 하드웨어로 구현된 사례는 드물다. 예외라면 Burroughs B5000 계열, 그리고 x86 호환 CPU 안의 **x87 부동소수점 유닛**이 있다 — 스택 머신으로 설계됐고 하위 호환 때문에 지금도 그렇게 프로그래밍한다.

그런데 왜 이런 기계 얘기를 하나? **플랫폼 독립적인 가상 머신을 설계하는 데 훌륭한 방법**이기 때문이다. **JVM과 .NET 런타임이 완벽한 스택 머신의 예다.** x86이나 ARM이라는 레지스터 머신 위에 구현돼 있지만, 그들이 실현하는 로직은 스택 머신이다.

왜 그렇게 설계했나? 스택 머신 코드는 **가용 레지스터 개수에 의존하지 않아** 하드웨어를 추상화하기에 좋다. 스택 머신 코드를 실제 레지스터 기반 코드로 번역하는 일은 대상 하드웨어별 구현에 맡긴다. 가상 스택 머신은 구현하기 쉽고 좋은 플랫폼 독립성을 주면서도 고성능 코드를 만들어낸다. 조밀한 코드 밀도까지 합치면, 넓은 범위의 장치에서 돌아야 하는 플랫폼에 좋은 선택이다.

> **📌 모든 가상 머신이 스택 머신은 아니다**
>
> 전혀 그렇지 않다. Android 4.4 이전 Google의 Dalvik은 **레지스터 기반** JVM 구현이었다. BEAM(Erlang/Elixir), Chakra(IE9의 JavaScript 엔진), Parrot(Perl 6), Lua VM도 있다. 레지스터 기반 설계는 실제 하드웨어에 더 가까워 최적화에 유리하다는 주장이 있고, 특히 인터프리터 런타임에서 그렇다. 논쟁은 아직 끝나지 않았다.

### 포인터

**포인터(pointer)** 는 메모리 위치의 주소를 담는 변수다. 주소로 메모리의 다른 곳을 참조할 수 있게 해준다. 포인터 크기는 **워드 길이(word length)** 와 관련되며 컴퓨터 아키텍처에 달렸다. 오늘날 우리는 보통 32비트 또는 64비트 폭 포인터를 다루고, 그것들은 스택(지역 변수나 함수 인자로) 또는 CPU 레지스터에 놓인다.

```text
        스택                              힙 (또는 다른 메모리 영역)
 ┌────────────────────┐
 │  ...               │            ┌──────────────────────┐
 ├────────────────────┤            │                      │
 │  ptr = 0x7F3A_1000 │───────────→│  0x7F3A_1000 부터    │
 ├────────────────────┤            │  시작하는 데이터      │
 │  ...               │            │                      │
 └────────────────────┘            └──────────────────────┘
```

포인터라는 단순한 착상 덕에 연결 리스트나 트리 같은 정교한 자료 구조를 만들 수 있다. 메모리 안의 데이터 구조가 서로를 참조해 더 복잡한 구조를 이룰 수 있기 때문이다.

> **📌 명령 포인터와 스택 포인터도 포인터다**
>
> 포인터 개념은 컴퓨팅 초기부터 있었다. 앞에서 본 명령 포인터(PC)나 스택 포인터(SP)가 그렇다. 메모리 주소 지정을 위한 인덱스 레지스터도 포인터로 볼 수 있다. 인덱스 레지스터는 Manchester Mark 1에서 도입됐고, 다른 레지스터 값에 더해 메모리를 간접 참조할 수 있게 해 배열 같은 연속 메모리 영역을 다루는 명령 수를 줄였다.

### 힙 — 자유 저장소

드디어 .NET 메모리 관리에서 가장 중요한 개념에 도달했다. **힙(heap)** 은 동적으로 할당된 객체를 위한 메모리 영역이다. **자유 저장소(free store)** 라는 덜 알려진 이름이 사실 더 나은 이름이다. 내부 구조를 암시하지 않고 목적만 말하기 때문이다.

여기서 정당한 의문 하나. **힙 자료 구조와 이 "힙"은 무슨 관계인가?** 답은 **아무 관계도 없다.** 스택은 잘 조직돼 있지만(LIFO 자료 구조 개념 기반), 힙은 그저 "메모리를 달라"고 요청하면 어디서든 가져다주는 **블랙박스**에 가깝다. "풀(pool)"이나 "자유 저장소"가 훨씬 나은 이름이었을 것이다. "힙"이라는 이름은 아마 잘 정돈된 스택 공간과 대비되는 **"어질러진 곳"** 이라는 영어의 전통적 의미에서 처음부터 쓰였을 것이다. 역사적으로는 ALGOL 68이 힙 할당을 도입했지만 널리 채택되지는 않았다.

힙은 **지정된 크기의 연속된 메모리 블록을 제공할 수 있는 메커니즘**이다. 이 연산을 **동적 메모리 할당(dynamic memory allocation)** 이라 부른다. 크기와 실제 위치 모두 컴파일 시점에 알 필요가 없기 때문이다. 위치를 컴파일 시점에 모르므로 동적 할당 메모리는 **반드시 포인터로 참조해야 한다.** 포인터와 힙은 본질적으로 얽혀 있다.

```text
        스택                              힙
 ┌────────────────────┐
 │  ptr ──────────────┼───┐        ┌──────────────────────────┐
 └────────────────────┘   └───────→│ 10바이트 블록            │
                                   ├──────────────────────────┤
   PTR ptr = allocate(10);         │ (다른 할당들)            │
                                   └──────────────────────────┘
```

할당의 역연산은 **해제(deallocation)** 로, 주어진 블록을 이후 사용을 위해 메모리 풀에 되돌린다. 힙이 주어진 크기의 블록을 **어떻게** 할당하는지는 구현 세부사항이다. 여러 종류의 **할당자(allocator)** 가 존재한다.

많은 블록을 할당하고 해제하다 보면, **전체적으로는 자유 공간이 충분한데도 특정 객체를 위한 연속 자유 공간이 부족한** 상황에 이를 수 있다. 이것이 **힙 단편화(heap fragmentation)** 이며 심각한 메모리 비효율을 낳는다.

```text
 할당/해제를 반복한 뒤의 힙

 ┌────┬──────┬────┬──────┬────┬────────┬────┐
 │ A  │ 자유 │ C  │ 자유 │ E  │  자유  │ F  │
 └────┴──────┴────┴──────┴────┴────────┴────┘
        (B 삭제)    (D 삭제)

 자유 공간 합계는 X를 담기에 충분하다.
 그러나 X가 들어갈 만한 "연속된" 자유 공간은 없다.

 ┌──────────────┐
 │      X       │  ← 어디에도 못 들어간다
 └──────────────┘
```

프로세스 안에 힙이 하나인지 여러 개인지도 구현 세부사항이다. .NET의 답은 62장에서 본다.

### 스택과 힙 비교

| 속성 | 스택 | 힙 |
|---|---|---|
| **수명** | 지역 변수는 함수 스코프(진입 시 push, 탈출 시 pop) | 명시적(할당, 그리고 선택적 해제) |
| **범위** | 지역(스레드) | 전역(포인터를 가진 누구든) |
| **접근** | 지역 변수, 함수 인자 | 포인터 |
| **접근 시간** | 빠름(자주 쓰는 영역이라 CPU 캐시에 있을 확률이 높다) | 느림(디스크로 스왑됐을 수도 있다) |
| **할당** | 스택 포인터 이동 | 여러 전략 가능 |
| **할당 시간** | 매우 빠름(SP를 더 미는 것) | 느림(할당 전략에 따라) |
| **해제** | 스택 포인터 이동 | 여러 전략 가능 |
| **용도** | 서브루틴 매개변수, 지역 변수, 활성화 프레임, 작은 고정 크기 배열 | 전부 |
| **용량** | 제한적(보통 스레드당 수 MB) | 사실상 무제한(GB + 디스크 여유, OS 설정에 따름). 32비트에서는 최대 4 GB |
| **가변 크기** | 불가 | 가능(재할당 함수 제공) |
| **단편화** | 없음 | 발생하기 쉬움 |
| **주 위험** | 스택 오버플로 | 메모리 누수(해제 잊음), 단편화 |

> **⚠️ "값 타입은 스택에 간다"는 반쪽 진실이다**
>
> 이 말은 자주 틀린다. `int[]` 배열을 만들면 배열 자체가 참조 타입이므로 **힙에 놓이고**, 그 안의 `int` 원소들은 전부 **힙에 연속으로** 놓인다. 클래스의 `int` 필드도 힙에 있다. 값 타입 지역 변수가 스택에 놓이는 것은 "값 타입이라서"가 아니라 **"지역 변수라서"** 다. 16장에서 본 값 타입의 정의도, 15장에서 본 박싱도 저장 위치를 규정하지 않는다. 그마저도 JIT이 레지스터에 올려버리면 스택에 아예 안 나타난다. 더 정확한 표현은 이것이다 — **저장 위치는 타입이 아니라 그 변수가 어디에 선언됐는지가 결정한다.** 자세히는 62장과 63장에서 다룬다.

> **⚠️ "참조 타입은 참조 카운팅된다"는 틀린 설명이다**
>
> 일부 C# 입문서가 "참조 타입은 reference-counted라서 그렇게 부른다"고 쓴다. **.NET은 참조 카운팅을 쓰지 않는다.** 참조 타입이라는 이름은 "값이 아니라 참조(주소)로 다뤄진다"는 뜻일 뿐이고, .NET의 수집기는 참조 카운터가 아니라 **도달 가능성 추적**으로 동작한다. 두 방식의 차이는 61.9절에서 정면으로 다룬다. 참조 카운팅을 실제로 쓰는 것은 COM 상호 운용 경계와 `SafeHandle` 같은 특정 지점뿐이다.

> **💡 스택 사용량을 줄이는 것은 대체로 이득이다**
>
> 메서드를 작게 유지하고 실행되지 않을 죽은 코드를 제거하면 사용 중인 지역 변수 수가 줄고 스택 프레임이 작아진다. 프레임이 작으면 같은 캐시 라인 안에 더 많은 프레임이 들어가고, 함수 진입/탈출 시 건드릴 메모리가 줄어든다. 다만 이건 마이크로 최적화다. 인라인 여부와 JIT의 레지스터 할당이 결과를 크게 바꾸므로, **측정 없이 믿지 마라.**

## 61.2 가상 메모리, 페이지, 대용량 페이지, 단편화

### 왜 가상 메모리가 필요했나

운영체제와 하드웨어 아키텍처에 따라 물리 메모리 한계는 2 GB에서 24 TB까지 다양하다. 요즘 흔한 하드웨어도 수십 GB를 달고 있다. 만약 프로그램이 **물리 메모리를 직접** 써야 한다면 무슨 일이 벌어질까?

- 자기가 만들고 지우는 모든 메모리 영역을 스스로 관리해야 한다. 이 로직은 복잡할 뿐 아니라 **모든 프로그램마다 반복**된다.
- 각 프로그램이 자기가 쓰는 영역을 기억해서 서로 간섭하지 않게 해야 한다. 할당자끼리 협력해야 한다.
- 보안상 위험하다. 중간 계층이 없으면 프로그램이 **자기 메모리뿐 아니라 다른 프로세스의 데이터 전부**에 접근할 수 있다.

그래서 아주 편리한 추상화가 도입됐다 — **가상 메모리(virtual memory)** 다. 메모리 관리 로직을 운영체제로 옮기고, 운영체제는 모든 프로그램에 **가상 주소 공간(virtual address space)** 을 제공한다. 각 프로세스는 자기가 시스템에서 유일하게 돌아가고 있으며 메모리 전체가 자기 것이라고 **믿는다.** 더 좋은 점은, 주소 공간이 가상이므로 **물리 메모리보다 클 수 있다**는 것이다.

운영체제 메모리 관리자의 책임은 두 가지다.

- **가상 주소 공간을 물리 메모리에 매핑한다.** 가상 주소는 32비트 머신에서 32비트, 64비트 머신에서 64비트다(다만 현재는 하위 48비트만 쓰이며, 그래도 128 TB 주소 공간이 나온다).
- **일부 메모리 영역을 DRAM에서 디스크로 옮긴다.** 총 사용 메모리가 물리 메모리보다 클 수 있으므로 데이터를 HDD/SSD 같은 느린 매체에 임시 저장하는 메커니즘이 필요하다. 이 데이터는 **페이지 파일** 또는 **스왑 파일**에 저장된다.

RAM의 데이터를 임시 저장소에 내보내는 일은 당연히 성능을 크게 떨어뜨린다. 이 과정을 시스템에 따라 **스와핑(swapping)** 또는 **페이징(paging)** 이라고 부르는데, 대체로 역사적 이유다. Windows에는 **페이지 파일**이라는 전용 파일이 있어 페이징이라 하고, Linux는 **스왑 파티션**에 저장하므로 Unix 계열에서는 스와핑이라 한다.

> **📌 가상 메모리 없는 운영체제도 있나**
>
> 일반적인 용도로는 없다. 다만 μClinux 커널처럼 임베디드 대상의 아주 작은 운영체제·프레임워크는 존재한다.

### 페이지와 페이지 디렉터리

가상 메모리는 **CPU의 메모리 관리 유닛(MMU)** 이 운영체제와 협력해 구현한다. 가상-물리 공간을 바이트 단위로 매핑하는 건 너무 비싸므로 **페이지(page)** 라는 연속 메모리 블록 단위로 한다.

```text
    프로세스 A의 가상 주소 공간           물리 메모리 (RAM)
  ┌────────────────────────┐          ┌────────────────────────┐
  │ 페이지 A0              │────┐     │ 프레임 0   ← A0        │
  ├────────────────────────┤    └────→├────────────────────────┤
  │ 페이지 A1              │─────────→│ 프레임 1   ← B0        │
  ├────────────────────────┤          ├────────────────────────┤
  │ 페이지 A2              │───┐      │ 프레임 2   ← A1        │
  └────────────────────────┘   │      ├────────────────────────┤
                               │      │ 프레임 3   ← B1        │
    프로세스 B의 가상 주소 공간 │      ├────────────────────────┤
  ┌────────────────────────┐   │      │ 프레임 4   (비어 있음) │
  │ 페이지 B0              │───┼─────→└────────────────────────┘
  ├────────────────────────┤   │
  │ 페이지 B1              │───┘        페이지 파일 / 스왑
  ├────────────────────────┤          ┌────────────────────────┐
  │ 페이지 B2              │─────────→│ 스왑아웃된 A2, B2      │
  └────────────────────────┘          └────────────────────────┘

  두 프로세스는 같은 가상 주소를 쓸 수 있다. 물리적으로는 서로 다른
  프레임에 매핑되거나, 아예 디스크로 밀려나 있다.
```

운영체제는 프로세스마다 **페이지 디렉터리(page directory)** 를 유지해 가상 주소를 물리 주소로 매핑한다. 간단히 말해 페이지 디렉터리 항목은 페이지의 **물리 시작 주소**와 **권한 같은 메타데이터**를 가리킨다.

현대 운영체제는 흔히 **다단계 디렉터리**를 쓴다. 페이지 크기를 작게 유지하면서 희소한(sparse) 페이지 디렉터리 데이터를 조밀하게 저장할 수 있기 때문이다. 현재 대부분의 아키텍처(x86, x64, ARM 포함)에서 **전형적인 페이지 크기는 4 kB이고 4단계 페이지 디렉터리**를 쓴다.

```text
  가상 주소 (48비트 유효)
  ┌────────┬────────┬────────┬────────┬──────────────┐
  │ L1 선택│ L2 선택│ L3 선택│ L4 선택│  페이지 내 오프셋 │
  └───┬────┴───┬────┴───┬────┴───┬────┴──────┬───────┘
      │        │        │        │           │
      ↓        │        │        │           │
  ┌────────┐   │        │        │           │
  │ L1 디렉│───┘        │        │           │
  │  터리  │            │        │           │
  └────────┘            │        │           │
      ↓                 │        │           │
  ┌────────┐            │        │           │
  │ L2 디렉│────────────┘        │           │
  └────────┘                     │           │
      ↓                          │           │
  ┌────────┐                     │           │
  │ L3 디렉│─────────────────────┘           │
  └────────┘                                 │
      ↓                                      │
  ┌────────┐        물리 메모리               │
  │ L4 디렉│───→ ┌──────────────────┐         │
  └────────┘     │  4 kB 페이지     │←────────┘
                 │  ...   [대상 주소]│
                 └──────────────────┘
```

이 변환은 **물리 메모리에 보관된 페이지 디렉터리 트리를 걸어야(walk) 한다.** 그러니 이 데이터 자체도 L1/L2/L3 캐시에 캐시될 수 있다. 그래도 매번(아주 자주 수행되는) 주소 변환마다 이 데이터에 접근한다면 엄청난 오버헤드다.

그래서 **변환 색인 버퍼(TLB, Translation Look-Aside Buffer)** 가 도입됐다. 변환 자체를 캐시한다. 선택자가 키, 페이지의 물리 시작 주소가 값인 맵이라고 보면 된다. TLB는 극도로 빨라야 하므로 저장 용량이 작다. 페이지 디렉터리 구조를 흉내 내 다단계로도 만든다. **TLB 미스**의 결과는 전체 페이지 디렉터리 워크 수행이고, 이건 비싸다.

> **⚠️ L1 캐시는 보통 가상 주소로 동작한다**
>
> 물리 주소로 번역하는 비용이 캐시 접근 자체보다 훨씬 크기 때문이다. 이 말은 **페이지가 바뀌면 캐시 라인 전부 또는 일부를 무효화해야 한다**는 뜻이다. 따라서 **페이지 전환이 잦으면 캐시 성능이 떨어진다.** 메모리를 넓게 흩뿌리며 접근하는 코드는 캐시 미스뿐 아니라 TLB 미스와 캐시 무효화까지 세 겹으로 손해를 본다.

> **📌 TLB 프리페칭은 소프트웨어가 제어한다**
>
> 모든 캐시가 그렇듯 TLB 프리페칭도 까다롭다. CPU가 분기 예측 등을 이유로 스스로 프리페치를 촉발하면, 예측이 틀렸을 때 **불필요한 페이지 디렉터리 워크**를 유발한다. 이를 막기 위해 TLB 프리페칭은 소프트웨어가 제어한다. 또한 **하드웨어 프리페칭은 페이지 경계를 넘지 않는다.** 넘는다면 추측이 틀렸을 때 큰 오버헤드가 될 페이지 미스를 촉발하기 때문이다.

### 페이지 폴트 — 매핑이 없을 때 벌어지는 일

가상 주소를 물리 주소로 변환하려는데 **해당 매핑이 없으면** CPU가 예외를 일으키고 운영체제가 개입한다. 이것이 **페이지 폴트(page fault)** 다. 이름 때문에 오류처럼 들리지만, 대부분의 페이지 폴트는 **정상적이고 필수적인 동작**이다.

| 종류 | 무슨 일이 일어나나 | 비용 |
|---|---|---|
| **소프트 페이지 폴트** | 페이지가 물리 메모리에는 있지만 이 프로세스의 페이지 테이블에 아직 매핑되지 않았다. OS가 테이블 항목만 채운다 | 낮다(디스크 접근 없음) |
| **하드 페이지 폴트** | 페이지가 물리 메모리에 없다. **디스크(페이지 파일/스왑, 또는 매핑된 실행 파일)에서 읽어와야 한다** | **매우 높다.** 61.4절의 HDD 지연 표를 보라 |
| **무효 접근** | 예약만 됐거나 아예 매핑되지 않은 주소. Windows는 액세스 위반, Linux는 세그멘테이션 폴트 | 프로세스가 죽는다 |

CLR이 페이지를 커밋한 직후 그 페이지에 처음 쓸 때 발생하는 것이 전형적인 **소프트 페이지 폴트**다. Windows 메모리 관리자가 이때 0으로 초기화된 물리 프레임을 붙여준다. **Linux의 지연 할당도 정확히 같은 메커니즘 위에 서 있다** — `mmap`은 매핑만 만들고, 실제 물리 프레임은 첫 접근의 페이지 폴트에서 붙는다.

> **⚠️ 하드 페이지 폴트가 보이면 성능 튜닝은 거기서 멈춰야 한다**
>
> 프로세스가 하드 페이지 폴트를 지속적으로 일으킨다면 물리 메모리가 부족해 스와핑이 일어나고 있는 것이다. 이 상태에서 GC 튜닝이나 알고리즘 최적화를 논하는 것은 무의미하다 — 61.4절 표대로 디스크 접근은 DRAM보다 **세 자릿수** 느리다. **GC 자신이 힙 전체를 훑는 마크 단계에서 하드 페이지 폴트를 대량으로 일으키면 일시 정지 시간이 초 단위로 폭발한다.** Windows에서는 `Process\Page Faults/sec`와 `Memory\Pages/sec` 카운터를, Linux에서는 `/proc/<pid>/stat`의 `majflt`나 `vmstat`의 `si`/`so`를 먼저 확인하라.

### 대용량 페이지

주소 변환이 비싸다면 **페이지를 더 크게** 만들면 된다. 같은 페이지 안에 더 많은 주소가 들어가므로 이미 TLB에 캐시된 변환을 재사용할 수 있어 변환 횟수가 준다. 하지만 큰 페이지는 RAM이나 스왑 파일 공간을 낭비할 수 있다.

절충안이 **대용량 페이지(large page, 또는 huge page)** 다. 하드웨어 지원을 받아, 순차적으로 배치된 다수의 일반 페이지로 이루어진 크고 연속된 물리 메모리 블록을 만든다. 이 페이지들은 **보통 일반 페이지보다 두세 자릿수(대략 100~1000배) 크다.** 기가바이트 단위 데이터에 무작위 접근이 필요한 시나리오에서 유용하다 — 데이터베이스 엔진이 대표적 소비자다. Windows 운영체제도 자기 커널 이미지와 데이터를 대용량 페이지로 매핑한다.

대용량 페이지는 **페이지 아웃될 수 없고(non-pageable)**, Windows와 Linux 모두에서 지원된다. 다만 **대용량 페이지를 채우기가 상당히 어렵다** — 그래서 단편화로 이어진다. 애초에 연속된 물리 메모리 범위가 없을 수도 있다.

.NET에서는 .NET Core 3.0부터 `COMPlus_GCLargePages` / `DOTNET_GCLargePages` 설정으로 대용량 페이지를 켤 수 있다. 자세히는 65.6절에서 다룬다.

> **⚠️ 대용량 페이지는 켜기만 하면 빨라지는 스위치가 아니다**
>
> 대용량 페이지는 (1) 운영체제 수준에서 권한 설정이 필요하고(Windows에서는 "메모리에 페이지 잠금" 권한), (2) 연속된 물리 메모리를 확보하지 못하면 실패하거나 시작이 느려지고, (3) 페이지 아웃될 수 없으므로 그만큼의 물리 RAM을 프로세스가 붙잡는다. 무작위 접근이 지배적이고 작업 집합이 수 GB인 워크로드가 아니면 이득보다 손해가 크기 쉽다.

### 가상 메모리 단편화

메모리를 할당하고 해제하는 곳이면 어디든 단편화가 나타난다. 가상 메모리의 경우 그것은 **운영체제가 프로세스 주소 공간 안에서 주어진 크기의 연속 블록을 예약하지 못한다**는 뜻이다. 이미 예약된 메모리 사이에 충분히 큰 틈이 없다. **자유 틈의 총합이 요구 크기를 크게 넘어서는데도** 그렇다.

이 문제는 오늘날 요구에 비해 가상 공간이 너무 작은 **32비트 애플리케이션**에서 심각할 수 있다. 프로세스가 큰 메모리 세그먼트를 할당하면서 오래 동작할 때 특히 심하다 — **IIS에 호스팅된 32비트 .NET 웹 애플리케이션**이 정확히 그런 상황이었다. 단편화를 막으려면 프로세스가 메모리를 제대로 관리해야 하고, .NET 프로세스에서 그것은 **CLR 자신**을 뜻한다.

> **💡 64비트로 옮기는 것이 거의 항상 정답이다**
>
> 32비트 .NET 프로세스는 64비트 Windows에서 돌더라도 가상 주소 공간 한계가 4 GB다. "물리 메모리는 남는데 `OutOfMemoryException`이 난다"는 증상은 십중팔구 물리 메모리 부족이 아니라 **가상 주소 공간 단편화**다. 레거시 네이티브 의존성 때문에 32비트를 유지해야 하는 게 아니라면 `<PlatformTarget>x64</PlatformTarget>`로 옮기는 것이 어떤 GC 튜닝보다 효과가 크다.

## 61.3 Windows / Linux 메모리 관리와 레이아웃

### 일반적인 프로세스 메모리 레이아웃

프로그램의 주소 공간은 크게 두 영역으로 나뉜다.

- **커널 공간(kernel space)** — 주소의 상위 범위를 운영체제 자신이 차지한다. 디바이스 드라이버와 커널 자료 구조가 매핑되는 곳이라 커널 공간이라 부른다. **커널 코드만** 이 부분에 접근할 수 있다.
- **사용자 공간(user space)** — 주소 공간의 하위 부분으로 애플리케이션 코드가 쓴다(널 포인터 탐지에 쓰이는 맨 아래는 제외).

우리 관심사는 당연히 사용자 공간이다. CLR이 우리 데이터를 저장하는 곳이 여기다. 사용자 공간에는 다음이 놓인다.

- **스레드마다 스택이 하나씩** 생성된다.
- 운영체제는 런타임이 **힙을 만들 수 있는 여러 API**를 제공한다.
- 애플리케이션이 시작되면 운영체제가 **디스크의 바이너리 파일을 주소 공간에 매핑**한다. 실행 가능한 어셈블리 코드 같은 일부 읽기 전용 데이터는 프로세스 간에 공유될 수 있다.

이건 조감도다. 현실은 더 복잡하고, 두 주요 운영체제에서 서로 다르다.

### Windows — 주소 공간 한계

| 프로세스 종류 | Windows(32비트) | Windows 8 / Server 2012 | Windows 8.1+ / Server 2012+ |
|---|---|---|---|
| 32비트 | 2/2 GB | 2/2 GB | 2/2 GB |
| 32비트 (*) | 3/1 GB | 4 GB / 8 TB | 4 GB / 128 TB |
| 64비트 | – | 8/8 TB | 128/128 TB |

(*) 큰 주소 인식(large address aware) 플래그, `/3GB` 스위치로도 알려진 것

32비트 시대 말기에 이 한계는 고통스러웠다. 2 GB(확장 모드에서 3 GB)로 제한되는 것은 큰 엔터프라이즈 애플리케이션에서 문제였다. 32비트 Windows Server의 IIS에 호스팅된 ASP.NET 웹 애플리케이션이 고전적 예다. 한계에 도달하면 **웹 애플리케이션 전체를 재시작하는 것 외에 방법이 없었다.** 이 때문에 대형 웹 시스템은 수평 확장을 강요당했다 — 트래픽을 덜 받고 메모리를 덜 쓰는 서버 인스턴스를 여러 개 만드는 식으로. 지금은 64비트 세상이라 이 문제는 사라졌다. 다만 **32비트로 컴파일된 프로그램은 64비트 Windows Server에서도 가상 주소 공간 한계가 4 GB**라는 점은 여전하다.

> **📌 AWE는 CLR과 무관하다**
>
> Windows에는 여기 나열된 것보다 더 많은 물리 메모리에 접근한 뒤 그 일부만 "AWE 창"을 통해 가상 주소 공간에 매핑하는 **주소 창 확장(AWE, Address Windowing Extensions)** 메커니즘이 있다. 32비트 환경에서 프로세스당 2~3 GB 한계를 넘는 데 유용했다. 하지만 **CLR은 이 기능을 활용하지 않으므로** .NET 개발자에게는 관계없는 이야기다.

### Windows — 두 개의 API, 그리고 두 단계 할당

Windows 메모리 관리자는 두 가지 주요 API를 제공한다.

| API 계층 | 함수 | 역할 | CLR이 쓰나 |
|---|---|---|---|
| **가상 메모리(Virtual)** | `VirtualAlloc`, `VirtualFree`, `VirtualLock`, `VirtualUnlock` | 주소 공간 자체를 다뤄 페이지를 **예약(reserve)** 하고 **커밋(commit)** 한다 | **쓴다** |
| **힙(Heap)** | `HeapAlloc`, `HeapFree` | 상위 수준 API로 할당자를 제공. C/C++ 런타임이 `malloc`/`free`, `new`/`delete`를 구현하는 데 쓴다 | 직접은 안 쓴다(*) |

(*) CLR은 .NET 객체를 위한 **자기 할당자**를 갖고 있으므로 Virtual API만 쓴다. 다만 CLR 자신의 내부 네이티브 자료 구조는 C++ `new` 연산자로 만들고, 그건 Heap API 위에 올라간다.

Windows의 가상 메모리 API는 **두 단계**로 동작한다.

1. **예약** — `VirtualAlloc`을 `MEM_RESERVE`와 `PAGE_READWRITE`로 호출해 주소 공간에서 연속 범위를 확보한다. 메모리 관리자가 예약된 범위의 시작 주소를 돌려준다. **주의: 아직 이 메모리에 접근할 수 없다.**
2. **커밋** — 읽거나 쓸 때가 되면 예약된 범위에서 **필요한 페이지만** 커밋한다. 범위 전체를 커밋할 필요가 없다.

CLR이 하는 일이 정확히 이것이다. **주소 공간에 큰 범위를 한 번 예약해두고, 객체를 더 할당할 공간이 필요할 때마다 페이지를 커밋한다.** 커밋된 페이지에 처음 접근하면 메모리 관리자가 **0으로 초기화되어 있음을 보장한다.**

객체가 수집되고 충분한 자유 공간이 감지되면 해당 페이지는 `VirtualFree`를 `MEM_DECOMMIT`으로 호출해 **디커밋**되어 Windows 메모리 관리자에게 반환된다.

> **⚠️ 자유 메모리나 예약된 메모리에 접근하면 액세스 위반이다**
>
> 예약만 하고 커밋하지 않은 페이지는 아직 물리 메모리에 매핑될 수 없다. 접근하면 액세스 위반 예외가 난다. "`VirtualAlloc`이 성공했으니 써도 된다"는 착각이 네이티브 상호 운용 코드에서 흔한 사고 원인이다.

> **📌 왜 두 단계로 나눴나**
>
> 순차적 메모리 접근 패턴은 여러 이유로 좋다. 연속된 페이지 시퀀스로 이루어진 공간은 단편화를 막고 TLB 사용을 최적화하며 페이지 디렉터리 워크를 피한다. 캐시 활용에도 당연히 유리하다. 그러니 **지금 필요하지 않더라도 큰 공간을 미리 예약해두는 것이 좋다.** 운영체제가 스레드 스택을 구현하는 방식이 정확히 이렇다 — 스택 전체를 주소 공간에 예약해두고, 더 깊은 메서드 호출이 매개변수와 지역 변수를 위해 공간을 요구할 때마다 페이지를 하나씩 커밋한다.

### Windows — 메모리 지표의 집합 관계

"우리 .NET 프로세스가 메모리를 얼마나 쓰나"라는 질문의 답이 간단하지 않은 이유가 여기 있다.

```text
             ┌──────────────────────────────────────────────┐
             │  가상 바이트 (Virtual bytes)                 │
             │  주소 공간에 예약된 전부(커밋+미커밋)         │
             │                                              │
             │   ┌────────────────────────────────────────┐ │
             │   │  프라이빗 바이트 (Private bytes)       │ │
             │   │  커밋된 프라이빗 페이지 전부           │ │
             │   │  (물리 + 페이지 파일)                  │ │
             │   │                                        │ │
             │   │  ┌──────────────┬───────────────────┐  │ │
             │   │  │ 프라이빗     │ 페이지된 바이트   │  │ │
             │   │  │ 워킹 세트    │ (Paged bytes)     │  │ │
             │   │  │ = 물리 상주  │ = 페이지 파일에   │  │ │
             │   │  └──────┬───────┴───────────────────┘  │ │
             │   └─────────┼──────────────────────────────┘ │
             │             │                                │
             │   ┌─────────┴────────────────┐               │
             │   │ 워킹 세트 (Working set)  │               │
             │   │ = 물리 메모리에 상주하는  │               │
             │   │   가상 주소 공간의 부분   │               │
             │   │   (프라이빗 + 공유)       │               │
             │   └──────────────────────────┘               │
             └──────────────────────────────────────────────┘
```

- **워킹 세트(working set)** — 현재 물리 메모리에 상주하는 가상 주소 공간의 부분. **프라이빗 워킹 세트**(물리 메모리에 있는 커밋된 프라이빗 페이지)와 **공유 워킹 세트**(다른 프로세스와 공유되는 페이지)로 나뉜다.
- **프라이빗 바이트(private bytes)** — 커밋된 프라이빗 페이지 전부. 물리 메모리에 있든 페이지 파일에 있든.
- **가상 바이트(virtual bytes)** — 주소 공간에 예약된 메모리(커밋됐든 아니든).
- **페이지된 바이트(paged bytes)** — 가상 바이트 중 페이지 파일에 저장된 부분.

우리 객체가 저장되는 메모리는 프로세스의 **프라이빗 커밋 메모리**다. 공유 가능 커밋 메모리는 실행 파일에 저장된 어셈블리 코드 같은 읽기 전용 데이터를 세는 것이라 이 맥락에서는 흥미롭지 않다.

> **⚠️ "프라이빗 워킹 세트만 보면 된다"는 틀렸다**
>
> 프라이빗 워킹 세트가 가장 중요한 지표라는 오해가 흔하다. 실제 물리 RAM 소비를 보여주니 그럴듯하다. 하지만 **메모리 누수가 있을 때는 프라이빗 바이트가 늘어나되 프라이빗 워킹 세트는 그렇지 않을 수 있다.** 누수된 페이지가 접근되지 않으니 페이지 아웃되어버리기 때문이다. 누수를 추적할 때는 **프라이빗 바이트**를 봐야 한다.

프라이빗 페이지는 **잠글(lock) 수도 있다.** 잠긴 페이지는 명시적으로 잠금을 풀거나 애플리케이션이 끝날 때까지 물리 메모리에 남는다(페이지 파일로 이동하지 않는다). 프로그램의 성능 임계 경로에서 이득이 될 수 있다.

### Windows — 할당 세분성 64 kB

Windows가 프로세스 주소 공간에 메모리 영역을 예약할 때는 내부 구조 때문에 제약이 붙는다. **영역의 시작과 크기 모두가 시스템 페이지 크기(보통 4 kB)와 이른바 할당 세분성(allocation granularity, 보통 64 kB)의 배수여야 한다.** 실질적으로 모든 예약 영역의 시작 주소와 크기는 64 kB의 배수다. 더 작게 할당하려 하면 **나머지는 접근 불가(사용 불가)** 가 된다. 그러니 블록의 적절한 정렬과 크기는 메모리 낭비를 막는 데 결정적이다.

> **📌 왜 페이지는 4 kB인데 할당 세분성은 64 kB인가**
>
> Raymond Chen이 2003년에 답했다. 대체로 역사적 이유다. 오늘날 Windows 계열의 커널은 초기 Windows NT 커널에 뿌리를 두는데, NT는 DEC Alpha를 포함해 여러 플랫폼을 지원했다. 다양한 지원 플랫폼 때문에 이 제약이 도입됐고, 다른 플랫폼에 골칫거리가 아니라고 판단되어 공통 커널 코드베이스를 유지하는 쪽이 선호됐다. 매일 Virtual API 수준에서 메모리를 관리하지는 않더라도, 이 지식은 **CLR 코드가 왜 그렇게 정렬에 신경 쓰는지** 이해하는 데 도움이 된다.

### Windows — 힙 종류와 프로세스 레이아웃

프로세스는 **기본 프로세스 힙** 하나(주로 내부 Windows 함수가 쓴다)와 Heap API로 만든 임의 개수의 선택적 힙을 갖는다. Microsoft C 런타임이 만들어 C/C++ 연산자가 소비하는 힙이 그런 예다. 주요 힙 종류는 셋이다.

| 힙 종류 | 설명 |
|---|---|
| **일반(NT) 힙** | 일반(비 UWP) 앱이 쓴다. 메모리 블록 관리의 기본 기능을 제공 |
| **저단편화 힙(LFH)** | 일반 힙 위의 추가 계층. 미리 정의된 다양한 크기의 블록으로 할당을 관리해 작은 데이터의 단편화를 막고, 내부 OS 최적화 덕에 접근도 약간 빠르다 |
| **세그먼트 힙(Segment heap)** | UWP 앱이 쓴다. 저단편화 할당자를 포함한 더 정교한 할당자를 제공 |

.NET 관리 코드를 실행하는 Windows 프로세스의 사용자 공간 레이아웃은 대략 이렇다.

- 앞서 말한 기본 힙
- 대부분의 이미지(exe, dll)는 **높은 주소**에 위치
- **스레드 스택은 아무 데나** 있을 수 있다. 프로세스의 각 스레드가 자기 스택 영역을 갖는다. 네이티브 시스템 스레드를 감싼 CLR 스레드도 마찬가지다
- 우리가 만든 .NET 객체를 담는 **CLR 관리 GC 힙**(Windows 용어로는 Virtual API로 예약·커밋된 평범한 페이지들이다)
- 내부 용도의 **여러 CLR 프라이빗 힙**
- 그리고 주소 공간 한가운데에 기가바이트·테라바이트 단위의 거대한 **빈 가상 주소 공간**

### Windows / Linux 레이아웃 대비

```text
        Windows (x64, 64비트)                 Linux (x64, 64비트)
   0xFFFF_FFFF_FFFF_FFFF                 0xFFFF_FFFF_FFFF_FFFF
  ┌──────────────────────────┐          ┌──────────────────────────┐
  │                          │          │                          │
  │   커널 공간  128 TB      │          │   커널 공간  128 TB      │
  │                          │          │                          │
  ├──────────────────────────┤ 경계     ├──────────────────────────┤ 경계
  │  (사용 불가 영역)        │          │  (사용 불가 영역)        │
  ├──────────────────────────┤          ├──────────────────────────┤
  │  이미지(exe/dll)         │ 높은 주소│  스택 (아래로 성장)      │
  │  ─ 대개 상위 주소        │          │      ↓                   │
  ├──────────────────────────┤          ├──────────────────────────┤
  │  스레드 스택 (여기저기)  │          │  mmap 영역               │
  ├──────────────────────────┤          │  ─ 공유 라이브러리       │
  │                          │          │  ─ 익명 매핑(= CLR 힙)   │
  │  거대한 빈 공간          │          ├──────────────────────────┤
  │  (GB~TB 단위)            │          │      ↑                   │
  │                          │          │  힙 (brk/sbrk, 위로 성장)│
  ├──────────────────────────┤          ├──────────────────────────┤
  │  GC 힙                   │          │  BSS / 데이터 세그먼트   │
  │  CLR 프라이빗 힙들       │          ├──────────────────────────┤
  ├──────────────────────────┤          │  텍스트(코드) 세그먼트   │
  │  기본 프로세스 힙        │          │                          │
  ├──────────────────────────┤          ├──────────────────────────┤
  │  널 포인터 탐지용 미매핑 │          │  널 포인터 탐지용 미매핑 │
  └──────────────────────────┘ 0x0      └──────────────────────────┘ 0x0

  32비트일 때:                          32비트일 때:
   커널 2 GB / 사용자 2 GB               커널 1 GB / 사용자 3 GB
   (LAA 플래그 시 사용자 3 GB)           (CONFIG_PAGE_OFFSET로 변경 가능:
                                          3/1, 2/2, 1/3 GB)
```

> **⚠️ 위 레이아웃 그림은 ASLR 때문에 예시일 뿐이다**
>
> 보안을 위해 **주소 공간 배치 무작위화(ASLR, address space layout randomization)** 가 도입됐다. 모든 구성 요소(바이너리 이미지)가 주소 공간 전체에 무작위로 배치되어, 공격자가 이용할 수 있는 공통 패턴이 반복되지 않게 한다. 그래서 "GC 힙은 항상 이 주소대에 있다" 같은 가정을 코드에 넣으면 안 된다.

### 스레드 스택의 기본 크기

Windows에서 최초 스레드 스택 크기(예약분과 초기 커밋분 모두)는 **실행 파일 헤더**에서 온다. 수동으로 만드는 스레드는 Windows `CreateThread` API로 스택 크기를 지정할 수도 있다.

.NET 런타임이 기본 스택 크기를 계산하는 방식은 꽤 복잡하다. **기본값은 전형적인 32비트 컴파일에서 1 MB, 전형적인 64비트 컴파일에서 4 MB다.** 스택 데이터는 대체로 작고 호출 스택은 보통 얕으므로(수백 단계 중첩 호출은 드물다) 1 또는 4 MB는 좋은 기본값이다.

`StackOverflowException`을 만났다면 바로 이 벽에 부딪힌 것이다. 그리고 그때조차도 대부분은 무한 재귀 같은 프로그래밍 오류다.

> **⚠️ `StackOverflowException`은 잡을 수 없다**
>
> .NET Framework 2.0부터 `StackOverflowException`은 `catch` 블록으로 잡히지 않고 프로세스를 즉시 종료시킨다. 스택이 이미 고갈된 상태에서 예외 처리 코드를 실행할 방법이 없기 때문이다. 재시도나 로깅으로 대응할 수 있는 예외가 아니다. **깊은 재귀를 쓰는 코드는 애초에 깊이를 제한하거나 명시적 스택 자료 구조로 재작성해야 한다.**

### Linux — 페이지 상태와 지연 할당

Linux도 가상 메모리를 쓴다. 프로세스당 한계도 비슷하다.

| 프로세스 종류 | Linux 32비트 | Linux 64비트 |
|---|---|---|
| 32비트 프로세스 | 3/1, 2/2, 1/3 GB | – |
| 64비트 프로세스 | – | 128/128 TB (*) |

(*) 정규(canonical) 48비트 주소 지정

Windows처럼 기본 구성 요소는 페이지이고 크기도 보통 4 kB다. 페이지는 세 상태 중 하나다.

- **자유(free)** — 어떤 프로세스에도 시스템에도 배정되지 않음
- **할당됨(allocated)** — 프로세스에 배정됨
- **공유됨(shared)** — 프로세스를 위해 예약됐지만 다른 프로세스와 공유될 수 있음. 시스템 전역 라이브러리·리소스의 바이너리 이미지와 메모리 매핑 파일이 전형적인 경우

Windows보다 프로세스 메모리 소비를 보는 시각이 단순하고 명확하다. **Windows의 명시적 페이지 예약 단계가 없다.** Linux에는 그것을 대신하는 **지연 할당(lazy allocation)** 메커니즘이 내장돼 있다. Linux에서 메모리를 할당하면 할당된 것으로 취급되지만 **물리 자원은 배정되지 않는다**(그러니 Windows의 예약과 비슷하다). 실제 자원 배정(물리 메모리 소비)은 **그 영역에 실제로 접근할 때까지** 일어나지 않는다. 성능이 중요한 시나리오에서 미리 페이지를 준비하고 싶다면 최소 1바이트라도 읽어 **"터치"** 하면 된다.

### Linux — 메모리 측정 지표

| 지표 | 의미 | `top` 열 | Windows 대응 |
|---|---|---|---|
| **Virtual (vsz)** | 프로세스가 지금까지 예약한 가상 주소 공간 총 크기 | `VIRT` | 가상 바이트 |
| **Resident (RSS)** | 현재 물리 메모리에 상주하는 페이지 공간 | `RES` | 워킹 세트 |
| **Private resident** | 이 프로세스를 위해 예약된 익명 상주 페이지 전부(`MM_ANONPAGES`) | – | 프라이빗 워킹 세트 |
| **Shared resident** | 파일 기반(`MM_FILEPAGES`)과 익명 상주 페이지 | `SHR` | 공유 워킹 세트 |
| **Private** | 프로세스의 모든 프라이빗 페이지. **예약** 지표이며 얼마나 터치되어 상주가 됐는지는 말해주지 않는다 | `DATA` | 프라이빗 바이트 |
| **swapped** | 스왑 파일에 저장된 가상 메모리 부분 | – | 페이지된 바이트 |

Windows와 마찬가지로 "우리 .NET 프로세스가 무엇을 소비하는가"의 답은 간단하지 않다. 가장 합리적인 것은 **프라이빗 상주 페이지**를 보는 것이다. 귀한 RAM 자원의 실제 사용량을 보여주기 때문이다.

> **📌 Linux의 할당 세분성은 페이지 크기다**
>
> Windows의 할당 세분성이 64 kB인 반면, Linux에서는 페이지 크기로만 제한된다 — 대부분 4 kB다.

### Linux — API와 CLR의 대응

| 목적 | Windows | Linux |
|---|---|---|
| 페이지 직접 조작 | `VirtualAlloc` / `VirtualFree` | `mmap` (파일 맵, 공유·일반, 그리고 파일과 무관한 **익명 매핑**) |
| 힙 크기 증가 | Heap API | `brk` / `sbrk` — "프로그램 브레이크"를 설정·증가시켜 힙 크기를 늘린다 |
| 예약 / 커밋 2단계 | `MEM_RESERVE` → `MEM_COMMIT` | **없음.** `PROT_NONE`으로 할당해 "예약"을 흉내 낸다 |
| 수정된 페이지 추적 | `MEM_WRITE_WATCH` + `GetWriteWatch` | **없음.** 쓰기 배리어로 대체 |

잘 알려진 C/C++ 할당자는 할당 크기에 따라 `mmap`이나 `brk`를 쓴다. 이 임계값은 `mallopt`과 `M_MMAP_THRESHOLD` 설정으로 조정할 수 있다. **CLR은 익명 프라이빗 페이지와 함께 `mmap`을 쓴다.**

두 운영체제 간 GC 코드 차이는 대체로 없다. 메모리 관리자가 두 시스템에서 비슷하게 동작하기 때문이다 — 가상 메모리, 페이징, 비슷한 할당 방식. 물론 호출되는 시스템 API는 다르지만 개념적으로는 특별한 차이가 없다. 다만 **두 가지 예외**가 있다.

**첫째, Linux에는 예약/커밋 2단계가 없다.** 시스템 API로 이 방식을 흉내 낼 필요가 있었고, 유명한 트릭이 쓰였다. Linux에서 "예약"은 **접근 모드 `PROT_NONE`으로 메모리를 할당**하는 것으로 이뤄진다 — 사실상 이 메모리에 어떤 접근도 허용하지 않는다는 뜻이다. 그러나 그렇게 예약된 영역 안에서 정상 권한으로 특정 하위 영역을 다시 할당할 수 있고, 이것이 "커밋"을 시뮬레이션한다.

**둘째, 메모리 쓰기 감시(memory write watch) 메커니즘이다.** GC는 어떤 메모리 영역(페이지)이 수정됐는지 추적해야 한다. Windows는 편리한 API를 제공한다 — 페이지를 할당할 때 `MEM_WRITE_WATCH` 플래그를 설정하면 `GetWriteWatch` API로 수정된 페이지 목록을 얻을 수 있다. .NET Core를 구현하면서 **Linux에는 그런 감시 메커니즘을 만들 시스템 콜이 없다**는 것이 드러났다. 그래서 이 로직을 **쓰기 배리어(write barrier)** 로 옮겨야 했고, 그것은 운영체제 지원 없이 런타임 자체가 지원한다. 쓰기 배리어는 64장에서 자세히 다룬다.

> **⚠️ Linux에서 스레드 스택은 연속된 메모리 영역이 아니다**
>
> Windows와의 중요한 차이가 하나 더 있다. **2단계 메모리 예약이 없으므로 Linux의 스택은 필요에 따라 확장될 뿐이다.** 해당 메모리 페이지를 미리 예약하지 않는다. 다음 페이지가 필요할 때 만들어지므로 **스레드 스택은 연속된 메모리 영역이 아니다.** 스택 주소 범위를 하나의 연속 블록으로 가정하는 진단 도구나 네이티브 코드는 Linux에서 오작동할 수 있다.

> **💡 컨테이너 안에서는 다시 이야기가 달라진다**
>
> cgroup으로 메모리 한계를 건 컨테이너에서 .NET을 실행하면 GC는 호스트 전체 RAM이 아니라 **컨테이너 한계**를 기준으로 힙 크기를 정한다(`DOTNET_GCHeapHardLimit`, `DOTNET_GCHeapHardLimitPercent`). 그런데 `top`이나 `/proc/meminfo`는 여전히 호스트 값을 보여줄 수 있다. 컨테이너에서 메모리를 진단할 때는 `/sys/fs/cgroup` 아래 값을 봐야 한다. ※.NET 8

## 61.4 CPU 캐시 계층과 캐시 히트/미스

### 문제 — CPU는 메모리보다 훨씬 빠르다

모든 메모리 관리 뒤에 있는 근본 문제는 **오늘날 CPU와 메모리·저장 서브시스템의 성능 격차**다. 프로세서가 메모리보다 훨씬 빠르므로 메모리 접근은 매번 원치 않는 지연을 만든다. CPU가 메모리 접근(읽기든 쓰기든)을 기다려야 하는 상황을 **스톨(stall)** 이라 한다. 스톨은 CPU 사이클을 일 대신 기다림에 낭비시킨다.

현재 전형적인 프로세서는 3 GHz 이상에서 동작한다. 반면 메모리는 **차원이 다른 200~400 MHz 내부 클록**으로 동작한다. CPU 주파수로 도는 RAM 칩을 만드는 건 너무 비싸다. 현대 RAM의 구조 때문이다 — 내부 커패시터의 충전과 방전에 시간이 걸리고 이를 줄이기가 매우 어렵다.

메모리 모듈이 3200이나 4800 MHz로 광고되는 것을 보면 놀랄 것이다. 그 숫자는 어디서 오나?

### DDR의 숫자 읽는 법

메모리 모듈은 데이터를 저장하는 내부 메모리 셀과, 낮은 내부 클록 한계를 극복하는 추가 버퍼로 구성된다. 대부분의 트릭은 **읽기를 곱하는** 것에 기댄다.

- **단일 클록 사이클 안에서 내부 메모리 셀로부터 두 번 데이터를 보낸다.** 정확히는 신호의 하강 에지와 상승 에지 모두에서. 그래서 여러 세대 메모리 중 가장 유명한 이름이 나왔다 — **DDR(Double Data Rate)**. **더블 펌핑(double pumping)** 이라고도 한다.
- **내부 버퍼링으로 한 메모리 클록 사이클에 여러 번 읽는다("버스트 모드").** DDR2 인터페이스는 외부 클록 주파수를 두 배로, DDR3와 DDR4는 네 배로, DDR5는 거기서 다시 두 배로 만든다.

DDR5의 경우 **모듈 "버스트" 길이는 16**이다 — 더블 펌핑과 8회 동시 읽기를 결합한 결과다.

구체적인 예를 보자. 16 GB 2400 MHz DDR4 칩(스펙상 DDR4-2400, PC4-19200)이다.

| 항목 | 값 | 유래 |
|---|---|---|
| 내부 DRAM 어레이 클록 | 300 MHz | 실제 셀이 도는 속도 |
| 메모리 버스 클록 | 1200 MHz | 내부 I/O 버퍼로 4배 |
| 데이터 전송률 | 2400 MT/s | 클록 사이클당 2회 전송(양쪽 에지) |
| 광고되는 "2400 MHz" | 2400 MT/s를 MHz로 표기한 것 | **마케팅 단순화** |
| PC4-19200 | 19200 MB/s | 2400 MT/s × 8바이트(64비트 워드) |

또 다른 예. Intel Core i7-4770K(Haswell)는 3.5 GHz에서 돈다. **프론트사이드 버스 주파수는 겨우 100 MHz다.** 쓰이는 DDR3-1600(PC3-12800) 메모리는 내부 메모리 클록이 200 MHz이고, DDR3 메커니즘 덕에 I/O 버스 클록은 800 MHz다.

> **⚠️ "3200 MHz 램"은 3200 MHz로 돌지 않는다**
>
> 광고되는 주파수는 **초당 메가 전송(MT/s)** 을 MHz로 표기한 마케팅 단순화다. 실제 내부 셀 클록은 그것의 8분의 1 수준이다. 이 사실이 중요한 이유는, **메모리 대역폭을 늘리는 기술이 지연 시간(latency)을 줄이지는 못한다**는 것을 알려주기 때문이다. DDR5가 DDR4보다 대역폭은 훨씬 크지만 첫 바이트가 도착하는 데 걸리는 시간은 크게 나아지지 않았다. 순차 접근은 대역폭 게임이고, 무작위 접근은 지연 시간 게임이다.

### DRAM 내부 — RAS, CAS, 그리고 타이밍

메모리에는 두 종류가 있고 생산 비용과 성능이 크게 다르다.

| 종류 | 셀 구조 | 새로고침 | 속도 | 용도 |
|---|---|---|---|---|
| **SRAM** (Static RAM) | 셀(1비트)당 트랜지스터 4~6개 | 불필요(전원만 있으면 유지) | 매우 빠름 | **CPU 캐시** |
| **DRAM** (Dynamic RAM) | 트랜지스터 1개 + 커패시터 1개 | **필요**(커패시터 누설 때문) | 느림 | DIMM 슬롯의 주 메모리 |

DRAM 셀 하나는 트랜지스터와 커패시터로 1비트를 저장한다. 이런 셀들이 **DRAM 어레이**로 묶인다. 특정 셀에 접근하는 주소는 **주소 라인(address line)** 으로 전달된다.

어레이의 각 셀마다 자기 주소를 갖게 하는 건 너무 복잡하고 비싸다. 32비트 주소 지정이라면 32비트 폭 주소 라인 디코더가 필요하다. 주소 라인 수는 시스템 전체 비용에 크게 영향을 준다 — 라인이 많을수록 메모리 컨트롤러와 메모리 칩 사이의 핀과 상호 연결이 많아진다. 그래서 **주소 라인은 행(row)과 열(column) 라인으로 재사용되고**, 전체 주소를 주려면 같은 라인에 **두 번** 써야 한다.

특정 셀에서 1비트를 읽는 데는 다섯 단계가 걸린다.

```text
 1. 주소 라인에 행 번호를 올린다
 2. RAS(Row Address Strobe) 신호로 해석을 촉발한다
 3. 주소 라인에 열 번호를 올린다
 4. CAS(Column Address Strobe) 신호로 해석을 촉발한다
 5. 행과 열이 어레이의 특정 셀을 가리킨다.
    셀에서 1비트를 읽어 데이터 라인에 쓴다
```

이 단계 사이의 전환 시간이 메모리 성능을 크게 좌우한다. DIMM 모듈 스펙에 나오는 `9-9-9-24` 같은 숫자가 바로 그것이고, 모두 **클록 사이클 수**다.

| 타이밍 | 이름 | 의미 |
|---|---|---|
| **tCL** | CAS 지연 | CAS와 응답 시작(데이터 수신) 사이의 시간 |
| **tRCD** | RAS to CAS 지연 | RAS와 CAS가 일어날 수 있는 최소 간격 |
| **tRP** | 행 프리차지 | 행에 접근하기 전 프리차지에 걸리는 시간. 준비 없이는 행을 쓸 수 없다 |
| **tRAS** | 행 활성 지연 | 행 안의 정보에 접근하기 위해 행이 활성 상태여야 하는 최소 시간 |

이 시간의 의미를 잘 보자. **관심 있는 행과 열이 이미 설정돼 있다면 읽기는 거의 즉시다.** 열을 바꾸려면 tCL 사이클이 걸린다. **행을 바꾸려면 상황이 훨씬 나쁘다** — 먼저 프리차지해야 하고(tRP), 이어 RAS와 CAS 지연(tRCD, tCL)이 붙는다.

**이것이 순차 접근 패턴이 비순차 접근보다 훨씬 빠른 여러 이유 중 하나다.** 한 행에서 버스트로 읽는 것(가끔 열만 바꾸며)이 행을 자주 바꾸는 것보다 훨씬 빠르다. 접근 패턴이 완전히 무작위라면 **매번의 메모리 접근마다 행 변경 타이밍에 얻어맞는다.**

### 캐시 — 히트와 미스

CPU와 RAM의 성능 격차를 완화하기 위해, 가장 많이 쓰고 가장 필요한 데이터의 사본을 저장하는 중간 구성 요소가 쓰인다 — **CPU 캐시**다.

이 캐시는 **ISA 관점에서 투명하다.** 프로그래머도 운영체제도 그 존재를 알 필요가 없다. 관리할 필요도 없다. 이상적인 세계라면 캐시의 적절한 사용과 관리는 전적으로 CPU 책임이다.

캐시는 가능한 한 빨라야 하므로 앞서 말한 SRAM 칩을 쓴다. 비용과 크기(프로세서 안의 귀한 공간을 차지한다) 때문에 주 RAM만큼 커질 수 없다.

착상은 사소하다. 프로세서가 실행하는 명령이 메모리에 접근해야 할 때(쓰기든 읽기든), 먼저 캐시를 봐서 필요한 데이터가 이미 있는지 확인한다. 있다면 훌륭하다 — 아주 빠른 메모리 접근을 얻었고, 이런 상황을 **캐시 히트(cache hit)** 라 한다. 데이터가 캐시에 없으면(**캐시 미스, cache miss**) 먼저 RAM에서 읽어 캐시에 저장해야 하고, 당연히 훨씬 느린 연산이다. **캐시 히트율과 캐시 미스율**은 우리 코드가 캐시를 효율적으로 쓰는지 알려주는 매우 중요한 지표다.

> **📌 캐시 쓰기 전략**
>
> 메모리에 데이터를 **쓸** 때의 첫 단계는 읽을 때와 정확히 같다 — 캐시 라인이 없으면 캐시에 채워진다. 그다음 캐시된 데이터가 수정되고, 두 전략 중 하나가 적용된다.
>
> - **라이트 스루(write-through)** — 캐시 라인에 쓴 뒤 수정된 데이터를 즉시 주 메모리에 저장한다. 구현이 단순하지만 메모리 버스에 큰 오버헤드를 만든다.
> - **라이트 백(write-back)** — 캐시 라인에 쓴 뒤 **더티(dirty)** 로 표시한다. 다른 데이터를 위한 캐시 공간이 없을 때 이 더티 블록이 메모리에 기록된다(그리고 더티 항목은 삭제된다). 프로세서는 적절하다고 판단할 때(예: 유휴 시간) 이 블록들을 기록할 수도 있다.
>
> **라이트 컴바이닝(write-combining)** 이라는 최적화도 있다. 특정 메모리 영역의 주어진 캐시 라인이 개별 워드가 아니라 **통째로** 기록되도록 보장해, 역시 빠른 순차 접근의 이점을 취한다.

### 계층 캐시

성능 요구와 비용 최적화 사이에서 CPU 설계는 오늘날 더 복잡한 **계층 캐시**로 진화했다. 착상은 단순하다. 캐시를 하나 두는 대신 크기와 속도가 다른 것을 여러 개 만든다. 아주 작고 아주 빠른 1차 캐시(L1), 조금 더 크고 조금 더 느린 2차 캐시(L2), 마지막으로 3차 캐시(L3). **현대 아키텍처에서 이 열거는 세 단계에서 끝난다.**

```text
                    ┌───────────────────────────────┐
                    │           CPU 코어            │
                    │   ┌──────────────────────┐    │
                    │   │  레지스터            │    │  ← 1 사이클, 지연 없음
                    │   └──────────────────────┘    │
                    │        ↑          ↑           │
                    │   ┌────────┐ ┌────────┐       │
                    │   │  L1i   │ │  L1d   │       │  ← 명령 / 데이터 분리
                    │   │ 32 KiB │ │ 32 KiB │       │     (Modified Harvard)
                    │   └────────┘ └────────┘       │
                    │        ↑          ↑           │
                    │   ┌──────────────────────┐    │
                    │   │        L2  256 KiB   │    │
                    │   └──────────────────────┘    │
                    │             ↑                 │
                    │   ┌──────────────────────┐    │
                    │   │        L3   8 MiB    │    │
                    │   └──────────────────────┘    │
                    └─────────────┬─────────────────┘
                                  ↓  메모리 버스
                    ┌───────────────────────────────┐
                    │         DRAM (주 메모리)      │
                    └───────────────────────────────┘

  크기 수치는 Intel Core i7-4770K 기준
```

**1차 캐시는 두 블록으로 나뉜다.** 하나는 데이터용(L1d), 다른 하나는 명령용(L1i)이다. 메모리에서 읽혀 프로세서가 실행하는 명령도 사실 데이터이지만 적절히 해석될 뿐이다. **L1보다 높은 계층에서는 데이터와 코드 명령을 동일하게 취급한다.** 그러나 가장 낮은 캐시 계층에서는 둘을 따로 다루는 것이 낫다는 것이 실무로 드러났다. 이것이 **하버드 아키텍처**의 접근이고, 그래서 오늘날 컴퓨터 아키텍처를 **수정 하버드 아키텍처(Modified Harvard Architecture)** 라 부른다. 이 방식이 잘 통하는 이유는 데이터 저장 영역과 프로그램 코드 영역의 사용이 강하게 독립적이기 때문이지만, **가장 낮은 계층에서만** 그렇다.

> **📌 L4 캐시는 다른 것이다**
>
> L4 캐시를 갖춘 프로세서를 가끔 볼 수 있지만, 조금 다른 종류의 메모리이며 주로 그 CPU 안의 통합 그래픽 카드를 위해 설계된 것이다.

### 지연 시간 — 실측 수치

숫자가 없으면 감이 안 온다. 다음 표는 Intel Core i7-4712MQ(Haswell) 2.30 GHz 노트북에서 측정한 값이다. **CPU 사이클 하나가 대략 0.4 ns**(≈ 1/2.30 GHz)라고 가정하고 Haswell i7 스펙을 쓴 결과다.

| 접근 대상 | 지연 시간 | 대략적 사이클 수(2.30 GHz 기준) | 주 메모리 대비 |
|---|---|---|---|
| **레지스터** | 지연 없음 | 1 사이클 안 | — |
| **L1 캐시** | < 2.0 ns | 대략 5 사이클 미만 | 30배 이상 빠름 |
| **L2 캐시** | 4.8 ns | 대략 12 사이클 | 약 15배 빠름 |
| **L3 캐시** | 14.4 ns | 대략 36 사이클 | 약 5배 빠름 |
| **주 메모리(DRAM)** | 71.4 ns | 대략 178 사이클 | 1배(기준) |
| **HDD** | 150,000 ns | 대략 375,000 사이클 | 약 2,100배 느림 |

사이클 수 열은 0.4 ns를 한 사이클로 놓고 계산한 **대략적** 환산이다. 정확한 값은 마이크로아키텍처와 접근 유형에 따라 다르다.

이 표에서 읽어야 할 것은 두 가지다.

- **필요한 데이터가 RAM이 아니라 L3에 있으면 지연이 약 5배 낫다. L1에 있으면 30배 이상 낫다.** 캐시 사용 최적화를 위해 싸울 가치가 충분하다.
- **HDD는 주 메모리보다 세 자릿수 느리다.** 스와핑이 벌어지면 성능 논의는 무의미해진다.

캐시에 얼마나 들어가나? 구체적 CPU 모델에 달렸지만 i7-4770K 스펙이 시장 표준을 꽤 잘 반영한다.

| 계층 | i7-4770K 용량 |
|---|---|
| L1 | **64 KiB** (코드 32 KiB + 데이터 32 KiB) |
| L2 | **256 KiB** |
| L3 | **8 MiB** |

### 데이터 크기가 커지면 무슨 일이 일어나는가

이 숫자들이 관리 코드 세계에 무슨 영향을 주는지 직접 보자. 다음 코드는 순차 읽기(최적의 경우)를 반복한다. 쓰인 구조체 크기가 **정확히 64바이트**라서 읽기는 64바이트씩 건너뛰고 **매번 새 캐시 라인이 로드된다.**

```csharp
public struct OneLineStruct
{
    public long data1;
    public long data2;
    public long data3;
    public long data4;
    public long data5;
    public long data6;
    public long data7;
    public long data8;
}

public static long OneLineStructSequentialReadPattern(OneLineStruct[] tab)
{
    long sum = 0;
    int n = tab.Length;
    for (int i = 0; i < n; ++i)
    {
        unchecked { sum += tab[i].data1; }
    }
    return sum;
}
```

배열이 차지하는 총 메모리 크기를 늘려가며 원소 하나당 평균 접근 시간을 재면, **각 캐시 계층 크기를 넘어서는 지점마다 접근 시간이 뚜렷이 악화된다.** Intel i7-4770K에서 벤치마크했을 때 성능 저하가 확연히 보이는 지점은 **약 256 KiB와 약 8192 KiB(8 MiB)** 였고, 이것은 정확히 **L2와 L3 캐시 크기**에 해당한다.

```text
  원소당 평균 접근 시간 (개념도, 두 축 모두 로그 스케일)

   느림 ↑
        │                                        ┌──────────
        │                                        │
        │                       ┌────────────────┘
        │                       │      ← 8 MiB (L3 한계)
        │      ┌────────────────┘
        │      │   ← 256 KiB (L2 한계)
   빠름 └──────┴──────────────────────────────────────────→
         작음                 배열 총 크기                  큼
```

**작은 데이터 크기에서 동작하는 것이 L3에 들어가지 않는 데이터에서 동작하는 것보다 몇 배 빠를 수 있다.**

> **💡 "작업 집합을 캐시에 넣어라"가 실무 지침이다**
>
> 이 그래프의 실무적 함의는 단순하다. **한 번에 다루는 데이터 덩어리를 L2/L3 크기 아래로 쪼개라.** 큰 배열을 통째로 여러 번 순회하는 대신, 캐시에 들어가는 블록 단위로 나눠서 각 블록에 대한 모든 처리를 끝내고 다음 블록으로 가는 방식(블로킹, 타일링)이 같은 알고리즘 복잡도에서 몇 배 빨라지는 이유가 여기 있다.

### 멀티코어 계층 캐시와 캐시 일관성

여정은 아직 끝나지 않았다. 현대 CPU 대부분은 코어가 여러 개다. 단순화해 말하면 코어는 개별적이고 단순화된 프로세서다 — 다른 코어와 독립적으로 코드를 실행할 수 있다. 과거에는 각 코어가 한 번에 정확히 하나의 스레드를 실행했다. 요즘은 사실상 모든 프로세서가 **동시 멀티스레딩(SMT)** 을 갖춰 코어 하나에서 두 스레드를 동시에 실행한다. Intel에서는 **하이퍼스레딩**이라 부르고, AMD는 Zen 마이크로아키텍처에서 완전한 SMT 지원을 넣었다.

```text
 ┌──────────────────────────────────────────────────────────────────┐
 │                             CPU                                  │
 │                                                                  │
 │  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐          │
 │  │ 코어 0   │  │ 코어 1   │  │ 코어 2   │  │ 코어 3   │          │
 │  │ ┌──┬───┐ │  │ ┌──┬───┐ │  │ ┌──┬───┐ │  │ ┌──┬───┐ │          │
 │  │ │L1│L1 │ │  │ │L1│L1 │ │  │ │L1│L1 │ │  │ │L1│L1 │ │  코어    │
 │  │ │i │ d │ │  │ │i │ d │ │  │ │i │ d │ │  │ │i │ d │ │  전용     │
 │  │ └──┴───┘ │  │ └──┴───┘ │  │ └──┴───┘ │  │ └──┴───┘ │          │
 │  │ ┌──────┐ │  │ ┌──────┐ │  │ ┌──────┐ │  │ ┌──────┐ │          │
 │  │ │  L2  │ │  │ │  L2  │ │  │ │  L2  │ │  │ │  L2  │ │          │
 │  │ └──────┘ │  │ └──────┘ │  │ └──────┘ │  │ └──────┘ │          │
 │  └────┬─────┘  └────┬─────┘  └────┬─────┘  └────┬─────┘          │
 │       └─────────────┴──────┬──────┴─────────────┘                │
 │                    ┌───────┴────────┐                            │
 │                    │   L3 (공유)    │  ←── 모든 코어가 공유       │
 │                    └───────┬────────┘                            │
 └────────────────────────────┼─────────────────────────────────────┘
                              ↓  메모리 버스
                    ┌──────────────────┐
                    │  DRAM (주 메모리)│
                    └──────────────────┘

  SMT(하이퍼스레딩)일 때: 같은 코어의 두 스레드는 L1과 L2를 나눠 쓴다.
  둘이 같은 데이터를 쓰지 않는 한 실제 가용량은 절반이 된다.
```

각 코어가 자기 1·2차 캐시를 갖고, 3차 캐시만 공유된다. 코어와 L3를 어떻게 연결하는지는 구현 세부사항이다. 예를 들어 대부분의 현대 Intel CPU에는 **양방향의 극도로 빠른 32바이트 폭 버스**가 있어 통합 GPU 및 시스템 에이전트와도 연결한다.

각 스레드가 별개의 프로세서/코어에서 돌 수 있으므로 **캐시된 데이터의 일관성 문제**가 생긴다. 이 때문에 **캐시 일관성(cache coherency)** 이라는 복잡한 개념이 필요하다. 저장된 데이터의 일관성이 어떻게 유지되는지를 기술하며, **캐시 일관성 프로토콜**로 적용된다 — 코어 간 데이터 변경을 알리는 방식이다. 지역 캐시의 데이터가 수정될 때마다(더티나 수정 플래그로 관리된다) 그 정보를 다른 코어에 방송해야 한다.

효율적 동작을 위해 설계된 여러 확장·고급 프로토콜이 있고, 특히 **MESI 프로토콜**이 유명하다. 이름은 캐시 라인이 가질 수 있는 네 상태에서 왔다 — **Modified, Exclusive, Shared, Invalid.**

그럼에도 **캐시 일관성 프로토콜은 메모리 트래픽에, 따라서 전체 프로그램 성능에 큰 오버헤드를 지울 수 있다.** 코어 간 캐시를 계속 상호 갱신해야 하는 필요는 눈에 띄는 오버헤드를 낳는다. **우리가 쓰는 코드는 서로 다른 코어가 같은 캐시 라인 아래의 메모리 주소에 접근하는 것을 최소화해야 한다.**

> **⚠️ 이것이 거짓 공유(false sharing)의 하드웨어적 정체다**
>
> 논리적으로는 서로 다른 데이터를 만지는 스레드들이 물리적으로 **같은 64바이트 캐시 라인** 안에 있으면, 각 코어는 매 수정마다 다른 코어의 사본을 무효화한다. 코드에는 공유가 없는데 하드웨어에는 공유가 있는 것이다. 원천 벤치마크에서 이 하나의 차이로 **실행 시간이 5.0초에서 0.7초로, 약 7배** 좋아졌다. C#에서의 대응 방법(`StructLayout` 패딩, 배열 오프셋 조정, `PaddedReference` 패턴)은 50.12절에서 이미 다뤘다. 여기서 기억할 것은 **원인이 코드가 아니라 캐시 라인 경계**라는 사실이다.

> **📌 캐시 축출 전략**
>
> 어떤 계층에 공간이 없을 때 새 데이터 자리를 어떻게 만드느냐에도 두 가지 접근이 있다.
>
> - **배타적(exclusive) 캐시** — 데이터는 캐시의 한 계층에만 있다. AMD 프로세서에서 흔하다.
> - **포함적(inclusive) 캐시** — 낮은 계층(예: L1d)의 각 캐시 라인이 높은 계층(예: L2)에도 존재한다.
>
> 흥미롭지만 메모리 관리 이해에 영향을 주지는 않는다. CPU 제조사가 최선을 다하고 있다고 가정하면 된다.

> **📌 명령 캐시(L1i)는 왜 덜 이야기하나**
>
> 이유는 몇 가지다. 첫째, 컴파일러가 코드를 적절히 준비하는 일을 잘 하고 CPU도 코드 접근 패턴을 잘 추측한다. 결과적으로 컴파일러와 프로그램 실행의 본성이 CPU가 활용할 만한 좋은 시간적·공간적 지역성을 만들어낸다. 둘째, 명령 캐시 관리는 데이터 관리에 초점을 둔 .NET 메모리 관리의 영역이 아니다. 유일한 명백한 개선은 가능한 한 작은 코드를 생성하는 것인데, 오늘날 이것은 실천하기 어렵다 — 전부 컴파일러 최적화가 하고 코드 크기는 오히려 비즈니스 요구가 결정한다. 다만 .NET에서도 **가상 호출을 많이 만들지 않고 같은 메서드를 큰 데이터 집합에 반복 호출하는 쪽을 선호**하는 식으로 L1i 미스를 염두에 둘 수는 있다.

## 61.5 데이터 지역성(공간적/시간적)과 정렬

### 두 가지 지역성

애초에 캐시가 왜 도움이 되나? 캐싱은 **데이터 지역성(data locality)** 이라는 아주 중요한 개념에 기댄다. 두 종류가 있다.

- **시간적 지역성(temporal locality)** — 어떤 메모리 영역에 접근했다면, 가까운 미래에 **그것에 다시** 접근할 가능성이 높다. 이것이 캐시를 완벽히 정당화한다 — 메모리에서 데이터를 읽었고, 아마 나중에 몇 번 더 재사용할 것이다. 일반적으로 우리는 어떤 자료 구조를 변수에 싣고 그 변수를 반복해서 쓴다(카운터, 파일에서 읽은 임시 데이터 등).
- **공간적 지역성(spatial locality)** — 어떤 메모리 영역에 접근했다면, **가까운 이웃**의 데이터에 접근할 가능성이 높다. 지금 필요한 것보다 주변 데이터를 조금 더 캐시해두면 이 지역성이 우리 편이 된다. 몇 바이트가 필요하다면 열 몇 바이트를 더 읽어 캐시해두자는 것이다. 아주 고립된 메모리 영역을 쓰는 일은 드물다. 스택과 힙은 스레드가 일하면서 **비슷한 영역에 접근하도록** 조직되어 있다. 지역 변수나 자료 구조의 필드도 대체로 가까이 놓인다.

> **⚠️ 캐시는 양날의 검이다**
>
> 위 조건이 실제로 성립할 때만 캐시가 이롭다. **데이터 지역성을 깨는 방식으로 프로그램을 쓰면 캐시는 불필요한 짐이 된다.** 필요한 1바이트를 위해 64바이트를 읽고, 그 63바이트를 버리고, 다시 다른 곳에서 64바이트를 읽는다. 이 경우 캐시가 없는 편이 나았을 수도 있다.

### 캐시 라인 — 64바이트라는 단위

가장 중요하고 가장 영향력이 큰 사실은, **RAM과 캐시 사이의 데이터가 캐시 라인(cache line)이라는 블록 단위로 전송된다**는 것이다. 캐시 라인은 고정 크기이고, **오늘날 압도적 다수의 컴퓨터에서 64바이트**다.

반드시 기억해야 한다 — **캐시 라인 크기보다 적은 데이터를 메모리에서 읽거나 쓸 수 없다.** 메모리에서 단 1비트를 읽고 싶어도 **64바이트 캐시 라인 전체가 채워진다.** 이 설계는 DRAM의 빠른 순차 접근을 활용한 것이다(앞에서 본 프리차지와 RAS 지연을 떠올려라).

DRAM 접근은 64비트(8바이트) 폭이므로, 캐시 라인 하나를 채우려면 **RAM에서 8회 전송**이 필요하다. 이는 많은 CPU 사이클을 요구하므로 이를 감안한 여러 기법이 있다. 그중 하나가 **Critical Word First and Early Restart**다. 캐시 라인을 워드 단위로 순서대로 읽지 않고 **가장 필요한 워드부터** 읽기 시작한다. 최악의 경우 그 8바이트 워드가 캐시 라인 끝에 있어서 앞의 일곱 번 전송을 모두 기다려야 할 수도 있음을 상상해보라. 이 기법은 가장 중요한 워드를 먼저 읽는다. 그 데이터를 기다리던 명령은 실행을 계속하고, 캐시 라인의 나머지는 비동기적으로 채워진다.

### 실측 — 행 우선 vs 열 우선

관리 코드의 안락한 세계에서 이런 하드웨어 구현 세부가 정말 중요한가? 확인해보자. 같은 2차원 배열에 두 방식으로 접근한다.

```csharp
// 방식 A — 행 우선 (순차)
int[,] tab = new int[n, m];
for (int i = 0; i < n; ++i)
{
    for (int j = 0; j < m; ++j)
    {
        tab[i, j] = 1;
    }
}
```

```csharp
// 방식 B — 열 우선 (비순차)
int[,] tab = new int[n, m];
for (int i = 0; i < n; ++i)
{
    for (int j = 0; j < m; ++j)
    {
        tab[j, i] = 1;   // 인덱스 순서만 바뀌었다
    }
}
```

바뀐 것은 `tab[i, j]`가 `tab[j, i]`가 된 것뿐이다. 결과는 이렇다(`n = m = 5000`, 즉 2500만 개의 `int`).

| 접근 패턴 | PC (i7-4770K 3.5 GHz) | 노트북 (i7-4712MQ 2.3 GHz) | Raspberry Pi 2 (ARM Cortex-A7 0.9 GHz) |
|---|---|---|---|
| **행 우선** | **52 ms** | **127 ms** | **918 ms** |
| **열 우선** | 401 ms | 413 ms | 2001 ms |
| 배율 | **7.7배** | 3.3배 | 2.2배 |

**같은 알고리즘, 같은 원소 개수, 같은 명령 개수인데 최대 7.7배 차이가 난다.**

왜 그런지 그림으로 보자. 값 1~40을 담은 작은 배열이고, **캐시 라인 하나에 값 네 개가 들어가고 CPU 캐시가 라인 네 개만 담을 수 있다**고 가정한다(실제 CPU는 수백~수천 개를 담는다).

```text
   배열의 메모리 배치 (행 우선으로 저장됨)
   ┌────┬────┬────┬────┐  ← 캐시 라인 1
   │  1 │  2 │  3 │  4 │
   ├────┼────┼────┼────┤  ← 캐시 라인 2
   │  9 │ 10 │ 11 │ 12 │
   ├────┼────┼────┼────┤  ← 캐시 라인 3
   │ 17 │ 18 │ 19 │ 20 │
   ├────┼────┼────┼────┤  ← 캐시 라인 4
   │ 25 │ 26 │ 27 │ 28 │
   ├────┼────┼────┼────┤  ← 캐시 라인 5
   │ 33 │ 34 │ 35 │ 36 │
   └────┴────┴────┴────┘

  [행 우선 접근]  1→2→3→4→9→10→...    [열 우선 접근]  1→9→17→25→33→2→...

   캐시 라인 1 로드 → 1,2,3,4 전부 사용   캐시 라인 1 로드 → 1만 사용
   캐시 라인 2 로드 → 9,10,11,12 전부 사용 캐시 라인 2 로드 → 9만 사용
   캐시 라인 3 로드 → 전부 사용            캐시 라인 3 로드 → 17만 사용
   ...                                     캐시 라인 4 로드 → 25만 사용
                                           캐시 라인 5 로드 → 버퍼가 꽉 참!
   ▶ 캐시 라인 활용률 100%                     가장 덜 쓴 라인 1(1,2,3,4)을 축출
   ▶ 로드 횟수 = 원소 수 / 4                다음에 2를 읽어야 하는데 라인 1이
                                           방금 축출됨 → 다시 로드
                                       ▶ 캐시 라인 활용률 25%
                                       ▶ 같은 라인을 네 번씩 다시 읽는다
```

.NET 런타임 환경 전체와 그 정교한 메모리 관리 기법도 **우리를 때리는 이 CPU 구현 세부를 숨기지 못한다.** 불리한 메모리 접근 패턴은 코드 성능을 몇 배 나쁘게 만든다. Java와 C/C++로 같은 테스트를 해도 비슷하게 불리한 결과가 나온다.

> **📌 Rule 2 — 무작위 접근을 피하고 순차 접근을 권장하라**
>
> **적용 범위**: 주로 저수준, 성능 지향 코드.
>
> **근거**: RAM과 프로세서 캐시 설계를 포함한 여러 계층의 내부 메커니즘 때문에 순차 접근이 확실히 더 효율적이다. DRAM의 먼 메모리에 도달하는 데는 캐시보다 훨씬 많은 CPU 사이클이 든다. 프로세서는 데이터를 64바이트 캐시 라인 블록으로 싣는다. **64바이트보다 작은 모든 메모리 접근은 비싼 자원의 낭비다.** 게다가 무작위 접근 패턴은 캐시 프리페칭 메커니즘이 동작할 가능성을 없앤다. 프로세서가 예측 가능한 패턴을 발견할 기회가 없기 때문이다. 여기서 "무작위"란 완전한 무작위가 아니라 **탐지 가능한 패턴과 맞지 않는 모든 접근**을 뜻한다.
>
> **적용 방법**: 무작위 접근의 반대는 순차 접근이므로, 항상 순차 접근을 쓰려고 노력하라. 대량의 데이터를 다룬다면 **배열로 묶어 메모리 연속성을 보장**하는 것을 고려하라. **이중 연결 리스트 순회가 전형적인 비구조적 접근의 예다.**

> **📌 Rule 3 — 공간적·시간적 데이터 지역성을 개선하라**
>
> **적용 범위**: 주로 저수준, 성능 지향 코드.
>
> **근거**: 공간적·시간적 지역성은 좋은 캐시의 두 기둥이다. 지켜지면 캐시가 효과적으로 쓰이고 더 나은 성능에 기여한다. 반대로 지역성을 해치면 심각한 성능 손실로 이어진다.
>
> **적용 방법**: 데이터의 지역성을 챙기고 시간적 재사용성을 최대화하도록 자료 구조를 설계하라. 분산되고 무작위한 데이터 접근은 몇 배 느릴 수 있다. 아주 고급의 고성능 코드에서는 때때로 **직관에 반하는 변경**이 필요한데, 이것이 70장에서 다룰 데이터 지향 설계다. 더 일반적으로는 **자료 구조를 적당히 작게, 미리 할당하고, 반복적으로 재사용하도록** 만드는 일로 귀결된다.

### 데이터 정렬

메모리 접근에 관해 서술해야 할 또 하나의 아주 중요한 측면이 있다. 대부분의 CPU 아키텍처는 **적절히 정렬된(aligned) 데이터**에 접근하도록 설계됐다. 그 데이터의 시작 주소가 바이트로 지정된 어떤 정렬 값의 배수라는 뜻이다. 타입마다 자기 정렬이 있고, 자료 구조의 정렬은 그 필드들의 정렬에 달렸다. **정렬되지 않은 데이터 접근은 몇 배 느릴 수 있으므로** 많은 주의가 필요하다.

캐시 라인 때문에 메모리에 저장된 데이터는 **64바이트 경계에 정렬된다.** 그러므로 **연속된 2바이트를 읽는 최악의 경우 총 128바이트에 해당하는 캐시 라인 두 개를 소비해야 한다.**

```text
        캐시 라인 N                      캐시 라인 N+1
 ┌──────────────────────────┐   ┌──────────────────────────┐
 │ ...                   [b0]│  │[b1] ...                  │
 └──────────────────────────┘   └──────────────────────────┘
                          ↑ ↑
                       주소 A에서 시작하는 2바이트를 읽으려는데
                       하필 캐시 라인 경계를 한 바이트 걸쳤다
                       → 64바이트가 아니라 128바이트를 읽어야 한다
```

### 실측 — 캐시 라인 경계 하나가 만드는 7배

캐시 라인 경계에 데이터를 어떻게 놓느냐가 만드는 차이를 숫자로 보자. 다음 코드는 스레드 `threadsCount`개가 같은 `sharedData` 배열의 **서로 다른 원소**를 증가시킨다. 이론적으로는 스레드끼리 아무 영향이 없어야 한다. 두 매개변수가 원소의 배치를 결정한다 — 시작 간격(`gap`)과 원소 간 거리(`offset`)다.

```csharp
const int offset = 1;
const int gap = 0;
public static int[] sharedData = new int[4 * offset + gap * offset];

public static long DoFalseSharingTest(int threadsCount, int size = 100_000_000)
{
    Thread[] workers = new Thread[threadsCount];
    for (int i = 0; i < threadsCount; ++i)
    {
        workers[i] = new Thread(new ParameterizedThreadStart(idx =>
        {
            int index = (int)idx + gap;
            for (int j = 0; j < size; ++j)
            {
                sharedData[index * offset] = sharedData[index * offset] + 1;
            }
        }));
    }
    for (int i = 0; i < threadsCount; ++i)
        workers[i].Start(i);
    for (int i = 0; i < threadsCount; ++i)
        workers[i].Join();
    return 0;
}
```

`threadsCount = 4`로 4코어 머신에서 돌리면 각 스레드가 자기 물리 코어에서 돌 가능성이 높다.

| 버전 | 배치 | PC | 노트북 | Raspberry Pi 2 |
|---|---|---|---|---|
| **#1** (offset=1, gap=0) | 네 스레드가 **같은 캐시 라인**을 수정 | 5.0 s | 6.7 s | 29.0 s |
| **#2** (offset=16, gap=0) | 각자 자기 캐시 라인을 수정하되 **배열 헤더 라인을 공유** | 2.4 s | 2.6 s | 13.8 s |
| **#3** (offset=16, gap=16) | 각자 자기 캐시 라인 + 헤더 라인은 **읽기 전용** 공유 | **0.7 s** | **0.8 s** | 12.1 s |

```text
 #1  offset=1, gap=0                     64B (캐시 라인 하나)
     ┌───────────────────────────────────────────────────────┐
     │ 4B  │ 4B  │ 4B  │ 4B  │ ......                        │
     │Core1│Core2│Core3│Core4│                               │
     └───────────────────────────────────────────────────────┘
     네 코어가 같은 라인을 수정 → 매 증가마다 서로 무효화

 #2  offset=16, gap=0
     ┌──────────────┐┌──────────────┐┌──────────────┐┌──────────────┐
     │H MT len  4B  ││    4B        ││    4B        ││    4B        │
     │          C1  ││    C2        ││    C3        ││    C4        │
     └──────────────┘└──────────────┘└──────────────┘└──────────────┘
     각자 자기 라인. 그런데 첫 라인에 배열 헤더(H, 메서드 테이블 MT, 길이 len)가
     같이 있고, 인덱서는 매번 범위 검사를 위해 길이를 읽는다.
     → Core1이 첫 라인을 계속 수정하므로 다른 코어의 사본이 계속 무효화된다

 #3  offset=16, gap=16
     ┌──────────────┐┌──────────────┐┌──────────────┐┌──────────────┐
     │H MT len      ││    4B        ││    4B        ││    4B        │ ...
     │(읽기 전용)   ││    C1        ││    C2        ││    C3        │
     └──────────────┘└──────────────┘└──────────────┘└──────────────┘
     헤더 라인은 아무도 쓰지 않으므로 각 코어가 읽기 전용 사본을 유지한다.
     캐시 일관성 오버헤드가 사라진다 → 7배 빠르다
```

여기서 눈여겨볼 것은 **#2에서 #3으로의 개선**이다. 각 스레드가 이미 자기 캐시 라인을 갖고 있는데도 여전히 느렸다. 이유는 .NET의 객체 레이아웃에 있다 — **배열은 객체 시작부에 헤더와 길이를 저장하고, 인덱서로 원소에 접근할 때마다 범위 검사를 위해 그 길이를 읽는다.** 그래서 첫 코어가 헤더가 있는 캐시 라인을 계속 수정하면서 다른 코어의 사본을 무효화하고 있었다. 원소를 캐시 라인 하나만큼 더 밀어야(`gap = 16`) 비로소 이 공유가 사라진다.

**같은 C# 코드, 같은 스레드 수, 같은 총 연산 횟수인데 배열 인덱스 배치만 바꿔 PC에서 5.0초가 0.7초가 됐다.** 객체 레이아웃 상세는 54장에서 다뤘고, C#에서의 실전 대응은 50.12절에 있다.

CLR 자료 구조의 레이아웃은 대체로 런타임 자신이 관리한다. **가비지 컬렉터 코드에 정렬을 제대로 다루는 코드가 잔뜩 있는 이유가 여기 있다.** 객체 메모리 레이아웃이 어떻게 생겼고 어떻게 제어할 수 있는지는 54장에서 이미 봤다.

### 정렬을 직접 다뤄야 할 때

.NET Core 3.0부터 **하드웨어 내장 함수(hardware intrinsics)** 가 도입됐다. 더 범용적인 메커니즘으로 노출하기 어려운 하드웨어별 CPU 명령에 접근하게 해준다. 그때부터 `LoadAlignedVector256`이나 `StoreAligned` 같은 메서드 덕에 **정렬된 메모리 로드/스토어**를 쓸 수 있다. 이것들은 아주 저수준에서, 주로 포인터를 통해 비관리 네이티브 메모리를 다룰 때만 유용하다. 특히 **벡터화(vectorization)** — 반복마다 값 하나가 아니라 값의 집합(벡터)을 처리하도록 알고리즘을 바꾸는 것 — 에서 유용하다. 특별한 CPU **SIMD(Single Instruction, Multiple Data)** 명령을 쓴다.

정렬된 네이티브 메모리가 필요하면 `NativeMemory.AlignedAlloc`이 있다. ※.NET 6

```csharp
using System.Runtime.InteropServices;

unsafe
{
    // 64바이트(캐시 라인) 경계에 정렬된 4096바이트 블록
    void* p = NativeMemory.AlignedAlloc(byteCount: 4096, alignment: 64);
    try
    {
        var span = new Span<byte>(p, 4096);
        span.Clear();
        // ... 사용 ...
    }
    finally
    {
        NativeMemory.AlignedFree(p);   // 반드시 AlignedFree로 해제한다
    }
}
```

> **⚠️ `AlignedAlloc`은 `NativeMemory.Free`로 해제하면 안 된다**
>
> `NativeMemory.AlignedAlloc`으로 얻은 포인터는 반드시 `NativeMemory.AlignedFree`로 해제해야 한다. 플랫폼에 따라 정렬 할당은 내부적으로 실제 블록 시작보다 앞선 주소를 반환하므로, 일반 `Free`에 넘기면 정의되지 않은 동작이다. 반대로 `NativeMemory.Alloc`으로 얻은 포인터를 `AlignedFree`에 넘기는 것도 마찬가지다.

> **💡 관리 배열의 정렬은 보장되지 않는다**
>
> `new float[N]`으로 만든 관리 배열의 데이터 시작 주소가 32바이트나 64바이트 경계에 정렬되어 있으리라는 보장은 없다. GC가 객체를 옮기면 주소도 바뀐다. 정렬이 필요한 SIMD 코드에서 관리 배열을 쓰려면 (1) `fixed`로 고정한 뒤 배열 안의 첫 정렬 주소를 찾아 거기서부터 처리하고 앞부분은 스칼라로 처리하거나, (2) 아예 `NativeMemory.AlignedAlloc`으로 네이티브 메모리를 쓰는 두 가지 방법뿐이다.

> **📌 GC 알고리즘 자체가 캐시를 잘못 쓰면 어떻게 되나**
>
> 가비지 컬렉션 알고리즘을 설계할 때, 아주 작은 1바이트짜리 진단 데이터를 메모리 전체에 무작위로 흩뿌려 놓았다고 하자. 이 정보를 모으는 연산은 캐싱 관점에서 극도로 비싸다. **1바이트를 읽자고 캐시 라인 하나를 통째로 채워야 하기 때문이다.** 메모리를 집중적으로 다루는 알고리즘(그리고 가비지 컬렉션은 본질적으로 메모리를 다룬다)은 이 CPU 내부 사정을 반드시 고려해야 한다. **메모리는 아무 대가 없이 여기저기서 바이트를 집어올 수 있는 평평한 공간이 아니다.** 64장에서 볼 GC의 자료 구조 설계가 왜 그렇게 생겼는지 이해하는 열쇠다.

## 61.6 프리페칭과 비일시적(non-temporal) 접근

### 프리페칭 — 미리 끌어오기

캐시 활용을 개선하려는 메커니즘이 하나 더 있다. **가까운 미래에 필요할 가능성이 높은 데이터로 캐시를 미리 채우는 것**이다. 이 메커니즘을 **프리페칭(prefetching)** 이라 하고, 두 가지 모드로 동작한다.

| 모드 | 촉발 주체 | 방식 |
|---|---|---|
| **하드웨어 주도** | CPU | 특정 패턴을 가진 캐시 미스를 몇 번 관찰하면 자동으로 시작한다. 대부분의 CPU가 **8~16개의 메모리 접근 패턴**을 추적한다(전형적인 멀티스레드·멀티프로세스 환경을 감안한 수) |
| **소프트웨어 주도** | 프로그램 | `PREFETCHT0` 명령을 명시적으로 호출한다. C/C++의 `_mm_prefetch` 함수로 노출된다 |

프리페치도 다른 모든 캐싱 메커니즘처럼 **양날의 검**이다. 코드의 메모리 접근 패턴을 잘 이해하고 있다면 프리페치로 성능을 눈에 띄게 올릴 수 있다. 그러나 그 패턴을 제대로 이해하고 있다고 확신하기가 매우 어렵다 — 우리 코드가 동작하는 맥락이 너무 넓기 때문이다. 프로그램의 다른 스레드, 다른 프로그램의 스레드, 운영체제 자신의 스레드가 모두 영향을 준다.

**타이밍이 결정적이다.**

- **너무 늦게 프리페치하면** 필요할 때 데이터가 준비돼 있지 않다.
- **너무 일찍 프리페치하면** 쓰기 시작하는 시점에 이미 캐시에서 축출되어 있을 수 있다.

프리페칭은 .NET **GC 자신이 x86, x64, ARM64에서 사용한다.** 런타임 소스에서 실제로 이렇게 생겼다.

```cpp
// 유용한 프리페치 명령이 있다고 알려진 프로세서에서 활성화한다
#if defined(TARGET_AMD64) || defined(TARGET_X86) || defined(TARGET_ARM64)
#define PREFETCH
#endif

#ifdef PREFETCH
inline void Prefetch(void* addr)
{
#ifdef TARGET_WINDOWS
#if defined(TARGET_AMD64) || defined(TARGET_X86)
#ifndef _MM_HINT_T0
#define _MM_HINT_T0 1
#endif
    _mm_prefetch((const char*)addr, _MM_HINT_T0);
#elif defined(TARGET_ARM64)
    __prefetch((const char*)addr);
#endif //defined(TARGET_AMD64) || defined(TARGET_X86)
#elif defined(TARGET_UNIX)
    __builtin_prefetch(addr);
#else //!(TARGET_WINDOWS || TARGET_UNIX)
    UNREFERENCED_PARAMETER(addr);
#endif //TARGET_WINDOWS
}
#else //PREFETCH
inline void Prefetch (void* addr)
{
    UNREFERENCED_PARAMETER(addr);
}
#endif //PREFETCH
```

이 코드가 말하는 것은 두 가지다. 첫째, **GC는 객체 그래프를 순회하면서 다음에 방문할 객체를 미리 프리페치한다.** 마크 단계의 그래프 순회는 본질적으로 포인터 추적이고, 포인터 추적은 캐시에 최악의 패턴이다. 둘째, **플랫폼마다 프리페치 명령의 이름과 유무가 다르므로 조건부 컴파일이 필요하다.**

> **⚠️ C#에서 프리페치를 직접 호출할 표준 API는 없다**
>
> `System.Runtime.Intrinsics.X86.Sse.Prefetch0` 같은 하드웨어 내장 함수가 존재하지만, 이것은 x86 전용이고 `Sse.IsSupported` 검사를 반드시 해야 한다. 그리고 대부분의 관리 코드에서 수동 프리페치는 **이득이 없거나 오히려 해롭다.** JIT이 만든 코드의 실제 명령 순서를 우리가 통제하지 못하고, 하드웨어 프리페처가 이미 잘 하고 있는 순차 패턴을 방해할 수 있기 때문이다. 프리페치보다 **접근 패턴 자체를 순차로 바꾸는 것**이 거의 항상 더 큰 이득이다.

### 비일시적 접근 — 캐시를 건너뛰기

지금까지 말한 대로, 가장 흔한 CPU 아키텍처에서는 **캐시를 통하지 않고 메모리에 접근할 방법이 없다.** CPU가 DRAM에서 읽거나 쓰는 모든 메모리는 캐시에 저장된다.

아주 큰 배열을 초기화하는데 그것을 먼 미래에나 쓸 것임을 안다고 하자. 지금까지 배운 바로는 이 초기화가 큰 메모리 트래픽을 유발한다. 배열은 캐시 라인 하나씩 차례로 기록된다. 게다가 **각 쓰기 연산은 세 단계**를 포함한다 — 데이터를 캐시로 읽어들이고, 캐시 내용을 수정하고, 마지막으로 캐시 라인을 주 메모리로 되쓴다. 이 시나리오에서 캐시 라인은 **오직 데이터를 주 메모리로 되쓰기 위해서만** 채워진다. 그 자체로 최적이 아닐 뿐 아니라, **다른 프로그램이 쓸 수 있었던 캐시 공간까지 낭비한다.**

이런 캐시 트래픽은 **비일시적 접근(non-temporal access)** 명령 집합으로 피할 수 있다 — `MOVNTI`, `MOVNTQ`, `MOVNTDQ` 등이다. 메모리에 쓰는 동안 데이터가 캐시되는 것을 막아준다. C/C++에서는 `_mm_stream_*` 함수 집합으로 노출되므로 어셈블리를 쓸 필요가 없다. 예를 들어 `_mm_stream_si128`은 `MOVNTDQ` 명령을 실행해 **128비트(16바이트)** 한 덩어리를 메모리에 직접 쓴다. (원천 도서는 이것을 "쿼드 워드"라고 적었지만, x86에서 쿼드 워드는 8바이트이고 `MOVNTDQ`가 옮기는 것은 그 두 배인 더블 쿼드 워드다.)

```cpp
#include <emmintrin.h>
void setbytes(char *p, int c)
{
  // 부호 있는 8비트 정수 16개를 설정한다
  __m128i i = _mm_set_epi8(c, c, c, c, c, c, c, c, c, c, c, c, c, c, c, c);
  _mm_stream_si128((__m128i *)&p[0],  i);
  _mm_stream_si128((__m128i *)&p[16], i);
  _mm_stream_si128((__m128i *)&p[32], i);
  _mm_stream_si128((__m128i *)&p[48], i);
}
```

앞서 말한 하드웨어 내장 함수는 .NET Core 3.0부터 쓸 수 있고, **비일시적 접근 가능성도 포함한다.** `StoreAlignedNonTemporal` 함수 집합을 쓰면 JIT이 접근하는 메모리의 데이터 타입(바이트, 정수, 부동소수 등)에 따라 `MOVNTxx` 명령 중 하나로 번역해준다.

다음은 입력 배열의 값을 2배로 만들어 배치 단위로 저장하는 간단한 예다.

```csharp
int simdLength = Vector<float>.Count;
var vec2 = new Vector<float>(2.0f);
int i = 0;

unsafe
{
    fixed (float* p = outputArray)
    {
        for (; i <= arrayLength - simdLength; i += simdLength)
        {
            var vector = new Vector<float>(inputArray, i);
            vector = vector * vec2;
            vector.StoreAlignedNonTemporal(p + i);
        }
    }
}
// 남은 꼬리 원소는 일반 스칼라 코드로 처리한다
for (; i < arrayLength; ++i)
    outputArray[i] = inputArray[i] * 2.0f;
```

까다로운 점 하나는 이런 저장이 **"정렬"되어 있어야 한다**는 것이다. `StoreAlignedNonTemporal`로 쓰는 메모리 주소는 벡터 폭의 배수여야 한다. **일반 관리 `float` 배열에는 이것이 기본적으로 보장되지 않는다.** 두 가지 방법으로 대응할 수 있다.

- 일반 관리 배열 대신 `NativeMemory.AlignedAlloc`으로 할당한 **정렬된 네이티브 메모리**를 쓴다. ※.NET 6
- 배열 안에서 **첫 번째 정렬된 주소를 찾아 거기서부터** 처리한다. 나머지(앞뒤 꼬리)는 비일시적·비정렬 API 없이 처리한다.

> **⚠️ "캐시 라인 크기 32바이트"라는 표현에 속지 마라**
>
> 원천 도서는 `StoreAlignedNonTemporal`의 정렬 요구를 "캐시 라인 크기(32바이트)의 배수"라고 적었다. 그러나 캐시 라인은 앞에서 본 대로 **64바이트**다. 실제로 요구되는 것은 **벡터 폭 정렬**이다 — AVX2의 256비트 벡터라면 32바이트, AVX-512의 512비트 벡터라면 64바이트, SSE의 128비트 벡터라면 16바이트다. `Vector<T>.Count`가 런타임에 결정되므로 하드코딩하지 말고 `Vector<T>.Count * sizeof(T)`로 계산하는 것이 안전하다.
>
> 버전도 주의하라. 위 예제가 쓴 `Vector<T>`의 `StoreAligned`·`StoreAlignedNonTemporal` 메서드 집합은 ※.NET 7에서 추가되었다. 그 이전 런타임에서는 `System.Runtime.Intrinsics.X86.Avx.StoreAlignedNonTemporal` 같은 하드웨어 내장 함수를 직접 써야 한다.

> **⚠️ 비일시적 접근은 "빠른 메모리 접근" 기본기가 아니다**
>
> 일반적으로 비일시적 접근은 복잡하고 까다롭다. **기본 "빠른 메모리 접근" 기법으로 써서는 절대 안 된다.** 조건이 맞지 않으면(데이터를 곧 다시 읽는다면) 오히려 훨씬 느려진다. 게다가 비일시적 명령은 **정상적인 캐시 일관성 규칙을 우회하므로**, 그 결과를 다른 코어에서 보이게 하려면 특별한 `sfence` 어셈블리 명령과 짝지어 써야 한다. 이 두 가지를 정확히 지키지 못하면 성능이 아니라 **정확성**을 잃는다.

> **📌 비일시적 로드도 있다**
>
> `_mm_stream_load_si128` 함수로 노출되는 비일시적 로드 명령 `MOVNTDQA`도 있다. 이에 대응해 .NET 하드웨어 내장 함수 API는 `LoadAlignedNonTemporal` 메서드 집합을 노출한다.

> **📌 Rule 4 — 더 고급 가능성을 고려하라**
>
> **적용 범위**: 극도로 저수준인 성능 지향 코드.
>
> **근거**: .NET 런타임은 가능한 한 범용적으로 구현되어 있다. 다양한 시나리오에서 제대로 동작하도록 보장하기 위해서다. 그러나 우리 애플리케이션을 쓸 때는 **어디가 핫스팟인지 우리가 알고 있다.** 극도로 빠른 메모리 관련 코드 조각이 필요할 수 있고, 그렇다면 운영체제별 고급 메커니즘을 고려할 수 있다. 이런 메커니즘은 세상의 .NET 개발자 중 아주 작은 일부에게만 필요하다. **직렬화기, 메시징 버퍼, 극도로 빠른 이벤트 처리기** 같은 메모리 관련 라이브러리를 쓴다면 여기 언급된 저수준 시스템 API가 도움이 될 수 있다.
>
> **적용 방법**: 매우 복잡한 코드를 쓰게 될 것이다. 쓰기 고통스럽고, 아마 우리 자신 외에는 아무도 유지보수하려 하지 않을 것이다. 운영체제의 저수준 API를 쓰므로 OS를 업데이트하거나 버전을 바꾼 뒤 문제가 생길 수도 있다. 그리고 애초에 이런 저수준 메모리 관리가 정말 필요한 경우는 매우 드물다. 극도의 주의가 필요하고, **실수하기 아주 쉬우며, 그 실수는 성능을 올리는 대신 극적으로 떨어뜨린다.**

## 61.7 NUMA와 CPU 그룹

### SMP에서 NUMA로

메모리 관리 퍼즐에 넣어야 할 중요한 조각이 하나 더 있다. **대칭 다중 처리(SMP, symmetric multiprocessing)** 는 컴퓨터에 동일한 CPU 여러 개가 있고 그것들이 **공유된 주 메모리**에 연결되어 있다는 뜻이다. 하나의 운영체제가 그들을 제어하며, 모든 프로세서를 동등하게 다룰 수도 아닐 수도 있다.

앞에서 본 대로 각 CPU는 자기 L1·L2 캐시 집합을 갖는다. 다시 말해 **각 CPU에는 다른 메모리 영역보다 훨씬 빨리 접근할 수 있는 전용 지역 메모리가 있다.** 서로 다른 CPU에서 도는 스레드와 프로그램은 아마 어떤 데이터를 공유할 텐데, 이건 이상적이지 않다. **CPU 상호 연결을 통한 데이터 공유는 상당한 지연을 유발하기 때문이다.**

여기서 **비균일 메모리 아키텍처(NUMA, non-uniform memory architecture)** 가 등장한다. **메모리 영역이 그것에 접근하는 CPU에 따라 서로 다른 성능 특성을 갖는다**는 뜻이다. 그리고 소프트웨어(주로 운영체제, 선택적으로 프로그램 자신)는 **NUMA를 인지(NUMA-aware)** 해서 먼 메모리보다 지역 메모리를 선호해야 한다.

```text
  ┌─────────────────────────────────┐   ┌─────────────────────────────────┐
  │        NUMA 노드 0              │   │        NUMA 노드 1              │
  │                                 │   │                                 │
  │  ┌────┐┌────┐┌────┐┌────┐       │   │  ┌────┐┌────┐┌────┐┌────┐       │
  │  │CPU0││CPU1││CPU2││CPU3│       │   │  │CPU4││CPU5││CPU6││CPU7│       │
  │  └─┬──┘└─┬──┘└─┬──┘└─┬──┘       │   │  └─┬──┘└─┬──┘└─┬──┘└─┬──┘       │
  │    └─────┴──┬──┴─────┘          │   │    └─────┴──┬──┴─────┘          │
  │        ┌────┴─────┐             │   │        ┌────┴─────┐             │
  │        │ 지역 DRAM│             │   │        │ 지역 DRAM│             │
  │        └────┬─────┘             │   │        └────┬─────┘             │
  └─────────────┼───────────────────┘   └─────────────┼───────────────────┘
                │                                     │
                └──────── 노드 간 상호 연결 ──────────┘
                          (여기를 지나는 접근이 "먼" 접근)
```

이 **비지역 메모리 접근의 추가 오버헤드를 NUMA 팩터(NUMA factor)** 라 부른다. 모든 CPU를 직접 상호 연결하는 것은 매우 비싸므로, 각 CPU는 보통 **다른 CPU 두세 개에만** 연결된다. 먼 메모리에 접근하려면 프로세서 사이를 **몇 홉(hop)** 지나야 하고, 그만큼 지연이 늘어난다. CPU가 많을수록 비지역 메모리를 쓸 때 NUMA 팩터의 영향이 커진다.

프로세서 그룹이 어떤 메모리를 공유하고 그룹 사이에는 큰 NUMA 팩터로 메모리가 비균일한 혼합 방식의 시스템도 있다. 사실 이것이 NUMA 인지 시스템에서 **가장 흔한 접근**이다. CPU를 **NUMA 노드**라는 작은 시스템으로 묶는다. 각 NUMA 노드는 하드웨어 조직 덕에 작은 NUMA 팩터를 갖는 자기 프로세서와 메모리를 가진다. NUMA 노드는 당연히 상호 연결되지만 **그들 사이의 전송에는 더 큰 오버헤드가 든다.**

| 접근 유형 | 경로 | 상대 비용 |
|---|---|---|
| 코어의 L1/L2 | 코어 내부 | 가장 낮음 |
| 같은 노드의 L3 | 노드 내부 상호 연결 | 낮음 |
| **지역 DRAM** | 같은 NUMA 노드의 메모리 컨트롤러 | 기준선 |
| **원격 DRAM (1홉)** | 노드 간 상호 연결 1회 통과 | 기준선 + NUMA 팩터 |
| **원격 DRAM (N홉)** | 노드 간 상호 연결 N회 통과 | 홉 수에 비례해 증가 |

> **⚠️ NUMA 팩터에는 보편적인 숫자가 없다**
>
> 원천 도서는 NUMA 팩터의 구체적 수치를 제시하지 않는다. 그럴 만한 이유가 있다 — **NUMA 팩터는 CPU 제조사, 세대, 상호 연결 기술(Intel UPI/QPI, AMD Infinity Fabric), 노드 토폴로지에 따라 완전히 다르다.** 실무에서는 대략 1.2배에서 3배 이상까지 폭넓게 관찰되지만, 이 숫자를 그대로 믿지 말고 **자기 하드웨어에서 측정해야 한다.** Linux에서는 `numactl --hardware`가 노드 간 거리 행렬(`node distances`)을 보여주고, Windows에서는 `GetLogicalProcessorInformationEx`나 성능 카운터로 확인한다.

### .NET은 NUMA를 인지하는가

**그렇다.** .NET GC는 **적절한 NUMA 노드에 메모리를 할당한다** — 관리 코드를 실행하는 스레드에 메모리가 "가깝게" 놓이도록. 그리고 **힙 균형 조정(heap balancing)** 시 같은 NUMA 노드에 위치한 힙으로의 할당 균형을 우선한다.

NUMA 인지는 이론적으로 런타임 구성의 `GCNumaAware` 설정으로 끌 수 있지만, 왜 그러고 싶어할지 상상하기 어렵다.

### CPU 그룹

NUMA와는 별개로 중요한 설정이 하나 더 있다. **논리 프로세서가 64개를 넘는 Windows 시스템에서는 프로세서가 CPU 그룹으로 묶인다.** 기본적으로 프로세스는 **단일 CPU 그룹으로 제한된다.** 즉 시스템의 모든 CPU를 쓰지 못한다는 뜻이다.

Windows 기반 .NET 런타임에서 CPU 그룹 인지를 켤 수 있다.

```xml
<configuration>
   <runtime>
      <GCCpuGroup enabled="true"/>
      <gcServer enabled="true"/>
   </runtime>
</configuration>
```

`GCCpuGroup` 설정은 가비지 컬렉터가 **가용한 모든 그룹에 걸쳐 내부 GC 스레드를 만들지**, 그리고 **힙을 만들고 관리할 때 모든 가용 코어를 고려할지**를 지정한다. **`gcServer` 설정과 함께 켜야 한다.**

> **⚠️ 64코어 넘는 머신에서 절반만 쓰고 있을 수 있다**
>
> 논리 프로세서가 64개를 넘는 머신에 .NET 서버 애플리케이션을 배포했는데 CPU 사용률이 절반 수준에서 정체된다면, CPU 그룹 문제일 가능성이 크다. 프로세스가 단일 CPU 그룹에 갇혀 있는 것이다. **이것은 Windows 전용 이슈다** — Linux에는 CPU 그룹이라는 개념이 없고, CPU 친화도(affinity) 마스크가 전체 프로세서를 커버한다.

### 내 머신의 NUMA 토폴로지 확인하기

추측 대신 확인하는 것이 항상 낫다. Linux에서는 `numactl`이 노드 구성과 **노드 간 거리 행렬**을 보여준다.

```text
$ numactl --hardware
available: 2 nodes (0-1)
node 0 cpus: 0 1 2 3 4 5 6 7
node 0 size: 65536 MB
node 0 free: 41234 MB
node 1 cpus: 8 9 10 11 12 13 14 15
node 1 size: 65536 MB
node 1 free: 39871 MB
node distances:
node   0   1
  0:  10  21
  1:  21  10
```

여기서 `node distances`가 핵심이다. **10은 지역 접근의 기준값이고, 21은 원격 노드 접근의 상대 비용**이다. 즉 이 머신에서 원격 DRAM 접근은 지역 접근의 **대략 2.1배** 비용이라고 펌웨어(ACPI SLIT 테이블)가 보고하고 있다. 이 값은 제조사가 보고하는 값이지 실측이 아니므로 참고치로만 쓰고, 정확한 수치가 필요하면 직접 벤치마크해야 한다.

Windows에서는 `Get-WmiObject Win32_Processor`나 `coreinfo -n`(Sysinternals)으로 노드 구성을 볼 수 있고, .NET 코드에서는 `Environment.ProcessorCount`가 **현재 프로세스가 쓸 수 있는 논리 프로세서 수**를 알려준다 — 시스템 전체 코어 수가 아니다.

```csharp
using System.Runtime;

Console.WriteLine($"논리 프로세서: {Environment.ProcessorCount}");
Console.WriteLine($"서버 GC 여부: {GCSettings.IsServerGC}");

var info = GC.GetGCMemoryInfo();
Console.WriteLine($"힙 하드 리밋: {info.TotalAvailableMemoryBytes:N0} 바이트");
Console.WriteLine($"현재 힙 크기: {info.HeapSizeBytes:N0} 바이트");
```

> **⚠️ `Environment.ProcessorCount`는 물리 코어 수가 아니다**
>
> 이 값은 (1) 하이퍼스레딩을 포함한 **논리** 프로세서를 세고, (2) CPU 친화도 마스크나 컨테이너 CPU 제한에 의해 **줄어들 수 있으며**, (3) Windows에서 CPU 그룹에 갇혀 있으면 **64를 넘지 않을 수 있다.** 스레드 풀 크기나 파티션 개수를 이 값으로 정하는 코드는 이 세 가지를 모두 고려해야 한다.

> **💡 컨테이너와 NUMA는 잘 섞이지 않는다**
>
> 컨테이너 오케스트레이터가 CPU 제한을 걸면 컨테이너의 스레드가 여러 NUMA 노드에 흩어지기 쉽고, GC의 NUMA 인지 최적화는 무력해진다. 지연 시간이 중요한 워크로드라면 **노드 단위로 CPU를 고정(pinning)** 하는 것이 훨씬 큰 효과를 낸다. 이건 .NET 설정이 아니라 오케스트레이터 설정 영역이다.

## 61.8 수동 관리 vs 자동 관리 — 무엇을 포기하고 무엇을 얻었나

Ellis와 Stroustrup은 『The Annotated C++ Reference Manual』에서 이렇게 썼다.

> C 프로그래머는 메모리 관리가 너무 중요해서 컴퓨터에 맡길 수 없다고 생각한다.
> Lisp 프로그래머는 메모리 관리가 너무 중요해서 사용자에게 맡길 수 없다고 생각한다.

### 수동 관리 — 수동 변속기 비유

지금까지 본 것은 전부 **수동 메모리 관리**였다. 개발자가 명시적으로 메모리를 할당하고, 더 이상 필요 없을 때 해제할 책임을 진다. 이건 진짜 수동 노동이다. 유럽 차의 수동 변속기와 정확히 같다. 수동으로 기어를 바꾸는 데 익숙한 사람은 지금 바꿀지 엔진 회전수가 충분히 오를 때까지 몇 초 기다릴지 스스로 판단한다. 큰 장점이 하나 있다 — **차에 대한 완전하고 온전한 통제.** 엔진이 최적으로 쓰이는지 아닌지는 운전자 책임이다. 인간은 변하는 조건에 훨씬 잘 적응하므로 좋은 운전자는 자동 변속기보다 잘한다.

물론 큰 단점도 하나 있다. **A에서 B로 간다는 본래 목표 대신 기어 변경을 추가로 생각해야 한다** — 긴 여행 동안 수백, 수천 번씩. 시간이 들고 피곤하다.

메모리 관리도 똑같다. 명시적 할당·해제를 이야기할 때, 그것은 정확히 수동 변속기다. **아마도 비즈니스 처리와 관련되어 있을 본래 목표 대신, 프로그램에서 메모리를 어떻게 관리할지도 생각해야 한다.** 알고리즘, 비즈니스 로직, 도메인을 생각하는 대신 **메모리가 얼마나 필요하고 얼마나 오래 필요한지**를 생각해야 한다. 그리고 **코드의 어느 부분이 해제를 책임지는지**도. 그게 비즈니스 로직처럼 들리는가? 물론 아니다.

### C — 여덟 가지 책임

간단한 C 프로그램을 보자.

```c
#include <stdio.h>

void printReport(int* data)
{
    printf("Report: %d\n", *data);
}

int main(void)
{
    int* ptr;
    ptr = (int*)malloc(sizeof(int));
    if (ptr == NULL)
    {
        printf("ERROR: Out of memory\n");
        return 1;
    }
    *ptr = 25;
    printReport(ptr);
    free(ptr);
    ptr = NULL;
    return 0;
}
```

과장된 예이긴 하지만 문제를 잘 보여준다. 이 코드의 **비즈니스 목표는 단 하나** — "보고서"를 출력하는 것이다. 단순화를 위해 보고서가 정수 하나지만, 다른 자료 구조에 대한 포인터를 담은 더 복잡한 구조라고 상상해도 된다. **이 단순한 비즈니스 목표가 메모리만 돌보는 "의례 코드(ceremony code)"에 압도당해 있다.** 이것이 수동 메모리 관리의 본질이다.

개발자가 해야 하는 일을 정리하면 이렇다.

| # | 해야 할 일 | 실수했을 때 |
|---|---|---|
| 1 | `malloc`으로 **적절한 양**의 메모리를 할당한다 | 너무 많이 → 성능 저하·메모리 누수. 너무 적게 → **버퍼 오버플로**. 최선의 경우 Linux 세그멘테이션 폴트나 Windows 액세스 위반, 최악의 경우 **데이터 손상이나 보안 취약점** |
| 2 | 반환된 제네릭 `void*` 포인터를 **적절한 타입으로 캐스팅**한다 | 타입 불일치가 우연히 섞이면 진단하기 어려운 버그. 다른 타입인 척 해석하다 **치명적 액세스 위반** |
| 3 | 할당된 영역의 **포인터를 지역 변수에 추적**한다 | 포인터를 잃으면 그 메모리는 영원히 회수 불가 |
| 4 | 요청한 양이 **성공적으로 할당됐는지 검사**한다 | 한 번은 성가시지 않지만 함수마다 백 번이면 반드시 생략하게 되고, 할당 실패한 메모리에 접근해 **정의되지 않은 동작** |
| 5 | 포인터를 **역참조**해 데이터를 저장한다 | 역참조는 항상 위험하다. 그 주소에 뭐가 있는지 아무도 모른다. 유효한 객체가 아직 있나? 이미 해제됐나? 애초에 유효한 포인터인가? |
| 6 | 포인터를 **다른 함수에 전달**한다 | 함수와 스레드 사이로 포인터를 넘기면 멀티스레드 환경에서 걱정이 한 자릿수 더 늘어난다 |
| 7 | 더 이상 필요 없을 때 `free`로 **해제**한다 | 생략하면 **메모리 누수**. 이미 해제된 메모리를 또 해제하는 것을 아무도 막지 않는다 → **이중 해제** |
| 8 | 포인터를 **`NULL`로 표시**한다 | 안 하면 **댕글링 포인터(dangling pointer)**. 다른 코드가 유효한 데이터라고 믿고 역참조하다 언젠가 크래시 |

이 문제들은 **멀티스레드 환경에서 전부 악화된다.** 포인터가 여러 실행 단위 사이에서 공유될 수 있기 때문이다. 잘못된 데이터가 섞이지 않도록 신중한 동기화가 필요하다. 예를 들어 **한 스레드가 포인터가 유효한지(`NULL`이 아닌지) 검사한 직후 다른 스레드가 그 메모리를 해제하면** 어떻게 되나? 간헐적이고 진단하기 극도로 어려운 문제가 된다. 명시적 메모리 관리 세계에서는 이런 상황을 피할 적절한 동기화를 제공하는 것도 **개발자 책임이다.**

### C++ — 개선, 그리고 남은 문제

C의 직계 후손인 C++은 상황을 약간 개선한다.

```cpp
#include <iostream>

void printReport(int* data)
{
    std::cout << "Report: " << *data << "\n";
}

int main()
{
    try
    {
        int* ptr;
        ptr = new int();
        *ptr = 25;
        printReport(ptr);
        delete ptr;
        ptr = NULL;
        return 0;
    }
    catch (std::bad_alloc& ba)
    {
        std::cout << "ERROR: Out of memory\n";
        return 1;
    }
}
```

의미 있는 개선이 몇 가지 보인다.

- **`new` 연산자가 충분한 메모리 할당을 알아서 처리한다.** 컴파일러가 타입 크기를 알려주기 때문이다.
- **얻은 포인터를 적절한 타입으로 캐스팅할 필요가 없다.** 앞서 본 타입 안전성 우려가 일부 사라진다.
- **할당 오류 처리가 예외로 개선된다.**

그래도 의례 코드는 여전히 많다. **새로운 우려도 생긴다.** `printReport()`가 예외를 던지면 어떻게 되나? 적절한 오류 처리 없이는 `delete` 호출이 쉽게 건너뛰어져 **메모리 누수**가 생긴다. 이 예제를 고치는 건 쉽지만, 데이터 소유권(누가, 어느 계층이 이 포인터를 지워야 하는가)이 자명하지 않은 더 복잡한 애플리케이션에서는 그렇지 않다.

### RAII와 스마트 포인터

현대 C++은 **RAII(Resource Acquisition Is Initialization)** 기법을 쓴다. 자원(메모리 같은)을 어떤 메모리 소유권 로직을 구현한 타입의 지역 변수로 표현하는 것이다.

**스마트 포인터(smart pointer)** 는 가리키는 객체의 수명을 관리하는 더 정교한 방법으로 도입됐다. 구현 관점에서 C++의 스마트 포인터는 사실 **연산자 오버로딩으로 일반 포인터처럼 행동하는 템플릿 클래스**다. C++의 주요 스마트 포인터는 둘이다.

- **`unique_ptr`** — 고유 소유권 의미론. 포인터가 객체의 유일한 소유자이고, `unique_ptr`이 스코프를 벗어나거나 다른 객체가 대입되면 객체가 파괴된다.
- **`shared_ptr`** — **참조 카운팅** 의미론.

```cpp
#include <iostream>
#include <memory>

void printReport(std::shared_ptr<int> data)
{
    std::cout << "Report: " << *data << "\n";
}

int main()
{
    try
    {
        std::shared_ptr<int> ptr(new int());
        *ptr = 25;
        printReport(ptr);
        return 0;
    }
    catch (std::bad_alloc& ba)
    {
        std::cout << "ERROR: Out of memory\n";
        return 1;
    }
}
```

`printReport` 안에서 `data.use_count()`를 부르면 **2**가 나온다. 서로 다른 두 스마트 포인터가 같은 객체를 가리키기 때문이다 — `main()`에서 만든 것과, 인자를 값으로 전달하면서 만들어진 사본. 반면 `try` 블록 스코프를 벗어나면 사용 카운트는 0이 된다.

개선점은 명확하다.

- **`delete`로 객체를 수동 파괴할 필요가 없다.**
- **예외 처리가 단순해진다.** `printReport()`가 예외를 던져도 실행이 `try` 블록 스코프를 벗어날 때 스마트 포인터가 자동으로 파괴된다. 앞서 말한 RAII 원칙의 적용이다.

> **📌 이 C++ 예제는 모범 사례가 아니다**
>
> 밑에 깔린 데이터를 읽기만 하려고 스마트 포인터를 넘길 때는 값이 아니라 **상수 참조(`const&`)** 로 넘겨야 한다. 여기서 값으로 넘긴 것은 **사본이 참조 카운트를 올리는 것을 보여주기 위해서**다.

### 왜 .NET은 처음부터 자동 관리를 택했나

C++의 스마트 포인터는 **언어가 아니라 표준 라이브러리 수준에서** 도입됐다. 그 때문에 다른 라이브러리들이 자기 구현을 도입했고, 그들끼리 사이좋게 대화하게 만드는 게 때때로 문제가 된다. Qt에는 `QtSharedPointer`가, wxWidgets에는 `wxSharedPtr<T>`가 있다.

**이것이 .NET의 C# 같은 컴포넌트 지향 프로그래밍에서 자동 메모리 관리가 결정적인 이유다.** 여러 개의 작고 교체 가능한 의존성으로 이루어진 세계에서, .NET이 태어날 때 **메모리 관리 책임을 개발자에서 런타임 자신으로 옮긴 것은 주요하고 결정적인 설계 결정이었다.** 객체가 어떻게 만들어지고 관리되고 회수되는지에 대한 공통 플랫폼이 있다는 것은, **모든 컴포넌트가 같은 방식으로 그것을 재사용하고 런타임 외에는 컴포넌트 간 결합이 없다**는 뜻이다.

다른 언어들은 스마트 포인터를 설계에 **직접** 넣었다. **Rust**가 그렇다 — 몇 가지 스마트 포인터를 언어에 직접 통합해 컴파일 수준에서 데이터 안전성을 강제한다. 소유권 의미론과 RAII 원칙을 강하게 써서 댕글링 포인터 역참조 같은 위반을 **컴파일 타임에** 검사한다. **Swift에 내장된 자동 참조 카운팅(ARC)** 도 주목할 만한 참조 카운팅 사용례다.

> **📌 C++ 표준은 GC를 금지하지 않는다**
>
> Bjarne Stroustrup은 C++ 표준에서 더 정교한 GC를 허용했다 — 금지된 게 아니라 아직 구현되지 않았을 뿐이다. 게다가 C++의 유연성 덕분에 Memory Pool System이나 **Boehm–Demers–Weiser 수집기**를 통해 **확장 라이브러리로서** 가비지 컬렉션을 쓰는 것이 가능하다.

### Mutator, Allocator, Collector

자동 메모리 관리를 정확히 논하려면 학계 연구에서 쓰는 세 용어를 알아야 한다. 이 정의 덕에 "특정 알고리즘의 **Mutator 오버헤드**" 같은 말을 모호함 없이 할 수 있다.

**Mutator(뮤테이터)** 는 가장 기본적이면서 가장 중요한 추상화다. 가장 단순한 형태로는 **애플리케이션 코드를 실행하는 개체**로 정의된다. 이름은 그것이 **메모리의 상태를 변경(mutate)한다**는 사실에서 왔다 — 객체가 할당되거나 수정되고, 객체 사이의 참조가 바뀐다. 이 이름은 Edsger Dijkstra가 1978년 논문 "On-the-Fly Garbage Collection: An Exercise in Cooperation"에서 만들었다.

Mutator가 온전히 동작하려면 실행 중인 애플리케이션에 세 연산을 제공해야 한다.

```text
Mutator.New(amount)
{
   return Allocator.Allocate(amount);
}

Mutator.Write(address, value)
{
   *address = value;
}

Mutator.Read(address) : value
{
   return *address;
}
```

- **`New(amount)`** — 새로 만들 객체가 쓸 주어진 양의 메모리를 할당한다. 이 추상화 수준에서 **객체의 타입 정보는 무관하다.** 할당할 메모리 크기만 주어진다.
- **`Write(address, value)`** — 주어진 주소에 지정된 값을 쓴다. 객체 필드인지 전역 변수인지 다른 데이터 조직인지도 추상화한다.
- **`Read(address)`** — 지정된 주소에서 값을 읽는다.

가비지 컬렉션 알고리즘이 없는 가장 단순한 세계에서 이 세 연산의 구현은 위처럼 사소하다. 그러나 **자동화된 가비지 컬렉션의 세계에서 이 세 연산은 Mutator가 Collector 및 Allocator와 협력하는 지점이다.** 이 협력이 어떻게 생겼고 위 구현의 단순함을 얼마나 해치는지가 가장 중요한 설계 관심사다.

가장 흔한 보강은 **배리어(barrier)** 다 — **읽기 배리어(read barrier)** 이거나 **쓰기 배리어(write barrier)** 다. 배리어는 연산을 (앞이나 뒤에서) 증강하는 방법이다. 배리어는 프로그램 실행과 메모리 사용을 가비지 컬렉션 메커니즘에 알리기 위해 (직접적이든 간접적이든, 동기적이든 비동기적이든) 동기화하게 해준다. **위 세 메서드는 모든 가비지 컬렉터가 끼어들고 싶어 하는 주입 지점이다.**

일상에서 Mutator 추상화의 가장 흔한 구현은 잘 알려진 **스레드**다. 정의에 완벽히 들어맞는다 — 객체와 객체 간 참조 그래프를 변경하는 코드를 실행하는 단일 단위. 다만 Mutator가 반드시 운영체제 스레드일 필요는 없다. Erlang 생태계의 프로세스(런타임 자체에 사는 초경량 코루틴, "그린 스레드"보다 격리가 강해 "그린 프로세스"라 부르는 편이 낫다)나, Linux와 Windows 양쪽에 구현된 경량 실행 단위인 **파이버(fiber)** 도 있다.

**Allocator(할당자)** 는 동적 메모리 할당과 해제를 관리하는 개체다. 두 연산을 제공한다.

- **`Allocate(amount)`** — 지정된 양의 메모리를 할당한다. 타입 정보가 있다면 특정 타입의 객체를 위한 할당 메서드로 확장할 수 있다. `Mutator.New`가 내부적으로 이것을 쓴다.
- **`Deallocate(address)`** — 주어진 주소의 메모리를 이후 할당에 쓸 수 있도록 해제한다. **자동 메모리 관리에서는 이 메서드가 내부용이고 Mutator에 노출되지 않는다.** 따라서 **어떤 사용자 코드도 이것을 명시적으로 호출할 수 없다.**

**Collector(수집기)** 는 가비지 컬렉션(자동 메모리 회수) 코드를 실행하는 개체다. 소프트웨어 조각(코드)일 수도, 그것을 실행하는 스레드일 수도, 둘 다일 수도 있다. 맥락에 따라 다르다.

> **⚠️ 자동 메모리 관리는 "무한 메모리 컴퓨터의 시뮬레이션"이다**
>
> `Allocator.Deallocate`가 공개되지 않으므로 **Mutator는 얻은 메모리를 명시적으로 해제할 방법이 없다.** Mutator는 마치 무한한 원천이 있는 것처럼 더, 더 할당해달라고 요청할 수만 있다. 이는 곧 **가비지 컬렉션 메커니즘이 사실상 무한한 메모리를 가진 컴퓨터의 시뮬레이션**이라는 뜻이다. 이 시뮬레이션이 어떻게 동작하고 얼마나 효율적인지는 구현에 달렸다. C#의 `IDisposable`과 `Dispose()`는 이 규칙의 예외가 **아니다** — 그것은 메모리가 아니라 파일 핸들·소켓 같은 **비메모리 자원**을 해제하는 규약이고, 관리 메모리는 여전히 GC만이 회수한다. 이 구분을 흐리는 순간 33장(결정적 정리와 IDisposable)과 34장(객체 수명과 파이널라이제이션)에서 본 논의 전체가 헷갈리기 시작한다.

> **📌 Null 가비지 컬렉터**
>
> 할당된 메모리를 **전혀** 해제하지 않는 특별한 수집기를 상상할 수 있다. **Null(또는 Zero) 가비지 컬렉터**라고 한다. 무한한 메모리를 가진 컴퓨터에서만 올바르게 동작할 텐데, 불행히도 그런 것은 아직 없다. 그러나 실용적 쓸모가 아예 없지는 않다. 무한한 메모리 증가가 용인되는 **아주 짧게 사는 프로그램**에 쓸 수 있다. 서버리스, 단발성 함수 세계에서 점점 인기를 얻을지도 모른다.

### 생존성과 도달 가능성 — 관리 메모리 누수의 뿌리

Collector는 어떤 객체가 더 이상 필요 없어 해제 가능한지 어떻게 아나? **이건 불가능한 문제다.** 미래를 추측해야 하기 때문이다. 특정 객체가 다시 쓰일지는 앞으로 실행될 코드에 달렸고, 그것은 사용자 행동이나 외부 데이터 같은 독립 요인에 또 달려 있다.

이상적인 Collector라면 객체의 **생존성(liveness)** 을 안다 — **살아 있는 객체는 앞으로 필요할 객체**다. 반대로 **죽은(쓰레기) 객체는 다시 쓰이지 않을 것이므로 파괴할 수 있다.**

생존성을 아는 것이 불가능하므로 Collector는 다른 것에 기댄다 — **어떤 Mutator로부터의 도달 가능성(reachability)** 이다. 객체가 도달 가능하다는 것은 **어떤 Mutator가 접근할 수 있는 메모리에서 출발해 그 객체에 이르는 참조의 사슬이 존재한다**는 뜻이다.

**도달 가능성은 생존성을 함의하지 않는다. 그러나 우리가 가진 최선의 근사다.** 어떤 Mutator에서도 도달할 수 없다면 그 객체는 더 이상 쓰일 수 없으므로 죽었고 안전하게 회수할 수 있다. **반대는 성립하지 않는다.** 도달 가능한 객체가 (복잡한 참조 그래프에 붙들려) 영원히 도달 가능한 채로 남지만, 실행 조건 때문에 다시는 접근되지 않을 수 있다. 그런 객체는 사실 죽었다.

> **⚠️ 생존성과 도달 가능성의 이 어긋남이 관리 메모리 누수 대부분의 원인이다**
>
> .NET에서 "메모리 누수"라고 부르는 것의 정체가 이것이다. **더 이상 쓰지 않을 객체를 여전히 참조하고 있는 것.** 정적 컬렉션에 계속 넣기만 하는 캐시, 해제하지 않은 이벤트 핸들러 구독, 살아 있는 객체가 붙잡고 있는 큰 그래프. GC는 잘못한 게 없다 — **도달 가능한 것을 회수하지 않았을 뿐이다.** 66장에서 이 진단을 다룬다.

Mutator의 도달 가능성 출발점을 **루트(root)** 라 한다. 정확히 무엇인지는 Mutator 구현에 달렸지만, Mutator가 (네이티브 스레드로 표현된) 단순한 스레드인 가장 흔한 경우에 루트는 이렇다.

- **지역 변수와 서브루틴 인자** — 스택에 놓이거나 레지스터에 저장된 것
- **정적으로 할당된 객체**(예: 전역 변수) — 힙에 놓인 것
- **Collector 자신 안에 저장된 다른 내부 자료 구조**

### 무엇을 포기하고 무엇을 얻었나

| 항목 | 수동 관리 | 자동 관리(추적 GC) |
|---|---|---|
| **해제 시점** | 개발자가 정한다. 결정적 | 런타임이 정한다. **비결정적** |
| **해제 지연** | 없음(즉시) | 도달 불가능해진 뒤 회수까지 **예측 불가능한 시간** |
| **메모리 오버헤드** | 낮음 | **높음**(죽은 객체가 즉시 회수되지 않으므로) |
| **개발자 인지 부담** | 매우 높음(위 여덟 가지) | 매우 낮음(메모리를 무한한 것처럼 다룬다) |
| **버퍼 오버플로·댕글링 포인터** | 발생 가능 | 구조적으로 차단 |
| **이중 해제** | 발생 가능 | 불가능(해제 API가 없다) |
| **순환 참조** | 개발자가 처리 | 문제 없음(도달 가능성 기반) |
| **일시 정지(pause)** | 없음 | 발생(비동시성 마크 단계는 **전 스레드 중단**) |
| **컴포넌트 간 상호 운용** | 라이브러리마다 소유권 규약이 달라 결합이 생긴다 | 런타임이 유일한 결합점 |
| **최고 성능 한계** | 전문가가 튜닝하면 더 높다 | 범용 최적화의 한계 안 |

**핵심은 이것이다.** 자동 메모리 관리는 **결정적 해제와 메모리 오버헤드를 포기하고, 개발자의 인지 부담과 메모리 안전성 사고를 얻어냈다.** 그리고 이 거래에서 포기한 쪽(비결정성, 일시 정지, 메모리 오버헤드)이 바로 **62장부터 66장까지가 통째로 다룰 주제**다.

## 61.9 참조 카운팅 vs 추적 수집기, 보수적 GC vs 정밀 GC

자동 메모리 관리를 실현하는 방법은 크게 둘이다. 그리고 두 번째 방법 안에서 다시 두 갈래가 갈린다. 이 절은 그 지도를 그린다.

```text
                자동 메모리 관리
                       │
        ┌──────────────┴──────────────┐
        │                             │
  참조 카운팅                    추적 수집기
  (Reference Counting)          (Tracking Collector)
  · 지역 정보만 본다             · 전역 그래프를 순회한다
  · 즉시 해제                    · 도달 가능성 기반
  · 순환 참조에 취약              · Mark → Collect
  · C++ shared_ptr,                    │
    Swift ARC              ┌───────────┴───────────┐
                           │                       │
                     보수적 GC                정밀 GC
                     (Conservative)          (Precise)
                     · 포인터를 "추측"        · 타입 레이아웃을 안다
                     · 객체 이동 불가         · 이동(컴팩션) 가능
                     · Boehm GC,             · **.NET**, JVM
                       Mono ~2.8               Mono 2.8+ (혼합)
```

### 참조 카운팅

가장 인기 있는 두 자동 메모리 관리 방법 중 하나가 **참조 카운팅(Reference Counting)** 이다. 착상은 아주 단순하다. **객체에 대한 참조 개수를 센다.** 모든 객체가 자기 참조 카운터를 갖는다. 객체가 변수나 필드에 대입되면 그 참조 카운터가 증가한다. 동시에 그 변수가 이전에 가리키던 객체의 참조 카운트는 감소한다.

참조 카운팅에서 객체의 생존성은 **참조하는 객체의 수**에 달렸다. **카운터가 0으로 떨어지면 아무도 참조하지 않는 것이므로 해제할 수 있다.** 카운터가 0으로 떨어지지 않으면? 그건 생존성에 대해 아무것도 말해주지 않는다 — **누군가 참조를 붙들고 있다는 것만 말해줄 뿐, 그것을 쓸 것이라는 뜻은 아니다.** 그러니 참조 카운팅도 생존성을 추측하는 또 하나의 방식이다.

앞서 본 Mutator 연산으로 표현하면 이렇게 된다.

```text
Mutator.New(amount)
{
   obj = Allocator.Allocate(amount);
   obj.counter = 0;
   return obj;
}

Mutator.Write(address, value)
{
   if (address != NULL)
      ReferenceCountingCollector.DecreaseCounter(address);
   *address = value;
   if (value != NULL)
      value.counter++;
}

ReferenceCountingCollector.DecreaseCounter(address)
{
   *address.counter--;
   if (*address.counter == 0)
      Allocator.Deallocate(address)
}
```

세 줄짜리 코드로 동작을 따라가보자.

```text
o1 = new SomeObject();
o2 = new SomeObject();
o2 = o1;

// 위 코드는 사실 다음과 같다:
addr1 = Mutator.New(SizeOf(SomeObject))    // addr1.counter = 0
Mutator.Write(&o1, addr1)                  // addr1.counter = 1
addr2 = Mutator.New(SizeOf(SomeObject))    // addr2.counter = 0
Mutator.Write(&o2, addr2)                  // addr2.counter = 1
Mutator.Write(&o2, &o1)                    // addr2.counter = 0 (해제!)
                                           // addr1.counter = 2
```

**`Mutator.Write`에 큰 오버헤드가 추가된 것이 보인다.** 카운터 데이터를 검사하고 수정해야 하고, 0으로 떨어지면 해제 조치를 취해야 한다. 멀티스레드 환경에서는 훨씬 복잡해진다. 여러 Mutator가 병렬로 일하므로 이 연산들이 **스레드 안전**해야 하고, 추가 동기화가 자기 오버헤드를 얹는다.

**`Mutator.Write`는 아주 흔한 연산이다**(모든 대입이 그것을 일으킨다). 그러니 여기의 어떤 오버헤드도 누적되어 전체 프로그램 실행에 상당한 오버헤드를 만든다. 구현 관점에서 **객체의 카운터를 어디에 저장할지도 자명하지 않다.** 전용 공간일 수도, 객체에 가능한 한 가까운 헤더일 수도 있다. 어느 쪽이든 **모든 대입이 추가 메모리 쓰기를 만든다**는 사실은 변하지 않고, 이것은 매우 바람직하지 않다. **CPU 캐시 사용도 비효율적으로 만든다.**

### 순환 참조 문제

앞서 말한 도달 가능성 관점에서 보면, 참조 카운팅은 **지역 참조로 생존성을 근사할 뿐 객체 참조 그래프의 전역 상태를 추적하지 않는다.** 특히 아무 개선 없이는 **순환 참조에 속는다.**

```text
       ┌─────────────────┐        ┌─────────────────┐
       │  노드 A         │        │  노드 B         │
       │  counter = 1    │        │  counter = 1    │
       │                 │        │                 │
       │  next  ─────────┼───────→│                 │
       │                 │←───────┼──── prev        │
       └─────────────────┘        └─────────────────┘
              ↑
        (외부 참조가 모두 사라졌다)

  둘 다 카운터가 0이 되지 않는다. 서로를 가리키고 있기 때문이다.
  → 영원히 회수되지 않는다.
```

이중 연결 리스트 같은 흔한 자료 구조에서 바로 이 문제가 생긴다. 값1을 가진 구조와 값2를 가진 구조가 서로를 가리키므로 참조 카운터가 절대 0으로 떨어지지 않는다.

다만 **언어 수준에서 순환 참조를 만들기 어렵게 만들 수 있고**, 그건 이기는 상황이다. 그런 경우 순환에서 오는 메모리 누수를 크게 걱정하지 않고 참조 카운팅 알고리즘을 쓸 수 있다.

### 참조 카운팅의 결정적 장점

참조 카운팅의 아주 큰 장점 하나는 **런타임 지원이 전혀 필요 없다는 것**이다. 특정 타입을 위한 추가 메커니즘으로, 외부 라이브러리 형태로 구현할 수 있다. 원래의 `Mutator.New`와 `Mutator.Write`를 그대로 두고 기존 런타임 구성 요소(적절히 오버로드된 연산자와 생성자를 가진 클래스 등)로 참조 카운팅 로직을 구현할 수 있다는 뜻이다. **가장 인기 있는 C++ 구현이 정확히 이 경우다.**

정리하면 이렇다.

**장점**

- **결정적 해제(deterministic deallocation)** — 객체의 참조 카운터가 0으로 떨어질 때 해제가 일어난다는 것을 안다. 따라서 더 이상 필요 없어지자마자 메모리가 회수된다.
- **더 적은 메모리 압박(less memory pressure)** — 객체를 더 이상 쓰지 않는 즉시 메모리가 회수되므로, 수집을 기다리는 객체가 메모리를 낭비하지 않는다.
- **런타임 지원 없이 구현할 수 있다.**

**단점**

- 순진한 구현은 **Mutator에 상당한 오버헤드**를 도입한다.
- **참조 카운터에 대한 멀티스레딩 연산은 잘 설계된 동기화가 필요**하고, 이것이 추가 오버헤드를 만든다.
- **추가 개선 없이는 순환 참조를 회수할 수 없다.**

**지연 참조 카운팅(Deferred Reference Counting)** 이나 **병합 참조 카운팅(Coalesced Reference Counting)** 같은 개선이 있어 이 문제 일부를 제거하지만, 장점 일부(주로 즉각적 메모리 회수)를 대가로 치른다.

### 추적 수집기

객체의 도달 가능성을 알아내는 일이 어려운 이유는 그것이 **전역 상태**이기 때문이다(프로그램 전체의 객체 그래프에 달렸다). 반면 객체 해제를 명시적으로 호출하는 것은 **지역적**이다. 이 지역 맥락에서 우리는 전역 맥락을 모른다 — 다른 객체들이 지금 이 객체를 쓰고 있나? 참조 카운팅은 **지역 맥락에 약간의 추가 정보(참조 수)만 얹어** 이를 극복하려 하지만, 앞서 본 대로 순환 참조 문제와 다른 단점이 있다.

**추적 가비지 컬렉터(Tracking Garbage Collector)** 는 객체 수명의 **전역 맥락**에 대한 지식에 기반하며, 객체를 지울(메모리를 회수할) 좋은 시점인지 더 나은 결정을 내릴 수 있다. 사실 너무나 인기 있는 접근이라, **누군가 "가비지 컬렉터"라고 말하면 거의 확실히 추적 가비지 컬렉터를 뜻한다.** .NET과 여러 JVM 구현이 그렇다.

핵심 개념은 이렇다. 추적 GC는 **Mutator의 루트에서 출발해 프로그램의 객체 그래프 전체를 재귀적으로 추적**함으로써 객체의 진짜 도달 가능성을 알아낸다. 이건 당연히 사소한 일이 아니다. 프로세스 메모리가 수 GB일 수 있고, 그렇게 큰 데이터에서 모든 객체 간 참조를 추적하는 것은 어렵다. **특히 Mutator들이 돌면서 그 참조들을 계속 바꾸고 있는 동안에는.**

전형적인 접근은 두 단계로 이루어진다.

- **Mark(마크)** — Collector가 도달 가능성을 찾아 어떤 객체가 수집될 수 있는지 결정한다.
- **Collect(수집)** — Collector가 도달 불가능하다고 판정된 객체들의 메모리를 회수한다.

**.NET은 이 단순한 2단계 로직을 Mark-Plan-Sweep-Compact로 확장한다.** 상세는 64장에서 다룬다.

### Mark 단계

Mark 단계에서 Collector는 **Mutator의 루트에서 출발해 객체 그래프 전체를 여행하며 방문한 것을 마크한다.** Mark 단계가 끝났을 때 마크되지 않은 객체는 도달 불가능한 것이다. **객체를 마크하는 것은 순환 참조에도 도움이 된다.** 그래프 순회 중 같은 객체를 여러 번 만나도 마크 덕에 한 번만 검사한다.

그래프를 깊이 우선으로 도는지 너비 우선으로 도는지는 구현 세부사항이다. 깊이 우선 방식의 처음 몇 단계를 보자. 객체는 세 상태 중 하나다 — **아직 방문 안 함**(`□`), **방문 예정 큐에 있음**(`▢`), **이미 방문함**(`■`).

```text
  객체 그래프:  루트 → A ─→ B
                       └─→ D ─→ E ─→ G
                (C, F는 아무도 가리키지 않는다)

  1) 초기 상태            □A  □B  □C  □D  □E  □F  □G     큐: []
  2) A를 루트로 큐에 넣음  ▢A  □B  □C  □D  □E  □F  □G     큐: [A]
  3) A 방문. B, D 큐에    ■A  ▢B  □C  ▢D  □E  □F  □G     큐: [B, D]
  4) B 방문(외부 참조 X)  ■A  ■B  □C  ▢D  □E  □F  □G     큐: [D]
  5) D 방문. E 큐에       ■A  ■B  □C  ■D  ▢E  □F  □G     큐: [E]
  6) E 방문. G 큐에       ■A  ■B  □C  ■D  ■E  □F  ▢G     큐: [G]
  7) G 방문. 큐가 빔      ■A  ■B  □C  ■D  ■E  □F  ■G     큐: []

  → C와 F는 끝까지 □ 다. 도달 불가능(죽음)으로 판정된다.
```

**Mutator가 정상적으로 일하는 동안 이런 그래프를 순회하는 것은 어렵다.** 프로그램 실행(새 객체 생성, 변수 대입, 객체 필드 대입)으로 그래프가 계속 바뀌기 때문이다. 그래서 일부 GC 구현은 **Mark 단계 동안 모든 Mutator를 그냥 멈춘다.** 이러면 그래프를 안전하고 일관되게 순회할 수 있다.

물론 스레드가 동작을 재개하는 순간 Collector가 가진 객체 그래프 지식은 낡은 것이 된다. **그러나 도달 불가능한 객체에 대해서는 문제가 아니다** — 이전에 도달 불가능했다면 다시 도달 가능해지지 않는다. 한편 Mark 단계를 **동시(concurrent) 방식**으로 수행하는 구현도 많아서, 마킹 프로세스가 Mutator 코드와 나란히 돌 수 있다. JVM의 CMS(Concurrent Mark Sweep)와 G1, 그리고 **.NET 자신**이 그렇다. .NET의 동시 마킹 구현은 64장에서 자세히 다룬다.

### 보수적 GC vs 정밀 GC

Mark 단계에는 자명하지 않은 문제가 하나 있다. **도달 가능성을 추적하려면 Collector가 루트가 무엇인지, 그리고 힙 어디에 다른 객체로의 참조가 놓여 있는지 알 수 있어야 한다.** 런타임이 그런 정보를 제공하면 사소한 문제다. 하지만 다른 방식으로도 극복할 수 있다.

**보수적 가비지 컬렉터(Conservative Garbage Collector)** 는 "가난한 자의 해법"으로 볼 수 있다. 런타임이나 컴파일러가 정확한 타입 정보(객체의 메모리 내 레이아웃)를 제공해 수집을 직접 지원하지 않고, Collector가 포인터를 다룰 때 Mutator의 도움을 받지 못할 때 쓸 수 있다.

보수적 Collector가 어떤 객체가 도달 가능한지 알아내려면 **스택 전체, 정적 데이터 영역, 레지스터를 스캔한다.** 런타임의 도움 없이 **무엇이 포인터이고 무엇이 아닌지 그냥 추측한다.** 여러 가지를 검사하는데(구체적 구현마다 다르다), 가장 중요한 검사는 **어떤 워드를 주소로 해석했을 때 그것이 메모리의 유효한 영역(할당자 힙 영역)을 가리키는가**다. 그렇다면 Collector는 **보수적으로(그래서 이 이름이다)** 그것이 포인터라고 가정하고 Mark 단계 그래프 순회에서 따라갈 참조로 취급한다.

당연히 Collector는 무엇이 포인터인지 추측하면서 틀릴 수 있고, 그것은 부정확성으로 이어진다. **메모리의 무작위 비트가 적절한 주소를 가진 유효한 포인터처럼 보일 수 있고, 그러면 실제로는 쓰이지 않는 메모리를 붙잡게 된다.** 아주 흔한 문제는 아니다 — 메모리의 대부분 수치 값은 오히려 작고(카운터, 금융 데이터, 인덱스) 메모리 주소는 보통 크기 때문이다. **문제가 될 수 있는 것은 비트맵, 부동소수, 특정 IP 주소 블록 같은 조밀한 이진 데이터뿐이다.**

그리고 결정적인 제약이 하나 더 있다. **보수적 보고는 메모리에서 객체를 이동시킬 수 없다는 뜻이다.** 옮긴 객체를 가리키는 포인터를 갱신해야 하는데, 포인터처럼 보이는 무언가가 정말 포인터인지 확신할 수 없다면 그건 불가능하다.

그럼 애초에 누가 이런 Collector를 필요로 하나? **주된 장점은 런타임 지원 없이 동작할 수 있다는 것**이다 — 그냥 메모리를 스캔하므로 런타임 지원(참조 추적)이 필요 없다. 예를 들어 **새 런타임을 개발 중이라 GC를 위한 완전한 타입 정보가 아직 준비되지 않았을 때** 편리하다. 초기 버전은 보수적 GC를 써서 나머지 시스템의 개발이 막히지 않게 할 수 있다. 제대로 된 런타임 지원이 구현되면 보수적 추적을 그냥 끄면 된다. **Microsoft도 자기 런타임의 일부 버전을 개발할 때 이 접근을 썼다.**

다만 보수적 Collector는 객체 레이아웃을 모르므로 **할당자의 지원이 필요하다.** 예를 들어 **같은 크기 객체들을 세그먼트로 묶어** 할당하도록 배치할 수 있다. 그러면 객체 레이아웃 지식 없이도 그 영역을 스캔할 수 있다 — 크기를 알고, 객체 경계는 세그먼트 객체 크기의 단순 배수로 정의되기 때문이다.

많은 언어에서 할당자를 언어(라이브러리) 수준에서 교체할 수 있고, 그래서 **라이브러리로서의 보수적 가비지 컬렉션**이 인기를 얻었다. C와 C++에서 가장 널리 쓰이는 API 무관 구현이 **Boehm–Demers–Weiser GC(줄여서 Boehm GC)** 다. **Mono(오픈 소스 CLR 구현)도 2.8 버전(2010년)까지 이것을 썼다.** 2.8에서 도입된 **SGen 가비지 컬렉터**는 혼합 방식이다 — 스택과 레지스터는 여전히 보수적으로 스캔하지만, **힙 스캔은 런타임 타입 정보의 지원을 받는다.**

**정밀 가비지 컬렉터(Precise Garbage Collector)** 에서는 훨씬 단순하다. **컴파일러 그리고/또는 런타임이 Collector에게 객체의 메모리 레이아웃에 대한 완전한 정보를 제공한다.** 스택 크롤링(스택 위의 모든 객체 루트 열거)도 지원할 수 있다. 이 경우 추측이 필요 없다. 잘 정의된 루트에서 출발해 **객체 단위로 메모리를 스캔**한다. 객체의 시작을 가리키는 메모리 주소가 주어지면(또는 객체 내부를 가리키는 **내부 포인터(interior pointer)** 와 그것을 제대로 해석할 지식이 주어지면), Collector는 나가는 참조(포인터)가 어디에 놓여 있는지 **그냥 안다.** 그래서 그래프 순회 중 재귀적으로 따라갈 수 있다.

**.NET은 정밀 가비지 컬렉터를 쓴다.**

| 항목 | 보수적 GC | 정밀 GC |
|---|---|---|
| **포인터 식별** | **추측한다.** 워드가 유효한 힙 주소를 가리키면 포인터로 간주 | **안다.** 컴파일러·런타임이 타입 레이아웃과 GC 정보를 제공 |
| **런타임 지원** | 불필요 | **필수** |
| **부정확성** | 있다. 우연히 포인터처럼 보이는 값이 메모리를 붙잡는다 | 없다 |
| **객체 이동(컴팩션)** | **불가능**(단순한 접근에서) | **가능** |
| **단편화 해소** | 어렵다. Sweep + 자유 리스트에 의존 | Compact로 해소 가능 |
| **할당자 제약** | 있다(동일 크기 세그먼트 등) | 적다. 범프 포인터 할당 가능 |
| **대표 구현** | Boehm GC, Mono ~2.8 | **.NET**, JVM, Mono 2.8+(혼합) |

> **⚠️ .NET이 정밀 GC여야만 하는 이유**
>
> 이것은 취향의 문제가 아니라 **필연**이다. .NET의 할당 경로는 **범프 포인터 할당**이고(63장), 그것이 성립하려면 힙이 조각나지 않아야 하며, 조각나지 않으려면 **살아남은 객체를 앞으로 밀어붙이는 컴팩션**이 가능해야 한다. 컴팩션은 **모든 참조를 정확히 찾아 새 주소로 갱신할 수 있어야** 가능하다. 즉 **정밀 GC → 컴팩션 가능 → 범프 포인터 할당 → 극도로 빠른 할당**이라는 사슬이다. 보수적 GC를 택했다면 .NET의 할당은 C의 `malloc`처럼 자유 리스트를 뒤지는 일이 됐을 것이고, 세대별 GC의 이점도 대부분 사라졌을 것이다. 이 사슬을 이해하면 62~64장의 설계가 전부 하나의 결정에서 파생됐음이 보인다.
>
> 이를 가능하게 하기 위해 CLR은 각 메서드마다 **GC 정보(GC info)** 를 만든다 — "이 명령 오프셋에서 어느 레지스터와 어느 스택 슬롯이 객체 참조를 담고 있는가"를 기술한 테이블이다. JIT이 이것을 생성하고, 스레드는 이 정보가 유효한 지점(**세이프 포인트**)에서만 멈출 수 있다. 이것이 64장에서 볼 "GC가 스레드를 아무 데서나 멈추지 못하는" 이유다.

> **📌 .NET 안에도 보수적 수집기 구현이 들어 있다**
>
> 흥미로운 사실이 하나 있다. **.NET에는 이미 보수적 수집기 구현이 내장돼 있고, 기본적으로 비활성화되어 있다.** 특정 상황(런타임 자신의 개발이나 진단)을 위한 것이지 일반 애플리케이션이 켤 스위치가 아니다.

> **📌 Boehm GC의 원자적 블록**
>
> Boehm GC를 비롯한 보수적 GC는 특별한 플래그(Boehm의 경우 `GC_MALLOC_ATOMIC`)를 붙여 블록이나 영역을 할당할 수 있다. 이 블록에 포인터가 없으니 스캔하지 말라고 Collector에게 알려주는 것이다. 그래서 **비트맵 같은 조밀한 이진 데이터를 이런 블록에 저장**하면 앞서 말한 오탐 문제를 줄일 수 있다.

### Collect 단계 — Sweep와 Compact

추적 GC가 도달 가능한 객체를 찾고 나면 나머지 죽은 객체들의 메모리를 회수할 수 있다. Collect 단계는 여러 방식으로 설계할 수 있지만, **두 가지 주요 접근**을 구별해야 한다.

**Sweep(스윕)** 방식에서는 죽은 객체를 **나중에 재사용할 수 있는 자유 공간으로 표시할 뿐**이다. 예시 구현에서는 메모리 블록의 단일 비트 마크만 바꾸면 되므로 매우 빠른 연산일 수 있다.

순진한 구현에서는 **할당할 때마다 메모리를 스캔**해 생성 중인 객체가 들어갈 만큼 큰 틈을 찾는다. 그러나 자명하지 않은 구현은 자유 메모리 블록 정보를 담는 자료 구조를 만들어 빠르게 찾아낸다 — 전형적으로 **자유 리스트(free-list)** 형태다. 이 자유 리스트는 **인접한 자유 블록을 병합할 만큼 똑똑해야 한다.** 더 나아가 다양한 크기 범위별로 자유 리스트를 여러 개 두기도 한다.

자유 리스트를 스캔하는 방식도 여럿이다. 가장 인기 있는 두 가지는 이렇다.

| 방식 | 동작 | 성질 |
|---|---|---|
| **최초 적합(first-fit)** | 적합한 자유 블록을 **처음 찾는 즉시** 스캔을 멈춘다 | **빠르다.** 대신 단편화가 커질 수 있다 |
| **최적 적합(best-fit)** | 자유 리스트 항목을 **항상 전부** 스캔해 요구 크기에 가장 잘 맞는 것을 찾는다 | 느리다. 대신 단편화가 적다 |

Sweep은 꽤 빠르지만 **큰 단점이 하나 있다 — 결국 메모리 단편화로 이어진다.** 객체가 생성되고 파괴되면서 힙에 작은 자유 틈들이 생긴다. 총량으로는 충분한 자유 메모리가 있는데도 **새 객체를 위한 연속된 자유 공간이 하나도 없는** 상황이 벌어진다.

**Compact(컴팩트)** 방식에서는 **성능을 대가로 단편화를 제거한다.** 메모리 안에서 객체를 이동시켜야 하기 때문이다. 객체를 삭제한 뒤 생긴 틈을 줄이도록 객체들을 옮긴다. 두 가지 접근이 있다.

- **복사 컴팩션(Copying Compacting)** — 수집이 일어날 때마다 살아 있는(도달 가능한) 객체 전부를 **다른 메모리 영역으로 옮긴다(복사한다).** 살아 있는 객체를 필요 없는 것을 건너뛰며 하나씩 이어 복사하는 것만으로 컴팩션이 된다. 당연히 모든 살아 있는 객체를 왔다 갔다 복사해야 하므로 **높은 메모리 트래픽**을 유발한다. 또한 **필요한 것의 두 배 메모리를 유지**해야 하므로 메모리 오버헤드도 크다. 그럼에도 효과적으로 쓸 수 있다 — **프로세스 메모리 전체가 아니라 특정한 작은 메모리 영역에만** 쓰면 된다. 일부 JVM 구현이 작은 메모리 영역에 이 방식을 쓴다.
- **제자리 컴팩션(In-Place Compacting)** — 객체들을 **서로를 향해 밀어** 사이의 틈을 없앤다. 가장 직관적인 해법이고, 레고 블록을 밀 때 하는 것과 정확히 같다. 구현 관점에서는 자명하지 않지만 할 수 있다. **어려운 점은 서로를 덮어쓰지 않으면서 객체들을 상대적으로 옮기는 방법을 알아내는 것**이고, 성능을 위해 임시 버퍼 없이 하려 하면 더 까다로워진다. **.NET이 정확히 이 접근을 쓴다** — 최적화를 위한 아주 영리한 자료 구조와 함께. 그 답은 64장에 있다.

세 단계를 한 그림으로 보면 이렇다.

```text
 [0] 수집 직전 — 힙에 객체 A~G가 있고 C, F는 도달 불가능

     ┌────┬────┬────┬────┬────┬────┬────┐
     │ A  │ B  │ C  │ D  │ E  │ F  │ G  │
     └────┴────┴────┴────┴────┴────┴────┘

 [1] MARK — 루트에서 그래프를 순회해 도달 가능한 것을 표시

     ┌────┬────┬────┬────┬────┬────┬────┐
     │ ■A │ ■B │ □C │ ■D │ ■E │ □F │ ■G │
     └────┴────┴────┴────┴────┴────┴────┘
       마크됨      미마크          미마크

 [2a] SWEEP — 마크 안 된 자리를 자유 공간으로 표시하고 자유 리스트에 넣는다
      객체는 움직이지 않는다. 틈이 남는다 → 단편화

     ┌────┬────┬────┬────┬────┬────┬────┐
     │ A  │ B  │////│ D  │ E  │////│ G  │
     └────┴────┴──┬─┴────┴────┴──┬─┴────┘
                  └──── 자유 리스트 ────┘
                  head → [gap1] → [gap2] → null

 [2b] COMPACT — 살아남은 객체를 앞으로 밀어붙이고 참조를 전부 갱신한다
      틈이 사라진다 → 뒤쪽이 통째로 연속된 자유 공간이 된다

     ┌────┬────┬────┬────┬────┬─────────────┐
     │ A  │ B  │ D  │ E  │ G  │  연속 자유   │
     └────┴────┴────┴────┴────┴─────────────┘
                                    ↑
                            할당 포인터가 여기 있으면
                            다음 할당은 "포인터를 미는 것"뿐이다
```

**.NET은 이 두 가지를 상황에 따라 모두 쓴다.** 어떤 세대에서 언제 컴팩션을 하고 언제 스윕만 하는지, 그리고 대형 객체 힙에서는 왜 기본적으로 컴팩션하지 않는지가 62장과 64장의 주제다.

### 추적 GC 총평

| 항목 | 참조 카운팅 | 추적 수집기 |
|---|---|---|
| **생존성 근사 방식** | 지역적(참조 개수) | 전역적(루트에서의 도달 가능성) |
| **순환 참조** | **회수 못 함**(개선 없이는) | **문제 없음** |
| **해제 시점** | **결정적**(카운터가 0이 되는 순간) | **비결정적**(도달 불가능 판정 후 언젠가) |
| **Mutator 오버헤드** | **크다.** 모든 대입이 카운터를 갱신 | **작다.** 배리어 비용만 |
| **처리량(throughput)** | 대입이 잦으면 낮다 | 대체로 높다 |
| **일시 정지(pause)** | 원칙적으로 없다. 단, 큰 그래프의 연쇄 해제가 순간적 정지를 만든다 | **있다.** 비동시 마크 단계는 전 스레드 중단(stop-the-world) |
| **메모리 오버헤드** | 낮다(즉시 회수) | **높다**(죽은 객체가 남아 있다) |
| **객체당 공간 오버헤드** | 카운터 필드 필요 | 마크 비트(대개 헤더에 흡수) |
| **런타임 지원** | **불필요.** 라이브러리로 구현 가능 | **필수** |
| **구현 복잡도** | 낮다 | **높다** |
| **스레드 안전성 비용** | 카운터마다 원자적 연산 | 배리어와 세이프 포인트 |
| **대표 사용처** | C++ `shared_ptr`, Swift ARC, Rust `Rc`/`Arc` | **.NET**, JVM |

추적 GC의 장단점을 정리하면 이렇다.

**장점**

- **개발자에게 완전히 투명하다.** 더 이상 필요 없는 객체 해제를 걱정할 필요 없이 메모리가 무한한 것처럼 추상화된다.
- **순환 참조에 문제가 없다.**
- **Mutator에 큰 오버헤드가 없다.**

**단점**

- **구현이 더 복잡하다.**
- **객체가 비결정적으로 해제된다** — 도달 불가능해진 뒤 회수되기까지 예측 불가능한 시간이 걸린다.
- **Mark 단계를 위해 모든 애플리케이션 스레드를 중단해야 한다**(이른바 stop-the-world) — 단, 비동시 방식일 때만.
- **더 큰 메모리 제약** — 죽은 객체가 즉시 회수되지 않으므로 메모리 사용량이 늘어난다.

주로 **첫 번째 장점 때문에** 추적 GC는 여러 런타임과 환경에서 매우 인기 있다.

>

Python이나 Ruby의 GC가 더 나은가? 애초에 "더 나은 GC"가 무슨 뜻인가? **가비지 컬렉션 알고리즘 비교의 첫 번째이자 가장 중요한 규칙은, 모든 비교가 근본부터 매우 모호하다는 것이다.** GC는 자기 런타임 환경과 강하게 결합되어 있어 따로 떼어 테스트하는 것이 사실상 불가능하다. **처리량(Throughput), 지연 시간(Latency), 일시 정지 시간(Pause Time)** 같은 척도를 쓸 수 있지만, 그 측정은 GC만이 아니라 **런타임 전체의 맥락에서** 이뤄진다. 할당 패턴, 내부 객체 풀링, 추가 컴파일 같은 숨은 메커니즘이 GC 오버헤드를 줄이도록 도입되어 있을 수 있다. 게다가 각 GC에는 특정 워크로드에서 더 잘 동작하게 하는 미세 조정이 잔뜩 있다. 어떤 것은 대화형 환경에서 빠르게 응답하도록, 어떤 것은 거대한 데이터 집합을 처리하도록 최적화된다. 하드웨어 구성(프로세서 아키텍처, 코어 수, 메모리 아키텍처)에 따라서도 다르게 동작한다. **"완벽한 해법은 없다."**

## 이 장의 요약

- **데이터가 놓일 자리는 네 곳뿐이다** — 레지스터, 정적 영역, 스택, 힙. 앞의 셋은 크기가 컴파일 시점에 정해지고, 힙만 실행 시점에 정해진다. 그래서 힙만이 포인터를 필요로 하고, 힙만이 단편화된다.
- **스택은 활성화 프레임이 쌓이는 구조**다. 호출 시 인자·반환 주소·지역 변수가 프레임으로 쌓이고 SP가 내려가며, 반환 시 **SP를 올리는 것만으로** 해제된다. 데이터는 지워지지 않고 남는다. .NET 스레드 스택 기본 크기는 32비트 1 MB, 64비트 4 MB다.
- **.NET과 JVM은 스택 머신이다.** 레지스터 개수에 의존하지 않아 하드웨어를 추상화하기 좋고 코드 밀도가 높기 때문이다. 실제 실행은 레지스터 머신인 x86/ARM 위에서 이뤄진다.
- **가상 메모리는 4 kB 페이지와 4단계 페이지 디렉터리로 구현된다.** 변환은 TLB로 캐시되고, TLB 미스는 전체 디렉터리 워크를 유발한다. L1 캐시가 가상 주소로 동작하므로 **페이지 전환이 잦으면 캐시까지 무효화된다.**
- **Windows는 예약/커밋 2단계, Linux는 지연 할당**이다. CLR은 Windows에서 `VirtualAlloc`을, Linux에서 익명 프라이빗 `mmap`을 쓰며, Linux에서 "예약"은 `PROT_NONE` 트릭으로 흉내 낸다. Windows의 쓰기 감시(`GetWriteWatch`)에 대응하는 Linux 시스템 콜이 없어 .NET Core는 이를 **쓰기 배리어**로 옮겼다.
- **캐시 계층의 지연 차이는 극적이다.** Haswell 기준 L1 < 2.0 ns, L2 4.8 ns, L3 14.4 ns, 주 메모리 71.4 ns, HDD 150,000 ns. **L1은 RAM보다 30배 이상 빠르다.**
- **캐시 라인은 64바이트이고, 이보다 적게 읽거나 쓸 수 없다.** 1비트를 읽어도 64바이트가 채워진다. 행 우선 대신 열 우선으로 배열을 순회하면 같은 코드가 **최대 7.7배 느려진다.** 배열 인덱스를 캐시 라인 하나만큼 미는 것만으로 멀티스레드 벤치마크가 **5.0초에서 0.7초로** 바뀐다.
- **참조 카운팅은 결정적 해제를 주지만 순환 참조를 못 풀고 모든 대입에 오버헤드를 얹는다.** 추적 수집기는 전역 도달 가능성으로 순환을 풀고 Mutator 오버헤드가 작지만, **비결정적 해제·일시 정지·메모리 오버헤드**를 대가로 낸다. .NET은 후자를 택했다.
- **.NET은 정밀 GC다.** 컴파일러와 런타임이 완전한 타입 레이아웃과 GC 정보를 제공하므로 포인터를 추측할 필요가 없고, 따라서 **객체를 이동(컴팩션)할 수 있으며**, 그 덕에 **범프 포인터 할당**이 성립한다. 보수적 GC(Boehm GC, Mono ~2.8)를 택했다면 이 사슬 전체가 불가능했다.
- **생존성은 알 수 없고 도달 가능성만 알 수 있다.** 이 어긋남이 관리 환경 메모리 누수의 본질이다 — 쓰지 않을 객체를 여전히 참조하고 있는 것.

## 연습 문제

1. `int[,] tab = new int[5000, 5000]`을 행 우선과 열 우선으로 각각 채우는 코드를 작성하고 `Stopwatch`로 시간을 재라. 배율이 본문의 수치(PC에서 7.7배)와 어떻게 다른가? `int` 대신 `byte`, `long`, 그리고 64바이트짜리 구조체로 바꿔가며 배율이 어떻게 변하는지 확인하고 캐시 라인 크기로 설명하라.
2. 61.4절의 `OneLineStruct` 배열 순차 읽기 벤치마크를 BenchmarkDotNet으로 작성하되 배열 크기를 16 KiB부터 64 MiB까지 두 배씩 늘려가며 원소당 평균 시간을 표로 만들어라. 성능이 꺾이는 지점이 자기 CPU의 L2·L3 크기와 일치하는지 확인하라(`wmic cpu get L2CacheSize,L3CacheSize` 또는 `lscpu`).
3. 61.5절의 거짓 공유 벤치마크를 `offset`/`gap` 조합 `(1,0)`, `(16,0)`, `(16,16)`으로 실행하고 시간을 비교하라. 그다음 `int` 대신 `long`을 쓰면 필요한 `offset`이 얼마로 바뀌어야 하는지 계산하고 실측으로 확인하라.
4. 콘솔 앱에서 `GC.GetTotalMemory(false)`, `Process.GetCurrentProcess().PrivateMemorySize64`, `WorkingSet64`, `VirtualMemorySize64`를 동시에 출력하라. 큰 배열을 할당한 직후와 `GC.Collect()` 직후에 네 값이 각각 어떻게 변하는지 표로 정리하고, 61.3절의 집합 관계 그림으로 설명하라.
5. Linux에서 같은 .NET 프로그램을 실행하고 `top`의 `VIRT`, `RES`, `SHR`, `DATA` 값을 4번 문제의 값들과 대응시켜라. 어느 값이 Windows의 무엇에 해당하는가?
6. 순환 참조를 이루는 두 객체(`A.Next = B; B.Prev = A;`)를 만들고 루트 참조를 모두 끊은 뒤 `WeakReference`로 두 객체가 실제로 수집되는지 확인하라. 참조 카운팅 방식이었다면 결과가 어떻게 달랐을지 설명하라.
7. `NativeMemory.AlignedAlloc`으로 64바이트 정렬된 버퍼와 `NativeMemory.Alloc`으로 정렬되지 않은 버퍼를 각각 만들고, 두 주소를 16진수로 출력해 하위 6비트를 비교하라. 그다음 두 버퍼에 대해 같은 순차 쓰기 루프를 돌려 시간 차이를 측정하고, 차이가 없다면 왜 없는지 생각해보라.
