## 80.1 단위 테스트 기초 (xUnit)와 테스트 가능한 설계

### 버그는 늦게 찾을수록 비싸다

코드의 버그를 고치는 일에는 비용이 든다. 그리고 그 비용은 버그가 발견되는 시점이 늦어질수록 **가파르게** 올라간다. 개발자가 자기 머신에서 30초 만에 잡는 버그와, 고객사 프로덕션에서 장애 보고서로 올라온 버그는 같은 한 줄짜리 오타여도 비용이 세 자릿수 배 차이가 난다.

단위 테스트(unit test)가 존재하는 이유가 정확히 이것이다. 단위 테스트는 코드 조각들이 서로 통합되기 전에, 사용자 인수 테스터가 보기 전에, 아주 작은 단위 하나를 격리해서 검증한다. 어떤 개발자들은 코드를 쓰기 *전에* 테스트를 먼저 쓰는 원칙을 따르는데 이것이 **테스트 주도 개발(TDD, Test-Driven Development)** 이다.

### 테스트의 종류

단위 테스트는 여러 테스트 유형 중 하나일 뿐이다.

| 유형 | 대상 | 설명 |
|---|---|---|
| **단위(unit)** | 메서드·함수 하나 | 가장 작은 코드 단위를 테스트한다. 의존성은 필요하면 목(mock)으로 대체해 격리한다. 각 단위마다 여러 테스트가 필요하다 — 전형적인 입력, 경계를 확인하는 극단값, 예외 처리를 확인하는 의도적으로 잘못된 입력 |
| **통합(integration)** | 여러 컴포넌트의 조합 | 작은 단위들과 큰 컴포넌트들이 하나의 소프트웨어로 함께 동작하는지 확인한다. 소스 코드가 없는 외부 컴포넌트와의 통합을 포함하기도 한다 |
| **시스템(system)** | 실행 환경 전체 | 소프트웨어가 실제로 돌아갈 환경 전체를 테스트한다 |
| **성능(performance)** | 응답 시간·처리량 | 예: 데이터로 채워진 웹 페이지를 20밀리초 안에 반환해야 한다 |
| **부하(load)** | 동시 처리량 | 요구 성능을 유지하면서 동시에 몇 개의 요청을 처리할 수 있는지. 예: 동시 접속자 10,000명 |
| **사용자 인수(user acceptance)** | 실사용 시나리오 | 사용자가 이 소프트웨어로 자기 일을 무리 없이 끝낼 수 있는지 |

이 장의 무게 중심은 단위 테스트와 통합 테스트에 있다. 성능 테스트는 80.6절에서, 부하 테스트는 이 책의 범위 밖이다.

> **📌 왜 xUnit인가**
>
> .NET에는 세 가지 주요 테스트 프레임워크가 있다. Microsoft의 **MSTest**, **NUnit**, 그리고 **xUnit.net**이다. 셋 다 기본적으로 같은 일을 한다.
>
> xUnit은 NUnit을 만들었던 팀이 "우리가 전에 저질렀다고 생각하는 실수들"을 고쳐서 다시 만든 프레임워크다. 확장성이 더 좋고 커뮤니티 지원이 넓다. 이 책은 xUnit을 쓰지만, 이 장의 설계 논의는 프레임워크와 무관하다 — 테스트 가능한 코드는 어떤 러너에서도 테스트 가능하다.

### 테스트하기 어려운 코드의 공통 징후

여기서 이 장 전체를 관통하는 명제를 먼저 박아 두자.

> **테스트 가능성은 목표가 아니라 결과다.** 테스트를 쓰기 어렵다면, 그것은 테스트 프레임워크가 부족해서가 아니라 **코드가 자기 협력자를 스스로 골랐기 때문**이다.

테스트를 쓰려고 앉았을 때 손이 멈추게 만드는 코드에는 반복되는 패턴이 있다. 이 목록은 코드 리뷰 체크리스트로 그대로 써도 된다.

| 징후 | 왜 테스트를 막는가 | 방향 |
|---|---|---|
| **정적 가변 상태** (`static` 필드, 싱글턴, `static` 캐시) | 테스트 간에 상태가 새어 나간다. 테스트 순서에 따라 결과가 바뀌고, 병렬 실행에서 무작위로 깨진다 | 인스턴스 상태로 내리거나, 명시적으로 리셋 가능한 경계를 준다 (80.2절) |
| **협력자를 `new`로 직접 생성** | 대체할 지점이 없다. `new SqlConnection(...)`이 메서드 안에 있으면 테스트는 DB를 켜야 한다 | 생성 책임을 밖으로 밀어낸다 — 매개변수, 생성자, 팩터리 |
| **`DateTime.Now` / `DateTime.UtcNow` 직접 호출** | 시간이 입력인데 그 입력을 통제할 수 없다. "월말에만 깨지는 테스트"의 근원 | `TimeProvider`를 주입한다 ※.NET 8 (80.4절, 37.9절) |
| **`Random`을 내부에서 생성** | 결과가 실행마다 달라 어서션을 쓸 수 없다 | 시드를 주입하거나 난수원 자체를 주입한다 (80.4절) |
| **파일 시스템·네트워크 직접 접근** | 테스트가 환경에 묶인다. CI 러너에 그 경로가 없다 | 스트림 수준으로 추상화하거나 파일 시스템 추상화를 쓴다 (80.4절) |
| **`sealed` + 비가상 메서드로만 된 협력자 타입** | 상속으로도 인터페이스로도 대체할 수 없다 | 협력자를 인터페이스 뒤에 두거나, 그 타입 자체를 얇은 어댑터로 감싼다 |
| **거대한 생성자** (인수 10개, 또는 생성자에서 I/O) | 테스트마다 열 개를 다 채워야 하고, 인스턴스를 만드는 것만으로 DB에 붙는다 | 책임을 쪼갠다. 생성자는 **대입만** 한다 (79.5절) |
| **`void`를 반환하고 부작용만 남기는 메서드** | 관찰할 반환값이 없어 목 검증에만 의존하게 된다 | 결과를 값으로 반환하고 부작용은 경계로 밀어낸다 |
| **`private`에 로직이 몰려 있고 `public`은 한 개** | 진입점 하나로 모든 분기를 통과시켜야 해 테스트가 거대해진다 | 로직 덩어리를 별도 타입으로 승격시킨다 |
| **환경 변수·구성 파일을 코드 안에서 읽음** | 테스트가 프로세스 전역 상태에 의존한다 | 구성 값을 옵션 객체로 주입받는다 |

> **💡 "테스트를 쓰기 어렵다"는 신호를 설계 피드백으로 읽어라**
>
> 초보 팀이 가장 흔히 저지르는 실수는 이 신호를 **도구 문제**로 오해하는 것이다. `DateTime.Now`를 통제할 수 없으니 시간까지 가로챌 수 있는 강력한 목킹 도구를 사 오고, 정적 상태를 리셋할 수 없으니 리플렉션으로 `private static` 필드를 뒤지는 헬퍼를 만든다.
>
> 그렇게 하면 테스트는 통과한다. 그리고 **설계는 영구히 고정된다.** 리플렉션으로 고정된 코드는 리팩터링할 때마다 테스트가 깨지므로 아무도 손대지 않게 된다.
>
> 반대로 읽어라. 테스트가 어렵다는 것은 그 코드가 **너무 많은 것을 스스로 결정하고 있다**는 뜻이다. 결정을 호출자에게 돌려주면 테스트는 저절로 쉬워진다.

### 테스트할 클래스 라이브러리 만들기

먼저 테스트 대상이 필요하다. 클래스 라이브러리 프로젝트를 만들고, 콘솔 앱 프로젝트와 분리한다.

```text
dotnet new classlib -o CalculatorLib && dotnet sln add CalculatorLib
```

`Class1.cs`를 `Calculator.cs`로 바꾸고 다음과 같이 쓴다. **의도적으로 버그를 심어 둔다.**

```csharp
namespace CalculatorLib;

public class Calculator
{
    public double Add(double a, double b)
    {
        return a * b;   // 버그: 곱하고 있다
    }
}
```

이제 xUnit 테스트 프로젝트를 만든다.

```text
dotnet new xunit -o CalculatorLibUnitTests
dotnet sln add CalculatorLibUnitTests
dotnet add CalculatorLibUnitTests reference CalculatorLib   # 테스트 대상 참조
```

`dotnet new xunit`이 만들어 주는 `.csproj`는 대략 이런 모습이다.

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>net8.0</TargetFramework>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
    <IsPackable>false</IsPackable>
  </PropertyGroup>
  <ItemGroup>
    <PackageReference Include="Microsoft.NET.Test.Sdk" Version="17.*" />
    <PackageReference Include="xunit" Version="2.*" />
    <PackageReference Include="xunit.runner.visualstudio" Version="2.*" />
    <PackageReference Include="coverlet.collector" Version="6.*" />
  </ItemGroup>
  <ItemGroup>
    <ProjectReference Include="..\CalculatorLib\CalculatorLib.csproj" />
  </ItemGroup>
</Project>
```

네 개의 패키지가 각각 무슨 일을 하는지 아는 것이 중요하다. 하나가 빠지면 "테스트가 발견되지 않음"이라는 아무 정보 없는 실패를 만난다.

| 패키지 | 역할 | 빠지면 |
|---|---|---|
| `Microsoft.NET.Test.Sdk` | VSTest 플랫폼 진입점. `dotnet test`가 이 프로젝트를 테스트 프로젝트로 인식하게 하는 근거 | `dotnet test`가 아무 테스트도 실행하지 않는다 |
| `xunit` | 테스트 프레임워크 본체. `[Fact]`, `[Theory]`, `Assert` 제공 | 컴파일 자체가 안 된다 |
| `xunit.runner.visualstudio` | xUnit 테스트를 VSTest 플랫폼에 노출하는 **어댑터** | 프로젝트는 인식되지만 테스트가 0개로 보고된다 |
| `coverlet.collector` | 코드 커버리지 수집기(`--collect:"XPlat Code Coverage"`) | 커버리지 수집만 안 된다. 테스트는 정상 동작 |

> **⚠️ "0개의 테스트가 실행되었습니다"의 원인 대부분은 어댑터 누락이다**
>
> 기존 클래스 라이브러리에 `xunit` 패키지만 추가해서 테스트 프로젝트로 승격시키려는 시도는 거의 항상 여기서 막힌다. `xunit` 하나로는 테스트가 **컴파일되지만 실행되지 않는다.** VSTest 플랫폼은 어댑터(`xunit.runner.visualstudio`)를 통해서만 xUnit 테스트를 볼 수 있다.
>
> 두 번째로 흔한 원인은 `<IsTestProject>` 또는 `Microsoft.NET.Test.Sdk` 누락이고, 세 번째는 **테스트 클래스가 `public`이 아닌 경우**다. xUnit은 `public` 클래스의 `public` 메서드만 발견한다.

> **📌 ※xUnit v3**
>
> xUnit은 v3에서 패키지 이름(`xunit.v3`)과 실행 모델을 바꿨다. v3 테스트 프로젝트는 VSTest 호스트에 얹히는 라이브러리가 아니라 **스스로 실행되는 콘솔 애플리케이션**이다(`OutputType`이 `Exe`가 된다). 이 장의 코드는 v2 기준으로 쓰였고, `[Fact]`·`[Theory]`·`Assert`·픽스처 같은 표면 API는 v3에서도 거의 그대로다. 마이그레이션을 고려한다면 프로젝트 파일과 러너 설정이 달라진다는 점만 먼저 확인하라.

### 테스트를 구성하는 세 부분 — AAA

잘 쓴 단위 테스트는 세 부분으로 나뉜다.

- **Arrange(준비)** — 입력과 출력을 담을 변수를 선언·초기화하고, 테스트 대상을 만든다.
- **Act(실행)** — 테스트하려는 단위를 실행한다. 우리 경우엔 메서드 호출이다.
- **Assert(단언)** — 출력에 대해 하나 이상의 단언을 한다. 단언은 *"이것이 참이 아니라면 테스트가 실패한 것"* 이라는 믿음의 표현이다. 2와 2를 더하면 4가 나오리라는 것 같은.

`UnitTest1.cs`를 `CalculatorUnitTests.cs`로 바꾸고 다음과 같이 쓴다.

```csharp
using CalculatorLib; // Calculator를 쓰기 위해.

namespace CalculatorLibUnitTests;

public class CalculatorUnitTests
{
    [Fact]
    public void TestAdding2And2()
    {
        // Arrange: 입력과 테스트 대상을 준비한다.
        double a = 2;
        double b = 2;
        double expected = 4;
        Calculator calc = new();

        // Act: 테스트할 함수를 실행한다.
        double actual = calc.Add(a, b);

        // Assert: 기대값과 실제값을 비교하는 단언을 한다.
        Assert.Equal(expected, actual);
    }

    [Fact]
    public void TestAdding2And3()   // 같은 구조로 2 + 3 = 5를 검증한다.
    {
        Calculator calc = new();
        Assert.Equal(5d, calc.Add(2d, 3d));
    }
}
```

실행해 보자.

```text
dotnet test
```

두 테스트가 실행되고 **하나는 통과, 하나는 실패**한다. `2 * 2`와 `2 + 2`는 둘 다 4이기 때문에 첫 번째 테스트는 버그를 통과시킨다. 두 번째가 잡아낸다.

이 사소한 결과가 단위 테스트에 대한 가장 중요한 교훈을 담고 있다. **테스트 하나로는 아무것도 증명하지 못한다.** 우연히 맞는 입력을 골랐을 뿐일 수 있다. 그래서 "전형적인 입력 + 경계값 + 잘못된 입력"이라는 세 축이 필요한 것이다.

이제 `Add`를 `a + b`로 고치고 다시 실행하면 둘 다 통과한다.

> **💡 실패하는 것을 먼저 보라**
>
> 새 테스트를 썼을 때 그것이 **한 번도 실패하는 것을 보지 않았다면**, 그 테스트는 아무것도 검증하지 않을 가능성이 상당히 있다. 어서션을 빠뜨렸거나, 잘못된 객체를 검사하거나, 예외가 삼켜지고 있을 수 있다.
>
> 실무 습관: 새 테스트를 통과시키기 전에 **프로덕션 코드를 일부러 한 글자 망가뜨려서** 테스트가 빨간불이 되는지 확인한다. 이건 TDD를 하지 않는 팀에게도 유효한 30초짜리 보험이다.

### 테스트 이름 짓기

테스트 이름은 실패 보고서에서 **가장 먼저 읽히는 한 줄**이다. CI 로그에서 `TestAdding2And3` 같은 이름을 봤을 때 무엇이 왜 깨졌는지 즉시 알 수 있어야 한다.

널리 쓰이는 규약 세 가지다.

| 규약 | 형태 | 예 |
|---|---|---|
| **MethodName_Scenario_ExpectedBehavior** | 언더스코어 3분할 | `Withdraw_AmountExceedsBalance_ThrowsInvalidOperationException` |
| **Should 문장형** | 서술문 | `Should_ThrowInvalidOperation_When_AmountExceedsBalance` |
| **Given/When/Then** | BDD 스타일 | `GivenEmptyCart_WhenAddingItem_ThenTotalIsItemPrice` |

어느 것을 고르든 상관없다. **한 프로젝트 안에서 섞지 않는 것**이 유일한 규칙이다. 이 장은 첫 번째를 쓴다.

```csharp
[Fact]
public void Withdraw_AmountIsZero_ThrowsArgumentOutOfRangeException()
{
    Account account = new(balance: 100m);

    var ex = Assert.Throws<ArgumentOutOfRangeException>(() => account.Withdraw(0m));

    Assert.Equal("amount", ex.ParamName);
}
```

`Assert.Throws<T>`는 잡은 예외를 **반환한다.** 예외 타입만 확인하고 끝내지 말고 `ParamName`이나 메시지의 핵심 조각까지 확인하면, "다른 이유로 같은 예외가 나서 테스트가 우연히 통과하는" 사고를 막을 수 있다.

> **⚠️ `Assert.Throws<T>`는 정확한 타입을 요구한다**
>
> `Assert.Throws<ArgumentException>(...)`는 `ArgumentNullException`이 던져지면 **실패한다.** `ArgumentNullException`은 `ArgumentException`의 파생 타입이지만 xUnit의 `Assert.Throws<T>`는 **정확히 그 타입**일 것을 요구한다.
>
> 파생 타입까지 허용하려면 `Assert.ThrowsAny<T>`를 써야 한다. 32.4절에서 본 예외 계층을 그대로 기대하고 있다가 여기서 당황하는 경우가 많다.
>
> 그리고 이것은 xUnit의 의도적 설계다 — 예외 타입 단정은 정확해야 회귀를 잡는다.

### `[Fact]`와 `[Theory]`

`[Fact]`는 "항상 참인 사실"이다. 매개변수를 받지 않는다.

`[Theory]`는 "이 데이터들에 대해 참인 이론"이다. 매개변수를 받고, 데이터 소스 특성이 값을 공급한다.

```csharp
public class CalculatorTheoryTests
{
    [Theory]  // 각 InlineData가 독립된 테스트 케이스가 된다
    [InlineData(2, 2, 4)]
    [InlineData(2, 3, 5)]
    [InlineData(-1, 1, 0)]
    [InlineData(double.MaxValue, double.MaxValue, double.PositiveInfinity)]
    public void Add_VariousInputs_ReturnsSum(double a, double b, double expected)
    {
        Calculator calc = new();

        double actual = calc.Add(a, b);

        Assert.Equal(expected, actual);
    }
}
```

`[InlineData]` 하나가 **독립된 테스트 케이스 하나**가 된다. 세 번째가 실패해도 나머지 넷은 실행되고, 테스트 탐색기에는 다섯 줄이 따로 보인다. 이것이 `foreach`로 배열을 돌면서 다섯 번 `Assert`하는 것과 결정적으로 다른 점이다 — 루프 안에서는 **첫 실패에서 멈추고**, 어느 입력이 문제였는지 이름으로 알 수 없다.

`[InlineData]`는 특성 인수이므로 **컴파일 타임 상수**만 담을 수 있다(79.2절에서 `const`의 제약을 본 그대로다). `decimal`, 배열, 사용자 정의 객체를 넘기려면 `[MemberData]`를 쓴다.

```csharp
public class OrderTests
{
    public static IEnumerable<object[]> DiscountCases()
    {   // { 총액, 할인율, 기대값 }
        yield return new object[] { 100m, 0, 100m };
        yield return new object[] { 100m, 10, 90m };
    }
    [Theory]
    [MemberData(nameof(DiscountCases))]
    public void ApplyDiscount_ValidPercent_ReturnsDiscountedTotal(
        decimal total, int percent, decimal expected)
    {
        Assert.Equal(expected, Order.ApplyDiscount(total, percent));
    }
}
```

`[MemberData]`가 가리키는 멤버는 **`public static`** 이어야 하고 `IEnumerable<object[]>`를 반환해야 한다. `object[]`는 타입 안전하지 않아서 인수 순서를 틀려도 컴파일러가 못 잡는다. xUnit은 이를 위해 타입 안전한 컨테이너를 제공한다.

```csharp
public static TheoryData<decimal, int, decimal> DiscountCases() =>
    new() { { 100m, 0, 100m }, { 100m, 10, 90m }, { 100m, 100, 0m } };
```

`TheoryData<T1, T2, T3>`는 `IEnumerable<object[]>`를 구현하면서 요소 타입을 제네릭으로 고정한다. 인수 개수나 타입이 틀리면 **컴파일 오류**가 난다. `[MemberData]`를 쓴다면 기본으로 이것을 쓰는 편이 낫다.

세 번째 방식은 `[ClassData]`다. `TheoryData<T>`를 상속한 클래스를 만들고 `[ClassData(typeof(InvalidAccountNames))]`로 지정한다. 데이터 생성 로직이 복잡하거나 **여러 테스트 클래스가 같은 데이터 집합을 공유**해야 할 때 쓴다.

| 데이터 소스 | 담을 수 있는 것 | 타입 안전성 | 쓸 자리 |
|---|---|---|---|
| `[InlineData]` | 컴파일 타임 상수 (`int`, `string`, `bool`, `typeof`, ...) | 컴파일러가 시그니처와 대조 | 케이스 2~8개, 값이 단순할 때 |
| `[MemberData]` + `IEnumerable<object[]>` | 무엇이든 | **없음** — 런타임에 터진다 | 레거시 코드에서만 |
| `[MemberData]` + `TheoryData<...>` | 무엇이든 | 제네릭으로 고정 | **기본 선택** |
| `[ClassData]` | 무엇이든 | `TheoryData` 상속 시 고정 | 여러 클래스가 데이터를 공유할 때 |

> **⚠️ `[Theory]` 데이터가 가변 객체면 테스트가 서로를 오염시킨다**
>
> `[MemberData]`가 제공하는 객체 인스턴스는 여러 테스트 케이스에서 **같은 인스턴스**일 수 있다. `static readonly` 리스트를 데이터 소스로 두고 테스트가 그 리스트를 수정하면, 다음 케이스는 오염된 상태를 받는다. 게다가 xUnit은 기본적으로 테스트 컬렉션을 **병렬로** 실행하므로 실패가 무작위로 나타난다.
>
> 규칙: **데이터 소스는 매번 새 인스턴스를 만들어라.** `yield return new object[] { new Cart() }`이지 `yield return new object[] { SharedCart }`가 아니다.

> **⚠️ `[Theory]`인데 데이터 특성이 없으면 조용히 실패한다**
>
> `[Theory]`를 붙이고 `[InlineData]`를 잊으면, xUnit은 그 테스트를 "데이터가 없다"는 이유로 **실패**로 보고한다(통과가 아니다). 반대로 `[Fact]`를 붙인 메서드에 매개변수가 있어도 실패다.
>
> 더 위험한 쪽은 **특성을 아예 빠뜨린 `public` 메서드**다. 이건 테스트로 발견되지 않으므로 통과도 실패도 아닌 **존재하지 않는 테스트**가 된다. xUnit.net 분석기가 이 경우 `xUnit1013` 경고를 내므로, 테스트 프로젝트에서는 경고를 오류로 승격시키는 것이 좋다(79.13절).
>
> ```xml
> <PropertyGroup>
>   <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
> </PropertyGroup>
> ```

### `Assert` 카탈로그

`Assert.Equal`만 알아도 대부분은 굴러가지만, 적절한 단언을 고르면 **실패 메시지의 품질**이 달라진다. 이것이 80.7절의 주제와 곧바로 이어진다.

| 단언 | 용도 | 실패 메시지가 주는 정보 |
|---|---|---|
| `Assert.Equal(e, a)` | 값 동등성 | 기대값·실제값 둘 다 |
| `Assert.Equal(e, a, precision)` | `double`/`decimal` 자릿수 비교 | 반올림 자릿수 포함 |
| `Assert.Same(e, a)` | 참조 동일성 | 두 참조가 다르다는 사실 |
| `Assert.True(cond, msg)` | 임의 조건 | **`msg`를 안 주면 "Expected: True"뿐** |
| `Assert.Throws<T>(action)` | 정확한 예외 타입 | 실제로 던져진 타입 또는 "던지지 않음" |
| `Assert.ThrowsAny<T>(action)` | `T` 또는 파생 | 위와 같음 |
| `Assert.ThrowsAsync<T>(func)` | 비동기 예외 (80.3절) | 위와 같음 |
| `Assert.Contains(item, coll)` | 포함 여부 | 컬렉션 내용 일부 |
| `Assert.Collection(coll, insp...)` | 요소별 검사기 | **몇 번째 요소가 왜 틀렸는지** |
| `Assert.Empty(coll)` / `NotEmpty` | 비어 있음 | 실제 개수 |
| `Assert.IsType<T>(obj)` | 정확한 런타임 타입 | 실제 타입 이름 |
| `Assert.IsAssignableFrom<T>(obj)` | `T`로 대입 가능 | 실제 타입 이름 |
| `Assert.Raises<T>(...)` | 이벤트 발생 (78.10절) | 발생 여부와 인수 |

> **💡 `Assert.True(x == y)`는 최악의 단언이다**
>
> 실패했을 때 로그에 남는 것은 이게 전부다.
>
> ```text
> Assert.True() Failure
> Expected: True
> Actual:   False
> ```
>
> `x`가 뭐였는지, `y`가 뭐였는지 알 수 없다. 재현하려면 디버거를 붙여야 한다. **`Assert.Equal(y, x)`로 바꾸는 것만으로** 실패 메시지에 두 값이 다 찍힌다.
>
> 조건 단언이 정말로 필요하면 최소한 메시지를 넣어라. `Assert.True(cart.Total > 0, $"장바구니 합계가 0 이하다: {cart.Total}")`.

컬렉션 검증에서는 `Assert.Collection`이 압도적으로 낫다.

```csharp
Assert.Collection(CsvParser.Parse(" a , b ,c "),
    f => Assert.Equal("a", f),
    f => Assert.Equal("b", f),
    f => Assert.Equal("c", f));
```

요소 개수가 다르면 그것부터 보고하고, 두 번째 요소가 틀리면 "인덱스 1에서 실패"라고 알려 준다. `Assert.Equal(new[]{"a","b","c"}, fields)`는 배열 전체를 덤프할 뿐이다.

### 어서션 라이브러리를 쓸 것인가

`Assert.*` 대신 유창한(fluent) 문법을 제공하는 라이브러리들이 있다. 대표적으로 **FluentAssertions**와 **Shouldly**다.

```csharp
actual.Should().Be(4);                                    // FluentAssertions
order.Items.Should().HaveCount(3).And.OnlyHaveUniqueItems();

actual.ShouldBe(4);                                       // Shouldly
Should.Throw<ArgumentOutOfRangeException>(action);
```

가치는 문법의 미려함이 아니라 **실패 메시지**에 있다. 이들 라이브러리는 식 트리와 호출자 정보를 이용해 "무엇을 비교했는지"까지 메시지에 담는다.

> **⚠️ FluentAssertions는 8.0부터 라이선스가 바뀌었다**
>
> FluentAssertions는 오랫동안 Apache 2.0 라이선스의 무료 라이브러리였다. **8.0 버전부터 상용 개발에 유료 라이선스를 요구하는 조건으로 전환**되었다. 7.x 계열은 종전 라이선스로 남아 있다.
>
> 사내 정책상 이것이 문제가 된다면 선택지는 세 가지다 — 7.x에 고정하거나, **Shouldly**로 옮기거나, 아예 xUnit 내장 `Assert`만 쓰는 것이다. 커뮤니티 포크도 여럿 나와 있으나 각각 유지보수 상태가 다르므로 도입 전에 직접 확인해야 한다.
>
> 교훈은 라이브러리 선택 자체보다 넓다. **테스트 코드는 프로젝트에서 가장 많은 줄 수를 차지하게 되는 부분이고, 그만큼 어서션 라이브러리 교체 비용이 크다.** 도입 시점에 라이선스와 유지보수 상태를 확인해 두는 것이 나중에 수천 줄을 기계적으로 고치는 것보다 싸다.

### 생성자와 `IDisposable`이 Setup/Teardown인 이유

JUnit 계열에 익숙한 사람은 `[SetUp]` / `[TearDown]` 특성을 찾는다. xUnit에는 없다. 대신 **생성자와 `IDisposable`** 을 쓴다.

```csharp
public class OrderServiceTests : IDisposable
{
    private readonly TempDirectory _temp;
    private readonly OrderService _sut;   // sut = system under test
    public OrderServiceTests()          // Setup: 테스트 메서드마다 새로 실행된다.
    {
        _temp = new TempDirectory();
        _sut = new OrderService(_temp.Path);
    }

    public void Dispose() => _temp.Dispose();   // Teardown: 테스트 메서드마다 실행된다.

    [Fact] public void Save_NewOrder_WritesFile() { /* ... */ }
    [Fact] public void Save_DuplicateId_Throws() { /* ... */ }
}
```

여기서 핵심은 문법이 아니라 **xUnit이 테스트 메서드마다 테스트 클래스의 인스턴스를 새로 만든다**는 사실이다. 위 클래스에 테스트가 두 개 있으면 `OrderServiceTests` 인스턴스도 **두 개** 만들어진다. 생성자는 두 번, `Dispose`도 두 번 실행된다.

이 설계는 의도적이다.

- **테스트 격리가 언어 규칙으로 보장된다.** 인스턴스 필드는 테스트 간에 공유되지 않는다. `[SetUp]`을 잊어서 앞 테스트의 상태가 새어 나오는 사고가 구조적으로 불가능하다.
- **별도 특성을 배울 필요가 없다.** 생성자와 `Dispose`는 C# 개발자가 이미 아는 개념이다(33장).
- **`readonly` 필드를 쓸 수 있다.** 준비된 객체가 테스트 도중 바뀌지 않는다는 것을 컴파일러가 보장한다.

> **⚠️ `static` 필드는 이 격리를 그대로 무너뜨린다**
>
> 테스트 클래스의 `static` 필드는 인스턴스가 몇 개 만들어지든 **하나뿐**이다. 편의를 위해 `private static readonly HttpClient` 하나를 두는 순간 xUnit의 격리 보장은 사라진다.
>
> 이것이 이 절 앞의 "테스트하기 어려운 코드의 징후" 표에서 정적 가변 상태를 1번에 놓은 이유다. 프로덕션 코드의 정적 상태는 테스트를 어렵게 만들고, 테스트 코드의 정적 상태는 **테스트를 거짓말하게** 만든다.

비동기 준비·정리가 필요하면 `IAsyncLifetime`을 구현한다. 생성자는 `await`할 수 없기 때문이다(47.5절).

```csharp
public class DatabaseTests : IAsyncLifetime
{
    private DbConnection _connection = null!;

    public async Task InitializeAsync()
    {
        _connection = new SqliteConnection("Data Source=:memory:");
        await _connection.OpenAsync();
        await CreateSchemaAsync(_connection);
    }

    public async Task DisposeAsync() => await _connection.DisposeAsync();

    [Fact] public async Task Insert_ValidRow_Persists() { /* ... */ }
}
```

`IAsyncLifetime`을 구현하면 `InitializeAsync`가 생성자 **다음에**, `DisposeAsync`가 `Dispose` **앞에** 실행된다. 둘 다 구현할 수도 있다.

### 픽스처 — 비싼 준비를 공유하기

테스트마다 새 인스턴스를 만드는 것은 격리에는 좋지만, 준비가 비싸면 감당이 안 된다. 데이터베이스 스키마를 만드는 데 3초가 걸린다면 테스트 50개에 150초다.

xUnit은 두 단계의 공유 메커니즘을 준다.

```text
┌────────────────────────────────────────────────────────┐
│ ICollectionFixture<T> — 여러 테스트 클래스가 공유       │
│ (컬렉션 안의 클래스들은 서로 병렬 실행되지 않는다)      │
│  ┌──────────────────────────┐ ┌──────────────────────┐ │
│  │ IClassFixture<T>         │ │ IClassFixture<T>     │ │
│  │  ┌──────┐┌──────┐┌──────┐│ │  ┌──────┐┌──────┐    │ │
│  │  │테스트││테스트││테스트││ │  │테스트││테스트│    │ │
│  │  └──────┘└──────┘└──────┘│ │  └──────┘└──────┘    │ │
│  │   ↑ 생성자/Dispose 매번  │ │                      │ │
│  └──────────────────────────┘ └──────────────────────┘ │
└────────────────────────────────────────────────────────┘
```

**`IClassFixture<T>`** — 한 테스트 클래스 안의 모든 테스트가 픽스처 인스턴스 하나를 공유한다.

```csharp
// 픽스처 자체는 특별한 인터페이스가 필요 없다. 정리가 필요하면 IDisposable.
public class SchemaFixture : IDisposable
{
    public string ConnectionString { get; }
    public SchemaFixture()
    {
        ConnectionString = "Data Source=" + Path.GetTempFileName();
        CreateSchema(ConnectionString);   // 비싼 준비. 클래스당 한 번.
    }
    public void Dispose() => File.Delete(/* ... */);
}

public class ProductRepositoryTests : IClassFixture<SchemaFixture>
{
    private readonly SchemaFixture _fixture;
    public ProductRepositoryTests(SchemaFixture fixture) => _fixture = fixture;  // 생성자 주입

    [Fact] public void Add_NewProduct_AssignsId() { /* _fixture.ConnectionString 사용 */ }
}
```

**`ICollectionFixture<T>`** — 여러 테스트 클래스가 픽스처 하나를 공유한다. 정의를 위해 컬렉션 선언 클래스가 하나 필요하다.

```csharp
// 1) 컬렉션을 정의한다. 이 클래스에는 코드가 없어도 된다.
[CollectionDefinition("Database collection")]
public class DatabaseCollection : ICollectionFixture<SchemaFixture>
{
    // 이 클래스는 비어 있어야 한다.
    // [CollectionDefinition]과 ICollectionFixture<>를 붙이는 자리일 뿐이다.
}

// 2) 참여할 테스트 클래스에 같은 이름을 붙인다.
[Collection("Database collection")]
public class ProductRepositoryTests
{
    private readonly SchemaFixture _fixture;
    public ProductRepositoryTests(SchemaFixture fixture) => _fixture = fixture;
    // ...
}

// OrderRepositoryTests 등 다른 클래스에도 같은 [Collection] 이름을 붙이면
// 그 클래스들이 SchemaFixture 인스턴스 하나를 공유한다.
```

| 범위 | 인터페이스 | 인스턴스 개수 | 병렬성 |
|---|---|---|---|
| 테스트 하나 | (생성자 / `Dispose`) | 테스트마다 1개 | — |
| 테스트 클래스 하나 | `IClassFixture<T>` | 클래스마다 1개 | 다른 클래스와 병렬 실행 |
| 테스트 클래스 여러 개 | `ICollectionFixture<T>` + `[Collection]` | 컬렉션마다 1개 | **같은 컬렉션 안에서는 직렬** |
| 어셈블리 전체 | (별도 개념 — 러너 설정) | — | `xunit.runner.json`으로 제어 |

> **⚠️ 컬렉션 픽스처는 병렬성을 끄는 대가로 얻는 것이다**
>
> `[Collection]`으로 묶인 테스트 클래스들은 **서로 병렬로 실행되지 않는다.** xUnit의 병렬 실행 단위가 테스트 컬렉션이기 때문이다.
>
> 이것은 버그가 아니라 기능이다. 공유 리소스(데이터베이스 하나)를 여러 클래스가 동시에 건드리지 못하게 막아 준다. 하지만 컬렉션 하나에 테스트 클래스를 40개 몰아넣으면 **테스트 스위트 전체가 사실상 직렬화된다.**
>
> 판단 기준: 픽스처가 **읽기 전용**이면(예: 스키마만 만들고 각 테스트가 자기 트랜잭션에서 작업) 컬렉션 픽스처가 이득이다. 픽스처가 **가변 상태를 공유**하면 컬렉션 픽스처는 직렬화 + 상태 오염이라는 최악의 조합이 된다. 그럴 땐 클래스 픽스처로 내리거나 아예 테스트마다 새로 만들어라.

> **📌 병렬성 제어**
>
> 어셈블리 수준에서 병렬 실행을 끄려면 특성을 쓴다.
>
> ```csharp
> [assembly: CollectionBehavior(DisableTestParallelization = true)]
> ```
>
> 또는 테스트 프로젝트에 `xunit.runner.json`을 두고 `Content`로 복사되게 한다.
>
> ```json
> { "parallelizeTestCollections": true, "maxParallelThreads": 4 }
> ```
>
> CI 러너의 코어 수가 적을 때 `maxParallelThreads`를 낮추면 오히려 전체 시간이 줄기도 한다. 컨텍스트 전환과 메모리 경합 때문이다.

### 테스트 실행과 분류

```text
dotnet test                                        # 솔루션 전체
dotnet test --filter "FullyQualifiedName~Order"    # 이름에 Order가 든 것만
dotnet test --filter "Category=Integration"        # 특성으로 분류
dotnet test --logger "trx;LogFileName=results.trx" # TRX 리포트
dotnet test --collect:"XPlat Code Coverage"        # coverlet.collector 필요
dotnet test --blame-hang-timeout 60s               # 멈춘 테스트를 잡아낸다
```

분류에는 `[Trait]`을 쓴다.

```csharp
[Fact, Trait("Category", "Integration")]
public async Task Repository_AgainstRealDatabase_RoundTrips() { /* ... */ }
```

이렇게 해 두면 PR 검증에서는 단위 테스트만 돌리고, 야간 빌드에서 통합 테스트를 포함해 전부 돌리는 분리가 가능해진다.

```text
dotnet test --filter "Category!=Integration"   # PR 게이트: 빠른 것만
```

> **💡 테스트 스위트는 속도로 계층을 나눠라**
>
> 개발자가 테스트를 돌리지 않게 되는 유일한 이유는 **느려서**다. 커밋 전에 돌리는 스위트가 10초를 넘어가면 사람들은 그냥 푸시하고 CI에 맡긴다. 그 순간 단위 테스트의 가장 큰 가치(즉각적인 피드백)가 사라진다.
>
> 실무 기준선: **단위 테스트 스위트 전체가 10초 이내**, 통합 테스트는 별도 스위트로 분리해 몇 분까지 허용. 10초를 못 지키겠다면 그건 대개 테스트가 많아서가 아니라 **단위 테스트인 척하는 통합 테스트가 섞여 있어서**다.

### `internal` 멤버를 테스트하기

테스트하고 싶은 로직이 `internal`이라면 `InternalsVisibleTo`로 테스트 어셈블리에 노출할 수 있다(17.2절).

```xml
<ItemGroup>
  <InternalsVisibleTo Include="CalculatorLibUnitTests" />
</ItemGroup>
```

※.NET 5 이후 SDK는 이 MSBuild 항목을 보고 `[assembly: InternalsVisibleTo(...)]` 특성을 생성해 준다. 예전 방식대로 `AssemblyInfo.cs`에 직접 써도 된다.

> **⚠️ `InternalsVisibleTo`는 필요악이지 기본 도구가 아니다**
>
> `internal`을 테스트에 여는 것 자체는 정당하다. 17.6절이 말하는 "가시성 최소화"를 지키면서도 내부 알고리즘을 직접 검증할 수 있게 해 준다.
>
> 문제는 이것이 **설계 문제의 진통제로 쓰일 때**다. `private` 메서드를 테스트하려고 `internal`로 승격시키기 시작하면, 테스트가 구현 세부에 결합되어 리팩터링할 때마다 깨진다.
>
> 판단 기준: 그 `internal` 타입이 **독립된 이름과 책임을 가질 만한가?** 그렇다면 별도 타입으로 분리하고 그것을 테스트하라(그리고 아마 `public`이어도 된다). 아니라면 그것은 구현 세부이고, 공개 API를 통해 간접적으로 검증되어야 한다.
>
> 그리고 강력한 이름(strong name)이 붙은 어셈블리에서는 `InternalsVisibleTo`에 **공개 키까지** 적어야 한다는 점을 기억하라(52장). 테스트 프로젝트에 서명을 하지 않았다면 그냥 실패한다.

## 80.2 의존성 주입과 경계 설계

### 문제는 "결합"이 아니라 "결정"이다

의존성 주입(DI, dependency injection)을 "결합도를 낮추는 기법"으로만 배우면 대개 과용으로 이어진다. 더 정확한 프레임은 이것이다.

> 모든 타입은 **자기가 내리는 결정**과 **호출자가 내려야 할 결정**을 구분해야 한다. 의존성 주입은 후자를 호출자에게 돌려주는 문법적 수단일 뿐이다.

`OrderProcessor`가 주문 총액 계산 규칙을 아는 것은 자기 결정이다. 그 결과를 **어디에 저장할지**, **어떤 시각을 기준으로 할지**, **어떤 결제 게이트웨이를 부를지**는 자기 결정이 아니다. 후자를 스스로 정하는 순간 그 타입은 테스트 불가능해진다.

다음 코드를 보자.

```csharp
public class OrderProcessor
{
    public async Task<Receipt> ProcessAsync(Order order)
    {
        // 결정 1: 어떤 DB에 붙을지를 스스로 정했다.
        using var conn = new SqlConnection(
            Environment.GetEnvironmentVariable("ORDERS_DB"));

        // 결정 2: 시각을 스스로 정했다.
        var placedAt = DateTime.UtcNow;

        // 결정 3: 어떤 게이트웨이를 쓸지 스스로 정했다.
        var gateway = new StripeGateway(apiKey: Config.StripeKey);

        // 결정 4: 로그를 어디로 보낼지 스스로 정했다.
        File.AppendAllText(@"C:\logs\orders.txt", $"{placedAt}: {order.Id}");

        var total = order.Items.Sum(i => i.Price * i.Quantity);   // ← 진짜 로직
        return await gateway.ChargeAsync(order.CustomerId, total);
    }
}
```

이 클래스에서 **실제로 검증하고 싶은 로직은 `total` 계산 한 줄**이다. 그런데 그 한 줄을 실행하려면 SQL Server, 환경 변수, Stripe 계정, `C:\logs` 디렉터리가 전부 필요하다. 네 개의 결정이 한 줄의 로직을 인질로 잡고 있다.

### 무엇을 주입하고 무엇을 주입하지 않는가

DI를 배운 팀이 다음으로 저지르는 실수는 **모든 것을 주입하는 것**이다. `IStringBuilderFactory`, `IListFactory<T>`, `IMathOperations` 같은 것이 등장하기 시작한다.

판단 기준은 간단하다.

| 주입할 것 | 이유 |
|---|---|
| **프로세스 밖으로 나가는 것** — DB, HTTP, 파일, 메시지 큐, 메일 | 테스트에서 실행할 수 없거나 느리다 |
| **환경에서 읽어 오는 것** — 시각, 난수, 환경 변수, 머신 이름 | 통제할 수 없으면 어서션을 쓸 수 없다 |
| **정책·전략** — 할인 규칙, 재시도 정책, 직렬화 형식 | 호출자가 바꿔야 하는 결정이다 |
| **비용이 큰 자원** — 커넥션 풀, `HttpClient`, 캐시 | 수명을 컨테이너가 관리해야 한다 |

| 주입하지 **않을** 것 | 이유 |
|---|---|
| **순수 값 타입과 자료구조** — `List<T>`, `Dictionary<K,V>`, `StringBuilder` | 결정론적이고 빠르다. 대체할 이유가 없다 |
| **순수 함수** — `Math.Sqrt`, `string.Split`, 정규식 매칭 | 같은 입력에 항상 같은 출력. 그것이 곧 테스트 가능성이다 |
| **자기 자신의 도메인 로직** | 대체하는 순간 테스트할 대상이 사라진다 |
| **`sealed`도 아니고 밖으로 나가지도 않는 협력자** | 실제 객체를 그냥 쓰면 된다 |

> **⚠️ 도메인 로직을 목으로 대체하면 테스트는 아무것도 검증하지 않는다**
>
> 다음 테스트를 보라.
>
> ```csharp
> var calculator = new Mock<IPriceCalculator>();
> calculator.Setup(c => c.Calculate(It.IsAny<Order>())).Returns(100m);
> var sut = new OrderProcessor(calculator.Object, ...);
>
> var receipt = await sut.ProcessAsync(order);
>
> Assert.Equal(100m, receipt.Total);   // ← 무엇을 검증했는가?
> ```
>
> 이 테스트는 "100을 반환하도록 설정한 목이 100을 반환한다"는 것을 검증한다. **가격 계산 로직은 단 한 줄도 실행되지 않았다.** 커버리지 리포트는 초록색이고, 계산 로직의 버그는 그대로 프로덕션에 간다.
>
> 이것이 이 장에서 가장 흔하고 가장 비싼 실수다. 규칙: **테스트하려는 로직 자체는 절대 목으로 대체하지 않는다.**

### 주입의 세 가지 형태

```csharp
// 1) 생성자 주입 — 기본. 필수 의존성.
public class OrderProcessor
{
    private readonly IOrderRepository _repository;
    private readonly IPaymentGateway _gateway;
    private readonly TimeProvider _time;
    public OrderProcessor(IOrderRepository repository, IPaymentGateway gateway, TimeProvider time)
    {
        _repository = repository ?? throw new ArgumentNullException(nameof(repository));
        _gateway    = gateway    ?? throw new ArgumentNullException(nameof(gateway));
        _time       = time       ?? throw new ArgumentNullException(nameof(time));
    }
}

// 2) 메서드 주입 — 호출마다 달라지는 것.
public Receipt Process(Order order, IDiscountPolicy policy) { /* ... */ }
// 3) 프로퍼티 주입 — 선택적 의존성. 기본값이 있고 없어도 동작해야 한다.
public ILogger Logger { get; set; } = NullLogger.Instance;
```

**생성자 주입이 기본이다.** 이유는 테스트가 아니라 컴파일러에 있다 — 필수 의존성이 빠지면 **컴파일되지 않는다.** 프로퍼티 주입은 런타임에 `NullReferenceException`으로 나타난다.

79.5절에서 본 원칙이 여기서 그대로 적용된다. **생성자는 대입만 한다.** 생성자에서 DB에 붙거나, 파일을 읽거나, 백그라운드 스레드를 띄우면 그 타입은 "인스턴스를 만드는 것"만으로 환경을 요구하게 된다.

> **⚠️ 생성자에서 가상 메서드를 부르지 마라 — 테스트 대역이 반쯤 초기화된 상태를 본다**
>
> 79.6절에서 본 문제가 테스트에서는 더 고약하게 나타난다. 기반 클래스 생성자가 가상 메서드를 부르면, 파생 클래스(테스트용 서브클래스일 수도 있다)의 생성자 본문이 **아직 실행되지 않은 상태**에서 그 메서드가 호출된다.
>
> 테스트 대역을 상속으로 만드는 경우 이것이 `NullReferenceException`의 형태로 튀어나오는데, 원인이 상속 계층에 있어서 추적하기 어렵다.

### 의존성이 너무 많다면 그것이 신호다

생성자 인수가 8개, 10개로 늘어나기 시작하면 DI 컨테이너 설정을 개선할 때가 아니라 **클래스를 쪼갤 때**다.

```csharp
// 냄새: 이 클래스는 몇 가지 일을 하고 있는가?
public OrderService(
    IOrderRepository orders, ICustomerRepository customers, IInventoryService inventory,
    IPaymentGateway payment, IShippingCalculator shipping, ITaxCalculator tax,
    IEmailSender email, ISmsSender sms, IAuditLog audit,
    TimeProvider time, ILogger<OrderService> logger) { /* ... */ }
```

이 생성자는 "이 클래스가 열한 가지 이유로 바뀔 수 있다"고 말하고 있다. 테스트 관점에서는 더 직설적이다 — **모든 테스트가 열한 개의 대역을 준비해야 한다.**

쪼개는 방향은 보통 셋 중 하나다.

1. **응집된 묶음을 별도 타입으로 추출** — `shipping` + `tax` + 가격 계산을 `IOrderPricing` 하나로.
2. **알림 계열을 파사드로** — `email` + `sms`를 `INotificationService` 하나로.
3. **오케스트레이션과 계산을 분리** — 순수 계산 부분을 의존성 없는 클래스로 빼면, 그 부분은 **아무 대역 없이** 테스트할 수 있다.

3번이 가장 강력하다. 이것이 "함수형 코어, 명령형 셸(functional core, imperative shell)"이라 불리는 배치다.

```text
┌─────────────────────────────────────────────────────────┐
│  명령형 셸 (imperative shell)                           │
│  ─ I/O, DB, HTTP, 시각, 난수                            │
│  ─ 의존성 많음, 로직 없음                               │
│  ─ 테스트: 통합 테스트 소수 (80.5절)                     │
│                                                          │
│      데이터 읽기 ──→ ┌──────────────────────┐ ──→ 쓰기  │
│                      │  함수형 코어         │            │
│                      │  ─ 순수 함수         │            │
│                      │  ─ 의존성 0개        │            │
```

핵심 로직에서 의존성을 0개로 만들면 그 부분은 목도 픽스처도 필요 없다. `[Theory]`에 데이터를 30줄 넣고 끝난다. 그리고 셸은 얇아서 통합 테스트 몇 개로 덮인다.

> **💡 "인터페이스는 구현이 둘 이상일 때 만든다"는 규칙은 반만 맞다**
>
> 흔한 반론: "`IOrderRepository` 구현이 `SqlOrderRepository` 하나뿐인데 왜 인터페이스를 만드나?"
>
> 사실은 구현이 둘이다 — **프로덕션 구현과 테스트 대역**이다. 테스트 대역도 정당한 구현이다.
>
> 하지만 이 논리를 무한정 확장하면 안 된다. 인터페이스를 만들 가치가 있는지는 **그 경계를 넘는 것이 무엇인지**로 판단하라. 프로세스 밖으로 나가는 경계라면 인터페이스가 맞다. 같은 어셈블리 안의 순수 계산이라면 인터페이스는 간접 계층만 하나 늘리는 것이다.

### 과도한 추상화의 대가

인터페이스를 남발했을 때 치르는 비용은 눈에 잘 안 띄지만 실재한다.

| 비용 | 내용 |
|---|---|
| **탐색 불가능성** | "F12(정의로 이동)"가 인터페이스로만 데려간다. 실제 구현을 찾으려면 컨테이너 등록을 뒤져야 한다 |
| **호출 그래프 단절** | 정적 분석 도구·IDE가 "이 메서드를 누가 부르는가"에 답하지 못한다 |
| **디버깅 비용** | 스택 트레이스가 인터페이스 디스패치와 컨테이너 프록시로 채워진다 (74장) |
| **런타임 비용** | 인터페이스 호출은 `callvirt` + 인터페이스 디스패치 스텁을 거친다. 핫 패스에서는 인라이닝을 막는다 (55장) |
| **변경 비용의 역전** | 메서드 하나를 추가하려면 인터페이스, 구현, 목 설정, 컨테이너 등록을 전부 고쳐야 한다 |
| **거짓 안정감** | "인터페이스로 감쌌으니 교체 가능하다"는 착각. 실제로는 첫 구현의 의미론이 인터페이스에 새어 있어서 두 번째 구현이 안 맞는다 |

마지막 항목이 가장 중요하다. `IOrderRepository.SaveAsync`가 "즉시 커밋"인지 "유닛 오브 워크에 등록"인지는 인터페이스에 적혀 있지 않다. 첫 구현의 동작이 사실상의 계약이 되고, 두 번째 구현은 그 암묵적 계약을 어긴다. 78.13절이 말하는 "바이너리 호환성은 지켰지만 의미론이 깨진" 상황이다.

> **⚠️ 목이 통과시키는 계약 위반**
>
> 목은 **당신이 설정한 대로만** 동작한다. 실제 구현이 `null`을 반환할 수 있는데 목이 항상 객체를 반환하도록 설정되어 있으면, 그 코드 경로의 `NullReferenceException`은 프로덕션에서 처음 발견된다.
>
> 이것을 완화하는 유일한 방법은 **계약 테스트(contract test)** 다 — 인터페이스에 대한 테스트 묶음을 하나 만들고, 실제 구현과 테스트용 페이크를 **같은 테스트로** 돌린다.
>
> ```csharp
> public abstract class OrderRepositoryContractTests
> {
>     protected abstract IOrderRepository CreateSut();   // 파생 클래스가 구현체를 고른다
>
>     [Fact]
>     public async Task GetAsync_UnknownId_ReturnsNull()
>         => Assert.Null(await CreateSut().GetAsync(Guid.NewGuid()));
> }
>
> public class InMemoryOrderRepositoryTests : OrderRepositoryContractTests
> {
>     protected override IOrderRepository CreateSut() => new InMemoryOrderRepository();
> }
>
> [Trait("Category", "Integration")]                     // 실제 DB 구현에도 같은 검사를
> public class SqlOrderRepositoryTests : OrderRepositoryContractTests
> {
>     protected override IOrderRepository CreateSut() => new SqlOrderRepository(/* ... */);
> }
> ```
>
> 이제 페이크가 실제 구현과 다르게 동작하면 **테스트가 잡는다.**

### 테스트 대역 5종

"목(mock)"은 일상어에서 모든 테스트 대역을 뭉뚱그려 부르는 말이 되었지만, 원래는 다섯 종류가 구분된다. 이 구분은 학술적 취미가 아니라 **테스트가 무엇에 결합되는지**를 결정한다.

| 대역 | 정의 | 검증 대상 | 언제 쓰나 | 위험 |
|---|---|---|---|---|
| **더미(Dummy)** | 자리를 채우기만 한다. 실제로 호출되지 않는다 | 없음 | 필수 인수인데 이 테스트에서는 안 쓰일 때 | 실제로 호출되면 `NullReferenceException` |
| **스텁(Stub)** | 미리 정한 값을 돌려준다 | **상태** (반환값·최종 상태) | 대부분의 경우. **기본 선택** | 거의 없음 |
| **스파이(Spy)** | 호출된 사실을 기록해 두고 나중에 조회 | 상태 + 호출 이력 | "메일이 발송되었는가"처럼 부작용이 관찰 대상일 때 | 이력 검증이 과하면 구현에 결합 |
| **목(Mock)** | 기대할 호출을 **미리 선언**하고, 그대로 왔는지 검증 | **상호작용** (호출 순서·횟수·인수) | 부작용이 유일한 결과물일 때 | **구현 세부에 강하게 결합** |
| **페이크(Fake)** | 동작하는 대체 구현. 단순화되어 있을 뿐 진짜로 작동 | 상태 | 저장소·시계·파일 시스템 | 페이크 자체에 버그가 생긴다 |

```csharp
// 더미 — 이 테스트에서는 로거를 쓰지 않는다.
var sut = new OrderProcessor(repo, gateway, NullLogger<OrderProcessor>.Instance);

// 스텁 — 값을 돌려주기만 한다.
var repo = Substitute.For<IOrderRepository>();
repo.GetAsync(orderId).Returns(new Order { Id = orderId, Total = 100m });

// 스파이 — 호출 사실을 확인한다.
await sut.ProcessAsync(order);
await gateway.Received(1).ChargeAsync(order.CustomerId, 100m);

// 목 — 엄격 모드: 설정하지 않은 호출이 오면 즉시 실패한다.
var strict = new Mock<IPaymentGateway>(MockBehavior.Strict);
strict.Setup(g => g.ChargeAsync(It.IsAny<string>(), 100m)).ReturnsAsync(ChargeResult.Ok);

// 페이크 — Dictionary 하나로 실제로 동작하는 단순 구현.
public sealed class InMemoryOrderRepository : IOrderRepository { /* ... */ }
```

.NET에서 목 라이브러리로 널리 쓰이는 것은 **Moq**와 **NSubstitute**다. 둘 다 동적 프록시(58장·59장의 동적 코드 생성 위에 서 있다)로 인터페이스 구현을 런타임에 만들어 낸다.

```csharp
// Moq
var mock = new Mock<IOrderRepository>();
mock.Setup(r => r.GetAsync(It.IsAny<Guid>())).ReturnsAsync((Order?)null);
mock.Verify(r => r.SaveAsync(It.Is<Order>(o => o.Total == 100m)), Times.Once);

// NSubstitute
var repo = Substitute.For<IOrderRepository>();
repo.GetAsync(Arg.Any<Guid>()).Returns((Order?)null);
await repo.Received(1).SaveAsync(Arg.Is<Order>(o => o.Total == 100m));
```

> **📌 Moq 4.20의 SponsorLink 사건**
>
> 2023년 Moq 4.20.0은 빌드 시점에 개발자의 git 이메일을 해시해 외부 서비스로 보내는 **SponsorLink** 구성 요소를 포함한 채 배포되었다. 강한 반발이 있었고 곧 제거되었지만, 이 사건 이후 상당수 조직이 NSubstitute나 수작업 페이크로 이동했다.
>
> 실무 교훈은 특정 라이브러리에 대한 것이 아니다. **테스트 인프라도 공급망(supply chain)의 일부다.** 목 라이브러리는 리플렉션·동적 코드 생성·빌드 태스크를 모두 쓰므로 권한 표면이 넓다. 버전을 고정하고(`Directory.Packages.props`), 변경 로그를 읽는 습관이 필요하다.

### 목 남용의 문제

목(엄밀한 의미의 목 — 상호작용 검증)을 많이 쓸수록 테스트는 **구현 세부에 결합**된다.

```csharp
// 나쁜 예: 이 테스트는 무엇이 바뀌면 깨지는가?
[Fact]
public async Task ProcessAsync_ValidOrder_CallsEverythingInOrder()
{
    await _sut.ProcessAsync(order);

    _inventory.Received(1).Reserve(order.Items);
    _payment.Received(1).ChargeAsync(order.CustomerId, 100m);
    _audit.Received(1).Log("order.processed", order.Id);
}
```

이 테스트는 **결과를 검증하지 않는다.** 호출 순서를 검증한다. 리팩터링해서 감사 로그를 이벤트 핸들러로 옮기면 — 동작은 완전히 동일한데 — 테스트가 깨진다. 이런 테스트가 수백 개 쌓이면 리팩터링 비용이 리팩터링 가치를 넘어서고, 코드는 얼어붙는다.

> **💡 목 사용의 3원칙**
>
> 1. **관찰 가능한 결과가 있으면 그것을 검증하라.** 반환값·최종 상태·던져진 예외. 목 검증은 관찰할 결과가 **없을 때만** 쓴다.
> 2. **프로세스 경계를 넘는 호출만 목으로 검증하라.** "메일이 실제로 나갔는가", "결제가 한 번만 청구되었는가"는 정당하다. "내부 헬퍼가 호출되었는가"는 아니다.
> 3. **호출 순서 검증은 순서가 계약의 일부일 때만.** 대부분은 아니다.
>
> 이 세 가지를 지키면 목의 개수는 자연히 줄고, 남은 목은 전부 의미가 있다.

> **⚠️ `MockBehavior.Strict`는 양날의 검이다**
>
> 엄격 모드는 설정하지 않은 호출이 오면 즉시 실패시킨다. "예상 못한 호출"을 잡아 주므로 안전해 보이지만, 실제로는 **테스트를 구현에 더 강하게 묶는다.** 무해한 호출 하나(로깅을 위한 `GetName()` 같은 것)를 추가해도 관련 없는 테스트 수십 개가 무너진다.
>
> 기본은 느슨한 모드(설정되지 않은 호출은 기본값 반환)로 두고, "이 협력자는 절대 호출되면 안 된다"를 표현해야 하는 소수의 경우에만 엄격 모드를 쓰는 편이 낫다. 그 의도가 명확하다면 `Received(0)` / `Times.Never`로 표현하는 것이 더 읽기 쉽다.

## 80.3 비동기 코드 테스트

### 테스트 메서드는 `async Task`여야 한다

47장에서 본 것처럼 `async` 메서드의 반환 타입은 `void`, `Task`, `Task<T>`, `ValueTask`, 커스텀 빌더 중에서 고른다. 테스트 메서드에서는 선택지가 하나뿐이다.

```csharp
[Fact]
public async Task GetAsync_UnknownId_ReturnsNull()
{
    var repo = new InMemoryOrderRepository();

    var result = await repo.GetAsync(Guid.NewGuid());

    Assert.Null(result);
}
```

`async Task`다. 러너는 반환된 `Task`를 기다리고, 그 `Task`가 오류로 완료되면 테스트를 실패로 기록한다. **테스트가 실패로 기록되는 유일한 경로가 이것**이라는 점이 중요하다.

> **⚠️ `async void` 테스트는 통과하는 것처럼 보인다**
>
> ```csharp
> [Fact]
> public async void Broken()          // ← void
> {
>     await Task.Delay(50);
>     Assert.Equal(1, 2);             // 이 어서션은 실패한다
> }
> ```
>
> 47.14절에서 본 대로 `async void`는 호출자에게 완료를 알릴 수단이 없다. 첫 `await`에서 제어가 러너로 돌아가고, 러너는 "메서드가 반환되었으니 성공"으로 판단한다. 어서션 실패는 **캡처된 동기화 컨텍스트나 `ThreadPool`에서 예외로 튀어나오고**, 잡히지 않은 예외로 테스트 호스트를 죽이거나 아무 흔적 없이 사라진다.
>
> 즉 이 테스트는 **거짓 통과**하거나 **엉뚱한 테스트를 실패시킨다.** 둘 다 최악이다.
>
> xUnit.net 분석기는 `async void` 테스트를 진단으로 잡아 준다. 최신 xUnit은 이를 아예 허용하지 않는 방향으로 갔다. 어느 버전을 쓰든 규칙은 하나다 — **테스트 메서드에 `void`를 쓰지 마라.** 예외는 없다.

### 비동기 예외 단언

동기 코드의 `Assert.Throws<T>`에 대응하는 것은 `Assert.ThrowsAsync<T>`다.

```csharp
[Fact]
public async Task ChargeAsync_NegativeAmount_ThrowsArgumentOutOfRange()
{
    var gateway = new FakePaymentGateway();

    var ex = await Assert.ThrowsAsync<ArgumentOutOfRangeException>(
        () => gateway.ChargeAsync("cust-1", -5m));

    Assert.Equal("amount", ex.ParamName);
}
```

`await`를 빼먹으면 어떻게 되는지가 중요하다.

```csharp
// 잘못됨: 반환된 Task를 버렸다.
Assert.ThrowsAsync<ArgumentOutOfRangeException>(() => gateway.ChargeAsync("c", -5m));
```

이 줄은 **아무것도 검증하지 않는다.** `ThrowsAsync`는 `Task<T>`를 반환하고, 그것을 기다리지 않으면 단언 실패가 어디에도 보고되지 않는다. 테스트는 초록불이다.

> **⚠️ `await` 없는 어서션은 침묵한다 — CS4014를 오류로 켜라**
>
> 컴파일러는 이 경우 **CS4014**("이 호출을 대기하지 않으므로 호출이 완료되기 전에 현재 메서드 실행이 계속됩니다")를 경고로 낸다. 테스트 프로젝트에서는 이것을 오류로 승격시켜야 한다.
>
> ```xml
> <PropertyGroup>
>   <!-- 대기하지 않은 비동기 호출을 오류로 -->
>   <WarningsAsErrors>$(WarningsAsErrors);CS4014</WarningsAsErrors>
> </PropertyGroup>
> ```
>
> 이 한 줄이 실무에서 잡아내는 거짓 통과 테스트의 양은 놀라울 정도다.

`AggregateException`도 함정이다. `await`는 `AggregateException`을 풀어 **첫 번째 내부 예외**를 다시 던지지만(32.13절), `Task.Wait()`나 `.Result`는 `AggregateException`을 그대로 던진다.

```csharp
// await 경로: ArgumentOutOfRangeException이 잡힌다.
await Assert.ThrowsAsync<ArgumentOutOfRangeException>(() => task);

// 블로킹 경로: AggregateException이 나온다.
Assert.Throws<AggregateException>(() => task.Wait());
```

같은 코드인데 단언이 달라진다. 테스트에서 블로킹을 쓰지 말아야 할 이유가 하나 더 늘었다.

### 데드락 재현 — 그리고 왜 재현되지 않는가

47.14절에서 sync-over-async 데드락의 메커니즘을 해부했다. 요약하면 이렇다.

```text
UI 스레드                     라이브러리
────────                     ──────────
task.Result → 블로킹
                             await httpClient.GetAsync(...)
                             ↓ 완료 시 continuation을 캡처된
                               SynchronizationContext에 게시
              SynchronizationContext는 UI 스레드에서만 실행
              ↓ 그런데 UI 스레드는 .Result에서 블로킹 중
           ┌──── 데드락 ────┐
```

여기서 실무자를 가장 많이 곤란하게 하는 사실이 있다.

> **⚠️ 데드락은 대개 테스트에서 재현되지 않는다**
>
> 이 데드락이 성립하려면 **동기화 컨텍스트(`SynchronizationContext`)가 필요하다.** 그리고,
>
> - **콘솔 앱**: 동기화 컨텍스트 없음 → 데드락 안 남
> - **ASP.NET Core**: 동기화 컨텍스트 없음 → 데드락 안 남
> - **WinForms / WPF**: 있음 → 데드락 남
> - **ASP.NET (.NET Framework)**: 있음 → 데드락 남 (**.NET Framework 전용**)
>
> 단위 테스트 러너는 콘솔 호스트에 가깝다. 그래서 라이브러리 안의 `.Result` 호출은 **테스트를 전부 통과하고 WPF 앱에서 처음 멈춘다.**
>
> 결론: 데드락은 테스트로 잡는 것이 아니라 **정적으로 금지**하는 것이다. `.Result`, `.Wait()`, `GetAwaiter().GetResult()`를 라이브러리 코드에서 금지하고, 분석기 규칙으로 강제하라(79.13절).

동기화 컨텍스트가 있을 때의 동작을 정말로 테스트해야 한다면, 테스트용 동기화 컨텍스트를 직접 설치하는 방법이 있다. 단일 스레드 펌프를 구현해 `SynchronizationContext.SetSynchronizationContext`로 설치하면, 위 시나리오를 결정론적으로 재현할 수 있다. 다만 이것은 프레임워크 코드를 만드는 팀에게나 필요한 수준이고, 대부분의 애플리케이션 코드에서는 **`ConfigureAwait(false)` 규칙과 분석기**로 충분하다(47.12절).

> **📌 xUnit v2와 동기화 컨텍스트**
>
> xUnit v2는 테스트 컬렉션의 동시성을 제한하기 위해 자체 동기화 컨텍스트를 테스트 실행 중에 설치한다. 그 결과 **xUnit 안에서는 콘솔 앱과 다르게 동작하는 비동기 코드가 있을 수 있다.**
>
> 실무에서 이것이 드러나는 방식은 대개 이렇다 — 테스트에서만 멈추거나, 테스트에서만 통과한다. 비동기 관련 테스트가 프로덕션 동작과 어긋나 보이면 러너의 동기화 컨텍스트를 의심할 가치가 있다.

### 시간에 의존하는 비동기 코드

가장 흔한 비동기 테스트 실패 원인은 `Task.Delay`다.

```csharp
// 테스트하려는 코드
public async Task<Result> FetchWithRetryAsync(CancellationToken ct)
{
    for (int attempt = 0; attempt < 3; attempt++)
    {
        try { return await _client.FetchAsync(ct); }
        catch (HttpRequestException) when (attempt < 2)
        { await Task.Delay(TimeSpan.FromSeconds(30), ct); }   // ← 문제
    }
    throw new InvalidOperationException("재시도 소진");
}
```

이 재시도 로직을 테스트하려면 **60초를 기다려야 한다.** 실무에서 실제로 목격되는 대응은 두 가지인데 둘 다 나쁘다.

1. 딜레이를 `TimeSpan.FromMilliseconds(10)`으로 줄이고 테스트한다 → 프로덕션 상수를 테스트가 결정하게 된다.
2. 테스트에서 `Thread.Sleep(100)`으로 "대충 기다린다" → **플래키(flaky) 테스트**의 근원. CI 러너가 느린 날 깨진다.

정답은 **시간을 주입하는 것**이다. ※.NET 8은 `Task.Delay`에 `TimeProvider`를 받는 오버로드를 추가했다.

```csharp
public class ResilientFetcher
{
    private readonly IHttpFetcher _client;
    private readonly TimeProvider _time;
    public ResilientFetcher(IHttpFetcher client, TimeProvider time) => (_client, _time) = (client, time);

    public async Task<Result> FetchWithRetryAsync(CancellationToken ct)
    {
        for (int attempt = 0; attempt < 3; attempt++)
        {
            try { return await _client.FetchAsync(ct); }
            catch (HttpRequestException) when (attempt < 2)
            { await Task.Delay(TimeSpan.FromSeconds(30), _time, ct); }  // 오버로드 ※.NET 8
        }
        throw new InvalidOperationException("재시도 소진");
    }
}
```

테스트에서는 가짜 시계를 넣고 시간을 **명령으로** 진행시킨다.

```csharp
[Fact]
public async Task FetchWithRetryAsync_TwoFailuresThenSuccess_RetriesTwice()
{
    var time = new FakeTimeProvider();       // 패키지: Microsoft.Extensions.TimeProvider.Testing
    var client = new ScriptedFetcher(throwCount: 2, thenReturn: Result.Ok);
    var sut = new ResilientFetcher(client, time);

    var task = sut.FetchWithRetryAsync(CancellationToken.None);

    // 아직 완료되지 않았다 — 첫 딜레이에서 대기 중.
    Assert.False(task.IsCompleted);

    time.Advance(TimeSpan.FromSeconds(30));     // 1차 재시도 대기 소진
    time.Advance(TimeSpan.FromSeconds(30));     // 2차 재시도 대기 소진

    var result = await task;

    Assert.Equal(Result.Ok, result);
    Assert.Equal(3, client.CallCount);
}
```

60초가 아니라 **밀리초 단위**로 끝나고, 결정론적이다. `TimeProvider`와 `FakeTimeProvider`의 자세한 사용법은 다음 절에서 이어진다.

### 비동기 완료 시점을 통제하기

"작업이 아직 끝나지 않았을 때 무슨 일이 일어나는가"를 테스트하려면 완료 시점을 직접 조종해야 한다. `TaskCompletionSource<T>`가 그 도구다.

```csharp
[Fact]
public async Task ProcessAsync_SecondCallWhileFirstPending_IsRejected()
{
    var gate = new TaskCompletionSource<Result>(TaskCreationOptions.RunContinuationsAsynchronously);
    var client = Substitute.For<IHttpFetcher>();
    client.FetchAsync(Arg.Any<CancellationToken>()).Returns(gate.Task);
    var sut = new SingleFlightProcessor(client);

    var first = sut.ProcessAsync();                 // 첫 호출: 게이트에서 대기
    var second = sut.ProcessAsync();                // 두 번째 호출: 거절되어야 한다

    await Assert.ThrowsAsync<InvalidOperationException>(() => second);

    gate.SetResult(Result.Ok);                      // 이제 첫 호출을 풀어 준다
    Assert.Equal(Result.Ok, await first);
}
```

> **⚠️ `TaskCompletionSource`에는 `RunContinuationsAsynchronously`를 붙여라**
>
> 기본 설정에서 `SetResult`를 호출하면 **연속(continuation)이 `SetResult`를 호출한 스레드에서 동기적으로 실행된다.** 테스트에서는 이것이 두 가지 문제를 만든다.
>
> - `gate.SetResult(...)` 한 줄이 프로덕션 코드 수십 줄을 그 자리에서 실행시킨다. 스택 트레이스가 뒤엉키고, 그 안에서 예외가 나면 `SetResult` 호출 지점에서 튀어나온다.
> - 잠금을 쥔 채 `SetResult`를 부르면 연속이 같은 잠금을 요구해 **데드락**이 난다 (48장).
>
> `TaskCreationOptions.RunContinuationsAsynchronously`를 지정하면 연속이 `ThreadPool`로 넘어간다. 테스트에서든 프로덕션에서든 이것이 기본이어야 한다.

### 취소 테스트

취소는 비동기 API 계약의 일부인데(47.15절) 테스트되는 일이 드물다.

```csharp
[Fact]
public async Task FetchAsync_CancelledBeforeStart_ThrowsOperationCanceled()
{
    using var cts = new CancellationTokenSource();
    cts.Cancel();                                    // 시작 전에 이미 취소됨
    var sut = new ResilientFetcher(new SlowFetcher(), TimeProvider.System);

    await Assert.ThrowsAsync<TaskCanceledException>(() => sut.FetchWithRetryAsync(cts.Token));
}
```

> **⚠️ 취소 시 던져지는 예외 타입은 코드 형태에 따라 다르다**
>
> - `cancellationToken.ThrowIfCancellationRequested()` → **`OperationCanceledException`**
> - `Task.Delay(..., ct)`가 취소됨 → **`TaskCanceledException`** (이것은 `OperationCanceledException`의 파생 타입이다)
> - `await task`에서 `task`가 `Canceled` 상태로 완료 → `TaskCanceledException`
>
> 따라서 `Assert.Throws<OperationCanceledException>`은 **`TaskCanceledException`이 나면 실패한다**(정확한 타입을 요구하므로). 취소를 단언할 때는 `Assert.ThrowsAnyAsync<OperationCanceledException>`을 쓰는 편이 안전하다.
>
> ```csharp
> await Assert.ThrowsAnyAsync<OperationCanceledException>(
>     () => sut.FetchWithRetryAsync(cts.Token));
> ```

### 동시성 테스트의 비결정성

여기서 냉정해질 필요가 있다.

> **⚠️ 스레드 인터리빙을 테스트로 증명할 수는 없다**
>
> 두 스레드가 동시에 카운터를 증가시키는 코드에 경합(race)이 있는지 확인하려고 다음과 같은 테스트를 쓰는 경우가 많다.
>
> ```csharp
> [Fact]
> public void Increment_FromManyThreads_IsThreadSafe()
> {
>     var counter = new Counter();
>     Parallel.For(0, 100_000, _ => counter.Increment());
>     Assert.Equal(100_000, counter.Value);
> }
> ```
>
> 이 테스트는 **버그가 있어도 통과할 수 있고, 버그가 없어도 실패할 수 있다.** 통과는 "이번 실행에서는 나쁜 인터리빙이 발생하지 않았다"만 말한다. 스케줄러·코어 수·JIT 상태에 따라 결과가 달라진다.
>
> 실제로 벌어지는 일: 로컬에서 100번 통과 → CI에서 500번째 실행에 한 번 실패 → 아무도 재현 못 함 → **`[Fact(Skip = "flaky")]`** → 테스트 사망.

그렇다고 아무것도 못 하는 것은 아니다. 현실적인 전략은 이렇다.

| 전략 | 무엇을 얻나 | 한계 |
|---|---|---|
| **스트레스 루프** (위 예제) | 명백한 경합은 잡힌다. 특히 CI에서 반복 실행하면 확률이 쌓인다 | 통과가 정확성을 증명하지 못한다 |
| **결정론적 인터리빙 강제** — `ManualResetEventSlim`/`Barrier`로 두 스레드를 특정 지점에서 만나게 한다 | **특정 시나리오는 결정론적으로 재현** | 개발자가 상상한 인터리빙만 검사한다 |
| **불변 조건 단언** — 실행 후 상태가 일관적인지 검사 | 최종 상태 검증 | 중간 상태의 오류는 놓친다 |
| **설계로 제거** — 불변 객체, `Interlocked`, 채널 | 테스트가 필요 없어진다 | 항상 가능하지는 않다 |
| **잠금 순서 검사** — 진단 빌드에서 잠금 획득 순서를 기록 | 데드락 조건을 조기 발견 | 계측 비용 (73.1절의 조건부 컴파일과 함께 쓴다) |

결정론적 인터리빙의 예를 보자.

```csharp
[Fact]
public void Withdraw_TwoThreadsAtSameBalance_OnlyOneSucceeds()
{
    var account = new Account(balance: 100m);
    using var bothReady = new Barrier(participantCount: 2);
    var results = new bool[2];

    void Attempt(int index)
    {
        bothReady.SignalAndWait();      // 두 스레드를 같은 지점에 세운다
        results[index] = account.TryWithdraw(100m);
    }

    Task.WaitAll(Task.Run(() => Attempt(0)), Task.Run(() => Attempt(1)));

    // 불변 조건: 잔고 100에서 100씩 두 번 인출이 성공할 수는 없다.
    Assert.Single(results, r => r);
    Assert.Equal(0m, account.Balance);
}
```

`Barrier`가 "두 스레드가 동시에 잔고를 본다"는 시나리오의 발생 확률을 크게 올린다. 그래도 **보장은 아니다.** 이 테스트의 가치는 증명이 아니라 **회귀 탐지**에 있다 — 잠금을 실수로 제거하면 몇 번의 CI 실행 안에 잡힐 확률이 높다.

> **💡 플래키 테스트는 무시하지 말고 격리하라**
>
> 간헐적으로 실패하는 테스트를 방치하면 팀은 **모든 빨간불을 무시하기 시작한다.** 이것이 테스트 스위트가 죽는 가장 흔한 방식이다.
>
> 실무 처리 순서:
> 1. **즉시 별도 트레이트로 분리**한다 — `[Trait("Stability", "Flaky")]`. PR 게이트에서 제외한다.
> 2. **원인을 조사한다.** 대개 셋 중 하나다 — 시간 의존(80.4절), 공유 상태, 진짜 경합.
> 3. **고치거나 지운다.** 3주 안에 둘 중 하나를 하지 않으면 그 테스트는 순수한 소음이다.
>
> `Skip`을 달고 방치하는 것은 최악이다. 스킵된 테스트는 아무도 보지 않는 TODO다.

## 80.4 시간·난수·파일 시스템 의존성 제거

### 환경은 숨은 입력이다

`Add(a, b)`가 테스트하기 쉬운 이유는 **모든 입력이 매개변수로 보이기 때문**이다. 다음 메서드는 그렇지 않다.

```csharp
public bool IsExpired(Subscription sub)
    => DateTime.UtcNow > sub.ExpiresAt;
```

이 메서드의 입력은 둘이다 — `sub`와 **현재 시각**. 그런데 두 번째 입력은 시그니처에 없다. 이런 것을 **숨은 입력**이라 부르자. 숨은 입력의 목록은 놀랍도록 짧다.

| 숨은 입력 | 전형적 호출 | 제거 방법 |
|---|---|---|
| 현재 시각 | `DateTime.Now`, `DateTime.UtcNow`, `DateTimeOffset.UtcNow`, `Stopwatch` | `TimeProvider` 주입 ※.NET 8 |
| 난수 | `new Random()`, `Random.Shared`, `Guid.NewGuid()` | 시드 고정 또는 난수원 주입 |
| 파일 시스템 | `File.*`, `Directory.*`, `Path.GetTempPath()` | 스트림 추상화 또는 파일 시스템 추상화 |
| 환경 | `Environment.GetEnvironmentVariable`, `Environment.MachineName` | 옵션 객체로 주입 |
| 프로세스/스레드 | `Thread.CurrentThread`, `Process.GetCurrentProcess()` | 필요한 값만 주입 |
| 문화권 | `CultureInfo.CurrentCulture` | 명시적 `IFormatProvider` 전달 (79.4절) |
| 네트워크 | `HttpClient`, DNS | 인터페이스 또는 `HttpMessageHandler` 대체 |

이 목록에 없는 것은 대부분 주입할 필요가 없다. 80.2절의 판단 기준과 정확히 일치한다.

### `TimeProvider` — 시간을 매개변수로 만들기

※.NET 8이 도입한 `System.TimeProvider`는 시각·타임존·고해상도 타임스탬프·타이머를 하나의 추상 클래스로 묶는다(37.9절).

```csharp
public abstract class TimeProvider
{
    public static TimeProvider System { get; }        // 실제 시계
    public virtual DateTimeOffset GetUtcNow();
    public DateTimeOffset GetLocalNow();              // LocalTimeZone 기준
    public virtual TimeZoneInfo LocalTimeZone { get; }
    public virtual long GetTimestamp();               // Stopwatch 대체
    public virtual long TimestampFrequency { get; }
    public TimeSpan GetElapsedTime(long startingTimestamp);
    public virtual ITimer CreateTimer(
        TimerCallback callback, object? state, TimeSpan dueTime, TimeSpan period);
}
```

앞의 `IsExpired`를 고치면 이렇게 된다.

```csharp
public class SubscriptionService
{
    private readonly TimeProvider _time;

    // 기본값을 주면 프로덕션 호출부는 바뀌지 않는다.
    public SubscriptionService(TimeProvider? time = null) => _time = time ?? TimeProvider.System;

    public bool IsExpired(Subscription sub) => _time.GetUtcNow() > sub.ExpiresAt;
}
```

.NET 8은 시간을 소비하는 여러 API에 `TimeProvider` 오버로드를 추가했다.

```csharp
await Task.Delay(TimeSpan.FromSeconds(30), timeProvider, cancellationToken);
using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(5), timeProvider);
await task.WaitAsync(TimeSpan.FromSeconds(10), timeProvider, cancellationToken);
using var timer = new PeriodicTimer(TimeSpan.FromSeconds(1), timeProvider);
```

이것이 결정적으로 중요하다. `TimeProvider`를 주입해 놓고 내부에서 `Task.Delay(ts)`(오버로드 없는 버전)를 부르면 **시간의 절반만 통제한 것**이고, 테스트는 여전히 실제로 기다린다.

### `FakeTimeProvider`

가짜 시계 구현은 별도 NuGet 패키지에 있다.

```xml
<PackageReference Include="Microsoft.Extensions.TimeProvider.Testing" Version="8.*" />
```

타입은 `Microsoft.Extensions.Time.Testing.FakeTimeProvider`다.

> **⚠️ `TimeProvider`는 런타임에, `FakeTimeProvider`는 별도 패키지에 있다**
>
> `TimeProvider`는 ※.NET 8부터 `System.Runtime`(BCL)에 들어 있다. 그런데 `FakeTimeProvider`는 BCL에 **없다.** `Microsoft.Extensions.TimeProvider.Testing` 패키지를 테스트 프로젝트에 따로 추가해야 한다.
>
> 그리고 `TimeProvider` 자체는 .NET Standard 2.0 / .NET Framework 대상에서도 `Microsoft.Bcl.TimeProvider` 패키지로 쓸 수 있다. 멀티 타기팅 라이브러리를 만든다면 이 조합을 확인해 두라.

전체 예제를 보자. 세션 만료를 감시하고 만료 시 이벤트를 올리는 서비스다.

```csharp
public sealed class SessionMonitor : IDisposable
{
    private readonly TimeProvider _time;
    private readonly TimeSpan _idleTimeout;
    private readonly ITimer _timer;
    private DateTimeOffset _lastActivity;
    public event Action? SessionExpired;

    public SessionMonitor(TimeProvider time, TimeSpan idleTimeout)
    {
        (_time, _idleTimeout, _lastActivity) = (time, idleTimeout, time.GetUtcNow());

        // 1초마다 확인한다. 실제 시계인지 가짜 시계인지 이 코드는 모른다.
        _timer = time.CreateTimer(_ => Check(), null,
            dueTime: TimeSpan.FromSeconds(1), period: TimeSpan.FromSeconds(1));
    }

    public void RecordActivity() => _lastActivity = _time.GetUtcNow();

    private void Check()
    {
        if (_time.GetUtcNow() - _lastActivity >= _idleTimeout) SessionExpired?.Invoke();
    }

    public void Dispose() => _timer.Dispose();
}
```

테스트는 이렇게 쓴다.

```csharp
using Microsoft.Extensions.Time.Testing;

public class SessionMonitorTests
{
    [Fact]
    public void Expires_AfterIdleTimeout_RaisesEvent()
    {
        // Arrange: 시작 시각을 고정한다.
        var time = new FakeTimeProvider(new DateTimeOffset(2026, 3, 1, 12, 0, 0, TimeSpan.Zero));
        using var sut = new SessionMonitor(time, TimeSpan.FromMinutes(30));
        int expiredCount = 0;
        sut.SessionExpired += () => expiredCount++;

        // Act: 29분을 흘려보낸다.
        time.Advance(TimeSpan.FromMinutes(29));
        Assert.Equal(0, expiredCount);              // 아직 만료 아님
        time.Advance(TimeSpan.FromMinutes(1));      // 1분 더 — 정확히 경계

        // Assert
        Assert.True(expiredCount > 0);
    }
}
```

**30분 만료를 30분 기다리지 않고 검증했다.** 그리고 이 테스트는 서머타임 전환일에도, 연말에도, 느린 CI 러너에서도 같은 결과를 낸다.

`FakeTimeProvider`의 주요 멤버는 다음과 같다.

| 멤버 | 동작 |
|---|---|
| `new FakeTimeProvider()` | 고정된 기본 시각에서 시작 |
| `new FakeTimeProvider(DateTimeOffset)` | 지정한 시각에서 시작 |
| `Advance(TimeSpan)` | 시각을 앞으로 밀고, **그 구간에 도달한 타이머 콜백을 실행**한다 |
| `SetUtcNow(DateTimeOffset)` | 특정 시각으로 점프 |
| `AutoAdvanceAmount` | `GetUtcNow()`를 부를 때마다 자동으로 흐르는 양. 기본 `TimeSpan.Zero` |
| `SetLocalTimeZone(TimeZoneInfo)` | 타임존을 바꿔 DST 시나리오를 재현 (37.7절). 읽기는 `LocalTimeZone` |

> **💡 `AutoAdvanceAmount`로 "시간이 흐르지 않아서" 생기는 무한 루프를 피하라**
>
> 가짜 시계의 기본 동작은 **완전 정지**다. `while (_time.GetUtcNow() < deadline)` 같은 폴링 루프가 프로덕션 코드에 있으면 테스트는 영원히 돈다.
>
> `time.AutoAdvanceAmount = TimeSpan.FromMilliseconds(1);`을 설정하면 `GetUtcNow()` 호출마다 1밀리초씩 자동으로 흐른다. 폴링 코드를 테스트할 때 유용하다.
>
> 다만 이 증상 자체가 설계 피드백이라는 점을 놓치지 마라 — **폴링 루프는 대개 `PeriodicTimer`나 이벤트로 대체되어야 한다.**

> **⚠️ DST 경계에서만 깨지는 코드는 `LocalTimeZone`으로 재현하라**
>
> 37.7절에서 본 "존재하지 않는 시각"과 "중복되는 시각"은 실무 장애의 단골이다. 그런데 이 버그는 1년에 두 번, 특정 시간대에서만 나타난다.
>
> `FakeTimeProvider`의 `LocalTimeZone`을 DST가 있는 지역으로 설정하고 전환 시점 전후로 `SetUtcNow`를 옮기면, 그 시나리오를 **아무 날에나** 재현할 수 있다. 한국 표준시(KST)에는 DST가 없으므로 국내 개발 머신에서는 절대 재현되지 않는다는 점이 특히 위험하다.

### 난수

`Random`은 두 가지 다른 문제를 만든다.

```csharp
// 문제 1: 결과를 예측할 수 없다.
public string GenerateCoupon() => new string(Enumerable.Range(0, 8)
    .Select(_ => Chars[Random.Shared.Next(Chars.Length)]).ToArray());

// 문제 2: Guid도 같은 문제다.
public Order Create() => new() { Id = Guid.NewGuid(), /* ... */ };
```

해법은 세 단계로 나뉜다.

**1단계 — 시드를 고정한다.** 가장 가벼운 방법이다. `Random`은 시드가 같으면 같은 수열을 낸다.

```csharp
public class CouponGenerator
{
    private readonly Random _random;
    public CouponGenerator(Random? random = null) => _random = random ?? Random.Shared;
    public string Generate() { /* _random 사용 */ }
}

[Fact]
public void Generate_WithFixedSeed_IsDeterministic()
{
    var sut = new CouponGenerator(new Random(Seed: 12345));

    var first = sut.Generate();
    var second = sut.Generate();

    Assert.NotEqual(first, second);
    Assert.All(new[] { first, second }, c => Assert.Equal(8, c.Length));
}
```

> **⚠️ 시드가 같으면 같은 수열이 나온다는 보장은 런타임 버전을 넘지 않는다**
>
> `new Random(42)`가 만드는 구체적인 수열은 **문서화된 계약이 아니다.** .NET Core 3.0에서 `Random`의 내부 알고리즘이 바뀌었고, 앞으로도 바뀔 수 있다.
>
> 따라서 `Assert.Equal("A7K2M9QX", sut.Generate())`처럼 **구체적인 출력값을 하드코딩한 테스트는 런타임 업그레이드에서 깨진다.** 시드 고정으로 검증할 것은 "결정론적이다", "길이가 8이다", "허용된 문자만 쓴다" 같은 **성질**이지 특정 값이 아니다.

**2단계 — 난수원을 추상화한다.** 특정 값이 나왔을 때의 동작을 테스트해야 하면 값을 직접 지시할 수 있어야 한다. `int Next(int)`와 `double NextDouble()`만 담은 좁은 인터페이스를 정의하고, 프로덕션 구현은 `Random.Shared`에 위임하고 테스트 구현은 `Queue<int>`에서 정해진 값을 순서대로 꺼내게 한다. 이제 "A/B 테스트에서 10% 그룹에 배정되었을 때"를 정확히 재현할 수 있다.

**3단계 — 식별자는 아예 밖에서 받는다.** `Guid.NewGuid()`는 `Random`보다 더 다루기 어렵다. 시드가 없기 때문이다. 실무에서 가장 단순한 해법은 ID 생성을 팩터리로 밀어내는 것이다.

```csharp
public interface IIdGenerator { Guid NewId(); }
public sealed class GuidIdGenerator : IIdGenerator { public Guid NewId() => Guid.NewGuid(); }

public sealed class SequentialIdGenerator : IIdGenerator      // 테스트용
{
    private int _n;
    public Guid NewId() => new($"00000000-0000-0000-0000-{++_n:D12}");
}
```

테스트 로그에 `00000000-0000-0000-0000-000000000003`이 찍히는 것과 무작위 GUID가 찍히는 것의 디버깅 편의 차이는 크다(80.7절).

### 파일 시스템

가장 흔하고 가장 쉽게 잘못 다뤄지는 의존성이다. 다음 세 층위의 해법이 있고, **위로 갈수록 낫다.**

```text
┌──────────────────────────────────────────────────────────┐
│ 층위 1 (권장): Stream을 받는다 → 테스트는 MemoryStream    │
│                추상화 0개, 패키지 0개                     │
├──────────────────────────────────────────────────────────┤
│ 층위 2: 좁은 인터페이스를 직접 만든다 (IReportStore 등)   │
│                → 테스트는 Dictionary 기반 페이크          │
├──────────────────────────────────────────────────────────┤
│ 층위 3: 파일 시스템 전체 추상화 (IFileSystem)             │
│                → File.* 호출이 흩어진 레거시에 적합       │
├──────────────────────────────────────────────────────────┤
│ 층위 0: 실제 임시 디렉터리 (통합 테스트에서만)            │
└──────────────────────────────────────────────────────────┘
```

**층위 1**이 압도적으로 자주 정답이다.

```csharp
// 나쁨: 경로를 받고 파일을 연다.
public void ExportCsv(IEnumerable<Order> orders, string path)
{
    using var writer = new StreamWriter(path);
    foreach (var o in orders) writer.WriteLine($"{o.Id},{o.Total}");
}

// 좋음: 스트림을 받는다. 파일을 여는 결정은 호출자의 것이다.
public void ExportCsv(IEnumerable<Order> orders, Stream destination)
{
    using var writer = new StreamWriter(destination, leaveOpen: true);
    foreach (var o in orders) writer.WriteLine($"{o.Id},{o.Total}");
}
```
```csharp
[Fact]
public void ExportCsv_TwoOrders_WritesTwoLines()
{
    using var buffer = new MemoryStream();

    Exporter.ExportCsv(new[] { Order1, Order2 }, buffer);

    var lines = Encoding.UTF8.GetString(buffer.ToArray())
        .Split(Environment.NewLine, StringSplitOptions.RemoveEmptyEntries);

```

패키지 0개, 인터페이스 0개, 임시 파일 0개다. 그리고 이 API는 테스트가 아닌 곳에서도 더 유용하다 — HTTP 응답 스트림에도, 압축 스트림에도 그대로 쓸 수 있다. **테스트 가능성이 좋은 API 설계와 같은 방향을 가리키는 전형적인 사례다**(78장).

**층위 3**은 기존 코드가 `File.*`을 곳곳에서 부르고 있어 스트림으로 바꿀 수 없을 때 쓴다. `System.IO.Abstractions` 패키지가 `IFileSystem`을 제공하고, `System.IO.Abstractions.TestingHelpers`가 메모리 기반 구현을 제공한다.

```csharp
public class ConfigLoader
{
    private readonly IFileSystem _fs;
    public ConfigLoader(IFileSystem fs) => _fs = fs;
    public string[] Load(string path)
        => _fs.File.Exists(path) ? _fs.File.ReadAllLines(path) : Array.Empty<string>();
}
```

```csharp
[Fact]
public void Load_MissingFile_ReturnsEmpty()
{
    var fs = new MockFileSystem();       // 실제 디스크를 건드리지 않는다
    Assert.Empty(new ConfigLoader(fs).Load(@"C:\app\missing.txt"));
}
```

> **⚠️ 파일 시스템 추상화는 파일 시스템의 의미론을 재현하지 못한다**
>
> 메모리 기반 파일 시스템은 경로 정규화, 대소문자 구분, 잠금, 동시 접근, 권한, 긴 경로, 심볼릭 링크를 **실제 OS와 다르게** 처리한다. 특히 Windows와 Linux의 경로 대소문자 규칙 차이는 테스트에서 잡히지 않는다.
>
> 그래서 파일 I/O가 로직의 핵심인 코드(백업 도구, 동기화 클라이언트)는 **실제 임시 디렉터리를 쓰는 통합 테스트**가 반드시 함께 있어야 한다. 추상화는 단위 테스트를 빠르게 만들 뿐, 통합 테스트를 대체하지 않는다.

실제 디렉터리를 쓸 때는 정리를 `IDisposable`에 묶는 것이 안전하다(33장).

```csharp
public sealed class TempDirectory : IDisposable
{
    public string Path { get; } =
        System.IO.Path.Combine(System.IO.Path.GetTempPath(), Guid.NewGuid().ToString("N"));

    public TempDirectory() => Directory.CreateDirectory(Path);

    public void Dispose()
    {
        try { Directory.Delete(Path, recursive: true); }
        catch (IOException) { /* 다른 프로세스가 잡고 있으면 포기한다 */ }
    }
}
```

`Guid`로 디렉터리 이름을 만드는 것이 중요하다. 고정된 이름을 쓰면 **병렬 실행되는 테스트끼리 충돌한다.**

## 80.5 통합 테스트와 테스트 컨테이너

### 단위 테스트가 증명하지 못하는 것

단위 테스트를 아무리 많이 써도 답하지 못하는 질문이 있다. **"조립했을 때 돌아가는가?"** DI 컨테이너 등록이 빠졌는지, 커넥션 문자열이 틀렸는지, 미들웨어 순서가 뒤바뀌었는지, EF Core가 만든 SQL이 실제 DB에서 실행되는지는 단위 테스트의 사각지대다.

통합 테스트는 이 사각지대를 덮는다. 대신 느리고 환경에 의존한다. 그래서 **개수를 적게 유지하고 시나리오를 신중히 고르는 것**이 설계의 전부다.

| 축 | 단위 테스트 | 통합 테스트 |
|---|---|---|
| 개수 | 수백~수천 | 수십 |
| 실행 시간 | 전체 10초 이내 | 분 단위 허용 |
| 검증 대상 | 로직의 정확성 | **배선(wiring)과 계약** |
| 실패 시 | 어느 줄이 틀렸는지 즉시 안다 | "어딘가 깨졌다"만 안다 |
| 언제 돌리나 | 저장할 때마다 | PR 게이트 / 야간 |

### `WebApplicationFactory<T>` — 앱을 메모리에서 띄우기

ASP.NET Core 앱은 `Microsoft.AspNetCore.Mvc.Testing` 패키지로 **실제 포트를 열지 않고** 전체 파이프라인을 인메모리 서버에 띄울 수 있다.

```xml
<PackageReference Include="Microsoft.AspNetCore.Mvc.Testing" Version="8.*" />
```
```csharp
public class OrdersApiTests : IClassFixture<WebApplicationFactory<Program>>
{
    private readonly WebApplicationFactory<Program> _factory;
    public OrdersApiTests(WebApplicationFactory<Program> factory) => _factory = factory;

    [Fact]
    public async Task GetOrder_UnknownId_Returns404()
    {
        HttpClient client = _factory.CreateClient();

        var response = await client.GetAsync($"/orders/{Guid.NewGuid()}");

        Assert.Equal(HttpStatusCode.NotFound, response.StatusCode);
    }
}
```

`CreateClient()`가 돌려주는 `HttpClient`는 TCP를 쓰지 않는다. `TestServer`가 요청을 미들웨어 파이프라인에 직접 주입한다. 라우팅·모델 바인딩·필터·인증이 전부 실제로 실행되고, 네트워크 스택만 빠진다.

일부 의존성만 바꾸려면 `WithWebHostBuilder`로 서비스 등록을 덮어쓴다.

```csharp
var client = _factory.WithWebHostBuilder(builder =>
    builder.ConfigureTestServices(services =>
    {
        // 실제 결제 게이트웨이만 페이크로 교체한다. 나머지는 그대로.
        services.RemoveAll<IPaymentGateway>();
        services.AddSingleton<IPaymentGateway, FakePaymentGateway>();
    })).CreateClient();
```

> **⚠️ `Program` 클래스가 보이지 않는다는 컴파일 오류**
>
> 최상위 문(top-level statements)으로 작성된 ASP.NET Core 앱의 `Program` 클래스는 컴파일러가 자동 생성하며 **`internal`** 이다. 테스트 프로젝트에서 `WebApplicationFactory<Program>`을 쓰면 접근할 수 없다.
>
> 해결책은 두 가지다. 웹 프로젝트에 `InternalsVisibleTo`를 추가하거나(17.2절), `Program.cs` 맨 아래에 다음 한 줄을 넣는다.
>
> ```csharp
> public partial class Program { }   // 테스트에서 참조하기 위해 public으로 승격
> ```
>
> 후자가 관행이다. `partial`이므로 컴파일러가 생성한 `Program`과 병합된다.

> **⚠️ `ConfigureServices`가 아니라 `ConfigureTestServices`다**
>
> `builder.ConfigureServices(...)`로 등록한 서비스는 앱의 `Program.cs`가 등록하기 **전에** 실행되어 덮어써진다. `ConfigureTestServices`는 앱의 등록이 모두 끝난 **뒤에** 실행되므로 교체가 실제로 적용된다.
>
> 이 실수는 "테스트 대역을 등록했는데 실제 구현이 호출된다"는 형태로 나타나고, 원인을 찾는 데 몇 시간이 걸린다.

### 인메모리 데이터베이스의 함정

통합 테스트에서 DB를 어떻게 할 것인가. 가장 손쉬운 답은 `Microsoft.EntityFrameworkCore.InMemory`인데, **이것이 실무에서 가장 비싼 지름길이다.**

> **⚠️ EF Core InMemory 공급자는 관계형 데이터베이스가 아니다**
>
> EF Core의 InMemory 공급자는 이름 그대로 **인메모리 객체 저장소**이며 관계형 데이터베이스를 흉내 내지 않는다. EF Core 팀 자신이 테스트용으로 권장하지 않는다고 명시해 왔다. 구체적으로 무엇이 다른가.
>
> | 실제 관계형 DB | InMemory 공급자 |
> |---|---|
> | 참조 무결성 제약을 위반하면 실패 | **통과한다** — 외래 키 제약이 없다 |
> | 고유 인덱스 위반 시 실패 | **통과한다** |
> | `NOT NULL` 위반 시 실패 | 통과할 수 있다 |
> | 트랜잭션·롤백 동작 | **트랜잭션이 무시된다** |
> | 번역 불가 LINQ는 예외 또는 클라이언트 평가 | **전부 LINQ to Objects로 실행된다** |
> | `string` 비교가 DB 콜레이션을 따름 | .NET의 순서 비교를 따름 |
> | 동시성 토큰 검사 | 제한적 |
>
> 마지막에서 두 번째가 특히 위험하다. `Where(o => o.Name.ToLower().Contains(term))` 같은 쿼리는 InMemory에서 완벽히 동작하고 **SQL Server에서 런타임 예외로 터진다.** 테스트는 전부 초록불인데 프로덕션이 죽는다.

대안은 두 가지다.

**대안 1 — SQLite 인메모리 모드.** 진짜 관계형 엔진이면서 프로세스 안에서 돌고 빠르다.

```csharp
public sealed class SqliteFixture : IDisposable
{
    private readonly SqliteConnection _connection;
    public SqliteFixture()
    {
        // 연결을 열어 둔 동안만 DB가 존재한다. 닫으면 사라진다.
        _connection = new SqliteConnection("DataSource=:memory:");
        _connection.Open();
        using var context = CreateContext();
        context.Database.EnsureCreated();
    }

    public AppDbContext CreateContext() => new(new DbContextOptionsBuilder<AppDbContext>()
        .UseSqlite(_connection).Options);

    public void Dispose() => _connection.Dispose();
}
```

> **⚠️ SQLite 인메모리는 연결을 닫는 순간 데이터베이스가 사라진다**
>
> `DataSource=:memory:`로 만든 DB의 수명은 **연결의 수명**이다. `DbContext`를 `using`으로 감싸면 컨텍스트가 연결을 닫고, 다음 컨텍스트는 빈 DB를 본다.
>
> 위 코드처럼 **`SqliteConnection`을 픽스처가 직접 열어서 붙들고**, 그 연결 객체를 `UseSqlite`에 넘겨야 여러 컨텍스트가 같은 DB를 본다.
>
> 그리고 SQLite도 완벽한 대역은 아니다. 데이터 타입 체계(동적 타입), `DateTimeOffset` 저장, 대소문자 구분, 스키마 변경 기능이 SQL Server/PostgreSQL과 다르다. **마이그레이션 검증에는 쓸 수 없다.**

**대안 2 — Testcontainers.** 진짜 데이터베이스를 Docker 컨테이너로 테스트 중에 띄운다.

| 접근 | 충실도 | 속도 | 요구 사항 |
|---|---|---|---|
| EF Core InMemory | **매우 낮음** | 가장 빠름 | 없음 |
| 직접 만든 페이크 저장소 | 낮음(계약 테스트로 보완) | 가장 빠름 | 없음 |
| SQLite 인메모리 | 중간 | 빠름 | 없음 |
| Testcontainers | **실제와 동일** | 느림(컨테이너 기동) | **Docker** |
| 공유 개발 DB | 실제와 동일 | 느림 | 서버 + **테스트 간 격리 문제** |

> **💡 데이터 접근 계층만 통합 테스트로 덮고, 나머지는 페이크로 가라**
>
> "모든 테스트를 실제 DB로 돌리면 확실하지 않나"는 유혹이 있다. 실제로 해 보면 스위트가 20분이 되고, 병렬 실행이 데이터 충돌을 일으키고, 결국 아무도 로컬에서 돌리지 않게 된다.
>
> 현실적 배치는 이렇다.
> - **저장소 구현**(`SqlOrderRepository`)은 Testcontainers로 계약 테스트를 돌린다. 80.2절의 `OrderRepositoryContractTests`를 그대로 재사용한다.
> - **그 위의 모든 것**(서비스, 핸들러, 도메인)은 인메모리 페이크로 단위 테스트한다. 페이크가 실제와 같게 동작한다는 것은 이미 계약 테스트가 보장한다.
> - **API 표면**은 `WebApplicationFactory`로 몇 개의 스모크 테스트만 둔다 — 라우팅·직렬화·인증 배선 확인용.
>
> 이렇게 하면 느린 테스트의 개수가 저장소 구현 수에 비례해 고정되고, 기능이 늘어도 스위트 시간이 선형으로 늘지 않는다.

> **⚠️ CI에서 Docker를 쓸 수 없는 환경을 먼저 확인하라**
>
> Testcontainers는 **Docker 데몬에 접근할 수 있어야** 동작한다. 컨테이너 안에서 도는 CI 러너, Docker-in-Docker가 막힌 보안 정책, 일부 관리형 러너에서는 쓸 수 없다.
>
> 이 경우 통합 테스트가 CI에서 조용히 스킵되거나 전부 실패한다. `[Trait("Category", "Integration")]`으로 분리해 두면 최소한 **실행되지 않았다는 사실이 보인다.** "테스트가 통과했다"와 "테스트가 실행되지 않았다"를 구분할 수 없는 파이프라인이 가장 위험하다.

## 80.6 성능 테스트를 테스트 스위트에 넣기

### 벤치마크와 성능 테스트는 다른 물건이다

67장 전체가 벤치마킹을 다뤘다. 여기서 반복하지 않는다. 대신 구분을 명확히 하자.

| | 벤치마크 (67.3절) | 성능 **테스트** (이 절) |
|---|---|---|
| 질문 | "얼마나 빠른가" | "느려지지 **않았는가**" |
| 출력 | 수치와 통계 분포 | **통과/실패** |
| 실행 위치 | 전용 실행, 조용한 머신 | 일반 테스트 스위트 |
| 소요 시간 | 분~시간 | 밀리초~초 |
| 도구 | BenchmarkDotNet | xUnit + 어서션 |

BenchmarkDotNet 벤치마크를 `[Fact]` 안에서 부르는 것은 **하면 안 된다.** BenchmarkDotNet은 Release 빌드로 별도 프로세스를 띄우고 워밍업과 다중 반복을 수행하는 도구다. 테스트 호스트 안에서 돌리면 워밍업이 오염되고 시간이 폭발한다. 67.8절이 제시한 대로 **CI 파이프라인의 별도 단계**에서 실행하고, JSON 결과를 기준선과 비교하는 것이 벤치마크의 자리다.

그렇다면 테스트 스위트에는 무엇을 넣는가. **결정론적인 지표**만 넣는다.

### 할당 어서션 — 시간 대신 바이트를 단언한다

67.8절에서 CI 게이트의 1순위 지표가 `Allocated`였던 이유가 여기서도 그대로 적용된다. **같은 코드는 항상 같은 바이트를 할당한다.** 머신 속도, 부하, 온도와 무관하다. 그래서 시간과 달리 **일반 단위 테스트에서 단언할 수 있다.**

.NET은 스레드 단위 누적 할당량을 조회하는 API를 제공한다.

```csharp
long before = GC.GetAllocatedBytesForCurrentThread();
// ... 측정 대상 ...
long allocated = GC.GetAllocatedBytesForCurrentThread() - before;
```

이것을 테스트 헬퍼로 감싼다.

```csharp
public static class AllocationAssert
{
    /// <summary>지정한 동작의 할당량이 상한 이하인지 단언한다.</summary>
    public static void AtMost(long maxBytes, Action action, int warmup = 3)
    {
        // JIT과 정적 초기화를 먼저 끝낸다. 없으면 첫 호출에 타입 초기화·JIT 할당이 섞인다.
        for (int i = 0; i < warmup; i++) action();

        long before = GC.GetAllocatedBytesForCurrentThread();
        action();
        long actual = GC.GetAllocatedBytesForCurrentThread() - before;

        Assert.True(actual <= maxBytes,
            $"할당량이 상한을 넘었다: {actual} B (상한 {maxBytes} B, 초과 {actual - maxBytes} B)");
    }

    /// <summary>완전 무할당을 단언한다.</summary>
    public static void Zero(Action action) => AtMost(0, action);
}
```

이제 68장·69장에서 공들여 없앤 할당이 **다시 살아나는 것을 테스트가 막는다.**

```csharp
[Fact]
public void ParseHeader_ValidInput_AllocatesNothing()
{
    // Span 기반 파서는 문자열을 하나도 만들지 않아야 한다.
    AllocationAssert.Zero(() => HeaderParser.TryParse("Content-Length: 1024", out _, out _));
}

[Fact]
public void FormatOrderId_TypicalOrder_AllocatesAtMostOneString()
{
    var order = new Order { Id = 12345 };

    // 문자열 하나(약 40바이트) 외에는 아무것도 할당하지 않는다.
    AllocationAssert.AtMost(64, () => _ = Formatter.FormatOrderId(order));
}
```

실패 메시지가 정확히 몇 바이트 초과인지 말해 준다는 점이 중요하다(80.7절).

> **⚠️ 할당 어서션은 상한(≤)이지 등식(==)이 아니다**
>
> `Assert.Equal(56, allocated)`로 쓰고 싶은 유혹이 있지만 하면 안 된다. 정확한 바이트 수는 다음 요인으로 **정당하게** 변한다.
>
> - 런타임 버전 (객체 헤더·정렬·내부 구현 변경, 61장)
> - 32비트 대 64비트 (참조 크기)
> - 서버 GC 대 워크스테이션 GC의 할당 컨텍스트 크기 (65장)
> - `string` 인터닝 여부
>
> 상한으로 쓰면 이런 변동을 흡수하면서도 **"두 배 늘었다"는 회귀는 잡는다.** 상한은 실측값에 20~50% 여유를 두고 정하되, 0바이트를 목표로 하는 코드에는 `Zero`를 쓴다.

> **⚠️ `GC.GetAllocatedBytesForCurrentThread`는 현재 스레드만 센다**
>
> 이름 그대로다. 측정 대상이 `Task.Run`으로 다른 스레드에 일을 넘기거나, `await` 후에 다른 스레드에서 재개되면(47.12절) **그쪽 할당은 세어지지 않는다.**
>
> 비동기 코드의 할당을 재려면 프로세스 전체를 보는 `GC.GetTotalAllocatedBytes(precise: true)`를 쓸 수 있지만, 이 값은 **다른 테스트의 병렬 실행에 오염된다.** 병렬 실행을 끈 전용 컬렉션에 넣거나(80.1절), 비동기 할당 검증은 BenchmarkDotNet의 `[MemoryDiagnoser]`에 맡기는 편이 낫다(67.5절).

### 시간 어서션은 어떻게 할 것인가

"이 메서드는 100ms 이내에 끝나야 한다" 같은 단언을 테스트에 넣고 싶어진다. 결론부터 말하면 **일반 스위트에는 넣지 마라.**

> **⚠️ 시간 어서션은 CI에서 플래키 테스트가 된다**
>
> CI 러너는 공유 하드웨어에서 돌고, 다른 작업과 CPU를 나눠 쓰며, 계층형 컴파일(55장)로 인해 초반 실행이 느리다. 로컬에서 20ms인 코드가 CI에서 300ms가 되는 일은 일상이다.
>
> 그 결과는 정해져 있다 — 임계값을 올린다 → 또 실패한다 → 더 올린다 → **임계값이 의미를 잃는다** → 테스트를 지운다.

시간 관련 단언을 정당하게 쓸 수 있는 경우는 딱 셋이다.

1. **타임아웃 상한** — "무한 대기하지 않는다"의 검증. 임계값을 기대치의 10배쯤 크게 잡는다. 이건 성능 테스트가 아니라 **행(hang) 탐지**다.
2. **복잡도 검증** — 절대 시간이 아니라 **비율**을 본다. 입력을 10배로 늘렸을 때 시간이 10배 근처인지(선형) 100배인지(제곱). 비율은 머신 속도에 둔감하다.
3. **가짜 시계 기반 논리 시간** — 80.4절의 `FakeTimeProvider`. 이건 실제 시간이 아니므로 완전히 결정론적이다.

```csharp
[Fact]
public async Task ProcessAsync_LargeBatch_CompletesWithinTimeout()
{
    using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(30));

    // 성능 측정이 아니라 "멈추지 않는다"의 검증이다.
    await new BatchProcessor().ProcessAsync(LargeBatch, cts.Token);
}
```

```csharp
[Fact]
public void Search_TenTimesMoreItems_IsNotQuadratic()
{
    double t1 = Measure(() => BuildIndex(1_000).Search("term"));
    double t2 = Measure(() => BuildIndex(10_000).Search("term"));

    // 선형이면 비율이 10 근처, 제곱이면 100 근처다.
    // 노이즈를 크게 허용해도 O(n²) 회귀는 확실히 걸린다.
    Assert.True(t2 / t1 < 30, $"확장 비율이 {t2 / t1:F1}배다 — 제곱 복잡도로 회귀했을 수 있다");
}
```

> **💡 성능 테스트의 계층 배치**
>
> | 계층 | 무엇 | 어디서 |
> |---|---|---|
> | 1 | 할당 어서션(`Zero`/`AtMost`) | **일반 단위 테스트 스위트.** 빠르고 결정론적 |
> | 2 | 복잡도 비율, 행 탐지 타임아웃 | 일반 스위트. 임계값을 넉넉히 |
> | 3 | BenchmarkDotNet + 기준선 비교 | **CI 별도 단계** (67.8절) |
> | 4 | 부하·스트레스 테스트 | 전용 환경, 릴리스 전 |
>
> 1과 2가 개발자의 즉각적 피드백을 담당하고, 3이 회귀 게이트를, 4가 용량 계획을 담당한다. **1을 건너뛰고 3부터 시작하는 팀이 많은데, 그러면 할당 회귀가 CI까지 가서야 발견된다.**

## 80.7 디버깅이 쉬운 코드를 만드는 습관

### 실패 메시지가 곧 디버깅 예산이다

테스트가 실패했을 때 개발자가 하는 일은 둘 중 하나다. 메시지를 읽고 **10초 만에** 원인을 아는 것, 또는 디버거를 붙이고 **20분을** 쓰는 것. 이 차이를 만드는 것은 코드의 복잡도가 아니라 **메시지에 담긴 정보의 양**이다.

```csharp
Assert.True(result.IsValid);   // 0점: 무엇이 왜 틀렸는지 아무 정보가 없다.

Assert.True(result.IsValid, $"검증 실패: {result.ErrorCode}");   // 60점: 값 하나가 보인다.

Assert.True(result.IsValid,    // 100점: 입력·기대·실제가 전부 보인다.
    $"입력 '{input}'에 대해 검증이 실패했다. " +
    $"코드={result.ErrorCode}, 메시지={result.ErrorMessage}");
```

같은 원칙이 **프로덕션 예외 메시지**에도 적용된다. 32장이 예외의 메커니즘을 다뤘다면, 여기서는 메시지의 내용을 다룬다.

```csharp
throw new InvalidOperationException("잘못된 상태");   // 나쁨 — 로그를 봐도 할 일이 없다.

// 좋음 — 무엇이, 무엇이어야 했고, 지금 무엇인지.
throw new InvalidOperationException(
    $"주문 {order.Id}은(는) '{order.Status}' 상태에서 배송할 수 없다. " +
    $"'{OrderStatus.Paid}' 상태여야 한다.");
```

> **💡 예외 메시지에 담을 세 가지**
>
> 1. **무엇이** — 대상의 식별자 (`order.Id`, 파일 경로, 사용자 ID)
> 2. **무엇이어야 했는가** — 기대한 조건
> 3. **실제로 무엇인가** — 관찰된 값
>
> 셋이 다 있으면 로그 한 줄로 재현 없이 원인을 안다. 80.4절에서 순차 ID 생성기를 권한 이유도 이것이다 — 무작위 GUID 대신 `...000000000003`이 찍히면 로그를 눈으로 따라갈 수 있다.
>
> 단, **비밀 값은 넣지 마라.** 비밀번호, 토큰, 개인 정보가 예외 메시지에 담기면 로그 수집 시스템 전체가 유출 경로가 된다(75장).

### 인수 검증 — 가드 절

32장이 소개한 원칙을 다시 확인하자. 함수가 매개변수를 받으면 **값을 검사하고, 함수가 제대로 동작할 수 없는 값이면 예외를 던져야 한다.** 사용 오류(usage error)를 위해 새 예외 타입을 정의할 일은 거의 없다 — .NET이 이미 충분히 정의해 두었다.

```csharp
static void Withdraw(string accountName, decimal amount)
{
    if (string.IsNullOrWhiteSpace(accountName))
        throw new ArgumentException(
            message: $"{nameof(accountName)} cannot be null or whitespace.",
            paramName: nameof(accountName));

    if (amount <= 0)
        throw new ArgumentOutOfRangeException(paramName: nameof(amount),
            message: $"{nameof(amount)} cannot be negative or zero.");

    // 매개변수를 처리한다
}
```

.NET 6부터 도입되고 .NET 8에서 확장된 **가드 절(guard clause)** 정적 메서드를 쓰면 같은 코드가 짧아진다.

| 예외 | 가드 절 메서드 |
|---|---|
| `ArgumentException` | `ThrowIfNullOrEmpty`, `ThrowIfNullOrWhiteSpace` |
| `ArgumentNullException` | `ThrowIfNull` |
| `ArgumentOutOfRangeException` | `ThrowIfEqual`, `ThrowIfGreaterThan`, `ThrowIfGreaterThanOrEqual`, `ThrowIfLessThan`, `ThrowIfLessThanOrEqual`, `ThrowIfNegative`, `ThrowIfNegativeOrZero`, `ThrowIfNotEqual`, `ThrowIfZero` |

```csharp
static void Withdraw(string accountName, decimal amount)
{
    ArgumentException.ThrowIfNullOrWhiteSpace(accountName,
        paramName: nameof(accountName));
    ArgumentOutOfRangeException.ThrowIfNegativeOrZero(amount,
        paramName: nameof(amount));
    // 매개변수를 처리한다
}
```

테스트 관점의 이득은 명확하다. 가드 절은 **경계 테스트를 쓸 자리를 만들어 준다.** 0, -1, `null`, 빈 문자열에 대한 `[Theory]` 하나면 진입 계약 전체가 고정된다.

> **⚠️ 반복자·비동기 메서드에서 가드 절은 즉시 실행되지 않는다**
>
> 78.12절에서 본 문제다. `yield return`이 있는 메서드나 `async` 메서드의 본문은 **첫 열거 시점 / 첫 `await` 시점**에야 실행되므로, 메서드 시작부에 둔 가드 절이 호출 즉시 던지지 않는다.
>
> ```csharp
> // 이 호출은 예외를 던지지 않는다. 열거해야 던진다.
> var results = Search(null!);
> ```
>
> 테스트에서는 이것이 `Assert.Throws<ArgumentNullException>(() => sut.Search(null!))`의 실패로 나타난다. 해결책은 검증을 일반 메서드에 두고 본체를 지역 반복자 함수로 분리하는 것이다(79.11절).

### `Debug.Assert` vs 예외 — 판단 기준

두 도구는 **다른 대상을 향한다.**

| | `Debug.Assert` | 예외 (`throw`) |
|---|---|---|
| 대상 | **나 자신** (이 코드의 작성자) | **호출자** |
| 검사하는 것 | 내부 불변 조건(invariant) | 인수·상태의 유효성 |
| 위반의 의미 | **이 코드에 버그가 있다** | 호출 방식이 잘못되었다 |
| Release 빌드 | **사라진다** (`[Conditional("DEBUG")]`) | 남는다 |
| 성능 비용 | 릴리스에서 0 | 검사 비용만큼 |

```csharp
public decimal CalculateTotal(IReadOnlyList<LineItem> items)
{
    ArgumentNullException.ThrowIfNull(items);   // 예외: 호출자의 실수. 릴리스에서도 검사한다.

    decimal total = 0m;
    foreach (var item in items) total += item.Price * item.Quantity;

    // 어서션: 내 알고리즘의 불변 조건. 호출자는 이걸 깰 수 없다.
    // 깨졌다면 위의 루프에 버그가 있다는 뜻이다.
    Debug.Assert(total >= 0m, $"합계가 음수다: {total}");

    return total;
}
```

`Debug.Assert`는 `[Conditional("DEBUG")]`가 붙어 있어(73.1절) **Release 빌드에서는 호출 자체가 컴파일되지 않는다.** 인수까지 통째로 사라지므로 릴리스 성능에 영향이 0이다. 반대로 말하면, **릴리스에서 반드시 검사되어야 하는 것에 `Debug.Assert`를 쓰면 안 된다.**

> **⚠️ 실패한 `Debug.Assert`는 테스트 호스트를 통째로 죽인다**
>
> .NET Framework에서 어서션 실패는 모달 대화 상자를 띄웠다(**.NET Framework 전용 동작**). .NET(Core)에는 대화 상자가 없다. 대신 메시지를 출력하고 **프로세스를 중단시킨다.**
>
> 테스트 실행 중에 이 일이 일어나면 그 테스트 하나가 실패하는 것이 아니라 **테스트 호스트 프로세스가 죽고, 같은 프로세스에서 돌던 다른 테스트 결과가 전부 사라진다.** CI 로그에는 "테스트 호스트 프로세스가 예기치 않게 종료되었습니다"만 남는다.
>
> 그래서 `Debug.Assert`가 있는 코드를 테스트할 때는 **어서션이 걸릴 입력을 테스트에 넣지 않도록** 주의해야 한다. 어서션이 걸리는 상황을 테스트하고 싶다면, 그것은 애초에 어서션이 아니라 예외여야 한다는 신호다.
>
> Release 구성으로 테스트를 돌리면 이 문제가 사라지지만, 그러면 **어서션이 검증하는 것도 함께 사라진다.**

`Trace.Assert`는 `[Conditional("TRACE")]`이며, 기본 릴리스 구성에서도 `TRACE`가 정의되므로 살아남는다. 릴리스에서도 검사가 필요하지만 예외를 던지고 싶지 않은 경우에 쓸 수 있으나, 실무에서는 **예외를 던지거나 로그를 남기는 편**이 대개 낫다.

### 불변 조건을 코드로 표현하기

가장 좋은 불변 조건은 **검사할 필요가 없는 불변 조건**이다. 타입이 그것을 보장하면 어서션도 테스트도 필요 없다.

| 런타임 검사 | 타입으로 제거 |
|---|---|
| `Debug.Assert(x >= 0)` | `uint`, 또는 검증하는 생성자를 가진 `readonly record struct Quantity` |
| `Debug.Assert(list != null)` | 널 허용 참조 형식 활성화 (`<Nullable>enable</Nullable>`) |
| `Debug.Assert(!_disposed)` | `ObjectDisposedException.ThrowIf` — 릴리스에도 남아야 하므로 예외가 맞다 (33장) |
| `Debug.Assert(state == Ready)` | 상태별로 다른 타입 (상태 기계를 타입으로) |
| `Debug.Assert(items.Count > 0)` | 비어 있을 수 없는 컬렉션 타입 |

> **💡 디버깅이 쉬운 코드의 체크리스트**
>
> - **작은 함수.** 스택 프레임 이름이 곧 설명이다. 200줄짜리 메서드의 스택 트레이스는 줄 번호 하나만 준다.
> - **의미 있는 타입 이름.** `[DebuggerDisplay("Order {Id}: {Status}, {Items.Count} items")]`를 붙이면 디버거 변수 창이 읽을 수 있게 된다(74.2절).
> - **불변 객체.** "이 값이 언제 바뀌었는가"를 추적할 필요가 없어진다.
> - **로그에 상관 관계 ID.** 분산 추적의 `Activity.Id`가 그 역할을 한다(75.4절).
> - **`ToString()` 재정의.** 테스트 실패 메시지, 로그, 디버거 창에 동시에 이득이 온다.
> - **`ITestOutputHelper`로 테스트 중간 상태를 남겨라.** xUnit은 `Console.WriteLine` 출력을 잡아 주지 않는다. 생성자로 주입받아 쓴다.
>
> ```csharp
> public class OrderTests
> {
>     private readonly ITestOutputHelper _output;
>     public OrderTests(ITestOutputHelper output) => _output = output;   // 생성자 주입
>
>     [Fact]
>     public void Process_ComplexOrder_Succeeds()
>     {
>         _output.WriteLine($"준비된 주문: {BuildOrder()}");   // 실패 시에만 표시된다
>     }
> }
> ```

마지막으로, 이 장 전체를 한 문장으로 압축하면 이렇게 된다.

> **테스트하기 쉬운 코드, 디버깅하기 쉬운 코드, 읽기 쉬운 코드는 서로 다른 세 가지 목표가 아니라 같은 하나의 성질을 세 방향에서 본 것이다.** 그 성질의 이름은 **명시성**이다 — 입력이 시그니처에 보이고, 결정이 호출자에게 있고, 실패가 스스로를 설명하는 것.

## 이 장의 요약

- **테스트 가능성은 목표가 아니라 좋은 경계 설계의 부산물이다.** 정적 가변 상태, 협력자의 직접 `new`, `DateTime.Now`, 파일 시스템 직접 접근, 거대한 생성자 — 이 징후들은 "테스트 도구가 부족하다"는 신호가 아니라 **그 타입이 호출자의 결정을 대신 내리고 있다**는 신호다.
- **xUnit은 특성이 아니라 언어 규칙으로 격리를 보장한다.** 테스트 메서드마다 테스트 클래스 인스턴스가 새로 만들어지므로 생성자가 Setup이고 `Dispose`가 Teardown이다. 비싼 준비는 `IClassFixture<T>`(클래스 범위)와 `ICollectionFixture<T>`(컬렉션 범위, **병렬성을 대가로 지불한다**)로 공유한다.
- **`[Theory]`의 데이터 소스는 `TheoryData<...>`가 기본이다.** `IEnumerable<object[]>`는 타입 안전성이 없고, `[InlineData]`는 컴파일 타임 상수만 담는다. 데이터 소스는 매번 새 인스턴스를 만들어야 병렬 실행에서 오염되지 않는다.
- **`Assert.True(x == y)`는 실패 메시지에 아무 정보를 남기지 않는다.** 적절한 단언을 고르는 것이 실패 시 디버깅 시간을 좌우한다. `Assert.Throws<T>`는 **정확한 타입**을 요구하므로 파생 예외에는 `ThrowsAny<T>`를 쓴다.
- **주입할 것은 프로세스 밖으로 나가는 것과 환경에서 읽어 오는 것뿐이다.** 순수 함수와 자료구조까지 추상화하면 탐색 불가능성, 호출 그래프 단절, 인라이닝 방해, 변경 비용 역전이라는 대가를 치른다.
- **테스트하려는 로직 자체를 목으로 대체하면 그 테스트는 아무것도 검증하지 않는다.** 목은 관찰 가능한 결과가 없을 때, 프로세스 경계를 넘는 호출에 대해서만 쓴다. 나머지는 스텁과 페이크다. 페이크와 실제 구현은 **계약 테스트**로 같은 검사를 통과시켜라.
- **`async void` 테스트는 거짓 통과한다.** 러너가 완료를 기다릴 방법이 없기 때문이다. `await`하지 않은 `Assert.ThrowsAsync`도 마찬가지로 침묵한다 — 테스트 프로젝트에서 CS4014를 오류로 승격시켜라.
- **sync-over-async 데드락은 대개 테스트에서 재현되지 않는다.** 콘솔 호스트와 ASP.NET Core에는 동기화 컨텍스트가 없기 때문이다. 데드락은 테스트로 잡는 것이 아니라 분석기로 금지하는 것이다.
- **시간·난수·파일 시스템은 시그니처에 보이지 않는 숨은 입력이다.** ※.NET 8의 `TimeProvider`와 `Microsoft.Extensions.TimeProvider.Testing`의 `FakeTimeProvider`(**별도 패키지**)로 30분 타임아웃을 밀리초에 검증할 수 있다. `Task.Delay`·`CancellationTokenSource`·`PeriodicTimer`의 `TimeProvider` 오버로드까지 함께 써야 시간이 완전히 통제된다.
- **파일 의존성 제거의 1순위는 `Stream`을 받는 것이다.** 패키지도 인터페이스도 필요 없고, API가 테스트 밖에서도 더 유용해진다. 파일 시스템 추상화는 레거시 코드용이며, OS 의미론을 재현하지 못하므로 실제 디렉터리를 쓰는 통합 테스트를 대체하지 않는다.
- **EF Core InMemory 공급자는 관계형 데이터베이스가 아니다.** 외래 키·고유 인덱스·트랜잭션을 강제하지 않고 모든 LINQ를 클라이언트에서 평가한다. 테스트는 초록불인데 프로덕션이 죽는다. SQLite 인메모리(연결을 붙들어야 한다)나 Testcontainers를 쓰라.
- **성능 "테스트"는 벤치마크가 아니라 결정론적 지표에 대한 통과/실패다.** 할당량은 결정론적이므로 `GC.GetAllocatedBytesForCurrentThread`로 일반 스위트에서 단언할 수 있다(등식이 아니라 **상한**으로). 시간 어서션은 CI에서 플래키가 되므로 행 탐지와 복잡도 비율에만 쓴다. BenchmarkDotNet은 67.8절대로 CI 별도 단계에 둔다.
- **`Debug.Assert`는 나를 향하고 예외는 호출자를 향한다.** 어서션은 Release에서 사라지고, 실패하면 **테스트 호스트 프로세스를 통째로 죽인다.** 릴리스에서 반드시 검사되어야 하는 것에는 예외를, 그리고 가능하면 검사 자체가 필요 없도록 타입으로 불변 조건을 표현하라.

## 연습 문제

1. `dotnet new classlib`로 `Calculator`를 만들고 `Add`가 `a * b`를 반환하도록 버그를 심어라. `dotnet new xunit` 프로젝트에서 `TestAdding2And2`와 `TestAdding2And3`을 작성해 **하나만 실패**하는 것을 확인하라. 그다음 `.csproj`에서 `xunit.runner.visualstudio` 참조를 지우고 `dotnet test`를 다시 실행해 **테스트가 0개로 보고되는 것**을 확인하라.
2. 테스트 클래스에 `private int _counter;` 필드와 이를 증가시키는 테스트 두 개를 만들어 각 테스트가 항상 `1`을 보는 것을 확인하라. 그다음 `private static int _counter;`로 바꾸고 `dotnet test`를 여러 번 실행해 결과가 실행마다 달라지는 것을 관찰하라. `[assembly: CollectionBehavior(DisableTestParallelization = true)]`를 추가하면 어떻게 달라지는가?
3. `[Theory]`에 `[MemberData]`로 `static readonly List<int>` 하나를 공유하는 데이터 소스를 만들고, 각 테스트 케이스가 그 리스트에 항목을 추가하게 하라. 케이스 순서에 따라 결과가 달라지는 것을 확인한 뒤 `TheoryData<T>`로 바꿔 매번 새 인스턴스를 만들도록 고쳐라.
4. `async void`로 선언한 `[Fact]` 안에 `Assert.Equal(1, 2)`를 넣고 실행하라. 테스트가 통과로 보고되는지, 호스트가 죽는지, 아무 일도 안 일어나는지 관찰하고 러너 로그를 확인하라. `async Task`로 바꿔 정상적으로 실패하는 것과 비교하라.
5. 30초 딜레이가 있는 3회 재시도 로직을 작성하고, 먼저 `Task.Delay(TimeSpan)`으로 테스트해 60초가 걸리는 것을 확인하라. 그다음 `TimeProvider`를 주입하고 `Task.Delay(TimeSpan, TimeProvider, CancellationToken)` 오버로드로 바꾼 뒤 `FakeTimeProvider.Advance`로 같은 시나리오를 검증하고 **실행 시간을 비교**하라.
6. `Order`에 `Number` 컬럼의 고유 인덱스를 선언한 EF Core 모델을 만들어라. 같은 번호를 두 번 저장하는 테스트를 (a) `Microsoft.EntityFrameworkCore.InMemory`, (b) SQLite 인메모리, (c) Testcontainers로 각각 실행해 **어디서 예외가 나고 어디서 조용히 통과하는지** 확인하라. `Where(o => o.Number.ToLower() == x)` 쿼리도 같은 세 환경에서 비교하라.
7. `string.Join`을 쓰는 포맷 메서드와 `Span<char>` 기반 포맷 메서드를 각각 작성하고, 80.6절의 `AllocationAssert.AtMost`로 두 구현의 할당량을 단언하라. `warmup` 횟수를 0으로 바꿨을 때 측정값이 어떻게 달라지는지, 그리고 측정 대상 안에 `Task.Run`을 넣으면 할당이 세어지는지 확인하라.
