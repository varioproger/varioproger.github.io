# 20장. 열거형과 특성(Attribute)

> **이 장의 위치** — Part III「타입 만들기」의 마지막 장이다. 6.6절에서 사용자 정의 타입 다섯 종류를 훑을 때 `enum`을 "이름 붙은 정수 상수의 집합"이라고만 하고 20장으로 미뤘고, 15.1절에서 타입 계층을 그릴 때 `System.Enum`이라는 상자를 그려 놓고 설명은 여기로 넘겼다. 이 장이 그 빚을 갚는다. `enum`과 특성은 겉보기에 전혀 다른 기능이지만 한 가지를 공유한다 — **둘 다 컴파일 타임에만 존재하는 약속이고, 런타임에는 다른 것으로 변해 있다.** `enum`은 정수가 되고, 특성은 메타데이터 안의 바이트 뭉치가 된다. 이 장의 함정은 거의 전부 그 간극에서 나온다.
>
> **선수 지식** — 6장(구문과 타입 기초), 7장(숫자와 불리언 — 특히 7.4절 비트 연산), 13장(클래스와 캡슐화), 15장(`object` 타입과 박싱), 16장(구조체와 값 타입)
>
> **이 장에서 다루지 않는 것** — 특성을 **런타임에 조회하는 방법 전체**(리플렉션 API 계층, `CustomAttributeData`, 캐싱 전략, 트리밍/AOT에서 깨지는 지점)는 57.11절과 57.12절이다. 이 장의 20.9절은 그 입구까지만 안내한다. 진단 코드 관점에서 조건부 컴파일·정적 플래그·`[Conditional]`을 끝까지 비교하는 것은 73.1절이고, 문법 관점의 요약은 12.8절에 이미 있다. 이 장의 20.10절은 **특성 자체의 동작**만 다룬다. 컴파일 타임에 코드를 생성해 특성+리플렉션을 대체하는 소스 생성기는 57.15절, 디버거용 특성(`DebuggerDisplay` 계열)은 74.2절, 널 관련 특성(`NotNullWhen` 계열)은 21.9절, 열거형 형식 문자열의 국제화 맥락은 38.7절이다. 확장 메서드의 문법과 해석 규칙 자체는 6장 이후 계속 써 왔지만 정식 정리는 하지 않았다 — 이 장의 20.5절은 열거형에 쓰는 용법에 한정한다.

## 20.1 `enum`의 기저 타입과 런타임 실체 — "enum은 어떻게 동작하는가"

### 문법 — 이름 붙은 정수 상수의 집합

`enum`은 이름 붙은 숫자 상수 묶음을 정의하는 특별한 값 타입이다.

```csharp
public enum BorderSide { Left, Right, Top, Bottom }
```

쓰는 쪽은 이렇다.

```csharp
BorderSide topSide = BorderSide.Top;
bool isTop = (topSide == BorderSide.Top);   // true
```

각 멤버는 **기저 정수 값(underlying integral value)** 을 하나씩 갖는다. 아무것도 지정하지 않으면 규칙은 둘이다.

- 기저 값의 타입은 `int`다.
- 값은 선언 순서대로 `0, 1, 2, ...`가 자동 배정된다.

기저 타입은 바꿀 수 있다.

```csharp
public enum BorderSide : byte { Left, Right, Top, Bottom }
```

각 멤버의 값을 직접 줄 수도 있다.

```csharp
public enum BorderSide : byte { Left = 1, Right = 2, Top = 10, Bottom = 11 }
```

일부만 지정하는 것도 가능하다. 지정하지 않은 멤버는 **직전 명시값에서 계속 증가**한다. 아래 두 선언은 완전히 같다.

```csharp
public enum BorderSide : byte { Left = 1, Right = 2, Top = 10, Bottom = 11 }
public enum BorderSide : byte { Left = 1, Right,    Top = 10, Bottom      }
```

### 기저 타입으로 쓸 수 있는 여덟 가지

| 기저 타입 | 크기 | 범위 | 실무 용도 |
|---|---|---|---|
| `byte` | 1바이트 | 0 ~ 255 | 멤버가 적고 배열/구조체에 대량으로 박아 넣을 때 |
| `sbyte` | 1바이트 | −128 ~ 127 | 음수 센티널이 필요한 소형 열거형 |
| `short` | 2바이트 | −32,768 ~ 32,767 | 상호운용에서 16비트 코드값을 받을 때 |
| `ushort` | 2바이트 | 0 ~ 65,535 | 16비트 플래그 집합 |
| `int` | 4바이트 | 약 ±21억 | **기본값.** 특별한 이유가 없으면 이것 |
| `uint` | 4바이트 | 0 ~ 약 43억 | 최상위 비트까지 쓰는 32비트 플래그 |
| `long` | 8바이트 | 약 ±9.2×10^18 | 33개 이상의 비트 플래그 |
| `ulong` | 8바이트 | 0 ~ 약 1.8×10^19 | 64비트 전부를 플래그로 쓸 때 |

`char`, `bool`, `decimal`, 부동소수점 타입은 기저 타입이 될 수 없다.

> **⚠️ 기저 타입 자리에는 BCL 타입 이름을 쓸 수 없다**
>
> `enum Color : Int32`는 컴파일되지 않는다. C# 컴파일러는 이 자리에서 **C# 키워드 형태의 원시 타입 이름만** 받는다. 오류 메시지는 다음과 같다.
>
> ```text
> error CS1008: Type byte, sbyte, short, ushort, int, uint, long, or ulong expected
> ```
>
> `int`와 `Int32`가 완전히 같은 타입인데도(6.2절) 여기서만 다르게 취급된다. 컴파일러 구현을 단순하게 유지하기 위한 제약이다. `using` 별칭으로 `Int32`를 `int`에 매핑해도 통하지 않는다.

### 컴파일 결과 — 상수 필드 하나와 인스턴스 필드 하나

여기서부터가 이 절의 핵심이다. `enum`은 문법적으로 특별해 보이지만, 컴파일러가 만들어내는 것은 **구조체 하나**다. C# 컴파일러는 위의 `Color`를 대략 다음과 같이 취급한다.

```csharp
// 실제로 이렇게 쓸 수는 없다 — System.Enum에서 파생하는 것은 C#이 금지한다.
// 컴파일 결과가 무엇인지를 보여주기 위한 의사 선언이다.
internal struct Color : System.Enum
{
    // 각 심볼은 상수 필드가 된다
    public const Color White  = (Color) 0;
    public const Color Red    = (Color) 1;
    public const Color Green  = (Color) 2;
    public const Color Blue   = (Color) 3;
    public const Color Orange = (Color) 4;

    // 값을 담는 유일한 인스턴스 필드. 소스에서 직접 참조할 수 없다.
    public int value__;
}
```

정리하면 열거형은 **상수 필드 여러 개 + 인스턴스 필드 하나**짜리 구조체다. 상수 필드는 어셈블리 메타데이터에 기록되므로 리플렉션으로 전부 꺼낼 수 있고, 그래서 `System.Enum`이 제공하는 온갖 정적 메서드(`GetNames`, `GetValues`, `Parse`)가 성립한다.

실제 IL을 보면 의사 선언과 정확히 대응한다.

```il
.class public auto ansi sealed BorderSide
       extends [System.Runtime]System.Enum
{
  .field public specialname rtspecialname int32 value__
  .field public static literal valuetype BorderSide Left   = int32(0x00000000)
  .field public static literal valuetype BorderSide Right  = int32(0x00000001)
  .field public static literal valuetype BorderSide Top    = int32(0x00000002)
  .field public static literal valuetype BorderSide Bottom = int32(0x00000003)
}
```

읽을 곳은 네 군데다.

- `extends System.Enum` — 기반 타입이 `System.Enum`이다.
- `sealed` — 열거형은 항상 봉인되어 있다. 상속할 수 없다.
- `.field public specialname rtspecialname int32 value__` — 값을 담는 필드. `rtspecialname`은 "런타임이 이름 자체를 특별하게 취급한다"는 표시다. 이 필드 이름이 `value__`인 것은 관례가 아니라 CLR의 규약이다.
- `.field public static literal` — `literal`이 IL에서 `const`에 해당한다. 값이 필드 슬롯이 아니라 메타데이터에 직접 박혀 있다.

### 타입 계층 — 값 타입인데 클래스에서 파생한다

```text
                       System.Object
                             │
                       System.ValueType     (class)
                             │
                        System.Enum         (class, abstract)
                             │
        ┌────────────┬───────┴───────┬────────────────┐
   BorderSide    ConsoleColor   FileAttributes    DayOfWeek     (전부 값 타입)
```

여기서 처음 보면 반드시 걸리는 대목이 있다. `System.ValueType`도 `System.Enum`도 **클래스**(참조 타입)인데, 그것을 상속한 열거형은 **값 타입**이다. 15.1절에서 구조체를 두고 이미 본 구도다. CLR은 "`System.ValueType`을 직접 또는 간접으로 상속하는 타입은 값 타입"이라는 규칙을 특별 취급으로 박아 두었고, `System.Enum`은 그 중간 노드일 뿐이다.

> **📌 열거형은 메서드를 정의할 수 없다**
>
> 열거형은 값 타입이지만 다른 값 타입과 달리 **메서드·프로퍼티·이벤트를 정의할 수 없다.** 인터페이스를 구현할 수도 없다. 정의할 수 있는 것은 이름-값 쌍뿐이다.
>
> 그래서 열거형에 동작을 붙이려면 확장 메서드를 쓴다. 20.5절이 그 이야기다.

### 런타임 동작 — 언박싱 상태에서는 그냥 정수다

CLR 관점에서 **언박싱된 열거형 인스턴스와 그 기저 정수 값 사이에는 아무 차이도 없다.** 지역 변수 `BorderSide side`는 스택에 4바이트를 차지하고, `side == BorderSide.Top` 비교는 `ceq` 하나로 끝난다. 정수 상수를 직접 쓰는 코드와 IL이 동일하다.

```csharp
BorderSide side = BorderSide.Top;
if (side == BorderSide.Top) Console.WriteLine("top");
```

```il
  ldc.i4.2            // BorderSide.Top의 값 2를 그대로 밀어 넣는다
  stloc.0
  ldloc.0
  ldc.i4.2
  bne.un.s  IL_000f
  ldstr     "top"
  call      void [System.Console]System.Console::WriteLine(string)
```

`BorderSide`라는 이름은 IL 어디에도 없다. 상수 필드를 참조하는 순간 컴파일러가 값으로 치환해 버렸기 때문이다. **열거형의 일상적 사용에는 정수 상수와 똑같은 런타임 비용이 든다** — 즉 비용이 없다.

> **⚠️ 열거형 멤버는 `const`다 — 버전 관리 함정이 그대로 따라온다**
>
> 열거형 심볼이 상수 필드라는 사실에는 직접적인 결과가 하나 있다. 컴파일러가 `BorderSide.Top`을 보면 **컴파일 시점에 값 2로 치환**하고, 그 코드는 더 이상 `BorderSide` 타입을 참조하지 않는다.
>
> 라이브러리 A가 `enum LogLevel { Info = 0, Warn = 1, Error = 2 }`를 정의하고, 애플리케이션 B가 `LogLevel.Error`를 쓴다고 하자. B의 IL에는 `2`만 남는다. 나중에 A가 `enum LogLevel { Info = 0, Debug = 1, Warn = 2, Error = 3 }`으로 값을 재배치하고 A만 다시 배포하면, **B를 재컴파일하지 않는 한 B는 계속 2를 보낸다.** 이제 그 2는 `Warn`이다. 컴파일 오류도, 런타임 예외도 없다. 조용히 틀린 값이 흐른다.
>
> 결론은 하나다. **공개 API에 노출된 열거형의 기존 멤버 값은 절대 바꾸지 않는다.** 새 멤버는 끝에 추가하거나 명시적으로 남는 값을 준다. 상수와 `readonly` 필드의 버전 관리 차이는 79.2절에서 더 다룬다.

> **📌 열거형을 정의한 어셈블리가 런타임에 필요 없을 수도 있다**
>
> 위의 성질에는 재미있는 따름정리가 있다. 심볼만 참조하고 열거형 **타입 자체**는 참조하지 않는 코드는, 그 열거형을 정의한 어셈블리 없이도 실행된다. 값이 이미 박혀 있기 때문이다. 반대로 `typeof(LogLevel)`이나 `LogLevel` 타입의 매개변수처럼 타입을 실제로 참조하면 그 어셈블리가 런타임에 필요하다.

### 그런데 `ToString()`은 왜 이름을 돌려주는가

"런타임에는 그냥 정수"라는 말과 다음 코드는 모순처럼 보인다.

```csharp
[Flags] public enum BorderSides { Left = 1, Right = 2, Top = 4, Bottom = 8 }
...
Console.WriteLine (BorderSides.Right.ToString());     // Right
Console.WriteLine (BorderSides.Right.GetType().Name); // BorderSides
```

정수라면 `2`와 `Int32`가 나와야 한다. 답은 다시 컴파일러의 손재주다. **C#은 열거형 인스턴스에 대해 `System.Enum`/`System.Object`가 제공하는 메서드(`ToString`, `Equals`, `GetHashCode`, 그리고 비가상인 `GetType`)를 호출하기 전에 명시적으로 박싱한다.** 열거형 타입 자신은 이 메서드들을 재정의하지 않으므로 값을 그대로 호출할 방법이 없다. 박싱된 순간 힙 객체가 만들어지고, 그 객체의 메서드 테이블 포인터가 `BorderSides`를 가리킨다(54.1절). 그래서 타입 정보가 되살아난다.

```il
  ldc.i4.2
  box        BorderSides         // ← 여기서 열거형 타입이라는 신원이 붙는다
  callvirt   instance string [System.Runtime]System.Object::ToString()
```

> **⚠️ 열거형의 `ToString()`은 박싱을 동반한다**
>
> 열거형 자체는 값 타입이므로 할당이 없지만, `ToString()`·`GetType()`·`Equals(object)`를 부르는 순간 박싱 할당이 발생한다(15.2절). 여기에 `ToString()`이 만드는 문자열 할당이 더해진다. 로그 한 줄에 두 번 할당이 일어나는 셈이라, 초당 수만 건이 흐르는 경로에서는 눈에 띄는 비용이 된다. 열거형→문자열 변환을 뜨거운 경로에서 반복한다면 `switch` 식으로 상수 문자열을 돌려주는 손수 만든 매핑이 훨씬 싸다.
>
> 구조적 대안은 20.5절의 확장 메서드다.

성능 관점의 4단 정리는 이렇다.

- **문법** — 이름-값 쌍 선언. 기저 타입 지정 가능(기본 `int`).
- **컴파일 결과** — `System.Enum`을 상속하는 `sealed` 값 타입. 상수 필드 N개 + `value__` 필드 1개. 심볼 참조는 값으로 치환된다.
- **런타임 동작** — 언박싱 상태에서는 기저 정수와 구별할 수 없다. 가상 메서드를 호출할 때만 박싱되며 그때 타입 신원이 붙는다.
- **성능 영향** — 비교·대입·산술은 정수와 동일해 비용이 0이다. `ToString`·`GetType`·`Equals(object)`, 그리고 구버전 런타임의 `HasFlag`는 박싱을 부른다.

## 20.2 열거형 변환과 값 열거하기

열거형 값은 세 가지 모습으로 존재한다. **열거형 멤버**, **기저 정수 값**, **문자열**이다. 실무 코드의 상당 부분이 이 셋 사이를 오간다.

```text
                    (int) / (BorderSide)
        ┌───────────────────────────────────────┐
        │                                       │
        ▼                                       ▼
  ┌───────────┐                          ┌────────────┐
  │  정수 값   │                          │ 열거형 멤버 │
  │   int 4    │                          │  Side.Top   │
  └───────────┘                          └────────────┘
        ▲                                       │  ToString() / ToString("G")
        │ Enum.ToObject / Convert.ChangeType     ▼
        │                                 ┌────────────┐
        └─────── ToString("D") ───────────│  문자열     │
                  Enum.Parse / TryParse   │   "Top"     │
                                          └────────────┘
```

### 열거형 ↔ 정수 — 왜 명시적 캐스트가 필요한가

두 방향 모두 **명시적 캐스트**가 필요하다.

```csharp
int i = (int) BorderSide.Left;      // 열거형 → 정수
BorderSide side = (BorderSide) i;   // 정수 → 열거형
bool leftOrRight = (int) side <= 2;
```

기저 표현이 완전히 같은데도 캐스트를 요구하는 이유는 성능이 아니라 **의도 표명**이다. 열거형의 존재 이유가 "이 정수는 아무 정수가 아니라 테두리의 한 변"이라는 의미 부여인데, 암시적 변환을 허용하면 그 의미가 아무 데서나 새어 나간다. 컴파일러는 `SetBorder(3)` 같은 호출을 막아 준다 — 3이 무엇을 뜻하는지 코드가 말하지 않기 때문이다.

열거형끼리의 캐스트도 명시적으로 가능하며, **기저 정수 값을 통해** 변환된다.

```csharp
public enum HorizontalAlignment
{
    Left = BorderSide.Left,
    Right = BorderSide.Right,
    Center
}

HorizontalAlignment h = (HorizontalAlignment) BorderSide.Right;
// 위 줄은 다음과 정확히 같다
HorizontalAlignment h2 = (HorizontalAlignment) (int) BorderSide.Right;
```

이 캐스트는 이름을 맞춰 보지 않는다. **숫자만 옮긴다.** 두 열거형의 멤버 이름이 우연히 같아도 값이 다르면 엉뚱한 멤버가 된다.

### 0만 특별하다

숫자 리터럴 중 `0`만은 열거형 식에서 캐스트 없이 쓸 수 있다.

```csharp
BorderSide b = 0;        // 캐스트 불필요
if (b == 0) { ... }      // 캐스트 불필요
BorderSide c = 1;        // 컴파일 오류 CS0266
```

이유는 둘이다.

- 열거형의 **첫 멤버가 기본값 역할**을 하는 경우가 많다. 값 타입의 기본값은 모든 비트가 0이므로(16.4절), 초기화되지 않은 열거형 변수는 항상 0이다.
- 비트 플래그 열거형에서 **0은 "아무 플래그도 없음"** 을 뜻한다.

> **⚠️ 기본값이 유효한 멤버가 아니면 곤란해진다**
>
> `enum Priority { Low = 1, Normal = 2, High = 3 }` 같은 선언은 흔하지만 위험하다. `Priority`를 필드로 가진 클래스를 생성하면 그 필드는 `(Priority)0`이 되고, 이 값에 대응하는 이름이 없다. `ToString()`은 `"0"`을 돌려주고, `switch`는 어느 분기에도 걸리지 않는다.
>
> 16.4절에서 구조체를 두고 한 말이 열거형에도 그대로 적용된다. **0은 반드시 유효하고 안전한 상태여야 한다.** 실무 규칙은 하나다 — 값 0에 대응하는 멤버를 반드시 정의하고, 그것을 "지정되지 않음" 또는 가장 무해한 기본 동작에 대응시켜라.
>
> ```csharp
> enum Priority { Unspecified = 0, Low = 1, Normal = 2, High = 3 }
> ```

### `System.Enum` — 타입 통합과 유틸리티

`System.Enum` 타입은 두 가지 역할을 한다.

1. **모든 열거형 타입의 통합점(type unification)** — 어떤 열거형 멤버든 `System.Enum` 매개변수에 암시적으로 넘길 수 있다.
2. **정적 유틸리티 메서드의 집합** — 변환과 멤버 목록 조회.

```csharp
Display (Nut.Macadamia);   // Nut.Macadamia
Display (Size.Large);      // Size.Large

void Display (Enum value)
    => Console.WriteLine (value.GetType().Name + "." + value.ToString());

enum Nut  { Walnut, Hazelnut, Macadamia }
enum Size { Small, Medium, Large }
```

> **⚠️ `Enum` 매개변수는 박싱을 강제한다**
>
> `Display(Nut.Macadamia)` 호출은 `Enum`이 참조 타입이므로 **반드시 박싱**된다. 편의를 위한 통합점이지만 뜨거운 경로에서는 대가가 있다. 제네릭 제약 `where TEnum : struct, Enum`(※C# 7.3)을 쓰면 박싱 없이 같은 일을 할 수 있다.
>
> ```csharp
> static void Display<TEnum>(TEnum value) where TEnum : struct, Enum
>     => Console.WriteLine (typeof(TEnum).Name + "." + value);
> ```
>
> 다만 `value`를 문자열로 만드는 순간 결국 박싱이 일어난다는 점은 20.1절에서 본 그대로다. 제네릭 제약은 "인수 전달 시점의 박싱"을 없애 줄 뿐이다.

### 기저 타입을 모를 때 정수 값 꺼내기

컴파일 타임에 열거형 타입을 알면 캐스트가 정답이다. `System.Enum`으로만 받았다면 사정이 다르다. 박싱된 열거형은 **박싱된 정수와 같은 비트**를 담고 있으므로, `object`를 거쳐 언박싱하면 값을 꺼낼 수 있다.

```csharp
static int GetIntegralValue (Enum anyEnum)
    => (int) (object) anyEnum;    // 기저 타입이 int일 때만 동작한다
```

이 코드는 기저 타입이 `long`인 열거형을 받으면 언박싱에 실패한다. 언박싱은 정확한 타입 일치를 요구하기 때문이다(15.2절). 어떤 기저 타입이든 받으려면 세 가지 방법이 있다.

```csharp
// (1) decimal 경유 — 모든 정수 타입(ulong 포함)이 손실 없이 decimal로 간다
static decimal GetAnyIntegralValue (Enum anyEnum)
    => Convert.ToDecimal (anyEnum);

// (2) 기저 타입을 조회해 그 타입으로 변환 — 원래 타입이 보존된다
static object GetBoxedIntegralValue (Enum anyEnum)
{
    Type integralType = Enum.GetUnderlyingType (anyEnum.GetType());
    return Convert.ChangeType (anyEnum, integralType);
}

// (3) "D" 서식으로 문자열화 — 커스텀 직렬화 포매터를 쓸 때 편하다
static string GetIntegralValueAsString (Enum anyEnum)
    => anyEnum.ToString ("D");
```

```csharp
object result = GetBoxedIntegralValue (BorderSides.Top);
Console.WriteLine (result);              // 4
Console.WriteLine (result.GetType());    // System.Int32
```

> **📌 `GetBoxedIntegralValue`는 값을 변환하지 않는다**
>
> 이 메서드가 하는 일은 값 변환이 아니라 **재박싱(reboxing)** 이다. "열거형 옷을 입은 정수"를 "정수 옷을 입은 정수"로 갈아입힌다. 비트는 그대로다. 20.1절에서 본 "언박싱 상태에서는 구별할 수 없다"는 성질의 직접적 결과다.

반대 방향은 `Enum.ToObject`다.

```csharp
object bs = Enum.ToObject (typeof (BorderSides), 3);
Console.WriteLine (bs);        // Left, Right
```

이것은 `(BorderSides) 3`의 동적 등가물이다. `ToObject`는 모든 정수 타입과 `object`를 받는 오버로드를 갖는다.

### 문자열 변환 — 서식 문자열

`ToString()` 또는 정적 `Enum.Format`은 서식 문자열을 받는다.

| 서식 | 의미 | `ConsoleColor.Red`의 결과 | 비고 |
|---|---|---|---|
| `G` / `g` | 일반(General) | `Red` | 기본값 |
| `F` / `f` | `Flags`가 붙은 것처럼 취급 | `Red` | `[Flags]`가 없는 열거형의 조합 값도 이름으로 분해한다 |
| `D` / `d` | 10진 값 | `12` | 기저 정수 값을 문자열로 |
| `X` / `x` | 16진 값 | `0000000C` | 자릿수는 기저 타입 크기를 따른다 |

```csharp
Color c = Color.Blue;                   // Blue = 3, 기저 타입 byte
Console.WriteLine (c);                  // Blue
Console.WriteLine (c.ToString("G"));    // Blue
Console.WriteLine (c.ToString("D"));    // 3
Console.WriteLine (c.ToString("X"));    // 03
```

> **📌 16진 서식의 자릿수는 기저 타입이 정한다**
>
> `X` 서식은 항상 대문자를 쓰고, 자릿수는 기저 타입에 고정된다 — `byte`/`sbyte`는 2자리, `short`/`ushort`는 4자리, `int`/`uint`는 8자리, `long`/`ulong`는 16자리. 필요하면 앞을 0으로 채운다. 그래서 위 예제가 `3`이 아니라 `03`을 출력한다.

정적 `Enum.Format`은 인스턴스 대신 **정수 값을 직접** 넘길 수 있다는 점이 `ToString`과 다르다.

```csharp
public static string Format (Type enumType, object value, string format);

Console.WriteLine (Enum.Format (typeof(Color), (byte)3, "G"));   // Blue
```

> **⚠️ 같은 값을 가진 심볼이 여러 개면 어느 이름이 나올지 보장되지 않는다**
>
> 한 열거형에 값이 같은 심볼을 둘 이상 정의할 수 있다(`Loud = 3, Max = 3`). 이때 `ToString`이나 `GetName`이 어느 이름을 돌려줄지는 **정해져 있지 않다.** 로그나 직렬화가 이 이름에 의존하고 있다면, 런타임 버전이 바뀔 때 조용히 다른 문자열이 나올 수 있다. 값이 겹치는 별칭 심볼을 정의할 때는 출력 문자열에 의존하지 않는 것이 안전하다.
>
> 정의되지 않은 숫자를 넘기면 이름 대신 **숫자를 담은 문자열**이 돌아온다. 예외가 아니다. 이 조용한 동작이 20.4절 함정의 절반을 차지한다.

### 문자열 → 열거형: `Parse`와 `TryParse`

```csharp
// "orange"를 대소문자 무시로 찾는다 → Orange(4)
Color c = (Color) Enum.Parse (typeof(Color), "orange", true);

// Brown은 정의되지 않았다 → ArgumentException
c = (Color) Enum.Parse (typeof(Color), "Brown", false);

// 제네릭 버전 — 캐스트가 필요 없다
Enum.TryParse<Color> ("1", false, out c);    // 값 1인 Color
Enum.TryParse<Color> ("23", false, out c);   // 값 23인 Color — true를 돌려준다!
```

마지막 두 줄이 중요하다. `Parse`와 `TryParse`가 내부에서 하는 일은 다음 순서다.

1. 문자열 앞뒤 공백을 제거한다.
2. **첫 글자가 숫자·`+`·`-`이면 숫자 문자열로 간주**하고, 변환된 정수를 그대로 값으로 삼는다.
3. 아니면 쉼표로 토큰을 나누고 각 토큰의 공백을 제거한다.
4. 각 토큰을 열거형의 심볼 목록에서 찾는다. 없으면 `Parse`는 `ArgumentException`을 던지고 `TryParse`는 `false`를 돌려준다. 찾으면 그 값을 누적 결과에 **비트 OR**로 합친다.
5. 모든 토큰을 찾았으면 누적 결과를 돌려준다.

> **⚠️ `Enum.TryParse`는 "23"에도 `true`를 돌려준다**
>
> 2단계 때문이다. 숫자로 시작하는 문자열은 심볼 목록을 아예 조회하지 않고 통과한다. 사용자 입력이나 외부 JSON에서 온 문자열을 `TryParse`로만 검증하면 **정의되지 않은 값이 그대로 들어온다.**
>
> ```csharp
> if (Enum.TryParse<Color>(userInput, out var color))
>     Use(color);            // userInput이 "9999"면 여기까지 온다
> ```
>
> 방어는 `TryParse` 성공 후 `Enum.IsDefined`를 한 번 더 거는 것이다(단, 플래그 열거형에는 쓸 수 없다 — 20.4절).
>
> ```csharp
> if (Enum.TryParse<Color>(userInput, out var color) && Enum.IsDefined(color))   // 제네릭 IsDefined는 ※.NET 5
>     Use(color);
> ```

> **⚠️ `Parse`가 던지는 예외는 상황에 따라 다르다**
>
> 정의되지 않은 **이름**을 넘기면 `ArgumentException`이다. 첫 인수가 열거형이 아닌 `Type`이면 `ArgumentException`, `null`이면 `ArgumentNullException`이다. 숫자 문자열이 기저 타입의 범위를 넘으면 `OverflowException`이 나온다. 즉 "`Parse` 실패 = `ArgumentException`"이라고 단정하고 `catch (ArgumentException)`만 걸어 두면 새는 경로가 생긴다. **검증이 목적이라면 예외를 잡지 말고 `TryParse`를 써라.**

### 값 열거하기

`Enum.GetValues`는 열거형의 모든 멤버를 배열로 돌려준다.

```csharp
foreach (Enum value in Enum.GetValues (typeof (BorderSides)))
    Console.WriteLine (value);
```

`LeftRight = Left | Right` 같은 **조합 멤버도 포함**된다. 이름만 필요하면 `Enum.GetNames`가 `string[]`을 돌려준다.

.NET 5부터는 제네릭 버전이 생겨서 캐스트가 사라졌다.

```csharp
Color[] colors = Enum.GetValues<Color>();      // ※.NET 5
string[] names = Enum.GetNames<Color>();       // ※.NET 5
```

그 이전에는 `Enum.GetValues(Type)`이 `System.Array`를 돌려주므로 직접 캐스트해야 했다. 지금도 .NET Framework를 대상으로 한다면 이 형태를 쓴다.

```csharp
Color[] colors = (Color[]) Enum.GetValues (typeof (Color));

// 멀티 타깃이라면 이런 헬퍼를 하나 두는 편이 낫다
public static TEnum[] GetEnumValues<TEnum>() where TEnum : struct
    => (TEnum[]) Enum.GetValues (typeof (TEnum));
```

```csharp
Color[] colors = Enum.GetValues<Color>();
Console.WriteLine ("Number of symbols defined: " + colors.Length);
Console.WriteLine ("Value\tSymbol\n-----\t------");
foreach (Color c in colors)
    Console.WriteLine ("{0,5:D}\t{0:G}", c);
```

```text
Number of symbols defined: 5
Value   Symbol
-----   ------
    0   White
    1   Red
    2   Green
    3   Blue
    4   Orange
```

> **📌 `GetValues`/`GetNames`는 리플렉션이지만 결과가 캐시된다**
>
> CLR은 이 메서드들을 열거형 타입의 필드를 리플렉션으로 훑어서 구현한다. 다만 **결과를 캐시**하므로 같은 열거형에 대한 두 번째 호출부터는 훨씬 싸다. 그래도 공짜는 아니다 — `GetValues`는 호출할 때마다 **새 배열을 할당해서** 돌려준다(호출자가 배열을 수정할 수 있어야 하므로). 매 요청마다 `Enum.GetValues<T>()`를 부르는 코드는 조용히 쓰레기를 만든다. 정적 `readonly` 필드에 한 번 담아 두고 재사용하라.

### `System.Enum`의 주요 정적 메서드 정리

| 메서드 | 하는 일 | 주의점 |
|---|---|---|
| `GetUnderlyingType(Type)` | 기저 정수 타입을 돌려준다 | `Type.GetEnumUnderlyingType()` 인스턴스 버전도 있다 |
| `GetValues(Type)` / `GetValues<T>()` ※.NET 5 | 모든 멤버 값의 배열 | 호출마다 새 배열 할당. 조합 멤버 포함 |
| `GetNames(Type)` / `GetNames<T>()` ※.NET 5 | 모든 멤버 이름의 배열 | 위와 동일 |
| `GetName(Type, object)` | 값 하나에 대응하는 이름 | 같은 값의 심볼이 여럿이면 어느 것인지 미정 |
| `Parse` / `Parse<T>` | 문자열 → 열거형 | 실패 시 예외. 숫자 문자열은 검증 없이 통과 |
| `TryParse<T>` | 문자열 → 열거형 (실패 시 `false`) | 숫자 문자열은 검증 없이 `true` |
| `IsDefined(Type, object)` / `IsDefined<T>(T)` ※.NET 5 | 값이 정의된 멤버인지 | 대소문자 구분. 플래그 열거형에는 무의미(20.4절) |
| `ToObject(Type, ...)` | 정수 → 박싱된 열거형 | `(T)` 캐스트의 동적 버전 |
| `Format(Type, object, string)` | 서식 문자열로 변환 | 정수 값을 직접 받을 수 있다 |
| `HasFlag(Enum)` (인스턴스) | 플래그 포함 여부 | 20.3절 참조 |

## 20.3 `[Flags]` 비트 플래그 패턴과 열거형 연산자

### 열거형 연산자

열거형에 쓸 수 있는 연산자는 다음과 같다.

| 분류 | 연산자 | 결과 타입 |
|---|---|---|
| 대입 | `=`, `+=`, `-=` | 열거형 |
| 동등·비교 | `==`, `!=`, `<`, `>`, `<=`, `>=` | `bool` |
| 증감 | `++`, `--` | 열거형 |
| 산술 | `+`, `-` | 열거형(정수와의 연산) / 기저 타입(열거형끼리의 뺄셈) |
| 비트 | `&`, `\|`, `^`, `~` | 열거형 |
| 기타 | `sizeof` | `int` |

비트·산술·비교 연산자는 전부 **기저 정수 값에 대해** 동작한다. 덧셈은 열거형과 정수 사이에서만 허용되고, **열거형끼리의 덧셈은 허용되지 않는다.** 반면 열거형끼리의 뺄셈은 허용되며 결과는 기저 정수 타입이다.

```csharp
BorderSide s = BorderSide.Top;
s = s + 1;                    // OK — 열거형 + 정수 = 열거형
int distance = BorderSide.Bottom - BorderSide.Left;   // OK — 결과는 int
// var bad = BorderSide.Top + BorderSide.Left;        // 컴파일 오류
```

`~` 연산자의 결과는 열거형 타입이지만, 실제 비트는 기저 타입 전체를 뒤집은 값이다. `~BorderSides.Left`는 `int` 기준으로 `0xFFFFFFFE`가 되고, 이 값에 대응하는 심볼은 당연히 없다.

### 문법 — 2의 거듭제곱으로 값을 배정한다

여러 값을 동시에 담아야 하는 열거형은 각 멤버가 **서로 다른 비트 하나씩**을 차지하도록 값을 명시한다.

```csharp
[Flags]
enum BorderSides { None = 0, Left = 1, Right = 2, Top = 4, Bottom = 8 }
```

시프트로 쓰면 의도가 눈에 더 잘 들어온다.

```csharp
[Flags]
enum BorderSides { None = 0, Left = 1, Right = 1 << 1, Top = 1 << 2, Bottom = 1 << 3 }
```

```text
 비트 위치   ...  3     2     1     0
            ┌─────┬─────┬─────┬─────┐
 Left  = 1  │  0  │  0  │  0  │  1  │
 Right = 2  │  0  │  0  │  1  │  0  │
 Top   = 4  │  0  │  1  │  0  │  0  │
 Bottom= 8  │  1  │  0  │  0  │  0  │
            └─────┴─────┴─────┴─────┘
 Left|Right │  0  │  0  │  1  │  1  │  = 3
```

조합 멤버를 선언에 미리 넣어 둘 수도 있다.

```csharp
[Flags]
enum BorderSides
{
    None = 0,
    Left = 1, Right = 1 << 1, Top = 1 << 2, Bottom = 1 << 3,
    LeftRight = Left | Right,
    TopBottom = Top | Bottom,
    All       = LeftRight | TopBottom
}
```

BCL의 대표 사례가 `System.IO.FileAttributes`다.

```csharp
[Flags]
public enum FileAttributes
{
    ReadOnly          = 0x00001,
    Hidden            = 0x00002,
    System            = 0x00004,
    Directory         = 0x00010,
    Archive           = 0x00020,
    // ...
}
```

### 값 설계 규칙

| 규칙 | 이유 |
|---|---|
| 각 원자 플래그는 **2의 거듭제곱** | 비트가 겹치면 `&` 검사가 오작동한다 |
| **`None = 0`** 을 정의한다 | 기본값(모든 비트 0)에 이름을 준다. 단, `None`을 `&`로 검사하면 항상 `false`다 |
| 조합 멤버는 **원자 플래그의 OR로 정의** | 숫자를 직접 쓰면 원자 값이 바뀔 때 조용히 어긋난다 |
| 이름은 **복수형**(`BorderSides`) | 단일 값 열거형(`BorderSide`)과 구분된다 |
| **`[Flags]`를 반드시 붙인다** | 없어도 비트 연산은 되지만 `ToString`이 숫자를 뱉는다 |
| 기저 타입은 필요한 비트 수에 맞춘다 | 33개 이상이면 `long`, 최상위 비트까지 쓰면 부호 없는 타입 |

### 비트 연산 관용구

```csharp
BorderSides leftRight = BorderSides.Left | BorderSides.Right;

// 포함 검사
if ((leftRight & BorderSides.Left) != 0)
    Console.WriteLine ("Includes Left");        // Includes Left

// 문자열화
string formatted = leftRight.ToString();        // "Left, Right"

// 플래그 켜기
BorderSides s = BorderSides.Left;
s |= BorderSides.Right;
Console.WriteLine (s == leftRight);             // True

// 플래그 토글
s ^= BorderSides.Right;
Console.WriteLine (s);                          // Left

// 플래그 끄기
s = leftRight & ~BorderSides.Right;             // Left
```

관용구를 한 표로 정리한다.

| 하려는 일 | 관용구 | 주의 |
|---|---|---|
| 플래그 하나 켜기 | `v \|= F` | — |
| 플래그 하나 끄기 | `v &= ~F` | `~`를 빠뜨리면 정반대가 된다 |
| 토글 | `v ^= F` | — |
| **정확히 포함**하는지 | `(v & F) == F` | 조합 플래그 `F`에도 올바르게 동작 |
| **하나라도** 포함하는지 | `(v & F) != 0` | 원자 플래그 검사에는 이게 충분하다 |
| 비어 있는지 | `v == 0` | `(v & None) != 0`은 항상 `false` |

> **⚠️ 조합 플래그를 `!= 0`으로 검사하면 틀린다**
>
> `F`가 조합 플래그(`LeftRight = Left | Right`)일 때 `(v & F) != 0`은 **둘 중 하나만 있어도 참**이다. "둘 다 있는가"를 물으려면 `(v & F) == F`를 써야 한다. 원자 플래그만 다룰 때는 두 형태가 같은 결과를 내기 때문에, 조합 플래그를 나중에 추가하는 순간 조용히 깨진다.

### `HasFlag`의 비용

`System.Enum`에는 편의 메서드가 있다.

```csharp
public bool HasFlag (Enum flag);
```

```csharp
Console.WriteLine (attributes.HasFlag (FileAttributes.Hidden));
// 비트 연산 버전
Console.WriteLine ((attributes & FileAttributes.Hidden) != 0);
```

`HasFlag`는 `(v & F) == F` 의미론을 따르므로 조합 플래그에도 올바르게 동작한다. 문제는 **시그니처가 `Enum` 매개변수**라는 점이다. 20.2절에서 본 대로 `Enum`은 참조 타입이므로, 호출할 때마다 **인수와 수신자 양쪽이 박싱**되어 힙 할당 두 번이 발생한다. `CLR via C#`이 "`HasFlag`를 피하라"고 못 박은 것이 이 때문이다.

> **📌 최신 런타임은 `HasFlag` 박싱을 지워 준다 ※.NET Core 2.1**
>
> .NET Core 2.1부터 JIT은 `HasFlag` 호출 패턴을 인식해 **박싱 없는 비트 검사로 치환**한다. 다만 조건이 있다. **두 피연산자의 정적 타입이 같은 열거형으로 컴파일 타임에 확정**되어야 한다. 아래 두 번째 호출처럼 `Enum`으로 받아 넘기면 최적화가 걸리지 않고 원래대로 박싱된다.
>
> ```csharp
> attributes.HasFlag (FileAttributes.Hidden);   // 최적화 대상
> Enum e = attributes;
> e.HasFlag (FileAttributes.Hidden);            // 박싱 그대로
> ```
>
> .NET Framework를 대상으로 하는 코드에서는 **어떤 경우에도 최적화가 없다.** 멀티 타깃 라이브러리라면 비트 연산으로 쓰거나, 20.5절처럼 확장 메서드로 감싸는 편이 안전하다.

| 방식 | 조합 플래그 정확성 | 박싱 | 읽기 쉬움 |
|---|---|---|---|
| `(v & F) != 0` | **틀릴 수 있다** | 없음 | 보통 |
| `(v & F) == F` | 정확 | 없음 | 낮음(괄호가 많다) |
| `v.HasFlag(F)` | 정확 | .NET Core 2.1+ 최적화 시 없음 / 그 외 2회 | 높음 |
| 확장 메서드 `v.IsSet(F)` | 정확(직접 구현) | 없음 | 높음 |

### `[Flags]`가 실제로 바꾸는 것 — `ToString`

`[Flags]`는 컴파일러에게 아무 지시도 하지 않는다. 비트 연산은 특성이 없어도 그대로 동작한다. 이 특성이 바꾸는 것은 **런타임에 `Enum.ToString`과 `Enum.Format`이 취하는 경로**뿐이다.

```csharp
Actions actions = Actions.Read | Actions.Delete;   // 0x0005
Console.WriteLine (actions.ToString());
// [Flags]가 있으면  → "Read, Delete"
// [Flags]가 없으면  → "5"
```

`ToString`이 `G` 서식으로 값을 문자열화할 때 하는 일은 다음과 같다. 먼저 해당 열거형 타입에 `[Flags]`가 붙어 있는지 리플렉션으로 확인한다(`Type.IsDefined`). 붙어 있지 않으면 값과 일치하는 심볼 하나를 찾아 돌려주고 끝이다. 붙어 있으면 다음 절차를 밟는다.

1. 열거형이 정의한 값의 집합을 얻고 **내림차순으로 정렬**한다.
2. 각 값을 인스턴스 값과 비트 AND 하고, 결과가 그 값과 같으면 대응 문자열을 출력에 덧붙이고 **해당 비트를 꺼서 처리 완료로 표시**한다. 모든 값을 검사하거나 인스턴스의 비트가 전부 꺼질 때까지 반복한다.
3. 모든 값을 검사한 뒤에도 인스턴스가 0이 아니면, 대응 심볼이 없는 비트가 남아 있다는 뜻이다. 이 경우 **원래 숫자를 문자열로** 돌려준다.
4. 원래 값이 0이 아니었다면 쉼표로 이어 붙인 심볼 문자열을 돌려준다.
5. 원래 값이 0이고 값 0인 심볼이 정의되어 있으면 그 심볼을 돌려준다.
6. 여기까지 오면 `"0"`을 돌려준다.

> **⚠️ 대응하지 않는 비트가 하나라도 있으면 심볼이 전부 사라진다**
>
> 3단계가 핵심이다. `Read | Delete | (Actions)0x8000`처럼 정의되지 않은 비트가 섞이면, 이미 찾아낸 `"Read, Delete"`를 **버리고** `"32773"` 같은 숫자만 돌려준다. 부분적으로 해석된 결과를 주지 않는다. 로그에서 열거형이 갑자기 숫자로 찍히기 시작했다면 값이 오염됐다는 신호다.

1단계의 내림차순 정렬에는 실용적 결과가 있다. 심볼이 2의 거듭제곱일 필요는 없으므로, `All = 0x001F` 같은 심볼을 정의해 두면 값이 정확히 `0x001F`일 때 `"All"` 하나만 출력된다 — 더 큰 값이 먼저 검사되어 모든 비트를 가져가기 때문이다.

`[Flags]` 없이도 조합 분해 출력을 얻는 방법이 있다. `F` 서식이다.

```csharp
// [Flags]가 없는 Actions
Actions actions = Actions.Read | Actions.Delete;
Console.WriteLine (actions.ToString("F"));    // "Read, Delete"
```

> **💡 `[Flags]`는 문서이기도 하다**
>
> `F` 서식으로 우회할 수 있다는 사실이 `[Flags]`를 생략할 이유가 되지는 않는다. 이 특성은 런타임뿐 아니라 **사람과 도구에게 보내는 신호**다. 디버거는 `[Flags]` 열거형을 조합으로 표시하고, JSON 직렬화기(`JsonStringEnumConverter`)와 코드 분석기도 이 특성을 본다. 조합 가능한 열거형에는 예외 없이 붙여라.

### 플래그 문자열 파싱

`Parse`/`TryParse`는 쉼표로 구분된 여러 심볼을 받아 OR로 합친다(20.2절의 4단계).

```csharp
Actions a = (Actions) Enum.Parse (typeof(Actions), "Query", true);
Console.WriteLine (a.ToString());                 // "Query"

Enum.TryParse<Actions> ("Query, Read", false, out a);
Console.WriteLine (a.ToString());                 // "Read, Query"

a = (Actions) Enum.Parse (typeof(Actions), "28", false);
Console.WriteLine (a.ToString());                 // "Delete, Query, Sync"
```

마지막 줄이 다시 보여주는 것 — 숫자 문자열은 심볼 검증을 거치지 않고 그대로 값이 된다.

## 20.4 열거형의 타입 안전성 문제

### 구멍의 정체

`CLR via C#`은 열거형의 장점으로 "강타입"을 든다. `Color.Orange`를 `Fruit` 매개변수에 넘기면 컴파일 오류가 난다는 의미에서는 맞다. 하지만 그 타입 안전성은 **정적(static)이지 강한(strong) 것이 아니다.**

```csharp
public enum BorderSide { Left, Right, Top, Bottom }   // 0, 1, 2, 3
...
BorderSide b = (BorderSide) 12345;
Console.WriteLine (b);        // 12345
```

컴파일도, 실행도 아무 문제 없이 통과한다. 예외도, 경고도 없다. 20.1절에서 본 이유 그대로다 — **런타임에는 열거형과 정수가 같은 것**이므로, 검사할 주체가 아무도 없다.

산술·비트 연산으로도 같은 상태를 만들 수 있다.

```csharp
BorderSide b = BorderSide.Bottom;   // 3
b++;                                // 4 — 오류 없음

BorderSides s = BorderSides.Left;
s += 1234;                          // 오류 없음
```

C# 컴파일러가 검증할 수 있는 자리(`BorderSide b = 5;` 같은 직접 대입)에서는 막아 준다. 그러나 **컴파일러가 검증할 수 없는 자리에서는 런타임이 대신 예외를 던져 주지 않는다.** 이것이 "정적 타입 안전성은 있지만 강한 타입 안전성은 없다"는 말의 정확한 뜻이다.

정의되지 않은 값이 들어오는 현실적 경로를 정리하면 이렇다.

| 경로 | 예 |
|---|---|
| 명시적 캐스트 | `(BorderSide) userInputInt` |
| 산술·증감 연산 | `b++`, `b += n` |
| `Enum.Parse` / `TryParse`의 숫자 문자열 | `Enum.TryParse<Color>("9999", out c)` → `true` |
| `Enum.ToObject` | `Enum.ToObject(typeof(Color), 42)` |
| 역직렬화 | JSON/DB/바이너리에서 정수 그대로 매핑 |
| 상호운용 | P/Invoke·COM이 돌려준 원시 정수 |
| **버전 불일치** | 새 버전 라이브러리가 추가한 멤버를 구버전 코드가 받는 경우 |

마지막 항목이 특히 위험하다. 열거형은 시간이 지나며 멤버가 늘어나는 것이 정상이고, **오늘 정의되지 않은 값이 내일은 정상 값**이다.

### 무엇이 깨지는가

```csharp
void Draw (BorderSide side)
{
    if      (side == BorderSide.Left)  { ... }
    else if (side == BorderSide.Right) { ... }
    else if (side == BorderSide.Top)   { ... }
    else                               { ... }   // Bottom이라고 가정
}
```

이 코드는 `(BorderSide)12345`를 받으면 **조용히 `Bottom`으로 처리**한다. 아무도 모른다. `switch` 문으로 써도 `default` 절이 같은 역할을 한다.

### 방어 1 — 마지막 분기를 열어 두지 마라

가장 값싼 방어는 마지막 `else`를 "나머지 전부"가 아니라 명시적 비교로 바꾸고, 진짜 나머지에서는 예외를 던지는 것이다.

```csharp
void Draw (BorderSide side)
{
    if      (side == BorderSide.Left)   { ... }
    else if (side == BorderSide.Right)  { ... }
    else if (side == BorderSide.Top)    { ... }
    else if (side == BorderSide.Bottom) { ... }
    else throw new ArgumentException ("Invalid BorderSide: " + side, nameof (side));
}
```

`switch` 식으로 쓰면 더 짧다. C# 컴파일러는 열거형에 대한 `switch` 식의 완전성 검사에서, **선언된 멤버를 전부 처리해도** "정의되지 않은 값이 올 수 있다"는 이유로 경고(CS8509)를 낸다. 이 경고는 잔소리가 아니라 정확한 지적이다.

```csharp
string Describe (BorderSide side) => side switch
{
    BorderSide.Left   => "왼쪽",
    BorderSide.Right  => "오른쪽",
    BorderSide.Top    => "위",
    BorderSide.Bottom => "아래",
    _ => throw new ArgumentOutOfRangeException (nameof (side), side, "Invalid BorderSide")
};
```

`switch` 식의 완전성 검사 규칙 전체는 77.14절에서 다룬다.

### 방어 2 — `Enum.IsDefined`

경계에서 값을 한 번 검증하는 방법이다.

```csharp
BorderSide side = (BorderSide) 12345;
Console.WriteLine (Enum.IsDefined (typeof (BorderSide), side));   // False
```

```csharp
public void SetColor (Color c)
{
    if (!Enum.IsDefined (typeof (Color), c))
        throw new ArgumentOutOfRangeException (nameof (c), c, "Invalid Color value.");
    // ...
}
```

.NET 5부터는 박싱 없는 제네릭 오버로드가 있다.

```csharp
if (!Enum.IsDefined (c))      // ※.NET 5, 인수 박싱 없음
    throw new ArgumentOutOfRangeException (nameof (c), c, "Invalid Color value.");
```

> **⚠️ `IsDefined`에는 함정이 세 개 있다**
>
> **(1) 느리다.** 내부적으로 리플렉션으로 심볼 목록을 얻어 선형 검색한다. 목록 자체는 캐시되지만 검색과 (비제네릭 오버로드의 경우) 박싱은 매번 일어난다. 손으로 범위를 검사하는 코드보다 확실히 느리다. 초당 수만 번 호출되는 경로에는 넣지 마라.
>
> **(2) 대소문자를 구분한다.** 문자열을 넘기는 오버로드는 **항상 대소문자 구분 검색**을 하며, 이를 끄는 방법이 없다. `Enum.IsDefined(typeof(Color), "white")`는 `White`가 정의되어 있어도 `False`다.
>
> **(3) 버전 경계를 넘으면 의미가 달라진다.** `Color`가 어셈블리 A에, `SetColor`가 어셈블리 B에 있다고 하자. B는 White/Red/Green/Blue/Orange만 처리하도록 작성됐는데, 나중에 A가 `Purple`을 추가하면 `IsDefined`는 `Purple`에 대해 `true`를 돌려준다. B는 처리할 줄 모르는 값을 통과시키게 된다. **`IsDefined`는 열거형을 정의한 어셈블리와 호출하는 코드가 같은 어셈블리에 있을 때만 의도대로 동작한다.**

> **⚠️ `IsDefined`는 `[Flags]` 열거형에 쓸 수 없다**
>
> 두 가지 이유로 무의미하다.
>
> - **문자열을 넘기면** 쉼표로 토큰을 나누지 않는다. `"Read, Delete"`를 쉼표가 포함된 하나의 심볼 이름으로 찾으려 하는데, 그런 심볼은 정의할 수 없으므로 영원히 찾지 못한다.
> - **숫자를 넘기면** 그 값과 **정확히 일치하는 단일 심볼**이 있는지만 본다. `Read | Delete`(5)에 대응하는 심볼이 따로 정의되어 있지 않으면 `false`다. 비트 플래그의 정상 조합은 대부분 여기에 걸린다.

### 방어 3 — 플래그 열거형 검증

플래그 열거형의 유효성은 다르게 판정해야 한다. `Enum.ToString()`이 정의되지 않은 비트를 만나면 심볼 대신 숫자를 돌려준다는 성질을 이용하는 방법이 있다.

```csharp
for (int i = 0; i <= 16; i++)
{
    BorderSides side = (BorderSides) i;
    Console.WriteLine (IsFlagDefined (side) + " " + side);
}

bool IsFlagDefined (Enum e)
{
    decimal d;
    return !decimal.TryParse (e.ToString(), out d);
}

[Flags] public enum BorderSides { Left = 1, Right = 2, Top = 4, Bottom = 8 }
```

`ToString()` 결과가 숫자로 파싱되면 정의되지 않은 비트가 있다는 뜻이다.

> **💡 문자열 왕복은 검증 도구로는 비싸다**
>
> 위 트릭은 동작하지만 호출마다 문자열을 만들고 파싱한다. 뜨거운 경로에는 적합하지 않다. 실무에서는 **유효한 비트의 마스크를 상수로 두고 비트 검사 한 번**으로 끝내는 편이 훨씬 낫다.
>
> ```csharp
> [Flags]
> public enum BorderSides
> {
>     None = 0, Left = 1, Right = 2, Top = 4, Bottom = 8,
>     All = Left | Right | Top | Bottom          // 유효 마스크
> }
>
> static bool IsValid (BorderSides v) => (v & ~BorderSides.All) == 0;
> ```
>
> 이 방식은 리플렉션도 문자열 할당도 쓰지 않으며, `All` 멤버를 조합으로 정의해 두었으므로 플래그를 추가해도 자동으로 따라온다.

### 검증을 어디에 둘 것인가

- **신뢰 경계**(사용자 입력·역직렬화·상호운용) — `IsDefined` 또는 마스크 검사. 비용을 한 번만 내면 된다.
- **공개 API 진입점** — `switch` + `default: throw`. 비용이 사실상 0이다.
- **내부 호출 경로** — 검증하지 않는다.

> **💡 열거형 검증은 경계에서 한 번만**
>
> 정수를 열거형으로 캐스트하는 지점은 대개 시스템의 **가장자리**다 — HTTP 요청 파싱, DB 열 읽기, P/Invoke 반환값. 그 자리에서 한 번 검증하고 내부로는 검증된 값만 흘려보내는 것이 원칙이다. 내부 메서드마다 `IsDefined`를 뿌리면 비용은 곱해지고 안전성은 그대로다.
>
> 이 원칙은 널 검사와 정확히 같은 구조다(21.10절).

## 20.5 `enum`에 동작 붙이기 — 확장 메서드

### 왜 필요한가

20.1절에서 본 제약이 여기서 문제가 된다. 열거형은 메서드를 정의할 수 없다. 그런데 열거형을 다루는 코드에는 늘 같은 조각이 반복된다 — 플래그 설정, 해제, 검사, 유효성 확인, 표시 이름 얻기. 이 조각들이 호출부에 흩어지면 20.3절의 `(v & F) == F` 같은 미묘한 관용구를 매번 정확히 써야 한다.

C#의 확장 메서드가 이 구멍을 메운다. 정적 클래스의 정적 메서드 첫 매개변수에 `this`를 붙이면, 호출부에서는 그 타입의 인스턴스 메서드처럼 보인다.

```csharp
internal static class FileAttributesExtensionMethods
{
    public static bool IsSet (this FileAttributes flags, FileAttributes flagToTest)
    {
        if (flagToTest == 0)
            throw new ArgumentOutOfRangeException (nameof (flagToTest), "Value must not be 0");
        return (flags & flagToTest) == flagToTest;
    }

    public static bool IsClear (this FileAttributes flags, FileAttributes flagToTest)
    {
        if (flagToTest == 0)
            throw new ArgumentOutOfRangeException (nameof (flagToTest), "Value must not be 0");
        return !IsSet (flags, flagToTest);
    }

    public static bool AnyFlagsSet (this FileAttributes flags, FileAttributes testFlags)
        => (flags & testFlags) != 0;

    public static FileAttributes Set (this FileAttributes flags, FileAttributes setFlags)
        => flags | setFlags;

    public static FileAttributes Clear (this FileAttributes flags, FileAttributes clearFlags)
        => flags & ~clearFlags;

    public static void ForEach (this FileAttributes flags, Action<FileAttributes> processFlag)
    {
        if (processFlag == null) throw new ArgumentNullException (nameof (processFlag));
        for (uint bit = 1; bit != 0; bit <<= 1)
        {
            uint temp = ((uint) flags) & bit;
            if (temp != 0) processFlag ((FileAttributes) temp);
        }
    }
}
```

호출부에서는 열거형에 메서드가 달린 것처럼 보인다.

```csharp
FileAttributes fa = FileAttributes.System;
fa = fa.Set   (FileAttributes.ReadOnly);
fa = fa.Clear (FileAttributes.System);
fa.ForEach (f => Console.WriteLine (f));
```

`ForEach`의 루프 조건을 눈여겨보라. `bit`가 `1`에서 시작해 왼쪽으로 밀리다가 최상위 비트를 넘어가면 `0`이 되어 루프가 끝난다. 부호 있는 타입으로 썼다면 최상위 비트에서 음수가 되어 조건이 꼬인다. **비트를 훑을 때는 부호 없는 타입을 쓴다.**

### 컴파일 결과와 성능

확장 메서드는 **문법적 재배치일 뿐**이다. `fa.Set(x)`는 `FileAttributesExtensionMethods.Set(fa, x)`로 컴파일되고, IL에는 평범한 정적 메서드 호출(`call`)만 남는다. 가상 디스패치도, 박싱도, 할당도 없다.

```il
  ldloc.0
  ldc.i4.1
  call  valuetype FileAttributes FileAttributesExtensionMethods::Set(
            valuetype FileAttributes, valuetype FileAttributes)
```

게다가 `Set`/`Clear`/`IsSet` 같은 한 줄짜리 메서드는 JIT이 거의 확실히 인라인한다. 결과적으로 **`HasFlag`보다 읽기 쉬우면서 비트 연산과 같은 비용**을 갖는다. 20.3절의 표에서 확장 메서드가 유일하게 세 열 모두에서 좋았던 이유다.

> **📌 확장 메서드는 `null`에서도 폭발하지 않는다**
>
> 확장 메서드는 정적 호출이므로 수신자가 `null`이어도 `NullReferenceException`이 나지 않는다. 열거형은 값 타입이라 이 논점이 직접 걸리지는 않지만, `MyEnum?`(널 가능 값 타입)에 대한 확장 메서드를 정의하면 `null` 수신자를 메서드 안에서 처리할 수 있다.
>
> ```csharp
> public static bool IsSetOrDefault (this BorderSides? v, BorderSides f)
>     => v.HasValue && (v.Value & f) == f;
> ```

### 표시 이름 붙이기 — 특성과 확장 메서드의 결합

열거형에 사람이 읽을 이름을 붙이는 문제는 이 장의 두 주제를 잇는 다리다. 심볼 이름은 식별자 규칙을 따라야 하므로 공백도, 한글도, 문장 부호도 넣기 어렵다. 해법은 **각 멤버에 특성을 붙이고, 확장 메서드가 그것을 읽는 것**이다.

```csharp
using System.ComponentModel;

public enum OrderState
{
    [Description("주문 접수")]     Received,
    [Description("결제 대기")]     AwaitingPayment,
    [Description("배송 준비 중")]  Preparing,
    [Description("배송 완료")]     Delivered
}
```

읽는 쪽은 리플렉션을 쓴다.

```csharp
public static string ToDisplayName (this OrderState state)
{
    var field = typeof(OrderState).GetField (state.ToString());
    var attr = (DescriptionAttribute?) Attribute.GetCustomAttribute (
                   field!, typeof (DescriptionAttribute));
    return attr?.Description ?? state.ToString();
}
```

> **⚠️ 이 패턴은 편하지만 호출마다 리플렉션을 돈다**
>
> 위 코드는 호출할 때마다 `state.ToString()`으로 문자열을 할당하고, `GetField`로 메타데이터를 문자열 비교하며 검색하고, 특성 인스턴스를 새로 만든다(20.9절). 화면 렌더링처럼 드문 호출이라면 문제없지만, 루프 안에서 부르면 대가가 크다.
>
> 실무 해법은 **정적 딕셔너리에 한 번 채워 두는 것**이다.
>
> ```csharp
> static readonly Dictionary<OrderState, string> Names =
>     Enum.GetValues<OrderState>().ToDictionary (s => s, s => LookupSlow (s));
>
> public static string ToDisplayName (this OrderState s) => Names[s];
> ```
>
> 더 근본적인 대안은 컴파일 타임에 매핑 코드를 생성하는 소스 생성기다(57.15절). 리플렉션 자체를 없애므로 트리밍·AOT 환경에서도 안전하다(57.14절).

> **💡 지역화가 필요하면 열거형 이름에 의존하지 마라**
>
> `[Description]`에 박은 문자열은 어셈블리에 하드코딩된다. 다국어가 필요하면 리소스 키만 특성에 담고 실제 문자열은 `ResourceManager`로 조회하는 형태가 되어야 한다(53장). 열거형 자체는 지역화를 전혀 지원하지 않는다는 점을 기억하라 — `ToString()`이 돌려주는 것은 언제나 소스 코드의 식별자다.

### 확장 메서드를 어디에 둘 것인가

열거형과 **같은 네임스페이스**에 두면 `using` 하나로 따라오지만, 원치 않는 곳에서도 IntelliSense 목록에 뜬다. **전용 네임스페이스**(`MyApp.Extensions`)로 분리하면 명시적으로 가져와야 하는 대신, `using`을 빠뜨렸을 때 "메서드가 없다"는 엉뚱한 오류를 만난다. **같은 파일**에 두면 함께 관리되지만 파일이 커진다.

> **💡 열거형 확장 메서드는 열거형 옆에 두고 같은 네임스페이스에 넣어라**
>
> 열거형과 그 동작은 개념적으로 한 덩어리다. 파일을 나누면 열거형에 멤버를 추가할 때 확장 메서드의 `switch`를 갱신하는 것을 잊기 쉽다. 같은 파일에 두고 `switch` 식으로 매핑하면 CS8509 경고가 누락을 잡아 준다(20.4절).

## 20.6 특성 클래스 정의와 `AttributeUsage`

### 특성이란 무엇인가

`virtual`, `ref`, `static` 같은 수정자로 코드 요소를 한정하는 것에는 이미 익숙하다. 이 수정자들은 언어에 **박혀 있다.** 새로 만들 수 없고, 컴파일러가 아는 것만 존재한다.

특성(attribute)은 그 자리를 **확장 가능하게** 만드는 장치다. 어셈블리·타입·멤버·반환값·매개변수·제네릭 타입 매개변수에 임의의 정보를 붙일 수 있고, 그 정보는 어셈블리 메타데이터에 기록된다. 덕분에 타입 시스템과 깊이 통합되는 서비스를 **C# 문법을 늘리지 않고** 만들 수 있다.

적용은 대괄호로 한다.

```csharp
[ObsoleteAttribute]
public class Foo { }
```

`ObsoleteAttribute`는 컴파일러가 아는 특성이라, 이 타입을 참조하는 코드에 경고를 낸다. 선언은 이렇게 생겼다(간략화).

```csharp
public sealed class ObsoleteAttribute : Attribute { ... }
```

관례상 모든 특성 타입의 이름은 `Attribute`로 끝난다. C#은 이 관례를 알고 있어서 **적용할 때 접미사를 생략**할 수 있게 해 준다.

```csharp
[Obsolete]              // ObsoleteAttribute와 동일
public class Foo { }
```

> **📌 접미사 생략은 컴파일러의 이름 조회 규칙이다**
>
> `[Foo]`를 만나면 컴파일러는 `Foo`와 `FooAttribute` **둘 다** 찾는다. 둘 다 존재하고 둘 다 특성 클래스이면 모호성 오류(CS1614)가 난다. 실무에서 마주칠 일은 거의 없지만, `Attribute` 접미사를 쓰지 않은 특성 클래스를 정의하면 이런 충돌을 만들 수 있다. 관례를 지키는 편이 낫다.

### 특성 클래스 정의

특성은 **클래스**다. `System.Attribute`를 직접 또는 간접으로 상속하면 된다. 그 이상 특별한 것이 없다.

`[Flags]`를 직접 만든다면 이렇게 된다.

```csharp
namespace System
{
    public class FlagsAttribute : System.Attribute
    {
        public FlagsAttribute() { }
    }
}
```

여기서 만족해야 할 조건은 셋이다.

- `System.Attribute`에서 파생한다. 이것이 CLS 규격 준수 특성의 조건이며, **C#은 CLS 규격 특성만 허용**한다.
- 클래스 이름이 `Attribute`로 끝난다(관례. 강제는 아니다).
- 추상이 아니라면 **public 생성자가 최소 하나** 있어야 한다.

> **💡 특성은 논리적 상태 컨테이너로 생각하라**
>
> 특성 타입은 클래스지만, 클래스답게 설계하면 안 된다. 다음 형태를 지켜라.
>
> - **public 생성자 하나**가 필수 상태(위치 인수)를 받는다.
> - **public 프로퍼티**가 선택 상태(명명 인수)를 받는다.
> - **public 메서드·이벤트·그 밖의 멤버는 두지 않는다.**
>
> 필드 대신 프로퍼티를 쓰는 이유는 일반 클래스와 같다 — 나중에 구현을 바꿀 여지를 남긴다. BCL의 오래된 특성들이 public 필드를 쓰는 것은 시대적 유물이지 본받을 것이 아니다.

> **💡 특성 클래스는 `sealed`로 만들어라**
>
> 특성 조회 API(`IsDefined`, `GetCustomAttribute`)는 **지정한 클래스뿐 아니라 그 파생 클래스도** 찾는다. 특성 계층을 만들면 "정확히 이 특성인가"를 판정하기 위해 조회 결과에 추가 검사를 붙여야 한다. `sealed`로 막아 두면 그 혼란과 추가 검사가 통째로 사라진다.

### `AttributeUsage` — 특성에 붙이는 특성

위 상태의 `FlagsAttribute`는 아무 데나 붙을 수 있다. 프로퍼티나 메서드에 `[Flags]`를 다는 것은 무의미한데도 컴파일러가 막지 않는다.

어디에 붙을 수 있는지 컴파일러에게 알려 주는 것이 `System.AttributeUsageAttribute`다. 특성 클래스도 클래스이므로, 여기에 특성을 붙일 수 있다.

```csharp
namespace System
{
    [AttributeUsage (AttributeTargets.Enum, Inherited = false)]
    public class FlagsAttribute : System.Attribute
    {
        public FlagsAttribute() { }
    }
}
```

이제 `[Flags]`를 열거형이 아닌 곳에 붙이면 컴파일 오류다. **모든 C# 컴파일러가 이 특성을 내장 지원**하며, 위반을 오류로 보고한다.

`AttributeUsageAttribute`의 실제 정의는 다음과 같다.

```csharp
[AttributeUsage (AttributeTargets.Class, Inherited = true)]
public sealed class AttributeUsageAttribute : Attribute
{
    // 유일한 public 생성자 — 위치 인수
    public AttributeUsageAttribute (AttributeTargets validOn) { ... }

    public bool AllowMultiple { get; set; }        // 기본 false
    public bool Inherited     { get; set; }        // 기본 true
    public AttributeTargets ValidOn { get; }       // 읽기 전용
}
```

`ValidOn`에 세터가 없다는 점을 보라. 생성자로만 지정할 수 있는 **필수 상태**이고, 나머지 둘은 **선택 상태**다. 20.7절에서 이 구분을 정식으로 다룬다.

### `AttributeTargets`

```csharp
[Flags, Serializable]
public enum AttributeTargets
{
    Assembly         = 0x0001,
    Module           = 0x0002,
    Class            = 0x0004,
    Struct           = 0x0008,
    Enum             = 0x0010,
    Constructor      = 0x0020,
    Method           = 0x0040,
    Property         = 0x0080,
    Field            = 0x0100,
    Event            = 0x0200,
    Interface        = 0x0400,
    Parameter        = 0x0800,
    Delegate         = 0x1000,
    ReturnValue      = 0x2000,
    GenericParameter = 0x4000,
    All              = Assembly | Module | Class | Struct | Enum |
                       Constructor | Method | Property | Field | Event |
                       Interface | Parameter | Delegate | ReturnValue |
                       GenericParameter
}
```

`AttributeTargets` 자신이 `[Flags]` 열거형이므로 `|`로 조합한다. 이 장의 두 주제가 여기서 만난다.

```csharp
[AttributeUsage (AttributeTargets.Class | AttributeTargets.Struct)]
public sealed class EntityAttribute : Attribute { }
```

### 세 프로퍼티가 실제로 하는 일

| 프로퍼티 | 기본값 | 의미 | 위반 시 |
|---|---|---|---|
| `ValidOn`(생성자 인수) | `AttributeTargets.All` | 붙일 수 있는 대상 집합 | 컴파일 오류 CS0592 |
| `AllowMultiple` | `false` | 같은 대상에 두 번 이상 붙일 수 있는가 | 컴파일 오류 CS0579 |
| `Inherited` | `true` | 기반 클래스·가상 메서드에 붙은 특성이 파생 쪽에도 적용되는가 | — |

**`AllowMultiple`.** 대부분의 특성은 한 대상에 두 번 붙을 이유가 없다. `[Flags][Flags]`는 오류다.

```text
error CS0579: Duplicate 'Flags' attribute
```

여러 번 붙는 것이 자연스러운 특성도 있다. BCL의 `ConditionalAttribute`가 그렇다(20.10절). 명시적으로 `AllowMultiple = true`를 주지 않으면 한 번만 붙일 수 있다.

**`Inherited`.** 기반 클래스에 붙은 특성이 파생 클래스에도 "보이는지"를 정한다.

```csharp
[AttributeUsage (AttributeTargets.Class | AttributeTargets.Method, Inherited = true)]
internal class TastyAttribute : Attribute { }

[Tasty][Serializable]
internal class BaseType
{
    [Tasty] protected virtual void DoSomething() { }
}

internal class DerivedType : BaseType
{
    protected override void DoSomething() { }
}
```

`DerivedType`과 그 `DoSomething`은 둘 다 `Tasty`로 간주된다. 반면 `DerivedType`은 **직렬화 가능하지 않다** — BCL의 `SerializableAttribute`는 `Inherited = false`로 선언되어 있기 때문이다.

> **⚠️ `Inherited`는 상속되는 대상 종류가 정해져 있다**
>
> .NET이 상속 가능하다고 보는 대상은 **클래스, 메서드, 프로퍼티, 이벤트, 필드, 메서드 반환값, 매개변수**뿐이다. 어셈블리·모듈·인터페이스·제네릭 매개변수에는 상속 개념이 적용되지 않는다. 이런 대상만 받는 특성이라면 `Inherited`를 `true`로 두어도 아무 효과가 없다.

> **⚠️ 상속된 특성은 메타데이터에 존재하지 않는다**
>
> `Inherited = true`인 특성이 파생 타입에도 "적용된다"는 말은 **리플렉션 API가 계층을 거슬러 올라가 찾아 준다**는 뜻이지, 파생 타입의 메타데이터에 특성이 복사된다는 뜻이 아니다. `DerivedType`의 메타데이터에는 `Tasty`가 없다.
>
> 결과가 둘 있다. 첫째, 조회할 때 **상속을 탐색하라고 명시적으로 요청**해야 한다(`inherit: true`). 둘째, 상속 탐색은 계층을 거슬러 올라가는 만큼 비용이 든다. 그리고 모든 리플렉션 메서드가 이 매개변수를 존중하지는 않는다(20.9절).

> **📌 `AttributeUsage`를 빠뜨리면 어떻게 되는가**
>
> 특성 클래스에 `[AttributeUsage]`를 붙이지 않으면 컴파일러와 CLR은 다음을 가정한다.
>
> - 모든 대상에 붙일 수 있다 (`AttributeTargets.All`)
> - 한 대상에 한 번만 붙일 수 있다 (`AllowMultiple = false`)
> - 상속된다 (`Inherited = true`)
>
> 이 기본값은 `AttributeUsageAttribute` 클래스의 필드 초기값 그대로다. 셋 중 가장 위험한 것은 첫 번째다 — 아무 데나 붙는 특성은 조회 코드가 예상하지 못한 위치에서 발견되어 엉뚱하게 동작한다. **특성을 정의할 때 `[AttributeUsage]`는 사실상 필수라고 생각하라.**

## 20.7 명명된 매개변수 vs 위치 매개변수

### 두 종류의 인수

특성에 값을 넘기는 자리는 두 갈래로 갈린다.

```csharp
[XmlType ("Customer", Namespace = "http://oreilly.com")]
public class CustomerEntity { }
```

- `"Customer"` — **위치 매개변수(positional parameter)**. 특성 타입의 **public 생성자 매개변수**에 대응한다.
- `Namespace = "..."` — **명명된 매개변수(named parameter)**. 특성 타입의 **public 필드 또는 public 프로퍼티**에 대응한다.

규칙은 단순하다. **위치 인수는 어느 생성자 하나의 시그니처를 완전히 만족시켜야 하고(필수), 명명 인수는 선택**이다. 그리고 위치 인수가 항상 명명 인수보다 앞에 온다.

```csharp
[DllImport ("Kernel32", CharSet = CharSet.Auto, SetLastError = true)]
public static extern bool GetVersionEx (OSVERSIONINFO ver);
```

`DllImportAttribute`의 생성자는 `string` 하나를 받고, `CharSet`과 `SetLastError`는 public 필드다. 처음 보면 "생성자에 이름 붙은 인수를 넘기는 것"처럼 보이지만 그렇지 않다. **객체를 생성한 뒤 필드·프로퍼티에 대입**하는 별개의 문법이다.

### 컴파일러가 하는 일

논리적으로 컴파일러는 다음 순서를 밟는다.

```text
  [DllImport("Kernel32", CharSet = CharSet.Auto, SetLastError = true)]
                │
                ▼  (1) 위치 인수로 생성자 오버로드 해석
        new DllImportAttribute("Kernel32")
                │
                ▼  (2) 명명 인수를 필드/프로퍼티에 대입
        obj.CharSet = CharSet.Auto;  obj.SetLastError = true;
                │
                ▼  (3) 그 객체의 상태를 바이트 스트림으로 직렬화
        메타데이터 테이블의 blob에 기록
```

3단계의 형식은 이렇다. 각 생성자 인수는 **1바이트 타입 ID + 값**으로 기록되고, 그 뒤에 각 필드/프로퍼티가 **이름 + 1바이트 타입 ID + 값** 순으로 이어진다. 배열은 원소 개수를 먼저 쓰고 원소를 나열한다.

> **📌 특성을 이해하는 가장 좋은 모델**
>
> **"메타데이터 안의 바이트 스트림으로 직렬화된 클래스 인스턴스."** 컴파일 시점에는 인스턴스를 만드는 데 필요한 정보만 기록되고, 런타임에 그 바이트를 역직렬화해 인스턴스를 되살린다. 실제로 컴파일러가 특성 객체를 만들었다가 직렬화하는 것은 아니지만, 관찰되는 동작은 정확히 이 모델대로다. 20.9절이 이 모델의 나머지 절반이다.

### 인수로 쓸 수 있는 타입

특성 생성자의 매개변수, 그리고 public 필드·프로퍼티의 타입은 다음으로 **제한**된다.

| 분류 | 허용되는 타입 |
|---|---|
| 불리언·문자 | `bool`, `char` |
| 정수 | `byte`, `sbyte`, `short`, `ushort`, `int`, `uint`, `long`, `ulong` |
| 부동소수점 | `float`, `double` |
| 기타 | `string`, `System.Type`, `object`, 모든 열거형 |
| 배열 | 위 타입들의 **1차원 0-기반 배열** |

여기 없는 것은 전부 불가능하다. **`decimal`은 쓸 수 없다.** `DateTime`도, 사용자 정의 클래스도, `List<T>`도, 다차원 배열도 안 된다.

```csharp
internal enum Color { Red }

[AttributeUsage (AttributeTargets.All)]
internal sealed class SomeAttribute : Attribute
{
    public SomeAttribute (string name, object o, Type[] types)
    {
        // name  : string
        // o     : 허용된 타입 중 아무거나 (값 타입이면 런타임에 박싱된다)
        // types : Type의 1차원 0-기반 배열
    }
}

[Some ("Jeff", Color.Red, new Type[] { typeof (Math), typeof (Console) })]
internal sealed class SomeType { }
```

`Type` 자리에는 **반드시 `typeof` 연산자**를 쓴다. `object` 자리에는 허용된 타입의 상수 식이면 무엇이든 올 수 있고(`null` 포함), 값 타입이면 특성 인스턴스가 생성될 때 박싱된다.

> **⚠️ 인수는 컴파일 타임 상수 식이어야 한다**
>
> 값이 메타데이터에 **기록**되어야 하므로, 컴파일러가 그 값을 컴파일 시점에 확정할 수 있어야 한다. 올 수 있는 것은 리터럴, `const` 필드, `typeof(...)`, `nameof(...)`, 그리고 이들의 상수 식 조합뿐이다.
>
> ```csharp
> [Description ("v" + Version)]        // OK — const 문자열 연결
> [Description (Config.Title)]         // static readonly 필드면 오류 CS0182
> [Description (GetTitle())]           // 오류 — 메서드 호출
> [MyAttr (typeof (List<int>))]        // OK
> [MyAttr (typeof (List<>))]           // OK — 언바운드 제네릭도 typeof로 가능
> ```
>
> `static readonly`와 `const`의 차이가 여기서 다시 드러난다(79.2절). 버전 관리 관점에서는 `readonly`가 낫지만, **특성 인수 자리에는 `const`만 온다.**

> **⚠️ 배열 인수는 CLS 규격을 벗어난다**
>
> 배열을 받는 생성자를 가진 특성 클래스는 **CLS 규격 준수가 아니다.** C#에서는 동작하지만 모든 .NET 언어에서 쓸 수 있다는 보장이 사라진다. 공개 라이브러리의 특성이라면 배열 대신 `AllowMultiple = true`로 여러 번 붙이게 하는 설계가 낫다.
>
> ```csharp
> // 이것보다
> [Roles (new[] { "Admin", "Auditor" })]
> // 이 쪽이 낫다
> [AttributeUsage (AttributeTargets.Method, AllowMultiple = true)]
> public sealed class RoleAttribute : Attribute { ... }
>
> [Role ("Admin")]
> [Role ("Auditor")]
> public void Delete() { }
> ```

### 위치와 명명, 어느 쪽으로 설계할 것인가

| 기준 | 위치 매개변수 | 명명된 매개변수 |
|---|---|---|
| 대응하는 멤버 | public 생성자 매개변수 | public 필드 / 프로퍼티 |
| 필수 여부 | 필수 | 선택 |
| 적용부 문법 | `[Attr(x, y)]` | `[Attr(Name = x)]` |
| 나중에 추가할 때 | 생성자 오버로드가 늘어난다 | 프로퍼티 하나 추가로 끝 |
| 읽는 쪽 | `ConstructorArguments` | `NamedArguments` |

> **💡 필수는 생성자로, 선택은 프로퍼티로 — 예외 없이**
>
> "이 특성이 의미를 가지려면 반드시 있어야 하는 값"만 생성자로 받고 나머지는 전부 프로퍼티로 만들어라. 선택 값을 생성자 오버로드로 표현하기 시작하면 조합 폭발이 일어나고, 나중에 인수 하나를 추가할 때 기존 호출부와 이진 호환성 문제가 생긴다. 프로퍼티는 추가해도 기존 적용부가 그대로 컴파일된다.
>
> 특성에 **선택적 매개변수(기본값 있는 생성자 매개변수)** 를 쓰는 것도 가능하지만, 그 기본값은 호출부에 박히므로 나중에 기본값을 바꿔도 재컴파일 전에는 반영되지 않는다. 특성 인수에서는 프로퍼티 쪽이 안전하다.

## 20.8 어셈블리·백킹 필드·람다에 특성 적용하기

### 암시적 대상과 명시적 대상

특성의 대상은 **바로 뒤에 오는 코드 요소**다. 대개는 타입이나 멤버이고, 이때는 대상을 따로 밝힐 필요가 없다.

그런데 "바로 뒤에 오는 것"으로는 지목할 수 없는 대상이 있다. 어셈블리 전체가 그렇고, 자동 구현 프로퍼티가 만들어내는 백킹 필드가 그렇고, 메서드의 반환값이 그렇다. 이때 **대상 지정자(target specifier)** 를 접두사로 붙인다.

CLR은 파일 메타데이터로 표현되는 거의 모든 것에 특성을 붙일 수 있게 허용한다. 주로 쓰이는 정의 테이블은 TypeDef(클래스·구조체·열거형·인터페이스·델리게이트), MethodDef(생성자 포함), ParamDef, FieldDef, PropertyDef, EventDef, AssemblyDef, ModuleDef다. C#이 소스에서 지목할 수 있는 대상은 다음과 같다.

```csharp
using System;

[assembly: SomeAttr]                                  // 어셈블리
[module:   SomeAttr]                                  // 모듈

[type: SomeAttr]                                      // 타입
internal sealed class SomeType<[typevar: SomeAttr] T> // 제네릭 타입 매개변수
{
    [field: SomeAttr]                                 // 필드
    public int SomeField = 0;

    [return: SomeAttr]                                // 반환값
    [method: SomeAttr]                                // 메서드
    public int SomeMethod (
        [param: SomeAttr]                             // 매개변수
        int someParam) => someParam;

    [property: SomeAttr]                              // 프로퍼티
    public string SomeProp
    {
        [method: SomeAttr]                            // get 접근자 메서드
        get => null;
    }

    [event:  SomeAttr]                                // 이벤트
    [field:  SomeAttr]                                // 컴파일러가 만든 필드
    [method: SomeAttr]                                // 컴파일러가 만든 add/remove 메서드
    public event EventHandler SomeEvent;
}
```

| 지정자 | 대상 | 생략 가능? |
|---|---|---|
| `assembly` | 어셈블리 | **불가** |
| `module` | 모듈 | **불가** |
| `type` | 클래스·구조체·열거형·인터페이스·델리게이트 | 가능 |
| `method` | 메서드·생성자·접근자 | 가능(접근자에서는 필요할 수 있다) |
| `param` | 매개변수 | 가능 |
| `return` | 메서드 반환값 | **불가** |
| `field` | 필드 | 가능(자동 프로퍼티·이벤트에서는 필요) |
| `property` | 프로퍼티 | 가능 |
| `event` | 이벤트 | 가능 |
| `typevar` | 제네릭 타입 매개변수 | 가능 |

생략할 수 있는 경우에도, 같은 자리에 여러 대상이 겹칠 때는 접두사로 의도를 밝혀야 한다. 자동 프로퍼티 선언 앞에 특성을 쓰면 기본 대상은 **프로퍼티**이고, 이벤트 선언 앞이면 **이벤트**다. 백킹 필드나 접근자 메서드를 노리려면 접두사가 필수다.

### 어셈블리 특성

어셈블리 전체에 붙는 정보는 `[assembly:]`로 지정한다.

```csharp
[assembly: AssemblyFileVersion ("1.2.3.4")]
```

관례적으로 이런 선언은 `AssemblyInfo.cs` 같은 별도 파일에 모은다. 어셈블리 특성이 매니페스트로 흘러가는 경로와 SDK 스타일 프로젝트가 이 특성들을 자동 생성하면서 생기는 충돌(CS0579)은 52.2절에서 다뤘다.

> **⚠️ 어셈블리 특성은 `using` 뒤, 타입 선언 앞에 와야 한다**
>
> C#은 `[assembly:]`와 `[module:]` 특성이 **`using` 지시문 다음, 첫 타입 선언 이전**에 오도록 강제한다. 위치를 어기면 CS1730 오류가 난다. 파일 범위 네임스페이스(12.1절)를 쓰는 파일에서는 네임스페이스 선언보다도 앞이어야 한다.

### 백킹 필드에 특성 붙이기

`field:` 접두사는 자동 구현 프로퍼티의 백킹 필드를 지목한다.

```csharp
[field: NonSerialized]
public int MyProperty { get; set; }
```

`NonSerialized`는 필드에만 붙는 특성이라 프로퍼티에 직접 붙일 수 없다. 접두사가 없으면 CS0592("이 선언 형식에 적용할 수 없는 특성") 오류가 난다.

> **📌 `[field:]`가 실무에서 쓰이는 자리**
>
> `NonSerialized`는 이제 권장되지 않는 이진 직렬화의 유물이지만(41장), `[field:]` 자체는 여전히 쓸모가 있다. 백킹 필드에만 적용되는 특성 — 상호운용의 `[MarshalAs]`, 일부 ORM/직렬화 라이브러리의 필드 대상 특성, 디버거의 `[DebuggerBrowsable]`(74.2절) — 을 자동 프로퍼티에 걸 때 필요하다. 이 접두사가 없다면 자동 프로퍼티를 포기하고 백킹 필드를 손으로 써야 한다.
>
> ※C# 13의 `field` 키워드(13.8절)와 이름이 같지만 서로 다른 기능이다. 하나는 특성 대상 지정자, 하나는 접근자 본문에서 백킹 필드를 참조하는 컨텍스트 키워드다.

### 반환값에 특성 붙이기

```csharp
[return: MarshalAs (UnmanagedType.Bool)]
public static extern bool SomeNativeCall();
```

반환값은 CLR 메타데이터에서 **매개변수 번호 0의 ParamDef 항목**으로 표현된다. 그래서 매개변수와 같은 방식으로 특성을 붙일 수 있다. `return:`을 생략하면 특성이 메서드 자체에 붙으므로 의미가 완전히 달라진다.

### 람다 식에 특성 붙이기 ※C# 10

C# 10부터 람다 식의 메서드·매개변수·반환값에 특성을 붙일 수 있다.

```csharp
Action<int> a = [Description ("Method")]
                [return: Description ("Return value")]
                ([Description ("Parameter")] int x) => Console.Write (x);
```

이 특성들은 **델리게이트가 가리키는, 컴파일러가 생성한 메서드**에 적용된다. 그래서 조회할 때는 델리게이트에서 메서드로 한 단계 들어가야 한다.

```csharp
var methodAtt = a.GetMethodInfo().GetCustomAttributes();
var paramAtt  = a.GetMethodInfo().GetParameters()[0].GetCustomAttributes();
var returnAtt = a.GetMethodInfo().ReturnParameter.GetCustomAttributes();
```

> **📌 람다 특성이 있어서 좋은 곳**
>
> ASP.NET처럼 "메서드에 특성을 붙이면 프레임워크가 알아서 한다"는 모델을 쓰는 곳이다. 최소 API의 엔드포인트 하나를 위해 이름 있는 메서드를 따로 만들 필요가 없어진다.

> **⚠️ 람다 특성에는 문법 제약이 둘 있다**
>
> **(1) 매개변수 괄호가 필수다.** 특성을 붙이는 순간 `x => ...` 형태를 쓸 수 없고 `(int x) => ...`로 써야 한다. 문법적 모호성을 없애기 위한 규칙이다.
>
> **(2) 식 트리 람다에는 붙일 수 없다.** `Expression<Func<...>>`으로 변환되는 람다에 특성을 붙이면 컴파일 오류다. 식 트리는 메서드로 컴파일되지 않고 데이터 구조로 만들어지므로 특성을 매달 메타데이터 항목이 없다(31장).

### 여러 특성을 한 번에

한 대상에 특성을 여러 개 붙일 수 있다. 대괄호 하나에 쉼표로 나열해도 되고, 대괄호를 여러 벌 써도 되고, 섞어도 된다. **세 형태는 의미가 완전히 같다.**

```csharp
[Serializable, Obsolete, CLSCompliant (false)]
public class Bar { }

[Serializable] [Obsolete] [CLSCompliant (false)]
public class Bar2 { }

[Serializable, Obsolete]
[CLSCompliant (false)]
public class Bar3 { }
```

적용 **순서에는 의미가 없다.** 메타데이터에 기록되는 순서가 소스 순서와 같다는 보장도 없고, 조회 API가 돌려주는 순서도 정해져 있지 않다. 특성 여러 개의 상대적 순서에 의존하는 코드를 쓰지 마라.

생성자가 매개변수를 받지 않으면 괄호는 선택이고, `Attribute` 접미사도 선택이다. 아래 네 줄은 전부 같은 동작을 한다.

```csharp
[Serializable][Flags]
[Serializable, Flags]
[FlagsAttribute, SerializableAttribute]
[FlagsAttribute()][Serializable()]
```

## 20.9 런타임에 특성 조회하기 (심화는 57장)

### 특성만으로는 아무 일도 일어나지 않는다

특성 클래스를 정의하고 여기저기 붙여도 프로그램의 동작은 **전혀 바뀌지 않는다.** 어셈블리에 메타데이터가 조금 늘어날 뿐이다. 대부분의 특성은 컴파일러에게도 아무 의미가 없다 — 컴파일러는 소스에서 특성을 발견해 대응하는 메타데이터를 방출할 뿐이다.

특성이 의미를 가지려면 **누군가 그것을 읽고 다르게 행동해야** 한다. 그 누군가는 컴파일러이거나(`[Obsolete]`, `[Conditional]`), 런타임이거나(`[DllImport]`, `[StructLayout]`), 프레임워크이거나, 우리가 짠 리플렉션 코드다.

```text
   [소스]                    [컴파일 타임]                 [런타임]

  [Flags]                컴파일러가 특성 정보를        누군가 GetCustomAttribute를
  enum Actions   ───►    blob으로 직렬화해            ───►  호출하는 그 순간
  { ... }                메타데이터에 기록                  blob을 역직렬화해
                                                            FlagsAttribute 인스턴스 생성
                         ※ 이 시점에 특성 인스턴스는              │
                            만들어지지 않는다                     ▼
                                                        Enum.ToString이 분기를 바꾼다
```

### 정전(正典) 예제 — `[Flags]`는 이렇게 동작한다

20.3절에서 `[Flags]`가 `Enum.ToString`의 경로를 바꾼다고 했다. 그 구현을 개념적으로 쓰면 이렇다.

```csharp
public override string ToString()
{
    // 이 열거형 타입에 FlagsAttribute가 적용되어 있는가?
    if (this.GetType().IsDefined (typeof (FlagsAttribute), false))
    {
        // 그렇다 — 비트 플래그로 취급하는 경로
        // ...
    }
    else
    {
        // 아니다 — 단일 값으로 취급하는 경로
        // ...
    }
    // ...
}
```

`[Flags]`가 특별한 언어 기능처럼 보였다면, 실체는 이 `if` 한 줄이다. 우리가 정의한 특성도 정확히 같은 방식으로 동작하게 만들 수 있다.

### 조회 API 세 갈래

`System.Reflection.CustomAttributeExtensions`가 제공하는 확장 메서드가 표준 경로다. `Assembly`, `Module`, `MemberInfo`(및 그 파생인 `Type`, `MethodInfo`, `FieldInfo`, `PropertyInfo`, `EventInfo`), `ParameterInfo`에 대해 오버로드를 갖는다.

| 메서드 | 돌려주는 것 | 특성 인스턴스를 만드는가 | 언제 쓰나 |
|---|---|---|---|
| `IsDefined` | `bool` | **만들지 않는다** | 유무만 알면 될 때 |
| `GetCustomAttributes` | 컬렉션(없으면 빈 컬렉션) | 매번 새로 만든다 | `AllowMultiple = true`이거나 전부 나열할 때 |
| `GetCustomAttribute` | 인스턴스 하나(없으면 `null`) | 매번 새로 만든다 | `AllowMultiple = false`일 때 |

```csharp
// 유무만 확인 — 가장 싸다
bool isEntity = typeof(Customer).IsDefined (typeof (EntityAttribute), inherit: false);

// 인수까지 필요 — 인스턴스가 만들어진다
var attr = typeof(Customer).GetCustomAttribute<EntityAttribute>();
if (attr != null) Console.WriteLine (attr.TableName);
```

> **⚠️ 특성 인스턴스는 조회할 때마다 새로 만들어진다**
>
> 이것이 이 절에서 가장 중요한 사실이다. `GetCustomAttribute(s)`를 호출할 때마다 런타임은 메타데이터의 blob을 읽어 **생성자를 호출하고 프로퍼티 세터를 실행**해 새 인스턴스를 만든다. 같은 대상에 두 번 물으면 서로 다른 두 객체가 돌아온다.
>
> 결과가 셋 있다.
>
> - **캐시하지 않으면 반복 비용이 그대로 든다.** 조회는 메타데이터를 훑으며 문자열 비교를 수행한다. 값싸지 않다.
> - **`ReferenceEquals`로 특성을 비교하면 언제나 `false`다.** 비교가 필요하면 `System.Attribute`가 재정의한 `Equals`(리플렉션으로 필드를 비교한다)나 `Match` 가상 메서드를 쓴다.
> - **특성 클래스의 생성자·세터·정적 생성자가 실행된다.** 신뢰할 수 없는 어셈블리의 특성을 훑는 코드라면 이것이 보안 문제가 된다. 코드를 실행하지 않고 특성 정보만 읽는 `System.Reflection.CustomAttributeData` 경로가 이 때문에 존재한다(57.11절).

> **⚠️ `GetCustomAttribute`는 여러 개가 있으면 예외를 던진다**
>
> `AllowMultiple = true`인 특성에 대해 단수형 `GetCustomAttribute`를 부르고 대상에 두 개 이상이 붙어 있으면 `System.Reflection.AmbiguousMatchException`이 나온다. 특성 설계와 조회 코드가 짝을 이루어야 한다.

> **⚠️ `inherit` 매개변수를 모든 API가 존중하지는 않는다**
>
> `Attribute`, `Type`, `MethodInfo`가 제공하는 조회 메서드만 `inherit` 매개변수를 실제로 따른다. 그 밖의 리플렉션 메서드는 이 인수를 받으면서도 **무시하고 상속 계층을 보지 않는다.** 이벤트·프로퍼티·필드·생성자·매개변수에 대해 상속된 특성을 찾아야 한다면 `System.Attribute`의 정적 메서드를 써야 한다.
>
> 또 하나. 조회 메서드에 특성 클래스를 넘기면 **그 클래스와 그 파생 클래스 전부**를 찾는다. 정확히 그 타입만 원한다면 반환값을 한 번 더 검사하거나, 20.6절의 권고대로 특성 클래스를 `sealed`로 만들어라.

### 여기서 멈추는 이유

리플렉션 API의 전체 계층, `CustomAttributeData`를 이용한 안전한 조회, 조회 결과 캐싱 전략, 트리밍/Native AOT에서 특성 기반 코드가 깨지는 지점은 **57.11절과 57.12절**에서 다룬다. 이 장의 목표는 "특성은 메타데이터일 뿐이며 인스턴스는 조회 시점에 생긴다"는 모델을 세우는 것까지다.

> **💡 특성 + 리플렉션을 쓰기 전에 소스 생성기를 검토하라**
>
> "특성을 붙이면 프레임워크가 알아서 처리한다"는 설계는 오랫동안 리플렉션으로 구현됐다. 지금은 같은 일을 **컴파일 타임**에 하는 길이 있다. 소스 생성기는 특성을 코드 생성의 트리거로 읽고 평범한 C# 코드를 만들어 낸다. 시작 비용도, 런타임 리플렉션 비용도, 트리밍 문제도 사라진다. 최신 BCL이 로깅·JSON·정규식에서 이 방향으로 옮겨 간 이유다(57.15절).

## 20.10 조건부 특성 `[Conditional]`

`System.Diagnostics.ConditionalAttribute`는 붙는 자리에 따라 두 가지 다른 일을 한다. 메서드에 붙으면 **호출부가 지워지고**, 특성 클래스에 붙으면 **특성 자체가 메타데이터에서 빠진다.**

### 메서드에 붙였을 때 — 호출부가 사라진다

```csharp
[Conditional ("DEBUG")]
static void LogStatus (string message) => Console.WriteLine (message);
```

지정한 전처리기 심볼이 **호출하는 쪽 파일에서** 정의되어 있지 않으면, 컴파일러는 그 호출문 전체를 IL에서 제거한다. 메서드 본문은 어셈블리에 그대로 남는다. 사라지는 것은 호출이다.

```csharp
LogStatus ($"처리 완료: {ComputeExpensiveReport()}");
```

`DEBUG`가 없으면 이 줄이 통째로 없어진다. **인수 계산도 함께 사라진다** — `ComputeExpensiveReport()`는 호출되지 않는다. 이것이 `#if`로 감싸는 것과 정적 `bool` 플래그로 분기하는 것 사이의 정확한 중간 지점이고, `[Conditional]`의 존재 이유다.

> **⚠️ `[Conditional]` 메서드의 인수에 부수 효과를 넣지 마라**
>
> 인수 계산이 사라진다는 성질의 반대편이다. `Debug.Assert(list.Remove(item))` 같은 코드는 릴리스 빌드에서 `list.Remove` 자체가 실행되지 않는다. 디버그 빌드에서는 정상인데 릴리스에서만 틀리는, 재현이 지독하게 어려운 버그가 된다.
>
> 이 함정의 전체 사례와 세 가지 조건부 코드 기법의 비교는 12.8절과 73.1절에 있다.

조건 검사가 **호출자를 컴파일할 때** 수행된다는 점이 중요하다. 라이브러리를 한 벌만 빌드해 배포해도, 그것을 쓰는 각 애플리케이션이 자기 빌드 구성에 따라 호출을 남기거나 지운다.

`[Conditional]`은 `AllowMultiple = true`로 선언되어 있어 한 메서드에 여러 번 붙일 수 있고, 이때 조건은 **OR**로 결합된다.

```csharp
[Conditional ("DEBUG"), Conditional ("VERBOSE")]
static void Trace (string m) { }     // 둘 중 하나만 정의돼 있어도 호출이 남는다
```

메서드에 붙일 때의 제약(반환 타입이 `void`여야 하고, `override`할 수 없으며, 델리게이트를 만들 수 없다는 것)과 리플렉션 호출을 막지 못한다는 사실은 73.1절에서 다룬다.

### 특성 클래스에 붙였을 때 — 특성이 방출되지 않는다

`[Conditional]`을 **특성 클래스 자체**에 붙이면 다른 규칙이 적용된다. 그 특성은 지정한 심볼이 정의된 파일에서만 메타데이터에 기록된다.

```csharp
// file1.cs
#define DEBUG
using System;
using System.Diagnostics;

[Conditional ("DEBUG")]
public class TestAttribute : Attribute { }
```

```csharp
// file2.cs
#define DEBUG
[Test]
class Foo
{
    [Test] string s;
}
```

컴파일러는 `file2.cs`의 범위에서 `DEBUG` 심볼이 유효할 때만 `[Test]`를 메타데이터에 넣는다. 심볼이 없으면 **특성 클래스의 정의와 구현은 어셈블리에 그대로 남지만, 적용 기록만 사라진다.**

여러 조건을 걸면 역시 OR다.

```csharp
//#define TEST
#define VERIFY
using System;
using System.Diagnostics;

[Conditional ("TEST")][Conditional ("VERIFY")]
public sealed class CondAttribute : Attribute { }

[Cond]
public sealed class Program
{
    public static void Main()
        => Console.WriteLine ("CondAttribute is {0}applied to Program type.",
               Attribute.IsDefined (typeof (Program), typeof (CondAttribute)) ? "" : "not ");
}
```

`TEST`나 `VERIFY` 중 하나라도 정의되어 있으면 `[Cond]`가 방출되고 `IsDefined`가 `true`를 돌려준다.

> **📌 왜 특성 방출을 조건부로 만들고 싶은가**
>
> 개발 도구용 특성이 늘어나면 메타데이터가 부풀고, 그만큼 파일이 커지고 프로세스의 워킹 셋이 늘고 시작 시간이 나빠진다. 정적 분석 도구만 읽는 `SuppressMessage` 같은 특성이 대표적이다 — 프로그램이 정상 실행될 때는 아무도 읽지 않는데 배포본에 계속 실려 다닌다.
>
> `[Conditional]`을 특성 클래스에 붙여 두면 분석을 돌릴 때만 심볼을 정의해 특성을 남기고, 평소 배포 빌드에서는 통째로 빠지게 만들 수 있다.

정리하면 이렇다. **메서드**에 붙었을 때 심볼이 없으면 그 메서드에 대한 **호출문**이 인수 계산까지 통째로 사라지고, 메서드 본문과 메타데이터는 남는다. **특성 클래스**에 붙었을 때 심볼이 없으면 그 특성의 **적용 기록**(메타데이터 blob)만 사라지고, 특성 클래스의 정의와 구현은 남는다.

> **⚠️ 심볼은 "정의하는 쪽"이 아니라 "쓰는 쪽"에서 판정된다**
>
> 두 경우 모두 판단 기준은 **소비 지점의 컴파일 컨텍스트**다. `[Conditional("DEBUG")]`를 선언한 파일에 `#define DEBUG`가 있어도, 호출하거나 적용하는 파일에 심볼이 없으면 사라진다. 반대도 마찬가지다. 프로젝트 전체에 적용하려면 `#define`이 아니라 `.csproj`의 `DefineConstants`를 쓴다(12.7절).

## 20.11 호출자 정보 특성 — `CallerMemberName`, `CallerFilePath`, `CallerLineNumber`, `CallerArgumentExpression`

### 네 가지 특성

`System.Runtime.CompilerServices` 네임스페이스에는 **선택적 매개변수의 기본값을, 호출부의 소스 코드에서 뽑아낸 정보로 채우라**고 컴파일러에 지시하는 특성이 있다. 네 개다.

| 특성 | 채워지는 값 | 매개변수 타입 | 도입 |
|---|---|---|---|
| `[CallerMemberName]` | 호출한 멤버의 이름 | `string` | C# 5 |
| `[CallerFilePath]` | 호출한 소스 파일의 경로 | `string` | C# 5 |
| `[CallerLineNumber]` | 호출한 소스의 줄 번호 | `int` | C# 5 |
| `[CallerArgumentExpression("param")]` | 지정한 매개변수에 넘긴 **인수 식의 원문** | `string` | ※C# 10 |

앞의 세 개를 한 번에 보여주는 예제다.

```csharp
using System;
using System.Runtime.CompilerServices;

class Program
{
    static void Main() => Foo();

    static void Foo (
        [CallerMemberName] string memberName = null,
        [CallerFilePath]   string filePath   = null,
        [CallerLineNumber] int    lineNumber = 0)
    {
        Console.WriteLine (memberName);
        Console.WriteLine (filePath);
        Console.WriteLine (lineNumber);
    }
}
```

프로그램이 `c:\source\test\Program.cs`에 있다면 출력은 이렇다.

```text
Main
c:\source\test\Program.cs
6
```

### 컴파일 결과 — 치환은 호출부에서 일어난다

핵심은 이것이다. 이 특성들은 런타임에 스택을 걷지 않는다. **일반적인 선택적 매개변수와 똑같이, 컴파일러가 호출 지점에서 인수를 채워 넣는다.** 위의 `Main`은 다음의 문법 설탕일 뿐이다.

```csharp
static void Main() => Foo ("Main", @"c:\source\test\Program.cs", 6);
```

```text
   호출부 소스                   컴파일러                        IL
  ─────────────                ───────────                   ─────────
                             호출부의 멤버 이름·파일 경로·
     Foo();          ───►    줄 번호를 알고 있으므로     ───►   ldstr "Main"
                             생략된 인수 자리에                 ldstr "c:\source\..."
                             리터럴을 채워 넣는다               ldc.i4.6
                                                               call Foo
```

그래서 비용이 사실상 0이다. `StackTrace`로 호출자를 알아내는 방식(73.4절)과 비교하면 차원이 다르다 — 그쪽은 런타임에 스택을 걷고 심볼을 해석해야 한다.

> **⚠️ 치환이 일어나지 않는 경우가 있다**
>
> 치환의 주체가 컴파일러이므로, 호출부가 컴파일 타임에 확정되지 않으면 아무 일도 일어나지 않는다.
>
> - **리플렉션 호출** — `MethodInfo.Invoke`로 부르면 인수를 직접 채워야 하고, 생략하면 선언된 기본값(대개 `null`이나 `0`)이 그대로 들어간다.
> - **`dynamic` 경유 호출** — 바인딩이 런타임으로 미뤄지므로 마찬가지다(59장).
> - **호출자가 값을 명시적으로 넘긴 경우** — 명시한 값이 이긴다. 특성이 있어도 덮어쓰지 않는다.
>
> 마지막 항목은 함정이자 기능이다. 래퍼 메서드가 자기 호출자의 정보를 그대로 전달하고 싶을 때 유용하다.
>
> ```csharp
> void LogInfo (string msg, [CallerMemberName] string caller = null)
>     => LogCore (msg, caller);        // 자기 이름이 아니라 원래 호출자 이름이 전달된다
> ```

> **⚠️ `[CallerMemberName]`이 돌려주는 "이름"의 정체**
>
> 항상 우리가 기대하는 C# 식별자가 나오는 것은 아니다. 생성자에서 호출하면 `".ctor"`, 정적 생성자에서는 `".cctor"`, 파이널라이저에서는 `"Finalize"`가 들어온다. 프로퍼티나 인덱서의 접근자에서 호출하면 접근자 이름(`get_Name`)이 아니라 **프로퍼티 이름**이 들어온다 — 이것이 아래 `INotifyPropertyChanged` 패턴이 성립하는 이유다.
>
> 최상위 문(top-level statements)이나 람다 안에서 호출하면 컴파일러가 생성한 메서드의 이름이 나올 수 있다. 이 값을 로그 이상의 용도로 — 예컨대 문자열 키로 — 쓸 때는 실제 출력을 확인해야 한다.

> **⚠️ `[CallerFilePath]`는 빌드 머신의 경로를 어셈블리에 박는다**
>
> 채워지는 값은 **컴파일러에게 보인 경로 그대로**다. 개발자 로컬 빌드라면 `C:\Users\누구\source\repos\...`가 문자열 리터럴로 어셈블리에 들어간다. 이것이 로그에 찍혀 나가면 사소하지만 실질적인 정보 노출이다.
>
> 완화 방법은 컴파일러의 경로 매핑 기능이다. `<DeterministicSourcePaths>`를 켜거나 `PathMap`을 지정하면 소스 경로가 결정적인 형태로 치환된다. CI 빌드에서는 대개 기본으로 켜져 있다.

### 실전 용례 1 — 로깅

가장 흔한 용도다. 로그 호출부마다 메서드 이름을 손으로 적을 필요가 없고, 이름을 바꿔도 로그가 저절로 따라온다.

```csharp
static void Log (
    string message,
    [CallerMemberName] string member = "",
    [CallerFilePath]   string file   = "",
    [CallerLineNumber] int    line   = 0)
{
    Console.WriteLine ($"[{Path.GetFileName(file)}:{line} {member}] {message}");
}
```

> **💡 리팩터링에 강한 로그**
>
> 손으로 적은 `Log("SaveOrder: 시작")` 같은 문자열은 메서드 이름을 바꾸는 순간 거짓말이 된다. 컴파일러는 문자열 안의 이름을 고쳐 주지 않는다. `[CallerMemberName]`은 그 결합을 끊는다. `nameof`가 하는 일(13.15절)과 같은 종류의 개선이다.

### 실전 용례 2 — `INotifyPropertyChanged`

`System.ComponentModel`의 표준 인터페이스다. 이벤트 인수가 **바뀐 프로퍼티의 이름**을 요구한다.

```csharp
public interface INotifyPropertyChanged
{
    event PropertyChangedEventHandler PropertyChanged;
}

public delegate void PropertyChangedEventHandler (object sender, PropertyChangedEventArgs e);

public class PropertyChangedEventArgs : EventArgs
{
    public PropertyChangedEventArgs (string propertyName);
    public virtual string PropertyName { get; }
}
```

`[CallerMemberName]` 없이 구현하면 세터마다 프로퍼티 이름을 문자열로 적어야 한다. 오타가 나도 컴파일은 통과하고, 이름을 바꾸면 조용히 깨진다. 특성을 쓰면 이름이 아예 등장하지 않는다.

```csharp
public class Foo : INotifyPropertyChanged
{
    public event PropertyChangedEventHandler PropertyChanged = delegate { };

    void RaisePropertyChanged ([CallerMemberName] string propertyName = null)
        => PropertyChanged (this, new PropertyChangedEventArgs (propertyName));

    string customerName;
    public string CustomerName
    {
        get => customerName;
        set
        {
            if (value == customerName) return;
            customerName = value;
            RaisePropertyChanged();
            // 컴파일러가 위 줄을 이렇게 바꾼다:
            // RaisePropertyChanged ("CustomerName");
        }
    }
}
```

### `CallerArgumentExpression` ※C# 10

넷째 특성은 값이 아니라 **인수로 쓰인 식의 소스 코드 원문**을 가져온다. 어느 매개변수를 대상으로 할지 문자열로 지정한다.

```csharp
Print (Math.PI * 2);

void Print (double number,
            [CallerArgumentExpression ("number")] string expr = null)
    => Console.WriteLine (expr);

// 출력: Math.PI * 2
```

컴파일러는 호출 식의 소스를 **문자 그대로** 넘긴다. 주석까지 포함된다.

```csharp
Print (Math.PI /*(π)*/ * 2);
// 출력: Math.PI /*(π)*/ * 2
```

주 용도는 **검증·단언 라이브러리**다. 실패 메시지에 조건식 자체가 들어가면 디버깅이 훨씬 쉬워진다.

```csharp
Assert (2 + 2 == 5);

void Assert (bool condition,
             [CallerArgumentExpression ("condition")] string message = null)
{
    if (!condition) throw new Exception ("Assertion failed: " + message);
}
// 예외 메시지: Assertion failed: 2 + 2 == 5
```

BCL도 이 패턴을 쓴다. .NET 6에 추가된 `ArgumentNullException.ThrowIfNull`이 그렇다.

```csharp
public static void ThrowIfNull (object argument,
    [CallerArgumentExpression ("argument")] string paramName = null)
{
    if (argument == null)
        throw new ArgumentNullException (paramName);
}
```

```csharp
void Print (string message)
{
    ArgumentNullException.ThrowIfNull (message);   // paramName이 "message"로 채워진다
    // ...
}
```

`[CallerArgumentExpression]`은 여러 매개변수에 각각 적용해 여러 인수 식을 동시에 잡을 수 있다. 널 검사 관용구로서의 `ThrowIfNull`은 21.10절에서 더 다룬다.

> **💡 대상 이름은 `nameof`로 써라**
>
> `[CallerArgumentExpression("number")]`의 문자열은 매개변수 이름과 정확히 일치해야 하는데, 틀려도 컴파일 오류가 아니라 **경고**로 끝나고 런타임에는 기본값이 그대로 들어간다. `nameof`를 쓰면 이름을 바꿀 때 컴파일러가 잡아 준다.
>
> ```csharp
> void Assert (bool condition,
>              [CallerArgumentExpression (nameof (condition))] string message = null)
> ```
>
> `nameof`는 컴파일 타임 상수 문자열을 만들므로 특성 인수 제약(20.7절)을 만족한다.

> **⚠️ 호출자 정보 특성은 반드시 선택적 매개변수에 붙인다**
>
> 치환 메커니즘 자체가 "생략된 선택적 매개변수의 기본값 자리"에 값을 넣는 것이므로, 기본값이 없는 매개변수에는 채울 자리가 없다. `CallerMemberName`·`CallerFilePath`·`CallerLineNumber`를 기본값 없는 매개변수에 붙이면 컴파일러가 오류로 거부한다. 반면 `[CallerArgumentExpression]`의 대상 이름이 틀린 경우는 경고에 그치고 런타임에는 기본값이 그대로 들어간다.
>
> 매개변수 타입도 맞아야 한다. `[CallerLineNumber]`를 `string` 매개변수에 붙이면 `int`에서 `string`으로의 표준 변환이 없으므로 컴파일 오류다.

| 상황 | 어느 특성을 쓰나 |
|---|---|
| 로그에 호출 위치를 남긴다 | `CallerMemberName` + `CallerFilePath` + `CallerLineNumber` |
| 프로퍼티 변경 알림 | `CallerMemberName` |
| 인수 검증 헬퍼의 `paramName` | `CallerArgumentExpression` |
| 단언 실패 메시지 | `CallerArgumentExpression` |
| 래퍼가 원래 호출자 정보를 전달 | `CallerMemberName`(값을 그대로 넘긴다) |

## 이 장의 요약

- **`enum`은 상수 필드 N개와 `value__` 필드 하나를 가진 값 타입이다.** `System.Enum`을 상속하지만 그 자체는 봉인된 값 타입이고, 언박싱 상태에서는 기저 정수와 런타임에서 구별되지 않는다. 그래서 일상적 사용에 비용이 없다.
- **열거형 심볼은 `const`다.** 컴파일러가 값으로 치환하므로, 공개된 열거형의 기존 멤버 값을 바꾸면 재컴파일하지 않은 소비자가 조용히 틀린 값을 쓰게 된다. 값은 추가만 하고 바꾸지 않는다.
- **정수 ↔ 열거형 변환에 명시적 캐스트를 요구하는 것은 성능이 아니라 의미 보호 때문이다.** 예외는 `0` 하나뿐이며, 그래서 값 0에는 반드시 유효한 멤버를 정의해야 한다.
- **`(Color)999`는 완전히 합법이다.** 열거형은 정적 타입 안전성만 주고 강한 타입 안전성은 주지 않는다. 캐스트·산술·역직렬화·상호운용·버전 불일치로 정의되지 않은 값이 들어오며, 런타임은 아무 예외도 던지지 않는다. 방어는 경계에서 한 번, `switch`의 `default: throw` 또는 마스크 검사로 한다.
- **`Enum.IsDefined`는 느리고, 대소문자를 구분하고, 어셈블리 경계를 넘으면 의미가 달라지고, `[Flags]` 열거형에는 아예 쓸 수 없다.** `TryParse`가 숫자 문자열에 `true`를 돌려준다는 사실과 함께 기억해야 할 함정이다.
- **`[Flags]`는 컴파일러에 아무 지시도 하지 않는다.** 바뀌는 것은 `Enum.ToString`/`Format`의 런타임 경로뿐이며, 대응 심볼이 없는 비트가 하나라도 섞이면 이름을 전부 버리고 숫자를 돌려준다.
- **`HasFlag`는 읽기 좋지만 `Enum` 매개변수 때문에 박싱을 부른다.** .NET Core 2.1 이후 JIT이 정적 타입이 확정된 호출을 최적화하지만, .NET Framework에는 그 최적화가 없다. 확장 메서드로 감싸면 읽기 쉬움과 무할당을 동시에 얻는다.
- **특성은 `System.Attribute`에서 파생한 클래스이며 논리적 상태 컨테이너로 설계한다.** 필수 상태는 생성자(위치 인수), 선택 상태는 프로퍼티(명명 인수)로 받고, 클래스는 `sealed`로 만들고, `[AttributeUsage]`로 대상·중복·상속을 명시한다. 생략하면 "모든 대상·한 번만·상속됨"이 된다.
- **특성 인수는 컴파일 타임 상수 식이어야 하고 타입도 제한된다.** `decimal`, `DateTime`, 사용자 정의 타입, 다차원 배열은 쓸 수 없다. `static readonly` 필드도 안 된다.
- **특성은 메타데이터에 직렬화된 바이트 뭉치일 뿐이며, 인스턴스는 조회하는 그 순간 만들어진다.** 조회할 때마다 새 객체가 생기고 생성자와 세터가 실행된다. 그래서 조회 결과는 캐시하고, `ReferenceEquals`로 비교하지 않으며, 유무만 알면 될 때는 `IsDefined`를 쓴다.
- **`[Conditional]`은 메서드에 붙으면 호출부를, 특성 클래스에 붙으면 적용 기록을 지운다.** 두 경우 모두 판정 기준은 정의한 쪽이 아니라 **소비하는 쪽**의 컴파일 컨텍스트다.
- **호출자 정보 특성 네 종은 런타임 스택 조사가 아니라 컴파일 타임 인수 치환이다.** 비용이 사실상 0인 대신, 리플렉션이나 `dynamic`을 거친 호출에서는 아무것도 채워지지 않는다.

## 연습 문제

1. **열거형의 IL을 직접 확인하라.** `public enum BorderSide : byte { Left = 1, Right, Top = 10, Bottom }`을 컴파일하고 ILSpy나 `ildasm`으로 열어라. `extends System.Enum`, `sealed`, `value__` 필드의 타입, 그리고 `Right`와 `Bottom`에 실제로 배정된 값을 확인하라. 그다음 기저 타입을 `Int32`로 바꿔 컴파일하고 어떤 오류 번호가 나오는지 기록하라.

2. **심볼 치환을 관찰하라.** 클래스 라이브러리에 `enum LogLevel { Info, Warn, Error }`를 정의하고, 별도 콘솔 프로젝트에서 `LogLevel.Error`를 출력하는 코드를 작성해 빌드하라. 라이브러리 쪽 열거형을 `{ Info, Debug, Warn, Error }`로 바꿔 **라이브러리만** 다시 빌드하고 DLL을 교체한 뒤, 콘솔 프로그램을 재컴파일하지 않고 실행해 무엇이 출력되는지 확인하라.

3. **`TryParse`의 구멍을 재현하라.** `Enum.TryParse<ConsoleColor>("9999", out var c)`의 반환값과 `c`의 값을 출력하라. 그다음 `Enum.IsDefined(c)`를 덧붙여 검증이 어떻게 달라지는지 확인하고, 같은 실험을 `"+3"`, `" Red "`, `"red"` 세 입력에 대해 반복해 표로 정리하라.

4. **`ToString`의 3단계 규칙을 확인하라.** `[Flags] enum Actions { None=0, Read=1, Write=2, Delete=4 }`를 만들고 `(Actions)5`, `(Actions)8`, `(Actions)13`, `(Actions)0`을 각각 출력하라. 왜 그중 하나만 이름 조합이 나오고 나머지는 숫자가 나오는지 20.3절의 절차로 설명하라. 그다음 `All = Read | Write | Delete`를 추가하고 `(Actions)7`을 출력해 무엇이 달라지는지 보라.

5. **`HasFlag`의 할당을 측정하라.** `MemoryDiagnoser`를 켠 BenchmarkDotNet으로 (가) `v.HasFlag(F)`, (나) `(v & F) == F`, (다) 20.5절의 확장 메서드 `v.IsSet(F)` 세 가지를 비교하라(67.5절). 그다음 수신자를 `Enum` 타입 지역 변수에 담아 (가)를 다시 측정하고 할당 바이트가 어떻게 변하는지 확인하라.

6. **특성을 만들어 조회하라.** `[AttributeUsage(AttributeTargets.Method, AllowMultiple = true)] sealed class RoleAttribute : Attribute`를 정의해 `Name`을 위치 인수로, `Optional`을 명명 인수로 받게 하라. 메서드 하나에 `[Role]`을 두 번 붙이고 `GetCustomAttribute<RoleAttribute>()`를 호출해 어떤 예외가 나오는지 확인한 뒤, 복수형 API로 고쳐라. 마지막으로 `AllowMultiple`을 `false`로 바꿔 컴파일 오류 번호를 기록하라.

7. **특성 인스턴스가 매번 새로 생기는 것을 증명하라.** 특성 클래스의 생성자에 `Console.WriteLine`을 넣고, 같은 대상에 대해 `GetCustomAttribute`를 세 번 호출하라. 생성자가 몇 번 실행되는지, 그리고 세 반환값에 대한 `ReferenceEquals`와 `Equals`의 결과가 각각 무엇인지 확인하라. `IsDefined`로 바꾸면 생성자가 실행되는지도 확인하라.

8. **호출자 정보 특성의 치환을 IL에서 확인하라.** 20.11절의 `Log` 메서드를 만들어 호출하고, 릴리스 빌드의 IL에서 `ldstr`과 `ldc.i4` 명령으로 인수가 박혀 있는 것을 확인하라. 그다음 같은 메서드를 `MethodInfo.Invoke`로 호출해 매개변수가 무엇으로 채워지는지 비교하라. 마지막으로 `[CallerMemberName]`을 생성자·정적 생성자·프로퍼티 세터에서 각각 호출해 어떤 문자열이 나오는지 표로 정리하라.
