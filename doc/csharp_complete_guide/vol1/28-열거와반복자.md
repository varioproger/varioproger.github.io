# 28장. 열거와 반복자

> **이 장의 위치** — Part V의 세 번째 장이다. 11.5절에서 `foreach`가 어떤 코드로 낮춰지는지를 **소비자 쪽에서** 읽었고, 24.1절에서 `IEnumerable`/`IEnumerator` 한 쌍이 왜 존재하는지를 **컬렉션 쪽에서** 봤다. 이 장은 그 반대편, 곧 **시퀀스를 만드는 쪽**을 끝까지 판다. `yield return` 한 줄이 어떤 클래스로 부풀어 오르는지, 그 클래스의 `MoveNext()` 안에 무엇이 들어 있는지, 그리고 그 구조 때문에 `finally`가 언제 돌고 인자 검증이 언제 터지는지를 다룬다. 다음 두 장(LINQ)의 지반이 되는 장이다.
>
> **선수 지식** — 11장(문과 제어 흐름, 특히 11.5절), 18장(인터페이스), 23장(제네릭), 24장(컬렉션), 26장(델리게이트와 람다)
>
> **이 장에서 다루지 않는 것** — `Where`·`Select` 같은 LINQ 연산자 자체는 29장과 30장에서, 식 트리와 `IQueryable`은 31장에서, `async`/`await`가 만드는 상태 기계의 세부는 47장에서, `IDisposable` 구현 계약과 `await using`은 33장에서, 예외 설계 원칙은 32장에서 다룬다. `foreach`의 낮춤 경로별 IL 비교는 11.5절에 이미 있으므로 반복하지 않는다.

## 28.1 열거의 의미론 — 열거자 패턴의 덕 타이핑

### 두 가지 물건을 구별하는 것에서 시작한다

이 장 전체가 두 개념의 구별 위에 서 있다. 헷갈리면 그 뒤가 전부 흐려진다.

**열거자(enumerator)** 는 값의 시퀀스 위를 훑는 **읽기 전용·전방 전용 커서**다. 상태를 가진다. 지금 어디에 있는지를 기억하고, 요청받으면 한 칸 전진한다.

**열거 가능 객체(enumerable object)** 는 시퀀스의 **논리적 표현**이다. 그 자체는 커서가 아니라, **자기 위를 지나갈 커서를 만들어 내는 물건**이다.

책과 책갈피를 떠올리면 정확하다. 책 한 권에 책갈피는 여러 개 꽂을 수 있다. 책갈피를 다음 장으로 옮겨도 책은 바뀌지 않고 다른 책갈피도 영향을 받지 않는다. 바뀌는 것은 그 책갈피의 위치뿐이다. `GetEnumerator()`는 "이 책에 새 책갈피를 하나, 맨 앞에 꽂아 달라"는 요청이다.

```text
 IEnumerable<T>  (책)                    IEnumerator<T>  (책갈피)
┌──────────────────────────┐            ┌────────────────────────┐
│  GetEnumerator()  ───────┼──── 생성 ──→│  MoveNext() : bool     │
│                          │            │  Current   : T         │
│  상태 없음 (보통)         │            │  상태 있음 (위치)       │
│  여러 번 호출 가능         │            │  한 방향, 한 번만       │
└──────────────────────────┘            └────────────────────────┘
        │                                          │
        └── 같은 책에 책갈피 여러 개 ────────────────┘
```

이 구별이 실무에서 드러나는 지점은 이렇다. `IEnumerable<T>`를 매개변수로 받은 메서드가 그것을 두 번 `foreach` 하면 **소스가 두 번 돈다**. `IEnumerator<T>`를 받은 메서드가 그것을 두 번 돌려 하면 **두 번째는 아무것도 안 나온다**. 같아 보이는 두 타입이 전혀 다른 계약이다.

### C#이 "열거자"로 인정하는 조건

C#은 다음 중 **하나라도** 만족하는 타입을 열거자로, 또 하나라도 만족하는 타입을 열거 가능 객체로 취급한다. 열거 가능 객체 쪽은 **검사가 이 순서대로** 진행된다.

| 대상 | 순서 | 조건 |
|---|---|---|
| 열거자 | — | `MoveNext`라는 이름의 public 무인수 메서드와 `Current` 프로퍼티를 가진다 |
| 열거자 | — | `System.Collections.Generic.IEnumerator<T>`를 구현한다 |
| 열거자 | — | `System.Collections.IEnumerator`를 구현한다 |
| 열거 가능 | 1 | 열거자를 반환하는 public 무인수 `GetEnumerator` 메서드를 가진다 |
| 열거 가능 | 2 | `System.Collections.Generic.IEnumerable<T>`를 구현한다 |
| 열거 가능 | 3 | `System.Collections.IEnumerable`을 구현한다 |
| 열거 가능 | 4 | 열거자를 반환하는 `GetEnumerator`라는 이름의 **확장 메서드**에 바인딩된다 ※C# 9 |

정리하면 **열거 패턴**은 인터페이스가 아니라 이런 **모양**이다.

```csharp
class Enumerator      // 보통은 IEnumerator나 IEnumerator<T>를 구현한다
{
    public IteratorVariableType Current { get {...} }
    public bool MoveNext() {...}
}

class Enumerable      // 보통은 IEnumerable이나 IEnumerable<T>를 구현한다
{
    public Enumerator GetEnumerator() {...}
}
```

"보통은 구현한다"이지 "반드시 구현해야 한다"가 아니다. 컴파일러가 확인하는 것은 계약(인터페이스)이 아니라 **멤버의 존재**다. 이 규칙을 **덕 타이핑**(duck typing)이라고 부른다.

`foreach`가 이 순서로 후보를 고르는 과정, 배열·문자열의 특수 경로, `Dispose` 호출이 삽입되는 조건은 11.5절에서 IL까지 내려가서 다뤘다. 여기서는 **생산자 쪽에서 알아야 할 결론**만 붙잡는다.

- 열거자 타입은 무엇이든 될 수 있다. 구조체여도, `ref struct`여도 된다.
- `Current`의 타입도 무엇이든 될 수 있다. `ref T`를 반환해도 된다.
- 인터페이스를 구현하면 LINQ와 호환되는 대신, 인터페이스로 받는 순간 박싱과 가상 호출이 붙는다(18.6절).

고수준으로 쓴 순회는 이렇다.

```csharp
foreach (char c in "beer")
    Console.WriteLine (c);
```

같은 일을 저수준으로 쓰면 이렇다.

```csharp
using (var enumerator = "beer".GetEnumerator())
    while (enumerator.MoveNext())
    {
        var element = enumerator.Current;
        Console.WriteLine (element);
    }
```

열거자가 `IDisposable`을 구현하면 `foreach`는 `using` 문의 역할까지 겸해서 열거자를 암묵적으로 해제한다. 이 한 줄이 28.5절 전체의 씨앗이다.

> **📌 왜 인터페이스로 못 박지 않았나**
>
> C# 1.0 설계자들이 `foreach`를 인터페이스가 아니라 모양에 묶은 데는 두 가지 이유가 있었다. 첫째는 성능이다. 열거자를 구조체로 만들면 힙 할당이 사라지는데, 인터페이스로만 받는다면 그 구조체가 매번 박싱되어 이득이 통째로 날아간다. 둘째는 인터페이스로 표현할 수 없는 타입이다. `Span<T>`의 열거자는 `ref struct`이고, `ref struct`는 오랫동안 인터페이스를 구현할 수 없었다. 인터페이스 기반 규칙만 있었다면 `Span<T>`에는 `foreach`를 쓸 수 없었을 것이다.
>
> 2000년에 내린 판단이 2018년의 `Span<T>`를 가능하게 만들었다. 언어 설계에서 유연성을 남겨 두는 것의 값어치를 보여 주는 사례로 자주 인용된다.

### 확장 메서드 `GetEnumerator` ※C# 9

C# 9부터는 `GetEnumerator`가 **확장 메서드**여도 `foreach`가 성립한다. 내가 소스를 고칠 수 없는 남의 타입에 열거 능력을 나중에 붙일 수 있다는 뜻이다.

```csharp
using System.Collections.Generic;

public static class RangeExtensions
{
    public static IEnumerator<int> GetEnumerator (this System.Range r)
    {
        for (int i = r.Start.Value; i < r.End.Value; i++)
            yield return i;
    }
}

// 사용
foreach (int i in 1..5)          // 1 2 3 4
    System.Console.Write (i + " ");
```

`System.Range`는 `GetEnumerator`라는 인스턴스 메서드를 갖고 있지 않고 `IEnumerable`도 구현하지 않는다. 그런데도 위 코드가 컴파일된다. 확장 메서드가 4순위 후보로 발견되기 때문이다.

> **⚠️ 확장 메서드 `GetEnumerator`는 인스턴스 메서드를 이기지 못한다**
>
> 확장 메서드는 **맨 마지막** 후보다. 타입에 이미 접근 가능한 `GetEnumerator()` 인스턴스 메서드가 있으면 확장 메서드는 절대 선택되지 않는다. "우리 팀 타입의 열거 방식을 확장 메서드로 바꿔 치자"는 시도가 조용히 실패하는 이유가 이것이고, 그 실패는 컴파일 오류가 아니라 **동작 차이**로만 드러나므로 발견이 늦다.
>
> 확장 메서드가 다른 `using` 네임스페이스 아래에 있으면 파일마다 `foreach`의 의미가 달라질 수도 있다. 같은 타입을 어떤 파일에서는 확장 메서드로, 어떤 파일에서는 컴파일 오류로 만들 수 있다는 뜻이다. 라이브러리 공개 API에 이 기법을 쓸 때는 이 위험을 감수한다는 점을 알고 써야 한다.

### 열거 계약 — 지켜야 할 다섯 가지

인터페이스를 구현하든 모양만 맞추든, 열거자를 직접 만들 때 지켜야 할 규약이 있다. `foreach`와 LINQ 연산자 전체가 이 규약을 전제로 짜여 있다.

| 규약 | 내용 | 어기면 |
|---|---|---|
| 시작 위치는 첫 요소 **이전** | 첫 값을 얻으려면 `MoveNext()`를 먼저 불러야 한다 | 첫 요소가 유실되거나 빈 시퀀스를 표현할 수 없다 |
| `MoveNext()`가 `false`를 반환한 뒤에는 계속 `false` | 되살아나면 안 된다 | LINQ 연산자가 무한 루프에 빠질 수 있다 |
| 시작 전·종료 후의 `Current`는 **정의되지 않음** | 예외를 던져도, 쓰레기 값을 돌려줘도 규약 위반이 아니다 | 소비자가 `Current`를 방어적으로 읽으면 안 된다 |
| 전방 전용 | 뒤로 갈 수단이 없다 | — |
| 정리가 필요하면 `IDisposable` | `foreach`가 `finally`에서 불러 준다 | 리소스 누수 |

`Reset()`은 비제네릭 `IEnumerator`에만 있고, 사실상 죽은 멤버다(24.1절). 구현체가 `NotSupportedException`을 던져도 규약 위반이 아니며, 컴파일러가 만들어 주는 반복자도 정확히 그렇게 한다(28.4절).

> **⚠️ 종료 후 `Current`의 동작은 타입마다 다르다**
>
> ```csharp
> var list = new System.Collections.Generic.List<int> { 1, 2 };
> var e = list.GetEnumerator();
> while (e.MoveNext()) { }
> System.Console.WriteLine (e.Current);   // 0 — 예외 없음
> ```
>
> `List<T>.Enumerator.Current`(제네릭 쪽)는 예외를 던지지 않고 `default(int)`를 돌려주지만, 같은 열거자를 `IEnumerator`로 캐스트해서 비제네릭 `Current`를 읽으면 `InvalidOperationException`이 난다. 컴파일러가 생성하는 반복자(28.4절)는 어느 쪽이든 예외를 던지지 않고 필드에 남아 있는 값을 그대로 돌려준다.
>
> 어느 동작에도 의존하지 마라. **"`MoveNext()`가 `true`를 돌려준 직후에만 `Current`를 읽는다"** 가 유일하게 안전한 사용법이다.

> **💡 열거자를 손으로 구현할 일은 거의 없다**
>
> `IEnumerator<T>`를 직접 구현하는 코드는 세 종류뿐이다. (1) 성능을 위해 구조체 열거자를 제공하는 컬렉션 타입, (2) `ref struct` 열거자가 필요한 스팬 계열 타입, (3) 반복자 문법으로 표현할 수 없는 특수한 상태 전이가 필요한 경우. 나머지는 전부 `yield return`이 정답이다(28.3절부터).
>
> 손으로 쓰면 위 규약 다섯 개를 전부 스스로 지켜야 하고, `finally` 처리와 `Dispose` 재진입까지 직접 맞춰야 한다. 컴파일러는 그걸 틀리지 않는다.

## 28.2 컬렉션 초기화자와 컬렉션 식

### 문법 — 한 걸음에 만들고 채우기

**컬렉션 초기화자**(collection initializer)를 쓰면 열거 가능 객체를 만들면서 동시에 채울 수 있다.

```csharp
using System.Collections.Generic;

var list = new List<int> {1, 2, 3};
```

C# 12부터는 **컬렉션 식**(collection expression)으로 더 줄일 수 있다. 대괄호를 쓴다.

```csharp
using System.Collections.Generic;

List<int> list = [1, 2, 3];
```

컬렉션 식은 **대상 타입 지정**(target-typed)된다. `[1,2,3]`의 타입은 대입되는 쪽의 타입에 따라 결정된다.

```csharp
int[] array = [1, 2, 3];
System.Span<int> span = [1, 2, 3];
```

대상 타입이 결정되는 자리라면 메서드 인수 위치에서도 타입을 생략할 수 있다.

```csharp
Foo ([1, 2, 3]);

void Foo (List<int> numbers) { /* ... */ }
```

컬렉션 식의 대상 타입 표, 스프레드 연산자 `..`의 문법, `CollectionBuilderAttribute`는 24.14절에서 다뤘고 배열 관점의 초기화는 9.2절에 있다. 이 절은 24.14절이 28.2절로 넘긴 것 — **`Add` 메서드 기반 번역 규칙과 그 결과** — 을 마저 판다.

### 컴파일 결과 — 초기화자는 `Add` 호출로 번역된다

컴파일러는 컬렉션 초기화자를 다음으로 바꾼다.

```csharp
using System.Collections.Generic;

List<int> list = new List<int>();
list.Add (1);
list.Add (2);
list.Add (3);
```

문법 설탕 이상도 이하도 아니다. 그래서 다음 두 조건이 요구된다.

1. 대상 타입이 **`System.Collections.IEnumerable`을 구현**할 것
2. 호출에 맞는 매개변수 개수를 가진 **`Add` 메서드**가 있을 것

두 조건 중 두 번째만이 실제로 코드를 만들어 낸다. 첫 번째는 **순수한 자격 검사**다.

> **📌 컴파일러는 `IEnumerable` 구현을 쳐다보기만 한다**
>
> 컬렉션 초기화자를 컴파일할 때 컴파일러는 `IEnumerable`의 **구현을 절대 호출하지 않는다.** 그 인터페이스가 붙어 있는지만 확인한다. 언어 설계자들이 이 조건을 넣은 이유는, `Add`라는 이름의 메서드를 가진 타입 전부(예: `Add(int, int)`를 가진 계산기 클래스)가 초기화자 문법의 대상이 되는 것을 막기 위해서였다.
>
> 부수 효과로 재미있는 기법이 하나 생긴다. 테스트 프로젝트에서 `Add` 메서드만 제대로 만들어 두고 `IEnumerable`은 `NotImplementedException`을 던지도록 구현한 타입을 만들면, 초기화자 문법으로 테스트 데이터를 조립하면서도 그 타입을 실수로 열거하는 코드를 즉시 잡아낼 수 있다. 권장할 만한 관행이라기보다는, 이 검사가 얼마나 형식적인지를 보여 주는 증거로 알아 둘 만하다.

`Add`는 오버로드 해결의 일반 규칙을 그대로 탄다. 인수 개수도 자유롭고, 여러 개의 오버로드가 있으면 각 초기화자 요소마다 따로 해결된다.

```csharp
using System.Collections;
using System.Collections.Generic;

class Bag : IEnumerable
{
    readonly List<string> items = new();

    public void Add (string s)          => items.Add (s);
    public void Add (int n)             => items.Add ("#" + n);
    public void Add (string s, int n)   => items.Add (s + n);

    public IEnumerator GetEnumerator() => items.GetEnumerator();
}

var bag = new Bag { "a", 7, { "b", 2 } };
// items: "a", "#7", "b2"
```

중괄호로 감싼 `{ "b", 2 }`가 인수 두 개짜리 `Add` 호출로 번역된다. 딕셔너리 초기화자가 동작하는 원리가 정확히 이것이다.

### 딕셔너리를 채우는 두 가지 문법

```csharp
using System.Collections.Generic;

var dict = new Dictionary<int, string>()
{
    { 5, "five" },
    { 10, "ten" }
};
```

또는 더 짧게 이렇게 쓸 수 있다.

```csharp
using System.Collections.Generic;

var dict = new Dictionary<int, string>()
{
    [3] = "three",
    [10] = "ten"
};
```

두 번째 형태는 딕셔너리 전용이 아니다. **인덱서를 가진 모든 타입**에 쓸 수 있다. 그리고 두 문법은 **같은 코드로 번역되지 않는다.**

| 문법 | 번역 결과 | 키가 중복되면 |
|---|---|---|
| `{ k, v }` | `dict.Add(k, v)` | `ArgumentException` |
| `[k] = v` | `dict[k] = v` | 조용히 덮어쓴다 |

> **⚠️ `{ }` 와 `[ ] =` 의 중복 키 동작이 다르다**
>
> ```csharp
> // ArgumentException — 같은 키를 가진 항목이 이미 있다는 메시지
> var a = new Dictionary<string,int> { { "x", 1 }, { "x", 2 } };
>
> // 예외 없음 — x는 2가 된다
> var b = new Dictionary<string,int> { ["x"] = 1, ["x"] = 2 };
> ```
>
> 상수 리터럴이라면 눈에 보이지만, 키가 변수거나 계산식이면 보이지 않는다. 설정 파일을 코드로 옮겨 적는 코드에서 실제로 자주 터진다. **중복이 실수라면 `{ }` 형태를 써서 즉시 터지게 하고**, 덮어쓰기가 의도라면 `[ ] =`를 써서 의도를 드러내라.

> **📌 확장 메서드 `Add` ※C# 6**
>
> C# 6부터는 `Add`가 확장 메서드여도 컬렉션 초기화자가 성립한다. `IEnumerable` 구현 조건은 그대로 요구된다. 내가 못 고치는 타입에 초기화자 문법을 붙일 수 있다는 점에서 `GetEnumerator` 확장 메서드(28.1절)와 짝을 이룬다.

### 컬렉션 식은 초기화자와 같은 코드가 아니다

컬렉션 식 `[1, 2, 3]`이 `List<T>`를 대상으로 하면 결과는 초기화자와 같다. `new List<int>()` 뒤에 `Add` 세 번이다. 그러나 대상이 달라지면 컴파일러가 만들어 내는 것도 달라진다.

| 대상 타입 | 컴파일러가 만드는 것 | 비고 |
|---|---|---|
| `T[]` | 크기를 아는 배열 생성 + 요소 대입 | `[]`는 `Array.Empty<T>()`가 될 수 있다 |
| `Span<T>` / `ReadOnlySpan<T>` | 스택 할당 또는 정적 데이터 참조 | 힙 할당이 없을 수 있다 |
| `List<T>` 등 `IEnumerable` + `Add` | `new` + `Add` 반복 | 초기화자와 동일 |
| `IEnumerable<T>` 등 읽기 전용 인터페이스 | 컴파일러가 적당한 구현을 고른다 | 구체 타입은 명세되지 않는다 |
| `[CollectionBuilder]`가 붙은 타입 | 지정된 빌더 팩토리 호출 | `ImmutableArray<T>` 등 |

**읽기 전용 컬렉션은 컬렉션 초기화자로 만들 수 없었지만 컬렉션 식으로는 만들 수 있다.** `Add`가 없어도 되기 때문이다. 이것이 컬렉션 식이 단순한 축약 문법이 아닌 이유다.

```csharp
using System.Collections.Generic;
using System.Collections.Immutable;

ImmutableArray<int> frozen = [1, 2, 3];      // Add가 없는데도 된다
IReadOnlyList<int> ro       = [1, 2, 3];
```

> **⚠️ 컬렉션 식의 대상 타입이 인터페이스면 구체 타입을 가정하지 마라**
>
> ```csharp
> IEnumerable<int> xs = [1, 2, 3];
> var asList = (List<int>) xs;        // 던질 수 있다 — 보장된 동작이 아니다
> ```
>
> `IEnumerable<T>`나 `IReadOnlyList<T>`를 대상으로 한 컬렉션 식이 어떤 구체 타입을 만드는지는 **명세되지 않았고 컴파일러 버전에 따라 바뀔 수 있다.** 캐스트해서 쓰는 코드는 컴파일러를 올리는 순간 깨진다. 구체 타입이 필요하면 그 타입을 대상 타입으로 써라.

### 스프레드와 반복자의 관계

스프레드 요소 `..source`는 `source`를 **열거해서** 펼쳐 넣는다. `source`가 반복자 메서드가 돌려준 지연 시퀀스라면, **스프레드가 놓인 그 자리에서 반복자가 실제로 돈다.**

```csharp
using System.Collections.Generic;

IEnumerable<int> Lazy()
{
    System.Console.WriteLine ("반복자 실행!");
    yield return 1;
    yield return 2;
}

var seq = Lazy();                 // 아무것도 출력되지 않는다
int[] all = [0, ..seq, 3];        // 여기서 "반복자 실행!" 출력
```

지연 실행이 여기서 종료되는 것이다. 컬렉션 식과 `ToList()`는 이 점에서 같은 부류다 — **즉시 평가 지점**이다(29.11절, 30.8절).

> **💡 컬렉션 식은 "여기서 물질화한다"는 선언으로 읽어라**
>
> 파이프라인 중간에 `[..query]`가 등장하면 그 지점에서 시퀀스가 메모리에 통째로 눕는다는 뜻이다. 무한 시퀀스(28.3절의 `Fibonacci` 같은)에 대고 쓰면 프로그램이 멈추지 않는다. 대괄호가 짧고 가벼워 보여서 이 비용이 눈에 잘 안 띈다.

## 28.3 `yield return` / `yield break`

### 소비자에서 생산자로

`foreach`는 열거자의 **소비자**다. **반복자**(iterator)는 열거자의 **생산자**다. 여기서부터가 이 장의 본론이다.

피보나치 수열을 만드는 반복자를 보자.

```csharp
using System;
using System.Collections.Generic;

foreach (int fib in Fibs(6))
    Console.Write (fib + "  ");

IEnumerable<int> Fibs (int fibCount)
{
    for (int i = 0, prevFib = 1, curFib = 1; i < fibCount; i++)
    {
        yield return prevFib;
        int newFib = prevFib + curFib;
        prevFib = curFib;
        curFib = newFib;
    }
}

// 출력: 1  1  2  3  5  8
```

`return` 문이 "네가 요청한 반환값이다"라고 말한다면, `yield return` 문은 **"네가 이 열거자에서 요청한 다음 요소다"** 라고 말한다. 모든 `yield` 문에서 제어는 호출자에게 돌아가지만, **호출된 쪽의 상태는 유지된다.** 그래서 호출자가 다음 요소를 요구하는 순간 메서드가 그 자리에서 이어 실행된다. 이 상태의 수명은 열거자에 묶인다. 호출자가 열거를 끝내면 상태도 놓아 줄 수 있다.

> **📌 반복자 메서드를 호출해도 코드는 한 줄도 안 돈다**
>
> 컴파일러는 반복자 메서드를 `IEnumerable<T>`와/또는 `IEnumerator<T>`를 구현하는 private 클래스로 변환한다. 반복자 블록 안의 논리는 "뒤집혀서" 그 컴파일러 생성 클래스의 `MoveNext` 메서드와 `Current` 프로퍼티에 접합된다.
>
> 그래서 반복자 메서드를 호출하는 것은 **그 컴파일러 생성 클래스를 인스턴스화하는 일이 전부**다. 당신의 코드는 한 줄도 실행되지 않는다. 실제 실행은 결과 시퀀스를 열거하기 시작할 때 — 보통은 `foreach`로 — 비로소 시작된다.
>
> 이 문장이 28.5절과 28.6절의 모든 함정의 원인이다.

### 반복자가 될 수 있는 것과 반환 타입

반복자는 **하나 이상의 `yield` 문을 담은 메서드, 프로퍼티, 인덱서**다. 반환 타입은 다음 넷 중 하나여야 한다. 아니면 컴파일 오류다.

```csharp
// 열거 가능 인터페이스
System.Collections.IEnumerable
System.Collections.Generic.IEnumerable<T>

// 열거자 인터페이스
System.Collections.IEnumerator
System.Collections.Generic.IEnumerator<T>
```

반환 타입이 비제네릭이면 **yield 타입**은 `object`이고, 제네릭이면 인터페이스에 준 타입 인수다. `IEnumerator<string>`을 반환하는 메서드의 yield 타입은 `string`이다.

반환 타입이 열거 **가능** 인터페이스냐 열거자 인터페이스냐에 따라 의미론이 달라진다. 그 차이는 28.4절에서 상태 기계를 뜯으며 확인한다.

반복자는 **지역 함수**여도 된다(26.12절). 이 사실이 28.6절의 해법이 된다.

`yield` 문은 여러 개 놓을 수 있다.

```csharp
using System.Collections.Generic;

foreach (string s in Foo())
    System.Console.WriteLine (s);

IEnumerable<string> Foo()
{
    yield return "One";
    yield return "Two";
    yield return "Three";
}

// One, Two, Three
```

### `yield break`

반복자 블록 안에서 `return` 문은 **불법**이다. 대신 `yield break`로 "더 이상 요소 없이 일찍 끝낸다"를 표현한다.

```csharp
using System.Collections.Generic;

IEnumerable<string> Foo (bool breakEarly)
{
    yield return "One";
    yield return "Two";

    if (breakEarly)
        yield break;

    yield return "Three";
}
```

`yield break`는 시퀀스의 끝을 알린다. 반복자 블록의 끝에 도달하는 것과 같은 효과다.

> **⚠️ `return`을 쓰면 CS1622다 — 그런데 눈에 잘 안 띈다**
>
> ```csharp
> IEnumerable<int> Bad (int[] xs)
> {
>     if (xs == null) return null;     // CS1622: 반복자에서 값을 반환할 수 없다
>     foreach (var x in xs) yield return x;
> }
> ```
>
> "null이면 null을 돌려주자"는 흔한 방어 코드가 반복자에서는 아예 컴파일되지 않는다. 메서드 본문 어딘가에 `yield`가 **하나라도** 있으면 그 메서드 전체가 반복자가 되기 때문이다. 이 오류가 나면 보통은 28.6절의 래퍼 메서드 패턴으로 가야 한다는 신호다.
>
> 참고로 반복자가 `null`을 반환하는 것 자체가 안티패턴이다. 빈 시퀀스는 `null`이 아니라 요소 0개의 시퀀스로 표현한다(`Enumerable.Empty<T>()` — 30.12절).

### 반복자와 `try`/`catch`/`finally`

`yield return` 문은 **`catch` 절이 있는 `try` 블록 안에 놓을 수 없다.**

```csharp
using System.Collections.Generic;

IEnumerable<string> Foo()
{
    try { yield return "One"; }        // 불법
    catch { /* ... */ }
}
```

`catch` 블록 안에도, `finally` 블록 안에도 `yield return`을 놓을 수 없다. 이유는 컴파일러가 반복자를 `MoveNext`·`Current`·`Dispose` 멤버를 가진 평범한 클래스로 번역해야 하는데, 예외 처리 블록까지 번역하면 복잡도가 지나치게 커지기 때문이다.

`finally`만 있는 `try` 블록 안에서는 `yield`할 수 있다.

```csharp
using System.Collections.Generic;

IEnumerable<string> Foo()
{
    try { yield return "One"; }        // OK
    finally { /* ... */ }
}
```

`finally` 블록의 코드는 **소비하는 열거자가 시퀀스의 끝에 도달하거나 해제될 때** 실행된다. 이 규칙 하나가 28.5절 전체다.

### 반복자에 걸린 제약 전체 목록

| 제약 | 컴파일러 오류 | 설명 |
|---|---|---|
| `return` 문 금지 | CS1622 | `yield break`를 쓴다 |
| 반환 타입은 네 인터페이스 중 하나 | CS1624 | `List<T>`나 `T[]`를 반환할 수 없다 |
| `ref` / `out` / `in` 매개변수 금지 | CS1623 | 상태 기계 필드로 승격할 수 없기 때문 |
| 람다·익명 메서드 본문에서 `yield` 금지 | CS1621 | 지역 함수에서는 가능하다 |
| `catch` 절이 있는 `try`에서 `yield return` 금지 | CS1626 | — |
| `catch` 블록에서 `yield return` 금지 | CS1631 | — |
| `finally` 블록에서 `yield` 금지 | CS1625 | `yield break`도 안 된다 |
| `unsafe` 문맥 금지 | CS1629 | ※C# 13에서 완화되었다 |

> **📌 ※C# 13 — 반복자 안의 `ref` 지역 변수와 `unsafe`**
>
> C# 13부터 반복자 메서드와 async 메서드 안에서 `ref` 지역 변수, `ref struct` 지역 변수, `unsafe` 문맥을 쓸 수 있게 되었다. 다만 그 변수들이 `yield return`이나 `await` 경계를 **넘어 살아남을 수는 없다.** 상태 기계 필드로 승격할 수 없는 것들이기 때문이다. `yield` 사이사이의 순수한 계산에는 쓸 수 있고 경계를 가로지르면 여전히 오류라는 뜻이다.
>
> `ref`/`out`/`in` **매개변수** 금지는 C# 13에서도 그대로다. 매개변수는 반드시 상태 기계 필드로 복사되어야 하기 때문이다.

> **⚠️ 반복자 안에서 예외를 잡으려면 구조를 바꿔야 한다**
>
> `yield return`을 감싸는 `try/catch`를 쓸 수 없으므로, "요소를 만들다 실패하면 로그를 남기고 계속" 같은 패턴을 반복자 안에서 직접 쓸 수 없다. 우회 방법은 하나뿐이다 — **`yield` 없는 별도 메서드로 잡아서 결과를 돌려받고, 그 결과를 `yield return` 한다.**
>
> ```csharp
> using System.Collections.Generic;
>
> IEnumerable<Record> Parse (IEnumerable<string> lines)
> {
>     foreach (var line in lines)
>     {
>         if (TryParseOne (line, out var rec))     // try/catch는 여기 안에
>             yield return rec;
>     }
> }
> ```
>
> 시퀀스를 만드는 코드에서 예외를 어떻게 다뤄야 하는지의 설계 원칙은 32장에서 다룬다.

## 28.4 반복자 의미론과 컴파일러가 만드는 상태 기계 — 실물 IL 읽기

이 절이 이 장의 심장이다. `yield return` 한 줄이 어떤 물건으로 바뀌는지를 실물 수준에서 본다.

### 재료 — 다섯 가지 요소를 담은 반복자

일부러 다음 다섯 가지를 전부 담은 메서드로 시작한다.

- 매개변수 하나
- `yield return`을 가로질러 **살아남아야 하는** 지역 변수
- `yield return`을 가로질러 **살아남지 않아도 되는** 지역 변수
- `yield return` 두 개
- `finally` 블록

```csharp
using System;
using System.Collections.Generic;

public static IEnumerable<int> GenerateIntegers (int count)
{
    try
    {
        for (int i = 0; i < count; i++)
        {
            Console.WriteLine ("Yielding {0}", i);
            yield return i;

            int doubled = i * 2;
            Console.WriteLine ("Yielding {0}", doubled);
            yield return doubled;
        }
    }
    finally
    {
        Console.WriteLine ("In finally block");
    }
}
```

`count`가 5면 `0, 0, 1, 2, 2, 4, 3, 6, 4, 8`을 내놓는다.

### 1단계 — 원래 메서드는 스텁만 남는다

컴파일러는 원래 시그니처를 가진 메서드를 그대로 남기되, 그 본문을 **상태 기계 객체를 하나 만들어 돌려주는 것**으로 갈아 치운다. IL로 보면 이렇다.


읽을 것은 네 줄이다.

- `ldc.i4.s -2` — 초기 상태값 `-2`를 생성자에 넘긴다. 이 값의 의미는 곧 본다.
- `newobj ... '<GenerateIntegers>d__0'::.ctor` — 상태 기계 객체를 **힙에 하나 만든다**. 반복자 호출당 할당 1회는 여기서 발생한다.
- `stfld ... '<>3__count'` — 매개변수를 필드로 **복사한다**.
- `ret` — 끝. **원본 코드는 한 줄도 실행되지 않았다.**

`IteratorStateMachineAttribute`는 진짜 특성이다. 디버거와 진단 도구가 "이 메서드의 진짜 몸통은 저 타입 안에 있다"를 알아내는 데 쓴다.

> **📌 생성 타입 이름의 규칙**
>
> `<GenerateIntegers>d__0`처럼 꺾쇠와 `d__`가 들어간 이름은 C# 식별자로 쓸 수 없는 문자를 포함한다. 컴파일러가 일부러 그렇게 짓는다. **사용자 코드가 절대 그 이름을 참조하지 못하게 하기 위해서**이고, 동시에 사용자가 만든 타입과 이름이 충돌하지 않게 하기 위해서다. `d`는 반복자, `<...>c__DisplayClass...`는 클로저(26.10절), `<...>d__`에 `AsyncStateMachine` 특성이 붙으면 async 메서드(47.7절)다.
>
> 이 이름들은 **구현 세부사항이며 컴파일러 버전에 따라 바뀐다.** 리플렉션으로 이름을 파싱하는 코드를 쓰지 마라.

### 2단계 — 생성된 클래스의 뼈대

만들어지는 중첩 private 클래스의 구조는 이렇다. 컴파일러가 붙인 이름을 읽기 좋게 바꾸면 다음과 같다.

```csharp
private sealed class GeneratedClass
    : IEnumerable<int>, IEnumerable,
      IEnumerator<int>, IEnumerator,
      IDisposable
{
    // ── 필드 ──────────────────────────────────
    private int state;                 // <>1__state
    private int current;               // <>2__current
    private int initialThreadId;       // <>l__initialThreadId
    public  int count;                 // 활성 인스턴스가 쓰는 매개변수 복사본
    private int seedCount;             // <>3__count : 원본 인자 보관용
    private int i;                     // <i>5__1 : 승격된 지역 변수

    public GeneratedClass (int state)
    {
        this.state = state;
        this.initialThreadId = Environment.CurrentManagedThreadId;
    }

    public bool MoveNext() { /* ... 본문 전체가 여기 있다 ... */ }

    public IEnumerator<int> GetEnumerator() { /* ... 스레드 ID 트릭 ... */ }

    public int Current => current;
    object IEnumerator.Current => current;

    public void Dispose() { /* 필요한 finally를 실행한다 */ }

    public void Reset() => throw new NotSupportedException();

    private void Finally1() { Console.WriteLine ("In finally block"); }

    IEnumerator IEnumerable.GetEnumerator() => GetEnumerator();
}
```

핵심 관찰 네 가지.

1. **하나의 클래스가 `IEnumerable<int>`와 `IEnumerator<int>`를 동시에 구현한다.** 정상적인 손코딩에서는 거의 볼 수 없는 형태다. 이유는 곧 나온다.
2. **매개변수마다 필드가 두 개다.** 원본 보관용(`<>3__count`)과 현재 인스턴스 작업용(`count`)이다.
3. **`yield` 경계를 넘어 살아남는 지역 변수만 필드로 승격된다.** `i`는 필드가 되었지만 `doubled`는 없다.
4. **`finally` 블록의 몸통이 별도 메서드(`Finally1`)로 뽑혀 나갔다.** `MoveNext`와 `Dispose` 양쪽에서 불러야 하기 때문이다.

| 필드 | 컴파일러가 붙이는 이름 | 역할 |
|---|---|---|
| 상태 | `<>1__state` | 지금 메서드의 어느 지점에서 멈춰 있는가 |
| 현재 값 | `<>2__current` | `Current`가 돌려줄 마지막 yield 값 |
| 스레드 ID | `<>l__initialThreadId` | 최초로 만들어진 스레드 |
| 매개변수 원본 | `<>3__파라미터명` | 새 열거자를 만들 때 복사해 갈 씨앗 |
| 매개변수 작업본 | `파라미터명` | `MoveNext`가 실제로 읽는 값 |
| 승격된 지역 변수 | `<지역변수명>5__N` | yield 경계를 살아남는 지역 변수 |

### 3단계 — 상태값의 의미

상태 필드가 갖는 값은 컴파일러 구현 세부사항이지만, Roslyn이 쓰는 값들은 다음과 같다.

| 값 | 의미 |
|---|---|
| `-3`(이하) | `MoveNext()`가 지금 `try` 영역 안에서 실행 중이다 |
| `-2` | `GetEnumerator()`가 아직 호출되지 않았다 |
| `-1` | 완료됨(정상이든 예외든) |
| `0` | `GetEnumerator()`는 호출됐지만 `MoveNext()`는 아직 — 메서드 시작 지점 |
| `1` | 첫 번째 `yield return` 지점 |
| `2` | 두 번째 `yield return` 지점 |

주목할 것 두 가지.

**첫째, 상태 번호는 `yield return`마다 하나씩만 붙는다.** "`doubled`에 값을 대입한 직후" 같은 지점에는 상태가 없다. 거기서 재개할 일이 없기 때문이다. 재개 지점은 **일시 정지한 지점뿐**이다.

**둘째, `try` 영역 안에서 실행 중임을 나타내는 음수 상태가 따로 있다.** `Dispose()`가 "어느 `finally`를 돌려야 하는가"를 판정하는 근거가 이 값이다. `finally`가 중첩될수록 이 계산이 복잡해진다.

> **⚠️ `IEnumerator<T>`를 반환하는 반복자는 초기 상태가 다르다**
>
> 반복자의 반환 타입이 `IEnumerator<T>`나 `IEnumerator`면, 생성된 상태 기계는 `IEnumerable<T>`를 **구현하지 않고** 초기 상태가 `-2`가 아니라 `0`으로 시작한다. 스텁 메서드가 곧바로 "열거를 시작할 준비가 된 커서"를 돌려주는 것이다.
>
> 실무적 결과는 이렇다. **`IEnumerator<T>`를 반환하는 반복자의 결과는 딱 한 번만 열거할 수 있다.** `foreach`에 직접 넣을 수도 없다(`foreach`는 열거 가능 객체를 요구한다 — 11.5절). 특별한 이유가 없으면 `IEnumerable<T>`를 반환해라.

### 4단계 — `GetEnumerator()`의 스레드 ID 트릭

거의 모든 경우에 상태 기계는 **만들어진 스레드에서 딱 한 번만** 쓰인다. 컴파일러는 그 경우를 최적화한다.

```csharp
public IEnumerator<int> GetEnumerator()
{
    if (state == -2 && initialThreadId == Environment.CurrentManagedThreadId)
    {
        state = 0;              // 커서로 승격
        return this;            // 새 객체를 만들지 않는다
    }

    var fresh = new GeneratedClass (0);
    fresh.count = this.seedCount;    // 원본 인자를 복사
    return fresh;
}
```

조건 두 개가 모두 참일 때만 `this`를 돌려준다.

- `state == -2` — 아직 아무도 이 인스턴스를 커서로 쓰지 않았다
- `initialThreadId == 현재 스레드` — 만들어진 그 스레드다

그래서 **반복자 호출 한 번 + `foreach` 한 번**이라는 압도적으로 흔한 경로에서는 **객체가 딱 하나만 할당된다.** 시퀀스 역할과 커서 역할을 같은 객체가 겸한다. 이것이 한 클래스가 `IEnumerable<int>`와 `IEnumerator<int>`를 동시에 구현하는 이유다.

`GetEnumerator()`가 두 번째로 불리거나 다른 스레드에서 불리면, 그때는 원본 인자를 복사한 **새 상태 기계**가 만들어진다. 그래서 같은 `IEnumerable<T>`를 두 번 `foreach` 하면 반복자가 처음부터 다시 돈다.

```csharp
var seq = GenerateIntegers (2);

foreach (var x in seq) { }     // 상태 기계 A (재사용된 원본 객체)
foreach (var x in seq) { }     // 상태 기계 B (새로 할당) — 처음부터 다시 실행
```

> **⚠️ 스레드 ID 트릭이 실패하면 할당이 두 배가 된다**
>
> 반복자를 만든 스레드와 다른 스레드에서 열거하면 상태 기계 객체가 **두 개** 만들어진다(원본 + 커서). `Task.Run` 안으로 `IEnumerable<T>`를 넘겨 열거하는 코드, `Parallel.ForEach`에 반복자 결과를 넘기는 코드가 여기 해당한다.
>
> 개당 수십 바이트라 대개는 무시할 만하지만, 초당 수십만 번 도는 경로에서는 프로파일러에 잡힌다. 이 최적화의 존재 자체를 몰라서 "왜 스레드를 넘겼더니 할당이 늘었지"라고 헤매는 경우가 있다.

### 5단계 — `MoveNext()`의 실제 구조

`MoveNext()`가 어려운 부분이다. 첫 호출에서는 메서드 코드를 처음부터 실행해야 하고, 이후 호출에서는 **적절한 지점으로 점프**해야 한다.

구조를 스케치하면 이렇다.

```csharp
public bool MoveNext()
{
    try
    {
        switch (state)
        {
            // 상태값으로 올바른 지점으로 점프하는 점프 테이블
            // 그 뒤로 원본 메서드 본문이 이어지고,
            // yield return마다 return true로 빠져나간다
        }
    }
    fault
    {
        Dispose();          // 예외가 났을 때만 도는 정리 경로
    }
}
```

`fault` 블록은 **IL의 구성 요소이며 C#에는 직접 대응하는 문법이 없다.** 예외가 발생했을 때 실행되지만 예외를 잡지는 않는 `finally`라고 보면 된다.

앞의 `GenerateIntegers`를 실제 형태에 가깝게 풀어 쓰면 다음과 같다.

```csharp
public bool MoveNext()
{
    try
    {
        switch (state)
        {
            case 0:  goto Start;
            case 1:  goto Resume1;
            case 2:  goto Resume2;
            default: return false;      // -1 (완료) 등
        }

    Start:
        state = -3;                     // "try 영역 안에서 실행 중"
        i = 0;
        goto LoopTest;

    LoopBody:
        Console.WriteLine ("Yielding {0}", i);
        current = i;
        state = 1;                      // 첫 yield 지점 표시
        return true;                    // ← 여기서 호출자에게 돌아간다

    Resume1:
        state = -3;
        {
            int doubled = i * 2;                       // 승격되지 않은 지역 변수
            Console.WriteLine ("Yielding {0}", doubled);
            current = doubled;
        }
        state = 2;
        return true;                    // ← 두 번째 yield

    Resume2:
        state = -3;
        i++;

    LoopTest:
        if (i < count) goto LoopBody;

        state = -1;                     // 정상 종료
        Finally1();                     // finally 블록 실행
        return false;
    }
    fault
    {
        Dispose();
    }
}
```

여섯 가지를 확인해라.

1. **점프 테이블이 맨 앞에 온다.** `switch`가 상태값을 보고 재개 지점으로 뛴다.
2. **`yield return`은 `return true`가 된다.** "일시 정지"의 정체는 그냥 리턴이다. 다만 리턴 직전에 상태 번호를 박아 놓는다.
3. **`try` 영역에 들어갈 때마다 상태를 `-3`으로 바꾼다.** `Dispose()`가 이걸 보고 `Finally1()`을 돌려야 하는지 판정한다.
4. **`doubled`는 필드가 아니라 진짜 지역 변수다.** `yield`를 가로질러 살아남을 필요가 없기 때문이다.
5. **정상 종료 경로에서 `Finally1()`을 직접 부른다.** `Dispose()`가 아니라.
6. **`fault` 블록은 예외 경로 전용이다.** 예외로 빠져나가면 `Dispose()`를 통해 `finally`가 돈다.

IL로 보면 점프 테이블은 이렇게 생겼다. 상태가 셋 이상이면 Roslyn은 `switch` 옵코드를 쓴다.

```il

{

  .maxstack  3

                int32 V_1)          // doubled — 필드가 아니라 지역 슬롯이다

  {
```

`.locals init`에 `V_1`이 잡혀 있는 것이 `doubled`가 필드로 승격되지 않았다는 증거다. `.try` 뒤에 `fault` 절이 오는 것은 C# 소스로는 만들 수 없는 형태다.

> **📌 지역 변수 승격 최적화가 깨지는 조건**
>
> `doubled`가 지역 변수로 남을 수 있는 이유는 "대입 → 사용 → yield" 순서이기 때문이다. yield 이후에 그 값을 다시 쓰지 않는다.
>
> ```csharp
> int doubled = i * 2;
> Console.WriteLine ("Yielding {0}", doubled);
> yield return doubled;                          // 이후 doubled를 안 쓴다 → 지역 변수 OK
> ```
>
> 마지막 두 줄의 순서를 바꾸면 최적화가 불가능해진다.
>
> ```csharp
> int doubled = i * 2;
> yield return doubled;
> Console.WriteLine ("Yielding {0}", doubled);   // yield 이후에 쓴다 → 필드로 승격
> ```
>
> 디버그 빌드에서는 디버깅 경험을 위해 릴리스에서라면 승격하지 않을 변수도 필드로 남길 수 있다. **디버그 빌드에서 관찰한 필드 목록으로 릴리스 동작을 추론하지 마라.**

### 6단계 — `Dispose()`와 `Reset()`

`Dispose()`는 상태값을 보고 지금 어느 `try` 영역 안에 멈춰 있는지 판정한 뒤, 해당하는 `finally` 몸통을 부른다.

```csharp
public void Dispose()
{
    switch (state)
    {
        case -3:            // try 안에서 실행 중이었다
        case 1:             // try 안의 첫 yield에서 멈춰 있다
        case 2:             // try 안의 두 번째 yield에서 멈춰 있다
            try { }
            finally
            {
                state = -1;
                Finally1();
            }
            break;
        // -1(완료), -2(미시작), 0(시작 전) → 할 일 없음
    }
}
```

`finally`가 여러 겹이면 이 판정이 겹겹이 중첩된다. 손으로 짜기 싫은 코드가 정확히 이런 것이다.

`Reset()`은 무조건 `NotSupportedException`을 던진다. 컴파일러 생성 반복자는 되감기를 지원하지 않는다. 되감고 싶으면 `GetEnumerator()`를 다시 부르면 된다.

> **💡 이 구조를 아는 것이 실무에서 값어치를 하는 지점**
>
> 세 군데다.
>
> 1. **메모리 덤프에서 `<Xxx>d__N` 타입이 잔뜩 보일 때** — 반복자가 열거되지 않은 채 살아 있다는 뜻이다. 캐시나 컬렉션에 `IEnumerable<T>`를 그대로 담아 두면 이렇게 된다. 그 상태 기계는 **매개변수와 캡처된 변수를 붙잡고 있다.**
> 2. **스택 트레이스가 `MoveNext`에서 시작할 때** — 반복자 안에서 던진 예외는 호출자가 아니라 열거자를 **돌린 쪽** 스택에 나타난다. 28.6절이 그 이야기다.
> 3. **할당 프로파일에서 반복자 호출 하나가 객체 하나로 잡힐 때** — 그게 정상이다. 두 개로 잡히면 스레드 ID 트릭이 실패한 것이다.

## 28.5 지연 실행의 의미와 `finally` 블록 처리

### 아무것도 실행되지 않는다는 것의 실제 모습

지연 실행(lazy execution, lazy evaluation)의 발상은 1930년대 람다 대수까지 거슬러 올라간다. **값이 필요할 때 비로소 그 값을 계산하는 코드를 실행한다.**

반복자에서 그 의미는 정확히 이렇다.

```csharp
using System.Collections.Generic;

static IEnumerable<int> CreateSimpleIterator()
{
    yield return 10;
    for (int i = 0; i < 3; i++)
    {
        yield return i;
    }
    yield return 20;
}
```

`CreateSimpleIterator()`를 호출해도 메서드 본문은 실행되지 않는다. `yield return 10;` 줄에 중단점을 걸고 단계 실행해도 **메서드를 호출할 때 중단점에 걸리지 않는다.** `GetEnumerator()`를 불러도 걸리지 않는다. 본문이 실행되기 시작하는 것은 **`MoveNext()`가 호출될 때**다.

`foreach` 루프를 풀어 쓰면 어디서 무슨 일이 일어나는지가 드러난다.

```csharp
using System.Collections.Generic;

IEnumerable<int> enumerable = CreateSimpleIterator();      // ① 상태 기계 생성만
using (IEnumerator<int> enumerator = enumerable.GetEnumerator())   // ② 커서 확보
{
    while (enumerator.MoveNext())                          // ③ 여기서 본문이 돈다
    {
        int value = enumerator.Current;                    // ④ 마지막 yield 값
        System.Console.WriteLine (value);
    }
}                                                          // ⑤ Dispose
```

### `MoveNext()`가 멈추는 네 가지 지점

메서드가 실행되기 시작해도 **필요한 만큼만** 간다. 다음 중 하나가 일어나면 멈춘다.

| 멈추는 이유 | `MoveNext()`의 반환 | `Current` |
|---|---|---|
| 예외가 던져졌다 | 반환하지 않고 예외 전파 | 변경 없음 |
| 메서드 끝에 도달했다 | `false` | 정의되지 않음 |
| `yield break`에 닿았다 | `false` | 정의되지 않음 |
| `yield return`의 피연산자를 평가했다 | `true` | 그 값으로 설정됨 |

예외는 평범하게 전파된다. 단, **당신이 이미 반복자 코드를 실행 중일 때만** 그렇다. 호출 코드가 반환된 시퀀스를 열거하기 전까지는 반복자 코드가 시작조차 안 하므로, **예외를 던지는 것은 반복자 메서드 호출이 아니라 `MoveNext()` 호출이다.**

두 번째 이후의 `MoveNext()`에서는 처음부터 다시 시작하지 않는다. 그러면 `10`이 무한히 반복될 것이다. `MoveNext()`가 반환할 때 메서드는 **일시 정지된 것처럼** 취급되고, 생성된 코드가 어디까지 갔는지와 지역 변수 `i` 같은 나머지 상태를 계속 들고 있다가, 다음 `MoveNext()`에서 그 지점부터 이어 간다.

### 게으름이 왜 중요한가 — 무한 시퀀스

```csharp
using System;
using System.Collections.Generic;

static IEnumerable<int> Fibonacci()
{
    int current = 0;
    int next = 1;
    while (true)                       // 무한 루프? 계속 요청할 때만 그렇다
    {
        yield return current;
        int oldCurrent = current;
        current = next;
        next = next + oldCurrent;
    }
}

static void Main()
{
    foreach (var value in Fibonacci())
    {
        Console.WriteLine (value);
        if (value > 1000)
            break;
    }
}
```

반복자 없이 같은 일을 하려면 어떻게 해야 하나. `List<int>`를 만들어 한계까지 채울 수 있다. 그런데 한계가 크면 리스트도 커진다. 그리고 더 근본적인 문제 — **피보나치 수열의 규칙을 아는 메서드가 왜 "언제 멈출지"까지 알아야 하나?**

멈추는 조건이 때로는 경과 시간, 때로는 출력 개수, 때로는 현재 값일 수 있다. 그때마다 메서드를 다시 구현할 수는 없다. 루프 안에서 값을 곧바로 출력해 버리면 리스트는 피할 수 있지만, 이번에는 `Fibonacci()`가 "지금 이 값으로 하고 싶은 일"에 단단히 결합된다. 값을 더하고 싶어지면 메서드를 또 하나 쓸 것인가. 관심사 분리의 완전한 붕괴다.

반복자 해법은 정확히 필요한 것을 준다. **무한 시퀀스의 표현, 그게 전부다.** 호출 코드가 원하는 만큼 열거하고 원하는 대로 쓴다.

> **📌 무한 시퀀스는 반복자에서만 자연스럽다**
>
> `int` 범위를 넘기면 오버플로가 나며, `checked` 문맥이냐 아니냐에 따라 예외가 나기도 하고 큰 음수로 언더플로하기도 한다(7장). 무한 시퀀스를 쓸 때는 소비자 쪽에서 반드시 종료 조건을 건다. `Take`, `TakeWhile`, `First` 같은 LINQ 연산자가 그 역할을 한다(30.2절).

### `finally`는 언제 도는가 — 이 절의 핵심

`try`/`finally`가 반복자 안에서 어떻게 처리되는지는 이 기능의 쓸모를 결정한다. 실무에서는 날 `finally`보다 `using` 문을 훨씬 많이 쓰지만, `using`은 `finally`로 만들어진 것이므로 동작은 같다.

진행 상황을 출력하는 반복자로 확인한다.

```csharp
using System;
using System.Collections.Generic;

static IEnumerable<string> Iterator()
{
    try
    {
        Console.WriteLine ("Before first yield");
        yield return "first";
        Console.WriteLine ("Between yields");
        yield return "second";
        Console.WriteLine ("After second yield");
    }
    finally
    {
        Console.WriteLine ("In finally block");
    }
}
```

`first`가 반환되는 시점에 `In finally block`이 보일까? 생각하는 방식이 둘 있다.

- `yield return` 문에서 실행이 **일시 정지**된다고 보면, 논리적으로 아직 `try` 안에 있으므로 `finally`를 돌 이유가 없다.
- `yield return`에 닿을 때 실제로 `MoveNext()` 호출자에게 **돌아가야 한다**고 보면, `try`를 빠져나가는 것이므로 `finally`가 평소처럼 돌아야 할 것 같다.

**일시 정지 모델이 이긴다.** 훨씬 유용하고, 다른 면에서 직관에 어긋나는 결과를 피할 수 있다. `try` 블록의 각 문장은 한 번씩만 실행하면서 `finally`는 세 번 실행하는 — 값을 내놓을 때마다 한 번씩, 그리고 나머지 코드를 실행할 때 한 번 — 것은 이상하다.

#### 경우 ① 끝까지 열거

```csharp
static void Main()
{
    foreach (string value in Iterator())
    {
        Console.WriteLine ("Received value: {0}", value);
    }
}
```

```text
Before first yield
Received value: first
Between yields
Received value: second
After second yield
In finally block
```

`finally`는 **맨 끝에 한 번만** 돈다. 그리고 출력이 서로 엇갈려 있는 것 자체가 지연 평가의 증거다. `Main()`의 출력과 `Iterator()`의 출력이 번갈아 나온다. 반복자가 반복적으로 멈췄다 이어지기 때문이다.

#### 경우 ② `foreach`를 중간에 `break`

```csharp
static void Main()
{
    foreach (string value in Iterator())
    {
        Console.WriteLine ("Received value: {0}", value);
        if (value != null)
        {
            break;
        }
    }
}
```

```text
Before first yield
Received value: first
In finally block
```

마지막 줄이 핵심이다. **`finally`가 여전히 돈다.** `foreach` 루프를 빠져나가면 자동으로 그렇게 된다. `foreach`에는 숨은 `using` 문이 있기 때문이다.

손으로 풀어 쓰면 이렇다.

```csharp
using System.Collections.Generic;

static void Main()
{
    IEnumerable<string> enumerable = Iterator();
    using (IEnumerator<string> enumerator = enumerable.GetEnumerator())
    {
        while (enumerator.MoveNext())
        {
            string value = enumerator.Current;
            System.Console.WriteLine ("Received value: {0}", value);
            if (value != null)
            {
                break;
            }
        }
    }
}
```

중요한 부분은 `using` 문이다. 어떻게 빠져나가든 `IEnumerator<string>`의 `Dispose`가 불린다. 그 시점에 반복자 메서드가 `try` 안에서 "일시 정지"되어 있으면, `Dispose`가 `finally` 블록을 실행해 준다.

#### 경우 ③ 수동 열거 후 방치

```csharp
using System.Collections.Generic;

var enumerator = Iterator().GetEnumerator();
enumerator.MoveNext();
string first = enumerator.Current;
// Dispose를 안 부르고 그냥 둔다
```

```text
Before first yield
```

**`finally`가 영원히 돌지 않는다.** 상태 기계 객체가 GC에 수거되어도 마찬가지다 — 컴파일러 생성 반복자에는 파이널라이저가 없다. 파일 핸들을 잡고 있었다면 그대로 새는 것이다.

정리하면 이렇다.

| 소비 방식 | `finally`가 도는 시점 |
|---|---|
| `foreach`로 끝까지 | 마지막 `MoveNext()`가 `false`를 돌려주는 그 안에서 |
| `foreach`에서 `break`/`return`/예외 | 루프를 빠져나갈 때 `Dispose()`를 통해 |
| `using (var e = ...GetEnumerator())` | `using` 블록을 벗어날 때 |
| 수동 열거 + `Dispose()` 호출 | `Dispose()` 안에서 |
| 수동 열거 + `Dispose()` 미호출 | **절대 돌지 않는다** |
| 반복자 안에서 예외 발생 | `fault` 블록 → `Dispose()` 경유 |
| 반복자를 만들고 열거하지 않음 | **절대 돌지 않는다** (본문이 시작조차 안 했다) |

> **⚠️ 열거자를 직접 다룰 때는 반드시 `using`으로 감싸라**
>
> 이것이 반복자에서 가장 흔한 리소스 누수다. 열거를 일찍 포기하면서 열거자를 해제하지 않으면 `finally`가 통째로 우회된다.
>
> ```csharp
> using System.Collections.Generic;
>
> string firstElement = null;
> var sequence = Foo();
> using (var enumerator = sequence.GetEnumerator())
>     if (enumerator.MoveNext())
>         firstElement = enumerator.Current;
> ```
>
> 비제네릭 `IEnumerator`는 `IDisposable`을 상속하지 않는다. 그래서 비제네릭 시퀀스를 수동 열거할 때는 `foreach`가 하는 것과 같은 인터페이스 검사를 직접 해야 한다 — 런타임 구현이 `IDisposable`인지 보고 그렇다면 부른다. 제네릭 `IEnumerator<T>`는 `IDisposable`을 상속하므로 이 문제가 없다.

### 그래서 반복자가 리소스를 잡을 수 있다

`finally` 처리가 제대로 되지 않았다면 반복자의 쓸모는 절반 이하였을 것이다. 제대로 되기 때문에 **정리가 필요한 리소스를 획득하는 메서드**를 반복자로 쓸 수 있고, 같은 요구를 가진 다른 반복자에 **연결**할 수도 있다.

```csharp
using System.Collections.Generic;
using System.IO;

static IEnumerable<string> ReadLines (string path)
{
    using (TextReader reader = File.OpenText (path))
    {
        string line;
        while ((line = reader.ReadLine()) != null)
        {
            yield return line;
        }
    }
}
```

파일 크기와 무관하게 메모리는 한 줄치만 쓰고, 소비자가 `break`로 나가도 파일이 닫힌다. `foreach` 루프가 예외를 던지거나 일찍 반환했을 때 파일 핸들이 열린 채 매달려 있게 된다면 이 메서드는 쓸모없는 물건이었을 것이다.

> **📌 `File.ReadLines`와의 미묘한 차이**
>
> .NET 4.0에서 위와 비슷한 메서드가 프레임워크에 들어왔다(`File.ReadLines`). 다만 .NET Framework 4.0 시점의 프레임워크 메서드는 **한 번 호출해서 결과를 여러 번 열거하는** 경우에 잘 동작하지 않았다. 파일을 한 번만 열었기 때문이다(이 부분은 런타임 구현 사항이므로 현재 대상 런타임에서 여러 번 열거할 생각이라면 직접 확인하라). 위 코드는 열거할 때마다 파일을 다시 연다. 추론하기는 이쪽이 더 쉽지만, 파일이 없거나 읽을 수 없는 경우의 예외가 **첫 `MoveNext()`까지 지연된다**는 단점이 따라온다. API 설계에는 늘 이런 까다로운 절충이 있다.
>
> 이 지연된 예외 문제가 다음 절의 주제다.

`IDisposable` 구현 계약 자체 — `Dispose(bool)` 패턴, 재진입 안전성, 파이널라이저 — 는 33장에서 다룬다. 여기서 붙잡을 것은 **반복자가 그 계약의 소비자이면서 생산자라는 사실**이다.

> **💡 반복자 안에서 리소스를 잡을 때의 규칙 세 가지**
>
> 1. **`using` 문의 범위를 `yield`를 감싸도록 잡아라.** 그래야 소비자가 중단해도 닫힌다.
> 2. **비싼 리소스는 반복자 안에 가두지 마라.** DB 커넥션을 잡은 반복자를 필드에 저장해 두면 커넥션 풀이 마른다. 무엇을 클로저·상태 기계에 가둘지의 원칙은 79.12절에서 다룬다.
> 3. **소비자가 `foreach`를 쓸 것을 전제해도 된다.** 수동 열거는 예외적이며, 그 경우 `using`은 소비자의 책임이다.

## 28.6 반복자의 오류 보고 시점 문제와 지역 함수 해법

### 증상 — 인자 검증이 엉뚱한 곳에서 터진다

인자를 받아 시퀀스를 만드는 반복자를 보자.

```csharp
using System;
using System.Collections.Generic;

public static IEnumerable<char> GenerateAlphabetSubset (char first, char last)
{
    if (first < 'a')
        throw new ArgumentException (
            "first must be at least the letter a", nameof (first));
    if (first > 'z')
        throw new ArgumentException (
            "first must be no greater than z", nameof (first));
    if (last < first)
        throw new ArgumentException (
            "last must be at least as large as first", nameof (last));
    if (last > 'z')
        throw new ArgumentException (
            "last must not be past z", nameof (last));

    var letter = first;
    while (letter <= last)
    {
        yield return letter;
        letter++;
    }
}
```

정상적인 방어 코드다. 그런데 이렇게 부르면 아무 일도 안 일어난다.

```csharp
var seq = GenerateAlphabetSubset ('Z', 'a');   // 예외 없음!
Console.WriteLine ("여기까지 무사 통과");

foreach (var c in seq)                          // ← 여기서 ArgumentException
    Console.Write (c);
```

이 코드는 **첫 요소가 요청될 때까지 인자 검사를 하나도 실행하지 않는다.** 다른 개발자가 이 메서드를 잘못 호출했을 때 진단과 수정이 훨씬 어려워진다. 프로그래밍 실수를 한 지점에서 예외가 나는 대신, **그 함수의 반환값을 사용할 때** 나중에 오류를 보게 된다.

### 왜 그런가 — 28.4절이 답이다

컴파일러가 만드는 것은 다음과 비슷한 구조다. 검사 코드가 상태 기계 클래스 안으로 들어가 `MoveNext()`의 **첫 호출 경로**에 놓인다.

```csharp
using System;
using System.Collections;
using System.Collections.Generic;

public class EmbeddedSubsetIterator : IEnumerable<char>
{
    private readonly char first;
    private readonly char last;

    public EmbeddedSubsetIterator (char first, char last)
    {
        this.first = first;
        this.last = last;
    }

    public IEnumerator<char> GetEnumerator() => new LetterEnumerator (first, last);
    IEnumerator IEnumerable.GetEnumerator() => new LetterEnumerator (first, last);

    private class LetterEnumerator : IEnumerator<char>
    {
        private readonly char first;
        private readonly char last;
        private bool isInitialized = false;
        private char letter = (char)('a' - 1);

        public LetterEnumerator (char first, char last)
        {
            this.first = first;
            this.last = last;
        }

        public bool MoveNext()
        {
            if (!isInitialized)
            {
                // ← 인자 검사가 전부 여기로 옮겨 왔다
                if (first < 'a')
                    throw new ArgumentException (
                        "first must be at least the letter a", nameof (first));
                if (first > 'z')
                    throw new ArgumentException (
                        "first must be no greater than z", nameof (first));
                if (last < first)
                    throw new ArgumentException (
                        "last must be at least as large as first", nameof (last));
                if (last > 'z')
                    throw new ArgumentException (
                        "last must not be past z", nameof (last));

                letter = (char)(first - 1);
                isInitialized = true;
            }
            letter++;
            return letter <= last;
        }

        public char Current => letter;
        object IEnumerator.Current => letter;
        public void Reset() => isInitialized = false;
        void IDisposable.Dispose() { }
    }
}
```

메서드 본문의 **모든 코드**가 상태 기계로 이주한다. `yield` 앞에 있든 뒤에 있든 상관없다. 컴파일러의 알고리즘은 바꿀 수 없다. 그러나 **코드를 재배치해서 초기 인자 검사와 시퀀스 생성을 분리할 수는 있다.**

### 해법 1 — 래퍼 메서드 + private 구현 메서드

공개 메서드는 `yield`를 하나도 갖지 않는 **평범한 메서드**로 만들고, 실제 생성은 별도의 private 반복자에 맡긴다.

```csharp
using System;
using System.Collections.Generic;

public static IEnumerable<char> GenerateAlphabetSubset (char first, char last)
{
    if (first < 'a')
        throw new ArgumentException (
            "first must be at least the letter a", nameof (first));
    if (first > 'z')
        throw new ArgumentException (
            "first must be no greater than z", nameof (first));
    if (last < first)
        throw new ArgumentException (
            "last must be at least as large as first", nameof (last));
    if (last > 'z')
        throw new ArgumentException (
            "last must not be past z", nameof (last));

    return GenerateAlphabetSubsetImpl (first, last);
}

private static IEnumerable<char> GenerateAlphabetSubsetImpl (char first, char last)
{
    var letter = first;
    while (letter <= last)
    {
        yield return letter;
        letter++;
    }
}
```

`GenerateAlphabetSubset`에는 `yield`가 없으므로 반복자가 아니다. 평범한 메서드이고, 호출하면 **즉시 실행된다.** 잘못된 인자로 부르면 private 생성 메서드에 들어가기도 전에 공개 메서드가 예외를 던진다. 호출자가 **실수한 바로 그 지점에서** 오류를 관찰한다.

### 해법 2 — 지역 함수 ※C# 7

반복자는 지역 함수여도 된다(28.3절). 그래서 private 헬퍼를 타입 수준에 노출할 필요 없이 메서드 안으로 밀어 넣을 수 있다.

```csharp
using System;
using System.Collections.Generic;

public static IEnumerable<char> GenerateAlphabetSubset (char first, char last)
{
    if (first < 'a')
        throw new ArgumentException (
            "first must be at least the letter a", nameof (first));
    if (first > 'z')
        throw new ArgumentException (
            "first must be no greater than z", nameof (first));
    if (last < first)
        throw new ArgumentException (
            "last must be at least as large as first", nameof (last));
    if (last > 'z')
        throw new ArgumentException (
            "last must not be past z", nameof (last));

    return Iterate();

    IEnumerable<char> Iterate()
    {
        var letter = first;                 // 바깥 매개변수를 캡처한다
        while (letter <= last)
        {
            yield return letter;
            letter++;
        }
    }
}
```

두 해법의 차이는 이렇다.

| 항목 | private 구현 메서드 | 지역 함수 |
|---|---|---|
| 인자 전달 | 명시적으로 다시 넘긴다 | 캡처된다 |
| 타입 표면 | private 멤버가 하나 늘어난다 | 타입 표면에 안 보인다 |
| 인자를 실수로 빠뜨림 | 가능하다 | 불가능하다(캡처라서) |
| 추가 할당 | 상태 기계 1개 | 상태 기계 1개 (`static` 아닌 지역 함수라도 반복자는 어차피 클래스가 생긴다) |
| 오버로드가 여럿일 때 | 구현 메서드 재사용이 쉽다 | 각 메서드가 자기 것을 갖는다 |

> **💡 지역 함수 쪽을 기본으로 삼아라**
>
> 이유는 "인자를 다시 넘기다가 순서를 바꿔 적는 실수"가 사라지기 때문이다. `Impl(first, last)`를 `Impl(last, first)`로 잘못 적는 버그는 컴파일러가 못 잡는다(타입이 같으므로). 캡처는 그 실수를 구조적으로 불가능하게 만든다.
>
> 예외는 두 가지다. (1) 오버로드가 여러 개인데 전부 같은 구현을 공유해야 할 때, (2) 검증 코드가 길어서 함수 하나가 세 화면을 넘길 때. 이때는 private 구현 메서드가 낫다.
>
> 람다와 지역 함수의 할당 차이 일반론은 26.12절에 있다.

### 무엇을 즉시 검증하고 무엇을 미룰 것인가

전부 앞으로 당길 수는 없다. 원칙은 이렇다.

| 검사 | 어디서 | 이유 |
|---|---|---|
| `null` 인자 | 래퍼 (즉시) | 호출자의 프로그래밍 실수다 |
| 범위·형식 검증 | 래퍼 (즉시) | 같다 |
| 델리게이트 인자 `null` | 래퍼 (즉시) | 같다 |
| 열거 중 발견되는 데이터 오류 | 반복자 안 (지연) | 데이터를 봐야만 알 수 있다 |
| 파일 존재 여부 | 상황에 따라 | 아래 참조 |

파일 존재 검사는 판단이 갈린다. 래퍼에서 미리 확인하면 오류가 일찍 나지만, 검사 시점과 열기 시점 사이에 파일이 사라질 수 있어서 **검사가 보증이 되지 못한다.** 그러면서 파일 시스템 왕복만 한 번 더 는다. 일반적으로는 "확인하지 말고 열다가 실패해라"가 낫고, 정말 이른 실패가 중요하면 두 번 다 실패하는 것을 감수한다.

> **⚠️ 이 문제는 `async` 메서드에도 똑같이 있다**
>
> `async` 메서드에서 인자 검증을 하면, 예외가 `Task`에 **담겨서** 돌아온다. 호출자가 `await` 하기 전까지 아무 일도 안 일어난다. 구조가 다르지만(반복자는 `MoveNext`까지, async는 `await`까지) 증상과 해법은 같다 — **동기 래퍼 + async 지역 함수**다.
>
> ```csharp
> public Task<int> ComputeAsync (string path)
> {
>     if (path is null) throw new ArgumentNullException (nameof (path));
>     return Impl();
>
>     async Task<int> Impl() { /* ... await ... */ }
> }
> ```
>
> 반복자와 다른 점 하나는, async에서는 예외가 **소실될** 수도 있다는 것이다. 반환된 `Task`를 아무도 `await` 하지 않으면 예외를 아무도 못 본다. 자세히는 47.5절과 46.11절에서 다룬다.

> **⚠️ 스택 트레이스도 함께 이동한다**
>
> 반복자 안에서 던진 예외의 스택 트레이스는 `GenerateAlphabetSubset`이 아니라 `<GenerateAlphabetSubset>d__0.MoveNext()`에서 시작한다. 그리고 그 위에는 반복자를 **호출한 코드**가 아니라 **열거한 코드**가 있다. 두 지점이 다른 파일, 다른 계층일 수 있다.
>
> 프로덕션 로그에서 `MoveNext`로 시작하는 스택을 보면 "여기가 진짜 원인 지점이 아닐 수 있다"를 먼저 의심해라. 래퍼 메서드 패턴을 쓰면 최소한 인자 오류만큼은 정확한 자리에서 잡힌다.

## 28.7 시퀀스 합성(composing sequences)

### 반복자는 조립된다

반복자는 대단히 합성 가능하다. 앞의 `Fibs` 예제를 확장해서 짝수 피보나치 수만 출력해 보자.

```csharp
using System;
using System.Collections.Generic;

foreach (int fib in EvenNumbersOnly (Fibs (6)))
    Console.WriteLine (fib);

IEnumerable<int> Fibs (int fibCount)
{
    for (int i = 0, prevFib = 1, curFib = 1; i < fibCount; i++)
    {
        yield return prevFib;
        int newFib = prevFib + curFib;
        prevFib = curFib;
        curFib = newFib;
    }
}

IEnumerable<int> EvenNumbersOnly (IEnumerable<int> sequence)
{
    foreach (int x in sequence)
        if ((x % 2) == 0)
            yield return x;
}
```

각 요소는 마지막 순간까지 계산되지 않는다 — `MoveNext()` 연산이 요청할 때 계산된다.

여기서 결정적인 것은 `EvenNumbersOnly`의 시그니처다. **`IEnumerable<T>`를 받아 `IEnumerable<T>`를 돌려준다.** 이 모양이 반복자를 레고 블록으로 만든다.

### 왜 이 모양이 이기는가

시퀀스를 다루는 코드를 쓰는 방법은 셋이다.

| 전략 | 중간 저장 | 순회 횟수 | 재사용성 |
|---|---|---|---|
| 단계마다 컬렉션을 만들어 넘긴다 | 단계마다 N개 | 단계 수만큼 | 높다 |
| 루프 하나에 전 단계를 우겨 넣는다 | 없음 | 1회 | **낮다** |
| 반복자 파이프라인 | 요소 1개씩 | 1회 | 높다 |

첫 번째 전략의 문제는 명백하다. 변환이 여러 단계면 단계마다 (아마도 큰) 컬렉션을 만들어 중간 결과를 담는다. 그리고 **앞 단계가 완전히 끝나기 전에는 다음 단계의 첫 요소조차 시작하지 못한다.** 게다가 변환마다 컬렉션을 한 번씩 순회한다.

두 번째 전략은 성능은 낫다. 한 번만 순회하고, 단계마다 N개짜리 컬렉션을 만들지 않으니 메모리도 적게 쓴다. 그러나 **재사용성을 희생한다.** 다단계 연산 하나보다는 개별 변환 각각을 재사용할 일이 훨씬 많다.

반복자는 셋 다 준다. `yield return`을 쓰면 요소 전체를 담을 저장 공간을 할당할 필요가 없다. 입력 시퀀스의 다음 요소는 필요할 때만 요청하고, 출력 시퀀스의 다음 값은 호출 코드가 요청할 때만 만든다.

### 실제로 관찰하기 — 추적 출력

중복 제거 반복자에 로그를 넣어 보면 실행 순서가 눈에 보인다.

```csharp
using System.Collections.Generic;
using static System.Console;

public static IEnumerable<int> Unique (IEnumerable<int> nums)
{
    var uniqueVals = new HashSet<int>();
    WriteLine ("\tEntering Unique");
    foreach (var num in nums)
    {
        WriteLine ("\tevaluating {0}", num);
        if (!uniqueVals.Contains (num))
        {
            WriteLine ("\tAdding {0}", num);
            uniqueVals.Add (num);
            yield return num;
            WriteLine ("\tRe-entering after yield return");
        }
    }
    WriteLine ("\tExiting Unique ");
}
```

입력이 `0, 3, 4, 5, 7, 3, 2, 7, 8, 0, 3, 1`일 때 출력은 이렇게 나온다.

```text
Entering Unique
evaluating 0
Adding 0
0
Re-entering after yield return
evaluating 3
Adding 3
3
Re-entering after yield return
evaluating 4
Adding 4
4
Re-entering after yield return
        ⋮
evaluating 3
evaluating 2
Adding 2
2
Re-entering after yield return
        ⋮
Exiting Unique
```

`yield return` 문이 재미있는 재주를 부린다. **값을 반환하면서 동시에 현재 위치와 내부 반복 상태를 보존한다.** 입력과 출력이 둘 다 반복자인 메서드가 되었고, 내부적으로는 입력 시퀀스에서의 현재 위치를 유지하면서 출력 시퀀스의 다음 항목을 계속 돌려준다. 이런 메서드를 **계속 가능 메서드**(continuable method)라고 부른다. 자기 상태를 기억하고 다시 진입할 때 그 위치에서 실행을 재개한다.

계속 가능 메서드라는 사실이 두 가지 이득을 준다. 첫째, 요소별 지연 평가가 가능해진다. 둘째, 그리고 더 중요하게, **각 메서드가 자기 `foreach` 루프를 가졌다면 얻기 어려웠을 합성 가능성**을 지연 실행이 준다.

### 제네릭화 — 타입에 무관해진다

`Unique()`는 입력이 정수라는 사실을 전혀 이용하지 않는다. 제네릭 메서드로 바꾸기에 완벽한 후보다.

```csharp
using System.Collections.Generic;

public static IEnumerable<T> Unique<T> (IEnumerable<T> sequence)
{
    var uniqueVals = new HashSet<T>();
    foreach (T item in sequence)
    {
        if (!uniqueVals.Contains (item))
        {
            uniqueVals.Add (item);
            yield return item;
        }
    }
}
```

반복자 메서드의 몸통은 대개 자기가 다루는 타입에 대해 아무 가정도 하지 않는다. 그래서 제네릭 메서드로 승격시켜 재사용을 더 얻을 수 있다.

### 파이프라인 조립

여러 단계를 조립할 때 진짜 힘이 나온다. 제곱 반복자를 추가한다.

```csharp
using System.Collections.Generic;

public static IEnumerable<int> Square (IEnumerable<int> nums)
{
    foreach (var num in nums)
        yield return num * num;
}
```

호출부는 중첩 호출 한 줄이다.

```csharp
foreach (var num in Square (Unique (nums)))
    System.Console.WriteLine ("Number returned from Unique: {0}", num);
```

**서로 다른 반복자 메서드를 아무리 많이 불러도 순회는 한 번만 일어난다.**

```text
   nums          Unique()          Square()          foreach
 ┌────────┐    ┌───────────┐    ┌───────────┐    ┌───────────┐
 │ 0      │───→│ 처음 보는  │───→│  x * x    │───→│ WriteLine │
 │ 3      │    │ 값만 통과  │    │           │    │           │
 │ 4      │ ←──┤ MoveNext  │←───┤ MoveNext  │←───┤ MoveNext  │
 │ 5      │    └───────────┘    └───────────┘    └───────────┘
 │ 7      │
 │ 3      │      ↑ 데이터는 →,  요청은 ←
 │ ⋮      │
 └────────┘      한 시점에 파이프 안에 있는 요소는 하나뿐이다
```

구슬 굴리기 장난감과 같다. 구슬을 하나씩 떨어뜨리면 관을 지나며 장애물을 통과한다. 구슬이 각 장애물 앞에 모여 기다리지 않는다. 첫 구슬은 마지막 구슬보다 몇 개의 장애물을 앞서 있을 수 있다. 각 반복자 메서드는 입력 시퀀스의 요소 하나에 연산 하나를 수행해서 출력 시퀀스에 새 객체를 얹는다. 개별적으로는 하는 일이 아주 적지만, 단일 입력·출력 스트림 위에 서 있으므로 조합이 쉽다.

### 시퀀스 두 개를 합치는 반복자

입력이 하나일 필요도 없다.

```csharp
using System.Collections.Generic;

public static IEnumerable<string> Zip (IEnumerable<string> first,
                                       IEnumerable<string> second)
{
    using (var firstSequence = first.GetEnumerator())
    {
        using (var secondSequence = second.GetEnumerator())
        {
            while (firstSequence.MoveNext() &&
                   secondSequence.MoveNext())
            {
                yield return string.Format ("{0} {1}",
                                            firstSequence.Current,
                                            secondSequence.Current);
            }
        }
    }
}
```

두 소스에서 요소를 하나씩 꺼내 하나로 합쳐 출력 시퀀스에 실어 보낸다. 여기서 `using`이 두 겹으로 쓰인 것에 주목해라. 28.5절의 규칙 그대로다 — 열거자를 수동으로 다루므로 해제는 이쪽 책임이다.

> **⚠️ 반복자는 소스 시퀀스를 변경하지 않는다 — 요소는 변경할 수 있다**
>
> `Square()`는 소스 요소를 변형하고, `Unique()`는 시퀀스 자체를 변형한다(각 값의 첫 복사본만 통과시킨다). 그러나 두 메서드 모두 **소스 시퀀스를 바꾸지 않는다.** 새 시퀀스를 출력으로 만들어 낼 뿐이다.
>
> 다만 시퀀스가 **참조 타입**을 담고 있으면 이야기가 달라진다. 반복자 안에서 요소의 프로퍼티를 건드리면 소스 쪽 객체가 실제로 바뀐다. "LINQ는 원본을 안 바꾼다"는 흔한 믿음은 시퀀스 구조에 대해서만 참이고 요소 내부 상태에 대해서는 거짓이다.

> **⚠️ 파이프라인은 소스를 여러 번 열거할 수 있다**
>
> ```csharp
> IEnumerable<int> data = ReadFromNetwork();
> var a = Square (Unique (data));
>
> foreach (var x in a) { }        // data를 1회 순회
> int count = 0;
> foreach (var x in a) { count++; }   // data를 또 1회 순회 — 네트워크 재호출
> ```
>
> 파이프라인은 **레시피**이지 결과가 아니다. 열거할 때마다 맨 밑바닥 소스까지 요청이 내려간다. 소스가 파일·네트워크·DB라면 그때마다 실제로 다시 읽는다. 소스가 한 번만 읽을 수 있는 것(예: 이미 소비된 스트림)이면 두 번째 열거는 빈 결과나 예외가 된다.
>
> 두 번 이상 쓸 것이 확실하면 `ToList()`로 한 번 물질화해라(30.8절). 지연 실행의 재평가 규칙 전반은 29.6절과 29.7절에서 다룬다.

> **📌 LINQ의 정체가 바로 이것이다**
>
> `Where`, `Select`, `Take` 같은 LINQ to Objects 연산자는 거의 전부 이 절에서 손으로 만든 것과 같은 모양의 반복자다 — `IEnumerable<T>`를 받아 `IEnumerable<T>`를 돌려주는 메서드. 확장 메서드로 선언되어 있어서 점으로 이어 붙일 수 있다는 점이 다를 뿐이다.
>
> 라이브러리가 진화하면서 서로 다른 연산을 서로 다른 CPU 코어에 배정할 수 있는 여지도 이 모양에서 나온다(50.3절 PLINQ). 연산자 각각의 구현과 성능 특성은 29장과 30장에서, 합성 가능한 시퀀스 API를 설계하는 원칙은 31.9절에서 다룬다.

## 28.8 반복자 메서드가 컬렉션 반환보다 나은 경우

### 기본 원칙

시퀀스를 반환하는 메서드를 만들 때는 **반복자 메서드로 만들어라.** 그러면 호출자에게 시퀀스를 처리하는 방법의 선택권을 더 많이 준다.

이유는 다음 다섯 가지로 정리된다.

**첫째, 호출자가 저장 구조를 고를 수 있다.** 컬렉션을 반환하면 그 구체 타입을 강요하는 셈이다.

```csharp
using System.Collections.Generic;

static IList<int> CreateSequence (int numberOfElements, int startAt, int stepBy)
{
    var collection = new List<int> (numberOfElements);
    for (int i = 0; i < numberOfElements; i++)
        collection.Add (startAt + i * stepBy);
    return collection;
}
```

이 결과를 `BindingList<int>`에 담고 싶은 클라이언트는 변환을 거쳐야 한다.

```csharp
var data = new System.ComponentModel.BindingList<int> (
    CreateSequence (100, 0, 5).ToList());
```

**둘째, 그 변환에 미묘한 버그가 숨을 수 있다.** `BindingList<T>` 생성자는 리스트의 요소를 복사하지 않고 **같은 저장 위치를 그대로 쓴다.** 초기화에 쓰인 저장 위치를 다른 코드가 도달할 수 있다면 데이터 무결성 오류가 생긴다. 참조가 여러 개라도 저장 위치는 하나다.

**셋째, 전체 리스트를 만들면 클라이언트가 조건에 따라 생성을 멈출 기회가 없다.** `CreateSequence`는 언제나 요청된 개수를 전부 만든다. 사용자가 페이징 때문이든 다른 이유든 중간에 멈추고 싶어도 멈출 수 없다.

**넷째, 파이프라인의 병목이 된다.** 이 메서드가 여러 단계 변환의 첫 단계라면(28.7절), 다음 단계가 시작되기 전에 모든 요소가 만들어져 내부 컬렉션에 추가되어야 한다.

반복자로 바꾸면 제약이 전부 사라진다.

```csharp
using System.Collections.Generic;

static IEnumerable<int> CreateSequence (int numberOfElements, int startAt, int stepBy)
{
    for (var i = 0; i < numberOfElements; i++)
        yield return startAt + i * stepBy;
}
```

핵심 논리는 그대로다. 숫자 시퀀스를 만든다.

**다섯째, 중단이 공짜가 된다.**

```csharp
// 익명 델리게이트로
var sequence = CreateSequence (10000, 0, 7)
    .TakeWhile (delegate (int num) { return num < 1000; });

// 람다 표기로
var sequence2 = CreateSequence (10000, 0, 7)
    .TakeWhile ((num) => num < 1000);
```

이 코드는 `CreateSequence`의 두 버전 모두와 동작한다. 그러나 **첫 번째(리스트) 구현이면 호출자가 어디서 멈추고 싶어 하든 10,000개가 전부 만들어진다.** 반복자 버전이면 조건에 맞지 않는 첫 값이 나오는 즉시 단락된다. 요소 생성 비용이 크면 절감폭도 크다.

### 실행 의미론이 달라진다는 점은 알고 써야 한다

반복자 버전에서는 **코드가 시퀀스를 열거할 때마다 숫자 시퀀스를 다시 만든다.** 위 예제는 항상 같은 수열을 만들므로 동작이 달라지지 않지만, 계산에 부작용이 있거나 외부 상태에 의존하면 이야기가 달라진다.

```csharp
using System.Collections.Generic;

int callCount = 0;

IEnumerable<int> Counted()
{
    for (int i = 0; i < 3; i++)
    {
        callCount++;
        yield return i;
    }
}

var seq = Counted();
foreach (var x in seq) { }
foreach (var x in seq) { }
System.Console.WriteLine (callCount);      // 6 — 3이 아니다
```

`List<int>` 하나를 저장할 이유가 있다면 클라이언트가 그렇게 하면 된다.

```csharp
var listStorage = new System.Collections.Generic.List<int> (CreateSequence (100, 0, 5));
```

`List<T>`에는 `IEnumerable<T>`를 받는 생성자가 있어서 시퀀스가 딱 한 번만 생성되도록 보장한다.

> **⚠️ 다중 열거는 조용한 성능 사고다**
>
> ```csharp
> void Report (IEnumerable<Order> orders)
> {
>     if (orders.Any())                       // 1회 열거
>         Console.WriteLine (orders.Count()); // 또 1회 열거
>     foreach (var o in orders) { }           // 또 1회 열거
> }
> ```
>
> `orders`가 리스트면 세 번 다 싸다. DB 쿼리나 파일 반복자면 세 번 전부 실제 I/O다. Roslyn 분석기와 ReSharper가 "Possible multiple enumeration"으로 경고해 주지만, 경고를 끄고 사는 코드베이스가 많다.
>
> 방어책은 셋이다. (1) 메서드 입구에서 `ToList()`로 물질화한다, (2) 매개변수 타입을 `IReadOnlyCollection<T>`로 바꿔 "여러 번 봐도 되는 것만 넘겨라"를 계약으로 만든다, (3) `Enumerable.TryGetNonEnumeratedCount` ※.NET 6로 열거 없이 개수를 얻을 수 있는지 먼저 시도한다.

### 반복자를 쓰면 안 되는 경우

"반복자가 기본"이라고 해서 늘 옳지는 않다. 컬렉션을 반환해야 하는 경우가 분명히 있다.

| 상황 | 무엇을 반환할 것인가 | 이유 |
|---|---|---|
| 요소 개수를 호출자가 반드시 알아야 한다 | `IReadOnlyList<T>` / `T[]` | 반복자는 `Count`가 없다 |
| 결과가 이미 메모리에 다 있다 | 컬렉션 | 상태 기계 할당이 순손해다 |
| 인덱스 접근이 필요하다 | `IReadOnlyList<T>` | — |
| 호출자가 거의 항상 전체를 여러 번 쓴다 | 컬렉션 | 재계산을 강요하지 않는다 |
| 스레드 안전한 스냅숏이 필요하다 | 불변 컬렉션 | 지연 실행은 열거 시점의 상태를 본다 |
| 잠금 안에서 만든 결과 | 컬렉션 | 지연시키면 잠금 밖에서 소스를 읽는다 |
| 요소가 많거나 무한하다 | 반복자 | — |
| 파이프라인의 한 단계다 | 반복자 | — |
| 요소 생성 비용이 크다 | 반복자 | — |
| 외부 리소스에서 스트리밍한다 | 반복자 | — |

> **⚠️ 잠금 안에서 반복자를 만들면 잠금이 무의미해진다**
>
> ```csharp
> IEnumerable<Item> Snapshot()      // 반복자
> {
>     lock (gate)
>     {
>         foreach (var item in items)
>             yield return item;     // 잠금을 쥔 채로 호출자에게 제어가 넘어간다
>     }
> }
> ```
>
> 이 코드에는 두 가지 문제가 겹쳐 있다. 첫째, `lock` 블록이 `yield` 경계를 가로지르므로 **잠금을 쥔 채 호출자 코드가 실행된다.** 호출자가 오래 걸리면 그동안 잠금이 잡혀 있고, 호출자가 같은 잠금을 다시 잡으려 하면 상황에 따라 데드락이다. 둘째, 소비자가 열거를 중단하고 `Dispose`도 안 하면 **잠금이 영원히 풀리지 않는다.**
>
> 잠금 안에서 만든 결과는 반복자가 아니라 **완성된 컬렉션**으로 돌려줘야 한다. `lock (gate) { return items.ToArray(); }`가 정답이다. 참고로 `lock` 블록 안에 `yield return`을 두는 것은 컴파일 오류가 아니다 — 컴파일러가 막아 주지 않는다.

> **💡 공개 API의 기본값은 `IEnumerable<T>` 반환, 내부 캐싱은 자유**
>
> 시퀀스가 반복해서 쓰이고 캐싱할 수 있다면, 그 결정은 **생성기 메서드를 호출하는 코드에 맡겨라.** 호출자가 당신의 메서드를 어떻게 쓸지 넘겨짚지 마라. 호출자는 스스로 판단할 수 있고, `ToList()`와 `ToArray()` 확장 메서드가 `IEnumerable<T>`로 표현된 시퀀스를 저장 컬렉션으로 만들어 준다(30.8절).
>
> 시퀀스 반환 메서드를 만들면 두 시나리오를 **동시에** 지원할 수 있다 — 컬렉션 저장이 효율적인 경우와 시퀀스 생성이 효율적인 경우 둘 다. 공개 API가 시퀀스를 생성하지 **않으면** 생성이 더 쉬운 시나리오를 아예 지원할 수 없다. 내부적으로는 측정 가능한 이점이 있다면 이전 생성 결과를 캐싱해도 된다.

### 성능 비교 — 무엇이 얼마나 드는가

| 항목 | 반복자 (`IEnumerable<T>`) | 컬렉션 (`List<T>`) |
|---|---|---|
| 호출 시 할당 | 상태 기계 객체 1개 | 리스트 + 내부 배열 (성장 시 재할당) |
| 요소 N개 저장 | 없음 (한 번에 1개) | N개분 |
| 첫 요소까지의 지연 | 최소 | 전체 생성 완료까지 |
| 전체 순회 비용 | 요소마다 `MoveNext` 인터페이스 호출 2회 | 인덱스 접근 또는 구조체 열거자 |
| `Count` 조회 | 전체 열거 필요 | O(1) |
| 재열거 | 처음부터 다시 실행 | 저장된 값 재사용 |
| 조기 중단 | 만든 것까지만 비용 | 전량 생성 후 버림 |

**작은 컬렉션을 여러 번 도는 경우에는 반복자가 손해다.** 상태 기계 할당과 인터페이스 디스패치 비용이 그대로 남고 지연 실행의 이득은 없다. 요소가 열 개인 시퀀스를 만들어 즉시 세 번 순회하는 코드라면 `ToArray()`가 낫다.

반대로 **첫 요소만 쓰거나 조건에 걸려 일찍 멈추는 경우, 요소 생성 비용이 큰 경우, 요소 수가 크거나 무한한 경우**에는 반복자의 이득이 압도적이다.

메서드마다 반환 타입이 다를 수 있고 각 타입을 만드는 비용도 다르다. 시퀀스를 반환하는 메서드는 시퀀스 전체를 만드는 데 큰 비용이 들 수 있다 — 계산 시간과 저장 공간 양쪽에서. 모든 API의 사용법을 예상할 수는 없지만, API를 쓰는 개발자에게 **최대한의 유연성**을 줄 수는 있다. 그게 생성기 메서드를 만드는 이유다.

LINQ 관용구로서의 "반복자 메서드와 지연 평가 선호"는 79.11절에서 설계 원칙으로 다시 다룬다.

## 28.9 `IAsyncEnumerable<T>`와 `await foreach` ※C# 8

### 두 기능을 합치면

`yield return`으로는 반복자를 쓸 수 있고 `await`로는 비동기 함수를 쓸 수 있다. **비동기 스트림**(asynchronous stream, C# 8부터)은 이 두 개념을 합쳐서, **await 하는 반복자** — 요소를 비동기적으로 내놓는 반복자 — 를 쓸 수 있게 한다.

기반이 되는 인터페이스 한 쌍은 28.1절의 열거 인터페이스에 대응한다.

```csharp
public interface IAsyncEnumerable<out T>
{
    IAsyncEnumerator<T> GetAsyncEnumerator (...);
}

public interface IAsyncEnumerator<out T> : IAsyncDisposable
{
    T Current { get; }
    System.Threading.Tasks.ValueTask<bool> MoveNextAsync();
}
```

동기 쪽과의 대응은 이렇다.

| 동기 | 비동기 | 차이점 |
|---|---|---|
| `IEnumerable<T>` | `IAsyncEnumerable<T>` | — |
| `GetEnumerator()` | `GetAsyncEnumerator(CancellationToken)` | 취소 토큰을 받는다 |
| `IEnumerator<T>` | `IAsyncEnumerator<T>` | — |
| `bool MoveNext()` | `ValueTask<bool> MoveNextAsync()` | 반환이 대기 가능하다 |
| `T Current` | `T Current` | 동일 (동기다) |
| `IDisposable` | `IAsyncDisposable` | `ValueTask DisposeAsync()` |
| `foreach` | `await foreach` | — |
| `yield return` | `yield return` (메서드가 `async`) | 동일 문법 |

`ValueTask<T>`는 `Task<T>`를 감싸는 **구조체**이며 동작은 `Task<T>`와 비슷하되, 태스크가 동기적으로 완료될 때 더 효율적으로 실행할 수 있게 해 준다. 시퀀스를 열거할 때는 그런 일이 자주 일어난다 — 버퍼에 이미 데이터가 있으면 `MoveNextAsync()`는 대기 없이 완료된다. `ValueTask<T>`를 언제 쓰고 언제 쓰면 안 되는지는 47.13절에서 다룬다.

`IAsyncDisposable`은 `IDisposable`의 비동기 버전이다. 인터페이스를 수동으로 구현하기로 했을 때 정리 작업을 수행할 기회를 준다.

```csharp
public interface IAsyncDisposable
{
    System.Threading.Tasks.ValueTask DisposeAsync();
}
```

`IAsyncDisposable`의 계약과 `await using` 문 자체는 33.6절에서 다룬다.

> **📌 `IAsyncEnumerable<T>`와 `Task<IEnumerable<T>>`는 다른 물건이다**
>
> 시퀀스에서 각 요소를 가져오는 행위(`MoveNextAsync`)가 비동기 연산이므로, 비동기 스트림은 **요소가 조금씩 도착할 때** 적합하다(비디오 스트림 데이터 처리 같은 경우). 반면 **시퀀스 전체가 지연되지만 도착할 때는 한꺼번에 오는** 경우에는 다음 타입이 더 알맞다.
>
> ```csharp
> System.Threading.Tasks.Task<System.Collections.Generic.IEnumerable<T>>
> ```
>
> 이 구별을 API 설계에서 틀리면 소비자가 계속 손해를 본다. "조금씩 오는가, 한꺼번에 오는가"가 판단 기준이다.

### 비동기 스트림 만들기

반복자와 비동기 메서드의 원리를 결합한 메서드를 쓴다. 즉 **`yield return`과 `await`를 둘 다 포함하고 `IAsyncEnumerable<T>`를 반환하는** 메서드다. 그리고 `async` 한정자를 붙인다.

```csharp
using System.Collections.Generic;
using System.Threading.Tasks;

async IAsyncEnumerable<int> RangeAsync (int start, int count, int delay)
{
    for (int i = start; i < start + count; i++)
    {
        await Task.Delay (delay);
        yield return i;
    }
}
```

비동기 스트림을 반환하는 메서드의 요건 세 가지를 정리하면 이렇다.

- `async` 한정자로 선언된다
- `IAsyncEnumerable<T>`를 반환한다
- 연속된 요소를 돌려주는 `yield return` 문을 담는다

### 비동기 스트림 소비하기

`await foreach` 문을 쓴다.

```csharp
await foreach (var number in RangeAsync (0, 10, 500))
    System.Console.WriteLine (number);
```

데이터가 500밀리초마다 꾸준히 도착한다(실제 상황이라면 사용 가능해지는 대로 도착한다). `Task<IEnumerable<T>>`를 쓴 비슷한 구조와 대비된다. 그쪽은 **마지막 데이터 조각이 준비될 때까지 아무 데이터도 반환되지 않는다.**

```csharp
using System.Collections.Generic;
using System.Threading.Tasks;

static async Task<IEnumerable<int>> RangeTaskAsync (int start, int count, int delay)
{
    List<int> data = new List<int>();
    for (int i = start; i < start + count; i++)
    {
        await Task.Delay (delay);
        data.Add (i);
    }
    return data;
}
```

소비 쪽은 평범한 `foreach`다. 다만 5초를 기다린 뒤에야 첫 숫자를 본다.

```csharp
foreach (var data in await RangeTaskAsync (0, 10, 500))
    System.Console.WriteLine (data);
```

### `await foreach`도 덕 타이핑이다

`await foreach`는 `IAsyncEnumerable<T>` 구현을 **요구하지 않는다.** 동기 `foreach`와 마찬가지로 패턴 기반이다.

- **`GetAsyncEnumerator()`** — 인수가 없거나, 선택적 `CancellationToken` 하나만 받는다. 확장 메서드여도 된다 ※C# 9
- **반환 타입의 `MoveNextAsync()`** — 대기 가능한 값을 반환하고, 그것을 `await` 한 결과가 `bool`이어야 한다
- **반환 타입의 `Current`** — 접근 가능한 getter를 가진 프로퍼티
- **(선택) `DisposeAsync()`** — 있으면 `await foreach`가 끝날 때 `await` 해서 호출한다

낮춘 결과는 개념적으로 이렇다.

```csharp
var e = source.GetAsyncEnumerator (token);
try
{
    while (await e.MoveNextAsync())
    {
        var item = e.Current;
        // 본문
    }
}
finally
{
    if (e is not null)
        await e.DisposeAsync();
}
```

동기 버전과 모양이 같고, `MoveNext`와 `Dispose` 자리에 `await`가 붙었을 뿐이다.

> **📌 C# 8 이전 설계안은 지금과 달랐다**
>
> C# 8이 확정되기 전의 초안에서는 문법이 `foreach await` / `using await`였고, `IAsyncEnumerator<T>`의 멤버도 `Task<bool> WaitForNextAsync()`와 `T TryGetNext(out bool success)` 두 개였다. 버퍼링된 결과 안에서는 동기적으로 훑고 버퍼가 비면 그때만 비동기로 다음 묶음을 가져오자는 설계였다.
>
> 최종 출시본은 `await foreach` / `await using` 문법에 `ValueTask<bool> MoveNextAsync()` 하나로 정리되었다. 동기 완료 경로의 효율은 `ValueTask<T>`가 담당하게 되었다. 오래된 블로그 글이나 프리뷰 시절 자료에서 `WaitForNextAsync`를 보게 되면 **그건 출시되지 않은 설계다.**

### 취소 — `WithCancellation`과 `[EnumeratorCancellation]`

`GetAsyncEnumerator`가 `CancellationToken`을 받는다는 사실이 여기서 쓰인다. 그런데 `await foreach` 문법에는 토큰을 넘길 자리가 없다. 그래서 확장 메서드가 있다.

```csharp
using System.Collections.Generic;
using System.Threading;
using System.Threading.Tasks;

async Task Consume (IAsyncEnumerable<int> source, CancellationToken token)
{
    await foreach (var x in source.WithCancellation (token))
        System.Console.WriteLine (x);
}
```

`WithCancellation`은 `System.Threading.Tasks.TaskAsyncEnumerableExtensions`가 제공하는 확장 메서드이고, `System.Runtime.CompilerServices.ConfiguredCancelableAsyncEnumerable<T>`라는 구조체를 반환한다. 그 구조체는 `GetAsyncEnumerator()` 모양을 갖추고 있으므로 `await foreach`가 그대로 받아 준다. 인터페이스가 아니라 모양을 보는 규칙이 여기서 다시 값어치를 한다.

생산자 쪽에서 그 토큰을 받으려면 매개변수에 `[EnumeratorCancellation]` 특성을 붙인다.

```csharp
using System.Collections.Generic;
using System.Runtime.CompilerServices;
using System.Threading;
using System.Threading.Tasks;

async IAsyncEnumerable<int> RangeAsync (
    int start, int count, int delay,
    [EnumeratorCancellation] CancellationToken token = default)
{
    for (int i = start; i < start + count; i++)
    {
        await Task.Delay (delay, token);
        yield return i;
    }
}
```

이 특성이 붙은 매개변수는 컴파일러가 특별 취급한다. 생성된 `GetAsyncEnumerator(CancellationToken)`이 받은 토큰을 **그 매개변수 자리에 흘려 넣는다.** 그래서 다음 두 호출이 모두 동작한다.

```csharp
// 반복자 호출 시점에 토큰을 준다
await foreach (var x in RangeAsync (0, 10, 500, token)) { }

// 열거 시점에 토큰을 준다
await foreach (var x in RangeAsync (0, 10, 500).WithCancellation (token)) { }
```

> **⚠️ `[EnumeratorCancellation]`을 안 붙이면 `WithCancellation`이 조용히 무력해진다**
>
> 특성을 빠뜨리면 컴파일도 되고 실행도 된다. 다만 `WithCancellation(token)`으로 넘긴 토큰이 **반복자 본문의 `token` 매개변수에 도달하지 않는다.** 취소를 요청해도 아무 일이 없다. 오류도 경고도 없이 취소 기능만 죽는다.
>
> 반대로 두 자리에서 서로 다른 토큰이 들어오면(호출 인수로 하나, `WithCancellation`으로 또 하나) 컴파일러가 두 토큰을 링크한 결합 토큰을 만들어 준다 — 즉 어느 쪽이 취소돼도 취소된다.
>
> **`IAsyncEnumerable<T>`를 반환하는 반복자를 만들 때는 `[EnumeratorCancellation] CancellationToken token = default`를 마지막 매개변수로 두는 것을 관행으로 삼아라.** 협력적 취소 프로토콜 전반은 46.8절에서 다룬다.

### `ConfigureAwait`

`await foreach`는 `MoveNextAsync()`와 `DisposeAsync()`를 자동으로 `await` 한다. 그러면 `ConfigureAwait(false)`를 붙일 자리가 없어 보이지만, 같은 확장 메서드 집합이 답을 준다.

```csharp
await foreach (var x in source.ConfigureAwait (false))
    { /* ... */ }

// 둘 다 필요하면 이어 붙인다
await foreach (var x in source.WithCancellation (token).ConfigureAwait (false))
    { /* ... */ }
```

`ConfigureAwait`도 `ConfiguredCancelableAsyncEnumerable<T>`를 돌려주며, 그 구조체가 `WithCancellation`과 `ConfigureAwait` 메서드를 다시 제공하므로 순서에 상관없이 이어 붙일 수 있다.

기본값(즉 `ConfigureAwait(true)`)은 태스크를 `await` 할 때 동기화 컨텍스트를 활용한다. GUI 애플리케이션(WinForms, WPF)에서는 그게 원하는 동작이다. 그러나 GUI가 아닌 코드를 쓸 때는 필요하지도 않은 원래 컨텍스트를 큐에 넣는 오버헤드가 성능 문제를 일으킬 수 있다.

.NET 팀의 지침은 이렇다. **애플리케이션 코드(WinForms, WPF 등)에서는 기본 동작을 그대로 둔다. 애플리케이션이 아닌 코드(라이브러리 코드)에서는 `ConfigureAwait(false)`를 쓴다.** 한 가지 예외는 ASP.NET Core다 — ASP.NET Core는 커스텀 `SynchronizationContext`를 만들지 않으므로 `ConfigureAwait(false)`의 이득이 없다.

`ConfigureAwait(false)`의 정확한 의미와 동기화 컨텍스트의 동작은 47.12절에서 다룬다.

### 비동기 반복자의 상태 기계

컴파일러가 만드는 것은 28.4절의 반복자 상태 기계와 47.7절의 async 상태 기계를 **합친 물건**이다. 생성 클래스가 구현하는 인터페이스만 봐도 짐작이 간다.

```csharp
private sealed class GeneratedAsyncIterator
    : IAsyncEnumerable<int>, IAsyncEnumerator<int>,
      IAsyncStateMachine, IValueTaskSource<bool>, IValueTaskSource
{
    private int state;                        // <>1__state
    private int current;                      // <>2__current
    private AsyncIteratorMethodBuilder builder;              // <>t__builder
    private ManualResetValueTaskSourceCore<bool> promise;    // <>v__promiseOfValueOrEnd
    private bool disposeMode;                 // <>w__disposeMode
    private CancellationToken token;
    // ... 승격된 지역 변수, awaiter 필드 ...
}
```

주목할 점 넷.

1. **동기 반복자와 마찬가지로 하나의 객체가 시퀀스와 커서를 겸한다.** 스레드 ID 트릭도 그대로 쓴다.
2. **`ValueTask<bool>`을 매번 할당하지 않기 위해 상태 기계 자신이 `IValueTaskSource<bool>`을 구현한다.** 그래서 `MoveNextAsync()`가 요소마다 `Task`를 새로 만들지 않는다. `ValueTask<T>`를 **두 번 await 하면 안 되는** 이유가 정확히 이것이다 — 뒤에 오는 `MoveNextAsync()`가 같은 슬롯을 재사용한다.
3. **`disposeMode` 플래그가 있다.** `DisposeAsync()`가 불리면 이 플래그를 켜고 `MoveNext`를 다시 돌려서, 남아 있는 `finally` 블록들을 비동기적으로 실행한다. 동기 반복자의 `Dispose()`가 하는 일의 비동기 버전이다.
4. **`AsyncIteratorMethodBuilder`는 async 메서드용 빌더와 다른 타입이다.** 완료 시 반환할 태스크가 없기 때문이다.

세부는 47.11절에서 다룬다. 여기서 알아 둘 것은 **비동기 반복자 하나가 동기 반복자보다 상당히 무겁다**는 사실이다. 요소마다 진짜 비동기 대기가 필요한 경우에만 값어치를 한다.

> **⚠️ `ValueTask<bool>`은 한 번만 await 한다**
>
> ```csharp
> var e = source.GetAsyncEnumerator();
> var vt = e.MoveNextAsync();
> bool a = await vt;
> bool b = await vt;        // 하면 안 된다 — 동작이 정의되지 않는다
> ```
>
> `MoveNextAsync()`가 돌려주는 `ValueTask<bool>`은 상태 기계 내부 슬롯을 가리키는 얇은 구조체다. 한 번 `await` 하고 나면 그 슬롯은 다음 호출을 위해 재사용될 수 있다. 저장해 뒀다가 나중에 `await` 하는 것, 두 번 `await` 하는 것, `.Result`로 읽는 것 전부 금지다. `await foreach`를 쓰면 이 실수를 할 수 없다. 수동으로 열거할 때만 주의하면 된다.

### `IAsyncEnumerable<T>`에 LINQ 쓰기

`System.Linq.Async` NuGet 패키지가 `IAsyncEnumerable<T>` 위에서 동작하는 LINQ 쿼리 연산자를 정의한다. `IEnumerable<T>`에서 하던 것과 거의 같게 쿼리를 쓸 수 있다.

```csharp
using System.Collections.Generic;
using System.Linq;

IAsyncEnumerable<int> query =
    from i in RangeAsync (0, 10, 500)
    where i % 2 == 0                    // 짝수만
    select i * 10;                      // 10을 곱한다

await foreach (var number in query)
    System.Console.WriteLine (number);
```

출력은 0, 20, 40, ... 이다.

> **📌 Rx와의 상호 변환**
>
> Rx(Reactive Extensions)에 익숙하다면 `ToObservable` 확장 메서드를 불러 `IAsyncEnumerable<T>`를 `IObservable<T>`로 바꿔서 Rx의 (더 강력한) 쿼리 연산자를 쓸 수 있다. 반대 방향으로 변환하는 `ToAsyncEnumerable` 확장 메서드도 있다.
>
> 두 모델의 근본적 차이는 **당김(pull)이냐 밀어냄(push)이냐**다. `IAsyncEnumerable<T>`는 소비자가 `MoveNextAsync()`로 당긴다. `IObservable<T>`는 생산자가 밀어낸다. 밀어내는 모델에서는 소비자가 못 따라가면 배압(backpressure)을 스스로 관리해야 한다. 프로듀서/컨슈머 파이프라인의 배압 설계는 51.1절과 51.2절에서 다룬다.

### ASP.NET Core에서의 `IAsyncEnumerable<T>`

ASP.NET Core 컨트롤러 액션이 `IAsyncEnumerable<T>`를 반환할 수 있다. 그런 메서드는 `async`로 표시되어야 한다.

```csharp
[HttpGet]
public async IAsyncEnumerable<string> Get()
{
    using var dbContext = new BookContext();
    await foreach (var title in dbContext.Books
                                         .Select (b => b.Title)
                                         .AsAsyncEnumerable())
        yield return title;
}
```

응답이 스트리밍되므로 결과 전체를 메모리에 모으지 않는다. 큰 결과 집합을 돌려주는 API에서 메모리 사용량이 눈에 띄게 줄어든다.

> **⚠️ 스트리밍 응답에서 중간에 예외가 나면 상태 코드를 못 바꾼다**
>
> `IAsyncEnumerable<T>`를 반환하면 첫 요소가 나오는 순간 HTTP 상태 코드와 헤더가 이미 전송된다. 열거 도중에 DB 오류가 나면 **200 OK로 시작한 응답의 본문이 중간에서 끊긴다.** 클라이언트는 "성공했는데 JSON이 깨졌다"를 보게 된다.
>
> 실패 가능성이 높은 쿼리라면 스트리밍보다 물질화가 나을 수 있고, 스트리밍을 유지하려면 클라이언트 쪽에서 불완전한 응답을 감지할 수단(예: 마지막 요소 표식, chunked 인코딩 종료 검증)을 함께 설계해야 한다.

> **💡 `IAsyncEnumerable<T>`를 도입할 자리와 도입하지 말 자리**
>
> **도입할 자리** — 페이지 단위로 오는 원격 API 결과, 서버 스트리밍 gRPC, DB 커서, 파일/네트워크 스트림 파싱, 메시지 큐 소비. 공통점은 "요소가 시간에 걸쳐 조금씩 온다"이다.
>
> **도입하지 말 자리** — 한 번의 요청으로 전부 오는 결과(그건 `Task<IReadOnlyList<T>>`다), 이미 메모리에 있는 데이터(그건 `IEnumerable<T>`다), 요소가 열 개인 시퀀스(상태 기계와 `ValueTask` 기계가 이득보다 크다).
>
> 판단 기준 하나만 기억하면 된다 — **`MoveNextAsync()`가 실제로 비동기적으로 완료될 일이 있는가.** 없다면 비동기 스트림은 순수한 오버헤드다.

## 이 장의 요약

- **열거 가능 객체와 열거자는 다른 물건이다.** 전자는 시퀀스(책), 후자는 커서(책갈피)다. `IEnumerable<T>`는 여러 번 열거할 수 있고 `IEnumerator<T>`는 한 번뿐이다. 이 구별을 놓치면 뒤가 전부 흐려진다.
- **`foreach`도 `await foreach`도 인터페이스가 아니라 모양을 본다.** `GetEnumerator`/`GetAsyncEnumerator`는 확장 메서드여도 되며(※C# 9), 이 덕 타이핑 덕분에 구조체 열거자와 `ref struct` 열거자가 가능해졌다. 확장 메서드는 항상 인스턴스 메서드에 진다.
- **컬렉션 초기화자는 `Add` 호출로 번역된다.** `IEnumerable` 구현은 자격 검사일 뿐 호출되지 않는다. 딕셔너리의 `{ k, v }`는 `Add`(중복 시 예외), `[k] = v`는 인덱서(중복 시 덮어쓰기)이며 동작이 다르다. 컬렉션 식 ※C# 12은 `Add` 없이도 읽기 전용 컬렉션을 만들 수 있어 초기화자의 상위 호환이 아니라 별개 기능이다.
- **반복자 메서드를 호출하면 상태 기계 객체 하나가 만들어질 뿐 코드는 한 줄도 돌지 않는다.** 실행은 `MoveNext()`에서 시작한다. `yield return`은 상태 번호를 박고 `return true` 하는 것이고, 다음 `MoveNext()`는 점프 테이블로 그 지점에 돌아온다. `yield` 경계를 살아남는 지역 변수만 필드로 승격되고, `GetEnumerator()`는 스레드 ID 트릭으로 첫 열거에서 객체 재할당을 피한다.
- **`finally`는 열거가 끝나거나 열거자가 해제될 때 돈다.** `foreach`는 `break`로 나가도 숨은 `using` 덕에 `Dispose()`를 부른다. 수동 열거를 `using` 없이 하면 `finally`가 영원히 돌지 않고, 반복자를 만들기만 하고 열거하지 않으면 애초에 시작조차 안 한다.
- **반복자의 인자 검증은 첫 `MoveNext()`까지 미뤄진다.** 모든 코드가 상태 기계로 이주하기 때문이다. 해법은 `yield` 없는 래퍼 메서드에서 검증하고 실제 생성은 지역 함수(또는 private 구현 메서드)에 맡기는 것이다. `async` 메서드도 같은 문제와 같은 해법을 갖는다.
- **`IEnumerable<T>`를 받아 `IEnumerable<T>`를 돌려주는 반복자는 조립된다.** 몇 단계를 이어 붙여도 소스 순회는 한 번이고, 한 시점에 파이프라인 안에 있는 요소는 하나뿐이다. LINQ to Objects 연산자 전체가 이 모양이다. 대신 파이프라인은 레시피이므로 열거할 때마다 밑바닥까지 다시 요청이 내려간다.
- **시퀀스를 반환하는 공개 API의 기본값은 반복자다.** 호출자에게 저장 구조·중단 시점·캐싱 여부의 선택권을 넘긴다. 예외는 개수·인덱스 접근이 필요할 때, 결과가 이미 메모리에 있을 때, 잠금 안에서 만들 때다. 특히 `lock` 안에서 `yield return` 하면 잠금을 쥔 채 호출자 코드가 돈다.
- **비동기 스트림 ※C# 8은 요소가 시간에 걸쳐 조금씩 올 때 쓴다.** 한꺼번에 오면 `Task<IEnumerable<T>>`가 맞다. `[EnumeratorCancellation]`을 빠뜨리면 `WithCancellation`이 조용히 무력해지고, `MoveNextAsync()`가 돌려준 `ValueTask<bool>`을 두 번 `await` 하면 안 된다.

## 연습 문제

1. **상태 기계를 실물로 확인하라.** 이 장의 `GenerateIntegers`를 컴파일한 뒤 ILSpy나 `ildasm`으로 열어라. `<GenerateIntegers>d__N` 타입의 필드 목록을 적고, `doubled`가 필드로 잡혔는지 확인하라. 그다음 `yield return doubled;`와 `Console.WriteLine("Yielding {0}", doubled);`의 순서를 바꿔 다시 컴파일하고, 필드 목록이 어떻게 달라지는지 비교하라. 디버그 빌드와 릴리스 빌드를 각각 확인하라.

2. **`finally` 실행 시점을 전부 재현하라.** 28.5절의 `Iterator()` 메서드를 그대로 만들고, 다음 다섯 가지 소비 방식으로 각각 실행해서 출력을 기록하라. (a) `foreach`로 끝까지, (b) 첫 요소에서 `break`, (c) 루프 본문에서 예외 던지기, (d) `using`으로 감싼 수동 열거 1회, (e) `using` 없는 수동 열거 1회. 28.5절의 표와 결과가 일치하는지 대조하라.

3. **스레드 ID 트릭이 실패하게 만들어라.** 반복자를 호출해 `IEnumerable<T>`를 얻고, 그것을 `Task.Run` 안에서 열거하라. 할당 프로파일러(또는 `GC.GetAllocatedBytesForCurrentThread()`)로 같은 스레드에서 열거했을 때와 할당량을 비교하라. 차이가 상태 기계 객체 하나 크기인지 확인하라.

4. **인자 검증을 앞으로 당겨라.** 문자열 배열과 최소 길이를 받아 조건에 맞는 문자열만 돌려주는 반복자를 만들고, `null` 배열과 음수 길이에 대해 예외를 던지게 하라. 먼저 검증 코드를 반복자 안에 두고 예외가 언제 나는지 확인한 뒤, 지역 함수 해법으로 고쳐서 호출 즉시 예외가 나는 것을 확인하라. 두 버전의 스택 트레이스를 비교하라.

5. **파이프라인의 순회 횟수를 세라.** 28.7절의 `Unique`와 `Square`를 만들되, 소스 시퀀스를 "요소를 하나 내놓을 때마다 카운터를 올리는 반복자"로 만들어라. `Square(Unique(source))`를 한 번 `foreach` 했을 때 카운터가 소스 요소 개수와 같은지 확인하라. 그다음 결과를 두 번 `foreach` 하고 카운터가 두 배가 되는지 확인하라. `ToList()`를 끼워 넣으면 어떻게 달라지는가.

6. **`lock` 안의 `yield return`이 만드는 문제를 관찰하라.** 잠금을 잡고 `yield return` 하는 반복자를 만들고, 소비자가 첫 요소만 받은 뒤 `Dispose` 없이 열거를 포기하게 하라. 다른 스레드에서 같은 잠금을 잡으려 할 때 무슨 일이 일어나는지 확인하라. 그다음 `lock (gate) { return items.ToArray(); }` 형태로 고쳐서 문제가 사라지는지 확인하라.

7. **취소가 실제로 도달하는지 확인하라.** `IAsyncEnumerable<int>`를 반환하는 반복자를 만들되, `CancellationToken` 매개변수에 `[EnumeratorCancellation]`을 **붙이지 않은** 버전과 붙인 버전을 각각 만들어라. `await foreach (var x in src.WithCancellation(cts.Token))`로 소비하면서 1초 뒤 취소를 요청하라. 두 버전의 동작 차이를 기록하고, 왜 컴파일 경고가 하나도 없는지 설명하라.
