# 27장. 이벤트

> **이 장의 위치** — 26장에서 델리게이트를 "동작을 담는 값"으로 배웠다. 그 값을 필드에 담아 `public`으로 열면 콜백 구조가 완성되는 것처럼 보이지만, 실제로는 캡슐화가 통째로 뚫린다. `event` 키워드는 그 구멍을 막기 위해 언어가 델리게이트 위에 씌운 얇은 껍질이다. 이 장은 그 껍질이 정확히 무엇으로 컴파일되는지, 왜 그렇게 컴파일되어야 했는지, 그리고 그 껍질을 씌우고 나서도 남는 문제 — 스레드 경합, 수명 결합, 메모리 누수 — 를 끝까지 판다.
>
> **선수 지식** — 26장(델리게이트와 람다), 13장(클래스와 캡슐화), 14장(상속과 다형성), 18장(인터페이스), 23장(제네릭)
>
> **이 장에서 다루지 않는 것** — 델리게이트의 내부 구조, 멀티캐스트 체인의 예외 전파와 반환값 처리, 람다와 클로저는 26장에서 이미 다뤘다. 이벤트로 인한 런타임 결합을 API 설계 원칙으로 정리한 것은 78.10절이다. 파이널라이저와 객체 수명 일반론은 34장, 약한 참조 그 자체의 의미론은 34.5절·34.6절, 메모리 누수를 도구로 잡아내는 실무는 66장, GC 루트와 도달성 이론은 64.3절에 있다. `Interlocked`·`Volatile`·`lock`의 정확한 의미론은 48장에서 다룬다.

## 27.1 이벤트 선언과 컴파일러가 만드는 `add` / `remove`

### 델리게이트를 쓰다 보면 저절로 생기는 두 역할

델리게이트를 실무에서 쓰다 보면 두 개의 역할이 자연스럽게 나타난다.

- **발행자(broadcaster)** — 델리게이트 필드를 가진 타입. 언제 방송할지를 델리게이트를 호출해서 결정한다.
- **구독자(subscriber)** — 호출당할 메서드를 가진 쪽. `+=`와 `-=`로 언제 듣기 시작하고 언제 그만둘지를 결정한다.

이 구조의 핵심 성질은 **구독자가 다른 구독자를 모른다**는 것이다. 팩스 객체는 페이저 객체가 같은 알림을 듣고 있는지 알 필요가 없고, 알아서도 안 된다.

```text
   ┌──────────┐                        ┌──────────┐
   │  Fax #1  │                        │ Pager #1 │
   └────┬─────┘                        └────┬─────┘
        │ ① NewMail += FaxMsg               │ ② NewMail += SendMsgToPager
        ↓                                   ↓
   ┌────────────────────────────────────────────────┐
   │              MailManager                       │
   │   private EventHandler<NewMailEventArgs>       │
   │           NewMail;  ← 호출 목록                 │
   └────────────────────────────────────────────────┘
        ↑ ③ 새 메일 도착                    │
        │                                  │ ④ 등록된 모든 메서드에 통지
        └──────────────────────────────────┘
```

*발행자 하나, 구독자 여럿. 구독자는 서로를 모른다.*

**이벤트는 이 패턴을 언어가 형식화한 것이다.** 이벤트는 델리게이트가 제공하는 기능 중 발행자/구독자 모델에 필요한 **부분집합만** 밖으로 노출하는 구조물이다. 그리고 그 주목적은 하나로 요약된다 — **구독자끼리 서로 간섭하지 못하게 하는 것.**

### 델리게이트 필드를 그냥 열면 무엇이 뚫리는가

먼저 이벤트 없이 델리게이트 필드를 `public`으로 노출해 보자.

```csharp
public class Car
{
    public delegate void CarEngineHandler(string msgForCaller);

    // 이벤트가 아니라 그냥 public 필드다
    public CarEngineHandler ListOfHandlers;

    public void Accelerate(int delta)
    {
        if (ListOfHandlers != null)
            ListOfHandlers("Sorry, this car is dead...");
    }
}
```

호출자 쪽에서 무엇이 가능한지 보자.

```csharp
Car myCar = new Car();

myCar.ListOfHandlers = CallWhenExploded;   // ① 대입 — 기존 구독을 통째로 대체
myCar.Accelerate(10);

myCar.ListOfHandlers = CallHereToo;        // 앞의 구독자는 조용히 사라졌다
myCar.Accelerate(10);

myCar.ListOfHandlers = null;               // ② 전체 구독 제거
myCar.ListOfHandlers.Invoke("hee, hee...");  // ③ 남에게 마음대로 브로드캐스트
```

구독자가 서로 간섭할 수 있는 경로는 정확히 세 가지다.

| # | 구멍 | 코드 | 결과 |
|---|---|---|---|
| ① | **재대입으로 남을 대체** | `pub.Handlers = MyMethod;` | 앞서 등록한 모든 구독자가 조용히 제거된다 |
| ② | **`null` 대입으로 전체 제거** | `pub.Handlers = null;` | 구독 목록 전체가 사라진다 |
| ③ | **직접 호출로 남에게 방송** | `pub.Handlers.Invoke(...)` | 발행자가 아닌 코드가 가짜 알림을 뿌린다 |

세 가지 모두 **컴파일도 되고 예외도 안 난다.** 그래서 위험하다. 특히 ①은 `+=`를 써야 할 자리에 `=`를 오타로 쓰는 것만으로 발생하고, 증상은 "가끔 알림이 안 온다"로 나타난다.

> **⚠️ `=`와 `+=`를 오타로 바꿔 쓰는 사고**
>
> 델리게이트 필드가 열려 있으면 `pub.Handlers += Handle;`를 `pub.Handlers = Handle;`로 잘못 쓴 코드가 **아무 경고 없이 빌드된다.** 그리고 이 코드가 실행되는 순간, 그 시점까지 등록된 다른 모든 구독자가 사라진다. 원인 추적이 극도로 어려운 종류의 버그다. 이벤트로 선언하면 같은 오타가 컴파일 오류(CS0070)로 잡힌다.

### `event` 키워드

가장 쉬운 이벤트 선언은 델리게이트 멤버 앞에 `event`를 붙이는 것이다.

```csharp
// 델리게이트 정의
public delegate void PriceChangedHandler(decimal oldPrice, decimal newPrice);

public class Broadcaster
{
    // 이벤트 선언
    public event PriceChangedHandler PriceChanged;
}
```

이제 규칙이 바뀐다.

- `Broadcaster` **안의 코드**는 `PriceChanged`를 델리게이트처럼 온전히 다룰 수 있다. 호출도, `null` 비교도, 대입도 된다.
- `Broadcaster` **밖의 코드**는 `+=`와 `-=` **단 두 개의 연산만** 할 수 있다.

이게 전부다. 이벤트는 새로운 런타임 개념이 아니라, 델리게이트 필드에 대한 접근을 두 연산으로 제한하는 **접근 제어 장치**다.

> **📌 이벤트는 타입이 아니다**
>
> `event`는 타입이 아니라 **멤버 종류**다. 클래스가 가질 수 있는 멤버는 필드·메서드·프로퍼티·인덱서·생성자·연산자·중첩 타입 그리고 이벤트다. 이벤트의 *타입*은 언제나 델리게이트 타입이다. 델리게이트 타입이 아닌 것을 `event`로 선언하면 컴파일 오류(CS0066)다.

### 컴파일러는 한 줄을 세 가지로 번역한다

핵심은 여기다. 다음 한 줄을 보자.

```csharp
public event EventHandler<NewMailEventArgs> NewMail;
```

C# 컴파일러는 이 한 줄을 **세 가지 구성물**로 번역한다.

```text
      public event EventHandler<NewMailEventArgs> NewMail;
                            │
        ┌───────────────────┼───────────────────┐
        ↓                   ↓                   ↓
 ┌─────────────┐    ┌──────────────┐    ┌─────────────────┐
 │ ① private   │    │ ② public     │    │ ③ public        │
 │  델리게이트  │    │  add_NewMail │    │  remove_NewMail │
 │    필드     │    │   (value)    │    │    (value)      │
 └─────────────┘    └──────────────┘    └─────────────────┘
   항상 private       Delegate.Combine     Delegate.Remove
                       + CAS 루프            + CAS 루프
```

**① 항상 `private`인 델리게이트 필드**

```csharp
// 1. null로 초기화되는 PRIVATE 델리게이트 필드
private EventHandler<NewMailEventArgs> NewMail = null;
```

이 필드는 이 이벤트의 호출 목록의 머리(head)를 가리킨다. `null`이면 아무도 구독하지 않은 상태다.

**원래 소스가 `public event`였는데도 필드는 `private`다.** 이 점이 결정적이다. 필드가 `public`이었다면 바깥 코드가 필드 값을 갈아치워 등록된 델리게이트 전부를 날려버릴 수 있다 — 앞에서 본 구멍 ①·② 그 자체다. 필드를 `private`로 가둠으로써 그 경로가 막힌다.

**② `public add_Xxx` 메서드**

```csharp
// 2. PUBLIC add_Xxx 메서드 (Xxx는 이벤트 이름)
public void add_NewMail(EventHandler<NewMailEventArgs> value)
{
    // 루프와 CompareExchange 호출은 델리게이트를
    // 스레드 안전하게 추가하기 위한 장치다
    EventHandler<NewMailEventArgs> prevHandler;
    EventHandler<NewMailEventArgs> newMail = this.NewMail;
    do
    {
        prevHandler = newMail;
        EventHandler<NewMailEventArgs> newHandler =
            (EventHandler<NewMailEventArgs>)Delegate.Combine(prevHandler, value);
        newMail = Interlocked.CompareExchange<EventHandler<NewMailEventArgs>>(
            ref this.NewMail, newHandler, prevHandler);
    } while (newMail != prevHandler);
}
```

**③ `public remove_Xxx` 메서드**

```csharp
// 3. PUBLIC remove_Xxx 메서드
public void remove_NewMail(EventHandler<NewMailEventArgs> value)
{
    EventHandler<NewMailEventArgs> prevHandler;
    EventHandler<NewMailEventArgs> newMail = this.NewMail;
    do
    {
        prevHandler = newMail;
        EventHandler<NewMailEventArgs> newHandler =
            (EventHandler<NewMailEventArgs>)Delegate.Remove(prevHandler, value);
        newMail = Interlocked.CompareExchange<EventHandler<NewMailEventArgs>>(
            ref this.NewMail, newHandler, prevHandler);
    } while (newMail != prevHandler);
}
```

두 접근자의 구조는 동일하다. `Delegate.Combine` 대신 `Delegate.Remove`를 쓰는 것만 다르다.

### CAS 루프 — 잠금 없는 스레드 안전

`add_NewMail`의 do-while 루프는 **비교 후 교환(compare-and-swap, CAS)** 패턴이다. 흐름은 이렇다.

1. 현재 필드 값을 읽어 `prevHandler`에 담는다.
2. `Delegate.Combine(prevHandler, value)`로 **새로운** 델리게이트 체인을 만든다. 델리게이트는 불변이므로 기존 체인은 손대지 않고 새 인스턴스가 생긴다(26.4절).
3. `Interlocked.CompareExchange(ref field, newHandler, prevHandler)` — 필드가 아직 `prevHandler`와 같으면 `newHandler`로 바꾸고, 어느 쪽이든 **바꾸기 전의 값**을 반환한다.
4. 반환값이 `prevHandler`와 같으면 내가 성공한 것이다. 다르면 그사이 다른 스레드가 끼어든 것이므로 반환된 최신 값으로 처음부터 다시 시도한다.

`lock`을 쓰지 않으므로 **잠금 없는(lock-free)** 방식이다. 경합이 없으면 루프는 정확히 한 번 돈다. `Interlocked` 계열의 정확한 의미론과 이 "Interlocked Anything" 패턴의 일반형은 48.4절에서 다룬다.

> **📌 C# 3 컴파일러는 다르게 만들었다**
>
> C# 3 컴파일러까지는 필드형 이벤트의 `add`/`remove` 접근자에 `[MethodImpl(MethodImplOptions.Synchronized)]`를 붙여 접근자 전체를 잠갔다. 인스턴스 이벤트는 `this`를, 정적 이벤트는 타입 객체를 잠금 대상으로 삼는 셈이라 외부 코드가 같은 객체를 잠그면 교착에 빠질 수 있었다. C# 4부터 지금 본 CAS 루프로 바뀌었다. 오래된 코드베이스에서 IL을 뜯어볼 때 두 형태가 다르게 보이는 이유다.

> **⚠️ 이 스레드 안전은 "구독 목록 갱신"에만 적용된다**
>
> CAS 루프가 보장하는 것은 **구독 추가·제거가 유실되지 않는다**는 것뿐이다. 이벤트를 *발생시키는* 쪽은 아무 보호도 받지 않는다. 발생 시점의 경쟁 조건은 27.5절에서 따로 다룬다. 그리고 이 보호는 **컴파일러가 접근자를 만들어 줄 때만** 존재한다. 접근자를 직접 구현하면 이 로직이 통째로 사라진다(27.3절).

### 접근자의 접근성은 이벤트 선언을 따른다

```csharp
public    event EventHandler A;   // add_A / remove_A 는 public
protected event EventHandler B;   // add_B / remove_B 는 protected
internal  event EventHandler C;   // add_C / remove_C 는 internal
private   event EventHandler D;   // add_D / remove_D 는 private
```

즉 **이벤트의 접근성은 "누가 구독·해지할 수 있는가"를 정한다.** 델리게이트 필드에 직접 접근할 수 있는 것은 어떤 경우에도 그 타입 자신뿐이다.

> **⚠️ `add`/`remove`에 개별 접근성을 줄 수 없다**
>
> 프로퍼티는 `public int X { get; private set; }`처럼 접근자마다 접근성을 다르게 줄 수 있지만, **이벤트 접근자에는 한정자를 붙일 수 없다.** 시도하면 CS1609("Modifiers cannot be placed on event accessor declarations") 오류다. "구독은 아무나, 해지는 나만"같은 비대칭 설계는 언어가 지원하지 않는다. 필요하면 이벤트 대신 `Subscribe()` 메서드와 해지 토큰을 노출하는 설계로 가야 한다(27.7절).

### 메타데이터에 남는 `.event` 엔트리

컴파일러는 위 세 구성물 외에 **어셈블리 메타데이터에 이벤트 정의 엔트리**도 내보낸다. 이 엔트리는 플래그, 밑에 깔린 델리게이트 타입, 그리고 `add`/`remove` 접근자 메서드에 대한 참조를 담는다.

```il
.event class [System.Runtime]System.EventHandler`1<class CarEvents.CarEventArgs> AboutToBlow
{
  .addon instance void CarEvents.Car::add_AboutToBlow(
    class [System.Runtime]System.EventHandler`1<class CarEvents.CarEventArgs>)
  .removeon instance void CarEvents.Car::remove_AboutToBlow(
    class [System.Runtime]System.EventHandler`1<class CarEvents.CarEventArgs>)
} // end of event Car::AboutToBlow
```

접근자 본문의 IL을 보면 예상대로 `Delegate.Combine` / `Delegate.Remove` 호출이 들어 있다.

```il
.method public hidebysig specialname instance void add_AboutToBlow(
  class [System.Runtime]System.EventHandler`1<class CarEvents.CarEventArgs> 'value')
cil managed
{
  // ...
  IL_000b: call class [System.Runtime]System.Delegate
           [System.Runtime]System.Delegate::Combine(
             class [System.Runtime]System.Delegate,
             class [System.Runtime]System.Delegate)
  // ...
} // end of method Car::add_AboutToBlow
```

`remove_AboutToBlow`는 같은 자리에서 `Delegate::Remove`를 호출한다. `specialname` 플래그는 "이 메서드는 다른 구조물의 접근자다, 이름으로 직접 부르지 마라"는 표시다(56장에서 IL 읽기를 본격적으로 다룬다).

여기서 중요한 사실 하나.

> **📌 CLR은 `.event` 엔트리를 쓰지 않는다**
>
> `.event` 메타데이터는 **"이벤트"라는 추상 개념과 그 접근자 메서드를 연결 짓기 위해서만** 존재한다. 컴파일러와 각종 도구가 이 정보를 읽고, `System.Reflection.EventInfo`로도 조회할 수 있다. 하지만 **CLR 자신은 런타임에 이 메타데이터를 쓰지 않는다.** CLR이 필요로 하는 것은 접근자 메서드뿐이다. 이벤트를 지원하지 않는 언어에서도 `add_Xxx`/`remove_Xxx`를 직접 호출하면 똑같이 동작하는 이유가 이것이다. 모양이 예쁘지 않을 뿐이다.

리플렉션으로 확인해 보자.

```csharp
using System.Reflection;

EventInfo ei = typeof(Car).GetEvent("AboutToBlow");
Console.WriteLine(ei.EventHandlerType);        // System.EventHandler`1[CarEventArgs]
Console.WriteLine(ei.GetAddMethod().Name);     // add_AboutToBlow
Console.WriteLine(ei.GetRemoveMethod().Name);  // remove_AboutToBlow
Console.WriteLine(ei.GetRaiseMethod() is null); // True

// 리플렉션으로 구독하기
Car c = new Car();
EventHandler<CarEventArgs> h = (s, e) => Console.WriteLine(e.msg);
ei.AddEventHandler(c, h);
```

`GetRaiseMethod()`가 `null`인 것에 주목하자. IL에는 `.fire` 디렉티브로 "이벤트를 발생시키는 메서드"를 기록하는 자리가 있지만 **C# 컴파일러는 그것을 내보내지 않는다.** C#에서 이벤트를 발생시키는 것은 언제나 필드를 직접 호출하는 평범한 코드다.

### 클래스 안과 밖에서 이름이 다르게 해석된다

컴파일러가 하는 나머지 두 가지 일이 있다.

**둘째, 컴파일러는 선언 클래스 내부에서 `PriceChanged`를 `+=`/`-=` 이외의 방식으로 쓰는 모든 참조를 내부 델리게이트 필드로 리다이렉트한다.**

```csharp
public class Stock
{
    public event PriceChangedHandler PriceChanged;

    public decimal Price
    {
        get => price;
        set
        {
            if (price == value) return;      // 변한 게 없으면 나간다
            decimal oldPrice = price;
            price = value;
            if (PriceChanged != null)        // ← 필드 읽기로 번역된다
                PriceChanged(oldPrice, price); // ← 필드 호출로 번역된다
        }
    }
}
```

`PriceChanged != null`도, `PriceChanged(...)`도 접근자 호출이 아니라 **필드 접근**이다. 그래서 이 코드는 클래스 안에서만 쓸 수 있다.

**셋째, 컴파일러는 이벤트에 대한 `+=`/`-=` 연산을 `add`/`remove` 접근자 호출로 번역한다.**

```csharp
mm.NewMail += FaxMsg;
```

는 실제로 이렇게 번역된다.

```csharp
mm.add_NewMail(new EventHandler<NewMailEventArgs>(this.FaxMsg));
```

`-=`도 마찬가지다.

```csharp
mm.NewMail -= FaxMsg;
// → mm.remove_NewMail(new EventHandler<NewMailEventArgs>(this.FaxMsg));
```

> **⚠️ 이벤트의 `+=`는 "`+` 후 대입"의 축약이 아니다**
>
> 다른 모든 문맥에서 `x += y`는 `x = x + y`의 축약이다. **이벤트에 적용될 때만 다르다.** 이벤트의 `+=`는 `add` 접근자 호출로, `-=`는 `remove` 접근자 호출로 번역되는 **고유한 연산**이다. 읽기(`x`)도 대입(`x =`)도 일어나지 않는다. 그래서 바깥에서는 `+=`와 `-=`만 가능하고 `=`는 불가능한 것이다 — 애초에 대입이라는 개념이 없다.

바깥에서 다른 짓을 하려 들면 이렇게 막힌다.

```csharp
var mm = new MailManager();

mm.NewMail = FaxMsg;        // 오류 CS0070
mm.NewMail = null;          // 오류 CS0070
mm.NewMail(this, args);     // 오류 CS0070
if (mm.NewMail != null) { } // 오류 CS0070

mm.add_NewMail(FaxMsg);     // 오류 CS0571 — 접근자를 직접 부를 수 없다
```

| 오류/경고 | 상황 | 메시지 요지 |
|---|---|---|
| **CS0070** | 선언 클래스 밖에서 `+=`/`-=` 아닌 연산 | 이벤트는 `+=` 또는 `-=` 왼쪽에만 올 수 있다 |
| **CS0571** | `add_X`/`remove_X`를 직접 호출 | 연산자나 접근자를 명시적으로 호출할 수 없다 |
| **CS0066** | 델리게이트 아닌 타입을 `event`로 선언 | 이벤트는 델리게이트 타입이어야 한다 |
| **CS0071** | 명시적 인터페이스 이벤트를 필드형으로 | 이벤트 접근자 구문을 써야 한다 |
| **CS1609** | `add`/`remove`에 접근성 한정자 | 이벤트 접근자에 한정자를 놓을 수 없다 |
| **CS0067**(경고) | `private`/`internal` 이벤트를 한 번도 발생시키지 않음 | 이 이벤트는 사용되지 않았다 |

> **⚠️ CS0067을 무시하지 마라**
>
> "The event 'X' is never used"는 **선언만 해 놓고 한 번도 발생시키지 않는 이벤트**를 가리킨다. 구독자는 멀쩡히 `+=`로 붙는데 알림이 영원히 오지 않는다. 인터페이스 구현이나 리팩터링 중에 이벤트를 발생시키던 코드만 지워졌을 때 흔히 나온다. 조용한 무동작이라 테스트로도 잘 안 잡힌다.

### `-=`로 없는 것을 지우면 아무 일도 일어나지 않는다

```csharp
var mm = new MailManager();
mm.NewMail -= SomeMethodNeverAdded;   // 컴파일 통과, 실행도 통과
```

`remove_NewMail` 안의 `Delegate.Remove`는 목록을 훑어 **같은 대상 객체와 같은 메서드를 감싼** 델리게이트를 찾는다. 찾으면 제거하고, **못 찾으면 아무 일도 하지 않는다.** 예외도, 경고도, 반환값도 없다. 목록은 그대로다.

> **⚠️ 해지 실패는 조용히 지나간다 — 두 개의 흔한 원인**
>
> 1. **람다로 구독하고 다른 람다로 해지** — `x.E += (s, e) => Foo();` 뒤에 `x.E -= (s, e) => Foo();`를 쓰면 두 람다는 서로 다른 델리게이트다. 해지는 실패하고, 아무도 알려주지 않는다.
> 2. **다른 인스턴스의 같은 메서드** — 델리게이트 동등성은 (대상 객체, 메서드)의 쌍으로 판단한다. `a.Handle`로 구독하고 `b.Handle`로 해지하면 실패한다.
>
> 이 조용한 실패가 27.6절에서 다룰 메모리 누수의 1번 원인이다. 람다로 구독했으면 **델리게이트 인스턴스를 필드에 보관**해 두고 그것으로 해지해야 한다.

메서드 그룹으로 구독·해지하는 경우는 안전하다.

```csharp
mm.NewMail += FaxMsg;   // new EventHandler<...>(this.FaxMsg) 생성
mm.NewMail -= FaxMsg;   // 또 다른 인스턴스가 생기지만, (this, FaxMsg)가 같으므로 제거된다
```

두 번 만들어진 델리게이트 인스턴스는 서로 다른 객체지만 `Delegate.Remove`는 참조 동일성이 아니라 **대상과 메서드의 일치**로 판단하기 때문에 정상 동작한다.

> **📌 메서드 그룹 변환 캐싱 ※C# 11**
>
> C# 11부터 컴파일러는 메서드 그룹을 델리게이트로 변환할 때 만들어진 델리게이트 객체를 **캐시할 수 있게** 되었다. 같은 `+= FaxMsg`가 루프 안에서 반복 실행돼도 델리게이트 할당이 매번 일어나지 않을 수 있다는 뜻이다. 동작 의미론은 그대로다 — 어차피 `Delegate.Remove`는 참조가 아니라 (대상, 메서드) 쌍으로 비교하기 때문이다.

### 성능 — 구독이 늘어날 때 무슨 일이 생기나

`Delegate.Combine`은 기존 체인을 수정하지 않는다. 대신 **호출 목록 배열을 새로 할당해서 복사**한 새 멀티캐스트 델리게이트를 만든다(26.4절). 구독자가 N명일 때 N+1번째를 추가하는 비용은 O(N)이다. 따라서 N명을 순서대로 등록하는 총비용은 **O(N²)**이다.

| 상황 | 비용 |
|---|---|
| 구독자 0명 → 1명 | 델리게이트 인스턴스만 저장. 배열 할당 없음 |
| 구독자 N명 → N+1명 | 길이 N+1 배열 할당 + N개 복사 = O(N) |
| N명을 차례로 등록 | 총 O(N²), 배열 N개가 세대 0 쓰레기로 쌓인다 |
| 이벤트 발생 (N명) | 호출 목록을 순회하며 N번 호출. 인라인 안 됨 |
| CAS 경합 발생 | 루프 재시도 — 새 `Combine` 결과 배열이 또 버려진다 |

> **💡 수천 명이 구독하는 이벤트는 이벤트가 아니라 컬렉션으로 설계하라**
>
> 구독자가 수십 명을 넘어가고 등록·해지가 빈번하다면 이벤트는 잘못된 도구다. `List<IObserver>`나 `ConcurrentDictionary<Guid, Action<T>>`를 직접 관리하면 등록이 O(1)이 되고 해지 토큰도 자연스럽게 줄 수 있다. 이벤트는 "구독자 몇 명, 등록은 초기화 때 한 번"이 전형적인 사용처다.

## 27.2 표준 이벤트 패턴 — `EventHandler<T>`, `EventArgs`

.NET 라이브러리에서 정의된 이벤트는 거의 전부 하나의 표준 패턴을 따른다. 라이브러리 코드와 사용자 코드 사이의 일관성을 위해서다. 이 절은 그 패턴을 네 단계로 나눠 처음부터 끝까지 만든다.

### 4단계 요약

| 단계 | 무엇을 | 규칙 |
|---|---|---|
| **①** | `EventArgs` 파생 정보 클래스 | 읽기 전용 프로퍼티, 이름은 **담는 정보** 기준 + `EventArgs` 접미사 |
| **②** | `event` 멤버 선언 | 타입은 `EventHandler<TEventArgs>` |
| **③** | `protected virtual void OnXxx(e)` | 이름은 이벤트명 앞에 `On`. `sealed` 클래스면 `private` 비가상 |
| **④** | 입력을 이벤트로 번역하는 메서드 | 외부 입력을 받아 `EventArgs`를 만들고 `OnXxx`를 부른다 |

### 단계 ① — 정보를 담을 타입

이벤트가 발생할 때 발행자가 수신자에게 추가 정보를 전달하고 싶다면, 그 정보를 **자기 클래스로 캡슐화**한다. 관례상 `System.EventArgs`에서 파생하고, 클래스 이름은 `EventArgs`로 끝낸다.

```csharp
// 단계 #1: 이벤트 알림 수신자에게 전달할 추가 정보를 담는 타입
internal class NewMailEventArgs : EventArgs
{
    private readonly String m_from, m_to, m_subject;

    public NewMailEventArgs(String from, String to, String subject)
    {
        m_from = from; m_to = to; m_subject = subject;
    }

    public String From    { get { return m_from;    } }
    public String To      { get { return m_to;      } }
    public String Subject { get { return m_subject; } }
}
```

`private readonly` 필드 몇 개와 그것을 노출하는 **읽기 전용 프로퍼티**들 — 이게 전형적인 모양이다.

> **📌 이름은 이벤트가 아니라 정보를 기준으로**
>
> 재사용성 때문이다. `PriceChangedEventArgs`는 "가격이 바뀌었다"는 이벤트가 아니라 **"이전 가격과 새 가격"이라는 정보**의 이름이다. 그래서 `Stock.PriceChanged`뿐 아니라 `Commodity.PriceAdjusted`도 같은 타입을 쓸 수 있다. 이벤트 이름을 따라 `StockPriceChangedEventArgs`라고 지으면 재사용의 여지가 없어진다.

### `EventArgs`의 실제 구현

`EventArgs`는 .NET 클래스 라이브러리에 정의돼 있고, 구현은 이게 사실상 전부다.

```csharp
[ComVisible(true), Serializable]
public class EventArgs
{
    public static readonly EventArgs Empty = new EventArgs();
    public EventArgs() { }
}
```

(위 특성 두 개는 .NET Framework 시절의 선언이다. 현대 .NET에서도 `Empty` 정적 읽기 전용 필드와 기본 생성자뿐이라는 사실은 같다.)

내세울 게 하나도 없는 타입이다. **다른 타입이 파생할 기반 타입으로서만 존재한다.** 실제로 많은 이벤트는 전달할 추가 정보가 없다. 버튼이 "클릭됐다"고 알릴 때는 콜백 메서드가 호출된다는 사실 자체가 정보의 전부다.

추가 데이터가 없는 이벤트를 정의할 때는 **새 `EventArgs` 객체를 만들지 말고 `EventArgs.Empty`를 쓴다.**

```csharp
protected virtual void OnPriceChanged(EventArgs e) => PriceChanged?.Invoke(this, e);

public decimal Price
{
    get => price;
    set
    {
        if (price == value) return;
        price = value;
        OnPriceChanged(EventArgs.Empty);   // 불필요한 할당을 피한다
    }
}
```

> **💡 `EventArgs.Empty`는 정적 읽기 전용 인스턴스 하나다**
>
> 프로세스 전체에서 하나만 존재한다. 이벤트가 초당 수만 번 발생하는 코드에서 `new EventArgs()`를 쓰면 그만큼 세대 0 할당이 생긴다. 의미가 완전히 같으니 언제나 `EventArgs.Empty`를 쓴다. 반대로 **`EventArgs` 파생 타입은 절대 캐시해 재사용하지 마라** — 구독자가 그 객체를 붙잡아 두거나 수정할 수 있다(27.6절).

### 단계 ② — 이벤트 멤버 선언

```csharp
internal class MailManager
{
    // 단계 #2: 이벤트 멤버 선언
    public event EventHandler<NewMailEventArgs> NewMail;
    // ...
}
```

이벤트의 타입이 `EventHandler<NewMailEventArgs>`라는 것은 **모든 수신자가 이 델리게이트 타입의 원형에 맞는 콜백 메서드를 제공해야 한다**는 뜻이다. 제네릭 `System.EventHandler` 델리게이트는 이렇게 정의돼 있다.

```csharp
public delegate void EventHandler<TEventArgs>(Object sender, TEventArgs e);
```

따라서 콜백 메서드의 원형은 이래야 한다.

```csharp
void MethodName(Object sender, NewMailEventArgs e);
```

델리게이트를 고르거나 정의할 때의 규칙은 세 가지다.

1. **반환 타입이 `void`여야 한다.**
2. **인자를 정확히 둘 받는다.** 첫째는 `object` 타입 — 이벤트 발행자를 가리킨다. 둘째는 `EventArgs`의 파생 타입 — 전달할 추가 정보다.
3. **이름은 `EventHandler`로 끝난다.**

> **📌 제네릭이 없던 시절**
>
> C# 2.0 이전에는 제네릭이 없었으므로 이벤트마다 커스텀 델리게이트를 따로 써야 했다.
>
> ```csharp
> public delegate void PriceChangedHandler(object sender, PriceChangedEventArgs e);
> ```
>
> 역사적 이유로 .NET 라이브러리 안의 이벤트 대부분은 지금도 이런 방식으로 정의된 델리게이트를 쓴다. `System.EventHandler<TEventArgs>` 하나로 통일된 것은 그 뒤의 일이다. 새 코드에서는 커스텀 델리게이트를 정의할 이유가 거의 없다.

> **📌 `EventHandler<TEventArgs>`의 제약이 사라졌다**
>
> `EventHandler<TEventArgs>`는 원래 `where TEventArgs : EventArgs` 제약을 갖고 있었지만 .NET Framework 4.5에서 제약이 제거되었고 현대 .NET도 마찬가지다. 문법적으로는 `EventArgs`에서 파생하지 않은 타입도 쓸 수 있다는 뜻이다. 그렇다고 그렇게 쓰라는 뜻은 아니다 — 관례를 벗어나면 도구와 사람 모두 헷갈린다.

추가 정보가 없는 이벤트에는 비제네릭 `EventHandler`를 쓴다.

| 델리게이트 | 서명 | 언제 |
|---|---|---|
| `EventHandler` | `void (object? sender, EventArgs e)` | 추가 정보가 없을 때 |
| `EventHandler<TEventArgs>` | `void (object? sender, TEventArgs e)` | 추가 정보가 있을 때 (기본 선택) |
| 커스텀 `XxxHandler` | 규칙에 맞게 직접 정의 | 레거시 호환이 필요할 때만 |

### 왜 `sender`가 `object`인가

패턴을 처음 보면 누구나 같은 의문을 갖는다. `MailManager`만이 `NewMailEventArgs`를 담은 이벤트를 발생시킬 텐데, 이렇게 하면 더 낫지 않은가?

```csharp
void MethodName(MailManager sender, NewMailEventArgs e);   // 왜 안 되나?
```

이유는 두 가지다.

**첫째, 상속 때문이다.** `MailManager`를 기반 클래스로 `SmtpMailManager`가 파생되었다고 하자. 이 경우 콜백 메서드의 `sender`는 `MailManager`가 아니라 `SmtpMailManager`로 선언되는 게 맞다. 그런데 그럴 수 없다 — `SmtpMailManager`는 `NewMail` 이벤트를 **물려받았을 뿐** 다시 선언하지 않았기 때문이다. 결국 `SmtpMailManager`가 이벤트를 발생시킬 것을 기대하는 코드는 `sender`를 `SmtpMailManager`로 **캐스팅해야 한다.** 어차피 캐스팅이 필요하다면 애초에 `object`로 두는 편이 낫다.

**둘째, 유연성 때문이다.** `sender`가 `object`면 같은 델리게이트를 **서로 무관한 여러 타입이 재사용**할 수 있다. `MailManager`에서 파생하지 않은 `PopMailManager`도 `NewMailEventArgs`를 전달하는 이벤트를 정의할 때 같은 델리게이트를 쓸 수 있다.

수신 측에서 발행자를 실제로 쓰고 싶다면 안전하게 캐스팅한다.

```csharp
static void CarAboutToBlow(object sender, CarEventArgs e)
{
    // 캐스팅 전에 런타임 검사를 한다
    if (sender is Car c)
        Console.WriteLine($"Critical Message from {c.PetName}: {e.msg}");
}
```

### 왜 매개변수 이름이 `e`이고 왜 반환형이 `void`인가

**매개변수 이름 `e`** — 표준 패턴은 델리게이트 정의와 콜백 메서드 양쪽에서 `EventArgs` 파생 매개변수의 이름을 `e`로 지을 것을 요구한다. 이유는 **일관성 하나뿐이다.** 패턴을 배우고 구현하기 쉬워지고, 소스 코드를 생성하는 도구(Visual Studio 등)도 그 이름을 안다.

**반환형 `void`** — 이건 이유가 실질적이다. 이벤트를 발생시키면 **여러 개의 콜백 메서드가 호출될 수 있고, 그 모두의 반환값을 모을 방법이 없다.** 멀티캐스트 델리게이트를 호출하면 마지막 하나의 반환값만 남는 이유와 정확히 같다(26.4절). 반환 타입을 `void`로 두면 애초에 콜백이 값을 반환할 수 없게 된다.

> **⚠️ .NET 라이브러리 자신도 이 규칙을 어긴 사례가 있다**
>
> `ResolveEventHandler`는 마이크로소프트가 직접 정한 패턴을 따르지 않는다. **`Assembly` 타입의 객체를 반환**하기 때문이다.
>
> ```csharp
> public delegate Assembly? ResolveEventHandler(object? sender, ResolveEventArgs args);
> ```
>
> `AppDomain.AssemblyResolve` 같은 이벤트가 이 델리게이트를 쓴다. "찾지 못한 어셈블리를 대신 제공해 달라"는 요청이므로 반환값이 꼭 필요했던 것이다. 여러 구독자가 붙으면 어떻게 되는가? 실제로는 **`null`이 아닌 값을 처음 반환하는 구독자에서 멈추는** 식으로 런타임이 호출 목록을 직접 순회한다. 이런 처리는 이벤트 문법이 아니라 CLR/BCL의 특수 로직이다. 흉내 내지 마라 — 필요하다면 이벤트가 아니라 인터페이스나 델리게이트 인자를 쓰는 게 맞다(27.6절).

### 단계 ③ — `OnXxx` 메서드

관례상 클래스는 **`protected`이고 `virtual`인 메서드**를 정의한다. 이 메서드는 클래스 자신과 그 파생 클래스가 이벤트를 발생시키고자 할 때 호출한다. 매개변수는 하나 — 수신자에게 전달할 정보를 담은 `EventArgs` 파생 객체다.

```csharp
internal class MailManager
{
    // 단계 #3: 등록된 객체들에 이벤트가 일어났음을 알리는 메서드
    // 이 클래스가 sealed라면 이 메서드를 private 비가상으로 만든다
    protected virtual void OnNewMail(NewMailEventArgs e)
    {
        // 스레드 안전을 위해 델리게이트 필드 참조를 지역 변수에 복사한다
        EventHandler<NewMailEventArgs> temp = Volatile.Read(ref NewMail);

        // 이 이벤트에 등록한 메서드가 있으면 통지한다
        if (temp != null) temp(this, e);
    }
}
```

이름은 **이벤트 이름 앞에 `On`을 붙인 것**이어야 한다. `NewMail` 이벤트 → `OnNewMail`.

`Volatile.Read`가 왜 거기 있는지, 그리고 실무에서 `NewMail?.Invoke(this, e)`로 써도 되는 이유는 27.5절에서 통째로 다룬다. 지금은 "여기가 이벤트를 발생시키는 유일한 지점"이라는 사실이 중요하다.

> **💡 `sealed` 클래스에서는 `private` 비가상으로**
>
> `protected virtual`은 파생 클래스에게 확장점을 열어 주기 위한 것이다. 클래스가 `sealed`면 파생 클래스가 존재할 수 없으므로 `protected`도 `virtual`도 의미가 없다. `private void OnNewMail(...)`로 선언하는 게 맞다. 컴파일러가 가상 디스패치를 생략할 수 있어 아주 미세하게 유리하기도 하지만, 본질은 **의도를 정확히 표현하는 것**이다.

### 파생 클래스가 얻는 통제권

`MailManager`를 기반 타입으로 쓰는 클래스는 `OnNewMail`을 자유롭게 오버라이드할 수 있다. 이 능력이 파생 클래스에게 **이벤트 발생 자체에 대한 통제권**을 준다.

```csharp
internal class SmtpMailManager : MailManager
{
    protected override void OnNewMail(NewMailEventArgs e)
    {
        if (IsSpam(e.Subject)) return;   // 이벤트 전달을 막는다
        LogIncoming(e);                  // 기반 클래스보다 먼저 처리한다
        base.OnNewMail(e);               // 등록된 구독자들에게 통지한다
    }
}
```

보통 파생 타입은 기반 타입의 `OnNewMail`을 호출해 등록된 메서드들이 통지를 받게 한다. 그러나 위 예처럼 **이벤트가 전달되지 않게 결정할 수도 있다.**

> **⚠️ `base.OnXxx(e)`를 빠뜨리면 구독자가 전멸한다**
>
> `OnXxx`를 오버라이드하면서 `base` 호출을 잊으면 **등록된 이벤트 핸들러가 하나도 호출되지 않는다.** 예외도 경고도 없고, 구독자 쪽 코드는 멀쩡히 컴파일된다. 증상은 "이벤트가 안 온다"뿐이다. 오버라이드할 때 첫 줄 또는 마지막 줄에 `base` 호출을 넣는 습관을 들여야 한다. 27.8절에서 이 함정을 다시 만난다.

### 단계 ④ — 입력을 이벤트로 번역하는 메서드

클래스에는 **외부 입력을 받아 이벤트 발생으로 번역하는 메서드**가 있어야 한다.

```csharp
internal class MailManager
{
    // 단계 #4: 입력을 원하는 이벤트로 번역하는 메서드
    public void SimulateNewMail(String from, String to, String subject)
    {
        // 알림 수신자에게 전달할 정보를 담을 객체를 만든다
        NewMailEventArgs e = new NewMailEventArgs(from, to, subject);

        // 이벤트가 일어났음을 객체에 알리는 가상 메서드를 호출한다.
        // 아무도 이 메서드를 오버라이드하지 않았다면
        // 이벤트에 등록한 모든 객체에 통지된다
        OnNewMail(e);
    }
}
```

이 네 단계가 완성되면 발행자 쪽은 끝이다.

### 구독하는 타입 설계하기

이제 반대편이다. `Fax` 타입을 보자.

```csharp
internal sealed class Fax
{
    // MailManager 객체를 생성자로 전달받는다
    public Fax(MailManager mm)
    {
        // FaxMsg 콜백 메서드를 가리키는 EventHandler<NewMailEventArgs>
        // 델리게이트 인스턴스를 만들어 NewMail 이벤트에 등록한다
        mm.NewMail += FaxMsg;
    }

    // 새 메일이 도착하면 MailManager가 호출할 메서드
    private void FaxMsg(Object sender, NewMailEventArgs e)
    {
        // 'sender'는 MailManager 객체다. 되돌려 통신하고 싶을 때 쓴다.
        // 'e'는 MailManager가 주고 싶어 한 추가 정보다.
        Console.WriteLine("Faxing mail message:");
        Console.WriteLine("   From={0}, To={1}, Subject={2}", e.From, e.To, e.Subject);
    }

    // Fax 객체가 NewMail 이벤트 구독을 해지해
    // 더 이상 통지를 받지 않게 하는 메서드
    public void Unregister(MailManager mm)
    {
        mm.NewMail -= FaxMsg;
    }
}
```

애플리케이션 초기화 순서는 이렇다. `MailManager` 객체를 만들어 참조를 보관하고, `Fax` 객체를 만들면서 `MailManager` 참조를 넘긴다. `Fax` 생성자 안에서 `+=`로 구독이 이뤄진다.

**`Unregister` 메서드가 생성자와 거의 똑같이 생겼다는 점에 주목하자.** 차이는 `+=`가 `-=`로 바뀐 것뿐이다. 짝이 맞아야 한다는 사실을 코드 모양이 그대로 보여 준다.

### 완성 예제 — 주식 가격

지금까지의 네 단계를 하나로 합친 최소 예제다.

```csharp
using System;

Stock stock = new Stock("THPW");
stock.Price = 27.10M;

// PriceChanged 이벤트에 등록
stock.PriceChanged += stock_PriceChanged;
stock.Price = 31.59M;

void stock_PriceChanged(object sender, PriceChangedEventArgs e)
{
    if ((e.NewPrice - e.LastPrice) / e.LastPrice > 0.1M)
        Console.WriteLine("Alert, 10% stock price increase!");
}

public class PriceChangedEventArgs : EventArgs      // ①
{
    public readonly decimal LastPrice;
    public readonly decimal NewPrice;

    public PriceChangedEventArgs(decimal lastPrice, decimal newPrice)
    {
        LastPrice = lastPrice; NewPrice = newPrice;
    }
}

public class Stock
{
    string symbol;
    decimal price;

    public Stock(string symbol) => this.symbol = symbol;

    public event EventHandler<PriceChangedEventArgs> PriceChanged;   // ②

    protected virtual void OnPriceChanged(PriceChangedEventArgs e)   // ③
    {
        PriceChanged?.Invoke(this, e);
    }

    public decimal Price                                              // ④
    {
        get => price;
        set
        {
            if (price == value) return;
            decimal oldPrice = price;
            price = value;
            OnPriceChanged(new PriceChangedEventArgs(oldPrice, price));
        }
    }
}
```

첫 번째 대입(`stock.Price = 27.10M`)은 구독 전이므로 아무 일도 일어나지 않고, 두 번째 대입에서 알림이 발생한다.

> **📌 `if (price == value) return;` 한 줄의 중요성**
>
> 값이 실제로 바뀌지 않았으면 이벤트를 발생시키지 않는다. 이 가드가 없으면 같은 값을 다시 대입하는 코드가 불필요한 알림을 뿌리고, 그 알림을 받은 구독자가 다시 값을 쓰면 **무한 재귀**가 될 수 있다. UI 바인딩에서 `INotifyPropertyChanged`를 구현할 때 가장 흔한 사고다.

## 27.3 이벤트 접근자 직접 구현하기

이벤트의 접근자는 `+=`와 `-=`가 실제로 하는 일의 구현이다. 기본적으로는 컴파일러가 암묵적으로 만들어 주지만, **직접 구현해서 그 과정을 넘겨받을 수 있다.**

```csharp
private EventHandler priceChanged;          // private 델리게이트 필드를 직접 선언

public event EventHandler PriceChanged
{
    add    { priceChanged += value; }
    remove { priceChanged -= value; }
}
```

문법은 프로퍼티의 `get`/`set`과 비슷하다. `value`는 `+=`/`-=`의 오른쪽에 있던 델리게이트다. 접근자를 직접 쓰면 컴파일러는 **기본 필드와 접근자 로직을 만들지 않는다.**

> **⚠️ `add`와 `remove` 중 하나만 쓸 수 없다**
>
> 프로퍼티는 `get`만 있는 읽기 전용이 가능하지만, **이벤트는 `add`와 `remove` 둘 다 반드시 구현해야 한다.** 하나만 쓰면 컴파일 오류다. "구독은 되는데 해지는 안 되는 이벤트"는 언어가 허용하지 않는다.

> **⚠️ 접근자를 직접 쓰면 CAS 로직이 사라진다 — 스레드 안전은 직접 책임**
>
> 위 예제는 C#의 기본 접근자 구현과 **기능적으로 동일하지만, 스레드 안전성은 다르다.** 컴파일러가 만들어 주던 `Interlocked.CompareExchange` do-while 루프(27.1절)가 통째로 없어지고, `priceChanged += value`라는 평범한 읽기-수정-쓰기가 남는다. 두 스레드가 동시에 구독하면 한쪽 구독이 유실될 수 있다.
>
> 해결책은 두 가지다.
>
> ```csharp
> // (a) 접근자에 [MethodImpl(MethodImplOptions.Synchronized)]
> [MethodImpl(MethodImplOptions.Synchronized)]
> add { priceChanged += value; }
>
> // (b) 명시적 lock — 잠금 객체를 스스로 통제할 수 있어 더 낫다
> private readonly object gate = new object();
> add    { lock (gate) { priceChanged += value; } }
> remove { lock (gate) { priceChanged -= value; } }
> ```
>
> `MethodImplOptions.Synchronized`는 인스턴스 메서드에서 `this`를, 정적 메서드에서 타입 객체를 잠근다. 외부 코드가 같은 객체를 잠글 수 있으므로 (b)가 실무적으로 안전하다. 잠금 객체 선택 기준은 48.6절에서 다룬다.

접근자를 직접 구현할 이유는 크게 세 가지다.

### 이유 1 — 다른 클래스의 이벤트를 중계할 때

접근자가 **다른 객체가 발생시키는 이벤트로 가는 중계기(relay)** 역할만 하는 경우다.

```csharp
public sealed class DocumentView
{
    private readonly Document _model;

    public DocumentView(Document model) => _model = model;

    // 자체 저장소 없이 모델의 이벤트로 그대로 넘긴다
    public event EventHandler<ChangedEventArgs> Changed
    {
        add    { _model.Changed += value; }
        remove { _model.Changed -= value; }
    }
}
```

`DocumentView`는 델리게이트 필드를 하나도 갖지 않는다. 구독자는 `DocumentView.Changed`에 붙는다고 생각하지만 실제 등록은 `_model`에서 일어난다.

> **⚠️ 중계 이벤트의 수명 함정**
>
> 위 코드에서 구독자는 `DocumentView`가 아니라 **`_model`에 붙는다.** `DocumentView`가 사라져도 `_model`은 구독자를 계속 붙들고 있다. 구독자 입장에서는 "뷰를 버렸으니 구독도 사라졌겠지"라고 오해하기 딱 좋다. 중계 이벤트를 노출하는 타입은 `Dispose`에서 자신이 중계한 구독을 정리하거나, 아예 중계하지 말고 모델을 직접 노출하는 편이 낫다. 27.6절과 연결되는 문제다.

### 이유 2 — 이벤트는 많은데 구독자는 대부분 없을 때

`System.Windows.Forms.Control` 타입은 약 70개의 이벤트를 정의한다. 이 이벤트들을 전부 컴파일러가 암묵적으로 구현하게 두면, **모든 `Control` 객체가 이벤트 때문에만 델리게이트 필드 70개를 갖게 된다.** 대부분의 프로그래머는 그중 몇 개만 쓰는데도 말이다. `Control`에서 파생된 타입으로 만든 객체마다 엄청난 양의 메모리가 낭비된다. ASP.NET의 `System.Web.UI.Control`과 WPF의 `System.Windows.UIElement`도 사정이 같다.

해법은 **이벤트 식별자를 키로, 델리게이트 목록을 값으로 갖는 컬렉션(보통 딕셔너리) 하나**를 두는 것이다.

```text
  [ 필드형 이벤트 70개 ]              [ 딕셔너리 1개 ]

  Control 인스턴스                    Control 인스턴스
  ┌───────────────────┐               ┌───────────────────┐
  │ click     = null  │               │ events ──────────┐│
  │ mouseMove = null  │               └──────────────────┼┘
  │ keyDown   = null  │                                  ↓
  │ ...(67개 더)...   │                      ┌────────────────────────┐
  │ paint  = <핸들러> │                      │ {Paint: <핸들러 체인>} │
  └───────────────────┘                      └────────────────────────┘
   참조 70개 × 8바이트                        참조 1개 + 항목 1개
   = 560바이트 (대부분 null)                  = 실제 쓰는 만큼만
```

*구독자가 희소할 때 저장 공간 비교(64비트 기준의 개념도).*

새 객체가 생성되면 이 컬렉션은 비어 있다. 어떤 이벤트에 관심이 등록되면 컬렉션에서 그 이벤트 식별자를 찾는다. 있으면 새 델리게이트를 기존 목록에 결합하고, 없으면 식별자와 델리게이트를 새로 넣는다. 이벤트를 발생시켜야 할 때도 식별자를 찾아, 없으면 아무도 관심 없다는 뜻이므로 아무것도 하지 않는다.

**이 설계를 구현하는 것은 이벤트를 정의하는 타입 설계자의 책임이다.** 타입을 쓰는 개발자는 이벤트가 내부적으로 어떻게 구현됐는지 전혀 알 필요가 없다.

먼저 이벤트 집합을 표현하는 `EventSet` 클래스다.

```csharp
using System;
using System.Collections.Generic;
using System.Threading;

// EventSet을 쓸 때 타입 안전성과 유지보수성을 조금 더 주기 위한 클래스
public sealed class EventKey { }

public sealed class EventSet
{
    // EventKey -> Delegate 매핑을 유지하는 private 딕셔너리
    private readonly Dictionary<EventKey, Delegate> m_events =
        new Dictionary<EventKey, Delegate>();

    // EventKey -> Delegate 매핑이 없으면 추가하고,
    // 있으면 기존 EventKey에 델리게이트를 결합한다
    public void Add(EventKey eventKey, Delegate handler)
    {
        Monitor.Enter(m_events);
        Delegate d;
        m_events.TryGetValue(eventKey, out d);
        m_events[eventKey] = Delegate.Combine(d, handler);
        Monitor.Exit(m_events);
    }

    // EventKey에서 델리게이트를 제거하고(있다면),
    // 마지막 델리게이트가 제거되면 EventKey 매핑 자체를 제거한다
    public void Remove(EventKey eventKey, Delegate handler)
    {
        Monitor.Enter(m_events);
        // 집합에 없는 EventKey에서 제거를 시도해도
        // 예외가 나지 않도록 TryGetValue를 쓴다
        Delegate d;
        if (m_events.TryGetValue(eventKey, out d))
        {
            d = Delegate.Remove(d, handler);
            // 델리게이트가 남아 있으면 새 머리를 설정, 아니면 EventKey를 제거
            if (d != null) m_events[eventKey] = d;
            else m_events.Remove(eventKey);
        }
        Monitor.Exit(m_events);
    }

    // 지정된 EventKey에 대한 이벤트를 발생시킨다
    public void Raise(EventKey eventKey, Object sender, EventArgs e)
    {
        // EventKey가 집합에 없어도 예외를 던지지 않는다
        Delegate d;
        Monitor.Enter(m_events);
        m_events.TryGetValue(eventKey, out d);
        Monitor.Exit(m_events);

        if (d != null)
        {
            // 딕셔너리가 여러 종류의 델리게이트 타입을 담을 수 있으므로
            // 컴파일 시점에 타입 안전한 호출을 구성하는 것이 불가능하다.
            // 그래서 System.Delegate의 DynamicInvoke 메서드를 호출하고,
            // 콜백 메서드의 매개변수를 object 배열로 넘긴다.
            // DynamicInvoke는 내부적으로 매개변수의 타입 안전성을 검사한 뒤 호출한다.
            // 타입이 맞지 않으면 예외를 던진다.
            d.DynamicInvoke(new Object[] { sender, e });
        }
    }
}
```

이제 이 `EventSet`을 쓰는 클래스다. 각 이벤트가 명시적으로 구현되어, `add`는 콜백 델리게이트를 `EventSet` 객체에 저장하고 `remove`는 그것을 제거한다.

```csharp
using System;

// 이 이벤트를 위한 EventArgs 파생 타입
public class FooEventArgs : EventArgs { }

public class TypeWithLotsOfEvents
{
    // 컬렉션을 참조하는 private 인스턴스 필드.
    // 컬렉션이 이벤트/델리게이트 쌍의 집합을 관리한다.
    // 주의: EventSet은 .NET 라이브러리 타입이 아니라 직접 만든 타입이다.
    private readonly EventSet m_eventSet = new EventSet();

    // 파생 타입이 컬렉션에 접근할 수 있게 하는 protected 프로퍼티
    protected EventSet EventSet { get { return m_eventSet; } }

    #region Foo 이벤트 지원 코드 (이벤트를 추가할 때마다 이 패턴을 반복한다)

    // 이 이벤트를 식별할 정적 읽기 전용 객체를 만든다.
    // 각 객체는 자기만의 해시 코드를 가지므로
    // 객체의 컬렉션에서 이 이벤트의 델리게이트 연결 리스트를 찾는 키가 된다.
    protected static readonly EventKey s_fooEventKey = new EventKey();

    // 컬렉션에서 델리게이트를 추가/제거하는 이벤트 접근자를 정의한다.
    public event EventHandler<FooEventArgs> Foo
    {
        add    { m_eventSet.Add(s_fooEventKey, value); }
        remove { m_eventSet.Remove(s_fooEventKey, value); }
    }

    // 이 이벤트를 위한 protected virtual On 메서드
    protected virtual void OnFoo(FooEventArgs e)
    {
        m_eventSet.Raise(s_fooEventKey, this, e);
    }

    // 입력을 이 이벤트로 번역하는 메서드
    public void SimulateFoo() { OnFoo(new FooEventArgs()); }

    #endregion
}
```

**결정적인 점은 사용하는 쪽 코드가 아무것도 달라지지 않는다는 것이다.**

```csharp
public sealed class Program
{
    public static void Main()
    {
        TypeWithLotsOfEvents twle = new TypeWithLotsOfEvents();

        twle.Foo += HandleFooEvent;   // 평범한 구독 문법
        twle.SimulateFoo();           // 동작한다
    }

    private static void HandleFooEvent(object sender, FooEventArgs e)
    {
        Console.WriteLine("Handling Foo Event here...");
    }
}
```

`TypeWithLotsOfEvents`를 쓰는 코드는 이벤트가 컴파일러에 의해 암묵적으로 구현됐는지 개발자가 명시적으로 구현했는지 **구별할 수 없다.**

### .NET 라이브러리가 제공하는 같은 기능의 타입들

| 타입 | 어디에 | 특징 |
|---|---|---|
| `System.Windows.EventHandlersStore` | WPF (`WindowsBase`) | WPF 타입들이 희소한 이벤트 집합을 관리하는 데 내부적으로 쓴다 |
| `System.ComponentModel.EventHandlerList` | 범용 | 키(`object`)로 델리게이트를 찾는 목록. `Component.Events`가 이 타입 |
| 직접 만든 `EventSet` | — | 위 예제. 스레드 안전을 직접 넣을 수 있다 |
| `Dictionary<TKey, EventHandler<T>>` | — | 제네릭이라 캐스팅이 없다. 대신 코드가 늘어난다 |

> **⚠️ `EventHandlersStore`는 스레드 안전을 제공하지 않는다**
>
> .NET은 앞의 `EventSet`과 사실상 같은 일을 하는 `System.Windows.EventHandlersStore` 타입을 정의한다. WPF의 여러 타입이 희소한 이벤트 집합을 관리하는 데 내부적으로 쓰고 있고, 원한다면 직접 써도 된다. **`EventSet`과의 큰 차이는 `EventHandlersStore`가 이벤트에 접근하는 어떤 스레드 안전 수단도 제공하지 않는다는 점이다.** 필요하다면 그 컬렉션 주위에 스레드 안전 래퍼를 직접 구현해야 한다.

`EventHandlerList`를 쓴 로거 예제를 보자. 서브시스템 이름을 키로 삼는다.

```csharp
using System.ComponentModel;

public sealed class Logger
{
    private static EventHandlerList Handlers = new EventHandlerList();

    static public void AddLogger(string system, EventHandler<LoggerEventArgs> ev) =>
        Handlers.AddHandler(system, ev);

    static public void RemoveLogger(string system, EventHandler<LoggerEventArgs> ev) =>
        Handlers.RemoveHandler(system, ev);

    static public void AddMsg(string system, int priority, string msg)
    {
        if (!string.IsNullOrEmpty(system))
        {
            EventHandler<LoggerEventArgs> handler =
                Handlers[system] as EventHandler<LoggerEventArgs>;
            LoggerEventArgs args = new LoggerEventArgs(priority, msg);
            handler?.Invoke(null, args);

            // 빈 문자열은 "모든 메시지를 받는다"는 뜻이다
            handler = Handlers[""] as EventHandler<LoggerEventArgs>;
            handler?.Invoke(null, args);
        }
    }
}
```

클라이언트가 특정 서브시스템에 붙으면 그때 이벤트 객체가 만들어지고, 같은 서브시스템에 대한 이후 요청은 같은 이벤트 객체를 가져온다. **인터페이스에 이벤트가 아주 많은 클래스를 만든다면 이런 이벤트 핸들러 컬렉션을 고려할 만하다.** .NET 내부에서 `System.Windows.Forms.Control` 클래스가 이 방식의 더 복잡한 변형으로 모든 이벤트 필드의 복잡성을 감춘다.

> **📌 `EventHandlerList`에는 제네릭 버전이 없다**
>
> `EventHandlerList`는 제네릭 버전으로 갱신되지 않은 타입 중 하나다. 그래서 위 코드에는 다른 예제보다 훨씬 많은 캐스팅과 변환이 등장한다. `Dictionary<string, EventHandler<LoggerEventArgs>>`로 직접 만들면 캐스팅이 사라지는 대신 이벤트 맵을 다루는 코드가 늘어난다. 어느 쪽이 나은지는 미묘한 절충이다.

> **⚠️ `DynamicInvoke`는 리플렉션 기반이다 — 뜨거운 경로에 두지 마라**
>
> `EventSet.Raise`가 `DynamicInvoke`를 쓰는 이유는 딕셔너리가 여러 델리게이트 타입을 섞어 담기 때문이다. 대가는 크다. `DynamicInvoke`는 매개변수를 `object[]`로 박싱하고 런타임에 타입을 검사한 뒤 호출하므로 **직접 호출보다 수십~수백 배 느리다.** 이벤트가 초당 수천 번 발생하는 경로라면 델리게이트 타입을 고정하고 캐스팅해서 직접 호출하는 방식으로 바꿔야 한다.

### 이유 3 — 명시적 인터페이스 이벤트 구현

인터페이스가 선언한 이벤트를 **명시적으로** 구현할 때는 반드시 접근자 구문을 써야 한다.

```csharp
public interface IFoo { event EventHandler Ev; }

class Foo : IFoo
{
    private EventHandler ev;

    event EventHandler IFoo.Ev
    {
        add    { ev += value; }
        remove { ev -= value; }
    }
}
```

> **⚠️ 명시적 구현에는 필드형 문법을 쓸 수 없다**
>
> `event EventHandler IFoo.Ev;`처럼 쓰면 CS0071 오류다 — "명시적 인터페이스 이벤트 구현은 이벤트 접근자 구문을 써야 한다". 이유는 단순하다. 필드형 이벤트는 **이벤트 이름과 같은 이름의 필드**를 만드는데, `IFoo.Ev`라는 이름은 필드 이름으로 쓸 수 없기 때문이다. 암묵적 구현(`public event EventHandler Ev;`)이라면 필드형 문법이 그대로 된다.

## 27.4 이벤트 한정자 — `static`, `virtual`, `sealed`, `abstract`

메서드와 마찬가지로 이벤트도 `virtual`·`override`·`abstract`·`sealed`가 될 수 있고, `static`으로도 선언할 수 있다.

```csharp
public class Foo
{
    public static  event EventHandler<EventArgs> StaticEvent;
    public virtual event EventHandler<EventArgs> VirtualEvent;
}
```

핵심 규칙은 하나다. **컴파일러가 만드는 `add`/`remove` 접근자도 같은 한정자를 받는다.** 이벤트를 `static`으로 선언하면 `add_X`/`remove_X`도 `static` 메서드가 되고, `virtual`로 선언하면 접근자도 `virtual` 메서드가 된다.

| 한정자 | 접근자에 미치는 영향 | 필드형 문법 | 실무 판단 |
|---|---|---|---|
| (없음) | 인스턴스, 비가상 | 가능 | 기본. 대부분 이걸 쓴다 |
| `static` | 접근자도 `static`, 백킹 필드도 `static` | 가능 | 수명 문제가 심각하다 — 아래 참조 |
| `virtual` | 접근자도 `virtual` | 가능하지만 **쓰면 안 된다** | 27.8절에서 통째로 금지한다 |
| `override` | 접근자도 `override` | 가능하지만 **쓰면 안 된다** | 기반 클래스 필드를 가린다 |
| `abstract` | 접근자도 `abstract`, 본문 없음 | 필수(선언만) | 백킹 필드가 없다 |
| `sealed override` | 더 이상 오버라이드 불가 | — | 가상 이벤트를 끝낼 때 |
| `new` | 기반 이벤트를 가린다 | 가능 | 거의 언제나 실수다 |

### `static` 이벤트

```csharp
public static class ApplicationEvents
{
    public static event EventHandler<ThemeChangedEventArgs> ThemeChanged;

    internal static void RaiseThemeChanged(ThemeChangedEventArgs e)
        => ThemeChanged?.Invoke(null, e);
}
```

정적 이벤트는 `sender`에 넘길 인스턴스가 없으므로 관례상 `null`을 넘긴다.

> **⚠️ 정적 이벤트는 메모리 누수의 가장 흔한 원천이다**
>
> 정적 필드는 **GC 루트**다(64.3절). 정적 이벤트의 백킹 필드도 마찬가지다. 여기에 인스턴스 메서드를 등록하면 **그 인스턴스는 프로세스가 끝날 때까지 살아남는다.** 해지하지 않는 한 예외는 없다. 27.6절에서 이 시나리오를 자세히 본다. 정적 이벤트를 노출하는 API를 설계한다면 해지 의무를 문서 첫 줄에 써야 한다.

### `abstract` 이벤트

```csharp
public abstract class Shape
{
    public abstract event EventHandler<EventArgs> Invalidated;
}

public sealed class Circle : Shape
{
    public override event EventHandler<EventArgs> Invalidated;   // 필드형으로 구현
}
```

추상 이벤트는 선언만 있고 백킹 필드가 없다. 파생 클래스가 구현을 제공한다. 그런데 위 코드는 `Shape` 자신이 이벤트를 발생시킬 수 없다는 뜻이기도 하다 — 필드가 없으니 호출할 것이 없다. 그래서 추상 이벤트를 쓸 거라면 이벤트를 발생시키는 **추상 또는 가상 메서드**도 같이 두는 게 보통이다.

### 인터페이스 이벤트

인터페이스는 이벤트를 선언할 수 있다.

```csharp
public interface INotifyPropertyChanged
{
    event PropertyChangedEventHandler? PropertyChanged;
}
```

구현하는 쪽은 두 가지 선택지가 있다.

```csharp
// (a) 암묵적 구현 — 필드형 문법이 그대로 된다
public class Person : INotifyPropertyChanged
{
    public event PropertyChangedEventHandler? PropertyChanged;

    protected void OnPropertyChanged(string name)
        => PropertyChanged?.Invoke(this, new PropertyChangedEventArgs(name));
}

// (b) 명시적 구현 — 접근자 구문 필수 (27.3절)
public class Hidden : INotifyPropertyChanged
{
    private PropertyChangedEventHandler? _propertyChanged;

    event PropertyChangedEventHandler? INotifyPropertyChanged.PropertyChanged
    {
        add    { _propertyChanged += value; }
        remove { _propertyChanged -= value; }
    }
}
```

> **📌 `INotifyPropertyChanged`는 명시적으로 구현하지 마라**
>
> 데이터 바인딩 인프라는 인터페이스를 통해 접근하므로 명시적 구현도 동작한다. 하지만 XAML 디자이너, 단위 테스트, 로깅 코드가 `person.PropertyChanged += ...`로 직접 붙으려 할 때 컴파일이 안 된다. 이 인터페이스는 **숨길 이유가 없는** 인터페이스다. 암묵적으로 구현하는 것이 관례다.

> **📌 인터페이스의 기본 구현 ※C# 8**
>
> C# 8부터 인터페이스가 멤버의 기본 구현을 가질 수 있다. 이벤트도 예외가 아니어서 인터페이스 안에서 `add`/`remove` 본문을 제공할 수 있다. 다만 인터페이스는 인스턴스 필드를 가질 수 없으므로 **필드형 이벤트의 기본 구현은 불가능하다.** 정적 필드나 `ConditionalWeakTable`(34.9절) 같은 외부 저장소로 우회해야 하는데, 그렇게까지 할 값어치가 있는 경우는 드물다.

### `sealed`와 `new`

```csharp
public class Middle : Base
{
    // 여기서 가상 이벤트를 끝낸다 — 더 아래 파생에서 오버라이드 불가
    public sealed override event EventHandler Changed
    {
        add    { base.Changed += value; }
        remove { base.Changed -= value; }
    }
}
```

`new`로 기반 클래스의 이벤트를 가리는 것은 문법적으로 가능하지만 거의 언제나 사고다.

> **⚠️ `new` 이벤트는 기반 타입 참조로 접근할 때 다르게 동작한다**
>
> ```csharp
> Base b = new Derived();
> b.Changed += Handle;      // Base.Changed에 붙는다
> ((Derived)b).Changed += Handle;  // Derived.Changed에 붙는다
> ```
>
> 같은 객체인데 정적 타입에 따라 **다른 이벤트에 구독된다.** 알림이 오다 말다 하는 버그로 나타나고 원인 파악이 극도로 어렵다. 이벤트 이름을 가릴 일이 있으면 이름을 바꿔라.

## 27.5 스레드 안전한 이벤트 호출 — `?.Invoke` 관용구

이벤트를 발생시키는 코드는 겉보기에 사소하다. 실제로는 .NET이 처음 나온 뒤 두 번 개정된 문제다.

### v1 — 처음 권장된 방식

.NET Framework이 처음 출시됐을 때 권장된 방식은 이것이었다.

```csharp
// Version 1
protected virtual void OnNewMail(NewMailEventArgs e)
{
    if (NewMail != null) NewMail(this, e);
}
```

문제는 명확하다. 스레드가 `NewMail`이 `null`이 아님을 확인하고, **`NewMail`을 호출하기 직전에** 다른 스레드가 체인에서 델리게이트를 제거해 `NewMail`을 `null`로 만들 수 있다. 결과는 `NullReferenceException`이다.

```text
  스레드 A (발행)                    스레드 B (해지)
  ─────────────────                  ─────────────────
  if (NewMail != null)  ← true
                                     NewMail -= LastHandler;
                                     → 필드가 null이 된다
  NewMail(this, e);     ← NullReferenceException
```

*검사와 호출 사이의 창(window). 발생 확률은 낮지만 0이 아니다.*

> **⚠️ 재현되지 않는 버그의 전형**
>
> 이 경합은 "마지막 구독자가 해지되는 바로 그 순간에 이벤트가 발생"할 때만 터진다. 개발 환경에서는 몇 달 동안 한 번도 안 나오다가 부하가 걸린 운영 서버에서 하루에 몇 번씩 나온다. 스택 트레이스는 `OnNewMail` 안의 `NullReferenceException`만 보여 주므로 원인을 짐작하기 어렵다.

### v2 — 지역 변수로 복사

이 경합을 고치려고 많은 개발자가 다음과 같이 쓴다.

```csharp
// Version 2
protected virtual void OnNewMail(NewMailEventArgs e)
{
    EventHandler<NewMailEventArgs> temp = NewMail;
    if (temp != null) temp(this, e);
}
```

발상은 이렇다. `NewMail`에 대한 참조를 임시 변수 `temp`에 복사한다. `temp`는 **대입이 수행된 시점의 델리게이트 체인**을 가리킨다. 이제 `temp`를 `null`과 비교하고 `temp`를 호출하므로, 대입 이후 다른 스레드가 `NewMail`을 바꿔도 상관없다. **델리게이트는 불변이기 때문에** 이 기법은 이론상 동작한다(26.4절).

그런데 많은 개발자가 모르는 사실이 있다. **컴파일러가 지역 변수 `temp`를 통째로 없애 버리는 최적화를 할 수 있다.** 그렇게 되면 이 버전은 첫 번째 버전과 동일한 코드가 되고, `NullReferenceException`이 다시 가능해진다.

### v3 — `Volatile.Read`

정말로 고치려면 이렇게 써야 한다.

```csharp
// Version 3
protected virtual void OnNewMail(NewMailEventArgs e)
{
    EventHandler<NewMailEventArgs> temp = Volatile.Read(ref NewMail);
    if (temp != null) temp(this, e);
}
```

`Volatile.Read` 호출은 **`NewMail`을 그 호출 지점에서 읽도록 강제하고**, 참조가 실제로 `temp` 변수에 복사되게 만든다. 그 뒤 `temp`는 `null`이 아닐 때만 호출된다. `Volatile.Read`의 정확한 의미론은 48.3절에서 다룬다.

| 버전 | 코드 | 안전한가 | 비고 |
|---|---|---|---|
| v1 | `if (E != null) E(this, e);` | **아니다** | 검사와 호출 사이의 경합 |
| v2 | `var t = E; if (t != null) t(this, e);` | 이론상 그렇다 | 컴파일러가 `t`를 제거할 수 있다 |
| v2′ | `E?.Invoke(this, e);` | v2와 동일 | 문법 설탕. 가장 널리 쓰인다 |
| v3 | `var t = Volatile.Read(ref E); ...` | **그렇다** | 기술적으로 완전한 버전 |

### 그런데 실무에서는 v2를 써도 된다

마지막 버전이 최선이자 기술적으로 정확한 버전이지만, **실제로는 두 번째 버전을 써도 된다.** 이유는 다음과 같다.

JIT(just-in-time) 컴파일러는 이 패턴을 알고 있고, 지역 변수 `temp`를 최적화로 없애지 않는다. 더 구체적으로는, **마이크로소프트의 JIT 컴파일러들은 "힙 메모리에 대한 새로운 읽기를 도입하지 않는다"는 불변식을 지킨다.** 따라서 참조를 지역 변수에 캐시하면 힙 참조는 정확히 한 번만 접근된다.

> **⚠️ 이것은 문서화되지 않은 사실이다**
>
> 이 JIT 동작은 문서화된 보장이 아니다. 이론적으로는 바뀔 수 있고, 그래서 원칙적으로는 마지막 버전을 써야 한다. 현실적으로는 마이크로소프트의 JIT 컴파일러가 이 패턴을 깨는 변경을 받아들일 리 없다 — **너무 많은 애플리케이션이 깨지기 때문이다.** 게다가 이벤트는 주로 단일 스레드 시나리오(WPF, Windows Store 앱 등)에서 쓰이므로 애초에 스레드 안전이 문제가 되지 않는 경우가 많다.

C#의 널 조건부 연산자를 쓰면 임시 변수 없이 같은 기능을 얻는다.

```csharp
PriceChanged?.Invoke(this, e);
```

**스레드 안전하면서 간결하므로 이것이 이벤트를 발생시키는 가장 좋은 일반적 방법이다.** `?.`는 왼쪽 피연산자를 **한 번만 평가**하도록 언어가 보장하므로, 컴파일러는 필연적으로 v2와 같은 코드를 만든다.

```csharp
// PriceChanged?.Invoke(this, e); 가 만드는 코드의 의미
var __temp = PriceChanged;
if (__temp != null) __temp.Invoke(this, e);
```

> **⚠️ `?.Invoke`는 선언 클래스 안에서만 쓸 수 있다**
>
> `?.`는 필드 읽기를 필요로 하는데, 이벤트의 백킹 필드는 `private`다. 그래서 `publisher.SomeEvent?.Invoke(...)`처럼 바깥에서 쓰면 CS0070이다. 심지어 **파생 클래스에서도 안 된다.** 파생 클래스가 이벤트를 발생시켜야 한다면 기반 클래스가 `protected virtual OnXxx` 메서드를 제공해야 하는 이유가 이것이다(27.2절).

### 어느 버전을 써도 남는 문제

여기서 아주 중요한 점 하나. 이 스레드 경쟁 조건 때문에 **이미 이벤트의 델리게이트 체인에서 제거된 메서드가 호출되는 일도 가능하다.**

v2·v3 어느 쪽이든 `temp`는 **복사 시점의 스냅샷**이다. 복사 직후 어떤 구독자가 `-=`로 해지해도, 이미 복사된 체인에는 그 구독자가 남아 있으므로 그대로 호출된다.

```text
  스레드 A (발행)                     스레드 B (구독자)
  ────────────────────                ─────────────────────
  temp = Volatile.Read(ref E)
   → [H1, H2, H3] 스냅샷
                                      E -= H2;      (해지 성공)
                                      Dispose();    (자원 정리)
  temp(this, e)
   → H1 호출
   → H2 호출  ← 해지된 뒤인데도 호출된다!
   → H3 호출
```

> **⚠️ 해지했다고 "이제 안 불린다"고 가정하지 마라**
>
> 이벤트 핸들러는 **해지 이후에도 한 번 더 호출될 수 있다.** 이미 정리한 자원을 핸들러가 만지면 `ObjectDisposedException`이 나거나, 더 나쁘게는 조용히 잘못된 상태를 만든다.
>
> 방어는 핸들러 쪽에서 한다.
>
> ```csharp
> private void OnData(object? sender, DataEventArgs e)
> {
>     if (_disposed) return;    // 방어 가드
>     Process(e.Payload);
> }
> ```
>
> 그리고 이 문제는 단일 스레드에서도 발생한다 — 핸들러 A가 실행되는 도중에 핸들러 B를 해지해도, 이미 시작된 순회는 스냅샷을 따라 끝까지 간다.

### 확장 메서드로 감싸기

편의를 위해 이 스레드 안전 로직을 캡슐화한 **확장 메서드**를 정의할 수 있다.

```csharp
public static class EventArgExtensions
{
    public static void Raise<TEventArgs>(this TEventArgs e,
        Object sender, ref EventHandler<TEventArgs> eventDelegate)
    {
        // 스레드 안전을 위해 델리게이트 필드 참조를 지역 변수에 복사한다
        EventHandler<TEventArgs> temp = Volatile.Read(ref eventDelegate);

        // 이 이벤트에 등록한 메서드가 있으면 통지한다
        if (temp != null) temp(sender, e);
    }
}
```

이제 `OnNewMail`은 이렇게 다시 쓸 수 있다.

```csharp
protected virtual void OnNewMail(NewMailEventArgs e)
{
    e.Raise(this, ref NewMail);
}
```

> **📌 `ref`로 필드를 넘기는 것이 핵심이다**
>
> 확장 메서드가 `EventHandler<TEventArgs>`를 값으로 받으면 이미 호출 지점에서 필드를 읽어 버린 것이므로 `Volatile.Read`가 의미를 잃는다. `ref`로 **필드 자체를 넘겨야** 확장 메서드 안에서 휘발성 읽기를 할 수 있다. 그리고 `ref`로 넘길 수 있는 것은 필드형 이벤트의 백킹 필드뿐이므로, 이 확장 메서드는 선언 클래스 안에서만 호출할 수 있다.

> **💡 실무 선택 — `?.Invoke`를 기본으로**
>
> 세 가지를 저울질하면 결론은 단순하다.
>
> - 단일 스레드 UI 코드 → `PriceChanged?.Invoke(this, e);`
> - 다중 스레드에서 구독·해지가 실제로 오가는 라이브러리 → `?.Invoke`로도 충분하되, **핸들러 쪽 방어 가드**를 반드시 둔다
> - 극단적으로 보수적으로 가야 하는 코드 → `Volatile.Read` 또는 `Raise` 확장 메서드
>
> 어느 쪽이든 **"해지된 핸들러가 한 번 더 불릴 수 있다"**는 사실은 남는다. 이 사실을 계약으로 문서화하는 것이 코드로 막으려 애쓰는 것보다 낫다.

### 성능 — 이벤트 발생 비용

| 상황 | 무슨 일이 일어나나 |
|---|---|
| 구독자 0명 | 필드 읽기 + `null` 비교. 사실상 공짜 |
| 구독자 1명 | 델리게이트 호출 1회. 가상 호출 수준의 비용 |
| 구독자 N명 | 호출 목록 배열 순회 + N회 호출. **인라이닝되지 않는다** |
| `EventArgs` 새로 생성 | 이벤트마다 세대 0 할당 1건 |
| `?.Invoke` | 필드 읽기 1회 + 분기 1회. 추가 비용 없음 |

> **💡 이벤트 발생 자체보다 `EventArgs` 할당이 비싼 경우가 많다**
>
> 초당 수만 번 발생하는 진행률 보고 같은 이벤트에서는 `new ProgressEventArgs(...)`가 GC 압력의 주범이 된다. 대책은 세 가지다. (1) 추가 정보가 없으면 `EventArgs.Empty`를 쓴다. (2) 구독자가 없을 때는 `EventArgs`를 만들지도 않는다 — `if (Progress is null) return;`을 먼저 둔다. (3) 이벤트 발생 빈도를 줄인다(1%마다 한 번 등). 할당 줄이기의 일반론은 69장에 있다.

```csharp
protected virtual void OnProgress(int percent)
{
    var handler = Progress;
    if (handler is null) return;              // EventArgs를 만들기 전에 나간다
    handler(this, new ProgressEventArgs(percent));
}
```

## 27.6 이벤트가 만드는 런타임 결합과 메모리 누수

이벤트는 클래스를, 통지해야 할 타입들로부터 **완전히 분리해 주는 것처럼 보인다.** 밖으로 나가는 이벤트를 정의하고, 어떤 타입이든 구독하게 두고, 클래스 안에서는 이벤트를 발생시킨다. 클래스는 구독자를 전혀 모르고, 구독자가 될 클래스에 아무 제약도 걸지 않는다.

**그런데 그렇게 단순하지 않다.** 이벤트 기반 API에는 두 종류의 결합 문제가 있다.

### 문제 1 — 가변 `EventArgs` + 다중 구독자

일부 이벤트 인자 타입은 **클래스가 특정 동작을 하도록 지시하는 상태 플래그**를 담는다.

```csharp
public class WorkerEngine
{
    public event EventHandler<WorkerEventArgs> OnProgress;

    public void DoLotsOfStuff()
    {
        for (int i = 0; i < 100; i++)
        {
            SomeWork();
            WorkerEventArgs args = new WorkerEventArgs();
            args.Percent = i;
            OnProgress?.Invoke(this, args);
            if (args.Cancel)
                return;
        }
    }

    private void SomeWork()
    {
        // 생략
    }
}
```

이제 **그 이벤트의 모든 구독자가 서로 결합된다.** 한 이벤트에 구독자가 여럿이라고 하자. 어떤 구독자는 취소를 요청하고, 두 번째 구독자는 그 요청을 되돌릴 수 있다. 위 정의는 그런 일이 벌어지지 않는다는 보장을 전혀 주지 못한다.

```text
   OnProgress?.Invoke(this, args)
        │
        ├─→ 구독자 A:  args.Cancel = true;    "사용자가 취소 눌렀다"
        ├─→ 구독자 B:  (읽기만)
        └─→ 구독자 C:  args.Cancel = false;   "나는 계속하고 싶다"
                              ↓
                       마지막 값이 이긴다 → 취소가 무시된다
```

**구독자가 하나뿐임을 강제할 방법이 없고, 내가 마지막 구독자임을 보장할 방법도 없다.** 가변 이벤트 인자와 다중 구독자가 만나면 체인의 마지막 구독자가 앞의 모든 구독자를 뒤집을 수 있다.

### 해결 — 단조 변경만 허용하기

이벤트 인자를 수정해 **취소 플래그가 한 번 설정되면 어떤 구독자도 되돌릴 수 없게** 만들 수 있다.

```csharp
public class WorkerEventArgs : EventArgs
{
    public int Percent { get; set; }
    public bool Cancel { get; private set; }

    public void RequestCancel()
    {
        Cancel = true;
    }
}
```

`Cancel`의 setter를 `private`로 만들고 `RequestCancel()`이라는 **단방향 연산**만 노출한다. 이제 상태 변화는 `false → true` 한 방향으로만 일어난다. 순서에 관계없이 결과가 같아지므로 구독자 간의 결합이 끊긴다.

> **💡 가변 `EventArgs`는 언제나 단조 연산으로 설계하라**
>
> "플래그를 세운다", "취소를 요청한다", "처리했음을 표시한다"는 되돌릴 수 없어야 한다. `Handled = true`만 가능하고 `Handled = false`는 불가능해야 한다. 실제로 .NET의 `HandledEventArgs`나 `CancelEventArgs`는 이 규칙을 지키지 않는(둘 다 public setter를 가진) 오래된 설계이므로, 새로 만든다면 위 방식을 따르는 게 낫다.

### 구독자가 정확히 하나여야 한다면 이벤트를 쓰지 마라

공개 인터페이스를 바꾸는 방법이 여기서는 통했지만 모든 경우에 통하지는 않는다. **구독자가 정확히 하나임을 보장해야 한다면 다른 통신 수단을 골라야 한다.**

| 요구 | 도구 |
|---|---|
| 구독자 0~N명, 순서 무관, 반환값 없음 | **이벤트** |
| 구독자 정확히 1명, 반환값 필요 | **인터페이스** 정의 후 그 메서드 하나 호출 |
| 구독자 정확히 1명, 가벼운 콜백 | **델리게이트를 인자로** 받는다 |
| 구독자 1명인데 그쪽이 여럿에 뿌리고 싶다 | 그 판단은 구독자에게 맡긴다 |

예를 들어 인터페이스를 정의하고 그 메서드 하나를 호출하거나, 나갈 메서드를 정의하는 델리게이트를 요구할 수 있다. 그러면 **단일 구독자가 스스로** 다중 구독을 지원할지, 취소 요청의 의미론을 어떻게 조율할지를 결정한다. 델리게이트와 인터페이스 중 무엇을 고를지의 일반 기준은 26.7절에 있다.

### 문제 2 — 수명이 묶인다

런타임에는 이벤트 소스와 이벤트 구독자 사이에 **또 다른 형태의 결합**이 있다.

**이벤트 소스는 이벤트 구독자를 나타내는 델리게이트에 대한 참조를 붙들고 있다.** 델리게이트는 대상 객체를 강하게 참조한다(26.3절). 따라서 **이벤트 구독자의 객체 수명이 이벤트 소스의 객체 수명과 같아진다.**

```text
   [GC 루트]
      │
      ↓
 ┌──────────────────┐         ┌─────────────────────────┐
 │  Publisher       │  강참조  │ EventHandler 델리게이트  │
 │   (정적 필드 등) │ ───────→ │  Target ──────┐         │
 └──────────────────┘         └───────────────┼─────────┘
                                              │ 강참조
                                              ↓
                                    ┌──────────────────┐
                                    │  Subscriber      │
                                    │ (화면·뷰모델 등) │  ← 수집되지 않는다
                                    └──────────────────┘
```

*발행자가 살아 있는 한 구독자는 도달 가능하다. 도달 가능하면 수집되지 않는다(64.3절).*

이벤트 소스는 이벤트가 일어날 때마다 구독자의 핸들러를 호출한다. **그 동작은 이벤트 구독자가 정리(dispose)된 후에는 계속되면 안 된다.** `IDisposable`의 계약은 객체가 정리된 후에는 다른 메서드가 호출되어서는 안 된다는 것이다(33.2절).

결과적으로 **이벤트 구독자는 `Dispose()` 메서드의 일부로 이벤트 핸들러를 떼어내도록 정리 패턴 구현을 수정해야 한다.** 그러지 않으면 이벤트 소스 객체 안에 도달 가능한 델리게이트가 남아 있으므로 구독자 객체가 계속 살아 있게 된다.

```csharp
public sealed class DashboardView : IDisposable
{
    private readonly WorkerEngine _engine;
    private bool _disposed;

    public DashboardView(WorkerEngine engine)
    {
        _engine = engine;
        _engine.OnProgress += HandleProgress;    // 구독
    }

    private void HandleProgress(object? sender, WorkerEventArgs e)
    {
        if (_disposed) return;                   // 27.5절의 방어 가드
        UpdateBar(e.Percent);
    }

    public void Dispose()
    {
        if (_disposed) return;
        _engine.OnProgress -= HandleProgress;    // 반드시 해지
        _disposed = true;
    }
}
```

> **⚠️ 구독한 객체가 `IDisposable`이 아니면 누수는 확정된다**
>
> "이 클래스는 정리할 비관리 자원이 없으니 `IDisposable`이 필요 없다"는 판단은, **이벤트를 구독하는 순간 틀린 판단이 된다.** 이벤트 구독 자체가 정리해야 할 자원이다. 구독하는 타입은 거의 언제나 `IDisposable`이어야 한다.

### 전형적인 누수 — 장수명 발행자 + 단수명 구독자

가장 흔한 형태는 **정적 이벤트나 싱글턴이 발행자**이고, **화면·뷰모델·요청 스코프 객체가 구독자**인 경우다.

```csharp
public class Logger
{
    static Logger() { Singleton = new Logger(); }
    private Logger() { }

    public static Logger Singleton { get; }

    public event EventHandler<LoggerEventArgs> Log;

    public void AddMsg(int priority, string msg) =>
        Log?.Invoke(this, new LoggerEventArgs(priority, msg));
}
```

`Logger.Singleton`은 정적 프로퍼티다 — 프로세스가 끝날 때까지 산다. 여기에 화면 객체가 구독하면:

```csharp
public class OrderScreen
{
    public OrderScreen()
    {
        Logger.Singleton.Log += OnLog;   // 해지하지 않으면 이 화면은 영원히 산다
    }

    private void OnLog(object? sender, LoggerEventArgs e) => Append(e.Message);
}
```

화면을 100번 열고 닫으면 **`OrderScreen` 인스턴스 100개가 전부 힙에 남는다.** 각 화면이 붙들고 있는 컨트롤·데이터·이미지까지 통째로. 그리고 로그 메시지 하나가 발생할 때마다 죽은 화면 100개의 `OnLog`가 전부 호출된다. 메모리 누수이면서 동시에 성능 문제다.

> **⚠️ 이 누수는 `!gcroot`로 잡는다**
>
> WinDbg + SOS에서 `!gcroot <주소>`를 찍으면 루트 경로에 발행자의 정적 필드 → 델리게이트 → 구독자가 그대로 드러난다. dotMemory의 지배자 분석이나 `dotnet-gcdump`도 같은 경로를 보여 준다. 도구 사용법은 66.5절·66.9절, 이벤트 누수 시나리오는 66.11절에 정리돼 있다.

### 람다·클로저 구독이 더 위험한 이유

```csharp
// 위험: 해지할 참조가 없다
Logger.Singleton.Log += (s, e) => this.Append(e.Message);
```

이 코드는 세 가지가 동시에 나쁘다.

1. **해지할 델리게이트 참조가 없다.** 나중에 똑같은 모양의 람다를 써서 `-=`해도 다른 인스턴스이므로 제거되지 않는다(27.1절).
2. **클로저가 `this`를 캡처한다.** 컴파일러가 만든 디스플레이 클래스가 `this`를 필드로 붙들고, 그 디스플레이 클래스를 델리게이트가 붙든다(26.10절). 구독자 객체가 통째로 살아남는다.
3. **코드만 보면 문제가 안 보인다.** `+=` 한 줄뿐이므로 리뷰에서 잡히지 않는다.

해결은 델리게이트를 필드에 보관하는 것이다.

```csharp
public sealed class Screen : IDisposable
{
    private readonly EventHandler<LoggerEventArgs> _handler;

    public Screen()
    {
        _handler = (s, e) => Append(e.Message);   // 인스턴스를 보관한다
        Logger.Singleton.Log += _handler;
    }

    public void Dispose() => Logger.Singleton.Log -= _handler;
}
```

> **💡 람다로 이벤트를 구독할 때의 규칙**
>
> **"수명이 발행자보다 짧은 구독자는 절대 람다로 구독하지 않는다."** 짧은 스코프에서 발행자와 구독자의 수명이 같다고 확신할 수 있을 때만 람다를 쓴다. 확신이 안 서면 메서드 그룹으로 구독하고 `Dispose`에서 해지한다.

### 정리 — 정적 결합이 느슨해지는 대가

이벤트 기반 통신은 **타입 간의 정적 결합을 느슨하게 하지만, 그 대가로 이벤트 생성자와 이벤트 구독자 사이의 런타임 결합을 조인다.**

이벤트의 멀티캐스트 성질 때문에 **모든 구독자가 이벤트 소스에 응답하는 프로토콜에 합의해야 한다.** 그리고 이벤트 소스가 모든 구독자에 대한 참조를 붙드는 모델이므로, 모든 구독자는 다음 둘 중 하나여야 한다.

1. 자신이 정리되기를 원할 때 **이벤트 핸들러를 제거**하거나,
2. 단순히 **존재하기를 멈추거나** (즉 발행자와 수명이 같거나).

또한 **이벤트 소스도 자신이 사라져야 할 때 모든 이벤트 핸들러를 떼어내야 한다.** 이벤트를 쓰기로 하는 설계 결정에는 이 문제들을 반드시 고려해야 한다.

| 결합의 종류 | 이벤트를 쓰면 |
|---|---|
| 컴파일 시점 타입 의존성 | **느슨해진다** — 발행자는 구독자 타입을 모른다 |
| 구독자 간 프로토콜 | **조여진다** — 가변 `EventArgs`를 공유한다 |
| 객체 수명 | **조여진다** — 구독자 수명이 발행자에 묶인다 |
| 예외 전파 | **조여진다** — 한 핸들러의 예외가 뒤 핸들러를 막는다(26.4절) |
| 호출 스레드 | **조여진다** — 핸들러는 발행자의 스레드에서 실행된다 |

이 결합 문제를 API 설계 원칙의 층위에서 정리한 것이 78.10절이다.

> **⚠️ 이벤트 핸들러는 발행자의 스레드에서 실행된다**
>
> 백그라운드 스레드에서 발생한 이벤트의 핸들러도 그 백그라운드 스레드에서 실행된다. UI 컨트롤을 만지면 그 자리에서 예외가 난다. 구독자는 자기가 어느 스레드에서 불릴지 **알 수 없으므로**, 발행자는 문서로 명시해야 하고 UI 구독자는 디스패처로 마셜링해야 한다(45.8절).

## 27.7 약한 이벤트 패턴

27.6절의 수명 결합을 근본적으로 끊는 방법은 하나다. **발행자가 구독자를 약하게(weakly) 참조하는 것.**

약한 참조(`WeakReference<T>`)는 GC가 도달성을 판단할 때 세지 않는 참조다. 약한 참조만 남은 객체는 수집된다. 약한 참조 자체의 의미론(짧은/긴 약한 참조, 부활 문제)은 34.5절에서 다루므로, 여기서는 이벤트에 적용하는 방법만 본다.

### 왜 델리게이트를 통째로 약하게 참조하면 안 되는가

가장 순진한 접근은 이렇다.

```csharp
// 동작하지 않는다
private readonly List<WeakReference<EventHandler<T>>> _handlers = new();
```

문제는 **델리게이트 객체 자체를 아무도 붙들고 있지 않다는 것**이다. `pub.E += sub.Handle;`이 만드는 `EventHandler` 인스턴스는 그 자리에서 만들어져 발행자에게 넘어간다. 구독자는 그 델리게이트 객체에 대한 참조를 갖지 않는다. 델리게이트를 약하게 참조하면 **다음 GC에서 곧바로 수집되어 구독이 즉시 사라진다.**

### 대상만 약하게 참조하는 기법

정답은 **델리게이트를 분해해서 대상 객체만 약하게 붙드는 것**이다. 델리게이트는 `Target`(대상 객체)과 `Method`(메서드 정보)의 쌍이다(26.3절). 대상만 `WeakReference<object>`로 담고, 메서드 정보는 강하게 들고 있어도 된다 — `MethodInfo`는 타입에 속하는 메타데이터이지 인스턴스가 아니기 때문이다.

```csharp
using System.Reflection;

public sealed class WeakEventSource<TEventArgs>
{
    private readonly List<Entry> _entries = new();
    private readonly object _gate = new();

    private sealed class Entry
    {
        // 정적 메서드면 Target이 null이므로 약참조를 만들지 않는다
        public WeakReference<object>? TargetRef;
        public MethodInfo Method = null!;
        public Type HandlerType = null!;
    }

    public void Subscribe(EventHandler<TEventArgs> handler)
    {
        var entry = new Entry
        {
            TargetRef = handler.Target is null
                        ? null
                        : new WeakReference<object>(handler.Target),
            Method = handler.Method,
            HandlerType = handler.GetType()
        };
        lock (_gate) _entries.Add(entry);
    }

    public void Unsubscribe(EventHandler<TEventArgs> handler)
    {
        lock (_gate)
        {
            _entries.RemoveAll(e =>
                e.Method == handler.Method &&
                (e.TargetRef is null
                    ? handler.Target is null
                    : e.TargetRef.TryGetTarget(out var t) && ReferenceEquals(t, handler.Target)));
        }
    }

    public void Raise(object? sender, TEventArgs args)
    {
        Entry[] snapshot;
        lock (_gate) snapshot = _entries.ToArray();

        List<Entry>? dead = null;

        foreach (var entry in snapshot)
        {
            object? target = null;
            if (entry.TargetRef is not null && !entry.TargetRef.TryGetTarget(out target))
            {
                // 대상이 수집되었다 — 죽은 항목이다
                (dead ??= new List<Entry>()).Add(entry);
                continue;
            }

            // 대상 + 메서드로 델리게이트를 복원해 호출한다
            var d = (EventHandler<TEventArgs>)Delegate.CreateDelegate(
                        entry.HandlerType, target, entry.Method);
            d(sender, args);
        }

        if (dead is not null)
            lock (_gate) foreach (var e in dead) _entries.Remove(e);
    }
}
```

발행자는 이 타입을 필드로 두고 이벤트 접근자를 직접 구현해 중계한다(27.3절).

```csharp
public class Logger
{
    private readonly WeakEventSource<LoggerEventArgs> _log = new();

    public event EventHandler<LoggerEventArgs> Log
    {
        add    { _log.Subscribe(value); }
        remove { _log.Unsubscribe(value); }
    }

    public void AddMsg(int priority, string msg)
        => _log.Raise(this, new LoggerEventArgs(priority, msg));
}
```

구독자 쪽 코드는 평범한 `+=` 그대로다. 구독자가 수집되면 다음 `Raise` 때 항목이 정리된다.

> **⚠️ 약한 이벤트는 람다 구독을 더 위험하게 만든다**
>
> 약한 이벤트에 **클로저를 캡처한 람다**를 등록하면, 그 람다의 `Target`은 컴파일러가 만든 디스플레이 클래스 인스턴스다(26.10절). 이 인스턴스를 붙드는 다른 참조가 없으므로 **다음 GC에서 곧바로 수집되고 구독이 조용히 사라진다.** "가끔 알림이 안 온다"가 아니라 "GC가 도는 순간부터 영영 안 온다"가 된다. 약한 이벤트를 노출하는 API는 이 사실을 반드시 문서화해야 하고, 구독자는 델리게이트를 필드에 보관해야 한다.

> **⚠️ 죽은 항목 정리 시점의 함정**
>
> 위 구현은 `Raise`가 호출될 때만 죽은 항목을 정리한다. 이벤트가 오랫동안 발생하지 않으면 `Entry` 객체와 `WeakReference` 핸들이 계속 쌓인다. `WeakReference`는 GC 핸들 테이블에 항목을 만들므로 완전히 공짜가 아니다. 구독이 매우 잦은 시나리오라면 주기적인 청소 또는 등록 시 청소를 추가해야 한다.

### WPF의 `WeakEventManager`

WPF는 약한 이벤트를 인프라 수준에서 제공한다.

```csharp
// WPF 전용 — WindowsBase 어셈블리
WeakEventManager<Logger, LoggerEventArgs>
    .AddHandler(Logger.Singleton, nameof(Logger.Log), OnLog);

WeakEventManager<Logger, LoggerEventArgs>
    .RemoveHandler(Logger.Singleton, nameof(Logger.Log), OnLog);
```

WPF는 자주 쓰이는 이벤트에 대해 전용 관리자도 제공한다.

| 타입 | 대상 | 비고 |
|---|---|---|
| `WeakEventManager<TSource, TArgs>` | 임의의 이벤트 | 이벤트 이름을 문자열로 지정 |
| `PropertyChangedEventManager` | `INotifyPropertyChanged` | 바인딩 인프라가 내부적으로 사용 |
| `CollectionChangedEventManager` | `INotifyCollectionChanged` | 컬렉션 바인딩용 |
| `WeakEventManager` (추상 기반) | 직접 파생 | `IWeakEventListener`와 함께 쓴다 |

> **⚠️ `WeakEventManager`는 WPF 전용이다**
>
> `System.Windows.WeakEventManager` 계열은 WPF(`WindowsBase`)에 들어 있다. ASP.NET Core, 콘솔, 라이브러리 프로젝트에서는 쓸 수 없다. 범용 코드에서는 직접 구현하거나 명시적 해지 설계를 택해야 한다. 그리고 문자열로 이벤트 이름을 넘기는 API이므로 이름을 잘못 쓰면 **컴파일이 아니라 런타임에** 실패한다 — `nameof`를 쓰는 습관이 필수다.

### 그런데 약한 이벤트가 정답인 경우는 생각보다 적다

| 방식 | 장점 | 단점 |
|---|---|---|
| **명시적 해지** (`Dispose`) | 결정적, 예측 가능, 비용 0 | 짝을 맞춰야 한다. 잊으면 누수 |
| **`IDisposable` 구독 토큰** | 해지를 잊기 어렵다. `using`과 결합 | 이벤트 문법을 못 쓴다 |
| **약한 이벤트** | 잊어도 누수가 없다 | 비결정적, 람다 위험, GC 핸들 비용, 디버깅 난이도↑ |
| **수명 일치 설계** | 아무것도 안 해도 된다 | 항상 가능하지는 않다 |

구독 토큰 방식은 이렇게 생겼다.

```csharp
public interface IEventBus
{
    IDisposable Subscribe<T>(Action<T> handler);   // 해지 토큰을 돌려준다
}

// 사용하는 쪽
using IDisposable sub = bus.Subscribe<OrderPlaced>(OnOrderPlaced);
// 스코프를 벗어나면 자동 해지
```

> **💡 순서대로 시도할 것**
>
> 1. **구독자와 발행자의 수명을 일치시킬 수 있는가?** 가능하면 아무 문제도 없다.
> 2. **명시적 해지가 가능한가?** 구독자가 `IDisposable`이고 정리 시점이 명확하면 이걸로 끝이다.
> 3. **해지 시점을 호출자가 알 수 없는가?** 그때 `IDisposable` 구독 토큰을 준다. `IObservable<T>.Subscribe`가 `IDisposable`을 반환하는 이유가 정확히 이것이다.
> 4. **그래도 안 되면** 약한 이벤트를 쓴다.
>
> 약한 이벤트를 1번으로 꺼내 드는 것은 설계 실패를 도구로 덮는 것이다. 비결정적 동작이 들어오고, "구독했는데 알림이 안 온다"는 새로운 종류의 버그가 생긴다.

> **📌 `ConditionalWeakTable`이라는 다른 접근**
>
> 발행자와 구독자를 연결하되 어느 쪽도 상대를 살려 두지 않아야 한다면 `ConditionalWeakTable<TKey, TValue>`가 유용하다. 키를 약하게 참조하고, 값이 키를 참조해도 순환이 만들어지지 않도록 런타임이 처리한다. 자세한 것은 34.9절에 있다.

## 27.8 비가상 이벤트만 선언하라, 이벤트 핸들러 대신 오버라이드를 쓸 자리

이 절은 두 개의 독립된 지침을 다룬다. 하나는 이벤트를 **선언하는** 쪽, 하나는 이벤트를 **소비하는** 쪽이다.

### 지침 1 — 이벤트를 `virtual`로 선언하지 마라

C#의 다른 클래스 멤버처럼 이벤트도 `virtual`로 선언할 수 있다. 다른 언어 요소를 `virtual`로 만드는 것처럼 간단하리라 생각하기 쉽다. 그렇지 않다. **이벤트를 필드형 문법으로도, `add`/`remove` 문법으로도 선언할 수 있기 때문에** 기반 클래스와 파생 클래스에 걸쳐 기대와 다르게 동작하는 이벤트 핸들러를 만들기가 놀랄 만큼 쉽다. 더 나쁘게는 진단하기 어려운 충돌까지 만들 수 있다.

앞 절의 작업 엔진을 기반 클래스로 바꿔 보자.

```csharp
public abstract class WorkerEngineBase
{
    public virtual event EventHandler<WorkerEventArgs> OnProgress;

    public void DoLotsOfStuff()
    {
        for (int i = 0; i < 100; i++)
        {
            SomeWork();
            WorkerEventArgs args = new WorkerEventArgs();
            args.Percent = i;
            OnProgress?.Invoke(this, args);
            if (args.Cancel)
                return;
        }
    }

    protected abstract void SomeWork();
}
```

컴파일러는 `private` 백킹 필드와 `public` `add`/`remove` 메서드를 만든다.

**그 `private` 백킹 필드는 컴파일러가 만든 것이므로 직접 접근하는 코드를 작성할 수 없다.** 공개적으로 접근 가능한 이벤트 선언을 통해서만 다룰 수 있다. 이 제약은 당연히 파생 클래스의 이벤트에도 적용된다. 기반 클래스의 `private` 백킹 필드에 접근하는 코드를 손으로 쓸 수 없다. **그러나 컴파일러는 자기가 만든 필드에 접근할 수 있으므로**, 이벤트를 올바른 방식으로 오버라이드하는 코드를 생성할 수는 있다.

먼저 이벤트를 오버라이드하지 않는 파생 클래스는 정상 동작한다.

```csharp
public class WorkerEngineDerived : WorkerEngineBase
{
    protected override void SomeWork()
    {
        // 생략
    }
}
```

**이제 `override` 이벤트를 추가하면 코드가 깨진다.**

```csharp
public class WorkerEngineDerived : WorkerEngineBase
{
    protected override void SomeWork()
    {
        Thread.Sleep(50);
    }

    // 깨졌다. 기반 클래스의 private 이벤트 필드를 가린다
    public override event EventHandler<WorkerEventArgs> OnProgress;
}
```

무슨 일이 일어나는가.

```text
   사용자 코드:  derived.OnProgress += Handle;
                        ↓ (파생 클래스의 add 접근자)
   ┌──────────────────────────────────────┐
   │ WorkerEngineDerived                  │
   │   private OnProgress = [Handle]  ←── 구독자는 전부 여기 붙는다
   └──────────────────────────────────────┘

   기반 클래스 코드:  OnProgress?.Invoke(this, args);
                        ↓ (기반 클래스의 필드 읽기)
   ┌──────────────────────────────────────┐
   │ WorkerEngineBase                     │
   │   private OnProgress = null      ←── 영원히 비어 있다
   └──────────────────────────────────────┘
                        ↓
                   아무 일도 일어나지 않는다
```

오버라이드된 이벤트 선언은 **사용자 코드가 이벤트를 구독할 때 기반 클래스의 숨겨진 백킹 필드가 대입되지 않는다**는 뜻이다. 사용자 코드는 파생 클래스의 이벤트를 구독하는데, 파생 클래스에는 그 이벤트를 발생시키는 코드가 없다.

따라서 **기반 클래스가 필드형 이벤트를 쓰면, 그 이벤트 정의를 오버라이드하는 것은 기반 클래스에 정의된 이벤트 필드를 가리게 된다.** 이벤트를 발생시키는 기반 클래스의 코드는 아무것도 하지 않는다. 모든 구독자는 파생 클래스에 붙었다. **파생 클래스가 필드형 이벤트를 쓰든 프로퍼티형(접근자) 이벤트를 쓰든 상관없다.** 파생 클래스 버전이 기반 클래스 이벤트를 가린다. 기반 클래스 코드에서 발생시킨 이벤트는 어떤 구독자의 코드도 호출하지 않는다.

> **⚠️ 이 버그는 컴파일도 되고, 예외도 없고, 로그도 없다**
>
> 증상은 **"진행률 표시줄이 움직이지 않는다"** 하나뿐이다. 구독 코드는 정상 실행되고, `+=`도 성공하고, `DoLotsOfStuff()`도 정상 종료한다. 그저 핸들러가 한 번도 호출되지 않을 뿐이다. 디버거로 `OnProgress`에 중단점을 걸면 파생 클래스의 필드에는 핸들러가 들어 있는 것이 보이므로 더 헷갈린다.

### 해결 (a) — 가상 이벤트에는 절대 필드형 문법을 쓰지 마라

파생 클래스가 `add`/`remove` 접근자를 쓰면 동작한다.

```csharp
public class WorkerEngineDerived : WorkerEngineBase
{
    protected override void SomeWork()
    {
        Thread.Sleep(50);
    }

    public override event EventHandler<WorkerEventArgs> OnProgress
    {
        add    { base.OnProgress += value; }
        remove { base.OnProgress -= value; }
    }

    // 중요: 기반 클래스만 이벤트를 발생시킬 수 있다.
    // 파생 클래스는 이벤트를 직접 발생시킬 수 없다.
    // 파생 클래스가 이벤트를 발생시켜야 한다면
    // 기반 클래스가 이벤트를 발생시키는 protected 메서드를 제공해야 한다.
}
```

기반 클래스가 프로퍼티형(접근자) 이벤트를 선언하는 방식으로도 이 관용구를 동작하게 만들 수 있다. **기반 클래스가 `protected` 이벤트 필드를 갖도록 수정하고, 파생 클래스의 접근자가 그 기반 클래스 변수를 조작하게 하는 것이다.**

```csharp
using System.Runtime.CompilerServices;

public abstract class WorkerEngineBase
{
    protected EventHandler<WorkerEventArgs> progressEvent;

    public virtual event EventHandler<WorkerEventArgs> OnProgress
    {
        [MethodImpl(MethodImplOptions.Synchronized)]
        add
        {
            progressEvent += value;
        }
        [MethodImpl(MethodImplOptions.Synchronized)]
        remove
        {
            progressEvent -= value;
        }
    }

    public void DoLotsOfStuff()
    {
        for (int i = 0; i < 100; i++)
        {
            SomeWork();
            WorkerEventArgs args = new WorkerEventArgs();
            args.Percent = i;
            progressEvent?.Invoke(this, args);
            if (args.Cancel)
                return;
        }
    }

    protected abstract void SomeWork();
}

public class WorkerEngineDerived : WorkerEngineBase
{
    protected override void SomeWork()
    {
        // 생략
    }

    // 동작한다. 기반 클래스의 이벤트 필드에 접근한다.
    public override event EventHandler<WorkerEventArgs> OnProgress
    {
        [MethodImpl(MethodImplOptions.Synchronized)]
        add
        {
            progressEvent += value;
        }
        [MethodImpl(MethodImplOptions.Synchronized)]
        remove
        {
            progressEvent -= value;
        }
    }
}
```

`[MethodImpl(MethodImplOptions.Synchronized)]`가 붙은 이유는 27.3절에서 본 그대로다 — **접근자를 직접 쓰는 순간 컴파일러의 CAS 로직이 사라지므로 스레드 안전을 직접 책임져야 한다.**

그런데 이 코드도 여전히 파생 클래스 구현에 제약을 건다. **파생 클래스는 필드형 이벤트 문법을 쓸 수 없다.**

```csharp
public class WorkerEngineDerived : WorkerEngineBase
{
    protected override void SomeWork()
    {
        // 생략
    }

    // 깨졌다. private 필드가 기반 클래스를 가린다
    public override event EventHandler<WorkerEventArgs> OnProgress;
}
```

### 해결 (b) — 이벤트를 올리는 가상 메서드를 둔다

두 번째 해법은 **가상 이벤트 정의를 만들 때마다 이벤트를 발생시키는 가상 메서드도 함께 만드는 것**이다. 파생 클래스는 가상 이벤트 정의뿐 아니라 이벤트 발생 메서드도 오버라이드해야 한다.

```csharp
public abstract class WorkerEngineBase
{
    public virtual event EventHandler<WorkerEventArgs> OnProgress;

    protected virtual WorkerEventArgs RaiseEvent(WorkerEventArgs args)
    {
        OnProgress?.Invoke(this, args);
        return args;
    }

    public void DoLotsOfStuff()
    {
        for (int i = 0; i < 100; i++)
        {
            SomeWork();
            WorkerEventArgs args = new WorkerEventArgs();
            args.Percent = i;
            RaiseEvent(args);
            if (args.Cancel)
                return;
        }
    }

    protected abstract void SomeWork();
}

public class WorkerEngineDerived : WorkerEngineBase
{
    protected override void SomeWork()
    {
        Thread.Sleep(50);
    }

    public override event EventHandler<WorkerEventArgs> OnProgress;

    protected override WorkerEventArgs RaiseEvent(WorkerEventArgs args)
    {
        OnProgress?.Invoke(this, args);
        return args;
    }
}
```

이 코드를 보면 곧바로 드러나는 사실이 있다. **이벤트를 `virtual`로 선언해서 얻는 것이 사실상 없다.** 파생 클래스에서 이벤트 발생 동작을 커스터마이즈하는 데 필요한 것은 **이벤트를 발생시키는 가상 메서드의 존재**가 전부다. 이벤트 자체를 오버라이드해서 할 수 있는 일 중에, 이벤트를 발생시키는 메서드를 오버라이드해서 못 할 일은 없다. 델리게이트를 손으로 순회할 수도 있고, 각 구독자가 이벤트 인자를 어떻게 바꾸는지에 대해 다른 의미론을 제공할 수도 있고, 아무것도 발생시키지 않아 이벤트를 억제할 수도 있다.

> **💡 결론 — 이벤트는 비가상으로, `protected virtual On` 메서드만 열어라**
>
> 언뜻 보면 이벤트는 클래스와 그 클래스와 통신하려는 코드 사이에 느슨한 결합 인터페이스를 제공하는 것처럼 보인다. **가상 이벤트를 만들었다면 이벤트 소스와 구독 클래스 사이에 컴파일 시점 결합과 런타임 결합이 둘 다 생긴다.** 가상 이벤트를 동작하게 만들려고 추가해야 하는 수정들은 대개 애초에 가상 이벤트가 필요 없었음을 뜻한다.
>
> 표준 이벤트 패턴(27.2절)이 처음부터 `protected virtual void OnXxx(e)`를 지정한 이유가 바로 이것이다. **이벤트는 비가상으로 두고, 확장점은 `On` 메서드 하나로 낸다.**

| 무엇을 | 어떻게 |
|---|---|
| 이벤트 선언 | **비가상**. 필드형 문법 그대로 |
| 파생의 확장점 | `protected virtual void OnXxx(TEventArgs e)` |
| 파생이 알림 차단 | `OnXxx`를 오버라이드하고 `base` 호출을 생략 |
| 파생이 전처리/후처리 | `base.OnXxx(e)` 앞뒤에 코드를 넣는다 |
| 파생이 순서를 통제 | `OnXxx`에서 `GetInvocationList()`를 직접 순회(26.4절) |

### 지침 2 — 파생 클래스 안에서는 오버라이드를 쓰라

많은 .NET 클래스는 시스템 이벤트를 처리하는 **두 가지 방법**을 제공한다. 이벤트 핸들러를 붙이거나, 기반 클래스의 가상 함수를 오버라이드하거나. 왜 같은 일을 하는 두 가지 방법이 있는가? **상황이 다르면 방법도 달라야 하기 때문이다.**

원칙은 이렇다. **파생 클래스 안에서는 항상 가상 함수를 오버라이드하라. 이벤트 핸들러 사용은 무관한 객체의 이벤트에 반응할 때로 제한하라.**

마우스 다운 이벤트에 반응해야 하는 WPF 애플리케이션을 쓴다고 하자. 폼 클래스에서 `OnMouseDown()` 메서드를 오버라이드할 수 있다.

```csharp
public partial class MainWindow : Window
{
    public MainWindow()
    {
        InitializeComponent();
    }

    protected override void OnMouseDown(MouseButtonEventArgs e)
    {
        DoMouseThings(e);
        base.OnMouseDown(e);
    }
}
```

또는 이벤트 핸들러를 붙일 수도 있다(C#과 XAML 둘 다 필요하다).

```xml
<!-- XAML 기술 -->
<Window x:Class="WpfApp1.MainWindow"
        xmlns:local="clr-namespace:WpfApp1"
        mc:Ignorable="d"
        Title="MainWindow" Height="350" Width="525"
        MouseDown="OnMouseDownHandler">
  <Grid>
  </Grid>
</Window>
```

```csharp
// C# 파일
public partial class MainWindow : Window
{
    public MainWindow()
    {
        InitializeComponent();
    }

    private void OnMouseDownHandler(object sender, MouseButtonEventArgs e)
    {
        DoMouseThings(e);
    }
}
```

**첫 번째 해법을 선호해야 한다.** WPF가 선언적 코드를 강조한다는 점을 생각하면 뜻밖으로 들릴 수 있다. 그래도 로직이 코드로 구현되어야 한다면 가상 메서드를 써야 한다. 이유는 셋이다.

**이유 1 — 핸들러 하나가 예외를 던지면 체인의 나머지가 호출되지 않는다.** 이벤트 핸들러가 예외를 던지면 그 이벤트의 체인에 있는 다른 어떤 핸들러도 호출되지 않는다(26.4절). 다른 잘못 작성된 코드가 시스템이 내 핸들러를 호출하는 것을 막을 수 있다는 뜻이다. **protected 가상 함수를 오버라이드하면 내 핸들러가 먼저 호출된다.** 가상 함수의 기반 클래스 버전이 그 이벤트에 붙은 이벤트 핸들러들을 호출할 책임을 진다.

**이유 2 — 유지보수 지점이 하나다.** 가상 함수를 오버라이드하면 폼을 유지보수해야 할 때 살펴보고 수정할 함수가 **하나**다. 이벤트 메커니즘에는 유지보수 지점이 **둘** 있다 — 이벤트 핸들러 함수와 이벤트를 연결하는 코드다. 둘 중 어느 쪽이든 실패 지점이 될 수 있다. 함수 하나가 더 단순하다.

**이유 3 — 순서를 통제할 수 있다.** 내가 먼저 처리하고 나서 기반 클래스에 넘길지, 아예 넘기지 않을지를 결정할 수 있다.

> **⚠️ `base` 호출을 빠뜨리면 이벤트 핸들러가 전혀 호출되지 않는다**
>
> 이벤트 핸들러들이 호출되기를 원한다면(거의 언제나 그렇다) **반드시 기반 클래스를 호출해야 한다.** 드문 경우지만 기본 동작을 대체하고 싶어서 기반 클래스 버전을 부르지 않아 어떤 이벤트 핸들러도 호출되지 않게 만들 수도 있다 — 그건 의도적일 때만 해야 한다.
>
> 모든 이벤트 핸들러가 호출되리라 보장할 수는 없다. 잘못 작성된 이벤트 핸들러가 예외를 던질 수 있기 때문이다. 그러나 **내 파생 클래스의 동작이 올바르다는 것은 보장할 수 있다.**

### 그럼 이벤트는 언제 쓰는가

.NET 설계자들이 이유 없이 이벤트를 넣었을 리 없다. **오버라이드는 파생 클래스를 위한 것이고, 그 외의 모든 클래스는 이벤트 메커니즘을 써야 한다.**

**첫째, 디자이너와 선언적 XAML에서 연결할 때.** XAML 파일에 정의된 선언적 동작은 이벤트 핸들러를 통해 접근된다. 디자이너가 `MouseDown` 이벤트에 대해 일어나야 할 동작들을 XAML 선언으로 만들어 두면, 그 동작들은 폼의 이벤트를 통해 접근된다. 그 동작 전부를 코드로 다시 정의할 수도 있지만 이벤트 하나 처리하자고 하기엔 일이 너무 많다. **문제를 디자이너의 손에서 내 손으로 옮기는 것뿐이다.** 디자이너가 디자인 작업을 하게 두는 편이 명백히 낫다. 결국 폼 클래스에 이벤트를 보내는 새 클래스를 만들게 되느니, 애초에 폼의 이벤트 핸들러를 폼에 붙이는 편이 더 단순하다.

**둘째, 런타임에 연결을 바꿔야 할 때.** 이벤트는 런타임에 연결되므로 유연성이 더 크다. 프로그램의 상황에 따라 다른 이벤트 핸들러를 연결할 수 있다. 그리기 프로그램을 쓴다고 하자. 프로그램 상태에 따라 마우스 다운이 **선을 그리기 시작**할 수도 있고 **객체를 선택**할 수도 있다. 사용자가 모드를 전환하면 이벤트 핸들러를 갈아 끼우면 된다. 서로 다른 이벤트 핸들러를 가진 서로 다른 클래스들이 애플리케이션 상태에 따라 이벤트를 처리한다.

**셋째, 여러 핸들러를 붙일 때.** 이벤트를 쓰면 같은 이벤트에 여러 이벤트 핸들러를 연결할 수 있다. 같은 그리기 프로그램을 다시 생각해 보자. `MouseDown` 이벤트에 여러 핸들러를 걸 수 있다. 첫 번째는 실제 동작을 수행하고, 두 번째는 상태 표시줄을 갱신하거나 여러 명령의 활성화 상태를 갱신한다. **같은 이벤트에 반응해 여러 동작이 일어날 수 있다.**

### 선택 기준표

| 상황 | 오버라이드 | 이벤트 |
|---|---|---|
| 내가 그 클래스의 파생 클래스다 | **이걸 쓴다** | |
| 무관한 객체의 이벤트에 반응한다 | | **이걸 쓴다** |
| 핸들러가 정확히 하나다 | **예** | |
| 여러 동작을 붙여야 한다 | | **예** |
| 런타임에 연결을 바꿔야 한다 (그리기 모드 전환) | | **예** |
| 디자이너·XAML에서 연결한다 | | **예** |
| 다른 핸들러의 예외에 영향받고 싶지 않다 | **예** | |
| 처리 순서를 통제해야 한다 | **예** | |
| 유지보수 지점을 하나로 줄이고 싶다 | **예** (함수 1개) | (핸들러 + 연결 코드 2개) |
| 기본 동작을 아예 막아야 한다 | **예** (`base` 미호출) | |

**파생 클래스에서 하나의 이벤트를 하나의 함수로 처리하는 경우라면 오버라이드가 더 나은 접근이다.** 유지보수가 쉽고, 시간이 지나도 올바를 가능성이 높고, 더 효율적이다. 이벤트 핸들러는 다른 용도로 아껴 두라.

## 이 장의 요약

- **이벤트는 발행자/구독자 패턴을 언어가 형식화한 것이다.** 델리게이트가 제공하는 기능 중 이 모델에 필요한 부분집합만 노출하고, 주목적은 **구독자끼리 서로 간섭하지 못하게 하는 것**이다. 델리게이트 필드를 그냥 열면 재대입·`null` 대입·직접 호출 세 가지 구멍이 뚫린다.

- **컴파일러는 `public event EventHandler<T> X;` 한 줄을 세 가지로 번역한다.** 항상 `private`인 델리게이트 필드, `public add_X`, `public remove_X`. 접근자 본문은 `Delegate.Combine`/`Delegate.Remove`와 `Interlocked.CompareExchange` do-while 루프 — 잠금 없는 CAS다. 접근자의 접근성은 이벤트 선언의 접근성을 따른다. 메타데이터에 `.event` 엔트리가 나가고 `EventInfo`로 조회되지만 **CLR 자신은 그것을 쓰지 않고 접근자 메서드만 필요로 한다.**

- **이벤트의 `+=`는 "`+` 후 대입"의 축약이 아니다.** 선언 클래스 안에서 `+=`/`-=` 이외의 참조는 내부 델리게이트 필드로 리다이렉트되고, 바깥의 `+=`/`-=`는 `add`/`remove` 호출로 번역되는 고유한 연산이다. 그리고 **한 번도 추가하지 않은 메서드를 `-=`로 제거하면 아무 일도 일어나지 않는다** — 예외도 경고도 없다.

- **표준 이벤트 패턴은 네 단계다.** `EventArgs` 파생 정보 클래스(읽기 전용 프로퍼티, 이름은 담는 정보 기준) → `event` 멤버 선언 → `protected virtual OnXxx(e)`(`sealed` 클래스면 `private` 비가상) → 입력을 이벤트로 번역하는 메서드. `sender`가 `object`인 이유는 상속과 재사용 유연성 때문이고, 반환형이 `void`인 이유는 여러 콜백의 반환값을 모을 방법이 없기 때문이다.

- **스레드 안전한 발생은 세 번 진화했다.** `if (E != null) E(...)`는 검사와 호출 사이에 경합이 있고, 지역 변수 복사는 컴파일러가 변수를 없앨 수 있으며, `Volatile.Read`가 기술적으로 완전한 버전이다. 실무에서는 `E?.Invoke(this, e)`로 충분하다 — 마이크로소프트 JIT이 힙 읽기를 새로 도입하지 않는 불변식을 지키기 때문이다(문서화되지 않은 사실). **어느 버전이든 이미 해지된 핸들러가 호출될 수 있다는 점은 남는다.**

- **접근자를 직접 구현할 이유는 셋이다.** 다른 클래스의 이벤트를 중계할 때, 이벤트는 많은데 구독자는 대부분 없을 때(딕셔너리 하나가 수십 개의 `null` 필드보다 작다), 명시적 인터페이스 이벤트를 구현할 때. **직접 쓰는 순간 컴파일러의 CAS 로직이 사라지므로 스레드 안전은 직접 책임진다.**

- **이벤트는 정적 결합을 느슨하게 하는 대가로 런타임 결합을 조인다.** 가변 `EventArgs`와 다중 구독자가 만나면 마지막 구독자가 앞을 뒤집으므로 단조 변경만 허용해야 한다. 구독자가 정확히 하나여야 하면 인터페이스나 델리게이트 인자를 쓴다. 발행자가 구독자 델리게이트를 붙들므로 **구독자는 `Dispose()`에서 반드시 해지해야 하고**, 장수명 정적 이벤트 + 단수명 구독자가 전형적 누수다. 람다 구독은 해지할 참조가 없어 더 위험하다.

- **약한 이벤트는 마지막 수단이다.** 수명 일치 → 명시적 해지 → `IDisposable` 구독 토큰 순으로 시도하고, 그래도 안 될 때만 `WeakReference<T>` 기반 구현이나 WPF `WeakEventManager`(WPF 전용)를 쓴다. 약한 이벤트에 람다를 등록하면 다음 GC에서 구독이 조용히 사라진다.

- **이벤트는 비가상으로만 선언하라.** 필드형 이벤트를 `virtual`로 두고 파생에서 `override`하면 파생이 자기 백킹 필드를 만들어 기반 필드를 가린다 — 구독자는 파생에 붙고 기반이 올리는 이벤트는 아무도 못 받는 **조용한 무동작**이 된다. 확장점은 `protected virtual OnXxx` 메서드 하나로 낸다.

- **파생 클래스 안에서는 오버라이드를, 무관한 객체의 이벤트에는 핸들러를.** 핸들러 하나의 예외가 체인의 나머지를 막고, 오버라이드하면 내 코드가 먼저 불리고, 유지보수 지점이 둘이 아니라 하나다. 단 **`base` 호출을 빠뜨리면 이벤트 핸들러가 전혀 호출되지 않는다.**

## 연습 문제

1. `public event EventHandler<EventArgs> Ping;` 한 줄만 든 클래스를 컴파일한 뒤 ILSpy나 `ildasm`으로 열어라. `add_Ping`/`remove_Ping` 메서드와 `.event` 디렉티브를 찾고, 백킹 필드의 접근성이 실제로 `private`인지 확인하라. 이벤트 선언을 `internal`로 바꿔 다시 컴파일하고 접근자 두 개의 접근성이 어떻게 바뀌는지 비교하라.

2. 27.1절의 `add_NewMail` CAS 루프를 직접 구현한 이벤트와, `add { field += value; }`만 쓴 이벤트를 각각 만들어라. 스레드 8개가 각각 1,000번씩 `+=`를 호출한 뒤 `GetInvocationList().Length`를 찍어 보고 두 결과를 비교하라. 후자에서 구독이 유실되는가?

3. 람다로 이벤트를 구독한 뒤 겉보기에 동일한 람다로 `-=`를 호출하는 프로그램을 작성하라. 해지 전후로 `GetInvocationList().Length`를 출력해 **해지가 실패했는데도 아무 예외가 나지 않음**을 확인하라. 그다음 델리게이트를 필드에 보관하도록 고쳐 해지가 성공하게 만들어라.

4. 정적 이벤트를 가진 싱글턴 발행자와, 그것을 구독하지만 해지하지 않는 클래스를 만들어라. 구독자를 10,000개 만들고 `GC.Collect()` 후 `dotnet-gcdump`나 `GC.GetTotalMemory(true)`로 메모리를 측정하라. 구독자에 `IDisposable`을 구현해 해지하도록 고친 뒤 다시 측정해 차이를 확인하라.

5. 27.8절의 `WorkerEngineBase`/`WorkerEngineDerived` 예제를 그대로 실행해 **진행률 핸들러가 한 번도 호출되지 않는 것**을 눈으로 확인하라. 그다음 (a) 파생 클래스에서 `override event`를 제거, (b) `add`/`remove` 접근자로 기반 이벤트에 중계, 두 방식으로 각각 고치고 동작을 비교하라.

6. `WorkerEventArgs.Cancel`을 `public set`으로 두고 구독자 세 개를 등록하되, 두 번째가 `Cancel = true`, 세 번째가 `Cancel = false`를 설정하게 하라. 취소가 무시되는 것을 확인한 뒤 `Cancel { get; private set; }` + `RequestCancel()`로 바꿔 순서에 무관해지는지 검증하라.

7. `EventSet`(27.3절)을 그대로 구현해 이벤트 20개를 가진 타입을 두 가지 방식 — 필드형 이벤트 20개 vs `EventSet` 하나 — 으로 만들고, 각각 인스턴스를 100,000개 만들어 `GC.GetTotalMemory(true)`를 비교하라. 그다음 `DynamicInvoke` 기반 `Raise`와 직접 델리게이트 호출의 처리량을 `BenchmarkDotNet`으로 측정해 차이를 확인하라.
