# 32장. 예외 처리

> **이 장의 위치** — Part VI「예외·리소스·객체 수명」의 첫 장이다. 11.6절에서 `throw`를 점프문의 하나로 소개하고, 11.7절에서 `using`과 `lock`이 `try`/`finally`로 낮춰진다는 것만 보인 뒤 의미론은 통째로 미뤄 두었다. 여기서 그 빚을 갚는다. 예외는 문법이 아니라 **CLR의 실행 메커니즘**이고, 그 메커니즘을 모르면 `throw`와 `throw ex`가 왜 다른지, `when` 필터가 왜 `catch`-후-재던지기보다 나은지, `finally`가 언제 실행되지 **않는지**를 설명할 수 없다.
>
> **선수 지식** — 11장(문과 제어 흐름), 13장(클래스와 캡슐화), 14장(상속과 다형성), 21장(널 안정성)
>
> **이 장에서 다루지 않는 것** — `IDisposable`과 `using`의 정리 계약, 표준 Dispose 패턴은 33장이다. 파이널라이저의 실행 순서와 객체 수명은 34장이다. `async` 메서드에서 예외가 어떻게 상태 기계를 타고 전파되는지는 47.4절과 47.5절, `Task`가 예외를 잡아 두었다가 다시 던지는 시점은 46.4절, 관찰되지 않은 태스크 예외 정책은 46.11절, 병렬 루프의 `AggregateException` 사용례는 50.9절이다. 다만 **`AggregateException` 타입 자체의 API**(`InnerExceptions` · `Flatten` · `Handle`)는 32.13절에서 다룬다. 예외 처리 절이 IL에서 어떤 테이블로 표현되는지의 바이트 수준 형식은 56장이다.

## 32.1 예외란 무엇인가 — 반환 코드 방식과의 대비

### 정의부터

예외의 정의는 놀랄 만큼 단순하다.

> **멤버가 자신의 이름이 약속한 작업을 완수하지 못했을 때, 그 사실을 알리는 수단이 예외다.**

타입을 설계할 때 타입 이름은 보통 명사가 된다 — `FileStream`, `StringBuilder`. 그 위에 얹는 멤버 이름은 보통 동사가 된다 — `Read`, `Write`, `Flush`, `Append`, `Insert`, `Remove`. 동사가 약속한 일을 못 하면 예외를 던진다. 그게 전부다.

여기서 흔한 오해를 하나 걷어내야 한다.

> **⚠️ "자주 일어나는 일이니까 예외가 아니다"는 틀린 추론이다**
>
> 파일 `Read` 메서드를 설계하는 개발자는 이렇게 말하기 쉽다. "파일을 읽다 보면 언젠가는 끝에 도달한다. 끝에 도달하는 건 **항상** 일어나는 일이니 예외 대신 특별한 반환값으로 알리겠다."
>
> 이 추론의 결함은 **판단 주체가 잘못됐다**는 데 있다. `Read`를 설계하는 사람은 이 메서드가 어떤 상황에서 호출될지 전부 알 수 없다. 대부분의 파일은 구조화된 데이터를 담고 있고, 그런 파일에서 끝을 넘어 읽으려 시도하는 것은 **거의 일어나지 않는** 일이다. 빈도는 호출자의 맥락에 달렸고, 설계자는 그 맥락을 모른다.
>
> 판단 기준은 빈도가 아니라 **계약**이다. `File.Exists()`는 파일이 없어도 성공한다 — "있는가?"라는 질문에 "없다"고 정확히 답했으니 계약을 지킨 것이다. `File.Open()`은 파일이 없으면 실패한다 — "열어라"는 계약을 못 지켰으니 예외다. **원하지 않는 답과 실패는 다르다.**

### 반환 코드 방식의 네 가지 결함

.NET 이전 Windows에서 오류 처리는 통일된 방식이 없었다. 팀마다 오류를 뜻하는 숫자 상수를 정의하고 반환값으로 썼다.

```c
/* 아주 전형적인 C 스타일 오류 처리 */
#define E_FILENOTFOUND 1000

int UseFileSystem() { return E_FILENOTFOUND; }

void main()
{
  int retVal = UseFileSystem();
  if (retVal == E_FILENOTFOUND) printf("Cannot find file...");
}
```

`E_FILENOTFOUND`는 숫자 하나일 뿐이다. 이 값 자체는 문제를 어떻게 다뤄야 하는지에 대해 아무것도 말해 주지 않는다. Windows API는 `#define` 상수, `HRESULT`, 그리고 단순 불리언의 변종(`bool`, `BOOL`, `VARIANT_BOOL`) 수백 개를 이런 식으로 뿌려 놓았다. 문제를 네 가지로 정리하면 이렇다.

| 결함 | 내용 | 예외는 어떻게 해결하는가 |
|---|---|---|
| **무시할 수 있다** | 반환값을 검사하지 않아도 컴파일된다. 검사하지 않은 실패 위에서 프로그램이 계속 돌아 데이터가 깨진다 | 처리하는 `catch`가 없으면 프로세스가 종료된다. 조용히 무시되지 않는다 |
| **시그니처를 오염시킨다** | 반환 타입은 원래 계산 결과를 담는 자리다. 오류 코드가 그 자리를 차지하면 진짜 결과는 `out` 매개변수로 밀려난다 | 반환 타입은 결과만 담는다. 실패는 별도 채널로 나간다 |
| **호출자가 즉시 처리해야 한다** | 오류 코드는 한 단계씩 손으로 위로 올려야 한다. 중간 계층 전부가 오류 전파 코드를 짊어진다 | 예외는 처리할 수 있는 `catch`를 만날 때까지 호출 스택을 스스로 거슬러 올라간다 |
| **쓸 수 없는 자리가 있다** | 생성자, 속성 getter/setter, 이벤트 add/remove, 연산자 오버로드, 변환 연산자는 반환값이 없거나 이미 쓰이고 있다 | 어느 멤버에서든 던질 수 있다 |

마지막 항목이 결정적이다. 객체지향 코드는 이렇게 생겼다.

```csharp
bool f = "Jeff".Substring(1, 1).ToUpper().EndsWith("E");   // true
```

의도를 체이닝으로 표현한 코드다. 쓰기 쉽고 읽기 쉽다. 하지만 여기에는 커다란 가정이 하나 깔려 있다 — **어떤 연산도 실패하지 않는다**는 가정이다. 물론 오류는 언제나 가능하고, 그래서 오류를 다룰 방법이 필요하다. 그런데 `Substring`이 실패했다는 사실을 반환 코드로 알리려면 반환 타입이 `string`이 아니어야 하고, 그러면 `.ToUpper()`를 붙일 수 없다. 체이닝 자체가 성립하지 않는다.

생성자는 더 명확하다.

```csharp
public sealed class Account
{
    private readonly decimal _balance;

    // 반환값이 없다. 잔액이 음수라는 사실을 어떻게 알릴 것인가?
    public Account(decimal initialBalance)
    {
        if (initialBalance < 0)
            throw new ArgumentOutOfRangeException(nameof(initialBalance));
        _balance = initialBalance;
    }
}
```

생성자에는 반환값이 없다. 오류 코드를 돌려줄 자리가 물리적으로 없다. 실패한 생성자가 "반쯤 만들어진 객체"를 남기지 않으려면 예외 말고 다른 선택지가 없다.

> **📌 이름과 계약, 그리고 `Transfer`**
>
> 다음 메서드를 보자.
>
> ```csharp
> internal sealed class Account
> {
>     public static void Transfer(Account from, Account to, decimal amount) { /* ... */ }
> }
> ```
>
> 반환 타입이 `void`인 것에 주목하라. 이건 게으름이 아니라 **설계**다. `Transfer`가 의미 있게 돌려줄 값은 없다. 반환한다면 성공한 것이고, 실패했다면 예외를 던진다. 이 메서드는 `from`이나 `to`가 `null`일 수도, 계좌가 닫혀 있을 수도, 잔액이 부족할 수도, 받는 쪽이 오버플로할 수도, `amount`가 0이거나 음수이거나 소수점 셋째 자리를 가질 수도 있다. 전부 "이체하지 못했다"는 하나의 사실로 수렴하고, 각각은 서로 다른 예외 타입으로 구분된다.

### 예외의 세 가지 이점

원천 도서들이 공통으로 드는 이점은 셋이다. **첫째, 풍부한 정보를 담는다** — 암호 같은 숫자 대신 사람이 읽을 수 있는 설명, 호출 스택 스냅숏, 도움말 링크, 개발자가 정의한 임의의 데이터를 담은 객체를 받는다. **둘째, 언어와 경계를 넘어 동일하다** — CLR을 대상으로 하는 모든 언어가 같은 방식으로 던지고 잡으며, 어셈블리·머신 경계를 넘어도 같은 키워드를 쓴다. **셋째, 오류 생성과 오류 처리를 분리한다** — 두 지점이 호출 스택에서 여러 단계 떨어져 있어도 되고, 중간 계층은 아무것도 하지 않아도 된다.

> **⚠️ 그렇다고 예외를 제어 흐름으로 쓰라는 뜻은 아니다**
>
> 예외는 런타임에 비싸고(32.12절), 예외에 안전한 코드를 쓰는 것은 어렵다(32.11절). 정상적인 운영 조건에서 예외가 던져지지 않도록 **미리 조건을 검사할 수 있는 공개 메서드를 함께 제공하는 것**이 라이브러리 설계자의 책임이다. 그 표준 형태가 `TryXXX` 패턴이며 32.9절에서 다룬다.
>
> 나눗셈 앞에서 0인지 확인하는 것이 `DivideByZeroException`을 잡는 것보다 낫다. 예외는 "예방할 수 없는 실패"를 위한 것이다.

> **💡 C#에는 검사 예외(checked exception)가 없다**
>
> Java와 달리 C#에는 "이 메서드는 이런 예외를 던질 수 있다"를 시그니처에 선언하는 문법이 없다. 모든 예외는 런타임 예외다. 컴파일러는 당신이 어떤 예외도 처리하도록 강제하지 않는다.
>
> 이건 축복이자 저주다. 축복인 이유는 검사 예외가 만드는 `throws` 오염과 "일단 잡아서 삼키기" 관행을 피할 수 있어서다. 저주인 이유는 **어떤 예외가 날 수 있는지 알아내려면 문서를 읽거나 소스를 봐야 한다**는 것이다. 그래서 이 장의 32.4절에 카탈로그 표를 두었다.

## 32.2 `try` / `catch` / `finally` / `when`

### 문법

```csharp
private void SomeMethod()
{
    try
    {
        // 우아한 복구나 정리가 필요한 코드
    }
    catch (InvalidOperationException)
    {
        // InvalidOperationException에서 복구하는 코드
    }
    catch (IOException)
    {
        // IOException에서 복구하는 코드
    }
    catch
    {
        // 나머지 모든 예외. 이 자리에서는 보통 다시 던진다
        throw;
    }
    finally
    {
        // try 블록에서 시작한 작업을 정리하는 코드
    }
    // finally 아래 코드는 try에서 예외가 나지 않았거나,
    // catch가 예외를 잡고 다시 던지지 않은 경우에 실행된다
}
```

`try` 블록은 **`catch`나 `finally` 중 최소 하나**와 짝을 이뤄야 한다. 홀로 선 `try`는 의미가 없고 C# 컴파일러가 막는다.

`catch` 뒤 괄호 안의 타입을 **catch 타입**이라 부른다. C#에서 catch 타입은 `System.Exception`이거나 그 파생 타입이어야 한다. 타입을 아예 생략한 `catch { }`는 모든 예외를 잡되 예외 객체에 접근할 수 없는 형태다.

`finally` 블록은 `try` 하나당 **최대 하나**이며, 모든 `catch` 블록 **뒤에** 와야 한다.

### 실행 순서 — 정확히

예외가 `try` 문 안에서 던져지면 런타임은 다음 검사를 한다.

- **이 `try` 문에 호환되는 `catch`가 있는가** — 타입이 맞고 필터를 통과하는가.
- **있으면** 그 `catch`로 점프하고, 이어서 `finally`(있다면)를 실행한 뒤 정상 흐름을 계속한다.
- **없으면** 곧바로 `finally`(있다면)를 실행하고, 호출 스택 위쪽의 다른 `try` 문을 찾아 같은 검사를 반복한다.
- **호출 스택의 어느 함수도 책임지지 않으면** 프로그램이 종료된다.

이 요약은 관찰되는 결과를 설명하지만 실제 순서는 아니다. 정확한 메커니즘은 32.6절이다.

여기서 미묘하지만 중요한 규칙이 있다.

> **📌 처리하는 `catch`에 딸린 `finally`는 그 `catch` 다음에 실행된다**
>
> CLR이 타입이 맞는 `catch`를 찾으면, **예외를 던진 `try`부터 시작해 그 `catch`가 속한 `try`의 바로 안쪽까지**의 모든 `finally`를 먼저 실행한다. 그 다음 `catch` 본문이 실행되고, **그러고 나서** `catch`와 같은 `try`에 딸린 `finally`가 실행된다.
>
> 즉 "안쪽 `finally`들 → 처리하는 `catch` → 그 `catch`의 `finally`" 순서다. 이 순서가 왜 이렇게 되는지는 2단계 처리 모델(32.6절)을 보면 필연으로 이해된다.

`catch` 본문 끝에서 할 수 있는 일은 셋뿐이다.

| 선택 | 코드 | 의미 |
|---|---|---|
| 같은 예외를 다시 던진다 | `throw;` | 위쪽 호출자에게 실패를 알린다. 스택 정보 보존 |
| 다른 예외를 던진다 | `throw new XxxException(msg, e);` | 더 풍부한/추상화된 정보를 위쪽에 준다 |
| 그냥 빠져나간다 | (아무것도 안 함) | 예외를 처리했다고 선언한다. `finally` 후 정상 흐름 |

### `catch` 절의 순서

CLR은 `catch` 타입을 **위에서 아래로** 검사한다. 그래서 더 구체적인 예외 타입을 위에 두어야 한다. 가장 파생된 타입이 먼저, 그 기반 타입들이 뒤로, `System.Exception`(또는 타입 없는 `catch`)이 맨 마지막이다.

```csharp
try { myCar.Accelerate(-10); }
catch (CarIsDeadException e) { Log(e); }            // 가장 구체적
catch (ArgumentOutOfRangeException e) { Log(e); }   // 그 다음
catch (Exception e) { Log(e); }                     // 마지막 그물
```

순서를 뒤집으면 컴파일 오류다. 기반 타입 `catch`가 위에 있으면 아래 `catch`는 도달 불가능(unreachable)하기 때문이다.

> **⚠️ `catch (Exception)`을 맨 위에 두면 컴파일이 안 된다 — 단, `when`이 붙으면 이야기가 다르다**
>
> 필터가 붙은 `catch (Exception e) when (...)`는 조건에 따라 잡지 않을 수 있으므로, 아래의 더 구체적인 `catch`가 도달 불가능이 아니다. 그래서 컴파일된다. 이 성질을 이용한 로깅 관용구가 32.8절이다.

### `finally`가 실행되는 조건

`finally`는 `catch` 블록이 끝났을 때(새 예외를 던지며 끝나도), `try` 블록이 끝났을 때(잡히지 않는 예외를 던지며 끝나도), 그리고 점프문(`return`, `goto`, `break`, `continue`) 때문에 `try` 블록을 벗어날 때 실행된다.

```csharp
void ReadFile()
{
    StreamReader reader = null;      // System.IO
    try
    {
        reader = File.OpenText("file.txt");
        if (reader.EndOfStream) return;      // 여기서 나가도 finally는 돈다
        Console.WriteLine(reader.ReadToEnd());
    }
    finally
    {
        if (reader != null) reader.Dispose();
    }
}
```

정리 코드를 `finally` **뒤에** 두면 안 된다. 예외가 던져지고 잡히지 않으면 그 문장은 실행되지 않고, 파일은 다음 가비지 컬렉션까지 열린 채로 남는다.

`using` 문은 이 관용구의 문법 설탕이다. 낮춤 형태와 `Dispose` 계약은 33.5절과 33.10절에서 다룬다.

### `finally`가 실행되지 **않는** 경우

이게 이 절의 핵심이다. "`finally`는 언제나 실행된다"는 문장은 **거짓**이다. 정확한 표현은 "CLR은 `finally`를 실행하려고 최선을 다한다"이다.

| 상황 | `finally` 실행 여부 | 비고 |
|---|---|---|
| 예외가 잡혔다 | 실행됨 | 정상 |
| `return` / `break` / `goto`로 탈출 | 실행됨 | 정상 |
| `try` 안에서 무한 루프 | 실행 안 됨 | 애초에 블록을 벗어나지 않는다 |
| `Environment.FailFast` 호출 | **실행 안 됨** | 설계된 동작. 상태가 깨졌을 때 더 이상 코드를 돌리지 않으려는 것 |
| Win32 `TerminateProcess` / `TerminateThread` | **실행 안 됨** | OS가 프로세스 자원은 회수한다 |
| `StackOverflowException` | **실행 안 됨** | 프로세스가 즉시 종료된다 |
| 손상된 상태 예외(CSE) | **실행 안 됨** | .NET Framework 기준. 32.14절 |
| 예외를 아무도 처리하지 않음 | **보장되지 않음** | 2단계 모델의 결과. 아래 참조 |

마지막 항목이 가장 자주 사람을 놀라게 한다.

> **⚠️ 처리되지 않는 예외에서는 `finally`가 돌지 않을 수 있다**
>
> CLR의 2단계 처리(32.6절)에서 **스택 언와인딩과 `finally` 실행은 2단계에서 일어난다.** 그런데 1단계에서 처리할 `catch`를 끝내 못 찾으면 예외는 "처리되지 않은 예외"가 되고, 런타임은 프로세스를 종료한다. 이때 2단계가 시작되지 않으므로 `finally` 블록이 실행되지 않을 수 있다.
>
> 이것은 버그가 아니라 의도다. 스택을 언와인딩해 버리면 디버거가 예외 발생 지점의 스택을 볼 수 없다. 크래시 덤프에 원래 상태를 남기는 쪽이 정리보다 가치 있다는 판단이다.
>
> 실무적 함의: **`finally`에 "반드시 일어나야 하는 외부 부작용"(로그 flush, 원격 커밋 취소)을 걸어 두고 그것이 언제나 실행된다고 믿으면 안 된다.** 프로세스 종료 시점의 정리는 별도 메커니즘(`AppDomain.ProcessExit`, 프로세스 감시자)으로 해야 한다.

### `catch`와 `finally` 안에서 예외가 나면

정리 코드나 복구 코드 자체가 실패할 수 있다. 가능성은 낮지만 0은 아니다. `catch`나 `finally` 안에서 예외가 던져지면, CLR의 예외 메커니즘은 **그 예외가 `finally` 이후에 던져진 것처럼** 동작한다.

> **⚠️ 두 번째 예외가 첫 번째 예외를 완전히 지운다**
>
> CLR은 원래 `try` 블록에서 던져진 첫 예외를 기억하지 않는다. 스택 트레이스를 포함해 첫 예외에 대한 모든 정보가 사라진다. 남는 것은 정리 코드가 던진 새 예외뿐이다.
>
> ```csharp
> try
> {
>     throw new InvalidOperationException("진짜 원인");
> }
> finally
> {
>     throw new IOException("정리 실패");   // 이것만 남는다
> }
> ```
>
> 호출자가 보는 것은 `IOException`뿐이다. `InvalidOperationException`은 흔적도 없이 증발한다.
>
> 그래서 `catch`와 `finally` 안의 코드는 **아주 짧아야 하고, 실패할 가능성이 매우 낮아야 한다.** 보통 한두 줄이다. 여기서 예외가 나면 대개 어딘가의 상태가 심각하게 깨졌다는 뜻이고, 그 예외가 처리되지 않아 프로세스가 종료되는 편이 낫다 — 깨진 상태로 계속 돌면서 예측 불가능한 결과와 보안 구멍을 만드는 것보다는. `Dispose`가 예외를 던지면 안 된다는 규칙(33.2절)도 같은 이유에서 나온다.

### `when` — 예외 필터

C# 6부터 `catch` 절에 `when` 절을 붙여 **필터**를 지정할 수 있다.

```csharp
catch (WebException ex) when (ex.Status == WebExceptionStatus.Timeout)
{
    // ...
}
```

`WebException`이 던져지면 `when` 뒤의 불리언 식이 평가된다. 결과가 `false`면 이 `catch` 블록은 무시되고 이후의 `catch` 절들이 계속 검토된다.

필터가 있으면 **같은 예외 타입을 여러 번 잡는 것이 의미를 갖는다.**

```csharp
catch (WebException ex) when (ex.Status == WebExceptionStatus.ConnectFailure)
{
    // 연결 실패 처리
}
catch (WebException ex) when (ex.Status == WebExceptionStatus.NameResolutionFailure)
{
    // 이름 해석 실패 처리
}
catch (WebException ex)
{
    // 나머지 WebException
}
```

필터가 없던 시절에는 같은 타입을 두 번 쓰는 것이 무조건 컴파일 오류였다. 두 번째는 도달할 수 없었기 때문이다.

`when` 절의 불리언 식은 **부작용을 가질 수 있다.** 진단 목적으로 예외를 로그에 남기는 메서드를 호출해도 된다. 이 성질은 강력하고 위험하며, 32.8절에서 따로 다룬다.

개념적으로 `catch (IOException e) { ... }`는 `catch (Exception tmp) when (tmp is IOException) { IOException e = (IOException)tmp; ... }`와 거의 같다. 즉 **타입 검사는 필터의 특수한 경우**이고, `when`은 그 일반화다.

### 컴파일 결과 — `catch`와 `filter`의 IL

11.7절에서 `.try`/`finally`가 명령이 아니라 메서드 본문 뒤에 붙는 **예외 처리 절 테이블**(EH clause table)의 항목이라는 것을 봤다. `catch`와 `filter`도 같은 테이블의 다른 종류다.

절의 종류는 넷이다.

| 종류 | C# 문법 | 동작 |
|---|---|---|
| `catch` | `catch (T e)` | 타입이 `T`와 호환되면 핸들러 실행 |
| `filter` | `catch (T e) when (cond)` | 필터 블록을 실행해 1이면 핸들러 실행 |
| `finally` | `finally` | 정상 종료·예외 전파 양쪽에서 실행 |
| `fault` | (C#에 없음) | 예외 전파 시에만 실행. IL/다른 언어에서만 |

다음 C# 코드를 보자.

```csharp
static void M()
{
    try { Work(); }
    catch (IOException e) when (e.HResult != 0) { Log(e); }
    finally { Cleanup(); }
}
```

Roslyn이 만드는 IL은 대략 이렇다.

```il
.method private hidebysig static void M() cil managed
{
  .maxstack  2
  .locals init ([0] class [System.Runtime]System.IO.IOException e)
  .try
  {
    .try
    {
      IL_0000:  call       void Program::Work()
      IL_0005:  leave.s    IL_0031
    }  // end .try
    filter
    {
      IL_0007:  isinst     [System.Runtime]System.IO.IOException
      IL_000c:  dup
      IL_000d:  brtrue.s   IL_0013
      IL_000f:  pop
      IL_0010:  ldc.i4.0
      IL_0011:  br.s       IL_0020
      IL_0013:  stloc.0
      IL_0014:  ldloc.0
      IL_0015:  callvirt   instance int32 [System.Runtime]System.Exception::get_HResult()
      IL_001a:  ldc.i4.0
      IL_001b:  cgt.un
      IL_001d:  ldc.i4.0
      IL_001e:  cgt.un
      IL_0020:  endfilter
    }  // end filter
    {  // handler
      IL_0022:  pop
      IL_0023:  ldloc.0
      IL_0024:  call       void Program::Log(class [System.Runtime]System.Exception)
      IL_0029:  leave.s    IL_0031
    }  // end handler
  }  // end .try
  finally
  {
    IL_002b:  call       void Program::Cleanup()
    IL_0030:  endfinally
  }  // end handler
  IL_0031:  ret
}
```

읽을 점 네 가지.

**첫째, 필터 블록의 시작은 스택에 예외 객체가 올려진 상태다.** `isinst`로 타입을 검사하고, 맞지 않으면 `pop` 후 `ldc.i4.0`(=거짓)을 남긴 채 `endfilter`로 간다.

**둘째, `endfilter`는 스택 맨 위의 `int32`를 결과로 소비한다.** 0이면 `exception_continue_search`(계속 찾아라), 1이면 `exception_execute_handler`(이 핸들러를 실행하라)를 뜻한다. C#의 `bool`이 그대로 이 정수가 된다.

**셋째, 핸들러 블록의 시작도 예외 객체가 스택에 올려진 상태다.** 필터가 이미 지역 변수 `e`에 저장해 두었으므로 `pop`으로 버린다. 필터가 없는 순수 `catch`였다면 `stloc`으로 저장한다.

**넷째, `finally`가 있으므로 `try`가 이중으로 중첩됐다.** C# 소스에는 `try` 하나뿐이지만 IL에서는 두 개다. 한 보호 구역에 `catch`와 `finally`를 동시에 달 수 없기 때문이다.

> **📌 `leave` 명령이 하는 일**
>
> `try`/`catch`/`filter` 블록을 정상적으로 빠져나갈 때는 `br`이 아니라 `leave`를 쓴다. `leave`는 평가 스택을 비우고, 중간에 있는 모든 `finally` 핸들러를 실행한 뒤 목적지로 점프한다. 그래서 `return`이 `try` 안에 있어도 `finally`가 실행되는 것이다.
>
> `endfinally`는 "핸들러가 끝났으니 원래 하려던 일을 계속하라"는 뜻이다. `leave`로 들어왔으면 `leave`의 목적지로, 예외 전파 중에 들어왔으면 전파를 계속한다.

### 성능 영향

RyuJIT은 예외가 던져지지 않는 정상 경로를 최적화한다. 특히 `finally` 클로닝(11.7절) 덕분에 `try`/`finally`의 정상 경로 비용은 사실상 없다. **"보호 구역이 있는 것" 자체는 거의 공짜이고, 비싼 것은 예외를 던질 때다.** 다만 예외 처리 절이 있는 메서드는 JIT이 인라인하지 않는 경우가 있고, 일부 지역 변수를 레지스터에 올리지 않을 수 있다. 수치와 측정 방법은 32.12절에서 다룬다.

> **💡 `try` 블록의 크기를 정하는 기준은 "상태 관리"다**
>
> "한 `try` 블록에 코드를 얼마나 넣어야 하는가"라는 질문의 답은 성능이 아니라 상태에 달렸다.
>
> `try` 안에서 같은 예외 타입을 던질 수 있는 연산을 여러 개 수행하는데, **어느 연산에서 났느냐에 따라 복구 방법이 다르다면** 각 연산을 별도의 `try`로 쪼개야 한다. 그래야 상태를 정확히 되돌릴 수 있다. 복구 방법이 같다면 하나로 묶어도 된다.

## 32.3 `System.Exception`의 핵심 속성과 예외 계층

### 왜 `System.Exception`이 존재하는가

CLR 자체는 **아무 타입의 인스턴스든** 예외로 던지는 것을 허용한다. `int`도, `string`도, `DateTime`도 던질 수 있다. 그런데 마이크로소프트는 모든 언어에 그 부담을 지우지 않기로 했고, `System.Exception` 타입을 정의한 뒤 "CLS를 따르는 모든 언어는 이 타입에서 파생된 예외를 던지고 잡을 수 있어야 한다"고 규정했다. C# 컴파일러는 CLS를 따르는 예외만 던지도록 강제한다.

> **📌 `RuntimeWrappedException` — 비 CLS 예외의 처리**
>
> CLR 2.0부터, `Exception`에서 파생되지 않은 객체가 던져지면 CLR이 자동으로 `System.Runtime.CompilerServices.RuntimeWrappedException` 인스턴스를 만들어 감싼다. 원래 객체는 이 타입의 `WrappedException` 속성으로 꺼낼 수 있다. 그 전에는 C#의 `catch (Exception e)`가 다른 언어에서 던진 비 CLS 예외를 **아예 못 잡아** 보안 취약점이 됐다. 지금은 `catch (Exception)`이 모든 것을 잡는다.
>
> 어셈블리 단위로 옛 동작을 되살리려면 `[assembly: RuntimeCompatibility(WrapNonExceptionThrows = false)]`를 적용한다. 어셈블리 전체에 걸리며 섞어 쓸 수 없다. 실무에서 이걸 쓸 이유는 거의 없다.

### 핵심 속성

`System.Exception`은 놀랄 만큼 단순한 타입이다.

| 속성 | 접근 | 타입 | 설명 |
|---|---|---|---|
| `Message` | 읽기 전용 | `string` | 예외가 던져진 이유를 설명하는 텍스트. 처리되지 않으면 보통 로그로 나간다 |
| `Data` | 읽기 전용 | `IDictionary` | 키-값 쌍 컬렉션. 던지는 쪽이 정보를 채우고, 잡는 쪽이 복구 처리에 쓴다. 기본은 비어 있다 |
| `Source` | 읽기/쓰기 | `string` | 예외를 생성한 어셈블리(또는 객체)의 이름 |
| `StackTrace` | 읽기 전용 | `string` | 예외 발생까지 호출된 메서드들의 이름과 시그니처 |
| `TargetSite` | 읽기 전용 | `MethodBase` | 예외를 던진 메서드 |
| `HelpLink` | 읽기 전용* | `string` | 이 예외를 설명하는 문서의 URL |
| `InnerException` | 읽기 전용 | `Exception` | 다른 예외를 처리하다가 이 예외가 생겼다면 그 이전 예외. 보통 `null` |
| `HResult` | 읽기/쓰기 | `int` | 관리/네이티브 경계를 넘을 때 쓰는 32비트 값 |

\* `HelpLink`는 `Exception` 정의상 `get`/`set`을 모두 갖는 가상 속성이다. 객체 초기화자로 설정할 수 있다.

메서드도 두 개 알아 둘 만하다.

```csharp
public virtual Exception GetBaseException();   // InnerException 사슬의 맨 끝을 반환
public virtual string ToString();              // 타입 이름 + Message + 내부 예외 + StackTrace
```

### `Message`

`Message`는 **개발자를 위한 텍스트**다. 최종 사용자는 이 문자열을 보지 못하게 해야 한다(보안상으로도, 사용성으로도). 그러니 최대한 기술적으로, 개발자가 로그만 보고 코드를 고칠 수 있을 만큼 자세하게 쓴다. 프로그래밍 언어와 BCL의 이름이 영어이므로 원칙적으로 지역화는 필요 없다 — 여러 언어권 개발자가 쓸 클래스 라이브러리라면 예외다. 마이크로소프트가 BCL의 예외 메시지를 지역화하는 이유가 그것이다.

### `StackTrace`

`StackTrace`는 단순히 문자열을 반환하는 속성이 아니다. **이 속성에 접근하는 순간 CLR 안으로 들어가 문자열을 만든다.**

```csharp
var e = new InvalidOperationException("아직 던지지 않았다");
Console.WriteLine(e.StackTrace is null);   // True
```

새로 만든 예외 객체의 `StackTrace`는 `null`이다. 스택 트레이스는 **던지는 시점에** 기록되기 때문이다. 예외가 던져지면 CLR이 `throw` 명령의 위치를 기록하고, `catch`가 예외를 받아들이면 잡힌 위치를 기록한다. `catch` 안에서 `StackTrace`를 읽으면 CLR이 **던져진 지점과 잡은 필터 사이의** 모든 메서드를 나열한 문자열을 만든다.

핵심 결과 두 가지.

> **⚠️ `StackTrace`에는 `catch`보다 위쪽 프레임이 들어 있지 않다**
>
> `StackTrace`가 반환하는 문자열에는 예외를 받아들인 `catch` 블록보다 **위(호출자 쪽)** 에 있는 프레임이 없다. 스레드 시작 지점부터의 완전한 스택이 필요하다면 `System.Diagnostics.StackTrace` 타입을 직접 써야 한다. 이 타입은 스레드의 시작부터 현재까지를 담는 생성자와, `Exception` 객체로부터 프레임을 초기화하는 생성자를 모두 제공한다.

> **⚠️ 실제 호출 스택에 있던 메서드가 트레이스에 안 보일 수 있다**
>
> 이유가 두 가지 있다.
>
> 1. **스택은 "어디서 왔는가"가 아니라 "어디로 돌아가야 하는가"의 기록이다.** 꼬리 호출 등으로 프레임이 남지 않을 수 있다.
> 2. **JIT이 메서드를 인라인한다.** 인라인된 메서드는 별도 프레임을 만들지 않으므로 트레이스에 나타나지 않는다(55장).
>
> 컴파일러의 `/debug` 스위치를 쓰면 `System.Diagnostics.DebuggableAttribute`가 `DisableOptimizations` 플래그와 함께 붙고, JIT이 그 어셈블리의 메서드를 인라인하지 않는다. 특정 메서드만 막으려면 이렇게 한다.
>
> ```csharp
> using System.Runtime.CompilerServices;
>
> internal sealed class SomeType
> {
>     [MethodImpl(MethodImplOptions.NoInlining)]
>     public void SomeMethod() { /* ... */ }
> }
> ```
>
> 다만 릴리스 빌드에서 이걸 남발하면 성능을 잃는다. 진단이 목적이라면 소스 링크와 PDB 배포(74.6절·74.7절)가 더 나은 답이다.

PDB(.pdb 심볼 파일)를 찾을 수 있으면 `StackTrace` 문자열에 **소스 파일 경로와 줄 번호**가 포함된다.

```text
Stack: at SimpleException.Car.Accelerate(Int32 delta)
   in [path to file]\Car.cs:line 57
   at <Program>$.<Main>$(String[] args)
   in [path to file]\Program.cs:line 20
```

문자열의 **맨 아래 줄이 호출 사슬의 시작**, **맨 위 줄이 예외가 실제로 난 지점**이다.

### `TargetSite`

`TargetSite`는 문자열이 아니라 `System.Reflection.MethodBase` 객체를 반환한다. 그래서 예외를 던진 메서드에 대해 더 많은 것을 물어볼 수 있다 — `DeclaringType`으로 정의한 클래스를, `MemberType`으로 멤버 종류(메서드인지 속성인지)를 알 수 있다.

> **⚠️ `TargetSite`는 `null`일 수 있다**
>
> 예외를 던진 메서드 정보를 얻을 수 없는 환경 — 스택 트레이스 정보가 제거된 트리밍/NativeAOT 배포 등 — 에서는 `null`이 반환된다. 로깅 코드가 `e.TargetSite.Name`을 무조건 참조하면 로깅 도중에 `NullReferenceException`이 나고, 그러면 32.2절의 "두 번째 예외가 첫 번째를 지운다" 상황이 된다. **로깅 코드에서는 널 조건 연산자를 써라.**
>
> 그리고 `TargetSite.Name`으로 분기하는 코드(“`Foo`에서 났으면 이렇게, `Bar`에서 났으면 저렇게”)는 절대 쓰지 마라. 메서드 이름을 바꾸면 깨지고, 호출을 유틸리티 함수로 옮기면 깨진다. 스택 깊이가 깊을수록 더 잘 깨진다. 그런 분기가 필요하면 **예외 타입을 나눠라**(32.10절).

### `Data`

`Data`는 `IDictionary`를 반환한다. 던지는 쪽에서 임의의 정보를 실을 수 있고, 잡는 쪽은 `DictionaryEntry`로 순회한다.

```csharp
using System.Collections;

try
{
    throw new InvalidOperationException("차가 과열됐다")
    {
        HelpLink = "https://example.com/help/overheat",
        Data =
        {
            { "TimeStamp", DateTime.Now },
            { "Cause", "가속 페달을 너무 오래 밟았다" }
        }
    };
}
catch (Exception e)
{
    foreach (DictionaryEntry de in e.Data)
        Console.WriteLine("-> {0}: {1}", de.Key, de.Value);
}
```

`Data`의 가장 좋은 용도는 **잡았다가 그대로 다시 던지면서 문맥을 얹는 것**이다.

```csharp
private static void SomeMethod(string filename)
{
    try
    {
        // ...
    }
    catch (IOException e)
    {
        e.Data.Add("Filename", filename);   // 정보를 얹고
        throw;                              // 같은 객체를 그대로 다시 던진다
    }
}
```

새 예외 타입을 만들지 않고도 문맥을 붙일 수 있고, 스택 트레이스도 보존된다(32.5절).

> **💡 `Data` vs 강타입 속성**
>
> `Data`는 편하지만 **약타입**이다. 잡는 쪽이 문자열 키를 알아야 하고, 오타가 컴파일 오류가 되지 않는다. 잡는 쪽이 구조적으로 접근해야 할 정보라면 **전용 예외 타입에 강타입 속성으로** 두는 것이 낫다(32.10절). `Data`는 "로그에 남기면 좋을 부가 정보"에 쓴다.

### `HResult`

`HResult`는 관리 코드와 네이티브 코드 경계를 넘을 때 쓰이는 32비트 값이다. COM API가 실패 `HRESULT`를 반환하면 CLR이 `Exception` 파생 객체를 던지면서 그 값을 여기에 보존한다. 반대 방향으로, 관리 예외가 COM 호출자에게 전파될 때도 이 값이 `HRESULT`가 된다.

`HRESULT`의 비트 구조는 이렇다.

```text
 31 30      16 15                              0
┌──┬──────────┬──────────────────────────────────┐
│S │ Facility │            Code                  │
└──┴──────────┴──────────────────────────────────┘
  │      │                     └─ 오류 코드
  │      └─ 오류의 출처(0x07 = Win32, 0x13 = CLR)
  └─ 심각도. 1이면 실패
```

`0x8007xxxx`는 Win32 오류에서 온 것이고, `0x8013xxxx`는 CLR이 정의한 것이다.

> **⚠️ `HResult` 값을 외우거나 하드코딩하지 마라**
>
> 예외 타입별 `HResult` 값은 문서화된 상수이지만, 코드에 매직 넘버로 박아 두면 읽는 사람이 무슨 뜻인지 알 수 없다. 그리고 값이 필요한 상황은 대부분 상호 운용(60장)이나 특정 플랫폼 오류 식별이다.
>
> 값을 확인하고 싶으면 직접 출력하는 게 가장 확실하다.
>
> ```csharp
> void Show<T>() where T : Exception, new()
>     => Console.WriteLine($"{typeof(T).Name,-32} 0x{new T().HResult:X8}");
>
> Show<Exception>();
> Show<ArgumentException>();
> Show<InvalidOperationException>();
> ```
>
> 실행해서 확인하라. 프레임워크 버전과 플랫폼에 따라 달라질 수 있는 값을 책이 대신 외워 줄 필요는 없다.

`HResult`는 `set` 접근자가 공개되어 있으므로, 사용자 정의 예외에서 특정 값을 설정해 상호 운용 시나리오에 쓸 수 있다.

### `InnerException`과 예외 번역

`InnerException`은 **예외 사슬**을 만든다. 저수준 예외를 잡아 고수준 예외로 감싸면서 원인을 잃지 않는 표준 수단이다.

```csharp
try
{
    // XML 요소 데이터에서 DateTime 파싱
}
catch (FormatException ex)
{
    throw new XmlException("Invalid DateTime", ex);
}
```

두 번째 생성자 인자가 `InnerException`을 채운다. 거의 모든 예외 타입이 이 형태의 생성자를 제공한다. `GetBaseException()`은 이 사슬을 끝까지 따라가 **가장 안쪽 예외**를 반환한다.

### 예외 계층

BCL이 정의하는 예외 타입은 전부 `System.Exception`에서 파생된다. 원래 설계 의도는 CLR/런타임이 던지는 것을 `System.SystemException` 아래에, 애플리케이션이 던지는 것을 `System.ApplicationException` 아래에 두어, 개발자가 둘을 구분해 잡을 수 있게 하는 것이었다.

**이 규칙은 지켜지지 않았다.**

| 반례 | 실제 위치 | 원래 있어야 할 위치 |
|---|---|---|
| `IsolatedStorageException` | `Exception` 바로 아래 | `SystemException` 아래 |
| `TargetInvocationException` | `ApplicationException` 아래 | CLR이 던지므로 `SystemException` 아래 |
| `FormatException` | `SystemException` 아래 | 애플리케이션도 던지므로 `ApplicationException` 아래 |
| `AggregateException` | `Exception` 바로 아래 | — |

결과적으로 **`SystemException`과 `ApplicationException`은 아무 특별한 의미도 갖지 못한다.** 마이크로소프트는 이 둘을 계층에서 제거하고 싶어 하지만, 이미 이 타입들을 참조하는 코드가 깨지므로 제거하지 못한다.

> **⚠️ 사용자 정의 예외를 `ApplicationException`에서 파생시키지 마라**
>
> 오래된 책과 오래된 코드베이스는 "애플리케이션 전용 예외는 `ApplicationException`에서 파생시켜라"고 말한다. 그 조언은 **원래 의도가 무너진 뒤의 잔재**다.
>
> `ApplicationException`을 상속해도 얻는 게 없다 — 그 타입은 생성자 말고는 아무 멤버도 추가하지 않는다. 반면 잃는 것은 있다. `catch (ApplicationException)`으로 잡는 코드가 어딘가 존재하면 당신의 예외가 의도치 않게 그 그물에 걸리고, 그 `catch`가 무엇을 하는지 당신은 모른다.
>
> **`System.Exception`에서 직접 파생시켜라.** 또는 의미가 정말 맞는 기존 예외(`ArgumentException`, `InvalidOperationException` 등)에서 파생시켜라. 이것이 현재 .NET 설계 지침이다.

### 계층을 얕고 넓게

사용자 정의 예외 계층을 만든다면 **얕고 넓게(shallow and wide)** 만들어라. 기반 클래스를 되도록 적게 만든다는 뜻이다.

기반 클래스는 "여러 오류를 하나로 취급하는 수단"이고, 그건 대체로 위험하다. `catch (MyBaseException)`을 쓰는 코드는 그 아래 어떤 파생 타입이 있는지 모른 채 전부를 처리한다고 선언하는 것이다.

> **⚠️ 새 예외 타입을 추가하는 것은 버전 호환성 문제다**
>
> 기존 예외 타입에서 파생된 새 타입을 정의하면, **기존 기반 타입을 잡던 모든 코드가 새 타입도 잡게 된다.** 그 코드가 새 예외를 전혀 예상하지 못했다면 예측 불가능하게 동작하거나 보안 구멍을 만들 수 있다.
>
> 새 예외 타입을 정의하는 사람은 기반 예외가 어디서 어떻게 잡히는지 전부 알 수 없다. 그래서 이 판단은 원리적으로 완전할 수 없다. **기반 클래스를 적게 만들라**는 조언이 여기서 나온다.

그리고 **절대 `System.Exception` 객체 자체를 던지지 마라.** 다른 기반 예외 타입을 던질 때도 극도로 조심해야 한다. `System.Exception`은 애초에 `abstract`였어야 했다는 것이 원천 저자의 견해다.

## 32.4 자주 만나는 예외 타입 카탈로그

C#에는 검사 예외가 없으므로, 어떤 API가 무엇을 던지는지는 결국 **외워 두거나 문서를 봐야** 한다. 자주 마주치는 것들을 정리한다.

### 인수 관련

| 타입 | 언제 던져지는가 | 던지는 쪽 관용구 |
|---|---|---|
| `ArgumentException` | 인수 값이 잘못됐다. 대개 프로그램 버그 | `throw new ArgumentException(msg, nameof(x))` |
| `ArgumentNullException` | 인수가 (예상과 달리) `null` | `ArgumentNullException.ThrowIfNull(x)` |
| `ArgumentOutOfRangeException` | 보통 숫자 인수가 너무 크거나 작다 | `throw new ArgumentOutOfRangeException(nameof(i))` |

생성자 인자 순서에 주의하라. 셋의 시그니처가 서로 다르다.

```csharp
new ArgumentException(message, paramName);            // 메시지가 먼저
new ArgumentNullException(paramName, message);        // 이름이 먼저
new ArgumentOutOfRangeException(paramName, message);  // 이름이 먼저
```

> **⚠️ `ArgumentException`만 인자 순서가 반대다**
>
> 이 비대칭은 BCL의 오래된 설계 실수이며, 조용히 잘못된 로그를 만드는 흔한 원인이다. `new ArgumentNullException("이름이 null입니다", nameof(name))`라고 쓰면 파라미터 이름 자리에 문장이, 메시지 자리에 파라미터 이름이 들어간다. 컴파일은 통과한다. 외우기 어렵다면 `nameof`만 넘기는 단일 인자 오버로드를 쓰거나 아래의 정적 헬퍼를 쓰라.

`ArgumentNullException.ThrowIfNull`은 .NET 6에서 추가된 정적 헬퍼다.

```csharp
void Display(string name)
{
    ArgumentNullException.ThrowIfNull(name);
    Console.WriteLine(name);
}
```

파라미터 이름을 넘기지 않았는데도 예외 메시지에 `name`이 들어간다. 정의가 이렇게 되어 있기 때문이다.

```csharp
public static void ThrowIfNull(object argument,
    [CallerArgumentExpression("argument")] string paramName = null)
{
    if (argument == null)
        throw new ArgumentNullException(paramName);
}
```

`[CallerArgumentExpression]`(C# 10)은 **호출 지점의 인수 식을 소스 그대로** 캡처한다. 주석까지 포함해서 문자열로 들어온다. 주 용도가 검증·어서션 라이브러리다.

```csharp
void Assert(bool condition,
    [CallerArgumentExpression("condition")] string message = null)
{
    if (!condition) throw new Exception("Assertion failed: " + message);
}

Assert(2 + 2 == 5);   // 메시지에 "2 + 2 == 5"가 들어간다
```

`ThrowIfNull` 계열은 21.10절에서 널 검사 관용구로 이미 다뤘다.

### 상태·연산 관련

| 타입 | 언제 던져지는가 |
|---|---|
| `InvalidOperationException` | 인수와 무관하게, 객체의 **현재 상태**가 이 연산에 맞지 않다. 열리지 않은 파일 읽기, 열거 중에 수정된 컬렉션의 다음 원소 요청 |
| `NotSupportedException` | 이 기능은 지원하지 않는다. `IsReadOnly`가 `true`인 컬렉션의 `Add` |
| `NotImplementedException` | 아직 구현하지 않았다 |
| `ObjectDisposedException` | 이미 `Dispose`된 객체의 멤버를 호출했다(33장) |
| `PlatformNotSupportedException` | 현재 OS/아키텍처에서 지원하지 않는다 |

> **⚠️ `NotSupportedException`과 `NotImplementedException`은 다르다**
>
> `NotImplementedException`은 "만들다 말았다"는 뜻이며, 출시된 코드에 남아 있으면 안 된다. `NotSupportedException`은 "설계상 이 타입은 이 연산을 제공하지 않는다"는 **영구적 계약**이다. 읽기 전용 컬렉션의 `Add`가 후자다. 둘을 바꿔 쓰면 호출자가 "다음 버전에서는 되겠지"라고 오해한다.

### CLR이 던지는 것

| 타입 | 언제 |
|---|---|
| `NullReferenceException` | `null` 참조의 멤버에 접근했다. **코드 버그** |
| `IndexOutOfRangeException` | 배열 인덱스가 범위를 벗어났다 |
| `InvalidCastException` | 캐스트가 실패했다 |
| `ArrayTypeMismatchException` | 배열 요소 타입과 저장하려는 타입이 맞지 않는다 |
| `DivideByZeroException` | 정수 0으로 나눴다 |
| `OverflowException` | `checked` 문맥에서 산술 오버플로가 났다(7.9절) |
| `StackOverflowException` | 스택이 넘쳤다. **잡을 수 없다** |
| `OutOfMemoryException` | 메모리 할당에 실패했다. 잡을 수는 있다 |
| `TypeInitializationException` | 정적 생성자가 예외를 던졌다 |
| `RankException` | 배열 차수가 맞지 않는다 |

> **⚠️ `IndexOutOfRangeException`과 `ArgumentOutOfRangeException`은 던지는 주체가 다르다**
>
> **배열**의 인덱스가 범위를 벗어나면 CLR이 `IndexOutOfRangeException`을 던진다. **`List<T>` 같은 컬렉션**은 자기 인덱서에서 `ArgumentOutOfRangeException`을 던진다. 같은 실수인데 예외 타입이 다르다.
>
> 그래서 `catch (IndexOutOfRangeException)`으로 리스트 접근 오류를 잡으려는 코드는 조용히 안 잡힌다. 어느 쪽이 던져질지는 **대상이 배열인지 컬렉션인지에 달렸다.**
>
> 그리고 `IndexOutOfRangeException`을 사용자 코드에서 직접 던지지 마라. 그건 CLR의 몫이다.

`TypeInitializationException`은 예외 번역의 좋은 사례다. 정적 생성자에서 잡히지 않은 예외가 나면 CLR이 그것을 잡아 이 타입으로 감싸 다시 던진다. 정적 생성자 호출은 컴파일러가 암묵적으로 삽입하므로, 감싸지 않으면 개발자가 "부르지도 않은 코드"에서 난 `DivideByZeroException`을 보게 된다. 원래 예외는 `InnerException`에 있다.

`TargetInvocationException`은 반대로 **나쁜 사례**다. 리플렉션으로 메서드를 호출하면 CLR이 그 안의 모든 예외를 잡아 이 타입으로 바꾼다. 진짜 원인을 알려면 `InnerException`을 파야 하고, 그것을 그냥 `throw`하면 스택 트레이스가 잘린다(32.5절).

> **💡 C#의 `dynamic`은 이 문제가 없다**
>
> `dynamic` 원시 타입으로 멤버를 호출하면, 컴파일러가 만드는 코드는 예외를 잡아 `TargetInvocationException`으로 바꾸지 않는다. 원래 던져진 예외 객체가 그대로 스택을 타고 올라간다. 리플렉션보다 `dynamic`을 선호할 이유 중 하나다(59장).
>
> 리플렉션을 써야 한다면, `e.InnerException`을 그냥 `throw`하지 말고 `ExceptionDispatchInfo`로 다시 던져라(32.5절).

### I/O와 컬렉션

| 타입 | 언제 |
|---|---|
| `IOException` | I/O 오류의 기반 타입 |
| `FileNotFoundException` | 파일이 없다 |
| `DirectoryNotFoundException` | 디렉터리가 없다 |
| `DriveNotFoundException` | 드라이브가 없다 |
| `PathTooLongException` | 경로가 너무 길다 |
| `EndOfStreamException` | 스트림 끝을 넘어 읽으려 했다 |
| `FileLoadException` | 어셈블리/파일을 찾았지만 로드에 실패했다 |
| `UnauthorizedAccessException` | 권한이 없다 |
| `KeyNotFoundException` | 딕셔너리에 키가 없다 |

I/O 예외를 구분해서 잡고 재시도 정책을 세우는 것은 40.16절에서 다룬다.

### 취소·시간 초과·동시성

| 타입 | 언제 |
|---|---|
| `OperationCanceledException` | 협력적 취소가 요청됐다(46.8절) |

| `SemaphoreFullException` | 세마포어를 최대치 이상 해제했다 |

### `throw null`

`NullReferenceException`은 CLR이 던지는 것이 보통이지만, 테스트 목적으로 `throw null;`이라고 쓰면 직접 유발할 수 있다. `throw`의 피연산자가 `null`이면 CLR이 `NullReferenceException`을 던진다.

> **📌 이 카탈로그가 완전할 수 없는 이유**
>
> mscorlib/System.Private.CoreLib 하나만 해도 100개가 넘는 예외 타입을 정의하고, 다른 어셈블리는 더 정의한다. 그리고 CLR이 암묵적으로 하는 일 — 어셈블리 로드, JIT 컴파일, 정적 생성자 호출, 박싱, `AppDomain` 경계 통과 — 하나하나가 각자의 예외를 던질 수 있다.
>
> 한 줄짜리 C# 문 하나가 `OutOfMemoryException`, `TypeInitializationException`, `OverflowException`, 그리고 가상 메서드가 던지는 임의의 예외를 모두 낼 수 있다. **모든 실패를 예상하고 대비하는 코드를 쓰는 것은 사실상 불가능하다.** 이 사실이 32.11절의 논의로 이어진다.

## 32.5 `throw` vs `throw ex` — 스택 트레이스 보존

### 두 문장의 차이

`catch` 블록 안에서 잡은 예외를 다시 던지는 방법은 두 가지로 **보인다.**

```csharp
catch (Exception e)
{
    // ...
    throw e;    // (A) 새로 던진다
}

catch (Exception e)
{
    // ...
    throw;      // (B) 다시 던진다
}
```

두 코드는 같은 예외 객체를 다시 던진다. 던져지는 객체의 참조는 동일하다. 그런데 **CLR이 "이 예외가 어디서 시작됐다고 생각하는가"가 달라진다.**

> **⚠️ `throw ex`는 스택 트레이스를 그 자리에서 잘라 버린다**
>
> 예외를 던질 때 CLR은 그 예외의 **시작점을 재설정한다.** 즉 가장 최근에 던져진 위치만 기억한다.
>
> `throw e;`는 새로운 `throw`이므로 CLR이 시작점을 `catch` 블록의 그 줄로 재설정한다. 원래 예외가 어느 깊은 호출에서 시작됐는지에 대한 정보가 사라진다.
>
> `throw;`는 **재던지기(rethrow)** 이며 CLR이 시작점을 재설정하지 않는다. 원래 위치가 보존된다.

정적 분석기(예전의 FxCop, 지금의 .NET 분석기)는 `catch` 안의 `throw ex;`를 경고로 표시하고 `throw;`는 표시하지 않는다.

### 컴파일 결과 — 옵코드가 다르다

이 차이는 언어 수준의 마술이 아니다. **IL 명령 자체가 다르다.**

```csharp
static void A()
{
    try { Work(); }
    catch (Exception e) { throw e; }
}

static void B()
{
    try { Work(); }
    catch (Exception) { throw; }
}
```

```il
// A()의 핸들러
  catch [System.Runtime]System.Exception
  {
    IL_0007:  stloc.0
    IL_0008:  ldloc.0
    IL_0009:  throw          // ← 새로운 throw
  }

// B()의 핸들러
  catch [System.Runtime]System.Exception
  {
    IL_0007:  pop
    IL_0008:  rethrow        // ← 전혀 다른 명령
  }
```

| 항목 | `throw` (0x7A) | `rethrow` (0xFE 0x1A) |
|---|---|---|
| 피연산자 | 평가 스택에서 예외 객체를 뽑는다 | 없다. 현재 처리 중인 예외를 쓴다 |
| 쓸 수 있는 위치 | 어디서나 | `catch` 핸들러 블록 안에서만 |
| 스택 트레이스 | 이 지점으로 재설정 | 원래 지점 유지 |
| C# 문법 | `throw expr;` | `throw;` |

`rethrow`는 `catch` 핸들러 블록 밖에서 쓰면 IL 검증에 실패한다. C#에서 `try` 밖에 `throw;`만 쓰면 컴파일 오류가 나는 이유다.

### 무엇이 잘리는가 — 그림으로

```text
     원래 스택            throw ex 후          throw; 후
 ┌────────────────┐    ┌────────────┐    ┌────────────────┐
 │ Deep()  ← 발생  │    │     —      │    │ Deep()  ← 보존  │
 │ Middle()       │    │     —      │    │ Middle()← 보존  │
 │ Catcher()←catch│    │ Catcher()  │    │ Catcher()      │
 │ Top()          │    │ Top()      │    │ Top()          │
 └────────────────┘    └────────────┘    └────────────────┘
                       Deep과 Middle이     원래 프레임이
                       통째로 사라진다      그대로 남는다
```

운영 환경에서 이 차이는 결정적이다. `throw ex`로 잘린 로그를 받으면 "예외가 `Catcher`의 47번째 줄에서 났다"는 사실만 알 수 있고, 진짜 원인인 `Deep()`은 보이지 않는다.

> **⚠️ `throw`/`rethrow` 어느 쪽이든 Windows Error Reporting에는 마지막 위치가 보고된다**
>
> CLR은 `rethrow`에서 시작점을 재설정하지 않지만, **Windows는 재설정한다.** 그래서 예외가 끝내 처리되지 않아 프로세스가 죽으면, Windows Error Reporting에 보고되는 스택 위치는 CLR이 아는 원래 위치가 아니라 **마지막 `throw`/`rethrow` 위치**다.
>
> 현장에서 실패한 애플리케이션을 디버깅하기 어렵게 만드는 요인이며, 이 문제 때문에 아예 `catch`를 쓰지 않고 플래그와 `finally`로 우회하는 개발자도 있다.
>
> ```csharp
> private void SomeMethod()
> {
>     bool trySucceeds = false;
>     try
>     {
>         // ...
>         trySucceeds = true;
>     }
>     finally
>     {
>         if (!trySucceeds) { /* catch에 넣었을 코드를 여기에 */ }
>     }
> }
> ```
>
> 이 관용구는 스택을 건드리지 않는다는 장점이 있지만 읽기 어렵다. **더 나은 답은 예외 필터(32.7절)** 다.

### 그렇다면 `throw e.InnerException`은?

32.4절에서 본 리플렉션 관용구를 다시 보자. `catch (TargetInvocationException e) { throw e.InnerException; }`에서 `e.InnerException`은 이미 스택 트레이스를 갖고 있는 객체다. 그런데 `throw`로 다시 던지면 CLR이 시작점을 이 줄로 재설정한다. 원래 트레이스는 덮어써진다.

`rethrow`를 쓸 수도 없다. `rethrow`는 "지금 처리 중인 예외"를 던지는데, 지금 처리 중인 것은 `TargetInvocationException`이지 그 내부 예외가 아니다.

### `ExceptionDispatchInfo` — 잡은 예외를 나중에, 원래 스택으로

이 문제의 표준 해법이 `System.Runtime.ExceptionServices.ExceptionDispatchInfo`다.

```csharp
public sealed class ExceptionDispatchInfo
{
    public static ExceptionDispatchInfo Capture(Exception source);
    public Exception SourceException { get; }
    public void Throw();
    public static void Throw(Exception source);          // 캡처와 던지기를 한 번에
    public static Exception SetCurrentStackTrace(Exception source);   // ※.NET 5
}
```

`Capture`는 예외 객체의 **현재 스택 트레이스 상태를 붙잡아** `ExceptionDispatchInfo` 인스턴스에 보관한다. 나중에 `Throw()`를 호출하면 원래 트레이스를 잃지 않고 다시 던진다.

```csharp
private static void Reflection(object o)
{
    try
    {
        var mi = o.GetType().GetMethod("DoSomething");
        mi.Invoke(o, null);
    }
    catch (System.Reflection.TargetInvocationException e)
    {
        // 내부 예외를 원래 스택 트레이스 그대로 다시 던진다
        ExceptionDispatchInfo.Throw(e.InnerException!);
        throw;   // 도달하지 않지만, 컴파일러의 흐름 분석을 위해 필요
    }
}
```

> **📌 `ExceptionDispatchInfo.Throw`는 스택 트레이스를 이어 붙인다**
>
> `throw ex`가 트레이스를 **덮어쓰는** 것과 달리, `ExceptionDispatchInfo.Throw`는 원래 트레이스를 보존한 채 그 아래에 새 프레임을 **덧붙인다.** 두 트레이스 사이에는 구분 줄이 들어간다.
>
> ```text
>    at Deep()
>    at Middle()
>    --- End of stack trace from previous location ---
>    at Reflection(Object o)
>    at Main()
> ```
>
> 구분 줄의 정확한 문구는 런타임 버전에 따라 다르다(.NET Framework 쪽이 더 길다). 로그 파서를 이 문자열에 의존시키지 마라.
>
> `await`가 태스크에 저장된 예외를 다시 던질 때도 같은 메커니즘이 쓰인다. 비동기 스택 트레이스에 이 구분 줄이 보이는 이유다(47장).

`ExceptionDispatchInfo`가 진가를 발휘하는 곳은 **예외를 잡아 두었다가 나중에, 다른 스레드에서 다시 던지는** 시나리오다. `catch`에서 `ExceptionDispatchInfo.Capture(e)`의 결과를 필드에 보관해 두었다가, 나중에 그 인스턴스의 `Throw()`를 호출하면 된다.

한 스레드에서 잡은 예외를 다른 스레드에서 다시 던지는 것은 **정당한 패턴이다.** 예외가 첫 스레드에서 삼켜지긴 하지만, 다른 스레드가 다시 던지므로 애플리케이션에서 숨겨지지 않는다. `Task`가 하는 일이 정확히 이것이다(46.4절).

`SetCurrentStackTrace`(※.NET 5)는 아직 던져지지 않은 예외 객체에 현재 위치의 스택 트레이스를 심는다. 예외 객체를 캐싱해 재사용하는 고성능 코드에서 쓴다.

> **💡 언제 어느 것을 쓰는가**
>
> | 상황 | 쓸 것 |
> |---|---|
> | 잡은 예외를 그대로 위로 올린다 | `throw;` |
> | 문맥을 얹어 위로 올린다 | `e.Data.Add(...)` 후 `throw;` |
> | 저수준 예외를 고수준 예외로 번역한다 | `throw new MyException(msg, e);` |
> | 감싸인 예외의 알맹이를 원래 트레이스로 올린다 | `ExceptionDispatchInfo.Throw(inner)` |
> | 예외를 저장했다가 나중/다른 스레드에서 던진다 | `Capture` → `Throw()` |
> | 조건에 따라 잡을지 말지 정한다 | `when` 필터 (32.7절) |
> | **`throw e;`** | **거의 언제나 잘못이다** |

### 예외 번역 — 계약을 지키기 위해 다른 예외로 바꾸기

한 예외를 잡아 **다른** 예외를 던지는 정당한 이유가 하나 있다. **메서드 계약의 의미를 지키기 위해서**다.

```csharp
internal sealed class PhoneBook
{
    private readonly string _pathname;   // 주소록 파일 경로

    public PhoneBook(string pathname) => _pathname = pathname;

    public string GetPhoneNumber(string name)
    {
        try
        {
            using var fs = new FileStream(_pathname, FileMode.Open);
            return LookUp(fs, name);
        }
        catch (Exception e) when (e is FileNotFoundException or IOException)
        {
            // 다른 예외를 던지되, 원인을 InnerException으로 보존한다
            throw new NameNotFoundException(name, e);
        }
    }

    private static string LookUp(Stream s, string name) { /* ... */ }
}
```

전화번호부 데이터가 파일에서 온다는 것은 **구현 세부사항**이다. 나중에 데이터베이스로 바뀔 수도 있다. 호출자가 `FileNotFoundException`을 보게 되면 그건 계약에 없던 것이고, 호출자로서는 예상할 방법이 없었다. 그래서 `NameNotFoundException`으로 번역한다. 원인은 `InnerException`으로 보존한다.

> **⚠️ 예외 번역은 두 가지 거짓말을 한다**
>
> 1. **무엇이 잘못됐는지에 대해 거짓말한다.** 실제로는 파일이 없었는데 이름을 못 찾았다고 보고한다.
> 2. **어디서 실패했는지에 대해 거짓말한다.** `FileNotFoundException`이 그대로 올라갔다면 `StackTrace`는 `FileStream` 생성자를 가리켰을 것이다. 새 예외를 던지면 트레이스는 `catch` 블록 안, 진짜 발생 지점에서 몇 줄 떨어진 곳을 가리킨다.
>
> 디버깅을 매우 어렵게 만들 수 있으므로 **아주 조심해서** 써야 하고, 번역할 때는 반드시 원래 예외를 `InnerException`으로 넘겨야 한다.
>
> 반대로, 만약 `PhoneBook`이 `PhoneBookPathname` 속성을 공개해 "이 데이터는 파일에서 온다"가 계약의 일부가 됐다면 번역하면 안 된다. 그때는 `FileNotFoundException`을 그대로 올려보내는 것이 정직하다.

번역할 때 던지는 새 예외는 **구체적인 타입**이어야 한다. 다른 예외의 기반 타입으로 쓰이지 않는 타입이라는 뜻이다.

부가 정보만 붙이고 싶은 것이라면 번역하지 마라. `Data`에 넣고 `throw;` 하면 된다(32.3절).

## 32.6 예외 처리 메커니즘 — 2단계 처리(1st pass 필터, 2nd pass 언와인딩)

### 예상과 다른 것

"예외가 던져지면 CLR이 스택을 언와인딩하면서 위로 올라가다가 맞는 `catch`를 만나면 멈춘다." 대부분의 개발자가 갖고 있는 모델이고, **틀렸다.** 실제로는 **2단계 모델**이며, Windows의 구조적 예외 처리(SEH)에서 물려받은 것이다.

### 알고리즘

**1단계 (first pass) — 핸들러 탐색**

1. 예외가 던져지고 1단계가 시작된다.
2. CLR이 스택을 훑으며 **어느 `catch` 블록이 이 예외를 처리할지** 찾는다. (이 블록을 편의상 "처리하는 `catch`"라 부른다.)
3. 예외 타입이 호환되는 `catch` 블록만 후보가 된다.
4. `catch`에 예외 필터가 붙어 있으면 **필터를 지금 실행한다.** `false`를 반환하면 이 `catch`는 처리하지 않는다.
5. 필터가 없는 `catch`는 항상 `true`를 반환하는 필터와 같다.

**2단계 (second pass) — 언와인딩**

6. 처리하는 `catch`가 정해졌으니 2단계가 시작된다.
7. CLR이 예외가 던져진 지점부터 그 `catch`가 있는 프레임까지 **스택을 언와인딩한다.**
8. 언와인딩 도중 만나는 모든 `finally` 블록이 실행된다. (처리하는 `catch`와 짝지어진 `finally`는 여기 포함되지 않는다.)
9. 처리하는 `catch` 블록이 실행된다.
10. 그 `catch`와 짝지어진 `finally`가 있으면 마지막으로 실행된다.

**결정적 결론: 필터는 스택이 아직 살아 있는 상태에서 실행된다.**

### 눈으로 확인하기

세 단계 호출을 만들어 순서를 관찰하자. `Bottom`이 `Middle`을 부르고 `Middle`이 `Top`을 부른다.

```csharp
static bool LogAndReturn(string message, bool result)
{
    Console.WriteLine(message);
    return result;
}

static void Top()
{
    try
    {
        throw new Exception();
    }
    finally
    {
        Console.WriteLine("Top finally");    // 2단계에 실행
    }
}

static void Middle()
{
    try
    {
        Top();
    }
    catch (Exception e) when (LogAndReturn("Middle filter", false))
    {
        Console.WriteLine("Caught in middle");   // 필터가 false라 실행 안 됨
    }
    finally
    {
        Console.WriteLine("Middle finally");     // 2단계에 실행
    }
}

static void Bottom()
{
    try
    {
        Middle();
    }
    catch (IOException e) when (LogAndReturn("Never called", true))
    {
        // 타입이 안 맞으므로 필터조차 실행되지 않는다
    }
    catch (Exception e) when (LogAndReturn("Bottom filter", true))
    {
        Console.WriteLine("Caught in Bottom");
    }
}

static void Main() => Bottom();
```

출력은 이렇다.

```text
Middle filter
Bottom filter
Top finally
Middle finally
Caught in Bottom
```

**두 필터가 두 `finally`보다 먼저 실행됐다.** 이것이 2단계 모델의 직접적 증거다. 순차 모델이었다면 `Top finally`가 `Middle filter`보다 먼저 나왔어야 한다.

`Never called`가 출력되지 않은 것도 중요하다. `catch (IOException)`은 타입이 맞지 않으므로 **필터 식 자체가 평가되지 않는다.** 타입 검사가 필터보다 먼저다.

### 진행 그림

```text

 Top           Top이 예외를 던진다. 1단계 시작          —

 ────────────────────────────────────────────────────────────────
 Top           스택을 내려가며 Middle의 필터 평가.   Middle filter

 ────────────────────────────────────────────────────────────────

 Middle        1단계 완료! 2단계 시작

```

### 런타임 구현

예외 핸들러는 **펀클릿(funclet)** 이라 부르는 별도 코드 조각으로 JIT 컴파일된다(11.7절). 예외 처리 중에 런타임이 그것을 호출한다. 필터도 펀클릿이다. **필터 펀클릿은 원래 프레임의 지역 변수에 접근할 수 있도록 부모 프레임 포인터를 넘겨받아 호출된다** — 그래서 필터 안에서 `catch`가 속한 메서드의 지역 변수를 읽을 수 있다.

> **📌 ※.NET 9 — 예외 처리 구현이 관리 코드로 바뀌었다**
>
> CoreCLR의 예외 처리 구현이 네이티브 코드에서 관리 코드로 교체됐다. NativeAOT에서 쓰던 구현을 CoreCLR로 가져온 것이다. **관찰 가능한 의미론 — 2단계 모델, 필터 실행 시점, `finally` 순서 — 은 동일하다.**
>
> 이전 구현으로 되돌리려면 런타임 구성에 `System.Runtime.LegacyExceptionHandling`을 `true`로 설정한다. 새 구현에서 문제가 재현되는 경우의 비교 진단용이며, 일반적으로 켤 이유가 없다.

### 보안적 함의

2단계 모델은 보안상 중요한 결과를 낳는다.

> **⚠️ 적대적 코드가 당신의 `finally`보다 먼저 실행될 수 있다**
>
> 당신의 메서드가 신뢰할 수 없는 코드에서 호출될 수 있고 그 메서드가 예외를 밖으로 내보낸다면, **호출자는 예외 필터를 이용해 당신의 `finally`가 실행되기 전에 자기 코드를 실행할 수 있다.** 필터는 1단계에, `finally`는 2단계에 실행되기 때문이다.
>
> 그래서 **보안에 민감한 것을 `finally`에 두면 안 된다.** `try`에서 권한을 상승시키고 `finally`에서 되돌리는 구조라면, 상승된 권한 상태에서 남의 코드가 실행될 수 있다. `using`과 `lock`도 결국 `finally`이므로 같은 성질을 갖는다.
>
> 대부분의 코드는 우호적 환경에서만 돌기 때문에 이 걱정을 할 필요가 없다. 하지만 플러그인 호스트나 샌드박스를 만든다면 반드시 알아야 한다.

### 필터에서 예외가 나면

필터 식 자체가 예외를 던지면 어떻게 되는가.

> **⚠️ 필터 안에서 절대 예외를 던지지 마라**
>
> 새 예외가 현재 예외가 되고, 원래 예외에 대한 정보를 되찾을 수 없게 된다. 필터가 실행되는 시점은 1단계 한복판이며, 이 상태에서 예외가 나면 진단 정보가 파괴된다.
>
> 실무 규칙은 단순하다. **필터 식은 부작용 없는 순수 검사이거나, 절대 실패하지 않도록 방어적으로 작성된 로깅이어야 한다.** 널 조건 연산자를 쓰고, 사전을 조회할 때는 `TryGetValue`를 쓰고, 파싱은 `TryParse`를 쓴다.
>
> ```csharp
> // 나쁨: ex.Data["Code"]가 없으면 예외, InnerException이 null이면 예외
> catch (Exception ex) when ((int)ex.Data["Code"] == 42) { }
>
> // 좋음
> catch (Exception ex) when (ex.Data["Code"] is int code && code == 42) { }
> ```

### 왜 이 모델을 아는 것이 중요한가

세 가지 실용적 결론이 따라 나온다.

| 결론 | 근거 |
|---|---|
| **필터는 스택이 살아 있을 때 실행된다** | 1단계는 언와인딩 전이다. 필터 안에서 덤프를 뜨면 원래 스택이 전부 보인다 |
| **처리되지 않는 예외에서는 `finally`가 안 돌 수 있다** | 1단계가 실패하면 2단계가 시작되지 않는다 |
| **`when`이 `catch`-후-재던지기보다 싸고 정확하다** | 재던지기는 언와인딩을 한 번 하고 다시 시작한다. 필터는 언와인딩을 아예 안 한다 |

세 번째가 다음 절의 주제다.

## 32.7 예외 필터(`when`)가 catch-rethrow보다 나은 이유

### 같은 일을 하는 두 코드

웹 요청을 최대 3회 재시도하는 코드를 두 가지로 써 보자.

**필터 방식**

```csharp
var retryCount = 0;
var dataString = default(string);

while (dataString == null)
{
    try
    {
        dataString = MakeWebRequest();
    }
    catch (TimeoutException e) when (retryCount++ < 3)
    {
        Console.WriteLine("Operation timed out. Trying again");
        Thread.Sleep(1000 * retryCount);   // 동기 코드이므로 대기도 동기다
    }
}
```

**catch-후-재던지기 방식**

```csharp
    try
    {
        dataString = MakeWebRequest();
    }
    catch (TimeoutException e)
    {
        if (retryCount++ < 3)
        {
            Console.WriteLine("Timed out. Trying again");
            Thread.Sleep(1000 * retryCount);
        }
        else
            throw;
    }
```

기능은 같다. 실행 방식은 전혀 다르다.

### 차이 1 — 스택 언와인딩

**필터 방식**에서 컴파일러가 만드는 코드는 **언와인딩이 일어나기 전에** 필터를 평가한다. 원래 예외 위치가 알려져 있고, 지역 변수 값을 포함해 호출 스택의 모든 정보가 아직 유효하다. 식이 `false`를 반환하면 런타임은 스택 위쪽으로 계속 탐색하며, **프로그램 상태는 전혀 흐트러지지 않는다.**

**catch-후-재던지기 방식**에서는 런타임이 처리할 `catch` 절을 찾는 즉시 **언와인딩을 시작한다.** 언와인딩되는 메서드들에 선언된 지역 변수 대부분은 도달 가능한 루트를 잃는다(클로저에 갇힌 변수는 클로저가 살아 있으면 접근 가능하다). 근본 원인 진단에 필요한 값들이 사라진다. 그리고 `catch` 안에서 "복구할 수 없다"고 판단해 `throw;`로 다시 던지면, 언와인딩을 한 번 하고 처음부터 탐색을 다시 시작하는 셈이다.

### 차이 2 — 스택 트레이스에 기록되는 위치

```csharp
static void TreeOfErrors()
{
    try
    {
        SingleBadThing();
    }
    catch (RecoverableException e)
    {
        throw;   // ← 호출 스택에 이 줄이 보고된다
    }
}

static void TreeOfErrorsTwo()
{
    try
    {
        SingleBadThing();   // ← 호출 스택에 이 줄이 보고된다
    }
    catch (RecoverableException e) when (false)
    {
        Console.WriteLine("Can't happen");
    }
}
```

`throw;` 문법을 쓰면 호출 스택에 **`throw`의 위치**가 보고된다. 실행이 `catch` 절에 진입했고 거기서 다시 던졌기 때문이다. `try` 절 안의 그 윗줄은 사라진다.

필터를 쓰면 호출 스택에 **예외를 유발한 메서드 호출의 위치**가 보고된다.

위 예제는 최소 크기라 어디서 예외가 났는지 명백하다. 큰 애플리케이션에서는 그렇지 않다.

> **⚠️ `throw;`가 스택 트레이스를 보존한다는 말과 모순 아닌가?**
>
> 모순이 아니다. 정확히 구분하자.
>
> - `throw;`(rethrow)는 **예외 객체가 이미 갖고 있던 트레이스를 지우지 않는다.** `throw ex;`와 대비되는 이 성질은 32.5절의 내용이며 여전히 맞다.
> - 하지만 재던지기 자체가 **새 프레임을 트레이스에 추가한다.** 예외가 `catch`에 진입했다가 나갔다는 사실이 기록에 남고, `try` 블록 안의 어느 줄에서 났는지는 그 프레임의 정보로 대체된다.
>
> 즉 `throw ex` < `throw;` < `when` 순으로 정보가 더 보존된다. **`when`이 최선이다.**

### 차이 3 — 성능

.NET CLR은 **`catch` 절에 진입하지 않는 `try`/`catch` 블록의 존재가 런타임 성능에 미치는 영향이 최소가 되도록** 최적화되어 있다. 반면 **스택 언와인딩과 `catch` 절 진입은 런타임에 큰 영향을 준다.**

예외 필터는 처리할 수 없는 예외에 대해 언와인딩과 `catch` 진입을 회피한다. 그래서 성능을 개선할 수 있고, **최소한 나빠지게 하지는 않는다.**

### 어디에 쓰는가

| 유형 | 예 | 필터 식 |
|---|---|---|
| **예외 속성에 따른 분기** | `WebException.Status`, `COMException.HResult`, HTTP 상태 코드 | `when (e.Status == ...)` |
| **재시도 정책** | 남은 시도 횟수, 백오프 상태 | `when (attempts-- > 0)` |
| **환경 조건** | 디버거 연결 여부, 기능 플래그 | `when (!Debugger.IsAttached)` |

`AggregateException`처럼 여러 예외를 담는 타입도 좋은 후보다. `Task`는 자식 태스크가 여러 개일 수 있어 여러 예외로 실패할 수 있고, 그래서 `Task.Exception`은 항상 `AggregateException`이다. 처리할 수 있는 예외인지 판단하려면 `InnerExceptions`를 들여다봐야 하는데, **필터가 그 로직을 `catch` 진입 없이 수행한다**(32.13절).

### 습관 바꾸기

```csharp
// 이전 습관
catch (SqlException e)
{
    if (e.Number == 1205) RetryTransaction();   // 데드락 희생자
    else throw;
}

// 바꿀 형태
catch (SqlException e) when (e.Number == 1205)
{
    RetryTransaction();
}
```

**`catch` 절 안에서 조건을 검사한 뒤 `throw;`로 끝나는 분기가 있다면, 그 조건은 `when`으로 옮겨야 한다.** 이 규칙 하나만 지켜도 진단 품질이 크게 오른다.

> **💡 예외의 타입만으로 부족할 때가 필터의 자리다**
>
> 예외에 대해 타입 이상의 정보가 필요하다면, `catch` 절에 진입하기 전에 복구 가능 여부를 판단하도록 예외 필터를 추가하라. `catch` 절은 **완전히 처리할 수 있을 때만** 실행되게 하라.

### 필터의 한계

> **⚠️ 필터는 `try` 블록 자체를 되돌리지 않는다**
>
> `when (attempts++ < 3)` 같은 필터는 예외를 잡지 **않기로** 결정할 뿐, 이미 부분적으로 수행된 작업을 되돌리지 않는다. 재시도 루프를 만들 때는 `try` 블록의 연산이 **멱등(idempotent)** 하거나, 실패해도 상태를 바꾸지 않아야 한다(32.11절).

> **⚠️ 재시도 계층이 겹치면 실패 보고가 지연된다**
>
> 여러 추상화 계층이 각자 "친절하게" 투명한 재시도를 하면, 실제 실패가 로그에 남기까지 시간이 기하급수로 늘어난다. 3회씩 재시도하는 계층 세 개가 겹치면 27회다. **이 패턴은 자기 자신과 잘 합성되지 않는다.** 애플리케이션 전체 스택을 통제한다면 재시도가 일어날 계층을 하나로 정하고, 한 계층만 책임진다면 **재시도를 구성 가능하게** 만들어 전체를 통제하는 개발자가 끌 수 있게 하라.

> **⚠️ 필터의 부작용은 필터가 평가되지 않으면 일어나지 않는다**
>
> `when (retryCount++ < 3)`처럼 필터 식에 부작용을 넣으면, **그 예외 타입이 던져질 때만** 카운터가 증가한다. 다른 타입의 예외가 나면 필터가 평가되지 않으므로 카운터는 그대로다. 재시도 상태를 필터 식의 부작용에만 의존시키면 미묘한 버그가 생긴다.

## 32.8 예외 필터의 부수 효과 활용 — 로깅과 재시도

### 항상 `false`를 반환하는 필터

앞 절에서 필터가 **1단계에서, 스택이 언와인딩되기 전에** 실행된다는 것을 봤다. 그렇다면 **잡을 생각이 전혀 없어도 필터를 다는 것**이 의미를 갖는다. 항상 `false`를 반환하는 필터는 형용 모순처럼 들리지만, 예외가 발생하는 순간을 관찰하는 강력한 방법이다.

### 로깅 관용구

```csharp
public static bool ConsoleLogException(Exception e)
{
    var oldColor = Console.ForegroundColor;
    Console.ForegroundColor = ConsoleColor.Red;
    Console.WriteLine("Error: {0}", e);
    Console.ForegroundColor = oldColor;
    return false;      // ← 반드시 false
}
```

```csharp
try
{
    data = MakeWebRequest();
}
catch (Exception e) when (ConsoleLogException(e)) { }
catch (TimeoutException e) when (failures++ < 10)
{
    Console.WriteLine("Timeout error: trying again");
}
```

이 관용구에는 중요한 규칙이 있다.

**첫째, 필터는 반드시 항상 `false`를 반환해야 한다.** `true`를 반환하면 로깅 메서드가 예외 전파를 멈춰 버린다.

**둘째, `catch` 절이 기반 `Exception`을 잡는다.** 그래야 모든 예외를 로깅할 수 있다.

**셋째, 기반 `Exception`을 잡는데도 `catch` 목록의 맨 앞에 올 수 있다.** 이 `catch` 절은 예외를 결코 처리하지 않으므로 런타임은 계속 다음 `catch`를 찾는다. 그래서 뒤의 구체적인 `catch`가 도달 불가능이 되지 않는다.

> **📌 모든 예외를 잡는 `catch`가 허용되는 몇 안 되는 자리**
>
> "`catch (Exception)`을 쓰지 마라"는 이 책 전체를 관통하는 규칙이지만(32.14절), 이 로깅 관용구는 그 규칙의 정당한 예외다. **예외를 처리하지 않기 때문**이다. 잡지 않는 `catch`는 정책을 결정하지 않는다.

**넷째, 위치를 골라 의미를 바꿀 수 있다.**

로깅 `catch`를 **맨 뒤**에 두면, 어느 `catch`에서도 처리되지 않은 예외만 로깅된다.

```csharp
try
{
    data = MakeWebRequest();
}
catch (TimeoutException e) when (failures++ < 10)
{
    Console.WriteLine("Timeout error: trying again");
}
catch (Exception e) when (ConsoleLogException(e)) { }
```

이 배치는 "이 코드가 처리하지 못한 실패"만 골라 기록한다.

### 왜 이것이 다른 로깅 방식보다 나은가

| 방식 | 문제 |
|---|---|
| 최상위 메서드에서만 로깅 | 라이브러리 내부에서 처리된 예외는 전혀 안 보인다 |
| 예외를 던지는 모든 지점에서 로깅 | 내 코드가 던지는 것만 보인다. 하부 코드가 던지는 것은 안 보인다 |
| 잡아서 로깅하고 다시 던지기 | **스택 정보가 손상된다.** 사용자의 디버깅을 더 어렵게 만든다 |

필터 방식은 이 셋의 문제를 모두 피한다. **라이브러리 작성자가 자기 공개 API마다 이 관용구를 넣으면, 스택 정보를 전혀 건드리지 않고 라이브러리 경계에서 예외를 기록할 수 있다.** 그리고 실행 흐름에 영향을 주지 않으므로 어디에나 추가할 수 있다 — 기존 `catch` 절 앞에도, `try`/`finally` 앞에도. 특정 타입만 관찰하고 싶으면 `catch`의 타입만 바꾸면 된다.

### 디버거가 붙었을 때만 잡지 않기

필터의 또 다른 용도는 **디버깅 세션에서 `catch`가 실행되지 않게 하는 것**이다.

```csharp
catch (TimeoutException e) when ((failures++ < 10) &&
                                 (!System.Diagnostics.Debugger.IsAttached))
{
    Console.WriteLine("Timeout error: trying again");
}
```

`Debugger.IsAttached`는 **런타임 환경**에 의해 결정된다. 디버그 빌드인지 릴리스 빌드인지와 무관하며, 프로세스에 디버거가 붙어 있을 때만 `true`다. 이 관용구를 코드베이스 전체에 적용하면 디버거 아래에서 애플리케이션이 **어떤 예외도 잡지 않는다.** 디버거를 "모든 처리되지 않은 예외에서 중단"으로 설정해 두면 예외가 던져지는 순간 그 자리에서 멈춘다. 큰 코드베이스에서 근본 원인을 찾는 훌륭한 도구다.

> **⚠️ 이 관용구를 운영 코드에 넣을 때는 신중하라**
>
> `Debugger.IsAttached`는 운영 환경에서 항상 `false`이므로 실질적으로는 안전하다. 하지만 **운영 서버에 디버거를 붙여 진단하는 순간 애플리케이션이 예외를 하나도 잡지 않게 된다.** 서비스가 그 자리에서 무너질 수 있다. 조건부 컴파일(`#if DEBUG`)로 감싸거나 기능 플래그로 켜고 끌 수 있게 하라.

### 재시도 관용구의 완전한 형태

```csharp
static T Retry<T>(Func<T> operation, int attempts)
{
    while (true)
    {
        try
        {
            attempts--;
            return operation();
        }
        catch (Exception e) when (attempts > 0)
        {
            Console.WriteLine($"Failed: {e}");
            Thread.Sleep(5000);
        }
    }
}
```

`while (true)` 루프가 여기서는 타당하다. `attempts`를 조건으로 하는 루프를 쓸 수도 있지만 **필터가 이미 그 조건을 표현하고 있으므로** 중복이고 오해를 부른다. 그리고 컴파일러 관점에서 루프의 끝이 도달 가능해지면 메서드 끝에 `return`이나 `throw`가 필요해진다.

> **⚠️ 이 재시도 구현은 교육용이다**
>
> 실무 재시도는 훨씬 복잡하다. 최소한 다음이 필요하다.
>
> - **재시도 가능한 실패인지 판별하는 필터.** 모든 예외를 재시도하면 안 된다. `ArgumentNullException`을 세 번 재시도해 봐야 세 번 실패한다
> - **호출 사이의 지연**, 그리고 **지수 백오프**
> - **지터(jitter)**. 무작위 요소가 없으면 재시도하는 클라이언트들이 동기화되어 동시에 몰린다
> - **취소 토큰**과 전체 시간 예산
>
> `Thread.Sleep`으로 대기하는 것은 스레드를 낭비한다. 비동기 코드라면 `await Task.Delay(...)`를 써야 한다(51.4절에서 타임아웃·재시도·취소의 결합을 다룬다).
>
> 프로덕션에서는 직접 만들기보다 검증된 라이브러리를 쓰는 것이 낫다.

### 부작용 필터의 위험

부작용을 가진 필터는 강력하지만 조용히 위험하다.

> **⚠️ 필터는 예상보다 여러 번 실행될 수 있다**
>
> 하나의 예외가 스택을 타고 올라가는 동안 **같은 필터가 여러 번 평가될 수 있다.** 재던지기가 있거나, 예외가 다른 예외를 유발하거나, 중첩된 `try`가 있으면 그렇다. 필터에 카운터 증가나 로그 기록 같은 부작용이 있으면 중복 계상된다.
>
> 로그가 두 번 남는 것은 견딜 만하다. **결제 재시도 카운터가 두 번 감소하는 것은 견딜 수 없다.** 필터의 부작용은 "관찰"에 국한하고 "결정"에 쓰지 마라.

> **⚠️ 필터는 예외를 던진 스레드에서, 그 스레드의 스택 위에서 실행된다**
>
> 필터 안에서 오래 걸리는 일(네트워크 로그 전송, 파일 flush)을 하면 그동안 스택이 언와인딩되지 않고, 그 프레임들이 잡고 있는 자원이 해제되지 않는다. **필터 안의 로깅은 메모리 버퍼에 쓰고 끝내라.** 실제 전송은 비동기 파이프라인에 맡긴다(75.1절).

> **💡 정리 — 필터를 쓰는 세 가지 형태**
>
> | 형태 | 반환값 | 목적 |
> |---|---|---|
> | `when (조건)` | 조건에 따라 | 처리할 수 있을 때만 `catch` 진입 |
> | `when (Log(e))` | 항상 `false` | 스택을 보존한 채 관찰 |
> | `when (retry-- > 0)` | 조건에 따라 | 재시도 정책. 부작용 주의 |

## 32.9 `TryXXX` 메서드 패턴과 예외의 대안

### 문제

`int.Parse`는 파싱에 실패하면 예외를 던진다. 이건 옳은 설계다 — "파싱하라"는 계약을 못 지켰으니까. 그런데 마이크로소프트는 여러 고객으로부터 **최종 사용자가 입력한 데이터를 `Parse`에 넘기는데 그 데이터가 파싱되지 않는 일이 잦다**는 피드백을 받았다. `Parse`가 자주 호출되고 자주 실패하니, 예외를 던지고 잡는 비용이 애플리케이션 전체 성능에 큰 부담이 됐다. 이 상황을 해결하면서 예외 설계 지침도 지키는 방법이 `TryXXX` 패턴이다.

```csharp
public static bool TryParse(string s, out int result);
public static bool TryParse(string s, NumberStyles styles,
                            IFormatProvider provider, out int result);
```

반환값 `bool`은 문자열이 파싱 가능한 문자로 이루어져 있는지를 알려준다. `true`면 `result`에 결과가 들어 있고, `false`면 `result`는 0이지만 그 값을 봐서는 안 된다.

### 규칙 — `bool`은 오직 한 종류의 실패만 뜻한다

> **⚠️ `TryXXX`가 `false`를 반환하는 실패는 딱 하나여야 한다**
>
> `TryXXX` 메서드의 `bool` 반환값은 **단 한 가지 유형의 실패**를 나타낸다. 그 외의 모든 실패에 대해서는 여전히 예외를 던져야 한다.
>
> 예를 들어 `int.TryParse`는 `styles` 인수가 유효하지 않으면 `ArgumentException`을 던진다. 그리고 `TryParse`를 호출하는 중에 `OutOfMemoryException`이 날 수도 있다.
>
> "`Try`가 붙었으니 절대 예외가 안 난다"는 오해가 널리 퍼져 있는데, 틀렸다. **`TryXXX`는 예외를 없애는 것이 아니라, 예상되는 흔한 실패 하나를 예외에서 제외하는 것이다.**

### 구현 방향

`TryXXX`를 만들 때 방향은 **`XXX`가 `TryXXX`를 호출하는 것**이다. 반대가 아니다.

```csharp
public return-type XXX(input-type input)
{
    return-type returnValue;
    if (!TryXXX(input, out returnValue))
        throw new YYYException(/* ... */);
    return returnValue;
}
```

거꾸로 `TryXXX`가 `XXX`를 호출하고 예외를 잡아 `false`를 반환하게 만들면, 성능 이점이 전부 사라진다. 예외는 여전히 던져지고 잡히기 때문이다.

### 네 메서드 구조

더 일반적인 형태는 조건 검사, 실제 작업, 그리고 두 개의 공개 진입점으로 나누는 것이다.

```csharp
public class DoesWorkThatMightFail
{
    // 조건을 먼저 검사한다. 실패는 false로 알린다
    public bool TryDoWork()
    {
        if (!TestConditions()) return false;
        Work();                 // 그래도 예외는 날 수 있다
        return true;
    }

    // 실패가 치명적 문제를 뜻할 때만 호출한다
    public void DoWork() => Work();

    private bool TestConditions() { /* 인수와 내부 상태 검사 */ return true; }
    private void Work() { /* 실제 작업 */ }
}
```

호출자는 이렇게 쓴다.

```csharp
if (!worker.TryDoWork())
{
    ReportErrorToUser("Test Conditions Failed. Please check widgets");
}
```

`TryDoWork`를 제공하지 않으면 사용자는 정상 워크플로에서도 `try`/`catch`를 써야 한다. 예외를 제어 흐름으로 쓰도록 강요하는 API인 셈이다.

> **💡 언제 `TryXXX`를 추가하는가**
>
> **먼저 최선의 객체 모델을 만들어라.** 생성자·메서드·속성은 "호출하면 성공한다"는 전제로 설계한다. 제대로 설계했다면 대부분의 사용에서 실패하지 않고, 예외가 던져지지 않으니 성능 문제도 없다.
>
> 그 뒤에 **사용자로부터 예외 때문에 성능이 문제라는 피드백을 받으면**, 그때 `TryXXX`를 추가하라. 성능 문제를 겪지 않는 사용자는 계속 `XXX` 버전을 쓰면 된다. 그쪽이 더 나은 객체 모델이기 때문이다.
>
> `TryXXX`를 미리 다 만들어 두면 API 표면이 두 배가 되고, 어느 쪽을 써야 하는지 사용자를 혼란스럽게 한다.

`TryXXX` 관용구를 쓰기 가장 좋은 경우는 **신뢰할 수 없는 입력을 처리할 때**다. 사용자 입력, 파일 입력, 알려지지 않은 코드에서 온 매개변수. 이런 실패는 애플리케이션이 정의한 복구 시나리오가 있고, 꽤 자주 일어난다. 예외가 아닌 제어 메커니즘으로 지원해야 한다.

### BCL의 `TryXXX` 목록

| 원본 | Try 버전 | `false`가 뜻하는 것 |
|---|---|---|
| `int.Parse` | `int.TryParse` | 문자열이 숫자 형식이 아니다 |
| `DateTime.Parse` | `DateTime.TryParse` | 문자열이 날짜 형식이 아니다 |
| `Enum.Parse` | `Enum.TryParse` | 이름이 열거형에 없다 |
| `dict[key]` | `dict.TryGetValue` | 키가 없다 |
| `Uri` 생성자 | `Uri.TryCreate` | URI 형식이 아니다 |
| `Stack<T>.Pop` | `Stack<T>.TryPop` | 스택이 비어 있다 |
| `Queue<T>.Dequeue` | `Queue<T>.TryDequeue` | 큐가 비어 있다 |
| — | `ConcurrentDictionary<K,V>.TryAdd` | 키가 이미 있다 |

`TryPop`/`TryDequeue`/`TryPeek`는 .NET Core 2.0에서 추가됐다. `ConcurrentDictionary<K,V>`는 처음부터 `Try` 계열로 설계됐는데, 동시성 환경에서는 "검사 후 실행"이 원자적이지 않아서다(48장).

> **⚠️ `out` 변수를 검사 없이 쓰지 마라**
>
> ```csharp
> int.TryParse(input, out int n);
> UseValue(n);        // false였다면 n은 0이다
> ```
>
> 컴파일러는 이 코드를 통과시킨다. `out` 매개변수는 반환 전에 반드시 대입되기 때문이다. 하지만 `false`일 때의 값은 "정의된 실패 값"이지 유효한 결과가 아니다. **반환값을 반드시 검사하라.**

### 예외의 대안 (1) — `Nullable<T>`

값 타입 결과의 "값 없음"은 `Nullable<T>`로도 표현할 수 있다.

```csharp
public static int? ParseOrNull(string s)
    => int.TryParse(s, out int n) ? n : null;

// 사용
int? maybe = ParseOrNull(input);
int value = maybe ?? -1;
```

`out` 매개변수 없이 한 값으로 결과와 실패를 함께 표현하므로 조합하기 좋다. LINQ 파이프라인에 넣을 수 있는 것도 장점이다.

한계는 명확하다. **왜 실패했는지 알 수 없고, 참조 타입에서는 `null`과 "값 없음"을 구분할 수 없다.** `Nullable<T>` 자체의 구조와 리프팅은 21장에서 다뤘고, 대안 설계는 21.11절이다.

### 예외의 대안 (2) — 결과 타입

실패 이유까지 값으로 표현하려면 **결과 타입**을 만든다.

```csharp
public readonly struct Result<T>
{
    private readonly T _value;
    private readonly string? _error;

    private Result(T value, string? error) { _value = value; _error = error; }

    public static Result<T> Ok(T value) => new(value, null);
    public static Result<T> Fail(string error) => new(default!, error);

    public bool IsOk => _error is null;
    public T Value => IsOk ? _value
        : throw new InvalidOperationException($"실패한 결과입니다: {_error}");
    public string Error => _error
        ?? throw new InvalidOperationException("성공한 결과입니다");

    public Result<TOut> Map<TOut>(Func<T, TOut> f)
        => IsOk ? Result<TOut>.Ok(f(_value)) : Result<TOut>.Fail(_error!);
}
```

```csharp
Result<int> r = ParseAge(input).Map(age => age + 1);
Console.WriteLine(r.IsOk ? r.Value.ToString() : $"오류: {r.Error}");
```

성공과 실패를 하나의 값으로 다루므로 조합이 쉽다. 대신 **모든 호출자가 결과를 검사하도록 강제할 수단이 없고**, 결국 반환 코드 방식의 첫 번째 결함이 되돌아온다. 경계가 좁고 실패가 정상 워크플로의 일부인 계층에서만 쓸 것.

### 예외의 대안 (3) — 전역 오류 저장소 (쓰지 마라)

함수가 아닌 것 — 연산자, 속성 — 은 반환 코드를 쓸 수 없다. 그래서 오래된 API들은 **호출 스택의 모든 함수가 볼 수 있는 공용 장소**에 오류를 두는 방식을 썼다. 스레드별로 현재 오류를 저장하는 정적 메서드 같은 것이며, Win32의 `GetLastError`가 그 예다. 이 방식은 **모든 함수가 오류 전파 패턴에 참여해야** 성립한다. 번거롭고, 아이러니하게도 그 자체가 오류를 유발한다.

> **⚠️ 오류 코드와 예외를 섞으면 최악이다**
>
> "예외는 느리니 우리 코드는 오류 코드를 반환하겠다"고 결정하면 어떻게 되는가. CLR과 클래스 라이브러리는 여전히 예외를 던진다. 그러면 코드는 **두 가지를 모두 다뤄야 한다.** 두 세계의 나쁜 점만 갖게 되는 것이다. 객체지향 플랫폼에서 예외 처리는 선택이 아니라 필수다.

### 선택 기준

| 상황 | 권장 |
|---|---|
| 계약을 지킬 수 없다 | **예외** |
| 흔한 입력 검증 실패, 성능이 문제 | `TryXXX` |
| 값 타입의 "값 없음", 이유가 필요 없다 | `T?` |
| 실패 이유를 값으로 다루고 조합해야 한다 | 결과 타입 |
| 즉시 처리하지 않으면 문제가 커진다 (데이터 무결성) | **예외** |
| 로컬에서 무시해도 큰 문제가 없다 (UI 설정 저장 실패) | 반환 코드로 충분 |

마지막 두 줄이 핵심 판별식이다. **처리되지 않았을 때 오래 지속되는 문제를 만드는 오류 조건에는 예외를 던져라.** 데이터베이스의 데이터 무결성 오류는 무시하면 문제가 커지기만 하므로 예외다. 사용자의 창 위치 설정을 저장하지 못한 것은 파급 효과가 없으므로 실패를 알리는 반환 코드로 충분하다.

## 32.10 애플리케이션 전용 예외 클래스 설계

### 언제 새 타입을 만드는가

기준은 하나다.

> **서로 다른 `catch` 절에서 서로 다른 조치를 취할 수 있을 때, 그리고 오직 그때만 새 예외 클래스를 만든다.**

라이브러리를 쓰는 개발자가 `catch` 절을 쓸 때 구분하는 것은 예외의 **런타임 타입**이다.

```csharp
try { Foo(); Bar(); }
catch (MyFirstApplicationException e1)   { FixProblem(e1); }          // 고칠 수 있다
catch (AnotherApplicationException e2)   { ReportErrorAndContinue(e2); }
catch (YetAnotherApplicationException e3){ ReportErrorAndShutdown(e3); }
catch (Exception e)                      { ReportGenericError(e); throw; }
finally { CleanupResources(); }
```

세 예외가 각각 **다르게 처리된다.** 이럴 때 세 타입이 필요하다. 처리가 같다면 타입을 나누는 것은 그냥 일거리다.

타입을 나누지 않으면 사용자는 두 가지 나쁜 선택지만 갖는다. 예외가 나면 무조건 종료하거나, 예외 내부를 뒤져 고칠 수 있는지 판단하는 것이다.

```csharp
catch (Exception e)
{
    switch (e.TargetSite.Name)      // 매우 취약한 코드
    {
        case "Foo": FixProblem(e); break;
        case "Bar": ReportErrorAndContinue(e); break;
        default: ReportErrorAndShutdown(e); throw;
    }
}
```

이 코드는 메서드 이름을 바꾸면 깨진다. 오류를 유발하는 호출을 공용 유틸리티로 옮겨도 깨진다. **예외가 스택 깊은 곳에서 생성될수록 더 취약해진다.**

> **⚠️ `throw`를 쓸 때마다 새 예외 클래스를 만들라는 뜻은 아니다**
>
> 이 절의 조언이 "예외 클래스를 많이 만들어라" 쪽으로 기울어 있는 이유는 사람들의 자연스러운 성향 때문이다. **개발자는 예외를 던질 때 `System.Exception`을 쓰는 쪽으로 끌린다.** 그건 호출 코드에 가장 적은 정보를 주는 선택이다.
>
> 그러니 균형을 잡아라. 복구 조치가 달라질 수 있는 오류 조건을 찾아 그것에 대해 타입을 만들어라. 파일/디렉터리 부재에서 복구할 수 있는가? 권한 부족에서? 네트워크 자원 부재에서? 각각 다른 조치가 가능하다면 각각의 타입이다.

### 명명과 상속

- 예외 클래스 이름은 **`Exception`으로 끝난다.**
- **`public`으로 선언한다.** 중첩되지 않은 타입의 기본 접근자는 `internal`이므로 명시해야 한다. 예외는 어셈블리 경계를 넘어 전달되므로 호출 코드가 접근할 수 있어야 한다.
- **`System.Exception`이나 적절한 다른 예외 클래스에서 파생시킨다.** `ApplicationException`은 쓰지 마라(32.3절).
- 계층은 **얕고 넓게.**

### 생성자 네 개

`Exception` 클래스는 생성자를 네 개 갖는다 — 기본, `(string message)`, `(string message, Exception inner)`, 그리고 역직렬화용 `protected Exception(SerializationInfo, StreamingContext)`. 새 예외 클래스를 만들 때는 앞의 세 개를 모두 만들고 기반 클래스 구현에 위임한다.

```csharp
public class MyAssemblyException : Exception
{
    public MyAssemblyException() : base() { }
    public MyAssemblyException(string s) : base(s) { }
    public MyAssemblyException(string s, Exception e) : base(s, e) { }
}
```

> **⚠️ 직렬화 생성자는 .NET 5 이후 사실상 유물이다**
>
> 네 번째 생성자와 `[Serializable]`은 예외가 **`AppDomain` 경계를 넘거나 로그·데이터베이스에 기록될 수 있어야 한다**는 .NET Framework 시절 요구에서 나왔다. 그 기반이던 `BinaryFormatter`는 역직렬화 공격 표면 때문에 폐기됐고, .NET 9에서 제거됐다(41.7절).
>
> .NET 8부터는 레거시 직렬화 인프라 API가 `[Obsolete]`로 표시되어(진단 ID `SYSLIB0051`) `protected Exception(SerializationInfo, StreamingContext)`를 호출하면 경고가 난다.
>
> **새 코드에서는 이 생성자와 `[Serializable]`을 넣지 마라.** 예외를 프로세스 경계 너머로 전달해야 한다면 JSON 등 명시적 직렬화 계약(41장)을 설계하라. 다만 .NET Framework를 대상으로 하는 코드베이스나 오래된 라이브러리를 읽을 때는 이 패턴을 보게 될 것이므로, 왜 있는지는 알아 둬야 한다.

### 강타입 속성 추가

기반 클래스에 기능을 더하는 일은 드물다. 예외 클래스의 목적은 **`catch` 절에서 오류 원인을 구별할 수 있게 하는 것**이므로, 이름만 있어도 절반은 달성된다.

그래도 복구에 필요한 데이터가 있다면 강타입 속성으로 노출한다.

```csharp
public class CarIsDeadException : Exception
{
    public DateTime ErrorTimeStamp { get; }
    public string CauseOfError { get; }

    public CarIsDeadException() { }
    public CarIsDeadException(string message) : base(message) { }
    public CarIsDeadException(string message, Exception inner)
        : base(message, inner) { }

    public CarIsDeadException(string message, string cause, DateTime time,
                              Exception inner = null)
        : base(message, inner)
    {
        CauseOfError = cause;
        ErrorTimeStamp = time;
    }
}
```

잡는 쪽은 `Data` 딕셔너리를 뒤질 필요 없이 강타입으로 접근한다.

```csharp
catch (CarIsDeadException e)
{
    Console.WriteLine(e.Message);
    Console.WriteLine(e.ErrorTimeStamp);
    Console.WriteLine(e.CauseOfError);
}
```

> **📌 `Message`를 재정의할 것인가**
>
> `Message`는 가상 속성이므로 재정의할 수 있다. 필드를 따로 두고 `Message`를 오버라이드해 문자열을 조립하는 구현도 가능하다.
>
> ```csharp
> public override string Message => $"Car Error Message: {_messageDetails}";
> ```
>
> 하지만 대부분의 경우 **메시지를 기반 생성자에 넘기는 편이 낫다.** 재정의하면 기반 클래스가 하던 일(널 처리, 지역화된 기본 메시지)을 다시 해야 하고, `Message`가 계산 도중 예외를 던질 위험이 생긴다. 이건 32.2절의 "두 번째 예외" 문제로 이어진다.

### 예외 번역과 `InnerException`

라이브러리를 감쌀 때 저수준 예외를 그대로 흘려보내면 호출자가 얻는 정보가 적다. 자기 라이브러리의 정보를 얹어야 한다.

```csharp
public double DoSomeWork()
{
    try
    {
        return ThirdPartyLibrary.ImportantRoutine();
    }
    catch (ThirdPartyException e)
    {
        throw new DoingSomeWorkException($"Problem with {ToString()} using library", e);
    }
}
```

`ToString()`을 제대로 구현해 두었다면 **문제를 일으킨 객체의 상태 전체를 설명하는 예외**가 되고, `InnerException`이 근본 원인을 가리킨다. 이것이 **예외 번역(exception translation)** 이다. 단, 32.5절의 두 가지 거짓말을 잊지 마라.

### 제네릭으로 반복을 줄이는 접근

예외 클래스를 손으로 쓰는 일이 지루하다는 인식에서 나온 접근이 있다. 예외 인자를 제네릭 타입 매개변수로 받는 예외 클래스 하나를 만들고, 새 "예외 타입"이 필요할 때마다 인자 클래스만 정의하는 것이다.

```csharp
public abstract class ExceptionArgs
{
    public virtual string Message => string.Empty;
}

public sealed class Exception<TExceptionArgs> : Exception
    where TExceptionArgs : ExceptionArgs
{
    public TExceptionArgs Args { get; }

    public Exception(string message = null, Exception innerException = null)
        : this(null, message, innerException) { }

    public Exception(TExceptionArgs args, string message = null,
                     Exception innerException = null)
        : base(message, innerException) { Args = args; }

    public override string Message
        => Args == null ? base.Message : base.Message + " (" + Args.Message + ")";
}

// 새 예외 "타입"은 인자 클래스 하나로 끝난다
public sealed class DiskFullExceptionArgs : ExceptionArgs
{
    public string DiskPath { get; }
    public DiskFullExceptionArgs(string diskPath) => DiskPath = diskPath;
    public override string Message
        => DiskPath == null ? base.Message : "DiskPath=" + DiskPath;
}

// 사용
throw new Exception<DiskFullExceptionArgs>(
    new DiskFullExceptionArgs(@"C:\"), "The disk is full");
```

> **⚠️ 이 접근에는 두 가지 대가가 있다**
>
> 1. **모든 예외 타입이 `System.Exception`에서 직접 파생된다.** 얕고 넓은 계층이 선호되므로 대체로 문제가 아니지만, 의미상 계층이 필요한 경우에는 표현할 수 없다.
> 2. **디버거와 도구가 제네릭 타입 인자를 보여 주지 않는 경우가 있다.** Visual Studio의 처리되지 않은 예외 대화 상자가 `Exception<T>`의 `T`를 표시하지 못한다는 보고가 원천에 있다.
>
> 게다가 반복 작성의 부담 자체가 크지 않다. Visual Studio에는 .NET 모범 사례를 따르는 예외 클래스를 자동 생성하는 코드 조각이 있다 — 편집기에서 `exc`를 입력하고 Tab을 누르면 된다.

> **💡 예외 클래스 체크리스트**
>
> - 이름이 `Exception`으로 끝나는가
> - `public`인가
> - `System.Exception`(또는 의미가 맞는 구체 예외)에서 파생됐는가 — `ApplicationException`이 아닌가
> - 생성자 세 개(기본, 메시지, 메시지+내부 예외)를 모두 제공하는가
> - **잡는 쪽이 이 타입을 다르게 처리할 이유가 실제로 있는가**
> - 다른 예외의 기반 타입으로 쓰이지 않는 구체 타입인가
> - 복구에 필요한 데이터가 강타입 속성으로 노출되는가

## 32.11 강한 예외 보장(strong exception guarantee)

### 왜 필요한가

예외를 던지면 애플리케이션에 파괴적 사건을 도입하는 것이다. 제어 흐름이 훼손됐고, 예상했던 동작이 일어나지 않았다. 더 나쁜 것은 **정리 작업의 부담을 나중에 예외를 잡을 코드에 떠넘겼다**는 점이다. 예외를 잡았을 때 할 수 있는 조치는, 예외가 던져질 때 프로그램 상태를 얼마나 잘 관리했는가에 직접 달려 있다.

C++ 커뮤니티가 1994년부터 2000년까지 6년에 걸쳐 이 문제를 논의했고, Dave Abrahams가 세 가지 예외 안전 보장을 정의했다. C#에서도 그대로 쓸 수 있다.

### 세 가지 보장

| 보장 | 정의 | 비고 |
|---|---|---|
| **기본 보장** (basic) | 예외가 함수를 떠난 뒤에도 자원이 새지 않고 모든 객체가 유효한 상태다 | `finally` 절이 다 실행된 뒤 기준 |
| **강한 보장** (strong) | 기본 보장에 더해, 예외가 발생하면 **프로그램 상태가 변하지 않았다** | 연산은 완료되거나, 아무것도 바꾸지 않는다 |
| **무예외 보장** (no-throw) | 연산이 절대 실패하지 않는다. 즉 메서드가 예외를 밖으로 내보내지 않는다 | 극히 제한된 자리에서만 |

**강한 예외 보장이 복구 가능성과 처리 단순성 사이에서 가장 좋은 균형을 준다.**

### 기본 보장 — CLR이 절반을 해 준다

.NET 환경은 메모리를 관리한다. 예외 때문에 자원이 새는 유일한 경로는 **`IDisposable`을 구현한 자원을 소유한 상태에서 예외를 던지는 것**이고, 그건 `using`으로 막는다(33장).

하지만 그게 이야기의 절반이다. **객체 상태가 유효한지 보장하는 것은 여전히 당신 책임이다.** 컬렉션과 함께 그 크기를 캐시하는 타입을 상상해 보라. `Add()`가 예외를 던졌을 때 캐시된 크기가 실제 저장소와 일치하는지 보장해야 한다. 부분적으로만 완료되면 유효하지 않은 상태를 남기는 연산은 수없이 많다.

### 강한 보장 — 방어적 복사 후 교환

강한 보장을 얻는 표준 절차는 세 단계다. **(1)** 변경할 데이터의 방어적 복사본을 만든다. **(2)** 복사본에 대해 모든 변경을 수행한다 — 예외를 던질 수 있는 모든 연산이 여기 들어간다. **(3)** 임시 복사본을 원본과 교환한다 — **이 연산은 예외를 던질 수 없어야 한다.**

```csharp
public void PhysicalMove(string title, decimal newPay)
{
    // PayrollData는 구조체다.
    // 필드가 유효하지 않으면 생성자가 예외를 던진다.
    PayrollData d = new PayrollData(title, newPay, this.payrollData.DateOfHire);

    // d가 제대로 구성됐다면 교환한다
    this.payrollData = d;
}
```

생성자가 던지면 `this.payrollData`는 손대지 않은 상태로 남는다. 생성자가 성공하면 대입은 실패할 수 없다.

**불변 값 타입으로 데이터를 저장하면** 이 패턴이 훨씬 쉬워진다. 함수형 스타일(LINQ 쿼리 등)은 **자동으로 강한 예외 보장을 따른다.**

### 참조 타입 교환의 함정

이 패턴에는 조용한 함정이 있다.

```csharp
private List<PayrollData> data;

public IList<PayrollData> MyCollection => data;

public void UpdateData()
{
    // 신뢰할 수 없는 연산. 실패할 수 있다
    var temp = UnreliableOperation();

    // UnreliableOperation이 예외를 던지지 않은 경우에만 실행된다
    data = temp;
}
```

방어적 복사의 훌륭한 사용처처럼 보인다. 임시 데이터를 채우고, 성공하면 교환한다. 데이터를 가져오다 무언가 잘못되면 아무 변경도 하지 않는다. **그런데 동작하지 않는다.**

> **⚠️ 교환 기법은 값 타입에서만 통한다**
>
> `MyCollection` 속성은 `data` 객체에 대한 **참조**를 반환한다. 이 클래스의 모든 클라이언트는 `UpdateData`를 호출한 뒤에도 **원래 `List<>`에 대한 참조를 들고 있다.** 그들은 옛 데이터를 보고 있다.
>
> 참조 타입에서는 교환이 통하지 않는다. 값 타입에서만 통한다.

고치려면 현재 참조 객체 안의 데이터를 교체해야 하는데, 그것을 예외 없이 하기는 어렵다. 두 개의 원자적이지 않은 연산 — 기존 객체 제거와 새 객체 추가 — 이기 때문이다.

```csharp
public void UpdateData()
{
    var temp = UnreliableOperation();

    // UnreliableOperation이 성공한 경우에만 실행된다
    data.Clear();
    foreach (var item in temp)
        data.Add(item);
}
```

**합리적이지만 방탄은 아닌** 해법이다. `Clear`와 `Add` 사이에서 예외가 나면 컬렉션은 비어 있는 상태로 남는다. 실무에서는 "합리적"이 필요한 수준일 때가 많고, 그럴 때는 여기까지가 답이다.

### 방탄이 필요할 때 — 봉투-편지 패턴

진짜 방탄이 필요하면 **봉투-편지 패턴(envelope-letter pattern)** 을 쓴다. 구현(편지)을 래퍼(봉투) 안에 숨기고, 공개 클라이언트에게는 봉투를 준다.

```csharp
public class Envelope : IList<PayrollData>
{
    private List<PayrollData> data = new List<PayrollData>();

    public void SafeUpdate(IEnumerable<PayrollData> sourceList)
    {
        // 복사본을 만든다
        List<PayrollData> updates = new List<PayrollData>(sourceList.ToList());
        // 교환한다 — 중단될 수 없다
        data = updates;
    }

    public PayrollData this[int index]
    {
        get => data[index];
        set => data[index] = value;
    }
    public int Count => data.Count;
    public void Add(PayrollData item) => data.Add(item);
    public IEnumerator<PayrollData> GetEnumerator() => data.GetEnumerator();
    // IList<PayrollData>의 나머지 멤버도 전부 같은 방식으로 data에 전달한다
}
```

```csharp
private Envelope data;

public IList<PayrollData> MyCollection => data;

public void UpdateData() => data.SafeUpdate(UnreliableOperation());
```

클라이언트는 언제나 `Envelope` 인스턴스를 들고 있고, 그 안의 `List<>`가 통째로 교체되는 것은 보이지 않는다. `SafeUpdate`의 교환은 참조 대입 하나이므로 **중단될 수 없다.** 멀티스레드 애플리케이션에서도 안전하다. 보일러플레이트가 많으니, 이 대가를 지불할 가치가 있는 자리인지 먼저 판단하라.

### 강한 보장이 비쌀 때

루프 안에서 프로그램 상태를 변경하면서 예외를 던질 수 있다면, 선택은 둘 중 하나다 — 루프에서 쓰는 모든 객체의 방어적 복사본을 만들거나, 기대치를 낮추고 기본 보장만 지원하거나. 정해진 규칙은 없다. 다만 **관리 환경에서 힙 할당 객체를 복사하는 비용은 네이티브 환경만큼 비싸지 않다.** 복사를 피해 얻는 작은 성능보다 오류에서 복구할 수 있는 능력이 대개 더 값지다. 어떤 예외가 나도 결국 프로그램을 종료할 것이라면 강한 보장을 걱정할 이유가 없다.

### 무예외 보장이 필요한 네 자리

큰 프로그램의 모든 루틴에서 무예외 보장을 지키는 것은 비현실적이다. 하지만 **반드시 지켜야 하는 자리가 넷** 있다.

| 자리 | 예외가 나면 |
|---|---|
| **파이널라이저** | 프로그램이 추가 정리 없이 종료된다(34장) |
| **`Dispose` 메서드** | 두 번째 예외가 첫 예외를 삼킨다. 원래 예외를 어디서도 잡을 수 없다(33장) |
| **`when` 절(예외 필터)** | 새 예외가 활성 예외가 되고 원래 정보를 되찾을 수 없다(32.6절) |
| **델리게이트 대상** | 같은 멀티캐스트 델리게이트의 나머지 대상이 호출되지 않는다(26장·27장) |

> **⚠️ 이벤트 핸들러와 델리게이트 대상은 예외를 던지지 마라 — 그리고 남이 그럴 것을 가정하라**
>
> 델리게이트 대상이 예외를 던지면 같은 멀티캐스트 델리게이트의 다른 대상들은 호출되지 않는다. 이벤트를 발생시키는 코드는 강한 예외 보장에 참여할 수 없게 된다.
>
> 그렇다고 남들이 이 조언을 지킬 것이라 믿어서는 안 된다. **당신의 델리게이트 호출에서 무예외 보장에 의존하지 마라.** 멀티캐스트 델리게이트를 하나씩 꺼내 개별 호출하고 예외를 개별 처리하는 기법이 26장에 있다. 방어적 프로그래밍이다 — 당신은 할 수 있는 최선을 하고, 남은 최악을 할 수 있다고 가정한다.

### 상태가 회복 불가능하다면

이미 상태가 회복할 수 없을 만큼 깨졌다고 판단했다면, **깨진 상태를 파괴해 더 이상 해를 끼치지 못하게 해야 한다.** 프로세스 전체를 끝내야 할 만큼 나쁘다면 `Environment.FailFast(message)` 또는 `FailFast(message, exception)`을 호출한다. 이 메서드는 **활성 `try`/`finally` 블록도, 파이널라이저도 실행하지 않고** 프로세스를 종료한다 — 깨진 상태에서 코드를 더 돌리면 상황이 나빠지기만 하므로 이것이 옳다. 다만 `CriticalFinalizerObject` 파생 객체에는 정리 기회를 준다(34.4절).

> **⚠️ FCL 코드 대부분은 예상치 못한 예외 뒤에도 상태가 온전하다고 보장하지 않는다**
>
> FCL 코드를 통과한 예외를 잡고 나서 그 FCL 객체를 계속 쓰면, 그 객체가 예측 불가능하게 동작할 가능성이 있다. FCL 객체들이 예상치 못한 예외 앞에서 상태를 더 잘 유지하거나, 상태를 복원할 수 없으면 `FailFast`를 호출해 주면 좋았을 텐데 그렇지 않다.
>
> 실무 결론: **`catch (Exception)`으로 잡고 계속 실행하는 것은 "이 프로세스는 이제 신뢰할 수 없다"를 선언하는 것과 같다.** 정말로 계속 실행해야 한다면, 그 이후로 만지는 객체를 전부 새로 만들어라.

### 상태 손상을 줄이는 실무 기법

| 기법 | 내용 |
|---|---|
| **불변 데이터 구조** | 변경 자체가 없으면 부분 변경도 없다(19장) |
| **함수형 스타일** | LINQ 쿼리는 원본을 바꾸지 않는다. 자동으로 강한 보장 |
| **복사 후 교환** | 위에서 본 세 단계 절차 |
| **트랜잭션** | 상태가 데이터베이스에 있으면 트랜잭션이 잘 맞는다 |
| **명시적 API 설계** | 잠금 획득 여부를 `ref bool`로 돌려주는 `Monitor.Enter` 오버로드가 그 예 |

마지막 항목의 예를 보자. `Monitor.Enter(obj)` 호출 도중 스레드가 중단되면 잠금을 얻었는지 알 수 없다. 얻었다면 해제되지 않고, 안 얻었는데 `Exit`을 부르면 그것대로 예외다. 그래서 이 오버로드는 권장되지 않고, 획득 여부를 `ref bool`로 돌려주는 오버로드를 쓴다.

```csharp
bool lockTaken = false;               // 잠금을 얻지 않았다고 가정
try
{
    // 예외가 나든 안 나든 lockTaken이 정확하다
    Monitor.Enter(s_myLockObject, ref lockTaken);
    // 스레드 안전 연산
}
finally
{
    if (lockTaken) Monitor.Exit(s_myLockObject);
}
```

C#의 `lock` 문이 만드는 코드가 정확히 이 형태다(11.7절). 잠금과 예외 처리를 함께 다루는 현대적 권고는 48장이다.

## 32.12 예외 비용 측정 — 던지지 않을 때 / 던질 때 / 스택이 깊을 때

### 세 가지 비용을 분리하라

"예외는 느리다"는 문장은 세 가지 서로 다른 비용을 뭉뚱그린다.

| 비용 | 무엇 | 크기 |
|---|---|---|
| **보호 구역을 두는 비용** | `try`/`catch`/`finally` 블록이 존재하는 것 | 거의 없다 |
| **던지는 비용** | 예외 객체 생성 + 1단계 스택 워크 + 2단계 언와인딩 | 크다 |
| **스택 깊이에 따른 추가 비용** | 훑어야 할 프레임 수에 비례 | 깊을수록 커진다 |

### 던지지 않을 때 — 거의 공짜

.NET CLR은 **`catch` 절에 진입하지 않는 `try`/`catch` 블록의 존재가 런타임 성능에 미치는 영향이 최소가 되도록** 최적화되어 있다. 11.7절에서 봤듯 `.try`/`catch`/`finally`는 IL 명령이 아니라 **메서드 본문 뒤에 붙는 예외 처리 절 테이블의 항목**이다. 정상 경로의 IL에는 `leave` 명령 하나가 추가될 뿐이고, `finally`는 JIT의 클로닝 최적화로 정상 경로에 복제되어 펀클릿 호출조차 없어진다.

관리 컴파일러가 네이티브 C++ 컴파일러보다 유리한 지점도 여기다. C++ 컴파일러는 어떤 객체가 성공적으로 생성됐는지 추적하는 코드와, 예외를 잡았을 때 각각의 소멸자를 부르는 코드를 생성해야 한다. 그 장부 코드가 코드 크기와 실행 시간에 영향을 준다. **관리 객체는 GC가 감시하는 관리 힙에 할당되므로 이 장부가 필요 없다.**

> **⚠️ 그렇다고 완전히 0은 아니다**
>
> 예외 처리 구문이 있는 메서드를 인라인하지 못하는 컴파일러가 있고, 예외 핸들러가 있으면 일부 변수를 레지스터에 배치하지 않는 구현도 있다. 어떤 구현은 예외 처리 구문을 메서드 안에 직접 컴파일하고, 어떤 구현은 별도 데이터 테이블에 저장했다가 예외가 던져질 때만 참조한다.
>
> **추가 오버헤드가 정확히 얼마인지는 결정할 수 없다.** 관리 환경에서는 더욱 그렇다 — 같은 어셈블리가 x86, x64, ARM64에서 서로 다른 코드로 JIT되고, .NET Compact Framework나 Mono 같은 다른 CLR 구현은 또 다른 코드를 만든다.
>
> 원천 저자는 마이크로소프트 내부의 여러 JIT 컴파일러로 자신의 코드를 시험했고, **관찰된 성능 차이가 상당히 극적이고 놀라웠다**고 적었다. 결론은 하나다 — **사용자가 실행할 플랫폼에서 직접 측정하라.**

### 던질 때 — 비싸다

예외를 던지는 것은 **상대적으로 비싸며, 수백 클록 사이클 이상이 걸린다.** 비용은 네 곳에서 나온다.

1. **예외 객체 할당.** 관리 힙 할당 + 나중의 GC 부담(63장)
2. **1단계 스택 워크.** 프레임마다 예외 처리 절 테이블을 조회하고, 타입을 비교하고, 필터를 실행한다
3. **2단계 언와인딩.** 프레임을 하나씩 해체하고 `finally` 펀클릿을 호출한다
4. **`StackTrace` 문자열 생성.** 접근할 때마다 CLR 안으로 들어가 메서드 이름과 PDB 정보를 조합한다

이 중 4번은 **접근하지 않으면 지불하지 않는다.** 예외를 잡아서 종류만 확인하고 버리는 코드는 이 비용을 내지 않는다. 반대로 모든 예외에 대해 `e.ToString()`을 로그에 남기는 코드는 매번 낸다.

### 스택이 깊을수록 비싸진다

1단계와 2단계 모두 **프레임 수에 비례**한다. 처리할 `catch`가 스택 위쪽 멀리 있을수록 훑을 프레임이 많다.

```text
  얕은 스택                       깊은 스택
┌──────────┐  ← catch          ┌──────────┐  ← catch
│ Caller   │                   │ L0       │
├──────────┤                   ├──────────┤
│ Thrower  │  ← throw          │ ...      │  40 프레임
└──────────┘                   ├──────────┤
                               │ L40      │  ← throw
  훑을 프레임: 2                └──────────┘
                                 훑을 프레임: 42
```

여기에 두 가지가 더 곱해진다.

- **재던지기가 있으면 전체 과정이 다시 시작된다.** `throw;`는 언와인딩을 한 번 하고 새 탐색을 시작한다. 계층마다 잡아서 다시 던지는 코드는 스택 워크를 계층 수만큼 반복한다
- **필터가 있으면 1단계에서 필터 코드가 실행된다.** 필터 자체가 무거우면 그만큼 더 걸린다

**언와인딩과 `catch` 절 진입은 런타임에 큰 영향을 준다.** 예외 필터가 성능에 긍정적인 이유가 이것이다 — 처리할 수 없는 예외에 대해 언와인딩과 `catch` 진입을 회피한다(32.7절).

### 직접 측정하기

수치는 플랫폼과 런타임 버전에 따라 달라진다. 이 책이 대신 외워 줄 수 없으니 직접 재라.

```csharp
using BenchmarkDotNet.Attributes;
using BenchmarkDotNet.Running;

[MemoryDiagnoser]
public class ExceptionCost
{
    [Params(1, 10, 40)]
    public int Depth;                 // 스택 깊이

    [Benchmark(Baseline = true)]
    public int NoTryBlock() => Recurse(Depth, throwIt: false);

    [Benchmark]
    public int WithTryBlockNoThrow()
    {
        try { return Recurse(Depth, throwIt: false); }
        catch (InvalidOperationException) { return -1; }
    }

    [Benchmark]
    public int Throwing()
    {
        try { return Recurse(Depth, throwIt: true); }
        catch (InvalidOperationException) { return -1; }
    }

    [Benchmark]
    public bool TryPattern() => int.TryParse("not a number", out _);

    [Benchmark]
    public int ParseThrowing()
    {
        try { return int.Parse("not a number"); }
        catch (FormatException) { return -1; }
    }

    private static int Recurse(int depth, bool throwIt)
    {
        if (depth == 0)
        {
            if (throwIt) throw new InvalidOperationException("boom");
            return 0;
        }
        return Recurse(depth - 1, throwIt) + 1;
    }
}

// BenchmarkRunner.Run<ExceptionCost>();
```

`[Params]`로 깊이를 바꿔 가며 돌리면 **깊이에 대한 기울기**가 보인다. 실행할 때 두 가지를 반드시 지켜라.

- **릴리스 빌드로 돌려라.** 디버그 빌드는 JIT 최적화가 꺼져 있어 의미 있는 수치가 나오지 않는다
- **디버거를 붙이지 마라.** 디버거가 붙으면 예외마다 디버거에 통보가 가고, 비용이 몇 자릿수 달라진다

측정 방법론 전반은 67장에서 다룬다.

### 얼마나 던지고 있는지부터 보라

Windows 성능 모니터에는 .NET Framework와 함께 설치되는 `.NET CLR Exceptions` 카운터 범주가 있고, `# of Exceps Thrown / sec`로 초당 던져지는 예외 수를 볼 수 있다. 현대 .NET에서는 `dotnet-counters`와 EventCounter로 같은 정보를 본다(73장).

**"내 코드는 예외를 안 던지는데?"라고 생각하는 코드가 초당 수천 개를 던지고 있는 경우가 흔하다.** 라이브러리 내부에서 던지고 잡는 예외는 코드에서 보이지 않기 때문이다.

> **💡 성능 때문에 예외를 안 쓰겠다는 결정은 잘못된 트레이드오프다**
>
> 객체지향 플랫폼에서 예외 처리는 선택이 아니다. 쓰지 않겠다면 무엇을 쓸 것인가? 메서드가 `true`/`false`나 오류 코드 열거형을 반환하게 하겠다는 것인가? 그러면 **두 세계의 나쁜 점만 갖게 된다** — CLR과 클래스 라이브러리는 여전히 예외를 던지고, 당신의 코드는 오류 코드를 반환한다. 이제 둘 다 다뤄야 한다.
>
> 게다가 모든 메서드 호출의 반환값을 검사하고 그것을 자기 호출자에게 필터링해 올리는 코드를 쓰면 **애플리케이션 성능이 심각하게 영향받는다.** 추가로 작성해야 하는 코드의 양과 실수 가능성은 말할 것도 없다.
>
> 올바른 접근은 **자주 호출되면서 실패율이 높은 특정 메서드를 찾아 `TryXXX` 대안을 제공하는 것**이다(32.9절). 예외 처리 자체를 포기하는 것이 아니다.

## 32.13 `AggregateException`, `Flatten`, `Handle`

### 왜 필요한가

지금까지의 모델은 "한 번에 하나의 예외"를 전제했다. 그런데 **여러 작업이 병렬로 실행되면 여러 예외가 동시에 발생할 수 있다.** 부모 태스크가 자식 태스크 셋을 만들었고 그중 둘이 각기 다른 예외로 실패했다면, 어느 하나를 골라 던지는 것은 정보를 버리는 일이다. `System.AggregateException`은 **예외 객체의 컬렉션을 캡슐화**하는 타입이며 `System.Exception`에서 직접 파생된다.

### API

```csharp
public class AggregateException : Exception
{
    public AggregateException(params Exception[] innerExceptions);
    public AggregateException(IEnumerable<Exception> innerExceptions);
    public AggregateException(string message, params Exception[] innerExceptions);
    public AggregateException(string message, Exception innerException);
    // 그 밖에 기본 생성자와 (string message) 오버로드

    public ReadOnlyCollection<Exception> InnerExceptions { get; }

    public AggregateException Flatten();
    public void Handle(Func<Exception, bool> predicate);
    public override Exception GetBaseException();
}
```

> **⚠️ `InnerExceptions`와 `InnerException`을 혼동하지 마라**
>
> `InnerExceptions`(복수)는 `AggregateException`이 정의하는 `ReadOnlyCollection<Exception>`이다. `InnerException`(단수)은 `System.Exception`에서 상속받은 것이며, 관례상 `InnerExceptions`의 첫 원소를 가리킨다.
>
> `catch (AggregateException ae) { Log(ae.InnerException); }` 처럼 쓰면 **두 번째 이후의 예외를 조용히 버린다.** 병렬 작업의 실패 원인 중 하나만 보고 나머지를 놓치는 전형적 버그다.

### 어디서 나오는가

| 상황 | 던져지는 것 |
|---|---|
| `task.Wait()` / `task.Result` — 태스크가 실패했다 | `AggregateException` |
| `Task.WaitAll(...)` | `AggregateException` |
| `Parallel.For` / `Parallel.ForEach` 내부에서 예외 | `AggregateException` |
| PLINQ 쿼리 내부에서 예외 | `AggregateException` |
| `await task` — 태스크가 실패했다 | **첫 내부 예외** (감싸지 않는다) |

계산 위주 태스크가 처리되지 않은 예외를 던지면, 그 예외는 삼켜져 컬렉션에 저장되고 스레드 풀 스레드는 풀로 돌아간다. 나중에 `Wait` 메서드나 `Result` 속성을 호출하면 그때 `AggregateException`이 던져진다.

`await`가 다르게 동작하는 이유는 프로그래밍 경험 때문이다. `await`할 때마다 `AggregateException`을 잡고 내부 예외를 확인해 처리하거나 다시 던지는 코드를 써야 한다면 지나치게 번거롭다. 그래서 `TaskAwaiter`의 `GetResult` 메서드가 **첫 내부 예외를 대신 던진다.** 자세한 것은 47.4절이다.

### `GetBaseException`

`AggregateException`은 `Exception.GetBaseException`을 재정의한다. 구현은 **문제의 근본 원인인 가장 안쪽의 `AggregateException`을 반환한다** — 컬렉션에 가장 안쪽 예외가 하나뿐이라는 가정 아래서다.

### `Flatten` — 중첩을 편다

부모 태스크가 자식 태스크를 만들고, 자식이 다시 자식을 만들면 `AggregateException` 안에 `AggregateException`이 들어간다.

```text
AggregateException
├── AggregateException
│   ├── OverflowException
│   └── InvalidOperationException
└── IOException
```

`Flatten()`은 원래 `AggregateException`의 내부 예외 계층을 훑어, **중첩되지 않은 평평한 목록**을 `InnerExceptions`에 담은 **새 `AggregateException`** 을 만든다.

```text
AggregateException (Flatten 결과)
├── OverflowException
├── InvalidOperationException
└── IOException
```

```csharp
parent.ContinueWith(p =>
{
    var sb = new StringBuilder(
        "The following exception(s) occurred:" + Environment.NewLine);
    foreach (var e in p.Exception.Flatten().InnerExceptions)
        sb.AppendLine("   " + e.GetType().ToString());
    Console.WriteLine(sb.ToString());
}, TaskContinuationOptions.OnlyOnFaulted);
```

> **💡 `AggregateException`을 다룰 때는 거의 언제나 먼저 `Flatten()`을 호출하라**
>
> `Flatten()` 없이 `InnerExceptions`를 순회하면 중첩된 `AggregateException` 객체 자체를 원소로 만나게 되고, 진짜 예외는 그 안에 숨어 있다. 재귀 순회를 직접 짜지 말고 `Flatten()`을 써라. 원본 객체는 변경되지 않으며 새 객체가 반환된다.

### `Handle` — 처리할 수 있는 것만 골라 처리하기

`Handle`은 `AggregateException`에 담긴 각 예외에 대해 콜백을 호출한다. 콜백은 각 예외를 **처리한 것으로 볼지** 결정한다 — `true`면 처리, `false`면 미처리다.

**`Handle` 호출 후 처리되지 않은 예외가 하나라도 있으면, 그 미처리 예외들만 담은 새 `AggregateException`이 만들어져 던져진다.**

```csharp
CancellationTokenSource cts = new CancellationTokenSource();
Task<int> t = Task.Run(() => Sum(cts.Token, 1000000000), cts.Token);

cts.Cancel();   // 비동기 요청이다. 태스크가 이미 끝났을 수도 있다

try
{
    // 태스크가 취소됐다면 Result가 AggregateException을 던진다
    Console.WriteLine("The sum is: " + t.Result);
}
catch (AggregateException x)
{
    // OperationCanceledException 객체는 처리된 것으로 본다.
    // 그 밖의 예외가 있으면 미처리 예외만 담은 새 AggregateException이 던져진다
    x.Handle(e => e is OperationCanceledException);

    // 모든 예외가 처리됐다면 여기가 실행된다
    Console.WriteLine("Sum was canceled");
}
```

> **⚠️ `Handle`의 콜백에서 부작용을 일으키지 마라**
>
> `Handle`은 **술어(predicate)** 를 받는다. "이 예외를 처리한 것으로 보는가"에 답할 뿐이다. 콜백 안에서 실제 복구 작업을 하면, 나중에 미처리 예외가 발견되어 새 `AggregateException`이 던져질 때 **이미 부분적으로 복구가 진행된 상태**가 된다. 32.11절의 강한 보장이 깨진다.
>
> 복구는 `Handle`이 예외 없이 반환된 뒤에 하라.

> **⚠️ `AggregateException`의 예외들은 어느 작업에서 왔는지 알 수 없다**
>
> `InnerExceptions` 컬렉션의 예외 객체를 **그것을 던진 작업과 짝지을 방법이 없다.** 어떤 항목이 실패했는지 알아야 한다면, 각 작업이 자기 식별자를 예외의 `Data`에 넣거나 전용 예외 타입의 속성으로 담아야 한다.

### 직접 만들어 던지기

`AggregateException`은 병렬 라이브러리 전용이 아니다. **여러 독립 작업의 실패를 모아 보고해야 하는 어떤 코드에서든** 쓸 수 있다.

```csharp
public static void ValidateAll(IEnumerable<IValidatable> items)
{
    var failures = new List<Exception>();
    foreach (var item in items)
    {
        try { item.Validate(); }
        catch (ValidationException e) { failures.Add(e); }
    }
    if (failures.Count > 0)
        throw new AggregateException("검증에 실패한 항목이 있다", failures);
}
```

첫 실패에서 멈추지 않고 **모든 실패를 한 번에 보고**하는 API를 만들 수 있다. 폼 검증, 설정 파일 파싱, 배치 처리에 잘 맞는다.

> **📌 `catch (AggregateException)`은 필터와 궁합이 좋다**
>
> `AggregateException`은 처리할 수 있는 예외와 없는 예외를 함께 담을 수 있으므로, "이 예외 집합을 내가 처리할 수 있는가"를 판단한 뒤에만 `catch`에 진입하는 편이 낫다. 그 판단이 정확히 필터의 일이다(32.7절).
>
> ```csharp
> catch (AggregateException ae)
>     when (ae.Flatten().InnerExceptions.All(e => e is TimeoutException))
> {
>     // 전부 타임아웃일 때만 재시도한다
> }
> ```
>
> `catch`로 들어간 뒤 판단하고 `throw;`로 되던지는 형태보다 스택 정보가 훨씬 잘 보존된다.

`Task`의 예외 저장·재던지기 시점, 연속(continuation)에서의 예외 관찰, 병렬 루프의 사용례는 46.4절과 50.9절에서 다룬다.

## 32.14 처리되지 않은 예외와 프로세스 종료

### 기본 정책

예외가 던져지면 CLR은 호출 스택을 거슬러 올라가며 타입이 맞는 `catch` 블록을 찾는다. 어디에도 없으면 **처리되지 않은 예외**가 된다.

> **프로세스의 어느 스레드에서든 처리되지 않은 예외가 발생하면 CLR은 프로세스를 종료한다.**

이건 결함이 아니라 기능이다. 처리되지 않은 예외는 애플리케이션이 예상하지 못한 상황을 나타내며 **진짜 버그**로 간주된다. 동시에 종료는 **상태 손상의 확산을 막는다.** 32.1절의 `Transfer` 예를 다시 보라. 출금은 성공하고 입금 직전에 예외가 났는데 호출 코드가 `System.Exception`을 잡고 계속 실행한다면, 두 계좌 모두 있어야 할 돈보다 적다. 돈 이야기이므로 이건 단순 버그가 아니라 **보안 버그**다. 계속 실행하면 다른 계좌로도 이체를 시도하며 상태 손상이 걷잡을 수 없이 번진다.

> **⚠️ 클래스 라이브러리 개발자는 처리되지 않은 예외를 생각조차 하면 안 된다**
>
> 처리되지 않은 예외에 대한 정책은 **애플리케이션 개발자만** 정할 수 있다. 라이브러리는 애플리케이션이 어떻게 대응하고 싶어 하는지 알 방법이 없다.
>
> 라이브러리 타입은 **절대, 어떤 상황에서도 모든 예외를 잡아 삼키면 안 된다.** 게다가 라이브러리는 델리게이트·가상 메서드·인터페이스 메서드를 통해 애플리케이션 코드를 호출하는 일이 잦다. 그 애플리케이션 코드가 던진 예외를 애플리케이션의 다른 부분이 잡으려고 기다리고 있을 수 있다. 예외가 호출 스택을 타고 올라가게 두어라.

### 정책 훅 — `AppDomain.UnhandledException`

애플리케이션 개발자는 처리되지 않은 예외를 기록할 수 있다. 마이크로소프트의 권고는 사실 **CLR 기본 정책을 그대로 받아들이는 것**이다 — 처리되지 않은 예외가 나면 Windows가 시스템 이벤트 로그에 항목을 쓴다. 하지만 자체 보고 체계가 필요하면 훅을 걸 수 있다.

```csharp
AppDomain.CurrentDomain.UnhandledException += (sender, e) =>
{
    var ex = e.ExceptionObject as Exception;
    Log.Fatal(ex, "처리되지 않은 예외. 종료 예정: {Terminating}", e.IsTerminating);
    Log.Flush();     // 프로세스가 곧 죽는다. 반드시 flush 하라
};
```

`UnhandledExceptionEventArgs`의 두 멤버가 핵심이다.

| 멤버 | 타입 | 의미 |
|---|---|---|
| `ExceptionObject` | `object` | 던져진 객체. `Exception`이 아닐 수도 있어 `object`다 |
| `IsTerminating` | `bool` | 이 예외 때문에 런타임이 종료 중인가 |

> **⚠️ 이 이벤트는 통보이지 처리가 아니다**
>
> 핸들러에서 예외를 "처리"할 수 없다. 프로세스 종료를 막을 수 없다. 할 수 있는 것은 기록과 정리뿐이다. 그리고 **핸들러가 실행되는 동안에도 프로세스는 종료 절차에 있으므로 시간이 무한하지 않다.** 원격 로그 서버로 동기 전송하는 코드를 여기 넣으면 기록되기 전에 프로세스가 사라질 수 있다.
>
> .NET Framework에는 `<legacyUnhandledExceptionPolicy>` 구성 요소로 이 동작을 .NET 1.x 시절로 되돌리는 스위치가 있었다. **.NET Framework 전용이며, 새 코드에서 쓸 이유가 없다.**

애플리케이션 모델마다 별도의 훅이 또 있다.

| 모델 | 훅 |
|---|---|
| 모든 애플리케이션 | `AppDomain.UnhandledException` |
| Windows Forms | `Application.ThreadException`, `Application.OnThreadException` |
| WPF | `Application.DispatcherUnhandledException`, `Dispatcher.UnhandledException` |
| ASP.NET | 미들웨어 파이프라인의 예외 처리기 |

> **⚠️ UI 모델의 전역 훅은 작업자 스레드를 덮지 않는다**
>
> `Application.DispatcherUnhandledException`과 `Application.ThreadException`은 **메시지 루프를 통해 호출된 코드** — 즉 `Application`이 활성인 동안 메인 스레드에서 도는 코드 — 에 대해서만 발생한다. **직접 만든 작업자 스레드의 처리되지 않은 예외에는 발생하지 않는다.**
>
> 이 이벤트들을 처리하면 프로그램이 종료되지 않지만, 처리되지 않은 예외가 남긴(혹은 유발한) 상태 손상을 피하려면 애플리케이션을 재시작하는 편이 낫다.

### 스레드 진입점마다 핸들러가 필요하다

스레드를 만들 때 유효했던 `try`/`catch`/`finally` 블록은 **그 스레드가 실행을 시작할 때 아무 관련이 없다.**

```csharp
try
{
    new Thread(Go).Start();
}
catch (Exception ex)
{
    // 여기에는 절대 오지 않는다!
    Console.WriteLine("Exception!");
}

void Go() { throw null; }   // NullReferenceException을 던진다
```

각 스레드는 독립적인 실행 경로를 갖는다는 것을 생각하면 당연한 동작이다. 해법은 예외 처리기를 `Go` 메서드 **안으로** 옮기는 것이다.

> **💡 프로덕션 애플리케이션은 모든 스레드 진입점에 예외 처리기가 있어야 한다**
>
> 메인 스레드에 (보통 실행 스택의 더 높은 수준에) 두는 것과 마찬가지다. 처리되지 않은 예외는 애플리케이션 전체를 종료시킨다.
>
> 처리기 안에서 오류를 무시하는 일은 거의 없어야 한다. 보통 예외의 세부 정보를 로그에 남긴다. 클라이언트 애플리케이션이라면 사용자에게 세부 정보를 서버로 보낼지 물을 수 있다. 그 후 애플리케이션을 재시작하는 선택도 고려하라 — 예상치 못한 예외는 프로그램을 유효하지 않은 상태로 남겼을 가능성이 있다.
>
> 스레드를 직접 만드는 것 자체를 피해야 하는 이유는 45.9절이다.

### 첫 기회 예외 — `FirstChanceException`

`AppDomain`마다 콜백을 등록해 **CLR이 `catch` 블록을 찾기 시작할 때** 통보를 받을 수 있다.

```csharp
AppDomain.CurrentDomain.FirstChanceException += (sender, e) =>
{
    Diagnostics.Record(e.Exception);   // 잡을 수도, 삼킬 수도 없다
};
```

동작 순서는 이렇다. 예외가 던져지면 **먼저** `FirstChanceException` 콜백이 호출되고 — 이 시점에는 CLR이 아직 어떤 `catch` 블록도 찾지 않았다 — 그 다음에 1단계 탐색이 시작된다. `AppDomain` 경계를 넘어갈 때는 새 `AppDomain`에서 예외가 다시 던져지므로 콜백도 다시 호출된다.

> **⚠️ `FirstChanceException`은 관찰 전용이며, 매우 시끄럽다**
>
> 콜백은 예외를 처리하거나 어떤 식으로든 삼킬 수 없다. 예외가 발생했다는 통보를 받을 뿐이다.
>
> 그리고 **정상적으로 잡히고 처리되는 예외까지 전부** 여기로 온다. 라이브러리 내부에서 던지고 잡는 예외가 초당 수천 개일 수 있다(32.12절). 이 훅에 무거운 작업을 걸면 애플리케이션이 느려진다.
>
> 진단 목적으로 잠깐 켜는 도구로 생각하라. 상시 로깅에는 32.8절의 필터 관용구가 훨씬 낫다 — 범위를 좁힐 수 있기 때문이다.

### 백그라운드 스레드와 관찰되지 않은 태스크 예외

`Task`는 예외를 삼켰다가 나중에 다시 던진다. 문제는 **아무도 관찰하지 않으면 어떻게 되는가**다.

`Wait`나 `Result`를 호출하지 않고 `Exception` 속성도 조회하지 않으면, 코드는 예외가 발생했다는 사실을 **결코 관찰하지 못한다.** 프로그램에 예상치 못한 문제가 생겼는데 당신이 모르는 상태다.

이를 감지하려면 `TaskScheduler`의 정적 `UnobservedTaskException` 이벤트에 콜백을 등록한다.

```csharp
TaskScheduler.UnobservedTaskException += (sender, e) =>
{
    Log.Error(e.Exception, "관찰되지 않은 태스크 예외");
    e.SetObserved();     // 관찰했다고 표시한다
};
```

이 이벤트는 **관찰되지 않은 예외를 가진 `Task`가 가비지 컬렉션될 때 CLR의 파이널라이저 스레드에서 발생한다.** 이벤트 인자는 관찰되지 않은 `AggregateException`을 담고 있다.

"관찰되지 않음"의 판정에는 미묘한 구석이 있다. **타임아웃과 함께 대기한 태스크**는 타임아웃 간격 이후에 오류가 발생하면 관찰되지 않은 예외를 만든다. 반대로 **실패한 태스크의 `Exception` 속성을 확인하는 행위 자체가** 그 예외를 "관찰된" 것으로 만든다.

> **⚠️ 정책이 .NET Framework 4.5에서 바뀌었다**
>
> .NET Framework 4.0에서는 관찰되지 않은 태스크 예외가 파이널라이저 스레드에서 다시 던져져 **프로세스를 종료시켰다.** 4.5부터 기본 동작이 바뀌어 **프로세스를 종료시키지 않는다.** .NET(Core) 계열도 종료시키지 않는다.
>
> .NET Framework에서는 app.config의 `<ThrowUnobservedTaskExceptions enabled="true"/>` 요소로 옛 동작을 되살릴 수 있었다.
>
> 실무적 함의가 크다. **현대 .NET에서 "발사 후 망각(fire-and-forget)" 태스크의 실패는 기본적으로 조용히 사라진다.** 로그에 아무것도 남지 않는다. 자율 태스크를 만들 때는 스레드와 마찬가지로 **태스크 코드 안에서 명시적으로 예외를 처리하는 것이 좋은 습관**이다.
>
> 예외를 무시해도 되는 경우는 예외가 "더 이상 관심 없는 결과를 못 얻었다"만 뜻할 때다. 사용자가 웹 페이지 다운로드를 취소했다면 그 페이지가 없었다는 사실은 중요하지 않다. 반면 예외가 **프로그램의 버그**를 뜻한다면 무시가 문제가 된다 — 버그가 프로그램을 유효하지 않은 상태로 남겼을 수 있고, 초기 오류를 기록하지 않으면 이후에 파생되는 예외들의 진단이 어려워진다.

`async void` 메서드에서 처리되지 않은 예외는 또 다른 경로를 탄다. 호출자가 발견할 방법이 없으므로, 컴파일러가 생성한 코드가 예외를 잡아 **호출자의 동기화 컨텍스트에서 다시 던진다.** GUI 스레드에서 호출했으면 GUI 스레드가, 아니면 어떤 스레드 풀 스레드가 결국 다시 던진다. 보통 프로세스 종료로 이어진다. `async void`를 금지하는 이유이며 47.14절에서 다룬다.

### 잡을 수 없는 예외

일부 예외는 **애초에 잡을 수 없다.** `StackOverflowException`은 .NET 2.0 이후 잡을 수 없으며, CLR이 내부적으로 `Environment.FailFast`를 호출해 즉시 종료한다. **손상된 상태 예외(CSE)** 는 기본적으로 관리 코드가 잡을 수 없고 `finally` 블록도 실행되지 않는다.

CLR이 손상된 상태 예외로 간주하는 네이티브 Win32 예외 목록은 다음과 같다.

```text
EXCEPTION_ACCESS_VIOLATION          EXCEPTION_STACK_OVERFLOW
EXCEPTION_ILLEGAL_INSTRUCTION       EXCEPTION_IN_PAGE_ERROR
EXCEPTION_INVALID_DISPOSITION       EXCEPTION_NONCONTINUABLE_EXCEPTION
EXCEPTION_PRIV_INSTRUCTION          STATUS_UNWIND_CONSOLIDATE
```

이들은 대개 CLR 자체의 버그이거나, 관리 개발자가 통제할 수 없는 네이티브 코드의 버그다. CLR은 대부분을 `System.Runtime.InteropServices.SEHException`으로 변환하며, `EXCEPTION_ACCESS_VIOLATION`은 `System.AccessViolationException`으로, `EXCEPTION_STACK_OVERFLOW`는 `System.StackOverflowException`으로 변환한다.

> **⚠️ CSE를 잡는 스위치는 .NET Framework 전용이다**
>
> .NET Framework에서는 개별 메서드에 `System.Runtime.ExceptionServices.HandleProcessCorruptedStateExceptionsAttribute`를 적용하고 `System.Security.SecurityCriticalAttribute`도 함께 붙이면 기본 동작을 재정의해 CSE를 잡을 수 있었다. 프로세스 전체는 구성 파일의 `<legacyCorruptedStateExceptionsPolicy>` 요소로 바꿀 수 있었다.
>
> **.NET(Core) 계열에서는 이 특성이 무시된다.** 액세스 위반이 나면 프로세스가 종료된다. 잡을 방법이 없다. 이것을 우회하려 시도하지 마라 — 이미 메모리가 손상된 상태에서 코드를 더 실행하는 것은 어떤 이득도 없다.

재귀 메서드에서 스택 여유를 미리 확인하고 싶다면 `RuntimeHelpers.EnsureSufficientExecutionStack`을 호출할 수 있다. 호출 스레드에 평균적인 메서드를 실행할 만한 스택 공간이 있는지 검사하고, 부족하면 **잡을 수 있는** `InsufficientExecutionStackException`을 던진다.

### 서버 애플리케이션에서

분산 애플리케이션에서 처리되지 않은 예외가 발생하면 이상적인 동작은 예외를 기록하고, 작업을 완료할 수 없다는 통보를 클라이언트에 보내고, 서버를 종료하는 것이다. 현실은 그렇지 않다 — 실패 통보를 보내는 것이 불가능할 수도 있고, 상태를 가진 서버라면 종료 후 새 인스턴스를 띄우는 것이 실용적이지 않을 수도 있다.

> **⚠️ 처리되지 않은 예외 정보를 클라이언트에 반환하지 마라**
>
> 클라이언트가 그 정보로 할 수 있는 일이 거의 없다 — 특히 클라이언트를 다른 회사가 구현했다면 더욱 그렇다. 그리고 서버는 **해킹 가능성을 줄이기 위해 자기 자신에 대한 정보를 가능한 한 적게 노출해야 한다.** 스택 트레이스에는 파일 경로, 어셈블리 버전, 내부 타입 이름이 그대로 들어 있다.
>
> 상관관계 ID를 만들어 클라이언트에는 그것만 주고, 상세는 서버 로그에 남겨라(75.4절).

### 예외 디버깅

Visual Studio는 예외에 대한 특별한 지원을 제공한다. 디버그 메뉴의 예외 설정 창에서 예외 종류별로 **던져질 때 중단(Thrown)** 할지 **처리되지 않았을 때만 중단** 할지 고를 수 있다.

- **Thrown 체크됨** — 예외가 던져지는 즉시 디버거가 멈춘다. CLR이 아직 어떤 `catch` 블록도 찾기 전이다. 예외를 잡아 처리하는 코드를 디버깅할 때, 그리고 **어떤 컴포넌트나 라이브러리가 예외를 삼키거나 다시 던지고 있다고 의심되는데 어디에 중단점을 걸어야 할지 모를 때** 유용하다
- **Thrown 체크 안 됨** — 예외가 처리되지 않았을 때만 멈춘다. 기본값이며, 처리된 예외는 애플리케이션이 상황을 예상하고 대응했다는 뜻이므로 정상 진행시킨다

디버깅 중 현재 던져진 예외 객체는 조사식 창에 특수 변수 이름 `$exception`을 추가해 볼 수 있다. 사용자 정의 예외 타입도 정규화된 이름으로 이 목록에 추가할 수 있으며, `System.Exception`에서 파생되지 않은 비 CLS 타입도 지원된다.

프로덕션에서 예외로 죽은 프로세스의 덤프를 분석하는 방법은 74.5절과 74.8절이다.

## 이 장의 요약

- **예외는 "멤버가 이름이 약속한 일을 완수하지 못했다"는 신호다.** 판단 기준은 빈도가 아니라 계약이다. `File.Exists`는 파일이 없어도 성공하고, `File.Open`은 실패한다.
- **반환 코드는 네 가지로 부족하다.** 무시할 수 있고, 반환 타입을 오염시키고, 모든 중간 계층이 전파에 참여해야 하고, 생성자·속성·연산자에는 아예 쓸 수 없다. 예외는 이 넷을 모두 해결한다.
- **`finally`는 "언제나" 실행되지 않는다.** `FailFast`, `TerminateProcess`, 스택 오버플로, 손상된 상태 예외, 그리고 **처리할 `catch`를 아무도 제공하지 않은 경우**에는 실행되지 않을 수 있다.
- **`catch`나 `finally` 안에서 던진 예외가 원래 예외를 완전히 지운다.** 그래서 정리 코드는 짧고 실패 가능성이 낮아야 한다. `Dispose`·파이널라이저·필터·델리게이트 대상은 무예외 보장을 지켜야 한다.
- **`throw ex`는 `throw` 명령, `throw;`는 `rethrow` 명령이다.** 전자는 스택 트레이스 시작점을 그 자리로 재설정한다. 감싸인 예외를 원래 트레이스로 올리려면 `ExceptionDispatchInfo.Capture`/`Throw`를 쓴다.
- **CLR의 예외 처리는 2단계다.** 1단계에서 스택을 훑으며 필터를 평가해 처리할 `catch`를 찾고, 2단계에서 언와인딩하며 `finally`를 실행한다. **필터는 스택이 살아 있는 상태에서 실행된다.**
- **`when` 필터가 catch-후-재던지기보다 낫다.** 언와인딩이 일어나지 않으므로 지역 변수와 원래 발생 지점이 보존되고, 성능도 나빠지지 않는다. `catch` 안에서 조건 검사 후 `throw;`로 끝나는 분기는 전부 `when`으로 옮겨라.
- **항상 `false`를 반환하는 필터로 스택을 건드리지 않고 로깅할 수 있다.** 라이브러리 경계에서도 쓸 수 있는 유일한 로깅 방식이다. 필터의 부작용은 "관찰"에만 쓰고 "결정"에는 쓰지 마라.
- **`TryXXX`는 예외를 없애지 않는다.** `bool` 반환값은 단 한 종류의 실패만 뜻하고, 나머지 실패는 여전히 예외다. 최선의 객체 모델을 먼저 만들고, 성능 피드백을 받은 뒤에 `TryXXX`를 추가하라.
- **새 예외 타입은 `catch` 절이 다르게 처리할 때만 만든다.** `System.Exception`에서 파생시키고(`ApplicationException` 아님), `public`으로 선언하고, 생성자 세 개를 제공하고, 계층은 얕고 넓게.
- **강한 예외 보장은 복사 후 교환으로 얻는다.** 값 타입에서만 교환이 통한다. 참조 타입을 교환하면 클라이언트가 옛 객체를 계속 들고 있다 — 봉투-편지 패턴이 필요하다.
- **보호 구역을 두는 것은 거의 공짜, 던지는 것은 비싸다.** 던지는 비용은 수백 클록 사이클 이상이며 스택 깊이에 비례한다. 정확한 수치는 플랫폼·런타임·JIT에 따라 달라지므로 릴리스 빌드에서 직접 측정하라.
- **`AggregateException`은 `InnerExceptions`(복수)를 갖는다.** 다루기 전에 `Flatten()`으로 중첩을 펴고, `Handle`의 술어에서 부작용을 일으키지 마라. `await`는 첫 내부 예외만 던진다.
- **어느 스레드에서든 처리되지 않은 예외가 나면 프로세스가 종료된다.** 스레드 진입점마다 처리기가 필요하며, UI의 전역 훅은 작업자 스레드를 덮지 않는다. 관찰되지 않은 태스크 예외는 .NET Framework 4.5 이후 프로세스를 죽이지 않는다 — 조용히 사라진다.

## 연습 문제

1. 32.6절의 `Bottom`/`Middle`/`Top` 프로그램을 그대로 입력해 실행하고, 출력이 `Middle filter` → `Bottom filter` → `Top finally` → `Middle finally` → `Caught in Bottom` 순인지 확인하라. 그 다음 `Middle`의 필터를 `true`로 바꾸고 출력이 어떻게 달라지는지 관찰하라.
2. `throw ex;`와 `throw;`를 각각 쓰는 두 메서드를 3단계 깊이의 호출 사슬 아래 두고, 최상위에서 `e.StackTrace`를 출력해 줄 수를 비교하라. 이어서 `ExceptionDispatchInfo.Throw`로 바꿔 세 번째 결과를 비교하라.
3. `finally` 안에서 예외를 던지는 메서드를 만들고, `try` 블록에서도 다른 예외를 던져라. 호출자가 어느 예외를 보는지 확인하고, 첫 예외의 정보를 되찾을 방법이 있는지 시도해 보라.
4. 32.8절의 로깅 필터 관용구를 구현하고, `catch (Exception e) when (Log(e)) { }`를 `catch` 목록의 맨 앞과 맨 뒤에 각각 두었을 때 무엇이 로깅되는지 비교하라.
5. 32.12절의 BenchmarkDotNet 클래스를 릴리스 빌드로 실행하라. `Depth`를 1·10·40으로 바꿔 가며 `Throwing`의 시간이 깊이에 대해 어떤 기울기를 갖는지 그래프로 그려라. `TryPattern`과 `ParseThrowing`의 비율도 기록하라.
6. `Environment.FailFast("test")`를 `finally` 블록이 있는 메서드 안에서 호출하고, `finally`가 실행되지 않는 것을 콘솔 출력으로 확인하라. 이어서 Windows 이벤트 뷰어(또는 리눅스의 코어 덤프 설정)에 무엇이 기록됐는지 찾아보라.
7. 자식 태스크 셋을 만들어 서로 다른 예외로 실패시키고, 부모 태스크의 `Exception`을 `Flatten()` 없이 순회했을 때와 `Flatten()` 후 순회했을 때의 결과를 비교하라. 이어서 `Handle`로 한 종류만 처리했을 때 어떤 예외가 다시 던져지는지 확인하라.
8. `Task.Run(() => throw new InvalidOperationException())`을 만들고 아무것도 관찰하지 않은 채 `GC.Collect()`와 `GC.WaitForPendingFinalizers()`를 호출하라. `TaskScheduler.UnobservedTaskException`에 핸들러를 걸어 두고, 그 핸들러가 실제로 호출되는지 확인하라.
9. 32.11절의 참조 타입 교환 함정을 재현하라. `MyCollection` 속성으로 참조를 받아 둔 뒤 `UpdateData()`를 호출하고, 받아 둔 참조가 옛 데이터를 보고 있는지 확인하라. 그 다음 `Envelope` 버전으로 바꿔 문제가 사라지는지 검증하라.
