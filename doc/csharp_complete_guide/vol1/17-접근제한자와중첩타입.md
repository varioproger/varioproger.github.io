# 17장. 접근 제한자와 중첩 타입

> **이 장의 위치** — 13장부터 16장까지 클래스·상속·`object`·구조체를 다루면서 접근 제한자는 `public`과 `private` 두 개만 썼다. 나머지 네 개(`internal`, `protected`, `protected internal`, `private protected`)와 ※C# 11의 `file`은 계속 미뤄 두었다. 이 장에서 그 빚을 갚는다. 접근 제한자는 문법이 단순한 대신 **규칙이 조합적**이라 정확히 알지 못하면 "왜 이게 안 보이지"에서 하루를 날린다. 그리고 접근 제어의 가장 강한 형태인 **중첩 타입**으로 Part III의 캡슐화 논의를 마무리한다.
>
> **선수 지식** — 12장(네임스페이스와 전처리기), 13장(클래스와 캡슐화), 14장(상속과 다형성)
>
> **이 장에서 다루지 않는 것** — 어셈블리가 무엇을 담고 매니페스트에 무엇이 기록되는지는 52.1절과 52.2절이다. 이 장은 "어셈블리는 접근성의 경계"라는 사실만 쓰고 그 실체는 52장에 맡긴다. 인터페이스 멤버의 접근성 규칙 전체(명시적 구현, 기본 구현 멤버의 한정자)는 18.3절과 18.7절이며 여기서는 접근 제한자와 충돌하는 지점만 본다. `sealed`의 문법은 14.5절, 컴파일러가 반복자·람다를 위해 만드는 중첩 타입의 내부는 28.4절과 26.10절이다. **API 설계 원칙으로서의 "가시성을 최소화하라"는 78.1절**에서 버전 관리·바이너리 호환성까지 묶어 다룬다. 이 장의 17.6절은 그 원칙을 지금 당장 쓸 수 있게 압축한 실무판이다. 리플렉션으로 비공개 멤버에 접근하는 방법은 57.7절이다.

## 17.1 접근 제한자 전체 — `public` / `internal` / `protected` / `private` / `protected internal` / `private protected`

캡슐화를 위해, 타입과 타입 멤버는 선언에 **접근 제한자(access modifier)** 를 붙여 다른 타입·다른 어셈블리에 대한 접근성을 제한할 수 있다. 이 절은 여섯 개(그리고 ※C# 11의 `file`까지 일곱 개)를 하나씩 정의하고, 그것이 IL과 런타임에서 무엇이 되는지까지 내려간다.

### 두 개의 축을 먼저 분리하라

접근 제한자를 어렵게 만드는 첫 번째 원인은 **서로 다른 두 질문을 하나의 키워드 목록으로 답하기 때문**이다. 두 질문은 이것이다.

1. **가시성(visibility)** — 이 타입이 다른 어셈블리에서 보이는가?
2. **접근성(accessibility)** — 이 멤버를 어떤 코드가 부를 수 있는가?

CLR 문헌은 이 둘을 다른 이름으로 부른다. 파일 수준(즉 다른 타입 안에 중첩되지 않은) 타입에 붙는 것은 **타입 가시성**이고, 멤버(중첩 타입 포함)에 붙는 것은 **멤버 접근성**이다.

```text
     타입 가시성                          멤버 접근성
   ┌───────────────┐                  ┌───────────────────────────┐
   │ public        │                  │ public                    │
   │ internal      │                  │ protected internal        │
   └───────────────┘                  │ internal                  │
   (최상위 타입은 이 둘뿐)             │ protected                 │
                                      │ private protected         │
   ※C# 11: file 추가                  │ private                   │
                                      └───────────────────────────┘
                                      (중첩 타입은 이 여섯 개 전부)
```

**최상위 타입에는 `public`과 `internal`만 붙는다.** `private class Foo {}`를 네임스페이스 바로 아래에 쓰면 컴파일 오류(CS1527)다. 이유는 단순하다 — `private`은 "포함하는 타입 안에서만"이라는 뜻인데, 최상위 타입에는 포함하는 타입이 없다. `protected` 계열도 마찬가지로 "파생 타입에서"라는 개념이 성립하지 않는다.

반면 **중첩 타입은 멤버**다. 그래서 여섯 가지 전부 붙일 수 있다. 이것이 중첩 타입의 존재 이유 중 하나이고, 17.5절에서 다시 본다.

> **📌 CTS가 정하고 CLR이 강제한다**
>
> 접근 제한자는 C#의 발명품이 아니다. 공통 타입 시스템(CTS)이 여섯 등급을 정의하고, CLR이 그것을 강제한다(2장). 각 언어는 그 여섯 등급에 자기 나름의 키워드를 붙일 뿐이다. 예를 들어 CTS가 `Assembly`라고 부르는 것을 C#은 `internal`이라 부르고, Visual Basic은 `Friend`라고 부른다. 그래서 IL을 읽을 때는 C# 키워드가 아니라 CTS 이름이 보인다.

### 여섯 개의 정의

| 한정자 | 접근 가능한 범위 | 붙일 수 있는 곳 |
|---|---|---|
| `public` | 완전 공개. 어느 어셈블리의 어떤 코드든 | 타입, 멤버, 중첩 타입 |
| `internal` | 포함하는 어셈블리, 그리고 friend 어셈블리(17.2절) 안에서만 | 타입, 멤버, 중첩 타입 |
| `protected` | 포함하는 타입, 그리고 그 타입에서 파생된 클래스 안에서만. **어셈블리는 무관** | 멤버, 중첩 타입 |
| `private` | 포함하는 타입 안에서만 | 멤버, 중첩 타입 |
| `protected internal` | `protected`와 `internal`의 **합집합(OR)** | 멤버, 중첩 타입 |
| `private protected` | `protected`와 `internal`의 **교집합(AND)** ※C# 7.2 | 멤버, 중첩 타입 |
| `file` | 같은 **파일** 안에서만. 소스 생성기용 ※C# 11 | 최상위 타입 선언만 |

정의는 짧지만 실제로 헷갈리는 것은 `protected internal`과 `private protected`다. 이름만 보면 둘 다 "protected와 internal을 섞은 것"이라 구분이 안 된다. 그래서 다이어그램이 필요하다.

### 접근 사분면 — 누가 접근할 수 있는가

어떤 멤버가 타입 `Base` 안에 선언되어 있다고 하자. 그 멤버에 접근하려는 코드는 **두 개의 축**으로 분류된다. 하나는 "같은 어셈블리인가", 다른 하나는 "`Base`에서 파생된 타입인가"다. 여기에 "`Base` 자기 자신 안인가"를 더하면 다섯 개의 영역이 나온다.

```text
                          같은 어셈블리              다른 어셈블리
                     ┌──────────────────────┬──────────────────────┐
   Base에서          │  ①                   │  ②                   │
   파생된 타입       │  같은 asm의 파생 타입 │  다른 asm의 파생 타입 │
                     ├──────────────────────┼──────────────────────┤
   Base와            │  ③                   │  ④                   │
   무관한 타입       │  같은 asm의 남         │  다른 asm의 남        │
                     └──────────────────────┴──────────────────────┘

              ⓪ = Base 타입 자신의 본문 안 (그리고 Base의 중첩 타입 안)
```

이제 여섯 한정자를 이 다섯 영역에 매핑하면 전부 설명된다.

| 한정자 | ⓪ 자기 안 | ① 같은asm 파생 | ② 다른asm 파생 | ③ 같은asm 남 | ④ 다른asm 남 |
|---|---|---|---|---|---|
| `private` | O | X | X | X | X |
| `private protected` | O | O | X | X | X |
| `protected` | O | O | O | X | X |
| `internal` | O | O | X | O | X |
| `protected internal` | O | O | O | O | X |
| `public` | O | O | O | O | O |

이 표가 이 절의 핵심이다. 여기서 세 가지가 즉시 읽힌다.

**첫째, `protected internal`은 OR다.** ①②③을 전부 덮는다. "파생 타입이거나(OR) 같은 어셈블리이거나" 둘 중 **하나만** 만족하면 접근된다. 그래서 `protected`보다도 넓고 `internal`보다도 넓다. `public` 바로 아래로 가장 넓은 한정자다.

**둘째, `private protected`는 AND다.** ①만 덮는다. "파생 타입이면서(AND) 같은 어셈블리"를 **동시에** 만족해야 한다. 그래서 `protected`보다도 좁고 `internal`보다도 좁다. `private` 바로 위로 가장 좁은 한정자다.

**셋째, 이름과 의미가 반대로 느껴지는 것이 정상이다.** `protected internal`은 두 키워드 중 어느 쪽에도 없던 넓이를 만들고, `private protected`는 두 키워드 중 어느 쪽에도 없던 좁음을 만든다. 헷갈릴 때는 **첫 번째 키워드가 힌트**라고 기억하면 된다. `protected internal`은 `protected`로 시작하니 열려 있고, `private protected`는 `private`으로 시작하니 닫혀 있다.

> **⚠️ `protected`는 어셈블리 경계를 무시한다**
>
> `protected` 멤버는 **다른 어셈블리의 파생 클래스에서도 보인다**(② 영역). 이것은 종종 잊힌다. `public` 클래스에 `protected` 멤버를 두면 그 멤버는 사실상 **공개 API의 일부**다. 누구든 그 클래스를 상속해서 `protected` 멤버를 읽고 쓸 수 있고, 시그니처를 바꾸면 남의 코드가 깨진다.
>
> `public` 타입의 `protected` 멤버를 "구현 세부사항"이라고 생각하고 마음대로 바꾸면 안 된다. 진짜로 어셈블리 안에서만 쓸 상속 훅이라면 `private protected`가 정확한 한정자다.

### 실코드로 확인하기

```csharp
// ---------- 어셈블리 A ----------
public class Base
{
    private            int a = 1;   // ⓪
    private protected  int b = 2;   // ⓪ ①
    protected          int c = 3;   // ⓪ ① ②
    internal           int d = 4;   // ⓪ ① ③
    protected internal int e = 5;   // ⓪ ① ② ③
    public             int f = 6;   // 전부

    void Self()
    {
        // 자기 본문(⓪) — 전부 보인다
        _ = a + b + c + d + e + f;
    }
}

class SameAsmDerived : Base          // ① 영역
{
    void M()
    {
        // _ = a;  // 오류 CS0122: 보호 수준 때문에 접근할 수 없다
        _ = b + c + d + e + f;       // private protected부터 전부 OK
    }
}

class SameAsmStranger                // ③ 영역
{
    void M(Base x)
    {
        // _ = x.b;  // 오류 — 파생 타입이 아니다
        // _ = x.c;  // 오류 — 파생 타입이 아니다
        _ = x.d + x.e + x.f;         // internal 계열과 public만 OK
    }
}
```

다른 어셈블리에서 보면 그림이 달라진다.

```csharp
// ---------- 어셈블리 B (A를 참조, friend 아님) ----------
using AssemblyA;

class OtherAsmDerived : Base         // ② 영역
{
    void M()
    {
        // _ = b;  // 오류 — private protected는 같은 어셈블리만
        // _ = d;  // 오류 — internal은 어셈블리 밖에서 안 보인다
        _ = c + e + f;               // protected, protected internal, public
    }
}

class OtherAsmStranger               // ④ 영역
{
    void M(Base x)
    {
        _ = x.f;                     // public만
    }
}
```

> **💡 `protected internal`을 실제로 써야 할 일은 드물다**
>
> 실무 코드베이스를 훑어보면 `protected internal`은 프레임워크 기반 클래스에서나 가끔 보이고, 애플리케이션 코드에는 거의 없다. "파생 타입 **또는** 같은 어셈블리"라는 조건이 자연스럽게 필요한 설계 상황이 드물기 때문이다.
>
> 대부분의 경우 실제로 원했던 것은 둘 중 하나다. 어셈블리 안의 협력이 필요하면 `internal`, 상속 훅이 필요한데 밖으로 열고 싶지 않으면 `private protected`. `protected internal`을 쓰려는 순간에는 "정말 두 경우를 다 열어야 하나"를 한 번 되물어라.

### 기본값 — 아무것도 안 쓰면 무엇이 되는가

접근 제한자를 생략했을 때의 기본값은 **선언 위치마다 다르다**. 이것이 두 번째로 흔한 사고 원인이다.

| 선언 위치 | 기본 접근성 | 비고 |
|---|---|---|
| 네임스페이스 직속(최상위) 타입 | `internal` | 둘 중 더 제한적인 쪽 |
| 클래스의 멤버 | `private` | 필드·메서드·프로퍼티·생성자 전부 |
| 구조체의 멤버 | `private` | 클래스와 동일 |
| 중첩 타입 | `private` | `internal`이 **아니다** |
| 인터페이스의 멤버 | `public` | 명시적으로 쓸 수 없었다(※C# 8부터 완화) |
| 열거형의 멤버 | `public` | 한정자를 붙일 수 없다 |
| 명시적 인터페이스 구현 | (한정자 금지) | 18.3절 |

```csharp
class Class1 {}                 // internal (기본값)
public class Class2 {}          // public — 어셈블리 밖에서 보인다

class ClassA { int x; }         // x는 private (기본값)
class ClassB { internal int x; } // x는 같은 어셈블리의 다른 타입에 노출된다

// 기본 생성자도 private이 될 수 있다
class Radio
{
    Radio() {}                  // private 생성자
}
```

> **⚠️ 중첩 타입의 기본값은 `private`이지 `internal`이 아니다**
>
> 최상위 타입의 기본값이 `internal`이라는 사실에 익숙해지면, 중첩 타입도 그럴 것이라고 착각하기 쉽다. 아니다. **중첩 타입은 멤버이므로 멤버의 기본값인 `private`을 따른다.**
>
> ```csharp
> public class Outer
> {
>     class Inner { }          // private! 같은 어셈블리에서도 안 보인다
> }
> ```
>
> 같은 어셈블리의 다른 파일에서 `Outer.Inner`를 못 찾겠다면 십중팔구 이것이다.

한 가지 더. **정적 클래스와 파이널라이저처럼 한정자를 아예 못 붙이는 자리**가 있다. 파이널라이저(`~Foo()`)에는 접근 제한자를 붙일 수 없고, 정적 생성자(`static Foo()`)에도 붙일 수 없다. 이들은 사용자 코드가 직접 호출하는 대상이 아니라 런타임이 호출하는 것이라 접근성 개념이 성립하지 않는다(13.12절, 13.16절).

### 컴파일 결과 — IL에서는 무엇이 되는가

이제 아래로 내려간다. C# 키워드는 IL 메타데이터의 **가시성 플래그**로 번역된다. 이름이 다르므로 대응표가 필요하다.

| C# 키워드 | CTS 이름 | IL 플래그 (멤버) | IL 플래그 (최상위 타입) | IL 플래그 (중첩 타입) |
|---|---|---|---|---|
| `private` | Private | `private` | (불가) | `nested private` |
| `private protected` | Family and Assembly | `famandassem` | (불가) | `nested famandassem` |
| `protected` | Family | `family` | (불가) | `nested family` |
| `internal` | Assembly | `assembly` | `private` | `nested assembly` |
| `protected internal` | Family or Assembly | `famorassem` | (불가) | `nested famorassem` |
| `public` | Public | `public` | `public` | `nested public` |

> **⚠️ 최상위 `internal` 타입은 IL에서 `private`으로 적힌다**
>
> 표의 이 칸이 IL 초심자를 반드시 한 번 넘어뜨린다. `ildasm` 출력에서 `.class private auto ansi Foo`를 보고 "이게 왜 private이지, 최상위 타입인데?"라고 생각하게 된다.
>
> IL 어셈블리 문법에서 최상위 타입의 가시성은 `public`(어셈블리 밖에서 보임)과 `private`(어셈블리 안에서만 보임) 두 개뿐이고, 후자가 C#의 `internal`이다. 즉 **같은 단어 `private`이 최상위 타입에서는 "어셈블리 스코프"를, 멤버에서는 "타입 스코프"를 뜻한다.** 문맥으로 구분해야 한다.
>
> 중첩 타입에는 `nested` 접두사가 붙으므로 헷갈리지 않는다. `nested private`은 진짜로 바깥 타입 안에서만 보인다는 뜻이다.

실제 출력을 보자. 다음 C# 코드를

```csharp
internal class Sample
{
    private            int _a;
    private protected  int _b;
    protected          int _c;
    internal           int _d;
    protected internal int _e;
    public             int _f;

    public class NestedPub { }
    private class NestedPriv { }
}
```

컴파일해서 `ildasm`으로 열면 이런 형태가 나온다.

```il
.class private auto ansi beforefieldinit Sample
       extends [System.Runtime]System.Object
{
  .class auto ansi nested public beforefieldinit NestedPub
         extends [System.Runtime]System.Object { }

  .class auto ansi nested private beforefieldinit NestedPriv
         extends [System.Runtime]System.Object { }

  .field private       int32 _a
  .field famandassem   int32 _b
  .field family        int32 _c
  .field assembly      int32 _d
  .field famorassem    int32 _e
  .field public        int32 _f
}
```

메서드도 마찬가지다. `.method public hidebysig instance void M() cil managed`에서 첫 번째 토큰이 접근성이다. IL을 읽는 법 전체는 56장에서 다루고, 가시성 플래그 목록은 56.3절에 있다.

### 메타데이터에서의 실체 — 3비트짜리 필드

한 층 더 내려가면, 이 플래그는 메타데이터 테이블의 **비트 필드**다. 리플렉션 API가 그대로 노출한다.

| `TypeAttributes` (타입) | 값 | 의미 |
|---|---|---|
| `NotPublic` | 0 | 최상위 `internal` |
| `Public` | 1 | 최상위 `public` |
| `NestedPublic` | 2 | 중첩 `public` |
| `NestedPrivate` | 3 | 중첩 `private` |
| `NestedFamily` | 4 | 중첩 `protected` |
| `NestedAssembly` | 5 | 중첩 `internal` |
| `NestedFamANDAssem` | 6 | 중첩 `private protected` |
| `NestedFamORAssem` | 7 | 중첩 `protected internal` |

이 8개 값은 `TypeAttributes.VisibilityMask`(= 7)로 마스킹해서 꺼낸다. 즉 **타입 가시성은 3비트**로 인코딩된다.

멤버 쪽도 구조가 같다. `MethodAttributes`와 `FieldAttributes`는 하위 3비트를 접근성에 쓴다. 마스크 상수의 이름은 두 열거형에서 서로 다르다 — `MethodAttributes.MemberAccessMask`(= 7)와 `FieldAttributes.FieldAccessMask`(= 7)다.

| `MethodAttributes` / `FieldAttributes` | 값 | C# |
|---|---|---|
| `PrivateScope` | 0 | (컴파일러 전용, C#에서 만들 수 없음) |
| `Private` | 1 | `private` |
| `FamANDAssem` | 2 | `private protected` |
| `Assembly` | 3 | `internal` |
| `Family` | 4 | `protected` |
| `FamORAssem` | 5 | `protected internal` |
| `Public` | 6 | `public` |

```csharp
using System.Reflection;

var t = typeof(Sample);
Console.WriteLine(t.Attributes & TypeAttributes.VisibilityMask);  // NotPublic

var f = t.GetField("_c", BindingFlags.Instance | BindingFlags.NonPublic);
Console.WriteLine(f!.Attributes & FieldAttributes.FieldAccessMask); // Family
```

> **📌 값이 낮을수록 좁다 — 우연이 아니다**
>
> 멤버 접근성 값 1~6은 `Private`(1)부터 `Public`(6)까지 **좁은 것부터 넓은 순서**로 배열되어 있다. 덕분에 두 접근성을 정수로 비교해서 "어느 쪽이 더 넓은가"를 판정할 수 있다. 컴파일러가 접근성 제한(17.3절)을 검사할 때 하는 일이 정확히 이 비교다.
>
> 딱 한 자리가 순서를 깬다. `FamANDAssem`(2, `private protected`)과 `Assembly`(3, `internal`)는 서로 포함 관계가 아니다 — `private protected`는 `internal`보다 좁지만, `Family`(4, `protected`)와는 비교 불가다. 접근성은 완전 순서가 아니라 **부분 순서**이고, 이 표의 숫자 순서는 근사일 뿐이다.

### 런타임 동작 — 접근 검사는 두 번 일어난다

접근 제한자는 컴파일 타임 개념처럼 보이지만 실제로는 **런타임에도 강제된다**. 검사는 두 단계다.

```text
   ┌──────────────────────────────────────────────────────────────┐
   │ 1단계  컴파일 타임 — C# 컴파일러                              │
   │   호출 지점의 접근성을 확인. 위반이면 CS0122 등으로 거부       │
   └────────────────────────┬─────────────────────────────────────┘
                            ↓  (IL 생성)
   ┌──────────────────────────────────────────────────────────────┐
   │ 2단계  JIT 타임 — 런타임                                      │
   │   IL의 필드·메서드 참조가 정말로 접근 가능한지 재확인          │
   │   위반이면 FieldAccessException / MethodAccessException 발생   │
   └──────────────────────────────────────────────────────────────┘
```

2단계가 왜 필요한가. 두 가지 이유다.

**첫째, 언어 컴파일러를 믿을 수 없다.** IL은 어떤 도구로든 만들 수 있고, 접근성 검사를 안 하는 컴파일러가 있을 수 있다. CLR은 IL을 네이티브 코드로 변환하면서 참조가 합법인지 스스로 확인한다.

**둘째, 그리고 훨씬 현실적인 이유 — 어셈블리는 따로 버전업된다.** 어셈블리 A가 어셈블리 B의 `public` 메서드를 호출하도록 컴파일되었다고 하자. 나중에 B의 새 버전에서 그 메서드가 `protected`나 `private`으로 바뀌었고, A는 재컴파일 없이 그 새 B와 함께 실행된다. 컴파일 타임에는 아무 문제가 없었지만 실행 시점에는 불법 접근이다. 이때 JIT이 `MethodAccessException`을 던진다.

```csharp
// 어셈블리 B v1: public void Helper()
// 어셈블리 B v2: internal void Helper()   ← 접근성이 좁아졌다
// 어셈블리 A는 v1로 컴파일된 채 v2와 실행 → MethodAccessException
```

> **⚠️ 접근성 축소는 바이너리 호환성을 깬다**
>
> 컴파일이 성공한다고 안전한 게 아니다. `public`을 `internal`로 바꾸는 것은 소스 호환성뿐 아니라 **바이너리 호환성**도 깬다. 이미 배포된 소비자 어셈블리는 재컴파일 없이 실행되다가 런타임 예외를 만난다. 그래서 라이브러리에서 `public`을 좁히는 변경은 사실상 메이저 버전 변경이다. 호환성을 깨는 변경 목록 전체는 78.13절에 있다.
>
> 반대 방향(좁은 것을 넓히는 것)은 안전하다. 그래서 처음에 좁게 시작하는 것이 이득이다(17.6절).

접근 위반 시 던져지는 예외는 **무엇에 접근했는가**에 따라 다르다.

| 위반 대상 | 예외 타입 |
|---|---|
| 필드 | `FieldAccessException` |
| 메서드(생성자 포함) | `MethodAccessException` |
| 타입 | `TypeAccessException` |

셋 다 `MemberAccessException`을 상속한다. 리플렉션으로 비공개 멤버를 부를 때도 같은 예외가 나올 수 있다(57.7절).

### 성능 영향

**정상 경로에서 접근 제한자의 런타임 비용은 0이다.** 검사는 JIT이 메서드를 컴파일할 때 **한 번** 일어나고, 생성된 네이티브 코드에는 아무 검사 코드도 남지 않는다. `private` 필드 읽기와 `public` 필드 읽기는 완전히 같은 기계어가 된다.

메타데이터 크기에도 영향이 없다. 앞에서 봤듯 접근성은 이미 존재하는 플래그 워드의 3비트를 쓸 뿐이다.

성능이 갈리는 지점은 다른 데 있다.

| 항목 | 영향 |
|---|---|
| 정상 호출 | 차이 없음. JIT 시점 1회 검사 후 코드에 흔적 없음 |
| 리플렉션 우회 | `BindingFlags.NonPublic` 조회 + 접근 검사 우회 비용이 크다(57.7절) |
| `[UnsafeAccessor]` ※.NET 8 | 런타임이 JIT 시점에 해석 → 호출 비용 0. 리플렉션의 대안(57.12절) |
| `sealed`와 결합 | 봉인된 타입에 대한 가상 호출은 JIT이 비가상으로 낮춘다(17.6절) |
| 트리밍·AOT | `internal`은 어셈블리 밖에서 참조 불가라는 사실이 정적 분석의 확실한 근거가 된다 |

> **💡 `private`은 성능 최적화가 아니라 설계 도구다**
>
> "필드를 `private`으로 두면 JIT이 더 최적화한다"는 말은 사실이 아니다. JIT은 접근성이 아니라 **타입이 봉인되었는지, 가상 호출인지, 인라인 가능한지**를 본다.
>
> 접근 제한자가 성능에 기여하는 경로는 간접적이다. 좁은 접근성은 곧 "이 멤버를 건드릴 수 있는 코드의 집합이 작다"는 뜻이고, 그래야 나중에 `sealed`를 붙이거나 필드를 없애거나 표현을 바꾸는 최적화를 **안심하고** 할 수 있다. 좁게 시작하는 것이 남기는 것은 성능이 아니라 **성능을 나중에 얻을 자유**다.

### `file` 한정자 ※C# 11

C# 11은 일곱 번째 한정자를 추가했다. `file`이 붙은 타입은 **같은 소스 파일 안에서만** 접근된다.

```csharp
// Helpers.cs
file class Formatter          // 이 파일 밖에서는 존재하지 않는 것과 같다
{
    public static string Wrap(string s) => $"[{s}]";
}

public class Report
{
    public string Render() => Formatter.Wrap("ok");   // 같은 파일이므로 OK
}
```

```csharp
// Other.cs
class Consumer
{
    // void M() => Formatter.Wrap("x");   // 오류 — Formatter가 보이지 않는다

    // 그리고 이렇게 써도 충돌하지 않는다
}

file class Formatter          // 다른 파일의 file 타입과 이름이 같아도 무방
{
    public static string Wrap(string s) => $"<{s}>";
}
```

**이 기능은 사람이 쓰라고 만든 게 아니다.** 소스 생성기(source generator)를 위한 것이다. 소스 생성기는 사용자 프로젝트에 코드 파일을 밀어 넣는데, 그 파일에 헬퍼 타입을 정의하면 이름이 충돌할 위험이 있다. 생성기가 여러 개 돌거나, 같은 생성기가 여러 파일을 만들거나, 사용자가 우연히 같은 이름을 썼을 때다. `file`은 그 충돌을 원천 차단한다. 소스 생성기와 부분 타입의 접점은 13.14절에서 다뤘다.

컴파일 결과를 보면 트릭이 드러난다. 컴파일러는 `file` 타입을 **`internal` 타입으로 방출하되 이름을 맹글링**한다. 파일마다 다른 이름이 되므로 메타데이터 수준에서 충돌이 사라진다.

```text
소스:      file class Formatter
메타데이터: <Helpers>F<해시>__Formatter   (형태는 컴파일러 구현 세부. 버전에 따라 다르다)
가시성:     internal (assembly)
```

즉 **`file`은 CLR의 새 가시성 등급이 아니다.** 앞의 6등급 체계는 그대로이고, `file`은 C# 컴파일러가 이름 맹글링으로 구현하는 **언어 수준 한정자**다. IL을 읽다가 이상한 꺾쇠 이름을 만나면 이것일 수 있다.

> **⚠️ `file` 한정자의 제약 네 가지**
>
> 1. **최상위 타입 선언에만 붙는다.** 중첩 타입에는 못 붙이고, 멤버에는 당연히 못 붙인다.
> 2. **다른 접근 제한자와 함께 쓸 수 없다.** `public file class`는 오류다.
> 3. **`file` 타입이 다른 타입의 공개 시그니처에 새어 나가면 오류다.** `file class F {}` 옆에서 `public F Get() => ...`를 쓸 수 없다. 파일 밖 코드가 그 반환 타입을 표현할 방법이 없기 때문이다. 이것은 접근성 제한(17.3절)의 특수한 형태다.
> 4. **`partial`과 함께 쓸 때 모든 부분 선언이 같은 파일에 있어야 한다.** 정의상 당연하다.
>
> 실무에서 손으로 `file`을 쓸 일은 거의 없다. 만약 쓰고 싶어진다면, 그 타입이 정말 파일 하나에만 쓰인다는 뜻이므로 **중첩 `private` 타입**(17.5절)이 더 나은 선택인지 먼저 검토하라.

## 17.2 friend 어셈블리 (`InternalsVisibleTo`)

`internal`의 경계는 어셈블리다. 그런데 그 경계를 **선택적으로** 뚫어야 할 때가 있다. .NET은 그것을 **friend 어셈블리**로 지원한다.

### 왜 필요한가

두 가지 상황이 압도적으로 흔하다.

**첫째, 팀 분리.** 회사에 팀 A가 유틸리티 타입 묶음을 만들고 팀 B가 그것을 쓴다. 일정·조직·비용 센터가 달라서 두 팀은 하나의 어셈블리로 빌드할 수 없고 각자 어셈블리를 낸다. 팀 B가 팀 A의 타입을 쓰려면 팀 A는 그 타입들을 `public`으로 만들어야 한다. 그런데 `public`으로 만드는 순간 **세상 모든 어셈블리에 공개**된다. 다른 회사 개발자가 그 유틸리티 타입에 의존하는 코드를 쓸 수도 있는데, 이건 원하는 바가 아니다. 팀 A의 타입은 팀 B가 지키는 특정 가정 위에서만 안전할지도 모른다.

**둘째, 단위 테스트.** 테스트 프로젝트는 별도 어셈블리인데, `internal` 클래스와 `internal` 메서드를 테스트하고 싶다. 테스트를 위해 프로덕션 API를 `public`으로 넓히는 것은 꼬리가 개를 흔드는 짓이다.

두 경우 모두 답은 같다. **타입은 `internal`로 두되, 특정 어셈블리에게만 `internal`을 보여준다.**

### 문법

`internal`을 가진 쪽(= 노출하는 쪽)이 어셈블리 수준 특성을 선언한다.

```csharp
using System.Runtime.CompilerServices;

[assembly: InternalsVisibleTo("MyApp.Tests")]

internal sealed class OrderValidator { /* ... */ }
```

이제 `MyApp.Tests` 어셈블리는 이 어셈블리의 **모든 `internal` 타입과 모든 `internal` 멤버**를 마치 `public`인 것처럼 쓸 수 있다.

```csharp
// MyApp.Tests 어셈블리
using MyApp;

public class OrderValidatorTests
{
    [Fact]
    public void RejectsNegativeQuantity()
    {
        var v = new OrderValidator();      // internal 타입인데 보인다
        Assert.False(v.IsValid(-1));
    }
}
```

SDK 스타일 프로젝트에서는 특성 대신 **MSBuild 항목**을 쓸 수 있다(.NET 5 SDK 이상).

```xml
<ItemGroup>
  <InternalsVisibleTo Include="MyApp.Tests" />
</ItemGroup>
```

빌드 시스템이 이 항목을 보고 위의 특성을 자동으로 생성해 준다. 4.8절에서 본 것처럼 이 방식이 선호되는 이유는 **가시성**이다. 프로젝트 파일을 열면 어떤 어셈블리가 friend인지 한눈에 보인다. 소스 트리 어딘가의 `AssemblyInfo.cs`를 뒤질 필요가 없다.

> **⚠️ 이름이 정확히 일치해야 하고, 조용히 끊긴다**
>
> `InternalsVisibleTo`의 문자열은 friend 어셈블리의 **단순 이름**이다. 프로젝트 이름이 아니라 어셈블리 이름이므로, `<AssemblyName>`을 프로젝트 이름과 다르게 지정했다면 그쪽을 써야 한다.
>
> 그리고 오타가 나거나 나중에 어셈블리 이름을 바꾸면 **경고 없이 friend 관계가 사라진다.** 존재하지 않는 어셈블리를 friend로 지정하는 것 자체는 오류가 아니기 때문이다. 증상은 "어제까지 되던 테스트가 갑자기 컴파일 안 됨"으로 나타난다. `InternalsVisibleTo`를 건드린 적이 없어도 `AssemblyName`이나 프로젝트 이름을 바꿨다면 여기를 의심하라.

### 강력한 이름이 붙은 경우 — 공개 키가 필요하다

friend 어셈블리가 **강력한 이름(strong name)** 으로 서명되어 있다면 단순 이름만으로는 부족하다. 전체 공개 키를 함께 지정해야 한다.

```csharp
[assembly: InternalsVisibleTo("StrongFriend, PublicKey=0024f000048c...")]
```

여기서 지정하는 것은 **공개 키 토큰(public key token)이 아니라 전체 공개 키**다. 1024비트 RSA 키의 경우 공개 키 blob은 160바이트, 16진수로는 320자다. 토큰(8바이트, 16자)을 넣으면 동작하지 않는다.

전체 공개 키는 대상 어셈블리에서 리플렉션으로 뽑을 수 있다.

```csharp
using System.Reflection;

string key = string.Join("",
    Assembly.GetExecutingAssembly().GetName().GetPublicKey()
            .Select(b => b.ToString("x2")));

Console.WriteLine(key);   // 320자 16진 문자열
```

.NET Framework SDK가 설치된 Windows에서는 `sn -Tp <assembly.dll>` 명령으로도 확인할 수 있다. 강력한 이름과 서명 전반은 52.5절에서 다룬다.

> **⚠️ 강력한 이름 어셈블리는 서명 안 된 friend를 가질 수 없다**
>
> 노출하는 쪽이 강력한 이름으로 서명되어 있다면, friend로 지정하는 모든 어셈블리도 서명되어 있어야 하고 공개 키를 명시해야 한다. 서명 안 된 어셈블리 이름만 적으면 "강력한 이름으로 서명된 어셈블리는 `InternalsVisibleTo` 선언에 공개 키를 명시해야 한다"는 취지의 컴파일 오류가 난다.
>
> 이유는 보안이다. 이름만으로 friend를 정하면 아무나 같은 이름의 어셈블리를 만들어 `internal`에 접근할 수 있다. 공개 키를 요구하면 위조가 불가능해진다. 반대로 **노출하는 쪽이 서명되어 있지 않다면** friend 이름만 적어도 되고, friend 쪽도 서명될 필요가 없다.

> **⚠️ 문자열에 버전·컬처·아키텍처를 넣으면 안 된다**
>
> `InternalsVisibleTo`에 넘기는 문자열은 **이름과 `PublicKey`만** 담아야 한다. `Version=`, `Culture=`, `ProcessorArchitecture=`를 붙이면 안 된다. 그래서 friend 관계는 버전과 무관하게 유지된다 — 팀 B가 어셈블리를 2.0으로 올려도 friend 관계는 그대로다.
>
> 실수로 정규화된 어셈블리 이름 전체를 복사해 붙이는 경우가 있는데, 이러면 관계가 성립하지 않는다.

### 컴파일 결과와 런타임 동작

`InternalsVisibleTo`는 특별한 컴파일러 마법이 아니라 **평범한 어셈블리 수준 특성**이다. 매니페스트의 `CustomAttribute` 테이블에 그대로 기록된다(52.2절).

```il
.assembly MyApp
{
  .custom instance void [System.Runtime]System.Runtime.CompilerServices
          .InternalsVisibleToAttribute::.ctor(string)
          = ( 01 00 0C 4D 79 41 70 70 2E 54 65 73 74 73 00 00 )  // ...MyApp.Tests..
  .ver 1:0:0:0
}
```

컴파일 타임에는 C# 컴파일러가 참조된 어셈블리의 이 특성을 읽어 "내가 friend인가"를 판정하고, 맞으면 `internal` 멤버를 이름 조회 후보에 포함시킨다.

런타임에도 같은 확인이 일어난다. 17.1절에서 본 JIT의 2단계 접근 검사는 `assembly`(= `internal`) 접근성을 만나면 **호출자 어셈블리가 정의 어셈블리와 같은지, 또는 friend 목록에 있는지**를 확인한다. 즉 friend 관계는 메타데이터에 기록된 실제 런타임 개념이지 컴파일러가 눈감아 주는 것이 아니다.

> **📌 `/out:` 스위치라는 역사적 유물**
>
> 오래된 문헌은 "friend 어셈블리(특성을 갖지 **않은** 쪽)를 컴파일할 때 `/out:<file>` 스위치가 필요하다"고 설명한다. 컴파일러가 자신이 만드는 어셈블리의 이름을 알아야 friend 여부를 판정할 수 있는데, 원래는 컴파일이 끝나야 출력 파일 이름이 정해지기 때문이었다. 성능상의 이유로 명시를 요구한 것이다.
>
> SDK 스타일 프로젝트에서는 MSBuild가 항상 `-out:`을 넘기므로 이 제약이 보이지 않는다. 마찬가지로 `/t:module`과 `/moduleassemblyname:` 이야기도 다중 모듈 어셈블리 시절 유물이다(52.3절).

### 실무 함정 네 가지

**첫째, friend 관계는 단방향이다.** A가 B를 friend로 선언해도 B의 `internal`이 A에게 보이지는 않는다. 양방향이 필요하면 양쪽 다 선언해야 한다.

**둘째, friend 관계는 전이되지 않는다.** A가 B를 friend로, B가 C를 friend로 선언해도 C는 A의 `internal`을 볼 수 없다.

**셋째, 문은 전부 아니면 전무다.** "이 `internal` 타입만 열고 저건 닫기" 같은 세밀한 제어는 없다. friend로 지정하면 **그 어셈블리의 모든 `internal` 타입과 모든 `internal` 멤버**가 열린다. 그래서 어떤 멤버를 `internal`로 둘지, 누구를 friend로 선언할지를 신중히 정해야 한다.

**넷째, `internal` 타입의 인터페이스 구현은 `InternalsVisibleTo` 없이도 밖에서 호출된다.** 이건 friend와 무관한 별개 함정인데 같이 알아둘 만하다.

```csharp
internal class Countdown : IEnumerator
{
    int count = 11;
    public bool MoveNext() => count-- > 0;
    public object Current => count;
    public void Reset() => throw new NotSupportedException();
}

public static class Util
{
    public static object GetCountdown() => new Countdown();
}
```

`Countdown`은 `internal`이지만, 다른 어셈블리에서 이렇게 할 수 있다.

```csharp
IEnumerator e = (IEnumerator) Util.GetCountdown();
e.MoveNext();      // 동작한다
```

`IEnumerator` 자체가 `public` 인터페이스이고, `Countdown`의 구현 멤버들은 `public`이기 때문이다. 호출자는 `Countdown`이라는 이름을 표현할 수 없을 뿐, 그 동작에는 완전히 접근한다. `IEnumerator`가 `internal`이었다면 이것도 불가능했을 것이다.

> **💡 friend 어셈블리 대신 검토할 것**
>
> `InternalsVisibleTo`는 편리하지만 어셈블리 경계에 구멍을 낸다. 쓰기 전에 세 가지를 확인하라.
>
> 1. **테스트가 진짜로 `internal`에 닿아야 하나.** 공개 API만으로 테스트할 수 있다면 그게 더 나은 테스트다. 구현 세부에 붙은 테스트는 리팩터링마다 깨진다(80.1절).
> 2. **`internal`이어야 할 것이 사실은 별도 타입인가.** 테스트하고 싶은 로직을 `public`한 작은 타입으로 뽑아내면 구멍이 필요 없어진다.
> 3. **리플렉션이 아니라 `[UnsafeAccessor]`가 답인가.** ※.NET 8 이상이라면 비공개 멤버에 접근하는 정적 방법이 있다(57.12절). 다만 이것도 캡슐화를 깨는 것이므로 최후 수단이다.
>
> 그럼에도 단위 테스트를 위한 `InternalsVisibleTo`는 널리 인정된 관행이다. 문제가 되는 것은 **프로덕션 어셈블리 사이에** 이걸 남발하는 경우다. 두 어셈블리가 서로의 `internal`을 알아야 한다면, 그건 애초에 하나의 어셈블리여야 했다는 신호인 경우가 많다.

## 17.3 접근성 제한(accessibility capping)

접근 제한자를 정확히 이해하려면 마지막 규칙 하나가 필요하다. **멤버의 실제 접근성은 자기가 붙인 한정자와 자신을 감싼 것들의 한정자를 모두 고려해서 결정된다.** 컨테이너보다 넓은 접근성은 의미를 가질 수 없기 때문이다. 이것을 **접근성 제한(capping)** 이라고 부른다.

### 가장 흔한 형태

가장 흔한 예는 `internal` 타입에 `public` 멤버를 두는 것이다.

```csharp
class C                      // 한정자 없음 → internal (기본값)
{
    public void Foo() {}     // public이라고 썼지만…
}
```

`C`의 `internal` 가시성이 `Foo`의 접근성을 **상한선으로 자른다**. 결과적으로 `Foo`는 사실상 `internal`이다. 다른 어셈블리에서는 `C`라는 타입 자체가 보이지 않으므로 `Foo`에 도달할 방법이 없다.

여기서 중요한 것은 **이것이 오류가 아니라는 점**이다. 컴파일러는 아무 말도 하지 않는다.

> **📌 그럼에도 `public`을 붙이는 이유**
>
> "어차피 잘릴 텐데 왜 `public`을 쓰나"라는 질문이 나온다. 이유는 **리팩터링 대비**다. 나중에 `C`를 `public`으로 승격시키기로 결정했을 때, 멤버가 이미 `public`이면 클래스 선언 한 줄만 고치면 된다. 멤버가 전부 기본값 `private`이었다면 승격과 동시에 멤버를 하나씩 열어야 하고, 그 과정에서 열어야 할 것과 아닌 것을 다시 판단해야 한다.
>
> 반대 입장도 있다. "실제 접근성과 코드에 쓰인 글자가 다르면 읽는 사람이 오해한다"는 것이다. 어느 쪽이든 팀 안에서 일관되면 된다. 다만 **`internal` 타입 안의 `public`은 진짜 `public`이 아니라는 사실**만은 모두가 알아야 한다.

### 접근성 도메인 — 정확한 계산 규칙

capping을 정확히 계산하려면 **접근성 도메인(accessibility domain)** 이라는 개념이 필요하다. 어떤 선언의 접근성 도메인은 "그 선언을 참조할 수 있는 프로그램 텍스트의 집합"이다.

규칙은 재귀적이다.

```text
   실효 접근성(M) = min( 선언된 접근성(M), 실효 접근성(M을 감싼 타입) )

   여기서 min은 "더 좁은 쪽"을 뜻한다.
```

이 규칙이 중첩을 따라 밖으로 계속 적용된다.

```csharp
public class A                 // 실효: public
{
    protected class B          // 선언 protected, 컨테이너 public → 실효 protected
    {
        public class C         // 선언 public,   컨테이너 protected → 실효 protected
        {
            internal int x;    // 선언 internal, 컨테이너 protected → 실효 private protected
        }
    }
}
```

마지막 줄이 흥미롭다. `internal`과 `protected`의 교집합은 `private protected`다. 즉 `x`는 "같은 어셈블리이면서 `A`에서 파생된 타입" 안에서만 닿을 수 있다. 선언에는 `private protected`라는 글자가 어디에도 없지만 결과는 그렇게 된다.

| 컨테이너의 실효 접근성 | 멤버 선언 | 멤버의 실효 접근성 |
|---|---|---|
| `public` | `public` | `public` |
| `internal` | `public` | `internal` |
| `internal` | `protected` | `private protected` |
| `internal` | `protected internal` | `internal` |
| `protected` | `public` | `protected` |
| `protected` | `internal` | `private protected` |
| `private` (중첩) | 무엇이든 | `private` |

> **⚠️ `internal` 클래스의 `protected` 멤버는 `private protected`가 된다**
>
> 표의 세 번째 행이 실무에서 종종 혼란을 부른다. `internal class Base { protected int X; }`에서 `X`는 "어느 어셈블리든 파생 타입"이 아니라 "같은 어셈블리의 파생 타입"에서만 보인다. 어차피 `Base`가 밖에서 안 보이니 밖에서 파생할 수도 없다 — 논리적으로는 당연하다.
>
> 문제는 나중에 `Base`를 `public`으로 승격시킬 때다. 그 순간 `X`의 실효 접근성이 `private protected`에서 `protected`로 **조용히 넓어진다**. 코드 한 글자 안 바꿨는데 공개 API 표면이 늘어난 것이다. 라이브러리에서 타입을 승격시킬 때는 그 안의 `protected` 멤버를 전부 다시 검토해야 한다.

### 조용히 좁혀지는 경우 vs 컴파일 오류가 나는 경우

여기가 이 절의 핵심이다. **컨테이너가 멤버를 자르는 것은 조용하고, 시그니처가 접근성을 새게 하는 것은 오류다.** 왜 다른가.

```text
  ┌──────────────────────────────────────────────────────────────────┐
  │ 조용한 capping                                                    │
  │                                                                   │
  │   internal class C { public void Foo() {} }                       │
  │                                                                   │
  │   → 밖에서 C가 안 보이니 Foo에도 도달 불가. 모순이 없다.          │
  │   → 컴파일러는 "당신이 쓴 public은 아무 해를 끼치지 않는다"고 판단 │
  └──────────────────────────────────────────────────────────────────┘

  ┌──────────────────────────────────────────────────────────────────┐
  │ 컴파일 오류 (CS0050 계열)                                          │
  │                                                                   │
  │   internal class Secret {}                                        │
  │   public class Api { public Secret Get() => new(); }              │
  │                                                                   │
  │   → 밖에서 Api.Get()은 보이는데, 그 반환 타입 Secret은 안 보인다.  │
  │   → 호출자가 결과를 담을 변수를 선언할 방법이 없다. 모순이다.      │
  └──────────────────────────────────────────────────────────────────┘
```

핵심은 **표현 가능성(expressibility)** 이다. 접근 가능한 멤버의 시그니처에 등장하는 모든 타입은 그 멤버를 볼 수 있는 모든 코드에서도 볼 수 있어야 한다. 그렇지 않으면 호출자가 그 멤버를 문법적으로 사용할 수 없다.

컴파일러는 이 위반을 **자리마다 다른 오류 번호**로 보고한다.

| 오류 | 상황 |
|---|---|
| CS0050 | 반환 타입이 메서드보다 덜 접근 가능 |
| CS0051 | 매개변수 타입이 메서드보다 덜 접근 가능 |
| CS0052 | 필드 타입이 필드보다 덜 접근 가능 |
| CS0053 | 프로퍼티 타입이 프로퍼티보다 덜 접근 가능 |
| CS0060 | 기반 클래스가 파생 클래스보다 덜 접근 가능 |
| CS0061 | 기반 인터페이스가 파생 인터페이스보다 덜 접근 가능 |

인덱서와 델리게이트에도 각각 대응하는 오류 번호가 따로 있다. 번호를 외울 필요는 없고, 메시지의 첫 단어가 항상 "Inconsistent accessibility"라는 것만 기억하면 된다. 한국어 환경에서는 "일관성 없는 접근성"으로 나온다.

```csharp
internal class Secret { }

public class Api
{
    public Secret Get() => new();          // CS0050
    public void Put(Secret s) { }          // CS0051
    public Secret Field;                   // CS0052
    public Secret Prop { get; set; }       // CS0053
}

internal class Base { }
public class Derived : Base { }            // CS0060
```

고치는 방법은 셋 중 하나다.

1. **노출되는 타입을 넓힌다** — `Secret`을 `public`으로. 정말 공개할 만한 타입인지 먼저 판단하라.
2. **노출하는 멤버를 좁힌다** — `Get`을 `internal`로. 대개 이쪽이 정답이다.
3. **경계에서 타입을 바꾼다** — `Secret` 대신 `public` 인터페이스나 DTO를 반환한다. 설계상 가장 깨끗하다.

> **⚠️ `private` 멤버는 이 검사에서 자유롭다**
>
> `private` 멤버의 시그니처에는 무엇이든 올 수 있다. `private` 멤버는 컨테이너 타입 안에서만 보이고, 그 안에서는 모든 중첩 타입이 보이기 때문이다.
>
> ```csharp
> public class Api
> {
>     private class Impl { }
>     private Impl Make() => new();   // OK — 아무 오류 없음
>     // public Impl Make2() => new(); // 오류 CS0050
> }
> ```
>
> 이 성질이 중첩 `private` 타입을 유용하게 만든다(17.5절).

### 제네릭이 개입할 때

제네릭 타입 인자도 시그니처의 일부이므로 같은 검사를 받는다.

```csharp
internal class Secret { }

public class Api
{
    // public List<Secret> GetAll() => new();   // 오류 — Secret이 새어 나간다
    internal List<Secret> GetAll() => new();    // OK
}
```

제네릭 **제약**도 마찬가지다. `public` 제네릭 타입의 `where` 절에 `internal` 타입을 쓰면 접근성이 일관되지 않다는 오류가 난다. 제약이 호출자에게 보이지 않으면 그 제약을 만족하는 타입 인자를 고를 수 없기 때문이다. 제네릭 제약 전체는 23.6절에서 다룬다.

> **💡 capping을 진단하는 가장 빠른 방법**
>
> "이게 왜 안 보이지"를 디버깅할 때는 **바깥에서 안으로** 훑어라. 순서는 이렇다.
>
> 1. 어셈블리가 다른가? → `internal`이면 여기서 끝. friend인지 확인
> 2. 최상위 타입이 `public`인가? → 아니면 여기서 끝
> 3. (중첩이라면) 각 단계의 중첩 타입이 충분히 열려 있는가?
> 4. 멤버 자신의 한정자는?
>
> 대부분의 사고는 2번과 3번에서 난다. IDE의 "Go to Definition"은 접근성과 무관하게 동작하므로, 정의로 점프가 되는데도 코드가 컴파일 안 되는 상황이 자연스럽게 생긴다. 정의로 갈 수 있다는 것과 부를 수 있다는 것은 다른 얘기다.

## 17.4 접근 제한자에 걸리는 제약들

접근 제한자는 아무 데나 아무거나 붙일 수 있는 게 아니다. 컴파일러는 일관성 없는 사용을 막는다. 이 절은 그 제약들을 한자리에 모은다.

### 제약 1 — 재정의할 때 접근성은 동일해야 한다

기반 클래스의 함수 멤버를 재정의할 때, **재정의 멤버의 접근성은 원본과 같아야 한다.**

```csharp
class BaseClass
{
    protected virtual void Foo() {}
}

class Subclass1 : BaseClass
{
    protected override void Foo() {}     // OK
}

class Subclass2 : BaseClass
{
    public override void Foo() {}        // 오류 CS0507 — 접근성을 바꿀 수 없다
}
```

예외가 하나 있다. **다른 어셈블리에서 `protected internal` 메서드를 재정의할 때는 재정의가 `protected`여야 한다.** 그 어셈블리에서는 `internal` 부분이 의미를 잃기 때문이다(14.2절에서 이미 언급했다).

```csharp
// 어셈블리 A
public class Base
{
    protected internal virtual void Hook() {}
}

// 어셈블리 B
public class Derived : Base
{
    protected override void Hook() {}    // OK — protected internal이 아니라 protected
}
```

> **📌 이것은 C#의 제약이지 CLR의 제약이 아니다**
>
> CLR은 파생 타입에서 멤버의 접근성이 **덜 제한적으로** 바뀌는 것을 허용한다. `protected` 메서드를 재정의하면서 `public`으로 넓히는 것이 IL 수준에서는 합법이다. C# 팀이 언어 차원에서 그것을 금지한 것이다.
>
> 그런데 CLR도 반대 방향은 금지한다. `protected`를 `private`으로 좁히는 재정의는 CLR 수준에서 불법이다. 이유는 명쾌하다 — 파생 타입 사용자가 언제든 기반 타입으로 캐스팅해서 그 멤버에 접근할 수 있으므로, **좁혔다고 주장해 봐야 강제할 수 없기 때문**이다. 강제할 수 없는 주장은 애초에 하지 않게 만드는 것이 CLR의 설계 원칙이다.

한 가지 더. **`virtual`, `abstract`, `override` 멤버는 `private`일 수 없다.** 파생 타입에서 보이지 않는 멤버를 재정의하라는 것은 모순이므로 컴파일 오류다. `private protected`는 가능하다 — 같은 어셈블리의 파생 타입에서는 보이기 때문이다.

### 제약 2 — 파생 타입은 기반 타입보다 넓을 수 없다

```csharp
internal class A {}
public class B : A {}     // 오류 CS0060
```

이유는 17.3절의 표현 가능성 논리와 같다. 다른 어셈블리에서 `B`가 보이는데, `B`가 무엇을 상속했는지는 표현할 수 없다. `B`의 인스턴스를 `A`로 취급하는 코드도 쓸 수 없다. 인터페이스도 같다.

```csharp
internal interface IHidden {}
public interface IVisible : IHidden {}    // 오류 CS0061
```

**반대 방향은 자유롭다.** 파생 타입이 기반 타입보다 좁은 것은 아무 문제가 없다.

```csharp
public class A {}
internal class B : A {}   // OK — 흔한 패턴이다
```

이 패턴은 실무에서 매우 유용하다. 공개 추상 기반 클래스나 인터페이스를 노출하고, 구체 구현은 `internal`로 감춘 뒤 팩터리로 만들어 주는 것이다.

```csharp
public abstract class Cache
{
    public static Cache Create(int capacity) => new LruCache(capacity);
    public abstract object? Get(string key);
    public abstract void Set(string key, object value);
}

internal sealed class LruCache : Cache        // 구현은 감춘다
{
    // ...
    public override object? Get(string key) => throw new NotImplementedException();
    public override void Set(string key, object value) { }
}
```

호출자는 `Cache`만 알고, `LruCache`라는 이름은 어셈블리 밖으로 나가지 않는다. 나중에 구현을 통째로 바꿔도 공개 API는 그대로다.

### 제약 3 — 인터페이스 구현은 `public`이어야 한다

인터페이스 멤버는 암묵적으로 `public`이다. 따라서 **암시적 구현(implicit implementation)은 반드시 `public`이어야 한다.**

```csharp
internal class Countdown : IEnumerator
{
    int count = 11;
    public bool MoveNext() => count-- > 0;      // public 필수
    public object Current => count;
    public void Reset() => throw new NotSupportedException();
}
```

`public`을 빼면 "구현이 public이 아니므로 인터페이스 멤버를 구현할 수 없다"는 취지의 오류가 난다.

**명시적 구현(explicit implementation)은 정반대로 접근 제한자를 붙일 수 없다.**

```csharp
class Countdown2 : IEnumerator
{
    int count = 11;
    bool IEnumerator.MoveNext() => count-- > 0;      // 한정자 금지
    object IEnumerator.Current => count;
    void IEnumerator.Reset() => throw new NotSupportedException();
    // public bool IEnumerator.MoveNext() => ...;    // 오류
}
```

명시적 구현 멤버는 이름으로는 호출할 수 없고, 인터페이스로 캐스팅해야만 닿는다. 그래서 "접근성"이라는 개념이 성립하지 않는다. IL 수준에서는 `private final virtual newslot`으로 방출되고 `.override` 지시문이 붙는다. 자세한 것은 18.3절이다.

> **⚠️ ※C# 8부터 인터페이스 멤버에도 한정자를 붙일 수 있다**
>
> "인터페이스 멤버에는 접근 제한자를 쓸 수 없다"는 서술은 **C# 8 이전의 이야기**다. 기본 구현 멤버(default interface member)가 도입되면서 인터페이스에도 `private`, `protected`, `internal`, `public`, `static`, `virtual`, `sealed`, `abstract`를 명시할 수 있게 되었다.
>
> ```csharp
> public interface ILogger
> {
>     void Log(string message);                      // 암묵적 public abstract
>     public void LogError(string m) => Log("E: " + m);   // 기본 구현
>     private static string Stamp() => DateTime.UtcNow.ToString("O");
> }
> ```
>
> 그래도 **한정자를 생략하면 여전히 `public`** 이다. 클래스와 정반대라는 사실은 변하지 않았다. 기본 구현 멤버의 의미론 전체는 18.7절이다.

### 제약 4 — `protected` 접근에는 자격이 필요하다

이것이 가장 자주 사람을 넘어뜨리는 제약이다. `protected` 멤버를 파생 클래스에서 접근할 때, **접근 대상의 정적 타입이 자기 자신(또는 자기에서 파생된 타입)이어야 한다.**

```csharp
public class Base
{
    protected int Value;
}

public class DerivedA : Base
{
    void M(Base other, DerivedA sameKind, DerivedB otherKind)
    {
        _ = this.Value;       // OK
        _ = sameKind.Value;   // OK — DerivedA
        // _ = other.Value;   // 오류 CS1540 — 한정자가 Base 타입이다
        // _ = otherKind.Value; // 오류 CS1540 — 형제 타입이다
    }
}

public class DerivedB : Base { }
```

왜 이런 규칙이 있는가. `protected`는 "파생 클래스가 **자기 자신의** 기반 부분을 다룰 수 있다"는 뜻이지, "파생 클래스가 **아무 `Base` 인스턴스든** 뜯어볼 수 있다"는 뜻이 아니다. 후자를 허용하면 아무나 `Base`를 상속하는 클래스를 하나 만들어서 모든 `Base` 인스턴스의 `protected` 상태를 읽고 쓸 수 있게 된다 — 캡슐화가 완전히 무너진다.

> **⚠️ CS1540은 상속을 처음 쓸 때 반드시 한 번 만난다**
>
> 오류 메시지는 "'Base.Value'는 'Base' 형식의 한정자를 통해 액세스할 수 없습니다. 한정자는 'DerivedA' 형식이거나 여기에서 파생된 형식이어야 합니다"처럼 나온다. `Equals`나 `CompareTo`를 구현하면서 상대방 객체의 `protected` 필드를 읽으려 할 때 자주 나온다.
>
> 해법은 대개 셋 중 하나다. (1) 매개변수 타입을 `DerivedA`로 좁힌다, (2) `protected` 대신 `internal`로 바꾼다(같은 어셈블리라면), (3) 애초에 `protected` 필드를 쓰지 말고 `protected` 프로퍼티/메서드로 감싼다.

### 제약 5 — 위치에 따라 아예 못 쓰는 한정자

| 위치 | 못 쓰는 한정자 | 이유 |
|---|---|---|
| 네임스페이스 직속 타입 | `private`, `protected` 계열 | 감싸는 타입이 없다 (CS1527) |
| 구조체의 멤버 | `protected` 계열 셋 전부 | 구조체는 상속될 수 없다 (16.1절) |
| 정적 클래스의 멤버 | `protected` 계열 | 파생될 수 없다 |
| 파이널라이저 | 전부 | 런타임이 호출한다 (13.16절) |
| 정적 생성자 | 전부 | 런타임이 호출한다 (13.12절) |
| 명시적 인터페이스 구현 | 전부 | 이름으로 호출 불가 (18.3절) |
| 열거형 멤버 | 전부 | 항상 `public` |
| 지역 함수·지역 변수 | 전부 | 스코프가 이미 메서드 본문이다 |
| `file` 타입 | 다른 접근 제한자와 병용 | 배타적이다 (17.1절) |

`sealed` 클래스에 `protected` 멤버를 선언하는 것은 오류는 아니지만 **경고(CS0628)** 가 나온다. 봉인 클래스에는 파생 타입이 있을 수 없으므로 `protected`는 `private`과 다름없고, 그러면서 읽는 사람에게는 "상속을 염두에 둔 멤버"라는 잘못된 신호를 준다. 경고를 그대로 두지 말고 `private`으로 바꿔라.

### 제약 6 — 프로퍼티 접근자의 접근성

프로퍼티와 인덱서는 접근자별로 **더 좁은** 접근성을 지정할 수 있다.

```csharp
public class Account
{
    public decimal Balance { get; private set; }        // 흔한 관용구
    public string Name { get; protected set; }
    internal int Version { get; private set; }
}
```

규칙은 셋이다.

1. **접근자 한정자는 프로퍼티 자신보다 반드시 좁아야 한다.** `private string Name { get; public set; }`은 오류다.
2. **두 접근자 중 하나에만 붙일 수 있다.** 둘 다 붙이면 오류다. 둘 다 좁히고 싶으면 프로퍼티 자체를 좁혀라.
3. **자동 구현 프로퍼티가 아니어도 같다.** 명시적 접근자 본문이 있어도 규칙은 동일하다.

> **💡 `{ get; private set; }`이 진짜 불변은 아니다**
>
> `private set`은 "밖에서 못 쓴다"는 뜻이지 "아무도 못 쓴다"는 뜻이 아니다. 클래스 안의 어떤 메서드든 값을 바꿀 수 있다. 진짜 불변을 원한다면 `{ get; }`(읽기 전용 자동 프로퍼티)나 `{ get; init; }`를 쓰는 게 낫다(13.8절, 19장).
>
> 그렇더라도 `private set`은 유용하다. "이 값은 클래스 내부 로직으로만 변한다"는 의도를 코드로 표현하고, 밖에서의 잘못된 대입을 컴파일 타임에 막는다.

### 인터페이스 재구현과 접근성

인터페이스를 명시적으로 구현한 멤버는 파생 클래스에서 접근할 수 없다. `protected` 훅을 함께 두는 것이 표준 관용구다.

```csharp
public class TextBox : IUndoable
{
    void IUndoable.Undo() => Undo();          // 명시적 구현은 protected 훅으로 위임
    protected virtual void Undo() { /* ... */ }
}

public class RichTextBox : TextBox
{
    protected override void Undo() { /* 재정의 가능 */ }
}
```

이 관용구가 왜 필요하고 어떤 대안이 있는지는 18.4절에서 다룬다.

## 17.5 중첩 타입 — 언제 쓰고 언제 피하나

**중첩 타입(nested type)** 은 다른 타입의 스코프 안에 선언된 타입이다.

```csharp
public class TopLevel
{
    public class Nested { }                     // 중첩 클래스
    public enum Color { Red, Blue, Tan }        // 중첩 열거형
}
```

클래스, 구조체, 인터페이스, 델리게이트, 열거형 — **모든 타입**을 클래스나 구조체 안에 중첩할 수 있다. 인터페이스 안에도 중첩할 수 있다 ※C# 8. 반면 네임스페이스는 타입 안에 중첩할 수 없다.

### 중첩 타입의 네 가지 특징

**첫째, 바깥 타입의 `private` 멤버에 접근할 수 있다.** 그리고 바깥 타입이 접근할 수 있는 모든 것에도 접근할 수 있다.

```csharp
public class TopLevel
{
    static int x;

    class Nested
    {
        static void Foo() => Console.WriteLine(TopLevel.x);   // private 필드에 접근
    }
}
```

이것이 중첩 타입의 가장 강력한 성질이다. 별도 타입으로 뺐다면 `x`를 `internal`로 열어야 했을 텐데, 중첩하면 `private`인 채로 협력할 수 있다.

**그리고 이 관계는 양방향이다.** 바깥 타입도 중첩 타입의 `private` 멤버에 접근할 수 있다. `private`의 정확한 정의가 "선언된 타입 선언의 프로그램 텍스트 안"이고, 중첩 타입은 바깥 타입의 텍스트 안에 있기 때문이다.

```csharp
public class Outer
{
    class Inner
    {
        private int secret = 42;
    }

    int Read() => new Inner().secret;    // OK — 바깥이 안쪽의 private을 읽는다
}
```

**둘째, 접근 제한자 여섯 가지를 전부 쓸 수 있다.** 최상위 타입은 `public`과 `internal`뿐이지만 중첩 타입은 멤버이므로 `private`, `protected`, `private protected`도 가능하다.

```csharp
public class TopLevel
{
    protected class Nested { }
}

public class SubTopLevel : TopLevel
{
    static void Foo() => new TopLevel.Nested();   // 파생 타입이므로 OK
}
```

**셋째, 기본 접근성은 `private`이다.** `internal`이 아니다. 17.1절에서 강조한 함정이다.

**넷째, 바깥에서 참조하려면 바깥 타입 이름으로 한정해야 한다.** 정적 멤버에 접근할 때와 같은 문법이다.

```csharp
public class TopLevel
{
    public class Nested { }
}

class Test
{
    TopLevel.Nested n;                            // 한정 필요
}

// 열거형도 같다
TopLevel.Color color = TopLevel.Color.Red;
```

`using static TopLevel;`을 쓰면 한정을 생략할 수 있다. 정적 using은 중첩 타입도 가져오기 때문이다(12.4절).

### 컴파일 결과 — 메타데이터에서의 이름

중첩 타입의 이름은 메타데이터에서 **`Outer+Inner`** 형태가 된다. 네임스페이스 구분자인 점(`.`)이 아니라 **더하기(`+`)** 를 쓴다.

| 개념 | 소스 | 메타데이터 이름 | 네임스페이스 필드 |
|---|---|---|---|
| 네임스페이스 중첩 | `namespace A { class B {} }` | `B` | `A` |
| 타입 중첩 | `class A { class B {} }` | `B` | (비어 있음) |
| 완전 정규화 표기 | — | `A+B` | — |

즉 중첩 타입은 **자기 네임스페이스를 갖지 않는다.** 대신 메타데이터의 `NestedClass` 테이블에 "`B`의 바깥은 `A`"라는 항목이 하나 추가된다(52.2절). 이 차이는 리플렉션에서 즉시 드러난다.

```csharp
Type t1 = Type.GetType("MyNs.Outer");           // 최상위 타입
Type t2 = Type.GetType("MyNs.Outer+Inner");     // 중첩 타입 — 점이 아니라 +

Console.WriteLine(typeof(Environment.SpecialFolder).FullName);
// System.Environment+SpecialFolder
```

리플렉션 API도 중첩 타입을 특별 취급한다. `public`으로 선언한 중첩 타입도 `Type.IsPublic`은 `false`이고 `IsNestedPublic`이 `true`다. 자세한 것은 57.1절이다.

```il
.class public auto ansi beforefieldinit MyNs.Outer
       extends [System.Runtime]System.Object
{
  .class auto ansi nested public beforefieldinit Inner
         extends [System.Runtime]System.Object
  {
  }
}
```

> **⚠️ 중첩 타입은 바깥 인스턴스를 자동으로 참조하지 않는다**
>
> Java의 내부 클래스(inner class)를 아는 사람이 반드시 걸려 넘어지는 지점이다. Java의 비정적 내부 클래스는 바깥 인스턴스에 대한 숨은 참조를 갖고, `outer.new Inner()`로 만들며, 내부에서 `Outer.this`를 쓸 수 있다.
>
> **C#의 중첩 타입에는 그런 것이 없다.** C#의 중첩 타입은 항상 Java의 `static` 중첩 클래스에 해당한다. 바깥 인스턴스의 필드에 접근하려면 명시적으로 참조를 넘겨야 한다.
>
> ```csharp
> public class Outer
> {
>     int _value;
>
>     public class Inner
>     {
>         readonly Outer _owner;                    // 직접 들고 있어야 한다
>         public Inner(Outer owner) => _owner = owner;
>         public int Read() => _owner._value;       // private에는 접근 가능
>     }
> }
> ```
>
> 좋은 소식은, 그 덕분에 **C#의 중첩 타입은 뜻하지 않은 메모리 누수를 만들지 않는다**는 점이다. Java의 내부 클래스는 바깥 객체를 살려 두는 흔한 누수 원인이다.

### 제네릭 중첩

제네릭 타입 안의 중첩 타입은 **바깥의 타입 매개변수를 그대로 쓸 수 있다.**

```csharp
public class Cache<TKey, TValue>
{
    private sealed class Entry           // TKey, TValue를 그냥 쓴다
    {
        public TKey Key = default!;
        public TValue Value = default!;
        public Entry? Next;
    }

    private Entry?[] _buckets = new Entry?[16];
}
```

`Entry`는 자기 타입 매개변수를 선언하지 않았지만 **암묵적으로 `Cache<TKey, TValue>`의 것을 물려받는다.** 그래서 `Cache<string, int>.Entry`와 `Cache<int, int>.Entry`는 서로 다른 닫힌 타입이다.

메타데이터 이름 규칙은 조금 까다롭다. **제네릭 타입의 아리티(arity) 표기는 그 타입이 직접 선언한 타입 매개변수의 개수만 센다.**

| 소스 | 메타데이터 이름 |
|---|---|
| `class Outer<T> { class Inner {} }` | `Outer\`1+Inner` |
| `class Outer<T> { class Inner<U> {} }` | `Outer\`1+Inner\`1` |
| `class Outer { class Inner<U> {} }` | `Outer+Inner\`1` |

두 번째 행이 핵심이다. `Inner<U>`는 실제로는 타입 인자가 두 개(`T`와 `U`)지만 이름에는 `` `1 ``만 붙는다. `Inner`가 **직접 선언한** 것이 하나이기 때문이다. 리플렉션으로 이런 타입을 다룰 때 이 규칙을 모르면 `Type.GetType`이 계속 `null`을 반환한다(57.4절).

```csharp
// 언바운드 제네릭 중첩 타입을 typeof로 얻는 문법
Type t = typeof(Cache<,>.Entry);          // 꺾쇠는 바깥에만 붙는다
```

> **⚠️ 중첩 타입은 바깥의 타입 매개변수 이름을 재사용할 수 없다**
>
> ```csharp
> class Outer<T>
> {
>     class Inner<T> { }        // 경고 CS0693 — 이름이 가려진다
> }
> ```
>
> 컴파일은 되지만 경고가 난다. 안쪽 `T`가 바깥 `T`를 완전히 가려서, 안쪽에서는 바깥 `T`를 표현할 방법이 사라진다. 거의 항상 버그이니 이름을 바꿔라.

### 컴파일러가 만드는 중첩 타입

중첩 타입은 컴파일러 자신이 가장 많이 쓴다. C#의 여러 문법 설탕이 상태를 담을 클래스를 필요로 하는데, 그것을 **`private` 중첩 타입**으로 만든다.

| C# 문법 | 생성되는 중첩 타입 | 다루는 장 |
|---|---|---|
| `yield return` 반복자 | `<M>d__0` 상태 기계 | 28.4절 |
| `async` 메서드 | `<M>d__0` 상태 기계 | 47장 |
| 변수를 캡처하는 람다 | `<>c__DisplayClass0_0` 디스플레이 클래스 | 26.10절 |
| 캡처 없는 람다 | `<>c` 캐시 클래스 | 26.11절 |
| LINQ 쿼리의 익명 타입 | `<>f__AnonymousType0<...>` | 29.10절 |

이름이 전부 꺾쇠(`<>`)로 시작하는 이유가 있다. **C# 식별자로는 쓸 수 없는 문자**라서 사용자 코드와 절대 충돌하지 않기 때문이다. IL은 이런 이름을 허용한다.

```il
.class auto ansi sealed nested private beforefieldinit
       '<GetNumbers>d__0'
       extends [System.Runtime]System.Object
       implements class [System.Runtime]System.Collections.Generic.IEnumerable`1<int32>,
                  ...
```

디컴파일러에서 이런 타입이 안 보인다면 "컴파일러 생성 멤버 표시" 옵션이 꺼져 있는 것이다(56.8절).

### 정당한 사례 — 중첩 타입을 써야 할 때

중첩 타입을 쓰는 이유는 딱 두 가지여야 한다. **(1) 더 강한 접근 제어가 필요하거나, (2) 바깥 타입의 `private` 멤버에 접근해야 하거나.** 다음은 그 둘 중 하나 이상을 만족하는 실제 패턴들이다.

**사례 1 — 열거자 구조체.** 컬렉션의 열거자는 컬렉션의 내부 배열과 버전 카운터를 읽어야 한다. 중첩하면 그것들을 `private`으로 유지할 수 있다.

```csharp
public sealed class RingBuffer<T>
{
    private T[] _items;
    private int _head, _count, _version;

    public RingBuffer(int capacity) => _items = new T[capacity];

    public Enumerator GetEnumerator() => new Enumerator(this);

    public struct Enumerator                      // 구조체 → foreach에서 힙 할당 없음
    {
        private readonly RingBuffer<T> _owner;
        private readonly int _version;
        private int _index;

        internal Enumerator(RingBuffer<T> owner)
        {
            _owner = owner;
            _version = owner._version;            // private 필드 직접 접근
            _index = -1;
        }

        public T Current => _owner._items[(_owner._head + _index) % _owner._items.Length];

        public bool MoveNext()
        {
            if (_version != _owner._version)
                throw new InvalidOperationException("열거 중 컬렉션이 변경되었다.");
            return ++_index < _owner._count;
        }
    }
}
```

BCL이 정확히 이 구조를 쓴다. `List<T>.Enumerator`, `Dictionary<TKey,TValue>.Enumerator`가 전부 중첩 구조체다. **성능 효과가 실질적이다** — `foreach`가 인터페이스 대신 구조체 열거자를 쓰면 박싱과 힙 할당이 사라지고 `MoveNext`가 인라인될 수 있다(24.1절, 28.1절).

**사례 2 — 빌더.** 빌더는 만들어질 대상의 내부 상태를 채워야 한다. 중첩하면 대상의 생성자를 `private`으로 두고도 빌더만 부를 수 있다.

```csharp
public sealed class HttpRequest
{
    public string Method { get; }
    public Uri Url { get; }

    private HttpRequest(string method, Uri url) => (Method, Url) = (method, url);
    //  ↑ private 생성자 — 빌더를 통해서만 만들 수 있다

    public static Builder Create(Uri url) => new Builder(url);

    public sealed class Builder
    {
        private string _method = "GET";
        private readonly Uri _url;

        internal Builder(Uri url) => _url = url;

        public Builder WithMethod(string m) { _method = m; return this; }
        public HttpRequest Build() => new HttpRequest(_method, _url);   // private 생성자 호출
    }
}
```

**사례 3 — 전용 비교자·전략 객체.** 하나의 타입만을 위한 `IComparer<T>` 구현을 밖에 노출할 이유가 없다.

```csharp
public sealed class Version2
{
    public int Major { get; init; }
    public int Minor { get; init; }

    public static IComparer<Version2> Comparer { get; } = new ByNumber();

    private sealed class ByNumber : IComparer<Version2>
    {
        public int Compare(Version2? a, Version2? b)
        {
            if (a is null || b is null) return Comparer<object>.Default.Compare(a, b);
            int c = a.Major.CompareTo(b.Major);
            return c != 0 ? c : a.Minor.CompareTo(b.Minor);
        }
    }
}
```

호출자는 `Version2.Comparer`라는 `IComparer<Version2>`만 본다. `ByNumber`라는 이름은 존재조차 모른다. 구현을 통째로 갈아치워도 API가 안 변한다.

**사례 4 — 옵션·설정 열거형.** 하나의 타입에만 의미가 있는 열거형은 그 타입 안에 두는 것이 정확하다.

```csharp
public sealed class JsonWriter
{
    public enum Indentation { None, Tab, TwoSpaces, FourSpaces }
    public Indentation Style { get; set; }
}
```

이 경우는 위의 두 이유 중 어느 것도 만족하지 않지만, **이름이 곧 문서**가 되는 효과가 있어서 예외적으로 인정된다. `JsonWriter.Indentation.Tab`은 `Indentation.Tab`보다 읽기 쉽다. BCL의 `Environment.SpecialFolder`, `StringSplitOptions`(이쪽은 중첩이 아니다) 같은 사례를 비교해 보면 기준이 감각적으로 잡힌다.

### 남용 — 중첩 타입을 피해야 할 때

> **⚠️ 네임스페이스가 지저분해지는 것을 막으려고 중첩하지 마라**
>
> "타입이 너무 많아서 네임스페이스가 어지럽다"는 이유로 중첩 타입을 쓰는 것은 잘못된 도구 선택이다. 그럴 때 필요한 것은 **중첩 네임스페이스**다.
>
> ```csharp
> // 나쁨 — 정리 목적의 중첩
> public class Shapes
> {
>     public class Circle { }
>     public class Square { }
> }
>
> // 좋음 — 네임스페이스로 정리
> namespace MyApp.Shapes;
> public class Circle { }
> public class Square { }
> ```
>
> 중첩 타입은 **더 강한 접근 제어가 필요할 때**, 또는 **바깥 타입의 `private` 멤버에 접근해야 할 때** 쓰는 것이다. 정리는 네임스페이스의 일이다(12장).

`public` 중첩 타입은 특히 문제가 많다. 코드 분석기의 **CA1034 "중첩 타입은 표시되지 않아야 합니다"** 규칙이 이것을 잡아낸다. 이유는 이렇다.

| 문제 | 설명 |
|---|---|
| 이름이 길어진다 | `Outer.Middle.Inner` 같은 이름을 매번 써야 한다 |
| 발견 가능성이 낮다 | IDE의 타입 목록·문서에서 최상위 타입보다 눈에 덜 띈다 |
| 이동이 파괴적 변경이다 | 나중에 최상위로 빼면 이름이 바뀌므로 호환성이 깨진다 |
| 언어 간 상호운용 | 일부 언어에서 중첩 타입 접근 문법이 어색하다 |
| 순환 의존을 감춘다 | 바깥과 안쪽이 서로를 알아도 파일 하나 안이라 잘 안 보인다 |

> **💡 판단 체크리스트**
>
> 중첩할지 말지 3초 안에 결정하는 방법이다.
>
> | 질문 | 예 | 아니오 |
> |---|---|---|
> | 바깥 타입의 `private` 멤버를 읽어야 하나? | 중첩 강력 추천 | 다음 질문 |
> | 바깥 타입 밖에서 이 타입을 이름으로 쓸 일이 있나? | 최상위로 빼라 | 다음 질문 |
> | 이 타입 이름이 바깥 타입 이름 없이도 뜻이 통하나? | 최상위로 빼라 | 중첩 |
> | 중첩 깊이가 2를 넘나? | 무조건 리팩터링 | OK |
>
> 그리고 결론이 "중첩"이라면 **접근성을 `private` 또는 `internal`로 두는 것을 기본으로 하라.** `public` 중첩 타입은 위 표의 정당한 사례(열거자, 빌더, 전용 열거형)에 해당할 때만 쓴다.

### 성능 영향

**중첩 자체에는 런타임 비용이 없다.** 중첩 타입은 이름과 메타데이터 관계만 다를 뿐, 실행 시점에는 최상위 타입과 완전히 같은 방식으로 로드되고 인스턴스화된다. `Outer.Inner`를 만드는 것이 `OuterInner`를 만드는 것보다 느리지 않다.

성능이 갈리는 것은 **중첩 덕분에 가능해진 설계**다.

| 효과 | 설명 |
|---|---|
| 구조체 열거자 | `private` 필드 직접 접근 덕분에 열거자를 구조체로 만들 수 있다 → `foreach`에서 힙 할당 0 |
| `private sealed` 구현 | 어셈블리 밖에서 파생될 수 없으므로 JIT의 비가상화 판단이 쉬워진다 |
| 접근자 메서드 생략 | `internal` 프로퍼티로 감쌀 필요 없이 필드에 직접 접근 → 인라인되지 않을 위험 제거 |
| 트리밍 | `private` 중첩 타입은 바깥 타입이 제거되면 함께 제거된다 |

반대로 **중첩 타입이 성능을 해치는 경우**도 하나 있다. 중첩 구조체가 바깥 클래스의 참조를 필드로 들고 있으면(위 `RingBuffer<T>.Enumerator`처럼) 그 구조체는 참조를 포함하므로 GC 스캔 대상이 된다. `Span<T>`처럼 참조를 아예 안 담는 설계와는 다른 비용 프로필을 갖는다(68장).

## 17.6 타입 가시성을 최소화하라 — 설계 원칙

접근 제한자의 문법과 기계는 앞의 다섯 절에서 끝났다. 이 절은 그것을 **어떻게 고를 것인가**를 다룬다. API 설계 원칙으로서의 전체 논의 — 버전 관리, 바이너리 호환성, 컴포넌트와 다형성의 삼각관계 — 는 78.1절과 78.13절에 있다. 여기서는 지금 코드를 쓰면서 바로 적용할 수 있는 것만 압축한다.

### 원칙: 좁게 시작하고, 필요할 때 넓혀라

이 원칙의 근거는 **비대칭성**이다.

```text
   좁은 것 → 넓은 것              넓은 것 → 좁은 것
   ┌──────────────────┐          ┌──────────────────┐
   │  internal        │          │  public          │
   │      ↓           │          │      ↓           │
   │  public          │          │  internal        │
   └──────────────────┘          └──────────────────┘

   안전하다.                      깨진다.
   소비자 코드는 그대로 컴파일     소스 호환성 파괴 + 바이너리 호환성 파괴
   되고 그대로 실행된다.           (MethodAccessException — 17.1절)
```

넓히기는 언제든 할 수 있고 아무도 다치지 않는다. 좁히기는 이미 배포된 소비자를 깨뜨린다. 따라서 **확신이 없으면 좁은 쪽**이 항상 옳다. C#이 기본값을 `internal`과 `private`으로 정한 것도 이 비대칭 때문이다.

### 규칙 1 — 필드는 예외 없이 `private`

데이터 필드는 항상 `private`이다. 여기에는 타협이 없다. 필드를 `public`이나 `protected`로 열면 다음을 전부 포기하게 된다.

- 값의 유효성 검사
- 값이 바뀔 때의 부수 효과(알림, 캐시 무효화)
- 표현 변경(필드 두 개를 하나로 합치거나, 계산 값으로 바꾸기)
- 스레드 안전성 확보

밖에 노출해야 한다면 프로퍼티로 감싸라. 컴파일된 코드에서 자동 구현 프로퍼티의 접근자는 대개 인라인되므로 **직접 필드 접근과 성능이 같다**(13.8절).

> **⚠️ `protected` 필드는 `public` 필드와 다를 게 없다**
>
> `protected` 필드는 "파생 클래스만 쓰니까 안전하다"고 착각하기 쉽다. 아니다. `public` 클래스의 `protected` 필드는 **누구든 상속해서 마음대로 읽고 쓸 수 있다**(17.1절의 ② 영역). 기반 클래스는 자기 상태가 언제 어떻게 바뀌는지 통제권을 잃는다.
>
> 상속 훅이 필요하다면 `protected` **프로퍼티**나 `protected` **메서드**로 노출하라. 필드는 `private`으로 남긴다.

### 규칙 2 — 클래스는 기본적으로 `sealed`

이것은 논쟁적인 규칙이지만 근거가 탄탄하다. 세 가지 이유가 있다.

**첫째, 버전 관리.** 봉인된 클래스는 나중에 봉인을 풀 수 있다. 호환성이 깨지지 않는다. 그러나 봉인되지 않은 클래스는 **영원히 봉인할 수 없다** — 그렇게 하면 모든 파생 클래스가 깨진다. 게다가 봉인되지 않은 클래스에 봉인되지 않은 `virtual` 메서드가 있다면, 새 버전에서도 가상 메서드 호출 순서를 유지해야 한다. 그러지 않으면 파생 타입이 조용히 오동작한다.

**둘째, 성능.** 가상 메서드 호출은 비가상 호출보다 느리다. CLR이 실행 시점에 객체의 타입을 조회해서 어느 타입의 메서드를 부를지 정해야 하기 때문이다. 그런데 **JIT이 봉인 타입에 대한 가상 호출을 보면 비가상으로 낮춘다.** 봉인되었으니 파생 클래스가 있을 수 없다는 것을 알기 때문이다.

```csharp
public sealed class Point
{
    private int _x, _y;
    public Point(int x, int y) => (_x, _y) = (x, y);
    public override string ToString() => $"({_x}, {_y})";
}

// 호출 지점
Point p = new Point(3, 4);
Console.WriteLine(p.ToString());
// C# 컴파일러는 callvirt를 방출하지만, p의 타입 Point가 sealed이므로
// JIT은 이 호출을 비가상으로 만든다(그리고 인라인 후보가 된다).
```

**셋째, 보안과 예측 가능성.** 클래스는 자기 상태를 지켜야 하고 절대 손상되게 두면 안 된다. 봉인되지 않으면 파생 클래스가 `private`이 아닌 데이터 필드와 메서드를 통해 기반 클래스의 상태에 접근하고 조작할 수 있다. 게다가 `virtual` 메서드는 재정의될 수 있고, 파생 클래스는 기반 구현을 부를지 말지 스스로 정한다. 메서드·프로퍼티·이벤트를 `virtual`로 만드는 순간 **기반 클래스는 자기 동작과 상태에 대한 통제권 일부를 포기하는 것**이다. 충분히 설계하지 않으면 객체가 예측 불가능하게 동작하고 보안 구멍이 생긴다.

> **📌 봉인이 기본값이었어야 했다**
>
> CLR 설계자 관점에서는 컴파일러가 클래스를 **기본적으로 봉인**해야 했다. 실제로는 C#을 포함한 대부분의 컴파일러가 봉인되지 않은 클래스를 기본으로 삼고, 프로그래머가 `sealed`를 명시하게 한다. 이제 와서 바꿀 수는 없지만, 오늘의 컴파일러가 잘못된 기본값을 골랐다는 견해는 널리 공유된다.
>
> 봉인 클래스의 문제는 **타입 사용자에게 불편하다**는 것이다. 개발자는 기존 타입에서 파생해서 자기 애플리케이션용 필드나 상태 정보를 붙이고 싶을 때가 있다. CLR은 이미 빌드된 타입을 헬퍼 메서드나 필드로 확장하는 메커니즘을 제공하지 않지만, **확장 메서드**로 헬퍼 메서드를 흉내 낼 수 있고 `ConditionalWeakTable`로 객체에 상태를 덧붙이는 것을 흉내 낼 수 있다.

### 규칙 3 — 타입은 기본적으로 `internal`

퍼블릭 API 표면은 **약속**이다. 한 번 `public`으로 내보낸 타입은 다음을 전부 감수해야 한다.

| 비용 | 내용 |
|---|---|
| 이름을 못 바꾼다 | 이름 변경은 소스·바이너리 양쪽 호환성을 깬다 |
| 시그니처를 못 바꾼다 | 매개변수 추가·타입 변경이 전부 파괴적이다 |
| 삭제할 수 없다 | 사용자가 하나라도 있으면 영원히 남는다 |
| 문서화 의무 | XML 문서 주석, 예제, 마이그레이션 가이드 |
| 리플렉션 대상 | 사용자가 리플렉션으로 접근할 수 있고, 트리밍이 보수적이 된다 |

이 비용을 지불할 가치가 있는 타입만 `public`으로 만든다. 나머지는 전부 `internal`이다. C#이 최상위 타입의 기본값을 `internal`로 정한 것은 다행이다 — 아무것도 안 쓰면 옳은 쪽으로 간다.

```csharp
// 라이브러리의 전형적 구조
public interface IPaymentGateway { Task<Receipt> ChargeAsync(decimal amount); }
public sealed record Receipt(string Id, decimal Amount);

public static class PaymentGateways                      // 진입점만 public
{
    public static IPaymentGateway CreateStripe(string key) => new StripeGateway(key);
}

internal sealed class StripeGateway : IPaymentGateway    // 구현은 전부 internal
{
    private readonly HttpClient _http;
    // ...
    public Task<Receipt> ChargeAsync(decimal amount) => throw new NotImplementedException();
}

internal sealed class RetryPolicy { /* ... */ }
internal static class SignatureUtil { /* ... */ }
```

공개 표면은 인터페이스 하나, 레코드 하나, 정적 팩터리 하나다. 나머지 구현은 언제든 통째로 갈아치울 수 있다.

### 실전 판단표

| 상황 | 고를 한정자 |
|---|---|
| 데이터 필드 | `private` (예외 없음) |
| 상수(`const`)이고 의미가 공개적 | `public` 허용. 단 값이 컴파일 타임에 박히므로 주의(79.2절) |
| 클래스 내부 헬퍼 메서드 | `private` |
| 같은 어셈블리의 다른 타입이 쓰는 헬퍼 | `internal` |
| 테스트에서만 필요한 접근 | `internal` + `InternalsVisibleTo`(17.2절) |
| 어셈블리 안의 상속 훅 | `private protected` |
| 라이브러리 사용자를 위한 상속 훅 | `protected` — 신중히. 사실상 공개 API다 |
| 하나의 타입만을 위한 도우미 타입 | `private` 중첩 타입 |
| 라이브러리의 진입점 | `public` — 최소 개수로 |
| 소스 생성기가 만드는 헬퍼 타입 | `file` ※C# 11 |

> **💡 `.editorconfig`로 강제하라**
>
> 접근성 규칙은 코드 리뷰에서 잡기 힘들다. 사람이 매번 "이거 왜 public이지"를 묻기는 지친다. 분석기에 맡기는 것이 낫다.
>
> ```text
> # .editorconfig
> # 중첩 타입은 표시되지 않아야 한다
> dotnet_diagnostic.CA1034.severity = warning
> # 인스턴스화되지 않는 internal 클래스
> dotnet_diagnostic.CA1812.severity = suggestion
> # 봉인할 수 있는 타입은 봉인하라
> dotnet_diagnostic.CA1852.severity = warning
> # 가시적 인스턴스 필드를 쓰지 마라
> dotnet_diagnostic.CA1051.severity = warning
> ```
>
> `CA1852`(봉인 가능한 타입 봉인)는 특히 유용하다. 코드베이스 전체를 훑어서 파생 타입이 없는 `internal` 클래스를 찾아 준다. 분석기와 `.editorconfig` 활용 전반은 79.13절에서 다룬다.

> **⚠️ 접근성을 좁히는 리팩터링은 배포 전에 하라**
>
> `public`을 `internal`로 되돌리는 것은 라이브러리를 배포한 뒤에는 사실상 불가능하다. 그래서 **첫 배포 직전이 마지막 기회**다. 릴리스 체크리스트에 "공개 타입 목록 검토"를 넣어라.
>
> 공개 표면 목록은 리플렉션으로 뽑을 수 있다.
>
> ```csharp
> foreach (Type t in typeof(SomePublicType).Assembly.GetExportedTypes())
>     Console.WriteLine(t.FullName);
> ```
>
> `GetExportedTypes()`는 어셈블리 밖에서 보이는 타입만 준다 — 즉 정확히 "약속한 것들"의 목록이다(57.10절). 이 목록이 예상보다 길다면 지금이 줄일 때다.

## 이 장의 요약

- **접근 제한자는 두 개의 축을 하나의 키워드 목록으로 답한다.** 최상위 타입에 붙는 것은 **가시성**(`public` / `internal` 둘뿐)이고, 멤버와 중첩 타입에 붙는 것은 **접근성**(여섯 가지 전부)이다. 이 둘을 분리해서 생각하면 대부분의 혼란이 사라진다.
- **`protected internal`은 OR이고 `private protected`는 AND다.** 전자는 "파생 타입이거나 같은 어셈블리"로 `public` 다음으로 넓고, 후자는 "파생 타입이면서 같은 어셈블리"로 `private` 다음으로 좁다. 첫 번째 키워드가 넓이의 힌트다.
- **기본값은 위치마다 다르다.** 최상위 타입은 `internal`, 클래스·구조체 멤버는 `private`, **중첩 타입도 `private`**(`internal`이 아니다), 인터페이스 멤버는 `public`, 열거형 멤버도 `public`이다.
- **IL에서 이름이 다르고, 최상위 `internal`은 `private`으로 적힌다.** `private` / `famandassem` / `family` / `assembly` / `famorassem` / `public` 여섯 플래그가 CTS의 등급이고, 접근성은 메타데이터의 하위 3비트에 인코딩된다.
- **접근 검사는 컴파일 타임과 JIT 타임 두 번 일어난다.** 어셈블리가 따로 버전업되면서 접근성이 좁아지면 런타임에 `MethodAccessException` / `FieldAccessException` / `TypeAccessException`이 난다. 그래서 `public`을 좁히는 것은 바이너리 호환성을 깨는 변경이다.
- **`InternalsVisibleTo`는 어셈블리 경계에 단방향·비전이·전부 아니면 전무의 구멍을 낸다.** 강력한 이름이 붙었다면 토큰이 아니라 **전체 공개 키**를 써야 하고, 문자열에 버전·컬처를 넣으면 안 된다. 단위 테스트가 정당한 주 용례다.
- **컨테이너가 멤버를 자르는 것은 조용하고, 시그니처가 접근성을 새게 하는 것은 오류다.** 전자는 모순이 없어서(밖에서 컨테이너가 안 보이니 도달 불가) 허용되고, 후자는 호출자가 그 멤버를 표현할 수 없어서 CS0050 계열 오류가 된다.
- **중첩 타입의 존재 이유는 강한 접근 제어와 바깥 `private` 멤버 접근이다.** 네임스페이스 정리가 목적이라면 중첩 네임스페이스를 써라. `public` 중첩 타입은 열거자·빌더·전용 열거형 같은 확립된 패턴에서만 정당하다.
- **C#의 중첩 타입은 바깥 인스턴스를 자동으로 참조하지 않는다.** Java의 내부 클래스와 다르다. 그래서 뜻하지 않은 메모리 누수를 만들지 않는 대신, 바깥 인스턴스가 필요하면 명시적으로 넘겨야 한다.
- **좁게 시작하고 필요할 때 넓혀라.** 넓히기는 안전하고 좁히기는 파괴적이다. 필드는 예외 없이 `private`, 클래스는 기본적으로 `sealed`, 타입은 기본적으로 `internal`이 출발점이다.

## 연습 문제

1. **접근 사분면을 직접 확인하라.** 클래스 라이브러리 프로젝트 두 개(`Lib`, `Consumer`)와 콘솔 프로젝트를 만들고, `Lib`에 17.1절의 `Base` 클래스를 그대로 옮겨라. `Lib` 안과 `Consumer` 안에 각각 파생 클래스와 무관한 클래스를 만들어 여섯 필드에 접근을 시도하고, 어떤 조합에서 CS0122가 나는지 표로 정리하라. 결과가 본문의 표와 일치하는지 확인하라.

2. **IL에서 가시성 플래그를 확인하라.** `internal class Sample`에 여섯 가지 접근성의 필드를 하나씩 두고 빌드한 뒤 `ildasm`(또는 ILSpy의 IL 뷰)으로 열어라. 최상위 타입이 `.class private`으로 나오는지, 각 필드가 `private` / `famandassem` / `family` / `assembly` / `famorassem` / `public`으로 나오는지 눈으로 확인하라. 그다음 `public class Sample`로 바꿔 다시 빌드하고 무엇이 달라지는지 비교하라.

3. **런타임 접근 검사를 재현하라.** 클래스 라이브러리 `L`에 `public void Helper()`를 만들고, 그것을 호출하는 앱 `A`를 빌드해서 `A.dll`과 `L.dll`을 보관하라. 이제 `L`의 `Helper`를 `internal`로 바꿔 다시 빌드하고, **`A`는 재컴파일하지 않은 채** 새 `L.dll`로 덮어써서 실행하라. `MethodAccessException`이 나는 것을 확인하라. 이것이 접근성 축소가 바이너리 호환성을 깨는 방식이다.

4. **`InternalsVisibleTo`를 붙였다 떼 보라.** 라이브러리와 xUnit 테스트 프로젝트를 만들고, `internal sealed class Validator`를 테스트에서 인스턴스화해 보라. 처음에는 컴파일 오류가 날 것이다. `.csproj`에 `<InternalsVisibleTo Include="..." />`를 추가해서 통과시킨 뒤, 라이브러리 `.csproj`의 `<AssemblyName>`을 다른 값으로 바꿔라. 무슨 일이 일어나는지 관찰하고 왜 그런지 설명하라.

5. **접근성 제한을 계산하라.** 다음 각 선언에서 `x`의 **실효** 접근성을 손으로 계산한 뒤, 실제로 코드를 작성해 다른 어셈블리·같은 어셈블리·파생 타입에서 접근을 시도해 검증하라.
   - `internal class A { protected int x; }`
   - `public class A { protected class B { internal int x; } }`
   - `public class A { private class B { public class C { public int x; } } }`

6. **CS0050 계열을 전부 만들어 보라.** `internal class Secret {}`을 만들고 `public class Api` 안에서 그것을 반환 타입·매개변수 타입·필드 타입·프로퍼티 타입으로 각각 노출하라. 네 가지 오류 번호가 다르게 나오는지 확인하고, 각각을 세 가지 방법(타입 넓히기 / 멤버 좁히기 / 경계 타입 바꾸기)으로 고쳐 보라.

7. **구조체 열거자를 직접 만들어 벤치마크하라.** 17.5절의 `RingBuffer<T>`를 완성하고, `Enumerator`를 (a) 중첩 `struct`, (b) 중첩 `class`, (c) `IEnumerator<T>`를 반환하는 반복자 메서드 세 가지 버전으로 구현하라. BenchmarkDotNet으로 `foreach` 100만 회의 할당량(`[MemoryDiagnoser]`)과 시간을 비교하고, 중첩 구조체가 왜 할당 0인지 설명하라.

**다음 장** — 18장「인터페이스」에서는 이 장에서 "인터페이스 멤버는 암묵적으로 `public`"이라고만 말하고 넘어간 것을 끝까지 판다. 암시적 구현과 명시적 구현이 IL에서 무엇이 다른지, 명시적 구현 멤버가 왜 `private final virtual newslot`으로 방출되는지, 구조체가 인터페이스를 구현할 때 어디서 박싱이 일어나는지를 본다. 그리고 ※C# 8의 기본 구현 멤버가 인터페이스에 접근 제한자를 되돌려준 결과, 인터페이스가 추상 클래스와 얼마나 가까워졌는지를 설계 결정표로 정리한다.
