# 22장. 연산자 오버로딩과 정적 다형성

> **이 장의 위치** — 13장부터 21장까지 타입을 만드는 도구를 모두 꺼내 놓았다. 클래스, 구조체, 인터페이스, 레코드, 열거형, 널 가능성까지. 그런데 아직 남은 것이 하나 있다. **직접 만든 타입이 `+`나 `==` 같은 기호에 반응하게 만드는 법**이다. 14장에서 본 다형성은 인스턴스 위에서 일어났다 — 객체가 있어야 가상 메서드를 부를 수 있었다. 이 장은 그 반대편을 다룬다. 연산자는 **정적 메서드**이므로 인스턴스 다형성의 사각지대에 있었고, 그래서 C# 11 이전에는 제네릭 코드 안에서 `a + b`를 쓸 수 없었다. C# 11의 정적 추상 인터페이스 멤버가 그 벽을 허물었고, .NET 7의 제네릭 수학이 그 위에 세워졌다. 연산자 함수 하나에서 시작해 정적 다형성까지 한 줄로 이어지는 것이 이 장이다.
>
> **선수 지식** — 13장(클래스와 캡슐화), 14장(상속과 다형성), 15장(`object` 타입과 박싱 — 특히 15.3절), 16장(구조체와 값 타입), 18장(인터페이스 — 특히 18.8절), 21장(널 안정성 — 특히 21.4절)
>
> **이 장에서 다루지 않는 것** — 동등성의 계약 자체(`Equals` 재정의 5계명, `GetHashCode`의 분포 요건, `IEqualityComparer<T>`)는 25장이다. 이 장은 **연산자를 정의하는 쪽**만 보고, 계약의 세부는 25장으로 넘긴다. 공개 API에서 변환 연산자를 피해야 하는 설계 근거는 78.6절이다. 정적 추상 인터페이스 멤버를 **리플렉션으로** 호출하는 방법은 57.9절이다. 제네릭 문법 자체(타입 매개변수, 제약, 타입 추론)는 23장에서 정면으로 다룬다 — 이 장은 그중 `where T : IFoo<T>` 형태만 미리 빌려 쓴다. 널 가능 값 타입에 대한 연산자 리프팅은 21.4절에서 끝냈다.

## 22.1 연산자 함수의 문법과 규칙

### 왜 이 기능이 있는가

C#은 내장 타입에 대해 이미 연산자를 다르게 해석한다.

```csharp
int a = 100, b = 240;
int c = a + b;                      // 340 — 산술 덧셈

string s1 = "Hello", s2 = " world!";
string s3 = s1 + s2;                // "Hello world!" — 문자열 연결
```

같은 `+` 기호가 피연산자 타입에 따라 완전히 다른 코드로 컴파일된다. 숫자면 덧셈 IL 명령이 나오고, 문자열이면 `String.Concat` 호출이 나온다. **연산자 오버로딩은 이 선택지를 사용자 타입까지 확장하는 기능이다.**

목적은 하나뿐이다. **원시 데이터 타입에 가까운 타입을 자연스럽게 읽히게 만드는 것.** 벡터, 행렬, 복소수, 화폐 금액, 좌표, 음정, 집합, 물리 단위 — 수학 교과서에 기호로 등장하는 개념이라면 좋은 후보다. 그 밖에는 대체로 나쁜 후보다(이 절 마지막에서 다시 다룬다).

### 문법 — 연산자 함수

연산자를 오버로딩하려면 **연산자 함수(operator function)** 를 선언한다. 규칙은 다섯 개다.

| # | 규칙 | 어기면 |
|---|---|---|
| 1 | 함수 이름은 `operator` 키워드 + 연산자 기호 | 문법 오류 |
| 2 | `public`이고 `static`이어야 한다 | CS0558 |
| 3 | 매개변수가 피연산자를 나타낸다 (단항 1개, 이항 2개) | CS0562 / CS0563 |
| 4 | 반환 타입이 식의 결과 타입이다 | — |
| 5 | **피연산자 중 최소 하나는 연산자 함수를 선언한 타입이어야 한다** | CS0563 |

5번이 이 기능의 성격을 결정한다. `int`와 `string`을 받아 `+`를 재정의하는 연산자를 아무 데서나 선언할 수 없다. 반드시 자기 타입이 끼어 있어야 한다.

> **📌 5번 규칙은 컴파일러의 검색 시간 때문에 있다**
>
> CLR 명세는 연산자 오버로드 메서드가 `public static`이어야 한다는 것만 요구한다. "피연산자 중 하나가 선언 타입이어야 한다"는 제약은 **C#(과 다른 여러 언어)이 추가로 건 것**이며, 이유는 순전히 실용적이다. `a + b`를 만났을 때 컴파일러는 후보 연산자를 어딘가에서 찾아야 하는데, 이 제약이 있으면 **`a`의 타입과 `b`의 타입, 딱 두 곳만 뒤지면 된다.** 이 제약이 없으면 참조된 모든 어셈블리의 모든 타입을 뒤져야 한다. C++의 전역 연산자 오버로딩이 정확히 그런 세계이고, 그래서 오버로드 해석이 훨씬 복잡하다.

가장 단순한 예제부터 보자. 음정을 표현하는 구조체다.

```csharp
public struct Note
{
    int value;                                        // A로부터 몇 반음 떨어져 있는가

    public Note(int semitonesFromA) { value = semitonesFromA; }

    public static Note operator + (Note x, int semitones)
    {
        return new Note(x.value + semitones);
    }
}
```

이제 `Note`에 `int`를 더할 수 있다.

```csharp
Note B = new Note(2);
Note CSharp = B + 2;
```

메서드나 프로퍼티와 마찬가지로, 식 하나로 끝나는 연산자 함수는 식 본문(expression-bodied) 문법으로 줄여 쓸 수 있다.

```csharp
public static Note operator + (Note x, int semitones)
    => new Note(x.value + semitones);
```

### 이항 연산자 — 두 피연산자가 같은 타입일 필요는 없다

가장 흔한 형태는 두 피연산자가 모두 선언 타입인 경우다.

```csharp
public class Point
{
    public int X { get; set; }
    public int Y { get; set; }

    public Point(int xPos, int yPos) { X = xPos; Y = yPos; }

    public override string ToString() => $"[{X}, {Y}]";

    public static Point operator + (Point p1, Point p2)
        => new Point(p1.X + p2.X, p1.Y + p2.Y);

    public static Point operator - (Point p1, Point p2)
        => new Point(p1.X - p2.X, p1.Y - p2.Y);
}
```

`p1 + p2`는 개념적으로 `Point.operator+(p1, p2)` 호출로 바뀐다.

```csharp
Point ptOne = new Point(100, 100);
Point ptTwo = new Point(40, 40);

Console.WriteLine(ptOne + ptTwo);      // [140, 140]
Console.WriteLine(ptOne - ptTwo);      // [60, 60]
```

피연산자 타입이 달라도 된다. 5번 규칙만 지키면 된다.

```csharp
public class Point
{
    // ...
    public static Point operator + (Point p1, int change)
        => new Point(p1.X + change, p1.Y + change);

    public static Point operator + (int change, Point p1)
        => new Point(p1.X + change, p1.Y + change);
}
```

> **⚠️ 교환법칙은 공짜가 아니다**
>
> `Point + int`를 정의했다고 `int + Point`가 따라오지 않는다. **두 방향을 각각 선언해야 한다.** 컴파일러는 피연산자 순서를 바꿔 보지 않는다.
>
> ```csharp
> Point biggerPoint = ptOne + 10;        // 첫 번째 오버로드
> Point other       = 10 + biggerPoint;  // 두 번째 오버로드가 없으면 CS0019
> ```
>
> 수학적으로 교환법칙이 성립하는 연산이라면 두 개를 짝으로 선언하고, 한쪽이 다른 쪽을 호출하게 해서 구현을 한 곳에만 두는 것이 안전하다. 두 곳에 각각 구현을 쓰면 언젠가 두 결과가 어긋난다.

### 단항 연산자

단항 연산자는 매개변수가 하나이고, 그 타입이 선언 타입이어야 한다.

```csharp
public class Point
{
    // ...
    public static Point operator ++ (Point p1) => new Point(p1.X + 1, p1.Y + 1);
    public static Point operator -- (Point p1) => new Point(p1.X - 1, p1.Y - 1);
    public static Point operator -  (Point p1) => new Point(-p1.X, -p1.Y);
}
```

`++`와 `--`는 특별한 규칙이 하나 더 있다. **반환 타입이 매개변수 타입과 같거나 그로부터 파생된 타입이어야 한다.** 아니면 CS0448이다. 컴파일러가 결과를 다시 원래 변수에 대입해야 하기 때문이다.

```csharp
Point ptFive = new Point(1, 1);
Console.WriteLine(++ptFive);      // [2, 2]
Console.WriteLine(--ptFive);      // [1, 1]

Point ptSix = new Point(20, 20);
Console.WriteLine(ptSix++);       // [20, 20] — 증가 전 값이 식의 값
Console.WriteLine(ptSix--);       // [21, 21] — 감소 전 값이 식의 값
```

> **📌 C#은 전위·후위 증감을 따로 오버로딩할 수 없다**
>
> C++에서는 `operator++()`(전위)와 `operator++(int)`(후위)를 별도로 정의한다. C#에는 그런 구분이 없다. **`++` 하나만 정의하고, 전위/후위 의미론은 컴파일러가 알아서 붙인다.** `x++`는 "증가 전 값을 식의 값으로 쓰고 변수에는 증가된 값을 넣는다"로, `++x`는 "증가된 값을 변수에 넣고 그 값을 식의 값으로 쓴다"로 전개된다. C++의 자유도를 잃은 대신 **두 형태가 어긋날 수 없다**는 보장을 얻었다.

증감 연산자를 오버로딩할 때 가장 흔한 실수는 **피연산자를 직접 변경하고 그것을 반환하는 것**이다.

> **⚠️ 참조 타입의 `++`에서 인자를 변경하면 의미론이 깨진다**
>
> ```csharp
> // 절대 이렇게 쓰지 마라
> public static Point operator ++ (Point p)
> {
>     p.X++;          // 인자가 가리키는 객체를 직접 변경
>     p.Y++;
>     return p;       // 같은 참조를 반환
> }
> ```
>
> `Point`가 클래스일 때, 이 코드는 `q = p++`를 실행하면 `q`와 `p`가 **같은 객체**를 가리키게 만든다. "증가 전 값"을 담아야 할 `q`가 증가 후 값을 보게 된다. 게다가 그 `Point`를 참조하던 다른 모든 변수도 함께 바뀐다. **증감 연산자는 반드시 새 인스턴스를 만들어 반환해야 한다.** 구조체라면 매개변수가 복사본이므로 이 사고는 나지 않지만, 그렇더라도 새 값을 만들어 반환하는 편이 읽기 쉽다.

### 복합 대입은 공짜로 따라온다

C++ 출신이라면 `+=`, `-=` 같은 복합 대입 연산자를 따로 오버로딩하고 싶을 것이다. C#에는 그 문법이 없다. **대신 대응하는 이항 연산자를 오버로딩하면 복합 대입이 자동으로 생긴다.**

```csharp
Note CSharp = new Note(4);
CSharp += 2;                    // + 를 오버로딩했으므로 동작한다

Point ptThree = new Point(90, 5);
ptThree += ptTwo;               // [130, 45]

Point ptFour = new Point(0, 500);
ptFour -= ptThree;              // [-130, 455]
```

컴파일러는 `x op= y`를 `x = x op y`로 전개한다(필요한 변환을 붙여서). 정확히 말하면 다음 두 조건이 만족될 때다.

- 선택된 연산자의 반환 타입이 `x`의 타입으로 **암시적으로** 변환 가능하거나,
- 선택된 연산자가 `x`의 타입 자체를 반환한다.

대응 관계는 기계적이다. `+` → `+=`, `-` → `-=`, `*` → `*=`, `/` → `/=`, `%` → `%=`, `&` → `&=`, `|` → `|=`, `^` → `^=`, `<<` → `<<=`, `>>` → `>>=`.

> **⚠️ `x += y`에서 `x`는 한 번만 평가된다**
>
> `x = x + y`로 전개된다고 했지만, `x`가 부수 효과가 있는 식일 때 **`x`는 두 번이 아니라 한 번만 평가된다.**
>
> ```csharp
> Point[] arr = { new Point(1, 1) };
> int i = 0;
> arr[i++] += new Point(1, 1);   // i는 1이 된다. 2가 아니다.
> ```
>
> 컴파일러는 인덱스를 임시 변수에 담아 두고 재사용한다. 프로퍼티도 마찬가지여서 `obj.Prop += v`는 getter 한 번, setter 한 번을 호출한다. 이 규칙 자체는 내장 타입에서도 같지만, 오버로딩된 연산자에서는 `+` 호출 비용이 눈에 띄게 커질 수 있으므로 기억해 둘 값어치가 있다.

### 오버로드 가능한 연산자 전체 목록

```csharp
// 단항
+   -   !   ~   ++   --   true   false

// 이항
+   -   *   /   %   &   |   ^   <<   >>   >>>

// 비교·동등
==   !=   <   >   <=   >=

// 변환
implicit   explicit
```

이 목록에서 `>>>`와 `operator checked ...`는 ※C# 11에서 추가된 것이고, `true`/`false`와 `==`/`!=`, `<`/`>`, `<=`/`>=`는 반드시 짝으로 정의해야 한다(22.2절). 변환 연산자는 22.4절에서 따로 다룬다.

**간접적으로 오버로딩되는 것**도 있다.

- 복합 대입(`+=`, `/=` 등) — 대응하는 이항 연산자를 정의하면 자동으로 생긴다.
- 조건 논리 연산자 `&&`, `||` — 비트 연산자 `&`, `|`와 `true`/`false`를 정의하면 동작한다(22.5절).

### 오버로드 **불가능한** 연산자

| 연산자 | 왜 안 되는가 | 대안 |
|---|---|---|
| `=` | 대입 의미론은 언어가 고정한다. 값 타입은 복사, 참조 타입은 참조 복사 | 복사 생성자, `with` 식(19.4절) |
| `&&`, `\|\|` | 단축 평가 규칙을 사용자 코드가 바꿀 수 없다 | `&`/`\|` + `true`/`false` (22.5절) |
| `?:` | 조건 연산자 자체는 재정의 불가 | `true` 연산자로 조건부만 참여 |
| `??`, `??=` | 널 병합은 널 판정 규칙에 묶여 있다 | — |
| `is`, `as` | 타입 검사·참조 변환은 CLR의 일이다 | 명시적 변환 연산자 + `try` 패턴 |
| `[]` | | 인덱서(13.9절) |
| `()` | 호출·캐스트 | 변환 연산자 / 메서드 |
| `.`, `?.` | 멤버 접근 | — |
| `new`, `typeof`, `sizeof`, `nameof` | 컴파일러/런타임 내장 | — |
| `=>`, `->` | 람다, 포인터 역참조 | — |
| `+=` 등 복합 대입 | 직접 선언 불가 | 이항 연산자를 정의하면 자동 |

> **⚠️ `??`가 오버로드 불가라는 사실은 종종 사고로 이어진다**
>
> 어떤 타입이 "비어 있음"을 나타내는 자체 값(예: `Money.None`)을 갖더라도 `money ?? fallback`은 **`money`가 `null`인지만 본다.** `Money`가 구조체라면 아예 컴파일되지 않고, 클래스라면 `Money.None` 인스턴스는 `null`이 아니므로 `fallback`이 절대 선택되지 않는다. `??`는 타입의 "비어 있음" 개념을 존중하지 않는다. `null` 하나만 안다.
>
> 같은 이유로 `is null` / `is not null` 패턴은 **`==` 오버로드를 무시하고** 진짜 널 참조인지만 검사한다. 이 성질은 22.3절에서 무한 재귀를 피하는 도구로 쓰인다.

### 시프트 연산자와 `>>>` ※C# 11

C# 11은 시프트 연산자 오버로딩의 제약 두 가지를 손봤다.

첫째, **부호 없는 오른쪽 시프트 `>>>` 가 추가되었고 오버로딩 대상이 되었다.**

둘째, **두 번째 피연산자가 반드시 `int`여야 한다는 제약이 사라졌다.** C# 10까지는 `public static T operator <<(T left, int count)` 형태만 허용됐고, 아니면 CS0564였다. C# 11부터는 두 번째 피연산자를 원하는 타입으로 둘 수 있다. 제네릭 수학의 `IShiftOperators<TSelf, TOther, TResult>`가 이 완화 없이는 성립하지 않기 때문에 함께 들어온 변경이다. **첫 번째 피연산자가 선언 타입이어야 한다는 제약은 그대로다.**

### 검사 연산자 ※C# 11

C# 11부터 연산자 함수에 `checked` 버전을 함께 선언할 수 있다.

```csharp
public struct Note
{
    int value;
    public Note(int semitonesFromA) { value = semitonesFromA; }

    public static Note operator + (Note x, int semitones)
        => new Note(x.value + semitones);

    public static Note operator checked + (Note x, int semitones)
        => checked(new Note(x.value + semitones));
}
```

`checked` 버전은 `checked` 식이나 블록 안에서 호출된다.

```csharp
Note B = new Note(2);
Note other = checked(B + int.MaxValue);    // OverflowException
```

`checked` 버전을 선언하려면 **대응하는 검사되지 않는(unchecked) 버전이 반드시 있어야 한다.** 검사 버전만 단독으로 선언할 수 없다. 검사 연산자를 붙일 수 있는 대상은 `++`, `--`, 단항 `-`, 이항 `+`, `-`, `*`, `/`, 그리고 명시적 변환 연산자다.

| 컨텍스트 | 호출되는 것 |
|---|---|
| `checked(expr)` / `checked { ... }` 안 | `operator checked +` (있으면), 없으면 일반 `operator +` |
| `unchecked(expr)` / `unchecked { ... }` 안 | 항상 일반 `operator +` |
| 아무 표시 없음 | 프로젝트의 `<CheckForOverflowUnderflow>` 설정을 따른다 |

### 컴파일 결과와 런타임 동작

연산자 함수는 **평범한 정적 메서드로 컴파일된다.** 이름만 `op_Addition` 같은 규약 이름으로 바뀌고 `specialname` 플래그가 붙는다. 자세한 매핑은 22.6절에서 다룬다. 여기서는 결과만 확인해 두자.

```il
.method public hidebysig specialname static
        valuetype Note op_Addition(valuetype Note x, int32 semitones) cil managed
{
  .maxstack  8
  IL_0000:  ldarga.s   x
  IL_0002:  ldfld      int32 Note::value
  IL_0007:  ldarg.1
  IL_0008:  add
  IL_0009:  newobj     instance void Note::.ctor(int32)
  IL_000e:  ret
}
```

호출 지점은 `call` 명령 하나다. 정적 메서드이므로 `callvirt`가 아니다.

```il
// Note CSharp = B + 2;
IL_0000:  ldloc.0                                        // B
IL_0001:  ldc.i4.2
IL_0002:  call       valuetype Note Note::op_Addition(valuetype Note, int32)
IL_0007:  stloc.1                                        // CSharp
```

**성능 관점에서 알아야 할 것은 셋이다.**

첫째, **가상 디스패치가 없다.** 연산자는 정적으로 바인딩되므로 인터페이스 호출이나 가상 호출의 간접 비용이 없다. 컴파일 타임에 어느 메서드를 부를지 확정된다.

둘째, **JIT이 인라인할 가능성이 높다.** 위의 `op_Addition`처럼 짧은 본문이면 대개 인라인되어 호출 비용이 사라진다. 그러면 `B + 2`는 필드 로드와 `add` 명령 몇 개로 줄어든다.

셋째, **값 타입 연산자는 복사 비용을 부른다.** 매개변수가 값으로 전달되므로 큰 구조체를 피연산자로 쓰면 호출마다 구조체 전체가 복사된다. 16.2절에서 본 숨은 복사가 그대로 적용된다. 4×4 행렬 구조체(`double` 16개 = 128바이트)에 `+`를 정의하면 호출 한 번에 256바이트가 복사되고 결과로 128바이트가 더 만들어진다. BCL의 `System.Numerics.Matrix4x4`도 연산자와 함께 이름 있는 정적 메서드(`Matrix4x4.Add`, `Matrix4x4.Multiply`)를 제공하지만, 그 역시 값으로 받는다. 복사가 실제 병목이라면 `in` 매개변수를 받는 자체 메서드를 따로 두는 것이 대안이다(10.2절).

> **💡 연산자를 오버로딩할 때는 이름 있는 메서드를 함께 제공하라**
>
> Microsoft의 프레임워크 설계 지침은 연산자 오버로드마다 **대응하는 이름 있는 공개 정적 메서드**를 함께 두라고 권한다.
>
> ```csharp
> public static Complex operator + (Complex c1, Complex c2) { /* ... */ }
> public static Complex Add       (Complex c1, Complex c2) => c1 + c2;
> ```
>
> 이유는 둘이다. 첫째, **연산자 오버로딩을 지원하지 않는 언어**에서 이 타입을 쓸 수 있게 한다. 둘째, `Add`라는 이름은 IDE의 자동 완성에 뜨지만 `op_Addition`은 뜨지 않는다.
>
> 실제 사례는 `System.Decimal`이다. `Decimal`은 연산자 오버로드와 `Decimal.Add`, `Decimal.Subtract`, `Decimal.Multiply`, `Decimal.Divide`를 모두 갖는다. 다만 이 지침을 기계적으로 따를 필요는 없다. **공개 라이브러리를 만든다면 따르고, 애플리케이션 내부 타입이라면 굳이 두 벌을 유지할 이유가 없다.** 이름 있는 메서드가 연산자를 그대로 호출하기만 한다면 JIT이 인라인해 주므로 성능 손실도 없다.

### 언제 오버로딩하지 말아야 하는가

이 절에서 가장 중요한 부분이다.

**연산자를 오버로딩해도 되는지 판단하는 기준은 하나다. 그 기호의 의미가 코드를 처음 보는 사람에게 자명한가.**

```csharp
// 이건 무슨 뜻인가?
MiniVan newVan = myVan * yourVan;
```

미니밴 두 대를 곱하면 무엇이 나오는가? 아무도 모른다. 이런 코드는 팀 동료를 정의부로 보내 버린다. 연산자의 목적은 코드를 짧게 만드는 것이 아니라 **읽는 사람의 머릿속에 이미 있는 규칙을 재사용하는 것**이다. 규칙이 없는 곳에 기호를 붙이면 오히려 읽는 비용이 늘어난다.

| 좋은 후보 | 나쁜 후보 |
|---|---|
| 벡터, 행렬, 사원수 | 사람, 관리자, 부서 |
| 복소수, 유리수, 큰 정수 | 자동차, 웹 페이지 |
| 화폐 금액, 물리 단위(길이·질량·시간) | 데이터베이스 연결, 파일 핸들 |
| 좌표, 크기, 사각형 | 리포지토리, 서비스, 컨트롤러 |
| 날짜·시간·기간 | 요청, 응답, 세션 |
| 집합, 비트 플래그 | 로거, 캐시, 큐 |

경계선은 대체로 **"이 타입이 값인가, 아니면 무언가를 하는 물건인가"** 다. 값이면 후보가 되고, 행위자면 후보가 아니다.

> **⚠️ 의미가 두 개 이상 성립하면 이미 나쁜 후보다**
>
> `Set<T>`에 `+`를 정의한다면 합집합인가 원소 추가인가? `string[]`에 `-`를 정의한다면 차집합인가 뒤에서 자르기인가? **후보가 둘 이상 떠오르는 순간 그 연산자는 오버로딩하지 말아야 한다.** BCL이 `HashSet<T>`에 연산자를 주지 않고 `UnionWith`, `ExceptWith` 같은 이름 있는 메서드만 준 이유가 이것이다. 반대로 `System.Numerics.Vector3`는 `+`가 성분별 덧셈 말고 다른 뜻이 될 수 없어서 연산자를 준다.

> **💡 두 개의 실무 규칙**
>
> **첫째, 수학적 성질을 어기지 마라.** `+`를 정의했다면 결합법칙이 성립해야 하고, 두 피연산자를 바꿔도 되는 연산이라면 교환법칙이 성립해야 하며, `a + b`는 `a`와 `b`를 변경하지 않아야 한다. `a + b`가 `a`를 수정한다면 그건 `+`가 아니라 `AddTo`다.
>
> **둘째, 성능이 직관과 어긋나면 연산자를 쓰지 마라.** `matrixA * matrixB * matrixC`는 세 줄짜리 코드처럼 보이지만 임시 행렬을 두 개 만든다. 큰 행렬이라면 이것이 눈에 띄는 할당이 되고, 읽는 사람은 그 비용을 짐작하지 못한다. 비용이 큰 연산에 짧은 기호를 붙이면 사람들은 그것을 싸다고 착각한다. **기호의 길이는 비용의 신호로 읽힌다.**

## 22.2 쌍(pair) 제약 — 반드시 함께 정의해야 하는 연산자

### 규칙

C# 컴파일러는 **논리적으로 짝인 연산자를 함께 정의하도록 강제한다.** 짝은 네 개다.

| 짝 | 한쪽만 정의하면 | 오류 코드 |
|---|---|---|
| `==` / `!=` | 컴파일 오류 | CS0216 |
| `<` / `>` | 컴파일 오류 | CS0216 |
| `<=` / `>=` | 컴파일 오류 | CS0216 |
| `true` / `false` | 컴파일 오류 | CS0216 |

오류 메시지는 이런 형태다.

```text
error CS0216: The operator 'Point.operator ==(Point, Point)' requires a matching
operator '!=' to also be defined
```

주의할 점은 **`<`/`>`와 `<=`/`>=`가 별개의 짝**이라는 것이다. `<`와 `>`만 정의하고 `<=`, `>=`를 빼도 컴파일된다. 반대도 마찬가지다. 컴파일러는 두 짝을 서로 연결해 주지 않는다.

```csharp
public class Point : IComparable<Point>
{
    // ...
    public int CompareTo(Point other)
    {
        if (X > other.X && Y > other.Y) return 1;
        if (X < other.X && Y < other.Y) return -1;
        return 0;
    }

    public static bool operator <  (Point p1, Point p2) => p1.CompareTo(p2) <  0;
    public static bool operator >  (Point p1, Point p2) => p1.CompareTo(p2) >  0;
    public static bool operator <= (Point p1, Point p2) => p1.CompareTo(p2) <= 0;
    public static bool operator >= (Point p1, Point p2) => p1.CompareTo(p2) >= 0;
}
```

### 왜 강제하는가

이유는 **부정 가능성**이다.

`a == b`가 존재하는데 `a != b`가 없다면, 컴파일러는 `!(a == b)`로 대체할 수 있을까? 할 수 없다. `!=`가 `==`의 부정이라는 보장이 언어에 없기 때문이다. `double.NaN`이 그 반례다.

```csharp
double nan = double.NaN;
Console.WriteLine(nan == nan);      // False
Console.WriteLine(nan != nan);      // True
```

여기까지는 부정 관계가 성립한다. 그런데 세 값 논리를 구현한 타입이라면 `==`도 `!=`도 `false`일 수 있다. 컴파일러가 자동으로 부정을 만들어 주면 그런 타입을 쓸 수 없게 된다. **그래서 언어는 자동 생성 대신 강제 선언을 택했다.** 저자가 직접 두 함수를 쓰게 함으로써, 두 연산의 관계를 저자가 결정하게 한다.

> **⚠️ 컴파일러는 짝을 강제할 뿐 일관성은 검사하지 않는다**
>
> 다음 코드는 경고 없이 컴파일된다.
>
> ```csharp
> public static bool operator == (Point a, Point b) => a.X == b.X;
> public static bool operator != (Point a, Point b) => a.Y != b.Y;   // 완전히 다른 판정
> ```
>
> `==`가 `true`이면서 `!=`도 `true`인 `Point` 쌍을 만들 수 있다. 컴파일러는 **두 함수가 존재하는지**만 본다. 짝 제약은 실수로 한쪽을 빠뜨리는 것을 막을 뿐, 논리를 검증해 주지 않는다. 이 검증은 25장의 동등성 계약과 단위 테스트의 몫이다.

### 비교 연산자와 순서 관계

비교 연산자 네 개를 정의하면 **`IComparable<T>`를 함께 구현해야 한다.** 이것은 컴파일러가 강제하지 않지만 사실상 의무다. 정렬(`List<T>.Sort`, `Array.Sort`, `OrderBy`)과 정렬된 컬렉션(`SortedSet<T>`, `SortedDictionary<TKey, TValue>`)은 **연산자를 전혀 보지 않고 `IComparable<T>`만 본다.** 연산자만 정의하면 다음이 벌어진다.

```csharp
var list = new List<Point> { new Point(3, 3), new Point(1, 1) };
list.Sort();     // InvalidOperationException — Point가 IComparable을 구현하지 않았다
```

던져지는 예외는 `InvalidOperationException`이고, `InnerException`이 `Point`를 `IComparable`로 캐스트할 수 없다는 `InvalidCastException`이다.

| 소비자 | 무엇을 보는가 |
|---|---|
| `a < b` 식 | `operator <` |
| `List<T>.Sort()` | `Comparer<T>.Default` → `IComparable<T>` → `IComparable` |
| `Array.Sort` | 같음 |
| `SortedSet<T>`, `SortedDictionary<K,V>` | 같음 (또는 생성자에 준 `IComparer<T>`) |
| LINQ `OrderBy` | 같음 |
| `Enumerable.Max` / `Min` | 같음 |

**따라서 순서를 가진 타입을 만들 때의 올바른 순서는 이렇다.** `IComparable<T>.CompareTo`를 먼저 정확히 구현하고, 네 연산자는 전부 `CompareTo`를 호출하는 한 줄짜리로 쓴다. 그러면 연산자와 정렬이 어긋날 수 없다. 순서 비교의 계약(전순서 요건, `null` 처리, `IComparer<T>`로 외부에서 정의하기)은 25.6절과 25.7절에서 다룬다.

> **⚠️ 위의 `Point.CompareTo`는 사실 잘못된 구현이다**
>
> 예제로 쓴 `Point.CompareTo`를 다시 보라.
>
> ```csharp
> if (X > other.X && Y > other.Y) return 1;
> if (X < other.X && Y < other.Y) return -1;
> return 0;
> ```
>
> `(1, 5)`와 `(5, 1)`을 비교하면 `0`이 나온다. "같다"는 뜻이다. 그런데 두 점은 같지 않다. 즉 `a < b`도 `false`, `a > b`도 `false`, `a.Equals(b)`도 `false`인 상태가 만들어진다. 이것은 **전순서(total order)가 아니라 부분순서(partial order)** 이고, `Sort`가 요구하는 계약을 어긴다. 계약을 어긴 비교자를 `List<T>.Sort`에 넘기면 정렬 결과가 예측 불가능해지거나 `InvalidOperationException`(비교자가 일관성 없는 결과를 반환한다는 메시지)이 나올 수 있다.
>
> **2차원 좌표에는 자연스러운 전순서가 없다.** 억지로 만들려면 사전식 순서(X를 먼저 비교하고 같으면 Y)를 쓰면 되지만, 그것이 "점의 크기"를 뜻하지 않는다는 점을 문서에 밝혀야 한다. **자연스러운 순서가 없는 타입에는 비교 연산자를 정의하지 않는 것이 정답이다.** 정렬이 필요하면 `IComparer<T>`를 별도로 만들어 호출자가 고르게 한다.

### `true`/`false` 짝

`true`와 `false` 연산자도 짝이다. 둘 다 반환 타입이 `bool`이어야 하고(아니면 CS0215), 하나만 정의하면 CS0216이다. 왜 둘 다 필요한지는 22.5절에서 다룬다. 요약하면, **"참"과 "거짓"과 "둘 다 아님"을 구분하는 타입을 지원하기 위해서**다.

### 쌍 제약 요약

```text
     ┌─────────────────────────────────────────────────────┐
     │  1. 컴파일러가 강제 (없으면 CS0216)                  │
     │     ==  ←→  != │ <  ←→  > │ <= ←→ >= │ true ←→ false│
     ├─────────────────────────────────────────────────────┤
     │  2. 컴파일러가 경고 (CS0660 / CS0661)                │
     │     ==/!= 를 정의했으면 Equals / GetHashCode 재정의  │
     ├─────────────────────────────────────────────────────┤
     │  3. 아무도 강제하지 않음 (당신의 책임)               │
     │     <,>,<=,>= 를 정의했으면 IComparable<T> 구현      │
     │     네 연산자와 CompareTo 의 결과가 일치할 것        │
     │     ==/!= 와 Equals 의 결과가 일치할 것              │
     └─────────────────────────────────────────────────────┘
                   아래로 갈수록 어겨도 조용하다
```

강제 → 경고 → 무보증의 세 단계다. **아래로 갈수록 어겨도 조용하고, 그만큼 사고가 커진다.**

## 22.3 동등·비교 연산자 오버로딩과 `Equals`/`GetHashCode` 동기화

### 두 개의 동등성 창구

C#에는 "두 값이 같은가"를 묻는 창구가 두 개 있다. **이 둘은 완전히 다른 메커니즘이며, 서로 자동으로 동기화되지 않는다.**

| | `==` 연산자 | `Equals` 메서드 |
|---|---|---|
| 종류 | 정적 메서드 (`op_Equality`) | 가상 인스턴스 메서드 |
| 바인딩 시점 | **컴파일 타임** | **런타임** |
| 무엇으로 결정되는가 | 피연산자의 **컴파일 타임 타입** | 대상의 **런타임 타입** |
| IL 명령 | `call` | `callvirt` |
| 정의하지 않으면 (클래스) | 참조 동등성 | `Object.Equals` = 참조 동등성 |
| 정의하지 않으면 (구조체) | **컴파일 오류 CS0019** | `ValueType.Equals` = 필드 비교(느림, 16.7절) |
| `null` 처리 | 직접 짜야 함 | 호출 대상이 `null`이면 `NullReferenceException` |

**세 번째 행이 이 절 전체의 핵심이다.** `==`는 가상이 아니다. 컴파일러가 피연산자의 정적 타입을 보고 어느 `op_Equality`를 부를지 결정하고, 그 결정은 실행 중에 바뀌지 않는다.

```csharp
Point p1 = new Point(1, 1);
Point p2 = new Point(1, 1);

Console.WriteLine(p1 == p2);        // Point.op_Equality 호출 → True (오버로딩했다면)

object o1 = p1;
object o2 = p2;
Console.WriteLine(o1 == o2);        // object의 == → 참조 비교 → False
Console.WriteLine(o1.Equals(o2));   // Point.Equals 호출 (가상) → True
```

`o1`과 `o2`가 가리키는 객체는 그대로인데 **변수의 선언 타입만 바꿨더니 결과가 뒤집혔다.** 15.3절의 정적 타입 검사와 런타임 타입 검사의 구분이 그대로 드러난다 — `==`는 정적 타입 검사 쪽에 산다.

### 오버로딩하는 법

```csharp
public class Point
{
    public int X { get; }
    public int Y { get; }
    public Point(int x, int y) { X = x; Y = y; }

    public override bool Equals(object o)
        => o is Point p && p.X == X && p.Y == Y;

    public override int GetHashCode() => HashCode.Combine(X, Y);

    public static bool operator == (Point p1, Point p2)
        =>  ReferenceEquals(p1, null) ? ReferenceEquals(p2, null) : p1.Equals(p2);

    public static bool operator != (Point p1, Point p2) => !(p1 == p2);
}
```

**패턴은 늘 같다.** `Equals`에 판정 논리를 한 번만 쓰고, `==`는 `Equals`를 호출하고, `!=`는 `==`를 부정한다. 논리가 한 곳에만 있으므로 세 창구가 어긋날 수 없다.

### `Equals`/`GetHashCode`를 안 고치면 무엇이 벌어지는가

컴파일러가 먼저 알려 준다. **두 개의 경고**다.

```text
warning CS0660: 'Point' defines operator == or operator != but does not override
Object.Equals(object o)

warning CS0661: 'Point' defines operator == or operator != but does not override
Object.GetHashCode()
```

경고이지 오류가 아니다. 무시하고 빌드할 수 있다. 무시하면 다음이 벌어진다.

```csharp
// == 만 오버로딩하고 Equals/GetHashCode는 그대로 둔 Point
var a = new Point(1, 1);
var b = new Point(1, 1);

Console.WriteLine(a == b);                     // True  — 연산자를 탄다

var list = new List<Point> { a };
Console.WriteLine(list.Contains(b));           // False — EqualityComparer<T>.Default → Equals
Console.WriteLine(list.IndexOf(b));            // -1

var set = new HashSet<Point> { a };
Console.WriteLine(set.Add(b));                 // True — 중복인데 들어간다

var dict = new Dictionary<Point, string> { [a] = "origin" };
Console.WriteLine(dict.ContainsKey(b));        // False

Console.WriteLine(new[] { a, b }.Distinct().Count());                   // 2 — 같은 값인데 둘
Console.WriteLine(Enumerable.SequenceEqual(new[] { a }, new[] { b }));  // False
```

**`==`로 물어보면 같다고 하고, 컬렉션에 물어보면 다르다고 한다.** 같은 프로그램 안에서 두 가지 답이 공존한다. 이 상태로 배포된 코드는 "가끔 캐시가 안 맞는다", "중복이 들어간다", "삭제가 안 된다" 같은 증상으로 나타나고, 재현이 어려워 오래 산다.

> **⚠️ BCL의 어떤 코드도 `==` 연산자를 보지 않는다**
>
> `List<T>.Contains`, `Dictionary<K,V>`, `HashSet<T>`, `Distinct`, `GroupBy`, `Join`, `Except`, `SequenceEqual` — 전부 `EqualityComparer<T>.Default`를 쓴다. 그리고 `EqualityComparer<T>.Default`는 `T`가 `IEquatable<T>`를 구현하면 그 `Equals(T)`를, 아니면 `Object.Equals(object)`를 호출한다. **`op_Equality`를 찾는 코드 경로는 없다.** 제네릭 코드는 `T`에 어떤 연산자가 있는지 컴파일 타임에 알 수 없었기 때문이다(C# 11 이전에는 알 방법 자체가 없었다 — 22.7절).
>
> 그래서 규칙은 뒤집어 읽는 편이 낫다. **`==`를 오버로딩할지 말지와 무관하게, 값 의미론이 필요한 타입은 `Equals`와 `GetHashCode`를 재정의해야 한다.** `==`는 그 위에 얹는 편의 문법일 뿐이다.

여기에 하나가 더 붙는다.

> **⚠️ `GetHashCode`를 재정의하지 않은 채 `Equals`만 고치면 딕셔너리가 조용히 망가진다**
>
> `Equals`는 "같다"고 하는데 `GetHashCode`가 다른 값을 주면, 두 객체는 서로 다른 버킷으로 들어간다. `Dictionary<K,V>`는 먼저 해시로 버킷을 고르고 그 안에서만 `Equals`를 부르므로 **끝내 서로를 만나지 못한다.** 넣은 키로 조회가 실패한다. 반대 방향(해시는 같은데 `Equals`가 다르다)은 성능만 나빠지고 정확성은 유지된다. 해시 계약의 세부는 25.4절이다.

### 클래스에서 `==`를 오버로딩할 때의 무한 재귀

이것이 이 절에서 가장 자주 사고를 내는 지점이다.

```csharp
// 무한 재귀 — 절대 이렇게 쓰지 마라
public static bool operator == (Point p1, Point p2)
{
    if (p1 == null)                 // 여기서 다시 operator == 를 호출한다
        return p2 == null;          // 여기서도
    return p1.Equals(p2);
}
```

`p1 == null` 안에서 컴파일러는 다시 `Point.op_Equality(p1, null)`을 부른다. 스택이 넘칠 때까지 자기 자신을 호출한다. 결과는 `StackOverflowException`이며, **이 예외는 .NET Core 이후 `catch`로 잡을 수 없고 프로세스가 즉시 종료된다.**

탈출구는 세 가지다.

```csharp
// 1) ReferenceEquals — 연산자를 타지 않고 참조만 비교하는 정적 메서드
if (ReferenceEquals(p1, null)) return ReferenceEquals(p2, null);

// 2) is null 패턴 — 패턴 매칭은 사용자 정의 == 를 무시한다 (※C# 7)
if (p1 is null) return p2 is null;

// 3) object 로 캐스트 — 컴파일 타임 타입이 object 가 되므로 기본 == 를 탄다
if ((object)p1 == null) return (object)p2 == null;
```

**셋 다 정확하다.** 현대 코드에서는 `is null`이 가장 읽기 쉽다. 22.1절에서 본 대로 `is` 패턴은 사용자 정의 연산자와 변환을 무시하고 진짜 참조가 널인지만 본다 — 여기서는 그 성질이 정확히 필요한 것이다.

`!=`도 같은 함정이 있다. `!(p1 == p2)`로 쓰면 안전하다. `p1 != p2`라고 쓰면 자기 자신을 부른다.

> **📌 구조체에는 이 함정이 없다**
>
> 구조체는 `null`이 될 수 없으므로 널 검사 코드 자체가 필요 없다. 대신 다른 짐이 있다 — 구조체는 `==`를 오버로딩하기 **전까지는 `==`를 쓸 수 없다.**
>
> ```csharp
> struct Money { public decimal Amount; }
> Money m1 = default, m2 = default;
> bool same = m1 == m2;    // CS0019: '==' 연산자는 'Money'와 'Money' 형식의 피연산자에 적용할 수 없다
> ```
>
> 참조 타입은 `Object`로부터 참조 동등성 `==`를 물려받지만, 값 타입에는 물려받을 기본 `==`가 없다. `Equals`는 `ValueType.Equals`가 있어서 동작하지만 리플렉션 기반이라 느리다(16.7절). **구조체를 만들면 `Equals`, `GetHashCode`, `IEquatable<T>`, `==`, `!=`를 한 세트로 쓰는 것이 기본 자세다.**

### 상속과 `==`

`==`가 정적 바인딩이라는 사실은 상속 계층에서 특히 위험하다.

```csharp
public class Point
{
    public int X, Y;
    public static bool operator == (Point a, Point b) => /* X, Y 비교 */ ...;
    public static bool operator != (Point a, Point b) => !(a == b);
}

public class Point3D : Point
{
    public int Z;
    // == 를 오버로딩하지 않았다
}

Point3D a = new Point3D { X = 1, Y = 1, Z = 1 };
Point3D b = new Point3D { X = 1, Y = 1, Z = 99 };

Console.WriteLine(a == b);          // True — Point.op_Equality가 불린다. Z를 안 본다.
Console.WriteLine(a.Equals(b));     // Equals를 제대로 재정의했다면 False
```

파생 클래스가 `==`를 다시 정의하지 않으면 기반 클래스의 연산자가 그대로 선택된다. `virtual`이 아니므로 재정의라는 개념 자체가 없다. **`Equals`는 파생 타입의 것이 불리고 `==`는 기반 타입의 것이 불린다.** 두 창구의 답이 갈린다.

> **💡 상속 가능한 클래스에는 `==`를 오버로딩하지 마라**
>
> 실무 규칙은 명확하다. **`==` 오버로딩은 `sealed` 클래스, 구조체, 레코드에만 하라.** 상속 계층의 루트에 값 동등성 연산자를 얹는 순간, 모든 파생 타입 작성자가 연산자를 다시 정의할 의무를 진다. 그 의무는 문서 어디에도 강제되지 않고, 빠뜨려도 경고조차 나지 않는다.
>
> 상속 계층에서 값 동등성이 필요하면 **`Equals`(가상)만 재정의하고 `==`는 참조 동등성으로 남겨 두는 편**이 훨씬 안전하다. 그러면 두 창구의 역할이 명확히 갈린다 — `==`는 "같은 객체인가", `Equals`는 "같은 값인가".

### 레코드는 이 전부를 자동으로 한다

```csharp
public record Point(int X, int Y);
```

이 한 줄이 `Equals(object)`, `Equals(Point)`, `GetHashCode`, `op_Equality`, `op_Inequality`, `EqualityContract`를 전부 생성한다. 생성된 `==`는 `Equals`를 호출하고, `Equals`는 `EqualityContract`(런타임 타입)를 먼저 비교하므로 **상속 계층에서도 위의 `Point3D` 문제가 나지 않는다.** 생성 멤버의 세부는 19.3절, 레코드의 동등성 규칙은 19.7절이다.

**직접 만드는 값 타입에서 동등성이 필요하고 다른 요구가 없다면, 레코드를 쓰는 것이 가장 적은 실수로 가는 길이다.**

### 컴파일 결과와 성능

```il
.method public hidebysig specialname static
        bool op_Equality(class Point p1, class Point p2) cil managed
{
  // ...
}
```

`==` 호출은 `call bool Point::op_Equality(class Point, class Point)`가 된다. 인수가 널이어도 `call`이므로 널 검사가 일어나지 않는다 — 그래서 연산자 본문에서 직접 널을 처리해야 하는 것이다. 반면 `a.Equals(b)`는 `callvirt`이므로 **`a`가 널이면 호출 시점에 `NullReferenceException`이 난다.**

| 식 | IL | `a`가 널일 때 |
|---|---|---|
| `a == b` | `call op_Equality` | 연산자 본문이 처리 (제대로 짰다면 `b == null` 여부 반환) |
| `a.Equals(b)` | `callvirt Equals` | `NullReferenceException` |
| `object.Equals(a, b)` | `call` (정적 헬퍼) | `false` 또는 `b`도 널이면 `true` |
| `a is null` | `ldnull` + `ceq` | `true` |

**널 안전한 동등 비교가 필요하면 정적 `object.Equals(a, b)`나 `EqualityComparer<T>.Default.Equals(a, b)`를 쓴다.** 둘 다 내부에서 널을 먼저 걸러 낸다.

성능 측면에서는 `==` 쪽이 유리한 경우가 있다. `==`는 정적 호출이라 인라인되기 쉽고, `Equals(object)`는 값 타입일 때 인수를 **박싱**한다(15.2절). 그래서 구조체에는 `IEquatable<T>.Equals(T)`를 함께 구현해 박싱 없는 경로를 열어 두는 것이 표준이다. `EqualityComparer<T>.Default`가 그 경로를 찾아 쓴다.

```csharp
public readonly struct Money : IEquatable<Money>
{
    public readonly decimal Amount;
    public readonly string Currency;

    public Money(decimal amount, string currency) { Amount = amount; Currency = currency; }

    public bool Equals(Money other)                          // 박싱 없음
        => Amount == other.Amount && Currency == other.Currency;
    public override bool Equals(object obj)                  // 박싱 있음 (호환용)
        => obj is Money m && Equals(m);

    public override int GetHashCode() => HashCode.Combine(Amount, Currency);

    public static bool operator == (Money a, Money b) =>  a.Equals(b);
    public static bool operator != (Money a, Money b) => !a.Equals(b);
}
```

이 다섯 멤버가 값 타입 동등성의 최소 완전 집합이다. 각 멤버가 지켜야 할 계약과 그 이유는 25.2절과 25.3절에서 다룬다.

## 22.4 사용자 정의 암시적·명시적 변환 — 그리고 그 위험

### 두 종류의 변환

내장 숫자 타입에서 이미 익숙한 구분이다.

```csharp
int  a = 123;
long b = a;             // 암시적 — 정보 손실이 없다
int  c = (int) b;       // 명시적 — 손실 가능성이 있으므로 캐스트를 요구한다
```

C#은 이 구분을 사용자 타입까지 확장한다. `implicit`과 `explicit` 두 키워드가 그것이다.

```csharp
public static implicit operator double (Note x)
    => 440 * Math.Pow(2, (double) x.value / 12);          // 헤르츠로 변환

public static explicit operator Note (double x)
    => new Note((int)(0.5 + 12 * (Math.Log(x / 440) / Math.Log(2))));
```

```csharp
Note n = (Note) 554.37;      // 명시적 변환 — 캐스트 문법 필요
double x = n;                // 암시적 변환 — 캐스트 없이 대입
```

### 문법 규칙

변환 연산자도 연산자 함수다. 규칙은 다음과 같다.

| # | 규칙 | 어기면 |
|---|---|---|
| 1 | `public static`이어야 한다 | CS0558 |
| 2 | `implicit` 또는 `explicit` + `operator` + **대상 타입** | 문법 오류 |
| 3 | 매개변수가 **원본 타입**, 반환 타입이 **대상 타입** | — |
| 4 | 원본과 대상 중 하나는 선언 타입이어야 한다 | CS0556 |
| 5 | 이미 존재하는 변환을 다시 정의할 수 없다 | 아래 표 참조 |

읽는 순서가 헷갈리기 쉽다. **`operator` 다음에 오는 것이 "무엇으로" 변환하는지이고, 괄호 안이 "무엇으로부터"다.**

```csharp
public static explicit operator Square(Rectangle r)
//                              ↑대상        ↑원본
```

### 금지되는 변환

| 금지 대상 | 이유 | 오류 코드 |
|---|---|---|
| 항등 변환 (`T` → `T`) | 이미 존재한다 | CS0555 |
| `object`로 / `object`에서 | 모든 타입의 기반이므로 이미 변환이 있다 | CS0553 |
| 기반 클래스로 / 기반 클래스에서 | 업캐스트는 이미 암시적 | CS0553 |
| 파생 클래스로 / 파생 클래스에서 | 다운캐스트는 이미 명시적 | CS0554 |
| 인터페이스로 / 인터페이스에서 | 인터페이스 변환은 CLR이 처리 | CS0552 |
| 같은 원본·대상 쌍을 `implicit`과 `explicit` 둘 다 | 중복 | CS0557 |

마지막 항목은 실무에서 자주 부딪힌다. **같은 타입 쌍에 대해 암시적 변환과 명시적 변환을 동시에 선언할 수 없다.** 그런데 이것은 제약처럼 보이지만 사실 문제가 되지 않는다. **암시적 변환을 정의하면 명시적 캐스트 문법도 자동으로 허용되기 때문이다.**

```csharp
public struct Rectangle
{
    public int Width  { get; set; }
    public int Height { get; set; }

    public static implicit operator Rectangle(Square s)
        => new Rectangle { Height = s.Length, Width = s.Length * 2 };
}

Square s3 = new Square { Length = 7 };

Rectangle r1 = s3;                  // 암시적 — OK
Rectangle r2 = (Rectangle) s3;      // 명시적 캐스트 문법도 OK
```

반대는 성립하지 않는다. `explicit`만 정의하면 캐스트 없는 대입은 컴파일 오류다.

### `implicit`과 `explicit`을 고르는 기준

**기준은 하나다. 변환이 실패하거나 정보를 잃을 수 있는가.**

| | `implicit` | `explicit` |
|---|---|---|
| 언제 쓰는가 | 항상 성공하고 정보를 잃지 않을 때 | 실패할 수 있거나 정보를 잃을 때 |
| 예외를 던져도 되는가 | **안 된다** | 던져도 된다 |
| 호출자가 알아채는가 | 알아채지 못한다 | 캐스트가 코드에 보인다 |
| 예시 | `int` → `Rational`, `Square` → `Rectangle` | `Rational` → `int`, `double` → `Note` |

명시적 변환이 실패할 때 던질 예외는 상황에 따라 다르다. **값의 범위를 벗어난 경우에는 `OverflowException`, 그 인스턴스의 상태로는 변환이 불가능한 경우에는 `InvalidOperationException`이 관례다.** 인수 자체가 잘못됐다면 `ArgumentException` 계열도 쓰인다. 어느 쪽이든 문서에 명시해야 한다.

> **⚠️ 암시적 변환이 예외를 던지면 코드에 아무 단서가 남지 않는다**
>
> ```csharp
> // 나쁜 설계
> public static implicit operator int (BigNumber n)
> {
>     if (n.Value > int.MaxValue) throw new OverflowException();
>     return (int) n.Value;
> }
> ```
>
> 호출부는 이렇게 생겼다.
>
> ```csharp
> int x = bigNumber;      // 여기서 예외가 날 수 있다는 신호가 하나도 없다
> ```
>
> 캐스트도 없고, 메서드 호출도 없다. 코드 리뷰에서 이 줄을 예외 지점으로 지목할 사람은 없다. **암시적 변환은 "이 변환은 절대 실패하지 않는다"는 약속이다.** 약속을 지킬 수 없으면 `explicit`을 쓴다.

### 함정 1 — 변환은 컴파일 타임 타입만 본다

이것이 사용자 정의 변환의 가장 위험한 성질이다. **어떤 변환 연산자를 부를지는 컴파일 타임에 결정된다.** 15.3절의 정적 타입 검사와 런타임 타입 검사의 구분이 여기서도 그대로 적용된다.

```csharp
Note n = new Note(2);

double freq1 = n;                // Note → double 변환 연산자 호출. OK.

object o = n;                    // 박싱
double freq2 = (double) o;       // InvalidCastException!
```

두 번째 줄은 **컴파일된다.** `o`의 정적 타입이 `object`이므로 컴파일러는 "박싱된 `double`이 들어 있을 수도 있겠지"라고 판단하고 언박싱 코드를 낸다. 실행하면 CLR이 상자 안의 실제 타입이 `Note`임을 발견하고 `InvalidCastException`을 던진다. **사용자 정의 변환 연산자는 언박싱 경로에서 절대 호출되지 않는다.**

이 함정은 특히 다음 상황에서 조용히 나타난다.

```csharp
// 리플렉션
object result = method.Invoke(obj, args);
double d = (double) result;              // 실제로 Note가 반환됐다면 InvalidCastException

// 비제네릭 컬렉션 / dynamic 경계
ArrayList list = new ArrayList { n };
double d2 = (double) list[0];            // 같은 문제

// 제네릭 타입 매개변수
static double ToFrequency<T>(T value) => (double)(object) value;   // 같은 문제
```

마지막 형태 `(double)(object) value`는 제네릭 코드에서 타입을 우회하려고 자주 쓰는 관용구인데, **사용자 정의 변환을 완전히 건너뛴다.** 제네릭 코드에서 사용자 타입을 변환하려면 인터페이스 제약을 쓰거나(22.7절), `Convert.ChangeType`을 쓰거나, 함수를 인수로 받아야 한다.

> **⚠️ `is`와 `as`는 사용자 정의 변환을 무시한다**
>
> ```csharp
> Console.WriteLine(554.37 is Note);     // False — 변환 연산자가 있어도 False
> Note n = 554.37 as Note;               // 컴파일 오류 CS0077 (as는 참조/널가능 타입만)
> ```
>
> `is`와 `as`는 **참조 변환과 박싱/언박싱만** 본다. 사용자 정의 변환은 그들의 세계에 존재하지 않는다. `is`가 `false`를 반환한다고 해서 캐스트가 실패한다는 뜻이 아니고, 반대로 캐스트가 성공한다고 `is`가 `true`가 되지도 않는다. **`is`로 미리 확인하고 캐스트하는 관용구가 사용자 정의 변환 앞에서는 통하지 않는다.**

### 함정 2 — 사용자 정의 변환은 연쇄되지 않는다

```csharp
struct Meters
{
    public double Value;
    public static implicit operator double(Meters m) => m.Value;
}
struct Feet
{
    public double Value;
    public static implicit operator Meters(Feet f) => new Meters { Value = f.Value * 0.3048 };
}

Feet f = new Feet { Value = 10 };
Meters m = f;                  // OK — 사용자 정의 변환 한 번
double d = m;                  // OK — 역시 한 번
double e = f;                  // CS0029 — Feet → Meters → double 은 두 번이라 안 된다
```

C#의 변환 규칙은 **하나의 변환 시퀀스에 사용자 정의 변환을 최대 한 번만** 넣는다. 정확히는 "표준 변환 → 사용자 정의 변환 → 표준 변환" 형태다. 표준 변환(숫자 승격, 참조 변환, 박싱)은 앞뒤로 붙을 수 있지만, 사용자 정의 변환 두 개를 이어 붙일 수는 없다.

이 규칙 덕분에 **컴파일러가 변환 경로를 탐색하다가 폭발하지 않는다.** 대신 라이브러리 사용자는 중간 단계를 직접 써야 한다.

```csharp
double e2 = (Meters) f;     // 명시적으로 중간 단계를 거친다
```

### 함정 3 — 오버로드 해석이 흐려진다

암시적 변환은 **모든 오버로드 해석과 모든 대입 지점에 조용히 끼어든다.**

```csharp
public struct Money
{
    public decimal Amount;
    public static implicit operator decimal(Money m) => m.Amount;
    public static implicit operator Money(decimal d) => new Money { Amount = d };
}
void Log(string message) { }
void Log(decimal value)  { }

Money price = new Money { Amount = 100m };
Log(price);         // decimal 오버로드가 선택된다 — 의도한 것인가?

Money a = 10m, b = 3m;
var x = a / b;      // 무슨 타입인가? Money? decimal?
```

`Money`에 `/` 연산자가 없으면 컴파일러는 두 피연산자를 `decimal`로 암시적 변환한 뒤 `decimal` 나눗셈을 한다. 결과는 `decimal`이다. **화폐 타입을 만들어 놓고 나눗셈 결과만 원시 타입으로 새어 나간다.** 타입으로 세운 울타리에 구멍이 뚫린 것이다. 게다가 통화 정보가 있었다면 그것도 함께 사라진다.

> **⚠️ 암시적 변환은 타입 안전성의 우회로다**
>
> 어떤 타입을 만드는 이유는 대개 **다른 것과 섞이지 않게 하려는 것**이다. `UserId`와 `OrderId`를 둘 다 `int`로 두면 서로 바꿔 넣는 사고가 나므로 별도 타입으로 감싼다. 그런데 그 타입에 `int`로의 암시적 변환을 달면, `int`를 받는 모든 자리에 두 타입이 모두 들어갈 수 있게 된다. **울타리를 세우고 문을 열어 둔 셈이다.**
>
> ```csharp
> void Ship(int orderId) { }
>
> UserId u = new UserId(42);
> Ship(u);        // 암시적 변환이 있으면 컴파일된다 — 잡고 싶었던 바로 그 버그
> ```
>
> 공개 API에서 변환 연산자를 피해야 하는 설계 근거 전반은 78.6절에서 다룬다. 이 절의 결론만 옮기면 이렇다. **암시적 변환은 두 타입이 사실상 같은 것을 다른 표기로 나타낼 때만 쓴다.**

### 대안 — 생성자와 이름 있는 메서드

약하게 관련된 타입 사이에는 변환 연산자 대신 다음 두 가지를 쓴다.

1. **원본 타입을 매개변수로 받는 생성자**
2. **`ToXxx` 인스턴스 메서드와 `FromXxx` 정적 메서드**

```csharp
public sealed class Rational
{
    public Rational(int num)   { /* ... */ }     // int → Rational
    public Rational(float num) { /* ... */ }     // float → Rational
    public int   ToInt32()  { /* ... */ }        // Rational → int
    public float ToSingle() { /* ... */ }        // Rational → float
    public static Rational FromInt32(int num) => new Rational(num);
}
```

이 형태의 장점은 셋이다.

- **어떤 언어에서든 호출할 수 있다.** 연산자 오버로딩을 지원하지 않는 언어도 생성자와 메서드는 부른다.
- **호출부에 이름이 남는다.** `note.ToFrequency()`는 `(double) note`보다 무엇을 하는지 분명하다.
- **매개변수를 받을 수 있다.** 변환 연산자는 인수를 하나만 받지만, 메서드는 `ToString(format, culture)`처럼 옵션을 받을 수 있다.

> **💡 앞서 본 `Note` 예제도 사실 메서드가 나은 사례다**
>
> `Note`와 `double`(헤르츠)은 "같은 것의 다른 표기"가 아니다. `Note`는 12평균율의 반음 개수이고 `double`은 주파수다. 변환은 로그와 지수를 거치고, `double` → `Note`는 가장 가까운 반음으로 **반올림하면서 정보를 잃는다.**
>
> ```csharp
> public double ToFrequency() => 440 * Math.Pow(2, (double) value / 12);
> public static Note FromFrequency(double hz)
>     => new Note((int)(0.5 + 12 * (Math.Log(hz / 440) / Math.Log(2))));
> ```
>
> 이쪽이 호출부에서 훨씬 정직하다. 이 장에서 연산자 형태를 보여 준 것은 **문법을 설명하기 위해서**이지 그 설계를 권하기 위해서가 아니다.

### 널 가능 값 타입으로의 리프팅

원본과 대상이 모두 값 타입인 사용자 정의 변환은 **널 가능 버전으로 자동 리프팅된다.** 21.4절에서 본 연산자 리프팅과 같은 규칙이다.

```csharp
Note? maybeNote = null;
double? freq = maybeNote;        // null — 변환 연산자를 부르지 않는다
// 컴파일러의 전개: maybeNote.HasValue ? (double?)(double) maybeNote.Value : null

Note? real = new Note(2);
double? freq2 = real;            // 변환 연산자 호출
```

**널이면 변환 함수를 아예 호출하지 않으므로, 변환 함수 안에서 널을 걱정할 필요가 없다.**

### 검사 변환 연산자 ※C# 11

명시적 변환 연산자에도 `checked` 버전을 붙일 수 있다.

```csharp
public static explicit operator         int (BigNumber n) => (int) n.Value;
public static explicit operator checked int (BigNumber n) => checked((int) n.Value);
```

`checked` 컨텍스트 안의 캐스트는 검사 버전을 호출한다. 규칙은 22.1절의 산술 검사 연산자와 같다. **암시적 변환에는 `checked` 버전이 없다** — 암시적 변환은 애초에 실패하지 않아야 하므로 검사할 것도 없다.

### 컴파일 결과

변환 연산자는 IL에서 `op_Implicit` 또는 `op_Explicit`이라는 이름의 정적 메서드가 된다.

```il
.method public hidebysig specialname static
        float64 op_Implicit(valuetype Note x) cil managed

.method public hidebysig specialname static
        valuetype Note op_Explicit(float64 x) cil managed
```

**같은 타입에 여러 개의 `op_Explicit`이 있을 수 있고, 그들은 반환 타입만 다를 수 있다.**

```il
public static Rational op_Implicit(int32 num)
public static Rational op_Implicit(float32 num)
public static int32    op_Explicit(class Rational r)
public static float32  op_Explicit(class Rational r)
```

마지막 두 메서드는 **매개변수가 같고 반환 타입만 다르다.** C#은 반환 타입만 다른 오버로드를 허용하지 않지만, CLR은 허용한다. 컴파일러는 변환 연산자를 낼 때 이 CLR 기능을 내부적으로 쓴다. `Rational` 소스에는 `op_Explicit` 두 개가 있는데, C# 문법으로는 서로 다른 대상 타입(`int`, `float`)으로 선언되므로 충돌이 아니다.

> **📌 반환 타입만 다른 오버로드는 리플렉션에서 걸림돌이 된다**
>
> `typeof(Rational).GetMethod("op_Explicit")`은 `AmbiguousMatchException`을 던진다. 이름이 같은 메서드가 둘이기 때문이다. 특정 변환을 찾으려면 `GetMethods()`로 전부 가져와 `ReturnType`으로 걸러야 한다.
>
> ```csharp
> var conv = typeof(Rational).GetMethods(BindingFlags.Public | BindingFlags.Static)
>     .First(m => m.Name == "op_Explicit" && m.ReturnType == typeof(int));
> ```
>
> 리플렉션으로 변환을 찾는 코드(직렬화기, 매퍼, ORM)를 만든다면 이 처리가 필요하다.

호출 지점의 IL은 평범한 정적 호출이다.

```il
// double x = n;
IL_0000:  ldloc.0                                        // n
IL_0001:  call       float64 Note::op_Implicit(valuetype Note)
IL_0006:  stloc.1                                        // x
```

성능은 22.1절의 산술 연산자와 같다. 정적 호출이고, 본문이 짧으면 인라인된다. **다만 암시적 변환은 코드에 보이지 않으므로, 프로파일러에서 예상치 못한 메서드가 튀어나올 수 있다.** 뜨거운 루프 안에서 무거운 암시적 변환이 매 반복 실행되는 상황은 실제로 종종 나온다.

## 22.5 `true` / `false` 연산자 오버로딩

### 무엇을 위한 기능인가

`true`와 `false` 연산자는 C#에서 가장 쓸 일이 적은 오버로딩 대상이다. 그런데 이것이 존재하는 이유를 이해하면 언어 설계의 한 조각이 보인다.

용도는 하나다. **"불리언의 성격을 갖지만 `bool`로 변환할 수는 없는 타입"을 조건문에서 쓰게 하는 것.** 대표적인 예가 3값 논리 타입이다. 참, 거짓, 그리고 "모름"이 있는 타입은 `bool`로 변환할 수 없다 — "모름"을 어느 쪽으로 보낼지 정할 수 없기 때문이다.

BCL에 실제 사례가 있다. `System.Data.SqlTypes.SqlBoolean`이다.

```csharp
SqlBoolean a = SqlBoolean.Null;

if (a)
    Console.WriteLine("True");
else if (!a)
    Console.WriteLine("False");
else
    Console.WriteLine("Null");
```

출력은 `Null`이다. `if (a)`도 `false`고 `if (!a)`도 `false`인 상태가 성립한다. `bool`로는 표현할 수 없는 상태다.

### 구현

`SqlBoolean`의 관련 부분만 재구현하면 이렇다.

```csharp
public struct SqlBoolean
{
    public static bool operator true (SqlBoolean x) => x.m_value == True.m_value;
    public static bool operator false(SqlBoolean x) => x.m_value == False.m_value;

    public static SqlBoolean operator ! (SqlBoolean x)
        => x.m_value == Null.m_value  ? Null
         : x.m_value == False.m_value ? True
         : False;

    public static readonly SqlBoolean Null  = new SqlBoolean(0);
    public static readonly SqlBoolean False = new SqlBoolean(1);
    public static readonly SqlBoolean True  = new SqlBoolean(2);

    private SqlBoolean(byte value) { m_value = value; }
    private byte m_value;
}
```

핵심은 `operator true`와 `operator false`가 **서로 부정 관계가 아니라는 것**이다. `Null` 인스턴스에 대해 둘 다 `false`를 반환한다. 이 자유도가 3값 논리를 가능하게 한다.

| 값 | `operator true` | `operator false` | `if (x)` | `if (!x)` |
|---|---|---|---|---|
| `True` | `true` | `false` | 진입 | 진입 안 함 |
| `False` | `false` | `true` | 진입 안 함 | 진입 |
| `Null` | `false` | `false` | 진입 안 함 | 진입 안 함 (`!Null`은 `Null`) |

> **⚠️ `operator true`를 정의해도 `bool`로 대입할 수는 없다**
>
> ```csharp
> SqlBoolean a = SqlBoolean.True;
> bool b = a;                       // 컴파일 오류 — 암시적 변환이 없다
> if (a) { }                        // OK — operator true 를 탄다
> bool c = a ? true : false;        // OK — 조건 연산자의 조건부도 operator true 를 탄다
> ```
>
> `operator true`는 **"조건 위치에서 어떻게 판정할 것인가"만** 정의한다. 타입 변환이 아니다. 두 개념은 별개다.

### `operator true`가 쓰이는 자리

컴파일러가 `operator true`를 호출하는 위치는 정해져 있다.

| 위치 | 호출되는 것 |
|---|---|
| `if (x)` | `operator true` |
| `while (x)`, `do ... while (x)` | `operator true` |
| `for (; x; )` | `operator true` |
| `x ? a : b` | `operator true` |
| `x && y` | `operator false`(왼쪽) → 필요하면 `operator &` |
| `x \|\| y` | `operator true`(왼쪽) → 필요하면 `operator \|` |

마지막 두 줄이 이 절의 진짜 목적지다.

### `&&`와 `||`를 동작하게 만드는 법

22.1절에서 `&&`와 `||`는 오버로드할 수 없다고 했다. 그런데 사용자 타입에 대해 `&&`와 `||`가 동작하게 만들 수는 있다. 조건은 셋이다.

1. 타입 `T`가 `operator &`(또는 `operator |`)를 정의하고,
2. 그 연산자의 **두 매개변수와 반환 타입이 모두 `T`** 이고,
3. `T`가 `operator true`와 `operator false`를 정의한다.

조건이 갖춰지면 컴파일러는 `x && y`를 다음으로 전개한다.

```csharp
// x && y
T.false(x) ? x : T.&(x, y)

// x || y
T.true(x) ? x : T.|(x, y)
```

읽어 보면 논리가 명확하다. `x`가 확실히 거짓이면 `y`를 볼 필요 없이 `x`가 답이다. 아니면 `&`로 둘을 결합한다. **`y`는 필요할 때만 평가된다 — 단축 평가가 그대로 살아 있다.**

```text
   x && y  의 전개
   ┌──────────────────────────────────────────────┐
   │  x 평가                                       │
   │     │                                        │
   │     ↓                                        │
   │  operator false(x) 호출                       │
   │     │                                        │
   │     ├── true  → 결과는 x   (y를 평가하지 않음) │
   │     │                                        │
   │     └── false → y 평가                        │
   │                  │                           │
   │                  ↓                           │
   │              operator &(x, y) 호출 → 결과     │
   └──────────────────────────────────────────────┘
```

조건이 맞지 않으면 전용 오류가 나온다. `operator &`의 매개변수·반환 타입이 선언 타입과 다르면 CS0217, `operator true`/`false`가 없으면 CS0218, 그 둘의 반환 타입이 `bool`이 아니면 CS0215다. CS0218 메시지는 이렇다.

```text
error CS0218: In order for 'T.operator &(T, T)' to be applicable as a short circuit
operator, its declaring type 'T' must define operator true and operator false
```

> **📌 `bool?`의 3값 논리는 이 메커니즘을 쓰지 않는다**
>
> 21.5절에서 본 `bool?`의 `&`/`|` 3값 논리는 **컴파일러가 특별히 아는 규칙**이지 `Nullable<T>`에 정의된 연산자가 아니다. 그래서 `bool?`에는 `&&`와 `||`를 쓸 수 없다.
>
> ```csharp
> bool? a = null, b = true;
> var x = a | b;      // OK — True
> var y = a || b;     // 컴파일 오류 CS0019
> ```
>
> `Nullable<bool>`은 `operator true`/`false`를 정의하지 않는다. 정의했다면 `if (nullableBool)`이 컴파일되어 널 상태가 조용히 거짓으로 취급됐을 것이고, 그것은 언어 설계상 훨씬 나쁜 선택이었을 것이다. **명시적으로 `== true`를 쓰게 만드는 쪽을 택했다.**

### 컴파일 결과

`operator true`와 `operator false`는 IL에서 `op_True`, `op_False`라는 이름의 정적 메서드가 된다.

```il
.method public hidebysig specialname static
        bool op_True(valuetype SqlBoolean x) cil managed

.method public hidebysig specialname static
        bool op_False(valuetype SqlBoolean x) cil managed
```

`if (a)`는 `call bool SqlBoolean::op_True(valuetype SqlBoolean)` 뒤에 조건 분기가 붙는 형태로 컴파일된다. 즉 **조건문 하나마다 정적 메서드 호출이 하나 늘어난다.** 짧은 본문이면 인라인되므로 실제 비용은 거의 없다.

> **💡 애플리케이션 코드에서는 쓰지 마라**
>
> `true`/`false` 연산자는 **`if (x)`가 참도 거짓도 아닐 수 있게 만든다.** 코드를 읽는 사람이 그 가능성을 떠올리지 못하면 논리 버그가 조용히 자란다. `if`/`else`가 둘 다 실행되지 않는 코드는 대부분의 독자에게 상상 밖이다.
>
> 이 기능이 정당한 자리는 **데이터베이스의 3값 논리를 그대로 옮겨야 하는 타입** 정도다. 그 외에는 `IsTrue` 프로퍼티나 `Match(onTrue, onFalse, onUnknown)` 같은 명시적 API가 낫다. 프레임워크 설계 지침도 `op_True`/`op_False`에 대응하는 친화 멤버로 `IsTrue`/`IsFalse` 프로퍼티를 두라고 권한다. **친화 멤버가 있으면 대부분의 호출부는 그쪽을 쓰는 편이 낫다.**

## 22.6 `op_Addition` — 연산자의 IL 표현

### CLR은 연산자를 모른다

이 절의 출발점은 다음 문장이다. **CLR에는 "연산자"라는 개념이 없다.** `+`가 무엇을 뜻하는지, `^`가 XOR인지 거듭제곱인지는 전부 언어가 정한다. C#에서 `^`는 XOR이고 Visual Basic에서는 거듭제곱이다. C#의 부등호는 `!=`이고 Visual Basic은 `<>`다.

CLR이 정하는 것은 하나뿐이다. **연산자 오버로드를 다른 언어가 알아볼 수 있도록 어떤 형태로 메타데이터에 노출할 것인가.** 그래서 CLR 명세는 이렇게 규정한다.

- 연산자 오버로드 메서드는 `public`이고 `static`이어야 한다.
- 이름은 정해진 규약을 따른다(`op_Addition` 등).
- `specialname` 플래그를 붙인다.

**CLR 입장에서 연산자 오버로드는 그냥 이름이 특이한 정적 메서드다.**

### 이름 매핑 전체 표

**단항 연산자와 이항 연산자**

| C# 연산자 | IL 메서드 이름 | 권장 친화 메서드 이름 |
|---|---|---|
| `+` (단항) | `op_UnaryPlus` | `Plus` |
| `-` (단항) | `op_UnaryNegation` | `Negate` |
| `!` | `op_LogicalNot` | `Not` |
| `~` | `op_OnesComplement` | `OnesComplement` |
| `++` | `op_Increment` | `Increment` |
| `--` | `op_Decrement` | `Decrement` |
| `true` | `op_True` | `IsTrue { get; }` |
| `false` | `op_False` | `IsFalse { get; }` |
| `+` | `op_Addition` | `Add` |
| `-` | `op_Subtraction` | `Subtract` |
| `*` | `op_Multiply` | `Multiply` |
| `/` | `op_Division` | `Divide` |
| `%` | `op_Modulus` | `Mod` |
| `&` | `op_BitwiseAnd` | `BitwiseAnd` |
| `\|` | `op_BitwiseOr` | `BitwiseOr` |
| `^` | `op_ExclusiveOr` | `Xor` |
| `<<` | `op_LeftShift` | `LeftShift` |
| `>>` | `op_RightShift` | `RightShift` |
| `==` | `op_Equality` | `Equals` |
| `!=` | `op_Inequality` | `Equals` |
| `<` | `op_LessThan` | `Compare` |
| `>` | `op_GreaterThan` | `Compare` |
| `<=` | `op_LessThanOrEqual` | `Compare` |
| `>=` | `op_GreaterThanOrEqual` | `Compare` |

**변환과 C# 11 추가분**

| C# 선언 | IL 메서드 이름 |
|---|---|
| `implicit operator T` | `op_Implicit` |
| `explicit operator T` | `op_Explicit` |
| `>>>` ※C# 11 | `op_UnsignedRightShift` |
| `checked +` | `op_CheckedAddition` |
| `checked -` | `op_CheckedSubtraction` |
| `checked *` | `op_CheckedMultiply` |
| `checked /` | `op_CheckedDivision` |
| `checked -` (단항) | `op_CheckedUnaryNegation` |
| `checked ++` | `op_CheckedIncrement` |
| `checked --` | `op_CheckedDecrement` |
| `explicit operator checked T` | `op_CheckedExplicit` |

> **📌 CLR 명세에는 C#이 쓰지 않는 연산자 이름도 있다**
>
> ECMA-335 Partition I의 10.3.1(단항)과 10.3.2(이항)에는 위 표보다 많은 연산자 이름이 정의되어 있다. `op_MemberSelection`, `op_PointerToMemberSelection`, `op_LogicalAnd`, `op_LogicalOr`, `op_Assign` 같은 것들이다. C#은 이들을 쓰지 않으므로 실무에서 마주칠 일이 거의 없다. **다만 다른 언어로 만든 어셈블리를 리플렉션으로 훑을 때 낯선 `op_` 이름이 나올 수 있다는 것은 알아 둘 값어치가 있다.**

### `specialname` 플래그의 역할

메서드 정의에 붙는 `specialname` 플래그가 이 시스템의 접착제다. **컴파일러는 `+` 기호를 만나면 피연산자 타입에서 `specialname`이 붙은 `op_Addition`을 찾는다.** 이름만 같고 플래그가 없으면 찾지 못한다.

```il
.method public hidebysig specialname static
        class Complex op_Addition(class Complex c1, class Complex c2) cil managed
{
  // ...
}
```

이 설계의 결과는 다소 기묘하다.

> **⚠️ 이름만 `op_Addition`인 메서드는 `+`로 부를 수 없다**
>
> 연산자 오버로딩을 지원하지 않는 언어로 만든 타입이 `op_Addition`이라는 정적 메서드를 갖고 있다고 하자. C#에서 이 타입에 `+`를 쓰면 컴파일 오류가 난다. `specialname` 플래그가 없기 때문이다. **직접 이름으로 부르면 호출된다.**
>
> ```csharp
> var sum = SomeType.op_Addition(a, b);      // 이건 된다 (specialname이 없을 때)
> var sum2 = a + b;                          // CS0019
> ```
>
> 반대로 C#이 만든 진짜 연산자 오버로드는 **C# 소스에서 이름으로 직접 부를 수 없다.** `Complex.op_Addition(a, b)`라고 쓰면 CS0571(연산자나 접근자를 직접 호출할 수 없다)이 난다. `specialname` 메서드는 C#에서 기호로만 부를 수 있다. 이 비대칭 때문에 연산자 오버로딩을 지원하지 않는 언어와 섞어 쓸 때 **친화 메서드(`Add` 등)를 함께 제공하라는 지침**이 나왔다(22.1절).

### 실제 IL

`Point` 클래스의 `+` 연산자를 컴파일하면 다음이 나온다.

```il
.method public hidebysig specialname static
        class Point op_Addition(class Point p1, class Point p2) cil managed
{
  .maxstack  8
  IL_0000:  ldarg.0
  IL_0001:  callvirt   instance int32 Point::get_X()
  IL_0006:  ldarg.1
  IL_0007:  callvirt   instance int32 Point::get_X()
  IL_000c:  add
  IL_000d:  ldarg.0
  IL_000e:  callvirt   instance int32 Point::get_Y()
  IL_0013:  ldarg.1
  IL_0014:  callvirt   instance int32 Point::get_Y()
  IL_0019:  add
  IL_001a:  newobj     instance void Point::.ctor(int32, int32)
  IL_001f:  ret
}
```

호출부는 이렇다.

```il
// Point p3 = p1 + p2;
IL_0000:  ldloc.0                                        // p1
IL_0001:  ldloc.1                                        // p2
IL_0002:  call       class Point Point::op_Addition(class Point, class Point)
IL_0007:  stloc.2                                        // p3
```

**`call`이지 `callvirt`가 아니다.** 정적 메서드이므로 인스턴스도, 가상 디스패치도 없다. 그래서 22.3절에서 본 대로 `p1`이 `null`이어도 호출 자체는 문제없이 일어나고, 널 처리는 연산자 본문의 몫이 된다.

복합 대입도 확인해 보자.

```il
// p1 += p2;
IL_0000:  ldloc.0                                        // p1
IL_0001:  ldloc.1                                        // p2
IL_0002:  call       class Point Point::op_Addition(class Point, class Point)
IL_0007:  stloc.0                                        // p1 = 결과
```

**복합 대입 전용 IL이 없다.** `+` 호출 다음에 대입이 붙을 뿐이다. 22.1절에서 "복합 대입은 이항 연산자를 정의하면 공짜로 따라온다"고 한 것의 IL 수준 근거가 이것이다.

### 원시 타입에는 왜 연산자 메서드가 없었나

`System.Int32`, `System.Int64`, `System.Double` 같은 코어 숫자 타입의 메타데이터를 열어 보면 **역사적으로 `op_Addition` 같은 메서드가 하나도 없었다.** 이유는 성능이다. 컴파일러는 이 타입들에 대한 연산을 특별히 알고 있고, 메서드 호출 대신 **IL 산술 명령을 직접 낸다.**

```il
// int c = a + b;
IL_0000:  ldloc.0
IL_0001:  ldloc.1
IL_0002:  add                    // 메서드 호출이 아니라 명령 하나
IL_0003:  stloc.2
```

메서드로 만들었다면 호출 비용이 붙었을 것이고, 그 메서드 안에서도 결국 `add` 명령을 실행해야 했을 것이다. 그래서 코어 타입은 연산자 메서드를 두지 않았다.

**이 사실에는 대가가 있었다.** 어떤 언어가 `Int32`를 자기 언어의 원시 타입으로 취급하지 않는다면, 그 언어에서는 `Int32` 인스턴스에 어떤 연산도 할 수 없었다. 호출할 메서드가 없기 때문이다.

> **📌 .NET 7부터는 원시 타입에도 `op_` 메서드가 생겼다 ※.NET 7**
>
> 제네릭 수학(22.8절)이 이 상황을 바꿨다. `System.Int32`가 `IAdditionOperators<int, int, int>`를 구현하려면 **인터페이스의 정적 추상 `op_Addition`을 실제로 구현한 메서드가 있어야 한다.** 그래서 .NET 7부터 `Int32`, `Double`, `Decimal` 등은 `op_Addition`, `op_Equality` 같은 연산자 메서드를 실제로 갖는다.
>
> 그렇다고 성능이 나빠지지는 않았다. **C# 컴파일러는 `int a + int b`에 대해 여전히 `add` 명령을 직접 낸다.** 연산자 메서드는 제네릭 코드가 인터페이스를 통해 도달할 때만 쓰인다. 그리고 그 경로에서도 JIT이 값 타입 특수화 후 인라인해 버리면 결국 `add` 명령이 남는다(22.8절).

### 리플렉션으로 연산자 찾기

연산자는 정적 메서드이므로 리플렉션으로 조회할 수 있다.

```csharp
using System.Reflection;

MethodInfo add = typeof(Point).GetMethod(
    "op_Addition", BindingFlags.Public | BindingFlags.Static);

Point result = (Point) add.Invoke(null, new object[] { p1, p2 });

// 진짜 연산자인지는 IsSpecialName으로 가린다
foreach (var m in typeof(decimal).GetMethods(BindingFlags.Public | BindingFlags.Static))
    if (m.IsSpecialName && m.Name.StartsWith("op_"))
        Console.WriteLine($"{m.Name}: {m.ReturnType.Name}");
```

이 패턴은 직렬화기, 객체 매퍼, 식 트리를 만드는 코드에서 실제로 쓰인다. 22.4절에서 본 대로 **`op_Explicit`은 이름이 겹칠 수 있으므로 `GetMethod`가 `AmbiguousMatchException`을 던질 수 있다.** `GetMethods`로 전부 받아 반환 타입으로 걸러야 한다. 리플렉션 API의 전반은 57장에서 다룬다.

### 성능 정리

| 상황 | 실제 비용 |
|---|---|
| 코어 숫자 타입의 `+` | IL 명령 하나. 호출 없음 |
| 짧은 사용자 연산자 | 정적 호출 → JIT이 대개 인라인 → 명령 몇 개 |
| 큰 구조체 피연산자 | 인수 복사 비용 (16.2절) + 결과 생성 비용 |
| 참조 타입 연산자 | 결과 객체 힙 할당 (`a + b + c`는 임시 객체 두 개) |
| 리플렉션 `Invoke` | 수백 나노초 단위. 인수 박싱까지 붙는다 |
| 제네릭 수학 경로 (값 타입) | 특수화 + 인라인 후 코어 타입과 동일 |

**가장 흔한 함정은 세 번째와 네 번째다.** 연산자는 기호 하나로 보이지만 실제로는 메서드 호출과 객체 생성을 숨긴다. `for` 루프 안에서 `sum = sum + vector[i]`를 100만 번 돌리면 참조 타입 벡터일 때 100만 개의 임시 객체가 만들어진다. 값 타입이면 할당은 없지만 복사가 남는다. **연산자를 정의할 타입이라면 값 타입으로, 그것도 작게 만드는 것이 대개 옳다.**

## 22.7 다형적 연산자와 정적 추상 멤버 ※C# 11

### 무엇이 막혀 있었나

지금까지 본 연산자는 전부 **정적 메서드**였다. 정적 메서드는 인스턴스가 없으므로 가상 디스패치의 대상이 아니고, 따라서 **인터페이스로 계약할 수 없었다.** C# 10까지 인터페이스는 인스턴스 멤버만 추상으로 선언할 수 있었기 때문이다.

이 제약이 만든 구멍은 하나의 문장으로 요약된다. **제네릭 코드 안에서는 연산자를 쓸 수 없었다.**

```csharp
// C# 10 이하에서는 컴파일되지 않는다
static T Sum<T>(T[] values)
{
    T total = default;
    foreach (T v in values)
        total += v;             // CS0019: '+=' 연산자는 'T'와 'T' 형식의 피연산자에 적용할 수 없다
    return total;
}
```

`where T : ISomething` 제약을 아무리 걸어도 소용없었다. 인터페이스는 `T.operator +`를 약속할 방법이 없었다. `where T : struct`도, `where T : IComparable<T>`도 도움이 되지 않았다.

그래서 네 가지 회피책이 쓰였고, 넷 다 대가가 컸다.

| 회피책 | 방법 | 대가 |
|---|---|---|
| 타입별 오버로드 | `Sum(int[])`, `Sum(double[])`, `Sum(decimal[])`, ... | 코드 중복. 새 타입마다 추가. `BigInteger` 같은 사용자 타입은 지원 불가 |
| 델리게이트 주입 | `Sum<T>(T[] v, Func<T,T,T> add)` | 호출자마다 람다를 넘겨야 함. 델리게이트 호출은 인라인이 어렵고 값 타입 인수 전달 비용이 붙는다 |
| `dynamic` | `dynamic total = ...; total += v;` | 호출마다 DLR 바인딩. 컴파일 타임 검사 소실. 성능이 수십 배 나쁘다(59장) |
| 리플렉션 / 식 트리 | `op_Addition`을 찾아 델리게이트로 컴파일 | 초기 비용이 크고 트리밍·AOT에서 깨진다(57.14절) |

BCL 자체도 이 벽에 막혀 있었다. `Enumerable.Sum`이 `int`, `long`, `float`, `double`, `decimal`과 그 널 가능 버전까지 **스무 개가 넘는 오버로드**로 되어 있는 이유가 이것이다.

### C# 11이 푼 것

C# 11의 **정적 추상 인터페이스 멤버(static abstract interface member)** 가 이 벽을 정확히 겨냥해서 나왔다. 18.8절에서 문법을 봤다. 여기서는 그것이 연산자와 만나는 지점을 본다.

먼저 연산자가 아닌 단순한 예제로 개념을 잡자. **어떤 타입의 임의 인스턴스를 만드는 정적 메서드**를 인터페이스로 계약한다.

```csharp
interface ICreateRandom<T>
{
    static abstract T CreateRandom();      // T의 임의 인스턴스를 만든다
}
```

레코드가 이것을 구현한다.

```csharp
record Point(int X, int Y) : ICreateRandom<Point>
{
    static Random rnd = new();
    public static Point CreateRandom() => new Point(rnd.Next(), rnd.Next());
}
```

호출은 **제약된 타입 매개변수를 통해** 한다.

```csharp
T[] CreateTestData<T>(int count) where T : ICreateRandom<T>
{
    T[] result = new T[count];
    for (int i = 0; i < count; i++)
        result[i] = T.CreateRandom();      // 타입 매개변수 위의 정적 멤버 호출
    return result;
}

Point[] testData = CreateTestData<Point>(50);
```

`T.CreateRandom()`이 이 기능의 문법적 핵심이다. **`T`는 타입 매개변수인데 그 위에서 정적 메서드를 부른다.** 이 호출은 다형적이다 — `Point`뿐 아니라 `ICreateRandom<T>`를 구현한 어떤 타입에도 동작한다.

**인스턴스 다형성과의 차이가 여기서 분명해진다.** 인스턴스 다형성은 객체가 있어야 성립한다. 객체 안의 타입 정보가 어느 구현을 부를지 결정한다. 정적 다형성에는 객체가 없다. **타입 매개변수 `T` 자체가 "어느 구현인가"라는 정보를 실어 나른다.**

```text
   인스턴스 다형성                     정적 다형성
   ─────────────────                  ─────────────────
   IShape s = new Circle();           where T : ICreateRandom<T>
   s.Area();                          T.CreateRandom();
        │                                  │
        ↓                                  ↓
   객체 헤더의 메서드 테이블          컴파일/JIT 시점의 T 대입
   → Circle.Area 호출                 → Point.CreateRandom 호출
   (런타임 결정)                      (제네릭 인스턴스화 시점 결정)
```

### 연산자를 인터페이스로 계약하기

연산자도 정적 메서드이므로 같은 방식으로 계약할 수 있다.

```csharp
interface IAddable<T> where T : IAddable<T>
{
    abstract static T operator + (T left, T right);
}
```

**`where T : IAddable<T>`라는 자기 참조 제약이 왜 필요한지**가 이 절에서 가장 이해하기 어려운 부분이다. 22.1절의 5번 규칙을 다시 떠올려 보라. **연산자 함수의 피연산자 중 최소 하나는 연산자를 선언한 타입이어야 한다.**

여기서 연산자를 선언한 타입은 `IAddable<T>`이고, 피연산자는 `T`다. `T`와 `IAddable<T>`는 다른 타입이므로 규칙 위반이다. **자기 참조 제약 `where T : IAddable<T>`를 걸면 `T`가 `IAddable<T>`로 취급될 수 있게 되고, 그제서야 규칙이 만족된다.**

구현은 평범하다.

```csharp
record Point(int X, int Y) : IAddable<Point>
{
    public static Point operator + (Point left, Point right)
        => new Point(left.X + right.X, left.Y + right.Y);
}
```

이제 다형적으로 `+`를 부르는 메서드를 쓸 수 있다.

```csharp
T Sum<T>(params T[] values) where T : IAddable<T>
{
    T total = values[0];
    for (int i = 1; i < values.Length; i++)
        total += values[i];        // IAddable<T>의 + 에 바인딩된다
    return total;
}
```

`total += values[i]`의 `+` 호출은 `Point`가 아니라 **`IAddable<T>`에 바인딩된다.** 그래서 `Sum`은 `IAddable<T>`를 구현한 모든 타입에서 동작한다.

> **⚠️ `values[0]`으로 초기화한 것은 우연이 아니다**
>
> 위의 `Sum`은 `T total = values[0];`으로 시작한다. **`T total = default;`로 쓸 수 없기 때문이다.** `IAddable<T>`는 "0에 해당하는 값"을 약속하지 않는다. `default(T)`는 참조 타입이면 `null`이고, 구조체면 모든 필드가 0인 값인데 그것이 덧셈의 항등원이라는 보장이 없다.
>
> 그래서 위 코드는 **빈 배열에서 `IndexOutOfRangeException`을 던진다.** 실무용 코드라면 항등원을 인터페이스가 약속해야 한다 — 그것이 22.8절의 `IAdditiveIdentity<TSelf, TResult>`와 `T.Zero`다. 인터페이스를 설계할 때 **"연산"만 계약하고 "상수"를 계약하지 않으면 이런 구멍이 남는다.**

### 컴파일 결과

인터페이스 쪽 IL은 `abstract virtual static`이라는 낯선 조합이다.

```il
.class interface public abstract auto ansi IAddable`1<(class IAddable`1<!T>) T>
{
  .method public hidebysig specialname abstract virtual static
          !T op_Addition(!T left, !T right) cil managed
  {
  }
}
```

.NET 7 이전에는 IL 수준에서도 불가능했던 조합이다. **런타임 지원이 필요한 언어 기능**이라는 뜻이며, 그래서 .NET 6 이하를 대상으로 하면 컴파일되지 않는다.

호출 쪽은 `constrained.` 접두사가 붙은 `call`이다.

```il
// total += values[i];  (Sum<T> 안에서)
IL_0000:  ldloc.0                                        // total
IL_0001:  ldarg.0
IL_0002:  ldloc.1
IL_0003:  ldelem     !!T
IL_0008:  constrained. !!T
IL_000e:  call       !!T class IAddable`1<!!T>::op_Addition(!!T, !!T)
IL_0013:  stloc.0
```

`constrained.` 접두사가 **"인터페이스 메서드를 부르되, `T`의 실제 구현으로 해석하라"** 는 지시다. 인스턴스 메서드에 쓰이던 `constrained.`와 같은 접두사가 정적 호출로 확장된 것이다.

### 런타임 동작과 성능

여기서 제네릭의 코드 생성 방식(23.11절)이 결정적이다.

**`T`가 값 타입이면** CLR은 `T`마다 별도의 네이티브 코드를 만든다. `Sum<int>`와 `Sum<double>`은 서로 다른 기계어다. 특수화 시점에 `T`가 확정되므로 **`constrained. call`은 구체 타입의 메서드에 대한 직접 호출로 굳어지고, 짧으면 인라인된다.** 결과적으로 `int.op_Addition` 호출이 사라지고 `add` 명령만 남는다. **손으로 쓴 `int` 전용 코드와 같은 기계어가 나온다.**

**`T`가 참조 타입이면** 모든 참조 타입이 하나의 코드를 공유한다. 그러면 `T`가 무엇인지는 런타임에 넘어오는 타입 인수 정보로 알아야 하고, 호출은 간접 호출이 된다. 값 타입 경로만큼 빠르지는 않지만, 여전히 **박싱은 없고 DLR 바인딩도 없다.**

| 접근 | 호출 형태 | 박싱 | 인라인 가능성 |
|---|---|---|---|
| 타입별 오버로드 | 직접 호출 | 없음 | 높음 |
| 정적 추상 멤버 (`T` = 값 타입) | 특수화 후 직접 호출 | 없음 | 높음 |
| 정적 추상 멤버 (`T` = 참조 타입) | 공유 코드 + 간접 호출 | 없음 | 낮음 |
| 델리게이트 주입 | 델리게이트 호출 | 없음(제네릭 델리게이트) | 낮음 |
| `dynamic` | DLR 호출 사이트 | 있음 | 없음 |

**핵심은 값 타입 경로에서 추상화 비용이 0이라는 것이다.** 이것이 제네릭 수학이 실제로 쓸 만한 이유다.

### `static virtual` — 선택적 구현

`static abstract` 대신 `static virtual`을 쓰면 **기본 구현**을 줄 수 있다. 구현 타입은 그것을 재정의하거나 그냥 둘 수 있다.

BCL의 실제 사례가 이것을 잘 보여 준다.

```csharp
public interface IAdditionOperators<TSelf, TOther, TResult>
    where TSelf : IAdditionOperators<TSelf, TOther, TResult>?
{
    static abstract TResult operator + (TSelf left, TOther right);

    static virtual TResult operator checked + (TSelf left, TOther right)
        => left + right;                       // 위의 연산자를 그대로 호출
}
```

`checked` 버전은 `static virtual`이다. **검사 덧셈을 따로 정의하지 않은 타입은 일반 덧셈으로 대체된다.** 오버플로 검사가 의미 없는 타입(부동소수점, `BigInteger`)이 별도 구현을 강요받지 않는다.

### 제약과 한계

> **⚠️ 인터페이스 타입 자체로는 정적 추상 멤버를 부를 수 없다**
>
> ```csharp
> IAddable<Point>.op_Addition(a, b);      // 안 된다
> ICreateRandom<Point>.CreateRandom();    // 안 된다
> ```
>
> 어느 구현을 말하는지 알 수 없기 때문이다. **정적 추상 멤버는 제약된 타입 매개변수를 통해서만 호출된다.** 이것은 문법적 불편이 아니라 기능의 정의 그 자체다 — 타입 매개변수만이 "어느 타입인가"를 실어 나른다.
>
> 같은 이유로 **정적 추상 멤버를 가진 인터페이스는 변수의 타입으로 쓰기 어렵다.** `IAddable<Point> x = somePoint;`처럼 인스턴스를 담는 것 자체는 가능하지만, 그 변수로 정적 멤버에 접근할 수는 없다. 리플렉션으로 이 멤버를 호출하는 방법은 57.9절에서 다룬다.

> **⚠️ .NET 7 이상이 필요하다**
>
> 언어 기능은 C# 11이지만 **런타임 지원이 필수**다. `net6.0`을 대상으로 하면 `LangVersion`을 11로 올려도 컴파일되지 않는다. .NET 6에는 미리보기 기능으로 들어 있었으나 정식 지원은 .NET 7부터다. `netstandard2.0` 라이브러리에서는 쓸 수 없다.

> **💡 인터페이스를 직접 만들기 전에 BCL을 먼저 보라**
>
> `IAddable<T>` 같은 인터페이스를 직접 정의하면 **당신의 타입만 그것을 구현한다.** `int`도 `double`도 구현하지 않으므로 제네릭 코드에 넣을 수 없다.
>
> 인터페이스가 쓸모 있으려면 **런타임이 정의하고 모든 숫자 타입이 구현해야 한다.** .NET 7부터 실제로 그렇게 되었고, 그것이 `System.Numerics`의 산술 인터페이스 계층이다. 다음 절의 주제다. **직접 정의하는 것은 BCL 인터페이스로 표현할 수 없는 도메인 개념(예: "병합할 수 있는 것", "파싱할 수 있는 설정")에만 남겨 둔다.**

## 22.8 제네릭 수학 — `INumber<T>`, `IAdditionOperators<T>` 계열

### 문제와 해법

.NET 7 이전에는 산술 코드가 특정 숫자 타입에 못 박혀 있어야 했다.

```csharp
int Sum(params int[] numbers)          // int 전용
{
    int total = 0;
    foreach (int n in numbers)
        total += n;
    return total;
}
```

`double`이나 `decimal`에 쓰려면 같은 코드를 복사해야 했다. .NET 7이 도입한 `INumber<TSelf>`가 이것을 하나로 만든다.

```csharp
using System.Numerics;

T Sum<T>(params T[] numbers) where T : INumber<T>
{
    T total = T.Zero;                  // 정적 추상 프로퍼티
    foreach (T n in numbers)
        total += n;                    // 정적 추상 연산자
    return total;
}

int     intSum     = Sum(3, 5, 7);              // 15
double  doubleSum  = Sum(3.2, 5.3, 7.1);        // 15.6
decimal decimalSum = Sum(3.2m, 5.3m, 7.1m);     // 15.6
```

**한 메서드가 `int`, `long`, `double`, `float`, `decimal`, `BigInteger`, `Half`, `Int128`, 그리고 직접 만든 숫자 타입까지 전부 처리한다.**

### 인터페이스 계층

`INumber<TSelf>`는 단일 인터페이스가 아니라 **더 작은 인터페이스들의 우산**이다. 각 인터페이스가 하나의 연산 종류를 계약한다.

```text
                        ┌───────────────────────┐
                        │  IAdditionOperators   │  +
                        │  ISubtractionOperators│  -
                        │  IMultiplyOperators   │  *
                        │  IDivisionOperators   │  /
                        │  IUnaryNegation/Plus  │  단항 - +
                        │  IIncrement/Decrement │  ++ --
                        │  IEqualityOperators   │  == !=
                        │  IAdditiveIdentity    │  Zero의 근거
                        │  IMultiplicativeIdent.│  One의 근거
                        │  IParsable/ISpanPars. │  Parse / TryParse
                        │  IFormattable/ISpanF. │  ToString / TryFormat
                        └───────────┬───────────┘
                                    │ 이들을 상속
                        ┌───────────┴───────────┐
                        │   INumberBase<TSelf>  │  Zero, One, Radix, Abs,
                        │                       │  CreateChecked, IsNaN, ...
                        └───────────┬───────────┘
                                    │ + IComparisonOperators (< > <= >=)
                                    │ + IModulusOperators (%)
                        ┌───────────┴───────────┐
                        │    INumber<TSelf>     │  Max, Min, Clamp, Sign, CopySign
                        └───┬───────────────┬───┘
                            │               │
              + IBitwiseOp. │               │
        ┌───────────────────┴──┐      ┌─────┴──────────────────┐
        │ IBinaryNumber<TSelf> │      │ IFloatingPoint<TSelf>  │
        │  IsPow2, Log2        │      │  Ceiling, Floor, Round │
        └──────────┬───────────┘      └─────────┬──────────────┘
                   │ + IShiftOperators           │ + I{Exponential,Logarithmic,
        ┌──────────┴────────────┐                │    Power,Root,Trigonometric,
        │ IBinaryInteger<TSelf> │                │    Hyperbolic}Functions
        │  PopCount, RotateLeft │      ┌─────────┴──────────────────┐
        │  LeadingZeroCount     │      │ IFloatingPointIeee754<T>   │
        │  DivRem               │      │  NaN, Epsilon, Infinity    │
        └───────────────────────┘      └────────────────────────────┘
             ↑ int, long, byte,             ↑ double, float, Half
               Int128, BigInteger
```

이 계층이 존재하는 이유는 **제약을 필요한 만큼만 걸기 위해서**다. 덧셈만 필요한 알고리즘이 부동소수점 연산까지 요구할 이유가 없다.

주요 인터페이스를 표로 정리하면 다음과 같다.

| 인터페이스 | 계약하는 것 | 대표 멤버 |
|---|---|---|
| `IAdditionOperators<TSelf,TOther,TResult>` | `+` | `operator +`, `operator checked +` |
| `ISubtractionOperators<TSelf,TOther,TResult>` | `-` | `operator -` |
| `IMultiplyOperators<TSelf,TOther,TResult>` | `*` | `operator *` |
| `IDivisionOperators<TSelf,TOther,TResult>` | `/` | `operator /` |
| `IModulusOperators<TSelf,TOther,TResult>` | `%` | `operator %` |
| `IUnaryNegationOperators<TSelf,TResult>` | 단항 `-` | `operator -` |
| `IIncrementOperators<TSelf>` | `++` | `operator ++` |
| `IEqualityOperators<TSelf,TOther,TResult>` | `==`, `!=` | `operator ==`, `operator !=` |
| `IComparisonOperators<TSelf,TOther,TResult>` | `<`, `>`, `<=`, `>=` | 네 연산자 |
| `IBitwiseOperators<TSelf,TOther,TResult>` | `&`, `\|`, `^`, `~` | 네 연산자 |
| `IShiftOperators<TSelf,TOther,TResult>` | `<<`, `>>`, `>>>` | 세 연산자 |
| `IAdditiveIdentity<TSelf,TResult>` | 덧셈 항등원 | `AdditiveIdentity` |
| `IMultiplicativeIdentity<TSelf,TResult>` | 곱셈 항등원 | `MultiplicativeIdentity` |
| `IMinMaxValue<TSelf>` | 범위 | `MinValue`, `MaxValue` |
| `INumberBase<TSelf>` | 숫자의 기본 | `Zero`, `One`, `Radix`, `Abs`, `CreateChecked` |
| `INumber<TSelf>` | 비교 가능한 숫자 | `Max`, `Min`, `Clamp`, `Sign` |
| `IBinaryInteger<TSelf>` | 정수 비트 연산 | `PopCount`, `LeadingZeroCount`, `DivRem` |
| `IFloatingPointIeee754<TSelf>` | IEEE 754 | `NaN`, `Epsilon`, `PositiveInfinity` |
| `IRootFunctions<TSelf>` | 거듭제곱근 | `Sqrt`, `Cbrt`, `RootN`, `Hypot` |
| `ISignedNumber<TSelf>` | 부호 있는 수 | `NegativeOne` |
| `IUnsignedNumber<TSelf>` | 부호 없는 수 | — (표지 인터페이스) |

`INumber<TSelf>`는 **.NET의 모든 실수·정수 타입이 구현하며, `char`도 구현한다.**

### 상수 — `T.Zero`와 `T.One`

22.7절에서 본 구멍("`default(T)`가 항등원이라는 보장이 없다")을 `INumberBase<TSelf>`가 메운다.

```csharp
T zero = T.Zero;       // 덧셈 항등원
T one  = T.One;        // 곱셈 항등원
int radix = T.Radix;   // 진법 (2 또는 10)
```

`T.Zero`는 `int`면 `0`, `double`이면 `0.0`, `decimal`이면 `0m`, 사용자 타입이면 그 타입이 정의한 값이다. **이 한 줄 덕분에 제네릭 산술 알고리즘이 초기값을 안전하게 얻는다.**

부호 있는 수라면 `ISignedNumber<TSelf>.NegativeOne`도 쓸 수 있다.

### 실제 제네릭 알고리즘

**1) 평균**

```csharp
static T Average<T>(ReadOnlySpan<T> values) where T : INumber<T>
{
    if (values.Length == 0) throw new ArgumentException("빈 시퀀스", nameof(values));

    T total = T.Zero;
    foreach (T v in values)
        total += v;

    // values.Length는 int다. T로 바꿔야 나눌 수 있다.
    T count = T.CreateChecked(values.Length);
    return total / count;
}
```

**2) 제곱평균제곱근(RMS)** — 제곱근이 필요하므로 제약을 하나 더 붙인다.

```csharp
static T RMS<T>(params T[] values) where T : INumber<T>, IRootFunctions<T>
{
    T total = T.Zero;
    for (int i = 0; i < values.Length; i++)
        total += values[i] * values[i];

    T count = T.CreateChecked(values.Length);
    return T.RootN(total / count, 2);           // 제곱근
}

Console.WriteLine(RMS(3.0, 4.0));               // 3.5355339059327378
```

`IRootFunctions<T>`는 `INumber<T>`에 포함되지 않는다. **부동소수점에만 의미가 있는 연산이기 때문이다.** 필요한 만큼만 제약을 추가하는 이 방식이 계층 설계의 의도다.

**3) 비트 연산과 정규화** — 필요한 인터페이스만 골라 제약에 넣는다.

```csharp
static int CountSetBits<T>(T value) where T : IBinaryInteger<T>
    => int.CreateChecked(T.PopCount(value));

static T Normalize<T>(T value, T min, T max) where T : INumber<T>
    => (T.Clamp(value, min, max) - min) / (max - min);

Console.WriteLine(CountSetBits(0b1011_0110));      // 5
Console.WriteLine(CountSetBits(255L));             // 8
```

### 숫자 타입 사이의 변환 — `CreateXxx`

제네릭 산술에서 가장 자주 부딪히는 문제는 **`int` 같은 구체 타입 값을 `T`로 옮기는 것**이다. `(T) someInt`는 컴파일되지 않는다 — `T`가 무엇인지 모르므로 어떤 변환도 확정할 수 없다.

`INumberBase<TSelf>`가 세 개의 정적 팩터리를 제공한다.

| 메서드 | 범위를 벗어나면 |
|---|---|
| `T.CreateChecked<TOther>(value)` | `OverflowException` |
| `T.CreateSaturating<TOther>(value)` | `T.MinValue` / `T.MaxValue`로 포화 |
| `T.CreateTruncating<TOther>(value)` | 비트를 잘라 낸다(래핑) |

```csharp
byte a = byte.CreateChecked(300);        // OverflowException
byte b = byte.CreateSaturating(300);     // 255
byte c = byte.CreateTruncating(300);     // 44  (300 & 0xFF)
```

> **💡 기본값은 `CreateChecked`다**
>
> 셋 중 무엇을 쓸지 헷갈리면 `CreateChecked`를 쓴다. **조용히 틀린 답을 내는 것보다 예외로 멈추는 편이 거의 항상 낫다.** `CreateSaturating`은 신호 처리나 그래픽처럼 포화가 도메인의 정답인 곳에서, `CreateTruncating`은 해시나 체크섬처럼 비트 자르기가 의도인 곳에서만 쓴다.
>
> `values.Length`(항상 음이 아닌 `int`)를 `T`로 옮기는 것처럼 실패할 수 없는 경우라면 셋 중 무엇을 써도 결과가 같지만, 그래도 `CreateChecked`를 쓰는 편이 의도를 드러낸다.

### 자체 타입을 제네릭 수학에 참여시키기

`INumber<T>` 전체를 구현하는 것은 멤버가 수십 개라 부담이 크다. **필요한 인터페이스만 골라 구현하는 것이 정상적인 사용법이다.**

```csharp
using System.Numerics;

public readonly struct Vector2D :
    IAdditionOperators<Vector2D, Vector2D, Vector2D>,
    ISubtractionOperators<Vector2D, Vector2D, Vector2D>,
    IMultiplyOperators<Vector2D, double, Vector2D>,
    IUnaryNegationOperators<Vector2D, Vector2D>,
    IEqualityOperators<Vector2D, Vector2D, bool>,
    IAdditiveIdentity<Vector2D, Vector2D>
{
    public double X { get; }
    public double Y { get; }

    public Vector2D(double x, double y) { X = x; Y = y; }

    public static Vector2D AdditiveIdentity => default;

    public static Vector2D operator + (Vector2D a, Vector2D b)
        => new Vector2D(a.X + b.X, a.Y + b.Y);

    public static Vector2D operator - (Vector2D a, Vector2D b)
        => new Vector2D(a.X - b.X, a.Y - b.Y);

    public static Vector2D operator * (Vector2D a, double scalar)
        => new Vector2D(a.X * scalar, a.Y * scalar);

    public static Vector2D operator - (Vector2D a) => new Vector2D(-a.X, -a.Y);

    public static bool operator == (Vector2D a, Vector2D b) => a.X == b.X && a.Y == b.Y;
    public static bool operator != (Vector2D a, Vector2D b) => !(a == b);

    public override bool Equals(object obj) => obj is Vector2D v && this == v;
    public override int GetHashCode() => HashCode.Combine(X, Y);
    public override string ToString() => $"({X}, {Y})";
}
```

이제 항등원을 요구하는 제네릭 합계 함수를 안전하게 쓸 수 있다.

```csharp
static T Sum<T>(IEnumerable<T> values)
    where T : IAdditionOperators<T, T, T>, IAdditiveIdentity<T, T>
{
    T total = T.AdditiveIdentity;
    foreach (T v in values)
        total += v;
    return total;
}

var vectors = new[] { new Vector2D(1, 2), new Vector2D(3, 4) };
Console.WriteLine(Sum(vectors));       // (4, 6)
Console.WriteLine(Sum(new[] { 1, 2, 3 }));   // 6 — int도 같은 함수를 탄다
```

**`Vector2D`와 `int`가 같은 제네릭 함수를 통과한다.** `IAdditiveIdentity<T,T>`와 `IAdditionOperators<T,T,T>`만 요구했기 때문에 `INumber<T>`를 구현하지 않는 `Vector2D`도 조건을 만족한다.

> **💡 제약은 최소이면서 충분하게**
>
> 위 `Sum`은 `where T : INumber<T>`라고 써도 동작한다. 코드가 짧아진다. 그런데 그러면 **`Vector2D`는 통과하지 못한다.** `INumber<T>`는 비교, 나눗셈, 나머지, 부호, 파싱, 서식까지 전부 요구하고 벡터에는 그중 대부분이 없다.
>
> **알고리즘이 실제로 쓰는 연산만 제약에 넣으면 적용 가능한 타입의 집합이 넓어진다.** 반대로 필요한 것을 빠뜨리면 컴파일이 안 되므로, 최소이면서 충분한 지점이 있다. 제네릭 제약 설계의 일반 원칙은 23.13절에서 다룬다.

### 오버플로와 검사 연산

제네릭 수학의 산술도 기본적으로 **검사되지 않는다.**

```csharp
static T Double<T>(T x) where T : INumber<T> => x + x;

Console.WriteLine(Double(int.MaxValue));      // -2  (조용히 래핑)
```

검사가 필요하면 `checked` 블록을 쓴다. 22.7절에서 본 `static virtual operator checked +` 덕분에, **검사 버전을 정의한 타입은 그것이 불리고 정의하지 않은 타입은 일반 덧셈으로 대체된다.**

```csharp
static T DoubleChecked<T>(T x) where T : INumber<T> => checked(x + x);

Console.WriteLine(DoubleChecked(int.MaxValue));     // OverflowException
Console.WriteLine(DoubleChecked(double.MaxValue));  // Infinity — 부동소수점은 예외를 던지지 않는다
```

> **⚠️ 부동소수점은 `checked`에 반응하지 않는다**
>
> IEEE 754 산술은 오버플로에서 예외를 던지지 않고 `Infinity`를 만든다. `checked`를 붙여도 마찬가지다. **제네릭 코드에서 `T`가 정수인지 부동소수점인지에 따라 오버플로 동작이 완전히 달라진다.** `T.IsNaN(x)`나 `T.IsInfinity(x)`(`INumberBase<TSelf>`)로 결과를 검사하거나, 제약을 `IBinaryInteger<T>`로 좁혀 정수만 받는 편이 안전하다.

> **⚠️ `decimal`은 부동소수점 인터페이스를 구현하지 않는다**
>
> `decimal`은 `INumber<decimal>`을 구현하지만 `IFloatingPointIeee754<decimal>`은 구현하지 않는다. IEEE 754 이진 부동소수점이 아니기 때문이다. 그래서 `IRootFunctions<T>`나 `ITrigonometricFunctions<T>` 제약을 건 제네릭 메서드에 `decimal`을 넘길 수 없다. **금액 계산에 제네릭 수학을 쓰려면 제약을 `INumber<T>` 수준에 묶어 두어야 한다.**

### 성능

제네릭 수학의 성능은 22.7절에서 본 규칙 그대로다.

| 경우 | 결과 |
|---|---|
| `Sum<int>` | JIT이 `int` 전용 코드를 만들고 `op_Addition`을 인라인 → `add` 명령 |
| `Sum<double>` | 같은 방식 → `add` 부동소수점 명령 |
| `Sum<BigInteger>` | 구조체이므로 특수화되지만 `BigInteger`의 덧셈 자체가 비싸다 |
| `Sum<SomeClass>` | 참조 타입 공유 코드 → 간접 호출. 인라인 어려움 |

**값 타입에 대해서는 손으로 쓴 전용 코드와 같은 기계어가 나온다.** 이것이 이 기능의 존재 이유다. 다만 두 가지 비용은 남는다.

첫째, **코드 크기**다. `Sum<T>`를 열 개의 값 타입으로 인스턴스화하면 열 벌의 네이티브 코드가 만들어진다. JIT 시간과 코드 캐시를 쓴다.

둘째, **첫 호출 지연**이다. 각 인스턴스화마다 JIT이 한 번 돌아야 한다. 짧게 실행되는 프로그램이나 시작 시간이 중요한 서비스에서는 눈에 띌 수 있다.

> **💡 언제 제네릭 수학을 쓸 것인가**
>
> **쓸 때** — 라이브러리를 만들고, 같은 알고리즘을 여러 숫자 타입에 제공해야 하고, 타입 목록을 미리 고정하고 싶지 않을 때. 통계 함수, 보간, 단위 변환, 수치 알고리즘이 전형적이다.
>
> **쓰지 말 때** — 애플리케이션 코드에서 실제로 `double` 하나만 쓰는데 "혹시 몰라서" 제네릭으로 만드는 경우. 제약 목록이 길어지고 오류 메시지가 읽기 어려워지는 대가만 남는다. **타입이 하나면 그 타입으로 쓴다.**
>
> 중간 지점도 있다. `INumber<T>` 제네릭 버전을 안쪽에 두고 `double`, `decimal`처럼 실제로 자주 쓰이는 타입에 대한 얇은 오버로드를 바깥에 두면, 호출부는 타입 추론 없이 간결하게 쓰고 확장은 열어 둘 수 있다.

## 이 장의 요약

- **연산자 함수는 `public static`인 정적 메서드이고, 피연산자 중 최소 하나는 선언 타입이어야 한다.** 이 제약은 CLR이 아니라 C#이 건 것이며, 컴파일러가 후보 연산자를 두 곳만 뒤지게 하려는 실용적 이유에서 나왔다.
- **오버로드할 수 없는 연산자에는 각각 대안이 있다.** `[]`는 인덱서, `()`는 변환 연산자, `&&`/`||`는 `&`/`|` + `true`/`false`, 복합 대입은 이항 연산자를 정의하면 자동으로 따라온다. `=`, `?:`, `??`, `is`, `as`는 대안 없이 언어가 고정한다.
- **쌍 제약은 컴파일러가 강제하지만 일관성은 강제하지 않는다.** `==`/`!=`, `<`/`>`, `<=`/`>=`, `true`/`false` 네 짝은 한쪽만 정의하면 CS0216이다. 두 함수가 서로 모순되어도 컴파일러는 아무 말도 하지 않는다.
- **`==`는 정적 바인딩이고 `Equals`는 가상이다.** 이 한 문장이 22.3절 전체의 근거다. 변수의 선언 타입만 바꿔도 `==`의 결과가 뒤집히고, BCL의 어떤 컬렉션도 `op_Equality`를 보지 않는다. **값 의미론이 필요하면 `==` 오버로딩 여부와 무관하게 `Equals`와 `GetHashCode`를 재정의한다.**
- **클래스에서 `==`를 오버로딩할 때 널 검사에 `==`를 쓰면 무한 재귀다.** `is null`, `ReferenceEquals`, `(object)x == null` 셋 중 하나를 쓴다. 그리고 `==` 오버로딩은 `sealed` 클래스, 구조체, 레코드에만 한다.
- **암시적 변환은 "절대 실패하지 않는다"는 약속이다.** 실패하거나 정보를 잃을 수 있으면 `explicit`을 쓴다. 그리고 사용자 정의 변환은 **컴파일 타임 타입만 보고**, `is`/`as`가 무시하며, 두 번 연쇄되지 않는다. 공개 API에서 변환 연산자를 피해야 하는 이유는 78.6절이다.
- **연산자는 IL에서 `specialname` 플래그가 붙은 `op_Xxx` 정적 메서드가 된다.** 이름만 같고 플래그가 없으면 `+`로 부를 수 없고, 반대로 C#의 진짜 연산자는 이름으로 직접 부를 수 없다. 이 비대칭이 친화 메서드(`Add` 등)를 함께 두라는 지침의 근거다.
- **정적 추상 인터페이스 멤버(※C# 11)는 "정적 메서드는 인터페이스로 계약할 수 없다"는 벽을 허물었다.** 그래서 제네릭 코드 안에서 `T.Zero`와 `a + b`를 쓸 수 있게 되었고, 호출은 `T`로 제약된 타입 매개변수를 통해서만 가능하다. .NET 7 이상이 필요하다.
- **제네릭 수학의 값 타입 경로에는 추상화 비용이 없다.** JIT이 `T`마다 특수화하고 연산자를 인라인하므로 손으로 쓴 전용 코드와 같은 기계어가 나온다. 참조 타입은 코드를 공유하므로 간접 호출이 남는다.
- **연산자를 오버로딩할지는 문법 문제가 아니라 설계 문제다.** 기호의 의미가 자명하지 않으면 이름 있는 메서드를 쓴다. 의미 후보가 둘 이상 떠오르는 순간 이미 나쁜 후보다.

## 연습 문제

1. `Money` 구조체를 만들어라. `decimal Amount`와 `string Currency`를 갖고, `+`, `-`, 단항 `-`, `==`, `!=`를 오버로딩하며 `IEquatable<Money>`를 구현한다. 통화가 다른 두 `Money`를 더하면 `InvalidOperationException`을 던지게 하라. 그다음 `Equals`와 `GetHashCode`를 **일부러 재정의하지 않고** 빌드해서 CS0660과 CS0661 경고가 실제로 나오는지 확인하라.

2. 1번의 `Money` 여러 개를 `HashSet<Money>`와 `Dictionary<Money, string>`에 넣어라. `Equals`/`GetHashCode`가 없을 때와 있을 때 `Contains`, `ContainsKey`, `Distinct().Count()`의 결과가 어떻게 달라지는지 표로 정리하라.

3. 클래스 `Point`에 `operator ==`를 정의하되 본문에서 `if (p1 == null)`을 쓰고 실행하라. 어떤 예외가 나는지, 그리고 그 예외를 `try`/`catch`로 잡을 수 있는지 확인하라. 그다음 `is null`로 고치고 다시 실행하라.

4. `ildasm`이나 `ILSpy`로 1번 `Money`의 어셈블리를 열어 `op_Addition`, `op_Equality`, `op_UnaryNegation` 메서드 정의를 찾아라. 각 메서드에 `specialname` 플래그가 붙어 있는지 확인하고, C# 코드에서 `Money.op_Addition(a, b)`라고 직접 호출해 보면 어떤 오류가 나는지 확인하라.

5. `SqlBoolean`을 흉내 낸 3값 논리 구조체 `Tribool`을 만들어라. `operator true`, `operator false`, `operator !`, `operator &`, `operator |`를 정의하고, `Tribool.Unknown && Tribool.False`가 오른쪽 피연산자를 평가하는지 아닌지를 `Console.WriteLine`을 넣은 프로퍼티로 확인하라. 그다음 `operator false`만 지워 보고 CS0218 메시지를 읽어 보라.

6. `Note` 구조체에 `implicit operator double`을 정의하고, `Note`를 `object`에 담은 뒤 `(double)` 캐스트를 시도하라. 어떤 예외가 나는지 확인하고, `is Note`와 `as` 사용이 어떻게 동작하는지도 함께 확인하라. 같은 코드를 `ToFrequency()` 메서드로 바꿨을 때 호출부가 어떻게 달라지는지 비교하라.

7. `where T : INumber<T>` 제약으로 표준편차를 계산하는 제네릭 메서드를 작성하라(제곱근이 필요하므로 `IRootFunctions<T>` 제약을 추가한다). `double[]`, `float[]`에 대해 동작을 확인하고, `decimal[]`에 대해서는 왜 컴파일되지 않는지 오류 메시지를 근거로 설명하라. 그다음 `int` 전용 버전과 제네릭 버전의 실행 시간을 `Stopwatch`로 비교하고, `int` 경로에서 차이가 사실상 없는 이유를 22.7절의 특수화 규칙으로 설명하라.
