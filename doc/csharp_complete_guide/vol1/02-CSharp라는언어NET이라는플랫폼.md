## 2.1 C#을 규정하는 네 가지 — 객체 지향, 타입 안전성, 자동 메모리 관리, 플랫폼 지원

C#을 한 문장으로 정의하면 이렇다.

> C#은 범용(general-purpose)이고, 타입 안전(type-safe)하며, 객체 지향(object-oriented)인 프로그래밍 언어다.

이 언어의 목표는 **프로그래머의 생산성**이다. 그리고 그 목표를 위해 C#은 단순함, 표현력, 성능 사이에서 균형을 잡는다. 이 세 가지는 서로 밀고 당기는 관계다 — 표현력을 높이면 단순함을 잃고, 성능을 얻으려면 표현력을 포기해야 할 때가 있다. C#의 설계 역사는 이 줄다리기의 기록이라고 봐도 된다.

> **📌 앤더스 헤일스버그**
>
> C#의 초대 수석 설계자는 앤더스 헤일스버그(Anders Hejlsberg)다. 그는 Turbo Pascal을 만들었고 Delphi의 아키텍트였으며, 나중에 TypeScript도 설계했다. C#에서 "컴파일러가 최대한 많이 잡아주되 문법은 사람이 읽을 수 있어야 한다"는 감각은 이 계보에서 온 것이다.
>
> C# 언어 자체는 **플랫폼 중립적**이다. 언어는 특정 운영체제를 전제하지 않고, 플랫폼별 런타임들이 그 언어를 실행한다. 이 구분 — 언어와 런타임의 분리 — 이 이 장 전체의 골격이다.

C#을 다른 언어와 구분 짓는 성질은 네 가지다. 이 절에서 하나씩 본다.

| 성질 | 한 줄 요약 | 대비되는 언어와 그 방식 |
|---|---|---|
| **객체 지향** | 모든 타입이 하나의 뿌리를 공유하고, 데이터와 동작이 타입 안에 캡슐화된다 | C — 구조체와 함수가 분리. Java — 원시 타입만 객체 체계 밖 |
| **타입 안전성** | 타입은 자신이 정의한 방식으로만 상호작용한다. 컴파일 시점과 런타임 양쪽에서 강제된다 | JavaScript·Python — 동적 타입, 런타임에야 발견 |
| **자동 메모리 관리** | 더 이상 참조되지 않는 객체의 메모리를 런타임이 회수한다 | C·C++ — 수동 `malloc`/`free`, `new`/`delete` |
| **플랫폼 지원** | 같은 소스가 Windows·Linux·macOS·모바일·브라우저에서 돈다 | Objective-C/Swift — Apple 생태계. VB6 — Windows 전용 |

### 첫째, 객체 지향

C#은 객체 지향 패러다임의 풍부한 구현체다. 캡슐화, 상속, 다형성을 모두 지원한다. **캡슐화**란 객체 주위에 경계를 그어 외부에 드러나는 동작(public)과 내부 구현 세부(private)를 분리하는 것이다.

여기까지는 어느 객체 지향 언어에나 있다. C#을 특징짓는 것은 다음 네 가지다.

#### 통합 타입 시스템(unified type system)

C#의 기본 구성 단위는 **타입**이다 — 데이터와 함수를 캡슐화한 단위. 그리고 C#의 모든 타입은 궁극적으로 **하나의 공통 기반 타입**을 공유한다. 그 타입이 `System.Object`다.

이 말의 실질적 의미는, 업무 객체든 숫자 같은 원시 타입이든 **똑같은 기본 기능을 갖는다**는 것이다. 예를 들어 어떤 타입의 인스턴스든 `ToString()`을 호출해 문자열로 바꿀 수 있다.

```csharp
int number = 42;
string s1 = number.ToString();        // "42" — 정수에도 메서드가 있다

bool flag = true;
string s2 = flag.ToString();          // "True"

DateTime now = DateTime.Now;
string s3 = now.ToString();           // "2026-09-06 오후 3:20:11" (문화권에 따라 다름)
```

Java에서는 `int`가 객체가 아니어서 `42.toString()`이 성립하지 않고, `Integer`라는 별도의 래퍼 타입이 필요했다. C#에는 그런 이중 구조가 없다. `int`는 그 자체로 `System.Int32`이고, `System.Int32`는 `System.Object`에서 파생된다.

> **⚠️ "모든 것이 객체다"와 "모든 것이 힙에 있다"는 다른 말이다**
>
> `int`가 `System.Object`에서 파생된다고 해서, 정수 하나하나가 힙에 개별 객체로 존재한다는 뜻은 아니다. `int`는 **값 타입**이고 보통 스택이나 다른 객체 안에 직접 놓인다. 통합 타입 시스템은 **타입 계층의 통합**이지 **메모리 표현의 통합**이 아니다.
>
> 이 구분은 C#의 성능 특성에서 결정적으로 중요하다(2.7절). 값 타입이 `object`로 취급될 때 벌어지는 일 — **박싱**이라고 부른다 — 은 15장에서, 값 타입 자체의 설계는 16장에서 다룬다. **지금은 "값 타입은 힙에 안 갈 수도 있다" 정도만 기억하면 된다.**

#### 클래스와 인터페이스

전통적인 객체 지향에서 타입의 유일한 종류는 클래스다. C#에는 클래스 말고도 여러 종류의 타입이 있고, 그중 하나가 **인터페이스**다.

인터페이스는 데이터를 가질 수 없는 클래스 같은 것이다. 즉 **상태가 아니라 동작만** 정의한다. 이 제약 덕분에 두 가지가 가능해진다.

- **다중 상속** — 한 클래스가 여러 인터페이스를 구현할 수 있다.
- **명세와 구현의 분리** — "무엇을 할 수 있는가"와 "어떻게 하는가"를 다른 곳에 둘 수 있다.

```csharp
// 클래스는 하나만 상속할 수 있지만
// 인터페이스는 몇 개든 구현할 수 있다.
class FileLogger : LoggerBase, IDisposable, IAsyncDisposable
{
    // ...
}
```

C++은 클래스의 다중 상속을 허용한다. 그 결과 같은 기반 클래스를 두 경로로 상속하면 상태가 두 벌 생기는 이른바 "다이아몬드 문제"와 씨름해야 했다. C#은 **상태를 가질 수 있는 상속은 하나로 제한하고, 상태 없는 계약은 여러 개 허용**하는 쪽을 택했다. 이 제약은 C# 문법의 선택이 아니라 **런타임 차원의 규칙**이다 — 2.5절에서 그 이유를 본다.

#### 프로퍼티, 메서드, 이벤트

순수 객체 지향 패러다임에서는 모든 함수가 메서드다. C#에서 메서드는 **함수 멤버(function member)의 한 종류**일 뿐이고, 프로퍼티와 이벤트도 함수 멤버다.

- **프로퍼티** — 객체 상태의 한 조각을 캡슐화하는 함수 멤버. 버튼의 색, 레이블의 텍스트 같은 것.
- **이벤트** — 객체 상태 변화에 반응하는 일을 단순화하는 함수 멤버.

```csharp
class Thermometer
{
    private double celsius;

    // 프로퍼티 — 겉보기는 필드, 실제로는 메서드 한 쌍
    public double Celsius
    {
        get => celsius;
        set
        {
            if (value < -273.15)
                throw new ArgumentOutOfRangeException(nameof(value));
            celsius = value;
        }
    }

    // 읽기 전용 계산 프로퍼티 — 저장 공간이 없다
    public double Fahrenheit => celsius * 9 / 5 + 32;
}
```

Java에서는 같은 일을 `getCelsius()` / `setCelsius(double)` 메서드 쌍으로 표현하는 것이 관례였다. C#은 그 관례를 **언어 문법으로 승격**시켰다. 겉보기에는 사소한 차이지만, 이것 때문에 데이터 바인딩·직렬화·객체 초기화자 같은 것이 훨씬 매끄럽게 동작한다.

#### 함수형 패러다임의 차용

C#은 주로 객체 지향 언어이지만 함수형 프로그래밍에서도 빌려왔다.

- **함수를 값으로 다룬다** — **델리게이트**를 통해 함수를 다른 함수의 인자로 넘기고 반환받을 수 있다.
- **불변성을 위한 패턴** — 값이 바뀌는 변수를 피하고 선언적 패턴을 쓰는 것이 함수형의 핵심이다. C#은 변수를 "포획(capture)"하는 이름 없는 함수(**람다 식**), 리스트·반응형 프로그래밍을 위한 **쿼리 식**, 그리고 불변 타입을 쉽게 만드는 **레코드**를 제공한다.

```csharp
// 함수를 값으로 — 람다 식
Func<int, int> square = x => x * x;
Console.WriteLine(square(7));            // 49

// 쿼리 식 — 선언적 데이터 처리
int[] numbers = { 5, 12, 3, 21, 8 };
var big = from n in numbers
          where n > 6
          orderby n
          select n * 10;
// 결과: 80, 120, 210

// 레코드 — 불변 타입을 한 줄로
record Point(double X, double Y);
```

> **⚠️ "객체 지향 언어"라는 말에 속지 마라**
>
> C#을 배우면서 "모든 것을 클래스로 만들어야 한다"고 오해하기 쉽다. 아니다. C#의 타입은 다섯 종류다 — 클래스, 인터페이스, 구조체, 열거형, 델리게이트. 그리고 레코드처럼 이들의 변형도 있다.
>
> 클래스가 언제나 옳은 답은 아니다. 작고 값처럼 행동하는 것은 구조체가 맞고(16장), 계약만 필요하면 인터페이스가 맞고(18장), 콜백 하나에 클래스를 만드는 것은 과하다. **"무엇을 쓸 것인가"의 판단 기준은 이 책 전체에 걸쳐 반복해서 나온다.**

### 둘째, 타입 안전성

C#은 **타입 안전한(type-safe)** 언어다. 타입 안전성이란, 타입의 인스턴스가 **자기가 정의한 프로토콜을 통해서만** 상호작용할 수 있다는 뜻이다. 그래서 각 타입은 내부 일관성을 보장받는다. 예를 들어 C#은 `string` 타입을 마치 정수인 것처럼 다루는 것을 막는다.

이 안전성은 **두 축**으로 강제된다. 이 절의 핵심이 여기 있다.

| 축 | 언제 검사하나 | 무엇을 잡나 | 실패하면 |
|---|---|---|---|
| **정적 타입 검사** | 컴파일 시점 | 코드에 적힌 타입이 서로 맞지 않는 모든 경우 | 컴파일 오류 — 프로그램이 만들어지지 않는다 |
| **런타임 타입 안전성** | 실행 시점 | 컴파일 시점에 알 수 없었던 실제 타입의 불일치 | 예외 — 프로그램이 멈추지만 메모리는 안전하다 |

#### 정적 타입 검사 — 실행하기 전에 잡는다

C#은 **정적 타입(static typing)**을 지원한다. 즉 언어가 **컴파일 시점에** 타입 안전성을 강제한다.

```csharp
int count = 10;
string name = "Alice";

int wrong = name;     // 컴파일 오류 CS0029: 'string'을 'int'로 변환할 수 없다
```

이 코드는 **실행되지 않는다.** 빌드가 실패하기 때문이다. 정적 타입 검사가 주는 것은 세 가지다.

1. **실행 전에 상당한 종류의 오류가 제거된다.** 단위 테스트가 져야 할 부담 일부를 컴파일러가 대신 진다 — "이 프로그램의 모든 타입이 서로 맞물리는가"를 컴파일러가 검증한다. 프로그램이 커질수록 이 효과는 커진다. 큰 프로그램이 관리 가능하고, 예측 가능하고, 견고해지는 이유가 여기 있다.
2. **도구가 강력해진다.** IntelliSense 같은 자동 완성이 가능한 이유는, 어떤 변수가 무슨 타입인지 도구가 알기 때문이다. 그래서 그 변수에 무슨 메서드를 호출할 수 있는지 목록을 낼 수 있다.
3. **리팩터링이 안전해진다.** 도구가 "이 변수·타입·메서드가 프로그램의 어디어디에서 쓰이는가"를 정확히 찾아낼 수 있다. 이름 변경이 문자열 치환이 아니라 의미 기반 변환이 된다.

C#은 **강한 타입(strongly typed)** 언어이기도 하다. 타입 규칙이 — 정적으로든 런타임에든 — 엄격하게 강제된다는 뜻이다. 정수를 받도록 설계된 함수를 부동소수점 수로 호출할 수 없다. 먼저 명시적으로 변환해야 한다.

```csharp
void Draw(int width) { /* ... */ }

double d = 3.7;
Draw(d);            // 컴파일 오류 — 암시적 변환이 없다
Draw((int)d);       // OK — 명시적 변환. 값은 3이 된다(소수점 이하 버림)
```

JavaScript였다면 `Draw(3.7)`이 그냥 통과하고, 함수 안에서 소수점 때문에 배열 인덱스가 이상해지고, 그 결과가 세 함수 건너에서 `undefined`로 나타났을 것이다. C#은 그 지점에서 멈춰 세우고 **당신에게 의도를 묻는다** — 자르겠는가, 반올림하겠는가.

> **📌 `dynamic`이라는 예외**
>
> C#은 `dynamic` 키워드로 코드의 일부를 **동적 타입**으로 만들 수 있다. 이때 멤버 해석이 컴파일 시점에서 런타임으로 미뤄진다. 하지만 C#은 여전히 압도적으로 정적 타입 언어이고, `dynamic`은 COM 상호운용이나 동적 언어와의 연동 같은 특수한 상황을 위한 도구다.
>
> 자세히는 59장에서 다룬다. **입문 단계에서 `dynamic`을 쓸 일은 사실상 없다.**

#### 런타임 타입 안전성 — 컴파일러가 다 알 수는 없다

여기서 자연스러운 질문이 나온다. **컴파일 시점에 전부 검사하는데 런타임 검사가 왜 또 필요한가?**

답은 간단하다. **컴파일러가 알 수 없는 것이 있기 때문이다.** 세 가지 경우를 보자.

**(1) 다운캐스트 — 프로그래머가 컴파일러에게 "믿어달라"고 말하는 경우**

```csharp
object o = "hello";     // string을 object 변수에 담는다 — 항상 안전하다
int i = (int)o;         // 컴파일은 통과한다. 런타임에 InvalidCastException
```

`o`의 정적 타입은 `object`다. `object`는 언젠가 `int`를 담고 있을 수도 있으므로, 컴파일러는 이 캐스트를 **문법적으로는** 허용해야 한다. 실제로 무엇이 들어 있는지는 실행해봐야 안다. 그래서 런타임이 검사하고, 맞지 않으면 `InvalidCastException`을 던진다.

**(2) 배열 공변성 — 언어 설계가 남긴 구멍**

```csharp
string[] strings = new string[3];
object[] objects = strings;      // 배열 공변성 — 컴파일 통과
objects[0] = 42;                 // 런타임에 ArrayTypeMismatchException
```

`string[]`을 `object[]`로 다룰 수 있게 한 것은 초기 .NET의 설계 결정이었다. 그 결과 "`object[]`에 아무거나 넣을 수 있다"는 정적 타입 정보와 "실제로는 `string[]`이다"라는 런타임 사실이 어긋날 수 있게 되었다. 런타임은 배열에 값을 저장할 때마다 원소 타입을 확인해서 이 어긋남을 잡아낸다.

**(3) 외부에서 들어오는 것 — 리플렉션, 역직렬화, 다른 어셈블리**

리플렉션으로 만든 객체, JSON에서 역직렬화한 객체, 그리고 **컴파일할 때 참조한 것과 다른 버전으로 교체된 라이브러리**. 이런 것들의 실제 타입은 컴파일 시점에 알 수 없다.

이 세 경우 모두에서, 런타임 검사가 없다면 어떻게 될까? `int`를 담고 있다고 **잘못 믿은** 메모리를 정수로 읽게 된다. 즉 문자열의 내부 포인터가 정수로 해석되고, 그 정수로 다시 메모리에 접근하면 프로세스가 통째로 무너진다. **C/C++에서 실제로 벌어지는 일이 이것이다.**

C#의 런타임 타입 안전성은 이 지점에서 **예외를 던진다.** 프로그램은 멈추지만 메모리는 오염되지 않는다. 이것이 두 축이 모두 필요한 이유다.

> **📌 두 축을 한 문장으로**
>
> **정적 타입 검사는 잡을 수 있는 것을 전부 실행 전에 잡고, 런타임 타입 안전성은 남은 것을 안전하게 실패시킨다.**
>
> 앞의 것은 생산성을 위한 것이고, 뒤의 것은 안전성을 위한 것이다. 둘 중 하나만 있으면 안 된다. 정적 검사만 있으면 다운캐스트가 메모리를 깨고, 런타임 검사만 있으면 오류를 프로덕션에서야 만난다.

> **⚠️ 널 가능 참조 타입은 런타임이 강제하지 않는다**
>
> ※C# 8에서 들어온 **널 가능 참조 타입(nullable reference types)** 은 이름과 달리 **순전히 컴파일러 기능**이다. `string?`과 `string`은 런타임에 완전히 같은 타입이고, 런타임은 이 둘을 구분하지 않는다.
>
> ```csharp
> #nullable enable
> string s = null;      // 컴파일러 경고 — 그러나 오류가 아니다
> void Foo(string? x) => Console.Write(x.Length);   // 경고 — 그래도 컴파일된다
> ```
>
> 즉 경고를 무시하면 `NullReferenceException`은 여전히 난다. 다른 어셈블리에서 넘어온 값, 리플렉션, 역직렬화 결과는 컴파일러의 분석 밖에 있다. **널 가능 참조 타입은 안전망이 아니라 조기 경보 장치다.** 자세히는 21장에서 다룬다.

> **⚠️ `unsafe` 안에서는 타입 안전성이 없다**
>
> `unsafe` 블록 안에서는 포인터를 직접 다룰 수 있고, 그 안에서는 위에서 말한 보장이 전부 사라진다. 잘못된 포인터로 쓰면 프로세스가 죽거나, 더 나쁘게는 조용히 다른 데이터를 덮어쓴다.
>
> `unsafe`는 프로젝트 설정(`<AllowUnsafeBlocks>true</AllowUnsafeBlocks>`)으로 **명시적으로 켜야** 쓸 수 있다. 기본값이 꺼짐인 것은 우연이 아니다 — 2.6절에서 다시 본다.

### 셋째, 자동 메모리 관리

C#은 자동 메모리 관리를 **런타임에 의존한다.** 공용 언어 런타임(CLR)에는 **가비지 컬렉터(garbage collector, GC)** 가 있고, 이것이 프로그램의 일부로 실행되면서 **더 이상 참조되지 않는 객체의 메모리를 회수한다.**

이 덕분에 프로그래머는 객체의 메모리를 명시적으로 해제하지 않아도 된다. 그리고 C++ 같은 언어에서 마주치는 **잘못된 포인터 문제가 사라진다.**

C++에서 무엇이 문제였는지 보자.

```csharp
// C# — 해제 코드가 없다.
var buffer = new byte[1024];
UseBuffer(buffer);
// 여기서 끝. buffer를 더 이상 아무도 참조하지 않으면
// 언젠가 GC가 알아서 회수한다.
```

C++이었다면 대응하는 코드에 `delete[] buffer;`가 있어야 한다. 그리고 그 한 줄을 둘러싸고 세 종류의 사고가 기다린다.

| 사고 | 무슨 일이 일어나나 | C#에서는 |
|---|---|---|
| **해제 누락(leak)** | 해제를 잊는다. 메모리가 계속 쌓인다 | GC가 회수한다 |
| **이중 해제(double free)** | 같은 메모리를 두 번 해제한다. 힙 구조가 깨진다 | 해제 자체가 없다 |
| **댕글링 포인터(dangling pointer)** | 해제한 메모리를 계속 가리키는 포인터로 접근한다. 남의 데이터를 읽거나 쓴다 | 참조가 살아 있으면 GC가 회수하지 않는다 |

세 번째가 가장 무섭다. 즉시 죽지 않고 **조용히 잘못된 값을 반환하다가** 한참 뒤 엉뚱한 곳에서 터지기 때문이다.

C#이 포인터를 **없앤** 것은 아니다. 대부분의 프로그래밍 작업에서 포인터가 **불필요해지게** 만들었을 뿐이다. 성능이 결정적인 지점과 상호운용을 위해, `unsafe`로 표시한 블록 안에서는 포인터와 명시적 메모리 할당이 허용된다.

주요 언어들의 메모리 관리 모델을 비교하면 C#의 위치가 보인다.

| 언어 | 모델 | 대가 |
|---|---|---|
| C | 수동 (`malloc`/`free`) | 세 종류의 사고를 프로그래머가 전부 책임진다 |
| C++ | 수동 + RAII·스마트 포인터 | 규율을 지키면 안전하지만, 규율이 언어로 강제되지 않는다 |
| Rust | 소유권·수명을 **컴파일 시점에** 검증 | 런타임 비용은 없으나 학습 곡선과 표현 제약이 크다 |
| Java | 추적형 GC | GC 일시 중지. 값 타입이 없어 힙 압박이 크다 |
| Python | 참조 카운팅 + 순환 수집기 | 참조 갱신 비용이 상시 발생한다 |
| **C#** | **추적형 GC + 값 타입 + `unsafe` 탈출구** | GC 일시 중지. 대신 필요한 곳에서 GC를 우회할 수 있다 |

C#의 선택은 "기본은 안전하게, 필요하면 내려갈 수 있게"다. 이 설계가 2.7절에서 이야기할 성능 특성의 절반을 만든다.

> **⚠️ GC는 "메모리"만 관리한다**
>
> 가비지 컬렉터가 회수하는 것은 **관리 힙(managed heap)의 메모리**뿐이다. 파일 핸들, 소켓, 데이터베이스 연결, 네이티브 라이브러리가 잡고 있는 자원 — 이런 것들은 GC가 알지 못하고, 알아서 닫아주지도 않는다.
>
> 그래서 C#에는 `IDisposable`과 `using` 문이 따로 있다. 이 구분("관리 리소스"와 "비관리 리소스")은 실무에서 가장 흔한 사고 원인 중 하나다. 자세히는 33장에서 다룬다.

> **⚠️ GC가 있어도 메모리 누수는 난다**
>
> "GC가 있으니 메모리 누수는 없다"는 말은 틀렸다. GC는 **참조되지 않는** 객체를 회수한다. 뒤집어 말하면, **의도치 않게 참조가 남아 있는** 객체는 영원히 회수되지 않는다.
>
> 대표적인 원인은 정적 필드에 쌓이는 캐시, 해제하지 않은 이벤트 구독, 살아 있는 타이머다. 실제 서비스에서 메모리가 계속 오르는 사고의 대부분이 이 셋 중 하나다. 진단 방법은 66장에서, 객체 수명의 정확한 정의는 34장에서 다룬다.

### 넷째, 플랫폼 지원

C#에는 다음 플랫폼을 지원하는 런타임이 있다.

- **Windows 7 이상 데스크톱** — 리치 클라이언트, 웹, 서버, 명령행 애플리케이션
- **macOS** — 웹·명령행 애플리케이션, 그리고 Mac Catalyst를 통한 리치 클라이언트
- **Linux** — 웹·명령행 애플리케이션
- **Android와 iOS** — 모바일 애플리케이션
- **Windows 10 계열 기기** — Xbox, Surface Hub, HoloLens (UWP를 통해)

여기에 더해, **Blazor**라는 기술은 C#을 **WebAssembly로 컴파일해 브라우저 안에서 실행**한다.

이 지원 범위를 다른 언어와 비교해보자. Swift와 Objective-C로 만든 것은 사실상 Apple 생태계 안에서만 돈다. VB6는 Windows를 벗어날 수 없었다. Java는 JVM이 있는 곳이면 어디서나 돌지만, 모바일에서는 Android가 사실상 자체 노선을 갔다. C#의 특이한 점은 **같은 언어와 같은 표준 라이브러리로** 서버·데스크톱·모바일·브라우저·게임을 전부 다룬다는 것이다.

애플리케이션 종류별로 정리하면 이렇다.

| 애플리케이션 계층 | CLR/BCL | 프로그램 종류 | 실행 플랫폼 |
|---|---|---|---|
| ASP.NET Core | .NET 8 | 웹 | Windows, Linux, macOS |
| Windows Desktop (WinForms, WPF) | .NET 8 | Windows 데스크톱 | Windows 10+ |
| WinUI 3 | .NET 8 | Windows 데스크톱 | Windows 10+ |
| MAUI | .NET 8 | 모바일, 데스크톱 | iOS, Android, macOS, Windows 10+ |
| (없음 — 콘솔·라이브러리) | .NET 8 | 명령행, 클래스 라이브러리 | Windows, Linux, macOS |
| .NET Framework | .NET Framework | 웹, Windows | Windows 7+ |

> **📌 틈새 런타임들**
>
> 주류 밖에도 C#이 돌아가는 곳이 있다.
>
> - **Unity** — 게임 개발 플랫폼. 게임 로직을 C#으로 스크립팅한다. 세상에서 C#을 쓰는 사람의 상당수가 여기 있다.
> - **UWP(유니버설 Windows 플랫폼)** — Windows 10+ 데스크톱과 Xbox·Surface Hub·HoloLens용. .NET Core 2.2 기반 CLR/BCL을 쓰며, 이 의존성이 갱신될 가능성은 낮다. Microsoft는 WinUI 3로의 전환을 권한다. 다만 WinUI 3는 Windows 데스크톱만 지원하므로, Xbox·HoloLens를 노린다면 UWP가 여전히 남아 있다.
> - **.NET Micro Framework** — 1MB 미만의 극도로 제약된 임베디드 기기용.
> - **SQL Server CLR 통합** — SQL Server 프로세스 안에서 관리 코드를 실행한다. C#으로 사용자 정의 함수·저장 프로시저·집계를 작성하고 SQL에서 호출한다. .NET Framework와, 프로세스 무결성을 지키기 위해 샌드박스를 강제하는 특수한 "호스팅" CLR이 함께 동작한다.
>
> ※ 이 외에 Godot 게임 엔진도 C# 스크립팅을 지원한다.

> **⚠️ "크로스 플랫폼"은 "모든 API가 어디서나 동작한다"가 아니다**
>
> .NET 자체는 여러 OS에서 돌지만, **BCL의 모든 API가 모든 OS에서 동작하지는 않는다.** 대표적으로 Windows 레지스트리 API, WMI, Windows 서비스 제어 관련 타입은 Linux에서 `PlatformNotSupportedException`을 던진다.
>
> 그리고 이것은 **컴파일 시점에 잡히지 않는다** — 타입도 메서드도 존재하기 때문이다. .NET SDK는 이 문제를 위해 `CA1416`(플랫폼 호환성 검증) 분석기를 기본으로 켜두고, `[SupportedOSPlatform]` 특성으로 표시된 API를 잘못된 대상에서 호출하면 경고한다. **경고를 끄지 마라.**

### C# 1.0 (2002) — 시작점

C#과 .NET 플랫폼은 2002년경에 공식 등장했다. 이 첫 버전에는 클래스·인터페이스·구조체·열거형·델리게이트, 자동 메모리 관리, 예외 처리, 그리고 속성(attribute) 기반 프로그래밍이 있었다.

이 시점의 C#은 "Java와 비슷하다"는 평을 들었다. 실제로 두 언어는 C 계열(C, Objective-C, C++)의 후손이므로 문법이 닮은 것이 당연하다. 그러나 C#은 처음부터 Visual Basic에서 프로퍼티와 선택적 매개변수를, C++에서 연산자 오버로딩·구조체·열거형·콜백(델리게이트)을 가져왔다. **여러 언어의 혼합**이라는 성격은 이때부터였다.

당시의 "Hello, World"는 이렇게 생겼다.

```csharp
using System;

namespace HelloWorld
{
    class Program
    {
        static void Main(string[] args)
        {
            Console.WriteLine("Hello, World!");
        }
    }
}
```

오늘날 `dotnet new console`이 만들어주는 것은 이렇다.

```csharp
Console.WriteLine("Hello, World!");
```

20년 사이에 사라진 것 — `using`, 네임스페이스 블록, 클래스, `Main` 메서드 — 은 **없어진 것이 아니라 컴파일러가 대신 써주게 된 것**이다. C# 9의 최상위 문(2.2절)과 C# 10의 암시적 전역 `using`(2.2절)이 그 일을 한다. 컴파일러가 실제로 무엇을 만들어내는지는 3.7절에서 확인한다.

C# 1.0이 남긴 것 중 오늘까지 그대로인 것도 있다. **속성(attribute) 기반 프로그래밍**이 그것이다. 타입과 멤버에 주석을 붙여 그 동작을 한정하는 방식이다.

```csharp
// [Obsolete]를 붙이면, 이 메서드를 쓰려는 사람에게 경고가 뜬다
[Obsolete("대신 CalculateV2를 쓸 것")]
public int Calculate(int x) => x * 2;
```

이 문법이 나중에 직렬화, 의존성 주입, 테스트 프레임워크, 소스 생성기의 기반이 된다(20장).

### C# 2.0 (2005) — 제네릭

C# 2의 큰 기능은 **제네릭**, 널 가능 값 타입, **반복자**, 익명 메서드(람다 식의 전신)였다. 부분 클래스(partial class), 정적 클래스, 네임스페이스 별칭 한정자, 프렌드 어셈블리, 고정 크기 버퍼 등도 함께 들어왔다.

제네릭이 왜 필요했는지는 그 전 코드를 보면 안다.

```csharp
// C# 1.0 시절 — 모든 것이 object였다
ArrayList list = new ArrayList();
list.Add(42);                       // int가 object로 박싱된다
int x = (int)list[0];               // 꺼낼 때 캐스트가 필요하다
list.Add("oops");                   // 아무도 막지 않는다
int y = (int)list[1];               // 런타임에 InvalidCastException

// C# 2.0 이후
List<int> numbers = new List<int>();
numbers.Add(42);                    // 박싱 없음
int z = numbers[0];                 // 캐스트 없음
numbers.Add("oops");                // 컴파일 오류 — 실행조차 되지 않는다
```

정적 타입 검사가 회복되고, 박싱이 사라지고, 캐스트가 사라졌다. 2.1절에서 말한 "정적 타입 검사가 생산성을 만든다"의 가장 선명한 사례다.

> **📌 제네릭은 런타임을 바꿔야 했다**
>
> 제네릭 도입에는 **새 CLR(CLR 2.0)이 필요했다.** 제네릭이 런타임에도 완전한 타입 충실도(type fidelity)를 유지하기 때문이다. 즉 `List<int>`는 런타임에도 진짜 "int의 리스트"이지, 컴파일 후에 `List<object>`로 지워지지 않는다.
>
> 이 설계 결정 — **실체화된(reified) 제네릭** — 이 C#의 성능 특성에서 대단히 중요하다. Java는 다른 길을 갔고(타입 소거), 그 결과 `List<int>`에 해당하는 것이 존재하지 않아 정수마다 힙 객체가 하나씩 생긴다. 왜 이것이 결정적인지는 2.7절에서 다시 본다.
>
> C# 역사에서 **언어 기능 하나 때문에 런타임을 갈아엎은 일은 이때가 사실상 유일하다.**

### C# 3.0 (2007) — LINQ

C# 3.0에 추가된 기능은 대부분 **LINQ(통합 언어 질의, Language-Integrated Query)** 를 중심으로 모인다. LINQ는 C# 프로그램 안에 직접 질의를 작성하고, 그 질의의 정합성을 **정적으로 검사**하며, 지역 컬렉션(리스트나 XML 문서)과 원격 데이터 소스(데이터베이스)를 모두 대상으로 삼는다.

LINQ를 떠받치기 위해 한꺼번에 들어온 기능들이다.

| 기능 | 역할 |
|---|---|
| 암시적 타입 지역 변수 (`var`) | 컴파일러가 타입을 추론하게 해서 익명 타입을 쓸 수 있게 한다 |
| 익명 타입 | 이름 없는 클래스를 즉석에서 만든다. 질의 결과 형태를 만들 때 쓴다 |
| 객체 초기화자 | 생성자 호출 뒤에 프로퍼티를 인라인으로 설정한다 |
| 람다 식 | 컴파일러가 즉석에서 만드는 작은 함수 |
| 확장 메서드 | 기존 타입에 메서드를 덧붙인다. LINQ 질의 연산자가 전부 확장 메서드다 |
| 쿼리 식 | `from ... where ... select` 형태의 상위 문법 |
| 식 트리 | 람다 식을 **코드가 아니라 데이터**로 표현한다. 질의를 SQL로 번역할 수 있는 이유 |

여기에 자동 프로퍼티와 부분 메서드도 추가되었다.

### C# 4.0 (2010) — 동적 바인딩과 COM

네 가지 개선이 있었다.

- **동적 바인딩** — 타입과 멤버를 해석하는 과정(바인딩)을 컴파일 시점에서 런타임으로 미룬다. 복잡한 리플렉션 코드가 필요했을 시나리오와, 동적 언어·COM 컴포넌트와의 연동에 유용하다.
- **선택적 매개변수와 명명된 인수** — 함수가 기본값을 지정해 호출자가 인자를 생략할 수 있게 하고, 인자를 위치가 아니라 이름으로 지정할 수 있게 한다.
- **가변성(variance) 규칙 완화** — 제네릭 인터페이스와 제네릭 델리게이트의 타입 매개변수를 공변(covariant)·반공변(contravariant)으로 표시할 수 있게 되어, 더 자연스러운 타입 변환이 가능해졌다.
- **COM 상호운용 개선** — `ref` 없이 참조로 인자를 넘길 수 있고, COM 상호 운용 타입을 참조가 아니라 **포함**할 수 있게 되었으며(주 상호 운용 어셈블리(PIA)가 불필요해졌다), COM Variant를 반환하는 함수가 `object`가 아니라 `dynamic`으로 매핑되어 캐스트가 필요 없어졌다.

### C# 5.0 (2012) — `async` / `await`

C# 5.0의 큰 기능은 딱 하나였다. `async`와 `await` 두 키워드를 통한 **비동기 함수** 지원이다.

비동기 함수는 비동기 연속(continuation)을 가능하게 하는데, 이것이 두 가지를 준다. 첫째, 반응성 있고 스레드 안전한 리치 클라이언트 애플리케이션을 쓰기 쉬워진다. 둘째, 연산 하나당 스레드 하나를 묶어두지 않는 고도로 동시적이고 효율적인 I/O 중심 애플리케이션을 쉽게 만들 수 있다.

```csharp
// 동기 코드처럼 읽히지만 스레드를 붙잡고 있지 않다
async Task<string> FetchTitleAsync(string url)
{
    using var client = new HttpClient();
    string html = await client.GetStringAsync(url);
    return ExtractTitle(html);
}
```

이 두 키워드가 컴파일 후 무엇으로 바뀌는지 — **상태 기계** — 는 이 책에서 가장 긴 설명이 필요한 주제 중 하나다. 문법과 컴파일 결과, 런타임 동작 모두 47장에서 다룬다.

### C# 6.0 (2015) — Roslyn과 상용구 제거

C# 6.0에는 **완전히 C#으로 새로 작성된 차세대 컴파일러**가 함께 왔다. 코드명 "Roslyn"이라고 부른다. 이 컴파일러는 컴파일 파이프라인 전체를 라이브러리로 노출해서, 임의의 소스 코드에 대해 코드 분석을 수행할 수 있게 했다. 컴파일러 자체가 오픈 소스이고 소스는 `github.com/dotnet/roslyn`에 있다.

언어 기능은 대부분 **코드 잡음을 줄이는** 작지만 유의미한 개선이었다.

```csharp
// null 조건 연산자 — 명시적 null 검사 없이 안전하게 접근
StringBuilder sb = null;
string result = sb?.ToString();          // 예외 대신 null

// 식 본문 멤버
public int TimesTwo(int x) => x * 2;
public string SomeProperty => "Property value";

// 프로퍼티 초기화자
public DateTime TimeCreated { get; } = DateTime.Now;

// 보간 문자열
string s = $"It is {DateTime.Now.DayOfWeek} today";

// nameof — 심볼 이름을 문자열로. 이름을 바꿔도 깨지지 않는다
string x = nameof(capacity);             // "capacity"
```

여기에 인덱스 초기화자, 예외 필터(`catch (...) when (...)`), `using static`이 추가되었고, `catch`와 `finally` 블록 안에서 `await`할 수 있게 되었다.

> **📌 Roslyn이 바꾼 것**
>
> 컴파일러를 라이브러리로 만든 결정은 언어 기능 하나보다 훨씬 큰 영향을 남겼다. 오늘날 우리가 쓰는 코드 분석기, 자동 코드 수정, 소스 생성기(source generator), 그리고 이 책이 계속 쓰라고 권하는 SharpLab 같은 도구가 전부 이 위에 서 있다.

### C# 7.x (2017~2018) — 튜플, 패턴, 그리고 저할당

C# 7.0의 가장 눈에 띄는 개선은 **튜플**이었다. 함수가 `out` 매개변수나 별도의 타입 없이 여러 값을 반환할 수 있게 되었다.

```csharp
static (int row, int column) GetFilePosition() => (3, 10);

var pos = GetFilePosition();
Console.WriteLine(pos.row);              // 3

// 분해(deconstruction)
(int row, int column) = GetFilePosition();
```

여기에 **패턴 매칭**의 시작(`is` 연산자의 타입 패턴, `switch`의 타입 패턴), 지역 함수, `throw` 식, 숫자 리터럴의 자릿수 구분자(`1_000_000`)와 이진 리터럴(`0b1010`), `out` 변수 인라인 선언과 무시 항목(`_`), 분해자(deconstructor)가 들어왔다.

7.1은 `default` 리터럴의 타입 생략, 비동기 `Main`, 튜플 요소 이름 추론을 더했다. 7.2는 `private protected` 접근 한정자, 위치 인자 뒤에 명명 인자 허용, 그리고 **`readonly struct`, `in` 한정자, `ref` 지역/반환, `ref struct`** 같은 저할당 프로그래밍 기능을 넣었다. 7.3은 `ref` 지역 변수 재할당과 `stackalloc` 필드 초기화자 지원 등으로 그 위를 다졌다.

C# 7.2의 저할당 기능들은 당장 이해할 필요가 없다. **다만 이 시점부터 C#이 "고수준 언어이면서 동시에 메모리를 직접 통제할 수 있는 언어"로 방향을 잡았다**는 것만 기억하면 된다. 자세히는 68~69장에서 다룬다.

### C# 8.0 (2019) — 널 가능 참조 타입

가장 큰 변화는 **널 가능 참조 타입**이다. 널 가능 값 타입이 값 타입에 널 허용성을 준 것이라면, 널 가능 참조 타입은 정반대로 참조 타입에 **(어느 정도의) 널 비허용성**을 준다. 목적은 `NullReferenceException`을 피하는 것이다.

```csharp
#nullable enable

string s1 = null;      // 컴파일러 경고 — s1은 널 불가
string? s2 = null;     // OK — s2는 널 가능 참조 타입
```

이 외에 인덱스와 범위(`^1`, `..`), null 병합 할당(`??=`), `using` 선언, 읽기 전용 멤버, 정적 지역 메서드, **기본 인터페이스 멤버**, **`switch` 식**, 튜플·위치·프로퍼티 패턴, **비동기 스트림**(`IAsyncEnumerable<T>`와 `await foreach`)이 들어왔다.

### C# 9.0 (2020) — 레코드와 최상위 문

```csharp
// 최상위 문 — Main 메서드와 Program 클래스가 없어도 된다
using System;
Console.WriteLine("Hello, world");
```

**최상위 문(top-level statements)** 은 오늘날 `dotnet new console`로 만든 프로젝트가 한 줄짜리인 이유다. 3.7절에서 컴파일러가 실제로 무엇을 만들어내는지 확인한다.

**레코드**는 불변 데이터를 잘 다루도록 설계된 특수한 클래스다. 가장 특별한 기능은 `with` 키워드를 통한 **비파괴적 변경**이다.

```csharp
record Point(double X, double Y);

Point p1 = new Point(2, 3);
Point p2 = p1 with { Y = 4 };            // p1의 복사본에서 Y만 바꾼 것
Console.WriteLine(p2);                   // Point { X = 2, Y = 4 }
```

여기에 `init` 전용 설정자, 관계 패턴(`< 25m =>`)과 패턴 결합자(`and`, `or`, `not`), 대상 타입 지정 `new`(`StringBuilder sb = new();`), 공변 반환 타입, 정적 람다, 함수 포인터, `nint`/`nuint`가 추가되었다.

### C# 10 (2021) — 파일 단위 잡음 제거

```csharp
// 파일 범위 네임스페이스 — 중괄호와 들여쓰기 한 단계가 사라진다
namespace MyNamespace;

class Class1 {}
class Class2 {}
```

```csharp
// 전역 using — 프로젝트의 모든 파일에 적용된다
global using System;
global using System.Collections.Generic;
```

.NET 6 프로젝트는 여기에 더해 **암시적 전역 using**을 지원한다. 프로젝트 파일의 `ImplicitUsings`가 `true`면 SDK 종류에 맞는 흔한 네임스페이스가 자동으로 임포트된다. 4.6절에서 정확히 어떤 네임스페이스가 들어오는지 본다.

이 외에 익명 타입의 `with`, 구조체의 필드 초기화자와 매개변수 없는 생성자, **레코드 구조체**(`record struct`), 람다 식 개선(암시적 타입, 반환 타입 지정, 특성 적용), 중첩 프로퍼티 패턴 단순화, `CallerArgumentExpression`이 들어왔다.

### C# 11 (2022) — 원시 문자열과 제네릭 수학

```csharp
// 원시 문자열 리터럴 — 이스케이프 없이 그대로
string raw = """<file path="c:\temp\test.txt"></file>""";
```

```csharp
// 목록 패턴
int[] numbers = { 0, 1, 2, 3, 4 };
Console.WriteLine(numbers is [0, 1, 2, 3, 4]);      // True
Console.WriteLine(numbers is [_, 1, .., 4]);        // True
```

`required` 멤버, **정적 가상/추상 인터페이스 멤버**, 그리고 그 위에 세워진 **제네릭 수학**(`System.Numerics.INumber<TSelf>`), UTF-8 문자열 리터럴(`"..."u8`), `file` 접근 한정자, 체크된 연산자가 들어왔다.

제네릭 수학은 "모든 숫자 타입에 대해 하나의 제네릭 메서드를 쓸 수 있다"는 오랜 숙원을 풀었다.

```csharp
T Sum<T>(T[] numbers) where T : INumber<T>
{
    T total = T.Zero;
    foreach (T n in numbers)
        total += n;
    return total;
}
```

### C# 12 (2023) — 이 책의 기준선

C# 12는 Visual Studio 2022와 함께 배포되고, **.NET 8을 대상으로 할 때 기본으로 사용된다.** 이 책의 기준 버전이다.

```csharp
// 컬렉션 식 — 하나의 문법이 여러 컬렉션 타입에 통한다
char[] vowels = ['a','e','i','o','u'];
List<char> list = ['a','e','i','o','u'];
HashSet<char> set = ['a','e','i','o','u'];
```

```csharp
// 클래스·구조체의 기본 생성자
class Person(string firstName, string lastName)
{
    public void Print() => Console.WriteLine(firstName + " " + lastName);
}
```

여기에 람다의 기본 매개변수 값, 모든 타입에 대한 `using` 별칭(배열·튜플 포함), 그리고 `[InlineArray]` 특성을 통한 인라인 배열이 들어왔다.

> **⚠️ 레코드의 기본 생성자와 클래스의 기본 생성자는 다르게 동작한다**
>
> 기본 생성자 문법 자체는 C# 9의 레코드에서 먼저 나왔지만, 동작이 다르다. **레코드**에서는 컴파일러가 기본 생성자 매개변수마다 `public init` 전용 프로퍼티를 (기본적으로) 생성한다. **클래스와 구조체**에서는 그렇지 않다 — 매개변수는 생성자 매개변수일 뿐이고, 프로퍼티가 필요하면 직접 선언해야 한다.
>
> ```csharp
> class Person(string firstName, string lastName)
> {
>     public string FirstName { get; set; } = firstName;
>     public string LastName { get; set; } = lastName;
> }
> ```
>
> 같은 문법이 타입 종류에 따라 다르게 동작하는 몇 안 되는 경우다. 클래스의 기본 생성자는 13장에서, 레코드의 것은 19장에서 다룬다.

### C# 13 (2024) 이후

C# 13은 .NET 9와 함께 나왔다. `params` 한정자를 배열 외의 컬렉션 타입(`Span<T>`, `List<T>` 등)에도 쓸 수 있게 되었고, 전용 잠금 타입 `System.Threading.Lock`이 도입되었으며, 제네릭 제약에 `allows ref struct`가 추가되어 `ref struct`를 타입 인자로 넘길 수 있게 되었다. 부분(partial) 프로퍼티와 인덱서도 이때 들어왔다.

※ C# 13 이후로도 언어는 계속 나아가고 있다. **각 버전의 기능을 전수 조사한 지도는 76장에 있다.** 이 장에서는 흐름만 잡으면 된다.

> **⚠️ 언어 버전과 런타임 버전은 같은 것이 아니다**
>
> 흔한 혼동이다. **C# 12는 언어 버전이고 .NET 8은 런타임 버전이다.** 둘은 짝이 맞춰져 배포되지만 같은 것이 아니다.
>
> 대상 프레임워크를 `net8.0`으로 지정하면 C# 12가 기본으로 선택된다. 프로젝트 파일의 `LangVersion`으로 이를 덮어쓸 수도 있다 — 하지만 **런타임 지원이 필요한 기능은 그렇게 해도 쓸 수 없다.** 예를 들어 제네릭 수학은 .NET 7 이상의 BCL이 `INumber<TSelf>`를 제공해야만 성립한다.
>
> .NET Framework 4.8을 대상으로 하면 기본은 C# 7.3이다. `LangVersion`을 올리면 **런타임 지원이 필요 없는** 최신 기능 대부분을 쓸 수 있다. 자세히는 4.5절과 76.13절에서 다룬다.

> **💡 버전 역사를 외울 필요는 없다. 단, 두 상황에서는 필요하다**
>
> 첫째, **멀티 타깃팅**할 때. 하나의 라이브러리가 `net8.0`과 `netstandard2.0`을 동시에 대상으로 한다면, 후자에서 쓸 수 없는 문법을 알아야 한다.
>
> 둘째, **레거시 코드를 읽을 때.** 2010년에 쓰인 코드가 `ArrayList`와 델리게이트 명시 생성으로 가득한 것은 그때는 그것밖에 없었기 때문이지, 그 사람이 게을러서가 아니다. 코드의 나이를 읽을 줄 알면 무엇을 먼저 고칠지 판단이 선다.

### 1단계 — 갈라짐 (2001~2015)

**.NET Framework 1.0(2002)** 은 Microsoft의 원래 런타임이었다. 웹과 리치 클라이언트 애플리케이션을 만들되, **Windows 데스크톱·서버에서만** 돌았다. 이 런타임은 Windows에 미리 설치되고 Windows Update로 자동 패치된다.

여기서 결정적인 성질이 하나 있다. .NET Framework에서는 **CLR/BCL이 애플리케이션 계층과 통합되어 있다.** 즉 런타임과 프레임워크와 UI 스택이 하나의 묶음으로 머신 전체에 설치된다. 그래서 애플리케이션이 런타임 버전을 고를 여지가 거의 없었고, 런타임 하나를 고치면 그 머신의 모든 애플리케이션에 영향을 줬다.

한편 Microsoft는 CTS, 파일 형식, 메타데이터, IL, 그리고 기반 플랫폼 접근(P/Invoke)을 **ECMA에 표준화**로 제출했다. 그 표준이 **공용 언어 기반구조(CLI, Common Language Infrastructure)** 이고 **ECMA-335** 규격이다. C# 언어 자체도 **ECMA-334**로 제출되었다. 이것이 사실상 제3자 구현의 문을 열었다.

그 문으로 들어온 것이 **Mono**다. 2001년 시작되어 2004년 1.0이 나왔고, .NET Framework가 가지 못한 Linux와 macOS에서 .NET 코드를 실행했다. Mono는 뒤에 Xamarin의 기반이 되어 iOS와 Android로 갔고, 2016년 Microsoft가 Xamarin을 인수하면서 다시 본가로 돌아왔다.

**왜 갈라졌는가?** 답은 명확하다. **표준은 공개되었지만 구현은 Windows 전용이었기 때문이다.** Windows 밖에서 C#을 쓰고 싶은 사람들은 스스로 구현을 만드는 수밖에 없었다.

여기에 Silverlight, .NET Compact Framework, Windows Phone용 런타임 같은 파생이 더해지면서, 2015년 무렵의 .NET 생태계는 **서로 API 집합이 다른 런타임 대여섯 개**로 파편화되어 있었다.

### 2단계 — 다시 만듦 (2016~2019)

2016년 Microsoft는 **.NET Core**를 공식 출시했다. .NET Framework의 개선판이 아니라 **처음부터 다시 쓴 런타임**이었다. 목표는 세 가지였다.

- **크로스 플랫폼** — Windows뿐 아니라 Linux와 macOS에서 개발하고 실행한다.
- **병행 설치(side-by-side)** — 런타임이 머신 전체가 아니라 **애플리케이션 단위**로 결정된다. 앱마다 다른 .NET 버전을 쓸 수 있다.
- **오픈 소스** — 개발이 GitHub에서 공개적으로 이뤄진다.

여기에 컨테이너와 클라우드를 겨냥한 성능 개선이 따라붙었다.

문제는 **기존 코드와의 다리**였다. .NET Framework에 있는 BCL의 수가 .NET Core보다 압도적으로 많았다(14년의 격차였으니 당연하다). 이 차이 때문에 .NET Framework 코드를 .NET Core 코드와 함께 쓰기가 어려웠다.

그 해법이 **.NET Standard**다. .NET Standard는 **각 구현이 반드시 제공해야 하는 .NET API와 BCL의 집합을 정의한 사양**이다. 라이브러리를 `netstandard2.0`으로 만들면 .NET Framework 4.6.1 이상과 .NET Core 2.0 이상 양쪽에서 쓸 수 있었다.

> **⚠️ .NET Standard는 라이브러리를 위한 것이지 애플리케이션을 위한 것이 아니다**
>
> .NET Standard는 **구현이 아니라 사양**이다. `netstandard2.0`을 대상으로 하는 프로젝트는 실행되지 않는다 — 실행하려면 그 사양을 구현한 런타임 위에서 돌아야 한다.
>
> 그리고 .NET Standard 2.1(2019)은 **.NET Framework가 지원하지 않는다.** 즉 .NET Standard가 놓으려던 다리는 2.0에서 사실상 끊겼다. 오늘 새 프로젝트를 시작한다면 `netstandard2.0`은 "아직 .NET Framework를 쓰는 소비자를 지원해야 하는 라이브러리"에서만 고려하면 된다. 자세히는 4.3절에서 다룬다.

### 3단계 — 합침 (2020~)

2020년 11월, **.NET 5**가 나오면서 이름에서 "Core"가 빠졌다. 그리고 두 줄기가 하나로 합쳐졌다 — .NET Framework의 기능 자산과 Mono/Xamarin의 플랫폼 자산이 단일 노선으로 모였다.

**왜 합쳤는가?**

1. **두 벌의 코드베이스를 유지하는 비용이 감당되지 않았다.** 같은 기능을 두 번 구현하고 두 번 테스트해야 했다.
2. **.NET Standard라는 다리가 근본 해법이 아니었다.** 사양이 하나 더 늘어나면 배워야 할 것이 하나 더 느는 것이다.
3. **개발자가 "어떤 .NET을 써야 하나"를 매번 판단해야 했다.** 이 판단 비용 자체가 생태계의 손실이었다.

> **📌 왜 4를 건너뛰었나**
>
> .NET Core 3 다음이 .NET 5인 이유는, **.NET Framework 4.x와의 혼동을 피하기 위해서**다. ".NET 4"라고 하면 그것이 새 노선의 4인지 .NET Framework 4인지 알 수 없다. 버전 번호 하나를 버리는 대가로 20년치 혼란 하나를 줄인 셈이다.
>
> .NET의 갱신 역사는 이렇게 이어진다: .NET Core 1.x → .NET Core 2.x → .NET Core 3.x → .NET 5 → .NET 6 → .NET 7 → .NET 8 → .NET 9.

### 지금 남아 있는 것들

통합이 끝난 지금, 현장에서 만나게 되는 .NET 기술은 사실상 셋으로 정리된다.

| 기술 | 성격 | 지원 호스트 OS |

> **⚠️ 메이저 버전만 맞추면 되는 것이 아니다**
>
> 지원을 받으려면 **패치 릴리스도 따라가야 한다.** .NET 8.0.0을 쓰는 시스템에 8.0.1이 나왔다면, 8.0.1을 설치해야 지원 대상이다. 이 업데이트는 매월 둘째 화요일(Patch Tuesday)에 나온다.
>
> 실무에서 "우리는 .NET 8이니까 지원 대상"이라고 믿었다가 보안 감사에서 걸리는 경우가 이 지점이다.

> **⚠️ .NET Framework 어셈블리는 .NET에서 그대로 돌지 않는다**
>
> .NET Core 1.x부터 .NET 7까지 컴파일한 어셈블리는 **대부분 수정 없이** .NET 8에서 실행된다. 그러나 **.NET Framework의 어느 버전으로 컴파일한 어셈블리든 .NET 8과는 대체로 호환되지 않는다.**
>
> .NET Framework로 작성한 애플리케이션을 .NET에서 다시 컴파일할 수는 있지만, 보통 수정이 필요하다. .NET Framework에만 있고 .NET에 없는 기능이 있고, 그 반대도 있기 때문이다. 대표적으로 AppDomain, 원격(Remoting), GAC, `BinaryFormatter`, 코드 접근 보안(CAS)은 .NET에 없다.

> **⚠️ .NET은 Windows에 미리 설치되어 있지 않다**
>
> .NET Framework와 달리 .NET 8은 Windows에 기본 설치되지 않는다. 올바른 런타임 없이 .NET 8 애플리케이션을 실행하려 하면, 런타임을 내려받을 웹 페이지로 안내하는 메시지가 뜬다.
>
> 이것을 피하는 방법이 **자체 포함(self-contained) 배포**다 — 애플리케이션이 필요로 하는 런타임 부분을 함께 담아 배포한다. 배포 형태의 선택지는 4.9절에서 다룬다.

> **⚠️ ".NET"이라는 단어 자체가 중의적이다**
>
> 오랫동안 ".NET"은 이름에 ".NET"이 들어간 모든 기술을 뭉뚱그리는 우산 용어였다(.NET Framework, .NET Core, .NET Standard 등). 여기에 .NET Core를 .NET으로 개명한 일이 겹치면서 모호함이 생겼다.
>
> **이 책의 규약은 이렇다.**
>
> - **.NET** — 통합 이후의 현행 런타임 (5, 6, 7, 8, 9…)
> - **.NET Framework** — Windows 전용 레거시 런타임 (1.0~4.8). **줄여 쓰지 않고 항상 전체 이름을 쓴다.**
> - **.NET Core** — 2016~2019의 그 런타임 (1.0~3.1)
> - 애매할 때는 **.NET 5+** 로 쓴다.
>
> 그리고 .NET(5+)은 프레임워크이면서 .NET Framework와는 전혀 다르다. 그래서 이 책은 가능한 한 "프레임워크"보다 **"런타임"** 이라는 말을 쓴다.

> **💡 지금 새로 시작한다면**
>
> 새 프로젝트라면 **최신 LTS**를 골라라. 이 책 기준으로는 .NET 8이다. 그리고 다음 LTS가 나오면 1년 안에 올려라 — 그것이 이전 LTS의 수명이 끝나기 전까지 주어지는 시간이다.
>
> .NET Framework를 새로 선택할 이유는 하나뿐이다: **.NET에 이식되지 않은 의존성이 있는데 그 의존성을 바꿀 수 없을 때.** 그 외에는 없다.

## 2.4 CLR, BCL, 런타임, SDK의 역할 분담

앞 절에서 ".NET"이라는 이름의 혼란을 정리했다. 이 절은 그 안쪽의 구조를 정리한다. 여기서 나오는 네 단어 — CLR, BCL, 런타임, SDK — 는 서로 포함 관계에 있고, 그 관계를 헷갈리면 4장 이후의 모든 설명이 흐려진다.

### 전체 그림

각 층의 책임을 표로 정리하면 이렇다.

| 층 | 책임 | 대표 산출물 | 자세히는 |
|---|---|---|---|
| **CLR** | IL을 네이티브로 바꾸고, 메모리를 관리하고, 예외를 전달하고, 타입을 로드한다 | `coreclr.dll` / `libcoreclr.so` | 52~60장 |
| **BCL** | 어느 애플리케이션에나 필요한 공통 기능을 타입으로 제공한다 | `System.Runtime.dll` 외 수백 개 어셈블리 | 5장 |
| **애플리케이션 계층** | 특정 종류의 앱(웹·데스크톱·모바일)에 필요한 것을 얹는다 | ASP.NET Core, WPF, MAUI | 5.9절 |
| **런타임** | 위 셋을 묶은 **배포 단위**. 사용자 머신에 설치된다 | .NET Runtime, .NET Desktop Runtime | 4.9절 |
| **SDK** | 런타임 + 코드를 만들고 빌드하고 배포하는 도구 전부 | .NET SDK | 4.1절 |

### CLR — 공용 언어 런타임

**공용 언어 런타임(CLR, Common Language Runtime)** 은 자동 메모리 관리와 예외 처리 같은 필수 런타임 서비스를 제공한다.

이름의 "공용(common)"은 **같은 런타임을 다른 관리 언어들이 공유한다**는 사실을 가리킨다 — F#, Visual Basic, 관리 C++ 같은 것들. 이 사실이 왜 중요한지는 2.5절에서 다룬다.

C#을 **관리 언어(managed language)** 라고 부르는 이유는, 소스 코드를 **중간 언어(IL, Intermediate Language)** 로 표현되는 **관리 코드(managed code)** 로 컴파일하기 때문이다. CLR은 이 IL을 x64나 x86 같은 머신의 네이티브 코드로 바꾼다 — 보통 **실행 직전에**. 이것을 **JIT(Just-In-Time) 컴파일**이라고 한다.

큰 어셈블리의 시작 시간을 개선하거나 자원이 제한된 기기를 대상으로 할 때는(그리고 모바일 앱에서 iOS 앱스토어 규칙을 만족시키려면) **사전 컴파일(AOT, Ahead-Of-Time)** 도 쓸 수 있다.

관리 코드를 담는 컨테이너는 **어셈블리(assembly)** 다. 어셈블리에는 IL뿐 아니라 **타입 정보(메타데이터)** 도 들어 있다. 메타데이터가 있기 때문에, 어셈블리는 추가 파일 없이도 다른 어셈블리의 타입을 참조할 수 있다.

프로그램은 자기 자신의 메타데이터를 조회할 수도 있고(**리플렉션**), 런타임에 새 IL을 생성할 수도 있다(**리플렉션 이밋**).

> **📌 CLR은 하나가 아니다**
>
> 오늘날 .NET에서 쓰는 CLR 구현은 **CoreCLR**이다. 그러나 유일한 구현은 아니다.
>
> - **CoreCLR** — 서버·데스크톱·콘솔의 기본 구현. JIT 컴파일러 이름은 RyuJIT다.
> - **Mono 런타임** — MAUI의 iOS/Android 대상, Blazor WebAssembly에서 쓰인다.
> - **Native AOT** — 애플리케이션을 미리 네이티브로 컴파일하고 필요한 런타임 조각만 정적으로 링크한다. JIT이 없다.
>
> 같은 C# 소스가 어느 런타임 위에서 도는지에 따라 성능 특성과 사용 가능한 기능이 달라진다. 자세히는 55.7절과 4.9절에서 다룬다. **지금은 "CLR이라는 자리에 들어가는 구현이 여럿 있다"만 알면 된다.**

### BCL — 기본 클래스 라이브러리

CLR은 항상 **기본 클래스 라이브러리(BCL, Base Class Library)** 라고 부르는 어셈블리 집합과 함께 배포된다.

BCL이 제공하는 것은 두 종류다.

1. **프로그래머를 위한 핵심 기능** — 컬렉션, 입출력, 텍스트 처리, XML/JSON 처리, 네트워킹, 암호화, 상호운용, 동시성, 병렬 프로그래밍.
2. **C# 언어 자체가 요구하는 타입** — 열거, 질의, 비동기 같은 기능은 특정 타입이 존재해야만 성립한다. 그리고 리플렉션이나 메모리 관리처럼 CLR의 기능에 명시적으로 접근하는 통로도 BCL이 제공한다.

두 번째가 중요하다. **`foreach` 문은 `IEnumerable<T>`가 없으면 성립하지 않고, `async`/`await`는 `Task`가 없으면 성립하지 않는다.** 언어와 라이브러리가 서로를 필요로 하는 것이다.

BCL의 타입은 **네임스페이스**로 묶여 있다. 전체 지도는 5장에 있지만, 이름만 미리 보면 감이 온다.

| 네임스페이스 | 무엇이 들어 있나 |
|---|---|
| `System` | 모든 애플리케이션이 쓰는 기본 타입. `Object`, `Int32`, `String`, 예외, 수학 함수 |
| `System.Collections.Generic` | `List<T>`, `Dictionary<TKey,TValue>` 같은 컬렉션 |
| `System.IO` | 스트림 입출력, 디렉터리·파일 탐색 |
| `System.Net.Http` | HTTP 클라이언트 |
| `System.Text` / `System.Text.Json` | 인코딩, 문자열 빌더, JSON |
| `System.Linq` | LINQ 질의 연산자 |
| `System.Threading` / `System.Threading.Tasks` | 스레드, 동기화, `Task` |
| `System.Reflection` | 런타임 타입 탐색 |
| `System.Runtime.InteropServices` | 관리 코드가 비관리 OS 기능(COM, Win32 함수, 사용자 DLL)에 접근하는 통로 |
| `System.Security.Cryptography` | 암호화 |

> **📌 FCL과 BCL**
>
> .NET Framework 시절에는 이 라이브러리 묶음을 **FCL(Framework Class Library)** 이라고 불렀다. 오늘날 .NET 문서와 이 책은 **BCL**이라는 말을 쓴다. 오래된 문서에서 FCL을 만나면 같은 것을 가리킨다고 생각하면 된다.
>
> 그리고 BCL의 타입 수는 수천 개다. 전부 외우는 사람은 없다. 필요한 것은 **"이 기능은 어느 네임스페이스에 있을 것 같은가"를 짐작하는 감각**이고, 그 감각을 만드는 것이 5장의 목적이다.

### 런타임 — 배포 단위

**런타임(runtime, 프레임워크라고도 한다)** 은 **내려받아 설치하는 배포 단위**다. 런타임은 CLR(과 그 BCL)에 더해, 만들려는 애플리케이션 종류에 특화된 **선택적 애플리케이션 계층**으로 이뤄진다 — 웹, 모바일, 리치 클라이언트 등. 명령행 콘솔 애플리케이션이나 UI 없는 라이브러리를 쓴다면 애플리케이션 계층은 필요 없다.

애플리케이션을 작성할 때는 **특정 런타임을 대상(target)으로** 삼는다. 그 런타임이 제공하는 기능에 의존하겠다는 선언이다. 그리고 **런타임 선택이 곧 지원 플랫폼 선택**이다.

### SDK — 개발자가 설치하는 것

**.NET SDK**는 .NET 런타임에 더해, .NET 코드와 앱을 빌드하는 데 필요한 컴파일러와 도구를 포함한다.

즉 이렇게 정리된다.

- **사용자 머신에 필요한 것** = 런타임 (자체 포함 배포라면 이것도 필요 없다)
- **개발자 머신에 필요한 것** = SDK

```bash
# 설치된 SDK와 런타임을 확인한다
dotnet --list-sdks
dotnet --list-runtimes

# 둘 다와 환경 정보를 한꺼번에
dotnet --info
```

상황별로 무엇을 설치해야 하는지 정리하면 이렇다.

| 상황 | 필요한 것 | 이유 |
|---|---|---|
| C# 코드를 작성하고 빌드한다 | **.NET SDK** | 컴파일러와 빌드 도구가 필요하다 |
| 남이 만든 .NET 앱을 실행만 한다 | **.NET Runtime** | 실행에는 컴파일러가 필요 없다 |
| WinForms·WPF 앱을 실행한다 | **.NET Desktop Runtime** | 데스크톱 애플리케이션 계층이 추가로 필요하다 |
| ASP.NET Core 앱을 호스팅한다 | **ASP.NET Core Runtime** | 웹 애플리케이션 계층이 추가로 필요하다 |
| 자체 포함으로 배포된 앱을 실행한다 | **아무것도 필요 없다** | 런타임이 앱과 함께 배포되었다 |

SDK를 설치하면 그에 맞는 런타임이 함께 들어온다. 그래서 개발 머신에는 SDK 하나만 설치하면 되고, `dotnet --list-runtimes`에 런타임이 여러 개 보이는 것이 정상이다.

버전 규칙에도 함정이 있다.

**.NET 런타임의 버전은 유의적 버전(semantic versioning)을 따른다.** 메이저 증가는 호환성 깨짐, 마이너 증가는 새 기능, 패치 증가는 버그 수정을 뜻한다.

**.NET SDK의 버전은 유의적 버전을 따르지 않는다.** 메이저·마이너 번호는 짝이 되는 런타임 버전에 묶이고, **세 번째 숫자**는 별도의 규칙을 따른다 — SDK의 마이너 번호에 100을 곱하고 패치 번호를 더한다.

| 변경 내용 | 런타임 | SDK |
|---|---|---|
| 최초 릴리스 | 8.0.0 | 8.0.100 |
| SDK 버그 수정 | 8.0.0 | 8.0.101 |
| 런타임과 SDK 버그 수정 | 8.0.1 | 8.0.102 |
| SDK 새 기능 | 8.0.1 | 8.0.200 |

> **⚠️ SDK 버전 8.0.200이 8.0.101보다 크다**
>
> 위 규칙 때문에 SDK 버전을 단순 비교하면 오해하기 쉽다. `8.0.200`은 "SDK의 마이너 2, 패치 0"이지 "패치 200"이 아니다. CI 스크립트에서 SDK 버전을 문자열로 비교하다가 사고가 나는 지점이다.

> **⚠️ 최신 SDK 하나로 옛 런타임을 대상으로 빌드할 수 있다**
>
> .NET SDK의 새 릴리스는 **이전 버전 런타임을 대상으로 하는 빌드 능력을 유지한다.** 즉 .NET 9 SDK 하나로 `net8.0` 프로젝트를 빌드할 수 있다. 그래서 오래된 SDK를 안전하게 지울 수 있다.
>
> 반대는 성립하지 않는다. .NET 8 SDK로 `net9.0`을 대상으로 할 수는 없다. 그리고 **런타임 업데이트는 같은 메이저 버전 안에서만 호환**된다(8.x 안에서만).

> **📌 C# 언어는 이 그림 어디에도 없다**
>
> 그림 2-2를 다시 보면 이상한 점이 있다. CLR, BCL, 애플리케이션 계층, SDK는 있는데 **C#이라는 상자가 없다.**
>
> 맞다. **C#은 실행되는 물건이 아니라 사양(specification)이다.** 그 사양을 구현하는 것은 SDK 안의 Roslyn 컴파일러이고, 컴파일러가 만든 결과물(IL)만이 CLR에 도달한다. **CLR은 C#을 모른다.** IL과 메타데이터만 안다.
>
> 이 사실이 실무에서 갖는 의미는 크다. "C#에는 없지만 IL에는 있는 것"이 존재하고(2.5절), "C# 문법이 IL로 어떻게 번역되는가"가 성능을 좌우한다(이 책의 4단 원칙 2단). 그래서 이 책은 계속 IL을 본다.

## 2.5 CTS와 CLS — 다중 언어 플랫폼의 계약

### 왜 다중 언어 플랫폼이 필요했는가

2002년의 상황을 상상해보자. 회사 안에 Visual Basic 6로 만든 업무 앱이 있고, C++로 만든 계산 엔진이 있고, Delphi로 만든 도구가 있다. 이들을 연결하는 유일한 방법은 **COM**이었다.

COM은 서로 다른 언어로 만든 **객체가 통신**하게 해줬다. 그러나 거기까지였다. C++ 클래스를 Visual Basic에서 **상속**할 수는 없었고, 한 언어에서 던진 예외를 다른 언어에서 **잡을** 수 없었고, 두 언어를 넘나들며 **디버깅**할 수 없었다.

CLR은 여기서 한 걸음 더 나갔다. **모든 언어를 통합해서, 한 언어로 만든 객체를 완전히 다른 언어로 쓴 코드가 동등한 시민으로 다룰 수 있게** 했다. 크로스 언어 상속, 크로스 언어 예외 처리, 크로스 언어 디버깅이 가능해졌다. C#에서 기반 클래스를 정의하고 Visual Basic에서 확장할 수 있다.

이 통합이 가능한 이유는 CLR이 **표준 타입 집합, 메타데이터(자기 설명적 타입 정보), 공통 실행 환경**을 갖기 때문이다. 그중 "표준 타입 집합"의 형식 규격이 **CTS**이고, "모든 언어가 최소한 이만큼은 지원해야 한다"는 하한선이 **CLS**다.

### CTS — 공용 타입 시스템

CLR은 결국 **타입**에 관한 것이다. 타입이 애플리케이션과 다른 타입에 기능을 노출하고, 타입이야말로 한 언어로 쓴 코드가 다른 언어로 쓴 코드와 대화하는 메커니즘이다. 타입이 CLR의 뿌리이므로, Microsoft는 **타입이 어떻게 정의되고 어떻게 행동하는지를 기술하는 형식 규격**을 만들었다. 그것이 **공용 타입 시스템(CTS, Common Type System)** 이다.

#### CTS가 정하는 것 (1) — 멤버의 종류

CTS 규격은 타입이 0개 이상의 멤버를 가질 수 있다고 말한다. 멤버는 네 종류다.

| 멤버 | 정의 |
|---|---|
| **필드(field)** | 객체 상태의 일부인 데이터 변수. 이름과 타입으로 식별된다 |
| **메서드(method)** | 객체에 대해 연산을 수행하는 함수. 대개 객체 상태를 바꾼다. 이름·시그니처·한정자를 갖는다. 시그니처는 매개변수의 개수와 순서, 타입, 반환 여부와 반환 타입을 지정한다 |
| **프로퍼티(property)** | 호출자에게는 필드처럼 보이지만 구현자에게는 메서드(또는 두 개)로 보인다. 값에 접근하기 전 입력과 객체 상태를 검증하거나 필요할 때만 값을 계산할 수 있게 하고, 읽기 전용·쓰기 전용 "필드"를 만들 수 있게 한다 |
| **이벤트(event)** | 객체와 관심 있는 다른 객체 사이의 알림 메커니즘. 예를 들어 버튼은 클릭되었을 때 다른 객체에 알리는 이벤트를 제공할 수 있다 |

#### CTS가 정하는 것 (2) — 가시성과 접근성

CTS는 타입의 가시성과 타입 멤버 접근 규칙도 정한다. 타입을 `public`으로 표시하면 어느 어셈블리에서나 보이고 접근할 수 있다. `assembly`(C#에서는 `internal`)로 표시하면 같은 어셈블리 안의 코드에서만 보이고 접근할 수 있다. **즉 CTS가 "어셈블리는 타입 가시성의 경계"라는 규칙을 세우고, CLR이 그 규칙을 강제한다.**

멤버 수준의 접근 제어는 여섯 가지다.

| CTS 이름 | C# 키워드 | 의미 |
|---|---|---|
| Private | `private` | 같은 클래스 타입의 다른 멤버만 접근 가능 |
| Family | `protected` | 같은 어셈블리인지와 무관하게 파생 타입이 접근 가능 |
| Family and assembly | `private protected` | 파생 타입이되 **같은 어셈블리에 정의된** 경우만 접근 가능 |
| Assembly | `internal` | 같은 어셈블리 안의 어떤 코드든 접근 가능 |
| Family or assembly | `protected internal` | 어느 어셈블리의 파생 타입이든, 또는 같은 어셈블리의 어떤 타입이든 접근 가능 |
| Public | `public` | 어느 어셈블리의 어떤 코드든 접근 가능 |

> **📌 ※ `private protected`는 나중에 생겼다**
>
> 오래된 문헌(2010년대 초 책들 포함)에는 "C#과 Visual Basic은 family and assembly를 제공하지 않는다. IL 어셈블리 언어에서만 쓸 수 있다"고 적혀 있다. 이것은 **C# 7.2 이전의 이야기**다. C# 7.2에서 `private protected`가 추가되어 이 간극이 메워졌다.
>
> 오래된 .NET 문헌을 읽을 때는 이런 시차를 감안해야 한다. **CLR이 지원하던 것을 C#이 나중에 노출하는 일**은 드물지 않다.

#### CTS가 정하는 것 (3) — 상속과 루트 타입

CTS는 타입 상속, 가상 메서드, 객체 수명 등에 관한 규칙도 정한다. 그중 두 가지가 특히 중요하다.

**첫째, 타입은 오직 하나의 기반 클래스에서만 파생될 수 있다.** C++ 언어는 여러 기반 타입에서 상속하는 타입을 지원하지만, CTS는 그런 타입을 받아들이거나 다룰 수 없다. 그래서 Microsoft의 C++/CLI 컴파일러는 여러 기반 타입에서 파생되는 관리 코드를 만들려 하면 오류를 낸다.

2.1절에서 "클래스는 하나, 인터페이스는 여럿"이라고 한 규칙의 근거가 여기 있다. **그것은 C#의 선택이 아니라 CTS의 규칙이다.**

**둘째, 모든 타입은 (궁극적으로) 미리 정의된 타입 `System.Object`에서 상속받아야 한다.** `Object`는 다른 모든 타입의 루트이며, 따라서 모든 타입 인스턴스가 최소한의 동작 집합을 갖도록 보장한다. 구체적으로 `System.Object` 타입은 다음을 할 수 있게 한다.

- 두 인스턴스의 동등성 비교
- 인스턴스의 해시 코드 획득
- 인스턴스의 진짜 타입 조회
- 인스턴스의 얕은(비트 단위) 복사 수행
- 인스턴스의 현재 상태에 대한 문자열 표현 획득

2.1절에서 본 "통합 타입 시스템"이 바로 이것이다. **언어의 약속이 아니라 런타임의 규칙이다.**

#### CTS가 정하는 것 (4) — 내장 데이터 타입

CTS는 근본 데이터 타입 집합도 정의한다. 각 언어는 이 타입을 선언하는 고유한 키워드를 갖지만, **모든 .NET 언어의 키워드는 결국 같은 CTS 타입으로 귀결된다.**

| CTS 타입 | C# 키워드 | VB 키워드 |
|---|---|---|
| `System.Byte` | `byte` | `Byte` |
| `System.SByte` | `sbyte` | `SByte` |
| `System.Int16` | `short` | `Short` |
| `System.Int32` | `int` | `Integer` |
| `System.Int64` | `long` | `Long` |
| `System.UInt16` | `ushort` | `UShort` |
| `System.UInt32` | `uint` | `UInteger` |
| `System.UInt64` | `ulong` | `ULong` |
| `System.Single` | `float` | `Single` |
| `System.Double` | `double` | `Double` |
| `System.Decimal` | `decimal` | `Decimal` |
| `System.Boolean` | `bool` | `Boolean` |
| `System.Char` | `char` | `Char` |
| `System.String` | `string` | `String` |
| `System.Object` | `object` | `Object` |

C#에서 다음 두 줄은 **완전히 같은 것**이다.

```csharp
int i = 0;
System.Int32 j = 0;
```

`int`는 `System.Int32`의 별칭일 뿐이다. 컴파일 결과에는 차이가 없다.

> **📌 ECMA 표준**
>
> Microsoft는 CTS를 비롯해 파일 형식, 메타데이터, IL, 기반 플랫폼 접근(P/Invoke)을 ECMA에 표준화 목적으로 제출했다. 그 표준이 **공용 언어 기반구조(CLI)** 이고 **ECMA-335** 규격이다. C# 프로그래밍 언어도 **ECMA-334**로, C++/CLI도 함께 제출되었다.
>
> 2.3절에서 본 Mono가 존재할 수 있었던 법적·기술적 근거가 이 표준화다.

> **⚠️ CTS를 외울 필요는 없다**
>
> CTS 규칙 자체를 학습할 필요는 없다. 당신이 고른 언어가 자기 문법과 타입 규칙을 노출할 것이고, 컴파일이 어셈블리를 내보낼 때 그 언어별 문법을 CLR의 "언어"인 IL로 매핑해준다.
>
> 다만 **언어와 코드의 동작을 서로 다른 두 가지로 생각하는 습관**은 매우 유용하다. C++/CLI로 타입을 정의하든 C#이나 Visual Basic으로 정의하든, **문법은 다르지만 타입의 동작은 동일하다.** CTS가 타입의 동작을 정의하기 때문이다. 이 감각이 이 책의 4단 원칙(문법 → 컴파일 결과 → 런타임 동작 → 성능)의 밑바닥에 깔려 있다.

### CLS — 공용 언어 사양

언어 통합은 훌륭한 목표지만, 현실의 프로그래밍 언어들은 서로 매우 다르다. 어떤 언어는 심볼의 대소문자를 구분하지 않고, 어떤 언어는 부호 없는 정수나 연산자 오버로딩이나 가변 인자 메서드를 제공하지 않는다.

**다른 언어에서 쉽게 접근할 수 있는 타입을 만들고 싶다면, 다른 모든 언어에 존재한다고 보장되는 기능만 써야 한다.** 이를 돕기 위해 Microsoft는 **공용 언어 사양(CLS, Common Language Specification)** 을 정의했다. CLS는 컴파일러 제작자를 위한 것으로, "다른 CLS 준수 언어로 작성한 컴포넌트와 호환되는 타입을 생성하려면 컴파일러가 최소한 이만큼은 지원해야 한다"는 최소 기능 집합을 명시한다.

```text
        ┌───────────────────────────────────────────────┐
        │                  CLR / CTS                    │
        │       런타임이 표현할 수 있는 것 전부           │
        │                                               │
        │   ┌───────────┐   ┌───────────┐               │
        │   │    C#     │   │Visual Basic│               │
        │   │           │   │            │               │
        │   │      ┌────┴───┴─────┐      │               │
        │   │      │     CLS      │      │               │
        │   │      │ 모든 언어의   │      │               │
        │   │      │ 공통 하한선   │      │               │
        │   │      └────┬───┬─────┘      │               │
        │   │           │   │            │               │
        │   └───────────┘   └───────────┘               │
        │           ┌───────────┐                       │
        │           │  Fortran  │                       │
        │           └───────────┘                       │
        └───────────────────────────────────────────────┘
```

*그림 2-3. 각 언어는 CLR/CTS의 부분집합이자 CLS의 상위집합이다 — 다만 그 상위집합이 서로 같지는 않다.*

CLR/CTS는 CLS가 정의한 부분집합보다 훨씬 많은 기능을 지원한다. 그래서 **언어 간 상호운용성에 관심이 없다면**, 언어의 기능 집합만이 한계인 아주 풍부한 타입을 개발해도 된다.

#### 규칙 1 — CLS의 핵심

CLS의 여러 규칙 중 가장 중요한 것이 규칙 1이다.

> **규칙 1: CLS 규칙은 정의하는 어셈블리 밖으로 노출되는 타입의 부분에만 적용된다.**

이 규칙에서 따라 나오는 결론이 있다. **CLS의 나머지 규칙은 .NET 타입의 내부 구현 로직에는 적용되지 않는다.** 타입에서 CLS를 따라야 하는 유일한 부분은 **멤버 정의 자체**다 — 명명 규칙, 매개변수, 반환 타입. 멤버의 구현 로직은 CLS 밖의 기법을 얼마든지 써도 된다. 바깥세상은 그 차이를 알 수 없기 때문이다.

```csharp
class Calc
{
    // 부호 없는 정수를 노출한다 — CLS 비준수
    public ulong Add(ulong a, ulong b) => a + b;
}

class Calc2
{
    public int Add(int a, int b)
    {
        // ulong을 내부에서만 쓴다 — 여전히 CLS 준수
        ulong temp = 0;
        // ...
        return a + b;
    }
}
```

#### CLS 준수 검사하기

C#은 CLS를 준수하지 않는 여러 구문을 정의한다. 다행히 **특성 하나로 컴파일러에게 검사를 시킬 수 있다.**

```csharp
using System;

// 컴파일러에게 CLS 준수를 검사하라고 지시한다
[assembly: CLSCompliant(true)]

namespace SomeLibrary
{
    // 클래스가 public이므로 경고가 나타난다
    public sealed class SomeLibraryType
    {
        // 경고: 'SomeLibrary.SomeLibraryType.Abc()'의 반환 형식은
        // CLS를 준수하지 않는다
        public UInt32 Abc() { return 0; }

        // 경고: 대소문자만 다른 식별자
        // 'SomeLibrary.SomeLibraryType.abc()'는 CLS를 준수하지 않는다
        public void abc() { }

        // 경고 없음: 이 메서드는 private다
        private UInt32 ABC() { return 0; }
    }
}
```

첫 번째 경고는 `Abc` 메서드가 **부호 없는 정수**를 반환하기 때문에 나온다 — 어떤 프로그래밍 언어는 부호 없는 정수 값을 다루지 못한다. 두 번째 경고는 이 타입이 **대소문자와 반환 타입만 다른** 두 public 메서드 `Abc`와 `abc`를 노출하기 때문이다 — Visual Basic을 비롯한 일부 언어는 이 둘을 모두 호출할 수 없다.

흥미롭게도 `sealed class SomeLibraryType` 앞의 `public`을 지우고 다시 컴파일하면 **두 경고가 모두 사라진다.** 타입이 `internal`이 되어 어셈블리 밖으로 노출되지 않기 때문이다. 규칙 1이 정확히 이 이야기다.

> **⚠️ CLS 위반은 오류가 아니라 경고다**
>
> `[assembly: CLSCompliant(true)]`를 붙여도 CLS 위반은 **컴파일러 경고**로만 보고된다. 빌드는 성공한다. 경고를 무시하면 그 라이브러리는 조용히 CLS 비준수 상태로 배포된다.
>
> 이것을 강제하고 싶다면 프로젝트에서 경고를 오류로 승격시켜야 한다. 자세히는 4.6절에서 다룬다.

#### CLS의 다른 얼굴 — C# 문법이 IL에서 무엇이 되는가

CLS 규칙을 아주 단순하게 요약하면 이렇다. **CLR에서 타입의 모든 멤버는 필드(데이터) 아니면 메서드(동작)다.** 즉 모든 프로그래밍 언어는 필드에 접근하고 메서드를 호출할 수만 있으면 된다.

그런데 특정 필드와 특정 메서드는 특별하고 공통된 방식으로 쓰인다. 프로그래밍을 쉽게 하려고 언어들은 이런 흔한 패턴을 코딩하기 편하게 추가 추상화를 제공한다 — 열거형, 배열, 프로퍼티, 인덱서, 델리게이트, 이벤트, 생성자, 파이널라이저, 연산자 오버로드, 변환 연산자 등. **컴파일러는 소스 코드에서 이런 것을 만나면 필드와 메서드로 번역해야 한다.** 그래야 CLR과 다른 언어가 그 구문에 접근할 수 있기 때문이다.

생성자, 파이널라이저, 연산자 오버로드, 프로퍼티, 인덱서, 이벤트를 가진 타입을 컴파일하면 메타데이터에 이런 멤버들이 나타난다.

| 메타데이터의 멤버 | 멤버 종류 | 대응하는 언어 구문 |
|---|---|---|
| `AnEvent` | 필드 | 이벤트. 필드 이름은 `AnEvent`이고 타입은 `System.EventHandler` |
| `.ctor` | 메서드 | 생성자 |
| `Finalize` | 메서드 | 파이널라이저 |
| `add_AnEvent` | 메서드 | 이벤트 add 접근자 메서드 |
| `remove_AnEvent` | 메서드 | 이벤트 remove 접근자 메서드 |
| `get_AProperty` | 메서드 | 프로퍼티 get 접근자 메서드 |
| `set_AProperty` | 메서드 | 프로퍼티 set 접근자 메서드 |
| `get_Item` | 메서드 | 인덱서 get 접근자 메서드 |
| `set_Item` | 메서드 | 인덱서 set 접근자 메서드 |
| `op_Addition` | 메서드 | `+` 연산자 |
| `op_Equality` | 메서드 | `==` 연산자 |
| `op_Inequality` | 메서드 | `!=` 연산자 |

이 표가 이 절에서 가장 실용적인 부분이다. **프로퍼티는 런타임에 존재하지 않는다** — `get_X`와 `set_X`라는 두 메서드, 그리고 "이 둘이 프로퍼티 X를 이룬다"는 메타데이터가 있을 뿐이다. 이 사실은 리플렉션(57장)과 성능 분석(스택 트레이스에 `get_Name`이 찍히는 이유)에서 계속 다시 만난다.

> **💡 CLS는 지금도 의미가 있는가**
>
> 솔직하게 답하면, **다중 언어 플랫폼이라는 원래 꿈은 상당 부분 저물었다.** 오늘날 .NET에서 실질적으로 쓰이는 언어는 C#, F#, Visual Basic 셋이고, 그중 압도적 다수가 C#이다. 사내 코드에서 CLS 준수를 따질 실익은 거의 없다.
>
> 그래도 CLS가 중요한 곳이 두 군데 남아 있다.
>
> 1. **공개 NuGet 패키지를 만든다면** — 당신의 라이브러리를 F#이나 Visual Basic에서 쓰는 사람이 있을 수 있다. 공개 API에서 `uint`, `sbyte`, `ushort` 같은 타입을 피하고, 대소문자만 다른 이름을 만들지 않는 것만으로 대부분 해결된다.
> 2. **C#의 설계를 이해하는 데** — "왜 프로퍼티가 메서드 두 개로 컴파일되는가", "왜 클래스는 하나만 상속하는가", "왜 `int`가 `System.Int32`인가". 이 질문들의 답이 전부 CTS/CLS에 있다.
>
> **CLS 규칙 전체를 외우는 것은 컴파일러 제작자의 일이다.** 당신의 일은 위 두 가지를 아는 것이다.

## 2.6 관리 코드(managed) vs 비관리 코드

### 정의

용어부터 정확히 하자.

- **관리 코드(managed code)** — .NET 런타임을 대상으로 하는 코드. IL과 메타데이터로 어셈블리에 담기고, CLR이 로드해서 실행한다.
- **비관리 코드(unmanaged code)** — .NET 런타임이 직접 호스팅할 수 없는 코드. 특정 CPU의 네이티브 명령으로 컴파일되어 OS가 직접 실행한다.

C# 언어는 .NET 런타임 아래에서 호스팅되는 소프트웨어를 만드는 데만 쓸 수 있다. C#으로 네이티브 COM 서버나 비관리 C/C++ 스타일 애플리케이션을 만들 수는 없다.

### 무엇이 "관리"되는가

"관리"라는 말이 정확히 무엇을 가리키는지가 이 절의 핵심이다. 다섯 가지다.

| 관리되는 것 | 관리 코드에서 | 비관리 코드에서 |
|---|---|---|
| **메모리** | GC가 할당하고 회수한다 | `malloc`/`free`, `new`/`delete`로 직접 |
| **타입 안전성** | 런타임이 캐스트·배열 저장·배열 경계를 검사한다 | 검사 없음. 잘못된 포인터가 메모리를 오염시킨다 |
| **예외** | 구조화된 예외 처리가 언어·런타임 차원에서 통합된다 | 플랫폼마다 다르고 언어 경계를 넘기 어렵다 |
| **메타데이터** | 어셈블리가 자기 타입을 완전히 설명한다 | 별도의 헤더 파일·타입 라이브러리가 필요하다 |
| **실행 위치** | 어느 플랫폼의 런타임이든 같은 IL을 실행한다 | CPU와 OS에 묶인다 |

이 다섯 가지 덕분에, C# 애플리케이션을 Windows에서 만들어 .NET 런타임이 있는 macOS나 Linux에서 실행할 수 있다. Linux에서 Visual Studio Code로 만든 프로그램을 Windows에서 실행할 수도 있다.

그림으로 보면 경계가 분명해진다.

```text
        ┌─────────────────────────────────────────────┐
        │              관리 코드 영역                   │
        │                                             │
        │   C# 소스 ──▶ IL + 메타데이터 ──▶ 어셈블리     │
        │                     │                       │
        │                     ▼                       │
        │              CLR이 로드하고 실행              │
        │        (JIT · GC · 타입 검사 · 예외)          │
        │                                             │
        │   ┌───────────────────────────────────┐     │
        │   │  unsafe 블록                       │     │
        │   │  여전히 IL, 여전히 CLR이 실행       │     │
        │   │  그러나 타입 안전성 보장은 없다      │     │
        │   └───────────────────────────────────┘     │
        └──────────────────┬──────────────────────────┘
                           │
              ┌────────────┴────────────┐
              │  P/Invoke · COM 상호운용  │   ← 경계를 넘는 통로
              └────────────┬────────────┘
                           │
        ┌──────────────────▼──────────────────────────┐
        │             비관리 코드 영역                  │
        │                                             │
        │  C/C++ 소스 ──▶ 네이티브 기계어 ──▶ .dll/.so  │
        │                     │                       │
        │                     ▼                       │
        │                OS가 직접 실행                 │
        │         (수동 메모리 · 검사 없음)              │
        └─────────────────────────────────────────────┘
```

*그림 2-4. 관리 코드와 비관리 코드의 경계. `unsafe`는 경계를 넘는 것이 아니라, 관리 영역 안에서 보장 하나를 반납하는 것이다.*

> **⚠️ "관리 코드"와 "관리 리소스"는 다른 말이다**
>
> 초보자가 가장 자주 걸려 넘어지는 지점이다.
>
> - **관리 코드** — CLR이 실행하는 코드. C#으로 쓴 코드는 전부 관리 코드다.
> - **관리 리소스** — GC가 회수할 수 있는 것. 즉 **관리 힙의 메모리**.
> - **비관리 리소스** — GC가 모르는 것. 파일 핸들, 소켓, 윈도 핸들, 네이티브 메모리, DB 연결.
>
> **관리 코드가 비관리 리소스를 잡고 있는 것은 지극히 정상이다.** `FileStream`은 100% 관리 코드로 쓰였지만 안에 OS 파일 핸들(비관리 리소스)을 들고 있다. 그래서 `IDisposable`을 구현한다.
>
> 이 구분을 흐리면 "GC가 있는데 왜 `using`을 써야 하나"라는 질문에 영원히 답할 수 없다. 33.1절에서 이 모델을 처음부터 다시 세운다.

### 상호운용 — 경계를 넘는 세 가지 방법

.NET은 다른 개발 플랫폼에 비해 이점이 많지만, 기존 코드 전부를 다시 설계하고 다시 구현할 수 있는 회사는 거의 없다. Microsoft는 이 현실을 인지하고, **애플리케이션이 관리 부분과 비관리 부분으로 함께 구성될 수 있도록** CLR을 만들었다. 구체적으로 세 가지 상호운용 시나리오를 지원한다.

**(1) 관리 코드가 DLL의 비관리 함수를 호출한다**

**P/Invoke(Platform Invoke)** 라는 메커니즘으로 DLL에 든 함수를 쉽게 호출할 수 있다. 실제로 BCL에 정의된 많은 타입이 내부적으로 `kernel32.dll`, `user32.dll` 등에서 내보낸 함수를 호출한다.

```csharp
using System.Runtime.InteropServices;

class Native
{
    // Windows kernel32.dll의 함수를 호출한다
    [DllImport("kernel32.dll")]
    private static extern ulong GetTickCount64();

    public static TimeSpan Uptime()
        => TimeSpan.FromMilliseconds(GetTickCount64());
}
```

**(2) 관리 코드가 기존 COM 컴포넌트를 사용한다**

이미 구현된 비관리 COM 컴포넌트가 많은 회사가 있다. 그 컴포넌트의 타입 라이브러리로부터 COM 컴포넌트를 설명하는 관리 어셈블리를 만들 수 있고, 관리 코드는 그 어셈블리의 타입을 다른 관리 타입과 똑같이 쓴다.

**(3) 비관리 코드가 관리 타입을 사용한다**

반대 방향도 된다. 기존 비관리 코드가 COM 컴포넌트를 요구할 때, 그 컴포넌트를 관리 코드로 구현하면 참조 카운팅과 인터페이스에 관한 코드를 전부 피할 수 있다.

> **⚠️ P/Invoke는 이식성을 잃는다**
>
> 비관리 코드는 C# 프로그램에서 접근할 수 있지만, **그렇게 하는 순간 특정 개발·배포 대상에 묶인다.** 위 예제의 `GetTickCount64`는 Windows API다. 이 코드가 든 프로그램은 Linux에서 `DllNotFoundException`으로 죽는다.
>
> 그리고 이 오류는 **컴파일 시점에 잡히지 않는다.** 대상 DLL의 존재는 실행할 때야 확인되기 때문이다. 크로스 플랫폼을 목표로 한다면 P/Invoke는 반드시 조건부 경로로 격리해야 한다.
>
> 상호운용의 전모는 60장에서 다룬다. **지금 P/Invoke를 쓸 일은 없다.**

### `unsafe` — 관리 코드 안의 비관리 섬

C#에는 세 번째 영역이 있다. **관리 코드이면서 타입 안전성 보장을 포기하는** 코드다.

```csharp
// .csproj에 <AllowUnsafeBlocks>true</AllowUnsafeBlocks>가 필요하다
unsafe
{
    int value = 42;
    int* p = &value;      // 주소를 직접 잡는다
    *p = 99;              // 주소를 통해 직접 쓴다
    Console.WriteLine(value);   // 99
}
```

이 코드는 여전히 IL로 컴파일되고 CLR이 실행한다. **여전히 관리 코드다.** 다만 이 안에서는 런타임이 타입 안전성을 보장하지 않는다.

> **⚠️ `unsafe` 안에서 GC는 여전히 움직인다**
>
> 초보자가 가장 위험하게 오해하는 지점이다. `unsafe` 블록 안에 있다고 해서 GC가 멈추는 것이 아니다. **GC는 객체를 힙 안에서 이동시킬 수 있고**, 이동하면 당신이 잡아둔 포인터는 엉뚱한 곳을 가리키게 된다.
>
> 그래서 관리 객체의 주소를 잡을 때는 `fixed` 문으로 **고정(pinning)** 해야 한다. 자세히는 60.8절에서 다룬다.
>
> **이것이 `unsafe`가 기본으로 꺼져 있는 이유다.** 켤 이유가 확실하지 않으면 켜지 마라.

> **📌 Native AOT로 컴파일해도 여전히 관리 코드다**
>
> .NET 6부터는 애플리케이션을 **단일 파일**로 줄여 직접 실행할 수 있다. 이 단일 파일은 C++ 스타일의 네이티브 실행 파일처럼 보이고 그렇게 동작하지만, **패키징 편의를 위한 것**이다. 애플리케이션 실행에 필요한 모든 파일을, 경우에 따라 .NET 런타임 자체까지 담고 있을 뿐이다.
>
> Native AOT로 미리 네이티브 코드로 컴파일한 경우도 마찬가지다. **여전히 GC가 있고, 타입 안전성이 보장되고, 메타데이터가 있다.** 다만 JIT이 없을 뿐이다. "네이티브로 컴파일했으니 C++이 되었다"는 것은 오해다. 배포 형태는 4.9절, Native AOT의 실제 동작은 55.7절에서 다룬다.

## 2.7 왜 C#은 "느리지 않은" 언어가 되었나

이 절이 이 장의 하이라이트다. 그리고 **이 장에서 가장 조심스럽게 읽어야 하는 절**이기도 하다.

### 오해의 출처

"C#은 가상 머신 위에서 도니까 느리다." 이 말은 널리 퍼져 있고, 세 가지 서로 다른 오해가 섞여 있다.

1. **인터프리터와의 혼동.** IL은 인터프리트되지 않는다. 실행 전에 네이티브 기계어로 컴파일된다.
2. **2000년대 초의 기억.** .NET Framework 1.x 시절의 JIT은 지금과 비교할 수 없이 단순했다. 20년 동안 바뀌었다.
3. **"GC가 있으면 느리다"는 직관.** 이것은 절반만 맞다. 뒤에서 본다.

정확하게 말하면 이렇다. **C#은 C나 Rust만큼 빠르지 않다.** 그러나 **C#이 느린 언어라는 말도 틀렸다.** 그 이유가 세 가지 있다.

### 이유 1 — JIT은 사전 컴파일보다 **더 많이 알고** 컴파일한다

직관적으로는 반대일 것 같다. 미리 컴파일해두면 실행할 때 컴파일 시간이 안 드니까 더 빠를 것 같다. 그런데 **컴파일러가 아는 정보의 양**을 생각하면 이야기가 달라진다.

사전 컴파일된 바이너리를 배포하는 상황을 생각해보자. 그 바이너리는 **어떤 CPU에서 돌지 모른다.** 최신 AVX-512 명령을 쓰는 CPU일 수도 있고 10년 전 CPU일 수도 있다. 그래서 컴파일러는 **최소 공통 분모**를 대상으로 코드를 만들어야 한다. 아니면 여러 벌을 만들어 런타임에 고르게 해야 하는데, 그러면 바이너리가 커진다.

JIT은 다르다. **실행되는 바로 그 머신에서, 실행되기 직전에 컴파일한다.** 그래서 다음을 안다.

| JIT이 아는 것 | 사전 컴파일러가 모르는 이유 |
|---|---|
| **실제 CPU의 명령 집합** | 배포 대상 CPU를 특정할 수 없다 |
| **실제로 로드된 타입** | 어떤 인터페이스 구현이 실제로 쓰일지 모른다 |
| **실제 실행 프로필** | 어느 분기가 자주 타는지, 어느 메서드가 뜨거운지 모른다 |
| **설정 값과 상수** | 런타임 설정에 따라 죽는 코드가 되는 분기를 모른다 |

이 정보로 JIT이 하는 일이 있다. 예를 들어 인터페이스를 통한 가상 호출이 실제로는 항상 한 구현만 부른다면, JIT은 그 호출을 직접 호출로 바꾸고 인라인할 수 있다(**역가상화**). ※.NET 8부터는 **동적 PGO(프로파일 기반 최적화)** 가 기본으로 켜져서, 실행 초기에 수집한 프로필을 바탕으로 자주 쓰이는 메서드를 다시, 더 좋게 컴파일한다(**계층형 컴파일**).

JIT이 실행 시점 정보를 쓰는 것을 눈으로 볼 수 있는 가장 단순한 예가 이것이다.

```csharp
// 이 값은 컴파일 시점에는 알 수 없다. 실행하는 머신의 CPU에 달렸다.
static readonly bool UseFastPath = System.Numerics.Vector.IsHardwareAccelerated;

static int Sum(int[] data)
{
    if (UseFastPath)
        return SumVectorized(data);
    else
        return SumScalar(data);
}
```

C 컴파일러였다면 이 `if`는 **실행할 때마다** 평가되는 분기다. 그런데 JIT은 `Sum`을 컴파일하는 시점에 `UseFastPath`의 값을 **이미 알고 있다.** 정적 읽기 전용 필드가 클래스 초기화 때 확정되기 때문이다. 그래서 JIT은 분기를 통째로 지우고, 실제로 타지 않는 쪽 호출은 아예 생성하지 않을 수 있다.

이 "실행 시점 상수 접기"는 BCL 곳곳에서 쓰인다. 같은 소스가 AVX-512를 가진 서버에서는 벡터 경로로, 오래된 CPU에서는 스칼라 경로로 컴파일되고, **둘 다 분기 비용이 0이다.** 사전 컴파일된 단일 바이너리로는 이렇게 할 수 없다.

대가는 있다. **첫 실행이 느리다.** 그래서 시작 시간이 중요한 시나리오(짧게 살고 죽는 CLI 도구, 서버리스 함수)에서는 ReadyToRun이나 Native AOT를 쓴다.

> **📌 이 주장의 근거는 55장에 있다**
>
> 이 문단에서 이름만 나온 것들 — 계층형 컴파일, 역가상화, 동적 PGO, OSR, ReadyToRun — 은 전부 55장에서 실제 생성 코드를 보면서 다룬다. **지금은 "JIT은 정보를 더 많이 갖고 컴파일한다"는 원리만 가져가면 된다.**

### 이유 2 — 값 타입이 있다

이것이 C#과 Java를 가르는 가장 큰 차이다.

C#에는 **값 타입(구조체)** 이 있다. 값 타입은 참조로 가리켜지는 별도의 힙 객체가 아니라, **데이터가 놓인 자리에 직접** 존재한다. 배열 안에, 다른 객체의 필드로, 스택 위에.

그 결과 두 가지가 따라온다.

**(1) 할당이 줄어든다.** `Point` 구조체 백만 개를 담은 배열은 힙 객체 하나다. 같은 것을 클래스로 만들면 힙 객체 백만 한 개다.

**(2) 메모리가 연속적이다.** 구조체 배열의 원소는 메모리에 나란히 놓인다. 클래스 배열은 참조가 나란히 놓이고 실제 객체는 힙 여기저기 흩어진다. **CPU 캐시 관점에서 이 차이는 결정적이다** — 연속된 데이터를 순회하면 캐시 미스가 거의 없고, 흩어진 참조를 따라가면 매번 캐시 미스가 날 수 있다.

여기에 2.2절에서 본 **실체화된 제네릭**이 결합한다. `List<int>`는 런타임에도 진짜 int의 리스트다. 정수마다 힙 객체를 만들지 않는다. Java는 타입 소거를 택했기 때문에 이에 해당하는 것이 존재하지 않았고, 정수 컬렉션마다 박싱 비용을 냈다.

같은 데이터를 클래스로 담았을 때와 구조체로 담았을 때 무엇이 달라지는지 정리하면 이렇다.

| | `Point[]` (클래스) | `Point[]` (구조체) |
|---|---|---|
| 힙 객체 수 (원소 N개) | N + 1 (배열 1 + 원소 N) | 1 (배열만) |
| 원소 접근 | 배열에서 참조를 읽고, 그 주소로 한 번 더 간다 | 배열 안에서 바로 읽는다 |
| 메모리 배치 | 원소가 힙 여기저기 흩어질 수 있다 | 원소가 나란히 놓인다 |
| 순회 시 캐시 | 원소마다 캐시 미스가 날 수 있다 | 한 번 읽으면 여러 원소가 함께 올라온다 |
| GC 부담 | 추적할 객체가 N + 1개 | 추적할 객체가 1개 |

마지막 줄이 특히 크다. GC는 살아 있는 객체를 **하나씩 따라가며** 표시한다(64.2절). 객체 수가 백만 개에서 한 개로 줄면, 그 배열이 GC에 주는 부담도 그만큼 줄어든다.

> **⚠️ 값 타입이 항상 빠른 것은 아니다**
>
> 구조체는 **복사**된다. 메서드에 넘길 때마다, 변수에 대입할 때마다, 컬렉션에서 꺼낼 때마다. 큰 구조체는 이 복사 비용이 할당 비용보다 클 수 있다.
>
> 그리고 값 타입을 `object`나 인터페이스로 다루면 **박싱**이 일어나 결국 힙 객체가 생긴다 — 값 타입의 이점이 사라지고 오히려 손해가 된다.
>
> "구조체를 쓸까 클래스를 쓸까"의 판단 기준은 16.8절에, 박싱을 피하는 체크리스트는 15.7절에 있다. **지금 기억할 것은 "C#에는 선택지가 있다"는 사실 하나다.**

### 이유 3 — GC의 할당이 `malloc`보다 빠를 수 있다

이것이 가장 반직관적인 부분이다.

C에서 `malloc(24)`을 호출하면 무슨 일이 일어나는가? 할당자는 **자유 리스트(free list)** 를 뒤져서 24바이트가 들어갈 빈 조각을 찾아야 한다. 적당한 조각이 없으면 더 큰 조각을 쪼개고, 인접한 빈 조각들을 병합하기도 한다. 멀티스레드 환경이면 잠금이 필요하다. **탐색과 관리에 비용이 든다.**

.NET의 관리 힙에서 새 객체를 할당할 때는 대개 이렇게 된다. 힙의 "다음 빈 자리"를 가리키는 포인터가 있고, **그 포인터를 객체 크기만큼 앞으로 옮기면 끝이다.** 탐색이 없다. 이것을 **범프 포인터 할당(bump pointer allocation)** 이라고 부른다.

왜 이게 가능한가? **압축(compaction)** 때문이다. GC는 살아 있는 객체를 한쪽으로 모아 빈 공간의 파편화를 없앤다. 그래서 힙의 끝은 항상 연속된 빈 공간이고, 포인터를 밀기만 하면 된다.

즉 .NET은 **비용을 할당 시점에서 수집 시점으로 옮긴 것이다.**

| | 수동 관리 (`malloc`/`free`) | 추적형 GC |
|---|---|---|
| 할당 비용 | 자유 리스트 탐색 — 비쌀 수 있다 | 포인터 증가 — 매우 싸다 |
| 해제 비용 | 즉시, 그러나 프로그래머가 정확히 해야 한다 | 0 (해제 코드가 없다) |
| 수집 비용 | 없음 | **있다.** 살아 있는 객체를 찾고 옮긴다 |
| 언제 멈추나 | 멈추지 않는다 | GC가 도는 동안 애플리케이션이 멈출 수 있다 |
| 최악의 경우 | 단편화로 할당이 계속 느려진다 | 긴 일시 중지 |

**"GC가 있어서 느리다"는 말은 이 표의 세 번째·네 번째 줄만 본 것이다.** 첫 번째 줄은 GC 쪽이 유리하다.

> **📌 이 주장의 근거는 61~64장에 있다**
>
> 범프 포인터 할당의 실제 동작은 63.1절, 압축은 64.8절과 64.10절, 수동 관리와 자동 관리의 손익 계산은 61.8절에서 다룬다. 그리고 "GC가 도는 동안 멈춘다"는 문장이 실제로 얼마나 멈추는지, 어떻게 줄이는지는 65장 전체가 그 이야기다.
>
> **이 절에서는 여기까지만 안다.** 세대(generation)니 배리어니 하는 것은 아직 필요 없다.

### 그러면 어디서 느린가 — 정직하게

"느리지 않다"가 "빠르다"는 아니다. C#이 손해를 보는 지점을 정확히 알아야 한다.

| 손해 보는 지점 | 왜 | 다루는 장 |
|---|---|---|
| **GC 일시 중지** | 수집하는 동안 애플리케이션 스레드가 멈춘다 | 64.12절, 65장 |
| **숨은 할당** | 델리게이트, 클로저, 박싱, `yield`, 문자열 연결, LINQ가 조용히 객체를 만든다 | 63.9절 |
| **시작 시간** | 첫 호출마다 JIT이 컴파일한다 | 55.2절, 55.7절 |
| **간접 호출** | 인터페이스·가상 호출은 직접 호출보다 비싸다 (JIT이 자주 없애주지만) | 55.5절 |
| **경계 검사** | 배열 접근마다 범위를 검사한다 (JIT이 상당수 제거한다) | 55.6절 |
| **상호운용 마샬링** | 관리/비관리 경계를 넘을 때 데이터 변환이 필요할 수 있다 | 60.2~60.3절 |

이 목록에서 **실무에서 가장 자주 문제가 되는 것은 두 번째, 숨은 할당**이다. 코드에는 `new`가 한 번도 안 보이는데 초당 수백 MB를 할당하는 메서드가 있을 수 있다.

```csharp
// new가 한 번도 없지만, 이 메서드는 호출될 때마다 힙에 객체를 만든다
string Describe(int id, string name)
{
    return "id=" + id + ", name=" + name;
}
```

`+`로 문자열을 이어붙이면 컴파일러는 이것을 `string.Concat` 호출로 바꾼다. 그 과정에서 값 타입인 `id`는 먼저 `ToString()`으로 문자열이 되고, 이어붙인 결과를 담을 새 문자열이 힙에 만들어진다. 문자열은 불변이므로 기존 문자열을 고쳐 쓸 수 없기 때문이다. 여기에 더해, 값 타입을 `object`를 받는 오버로드로 넘기는 코드 형태에서는 **박싱**까지 얹힌다(15.2절).

소스 코드에는 `new`가 한 글자도 없다. 그런데 이 메서드가 초당 백만 번 호출되면 그만큼의 쓰레기가 쌓이고 GC가 그만큼 자주 돈다. 그런 코드를 찾아내는 방법 — 그리고 애초에 만들지 않는 방법 — 이 이 책 3권의 큰 주제다(63.9절, 69장).

> **⚠️ "느리지 않다"는 "측정하지 않아도 된다"가 아니다**
>
> 이 절의 논리를 "그러니까 C#은 빠르다, 신경 쓰지 말자"로 읽으면 안 된다. 반대다. **모든 주장은 조건부**다.
>
> - JIT이 유리한 것은 **오래 도는 프로세스**에서다. 짧게 죽는 도구에서는 반대다.
> - 값 타입이 유리한 것은 **작고 복사가 싼 경우**다.
> - 범프 포인터 할당이 유리한 것은 **할당한 객체 대부분이 금방 죽는 경우**다. 오래 사는 객체를 많이 만들면 수집 비용이 그 이득을 지운다.
>
> 그래서 이 책은 "측정 없이 최적화 없다"를 반복한다(67장). **자기 코드에서 재보지 않은 성능 주장은 전부 추측이다.**

> **⚠️ 벤치마크는 반드시 Release 구성으로, 디버거 없이**
>
> Debug 구성으로 잰 숫자는 무의미하다. Debug에서는 JIT 최적화가 대부분 꺼지고 컴파일러가 `nop` 명령과 불필요한 지역 변수를 남긴다. 디버거가 붙어 있으면 계층형 컴파일도 정상 동작하지 않는다.
>
> 1.7절에서 이미 말했지만 다시 말한다. **`dotnet run -c Release`로, 디버거 없이.** 이 규칙을 어긴 측정은 전부 버려야 한다.

> **💡 입문 단계에서 지킬 성능 습관은 셋뿐이다**
>
> 지금 단계에서 성능을 걱정할 필요는 없다. 다만 나중에 고치기 어려운 것만 피하면 된다.
>
> 1. **뜨거운 루프 안에서 문자열을 `+`로 이어붙이지 마라.** `StringBuilder`를 쓴다(8장).
> 2. **컬렉션의 크기를 미리 알면 용량을 지정해라.** `new List<int>(1000)`.
> 3. **`IDisposable`을 구현한 것은 `using`으로 감싸라.** 성능이 아니라 정확성의 문제이기도 하다(33장).
>
> 이 셋 말고는, **지금은 읽기 좋은 코드를 쓰는 데 집중해라.** 나머지는 재본 다음에 고치면 된다.

## 이 장의 요약

- **C#은 범용·타입 안전·객체 지향 언어이고, 목표는 프로그래머 생산성이다.** 단순함·표현력·성능 사이의 균형이 언어 설계의 축이고, 그 균형점의 이동이 C#의 버전 역사다(2.1절, 2.2절).
- **C#을 규정하는 네 가지는 객체 지향, 타입 안전성, 자동 메모리 관리, 플랫폼 지원이다.** 각각은 C++의 다중 상속과 수동 메모리, JavaScript의 동적 타입, Java의 원시 타입 이중 구조와 대비할 때 의미가 선명해진다(2.1절).
- **타입 안전성은 두 축으로 강제된다.** 정적 타입 검사는 잡을 수 있는 것을 실행 전에 전부 잡고, 런타임 타입 안전성은 다운캐스트·배열 공변성·외부 입력처럼 컴파일러가 알 수 없었던 것을 **안전하게 실패시킨다.** 하나만으로는 부족하다(2.1절).
- **GC는 관리 힙의 메모리만 회수한다.** 파일 핸들·소켓 같은 비관리 리소스는 `IDisposable`의 몫이고, 참조가 남아 있는 객체는 GC가 회수하지 않으므로 **GC가 있어도 메모리 누수는 난다**(2.1절, 33장, 34장).
- **.NET은 Windows 전용 .NET Framework(2002)와 크로스 플랫폼 Mono로 갈라졌다가, 다시 만든 .NET Core(2016)를 거쳐 .NET 5(2020)에서 하나로 합쳐졌다.** 갈라진 이유는 표준만 공개되고 구현은 Windows 전용이었기 때문이고, 합친 이유는 두 벌의 코드베이스와 .NET Standard라는 다리가 근본 해법이 아니었기 때문이다(2.3절).
- **SDK ⊃ 런타임 ⊃ (애플리케이션 계층 + BCL + CLR)이다.** CLR은 JIT·GC·타입 로더·예외를 책임지고, BCL은 공통 기능과 언어가 요구하는 타입을 제공하며, SDK는 여기에 컴파일러와 도구를 더한다. **C# 언어는 이 그림 안에 없다** — CLR은 IL만 안다(2.4절).
- **CTS는 타입이 어떻게 정의되고 행동하는지의 형식 규격이고, CLS는 모든 언어가 지켜야 할 최소 하한선이다.** 단일 상속, `System.Object` 루트, `int` = `System.Int32`가 전부 CTS의 규칙이며, 프로퍼티가 `get_X`/`set_X` 메서드로 컴파일되는 것은 CLS 설계의 흔적이다(2.5절).
- **관리 코드는 IL로 컴파일되어 CLR이 실행하는 코드이고, 관리 리소스는 GC가 회수할 수 있는 메모리다.** 이 둘은 다른 말이며, 관리 코드가 비관리 리소스를 잡고 있는 것은 정상이다(2.6절).
- **C#이 느리지 않은 이유는 셋이다** — JIT이 실제 CPU·실제 타입·실제 프로필을 알고 컴파일하고, 값 타입이 할당과 캐시 미스를 줄이고, 범프 포인터 할당이 `malloc`보다 쌀 수 있다. 대가는 GC 일시 중지, 숨은 할당, 시작 시간이다. **모든 주장은 조건부이고, 근거는 3권에 있다**(2.7절).

## 연습 문제

1. `dotnet --info`를 실행해 설치된 SDK와 런타임 목록을 확인하라. SDK 버전의 **세 번째 숫자**가 무엇을 뜻하는지 2.4절의 규칙에 따라 해석해보라. 런타임이 SDK보다 여러 개 설치되어 있는가? 왜 그런가?

2. 다음 코드를 실행해서 어떤 예외가 나는지 확인하라. 그다음 두 번째 줄을 지우고 `object o = 42;`로 바꾸면 어떻게 되는지 확인하라. 왜 컴파일러가 이것을 막지 않는지 설명할 수 있는가?

   ```csharp
   object o = "hello";
   int i = (int)o;
   ```

3. 배열 공변성이 런타임 검사에 걸리는 것을 직접 확인하라. 아래 코드를 실행하고, 세 번째 줄을 `objects[0] = "world";`로 바꾸면 어떻게 되는지도 확인하라.

   ```csharp
   string[] strings = new string[3];
   object[] objects = strings;
   objects[0] = 42;
   ```

4. `int i = 0;`과 `System.Int32 j = 0;`을 한 파일에 쓰고 SharpLab(1.6절)에 붙여 넣어라. **IL이 완전히 같은지** 확인하라. 같다면 그 이유를 2.5절의 어느 규칙으로 설명할 수 있는가?

5. 프로퍼티 하나와 이벤트 하나를 가진 클래스를 만들어 빌드한 뒤, ILSpy로 열어서 **메타데이터에 실제로 어떤 멤버가 있는지** 확인하라. `get_`, `set_`, `add_`, `remove_`로 시작하는 메서드가 보이는가? 2.5절의 표와 대조해보라.

6. 새 콘솔 프로젝트를 만들고 `.csproj`에 `[assembly: CLSCompliant(true)]`를 적용한 뒤, `public uint Foo()` 같은 CLS 비준수 public 메서드를 추가하라. 경고가 나는가? 그 메서드를 `private`으로 바꾸면 경고가 사라지는가? 사라진다면 그것이 CLS 규칙 1과 어떻게 연결되는가?

7. `List<int>`에 정수 1,000만 개를 넣는 코드와, `ArrayList`에 같은 수를 넣는 코드를 각각 만들어라. `-c Release`로 빌드하고 `Stopwatch`로 시간을 재보라. 차이가 몇 배인가? 그 차이를 2.2절(제네릭)과 2.7절(박싱)의 어느 문장으로 설명할 수 있는가? **이 실험의 정확한 해석은 15장에서 다시 한다.**
