# 19장. 레코드와 불변 타입

> **이 장의 위치** — 13장에서 `init` 전용 프로퍼티(13.8절)와 기본 생성자(13.10절)를, 16장에서 `readonly struct`와 값 동등성(16.5절, 16.7절)을 다루면서 매번 같은 각주를 달았다. "이걸 전부 자동으로 해 주는 것이 레코드다. 19장에서 본다." 이 장이 그 약속을 갚는 자리다. 레코드는 새 런타임 기능이 아니라 **컴파일러가 대신 써 주는 스무 줄**이다. 그래서 이 장의 대부분은 문법이 아니라 그 스무 줄이 정확히 무엇인지, 그리고 그것이 만들어내는 동작이 어디에서 배신하는지에 대한 이야기다.
>
> **선수 지식** — 13장(클래스와 캡슐화), 14장(상속과 다형성), 15장(`object` 타입과 박싱), 16장(구조체와 값 타입), 18장(인터페이스)
>
> **이 장에서 다루지 않는 것** — 레코드가 C# 9에 들어온 **버전 이력과 도입 배경 전체**는 76.8절, `record struct`가 C# 10에서 채운 빈 구석은 76.9절이다. 레코드와 **패턴 매칭의 결합**(위치 패턴, 속성 패턴, `switch` 식과의 조합)은 77.9절·77.10절이며, 튜플·익명 타입과의 상세 비교표는 77.5절에 있다. **동등성 프로토콜 전체**(`Equals` 재정의 5계명, `GetHashCode` 계약, `IEqualityComparer<T>`)는 25장이다. 이 장은 25장의 결론을 **레코드가 어떻게 자동으로 만족시키는가**만 본다. 불변 컬렉션(`ImmutableArray<T>` 계열)의 내부 구조는 24.10절이다.

## 19.1 레코드가 나온 배경

### 손으로 쓰는 불변 DTO

좌표 하나를 표현하는 타입을 쓴다고 하자. 요구 사항은 흔하다.

- 생성 후에는 값이 바뀌지 않는다(불변).
- 값이 같으면 같은 것으로 취급한다(구조적 동등성).
- 딕셔너리 키로 쓸 수 있어야 한다.
- 디버깅할 때 내용이 보여야 한다.
- 일부 값만 바꾼 새 인스턴스를 쉽게 만들 수 있어야 한다.

이 다섯 줄을 C# 8까지의 문법으로 옮기면 다음과 같다.

```csharp
public sealed class Point : IEquatable<Point>
{
    public double X { get; }
    public double Y { get; }

    public Point(double x, double y)
    {
        X = x;
        Y = y;
    }

    // 1) 구조적 동등성 — 강타입 버전
    public bool Equals(Point? other) =>
        other is not null && X == other.X && Y == other.Y;

    // 2) object 버전 (컬렉션이 비제네릭 경로를 탈 때 쓰인다)
    public override bool Equals(object? obj) => Equals(obj as Point);

    // 3) 해시 계약 — Equals가 true면 해시도 같아야 한다
    public override int GetHashCode() => HashCode.Combine(X, Y);

    // 4) 연산자 — Equals를 재정의했으면 ==도 맞춰야 한다
    public static bool operator ==(Point? a, Point? b) =>
        a is null ? b is null : a.Equals(b);
    public static bool operator !=(Point? a, Point? b) => !(a == b);

    // 5) 진단용 문자열
    public override string ToString() => $"Point {{ X = {X}, Y = {Y} }}";

    // 6) 분해
    public void Deconstruct(out double x, out double y)
    {
        x = X;
        y = Y;
    }

    // 7) 비파괴적 변경 — 프로퍼티마다 하나씩
    public Point WithX(double x) => new Point(x, Y);
    public Point WithY(double y) => new Point(X, y);
}
```

**60줄이다.** 그리고 이 코드에서 실제로 이 타입에 고유한 정보는 `double X`와 `double Y`, 딱 두 개다. 나머지는 전부 기계적 반복이다.

문제는 길이가 아니라 **깨지는 방식**이다. 여기에 `Z`를 추가한다고 하자. 고쳐야 할 곳이 일곱 군데다. 생성자, `Equals(Point)`, `GetHashCode`, `ToString`, `Deconstruct`, `WithZ` 추가, 그리고 기존 `WithX`/`WithY`. 하나라도 빠뜨리면 컴파일은 되고 동작만 틀린다. `GetHashCode`에서 `Z`를 빠뜨리면 딕셔너리는 여전히 "동작"한다 — 충돌이 늘어나 느려질 뿐이다. `Equals`에서 `Z`를 빠뜨리면 서로 다른 점이 같다고 나온다. 둘 다 테스트에 잡히지 않는 종류의 버그다.

> **⚠️ 이 보일러플레이트의 진짜 비용은 "쓰는 시간"이 아니라 "고치는 시간"이다**
>
> 필드를 추가할 때 함께 고쳐야 하는 지점의 개수를 **결합 지점**이라고 부르자. 위 `Point`의 결합 지점은 7이다. 필드가 열 개인 DTO에 필드 하나를 더하면, 개발자는 열 곳을 고치는 것이 아니라 **일곱 개 메서드 안의 열한 번째 항목**을 각각 찾아 넣어야 한다. 코드 리뷰에서 "`GetHashCode`에 `Z`가 빠졌다"를 잡아내는 사람은 드물다.
>
> 레코드의 결합 지점은 **1**이다. 선언에 `double Z`를 한 번 쓰면 끝이다.

### 세 가지 반복 노동

원서는 레코드가 해결하려 한 문제를 세 갈래로 정리한다.

**첫째, 비파괴적 변경(nondestructive mutation).** 불변 객체를 "수정"하려면 새 객체를 만들고 데이터를 복사하면서 변경분을 반영해야 한다. 성능 면에서는 생각만큼 비효율적이지 않다 — **얕은 복사(shallow copy)면 언제나 충분**하기 때문이다. 데이터가 불변이면 하위 객체와 컬렉션까지 복제하는 깊은 복사는 필요 없다. 그러나 **코딩 노력** 면에서는 대단히 비효율적이다. 프로퍼티가 많을수록 심해진다. 위 예제의 `WithX`/`WithY`는 프로퍼티가 여덟 개면 여덟 개가 되고, 각각이 나머지 일곱 개를 정확히 옮겨 적어야 한다.

**둘째, 동작 없이 데이터만 묶는 타입.** 함수형 스타일로 코드를 쓰다 보면 동작 없이 값만 조합한 타입이 계속 필요해진다. 이런 타입을 정의하는 데 필요한 노동은 마땅한 수준보다 크다. 매개변수 하나하나를 공개 프로퍼티에 대입하는 생성자를 써야 하고, 분해자도 있으면 좋다.

**셋째, 동등성의 의미.** 객체가 불변이라는 것의 귀결 중 하나는 **정체성(identity)이 변할 수 없다**는 것이다. 그렇다면 그런 타입에는 참조 동등성보다 **구조적 동등성**이 유용하다. 구조적 동등성이란 두 인스턴스의 데이터가 같으면 같은 것으로 본다는 뜻이다(튜플이 그렇다). 레코드는 기반 타입이 클래스든 구조체든 상관없이 **기본으로** 구조적 동등성을 준다.

```text
┌──────────────────────────────────────────────────────────────┐
│  불변 데이터 타입을 손으로 쓸 때의 노동 지도                     │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│   선언하고 싶은 것          실제로 써야 하는 것                 │
│   ─────────────────         ──────────────────                │
│   double X, Y        →      생성자                            │
│                             init 프로퍼티 ×2                   │
│                             Equals(T)      ┐                  │
│                             Equals(object) │ 동등성 4종 세트    │
│                             GetHashCode    │                  │
│                             ==, !=         ┘                  │
│                             IEquatable<T> 구현 선언            │
│                             ToString                          │
│                             Deconstruct                       │
│                             WithX, WithY (프로퍼티 수만큼)      │
│                                                              │
│   결합 지점 7개  ────────────►  레코드에서는 1개                │
└──────────────────────────────────────────────────────────────┘
```

### 레코드는 런타임 기능이 아니다

여기서 이 장 전체를 관통하는 사실 하나를 못 박아야 한다.

**레코드는 순수하게 C#의 컴파일 타임 구성물이다.** 런타임에 CLR이 보는 것은 그냥 클래스거나 그냥 구조체다. 다만 컴파일러가 **합성한(synthesized) 멤버 한 무더기**가 추가로 붙어 있을 뿐이다.

이 사실에서 여러 결론이 따라 나온다.

| 사실 | 귀결 |
|---|---|
| CLR에 `record` 개념이 없다 | `typeof(Point).IsRecord` 같은 API는 존재하지 않는다 |
| 합성 멤버는 평범한 IL 메서드다 | 리플렉션으로 보면 그냥 `Equals`, `GetHashCode`가 보인다 |
| `record`는 메타데이터 표식이 아니다 | C# 컴파일러는 다른 어셈블리의 타입이 레코드 **클래스**인지를 `<Clone>$` 멤버의 존재로 판정한다 |
| 새 IL 명령이 없다 | `with` 식도 결국 `callvirt` 두 번이다(19.4절) |
| 런타임 버전 요구가 없다 | 단 `init` 접근자가 `IsExternalInit` 타입을 요구한다(76.14절의 폴리필) |

> **📌 `record`를 지원하지 않는 대상 프레임워크에서 쓰기**
>
> 레코드 자체는 컴파일러 기능이므로 오래된 런타임에서도 원리상 동작한다. 걸림돌은 `init` 접근자가 참조하는 `System.Runtime.CompilerServices.IsExternalInit` 타입이다. 이 타입은 .NET 5부터 BCL에 있고, `netstandard2.0`이나 `net472`를 대상으로 하면 컴파일 오류가 난다. 컴파일러가 자동 생성해 주지 않으므로 직접 선언하거나 폴리필 패키지를 쓴다. 자세한 절차는 76.14절에 있다.

> **💡 "레코드는 DTO 전용"이라는 말은 절반만 맞다**
>
> 레코드가 데이터 전송 객체에 잘 맞는 것은 사실이다. 그러나 레코드는 클래스가 가질 수 있는 멤버를 **전부** 가질 수 있다 — 메서드, 정적 멤버, 이벤트, 인덱서, 중첩 타입, 인터페이스 구현, 상속. "데이터만 담아야 한다"는 규칙은 문법이 아니라 설계 취향이다. 실제로는 **잘 지어진 값 타입이 코드를 끌어당긴다.** `Money` 레코드를 만들면 결국 `Add`, `ConvertTo`, `Format` 같은 메서드가 그 안으로 들어오게 되고, 그것이 좋은 설계다(77.5절에서 같은 논지를 튜플과 대비해 다룬다).

## 19.2 `record class`와 `record struct` ※C# 9/10

### 세 가지 선언 형태

```csharp
record Point { }               // = record class. 기반 타입은 클래스
record class Point2 { }        // 위와 정확히 같은 의미
record struct Point3 { }       // ※C# 10. 기반 타입은 구조체
readonly record struct Point4 { }   // ※C# 10. 불변 구조체
```

`record`와 `record class`는 **완전히 같다.** `class` 키워드는 `record struct`와 눈으로 구분하기 좋으라고 허용된 것이지 의미 차이는 없다. 팀 컨벤션으로 `record class`를 강제하는 곳도 있고, 짧은 `record`를 쓰는 곳도 있다.

레코드 정의는 클래스·구조체 정의와 같은 종류의 멤버를 담을 수 있다. 필드, 프로퍼티, 메서드 무엇이든 들어간다. 레코드는 인터페이스를 구현할 수 있고, **클래스 기반 레코드는 다른 클래스 기반 레코드를 상속**할 수 있다.

가장 단순한 레코드는 `init` 전용 프로퍼티 몇 개와 생성자로 이루어진다.

```csharp
record Point
{
    public Point(double x, double y) => (X, Y) = (x, y);

    public double X { get; init; }
    public double Y { get; init; }
}
```

생성자 본문의 `(X, Y) = (x, y);`는 튜플 대입을 이용한 축약이다. 이 경우 `{ this.X = x; this.Y = y; }`와 같다(튜플 분해 대입은 77.6절).

### 상속 규칙

레코드의 상속 규칙은 좁고 명확하다.

| 시도 | 가능한가 | 이유 |
|---|---|---|
| `record B : A` (A도 레코드 클래스) | ✓ | 정상 경로 |
| `record B : SomeClass` | ✗ | 레코드는 레코드만 상속한다 |
| `class C : SomeRecord` | ✗ | 클래스는 레코드를 상속할 수 없다 |
| `record struct B : A` | ✗ | 구조체는 상속 자체가 불가(16.1절) |
| `abstract record Shape` | ✓ | 추상 레코드는 정상 문법 |
| `sealed record Point` | ✓ | 동등성 계층 문제를 원천 차단한다(19.7절) |
| `record Point : IComparable<Point>` | ✓ | 인터페이스 구현은 자유 |
| `static record` | ✗ | 존재하지 않는다 |

레코드 클래스가 레코드 클래스만 상속할 수 있는 것은 컴파일러가 만드는 합성 멤버 때문이다. 기반 타입이 `EqualityContract`나 `<Clone>$`를 갖고 있지 않으면 파생 레코드가 재정의할 대상이 없다(19.3절).

> **⚠️ `record`를 나중에 `class`로 바꾸는 것은 바이너리 호환성을 깬다**
>
> `record Point`를 `class Point`로 고치면 `==`의 의미가 값 비교에서 참조 비교로 조용히 바뀐다. 소비자 어셈블리가 다시 컴파일되지 않으면 `op_Equality` 메서드 자체가 사라져 `MissingMethodException` 계열의 런타임 실패가 나고, 다시 컴파일되면 **컴파일은 성공하고 의미만 달라진다.** 후자가 더 위험하다. 공개 API에서 `record` ↔ `class` 전환은 파괴적 변경 목록(78.13절)에 넣어야 한다.

### `record struct`는 왜 기본이 가변인가

`record struct`에 위치 매개변수를 쓰면 컴파일러는 `init` 전용이 아니라 **쓰기 가능한** 프로퍼티를 만든다. `record class`와 정반대다.

```csharp
public record struct P1(double X, double Y);            // X { get; set; }
public readonly record struct P2(double X, double Y);   // X { get; init; }
```

```csharp
var a = new P1(1, 2);
a.X = 8;               // 컴파일된다

var b = new P2(1, 2);
b.X = 8;               // 컴파일 오류
```

이 설계에는 근거가 있다. 원서의 설명은 이렇다. **전형적인 사용에서 불변성의 안전 이득은 구조체 자체가 불변이어서가 아니라 그 구조체가 사는 집(home)이 불변이어서 생긴다.**

```csharp
var test = new Immutable();
test.Field.X++;   // 금지 — Field가 readonly라서
test.Prop.X++;    // 금지 — Prop이 { get; }만 있어서

class Immutable
{
    public readonly Mutable Field;
    public Mutable Prop { get; }
}
struct Mutable { public int X, Y; }
```

`Mutable`은 완전히 가변인 구조체다. 그런데도 위 두 줄은 컴파일되지 않는다. 값 타입은 필드에서 읽는 순간 **복사**되고, `readonly` 필드나 `get`만 있는 프로퍼티에서 나온 복사본에는 대입할 수 없기 때문이다(16.2절, 16.5절).

```csharp
var test = new Immutable();
Mutable m = test.Prop;
m.X++;                   // 컴파일된다. 그러나...
```

이건 컴파일된다. 하지만 바뀌는 것은 **지역 변수 하나**다. `test.Prop`에는 아무 영향이 없다. 지역 변수를 변경하는 것은 유용한 최적화일 수 있고 불변 타입 시스템의 이점을 무효화하지 않는다.

반대로 `Field`를 쓰기 가능한 필드로, `Prop`을 쓰기 가능한 프로퍼티로 만들면 — `Mutable` 구조체가 어떻게 선언되었든 상관없이 — 내용을 통째로 교체할 수 있다. 즉 **구조체의 불변성보다 그것을 담은 자리의 불변성이 결정적**이다.

> **⚠️ 그래도 실무에서는 `readonly record struct`가 기본값이어야 한다**
>
> 위 논리는 설계 근거로는 타당하지만, 실무에서 가변 `record struct`가 만드는 사고는 실재한다. 대표적인 것이 **딕셔너리 키**다. `record struct` 인스턴스를 `Dictionary` 키로 넣은 뒤 원본 변수를 변경하면 — 키는 복사본이므로 딕셔너리 자체는 멀쩡하지만 — 같은 키를 다시 만들었다고 생각하고 조회하다 실패한다. 가변 값 타입이 만드는 함정 전체는 25.8절에 있다.
>
> 그리고 `readonly`를 붙이면 방어적 복사가 사라져 **성능도 유리하다**(16.5절). `readonly`로 시작해서 정말 못 하겠을 때만 푸는 것이 옳은 순서다.

### 세 형태 비교

| 항목 | `record class` | `record struct` | `readonly record struct` |
|---|---|---|---|
| 저장 위치 | 힙 | 인라인/스택 | 인라인/스택 |
| 위치 매개변수의 접근자 | `{ get; init; }` | `{ get; set; }` | `{ get; init; }` |
| 상속 | 가능 | 불가 | 불가 |
| `EqualityContract` | 있음 | 없음 | 없음 |
| 복사 생성자 / `<Clone>$` | 있음 | 없음 | 없음 |
| `with` 식의 구현 | `<Clone>$` 호출 | 값 복사 | 값 복사 |
| `null`이 될 수 있나 | 가능(참조) | 불가 | 불가 |
| `Equals` 합성 방식 | 필드별 + 타입 계약 | 필드별 | 필드별 |
| `IEquatable<T>` 구현 | 자동 | 자동 | 자동 |
| 기본값(`default`) | `null` | 모든 필드 0 | 모든 필드 0 |

> **⚠️ `record struct`에도 `default` 함정이 그대로 있다**
>
> `readonly record struct Money(decimal Amount, Currency Currency);`를 선언해도 `default(Money)`는 여전히 만들어진다. 배열 원소, 필드 기본값, `new Money[10]` 어디서든 나온다. 생성자에서 아무리 검증해도 **0으로 채워진 인스턴스는 그 검증을 통과하지 않고 존재한다.** `record`가 이 문제를 풀어 주지는 않는다. 값 타입에서 0이 유효한 상태여야 하는 이유는 16.4절에 있다.

> **📌 가변 `record class`도 문법상 가능하다**
>
> ```csharp
> record CarRecord
> {
>     public string Make { get; set; }
>     public string Model { get; set; }
> }
> ```
>
> `init` 대신 `set`을 쓰면 가변 레코드가 된다. 컴파일된다. 그러나 레코드 타입은 **불변 데이터 모델을 위해 만들어진 것**이고, 가변 레코드는 값 동등성과 조합될 때 25.8절의 함정으로 직행한다. 문법이 허용한다는 것과 써도 된다는 것은 다르다.

> **💡 언제 `record class`이고 언제 `record struct`인가**
>
> 판단 기준은 레코드냐 아니냐가 아니라 **참조 타입이냐 값 타입이냐**다. 그 결정 기준은 16.8절의 손익 계산법을 그대로 쓴다 — 크기(대략 16~24바이트 이하), 복사 빈도, `null`이 필요한지, 컬렉션에 대량으로 담기는지. 레코드는 그 결정 **다음에** 붙는 수식어다. "값 동등성이 필요하다"는 이유만으로 `record struct`를 고르면 안 된다. 큰 `record struct`를 여기저기 넘기면 복사 비용이 힙 할당보다 비싸지는 지점이 온다(19.8절).

## 19.3 컴파일러가 생성하는 멤버 — `Equals`, `GetHashCode`, `ToString`, `<Clone>$`, `Deconstruct`, `PrintMembers`

이 절이 이 장의 핵심이다. `record Point(double X, double Y);` 한 줄이 무엇이 되는지를 **하나도 빼지 않고** 본다.

### 전체 목록

`record class`(위치 매개변수 있음)가 생성하는 멤버는 다음과 같다.

| # | 멤버 | 시그니처(디컴파일 형태) | 조건 |
|---|---|---|---|
| 1 | 주 생성자 | `public Point(double X, double Y)` | 위치 매개변수가 있을 때 |
| 2 | `init` 프로퍼티 | `public double X { get; init; }` | 위치 매개변수마다 하나 |
| 3 | 백킹 필드 | `private readonly double <X>k__BackingField` | 프로퍼티마다 하나 |
| 4 | 동등성 계약 | `protected virtual Type EqualityContract { get; }` | 항상(레코드 클래스만) |
| 5 | 강타입 `Equals` | `public virtual bool Equals(Point? other)` | 항상 |
| 6 | `object` 버전 | `public override bool Equals(object? obj)` | 항상 |
| 7 | 해시 | `public override int GetHashCode()` | 항상 |
| 8 | 문자열 | `public override string ToString()` | 항상 |
| 9 | 멤버 출력 | `protected virtual bool PrintMembers(StringBuilder builder)` | 항상 |
| 10 | 같음 연산자 | `public static bool operator ==(Point? l, Point? r)` | 항상 |
| 11 | 다름 연산자 | `public static bool operator !=(Point? l, Point? r)` | 항상 |
| 12 | 복사 생성자 | `protected Point(Point original)` | 항상 |
| 13 | 복제 메서드 | `public virtual Point <Clone>$()` | 항상 |
| 14 | 분해자 | `public void Deconstruct(out double X, out double Y)` | 위치 매개변수가 있을 때 |
| 15 | 인터페이스 | `IEquatable<Point>` 구현 선언 | 항상 |

`record struct`는 4·12·13이 빠지고, 나머지의 접근성과 `readonly` 표시가 달라진다. 뒤에서 따로 본다.

먼저 IL 최상단부터 확인한다. `record CarRecord(string Make, string Model, string Color);`를 컴파일해 ildasm으로 열면 이렇게 보인다.

```il
.class private auto ansi beforefieldinit FunWithRecords.CarRecord
       extends [System.Runtime]System.Object
       implements class [System.Runtime]System.IEquatable`1<class FunWithRecords.CarRecord>
{
  .field private initonly string '<Make>k__BackingField'
  .field private initonly string '<Model>k__BackingField'
  .field private initonly string '<Color>k__BackingField'
  // ...
}
```

읽을 것이 셋이다.

- `extends System.Object` — 레코드는 별도의 기반 타입을 상속하지 않는다. 특별한 런타임 기반 클래스는 없다.
- `implements IEquatable<CarRecord>` — 컴파일러가 인터페이스 구현을 대신 선언해 준다.
- `initonly` 백킹 필드 — `init` 전용 프로퍼티의 백킹 필드는 `readonly`(IL 키워드로는 `initonly`)다. 즉 생성자 밖에서는 IL 수준에서도 대입할 수 없다.

> **📌 `init` 프로퍼티의 백킹 필드가 `readonly`인 것이 왜 중요한가**
>
> `init` 접근자는 "객체 초기화자와 생성자 안에서만 호출할 수 있다"는 **C# 컴파일러의 규칙**이다. 그런데 백킹 필드까지 `initonly`이므로, 리플렉션으로 `set_X`를 우회해 필드를 직접 쓰려는 시도도 CLR 수준의 제약을 만난다(가능은 하지만 정상 경로가 아니다). 다만 이는 **자동 구현 프로퍼티일 때** 이야기다. 백킹 필드를 직접 선언하고 `init` 접근자를 손으로 쓰면 그 필드는 `readonly`가 아니다(19.5절).

### 1) 복사 생성자와 `<Clone>$`

레코드 클래스에 대해 컴파일러가 하는 가장 중요한 일이 이것이다.

```csharp
// 컴파일러가 만드는 것 (디컴파일 형태)
protected Point(Point original)
{
    <X>k__BackingField = original.<X>k__BackingField;
    <Y>k__BackingField = original.<Y>k__BackingField;
}

public virtual Point <Clone>$() => new Point(this);
```

복사 생성자는 `protected`다. 외부에서 호출할 수 없다. 그래서 컴파일러는 그것을 감싸는 **공개 메서드**를 하나 더 만든다. 이름이 `<Clone>$`다. 꺾쇠와 달러 기호가 들어간 이름은 C# 식별자 규칙상 쓸 수 없다 — 의도적이다. **말할 수 없는 이름(unspeakable name)** 을 써서 사용자 코드와 절대 충돌하지 않게 한 것이다.

IL은 이렇다.

```il
.method public hidebysig newslot virtual
        instance class Point '<Clone>$'() cil managed
{
  .custom instance void [System.Runtime]System.Runtime.CompilerServices.CompilerGeneratedAttribute::.ctor() = ( 01 00 00 00 )
  .maxstack  8
  IL_0000:  ldarg.0
  IL_0001:  newobj     instance void Point::.ctor(class Point)
  IL_0006:  ret
}
```

`ldarg.0`(자기 자신)을 밀어 넣고 복사 생성자를 `newobj`로 호출해 반환한다. 세 줄이다.

`newslot virtual`에 주목한다. `<Clone>$`는 **가상 메서드**다. 파생 레코드에서는 공변 반환(covariant return, ※C# 9)을 이용해 재정의된다.

```csharp
// record Point3D(double X, double Y, double Z) : Point(X, Y);
public override Point3D <Clone>$() => new Point3D(this);
```

반환 타입이 `Point`가 아니라 `Point3D`다. 이 때문에 기반 타입 변수에 담긴 파생 레코드에 `with`를 써도 **파생 타입 인스턴스가 나온다**(19.4절).

> **⚠️ 레코드에는 `Clone`이라는 이름의 멤버를 선언할 수 없다**
>
> `<Clone>$`와 이름이 충돌해 컴파일 오류가 난다. `ICloneable`을 구현하려고 `public object Clone()`을 쓰려던 순간 막힌다. 애초에 `ICloneable`은 얕은 복사인지 깊은 복사인지 계약이 없어 권장되지 않는 인터페이스이고(18.11절, 78.7절), 레코드는 `with` 식이 그 자리를 대신한다.

### 2) `EqualityContract`

레코드 클래스에만 있는 멤버다. **런타임 타입을 동등성 비교에 끌어들이기 위한 장치**다.

```csharp
protected virtual Type EqualityContract => typeof(Point);
```

IL은 이렇다.

```il
.method family hidebysig specialname newslot virtual
        instance class [System.Runtime]System.Type get_EqualityContract() cil managed
{
  .custom instance void [System.Runtime]System.Runtime.CompilerServices.CompilerGeneratedAttribute::.ctor() = ( 01 00 00 00 )
  .maxstack  8
  IL_0000:  ldtoken    Point
  IL_0005:  call       class [System.Runtime]System.Type
                       [System.Runtime]System.Type::GetTypeFromHandle(valuetype [System.Runtime]System.RuntimeTypeHandle)
  IL_000a:  ret
}
```

`family`는 IL에서 `protected`를 뜻한다. 본문은 `typeof(Point)`의 표준 확장 — `ldtoken` + `Type.GetTypeFromHandle` — 그대로다.

접근성 규칙은 다음과 같다.

| 레코드 형태 | `EqualityContract` |
|---|---|
| 봉인되지 않은 레코드(기반 레코드 없음) | `protected virtual` |
| 파생 레코드 | `override` (`typeof(파생타입)` 반환) |
| `sealed` 레코드(기반 레코드 없음) | `private` — 재정의 대상이 없으므로 노출할 이유가 없다 |
| `record struct` | **생성되지 않는다** |

`record struct`에 없는 이유는 단순하다. 구조체는 상속되지 않으므로 **컴파일 시점에 정확한 타입을 이미 안다.** 런타임 타입을 물어볼 이유가 없다.

### 3) `Equals` 두 벌

```csharp
public override bool Equals(object? obj) => Equals(obj as Point);

public virtual bool Equals(Point? other) =>
    (object)this == other
    || ((object)other != null
        && EqualityContract == other.EqualityContract
        && EqualityComparer<double>.Default.Equals(<X>k__BackingField, other.<X>k__BackingField)
        && EqualityComparer<double>.Default.Equals(<Y>k__BackingField, other.<Y>k__BackingField));
```

읽을 지점이 네 개다.

**첫째, 참조 동일성 단축.** `(object)this == other`가 참이면 즉시 `true`다. 같은 객체를 자기 자신과 비교하는 흔한 경우를 필드 비교 없이 끝낸다.

**둘째, `EqualityContract` 비교.** 두 인스턴스의 런타임 타입이 다르면 필드를 볼 것도 없이 `false`다. `Type` 인스턴스는 프로세스 안에서 유일하므로 `==` 비교가 참조 비교가 되어 값싸다.

**셋째, 프로퍼티가 아니라 백킹 필드를 읽는다.** `other.X`가 아니라 `other.<X>k__BackingField`다. 프로퍼티 접근자에 로직이 들어 있어도 우회한다.

**넷째, `EqualityComparer<T>.Default`를 쓴다.** `X == other.X`가 아니다. 이 선택에는 이유가 있다.

- 필드 타입이 `IEquatable<T>`를 구현하면 그 강타입 `Equals`를 쓴다 — 박싱이 없다(18.6절).
- 필드 타입이 `null`일 수 있는 참조 타입이어도 `NullReferenceException`이 나지 않는다.
- 필드 타입이 `T`(제네릭 매개변수)여도 동작한다.
- 값 타입 인자에 대해 JIT이 `EqualityComparer<T>.Default`를 **디버추얼라이즈**해 인라인하므로, `double` 같은 원시 타입에서는 결국 `ceq` 한 개로 줄어든다.

즉 소스에 보이는 형태는 무겁지만 **최적화 후 기계어는 직접 비교와 같다.**

파생 레코드에서는 형태가 달라진다.

```csharp
// record Point3D(double X, double Y, double Z) : Point(X, Y);

public override bool Equals(object? obj) => Equals(obj as Point3D);

// 기반의 강타입 Equals를 sealed로 재정의해 파생 버전으로 넘긴다
public sealed override bool Equals(Point? other) => Equals((object?)other);

public virtual bool Equals(Point3D? other) =>
    base.Equals((Point?)other)
    && EqualityComparer<double>.Default.Equals(<Z>k__BackingField, other.<Z>k__BackingField);
```

세 겹이다. `object` 버전은 파생 타입으로 캐스팅해 넘기고, 기반의 강타입 버전은 `sealed override`로 막아 파생 버전으로 우회시키고, 파생 버전은 `base.Equals`를 호출한 뒤 자기 필드만 추가로 비교한다. **각 레코드는 자기 필드만 책임진다** — 상속 계층이 깊어져도 코드가 폭발하지 않는 구조다.

> **⚠️ `Equals(object)`는 직접 선언할 수 없다**
>
> 레코드 안에 `public override bool Equals(object? obj)`를 쓰면 컴파일 오류다. 컴파일러가 반드시 자기 버전을 만들기 때문이다. 동등성을 바꾸고 싶으면 **강타입 버전**을 재정의해야 한다(19.7절). 클래스·구조체에서 하던 습관이 여기서 막힌다.

### 4) `GetHashCode`

```csharp
public override int GetHashCode() =>
    (EqualityComparer<Type>.Default.GetHashCode(EqualityContract) * -1521134295
     + EqualityComparer<double>.Default.GetHashCode(<X>k__BackingField)) * -1521134295
    + EqualityComparer<double>.Default.GetHashCode(<Y>k__BackingField);
```

곱셈 상수 `-1521134295`(16진수로 `0xA5555529`)는 Roslyn이 합성 해시에 쓰는 고정 값이다. 각 항을 곱하고 더하는 이 형태는 흔히 쓰이는 다항식 해시 결합과 같은 계열이다.

주목할 점 셋.

- **`EqualityContract`가 해시에도 들어간다.** `Point(1,2)`와 `Point3D(1,2,0)`은 해시부터 다르다.
- 파생 레코드에서는 첫 항이 `base.GetHashCode()`로 바뀐다.
- **`HashCode.Combine`을 쓰지 않는다.** 손으로 쓴 코드에서는 `HashCode.Combine(X, Y)`가 권장되지만(25.4절), 합성 코드는 상속 계층에서 기반 해시를 이어붙여야 하므로 결합 가능한 형태를 쓴다.

> **⚠️ 레코드의 해시값은 프로세스 간·버전 간에 안정적이지 않다**
>
> `string.GetHashCode`가 프로세스마다 다른 값을 내는 것(25.4절)과 같은 이유로, 문자열 필드를 가진 레코드의 해시값도 실행할 때마다 달라진다. **해시값을 파일이나 DB에 저장하거나 캐시 키로 직렬화하면 안 된다.** 이 규칙은 레코드라고 달라지지 않는다.

### 5) `ToString`과 `PrintMembers`

레코드의 `ToString`은 둘로 나뉜다. 껍데기와 내용이다.

```csharp
public override string ToString()
{
    StringBuilder stringBuilder = new StringBuilder();
    stringBuilder.Append("Point");
    stringBuilder.Append(" { ");
    if (PrintMembers(stringBuilder))
        stringBuilder.Append(' ');
    stringBuilder.Append('}');
    return stringBuilder.ToString();
}

protected virtual bool PrintMembers(StringBuilder builder)
{
    builder.Append("X = ");
    builder.Append(X.ToString());
    builder.Append(", Y = ");
    builder.Append(Y.ToString());
    return true;      // 하나라도 출력했으면 true
}
```

출력은 이렇다.

```text
Point { X = 3, Y = 4 }
```

`PrintMembers`의 반환값은 "**내가 무언가를 출력했는가**"다. 멤버가 하나도 없는 레코드에서는 `false`를 반환하고, 그러면 `ToString`은 공백을 넣지 않아 `Empty { }`가 된다.

파생 레코드에서는 이렇게 이어붙인다.

```csharp
// Point3D
protected override bool PrintMembers(StringBuilder builder)
{
    if (base.PrintMembers(builder))
        builder.Append(", ");
    builder.Append("Z = ");
    builder.Append(Z.ToString());
    return true;
}
```

```text
Point3D { X = 3, Y = 4, Z = 5 }
```

타입 이름은 `ToString`이 붙이고, 그 타입 이름은 **정적으로 박힌 문자열**이다. `Point`의 `ToString`은 `"Point"`를 쓰고 `Point3D`의 `ToString`은 `"Point3D"`를 쓴다. `GetType().Name`을 호출하지 않으므로 리플렉션 비용이 없다.

> **💡 `PrintMembers`만 재정의하면 출력에서 필드를 뺄 수 있다**
>
> 비밀번호 해시나 토큰을 담은 레코드가 로그에 통째로 찍히는 사고는 흔하다. `ToString` 전체를 다시 쓰는 대신 `PrintMembers`만 바꾸면 `타입명 { ... }` 형식은 유지하면서 내용만 통제할 수 있다.
>
> ```csharp
> public record Credentials(string User, string Token)
> {
>     protected override bool PrintMembers(StringBuilder builder)
>     {
>         builder.Append("User = ").Append(User);
>         builder.Append(", Token = ***");
>         return true;
>     }
> }
> ```
>
> 더 확실하게 막으려면 `public sealed override string ToString()`으로 봉인해 파생 레코드가 다시 열지 못하게 한다.

> **⚠️ 레코드의 `ToString`은 진단용이지 직렬화 형식이 아니다**
>
> `Point { X = 3, Y = 4 }`는 사람이 읽으라고 만든 형식이다. 파싱 가능한 왕복(round-trip) 형식이 아니고, 숫자·날짜의 문화권 처리도 각 멤버의 `ToString()`에 위임된다. 로그에는 좋지만 **저장 형식이나 프로토콜에 쓰면 안 된다.**

### 6) `==`와 `!=`

```csharp
public static bool operator ==(Point? left, Point? right) =>
    (object)left == right || ((object)left != null && left.Equals(right));

public static bool operator !=(Point? left, Point? right) => !(left == right);
```

`op_Equality`는 `Equals`에 위임한다. 그리고 `Equals`는 가상이다. 따라서 `Point == Point` 비교에서 실제 인스턴스가 `Point3D`라도 **파생 타입의 `Equals`가 불린다.**

> **⚠️ `==`는 정적으로 해석된다 — `object`로 담으면 참조 비교가 된다**
>
> ```csharp
> var p1 = new Point(1, 2);
> var p2 = new Point(1, 2);
>
> Console.WriteLine(p1 == p2);              // True  — Point의 op_Equality
>
> object o1 = p1, o2 = p2;
> Console.WriteLine(o1 == o2);              // False — object의 참조 비교
> Console.WriteLine(o1.Equals(o2));         // True  — 가상 디스패치
> ```
>
> 연산자는 가상이 아니다(15장). 제네릭 메서드 안에서 `T a, T b`를 `==`로 비교하는 코드도 같은 이유로 위험하다 — 제약이 없으면 컴파일조차 되지 않고, `where T : class` 제약을 걸면 참조 비교가 된다. 제네릭 코드에서는 `EqualityComparer<T>.Default.Equals(a, b)`를 쓴다(23.6절, 25.7절).

### 7) `Deconstruct`

위치 매개변수가 있을 때만 생성된다.

```csharp
public void Deconstruct(out double X, out double Y)
{
    X = this.X;
    Y = this.Y;
}
```

`out` 매개변수 이름은 선언의 매개변수 이름을 그대로 따르지만, 호출하는 쪽에서는 **위치만 맞으면** 어떤 이름을 써도 된다.

```csharp
CarRecord car = new CarRecord("Honda", "Pilot", "Blue");

car.Deconstruct(out string make, out string model, out string color);
car.Deconstruct(out string a, out string b, out string c);   // 이름은 무관, 순서가 전부
var (make2, model2, color2) = car;                            // 튜플 분해 문법
```

세 번째 형태가 실제로 많이 쓰인다. 분해 대입의 규칙 전체는 13.5절과 77.6절에 있다. 그리고 `Deconstruct`가 있기 때문에 레코드는 **위치 패턴**에 바로 쓸 수 있다(77.10절).

### `record struct`가 생성하는 것

`readonly record struct Point(double X, double Y);`가 만드는 멤버는 이렇다.

```csharp
public readonly struct Point : IEquatable<Point>
{
    public double X { get; init; }
    public double Y { get; init; }

    public Point(double X, double Y)
    {
        this.X = X;
        this.Y = Y;
    }

    public override readonly bool Equals(object? obj) => obj is Point other && Equals(other);

    public readonly bool Equals(Point other) =>
        EqualityComparer<double>.Default.Equals(<X>k__BackingField, other.<X>k__BackingField)
        && EqualityComparer<double>.Default.Equals(<Y>k__BackingField, other.<Y>k__BackingField);

    public override readonly int GetHashCode() =>
        EqualityComparer<double>.Default.GetHashCode(<X>k__BackingField) * -1521134295
        + EqualityComparer<double>.Default.GetHashCode(<Y>k__BackingField);

    public static bool operator ==(Point left, Point right) => left.Equals(right);
    public static bool operator !=(Point left, Point right) => !(left == right);

    public override readonly string ToString() { /* record class와 같은 형태 */ }
    private readonly bool PrintMembers(StringBuilder builder) { /* ... */ }

    public readonly void Deconstruct(out double X, out double Y) { X = this.X; Y = this.Y; }
}
```

레코드 클래스와의 차이를 정리하면 이렇다.

| 항목 | `record class` | `record struct` |
|---|---|---|
| `EqualityContract` | 있음 | 없음 (타입이 확정적) |
| 복사 생성자 / `<Clone>$` | 있음 | 없음 (`with`가 값 복사) |
| `Equals(object)` | `Equals(obj as T)` | `obj is T other && Equals(other)` |
| 강타입 `Equals` | `public virtual` | `public readonly` (가상 아님) |
| `PrintMembers` | `protected virtual` | `private readonly` (상속이 없으므로) |
| `==` 피연산자 | `T?` (널 허용) | `T` (널 불가) |
| 참조 동일성 단축 | 있음 | 없음 (의미가 없다) |
| 합성 멤버의 `readonly` | 해당 없음 | 전부 `readonly`로 표시 |

`Equals(object)`가 `obj is Point other && Equals(other)`인 것은 언박싱 검사와 캐스팅을 한 번에 하기 위해서다. 이 경로에서는 **박싱이 이미 일어난 뒤**이므로(15장), 성능이 중요한 곳에서는 강타입 `Equals`가 불리게 해야 한다 — `EqualityComparer<T>.Default`가 `IEquatable<T>`를 찾아 그렇게 해 준다.

> **📌 `record struct`가 `ValueType.Equals`를 대체하는 것이 요점이다**
>
> 아무것도 재정의하지 않은 구조체의 `Equals`는 리플렉션과 박싱을 함께 요구한다(16.7절, 54.6절). `record struct`가 만드는 `Equals`는 **필드별 비교 코드**이므로 이 경로를 완전히 우회한다. 값 타입에 동등성이 필요하면 손으로 네 벌을 쓰는 대신 `readonly record struct`를 쓰는 것이 기본 선택인 이유가 이것이다.

### 무엇을 직접 재정의할 수 있고 무엇을 할 수 없는가

레코드는 "전부 자동"이 아니라 **부분적으로 열려 있다.** 어디가 열려 있는지가 실무에서 중요하다.

| 멤버 | 직접 선언 | 선언할 때의 규칙 |
|---|---|---|
| `ToString()` | ✓ | 보통의 `override`. `sealed override`로 봉인 가능 |
| `PrintMembers` | ✓ | 시그니처가 정확해야 한다. 클래스는 `protected virtual`/`override`, `sealed` 레코드와 `record struct`는 `private` |
| `GetHashCode()` | ✓ | 보통의 `override`. `Equals`를 바꿨으면 **반드시 함께** 바꾼다 |
| 강타입 `Equals(T)` | ✓ | `override`가 아니라 **`public virtual bool Equals(T? other)`** (`record struct`는 `public readonly bool`) |
| `Equals(object)` | ✗ | 컴파일 오류. 컴파일러가 항상 만든다 |
| `EqualityContract` | ✓ | 가능하지만 필요한 경우가 거의 없다 |
| `==` / `!=` | ✗ | 컴파일 오류. `Equals`를 통해서만 바꾼다 |
| `<Clone>$` | ✗ | 이름을 쓸 수 없다. `Clone`이라는 멤버도 선언 금지 |
| 복사 생성자 `protected T(T)` | ✓ | **대체만 가능하고 보강은 불가**(19.4절) |
| `Deconstruct` | ✓ | 같은 인자 개수로 선언하면 컴파일러 생성본이 나오지 않는다 |
| 위치 매개변수와 같은 시그니처의 생성자 | ✗ | 주 생성자와 충돌한다 |
| `IEquatable<T>` 명시적 구현 | 사실상 불필요 | 컴파일러가 이미 구현 선언을 넣는다 |

> **💡 레코드를 커스터마이즈할 때의 순서**
>
> 1. **출력만 바꾸고 싶다** → `PrintMembers` 재정의.
> 2. **비교에서 필드를 빼고 싶다** → 강타입 `Equals(T)` + `GetHashCode` 재정의.
> 3. **복사 방식을 바꾸고 싶다** → 복사 생성자 직접 작성.
> 4. **그 이상이 필요하다** → 레코드가 맞는 도구인지 다시 생각한다. 넷 이상을 손으로 쓰고 있다면 평범한 클래스로 쓰는 편이 읽기 쉽다.

> **⚠️ 합성 멤버는 `[CompilerGenerated]`가 붙는다 — 코드 커버리지가 왜곡된다**
>
> 레코드가 만드는 멤버에는 `CompilerGeneratedAttribute`가 붙는다. 커버리지 도구 대부분이 이 특성을 보고 제외하지만, 설정에 따라 **한 번도 호출되지 않은 `PrintMembers`와 `Deconstruct`가 미커버 라인으로 집계**되어 커버리지가 갑자기 떨어지는 일이 있다. 레코드를 대량 도입한 뒤 커버리지 수치가 흔들리면 이 설정을 먼저 본다.

## 19.4 비파괴적 변경 — `with` 식

### 문법

```csharp
Point p1 = new Point(3, 3);
Point p2 = p1 with { Y = 4 };
Console.WriteLine(p2);           // Point { X = 3, Y = 4 }

record Point(double X, double Y);
```

`p2`는 `p1`의 복사본이되 `Y`만 4다. 프로퍼티가 많아질수록 이득이 커진다.

```csharp
Test t1 = new Test(1, 2, 3, 4, 5, 6, 7, 8);
Test t2 = t1 with { A = 10, C = 30 };
Console.WriteLine(t2);

record Test(int A, int B, int C, int D, int E, int F, int G, int H);
```

```text
Test { A = 10, B = 2, C = 30, D = 4, E = 5, F = 6, G = 7, H = 8 }
```

`with` 뒤의 중괄호 안은 **객체 초기화자와 같은 문법**이다. 다만 대상이 새로 생성되는 복제본이라는 점이 다르다.

### 두 단계로 일어난다

비파괴적 변경은 정확히 두 단계다.

1. **복사 생성자가 레코드를 복제한다.** 기본 구현은 레코드의 **밑바탕 필드를 하나씩** 복사한다. `init` 접근자에 있는 로직을 (그 비용까지) 건너뛰면서 충실한 복제본을 만든다. 공개·비공개 필드는 물론 자동 프로퍼티의 숨은 백킹 필드까지 **전부** 포함된다.
2. **멤버 초기화자 목록의 각 프로퍼티가 갱신된다.** 이번에는 `init` 접근자를 통한다.

컴파일러는 다음 코드를

```csharp
Test t2 = t1 with { A = 10, C = 30 };
```

기능적으로 다음과 같은 것으로 번역한다.

```csharp
Test t2 = new Test(t1);   // 복사 생성자로 t1을 필드 단위로 복제
t2.A = 10;                // 프로퍼티 A 갱신
t2.C = 30;                // 프로퍼티 C 갱신
```

이 코드를 그대로 쓰면 컴파일되지 않는다. `A`와 `C`가 `init` 전용이기 때문이다. 게다가 복사 생성자는 `protected`다. C#은 레코드에 써 넣은 공개 은닉 메서드 `<Clone>$`를 통해 이 제약을 우회한다.

실제 IL은 이렇다.

```il
// Point p2 = p1 with { Y = 4 };
IL_0000:  ldloc.0                                        // p1
IL_0001:  callvirt   instance class Point Point::'<Clone>$'()
IL_0006:  dup
IL_0007:  ldc.r8     4.0
IL_0010:  callvirt   instance void Point::set_Y(float64)
IL_0015:  stloc.1                                        // p2
```

읽을 것은 셋이다.

- **`callvirt <Clone>$`** — 가상 호출이다. 정적 타입이 아니라 **런타임 타입의 복제 메서드**가 불린다.
- **`dup`** — 복제본 참조를 스택에 하나 더 쌓아 두고 `set_Y`를 호출한 뒤 그것을 지역 변수에 저장한다. 객체 초기화자와 같은 패턴이다.
- **`callvirt set_Y`** — `init` 접근자는 IL 수준에서 그냥 세터다. `init`이라는 제약은 리턴 타입에 붙은 `modreq(IsExternalInit)`으로만 표시되고, **강제하는 주체는 C# 컴파일러**다.

```text
┌───────────────────────────────────────────────────────────────────┐
│  p1 with { Y = 4 } 의 실행 흐름                                     │
├───────────────────────────────────────────────────────────────────┤
│                                                                   │
│   p1 ──► <Clone>$()                                               │
│           │                                                       │
│           └─► new Point(p1)          [protected 복사 생성자]        │
│                  │                                                │
│                  ├─ <X>k__BackingField = p1.<X>k__BackingField    │
│                  └─ <Y>k__BackingField = p1.<Y>k__BackingField    │
│                          ↓                                        │
│                   힙에 새 객체 (필드 단위 복제)                       │
│                          ↓                                        │
│                   set_Y(4)           [init 접근자 — 검증 실행됨]     │
│                          ↓                                        │
│                         p2                                        │
│                                                                   │
│   ※ 1단계는 접근자를 건너뛰고, 2단계만 접근자를 통과한다.              │
└───────────────────────────────────────────────────────────────────┘
```

이 비대칭이 19.5절의 유효성 검사 설계 전체를 결정한다.

### 얕은 복사라는 것

복사 생성자는 **필드를 그대로 옮긴다.** 필드가 참조 타입이면 참조가 복사되지 가리키는 객체가 복제되지는 않는다.

```csharp
record Order(string Id, List<string> Items);

var o1 = new Order("A", new List<string> { "x" });
var o2 = o1 with { Id = "B" };

o2.Items.Add("y");
Console.WriteLine(o1.Items.Count);        // 2 — 같은 리스트를 공유한다
Console.WriteLine(ReferenceEquals(o1.Items, o2.Items));   // True
```

> **⚠️ 얕은 복사는 버그가 아니라 설계다 — 그러나 값 의미론을 거짓말로 만든다**
>
> 데이터가 진짜로 불변이면 얕은 복사로 충분하다. 이것이 19.1절에서 본 원리다. 문제는 **가변 컬렉션을 레코드 멤버로 두는 순간** 그 전제가 무너진다는 점이다.
>
> 위 `Order`는 두 방향으로 배신한다.
> - `with`로 만든 복제본이 원본의 리스트를 공유한다(위 예제).
> - 합성된 `Equals`/`GetHashCode`가 `List<string>`에 대해 `EqualityComparer<List<string>>.Default`를 쓰는데, `List<T>`는 `IEquatable<T>`를 구현하지 않으므로 **참조 비교와 참조 해시**가 된다. 내용이 같은 두 리스트를 가진 두 주문이 서로 다르다고 나오고, 리스트 내용을 바꿔도 해시는 그대로다.
>
> 해법은 셋 중 하나다. (가) `ImmutableArray<T>` 같은 불변 컬렉션을 쓴다(24.10절). (나) 생성자에서 방어적 복사를 하고 읽기 전용 뷰로 노출한다. (다) 동등성을 직접 재정의한다(19.7절).

### 복사 생성자를 직접 쓰기

필요하면 복사 생성자를 직접 정의할 수 있다. 그러면 컴파일러는 자기 것을 쓰지 않고 이쪽을 쓴다.

```csharp
protected Point(Point original)
{
    this.X = original.X;
    this.Y = original.Y;
}
```

직접 쓰는 것이 유용한 경우는 둘이다. **레코드가 복제해야 할 가변 하위 객체나 컬렉션을 갖고 있을 때**, 그리고 **비워야 할 계산 필드가 있을 때**(19.5절)다.

> **⚠️ 복사 생성자는 대체만 되고 보강은 안 된다**
>
> 컴파일러가 만든 것에 "한 줄만 덧붙이는" 방법은 없다. 직접 쓰기로 한 순간 **모든 필드의 복사를 자기가 책임진다.** 필드를 나중에 하나 추가하고 복사 생성자에 넣는 것을 잊으면, `with`로 만든 복제본에서 그 필드만 기본값이 된다. 컴파일러는 아무 경고도 하지 않는다. 19.1절에서 없앤 결합 지점을 손으로 되살리는 셈이므로, 정말 필요할 때만 쓴다.

상속 계층에서는 복사 생성자가 **자기 필드만** 책임진다. 기반 레코드의 필드를 복사하려면 기반에 위임해야 한다.

```csharp
protected Point3D(Point3D original) : base(original)
{
    // 여기서는 Z만 처리한다
}
```

### 상속 계층에서의 `with`

`<Clone>$`가 가상이라는 사실이 여기서 드러난다.

```csharp
record Person(string Name);
record Employee(string Name, string Dept) : Person(Name);

Person p = new Employee("Jon", "Dev");
Person q = p with { Name = "Amy" };

Console.WriteLine(q.GetType().Name);     // Employee
Console.WriteLine(q);                    // Employee { Name = Amy, Dept = Dev }
```

정적 타입이 `Person`이어도 `<Clone>$`는 런타임 타입인 `Employee`의 것이 불리고, 그 결과 `Employee` 인스턴스가 나온다. `Dept`도 보존된다. 손으로 쓴 `With` 메서드였다면 **슬라이싱**이 일어나 `Person`이 되었을 것이다.

> **⚠️ 그러나 정적 타입에 없는 프로퍼티는 `with`로 바꿀 수 없다**
>
> ```csharp
> Person p = new Employee("Jon", "Dev");
> Person q = p with { Dept = "Sales" };   // 컴파일 오류 — Person에 Dept가 없다
> ```
>
> 복제본의 **런타임 타입**은 `Employee`지만, `with` 중괄호 안의 이름 해석은 **정적 타입** `Person`에서 이루어진다. 다형적으로 다루는 레코드 계층에서 `with`를 쓰려면 먼저 캐스팅하거나 패턴 매칭으로 좁혀야 한다(77.7절).

### `record struct`의 `with`

값 타입에는 복제 메서드가 없다. 그럴 필요가 없기 때문이다.

```csharp
readonly record struct Point(double X, double Y);

var a = new Point(1, 2);
var b = a with { Y = 5 };
```

컴파일러가 만드는 것은 대략 이렇다.

```csharp
Point temp = a;     // 값 복사 — 그냥 스택 위의 비트 복사
temp.Y = 5;         // init 접근자 호출 (with 식 안에서는 허용된다)
Point b = temp;
```

힙 할당이 없다. `readonly record struct`인데도 `Y`에 대입할 수 있는 이유는, `with` 식이 **객체 초기화 문맥**이어서 `init` 접근자 호출이 허용되기 때문이다.

> **📌 익명 타입도 `with`를 지원한다 ※C# 10**
>
> ```csharp
> var a1 = new { A = 1, B = 2, C = 3, D = 4, E = 5 };
> var a2 = a1 with { E = 10 };
> Console.WriteLine(a2);      // { A = 1, B = 2, C = 3, D = 4, E = 10 }
> ```
>
> 익명 타입은 원래부터 불변이고 구조적 동등성을 갖는다. C# 10부터 `with`까지 붙어 레코드와의 거리가 더 좁아졌다. 같은 C# 10 확장으로 **레코드가 아닌 평범한 구조체에도 `with`를 쓸 수 있다** — 값 복사 뒤 세터를 부르는 것뿐이므로 복제 메서드가 필요 없기 때문이다(동등성은 따라오지 않는다). 그래도 익명 타입은 **메서드 밖으로 반환할 수 없다**(반환 타입에 `var`를 쓸 수 없으므로). 이 차이가 선택의 기준이다(19.8절 선택표, 77.5절).

### 성능 — `with` 연쇄의 대가

`with` 한 번은 **레코드 클래스에서 힙 할당 한 번**이다. 이것을 파이프라인처럼 이어붙이면 중간 객체가 그만큼 쌓인다.

```csharp
// 예시 — 다섯 번의 with = 다섯 개의 힙 객체
var final = original
    with { A = 1 }
    with { B = 2 }
    with { C = 3 }
    with { D = 4 }
    with { E = 5 };
```

앞의 넷은 **즉시 쓰레기가 된다.** 0세대에 짧게 살다 죽는 객체라 GC 관점에서는 가장 싼 종류지만(64장), 핫 패스에서 초당 수백만 번 일어나면 이야기가 다르다.

| 상황 | 비용 | 대응 |
|---|---|---|
| `record class`에 `with` 한 번 | 힙 할당 1회 + 필드 복사 | 대개 무시 가능 |
| 반복문 안의 `with` 연쇄 | 반복 횟수 × 단계 수 만큼의 할당 | 한 번의 `with`에 여러 프로퍼티를 모아 쓴다 |
| LINQ 파이프라인마다 `with` | 원소 수 × 할당 | 마지막 단계에서 한 번만 |
| `record struct`에 `with` | 할당 없음, 값 복사 | 구조체가 크면 복사가 비싸진다 |
| 큰 `record struct`(필드 8개 초과)를 반복 복사 | 스택 트래픽 | `record class` 또는 `in` 매개변수 검토 |

**한 번의 `with`에 여러 프로퍼티를 넣는 것이 언제나 낫다.**

```csharp
var final = original with { A = 1, B = 2, C = 3, D = 4, E = 5 };   // 할당 1회
```

숨은 할당 카탈로그의 관점에서 `with`가 어디에 위치하는지는 63.9절에, 할당을 실제로 줄이는 전략은 69.1절에 있다.

> **💡 불변 자료구조와 "구조 공유"는 다른 이야기다**
>
> 함수형 언어의 불변 리스트는 `with`에 해당하는 연산이 O(1)이거나 O(log n)이다. 트리 구조를 공유하기 때문이다. 레코드의 `with`는 그런 최적화를 하지 않는다 — **필드 전부를 복사하는 O(필드 수) 연산**이다. 필드가 여섯 개인 레코드라면 이 비용은 무시할 만하지만, 프로퍼티 40개짜리 설정 객체를 요청마다 `with`로 스무 번 갱신하는 코드는 측정해 볼 값어치가 있다(67.5절).

## 19.5 프로퍼티 유효성 검사와 계산 필드·지연 평가

### `init` 접근자에 검증 넣기

명시적 프로퍼티를 쓰면 `init` 접근자에 검증 로직을 넣을 수 있다. 아래 예제는 `X`가 절대 `NaN`이 되지 않게 한다.

```csharp
record Point
{
    // 주의: x를 _x 필드가 아니라 X 프로퍼티에 대입한다
    public Point(double x, double y) => (X, Y) = (x, y);

    double _x;
    public double X
    {
        get => _x;
        init
        {
            if (double.IsNaN(value))
                throw new ArgumentException("X Cannot be NaN");
            _x = value;
        }
    }
    public double Y { get; init; }
}
```

이 설계는 **생성 시점과 비파괴적 변경 시점 양쪽에서** 검증이 돌게 한다.

```csharp
Point p1 = new Point(2, 3);
Point p2 = p1 with { X = double.NaN };    // 예외가 발생한다
```

생성자에서 `_x = x;`가 아니라 `X = x;`로 쓴 것이 핵심이다. 필드에 직접 대입하면 검증을 건너뛴다.

### 복사 생성자가 접근자를 우회하는 것은 문제가 아니다

19.4절에서 본 대로, 자동 생성된 복사 생성자는 **모든 필드와 자동 프로퍼티를 그대로 복사**한다. 위 레코드에서는 이런 모습이 된다.

```csharp
protected Point(Point original)
{
    _x = original._x;
    Y = original.Y;      // 자동 프로퍼티의 백킹 필드
}
```

`_x`를 직접 복사하므로 `X`의 접근자를 우회한다. **그러나 이것은 아무것도 깨뜨리지 않는다.** 복사되는 원본은 이미 `X`의 `init` 접근자를 통해 안전하게 채워졌기 때문이다. 이미 검증을 통과한 값을 다시 검증할 이유가 없다 — 오히려 `with`가 빨라진다.

| 경로 | `init` 접근자 실행 | 검증 실행 |
|---|---|---|
| `new Point(2, 3)` | ✓ (생성자가 프로퍼티에 대입) | ✓ |
| `new Point { X = 2 }` (객체 초기화자) | ✓ | ✓ |
| `p with { X = 5 }`의 1단계(복제) | ✗ (필드 직접 복사) | ✗ — 불필요 |
| `p with { X = 5 }`의 2단계(갱신) | ✓ | ✓ |

> **⚠️ 백킹 필드를 손으로 선언하면 그 필드는 `readonly`가 아니다**
>
> `double _x;`는 그냥 가변 필드다. 자동 구현 `init` 프로퍼티의 백킹 필드가 `initonly`로 나오는 것과 다르다(19.3절). 레코드 안의 다른 메서드에서 실수로 `_x = ...`를 쓰면 **불변성이 조용히 깨진다.** 검증이 필요해서 명시적 프로퍼티로 내려온 순간 이 보호막을 잃는다는 것을 알고 있어야 한다.
>
> ※C# 13의 `field` 키워드(13.8절)를 쓰면 백킹 필드를 선언하지 않고도 접근자 본문에서 백킹 필드를 참조할 수 있어 이 노출면이 줄어든다.

> **💡 검증은 예외를 던지는 것보다 "만들 수 없게" 하는 편이 낫다**
>
> `init` 접근자에서 던지는 예외는 `with` 식 한가운데에서 터진다. 호출 스택이 짧아 원인을 찾기는 쉽지만, 검증이 여러 프로퍼티에 걸친 **불변식**(예: `Start <= End`)이라면 접근자 하나로는 표현할 수 없다. 프로퍼티가 하나씩 갱신되는 중간 상태에서는 불변식이 깨져 있을 수 있기 때문이다.
>
> 이 경우는 위치 매개변수를 버리고 **명시적 생성자에서 한 번에 검증**하거나, 정적 팩터리(`Range.Create(start, end)`)로 만들기를 통제하는 편이 옳다. 후자는 19.8절에서 다시 본다.

### 계산 프로퍼티

가장 단순한 형태부터 본다. 원점으로부터의 거리를 반환하는 프로퍼티다.

```csharp
record Point(double X, double Y)
{
    public double DistanceFromOrigin => Math.Sqrt(X * X + Y * Y);
}
```

읽을 때마다 다시 계산한다. 위치 매개변수도 그대로 쓸 수 있고, 동등성 비교에도 영향이 없다 — **필드가 아니기 때문이다.** 합성된 `Equals`는 필드만 본다.

계산이 비싸다면 생성 시점에 한 번만 하고 싶어진다. 위치 매개변수를 버리고 읽기 전용 프로퍼티 셋으로 다시 쓰면 이렇게 된다.

```csharp
record Point
{
    public double X { get; }
    public double Y { get; }
    public double DistanceFromOrigin { get; }

    public Point(double x, double y) =>
        (X, Y, DistanceFromOrigin) = (x, y, Math.Sqrt(x * x + y * y));
}
```

동작은 한다. 그러나 문제가 둘이다.

- **비파괴적 변경이 불가능하다.** `X`와 `Y`를 `init` 전용으로 바꾸면 `init` 접근자가 실행된 뒤 `DistanceFromOrigin`이 **낡은 값**이 되어 버린다.
- **읽지도 않을 값을 항상 계산한다.**

### 지연 평가와 캐시

최적의 해법은 값을 필드에 캐시하고 **처음 쓸 때 채우는** 것이다.

```csharp
record Point
{
    // ...
    double? _distance;
    public double DistanceFromOrigin
    {
        get
        {
            if (_distance == null)
                _distance = Math.Sqrt(X * X + Y * Y);
            return _distance.Value;
        }
    }
}
```

`??=` 연산자를 쓰면 한 줄이 된다.

```csharp
public double DistanceFromOrigin => _distance ??= Math.Sqrt(X * X + Y * Y);
```

`_distance`가 널이 아니면 그것을 반환하고, 아니면 계산하면서 `_distance`에 대입한다.

여기서 `_distance`를 **변경한다.** 엄밀히 말해 필드가 바뀐다. 그래도 `Point`를 불변 타입이라 부르는 것은 정당하다. 지연 값을 채우기 위해서만 필드를 바꾸는 것은 불변성의 원칙이나 이점을 무효화하지 않으며, `Lazy<T>` 타입으로 감싸면 그 사실 자체를 숨길 수도 있다(34.7절).

### `init` 전용 프로퍼티와 함께 쓰려면

`X`, `Y`가 `init` 전용이면 한 단계가 더 필요하다. **값이 갱신될 때 캐시를 비워야 한다.**

```csharp
record Point
{
    public Point(double x, double y) => (X, Y) = (x, y);

    double _x, _y;
    public double X { get => _x; init { _x = value; _distance = null; } }
    public double Y { get => _y; init { _y = value; _distance = null; } }

    double? _distance;
    public double DistanceFromOrigin => _distance ??= Math.Sqrt(X * X + Y * Y);
}
```

```csharp
Point p1 = new Point(2, 3);
Console.WriteLine(p1.DistanceFromOrigin);       // 3.605551275463989

Point p2 = p1 with { Y = 4 };
Console.WriteLine(p2.DistanceFromOrigin);       // 4.47213595499958
```

여기에 뜻밖의 이점이 하나 있다. **자동 생성된 복사 생성자가 캐시된 `_distance` 필드까지 복사한다.** 계산에 관여하지 않는 다른 프로퍼티를 `with`로 바꿀 때는 캐시가 불필요하게 날아가지 않는다는 뜻이다.

이 이점이 필요 없다면 대안이 있다. `init` 접근자에서 캐시를 비우는 대신, **캐시 필드를 무시하는 복사 생성자**를 직접 쓰는 것이다. 이쪽이 더 간결한데, 위치 매개변수와 함께 쓸 수 있고 분해자를 활용할 수 있기 때문이다.

```csharp
record Point(double X, double Y)
{
    double? _distance;
    public double DistanceFromOrigin => _distance ??= Math.Sqrt(X * X + Y * Y);

    protected Point(Point other) => (X, Y) = other;   // other를 분해해 X, Y만 옮긴다
}
```

`(X, Y) = other;`는 컴파일러가 만든 `Deconstruct`를 호출하는 분해 대입이다. `_distance`는 복사되지 않으므로 자동으로 널이 된다.

| 전략 | 장점 | 단점 |
|---|---|---|
| `init`에서 캐시 비우기 | 관련 없는 프로퍼티 갱신 시 캐시 유지 | 위치 매개변수를 못 쓴다. 접근자를 전부 손으로 쓴다 |
| 복사 생성자에서 캐시 제외 | 위치 매개변수 유지, 코드가 짧다 | `with` 때마다 캐시가 무조건 무효화된다 |

> **⚠️ 지연 계산 필드는 기본 동등성 비교를 깨뜨린다**
>
> 두 전략 모두 같은 부작용을 낳는다. 합성된 `Equals`와 `GetHashCode`는 **모든 필드**를 본다. `_distance`는 읽었는지 여부에 따라 채워져 있기도 하고 널이기도 하다. 그 결과 이런 일이 생긴다.
>
> ```csharp
> var a = new Point(3, 4);
> var b = new Point(3, 4);
> _ = a.DistanceFromOrigin;        // a의 캐시만 채워진다
> Console.WriteLine(a == b);       // False — _distance가 5.0 vs null
> ```
>
> **동등성이 관찰 시점에 따라 달라진다.** 이보다 나쁜 버그는 드물다. 고치는 방법은 19.7절에서 본다 — 다행히 클래스나 구조체에 동등성을 통째로 붙이는 것보다 일이 적다.

> **💡 지연 캐시는 스레드 안전하지 않다**
>
> `_distance ??= ...`는 원자적이지 않다. 두 스레드가 동시에 처음 읽으면 계산이 두 번 일어난다. 계산이 순수 함수이고 결과가 같다면 대개 무해하지만(중복 계산일 뿐이다), 다음 두 경우에는 무해하지 않다.
>
> - 계산에 부수 효과가 있는 경우(로그, 카운터 증가, I/O).
> - 캐시 대상이 참조 타입이고 **호출자가 참조 동일성에 의존**하는 경우.
>
> 후자가 필요하면 `Lazy<T>`(34.7절)를 쓰거나 이중 검사 잠금(48.13절)을 정확히 구현해야 한다. `double?` 필드에 대한 대입 자체는 원자적이지 않다는 점도 기억한다(48.2절) — 참조 타입 필드나 `int`와 달리 8바이트 초과 구조체의 대입은 찢어질 수 있다.

> **📌 계산 결과를 필드가 아니라 프로퍼티로 두면 동등성 문제가 없다**
>
> 캐시하지 않는 계산 프로퍼티(`=> Math.Sqrt(...)`)는 필드가 아니므로 `Equals`·`GetHashCode`·`ToString`·복사 생성자 어디에도 나타나지 않는다. **캐시를 도입하는 순간에만** 이 절의 모든 복잡도가 발생한다. 계산이 정말 비싼지 먼저 재고(67장), 아니면 캐시하지 않는 편이 압도적으로 단순하다.

## 19.6 위치 지정 레코드와 기본 생성자의 관계

### 매개변수 목록이 하는 일

레코드 정의는 매개변수 목록으로 줄일 수 있다.

```csharp
record Point(double X, double Y)
{
    // 여기에 멤버를 추가로 정의할 수 있다
}
```

매개변수 목록이 지정되면 컴파일러가 추가로 하는 일은 셋이다.

1. 매개변수마다 **`init` 전용 프로퍼티**를 쓴다.
2. 그 프로퍼티들을 채우는 **기본 생성자(primary constructor)** 를 쓴다.
3. **분해자**를 쓴다.

따라서

```csharp
record Point(double X, double Y);
```

는 19.2절에서 손으로 쓴 형태와 거의 같은 것을 만든다. 사소한 차이는 기본 생성자의 매개변수 이름이 `x`, `y`가 아니라 **`X`, `Y`** 가 된다는 점이다.

```csharp
public Point(double X, double Y)      // 기본 생성자
{
    this.X = X;
    this.Y = Y;
}

public void Deconstruct(out double X, out double Y)   // 분해자
{
    X = this.X;
    Y = this.Y;
}
```

매개변수에는 `in`과 `params` 한정자를 붙일 수 있지만 **`out`과 `ref`는 붙일 수 없다.**

> **⚠️ 위치 매개변수의 대소문자가 프로퍼티 이름이 된다**
>
> `record CarRecord(string make, string model)`이라고 쓰면 프로퍼티 이름이 `make`, `model`이 된다. 컴파일러는 파스칼 케이스로 고쳐 주지 않는다. 공개 API에서 이 실수는 소비자 코드 전체를 고치게 만든다. 위치 매개변수는 **매개변수 이름이 아니라 프로퍼티 이름을 쓴다**고 생각하는 편이 안전하다.

> **⚠️ 위치 지정 레코드는 객체 초기화자로 만들 수 없다**
>
> ```csharp
> record CarRecord(string Make, string Model, string Color);
>
> var c = new CarRecord { Make = "Honda" };   // 컴파일 오류 — 매개변수 없는 생성자가 없다
> var d = new CarRecord("Honda", "Pilot", "Blue");   // 이렇게만 만들 수 있다
> ```
>
> 위치 매개변수를 쓰면 **모든 값을 올바른 순서로** 넘겨야 한다. 매개변수가 같은 타입 여럿(`string` 다섯 개 등)이면 순서를 틀려도 컴파일된다. 이 위험을 줄이려면 명명된 인수(`new CarRecord(Make: "Honda", ...)`)를 쓰거나, 위치 매개변수를 포기하고 `init` 프로퍼티 + 객체 초기화자로 간다.

### 상속과 위치 매개변수

매개변수 목록이 있는 레코드는 다음 문법으로 상속한다.

```csharp
record Point3D(double X, double Y, double Z) : Point(X, Y);
```

컴파일러가 만드는 것은 이렇다.

```csharp
class Point3D : Point
{
    public double Z { get; init; }

    public Point3D(double X, double Y, double Z) : base(X, Y)
        => this.Z = Z;
}
```

기반 목록의 `Point(X, Y)`는 **기반 생성자 호출**이며, 괄호 안의 `X`, `Y`는 파생 레코드의 기본 생성자 매개변수다. 이 문법이 아니면 `base(...)`를 쓸 자리가 없다 — 기본 생성자에는 본문이 없기 때문이다.

> **📌 매개변수 목록은 "곱 타입"을 위한 지름길이다**
>
> 함수형 프로그래밍에서 값 여럿을 묶은 타입을 **곱 타입(product type)** 이라 부른다. 매개변수 목록은 그런 타입이 필요할 때, 그리고 프로토타이핑할 때 좋은 지름길이다. 반대로 `init` 접근자에 로직(인수 검증 등)을 넣어야 할 때는 별 도움이 되지 않는다 — 그 이유를 이 절 뒷부분에서 본다.

### 프로퍼티를 "가로채기"

C#은 그 중간 선택지도 준다. 매개변수 목록을 쓰면서 **프로퍼티 선언 일부를 직접 쓰는** 것이다.

```csharp
record Student(string ID, string LastName, string GivenName)
{
    public string ID { get; } = ID;
}
```

여기서 `ID` 프로퍼티 정의를 가로채 `init` 전용이 아니라 **읽기 전용**으로 만들었다. 이렇게 하면 `ID`는 비파괴적 변경에 참여하지 않는다. 어떤 프로퍼티를 절대 `with`로 바꿀 일이 없다면, 읽기 전용으로 만들어 두는 것이 **계산된 데이터를 갱신 메커니즘 없이 저장**하는 방법이 된다.

굵게 봐야 할 부분은 프로퍼티 초기화자다.

```csharp
public string ID { get; } = ID;
```

프로퍼티 선언을 가로채는 순간 **값을 초기화할 책임도 가져온다.** 기본 생성자가 더 이상 자동으로 채워 주지 않는다. 이것은 클래스나 구조체에 기본 생성자를 정의할 때의 동작(13.10절)과 정확히 일치한다. 그리고 초기화자 우변의 `ID`는 **프로퍼티가 아니라 기본 생성자 매개변수**를 가리킨다.

기본 생성자 매개변수는 필드·프로퍼티 초기화자 어디에서나 보인다.

```csharp
record Student(string ID, string LastName, string FirstName)
{
    public string ID { get; } = ID;
    readonly int _enrollmentYear = int.Parse(ID.Substring(0, 4));
}
```

여기서도 `ID`는 매개변수다. 초기화자에서 프로퍼티에 접근하는 것 자체가 불법이므로 모호성이 생기지 않는다.

`record struct`에서는 프로퍼티를 **필드로 재정의**하는 것도 합법이다.

```csharp
record struct Student(string ID)
{
    public string ID = ID;      // 프로퍼티가 아니라 필드
}
```

### 기본 생성자로는 검증을 넣을 수 없다

앞의 `_enrollmentYear` 예제는 현실에서는 잘 동작하지 않는다. 이유는 명확하다. **명시적 생성자가 없으면 `ID`를 검증하고 의미 있는 예외를 던질 중심 지점이 없다.**

검증은 명시적 `init` 접근자를 써야 하는 대표적인 이유이기도 하다(19.5절). 그런데 기본 생성자는 이 시나리오와 잘 어울리지 않는다.

```csharp
record Person(string Name)
{
    string _name = Name;
    public string Name
    {
        get => _name;
        init => _name = value ?? throw new ArgumentNullException("Name");
    }
}
```

`Name`이 자동 프로퍼티가 아니므로 프로퍼티 초기화자를 정의할 수 없다. 할 수 있는 최선이 **백킹 필드에 초기화자를 다는 것**이다. 그런데 그렇게 하면 널 검사를 우회한다.

```csharp
var p = new Person(null);      // 성공한다! 널 검사를 건너뛴다
```

기본 생성자 매개변수를 **프로퍼티에** 대입할 방법이 없는 것이 문제의 뿌리다. 생성자를 직접 쓰지 않는 한 그 대입은 일어나지 않는다. 우회로가 없지는 않다(검증 로직을 정적 메서드로 빼서 두 번 호출하는 식) 하지만 가장 단순한 해법은 **매개변수 목록을 포기하고 평범한 생성자를 쓰는 것**이다.

```csharp
record Person
{
    public Person(string name) => Name = name;    // *프로퍼티*에 대입한다

    string _name;
    public string Name
    {
        get => _name;
        init => _name = value ?? throw new ArgumentNullException(nameof(value));
    }

    public void Deconstruct(out string name) => name = Name;   // 필요하면 직접 쓴다
}
```

> **⚠️ `record Person(string Name)`에 검증을 붙였다고 착각하기 쉽다**
>
> 위 코드가 컴파일되고 `new Person("Bob")`이 잘 동작하기 때문에, 널 검사가 걸려 있다고 믿기 쉽다. `p with { Name = null }`은 실제로 예외를 던진다 — `init` 접근자를 타기 때문이다. 그러나 **생성자 경로만 뚫려 있다.** 검증이 절반만 작동하는 상태이며, 이것이 아무 검증도 없는 상태보다 위험하다.
>
> 검증을 넣기로 했다면 위치 매개변수를 지우는 것이 정답이다.

### 클래스의 기본 생성자와 무엇이 다른가

C# 12부터 클래스와 구조체도 기본 생성자를 갖는다(13.10절). 문법은 같지만 동작은 다르다.

| | 클래스/구조체의 기본 생성자 ※C# 12 | 레코드의 위치 매개변수 ※C# 9/10 |
|---|---|---|
| 매개변수 → 공개 프로퍼티 | **생성되지 않는다** | `init`(또는 `set`) 프로퍼티 자동 생성 |
| `Deconstruct` | 없음 | 자동 생성 |
| `Equals`/`GetHashCode`/`ToString` | 없음 | 자동 생성 |
| `with` 식 | 불가 | 가능 |
| 매개변수의 수명 | 타입 본문 전체에서 접근 가능 | 같음 |
| 매개변수의 쓰기 가능 여부 | 쓰기 가능(메서드 안에서 대입 가능) | 같음 — 단 프로퍼티는 `init` |
| 매개변수 캡처 | 메서드에서 쓰면 숨은 필드 생성 | 같음 |
| 초기화자에서 매개변수 참조 | 가능 | 가능 |

핵심 차이는 첫 줄이다. `class Headset(string manufacturer, string productName);`에서 `manufacturer`는 **프로퍼티가 되지 않는다.** 외부에서 `vp.Manufacturer`도 `vp.manufacturer`도 접근할 수 없고, 시도하면 멤버를 찾을 수 없다는 컴파일 오류가 난다. 프로퍼티로 노출하려면 손으로 써야 한다.

```csharp
public class Headset(string manufacturer, string productName)
{
    public string Manufacturer { get; set; } = manufacturer;
    public string ProductName { get; set; } = productName;
}
```

레코드는 이 한 단계를 대신해 준다. **"매개변수를 그대로 공개 프로퍼티로 만들고 값 동등성까지 원한다"면 클래스가 아니라 레코드가 맞는 도구다.**

> **⚠️ 기본 생성자 매개변수는 필드가 아니다 — 값이 두 벌 저장될 수 있다**
>
> 레코드에서도 13.10절의 함정이 그대로 적용된다. 프로퍼티로 노출된 매개변수를 메서드 본문에서 다시 쓰면 컴파일러가 **캡처 필드를 따로 만든다.** 프로퍼티를 갱신해도(예: `with`로 새 인스턴스를 만들어도) 메서드가 보는 매개변수 값은 그 인스턴스의 생성 시점 값이다. 위치 매개변수를 프로퍼티로 노출하기로 했다면, 그 뒤로는 **프로퍼티만 쓴다.**

> **💡 위치 매개변수를 언제 쓰고 언제 버리는가**
>
> 다음 중 하나라도 해당하면 위치 매개변수를 버리고 명시적 프로퍼티로 간다.
>
> - 인수 검증이 필요하다.
> - 필드가 다섯 개를 넘어 호출부에서 순서를 틀릴 위험이 크다.
> - 나중에 프로퍼티를 추가할 때 **바이너리 호환성**을 지켜야 한다 — 위치 매개변수를 추가하면 생성자 시그니처가 바뀌어 기존 소비자가 깨진다(78.13절).
> - 선택적 값이 많다.
>
> 마지막 항목에 대한 원서의 권고가 특히 실용적이다. **공개 라이브러리에서는 선택적 매개변수를 생성자에 넣지 말고 `init` 전용 프로퍼티로만 노출하라.**
>
> ```csharp
> new Foo(123, 234) { Optional2 = 345 };
>
> record Foo
> {
>     public Foo(int required1, int required2) { /* ... */ }
>
>     public int Required1 { get; init; }
>     public int Required2 { get; init; }
>     public int Optional1 { get; init; }
>     public int Optional2 { get; init; }
> }
> ```
>
> 이 패턴의 이점은 **나중에 `init` 전용 프로퍼티를 안전하게 추가**할 수 있다는 것이다. 옛 버전 어셈블리로 컴파일한 소비자와의 바이너리 호환성이 깨지지 않는다. 필수 값을 강제하는 다른 방법으로 ※C# 11의 `required` 한정자(13.13절)도 있다.

## 19.7 레코드의 동등성 비교 규칙

### 기본 동작

구조체·익명 타입·튜플과 마찬가지로, 레코드는 **구조적 동등성을 기본으로 제공한다.** 두 레코드는 필드(그리고 자동 프로퍼티)가 같으면 같다.

```csharp
var p1 = new Point(1, 2);
var p2 = new Point(1, 2);

Console.WriteLine(p1.Equals(p2));         // True
Console.WriteLine(p1 == p2);              // True
Console.WriteLine(ReferenceEquals(p1, p2));  // False

record Point(double X, double Y);
```

같은 데이터를 가진 평범한 클래스는 이렇게 동작하지 않는다.

```csharp
public class AnimalClass  { public string? Name { get; set; } }
public record AnimalRecord { public string? Name { get; set; } }

AnimalClass ac1 = new() { Name = "Rex" };
AnimalClass ac2 = new() { Name = "Rex" };
Console.WriteLine($"ac1 == ac2: {ac1 == ac2}");     // False

AnimalRecord ar1 = new() { Name = "Rex" };
AnimalRecord ar2 = new() { Name = "Rex" };
Console.WriteLine($"ar1 == ar2: {ar1 == ar2}");     // True
```

클래스 인스턴스는 **문자 그대로 같은 객체일 때만** 같다. 메모리 주소가 같아야 한다는 뜻이다. 값 동등성과 참조 동등성의 구분 자체는 25.1절에 있다.

레코드 인스턴스를 다른 변수에 대입하면 여전히 **같은 참조를 가리킨다.** 레코드는 값 의미론으로 비교될 뿐 값 타입이 되는 것은 아니다.

```csharp
CarRecord copy = original;
Console.WriteLine(ReferenceEquals(copy, original));   // True — 그냥 대입이다
```

진짜 복사본이 필요하면 `with`를 쓴다(19.4절).

### `EqualityContract`가 계층에서 하는 일

레코드 동등성의 가장 중요한 규칙은 이것이다. **파생 타입 인스턴스는 기반 타입 인스턴스와 결코 같지 않다.**

```csharp
public record Person(string Name);
public record Employee(string Name, string Dept) : Person(Name);

Person a = new Person("Jon");
Person b = new Employee("Jon", "Dev");

Console.WriteLine(a == b);        // False
Console.WriteLine(a.Equals(b));   // False
Console.WriteLine(b.Equals(a));   // False
```

`Name`은 양쪽 다 `"Jon"`이다. 그런데도 다르다. `EqualityContract` 때문이다.

- `a.EqualityContract`는 `typeof(Person)`.
- `b.EqualityContract`는 `typeof(Employee)` — `Employee`가 `override`했다.

`Equals` 본문에서 두 계약을 비교하는 순간 `false`가 확정된다. 필드 비교까지 가지도 않는다.

```text
┌────────────────────────────────────────────────────────────────┐
│  a.Equals(b) 의 판정 순서                                        │
├────────────────────────────────────────────────────────────────┤
│                                                                │
│  a = Person("Jon")          b = Employee("Jon","Dev")          │
│      런타임 타입: Person          런타임 타입: Employee           │
│                                                                │
│  ① (object)a == b ?                     → false, 계속           │
│  ② b != null ?                          → true,  계속           │
│  ③ a.EqualityContract == b.EqualityContract ?                  │
│         typeof(Person) == typeof(Employee)                     │
│                                         → false ─► 즉시 false   │
│  ④ 필드 비교                             (도달하지 않음)          │
│                                                                │
│  ※ b.Equals(a)도 대칭적으로 false다.                             │
│     Employee.Equals(Person)은 sealed override →                │
│     Equals(a as Employee) → a는 Employee가 아니므로 null → false │
└────────────────────────────────────────────────────────────────┘
```

이 설계의 목적은 **대칭성**이다. `Equals` 계약의 5계명 중 하나가 `a.Equals(b)`와 `b.Equals(a)`가 항상 같아야 한다는 것이다(25.3절). 손으로 `Equals`를 쓸 때 가장 흔히 저지르는 실수가 여기다.

```csharp
// 흔한 잘못된 구현 — is 검사는 대칭성을 깬다
public override bool Equals(object? obj) =>
    obj is Person other && Name == other.Name;
```

이렇게 쓰면 `person.Equals(employee)`는 `true`(직원도 사람이므로)이고 `employee.Equals(person)`은 `false`가 되어 계약이 깨진다. `HashSet<T>`에 넣는 순서에 따라 결과가 달라지는 종류의 버그다. **레코드는 이 실수를 구조적으로 불가능하게 만든다.**

> **💡 그래도 대부분의 레코드는 `sealed`여야 한다**
>
> `EqualityContract`가 계층 문제를 해결하지만, 레코드 상속 자체가 잘 쓰이는 도구는 아니다. 데이터 타입에 상속을 도입하면 "같은 데이터인데 타입이 달라서 다르다"는 상황이 계속 생긴다. 컬렉션에 담아 비교하는 코드에서는 그 규칙이 직관에 어긋난다.
>
> 레코드 계층이 정말 유용한 경우는 **닫힌 합 타입(sum type)** 을 흉내 낼 때다.
>
> ```csharp
> abstract record Shape;
> sealed record Circle(double R) : Shape;
> sealed record Rect(double W, double H) : Shape;
> ```
>
> 이 형태는 `switch` 식의 타입 패턴과 결합하면 강력하다(77.7절, 77.14절). 그 외의 경우에는 `sealed record`가 기본값이다.

### `record struct`가 다른 이유

`record struct`에는 `EqualityContract`가 없다.

```csharp
public readonly bool Equals(Point other) =>
    EqualityComparer<double>.Default.Equals(_x, other._x) && ...;
```

이유는 구조체가 **상속되지 않기 때문**이다. `Point`라는 값 타입 변수에 들어갈 수 있는 것은 `Point`뿐이다. 강타입 `Equals`의 매개변수 타입이 곧 정확한 런타임 타입이므로 계약을 확인할 이유가 없다.

`Equals(object)` 경로는 조금 다르다.

```csharp
public override readonly bool Equals(object? obj) => obj is Point other && Equals(other);
```

`obj is Point`가 **정확한 타입 검사 + 언박싱**을 동시에 한다. 박싱된 다른 값 타입이 들어오면 그대로 `false`다.

| | `record class` | `record struct` |
|---|---|---|
| 정확한 타입 확인 방법 | `EqualityContract` 비교(런타임) | 정적 타입(컴파일 타임) 또는 `is` 검사 |
| 파생 타입 문제 | 있음 → 계약으로 해결 | 없음 |
| `null`과의 비교 | `p == null`이 의미 있다 | 컴파일 오류(널 허용 값 타입이 아니면) |
| 참조 동일성 단축 | 있음 | 없음 |
| 비교 비용 | 계약 비교 1회 + 필드 비교 | 필드 비교만 |
| 박싱 위험 | 없음 | `Equals(object)` 경로에서 발생(18.6절) |

> **⚠️ 레코드 구조체를 `object`나 비제네릭 컬렉션에 넣으면 박싱된다**
>
> `record struct`도 구조체다. `ArrayList`에 담거나 `object`로 캐스팅하면 박싱이 일어나고, 이후 `Equals` 호출은 언박싱 경로를 탄다(15장). 제네릭 컬렉션(`List<Point>`, `HashSet<Point>`)에서는 `EqualityComparer<Point>.Default`가 `IEquatable<Point>` 구현을 찾아 강타입 경로로 가므로 박싱이 없다. 레코드가 `IEquatable<T>`를 자동 구현해 주는 것의 실질적 가치가 여기에 있다.

### 동등성을 직접 정의하기

레코드의 기본 동등성 구현은 **불가피하게 취약하다.** 레코드가 지연 값, 일시적 값, 배열, 컬렉션 타입을 담고 있으면 깨진다(이들은 동등성 비교에 특별한 처리가 필요하다). 다행히 고치기는 상대적으로 쉽고, 클래스나 구조체에 동등성 동작을 통째로 추가하는 것보다 일이 적다.

클래스·구조체와 달리 `object.Equals` 메서드를 재정의하지 **않고**(할 수도 없고), 다음 시그니처의 공개 `Equals` 메서드를 정의한다.

```csharp
record Point(double X, double Y)
{
    double _someOtherField;

    public virtual bool Equals(Point other) =>
        other != null && X == other.X && Y == other.Y;
}
```

규칙이 둘이다.

- **`override`가 아니라 `virtual`이어야 한다.**
- **`object`가 아니라 실제 레코드 타입**(여기서는 `Point`)을 받아야 한다.

시그니처만 맞으면 컴파일러가 알아서 이 메서드를 자기 코드에 끼워 넣는다. 위 예제에서는 `X`와 `Y`만 비교하고 `_someOtherField`는 무시하도록 로직을 바꿨다 — 19.5절의 지연 캐시 문제를 푸는 방법이 바로 이것이다.

파생 레코드에서는 `base.Equals`를 부를 수 있다.

```csharp
public virtual bool Equals(Point other) => base.Equals(other) && /* ... */;
```

다른 타입과 마찬가지로 **동등성 비교를 가져왔으면 `GetHashCode()`도 함께 재정의해야 한다.**

```csharp
record Point(double X, double Y)
{
    double? _distance;
    public double DistanceFromOrigin => _distance ??= Math.Sqrt(X * X + Y * Y);

    public virtual bool Equals(Point? other) =>
        other is not null && X == other.X && Y == other.Y;

    public override int GetHashCode() => HashCode.Combine(X, Y);
}
```

레코드의 좋은 점은 여기서 끝난다는 것이다. **`!=`나 `==`를 오버로드할 필요도, `IEquatable<T>`를 구현할 필요도 없다.** 그 부분은 컴파일러가 계속 해 준다. `==`는 여전히 `Equals`에 위임하므로 새 로직을 자동으로 따른다.

| 손으로 쓸 때(클래스) | 레코드에서 동등성을 바꿀 때 |
|---|---|
| `Equals(object)` 재정의 | 컴파일러가 유지 |
| `Equals(T)` 구현 | **직접 작성** (`public virtual`) |
| `IEquatable<T>` 선언 | 컴파일러가 유지 |
| `GetHashCode` 재정의 | **직접 작성** |
| `==` 오버로드 | 컴파일러가 유지 |
| `!=` 오버로드 | 컴파일러가 유지 |
| 대칭성·이행성 보장 | 직접 작성한 부분만 책임 |

> **⚠️ `Equals`만 고치고 `GetHashCode`를 두면 딕셔너리가 조용히 틀린다**
>
> 25.4절의 계약이 그대로 적용된다. `Equals`가 `true`인 두 인스턴스는 반드시 같은 해시를 내야 한다. 지연 캐시 예제에서 `Equals`만 고치면, `_distance`가 채워진 인스턴스와 아닌 인스턴스가 **서로 같다고 나오면서 해시는 다른** 상태가 된다. `Dictionary`에 넣은 항목을 같은 값으로 조회했는데 못 찾는 전형적인 증상이 나온다. 이 증상은 부하가 걸린 뒤에야 드러나는 경우가 많다.

> **⚠️ 배열 멤버는 언제나 참조 비교다**
>
> ```csharp
> record Buffer(byte[] Data);
>
> var b1 = new Buffer(new byte[] { 1, 2, 3 });
> var b2 = new Buffer(new byte[] { 1, 2, 3 });
> Console.WriteLine(b1 == b2);        // False
> ```
>
> `byte[]`는 `IEquatable<byte[]>`를 구현하지 않으므로 `EqualityComparer<byte[]>.Default`가 참조 비교로 떨어진다. **레코드로 감쌌다고 내용 비교가 되지 않는다.** 내용 비교가 필요하면 `Equals`와 `GetHashCode`를 직접 쓰거나(`Data.AsSpan().SequenceEqual(...)`), 애초에 `ImmutableArray<T>`나 문자열처럼 값 동등성을 가진 타입을 멤버로 둔다.

> **📌 레코드 동등성이 옳은 순간과 아닌 순간**
>
> 레코드의 값 동등성은 "이 타입에는 정체성이 없다"는 선언이다. 좌표, 금액, 날짜 범위, 설정 스냅숏 — 여기서는 맞다. 반대로 **DB의 행을 표현하는 엔티티**에는 대개 틀리다. 엔티티는 `Id`로 식별되고, 다른 필드가 달라도 같은 엔티티다. 엔티티를 `record`로 선언하면 "이름을 바꾼 사용자"가 "다른 사용자"가 되어 버린다. ORM의 변경 추적과도 충돌한다.
>
> 판단 기준은 하나다. **"모든 필드가 같으면 같은 것인가?"** 이 질문에 "아니오, `Id`만 같으면 같다"고 답한다면 레코드가 아니다.

> **📌 위치 지정 레코드는 JSON 역직렬화와 잘 맞는다** ※.NET 5+
>
> `System.Text.Json`은 매개변수 있는 생성자를 통한 역직렬화를 지원한다. 위치 지정 레코드는 생성자 매개변수 이름과 프로퍼티 이름이 같으므로 별도 설정 없이 왕복하는 경우가 많다. 생성자가 여럿이라 모호하면 `[JsonConstructor]`로 지정한다. 다만 `init` 전용 프로퍼티만 있는 레코드를 **매개변수 없는 생성자 + 프로퍼티 설정** 방식으로만 다루는 옛 직렬화기(.NET Framework 시절의 일부 라이브러리 포함)에서는 실패할 수 있다. 직렬화기를 바꿀 때는 레코드 왕복 테스트를 반드시 넣는다.

## 19.8 값 타입의 불변성과 스레드 안전성 — 그리고 그 대가

### 불변성이 주는 것

불변 타입은 단순하다. **만들어진 뒤에는 상수다.** 여기서 네 가지가 따라 나온다.

**첫째, 검증이 한 번으로 끝난다.** 객체를 만들 때 쓰는 매개변수를 검증하면 그 시점부터 그 객체가 유효한 상태임을 안다. 내부 상태를 무효하게 만들 방법이 없다. 생성 후의 상태 변경을 금지하는 것만으로 원래는 필요했을 오류 검사를 대량으로 없앤다.

**둘째, 본질적으로 스레드 안전하다.** 여러 판독기가 같은 내용에 동시에 접근할 수 있다. 내부 상태가 변할 수 없으면 서로 다른 스레드가 일관성 없는 데이터를 볼 가능성이 없다. 잠금이 필요 없다는 것은 경합도, 데드락도, 메모리 배리어 고민도 없다는 뜻이다(48장).

**셋째, 밖으로 안전하게 내보낼 수 있다.** 호출자가 내부 상태를 바꿀 수 없으므로 내부 객체 참조를 반환해도 캡슐화가 깨지지 않는다. 가변 타입이라면 방어적 복사를 하거나 읽기 전용 래퍼를 씌워야 한다(78.5절).

**넷째, 해시 기반 컬렉션에서 더 잘 동작한다.** `Object.GetHashCode()`가 반환하는 값은 **인스턴스 불변량**이어야 한다. 불변 타입에서는 이것이 언제나 참이다.

### 가변 구조체가 만드는 무효 상태

원서의 예제를 그대로 본다. 가변 `Address` 구조체다.

```csharp
// 가변 Address 구조체
public struct Address
{
    private string state;
    private int zipCode;

    public string Line1 { get; set; }
    public string Line2 { get; set; }
    public string City { get; set; }

    public string State
    {
        get => state;
        set { ValidateState(value); state = value; }
    }

    public int ZipCode
    {
        get => zipCode;
        set { ValidateZip(value); zipCode = value; }
    }
    // 나머지 생략
}
```

프로퍼티마다 검증이 붙어 있다. 그런데도 이 코드는 안전하지 않다.

```csharp
Address a1 = new Address();
a1.Line1 = "111 S. Main";
a1.City = "Anytown";
a1.State = "IL";
a1.ZipCode = 61111;

// 수정:
a1.City = "Ann Arbor";   // 이 시점에 Zip, State가 무효해진다
a1.ZipCode = 48103;      // 여전히 State가 무효
a1.State = "MI";         // 이제야 정상
```

내부 상태를 부분적으로 바꾼다는 것은 **적어도 일시적으로는 객체 불변식을 위반할 수 있다**는 뜻이다. `City`를 바꾼 직후 `a1`은 무효 상태다. 도시는 바뀌었는데 주와 우편번호가 맞지 않는다.

문제가 둘로 갈라진다.

- **스레드.** 이 코드 조각이 다중 스레드 프로그램의 일부라면, 도시가 바뀐 뒤 주가 바뀌기 전의 어떤 컨텍스트 전환도 다른 스레드에게 일관성 없는 데이터를 보여 줄 수 있다.
- **예외.** 단일 스레드여도 안전하지 않다. `ZipCode`가 무효라 세터가 예외를 던졌다고 하자. 의도한 변경 중 **일부만 적용**된 채 시스템이 무효 상태로 남는다.

이 문제를 고치려면 상당한 양의 내부 검증 코드를 `Address` 구조체에 추가해야 한다. 그 검증 코드는 크기와 복잡도를 크게 늘린다. 예외 안전성을 완전히 구현하려면 필드를 두 개 이상 바꾸는 모든 코드 블록마다 방어적 복사본을 만들어야 한다. 스레드 안전성까지 원한다면 모든 프로퍼티 접근자 — 세터와 게터 양쪽 — 에 스레드 동기화 검사를 넣어야 한다. 전부 합치면 상당한 작업이고, 기능이 추가될 때마다 계속 늘어난다.

### 불변으로 바꾸기

`Address`가 구조체여야 한다면, **불변으로 만든다.** 외부에서 볼 때 모든 인스턴스 필드를 읽기 전용으로 바꾸는 것으로 시작한다.

```csharp
public struct Address
{
    public string Line1 { get; }
    public string Line2 { get; }
    public string City { get; }
    public string State { get; }
    public int ZipCode { get; }

    public Address(string line1, string line2, string city,
                   string state, int zipCode) : this()
    {
        Line1 = line1;
        Line2 = line2;
        City = city;
        ValidateState(state);
        State = state;
        ValidateZip(zipCode);
        ZipCode = zipCode;
    }
}
```

사용법이 달라진다. 기존 인스턴스를 수정하는 대신 **새 객체를 만든다.**

```csharp
Address a2 = new Address("111 S. Main", "", "Anytown", "IL", 61111);

// 변경하려면 다시 초기화한다
a2 = new Address(a2.Line1, a2.Line2, "Ann Arbor", "MI", 48103);
```

이제 값은 **두 상태 중 하나**다. Anytown의 원래 주소이거나, Ann Arbor의 갱신된 주소이거나. 앞 예제의 무효한 중간 상태를 만들지 않는다. 그런 중간 상태는 생성자 실행 중에만 존재하며 생성자 밖에서는 보이지 않는다. 예외 안전하기도 하다 — 새 `Address`를 만드는 도중 예외가 나면 `a2`의 원래 값은 그대로다.

그리고 이 코드 전체가 레코드 한 줄이다.

```csharp
public readonly record struct Address(string Line1, string Line2, string City, string State, int ZipCode);
```

검증이 필요하면 19.5절과 19.6절의 방법을 쓴다. `with`가 "다시 초기화"를 대신한다.

```csharp
a2 = a2 with { City = "Ann Arbor", State = "MI", ZipCode = 48103 };
```

**한 번의 `with`는 하나의 원자적 전이다.** 세 프로퍼티가 전부 적용된 새 인스턴스가 나오거나, 예외가 나서 아무것도 나오지 않거나 둘 중 하나다.

### 원자적 타입과 합성 타입

모든 타입을 불변으로 만드는 것은 실무에서 매우 어렵다. 그래서 이 권고는 **원자적(atomic)이면서 불변인 값 타입**을 대상으로 한다. 자연스럽게 하나의 개체를 이루는 구조로 타입을 분해하라는 뜻이다.

- `Address`는 그런 개체다. 주소는 여러 관련 필드로 이루어진 하나의 것이며, 한 필드가 바뀌면 다른 필드도 바뀔 가능성이 높다.
- `Customer`는 원자적이지 않다. 주소, 이름, 전화번호 여럿을 담는다. 이 독립적인 조각들은 각각 따로 바뀔 수 있다. 고객이 이사하지 않고 전화번호만 바꿀 수 있고, 이사했는데 번호는 그대로일 수 있고, 이사도 번호 변경도 없이 이름만 바꿀 수 있다.

`Customer`는 여러 불변 타입을 **합성**해 만든다. 주소 하나, 이름 하나, 전화번호/유형 쌍의 컬렉션 하나. 원자적 타입은 단일 개체이므로 내용을 통째로 교체하는 것이 자연스럽다.

| 성격 | 예 | 권장 형태 |
|---|---|---|
| 원자적 + 작음 | 좌표, 금액, 날짜 범위, 색상 | `readonly record struct` |
| 원자적 + 큼 | 주소, 설정 스냅숏 | `sealed record`(클래스) |
| 합성 | 고객, 주문, 집계 루트 | 가변 클래스 또는 불변 레코드 + 재생성 |
| 정체성이 있음 | DB 엔티티 | 평범한 클래스(19.7절 📌) |

### 불변성에 뚫리는 구멍

불변 타입을 만들려면 클라이언트가 내부 상태를 바꿀 수 있는 구멍이 없어야 한다. 값 타입은 파생 타입을 지원하지 않으므로 파생 타입이 필드를 바꾸는 것은 걱정할 필요가 없다. 그러나 **불변 타입 안의 가변 참조 타입 필드**는 감시해야 한다.

```csharp
// 거의 불변 — 그러나 상태 변경을 허용하는 구멍이 있다
public struct PhoneList
{
    private readonly Phone[] phones;

    public PhoneList(Phone[] ph) { phones = ph; }

    public IEnumerable<Phone> Phones => phones;
}
```

```csharp
Phone[] phones = new Phone[10];
// phones 초기화
PhoneList pl = new PhoneList(phones);

// 전화 목록을 수정한다 —
// (불변이라고 여겨졌던) 객체의 내부까지 함께 바뀐다
phones[5] = Phone.GeneratePhoneNumber();
```

배열 클래스는 참조 타입이다. `PhoneList` 구조체 안의 배열 참조는 **객체 밖에서 할당된 같은 저장소**를 가리킨다. 같은 저장소를 가리키는 다른 변수를 통해 이 "불변" 구조체를 수정할 수 있다. 이 가능성을 없애려면 배열의 방어적 복사본을 만들어야 한다. `Array`는 가변 타입이다. 대안 하나는 `System.Collections.Immutable` 네임스페이스의 불변 컬렉션을 쓰는 것이다.

```csharp
public struct PhoneList
{
    private readonly ImmutableList<Phone> phones;

    public PhoneList(Phone[] ph) { phones = ph.ToImmutableList(); }

    public IEnumerable<Phone> Phones => phones;
}
```

`Phone` 자체가 가변 참조 타입이면 장난칠 여지가 더 많아진다. 컬렉션이 어떤 수정으로부터도 보호되더라도 클라이언트가 컬렉션 안의 값을 바꿀 수 있다.

> **⚠️ 레코드는 이 구멍을 하나도 막아 주지 않는다**
>
> `record Order(string Id, List<string> Items)`가 만드는 불변성은 **`Items` 참조가 바뀌지 않는다**는 것뿐이다. 리스트 내용은 누구나 바꿀 수 있다. 19.4절의 얕은 복사 함정과 같은 뿌리다. `record`를 썼다는 사실이 불변성을 증명하지 않는다 — **멤버 타입이 전부 불변일 때만** 그 타입이 불변이다.
>
> 실무 규칙: 레코드 멤버는 `string`, 원시 타입, 열거형, 다른 불변 레코드, `ImmutableArray<T>`/`ImmutableList<T>`로 제한한다. `List<T>`, `Dictionary<K,V>`, 배열이 보이면 경고 신호다(24.10절).

### 불변 타입을 초기화하는 세 가지 전략

타입의 복잡도에 따라 셋 중 하나를 쓴다.

| 전략 | 방식 | 예 |
|---|---|---|
| 생성자 | 합리적인 생성자 집합을 정의한다. 가장 단순한 접근 | 위 `Address` |
| 팩터리 메서드 | 흔한 값을 만들기 쉽게 한다 | `Color.FromKnownColor()`, `Color.FromName()` |
| 가변 동반 클래스 | 완전히 만들기까지 여러 단계가 필요할 때 | `System.Text.StringBuilder` → `string` |

`Color` 타입은 시스템 색상을 초기화할 때 팩터리 전략을 따른다. 정적 메서드 `Color.FromKnownColor()`와 `Color.FromName()`은 주어진 시스템 색상의 현재 값을 나타내는 복사본을 반환한다.

`string`은 세 번째 전략의 표준 예다. `StringBuilder`로 여러 연산을 거쳐 문자열을 만들고, 필요한 작업이 끝나면 불변 문자열을 꺼낸다.

> **💡 레코드에 팩터리를 붙이는 관용구**
>
> 위치 매개변수는 검증을 넣기 어렵다(19.6절). 그렇다고 생성자를 손으로 다 쓰기는 아깝다면, **생성자를 비공개로 만들고 정적 팩터리를 노출하는** 절충이 있다.
>
> ```csharp
> public sealed record Percentage
> {
>     public double Value { get; }
>
>     private Percentage(double value) => Value = value;
>
>     public static Percentage Create(double value) =>
>         value is >= 0 and <= 100
>             ? new Percentage(value)
>             : throw new ArgumentOutOfRangeException(nameof(value));
>
>     public static bool TryCreate(double value, out Percentage? result) { /* ... */ }
> }
> ```
>
> 이때 `with`는 쓸 수 없다는 점을 감수해야 한다 — `Value`가 `init`이 아니기 때문이다. 검증의 완결성과 `with`의 편의성 중 무엇이 중요한지에 따라 고른다.

### 대가

불변성은 공짜가 아니다. 계산서를 정확히 알아야 한다.

**1) 할당.** 상태를 바꿀 때마다 새 객체가 생긴다. `record class`에서는 `with` 한 번이 힙 할당 한 번이다(19.4절). 0세대에서 죽는 객체라 GC 관점에서는 싼 편이지만, 초당 수백만 번이면 이야기가 다르다. 숨은 할당의 전체 지도는 63.9절에 있다.

**2) `with` 연쇄.** 여러 단계를 거치며 상태를 갱신하는 파이프라인은 중간 객체를 그 단계 수만큼 만든다. 한 번의 `with`에 모아 쓰는 것으로 대부분 해결된다.

**3) 큰 값 타입의 복사.** `record struct`는 할당을 없애지만 복사를 만든다. 필드가 여덟 개를 넘어가면 손익 계산표의 "인스턴스 크기" 항목이 손해 칸으로 이동한다(16.8절, 69.1절). 메서드 경계를 자주 넘는 큰 구조체는 `in` 매개변수로 받거나(10.2절), 아예 `record class`로 바꾼다.

**4) 얕은 불변.** 위에서 본 대로다. 멤버가 가변이면 불변성은 표면뿐이다.

**5) 컬렉션 갱신.** 불변 컬렉션의 갱신은 구조를 공유하더라도 O(log n)이다. 대량 갱신이 필요하면 빌더(`ImmutableList<T>.Builder`)를 쓰거나 가변 컬렉션으로 만들고 마지막에 고정한다(24.10절).

**6) 인터롭과 프레임워크 제약.** 매개변수 없는 생성자와 세터를 요구하는 오래된 데이터 바인딩·직렬화·ORM 스택은 `init` 전용 레코드를 다루지 못할 수 있다.

| 얻는 것 | 잃는 것 |
|---|---|
| 검증 한 번으로 끝나는 유효성 | 상태 변경마다 할당 |
| 잠금 없는 스레드 안전성 | 큰 값 타입의 복사 비용 |
| 예외 안전성(부분 적용 없음) | 프레임워크·직렬화 호환성 제약 |
| 안전한 외부 노출(방어적 복사 불필요) | 멤버가 가변이면 전부 무효 |
| 안정적인 해시 → 딕셔너리 키 적합 | 대량 갱신 시 중간 객체 |
| 시간 여행 · 스냅숏 · 되돌리기가 자연스러움 | 개체 정체성이 필요한 도메인과 충돌 |

> **💡 "불변이 기본, 가변은 측정 후"**
>
> 순서를 이렇게 잡는다. `readonly record struct` 또는 `sealed record`로 시작한다. 프로파일러가 그 타입의 할당이나 복사를 병목으로 지목하면(67.5절) 그때 가변 타입으로 내려간다. 반대 순서 — 가변으로 짜고 나중에 불변으로 올리기 — 는 훨씬 비싸다. 이미 `obj.Prop = x`가 코드베이스 전체에 퍼진 뒤이기 때문이다.

> **📌 불변 객체와 애플리케이션 서버**

## 이 장의 요약

- **레코드는 런타임 기능이 아니라 컴파일러가 대신 써 주는 코드다.** CLR은 레코드를 그냥 클래스나 구조체로 본다. 새 IL 명령도, 새 기반 타입도 없다. 다만 합성 멤버 열댓 개가 붙는다.
- **레코드가 없애는 것은 타이핑이 아니라 결합 지점이다.** 손으로 쓴 불변 DTO에 필드를 하나 추가하면 일곱 군데를 고쳐야 하고, 그중 하나를 빠뜨려도 컴파일은 성공한다. 레코드의 결합 지점은 선언 한 곳이다.
- **`record` = `record class`이고, `record struct`는 ※C# 10에 추가됐다.** 위치 매개변수의 기본 접근자가 클래스는 `init`, 구조체는 `set`으로 정반대이므로 값 타입에서는 거의 언제나 `readonly record struct`를 쓴다.
- **생성되는 멤버는 열댓 개이며 각각 형태가 정해져 있다.** `EqualityContract`·`Equals` 두 벌·`GetHashCode`·`ToString`·`PrintMembers`·`==`/`!=`·복사 생성자·`<Clone>$`·`Deconstruct`. 이 중 직접 대체할 수 있는 것은 `ToString`, `PrintMembers`, `GetHashCode`, 강타입 `Equals`, 복사 생성자뿐이다.
- **`with`는 `<Clone>$` 호출 후 `init` 세터를 부르는 두 단계다.** 1단계는 접근자를 우회하는 필드 단위 얕은 복사이고, 2단계만 검증을 통과한다. `<Clone>$`가 가상이므로 상속 계층에서 런타임 타입이 보존된다.
- **`EqualityContract`가 파생 타입 인스턴스를 기반 타입 인스턴스와 다르게 만든다.** 손으로 `Equals`를 쓸 때 흔한 대칭성 위반을 구조적으로 차단한다. `record struct`는 상속이 없으므로 이 장치가 필요 없다.
- **기본 동등성은 지연 값·배열·가변 컬렉션 앞에서 깨진다.** 고치는 방법은 `public virtual bool Equals(T other)`를 쓰는 것이며(`override`가 아니다), `GetHashCode`도 함께 바꿔야 한다. `==`·`!=`·`IEquatable<T>`는 계속 컴파일러가 맡는다.
- **위치 매개변수는 검증과 상극이다.** 기본 생성자 매개변수를 프로퍼티에 대입할 방법이 없어 `init` 접근자의 검사가 생성 경로에서 통째로 건너뛰어진다. 검증이 필요하면 매개변수 목록을 버리고 명시적 생성자를 쓴다.
- **불변성은 검증·스레드 안전성·예외 안전성·해시 안정성을 준다.** 대가는 상태 변경마다의 할당, 큰 값 타입의 복사 비용, 그리고 멤버가 가변이면 전부 무효가 된다는 것이다.
- **`record`를 붙였다는 사실이 불변성을 증명하지 않는다.** 멤버 타입이 전부 불변일 때만 그 타입이 불변이다. `List<T>`나 배열이 멤버에 보이면 값 의미론과 얕은 복사가 동시에 거짓말을 시작한다.

## 연습 문제

1. **합성 멤버를 눈으로 확인하라.** `public record Point(double X, double Y);` 한 줄만 있는 클래스 라이브러리를 만들고 릴리스로 빌드한 뒤, ILSpy나 dotPeek으로 열어라. 19.3절의 표에 있는 15개 항목이 전부 있는지 대조하고, `EqualityContract`의 접근성을 확인하라. 그다음 `sealed`를 붙여 다시 빌드하고 `EqualityContract`와 `PrintMembers`의 접근성이 어떻게 바뀌는지 비교하라.

2. **`with`의 IL을 확인하라.** `p1 with { Y = 4 }` 한 줄을 컴파일해 IL을 보고, `callvirt <Clone>$` → `dup` → `callvirt set_Y` 순서를 직접 확인하라. 그다음 같은 레코드를 `readonly record struct`로 바꿔 다시 컴파일하고, `<Clone>$` 호출이 사라진 것과 그 자리에 무엇이 들어왔는지 설명하라.

3. **얕은 복사를 재현하라.** `record Order(string Id, List<string> Items);`를 만들고 `with`로 복제본을 만든 뒤 복제본의 리스트에 항목을 추가하라. 원본의 `Items.Count`가 얼마인지 확인하고, `ReferenceEquals(o1.Items, o2.Items)`의 결과를 설명하라. 그다음 `List<string>`을 `ImmutableArray<string>`으로 바꿔 같은 실험을 반복하고, `==` 결과가 어떻게 달라지는지 기록하라.

4. **동등성이 관찰 시점에 따라 달라지는 것을 재현하라.** 19.5절의 지연 캐시 `Point`를 만들고, 두 인스턴스 중 하나만 `DistanceFromOrigin`을 읽은 뒤 `==`로 비교하라. `False`가 나오는 것을 확인한 다음, 강타입 `Equals`와 `GetHashCode`를 재정의해 고치고, `HashSet<Point>`에 두 인스턴스를 넣었을 때 개수가 1이 되는지 확인하라.

5. **검증이 절반만 걸린 레코드를 재현하라.** 19.6절의 `record Person(string Name)` 예제(백킹 필드 초기화자 + `init` 널 검사)를 그대로 만들고, `new Person(null)`이 성공하는 것과 `p with { Name = null }`이 예외를 던지는 것을 각각 확인하라. 그다음 매개변수 목록을 제거하고 명시적 생성자로 고쳐 두 경로 모두 막아라.

6. **상속 계층에서 `with`가 무엇을 반환하는지 확인하라.** `record Person(string Name);`과 `record Employee(string Name, string Dept) : Person(Name);`을 만들고, `Person`으로 선언한 변수에 `Employee`를 담아 `with { Name = "Amy" }`를 적용하라. `GetType().Name`과 `ToString()` 결과를 확인하고, `with { Dept = "Sales" }`가 왜 컴파일되지 않는지 설명하라.

7. **`with` 연쇄의 할당을 측정하라.** 프로퍼티 여덟 개짜리 레코드를 만들고, (가) `with`를 다섯 번 이어 쓴 버전과 (나) 한 번의 `with`에 다섯 프로퍼티를 모아 쓴 버전을 BenchmarkDotNet의 `MemoryDiagnoser`로 비교하라(67.5절). 할당 바이트 수의 비율이 예상과 맞는지 확인하고, 같은 실험을 `readonly record struct`로 반복해 할당이 0이 되는지 보라.
