# 17장. 컨테이너를 손으로 만들기

> **🎮 게임 서버 개발자에게** — 2부의 마지막 장이다. 9장(네임스페이스), 10장(cgroup), 11장(overlayfs), 12장(OCI 런타임)에서 따로 본 부품을 **리눅스 명령만으로 한 번에 조립**한다. `docker`도 `kubectl`도 쓰지 않는다. 직접 `clone`/`unshare`로 격리하고, 가상 랜선(veth)을 꽂고, cgroup 파일에 숫자를 써서 제한하면 "컨테이너는 그냥 프로세스"라는 말이 비유가 아니라 직접 만든 사실이 된다. 이 장의 "Pod"는 컨테이너 여러 개가 네트워크를 공유하는 쿠버네티스의 실행 단위인데, 3부에서 정식으로 다루기 전에 그 밑바닥 구조를 미리 만져 보는 것이다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 컨테이너가 "OOMKilled / exit 137"로 죽었는데, 그 숫자가 커널의 어느 파일(`memory.max`)에서 왔는지 설명해야 한다.
> - 한 파드 안의 두 컨테이너가 `localhost`로 통신하고, 한쪽이 재시작돼도 IP가 안 바뀌는 이유를 알고 싶다.
> - 보안 검토에서 "컨테이너에서 어떤 권한(capability)과 시스템 콜을 줄 것인가"를 결정해야 한다.

## 코어 — 이것만은 100%

> **한 문장:** "컨테이너"라는 커널 객체는 없고, namespace(무엇을 보는가)·cgroup(얼마나 쓰는가)·capability(무엇을 할 수 있는가)·overlayfs(파일을 어떻게 쌓는가)·seccomp(어떤 시스템 콜을 부르는가)를 조합한 프로세스일 뿐이며, 파드의 pause 컨테이너는 공유 네임스페이스를 대신 소유해 앱 컨테이너가 죽어도 IP를 지킨다.

1. **컨테이너 = 프리미티브 조합** — 5종 프리미티브를 조합한 프로세스이고, `/proc/<pid>/ns/*`의 inode 번호가 같으면 같은 네임스페이스다. `setns`가 "기존 네임스페이스에 합류"하는 파드의 핵심 호출이다.
2. **pause 컨테이너** — 빈 프로세스가 네임스페이스를 소유하고 PID 1로서 좀비를 수거한다. 그래서 앱 컨테이너가 죽었다 살아나도 파드 IP가 유지된다.
3. **손으로 만든 파드** — `ip netns`(pause 역할) + veth(CNI 역할) + cgroup + `unshare`로 파드와 동등한 환경을 만들면 localhost 통신, PID 격리, 메모리 제한 후 137 종료가 모두 재현된다. cgroup은 v2가 표준이다.
4. **overlayfs 직접 마운트** — 수정은 copy-up, 삭제는 whiteout이다. 다른 레이어에서 지워도 이미지 크기는 줄지 않는다.
5. **capability와 seccomp** — capability는 root 권한을 쪼갠 것이고 컨테이너 런타임은 기본적으로 일부만 남긴다. seccomp 프로파일은 호출 가능한 시스템 콜의 허용 목록이다.

## 코어 1. 컨테이너 = 프리미티브 조합

### 1.1 컨테이너를 이루는 것들

**한 줄 요약:** namespaces, cgroups, capabilities, union FS, seccomp/LSM의 조합을 컨테이너라고 부를 뿐이다.

```
┌───────────────────────────────────────────────────┐
│                   "컨테이너"                        │
│  namespaces   무엇을 볼 수 있는가                    │
│    PID, NET, MNT, UTS, IPC, USER, CGROUP, TIME    │
│  cgroups      얼마나 쓸 수 있는가                    │
│    cpu, memory, io, pids, hugetlb                 │
│  capabilities 무엇을 할 수 있는가                    │
│    CAP_NET_ADMIN, CAP_SYS_ADMIN, ...              │
│  union FS     파일 시스템을 어떻게 쌓는가             │
│    overlayfs (lowerdir + upperdir → merged)       │
│  seccomp/LSM  어떤 시스템콜을 호출할 수 있는가        │
│    seccomp-bpf, AppArmor, SELinux                 │
└───────────────────────────────────────────────────┘
```

**"컨테이너"라는 커널 객체는 존재하지 않는다.** 위 기능들을 조합한 프로세스를 컨테이너라고 부른다. 호스트에서 `ps aux`로 보면 그냥 프로세스다. 각 프리미티브의 상세는 [네임스페이스](09-네임스페이스.md), [cgroup](10-cgroup.md), [이미지·overlayfs](11-이미지-레이어-overlayfs.md), [OCI 런타임](12-OCI-표준과-런타임.md)에서 다뤘고, 이 장은 그것을 한 번에 조립한다.

### 1.2 네임스페이스 확인과 시스템 콜 3종

**한 줄 요약:** `/proc/<pid>/ns/*`의 대괄호 inode 번호가 같으면 같은 네임스페이스이고, `setns`가 파드의 핵심이다.

```bash
ls -l /proc/self/ns/
```

```
lrwxrwxrwx cgroup -> 'cgroup:[4026531835]'
lrwxrwxrwx ipc    -> 'ipc:[4026531839]'
lrwxrwxrwx mnt    -> 'mnt:[4026531841]'
lrwxrwxrwx net    -> 'net:[4026531840]'
lrwxrwxrwx pid    -> 'pid:[4026531836]'
lrwxrwxrwx time   -> 'time:[4026531834]'
lrwxrwxrwx user   -> 'user:[4026531837]'
lrwxrwxrwx uts    -> 'uts:[4026531838]'
```

두 프로세스가 같은 번호를 가지면 같은 네임스페이스를 공유한다. 이 사실이 뒤에서 파드를 검증하는 도구가 된다. 시스템 전체 목록은 `lsns`, 네트워크만은 `lsns -t net`이다.

| 시스템콜 | 하는 일 | 명령행 도구 |
|---|---|---|
| `clone(CLONE_NEW*)` | 새 네임스페이스와 함께 프로세스 생성 | `unshare --fork` |
| `unshare(CLONE_NEW*)` | 현재 프로세스를 새 네임스페이스로 분리 | `unshare` |
| `setns(fd, type)` | **기존 네임스페이스에 합류** | `nsenter` |

pause 컨테이너가 만든 네임스페이스에 다른 컨테이너들이 합류하는 것이 바로 `setns`다.

## 코어 2. pause 컨테이너

### 2.1 왜 필요한가

**한 줄 요약:** 앱 컨테이너 중 하나가 네임스페이스를 소유하면 그 컨테이너가 죽을 때 네트워크가 사라져 IP가 바뀌므로, 별도의 빈 프로세스가 소유한다.

파드에 컨테이너 A와 B가 있고 네트워크를 공유해야 한다고 하자. 누가 네임스페이스를 소유할까?

```
[방안 1] A가 소유하고 B가 합류
  → A가 크래시하면 네임스페이스가 사라진다
  → B의 네트워크도 끊기고, 파드 IP가 바뀐다  ✗

[방안 2] 별도의 "빈" 프로세스가 소유
  → A, B가 모두 죽었다 살아나도 네임스페이스는 유지
  → 파드 IP가 보존된다  ✓
```

방안 2의 빈 프로세스가 pause다(인프라 컨테이너, 샌드박스라고도 부른다). 소스는 놀랄 만큼 짧다.

```c
/* pause.c — 핵심만 */
static void sigdown(int signo) { _exit(0); }
static void sigreap(int signo) {
    while (waitpid(-1, NULL, WNOHANG) > 0);   /* 좀비 수거 */
}

int main() {
    signal(SIGINT,  sigdown);
    signal(SIGTERM, sigdown);
    signal(SIGCHLD, sigreap);
    for (;;) pause();          /* 시그널이 올 때까지 잠든다 */
}
```

하는 일은 두 가지다. (1) 프로세스가 살아 있어야 네임스페이스가 유지되므로 네임스페이스를 살려 둔다. (2) PID 네임스페이스의 PID 1로서 고아 프로세스를 입양해 `wait()`로 정리한다. 하지 않으면 좀비가 쌓인다([프로세스](../1부-리눅스-OS-구성-요소/02-프로세스.md), [시그널](../1부-리눅스-OS-구성-요소/03-시그널.md)). `shareProcessNamespace: true`인 파드에서 pause가 PID 1이 되는 이유다.

### 2.2 실제 노드에서 확인하기

**한 줄 요약:** 샌드박스와 앱 컨테이너의 네임스페이스를 비교하면 net·ipc·uts는 같고 mnt·pid는 다르다.

```bash
crictl pods                                                   # 샌드박스(pause) 목록
POD_PID=$(crictl inspectp <POD_ID> | jq -r '.info.pid')
ls -l /proc/$POD_PID/ns/
crictl ps --pod <POD_ID>
APP_PID=$(crictl inspect <CONTAINER_ID> | jq -r '.info.pid')
ls -l /proc/$APP_PID/ns/
```

두 출력을 비교하면 `net`, `ipc`, `uts`는 **inode 번호가 같고(공유)**, `mnt`, `pid`는 **다르다(분리)**. 파드 모델이 커널 데이터로 확인된다. 샌드박스를 다루는 kubelet·CRI는 [23장](../3부-쿠버네티스-구성-요소/23-kubelet과-CRI.md)에서, 파드 구조는 [24장](../3부-쿠버네티스-구성-요소/24-오브젝트-모델과-워크로드.md)에서 이어진다.

## 코어 3. 손으로 만든 파드

루트 권한이 있는 리눅스 머신이 필요하다. 원문은 kind 노드 안에서 하는 것이 안전하다고 안내한다(`docker exec -it k8s-guide-worker bash` 후 `iproute2 procps util-linux curl` 설치).

### 3.1 네트워크 네임스페이스와 veth (pause와 CNI 역할)

**한 줄 요약:** 빈 네트워크 네임스페이스를 만들고 veth 한쪽을 넣고 IP를 주면 그것이 파드 IP다.

```bash
# "pod-lab" 네트워크 네임스페이스 = 우리의 pause
ip netns add pod-lab
ip netns exec pod-lab ip addr
# 1: lo: <LOOPBACK> mtu 65536 state DOWN   ← lo 하나뿐, DOWN
```

CNI 플러그인이 하는 일이 바로 이 빈 네임스페이스를 채우는 것이다([26장](../3부-쿠버네티스-구성-요소/26-쿠버네티스-네트워크-모델과-CNI.md)).

```bash
# ① 루프백 활성화 — localhost 통신에 필수
ip netns exec pod-lab ip link set lo up
# ② veth 페어 생성 (가상 랜선 한 쌍)
ip link add veth-host type veth peer name veth-pod
# ③ 한쪽 끝을 네임스페이스 안으로
ip link set veth-pod netns pod-lab
# ④ 파드 쪽 인터페이스 설정
ip netns exec pod-lab ip link set veth-pod name eth0
ip netns exec pod-lab ip addr add 10.99.0.2/24 dev eth0
ip netns exec pod-lab ip link set eth0 up
# ⑤ 호스트 쪽 설정
ip addr add 10.99.0.1/24 dev veth-host
ip link set veth-host up
# ⑥ 파드의 기본 게이트웨이
ip netns exec pod-lab ip route add default via 10.99.0.1
```

```bash
ping -c 2 10.99.0.2                          # 호스트 → 파드
ip netns exec pod-lab ping -c 2 10.99.0.1    # 파드 → 호스트
```

`10.99.0.2`가 이 파드의 주소다. 외부 통신을 원한다면 `iptables -t nat -A POSTROUTING -s 10.99.0.0/24 ! -o veth-host -j MASQUERADE`와 `sysctl -w net.ipv4.ip_forward=1`로 NAT를 건다. 이 구조는 [16장](16-Docker-네트워크.md)의 브리지·veth·MASQUERADE와 같은 부품이다.

### 3.2 cgroup으로 자원 제한

**한 줄 요약:** cgroup v2에서는 디렉터리를 만들고 `cpu.max`, `memory.max`, `pids.max`에 숫자를 쓴다.

```bash
stat -fc %T /sys/fs/cgroup/        # cgroup2fs 이면 v2

mkdir -p /sys/fs/cgroup/pod-lab
echo "+cpu +memory +pids" > /sys/fs/cgroup/cgroup.subtree_control 2>/dev/null || true
echo "+cpu +memory +pids" > /sys/fs/cgroup/pod-lab/cgroup.subtree_control

# 파드 전체 제한 (limits 와 대응)
echo "20000 100000" > /sys/fs/cgroup/pod-lab/cpu.max          # 0.2 코어
echo $((256*1024*1024)) > /sys/fs/cgroup/pod-lab/memory.max   # 256Mi
echo 100 > /sys/fs/cgroup/pod-lab/pids.max

# 컨테이너별 하위 cgroup
mkdir -p /sys/fs/cgroup/pod-lab/container-a /sys/fs/cgroup/pod-lab/container-b
echo $((128*1024*1024)) > /sys/fs/cgroup/pod-lab/container-a/memory.max
echo $((64*1024*1024))  > /sys/fs/cgroup/pod-lab/container-b/memory.max
```

`cpu.max`의 `"20000 100000"`은 100ms 주기마다 20ms의 CPU 시간이라는 뜻이다([1부 커널·스케줄러](../1부-리눅스-OS-구성-요소/01-커널-시스템콜-스케줄러.md)의 스로틀링과 같은 메커니즘). 이 계층은 kubelet이 만드는 모양과 같다.

```
/sys/fs/cgroup/
└── kubepods.slice/                                  ← 모든 파드의 부모
    ├── kubepods-besteffort.slice/                   ← QoS 클래스별
    ├── kubepods-burstable.slice/
    │   └── kubepods-burstable-pod<UID>.slice/       ← 파드 하나
    │       ├── cri-containerd-<pause-id>.scope
    │       ├── cri-containerd-<container-a-id>.scope
    │       └── cri-containerd-<container-b-id>.scope
    └── (Guaranteed는 kubepods.slice 바로 아래)
```

### 3.3 컨테이너 실행과 검증

**한 줄 요약:** `ip netns exec`로 네트워크 네임스페이스에 합류하고 `unshare`로 mnt·pid를 새로 만들어 net은 같고 pid/mnt는 다른 두 프로세스를 만든다.

컨테이너 A(HTTP 서버)는 네트워크는 `pod-lab`에 합류하고 MNT/PID는 새로 만든다.

```bash
ip netns exec pod-lab \
  unshare --mount --pid --fork --mount-proc \
  bash -c '
    echo $$ > /sys/fs/cgroup/pod-lab/container-a/cgroup.procs   # 자신을 cgroup에 등록
    echo "=== container-a ==="
    echo "PID: $$"                                              # 1이어야 한다
    ip addr show eth0 | grep inet                               # 파드 IP
    python3 -m http.server 8080
  ' &
```

컨테이너 B는 같은 네트워크 네임스페이스에서 `localhost`로 A를 호출한다.

```bash
ip netns exec pod-lab \
  unshare --mount --pid --fork --mount-proc \
  bash -c '
    echo $$ > /sys/fs/cgroup/pod-lab/container-b/cgroup.procs
    echo "PID: $$"
    curl -s localhost:8080 | head -5      # container-a 의 응답
    ps aux                                # 자기 PID 네임스페이스만 보임
  '
```

```
=== container-b ===
PID: 1                              ← 자기만의 PID 네임스페이스
(container-a의 응답)                 ← NET 네임스페이스 공유!
PID  COMMAND
1    bash                           ← container-a의 프로세스는 안 보임
```

파드가 만들어졌다. 두 프로세스가 같은 IP와 포트 공간을 쓰고(localhost 통신), PID·MNT 네임스페이스는 다르며(서로의 프로세스·파일시스템이 안 보임), 각자 다른 cgroup에서 자원이 제한된다. 네임스페이스 공유를 확인한다.

```bash
for p in $(ip netns pids pod-lab); do
  echo "=== PID $p ==="
  readlink /proc/$p/ns/net    # 같아야 한다
  readlink /proc/$p/ns/pid    # 달라야 한다
  readlink /proc/$p/ns/mnt    # 달라야 한다
done
```

**net은 같고 pid/mnt는 다르다. 이것이 파드의 정의다.**

메모리 제한을 확인한다. 64Mi 한도를 두고 10MB씩 할당하면 60MB 부근에서 죽는다.

```bash
ip netns exec pod-lab unshare --pid --fork \
  bash -c '
    echo $$ > /sys/fs/cgroup/pod-lab/container-b/cgroup.procs
    echo "메모리 한도: $(cat /sys/fs/cgroup/pod-lab/container-b/memory.max)"
    python3 -c "
data = []
for i in range(1, 30):
    data.append(bytearray(10*1024*1024))
    print(f\"allocated {i*10}MB\", flush=True)
"
  '
# allocated 10MB ... allocated 60MB
# Killed                    ← 64Mi 한도 초과
echo $?
# 137                       ← 128 + 9(SIGKILL)
```

`OOMKilled`의 정체를 직접 만든 셈이다.

> **[보충]** 137은 128 + 9로, 프로세스가 시그널 9(SIGKILL)로 종료됐다는 셸의 관례적 표기다. 원문은 "137"이 쿠버네티스에서 보는 exitCode와 같다고만 설명한다([시그널](../1부-리눅스-OS-구성-요소/03-시그널.md) 참고).

마지막으로 앱 컨테이너를 죽여도 IP가 유지되는지 본다.

```bash
kill %1                                          # container-a 를 죽인다
ip netns exec pod-lab ip addr show eth0 | grep inet
# inet 10.99.0.2/24 ...                           ← 유지됨!
```

pause 역할을 하는 네임스페이스 파일(`/var/run/netns/pod-lab`)이 있기 때문에 IP가 보존된다. 정리는 `ip netns delete pod-lab`, `ip link delete veth-host`, 만든 cgroup 디렉터리 `rmdir`, iptables 규칙 `-D` 순이다.

### 3.4 cgroup v1과 v2

**한 줄 요약:** v2는 단일 통합 계층이고 `memory.high`·PSI를 제공하며 v2가 표준이다.

- **v1:** 컨트롤러마다 별도 계층(`/sys/fs/cgroup/cpu/...`, `memory/...`)이라 같은 프로세스를 각 계층에 따로 등록해야 한다.
- **v2:** 하나의 트리에 모든 컨트롤러가 있고 프로세스는 정확히 하나의 cgroup에만 속한다.

| 항목 | v1 | v2 |
|---|---|---|
| CPU 상한 | `cpu.cfs_quota_us` / `cpu.cfs_period_us` | `cpu.max` ("quota period") |
| CPU 가중치 | `cpu.shares` (2&#126;262144) | `cpu.weight` (1&#126;10000) |
| 메모리 상한 | `memory.limit_in_bytes` | `memory.max` |
| 메모리 소프트 | `memory.soft_limit_in_bytes` | `memory.high` |
| 현재 사용량 | `memory.usage_in_bytes` | `memory.current` |
| PID 제한 | `pids.max` | `pids.max` |
| 프로세스 등록 | `tasks` / `cgroup.procs` | `cgroup.procs` |

v2의 중요한 개선은 셋이다. (1) `memory.high`는 넘으면 회수 압력을 가하고 프로세스를 스로틀링해 **죽이지 않고 늦춘다**(v1은 하드 리밋뿐이라 넘으면 즉시 OOM Kill). `memory.max`는 OOM Kill 지점이다. (2) PSI(Pressure Stall Information)는 자원 경합 지연을 정량화한다. `cat /sys/fs/cgroup/kubepods.slice/cpu.pressure`에서 `some`은 최소 하나의 태스크가 대기한 시간 비율, `full`은 모든 태스크가 대기한 시간 비율이다(`memory.pressure`, `io.pressure`도 있다). (3) `cgroup.subtree_control`로 하위 계층에 컨트롤러 관리를 위임할 수 있다. Fedora 31+, Ubuntu 21.10+, RHEL 9+, Debian 11+가 기본 v2이고 쿠버네티스는 v1.25부터 cgroup v2를 GA로 지원하며 v1은 유지보수 모드다.

## 코어 4. overlayfs 직접 마운트

### 4.1 레이어 겹치기와 copy-up

**한 줄 요약:** 위 레이어가 이기고, 수정은 upperdir로의 copy-up이며, 원본은 그대로다.

```bash
mkdir -p /tmp/ofs/{lower1,lower2,upper,work,merged}
echo "from layer 1" > /tmp/ofs/lower1/a.txt
echo "from layer 1" > /tmp/ofs/lower1/shared.txt
echo "from layer 2" > /tmp/ofs/lower2/b.txt
echo "from layer 2 (overrides)" > /tmp/ofs/lower2/shared.txt

# lowerdir 은 오른쪽이 아래, 왼쪽이 위
mount -t overlay overlay \
  -o lowerdir=/tmp/ofs/lower2:/tmp/ofs/lower1,upperdir=/tmp/ofs/upper,workdir=/tmp/ofs/work \
  /tmp/ofs/merged

ls /tmp/ofs/merged/                 # a.txt  b.txt  shared.txt
cat /tmp/ofs/merged/shared.txt      # from layer 2 (overrides)  ← 위 레이어가 이긴다

echo "modified" >> /tmp/ofs/merged/a.txt
cat /tmp/ofs/lower1/a.txt           # from layer 1  ← 원본은 그대로
ls /tmp/ofs/upper/                  # a.txt         ← upperdir 에 사본(copy-up)
```

### 4.2 삭제는 whiteout

**한 줄 요약:** 하위 레이어의 파일을 지워도 실제로는 upperdir에 0:0 문자 디바이스 표시가 생길 뿐이다.

```bash
rm /tmp/ofs/merged/b.txt
ls -la /tmp/ofs/upper/
# c--------- b.txt        ← character device 0:0 = whiteout
ls /tmp/ofs/lower2/
# b.txt                   ← 원본은 살아 있다
```

이것이 컨테이너 파일시스템의 전부다. 삭제해도 이미지 레이어는 그대로이므로 이미지 크기가 줄지 않는다. Dockerfile에서 `RUN apt-get install ... && rm -rf /var/lib/apt/lists/*`를 **한 줄로 묶어야** 하는 이유다. 별도 레이어에서 지우면 whiteout만 추가되고 크기는 그대로다([15장](15-빌드-BuildKit-Dockerfile.md), [11장](11-이미지-레이어-overlayfs.md)). 정리는 `umount /tmp/ofs/merged; rm -rf /tmp/ofs`.

## 코어 5. capability와 seccomp

### 5.1 capability 확인과 제거

**한 줄 요약:** `CapEff` 비트마스크가 유효 권한이고, 필요 없는 capability를 떼어 내면 해당 동작이 거부된다.

```bash
grep Cap /proc/self/status
# CapInh: 0000000000000000
# CapPrm: 000001ffffffffff
# CapEff: 000001ffffffffff        ← 유효 capability 비트마스크
# CapBnd: 000001ffffffffff

capsh --decode=000001ffffffffff | tr ',' '\n' | head

# NET_ADMIN 없이 인터페이스 조작 시도 → 실패
capsh --drop=cap_net_admin -- -c 'ip link set lo down' 2>&1
# RTNETLINK answers: Operation not permitted
```

컨테이너 런타임은 기본적으로 14개 정도만 남기고 나머지를 제거한다. 쿠버네티스 securityContext의 권장 형태는 아래와 같다(30장에서 다룬다).

```yaml
securityContext:
  capabilities:
    drop: ["ALL"]
    add: ["NET_BIND_SERVICE"]     # 1024 미만 포트만 필요하다면
```

### 5.2 seccomp 프로파일

**한 줄 요약:** 허용 목록에 없는 시스템 콜은 `EPERM`을 돌려받고, `SCMP_ACT_KILL`이면 프로세스가 즉시 죽는다.

```json
{
  "defaultAction": "SCMP_ACT_ERRNO",
  "architectures": ["SCMP_ARCH_X86_64"],
  "syscalls": [
    {
      "names": ["read", "write", "exit", "exit_group", "rt_sigreturn",
                "brk", "mmap", "munmap", "openat", "close", "fstat"],
      "action": "SCMP_ACT_ALLOW"
    }
  ]
}
```

쿠버네티스에서는 노드의 `/var/lib/kubelet/seccomp/profiles/`에 배치한 뒤 `securityContext.seccompProfile`에 `type: Localhost`와 `localhostProfile: profiles/minimal.json`으로 지정한다. 실무에서는 Security Profiles Operator로 앱을 실행하며 사용하는 시스템 콜을 기록해 프로파일을 자동 생성한다. 시스템 콜 개념 자체는 [1부 커널·시스템콜](../1부-리눅스-OS-구성-요소/01-커널-시스템콜-스케줄러.md)이다.

### 5.3 손으로 만든 것 ↔ 쿠버네티스 대응표

**한 줄 요약:** 컨테이너 런타임(containerd/runc)이 하는 일이 정확히 이것이고, 손으로 한 것을 OCI 스펙에 따라 자동화할 뿐이다.

| 우리가 만든 것 | 쿠버네티스에서 |
|---|---|
| `ip netns add pod-lab` | pause 컨테이너 생성 |
| veth 페어 + IP 할당 | CNI 플러그인 `ADD` |
| `unshare --mount --pid` | 각 컨테이너의 격리 |
| `/sys/fs/cgroup/pod-lab/` | 파드 수준 cgroup |
| `.../container-a/memory.max` | `limits.memory` |
| `cpu.max` | `limits.cpu` |
| OOM으로 인한 종료(137) | `OOMKilled` |
| overlayfs merged | 컨테이너 rootfs |
| `capsh --drop` | `securityContext.capabilities.drop` |
| seccomp 프로파일 | `seccompProfile` |

runc가 받는 `config.json`은 `find /run/containerd -name config.json | head -1 | xargs cat | jq '.linux.namespaces, .linux.resources.memory'`로 구경할 수 있다([12장](12-OCI-표준과-런타임.md)). 요청이 runc까지 오는 경로는 [13장](13-Docker-아키텍처.md), 리소스 requests/limits가 cgroup으로 가는 과정은 [25장](../3부-쿠버네티스-구성-요소/25-Pod-생명주기와-리소스.md)에서 이어진다.

## 실무 적용

### 체크리스트

- [ ] 컨테이너가 namespace·cgroup·capability·overlayfs·seccomp의 조합이며 커널에 "컨테이너 객체"가 없다는 것을 설명할 수 있다.
- [ ] `ls -l /proc/<pid>/ns/`의 inode 번호 비교로 두 프로세스가 같은 네임스페이스를 공유하는지 판별할 수 있다.
- [ ] 파드의 컨테이너들이 net·ipc·uts를 공유하고 mnt·pid는 분리한다는 것, 그 소유자가 pause임을 안다.
- [ ] 컨테이너 재시작에도 파드 IP가 유지되는 이유(pause가 네임스페이스를 소유)를 설명할 수 있다.
- [ ] 메모리 한도 초과가 `memory.max` → 커널 OOM Kill → exit 137(`OOMKilled`)로 이어지는 흐름을 안다.
- [ ] 노드의 cgroup 버전(`stat -fc %T /sys/fs/cgroup/`)을 확인하고 v2의 `memory.high`와 PSI를 안다.
- [ ] 이미지에서 파일을 지울 때 별도 레이어는 whiteout만 추가해 크기가 줄지 않음을 알고, 설치와 정리를 한 `RUN`에 묶는다.
- [ ] 불필요한 capability는 `drop: ["ALL"]` 후 필요한 것만 `add`하고, seccomp 프로파일 적용을 검토한다.

### 시나리오로 확인하기

1. **상황:** 파드의 앱 컨테이너가 크래시 후 재시작됐는데 파드 IP가 그대로다. 동료는 "컨테이너를 새로 만들었는데 왜 같냐"고 묻는다.
   **질문:** 왜 IP가 유지되는가?

   <details markdown="1"><summary>답 확인</summary>

   네트워크 네임스페이스를 앱 컨테이너가 아니라 pause 컨테이너가 소유하기 때문이다. 앱 컨테이너는 `setns`로 그 네임스페이스에 합류할 뿐이라 죽었다 살아나도 네임스페이스(인터페이스, IP, 라우팅)는 유지된다. 손으로 만든 실험에서도 `container-a`를 `kill`한 뒤 `ip netns exec pod-lab ip addr show eth0`에 `10.99.0.2`가 그대로 남았다. 앱 컨테이너가 소유자였다면 크래시 때 네임스페이스가 사라져 IP가 바뀌었을 것이다. → 코어 2, 코어 3

   </details>

2. **상황:** 서버 컨테이너가 `Exit Code: 137, OOMKilled`로 반복 종료된다. 컨테이너의 메모리 한도는 256Mi다.
   **질문:** 커널에서 무슨 일이 일어났고 137은 어디서 나온 숫자인가?

   <details markdown="1"><summary>답 확인</summary>

   컨테이너의 cgroup `memory.max`(256Mi)를 넘어서자 커널이 그 cgroup의 프로세스를 OOM Kill(SIGKILL)했다. 137은 128 + 9(SIGKILL)이다. 손으로 만든 실험에서 `memory.max`를 64Mi로 둔 cgroup에서 10MB씩 할당하다 60MB 부근에서 `Killed`와 함께 `echo $?`가 137이었다. v2에서는 `memory.high`를 두면 `max` 도달 전에 회수 압력과 스로틀링으로 죽이지 않고 늦출 수 있다. → 코어 3

   </details>

3. **상황:** Dockerfile에 `RUN apt-get install -y curl`과 `RUN rm -rf /var/lib/apt/lists/*`가 별도 줄로 있다. 이미지 크기가 줄지 않는다.
   **질문:** 원인과 해결은?

   <details markdown="1"><summary>답 확인</summary>

   각 `RUN`이 별도 레이어를 만든다. 다른 레이어에서 파일을 지워도 overlayfs에서는 upperdir에 whiteout(0:0 문자 디바이스) 표시가 추가될 뿐 원본 레이어의 파일은 그대로 남아 이미지 크기가 줄지 않는다(`rm`해도 `lower2`의 `b.txt`가 살아 있는 실험). 설치와 정리를 `&& rm -rf ...`로 한 `RUN`에 묶어 같은 레이어 안에서 정리하게 한다. → 코어 4

   </details>

4. **상황:** 보안팀이 "컨테이너에 불필요한 권한을 주지 말고 호출 가능한 시스템 콜도 제한하라"고 요구한다. 서버는 1024 미만 포트 바인딩만 필요하다.
   **질문:** 어떻게 구성하나?

   <details markdown="1"><summary>답 확인</summary>

   `securityContext.capabilities`에 `drop: ["ALL"]`을 두고 `add: ["NET_BIND_SERVICE"]`만 남긴다(런타임 기본은 14개 정도 남기지만 더 줄인다). 호출 가능한 시스템 콜은 seccomp 프로파일(허용 목록, 위반 시 `EPERM` 또는 `SCMP_ACT_KILL`)로 제한한다. 프로파일은 Security Profiles Operator로 앱 실행 중 사용된 시스템 콜을 기록해 자동 생성하는 것이 실무적이다. `capsh --drop=cap_net_admin -- -c 'ip link set lo down'`이 `Operation not permitted`로 거부되는 실험으로 효과를 확인할 수 있다. → 코어 5

   </details>

### 2. 인출 질문

1. 컨테이너를 이루는 프리미티브 다섯 가지와 각각이 답하는 질문은?

   <details markdown="1"><summary>답 확인</summary>

   namespaces(무엇을 볼 수 있는가: PID, NET, MNT, UTS, IPC, USER, CGROUP, TIME), cgroups(얼마나 쓸 수 있는가: cpu, memory, io, pids), capabilities(무엇을 할 수 있는가), union FS/overlayfs(파일시스템을 어떻게 쌓는가), seccomp/LSM(어떤 시스템콜을 호출할 수 있는가). 커널에 "컨테이너"라는 객체는 없고 이 조합의 프로세스일 뿐이다. → 코어 1

   </details>

2. 네임스페이스 시스템 콜 세 가지와 `setns`가 파드의 핵심인 이유는?

   <details markdown="1"><summary>답 확인</summary>

   `clone(CLONE_NEW*)`(새 네임스페이스와 함께 프로세스 생성, `unshare --fork`), `unshare(CLONE_NEW*)`(현재 프로세스를 새 네임스페이스로 분리), `setns(fd, type)`(기존 네임스페이스에 합류, `nsenter`). pause 컨테이너가 만든 네임스페이스에 다른 컨테이너들이 합류하는 것이 `setns`이기 때문이다. → 코어 1

   </details>

3. pause 컨테이너가 하는 두 가지 일과 필요한 이유는?

   <details markdown="1"><summary>답 확인</summary>

   (1) 프로세스가 살아 있어야 유지되는 네임스페이스를 대신 소유해 살려 둔다. (2) PID 1로서 고아 프로세스를 입양해 `wait()`로 좀비를 수거한다. 앱 컨테이너 하나가 네임스페이스를 소유하면 그 크래시 때 네트워크가 사라져 파드 IP가 바뀐다. → 코어 2

   </details>

4. 같은 파드의 pause와 앱 컨테이너를 `/proc/<pid>/ns/`로 비교하면 어떻게 나오나?

   <details markdown="1"><summary>답 확인</summary>

   `net`, `ipc`, `uts`는 inode 번호가 같아 공유되고, `mnt`, `pid`는 다르다(분리). 번호가 같으면 같은 네임스페이스라는 규칙으로 판별한다. → 코어 2

   </details>

5. `ip netns` + veth + cgroup + `unshare`로 파드를 만드는 순서를 말해 보라.

   <details markdown="1"><summary>답 확인</summary>

   (1) `ip netns add pod-lab`(pause 역할), (2) lo up, veth pair 생성, 한쪽을 네임스페이스에 넣고 `eth0`로 이름 변경·IP 설정, 호스트 쪽 IP, 기본 게이트웨이(CNI 역할), (3) `/sys/fs/cgroup/pod-lab/`와 컨테이너별 하위 cgroup 생성, `cpu.max`·`memory.max`·`pids.max` 설정, (4) `ip netns exec pod-lab unshare --mount --pid --fork --mount-proc`로 컨테이너 프로세스를 실행하고 `cgroup.procs`에 등록. → 코어 3

   </details>

6. cgroup v2가 v1보다 나은 점 세 가지는?

   <details markdown="1"><summary>답 확인</summary>

   단일 통합 계층(프로세스는 정확히 한 cgroup), `memory.high`(넘으면 회수 압력과 스로틀링으로 죽이지 않고 늦춤, `memory.max`는 OOM Kill 지점), PSI(`some`/`full`로 자원 경합 지연을 정량화). 그 외 `cgroup.subtree_control`로 하위 계층에 컨트롤러를 위임할 수 있다. → 코어 3

   </details>

7. overlayfs에서 수정과 삭제는 각각 어떻게 처리되며 이미지 크기에 어떤 영향을 주나?

   <details markdown="1"><summary>답 확인</summary>

   수정은 하위 레이어의 파일을 upperdir로 복사(copy-up)한 뒤 복사본을 수정하고 원본은 그대로다. 삭제는 upperdir에 0:0 문자 디바이스(whiteout) 표시를 남길 뿐 원본 레이어 파일은 살아 있어서 이미지 크기가 줄지 않는다. 그래서 설치와 정리를 한 `RUN`에 묶는다. → 코어 4

   </details>

8. capability와 seccomp는 각각 무엇을 제한하며 쿠버네티스에서 어떻게 지정하나?

   <details markdown="1"><summary>답 확인</summary>

   capability는 root 권한을 쪼갠 단위를 제한한다(예: `NET_ADMIN` 없이 인터페이스 조작 시 `Operation not permitted`). `securityContext.capabilities`의 `drop: ["ALL"]`+`add: [...]`로 지정한다. seccomp는 호출 가능한 시스템 콜 허용 목록으로, 위반 시 `EPERM` 또는 `SCMP_ACT_KILL`이다. `securityContext.seccompProfile`의 `type: Localhost`와 `localhostProfile`로 지정한다. → 코어 5

   </details>

### 3. 기억 고리

- **C++ 유추:** `clone`/`unshare`/`setns` = 컨테이너 런타임이 하는 일 ⚠️ 이 호출들이 전부이고 "컨테이너 생성" 시스템 콜은 따로 없다. 조합과 자동화가 OCI 런타임의 일이다.
- **C++ 유추:** nginx 마스터가 리스닝 소켓을 들고 있고 워커가 재시작해도 포트 유지 = pause가 네임스페이스를 소유 ⚠️ 유지되는 것이 fd 하나가 아니라 인터페이스·IP·라우팅 등 네트워크 스택 전체다.
- **비유:** 파드 = 사무실 한 칸에 책상 두 개. 같은 전화번호·내선(net 공유)을 쓰지만 서류함(mnt)과 사원 명부(pid)는 각자 따로다. pause = 사무실 임대 계약자: 직원이 퇴사해도 사무실(IP)은 유지된다. ⚠️ 비유가 깨지는 지점: pause는 실제로는 아무 일도 안 하는 빈 프로세스이고 좀비 수거(PID 1 의무)가 유일한 업무다.
- **비유:** cgroup `memory.max` = 신용카드 한도, `memory.high` = 한도 임박 경고 후 결제 지연. ⚠️ 비유가 깨지는 지점: 한도를 넘으면 결제 거절이 아니라 **프로세스가 강제 종료(exit 137)** 된다.
- **묶음(3의 법칙):** 시스템콜 3종(clone·unshare·setns) / 공유하는 ns 3(net·ipc·uts) / 손으로 만든 것 3축(netns·cgroup·unshare).
- **대칭·순서:** 공유(net·ipc·uts) ↔ 분리(mnt·pid). 수정(copy-up) ↔ 삭제(whiteout). cgroup v1(컨트롤러별 계층) ↔ v2(단일 계층). 순서: netns → veth → cgroup → unshare → 검증.
