# 14장. 볼륨·바인드 마운트·tmpfs

> **🎮 게임 서버 개발자에게** — 게임 서버는 로그, 덤프, 설정 파일, 가끔은 로컬 DB 파일까지 디스크에 쓴다. 컨테이너에서는 이 "그냥 쓰던 경로"가 기본적으로 **컨테이너와 함께 사라지는 층**에 쓰인다. 컨테이너를 교체 배포하는 순간 쌓아 둔 파일이 같이 증발한다는 뜻이다. 이 장은 데이터를 컨테이너 수명 밖으로 빼는 세 가지 방법(named volume, bind mount, tmpfs)과 각각이 호스트 어디에 놓이고 언제 사라지는지를 정리한다. 서버가 `open()`/`write()`하는 경로는 그대로인데 그 경로 아래에 **무엇이 마운트되어 있느냐**만 바뀐다는 점이 핵심이다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 게임 서버 컨테이너를 새 버전으로 교체했더니 이전 컨테이너에 쌓이던 로그와 덤프 파일이 사라졌다.
> - 개발 중 소스나 설정 파일을 컨테이너 안에 즉시 반영하고 싶은데, 매번 이미지를 다시 빌드하고 싶지 않다.
> - 런타임에만 필요한 토큰 파일을 디스크에 흔적 없이 두고 싶다.

## 코어 — 이것만은 100%

> **한 문장:** 이미지 레이어는 읽기 전용이고 컨테이너의 쓰기 레이어(upperdir)는 컨테이너와 함께 사라지므로, 살아남아야 하는 데이터는 named volume이나 bind mount로, 디스크에 남기면 안 되는 임시 데이터는 tmpfs로 컨테이너 밖에 둔다.

1. **컨테이너 쓰기 레이어는 컨테이너와 운명을 같이한다** — 컨테이너 안의 모든 변경은 upperdir에 기록되고 컨테이너를 지우면 사라진다. 이 층은 호스트 디스크의 평범한 디렉터리다.
2. **세 가지 마운트는 저장 위치와 생명주기가 다르다** — named volume은 Docker가 관리하고 컨테이너와 독립, bind mount는 호스트의 임의 경로를 노출하고 호스트의 생명주기를 따르며, tmpfs는 메모리에만 있고 컨테이너가 멈추면 소멸한다.
3. **named volume은 드라이버 뒤로 저장소를 숨긴다** — 컨테이너는 마운트 지점만 알고, 실제 데이터가 로컬 디스크인지 NFS·클라우드 블록 스토리지인지는 볼륨 드라이버가 책임진다.
4. **bind mount와 tmpfs는 각자의 함정이 있다** — bind mount는 호스트 쪽 권한·SELinux 라벨 문제를 그대로 물려받고, tmpfs는 영속성이 없다는 점이 곧 용도다.

## 코어 1. 컨테이너 쓰기 레이어는 컨테이너와 운명을 같이한다

### 1.1 이미지는 읽기 전용, 변경은 쓰기 레이어에

**한 줄 요약:** 컨테이너가 파일을 바꾸면 그 변경은 upperdir에만 기록되고, 원본 이미지 레이어는 절대 수정되지 않는다.

[11장](11-이미지-레이어-overlayfs.md)에서 본 overlayfs 구조를 다시 짚는다. 이미지 레이어들은 읽기 전용 `lowerdir`이고, 컨테이너마다 쓰기 가능한 `upperdir` 하나가 얹히며, 컨테이너 프로세스는 이 둘을 합친 `merged` 뷰를 `/`로 본다. 이미지 레이어 파일을 수정하면 먼저 upperdir로 복사(copy-on-write)한 뒤 복사본을 수정하고, 삭제는 upperdir에 "지워졌다"는 whiteout 표시를 남기는 방식이다. 이 구조 덕분에 컨테이너를 지워도 이미지는 멀쩡하고, 같은 이미지로 컨테이너를 여러 개 띄워도 서로 간섭하지 않는다.

문제는 반대편이다. 컨테이너의 쓰기 레이어는 기본적으로 **컨테이너의 생명주기와 함께한다.** (이미지 레이어는 컨테이너를 지워도 남는다.) 컨테이너를 지우면 쓰기 레이어도 같이 사라지므로, 컨테이너 재시작이나 교체에도 살아남아야 하는 데이터는 별도의 마운트로 빼서 관리해야 한다.

### 1.2 쓰기 레이어는 호스트의 평범한 디렉터리다

**한 줄 요약:** "컨테이너의 쓰기 레이어"는 추상 표현일 뿐, 호스트에서는 `diff` 디렉터리다.

레거시 overlay2 그래프 드라이버를 쓰는 호스트에서는 컨테이너 안에서 만든 파일이 곧바로 `/var/lib/docker/overlay2/<id>/diff` 아래에 나타난다.

```bash
docker run -d --name overlay-demo nginx:alpine
docker inspect --format '{{json .GraphDriver.Data}}' overlay-demo | python3 -m json.tool
# LowerDir, UpperDir, MergedDir, WorkDir 경로가 나온다

docker exec overlay-demo sh -c 'echo hello > /tmp/marker.txt'
sudo cat /var/lib/docker/overlay2/$(docker inspect --format '{{.Id}}' overlay-demo)/diff/tmp/marker.txt
docker rm -f overlay-demo      # 이 순간 쓰기 레이어(와 marker.txt)도 사라진다
```

containerd 이미지 스토어를 쓰는 경우에는 스냅샷 데이터가 `/var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/` 아래에 있다(같은 개념, 관리 주체가 다르다). 어떤 저장 방식을 쓰는지는 `docker info | grep -A2 'Storage Driver'`로 확인한다.

### 1.3 쓰기 레이어 용량 제한은 검증하고 믿는다

**한 줄 요약:** 레거시 overlay2의 `--storage-opt size=`는 containerd 이미지 스토어에서 조용히 무시될 수 있다.

Docker Engine 29부터 신규 설치의 기본 저장소가 containerd 이미지 스토어로 바뀌었다(기존 설치는 자동 전환되지 않음). 이 전환에서 알아 둘 점은 다음과 같다.

- 컨테이너별 쓰기 레이어 크기를 제한하는 `--storage-opt size=<한도>`를 받아 주면서도 실제로는 한도를 강제하지 않는 사례가 보고되어 있다. 용량 제한을 운영 정책으로 쓰고 있었다면 전환 후 실제로 걸리는지 재검증한다.
- 압축본과 풀린 본을 함께 보관해 디스크 점유가 늘 수 있다.
- `userns-remap`과의 조합이 아직 완전하지 않을 수 있다.

`docker system df`(상세는 `-v`)로 이미지/컨테이너/볼륨/빌드 캐시별 사용량과 RECLAIMABLE 비율을 본다. 어차피 쓰기 레이어를 많이 쓰는 서버라면 그 데이터는 쓰기 레이어가 아니라 마운트로 빼는 쪽이 맞다.

## 코어 2. 세 가지 마운트는 저장 위치와 생명주기가 다르다

### 2.1 비교표

**한 줄 요약:** 어디에 저장되고(위치), 언제까지 사는가(생명주기)가 선택 기준이다.

| 방식 | 저장 위치 | 생명주기 | 주 용도 |
|---|---|---|---|
| named volume | `/var/lib/docker/volumes/<이름>/_data` (또는 볼륨 드라이버가 관리하는 위치) | 명시적으로 `docker volume rm`할 때까지 유지, 컨테이너 삭제와 무관 | 데이터베이스 파일 등 컨테이너와 독립적으로 지속돼야 하는 데이터 |
| bind mount | 호스트의 임의 경로(사용자가 직접 지정) | 호스트 파일시스템의 생명주기를 그대로 따름 | 소스 코드 실시간 반영, 호스트 설정 파일 주입 |
| tmpfs mount | 호스트 디스크가 아닌 메모리 | 컨테이너가 멈추면 즉시 소멸 | 비밀값 등 디스크에 남기면 안 되는 임시 데이터 |

### 2.2 직접 비교해 보기

**한 줄 요약:** 한 컨테이너에 세 방식을 모두 붙여 보면 차이가 눈으로 확인된다.

```bash
docker volume create demo-vol
docker run --rm \
  -v demo-vol:/data/volume \
  -v "$(pwd)":/data/bind \
  --tmpfs /data/tmpfs \
  alpine sh -c 'echo vol > /data/volume/f.txt; echo bind > /data/bind/f.txt; echo tmp > /data/tmpfs/f.txt'

ls "$(docker volume inspect demo-vol --format '{{.Mountpoint}}')"   # f.txt 남아 있음
ls ./f.txt                                                           # bind 로 쓴 파일 남아 있음
# tmpfs 에 쓴 파일은 컨테이너가 --rm 으로 삭제되어 어디에도 없다
```

결과는 이렇다. named volume으로 쓴 파일은 볼륨 마운트포인트에 남고, bind mount로 쓴 파일은 현재 작업 디렉터리에 남으며, tmpfs에 쓴 파일은 컨테이너 종료와 동시에 완전히 사라진다. 서버 코드는 `/data/volume`, `/data/bind`, `/data/tmpfs`를 똑같이 `write()`할 뿐이다. 차이는 전부 마운트 쪽에서 난다. 마운트의 커널 쪽 원리는 [1부 파일시스템과 I/O](../1부-리눅스-OS-구성-요소/05-파일시스템과-IO.md)의 마운트 절과 같다.

## 코어 3. named volume은 드라이버 뒤로 저장소를 숨긴다

### 3.1 볼륨의 생명주기는 Docker가 관리한다

**한 줄 요약:** named volume은 Docker(또는 containerd)가 생명주기를 직접 관리하는 저장 단위다.

기본 `local` 드라이버는 볼륨 데이터를 호스트 디스크(`/var/lib/docker/volumes/<이름>/_data`)에 그대로 저장한다. 컨테이너를 삭제해도 볼륨은 남고, 새 컨테이너가 같은 이름의 볼륨을 `-v <이름>:<경로>`로 붙이면 이전 데이터가 그대로 보인다. 지우려면 명시적으로 `docker volume rm`을 해야 한다. "컨테이너는 소모품, 데이터는 볼륨"이라는 운영 모델의 기반이다.

### 3.2 볼륨 드라이버 플러그인

**한 줄 요약:** 드라이버가 `Create`/`Mount`/`Path`/`Unmount`/`Remove`를 구현하면 NFS나 클라우드 스토리지도 같은 `-v` 문법으로 붙는다.

여러 호스트에서 같은 데이터를 공유하거나 클라우드 블록 스토리지에 볼륨을 얹어야 할 때는 볼륨 드라이버 플러그인을 설치해 쓴다. Docker의 볼륨 드라이버 인터페이스는 `Create`, `Mount`, `Path`, `Unmount`, `Remove` 같은 표준 동작을 플러그인이 구현하도록 정의한다. 설치는 `docker plugin install`, 사용은 `docker volume create --driver <플러그인 이름>`이다.

```bash
docker plugin install --grant-all-permissions vieux/sshfs
docker volume create --driver vieux/sshfs \
  --opt sshcmd=user@remote-host:/data \
  --opt password=... \
  remote-vol
```

컨테이너 입장에서는 여전히 평범한 `-v remote-vol:/data`지만 실제 데이터는 원격 호스트나 외부 스토리지에 놓인다. 어떤 드라이버를 쓰든 **컨테이너는 마운트 지점만 알고, 뒤에 실제 데이터가 어디 있는지는 드라이버가 책임진다**는 원칙은 같다. 이 원칙은 쿠버네티스의 PV/PVC와 CSI에서 그대로 확장된다([29장](../3부-쿠버네티스-구성-요소/29-스토리지.md)).

## 코어 4. bind mount와 tmpfs는 각자의 함정이 있다

### 4.1 bind mount: 호스트 경로를 그대로 노출

**한 줄 요약:** Docker는 bind mount의 내용 생명주기에 관여하지 않고, 호스트의 권한·SELinux 라벨 문제를 그대로 물려받는다.

bind mount는 호스트의 특정 경로를 컨테이너 안에 그대로 노출한다. 소스 코드 실시간 반영, 호스트 설정 파일 주입에 적합하다. 호스트 쪽 파일의 소유자·권한·SELinux 라벨이 컨테이너 안에서 그대로 적용되므로, "호스트에서는 되는데 컨테이너에서는 권한 거부"가 이 방식에서 흔하다. 또 컨테이너 설정이 호스트의 특정 디렉터리 구조에 의존하게 되어 이식성이 떨어진다. 이런 이유로 운영 데이터는 named volume, 개발·설정 주입은 bind mount가 일반적인 구분이다.

### 4.2 tmpfs: 디스크에 흔적을 남기지 않는다

**한 줄 요약:** tmpfs는 메모리 기반이라 컨테이너가 종료되는 순간 내용이 완전히 사라지고, 그 성질이 곧 용도다.

tmpfs는 애초에 디스크에 쓰이지 않으므로 런타임에만 필요한 토큰 파일처럼 짧게 다뤄야 하는 민감 정보를 두기에 맞다. 반대로 영속이 필요한 데이터를 tmpfs에 두면 재시작 때마다 비어 버린다. `--tmpfs <경로>`로 붙인다.

### 4.3 선택 기준 한눈에

**한 줄 요약:** 재시작에도 살아야 하면 volume 또는 bind, 흔적을 남기면 안 되면 tmpfs.

| 데이터 | 선택 | 이유 |
|---|---|---|
| 게임 DB 파일, 영속 상태 | named volume | 컨테이너와 독립, Docker가 생명주기 관리, 드라이버로 외부 스토리지 연결 가능 |
| 개발 중 소스·설정 파일 | bind mount | 호스트에서 수정하면 즉시 반영 |
| 런타임 토큰·임시 비밀값 | tmpfs | 디스크에 남지 않음 |
| 그 외 모두 | 쓰기 레이어(기본) | 컨테이너와 함께 사라져도 되는 데이터에만 |

### 시나리오로 확인하기

1. **상황:** 게임 서버를 새 버전 이미지로 교체 배포했더니 이전 컨테이너가 `/var/game/dump`에 쌓던 덤프 파일이 모두 사라졌다.
   **질문:** 원인과 대응은?

   <details markdown="1"><summary>답 확인</summary>

   덤프는 컨테이너의 쓰기 레이어(upperdir)에 쓰였고, 쓰기 레이어는 컨테이너 삭제와 함께 사라진다. 이미지 레이어는 읽기 전용이라 변경이 거기 저장되지도 않는다. 덤프 경로에 named volume(`-v dump-vol:/var/game/dump`)을 붙이면 컨테이너 교체와 무관하게 유지된다. 호스트에서 바로 접근해야 한다면 bind mount도 가능하다. → 코어 1, 코어 2

   </details>

2. **상황:** 개발 중에 서버 설정 파일을 자주 고치는데, 고칠 때마다 이미지를 다시 빌드하고 있다.
   **질문:** 더 나은 방법은?

   <details markdown="1"><summary>답 확인</summary>

   설정 파일(또는 디렉터리)을 bind mount로 호스트 경로에서 컨테이너에 노출한다. 호스트에서 수정하면 즉시 반영된다. 단 호스트 쪽 권한·SELinux 라벨 문제를 그대로 물려받고 호스트 디렉터리 구조에 의존한다는 점을 감수한다. → 코어 4

   </details>

3. **상황:** 런타임에만 필요한 인증 토큰을 파일로 컨테이너에 전달해야 하는데, 디스크에 남기고 싶지 않다.
   **질문:** 어떤 마운트를 쓰나?

   <details markdown="1"><summary>답 확인</summary>

   tmpfs mount다. 호스트 디스크가 아닌 메모리에만 있어 컨테이너가 멈추면 즉시 소멸한다. 짧게 다뤄야 하는 민감 정보용으로 쓰이는 이유다. 재시작하면 비어 있으므로 시작 시 다시 주입해야 한다. → 코어 2, 코어 4

   </details>

4. **상황:** 운영 정책상 컨테이너별 쓰기 레이어에 `--storage-opt size=10G` 제한을 걸어 왔다. 새 서버를 Docker 29로 설치했더니 용량이 제한 없이 늘어난다.
   **질문:** 무엇을 의심하나?

   <details markdown="1"><summary>답 확인</summary>

   Docker Engine 29 신규 설치는 containerd 이미지 스토어가 기본인데, 이 경로는 `--storage-opt size=`를 받아 주면서도 실제로 한도를 강제하지 않는 사례가 보고되어 있다. 프로젝트 쿼터 지원 검증 로직이 그래프 드라이버 경로와 다르기 때문이다. 전환 후 실제로 제한이 걸리는지 재검증하고, 근본적으로는 대용량 쓰기 데이터를 볼륨으로 빼서 용량을 별도 관리한다. → 코어 1

   </details>

### 2. 인출 질문

1. 컨테이너 안에서 만든 파일은 호스트 어디에 어떤 형태로 있나? 컨테이너를 지우면?

   <details markdown="1"><summary>답 확인</summary>

   overlay2 그래프 드라이버라면 `/var/lib/docker/overlay2/<id>/diff` 아래의 평범한 파일이다(containerd 이미지 스토어는 `/var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/` 아래). `docker inspect`의 `GraphDriver`에서 `UpperDir`로 확인한다. 컨테이너를 지우면 쓰기 레이어도 함께 사라지고, 이미지 레이어는 영향받지 않는다. → 코어 1

   </details>

2. 세 가지 마운트 방식의 저장 위치와 생명주기를 각각 말해 보라.

   <details markdown="1"><summary>답 확인</summary>

   named volume: `/var/lib/docker/volumes/<이름>/_data`(또는 드라이버 관리 위치), `docker volume rm`까지 유지. bind mount: 호스트의 사용자 지정 경로, 호스트 파일시스템의 생명주기를 따름. tmpfs: 메모리, 컨테이너가 멈추면 즉시 소멸. → 코어 2

   </details>

3. 용도별로 어떤 방식을 고르나? (DB 파일, 소스 실시간 반영, 임시 토큰)

   <details markdown="1"><summary>답 확인</summary>

   DB 파일 등 컨테이너와 독립적으로 지속돼야 하는 데이터는 named volume, 소스 코드 실시간 반영·호스트 설정 파일 주입은 bind mount, 디스크에 남기면 안 되는 임시 비밀값은 tmpfs. → 코어 2, 코어 4

   </details>

4. 볼륨 드라이버 플러그인은 무엇을 가능하게 하고 컨테이너는 무엇을 아는가?

   <details markdown="1"><summary>답 확인</summary>

   `Create`/`Mount`/`Path`/`Unmount`/`Remove` 표준 동작을 구현한 플러그인으로 NFS, 클라우드 블록 스토리지 등 외부 스토리지에 볼륨을 얹을 수 있다. 컨테이너는 여전히 평범한 `-v remote-vol:/data` 마운트 지점만 알고, 실제 데이터 위치는 드라이버가 책임진다. → 코어 3

   </details>

5. bind mount가 가진 대표적인 함정은?

   <details markdown="1"><summary>답 확인</summary>

   Docker가 내용의 생명주기에 관여하지 않고, 호스트 쪽 권한·SELinux 라벨 문제를 그대로 물려받는다. 호스트 디렉터리 구조에 의존해 이식성도 떨어진다. → 코어 4

   </details>

6. 컨테이너가 파일을 수정/삭제할 때 이미지 레이어는 어떻게 되나?

   <details markdown="1"><summary>답 확인</summary>

   이미지 레이어(lowerdir)는 절대 수정되지 않는다. 수정은 파일을 upperdir로 복사(copy-on-write)한 뒤 복사본을 바꾸고, 삭제는 upperdir에 whiteout 표시를 남긴다. 그래서 같은 이미지의 컨테이너들이 서로 간섭하지 않는다. → 코어 1

   </details>

7. containerd 이미지 스토어로 전환했을 때 쓰기 레이어 용량과 관련해 검증할 것은?

   <details markdown="1"><summary>답 확인</summary>

   `--storage-opt size=` 제한이 조용히 무시되어 실제로 강제되지 않을 수 있으므로 전환 후 재검증한다. 그 외 압축본·풀린 본 보관으로 디스크 사용량이 늘 수 있고 `userns-remap` 호환성도 확인해야 한다. → 코어 1

   </details>

### 3. 기억 고리

- **C++ 유추:** `open()`/`write()`하는 경로 = 마운트 지점 ⚠️ 코드는 같아도 경로 아래가 휘발성 쓰기 레이어면 컨테이너 삭제와 함께 데이터가 사라진다. 기본값이 "영속"이 아니다.
- **C++ 유추:** `/dev/shm` 같은 메모리 파일 = tmpfs mount ⚠️ 컨테이너가 멈추면 내용이 완전히 소멸하므로 재시작 시 다시 채워야 한다.
- **비유:** 쓰기 레이어 = 포스트잇 메모. 책(이미지)에는 못 쓰고 포스트잇에만 쓰며, 책 한 권 버릴 때(컨테이너 삭제) 같이 버려진다. named volume = 별도 서랍(Docker가 관리), bind mount = 내 책상 위 자료를 그대로 보여 주는 창, tmpfs = 화이트보드(전원 끄면 지워짐). ⚠️ 비유가 깨지는 지점: bind mount는 창이라서 컨테이너가 쓴 내용이 곧바로 호스트 파일을 바꾼다.
- **묶음(3의 법칙):** 마운트 3종(volume·bind·tmpfs) / 비교 3축(위치·생명주기·용도) / 이 장 첫머리 질문 3개(사라진 로그·설정 반영·토큰 파일).
- **대칭·순서:** 영속 ↔ 휘발. volume(Docker 관리) ↔ bind(호스트 관리). 디스크 ↔ 메모리(tmpfs).
