# 9장. 네임스페이스

> **🎮 게임 서버 개발자에게** — 같은 머신에서 게임 서버 인스턴스를 여러 개 띄우면 포트가 겹치고, PID를 헷갈리고, 서로의 공유 메모리 키가 충돌한다. 네임스페이스는 이 "전역 자원 충돌"을 커널이 프로세스 그룹별로 **다르게 보여 주는 것**으로 풀어 준다. 새 커널이 생기는 것도, 자원이 복제되는 것도 아니다. 같은 커널에 같은 `getpid()`, `bind()` 시스템 콜을 하는데 **대답을 필터링하는 렌즈**가 하나 끼워질 뿐이다. 이 관점을 잡으면 `docker run --net=host`, 쿠버네티스 Pod의 네트워크 공유, `PID 1` 문제가 모두 한 장의 그림으로 정리된다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 컨테이너 안에서 `ps`를 쳤더니 내 서버가 PID 1로 보이고, `docker stop`을 해도 SIGTERM에 반응하지 않는다.
> - 컨테이너 이미지에 `ip`, `ss`, 셸이 없는데 그 컨테이너의 네트워크 상태를 봐야 한다.
> - 같은 호스트에서 컨테이너 10개가 모두 `0.0.0.0:80`을 바인딩하는데 왜 충돌하지 않는지 설명해야 한다.

## 코어 — 이것만은 100%

> **한 문장:** 네임스페이스는 커널의 전역 자원(PID, 네트워크, 마운트, 호스트명, IPC, UID, cgroup 뷰, 시계)을 프로세스 그룹마다 다르게 "보이게" 하는 커널 기능이며, 컨테이너는 보통 프로세스에 이것을 씌운 것이다.

1. **네임스페이스 = 복제가 아니라 뷰** — 컨테이너 10개도 같은 커널·같은 CPU·같은 물리 NIC를 공유한다. 달라지는 것은 프로세스가 커널에 질의했을 때 보이는 결과뿐이다. `clone()`/`unshare()`/`setns()`에 `CLONE_NEW*` 플래그를 넘겨 만들거나 합류한다.
2. **8종류를 외운다** — Mount, UTS, IPC, PID, Network, User, cgroup, Time. "pid/net/mnt 세 가지뿐"이 아니다. PID 네임스페이스의 첫 프로세스는 PID 1이 되고, PID 1은 좀비 회수와 시그널 처리에서 특별하다.
3. **`/proc/PID/ns/`로 확인하고 `nsenter`로 들어간다** — 대괄호 안 inode 번호가 같으면 같은 네임스페이스이고, `setns()`와 그 CLI 포장인 `nsenter`로 도구 없는 컨테이너 안에 호스트 도구로 진입한다.
4. **Docker 옵션 = "새로 만들지, 공유할지"** — `--net=host`, `--net=container:X`, `--pid=host`, `--ipc=host`, `--userns=`는 모두 "이 네임스페이스는 새로 만들지 말고 지정한 대상과 공유하라"는 지시다. 쿠버네티스 Pod의 네트워크 공유도 같은 원리다.
5. **네임스페이스는 "가시성" 축일 뿐** — 보이는 것만 제한하고, 할 수 있는 일(권한)은 capabilities/seccomp가, 쓸 수 있는 양(자원)은 cgroup이 맡는다. 세 축 중 가장 약한 축이 전체 격리 수준을 정한다.

## C++·TCP 서버 경험에서 출발하기

| 이미 아는 것 (C++/소켓 서버) | 이 장의 개념 | 같은 점 | ⚠️ 다른 점 (유추가 깨지는 곳) |
|---|---|---|---|
| 같은 포트에 두 번째 서버 인스턴스를 `bind()`하면 `EADDRINUSE` | 네트워크 네임스페이스 | 포트 바인딩 공간이 "한 곳"에 있다는 문제를 푼다 | 인스턴스마다 포트를 바꾸는 것이 아니라 **포트 공간 자체를 인스턴스마다 따로** 준다. 인터페이스·라우팅 테이블·방화벽 규칙·소켓·`/proc/net` 통계까지 한 묶음이다 |
| `getpid()`, `kill(pid, sig)`로 프로세스 식별·제어 | PID 네임스페이스 | PID는 커널이 부여하는 번호다 | 프로세스는 네임스페이스 계층마다 **별도 번호**를 받는다. 컨테이너 안에서 1이어도 호스트에서는 다른 번호다 |
| SIGTERM 핸들러를 등록해 graceful shutdown 구현 | PID 1의 시그널 특성 | 핸들러가 있으면 정상 종료할 수 있다 | PID 1은 핸들러를 등록하지 않은 시그널을 커널 기본 동작대로 처리하지 않고 **무시하는 경우가 많다**. 핸들러가 없는 서버가 PID 1이면 SIGTERM에 안 죽는다 |
| 서버 프로세스가 `fork()`한 자식을 `waitpid()`로 회수 | PID 1의 좀비 회수 책임 | 회수하지 않으면 좀비가 쌓인다 | 컨테이너에서는 내 프로세스가 PID 1이라 **좀비 회수 책임까지 맡는다**. 셸 스크립트로 여러 데몬을 띄우면 좀비가 쌓인다 |
| System V 공유 메모리(`shmget`) 키를 인스턴스별로 달리 지정 | IPC 네임스페이스 | 키 충돌을 피한다 | 키를 바꾸는 대신 **키 공간을 분리**한다. 같은 키를 써도 컨테이너끼리 충돌하지 않는다 |
| `fork()`한 자식은 부모의 fd 테이블을 상속 | `clone()` 플래그로 네임스페이스 생성/상속 | 자식이 부모의 환경을 물려받는다 | 상속이 기본이고, **`CLONE_NEW*`를 지정한 항목만 새로 만든다**. Docker 옵션은 이 "새로 만들기/공유하기" 선택이다 |

>

### 이 장에서 배우는 것

- 네임스페이스가 무엇을 하고 무엇을 하지 않는지(복제 vs 뷰)
- 8가지 네임스페이스의 격리 대상과 도입 시점
- PID 네임스페이스와 PID 1의 특수한 책임, 그리고 `--init`
- `/proc/PID/ns/`, `unshare`, `nsenter`, `ip netns`로 직접 확인하고 진입하는 방법
- Docker 옵션이 네임스페이스를 새로 만들거나 공유하는 방식, 그리고 Pod의 pause 컨테이너와의 연결
- 네임스페이스만으로 충분하지 않은 이유

## 코어 1. 네임스페이스 = 복제가 아니라 뷰

### 1.1 네임스페이스란 무엇인가

**한 줄 요약:** 네임스페이스는 커널 전역 자원을 프로세스 그룹별로 다르게 "보이게" 하는 필터이며 자원을 복제하지 않는다.

리눅스 네임스페이스는 커널이 관리하는 전역 자원(프로세스 ID, 네트워크 인터페이스, 마운트 테이블 등)을 프로세스 그룹별로 서로 다르게 보이게 만드는 커널 기능이다. 중요한 것은 가상 머신처럼 자원을 실제로 복제하거나 물리적으로 분할하는 것이 **아니라는** 점이다.

- 같은 물리 서버 위의 컨테이너 10개는 같은 커널, 같은 CPU, 같은 물리 네트워크 인터페이스를 공유한다.
- 달라지는 것은 컨테이너 안 프로세스가 `ps`를 실행했을 때 자기 네임스페이스 안의 프로세스만 보이고, `ip addr`을 실행했을 때 자기 네트워크 네임스페이스 안의 인터페이스만 보인다는 점뿐이다.

원문의 표현으로, 컨테이너는 커널을 공유하는 "보통 프로세스"이고 네임스페이스는 그 프로세스가 커널에 질의할 때 결과를 필터링/치환해 주는 **렌즈**에 가깝다. 그래서 컨테이너는 VM보다 훨씬 가볍게 뜨지만, 커널 자체는 공유하므로 네임스페이스만으로는 완전한 보안 경계가 되지 못한다(코어 5).

### 1.2 만들고 합류하는 시스템 콜

**한 줄 요약:** `clone()`, `unshare()`, `setns()` 세 시스템 콜에 `CLONE_NEW*` 플래그를 넘긴다.

`clone()`, `unshare()`, `setns()` 시스템 콜에 네임스페이스별 플래그(`CLONE_NEWPID`, `CLONE_NEWNET` 등)를 넘기면 새 네임스페이스를 만들거나 기존 네임스페이스에 합류할 수 있다. C++로 `fork()`와 `clone()`을 써 본 경험이 있다면, "새 프로세스를 만들 때 어떤 자원을 부모와 공유할지 플래그로 고른다"는 `clone()`의 성격이 그대로 네임스페이스 생성에도 쓰인다고 보면 된다. 이 호출을 실제로 하는 쪽이 12장의 runc이고, 직접 해 보는 것이 17장이다.

→ [12장 OCI 표준과 런타임](12-OCI-표준과-런타임.md), [17장 컨테이너를 손으로 만들기](17-컨테이너를-손으로-만들기.md)

## 코어 2. 8종류와 PID 1

### 2.1 여덟 가지 네임스페이스

**한 줄 요약:** Mount, UTS, IPC, PID, Network, User, cgroup, Time. 도입 순서대로 외워 두면 목록이 빠지지 않는다.

| 네임스페이스 | 플래그 | 커널 버전 | 격리 대상 |
|---|---|---|---|
| Mount | `CLONE_NEWNS` | 2.4.19 | 마운트 테이블 |
| UTS | `CLONE_NEWUTS` | 2.6.19 | 호스트 이름, NIS 도메인 |
| IPC | `CLONE_NEWIPC` | 2.6.19 | System V IPC, POSIX 메시지 큐 |
| PID | `CLONE_NEWPID` | 2.6.24 | 프로세스 ID 공간 |
| Network | `CLONE_NEWNET` | 2.6.29 전후 | 네트워크 인터페이스, 라우팅, 방화벽 |
| User | `CLONE_NEWUSER` | 3.8 | UID/GID 매핑 |
| cgroup | `CLONE_NEWCGROUP` | 4.6 | cgroup 계층 뷰 |
| Time | `CLONE_NEWTIME` | 5.6 | 부팅 이후 경과 시각 클록 |

커널 버전은 해당 기능이 처음 병합되거나 안정화된 시점 기준이며, 배포판에 따라 백포트 여부가 다르다.

### 2.2 각 네임스페이스가 하는 일

**한 줄 요약:** 컨테이너 안에서 보이는 `hostname`, `eth0`, `/`, PID 1, root(UID 0)는 각각 UTS, Network, Mount, PID, User 네임스페이스 덕분이다.

- **Mount**: 프로세스별로 독립적인 마운트 테이블을 준다. 가장 먼저 도입됐고, 플래그 이름이 `CLONE_NEWNS`("new namespace")인 것은 당시 일반 이름을 그대로 가져다 쓴 탓이라 이후엔 어색해졌다. 컨테이너 안에서 `/`가 호스트 루트가 아니라 **이미지 레이어를 합성한 overlay 파일시스템**으로 보이는 것은 이 네임스페이스와 `pivot_root`(또는 구형 `chroot`)의 조합이다(레이어는 [11장](11-이미지-레이어-overlayfs.md)).
- **UTS**: 호스트 이름과 NIS 도메인 이름을 격리한다. 컨테이너 안 `hostname`이 컨테이너 ID 앞자리(또는 `--hostname` 값)로 보인다. 8종 중 가장 단순하다.
- **IPC**: System V IPC 객체(공유 메모리, 세마포어, 메시지 큐)와 POSIX 메시지 큐를 격리한다. 컨테이너마다 같은 IPC 키를 써도 충돌하지 않는다. System V 공유 메모리에 의존하는 레거시/DB 워크로드를 컨테이너로 쪼갤 때 이 격리 여부가 변수가 된다.
- **Network**: 인터페이스, 라우팅 테이블, iptables/nftables 규칙, 포트 바인딩 공간을 분리한다. 컨테이너는 기본적으로 자기만의 loopback(`lo`)과 가상 이더넷 인터페이스(veth pair의 한쪽 끝)를 갖고, 이것이 컨테이너마다 독립적으로 `0.0.0.0:80`을 바인딩할 수 있는 이유다. 라우팅·방화벽·소켓·`/proc/net` 통계까지 네임스페이스별로 유지되어야 해서 구현이 가장 복잡한 축이다. 이어지는 네트워크 장([16장](16-Docker-네트워크.md))의 근간이다.
- **User**: UID/GID 공간을 격리한다. 컨테이너 안 UID 0(root)을 호스트에서는 비특권 UID(예: 100000)로 매핑할 수 있다. 매핑은 `/proc/[pid]/uid_map`, `/proc/[pid]/gid_map`에 `<네임스페이스 내부 시작 ID> <호스트 시작 ID> <범위>` 형식으로 기록된다. 다른 네임스페이스는 보통 `CAP_SYS_ADMIN` 등 권한이 필요한 반면, 사용자 네임스페이스는 **일반 사용자도 스스로 생성**할 수 있도록 설계되어 있고, 이것이 rootless 컨테이너의 기반이다.
- **cgroup**: 프로세스가 자기 cgroup 계층을 볼 때, 호스트 전체 트리가 아니라 자기 하위 트리를 루트처럼 보게 한다. 없다면 컨테이너 안 `/proc/self/cgroup`이나 `/sys/fs/cgroup`에 호스트의 전체 cgroup 경로가 노출된다. 자원 **제한** 메커니즘은 [10장](10-cgroup.md)이고, 이 네임스페이스는 그것을 **보는 방식**을 격리한다.
- **Time**: 2020년(커널 5.6)에 안정화된 가장 최근 네임스페이스다. monotonic 클록과 boot-time 클록의 오프셋을 네임스페이스별로 달리 줄 수 있어 CRIU 체크포인트/복원이나 uptime 시뮬레이션에 쓰인다. 벽시계 시각(`CLOCK_REALTIME`)을 컨테이너별로 다르게 해 주는 기능은 **아니다**.

### 2.3 PID 네임스페이스와 PID 1

**한 줄 요약:** 새 PID 네임스페이스의 첫 프로세스는 PID 1이고, 호스트에서는 다른 번호이며, PID 1은 좀비 회수와 시그널에서 특별 취급을 받는다.

- 새 PID 네임스페이스에서 처음 실행되는 프로세스는 그 안에서 PID 1을 받는다. 컨테이너 안 `ps -ef`에서 엔트리포인트가 PID 1로 보이는 이유다. 호스트에서 보면 같은 프로세스가 호스트 PID 공간의 다른 번호(보통 두 자리&#126;네 자리)를 가진다.
- PID 네임스페이스는 **중첩**된다. 호스트가 최상위, 그 안에 컨테이너, 컨테이너 안에서 `unshare --pid`를 하면 손자가 생긴다. 프로세스는 자기 네임스페이스와 **조상** 네임스페이스에서는 보이지만 형제나 자식 네임스페이스에서는 보이지 않는다.
- PID 1의 책임은 둘이다. (1) **좀비 프로세스 회수(reap)**. (2) **시그널 기본 동작이 다르다.** 핸들러를 명시적으로 등록하지 않은 시그널을 커널 기본 동작대로 처리하지 않고 무시하는 경우가 많다.
- 그래서 엔트리포인트가 자식 프로세스를 여럿 fork하는 애플리케이션(셸 스크립트로 여러 데몬을 띄우는 경우 등)에서는 좀비가 쌓이는 문제가 흔하다. 대응은 `tini`처럼 최소한의 init 역할만 하는 바이너리를 PID 1로 앞세우는 것이고, Docker는 `docker run --init`으로 이를 켠다.

시그널과 좀비의 일반론은 1부에서 다뤘다.

→ [2장 프로세스](../1부-리눅스-OS-구성-요소/02-프로세스.md), [3장 시그널](../1부-리눅스-OS-구성-요소/03-시그널.md)

## 코어 3. 관찰하고 들어가기

### 3.1 /proc/PID/ns/

**한 줄 요약:** 대괄호 안 inode 번호가 같으면 같은 네임스페이스이고, 이 링크는 열 수 있는 fd라서 `setns()`에 넘길 수 있다.

리눅스는 프로세스가 속한 네임스페이스를 `/proc/[pid]/ns/` 아래 심볼릭 링크로 노출한다.

```bash
ls -l /proc/$$/ns/
```

```
lrwxrwxrwx 1 root root 0 ... cgroup -> 'cgroup:[4026531835]'
lrwxrwxrwx 1 root root 0 ... ipc -> 'ipc:[4026531839]'
lrwxrwxrwx 1 root root 0 ... mnt -> 'mnt:[4026531840]'
lrwxrwxrwx 1 root root 0 ... net -> 'net:[4026531992]'
lrwxrwxrwx 1 root root 0 ... pid -> 'pid:[4026531836]'
lrwxrwxrwx 1 root root 0 ... pid_for_children -> 'pid:[4026531836]'
lrwxrwxrwx 1 root root 0 ... time -> 'time:[4026531834]'
lrwxrwxrwx 1 root root 0 ... time_for_children -> 'time:[4026531834]'
lrwxrwxrwx 1 root root 0 ... user -> 'user:[4026531837]'
lrwxrwxrwx 1 root root 0 ... uts -> 'uts:[4026531838]'
```

- 대괄호 안 숫자는 네임스페이스의 고유 식별자(inode 번호)다. 두 프로세스의 번호를 비교하면 같은 네임스페이스인지 알 수 있다. 예를 들어 `--net=host` 컨테이너의 `net` 번호는 호스트와 같다.
- 이 링크는 읽기용 정보에 그치지 않고 **실제로 열 수 있는 fd**다. 열어서 얻은 fd를 `setns()`에 넘기면 호출한 프로세스가 그 네임스페이스에 합류한다. `nsenter`는 이 메커니즘을 CLI로 감싼 도구다.

### 3.2 unshare, nsenter, ip netns

**한 줄 요약:** `unshare`는 새로 만들고, `nsenter`는 기존 것에 들어가고, `ip netns`는 네트워크 네임스페이스만 단독 관리한다.

```bash
# 새 mount + PID 네임스페이스에서 셸 띄우기
sudo unshare --mount --pid --fork --mount-proc bash

# 새 네임스페이스 안에서 ps: 자기 자신과 극소수 프로세스만 보임
ps -ef
# 확인 포인트: fork한 bash가 PID 1로 보임. --mount-proc 덕분에 /proc가 새 PID
# 네임스페이스 기준으로 다시 마운트되어 ps가 정확한 결과를 보여줌
```

```bash
# 실행 중인 컨테이너의 네임스페이스에 호스트에서 진입
docker run -d --name web nginx:latest
PID=$(docker inspect -f '{{.State.Pid}}' web)

# 컨테이너의 네트워크 네임스페이스에 들어가 인터페이스 확인
sudo nsenter --target $PID --net -- ip addr

# 컨테이너의 마운트 네임스페이스에 들어가 파일시스템 확인
sudo nsenter --target $PID --mount -- ls /
```

`nsenter`는 컨테이너 디버깅에서 대단히 실용적이다. 이미지에 셸이나 디버깅 도구가 전혀 없는 **distroless** 이미지라도, 호스트에 설치된 도구로 그 컨테이너의 네임스페이스 안에 들어가 네트워크나 마운트 상태를 볼 수 있다.

```bash
# Docker와 무관하게 네트워크 네임스페이스만 독립 생성/관리
sudo ip netns add testns
sudo ip netns exec testns ip addr
sudo ip netns list
sudo ip netns delete testns
```

`ip netns`가 만드는 네임스페이스는 `/var/run/netns/` 아래에 이름이 붙어 등록되고, Docker가 만드는 네트워크 네임스페이스는 `/var/run/docker/netns/`(또는 유사 경로) 아래에 따로 관리된다. 즉 두 등록 체계가 같지 않아서 Docker 컨테이너의 네임스페이스는 `ip netns list`에 바로 안 보일 수 있다.

## 코어 4. Docker가 네임스페이스를 조합하는 방식

### 4.1 기본 동작

**한 줄 요약:** `docker run`은 PID, 마운트, UTS, IPC, 네트워크(그리고 조건부로 cgroup)를 새로 만들고, User와 Time은 기본으로 호스트와 공유한다.

- 기본으로 새로 만드는 것: PID, 마운트, UTS, IPC, 네트워크(그리고 조건부로 cgroup).
- 기본으로 만들지 않고 호스트와 공유하는 것: **사용자 네임스페이스**(단 `userns-remap`이 설정되었거나 `--userns=`를 명시하면 새로 생성), **타임 네임스페이스**.

### 4.2 공유 옵션

**한 줄 요약:** 이 옵션들은 모두 "새로 만들지 말고 지정한 대상과 공유하라"는 뜻이다.

```bash
# 네트워크 네임스페이스를 호스트와 공유
docker run --rm --net=host nginx:latest

# 네트워크 네임스페이스를 다른 컨테이너와 공유 (사이드카 패턴의 기반)
docker run -d --name app myapp:latest
docker run --rm --net=container:app busybox ip addr

# PID 네임스페이스를 호스트와 공유 (호스트의 모든 프로세스가 보임, 디버깅용)
docker run --rm --pid=host busybox ps -ef

# IPC 네임스페이스를 호스트(또는 다른 컨테이너)와 공유
docker run --rm --ipc=host busybox ipcs

# 사용자 네임스페이스: 리매핑을 우회하고 호스트 사용자 네임스페이스 사용
docker run --userns=host busybox id
```

`--userns=`는 Docker 버전과 데몬 설정에 따라 값과 기본 동작이 달라질 수 있으므로 운영에 적용하기 전에 사용 중인 버전의 공식 문서로 확인하는 것이 안전하다. 활성화하면 컨테이너 안 root가 호스트에서는 비특권 UID가 되어, 탈출 취약점이 있어도 호스트 root 권한을 바로 얻지 못하는 추가 방어선이 생긴다.

### 4.3 Pod 네트워킹과의 연결

**한 줄 요약:** `--net=container:app`은 쿠버네티스 Pod의 컨테이너들이 네트워크를 공유하는 구조와 같은 원리다.

쿠버네티스 Pod는 **pause 컨테이너**를 먼저 만들어 네트워크 네임스페이스를 생성해 두고, 같은 Pod의 나머지 컨테이너가 모두 그 네임스페이스에 합류한다(`--net=container:pause`와 동등한 방식).

> **[보충]** 네트워크 네임스페이스를 공유하므로 같은 Pod 안 컨테이너들은 같은 인터페이스·포트 공간을 함께 쓴다(26장에서 자세히).

네임스페이스 공유 메커니즘을 알면 Pod 네트워킹의 뿌리가 자연스럽게 이해된다.

→ [26장 쿠버네티스 네트워크 모델과 CNI](../3부-쿠버네티스-구성-요소/26-쿠버네티스-네트워크-모델과-CNI.md)

## 코어 5. 네임스페이스만으로는 부족하다

### 5.1 세 가지 이유

**한 줄 요약:** 커널은 공유되고, "보이는 것"만 제한하며, 자원 사용량은 건드리지 않는다.

1. **커널을 분리하지 않는다.** 호스트와 모든 컨테이너가 같은 커널 코드를 실행하므로, 네임스페이스 처리 로직 자체의 버그 같은 커널 취약점은 네임스페이스 경계를 그대로 넘을 수 있다.
2. **"무엇이 보이는지"만 제한하고 "무엇을 할 수 있는지"는 제한하지 않는다.** 사용자 네임스페이스 없이 컨테이너 안에서 진짜 UID 0으로 돌고 있다면, capability가 있을 때 커널 모듈 로드나 커널 파라미터 조정 같은 위험한 행위를 막는 것은 네임스페이스가 아니라 **capabilities**(root 권한을 잘게 쪼갠 단위)와 **seccomp**(허용된 시스템 콜만 호출하게 하는 필터)의 몫이다.
3. **자원 사용량을 제한하지 않는다.** 한 컨테이너가 호스트 메모리나 CPU를 독점하는 "noisy neighbor"는 [10장 cgroup](10-cgroup.md)의 역할이다. 예로 pids 컨트롤러는 네임스페이스만으로 막을 수 없는 "프로세스 무한 생성"을 자원 관점에서 막는다.

### 5.2 세 축 모델

**한 줄 요약:** 가시성(네임스페이스) / 권한(capabilities·seccomp) / 자원(cgroup) 중 가장 약한 축이 전체 격리 수준이다.

| 축 | 담당 | 한 줄 |
|---|---|---|
| 가시성 | 네임스페이스 | 무엇이 보이는가 |
| 권한 | capabilities, seccomp | 무엇을 할 수 있는가 |
| 자원 | cgroup | 얼마나 쓸 수 있는가 |

"컨테이너가 격리되어 있다"는 말은 세 축이 함께 작동한다는 뜻이다. 하나라도 느슨하면(예: `--privileged`로 capabilities와 seccomp를 사실상 무력화) 나머지 축이 아무리 엄격해도 전체 격리는 가장 약한 축을 따른다. capabilities/seccomp가 OCI 명세에서 어떻게 표현되는지는 [12장](12-OCI-표준과-런타임.md)의 `process` 필드와 이어진다.

## 실무 적용

### 체크리스트

- [ ] 네임스페이스는 자원을 복제하는 것이 아니라 프로세스 그룹별로 다른 "뷰"를 주는 커널 기능이고, 컨테이너는 같은 커널을 공유하는 보통 프로세스임을 설명할 수 있다.
- [ ] 8종(Mount, UTS, IPC, PID, Network, User, cgroup, Time)을 모두 말할 수 있고, `docker run`이 기본으로 새로 만드는 것과 공유하는 것(User, Time)을 구분한다.
- [ ] 내 서버가 컨테이너의 PID 1이 될 때 SIGTERM 핸들러를 등록했는가? 자식 프로세스를 여럿 띄우면 `docker run --init`(tini)을 고려했는가?
- [ ] 두 프로세스가 같은 네임스페이스인지 `/proc/PID/ns/*`의 inode 번호로 비교할 수 있다.
- [ ] 셸·도구가 없는 컨테이너는 `nsenter --target $PID --net -- ...`로 호스트 도구를 써서 들여다본다.
- [ ] `--net=host`, `--pid=host`, `--ipc=host`는 격리를 일부러 푸는 옵션임을 알고, 디버깅 용도 외에는 신중하게 쓴다.
- [ ] 네임스페이스 외에 capabilities/seccomp(권한)와 cgroup(자원)까지 함께 걸어야 격리가 완성된다는 점을 기억한다.

### 시나리오로 확인하기

1. **상황:** 게임 서버를 컨테이너로 옮겼다. 서버는 `SIGTERM` 핸들러를 따로 등록하지 않았고, `docker stop`을 하면 한참 기다린 뒤에야 강제로 종료된다.
   **질문:** 원인과 대응은?

   <details markdown="1"><summary>답 확인</summary>

   컨테이너의 엔트리포인트는 새 PID 네임스페이스의 PID 1이다. PID 1은 핸들러를 명시적으로 등록하지 않은 시그널에 커널 기본 동작을 따르지 않고 무시하는 경우가 많다. 그래서 SIGTERM이 먹히지 않는다. 서버에서 SIGTERM 핸들러를 등록해 graceful shutdown을 구현하거나, `docker run --init`(tini)처럼 최소 init을 PID 1로 앞세운다. 자식을 여럿 fork하는 구조라면 좀비 회수 문제도 함께 해결된다. → 코어 2

   </details>

2. **상황:** 운영 중인 distroless 이미지 컨테이너의 네트워크가 이상하다. 컨테이너에는 `ip`도 `ss`도 셸도 없다.
   **질문:** 어떻게 상태를 확인하나?

   <details markdown="1"><summary>답 확인</summary>

   `PID=$(docker inspect -f '{{.State.Pid}}' <컨테이너>)`로 호스트에서 본 PID를 얻고, `sudo nsenter --target $PID --net -- ip addr`처럼 호스트의 도구를 컨테이너의 네트워크 네임스페이스 안에서 실행한다. 마운트 네임스페이스에 들어가려면 `--mount -- ls /`를 쓴다. → 코어 3

   </details>

3. **상황:** 같은 호스트에서 인스턴스 10개가 모두 80번 포트를 바인딩하는데 충돌이 없다. 동료가 "어떻게 가능하냐"고 묻는다.
   **질문:** 한 문장으로 설명하면?

   <details markdown="1"><summary>답 확인</summary>

   컨테이너마다 별도의 네트워크 네임스페이스(자기만의 `lo`와 veth 한쪽 끝, 라우팅 테이블, 방화벽 규칙, 포트 바인딩 공간)를 가지므로 `0.0.0.0:80`이 네임스페이스마다 따로 존재한다. `--net=host`로 호스트 네임스페이스를 공유하면 이 분리가 사라지고 충돌한다. → 코어 2, 코어 4

   </details>

4. **상황:** 보안 리뷰에서 "컨테이너는 네임스페이스로 격리되어 있으니 안전하다"는 말이 나왔다. 그런데 이 컨테이너는 `--privileged`로 실행 중이다.
   **질문:** 무엇이 문제인가?

   <details markdown="1"><summary>답 확인</summary>

   네임스페이스는 "보이는 것"만 제한할 뿐 "할 수 있는 것(권한)"과 "쓸 수 있는 양(자원)"은 제한하지 않는다. 권한은 capabilities/seccomp가, 자원은 cgroup이 맡는데, `--privileged`는 capabilities와 seccomp를 사실상 무력화한다. 세 축 중 가장 약한 축이 전체 격리 수준을 정하므로 네임스페이스가 엄격해도 안전하다고 할 수 없다. 커널 자체를 공유한다는 점도 그대로다. → 코어 5

   </details>

### 2. 인출 질문

1. 네임스페이스는 VM과 무엇이 다른가?

   <details markdown="1"><summary>답 확인</summary>

   네임스페이스는 자원을 복제하거나 물리적으로 분할하지 않는다. 컨테이너 10개도 같은 커널, 같은 CPU, 같은 물리 NIC를 공유하고, 프로세스가 커널에 질의했을 때 결과를 필터링/치환해 주는 렌즈만 다르다. 그래서 VM보다 가볍게 뜨지만 커널 공유 때문에 네임스페이스만으로는 완전한 보안 경계가 아니다. → 코어 1

   </details>

2. 네임스페이스 8종과 각각이 격리하는 것은?

   <details markdown="1"><summary>답 확인</summary>

   Mount(마운트 테이블), UTS(호스트명·NIS 도메인), IPC(System V IPC·POSIX 메시지 큐), PID(프로세스 ID 공간), Network(인터페이스·라우팅·방화벽·포트), User(UID/GID 매핑), cgroup(cgroup 계층 뷰), Time(monotonic·boot-time 클록 오프셋)이다. → 코어 2

   </details>

3. 컨테이너 안에서 서버 프로세스가 PID 1이면 무엇이 달라지는가?

   <details markdown="1"><summary>답 확인</summary>

   좀비 프로세스를 회수해야 하는 책임이 생기고, 핸들러를 명시적으로 등록하지 않은 시그널을 커널 기본 동작대로 처리하지 않고 무시하는 경우가 많다. 자식을 여럿 띄우는 엔트리포인트(셸 스크립트로 여러 데몬 등)는 좀비가 쌓이기 쉬워서, `tini` 같은 최소 init을 PID 1로 쓰거나 `docker run --init`을 쓴다. → 코어 2

   </details>

4. 컨테이너의 프로세스가 호스트와 같은 네트워크 네임스페이스인지 어떻게 확인하나?

   <details markdown="1"><summary>답 확인</summary>

   `/proc/<pid>/ns/net` 링크(`net:[숫자]`)의 inode 번호를 컨테이너 프로세스와 호스트 프로세스에서 각각 읽어 비교한다. `--net=host`로 실행했다면 번호가 같고, 기본 컨테이너라면 다르다. → 코어 3

   </details>

5. `nsenter`와 `unshare`와 `ip netns`의 차이는?

   <details markdown="1"><summary>답 확인</summary>

   `unshare`는 새 네임스페이스를 만들어 그 안에서 프로그램을 실행하고, `nsenter`는 이미 있는 프로세스의 네임스페이스에 (`setns()`로) 진입하며, `ip netns`는 Docker와 무관하게 네트워크 네임스페이스만 독립적으로 만들고 관리한다. → 코어 3

   </details>

6. Docker의 `--net=container:app`은 쿠버네티스에서 무엇과 같은 원리인가?

   <details markdown="1"><summary>답 확인</summary>

   Pod 안 컨테이너들이 네트워크 네임스페이스를 공유하는 구조다. Pod는 pause 컨테이너가 네트워크 네임스페이스를 먼저 만들고 나머지 컨테이너가 거기에 합류한다(`--net=container:pause`와 동등). → 코어 4

   </details>

7. `docker run`이 기본으로 새로 만들지 않는 네임스페이스는?

   <details markdown="1"><summary>답 확인</summary>

   사용자 네임스페이스(`userns-remap`이나 `--userns=`를 지정하면 새로 만든다)와 타임 네임스페이스다. 이 둘은 호스트와 공유한다. → 코어 4

   </details>

8. 네임스페이스 외에 컨테이너 격리에 필요한 두 축과 그 이유는?

   <details markdown="1"><summary>답 확인</summary>

   권한 축(capabilities, seccomp)과 자원 축(cgroup)이다. 네임스페이스는 보이는 것만 제한하므로 root의 위험한 행위는 capabilities/seccomp가, 메모리·CPU 독점이나 fork bomb은 cgroup이 막아야 한다. `--privileged`처럼 한 축이 느슨하면 전체 격리는 가장 약한 축을 따른다. → 코어 5

   </details>

### 3. 기억 고리

- **C++ 유추:** `clone(CLONE_NEWPID | CLONE_NEWNET ...)` = 부모 환경을 상속하되 지정한 항목만 새로 만드는 `fork` ⚠️ 새로 만드는 것은 자원 자체가 아니라 그 자원을 보는 "뷰"이며, 커널은 하나다.
- **C++ 유추:** 컨테이너 안 PID 1에 SIGTERM 핸들러가 필요하다 = `signal()`/`sigaction()` 등록 ⚠️ 일반 프로세스는 핸들러가 없으면 기본 동작으로 종료되지만, PID 1은 핸들러가 없는 시그널을 무시하는 경우가 많아 결과가 반대다.
- **비유:** 네임스페이스 = 안경(렌즈). 같은 방을 보지만 안경에 따라 보이는 물건이 달라진다. ⚠️ 비유가 깨지는 지점: 안경은 보기만 바꾸지만, 네임스페이스 안의 프로세스는 실제로 그 자원에 접근하므로 권한과 자원 한도는 별도(capabilities/seccomp, cgroup)로 걸어야 한다.
- **비유:** 호텔 객실 호수 = PID 네임스페이스. 1층 로비 기준 번호와 객실 안 내선 번호가 다르다. ⚠️ 비유가 깨지는 지점: 프로세스는 자기 네임스페이스와 조상 네임스페이스에서만 보이는 중첩 구조이며, 호스트에서는 컨테이너 프로세스가 보이지만 컨테이너에서는 호스트 프로세스가 안 보인다.
- **묶음(3의 법칙):** 네임스페이스를 만드는 시스템 콜 3개(`clone`·`unshare`·`setns`) / 격리의 세 축(가시성·권한·자원) / 도구 3개(`unshare`·`nsenter`·`ip netns`).
- **대칭·순서:** `unshare`(새로 만들기) ↔ `nsenter`(들어가기). 도입 순서 Mount(2.4.19) → UTS·IPC(2.6.19) → PID(2.6.24) → Network(2.6.29) → User(3.8) → cgroup(4.6) → Time(5.6).
