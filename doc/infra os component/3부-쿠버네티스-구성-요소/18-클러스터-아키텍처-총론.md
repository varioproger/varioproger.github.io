# 18장. 클러스터 아키텍처 총론

> **🎮 게임 서버 개발자에게** — 쿠버네티스를 "컨테이너를 띄워 주는 도구"로만 보면 장애 때 엉뚱한 곳을 뒤지게 된다. 게임 서버로 치면 이 장은 **로비 서버·매치메이킹·게임 서버 프로세스·DB가 서로 어떤 메시지를 주고받는지 그린 시스템 구성도**다. 다만 구조가 하나 특이하다. 컴포넌트끼리 직접 RPC를 주고받지 않고, **모두가 "공용 상태판(API 서버)"을 읽고 쓰기만** 한다. 서버 코드로 비유하면 모든 모듈이 하나의 공유 상태 DB를 폴링·구독하며 각자 맡은 한 가지 일만 하는 구조다. 이 장은 3부 전체의 지도이고, 19&#126;23장이 이 지도의 칸을 하나씩 확대한다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - `kubectl apply`가 "created"를 찍었는데 Pod가 한참 `Pending`이다. 어느 컴포넌트를 의심해야 할지 모르겠다.
> - 컨트롤 플레인 노드가 하나 죽었다. 이미 떠 있는 게임 서버 Pod는 괜찮은지, 새 Pod는 못 만드는지 판단해야 한다.
> - 고가용성 구성에서 etcd를 3대로 할지 4대로 할지 정해야 한다.

## 코어 — 이것만은 100%

> **한 문장:** 쿠버네티스는 "원하는 상태(spec)"를 API 서버에 저장해 두면, 좁은 책임을 가진 여러 컨트롤러가 현재 상태와의 차이를 반복해서 줄여 나가는 **선언형 조정(reconcile) 시스템**이며, 모든 컴포넌트는 API 서버를 통해서만 서로 협력한다.

1. **선언적 상태 + 레벨 트리거 + 멱등한 조정** — 사용자는 "무엇을 원하는가"만 기록한다. 컨트롤러는 이벤트가 아니라 **현재 상태**를 다시 읽어 `desired`와 `observed`의 차이만큼만 행동하며, 몇 번 실행해도 결과가 같다. 이 덕분에 이벤트를 놓치거나 재시작해도 결국 수렴한다.
2. **컨트롤 플레인 5개 컴포넌트는 책임이 좁다** — apiserver(유일한 관문), etcd(진실의 원천), scheduler(배치 결정만), controller-manager(조정 루프 모음), cloud-controller-manager(클라우드 API 연동). 각자 "하지 않는 일"을 아는 것이 장애 위치 파악의 열쇠다.
3. **모든 화살표는 API 서버를 거친다** — 컴포넌트끼리 직접 통신하지 않고 watch/write만 한다. 그래서 각 컴포넌트를 독립적으로 재시작·교체할 수 있다. 노드 쪽에서는 kubelet이 CRI·CNI·CSI 뒤로 실제 일을 위임한다.
4. **`kubectl apply` 한 번 = 비동기 조정 루프 여러 개** — apply가 반환되는 시점과 컨테이너가 Running이 되는 시점 사이에 Deployment → ReplicaSet → scheduler → kubelet 루프가 순서대로 개입한다.
5. **고가용성은 컴포넌트마다 방식이 다르다** — apiserver는 active-active, scheduler·controller-manager는 리더 선출 active-standby, etcd는 Raft 과반수(쿼럼).

|---|---|---|---|
| 게임 월드 틱 루프: 매 틱 현재 상태를 읽고 목표와 맞추기 | 조정 루프(reconcile) | 주기적으로 "지금 상태"를 보고 차이를 줄인다 | 틱은 한 서버 안의 루프지만, 쿠버네티스는 **서로 모르는 수십 개 루프가 공유 상태를 매개로** 연쇄 반응한다 |

| 마스터-스탠바이 게임 서버(하트비트로 승격) | 리더 선출(Lease) | 활성 하나만 일하고 죽으면 대기가 승격 | apiserver는 반대로 **전부 활성**이다. 상태를 etcd에 위임했기 때문에 가능하다 |

## 코어 1. 선언적 상태 + 레벨 트리거 + 멱등한 조정

### 1.1 세 종류를 구분하라: 오브젝트, 프로그램, 실제 자원

**한 줄 요약:** "Deployment가 Pod를 만든다"의 주어는 Deployment 오브젝트가 아니라 그것을 읽고 일하는 컨트롤러 프로그램이다.

| 종류 | 예 | 실제 의미 |
|---|---|---|
| API 오브젝트 | Deployment, Pod, Service, Node | 클러스터가 저장·조회하는 구조화된 기록 |
| 동작하는 프로그램 | API Server, scheduler, kubelet, controller | 오브젝트를 읽고 판단하거나 실행을 요청하는 프로세스 |
| 실제 자원 | Linux 프로세스, EC2, IP, 디스크, ALB | 실행·통신·저장이 일어나는 대상 |

Node 오브젝트는 서버 머신 자체가 아니라 그 노드의 주소·용량·상태를 담은 **기록**이다. 머신이 멈춰도 Node 오브젝트는 남을 수 있고, Pod 오브젝트도 컨테이너가 시작되기 전에 존재할 수 있다. "설정은 맞는데 아무것도 안 생긴다"는 상황은 이 셋의 구분으로 설명된다. (C++로 치면 `struct` 레코드, 그 레코드를 처리하는 스레드, 실제 소켓·메모리가 서로 다른 것과 같다.)

### 1.2 desired, observed, reconcile

**한 줄 요약:** 컨트롤러는 목표를 직접 "만들어내지" 않고, 차이를 줄이는 한 걸음을 반복한다.

```
desired state  (spec)     : 사용자가 API 서버에 기록한 "원하는 결과"
observed state (status)   : 클러스터에서 현재 실제로 관찰되는 상태
reconcile(desired, observed) → action
                             : 두 상태의 차이를 관찰해 좁히는 방향의 조치
```

명령형(`docker run`)은 현재 상태를 모른 채 동작을 실행하므로 다시 실행하면 중복 컨테이너가 생긴다. 쿠버네티스는 "무엇을 원하는가"만 기술하고, 어떻게 만들지는 시스템이 정한다. ReplicaSet 컨트롤러가 "Pod가 2개 부족하다"를 보고 만들다가 일부만 성공해도 상관없다. 다음 조정 주기에 다시 관찰하고 다시 시도한다.

수렴이 성립하는 조건은 세 가지다.

```
① 조치가 항상 "차이를 줄이는 방향"이어야 한다 (발산하지 않음)
② 외부 조건이 고정되면 유한 스텝 안에 오차가 0에 도달해야 한다
③ 조정 도중 desired state가 다시 바뀌면, 새 목표를 향해 다시 수렴을 시작한다
```

실제 컨트롤러는 **매 조정마다 전체 상태를 다시 계산**하고 그 차이만큼만 행동한다. "지난번에 무엇을 했는지"를 기억하지 않는다.

### 1.3 레벨 트리거 vs 엣지 트리거

**한 줄 요약:** 이벤트는 "다시 봐라"는 신호일 뿐이고, 판단은 항상 최신 상태를 읽어서 한다.

```
엣지 트리거: state_t-1 → event → action        (event 유실 시 action 없음)
레벨 트리거: state_t   → diff(desired, state_t) → action  (항상 재계산 가능)
```

엣지 트리거는 `Pod 삭제됨` 같은 이벤트 자체에 반응한다. 네트워크 단절, 컨트롤러 재시작, 큐 오버플로로 이벤트 하나를 놓치면 그 조치는 영원히 실행되지 않는다. 레벨 트리거는 "Pod가 3개 있어야 하는데 지금 2개다"처럼 현재 값에 반응하므로, 이벤트를 몇 개 놓쳐도 다음 조정에서 오차가 드러나 교정된다. **쿠버네티스의 모든 내장 컨트롤러는 레벨 트리거로 설계되어 있다.**

> ⚠️ epoll의 LT/ET와 용어는 같지만 층위가 다르다. epoll은 "fd가 준비됐다는 통지를 한 번만 주느냐 계속 주느냐"이고, 여기서는 "시스템 설계가 이벤트 이력에 의존하느냐 현재 상태에 의존하느냐"다. 그래도 "ET로 한 번 놓치면 영영 못 읽는다"는 위험의 구조는 닮았다.

### 1.4 멱등성

**한 줄 요약:** "하나 더 만들어라"가 아니라 "3개여야 하는데 2개이니 1개 만들어라"로 짠다.

조정 함수는 같은 입력으로 여러 번 호출돼도 결과가 같아야 한다. 레벨 트리거에서는 조정이 몇 번 실행될지 예측할 수 없기 때문이다. watch 이벤트 중복, 컨트롤러 재시작 후 전체 재순회, 주기적 재동기화(resync)가 겹칠 수 있다. "항상 Pod를 하나 추가로 만든다" 같은 함수는 호출 횟수만큼 부작용이 쌓여 발산한다. 절대 목표와 비교해 차이만큼만 행동하면 중복 실행돼도 이미 3개이므로 아무 일도 일어나지 않는다.

```
선언적 API (spec에 원하는 상태 기록)
   → 레벨 트리거 (이벤트가 아니라 "현재 상태"로 판단)
   → 멱등한 조정 함수 (몇 번 실행되어도 같은 결과)
   → 수렴 (유한 스텝 안에 desired == observed)
```

이 네 가지가 맞물려야 "컨트롤러가 죽었다 살아나도, 이벤트를 놓쳐도 결국 올바른 상태로 돌아온다"는 신뢰성 모델이 성립한다.

### 1.5 오브젝트의 소유·선택·참조

**한 줄 요약:** 삭제가 전파되는 것은 "소유" 관계뿐이고, "선택"과 "참조"는 지워도 상대가 남는다.

| 관계 | 예 | 변경 시 생기는 일 |
|---|---|---|
| 소유 | Deployment → ReplicaSet → Pod의 `ownerReferences` | 삭제 전파 정책에 따라 종속 오브젝트 정리 |
| 선택 | Service selector → label이 일치하는 Pod | 대상 목록을 다시 계산한다. Pod 소유권을 얻는 것은 아니다 |
| 참조 | Pod → PVC, ConfigMap, ServiceAccount | 지정한 오브젝트를 사용한다. 함께 삭제되지는 않는다 |

Pod를 지워도 소유 ReplicaSet이 남으면 다시 만들어진다. Service를 지워도 Pod가 안 지워지는 것은 소유 관계가 아니기 때문이다. `finalizers`는 삭제 전에 외부 정리를 끝내도록 붙이는 장치라, `deletionTimestamp`가 찍혔는데 finalizer가 남아 있으면 오브젝트가 계속 보인다. 원인 확인 없이 finalizer부터 제거하면 외부 자원이 남을 수 있다(22장에서 다시 다룬다).

수정 추적용 필드도 구분해 둔다. 서버가 기본값과 UID를 채우므로 로컬 YAML과 조회 결과는 다르다. 변경 추적에는 `resourceVersion`(클라이언트가 시간값처럼 계산해서는 안 된다), 의도 변경에는 `generation`, 컨트롤러가 어디까지 처리했는지는 `status.observedGeneration`을 본다.

## 코어 2. 컨트롤 플레인 5개 컴포넌트와 "하지 않는 일"

### 2.1 컴포넌트 지도

**한 줄 요약:** 컨트롤 플레인은 클러스터의 "판단"을 맡고, 각 컴포넌트의 책임 경계는 의도적으로 좁다.

```
kube-apiserver            모든 요청의 단일 관문, 유일한 etcd 접근자
etcd                      상태 저장소 (진실의 원천)
kube-scheduler            Pod의 노드 배치 "결정"만
kube-controller-manager   수십 개 조정 루프의 집합
cloud-controller-manager  클라우드 API 연동 전용
```

### 2.2 각 컴포넌트의 책임과 하지 않는 일

**한 줄 요약:** 장애 때 로그를 볼 곳은 "누가 무엇을 하지 않는가"를 알아야 정해진다.

| 컴포넌트 | 책임 | 하지 않는 일 |
|---|---|---|
| kube-apiserver | 모든 상태 변경의 유일한 진입점. 인증·인가·어드미션·버전 변환·검증 후 etcd에 기록, watch로 변화 통지 | 스케줄링 결정(`spec.nodeName`이 빈 채로 저장 허용), 조정(종속 오브젝트를 스스로 만들지 않음), etcd 이외의 저장 로직. 진짜 상태는 전적으로 etcd에 있고 watch cache는 최적화일 뿐 |
| etcd | 유일한 진실의 원천. Raft로 복제 | 쿠버네티스 오브젝트를 이해하지 않음(범용 키-값 저장소). RBAC 같은 개념이 없고 접근 제어는 mTLS 인증서 수준 |
| kube-scheduler | `nodeName`이 없는 Pod를 감시하다 최적 노드를 찾아 Binding 요청 | Pod를 직접 실행하지 않음(kubelet의 일), 배치 후 상태 감시 안 함, 실행 중 리소스 초과 강제 안 함(kubelet과 커널의 몫) |
| kube-controller-manager | 수십 개 컨트롤러를 하나의 프로세스 안에서 각각 별도 고루틴으로 구동 | API 서버 대체 안 함(etcd 직접 접근 없이 항상 API 서버 경유), 스케줄링 안 함, 컨트롤러끼리 서로 존재를 모름 |
| cloud-controller-manager | 노드 정보 보강, LoadBalancer Service의 실제 클라우드 LB 생성, 라우팅 테이블 설정 | 클라우드와 무관한 컨트롤러 로직 없음. 온프레미스·kind에는 없거나 최소 기능 |

연쇄 반응(Deployment → ReplicaSet → Pod)은 각 컨트롤러가 자기 담당 범위에서 반응한 결과가 이어진 것이지, 하나의 통합된 로직이 아니다.

### 2.3 노드 컴포넌트 지도

**한 줄 요약:** 컨트롤 플레인이 "무엇을 할지" 정하면 노드 컴포넌트가 실제로 일으킨다. kubelet은 다시 표준 인터페이스 뒤로 위임한다.

```
워커 노드
  kubelet         노드의 에이전트, Pod 생명주기의 총괄자
    ├─ CRI ──→ 컨테이너 런타임(containerd 등) — 컨테이너 실행
    ├─ CNI ──→ 네트워크 플러그인 — Pod 네트워크 연결
    ├─ CSI ──→ 스토리지 플러그인 — 볼륨 attach/mount
    └─ 디바이스 플러그인 ──→ GPU 등 특수 하드웨어 노출
  kube-proxy      Service 가상 IP → Pod IP 변환 규칙 관리
```

| 컴포넌트 | 책임 | 하지 않는 일 |
|---|---|---|
| kubelet | 배정된 Pod 명세와 실제 컨테이너 상태를 지속 비교·조정(조정 루프의 노드 버전), CRI로 런타임에 지시, 상태 보고 | 컨테이너를 직접 실행하지 않음, Pod 간 네트워크를 직접 구성하지 않음(CNI에 위임), Service 라우팅 안 함, 다른 노드를 알지 못함 |
| kube-proxy | Service/EndpointSlice를 watch해 iptables/IPVS 규칙을 갱신, ClusterIP 트래픽을 Pod로 전달 | DNS 해석 안 함(CoreDNS), L7 라우팅 안 함(L3/L4만), 일부 CNI(Cilium eBPF 모드)에서는 아예 없을 수 있음 |
| 컨테이너 런타임 | CRI 규격 구현. 컨테이너 생성·이미지 pull·네임스페이스/cgroup 설정 | 쿠버네티스 오브젝트를 모름(`PodSandbox`, `Container`, `Image` 같은 런타임 개념만 앎), 네트워크 인터페이스는 CNI가 넣음 |
| CNI 플러그인 | Pod 네트워크 네임스페이스에 인터페이스를 만들고 IP 할당, 라우팅/오버레이 설정 | Service 개념을 모름(Pod 대 Pod 연결만) |
| CSI / 디바이스 플러그인 | 외부 스토리지 볼륨의 attach/mount 위임 / GPU 등 특수 자원을 kubelet에 노출 | (kubelet이 직접 하지 않고 표준 인터페이스 뒤로 위임하는 설계의 연장) |

2부에서 배운 containerd·runc·네임스페이스·cgroup이 바로 이 "컨테이너 런타임" 칸의 내부다([13장 Docker 아키텍처](../2부-컨테이너-커널-기능과-Docker/13-Docker-아키텍처.md), [17장 컨테이너를 손으로 만들기](../2부-컨테이너-커널-기능과-Docker/17-컨테이너를-손으로-만들기.md)). kubelet과 CRI는 [23장](23-kubelet과-CRI.md)에서 확대한다.

## 코어 3. 모든 화살표는 API 서버를 거친다

### 3.1 apply 이후 ①&#126;⑱ 여정

**한 줄 요약:** `kubectl apply`가 반환된 뒤 최소 4개의 조정 루프가 비동기로 이어진다.

3개 레플리카의 nginx Deployment를 `kubectl apply -f deployment.yaml`로 만드는 순간부터의 경로다.

```
[kubectl]
   │ ① HTTP POST (인증서/토큰 첨부)
[kube-apiserver]
   │ ② 인증 → 인가 → 어드미션 → 버전 변환 → 스키마 검증
   │ ③ etcd에 Deployment 오브젝트 기록
[etcd] ── Raft 합의 → 커밋 완료 응답 ──▶ [kube-apiserver] ──▶ [kubectl] "created"

   (이 시점에서 apply 명령은 이미 반환된다. 아래는 비동기로 이어진다)

[controller-manager] Deployment 컨트롤러
   │ ④ watch로 새 Deployment 감지  ⑤ "ReplicaSet이 없다" → ReplicaSet 생성 요청
[controller-manager] ReplicaSet 컨트롤러
   │ ⑥ watch로 새 ReplicaSet 감지  ⑦ "Pod가 0개인데 3개여야" → Pod 3개 생성 요청
   │   (저장된 Pod는 아직 spec.nodeName 없음)
[kube-scheduler]
   │ ⑧ watch로 nodeName 빈 Pod 3개 감지
   │ ⑨ Filter(불가능 노드 제외) → Score(순위)  ⑩ 최적 노드 선정 → Binding 생성 요청
   │   (Pod.spec.nodeName 갱신)
[kubelet] (배정된 노드)
   │ ⑪ watch로 "내 노드에 배정된 새 Pod" 감지  ⑫ PodSandbox 생성 요청 (CRI)
[컨테이너 런타임] ⑬ 네트워크 네임스페이스 생성
[CNI 플러그인]    ⑭ 인터페이스 생성, IP 할당, 라우팅 설정
[컨테이너 런타임] ⑮ 이미지 pull → 컨테이너 프로세스 시작
[kubelet] ⑯ readiness/liveness 확인 → Pod.status 갱신 (apiserver → etcd, Running)
[controller-manager] EndpointSlice 컨트롤러 ⑰ Ready Pod 감지 → EndpointSlice 갱신
[kube-proxy] (모든 노드) ⑱ EndpointSlice 변경 감지 → iptables/IPVS 규칙 갱신
```

### 3.2 이 여정에서 짚을 세 가지

**한 줄 요약:** 화살표는 모두 API 서버로, 성공 반환은 앱 정상이 아니며, 전체를 아는 컴포넌트는 없다.

1. **모든 화살표는 결국 API 서버를 거친다.** 스케줄러가 컨트롤러 매니저에 말을 걸지도, kubelet이 스케줄러에게 직접 통보받지도 않는다. 오직 watch/write로 통신하며, 그래서 각 컴포넌트를 독립적으로 재시작·교체할 수 있다.
2. **apply 반환 시점과 Running 시점 사이에는 간극이 있다.** 이 사이 Deployment, ReplicaSet, 스케줄러, kubelet 루프가 순차 개입하고, 각각 독립적으로 실패하고 재시도된다. apply 성공은 "오브젝트가 수락됨"일 뿐 이미지 다운로드·IP 할당·볼륨 연결·앱 초기화는 이후에 실패할 수 있다. 어드미션 웹훅이 응답하지 않으면 새 배포 자체가 막히기도 한다.
3. **"Deployment 전체를 이해하는 단일 컴포넌트"는 없다.** Deployment 컨트롤러는 ReplicaSet만, ReplicaSet 컨트롤러는 Pod만, 스케줄러는 배치만, kubelet은 자기 노드의 컨테이너만 안다. 전체 그림은 좁은 책임들의 합성으로만 존재한다.

### 3.3 컨트롤 플레인이 멈추면 무엇이 멈추나

**한 줄 요약:** 관리 API가 잠시 죽어도 이미 실행 중인 컨테이너와 기존 네트워크 규칙은 당장 사라지지 않는다.

Control Plane을 하나의 프로그램으로 생각하면 장애를 잘못 해석한다. API 서버가 응답해도 특정 컨트롤러가 멈춰 있으면 그 컨트롤러가 맡은 조정만 진행되지 않는다. 반대로 관리 API에 잠시 접근할 수 없어도 실행 중인 컨테이너와 기존 규칙은 유지되고, 영향을 받는 것은 새 배포·배치·대상 갱신이다.

> 게임 서버 감각: 매치 서버가 죽어도 이미 진행 중인 방(게임 서버 프로세스)은 계속 돌지만 새 방은 못 만드는 것과 같다. ⚠️ 다만 노드 장애 같은 일이 동시에 터지면 복구를 해 줄 루프가 멈춰 있다는 점이 다르다.

## 코어 4. 고가용성: 리더 선출, 쿼럼, 토폴로지

### 4.1 리더 선출과 active-active

**한 줄 요약:** scheduler·controller-manager는 한 번에 하나만 활성(Lease 보유), apiserver는 전부 활성이다.

`kube-scheduler`와 `kube-controller-manager`는 보통 3개 인스턴스를 띄우되 **하나만 active, 나머지는 standby**다. 활성이 죽으면 대기 중 하나가 Lease 오브젝트를 얻어 승격한다.

```
kube-scheduler #1 (active)   ── Lease 보유 중, 15초마다 갱신
kube-scheduler #2 (standby)  ── Lease 감시 중
kube-scheduler #3 (standby)  ── Lease 감시 중
```

`kube-apiserver`는 다르다. 여러 인스턴스가 **모두 동시에 요청을 처리한다**(active-active). 자체 상태를 갖지 않고 etcd에 위임하기 때문에 충돌하지 않으며, 앞단 로드밸런서로 트래픽을 분산한다. 리더 선출의 세부는 [22장](22-컨트롤러-매니저.md)에서 다룬다.

### 4.2 etcd 쿼럼 표

**한 줄 요약:** 노드는 홀수로, 과반수 `(N/2)+1`이 살아 있어야 하고, 짝수로 늘리는 것은 이득이 없다.

| 노드 수 | 쿼럼 | 허용 장애 수 |
|---|---|---|
| 1 | 1 | 0 |
| 3 | 2 | 1 |
| 5 | 3 | 2 |
| 7 | 4 | 3 |

4노드는 3노드보다 쓰기 지연이 늘어나는데 허용 장애 수는 여전히 1이다(쿼럼이 3으로 늘기 때문). 실무에서는 3 또는 5노드가 표준이다. 근거인 Raft는 [20장](20-etcd.md)에서 다룬다.

### 4.3 stacked vs external etcd

**한 줄 요약:** stacked는 단순하고 노드가 적게 들고, external은 컨트롤 플레인 장애와 etcd를 분리한다.

```
[stacked etcd]                    [external etcd]
control-plane-1                   control-plane-1        etcd-1
  ├─ kube-apiserver                 ├─ kube-apiserver ───┐
  ├─ etcd                           ├─ kube-scheduler    │
  ├─ kube-scheduler                 └─ kube-ctrl-manager │
  └─ kube-ctrl-manager            control-plane-2        etcd-2 ...
control-plane-2 ... (동일)
```

**stacked**는 etcd를 각 컨트롤 플레인 노드에 함께 두는 kubeadm 기본 구성이다. 컨트롤 플레인 노드 장애가 곧 etcd 노드 장애라 노드 수와 쿼럼 계산이 맞물린다. **external**은 etcd를 별도 노드 집합으로 분리해, 컨트롤 플레인 노드 장애가 쿼럼에 영향을 주지 않고 etcd에 빠른 로컬 디스크를 독립 할당할 수 있다. 대규모 프로덕션에서 선호된다.

## 실무 적용

### 체크리스트

- [ ] 오브젝트(기록), 프로그램(컨트롤러), 실제 자원(프로세스·IP)을 구분해서 "누가 이 일을 해야 하는가"를 말할 수 있다.
- [ ] 컨트롤러가 레벨 트리거 + 멱등이라 이벤트 유실이나 재시작에도 결국 수렴함을 설명할 수 있다.
- [ ] 컴포넌트마다 "하지 않는 일"을 말할 수 있다(특히 apiserver는 조정 안 함, scheduler는 실행 안 함, controller-manager는 etcd 직접 접근 안 함).
- [ ] `apply` 성공 후 Pending이면 ①&#126;⑱ 중 어느 단계 컴포넌트를 볼지 순서를 세울 수 있다.
- [ ] 컨트롤 플레인이 멈춰도 실행 중인 컨테이너는 유지되고 새 배포·배치가 멈춘다는 영향 범위를 안다.
- [ ] etcd는 홀수(3 또는 5)로 구성하고 쿼럼 표를 외웠다.
- [ ] scheduler·controller-manager는 리더 선출(Lease), apiserver는 active-active + 앞단 LB임을 안다.
- [ ] 컨트롤 플레인 점검은 `kubectl get --raw /readyz?verbose`, `kubectl get pods -n kube-system -o wide`로 시작한다.

   </details>

4. **상황:** 컨트롤 플레인 노드 3대 중 1대가 죽었다(stacked etcd 구성). 게임 서버 Pod는 계속 돌고 있다.
   **질문:** 지금 할 수 있는 것과 없는 것은? 노드 2대가 죽으면?

   <details markdown="1"><summary>답 확인</summary>

   1대가 죽어도 etcd 쿼럼(3노드 중 2)이 유지되고 apiserver는 active-active이며 scheduler·controller-manager는 standby가 리더로 승격하므로 새 배포·배치도 계속 동작한다. 2대가 죽으면 stacked라 etcd 노드도 2대를 잃어 쿼럼이 깨지고, 새 변경은 모두 막힌다. 다만 이미 실행 중인 컨테이너는 당장 사라지지 않는다. → 코어 4, 3.3

   </details>

### 2. 인출 질문

1. 선언형과 명령형의 차이는 무엇이고, 선언형의 신뢰성은 어떤 세 가지 성질에서 나오는가?

   <details markdown="1"><summary>답 확인</summary>

   명령형은 현재 상태를 모른 채 동작을 실행해 재실행 시 중복이 생긴다. 선언형은 원하는 상태(spec)만 기록하고 컨트롤러가 관찰 상태와의 차이를 줄인다. 신뢰성은 선언적 상태, 레벨 트리거(이벤트 대신 현재 상태로 판단), 멱등한 조정 함수의 조합에서 나오며, 이 덕에 이벤트를 놓쳐도 유한 스텝 안에 수렴한다. → 코어 1

   </details>

2. 레벨 트리거가 엣지 트리거보다 안전한 이유는?

   <details markdown="1"><summary>답 확인</summary>

   엣지 트리거는 이벤트 유실(네트워크 단절, 재시작, 큐 오버플로) 시 그 조치가 영원히 실행되지 않는다. 레벨 트리거는 현재 상태를 언제든 다시 읽어 `diff(desired, state)`를 재계산할 수 있어 놓친 이벤트가 다음 조정에서 교정된다. watch 이벤트는 "다시 봐라"는 신호로만 쓰인다. → 코어 1.3

   </details>

3. kube-apiserver가 하지 않는 일 세 가지는?

   <details markdown="1"><summary>답 확인</summary>

   스케줄링 결정(`nodeName`이 빈 채 저장 허용), 조정(종속 오브젝트를 스스로 만들지 않음, 컨트롤러가 watch로 처리), etcd 프로토콜 이외의 저장 로직(stateless에 가깝고 watch cache는 최적화일 뿐). → 코어 2

   </details>

4. 스케줄러의 작업은 언제 끝나고, 컨테이너는 누가 시작하는가?

   <details markdown="1"><summary>답 확인</summary>

   `Binding` 오브젝트를 만드는(=`spec.nodeName`을 채우는) 순간 끝난다. 실제 컨테이너 시작은 해당 노드의 kubelet이 CRI를 통해 컨테이너 런타임에 요청해 일어난다. 스케줄러는 배치 이후 상태도 감시하지 않는다. → 코어 2, 3

   </details>

5. 컴포넌트끼리 직접 통신하지 않는 설계의 이점은?

   <details markdown="1"><summary>답 확인</summary>

   모든 통신이 API 서버를 매개로 한 watch/write뿐이라 각 컴포넌트를 독립적으로 재시작·교체할 수 있고, 한 단계의 실패가 다른 컴포넌트를 깨뜨리지 않는다. 각 루프가 독립적으로 실패하고 재시도된다. → 코어 3.2

   </details>

6. `Service`를 삭제해도 Pod가 남고 `Pod`를 삭제하면 다시 생기는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   Service는 selector로 Pod를 "선택"할 뿐 소유하지 않는다. Pod는 ReplicaSet의 `ownerReferences`로 "소유"되어, 소유 ReplicaSet이 남아 있으면 컨트롤러가 부족분을 다시 만든다. 삭제 전파는 소유 관계에서만 일어난다. → 코어 1.5

   </details>

7. etcd 3노드, 5노드의 쿼럼과 허용 장애 수는? 4노드가 무의미한 이유는?

   <details markdown="1"><summary>답 확인</summary>

   3노드는 쿼럼 2에 허용 장애 1, 5노드는 쿼럼 3에 허용 장애 2다. 4노드는 쿼럼이 3으로 올라 허용 장애가 여전히 1이면서 쓰기 지연만 늘어난다. → 코어 4.2

   </details>

8. apiserver와 scheduler의 고가용성 방식은 어떻게 다르고, 왜 다른가?

   <details markdown="1"><summary>답 확인</summary>

   apiserver는 상태를 갖지 않고 etcd에 위임하므로 여러 인스턴스가 동시에 처리하는 active-active다(앞단 LB). scheduler와 controller-manager는 동시에 일하면 같은 Pod를 두 번 배치하는 식의 충돌이 생기므로 Lease 기반 리더 선출로 하나만 활성이고 나머지는 대기한다. → 코어 4.1

   </details>

### 3. 기억 고리

- **C++ 유추:** 게임 월드 틱 루프 = 조정 루프 ⚠️ 쿠버네티스에는 서로를 모르는 수십 개의 루프가 있고 공유 상태(오브젝트)만으로 연쇄 반응한다. 호출 스택이 없다.
- **C++ 유추:** epoll LT/ET = 레벨/엣지 트리거 ⚠️ epoll은 fd 통지 방식이고, 쿠버네티스는 "이력이 아니라 현재 상태로 판단"하는 설계 원칙이다. 위험 구조("한 번 놓치면 끝")만 닮았다.
- **비유:** API 서버 = 식당 주방의 주문 게시판. 홀 직원(kubectl)이 주문서를 붙이면 요리사(컨트롤러)들이 각자 게시판만 보고 자기 담당 단계를 한다. 요리사끼리는 말을 하지 않는다. ⚠️ 비유가 깨지는 지점: 게시판은 무한히 쌓이는 주문서가 아니라 "현재 원하는 상태"가 덮어써지는 상태판이다.
- **묶음(5·5):** 컨트롤 플레인 5개(apiserver, etcd, scheduler, controller-manager, cloud-cm) / 노드 쪽 5개(kubelet, kube-proxy, 런타임, CNI, CSI·디바이스 플러그인).
- **묶음(3·3·3):** 오브젝트·프로그램·실제 자원 구분 / 소유·선택·참조 / 선언형 신뢰성 3요소(선언적 상태·레벨 트리거·멱등성).
- **대칭:** 결정(scheduler) ↔ 실행(kubelet), 기록(etcd) ↔ 관문(apiserver), active-active(apiserver) ↔ active-standby(scheduler·controller-manager).
