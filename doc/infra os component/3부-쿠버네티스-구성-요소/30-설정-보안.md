# 30장. 설정·보안

> **🎮 게임 서버 개발자에게** — `getenv("DB_HOST")`로 환경변수를 읽고, `config.ini`를 시작 시 한 번 파싱하고, DB 비밀번호를 코드에 박지 않으려고 신경 써 본 경험이 그대로 출발점이다. 쿠버네티스의 ConfigMap/Secret은 이 값들이 **Pod 안의 환경변수나 파일로 변하는 과정**일 뿐이다. 그리고 보안은 낯선 영역이 아니다. `setuid` 바이너리, 루트로 서버를 띄우지 않기, 필요한 capability만 남기기, 시스템 콜 필터(seccomp) 같은 리눅스 이야기를 쿠버네티스가 `securityContext` 필드 몇 개로 켜 줄 뿐이다. 새로운 것은 "누가 API를 호출할 수 있는가"(RBAC)와 "그 워크로드가 실행된 뒤 무엇을 할 수 있는가"를 **서로 다른 문제로 나눠 막는다**는 관점이다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - ConfigMap의 로그 레벨을 바꿨는데 실행 중인 서버는 전혀 반응하지 않는다.
> - DB 비밀번호를 Secret에 넣었으니 안전하다고 생각했는데, 누군가 `base64 -d` 한 줄로 읽어 냈다.
> - 침해된 Pod 하나가 노드, 다른 Pod, 클라우드 자격증명까지 번지지 않게 하고 싶다.

## 코어 — 이것만은 100%

> **한 문장:** 설정은 환경변수(시작 시 고정)나 볼륨 파일(원자적으로 갱신)로 주입되고 Secret의 base64는 암호화가 아니며, 접근은 인증 → 인가(RBAC) → 어드미션을 지나고, 실행 후 권한은 `securityContext`가 리눅스의 uid·capability·seccomp·읽기 전용 파일시스템으로 좁힌다.

1. **ConfigMap/Secret = 환경변수 또는 파일** — 환경변수는 프로세스 시작 시 고정되어 **절대 갱신되지 않고**, 볼륨은 심볼릭 링크 교체로 갱신되며(최대 약 2분) `subPath`는 갱신되지 않는다. Secret은 노드의 tmpfs에 놓이지만 etcd에는 기본적으로 평문이다.
2. **세 개의 관문: 인증(401) → 인가(403) → 어드미션** — 쿠버네티스에는 사용자 오브젝트가 없다(ServiceAccount만 있다). 워크로드 신원은 projected 볼륨의 짧은 수명 토큰이며, API가 필요 없으면 자동 마운트를 끈다.
3. **RBAC = 허용 규칙만 더하는 모델** — Role/ClusterRole(권한) + RoleBinding/ClusterRoleBinding(연결). `list`는 `get`보다 훨씬 넓고, `pods` `create`는 사실상 노드 접근과 가깝다.
4. **`securityContext`는 리눅스 프리미티브의 스위치** — `runAsNonRoot`, `allowPrivilegeEscalation: false`(no_new_privs), `readOnlyRootFilesystem`, `capabilities.drop: ALL`, `seccompProfile: RuntimeDefault`. Pod Security Admission이 네임스페이스 라벨 하나로 이를 강제한다. 기준은 블래스트 레이디어스다.

## 코어 1. ConfigMap·Secret이 환경변수·파일이 되는 과정

### 1.1 설정을 이미지와 분리하는 이유

**한 줄 요약:** 같은 이미지를 모든 환경에 배포하고 설정만 환경별로 주입한다.

개발·스테이징·프로덕션에서 DB 주소, 로그 레벨, 기능 플래그는 다르다. 설정을 이미지에 넣으면 환경마다 다른 이미지를 빌드해야 하고, "스테이징에서 테스트한 이미지"와 "프로덕션에 배포한 이미지"가 다른 산출물이 되어 테스트의 의미가 사라진다. 쿠버네티스는 일반 설정용 **ConfigMap**과 민감 정보용 **Secret**을 제공한다. 둘 다 `data` 값은 문자열이어야 한다(`MAX_CONNECTIONS: "100"`).

### 1.2 환경변수로 주입

**한 줄 요약:** 편하지만 시작 시 고정되어 영원히 갱신되지 않는다.

```yaml
env:    [ { name: LOG_LEVEL, valueFrom: { configMapKeyRef: { name: app-config, key: LOG_LEVEL } } } ]
envFrom: [ { configMapRef: { name: app-config } }, { secretRef: { name: app-secret } } ]
```

`envFrom`은 ConfigMap의 **모든 키**를 환경변수로 만든다. 키 이름이 환경변수로 유효하지 않으면(`app.yaml`) 조용히 건너뛰고, 같은 키가 여러 소스에 있으면 나중 것이 이기며 `env`가 `envFrom`보다 우선한다.

> **⚠️ 환경변수는 절대 갱신되지 않는다.** 리눅스에서 프로세스의 환경변수는 시작 시점에 고정되기 때문이다. `exec` 이후 `getenv`가 보는 값은 그 프로세스의 `environ`이고(`/proc/<pid>/environ`, [2장](../1부-리눅스-OS-구성-요소/02-프로세스.md)), ConfigMap 수정은 거기에 닿지 않는다.

### 1.3 볼륨 마운트와 자동 갱신

**한 줄 요약:** 볼륨은 `..data` 심볼릭 링크를 원자적으로 바꿔 갱신되고, `subPath`는 갱신되지 않는다.

```yaml
volumes:
  - name: config
    configMap: { name: app-config, defaultMode: 0444 }   # items로 특정 키만 골라 path 지정 가능
containers:
  - name: app
    volumeMounts: [ { name: config, mountPath: /etc/app, readOnly: true } ]
```

`items`를 생략하면 모든 키가 파일이 된다. kubelet은 새 타임스탬프 디렉터리를 만들고 `..data` 심볼릭 링크를 원자적으로 교체한다.

```
lrwxrwxrwx  app.yaml -> ..data/app.yaml
drwxr-xr-x  ..2026_09_01_10_23_45.123456789/
lrwxrwxrwx  ..data -> ..2026_09_01_10_23_45.123456789
```

그래서 부분적으로 갱신된 파일을 읽는 일이 없다. 반영 지연은 kubelet의 동기화 주기(기본 1분) + 캐시 TTL로 **최대 2분 정도**다. 중요한 것은 **파일이 바뀌어도 앱이 다시 읽지 않으면 소용없다**는 점이다(inotify나 주기적 재로드, 혹은 1.5의 롤아웃 유도).

특정 파일 하나만 기존 디렉터리에 끼우려고 `subPath`를 쓰면 기존 파일이 유지되지만, **`subPath`로 마운트한 파일은 ConfigMap이 바뀌어도 자동 갱신되지 않는다.**

| | 환경변수 | 볼륨 마운트 | 볼륨 + `subPath` |
|---|---|---|---|
| 자동 갱신 | 절대 안 됨 | 됨 (최대 약 2분) | 안 됨 |
| 앱 수정 필요 | 없음 | 파일 읽기 로직 | 파일 읽기 로직 |
| 큰 설정 파일 | 부적합 | 적합 | 적합 |
| 확인 | `kubectl exec -- env` | `kubectl exec -- cat` | 동일 |

> **게임 서버 유추:** 환경변수 주입은 `execve()`에 넘긴 `envp`, 볼륨 주입은 서버가 읽는 설정 파일이다. ⚠️ 파일은 `rename()`으로 원자적 교체되지만 서버가 inotify로 다시 읽어 주지 않으면 이전 설정으로 돈다.

### 1.4 Secret: base64는 암호화가 아니다

**한 줄 요약:** Secret이 ConfigMap보다 나은 점은 노드 tmpfs 저장과 RBAC 분리 정도이고, etcd 평문은 별도로 막아야 한다.

| | ConfigMap | Secret |
|---|---|---|
| 데이터 필드 | `data` (평문) | `data` (base64) 또는 `stringData` (평문 입력) |
| etcd 저장 | 평문 | 평문 (**암호화 설정 안 하면**) |
| kubelet 캐싱 | 노드 디스크 | **tmpfs (메모리)** |
| 최대 크기 | 1MiB | 1MiB |

```bash
kubectl get secret db-secret -o jsonpath='{.data.password}' | base64 -d
# supersecret123
```

누구나 디코딩할 수 있다. 실제로 나은 점은 **노드에서 tmpfs에 저장되어 디스크에 남지 않는 것**과 **RBAC로 권한을 분리할 수 있고 로그·이벤트 노출에 더 조심하는 것** 두 가지뿐이다. `stringData`를 쓰면 base64를 직접 계산할 필요 없이 API 서버가 `data`로 변환해 저장한다. 타입을 지정하면(`kubernetes.io/tls`는 `tls.crt`/`tls.key` 필수 등) API 서버가 필수 키를 검증한다.

주입은 ConfigMap과 같지만 **환경변수보다 볼륨을 권장**한다. 환경변수는 크래시 시 스택 트레이스·에러 리포터가 통째로 전송하거나, 같은 Pod의 다른 컨테이너가 `/proc/<pid>/environ`으로 읽거나(PID 공유 시), 자식 프로세스에 자동 상속되기 때문이다. 볼륨은 파일 권한(`defaultMode: 0400`)으로 제어할 수 있고 갱신도 된다.

**저장 시 암호화.** 기본 설정에서 Secret은 etcd에 평문이라 etcd 백업 파일을 얻은 사람은 모든 시크릿을 읽는다. API 서버에 `EncryptionConfiguration`을 주고 `--encryption-provider-config`로 지정한다. 프로바이더 목록에서 **첫 번째가 암호화에 쓰이고**, 뒤의 `identity: {}`는 기존 평문 데이터를 읽기 위한 것이다.

프로바이더는 `identity`(암호화 안 함, 기본), `aescbc`(`aesgcm` 권장), `aesgcm`(빠르지만 키 교체가 잦아야 함), `secretbox`, 그리고 외부 KMS 연동인 `kms` v2가 있고 **프로덕션은 KMS v2**가 실질적인 정답이다(키가 etcd·API 서버 디스크에 남지 않는다).

암호화 설정은 **새로 쓰이는 데이터에만** 적용되므로 기존 Secret은 `kubectl get secrets -A -o json | kubectl replace -f -`로 다시 쓰게 만든다(etcd는 [20장](20-etcd.md)). Git 커밋, 수동 로테이션, 감사 추적 부재는 External Secrets Operator 같은 외부 시크릿 관리의 몫이다.

### 1.5 Downward API와 설정 변경 시 롤아웃

**한 줄 요약:** Pod 자신의 메타데이터·리소스 한도를 주입하고, 설정이 바뀌면 Pod 템플릿이 바뀌게 만들어야 롤아웃이 일어난다.

앱이 자기 Pod 이름·네임스페이스·노드·IP, 컨테이너의 메모리·CPU 한도를 알아야 할 때 환경변수(`fieldRef`, `resourceFieldRef`)로 받는다. 라벨·애노테이션 **전체**는 볼륨(`downwardAPI`)으로만 받을 수 있고, 볼륨은 갱신된다.

```yaml
env:
  - name: MEMORY_LIMIT_MB
    valueFrom: { resourceFieldRef: { resource: limits.memory, divisor: 1Mi } }
  - name: POD_NAME
    valueFrom: { fieldRef: { fieldPath: metadata.name } }
```

`resourceFieldRef`는 JVM·Node.js 같은 런타임이 컨테이너 한도를 알아 힙을 정할 때 유용하다([25장](25-Pod-생명주기와-리소스.md)). 

ConfigMap만 바꿔서는 Deployment의 Pod 템플릿이 바뀌지 않아(`generation`이 그대로) 컨트롤러가 아무 조치도 하지 않는다. 그래서 설정이 바뀌면 Pod를 새로 만드는 패턴을 쓴다.

| 방법 | 설명 |
|---|---|
| 체크섬 애노테이션 (권장) | ConfigMap 해시를 Pod 템플릿 애노테이션에 넣으면 설정 변경 → 해시 변경 → 템플릿 변경 → 롤링 업데이트. Kustomize는 `configMapGenerator`가 이름에 내용 해시를 붙여 자동 처리하고 이전 버전이 남아 롤백도 가능 |
| `kubectl rollout restart deployment/app` | `restartedAt` 애노테이션으로 롤링 유도. 간단하지만 자동화되지 않음 |
| Reloader | ConfigMap/Secret 변경을 감시해 관련 Deployment를 재시작하는 오퍼레이터 |
| 불변 ConfigMap + 버전 이름 | `immutable: true`. 실수 변경 방지, kubelet이 변경을 감시하지 않아 API 서버 부하 감소 |

## 코어 2. 세 개의 관문과 워크로드 신원

### 2.1 요청 처리 파이프라인

**한 줄 요약:** 인증(누구?) → 인가(권한?) → 어드미션(변형·검증) → etcd 저장, 실패 코드로 계층을 안다.

모든 요청이 API 서버([19장](19-kube-apiserver.md)) 한 곳을 지나므로 접근 통제도 한 곳에서 이루어진다.

```
① 인증 (Authentication)  "누구인가?"             → 실패 401 Unauthorized  (인증서·토큰·kubeconfig 문제)
② 인가 (Authorization)   "그 행동을 할 권한이?"   → 실패 403 Forbidden    (RBAC 문제)
③ 어드미션 제어           Mutating → 스키마 검증 → Validating
④ etcd 저장
```

```bash
kubectl auth whoami                  # 나는 누구인가
kubectl auth can-i create pods
kubectl auth can-i list secrets --as=system:serviceaccount:default:my-sa   # 가장(impersonate)해서 검증
kubectl auth can-i --list -n default
```

### 2.2 쿠버네티스에는 사용자 오브젝트가 없다

**한 줄 요약:** 인증은 증거(인증서, 토큰)에서 문자열 username·groups를 뽑을 뿐이다.

`kubectl get users`는 존재하지 않는 리소스 타입이라 실패한다. 인증이 성공하면 API 서버는 `username`, `groups`, `uid`, `extra`만 안다. 사용자 생성·삭제·비밀번호 변경은 외부 시스템(인증서 CA, OIDC 제공자, 클라우드 IAM)의 일이다. **예외는 ServiceAccount**이며 실제 API 오브젝트다(`system:serviceaccount:<ns>:<name>`).

| 인증 방식 | 핵심 |
|---|---|
| X.509 클라이언트 인증서 | CN → username, O → groups. **폐기(revocation) 불가**(만료까지 유효). 부트스트랩·긴급 접근용 |
| OIDC | 사람 인증의 표준. 중앙 ID 관리, MFA, 짧고 폐기 가능한 토큰 |
| ServiceAccount 토큰 | 워크로드용 |
| Webhook 토큰 | 외부 서비스(EKS는 IAM)에 검증 위임 |
| 정적 토큰 파일 | 절대 쓰지 말 것 (평문, 재시작 필요, 폐기 불가) |

`system:masters` 그룹은 RBAC 검사를 건너뛰고 모든 것을 할 수 있으며 RBAC로 제한할 수 없다. kubeadm이 만드는 `admin.conf`의 인증서가 `O=system:masters`이므로 금고에 넣어 평소에는 쓰지 않는다.

### 2.3 ServiceAccount 토큰

**한 줄 요약:** v1.24부터 Secret 없이 projected 볼륨의 만료되는 토큰이며, API가 필요 없으면 마운트를 끈다.

모든 Pod는 ServiceAccount를 갖고(미지정 시 네임스페이스의 `default`) 토큰이 projected 볼륨으로 주입된다.

```bash
kubectl exec <pod> -- ls /var/run/secrets/kubernetes.io/serviceaccount/
# ca.crt  namespace  token
```

v1.24 이전에는 SA마다 만료 없는 Secret이 자동 생성되었지만, 이후에는 **Secret 없이 projected 볼륨으로 1시간 만료·자동 갱신되는 토큰**(`audience` 지정 가능)을 전달한다.

대부분의 앱은 쿠버네티스 API를 호출하지 않는다. 토큰이 마운트되어 있으면 Pod 침해 시 공격자가 그 토큰으로 API에 접근할 수 있으므로 **필요 없으면 끈다**.

```yaml
spec:
  serviceAccountName: my-app
  automountServiceAccountToken: false
```

클라우드 자원 접근은 시크릿 없는 **워크로드 아이덴티티**로 푼다. Pod가 SA 토큰(JWT, audience는 클라우드 IAM)을 클라우드 STS에 제시하면 STS가 클러스터 OIDC 공개키로 검증하고 임시 자격증명(예: 1시간)을 발급한다. AWS의 IRSA는 SA 애노테이션 `eks.amazonaws.com/role-arn`과 IAM 신뢰 정책의 `sub` 조건(특정 네임스페이스·SA만)으로 연결한다. 어느 클라우드든 원리는 OIDC 신뢰를 통한 토큰 교환이다. ServiceAccount를 만들기만 해서는 S3 권한이 생기지 않는다. 쿠버네티스 신원과 AWS IAM은 별도 체계이고 연결과 대상 정책이 추가로 필요하다.

## 코어 3. RBAC: 허용 규칙만 더하는 권한 모델

### 3.1 네 개의 리소스와 조합 규칙

**한 줄 요약:** Role/ClusterRole이 권한, RoleBinding/ClusterRoleBinding이 연결이며, RoleBinding이 ClusterRole을 참조하면 그 네임스페이스에만 적용된다.

```
        네임스페이스 스코프          클러스터 스코프
권한        Role                      ClusterRole
연결     RoleBinding               ClusterRoleBinding
```

| Binding | Role 참조 | 적용 범위 |
|---|---|---|
| RoleBinding | Role | 그 네임스페이스 |
| RoleBinding | **ClusterRole** | **그 네임스페이스에만** (실무 핵심) |
| ClusterRoleBinding | ClusterRole | 클러스터 전체 |
| ClusterRoleBinding | Role | 불가능 |

`apiGroups`의 빈 문자열 `""`은 코어 그룹(Pod, Service, ConfigMap, Secret)이다. 주체(Subject)는 User, Group, ServiceAccount(네임스페이스 필수)이며 사람이 드나들 때마다 RBAC를 고치지 않도록 **그룹 기반 바인딩**을 권장한다.

```yaml
kind: Role
metadata: { name: dev-workloads, namespace: dev }
rules:
  - apiGroups: ["", "apps"]
    resources: ["pods", "services", "deployments", "replicasets", "configmaps"]
    verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
  - apiGroups: [""]
    resources: ["pods/log", "pods/exec"]     # 서브리소스는 별도로 허용 (Secret은 의도적으로 제외)
    verbs: ["get", "create"]
---
kind: RoleBinding
metadata: { name: dev-team-binding, namespace: dev }
subjects: [ { kind: Group, name: dev-team, apiGroup: rbac.authorization.k8s.io } ]
roleRef:   { kind: Role, name: dev-workloads, apiGroup: rbac.authorization.k8s.io }
```

내장 ClusterRole은 `cluster-admin`(모든 것), `admin`(네임스페이스 안의 모든 것 + RBAC 관리), `edit`(RBAC 관리 제외), `view`(읽기 전용, **Secret 제외**)다. `edit` ClusterRole을 여러 네임스페이스에서 RoleBinding으로 재사용하는 것이 표준 패턴이다.

### 3.2 위험 권한과 권한 상승 방지

**한 줄 요약:** `list`는 모든 오브젝트를 덤프하고, `pods` `create`는 사실상 노드 루트에 가깝다.

> **⚠️ `get`과 `list`의 큰 차이.** `get`은 이름을 알아야 하나씩 조회하지만 `list`는 모든 오브젝트를 한 번에 가져와, secrets에 `list` 권한이 있으면 그 네임스페이스의 모든 시크릿을 덤프할 수 있다. `resourceNames`로 제한해도 **`list`와 `watch`에는 적용되지 않는다.**

RBAC는 허용 규칙을 더하는 모델이라 한 binding을 지웠어도 다른 binding이 같은 권한을 주면 접근이 유지된다. 권한 상승 방지 규칙도 있다. Role을 만들거나 수정하려면 그 안의 모든 권한을 이미 갖고 있거나 `escalate` 권한이 있어야 하고, RoleBinding을 만들려면 참조 Role의 권한을 이미 갖거나 `bind` 권한이 있어야 한다.

| 위험한 권한 | 왜 위험한가 |
|---|---|
| `secrets` `list`/`get` | 자격증명 유출 |
| `pods/exec`, `pods/attach` | 컨테이너 침투 |
| `pods` `create` | hostPath 마운트, 특권 컨테이너로 노드 장악 가능 |
| `nodes/proxy` | kubelet API 직접 호출 |
| `escalate`, `bind`, `impersonate` | 권한 상승 |
| `serviceaccounts/token` | 임의 SA 토큰 발급 |

설계 원칙은 ① 최소 권한 ② 그룹 기반 ③ 네임스페이스 스코프 우선(`cluster-admin`은 극소수) ④ 위험 권한 점검이다. 검증은 사용자 kubeconfig를 만들지 않고 `kubectl auth can-i ... --as=alice --as-group=dev-team`으로 한다.

## 코어 4. securityContext는 리눅스 프리미티브의 스위치다

### 4.1 블래스트 레이디어스

**한 줄 요약:** "침해되면 피해가 어디까지 번지는가"를 층마다 좁힌다.

RBAC가 완벽해도 특권 컨테이너 하나가 노드를 장악하면 소용없다. 컨테이너 하나가 침해됐을 때 번지는 경로와 막는 수단은 다음과 같다.

```
① 컨테이너 안에서 무엇을 할 수 있나 (root? 쓰기 가능 FS? capability?)  → securityContext
② 같은 Pod의 다른 컨테이너로 갈 수 있나 (공유 볼륨, localhost)           → 최소 권한, 볼륨 분리
③ 노드로 탈출할 수 있나 (hostPath, hostNetwork, privileged)             → Pod Security Admission, 샌드박스
④ 다른 Pod와 통신할 수 있나 (기본은 전허용)                              → NetworkPolicy (28장)
⑤ API 서버를 호출할 수 있나                                              → automountServiceAccountToken: false, RBAC
⑥ 클라우드 자원에 접근할 수 있나 (IMDS, IAM 역할)                         → IMDSv2, 워크로드 아이덴티티
```

잊기 쉬운 경로는 **클라우드 메타데이터 서비스**다. 노드에 IAM 역할이 붙어 있으면 어떤 Pod든 `curl http://169.254.169.254/...`로 그 역할의 자격증명을 가져갈 수 있다. 대책은 IMDSv2 강제 + hop limit 1(`aws ec2 modify-instance-metadata-options --http-tokens required --http-put-response-hop-limit 1`), 워크로드 아이덴티티로 노드 역할 최소화, NetworkPolicy로 `169.254.169.254` 차단이다.

### 4.2 필드와 커널 동작

**한 줄 요약:** 각 필드는 2부(9~17장)에서 본 리눅스 프리미티브(uid, no_new_privs, capability, seccomp)를 켜는 스위치다.

```yaml
containers:
  - name: app
    securityContext:
      runAsNonRoot: true                # root면 컨테이너 시작 거부
      runAsUser: 10001
      allowPrivilegeEscalation: false   # setuid로 권한 상승 차단
      readOnlyRootFilesystem: true      # 루트 FS 쓰기 금지
      privileged: false
      capabilities:
        drop: ["ALL"]                   # 모든 capability 제거
        add: ["NET_BIND_SERVICE"]       # 필요한 것만 추가
      seccompProfile:
        type: RuntimeDefault            # 시스템콜 필터링
```

| 필드 | 커널 수준 동작 | 막는 공격 |
|---|---|---|
| `runAsNonRoot` | UID 0이면 kubelet이 시작을 거부 | root 권한 남용 |
| `allowPrivilegeEscalation: false` | `no_new_privs` 비트 설정 | setuid 바이너리로 권한 상승 |
| `readOnlyRootFilesystem` | 루트를 읽기 전용으로 마운트 | 악성 코드 설치, 바이너리 변조 |
| `capabilities.drop: ALL` | 모든 capability 제거 | 네트워크 조작, 마운트, 커널 모듈 |
| `privileged: false` | 모든 capability + 디바이스 접근 차단 | **노드 탈출** |
| `seccompProfile` | 허용된 시스템콜만 통과 | 커널 익스플로잇 표면 축소 |

`privileged: true`가 가장 위험하다. 사실상 노드의 root와 같아 `/dev`에 접근해 호스트 디스크를 마운트하거나 커널 모듈을 로드할 수 있다. 리눅스에는 350개 이상의 시스템콜이 있고 일반 애플리케이션은 50개 정도만 쓰는데, `RuntimeDefault`는 `mount`, `reboot`, `kexec_load`, `bpf` 등 위험한 시스템콜을 차단하며 오버헤드가 거의 없으니 항상 켠다.

Pod 수준 `securityContext`는 모든 컨테이너에 상속되고 컨테이너 수준이 우선한다. `fsGroup`은 볼륨 마운트 시 소유권을 그 GID로 바꿔 비루트 사용자가 쓰게 해 주지만, 기본값(`fsGroupChangePolicy: Always`)은 마운트마다 모든 파일의 소유권을 재귀 변경해 파일이 수백만 개면 Pod 시작이 몇 분 걸린다. `OnRootMismatch`로 바꾸면 루트 디렉터리만 확인한다.

**`readOnlyRootFilesystem`을 켜면 대부분의 앱이 죽는다.** 임시 파일을 쓸 곳이 없기 때문이다. 앱이 쓰는 경로(`/tmp`, `/var/cache/nginx`, `/var/run`)에 `emptyDir`을 마운트한다([29장](29-스토리지.md)). 실무에서는 먼저 `false`로 띄워 `find / -newer /etc/hostname -type f` 같은 방법으로 쓰는 경로를 확인한 뒤 적용한다.

> **게임 서버 유추:** 서버를 전용 uid로 실행하고, `setcap`으로 낮은 포트 바인딩만 허용하고, 쓰기 디렉터리를 `/var/game`으로 제한하는 것과 같다. ⚠️ 쿠버네티스에서는 이 설정을 Pod 스펙에 선언하고, 이미지가 root 전제로 만들어져 있으면 선언만으로 앱이 시작되지 않을 수 있다.

### 4.3 Pod Security Admission

**한 줄 요약:** 네임스페이스 라벨 하나로 privileged / baseline / restricted 프로파일을 enforce·warn·audit한다.

PodSecurityPolicy는 v1.25에서 제거됐고 후계인 PSA는 네임스페이스 라벨로 프로파일을 지정한다.

| 프로파일 | 내용 |
|---|---|
| `privileged` | 제한 없음 (시스템 컴포넌트용) |
| `baseline` | 알려진 권한 상승을 차단 (`privileged`, hostNetwork/hostPID/hostIPC, hostPath, 위험한 sysctl 등 금지). 대부분의 앱이 수정 없이 통과 |
| `restricted` | 강력한 하드닝. `runAsNonRoot`, `allowPrivilegeEscalation: false`, `capabilities.drop: ALL`, seccomp `RuntimeDefault`/`Localhost`, 허용된 볼륨 타입만 |

모드는 네임스페이스 라벨 `pod-security.kubernetes.io/enforce`(위반 시 Pod 생성 거부), `warn`(경고만, 생성은 됨), `audit`(감사 로그에만 기록)에 프로파일을 지정한다(예: `enforce: baseline`, `warn: restricted`).

**점진 도입이 핵심이다.** `warn`+`audit`만 설정해 위반을 파악 → 워크로드 수정 → `enforce: baseline` → `warn/audit`을 restricted로 → `enforce: restricted`. 한 번에 강제하면 배포가 전부 실패한다. RBAC로 Pod 생성 권한이 있어도 정책에 맞지 않으면 어드미션이 거절한다([19장](19-kube-apiserver.md)). 에러 메시지가 정확히 무엇을 고쳐야 하는지 알려 준다.

## 실무 적용

### 체크리스트

- [ ] 같은 이미지를 모든 환경에 배포하고 설정만 ConfigMap/Secret으로 주입한다. `data` 값은 문자열(`"100"`, `"true"`)이다.
- [ ] 환경변수는 갱신되지 않는다는 것을 알고, 반영하려면 롤아웃(체크섬 애노테이션, `rollout restart`)을 유도한다. 볼륨 설정은 앱이 다시 읽는지 확인했다. `subPath`는 갱신되지 않는다.
- [ ] Secret의 base64는 암호화가 아니다. etcd 저장 시 암호화(프로덕션은 KMS v2)를 켰고, 기존 Secret은 `replace`로 다시 썼다.
- [ ] 시크릿은 환경변수 대신 볼륨(`defaultMode: 0400`)으로 주입한다.
- [ ] 401(인증)과 403(인가)을 구분해 진단한다. `kubectl auth can-i`로 권한을 검증한다.
- [ ] API가 필요 없는 Pod에는 `automountServiceAccountToken: false`를 지정했다. 클라우드 접근은 정적 키 대신 워크로드 아이덴티티를 쓴다.
- [ ] RBAC는 최소 권한·그룹 기반·네임스페이스 스코프다. `secrets`의 `list`와 `pods/exec`, `pods` `create`를 신중히 다룬다.
- [ ] `runAsNonRoot`, `allowPrivilegeEscalation: false`, `capabilities.drop: ALL`, `seccompProfile: RuntimeDefault`를 기본으로 하고, 읽기 전용 루트에는 `emptyDir`로 쓰기 경로를 열어 주었다.
- [ ] 네임스페이스에 PSA 라벨을 단계적으로(warn/audit → enforce) 적용했다. IMDS 접근(`169.254.169.254`)을 막았다.

   **질문:** 왜 다르고, 환경변수 쪽은 어떻게 반영하나?

   <details markdown="1"><summary>답 확인</summary>

   프로세스의 환경변수는 시작 시점에 고정되어 실행 중에는 바뀌지 않는다. 볼륨은 kubelet이 `..data` 심볼릭 링크를 원자적으로 교체하며 최대 약 2분 지연으로 갱신된다(앱이 다시 읽어야 반영). 환경변수 쪽은 Pod를 재생성해야 하므로 Pod 템플릿의 체크섬 애노테이션을 바꾸거나 `kubectl rollout restart`로 롤링 업데이트를 유도한다. → 코어 1.2, 1.3, 1.5

   </details>

2. **상황:** 개발자 alice가 `kubectl get pods`를 실행하니 `pods is forbidden: User "alice" cannot list resource "pods"`가 나왔다.
   **질문:** 어느 단계의 실패이고 무엇을 확인하나?

   <details markdown="1"><summary>답 확인</summary>

   인증은 통과해 신원이 확인되었고, 인가(RBAC)에서 거절된 403이다(401이라면 인증서·토큰·kubeconfig 문제). `kubectl auth can-i --list -n <ns> --as=alice --as-group=<그룹>`으로 권한을 보고 Role/RoleBinding을 확인한다. RBAC는 허용만 더하는 모델이라 거부 규칙을 지우는 것이 아니라 필요한 권한을 주는 Role/RoleBinding을 추가해야 한다. → 코어 2.1, 코어 3

   </details>

3. **상황:** 게임 서버 컨테이너를 `readOnlyRootFilesystem: true`, `runAsNonRoot: true`로 하드닝했더니 시작 직후 크래시한다.
   **질문:** 원인과 해결은?

   <details markdown="1"><summary>답 확인</summary>

   읽기 전용 루트에서는 앱이 쓰던 임시·캐시·런타임 경로에 쓸 수 없어 죽는다. 먼저 `false`로 띄워 어디에 쓰는지 확인하고, 그 경로(`/tmp`, `/var/cache/...`, `/var/run`)에 `emptyDir`을 마운트한다. 이미지가 root 전제로 만들어졌다면 `runAsNonRoot`가 시작을 거부하므로 비루트 uid로 실행되게 이미지를 고치고, 낮은 포트가 필요하면 `NET_BIND_SERVICE`만 되돌려 넣는다. → 코어 4.2

   </details>

### 2. 인출 질문

1. ConfigMap 수정이 환경변수 주입 Pod에 반영되지 않는 이유는? 볼륨 마운트는 어떻게 갱신되는가?

   <details markdown="1"><summary>답 확인</summary>

   리눅스에서 프로세스의 환경변수는 시작 시점에 고정되므로 이미 실행 중인 Pod에는 반영되지 않고 Pod를 재생성해야 한다. 볼륨은 kubelet이 새 타임스탬프 디렉터리를 만들고 `..data` 심볼릭 링크를 원자적으로 교체하며, 동기화 주기(기본 1분) + 캐시 TTL로 최대 약 2분 걸린다. `subPath` 마운트는 자동 갱신되지 않는다. → 코어 1.2, 1.3

   </details>

2. Secret이 ConfigMap보다 실제로 나은 점은? 그리고 etcd 저장 문제는 어떻게 해결하나?

   <details markdown="1"><summary>답 확인</summary>

   노드에서 tmpfs(메모리)에 저장되어 디스크에 남지 않는 것, RBAC로 권한을 분리하고 로그·이벤트 노출에 더 조심하는 것 두 가지뿐이다. etcd에는 기본적으로 평문이므로 API 서버에 `EncryptionConfiguration`(`--encryption-provider-config`)을 주고, 프로덕션은 외부 KMS 연동인 `kms` v2를 쓴다. 기존 데이터는 다시 써야 암호화된다. → 코어 1.4

   </details>

3. 요청이 거치는 관문의 순서와 401/403의 의미는?

   <details markdown="1"><summary>답 확인</summary>

   인증(누구인가, 실패 401: 인증서·토큰·kubeconfig 문제) → 인가(권한 있는가, 실패 403: RBAC 문제) → 어드미션(Mutating → 스키마 검증 → Validating) → etcd 저장이다. → 코어 2.1

   </details>

4. RoleBinding이 ClusterRole을 참조하면 권한은 어디까지 적용되는가? `get`과 `list`의 차이는?

   <details markdown="1"><summary>답 확인</summary>

   RoleBinding이 ClusterRole을 참조하면 그 RoleBinding의 네임스페이스에만 적용되어, ClusterRole 하나를 여러 네임스페이스에서 재사용할 수 있다. `get`은 이름으로 하나씩 조회하지만 `list`는 모든 오브젝트를 한 번에 가져오며(secrets에 `list`면 전체 덤프), `resourceNames`는 `list`/`watch`에 적용되지 않는다. → 코어 3.1, 3.2

   </details>

5. `securityContext`의 `allowPrivilegeEscalation: false`, `capabilities.drop: ALL`, `seccompProfile: RuntimeDefault`는 커널 수준에서 각각 무엇을 하는가?

   <details markdown="1"><summary>답 확인</summary>

   `no_new_privs` 비트를 설정해 setuid 바이너리로의 권한 상승을 막고, 모든 capability를 제거해 네트워크 조작·마운트·커널 모듈 같은 특권 작업을 막고, 런타임 기본 프로파일로 위험한 시스템콜(`mount`, `reboot`, `kexec_load`, `bpf` 등)을 차단해 커널 공격 표면을 줄인다. → 코어 4.2

   </details>

6. Pod Security Admission의 세 프로파일과 점진 도입 순서는?

   <details markdown="1"><summary>답 확인</summary>

   `privileged`(제한 없음), `baseline`(알려진 권한 상승 차단), `restricted`(강력한 하드닝). 모드는 enforce/warn/audit이고, `warn`+`audit`로 위반 파악 → 워크로드 수정 → `enforce: baseline` → warn/audit을 restricted로 → `enforce: restricted` 순서다. 한 번에 강제하면 배포가 모두 실패한다. → 코어 4.3

   </details>

### 3. 기억 고리

- **C++ 유추:** `getenv()` = 환경변수 주입 ⚠️ `execve` 때 정해진 `envp`처럼 쿠버네티스에서도 시작 이후 갱신되지 않는다. 설정 파일 재로딩은 볼륨 + 앱 쪽 재읽기가 필요하다.
- **C++ 유추:** 전용 uid + `setcap` + 쓰기 디렉터리 제한 = `securityContext` ⚠️ 선언이 이미지와 안 맞으면(root 전제, 쓰기 경로) 앱이 시작되지 않을 수 있다.
- **비유:** Secret의 base64 = 서류를 투명 봉투에 넣어 우체통에 넣는 것(봉투가 있으니 안전해 보임). ⚠️ 비유가 깨지는 지점: 실제로는 봉투 자체가 없고 단순한 문자 변환이라 누구나 바로 읽는다. 진짜 잠금은 etcd 암호화와 RBAC다.
- **비유:** RBAC = 출입증 + 방별 허용 목록. ⚠️ 비유가 깨지는 지점: 출입 금지 목록이 없고 허용만 쌓이므로, 하나의 출입증을 회수해도 다른 출입증이 같은 방을 열 수 있다.
- **묶음(3의 법칙):** 주입 방식 3(env / 볼륨 / 볼륨+subPath) / 관문 3(인증·인가·어드미션) / PSA 프로파일 3 / 이 장 첫머리의 실무 상황 3개.
- **대칭·순서:** 환경변수(고정) ↔ 볼륨(갱신), 401(누구) ↔ 403(권한), Role(권한) ↔ Binding(연결), 시도 순서: 인증 → 인가 → 어드미션. 하드닝 순서: warn → enforce baseline → enforce restricted.
