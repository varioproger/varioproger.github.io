# 31장. 계층 종합과 장애 진단

> **🎮 게임 서버 개발자에게** — 라이브 서비스 중 "틱이 튄다", "접속이 안 된다", "서버가 갑자기 재시작한다"는 알림이 오면, 경험 있는 개발자는 코드를 열기 전에 먼저 **어느 계층의 문제인지**를 가른다. 클라이언트 → 네트워크 → 소켓 → 스레드 풀 → 로직 순으로 좁히는 습관이다. 컨테이너와 쿠버네티스가 얹히면 계층이 늘 뿐이다. 이 장은 책 전체를 한 장의 지도로 묶는다. 같은 일을 Docker 명령, 쿠버네티스 오브젝트, 리눅스 커널 기능으로 각각 부르는 이름을 나란히 놓고, 증상에서 시작해 증거를 따라 계층을 좁히는 순서를 정리한다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 새 버전을 배포했더니 사용자 오류가 늘었는데 모든 Pod가 `Running`이다.
> - `kubectl` 출력, `docker` 명령, 리눅스 `/proc`이 같은 사건을 다른 이름으로 말해서 어느 말이 어느 말인지 헷갈린다.
> - 장애 중에 이것저것 한꺼번에 바꿨다가 무엇이 효과를 냈는지 알 수 없게 됐다.

## 코어 — 이것만은 100%

> **한 문장:** 쿠버네티스의 모든 선언은 조정 루프를 거쳐 결국 리눅스 커널 기능(프로세스, 네임스페이스, cgroup, mount, netfilter)이 되므로, 장애는 "증상 → 가설 → 증거 → 변경 → 재검증"으로 계층을 한 칸씩 내려가며 좁힌다.

1. **계층은 선언자와 실행자와 커널 결과의 사슬이다** — 오브젝트(선언)를 읽고 행동하는 프로그램(컨트롤러, 스케줄러, kubelet, kube-proxy, CNI/CSI 드라이버)이 있고, 그 끝에는 리눅스 프로세스·cgroup·mount·iptables 규칙이 있다. YAML 파일 자체가 컨테이너를 실행하지 않는다.
2. **같은 일의 세 이름** — `docker run --cpus` = `resources.limits.cpu` = cgroup `cpu.max`. 대응표를 외우는 것이 아니라 "이 오브젝트는 결국 어떤 커널 기능인가"를 말할 수 있어야 한다.
3. **선언이 현실이 되는 경로는 둘이다** — 배포 경로(Deployment → ReplicaSet → Pod → scheduler → kubelet → CRI → containerd → runc → 프로세스)와 트래픽 경로(DNS → ClusterIP → 노드의 전달 규칙 → Pod IP, 외부는 Ingress/LB). 각 단계마다 책임 프로그램이 다르다.
4. **진단은 증거 순서다** — 맥락(cluster·namespace·버전)을 고정하고, 계층을 가르는 질문 하나씩 증거로 닫으며, 변경은 한 번에 하나만 한다. 쿠버네티스가 정상이라는 것과 업무가 정상이라는 것은 다른 증거로 평가한다.

## C++·TCP 서버 경험에서 출발하기

| 이미 아는 것 (C++/소켓 서버) | 이 장의 개념 | 같은 점 | ⚠️ 다른 점 (유추가 깨지는 곳) |
|---|---|---|---|
| 장애 시 "클라이언트 → 네트워크 → 소켓 → 스레드 → 로직" 순서로 좁히는 습관 | 계층별 진단 지도 | 가장 바깥에서 안쪽으로 가설을 닫는다 | 쿠버네티스는 중간에 *선언을 읽고 행동하는 프로그램*(컨트롤러, kubelet 등)이 끼어 있어서 "오브젝트에 쓰였다 ≠ 실행됐다"는 단계가 추가된다 |

| 모니터링 대시보드의 CPU/메모리 | Ready Pod 수, CPU, 메모리 | 보조 지표다 | 목표는 요청이 성공하는지이고, `Running`이어도 `Ready`가 아니거나 업무 로직이 틀릴 수 있다 |

### 이 장에서 배우는 것

- 컨테이너 기술 전체를 "선언 → 조정 → 커널 기능"의 사슬로 묶어 보는 법
- Docker 명령 ↔ 쿠버네티스 오브젝트 ↔ 리눅스 커널 기능 대응표
- 배포 경로와 트래픽 경로, 장애 때 누가 고치는가
- 증상별 진단 지도와 증거 순서 원칙

## 코어 1. 계층 지도: 선언자, 실행자, 커널 결과

### 1.1 컨테이너는 결국 리눅스 프로세스다

**한 줄 요약:** 컨테이너 = namespace로 보이는 범위를 좁히고 cgroup으로 사용량을 제한한 프로세스다.

Linux 컨테이너의 핵심은 네 가지다.

| 원리 | 바꾸는 것 | 의미 |
|---|---|---|
| Linux namespaces | 프로세스가 보는 PID·네트워크·마운트 등 | 격리된 환경처럼 보이게 함 ([9장](../2부-컨테이너-커널-기능과-Docker/09-네임스페이스.md)) |
| cgroups | 프로세스 묶음의 CPU·메모리 등 사용 | 자원 사용량 측정·제한 ([10장](../2부-컨테이너-커널-기능과-Docker/10-cgroup.md)) |
| 이미지 레이어와 쓰기 계층 | 실행할 파일들과 변경분 | 이미지 재사용, 변경 분리 ([11장](../2부-컨테이너-커널-기능과-Docker/11-이미지-레이어-overlayfs.md)) |
| capabilities·seccomp 등 | 허용할 특권·시스템 호출 | 격리를 추가로 강화 ([17장](../2부-컨테이너-커널-기능과-Docker/17-컨테이너를-손으로-만들기.md)) |

VM은 별도 게스트 커널을 실행하지만 일반적인 Linux 컨테이너는 **호스트 커널을 공유**한다. 그래서 가볍지만 VM과 같은 격리 경계는 아니다. 이미지는 컨테이너에 통째로 설치한 독립 OS가 아니라, 이미지를 바탕으로 런타임 설정·쓰기 공간·마운트 등을 조합해 실행하는 재료다.

### 1.2 쿠버네티스는 객체 저장소와 계속 움직이는 제어 루프다

**한 줄 요약:** 오브젝트(선언)와 그것을 읽고 행동하는 프로그램은 다르다.

Deployment는 "이미지 A의 Pod를 3개 유지하고 이런 방식으로 업데이트하라"는 *기록*이고, Deployment controller는 그 기록을 읽고 행동하는 *프로그램*이다. 제어 루프는 앱 코드의 오류를 이해해 고치는 것이 아니라 설정한 목표와 관찰 가능한 신호를 기준으로 현재 상태를 목표에 맞춘다([18장](18-클러스터-아키텍처-총론.md)).

| 계층 | 선언(오브젝트) | 실행 주체(프로그램) | 리눅스에서의 결과 |
|---|---|---|---|
| 요청 접수 | 모든 API 객체 | kube-apiserver ([19장](19-kube-apiserver.md)), etcd ([20장](20-etcd.md)) | 파일/네트워크 서버 프로세스 |
| 원하는 개수 유지 | Deployment, ReplicaSet | 컨트롤러 매니저 ([22장](22-컨트롤러-매니저.md)) | 없음 (Pod 객체를 만들 뿐) |
| 배치 | 미배정 Pod | kube-scheduler ([21장](21-kube-scheduler.md)) | 없음 (`nodeName`을 정할 뿐) |
| 실행 | Pod 스펙 | kubelet → CRI → containerd → runc ([23장](23-kubelet과-CRI.md), [12장](../2부-컨테이너-커널-기능과-Docker/12-OCI-표준과-런타임.md)) | clone + namespace + cgroup + mount로 만든 프로세스 |
| 서비스 전달 | Service, EndpointSlice | EndpointSlice 컨트롤러, kube-proxy ([27장](27-Service와-kube-proxy.md)) | iptables/IPVS/nftables 규칙 |
| 이름 해석 | Service 이름 | CoreDNS ([28장](28-CoreDNS-Ingress-NetworkPolicy.md)) | UDP 질의 응답, Pod의 `resolv.conf` |
| 네트워크 | Pod IP | CNI 플러그인 ([26장](26-쿠버네티스-네트워크-모델과-CNI.md)) | netns, veth, bridge/라우팅 |
| 저장 | PVC, PV | CSI 드라이버, kubelet ([29장](29-스토리지.md)) | 디스크 attach, `mount` |

`kubectl apply`의 성공은 **객체 반영 성공**이며 앱 준비 완료가 아니다. 컨트롤러와 스케줄러는 API 서버를 통해 상태를 읽고 쓰며 etcd를 직접 조작하지 않는다.

> **[보충]** 위 표의 "리눅스에서의 결과" 열은 각 장에서 다룬 구성 요소를 한 줄로 요약한 것이다. 세부는 해당 장을 본다.

### 1.3 계층 경계를 구분하는 습관

**한 줄 요약:** 관리 API 경로와 앱 요청 경로는 다른 입구이고, 네트워크·IAM·RBAC도 서로 다른 경계다.

| 호출자와 목적 | 요청을 받는 프로그램 | 예시 |
|---|---|---|
| 운영자·배포 도구가 클러스터를 관리 | Kubernetes API Server | Deployment 조회·변경 |
| 사용자가 서비스를 이용 | 로드밸런서/Ingress 뒤의 앱 | `/orders`에 주문 생성 |

같은 HTTPS와 443을 써도 목적지 프로그램과 요청 의미가 다르다. 권한도 세 질문으로 나눈다. 클라우드 자원을 바꿀 수 있는가(클라우드 IAM), 쿠버네티스 객체를 바꿀 수 있는가(API 인증·인가, [30장](30-설정-보안.md)), Pod의 앱이 클라우드 API를 호출할 수 있는가(워크로드 아이덴티티). 네트워크가 열려 있어도 IAM이 거절할 수 있고, IAM이 허용해도 경로가 막혀 있으면 호출할 수 없다.

## 코어 2. Docker 명령 ↔ 쿠버네티스 ↔ 리눅스 대응표

### 2.1 실행과 자원

**한 줄 요약:** 같은 제한이 `--cpus`, `limits.cpu`, `cpu.max`라는 세 이름을 갖는다.

| 하고 싶은 일 | Docker | Kubernetes | Linux 커널 기능 |
|---|---|---|---|
| 이미지로 실행 | `docker run <image>` | Pod의 `containers[].image` (보통 Deployment가 관리) | overlayfs mount + namespace/cgroup을 입힌 프로세스 ([11장](../2부-컨테이너-커널-기능과-Docker/11-이미지-레이어-overlayfs.md), [13장](../2부-컨테이너-커널-기능과-Docker/13-Docker-아키텍처.md)) |
| CPU 상한 | `--cpus="1.5"` | `resources.limits.cpu` | cgroup `cpu.max` (예: `50000 100000` = 100ms마다 50ms) ([10장](../2부-컨테이너-커널-기능과-Docker/10-cgroup.md)) |
| CPU 가중치 | `--cpu-shares=512` | `resources.requests.cpu` (비례) | cgroup `cpu.weight`(v2) / `cpu.shares`(v1). `cpu.shares` 기준 100m → 102, 500m → 512 |
| 메모리 상한 | `--memory=512m` | `resources.limits.memory` | cgroup `memory.max`, 초과 시 cgroup OOM killer가 SIGKILL ([4장](../1부-리눅스-OS-구성-요소/04-메모리.md)) |
| 프로세스 수 상한 | `--pids-limit=100` | (스펙 필드 직접 대응은 이 책 범위 밖) | cgroup `pids.max` |
| OOM 확인 | `docker inspect <c>`의 `State.OOMKilled` 필드 | `lastState`의 `OOMKilled`, `exitCode 137` ([25장](25-Pod-생명주기와-리소스.md)) | 종료 코드 137 = 128+9(SIGKILL). `dmesg -T \| grep -i oom` |
| 먼저 죽는 순서 | (대응 없음) | QoS class (Guaranteed/Burstable/BestEffort) | `oom_score_adj`: Guaranteed -997, Burstable 2&#126;999, BestEffort 1000 |
| 임시 쓰기 공간 | `--tmpfs`, 컨테이너 쓰기 레이어 | `emptyDir` (`medium: Memory`면 tmpfs) | overlayfs upperdir / tmpfs ([14장](../2부-컨테이너-커널-기능과-Docker/14-볼륨-바인드마운트-tmpfs.md), [29장](29-스토리지.md)) |

CPU와 메모리는 근본적으로 다르다. CPU는 **압축 가능**해서 초과하면 스로틀링(대기)되고 응답 지연으로 나타나며, 메모리는 **압축 불가**여서 초과하면 죽는다(`exitCode 137`, `OOMKilled`). `cpu.max`는 평균이 아니라 **매 100ms 주기**마다 적용되어, 스레드 4개가 각 30ms씩 일하면(총 120ms) CPU 사용률이 100%가 아니어도 지연이 생긴다. `nr_throttled / nr_periods`가 스로틀링 비율이며 높으면(5&#126;10%를 넘으면) limits를 올리거나 스레드 수를 쿼터에 맞춘다.

### 2.2 네트워크, 저장, 설정

**한 줄 요약:** 포트 공개는 DNAT 규칙, 볼륨은 mount, 설정은 환경변수 또는 파일이다.

| 하고 싶은 일 | Docker | Kubernetes | Linux 커널 기능 |
|---|---|---|---|
| 포트 공개 | `-p 8080:80` | Service (NodePort/LoadBalancer), 외부 HTTP는 Ingress/Gateway ([27장](27-Service와-kube-proxy.md), [28장](28-CoreDNS-Ingress-NetworkPolicy.md)) | iptables `nat` 테이블의 DNAT (`DOCKER` 체인) / kube-proxy의 iptables·IPVS·nftables 규칙 ([16장](../2부-컨테이너-커널-기능과-Docker/16-Docker-네트워크.md)) |
| 네트워크 연결 | `docker network create/connect` (CNM, bridge 드라이버) | CNI 플러그인이 Pod에 인터페이스·IP·경로를 설정 ([26장](26-쿠버네티스-네트워크-모델과-CNI.md)) | 네트워크 네임스페이스 + veth pair + bridge/라우팅 |
| 이름으로 호출 | 사용자 정의 네트워크의 내장 DNS | CoreDNS + Service, Pod의 `resolv.conf` ([28장](28-CoreDNS-Ingress-NetworkPolicy.md)) | UDP 53 질의, `/etc/resolv.conf`의 search/ndots |
| 볼륨 | `-v`, `docker volume create` | PVC → PV → CSI ([29장](29-스토리지.md)) | `mount`, bind mount ([14장](../2부-컨테이너-커널-기능과-Docker/14-볼륨-바인드마운트-tmpfs.md)) |
| 환경변수 | `-e`, `--env-file` | ConfigMap/Secret의 `env`/`envFrom` ([30장](30-설정-보안.md)) | 프로세스 `environ` (시작 시 고정) |
| 설정 파일 | `-v`로 마운트 | ConfigMap/Secret 볼륨 (`..data` 심볼릭 링크 교체) | bind mount, `rename` 원자성 |
| 최소 권한 | `--cap-drop`, `--read-only`, `--user`, `--privileged` | `securityContext` ([30장](30-설정-보안.md)) | capabilities, `no_new_privs`, seccomp, uid ([17장](../2부-컨테이너-커널-기능과-Docker/17-컨테이너를-손으로-만들기.md)) |

Pod 안의 컨테이너는 같은 노드에서 실행되며 **네트워크 네임스페이스와 IP·포트 공간을 공유**하므로 서로 `localhost`로 통신한다. 볼륨은 선언하고 각각 마운트해야 공유되며 파일시스템 전체가 자동으로 합쳐지지는 않는다.

### 2.3 종료, 접속, 관찰

**한 줄 요약:** 종료는 SIGTERM → 유예 → SIGKILL이고, `exec`는 네임스페이스 진입이다.

| 하고 싶은 일 | Docker | Kubernetes | Linux 커널 기능 |
|---|---|---|---|
| 정상 종료 | `docker stop` (SIGTERM 후 10초 뒤 SIGKILL) | Pod 삭제: preStop → SIGTERM → `terminationGracePeriodSeconds`(기본 30초) → SIGKILL ([25장](25-Pod-생명주기와-리소스.md)) | 시그널 15 → 9. `SIGKILL`은 잡을 수 없다 ([3장](../1부-리눅스-OS-구성-요소/03-시그널.md)) |
| PID 1 함정 | 핸들러 없는 서버는 `docker stop`에 10초 무반응 | `sh`가 PID 1이면 SIGTERM이 자식에 안 가고 30초 후 137 | PID 1은 핸들러 없는 시그널을 커널이 무시 ([3장](../1부-리눅스-OS-구성-요소/03-시그널.md)) |
| 컨테이너 안에서 명령 | `docker exec` | `kubectl exec` | `setns()`로 네임스페이스에 합류 ([9장](../2부-컨테이너-커널-기능과-Docker/09-네임스페이스.md)) |
| 호스트에서 컨테이너 네임스페이스로 | `docker inspect`의 `State.Pid`로 호스트 PID를 얻고 `nsenter --target <PID> --net -- ip addr` | `kubectl debug` 또는 노드에서 `nsenter` | `/proc/<pid>/ns/*` |
| 컨테이너 런타임 직접 조회 | `ctr -n moby containers list` | `crictl ps -a`, `crictl pods` ([23장](23-kubelet과-CRI.md)) | containerd 소켓 ([13장](../2부-컨테이너-커널-기능과-Docker/13-Docker-아키텍처.md)) |

`docker ps`로 보이는 컨테이너와 `ctr -n moby containers list`로 보이는 컨테이너가 같은 대상이다.

> **게임 서버 유추:** 대응표는 "같은 `connect()`가 라이브러리·시스템 콜·커널 소켓 구현에서 서로 다른 이름을 갖는 것"과 같다. ⚠️ 그러나 쿠버네티스 쪽 이름은 *선언*이므로, 이름이 있다고 해서 지금 그 커널 기능이 실제로 존재하는 것은 아니다. 조정이 끝났는지 증거로 확인해야 한다.

## 코어 3. 선언이 현실이 되는 두 경로

### 3.1 배포 경로

**한 줄 요약:** API 서버가 기록하고, 컨트롤러가 객체를 만들고, 스케줄러가 노드를 정하고, kubelet/runtime이 프로세스를 띄운다.

```
Deployment 반영 (배포 도구 → API 서버)
  → 컨트롤러가 관찰 후 ReplicaSet과 Pod 객체 생성
  → 스케줄러가 미배정 Pod를 노드에 배정 (nodeName)
  → 해당 노드의 kubelet이 자기 노드의 Pod를 확인
  → kubelet이 CRI로 containerd에 실행 요청
  → containerd가 필요 이미지를 pull, Pod sandbox 네트워크와 컨테이너 준비
  → OCI 런타임(runc)이 리눅스 프로세스를 실행
  → kubelet이 상태와 readiness를 API 서버에 반영
```

핵심은 **스케줄러가 직접 이미지를 실행하지 않고, 노드의 kubelet과 runtime이 실행을 맡는다**는 점이다. Docker로 빌드한 이미지가 Docker Engine 없이 돌 수 있는 것도 이 분리 때문이다. Dockerfile은 빌드 입력이고 이미지는 결과이며, 이미지를 만드는 도구와 읽는 도구가 달라도 된다(OCI 표준, [12장](../2부-컨테이너-커널-기능과-Docker/12-OCI-표준과-런타임.md)). CRI는 프로그램이 아니라 kubelet과 containerd 사이의 API 약속이고, runc는 OCI 런타임 규격의 구현체다. 

### 3.2 트래픽 경로

**한 줄 요약:** 이름 조회와 연결은 별개이고, Service는 별도의 서버 프로세스가 아니라 커널의 전달 규칙이다.

```
① DNS 조회: payments → (resolv.conf) → CoreDNS가 ClusterIP 응답
② 연결: Pod → ClusterIP:port → 노드의 Service 전달 규칙(kube-proxy가 구성한 iptables/IPVS) → 선택된 Pod IP:targetPort
외부: 사용자 → LB/Ingress 컨트롤러 → (IP target이면) Pod IP 직접
```

Pod가 교체되어도 Service 객체가 유지되는 동안 호출자는 같은 이름·ClusterIP를 쓴다. 뒤의 Pod A가 사라지고 같은 라벨의 Pod B가 준비되면 EndpointSlice 컨트롤러가 대상 목록을 갱신하고 kube-proxy 등이 전달 규칙을 갱신한다. `80 → 8080`은 포트 연결이고, IP 변경에 대응하는 것은 대상 주소의 갱신이다. 변경 반영에는 시간이 걸리고 이미 죽은 Pod의 TCP 연결이 새 Pod로 자동 이전되지는 않는다. IngressController, 로드밸런서 컨트롤러는 *설정을 바꾸는 관리자*이며 사용자 요청마다 거치지 않는다. API 서버도 일반 앱 요청의 중간 프록시가 아니다(`kubectl port-forward` 같은 관리·디버깅 경로는 예외).

| 설정상 관계 | 실제 패킷 경로 |
|---|---|
| `Ingress → Service → Pod 집합` | ALB IP target이면 `ALB → Pod IP` (Service 객체는 대상 발견·포트 설정에 쓰이지만 패킷이 반드시 ClusterIP를 지나지는 않음) |
| 내부 ClusterIP 접근 | `호출 Pod → Service IP → 전달 규칙 → 대상 Pod` |
| ALB Instance target | `ALB → Node IP:NodePort → Service 전달 규칙 → Pod` |

### 3.3 장애가 나면 누가 고치는가

**한 줄 요약:** "복구된다"는 설정한 목표에 도달하도록 다시 시도한다는 뜻이고, 용량·IP·권한·이미지·스토리지 문제가 남으면 도달하지 못한다.

| 사건 | 주로 반응하는 주체 | 한계 또는 추가 확인 |
|---|---|---|
| Pod 안의 앱 프로세스 종료 | kubelet/runtime, restart policy | 같은 오류가 반복되면 CrashLoopBackOff, 앱 수정 필요 |
| ReplicaSet 소속 Pod 삭제 | ReplicaSet 컨트롤러가 새 Pod 생성 | 원래 Pod가 되살아나는 것이 아님 |
| 노드 장애 | 상태 감지·퇴거 과정과 워크로드 컨트롤러가 대체 Pod 생성, 스케줄러가 배치 | 감지 지연, 여유 노드, 볼륨·네트워크 제약 |
| EC2 인스턴스 교체 필요 | 설정된 Node Group/Auto Scaling 기능 | Pod 복제와는 별도 계층 |
| CPU 수요 증가 | 구성한 HPA가 Pod 수 조정 | 노드를 직접 생성하지 않음 |
| Pod가 들어갈 노드 부족 | Cluster Autoscaler·Karpenter 등 | 설치·권한·정책·할당량 필요 |

## 코어 4. 증상에서 증거를 따라가는 진단 지도

### 4.1 원칙: 맥락을 고정하고 증거를 순서대로

**한 줄 요약:** 증상 → 가설 → 확인할 증거 → 변경 → 재검증, 변경은 한 번에 하나만.

목표는 사용자의 요청이 성공하는지 확인하는 것이다. CPU나 Ready Pod 수는 원인을 설명하는 보조 지표다. 증거는 세 종류다. **Metrics**는 지연·오류율·포화도, **Logs**는 특정 사건의 맥락, **Traces**는 여러 서비스에 걸친 한 요청의 경로다. 쿠버네티스 Events는 스케줄링·이미지·마운트 등 변화의 원인을 찾는 데 유용하지만 장기 감사 기록이나 모든 앱 로그를 대신하지 않는다.

먼저 맥락을 고정한다. 잘못된 context에서 정상인 앱을 조사하거나 새 버전 문제에 이전 Pod 로그를 읽는 실수를 줄이기 위해 "어느 cluster·Namespace·앱 버전·시간대인가"를 정하고, 최근 배포 digest와 Git commit을 함께 기록한다. 아래 조회 명령은 자원을 바꾸지 않는다.

```bash
kubectl config current-context
kubectl get nodes -o wide
kubectl get deploy,rs,pods,svc,endpointslices -n study -o wide
kubectl get events -n study --sort-by=.metadata.creationTimestamp
kubectl describe pod <pod> -n study
kubectl logs <pod> -n study -c api --tail=100
kubectl logs <pod> -n study -c api --previous --tail=100     # 직전 종료 컨테이너 (남아 있을 때만)
```

장애 중 변경을 여러 개 한꺼번에 하면 원인과 효과를 분리하기 어렵다. 복구 조치는 증거에 따라 이전 이미지로 되돌리거나 잘못된 설정을 수정하는 방식으로 고르고, DB 변경이 포함되었으면 이미지 롤백만으로 충분한지 먼저 판단한다.

### 4.2 Pod가 실행되기까지의 증상 지도

**한 줄 요약:** 증상이 *어느 단계에서 멈췄는지*를 말해 준다.

| 관찰한 현상 | 먼저 분리할 질문 | 확인 대상 | 바로 하면 안 맞을 수 있는 대응 |
|---|---|---|---|
| `kubectl`이 연결되지 않음 | 앱 장애인가, 관리 API 접근 문제인가? | kubeconfig, 인증·인가, API endpoint 경로 | 앱 재배포 |
| Pod가 생성되지 않음 | ReplicaSet 생성 실패, Quota, admission | Deployment/RS Events, quota | 노드 추가만 하기 |
| `Pending`, nodeName 없음 | 노드가 정해졌는가? | `FailedScheduling` 메시지, requests, taints, affinity, 노드 용량, PVC ([21장](21-kube-scheduler.md)) | 이미지 다시 빌드 |
| 노드 배정 후 `ContainerCreating`에서 멈춤 | 실행 준비 중 무엇이 실패했나? | CNI/IP, 볼륨 mount, sandbox Events ([26장](26-쿠버네티스-네트워크-모델과-CNI.md), [29장](29-스토리지.md)) | replicas를 더 늘리기 |
| `ImagePullBackOff` | 이미지가 존재하고 가져올 수 있나? | 이미지 경로·digest, 레지스트리 권한, DNS·네트워크 | CI push 권한만 수정 |
| `CrashLoopBackOff` | 왜 프로세스가 종료되나? | 이전 컨테이너 로그, 종료 코드, 설정, OOMKilled | 무조건 limit 늘리기 |
| `OOMKilled` (137) | 메모리 한계·사용 패턴 | `lastState`, limit, 메모리 추이 | liveness만 느슨하게 하기 |
| `Running`이지만 Ready 아님 | 요청 받을 준비가 됐나? | readiness 응답, 포트, 의존 서비스 ([25장](25-Pod-생명주기와-리소스.md)) | phase만 보고 정상 선언 |
| `PVC Pending` | class·driver·권한·바인딩 대기 | PVC Events, 소비 Pod, StorageClass ([29장](29-스토리지.md)) | 데이터 손상으로 단정 |
| API `403 Forbidden` | 허용 작업 부족 | 현재 신원, RBAC (`kubectl auth can-i`) ([30장](30-설정-보안.md)) | 네트워크를 public으로 열기 |
| API timeout | endpoint 도달 경로 | DNS·route·방화벽·접속 위치 | cluster-admin만 부여하기 |

표는 시작 가설이지 확정 진단이 아니다. 예를 들어 exit code 137만으로 항상 메모리 limit 초과라고 단정하지 않고 종료 reason, 커널·노드 상태와 함께 판단한다. `Pending`만 보고 무조건 노드를 늘리지 않는다. 이미 노드에 배정되었는지와 Events를 먼저 본다.

### 4.3 네트워크 증상 지도

**한 줄 요약:** 내부 호출 실패와 외부 호출 실패는 의심 계층이 다르다.

| 관찰한 현상 | 우선 분리할 질문 | 확인 대상 |
|---|---|---|
| 앱은 Ready인데 외부 요청 실패 | 로드밸런서까지와 그 이후 중 어디인가? | DNS, listener/rule, target health, 보안 그룹, 대상 포트 ([28장](28-CoreDNS-Ingress-NetworkPolicy.md)) |
| 내부 Service 연결 실패 | 대상 발견과 전달 중 어디인가? | selector, EndpointSlice, DNS, CNI, 전달 규칙, NetworkPolicy ([27장](27-Service와-kube-proxy.md), [28장](28-CoreDNS-Ingress-NetworkPolicy.md)) |
| Ingress `503` / `502` / `504` | 엔드포인트 / 백엔드 응답 / 백엔드 지연 | EndpointSlice, 포트, readiness ([28장](28-CoreDNS-Ingress-NetworkPolicy.md)) |
| 모든 DNS 실패 | CoreDNS Pod와 `kube-dns` EndpointSlice | 정상이면 Pod의 `resolv.conf` → ClusterIP 직접 질의 ([28장](28-CoreDNS-Ingress-NetworkPolicy.md)) |
| 다른 노드의 Pod와만 통신 실패 | CNI 오버레이/라우팅 | `/etc/cni/net.d/*`, 노드 간 경로 ([26장](26-쿠버네티스-네트워크-모델과-CNI.md)) |
| 정책 적용 뒤 전부 막힘 | NetworkPolicy가 DNS까지 막았나 | egress 기본 거부 + DNS(53) 예외 ([28장](28-CoreDNS-Ingress-NetworkPolicy.md)) |
| conntrack 의심 | 테이블 고갈·경쟁 조건 | `conntrack -C`, `conntrack -S` ([27장](27-Service와-kube-proxy.md)) |

연결 실패의 큰 흐름은 다음 순서로 좁힌다.

```
Pod A → Service/Pod B 연결 실패
  ├─ DNS 문제인가?              → resolv.conf, CoreDNS, kube-dns
  ├─ 같은 노드인가, 다른 노드인가? → 다른 노드면 CNI 오버레이/라우팅 확인
  ├─ Service 경유인가?           → EndpointSlice / kube-proxy 규칙
  ├─ NetworkPolicy가 걸려 있는가? → kubectl get networkpolicy -A
  └─ conntrack/포트 고갈인가?     → conntrack -C, -S (노드 리소스 문제)
```

### 4.4 쿠버네티스 밑의 리눅스로 내려가기

**한 줄 요약:** 오브젝트가 아무것도 말해 주지 않으면 노드와 컨테이너 안에서 `/proc`, cgroup, `ss`로 증거를 얻는다.

컨테이너는 같은 커널 위의 프로세스이므로 1부의 도구가 그대로 통한다([8장](../1부-리눅스-OS-구성-요소/08-진단-도구.md)). 최소 이미지에는 `top`/`ps`가 없을 수 있지만 `/proc`은 항상 있다.

| 증상 | 첫 명령 | 다음 |
|---|---|---|
| 컨테이너가 갑자기 죽었다 | `dmesg -T \| grep -iE 'oom\|segfault\|killed'`, 종료 코드 | 137이면 메모리, 139면 코어 덤프 분석 |
| 컨테이너가 느리다/지연이 튄다 | `cat /sys/fs/cgroup/cpu.stat`의 `nr_throttled` | 스레드 수 vs CPU 쿼터 ([10장](../2부-컨테이너-커널-기능과-Docker/10-cgroup.md), [7장](../1부-리눅스-OS-구성-요소/07-스레드와-동시성.md)) |
| CPU는 노는데 load가 높다 | `vmstat 1`의 `b`/`wa`, `ps`의 D 상태 | `iostat -x` ([1장](../1부-리눅스-OS-구성-요소/01-커널-시스템콜-스케줄러.md), [5장](../1부-리눅스-OS-구성-요소/05-파일시스템과-IO.md)) |
| 시작이 안 된다 | `strace -f -e trace=openat,connect,execve` | `ENOENT`/`EACCES`/`ECONNREFUSED`, `ldd` |
| 포트 바인딩 실패 | `ss -tlnp \| grep :PORT` | 점유 프로세스 또는 TIME_WAIT ([6장](../1부-리눅스-OS-구성-요소/06-네트워크-스택.md)) |
| fd가 부족(EMFILE) | `ls /proc/<pid>/fd \| wc -l`, `/proc/<pid>/limits` | fd 누수 추적 |
| 컨테이너 안 네트워크 관찰 | `nsenter -t <pid> -n ss -tanp`, `tcpdump` | `kubectl debug` 임시 컨테이너 |
| 디스크 용량이 안 맞다 | `df -h` vs `du -sh`, `lsof +L1` | 삭제된 열린 파일 ([5장](../1부-리눅스-OS-구성-요소/05-파일시스템과-IO.md)) |

이 표의 "컨테이너가 느리다" 행이 [1장](../1부-리눅스-OS-구성-요소/01-커널-시스템콜-스케줄러.md) 서두의 `--cpus=2` 사례와 같다. 쿠버네티스에서는 `limits.cpu`가 같은 `cpu.max`가 되고 `kubectl exec <pod> -- cat /sys/fs/cgroup/cpu.stat`으로 확인한다.

### 4.5 예제: 배포 뒤 오류가 늘었는데 Pod는 Running이다

**한 줄 요약:** "쿠버네티스 정상"과 "업무 정상"은 다른 증거로 평가한다.

첫째, rollout과 Ready 수를 본다. 새 Pod의 Ready가 false라면 새 버전이 요청을 받을 준비를 못 한 것이다. 둘째, 컨테이너 로그와 readiness 응답을 본다. `/ready`가 404이면 앱 경로와 probe 설정 불일치 가설을 검증한다. 셋째, EndpointSlice에 기존 Ready 대상이 남아 있는지 보고 로드밸런서 target health도 비교한다.

새 Pod가 Ready인데 로드밸런서만 unhealthy라면 조사 경계를 로드밸런서 → Pod로 옮겨 health check path·port와 보안 그룹을 확인한다. 모든 health가 정상인데 결제만 실패한다면 앱 trace·DB·외부 결제 API로 이동한다.

Readiness 실패는 보통 신규 트래픽 대상에서 빼는 신호이고, liveness 실패는 설정한 기준에 따라 컨테이너 재시작을 유도한다. 외부 DB의 짧은 장애를 liveness 실패로 연결하면 많은 앱을 불필요하게 재시작시킬 수 있다. 롤백도 구별한다. Deployment를 이전 이미지로 돌려도 이미 변경한 DB 데이터와 스키마가 자동 복구되지는 않는다.

## 실무 적용

### 체크리스트

- [ ] 컨테이너는 호스트 커널을 공유하는 프로세스이고, namespace(보이는 범위)·cgroup(사용량)·레이어(파일)·capability/seccomp(특권)로 이루어졌음을 설명할 수 있다.
- [ ] 오브젝트(선언)와 그것을 처리하는 프로그램(컨트롤러, 스케줄러, kubelet, kube-proxy, CNI/CSI)을 구분한다. `kubectl apply` 성공은 객체 반영일 뿐이다.
- [ ] `--cpus`/`limits.cpu`/`cpu.max`, `--memory`/`limits.memory`/`memory.max`, `-p`/Service/DNAT 같은 대응을 말할 수 있다.
- [ ] CPU는 스로틀링(지연), 메모리는 OOM(종료)이라는 비대칭을 알고, `cpu.stat`의 `nr_throttled`와 종료 코드 137로 구분한다.
- [ ] 종료는 SIGTERM → 유예 → SIGKILL이며 PID 1 핸들러/`tini` 문제를 점검했다.
- [ ] 장애 시 cluster·Namespace·앱 버전·시간대를 먼저 고정하고, 최근 배포 digest와 commit을 기록한다.
- [ ] 증상을 계층(스케줄링, 실행 준비, 이미지, 프로세스, 준비 상태, 서비스 전달, 외부 경로)으로 분리하고 Events/`describe`부터 본다.
- [ ] 변경은 한 번에 하나만 하고 재검증한다. 이미지 롤백이 DB 변경까지 되돌리지 않음을 안다.
- [ ] 쿠버네티스 지표(Ready 수, CPU)가 정상이어도 사용자 요청 성공률·지연·trace로 업무 정상을 따로 확인한다.

### 시나리오로 확인하기

1. **상황:** 게임 서버를 `limits.cpu: "2"` Pod로 옮겼더니 평균 CPU는 낮은데 틱 지연이 주기적으로 튄다.
   **질문:** Docker, 쿠버네티스, 리눅스 용어로 각각 무엇이고 어떻게 확인하나?

   <details markdown="1"><summary>답 확인</summary>

   Docker의 `--cpus=2`, 쿠버네티스의 `limits.cpu`는 모두 cgroup의 `cpu.max`(100ms마다 200ms 쿼터)다. 스레드가 많으면 쿼터를 몇 ms 만에 소진하고 그 주기의 나머지 동안 컨테이너 전체가 스로틀링된다. `kubectl exec <pod> -- cat /sys/fs/cgroup/cpu.stat`에서 `nr_throttled / nr_periods`가 5&#126;10%를 넘는지 보고, limits를 올리거나 스레드 풀 크기를 쿼터에 맞춘다. → 코어 2.1, 코어 4.4

   </details>

2. **상황:** 새 버전 배포 뒤 `kubectl get pods`는 전부 `Running`인데 사용자 오류율이 올랐다.
   **질문:** 무엇을 순서대로 보나?

   <details markdown="1"><summary>답 확인</summary>

   `Running`은 프로세스가 떠 있다는 뜻일 뿐이다. rollout과 Ready 수를 보고, Ready가 false면 로그와 readiness 응답(예: `/ready` 경로 불일치)을 본다. EndpointSlice에 기존 Ready 대상이 남아 있는지, 로드밸런서 target health가 어떤지 비교한다. 모두 정상이면 trace·DB·외부 API 등 업무 계층으로 이동한다. 변경은 하나씩 하며, 롤백이 DB 스키마까지 되돌리지는 않는다는 점을 고려한다. → 코어 4.5

   </details>

3. **상황:** 외부 사용자만 접속이 안 되고 클러스터 안에서 같은 Service를 호출하면 정상이다.
   **질문:** 어느 계층을 의심하고 어떤 순서로 보나?

   <details markdown="1"><summary>답 확인</summary>

   내부 경로(ClusterIP → Pod)는 정상이므로 앱·EndpointSlice·kube-proxy는 제외되고, 클러스터 밖에서 들어오는 입구를 의심한다. DNS(도메인 → LB 주소), 로드밸런서 listener/rule과 target health, 보안 그룹, 대상 포트, Ingress 컨트롤러 설정(ADDRESS, ingressClassName, 404/502/503/504)을 순서대로 확인한다. → 코어 4.3

   </details>

### 2. 인출 질문

1. `kubectl apply`가 성공했다는 것은 무엇을 뜻하고 무엇을 뜻하지 않는가?

   <details markdown="1"><summary>답 확인</summary>

   API 서버에 객체가 반영(저장)되었다는 뜻이다. 앱이 준비되었다는 뜻은 아니다. 그 뒤에 컨트롤러가 객체를 만들고, 스케줄러가 노드를 정하고, kubelet/runtime이 프로세스를 띄우고, readiness를 통과해야 실제로 요청을 받는다. → 코어 1.2, 코어 3.1

   </details>

2. `limits.memory`를 초과하면 무슨 일이 생기고 어떻게 확인하는가? CPU 초과와는 어떻게 다른가?

   <details markdown="1"><summary>답 확인</summary>

   cgroup `memory.max`를 넘으면 cgroup OOM killer가 SIGKILL을 보내 컨테이너가 죽고 `exitCode 137`, `OOMKilled`가 기록된다(`docker inspect`의 `State.OOMKilled`, 쿠버네티스 `lastState`). CPU는 압축 가능해서 초과하면 스로틀링되어 지연으로 나타나고, 메모리는 압축 불가라 죽는다. → 코어 2.1

   </details>

3. `docker stop`과 Pod 삭제의 종료 시퀀스를 비교하고, PID 1 함정을 설명하라.

   <details markdown="1"><summary>답 확인</summary>

   `docker stop`은 SIGTERM을 보내고 10초 뒤 SIGKILL, Pod 삭제는 preStop 완료 후 SIGTERM을 보내고 `terminationGracePeriodSeconds`(기본 30초) 뒤 SIGKILL이다. PID 1은 핸들러 없는 시그널을 커널이 무시하므로 핸들러 없는 서버는 유예 시간 동안 무반응하다가 137로 죽는다. `sh`가 PID 1이면 SIGTERM이 자식에게 전달되지 않는다. → 코어 2.3

   </details>

4. 배포 경로에서 스케줄러, kubelet, containerd, runc는 각각 무엇을 하는가?

   <details markdown="1"><summary>답 확인</summary>

   스케줄러는 미배정 Pod의 노드만 정한다(이미지를 실행하지 않음). kubelet은 자기 노드에 할당된 Pod의 실행·상태 보고를 관리하며 CRI로 containerd에 요청한다. containerd는 이미지 pull과 sandbox/컨테이너 준비를 하고, runc(OCI 런타임 구현체)가 리눅스 프로세스를 실제로 실행한다. → 코어 3.1

   </details>

5. Pod A가 Pod B로 교체될 때 Service의 ClusterIP는 유지되고 무엇이 바뀌는가?

   <details markdown="1"><summary>답 확인</summary>

   Service 객체가 유지되는 동안 이름과 ClusterIP는 그대로다. EndpointSlice 컨트롤러가 대상 목록을 갱신하고 kube-proxy 등이 전달 규칙을 갱신해 뒤의 목적지만 바뀐다. 반영에 시간이 걸리고 죽은 Pod의 TCP 연결이 새 Pod로 이전되지는 않는다. → 코어 3.2

   </details>

6. `Pending`, `ContainerCreating`, `ImagePullBackOff`, `CrashLoopBackOff`, `Running`이지만 Ready 아님은 각각 어느 단계의 증상인가?

   <details markdown="1"><summary>답 확인</summary>

   `Pending`(노드 미배정): 스케줄링 조건(requests, taints, affinity, PVC). `ContainerCreating`(배정 후): CNI/IP, 볼륨 mount, sandbox. `ImagePullBackOff`: 이미지 경로·권한·네트워크. `CrashLoopBackOff`: 프로세스 종료 원인(이전 로그, 종료 코드, 설정, OOM). Running but not Ready: readiness 응답, 포트, 의존 서비스. → 코어 4.2

   </details>

### 3. 기억 고리

- **C++ 유추:** 장애 시 "네트워크 → 소켓 → 스레드 → 로직" 순 좁히기 = 계층 진단 ⚠️ 쿠버네티스에는 *선언을 읽고 행동하는 프로그램*이 끼어 있어서 "오브젝트에 있다 ≠ 실제로 일어났다"를 증거로 확인해야 한다.
- **C++ 유추:** 같은 `connect()`를 라이브러리·시스템 콜·커널 구현이 다르게 부르는 것 = Docker·K8s·Linux 대응표 ⚠️ 쿠버네티스 이름은 선언이다.
- **비유:** 계층 지도 = 건물 층별 안내도(선언 서류층 → 담당 직원층 → 실제 설비층). ⚠️ 비유가 깨지는 지점: 건물과 달리 담당 직원(컨트롤러)이 쉬지 않고 서류와 설비를 계속 맞추려 하므로, 설비를 손으로 고쳐도 서류대로 되돌려질 수 있다.
- **비유:** 증거 순서 진단 = 의사의 문진 → 검사 → 처방 → 재진. ⚠️ 비유가 깨지는 지점: 한 번에 여러 처방을 내리면 무엇이 효과를 냈는지 알 수 없는 것은 같지만, 클러스터에서는 변경 하나가 다른 컨트롤러의 조정을 일으킬 수 있다.
- **묶음(3의 법칙):** 컨테이너 3축(namespace·cgroup·레이어) / 증거 3종(Metrics·Logs·Traces) / 같은 일의 세 이름(Docker·K8s·Linux) / 이 장 첫머리의 실무 상황 3개.
- **대칭·순서:** CPU(스로틀링, 지연) ↔ 메모리(OOM, 종료), 선언(오브젝트) ↔ 실행(프로그램) ↔ 결과(커널), 배포 경로 ↔ 트래픽 경로, 쿠버네티스 정상 ↔ 업무 정상. 진단 순서: 맥락 고정 → 증상 분리 → 증거 → 변경 1개 → 재검증.
