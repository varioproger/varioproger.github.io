# 29장. 스토리지

> **🎮 게임 서버 개발자에게** — 월드 스냅샷을 `fwrite`/`fsync`로 디스크에 쓰고, 로그를 파일로 남기고, 재시작하면 그 파일에서 상태를 복구해 본 적이 있다면 이 장의 문제의식은 이미 안다. 새로운 점은 컨테이너의 쓰기 공간(overlayfs의 upperdir, [11장](../2부-컨테이너-커널-기능과-Docker/11-이미지-레이어-overlayfs.md))이 **컨테이너와 함께 사라진다**는 것, 그리고 Pod가 어느 노드에 뜰지 스케줄러가 정하기 때문에 "그 디스크가 어디에 있느냐"가 스케줄링 제약이 된다는 것이다. 그래서 쿠버네티스는 스토리지를 요구하는 쪽(PVC)과 제공하는 쪽(PV, StorageClass)으로 갈라 두었고, 실제 연결은 kubelet이 **리눅스 `mount`**로 한다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 게임 서버 Pod를 재배포했더니 컨테이너 안에 쓰던 세이브/로그 파일이 통째로 사라졌다.
> - 새 DB Pod가 영원히 `Pending`이고, 이벤트에는 볼륨 때문에 스케줄할 수 없다고 나온다.
> - 실수로 PVC를 지웠더니 클라우드 디스크까지 같이 삭제되어 데이터가 없어졌다.

## 코어 — 이것만은 100%

> **한 문장:** 컨테이너 파일은 휘발성이므로 오래 살아야 하는 데이터는 PVC로 요청하고, StorageClass의 프로비저너(CSI 드라이버)가 PV를 만들어 1:1로 바인딩하며, 최종적으로 kubelet이 그 볼륨을 노드에 마운트해 컨테이너의 `mountPath`로 보이게 한다.

1. **수명 기준으로 세 부류로 나눈다** — 임시(`emptyDir`: 컨테이너 재시작에는 살고 Pod 삭제에는 사라짐), 설정 주입(`configMap`/`secret`), 영구(`persistentVolumeClaim`). `hostPath`는 시스템 컴포넌트가 아니면 쓰지 않는다.
2. **PVC(요청) ↔ PV(실물) ↔ StorageClass(종류)** — 개발자는 PVC만 쓴다. 바인딩은 1:1이고 배타적이며, 맞는 PV가 없으면 StorageClass의 프로비저너가 동적으로 만든다. `WaitForFirstConsumer`로 Pod의 노드가 정해진 뒤 볼륨을 만든다.
3. **접근 모드·회수 정책·확장을 의식적으로 고른다** — RWO는 "하나의 노드"이지 "하나의 Pod"가 아니다. 동적 프로비저닝 기본 회수 정책은 `Delete`라서 PVC를 지우면 실제 디스크까지 사라진다. 확장은 늘리기만 된다.
4. **CSI = 스토리지 드라이버를 클러스터 밖으로 분리한 gRPC 표준** — 컨트롤러 플러그인(생성/연결)과 노드 플러그인(마운트)으로 나뉜다. 마운트는 `NodeStageVolume`(노드 전역 경로에 한 번) → `NodePublishVolume`(Pod 경로로 바인드 마운트) 두 단계다. 스냅샷은 애플리케이션 백업이 아니다.

## 코어 1. 수명으로 나눈 세 가지 스토리지

### 1.1 왜 레이어 밖으로 나가야 하는가

**한 줄 요약:** overlayfs의 upperdir은 컨테이너와 함께 사라지고, 이 장은 그 레이어 구조 밖으로 나가는 방법이다.

컨테이너의 파일 시스템 변경은 휘발성이다([11장](../2부-컨테이너-커널-기능과-Docker/11-이미지-레이어-overlayfs.md)). `emptyDir`로 컨테이너 간 파일을 공유할 수 있지만 그것도 Pod가 삭제되면 없어진다. 오래 살아야 하는 데이터는 Pod 수명과 분리된 곳에 두어야 한다.

### 1.2 세 유형

**한 줄 요약:** 임시 스크래치 / 설정·시크릿 주입 / 영구 데이터 — 이 분류를 먼저 하면 선택이 쉽다.

| 유형 | 수명 | 공유 범위 | 볼륨 타입 |
|---|---|---|---|
| ① 임시 스크래치 | Pod와 동일 | 같은 Pod 내 컨테이너 | `emptyDir` |
| ② 설정·시크릿 주입 | Pod와 동일 (내용은 외부에서 관리) | 같은 Pod | `configMap`, `secret`, `downwardAPI`, `projected` |
| ③ 영구 데이터 | Pod보다 오래 | Pod를 넘어 유지 | `persistentVolumeClaim` |

②는 30장에서 다루고, 이 장의 주제는 ③이다.

```yaml
volumes:
  # 디스크 기반 스크래치
  - name: scratch
    emptyDir:
      sizeLimit: 1Gi

  # 메모리 기반 (tmpfs) — 빠르지만 컨테이너 메모리 한도를 소비한다
  - name: cache
    emptyDir:
      medium: Memory
      sizeLimit: 256Mi
```

`emptyDir`은 **컨테이너 재시작에는 살아남지만 Pod 삭제에는 사라진다.** `medium: Memory`로 tmpfs에 쓴 데이터는 컨테이너의 메모리 사용량에 포함되므로 1GB를 쓰면 `limits.memory`에서 1GB가 차감되고, 초과하면 `OOMKilled`다([25장](25-Pod-생명주기와-리소스.md)).

쓰기 공간이 PVC의 기능(동적 프로비저닝, 특정 StorageClass)이 필요하지만 수명은 Pod와 같아야 하면 `generic ephemeral volume`(`ephemeral.volumeClaimTemplate`, v1.23+ GA)을 쓴다. Pod가 삭제되면 볼륨도 자동 삭제된다.

### 1.3 hostPath를 쓰지 말아야 하는 이유

**한 줄 요약:** 스케줄링과 데이터가 분리되고, 노드 파일 시스템 접근은 보안 위험이다.

`hostPath`는 노드의 파일 시스템을 직접 마운트한다. Pod가 다른 노드로 가면 데이터가 없고, 노드가 죽으면 데이터도 죽으며, `/`를 마운트하면 노드를 장악할 수 있다([30장](30-설정-보안.md)). 정당한 용도는 DaemonSet으로 도는 로그 수집기(`/var/log/pods`)나 모니터링 에이전트(`/proc`) 같은 시스템 컴포넌트뿐이다. 로컬 디스크의 성능이 필요하면 **Local PersistentVolume**을 쓴다. 노드 어피니티가 자동으로 붙어 Pod가 데이터가 있는 노드로 스케줄된다.

> **게임 서버 유추:** `hostPath`는 서버 장비의 특정 경로를 직접 열어 쓰는 것과 같다. ⚠️ 서버 한 대에 고정된 프로세스라면 문제없지만, Pod는 어느 노드로든 옮겨 다닐 수 있어서 "그 경로"가 보장되지 않는다.

## 코어 2. PVC ↔ PV ↔ StorageClass

### 2.1 요구하는 쪽과 제공하는 쪽의 분리

**한 줄 요약:** 개발자는 PVC로 요청하고, 운영자(또는 프로비저너)가 PV와 StorageClass로 제공한다.

| 리소스 | 스코프 | 누가 만드는가 | 의미 |
|---|---|---|---|
| PersistentVolume (PV) | 클러스터 | 운영자 또는 프로비저너 | 실제 스토리지 조각 |
| PersistentVolumeClaim (PVC) | 네임스페이스 | 개발자 | 스토리지 요청 |
| StorageClass (SC) | 클러스터 | 운영자 | 스토리지 "종류"의 정의 |

PVC는 소비자의 요구, PV는 공급된 저장소의 쿠버네티스 표현이다. EBS라는 실제 디스크와 PV라는 API 오브젝트는 다른 것이다.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: standard        # 생략하면 기본 StorageClass
  resources:
    requests:
      storage: 10Gi
```

Pod에서는 `volumes`에 `persistentVolumeClaim.claimName`을 적고 `volumeMounts`로 `mountPath`에 마운트한다.

### 2.2 PV와 StorageClass 안쪽

**한 줄 요약:** PV에는 드라이버·볼륨 ID·노드 어피니티가 있고, StorageClass에는 프로비저너·파라미터·정책이 있다.

```yaml
# PV (시스템이 만든다) — 핵심 필드만
spec:
  capacity: { storage: 10Gi }
  accessModes: [ReadWriteOnce]
  persistentVolumeReclaimPolicy: Delete
  storageClassName: standard
  csi: { driver: ebs.csi.aws.com, volumeHandle: vol-0abc123def456, fsType: ext4 }
  nodeAffinity: ...                 # 이 볼륨에 접근 가능한 노드 (예: topology.ebs.csi.aws.com/zone In [ap-northeast-2a])
---
# StorageClass (스토리지의 "종류") — 핵심 필드만
provisioner: ebs.csi.aws.com
parameters: { type: gp3, iops: "6000", encrypted: "true" }   # 프로비저너별로 다름
reclaimPolicy: Delete               # 또는 Retain
allowVolumeExpansion: true          # 나중에 늘릴 수 있는가
volumeBindingMode: WaitForFirstConsumer
```

**PV의 `nodeAffinity`가 중요하다.** EBS 볼륨은 특정 AZ에 묶여 있어 그 AZ의 노드에만 붙을 수 있고, 스케줄러([21장](21-kube-scheduler.md))가 이것을 고려한다.

여러 클래스를 정의해 티어를 만든다(`fast-ssd` → DB, `standard` → 일반 앱, `cold-hdd` → 아카이브, `shared-nfs` → RWX 공유).

### 2.3 바인딩 과정과 PVC 상태

**한 줄 요약:** PV 컨트롤러가 맞는 PV를 찾고, 없으면 프로비저너가 만들며, 바인딩은 1:1 배타적이다.

```
① PVC 생성
     ▼
② PV 컨트롤러가 매칭되는 PV를 찾는다 (용량 ≥ 요청, accessMode 호환, storageClass 일치)
     ├─ 있음 → 바인딩 (정적 프로비저닝)
     └─ 없음 → StorageClass의 프로비저너 호출
                  ▼
            ③ 실제 스토리지 생성 (EBS 볼륨 등)
                  ▼
            ④ PV 오브젝트 생성 후 바인딩 (동적 프로비저닝)
```

10Gi를 요청했는데 100Gi PV가 매칭되면 **100Gi 전체를 차지한다.** driver가 없거나 권한이 없으면 PVC 객체는 있어도 실제 디스크는 생기지 않고, 바인딩이 끝나도 노드 연결·마운트에서 실패할 수 있다.

| STATUS | 의미 |
|---|---|
| `Pending` | 매칭되는 PV가 없거나 프로비저닝 대기 중 |
| `Bound` | PV와 연결됨 |
| `Lost` | 바인딩된 PV가 사라짐 |

### 2.4 volumeBindingMode: 디스크의 위치가 Pod의 위치를 제한한다

**한 줄 요약:** `Immediate`는 AZ가 어긋나 영구 Pending을 만들 수 있고, `WaitForFirstConsumer`는 스케줄 결과에 맞춰 볼륨을 만든다.

`Immediate`는 PVC가 생기는 즉시 PV를 만들고 바인딩한다. 멀티 AZ 클러스터에서 볼륨이 `ap-northeast-2a`에 생겼는데 스케줄러가 Pod를 `2c` 노드에 배치하려 하면 마운트할 수 없어 **영원히 Pending**이다.

```
Immediate:           PVC 생성 → 볼륨이 AZ-a에 생성 → Pod를 AZ-c에 배치 시도 → 마운트 불가 → Pending 영구화
WaitForFirstConsumer: PVC 생성 → 대기(Pending) → 스케줄러가 노드 결정 → 그 노드의 AZ에 볼륨 생성 → 마운트 성공
```

대부분의 클라우드 StorageClass는 `WaitForFirstConsumer`가 기본이고, 직접 만든다면 반드시 이렇게 한다. 이 모드에서는 **소비하는 Pod가 아직 없는 PVC의 `Pending`이 정상 대기**일 수 있다. `kubectl describe pvc`에 `waiting for first consumer to be created before binding`이 보이면 정상이다.

## 코어 3. 접근 모드·회수 정책·확장

### 3.1 접근 모드

**한 줄 요약:** RWO는 "하나의 노드", 정말 하나의 Pod만 원하면 RWOP.

| 모드 | 약칭 | 의미 |
|---|---|---|
| `ReadWriteOnce` | RWO | **하나의 노드**에서 읽기/쓰기 |
| `ReadOnlyMany` | ROX | 여러 노드에서 읽기 전용 |
| `ReadWriteMany` | RWX | **여러 노드**에서 읽기/쓰기 |
| `ReadWriteOncePod` | RWOP | **하나의 Pod**에서만 (v1.29+ GA) |

> **⚠️ RWO는 "하나의 Pod"가 아니라 "하나의 노드"다.** 같은 노드의 여러 Pod가 RWO 볼륨을 동시에 마운트할 수 있고 이것이 데이터 손상의 원인이 되기도 한다. 단일 Pod 제한은 `ReadWriteOncePod`로 표현하며 CSI와 버전 지원을 확인한다.

블록 스토리지(AWS EBS, GCP PD, Azure Disk)와 로컬 디스크는 RWX를 지원하지 않고, 파일 스토리지(EFS, Azure Files, NFS, CephFS 등)는 지원한다. "여러 Pod가 같은 파일에 접근해야 한다"는 요구는 대개 아키텍처 문제의 신호다. 업로드 파일은 오브젝트 스토리지(S3), 캐시 공유는 Redis, 로그는 중앙 로그 시스템이 정답인 경우가 많다.

### 3.2 회수 정책

**한 줄 요약:** `Delete`는 PVC를 지우면 실제 디스크까지 지우고, `Retain`은 PV를 `Released`로 남긴다.

| 정책 | 동작 |
|---|---|
| `Delete` | PV와 **실제 스토리지를 삭제**한다. 동적 프로비저닝의 대부분이 기본값이다 |
| `Retain` | PV를 `Released` 상태로 두고 **데이터를 보존**한다. 수동 정리가 필요하다 |

```bash
kubectl delete pvc data      # Delete 정책이면 실제 EBS 볼륨까지 삭제됨!
```

프로덕션 데이터에는 `Retain`을 쓰고, 이미 만든 PV는 패치한다.

```bash
kubectl patch pv <pv-name> -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'
# Retain된 PV를 다시 쓰려면 claimRef를 제거하면 Available이 된다
kubectl patch pv <pv-name> -p '{"spec":{"claimRef": null}}'
```

StatefulSet을 삭제할 때의 PVC 보존 정책도 따로 읽는다.

### 3.3 볼륨 확장

**한 줄 요약:** `allowVolumeExpansion: true`일 때만, 늘리기만 되며, 디스크와 파일 시스템 두 단계다.

```bash
kubectl patch pvc data -p '{"spec":{"resources":{"requests":{"storage":"20Gi"}}}}'
kubectl get pvc data -o jsonpath='{.status.conditions}'
```

확장은 줄일 수 없다. ① 클라우드 API로 디스크 크기 증가(온라인 가능) ② `resize2fs` 등으로 파일 시스템 확대의 두 단계로 진행된다. 과거에는 Pod 재시작이 필요했지만 현재는 대부분 온라인 확장이 가능하다. `CAPACITY`가 바로 바뀌지 않을 수 있으니 `describe pvc`의 conditions를 보고, `FileSystemResizePending`이 있으면 Pod 재시작이 필요한 경우다.

## 코어 4. CSI와 볼륨이 마운트되기까지

### 4.1 왜 CSI인가

**한 줄 요약:** 스토리지 드라이버를 쿠버네티스 본체(in-tree)에서 떼어 gRPC 표준으로 분리했다.

과거에는 모든 스토리지 드라이버 코드가 쿠버네티스 본체 안(`pkg/volume/aws_ebs`, `gce_pd` ...)에 있었다. 벤더가 버그를 고치려면 쿠버네티스 릴리스를 기다려야 했고, 드라이버 버그가 kubelet이나 컨트롤러 매니저를 죽일 수 있었으며, 벤더 자격증명이 컨트롤 플레인에 있어야 했다. **CSI**는 드라이버를 클러스터 밖 별도 컴포넌트로 분리하고 gRPC로 통신한다. in-tree 플러그인은 모두 CSI로 마이그레이션되어 v1.31에서 대부분 제거됐다. 런타임의 CRI와 같은 구조다([23장](23-kubelet과-CRI.md)). **CSI는 표준 인터페이스이고, CSI driver는 구현 프로그램이다.**

### 4.2 CSI 아키텍처

**한 줄 요약:** 컨트롤러 플러그인(Deployment)은 클라우드 API를, 노드 플러그인(DaemonSet)은 실제 마운트를 맡는다.

컨트롤러 플러그인은 Deployment(보통 1&#126;2 replica)로 사이드카(external-provisioner/attacher/resizer/snapshotter)와 CSI 드라이버(Controller)가 클라우드 API를 호출하고, 노드 플러그인은 DaemonSet(node-driver-registrar + CSI 드라이버(Node))으로 모든 노드에서 실제 마운트를 한다.

| 사이드카 | 역할 | 대응 CSI 호출 |
|---|---|---|
| `external-provisioner` | PVC 감시 → 볼륨 생성 | `CreateVolume` / `DeleteVolume` |
| `external-attacher` | VolumeAttachment 감시 → 노드에 연결 | `ControllerPublishVolume` |
| `external-resizer` | PVC 크기 변경 감시 | `ControllerExpandVolume` |
| `external-snapshotter` | VolumeSnapshot 처리 | `CreateSnapshot` |
| `node-driver-registrar` | kubelet에 드라이버 등록 | - |

사이드카는 쿠버네티스 프로젝트가 제공하는 공통 부품이라 벤더는 드라이버 본체만 구현하면 된다. 각 사이드카가 API 서버를 watch하다 반응하는 **컨트롤러 패턴**([22장](22-컨트롤러-매니저.md))이다.

### 4.3 볼륨이 Pod에 마운트되기까지

**한 줄 요약:** PVC → CreateVolume → PV 바인딩 → 스케줄 → attach → NodeStage → NodePublish → 컨테이너 시작.

```
① PVC 생성
② external-provisioner가 감지
③ CSI CreateVolume 호출 → 클라우드에 실제 볼륨 생성 (예: EBS vol-abc)
④ PV 오브젝트 생성 및 PVC와 바인딩
⑤ Pod가 스케줄됨 (노드 결정)
⑥ external-attacher가 VolumeAttachment 생성
⑦ CSI ControllerPublishVolume → 볼륨을 노드에 연결 (EBS attach)
⑧ kubelet이 CSI NodeStageVolume 호출
     → 노드의 글로벌 경로에 마운트 + 포맷
     /var/lib/kubelet/plugins/kubernetes.io/csi/.../globalmount
⑨ kubelet이 CSI NodePublishVolume 호출
     → Pod의 볼륨 디렉터리로 바인드 마운트
     /var/lib/kubelet/pods/<pod-uid>/volumes/...
⑩ 컨테이너 시작 (해당 경로가 mountPath로 보인다)
```

⑧과 ⑨가 나뉜 이유는 같은 노드의 여러 Pod가 같은 볼륨을 쓸 때 스테이지(포맷·마운트)는 한 번만 하고 퍼블리시(바인드 마운트)만 여러 번 하기 위해서다. 노드에서는 직접 확인할 수 있다.

```bash
docker exec k8s-guide-worker sh -c 'ls /var/lib/kubelet/pods/*/volumes/ 2>/dev/null | head'
docker exec k8s-guide-worker mount | grep kubelet
```

> **게임 서버 유추:** ⑧은 디스크를 한 번 `mount`해 두는 일, ⑨는 그 디렉터리를 각 컨테이너의 경로로 `mount --bind`하는 일이다. ⚠️ 이 모든 마운트가 컨테이너의 마운트 네임스페이스([9장](../2부-컨테이너-커널-기능과-Docker/09-네임스페이스.md)) 안에서 보이는 결과이며, 개발자가 `mount`를 직접 부르지 않는다.

### 4.4 스냅샷과 백업

**한 줄 요약:** 스냅샷은 디스크의 시점 이미지일 뿐 애플리케이션 일관성을 보장하지 않는다.

`VolumeSnapshotClass`/`VolumeSnapshot`은 CSI가 표준화한 스냅샷이며 CRD, snapshot controller, driver 지원이 필요하다. 스냅샷에서 복원하거나 PVC를 복제하려면 새 PVC의 `dataSource`에 `VolumeSnapshot` 또는 `PersistentVolumeClaim`을 지정한다.

백업은 한 가지 방법으로 충분하지 않다. 계층을 나눠 생각한다.

```
① 애플리케이션 수준(논리적): pg_dump, mysqldump — 일관성 보장, 다른 환경 복원 가능, 대용량에서 느림
② 볼륨 수준(물리적): VolumeSnapshot, 클라우드 스냅샷 — 빠르지만 일관성은 앱 협조 필요(fsfreeze 등)
③ 클러스터 수준: Velero — 네임스페이스 전체 복원, 마이그레이션·DR
```

복구 계획은 Git 등의 선언과 설정, 실제 데이터 백업, 새 환경에 복원할 실행 절차를 따로 갖는다. etcd 백업은 앱 DB 백업을 대신하지 않는다([20장](20-etcd.md)).

## 실무 적용

### 체크리스트

- [ ] 오래 살아야 하는 게임 데이터(세이브, DB 파일)를 컨테이너 쓰기 레이어에 쓰지 않고 PVC나 외부 DB/오브젝트 스토리지에 두었는가?
- [ ] 임시 파일에 `emptyDir`을 쓰고, `medium: Memory`는 메모리 한도에 포함됨을 반영했는가?
- [ ] 일반 애플리케이션에 `hostPath`를 쓰지 않았다. 로컬 디스크가 필요하면 Local PV를 쓴다.
- [ ] StorageClass의 `volumeBindingMode`가 `WaitForFirstConsumer`이고, 소비 Pod가 없는 PVC의 `Pending`이 정상 대기일 수 있음을 안다.
- [ ] PVC 상태가 `Bound`인데 Pod가 `ContainerCreating`이면 attach/mount Events를 본다.
- [ ] RWO가 "하나의 노드"임을 알고, 단일 Pod 제한이 필요하면 RWOP를 검토했다. 여러 Pod 공유가 정말 필요한지(S3/Redis로 대체 가능한지) 먼저 따졌다.
- [ ] 프로덕션 데이터 볼륨의 회수 정책이 `Retain`(또는 의도한 값)인지 확인했다. `kubectl delete pvc` 전에 정책을 본다.
- [ ] 확장은 늘리기만 되고, `allowVolumeExpansion: true`가 필요하다.
- [ ] 스냅샷만으로 DB가 복구된다고 가정하지 않고, 앱 수준 백업이나 `fsfreeze`를 병행한다.

### 시나리오로 확인하기

1. **상황:** 게임 서버가 컨테이너 안 `/var/game/save`에 월드 스냅샷을 쓴다. 재배포하자 파일이 모두 사라졌다.
   **질문:** 왜 그리고 어떻게 해결하나?

   <details markdown="1"><summary>답 확인</summary>

   컨테이너의 파일 변경은 overlayfs의 upperdir(쓰기 레이어)에 쌓이고 컨테이너/Pod가 사라지면 함께 사라진다. 영구 데이터는 PVC를 만들어 `volumes`에 `claimName`으로 연결하고 `/var/game/save`에 `volumeMounts`로 마운트한다. 업로드 파일 같은 용도라면 오브젝트 스토리지가 더 적합할 수 있다. → 코어 1, 코어 2

   </details>

2. **상황:** 멀티 AZ 클러스터에서 새 DB Pod가 영원히 `Pending`이다. PVC는 `Bound`이고 볼륨은 AZ `a`에 있는데 `a`의 노드는 자원이 부족하다.
   **질문:** 원인과 예방은?

   <details markdown="1"><summary>답 확인</summary>

   `volumeBindingMode: Immediate`로 PVC 생성 즉시 AZ `a`에 볼륨이 만들어졌고, 볼륨이 그 AZ에 묶여 있어 다른 AZ의 노드에는 마운트할 수 없다. 스케줄러는 PV의 `nodeAffinity`를 고려하므로 Pod는 갈 곳이 없다. `WaitForFirstConsumer`로 설정하면 Pod의 노드가 결정된 뒤 그 AZ에 볼륨을 만든다. → 코어 2.4

   </details>

3. **상황:** 운영자가 `kubectl delete pvc data`를 실행하자 클라우드 디스크까지 사라졌다.
   **질문:** 무엇이 원인이고 재발을 막으려면?

   <details markdown="1"><summary>답 확인</summary>

   동적 프로비저닝 StorageClass의 기본 회수 정책이 `Delete`여서 PVC가 삭제되자 PV와 실제 스토리지가 함께 삭제됐다. 프로덕션 데이터에는 StorageClass에 `reclaimPolicy: Retain`을 쓰거나 기존 PV를 `kubectl patch pv ... persistentVolumeReclaimPolicy: Retain`으로 바꾼다. `Retain`이면 PV가 `Released`로 남고 `claimRef`를 제거해 재사용한다. → 코어 3.2

   </details>

### 2. 인출 질문

1. 스토리지 요구의 세 유형과 각 볼륨 타입은?

   <details markdown="1"><summary>답 확인</summary>

   임시 스크래치(`emptyDir`, Pod와 같은 수명), 설정·시크릿 주입(`configMap`, `secret`, `downwardAPI`, `projected`), 영구 데이터(`persistentVolumeClaim`, Pod보다 오래 감)다. → 코어 1.2

   </details>

2. PV, PVC, StorageClass는 각각 누가 만들고 어떤 스코프인가?

   <details markdown="1"><summary>답 확인</summary>

   PV는 클러스터 스코프이며 운영자 또는 프로비저너가 만들고, PVC는 네임스페이스 스코프이며 개발자가 만들고, StorageClass는 클러스터 스코프이며 운영자가 스토리지 종류를 정의한다. 개발자는 PVC만 다룬다. → 코어 2.1

   </details>

3. `Immediate`와 `WaitForFirstConsumer`의 차이는? 후자에서 Pod 없는 PVC가 `Pending`인 것은 이상한가?

   <details markdown="1"><summary>답 확인</summary>

   `Immediate`는 PVC 생성 즉시 볼륨을 만들어 AZ가 어긋나면 영구 Pending이 될 수 있다. `WaitForFirstConsumer`는 Pod가 스케줄될 때까지 기다렸다가 결정된 노드의 AZ에 볼륨을 만든다. Pod가 없으니 `Pending`인 것은 정상 대기다. → 코어 2.4

   </details>

4. 동적 프로비저닝 StorageClass에서 PVC를 삭제하면 기본적으로 무슨 일이 생기고, 어떻게 막는가?

   <details markdown="1"><summary>답 확인</summary>

   기본 회수 정책 `Delete` 때문에 PV와 실제 스토리지(예: EBS 볼륨)가 함께 삭제된다. 프로덕션 데이터에는 `reclaimPolicy: Retain`을 쓰거나 PV를 `Retain`으로 패치한다. `Retain`이면 PV는 `Released`로 남고 `claimRef`를 비우면 재사용할 수 있다. → 코어 3.2

   </details>

5. CSI의 컨트롤러 플러그인과 노드 플러그인은 각각 어떻게 배포되며 무엇을 하는가?

   <details markdown="1"><summary>답 확인</summary>

   컨트롤러 플러그인은 Deployment(보통 1&#126;2 replica)로, external-provisioner/attacher/resizer/snapshotter 사이드카가 PVC 등을 watch해 CSI 드라이버가 클라우드 API로 볼륨을 생성·연결한다. 노드 플러그인은 DaemonSet으로 모든 노드에 떠서 node-driver-registrar와 함께 실제 마운트를 한다. → 코어 4.2

   </details>

6. `NodeStageVolume`과 `NodePublishVolume`이 분리된 이유는?

   <details markdown="1"><summary>답 확인</summary>

### 3. 기억 고리

- **C++ 유추:** `/tmp` 임시 파일 = `emptyDir` ⚠️ 프로세스가 아닌 **Pod**가 수명 단위이고, 컨테이너가 재시작해도 남는다.
- **C++ 유추:** 서버에 `mount`한 데이터 디스크 = PV/PVC ⚠️ Pod는 노드를 옮겨 다니므로 디스크의 AZ·노드가 스케줄링 제약이 된다.
- **비유:** PVC = 주문서, StorageClass = 메뉴판, PV = 실제 나온 요리. ⚠️ 비유가 깨지는 지점: 주문(PVC)이 없는데 요리(PV)가 먼저 나오지 않고, 요리가 크면(100Gi) 작은 주문(10Gi) 하나가 통째로 가져간다(1:1 배타적).
- **비유:** `NodeStage`/`NodePublish` = 창고에 물건을 한 번 입고(stage)하고 각 매장 진열대에 복사본 없이 연결(publish). ⚠️ 비유가 깨지는 지점: 실제로는 하나의 디렉터리를 바인드 마운트로 여러 경로에 보이게 하는 것이지 복사가 아니다.
- **묶음(3의 법칙):** 스토리지 요구 3유형 / PV·PVC·StorageClass 3자 / 백업 3계층(앱·볼륨·클러스터) / 이 장 첫머리의 실무 상황 3개.
- **대칭·순서:** 요구(PVC) ↔ 제공(PV, StorageClass), `Immediate` ↔ `WaitForFirstConsumer`, `Delete` ↔ `Retain`, Stage(한 번) ↔ Publish(Pod마다). 마운트 순서: 생성 → 바인딩 → 스케줄 → attach → stage → publish.
