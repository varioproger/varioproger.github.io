# 24장. 오브젝트 모델과 워크로드

> **🎮 게임 서버 개발자에게** — 쿠버네티스에는 수십 종의 리소스가 있지만 **전부 같은 구조와 같은 규칙**을 따른다. 그래서 하나씩 외우는 대신 공통 구조(`spec`/`status`, `resourceVersion`, 라벨, 소유 관계, 삭제 규칙)를 익히면 처음 보는 리소스도 읽힌다. 그 위에서 **Pod**는 "컨테이너 그룹"이다. 같은 IP와 포트 공간을 나눠 쓰는 프로세스들이라는 점에서 한 호스트의 프로세스 묶음과 닮았고, 그 위의 Deployment·StatefulSet·DaemonSet·Job은 게임 서버로 치면 **로비/게이트웨이 같은 무상태 서버, 룸/샤드 같은 식별자 있는 서버, 노드별 에이전트, 일회성 배치**를 각각 어떤 컨트롤러가 책임지느냐의 문제다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 게임 서버 이미지를 새 버전으로 바꿨는데 롤링 업데이트가 중간에서 멈춘다.
> - 샤드 서버처럼 `shard-0`, `shard-1`이라는 고정 식별자와 개별 디스크가 필요한데 Deployment로는 안 된다.
> - 네임스페이스가 `Terminating`에서 영원히 멈추거나, Pod를 지웠는데 계속 되살아난다.

## 코어 — 이것만은 100%

> **한 문장:** 모든 오브젝트는 TypeMeta·ObjectMeta·Spec·Status의 같은 구조이고, Pod는 NET·IPC·UTS를 공유하는 컨테이너 그룹이며, 컨트롤러(Deployment→ReplicaSet→Pod 등)가 "원하는 개수·버전"을 조정 루프로 유지한다.

1. **오브젝트 공통 구조** — `apiVersion/kind`, `metadata`(name, uid, `resourceVersion`, `generation`, 라벨, `ownerReferences`, `finalizers`), `spec`(사람이 씀), `status`(컨트롤러가 씀). 라벨은 선택, 애노테이션은 정보다.
2. **Pod = NET·IPC·UTS 공유, MNT·PID 분리** — pause 컨테이너가 네임스페이스를 소유한다. Pod는 일회용이며 직접 만들지 않는다.
3. **Deployment → ReplicaSet → Pod** — ReplicaSet은 개수만 지키고, Deployment가 ReplicaSet 여러 개로 버전과 롤링 업데이트(`maxSurge`/`maxUnavailable`)를 관리한다. 셀렉터가 소유권을 결정한다.
4. **워크로드 선택** — 상시 무상태는 Deployment, 고유 이름·스토리지·순서는 StatefulSet, 노드마다 하나는 DaemonSet, 끝나야 하는 일은 Job/CronJob.

## C++·TCP 서버 경험에서 출발하기

| 이미 아는 것 (C++/소켓 서버) | 이 장의 개념 | 같은 점 | ⚠️ 다른 점 (유추가 깨지는 곳) |
|---|---|---|---|
| 낙관적 락 / 버전 번호 비교 후 갱신(CAS) | `resourceVersion`, `409 Conflict` | 읽은 버전이 바뀌었으면 쓰기가 실패해 "읽기-수정-쓰기-재시도" 루프를 돈다 | 값은 불투명 문자열이고, 같은 값이 watch 재개 지점으로도 쓰인다 |
| RAII 소멸자가 정리 작업을 보장 | `finalizers` | 오브젝트가 사라지기 전에 정리가 끝나기를 강제한다 | 소멸자는 같은 프로세스가 돌리지만, 파이널라이저는 **담당 컨트롤러가 지워야** 한다. 컨트롤러가 죽으면 영원히 남는다 |
| 부모 객체 소멸 시 자식 소멸(소유 관계) | `ownerReferences`와 가비지 컬렉터 | 소유자를 지우면 소유된 것도 지워진다 | 참조가 자식에 기록되고 GC가 **비동기로** 따라가 지운다. `--cascade=orphan`으로 자식을 남길 수 있다 |
| 같은 호스트의 프로세스들이 `localhost`와 같은 포트 공간 공유 | Pod의 NET 네임스페이스 공유 | 컨테이너끼리 `localhost`로 통신하고 같은 포트를 두 번 못 연다 | 파일시스템(MNT)과 PID는 **분리**돼 있다. 파일은 볼륨으로만 공유한다 |
| 프로세스 감시자(`supervisord`)로 N개 유지 | ReplicaSet / Deployment | 죽으면 다시 띄워 개수를 맞춘다 | 개수는 라벨 셀렉터로 센다. 템플릿을 바꿔도 기존 Pod는 그대로이고, 버전 교체는 Deployment가 맡는다 |
| 룸/샤드 서버에 고정 ID와 전용 저장소 | StatefulSet | `name-0`, `name-1`처럼 이름이 안정적이고 Pod마다 PVC가 붙는다 | 이름·스토리지·순서만 보장한다. 리더 선출, 복제, 페일오버는 해 주지 않는다 |

> 3. Deployment의 이미지를 바꾸면 기존 Pod가 제자리에서 바뀔까, 새로 만들어질까?

## 코어 1. 오브젝트 공통 구조

### 1.1 API 그룹, 버전, 리소스

**한 줄 요약:** 모든 리소스는 REST URL을 가지며, 코어 그룹은 `/api/v1`, 나머지는 `/apis/<그룹>/<버전>`이다.

```
GET /api/v1/namespaces/default/pods/hello-6c8b4f9d7c-2xk4p
    └─┬─┘ └┬┘ └────────┬────────┘ └┬─┘ └────────┬────────┘
   코어그룹 버전    네임스페이스     리소스        이름
```

`kubectl`이 하는 일도 이 URL 호출이다(`-v=6` 이상이면 요청이 보인다). 그룹은 Pod·Service 등 코어(`/api/v1`), `apps`(Deployment, StatefulSet, DaemonSet, ReplicaSet), `batch`(Job, CronJob), `networking.k8s.io`(Ingress, NetworkPolicy) 등으로 나뉜다. 매니페스트의 `apiVersion`이 그룹/버전이다(`v1`, `apps/v1`).

| 버전 | 의미 | 실무 지침 |
|---|---|---|
| `v1alpha1` | 실험적, 예고 없이 변경 | 프로덕션 금지 |
| `v1beta1` | 잘 테스트됐으나 필드가 바뀔 수 있음 | 마이그레이션 계획 필수 |
| `v1` | 안정, 하위 호환 | 권장 |

서브리소스(`pods/status`, `pods/log`, `pods/exec`, `deployments/scale`)는 별도 엔드포인트라 **별도 RBAC 권한**을 줄 수 있다. 리소스는 네임스페이스 소속(namespaced)이거나 클러스터 전역(`nodes`, `persistentvolumes`, `namespaces` 등)이다. `kubectl api-resources`, `kubectl explain pod.spec.containers`로 탐색한다.

### 1.2 TypeMeta · ObjectMeta · Spec · Status

**한 줄 요약:** `spec`은 사람이, `status`는 컨트롤러가 쓰고, 둘의 차이를 줄이는 것이 조정 루프다.

```yaml
apiVersion: apps/v1          # TypeMeta: 무엇인가
kind: Deployment
metadata:                    # ObjectMeta: 누구인가
  name: hello
  namespace: default
  uid: 3f2a1b9c-...
  resourceVersion: "142857"
  generation: 3
  labels: { app: hello }
spec: { replicas: 3 }        # 원하는 상태 (사람)
status: { readyReplicas: 3, observedGeneration: 3 }   # 현재 상태 (시스템)
```

- **`name` vs `uid`**: `name`은 네임스페이스 안에서 유일하고 삭제 후 재사용된다. `uid`는 클러스터 전체에서 유일하고 재사용되지 않는다. 같은 이름의 다른 오브젝트를 구분하는 것은 uid다.
- **`resourceVersion`**: 변경마다 증가하는 불투명 문자열. 업데이트 요청에 읽은 값을 담아 보내는데, 그 사이 바뀌었으면 API 서버가 `409 Conflict`를 반환한다. 그래서 컨트롤러는 "읽기 → 수정 → 쓰기, 실패하면 재시도"를 돈다. 또 watch 재접속 시 "이 값 이후 변경만 달라"는 재개 지점으로도 쓰인다.
- **`generation` / `observedGeneration`**: `generation`은 spec이 바뀔 때마다 증가하고, `status.observedGeneration`은 컨트롤러가 마지막으로 처리한 값이다. 둘을 비교하면 컨트롤러가 변경을 반영했는지 안다(`4 / 3`이면 반영 중).
- **Conditions**: `status.conditions`는 `"True"/"False"/"Unknown"` 세 값의 표준 패턴이다. `Unknown`은 "아직 판단할 수 없다"로, 노드 무응답 시 `Ready=Unknown`이 되는 것이 `False`와 다르다([23장](23-kubelet과-CRI.md)의 축출 로직이 이 차이를 이용한다).

> **[보충]** `resourceVersion`·watch가 etcd의 리비전과 어떻게 연결되는지는 [19장](19-kube-apiserver.md)과 [20장](20-etcd.md)에서 이어진다.

### 1.3 ownerReferences와 finalizers

**한 줄 요약:** 소유 관계는 삭제를 연쇄시키고, 파이널라이저는 정리가 끝날 때까지 삭제를 붙잡는다.

Deployment를 만들면 ReplicaSet과 Pod가 자동 생기는데, 그 관계가 Pod의 `ownerReferences`(`kind: ReplicaSet`, `controller: true`)에 기록된다. **가비지 컬렉터**가 이 참조를 따라가 소유자 삭제 시 소유된 것도 삭제한다.

```bash
kubectl delete deploy hello                      # Background(기본): 소유자 먼저, 자식은 GC가 비동기로
kubectl delete deploy hello --cascade=foreground # 자식을 모두 지운 뒤 소유자
kubectl delete deploy hello --cascade=orphan     # 자식을 남긴다
```

**파이널라이저**가 붙은 오브젝트는 삭제 요청을 받아도 즉시 사라지지 않는다. `metadata.deletionTimestamp`가 설정되고 `finalizers` 목록이 빌 때까지 남는다. 용도는 정리 보장이다(PVC가 사용 중이면 삭제 차단, 클라우드 LB를 만든 Service는 실제 LB를 지운 뒤 사라짐).

> **⚠️ 네임스페이스가 `Terminating`에서 멈추는 경우** — 담당 컨트롤러가 죽어 파이널라이저를 제거해 줄 주체가 없으면 영원히 남는다. 원인을 먼저 찾고, 불가피하면 `kubectl patch ns <ns> -p '{"metadata":{"finalizers":[]}}' --type=merge`로 제거하되 **최후의 수단**이다. 정리되지 않은 외부 자원(클라우드 LB, 볼륨)이 남아 비용이 청구될 수 있다.

### 1.4 라벨, 셀렉터, 애노테이션

**한 줄 요약:** 쿠버네티스에는 폴더가 없고 오브젝트를 묶는 유일한 수단이 라벨이며, 시스템 동작을 결정한다.

- Service는 라벨 셀렉터로 대상 Pod를 찾고([27장](27-Service와-kube-proxy.md)), ReplicaSet은 라벨로 자기 Pod를 식별하고, NetworkPolicy도 라벨로 대상을 지정한다.
- 셀렉터는 등가 기반(`app=hello,tier=frontend`는 AND)과 집합 기반(`matchExpressions`의 `In`, `NotIn`, `Exists`, `DoesNotExist`) 두 가지다.
- 라벨 값은 63자 이내, 애노테이션은 총 256KB까지이고 셀렉터에는 쓰이지 않는다. `kubectl apply`도 `last-applied-configuration` 애노테이션을 쓴다.

> **⚠️ Deployment의 `selector`는 생성 후 변경할 수 없다.** 바꾸려면 삭제 후 재생성해야 한다. 변하지 않을 최소한의 라벨만 넣고, `version` 같은 자주 바뀌는 라벨은 `template.metadata.labels`에만 둔다.

디버깅 요령: 장애 Pod의 라벨을 Service 셀렉터와 다르게 바꾸면(`kubectl label pod <p> app=hello-debug --overwrite`) 그 Pod가 Service에서 빠진다. ReplicaSet도 그 Pod를 자기 것으로 인식하지 못해 새 Pod를 하나 더 만들므로, 용량은 유지한 채 문제 Pod를 살려 두고 분석할 수 있다.

**Event**는 `Normal`/`Warning` 두 타입의 오브젝트이며 **기본 1시간만 보관**된다(`--event-ttl`). `kubectl describe`의 Events 섹션이 같은 데이터이고, 문제를 찾을 때는 Warning부터 본다.

## 코어 2. Pod = NET·IPC·UTS 공유, MNT·PID 분리

### 2.1 왜 컨테이너가 아니라 Pod인가

**한 줄 요약:** 같은 노드에 함께 배치되고 함께 살고 죽는 컨테이너 묶음을 원자 단위로 정의한 것이 Pod다.

웹 서버 컨테이너와 그 설정을 주기적으로 동기화하는 컨테이너가 있다고 하자. 둘은 ① 같은 노드에서 ② 함께 시작·종료되고 ③ `localhost`로 통신하되 ④ 각자 다른 이미지와 라이프사이클을 가져야 한다. 컨테이너 단위 스케줄링으로는 이 요구를 표현할 수 없다.

| 네임스페이스 | 공유 여부 | 결과 |
|---|---|---|
| **NET** | 공유 | 같은 IP, 같은 포트 공간. `localhost`로 통신 |
| **IPC** | 공유 | System V IPC, POSIX 메시지 큐 공유 |
| **UTS** | 공유 | 같은 호스트명 |
| **MNT** | 각자 | 파일시스템 분리. 볼륨으로만 공유 |
| **PID** | 각자 (기본값) | 서로의 프로세스가 안 보임 (`shareProcessNamespace: true`로 공유 가능) |

따라서 두 컨테이너가 같은 포트를 열면 뒤에 시작한 쪽이 `Address already in use`로 실패하고(2부 [9장](../2부-컨테이너-커널-기능과-Docker/09-네임스페이스.md)의 네임스페이스), 파일을 공유하려면 **볼륨을 명시적으로 마운트**해야 한다. 볼륨은 Pod 수준에 정의하고 컨테이너마다 다른 경로에 마운트해도 같은 디렉터리다. `emptyDir`의 수명은 Pod와 같다(컨테이너 재시작에는 남고 Pod 삭제 시 사라짐).

> **⚠️ 유추가 깨지는 곳** — C++ 프로세스 묶음과 달리 Pod 안 컨테이너는 **서로 다른 이미지·루트 파일시스템**을 가진다. "같은 호스트처럼 보이지만 파일은 공유되지 않는다"가 핵심 차이다.

### 2.2 pause 컨테이너

**한 줄 요약:** pause가 네임스페이스를 소유하기 때문에 메인 컨테이너가 재시작해도 Pod IP가 유지된다.

Pod에 컨테이너를 하나만 정의해도 노드에는 `pause` 컨테이너가 하나 더 뜬다(`crictl pods`로 샌드박스가 보인다).

```
① pause 컨테이너를 먼저 띄운다
   → NET·IPC·UTS 네임스페이스를 "소유"하고, CNI가 여기에 인터페이스와 IP를 붙인다
② 나머지 컨테이너는 "pause의 네임스페이스에 합류하라"는 지시로 시작한다
```

pause의 코드는 시그널 핸들러를 등록하고 무한히 잠자는 것이 전부다. 메인 컨테이너가 네임스페이스를 소유했다면 재시작마다 IP가 바뀔 것이다. 이 구조는 [23장](23-kubelet과-CRI.md)의 `RunPodSandbox`와 [17장](../2부-컨테이너-커널-기능과-Docker/17-컨테이너를-손으로-만들기.md)에서 `unshare`로 재현하는 내용과 같다.

### 2.3 Pod는 일회용이다

**한 줄 요약:** 죽은 Pod는 되살아나지 않고 이름·IP·uid가 다른 새 Pod가 만들어지므로 IP, 로컬 파일, 직접 생성에 의존하면 안 된다.

- Pod IP에 의존하면 안 된다 → Service([27장](27-Service와-kube-proxy.md)).
- Pod 로컬 파일에 중요한 데이터를 두면 안 된다 → 볼륨([29장](29-스토리지.md)).
- Pod를 직접 만들면 안 된다 → 컨트롤러. `kind: Pod`로 만든 Pod는 노드가 죽으면 그대로 사라진다.

`ports`(containerPort)는 선언일 뿐 포트를 열거나 막지 않는다(문서화와 Service의 이름 참조용). `imagePullPolicy` 기본값은 태그 `myapp:1.0`이면 `IfNotPresent`, `latest`/태그 없음이면 `Always`다. Pod 삭제 시 순서는 `deletionTimestamp` 설정 → (동시에) 엔드포인트 제거와 `preStop` → SIGTERM → `terminationGracePeriodSeconds`(기본 30초) → SIGKILL이며 자세한 내용은 [25장](25-Pod-생명주기와-리소스.md)이다.

### 2.4 Init 컨테이너와 사이드카, 세 패턴

**한 줄 요약:** init은 순서대로 완료되고, `restartPolicy: Always`를 준 init 컨테이너가 정식 사이드카다.

- **Init 컨테이너**: 메인보다 먼저, 순서대로, exit 0까지 실행. 실패하면 재시도. 메인과 다른 이미지를 쓸 수 있다(의존성 대기, 설정 준비, 마이그레이션, `chown`, 시크릿 주입). `STATUS`가 `Init:0/2`이면 2개 중 0개 완료다.
- **사이드카**(v1.29 도입, 원문 기준 v1.33 GA): `initContainers`에 `restartPolicy: Always`를 주면 메인보다 먼저 시작하고 나중에 종료되며, Job에서는 메인이 끝나면 자동 종료돼 Job이 완료된다. 전통적 `containers` 방식 사이드카는 Job 완료를 막을 수 있다.
- **멀티 컨테이너 패턴**: 사이드카(기능 추가: 로그 수집·설정 동기화·프록시), 앰배서더(나가는 연결의 대리인, 앱은 `localhost`만 봄), 어댑터(밖에서 보는 형식 변환, 예: Prometheus 형식 메트릭).

> **⚠️ 멀티 컨테이너를 쓰지 말아야 할 때** — 판단 기준은 "이 둘이 항상 1:1로, 같은 개수만큼, 함께 스케일되어야 하는가"다. 아니라면 별도 Pod다. 웹 서버와 DB를 한 Pod에 넣으면 웹 서버를 5개로 늘릴 때 DB도 5개가 된다.

## 코어 3. Deployment → ReplicaSet → Pod

### 3.1 ReplicaSet: 개수만 지킨다

**한 줄 요약:** 셀렉터에 맞는 Pod 수를 `replicas`로 유지하고, 셀렉터가 소유권을 결정한다.

조정 루프는 "셀렉터에 맞는 Pod를 센다 → 원하는 수와 비교 → 부족하면 `template`으로 생성, 많으면 삭제"다. 삭제 우선순위는 Pending, Ready 아님, 재시작 많은 것, 더 최근 생성된 것, 같은 노드에 몰린 쪽 순이다(문제 있는 것을 먼저 지운다).

ReplicaSet은 **자기가 만들지 않은 Pod도 셀렉터에 맞으면 자기 것으로 센다.** 같은 라벨의 Pod를 직접 만들면 초과분을 삭제하고, 셀렉터가 겹치는 컨트롤러 두 개는 서로의 Pod를 지우려 드는 참사를 낳는다. 또 `template`을 바꿔도 **기존 Pod에는 영향이 없다**(새로 만들어지는 Pod부터 적용). 롤링 업데이트와 롤백이 없으므로 직접 쓰지 않고 Deployment를 쓴다.

```
Deployment  (버전 관리, 롤아웃 전략)
    └─ ReplicaSet v1  (replicas: 0)     ← 롤백용으로 보관
    └─ ReplicaSet v2  (replicas: 3)     ← 현재 활성
           └─ Pod, Pod, Pod
```

### 3.2 Deployment의 롤링 업데이트

**한 줄 요약:** `maxSurge`와 `maxUnavailable`이 속도와 안전성을 정하고, readiness가 다음 단계로 넘어가는 안전장치다.

전략은 `RollingUpdate`(기본, 조금씩 교체)와 `Recreate`(전부 죽이고 전부 생성, 다운타임 발생, 두 버전이 공존하면 안 될 때)다.

```
replicas: 4, maxSurge: 25%, maxUnavailable: 25% 일 때
maxSurge       = ceil(4 × 0.25)  = 1   → 최대 5개까지 존재
maxUnavailable = floor(4 × 0.25) = 1   → 최소 3개는 사용 가능
```

| 설정 | 동작 | 적합한 상황 |
|---|---|---|
| `maxSurge: 25%`, `maxUnavailable: 25%` (기본) | 균형 | 대부분 |
| `maxSurge: 1`, `maxUnavailable: 0` | 용량을 줄이지 않음, 새 Pod가 Ready된 뒤에만 기존 제거 | 프로덕션 권장 |
| `maxSurge: 0`, `maxUnavailable: 1` | 총 Pod 수가 늘지 않음 | 리소스가 빠듯할 때 |
| `maxSurge: 100%`, `maxUnavailable: 0` | 새 버전 전체를 먼저 띄운 뒤 교체 | 빠른 배포, 여유 있을 때 |

`maxUnavailable: 0`은 새 Pod가 뜰 자리가 있어야 진행되므로, 클러스터에 여유가 없으면 새 Pod가 `Pending`에 머물러 **롤아웃이 영원히 멈춘다.** `minReadySeconds`를 주면 Ready 후 그 시간 동안 크래시하지 않아야 "사용 가능"으로 인정하고, `progressDeadlineSeconds` 안에 진전이 없으면 실패 처리한다.

롤백은 이전 ReplicaSet(`replicas: 0`으로 보관, `revisionHistoryLimit` 기본 10)을 다시 스케일 업하는 것이라 빠르다.

```bash
kubectl rollout history deployment/web
kubectl rollout undo deployment/web [--to-revision=2]
kubectl rollout status deployment/web
```

> **⚠️ 롤백이 복구하지 못하는 것** — Pod 템플릿만 되돌아간다. DB 스키마 마이그레이션, ConfigMap/Secret 내용, 외부 시스템의 부수 효과는 되돌아가지 않는다. 잘못된 이미지로 업데이트해도 기존 Pod는 유지되므로 서비스는 멈추지 않고 롤아웃만 멈춘다.

블루-그린은 Service 셀렉터(`slot: blue` → `green`) 전환으로, 카나리는 같은 라벨 아래 replica 비율로 구현할 수 있다. 다만 카나리는 비율이 Pod 수에 묶이고 분배가 근사치이며 세션 고정·자동 롤백이 없어서, 정밀한 제어는 Ingress 가중치나 Argo Rollouts 같은 도구의 몫이다.

## 코어 4. 워크로드 선택: StatefulSet · DaemonSet · Job · CronJob

### 4.1 StatefulSet — 이름, 스토리지, 순서

**한 줄 요약:** `db-0`처럼 안정적인 이름, Pod마다 고유한 PVC, 순서 있는 생성·삭제를 보장하지만 그 이상은 해 주지 않는다.

Deployment는 Pod 이름이 무작위이고, 모든 Pod가 같은 볼륨을 공유하며, 시작 순서가 없고, 안정적인 네트워크 ID가 없다. StatefulSet은 이를 해결한다.

- **안정적 네트워크 ID**: `web-0`, `web-1`, 헤드리스 서비스(`clusterIP: None`)와 `serviceName`으로 `web-0.web-headless.default.svc.cluster.local`이라는 고유 DNS 이름.
- **안정적 스토리지**: `volumeClaimTemplates`로 Pod마다 `data-web-0` 같은 PVC가 생기고, Pod가 다시 만들어져도 같은 PVC에 붙는다.
- **순서**: 생성은 `web-0` → (Ready 대기) → `web-1`, 삭제는 역순. `podManagementPolicy: Parallel`이면 동시에 생성/삭제(이름·스토리지는 여전히 안정적).
- 롤링 업데이트는 **높은 인덱스부터 역순**이고 `partition`으로 단계적 업데이트(카나리)가 가능하다.

스케일 다운해도 PVC는 삭제되지 않는다(의도된 동작). v1.27+의 `persistentVolumeClaimRetentionPolicy`로 `whenScaled`/`whenDeleted`를 지정할 수 있다. 리더 선출, 복제 설정, 페일오버, 백업, 스키마 마이그레이션은 **애플리케이션이나 오퍼레이터의 일**이다. 실무에서는 StatefulSet을 직접 쓰기보다 오퍼레이터를 먼저 검토하고, 관리형 서비스(RDS 등)가 나은 경우도 많다고 원문은 말한다. 게임 서버라면 룸 상태를 외부 저장소에 두면 대개 Deployment로 충분하다.

### 4.2 DaemonSet — 노드마다 하나

**한 줄 요약:** 조건에 맞는 모든 노드에 정확히 하나의 Pod를 두는 시스템 에이전트용 컨트롤러다.

용도는 로그 수집기(Fluent Bit 등), 모니터링 에이전트(node-exporter), 네트워크 플러그인(CNI), CSI 노드 플러그인, 보안 에이전트다. 컨트롤 플레인 노드처럼 테인트가 걸린 노드에는 기본 배치되지 않으므로 `tolerations`가 대개 필요하다. `hostNetwork`, `hostPath`는 노드 수준 접근이라 보안 검토 대상이다.

DaemonSet Pod도 일반 스케줄러를 거친다(노드 어피니티로 표현). 그래서 리소스 부족으로 `Pending`이 될 수 있다. 앱 확장을 위해 추가한 노드도 시스템 DaemonSet 자원을 먼저 소비한다는 점을 용량 계산에 반영한다.

### 4.3 Job과 CronJob

**한 줄 요약:** Job은 "끝나야 하는" 일을 관리하고, `restartPolicy`는 `OnFailure` 또는 `Never`만 가능하다.

- `completions`(성공해야 할 수), `parallelism`(동시 수), `backoffLimit`(재시도, 기본 6), `activeDeadlineSeconds`, `ttlSecondsAfterFinished`. `completionMode: Indexed`면 각 Pod가 `JOB_COMPLETION_INDEX`(0&#126;N-1)를 받아 샤딩 처리에 쓴다.
- `OnFailure`는 같은 Pod 안에서 컨테이너를 재시작하고, `Never`는 새 Pod를 만들어 실패한 Pod가 남는다(디버깅에 유리).
- **CronJob**: `schedule`은 `timeZone`이 없으면 컨트롤러 매니저의 시간대(보통 UTC)를 따른다("새벽 3시"가 한국 정오가 되는 사고). `concurrencyPolicy`는 `Allow`(기본)/`Forbid`(이전이 실행 중이면 건너뜀)/`Replace`다. Kubernetes의 재시도와 업무의 exactly-once 처리는 다른 문제이므로 앱에서 중복 실행을 방어해야 한다(`concurrencyPolicy: Forbid`도 전 세계에서 한 번만 실행된다는 보장은 아니다).

### 4.4 선택 결정 트리

**한 줄 요약:** 끝나는가 → 노드마다인가 → 고유 ID/스토리지인가 순으로 물으면 90%는 Deployment다.

```
워크로드가 끝나는가?
├─ 예 → 정해진 시각에 반복? 예 → CronJob / 아니오 → Job
└─ 아니오 → 모든 노드에 하나씩? 예 → DaemonSet
              └─ 아니오 → 각 인스턴스가 고유 ID나 스토리지를 갖는가?
                    ├─ 예 → StatefulSet (오퍼레이터가 있다면 먼저 검토)
                    └─ 아니오 → Deployment  ← 90%의 경우
```

| | Deployment | StatefulSet | DaemonSet | Job |
|---|---|---|---|---|
| Pod 이름 | 무작위 | `name-0`, `name-1` | 무작위 | 무작위 |
| 시작 순서 | 동시 | 순차(기본) | 동시 | 병렬 설정 가능 |
| 스토리지 | 공유 또는 없음 | Pod마다 고유 PVC | hostPath 주로 | 임시 |
| 업데이트 | 롤링 | 롤링(역순) | 롤링 | - |

## 실무 적용

### 체크리스트

- [ ] 오브젝트는 `spec`(내가 쓴 것)과 `status`(컨트롤러가 쓴 것)를 구분해 읽는다. 변경 반영 여부는 `generation`/`observedGeneration`으로 확인한다.
- [ ] 라벨 셀렉터는 변하지 않을 최소한의 라벨만 넣었는가? Deployment `selector`는 생성 후 변경 불가이고, 겹치는 셀렉터의 컨트롤러가 없는가?
- [ ] Pod를 직접 만들지 않고 컨트롤러를 쓴다. 같은 Pod의 컨테이너는 포트를 공유하고 파일은 볼륨으로만 공유한다.
- [ ] 멀티 컨테이너 Pod는 "항상 1:1로 함께 스케일되는가"를 기준으로 판단한다. 아니면 별도 Pod + Service다.
- [ ] 프로덕션 롤링 업데이트는 `maxSurge: 1`, `maxUnavailable: 0` + readiness 프로브이고, 클러스터에 여유 용량이 있는가?
- [ ] 롤백이 DB 스키마나 ConfigMap을 되돌리지 못함을 알고 하위 호환 마이그레이션으로 설계했는가?
- [ ] StatefulSet은 스케일 다운 후 PVC가 남는 것을 알고 있고, 리더 선출·복제는 앱/오퍼레이터가 책임지는가?
- [ ] CronJob에 `timeZone`과 `concurrencyPolicy`를 명시했고 앱이 중복 실행에 안전한가?
- [ ] `Terminating`에서 멈춘 오브젝트는 `finalizers`를 먼저 확인했는가(제거는 최후의 수단)?

   </details>

3. **상황:** 같은 Pod 안의 `game-server`와 `metrics-agent` 컨테이너가 둘 다 9090 포트를 열려다 하나가 시작에 실패했다. 또 `metrics-agent`가 게임 서버의 `/tmp/stats`를 읽으려는데 파일이 없다고 나온다.
   **질문:** 두 현상의 원인과 해결은?

   <details markdown="1"><summary>답 확인</summary>

   Pod의 컨테이너는 NET 네임스페이스를 공유하므로 같은 IP·포트 공간을 쓰고, 같은 포트를 두 번 열 수 없다. 포트를 다르게 한다. 파일시스템(MNT)은 컨테이너마다 분리돼 있으므로 파일을 공유하려면 `emptyDir` 같은 볼륨을 양쪽에 마운트한다(경로는 달라도 된다). → 코어 2

   </details>

4. **상황:** `kubectl delete namespace game-staging`을 했는데 몇 시간째 `Terminating`이다.
   **질문:** 어떻게 접근하나?

   <details markdown="1"><summary>답 확인</summary>

   `kubectl get ns game-staging -o jsonpath='{.spec.finalizers}'`와 남은 오브젝트의 `finalizers`를 확인해 어느 컨트롤러가 정리를 끝내지 못했는지 찾는다. 담당 컨트롤러가 죽었다면 그것을 복구한다. 불가피할 때만 파이널라이저를 직접 제거(`patch`)하되, 클라우드 LB·볼륨 같은 외부 자원이 정리되지 않아 비용이 계속 청구될 수 있음을 감수한다. → 코어 1

   </details>

### 2. 인출 질문

1. `resourceVersion`의 두 가지 용도는 무엇인가?

   <details markdown="1"><summary>답 확인</summary>

   ① 낙관적 동시성 제어: 업데이트에 읽은 값을 실어 보내고, 그 사이 바뀌었으면 `409 Conflict`가 나므로 읽기-수정-쓰기-재시도 루프를 돈다. ② watch 재개 지점: 재접속 시 "이 값 이후 변경만" 달라고 요청한다. → 코어 1

   </details>

2. 가비지 컬렉터와 파이널라이저는 삭제를 각각 어떻게 바꾸는가?

   <details markdown="1"><summary>답 확인</summary>

   `ownerReferences`를 따라 GC가 소유자 삭제 시 소유된 오브젝트도 삭제한다(Background/Foreground/Orphan). 파이널라이저는 삭제 요청 시 `deletionTimestamp`만 설정하고 목록이 빌 때까지 오브젝트를 남겨 정리 작업을 보장한다. → 코어 1

   </details>

3. Pod에서 공유되는 네임스페이스와 분리되는 네임스페이스는 무엇이고, 실무 결과 두 가지는?

   <details markdown="1"><summary>답 확인</summary>

   NET·IPC·UTS는 공유, MNT·PID는 분리(PID는 `shareProcessNamespace`로 공유 가능). 결과: 같은 IP·포트 공간이라 포트 충돌이 나고 `localhost`로 통신한다. 파일은 자동 공유되지 않으므로 볼륨을 명시적으로 마운트해야 한다. → 코어 2

   </details>

4. pause 컨테이너가 존재하는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   pause가 NET·IPC·UTS 네임스페이스를 소유하고 CNI가 거기에 IP를 붙인다. 메인 컨테이너가 크래시·재시작해도 네임스페이스가 유지되므로 Pod IP가 바뀌지 않는다. → 코어 2

   </details>

5. ReplicaSet의 `template`을 바꾸면 기존 Pod는 어떻게 되고, 그래서 어떻게 쓰나?

   <details markdown="1"><summary>답 확인</summary>

   기존 Pod에는 영향이 없고 새로 만들어지는 Pod부터 적용된다. 롤링 업데이트와 롤백이 없으므로 직접 쓰지 않고, Deployment가 ReplicaSet 여러 개를 오가며 버전을 관리한다. → 코어 3

   </details>

6. `replicas: 4`, 기본 25%/25%일 때 `maxSurge`와 `maxUnavailable`은?

   <details markdown="1"><summary>답 확인</summary>

   `maxSurge = ceil(4×0.25) = 1`(최대 5개), `maxUnavailable = floor(4×0.25) = 1`(최소 3개 사용 가능). 올림/내림이 달라 안전한 쪽으로 계산한다. → 코어 3

   </details>

7. StatefulSet이 보장하는 것과 보장하지 않는 것은?

   <details markdown="1"><summary>답 확인</summary>

   보장: 안정적 이름·네트워크 ID, Pod별 PVC, 순서(생성 오름차순·삭제 역순). 보장 안 함: 리더 선출, 복제 설정, 페일오버, 백업, 스키마 마이그레이션(앱/오퍼레이터의 일). 스케일 다운해도 PVC는 남는다. → 코어 4

   </details>

8. Job의 `restartPolicy`로 `Always`를 못 쓰는 이유와 `OnFailure`/`Never`의 차이는?

   <details markdown="1"><summary>답 확인</summary>

   `Always`면 영원히 끝나지 않기 때문이다. `OnFailure`는 같은 Pod 안에서 컨테이너를 재시작하고(`restartCount` 증가), `Never`는 실패한 Pod를 남기고 새 Pod를 만든다(로그 확인에 유리). → 코어 4

   </details>

### 3. 기억 고리

- **C++ 유추:** `resourceVersion` = 낙관적 락의 버전 카운터. ⚠️ 쿠버네티스에서는 같은 값이 watch 재개 지점으로도 쓰이고, 값 자체는 불투명해서 비교 연산에 의미를 두지 않는다.
- **C++ 유추:** `finalizers` = RAII 소멸자. ⚠️ 정리를 수행하는 주체가 같은 프로세스가 아니라 별도 컨트롤러라서, 컨트롤러가 죽으면 소멸이 영원히 지연된다.
- **비유:** Pod = 한 아파트 호실(같은 현관·호수·우편함=IP/포트)에 사는 룸메이트들, 각자 자기 방(파일시스템)이 있다. pause = 호실 계약자(네임스페이스 소유자). ⚠️ 비유가 깨지는 지점: 룸메이트가 나갔다 들어와도(재시작) 호실은 유지되지만, 호실 전체가 철거되면(Pod 삭제) 같은 주소로 돌아오지 않는다.
- **비유:** Deployment → ReplicaSet → Pod = 총괄 매니저 → 현재 버전 팀장 → 팀원. 새 버전이 오면 새 팀장 아래 팀원을 한 명씩 채용하고 옛 팀원을 줄이되, 옛 팀장은 롤백용으로 보관. ⚠️ 비유가 깨지는 지점: 팀원 변경은 사람의 이동이 아니라 항상 **새 객체 생성과 기존 객체 삭제**다(제자리 변경 없음).
- **묶음(3의 법칙):** 공유 네임스페이스 3(NET·IPC·UTS) / StatefulSet 보장 3(이름·스토리지·순서) / 삭제 방식 3(Background·Foreground·Orphan) / 멀티 컨테이너 패턴 3(사이드카·앰배서더·어댑터).
- **대칭·순서:** 공유(NET·IPC·UTS) ↔ 분리(MNT·PID), `maxSurge`(올림) ↔ `maxUnavailable`(내림), StatefulSet 생성(0→N-1) ↔ 삭제·업데이트(N-1→0).
