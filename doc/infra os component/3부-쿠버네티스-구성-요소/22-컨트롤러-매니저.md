# 22장. 컨트롤러 매니저

> **🎮 게임 서버 개발자에게** — kube-controller-manager는 게임 서버로 치면 **방 수 유지 담당, 유저 세션 청소 담당, 로비 정리 담당 등 수십 개의 "관리 스레드"가 한 프로세스 안에서 돌아가는 관리 데몬**이다. 각 스레드는 같은 뼈대를 쓴다. 공유 상태를 로컬 캐시에 복제해 두고(Informer), 바뀐 항목의 "키"만 작업 큐에 넣고(워크큐), 워커가 큐에서 키를 꺼내 현재 상태를 보고 차이를 맞춘다(조정). 이미 익숙한 **이벤트 큐 + 워커 스레드 풀 + dirty 플래그 중복 제거** 구조다. 새로운 점은 이 뼈대가 쿠버네티스 전체의 표준 패턴이라는 것, 그리고 이벤트를 놓쳐도 되는 이유(레벨 트리거)가 설계의 중심에 있다는 것이다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - `kubectl delete`를 했는데 오브젝트가 `Terminating`에서 영원히 안 사라진다.
> - 특정 컨트롤러(예: 우리가 만든 오퍼레이터)만 반응이 없다. 큐가 막혔는지 리더 선출이 안 됐는지 판단해야 한다.
> - Deployment를 지웠더니 Pod가 같이 사라졌는지, 남겨야 하는지(고아) 결정해야 한다.

## 코어 — 이것만은 100%

> **한 문장:** 모든 내장 컨트롤러는 "Informer(로컬 캐시) → 워크큐(키만, 중복 제거, 레이트 리밋) → 멱등·레벨 트리거 조정 함수"라는 같은 뼈대를 쓰고, HA에서는 Lease 기반 리더 선출로 하나만 활성이다.

1. **Informer = API 서버의 로컬 복제본** — Reflector(List+Watch) → DeltaFIFO → Indexer(캐시)와 이벤트 핸들러. 컨트롤러는 API 서버가 아니라 캐시를 읽는다. SharedInformer로 리소스 타입당 하나만 공유한다.
2. **워크큐는 키만 넣고 중복을 제거한다** — `dirty`/`processing` 두 집합 덕분에 1초에 100번 바뀌어도 조정은 소수 번이다. 실패한 키만 지수 백오프로 늦춘다.
3. **조정 함수 원칙** — 멱등, 레벨 트리거("지금 상태가 어떤가"), 읽기는 캐시, 쓰기는 실제로 다를 때만 `status`에.
4. **리더 선출 = Lease + 낙관적 동시성** — 리더만 일한다. 리더가 죽으면 최대 `leaseDurationSeconds`(15초) 공백이 있지만 레벨 트리거라 문제없다.
5. **GC와 파이널라이저** — `ownerReferences` 그래프로 삭제를 전파(Background/Foreground/Orphan). 파이널라이저가 남아 있으면 오브젝트는 `Terminating`으로 남는다.

## 코어 1. Informer: API 서버의 로컬 복제본

### 1.1 왜 직접 호출하지 않는가

**한 줄 요약:** 컨트롤러가 반복해서 API 서버를 호출하면 서버가 무너지므로, Informer가 대상 리소스 전체를 로컬 메모리에 실시간 복제해 둔다.

가장 단순한 컨트롤러는 "반복: `obj = apiServer.Get(name)`, 조정, `sleep(1초)`"로 짤 수 있지만, 컨트롤러가 40개 이상이고 오브젝트가 수만 개면 API 서버를 순식간에 무너뜨린다. Informer는 파이프라인이다.

```
apiserver ── List(초기 전체) + Watch(이후 변경분)
    ▼
Reflector ──▶ DeltaFIFO (키별 변경 큐)
                 │ Pop()
                 ▼
          처리 루프: ① Indexer(로컬 캐시) 갱신 ② 이벤트 핸들러(OnAdd/OnUpdate/OnDelete) 호출
                                                    ▼
                                           워크큐에 키(namespace/name) 넣기
```

| 구성 요소 | 역할 |
|---|---|
| Reflector | 한 리소스 타입에 대해 List → `resourceVersion` 기억 → Watch → 이벤트마다 DeltaFIFO 적재. 끊기면 마지막 `resourceVersion`부터 재접속, `410 Gone`이면 처음부터 relist([19장](19-kube-apiserver.md)) |
| DeltaFIFO | 키별로 Deltas(`Added`/`Updated`/`Deleted`/`Replaced`/`Sync`)를 순서대로 쌓는 큐 |
| Indexer | 스레드 세이프 로컬 캐시. 키 저장 + 커스텀 보조 인덱스(예: nodeName으로 Pod 찾기) |
| Lister | 타입별로 Indexer를 감싼 읽기 API. **항상 로컬 캐시에서 읽고 API 서버에 접근하지 않는다** |
| 이벤트 핸들러 | Delta 처리 후 호출. 보통 워크큐에 키만 넣고 즉시 반환 |

Informer의 처리 루프는 단일 고루틴 직렬 처리라 핸들러에서 무거운 작업을 하면 안 된다(그래서 키만 큐에 넣는다).

### 1.2 SharedInformer와 resync

**한 줄 요약:** 리소스 타입당 Informer 하나를 모든 컨트롤러가 공유하고, resync는 로컬 캐시를 주기적으로 재생하는 안전망이다.

Deployment, ReplicaSet, HPA, GC 컨트롤러가 모두 Pod를 보는데 각자 Reflector를 만들면 같은 데이터를 N번 직렬화·전송한다. `SharedInformerFactory`는 GVR마다 Reflector+DeltaFIFO+Indexer 세트를 하나만 만들고, `sharedProcessor`가 핸들러들에게 fan-out한다. 핸들러마다 자기 버퍼와 고루틴이 있어 하나가 느려도 즉시 다른 핸들러가 막히지는 않는다. Indexer가 하나라 모든 컨트롤러가 같은 캐시 스냅샷을 본다.

**resync**는 주기마다 Indexer의 모든 오브젝트를 `Sync` Delta로 다시 넣어 핸들러(`OnUpdate`)를 재호출한다. **API 서버에 다시 요청하는 것이 아니라 로컬 캐시를 재생하는 것**이다. watch 이벤트 유실이나 조정 함수 버그로 놓친 상태를 주기적으로 다시 검토하게 하는 안전망이다. 시작 직후 캐시가 채워지기 전에 조정을 시작하면 Lister가 빈 결과를 돌려줘 "리소스가 없다"고 오판하므로 표준 컨트롤러는 `WaitForCacheSync`로 초기 List가 끝날 때까지 기다린다.

## 코어 2. 워크큐: 키만, 중복 제거, 레이트 리밋

### 2.1 dirty / processing

**한 줄 요약:** 이미 대기 중인 키는 다시 넣지 않고, 처리 중 재변경은 `Done` 때 자동으로 다시 큐에 들어간다.

핸들러는 오브젝트 전체가 아니라 `namespace/name` 키 하나만 넣는다. 오브젝트를 넣으면 처리할 때쯤 낡은 버전일 수 있고, 키만 넣고 처리 시점에 Indexer에서 다시 읽으면 항상 최신이기 때문이다.

```
type Type struct {
    queue      []t        // 처리 순서 (FIFO)
    dirty      set[t]     // "다시 봐야 할" 항목들
    processing set[t]     // "지금 워커가 처리 중"인 항목들
}

Add(key):
    if key in processing:  dirty.add(key); return       # 처리 중인데 또 바뀜 → 끝나면 다시
    if key in dirty:       return                       # 이미 대기 중 → 중복 추가 안 함 (핵심)
    dirty.add(key); queue.append(key)

Get(): key = queue.pop_front(); processing.add(key); dirty.remove(key); return key

Done(key): processing.remove(key); if key in dirty: queue.append(key); dirty.add(key)
```

이 상태 전이가 "유실 없이, 그러나 중복 없이" 이벤트를 흡수한다. 워커가 X를 처리하는 중에 X가 또 바뀌어도 큐에 X가 세 개, 네 개 쌓이지 않고 한 번 더 조정될 뿐이다. (C++의 `std::unordered_set` 두 개와 `std::deque` 하나로 구현하는 이벤트 합치기와 같다.)

### 2.2 레이트 리미터

**한 줄 요약:** 영구 실패하는 키가 CPU를 소모하지 않도록 키별 지수 백오프와 전역 토큰 버킷을 `MaxOf`로 합친다.

성공하면 `Forget(key)`로 실패 카운터를 지우고, 실패하면 `AddRateLimited(key)`로 지연시켜 다시 넣는다. `NumRequeues(key)`로 재시도 횟수를 본다.

```go
workqueue.DefaultControllerRateLimiter()
// = MaxOfRateLimiter(
//     ItemExponentialFailureRateLimiter(5ms, 1000s),  // 개별 키: 5ms → 10ms → 20ms ... 최대 1000초
//     BucketRateLimiter(10 QPS, burst 100),            // 전체: 초당 10개, 버스트 100개
//   )
```

`AddAfter(key, duration)`는 실패 이력과 무관한 명시적 예약("이 시간 뒤에 다시 봐라", 예: 인증서 만료 30일 전 갱신)이고 같은 dirty/processing 규칙을 따른다.

## 코어 3. 조정 함수 설계 원칙

### 3.1 멱등 + 레벨 트리거

**한 줄 요약:** 이벤트가 아니라 "지금 개수가 desired보다 적은가"를 보고, 같은 조정을 두 번 해도 결과가 같게 짠다.

ReplicaSet 컨트롤러의 조정은 Pod가 왜 삭제됐는지를 보지 않고 개수만 센다.

```go
func reconcile(rsKey string) error {
    rs, err := rsLister.Get(rsKey)
    if errors.IsNotFound(err) { return nil }
    pods, _ := podLister.List(labelSelectorFrom(rs))
    diff := len(pods) - int(*rs.Spec.Replicas)
    switch {
    case diff < 0: createPods(-diff)   // 부족 — 만든다
    case diff > 0: deletePods(diff)    // 초과 — 지운다
    }
    return nil                         // diff == 0 이면 아무것도 안 한다
}
```

이벤트 핸들러의 역할은 "이 키를 다시 봐야 할 수도 있다"고 워크큐에 알리는 트리거일 뿐이고, 조정 로직은 항상 현재 상태 전체를 다시 계산한다. 이것이 "쿠버네티스는 이벤트 유실에 강하다"의 정확한 의미다. 무조건 `Create`를 호출하는 함수는 두 번째 실행에서 실패하므로, 이미 있으면 통과하게 짠다.

| 원칙 | 이유 |
|---|---|
| 읽기는 Lister(캐시)에서 | API 서버 직접 호출은 부하와 지연을 유발한다 |
| 쓰기는 실제로 바뀔 때만 | 불필요한 쓰기는 `resourceVersion`을 올리고 watch 이벤트로 전파되어 연쇄 조정 폭풍을 유발한다 |
| `spec`은 건드리지 않고 `status`만 쓴다 | `spec`은 사용자(또는 상위 컨트롤러)의 의도다 |
| 충돌(409)은 재시도 | 최신 버전을 다시 읽어 재계산 후 재시도(낙관적 동시성 제어) |

### 3.2 내장 컨트롤러들

**한 줄 요약:** 40개가 넘는 컨트롤러가 한 프로세스 안에서 각자 고루틴으로 돈다.

| 컨트롤러 | 하는 일 |
|---|---|
| `deployment` / `replicaset` | Deployment → ReplicaSet 관리·롤아웃 / Pod 개수 유지 |
| `statefulset` / `daemonset` / `job` / `cronjob` | 순서 보장·PVC 생성 / 노드마다 Pod / 배치 |
| `node-lifecycle` | 노드 상태 감시, 테인트 부착, Pod 축출 |
| `endpointslice` | Service → EndpointSlice |
| `namespace` / `garbage-collector` | 네임스페이스 삭제 시 하위 정리 / `ownerReferences` 기반 삭제 |
| `resourcequota` / `persistentvolume-binder` / `attachdetach` / `horizontal-pod-autoscaler` | 쿼터 사용량 / PV-PVC 바인딩 / 볼륨 attach·detach / HPA |

하나가 느려져도 다른 것은 계속 돌지만 프로세스가 죽으면 모두 멈춘다. 컨트롤러끼리는 서로의 존재를 모른다([18장](18-클러스터-아키텍처-총론.md)).

## 코어 4. 리더 선출

### 4.1 Lease와 낙관적 동시성

**한 줄 요약:** 대기자들이 동시에 Lease를 가져가려 해도 `resourceVersion` 충돌 덕에 정확히 하나만 성공한다.

HA에서 controller-manager와 scheduler는 3개씩 뜨는데 모두 조정하면 ReplicaSet 컨트롤러 셋이 각자 "1개 부족"이라며 Pod를 3개 만들 수 있다. 그래서 한 번에 하나만 active다.

```bash
kubectl get leases -n kube-system
kubectl get lease kube-scheduler -n kube-system -o yaml
```

```yaml
spec:
  holderIdentity: k8s-guide-control-plane_d4e5f6
  leaseDurationSeconds: 15
  acquireTime: "2026-09-01T10:00:00Z"
  renewTime: "2026-09-01T10:23:45Z"
  leaseTransitions: 3
```

```
리더:   renewDeadline(10초) 안에 renewTime 갱신. 갱신 실패 시 스스로 리더십 포기하고 종료 (split-brain 방지)
대기자: retryPeriod(2초)마다 Lease 확인.
        renewTime + leaseDurationSeconds(15초)가 지났으면 holderIdentity를 자신으로 update 시도.
        resourceVersion이 그새 바뀌었으면 충돌로 실패 → 정확히 하나만 성공
```

```
--leader-elect=true
--leader-elect-lease-duration=15s    # 이 시간 갱신이 없으면 리더 만료로 간주
--leader-elect-renew-deadline=10s    # 리더가 이 시간 내 갱신 못 하면 스스로 포기
--leader-elect-retry-period=2s       # 대기자가 Lease를 확인하는 주기
```

별도의 분산 락 서비스 없이 etcd/API 서버의 낙관적 동시성만으로 리더 선출이 완성된다.

> **⚠️ 리더 전환 중의 공백** 리더가 죽으면 최대 약 15초 동안 아무도 조정하지 않는다. 이것은 정상이다. 레벨 트리거라 새 리더가 그 시점의 실제 상태를 보고 이어서 처리한다. 값을 너무 짧게 하면 GC 정지나 일시적 네트워크 지연에도 리더가 바뀌어 불안정해진다. `leaseTransitions`가 자주 증가하면 이 문제를 의심한다. 직접 만든 오퍼레이터도 같은 리더 선출이 필요하다.

## 코어 5. 가비지 컬렉터, 파이널라이저, CCM

### 5.1 ownerReferences와 삭제 전파 정책

**한 줄 요약:** GC는 `ownerReferences` 의존 그래프를 따라 자식을 정리하고, 삭제 방식은 Background/Foreground/Orphan 세 가지다.

```
Deployment(web) └─ owns → ReplicaSet(web-7f9c) └─ owns → Pod(web-7f9c-abcde), Pod(web-7f9c-fghij)
```

GC는 거의 모든 리소스 타입에 대해 `ownerReferences`만 추출하는 Informer(GraphBuilder)를 두고 메모리에 의존 그래프를 유지한다. 소유자가 이미 없는데 자식이 남아 있으면 고아로 판단해 정리한다.

| 정책 | 동작 |
|---|---|
| Background (기본) | 소유자를 즉시 삭제하고 자식은 GC가 비동기로 정리. 잠시 "소유자 없는 자식"이 존재 |
| Foreground | 소유자에 `foregroundDeletion` 파이널라이저를 걸고 **자식을 먼저 모두 지운 뒤** 소유자 삭제 |
| Orphan | 자식의 `ownerReferences`만 제거하고 소유자만 삭제. 자식은 고아로 남음 |

```bash
kubectl delete deployment web --cascade=orphan
kubectl delete deployment web --cascade=foreground
kubectl delete deployment web                      # Background (기본)
```

### 5.2 파이널라이저

**한 줄 요약:** `metadata.finalizers`가 비어 있지 않으면 삭제는 `deletionTimestamp`만 찍는 소프트 삭제가 되고, 컨트롤러가 정리 후 자기 항목을 지워야 완료된다.

```
kubectl delete pvc data-0
 ① API 서버: finalizers가 비어 있지 않음 → deletionTimestamp만 설정, 오브젝트는 남음
 ② 관련 컨트롤러가 deletionTimestamp != nil 감지 → 정리 작업(예: 볼륨 detach)
 ③ 정리 끝나면 자기 finalizer 문자열 제거 → 배열이 비면 실제 삭제 완료
```

PVC에는 `kubernetes.io/pvc-protection`이 붙어 있어 Pod가 쓰는 동안 삭제가 `Terminating`에 머문다. **파이널라이저가 제거되지 않으면 영원히 `Terminating`이다.** 원인은 대개 파이널라이저를 등록한 컨트롤러가 죽었거나 정리 로직이 실패를 반복하는 것이다. 원인 확인 없이 finalizer부터 지우면 외부 자원이 남을 수 있다([18장](18-클러스터-아키텍처-총론.md)).

### 5.3 cloud-controller-manager

**한 줄 요약:** 클라우드 연동을 본체에서 분리했고, 노드는 초기화 전까지 `uninitialized` 테인트로 스케줄링이 막혀 있다.

| 컨트롤러 | 하는 일 |
|---|---|
| `node` | 클라우드 API로 노드 정보 보강(인스턴스 타입, AZ 라벨), 삭제된 인스턴스의 Node 오브젝트 제거 |
| `route` | Pod CIDR을 위한 클라우드 라우트 설정 |
| `service` | LoadBalancer 타입 Service → 실제 클라우드 LB 생성 |

노드 초기화는 ① kubelet이 노드 등록 시 `node.cloudprovider.kubernetes.io/uninitialized:NoSchedule` 테인트 부착 → ② CCM이 클라우드 API를 조회해 zone/region 라벨, 인스턴스 타입, ProviderID 설정 → ③ 테인트 제거로 스케줄링 가능해진다.

### 5.4 진단 지표

**한 줄 요약:** 특정 컨트롤러만 반응이 없으면 리더 선출과 워크큐 포화를 본다.

| 증상 | 원인 | 확인 |
|---|---|---|
| 특정 컨트롤러만 반응 없음 | 리더 선출 문제, 워크큐 포화 | `leader_election_master_status`, `workqueue_depth` |
| 오브젝트가 계속 늘어남 | 컨트롤러 버그, 파이널라이저 | `apiserver_storage_objects` |
| 오브젝트가 `Terminating`에 머묾 | 파이널라이저 미제거 | `kubectl get ... -o jsonpath='{.metadata.finalizers}'` |
| 리더가 자주 바뀜 | Lease 값이 너무 짧음, 네트워크 지연 | `leaseTransitions` |

`workqueue_adds_total`은 계속 늘어도 `workqueue_depth`는 낮게 유지되는 것이 중복 제거가 동작한다는 증거다. `workqueue_queue_duration_seconds`가 늘면 큐 대기가 길어진 것이다.

## 실무 적용

### 체크리스트

- [ ] 직접 만든 컨트롤러/오퍼레이터는 API 서버를 반복 `Get`하지 않고 Informer/Lister 캐시를 읽는다.
- [ ] 조정 함수가 멱등이고 이벤트 종류에 의존하지 않으며 현재 상태 전체로 판단한다.
- [ ] `status`만 쓰고 이미 같은 값이면 쓰기를 생략한다(409는 재시도).
- [ ] 시작 시 `WaitForCacheSync`로 캐시가 채워진 뒤 조정을 시작한다.
- [ ] 오퍼레이터를 여러 복제로 띄울 때 리더 선출을 켰고, Lease 값을 환경에 맞게 정했다.
- [ ] 삭제 전파 정책(Background/Foreground/Orphan)을 의도에 맞게 골랐다.
- [ ] 파이널라이저를 쓰는 컨트롤러는 정리 실패 시 재시도하고 컨트롤러 장애 시 `Terminating`이 방치되지 않게 감시한다.
- [ ] `workqueue_depth`, `leader_election_master_status`, `leaseTransitions`를 모니터링한다.

### 시나리오로 확인하기

1. **상황:** 점검 중 controller-manager가 30초 동안 정지했다. 그동안 운영자가 Pod 몇 개를 수동으로 삭제했다.
   **질문:** 복귀 후 Pod 개수는 어떻게 되나?

   <details markdown="1"><summary>답 확인</summary>

   원래 개수로 복구된다. 컨트롤러는 삭제 이벤트가 아니라 "지금 Pod 개수가 desired보다 적다"는 현재 상태를 보고 조정하는 레벨 트리거이므로, 이벤트를 하나도 받지 못했어도 재시작 후 List로 현재 상태를 다시 읽어 부족분을 만든다. resync도 안전망이다. → 코어 3, 1

   </details>

2. **상황:** `kubectl delete pvc data-0`을 했는데 한참 `Terminating`이다. 같은 PVC를 쓰는 Pod가 아직 돌고 있다.
   **질문:** 이것은 장애인가?

   <details markdown="1"><summary>답 확인</summary>

   정상 동작이다. PVC에는 `kubernetes.io/pvc-protection` 파이널라이저가 있어 삭제 요청 시 `deletionTimestamp`만 찍히고, 사용하는 Pod가 사라져 정리 조건이 충족돼야 파이널라이저가 제거되며 실제 삭제가 완료된다. Pod를 종료하면 곧 사라진다. 파이널라이저를 등록한 컨트롤러가 죽은 경우라면 영구 `Terminating`이 되므로 컨트롤러를 먼저 복구한다. → 코어 5

   </details>

3. **상황:** 컨트롤 플레인 3노드 중 리더 controller-manager가 있는 노드가 죽었다. 그 직후 Deployment 스케일 요청이 약 15초간 반영되지 않다가 처리됐다.
   **질문:** 왜 지연되었고 데이터 손실은 없는가?

   <details markdown="1"><summary>답 확인</summary>

   리더가 `renewTime`을 갱신하지 못해 `leaseDurationSeconds`(15초)가 지나야 대기자가 만료를 감지해 Lease를 획득한다. 그 공백 동안 아무도 조정하지 않는다. 손실은 없다. 새 리더가 이벤트 이력이 아니라 현재 상태를 보고 이어서 조정하는 레벨 트리거 때문이다. 값을 줄이면 일시적 지연에도 리더가 자주 바뀌어 불안정해질 수 있다. → 코어 4

   </details>

4. **상황:** Deployment를 삭제하면서 Pod는 유지하고 싶다(고아 상태로 다른 곳에서 인수).
   **질문:** 어떤 삭제 정책을 쓰나?

   <details markdown="1"><summary>답 확인</summary>

   `--cascade=orphan`이다. 자식의 `ownerReferences`만 제거하고 소유자만 삭제하므로 ReplicaSet과 Pod가 고아로 남는다. 기본(Background)은 자식을 GC가 비동기로 지우고, Foreground는 자식을 먼저 모두 지운 뒤 소유자를 지운다. → 코어 5.1

   </details>

### 2. 인출 질문

1. Informer 파이프라인의 각 구성 요소 역할을 말하라.

   <details markdown="1"><summary>답 확인</summary>

   Reflector가 apiserver에 List+Watch해 DeltaFIFO에 Delta를 넣고, 처리 루프가 Pop해서 Indexer(로컬 캐시)를 갱신한 뒤 이벤트 핸들러를 호출한다. 핸들러는 보통 워크큐에 키만 넣는다. Lister는 Indexer를 감싼 읽기 API로 API 서버에 접근하지 않는다. → 코어 1

   </details>

2. SharedInformerFactory가 필요한 이유와 resync의 정체는?

   <details markdown="1"><summary>답 확인</summary>

   컨트롤러가 각자 Reflector를 만들면 같은 Pod 데이터를 N번 직렬화·전송하는 낭비가 생기므로 리소스 타입당 Informer를 하나만 만들어 `sharedProcessor`로 fan-out한다. resync는 API 서버를 다시 호출하지 않고 로컬 캐시의 모든 오브젝트를 `Sync` Delta로 재생해 핸들러를 다시 호출하는 안전망이다. → 코어 1.2

   </details>

3. 워크큐에 오브젝트 대신 키를 넣는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   (1) 최신성 — 처리 시점에 Indexer에서 다시 읽어 항상 최신 상태로 조정한다. (2) 중복 제거 — 같은 키가 이미 큐에 있으면 합쳐진다. → 코어 2

   </details>

4. 키 X를 처리하는 중에 X가 또 바뀌면 워크큐는 어떻게 동작하는가?

   <details markdown="1"><summary>답 확인</summary>

   `Add(X)`가 X가 processing에 있음을 보고 dirty에만 표시하고 반환한다. `Done(X)` 시 dirty에 있으면 큐에 다시 넣는다. 한 번 더 조정될 뿐 중복해서 쌓이지 않는다. → 코어 2.1

   </details>

5. 영구 실패하는 키가 시스템을 소모하지 않는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   기본 레이트 리미터가 키별 지수 백오프(5ms에서 시작해 최대 1000초)와 전역 토큰 버킷(10 QPS, burst 100)을 `MaxOf`로 합쳐 실패 횟수가 늘수록 재시도 간격을 늘린다. 성공하면 `Forget`으로 초기화되고 일시적 오류는 빨리 회복된다. → 코어 2.2

   </details>

6. 조정 함수가 지켜야 할 원칙 네 가지는?

   <details markdown="1"><summary>답 확인</summary>

   멱등성, 레벨 트리거(이벤트가 아니라 현재 상태로 판단), 읽기는 캐시에서·쓰기는 실제로 다를 때만, `spec`이 아닌 `status`만 쓰고 409는 재시도한다. → 코어 3

   </details>

7. 리더 선출에서 정확히 하나만 리더가 되는 메커니즘과 전환 공백이 문제 없는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   대기자들이 Lease의 `holderIdentity`를 자신으로 `update`하려 할 때 `resourceVersion`이 그사이 바뀌었으면 API 서버가 거부하는 낙관적 동시성으로 하나만 성공한다. 리더가 죽으면 최대 약 15초 공백이 있지만 새 리더가 이벤트 이력이 아니라 현재 상태를 관찰해 조정하는 레벨 트리거라 문제가 없다. → 코어 4

   </details>

8. 삭제 전파 정책 세 가지와 파이널라이저가 만드는 `Terminating` 문제를 설명하라.

   <details markdown="1"><summary>답 확인</summary>

### 3. 기억 고리

- **C++ 유추:** 이벤트 큐 + 워커 스레드 풀 + dirty 플래그 = 워크큐 ⚠️ 큐에는 이벤트가 아니라 **키**가 들어가고 같은 키는 합쳐지며, 처리 중 변경은 `Done` 때 한 번 더 처리된다.
- **C++ 유추:** 메모리 캐시 + 변경 알림 = Informer ⚠️ 캐시는 컨트롤러가 수정하지 않는 읽기 전용 복제본이고, API 서버의 watch로만 갱신된다.
- **비유:** 워크큐 = 병원 접수 창구의 "재진 환자 호출판". 같은 환자가 여러 번 접수해도 호출판에는 이름이 한 번만 뜨고, 진료 중에 다시 접수하면 진료가 끝난 뒤 한 번 더 호출된다. ⚠️ 비유가 깨지는 지점: 환자(오브젝트) 정보는 호출판에 없고 진료실에서 최신 차트(캐시)를 다시 본다.
- **묶음(3):** Informer 3단(Reflector → DeltaFIFO → Indexer) / 삭제 정책 3종(Background·Foreground·Orphan) / 큐 3요소(queue·dirty·processing).
- **묶음(숫자):** Lease 15 / 10 / 2초(duration·renewDeadline·retryPeriod), 백오프 5ms&#126;1000초.
- **대칭:** 이벤트 핸들러(트리거) ↔ 조정 함수(진짜 판단), `AddRateLimited`(실패 이력 지연) ↔ `AddAfter`(명시적 예약), 리더(갱신) ↔ 대기자(만료 감시), Background ↔ Foreground.
