# 3장. 시그널

> **🎮 게임 서버 개발자에게** — 클라이언트가 접속을 끊는 순간 서버가 로그 한 줄 없이 사라지는 `SIGPIPE`, 이벤트 루프의 `epoll_wait`가 가끔 `EINTR`로 깨어나는 현상은 소켓 서버를 만들어 본 사람이 한 번쯤 겪는다. 컨테이너 시대에는 여기에 **배포 때마다 도착하는 `SIGTERM`**이 더해진다. `docker stop`, `kubectl delete pod`, 롤링 업데이트는 모두 SIGTERM을 보내고, 유예 시간 안에 정리하지 못하면 `SIGKILL`로 끝난다. 접속 중인 유저를 우아하게 내보내는 종료 시퀀스가 곧 시그널 처리다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 배포할 때마다 접속 중이던 플레이어 세션이 비정상 종료로 끊긴다.
> - 파드가 `Exit Code: 137`로 재시작된다.
> - 클라이언트 연결이 끊기는 순간 서버 프로세스가 아무 로그 없이 종료된다.

## 코어 — 이것만은 100%

> **한 문장:** 시그널은 번호 하나짜리 비동기 통지이고, 핸들러에서는 플래그만 세워야 하며, 서버는 SIGTERM을 우아한 종료로 받고 SIGPIPE를 무시하고 SIGCHLD로 자식을 회수해야 하고, 컨테이너에서는 PID 1 규칙 때문에 이를 직접 챙겨야 한다.

1. **시그널과 종료 코드** — 시그널마다 기본 동작이 있고, `SIGKILL`/`SIGSTOP`은 잡을 수 없다. 시그널로 죽으면 종료 코드는 `128 + 번호`다(137 = SIGKILL).
2. **핸들러는 `sigaction` + 플래그만** — 핸들러는 임의 지점에서 실행되므로 async-signal-safe 함수만 부르고, `volatile sig_atomic_t` 플래그를 세운 뒤 메인 루프가 처리한다. 시스템 콜은 `EINTR`로 끊긴다.
3. **실무 필수 시그널** — SIGTERM(우아한 종료), SIGPIPE(무시), SIGCHLD(좀비 방지), SIGHUP(설정 리로드), SIGSEGV/SIGABRT(크래시). PID 1과 셸 스크립트 함정이 있다.
4. **마스크와 멀티스레드** — 표준 시그널은 큐잉되지 않는다. 멀티스레드는 시그널을 블록한 뒤 전용 스레드(`sigwait`)나 `signalfd`로 받는다.

## 코어 1. 시그널과 종료 코드

### 1.1 시그널이란

**한 줄 요약:** 시그널은 커널이 프로세스에 보내는 번호 하나짜리 비동기 통지이고, 기본 동작이 정해져 있다.

시그널은 도착하면 프로세스가 무엇을 하고 있었든 중단되고 미리 정해진 동작이 실행된다. 시그널마다 **기본 동작**이 있다.

| 기본 동작 | 시그널 |
|---|---|
| **종료(Term)** | `SIGTERM`(15), `SIGINT`(2, Ctrl+C), `SIGHUP`(1), `SIGPIPE`(13), `SIGALRM`(14), `SIGUSR1/2` |
| **종료 + 코어 덤프(Core)** | `SIGSEGV`(11), `SIGABRT`(6), `SIGBUS`(7), `SIGFPE`(8), `SIGILL`(4), `SIGQUIT`(3, Ctrl+\) |
| **무시(Ign)** | `SIGCHLD`(17), `SIGURG`, `SIGWINCH` |
| **정지(Stop)** | `SIGSTOP`(19), `SIGTSTP`(20, Ctrl+Z), `SIGTTIN/TTOU` |
| **재개(Cont)** | `SIGCONT`(18) |

프로세스는 대부분의 시그널에 대해 **핸들러를 등록**하거나 **무시**하거나 **블록**(나중에 받기)할 수 있다. 예외는 둘이다. **`SIGKILL`(9)과 `SIGSTOP`은 잡을 수도 무시할 수도 없다.** 그래서 `kill -9`는 최후의 수단이다. `kill -9`로 죽은 프로세스는 정리 코드를 실행할 기회가 없어 임시 파일, 락 파일, 절반 쓴 데이터가 남는다.

### 1.2 시그널의 출처

**한 줄 요약:** 하드웨어 예외, 커널 이벤트, 다른 프로세스, 터미널, 자기 자신의 다섯 가지다.

- **하드웨어 예외**: 잘못된 메모리 접근(`SIGSEGV`, `SIGBUS`), 0으로 나누기(`SIGFPE`). 동기적이며 그 명령을 실행한 스레드에 간다.
- **커널 이벤트**: 자식 종료(`SIGCHLD`), 닫힌 파이프에 쓰기(`SIGPIPE`), 터미널 끊김(`SIGHUP`), 타이머(`SIGALRM`), 윈도우 크기 변경(`SIGWINCH`).
- **다른 프로세스**: `kill(pid, sig)`. 같은 UID거나 root여야 한다. `docker stop`(SIGTERM 후 10초 뒤 SIGKILL), systemd(`KillSignal=`), 쿠버네티스(SIGTERM 후 `terminationGracePeriodSeconds`).
- **터미널**: Ctrl+C → SIGINT, Ctrl+\ → SIGQUIT, Ctrl+Z → SIGTSTP를 **전경 프로세스 그룹 전체**에.
- **자기 자신**: `raise`, `abort`, `alarm`.

### 1.3 종료 코드로 시그널 읽기

**한 줄 요약:** 시그널로 죽으면 종료 코드는 `128 + 시그널 번호`이고, 137이면 메모리 제한부터 의심한다.

| 종료 코드 | 의미 |
|---|---|
| 130 | SIGINT (Ctrl+C) |
| 137 | SIGKILL — **OOM killer** 또는 `kill -9`, `docker stop` 타임아웃 |
| 139 | SIGSEGV — 세그폴트 |
| 143 | SIGTERM — 정상 종료 요청 |
| 134 | SIGABRT — `abort()`, assert 실패, glibc가 힙 손상 감지 |

쿠버네티스 파드의 `Exit Code: 137`을 보면 첫 의심은 메모리 제한이다 ([4장](04-메모리.md)).

## 코어 2. 핸들러는 sigaction + 플래그만

### 2.1 핸들러 등록: signal()이 아니라 sigaction()

**한 줄 요약:** 항상 `sigaction`을 쓰고, 핸들러는 플래그 하나만 세운 뒤 즉시 반환한다.

```c
#include <signal.h>

static volatile sig_atomic_t got_term = 0;

static void on_term(int sig) {
    got_term = 1;                  // 플래그만 세운다. 다른 일은 메인 루프가
}

struct sigaction sa = {0};
sa.sa_handler = on_term;
sigemptyset(&sa.sa_mask);
sa.sa_flags = SA_RESTART;          // 중단된 시스템 콜을 자동 재시작
sigaction(SIGTERM, &sa, NULL);
sigaction(SIGINT,  &sa, NULL);

// 메인 루프
while (!got_term) {
    do_work();
}
cleanup_and_exit();
```

`signal()`은 역사적 이유로 플랫폼마다 동작이 다르다(핸들러가 한 번 실행되면 기본으로 되돌아가는 구현도 있었다). 항상 `sigaction`을 쓴다.

### 2.2 핸들러 안에서 할 수 있는 일은 거의 없다

**한 줄 요약:** 핸들러는 프로그램의 임의 지점에서 실행되므로 async-signal-safe 함수만 부를 수 있다.

핸들러는 `malloc` 도중일 수도, `printf`가 버퍼를 조작하는 도중일 수도 있다. 이때 핸들러가 다시 `malloc`이나 `printf`를 부르면 내부 자료구조가 깨지거나 데드락된다(`malloc`은 락을 잡는다. 락을 잡은 채 시그널이 오고 핸들러가 다시 `malloc`을 부르면 자기 자신을 기다린다).

호출 가능한 것은 **async-signal-safe** 목록(`man 7 signal-safety`)의 함수뿐이다. `write`, `_exit`, `kill`, `sigaction`, `waitpid` 등 시스템 콜 대부분은 안전하다. **`printf`, `malloc`, `free`, `syslog`, 뮤텍스 잠금, C++ 예외, 대부분의 라이브러리 함수는 안전하지 않다.** 로그를 남기려면 `write(2, "got signal\n", 11)`처럼 직접 쓴다. 그래서 표준 패턴은 위 코드처럼 **`volatile sig_atomic_t` 플래그 하나만 세우고 반환**하고 실제 처리는 메인 루프에서 하는 것이다. `errno`도 핸들러가 바꿀 수 있으므로 진입 시 저장하고 나갈 때 복원한다.

### 2.3 EINTR: 시그널이 시스템 콜을 끊는다

**한 줄 요약:** 블로킹 시스템 콜은 시그널에 끊겨 `-1`/`EINTR`로 돌아오므로 재시도 루프가 필요하다.

블로킹 시스템 콜(`read`, `accept`, `wait`, `nanosleep`...) 중에 핸들러가 실행되면 시스템 콜은 `-1`과 `errno = EINTR`로 반환된다. 처리하지 않으면 "가끔 이유 없이" 읽기 실패가 난다.

```c
// 방법 1: 재시도 루프
ssize_t n;
do {
    n = read(fd, buf, sz);
} while (n == -1 && errno == EINTR);

// 방법 2: SA_RESTART 플래그 - 커널이 대부분의 시스템 콜을 자동 재시작
```

`SA_RESTART`가 있어도 재시작되지 않는 것들이 있다. `sleep`류, `epoll_wait`/`poll`/`select`, 타임아웃이 설정된 소켓 연산이다. **이벤트 루프의 `epoll_wait`는 반드시 `EINTR`를 처리해야 한다.** 내가 등록하지 않은 시그널(`SIGCHLD`, `SIGWINCH` 등)도 언제든 올 수 있다.

## 코어 3. 실무 필수 시그널

### 3.1 SIGTERM: 우아한 종료와 PID 1 함정

**한 줄 요약:** `docker stop`·`kubectl delete pod`·`systemctl stop`이 보내는 종료 요청이며, 유예 시간 안에 정리하지 못하면 SIGKILL이다.

받으면 새 요청 수락을 멈추고, 진행 중인 요청을 마치고, 연결을 닫고, 상태를 저장한 뒤 종료해야 한다. 기본 동작(즉시 종료)에 맡기면 진행 중인 요청이 끊긴다. 유예 시간(도커 10초, 쿠버네티스 30초 기본) 안에 못 끝내면 `SIGKILL`이다.

**PID 1 함정**: 컨테이너에서 PID 1인 프로세스는 핸들러가 없는 시그널을 **커널이 무시한다.** 기본 동작이 "종료"인 `SIGTERM`도 무시된다. 핸들러 없는 서버는 `docker stop`에 10초 동안 반응하지 않다가 SIGKILL로 죽는다. 해결은 핸들러를 등록하거나 `tini`를 PID 1로 두는 것이다 ([2장](02-프로세스.md)).

**셸 스크립트 함정**: `CMD ["sh", "-c", "node server.js"]`처럼 셸이 PID 1이면 셸은 자식에게 시그널을 **전달하지 않는다.** `exec node server.js`로 셸을 교체하거나 exec 형식 `CMD ["node", "server.js"]`를 쓴다. C++ 서버라면 `CMD ["./gameserver"]` 형태를 쓰라는 뜻이다.

### 3.2 SIGPIPE: 소리 없는 죽음

**한 줄 요약:** 모든 네트워크 서버는 시작 시 `SIGPIPE`를 무시하고 `EPIPE`로 처리한다.

상대가 닫은 소켓이나 파이프에 `write`하면 `SIGPIPE`가 오고 기본 동작은 종료다. 클라이언트가 연결을 끊는 순간 서버가 로그도 없이 죽는다. **모든 네트워크 서버는 시작 시 `signal(SIGPIPE, SIG_IGN)`을 해야 한다.** 그러면 `write`가 `EPIPE`를 반환해 정상 처리할 수 있다. 소켓 단위로는 `send(..., MSG_NOSIGNAL)`을 쓴다. 많은 런타임(Go, Node.js, Python)이 대신 해 주지만 C/C++ 서버나 일부 라이브러리는 아니다.

반면 `cat bigfile | head -1`처럼 파이프라인 앞 명령이 `SIGPIPE`로 조용히 죽는 것은 의도된 동작이다. CLI 도구는 `SIGPIPE`를 무시하지 않는 것이 관례다.

### 3.3 SIGCHLD, SIGHUP, 크래시 시그널

**한 줄 요약:** SIGCHLD는 회수 루프, SIGHUP은 설정 리로드 관례, SIGSEGV/SIGABRT는 잡아서 계속 실행하지 않는다.

- **SIGCHLD**: 자식이 종료하면 온다. 기본 동작은 무시지만 무시한다고 좀비가 회수되는 것은 아니다. `waitpid(-1, ..., WNOHANG)` 루프로 회수하거나, 종료 코드가 필요 없으면 `SIG_IGN`으로 **명시적으로** 설정해 커널이 자동 회수하게 한다.
- **SIGHUP**: 터미널이 끊길 때 오지만, 터미널 없는 데몬은 **"설정 다시 읽어라"**로 재정의하는 것이 관례다(nginx, sshd, rsyslog). `kill -HUP <pid>`.
- **SIGSEGV, SIGABRT**: 잡을 수는 있지만 **잡아서 계속 실행하면 안 된다.** 메모리가 이미 손상된 상태다. 정당한 용도는 스택 트레이스를 덤프하고 죽는 크래시 리포터뿐이며, 그것도 `backtrace_symbols_fd`처럼 async-signal-safe해야 한다. 대신 **코어 덤프**를 켜 둔다: `ulimit -c unlimited`, `/proc/sys/kernel/core_pattern` 확인, 컨테이너는 호스트의 core_pattern이 적용된다는 점 주의 ([8장](08-진단-도구.md)).

## 코어 4. 마스크와 멀티스레드

### 4.1 시그널 마스크와 블로킹

**한 줄 요약:** 블록한 시그널은 pending으로 대기하며, 표준 시그널은 큐잉되지 않아 여러 번 와도 한 번만 전달된다.

시그널을 **블록**하면 도착해도 전달되지 않고 pending 상태로 대기한다. 언블록하면 그때 전달된다. 임계 영역에서 시그널을 잠시 막는 데 쓴다.

```c
sigset_t set, old;
sigemptyset(&set);
sigaddset(&set, SIGTERM);
pthread_sigmask(SIG_BLOCK, &set, &old);   // 스레드의 마스크 변경 (sigprocmask는 단일 스레드용)
/* SIGTERM 없이 처리할 구간 */
pthread_sigmask(SIG_SETMASK, &old, NULL);
```

**표준 시그널은 큐잉되지 않는다.** 블록된 동안 `SIGCHLD`가 다섯 번 와도 언블록 시 한 번만 전달된다. SIGCHLD 핸들러가 `while (waitpid(...) > 0)` 루프여야 하는 이유다. 실시간 시그널(`SIGRTMIN`&#126;`SIGRTMAX`)은 큐잉되고 값도 전달할 수 있지만 잘 쓰이지 않는다.

### 4.2 멀티스레드: 전용 스레드 패턴

**한 줄 요약:** 프로세스로 온 시그널은 블록하지 않은 스레드 중 임의의 하나가 받으므로, 먼저 모두 블록하고 전용 스레드가 `sigwait`으로 받는다.

어느 스레드에서 핸들러가 실행될지 모르기 때문에 정석은 다음과 같다.

1. `main`에서 스레드를 만들기 **전에** 관심 있는 시그널을 모두 블록한다(새 스레드는 마스크를 상속한다).
2. 시그널 전용 스레드 하나가 `sigwait`으로 **동기적으로** 받는다. 핸들러가 아니므로 async-signal-safe 제약이 없어 `printf`, 락, 큐 전송을 마음껏 할 수 있다.

```c
void *signal_thread(void *arg) {
    sigset_t *set = arg;
    int sig;
    for (;;) {
        sigwait(set, &sig);
        if (sig == SIGTERM) { request_shutdown(); return NULL; }
        if (sig == SIGHUP)  { reload_config(); }
    }
}
```

Go의 `signal.Notify`, Rust의 `signal-hook`, Java의 `sun.misc.Signal`이 내부적으로 이 패턴이다.

### 4.3 signalfd: 시그널을 이벤트 루프로

**한 줄 요약:** 시그널을 fd로 만들어 epoll에 등록하면 소켓 이벤트와 시그널을 하나의 `epoll_wait`로 처리한다.

시그널을 블록한 뒤 `signalfd`로 fd를 만들면 시그널이 `read`할 수 있는 데이터가 된다. 핸들러도, 전용 스레드도, `EINTR`도 없다. epoll 기반 게임 서버에 가장 깔끔한 방법이다(systemd가 이 방식).

```c
sigset_t mask; sigemptyset(&mask); sigaddset(&mask, SIGTERM); sigaddset(&mask, SIGCHLD);
sigprocmask(SIG_BLOCK, &mask, NULL);
int sfd = signalfd(-1, &mask, SFD_NONBLOCK | SFD_CLOEXEC);
// sfd를 epoll에 EPOLLIN으로 등록. 이벤트가 오면 read(sfd, &struct signalfd_siginfo, ...)
```

같은 철학의 `pidfd`(자식 종료를 poll로 대기), `timerfd`(타이머를 fd로)와 함께 쓰면 시그널 핸들러가 전혀 없는 서버를 만들 수 있다.

직접 확인해 보는 명령은 다음과 같다.

```bash
kill -l                                   # 시그널 번호 목록
grep -E 'Sig(Pnd|Blk|Ign|Cgt)' /proc/<pid>/status   # pending/blocked/ignored/caught 마스크 (16진)
kill -TERM <pid>; echo $?                 # 종료 코드 확인 (128+N)
strace -e trace=signal -p <pid>           # 시그널 전달과 sigaction 호출 관찰
strace -e trace=rt_sigaction ./prog       # 프로그램이 어떤 핸들러를 등록하는지
timeout 5 ./prog                          # 5초 후 SIGTERM 보내기
```

`/proc/<pid>/status`의 `SigCgt`(caught)가 0이면 아무 핸들러도 등록하지 않은 것이다. PID 1인 컨테이너 프로세스라면 `docker stop`이 안 먹을 것이라 예측할 수 있다.

> **[보충]** 쿠버네티스가 파드를 종료할 때의 전체 순서(preStop 훅, SIGTERM, 유예 시간, SIGKILL)는 [25장](../3부-쿠버네티스-구성-요소/25-Pod-생명주기와-리소스.md)에서 다룬다.

- [ ] 블로킹 시스템 콜과 `epoll_wait`의 `EINTR`을 처리하는가?

- [ ] 멀티스레드라면 시그널을 전용 스레드나 `signalfd`로 받는가?

### 시나리오로 확인하기

1. **상황:** 배포 때마다 접속 중이던 플레이어 세션이 저장되지 않고 끊긴다. 서버는 SIGTERM 핸들러가 없다.
   **질문:** 어떻게 개선하나?

   <details markdown="1"><summary>답 확인</summary>

   SIGTERM의 기본 동작은 즉시 종료라 정리 코드가 실행되지 않는다. `sigaction`으로 핸들러를 등록해 플래그만 세우고, 메인 루프가 새 접속 수락을 멈추고 진행 중 세션을 저장하고 연결을 닫은 뒤 종료하게 한다. 유예 시간(도커 10초, 쿠버네티스 30초) 안에 끝내야 하며 넘기면 SIGKILL이다. → 코어 3

   </details>

2. **상황:** 클라이언트가 접속을 끊는 순간 서버 프로세스가 아무 로그 없이 사라진다. 종료 상태를 확인하니 141(128+13)이다.
   **질문:** 원인과 대응은?

   <details markdown="1"><summary>답 확인</summary>

   끊어진 소켓에 `write`해서 `SIGPIPE`가 오고 기본 동작(종료)이 실행된 것이다. 시작 시 `signal(SIGPIPE, SIG_IGN)`을 하거나 `send(..., MSG_NOSIGNAL)`을 쓰면 `write`가 `EPIPE`를 반환하므로 정상 처리할 수 있다. → 코어 3

   </details>

3. **상황:** Dockerfile이 `CMD ["sh", "-c", "./gameserver"]`이고, `docker stop`을 하면 서버가 우아하게 종료되지 않고 10초 뒤 강제 종료된다. 서버에는 SIGTERM 핸들러가 있다.
   **질문:** 왜 그런가?

   <details markdown="1"><summary>답 확인</summary>

   셸이 PID 1이 되어 SIGTERM을 받지만 자식(서버)에게 전달하지 않는다. `exec ./gameserver`로 셸을 교체하거나 exec 형식 `CMD ["./gameserver"]`를 쓴다. → 코어 3

   </details>

4. **상황:** 이벤트 루프가 가끔 `epoll_wait` 실패로 종료된다. `SA_RESTART`를 줬는데도 그렇다.
   **질문:** 원인은?

   <details markdown="1"><summary>답 확인</summary>

   `epoll_wait`/`poll`/`select`, `sleep`류는 `SA_RESTART`가 있어도 재시작되지 않아 `-1`/`EINTR`로 반환된다. `SIGCHLD`나 `SIGWINCH` 같은 내가 등록하지 않은 시그널도 올 수 있으므로 `EINTR`이면 다시 호출하도록 처리하거나 `signalfd`로 시그널을 이벤트 루프에 넣는다. → 코어 2, 코어 4

   </details>

### 2. 인출 질문

1. 종료 코드 137과 143은 각각 무엇을 뜻하고 137을 보면 무엇을 먼저 의심하는가?

   <details markdown="1"><summary>답 확인</summary>

   128+9=137은 SIGKILL(OOM killer, `kill -9`, `docker stop` 타임아웃), 128+15=143은 SIGTERM(정상 종료 요청)이다. 쿠버네티스 파드의 137은 첫 의심이 메모리 제한이다. → 코어 1

   </details>

2. `kill -9`가 최후의 수단인 이유는?

   <details markdown="1"><summary>답 확인</summary>

   SIGKILL은 잡거나 무시할 수 없어 프로세스가 정리 코드를 실행할 기회가 없다. 임시 파일, 락 파일, 절반 쓴 데이터가 남는다. → 코어 1

   </details>

3. 핸들러에서 `printf`나 `malloc`을 부르면 왜 위험하고 표준 패턴은?

   <details markdown="1"><summary>답 확인</summary>

   핸들러는 임의 지점에서 실행되므로 `malloc`/`printf` 도중에 끼어들어 내부 자료구조를 깨거나, 락을 잡은 채 같은 락을 다시 잡아 자기 자신을 기다리는 데드락이 된다. async-signal-safe 함수(`write`, `_exit`, `waitpid` 등)만 쓰고, `volatile sig_atomic_t` 플래그만 세운 뒤 메인 루프가 처리한다. → 코어 2

   </details>

4. 컨테이너의 PID 1이 SIGTERM에 반응하지 않는 이유와 셸 스크립트 함정은?

   <details markdown="1"><summary>답 확인</summary>

   PID 1은 핸들러가 없는 시그널을 커널이 무시하므로 기본 동작이 종료인 SIGTERM도 무시된다. 또 `sh -c`로 셸이 PID 1이 되면 셸은 자식에게 시그널을 전달하지 않는다. 핸들러 등록, `tini`, `exec` 또는 exec 형식 CMD로 해결한다. → 코어 3

   </details>

5. 네트워크 서버가 SIGPIPE를 어떻게 다뤄야 하는가?

   <details markdown="1"><summary>답 확인</summary>

   시작 시 `signal(SIGPIPE, SIG_IGN)`으로 무시하고 `write`가 반환하는 `EPIPE`를 처리한다. 소켓 단위로는 `send(..., MSG_NOSIGNAL)`. 안 하면 상대가 끊는 순간 로그 없이 서버가 죽는다. → 코어 3

   </details>

6. SIGCHLD 핸들러를 `waitpid` 루프로 써야 하는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   표준 시그널은 큐잉되지 않아 여러 자식이 동시에 죽어도 시그널이 한 번만 전달될 수 있다. 한 번에 한 자식만 회수하면 나머지가 좀비로 남는다. → 코어 3, 코어 4

   </details>

7. 멀티스레드 서버에서 시그널을 안전하게 받는 두 가지 방법은?

   <details markdown="1"><summary>답 확인</summary>

   (1) `main`에서 스레드 생성 전에 시그널을 블록하고 전용 스레드가 `sigwait`으로 동기적으로 받는다. (2) 시그널을 블록한 뒤 `signalfd`를 epoll에 등록해 소켓 이벤트와 함께 하나의 `epoll_wait`로 처리한다. → 코어 4

   </details>

8. SIGSEGV를 잡아서 서버를 계속 돌리면 안 되는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   메모리가 이미 손상된 상태이기 때문이다. 정당한 용도는 스택 트레이스를 async-signal-safe하게 덤프하고 죽는 것뿐이다. 대신 `ulimit -c unlimited`로 코어 덤프를 켠다. → 코어 3

   </details>

### 3. 기억 고리

- **C++ 유추:** 서버 종료 시 접속자 공지 + 저장 = SIGTERM 핸들러 ⚠️ 유예 시간이 끝나면 정리 코드가 실행되지 않는 SIGKILL이 온다.
- **C++ 유추:** `epoll_wait`의 `EINTR` 재시도 ⚠️ `SA_RESTART`로도 자동 재시작되지 않는 대표 사례가 바로 `epoll_wait`다.
- **비유:** SIGTERM = "영업 종료 10분 전" 안내 방송, SIGKILL = 건물 전원 차단. ⚠️ 방송을 못 알아듣는 직원(PID 1, 핸들러 없음)은 방송이 나가도 반응하지 않는 것으로 처리된다.
- **비유:** 핸들러 = 대화 중에 끼어드는 응급 호출. 하던 말(`malloc` 중)을 끊고 대답하면 문장이 엉킨다. ⚠️ 그래서 쪽지(플래그)만 남기고 즉시 돌아간다.
- **묶음(3의 법칙):** 서버 필수 시그널 3(SIGTERM·SIGPIPE·SIGCHLD) / 이 장의 도입 상황 3개 / 멀티스레드 시그널 처리 3방식(전용 스레드·`signalfd`·플래그 핸들러).
- **대칭·순서:** SIGTERM(잡을 수 있음, 정리 가능) ↔ SIGKILL(못 잡음, 정리 불가). 순서: SIGTERM → 유예 시간 → SIGKILL. 종료 코드 143(SIGTERM) ↔ 137(SIGKILL).

- **랜덤 논리 게임:** A "시그널 핸들러에서 직접 정리하고 종료하는 게 간단하다" vs B "핸들러는 플래그만 세우고 메인 루프가 정리해야 한다" — async-signal-safe와 데드락을 근거로 번갈아 변호해 보세요.
- **AI 역할 반전:** "내가 PID 1의 시그널 규칙과 셸 스크립트 함정을 설명할 테니, 정답은 말하지 말고 틀리거나 빠진 부분만 질문으로 짚어 줘."
