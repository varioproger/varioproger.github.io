# 8장. 진단 도구

> **🎮 게임 서버 개발자에게** — 프레임/틱 지연을 프로파일러로 쫓아 본 경험이 있다면 이 장의 사고방식은 같다. 감으로 최적화하지 말고 측정한다. 다만 서버 환경에서는 Visual Studio 프로파일러가 없고, 컨테이너 안에는 `top`조차 없을 수 있다. 그래서 `/proc`, `strace`, `perf`, `gdb`, `ss`를 다룰 줄 알아야 한다. 앞 장들의 지식이 "가설을 세우는 능력"이라면 이 장은 그 가설을 **검증하는 도구**다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 운영 서버가 갑자기 느려졌는데 어디부터 봐야 할지 모른다.
> - 서버가 멈췄는데(hang) 로그가 없고, 크래시했는데 코어 덤프가 어디 있는지 모른다.
> - 컨테이너 안에 들어갔더니 `ps`, `top`, `ss`가 없다.

## 코어 — 이것만은 100%

> **한 문장:** 문제가 생기면 첫 60초 명령으로 전체를 보고, 도구가 없으면 `/proc`을 읽고, 증상별 첫 명령(`strace`·`perf`·`gdb`·`ss`)으로 가설을 검증하며, "CPU를 쓰는 곳"과 "CPU를 안 쓰고 기다리는 곳"을 구분해 분석한다.

1. **첫 60초 점검** — `uptime`, `dmesg`, `vmstat 1`, `mpstat`, `iostat`, `free`로 시스템 전체를 본다. `vmstat`의 `us/sy/wa/st/id`로 병목 종류를 가른다.
2. **`/proc`은 항상 있다** — 도구가 없는 컨테이너에서도 `status`, `fd`, `limits`, `cgroup`, PSI(`/proc/pressure`)를 읽을 수 있다.
3. **strace와 perf** — strace는 "커널에 무엇을 요청하나"(단, 수십 배 느려짐), perf는 "CPU가 어디에 쓰이나"(Flame Graph).
4. **gdb·코어 덤프·Sanitizer** — 멈춘 프로그램은 `thread apply all bt`, 크래시는 코어 덤프, 사전 예방은 ASan/TSan. 컨테이너의 `core_pattern`은 호스트 설정이다.
5. **eBPF와 네트워크 도구, 증상별 첫 명령** — 운영에서 안전한 추적(bpftrace, BCC)과 `ss`/`tcpdump`, 그리고 증상 표.

## C++·TCP 서버 경험에서 출발하기

| 이미 아는 것 (C++/소켓 서버) | 이 장의 개념 | 같은 점 | ⚠️ 다른 점 (유추가 깨지는 곳) |
|---|---|---|---|
| Visual Studio/Tracy 프로파일러, 틱 시간 측정 | `perf`, Flame Graph | 어느 함수가 시간을 쓰는지 샘플링 | `perf`는 **CPU를 쓰는 곳만** 보여준다. 느린데 CPU가 노는 경우(락·I/O·네트워크 대기)는 off-CPU 분석이 필요하다 |
| 디버거 attach, 브레이크포인트 | `gdb -p`, `strace -p` | 실행 중 프로세스에 붙는다 | **붙는 순간 프로세스가 멈춘다**(gdb). `strace`는 대상을 수십 배 느리게 해서 운영 장애가 될 수 있다 |

| 패킷 로깅, Wireshark | `tcpdump`, `ss -tin` | 실제 패킷과 연결별 상태를 본다 | 컨테이너의 네트워크 네임스페이스 안에서 봐야 한다(`nsenter -t <pid> -n`) |
| AddressSanitizer/Application Verifier | ASan, TSan, UBSan | 컴파일러 옵션으로 런타임 검사 | 오버헤드 2&#126;10배라 CI/테스트에서 켜고 프로덕션에서는 보통 끈다 |

> **🧭 읽기 전에 (2분)** — 아래 질문에 추측으로 답을 적고 정독하며 고쳐 쓰세요.
> 1. 느린 서버에 들어가 가장 먼저 어떤 정보를 봐야 할까? `vmstat`의 `wa`가 높다면 무슨 뜻일까?
> 2. 서버가 느린데 CPU 사용률은 낮다. CPU 프로파일러(`perf record`)로 원인을 찾을 수 있을까?
> 3. 운영 중인 고부하 서버에 `strace -p`를 붙여도 될까?
> 4. 컨테이너 안에서 죽은 서버의 코어 덤프는 어디에 쌓일까?
>
> **처리법:** 🛠 실습 `vmstat 1`, `cat /proc/<pid>/status`, `strace -c ./prog`, `perf top`, `gdb -p <pid> -batch -ex 'thread apply all bt'`, `ss -tin` → 바로 실행 · 🗺 관계도 증상 → 첫 명령 → 다음 명령(증상별 표), 도구가 보는 경계(`strace`=커널 경계, `ltrace`=libc 경계) · 📦 카드로 `vmstat` CPU 컬럼 5종(us/sy/wa/st/id), 종료 코드 137(메모리)·139(코어 덤프), 새너타이저 4종

## 코어 1. 첫 60초 점검

### 1.1 시스템 전체를 본다

**한 줄 요약:** `uptime`부터 `top`까지 열 개 명령으로 병목의 종류를 가른다.

문제가 있는 서버에 들어갔을 때 처음 볼 것들이다. Netflix의 Brendan Gregg가 정리한 순서를 기반으로 한다.

```bash
uptime                    # load average 3개 (1/5/15분). 코어 수보다 크면 CPU 또는 D 상태 대기 포화
dmesg -T | tail           # 커널 메시지. OOM kill, 디스크 에러, 네트워크 링크 다운
vmstat 1                  # r(실행 대기), b(D 상태), si/so(스왑), us/sy/wa/id(CPU 분류), cs
mpstat -P ALL 1           # 코어별 CPU. 한 코어만 100%면 단일 스레드 병목
pidstat 1                 # 프로세스별 CPU 시계열
iostat -xz 1              # 디스크별 r/s, w/s, await, %util
free -m                   # available을 볼 것
sar -n DEV 1              # 인터페이스별 처리량, 패킷/초
sar -n TCP,ETCP 1         # 초당 연결 수(active/passive), 재전송(retrans)
top                       # 종합
```

### 1.2 vmstat의 CPU 컬럼 해석

**한 줄 요약:** us는 내 코드, sy는 커널, wa는 디스크 대기, st는 하이퍼바이저, id는 놀고 있음.

| 컬럼 | 높으면 |
|---|---|
| `us` (user) | 내 코드가 CPU를 씀. 프로파일러로 어디인지 찾을 차례 |
| `sy` (system) | 커널이 CPU를 씀. 시스템 콜 과다, 컨텍스트 스위칭, 네트워크 스택. `strace -c`, `perf` |
| `wa` (iowait) | CPU가 놀면서 디스크를 기다림. I/O 병목 |
| `st` (steal) | 하이퍼바이저가 CPU를 다른 VM에 줌. 클라우드 노이즈 |
| `id` (idle) | 놀고 있음. CPU 문제가 아님 |

## 코어 2. /proc은 항상 있다

### 2.1 도구가 없을 때의 눈

**한 줄 요약:** 최소 컨테이너 이미지에는 `top`도 `ps`도 없을 수 있지만 `/proc`은 항상 있다.

```bash
cat /proc/loadavg                       # load average + 실행중/전체 태스크 + 마지막 PID
cat /proc/meminfo                       # MemAvailable, Dirty, Slab...
cat /proc/<pid>/status                  # State, VmRSS, Threads, SigCgt, voluntary_ctxt_switches
cat /proc/<pid>/stat                    # 숫자 배열: 14~15번째가 utime/stime (clock tick 단위)
cat /proc/<pid>/stack                   # 커널 안에서 어디에 잠들어 있나 (root)
cat /proc/<pid>/wchan                   # 잠든 커널 함수 이름
ls -l /proc/<pid>/fd                    # 열린 fd. 소켓은 socket:[inode]
cat /proc/<pid>/net/tcp                 # 이 네트워크 네임스페이스의 TCP 소켓 (ss의 원본)
cat /proc/<pid>/cgroup                  # 이 프로세스가 속한 cgroup
cat /proc/<pid>/limits                  # 적용된 ulimit
cat /proc/<pid>/environ | tr '\0' '\n'  # 환경변수
cat /proc/<pid>/cmdline | tr '\0' ' '   # 실제 커맨드라인
ls /proc/<pid>/task                     # 스레드 목록
cat /proc/pressure/{cpu,memory,io}      # PSI: 자원 부족으로 태스크가 멈춘 시간 비율 (4.20+)
```

### 2.2 PSI: 자원 부족을 직접 말해 주는 지표

**한 줄 요약:** `some avg10=12.5`면 최근 10초 중 12.5%의 시간에 최소 한 태스크가 그 자원을 기다렸다.

**PSI(Pressure Stall Information)**는 특히 유용하다. "메모리 때문에 태스크들이 전체 시간의 몇 %를 멈춰 있었나"를 직접 말해 준다. `some avg10=12.5`면 최근 10초 동안 시간의 12.5%에서 최소 하나의 태스크가 메모리 대기 중이었다는 뜻이다. 메모리·cgroup 쪽 해석은 [4장](04-메모리.md)과 [10장](../2부-컨테이너-커널-기능과-Docker/10-cgroup.md)에서 이어진다.

## 코어 3. strace와 perf

### 3.1 strace: 프로그램이 커널에 무엇을 요청하는가

**한 줄 요약:** 시스템 콜 경계를 보며 "왜 시작이 안 되나/느리나/어디서 멈췄나"에 답하지만, 대상을 수십 배 느리게 만든다.

```bash
strace ./prog                          # 모든 시스템 콜
strace -f ./prog                       # 자식 프로세스/스레드 포함
strace -p <pid>                        # 실행 중인 프로세스에 붙기
strace -c ./prog                       # 시스템 콜별 횟수/시간 집계 (성능 첫 진단)
strace -e trace=network,file ./prog    # 카테고리 필터 (process, signal, desc, memory)
strace -e trace=openat ./prog          # 특정 콜만. "어떤 설정 파일을 읽으려 하나"
strace -T -tt ./prog                   # 각 호출 소요 시간 + 타임스탬프. 어디서 오래 멈추나
strace -s 1024 ./prog                  # 문자열 인자를 길게 출력 (기본 32)
strace -o out.txt -ff ./prog           # 프로세스별 파일로 저장
strace -k ./prog                       # 각 시스템 콜의 유저 스택 트레이스
```

전형적 용도는 다음과 같다.

- "왜 시작이 안 되지?" → `strace -e trace=openat,connect`로 어떤 파일/주소에 실패(`ENOENT`, `ECONNREFUSED`, `EACCES`)하는지.
- "왜 느리지?" → `strace -c`로 시스템 콜 횟수 확인. `read`가 100만 번이면 버퍼링 문제. `futex`가 많으면 락 경합([7장](07-스레드와-동시성.md)).
- "어디서 멈췄지?" → `strace -p`로 붙으면 지금 어느 시스템 콜에서 블로킹 중인지 바로 보인다(`read(7,`에서 멈춰 있으면 fd 7이 무엇인지 `/proc/<pid>/fd/7`).

**경고**: strace는 ptrace 기반이라 **대상을 수십 배 느리게** 만든다. 운영 중 고부하 프로세스에 붙이면 장애가 된다. 잠깐만 붙이거나 `perf trace`(오버헤드 훨씬 적음)를 쓴다.

라이브러리 계층 도구도 있다. `ldd ./prog`는 어떤 공유 라이브러리를 로드하는지 보여준다("왜 다른 머신에서 안 돌지?" → `not found`). `ltrace ./prog`는 libc 경계의 호출(`malloc`, `strcpy`…)을 추적하고 `LD_DEBUG=libs`, `LD_PRELOAD=./mylib.so`로 동적 링커 과정을 보거나 함수를 가로챌 수 있다.

### 3.2 perf: CPU가 어디에 쓰이는가

**한 줄 요약:** `perf record -g`로 샘플링하고 Flame Graph의 넓은 평원을 핫스팟으로 읽는다.

```bash
perf top                                    # 시스템 전체 실시간 핫 함수 (커널 포함)
perf top -p <pid>
perf stat ./prog                            # 사이클, 명령 수, IPC, 캐시 미스, 컨텍스트 스위치, 페이지 폴트
perf stat -e cache-misses,dTLB-load-misses ./prog
perf record -g ./prog; perf report          # 콜 스택 샘플링 프로파일
perf record -g -p <pid> -- sleep 30         # 실행 중 프로세스 30초 샘플링
perf trace -p <pid>                         # strace 대체 (저오버헤드)
perf sched latency                          # 스케줄링 지연
perf lock record/report                     # 락 경합
perf c2c record/report                      # 거짓 공유(캐시 라인 경합)
```

`perf record -g` 결과는 **Flame Graph**로 보는 것이 가장 빠르다(Brendan Gregg의 `flamegraph.pl`, 또는 `perf script | inferno-collapse-perf | inferno-flamegraph`). 가로 폭이 CPU 시간 비율, 세로가 스택 깊이다. 넓은 평원(plateau)이 핫스팟이다.

`perf stat`의 **IPC(instructions per cycle)**가 1 미만이면 CPU가 메모리를 기다리고 있다는 뜻이다. 캐시 미스, TLB 미스를 의심한다([4장](04-메모리.md)). 4 근처면 계산 자체가 병목이다.

심볼이 없으면(`[unknown]`) 디버그 심볼(`-g`)로 빌드하거나 `-fno-omit-frame-pointer`를 켜라. JIT 언어(Java, Node.js)는 `perf-map-agent`나 `--perf-basic-prof` 같은 심볼 맵 옵션이 필요하다.

## 코어 4. gdb, 코어 덤프, Sanitizer

### 4.1 gdb: 멈춘 프로그램을 들여다본다

**한 줄 요약:** hang이면 `gdb -p <pid>` → `thread apply all bt`로 모든 스레드의 스택을 뽑는다.

```bash
gdb ./prog                                  # 실행 전부터
gdb -p <pid>                                # 실행 중 프로세스에 붙기 (멈춤!)
gdb ./prog core                             # 코어 덤프 분석
gdb -p <pid> -batch -ex 'thread apply all bt'   # 붙어서 모든 스레드 스택만 뽑고 떼기
```

gdb 안에서:

```
(gdb) bt                    # 현재 스레드 스택
(gdb) info threads          # 스레드 목록
(gdb) thread apply all bt   # 모든 스레드 스택 — 데드락/멈춤 분석의 핵심
(gdb) thread 3              # 스레드 전환
(gdb) frame 2; info locals  # 프레임 이동, 지역 변수
(gdb) p *ptr                # 값 출력
(gdb) x/16xb addr           # 메모리 덤프
(gdb) info proc mappings    # 주소 공간 (= /proc/pid/maps)
(gdb) catch syscall write   # 특정 시스템 콜에 브레이크
(gdb) watch var             # 변수가 바뀌면 멈춤 (하드웨어 워치포인트)
```

**데드락 진단 절차**: 멈춘 프로세스에 `gdb -p` → `thread apply all bt` → `futex_wait` 또는 `pthread_mutex_lock`에서 멈춘 스레드들을 찾는다 → 각각 어느 락을 기다리고 어느 락을 잡고 있는지(프레임에서 뮤텍스 주소 확인, `p *(pthread_mutex_t*)addr`의 `__owner`가 소유 스레드 TID) → 순환을 찾는다.

### 4.2 코어 덤프

**한 줄 요약:** `ulimit -c`로 켜고 `core_pattern`을 확인하며, 컨테이너에서는 호스트 설정이다.

크래시 후 사후 분석의 핵심이다. 켜는 법:

```bash
ulimit -c unlimited                              # 셸 세션. systemd는 LimitCORE=infinity
cat /proc/sys/kernel/core_pattern                # 어디에 어떤 이름으로. 파이프(|)면 프로그램으로 넘김
                                                  # systemd 환경: |/lib/systemd/systemd-coredump → coredumpctl
coredumpctl list; coredumpctl gdb <pid>          # systemd-coredump 사용 시
```

컨테이너 함정: `core_pattern`은 **호스트 커널 설정**이다. 컨테이너 안에서 바꿀 수 없고, 호스트가 `|/usr/lib/systemd/systemd-coredump`로 설정되어 있으면 코어가 호스트에 쌓인다. 컨테이너에서 코어를 받으려면 호스트의 `core_pattern`을 절대 경로로 바꾸고 그 경로를 볼륨으로 마운트한다.

### 4.3 Sanitizer: 크래시 전에 잡는다

**한 줄 요약:** 컴파일 옵션으로 런타임 검사를 심고, CI/테스트에서 켜며 프로덕션에서는 오버헤드(2&#126;10배) 때문에 보통 끈다.

| Sanitizer | 옵션 | 잡는 것 |
|---|---|---|
| AddressSanitizer | `-fsanitize=address` | 힙/스택 버퍼 오버플로, use-after-free, 메모리 누수(LeakSanitizer 포함) |
| ThreadSanitizer | `-fsanitize=thread` | 데이터 레이스, 락 순서 역전 |
| UndefinedBehaviorSanitizer | `-fsanitize=undefined` | 정수 오버플로, 널 역참조, 정렬 위반 |
| MemorySanitizer (clang) | `-fsanitize=memory` | 초기화 안 된 메모리 읽기 |

Valgrind(`valgrind --tool=memcheck ./prog`)는 재컴파일 없이 되지만 20&#126;50배 느리다. `--tool=helgrind`(레이스), `--tool=massif`(힙 프로파일), `--tool=cachegrind`(캐시 시뮬레이션)도 있다.

## 코어 5. eBPF, 네트워크 도구, 증상별 첫 명령

### 5.1 eBPF와 bpftrace: 운영 환경에서 안전하게

**한 줄 요약:** 대상을 멈추지 않고 커널·유저 공간의 임의 지점을 관찰하며, `offcputime`이 "CPU를 안 쓰는 이유"를 보여준다.

eBPF는 커널 안에서 안전하게 돌아가는 작은 프로그램이다. strace처럼 대상을 멈추지 않고, perf보다 유연하게 **커널과 유저 공간의 임의 지점**을 관찰한다. 프로덕션에서 쓸 수 있는 유일한 심층 추적 수단이다.

`bpftrace` 한 줄 예시:

```bash
bpftrace -e 'tracepoint:syscalls:sys_enter_openat { printf("%s %s\n", comm, str(args->filename)); }'
                                                  # 시스템 전체에서 누가 어떤 파일을 여나
bpftrace -e 'kprobe:vfs_read { @[comm] = count(); }'          # 프로세스별 read 횟수
bpftrace -e 'tracepoint:sched:sched_switch { @[prev_comm] = count(); }'   # 컨텍스트 스위치 유발자
bpftrace -e 'uprobe:/lib/x86_64-linux-gnu/libc.so.6:malloc { @[pid] = hist(arg0); }'  # malloc 크기 분포
```

BCC 도구 모음(`bcc-tools` 패키지)에 이미 만들어진 것들:

| 도구 | 용도 |
|---|---|
| `execsnoop` | 새 프로세스 실행 실시간 표시 |
| `opensnoop` | 파일 열기 실시간 |
| `tcpconnect`, `tcpaccept`, `tcpretrans` | TCP 연결/수락/재전송 |
| `biolatency` | 블록 I/O 지연 히스토그램 |
| `runqlat` | 스케줄러 대기(run queue) 지연 히스토그램. "CPU를 기다린 시간" |
| `offcputime` | 스레드가 **CPU를 안 쓰고 있던** 이유의 스택. perf가 못 보는 블로킹 분석 |
| `memleak` | 해제되지 않은 할당의 스택 |
| `cachestat` | 페이지 캐시 히트율 |

`offcputime`은 특히 중요하다. `perf`는 CPU를 쓰는 곳만 보여준다. 프로그램이 느린데 CPU는 노는 경우(락 대기, I/O 대기, 네트워크 대기)는 **off-CPU 분석**이 필요하고, 이것이 그 도구다.

### 5.2 네트워크 도구

**한 줄 요약:** `ss`로 연결별 상태, `nstat`로 커널 카운터, `tcpdump`로 실제 패킷, `nsenter`로 컨테이너 네임스페이스 안에서 본다.

```bash
ss -tanp                    # 모든 TCP 소켓 + 프로세스 (netstat 대체)
ss -tin                     # 연결별 TCP 내부 (rtt, cwnd, retrans, lastsnd)
ss -s                       # 소켓 통계 요약 (TIME_WAIT 수 등)
nstat -az                   # 커널 네트워크 카운터 (재전송, 리슨 오버플로, 드롭)
tcpdump -i any -nn -w cap.pcap port 8080    # 패킷 캡처 → Wireshark로 분석
tcpdump -i any -nn 'tcp[tcpflags] & (tcp-rst) != 0'   # RST 패킷만
ip addr; ip route; ip -s link               # 인터페이스, 라우팅, 드롭 카운터
nsenter -t <pid> -n ss -tanp                # 컨테이너의 네트워크 네임스페이스 안에서 실행
conntrack -L                                # NAT 연결 추적 테이블 (도커/쿠버네티스 네트워킹)
```

`ss -tin`의 `retrans:0/5`(누적 재전송 5회), `rto:204`(재전송 타임아웃 ms), `cwnd:10`(혼잡 윈도우)는 네트워크 품질을 연결 단위로 말해 준다. 애플리케이션이 느린데 CPU도 디스크도 놀면 이것을 보라([6장](06-네트워크-스택.md)). `nsenter`와 `conntrack`의 배경은 [9장](../2부-컨테이너-커널-기능과-Docker/09-네임스페이스.md), [16장](../2부-컨테이너-커널-기능과-Docker/16-Docker-네트워크.md)에서 이어진다.

### 5.3 문제 유형별 첫 명령

**한 줄 요약:** 증상 하나당 첫 명령과 다음 명령이 정해져 있다.

| 증상 | 첫 명령 | 다음 |
|---|---|---|
| 프로세스가 갑자기 죽었다 | `dmesg -T \| grep -iE 'oom\|segfault\|killed'` , 종료 코드 확인 | 137이면 메모리, 139면 코어 덤프 분석 |
| 메모리가 계속 는다 | `/proc/<pid>/status`의 VmRSS 시계열 | `smaps_rollup`, heaptrack/ASan, jemalloc 통계 |
| CPU 100% | `top -H -p <pid>`로 스레드 특정 | `perf top -p`, Flame Graph |
| 느린데 CPU는 놀고 있다 | `strace -p`로 어느 콜에 멈췄나, `vmstat`의 `wa`/`b` | `offcputime`, `iostat -x`, `ss -tin` |
| 응답이 완전히 멈췄다(hang) | `gdb -p -batch -ex 'thread apply all bt'` | 데드락 순환 찾기. `/proc/<pid>/stack` |
| 시작이 안 된다 | `strace -f -e trace=openat,connect,execve` | `ENOENT`/`EACCES`/`ECONNREFUSED` 찾기. `ldd` |
| 포트 바인딩 실패 | `ss -tlnp \| grep :PORT` | 점유 프로세스 또는 TIME_WAIT. `SO_REUSEADDR` |
| 커넥션이 가끔 끊긴다 | `nstat -az \| grep -i retrans`, `ss -tin` | `tcpdump`로 RST 출처. keepalive, 중간 장비 타임아웃 |
| 디스크 용량이 안 맞다 | `df -h` vs `du -sh`, `lsof +L1` | 삭제된 열린 파일 |
| fd가 부족하다(EMFILE) | `ls /proc/<pid>/fd \| wc -l`, `/proc/<pid>/limits` | fd 누수 경로 추적 `strace -e trace=desc` |
| 컨테이너가 느리다 | `cat /sys/fs/cgroup/cpu.stat`의 `nr_throttled` | 스레드 수 vs CPU 쿼터 |
| 지연이 가끔 튄다 | `runqlat`, `/proc/pressure/*`, THP 설정 | GC 로그, `perf sched`, `khugepaged` |

### 시나리오로 확인하기

1. **상황:** 게임 서버 응답이 느린데 `top`에서 CPU 사용률은 낮다. `perf record -g`로 떠 본 Flame Graph에는 뚜렷한 핫스팟이 없다.
   **질문:** 왜 perf에서 안 보이고, 무엇을 쓰나?

   <details markdown="1"><summary>답 확인</summary>

   `perf`는 CPU를 쓰는 곳만 보여준다. 락 대기, I/O 대기, 네트워크 대기처럼 CPU를 안 쓰고 기다리는 경우는 off-CPU 분석이 필요하다. `strace -p`로 어느 콜에 멈췄나, `vmstat`의 `wa`/`b`, BCC의 `offcputime`, `iostat -x`, `ss -tin`을 쓴다. → 코어 3, 코어 5

   </details>

2. **상황:** 서버가 완전히 응답하지 않는다. 프로세스는 살아 있다.
   **질문:** 첫 명령과 읽는 법은?

   <details markdown="1"><summary>답 확인</summary>

   `gdb -p <pid> -batch -ex 'thread apply all bt'`로 모든 스레드 스택을 뽑아 `futex_wait`/`pthread_mutex_lock`에서 멈춘 스레드를 찾고, 뮤텍스의 `__owner`로 누가 누구를 기다리는 순환인지 본다. `/proc/<pid>/stack`도 참고한다. → 코어 4

   </details>

3. **상황:** 컨테이너에서 도는 서버가 SIGSEGV로 죽었는데 코어 파일을 컨테이너 안에서 찾을 수 없다.
   **질문:** 왜이고 어떻게 받나?

   <details markdown="1"><summary>답 확인</summary>

   `core_pattern`은 호스트 커널 설정이라 컨테이너 안에서 바꿀 수 없다. 호스트가 `systemd-coredump`로 파이프하면 코어가 호스트에 쌓인다(`coredumpctl`). 받으려면 호스트의 `core_pattern`을 절대 경로로 바꾸고 그 경로를 볼륨으로 마운트한다. 종료 코드 139인지도 확인한다. → 코어 4

   </details>

4. **상황:** 최소 이미지 컨테이너에서 서버의 상태를 확인해야 하는데 `ps`, `top`, `ss`가 없다.
   **질문:** 어떻게 하나?

   <details markdown="1"><summary>답 확인</summary>

   `/proc`을 읽는다. `cat /proc/<pid>/status`(State, VmRSS, Threads), `ls -l /proc/<pid>/fd`, `cat /proc/<pid>/limits`, `cat /proc/<pid>/net/tcp`(ss의 원본), `cat /proc/pressure/*`, `cat /sys/fs/cgroup/cpu.stat`. 호스트에서는 `nsenter -t <pid> -n ss -tanp`로 컨테이너의 네트워크 네임스페이스 안에서 실행할 수도 있다. → 코어 2, 코어 5

   </details>

1. 문제 서버에서 처음 60초에 볼 것들을 다섯 가지 말하라.

   <details markdown="1"><summary>답 확인</summary>

   `uptime`(load average), `dmesg -T | tail`(OOM kill·디스크 에러), `vmstat 1`(r, b, si/so, us/sy/wa/id, cs), `mpstat -P ALL 1`(코어별), `iostat -xz 1`(디스크), `free -m`(available), `sar -n DEV/TCP,ETCP 1`, `top` 등이다. → 코어 1

   </details>

2. `vmstat`에서 `sy`, `wa`, `st`가 각각 높으면 무슨 뜻인가?

   <details markdown="1"><summary>답 확인</summary>

   `sy`는 커널이 CPU를 쓰는 중(시스템 콜 과다, 컨텍스트 스위칭, 네트워크 스택)이므로 `strace -c`, `perf`. `wa`는 CPU가 놀면서 디스크를 기다리는 I/O 병목. `st`는 하이퍼바이저가 CPU를 다른 VM에 준 클라우드 노이즈다. → 코어 1

   </details>

3. PSI의 `some avg10=12.5`는 무엇을 뜻하는가?

   <details markdown="1"><summary>답 확인</summary>

   최근 10초 동안 시간의 12.5%에서 최소 하나의 태스크가 해당 자원(예: 메모리)을 기다리며 멈춰 있었다는 뜻이다. → 코어 2

   </details>

4. 운영 중인 고부하 프로세스에 `strace -p`를 붙이면 왜 위험하고 대안은?

   <details markdown="1"><summary>답 확인</summary>

   ptrace 기반이라 대상을 수십 배 느리게 만들어 장애가 될 수 있다. 잠깐만 붙이거나 오버헤드가 훨씬 적은 `perf trace`, 또는 eBPF(bpftrace/BCC)를 쓴다. → 코어 3, 코어 5

   </details>

5. `strace -c`의 결과에서 `read`가 100만 번이거나 `futex`가 많다면 각각 무엇을 의심하나?

   <details markdown="1"><summary>답 확인</summary>

   `read` 100만 번은 버퍼링 문제(작은 단위 반복 호출), `futex`가 많으면 락 경합이다. → 코어 3

   </details>

6. Flame Graph를 읽는 법과 `perf stat`의 IPC가 1 미만이면 무슨 뜻인가?

   <details markdown="1"><summary>답 확인</summary>

   가로 폭이 CPU 시간 비율, 세로가 스택 깊이이며 넓은 평원이 핫스팟이다. IPC가 1 미만이면 CPU가 메모리를 기다리고 있어 캐시 미스·TLB 미스를 의심하고, 4 근처면 계산 자체가 병목이다. → 코어 3

   </details>

7. 컨테이너에서 코어 덤프가 컨테이너 안에 없는 이유와 받는 방법은?

   <details markdown="1"><summary>답 확인</summary>

   `core_pattern`이 호스트 커널 설정이라 컨테이너 안에서 바꿀 수 없고, systemd-coredump로 파이프되면 호스트에 쌓인다. 호스트의 `core_pattern`을 절대 경로로 바꾸고 그 경로를 볼륨으로 마운트한다. → 코어 4

   </details>

8. "느린데 CPU는 놀고 있다"와 "응답이 완전히 멈췄다(hang)"의 첫 명령은 각각 무엇인가?

   <details markdown="1"><summary>답 확인</summary>

   느린데 CPU가 놀면 `strace -p`로 어느 콜에 멈췄는지, `vmstat`의 `wa`/`b`를 본다(다음 `offcputime`, `iostat -x`, `ss -tin`). hang이면 `gdb -p <pid> -batch -ex 'thread apply all bt'`로 데드락 순환을 찾는다(`/proc/<pid>/stack`). → 코어 5

   </details>

### 3. 기억 고리

- **C++ 유추:** 프로파일러(Tracy 등) = `perf` + Flame Graph ⚠️ 프로파일러는 보통 "내가 계측한 구간"을 보지만 perf는 커널까지 샘플링하고, **CPU를 쓰는 곳만** 보인다. 기다리는 곳은 off-CPU 도구가 필요하다.
- **C++ 유추:** 디버거 attach = `gdb -p` ⚠️ 붙으면 프로세스가 멈추므로 운영에서는 `-batch -ex 'thread apply all bt'`로 스택만 뽑고 바로 떼는 방식으로 쓴다.
- **비유:** 첫 60초 점검 = 응급실 활력징후 측정. 원인을 찾기 전에 혈압·맥박·체온(load·CPU·메모리·디스크)부터 잰다. ⚠️ 비유가 깨지는 지점: 환자와 달리 서버의 활력징후 측정(`strace` 등)이 상태를 악화시킬 수 있다(수십 배 느려짐).
- **비유:** `perf` = CPU를 쓰는 사람만 찍는 CCTV, `offcputime` = 줄 서서 기다리는 사람을 찍는 CCTV. ⚠️ 비유가 깨지는 지점: 두 카메라 모두 샘플/이벤트 기반이라 짧은 순간은 놓칠 수 있고, 둘 다 켜야 전체 그림이 된다.
- **묶음(3의 법칙):** 시스템 콜 추적 3종(strace·perf trace·eBPF) / 사후 분석 3종(코어 덤프·gdb·`/proc`) / 새너타이저 핵심 3종(ASan·TSan·UBSan).
- **대칭·순서:** on-CPU(perf, Flame Graph) ↔ off-CPU(`offcputime`, `runqlat`). 증상 → 첫 명령 → 다음 명령.
