# 1장. 커널, 시스템 콜, 스케줄러

> **🎮 게임 서버 개발자에게** — `recv`/`send`, `epoll_wait`, 워커 스레드 풀을 다뤄 봤다면 이 장의 절반은 이미 아는 내용이다. 시스템 콜의 비용, `errno`, "스레드 수는 코어 수가 상한"이라는 감각이 그대로 나온다. 새로운 것은 하나다. **컨테이너 안의 서버도 호스트와 같은 커널 위의 평범한 프로세스**이고, 컨테이너의 CPU 제한은 별도 가상 머신이 아니라 그 커널이 가진 cgroup 쿼터라는 기능이라는 점이다. 이 관점이 잡히면 Docker와 쿠버네티스의 "이상한 동작"이 대부분 커널 동작으로 설명된다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 게임 서버를 `--cpus=2` 컨테이너로 옮겼더니 평균 CPU는 낮은데 틱 지연이 주기적으로 튄다.
> - 서버 머신의 CPU는 한가한데 load average가 코어 수의 몇 배라는 알림이 온다.
> - 서버가 "아무것도 안 했는데" 지연이 튀고 `top`의 `%si`가 높다.

## 코어 — 이것만은 100%

> **한 문장:** 내 프로그램은 유저 모드에 갇혀 시스템 콜·인터럽트·예외로만 커널에 들어가고, 커널은 프로세스와 스레드를 모두 태스크로 스케줄링하며, 컨테이너의 CPU 제한도 그 스케줄러 위의 cgroup 쿼터일 뿐이다.

1. **커널 = 하드웨어를 흉내 내는 거대한 라이브러리** — CPU 시분할, 메모리 가상화, 자원 중재, 격리를 대신한다. "모든 것은 파일(fd)"이고 내부 상태는 `/proc`·`/sys`로 들여다본다.
2. **유저 → 커널의 문은 세 개뿐** — 시스템 콜, 인터럽트, 예외/폴트. 시스템 콜은 비싸고 실패하면 -1과 `errno`를 남긴다.
3. **스케줄러와 태스크 상태 R/S/D/Z** — 단위는 태스크이고, D 상태는 `kill -9`로도 안 죽으며 load average에 포함된다. CPU 바운드 스레드 수의 상한은 코어 수다.
4. **컨테이너 CPU 제한 = cgroup 쿼터** — `--cpus=N`은 100ms 주기의 쿼터이고, 다 쓰면 컨테이너 안의 모든 태스크가 다음 주기까지 멈춘다.

## C++·TCP 서버 경험에서 출발하기

| 이미 아는 것 (C++/소켓 서버) | 이 장의 개념 | 같은 점 | ⚠️ 다른 점 (유추가 깨지는 곳) |
|---|---|---|---|
| `recv`/`send`/`epoll_wait` 호출 | 시스템 콜 | 유저 모드에서 커널로 들어가는 명시적 요청이고 호출마다 비용이 든다 | 컨테이너 안 프로세스도 **호스트와 같은 커널**에 직접 시스템 콜을 한다. 컨테이너마다 커널이 따로 있지 않다 |
| 논블로킹 소켓의 `EAGAIN`, `EINTR` 재시도 | `errno` 규약 | 실패는 -1 + `errno`, `EAGAIN`은 에러가 아니라 "지금은 없음" | `errno`는 성공한 호출에서 **초기화되지 않는다.** 실패를 확인한 직후에만 읽는다 |
| 워커 스레드 수 = 코어 수 | cgroup CPU 쿼터 (`--cpus`) | CPU 바운드 스레드 수의 상한이 코어 수라는 원리는 같다 | 코어 수를 직접 읽는 코드(`nproc`, `sysconf(_SC_NPROCESSORS_ONLN)`)는 쿼터가 아니라 **호스트의 코어 수**를 얻는다 |
| 틱 지연 스파이크 프로파일링 | 스로틀링 | 평균은 멀쩡한데 순간 지연이 튄다 | 원인이 내 코드나 락이 아니라 **쿼터 소진으로 컨테이너 전체가 정지**한 것일 수 있다 |
| `top`/`ps`로 서버 상태 보기 | 태스크 상태 R/S/D/Z, `/proc` | STAT 컬럼을 읽는다 | 커널은 스레드도 태스크로 똑같이 다룬다. D 상태는 CPU가 놀아도 load를 올린다 |

## 코어 1. 커널 = 하드웨어를 흉내 내는 라이브러리

### 1.1 커널이 대신 해주는 일

**한 줄 요약:** 시분할·가상화·중재·격리 네 축, 그리고 "모든 것은 파일".

프로그래머 입장에서 OS는 **하드웨어를 흉내 내는 거대한 라이브러리**다.

| 축 | 설명 |
|---|---|
| CPU 시분할 | 코어보다 많은 프로세스/스레드가 동시에 도는 것처럼 보이게 한다 |
| 메모리 가상화 | 모든 프로세스가 독립된 주소 공간을 가진 것처럼 보이게 한다 ([4장](04-메모리.md)) |
| 자원 중재 | 여러 프로그램이 같은 디스크, 같은 네트워크 카드를 써도 안전하게 한다 |
| 격리와 보호 | 한 프로그램의 버그가 다른 프로그램이나 커널을 건드리지 못하게 막는다 |

여기에 리눅스의 철학이 하나 더 있다. **"모든 것은 파일이다".** 디스크 파일, 소켓, 파이프, 디바이스, 타이머, 시그널까지 **파일 디스크립터(fd)** 하나로 다룬다. 소켓 서버에서 `accept`가 돌려준 정수와 `open`이 돌려준 정수가 같은 종류라는 사실이 그 예다.

### 1.2 /proc과 /sys: 커널 속을 들여다보는 창

**한 줄 요약:** 커널 상태는 가상 파일로 노출되고, 모니터링 도구는 전부 그것을 읽는다.

`/proc`은 디스크에 없는 가상 파일시스템이다. 커널 내부 상태를 파일처럼 읽을 수 있게 해 준다.

```bash
cat /proc/self/status        # 지금 이 프로세스의 상태 (VmRSS, Threads, State...)
ls -l /proc/self/fd          # 열린 파일 디스크립터 목록
cat /proc/self/maps          # 가상 주소 공간 레이아웃
cat /proc/cpuinfo            # CPU 정보
cat /proc/meminfo            # 시스템 메모리 통계
cat /proc/loadavg            # load average
cat /proc/sys/fs/file-max    # 시스템 전체 fd 한도 (쓰기도 가능 - 커널 파라미터 변경)
```

`ps`, `top`, `free`, `lsof` 같은 도구는 전부 `/proc`을 읽어서 보여주는 것이다. 그래서 도구가 없는 최소 컨테이너 환경에서도 `cat /proc/...`만은 항상 된다. 이 책의 거의 모든 장에서 `/proc`이 다시 등장한다.

## 코어 2. 유저 → 커널의 문은 세 개뿐

### 2.1 커널 모드와 유저 모드

**한 줄 요약:** 유저 코드는 세 경로로만 커널에 들어가고, 커널은 인터럽트로 언제든 유저 코드를 끊을 수 있다.

x86-64에서 CPU는 ring 0(커널)과 ring 3(유저)을 구분한다.

- **유저 모드**: 내 프로그램이 도는 곳. 자기 가상 주소 공간의 메모리만 접근할 수 있고 하드웨어에 직접 명령을 내릴 수 없다.
- **커널 모드**: 커널이 도는 곳. 모든 메모리와 하드웨어에 접근할 수 있다.

유저 모드에서 커널 모드로 들어가는 길은 정확히 세 가지다.

1. **시스템 콜** — 프로그램이 명시적으로 요청 (`read`, `write`, `mmap`...)
2. **인터럽트** — 하드웨어가 알림 (패킷 도착, 타이머 틱, 디스크 I/O 완료)
3. **예외/폴트** — CPU가 명령 실행 중 문제를 감지 (페이지 폴트, 0으로 나누기, 잘못된 주소 접근)

이 외에는 유저 코드가 커널을 "부를" 방법이 없다. 반대로 커널은 언제든(인터럽트로) 유저 코드를 중단시키고 다른 일을 할 수 있다. 이 비대칭이 격리와 보호의 근간이다.

### 2.2 시스템 콜 한 번의 내부 경로

**한 줄 요약:** 시스템 콜은 비싸고, glibc 함수는 대부분 래퍼이며, `strace`로 전부 보인다.

```c
ssize_t n = read(fd, buf, 4096);
```

이 한 줄에서 실제로 벌어지는 일은 다음과 같다.

```
유저 모드                              커널 모드
────────────────────────────────────────────────────────────
read(fd, buf, 4096)   ← glibc 래퍼 함수
  │ rax = 0 (SYS_read), rdi=fd, rsi=buf, rdx=4096
  │ syscall 명령         ────────────▶  entry_SYSCALL_64
  │                                      ├ 인자 검증 (buf가 정말 유저 메모리인가?)
  │                                      ├ fd → struct file 조회
  │                                      ├ 파일시스템/소켓/파이프의 read 구현 호출
  │                                      │   (데이터가 없으면 여기서 프로세스를 잠재움)
  │                                      └ 결과를 rax에 담아 복귀
  │ ◀──────────────────────────────────  sysret
  │ rax < 0 이면 errno = -rax, 반환값 -1
  ▼
n
```

기억할 것은 세 가지다.

- **비용**: 시스템 콜 하나는 함수 호출보다 훨씬 비싸다(수십&#126;수백 ns, Spectre 완화 패치가 있으면 더). 그래서 `read`를 1바이트씩 부르는 코드는 느리고, stdio가 버퍼링을 하는 이유도 이것이다.
- **glibc는 래퍼일 뿐**: `read()`, `malloc()`, `printf()`는 라이브러리 함수다. `malloc`은 가끔만 `brk`/`mmap`을 부르고 `printf`는 버퍼가 찰 때만 `write`를 부른다. **어떤 함수가 실제로 커널을 부르는지** 구분하는 감각이 성능 분석의 시작이다.
- **`strace`로 보면 다 나온다**: `strace -c ./myprog`는 부른 시스템 콜을 종류별로 집계한다 ([8장](08-진단-도구.md)).

### 2.3 errno: 커널의 실패 통보 규약

**한 줄 요약:** 실패는 -1 + `errno`이고, 서버 개발에서 자주 보는 일곱 개를 외운다.

시스템 콜이 실패하면 -1을 반환하고 전역(정확히는 스레드 로컬) 변수 `errno`에 이유를 넣는다.

```c
int fd = open("data.txt", O_RDONLY);
if (fd == -1) {
    perror("open");            // "open: No such file or directory"
    // errno == ENOENT
}
```

| errno | 의미 | 실무에서 만나는 상황 |
|---|---|---|
| `EINTR` | 시그널에 의해 시스템 콜이 중단됨 | 블로킹 `read`/`accept` 중 시그널 도착. **재시도해야 한다** ([3장](03-시그널.md)) |
| `EAGAIN` / `EWOULDBLOCK` | 지금은 데이터가 없음(논블로킹) | 논블로킹 소켓에서 정상적인 상황. 에러가 아니다 |
| `EMFILE` | 프로세스의 fd 한도 초과 | `ulimit -n` 기본 1024. 커넥션 많은 서버에서 흔함 |
| `ENOMEM` | 메모리 부족 | 오버커밋 때문에 실제로는 거의 안 나온다 ([4장](04-메모리.md)) |
| `EPIPE` | 닫힌 파이프/소켓에 쓰기 | 상대가 끊었는데 `write`. 기본은 `SIGPIPE`로 프로세스가 죽는다 |
| `ECONNRESET` | 상대가 RST를 보냄 | 클라이언트가 비정상 종료 |
| `EADDRINUSE` | 주소가 이미 사용 중 | `TIME_WAIT` 소켓, `SO_REUSEADDR` 누락 |

`errno`는 성공한 호출에서 변경되지 않을 뿐 **초기화도 안 된다.** 실패를 확인한 직후에만 읽어야 한다.

### 2.4 인터럽트: 커널이 내 CPU 시간을 쓰는 순간

**한 줄 요약:** `%si`/`%hi`가 높으면 내 코드가 아니라 커널이 인터럽트 처리에 CPU를 쓰는 중이다.

네트워크 카드에 패킷이 도착하면 CPU에 인터럽트가 걸린다. 그 순간 어떤 프로세스가 돌고 있었건 CPU는 커널의 인터럽트 핸들러로 점프한다. 핸들러가 패킷을 큐에 넣고 복귀하면 원래 프로세스가 재개된다.

- `top`의 `%si`(softirq), `%hi`(hardirq)가 높다면 커널이 인터럽트 처리에 CPU를 쓰고 있다는 뜻이다. 패킷이 초당 수백만 개 들어오는 서버에서 흔하다.
- 내 스레드가 "아무것도 안 했는데" 지연이 튄다면 인터럽트나 다른 프로세스에 CPU를 빼앗긴 것일 수 있다. 시스템 전체 관점 없이 내 코드만 프로파일링하면 원인을 못 찾는다.

## 코어 3. 스케줄러와 태스크 상태 R/S/D/Z

### 3.1 스케줄러의 단위는 태스크

**한 줄 요약:** 커널은 프로세스와 스레드를 구분하지 않고 `task_struct` 하나로 다루며, runnable 태스크 사이에서 CPU를 나눈다.

리눅스 스케줄러의 단위는 **태스크**다. 스케줄러는 "실행 가능한(runnable)" 태스크들 사이에서 CPU 시간을 나눈다. 스레드가 곧 태스크라는 점은 [7장](07-스레드와-동시성.md)에서 다시 본다.

### 3.2 태스크의 상태

**한 줄 요약:** R(실행·대기), S(깨울 수 있는 대기), D(깨울 수 없는 대기), Z(좀비). D는 load에 포함된다.

```
          fork/clone
              │
              ▼
   ┌──────▶ Runnable (R) ──── 스케줄러가 선택 ────▶ Running
   │            ▲                                     │
   │            │ 이벤트 발생(데이터 도착, 락 해제 등)    │ I/O 대기, sleep, 락 대기
   │            │                                     ▼
   │        Sleeping ◀────────────────────────────────┘
   │         (S: interruptible / D: uninterruptible)
   │
   └──── 타임슬라이스 소진 또는 더 급한 태스크 등장(preemption)

   종료 → Zombie (Z) → 부모가 wait() → 소멸
```

`ps`/`top`의 STAT 컬럼이 이것이다.

| 상태 | 의미 |
|---|---|
| **R** | 실행 중이거나 실행 대기 중. CPU를 원하는 태스크가 코어 수보다 많으면 `load average`가 올라간다 |
| **S** | 인터럽트 가능한 대기. `read`로 데이터를 기다리거나 `sleep` 중이며 시그널로 깨울 수 있다. 서버 프로세스의 대부분은 평소에 이 상태 |
| **D** | 인터럽트 불가능한 대기(주로 디스크 I/O, NFS). **`kill -9`로도 안 죽는다.** 많으면 I/O 병목이다 |
| **Z** | 좀비. 종료했지만 부모가 회수하지 않음 ([2장](02-프로세스.md)) |

D 상태도 load average에 포함된다. CPU는 놀고 있는데 load가 높은 이유다.

### 3.3 공평한 분배: CFS에서 EEVDF로

**한 줄 요약:** 가장 적게 실행된 태스크를 고르고, nice는 가중치이며, 실시간 정책은 일반 서버 코드에서 쓰지 않는다.

리눅스는 오랫동안 **CFS(Completely Fair Scheduler)**를 썼고 6.6부터 **EEVDF**로 교체됐다. 두 가지의 핵심 아이디어는 같다.

- 각 태스크의 **가상 실행 시간(vruntime)**을 추적하고 가장 적게 실행된 태스크를 다음에 고른다.
- **nice 값(-20 &#126; +19)**은 가중치다. nice가 낮을수록 vruntime이 느리게 쌓여 더 많은 CPU를 받는다. `nice -n 10 ./batch_job`은 "다른 것들에 양보하라"는 뜻이다.
- 고정된 타임슬라이스는 없다. 실행 가능한 태스크 수에 따라 동적으로 정해진다(기본 목표 지연 6ms 정도, 태스크가 많으면 최소 0.75ms 정도까지 줄어듦).

프로그래머에게 중요한 결과는 세 가지다.

- **I/O 바운드 태스크는 자연히 우선권을 얻는다.** 자주 잠들어서 vruntime이 적게 쌓이기 때문이다.
- **스레드를 코어 수보다 훨씬 많이 만들어도 얻는 게 없다.** CPU 바운드라면 스레드 수 = 코어 수가 상한이다. 그 이상은 컨텍스트 스위칭 비용만 늘린다.
- **`SCHED_FIFO`/`SCHED_RR`(실시간 정책)**은 일반 태스크보다 항상 우선한다. 잘못 쓰면 시스템이 멈추므로 일반 서버 코드에서는 쓸 일이 거의 없다.

### 3.4 컨텍스트 스위칭의 진짜 비용

**한 줄 요약:** 비용은 레지스터 저장이 아니라 캐시 오염과 TLB 플러시이고, `vmstat`의 `cs`로 의심한다.

전환의 직접 비용(레지스터 저장/복원)은 1&#126;2µs 정도로 크지 않다. 진짜 비용은 **간접 비용**이다.

- **CPU 캐시 오염**: 새 태스크가 L1/L2를 자기 데이터로 채우며 이전 태스크의 캐시가 밀려난다. 돌아왔을 때 캐시 미스가 쏟아진다.
- **TLB 플러시**: 다른 프로세스로 전환하면 주소 공간이 바뀌어 TLB가 무효화된다(같은 프로세스의 스레드 간 전환은 이 비용이 없다).

`vmstat 1`의 `cs` 컬럼으로 초당 컨텍스트 스위치 수를 본다. 수만&#126;수십만이면 "스레드가 너무 많거나 락 경합이 심하다"는 신호다.

## 코어 4. 컨테이너 CPU 제한 = cgroup 쿼터

### 4.1 `--cpus`는 대역폭 쿼터다

**한 줄 요약:** `--cpus=2`는 100ms마다 200ms의 쿼터이고, 다 쓰면 컨테이너 안 모든 태스크가 다음 주기까지 멈춘다.

도커의 `--cpus=2`는 **cgroup의 CPU 대역폭 제어**다. 100ms 주기마다 200ms의 CPU 시간(2코어분)을 쿼터로 준다. 쿼터를 다 쓰면 다음 주기까지 컨테이너 안의 모든 태스크가 **스로틀링**된다.

함정: 스레드가 16개인데 `--cpus=2`라면, 16개가 동시에 뛰어들어 12.5ms 만에 쿼터를 소진하고 나머지 87.5ms를 통째로 멈춘다. 지연 시간이 들쭉날쭉해지는 전형적인 원인이다.

```bash
cat /sys/fs/cgroup/cpu.stat    # nr_throttled, throttled_usec 확인
```

### 4.2 대응: 쿼터에 맞춘 스레드 풀

**한 줄 요약:** 스레드 풀 크기를 호스트 코어 수가 아니라 쿼터에 맞추고, `nr_throttled`로 검증한다.

많은 런타임(Java 10+, Go 1.25+, .NET)이 cgroup 한도를 자동 인식하지만, 직접 `nproc`이나 `sysconf(_SC_NPROCESSORS_ONLN)`으로 코어 수를 읽는 코드는 **호스트의 코어 수**를 얻는다. C++ 서버가 시작 시 코어 수로 워커 수를 정한다면 이 지점을 직접 점검해야 한다.

> **[보충]** 쿠버네티스의 `resources.limits.cpu`도 이 cgroup 쿼터로 변환된다. 변환 과정은 [25장](../3부-쿠버네티스-구성-요소/25-Pod-생명주기와-리소스.md), cgroup 자체의 구조는 [10장](../2부-컨테이너-커널-기능과-Docker/10-cgroup.md)에서 다룬다. 지금은 "컨테이너 CPU 제한 = 커널 cgroup 기능"만 기억하면 충분하다.

### 3. 기억 고리

- **C++ 유추:** 워커 수 = 코어 수 ⚠️ 컨테이너에서는 코어 수가 호스트 값으로 읽혀 쿼터와 어긋나고, 남는 스레드는 처리량이 아니라 스로틀링을 만든다.
- **C++ 유추:** `recv`/`send` = 시스템 콜 ⚠️ 컨테이너도 같은 호스트 커널을 쓰므로 "컨테이너 안 커널"은 없다. 제한은 그 커널의 cgroup 기능이다.
- **비유:** 시스템 콜 = 관공서 창구. 직접 금고(하드웨어)에 손대지 못하고 창구 직원(커널)에게 서류를 내며, 한 번 갈 때마다 번호표 비용이 든다(그래서 모아서 간다 = 버퍼링). ⚠️ 창구는 손님이 부를 때만 일하지만 커널은 인터럽트로 언제든 내 실행을 끊고 끼어든다.
- **비유:** cgroup CPU 쿼터 = 100ms마다 충전되는 교통카드 잔액. 16명이 한꺼번에 쓰면 금방 바닥나고 다음 충전까지 모두 못 탄다. ⚠️ "못 탄다"는 거부나 에러가 아니라 다음 주기까지의 일시 정지이고, 카드 한 장을 컨테이너 안 모든 태스크가 같이 쓴다.
- **묶음(3의 법칙):** 커널 진입 3경로(시스템 콜·인터럽트·예외) / 시스템 콜 기억 3가지(비용·glibc 래퍼·strace) / 이 장의 도입 상황 3개(`--cpus` 지연·load·`%si`).
- **대칭·순서:** S(깨울 수 있음) ↔ D(깨울 수 없음). 상태 흐름: fork → R → Running → S/D → R … → Z → wait → 소멸.

### 4. 가르치기 · 반대편 서기

- **거울 설명 (1분, 원고 없이):** "`read()` 한 줄이 커널에서 무슨 일을 하는가"를 처음 듣는 사람에게 설명해 보세요. 막히는 지점 = 지식의 구멍.
- **C++ 서버 동료에게 설명하기:** "우리 서버를 `--cpus=2` 컨테이너에 넣으면 왜 워커 스레드 수를 다시 정해야 하는가"를 쿼터와 스로틀링으로 1분 안에 설명해 보세요.
- **랜덤 논리 게임:** A "스레드를 많이 만들수록 처리량이 늘어난다" vs B "CPU 바운드라면 스레드 수는 코어(쿼터) 수가 상한이다" — 양쪽을 번갈아 변호해 보세요. (컨텍스트 스위칭 비용, 스로틀링, I/O 바운드 태스크를 근거로)
