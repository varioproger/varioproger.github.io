# 7장. 스레드와 동시성

> **🎮 게임 서버 개발자에게** — 스레드 풀, 뮤텍스, 조건 변수, `std::atomic`을 써 봤다면 이 장의 API는 낯설지 않다. 새로운 것은 **커널의 눈으로 본 스레드**다. 리눅스에게 스레드와 프로세스는 같은 `task_struct`이고 차이는 "무엇을 공유하느냐"뿐이다. 이 관점이 있으면 컨테이너(공유 대신 격리 플래그를 주는 `clone`)가 왜 같은 메커니즘인지 자연스럽게 이어지고, `--cpus` 쿼터와 스레드 수 문제도 명확해진다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 서버가 가끔 완전히 멈춘다(hang). CPU는 0%이고 로그도 없다.
> - 코어를 늘렸는데 처리량이 안 늘고, `vmstat`의 `cs`(컨텍스트 스위치)만 폭증한다.
> - 스레드별 통계 카운터를 만들었는데 락도 없는데 이상하게 느리다.

## 코어 — 이것만은 100%

> **한 문장:** 스레드는 `clone` 플래그로 주소 공간·fd 등을 공유하는 커널 태스크이고, 공유 때문에 원자성과 가시성 문제가 생기며, 락 자체는 싸지만 경합이 비싸고, 스레드 수는 작업 성격과 CPU 쿼터로 정한다.

1. **스레드 = 공유 플래그가 다른 태스크** — `pthread_create`는 `clone(CLONE_VM|CLONE_FILES|…)`이다. 힙·fd는 공유, 스택·errno·TID는 별도.
2. **동기화는 두 문제를 푼다** — 원자성(`counter++`)과 가시성·순서(`data=42; ready=true;`). 데이터 레이스는 정의되지 않은 동작이고 `volatile`은 해결책이 아니다.
3. **락은 싸고 경합이 비싸다** — 뮤텍스는 futex 위에 있어서 경합이 없으면 유저 공간 원자 연산 한 번이다. 경합이 있으면 `futex` 시스템 콜로 잠들고 깨운다.
4. **조건 변수와 데드락** — `cond_wait`는 `while`로 감싸고, 락에 전역 순서를 정하며, 멈추면 `gdb`로 `thread apply all bt`.
5. **스레드 수와 캐시 라인** — CPU 바운드는 코어(쿼터) 수, 블로킹 I/O는 공식, 네트워크는 이벤트 루프. 같은 캐시 라인의 변수는 거짓 공유를 만든다.

## 코어 1. 스레드 = 공유 플래그가 다른 태스크

### 1.1 커널의 눈으로 본 스레드

**한 줄 요약:** 커널은 스레드와 프로세스를 구분하지 않고, 차이는 `clone`에 준 공유 플래그뿐이다.

프로그래머에게 스레드는 "프로세스 안의 실행 흐름"이다. 리눅스 커널에게는 조금 다르다. **커널은 스레드와 프로세스를 구분하지 않는다.** 둘 다 `task_struct`이고, 스케줄러의 단위다([1장](01-커널-시스템콜-스케줄러.md)). 차이는 오직 **무엇을 공유하는가**다.

```c
// pthread_create()가 내부적으로 부르는 것
clone(fn, stack, CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND |
                 CLONE_THREAD | CLONE_SYSVSEM | CLONE_SETTLS | ..., arg);
```

- `CLONE_VM`: 주소 공간 공유 → 같은 힙, 같은 전역 변수
- `CLONE_FILES`: fd 테이블 공유 → 한 스레드가 연 소켓을 다른 스레드가 쓸 수 있음
- `CLONE_SIGHAND`: 시그널 핸들러 공유
- `CLONE_THREAD`: 같은 **스레드 그룹(TGID)**에 속함 → `getpid()`가 같은 값

`fork`는 이 플래그를 하나도 안 준 `clone`이다. 스레드는 대부분 준 `clone`이다. 그 사이의 조합(예: 주소 공간만 공유하는 프로세스)도 가능하며, 컨테이너 런타임이 네임스페이스 플래그(`CLONE_NEWPID`, `CLONE_NEWNET`)를 추가해 컨테이너를 만든다([9장](../2부-컨테이너-커널-기능과-Docker/09-네임스페이스.md)).

### 1.2 공유하는 것 / 스레드마다 따로 가지는 것

**한 줄 요약:** 주소 공간·fd·핸들러는 공유, 스택·errno·TID는 별도.

| 공유 (프로세스 단위) | 스레드마다 별도 |
|---|---|
| 주소 공간 (힙, 전역, 코드) | 스택 (기본 8MB, `RLIMIT_STACK`) |
| fd 테이블 | 레지스터, 프로그램 카운터 |
| 시그널 핸들러 설정 | 시그널 마스크, pending 시그널(스레드 단위) |
| 현재 디렉터리, umask | `errno` |
| PID(=TGID) | TID (`gettid()`), 스케줄링 정책/nice |

`ps -eLf` 또는 `top -H`로 스레드를 볼 수 있다. `/proc/<pid>/task/<tid>/`에 스레드별 정보가 있다. 스레드 이름은 `pthread_setname_np`로 붙일 수 있고 `top -H`에 표시된다. **디버깅 때 큰 도움이 되므로 스레드 풀에는 이름을 붙여라.**

### 1.3 스레드 생성 비용과 스택

**한 줄 요약:** 8MB 스택은 가상 주소 예약일 뿐이지만, 1만 스레드는 여전히 나쁜 설계다.

```c
pthread_t t;
pthread_create(&t, NULL, worker, arg);   // ~10µs 수준
pthread_join(t, NULL);                   // 종료 대기 (또는 pthread_detach)
```

- 스레드 스택은 `mmap`으로 할당된다. **8MB는 가상 주소 공간만 예약**된 것이고, 실제 물리 메모리는 사용한 만큼만 든다([4장](04-메모리.md)). 그래서 스레드 1만 개도 가상 주소 공간(80GB)은 128TB 안에 들어간다. 하지만 스레드별 커널 구조체와 최소 몇 페이지의 스택은 실제로 쓰이므로 1만 스레드는 여전히 나쁜 설계다.
- **join하지 않은 스레드는 좀비 프로세스와 같다.** 종료해도 스택 등이 회수되지 않는다. `pthread_detach`하거나 `pthread_join`해야 한다([2장](02-프로세스.md)의 좀비).
- 스택 오버플로는 `SIGSEGV`로 나타난다. 재귀가 깊거나 큰 지역 배열이 원인이다. 큰 버퍼는 힙에 두자.

## 코어 2. 동기화가 푸는 두 가지 문제

### 2.1 원자성과 가시성·순서

**한 줄 요약:** `counter++`는 3단계라 끼어들 수 있고, `ready` 플래그를 봐도 `data`가 보인다는 보장은 없다.

스레드가 힙을 공유하기 때문에 두 가지 별개의 문제가 생긴다.

**문제 1: 원자성(atomicity)**. `counter++`는 "읽기 → 더하기 → 쓰기" 세 단계다. 두 스레드가 끼어들면 한 번의 증가가 사라진다.

**문제 2: 가시성(visibility)과 순서(ordering)**. 스레드 A가 `data = 42; ready = true;`를 실행했다. 스레드 B가 `ready == true`를 봤다. 그러면 B가 `data`를 읽을 때 42가 보장되는가? **아니다.** 컴파일러가 두 대입의 순서를 바꿀 수 있고, CPU도 (특히 ARM에서) 저장 순서를 바꿀 수 있고, A의 코어 캐시에 있는 값이 B의 코어까지 아직 안 갔을 수 있다.

### 2.2 동기화 프리미티브와 실무 규칙

**한 줄 요약:** 락과 acquire/release는 원자성뿐 아니라 메모리 배리어를 포함하고, 데이터 레이스는 정의되지 않은 동작이다.

두 문제 모두를 해결하는 것이 **동기화 프리미티브**다. 뮤텍스의 `lock`/`unlock`, 원자 연산의 acquire/release는 원자성뿐 아니라 **메모리 배리어**를 포함한다. "락을 잡고 쓴 것은 같은 락을 잡은 다른 스레드에게 보인다"는 보장이 그 배리어에서 나온다.

**실무 규칙**: 데이터 레이스(동기화 없는 공유 변수 쓰기+읽기)는 C/C++에서 **정의되지 않은 동작**이다. "가끔만 틀리는 정도"가 아니라 컴파일러가 코드를 아예 지워 버릴 수 있다. `volatile`은 해결책이 아니다(컴파일러 최적화만 막고 CPU 순서는 못 막는다). 원자 타입(`_Atomic`, `std::atomic`)이나 락을 써라.

ThreadSanitizer(`gcc -fsanitize=thread`)는 데이터 레이스를 런타임에 잡아 준다. 테스트에서 켜 두는 것을 강력히 권한다([8장](08-진단-도구.md)).

## 코어 3. 락은 싸고 경합이 비싸다

### 3.1 뮤텍스와 futex

**한 줄 요약:** 경합이 없으면 유저 공간 원자 연산 한 번(약 20ns), 경합이 있으면 `futex` 시스템 콜로 잠들고 깨운다(µs).

```c
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
pthread_mutex_lock(&m);
/* 임계 영역 */
pthread_mutex_unlock(&m);
```

glibc의 뮤텍스는 **futex(fast userspace mutex)** 위에 구현되어 있다. 핵심 아이디어는 다음과 같다.

1. **경합이 없으면** 유저 공간에서 원자 연산(CAS) 한 번으로 끝난다. 시스템 콜 없음. 약 20ns.
2. **경합이 있으면** `futex(FUTEX_WAIT)` 시스템 콜로 커널에 잠들고, unlock하는 쪽이 `futex(FUTEX_WAKE)`로 깨운다. 여기서부터 µs 단위.

### 3.2 경합 줄이기

**한 줄 요약:** 임계 영역은 짧게, 락은 잘게 나누고, 단순한 것은 원자 연산으로.

따라서 **락 자체는 싸다. 비싼 것은 경합(contention)이다.** 경합이 심한 락은 스레드들을 계속 잠들고 깨우게 만들어 컨텍스트 스위치를 폭증시킨다(`vmstat`의 `cs`).

- 임계 영역을 짧게. 락 안에서 I/O나 `malloc`을 하지 않는다.
- 락을 잘게 나눈다(striped lock, 샤딩). 단일 전역 락은 코어가 늘어도 확장되지 않는다.
- 읽기가 대부분이면 `pthread_rwlock` 또는 RCU 스타일. 단, rwlock은 writer 기아나 오히려 느린 경우가 있어 벤치마크 없이 쓰면 안 된다.
- 카운터처럼 단순한 것은 원자 연산으로.

`strace`에 `futex(...)` 호출이 잔뜩 보이면 락 경합이다. `perf lock`이나 `mutrace`로 어느 락인지 찾을 수 있다.

## 코어 4. 조건 변수와 데드락

### 4.1 조건 변수: "무언가 일어나기를 기다린다"

**한 줄 요약:** `cond_wait`는 반드시 `while`로 감싸 조건을 다시 확인한다.

```c
pthread_mutex_lock(&m);
while (queue_empty())               // if가 아니라 반드시 while
    pthread_cond_wait(&cv, &m);     // m을 놓고 잠들고, 깨어나면 다시 m을 잡음
item = queue_pop();
pthread_mutex_unlock(&m);
```

`while`인 이유: **spurious wakeup**(이유 없는 깨어남)이 허용되고, 깨어난 뒤 락을 다시 잡기 전에 다른 스레드가 큐를 비울 수 있기 때문이다. 조건은 항상 다시 확인해야 한다.

`pthread_cond_signal`은 하나만, `broadcast`는 전부 깨운다. 잘못 쓰면 **thundering herd**(전부 깨어나 하나만 성공하고 나머지는 다시 잠듦)로 CPU를 낭비한다.

### 4.2 데드락과 그 친구들

**한 줄 요약:** 락에 전역 순서를 정하고, 멈추면 `gdb -p`로 모든 스레드의 스택을 본다.

**데드락**: A가 락1을 잡고 락2를 기다리고, B가 락2를 잡고 락1을 기다린다. 영원히 멈춘다.

예방의 실질적 규칙: **모든 락에 전역 순서를 정하고 항상 그 순서로만 잡는다.** 두 계좌 간 이체처럼 순서가 동적이면 주소나 ID 순으로 정렬해서 잡는다. `pthread_mutex_trylock`과 타임아웃은 회피책일 뿐, 설계로 막아야 한다.

진단: 멈춘 프로세스에 `gdb -p <pid>`를 붙여 `thread apply all bt`. 각 스레드가 어느 락에서 `futex_wait`하고 있는지 보인다([8장](08-진단-도구.md)).

**라이브락**: 서로 양보하느라 아무도 진행 못 함. **기아(starvation)**: 특정 스레드가 계속 락을 못 잡음. **우선순위 역전**: 낮은 우선순위 스레드가 잡은 락을 높은 우선순위 스레드가 기다리는데, 중간 우선순위 스레드가 CPU를 다 가져가는 상황. 실시간 시스템 외에는 드물다.

## 코어 5. 스레드 수와 캐시 라인

### 5.1 스레드 안전성과 TLS

**한 줄 요약:** 정적 버퍼를 쓰는 함수는 `_r` 버전을 쓰고, `errno`는 스레드 로컬이라 안전하다.

함수가 **스레드 안전(thread-safe)**하다는 것은 여러 스레드가 동시에 불러도 된다는 뜻이다. 안전하지 않은 고전적 함수들:

- `strtok`, `localtime`, `gethostbyname`, `readdir`, `rand` — 내부 정적 버퍼를 쓴다. `_r` 접미 버전(`strtok_r`, `localtime_r`)을 써라.
- `errno`는 스레드 로컬이므로 안전하다.

**스레드 로컬 저장소(TLS)**: 변수를 스레드마다 하나씩 갖게 한다.

```c
__thread int per_thread_counter;   // 또는 C11의 _Thread_local, C++의 thread_local
```

`errno`가 이렇게 구현된다. 스레드별 캐시, 스레드별 malloc 아레나, 스레드별 로그 컨텍스트에 쓴다. 남용하면 스레드 수가 많을 때 메모리를 많이 먹는다.

### 5.2 캐시 라인과 거짓 공유(false sharing)

**한 줄 요약:** 서로 무관한 변수도 같은 64바이트 캐시 라인이면 코어 간에 왕복해 10배 느려질 수 있다.

CPU는 메모리를 **64바이트 캐시 라인** 단위로 가져온다. 두 스레드가 각자 다른 변수를 쓰는데, 그 두 변수가 **같은 캐시 라인**에 있으면, 서로 무관한데도 코어 간 캐시 라인이 계속 왕복(ping-pong)한다. 락도 없고 데이터 레이스도 없는데 10배 느려질 수 있다.

```c
struct {
    _Atomic long counter_a;  // 스레드 A가 씀
    _Atomic long counter_b;  // 스레드 B가 씀 → 같은 캐시 라인! 거짓 공유
} bad;

struct {
    _Atomic long counter_a;
    char pad[64 - sizeof(long)];     // 캐시 라인 분리 (alignas(64)로도 가능)
    _Atomic long counter_b;
} good;
```

스레드별 통계 카운터 배열이 전형적인 피해자다. `perf c2c`로 진단할 수 있다.

### 5.3 스레드와 시그널

**한 줄 요약:** 시그널 핸들러는 임의의 한 스레드에서 실행되므로, 전용 스레드 하나가 `sigwait`/`signalfd`로 받는다.

시그널은 프로세스에 오지만, **핸들러는 임의의 한 스레드**에서 실행된다(마스크하지 않은 스레드 중 하나). 이것이 멀티스레드 프로그램에서 시그널을 다루기 어려운 이유다. 표준 패턴: 모든 워커 스레드에서 `pthread_sigmask`로 시그널을 막고, 전용 스레드 하나가 `sigwait` 또는 `signalfd`로 동기적으로 받는다([3장](03-시그널.md)).

### 5.4 몇 개의 스레드가 적당한가

**한 줄 요약:** CPU 바운드는 코어(쿼터) 수, 블로킹 I/O는 대기 비율만큼 더, 네트워크는 이벤트 루프.

| 작업 성격 | 권장 스레드 수 | 이유 |
|---|---|---|
| CPU 바운드 (계산) | 코어 수 (cgroup 쿼터 기준) | 더 많으면 컨텍스트 스위칭만 늘어남 |
| 블로킹 I/O 바운드 (동기 DB 호출 등) | 코어 수 × (1 + 대기시간/계산시간) | 대기 중인 스레드는 CPU를 안 씀 |
| 네트워크 I/O 대량 | 코어 수 개의 이벤트 루프 + epoll | 스레드 대신 이벤트로 대기 ([6장](06-네트워크-스택.md)) |

"스레드 하나당 커넥션 하나" 모델은 커넥션 수천 개까지는 단순하고 잘 돈다. 그 이상이면 스레드 생성·스위칭·스택 메모리가 병목이 되어 이벤트 기반(epoll)이나 M:N 런타임(Go의 goroutine, Java의 virtual thread)으로 넘어간다. 이 런타임들도 **결국 아래에서는 코어 수 정도의 커널 스레드 + epoll**을 쓴다.

> **[보충]** 컨테이너에서 "코어 수 (cgroup 쿼터 기준)"이 왜 중요한지는 [10장](../2부-컨테이너-커널-기능과-Docker/10-cgroup.md)에서 cgroup CPU 컨트롤러로 다시 다룬다.

### 시나리오로 확인하기

1. **상황:** 운영 중 서버가 완전히 멈췄다. CPU는 0%이고 프로세스는 살아 있고 로그도 없다.
   **질문:** 어떻게 원인을 찾나?

   <details markdown="1"><summary>답 확인</summary>

   데드락을 의심한다. 멈춘 프로세스에 `gdb -p <pid> -batch -ex 'thread apply all bt'`로 붙어 모든 스레드의 스택을 뽑고, `futex_wait`나 `pthread_mutex_lock`에서 멈춘 스레드를 찾는다. 프레임에서 뮤텍스 주소를 확인해 `__owner`(소유 스레드 TID)로 순환을 찾는다. 예방은 락의 전역 순서다. → 코어 4

   </details>

2. **상황:** 코어를 늘렸는데 처리량은 그대로이고 `vmstat 1`의 `cs`가 수십만이다. `strace -f -e trace=futex`에 호출이 쏟아진다.
   **질문:** 원인과 대응은?

   <details markdown="1"><summary>답 확인</summary>

   락 경합이다. 경합이 있으면 스레드들이 `futex` 시스템 콜로 계속 잠들고 깨면서 컨텍스트 스위치가 폭증한다. 임계 영역을 줄이고(락 안에서 I/O·`malloc` 금지), 단일 전역 락을 샤딩하며, 단순 카운터는 원자 연산으로 바꾼다. `perf lock`으로 어느 락인지 찾는다. → 코어 3

   </details>

3. **상황:** 스레드별 통계 카운터 배열(`std::atomic<long> stats[N]`)을 만들었다. 락도 레이스도 없는데 스레드를 늘릴수록 느려진다.
   **질문:** 왜인가?

   <details markdown="1"><summary>답 확인</summary>

   거짓 공유다. 인접 원소가 같은 64바이트 캐시 라인에 있어서 서로 무관한 쓰기가 코어 간 캐시 라인 왕복을 일으킨다. 원소마다 `alignas(64)`나 패딩으로 캐시 라인을 분리하고, `perf c2c`로 확인한다. → 코어 5

   </details>

4. **상황:** 큐에서 일을 꺼내는 워커 코드가 `if (queue_empty()) cond_wait(...)` 후 바로 `pop`한다. 가끔 빈 큐에서 pop하다 크래시한다.
   **질문:** 무엇이 문제인가?

   <details markdown="1"><summary>답 확인</summary>

   `if`가 아니라 `while`로 조건을 다시 확인해야 한다. spurious wakeup이 허용되고, 깨어난 뒤 락을 다시 잡기 전에 다른 스레드가 큐를 비울 수 있다. → 코어 4

   </details>

1. 리눅스 커널은 스레드와 프로세스를 어떻게 구분하는가?

2. 스레드가 공유하는 것과 따로 가지는 것을 각각 세 가지씩 말하라.

   공유: 주소 공간(힙·전역·코드), fd 테이블, 시그널 핸들러 설정, 현재 디렉터리·umask, PID(=TGID). 별도: 스택(기본 8MB), 레지스터·프로그램 카운터, 시그널 마스크·pending, `errno`, TID, 스케줄링 정책/nice. → 코어 1

   보장되지 않는다. 컴파일러와 CPU(특히 ARM)가 순서를 바꿀 수 있고, 다른 코어에 값이 아직 안 갔을 수 있다. 락이나 원자 연산의 acquire/release가 가진 메모리 배리어로 해결하며, `volatile`은 CPU 순서를 못 막는다. → 코어 2

   <details markdown="1"><summary>답 확인</summary>

   CPU 바운드는 코어 수, 블로킹 I/O는 코어 수 × (1 + 대기시간/계산시간)이다. 컨테이너에서는 호스트 코어 수가 아니라 cgroup 쿼터가 기준이다. 대량 네트워크 I/O는 코어 수 개의 이벤트 루프 + epoll이다. → 코어 5

   </details>

### 3. 기억 고리

- **C++ 유추:** `std::thread` = 커널 `clone` ⚠️ 커널 눈에는 프로세스와 같은 `task_struct`이므로 "스레드는 가볍고 프로세스는 무겁다"가 아니라 "무엇을 공유하느냐"의 차이이고, 컨테이너도 같은 clone이다.
- **C++ 유추:** `std::mutex` = futex ⚠️ 비용은 락 호출이 아니라 경합이 낼 때 생기는 `futex` 시스템 콜과 컨텍스트 스위치에서 나온다.
- **비유:** 스레드 = 한 집(프로세스)에 사는 룸메이트. 냉장고(힙)와 현관(fd)은 공유하고, 각자 방(스택)과 칫솔(errno)은 따로다. ⚠️ 비유가 깨지는 지점: 커널에게는 "집"과 "룸메이트"의 구분이 없고, 모두 같은 종류의 입주자(`task_struct`)이며 공유 약정만 다르다.
- **비유:** 거짓 공유 = 한 쪽지에 두 사람의 메모를 적어 매번 주고받는 것. 서로 다른 칸에 적어도 쪽지(캐시 라인) 단위로 오가야 한다. ⚠️ 비유가 깨지는 지점: 쪽지 크기는 64바이트로 고정이고, 쪽지 이동은 눈에 안 보여서 락·레이스 검사에는 안 걸린다.
- **묶음(3의 법칙):** 동기화가 막는 문제(원자성·가시성·순서) / 락 경합 해법(짧게·잘게·원자 연산) / 진단 3종(`strace futex`·`perf lock`·`gdb bt`).
- **대칭·순서:** `FUTEX_WAIT` ↔ `FUTEX_WAKE`, `cond_wait` ↔ `signal/broadcast`, 락 "공유(CLONE_VM…)" ↔ 컨테이너 "격리(CLONE_NEW…)".

### 4. 가르치기 · 반대편 서기

- **거울 설명 (1분, 원고 없이):** "리눅스에서 스레드는 프로세스와 무엇이 같고 무엇이 다른가"를 처음 듣는 사람에게 설명해 보세요. 말이 막히는 지점 = 지식의 구멍.
- **C++ 서버 동료에게 설명하기:** "락이 싸다는데 왜 경합이 심하면 `cs`가 폭증하는가"를 futex 두 경로로 1분 안에 설명해 보세요.
- **랜덤 논리 게임:** A "공유 카운터는 `volatile`이면 충분하다" vs B "`volatile`은 해결책이 아니다" — 양쪽을 번갈아 변호해 보세요. (원자성, 가시성, 컴파일러/CPU 재정렬, 정의되지 않은 동작을 근거로)
- **AI 역할 반전:** "내가 데드락 진단 절차를 설명할 테니, 정답은 말하지 말고 틀리거나 빠진 부분만 질문으로 짚어 줘."
