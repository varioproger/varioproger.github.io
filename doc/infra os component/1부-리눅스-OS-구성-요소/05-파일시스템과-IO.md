# 5장. 파일시스템과 I/O

> **🎮 게임 서버 개발자에게** — 소켓을 fd로 다뤄 왔다면 파일도 똑같은 fd라는 점은 이미 익숙하다. 이 장에서 새로운 것은 fd 뒤의 **세 개의 커널 테이블**, 그리고 `write()`가 성공해도 데이터가 디스크에 없다는 사실이다. 플레이어 세이브 데이터, 설정 파일 핫 리로드, 로그 파일은 모두 이 규칙 위에 있다. 컨테이너에서는 여기에 이미지 레이어(overlayfs)와 볼륨이라는 파일시스템 계층이 더해진다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 게임 서버 로그 파일을 `rm`했는데 디스크 사용량이 줄지 않는다.
> - 서버가 크래시한 뒤 재시작했더니 세이브/설정 파일이 절반만 쓰인 채 깨져 있다.
> - 컨테이너 안에서 큰 파일을 수정하면 유난히 느리고, `docker logs`에는 서버 출력이 한참 뒤에야 나온다.

## 코어 — 이것만은 100%

> **한 문장:** 파일은 fd → open file → inode 세 계층으로 열리고, `write()`는 페이지 캐시까지만 보장하므로 영속성은 `fsync`와 `rename` 같은 원자 연산의 조합으로 직접 만든다.

1. **fd 3계층** — fd 테이블(프로세스별) → open file table(오프셋이 여기 있다) → inode(이름은 없다). `fork`/`dup`/`open` 두 번의 차이와 "`rm`해도 용량이 안 줄어드는" 현상이 모두 여기서 나온다.
2. **모든 것은 파일 + VFS** — 소켓·타이머·시그널·프로세스까지 fd가 되므로 `epoll_wait` 하나로 기다린다. 파일시스템이 달라도(ext4, tmpfs, NFS, overlayfs) `read()`는 같다.
3. **버퍼링 4층과 fsync** — stdio 버퍼 → 페이지 캐시 → 디스크 캐시 → 매체. `write` 성공은 "커널이 받았다"일 뿐이다. 새 파일은 디렉터리도 `fsync`한다.
4. **원자성: 임시 파일 + fsync + rename** — POSIX가 보장하는 원자 연산(`O_APPEND`, `rename`, `O_EXCL`)을 조합해 크래시에도 안 깨지는 파일 코드를 만들고, 프로세스 간 조율에는 권고 락을 쓴다.
5. **링크·inotify·디스크 성능 감각** — 하드/심볼릭 링크의 차이, 폴링 없는 변경 감시, 매체별 IOPS 한도(클라우드 디스크 포함).

## C++·TCP 서버 경험에서 출발하기

|---|---|---|---|
| 소켓 fd를 `read`/`write`/`close`/`epoll`로 다룸 | 파일도 fd | 같은 시스템 콜, 같은 fd 번호 체계 | **디스크 파일에는 epoll이 통하지 않는다**(항상 준비됨으로 나온다). 이벤트 루프 안에서 파일 I/O를 하면 루프가 멈춘다 |
| `send()`가 성공해도 상대가 받았다는 뜻은 아님 | `write()` 성공 ≠ 디스크에 기록 | 둘 다 "커널 버퍼에 넣었다"는 뜻 | 소켓은 ACK 재전송이 있지만, 페이지 캐시는 정전 시 그냥 사라진다. 영속성은 `fsync`로 직접 요청해야 한다 |
| `std::ofstream`/`fprintf` 로그 | stdio 버퍼 (유저 공간) | 버퍼가 차야 `write`가 나간다 | 터미널이면 줄 버퍼, **파일·파이프면 전체 버퍼**. 컨테이너 `docker logs`에서 출력이 늦거나 안 보이는 원인이다 |
| 패킷을 길이 접두어로 프레이밍 | 원자 연산(`rename`, `O_APPEND`) | "중간 상태가 관찰되지 않게" 만든다는 목적 | 파일은 `rename` 한 번으로 통째 교체가 된다. 제자리에 덮어쓰면 크래시 시 절반짜리 파일이 남는다 |
| `shared_ptr` 참조 수가 0이면 해제 | 링크 수 + 열린 fd 수가 0이면 inode 해제 | 참조가 남아 있으면 객체가 산다 | 참조에 **링크 수(이름)와 열린 fd 두 종류**가 있다. 이름을 지워도 fd가 열려 있으면 용량이 그대로다 |

> 2. 큰 로그 파일을 `rm`했는데 `df`는 그대로다. 용량은 어디에 남아 있을까?

> 4. 설정 파일을 덮어쓰는 도중 서버가 죽어도 파일이 안 깨지게 하려면 어떻게 써야 할까?
>
> **처리법:** 🛠 실습 `ls -l /proc/<pid>/fd`, `lsof +L1`, `cat /proc/<pid>/fdinfo/<fd>`, `grep -E 'Dirty|Writeback' /proc/meminfo`, `strace -e trace=file,desc -p <pid>` → 바로 실행 · 🗺 관계도 fd 테이블 → open file table → inode(이름은 dentry), 버퍼링 4층 · 📦 카드로 원자 연산 4종(`O_APPEND`, `rename`, `O_CREAT|O_EXCL`, `link`/`unlink`/`mkdir`), 락 3종(BSD/POSIX/OFD), 매체별 IOPS 표

### 이 장에서 배우는 것

- `open()`이 반환하는 정수 하나 뒤의 세 계층과 그것이 설명하는 현상들
- "모든 것은 파일"의 실제 범위와 VFS가 있어서 생기는 결과(overlayfs 포함)
- `write()`부터 디스크까지의 4층과 `fsync`, 크래시에도 안전한 파일 덮어쓰기 패턴
- 파일 락, 링크, inotify, 디스크 성능 감각

## 코어 1. fd 3계층

### 1.1 `open()` 뒤의 세 개의 커널 테이블

**한 줄 요약:** fd 테이블(프로세스별) → open file table(시스템 전체, 오프셋 보관) → inode(파일 실체, 이름 없음).

```
프로세스 A의 fd 테이블        시스템 전체 open file table          inode 테이블
┌────┬──────┐              ┌─────────────────────────┐        ┌──────────────┐
│ 0  │  ────┼──────────▶   │ 오프셋=0, 플래그=O_RDONLY  ├──────▶ │ inode 1234    │
│ 1  │  ────┼──────┐       ├─────────────────────────┤        │ (크기, 권한,   │
│ 2  │  ────┼──────┤       │ 오프셋=512, O_WRONLY|APPEND├──┐    │  블록 위치...)  │
│ 3  │  ────┼───┐  └─────▶ │ 오프셋=0, O_RDWR          │  │    └──────────────┘
└────┴──────┘   │          └─────────────────────────┘  │
                │                       ▲                │    ┌──────────────┐
프로세스 B (A를 fork)                    │                └──▶ │ inode 5678    │
┌────┬──────┐   │                       │                     └──────────────┘
│ 3  │  ────┼───┴───────────────────────┘  ← fork로 복제된 fd는 같은 open file을 가리킴
└────┴──────┘                                 → 오프셋을 공유한다!
```

1. **fd 테이블(프로세스별)**: 정수 → open file 항목 포인터. `fork`하면 복사되고, `dup`하면 같은 항목을 가리키는 새 번호가 생긴다.
2. **open file table(시스템 전체)**: 파일 오프셋, 열기 플래그(`O_APPEND`, `O_NONBLOCK`), inode 포인터. **오프셋이 여기 있다**는 것이 중요하다.
3. **inode**: 파일의 실체. 크기, 권한, 소유자, 타임스탬프, 데이터 블록 위치. **파일 이름은 여기 없다.** 이름은 디렉터리 항목(dentry)이 가진다.

### 1.2 이 구조가 설명하는 현상들

**한 줄 요약:** fork는 오프셋을 공유하고, 두 번 open하면 따로이며, `rm`은 이름만 지운다.

- **`fork` 후 부모와 자식이 같은 파일에 쓰면 오프셋을 공유**하므로 서로 덮어쓰지 않고 이어 쓴다. 셸에서 `(echo a; echo b) > f`가 동작하는 원리다.
- 반대로 **같은 파일을 두 번 `open`하면 오프셋이 각각**이다. 두 프로세스가 로그 파일을 따로 열고 `write`하면 서로 덮어쓴다. `O_APPEND`가 필요한 이유다(코어 4).
- `dup2(fd, 1)`으로 stdout을 파일로 바꾸는 리다이렉션은 fd 테이블의 항목 1을 바꾸는 것뿐이다.
- **열린 파일을 `rm`해도 디스크 용량이 안 줄어든다.** `rm`은 디렉터리 항목만 지운다(`unlink`). inode는 링크 수가 0이고 **열고 있는 fd도 0**일 때 해제된다. 로그를 `rm`했는데 용량이 안 돌아오면 `lsof | grep deleted`로 아직 열고 있는 프로세스를 찾는다. 그 프로세스를 재시작하거나 `> /proc/<pid>/fd/N`으로 비운다. 이 성질을 이용해 임시 파일을 만들자마자 `unlink`하면 프로세스가 죽어도 자동으로 사라진다.

**fd 누수**: 에러 경로에서 `close`를 빠뜨리면 fd가 쌓여 `EMFILE`(Too many open files)로 죽는다. `ls /proc/<pid>/fd | wc -l`을 시간에 따라 보면 잡힌다([1장](01-커널-시스템콜-스케줄러.md)의 errno 표).

> **[보충]** 컨테이너 안의 프로세스도 같은 호스트 커널의 이 세 테이블을 쓴다. 따라서 호스트에서 `lsof`로 컨테이너 프로세스가 붙들고 있는 삭제된 파일을 찾는 것이 가능하다. 컨테이너 격리 방식은 [9장](../2부-컨테이너-커널-기능과-Docker/09-네임스페이스.md)에서 다룬다.

## 코어 2. 모든 것은 파일 + VFS

### 2.1 "모든 것은 파일이다"의 실제 의미

**한 줄 요약:** 소켓·타이머·시그널·프로세스까지 fd가 되므로 이벤트 루프 하나가 전부를 기다린다.

| 것 | 어떻게 fd가 되나 | 무엇을 할 수 있나 |
|---|---|---|
| 일반 파일 | `open` | read/write/mmap/fsync |
| 디렉터리 | `open` + `getdents` | 항목 열람, `openat`의 기준점 |
| 파이프/FIFO | `pipe`, `open` | read/write, epoll |
| 소켓 | `socket`, `accept` | read/write/send/recv, epoll |
| 디바이스 (`/dev/sda`, `/dev/null`, `/dev/urandom`) | `open` | read/write/ioctl |
| 타이머 | `timerfd_create` | read(만료 횟수), epoll |
| 시그널 | `signalfd` | read(시그널 정보), epoll |
| 프로세스 | `pidfd_open` | poll(종료 대기), `pidfd_send_signal` |
| 이벤트 카운터 | `eventfd` | read/write, epoll |
| 익명 메모리 | `memfd_create` | mmap, fd 전달로 공유 메모리 |
| 커널 내부 상태 | `/proc`, `/sys` | read/write(설정 변경) |

이 통일성 덕분에 이벤트 루프 하나가 "소켓에 데이터가 왔거나, 타이머가 울렸거나, SIGTERM이 왔거나, 자식이 죽었거나"를 `epoll_wait` 한 번으로 기다릴 수 있다([6장](06-네트워크-스택.md), [3장](03-시그널.md)).

### 2.2 VFS: 파일시스템이 여러 개인데 API는 하나인 이유

**한 줄 요약:** VFS가 공통 인터페이스를 정의하고 각 파일시스템이 구현하므로, 같은 `read()`라도 성능 특성은 제각각이다.

`read()`는 ext4, xfs, btrfs, tmpfs, NFS, overlayfs(도커 이미지 레이어), procfs 어디에서나 같다. 커널의 **VFS(Virtual File System)** 계층이 공통 인터페이스(`struct file_operations`)를 정의하고 각 파일시스템이 구현한다. 프로그래머에게 중요한 결과는 다음과 같다.

- 성능 특성은 파일시스템마다 다르다. tmpfs는 RAM이고, NFS는 네트워크이며, overlayfs는 첫 쓰기 시 파일 전체를 상위 레이어로 복사한다(도커 컨테이너 안에서 큰 파일을 수정하면 느린 이유. 볼륨을 써라).
- `mount`로 트리 어디든 다른 파일시스템을 붙일 수 있다. `/proc`, `/sys`, `/dev/shm`(tmpfs)이 그렇다.
- `df`는 마운트 지점별 용량이고, `du`는 디렉터리 트리 합계다. 둘이 다르면 삭제된 열린 파일(코어 1)이나 마운트로 가려진 디렉터리다.

overlayfs의 레이어 구조는 [11장](../2부-컨테이너-커널-기능과-Docker/11-이미지-레이어-overlayfs.md), 볼륨은 [14장](../2부-컨테이너-커널-기능과-Docker/14-볼륨-바인드마운트-tmpfs.md)에서 이어진다.

## 코어 3. 버퍼링 4층과 fsync

### 3.1 `write()`는 디스크에 쓰지 않는다

**한 줄 요약:** stdio 버퍼 → 페이지 캐시 → 디스크 캐시 → 매체. `write` 성공은 두 번째 층까지만 보장한다.

```
printf("log line\n")          ← 1. stdio 버퍼 (유저 공간, 보통 4~8KB)
   │ fflush() 또는 버퍼 가득/줄바꿈(터미널일 때)
   ▼
write(fd, ...)                ← 2. 페이지 캐시 (커널 메모리). 여기서 write()는 성공 반환
   │ 커널 writeback 스레드 (수 초 후) 또는 fsync()
   ▼
디스크 컨트롤러 캐시            ← 3. 디스크 자체 캐시 (fsync는 여기까지 플러시 요청)
   │
   ▼
플래터/NAND                   ← 4. 진짜 영속
```

### 3.2 각 층의 함정

**한 줄 요약:** 1층은 로그가 사라지고, 2층은 정전에 사라지며 dirty가 차면 `write`가 블로킹된다.

**1층, stdio 버퍼**: `printf`로 쓴 로그가 크래시 직전 내용이 안 보이는 이유다. stdout이 터미널이면 줄 단위 버퍼링, **파일이나 파이프면 전체 버퍼링**이다. 컨테이너에서 `docker logs`에 파이썬 출력이 안 나오는 고전적 문제가 이것이다(`PYTHONUNBUFFERED=1`, `setvbuf`, `stderr` 사용). `_exit()`나 시그널로 죽으면 stdio 버퍼는 플러시되지 않는다.

**2층, 페이지 캐시**: `write` 성공은 "커널이 받았다"는 뜻이다. 정전이면 사라진다. 기본 최대 30초(`dirty_expire_centisecs`)까지 메모리에만 있다. 또 dirty 페이지가 `dirty_ratio`(기본 20%)를 넘으면 **`write`가 갑자기 블로킹**된다. 대량 쓰기 중 지연이 튀는 원인이다([4장](04-메모리.md)의 페이지 캐시와 연결).

**3층, fsync**: `fsync(fd)`는 그 파일의 dirty 페이지와 메타데이터를 디스크에 쓰고 디스크 캐시도 플러시하라고 요청한 뒤 **완료까지 기다린다.** 수 ms(SSD)&#126;수십 ms(HDD)가 든다. DB가 커밋마다 하는 것이 이것이며, DB 쓰기 성능의 하한을 정한다. `fdatasync`는 메타데이터(mtime 등)를 빼고 데이터만 보장하므로 조금 빠르다.

**중요한 함정: 새 파일을 만들었으면 디렉터리도 fsync해야 한다.** 파일 내용을 fsync해도 그 파일의 **이름(디렉터리 항목)**은 디렉터리 inode에 속하므로 별도다. 크래시 후 "파일은 있는데 디렉터리에 없는" 상태가 될 수 있다.

**`O_DIRECT`**: 페이지 캐시를 우회해 유저 버퍼에서 디스크로 직접 간다. 자기 캐시를 가진 DB가 이중 캐시를 피하려 쓴다. 버퍼 정렬 제약(512B/4KB)이 있고, 커널 readahead의 이득을 잃는다. 일반 애플리케이션은 쓸 이유가 없다.

## 코어 4. 원자성: 임시 파일 + fsync + rename

### 4.1 POSIX가 보장하는 원자 연산

**한 줄 요약:** `O_APPEND`, `rename`, `O_CREAT|O_EXCL`, `link`/`unlink`/`mkdir`뿐이며 이것을 조합하는 것이 신뢰성 있는 파일 코드의 전부다.

- **`O_APPEND` 쓰기**: "끝으로 이동 + 쓰기"가 원자적이다. 여러 프로세스가 같은 로그 파일에 append하면 줄이 섞이지 않는다(단일 `write` 호출이 `PIPE_BUF`(4KB) 이하일 때 실질적으로). `lseek(END)` + `write`는 원자적이지 **않다.**
- **`rename(old, new)`**: 같은 파일시스템 안에서 원자적이다. `new`가 이미 있으면 교체된다. 관찰자는 옛 파일 또는 새 파일만 보고, 중간 상태를 보지 않는다.
- **`O_CREAT | O_EXCL`**: "없으면 만들고, 있으면 실패"가 원자적이다. 락 파일에 쓴다. (NFS에서는 옛 버전에서 보장되지 않는다.)
- **`link`, `unlink`, `mkdir`**: 각각 원자적이다.

### 4.2 설정 파일 안전하게 덮어쓰기

**한 줄 요약:** 임시 파일에 쓰고 fsync한 뒤 rename하고, 디렉터리도 fsync한다.

```c
// 나쁜 예: 쓰는 도중 크래시하면 config.json이 절반만 남는다
fd = open("config.json", O_WRONLY | O_TRUNC);
write(fd, data, n);
close(fd);

// 올바른 패턴: 임시 파일에 쓰고 fsync한 뒤 rename
fd = open("config.json.tmp", O_WRONLY | O_CREAT | O_TRUNC, 0644);
write(fd, data, n);
fsync(fd);                       // 데이터가 디스크에
close(fd);
rename("config.json.tmp", "config.json");   // 원자적 교체
dfd = open(".", O_RDONLY);
fsync(dfd);                      // 디렉터리 항목 변경도 디스크에
close(dfd);
```

이 패턴이 텍스트 에디터의 "저장", 패키지 매니저, DB의 체크포인트에 쓰인다. `rename`을 안 하고 제자리에 쓰면 절반짜리 파일이 남을 수 있다. 게임 서버라면 플레이어 세이브 스냅샷이나 설정 파일 저장이 이 패턴의 대상이다.

### 4.3 파일 락

**한 줄 요약:** 락은 3종이 서로 호환되지 않고 모두 권고 락이며, 새 코드는 OFD 락 또는 `flock`을 쓴다.

여러 프로세스가 같은 파일을 조율하려면 락이 필요하다. 리눅스에는 서로 호환되지 않는 세 종류가 있다.

| 종류 | API | 특징 |
|---|---|---|
| BSD 락 | `flock(fd, LOCK_EX)` | 파일 전체. **open file 항목**에 붙음(fork 후 공유). 단순. NFS 지원은 최근 |
| POSIX 레코드 락 | `fcntl(F_SETLK)` | 바이트 범위. **프로세스**에 붙음. **같은 프로세스가 그 파일의 어떤 fd든 닫으면 락이 풀린다**(악명 높은 함정). 스레드 간 동작 안 함 |
| Open file description 락 | `fcntl(F_OFD_SETLK)` | 레코드 락의 함정을 고친 리눅스 버전. 새 코드에서 권장 |

모두 **권고(advisory) 락**이다. 락을 확인하지 않는 프로세스는 그냥 쓸 수 있다. 참여자 모두가 같은 락을 쓰기로 약속해야 한다. "이미 실행 중인지 확인"하는 PID 파일 패턴은 `flock`으로 락 파일을 잡는 것이 `O_EXCL` 파일 생성보다 낫다. 프로세스가 죽으면 커널이 자동으로 락을 놓기 때문이다.

## 코어 5. 링크·inotify·디스크 성능 감각

### 5.1 디렉터리, 링크, 경로

**한 줄 요약:** 하드 링크는 같은 inode의 다른 이름, 심볼릭 링크는 경로 문자열을 담은 별도 파일이다.

- **하드 링크**: 같은 inode를 가리키는 다른 이름. `ln a b`. 링크 수가 2가 되고, 둘 다 지워야 inode가 해제된다. 디렉터리에는 못 만들고, 파일시스템 경계를 못 넘는다.
- **심볼릭 링크**: 경로 문자열을 담은 별도 파일. 대상이 없어도 존재할 수 있다(dangling). `open`은 따라가고, `lstat`/`readlink`는 링크 자체를 본다. 보안 함정: 권한 있는 프로세스가 `/tmp/foo`를 열 때 공격자가 그 자리에 `/etc/passwd`로의 심볼릭 링크를 만들어 둘 수 있다. `O_NOFOLLOW`, `openat2`의 `RESOLVE_*` 플래그로 막는다.
- **`openat(dirfd, "relative", ...)`**: 디렉터리 fd 기준의 상대 경로. 경로 해석 중 상위 디렉터리가 바뀌는 레이스(TOCTOU)를 막고, 스레드마다 다른 "현재 디렉터리"를 흉내 낼 수 있다(프로세스의 cwd는 스레드 간 공유다).
- 경로 해석 비용: 경로 요소마다 dentry 캐시 조회. 깊은 경로의 수십만 파일을 다루는 코드는 `openat`으로 디렉터리 fd를 재사용하면 빨라진다.

### 5.2 파일 변경 감시: inotify

**한 줄 요약:** 폴링 대신 커널이 알려주지만 재귀적이지 않고 watch 수 한도가 있다.

`inotify_init` → `inotify_add_watch(fd, "/path", IN_MODIFY|IN_CREATE|...)` → fd를 `read`(또는 epoll)한다. 파일 동기화 도구, 핫 리로드, 로그 수집기가 쓴다. 한계는 다음과 같다.

- **재귀적이지 않다**(하위 디렉터리마다 watch 필요)
- watch 수 한도(`fs.inotify.max_user_watches`, VS Code가 "ENOSPC"를 내는 원인)
- NFS/FUSE 미지원. `fanotify`가 더 넓은 범위를 다룬다.

### 5.3 디스크 I/O 성능 감각

**한 줄 요약:** HDD는 순차 vs 임의가 100배 차이이고, 클라우드 디스크는 IOPS 한도가 걸려 있다.

| 매체 | 순차 처리량 | 임의 4KB 읽기 지연 | 초당 임의 IOPS |
|---|---|---|---|
| HDD | 150&#126;250 MB/s | &#126;10 ms | 100&#126;200 |
| SATA SSD | &#126;550 MB/s | &#126;100 µs | 수만 |
| NVMe SSD | 3&#126;7 GB/s | &#126;20 µs | 수십만&#126;백만 |
| 클라우드 네트워크 디스크(EBS gp3) | 125&#126;1000 MB/s | &#126;1 ms | 3000&#126;16000 (프로비저닝) |

- HDD는 **순차 vs 임의 접근**이 100배 차이다. LSM 트리, WAL(로그 선행 기록)이 존재하는 이유다. SSD에서는 차이가 줄지만 여전히 순차가 빠르다.
- 클라우드 디스크는 **IOPS 한도**가 걸려 있다. 작은 임의 쓰기(예: fsync가 잦은 DB)가 처리량이 아니라 IOPS로 막힌다. `iostat -x 1`의 `%util`, `aqu-sz`, `r_await`/`w_await`로 확인한다.
- 커널은 **readahead**로 순차 읽기를 미리 가져온다. 임의 접근이라면 `posix_fadvise(POSIX_FADV_RANDOM)`으로 끄고, 한 번만 읽을 큰 파일은 `POSIX_FADV_DONTNEED`로 캐시에서 빨리 빼라고 힌트를 줄 수 있다.

### 시나리오로 확인하기

1. **상황:** 게임 서버의 로그 파일이 수십 GB가 되어 `rm`으로 지웠다. 그런데 `df -h`의 사용량이 그대로다.
   **질문:** 원인과 해결은?

   <details markdown="1"><summary>답 확인</summary>

   `rm`은 디렉터리 항목만 지운다(`unlink`). inode는 링크 수가 0이고 열고 있는 fd도 0일 때 해제되는데, 서버 프로세스가 로그 파일을 여전히 열고 있다. `lsof +L1` 또는 `lsof | grep deleted`로 열고 있는 프로세스를 찾고, 프로세스를 재시작하거나 `> /proc/<pid>/fd/N`으로 비운다. `df`와 `du`가 서로 다른 것도 같은 이유다. → 코어 1

   </details>

2. **상황:** 서버가 설정/세이브 파일을 `O_TRUNC`로 열어 덮어쓰는 도중 크래시했고, 재시작하니 JSON 파싱이 실패한다.
   **질문:** 어떻게 고치나?

   <details markdown="1"><summary>답 확인</summary>

   제자리 덮어쓰기는 쓰는 도중 크래시하면 절반짜리 파일을 남긴다. 임시 파일에 쓰고 `fsync`한 뒤 `rename`으로 원자적 교체를 하고, 마지막으로 디렉터리 fd를 `fsync`해서 이름 변경도 디스크에 반영한다. → 코어 4

   </details>

3. **상황:** 컨테이너에서 도는 서버의 `printf` 로그가 `docker logs`에 한참 뒤에야 나오거나, 크래시 직전 내용이 비어 있다.
   **질문:** 왜 그런가?

   <details markdown="1"><summary>답 확인</summary>

   stdout이 터미널이 아니라 파일/파이프이면 stdio는 전체 버퍼링을 하므로 버퍼가 찰 때까지 `write`가 나가지 않는다. `_exit()`나 시그널로 죽으면 버퍼는 플러시되지 않는다. `setvbuf`로 버퍼링을 끄거나 `stderr`로 쓴다(파이썬이면 `PYTHONUNBUFFERED=1`). → 코어 3

   </details>

4. **상황:** 컨테이너 이미지 안에 있는 수 GB짜리 데이터 파일의 일부를 서버가 갱신하는데 첫 쓰기가 유난히 오래 걸린다.
   **질문:** 원인과 대응은?

   <details markdown="1"><summary>답 확인</summary>

   overlayfs는 첫 쓰기 시 파일 전체를 상위(쓰기) 레이어로 복사한다. 자주 쓰는 큰 파일은 컨테이너 이미지 레이어에 두지 말고 볼륨을 써야 한다. → 코어 2

   </details>

   `write` 성공은 페이지 캐시(커널 메모리)에 들어갔다는 뜻이고, 기본 최대 30초(`dirty_expire_centisecs`)까지 메모리에만 있어서 정전이면 사라진다. `fsync(fd)`로 디스크에 쓰고 디스크 캐시 플러시까지 완료를 기다린다. → 코어 3

   </details>

5. 새 파일을 만들고 파일 내용을 `fsync`했는데도 크래시 후 파일이 사라질 수 있는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   파일의 이름(디렉터리 항목)은 디렉터리 inode에 속해서 별도로 디스크에 반영해야 한다. 디렉터리 fd를 열어 `fsync`해야 한다. → 코어 3

   </details>

6. 설정 파일을 크래시에 안전하게 교체하는 순서를 쓰시오.

   <details markdown="1"><summary>답 확인</summary>

   `config.json.tmp`에 쓰기 → `fsync(fd)` → `close` → `rename(tmp, config.json)`(원자적 교체) → 디렉터리 fd를 `fsync`. 제자리 `O_TRUNC` 덮어쓰기는 절반짜리 파일을 남길 수 있다. → 코어 4

   </details>

7. `flock`, `fcntl(F_SETLK)`, OFD 락의 차이와 공통점은?

   <details markdown="1"><summary>답 확인</summary>

   `flock`은 파일 전체 락이고 open file 항목에 붙는다. `F_SETLK`는 바이트 범위 락이고 프로세스에 붙어서, 같은 프로세스가 그 파일의 어떤 fd든 닫으면 풀리는 함정이 있다. OFD 락은 그 함정을 고친 리눅스 버전으로 새 코드에서 권장된다. 모두 권고 락이라 참여자가 약속해야 한다. → 코어 4

   </details>

8. 컨테이너에서 큰 파일을 수정하면 느린 이유는?

   <details markdown="1"><summary>답 확인</summary>

   overlayfs는 첫 쓰기 시 파일 전체를 상위 레이어로 복사한다. 자주 쓰는 큰 파일은 볼륨에 둔다. → 코어 2

   </details>

### 3. 기억 고리

- **C++ 유추:** 소켓의 `send()` 성공 = 파일의 `write()` 성공 ⚠️ 둘 다 "커널 버퍼에 넣었다"일 뿐인데, 소켓은 TCP가 재전송해 주지만 페이지 캐시는 정전 시 그냥 사라지므로 `fsync`를 직접 요청해야 한다.
- **C++ 유추:** `shared_ptr`의 참조 수 = 링크 수 + 열린 fd 수 ⚠️ 참조가 두 종류이고 `rm`은 그중 이름 쪽만 줄이므로, fd가 남은 동안은 "삭제됐지만 용량은 차지"하는 상태가 생긴다.
- **비유:** inode = 집(실체), dentry = 문패(이름), fd = 열쇠, open file = 열쇠에 붙은 "지금 읽던 쪽" 책갈피. 문패를 떼도(`rm`) 열쇠를 가진 사람이 있으면 집은 철거되지 않는다. ⚠️ 비유가 깨지는 지점: 책갈피(오프셋)는 열쇠 복사(`fork`/`dup`)끼리는 공유하지만, 같은 집에 새 열쇠를 따로 받으면(`open` 두 번) 새 책갈피가 생긴다.
- **비유:** `fsync` = 택배를 "접수"가 아니라 "수령 서명 완료"까지 기다리는 것. `write`는 접수 창구에 맡긴 상태다. ⚠️ 비유가 깨지는 지점: 접수된 택배는 분실 시 추적되지만, 페이지 캐시의 dirty 데이터는 정전되면 흔적 없이 사라진다.
- **묶음(3의 법칙):** fd 3계층(fd 테이블·open file·inode) / 해제 조건 3요소(링크 수 0·열린 fd 0·그때 해제) / 락 3종(BSD·POSIX 레코드·OFD).
- **대칭·순서:** 쓰기 쪽 4층(stdio → 페이지 캐시 → 디스크 캐시 → 매체) ↔ 안전한 덮어쓰기 5단계(쓰기 → fsync → close → rename → 디렉터리 fsync).
