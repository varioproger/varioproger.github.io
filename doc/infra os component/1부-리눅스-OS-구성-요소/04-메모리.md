# 4장. 메모리

> **🎮 게임 서버 개발자에게** — 메모리 풀과 오브젝트 풀로 할당을 직접 통제해 온 개발자라면 `new`/`malloc`이 "그냥 메모리를 준다"는 인상이 강할 것이다. 리눅스에서는 그 한 줄 밑에 가상 메모리, 지연 할당, 페이지 캐시, OOM killer가 깔려 있고, 컨테이너에서는 거기에 cgroup 메모리 제한이 더해진다. 장기 실행 게임 서버의 "누수는 없는데 RSS가 서서히 늘어나는" 현상과, 아무 경고 없이 서버가 사라지는 **OOM 종료(137)**가 이 장에서 설명된다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 컨테이너가 로그 한 줄 없이 재시작되고 `Exit Code: 137`이다.
> - `free`를 봤더니 free 메모리가 1GB 남짓이라 불안한데, 서버는 멀쩡하다.
> - 서버를 며칠 돌리면 RSS가 계속 늘어서 누수인지 단편화인지 모르겠다.

## 코어 — 이것만은 100%

> **한 문장:** 프로세스가 보는 주소는 가상이라 `malloc`은 예약일 뿐 쓰는 순간 물리 페이지가 배정되고, 물리 메모리가 바닥나면 OOM killer가 경고 없이 SIGKILL하며, 컨테이너는 cgroup 한도(`memory.max`)에서 같은 일이 그 컨테이너 안에서 일어난다.

1. **가상 메모리와 "할당 ≠ 사용"** — 페이지 단위(4KB) 매핑, 지연 할당, 페이지 폴트. RSS·PSS·USS·VSZ는 서로 다른 숫자다.
2. **malloc은 시스템 콜이 아니다** — `brk`/`mmap` 위의 할당자(ptmalloc2)는 `free`해도 RSS를 안 줄이고, 멀티스레드에서는 아레나가 RSS를 부풀린다.
3. **오버커밋과 OOM killer** — `ENOMEM`은 거의 안 나오고 대신 OOM kill이 온다. 컨테이너에서는 `OOMKilled`/137이다.
4. **페이지 캐시·mmap·스왑** — free가 적어도 `available`이 크면 정상이다. `write` 성공은 디스크 기록이 아니다. cgroup `memory.current`에는 페이지 캐시가 포함된다.
5. **측정과 누수 판별** — `/proc/<pid>/status`의 VmRSS 추세로 진짜 누수·논리적 누수·단편화를 구분한다.

## 코어 1. 가상 메모리와 "할당 ≠ 사용"

### 1.1 가상 메모리: 모든 것의 시작

**한 줄 요약:** 프로세스가 보는 주소는 MMU와 페이지 테이블이 물리 주소로 바꿔 주는 가상 주소다.

프로세스가 보는 주소(예: `0x7f3a1c200000`)는 **실제 물리 메모리 주소가 아니다.** CPU의 MMU가 **페이지 테이블**로 가상 주소를 물리 주소로 변환한다. 단위는 **페이지**, 기본 4KB다.

```
가상 주소 공간 (프로세스별 독립, x86-64: 128TB)    물리 메모리 (전체 시스템 공유)
┌──────────────┐                               ┌──────────────┐
│ 페이지 0x1000  │ ──────────────────────────────▶│ 물리 프레임 A   │
│ 페이지 0x2000  │ ──────────────────────────────▶│ 물리 프레임 B   │
│ 페이지 0x3000  │ ─(매핑 없음: 접근 시 페이지 폴트)   │  ...          │
│ 페이지 0x4000  │ ──(디스크/스왑에 있음)             │               │
└──────────────┘                               └──────────────┘
```

이렇게 하는 이유는 네 가지다.

1. **격리**: 다른 프로세스의 메모리는 페이지 테이블에 없으니 접근 자체가 불가능하다.
2. **지연 할당**: 실제로 접근할 때까지 물리 메모리를 배정하지 않는다(demand paging). 물리 메모리보다 큰 주소 공간을 쓸 수 있다.
3. **공유**: 같은 물리 페이지를 여러 프로세스가 매핑할 수 있다. libc 코드는 시스템에 한 번만 있다. COW도 이 원리다.
4. **파일 매핑**: 파일을 메모리처럼 접근한다(`mmap`).

**페이지 폴트**: 매핑이 없는 가상 주소에 접근하면 CPU가 예외를 던지고 커널이 처리한다.

- **Minor fault**: 물리 페이지를 새로 배정(첫 접근)하거나 이미 페이지 캐시에 있는 것을 매핑만 하면 됨. 수 µs.
- **Major fault**: 디스크에서 읽어 와야 함(스왑인, 파일 첫 읽기). 수 ms. **100배 이상 느리다.**
- **잘못된 접근**: 매핑도 없고 정당한 이유도 없음 → `SIGSEGV`. 이것이 "Segmentation fault"다.

`ps -o min_flt,maj_flt <pid>`나 `/proc/<pid>/stat`로 본다. major fault가 계속 늘면 메모리가 부족해 스왑을 치고 있다는 뜻이다.

### 1.2 "할당했다"와 "실제로 쓴다"는 다르다

**한 줄 요약:** `malloc`은 주소 공간 예약이고 물리 페이지는 처음 쓰는 순간 한 페이지씩 배정되므로, 메모리 숫자는 RSS/PSS/USS/VSZ 중 무엇인지부터 본다.

```c
char *p = malloc(1 << 30);        // 1GB. 성공. 그런데 RSS는 거의 안 늘어남
memset(p, 0, 1 << 30);            // 이제야 물리 페이지 262,144개가 실제로 배정됨
```

`malloc`은 큰 요청을 `mmap(MAP_ANONYMOUS)`로 처리하고, 이는 **가상 주소 공간에 예약만** 한다. 그래서 "메모리 사용량"에는 최소 4가지 다른 의미가 섞인다.

- **VSZ(가상 크기)**: 예약한 주소 공간. 의미 없는 숫자인 경우가 많다(JVM, Go 런타임은 수 GB를 예약한다).
- **RSS(Resident Set Size)**: 현재 물리 메모리에 있는 페이지. 실제 사용량에 가깝지만 **공유 라이브러리 페이지도 포함**되어 프로세스별로 더하면 실제 총량보다 크다.
- **PSS(Proportional Set Size)**: 공유 페이지를 공유하는 프로세스 수로 나눠 배분한 것. 여러 프로세스의 합이 실제 총량과 일치한다(`/proc/<pid>/smaps_rollup`).
- **USS(Unique Set Size)**: 이 프로세스만 쓰는 페이지. "이 프로세스를 죽이면 돌아오는 메모리".

| 상황 | 볼 숫자 |
|---|---|
| 이 프로세스가 얼마나 먹나 (대략) | RSS (`top`의 RES) |
| 여러 워커 프로세스의 합계 | PSS 합 |
| 컨테이너 메모리 제한에 걸리나 | cgroup `memory.current` (RSS + 페이지 캐시 + 커널 메모리) |
| 메모리 누수인가 | RSS 또는 USS의 **시간에 따른 추세** |

## 코어 2. malloc은 시스템 콜이 아니다

### 2.1 할당자의 내부: brk와 mmap

**한 줄 요약:** `malloc`/`free`는 glibc ptmalloc2가 `brk`/`mmap` 위에서 굴리므로 `free`해도 RSS가 안 줄 수 있다.

- `brk`/`sbrk`: 힙의 끝(program break)을 늘린다. 128KB 미만 작은 할당의 기본 공급원.
- `mmap`: 128KB 이상(`M_MMAP_THRESHOLD`, 동적 조정됨) 큰 할당은 별도 매핑. `free`하면 `munmap`으로 즉시 반환.

할당자는 작은 조각들을 자기가 관리하는 큰 블록(아레나) 안에서 잘라 준다. 그래서 **`free()`해도 RSS가 안 줄어든다.** 재사용을 위해 들고 있기 때문이다. 힙 꼭대기가 비어야만 `brk`로 반환하는데 중간에 살아 있는 조각 하나가 있으면 그 아래 전부가 갇힌다. 이것이 **단편화**다. 장기 실행 서버가 "누수는 없는데 RSS가 서서히 늘어나는" 흔한 원인이다.

### 2.2 멀티스레드와 아레나

**한 줄 요약:** 스레드마다 아레나가 생겨 조각이 흩어지므로 `MALLOC_ARENA_MAX`나 jemalloc 같은 대안을 검토한다.

락 경합을 피하려고 ptmalloc은 스레드마다 별도 아레나를 만든다(최대 코어 수 × 8). 스레드가 많은 서버에서 아레나마다 조각이 남아 RSS가 부풀어 오르는 것이 잘 알려진 문제다. 대응:

- `MALLOC_ARENA_MAX=2` 환경변수 (Java 컨테이너에서 흔한 설정)
- `jemalloc`, `tcmalloc`, `mimalloc`으로 교체 (`LD_PRELOAD=libjemalloc.so`). 단편화가 덜하고 메모리 반환이 적극적이다. Redis, Rust 프로젝트 다수가 jemalloc을 쓴다.
- `malloc_trim(0)`으로 강제 반환 시도

**`calloc`의 비밀**: `calloc`은 `malloc` + `memset(0)`이 아니다. 새 `mmap` 페이지는 커널이 이미 0으로 주므로 memset을 건너뛴다. 큰 배열을 0으로 초기화할 때 `calloc`이 훨씬 빠르다.

## 코어 3. 오버커밋과 OOM killer

### 3.1 오버커밋: ENOMEM이 안 나오는 이유

**한 줄 요약:** 리눅스는 기본적으로 오버커밋하므로 `malloc(100GB)`가 성공하고, 문제는 실제로 쓰기 시작할 때 터진다.

`vm.overcommit_memory`:

- `0` (기본, heuristic): 명백히 터무니없는 요청만 거절
- `1`: 항상 성공
- `2`: 엄격. 스왑 + RAM × `overcommit_ratio`까지만 허용. `ENOMEM`이 실제로 나온다.

### 3.2 OOM killer

**한 줄 요약:** 물리 메모리가 바닥나면 커널이 `oom_score`가 가장 높은 프로세스를 경고 없이 SIGKILL하고, 흔적은 `dmesg`에만 남는다.

물리 메모리가 진짜로 바닥나면 **OOM killer**가 발동해 `oom_score`가 가장 높은(대략 RSS가 가장 큰) 프로세스를 `SIGKILL`로 죽인다. **프로그램에는 아무 경고도 없다.** `dmesg | grep -i 'killed process'`에만 흔적이 남는다.

- `/proc/<pid>/oom_score_adj`(-1000 &#126; 1000)로 우선순위를 조정한다. -1000은 절대 안 죽임.
- `mlock`/`MAP_POPULATE`로 페이지를 미리 배정해 둘 수 있다. DB나 지연에 민감한 서버가 쓴다.

### 3.3 컨테이너에서의 OOM: cgroup 메모리 한도

**한 줄 요약:** `--memory`를 넘으면 그 cgroup 안에서 OOM kill이 일어나 `OOMKilled: true`, 종료 코드 137이 된다.

컨테이너가 `--memory` 한도를 넘으면 커널은 해당 cgroup 안에서 자체적으로 **cgroup-aware OOM killer**를 동작시킨다. 시스템 전체 메모리 부족 때의 전역 OOM killer와는 별개이며, cgroup 사용량이 `memory.max`(v1의 `memory.limit_in_bytes`)를 넘으면 그 안의 프로세스 중 하나(보통 메모리 사용량이 가장 크거나 `oom_score_adj`가 높은 것)를 `SIGKILL`한다.

- 도커는 `State.OOMKilled: true`, 쿠버네티스는 exit code 137로 보고한다. **137의 의미는 128 + SIGKILL 9**다 ([3장](03-시그널.md)).
- 애플리케이션 로그에는 대개 아무 흔적이 없고 프로세스가 갑자기 사라진 것처럼 보인다. 컨테이너가 "이유 없이" 재시작 정책에 의해 계속 재기동된다면 먼저 이 필드를 확인한다.

```bash
docker inspect --format '{{.State.OOMKilled}}' <container-id-or-name>
```

- `--oom-kill-disable`: 해당 cgroup의 OOM killer 발동 자체를 끈다. 단독으로 쓰면 한도를 넘은 프로세스가 죽는 대신 메모리 회수를 기다리며 hang할 수 있어, 반드시 `--memory` 상한과 함께 써야 하며 상한 없이 켜면 호스트 전체 메모리 고갈로 이어질 수 있다.
- `--oom-score-adj`: 전역 OOM killer가 누구를 먼저 죽일지 참고하는 가중치를 조정한다.

> **[보충]** `--memory`가 cgroup `memory.max`로 연결되는 구조는 [10장](../2부-컨테이너-커널-기능과-Docker/10-cgroup.md)에서, 쿠버네티스 `resources.limits.memory`와 QoS·축출·OOM은 [25장](../3부-쿠버네티스-구성-요소/25-Pod-생명주기와-리소스.md)에서 이어진다.

## 코어 4. 페이지 캐시·mmap·스왑

### 4.1 페이지 캐시: "free 메모리가 없다"는 착각

**한 줄 요약:** 남는 RAM은 파일 캐시로 쓰이고 필요하면 즉시 반환되므로 `free`가 아니라 `available`을 본다.

```
$ free -h
               total   used   free   shared  buff/cache  available
Mem:            31Gi   8.0Gi  1.2Gi   0.5Gi    22Gi       22Gi
```

free가 1.2GB뿐이어도 문제없다. 22GB는 **페이지 캐시**다. 커널은 디스크에서 읽은 내용과 쓸 내용을 남는 RAM에 최대한 캐시하고, 프로세스가 메모리를 필요로 하면 캐시를 버리고 내준다. **봐야 할 숫자는 `available`**이다.

- 파일을 `read()`하면 디스크 → 페이지 캐시 → 유저 버퍼로 복사된다. 두 번째 읽기는 캐시에서 나와 100배 빠르다.
- `write()`는 페이지 캐시에 쓰고 **즉시 반환**한다. 디스크에는 나중에(수 초 내, `dirty_expire_centisecs`) 커널 스레드가 쓴다. 그래서 `write` 성공 ≠ 디스크 기록이고, 정전이면 사라진다. `fsync`가 필요한 이유다 ([5장](05-파일시스템과-IO.md)).
- 컨테이너 cgroup의 `memory.current`에는 **그 컨테이너가 만든 페이지 캐시도 포함**된다. 큰 파일을 읽기만 해도 한도에 가까워 보이지만, 압박이 오면 회수되므로 대부분 OOM까지는 안 간다. 로그를 많이 쓰는 컨테이너에서 "메모리 사용량"이 높게 보이는 원인이다.

`echo 3 > /proc/sys/vm/drop_caches`로 캐시를 비울 수 있지만 벤치마크용이다. 운영에서 할 이유가 없다.

### 4.2 mmap: 파일을 메모리처럼

**한 줄 요약:** 페이지 캐시의 물리 페이지를 내 주소 공간에 그대로 매핑해서 복사 없이(zero-copy) 접근한다.

```c
int fd = open("data.bin", O_RDONLY);
char *p = mmap(NULL, size, PROT_READ, MAP_PRIVATE, fd, 0);
// 이제 p[i]로 파일 내용에 접근. read() 호출 없음
```

- `read`처럼 커널 버퍼 → 유저 버퍼 복사가 없다. 접근할 때마다 필요한 페이지만 폴트로 들어오므로 100GB 파일을 매핑해도 접근한 부분만 메모리를 쓴다.
- `MAP_SHARED`로 매핑하고 쓰면 파일에 반영되고 같은 파일을 매핑한 다른 프로세스에도 보여 공유 메모리 IPC가 된다. `msync`로 디스크 반영을 강제한다.
- 단점: 무작위 접근이 많으면 페이지 폴트 비용이 `read`보다 클 수 있고, 매핑된 파일이 I/O 에러를 내면 `SIGBUS`가 온다. 매핑 생성·삭제 자체가 비싸다(TLB 플러시).

실행 파일과 공유 라이브러리를 적재하는 방법도 mmap이다.

### 4.3 스왑

**한 줄 요약:** 조금 쓰이는 스왑은 정상이고, 계속 in/out 되는 thrashing이 문제다.

물리 메모리가 부족하면 커널은 익명 페이지(힙, 스택)를 스왑 공간에 내보낸다. 파일 페이지는 그냥 버린다(디스크에 원본이 있으므로). 나중에 접근하면 major fault로 다시 읽어 온다.

- **스왑 in/out이 계속 일어나는 것**(`vmstat`의 `si`/`so`)이 문제이고, 이 상태가 **thrashing**이다. 시스템이 "멈춘 듯" 느려진다.
- `vm.swappiness`(0&#126;200, 기본 60)로 조절한다. DB 서버는 낮게(1&#126;10) 두는 것이 관례다.
- 쿠버네티스는 전통적으로 스왑을 끈다. 스왑이 있으면 메모리 제한과 스케줄링 예측이 어려워지기 때문이다.
- 지연에 민감한 코드는 `mlock`으로 스왑을 막을 수 있다(`RLIMIT_MEMLOCK` 한도 내).

## 코어 5. 측정과 누수 판별

### 5.1 캐시, TLB, Huge Page, NUMA

**한 줄 요약:** 접근 패턴이 big-O보다 중요한 경우가 많고, 큰 힙의 무작위 접근은 TLB가 병목이다.

CPU 캐시(L1 &#126;1ns, L2 &#126;4ns, L3 &#126;15ns, 메모리 &#126;80ns)는 자릿수 차이다.

```c
// 캐시 친화적: 행 우선 순회 (연속 메모리)
for (i = 0; i < N; i++) for (j = 0; j < N; j++) sum += m[i][j];

// 캐시 비친화적: 열 우선 순회 (매번 다른 캐시 라인) - 같은 연산, 5~10배 느림
for (j = 0; j < N; j++) for (i = 0; i < N; i++) sum += m[i][j];
```

**TLB**는 가상→물리 변환 결과를 캐시한다. 4KB 페이지에서 엔트리 수천 개면 커버 범위가 수 MB밖에 안 되어, 수 GB 힙을 무작위 접근하는 프로그램(DB, 인메모리 캐시)은 TLB 미스가 병목이 된다. **Huge Page(2MB)**는 엔트리 하나가 512배 넓은 범위를 커버한다. **THP**는 커널이 자동으로 합치지만 `khugepaged`의 압축 작업이 지연 스파이크를 만들어 Redis, MongoDB, PostgreSQL은 `madvise` 또는 `never`를 권한다. 명시적으로는 `mmap(MAP_HUGETLB)`을 쓴다.

**NUMA**: 소켓이 2개 이상인 서버에서는 메모리가 소켓별로 나뉘고 다른 소켓의 메모리 접근은 1.5&#126;2배 느리다. `numactl --cpunodebind=0 --membind=0`으로 고정할 수 있다. 클라우드 VM 대부분은 단일 노드라 걱정할 일이 적다.

### 5.2 메모리 누수 찾기

**한 줄 요약:** 누수는 진짜 누수, 논리적 누수, 단편화 세 가지이고, 첫 조치는 VmRSS 추세 기록이다.

1. **진짜 누수**: 참조를 잃어 `free`할 수 없는 메모리. Valgrind(`memcheck`), AddressSanitizer(`-fsanitize=address`, LeakSanitizer 포함), heaptrack으로 잡는다.
2. **논리적 누수**: 참조는 살아 있지만 다시는 안 쓰는 것. 만료 없는 캐시, 계속 자라는 리스트, 닫지 않은 리스너. 힙 덤프 분석이 필요하다.
3. **할당자 단편화**: 누수가 아닌데 RSS가 는다. 코어 2에서 본 현상이며 `malloc_info`나 jemalloc 통계로 구분한다.

`/proc/<pid>/status`의 VmRSS를 시간에 따라 기록하고, 일정하게 증가하는지 계단식으로 증가 후 안정되는지(단편화나 캐시 워밍업) 본다.

```bash
cat /proc/<pid>/status | grep -E 'Vm(Size|RSS|Swap)|RssAnon|RssFile'
cat /proc/<pid>/smaps_rollup                 # PSS, USS, 공유/사적 페이지
pmap -x <pid> | sort -k3 -n | tail           # 가장 큰 매핑
free -h; cat /proc/meminfo
vmstat 1                                     # si/so (스왑), free, cache
ps -o pid,min_flt,maj_flt,rss,vsz,cmd -p <pid>
dmesg -T | grep -i -E 'oom|killed process'   # OOM 이력
cat /sys/fs/cgroup/memory.current /sys/fs/cgroup/memory.max   # 컨테이너 메모리 (cgroup v2)
```

### 시나리오로 확인하기

1. **상황:** 컨테이너 게임 서버가 로그 한 줄 없이 사라지고 재시작 정책으로 계속 다시 뜬다. 쿠버네티스 상태는 `Exit Code: 137`이다.
   **질문:** 무엇을 확인하고 왜 그런가?

   <details markdown="1"><summary>답 확인</summary>

   137 = 128 + SIGKILL(9). 메모리 한도(`memory.max`)를 넘어 cgroup 안의 OOM killer가 SIGKILL한 것이 첫 의심이다. 앱에는 경고가 없고 로그에도 흔적이 없다. 도커는 `docker inspect`의 `State.OOMKilled`, 호스트는 `dmesg -T | grep -i 'killed process'`로 확인하고, 한도와 실제 사용(`memory.current`, 페이지 캐시 포함)을 비교한다. → 코어 3

   </details>

2. **상황:** `free -h`에서 free가 1.2GB뿐이어서 운영팀이 메모리 증설을 요청했다. `buff/cache`는 22Gi, `available`은 22Gi다.
   **질문:** 증설이 필요한가?

   <details markdown="1"><summary>답 확인</summary>

   필요 없다. 22GB는 페이지 캐시이고 프로세스가 메모리를 필요로 하면 캐시를 버리고 내준다. 봐야 할 숫자는 `available`이다. → 코어 4

   </details>

3. **상황:** 서버를 일주일 돌리면 RSS가 계속 늘지만 Valgrind/ASan에서는 누수가 없다. 워커 스레드가 많다.
   **질문:** 의심할 것과 대응은?

   <details markdown="1"><summary>답 확인</summary>

   할당자 단편화와 스레드별 아레나다. `free`해도 할당자가 들고 있고 힙 중간의 살아 있는 조각이 아래를 가둔다. `MALLOC_ARENA_MAX=2`, jemalloc/tcmalloc/mimalloc 교체(`LD_PRELOAD`), `malloc_trim(0)`을 검토하고, VmRSS 추세가 계단식 후 안정되는지 선형 증가인지 본다. 선형 증가면 논리적 누수(만료 없는 캐시 등)도 의심한다. → 코어 2, 코어 5

   </details>

4. **상황:** 로그 파일을 많이 쓰는 컨테이너의 메모리 사용량이 한도에 가깝게 보이지만 OOM은 나지 않는다.
   **질문:** 왜 그런가?

   <details markdown="1"><summary>답 확인</summary>

   cgroup `memory.current`에는 그 컨테이너가 만든 페이지 캐시도 포함된다. 압박이 오면 캐시가 회수되므로 대부분 OOM까지 가지 않는다. 진짜 위험 여부는 RSS(익명 메모리) 추세로 판단한다. → 코어 4

   </details>

### 2. 인출 질문

1. `malloc(1GB)`이 성공했는데 RSS가 안 늘어난 이유는?

   <details markdown="1"><summary>답 확인</summary>

   큰 요청은 `mmap(MAP_ANONYMOUS)`로 가상 주소 공간에 예약만 하고, 물리 페이지는 처음 쓰기가 일어나는 페이지마다 페이지 폴트로 하나씩 배정되기 때문이다. `memset`하면 그때 262,144페이지가 실제로 배정된다. → 코어 1

   </details>

2. RSS, PSS, USS, VSZ의 차이와 각각 언제 보는가?

   <details markdown="1"><summary>답 확인</summary>

   VSZ는 예약한 주소 공간(대체로 무의미), RSS는 현재 물리 메모리의 페이지(공유 라이브러리 포함이라 프로세스 합이 총량보다 큼), PSS는 공유 페이지를 공유자 수로 나눈 값(워커 프로세스 합계에 적합), USS는 이 프로세스 전용 페이지다. 컨테이너 한도는 cgroup `memory.current`로 본다. → 코어 1

   </details>

3. `free()`해도 RSS가 안 줄어드는 이유와 대응은?

   <details markdown="1"><summary>답 확인</summary>

   할당자가 재사용을 위해 들고 있고, 힙 꼭대기가 비어야만 `brk`로 반환되는데 중간의 살아 있는 조각 하나가 아래를 가두는 단편화 때문이다. 멀티스레드에서는 아레나별로 조각이 남는다. `MALLOC_ARENA_MAX=2`, jemalloc 등으로 교체, `malloc_trim(0)`을 쓴다. → 코어 2

   </details>

4. `malloc(100GB)`가 16GB 머신에서 성공할 수 있는 이유와 `ENOMEM`이 실제로 나오게 하려면?

   <details markdown="1"><summary>답 확인</summary>

   기본 `vm.overcommit_memory=0`(heuristic)은 터무니없는 요청만 거절하는 오버커밋이어서, 실제로 쓰기 시작해야 문제가 된다. `2`(엄격)로 두면 스왑 + RAM × `overcommit_ratio`까지만 허용해 `ENOMEM`이 실제로 나온다. → 코어 3

   </details>

5. 컨테이너가 메모리 한도를 넘으면 무슨 일이 일어나고 어떻게 확인하는가?

   <details markdown="1"><summary>답 확인</summary>

   그 cgroup 안에서 cgroup-aware OOM killer가 프로세스를 SIGKILL한다. 도커는 `State.OOMKilled: true`, 쿠버네티스는 exit code 137로 보고한다. 앱 로그에는 흔적이 없고, `dmesg`에 OOM 이력이 남는다. → 코어 3

   </details>

6. `write()`가 성공했다고 디스크에 기록된 것인가?

   <details markdown="1"><summary>답 확인</summary>

   아니다. `write`는 페이지 캐시에 쓰고 즉시 반환하며 디스크에는 나중에(수 초 내) 커널 스레드가 쓴다. 정전이면 사라지므로 `fsync`가 필요하다. → 코어 4

   </details>

7. thrashing이란 무엇이며 어떻게 감지하는가?

   <details markdown="1"><summary>답 확인</summary>

   스왑 in/out이 계속 일어나 시스템이 멈춘 듯 느려지는 상태다. `vmstat`의 `si`/`so`가 지속되고 major fault가 계속 늘면 의심한다. 조금 쓰이는 스왑 자체는 정상이다. → 코어 4

   </details>

8. 메모리 누수의 세 종류와 첫 조치는?

   <details markdown="1"><summary>답 확인</summary>

   진짜 누수(참조를 잃은 메모리, Valgrind/ASan), 논리적 누수(참조는 있으나 안 쓰는 것, 힙 덤프), 할당자 단편화(누수 아님). 첫 조치는 `/proc/<pid>/status`의 VmRSS를 시간에 따라 기록해 일정 증가인지 계단식 후 안정인지 보는 것이다. → 코어 5

   </details>

### 3. 기억 고리

- **C++ 유추:** `new`가 성공 = 포인터를 받음 ⚠️ 물리 메모리는 쓰는 순간에야 배정되고, 부족하면 `bad_alloc`이 아니라 SIGKILL이 온다.
- **C++ 유추:** 메모리 풀로 단편화 방지 ⚠️ 풀 밖의 할당(로그 문자열, STL 컨테이너)은 여전히 ptmalloc 아레나에 흩어져 RSS를 부풀린다.
- **비유:** 가상 메모리 = 호텔 객실 예약. 예약(malloc)만 했을 때는 방을 안 쓴 것이고, 체크인(첫 쓰기)해야 실제 방이 배정된다. 호텔이 방보다 많이 예약을 받는 것이 오버커밋이다. ⚠️ 현실의 호텔은 만실이면 예약을 거절하지만 리눅스는 받아 놓고 나중에 투숙객 중 한 명을 내쫓는다(OOM kill).
- **비유:** 페이지 캐시 = 책상 위에 펼쳐 둔 자주 보는 서류. 책상이 가득 차 보여도 새 일감이 오면 치우고 자리를 낸다. ⚠️ 치우기 전의 "아직 안 저장한 서류"(dirty page)는 정전 시 사라질 수 있다.
- **묶음(3의 법칙):** 메모리 측정 3(RSS·PSS·cgroup `memory.current`) / 누수 3종 / 이 장의 도입 상황 3개(137·free 착시·RSS 증가).
- **대칭·순서:** minor fault(µs) ↔ major fault(ms), `ENOMEM`(엄격 모드) ↔ OOM kill(기본 모드). 순서: 캐시 회수 → 스왑 → OOM kill.
