# 2장. 프로세스

> **🎮 게임 서버 개발자에게** — 단일 프로세스 안에서 스레드 풀과 epoll로 접속자를 처리해 온 개발자에게 `fork`/`exec`/`wait`는 낯설 수 있다. 하지만 컨테이너는 "프로세스 하나를 격리해서 띄운 것"이므로, 컨테이너 안에서 서버가 **PID 1**이 되는 순간 이 장의 지식이 곧바로 필요해진다. 좀비 누적, `docker stop`이 먹지 않는 현상, `Too many open files`는 모두 프로세스의 성질에서 나온다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 서버가 외부 프로그램(운영 스크립트, 로그 수집기)을 띄우는데 시간이 지나면 `<defunct>` 프로세스가 쌓인다.
> - 컨테이너에서 `docker stop`을 하면 서버가 10초 동안 멈추지 않다가 강제 종료된다.
> - SSH 접속을 끊었더니 백그라운드로 띄운 서버가 같이 죽는다.

## 코어 — 이것만은 100%

> **한 문장:** 프로세스는 주소 공간·fd 테이블·자격 증명·한도를 묶은 "그릇"이고 실제 실행은 스레드가 하며, 자식은 fork+exec로 만들어져 부모가 wait로 회수해야 하고, 컨테이너의 PID 1은 그 회수와 시그널 처리의 책임을 진다.

1. **프로세스 = 그릇** — 가상 주소 공간, fd 테이블, 최소 1개 스레드, 자격 증명, 환경, `task_struct`의 묶음이다. 레이아웃은 `.text/.data/.bss`, 힙, mmap 영역, 스택이다.
2. **fork + exec + wait** — fork는 복제(COW), exec는 프로그램 교체(PID·fd 유지), wait는 종료 코드 회수다. 회수하지 않은 자식은 좀비(Z)로 남는다.
3. **컨테이너의 PID 1 문제** — 내 서버가 PID 1이면 고아가 모두 입양되어 좀비가 쌓이고, 핸들러 없는 시그널은 커널이 무시한다. 해법은 `tini`/`--init`이거나 직접 처리다.
4. **자격 증명과 자원 한도** — 권한 검사는 유효 UID로 하고, `RLIMIT_NOFILE` 기본 1024는 서버가 반드시 올린다.
5. **IPC와 세션** — 격리된 프로세스끼리는 파이프·Unix 소켓·공유 메모리로 통신하고, 세션과 프로세스 그룹이 터미널 종료 시 서버까지 죽이는 경로를 만든다.

## 코어 1. 프로세스 = 그릇

### 1.1 프로세스란 무엇인가

**한 줄 요약:** 프로세스는 "실행 중인 프로그램 하나에 대한 커널의 관리 단위"이고 실제 실행은 스레드가 한다.

프로세스는 다음의 묶음이다.

- **가상 주소 공간**: 이 프로세스만 보는 독립된 메모리 뷰 ([4장](04-메모리.md))
- **파일 디스크립터 테이블**: 열린 파일, 소켓, 파이프 등에 대한 참조 ([5장](05-파일시스템과-IO.md))
- **최소 1개의 스레드(태스크)**: 코드를 실제로 실행하는 주체 ([7장](07-스레드와-동시성.md))
- **자격 증명**: 실제/유효 UID·GID, capabilities
- **환경**: 인자, 환경변수, 현재 디렉터리, umask, 시그널 처리 방식, 자원 한도(`ulimit`)
- **`task_struct`**: 커널이 이것들을 관리하려고 들고 있는 구조체

핵심: **프로세스는 "그릇"이고 실제 실행은 스레드가 한다.**

### 1.2 프로세스의 메모리 레이아웃

**한 줄 요약:** 코드·데이터는 낮은 주소, 스택은 높은 주소에서 아래로, 힙은 위로 자라고 그 사이가 mmap 영역이다.

```
높은 주소  ┌──────────────────────┐ 0x7fff...
          │ 스택 (main 스레드)      │ ↓ 아래로 자람. 지역 변수, 리턴 주소
          │  ...                 │
          │ 메모리 매핑 영역        │ 공유 라이브러리(libc.so), mmap()한 파일/익명 메모리,
          │  (mmap)              │ 다른 스레드들의 스택
          │  ...                 │
          │ 힙 (brk)              │ ↑ 위로 자람. malloc이 관리
          ├──────────────────────┤
          │ .bss  (초기화 안 된 전역) │ 0으로 채워짐, 실행 파일에는 크기만 기록
          │ .data (초기화된 전역)    │
          │ .text (코드)           │ 읽기 전용, 실행 가능. 같은 프로그램 여러 개가 물리 페이지 공유
낮은 주소  └──────────────────────┘ 0x400000 (또는 PIE면 랜덤)
```

직접 확인: `cat /proc/self/maps` 또는 `pmap -x <pid>`. 각 줄이 하나의 매핑이고 권한(`r-xp`, `rw-p`)이 표시된다. `p`는 private(COW), `s`는 shared다.

## 코어 2. fork + exec + wait

### 2.1 프로세스 생성: fork와 exec

**한 줄 요약:** 리눅스는 "새 프로그램 실행"을 복제(fork)와 교체(exec) 두 단계로 나눈다.

```c
pid_t pid = fork();              // 1. 현재 프로세스를 복제
if (pid == -1) { perror("fork"); }
else if (pid == 0) {             // 자식
    execve("/bin/ls", argv, envp);   // 2. 자신을 다른 프로그램으로 교체
    _exit(127);                      //    exec이 반환했다면 실패
} else {                         // 부모
    int status;
    waitpid(pid, &status, 0);        // 3. 자식 종료 대기 + 종료 코드 회수
}
```

**fork가 저렴한 이유: Copy-on-Write.** `fork`는 부모의 주소 공간 전체를 "복제"하지만 실제로 페이지를 복사하지는 않는다. 페이지 테이블만 복사하고 모든 페이지를 읽기 전용으로 표시한다. 한쪽이 **쓰기**를 시도하는 순간 페이지 폴트가 나고 커널이 그 페이지 하나만 복사한다. 이것이 COW다. 그래서 fork 직후 exec하는 흔한 패턴은 거의 아무것도 복사하지 않는다.

다만 함정이 있다.

- **큰 프로세스의 fork는 여전히 비싸다.** 페이지 테이블 복사가 주소 공간 크기에 비례한다. 10GB 힙 프로세스의 fork는 수십 ms가 걸릴 수 있다(Redis BGSAVE 지연).
- **fork 후 부모가 계속 쓰기를 하면** COW 복사가 계속 일어나 메모리가 두 배 가까이 늘 수 있다.
- **멀티스레드 프로세스의 fork는 위험하다.** 자식에는 `fork`를 호출한 스레드 하나만 복제된다. 다른 스레드가 잡고 있던 뮤텍스는 영원히 잠긴 채 남는다(malloc 내부 락 포함). **fork 직후 exec만 하라.** 그 사이에 `malloc`이나 `printf`도 부르지 마라.
- 다른 프로그램을 띄우는 것이 목적이면 **`posix_spawn`**이 안전하고 빠르다.

### 2.2 exec: 프로세스 안의 프로그램을 통째로 교체

**한 줄 요약:** exec는 코드·데이터·힙·스택을 버리지만 PID와 열린 fd는 유지한다.

`execve`는 현재 프로세스의 코드, 데이터, 힙, 스택을 모두 버리고 새 실행 파일을 적재한다. **PID는 그대로**이고 열린 fd도 기본적으로 그대로 유지된다. 이것이 셸 리다이렉션 `ls > out.txt`의 원리다. fork 후 자식에서 fd 1을 `out.txt`로 바꾸고 exec하면 된다.

fd가 exec을 넘어 상속되는 게 싫으면 `O_CLOEXEC`로 열어라. 서버 소켓이 자식 프로세스에 새어 나가면 부모가 닫아도 포트가 안 풀리는 버그가 생긴다.

### 2.3 종료, 좀비, 고아

**한 줄 요약:** 종료한 프로세스는 부모가 wait로 회수할 때까지 PID와 종료 코드만 남은 좀비다.

**정상 종료 경로**: `exit()` → atexit 핸들러 실행, stdio 버퍼 플러시 → `_exit()` 시스템 콜 → 커널이 fd 닫기, 메모리 해제 → 종료 코드를 `task_struct`에 보관하고 **부모에게 `SIGCHLD` 전송**.

이 시점에서 프로세스는 **좀비(Z)**가 된다. 메모리도 fd도 없지만 종료 코드를 담은 `task_struct`와 PID가 남는다. 부모가 `wait()`/`waitpid()`로 회수하면 비로소 사라진다.

- **좀비가 쌓이면** PID를 낭비한다(`pid_max` 기본 32768 또는 4194304). 결국 `fork: Resource temporarily unavailable`이 난다. 좀비는 이미 죽었으므로 `kill -9`로 못 죽인다. **부모를 고쳐야 한다.**
- **고아(Orphan)**: 부모가 먼저 죽은 자식. **PID 1(init/systemd)**이나 "subreaper"로 지정된 프로세스에 재입양된다. init은 주기적으로 `wait`하여 고아가 좀비로 남지 않게 한다.

### 2.4 자식 회수의 올바른 패턴

**한 줄 요약:** SIGCHLD는 합쳐져서 올 수 있으므로 핸들러는 WNOHANG 루프로 회수한다.

```c
// 여러 자식이 동시에 죽어도 시그널은 한 번만 올 수 있으므로 루프
void on_sigchld(int sig) {
    int saved = errno;
    while (waitpid(-1, NULL, WNOHANG) > 0) { }
    errno = saved;
}
```

종료 코드에 관심이 없다면 `signal(SIGCHLD, SIG_IGN)`으로 커널이 자동 회수하게 할 수 있다. (시그널 자체는 [3장](03-시그널.md))

## 코어 3. 컨테이너의 PID 1 문제

### 3.1 PID 1이 특별한 두 가지 이유

**한 줄 요약:** PID 1은 고아의 입양처이자 시그널 무시 규칙의 대상이라서, 서버를 그대로 PID 1에 두면 좀비가 쌓이고 `docker stop`이 먹지 않는다.

도커 컨테이너 안에서는 **내 서버 프로세스가 PID 1**이 되는 경우가 많다. 그러면:

1. 컨테이너 내 모든 고아 프로세스가 내 서버에 재입양되는데 내 서버는 `wait`할 줄 모른다 → 좀비 누적.
2. PID 1은 시그널 처리가 특별하다. 핸들러를 등록하지 않은 시그널은 **커널이 무시**한다. 그래서 `docker stop`(SIGTERM)에 반응하지 않고 10초 뒤 SIGKILL로 강제 종료된다.

해결: `tini`나 `dumb-init`을 ENTRYPOINT로 쓰거나(`docker run --init`), 직접 SIGTERM 핸들러와 SIGCHLD 회수 로직을 구현한다.

> **[보충]** PID 1이 컨테이너 안에서 "내 서버"가 되는 이유(PID 네임스페이스)는 [9장](../2부-컨테이너-커널-기능과-Docker/09-네임스페이스.md)에서, 쿠버네티스 Pod의 종료 시퀀스는 [25장](../3부-쿠버네티스-구성-요소/25-Pod-생명주기와-리소스.md)에서 다룬다.

## 코어 4. 자격 증명과 자원 한도

### 4.1 자격 증명과 권한

**한 줄 요약:** 권한 검사는 유효 UID로 하고, 필요한 권한만 capabilities로 주며, 컨테이너는 root를 쓰지 않는 것이 좋다.

프로세스에는 **실제 UID(real)**, **유효 UID(effective)**, **저장된 set-UID(saved)**가 있고 권한 검사는 **유효 UID**로 한다.

- `passwd` 같은 set-UID 프로그램은 실행 시 유효 UID가 파일 소유자(root)가 된다.
- 서버가 80번 포트를 바인딩하려면 root(또는 `CAP_NET_BIND_SERVICE`)가 필요하다. root로 시작해 포트를 열고 `setuid`로 낮추는 고전 방식보다, `setcap cap_net_bind_service=+ep ./server`나 systemd의 `AmbientCapabilities`로 필요한 권한만 주는 것이 현재 표준이다.
- 컨테이너 안의 root는 기본적으로 capabilities가 제한된 root다. `docker run --user 1000` 등으로 애초에 root를 쓰지 않는 것이 좋다.

### 4.2 자원 한도: ulimit과 RLIMIT

**한 줄 요약:** 프로세스별 한도 중 서버가 반드시 올리는 것은 fd 수(`RLIMIT_NOFILE`)다.

`ulimit -a`로 보고 코드에서는 `getrlimit`/`setrlimit`을 쓴다.

| 한도 | 기본값(일반) | 초과 시 |
|---|---|---|
| `RLIMIT_NOFILE` (fd 수) | 1024 soft | `EMFILE`. 서버는 반드시 올려야 한다 |
| `RLIMIT_STACK` | 8MB | 스택 오버플로 → `SIGSEGV` |
| `RLIMIT_NPROC` (프로세스/스레드 수) | 수만 | `fork`/`pthread_create` 실패 `EAGAIN` |
| `RLIMIT_CORE` | 0 (코어 덤프 없음) | 디버깅 위해 `unlimited`로 |
| `RLIMIT_AS` (가상 메모리) | unlimited | `mmap` 실패 `ENOMEM` |

systemd 서비스는 `LimitNOFILE=65536` 식으로 지정한다. 컨테이너는 도커 데몬의 기본값을 상속한다.

## 코어 5. IPC와 세션

### 5.1 PID, 프로세스 그룹, 세션

**한 줄 요약:** 터미널이 끊기면 세션 리더에 SIGHUP이 가고, 그것이 백그라운드 서버까지 죽이는 경로가 된다.

```
세션(SID=100) ── 로그인 셸 bash(PID 100)
   ├─ 프로세스 그룹(PGID=200): cat file | grep x | sort
   │     ├─ cat  (PID 200)
   │     ├─ grep (PID 201)
   │     └─ sort (PID 202)
   └─ 프로세스 그룹(PGID=300): ./server &
         └─ server (PID 300)
```

- **프로세스 그룹**: 파이프라인 하나가 한 그룹이다. `Ctrl+C`는 전경 그룹 전체에 `SIGINT`를 보낸다. `kill -TERM -300`(음수 PID)으로 그룹 전체에 보낼 수 있다.
- **세션**: 터미널 하나에 연결된 그룹들의 묶음. 터미널이 끊기면(SSH 끊김) 세션 리더에게 `SIGHUP`이 가고 전파되어 백그라운드 서버까지 죽는다.

`nohup`, `setsid`, systemd 서비스가 이 문제를 푸는 방법이다. 직접 데몬을 만들던 고전 절차(fork → `setsid()` → 다시 fork → `chdir("/")`, `umask(0)`, 표준 입출력을 `/dev/null`로)는 systemd가 대신해 주므로, 요즘은 **포그라운드로 실행하고 stdout에 로그를 쓰는** 것이 권장된다. 컨테이너도 같은 원칙이다.

### 5.2 프로세스 간 통신(IPC)

**한 줄 요약:** 격리된 주소 공간 사이에는 커널이 중재하는 통로가 필요하고, 공유 메모리가 가장 빠르다.

| 방식 | 특징 | 용도 |
|---|---|---|
| 파이프 (`pipe`), FIFO | 단방향 바이트 스트림. 64KB 커널 버퍼. 꽉 차면 writer 블로킹 | 부모-자식, 셸 파이프라인 |
| Unix 도메인 소켓 | 양방향, 스트림/데이터그램, **fd 전달 가능**(`SCM_RIGHTS`) | 로컬 서비스 간 (Docker 데몬, systemd, DB 로컬 접속) |
| 공유 메모리 (`shm_open`+`mmap`, `memfd_create`) | 커널 개입 없이 직접 접근. 가장 빠름. 동기화는 직접 | 대용량·저지연 데이터 (DB 버퍼 풀, 멀티프로세스 캐시) |
| 시그널 | 정수 하나만 전달 | 종료·재시작 통지 ([3장](03-시그널.md)) |
| POSIX 메시지 큐, 세마포어 | 구조화된 메시지, 프로세스 간 동기화 | 잘 안 쓰인다. 대부분 소켓으로 대체 |
| eventfd | 카운터 하나. epoll에 붙일 수 있음 | 스레드/프로세스 간 이벤트 알림 |

공유 메모리가 가장 빠른 이유: 파이프/소켓은 데이터를 유저 버퍼 → 커널 버퍼 → 상대 유저 버퍼로 두 번 복사하지만, 공유 메모리는 **같은 물리 페이지를 두 프로세스의 가상 주소 공간에 매핑**만 해 두면 복사 없이 접근한다.

**파이프의 함정**: 자식의 stdout과 stderr을 둘 다 파이프로 받는 부모가 stdout만 읽으면, 자식이 stderr을 64KB 이상 쓰는 순간 자식이 블로킹되어 **데드락**이 된다. Python의 `subprocess.communicate()` 같은 API가 있는 이유다.

### 5.3 프로세스 vs 스레드

**한 줄 요약:** 프로세스는 격리와 안정성, 스레드는 저렴한 통신과 생성이라는 교환이다.

| 기준 | 여러 프로세스 | 여러 스레드 |
|---|---|---|
| 격리/안정성 | 하나가 죽어도 다른 것에 영향 없음 | 하나가 크래시하면 전체가 죽음 |
| 통신 비용 | IPC 필요, 상대적으로 비쌈 | 메모리 공유, 저렴하지만 동기화 필요 |
| 생성 비용 | 비쌈 (페이지 테이블 복사, 수십&#126;수백 µs) | 저렴 (수 µs) |
| 대표 사례 | nginx worker, PostgreSQL 백엔드, Chrome 탭, gunicorn 워커 | 웹 서버 요청 처리 풀, DB 커넥션 풀 |
| GIL 있는 언어(CPython) | 진짜 병렬 CPU 활용 가능 | CPU 바운드는 병렬 안 됨 |

직접 확인해 보는 명령은 다음과 같다.

```bash
ps -eo pid,ppid,pgid,sid,stat,cmd --forest     # 프로세스 트리와 그룹/세션
cat /proc/$$/status | grep -E 'State|Threads|VmRSS|Uid'
ls -l /proc/$$/fd                              # 셸이 열고 있는 fd
strace -f -e trace=process ./myprog            # fork/exec/wait/exit만 추적
ps -eo stat,pid,cmd | awk '$1 ~ /Z/'           # 좀비 찾기
```

- [ ] 프로세스는 그릇이고 실행은 스레드가 하며, `/proc/<pid>/maps`로 레이아웃을 볼 수 있다.

- [ ] 컨테이너에서 PID 1로 뜬다면 `tini`/`--init`을 쓰거나 SIGTERM/SIGCHLD를 직접 처리하는가?
- [ ] 서버의 `RLIMIT_NOFILE`을 예상 커넥션 수 이상으로 올렸는가?
- [ ] root 대신 필요한 capability만 주거나 `--user`로 비root로 실행하는가?
- [ ] 자식의 stdout/stderr 파이프를 동시에 소비하고 있는가?

### 시나리오로 확인하기

1. **상황:** 서버가 운영 스크립트를 `fork`+`exec`로 띄우는데, 며칠 뒤 `ps`에 `<defunct>` 프로세스가 수천 개 쌓이고 결국 `fork: Resource temporarily unavailable`이 난다.
   **질문:** 원인과 해결은?

   <details markdown="1"><summary>답 확인</summary>

   자식이 종료했는데 부모가 `wait`/`waitpid`로 회수하지 않아 좀비(Z)가 쌓이고 PID를 소진한 것이다. 좀비는 이미 죽었으므로 `kill -9`로 못 없애고 부모를 고쳐야 한다. SIGCHLD 핸들러에서 `waitpid(-1, NULL, WNOHANG)` 루프로 회수하거나, 종료 코드가 필요 없으면 `SIGCHLD`를 `SIG_IGN`으로 명시한다. → 코어 2

   </details>

2. **상황:** 컨테이너에서 `docker stop`을 하면 서버가 10초 동안 아무 반응이 없다가 강제 종료된다. 서버에는 SIGTERM 핸들러가 없다.
   **질문:** 왜 그런가?

   <details markdown="1"><summary>답 확인</summary>

   서버가 PID 1이라서다. PID 1은 핸들러를 등록하지 않은 시그널을 커널이 무시하므로 기본 동작이 "종료"인 SIGTERM도 무시된다. 10초 뒤 SIGKILL로 죽는다. 핸들러를 등록하거나 `tini`/`--init`으로 init을 PID 1에 두고 서버를 자식으로 둔다. → 코어 3

   </details>

3. **상황:** 서버가 설정 변경 시 `fork`+`exec`로 보조 프로세스를 띄운다. 이후 서버를 재시작하려 하면 포트가 이미 사용 중이라 `bind`가 실패하고, 부모는 이미 소켓을 닫은 상태다.
   **질문:** 원인은?

   <details markdown="1"><summary>답 확인</summary>

   exec 후에도 fd는 기본적으로 유지되어 리스닝 소켓이 자식에게 상속되었다. 자식이 계속 열고 있으므로 포트가 안 풀린다. 소켓을 `SOCK_CLOEXEC`/`O_CLOEXEC`로 열어 exec 때 닫히게 한다. → 코어 2

   </details>

4. **상황:** SSH로 접속해 `./server &`로 띄운 뒤 접속을 끊었더니 서버가 죽었다.
   **질문:** 원인과 대응은?

   <details markdown="1"><summary>답 확인</summary>

   터미널이 끊기면 세션 리더에게 SIGHUP이 가고 그것이 전파되어 백그라운드 서버까지 종료된다. `nohup`, `setsid`, systemd 서비스로 세션에서 분리한다. 요즘은 systemd 서비스로 포그라운드 실행하고 stdout에 로그를 쓰는 방식이 권장된다. → 코어 5

   </details>

### 3. 기억 고리

- **C++ 유추:** `new`/`delete` 쌍 = `fork`/`wait` 쌍 ⚠️ 회수 대상이 메모리가 아니라 종료 코드와 PID이고, 회수는 자식이 아니라 **부모**의 책임이다.
- **C++ 유추:** `main`에서 `SIGPIPE` 무시 설정 = 시그널 준비 ⚠️ PID 1은 핸들러가 없으면 SIGTERM마저 무시되는 별도 규칙이 있다.
- **비유:** 프로세스 = 가게(주소 공간·장부·허가증), 스레드 = 가게 안 직원, fork = 가게를 통째로 복사하는 것처럼 보이지만 실제로는 장부를 같이 보다가 누가 고쳐 쓸 때만 그 쪽을 복사(COW). ⚠️ 가게가 폐업(종료)해도 폐업 신고서(종료 코드)는 부모가 수령해 가야 정리되며, 수령 전의 가게 간판이 좀비다.
- **비유:** PID 1 = 건물 관리인. 주인 없는 우편물(고아)을 모두 맡고 정리해야 한다. ⚠️ 시그널 면에서는 반대로 "지시 매뉴얼(핸들러)이 없으면 관리인에게 오는 해고 통보를 무시"하는 특수 규칙이 있다.
- **묶음(3의 법칙):** fork·exec·wait / 좀비·고아·PID 1 / 파이프·Unix 소켓·공유 메모리(IPC 대표 3).
- **대칭·순서:** fork(복제) ↔ exec(교체), 생성 쪽 `fork` ↔ 회수 쪽 `wait`. 흐름: fork → exec → exit → SIGCHLD → wait → 소멸.

### 4. 가르치기 · 반대편 서기

- **거울 설명 (1분, 원고 없이):** "좀비 프로세스가 왜 생기고 왜 `kill -9`로 못 죽이는가"를 처음 듣는 사람에게 설명해 보세요.
- **C++ 서버 동료에게 설명하기:** "우리 서버를 컨테이너 PID 1로 띄우면 왜 `docker stop`이 10초 걸리는가"를 PID 1의 시그널 규칙으로 1분 안에 설명해 보세요.
- **랜덤 논리 게임:** A "서버는 멀티프로세스가 더 안전하다" vs B "서버는 멀티스레드가 더 효율적이다" — 격리, 통신 비용, 생성 비용을 근거로 번갈아 변호해 보세요.
