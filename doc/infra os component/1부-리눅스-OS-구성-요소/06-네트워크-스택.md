# 6장. 네트워크 스택

> **🎮 게임 서버 개발자에게** — 이 장은 거의 당신의 홈그라운드다. `socket`/`bind`/`listen`/`accept`, 논블로킹 소켓, epoll 이벤트 루프, `TCP_NODELAY`, `SIGPIPE`를 이미 써 봤을 것이다. 그래서 이 장의 목표는 새 API를 배우는 것이 아니라 **"내가 아는 것이 커널 안에서 정확히 어떻게 동작하는가"**를 다지는 것이다. 핸드셰이크와 accept 큐는 커널이 처리하고, `TIME_WAIT`는 커널 상태이며, 이 구조가 이후 Docker 브리지·iptables·kube-proxy가 끼어드는 바로 그 지점이 된다.
>
> **🎯 실무에서 이 장이 필요한 순간**
> - 서버를 재시작하면 `bind: Address already in use`가 나고, 접속 폭주 때 일부 클라이언트의 `connect`가 타임아웃된다.
> - 클라이언트가 전원이 꺼지거나 랜선이 뽑혔는데 서버에는 연결이 영원히 `ESTABLISHED`로 남아 있다.
> - 이벤트 루프(IO 스레드)에서 DNS 조회나 파일 I/O 한 번 때문에 모든 접속자의 틱이 멈춘다. 컨테이너에서는 DNS가 유난히 느리다.

## 코어 — 이것만은 100%

> **한 문장:** 소켓은 fd이고 TCP는 메시지 경계 없는 바이트 스트림이며, 핸드셰이크·accept 큐·TIME_WAIT는 커널이 관리하고, 대량 접속은 이벤트 루프(epoll) 안에서 절대 블로킹하지 않는 구조로 처리한다.

1. **소켓 = fd, 핸드셰이크는 커널의 일** — `accept()`는 완성된 연결을 큐에서 꺼낼 뿐이다. backlog가 차면 SYN이 무시된다. 관찰은 `ss -ltn`.
2. **TCP는 스트림** — `read`/`write`는 요청한 양보다 적게 처리될 수 있고, 메시지 경계는 애플리케이션이 만든다(길이 접두어). `read`가 0이면 EOF.
3. **TIME_WAIT와 `SO_REUSEADDR`** — 먼저 닫은 쪽이 60초 TIME_WAIT. 서버는 `bind` 전에 `SO_REUSEADDR`, 클라이언트 포트 고갈은 커넥션 풀로 푼다.
4. **epoll 이벤트 루프의 규칙** — O(준비된 수)로 대기하고, 루프 안에서 블로킹(DNS·파일·동기 DB)하지 않으며, ET는 `EAGAIN`까지 읽는다. io_uring은 완료 모델이다.
5. **죽은 연결과 SIGPIPE** — half-open은 heartbeat/keepalive 없이는 감지할 수 없고, 닫힌 소켓에 `write`하면 `SIGPIPE`로 프로세스가 죽는다. 같은 머신 IPC는 Unix 도메인 소켓.

|---|---|---|---|
| `listen(fd, backlog)` 후 `accept` 루프 | 커널의 3-way handshake와 accept 큐 | `accept`는 연결을 하나씩 꺼내는 호출 | **`accept`를 안 불러도 클라이언트의 `connect`는 성공한다**(커널이 이미 완료). 큐가 차야 비로소 SYN이 무시된다 |

## 코어 1. 소켓 = fd, 핸드셰이크는 커널의 일

### 1.1 소켓은 파일 디스크립터다

**한 줄 요약:** `socket()`의 반환값은 그냥 fd라서 `read`/`write`/`close`/`epoll`이 파일과 똑같이 동작한다.

```c
int fd = socket(AF_INET, SOCK_STREAM, 0);   // TCP 소켓. 반환값은 그냥 fd
```

`send`/`recv`는 플래그를 받는 소켓 전용 확장일 뿐이다. 이 통일성 덕분에 이벤트 루프 하나가 소켓, 파이프, 타이머(`timerfd`), 시그널(`signalfd`)을 한꺼번에 기다릴 수 있다([5장](05-파일시스템과-IO.md)).

### 1.2 TCP 서버의 생애

**한 줄 요약:** 3-way handshake는 커널이 하고, `accept()`는 완성된 연결을 큐에서 꺼내는 것뿐이다.

```
서버                                       클라이언트
socket()                                   socket()
bind(0.0.0.0:8080)
listen(backlog)          ◀── SYN ───────── connect()
  [커널이 3-way handshake 완료 → accept 큐에 넣음]
accept() → 새 fd         ─── SYN+ACK ──▶
                         ◀── ACK ────────
read(new_fd)             ◀── 데이터 ─────  write()
write(new_fd)            ─── 데이터 ────▶  read()
close(new_fd)            ─── FIN ───────▶
                         ◀── FIN ────────  close()
```

**핸드셰이크는 커널이 한다.** `accept()`는 이미 연결이 완성된 소켓을 큐에서 꺼내는 것뿐이다. 그래서 서버 프로세스가 `accept`를 안 부르고 있어도 클라이언트의 `connect`는 성공한다. 큐(backlog)가 꽉 차면 그때부터 SYN이 무시되고 클라이언트는 재전송 후 타임아웃을 겪는다.

- `listen(fd, backlog)`의 backlog는 `net.core.somaxconn`(기본 4096)으로 상한이 잡힌다. 트래픽 스파이크에서 `accept` 큐 오버플로가 나면 `ss -ltn`의 Recv-Q 컬럼과 `nstat -az TcpExtListenOverflows`로 확인한다.

## 코어 2. TCP는 스트림이다

### 2.1 메시지 경계가 없다

**한 줄 요약:** 보낸 쪽의 `write` 횟수와 받는 쪽의 `read` 횟수는 무관하다.

가장 흔한 초보 버그다.

```c
// 클라이언트
write(fd, "HELLO", 5);
write(fd, "WORLD", 5);

// 서버
n = read(fd, buf, 1024);   // "HELLOWORLD" 10바이트가 한 번에 올 수 있다.
                           // "HEL" 3바이트만 올 수도 있다. "HELLOWOR"이 올 수도 있다.
```

TCP는 **바이트 스트림**이다. 로컬에서 테스트할 땐 우연히 1:1로 맞아서 잘 되다가, 운영 환경에서 패킷이 나뉘거나 합쳐지면 깨진다.

### 2.2 경계는 애플리케이션이 만든다

**한 줄 요약:** 길이 접두어가 가장 일반적이고, `read`는 필요한 양이 찰 때까지 루프하며, 0은 EOF다.

**메시지 경계는 애플리케이션이 만들어야 한다.** 세 가지 방법이 있다.

1. **길이 접두어**: `[4바이트 길이][본문]`. 가장 일반적(gRPC, 대부분의 바이너리 프로토콜).
2. **구분자**: `\r\n`(HTTP 헤더, Redis 프로토콜). 본문에 구분자가 나오면 이스케이프가 필요.
3. **고정 길이**: 단순하지만 유연성 없음.

그리고 **`read`가 요청한 바이트를 다 채워줄 때까지 루프**해야 한다. `read`는 1바이트만 반환해도 정상이다. 마찬가지로 `write`도 요청한 양보다 적게 쓰고 반환할 수 있다(논블로킹 소켓에서 특히).

`read`가 **0을 반환**하면 상대가 연결을 닫았다는 뜻(EOF). -1과 `ECONNRESET`이면 상대가 비정상 종료(RST)했다는 뜻이다.

## 코어 3. TIME_WAIT와 SO_REUSEADDR

### 3.1 "Address already in use"

**한 줄 요약:** 먼저 닫은 쪽이 2×MSL(리눅스 60초) TIME_WAIT에 머물고, 서버는 `bind` 전에 `SO_REUSEADDR`을 켠다.

TCP 연결을 **먼저 닫은 쪽**은 마지막 ACK를 보낸 후 **TIME_WAIT** 상태로 2×MSL(리눅스: 60초) 동안 머문다. 늦게 도착하는 패킷이 새 연결과 섞이지 않게 하기 위해서다. 서버가 커넥션을 먼저 닫는 구조(HTTP 서버가 대부분 그렇다)라면 서버 쪽에 TIME_WAIT 소켓이 쌓이고, 그 소켓이 점유한 포트에는 `bind`가 안 된다.

해결: **`SO_REUSEADDR`**을 `bind` 전에 켠다. 모든 서버 코드에 넣어야 하는 것이 기본이다.

```c
int on = 1;
setsockopt(fd, SOL_SOCKET, SO_REUSEADDR, &on, sizeof(on));
bind(fd, ...);
```

### 3.2 TIME_WAIT 관련 추가 지식

**한 줄 요약:** TIME_WAIT 수만 개는 정상이고, 문제는 클라이언트 쪽 에페머럴 포트 고갈이다.

- TIME_WAIT 소켓 수만 개는 **정상**이다. 메모리를 조금 쓸 뿐이다. 문제는 클라이언트 측에서 **에페머럴 포트(기본 32768&#126;60999, 약 28,000개)**가 고갈되는 것이다. 초당 500개 짧은 연결을 만드는 클라이언트(예: DB에 커넥션 풀 없이 매번 연결)는 60초 안에 포트를 다 쓴다. 해결은 **커넥션 풀/keep-alive**다. `net.ipv4.tcp_tw_reuse=1`도 도움이 된다.
- `SO_REUSEPORT`는 다른 것이다. 여러 프로세스/스레드가 **같은 포트에 각자 `bind`**할 수 있게 하고 커널이 연결을 분배한다. 멀티프로세스 서버의 accept 경합을 없애는 용도(nginx `reuseport`).

> **[보충]** 컨테이너를 `docker run -p`로 노출하면 호스트 포트로의 연결이 NAT를 거치므로 TIME_WAIT와 conntrack 항목이 호스트에도 쌓인다. 이 경로는 [16장](../2부-컨테이너-커널-기능과-Docker/16-Docker-네트워크.md)에서 다룬다.

## 코어 4. epoll 이벤트 루프의 규칙

### 4.1 블로킹 I/O와 그 한계

**한 줄 요약:** 커넥션당 스레드는 수천까지 되지만 그 이상은 C10K 문제이고, 답은 I/O 멀티플렉싱이다.

기본 소켓은 블로킹이다. `read`는 데이터가 올 때까지, `accept`는 연결이 올 때까지, `connect`는 핸드셰이크가 끝날 때까지 스레드를 잠재운다. "커넥션당 스레드 하나" 모델은 단순하고 수천 커넥션까지는 잘 돈다. 그 이상에서는 다음 문제가 생긴다.

- 스레드 1만 개 = 스택 예약 80GB(가상), 실제 수십 MB 이상, 스케줄러 부담, 컨텍스트 스위칭 폭증([7장](07-스레드와-동시성.md)).
- 대부분의 스레드는 `read`에서 잠들어 있다. 코어는 놀고 있다.

이것이 1999년의 **C10K 문제**이고, 답은 "스레드가 기다리는 대신 커널에게 '이 소켓들 중 어느 것이든 준비되면 알려줘'라고 묻는" **I/O 멀티플렉싱**이다.

### 4.2 논블로킹 + epoll

**한 줄 요약:** 논블로킹은 `EAGAIN`을 즉시 돌려주고, epoll은 fd를 한 번 등록하면 준비된 것만 돌려준다(O(준비된 수)).

```c
fcntl(fd, F_SETFL, O_NONBLOCK);     // 또는 socket(..., SOCK_NONBLOCK)
n = read(fd, buf, sz);
if (n == -1 && errno == EAGAIN) { /* 지금은 데이터 없음. 에러 아님. 나중에 다시 */ }
```

논블로킹 소켓은 데이터가 없으면 즉시 `EAGAIN`을 반환한다. 이제 "언제 다시 시도할지"를 알아야 한다. 그것이 `epoll`이다.

```c
int ep = epoll_create1(0);
struct epoll_event ev = { .events = EPOLLIN, .data.fd = listen_fd };
epoll_ctl(ep, EPOLL_CTL_ADD, listen_fd, &ev);

for (;;) {
    struct epoll_event events[64];
    int n = epoll_wait(ep, events, 64, -1);        // 준비된 fd가 생길 때까지 잠듦
    for (int i = 0; i < n; i++) {
        if (events[i].data.fd == listen_fd) {
            int c = accept4(listen_fd, NULL, NULL, SOCK_NONBLOCK | SOCK_CLOEXEC);
            /* c를 epoll에 등록 */
        } else {
            /* read → 처리 → write. EAGAIN까지 반복 */
        }
    }
}
```

**왜 select/poll이 아니라 epoll인가**: `select`/`poll`은 매 호출마다 감시할 fd 목록 전체를 커널에 넘기고, 커널은 전체를 순회한다. O(n). fd 1만 개면 매번 1만 개를 검사한다. `epoll`은 fd를 **한 번 등록**해 두면 커널이 준비된 것만 돌려준다. O(준비된 수). `select`에는 fd 1024 한도(`FD_SETSIZE`)도 있다.

### 4.3 Level-triggered vs Edge-triggered

**한 줄 요약:** LT는 남아 있는 한 계속 알려주고, ET는 변할 때 한 번만 알려주므로 `EAGAIN`까지 읽어야 한다.

- **Level-triggered(기본)**: 읽을 데이터가 남아 있는 한 매번 알려준다. 안전하다. 조금 덜 효율적.
- **Edge-triggered(`EPOLLET`)**: 상태가 **변할 때만** 한 번 알려준다. 알림을 받으면 **`EAGAIN`이 나올 때까지 끝까지 읽어야 한다.** 안 그러면 남은 데이터에 대해 다시는 알림이 오지 않고 연결이 멈춘 듯 보인다. 고성능 서버가 쓰지만 실수하기 쉽다.

### 4.4 이벤트 루프의 규칙

**한 줄 요약:** 루프 안에서 블로킹하지 말고, CPU 작업은 워커로 넘기고, 코어 수만큼 루프를 띄운다.

1. **루프 안에서 블로킹하지 마라.** 파일 I/O, DNS 조회(`getaddrinfo`는 블로킹이다!), 동기 DB 호출 하나가 모든 커넥션을 멈춘다. Node.js가 DNS와 파일 I/O를 별도 스레드 풀에서 하는 이유다.
2. **CPU를 오래 쓰는 작업도 마찬가지다.** 워커 스레드 풀로 넘긴다.
3. 코어 수만큼 이벤트 루프를 띄워 각각 epoll을 돈다(nginx worker, `SO_REUSEPORT`).

Node.js(libuv), Go 런타임의 netpoller, Java NIO, Rust tokio, Python asyncio가 전부 아래에서 epoll을 쓴다. 언어의 `async/await`는 이 구조에 문법을 씌운 것이다.

### 4.5 io_uring: 다음 세대

**한 줄 요약:** 공유 링 버퍼 두 개로 시스템 콜 횟수를 줄이고 파일 I/O도 비동기로 만든 완료 모델이다.

`epoll`은 "준비됐다"고 알려줄 뿐 실제 `read`는 따로 시스템 콜이다. 그리고 **디스크 파일에는 epoll이 통하지 않는다**(항상 준비됨으로 나온다). `io_uring`(5.1+)은 이 둘을 해결한다.

- 유저 공간과 커널이 **공유 메모리 링 버퍼** 두 개(제출 큐, 완료 큐)를 공유한다. 요청을 링에 넣고 `io_uring_enter` 한 번으로 여러 개를 제출하며, 완료도 링에서 읽는다. 시스템 콜 횟수가 극적으로 줄어든다.
- 파일 I/O도 진정한 비동기로 된다. `read`, `write`, `accept`, `send`, `recv`, `fsync`, `openat` 등 대부분의 시스템 콜이 비동기 연산으로 제공된다.
- "준비 모델(readiness)"이 아니라 "완료 모델(completion)"이다. Windows IOCP와 같은 철학이다.

아직 `epoll`이 표준이고 `io_uring`은 보안 이슈로 일부 환경(일부 컨테이너 런타임)에서 막혀 있다. 하지만 고성능 스토리지·네트워크 코드의 방향은 이쪽이다.

## 코어 5. 죽은 연결, SIGPIPE, 그리고 소켓 옵션

### 5.1 알아야 할 소켓 옵션과 커널 동작

**한 줄 요약:** 게임·RPC는 `TCP_NODELAY`, 장기 연결은 keepalive를 짧게 조정한다.

| 옵션/동작 | 의미 | 언제 |
|---|---|---|
| `TCP_NODELAY` | Nagle 알고리즘 끄기. 작은 패킷을 모으지 않고 즉시 전송 | 요청-응답 지연이 중요한 RPC, 게임. 대부분의 RPC 라이브러리가 기본으로 켠다 |
| `SO_KEEPALIVE` + `TCP_KEEPIDLE/INTVL/CNT` | 유휴 연결에 주기적 probe. 상대가 죽었으면 감지 | 기본은 2시간 후 시작. 장기 연결은 반드시 짧게 조정(예: 60초) |
| `SO_RCVBUF`/`SO_SNDBUF` | 커널 소켓 버퍼 크기 | 보통 자동 조정(`tcp_rmem`/`tcp_wmem`)에 맡기는 게 낫다 |
| `SO_LINGER` | `close` 시 미전송 데이터 처리 | 대부분 건드리지 말 것. 0으로 설정하면 RST 전송 |
| `TCP_CORK` | 데이터를 모아서 한 번에 | 헤더+파일 본문을 하나의 패킷으로 (`sendfile`과 함께) |
| `TCP_FASTOPEN` | 핸드셰이크와 함께 데이터 전송 | 짧은 연결 반복 시 |

### 5.2 half-open 연결과 SIGPIPE

**한 줄 요약:** 상대가 소리 없이 사라지면 heartbeat 없이는 모르고, 닫힌 소켓에 쓰면 SIGPIPE로 서버가 조용히 죽는다.

**half-open 연결**: 상대 머신의 케이블이 뽑히거나 전원이 꺼지면 FIN도 RST도 오지 않는다. 내 소켓은 영원히 `ESTABLISHED`로 남는다. **애플리케이션 레벨 heartbeat나 keepalive 없이는 죽은 연결을 감지할 수 없다.** 커넥션 풀이 오래된 연결에서 갑자기 실패하는 이유다.

**`SIGPIPE`**: 상대가 닫은 소켓에 `write`하면 `EPIPE` 대신 `SIGPIPE` 시그널이 오고 **기본 동작은 프로세스 종료**다. 서버가 로그 한 줄 없이 사라진다. 모든 네트워크 서버는 `signal(SIGPIPE, SIG_IGN)`을 하거나 `send(..., MSG_NOSIGNAL)`을 써야 한다([3장](03-시그널.md)).

### 5.3 데이터 복사 줄이기: sendfile과 zero-copy

**한 줄 요약:** `sendfile`은 페이지 캐시에서 소켓 버퍼로 유저 공간을 거치지 않고 보낸다.

파일을 소켓으로 보내는 고전 코드는 다음과 같다.

```c
read(file_fd, buf, n);    // 디스크 → 페이지 캐시 → 유저 버퍼 (복사 1)
write(sock_fd, buf, n);   // 유저 버퍼 → 소켓 버퍼 (복사 2) → NIC
```

```c
sendfile(sock_fd, file_fd, &off, n);   // 페이지 캐시 → 소켓 버퍼. 유저 공간 거치지 않음
```

`sendfile`은 데이터를 유저 공간으로 올리지 않고 커널 안에서 페이지 캐시 → 소켓으로 넘긴다. 복사 한 번과 시스템 콜 두 번을 줄인다. 정적 파일 서버(nginx, Kafka의 consumer 전송)가 쓴다. `splice`는 파이프를 거쳐 임의의 fd 간에 같은 일을 한다. `MSG_ZEROCOPY`는 큰 `send`에서 유저 버퍼를 복사하지 않고 직접 NIC에 넘긴다(10KB 이상에서 이득).

### 5.4 Unix 도메인 소켓

**한 줄 요약:** 같은 머신 IPC는 TCP 스택을 건너뛰는 `AF_UNIX`이고, `SCM_RIGHTS`로 fd 자체를 전달할 수 있다.

같은 머신 안의 프로세스 간에는 `AF_UNIX`를 쓴다. TCP 스택(체크섬, 순서 제어, 혼잡 제어)을 통째로 건너뛰어 2배 이상 빠르고, 파일시스템 경로(`/var/run/docker.sock`)에 바인딩되어 파일 권한으로 접근 제어가 된다. API는 TCP 소켓과 같다.

특별한 능력: **`SCM_RIGHTS`로 파일 디스크립터 자체를 다른 프로세스에 전달**할 수 있다. 리스닝 소켓을 새 버전의 서버 프로세스에 넘겨 무중단 재시작을 하거나(HAProxy, systemd socket activation), 권한 있는 프로세스가 파일을 열어 권한 없는 워커에 넘기는 데 쓴다. Docker 데몬의 API도 `docker.sock`이라는 이 Unix 소켓이다([13장](../2부-컨테이너-커널-기능과-Docker/13-Docker-아키텍처.md)).

### 5.5 DNS는 블로킹이다

**한 줄 요약:** `getaddrinfo()`는 동기 블로킹이라 이벤트 루프 안에서 부르면 전체가 멈춘다.

`getaddrinfo()`는 `/etc/hosts`를 읽고, `/etc/resolv.conf`의 네임서버에 UDP로 묻고, 응답을 기다린다. **동기 블로킹**이고 타임아웃은 기본 5초 × 재시도다. 이벤트 루프 안에서 부르면 모든 커넥션이 5초 멈춘다. 별도 스레드에서 하거나(libuv 방식), 비동기 리졸버(c-ares)를 쓰거나, 결과를 캐시해야 한다. 컨테이너에서 DNS가 느린 것은 흔한 장애 원인이다(`ndots:5` 문제, [28장](../3부-쿠버네티스-구성-요소/28-CoreDNS-Ingress-NetworkPolicy.md)).

### 시나리오로 확인하기

1. **상황:** 점검 후 서버를 재시작했더니 `bind: Address already in use`로 올라오지 않는다. `ps`에는 옛 프로세스가 없다.
   **질문:** 원인과 해결은?

   <details markdown="1"><summary>답 확인</summary>

   서버가 연결을 먼저 닫았다면 서버 쪽에 TIME_WAIT 소켓이 2×MSL(60초) 남고, 그 포트에는 `bind`가 안 된다. 이 상태는 프로세스가 아니라 커널이 갖고 있다. `bind` 전에 `SO_REUSEADDR`을 켠다. `ss -tlnp | grep :PORT`로 점유 프로세스인지 TIME_WAIT인지 구분한다. → 코어 3

   </details>

2. **상황:** 이벤트가 몰리는 시간에 일부 클라이언트에서 `connect`가 타임아웃되고, 서버 로그에는 아무 흔적이 없다.
   **질문:** 무엇을 확인하나?

   <details markdown="1"><summary>답 확인</summary>

   accept 큐 오버플로를 의심한다. 핸드셰이크는 커널이 하고 `accept` 큐(backlog, `net.core.somaxconn` 상한)가 차면 SYN이 무시되어 클라이언트가 재전송 후 타임아웃을 겪는다. `ss -ltn`의 Recv-Q와 `nstat -az | grep ListenOverflows`로 확인하고 backlog/`somaxconn`을 올리며 `accept` 처리가 느린지 본다. → 코어 1

   </details>

3. **상황:** 한 클라이언트의 랜선이 뽑혔는데 서버의 `ss`에는 그 연결이 몇 시간째 `ESTABLISHED`다. 슬롯과 메모리가 계속 점유된다.
   **질문:** 왜 서버가 몰랐고 어떻게 막나?

   <details markdown="1"><summary>답 확인</summary>

   상대 머신이 사라지면 FIN도 RST도 오지 않아 half-open이 된다. 애플리케이션 heartbeat(응답 없으면 끊기)를 구현하거나 `SO_KEEPALIVE`와 `TCP_KEEPIDLE/INTVL/CNT`를 짧게 조정한다(기본은 2시간 후 시작). → 코어 5

   </details>

4. **상황:** 접속자 수가 늘자 IO 스레드에서 처음 보는 호스트 이름 조회(`getaddrinfo`)를 하는 코드 때문에 모든 접속자의 처리가 수 초씩 멈춘다.
   **질문:** 왜이고 어떻게 고치나?

   <details markdown="1"><summary>답 확인</summary>

   `getaddrinfo()`는 동기 블로킹이고 타임아웃이 기본 5초 × 재시도다. 이벤트 루프 안의 블로킹 호출은 모든 커넥션을 멈춘다. 별도 스레드로 빼거나(libuv 방식) 비동기 리졸버(c-ares)를 쓰거나 결과를 캐시한다. → 코어 4, 코어 5

   </details>

### 2. 인출 질문

1. 서버가 `accept()`를 호출하지 않아도 클라이언트의 `connect()`가 성공하는 이유는?

   <details markdown="1"><summary>답 확인</summary>

   3-way handshake는 커널이 완료하고 완성된 연결을 accept 큐에 넣기 때문이다. `accept()`는 그 큐에서 꺼내는 호출일 뿐이다. 큐(backlog)가 꽉 차면 그때부터 SYN이 무시되어 클라이언트가 타임아웃을 겪는다. → 코어 1

   </details>

2. 클라이언트가 `write` 두 번으로 "HELLO", "WORLD"를 보내면 서버의 `read`는 무엇을 받을 수 있는가? 어떻게 대응하나?

   <details markdown="1"><summary>답 확인</summary>

   "HELLOWORLD" 10바이트가 한 번에 올 수도, "HEL"만, "HELLOWOR"만 올 수도 있다. TCP는 경계 없는 바이트 스트림이므로 애플리케이션이 길이 접두어/구분자/고정 길이로 경계를 만들고, 필요한 양이 찰 때까지 루프로 읽는다. → 코어 2

   </details>

3. TIME_WAIT는 왜 존재하고, 수만 개가 있으면 문제인가?

   <details markdown="1"><summary>답 확인</summary>

   먼저 닫은 쪽이 2×MSL(60초) 머물러 늦게 도착한 패킷이 새 연결과 섞이지 않게 한다. 수만 개는 정상(메모리를 조금 쓸 뿐)이다. 문제는 클라이언트 측 에페머럴 포트(32768&#126;60999, 약 28,000개)가 고갈되는 것이며, 커넥션 풀/keep-alive로 푼다. → 코어 3

   </details>

4. `SO_REUSEADDR`와 `SO_REUSEPORT`의 차이는?

   <details markdown="1"><summary>답 확인</summary>

   `SO_REUSEADDR`은 TIME_WAIT 소켓이 있어도 `bind`가 되게 해서 재시작을 가능하게 한다. `SO_REUSEPORT`는 여러 프로세스/스레드가 같은 포트에 각자 `bind`하고 커널이 연결을 분배하게 해서 accept 경합을 없앤다. → 코어 3

   </details>

5. select/poll 대신 epoll을 쓰는 이유와 ET 모드의 주의점은?

   <details markdown="1"><summary>답 확인</summary>

   select/poll은 매 호출마다 fd 전체를 넘기고 순회하는 O(n)이고 select는 1024 한도가 있다. epoll은 한 번 등록하면 준비된 것만 돌려주는 O(준비된 수)다. ET는 상태가 변할 때 한 번만 알려주므로 `EAGAIN`이 나올 때까지 끝까지 읽어야 하며, 아니면 연결이 멈춘 듯 보인다. → 코어 4

   </details>

6. 이벤트 루프 안에서 하면 안 되는 일 세 가지는?

   <details markdown="1"><summary>답 확인</summary>

   파일 I/O, DNS 조회(`getaddrinfo`는 블로킹), 동기 DB 호출이다. 하나가 전 커넥션을 멈춘다. CPU를 오래 쓰는 작업도 워커 스레드 풀로 넘긴다. → 코어 4

   </details>

7. 상대 머신이 갑자기 전원이 꺼지면 내 소켓은 어떻게 되고, 어떻게 감지하나?

   <details markdown="1"><summary>답 확인</summary>

   FIN도 RST도 오지 않아 영원히 `ESTABLISHED`로 남는다(half-open). 애플리케이션 heartbeat나 keepalive(`SO_KEEPALIVE`, 기본 2시간 후 시작이므로 장기 연결은 60초 정도로 조정)로만 감지한다. → 코어 5

   </details>

8. 상대가 닫은 소켓에 `write`했더니 서버가 로그 없이 사라졌다. 왜 그리고 어떻게 막나?

   <details markdown="1"><summary>답 확인</summary>

   `EPIPE` 대신 `SIGPIPE`가 오고 기본 동작이 프로세스 종료이기 때문이다. `signal(SIGPIPE, SIG_IGN)` 또는 `send(..., MSG_NOSIGNAL)`을 쓴다. → 코어 5

   </details>

### 3. 기억 고리

- **C++ 유추:** `accept()` 루프 = 커널 큐 소비자 ⚠️ 연결을 "받는" 것이 아니라 커널이 이미 완료한 연결을 꺼내는 것이므로, 서버가 바빠도 `connect`는 성공하고 큐 오버플로가 나야 비로소 거부된다.
- **C++ 유추:** `epoll_wait` 루프 = 게임 서버 IO 스레드 ⚠️ 디스크 파일에는 epoll이 통하지 않고 `getaddrinfo`가 블로킹이라서, 루프 안의 "한 번뿐인" 호출이 전체 틱을 멈춘다.
- **비유:** 커널의 accept 큐 = 식당 대기 의자. 손님(연결)은 직원이 안 불러도 의자에 앉아(connect 성공) 있고, 의자가 다 차야 문 앞에서 돌려보낸다(SYN 무시). ⚠️ 비유가 깨지는 지점: 돌려보낸 손님은 포기하지 않고 재전송으로 계속 다시 와서 타임아웃까지 기다린다.
- **비유:** TIME_WAIT = 식당 테이블 정리 시간. 손님이 먼저 일어난 테이블은 60초 뒤에 새 손님이 앉는다. ⚠️ 비유가 깨지는 지점: 새 손님(`bind`)은 `SO_REUSEADDR`로 "정리 중이어도 앉겠다"고 선언할 수 있고, 정리 상태는 가게(커널)가 쥐고 있어서 프로세스를 죽여도 안 풀린다.
- **묶음(3의 법칙):** 메시지 경계 3방식(길이 접두어·구분자·고정 길이) / 이벤트 루프 금지 3가지(파일 I/O·DNS·동기 DB) / TIME_WAIT 3대 지식(60초·SO_REUSEADDR·포트 고갈).
- **대칭·순서:** `SO_REUSEADDR`(재시작용, TIME_WAIT 우회) ↔ `SO_REUSEPORT`(분산용, 같은 포트 다중 bind). LT(남아 있으면 계속) ↔ ET(변할 때 한 번). epoll(준비 모델) ↔ io_uring(완료 모델).
