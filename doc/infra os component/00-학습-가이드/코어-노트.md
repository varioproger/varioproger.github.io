# 코어 노트

## 결정적 지식 3개 (이 책 전체의 뼈대)

1. **컨테이너는 커널 객체가 아니다.** namespace(무엇을 보는가) + cgroup(얼마나 쓰는가) + capability/seccomp(무엇을 할 수 있는가) + overlayfs(어떤 파일을 보는가)를 붙인 **리눅스 프로세스**일 뿐이다.
2. **쿠버네티스는 "원하는 상태"를 저장하고 조정 루프가 현실을 맞추는 시스템이다.** API 서버(문지기) → etcd(저장) → 컨트롤러/스케줄러(판단) → kubelet(실행).
3. **쿠버네티스의 모든 선언은 결국 리눅스 커널 기능이 된다.** Pod = namespace 공유 컨테이너, limits = cgroup, Service = iptables/IPVS DNAT 규칙, Volume = mount.

## 장별 한 문장

시작 전 한 번 훑고, 매주 한 문장씩 소리 내어 설명해 보세요.

- **1장. 커널, 시스템 콜, 스케줄러** — 내 프로그램은 유저 모드에 갇혀 시스템 콜·인터럽트·예외로만 커널에 들어가고, 커널은 프로세스와 스레드를 모두 태스크로 스케줄링하며, 컨테이너의 CPU 제한도 그 스케줄러 위의 cgroup 쿼터일 뿐이다. ([본문](../1부-리눅스-OS-구성-요소\01-커널-시스템콜-스케줄러.md))
- **2장. 프로세스** — 프로세스는 주소 공간·fd 테이블·자격 증명·한도를 묶은 "그릇"이고 실제 실행은 스레드가 하며, 자식은 fork+exec로 만들어져 부모가 wait로 회수해야 하고, 컨테이너의 PID 1은 그 회수와 시그널 처리의 책임을 진다. ([본문](../1부-리눅스-OS-구성-요소\02-프로세스.md))
- **3장. 시그널** — 시그널은 번호 하나짜리 비동기 통지이고, 핸들러에서는 플래그만 세워야 하며, 서버는 SIGTERM을 우아한 종료로 받고 SIGPIPE를 무시하고 SIGCHLD로 자식을 회수해야 하고, 컨테이너에서는 PID 1 규칙 때문에 이를 직접 챙겨야 한다. ([본문](../1부-리눅스-OS-구성-요소\03-시그널.md))
- **4장. 메모리** — 프로세스가 보는 주소는 가상이라 `malloc`은 예약일 뿐 쓰는 순간 물리 페이지가 배정되고, 물리 메모리가 바닥나면 OOM killer가 경고 없이 SIGKILL하며, 컨테이너는 cgroup 한도(`memory.max`)에서 같은 일이 그 컨테이너 안에서 일어난다. ([본문](../1부-리눅스-OS-구성-요소\04-메모리.md))
- **5장. 파일시스템과 I/O** — 파일은 fd → open file → inode 세 계층으로 열리고, `write()`는 페이지 캐시까지만 보장하므로 영속성은 `fsync`와 `rename` 같은 원자 연산의 조합으로 직접 만든다. ([본문](../1부-리눅스-OS-구성-요소\05-파일시스템과-IO.md))
- **6장. 네트워크 스택** — 소켓은 fd이고 TCP는 메시지 경계 없는 바이트 스트림이며, 핸드셰이크·accept 큐·TIME_WAIT는 커널이 관리하고, 대량 접속은 이벤트 루프(epoll) 안에서 절대 블로킹하지 않는 구조로 처리한다. ([본문](../1부-리눅스-OS-구성-요소\06-네트워크-스택.md))
- **7장. 스레드와 동시성** — 스레드는 `clone` 플래그로 주소 공간·fd 등을 공유하는 커널 태스크이고, 공유 때문에 원자성과 가시성 문제가 생기며, 락 자체는 싸지만 경합이 비싸고, 스레드 수는 작업 성격과 CPU 쿼터로 정한다. ([본문](../1부-리눅스-OS-구성-요소\07-스레드와-동시성.md))
- **8장. 진단 도구** — 문제가 생기면 첫 60초 명령으로 전체를 보고, 도구가 없으면 `/proc`을 읽고, 증상별 첫 명령(`strace`·`perf`·`gdb`·`ss`)으로 가설을 검증하며, "CPU를 쓰는 곳"과 "CPU를 안 쓰고 기다리는 곳"을 구분해 분석한다. ([본문](../1부-리눅스-OS-구성-요소\08-진단-도구.md))
- **9장. 네임스페이스** — 네임스페이스는 커널의 전역 자원(PID, 네트워크, 마운트, 호스트명, IPC, UID, cgroup 뷰, 시계)을 프로세스 그룹마다 다르게 "보이게" 하는 커널 기능이며, 컨테이너는 보통 프로세스에 이것을 씌운 것이다. ([본문](../2부-컨테이너-커널-기능과-Docker\09-네임스페이스.md))
- **10장. cgroup** — cgroup은 프로세스 그룹의 자원 사용량 상한을 거는 커널 기능으로, 현재 표준은 모든 컨트롤러가 하나의 트리를 공유하는 v2이고, Docker 옵션은 컨트롤러의 제어 파일에 값을 쓰는 것이며, 메모리 한도를 넘으면 cgroup OOM killer가 SIGKILL로 종료시킨다. ([본문](../2부-컨테이너-커널-기능과-Docker\10-cgroup.md))
- **11장. 이미지·레이어·overlayfs** — 이미지는 순서가 있는 읽기 전용 레이어(변경분)의 집합이고, overlayfs가 lowerdir(이미지) + upperdir(컨테이너 쓰기 레이어)를 merged 뷰로 합쳐 보여 주며(쓰기는 copy-on-write), 모든 블롭은 내용의 해시(다이제스트)로 식별되어 디스크에 한 벌만 공유된다. ([본문](../2부-컨테이너-커널-기능과-Docker\11-이미지-레이어-overlayfs.md))
- **12장. OCI 표준과 런타임** — OCI는 컨테이너 실행(Runtime Spec: 번들 = config.json + rootfs, create/start/kill/delete), 이미지(Image Spec: 매니페스트·config·레이어, 인덱스), 배포(Distribution Spec: `/v2/` HTTP API)를 표준화했고, runc는 실행 표준의 참조 구현일 뿐이어서 격리 모델이 다른 crun, gVisor, Kata, youki를 `runtime_type`/`RuntimeClass`로 갈아 끼울 수 있다. ([본문](../2부-컨테이너-커널-기능과-Docker\12-OCI-표준과-런타임.md))
- **13장. Docker 아키텍처** — `docker` CLI는 REST 클라이언트일 뿐이고, 요청은 dockerd → containerd → shim → runc → 커널로 프로세스 경계마다 넘어가며, runc는 `execve`로 사라지고 shim이 컨테이너의 부모로 남기 때문에 상위 데몬이 재시작돼도 컨테이너는 산다. ([본문](../2부-컨테이너-커널-기능과-Docker\13-Docker-아키텍처.md))
- **14장. 볼륨·바인드 마운트·tmpfs** — 이미지 레이어는 읽기 전용이고 컨테이너의 쓰기 레이어(upperdir)는 컨테이너와 함께 사라지므로, 살아남아야 하는 데이터는 named volume이나 bind mount로, 디스크에 남기면 안 되는 임시 데이터는 tmpfs로 컨테이너 밖에 둔다. ([본문](../2부-컨테이너-커널-기능과-Docker\14-볼륨-바인드마운트-tmpfs.md))
- **15장. 빌드 — BuildKit과 Dockerfile의 핵심** — BuildKit은 Dockerfile을 프론트엔드가 LLB(콘텐츠 주소 기반 DAG)로 바꾸고 솔버가 병렬·캐시 판단으로 실행하는 빌드 엔진이므로, 빌드 속도는 "자주 바뀌는 것을 아래에, 안 바뀌는 것을 위에" 두는 순서와 캐시 마운트에서, 안전은 secret 마운트와 멀티스테이지에서 나온다. ([본문](../2부-컨테이너-커널-기능과-Docker\15-빌드-BuildKit-Dockerfile.md))
- **16장. Docker 네트워크** — Docker 네트워크는 Sandbox(네트워크 네임스페이스)·Endpoint(veth 한쪽 끝)·Network(브리지 등) 세 객체로 추상화되고, 컨테이너 간 통신은 브리지의 L2 스위칭, 외부 통신은 라우팅+NAT, 포트 게시는 iptables DNAT, 이름 해석은 127.0.0.11 내장 DNS가 맡는다. ([본문](../2부-컨테이너-커널-기능과-Docker\16-Docker-네트워크.md))
- **17장. 컨테이너를 손으로 만들기** — "컨테이너"라는 커널 객체는 없고, namespace(무엇을 보는가)·cgroup(얼마나 쓰는가)·capability(무엇을 할 수 있는가)·overlayfs(파일을 어떻게 쌓는가)·seccomp(어떤 시스템 콜을 부르는가)를 조합한 프로세스일 뿐이며, 파드의 pause 컨테이너는 공유 네임스페이스를 대신 소유해 앱 컨테이너가 죽어도 IP를 지킨다. ([본문](../2부-컨테이너-커널-기능과-Docker\17-컨테이너를-손으로-만들기.md))
- **18장. 클러스터 아키텍처 총론** — 쿠버네티스는 "원하는 상태(spec)"를 API 서버에 저장해 두면, 좁은 책임을 가진 여러 컨트롤러가 현재 상태와의 차이를 반복해서 줄여 나가는 **선언형 조정(reconcile) 시스템**이며, 모든 컴포넌트는 API 서버를 통해서만 서로 협력한다. ([본문](../3부-쿠버네티스-구성-요소\18-클러스터-아키텍처-총론.md))
- **19장. kube-apiserver** — kube-apiserver는 모든 요청을 "필터 체인(인증→감사→APF→인가) → 버전 변환 → 어드미션(Mutating→검증→Validating) → etcd 저장"의 정해진 순서로 처리하는 stateless 관문이고, 변경은 watch cache를 통해 수천 클라이언트에 fan-out한다. ([본문](../3부-쿠버네티스-구성-요소\19-kube-apiserver.md))
- **20장. etcd** — etcd는 Raft 합의로 과반수의 디스크 fsync를 받아야 쓰기가 커밋되는 강한 일관성(CP) 키-값 저장소이고, 값을 덮어쓰지 않고 리비전을 쌓는 MVCC라서 압축·조각 모음·백업이 운영의 핵심이다. ([본문](../3부-쿠버네티스-구성-요소\20-etcd.md))
- **21장. kube-scheduler** — kube-scheduler는 `nodeName`이 빈 Pod를 watch해 **Filter(가능/불가능) → Score(0&#126;100점)** 로 최적 노드를 골라 Binding을 기록하는 컨트롤러이며, 판단 기준은 실제 사용량이 아니라 `requests`다. ([본문](../3부-쿠버네티스-구성-요소\21-kube-scheduler.md))
- **22장. 컨트롤러 매니저** — 모든 내장 컨트롤러는 "Informer(로컬 캐시) → 워크큐(키만, 중복 제거, 레이트 리밋) → 멱등·레벨 트리거 조정 함수"라는 같은 뼈대를 쓰고, HA에서는 Lease 기반 리더 선출로 하나만 활성이다. ([본문](../3부-쿠버네티스-구성-요소\22-컨트롤러-매니저.md))
- **23장. kubelet과 CRI** — kubelet은 API 서버를 watch하며 스스로 판단해 Pod를 구현하는 노드 에이전트이고, 컨테이너 생성은 CRI로 런타임에 위임하며(CNI 호출도 런타임이 한다), 노드 생사는 Lease 하트비트와 테인트·톨러레이션 타이머로 판정된다. ([본문](../3부-쿠버네티스-구성-요소\23-kubelet과-CRI.md))
- **24장. 오브젝트 모델과 워크로드** — 모든 오브젝트는 TypeMeta·ObjectMeta·Spec·Status의 같은 구조이고, Pod는 NET·IPC·UTS를 공유하는 컨테이너 그룹이며, 컨트롤러(Deployment→ReplicaSet→Pod 등)가 "원하는 개수·버전"을 조정 루프로 유지한다. ([본문](../3부-쿠버네티스-구성-요소\24-오브젝트-모델과-워크로드.md))
- **25장. Pod 생명주기와 리소스** — Pod의 트래픽 수신 여부는 `Ready` 조건이 결정하고(프로브), 종료는 "엔드포인트 제거와 SIGTERM이 병렬"이라 preStop과 SIGTERM 처리가 필요하며, requests는 스케줄러가 limits는 cgroup이 쓰고 초과 시 CPU는 스로틀링·메모리는 OOM Kill이다. ([본문](../3부-쿠버네티스-구성-요소\25-Pod-생명주기와-리소스.md))
- **26장. 쿠버네티스 네트워크 모델과 CNI** — 쿠버네티스는 "모든 Pod가 고유 IP로 NAT 없이 통신한다"는 네 가지 요구사항만 정의하고, 이를 만드는 일은 런타임이 실행 파일로 호출하는 CNI 플러그인(주 플러그인 + IPAM + 메타 플러그인 체인)이 맡으며, 노드 간 전달은 오버레이·네이티브 라우팅·클라우드 IP 중 하나로 구현된다. ([본문](../3부-쿠버네티스-구성-요소\26-쿠버네티스-네트워크-모델과-CNI.md))
- **27장. Service와 kube-proxy** — Service의 ClusterIP는 어느 인터페이스에도 존재하지 않는 가상 좌표이고, EndpointSlice의 Ready Pod 목록을 kube-proxy가 노드 커널의 DNAT 규칙(iptables/IPVS/nftables)으로 번역하며, 패킷 처리는 conntrack을 따라 커널이 하고 kube-proxy는 데이터 경로에 없다. ([본문](../3부-쿠버네티스-구성-요소\27-Service와-kube-proxy.md))
- **28장. CoreDNS와 외부 노출** — Pod의 이름 조회는 `resolv.conf`(nameserver=kube-dns ClusterIP, search 3개, `ndots:5`)를 따라 CoreDNS 플러그인 체인이 답하고, 외부에서 오는 HTTP는 Ingress/Gateway(선언)를 컨트롤러(프로그램)가 프록시 설정으로 바꿔 받으며, Pod 사이의 허용 범위는 NetworkPolicy(스펙)를 CNI가 시행한다. ([본문](../3부-쿠버네티스-구성-요소\28-CoreDNS-Ingress-NetworkPolicy.md))
- **29장. 스토리지** — 컨테이너 파일은 휘발성이므로 오래 살아야 하는 데이터는 PVC로 요청하고, StorageClass의 프로비저너(CSI 드라이버)가 PV를 만들어 1:1로 바인딩하며, 최종적으로 kubelet이 그 볼륨을 노드에 마운트해 컨테이너의 `mountPath`로 보이게 한다. ([본문](../3부-쿠버네티스-구성-요소\29-스토리지.md))
- **30장. 설정·보안** — 설정은 환경변수(시작 시 고정)나 볼륨 파일(원자적으로 갱신)로 주입되고 Secret의 base64는 암호화가 아니며, 접근은 인증 → 인가(RBAC) → 어드미션을 지나고, 실행 후 권한은 `securityContext`가 리눅스의 uid·capability·seccomp·읽기 전용 파일시스템으로 좁힌다. ([본문](../3부-쿠버네티스-구성-요소\30-설정-보안.md))
- **31장. 계층 종합과 장애 진단** — 쿠버네티스의 모든 선언은 조정 루프를 거쳐 결국 리눅스 커널 기능(프로세스, 네임스페이스, cgroup, mount, netfilter)이 되므로, 장애는 "증상 → 가설 → 증거 → 변경 → 재검증"으로 계층을 한 칸씩 내려가며 좁힌다. ([본문](../3부-쿠버네티스-구성-요소\31-계층-종합과-장애-진단.md))
