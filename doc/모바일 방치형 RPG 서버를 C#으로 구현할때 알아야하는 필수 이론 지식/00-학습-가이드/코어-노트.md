## 결정적 지식 3개

13개 부의 수백 개 항목은 대부분 아래 세 원리 중 하나에서 파생됩니다. 세부가 기억나지 않으면 "이건 셋 중 무엇의 결과인가?"부터 물어보세요.

### ① 누가 무엇을, 얼마나 오래 붙잡고 있는가 — 참조와 수명

> 값 타입은 **복사**되고 참조 타입은 **공유**된다. 무엇이 무엇을 참조하는 한 그것은 살아 있고, 수명이 짧은 것을 긴 것이 붙잡으면 문제가 생긴다.

| 이 원리에서 나오는 것 | 부 |
|---|---|
| 대입·매개변수 전달 결과, struct 복사본 수정 함정, `==`의 의미 | 1·2부 |
| 박싱(값 타입이 object 자리에 가면 힙 복사) → 제네릭이 존재하는 이유 | 2·3부 |
| 클로저가 변수 수명을 늘림, 이벤트 구독 해제 누락 누수 | 3·4부 |
| GC는 루트에서 닿는 객체를 살려 둔다 → static 캐시·타이머·이벤트 누수 | 3부 |
| DI 수명: Singleton이 Scoped를 붙잡는 캡티브 의존성 | 8부 |
| DbContext는 요청당 하나(Scoped), 변경 추적은 읽은 시점 스냅샷 기준 | 10부 |
| BackgroundService(싱글톤)는 매번 스코프를 직접 만든다 | 12부 |

**스스로 확인:** "Singleton 서비스에 DbContext를 생성자 주입하면 왜 안 되는가?"를 ①만으로 설명할 수 있나요?

### ② 서버가 유일한 진실이다 — 클라이언트를 믿지 않고, 요청은 서로 모른다

> 시간·확률·재화는 서버가 결정한다. HTTP는 무상태이고 서버는 여러 대일 수 있으므로, 요청 하나하나가 스스로 검증·인증되고 반복되어도 안전해야 한다.

| 이 원리에서 나오는 것 | 부 |
|---|---|
| 큰 숫자는 `long`부터, 오버플로·실수 오차 의식(재화 계산) | 1부 |
| UTC 저장, 경과 시간 상한·음수 방어, 서버 측 `Random.Shared` 뽑기 | 5부 |
| 공유 가변 상태 보호(lock/SemaphoreSlim) → 재화 이중 지급 방지 | 6부 |
| 무상태 HTTP → 요청마다 토큰, DTO로 과다 바인딩(gold, IsAdmin) 차단 | 7부 |
| 동시성 토큰·트랜잭션·멱등성 키+유니크 제약으로 이중 처리 차단 | 10부 |
| 인증=누구인가, 인가=해도 되는가. JWT는 서명됐지만 암호화·취소 불가 | 11부 |
| 서버가 여러 대면 메모리 상태는 공유되지 않는다 → 분산 캐시, 백그라운드 중복 실행 | 12·13부 |

**스스로 확인:** "클라이언트가 보낸 '오프라인 8시간' 값을 그대로 쓰면 안 되는 이유"와 "같은 보상 요청이 두 번 오면?"을 ②로 답할 수 있나요?

### ③ 바뀌는 것은 인터페이스 뒤에 두고, 밖에서 넣어 준다 — DIP와 파이프라인

> 바뀌는 이유별로 나누고(SoC), 구현이 아닌 인터페이스에 의존하며(DIP), 실제 부품은 바깥(DI 컨테이너·미들웨어 파이프라인·설정)에서 조립한다.

| 이 원리에서 나오는 것 | 부 |
|---|---|
| 인터페이스·다형성(virtual/override)으로 if문 없는 종류별 처리 | 2부 |
| 델리게이트: 동작 자체를 값으로 넘김 | 4부 |
| `TimeProvider` 주입 → 시간에 의존하는 로직도 테스트 가능 | 5부 |
| Strategy·Decorator·Chain·Options 패턴, KISS·YAGNI로 과설계 경계 | 9부 |
| 미들웨어 파이프라인: 추가 순서대로 감싸는 양방향 구조 | 8부 |
| `IHttpClientFactory`·재시도·서킷 브레이커를 밖에서 끼워 넣기 | 12부 |
| 의존은 안쪽으로(Core ← Infrastructure), 인터페이스에 가짜 구현을 끼워 단위 테스트 | 13부 |

**스스로 확인:** "가챠 확률 로직을 테스트하려면 무엇을 인터페이스로 빼야 하는가?"를 ③으로 답할 수 있나요?

```
[언어]  1 문법 ─ 2 객체지향 ─ 3 메모리·GC ─ 4 델리게이트·예외 ─ 5 .NET 라이브러리 ─ 6 비동기·동시성
           │ 값/참조(①)    │ 다형성(③)   │ GC 루트(①)    │ 동작을 값으로(③)  │ UTC·Random(②)  │ 공유 상태(②)
           ▼
[서버]  7 웹 API(②) → 8 ASP.NET Core 파이프라인·DI(①③) → 9 설계 원칙·패턴(③: 방금 쓴 DI의 원리)
        → 10 EF Core(①②) → 11 인증·보안(②) → 12 백그라운드·캐시·외부 호출(①②③)
           │
           ▼
[구조]  13 아키텍처·테스트·배포(③)
```

**C++에서 오면 가장 먼저 바꿀 습관 3가지:** 소멸자 대신 `using`(①), 소켓 세션 대신 요청마다 토큰(②), 매니저 싱글턴 직접 생성 대신 DI 컨테이너 등록(③).
**한 요청의 일생으로 서버 덩어리를 다시 묶으면:** HTTP 요청(7) → 미들웨어·인증(8·11) → DI로 받은 서비스(8) → DbContext 저장(10) → JSON 응답(7), 요청 밖에서는 백그라운드·캐시(12).

## 부별 코어

### 제1부. C# 문법 기초

> C# 코드는 문장·메서드·클래스·네임스페이스로 묶이고, 값 타입은 복사·참조 타입은 공유(그리고 null 가능)되며, 방치형 서버의 큰 숫자는 long부터 시작해 조용한 오버플로와 실수 오차를 의식하고, null 연산자와 제어문으로 안전한 전투·보상 루프를 만든다.

- 코드의 골격 — 문장 → 메서드 → 클래스 → 네임스페이스로 묶이고 dotnet이 어셈블리로 컴파일하며, 인스턴스 멤버는 객체마다·static 멤버는 타입 전체에 하나다.
- 값 타입 vs 참조 타입 — struct·숫자·bool·char·enum은 대입·전달 시 복사, class·배열·string·델리게이트·인터페이스는 참조만 복사되어 공유되며, 스택/힙·기본값·값/ref/out/in 전달이 여기서 나온다.
- 숫자는 정해진 비트다 — int/long이 1급 시민이고 재화는 long부터, 정수 오버플로는 기본적으로 조용히 감아 돌며 checked로만 잡히고, 실수→정수는 버림, double은 근사·decimal은 정확하지만 약 10배 느리다.
- null 방어 — null 멤버 접근은 NullReferenceException이며, bool 전용 조건·&& 단락 평가와 ?. / ?? / ??=로 막는다.
- 문자열·배열·제어문 — string은 불변·$"" 보간, 배열은 고정 길이·범위 검사·^1/.., if / switch(식) / for / foreach / while / break / continue / return으로 전투·보상 루프를 만든다.

**C++·TCP 서버에서 출발하기**

- C++ struct/class → C# struct/class: C++은 접근 지정자 차이뿐, C#은 값 타입(복사) vs 참조 타입(공유)으로 의미론이 다르다.
- C++ T* (포인터 복사) → C# class 변수(참조): null 가능·대입 시 공유는 같지만 -&gt;·포인터 산술·delete가 없고 GC가 회수한다(소멸 시점 비결정).
- C++ 부호 있는 정수 오버플로(UB) → C# 정수 오버플로: C#은 기본적으로 정의된 wraparound라 예외도 경고도 없이 음수 골드가 생긴다. checked로만 예외.
- C++ T& / const T& → C# ref / in (+ out): 호출부에도 ref/out을 써야 하고 out은 반드시 채워야 한다.

### 제2부. 객체지향 프로그래밍

> 클래스는 필드·프로퍼티·메서드로 "데이터 + 행동"을 묶고 접근 제한자로 내부를 감추며, 구현을 공유하면 상속(virtual/override)·독립 능력이면 인터페이스로 다형성을 만들고, 작고 불변인 단일 값만 struct로, 타입이 달라도 같은 코드는 박싱 없는 제네릭으로 재사용한다.

- 캡슐화된 클래스 — 필드·프로퍼티·생성자로 데이터와 행동을 묶고, 필드는 private, 필요한 것만 public 프로퍼티/메서드로 연다(private set, init). 골드 같은 값은 정해진 메서드로만 바뀌게 한다.
- 다형성(상속 + 인터페이스) — 부모 타입 변수가 자식 객체를 가리키고, virtual/override면 실제 객체의 버전이 실행된다. 클래스 상속은 하나, 인터페이스 구현은 여러 개.
- 값 타입과 박싱 비용 — 값 타입을 object/인터페이스에 담으면 박싱(힙 복사), 언박싱은 원래 타입과 정확히 일치해야 한다. 기본은 class, struct는 단일 값·16바이트 미만·불변·박싱 드묾일 때만. enum은 정의되지 않은 값도 담을 수 있다.
- 제네릭 — T 자리표시 타입으로 박싱·캐스팅 없이 타입 안전하게 재사용하며, where 제약이 허락한 기능만 쓸 수 있다.

**C++·TCP 서버에서 출발하기**

- C++ virtual + override(선택) → C# virtual/override: 동적 디스패치는 같지만 C#은 override 키워드가 필수이고, 빼먹으면 숨기기(new)가 되어 부모 타입 변수로 부르면 부모 버전이 실행된다.
- C++ 다중 상속 → C# 단일 클래스 상속 + 인터페이스 다중 구현: 순수 가상 클래스 ≈ 인터페이스지만 클래스 부모는 하나뿐이고, C# 8부터 인터페이스에 기본 구현이 생길 수 있다.
- C++ struct/class(기본 접근 지정자 차이) → C# struct(값 타입)/class(참조 타입): 타입 정의 시점에 복사 vs 공유가 결정되고 struct는 상속·null 불가.
- C++ 템플릿 → C# 제네릭: 템플릿은 컴파일 타임 인스턴스화 + 덕 타이핑, 제네릭은 런타임 구체화 + where 제약이 허락한 멤버만 호출 가능.

### 제3부. 메모리와 성능 기초

> 힙에 만든 객체는 GC가 루트에서 닿지 않는 것을 세대별로 나중에 한꺼번에 치우며 그동안 스레드가 멈출 수 있으므로, 핫 경로에서는 박싱·문자열 +=·매번 new를 줄여 쓰레기를 덜 만들고, GC가 못 치우는 자원과 참조(Dispose·이벤트·타이머)는 직접 정리하되, 모든 최적화는 측정 후에 한다.

- 메모리 배치: 스택·힙과 숨은 할당(박싱) — 스택은 메서드 종료와 함께 즉시 정리, new 객체는 힙, 값 타입은 선언된 그 자리에 살며 object/인터페이스에 담으면 박싱으로 힙 할당이 생긴다.
- GC: 루트·세대·멈춤 — 루트에서 닿지 않는 객체를 Gen0→Gen1→Gen2로 주기 회수하며, 비용은 살아 있는 객체 수에 비례하고 수집 중 스레드가 멈출 수 있다. "Gen0에서 죽거나 Gen2에 오래 머물게".
- 할당 줄이기: 문자열·풀·struct·컬렉션 — StringBuilder, 재사용/ArrayPool, 작은 불변 struct, 제네릭 컬렉션, 감싸지 않은 foreach로 쓰레기를 줄이되 핫 경로에서만, 측정 후에.
- GC가 못 하는 정리: Dispose·이벤트·타이머 — GC는 메모리만 회수하므로 자원은 using/Dispose로, 이벤트 구독은 -=로 직접 정리한다. C#의 누수는 잊혀진 참조다.

**C++·TCP 서버에서 출발하기**

- new/delete·스마트 포인터 → new + GC: delete가 없고 회수 시점이 비결정적이며, 루트 추적이라 순환 참조도 회수되지만 수집 중 스레드가 멈출 수 있다(stop-the-world).
- C++ 소멸자 ~T() → C# finalizer ~T(): 문법만 같고, GC 이후 finalizer 스레드에서 비결정적으로 호출되는 백업 수단이며 객체 회수를 한 수집 늦춘다.
- RAII → IDisposable + using: 블록 끝(예외 포함)에서 정리되는 점은 같지만 using을 명시해야만 동작하고 멤버 자동 연쇄도 없다.
- 전역 리스너 목록에 넣고 안 뺀 shared_ptr → 이벤트 += 후 -= 누락: delete 누락형 누수는 없고 잊혀진 참조형 누수만 남는다.

### 제4부. 함수형 도구·예외·현대 C#

> 델리게이트·Func/Action·람다로 동작을 값처럼 넘기고 이벤트로 변화를 안전하게 알리며, try/catch/finally·using·TryXXX로 실패해도 서버가 계속 동작하게 하고, 이터레이터·nullable·확장 메서드·튜플·record·패턴 매칭으로 짧고 안전하게 쓴다.

- 동작을 값으로 — 델리게이트는 "이 모양의 메서드"를 담는 객체이며 Func(반환)/Action(void)으로 대부분 대체되고, +=로 여러 개를 쌓을 수 있다(멀티캐스트). event는 바깥에서 +=/-=만 허용하는 제한된 델리게이트다.
- 람다와 클로저 — 람다가 캡처한 바깥 변수는 호출 시점의 값으로 읽히고 수명이 늘어난다(for 반복 변수 캡처 함정은 복사로 해결, 캡처 할당은 static 람다로 방지).
- 실패 처리 — 구체적인 catch부터, finally는 return해도 실행, using은 try/finally { Dispose(); }, 다시 던질 땐 throw;. 흔한 실패는 bool + out의 TryXXX.
- 필요할 때 만드는 시퀀스 — foreach는 MoveNext/Current 커서의 소비자, yield return 이터레이터는 생산자이며 순회할 때 실행된다(지연 실행). 컬렉션 식 [ ]로 짧게 채운다.
- 현대 C# 데이터 문법 — int?(Nullable&lt;T&gt;)·string?(컴파일러 경고)으로 "없음"을 드러내고, 확장 메서드·튜플·record(구조적 동등성 + with)·패턴 매칭·특성으로 짧고 안전하게 쓴다.

**C++·TCP 서버에서 출발하기**

- C++ std::function → C# 델리게이트(Func/Action): 시그니처가 맞는 호출 대상을 담는 점은 같지만, C# 델리게이트는 멀티캐스트(+=로 여러 대상)가 기본이며 C++에는 대응물이 없다. 인스턴스 메서드를 담으면 GC가 그 객체를 살려 둔다.
- C++ 람다 [&] 참조 캡처 → C# 클로저: 변수 자체를 캡처해 호출 시점 값을 읽는 점은 비슷하지만, 캡처된 변수의 수명이 델리게이트만큼 늘어나 댕글링이 없고 값 캡처를 고를 수 없다.
- C++ RAII 소멸자 → C# using/IDisposable: 스코프 끝 정리는 같지만 using을 명시해야만 동작하고, finalizer는 호출 시점이 비결정적이라 소멸자를 대신하지 못한다.
- C++ 예외(noexcept) → C# 예외: 스택을 거슬러 처리할 곳을 찾는 점은 같지만 noexcept가 없고 finally·when 필터가 있으며, throw ex;는 스택 정보를 잃는다.

### 제5부. .NET 기본 라이브러리

> 서버는 시간(UTC 저장, TimeProvider 주입, 게임 시간대로 "오늘" 판정)·숫자와 난수(TryParse + 범위 검사, BigInteger, 스레드 안전한 Random.Shared)·문자열과 동등성(불변, Ordinal 비교, 값 vs 참조)을 "서버가 유일한 기준"이라는 원칙으로 다루고, 컬렉션은 "어떻게 찾을까"로 고르며 LINQ는 순회할 때 실행된다는 점을 의식하고, 프로세스 밖으로 나가는 데이터는 JSON으로 주고받고 자원은 using으로 닫는다.

- 시간 — 서버 시계가 유일한 기준: 저장·비교는 UTC(DateTime은 Kind 무시, DateTimeOffset은 같은 순간이면 같음), "지금"은 TimeProvider 주입, 일일 초기화는 게임 시간대로 바꿔 DateOnly로 판정.
- 숫자와 난수 — 입력은 검증하고 확률은 서버가 굴린다: TryParse + InvariantCulture + 범위 검사, 캐스트는 잘라내고 Convert는 은행가 반올림, long 초과는 BigInteger, 난수는 Random.Shared·보안용은 RandomNumberGenerator, 뽑기는 정수 가중치.
- 문자열과 동등성 — 불변과 "같다"의 기준: string은 불변(결과를 받고 반복 결합은 StringBuilder), == 는 Ordinal + 대소문자 구분, 값 타입은 내용·클래스는 참조로 같고 == 는 컴파일 시점 결정, enum은 범위 미검증, Guid는 겹치지 않는 ID.
- 컬렉션과 LINQ — 찾는 방식으로 고르고 순회할 때 계산된다: 번호 List, 키 Dictionary(O(1), TryGetValue), 포함 검사 HashSet, 순서 규칙 Queue/Stack. Where/Select/OrderBy는 지연 실행, ToList·Count·First는 즉시 실행.
- 경계 밖의 데이터 — JSON과 파일, 그리고 닫기: System.Text.Json(Reader/Writer, JsonDocument는 Dispose 필수, JsonNode는 수정 가능), 큰 수는 문자열, 스트림은 using으로 닫고(Flush 자동) 게임 데이터는 DB에.

**C++·TCP 서버에서 출발하기**

- std::chrono system_clock/duration → DateTime/TimeSpan/TimeProvider: chrono는 시계 혼용이 컴파일 에러지만 DateTime은 Local/Utc를 섞어도 조용히 틀린다. 시계 교체는 템플릿이 아니라 TimeProvider 주입.
- std::mt19937(thread_local) / discrete_distribution / random_device → Random.Shared / 직접 짜는 가중치 뽑기 / RandomNumberGenerator: Random.Shared 하나로 스레드 안전, 가중치 뽑기는 표준 도구가 없다.
- STL vector/unordered_map/unordered_set/queue/stack → List/Dictionary/HashSet/Queue/Stack: 없는 키 읽기는 삽입이 아니라 예외, 빈 Dequeue/Pop은 UB가 아니라 예외, 클래스 요소는 참조.
- C++20 ranges view → LINQ 지연 실행: 원본을 참조로 잡아 추가분이 반영되고 순회마다 재계산, 열거자 할당으로 GC 부담 가능, 고정은 ToList().

### 제6부. 비동기와 시간 흐름

> 비동기(async/await)는 기다리는 동안 스레드를 놀리지 않고 풀어 주는 방법이라 서버 확장성의 핵심이며, Task가 결과·예외·취소를 운반하므로 끝까지 await하고(.Result·async void 회피), 여러 요청이 공유하는 가변 상태는 최소화하거나 lock/SemaphoreSlim으로 보호하고, 주기 작업은 PeriodicTimer나 while + await Task.Delay로 만든다.

- 스레드를 놀리지 않는다: 스레드풀과 async/await — 스레드는 비싸므로(약 1MB, 시작 수백 μs) 스레드풀(Task.Run)을 쓰고, await는 미완료 작업에서 스레드를 돌려준 뒤 완료 시 이어 달린다. "async는 끝까지".
- Task가 운반한다: 예외·취소·진행 — 예외는 Task에 담겨 await에서 다시 던져지고, CancellationToken으로 협력적 취소, IProgress&lt;T&gt;로 진행 보고. .Result/.Wait()는 교착 위험, async void는 좋은 해법이 없다.
- 공유 상태를 지킨다: lock과 SemaphoreSlim — 필드·static·캡처 변수는 공유되어 x++도 위험하다. lock(await 불가) 또는 SemaphoreSlim(1).WaitAsync로 보호하되 최선은 공유 상태 최소화, lock은 한 프로세스 안에서만 유효.
- 시간 흐름: 타이머와 주기 작업 — Sleep 스레드 대신 PeriodicTimer/while + await Task.Delay. 다중 스레드 타이머 콜백은 스레드 안전해야 하고 잊힌 타이머는 누수 원인.

**C++·TCP 서버에서 출발하기**

- IOCP 완료 통지 + 워커 스레드 → async/await: 완료 콜백·상태 저장을 직접 짜지 않고 컴파일러가 상태 기계(C++20 코루틴과 유사)로 만들어 지역 변수까지 보존한다.
- std::future → Task: 결과·예외를 운반하는 점은 같지만 Task는 대개 이미 실행 중(hot)이며 .get() 같은 .Result 블로킹은 서버에서 금기다.
- std::mutex + lock_guard → lock: C# lock은 Monitor 기반이라 재진입 가능(std::mutex는 불가)하고 안에서 await할 수 없다.
- 세마포어 → SemaphoreSlim(1): WaitAsync로 await 가능(스레드를 막지 않음)하지만 재진입은 안 되고 finally Release를 직접 짝 맞춘다.

### 제7부. 웹 API 기초

> 웹 API는 무상태 HTTP 위에서 "리소스(명사) URL + 메서드(동작) → 상태 코드 + JSON"으로 대화하며, ASP.NET Core는 Program.cs에서 만든 앱이 요청을 라우팅 → 모델 바인딩 → 검증을 거쳐 핸들러(Minimal API 또는 컨트롤러)에 넘기고, DTO로 입출력을 통제해 내부 모델을 숨긴 채 System.Text.Json으로 응답하며, 그 약속을 API 계약(OpenAPI/Swagger)으로 고정한다.

- 무상태 요청/응답 — HTTP의 대화 규칙: 요청마다 누구인지(토큰)를 싣고, 상태 코드로 결과를 알리며, 서버는 먼저 말을 걸 수 없어 푸시가 필요하면 폴링·SignalR을 쓴다.
- 리소스 중심 설계 — URL은 명사, 동작은 메서드: 복수 명사·중첩·쿼리·하위 리소스, GET 안전 / PUT·DELETE 멱등 / POST·PATCH 둘 다 아님. REST는 스타일이지 규칙이 아니다.
- 앱 골격과 핸들러 — Program.cs, Minimal API, 컨트롤러: 빌더 → 서비스 등록 → Build → 미들웨어 → 엔드포인트 → Run, 핸들러는 MapGet 또는 [ApiController], 팀이 하나로 통일, Swagger로 시험.
- 요청 입구 3단계 — 라우팅 → 모델 바인딩 → 검증: 제약 불일치는 404(검증용 아님), 바인딩 실패 400·JSON 아님 415, DataAnnotations 검증(컨트롤러 자동 400).
- 입출력 통제 — DTO·API 계약·JSON 설정: DTO가 입력 화이트리스트·출력 필터, 계약(URI·메서드·입력·출력)과 버전 전략, JSON 옵션은 Program.cs에서 전역으로.

**C++·TCP 서버에서 출발하기**

- TCP 세션 객체(연결 = 유저 상태) → HTTP 무상태 요청(HttpContext는 요청 단위): 연결이 상태를 들지 않고 다음 요청은 다른 인스턴스로 갈 수 있어 매 요청에 토큰을 싣는다.
- 패킷 opcode → 핸들러 테이블 → 라우팅(메서드 + URL 템플릿): 키가 문자열 템플릿이고 경로에 파라미터가 박히며, 매칭 실패는 프레임워크가 404/405로 자동 응답한다.
- 바이너리 패킷 구조체 역직렬화 → 모델 바인딩 + JSON: 필드 이름으로 매칭하고 DTO에 없는 필드는 무시되므로 DTO가 곧 화이트리스트다.
- 서버의 세션 Send() 푸시 / TCP의 한 번만 도착 → 폴링·SignalR / 멱등성: HTTP는 서버가 먼저 말할 수 없고, 클라이언트 재시도로 같은 요청이 두 번 올 수 있다.

### 제8부. ASP.NET Core 핵심 동작

> ASP.NET Core 서버는 추가한 순서대로 양방향으로 실행되는 미들웨어 파이프라인 위에서, DI 컨테이너가 수명(Singleton/Scoped/Transient)에 맞춰 서비스를 넣어 주고, 여러 프로바이더에서 합친 설정을 검증된 옵션 클래스로 받으며, ILogger 로그·Problem Details 오류 응답·헬스 체크로 "운영 가능한" 틀을 갖춘다.

- 파이프라인 — 추가 순서대로 감싸는 양방향 체인: 미들웨어는 HttpContext를 받아 next 전후로 실행되며 Use* 순서 = 실행 순서. next를 안 부르면 단락, 예외 처리는 앞쪽에, MapGet은 엔드포인트.
- DI 수명 — 짧은 수명을 긴 수명이 붙잡지 않는다: 등록 + 생성자 주입, Transient·Scoped(요청당, DB 컨텍스트)·Singleton(스레드 안전). 캡티브 의존성 금지(검사는 개발 환경에서만), 루트에서 Scoped는 CreateAsyncScope로.
- 설정 — 나중 프로바이더가 이기고, 잘못된 값은 시작할 때 실패: 명령줄 &gt; 환경 변수 &gt; User Secrets &gt; 환경별 json &gt; appsettings.json, 계층 키 __, 비밀은 저장소 밖, 옵션 패턴 + ValidateDataAnnotations + ValidateOnStart.
- 운영 3종 — 로그는 템플릿으로, 오류는 Problem Details로, 상태는 live/ready로: ILogger&lt;T&gt; + 메시지 템플릿(민감 정보 금지), 운영은 UseExceptionHandler + Problem Details(스택 트레이스 금지), 헬스 체크는 liveness/readiness 분리.

**C++·TCP 서버에서 출발하기**

- 패킷 처리 필터 체인 → 미들웨어 파이프라인: 양방향이라 next 뒤에 응답 쪽 코드가 한 번 더 돌고, 예외가 앞쪽으로 거슬러 오르므로 예외 처리는 맨 앞.
- main()에서 매니저 싱글턴들을 조립하던 코드 → DI 컨테이너: 등록만 하면 생성자를 보고 자동 조립하며, 요청 단위 Scoped 수명은 C++ 서버에 거의 대응 개념이 없다(긴 수명이 붙잡으면 캡티브 의존성).
- 설정 파일 로더 → 설정 프로바이더 + 옵션 패턴: 파일 하나가 아니라 여러 출처가 겹쳐 나중 것이 이기고, 시작 시 검증·재시작 없는 변경 반영(IOptionsMonitor)이 붙는다.
- 패킷 처리 최상위 try/catch → UseExceptionHandler: 세션을 끊지 않고 500 Problem Details를 응답하며, 예상 가능한 실패는 예외 대신 4xx.

### 제9부. 설계 원칙과 패턴

> 좋은 설계는 바뀌는 이유별로 관심사를 나누고(SoC·SRP) 인터페이스에 의존해 밖에서 부품을 넣어 주는 것(DIP·DI)이며, 여러 패턴과 Options·Operation Result·이벤트는 모두 기존 코드를 고치지 않고 교체·확장하는(OCP) 도구이되 KISS·YAGNI로 과설계를 경계한다. 앞에서 쓴 DI 컨테이너·미들웨어·옵션 패턴은 이 원리들의 프레임워크 구현이다.

- 바뀌는 이유로 나누고, 필요한 만큼만 — 원칙: 코드 냄새(God class, 긴 메서드, Control Freak)를 SoC로 나누되 DRY는 "같은 이유로 바뀌는가"로 판단하고 KISS·YAGNI로 과설계를 막는다. SOLID는 지침이다.
- 인터페이스에 의존하고 밖에서 넣는다 — DI·Options의 뿌리: Strategy가 DI의 뼈대, Abstract Factory는 객체 그래프 조립 문제, Singleton 패턴 대신 DI singleton 수명. 생성자 주입 + Composition Root(= Program.cs 등록부), 수명 고려 순서 singleton → scoped → transient, 설정도 작은 객체로 밖에서 넣는다.
- 고치지 않고 감싸고, 잇고, 뼈대를 물려준다 — 구조·행동 패턴: Decorator(덧붙이기)·Composite(트리)·Adapter(변환)·Facade(단순화)·Template Method(뼈대)·Chain(분할). 미들웨어는 Chain의 파이프라인 변형.
- 실패와 변화를 값과 신호로 — Operation Result와 이벤트: 예상되는 실패는 Operation Result로(API 계층에서 4xx로 매핑), 상태 변화 알림은 이벤트(broadcaster/subscriber)로 표현한다.

**C++·TCP 서버에서 출발하기**

- 매니저 싱글턴 static T& Instance() → DI singleton 수명: 하나라는 점은 같지만 전역 Instance 호출 대신 생성자로 받아 테스트에서 교체할 수 있다.
- main()에서 매니저를 조립하던 코드 → Composition Root(Pure DI) / Program.cs 등록: 컨테이너가 생성을 대신하고 요청 단위 Scoped 수명이 더해진다.
- 패킷 처리 필터 체인 → Chain of Responsibility의 파이프라인 변형(미들웨어): 고전 Chain은 하나가 처리하면 끝, 미들웨어는 모두 일하고 넘기며 양방향이다.
- std::function 콜백 리스트 → C# event: 해제를 잊으면 댕글링이 아니라 구독자가 수거되지 않는 메모리 누수가 위험이다.

### 제10부. 데이터 접근 (EF Core)

> EF Core는 C# 클래스·관계를 테이블로 매핑하고(모델), IQueryable로 쌓은 쿼리를 실행 시점에 SQL로 내보내며(조회), DbContext가 엔티티 상태를 추적하다가 SaveChanges 한 번(= 한 트랜잭션, Unit of Work)으로 INSERT/UPDATE/DELETE를 만들어 내는 창구이고(쓰기), 웹에서는 요청당 하나(Scoped·async)로 쓰고 스키마는 마이그레이션으로 코드와 맞추며(수명·운영), 재화 이중 처리는 동시성 토큰(동시 수정)·트랜잭션(부분 반영)·멱등성 키+유니크 제약(반복 요청)으로 각각 막는다(방어).

- 모델 — 테이블은 클래스, 창구는 DbContext: 테이블=클래스·열=속성·행=객체, 규칙 → 어노테이션 → Fluent API(충돌 시 Fluent API 승), 관계는 탐색 속성+외래 키(1:1은 종속 쪽 명시, N:M은 연결 테이블 자동), 삭제는 Cascade/ClientSetNull/Restrict.
- 조회 — IQueryable은 실행 메서드에서 SQL이 된다: DbSet → LINQ → ToListAsync/First/Count/foreach. 필터·정렬·페이징은 실행 전에, 관련 데이터는 기본으로 안 불러오며(Eager/Explicit/Select/Lazy), 읽기 전용은 AsNoTracking, 대량 변경은 ExecuteUpdate.
- 쓰기 — 변경 추적과 SaveChanges 한 번(Unit of Work): 상태(Added/Unchanged/Modified/Deleted/Detached)를 보고 SQL 생성, SaveChanges 한 번 = 전부 성공 아니면 전부 취소이므로 로직은 저장을 모르게 두고 끝에서 한 번, 여러 번 저장을 묶을 때만 명시적 트랜잭션. 재화·레벨은 ID만 받아 서버가 다시 조회해 계산.
- 수명과 운영 — 요청당 DbContext 하나, 스키마는 마이그레이션: AddDbContext는 Scoped, DbContext는 스레드 비안전, 백그라운드는 IServiceScopeFactory, 웹에서는 항상 async. migrations add(파일만) → 검토 → database update.
- 방어 — 동시 수정은 동시성 토큰, 반복 요청은 멱등성 키 + 유니크 제약: 0행 갱신 → DbUpdateConcurrencyException → 409. 시간 차를 두고 다시 온 같은 요청은 키 기록+지급을 한 SaveChanges로, 최후 방어선은 (PlayerId, RequestId) 유니크 인덱스. 서로 대체 불가.

**C++·TCP 서버에서 출발하기**

- 저장 프로시저 호출·직접 쓴 SQL → EF Core 매핑 + LINQ: SQL이 생성되므로 번역 안 되는 코드·AsEnumerable 전체 로드를 로그로 확인해야 한다.
- 유저 객체 메모리 캐시 + dirty 플래그 + 주기적 flush → 변경 추적 + SaveChanges 한 번: 스냅샷 비교로 자동 추적, DbContext는 요청 하나 동안만 살고 저장은 타이머가 아니라 요청 끝(응답 전).
- DB 전용 스레드가 쥔 커넥션 → 요청당 DbContext(Scoped) + async: 전용 스레드 없이 요청 스레드가 await로 호출하고, 하나를 여러 Task가 동시에 쓰면 예외.
- 세션 단일 소유 / 패킷 시퀀스 번호 → 낙관적 동시성 토큰 / 멱등성 키 + 유니크 제약: HTTP에는 소유자가 없어 동시·반복 요청이 기본이고, 처리 기록은 메모리가 아니라 DB에 지급과 같은 트랜잭션으로 남긴다.

### 제11부. 인증과 보안 기초

> 연결에 계정을 귀속시키는 TCP 세션과 달리, HTTP API는 요청마다 서명된 JWT로 "누구인가"(ClaimsPrincipal)를 다시 만들고(인증, 401), 인가 미들웨어가 역할·클레임 정책과 리소스 소유 검사로 "해도 되는가"를 판단하며(인가, 403), 그 바깥은 HTTPS·매개변수화·속도 제한으로 지킨다. 단, 이 모두는 "누가"를 보증할 뿐 요청 내용의 정직성은 보증하지 않는다.

- 인증 → 인가 파이프라인 — 인증(누구인가, 실패 401)이 먼저, 인가(해도 되는가, 실패 403)가 다음. 라우팅 → UseAuthentication → UseAuthorization → 엔드포인트, [AllowAnonymous]가 [Authorize]보다 우선.
- JWT — 요청마다 들고 오는 서명된 신분증 — 헤더.페이로드.서명. 서명으로 위조는 막지만 암호화되지 않는다. 서버 세션 없는 자체 완결형이라 어느 서버든 오프라인 검증하지만 발급 후 취소할 수 없어 수명을 짧게 하고 리프레시 토큰으로 갱신한다.
- 인가는 점점 세밀해진다 — 역할(쉼표 OR, 겹치기 AND) → 클레임 정책 → 요구사항+핸들러(요구사항 AND, 핸들러 OR) → 리소스 기반(IAuthorizationService, IDOR 방어). 로그인 확인만으로는 남의 데이터를 막지 못한다.
- 경계 방어 — 전송·입력·데이터·빈도 — HTTPS만 열기(HSTS는 브라우저 전용), 입력을 SQL과 분리(LINQ/FromSql 보간), CORS는 브라우저 JS 규칙·비밀번호는 해시로만, 남용은 속도 제한(429, 인증 전 IP / 인증 후 플레이어 ID).

**C++·TCP 서버에서 출발하기**

- TCP 로그인 패킷 1회 인증 + socket→Session{accountId} → JWT Bearer 인증(요청마다 HttpContext.User 생성): 신분이 서버 메모리가 아니라 토큰에 있어 요청마다 검증하고, 키만 공유하면 어느 인스턴스든 처리한다.
- 운영자 킥/밴(소켓 close, 즉시 효과) → 자체 완결형 토큰 취소 불가: 발급한 토큰은 exp까지 유효해 짧은 수명·리프레시 토큰·서버 쪽 차단 상태가 필요하다.
- 패킷 핸들러의 ownerId == session.accountId 검사 → 리소스 기반 인가(IDOR 방어): 대상 ID가 URL에 드러나 조작이 쉽고, 검사를 정책·핸들러로 선언적으로 분리한다.
- 세션별 패킷 빈도 제한 → AddRateLimiter(429): 카운터가 프로세스 메모리라 서버 여러 대에서 합산되지 않고, 로그인 전 요청은 IP로 센다.

### 제12부. 백그라운드 서비스·캐시·외부 호출

> 요청 밖의 주기 작업은 싱글톤 BackgroundService에서 매번 스코프를 직접 만들어 돌리고, 자주 읽히는 공용 데이터는 성격에 맞는 캐시에 두며 목록은 페이지로 잘라 읽기 부하를 줄이고, 외부 호출은 IHttpClientFactory와 타임아웃·재시도·서킷 브레이커로 감싸며, 이 모든 작업은 취소 토큰을 끝까지 전달해 협력적으로 멈춘다.

- 요청 밖의 상주 일꾼 — BackgroundService와 직접 만드는 스코프: ExecuteAsync 루프, AddHostedService(싱글톤)라 DbContext는 반복마다 CreateScope()로 빌려 쓰고 using으로 해제, 서버가 여러 대면 중복 실행.
- 읽기 부하 줄이기 — 캐시는 위치·공유·무효화로 고르고 목록은 페이지로 자른다: 인메모리/분산/응답/출력 캐시, 절대+슬라이딩 만료, GetOrCreateAsync로 null도 캐시, 필터 → 정렬 → Skip/Take.
- 외부 호출은 팩토리와 회복 탄력성으로 감싼다: 매번 생성은 소켓 고갈, 싱글톤은 DNS 미감지 → IHttpClientFactory, 타임아웃·재시도(지수 백오프+지터)·서킷 브레이커, 재시도는 멱등한 요청에만.
- 취소는 협력적이다 — 토큰을 끝까지 넘겨 스스로 멈춘다: CancellationTokenSource가 보내고 CancellationToken을 받은 코드가 전달·폴링해 멈추며 OperationCanceledException으로 표현, 종료는 stoppingToken.

**C++·TCP 서버에서 출발하기**

- 게임 서버 타이머 스레드·틱 루프 → BackgroundService + Task.Delay: 스레드를 점유하지 않는 async 루프이고 호스트가 수명을 관리하며, 서버를 여러 대 띄우면 인스턴스마다 중복 실행된다.
- 틱 루프가 들고 있는 DB 커넥션 → 반복마다 CreateScope()로 꺼내는 DbContext: 싱글톤은 스코프 객체를 생성자로 받을 수 없고 DbContext는 스레드 비안전·추적 누적이라 오래 들고 있으면 안 된다.
- 전역 메모리에 올린 랭킹·기획 데이터 → IMemoryCache / IDistributedCache: 웹 서버는 인스턴스가 여러 대라 프로세스 메모리 캐시는 서로 다른 값을 들 수 있다.
- 종료 플래그 / std::stop_token → CancellationToken: 둘 다 협력적이지만 .NET은 취소가 예외로 전파되고 토큰을 비동기 호출 체인 끝까지 넘겨야 대기 중에도 깨어난다.

### 제13부. 아키텍처·테스트·배포 기초

> 비즈니스 로직을 중심(Core)에 두고 의존성이 바깥에서 안쪽으로만 향하게 하면, 로직을 가짜 구현으로 DB 없이 단위 테스트하고, WebApplicationFactory로 진짜 앱을 메모리에 띄워 요청→응답을 통합 테스트할 수 있으며, CI가 이 테스트들을 매 PR마다 돌려 통과한 코드만 불변 Docker 이미지로 만들어 어디서나 같은 방식으로 배포한다.

- 의존성은 안쪽으로 — 모놀리식에서 Clean Architecture까지: 모놀리식은 하나의 단위로 배포되는 앱이고 계층(논리)과 티어(물리)는 다르다. 전통 계층(UI→BLL→DAL)은 로직이 DB에 묶이므로 Core(엔티티·인터페이스·도메인 서비스)는 아무것도 모르게 하고 Infrastructure가 인터페이스를 구현하며 Program.cs(조립 지점)에서 DI로 연결한다.
- 단위 테스트 — 인터페이스 뒤에 가짜를 끼워 로직만 빠르게: 단위·통합·E2E를 투자 대비 효과로 균형 잡고, xUnit [Fact](AAA)·[Theory](동치 분할·경계값)로 규칙을 못 박으며, 의존성은 인터페이스 뒤의 가짜 구현으로 격리한다.
- 통합 테스트 — 진짜 앱을 메모리에서 띄우고, 통제 못 하는 것만 바꾼다: WebApplicationFactory&lt;Program&gt;이 실제 설정·DI·미들웨어로 앱을 TestServer 위에 띄워 라우팅·모델 바인딩·유효성 검사까지 검증하고, 외부 API·시간은 ConfigureTestServices로, DB는 테스트 전용(SQLite 인메모리 등)으로 바꿔 끼운다.
- 불변 이미지와 자동 파이프라인 — 빌드·테스트·배포를 사람 손에서 뗀다: CI는 커밋마다 restore→build→test, CD는 Docker 이미지를 환경에 배포한다. 이미지는 불변 패키지, 컨테이너는 실행 인스턴스이며 영속 데이터는 컨테이너 밖에 둔다.

**C++·TCP 서버에서 출발하기**

- 순수 가상 클래스 + main에서 구현 주입 → Core 인터페이스 + Program.cs DI: 조립을 DI 컨테이너가 런타임에 하고, 의존 방향은 .csproj 프로젝트 참조로 강제된다.
- 더미 클라이언트(봇)를 붙여 손으로 확인 → xUnit + WebApplicationFactory 통합 테스트: 포트·별도 프로세스 없이 TestServer로 프로세스 안에서 요청하고, 판정은 Assert가 한다.
- 빌드 머신 수동 빌드 → 바이너리 복사 → 점검 후 재시작 → CI/CD + Docker 이미지: 매 PR마다 자동 빌드·테스트로 병합 전에 막히고, 산출물은 런타임·설정까지 묶은 불변 이미지다.
- 서버 로컬 디스크의 세이브 파일 → 컨테이너 쓰기 계층: 컨테이너가 사라지면 함께 사라지므로 영속 데이터는 볼륨·DB에 둔다.
