# 6장. 이미지와 스토리지 — 레이어, snapshotter, overlay2, 볼륨

5장에서는 containerd의 서비스 구조를 다루며 Snapshots 서비스를 잠깐 언급했습니다. 이번 장은 그 스냅샷이
실제로 디스크 위에서 어떤 모습을 하고 있는지, 그리고 이미지 레이어들이 어떻게 겹쳐져 컨테이너가 보는
하나의 파일시스템이 되는지를 파고듭니다. "레이어를 캐싱해서 빌드가 빨라진다", "볼륨을 쓰면 데이터가
남는다" 같은 사용법 차원의 지식을 넘어, `/var/lib/docker/overlay2/` 아래에 실제로 어떤 디렉터리들이
생기는지, 그리고 2026년 현재 Docker Engine이 기본으로 쓰는 저장 방식이 왜 예전과 달라졌는지를 직접
확인하는 것이 이 장의 목표입니다.

## 6.1 레이어와 유니온 파일시스템의 원리

컨테이너 이미지는 하나의 거대한 파일시스템 스냅샷이 아니라, 순서가 있는 여러 겹의 변경분(diff)으로
이루어져 있습니다. `FROM ubuntu`로 시작해 `RUN apt-get install`, `COPY app /app` 같은 Dockerfile
명령을 거칠 때마다, 그 직전 상태와 비교한 파일시스템 변경 사항만 새로운 레이어로 기록됩니다. 이 레이어들을
쌓아 올려 하나의 통합된 뷰로 보여주는 기술이 유니온 파일시스템(union filesystem)이며, 리눅스에서는
`overlayfs`가 사실상 표준으로 자리잡았습니다.

레이어를 겹으로 쌓는 방식의 핵심 이점은 두 가지입니다. 첫째, 동일한 베이스 이미지를 쓰는 여러 이미지나
컨테이너가 그 베이스 레이어를 디스크에서 물리적으로 공유할 수 있습니다. `ubuntu:24.04`를 베이스로 하는
이미지 열 개를 받아도, 베이스 레이어는 디스크에 한 벌만 존재합니다. 둘째, 컨테이너가 실행 중 파일을
바꾸더라도 그 변경은 별도의 쓰기 가능한 레이어에만 기록되고, 원본 이미지 레이어는 절대 수정되지 않습니다.
컨테이너를 지워도 이미지가 멀쩡한 이유, 그리고 같은 이미지로 컨테이너를 여러 개 띄워도 서로 간섭하지
않는 이유가 바로 이 구조에 있습니다.

## 6.2 overlayfs의 lowerdir / upperdir / merged / workdir

overlayfs 마운트는 네 가지 역할의 디렉터리로 구성됩니다.

- **lowerdir**: 읽기 전용 레이어. 이미지 레이어들이 여기 해당하며, 여러 개를 콜론(`:`)으로 나열해 겹쳐
  쌓을 수 있습니다. overlay2 드라이버는 리눅스 커널 버전에 따라 다르지만 일반적으로 최대 128개 안팎의
  lowerdir을 지원합니다.
- **upperdir**: 쓰기 가능한 단일 레이어. 컨테이너가 실행되며 발생시키는 모든 파일 변경(생성, 수정, 삭제)이
  여기에 기록됩니다.
- **merged**: 컨테이너 프로세스가 실제로 `/`로 보게 되는, lowerdir과 upperdir을 합쳐서 보여주는 통합 뷰입니다.
- **workdir**: overlayfs가 파일 교체 같은 내부 연산을 원자적으로 처리하기 위해 쓰는 작업용 디렉터리로,
  사용자가 직접 다룰 일은 없습니다.

컨테이너 안에서 이미지 레이어에 있던 파일을 수정하면, overlayfs는 그 파일을 upperdir로 먼저 복사한 뒤
그 복사본을 수정합니다. 이를 copy-on-write(CoW)라고 부르며, 원본 lowerdir의 파일은 전혀 손대지 않기
때문에 같은 lowerdir을 공유하는 다른 컨테이너에는 영향이 없습니다. 파일을 삭제한 경우에도 실제로는
lowerdir의 파일이 지워지는 것이 아니라, upperdir에 "이 파일은 지워졌다"는 표시(whiteout)를 남기는
방식으로 처리됩니다.

### 실제 디스크에서 확인하기

Docker Engine이 레거시 overlay2 그래프 드라이버를 쓰는 경우, 이 구조는 `/var/lib/docker/overlay2/` 아래에
그대로 나타납니다.

```bash
docker inspect --format '{{json .GraphDriver}}' <container> | python3 -m json.tool
```

이 명령의 출력에는 `LowerDir`, `UpperDir`, `MergedDir`, `WorkDir` 네 경로가 그대로 표시됩니다. 실제
마운트 테이블에서도 동일한 정보를 볼 수 있습니다.

```bash
mount | grep overlay | grep <컨테이너ID의 앞부분>
```

출력은 대략 다음과 같은 형태입니다.

```text
overlay on /var/lib/docker/overlay2/<id>/merged type overlay (rw,relatime,
lowerdir=/var/lib/docker/overlay2/l/XXXX:/var/lib/docker/overlay2/l/YYYY,
upperdir=/var/lib/docker/overlay2/<id>/diff,
workdir=/var/lib/docker/overlay2/<id>/work)
```

여기서 `lowerdir`에 나열된 경로들이 실제 레이어 디렉터리가 아니라 `overlay2/l/` 아래의 짧은 심볼릭
링크라는 점이 눈에 띕니다. overlayfs를 마운트할 때 `lowerdir` 옵션에 넘기는 문자열 길이에는 커널이 정한
한계가 있는데, 이미지 레이어가 많아지면 전체 경로를 그대로 나열했을 때 이 길이 제한에 걸릴 수 있습니다.
Docker는 이를 피하기 위해 각 레이어 디렉터리에 대응하는 짧은 이름의 심볼릭 링크를 `overlay2/l/` 아래에
만들어 두고, 실제 마운트에는 이 짧은 링크 경로를 사용합니다.

## 6.3 containerd 네이티브 스냅샷터의 경로 구조

containerd가 자체적으로 이미지를 관리하는 경로에서는 스냅샷 데이터가 `/var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/`
아래에 저장됩니다. 개념적인 lowerdir/upperdir/merged/workdir 구조 자체는 동일하지만, 관리 단위가 Docker의
그래프 드라이버가 아니라 containerd의 Snapshots 서비스이고, 각 스냅샷은 숫자로 된 스냅샷 ID로 식별됩니다.

```bash
sudo ls /var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/snapshots/
```

이 아래에 스냅샷 ID별로 `fs/`(overlay2의 `diff/`에 해당하는 실제 내용물 디렉터리)와 `work/` 디렉터리가
생기는 구조를 볼 수 있습니다. 어느 스냅샷이 어느 스냅샷 위에 쌓였는지는 메타데이터 데이터베이스
(containerd의 bolt 기반 메타 스토어)에 부모-자식 관계로 기록되어 있으며, `ctr snapshots` 하위 명령으로
조회할 수 있습니다.

```bash
sudo ctr -n moby snapshots list
sudo ctr -n moby snapshots tree
```

`snapshots tree` 명령은 어느 레이어가 어느 레이어 위에 쌓였는지를 트리 형태로 보여주어, 이미지 레이어
공유 구조를 한눈에 파악하는 데 유용합니다.

## 6.4 레거시 graphdriver와 containerd 스냅샷터, 그리고 2026년의 기본값 전환

Docker Engine은 오랫동안 "그래프 드라이버(graphdriver)"라는 자체 추상화를 통해 이미지 저장소를 관리해
왔습니다. 이 그래프 드라이버 계층은 containerd가 아니라 dockerd 자신이 직접 관리하는 코드였고,
역사적으로는 containerd가 지금처럼 이미지 저장까지 담당하기 이전부터 존재하던 유산입니다. 시기별로
여러 구현체가 쓰였다는 점도 함께 알아 둘 만합니다.

- **aufs**: Docker 초창기의 기본 드라이버였습니다. 메인라인 리눅스 커널에 aufs가 포함되지 않아 배포판마다
  별도 패치가 필요했고, 이 유지보수 부담이 이후 overlayfs로 무게 중심이 옮겨간 배경 중 하나입니다.
- **devicemapper**: 블록 장치 기반의 씬 프로비저닝(thin provisioning)을 이용해 레이어를 관리하는
  드라이버로, 파일시스템이 아니라 블록 단위로 동작한다는 점이 특징이었지만 설정이 까다롭고 컨테이너
  밀도가 높아질수록 성능 저하가 두드러진다는 평가를 받았습니다.
- **btrfs / zfs**: 각각 btrfs, ZFS 파일시스템 자체의 스냅샷·클론 기능을 활용하는 드라이버로, 해당
  파일시스템을 이미 운영 중인 환경에서 선택되곤 했지만 범용성이 낮아 널리 쓰이지는 않았습니다.
- **overlay2**: 리눅스 커널 4.x 계열부터 다중 lowerdir을 지원하는 overlayfs가 메인라인 커널에 안정적으로
  포함되면서, 별도 패치나 특수한 파일시스템 없이도 대부분의 배포판에서 그대로 쓸 수 있는 overlay2가
  사실상의 기본값으로 자리잡았습니다.

이런 배경 때문에 aufs, devicemapper, btrfs, zfs 드라이버는 현재 사실상 레거시로 취급되며, 새로 구축하는
환경에서 이 드라이버들을 의도적으로 선택할 이유는 거의 없습니다.

containerd는 처음부터 스냅샷터(snapshotter)라는 자체 추상화를 이미지 저장의 기본 모델로 채택했습니다.
graphdriver와 snapshotter는 비슷한 문제(레이어를 쌓아 루트 파일시스템 만들기)를 풀지만 설계가 다른
별개의 코드 경로입니다. Docker Engine은 오랜 기간 이 두 세계를 모두 유지하면서, 기본값으로는 dockerd
자신의 graphdriver 경로를 쓰고 containerd의 스냅샷터 기반 "containerd 이미지 스토어"는 선택적 기능으로
제공해 왔습니다.

**Docker Engine v29부터는 이 기본값이 뒤집혔습니다.** 신규로 설치되는 Docker Engine은 기본적으로
containerd 이미지 스토어를 사용하며, 레거시 그래프 드라이버는 사실상 유지보수 모드로 들어가 향후
제거가 예고된 상태입니다. 다만 이미 운영 중이던 기존 설치는 업그레이드 시점에 자동으로 마이그레이션되지
않으며, 관리자가 명시적으로 전환하지 않는 한 계속 레거시 경로를 사용합니다. 어떤 저장소를 쓰고 있는지는
다음 명령으로 확인할 수 있습니다.

```bash
docker info --format '{{.DriverStatus}}'
docker info | grep -A2 'Storage Driver'
```

containerd 이미지 스토어를 쓰는 경우 `docker info`의 출력 형태 자체가 달라지며, `docker inspect`의
`GraphDriver` 항목도 이전과 다른 형식으로 나타납니다.

### 전환에 따른 실무 영향

기본값이 바뀌면서 실무에서 확인해야 할 지점도 함께 바뀌었습니다.

- **`--storage-opt size=` 같은 레거시 옵션이 조용히 무시될 수 있습니다.** 레거시 overlay2 그래프 드라이버는
  컨테이너별 쓰기 레이어 크기를 제한하는 `--storage-opt size=<한도>` 옵션을 지원했지만, containerd
  이미지 스토어 경로는 이 옵션을 그대로 받아주면서도 실제로는 용량 제한을 강제하지 않는 사례가 보고되어
  있습니다. 백엔드 파일시스템이 프로젝트 쿼터(project quota)를 지원하는지 검증하는 로직이 그래프 드라이버
  경로와 다르기 때문입니다. 용량 제한을 운영 정책으로 쓰고 있었다면, containerd 이미지 스토어로 전환한
  뒤 실제로 한도가 걸리는지 반드시 재검증해야 합니다.
- **디스크 사용량이 늘어날 수 있습니다.** containerd 스냅샷터 경로는 레이어를 압축된 형태와 압축이 풀린
  형태로 함께 보관하는 경우가 있어, 레거시 그래프 드라이버 대비 디스크 점유가 늘어나는 사례가 보고되고
  있습니다. 스토리지가 빠듯한 환경에서는 이 부분을 사전에 용량 계획에 반영해야 합니다.
- **user namespace remap(`userns-remap`)과의 조합이 아직 완전하지 않을 수 있습니다.** 보안 강화를 위해
  `userns-remap`을 쓰고 있는 환경이라면, containerd 이미지 스토어로 전환하기 전에 해당 기능과의 호환
  여부를 확인해야 합니다.

이런 이유로 실무에서는 "신규 설치는 기본값을 그대로 받아들이되, 기존 운영 환경은 위 항목들을 검증한
뒤 계획적으로 전환한다"는 접근이 안전합니다. 현재 어떤 저장 방식을 쓰고 있는지 모호하다면 `docker info`의
드라이버 이름을 확인하는 것이 가장 확실한 출발점입니다.

## 6.5 콘텐츠 주소화 저장소와 레이어 공유

containerd의 콘텐츠 스토어(content store)는 모든 블롭(레이어 tar, 이미지 config 등)을 파일 이름이 아니라
그 내용의 암호학적 해시(다이제스트, 예: `sha256:abcdef...`)로 식별하고 저장합니다. 이를 콘텐츠 주소화
저장소(content-addressable storage)라고 부릅니다. 이 방식의 핵심 성질은 "내용이 같으면 다이제스트도
같다"는 것이고, 그 역도 사실상 성립합니다(해시 충돌은 실용적으로 무시할 수 있는 확률입니다). 그 결과
서로 다른 이미지 태그, 심지어 서로 다른 이미지 이름이라도 실제 레이어 내용이 동일하다면 디스크에는
단 한 벌만 저장되고 여러 이미지가 그 블롭을 함께 참조합니다.

이 성질이 실무에서 체감되는 대표적 장면이 이미지 pull입니다. 새 이미지를 받을 때 로그에 종종
`Already exists`라는 문구가 찍히는 레이어가 있는데, 이는 그 레이어의 다이제스트가 이미 로컬 콘텐츠
스토어에 있어 다운로드를 건너뛰었다는 뜻입니다. 빌드 캐시나 멀티 스테이지 빌드가 빠르게 동작하는 것,
그리고 같은 베이스 이미지를 쓰는 여러 애플리케이션 이미지를 받아도 디스크 사용량이 이미지 개수만큼
선형으로 늘지 않는 것 모두 이 콘텐츠 주소화 저장 방식 덕분입니다.

이 공유 구조의 반대편에는 정리(garbage collection) 문제가 있습니다. 여러 이미지가 같은 블롭을 참조하고
있으므로, 이미지 하나를 지운다고 그 이미지가 쓰던 블롭을 곧바로 디스크에서 지워버리면 다른 이미지가
참조하던 데이터까지 함께 사라질 위험이 있습니다. containerd는 이를 막기 위해 각 블롭에 대한 참조
관계를 메타데이터로 추적하고 있다가, 더 이상 어떤 이미지·컨테이너·스냅샷도 참조하지 않는 블롭만 골라
지우는 참조 계수(reference counting) 방식의 가비지 컬렉션을 수행합니다. `docker image prune`이나
`docker system prune`을 실행했을 때 즉시 지워지는 레이어와 그렇지 않은 레이어가 갈리는 이유가 바로
이 참조 관계에 있습니다.

## 6.6 볼륨, 바인드 마운트, tmpfs — 컨테이너 밖에 데이터를 두는 세 가지 방법

이미지 레이어와 컨테이너의 쓰기 레이어는 기본적으로 컨테이너의 생명주기와 함께합니다. 컨테이너를 지우면
쓰기 레이어도 함께 사라지므로, 컨테이너 재시작이나 교체에도 살아남아야 하는 데이터는 별도의 마운트로
빼서 관리해야 합니다. Docker는 이를 위해 세 가지 마운트 방식을 제공합니다.

| 방식 | 저장 위치 | 생명주기 | 주 용도 |
|---|---|---|---|
| named volume | `/var/lib/docker/volumes/<이름>/_data` (또는 볼륨 드라이버가 관리하는 위치) | 명시적으로 `docker volume rm`할 때까지 유지, 컨테이너 삭제와 무관 | 데이터베이스 파일 등 컨테이너와 독립적으로 지속되어야 하는 데이터 |
| bind mount | 호스트의 임의 경로(사용자가 직접 지정) | 호스트 파일시스템의 생명주기를 그대로 따름 | 소스 코드 실시간 반영, 호스트 설정 파일 주입 |
| tmpfs mount | 호스트 디스크가 아닌 메모리 | 컨테이너가 멈추면 즉시 소멸 | 비밀값 등 디스크에 남기면 안 되는 임시 데이터 |

named volume은 Docker(또는 containerd)가 직접 생명주기를 관리하는 저장 단위로, 볼륨 드라이버 플러그인을
통해 로컬 디스크뿐 아니라 NFS, 클라우드 블록 스토리지 등 외부 스토리지 시스템과도 연결될 수 있습니다.
바인드 마운트는 반대로 호스트의 특정 경로를 그대로 컨테이너 안에 노출하는 방식이라 Docker가 그 내용의
생명주기에 전혀 관여하지 않으며, 호스트 쪽 권한·SELinux 라벨 문제를 그대로 물려받는다는 점을 주의해야
합니다. tmpfs 마운트는 애초에 디스크에 쓰이지 않는 메모리 기반이므로 컨테이너가 종료되는 순간 내용이
완전히 사라지며, 이 특성 때문에 짧게 다뤄야 하는 민감 정보(예: 런타임에만 필요한 토큰 파일)를 두는
용도로 자주 쓰입니다.

### 볼륨 드라이버 플러그인

기본 `local` 드라이버는 호스트 디스크에 볼륨 데이터를 그대로 저장하지만, 여러 호스트에서 같은 데이터를
공유해야 하거나 클라우드 블록 스토리지에 볼륨을 얹어야 하는 경우에는 별도의 볼륨 드라이버 플러그인을
설치해 사용합니다. Docker의 볼륨 드라이버 인터페이스는 `Create`, `Mount`, `Path`, `Unmount`, `Remove`
같은 표준 동작을 플러그인이 구현하도록 정의하고 있으며, 이 플러그인은 `docker plugin install`로 설치한
뒤 `docker volume create --driver <플러그인 이름>`으로 사용합니다.

```bash
docker plugin install --grant-all-permissions vieux/sshfs
docker volume create --driver vieux/sshfs \
  --opt sshcmd=user@remote-host:/data \
  --opt password=... \
  remote-vol
```

이 예시처럼 볼륨 드라이버 플러그인을 쓰면 컨테이너 입장에서는 여전히 평범한 `-v remote-vol:/data`
마운트일 뿐이지만, 실제 데이터는 원격 호스트나 외부 스토리지 시스템에 놓이게 됩니다. 어떤 드라이버를
쓰든 "컨테이너는 마운트 지점만 알고, 그 뒤에 실제로 어디에 데이터가 있는지는 드라이버가 책임진다"는
원칙은 동일합니다.

## 6.7 실습으로 저장 구조 직접 들여다보기

지금까지 설명한 개념을 실제 명령으로 확인해 보겠습니다. 아래는 레거시 overlay2 그래프 드라이버를 쓰는
호스트를 기준으로 하며, containerd 이미지 스토어를 쓰는 경우 경로만 6.3절에서 설명한 스냅샷터 경로로
바꿔 읽으면 됩니다.

```bash
# 1. 현재 어떤 저장 드라이버를 쓰고 있는지 확인합니다.
docker info --format 'Driver: {{.Driver}}'

# 2. 전체 디스크 사용량을 이미지/컨테이너/볼륨/빌드 캐시별로 요약해 봅니다.
docker system df
# TYPE, TOTAL, ACTIVE, SIZE, RECLAIMABLE 열이 출력됩니다. RECLAIMABLE 비율이 높다면
# docker system prune으로 정리할 여지가 있다는 뜻입니다.

# 3. 레이어 단위로 더 자세히 보고 싶다면 -v 옵션을 붙입니다.
docker system df -v

# 4. 컨테이너 하나를 띄우고 그 GraphDriver 정보를 조회합니다.
docker run -d --name overlay-demo nginx:alpine
docker inspect --format '{{json .GraphDriver.Data}}' overlay-demo | python3 -m json.tool

# 5. 위에서 얻은 LowerDir, UpperDir, MergedDir, WorkDir 경로를 직접 들어가 봅니다.
sudo ls /var/lib/docker/overlay2/$(docker inspect --format '{{.Id}}' overlay-demo)/diff
# nginx 설정 파일 등 이 컨테이너가 새로 쓴 파일이 있다면 여기 upperdir(diff)에서 보입니다.

# 6. 컨테이너 안에서 새 파일을 하나 만들고, 그 파일이 upperdir에 나타나는지 확인합니다.
docker exec overlay-demo sh -c 'echo hello > /tmp/marker.txt'
sudo cat /var/lib/docker/overlay2/$(docker inspect --format '{{.Id}}' overlay-demo)/diff/tmp/marker.txt

# 7. 정리합니다.
docker rm -f overlay-demo

# 8. named volume, bind mount, tmpfs를 각각 마운트해 저장 위치 차이를 비교합니다.
docker volume create demo-vol
docker run --rm \
  -v demo-vol:/data/volume \
  -v "$(pwd)":/data/bind \
  --tmpfs /data/tmpfs \
  alpine sh -c 'echo vol > /data/volume/f.txt; echo bind > /data/bind/f.txt; echo tmp > /data/tmpfs/f.txt'

ls "$(docker volume inspect demo-vol --format '{{.Mountpoint}}')"
ls ./f.txt
# tmpfs에 쓴 파일은 컨테이너가 이미 --rm으로 삭제되었으므로 호스트 어디에서도 찾을 수 없습니다.
```

5~6단계에서 컨테이너 안에서 만든 파일이 곧바로 호스트의 `overlay2/.../diff` 아래에 나타나는 것을 확인하면,
"컨테이너의 쓰기 레이어"라는 추상적 표현이 실제로는 호스트 디스크의 평범한 디렉터리라는 사실이 분명해집니다.
8단계에서는 named volume으로 쓴 파일은 볼륨 마운트포인트에 남아 있고, bind mount로 쓴 파일은 현재
작업 디렉터리에 그대로 남아 있지만, tmpfs에 쓴 파일은 컨테이너 종료와 동시에 완전히 사라진다는 차이를
직접 비교할 수 있습니다.

이미지가 어떻게 저장되고 컨테이너가 그 위에서 어떻게 쓰기 작업을 하는지까지 살펴봤으니, 1부에서 다룬
Docker 내부 아키텍처의 핵심 뼈대는 이것으로 마무리됩니다. 다음 2부에서는 시선을 옮겨, 이 아키텍처
위에서 dockerd가 제공하는 API와 BuildKit 기반 빌드 프레임워크가 어떻게 이미지를 만들어 내는지를 다룹니다.

## 핵심 요약

- 이미지는 순서가 있는 읽기 전용 레이어의 집합이며, overlayfs는 이를 lowerdir(이미지 레이어)/upperdir
  (컨테이너 쓰기 레이어)/merged(통합 뷰)/workdir(내부 작업용)로 조합해 하나의 파일시스템처럼 보여줍니다.
- 레거시 Docker 그래프 드라이버(overlay2 등)는 `/var/lib/docker/overlay2/`에, containerd 네이티브
  스냅샷터는 `/var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/`에 데이터를 저장합니다. 두
  모델은 같은 개념을 구현하지만 관리 주체(dockerd vs containerd)와 디렉터리 구조가 다릅니다.
- Docker Engine v29부터 containerd 이미지 스토어가 신규 설치 기본값이 되었고 레거시 그래프 드라이버는
  deprecated 상태입니다. 기존 설치는 자동 마이그레이션되지 않으며, 전환 시 `--storage-opt size=`의
  무력화, 디스크 사용량 증가, `userns-remap` 호환성 같은 항목을 반드시 검증해야 합니다.
- 콘텐츠 주소화 저장소는 모든 블롭을 다이제스트로 식별해, 동일한 내용의 레이어를 여러 이미지가 디스크
  상에서 물리적으로 공유하게 해 줍니다.
- named volume, bind mount, tmpfs mount는 저장 위치와 생명주기가 각각 다르며, 컨테이너 재시작에도
  살아남아야 하는 데이터는 named volume이나 bind mount로, 디스크에 남기면 안 되는 민감한 임시 데이터는
  tmpfs로 분리하는 것이 기본 원칙입니다.
- `docker system df`, `docker inspect`의 `GraphDriver`/스냅샷 정보, 그리고 실제 오버레이 디렉터리를
  직접 탐색하는 것으로 레이어 구조를 눈으로 검증할 수 있습니다.

## 실습

6.7절에 포함된 실습이 이번 장의 전체 실습입니다. 추가로, 레이어 공유를 직접 체감해 보고 싶다면 다음
명령으로 같은 베이스 이미지를 쓰는 두 이미지를 받아 콘텐츠 스토어 재사용을 관찰할 수 있습니다.

```bash
# 같은 베이스(alpine)를 쓰는 두 이미지를 연달아 받으며 pull 로그를 비교합니다.
docker pull alpine:3.20
docker pull curlimages/curl:latest
# curlimages/curl은 alpine 기반 이미지이므로, 공통 레이어 다이제스트에 대해
# "Already exists"로 표시되는 줄이 있는지 pull 로그에서 확인합니다.

docker system df -v
# alpine:3.20과 curlimages/curl이 공유하는 레이어가 있다면, 두 이미지의 "SIZE" 합계가
# 각 이미지의 독립적인 크기를 단순히 더한 값보다 작게 나타나는 것을 확인할 수 있습니다.
```
