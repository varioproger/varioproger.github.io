# 16장. 방화벽 백엔드의 전환 — iptables에서 nftables로

15장에서는 포트 매핑이 iptables의 `nat` 테이블 DNAT 규칙을 거쳐 컨테이너까지 도달하는 경로를 추적했습니다.
그 설명은 지난 10여 년간 Docker 네트워킹의 사실상 기본 전제였던 iptables를 기준으로 한 것이었습니다. 그런데
2026년 현재, 이 전제 자체가 흔들리고 있습니다. Docker Engine 28은 iptables 체인의 우선순위 문제로 인해
발생하던 보안 허점을 메우기 위해 기본 동작 자체를 바꾸었고, Docker Engine 29는 한 걸음 더 나아가 iptables를
아예 대체할 수 있는 실험적인 nftables 네이티브 백엔드를 도입했습니다. 이 장에서는 iptables가 왜 한계에
부딪혔는지, nftables가 그 한계를 어떻게 해결하도록 설계되었는지, 그리고 Docker가 이 전환을 어떤 방식으로
반영하고 있는지를 순서대로 다룹니다. 이 내용은 12장에서 다룬 브리지 네트워크의 iptables 규칙, 13장의 Swarm
오버레이 네트워크, 그리고 바로 앞 15장의 포트 매핑 DNAT 경로를 모두 다시 한번 "방화벽 백엔드"라는 축으로
정리하는 장이기도 합니다.

## 16.1 iptables의 한계 — 왜 대체가 필요했는가

iptables는 넷필터(netfilter) 프레임워크 위에 만들어진 사용자 공간 도구로, 1998년 무렵 도입된 이래 리눅스
방화벽의 사실상 표준으로 자리 잡아 왔습니다. 하지만 20년 넘게 기능이 누적되면서 몇 가지 구조적인 문제가
드러났습니다.

첫째, 규칙 순회 방식이 본질적으로 선형(linear) 탐색입니다. `filter` 테이블의 `INPUT`이나 `FORWARD` 체인에
수백, 수천 개의 규칙이 쌓이면 패킷 하나가 어떤 체인을 통과할 때마다 위에서부터 순서대로 규칙을 하나씩
검사해야 합니다. Docker처럼 컨테이너가 뜨고 사라질 때마다 규칙을 동적으로 추가/삭제하는 워크로드에서
컨테이너 수가 많아질수록 이 순회 비용이 누적되는 경향이 있습니다.

둘째, 문법과 도구 체계가 파편화되어 있습니다. IPv4용 `iptables`, IPv6용 `ip6tables`, 브리지 프레임을 다루는
`ebtables`, ARP를 다루는 `arptables`가 각각 별도의 명령과 별도의 커널 모듈로 존재합니다. 같은 종류의 규칙을
IPv4와 IPv6 양쪽에 동일하게 적용하려면 사실상 같은 내용을 두 번 작성해야 하는 구조입니다.

셋째, 리눅스 커널과 배포판 생태계는 이미 이 문제를 인식하고 `iptables` 자체를 nftables 위에 얹은 호환
레이어로 재구현하는 방향으로 오래전에 전환했습니다. 오늘날 대부분의 주요 배포판(Debian, Ubuntu, RHEL/Fedora
계열 등)에서 `iptables` 명령을 실행하면 실제로는 `iptables-nft`라는 바이너리가 호출되어, 사용자가 입력한
전통적인 iptables 문법을 nftables 규칙으로 변환해 커널의 nftables 서브시스템에 적재합니다. 과거의 진짜
legacy 구현은 `iptables-legacy`라는 별도 이름으로 남아 있으며, `update-alternatives`(Debian/Ubuntu 계열) 같은
메커니즘으로 두 구현 사이를 전환할 수 있게 되어 있습니다. 문제는 두 구현이 커널에 규칙을 적재하는 내부
표현 방식이 다르기 때문에, 한 시스템에 legacy와 nft 백엔드가 섞여 있으면(예: 어떤 도구는 `iptables-legacy`를
직접 호출하고, 다른 도구는 `iptables-nft`를 통해 규칙을 넣는 경우) 서로의 규칙을 인식하지 못해 방화벽 정책이
꼬여 있는데도 어느 쪽에서도 그 원인을 알아채기 어려운, 진단하기 까다로운 상황이 발생할 수 있다는 점입니다.
Docker는 오랫동안 이 iptables 호환 레이어(대부분의 현대 배포판에서는 사실상 `iptables-nft`) 위에서 동작해
왔으며, 이 장에서 다루는 "네이티브 nftables 백엔드"는 이 호환 레이어를 거치지 않고 Docker가 nftables 커널
API를 직접 사용하는 완전히 새로운 방식을 의미합니다.

### iptables-legacy와 iptables-nft, 그리고 ebtables/arptables의 흡수

배포판이 `iptables` 명령을 nftables 기반으로 전환한 방식은 완전히 새로운 명령을 쓰도록 강제하는 대신,
기존 `iptables` 문법을 그대로 받아들이되 내부적으로 nftables 규칙으로 번역해 커널에 적재하는 호환
바이너리(`iptables-nft`)를 만드는 것이었습니다. 이 덕분에 `iptables -A INPUT -p tcp --dport 22 -j ACCEPT`
같은 익숙한 명령을 그대로 쓰면서도, 실제로는 nftables 커널 서브시스템 위에서 동작하는 전환이 가능했습니다.
Debian/Ubuntu 계열에서는 다음과 같이 두 구현 사이를 전환할 수 있습니다.

```bash
# 현재 iptables가 어느 구현을 가리키는지 확인
sudo update-alternatives --display iptables

# nft 백엔드로 전환(대부분의 최신 배포판에서 이미 기본값)
sudo update-alternatives --set iptables /usr/sbin/iptables-nft

# 순수 legacy 구현으로 되돌리기 (호환성 문제 진단 등 특수한 목적)
sudo update-alternatives --set iptables /usr/sbin/iptables-legacy
```

같은 전환은 브리지 프레임을 다루던 `ebtables`와 ARP를 다루던 `arptables`에도 적용되었습니다. nftables는
브리지 패밀리(`bridge`)와 ARP 매칭을 자체 문법 안에 포함하고 있어서, `ebtables-nft`/`arptables-nft` 호환
바이너리를 통해 기존 명령 자산을 그대로 유지하면서도 내부적으로는 단일 nftables 프레임워크로 수렴시킬 수
있었습니다. 이 흐름 전체가 "각기 다른 프로토콜 계층마다 별도 도구를 두던 시대"에서 "하나의 프레임워크가
모든 계층을 다루는 시대"로 넘어가는 과정이었고, Docker의 네이티브 nftables 백엔드는 이 흐름의 연장선에서
호환 레이어조차 거치지 않고 nftables 커널 API(netlink 기반)를 직접 호출하는 마지막 단계에 해당합니다.

### nftables의 설계 목표

nftables는 이런 문제들을 근본적으로 다시 설계하기 위해 넷필터 프로젝트가 내놓은 후속 프레임워크입니다.
핵심 아이디어는 세 가지로 요약할 수 있습니다.

- **단일 프레임워크**: IPv4, IPv6, 브리지, ARP를 별도의 도구가 아니라 하나의 `nft` 명령과 하나의 규칙
  표현으로 다룹니다. 하나의 규칙에서 `ip`와 `ip6` 패밀리를 동시에 다루는 `inet` 패밀리를 쓰면 IPv4/IPv6
  규칙을 사실상 한 번만 작성해도 됩니다.
- **커널 내 가상 머신**: nftables 규칙은 커널 안에서 동작하는 작은 바이트코드 가상 머신(BPF와 유사한
  개념)으로 표현됩니다. 사용자 공간에서 규칙을 컴파일해 커널에 통째로 내려보내는 방식이라, iptables처럼
  매 규칙을 순서대로 재구성하는 대신 더 유연한 최적화가 가능합니다.
- **세트(set)와 맵(map) 기반 매칭**: "이 IP 목록에 포함되는가", "이 포트 중 하나인가" 같은 조건을 개별
  규칙을 N개 나열하는 대신 하나의 세트 자료구조로 표현할 수 있습니다. 세트는 커널 내부에서 해시 테이블이나
  트리 구조로 관리되므로, 규칙 수가 늘어나도 순회 비용이 선형으로 늘지 않고 훨씬 효율적으로 매칭할 수
  있습니다. Docker처럼 동적으로 늘고 주는 컨테이너 IP 목록을 다뤄야 하는 워크로드에 특히 잘 맞는 특성입니다.

### 같은 규칙, 두 가지 문법

두 프레임워크의 차이를 가장 빠르게 체감하는 방법은 같은 의도의 규칙을 나란히 놓고 비교하는 것입니다.
"TCP 22번 포트로 들어오는 패킷을 허용한다"는 규칙은 각각 다음과 같이 표현됩니다.

```bash
# iptables 문법
iptables -A INPUT -p tcp --dport 22 -j ACCEPT
```

```bash
# nftables 문법 (nft 스크립트)
nft add table inet filter
nft add chain inet filter input { type filter hook input priority 0 \; }
nft add rule inet filter input tcp dport 22 accept
```

nftables 쪽이 더 장황해 보이는 이유는, iptables에서는 `INPUT`, `FORWARD`, `OUTPUT` 같은 표준 체인과 그
체인이 걸리는 넷필터 훅(hook), 평가 순서(priority)가 프레임워크 안에 이미 고정되어 암묵적으로 정해져
있는 반면, nftables에서는 테이블과 체인을 사용자가 직접 선언하면서 그 체인이 어떤 훅(input, forward,
output, prerouting, postrouting)에 걸릴지와 같은 훅에 여러 체인이 걸릴 때 어떤 순서(priority 숫자가 작을수록
먼저 평가됨)로 평가될지를 명시적으로 지정해야 하기 때문입니다. 이 명시성이 처음에는 번거로워 보이지만,
바로 이 지점이 16.3절에서 설명할 Docker 전용 테이블의 격리를 가능하게 하는 핵심 메커니즘입니다. Docker가
`docker-bridges`라는 이름의 테이블을 만들고 그 안에 자체적인 훅과 우선순위를 지정하면, 다른 도구가 만든
테이블과 이름 공간 자체가 분리되어 있으므로 두 도구의 규칙이 우연히 뒤섞일 여지가 훨씬 줄어듭니다.

## 16.2 Docker Engine 28 — 게시되지 않은 포트를 막다

nftables 네이티브 백엔드 이야기를 하기 전에, 그 도입의 배경이 된 Docker Engine 28의 변화를 짚어야 합니다.
Docker는 오랫동안 "컨테이너의 포트는 명시적으로 게시(publish)한 것만 외부에 노출된다"는 것을 기본 원칙으로
내세워 왔지만, 실제로는 이 원칙에 허점이 있었습니다. Docker가 브리지 네트워크를 만들 때 컨테이너들은 사설
대역의 IP를 직접 부여받고, 호스트가 그 사설 대역으로 패킷을 라우팅할 수 있는 상태가 됩니다. 문제는 많은
리눅스 배포판이 기본 iptables 정책을 `ACCEPT`(모든 트래픽 허용)로 두고 있으며, Docker는 컨테이너 네트워크로
향하는 트래픽을 별도로 필터링하는 대신 이 관대한 기본 정책에 사실상 의존해 왔다는 점입니다. 그 결과 네트워크
경로만 확보되면(예: 같은 사설망 안의 다른 서버, 혹은 클라우드 환경에서 VPC 라우팅이 허용된 경로) 공식적으로
게시하지 않은 컨테이너의 포트에 컨테이너 IP로 직접 접근하는 것이 가능했습니다. `-p`로 포트를 게시하지
않았으니 안전하다고 믿었던 포트가, 실제로는 호스트를 거치지 않고 컨테이너 IP로 직접 라우팅되는 경로를 통해
그대로 열려 있었던 셈입니다.

여기에 더해, Docker가 만드는 iptables 규칙 자체가 호스트 방화벽 도구들과 충돌하는 문제도 있었습니다. Docker는
`FORWARD` 체인에 자신의 `DOCKER` 체인으로 점프하는 규칙을 다른 규칙보다 앞쪽에 삽입하는 방식으로 동작합니다.
그런데 `ufw`나 `firewalld` 같은 호스트 방화벽 관리 도구는 관리자가 설정한 규칙을 흔히 `INPUT` 체인이나
자신의 관리 체인에 넣는데, 컨테이너로 향하는 트래픽 상당수는 `INPUT`이 아니라 `FORWARD` 체인을 통과합니다.
그 결과 관리자가 `ufw`에서 "이 포트는 막아라"라고 설정해도, Docker가 `FORWARD` 체인에 심어둔 규칙이 그보다
먼저(또는 별도 경로로) 패킷을 처리해 버려 관리자의 의도와 무관하게 트래픽이 통과하는 상황이 발생했습니다.
이는 Docker의 버그라기보다, "컨테이너 네트워킹을 위한 규칙"과 "호스트 방화벽 정책을 위한 규칙"이 같은
netfilter 체인 공간을 서로 조율 없이 나눠 쓰던 구조적인 문제였습니다.

Docker Engine 28.0.0은 이 문제에 대응해 게시되지 않은 포트로 향하는 인바운드 트래픽을 컨테이너 IP 기준으로
기본 차단하도록 동작을 변경했습니다. 구체적으로는 `-p`/`--publish`로 명시적으로 게시하지 않은 컨테이너
포트로의 직접 라우팅 접근을 Docker가 관리하는 `DOCKER` iptables 체인 레벨에서 차단합니다. 이 변경은 Linux
호스트에서 iptables 기반으로 동작하는 Docker Engine에 적용되며, Docker Desktop 환경은 그 자체가 별도의
경량 VM 계층과 네트워킹 방식을 쓰기 때문에 이 변경의 직접적인 영향 대상이 아닙니다. 만약 기존에 게시하지
않은 포트로 원격 호스트에서 직접 라우팅 접근이 필요했던 구성이 있다면, 필요한 포트를 정식으로 게시하거나
`gateway_mode_ipv4`/`gateway_mode_ipv6`를 `nat-unprotected`로 설정해 이전 동작을 선택적으로 복원할 수
있습니다. 다만 이 옵션은 이름 그대로 보호되지 않는(unprotected) 상태로 되돌리는 것이므로, 정말 필요한
경우가 아니라면 포트를 정식으로 게시하는 쪽이 권장됩니다.

## 16.3 Docker Engine 29 — 실험적 네이티브 nftables 백엔드

Docker Engine 28의 하드닝이 iptables 체계 위에서 문제를 봉합한 것이라면, Docker Engine 29에서 도입된
nftables 네이티브 백엔드는 좀 더 근본적인 재설계에 해당합니다. 이 기능은 Docker 29.0.0부터 실험적으로
제공되며, 다음 두 가지 방법 중 하나로 활성화합니다.

```bash
# 방법 1: 데몬 실행 시 플래그로 지정
dockerd --firewall-backend=nftables
```

```json
// 방법 2: daemon.json에 명시
{
  "firewall-backend": "nftables"
}
```

daemon.json으로 설정한 뒤에는 데몬을 재시작해야 반영됩니다.

```bash
sudo systemctl restart docker
```

### 무엇이 근본적으로 달라지는가

기존 iptables 기반 경로에서 Docker는 `DOCKER`, `DOCKER-USER`, `DOCKER-ISOLATION-STAGE-1/2` 같은 체인들을
만들고, 이 체인들을 호스트의 표준 체인(`FORWARD`, `nat` 테이블의 `PREROUTING`/`OUTPUT` 등) 안에 점프 규칙
형태로 끼워 넣는 방식으로 동작했습니다. 이 방식의 근본적인 한계는, Docker가 만든 체인과 호스트 관리자
또는 다른 도구(`firewalld`, `ufw`)가 만든 체인이 결국 같은 공유된 네임스페이스(체인 이름 공간과 체인 간
점프 순서) 안에서 뒤섞인다는 점입니다. 어느 쪽이 먼저 평가되는지는 규칙이 삽입된 순서에 달려 있고, 이
순서는 두 도구가 서로의 존재를 모른 채 각자 규칙을 추가하고 삭제하는 과정에서 쉽게 뒤바뀔 수 있습니다.
16.2절에서 설명한 `FORWARD` 체인 우선순위 문제가 바로 이 공유된 네임스페이스 구조에서 비롯된 것입니다.

nftables 네이티브 백엔드는 이 문제를 nftables가 기본으로 제공하는 **테이블 네임스페이스 분리**를 활용해
설계를 다시 짭니다. nftables에서는 테이블(table)이 규칙을 담는 최상위 컨테이너 역할을 하며, 서로 다른
테이블은 이름과 우선순위(priority)로 명확히 구분됩니다. Docker의 nftables 백엔드는 브리지 네트워크 트래픽을
위해 호스트 네임스페이스에 `ip docker-bridges`, `ip6 docker-bridges`라는 Docker 전용 테이블을 만들고, 여기에
필요한 체인과 우선순위를 스스로 구성합니다. DNS 관련 규칙은 컨테이너 자신의 네트워크 네임스페이스 안에도
별도로 생성됩니다. 이렇게 Docker의 규칙이 자신만의 독립된 테이블 안에 격리되면, `firewalld`나 관리자가 직접
관리하는 다른 nftables 테이블과 이름이나 우선순위가 우연히 충돌할 가능성이 iptables 시절보다 훨씬 줄어들고,
어떤 트래픽이 Docker의 규칙 때문에 처리되었는지도 `nft list table ip docker-bridges`처럼 명확하게 분리해서
들여다볼 수 있게 됩니다.

한 가지 실무적으로 챙겨야 할 차이는, 전통적인 iptables 경로에서 관리자가 Docker의 규칙보다 먼저 자신의
정책을 적용하기 위해 흔히 활용하던 `DOCKER-USER` 체인이 nftables 백엔드에는 그대로 존재하지 않는다는
점입니다. `DOCKER-USER`는 Docker가 자신의 체인들보다 앞서 평가되도록 비워둔, 관리자를 위한 훅(hook)
포인트였는데, nftables 백엔드에서는 이 개념이 별도 테이블과 우선순위 조정이라는 다른 방식으로 대체됩니다.
즉 관리자가 커스텀 규칙을 추가하고 싶다면, `DOCKER-USER`에 규칙을 넣던 습관을 그대로 가져오는 대신 자신의
nftables 테이블을 만들고 그 테이블의 우선순위를 Docker의 `docker-bridges` 테이블과의 관계 속에서 명시적으로
조정해야 합니다.

### 실험적 상태라는 것의 의미

Docker 공식 문서는 이 기능에 대해 "Docker 29.0.0에 도입된 nftables 지원은 실험적(experimental)이며, 구성
옵션과 동작, 구현이 모두 앞으로 바뀔 수 있다"고 명시적으로 경고하고 있습니다. 이는 단순한 형식적 문구가
아니라, `firewall-backend` 플래그의 정확한 이름, daemon.json 스키마, 테이블/체인 구조, 심지어 어떤 트래픽
경로가 이 백엔드의 대상이 되는지까지 이후 릴리스에서 변경될 수 있다는 뜻입니다. 따라서 2026년 9월 현재
시점에서 이 백엔드를 프로덕션에 전면 도입하는 것은 신중해야 하며, 새 릴리스 노트를 매번 확인하는 것을
전제로 검토용/실험용 환경에서 먼저 검증하는 접근이 합리적입니다.

### Swarm 모드에서는 아직 활성화할 수 없다

13장에서 다룬 것처럼 Swarm 모드의 오버레이 네트워크는 VXLAN 캡슐화와 함께 상당히 복잡한 iptables 규칙
집합(각 노드의 ingress 네트워크, 서비스 VIP를 위한 IPVS 연동, 여러 오버레이 네트워크 간 격리 등)에 의존하고
있습니다. 이 규칙 집합은 아직 nftables 백엔드로 옮겨지지 않았습니다. 그 결과 Docker 데몬이 Swarm 모드로
동작 중인 상태에서 nftables 백엔드를 활성화하려고 하면 데몬이 이를 거부하며, 공식 문서 역시 "Docker
데몬이 Swarm 모드로 동작 중일 때는 nftables를 활성화할 수 없다"고 명확히 밝히고 있습니다. 즉 nftables
백엔드는 현재로서는 단일 호스트의 브리지 네트워크와 포트 게시 경로를 대상으로 한 기능이며, 멀티호스트
오버레이 네트워킹까지 포함하는 완전한 대체재는 아직 아닙니다. Swarm 클러스터를 운영 중이라면 오버레이
네트워크 규칙이 nftables로 이관되는 후속 릴리스를 기다려야 합니다.

### macvlan/ipvlan은 이 전환과 무관하다

14장에서 다룬 macvlan/ipvlan 드라이버는 애초에 호스트의 NAT나 포트 게시 경로를 거치지 않고 컨테이너를
물리 네트워크에 직접 연결하는 방식으로 동작합니다. 따라서 iptables든 nftables든 방화벽 백엔드가 담당하는
DNAT/필터링 규칙 자체가 이 두 드라이버의 트래픽 경로에 개입할 일이 원천적으로 없습니다. `--firewall-backend`
설정을 바꾸더라도 macvlan/ipvlan 네트워크의 동작 방식이나 필요한 설정에는 변화가 없으며, 이번 전환이 실질적으로
영향을 미치는 대상은 브리지 네트워크의 포트 게시 경로, 그리고 그 경로에 의존하는 컨테이너 격리/인바운드
정책이라는 점을 분명히 해 둘 필요가 있습니다.

## 16.4 실습으로 직접 규칙을 비교하기

이론만으로는 두 백엔드의 차이가 잘 와닿지 않으므로, 같은 컨테이너를 두고 iptables 백엔드와 nftables
백엔드가 각각 커널에 어떤 규칙을 만들어 내는지 직접 비교해 보는 것이 이해에 훨씬 도움이 됩니다. 아래
실습 섹션에서 이 과정을 순서대로 진행합니다.

## 핵심 요약

- iptables는 규칙 순회가 선형적이고 IPv4/IPv6/브리지/ARP가 별도 도구로 파편화되어 있다는 한계가 있으며,
  대부분의 현대 배포판은 이미 `iptables` 명령 자체를 nftables 위에 얹은 `iptables-nft` 호환 레이어로
  전환했다. Docker는 오랫동안 이 호환 레이어 위에서 동작해 왔다.
- nftables는 IPv4/IPv6/브리지를 단일 프레임워크로 통합하고, 커널 내 가상 머신과 세트/맵 기반 매칭으로
  대량의 동적 규칙을 iptables보다 효율적으로 처리하도록 설계되었다.
- Docker Engine 28.0.0은 iptables의 `FORWARD` 체인 우선순위 문제로 인해 게시되지 않은 포트가 컨테이너 IP로
  직접 라우팅 접근 가능했던 문제를 해결하기 위해, 게시하지 않은 포트로의 인바운드 트래픽을 기본 차단하도록
  변경했다(Linux 전용, Docker Desktop은 영향 없음). 이전 동작은 `gateway_mode_ipv4/ipv6=nat-unprotected`로
  복원할 수 있다.
- Docker Engine 29.0.0은 `--firewall-backend=nftables`(또는 daemon.json의 `"firewall-backend": "nftables"`)로
  활성화하는 실험적 네이티브 nftables 백엔드를 도입했다. Docker 전용 테이블(`ip docker-bridges`,
  `ip6 docker-bridges` 등)로 규칙을 네임스페이스 분리해 다른 방화벽 도구와의 충돌 가능성을 줄이는 방향으로
  설계되었으며, 기존 `DOCKER-USER` 훅 방식은 다른 방식(별도 테이블 + 우선순위 조정)으로 대체된다.
- 이 nftables 백엔드는 공식적으로 실험적(experimental) 단계이며 구성/동작/구현이 향후 릴리스에서 바뀔 수
  있다. Swarm 모드에서는 오버레이 네트워크 규칙이 아직 nftables로 마이그레이션되지 않아 활성화 자체가
  거부된다.
- macvlan/ipvlan은 애초에 호스트의 NAT/포트 게시 경로를 거치지 않으므로 이번 방화벽 백엔드 전환의 영향권
  밖에 있으며, 전환의 실질적 영향은 브리지 네트워크와 포트 게시 경로에 국한된다.

## 실습

다음 실습은 Docker Engine 29.x, systemd 기반 Linux 배포판, `nft`/`iptables` 도구가 설치된 환경을 전제로
합니다. 데몬 설정을 변경하므로 운영 환경이 아닌 테스트 환경에서 진행하는 것을 권장합니다.

```bash
# 1) 현재 방화벽 백엔드 확인 (기본값은 iptables)
docker info --format '{{.FirewallBackend}}'
# 확인 포인트: 아직 설정을 바꾸지 않았다면 iptables 또는 빈 값(기본 iptables 동작)이 나옵니다.
# (필드 이름은 Docker 버전에 따라 다를 수 있으므로, 없다면 `docker info | grep -i firewall`로 대체합니다.)

# 2) 컨테이너 하나를 포트 게시와 함께 실행하고 iptables 규칙 확인
docker run -d -p 18080:80 --name web-iptables nginx:latest
sudo iptables-save | grep -A 5 "DOCKER"
# 확인 포인트: nat 테이블의 DOCKER 체인에 18080 → 컨테이너 IP:80 DNAT 규칙이 보입니다.

docker rm -f web-iptables

# 3) daemon.json에 nftables 백엔드 설정 추가
sudo mkdir -p /etc/docker
cat <<'EOF' | sudo tee /etc/docker/daemon.json
{
  "firewall-backend": "nftables"
}
EOF
sudo systemctl restart docker

# 확인 포인트: 데몬이 정상적으로 재시작되는지 확인합니다(Swarm 모드가 활성화되어 있다면 이 단계에서
# 데몬이 시작에 실패하거나 오류 로그를 남길 수 있습니다. 이 경우 `docker swarm leave --force`로
# Swarm을 비활성화한 뒤 다시 시도합니다).
sudo journalctl -u docker -n 50 --no-pager | grep -i firewall

# 4) 백엔드 전환 확인
docker info --format '{{.FirewallBackend}}'
# 확인 포인트: nftables로 표시되는지 확인합니다.

# 5) 같은 컨테이너를 다시 실행하고 이번에는 nftables 규칙 확인
docker run -d -p 18080:80 --name web-nftables nginx:latest
sudo nft list table ip docker-bridges
# 확인 포인트: Docker 전용 테이블(docker-bridges) 안에 포트 18080에 대응하는 DNAT 규칙과
# 체인 구조가 iptables 때와는 별도의 네임스페이스로 구성되어 있는 것을 확인합니다.

curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:18080
# 확인 포인트: 200이 출력되어, 백엔드가 바뀌어도 실제 포트 게시 동작 자체는 동일하게 유지되는지 확인합니다.

# 6) 정리 및 원상 복구
docker rm -f web-nftables
sudo rm /etc/docker/daemon.json
sudo systemctl restart docker
docker info --format '{{.FirewallBackend}}'
# 확인 포인트: 기본값(iptables)으로 되돌아왔는지 확인합니다.
```

전반(18장)으로 이어집니다. 이 장에서 다룬 방화벽 백엔드 전환은 rootless 환경의 네트워킹 스택과는 또 다른
방식으로 얽히므로, 17장에서 RootlessKit과 사용자 네임스페이스 안에서 방화벽 규칙이 어떻게(혹은 어떤 이유로
어떻게 못) 적용되는지를 이어서 살펴보겠습니다.
