# 12장. 브리지 네트워크 심화 — veth, 방화벽, docker-proxy

11장에서는 CNM이 Network·Endpoint·Sandbox라는 세 객체로 컨테이너 네트워킹을 추상화한다는 것을 살펴봤고,
bridge 드라이버는 그 추상 모델을 리눅스 브리지와 veth pair로 구현한 것이라고 짧게 소개했습니다. 이 장은
그 구현을 실제로 뜯어봅니다. Docker를 설치하면 기본으로 만들어지는 `docker0` 브리지부터 시작해서, veth
pair가 커널 안에서 어떻게 컨테이너와 호스트를 연결하는지, 컨테이너 간 통신과 외부 통신의 경로가 어떻게
다른지, 그리고 실무에서 가장 자주 혼란을 일으키는 주제인 포트 게시(`-p`)의 내부 동작을 iptables와
docker-proxy 두 가지 메커니즘으로 나누어 다룹니다. 마지막으로 Docker Engine 28에서 바뀐 방화벽 기본
동작까지 2026년 현재 기준으로 정리합니다.

## 12.1 기본 브리지와 사용자 정의 브리지

Docker를 설치하면 별다른 설정 없이도 `docker0`이라는 리눅스 브리지 디바이스가 하나 만들어져 있습니다.
`docker run`에서 `--network`를 지정하지 않은 컨테이너는 기본적으로 이 `docker0` 브리지, 즉 CNM 상의
`bridge`라는 이름의 기본 Network에 연결됩니다. 반면 `docker network create -d bridge my-net`처럼
사용자가 직접 만든 브리지 네트워크는 흔히 "사용자 정의 브리지(user-defined bridge)"라고 부릅니다.
겉보기에는 둘 다 리눅스 브리지 디바이스라는 점에서 동일하지만, 실무에 영향을 주는 중요한 차이가 하나
있습니다.

기본 브리지 네트워크는 컨테이너 사이의 자동 DNS 해석을 지원하지 않습니다. 기본 브리지에 연결된 두
컨테이너는 서로의 이름으로 통신할 수 없고, `--link` 같은 레거시 옵션을 쓰거나 IP 주소를 직접 알아내야
했습니다. 반면 사용자 정의 브리지 네트워크에서는 같은 네트워크에 연결된 컨테이너들이 컨테이너 이름(또는
`--network-alias`로 지정한 별칭)을 그대로 호스트 이름처럼 사용해 서로를 찾을 수 있습니다. 이는 Docker가
사용자 정의 네트워크마다 내장 DNS 서버(embedded DNS)를 자동으로 구동하고, 각 컨테이너의
`/etc/resolv.conf`가 그 내장 DNS를 가리키도록 구성하기 때문입니다. 이 내장 DNS 서버의 정확한 동작
방식과 이름 해석 규칙은 15장(DNS와 서비스 디스커버리)에서 자세히 다루므로, 이 장에서는 "기본 브리지는
DNS 기반 자동 탐색이 없고, 사용자 정의 브리지는 있다"는 실무적 차이만 기억해 두면 충분합니다.

이 차이 때문에 실무 가이드에서는 거의 예외 없이 기본 브리지 네트워크를 그대로 쓰지 말고 프로젝트마다
사용자 정의 브리지 네트워크를 만들어 쓰라고 권합니다. Docker Compose가 프로젝트마다 자동으로 전용
네트워크를 만들어주는 것도 같은 이유입니다. 추가로 사용자 정의 브리지는 네트워크 간 격리도 더
명시적입니다. 기본 브리지에 연결된 모든 컨테이너는 별다른 조치가 없는 한 서로 통신이 가능한 하나의
평평한(flat) 공간에 놓이지만, 서로 다른 사용자 정의 브리지 네트워크에 속한 컨테이너들은 명시적으로
`docker network connect`로 연결하지 않는 한 기본적으로 서로 격리됩니다.

## 12.2 veth pair — 컨테이너와 호스트를 잇는 가상 케이블

브리지 네트워크에서 컨테이너 하나가 네트워크에 연결될 때 핵심이 되는 커널 오브젝트가 veth
(virtual ethernet) pair입니다. veth pair는 이름 그대로 항상 쌍으로 생성되는 가상 네트워크 인터페이스로,
한쪽 끝으로 들어간 패킷이 마치 물리적인 케이블로 연결된 것처럼 다른 쪽 끝으로 그대로 나옵니다. Docker는
컨테이너를 브리지 네트워크에 연결할 때 이 veth pair를 하나 만들어서, 한쪽 끝은 컨테이너의 네트워크
네임스페이스 안으로 옮겨 넣고(이 끝이 컨테이너 안에서는 `eth0`으로 보입니다), 다른 쪽 끝은 호스트의
기본 네임스페이스에 남겨둔 채 브리지 디바이스에 연결합니다.

이 구조를 그림으로 표현하면 다음과 같습니다.

```
[ 호스트 네트워크 네임스페이스 ]                [ 컨테이너 네트워크 네임스페이스 ]
                                                (2장에서 다룬 net ns)
   docker0 (브리지)
       │
       ├── vethXXXXXXX@if5  ◄──── veth pair ────►  eth0@if6
       │   (호스트 쪽 끝, 브리지에 연결)               (컨테이너 쪽 끝, CNM의 Endpoint)
       │
       └── vethYYYYYYY@if7  ◄──── veth pair ────►  eth0@if8  (다른 컨테이너)
```

11장에서 설명한 CNM 용어로 옮기면, 컨테이너 쪽 veth 끝(`eth0`)이 바로 Endpoint이고, 호스트 쪽 veth
끝(`vethXXXXXXX`)이 브리지라는 Network 실체에 연결되는 접점입니다. 이 veth pair 관계는 실제 리눅스
명령으로 직접 확인할 수 있습니다.

```bash
# 컨테이너 안에서 인터페이스 번호 확인
docker exec web ip link show eth0
# 예: 6: eth0@if7: <BROADCAST,MULTICAST,UP,LOWER_UP> ...

# 호스트에서 브리지에 연결된 veth 목록 확인
ip link show type veth
bridge link show
```

`ip link show eth0`의 출력에서 `eth0@if7`처럼 `@if` 뒤에 붙는 숫자는 veth pair의 반대쪽 끝이 호스트
네임스페이스에서 갖는 인터페이스 인덱스 번호입니다. 호스트에서 `ip link show`로 같은 인덱스 번호를 가진
인터페이스를 찾으면 그것이 바로 이 컨테이너와 짝을 이루는 veth의 호스트 쪽 끝입니다. 전통적으로는
`brctl show docker0` 명령으로 브리지에 연결된 veth 목록을 확인했지만, `brctl`은 오래된 `bridge-utils`
패키지에 속한 도구로 최근 배포판에서는 기본 설치되지 않는 경우가 많습니다. 요즘은 iproute2에 포함된
`bridge link show` 또는 `bridge fdb show br docker0`으로 동일한 정보를 확인하는 것이 일반적입니다.

## 12.3 통신 경로의 차이 — 컨테이너 간 vs 외부

같은 브리지 네트워크에 속한 두 컨테이너가 통신할 때와, 컨테이너가 외부 네트워크(인터넷 등)와 통신할 때
패킷이 지나는 경로는 근본적으로 다릅니다.

같은 브리지 안에 있는 두 컨테이너 사이의 통신은 순수한 L2 스위칭입니다. 컨테이너 A가 컨테이너 B의 IP로
패킷을 보내면, 그 패킷은 veth pair를 통해 `docker0` 브리지로 들어오고, 브리지는 자신이 학습한 MAC
주소 테이블(FDB, Forwarding Database)을 참고해 해당 프레임을 컨테이너 B의 veth 쪽으로 그대로
전달합니다. 이 경로에는 라우팅도, NAT도 개입하지 않습니다. 리눅스 브리지가 하는 일은 물리적인 이더넷
스위치가 하는 일과 개념적으로 동일합니다. 즉 같은 네트워크 안에서는 IP 계층보다 아래인 L2 계층에서
통신이 끝나 버립니다.

반면 컨테이너가 외부(인터넷이나 같은 호스트 바깥의 다른 네트워크)로 나가는 통신은 전혀 다른 경로를
탑니다. 목적지가 같은 브리지 대역 밖에 있으므로, 패킷은 브리지 자체가 아니라 컨테이너의 라우팅
테이블(기본 게이트웨이가 브리지의 IP, 예를 들어 `docker0`의 172.17.0.1)을 거쳐 리눅스 커널의 IP
포워딩 경로로 올라갑니다. 이때 호스트에는 Docker가 만들어 둔 `iptables`의 `nat` 테이블 `POSTROUTING`
체인에 마스커레이딩(MASQUERADE) 규칙이 들어 있어서, 브리지 대역에서 나가는 패킷의 출발지 IP가 호스트의
외부 인터페이스 IP로 치환됩니다. 이것이 바로 아웃바운드 NAT입니다. 정리하면 같은 브리지 내부 통신은
"스위칭"이고, 외부로 나가는 통신은 "라우팅 + NAT"라는 완전히 다른 계층의 동작입니다.

```bash
# Docker가 만들어 둔 마스커레이딩 규칙 확인
iptables -t nat -L POSTROUTING -n -v | grep -i MASQUERADE
```

## 12.4 포트 게시(`-p`)의 내부 동작 — iptables DNAT와 docker-proxy

브리지 네트워크에서 실무적으로 가장 많이 부딪히는 주제가 포트 게시입니다. `docker run -p 8080:80
nginx`처럼 호스트 포트를 컨테이너 포트에 연결하면, 호스트의 8080번으로 들어온 트래픽이 컨테이너의 80번
포트로 전달됩니다. 이 동작은 사실 두 개의 서로 다른 메커니즘이 함께 작동해서 만들어지는 결과입니다.

첫 번째는 iptables DNAT(Destination NAT) 규칙입니다. Docker는 컨테이너를 포트 게시와 함께 실행할 때
`nat` 테이블 안에 `DOCKER`라는 체인을 만들고(정확히는 최초 실행 시 만들어 둔 체인을 재사용), 그 체인에
"호스트의 8080번 포트로 들어오는 패킷의 목적지를 컨테이너의 IP:80으로 바꿔라"는 DNAT 규칙을 추가합니다.
`PREROUTING` 체인이 `DOCKER` 체인으로 점프하도록 연결되어 있어서, 호스트로 들어오는 모든 패킷은 라우팅
결정을 내리기 전에 먼저 이 DNAT 규칙을 거치게 됩니다. 이 경로로 도착한 패킷은 목적지가 컨테이너의 IP로
바뀐 채 `FORWARD` 체인을 거쳐 브리지를 통해 실제로 컨테이너 안으로 들어갑니다. 즉 커널 수준에서만
처리되는, 별도의 사용자 공간 프로세스가 개입하지 않는 순수한 NAT 경로입니다.

두 번째는 `docker-proxy`라는 별도의 사용자 공간(userland) 프로세스입니다. 포트를 게시할 때마다
dockerd는 호스트의 게시 포트를 직접 bind해서 리스닝하는 `docker-proxy` 프로세스를 하나씩 띄웁니다. 이
프로세스는 호스트 포트로 들어온 연결을 받아 컨테이너의 IP:포트로 그대로 중계(relay)하는 단순한 TCP/UDP
프록시입니다. 얼핏 보면 iptables DNAT만으로 충분한데 왜 이런 프로세스가 별도로 필요한가 싶지만,
`docker-proxy`는 순수 커널 NAT 경로만으로는 깔끔하게 처리되지 않는 몇 가지 상황을 보완하기 위해
존재합니다. 대표적으로 호스트 자신이 루프백(`127.0.0.1`)을 통해 자신이 게시한 포트로 접속하는 경우
(hairpin NAT라고 부르는 상황)나, 특정 네트워크 구성에서 IPv6 처리가 얽히는 경우처럼, DNAT 규칙만으로는
왕복 경로가 깔끔하게 완성되지 않는 케이스들이 있습니다. `docker-proxy`는 이런 경우에도 항상 사용자
공간에서 연결을 중계함으로써 일관되게 동작하도록 만드는 안전판 역할을 합니다.

이 이중 구조는 `--userland-proxy` 데몬 옵션으로 제어할 수 있습니다. 기본값은 활성화(`true`)이며,
`/etc/docker/daemon.json`에 다음과 같이 설정해서 끌 수 있습니다.

```json
{
  "userland-proxy": false
}
```

```bash
# 설정 반영 후 데몬 재시작
sudo systemctl restart docker
```

`--userland-proxy=false`로 설정하면 `docker-proxy` 프로세스가 더 이상 뜨지 않고, 포트 게시는 오직
iptables(또는 nftables) 기반의 커널 NAT 경로만으로 처리됩니다. 대부분의 표준적인 사용 패턴에서는 이
설정으로도 문제없이 동작하며, 호스트당 게시 포트 수가 많은 환경에서는 `docker-proxy` 프로세스 수를
줄여 리소스를 절약할 수 있다는 장점이 있습니다. 다만 위에서 언급한 hairpin NAT류의 특수한 시나리오에서
차이가 발생할 수 있으므로, 이 옵션을 끄기 전에는 자신의 환경에서 실제로 필요한 접근 경로(특히 호스트
자신의 루프백을 통한 접근이 필요한지)를 점검해 보는 것이 안전합니다.

```bash
# 현재 떠 있는 docker-proxy 프로세스와 게시 포트의 대응 확인
ps -ef | grep docker-proxy | grep -v grep
# 예: docker-proxy -proto tcp -host-ip 0.0.0.0 -host-port 8080 -container-ip 172.17.0.2 -container-port 80
```

## 12.5 2026년 현재 — 게시되지 않은 포트의 기본 차단과 남은 주의점

브리지 네트워크와 iptables를 함께 이야기할 때 오랫동안 따라다닌 유명한 문제가 있습니다. Docker가
컨테이너의 포트를 게시하면서 iptables의 `FORWARD` 체인에 직접 규칙을 끼워 넣다 보니, 관리자가
`ufw`나 `firewalld` 같은 호스트 방화벽 도구로 아무리 인바운드 규칙을 걸어 두어도 Docker가 만든 규칙이
그보다 먼저 평가되어 방화벽 정책을 사실상 우회해 버리는 문제였습니다. 관리자 입장에서는 `ufw deny`로
분명히 막아 둔 포트인데도 컨테이너가 그 포트를 게시하는 순간 외부에서 접근이 가능해지는, 직관에
어긋나는 상황이 반복적으로 보고되었습니다.

Docker Engine 28부터는 이 문제를 상당 부분 완화하는 방향으로 기본 동작이 바뀌었습니다. 게시하지 않은
포트로 향하는, 즉 명시적으로 `-p`나 `--publish`로 열어주지 않은 컨테이너의 포트로 들어오는 인바운드
트래픽을 컨테이너 IP 기준으로 기본 차단하도록 변경된 것입니다. 이 동작은 iptables 기반으로 구현되어
있으며 리눅스 환경에 한정되고, VM 계층을 통해 네트워킹이 이루어지는 Docker Desktop(macOS/Windows)에는
해당 사항이 없습니다. 이 변화 덕분에 "게시하지 않은 포트인데도 컨테이너의 IP를 직접 알면 LAN에서 접근이
가능하다"는 식의 사고가 크게 줄었습니다. 이전에는 게시하지 않은 포트라도 같은 브리지 대역에 도달할 수
있는 경로(같은 LAN, 또는 컨테이너 IP를 직접 아는 내부 사용자)만 있으면 사실상 열려 있는 것과 마찬가지인
경우가 많았는데, 이제는 게시 여부가 방화벽 레벨에서도 실제로 의미를 갖게 되었습니다.

다만 이 변화가 "Docker와 호스트 방화벽 사이의 상호작용 문제 전체"를 완전히 해소한 것은 아니라는 점은
분명히 해 둘 필요가 있습니다. Docker가 여전히 `FORWARD` 체인 등 호스트 방화벽 도구가 관리하는 것과
같은 iptables 테이블에 자신의 규칙을 직접 삽입하는 구조 자체는 유지되고 있고, 게시된 포트에 대해서는
여전히 Docker의 규칙이 우선 적용됩니다. 즉 "게시하지 않은 포트가 기본적으로 안전해졌다"는 것이지,
"Docker가 호스트의 방화벽 규칙 체계에 완전히 순응하게 되었다"는 의미는 아닙니다. 이 상호작용 문제를
구조적으로 다시 설계하려는 시도가 Docker Engine 29의 실험적 nftables 방화벽 백엔드이며, iptables
테이블에 직접 규칙을 끼워 넣는 대신 Docker 전용 nftables 체인을 별도로 구성해 호스트 방화벽 도구와의
충돌 가능성을 줄이는 방향을 지향합니다. 이 nftables 전환의 구체적인 구조와 현재의 제약(Swarm 모드
미지원 등)은 16장(방화벽 백엔드의 전환)에서 별도의 장을 할애해 자세히 다룹니다.

## 12.6 실제 규칙을 눈으로 확인하기

Docker가 만든 iptables 규칙은 추상적으로 설명을 듣기보다 직접 눈으로 보는 편이 훨씬 이해가 빠릅니다.
포트를 게시한 컨테이너를 하나 띄운 뒤, `iptables-save`로 전체 규칙을 텍스트로 덤프해서 Docker가 만든
부분을 찾아보겠습니다.

```bash
docker run -d --name web -p 8080:80 nginx:latest

# nat 테이블 전체를 텍스트로 덤프
iptables-save -t nat | grep -i docker
```

출력에는 `DOCKER`라는 체인이 정의되어 있고, 그 안에 `-p tcp --dport 8080 -j DNAT --to-destination
172.17.0.2:80`과 비슷한 규칙이 보일 것입니다. `PREROUTING` 체인과 (호스트 자신에서 접속하는 경우를
위한) `OUTPUT` 체인 양쪽에서 이 `DOCKER` 체인으로 점프하는 규칙도 함께 확인할 수 있습니다.

nftables가 설치되어 있고 iptables가 nftables 백엔드(iptables-nft)로 동작하는 배포판이라면, 같은 규칙을
`nft` 명령으로도 조회할 수 있습니다.

```bash
nft list ruleset | grep -A 5 -i docker
```

`--firewall-backend=nftables`로 Docker 자체의 실험적 nftables 백엔드를 켠 환경이라면, 여기서 보이는
규칙의 구조 자체가 지금까지 설명한 `iptables`/`DOCKER` 체인 방식과는 다른 형태(Docker 전용 네임스페이스로
분리된 테이블)로 나타납니다. 이 차이는 16장에서 실제 출력 예시와 함께 비교합니다.

## 핵심 요약

- 기본 브리지(`docker0`)는 컨테이너 간 자동 DNS 해석을 지원하지 않는 반면, 사용자 정의 브리지 네트워크는
  내장 DNS를 통해 컨테이너 이름으로 서로를 찾을 수 있다. 실무에서는 사용자 정의 브리지를 쓰는 것이
  권장된다.
- veth pair는 컨테이너 쪽(`eth0`, CNM의 Endpoint)과 호스트 쪽(`vethXXXXXXX`, 브리지에 연결)이 커널
  안에서 짝을 이루는 가상 인터페이스이며, `ip link`의 `@if` 번호와 `bridge link show`로 그 대응 관계를
  직접 확인할 수 있다.
- 같은 브리지 안의 컨테이너 간 통신은 L2 스위칭으로 처리되고, 외부로 나가는 통신은 라우팅과 NAT
  (마스커레이딩)를 거친다. 두 경로는 계층이 다르다.
- 포트 게시는 iptables `DOCKER` 체인의 DNAT 규칙(커널 경로)과 `docker-proxy` 사용자 공간 프로세스
  (hairpin NAT 등 보완용) 두 메커니즘이 함께 작동한 결과다. `--userland-proxy=false`로 후자를 끄면
  순수 커널 NAT 경로만 남는다.
- Docker Engine 28부터 게시하지 않은 포트로의 인바운드 트래픽이 컨테이너 IP 기준으로 기본 차단되도록
  바뀌어, "Docker가 호스트 방화벽을 우회한다"는 오래된 문제가 크게 완화되었다. 다만 게시된 포트에 대한
  Docker 자체 규칙의 우선순위 문제는 여전히 남아 있으며, 이는 16장에서 다룰 nftables 전환의 배경이 된다.

## 실습

```bash
# 1) 포트를 게시한 컨테이너 실행
docker run -d --name web -p 8080:80 nginx:latest

# 2) veth pair 대응 관계 확인
docker exec web ip link show eth0
# 출력에서 "eth0@ifN"의 N 값을 기록해 둡니다.
ip -all link show | grep -B1 "veth"
# 확인 포인트: 호스트 쪽 veth 인터페이스 중 하나가 "@ifN"으로 같은 번호를 가리키는지 확인합니다.

# 3) 브리지에 연결된 veth 목록 확인
bridge link show
# 확인 포인트: docker0(또는 사용자 정의 브리지)에 연결된 veth 항목들이 나열되는지 확인합니다.

# 4) iptables DNAT 규칙 확인
iptables-save -t nat | grep -i docker
# 확인 포인트: "--dport 8080"과 "DNAT --to-destination <컨테이너IP>:80" 규칙이 보이는지 확인합니다.

# 5) docker-proxy 프로세스 확인
ps -ef | grep docker-proxy | grep -v grep
# 확인 포인트: -host-port 8080, -container-port 80 인자가 매칭되는지 확인합니다.

# 6) userland-proxy를 끄고 다시 확인
sudo tee /etc/docker/daemon.json > /dev/null <<'EOF'
{
  "userland-proxy": false
}
EOF
sudo systemctl restart docker
docker run -d --name web2 -p 8081:80 nginx:latest
ps -ef | grep docker-proxy | grep -v grep
# 확인 포인트: web2에 대한 docker-proxy 프로세스가 뜨지 않지만, curl 등으로 접속은
# 여전히 정상 동작하는지 확인합니다.
curl -sI http://localhost:8081 | head -1

# 7) 정리
docker rm -f web web2
```

다음 장에서는 단일 호스트를 벗어나 여러 호스트에 걸친 컨테이너 통신을 다룹니다. 브리지만으로는 해결할
수 없는 이 문제를 오버레이 네트워크와 VXLAN이 어떻게 풀어내는지, 그리고 Swarm 모드가 그 위에서 어떻게
서비스 라우팅 메시를 구성하는지 살펴봅니다.
