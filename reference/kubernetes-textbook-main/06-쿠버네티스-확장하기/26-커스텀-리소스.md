# 26장. 커스텀 리소스

> **학습목표**
> - CRD를 정의하고 클러스터에 등록할 수 있다.
> - OpenAPI v3 스키마로 필드를 검증하고 기본값을 줄 수 있다.
> - status와 scale 서브리소스의 효과를 설명하고 적용할 수 있다.
> - printer columns, 짧은 이름 등으로 사용성을 높일 수 있다.
> - CRD를 버저닝하고 변환 웹훅으로 마이그레이션할 수 있다.
> - 좋은 API를 설계하는 원칙을 적용할 수 있다.

---

## 들어가며

25장에서 컨트롤러를 만들었지만 내장 리소스(Pod)만 다뤘다. 이제 **새로운 리소스 종류**를 정의한다.

24.1절의 예시를 다시 가져온다.

```yaml
apiVersion: db.example.com/v1
kind: PostgresCluster
metadata:
  name: orders-db
spec:
  version: "16.2"
  replicas: 3
```

이런 것을 만드는 것이 이 장의 목표다.

## 26.1 CRD 기본

### 가장 단순한 형태

```yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  # ★ 반드시 <plural>.<group> 형식이어야 한다
  name: widgets.example.com
spec:
  group: example.com
  scope: Namespaced              # 또는 Cluster
  names:
    plural: widgets              # URL에 쓰인다: /apis/example.com/v1/widgets
    singular: widget
    kind: Widget                 # Go 타입 이름, YAML의 kind
    listKind: WidgetList
    shortNames: [wg]             # kubectl get wg
    categories: [all]            # kubectl get all 에 포함
  versions:
    - name: v1
      served: true               # 이 버전으로 API 제공
      storage: true              # ★ etcd에 이 버전으로 저장 (정확히 하나만 true)
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              properties:
                size:
                  type: integer
```

```bash
kubectl apply -f widget-crd.yaml
kubectl get crd widgets.example.com
kubectl api-resources --api-group=example.com
```

**이제 새 리소스를 쓸 수 있다.**

```yaml
apiVersion: example.com/v1
kind: Widget
metadata:
  name: my-widget
spec:
  size: 3
```

```bash
kubectl apply -f widget.yaml
kubectl get widgets
kubectl get wg                     # 짧은 이름
kubectl describe widget my-widget
kubectl explain widget.spec        # ★ 스키마가 곧 문서다 (4.6절)
```

**컨트롤러가 없어도 저장과 조회는 동작한다.** CRD를 단순한 설정 저장소로 쓸 수도 있다.

### 등록 확인

```bash
kubectl get crd widgets.example.com -o jsonpath='{.status.conditions}' | jq
```
```json
[
  { "type": "NamesAccepted", "status": "True" },
  { "type": "Established",   "status": "True" }
]
```

**`Established=True`가 되어야 사용 가능하다.** 이름 충돌이 있으면 `NamesAccepted=False`가 된다.

### 삭제 시 주의

```bash
kubectl delete crd widgets.example.com
```

> **⚠️ CRD를 삭제하면 그 타입의 모든 커스텀 리소스가 삭제된다**
> 되돌릴 수 없다. 프로덕션에서는 CRD 삭제를 정책으로 막는 것이 좋다(18.6절).
>
> 파이널라이저가 붙은 CR이 있으면 삭제가 멈춘다(4.2절). 컨트롤러가 이미 제거된 상태라면 파이널라이저를 제거해 줄 주체가 없어 영원히 `Terminating`에 남는다. **오퍼레이터를 제거할 때는 CR을 먼저 정리하고 CRD를 나중에 지운다.**

## 26.2 OpenAPI v3 스키마

### 왜 중요한가

스키마는 세 가지 역할을 한다.

1. **검증** — 잘못된 필드나 값을 API 서버가 거부한다
2. **문서** — `kubectl explain`이 이것을 읽는다
3. **프루닝** — 스키마에 없는 필드는 **조용히 제거된다**

세 번째가 특히 중요하다.

```yaml
spec:
  size: 3
  unknownField: "hello"      # 스키마에 없으면 저장되지 않는다
```

> **⚠️ 프루닝은 조용하다**
> 에러도 경고도 없이 필드가 사라진다. 오타가 있으면 설정이 무시된 채 동작한다. **스키마를 정확히 정의하는 것이 그래서 중요하다.**
>
> `x-kubernetes-preserve-unknown-fields: true`로 프루닝을 끌 수 있지만, 검증도 함께 포기하는 것이라 권장되지 않는다.

### 상세한 스키마 예제

```yaml
versions:
  - name: v1
    served: true
    storage: true
    schema:
      openAPIV3Schema:
        type: object
        required: [spec]
        properties:
          spec:
            type: object
            required: [image, replicas]
            properties:
              # --- 문자열 ---
              image:
                type: string
                description: "컨테이너 이미지 (태그 필수)"
                minLength: 1
                maxLength: 253
                pattern: '^[a-z0-9.\-/]+:[a-zA-Z0-9._\-]+$'

              # --- 열거형 ---
              tier:
                type: string
                enum: [dev, staging, production]
                default: dev

              # --- 정수 ---
              replicas:
                type: integer
                minimum: 1
                maximum: 100
                default: 1

              # --- 리소스 수량 ---
              storage:
                type: string
                pattern: '^[0-9]+(\.[0-9]+)?(Ki|Mi|Gi|Ti|K|M|G|T)?$'
                default: "10Gi"

              # --- 불리언 ---
              enabled:
                type: boolean
                default: true

              # --- 중첩 객체 ---
              backup:
                type: object
                properties:
                  schedule:
                    type: string
                    pattern: '^(@(annually|yearly|monthly|weekly|daily|hourly))|((\*|[0-9,\-*/]+)\s+){4}(\*|[0-9,\-*/]+)$'
                  retentionDays:
                    type: integer
                    minimum: 1
                    default: 7
                  destination:
                    type: string
                    format: uri

              # --- 배열 ---
              env:
                type: array
                maxItems: 50
                items:
                  type: object
                  required: [name]
                  properties:
                    name:  { type: string }
                    value: { type: string }
                # ★ 배열 병합 전략 (Server-Side Apply, 25.3절)
                x-kubernetes-list-type: map
                x-kubernetes-list-map-keys: [name]

              # --- 임의 형식 (검증 없음) ---
              podTemplate:
                type: object
                x-kubernetes-preserve-unknown-fields: true

              # --- 변경 불가 필드 ---
              storageClass:
                type: string
                x-kubernetes-validations:
                  - rule: "self == oldSelf"
                    message: "storageClass는 생성 후 변경할 수 없습니다"

            # --- 필드 간 검증 (CEL) ---
            x-kubernetes-validations:
              - rule: "!has(self.backup) || has(self.backup.destination)"
                message: "backup을 설정하면 destination이 필요합니다"
              - rule: "self.tier != 'production' || self.replicas >= 3"
                message: "production 티어는 replicas가 3 이상이어야 합니다"

          status:
            type: object
            properties:
              phase:
                type: string
              readyReplicas:
                type: integer
              observedGeneration:
                type: integer
                format: int64
              conditions:
                type: array
                items:
                  type: object
                  required: [type, status]
                  properties:
                    type:               { type: string }
                    status:             { type: string, enum: ["True","False","Unknown"] }
                    reason:             { type: string }
                    message:            { type: string }
                    lastTransitionTime: { type: string, format: date-time }
                    observedGeneration: { type: integer, format: int64 }
                x-kubernetes-list-type: map
                x-kubernetes-list-map-keys: [type]
```

### 기본값 (defaulting)

```yaml
tier:
  type: string
  enum: [dev, staging, production]
  default: dev
```

**어드미션 단계에서 주입된다**(17.5절의 Mutating). 13.3절의 LimitRange가 하는 일과 같은 방식이다.

```bash
kubectl apply -f - <<EOF
apiVersion: example.com/v1
kind: Widget
metadata: { name: w1 }
spec:
  image: nginx:alpine
  replicas: 2
EOF

kubectl get widget w1 -o jsonpath='{.spec.tier}'
# dev          ← 기본값이 들어갔다
```

### CEL 검증 규칙

v1.29에서 GA된 기능이다. **웹훅 없이 복잡한 검증**을 할 수 있다.

```yaml
x-kubernetes-validations:
  # 불변 필드
  - rule: "self == oldSelf"
    message: "변경할 수 없습니다"

  # 조건부 필수
  - rule: "!has(self.tls) || has(self.tls.secretName)"
    message: "tls를 켜면 secretName이 필요합니다"

  # 필드 간 관계
  - rule: "self.minReplicas <= self.maxReplicas"
    message: "minReplicas는 maxReplicas 이하여야 합니다"

  # 리스트 검증
  - rule: "self.ports.all(p, p.port > 0 && p.port < 65536)"
    message: "포트는 1~65535 범위여야 합니다"

  # 중복 방지
  - rule: "self.env.map(e, e.name).size() == self.env.size()"
    message: "환경변수 이름이 중복됩니다"

  # 비용 제한이 있는 경우 명시
  - rule: "size(self.items) < 100"
    messageExpression: "'items는 100개 미만이어야 합니다. 현재: ' + string(size(self.items))"
```

**`oldSelf`는 업데이트 시에만 사용 가능하다.** 생성 시에는 규칙이 건너뛰어진다.

> **CEL이 웹훅을 대체한다**
> 예전에는 이런 검증을 위해 Validating Webhook을 만들어야 했다(28장). 웹훅 서버의 가용성이 곧 클러스터의 가용성이 되는 위험이 있었다.
>
> **CEL로 표현 가능한 검증은 CEL로 하는 것이 훨씬 안전하다.** 외부 시스템 조회가 필요한 경우에만 웹훅을 쓴다.

## 26.3 서브리소스

### status 서브리소스

```yaml
versions:
  - name: v1
    served: true
    storage: true
    subresources:
      status: {}          # ★ 이 한 줄
```

**효과가 크다.**

**① 별도 엔드포인트가 생긴다**

```
/apis/example.com/v1/namespaces/default/widgets/w1
/apis/example.com/v1/namespaces/default/widgets/w1/status
```

**② spec과 status의 쓰기가 분리된다**

```
메인 리소스에 쓰기 → status 필드는 무시된다
status 서브리소스에 쓰기 → spec 필드는 무시된다
```

**사용자가 실수로 status를 덮어쓸 수 없고, 컨트롤러가 실수로 spec을 바꿀 수 없다.** 4.2절에서 말한 원칙이 강제된다.

**③ RBAC을 분리할 수 있다**(17.3절)

```yaml
rules:
  # 사용자: spec만 수정
  - apiGroups: ["example.com"]
    resources: ["widgets"]
    verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
  # 컨트롤러: status만 수정
  - apiGroups: ["example.com"]
    resources: ["widgets/status"]
    verbs: ["get", "update", "patch"]
```

**④ `metadata.generation`이 자동 증가한다**

```
spec을 수정 → generation++
status를 수정 → generation 그대로
```

4.2절에서 본 `generation`과 `observedGeneration` 비교가 가능해진다.

```go
// 컨트롤러에서
if widget.Status.ObservedGeneration == widget.Generation {
    // 이미 최신 spec을 반영했다
}
```

**status 업데이트 코드**

```go
// 메인 리소스 업데이트가 아니다
_, err := client.Widgets(ns).UpdateStatus(ctx, widget, metav1.UpdateOptions{})

// controller-runtime에서는
err := r.Status().Update(ctx, widget)
```

### scale 서브리소스

```yaml
subresources:
  status: {}
  scale:
    specReplicasPath: .spec.replicas
    statusReplicasPath: .status.readyReplicas
    labelSelectorPath: .status.selector      # HPA에 필요
```

**효과**

```bash
kubectl scale widget w1 --replicas=5        # ★ 동작한다!
kubectl get widget w1 -o jsonpath='{.spec.replicas}'
```

**HPA를 붙일 수 있다**(16.2절).

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: widget-hpa
spec:
  scaleTargetRef:
    apiVersion: example.com/v1
    kind: Widget                # ★ 커스텀 리소스
    name: w1
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 70 }
```

**HPA는 `/scale` 엔드포인트만 알면 되므로 리소스 종류를 몰라도 된다.** 4.1절에서 말한 서브리소스의 가치가 여기서 드러난다.

**`labelSelectorPath`가 필요한 이유**: HPA가 어떤 Pod의 메트릭을 봐야 할지 알려면 셀렉터가 필요하다. 컨트롤러가 status에 이 값을 채워야 한다.

```go
widget.Status.Selector = "app=widget,instance=" + widget.Name
```

## 26.4 사용성 개선

### Printer Columns

```yaml
versions:
  - name: v1
    additionalPrinterColumns:
      - name: Image
        type: string
        jsonPath: .spec.image
      - name: Desired
        type: integer
        jsonPath: .spec.replicas
      - name: Ready
        type: integer
        jsonPath: .status.readyReplicas
      - name: Phase
        type: string
        jsonPath: .status.phase
      - name: Age
        type: date
        jsonPath: .metadata.creationTimestamp
      - name: Message
        type: string
        priority: 1                       # ★ -o wide 에서만 표시
        jsonPath: .status.conditions[?(@.type=="Ready")].message
```

```bash
kubectl get widgets
```
```
NAME   IMAGE          DESIRED   READY   PHASE     AGE
w1     nginx:alpine   3         3       Running   5m
```

**좋은 printer column이 오퍼레이터의 사용성을 크게 좌우한다.** 사용자가 `kubectl get`만으로 상태를 파악할 수 있어야 한다.

### 카테고리와 짧은 이름

```yaml
names:
  shortNames: [wg, wgt]
  categories: [all, example]
```

```bash
kubectl get wg
kubectl get all                # widgets도 포함된다
kubectl get example            # 이 카테고리의 모든 리소스
```

### 필드 셀렉터

v1.31부터 커스텀 리소스에도 필드 셀렉터를 쓸 수 있다.

```yaml

  - name: v1
    selectableFields:
      - jsonPath: .spec.tier

```

```bash
kubectl get widgets --field-selector spec.tier=production
```

## 26.5 버저닝과 변환

### 왜 필요한가

API는 진화한다. 처음 설계가 완벽할 수 없다.

```
v1alpha1: spec.size
    ↓ 이름이 모호하다
v1beta1:  spec.replicas
    ↓ 구조를 개선한다
v1:       spec.replicas, spec.resources.storage
```

**기존 사용자의 매니페스트를 깨뜨리지 않으면서** 바꿔야 한다.

### 여러 버전 제공

```yaml
spec:
  versions:
    - name: v1alpha1
      served: true          # 아직 제공
      storage: false
      deprecated: true      # ★ 사용 시 경고
      deprecationWarning: "example.com/v1alpha1 Widget은 폐기 예정입니다. example.com/v1을 사용하세요."
      schema: { ... }

    - name: v1beta1
      served: true
      storage: false
      schema: { ... }

    - name: v1
      served: true
      storage: true         # ★ etcd에 이 버전으로 저장
      schema: { ... }
```

```bash
kubectl apply -f old-widget.yaml
# Warning: example.com/v1alpha1 Widget은 폐기 예정입니다...
```

### 변환 전략

**① None — 필드 이름이 같을 때**

```yaml
spec:
  conversion:
    strategy: None
```

apiVersion만 바꾸고 나머지는 그대로 반환한다. **필드 추가/제거만 있는 경우**에 쓸 수 있다.

**② Webhook — 실제 변환이 필요할 때**

```yaml
spec:
  conversion:
    strategy: Webhook
    webhook:
      conversionReviewVersions: ["v1"]
      clientConfig:
        service:
          namespace: my-operator-system
          name: my-operator-webhook
          path: /convert
          port: 443
        caBundle: <base64 인코딩된 CA 인증서>
```

### 변환 웹훅 구현

21.1절에서 본 **허브 모델**을 그대로 쓴다.

```
v1alpha1 ──┐
           ├──→ v1 (허브) ──→ etcd
v1beta1 ───┘
```

```go
// 허브 버전 선언 (controller-runtime)
// api/v1/widget_types.go
func (*Widget) Hub() {}

// api/v1beta1/widget_conversion.go
func (src *Widget) ConvertTo(dstRaw conversion.Hub) error {
    dst := dstRaw.(*v1.Widget)

    dst.ObjectMeta = src.ObjectMeta
    dst.Spec.Image = src.Spec.Image
    dst.Spec.Replicas = src.Spec.Replicas

    // v1beta1의 spec.storageSize → v1의 spec.resources.storage
    dst.Spec.Resources = v1.ResourceSpec{
        Storage: src.Spec.StorageSize,
    }

    dst.Status.Phase = src.Status.Phase
    return nil
}

func (dst *Widget) ConvertFrom(srcRaw conversion.Hub) error {
    src := srcRaw.(*v1.Widget)

    dst.ObjectMeta = src.ObjectMeta
    dst.Spec.Image = src.Spec.Image
    dst.Spec.Replicas = src.Spec.Replicas
    dst.Spec.StorageSize = src.Spec.Resources.Storage
    dst.Status.Phase = src.Status.Phase
    return nil
}
```

> **⚠️ 변환은 손실이 없어야 한다**
> v1beta1 → v1 → v1beta1 왕복 후 원본과 같아야 한다. 새 버전에만 있는 필드는 **애노테이션에 보존**하는 기법을 쓴다.
> ```go
> // v1 → v1beta1 변환 시 잃어버릴 필드를 보존
> data, _ := json.Marshal(src.Spec.NewField)
> dst.Annotations["conversion.example.com/newField"] = string(data)
> ```

### 스토리지 버전 마이그레이션

**저장된 오브젝트는 옛 버전 그대로다.** 스토리지 버전을 v1으로 바꿔도, 이미 v1beta1로 저장된 것은 그대로 남는다.

```bash
# 어떤 버전으로 저장되어 있는지 확인
kubectl get crd widgets.example.com -o jsonpath='{.status.storedVersions}'
# ["v1beta1","v1"]
```

**모두 v1으로 옮기려면 다시 써야 한다**(22.6절의 재암호화와 같은 원리).

```bash
# ① 모든 오브젝트를 다시 쓴다
kubectl get widgets -A -o json | kubectl replace -f -

# ② storedVersions에서 옛 버전 제거
kubectl patch crd widgets.example.com --subresource=status --type=merge \
  -p '{"status":{"storedVersions":["v1"]}}'

# ③ 이제 v1beta1을 served: false로 바꿀 수 있다
```

**`storage-version-migrator`** 라는 도구가 이 과정을 자동화한다.

> **⚠️ storedVersions에 있는 버전은 제거할 수 없다**
> 그 버전으로 저장된 오브젝트를 읽을 수 없게 되기 때문이다. 마이그레이션 없이 CRD에서 버전을 지우면 **데이터를 잃는다.**

## 26.6 API 설계 원칙

좋은 CRD를 만드는 지침이다. 오퍼레이터의 사용성이 여기서 결정된다.

### ① 선언적으로 설계하라

```yaml
# ❌ 명령형 — 액션을 spec에 넣는다
spec:
  action: backup           # 이것이 완료되면 어떻게 되는가?
  triggerRestore: true

# ✅ 선언적 — 원하는 상태를 기술한다
spec:
  backup:
    schedule: "0 3 * * *"
    retention: 30d
---
# 일회성 작업은 별도 리소스로
apiVersion: db.example.com/v1
kind: Backup
metadata:
  name: manual-backup-20260901
spec:
  clusterRef: orders-db
```

**"동사"가 spec에 들어가면 설계를 다시 봐야 한다.** 조정 루프는 상태를 다루지 액션을 다루지 않는다.

### ② spec은 사용자 의도, status는 관측 결과

```yaml
spec:
  replicas: 3              # 사용자가 원하는 것
status:
  readyReplicas: 2         # 실제 관측된 것
  observedGeneration: 4
  conditions: [...]
```

**status만 보고 spec을 재구성할 수 있으면 안 된다.** 둘의 역할이 겹치면 안 된다.

### ③ 조건(conditions)은 표준 패턴을 따르라

4.2절에서 본 형식을 그대로 쓴다.

```yaml
status:
  conditions:
    - type: Ready
      status: "True"                    # "True" | "False" | "Unknown"
      reason: AllReplicasReady          # CamelCase, 기계가 읽는다
      message: "3/3 replicas are ready" # 사람이 읽는다
      lastTransitionTime: "2026-09-01T10:00:00Z"
      observedGeneration: 4
```

**권장 조건 타입**

| type | 의미 |
|---|---|
| `Ready` | 리소스가 정상 동작 중 |
| `Progressing` | 원하는 상태로 진행 중 |
| `Degraded` | 동작하지만 저하됨 |
| `Available` | 사용 가능 |

**Go 헬퍼**

```go
import "k8s.io/apimachinery/pkg/api/meta"

meta.SetStatusCondition(&widget.Status.Conditions, metav1.Condition{
    Type:               "Ready",
    Status:             metav1.ConditionTrue,
    Reason:             "AllReplicasReady",
    Message:            fmt.Sprintf("%d/%d replicas ready", ready, desired),
    ObservedGeneration: widget.Generation,
})

if meta.IsStatusConditionTrue(widget.Status.Conditions, "Ready") { ... }
```

### ④ 참조는 명확하게

```yaml
# ❌ 문자열 하나
spec:
  database: "prod/orders-db"

# ✅ 구조화된 참조
spec:
  databaseRef:
    name: orders-db
    namespace: prod          # 생략 시 같은 네임스페이스
```

**네임스페이스를 넘는 참조는 신중하게.** 보안 경계를 넘게 되므로(13.1절), 대개 같은 네임스페이스로 제한하는 것이 안전하다.

### ⑤ 확장 가능하게 남겨 두라

```yaml
spec:
  # 자주 쓰는 것은 최상위 필드로
  replicas: 3
  image: postgres:16

  # 드물게 필요한 세부 설정은 탈출구를 제공
  podTemplate:
    type: object
    x-kubernetes-preserve-unknown-fields: true
```

**모든 것을 필드로 노출하려 하면 CRD가 PodSpec의 복사본이 된다.** 흔한 설계 실수다. 80%의 사용자가 쓰는 것만 필드로 만들고, 나머지는 템플릿 오버라이드로 처리한다.

### ⑥ 기본값을 넉넉히 제공하라

```yaml
# 사용자가 이것만 써도 동작해야 한다
apiVersion: db.example.com/v1
kind: PostgresCluster
metadata:
  name: my-db
spec: {}
```

**"Hello World"가 짧을수록 좋은 API다.**

### ⑦ 불변 필드를 명시하라

```yaml
storageClass:
  type: string
  x-kubernetes-validations:
    - rule: "self == oldSelf"
      message: "생성 후 변경할 수 없습니다"
```

바꿀 수 없는 것을 바꾸려 할 때 **어드미션에서 거부**하는 편이, 컨트롤러가 조용히 무시하는 것보다 낫다.

## 26.7 실습: 완성도 있는 CRD 만들기

**① CRD 정의**

```yaml
# webapp-crd.yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: webapps.demo.example.com
spec:
  group: demo.example.com
  scope: Namespaced
  names:
    plural: webapps
    singular: webapp
    kind: WebApp
    listKind: WebAppList
    shortNames: [wa]
    categories: [all]
  versions:
    - name: v1
      served: true
      storage: true
      subresources:
        status: {}
        scale:
          specReplicasPath: .spec.replicas
          statusReplicasPath: .status.readyReplicas
          labelSelectorPath: .status.selector
      additionalPrinterColumns:
        - { name: Image,   type: string,  jsonPath: .spec.image }
        - { name: Desired, type: integer, jsonPath: .spec.replicas }
        - { name: Ready,   type: integer, jsonPath: .status.readyReplicas }
        - { name: Phase,   type: string,  jsonPath: .status.phase }
        - { name: Age,     type: date,    jsonPath: .metadata.creationTimestamp }
        - { name: Message, type: string,  priority: 1,
            jsonPath: '.status.conditions[?(@.type=="Ready")].message' }
      schema:
        openAPIV3Schema:
          type: object
          required: [spec]
          properties:
            spec:
              type: object
              required: [image]
              properties:
                image:
                  type: string
                  minLength: 1
                  pattern: '^[a-z0-9.\-/]+:[a-zA-Z0-9._\-]+$'
                  description: "컨테이너 이미지 (태그 필수, latest 금지)"
                replicas:
                  type: integer
                  minimum: 0
                  maximum: 50
                  default: 1
                port:
                  type: integer
                  minimum: 1
                  maximum: 65535
                  default: 8080
                tier:
                  type: string
                  enum: [dev, staging, production]
                  default: dev
                resources:
                  type: object
                  properties:
                    cpu:    { type: string, default: "100m" }
                    memory: { type: string, default: "128Mi" }
                  default: {}
                env:
                  type: array
                  maxItems: 30
                  x-kubernetes-list-type: map
                  x-kubernetes-list-map-keys: [name]
                  items:
                    type: object
                    required: [name]
                    properties:
                      name:  { type: string }
                      value: { type: string }
              x-kubernetes-validations:
                - rule: "self.tier != 'production' || self.replicas >= 2"
                  message: "production 티어는 replicas가 2 이상이어야 합니다"
                - rule: "!self.image.endsWith(':latest')"
                  message: "latest 태그는 사용할 수 없습니다"
            status:
              type: object
              properties:
                phase:
                  type: string
                  enum: [Pending, Progressing, Running, Failed]
                readyReplicas:
                  type: integer
                selector:
                  type: string
                observedGeneration:
                  type: integer
                  format: int64
                conditions:
                  type: array
                  x-kubernetes-list-type: map
                  x-kubernetes-list-map-keys: [type]
                  items:
                    type: object
                    required: [type, status]
                    properties:
                      type:               { type: string }
                      status:             { type: string, enum: ["True","False","Unknown"] }
                      reason:             { type: string }
                      message:            { type: string }
                      lastTransitionTime: { type: string, format: date-time }
                      observedGeneration: { type: integer, format: int64 }
```

```bash
kubectl apply -f webapp-crd.yaml
kubectl get crd webapps.demo.example.com -o jsonpath='{.status.conditions[?(@.type=="Established")].status}'
# True
```

## 실습 과제

**과제 1 — CEL 검증 확장**
26.7절의 WebApp에 다음 규칙을 추가하고 각각을 테스트한다.
- `port`가 80이나 443이면 `tier`가 `production`이어야 한다
- `env` 배열에 `name`이 중복되면 거부
- `resources.memory`가 `1Gi`를 넘으면 `tier`가 `dev`가 아니어야 한다

**과제 2 — 불변 필드**
`spec.port`를 생성 후 변경 불가로 만들고, 변경을 시도해 거부되는 것을 확인한다. 생성 시에는 `oldSelf`가 없어 규칙이 건너뛰어지는 것도 확인한다.

**과제 3 — 두 버전 CRD**
`v1alpha1`(`spec.size`)과 `v1`(`spec.replicas`)을 함께 제공하는 CRD를 만들고, `conversion.strategy: None`으로는 필드 이름이 달라 변환이 안 되는 것을 확인한다. (변환 웹훅은 27~28장에서 구현한다.)

**과제 4 — HPA 연결**
scale 서브리소스가 있는 CRD에 HPA를 붙이고, `kubectl describe hpa`에서 어떤 에러가 나는지 확인한다. (컨트롤러가 없어 `status.selector`가 비어 있으므로 메트릭을 못 찾는다.) 27장에서 컨트롤러를 만들면 해결된다.

**과제 5 — 실제 오퍼레이터의 CRD 분석**
cert-manager나 Prometheus Operator의 CRD를 하나 골라 다음을 조사한다.
- printer columns를 어떻게 설계했는가
- 어떤 서브리소스를 쓰는가
- status의 conditions 구조는 어떠한가
- 몇 개의 버전을 제공하고 변환 전략은 무엇인가

## 요약

- CRD의 이름은 **`<plural>.<group>`** 형식이어야 하고, `Established=True`가 되어야 사용할 수 있다. **CRD를 삭제하면 그 타입의 모든 리소스가 삭제된다.**
- **OpenAPI v3 스키마는 검증·문서·프루닝 세 역할**을 한다. 스키마에 없는 필드는 **에러 없이 조용히 제거되므로**, 스키마를 정확히 정의하는 것이 중요하다.
- **CEL 검증(`x-kubernetes-validations`)이 웹훅을 대체한다.** 불변 필드, 조건부 필수, 필드 간 관계를 웹훅 없이 표현할 수 있어 가용성 위험이 없다.
- **status 서브리소스**는 spec과 status의 쓰기를 분리하고, RBAC 분리를 가능하게 하며, **`generation`이 spec 변경에만 증가**하게 만든다.
- **scale 서브리소스**를 추가하면 `kubectl scale`과 **HPA**가 커스텀 리소스에 그대로 동작한다. `labelSelectorPath`를 컨트롤러가 채워야 한다.
- **printer columns가 오퍼레이터의 사용성을 좌우한다.** 사용자가 `kubectl get`만으로 상태를 파악할 수 있어야 한다.
- 버저닝에서 **`storage: true`는 정확히 하나**이고, 실제 변환은 **허브 모델**로 구현한다. **`storedVersions`에 남은 버전을 제거하려면 모든 오브젝트를 다시 써야 한다.**
- API 설계 원칙: **선언적으로**(동사가 spec에 들어가면 재설계), **spec은 의도 status는 관측**, **conditions는 표준 패턴**, **참조는 구조화**, **탈출구를 남기고**, **기본값을 넉넉히**, **불변 필드는 명시**.

**다음 장에서는** 이 CRD를 조정하는 컨트롤러를 만든다. 25장의 저수준 구현을 Kubebuilder로 훨씬 간결하게 작성하고, 실제로 동작하는 오퍼레이터를 완성한다.
