## 2.1 컨테이너 vs 가상 머신

두 기술 모두 "격리된 실행 환경"을 제공하지만, 격리의 위치가 다르다.

```
┌──── 가상 머신 ────────────────┐   ┌──── 컨테이너 ─────────────────┐
│                              │   │                              │
│  앱 A     앱 B     앱 C       │   │  앱 A     앱 B     앱 C        │
│  ─────    ─────    ─────     │   │  ─────    ─────    ─────      │
│  라이브러리 라이브러리 라이브러리 │   │  라이브러리 라이브러리 라이브러리 │
│  ─────    ─────    ─────     │   │  ─────    ─────    ─────      │
│  게스트OS  게스트OS  게스트OS   │   │                              │
│  (커널)    (커널)    (커널)    │   │      ← 커널을 공유 →           │
│  ─────────────────────────   │   │  ─────────────────────────    │
│      하이퍼바이저             │   │      컨테이너 런타임            │
│  ─────────────────────────   │   │  ─────────────────────────    │
│      호스트 OS (커널)          │   │      호스트 OS (커널)          │
│  ─────────────────────────   │   │  ─────────────────────────    │
│      물리 하드웨어             │   │      물리 하드웨어             │
└──────────────────────────────┘   └──────────────────────────────┘
```

**가상 머신**은 하드웨어를 가상화한다. 각 VM은 자기만의 커널을 갖고, 하이퍼바이저가 CPU·메모리·디바이스를 나눠 준다. 격리 경계가 하드웨어 수준이라 매우 강하다.

**컨테이너**는 프로세스를 격리한다. 모든 컨테이너가 호스트의 커널 하나를 공유하고, 커널이 제공하는 격리 기능으로 서로를 보이지 않게 만든다. 컨테이너 안에서 `ps`를 실행하면 자기 프로세스만 보이지만, 호스트에서 보면 그냥 하나의 프로세스일 뿐이다.

| 비교 항목 | 가상 머신 | 컨테이너 |
|---|---|---|
| 격리 수준 | 하드웨어 (강함) | 커널 네임스페이스 (상대적으로 약함) |
| 부팅 시간 | 수십 초 ~ 수 분 | 수십 밀리초 ~ 수 초 |
| 이미지 크기 | 수 GB | 수 MB ~ 수백 MB |
| 오버헤드 | 게스트 커널 + 하이퍼바이저 | 거의 없음 |
| 밀도 (호스트당) | 수십 개 | 수백 ~ 수천 개 |
| 커널 | 각자 다른 커널·OS 가능 | 호스트 커널 공유 (리눅스만) |

**"컨테이너는 격리가 약하다"의 의미**

컨테이너의 격리는 커널이 제공한다. 따라서 **커널에 취약점이 있으면 격리가 뚫린다.** 커널 익스플로잇으로 컨테이너를 탈출(container escape)하면 호스트 전체가 노출된다. VM은 하이퍼바이저까지 뚫어야 하므로 한 단계 더 어렵다.

이 때문에 신뢰할 수 없는 코드를 실행하는 멀티테넌트 환경에서는 **샌드박스 런타임**을 쓰기도 한다.

- **gVisor**: 사용자 공간에서 커널 시스템콜을 가로채 구현. 호스트 커널 노출 면적을 줄인다.
- **Kata Containers**: 컨테이너마다 경량 VM을 띄운다. VM 수준 격리 + 컨테이너 사용성.
- **Firecracker**: AWS Lambda·Fargate가 쓰는 마이크로 VM.

18장에서 워크로드 보안을 다룰 때 이 선택지들이 다시 나온다.

## 2.2 이미지, 레이어, 레지스트리, OCI 표준

### 레이어 구조

컨테이너 이미지는 **읽기 전용 레이어의 스택**이다. Dockerfile의 각 명령이 하나의 레이어를 만든다.

```dockerfile
FROM python:3.12-slim          # 레이어 1: 베이스 이미지
WORKDIR /app                   # (메타데이터만, 레이어 없음)
COPY requirements.txt .        # 레이어 2: 의존성 목록
RUN pip install -r requirements.txt   # 레이어 3: 설치된 패키지들
COPY . .                       # 레이어 4: 애플리케이션 코드
CMD ["python", "app.py"]       # (메타데이터만)
```

```
        ┌──────────────────────────┐
쓰기 →  │  컨테이너 레이어 (읽기/쓰기)  │  ← 컨테이너 실행 시에만 생성
        ├──────────────────────────┤
        │  레이어 4: 앱 코드          │ ┐
        ├──────────────────────────┤ │
        │  레이어 3: pip 패키지       │ │ 이미지 (읽기 전용, 불변)
        ├──────────────────────────┤ │
        │  레이어 2: requirements.txt│ │
        ├──────────────────────────┤ │
        │  레이어 1: python:3.12-slim │ ┘
        └──────────────────────────┘
```

이 구조가 만들어 내는 두 가지 이점이 있다.

**① 레이어 공유.** 같은 베이스 이미지를 쓰는 20개 서비스가 있어도 `python:3.12-slim` 레이어는 호스트에 한 벌만 저장된다. 각 이미지는 자기 고유 레이어만 추가로 차지한다.

**② 빌드 캐시.** 앱 코드만 바뀌면 레이어 1~3은 캐시에서 재사용되고 레이어 4만 다시 만들어진다. 그래서 **자주 바뀌는 것을 뒤에** 두는 순서가 중요하다.

```dockerfile
# ❌ 나쁜 순서 — 코드 한 줄만 바꿔도 pip install을 다시 한다
COPY . .
RUN pip install -r requirements.txt

# ✅ 좋은 순서 — 의존성이 안 바뀌면 캐시 적중
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
```

### 멀티 스테이지 빌드

빌드 도구와 실행 환경을 분리하면 최종 이미지가 극적으로 작아진다.

```dockerfile
# --- 빌드 스테이지 ---
FROM golang:1.22 AS builder
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /out/server ./cmd/server

# --- 실행 스테이지 ---
FROM gcr.io/distroless/static-debian12
COPY --from=builder /out/server /server
USER 65532:65532
ENTRYPOINT ["/server"]
```

빌드 스테이지 이미지는 800MB가 넘지만, 최종 이미지는 컴파일된 바이너리만 담아 10MB 남짓이다. `distroless` 이미지에는 셸조차 없어서 공격자가 침투해도 할 수 있는 일이 거의 없다. 18장의 공급망 보안과 직결되는 실천이다.

### 레지스트리와 이미지 참조

이미지는 **레지스트리**에 저장되고, 다음 형식으로 참조된다.

```
registry.example.com:5000/team/myapp:1.2.3
└──────── 호스트 ────────┘└─ 리포지토리 ─┘└ 태그 ┘
```

레지스트리를 생략하면 Docker Hub(`docker.io`)로 간주되고, 태그를 생략하면 `latest`가 된다.

> **⚠️ 프로덕션에서 `latest` 태그를 쓰지 말 것**
> `latest`는 "최신"이라는 약속이 아니라 그냥 기본 태그 이름이다. 같은 매니페스트를 두 번 배포해도 다른 이미지가 실행될 수 있어 재현성이 깨진다. 1장에서 본 드리프트가 이미지 수준에서 재발하는 셈이다.
>
> 더 강한 방법은 **다이제스트 고정**이다.
> ```
> myapp@sha256:5f2c9e...a31b
> ```
> 다이제스트는 이미지 내용의 해시라서 절대 변하지 않는다.

### OCI 표준

초기에는 "Docker 이미지"가 사실상 표준이었지만, 지금은 **OCI(Open Container Initiative)** 가 세 가지 명세를 관리한다.

- **Image Spec**: 이미지의 레이어·매니페스트·설정 포맷
- **Runtime Spec**: 컨테이너를 실행하는 방법 (runc가 참조 구현)
- **Distribution Spec**: 레지스트리 API

덕분에 Docker로 빌드한 이미지를 containerd로 실행하고, Podman으로 검사하고, GitHub Container Registry에 저장하는 조합이 문제없이 동작한다. 벤더 종속이 없다는 것이 컨테이너 생태계의 큰 강점이다.

## 2.3 실습: 이미지 빌드와 푸시

간단한 웹 애플리케이션을 만들어 이미지로 굽고 로컬 레지스트리에 올려 본다. 이 이미지는 3장에서 첫 클러스터에 배포할 때 그대로 쓴다.

**① 애플리케이션 작성**

```bash
mkdir -p ~/k8s-guide/hello && cd ~/k8s-guide/hello
```

`app.py`:
```python
import os, socket
from http.server import BaseHTTPRequestHandler, HTTPServer

VERSION = os.getenv("APP_VERSION", "1.0")

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path == "/healthz":
            self.send_response(200)
            self.end_headers()
            self.wfile.write(b"ok")
            return
        body = f"hello from {socket.gethostname()} (v{VERSION})\n"
        self.send_response(200)
        self.send_header("Content-Type", "text/plain")
        self.end_headers()
        self.wfile.write(body.encode())

    def log_message(self, *args):
        pass  # 접근 로그 억제

HTTPServer(("", 8080), Handler).serve_forever()
```

호스트명을 출력하게 만든 이유가 있다. 나중에 Pod를 여러 개 띄우면 요청마다 다른 호스트명이 돌아오는 것을 보고 로드밸런싱을 눈으로 확인할 수 있다.

**② Dockerfile 작성**

```dockerfile
FROM python:3.12-slim

# 비루트 사용자 생성 — 18장 보안의 기본 원칙
RUN useradd --uid 10001 --create-home appuser

WORKDIR /app
COPY app.py .

USER 10001
EXPOSE 8080
CMD ["python", "-u", "app.py"]
```

**③ 빌드**

```bash
docker build -t hello:1.0 .
docker images hello
```

**④ 실행과 확인**

```bash
docker run -d --name hello -p 8080:8080 hello:1.0
curl localhost:8080
# hello from 3f2a1b9c4d5e (v1.0)

curl localhost:8080/healthz
# ok
```

**⑤ 레이어 확인**

```bash
docker history hello:1.0
```

각 명령이 어떤 크기의 레이어를 만들었는지 볼 수 있다. `COPY app.py`는 몇 KB, 베이스 이미지는 100MB 남짓일 것이다.

**⑥ 로컬 레지스트리에 푸시**

```bash
# 로컬 레지스트리 실행
docker run -d -p 5000:5000 --name registry registry:2

# 태그를 붙이고 푸시
docker tag hello:1.0 localhost:5000/hello:1.0
docker push localhost:5000/hello:1.0

# 확인
curl -s localhost:5000/v2/_catalog
# {"repositories":["hello"]}
```

**⑦ 정리**

```bash
docker rm -f hello
```

레지스트리 컨테이너는 3장에서 다시 쓰므로 남겨 둔다.

## 2.4 컨테이너를 가능하게 하는 것

여기서부터가 이 장의 핵심이다. 컨테이너는 마법이 아니라 **리눅스 커널 기능의 조합**이다. 이 절의 내용을 이해하면 19장에서 Pod를 밑바닥부터 만들 때 훨씬 수월하다.

컨테이너를 이루는 세 기둥은 다음과 같다.

| 커널 기능 | 역할 | 한 줄 요약 |
|---|---|---|
| **namespaces** | 격리 | "무엇을 볼 수 있는가" |
| **cgroups** | 자원 제한 | "얼마나 쓸 수 있는가" |
| **capabilities** | 권한 제한 | "무엇을 할 수 있는가" |
| (+ union filesystem) | 레이어 | "파일 시스템을 어떻게 쌓는가" |

### 네임스페이스 — "무엇을 볼 수 있는가"

리눅스 네임스페이스는 시스템 자원의 **뷰를 분리**한다. 종류는 다음과 같다.

| 네임스페이스 | 격리 대상 |
|---|---|
| **PID** | 프로세스 ID 트리. 컨테이너 안에서 첫 프로세스가 PID 1이 된다 |
| **NET** | 네트워크 인터페이스, IP, 라우팅 테이블, 포트 |
| **MNT** | 마운트 포인트, 파일 시스템 뷰 |
| **UTS** | 호스트명, 도메인명 |
| **IPC** | System V IPC, POSIX 메시지 큐 |
| **USER** | UID/GID 매핑. 컨테이너 내 root를 호스트의 비특권 사용자로 매핑 |
| **CGROUP** | cgroup 계층 뷰 |
| **TIME** | 시스템 시계 오프셋 (커널 5.6+) |

**중요한 예고**: 5장에서 배울 Pod는 "여러 컨테이너가 **NET·IPC·UTS 네임스페이스를 공유**하고 **MNT·PID는 각자 갖는** 그룹"이다. Pod 안의 컨테이너들이 `localhost`로 통신할 수 있는 이유가 바로 NET 네임스페이스 공유다. 지금 이 문장이 이해되면 5장이 매우 쉬워진다.

**실험: 네임스페이스를 직접 만들어 보기**

```bash
# UTS + PID + MNT 네임스페이스를 새로 만들고 셸 실행 (root 필요)
sudo unshare --uts --pid --mount --fork bash

# 이제 새 네임스페이스 안이다
hostname isolated-box       # 호스트명 변경
hostname                    # isolated-box

mount -t proc proc /proc    # PID 네임스페이스에 맞는 /proc 마운트
ps aux                      # 프로세스가 거의 안 보인다
echo $$                     # 1  ← 이 셸이 PID 1이다!

exit
hostname                    # 원래 호스트명 그대로 — 격리 확인
```

`unshare` 명령 몇 개로 컨테이너의 핵심 성질을 재현한 것이다. 컨테이너 런타임이 하는 일도 본질적으로는 이것에 파일 시스템과 자원 제한을 더한 것뿐이다.

**실험: 네트워크 네임스페이스**

```bash
# 새 네트워크 네임스페이스 생성
sudo ip netns add demo

# 그 안에서 인터페이스 확인 — lo 하나뿐, 게다가 DOWN
sudo ip netns exec demo ip addr

# 호스트와 비교
ip addr    # eth0 등 실제 인터페이스들
```

23장에서 CNI 플러그인이 하는 일이 바로 이 빈 네트워크 네임스페이스에 인터페이스를 꽂고 IP를 할당하고 라우팅을 설정하는 것이다.

### cgroups — "얼마나 쓸 수 있는가"

cgroup(control group)은 프로세스 그룹의 **자원 사용량을 제한하고 측정**한다. CPU, 메모리, 블록 I/O, PID 개수 등을 제어할 수 있다.

현재는 **cgroup v2** 가 표준이며, 통합된 단일 계층 구조를 쓴다.

```bash
# cgroup 버전 확인
stat -fc %T /sys/fs/cgroup/
# cgroup2fs  → v2
# tmpfs      → v1
```

**실험: 메모리 제한 걸어 보기 (cgroup v2)**

```bash
# cgroup 생성
sudo mkdir /sys/fs/cgroup/demo

# 메모리 상한 50MB
echo $((50*1024*1024)) | sudo tee /sys/fs/cgroup/demo/memory.max

# 현재 셸을 이 cgroup에 넣기
echo $$ | sudo tee /sys/fs/cgroup/demo/cgroup.procs

# 100MB를 할당하려고 시도 → OOM으로 종료된다
python3 -c "x = bytearray(100*1024*1024); print('allocated')"
# Killed
```

이것이 14장에서 다룰 `resources.limits.memory`의 실체다. 컨테이너에 메모리 limit을 걸면 kubelet이 정확히 이런 cgroup 설정을 만든다. `OOMKilled` 상태는 커널이 이 한도를 강제한 결과다.

**CPU 제한은 조금 다르게 동작한다.**

```bash
# 100ms 주기 중 20ms만 사용 = 0.2 CPU
echo "20000 100000" | sudo tee /sys/fs/cgroup/demo/cpu.max
```

메모리는 초과 시 **죽지만**, CPU는 초과 시 **스로틀링**(대기)된다. 이 비대칭성이 14장 QoS의 핵심 주제다.

### capabilities — "무엇을 할 수 있는가"

전통적인 리눅스는 권한이 이분법이었다. root(UID 0)는 모든 것을 할 수 있고, 나머지는 거의 아무것도 못 한다. **capability**는 root의 권한을 40여 개 조각으로 나눈 것이다.

| capability | 허용하는 동작 |
|---|---|
| `CAP_NET_BIND_SERVICE` | 1024 미만 포트 바인딩 |
| `CAP_NET_ADMIN` | 네트워크 인터페이스·라우팅 설정 |
| `CAP_SYS_ADMIN` | 마운트 등 광범위한 관리 작업 (사실상 root와 유사, 위험) |
| `CAP_CHOWN` | 파일 소유자 변경 |
| `CAP_SYS_PTRACE` | 다른 프로세스 디버깅 |

컨테이너 런타임은 기본적으로 대부분의 capability를 **제거**한 채 컨테이너를 실행한다.

```bash
# 기본 실행 — 커널 모듈 로드 시도는 실패한다
docker run --rm alpine sh -c 'apk add -q libcap 2>/dev/null; capsh --print 2>/dev/null | head -3 || id'

# 특정 capability만 추가
docker run --rm --cap-add=NET_ADMIN alpine ip link set lo down && echo "성공"

# ❌ 절대 프로덕션에서 쓰지 말 것
docker run --rm --privileged alpine ...   # 모든 capability 부여 = 격리 포기
```

18장에서 다룰 `securityContext.capabilities.drop: ["ALL"]`이 바로 이 메커니즘을 쓴다.

### union filesystem — 레이어를 하나로 보이게 하는 법

앞서 이미지가 레이어의 스택이라고 했다. 이 여러 레이어를 **하나의 파일 시스템처럼 보이게** 하는 것이 union filesystem, 리눅스에서는 주로 **overlayfs**다.

```
┌───────────────────────────────────────┐
│  merged (컨테이너가 보는 /)             │  ← 하나로 합쳐진 뷰
└───────────────────────────────────────┘
        ▲                    ▲
        │                    │
┌───────┴────────┐   ┌───────┴─────────────────┐
│  upperdir      │   │  lowerdir (읽기 전용)     │
│  (쓰기 가능)     │   │  레이어 1 + 2 + 3 ...    │
└────────────────┘   └─────────────────────────┘
```

컨테이너 안에서 파일을 수정하면 **copy-up**이 일어난다. 하위 레이어의 파일을 upperdir로 복사한 뒤 그 사본을 수정한다. 원본 이미지 레이어는 절대 변하지 않는다. 컨테이너를 삭제하면 upperdir이 사라지고, 그래서 **컨테이너의 파일 시스템 변경은 휘발성**이다.

이것이 12장에서 볼륨이 필요한 이유다. 데이터를 유지하려면 이 레이어 구조 밖으로 나가야 한다.

## 2.5 컨테이너 런타임의 계보

"Docker를 쓴다"고 말할 때 실제로는 여러 층의 소프트웨어가 관여한다.

```
   사용자
     │
     ▼
┌─────────────┐
│   Docker    │  CLI + 이미지 빌드 + 네트워크 관리 + ...
│   (dockerd) │  = 개발자 도구 전체 패키지
└──────┬──────┘
       ▼
┌─────────────┐
│  containerd │  고수준 런타임: 이미지 관리, 컨테이너 수명주기
└──────┬──────┘
       ▼
┌─────────────┐
│    runc     │  저수준 런타임: 네임스페이스·cgroup을 실제로 설정
└──────┬──────┘   (OCI Runtime Spec 참조 구현)
       ▼
   리눅스 커널
```

**쿠버네티스와 런타임의 관계는 이렇게 변해 왔다.**

- **초기**: kubelet이 Docker를 직접 호출했다.
- **2016년**: **CRI(Container Runtime Interface)** 도입. kubelet이 표준 gRPC 인터페이스로 런타임과 대화하도록 추상화했다.
- **과도기**: Docker는 CRI를 구현하지 않았으므로 `dockershim`이라는 어댑터가 kubelet에 내장돼 있었다.
- **v1.24 (2022)**: dockershim 제거. 이것이 "쿠버네티스가 Docker를 버렸다"고 잘못 알려진 사건이다.

> **📌 자주 있는 오해 정리**
> "쿠버네티스가 Docker 지원을 중단했다"는 말은 **Docker로 빌드한 이미지를 못 쓴다는 뜻이 아니다.** 이미지는 OCI 표준이므로 아무 문제 없다. 바뀐 것은 **kubelet이 Docker 데몬을 직접 호출하지 않는다**는 점뿐이다. 지금은 containerd나 CRI-O가 직접 CRI를 구현해 kubelet과 대화한다. 개발자가 로컬에서 `docker build`를 쓰는 것에는 아무 영향이 없다.

**현재 주요 런타임**

| 런타임 | 특징 |
|---|---|
| **containerd** | 가장 널리 쓰인다. GKE·EKS·AKS 기본값 |
| **CRI-O** | 쿠버네티스 전용으로 설계. OpenShift 기본값 |
| **Docker Engine** | 개발 환경에서 여전히 표준. 내부적으로 containerd 사용 |
| **gVisor / Kata** | 샌드박스 런타임. RuntimeClass로 특정 워크로드에만 적용 가능 |

클러스터의 런타임은 노드 정보에서 확인할 수 있다(3장에서 클러스터를 만든 뒤 시도해 보자).

```bash
kubectl get nodes -o wide
# CONTAINER-RUNTIME 열: containerd://1.7.x
```

20장에서 kubelet이 CRI를 통해 어떻게 컨테이너를 만드는지, `crictl` 도구로 직접 추적한다.

## 실습 과제

**과제 1 — 멀티 스테이지 빌드로 이미지 줄이기**
2.3절의 `hello` 앱을 Go나 Rust로 다시 작성하고, 멀티 스테이지 빌드로 distroless 이미지를 만들어 본다. `docker images`로 크기를 비교하고, 얼마나 줄었는지 기록한다.

**과제 2 — 네임스페이스 조합 실험**
`unshare`로 **NET 네임스페이스만** 새로 만든 셸을 띄워 본다.
```bash
sudo unshare --net bash
ip addr        # lo 하나뿐
hostname       # 호스트명은 그대로! (UTS는 공유했으므로)
```
어떤 네임스페이스를 공유하고 어떤 것을 분리했는지에 따라 무엇이 달라지는지 확인한다. **이 실험이 Pod의 동작 원리와 정확히 같다.**

**과제 3 — cgroup으로 CPU 제한 관찰하기**
`cpu.max`를 `10000 100000`(0.1 CPU)으로 설정한 cgroup에 무한 루프 프로세스를 넣고, `top`으로 CPU 사용률이 10% 근처에 머무는지 확인한다. 그다음 `cpu.stat` 파일의 `throttled_usec` 값이 증가하는 것을 관찰한다. 14장에서 이 값이 왜 중요한 지표인지 다룬다.

## 요약

- **컨테이너는 커널을 공유하는 프로세스 격리**이고, VM은 하드웨어를 가상화한다. 컨테이너는 가볍고 빠르지만 격리 경계가 커널이므로, 신뢰할 수 없는 워크로드에는 gVisor·Kata 같은 샌드박스 런타임을 고려한다.
- **이미지는 읽기 전용 레이어의 스택**이다. 자주 바뀌는 것을 Dockerfile 뒤쪽에 두면 캐시 효율이 오르고, 멀티 스테이지 빌드로 최종 이미지를 극적으로 줄일 수 있다. 프로덕션에서는 `latest` 대신 명시적 태그나 다이제스트를 쓴다.
- 컨테이너를 이루는 세 기둥은 **namespace(무엇을 볼 수 있는가)**, **cgroup(얼마나 쓸 수 있는가)**, **capability(무엇을 할 수 있는가)** 이며, overlayfs가 레이어를 하나의 파일 시스템으로 합친다.
- Pod는 **NET·IPC·UTS를 공유하고 MNT·PID를 분리한 컨테이너 그룹**이다. 이 문장이 5장의 전부다.
- 쿠버네티스는 **CRI**를 통해 런타임과 대화한다. v1.24에서 dockershim이 제거됐지만 Docker로 빌드한 이미지는 OCI 표준이라 아무 영향이 없다.

**다음 장에서는** 실제 클러스터를 만든다. kind로 멀티 노드 클러스터를 띄우고, kubectl 사용법을 익히고, 이 장에서 만든 `hello` 이미지를 배포해 브라우저로 접속하는 것까지 완주한다.
