# 1장. 왜 쿠버네티스인가

> **학습목표**
> - 모놀리스에서 컨테이너 오케스트레이션에 이르는 흐름을 스스로 설명할 수 있다.
> - 인프라 드리프트가 왜 운영 사고의 근원이 되는지 사례로 설명할 수 있다.
> - 선언적 상태와 조정 루프(reconciliation loop)라는 쿠버네티스의 핵심 아이디어를 이해한다.
> - 컨트롤 플레인과 워커 노드의 역할을 구분해 그림으로 그릴 수 있다.
> - 쿠버네티스를 도입하지 말아야 할 상황을 판단할 수 있다.

---

## 1.1 인프라 드리프트 문제와 자동화의 필요성

새 서비스를 배포하는 흔한 풍경에서 시작해 보자. 개발자가 애플리케이션을 만들고, 운영자가 서버를 준비한다. 운영자는 우분투를 설치하고, 자바 런타임을 올리고, 방화벽을 열고, 로그 로테이션을 설정하고, 모니터링 에이전트를 붙인다. 서비스가 잘 돌아간다. 6개월 뒤 트래픽이 늘어 서버를 한 대 더 늘린다. 이번에는 다른 담당자가 작업하고, 우분투 버전이 한 단계 올라가 있고, 자바 패치 버전이 다르고, 방화벽 규칙 하나를 빠뜨린다.

이제 두 서버는 "같은 서버"라고 불리지만 실제로는 다른 서버다. 이 차이는 평소에는 드러나지 않다가, 특정 요청이 두 번째 서버로 라우팅될 때만 실패하는 형태로 나타난다. 이것이 **인프라 드리프트(infrastructure drift)** 다. 동일해야 할 시스템들이 시간이 지나며 조금씩 벌어지는 현상이다.

드리프트가 위험한 이유는 두 가지다.

첫째, **재현이 불가능하다.** "내 로컬에서는 되는데요"는 농담이 아니라 드리프트의 증상이다. 개발 환경, 스테이징, 프로덕션이 서로 다른 상태에 있으면 테스트를 통과한 코드가 프로덕션에서 실패한다.

둘째, **복구가 불가능하다.** 서버가 죽었을 때 "원래대로" 되돌리려면 원래 상태가 무엇이었는지 알아야 하는데, 수작업으로 쌓인 변경 이력은 어디에도 기록되어 있지 않다.

업계는 이 문제를 단계적으로 풀어 왔다.

**1단계: 설정 관리 도구.** Puppet, Chef, Ansible 같은 도구는 "서버가 어떤 상태여야 하는지"를 코드로 적게 했다. 진일보였지만 한계가 있었다. 이 도구들은 이미 존재하는 서버를 원하는 상태로 *수렴*시키는 방식이라, 기반 OS의 차이나 이전 작업의 잔여물까지 없애지는 못했다.

**2단계: 불변 인프라.** "고치지 말고 갈아엎자"는 발상이다. 서버를 수정하는 대신 새 이미지로 새 서버를 만들고 기존 서버를 버린다. AMI를 굽는 방식이 대표적이다. 드리프트는 크게 줄었지만, VM 이미지는 무겁고 빌드가 느렸다.

**3단계: 컨테이너.** 애플리케이션과 그 의존성만 담은 가벼운 패키지다. 수백 MB, 빌드는 수십 초. 어디서 실행하든 컨테이너 내부는 동일하다. 이 시점에서 "실행 단위의 재현성" 문제는 사실상 해결됐다.

그런데 컨테이너를 도입하고 나자 새로운 문제가 생겼다.

## 1.2 마이크로서비스와 배포 복잡도

컨테이너는 서비스를 잘게 쪼개기 쉽게 만들었다. 모놀리스 하나를 배포하던 조직이 이제 40개의 서비스를 배포한다. 각 서비스는 독립적으로 개발·배포되고, 서로 다른 언어와 런타임을 쓴다.

이때 운영자가 답해야 할 질문의 성격이 완전히 바뀐다.

| 모놀리스 시절의 질문 | 마이크로서비스 시대의 질문 |
|---|---|
| 이 서버에 앱을 어떻게 올리지? | 40개 서비스, 200개 인스턴스를 15대 서버에 **어떻게 배치**하지? |
| 서버가 죽으면 어떻게 살리지? | 서버가 죽었을 때 그 위에 있던 인스턴스를 **어디로 옮기지**? |
| 앱 주소가 뭐지? | 인스턴스가 계속 옮겨 다니는데 서비스 간 **주소를 어떻게 찾지**? |
| 배포 시 서버를 내리면 되나? | 40개 서비스를 각각 **무중단으로** 어떻게 업데이트하지? |
| CPU가 부족하면 서버를 늘리자 | 어떤 서비스가 병목인지 **어떻게 알고** 그것만 늘리지? |

이 질문들의 공통점은 **사람이 손으로 답하기에는 조합의 수가 너무 많다**는 것이다. 40개 서비스가 각각 3개 인스턴스를 갖고, 서버가 15대라면 배치 경우의 수는 천문학적이다. 게다가 서버는 언제든 죽고, 트래픽은 시시각각 변하고, 배포는 하루에도 여러 번 일어난다.

사람이 매번 결정을 내리는 방식으로는 유지될 수 없다. 필요한 것은 **결정을 대신 내려 주는 시스템**, 즉 오케스트레이터다.

## 1.3 쿠버네티스가 해결하는 것: 선언적 상태와 조정 루프

쿠버네티스의 핵심 아이디어는 한 문장으로 요약된다.

> **"무엇을 원하는지 적어 두면, 시스템이 알아서 그 상태를 유지한다."**

이것을 **선언적(declarative)** 접근이라고 부른다. 명령형(imperative)과 비교하면 차이가 분명해진다.

**명령형 — 절차를 지시한다**

```bash
ssh server-01 'docker run -d --name web-1 myapp:1.2'
ssh server-02 'docker run -d --name web-2 myapp:1.2'
ssh server-03 'docker run -d --name web-3 myapp:1.2'
# server-02가 죽으면? → 사람이 알아채고, 사람이 다시 실행
```

**선언적 — 목표 상태를 기술한다**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3              # "3개가 떠 있어야 한다"
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: web
        image: myapp:1.2   # "이 이미지여야 한다"
```

이 YAML은 절차를 담고 있지 않다. 어느 서버에 띄울지, 어떤 순서로 띄울지, 죽으면 어떻게 할지 아무것도 적혀 있지 않다. 오직 **결과로서의 상태**만 적혀 있다.

이 상태를 실제로 만들어 내는 것이 **조정 루프(reconciliation loop)** 다. 쿠버네티스 내부의 모든 컨트롤러는 다음 세 단계를 끝없이 반복한다.

```
     ┌─────────────────────────────────────────┐
     │                                         │
     ▼                                         │
 ① 관찰(observe)                                │
   현재 상태는? → "web Pod가 2개 떠 있음"         │
     │                                         │
     ▼                                         │
 ② 비교(diff)                                   │
   원하는 상태는? → "3개"                        │
   차이는? → "1개 부족"                          │
     │                                         │
     ▼                                         │
 ③ 조치(act)                                    │
   Pod 1개 생성 요청                             │
     │                                         │
     └─────────────────────────────────────────┘
```

이 루프가 왜 강력한지는 장애 상황에서 드러난다. 서버 한 대가 죽으면 그 위의 Pod가 사라지고, 다음 루프에서 "2개뿐"이라는 차이가 관측되고, 자동으로 다른 노드에 하나가 생성된다. **사람의 개입이 필요한 지점이 없다.**

같은 원리가 배포에도 적용된다. 이미지를 `myapp:1.3`으로 바꿔 적용하면, 컨트롤러는 "현재는 1.2인 Pod 3개, 원하는 것은 1.3인 Pod 3개"라는 차이를 발견하고, 정해진 전략(기본값은 롤링 업데이트)에 따라 하나씩 교체한다.

이 사고방식은 6부에서 직접 컨트롤러를 만들 때 다시 등장한다. 쿠버네티스를 확장한다는 것은 결국 **나만의 조정 루프를 추가하는 일**이기 때문이다.

## 1.4 아키텍처 한눈에 보기 — 컨트롤 플레인과 워커 노드

쿠버네티스 클러스터는 두 종류의 노드로 구성된다.

```
┌────────────────────── 컨트롤 플레인 (Control Plane) ──────────────────────┐
│                                                                          │
│   ┌────────────────┐   "클러스터의 정문"                                   │
│   │ kube-apiserver │ ← 모든 요청은 여기를 통과한다 (인증·인가·검증)          │
│   └───────┬────────┘                                                     │
│           │                                                              │
│   ┌───────▼────────┐   "클러스터의 유일한 기억"                            │
│   │      etcd      │ ← 모든 오브젝트의 상태가 저장되는 분산 KV 스토어        │
│   └────────────────┘                                                     │
│                                                                          │
│   ┌────────────────────────┐   "어디에 놓을지 결정"                        │
│   │    kube-scheduler      │ ← 새 Pod를 어느 노드에 배치할지 계산            │
│   └────────────────────────┘                                             │
│                                                                          │
│   ┌────────────────────────┐   "조정 루프의 집합"                          │
│   │ kube-controller-manager│ ← Deployment, ReplicaSet, Node 등의 컨트롤러  │
│   └────────────────────────┘                                             │
└──────────────────────────────────────────────────────────────────────────┘
                                    ▲
                                    │ (kubelet이 API 서버에 접속)
        ┌───────────────────────────┼───────────────────────────┐
        │                           │                           │
┌───────▼────────┐        ┌─────────▼──────┐        ┌───────────▼────┐
│  워커 노드 1     │        │  워커 노드 2    │        │  워커 노드 3     │
│                │        │                │        │                │
│  kubelet       │        │  kubelet       │        │  kubelet       │
│  kube-proxy    │        │  kube-proxy    │        │  kube-proxy    │
│  컨테이너 런타임  │        │  컨테이너 런타임  │       │  컨테이너 런타임  │
│                │        │                │        │                │
│  [Pod] [Pod]   │        │  [Pod]         │        │  [Pod] [Pod]   │
└────────────────┘        └────────────────┘        └────────────────┘
```

각 컴포넌트를 한 줄로 요약하면 이렇다.

**컨트롤 플레인 — "결정하는 쪽"**

- **kube-apiserver**: 클러스터의 유일한 진입점. `kubectl`도, 컨트롤러도, kubelet도 모두 이 API를 통해서만 대화한다. 컴포넌트끼리 직접 통신하지 않는 이 설계 덕분에 인증·인가·감사를 한 곳에서 처리할 수 있다.
- **etcd**: 클러스터의 모든 상태를 저장하는 분산 키-값 스토어. etcd가 곧 "클러스터의 진실"이다. etcd를 잃으면 클러스터를 잃는다(22장에서 백업·복구를 다룬다).
- **kube-scheduler**: 아직 노드가 정해지지 않은 Pod를 발견하면, 리소스 요구량·어피니티·테인트 등을 고려해 배치할 노드를 결정한다.
- **kube-controller-manager**: 수십 개의 내장 컨트롤러를 한 프로세스에서 실행한다. 각 컨트롤러가 앞서 본 조정 루프를 돌린다.
- **cloud-controller-manager**(클라우드 환경): 로드밸런서 생성, 볼륨 프로비저닝 등 클라우드 API와의 연동을 담당한다.

**워커 노드 — "실행하는 쪽"**

- **kubelet**: 각 노드의 에이전트. API 서버로부터 "이 노드에서 이 Pod를 실행하라"는 지시를 받아 실제로 컨테이너를 띄우고, 상태를 보고한다.
- **컨테이너 런타임**: containerd, CRI-O 등. kubelet이 CRI라는 표준 인터페이스로 호출한다.
- **kube-proxy**: 서비스 추상화를 노드 수준에서 구현한다. iptables나 IPVS 규칙을 관리해 서비스 IP로 오는 트래픽을 실제 Pod로 전달한다.

지금은 이름과 역할만 익혀 두면 충분하다. 21장(컨트롤 플레인)과 20장(kubelet)에서 각 컴포넌트의 내부를 코드 수준까지 파고든다.

## 1.5 쿠버네티스를 쓰지 말아야 할 경우

기술서에서 잘 다루지 않지만 가장 중요한 절이다. 쿠버네티스는 만능이 아니고, 잘못 도입하면 해결하는 문제보다 만드는 문제가 많다.

**도입을 재고해야 하는 신호들**

**① 서비스가 하나뿐이고, 트래픽이 예측 가능하다.** 웹 서버 2대로 충분한 서비스에 쿠버네티스를 얹으면 관리 대상이 2개에서 수십 개로 늘어난다. 이 경우 매니지드 PaaS(App Runner, Cloud Run, App Service)나 단순한 VM + 로드밸런서가 총소유비용 면에서 낫다.

**② 상태를 가진 레거시가 핵심이다.** 파일 락, 로컬 디스크 세션, 고정 IP에 의존하는 애플리케이션은 쿠버네티스의 "언제든 죽고 다시 뜬다"는 전제와 정면으로 충돌한다. 컨테이너화 자체는 가능하지만, 얻는 것보다 우회하는 데 드는 비용이 크다.

**③ 클러스터를 운영할 사람이 없다.** 쿠버네티스는 복잡한 분산 시스템이다. 매니지드 서비스가 컨트롤 플레인을 대신 운영해 주더라도, 네트워크 정책·RBAC·리소스 튜닝·업그레이드는 여전히 팀의 몫이다. 전담 인력 없이 도입하면 "아무도 손대지 못하는 블랙박스"가 된다.

**④ 지연 시간이 마이크로초 단위로 중요하다.** 오버레이 네트워크, iptables 홉, 스케줄링 지연은 대부분의 워크로드에서 무시할 수 있지만 고빈도 트레이딩이나 실시간 신호 처리에서는 아니다.

**⑤ "요즘 다 쓴다니까"가 유일한 이유다.** 도입 이유를 한 문장으로 적을 수 없다면 아직 때가 아니다.

**반대로, 도입이 정당화되는 신호들**

- 서비스 수가 열 개를 넘고 계속 늘어난다.
- 배포 빈도가 높고(주 수회 이상), 무중단 배포가 필요하다.
- 트래픽 변동이 커서 자동 스케일링의 이득이 크다.
- 여러 팀이 같은 인프라를 나눠 써야 한다.
- 멀티 클라우드나 하이브리드 환경에서 이식성이 필요하다.

건강한 판단 기준은 이것이다. **"지금 사람이 손으로 하고 있는 반복 결정이 무엇인가?"** 그 목록이 길고 자주 반복된다면 쿠버네티스가 그 결정을 자동화해 줄 수 있다. 목록이 짧다면 자동화할 것이 없는데 자동화 기계를 들이는 셈이다.

## 1.6 생태계 지도: CNCF, 배포판, 매니지드 서비스

쿠버네티스는 홀로 서 있지 않다. 처음 입문할 때 가장 혼란스러운 지점이 이 생태계의 규모이므로, 좌표부터 잡아 두자.

**CNCF와 프로젝트 성숙도**

쿠버네티스는 2014년 구글에서 시작해 2015년 CNCF(Cloud Native Computing Foundation)에 기증됐다. CNCF는 프로젝트를 세 단계로 분류한다.

- **Graduated**(졸업): 프로덕션 검증 완료. Kubernetes, Prometheus, etcd, Helm, containerd, Envoy, Argo, Cilium 등.
- **Incubating**(인큐베이팅): 실사용 사례가 있으나 성숙 중. Knative, KEDA, Kyverno 등.
- **Sandbox**(샌드박스): 초기 단계. 프로덕션 도입 시 신중해야 한다.

새 도구를 검토할 때 이 등급을 먼저 확인하는 습관이 도움이 된다.

**배포판(Distribution)**

순수 오픈소스 쿠버네티스에 설치 도구·기본 애드온·지원을 얹은 것이다.

| 배포판 | 특징 |
|---|---|
| **kubeadm** | 업스트림 공식 부트스트랩 도구. 가장 표준적 |
| **k3s** | 경량 배포판. 엣지·IoT·개발 환경에 적합 |
| **OpenShift** | Red Hat. 개발자 워크플로와 보안 정책이 강하게 통합 |
| **Rancher / RKE2** | 멀티 클러스터 관리에 강점 |
| **Talos Linux** | OS 자체가 쿠버네티스 전용. API로만 조작하는 불변 OS |

**매니지드 서비스**

컨트롤 플레인을 클라우드 사업자가 대신 운영한다. 이 책에서는 29장에서 셋을 나란히 다룬다.

| 서비스 | 사업자 | 특징 |
|---|---|---|
| **GKE** | Google | 가장 성숙. Autopilot 모드는 노드 관리까지 위임 |
| **EKS** | AWS | AWS 생태계 통합. IRSA로 IAM 연동 |
| **AKS** | Azure | Entra ID(구 Azure AD) 통합이 자연스러움 |

**주변 도구 지도**

이 책의 각 장이 생태계 어디에 해당하는지 미리 표시해 둔다.

```
패키징·배포   Helm, Kustomize, Argo CD, Flux          → 30장
관측성        Prometheus, Grafana, Loki, OpenTelemetry → 31장
네트워킹      Calico, Cilium, Antrea, Istio            → 11장, 23장
스토리지      CSI 드라이버, Rook, Longhorn             → 12장
보안·정책     OPA Gatekeeper, Kyverno, Falco, Trivy   → 18장
확장·개발     controller-runtime, Kubebuilder          → 6부
```

전부 알 필요는 없다. 각 영역에서 하나씩만 손에 익혀도 나머지는 유사한 구조를 갖는다.

## 실습 과제

이 장은 개념 장이므로 클러스터 실습은 없다. 대신 다음 두 가지를 직접 해 보길 권한다.

**과제 1 — 도입 판단서 써 보기**
지금 담당하고 있거나 관심 있는 시스템 하나를 골라, 1.5절의 기준에 따라 다음 세 항목을 각각 세 문장 이내로 적어 본다.
1. 현재 사람이 손으로 반복하고 있는 결정은 무엇인가?
2. 쿠버네티스가 그중 몇 개를 자동화할 수 있는가?
3. 도입 시 새로 생기는 운영 부담은 무엇인가?

**과제 2 — 조정 루프 찾아보기**
쿠버네티스 밖에서 조정 루프 패턴을 쓰고 있는 시스템을 하나 찾아본다(온도 조절기, 오토스케일링 그룹, Git 동기화 도구 등). 그 시스템의 "관찰-비교-조치"가 각각 무엇인지 적어 본다. 이 패턴이 익숙해지면 27장에서 오퍼레이터를 만들 때 훨씬 수월하다.

## 요약

- **인프라 드리프트**는 동일해야 할 시스템이 시간이 지나며 벌어지는 현상이며, 재현 불가능성과 복구 불가능성을 낳는다. 컨테이너는 실행 단위의 재현성 문제를 해결했다.
- 마이크로서비스로 서비스 수가 늘어나면 **배치·복구·디스커버리·배포·스케일링**이 사람이 손으로 감당할 수 없는 조합 문제가 된다. 오케스트레이터가 필요해지는 지점이다.
- 쿠버네티스의 핵심은 **선언적 상태**와 **조정 루프**다. 원하는 결과를 기술하면 컨트롤러가 관찰-비교-조치를 반복하며 그 상태를 유지한다.
- 클러스터는 **컨트롤 플레인**(apiserver, etcd, scheduler, controller-manager)과 **워커 노드**(kubelet, 런타임, kube-proxy)로 나뉜다. 모든 통신은 API 서버를 경유한다.
- 쿠버네티스는 **자동화할 반복 결정이 많을 때** 정당화된다. 서비스가 소수이거나, 운영 인력이 없거나, 마이크로초 지연이 중요하다면 다른 선택지가 낫다.

**다음 장에서는** 쿠버네티스가 실행하는 단위인 컨테이너를 들여다본다. 이미지가 어떻게 구성되는지, 그리고 컨테이너가 리눅스 커널의 어떤 기능 위에 서 있는지를 직접 실험으로 확인한다.
