# 13장. 네임스페이스와 멀티테넌시

> **학습목표**
> - 네임스페이스가 격리하는 것과 격리하지 못하는 것을 정확히 구분할 수 있다.
> - ResourceQuota로 팀별 자원 소비를 통제할 수 있다.
> - LimitRange로 기본값과 상하한을 강제할 수 있다.
> - 소프트 격리와 하드 격리의 차이를 이해하고 상황에 맞게 설계할 수 있다.
> - 계층적 네임스페이스와 가상 클러스터의 용도를 안다.

---

## 들어가며

3부까지는 하나의 워크로드를 잘 돌리는 방법이었다. 4부는 **여러 팀, 여러 워크로드가 하나의 클러스터를 나눠 쓰는 상황**을 다룬다.

클러스터를 공유하면 이런 질문이 생긴다.

- A팀의 배포 실수가 B팀 서비스를 죽이지 않게 하려면?
- 한 팀이 클러스터 자원을 독차지하지 못하게 하려면?
- 개발자가 자기 네임스페이스만 건드리게 하려면?
- 팀별로 비용을 어떻게 나눠 청구하나?

이 장은 그 출발점인 네임스페이스를 다룬다.

## 13.1 네임스페이스의 역할과 한계

### 네임스페이스가 하는 일

```bash
kubectl get namespaces
```

```
NAME              STATUS   AGE
default           Active   2d
kube-node-lease   Active   2d
kube-public       Active   2d
kube-system       Active   2d
```

| 네임스페이스 | 용도 |
|---|---|
| `default` | 지정하지 않았을 때의 기본 |
| `kube-system` | 시스템 컴포넌트 (건드리지 말 것) |
| `kube-public` | 인증 없이 읽을 수 있는 리소스 (거의 안 씀) |
| `kube-node-lease` | 노드 하트비트용 Lease 오브젝트 |

**네임스페이스가 제공하는 것은 네 가지다.**

**① 이름 스코프**
같은 이름의 리소스를 여러 네임스페이스에 만들 수 있다.
```
dev/web-service
staging/web-service
prod/web-service        ← 모두 공존 가능
```

**② DNS 스코프**
10장에서 본 것처럼 DNS 이름에 네임스페이스가 들어간다.
```
web.dev.svc.cluster.local
web.prod.svc.cluster.local
```
같은 네임스페이스 안에서는 짧은 이름으로 부를 수 있다.

**③ RBAC 경계**
Role과 RoleBinding은 네임스페이스에 속한다. "dev 네임스페이스에서만 Pod를 만들 수 있는" 역할을 정의할 수 있다(17장).

**④ 리소스 쿼터의 단위**
ResourceQuota는 네임스페이스마다 적용된다. 이 장의 주제다.

### 네임스페이스가 하지 못하는 일 — 중요

> **⚠️ 네임스페이스는 보안 경계가 아니다**
>
> 이것을 오해하면 위험한 설계를 하게 된다. 네임스페이스는 **이름 정리와 권한 그룹화**를 위한 것이지, 격리를 위한 것이 아니다.

**① 네트워크는 기본적으로 열려 있다**

```bash
# dev 네임스페이스의 Pod에서
kubectl run t -n dev --rm -it --image=nicolaka/netshoot --restart=Never -- \
  curl -s http://web.prod.svc.cluster.local
```

**연결된다.** 9장에서 본 것처럼 모든 Pod는 모든 Pod와 통신할 수 있다. 이것을 막으려면 **NetworkPolicy**가 필요하다(18장).

**② 노드는 공유된다**

```bash
kubectl get pods -A -o wide | grep k8s-guide-worker
```

여러 네임스페이스의 Pod가 같은 노드에서 돈다. 즉:
- 같은 커널을 공유한다 → 커널 취약점이 뚫리면 격리가 무너진다(2.1절)
- CPU/메모리를 경쟁한다 → 한 Pod가 노드를 마비시킬 수 있다(14장)
- 노드의 파일 시스템에 접근할 수 있다면(hostPath) 다른 Pod의 데이터도 볼 수 있다

**③ 클러스터 스코프 리소스는 공유된다**

```bash
kubectl api-resources --namespaced=false
```

Node, PersistentVolume, StorageClass, ClusterRole, CRD, IngressClass — 이것들은 네임스페이스에 속하지 않는다. **CRD를 설치하면 모든 네임스페이스에 영향을 준다.**

**④ 컨트롤 플레인은 하나다**

한 팀이 API 서버에 부하를 주면 모두가 느려진다. etcd가 가득 차면 클러스터 전체가 멈춘다.

### 정리하면

```
네임스페이스가 주는 것:  이름 정리, RBAC 그룹, 쿼터 단위, DNS 스코프
추가로 필요한 것:
  · 네트워크 격리      → NetworkPolicy (18장)
  · 자원 격리          → ResourceQuota + LimitRange (이 장)
  · 노드 격리          → 테인트 + 어피니티 (15장)
  · 커널 격리          → 샌드박스 런타임 (18장)
  · 권한 격리          → RBAC (17장)
```

**멀티테넌시는 이 모든 것의 조합이다.** 네임스페이스는 그 시작점일 뿐이다.

### 네임스페이스 관리

```bash
# 생성
kubectl create namespace team-a
# 또는
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Namespace
metadata:
  name: team-a
  labels:
    team: alpha
    environment: production
    # PSA 라벨 (18장)
    pod-security.kubernetes.io/enforce: baseline
EOF

# 현재 컨텍스트의 기본 네임스페이스 변경
kubectl config set-context --current --namespace=team-a
# 또는 kubens 플러그인
kubens team-a

# 삭제 — 안의 모든 리소스가 함께 삭제된다
kubectl delete namespace team-a
```

> **⚠️ 네임스페이스 삭제는 되돌릴 수 없다**
> 안의 모든 리소스(Deployment, Service, PVC, Secret...)가 사라진다. PVC가 `reclaimPolicy: Delete`라면 **데이터까지 사라진다**(12.3절).
>
> 프로덕션 네임스페이스에는 삭제 방어를 걸어 두는 것이 좋다. 정책 엔진(18장)으로 특정 라벨이 붙은 네임스페이스의 삭제를 거부할 수 있다.

**Terminating에서 멈추는 경우**는 4.2절에서 다룬 파이널라이저 문제다.

```bash
kubectl get ns stuck -o jsonpath='{.spec.finalizers}'
# 원인을 먼저 찾되, 불가피하면
kubectl patch ns stuck -p '{"metadata":{"finalizers":[]}}' --type=merge
```

## 13.2 ResourceQuota

### 무엇을 제한하는가

네임스페이스 전체가 소비할 수 있는 자원의 총량을 정한다.

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-a-quota
  namespace: team-a
spec:
  hard:
    # --- 컴퓨트 자원 ---
    requests.cpu: "20"
    requests.memory: 40Gi
    limits.cpu: "40"
    limits.memory: 80Gi

    # --- 스토리지 ---
    requests.storage: 500Gi
    persistentvolumeclaims: "20"
    # StorageClass별로도 제한 가능
    fast-ssd.storageclass.storage.k8s.io/requests.storage: 100Gi
    fast-ssd.storageclass.storage.k8s.io/persistentvolumeclaims: "5"

    # --- 오브젝트 개수 ---
    pods: "100"
    services: "20"
    services.loadbalancers: "2"      # ★ 비용 통제에 중요
    services.nodeports: "5"
    configmaps: "50"
    secrets: "50"
    replicationcontrollers: "20"
    count/deployments.apps: "30"
    count/jobs.batch: "50"
    count/cronjobs.batch: "10"
    count/ingresses.networking.k8s.io: "10"
```

**`services.loadbalancers`를 제한하는 이유**는 9장에서 말한 대로다. LoadBalancer Service 하나당 클라우드 LB 하나가 생기고 요금이 부과된다. 실수로 20개를 만들면 청구서가 놀랍게 나온다.

**임의의 리소스 개수**도 제한할 수 있다.
```yaml
count/<resource>.<group>: "10"
count/certificates.cert-manager.io: "20"
```

### 확인

```bash
kubectl get resourcequota -n team-a
kubectl describe resourcequota team-a-quota -n team-a
```

```
Name:                   team-a-quota
Namespace:              team-a
Resource                Used    Hard
--------                ----    ----
limits.cpu              12      40
limits.memory           24Gi    80Gi
persistentvolumeclaims  3       20
pods                    18      100
requests.cpu            6       20
requests.memory         12Gi    40Gi
services.loadbalancers  1       2
```

### 가장 중요한 규칙

> **⚠️ 컴퓨트 쿼터가 있으면 모든 컨테이너가 requests/limits를 명시해야 한다**
>
> ResourceQuota에 `requests.cpu`나 `limits.memory`가 있으면, 해당 값을 지정하지 않은 Pod는 **생성이 거부된다.**
>
> ```
> Error from server (Forbidden): error when creating "pod.yaml":
> pods "web" is forbidden: failed quota: team-a-quota:
> must specify limits.cpu for: app; limits.memory for: app;
> requests.cpu for: app; requests.memory for: app
> ```
>
> 이것은 **버그가 아니라 의도된 동작**이다. 쿼터를 계산하려면 각 Pod가 얼마를 쓸지 알아야 하기 때문이다.
>
> **해결책은 LimitRange로 기본값을 주는 것이다**(13.3절). 이 둘은 거의 항상 함께 쓴다.

### scopeSelector — 조건부 쿼터

특정 조건의 Pod에만 쿼터를 적용할 수 있다.

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: best-effort-quota
  namespace: team-a
spec:
  hard:
    pods: "10"
  scopes:
    - BestEffort              # QoS가 BestEffort인 Pod만 (14장)
```

**사용 가능한 스코프**

| 스코프 | 대상 |
|---|---|
| `Terminating` | `activeDeadlineSeconds`가 설정된 Pod |
| `NotTerminating` | 그렇지 않은 Pod |
| `BestEffort` | QoS = BestEffort |
| `NotBestEffort` | 그 외 |
| `PriorityClass` | 특정 우선순위 클래스 (15장) |
| `CrossNamespacePodAffinity` | 네임스페이스 간 어피니티 사용 |

**실용적 예: 고우선순위 워크로드 제한**

```yaml
spec:
  hard:
    requests.cpu: "10"
    requests.memory: 20Gi
  scopeSelector:
    matchExpressions:
      - scopeName: PriorityClass
        operator: In
        values: ["high-priority"]
```

팀이 무한정 `high-priority`를 남발해 다른 팀 Pod를 선점하는 것을 막는다.

### 쿼터 초과 시 동작

**Pod 생성이 거부된다.** 이미 실행 중인 Pod는 영향받지 않는다.

```bash
kubectl describe replicaset <name>
# Warning  FailedCreate  Error creating: pods "web-abc" is forbidden:
#   exceeded quota: team-a-quota, requested: requests.cpu=2,
#   used: requests.cpu=19, limited: requests.cpu=20
```

**중요**: Deployment는 계속 재시도한다. 이벤트를 모니터링하지 않으면 "왜 스케일이 안 되지?"라고 한참 헤맬 수 있다. 31장에서 쿼터 사용률 알림을 설정한다.

## 13.3 LimitRange

### 세 가지 역할

LimitRange는 **개별 컨테이너/Pod** 수준에서 동작한다. ResourceQuota가 총량이라면 LimitRange는 개별 값이다.

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: team-a-limits
  namespace: team-a
spec:
  limits:
    # --- 컨테이너 단위 ---
    - type: Container
      default:                  # ① limits 기본값
        cpu: 500m
        memory: 512Mi
      defaultRequest:           # ② requests 기본값
        cpu: 100m
        memory: 128Mi
      min:                      # ③ 최솟값 (이보다 작으면 거부)
        cpu: 10m
        memory: 32Mi
      max:                      # ④ 최댓값 (이보다 크면 거부)
        cpu: "4"
        memory: 8Gi
      maxLimitRequestRatio:     # ⑤ limits/requests 비율 상한
        cpu: "10"
        memory: "4"

    # --- Pod 단위 (모든 컨테이너 합계) ---
    - type: Pod
      max:
        cpu: "8"
        memory: 16Gi

    # --- PVC 단위 ---
    - type: PersistentVolumeClaim
      min:
        storage: 1Gi
      max:
        storage: 100Gi
```

### 각 필드의 의미

**`default` / `defaultRequest` — 기본값 주입**

컨테이너에 `resources`를 안 쓰면 이 값이 자동으로 들어간다. **ResourceQuota와 함께 쓸 때 필수적이다.**

```yaml
# 개발자가 쓴 것
containers:
  - name: app
    image: web:1.0
    # resources 없음

# 어드미션 후 실제 저장되는 것
containers:
  - name: app
    image: web:1.0
    resources:
      requests: { cpu: 100m, memory: 128Mi }    # defaultRequest에서
      limits:   { cpu: 500m, memory: 512Mi }    # default에서
```

**`min` / `max` — 범위 강제**

```
Error from server (Forbidden): pods "big" is forbidden:
maximum memory usage per Container is 8Gi, but limit is 16Gi
```

한 컨테이너가 노드 전체를 차지하는 것을 막는다.

**`maxLimitRequestRatio` — 오버커밋 제한**

```yaml
maxLimitRequestRatio:
  memory: "4"
```

`requests: 1Gi, limits: 8Gi`는 비율이 8이라 거부된다. `limits: 4Gi`까지만 허용된다.

**왜 이것이 필요한가?** requests가 낮고 limits가 높으면 스케줄러는 "이 Pod는 조금만 쓴다"고 판단해 많이 배치하는데, 실제로는 limits까지 쓸 수 있어 **노드가 과부하된다.** 14장에서 이 문제를 자세히 다룬다.

### 여러 LimitRange

한 네임스페이스에 여러 개를 만들 수 있지만 **혼란스러워지므로 권장하지 않는다.** 기본값은 첫 번째로 매칭되는 것이 적용되고, 제약은 모두 검사된다.

## 13.4 실습: 쿼터와 리밋 적용

**① 네임스페이스와 정책 생성**

```yaml
# tenant.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: team-a
  labels:
    team: alpha
---
apiVersion: v1
kind: LimitRange
metadata:
  name: defaults
  namespace: team-a
spec:
  limits:
    - type: Container
      default:
        cpu: 200m
        memory: 256Mi
      defaultRequest:
        cpu: 50m
        memory: 64Mi
      min:
        cpu: 10m
        memory: 16Mi
      max:
        cpu: "1"
        memory: 1Gi
---
apiVersion: v1
kind: ResourceQuota
metadata:
  name: quota
  namespace: team-a
spec:
  hard:
    requests.cpu: "1"
    requests.memory: 2Gi
    limits.cpu: "2"
    limits.memory: 4Gi
    pods: "10"
    services.loadbalancers: "0"      # LB 금지
```

```bash
kubectl apply -f tenant.yaml
```

**② 기본값 주입 확인**

```bash
kubectl run nginx -n team-a --image=nginx:alpine
kubectl get pod nginx -n team-a -o jsonpath='{.spec.containers[0].resources}' | jq
```

```json
{
  "limits":   { "cpu": "200m", "memory": "256Mi" },
  "requests": { "cpu": "50m",  "memory": "64Mi" }
}
```

**아무것도 지정하지 않았는데 값이 들어갔다.** LimitRange가 어드미션 단계에서 주입한 것이다.

**③ 최댓값 초과 시 거부**

```bash
kubectl run big -n team-a --image=nginx:alpine \
  --overrides='{"spec":{"containers":[{"name":"big","image":"nginx:alpine","resources":{"limits":{"memory":"4Gi"}}}]}}'
```

```
Error from server (Forbidden): pods "big" is forbidden:
maximum memory usage per Container is 1Gi, but limit is 4Gi
```

**④ 쿼터 소진**

```bash
kubectl create deployment many -n team-a --image=nginx:alpine --replicas=15
sleep 5
kubectl get pods -n team-a | wc -l
kubectl describe rs -n team-a | grep -A3 "FailedCreate"
```

```
Warning  FailedCreate  Error creating: pods "many-xyz" is forbidden:
  exceeded quota: quota, requested: pods=1, used: pods=10, limited: pods=10
```

**Pod 10개에서 멈췄다.**

**⑤ 쿼터 사용량 확인**

```bash
kubectl describe resourcequota quota -n team-a
```

**⑥ LoadBalancer 금지 확인**

```bash
kubectl expose deployment many -n team-a --type=LoadBalancer --port=80
```
```
Error from server (Forbidden): services "many" is forbidden:
exceeded quota: quota, requested: services.loadbalancers=1,
used: services.loadbalancers=0, limited: services.loadbalancers=0
```

**⑦ 정리**

```bash
kubectl delete namespace team-a
```

## 13.5 멀티테넌시 패턴

### 두 종류의 테넌트

설계는 **"테넌트가 누구인가"** 에 따라 완전히 달라진다.

| | **소프트 멀티테넌시** | **하드 멀티테넌시** |
|---|---|---|
| 테넌트 | 같은 조직의 다른 팀 | 서로 신뢰하지 않는 고객, 외부 사용자 |
| 신뢰 수준 | 서로 신뢰함 | **신뢰하지 않음** |
| 위협 모델 | 실수로 인한 영향 | **의도적 공격** |
| 커널 공유 | 허용 | 위험 |
| 구현 | 네임스페이스 + 쿼터 + NetworkPolicy + RBAC | 별도 클러스터 또는 샌드박스 런타임 |

> **핵심 판단 기준**
>
> **테넌트가 임의의 코드를 실행할 수 있는가?** 그렇다면 네임스페이스 격리로는 부족하다. 2.1절에서 본 대로 컨테이너의 격리 경계는 커널이고, 커널 취약점은 계속 발견된다.
>
> SaaS에서 고객이 자기 코드를 올리는 구조라면 **클러스터를 분리하거나 gVisor/Kata 같은 샌드박스 런타임을 써야 한다.**

### 소프트 멀티테넌시 구현 체크리스트

같은 조직 안의 팀 분리라면 다음을 조합한다.

```yaml
# ① 네임스페이스 + 라벨
apiVersion: v1
kind: Namespace
metadata:
  name: team-a
  labels:
    team: alpha
    cost-center: "1234"
    pod-security.kubernetes.io/enforce: baseline    # 18장
    pod-security.kubernetes.io/warn: restricted
---
# ② 자원 총량 제한
apiVersion: v1
kind: ResourceQuota
# ... 13.2절
---
# ③ 개별 컨테이너 기본값과 범위
apiVersion: v1
kind: LimitRange
# ... 13.3절
---
# ④ 네트워크 격리 — 기본 거부 (18장)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: team-a
spec:
  podSelector: {}
  policyTypes: [Ingress]
---
# ⑤ 같은 네임스페이스 내부는 허용
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-same-namespace
  namespace: team-a
spec:
  podSelector: {}
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector: {}
---
# ⑥ DNS는 반드시 허용 (10.6절에서 경고한 함정)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns
  namespace: team-a
spec:
  podSelector: {}
  policyTypes: [Egress]
  egress:
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: kube-system
      ports:
        - { protocol: UDP, port: 53 }
        - { protocol: TCP, port: 53 }
---
# ⑦ RBAC — 팀은 자기 네임스페이스만 (17장)
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: team-a-admin
  namespace: team-a
subjects:
  - kind: Group
    name: team-alpha
roleRef:
  kind: ClusterRole
  name: admin              # 내장 역할
  apiGroup: rbac.authorization.k8s.io
```

여기에 **노드 분리**를 더할 수 있다(15장).

```yaml
# 팀 전용 노드 풀에 테인트를 걸고
kubectl taint nodes node-a team=alpha:NoSchedule
kubectl label nodes node-a team=alpha

# 팀 Pod에 toleration과 어피니티를 강제 (정책 엔진으로)
```

### 네임스페이스를 어떻게 나눌 것인가

실무에서 자주 논쟁이 되는 부분이다.

| 전략 | 예시 | 장점 | 단점 |
|---|---|---|---|
| **팀별** | `team-a`, `team-b` | 권한 관리가 단순 | 팀 내 환경 구분 불가 |
| **환경별** | `dev`, `staging`, `prod` | 환경 정책 일관 | 팀 격리 안 됨 |
| **팀+환경** | `team-a-dev`, `team-a-prod` | 둘 다 만족 | 네임스페이스 수 폭발 |
| **애플리케이션별** | `shop`, `payment`, `auth` | 서비스 경계와 일치 | 소유 팀이 모호할 수 있다 |

**환경은 클러스터로 나누는 것이 일반적이다.**

```
dev-cluster       → 네임스페이스는 팀/앱별
staging-cluster
prod-cluster
```

이유: 프로덕션과 개발이 같은 클러스터에 있으면 컨트롤 플레인 장애나 노드 문제가 프로덕션에 전파된다. 클러스터 업그레이드도 프로덕션에서 먼저 테스트할 수 없다.

**작은 조직**이라면 클러스터 하나에 `dev`/`prod` 네임스페이스로 시작하고, 성장하면서 분리하는 것이 현실적이다.

## 13.6 계층적 네임스페이스와 가상 클러스터

### 네임스페이스의 확장성 문제

팀이 20개, 각 팀이 앱을 5개씩 운영하면 네임스페이스가 100개다. 각각에 ResourceQuota, LimitRange, NetworkPolicy, RBAC을 만들어야 한다. **수백 개의 리소스를 일관되게 관리하는 것이 새로운 문제**가 된다.

### Hierarchical Namespace Controller (HNC)

네임스페이스에 부모-자식 관계를 만들고, **정책을 상속**시킨다.

```
org
├── team-a
│   ├── team-a-dev
│   └── team-a-prod
└── team-b
    ├── team-b-dev
    └── team-b-prod
```

```bash
kubectl hns create team-a-dev -n team-a
kubectl hns tree org
```

부모에 만든 RoleBinding, NetworkPolicy, ResourceQuota가 **자식으로 전파된다.** 새 하위 네임스페이스를 만들어도 정책이 자동 적용된다.

```yaml
# 전파할 리소스 타입 지정
apiVersion: hnc.x-k8s.io/v1alpha2
kind: HNCConfiguration
metadata:
  name: config
spec:
  resources:
    - resource: networkpolicies
      mode: Propagate
    - resource: limitranges
      mode: Propagate
    - resource: secrets
      mode: Propagate
```

### 가상 클러스터 (vCluster)

**한 클러스터 안에 가상의 쿠버네티스 클러스터를 만든다.**

```
호스트 클러스터
└── namespace: vcluster-team-a
    └── [가상 컨트롤 플레인: k3s + syncer]
         ↑ 테넌트는 이것을 자기 클러스터로 인식
```

```bash
vcluster create team-a --namespace vcluster-team-a
vcluster connect team-a
kubectl get nodes        # 가상 클러스터의 뷰
```

**테넌트가 얻는 것**
- 자기만의 API 서버 → **CRD를 자유롭게 설치**할 수 있다
- `cluster-admin` 권한 → 네임스페이스를 마음대로 만든다
- ClusterRole, IngressClass 등 클러스터 스코프 리소스를 격리해서 쓴다

**실제로는**: vCluster 안에서 만든 Pod는 syncer가 호스트 클러스터의 실제 네임스페이스로 옮겨 실행한다. 노드와 커널은 여전히 공유된다.

**언제 쓰는가**
- 팀이 CRD나 오퍼레이터를 각자 설치해야 할 때
- 개발자마다 격리된 클러스터 환경이 필요할 때
- 클러스터를 여러 개 운영하기에는 비용이 부담될 때

**한계**: 커널을 공유하므로 **하드 멀티테넌시 요구는 여전히 충족하지 못한다.** 노드까지 분리하려면 별도 클러스터가 답이다.

### 선택 가이드

```
테넌트가 서로 신뢰하는가?
├─ 아니오 (외부 고객, 임의 코드 실행)
│   → 별도 클러스터 (+ 샌드박스 런타임)
│
└─ 예 (같은 조직의 팀)
    └─ 테넌트가 CRD/오퍼레이터를 각자 설치해야 하는가?
        ├─ 예 → vCluster
        └─ 아니오
            └─ 네임스페이스가 수십 개 이상인가?
                ├─ 예 → HNC로 정책 상속
                └─ 아니오 → 네임스페이스 + 쿼터 + NetworkPolicy + RBAC
```

## 13.7 비용 배분

멀티테넌시의 실무적 목적 중 하나는 **팀별 비용 청구**다.

**라벨 기반 추적**

```yaml
metadata:
  labels:
    team: alpha
    cost-center: "1234"
    app.kubernetes.io/part-of: shop-system
```

**도구**

| 도구 | 특징 |
|---|---|
| **OpenCost** | CNCF 프로젝트. 네임스페이스/라벨별 비용 계산 |
| **Kubecost** | OpenCost 기반 상용. 대시보드와 알림 |
| 클라우드 네이티브 | AWS Split Cost Allocation, GKE Cost Allocation |

**계산 방식**: 각 Pod의 `requests`와 실행 시간을 노드 비용에 안분한다. 그래서 **requests를 정확히 설정하는 것이 비용 배분의 전제**다. 다음 장의 주제다.

```bash
# OpenCost 예시 쿼리
kubectl cost namespace --window 7d
```

## 실습 과제

**과제 1 — 쿼터 없이 LimitRange만, LimitRange 없이 쿼터만**
두 가지 경우를 각각 만들어 어떤 문제가 생기는지 확인한다.
- ResourceQuota만: `resources`를 안 쓴 Pod가 거부되는 것을 확인
- LimitRange만: 기본값은 들어가지만 네임스페이스 총량은 제한되지 않는 것을 확인

**과제 2 — maxLimitRequestRatio 실험**
`maxLimitRequestRatio: {memory: "2"}`를 설정하고, `requests: 100Mi / limits: 500Mi`인 Pod를 만들어 거부되는 것을 확인한다. 이 제한이 없을 때 노드가 어떻게 과부하될 수 있는지 설명해 본다(14장 예습).

**과제 3 — 네임스페이스 격리의 한계 확인**
`team-a`와 `team-b` 네임스페이스를 만들고, `team-a`의 Pod에서 `team-b`의 Service에 접근되는 것을 확인한다. 그다음 13.5절의 NetworkPolicy를 적용해 차단되는 것을 확인하고, **DNS 예외를 빠뜨렸을 때** 무슨 일이 생기는지도 관찰한다(10.6절 복습).

**과제 4 — scopeSelector로 조건부 쿼터**
`BestEffort` 스코프의 쿼터를 `pods: "3"`으로 설정하고, `resources`를 명시한 Pod와 명시하지 않은 Pod가 각각 어느 쿼터에 카운트되는지 확인한다. (LimitRange가 있으면 BestEffort Pod가 생기지 않는다는 점도 관찰해 보자.)

## 요약

- **네임스페이스는 보안 경계가 아니다.** 이름 스코프, DNS 스코프, RBAC 그룹, 쿼터 단위를 제공할 뿐이다. 네트워크는 기본적으로 열려 있고, 노드와 커널과 컨트롤 플레인은 공유된다.
- **ResourceQuota**는 네임스페이스 총량을, **LimitRange**는 개별 컨테이너를 제어한다. 컴퓨트 쿼터가 있으면 모든 컨테이너가 requests/limits를 명시해야 하므로, **LimitRange의 기본값과 함께 쓰는 것이 사실상 필수**다.
- `services.loadbalancers` 쿼터로 클라우드 LB 비용 폭주를 막고, `maxLimitRequestRatio`로 과도한 오버커밋을 막는다.
- **소프트 멀티테넌시**(같은 조직의 팀)는 네임스페이스 + 쿼터 + NetworkPolicy + RBAC + PSA의 조합으로 구현한다. **하드 멀티테넌시**(신뢰할 수 없는 테넌트)는 커널 공유 때문에 별도 클러스터나 샌드박스 런타임이 필요하다.
- 판단 기준은 **"테넌트가 임의의 코드를 실행할 수 있는가"** 다.
- 네임스페이스가 수십 개를 넘으면 **HNC로 정책을 상속**시키고, 테넌트가 CRD를 각자 설치해야 하면 **vCluster**를 검토한다. 환경(dev/prod)은 대개 클러스터로 나누는 편이 안전하다.
- 비용 배분은 **requests 기반**으로 계산되므로, 정확한 리소스 설정이 전제 조건이다.

**다음 장에서는** 그 requests와 limits를 제대로 설정하는 방법을 다룬다. 두 값이 스케줄링·QoS·축출에 각각 어떤 영향을 주는지, 그리고 CPU와 메모리가 왜 비대칭적으로 동작하는지 살펴본다.
