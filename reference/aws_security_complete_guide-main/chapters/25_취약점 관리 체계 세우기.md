# 25장. 취약점 관리 체계 세우기

> **이 장에서 다루는 것**
> - **클라우드에서 달라지는 점** — 변화 속도, 짧은 수명의 자산, 전통 6단계 프로세스가 4단계로 접히는 과정
> - **취약 지점 7계층** 🔴 — 데이터 접근 / 애플리케이션 / 미들웨어 / OS / 네트워크 / 가상 인프라 / 물리 인프라의 **책임 주체와 AWS 탐지 수단** 매핑
> - **관리 프로세스** — 발견 → 우선순위 → 조치 → 검증 → 보고. 리스크 등록부, 예외의 만료일, 변경 관리
> - **우선순위 결정** — CVSS 기본 점수의 한계와 **노출 × 민감도 × 악용 가능성** 3축 매트릭스
> - **지표 6종** 🔴 — 도구 커버리지, MTTR, 미조치 비율, 오탐률, 미탐률, 재발률
> - **지표의 함정** ⚠️ — 스캔하지 않으면 취약점이 0으로 보인다
>
> **선행 지식**: 2장(공동 책임), 4장(데이터 분류), 12장(자산 관리 누수), 22장(호스트 보호), 24장(컨테이너·서버리스)
> **난이도**: ★★★

4부는 ShopMini의 네트워크·호스트·컨테이너를 하나씩 잠갔습니다. 남은 질문은 하나입니다. **"그 구성 안에 지금 어떤 결함이 있고, 무엇부터 고칠 것인가."**

> 📖 *Practical Cloud Security* 1판·2판 5장은 이 장을 신화로 엽니다. **"그리스 신화에서 아킬레우스는 그의 유일한 약점인 발뒤꿈치에 화살을 맞고 죽었다. 아킬레우스에게는 분명 더 나은 취약점 관리 계획이 필요했다! 단 하나의 취약 부위만 가졌던 아킬레우스와 달리, 당신의 클라우드 환경에는 취약점이 나타날 수 있는 여러 다른 영역이 있다. 접근 통제를 잠근 뒤, 잠재적 취약점을 관리하는 지속적 프로세스를 마련하는 것은 대개 보안을 개선하기 위해 할 수 있는 최선의 투자다."**

접근 통제(2부) 다음이 취약점 관리라는 우선순위는 이 책의 부 구성과 일치합니다. 이 장은 **체계와 프로세스**를 다루고, 개별 도구의 설정은 26장이 이어받습니다. 시작 전에 용어를 하나 정리합니다.

> 📖 1판·2판 5장 「Vulnerability Versus Patch Management」: **"'취약점 관리'와 '패치 관리'라는 용어는 종종 혼용되지만 서로 다르다. 소프트웨어 패치는 보안 취약점 외에 기능적 문제도 자주 고치며, 모든 취약점이 패치 적용으로 고쳐지는 것은 아니다. 예를 들어 당신의 취약점 관리 프로세스는 패치 없이 고쳐지는 안전하지 않은 구성을 식별할 수도 있고, 패치를 적용하는 대신 기능을 꺼서 취약점을 완화할 수도 있다."**

이 구분이 실무에서 중요한 이유는 25.5의 MTTR 때문입니다. **"패치를 적용한 건수"만 세면 기능을 꺼서 해결한 건이 조치로 잡히지 않고, 팀은 지표가 나빠지기 싫어 잘못된 선택을 합니다.**

## 25.1 클라우드에서 달라지는 점

### 변화 속도가 스캔 주기를 앞지른다

> 📖 1판·2판 5장 「Differences from Traditional IT」: **"클라우드 환경에서는 변화 속도가 온프레미스보다 훨씬 빠른 경우가 많고, 이 끊임없는 변화는 전통적인 취약점 관리 프로세스를 뒤처지게(leave in the dust) 만들 수 있다. 3장에서 논의했듯이, 새 시스템이 온라인 상태가 될 때 놓치지 않으려면 클라우드 API의 인벤토리를 사용해 생성되는 즉시 각 시스템을 취약점 관리 도구에 투입해야 한다."**

온프레미스의 스캔은 "매주 화요일 새벽 2시, 10.0.0.0/16" 같은 형태였고, 자산 목록이 한 달에 몇 건씩만 바뀌었기에 통했습니다. ShopMini의 앱 티어에서는 그 전제가 무너집니다.

| 클라우드의 사실 | 전통 스캔이 깨지는 지점 |
|---|---|
| Auto Scaling으로 트래픽에 따라 인스턴스가 뜨고 진다 | 야간 스캔 시각에 존재하지 않던 인스턴스는 영원히 스캔되지 않는다 |
| 스팟 인스턴스·Fargate 태스크의 수명이 수십 분 | "다음 주 스캔 주기"보다 자산 수명이 짧다 |
| 배포마다 인스턴스가 통째로 교체된다 | 스캔 결과의 리소스 ID가 다음 스캔 때 이미 없는 ID다 |
| 계정·리전이 수십 개 | 스캔 대상 IP 목록을 사람이 유지할 수 없다 |
| 개발자가 콘솔에서 리소스를 직접 만든다 | 스캔 대상 목록에 등재되는 절차 자체가 없다 |

해법의 방향은 원서가 이미 말했습니다. **스캔 대상 목록을 사람이 관리하지 말고 클라우드 API의 인벤토리를 그대로 먹이십시오.** AWS에서는 Inspector의 자동 활성화(새로 생기는 EC2·ECR 리포지터리·Lambda 함수를 자동 포함) + Config 인벤토리 + Organizations 위임 관리자 구성이 그 구현입니다. 12.5의 **도구 누수** — 자산은 인벤토리에 있는데 스캐너가 보지 않는 상태 — 가 정확히 이 지점입니다.

### 컨테이너에는 무거운 에이전트를 넣을 수 없다

> 📖 2판 5장: **"컨테이너가 많다면, 가상 머신에서처럼 CPU를 몇 퍼센트씩 쓰는 무거운 취약점 관리 도구를 모든 컨테이너에 넣을 수는 없다. 결국 시스템에서 에이전트 사본을 수백 개 돌리게 되어 정작 진짜 일에 쓸 CPU 시간이 남지 않을 것이다!"**
>
> 1판은 이를 **"You cannot put a heavyweight vulnerability management tool ... in every container"** 로 조건 없이 단정했고, 2판이 **"If you have a lot of containers,"** 라는 전제를 앞에 붙였습니다. 표현은 누그러졌지만 결론은 같습니다.

24장에서 컨테이너 스캔을 실행 중인 컨테이너가 아니라 **레지스트리(ECR)의 이미지**에 대해 설계한 근거가 여기 있습니다. 스캔 지점이 런타임에서 **아티팩트**로 옮겨간 것입니다.

### 프로세스가 6단계에서 4단계로 접힌다

> 📖 1판·2판 5장이 제시하는 **전통적 프로세스**는 여섯 단계입니다. ① 업데이트 발견 → ② 사고 리스크에 따른 우선순위 → ③ 테스트 환경 시험 → ④ 프로덕션 일정 수립 → ⑤ 배포 → ⑥ 프로덕션 동작 검증. 설계 의도는 이렇습니다. **"이런 유형의 프로세스는 보안 사고의 리스크와 프로덕션 환경의 가용성 사고 리스크를 저울질하도록 합리적으로 설계된 것이다. 내가 자주 하는 말로, 보안은 쉽다 — 전부 끄고 콘크리트에 묻어버리면 된다. 환경을 계속 돌아가고 쓸 수 있게 유지하면서 보안을 지키는 것이 훨씬 어렵다."**

원서는 IaC·CI/CD·마이크로서비스가 **가용성 리스크 쪽 저울을 가볍게 만들어** 균형점을 옮긴다고 설명합니다. 수평 확장에는 각주가 붙습니다. 📖 **"취약점 스캔의 장벽 중 하나는 실제로 취약점을 찾아냈을 때 스캔이 해당 컴포넌트를 다운시키는 경우가 있다는 것이다. 문제를 찾긴 했지만 다운타임이라는 대가를 치른 것이다!"** 한 번에 인스턴스 하나만 죽는다면 이 대가가 훨씬 쌉니다. 원서의 **새 프로세스**는 이렇습니다.

| 단계 | 원서의 새 프로세스 | ShopMini에서의 구현 |
|---|---|---|
| ① | 가용한 보안 업데이트를 **일상 개발 활동의 일부로 자동으로 끌어온다**. 정기적으로 하면 변경이 작고 소화하기 쉬워진다 | Dependabot/Renovate류의 의존성 PR + 베이스 이미지 주간 재빌드 |
| ② | 업데이트를 **다른 애플리케이션 변경과 함께** 평소 테스트 흐름에서 시험한다. 이 단계에서 문제가 발견된 경우에만 그 업데이트를 포함할지 되돌아가 판단한다 | 파이프라인의 단위·통합 테스트 + 이미지 스캔 게이트(27~28장) |
| ③ | 새 버전을 배포하면 코드 변경·보안 업데이트·구성 변경을 포함한 **새 프로덕션 환경이 자동 생성**된다. 많은 경우 처음에는 프로덕션 트래픽의 일부만 받게 해서, 문제가 있어도 소수 사용자만 영향받고 롤백된다 | ECS/EKS 롤링·블루그린 배포, ALB 가중치 기반 트래픽 전환 |
| ④ | 정상 배포 흐름으로 커버되지 않는 취약점을 테스트·프로덕션 환경에서 발견해 처리하고, **개발 백로그에 버그로 등록**해 다음 이터레이션(정말 급하면 특별 릴리스)에서 해결한다 | Inspector·Security Hub 결과 → 이슈 트래커 자동 등록 |
|  | 📖 **"4단계에는 여전히 수작업 취약점 관리가 남지만, 표준 프로세스보다 훨씬 적다."** | |

여기서도 두 판의 표현이 갈립니다. 1판은 이 변화가 **"전반적 가용성을 떨어뜨리지 않으면서(without lowering)"** 보안 업데이트를 선제적으로 만든다고 썼고, 2판은 **"시스템의 전반적 가용성을 오히려 높이면서(while still raising)"** 로 바꿔 썼습니다.

**실무적으로 이 전환의 핵심은 "패치"라는 단어가 사라진다는 점입니다.** 앱 인스턴스에 `yum update`를 하는 대신 패치된 골든 AMI·베이스 이미지를 다시 만들어 배포합니다(불변 인프라). 패치는 **배포**가 되고, 취약점 관리는 **릴리스 주기 문제**가 됩니다. 릴리스가 분기 1회인 팀은 아무리 좋은 스캐너를 사도 MTTR이 90일 밑으로 내려가지 않습니다.

## 25.2 취약 지점 7계층 🔴

### 스택으로 보기

> 📖 1판·2판 5장 「Vulnerable Areas」: **"당신의 애플리케이션이, 맨 위에 애플리케이션이 있고 맨 아래에 물리적 컴퓨터와 시설이 있는 컴포넌트 스택의 일부라고 상상해 보라. (…) 스택의 항목을 분류하는 방법은 여러 가지지만, 우리는 1장의 공동 책임 모델 다이어그램을 쓰겠다."**
>
> 2판은 여기에 **"당신의 책임은 전달 모델(IaaS, PaaS, SaaS)에 따라 달라진다"** 를 더하고, 각 계층 제목 아래에 **"Consumer responsibility for IaaS, PaaS, and SaaS"** 같은 책임 라벨을 붙였습니다. 1판에는 이 라벨이 없습니다.

### 🔴 7계층 × 책임 주체 × AWS 탐지 수단

**반드시 이 표를 만들고 "탐지 수단" 칸을 비워 두지 마십시오.** 빈 칸은 "이 계층에 취약점이 없다"가 아니라 **"이 계층은 보지 않고 있다"** 입니다.

| # | 계층 | 원서가 명시한 책임(2판) | AWS에서 실제로 누가 | AWS 탐지 수단 | 관련 장 |
|---|---|---|---|---|---|
| 1 | **데이터 접근**(Data Access) | IaaS·PaaS·SaaS **모두 고객** | 고객 (예외 없음) | IAM Access Analyzer, S3 퍼블릭 액세스 차단 상태, Config 규칙, Macie | 6~10, 12 |
| 2 | **애플리케이션**(Application) | IaaS·PaaS 고객 (SaaS는 제공자, 단 설정은 고객) | 고객 | Inspector(Lambda 코드 스캔·SCA), CodeGuru Security, SAST/DAST/SCA | 26, 27, 28 |
| 3 | **미들웨어**(Middleware) | IaaS·일부 PaaS 고객 | **RDS·ElastiCache 등 관리형은 AWS가 패치, 적용 시점 승인은 고객** | RDS 보류 중 유지 관리, Inspector(EC2 위 미들웨어), Config·Security Hub 보안 표준 | 15, 26 |
| 4 | **운영체제**(Operating System) | IaaS 고객 | EC2는 고객, Fargate·Lambda는 AWS | Inspector(SSM 에이전트 경유), SSM Patch Manager 컴플라이언스, ECR 향상 스캔 | 22, 24, 26 |
| 5 | **네트워크**(Network) | IaaS 고객 | 물리 네트워크 장비는 AWS. **논리 구성(SG/NACL/라우팅)은 고객** | VPC Reachability Analyzer, Network Access Analyzer, Config 규칙, Inspector 네트워크 도달성 | 18~21 |
| 6 | **가상화 인프라**(Virtualized Infrastructure) | **제공자 책임** | 하이퍼바이저(Nitro)는 AWS. **EKS 워커·컨테이너 런타임·K8s 오브젝트는 고객** | EKS 버전/애드온 상태, Inspector(워커 노드), 파드 보안 승인 | 24 |
| 7 | **물리 인프라**(Physical Infrastructure) | **제공자 책임** | AWS (Outposts·Dedicated Host도 물리 계층은 AWS) | 직접 탐지 불가 → **AWS Artifact의 감사 보고서로 검증** | 2, 36 |

각 계층에 대해 원서가 짚은 핵심은 이렇습니다.

**1. 데이터 접근** — 📖 **"데이터 접근 계층의 취약점은 거의 언제나 접근 관리 문제로 귀결된다 — 리소스를 공개로 열어두거나, 더 이상 필요 없는 개인에게 접근 권한을 그대로 두거나, 부실한 자격 증명을 쓰는 것."** 이 계층에는 CVE가 없습니다. **CVE 목록만 보는 프로그램은 가장 큰 사고 원인인 이 계층을 통째로 놓칩니다.** `shopmini-uploads` 버킷 정책 한 줄이 어떤 CVSS 9.8보다 위험합니다.

**2. 애플리케이션** — 📖 **"당신의 팀이 아무리 뛰어나도 당신의 코드에는 거의 확실히 버그가 있을 것이고, 그중 적어도 일부는 보안에 영향을 줄 가능성이 높다."** 그리고 상속 코드에 대한 경고가 이어집니다. 📖 2판: **"Log4j, Apache Struts, OpenSSL 같은 인기 오픈소스 컴포넌트의 취약점은 그것을 사용하는 많은 애플리케이션의 취약점으로 이어져 왔다. 공격자에게는 특정 애플리케이션 코드를 연구하는 것보다 이런 취약점을 익스플로잇하는 것이 훨씬 쉬우므로, 당신이 작성한 코드의 취약점보다 오히려 더 높은 리스크인 경향이 있다."** 1판은 이 자리에 **Apache Struts와 OpenSSL만** 열거했고 Log4j는 2판에서 추가되었습니다. 2판은 상속 코드의 위험을 **"취약점 또는 멀웨어"** 로 확장했고, 예시도 OWASP Top 10 **2017**(인젝션, XXE, XSS, 역직렬화)에서 **2021**(취약한 접근 통제, 인젝션, 취약하고 오래된 컴포넌트)로 갈아탔습니다.

**3. 미들웨어** — 📖 **"이 컴포넌트들이 클라우드 제공자에 의해 서비스로 제공된다면 보통 제공자가 패치 책임을 진다. 그런데 함정이 있다! 어떤 경우에는 업데이트가 자동으로 푸시되지 않는데, 중단을 일으킬 수 있기 때문이다. 그런 경우 여전히 당신이 테스트하고 편한 시점에 버튼을 눌러 업데이트를 배포할 책임이 있을 수 있다."** RDS의 보류 중인 유지 관리 작업이 이 "버튼"입니다. **RDS를 쓰니 DB 패치는 AWS가 알아서 한다는 이해는 절반만 맞습니다.** 📖 **"컨테이너에 설치된 항목은 가상 머신에 설치된 것을 인벤토리하는 도구로는 보통 찾아내지 못한다"** — 24장에서 이미지 스캔을 별도로 세운 이유입니다. 구성 결함 예시로는 웹 서버의 패스워드 파일 열람 허용, 잘못된 DB 인증 구성, Java 앱 서버의 디버그 출력에 의한 비밀번호 노출을 들고, 벤치마크는 **CIS Benchmarks** 에서 출발하라고 권합니다.

**4. 운영체제** — 📖 **"운영체제는 당신 환경에 필요 없는 여러 컴포넌트를 함께 담아 출하되는 경향이 있다. (…) 필요하지 않은 것은 모두 끄는 것이 중요하다. 이를 흔히 하드닝(hardening)이라 부른다. 컨테이너의 한 가지 장점은 흔히 최소 컨테이너 이미지에서 시작해 애플리케이션 실행에 필요한 것만 설치하므로, 기본적으로 컨테이너를 하드닝하는 결과가 된다는 것이다."** 22장의 골든 AMI와 24장의 최소 베이스 이미지가 같은 원리의 두 구현입니다.

**5. 네트워크** — 📖 **"네트워크 계층의 취약점 관리는 두 가지 주요 과제를 포함한다: 네트워크 컴포넌트 자체를 관리하는 것과, 어떤 네트워크 통신을 허용할지 관리하는 것."** AWS에서는 첫 번째(라우터·스위치·방화벽 장비의 패치)가 통째로 AWS 몫이 되고 **두 번째만 고객에게 남습니다.** 그래서 이 계층의 "스캔"은 CVE 스캔이 아니라 **경로 분석** — Reachability Analyzer로 "인터넷에서 isolated-data 서브넷의 3306에 닿는 경로가 있는가"를 묻는 일입니다.

**6. 가상화 인프라** — 📖 2판: **"IaaS 환경에서 가상화 인프라(가상 네트워크, 가상 머신, 스토리지)는 클라우드 제공자의 책임이다. 그러나 컨테이너 기반 환경에서는 제공자가 제공하는 것 위에 얹은 가상 인프라나 플랫폼에 대해 보안 책임을 질 수 있다. 예를 들어 Docker 같은 컨테이너 런타임이나 Kubernetes 같은 오케스트레이션 계층의 잘못된 구성이나 누락된 패치가 취약점의 원인이 될 수 있다."** **"제공자 책임"이라 적힌 이 행이 EKS를 쓰는 순간 고객 책임으로 되돌아옵니다.** 24장 4C 모델의 Cluster 계층이 여기입니다.

**7. 물리 인프라** — 📖 **"BIOS/마이크로코드 업데이트 누락이나, 물리 시스템의 원격 관리를 허용하는 베이스보드 관리 컨트롤러의 부실한 보안 구성으로 취약점이 발생할 수 있다."** 고객은 이 계층을 스캔할 수단이 없으므로 **"탐지"를 "검증"으로 대체합니다** — AWS Artifact에서 SOC 2 Type II·ISO 27001 보고서를 받아 확인하는 것이 전부이고, 그것으로 충분합니다.

### 🔴 계층별 도구를 한꺼번에 갖추려 하지 마십시오

> 📖 1판·2판 5장 「Finding and Fixing Vulnerabilities」: **"가성비가 가장 좋은 것부터 하라 — 조직에 가장 중요한 영역을 골라 거기서 가치를 얻은 뒤 다른 영역으로 넘어가라. 흔한 함정은 어딘가의 모범 사례 목록에 체크 표시를 하기 위해 네다섯 세트의 도구와 프로세스를 갖춰 놓고, 그중 어느 것도 취약점을 찾고 고치는 데 실제로 큰 가치를 제공하지 못하는 것이다."**

ShopMini처럼 **인터넷에 노출된 웹 애플리케이션이 핵심인 조직**의 순서는 ① 데이터 접근(1번), ② 애플리케이션 의존성(2번), ③ OS·이미지(4번)입니다. 6·7번은 AWS가 하고 있으니 뒤로 미룹니다.

## 25.3 취약점 관리 프로세스

### 5단계 사이클

취약점 관리는 **도구 도입이 아니라 사이클의 운영**입니다. 각 이음매가 12.5의 누수 지점과 대응합니다.

| 단계 | 하는 일 | 산출물 | 누수하면 |
|---|---|---|---|
| **① 발견** | 인벤토리 전체에 대해 계층별 스캔 실행 | 원시 findings | 도구 누수 — 스캔되지 않은 자산은 항상 "안전" |
| **② 우선순위** | 노출·민감도·악용 가능성으로 재점수화(25.4) | 처리 대기열 | 결과 누수 — CVSS 순 정렬은 대기열을 무한히 만든다 |
| **③ 조치** | 패치·구성 변경·기능 비활성화·보상 통제 | 변경 티켓, PR | 정책 기한 초과 건이 누적된다 |
| **④ 검증** | 재스캔으로 실제 해소 확인 | 상태 전이(해결됨) | "고쳤다고 티켓 닫았는데 안 고쳐짐" → 재발률 상승 |
| **⑤ 보고** | 지표 산출과 예외 재검토(25.5) | 대시보드, 리스크 등록부 | 경영진이 리스크를 모른 채 의사결정 |

**④ 검증을 티켓 종료로 대체하지 마십시오.** AWS에서 검증은 자동입니다 — 취약한 패키지가 사라지면 Inspector가 결과를 닫고 Security Hub의 `RecordState`가 `ARCHIVED`로 전이합니다. **사람이 `Workflow.Status`를 `RESOLVED`로 바꿨는데 `RecordState`가 여전히 `ACTIVE`라면 고쳐지지 않은 것입니다.** 이 두 필드의 불일치 건수만 세도 허위 종료가 드러납니다.

### 즉시 고칠 수 없는 것: 리스크 등록부

> 📖 1판·2판 5장 「Risk Management Processes」: **"이제 빠르게 고칠 수 없는 취약점의 우선순위를 정할 시스템이 필요하다. 여기서 '빠르게'는 보통 당신의 보안 정책에 있는 기간을 기준으로 정의된다. (…) 찾아낸 취약점 중 수용된 지침 안에서 처리할 수 없는 것은 각각 리스크로 평가되어야 하며, 그래야 나쁜 일이 일어날 가능성과 일어났을 때의 영향을 의식적으로 이해하게 된다."**
>
> 이 문단에서 1판과 2판이 갈립니다. 1판은 리스크 평가가 **"완화 전략(mitigation strategies)"** 으로 이어질 수 있다고만 썼고, 2판은 이를 **"가능성을 줄이기 위한 추가 통제(additional controls), 또는 영향을 줄이기 위한 완화(mitigations)"** 로 나눠 썼습니다. 4.1의 리스크 = 가능성 × 영향 공식과 맞물리는 정교화입니다. 양쪽 모두 **"시스템을 아예 꺼버리는 것 같은 회피(avoidance)"** 를 선택지로 남겨 둡니다.

> 📖 1판·2판 5장: **"정말 복잡한 리스크 관리 프로그램이 없어도 큰 가치를 얻을 수 있다. 리스크에 심각도를 부여하는 합의된 프로세스를 갖춘 단순한 리스크 등록부(risk register)만으로도 큰 도움이 된다. 그러나 미해결 취약점 각각에 대해 무엇을 할지 의식적으로 결정하기 전까지는 취약점 관리가 끝난 것이 아니다. 이 결정들은 (…) 주기적으로 — 이를테면 분기마다 — 재평가되어야 한다."** 처음부터 만들기보다 **NIST 800-30이나 ISO 31000** 을 쓰라는 권고도 함께 나옵니다. 이 지점의 누수는 📖 **"취약점을 찾았지만 즉시 고치지 못했고, 그것이 사업에 얼마나 나쁠 수 있는지도 실제로 이해하지 못했다는 뜻"** 입니다.

### 🔴 예외에는 반드시 만료일을 붙이십시오

원서의 "분기마다 재평가"를 AWS 구현으로 옮기면 **억제(suppression)에 만료일을 강제하는 것**입니다.

```bash
# Security Hub: 위험 수용 결정을 결과에 기록하고 억제 상태로 전이
aws securityhub batch-update-findings \
  --profile awssec-lab --region ap-northeast-2 \
  --finding-identifiers '[{"Id":"<finding-id>","ProductArn":"<product-arn>"}]' \
  --workflow Status=SUPPRESSED \
  --note Text="RISK-2026-014 승인 / 레거시 배치 서버 / 폐기예정 2026-12-31 / 재검토 2026-09-30",UpdatedBy="secops"
```

```bash
# Inspector: 억제 규칙 생성 (규칙 이름에 만료일을 넣어 회수 가능하게)
aws inspector2 create-filter \
  --profile awssec-lab --region ap-northeast-2 \
  --name "SUPPRESS-RISK-2026-014-expires-2026-12-31" \
  --action SUPPRESS \
  --filter-criteria '{"awsAccountId":[{"comparison":"EQUALS","value":"111122223333"}],"vulnerabilityId":[{"comparison":"EQUALS","value":"CVE-2024-XXXXX"}]}'
```

> ⚠️ **Security Hub의 `SUPPRESSED`도 Inspector의 억제 규칙도 자동 만료 기능이 없습니다.** 만료일을 이름·노트에만 적어 두면 아무도 회수하지 않습니다. **분기 1회, 억제 규칙 전체를 나열해 기한이 지난 것을 삭제하는 작업을 캘린더에 고정하십시오.** 담당자가 없으면 억제는 영구 면죄부가 됩니다.

### 심각도별 조치 기한(SLA)

원서가 말한 "보안 정책에 있는 기간"을 문서화하면 이렇게 됩니다. 이 표가 없으면 25.5의 MTTR도 "정책 기한 초과" 지표도 계산할 수 없습니다.

| 조정 후 심각도 | 인터넷 노출 자산 | 내부 전용 자산 | 초과 시 |
|---|---|---|---|
| **긴급**(KEV 등재 또는 실제 익스플로잇 확인) | **24시간** | 72시간 | 경영진 즉시 보고, 임시 차단(WAF 규칙·SG 축소) 병행 |
| **높음** | 7일 | 30일 | 리스크 등록부 등재 필수 |
| **보통** | 30일 | 90일 | 분기 리뷰 대상 |
| **낮음** | 90일 또는 다음 정기 재빌드 | 다음 정기 재빌드 | 기록만 |

### 변경 관리와의 관계

> 📖 1판·2판 5장 「Change Management」: **"가장 단순한 형태에서 변경 관리는 변경이 승인된 뒤에만 이루어지도록 보장하고, 변경에 따르는 리스크가 어느 정도 평가되도록 보장해야 한다. 변경 관리는 제안된 변경이 시스템에 새로운 보안 취약점을 들이지 않도록 함으로써 취약점 관리를 도울 수 있다. 잘못 운영되면 변경 관리는 취약점 해결에 필요한 변경을 늦춤으로써 취약점 관리를 방해하고 전체 리스크를 높일 수도 있다."**

**뒤쪽 경고가 실무에서 훨씬 자주 일어납니다.** 긴급 CVE 패치가 "다음 주 수요일 CAB 승인 대기"에 걸려 열흘을 흘려보내는 상황 말입니다. 원서의 해법은 절차를 없애는 것이 아니라 **되돌릴 수 있음을 근거로 사전 승인 범주를 만드는 것**입니다.

> 📖 1판·2판 5장: **"예를 들어 보안 수정과 함께 새 코드를 프로덕션에 푸시하는 것은, 좋은 상태로 빠르게 되돌아가는 프로세스가 입증되어 있다면, 변경 통제 위원회가 자동 승인하는 일상 업무(business-as-usual)일 수 있다. (…) 그러나 애플리케이션 설계 변경 같은 더 큰 변경은 여전히 수동 변경 관리 프로세스를 거쳐야 할 수 있다."** 그리고 **"이상적으로는 변경 통제 프로세스에 최소 한 명의 보안 실무자가 위원 또는 자문으로 참여해야 한다"**, **"문서화된 변경 관리 프로세스는 SOC 2, ISO 27001, PCI DSS를 포함한 여러 산업·규제 인증에서 요구된다"** 고 덧붙입니다.

ShopMini의 변경 관리는 세 갈래가 됩니다. **(가) 사전 승인** — 롤백이 입증된 파이프라인을 통한 코드·의존성·베이스 이미지 갱신. **(나) 표준 변경** — 보안 그룹·IAM 정책·Config 규칙 변경(동료 리뷰 + 자동 정책 검사). **(다) 수동 변경 관리** — 아키텍처 변경, 신규 계정·VPC, 데이터 분류 등급 변경. 인증 심사 대비상 **세 갈래 모두 기록이 남아야 한다**는 점은 같습니다.

## 25.4 우선순위 결정

### CVSS 기본 점수만으로 부족한 이유

> 📖 1판·2판 5장 「A Note on Vulnerability Scoring」: **"주어진 취약점에 대해 거의 모든 사람이 처음 던지는 질문은 '얼마나 나쁜가?'이다. '나쁨'에 대해 가장 널리 받아들여지는 표준은 CVSS다. (…) CVSSv2든 CVSSv3든 거기서 얻는 기본 점수(base number)는 당신의 환경과 당신의 조직에 대한 전체 이야기를 말해주지 않는다는 데 대부분의 보안 전문가가 동의한다. (…) CVSS 점수를 위협 환경과 당신의 구체적 환경에 맞게 조정할 방법을 갖추는 것이 중요하다."**
>
> 판 사이의 차이: 1판은 CVSS가 **"10년 넘게(for over a decade)"** 있었다고 쓰고, 2판은 **"2005년부터"** 로 바꿔 썼습니다. 두 판 모두 **"v2와 v3 두 메이저 버전이 널리 쓰인다"** 고 기술합니다.

> 💡 **원서 이후 변경** — CVSS v4.0이 2023년 FIRST에서 공개되어, 원서가 말한 temporal/environmental 조정이 위협(Threat)·환경(Environmental)·보충(Supplemental) 지표군으로 재편되었습니다. 다만 현장에서 유통되는 점수는 여전히 대부분 기본 점수이고, **원서의 결론 — "기본 점수는 전체 이야기가 아니다" — 은 그대로 유효합니다.**

기본 점수 내림차순으로 대기열을 정렬하면 무슨 일이 벌어지는지는 숫자로 분명합니다. ShopMini 규모의 계정에서도 심각·높음 결과는 수백~수천 건 나오지만, 그중 **인터넷에서 실제로 닿을 수 있고 익스플로잇이 공개되어 있으며 기밀 데이터 경로에 있는 것**은 대개 두 자릿수입니다. 함께 줄 세우면 그 두 자릿수가 묻힙니다.

### 3축 재점수화

**기본 점수는 "이 취약점이 얼마나 나쁜가"를 말하지만, 우리가 알아야 할 것은 "우리에게 얼마나 나쁜가"입니다.** 세 축을 곱합니다.

| 축 | 묻는 질문 | AWS에서 판정하는 근거 |
|---|---|---|
| **A. 노출**(Exposure) | 공격자가 이 자산에 닿을 수 있는가? | Inspector의 네트워크 도달성 분석, VPC Reachability Analyzer, ALB/CloudFront 뒤 여부, 퍼블릭 IP·퍼블릭 서브넷 배치 여부 |
| **B. 민감도**(Sensitivity) | 뚫리면 어떤 데이터가 나가는가? | 4.2의 `DataClass` 태그. 자산에 붙은 IAM 역할이 접근 가능한 리소스의 등급 |
| **C. 악용 가능성**(Exploitability) | 지금 실제로 악용되고 있는가? | **KEV 등재 여부**, **EPSS 점수**, Inspector 결과의 익스플로잇 가용 여부·수정 가용 여부 |

> 💡 **원서 이후 변경** — 원서 5장은 KEV와 EPSS를 다루지 않습니다. **KEV**(CISA Known Exploited Vulnerabilities)는 **실제 악용이 확인된** CVE만 모은 목록이고, **EPSS**(Exploit Prediction Scoring System, FIRST)는 향후 30일 내 악용 시도가 관측될 **확률**을 0~1로 추정합니다. 원서가 요구한 "위협 환경에 맞춘 조정"을 오늘날 가장 실용적으로 구현하는 수단이 이 둘입니다.

### 우선순위 매트릭스

세 축을 곱한 결과를 조치 대기열의 정렬 기준으로 씁니다. **CVSS는 이 표에 들어오기 위한 입장권이지 순번표가 아닙니다.**

| 노출(A) | 데이터 민감도(B) | 악용 가능성(C) | 조정 후 등급 | 조치 기한 |
|---|---|---|---|---|
| 인터넷 도달 가능 | 기밀·극비 | KEV 등재 또는 EPSS 높음 | **긴급(P0)** | 24시간 |
| 인터넷 도달 가능 | 기밀·극비 | 익스플로잇 미공개 | **높음(P1)** | 7일 |
| 인터넷 도달 가능 | 내부·공개 | KEV 등재 | **높음(P1)** | 7일 |
| VPC 내부만 도달 | 기밀·극비 | KEV 등재 | **높음(P1)** | 7일 |
| VPC 내부만 도달 | 기밀·극비 | 익스플로잇 미공개 | **보통(P2)** | 30일 |
| VPC 내부만 도달 | 내부·공개 | 무엇이든 | **낮음(P3)** | 90일/재빌드 |
| 도달 경로 없음(격리·미실행) | 무엇이든 | 무엇이든 | **낮음(P3)** | 재빌드 시 처리 |

한 가지 단서를 붙입니다. 마지막 행의 "도달 경로 없음"을 **"그러니 스캔할 필요도 없다"** 로 확장하지 마십시오.

> 📖 1판·2판 5장은 격리된 컴포넌트에 대한 스캔 논쟁을 이렇게 정리합니다. **"격리된 컴포넌트가 있다는 이유만으로 네트워크 취약점 스캔이 불필요하다고 생각하는 실수를 하지 마라. (…) 나는 알려지지 않은 취약점을 갖는 리스크가, 공격자가 바로 그 방화벽 규칙을 이용해 제한 구역에 들어올 리스크보다 훨씬 높다고 본다."**

### 그런데 대부분은 이렇게까지 따지지 않아도 된다

> 📖 1판·2판 5장: **"많은 경우 취약점이 얼마나 나쁜지 너무 깊이 생각할 필요가 없다. 클라우드 환경에서의 기본 동작은 보안 패치를 자동으로 적용하고 자동화된 테스트를 돌려 문제가 생겼는지 확인하는 것이어야 한다. 보안 패치나 구성 변경이 없거나, 문제를 일으키거나, 다른 이유로 실행할 수 없는 경우에만 그것이 당신 환경에 얼마나 큰 리스크인지 수동으로 평가하는 수고를 들여야 한다."**

**이 문장이 25.4 전체를 뒤집는 것처럼 보이지만 순서의 문제일 뿐입니다.** 기본값은 "생각하지 말고 자동 패치"이고, 위 매트릭스는 **자동 패치가 실패한 잔여분에만** 적용합니다. **매트릭스가 매주 수백 건으로 채워진다면 문제는 우선순위 로직이 아니라 자동 갱신 파이프라인입니다.**

## 25.5 취약점 관리 지표(Metrics) 🔴

> 📖 1판·2판 5장 「Vulnerability Management Metrics」: **"취약점 관리 프로그램이 어떻게 되어가고 있는지 측정할 수 없다면, 대개 그 유용성을 정당화할 수도 없고 변화가 필요한지 알 수도 없다. 지표는 유용하지만 위험한 것이다. 지속적 개선을 이끌고 문제를 드러내지만, 어리석은 결정으로 이어지기도 한다. 지표와 결과를 검토하는 프로세스에, 지표가 나쁜 방향으로 가는 데 합당한 정상참작 요인이 있는지 혹은 지표가 어떤 식으로든 조작되고 있는지 점검하는 과정을 반드시 포함시켜라."**
>
> 팀별 비교 보고에 대한 단서도 붙습니다. **"어떤 팀은 본래 취약점 관리를 따라가기가 다른 팀보다 더 어렵다는 점을 기억하라."**

원서가 제시하는 여섯 지표를 정의 → AWS 측정법 → 목표값 순으로 옮깁니다.

### 🔴 여섯 지표

**반드시 여섯 개를 모두 산출하십시오. 특히 ①을 빼면 나머지 다섯이 전부 거짓말이 됩니다.**

> ⚠️ **약어 충돌 주의 — 이 절의 MTTR은 사고 대응의 MTTR이 아닙니다.** 여기서 말하는 MTTR은 **Mean Time to Remediate**, 즉 **취약점 발견 → 조치 완료**(보통 일 단위)입니다. 32.6에서 다루는 사고 대응의 MTTR은 **Mean Time to Recover**, 즉 **사고 탐지 → 봉쇄·복구 완료**(보통 시간 단위)로 **세는 대상이 다릅니다.** 한 대시보드에 둘을 "MTTR"로 나란히 올리면 지표가 무의미해지므로, 경영 보고(39.2)에서는 약어 대신 **"취약점 조치 시간"** 과 **"사고 복구 시간"** 으로 풀어 쓰십시오(부록 G의 G.4 혼동 용어 쌍 참조).

| # | 지표 | 📖 원서의 정의 | AWS 측정 방법 | 목표값 |
|---|---|---|---|---|
| ① | **도구 커버리지**(Tool Coverage) | **"각 도구에 대해, 범위 내 시스템의 몇 퍼센트를 커버할 수 있는가? (…) 각 도구의 시스템 범위가 제대로 정의되어 있다면 이 지표들은 시간이 지나면서 100%에 가까워져야 한다."** | `inspector2 list-coverage`의 `ACTIVE` 리소스 수 ÷ Config 인벤토리의 동일 유형 리소스 수. Config 레코더 활성 계정/리전 비율 | **95% 이상, 목표 100%.** 90% 미만이면 다른 지표 발표 금지 |
| ② | **평균 조치 시간**(MTTR) | **"심각도별, 환경별로 나눠 보는 것이 유용한 경우가 많다"** — 심각도(critical은 low보다 빨라야)와 시스템 유형(내부/인터넷 노출)의 교차 | 결과의 `FirstObservedAt` → `RecordState=ARCHIVED` 전이 시각. Security Hub 결과를 S3로 내보내 Athena로 집계 | 25.3 SLA 표와 동일. **P0 24h, P1 7d** |
| ③ | **미조치 시스템/앱 비율** | **"보통 백분율로 표현되는데, 절대 숫자는 추적 항목이 늘어남에 따라 증가하는 경향이 있기 때문이다"** | 활성 결과를 가진 고유 리소스 수 ÷ 전체 리소스 수. `DataClass`·노출 여부로 분할 | 인터넷 노출 자산의 P0/P1 보유율 **0%** |
| ④ | **오탐률**(False Positives) | **"이 지표는 도구가 얼마나 잘하고 있는지, 그리고 도구 문제로 팀에 얼마나 많은 행정 부담이 지워지고 있는지 이해하는 데 도움이 된다"** | 억제 규칙 중 사유가 "오탐"인 건수 ÷ 총 결과 수 | 도구별 **10% 미만** |
| ⑤ | **미탐률**(False Negatives) | **"주어진 도구나 프로세스가 탐지했어야 하는데 다른 경로로 발견된 취약점이 얼마나 되는지 추적하는 것이 유용할 수 있다"** | 모의 침투·버그 바운티·사고 조사에서 나온 취약점 중, 기존 스캐너 범위에 있었으나 잡히지 않은 건수 | 분기당 **0건**. 1건이라도 나오면 근본 원인 분석 |
| ⑥ | **재발률**(Recurrence Rate) | **"조치된 뒤 취약점이 다시 돌아오는 것이 보인다면, 그것은 도구나 프로세스에 심각한 문제가 있다는 신호일 수 있다"** | 동일 (리소스 유형, CVE) 쌍이 `ARCHIVED` 이후 다시 `ACTIVE`가 된 건수 ÷ 조치 완료 건수 | **5% 미만** |

### 지표별로 원서가 덧붙인 단서

**①에 대해** — 📖 **"범위에 있어야 할 시스템이나 애플리케이션에 대해 커버리지가 정말 낮은 도구가 있다면, 그 도구에서 얻는 것이 별로 없는 것이다. 많은 경우 커버리지 비율을 높이는 프로젝트를 시작하거나, 아니면 그 도구를 폐기해야 한다."** 커버리지 20%짜리 스캐너는 **보고서에 도구 이름 한 줄을 넣기 위해 예산과 오탐 처리 시간을 쓰는 일**입니다. 이 지표는 📖 **"자산 및 취약점 관리 파이프라인의 누수를 발견하는 데 도움이 된다"** — 12.5의 도구 누수를 수치로 만든 것입니다.

**②에 대해** — 📖 **"조치가 항상 패치 설치를 뜻하지는 않는다는 점을 기억하라. (…) 패치 설치 이외의 수단을 통한 완화도 올바르게 집계되어야 한다."** 외부 요인 경고도 이어집니다. 📖 **"예를 들어 Spectre/Meltdown 취약점이 터졌을 때 많은 시스템에서 패치 제공이 지연되어 MTTR 지표가 올라갔다. 그 경우 지연은 조직의 취약점 관리 프로그램에 문제가 있다는 뜻이 아니라, 일반적인 컴퓨팅 환경이 심각한 취약점에 맞았다는 뜻이었다."** — **MTTR이 튀면 팀을 추궁하기 전에 그 달에 무슨 일이 있었는지 먼저 확인하십시오.**

**③에 대해** — 취약점 공표와 벤치마크 개정 때마다 부풀었다 줄어드는 주기성이 있으니 절대치보다 추세를 보십시오. 왜 시스템 수를 세고 취약점 개수를 세지 않는지는 원서가 답합니다. 📖 **"중요한 취약점 하나가 있는 시스템은 중요한 취약점 다섯 개가 있는 시스템과 대략 같은 리스크를 갖는다 — 어느 쪽이든 빠르게 침해될 수 있다. (…) 리눅스 시스템에서는 `yum -y update; shutdown -r now` 같은 명령 하나로 수백 개의 취약점을 몇 분 만에 해결할 수도 있다."**

2판은 여기에 세분화를 추가했습니다. 📖 2판: **"이 지표는 '미해결 취약점이 있으나 리스크가 수용된 시스템/애플리케이션'과 '정책 기한을 초과했고 리스크가 수용되지 않은 시스템/애플리케이션'으로 세분해, 리스크를 너무 많이 수용하고 있는지 혹은 충분히 빠르게 패치할 수 있는지를 알려줄 수 있다."** 1판에는 **"더 높은 수준의 리스크 지표를 도출하는 데 쓸 수 있다"** 는 한 문장뿐이었습니다. **이 두 분모를 분리하십시오** — 25.3의 억제 규칙 회수와 직결됩니다.

**④⑤에 대해** — 오탐과 미탐은 반드시 함께 봐야 합니다.

> 📖 2판 5장: **"통계적으로 말해서, 사람들은 통계에 형편없다. (…) 극단적인 예로, 모든 것을 문제로 표시하는 도구는 실제 문제를 전부 잡아내겠지만(참 양성률 100%) 오탐률이 너무 높아 쓸모없다. 마찬가지로 아무것도 문제로 표시하지 않는 도구는 오탐률이 완벽(0%)하지만 모든 것을 놓친 것이다. 방정식의 한쪽 면만 강조하는 마케팅 주장을 경계하라."** 그리고 📖 **"미탐이 너무 많은 도구나 프로세스는 잘못된 안도감(false sense of security)으로 이어질 수 있다."**

## 25.6 지표의 함정 ⚠️

원서가 지표를 **"유용하지만 위험한 것"** 이라 부른 이유를 세 시나리오로 풀어 봅니다.

### 함정 ① 스캔하지 않으면 취약점이 0으로 보인다

**사고 시나리오.** 월간 보고서에서 개발 계정(`555555555555`)의 미조치 취약점이 3개월 연속 0건입니다. 우수 사례로 언급되고 보안팀은 다른 계정에 집중합니다. 이후 침해 조사에서 그 계정의 오래된 개발 서버가 초기 진입점이었고, 1년 넘게 방치된 심각 CVE가 있었음이 드러납니다.

**원인.** 그 계정은 Inspector가 켜져 있지 않았습니다. 0건이었던 것은 취약점이 없어서가 아니라 **아무도 보지 않았기 때문**입니다. 커버리지 지표(①)를 산출하지 않으면 이 두 상태는 대시보드에서 **완전히 동일하게 보입니다.**

**올바른 구성.** **모든 취약점 지표 옆에 커버리지 분모를 반드시 함께 표시하십시오.** "심각 0건"이 아니라 **"스캔 대상 40대 중 40대 스캔, 심각 0건"** 입니다. 그리고 Organizations 위임 관리자에서 **신규 계정 자동 활성화**를 켜서 분모가 저절로 늘어나게 하십시오.

```bash
# 커버리지 상태 점검: 계정별 Inspector 스캔 활성화 여부
aws inspector2 batch-get-account-status \
  --profile awssec-lab --region ap-northeast-2 \
  --account-ids 111122223333 555555555555 444455556666

# 리소스 단위 커버리지: 스캔되지 않는 리소스 찾기
aws inspector2 list-coverage \
  --profile awssec-lab --region ap-northeast-2 \
  --filter-criteria '{"scanStatusCode":[{"comparison":"NOT_EQUALS","value":"ACTIVE"}]}'
```

두 번째 명령의 출력이 비어 있지 않다면 **그만큼이 대시보드에서 보이지 않는 영역**입니다. 22장에서 SSM 에이전트를 AMI에 구워 넣으라고 한 이유가 이것입니다 — 에이전트가 없는 EC2는 스캔 대상에서 조용히 빠집니다.

### 함정 ② MTTR을 낮추려고 심각도를 낮춘다

**사고 시나리오.** MTTR이 팀 KPI가 된 다음 분기, 심각 등급 MTTR이 21일에서 6일로 개선됩니다. 그런데 사고는 오히려 늘었습니다. 확인해 보니 심각으로 분류된 결과 수가 절반으로 줄었고, 줄어든 만큼이 "높음"으로 재분류되어 있었습니다.

**원인.** 원서가 정확히 예고한 행동입니다. 📖 1판·2판 5장: **"그러나 이것은 기한 초과를 피하려고 항목의 분류를 바꾸는 게임으로 빠르게 변질될 수 있다. 지표는 유용하지만, 진짜 목표가 보안 사고를 예방하는 것임을 놓치지 않는 것이 중요하다."** **MTTR은 "빨리 고쳤는가"와 "심각도를 낮췄는가"를 구분하지 못합니다.**

**올바른 구성.** 세 가지를 함께 겁니다. **(가) 심각도 하향에 별도 승인과 기록을 요구하고, 등급 변경 건수 자체를 지표로 봅니다.** `BatchUpdateFindings`로 `Severity`를 바꾼 이력은 CloudTrail에 남으므로 이 호출에 알람을 겁니다. **(나) 심각도의 근거를 사람이 아니라 25.4의 3축에 둡니다.** 노출 여부와 `DataClass` 태그는 임의로 바꾸기 어렵고, KEV 등재는 외부 데이터입니다. **(다) MTTR을 단독으로 보지 말고 ③·⑥과 세트로 봅니다.** 심각도를 낮추면 MTTR은 좋아지지만 미조치 비율은 그대로여서 조작이 드러납니다.

### 함정 ③ 오탐을 방치해 경보 전체가 무시된다

**사고 시나리오.** Security Hub에 결과 12,000건이 쌓여 있습니다. 대부분 이미 조치했거나 우리 환경에 해당하지 않는 것이어서, 팀은 "어차피 대부분 오탐"이라며 아무도 열지 않습니다. 진짜 심각 결과 3건이 그 안에 섞여 두 달간 방치됩니다.

**원인.** 오탐률(④)을 지표로 관리하지 않았기 때문입니다. 오탐은 도구의 문제로 보이지만 실제 피해는 **사람의 주의력 고갈**입니다. 원서가 오탐률을 **"도구 문제로 팀에 얼마나 많은 행정 부담이 지워지고 있는지"** 를 이해하는 지표로 정의한 이유가 여기 있습니다.

**올바른 구성.** **오탐을 "무시"하지 말고 "억제"하십시오.** 무시는 대시보드에 남아 신호 대 잡음비를 계속 떨어뜨리지만, 억제는 근거와 함께 사라지며 **집계 가능한 데이터**가 됩니다. 오탐률이 특정 도구에서 계속 높다면 원서의 조언대로 **개선 프로젝트를 하거나 그 도구를 폐기하십시오.**

> ⚠️ **세 함정의 공통 구조** — 셋 다 "지표를 개선하는 가장 쉬운 방법이 실제 보안을 개선하는 것이 아닐 때" 발생합니다. **지표를 설계할 때 "이 숫자를 부정직하게 좋게 만드는 가장 쉬운 방법"을 먼저 자문하고, 그 경로를 막는 보조 지표를 함께 두십시오.** 경영진 보고용 지표 설계는 39장에서 성숙도 모델과 함께 다룹니다.

## 이 장의 요약

| 항목 | 핵심 |
|---|---|
| 취약점 관리 ≠ 패치 관리 | 패치 없이 고치는 구성 결함, 기능 비활성화도 조치로 집계한다 |
| 클라우드의 차이 | 변화 속도. **클라우드 API 인벤토리를 스캐너에 직접 먹인다.** 컨테이너에는 무거운 에이전트를 넣지 않고 아티팩트를 스캔한다 |
| 프로세스 전환 | 전통 6단계 → 클라우드 4단계. 패치가 **배포**가 되고 MTTR은 릴리스 주기에 종속된다 |
| 7계층 | 데이터 접근 / 애플리케이션 / 미들웨어 / OS / 네트워크 / 가상 인프라 / 물리 인프라 |
| 책임의 반전 | 원서가 "제공자 책임"이라 한 가상화 인프라도 **EKS를 쓰면 고객 책임으로 되돌아온다** |
| CVE 없는 계층 | 데이터 접근 계층에는 CVE가 없다. CVE만 세는 프로그램은 최대 사고 원인을 놓친다 |
| 우선순위 | 기본값은 "생각 말고 자동 패치". 실패한 잔여분에만 **노출 × 민감도 × 악용 가능성** 매트릭스 적용 |
| 리스크 등록부 | 즉시 못 고치는 것은 전부 리스크로 등재. **분기 재평가**, 억제에는 만료일 |
| 변경 관리 | 롤백이 입증된 배포는 **사전 승인**. 잘못된 변경 관리는 오히려 리스크를 높인다 |
| 6대 지표 | 도구 커버리지 · MTTR · 미조치 비율 · 오탐률 · 미탐률 · 재발률 |
| 최대 함정 | **스캔하지 않으면 0으로 보인다.** 모든 지표 옆에 커버리지 분모를 붙인다 |

## 🔴 필수 구성 체크리스트

- [ ] 7계층 각각에 대해 **탐지 수단 표**를 작성하고 빈 칸이 있으면 "공백"으로 명시했다
- [ ] 스캔 대상 목록을 사람이 관리하지 않는다 — Organizations 위임 관리자 + **신규 계정 자동 활성화**가 켜져 있다
- [ ] 모든 EC2에 SSM 에이전트가 AMI 단계에서 포함되어 있고, `list-coverage`에 `ACTIVE`가 아닌 리소스가 없다
- [ ] 심각도별·노출별 **조치 기한(SLA)** 이 문서화되어 있다
- [ ] 기한 내 못 고친 것은 **리스크 등록부**에 등재되고 분기마다 재평가된다
- [ ] 모든 억제(SUPPRESSED)에 **사유·승인자·만료일**이 기록되고, 분기 1회 만료분을 회수한다
- [ ] 우선순위가 CVSS 단독이 아니라 **노출 × 민감도 × 악용 가능성**으로 결정된다
- [ ] 여섯 지표를 모두 산출하고, **커버리지를 첫 번째로** 보고한다
- [ ] `Workflow.Status=RESOLVED`인데 `RecordState=ACTIVE`인 결과 건수를 모니터링한다
- [ ] 보안 수정 배포가 **사전 승인 변경 범주**로 정의되어 CAB 대기에 걸리지 않는다
- [ ] `BatchUpdateFindings`로 심각도를 하향한 이력에 알람이 걸려 있다
