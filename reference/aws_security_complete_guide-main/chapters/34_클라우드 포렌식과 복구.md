# 34장. 클라우드 포렌식과 복구

> **이 장에서 다루는 것**
> - 물리 디스크가 없는 환경에서 무엇이 증거가 되는가 — 스냅샷과 API 로그

> - 인터넷과 끊긴 포렌식 계정에서 침해 자산을 읽기 전용으로 분석하는 법
> - 로그를 증거로 쓰기 전에 확인해야 할 감사 인프라의 신뢰도
> - 🔴 침해된 시스템은 치료하지 않고 재배포한다 — 재감염 없이 복구하는 순서
> - 비난 없는 사후 검토를 통제 개선으로 연결하기
>

> **난이도**: ★★★

33장에서 우리는 공격자를 막았습니다. 그런데 아직 끝나지 않았습니다. **무슨 일이 있었는지 증명할 수 있어야 하고, 공격자가 남긴 것이 하나도 없는 상태로 서비스를 되돌려야 합니다.** 앞이 포렌식, 뒤가 복구입니다. 둘 사이에는 긴장이 있습니다. 포렌식은 "아무것도 바꾸지 말라"고 하고 복구는 "지금 당장 다시 만들라"고 합니다. 순서를 잘못 잡으면 증거를 지우거나, 오염된 것을 그대로 되살립니다.

## 34.1 클라우드 포렌식이 다른 점

### 하드웨어를 만질 수 없다는 사실에서 출발한다

> 📖 *Practical Cloud Security* 1·2판 7장은 사고 대응이 전통 IT와 무엇이 다른지를 공동 책임 모델에서 끌어옵니다. **"클라우드 환경에서는 물리 하드웨어를 만지도록 허용되지 않는다. 많은 사고 대응 팀이 포렌식 노트북, 하드 드라이브 복제기, 그와 비슷한 기술을 담은 '점프백'을 쓴다. (…) 클라우드에서의 사고 대응에는 점프백 도구의 가상·클라우드 기반 등가물이 필요할 것이다."** 그리고 한 문장을 덧붙입니다 — **"이것은 또한 클라우드 사고 대응의 포렌식 부분을 어디서든 수행할 수 있다는 뜻이기도 하다."**

압수할 디스크가 없다는 것은 손해이자 이득입니다. 손해는 원본을 물리적으로 확보해 봉인할 수 없다는 것이고, 이득은 **API 한 번으로 완전한 사본을 만들 수 있다는 것**입니다. 디스크 복제기로 네 시간 걸리던 일이 `create-snapshots` 한 줄이고, 복제 과정에서 원본을 훼손할 위험도 없습니다.

또 하나 큰 차이가 있습니다. 원서는 클라우드에 **새로운 증거 원천**이 생긴다고 말합니다.

> 📖 1·2판 7장: **"대체로 제공자의 책임 영역에서 나오는 로그는 전혀 볼 수 없다. 다만 제공자가 당신을 대신해 한 행위 — 예컨대 당신의 암호화 키에 접근한 것 — 는 때때로 볼 수 있다. 그러나 클라우드 환경에는 중요한 특권 사용자 로그의 새로운 원천이 있다. 당신의 팀이 제공자의 포털, API, 명령줄 인터페이스를 사용해 한 일을 추적할 수 있다."**

온프레미스에서 "관리자가 무엇을 했는지"는 각 서버의 셸 히스토리를 긁어모아야 알 수 있었습니다. AWS에서는 CloudTrail이 제어 평면의 모든 행위를 구조화된 형태로 남깁니다. 클라우드 포렌식의 무게 중심이 디스크에서 API 로그로 옮겨 가는 이유입니다.

### 공동 책임 모델이 그리는 증거의 경계선

2장의 공동 책임 모델을 증거 관점에서 다시 그리면, 선이 아주 뚜렷하게 그어집니다. **고객 책임 영역의 증거는 전부 내가 직접 얻고, 제공자 책임 영역의 증거는 요청해도 받지 못합니다.**

| 증거 | 누가 가지고 있나 | 얻는 방법 |
|---|---|---|
| EBS 볼륨 내용 | 고객 | `create-snapshots` — 즉시, 무제한 |
| 인스턴스 메모리 | 고객(게스트 OS 안) | 실행 중 인스턴스에서 직접 덤프 — **종료하면 소멸** |
| 제어 평면 API 호출 | 고객(CloudTrail) | 트레일이 켜져 있던 기간만 |
| VPC 내 네트워크 흐름 | 고객(플로우 로그) | 플로우 로그가 켜져 있던 기간만, 헤더만 |
| 패킷 페이로드 | 고객(트래픽 미러링) | **사전에 켜 두지 않았으면 소급 불가** |
| S3 객체 접근 이력 | 고객(데이터 이벤트) | 데이터 이벤트가 켜져 있던 기간만 |
| 하이퍼바이저 로그 | AWS | **고객에게 제공되지 않음** |
| 물리 호스트·네트워크 장비 로그 | AWS | **고객에게 제공되지 않음** |
| 다른 테넌트 관련 정보 | AWS | 제공되지 않음(당연히) |
| 법 집행기관 대응 이력 | AWS | 고객이 요청할 수 있는 대상이 아님 |

결론은 하나입니다. **증거의 대부분은 사고 이전에 켜 둔 로그에서만 나옵니다.** 사고 후에 AWS에 연락해 "지난주 로그를 주세요"라고 하는 경로는 사실상 없습니다. 29장에서 "나중에 켤 수 없는 로그부터 켜라"고 한 이유가 여기서 회수됩니다.

> ⚠️ AWS 리소스가 공격에 사용되고 있다면 AWS Trust & Safety 팀에 남용 신고(abuse report) 경로가 있습니다. 그러나 이것은 **AWS 측 조사를 요청하는 경로이지 고객이 증거를 받아 오는 경로가 아닙니다.**

### 휘발성의 순서

증거는 사라지는 속도가 다릅니다. 빨리 사라지는 것부터 확보한다는 원칙(RFC 3227이 정리한 "휘발성의 순서")을 AWS 자원에 대입하면 다음 순서가 됩니다.

| 순위 | 증거 | 사라지는 계기 | 확보 수단 |
|---|---|---|---|
| 1 | 프로세스·네트워크 연결·메모리 | 인스턴스 중지·종료 | 메모리 덤프, 라이브 응답 명령 |
| 2 | 인스턴스 스토어 볼륨 | 인스턴스 중지·종료 | 즉시 EBS로 복사 |
| 3 | 임시 자격 증명 세션 정보 | 세션 만료(최대 12시간) | CloudTrail의 세션 컨텍스트 기록 |
| 4 | EBS 볼륨 | 종료 시 `DeleteOnTermination` | 스냅샷 |
| 5 | CloudWatch 로그 | 보존 기간 만료 | 내보내기 또는 보존 연장 |
| 6 | S3의 CloudTrail·플로우 로그 | 수명 주기 정책, 삭제 | 별도 버킷 복사 + 객체 잠금 |

**1번과 2번이 핵심입니다.** 33.5의 "성급한 종료가 증거를 지운다"가 정확히 이 두 줄입니다. 종료하는 순간 메모리와 인스턴스 스토어는 복구 불가능하게 사라지고, `DeleteOnTermination=true`인 볼륨까지 함께 사라집니다.

## 34.2 증거 보전 절차 🔴

> 📖 2판 7장 "클라우드 포렌식"은 절차의 본질을 이렇게 요약합니다. **"클라우드 포렌식은 CSI 텔레비전 쇼 같은 장면을 떠올리게 할지 모르지만, 안타깝게도 현실은 조금 덜 흥미진진하다. 본질적으로 당신은 중요할 수 있는 모든 것의 포렌식 사본을 만들고, 그다음 도구를 써서 그것을 분석하기만 하면 된다."** 그리고 바로 이어서 조건을 답니다. **"사본을 문서화되고 반복 가능한 방식으로 만드는 것이 중요하다. 그래야 변조되지 않은 원본 데이터의 정상 사본을 갖고 있음을 언제든 증명할 수 있다."**

"문서화되고 반복 가능한 방식"이 이 절의 전부입니다. 아래 다섯 단계를 **이 순서대로** 실행하십시오.

### 🔴 0단계 — 사건 번호를 먼저 만든다

무엇을 하기 전에 사건 ID를 정합니다. 이 값이 모든 스냅샷 태그, 버킷 프리픽스, 문서 파일명에 들어갑니다. **사건 ID 없이 뜬 스냅샷은 3주 뒤에 왜 존재하는지 아무도 모르는 비용 항목이 됩니다.**

```bash
export CASE_ID="IR-2026-0906-01"
export REGION="ap-northeast-2"
export PROFILE="awssec-lab"
export FORENSIC_ACCT="444455556666"
export TARGET_INSTANCE="i-0abc1234567890def"
```

### 🔴 1단계 — EBS 스냅샷 생성과 태깅

인스턴스에 붙은 **모든 볼륨을 한 시점으로** 뜹니다. 볼륨마다 따로 뜨면 시점이 어긋나 파일시스템 상태가 서로 맞지 않게 됩니다.

```bash
aws ec2 create-snapshots \
  --instance-specification "InstanceId=${TARGET_INSTANCE},ExcludeBootVolume=false" \
  --description "Forensic image ${CASE_ID}" \
  --copy-tags-from-source volume \
  --tag-specifications "ResourceType=snapshot,Tags=[{Key=IncidentId,Value=${CASE_ID}},{Key=Evidence,Value=true},{Key=SourceInstance,Value=${TARGET_INSTANCE}},{Key=CollectedBy,Value=ir-analyst-01},{Key=LegalHold,Value=true}]" \
  --region "$REGION" --profile "$PROFILE"
```

> ⚠️ **스냅샷은 증분 저장이지만 논리적으로는 완전한 사본입니다.** 나중에 원본 볼륨이 지워져도 스냅샷은 온전합니다. 다만 **같은 볼륨의 이전 스냅샷을 지우면 안 된다**는 오해가 흔한데, EBS는 삭제 시 필요한 블록을 자동으로 이관하므로 증거 스냅샷을 지키기 위해 다른 스냅샷을 붙잡아 둘 필요는 없습니다. 지키는 방법은 태그와 계정 분리, 그리고 SCP입니다.

증거 스냅샷의 삭제를 조직 차원에서 막습니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyDeleteEvidenceSnapshots",
      "Effect": "Deny",
      "Action": [
        "ec2:DeleteSnapshot",
        "ec2:ModifySnapshotAttribute"
      ],
      "Resource": "arn:aws:ec2:*::snapshot/*",
      "Condition": {
        "StringEquals": { "ec2:ResourceTag/LegalHold": "true" },
        "ArnNotLike": {
          "aws:PrincipalArn": "arn:aws:iam::444455556666:role/ForensicCustodian"
        }
      }
    }
  ]
}
```

### 🔴 2단계 — 메모리 확보 (인스턴스가 아직 살아 있을 때만)

메모리는 인스턴스를 중지하는 순간 사라집니다. **격리는 이미 33.3에서 보안 그룹으로 끝냈으므로**, 인스턴스는 네트워크에서 끊긴 채 살아 있는 상태여야 합니다. 이 상태에서 덤프를 뜹니다.

AWS에 "메모리를 덤프하는 API"는 없습니다. 게스트 OS 안에서 도구를 돌려야 하고, 그 통로가 SSM Run Command입니다.

```bash
# 실행할 명령을 파일로 만든다 — 인용 부호 중첩 사고를 피하고, 명령 전문이 그대로 증거 기록이 된다
cat > /tmp/acquire-memory.json <<EOF
{ "commands": [
  "set -euo pipefail",
  "DUMP=/mnt/evidence-scratch/${CASE_ID}-mem.lime",
  "insmod /opt/forensics/lime-\$(uname -r).ko path=\$DUMP format=lime",
  "sha256sum \$DUMP > \$DUMP.sha256",
  "aws s3 cp \$DUMP s3://shopmini-forensic-evidence/${CASE_ID}/ --checksum-algorithm SHA256",
  "aws s3 cp \$DUMP.sha256 s3://shopmini-forensic-evidence/${CASE_ID}/"
] }
EOF

aws ssm send-command \
  --document-name "AWS-RunShellScript" \
  --instance-ids "$TARGET_INSTANCE" \
  --comment "Memory acquisition ${CASE_ID}" \
  --parameters file:///tmp/acquire-memory.json \
  --region "$REGION" --profile "$PROFILE"
```

원서가 예시로 든 절차가 그대로 이 형태입니다.

> 📖 1·2판 7장은 사전 준비 항목으로 **"침해된 리눅스 가상 머신에서 메모리와 디스크 포렌식 정보를 수집하는 절차"** 를 들면서, 그 절차가 담아야 할 정확한 명령을 나열합니다 — **"메모리 덤프를 캡처하기 위해 LiME를 실행하고, 덤프의 해시를 생성하고, Volatility로 덤프를 검증하고, 악성 프로그램이 재부팅 전에 흔적을 지우는 것을 막기 위해 침해된 머신을 하드 전원 차단하고, 디스크의 스냅샷을 뜨는 것."**

놓치기 쉬운 것이 **"하드 전원 차단"** 입니다. 정상 종료(`stop-instances`)는 게스트 OS의 셧다운 스크립트를 실행시키고, 악성코드가 거기에 정리 루틴을 걸어 두었다면 그것이 실행됩니다. 실무에서는 **메모리를 먼저 확보한 뒤 스냅샷을 뜨고, 인스턴스는 격리 상태로 남겨 두는 것**이 안전합니다. 굳이 멈춰야 한다면 `stop-instances --force`를 씁니다.

> ⚠️ **SSM Run Command 자체가 시스템을 변경하고 공격자에게 노출됩니다.** 명령 실행은 프로세스를 만들고 로그를 남기며, 인스턴스에 남아 있는 공격자가 이를 볼 수 있습니다. 세 가지를 사전에 준비해야 합니다.
> - **LiME 커널 모듈은 실행 중인 커널 버전과 정확히 일치해야 합니다.** 사고 당일 컴파일하려 하면 인터넷 없는 격리 인스턴스에서 막힙니다. 골든 AMI(22.5)의 커널 버전에 맞춰 미리 빌드해 이미지에 넣어 두십시오.
> - 인스턴스에 SSM Agent와 최소한의 IAM 권한이 없으면 이 경로 자체가 없습니다. 침해 후에 인스턴스 프로파일을 붙이는 것은 **증거를 만들고 있는 시스템의 구성을 바꾸는 일**이므로 기록에 남겨야 합니다.
> - 덤프를 인스턴스의 EBS 루트 볼륨에 쓰지 마십시오. 증거 디스크를 덮어씁니다. 인스턴스 스토어나 새로 붙인 별도 볼륨에 씁니다.

인스턴스에 **들어가지 않고** 얻을 수 있는 증거도 있습니다. 침습이 없으므로 가장 먼저 챙깁니다.

```bash
# 시리얼 콘솔 출력 — 커널 메시지, 부팅 로그
# (CLI 버전에 따라 Output 이 base64 그대로 나올 수 있다. 그 경우 base64 -d 를 덧붙인다)
aws ec2 get-console-output --instance-id "$TARGET_INSTANCE" \
  --query Output --output text \
  --region "$REGION" --profile "$PROFILE" > "${CASE_ID}-console.txt"

# 콘솔 스크린샷 — 화면에 떠 있는 랜섬 노트 등
aws ec2 get-console-screenshot --instance-id "$TARGET_INSTANCE" \
  --query ImageData --output text \
  --region "$REGION" --profile "$PROFILE" | base64 -d > "${CASE_ID}-screen.jpg"

sha256sum "${CASE_ID}-console.txt" "${CASE_ID}-screen.jpg"
```

> 💡 **원서 이후 변경** — Nitro 기반 인스턴스에는 `ec2:SendDiagnosticInterrupt`로 NMI를 보내 게스트 OS의 크래시 덤프를 유도하는 경로가 있습니다. 게스트에 kdump가 미리 구성되어 있어야 하고 **인스턴스는 즉시 패닉으로 멈추므로**, LiME가 불가능한 상황의 최후 수단으로만 씁니다.

### 🔴 3단계 — 로그 범위 확정과 별도 보관

로그는 "지금 있는 것"이 아니라 "곧 사라질 것"으로 취급합니다. 순서는 **범위 확정 → 복사 → 잠금** 입니다.

**범위 확정.** 최초 침입 시점(patient zero)은 조사가 진행되면서 계속 앞으로 당겨지므로 **처음부터 넉넉하게** 잡으십시오. ShopMini의 기본값은 "최초 이상 징후 30일 전부터 현재까지"입니다.

| 로그 | 어디서 | 확보 방법 |
|---|---|---|
| CloudTrail 관리·데이터 이벤트 | 로그 아카이브 계정 S3 | 해당 프리픽스를 증거 버킷으로 복사 |
| VPC 플로우 로그 | 로그 아카이브 계정 S3 | 대상 ENI 관련 프리픽스 복사 |
| ALB 액세스 로그 | 로그 아카이브 계정 S3 | 사고 기간 복사 |
| CloudWatch Logs(앱·OS) | 운영 계정 | 로그 그룹 보존 기간 연장 후 S3 내보내기 |
| GuardDuty·Security Hub 결과 | 보안 도구 계정 | 결과 내보내기(JSON) |
| RDS 데이터 | 운영 계정 | `create-db-snapshot` |

**복사와 잠금.** 증거 버킷은 **사고 전에 객체 잠금을 켠 상태로 만들어 두어야 합니다**(객체 잠금은 원칙적으로 버킷 생성 시 활성화합니다). 조사가 언제 끝날지 모르므로 복사한 객체에는 기간이 없는 **법적 보존(Legal Hold)** 을 겁니다.

```bash
# 사고 기간 CloudTrail 로그를 증거 버킷으로 복사 (S3 SHA-256 체크섬 포함)
aws s3 cp \
  s3://shopmini-org-cloudtrail-logs/AWSLogs/o-exampleorgid/111122223333/CloudTrail/ap-northeast-2/2026/09/ \
  s3://shopmini-forensic-evidence/${CASE_ID}/cloudtrail/ \
  --recursive --checksum-algorithm SHA256 \
  --profile awssec-lab

# 복사된 각 객체에 기간 없는 법적 보존 적용
aws s3api put-object-legal-hold \
  --bucket shopmini-forensic-evidence \
  --key "${CASE_ID}/cloudtrail/2026/09/06/000000.json.gz" \
  --legal-hold Status=ON \
  --profile awssec-lab
```

CloudWatch Logs는 **보존 기간부터 늘리고** 내보냅니다. 순서가 바뀌면 내보내는 도중에 만료됩니다.

```bash
aws logs put-retention-policy \
  --log-group-name /shopmini/app --retention-in-days 365 \
  --region "$REGION" --profile "$PROFILE"

aws logs create-export-task \
  --log-group-name /shopmini/app \
  --from 1756944000000 --to 1757462400000 \
  --destination shopmini-forensic-evidence \
  --destination-prefix "${CASE_ID}/cwlogs/app" \
  --region "$REGION" --profile "$PROFILE"
```

### 🔴 4단계 — 해시 산출과 기록

> 📖 2판 7장: **"이것은 보통 손상되지 않은 데이터의 사본을 갖고 있음을 보이는 데 쓸 수 있는 검증 문자열(암호학적 해시)을 생성하는 일을 수반한다. SHA-256 같은 암호학적 해시는 계산은 빠르지만 같은 해시를 갖는 다른 데이터를 만드는 데 쓰기는 거의 불가능하도록 설계되어 있다. 데이터 사본과 암호학적 해시가 있으면, 누구든 빠르게 해시를 생성해 원본과 비교하여 자신의 사본이 최초 조사자가 수집한 것과 같은지 확인할 수 있다."** 그리고 대안을 언급하며 왜 해시를 쓰는지 못 박습니다 — **"원본 사본을 읽기 전용 매체에 기록하고 매번 사본을 비트 단위로 비교할 수도 있지만, 그건 시간이 훨씬 오래 걸린다!"**

AWS에서 해시를 다루는 방식은 대상에 따라 셋으로 갈립니다.

| 대상 | 해시를 어떻게 얻나 |
|---|---|
| 메모리 덤프, 내보낸 로그 파일 등 **파일** | `sha256sum` 산출 후 별도 파일로 함께 보관 |
| **S3에 올린 객체** | 업로드 시 `--checksum-algorithm SHA256`, 확인은 `head-object --checksum-mode ENABLED` |
| **EBS 스냅샷** | 스냅샷 전체에 대한 단일 해시는 AWS가 제공하지 않는다 |

마지막 줄이 중요합니다. **EBS 스냅샷에는 "이 스냅샷의 SHA-256"이라는 값이 없습니다.** 대신 세 가지로 무결성을 논증합니다.

1. **스냅샷은 생성 후 변경 불가능한 객체**입니다. 스냅샷 ID와 `StartTime`이 그 자체로 시점을 고정합니다.
2. **EBS direct API**(`aws ebs list-snapshot-blocks` / `get-snapshot-block`)는 블록 단위 SHA-256 체크섬을 반환합니다. 엄격한 요구가 있을 때 블록 체크섬을 순서대로 이어 매니페스트 해시를 만들 수 있지만, 대용량에서는 오래 걸립니다.
3. **분석용으로 복원한 파일시스템 이미지**를 파일로 떠서 그 파일의 해시를 기록합니다. 가장 흔한 방식입니다.

```bash
# 스냅샷의 불변 식별 정보를 기록에 남긴다
aws ec2 describe-snapshots --snapshot-ids snap-0aa11bb22cc33dd44 \
  --query 'Snapshots[0].{Id:SnapshotId,Vol:VolumeId,Size:VolumeSize,Start:StartTime,Enc:Encrypted,Key:KmsKeyId}' \
  --output json --region "$REGION" --profile "$PROFILE" \
  | tee "${CASE_ID}-snapshot-manifest.json"

sha256sum "${CASE_ID}-snapshot-manifest.json"
```

### 🔴 5단계 — 관리 연속성(Chain of Custody)

증거는 "누가, 언제, 무엇을, 어떻게 다뤘는가"가 끊기지 않게 기록되어야 법적·계약적으로 의미가 있습니다. 아래 표를 사건별 문서로 만들어 **모든 행위를 그 자리에서** 채우십시오. 나중에 기억으로 채운 기록은 기록이 아닙니다.

| 항목 | 내용 |
|---|---|
| 사건 ID | `IR-2026-0906-01` |
| 증거 ID | `EV-003` |
| 증거 설명 | `i-0abc…def` 루트 볼륨 스냅샷 `snap-0aa1…dd44` |
| 수집 일시 | `2026-09-06T14:22:31Z` (**UTC 표기 고정**) |
| 수집자 | 이름 / IAM 주체 ARN |
| 수집 방법 | `aws ec2 create-snapshots …` (명령 전문 첨부) |
| 검증값 | 매니페스트 SHA-256 / 파일 해시 |
| 보관 위치 | 계정 `444455556666`, 리전 `ap-northeast-2` |
| 접근 통제 | 역할 `ForensicCustodian`만, SCP로 삭제 차단 |
| 이관 기록 | 일시 / 이관자 / 인수자 / 사유 (행 추가) |

**이관 기록이 진짜 관리 연속성입니다.** AWS에서 "이관"은 물리적 인계가 아니라 **접근 권한 부여**입니다. 따라서 다음 두 가지가 이관의 증거가 됩니다.

- `modify-snapshot-attribute`로 다른 계정에 `createVolumePermission`을 부여한 CloudTrail 기록
- 증거 버킷 객체에 대한 `s3:GetObject`의 데이터 이벤트 기록

**증거 계정 안의 모든 API 호출에 대해 데이터 이벤트까지 켜 두십시오.** 조사자의 모든 행위가 기록되어야 조사 자체의 무결성이 성립합니다.

### 🧪 스냅샷을 포렌식 계정으로 넘기기

```bash
# ① [운영 계정 111122223333] 포렌식 계정에 볼륨 생성 권한만 부여
aws ec2 modify-snapshot-attribute \
  --snapshot-id snap-0aa11bb22cc33dd44 \
  --attribute createVolumePermission \
  --operation-type add --user-ids "$FORENSIC_ACCT" \
  --region "$REGION" --profile awssec-lab

# ② [포렌식 계정 444455556666] 자기 계정 키로 재암호화 복사 = 소유권 확보
aws ec2 copy-snapshot \
  --source-region "$REGION" --source-snapshot-id snap-0aa11bb22cc33dd44 \
  --description "Evidence copy ${CASE_ID}" \
  --encrypted --kms-key-id alias/forensic/evidence \
  --tag-specifications "ResourceType=snapshot,Tags=[{Key=IncidentId,Value=${CASE_ID}},{Key=LegalHold,Value=true}]" \
  --region "$REGION" --profile awssec-forensic
```

②를 하는 이유는 **운영 계정이 침해되었기 때문**입니다. 공유만 받은 상태에서는 원본 스냅샷을 운영 계정의 공격자가 삭제하거나 공유를 철회할 수 있습니다. 자기 계정 키로 복사하면 그 순간부터 증거는 포렌식 계정의 소유입니다.

> ⚠️ **KMS가 여기서 막습니다.** 32.3에서 예고한 함정이 바로 이 지점에서 터집니다.
> - 원본이 **고객 관리형 키**로 암호화되어 있으면, 그 키 정책에서 포렌식 계정에 `kms:Decrypt`·`kms:DescribeKey`·`kms:CreateGrant`·`kms:ReEncryptFrom`을 허용해야 복사가 성립합니다(16.7).
> - 원본이 **AWS 관리형 키**(`aws/ebs`)로 암호화되어 있으면 **스냅샷 공유 자체가 불가능합니다.** 사고 당일에는 바꿀 수 없습니다. 그래서 16장에서 EBS 기본 암호화 키를 고객 관리형 키로 지정하라고 한 것입니다.
> - 암호화되지 않은 볼륨은 공유는 되지만, 이번에는 **증거가 평문으로 떠도는 문제**가 생깁니다. 복사 시 `--encrypted`로 암호화를 입히십시오.

## 34.3 격리 환경에서 분석하기

### 침해된 자격 증명이 만든 것은 아무것도 믿지 않는다

분석 환경 설계의 제1원칙입니다. 침해된 계정의 AMI, Lambda 계층, 컨테이너 이미지, 조사용으로 급히 만든 인스턴스까지 — **공격자의 권한 범위 안에서 만들어진 것은 분석 도구로 쓰지 않습니다.** 관리자 권한을 가진 공격자는 AMI를 바꿔치기하고 SSM 문서를 수정할 수 있었습니다.

그래서 32.3에서 준비한 **포렌식 계정**을 씁니다. 분석 관점에서 다시 정리하면 다음과 같습니다.

| 요소 | 구성 | 이 구성이 막는 것 |
|---|---|---|
| 계정 | 운영과 별개, 워크로드 없음 | 침해된 자격 증명의 도달 범위 밖 |
| VPC | IGW·NAT 없음(`10.99.0.0/16`) | 분석 중 실행된 악성코드의 C2 통신 |
| 엔드포인트 | SSM·S3·KMS 인터페이스/게이트웨이 엔드포인트만 | 인터넷 없이 도구 접근 |
| 접근 | Session Manager 전용, 인바운드 0 | 분석 호스트 자체가 표적이 되는 것 |
| 분석 AMI | 사고 전에 구운 도구 이미지 | 사고 당일 설치 시도 → 인터넷 없어 실패 |
| SCP | 이 계정에서 IGW·NAT·피어링 생성 금지 | 조사자가 급한 마음에 인터넷을 여는 것 |

**"조사자가 인터넷을 여는 것"이 실제로 가장 흔한 사고입니다.** 도구 하나가 없어서 NAT 게이트웨이를 잠깐 붙였다가, 그 사이 분석 인스턴스에서 실행한 샘플이 외부와 통신합니다. SCP로 아예 못 만들게 잠그십시오.

### 스냅샷을 읽기 전용으로 붙이기

> ⚠️ **EC2에는 "볼륨을 읽기 전용으로 연결"하는 API 옵션이 없습니다.** `attach-volume`에 읽기 전용 인자가 있다고 착각하는 경우가 많은데, 없습니다. 읽기 전용은 **게스트 OS 수준에서** 보장해야 합니다.

```bash
# [포렌식 계정] ① 증거 스냅샷에서 분석용 볼륨 생성 (원본 스냅샷은 그대로 남는다)
aws ec2 create-volume \
  --snapshot-id snap-0copy1234567890ab \
  --availability-zone ap-northeast-2a \
  --volume-type gp3 \
  --tag-specifications "ResourceType=volume,Tags=[{Key=IncidentId,Value=${CASE_ID}}]" \
  --region ap-northeast-2 --profile awssec-forensic

# ② 분석 인스턴스에 연결
aws ec2 attach-volume \
  --volume-id vol-0ana1234567890abc \
  --instance-id i-0forensicworkstation \
  --device /dev/sdf \
  --region ap-northeast-2 --profile awssec-forensic
```

```bash
# ③ 게스트 OS에서 읽기 전용 확보 — 이 단계가 진짜 보호다
sudo mkdir -p /mnt/evidence

# 먼저 블록 장치 계층에서 쓰기를 차단한다 (가장 확실한 방어)
sudo blockdev --setro /dev/nvme1n1

# 그다음 마운트한다. 저널 재생(replay)까지 막아야 하므로 noload 를 반드시 준다.
# noload 없이 ro 로만 마운트하면 ext4 드라이버가 저널을 재생하며 디스크에 쓴다.
sudo mount -o ro,noload,noexec,nodev,nosuid /dev/nvme1n1p1 /mnt/evidence
```

**"ro로 마운트했으니 안 썼다"는 흔한 오해입니다.** `noload`가 없으면 ext4는 저널을 재생하며 디스크에 씁니다. XFS는 `norecovery`가 같은 역할을 합니다.

> 💡 볼륨을 붙이지 않고 스냅샷을 읽는 경로도 있습니다. **EBS direct API**(`list-snapshot-blocks`·`get-snapshot-block`)는 스냅샷 블록을 API로 직접 읽습니다. 인스턴스에 연결하는 행위 자체가 없으므로 쓰기 위험이 원천적으로 없고, 블록별 SHA-256 체크섬도 함께 받습니다. 다만 대용량에서는 느리고 API 호출 비용이 붙습니다.

### 분석 결과의 반출 통제

격리 환경을 만들어 놓고 분석 결과를 개인 노트북으로 내려받으면 격리가 무너집니다. **반출은 한 방향, 한 경로만** 허용합니다.

| 규칙 | 구현 |
|---|---|
| 원본 증거는 절대 나가지 않는다 | 증거 버킷에 `aws:PrincipalOrgID` + 특정 역할만 허용하는 버킷 정책 |
| 나가는 것은 보고서와 IOC 목록뿐 | 별도 "산출물" 버킷을 두고 거기로만 쓰기 |
| 악성 샘플은 격리 계정을 벗어나지 않는다 | 샘플 전용 프리픽스에 별도 SCP·버킷 정책 |
| 반출 행위는 전부 기록된다 | 산출물 버킷에 S3 데이터 이벤트 활성화 |
| 분석 인스턴스는 조사 종료와 함께 폐기 | 종료 시 볼륨은 스냅샷으로 보전 후 삭제 |

**분석 인스턴스 자체도 일회용입니다.** 사건 하나에 인스턴스 하나. 여러 사건을 같은 호스트에서 분석하면 교차 오염과 증거 혼입 논란이 생깁니다.

## 34.4 감사 인프라 이해하기

### 로그를 증거로 쓰려면 로그가 어떻게 만들어지는지 알아야 한다

> 📖 1·2판 7장 "감사 인프라 이해하기"는 예제 애플리케이션의 로그 애그리게이터·지표 애그리게이터·SIEM을 하나씩 뜯어보며, 그중 로그 애그리게이터에 대해 이렇게 요구합니다. **"로그 애그리게이터는 감시 대상 시스템과 분리된 관리 통제 아래에 있어야 한다. 그래야 감시 대상 시스템 중 하나에 접근한 공격자가 같은 자격 증명으로 애그리게이터에도 접근해 로그를 지울 수 없다. 감사와 로깅 구성 요소는 분리된 감사 클라우드 계정에 두기를 권한다."**

29장에서 우리는 이 권고대로 로그 아카이브 계정을 만들었습니다. 여기서 물어야 할 질문은 다릅니다. **"그래서 이 로그를 증거로 믿어도 되는가?"** 로그의 신뢰도는 **생성 → 전달 → 저장 → 조회** 네 구간에서 각각 무너집니다. 조사 시작 전에 네 구간을 점검하십시오.

| 구간 | 실패 방식 | AWS에서의 확인 |
|---|---|---|
| 생성 | 애초에 이벤트가 만들어지지 않음 | 트레일 이벤트 선택기, 데이터 이벤트 설정 이력 |
| 전달 | 지연·유실 | 다이제스트 파일 연속성, 로그 유입 지표의 공백 |
| 저장 | 삭제·변조 | `validate-logs`, 객체 잠금, 버킷 정책 변경 이력 |
| 조회 | 시간대·파티션 오류로 못 찾음 | UTC 고정, Athena 파티션 확인 |

### 생성 — CloudTrail에 남지 않는 것들

**"CloudTrail이 있으니 다 남는다"가 이 장에서 가장 위험한 착각입니다.** 남지 않는 것을 먼저 알아야 로그의 공백을 "공격자가 지웠다"로 오독하지 않습니다.

| 남지 않는 것 | 이유 | 대비 |
|---|---|---|
| S3 객체 읽기·쓰기 | **데이터 이벤트는 기본 꺼짐** | 민감 버킷에 데이터 이벤트 활성화(29.2) |
| Lambda 함수 호출 | 데이터 이벤트 대상 | 필요한 함수만 선택적으로 활성화 |
| DynamoDB 항목 수준 접근 | 데이터 이벤트 대상 | 동일 |
| EC2 인스턴스 **안에서** 벌어진 일 | 게스트 OS는 제어 평면 밖 | OS·앱 로그를 CloudWatch Logs로 |
| 데이터베이스 내부 쿼리 | RDS 엔진 내부 | RDS 감사 로그 별도 활성화 |
| 트레일이 없던 리전의 활동 | 리전별 구성 | **다중 리전 조직 트레일**(29.2) |
| 트레일 생성 이전 기간 | 소급 불가 | CloudTrail 이벤트 기록(90일)으로 일부 보완 |

마지막 줄이 실전에서 자주 구원투수가 됩니다. 트레일이 없었더라도 **CloudTrail 이벤트 기록**은 최근 90일의 관리 이벤트를 계정별·리전별로 보관합니다.

```bash
# 트레일이 없던 리전에서도 최근 90일 관리 이벤트는 조회된다
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=Username,AttributeValue=compromised-user \
  --start-time 2026-08-20T00:00:00Z --end-time 2026-09-06T00:00:00Z \
  --region ap-northeast-1 --profile awssec-lab
```

### 전달 — 지연이 만드는 타임라인의 함정

29.2에서 확인했듯 CloudTrail은 실시간이 아닙니다. 포렌식에서 이 지연은 두 가지 오류를 만듭니다.

1. **"사고 직후 조회했는데 아무것도 없다" → 아직 전달되지 않았을 뿐입니다.** 조사 초기에 로그가 비어 있다고 결론 내리지 말고, 시간을 두고 다시 조회하십시오.
2. **"이 API 호출이 저 파일 생성보다 먼저다" → S3 객체의 도착 순서는 실제 발생 순서가 아닙니다.** 인과 관계는 반드시 이벤트 내부의 `eventTime`으로 판단합니다.

### 시간 — 모든 타임라인은 UTC로 고정한다 ⚠️

> 📖 1·2판 7장은 로깅 체계를 설명하면서 이 점을 별도로 강조합니다. **"일반적으로 네트워크 시간 프로토콜(NTP)을 사용해 모든 시스템의 시간이 동기화되어 있는지 확인하라. 또한 모든 타임스탬프가 시간대 정보를 담고 있거나, 모든 로그에 같은 시간대(예: GMT)를 사용하도록 하라. 이것은 보통 설정하기 매우 쉬우며, 시스템 시계나 시간대가 어긋났을 때 서로 다른 로그 소스 간 이벤트를 상관 분석하려 애쓰는 악몽을 피하게 해 준다."**

**사고 시나리오.** 침해 조사 보고서에 "09:14에 키 유출, 09:02에 데이터 반출"이라고 적혀 조사가 뒤집힙니다. 유출보다 반출이 먼저인 타임라인은 성립하지 않습니다.

**원인.** CloudTrail의 `eventTime`은 UTC(`2026-09-06T09:02:11Z`)이고, 애플리케이션 로그는 KST 로컬 시각이었으며, 분석가는 콘솔에서 브라우저 로컬 시간대로 표시된 값을 옮겨 적었습니다. **세 개의 시간대가 한 표에 섞였습니다.**

**올바른 구성.**

| 항목 | 규칙 |
|---|---|
| 인스턴스 시각 동기화 | Amazon Time Sync Service(`169.254.169.123`) 사용, 별도 NTP 서버 지정 금지 |
| 컨테이너 | 호스트 시각을 상속하므로 호스트에서 보장 |
| 애플리케이션 로그 | **UTC로 기록하고 타임존 오프셋을 반드시 포함**(ISO 8601) |
| 조사 문서 | **모든 시각을 UTC로 통일**하고 표 머리에 "모든 시각 UTC" 명시 |
| 보고 시 | KST 변환은 마지막 요약본에서만, 병기 표기(`09:02 UTC / 18:02 KST`) |

**타임라인 표는 UTC 단일 기준으로 만들고, 원본 로그의 시간대 표기를 그대로 인용란에 남기십시오.**

### 저장·조회 — 로그 위조 가능성을 등급으로 평가한다

증거는 "믿는다/안 믿는다"가 아니라 **얼마나 조작이 어려웠는가**로 등급을 매기는 것이 실무적입니다. 조사 보고서에 이 등급을 함께 적으면 결론의 강도가 분명해집니다.

| 증거 | 조작 난이도 | 근거 |
|---|---|---|
| 로그 아카이브 계정의 CloudTrail + 객체 잠금(컴플라이언스) + 다이제스트 검증 | **매우 높음** | 별도 계정 + 불변 스토리지 + 서명 체인(29.3) |
| 같은 계정의 CloudTrail S3 로그 | 중간 | 계정 관리자 권한이면 버킷 조작 가능 |
| CloudWatch Logs의 OS·앱 로그 | 중간~낮음 | 인스턴스 침해 시 전송 전 단계에서 위조 가능 |
| 침해된 인스턴스의 **로컬** 로그 파일 | **매우 낮음** | 공격자가 직접 편집 가능 — 참고용 |
| 침해된 인스턴스의 셸 히스토리 | **매우 낮음** | 삭제·조작이 기본 수법 |

**이 절의 요지는 두 줄입니다.** 침해된 시스템 안에서 나온 로그는 단독으로 결론의 근거가 될 수 없습니다. 반드시 **시스템 밖에서 독립적으로 생성된 기록**(CloudTrail, 플로우 로그, ALB 로그)과 교차 검증하십시오. 원서가 로그 애그리게이터를 별도 관리 통제 아래 두라고 한 이유가 탐지 단계에서는 "지워지지 않게"였다면, 포렌식 단계에서는 **"증거 능력을 갖추게"** 입니다.

## 34.5 복구: IT 시스템 재배포 🔴

### 🔴 침해된 시스템은 치료하지 말고 재구축한다

> 📖 1·2판 7장 "IT 시스템 재배포"는 이 장에서 가장 단호한 문장으로 시작합니다. **"IT 관점에서 사고로부터 복구하는 가장 단순하고 효과적인 방법은 단연코 영향받은 모든 시스템을 재배포하는 것이다. 다시 말하지만 이것은 클라우드에서 조금 더 쉽다. 새 물리 하드웨어를 구매할 필요가 없고, 클라우드 제공자에게 용량이 있을 것이기 때문이다."** 그리고 못을 박습니다. **"침해된 클라우드 시스템은 모두 다시 만들어야 하고, 운영 트래픽은 새 시스템으로 전환해야 한다. 영향받은 워크스테이션은 모두 지우고 알려진 정상 이미지로 다시 만들어야 한다."** 저자는 영화 〈에이리언〉의 대사까지 인용합니다 — **"궤도에서 현장 전체를 핵으로 날려라. 그것만이 확실한 방법이다."**

7장의 마무리 절은 왜 그래야 하는지를 더 직접적으로 설명합니다.

> 📖 1·2판 7장 결론: **"복구 조치를 수행할 때 시스템을 청소하려고 시도하는 것은 매우 위험하다. 누군가 관리자 접근 권한을 얻고 나면, 악성코드가 숨을 곳이 너무 많기 때문에 모든 것을 제거했는지 알 방법이 사실상 없다. 훨씬 안전한 선택지는 침해된 각 시스템을 지우고 복원하거나, 삭제하고 새로 프로비저닝하는 것이다. 다행히 클라우드에서는 그렇게 하기 쉽다! 제자리 정리(clean up in-place)의 위험을 과소평가하지 마라. 접근 제어 권한 하나, 윈도우의 레지스트리 항목 하나, 혹은 찾기 어려운 다른 백도어 하나가 공격자를 쉽게 걸어 들어오게 할 수 있다."**(1판은 이 절의 제목이 "요약", 2판은 "결론"입니다.)

그럼에도 재배포가 불가능한 상황이 있습니다. 원서는 그 경우의 요건도 정합니다.

> 📖 1·2판 7장: **"그것이 가능하지 않다면, 공격자가 한동안 통제했던 시스템을 계속 운영함으로써 상당한 위험을 감수하고 있다는 사실에 대해 경영진의 인지(executive acknowledgment)를 받아야 한다."** 그리고 완화책의 한계를 분명히 합니다 — **"악성코드 스캐너를 돌리고, 침해 지표를 찾기 위해 네트워크와 프로세스를 각별히 주시하고, 다른 보안 조치를 시행할 수는 있다. 그러나 변경된 레지스트리 항목 하나만으로도 공격자가 시스템에 다시 들어오기에 충분할 수 있고, 놓친 악성코드 한 조각이 외부로 연락해 손쉬운 귀환로를 제공할 수 있다."**

**"재배포하지 않기로 하는 것은 기술 결정이 아니라 경영진이 서명하는 위험 수용 결정입니다."** 이 문장을 그대로 복구 절차서에 넣으십시오.

### 🔴 재배포 순서 — 이 순서를 지키지 않으면 재감염된다

| 단계 | 할 일 | 건너뛰면 |
|---|---|---|
| ① 근본 원인 확정 | 최초 침입 경로를 특정한다 | **같은 문을 열어 둔 채 재배포 → 즉시 재감염** |
| ② 원인 제거 | 취약점 패치·설정 수정을 **이미지와 IaC에** 반영 | 새 인스턴스가 같은 취약점을 갖고 태어난다 |
| ③ 증거 보전 완료 확인 | 34.2의 5단계가 끝났는지 | 재배포와 함께 증거 소멸 |
| ④ 자격 증명 전면 순환 | 아래 표 전부 | 공격자가 새 시스템으로 그대로 로그인 |
| ⑤ 골든 AMI·IaC로 재생성 | 22.5의 파이프라인, 28장의 템플릿 | 손으로 만든 시스템 = 검증 불가 |
| ⑥ 데이터 복원 | 오염되지 않은 복구 지점에서(17장) | 오염된 데이터를 되살린다 |
| ⑦ 트래픽 전환 | 새 대상 그룹으로 전환 후 구 시스템 격리 유지 | 롤백 불가 |
| ⑧ 구 시스템 폐기 | 증거 보전 후 삭제 | 잊힌 침해 인스턴스가 계속 살아 있음 |

**①과 ②가 없으면 나머지 전부가 무의미합니다.** 재감염의 대부분은 "빨리 서비스를 올려야 한다"는 압박에 밀려 원인 규명 전에 재배포한 경우입니다. 원인을 아직 모른다면, 재배포는 하되 **의심 경로를 전부 차단한 축소 구성으로** 올리는 것이 정직한 절충입니다.

### 🔴 ④ 자격 증명 순환 — 빠뜨리기 쉬운 목록

11.5의 순환 절차를 사고 상황용 전면 순환으로 확장한 것입니다. **하나라도 빠지면 그것이 재침입 경로가 됩니다.**

| 대상 | 조치 | 빠뜨리기 쉬운 이유 |
|---|---|---|
| IAM 사용자 액세스 키 | 비활성화 후 삭제, 신규 발급 | — |
| IAM 사용자 콘솔 비밀번호 | 재설정 + MFA 재등록 | MFA 장치 자체가 탈취되었을 수 있음 |
| 역할 세션 | 정책으로 발급 시각 기준 폐기(33.3) | **키를 지워도 이미 발급된 세션은 살아 있음** |
| Secrets Manager 시크릿 | `rotate-secret` 즉시 실행 | 자동 순환 주기를 기다리면 늦음 |
| RDS 마스터·앱 계정 비밀번호 | 변경 + 앱 재배포 | 앱 설정에 하드코딩된 사본 |
| SSH 키 페어 | 신규 이미지에서 제외(22.2) | 삭제해도 이미 배포된 인스턴스엔 남아 있음 |
| API 키·웹훅 URL(서드파티) | 발급처에서 재발급 | AWS 밖이라 목록에서 누락 |
| 인증서·서명 키 | 재발급 + 구 인증서 폐기 | 유효기간이 남아 있어 계속 통용됨 |
| IdP 페더레이션 신뢰 | 서명 인증서 교체 | 침해가 IdP에 있었다면 여기가 진짜 원인 |
| 애플리케이션 세션 토큰·쿠키 | 서명 키 교체로 일괄 무효화 | 사용자 세션이 그대로 유지됨 |

### ⚠️ 백업 자체가 오염되었을 가능성

**사고 시나리오.** 재배포는 교과서대로 했습니다. 새 AMI, 새 자격 증명, 새 인스턴스. 그리고 4일 전 백업에서 데이터를 복원했습니다. 이틀 뒤 GuardDuty가 같은 C2 도메인 조회를 다시 탐지합니다. **공격자는 6주 전에 들어와 있었고, 웹셸이 애플리케이션 업로드 디렉터리에 있었으며, 그 디렉터리가 백업에 그대로 들어 있었습니다.**

**원인.** 복구 지점을 **"가장 최근"** 기준으로 골랐고, **침해 시작 시점보다 뒤인 백업**을 썼습니다. RPO만 보고 침해 시점을 보지 않은 것입니다.

**올바른 구성.**

| 규칙 | 구체적으로 |
|---|---|
| 침해 시작 시점을 먼저 확정한다 | 최초 침입 시점 이전의 복구 지점만 후보 |
| 후보를 격리 환경에서 먼저 검증한다 | 포렌식 계정에서 복원 → IOC 스캔 → 통과분만 운영 복원 |
| 코드·설정과 데이터를 분리해 복원한다 | **코드는 백업이 아니라 Git·골든 AMI에서** 온다. 백업에서 되살리는 것은 데이터뿐 |
| 사용자 업로드 파일은 별도 검사 | `shopmini-uploads`의 객체를 멀웨어 스캔 후 반입 |
| 데이터베이스는 변경 이력을 대조한다 | 침해 이전 스냅샷과 스키마·계정·트리거 비교 |
| 백업 계정 분리를 확인한다 | 17.4 — 운영 자격 증명으로 백업을 못 지우는 구조인지 |

> 📖 2판 7장은 백업 자체가 표적이 된다는 점을 사전 준비 항목에서 경고합니다. **"백업이 운영 데이터와는 분리된 관리 자격 증명을 가진 별도의 클라우드 계정에 있는지 확인하라. 공격자가 운영 데이터뿐 아니라 운영 계정에서 접근 가능한 모든 백업까지 지워 버린 문서화된 사례들이 있다."** 이어서 복원 시간도 요건으로 못 박습니다 — **"복원이 얼마나 걸릴지 이해하는 것도 중요하다. 때때로 완벽하게 합리적인 복구 전략을 갖고 있지만, 그 전략이 온 세상이 일주일간 멈추기를 요구하기도 한다."**

> 💡 스냅샷 단계에서 멀웨어를 걸러 내는 AWS 네이티브 수단으로 **GuardDuty Malware Protection**이 있습니다. `guardduty start-malware-scan`으로 특정 EC2 인스턴스의 EBS 볼륨을 온디맨드로 스캔합니다(스캔은 AWS 관리 환경에서 스냅샷을 대상으로 수행되므로 인스턴스에 에이전트를 넣지 않습니다). 만능은 아니지만 **재배포 전 1차 관문**으로 유용합니다.

### 통지

원서는 복구 절에서 통지를 함께 다룹니다.

> 📖 1·2판 7장 "통지": **"고객에게 알리거나 법 집행 당국에 침해를 신고할 규제상·계약상 의무가 있을 수 있다. 세상에 알릴 의무가 없더라도, 결국 말이 새어 나갔을 때의 홍보 참사를 피하기 위해 어쨌든 알리고 싶을 수 있다."** 은폐에 대해서는 이렇게 씁니다 — **"명백한 이유로 성공한 은폐가 얼마나 많은지에 대한 좋은 통계는 없지만, 실패한 은폐의 잘 알려진 사례들은 있다."**(2판은 Yahoo!·Cathay Pacific·Uber를 예로 들고, **1판에는 Uber가 없습니다.**)

통지의 실무(신고 기한, 수신자별 문안)는 33.6에서 다뤘습니다. 복구 단계에서 확인할 것은 하나입니다. **"복구 완료"를 알리기 전에 근본 원인이 제거되었는지 재확인하십시오.** 완료 통지 후의 재감염은 첫 사고보다 신뢰 손상이 큽니다.

## 34.6 교훈 정리(Lessons Learned)

### 언제, 무엇을 고치는가

> 📖 1·2판 7장 "배운 교훈": **"가능한 한 빨리, 모두가 하룻밤 잘 자고 난 뒤에, 배운 교훈을 살펴보고 다음번에 도움이 될 팀 구성·계획·절차·도구·체크리스트에 대한 갱신을 수행해야 한다. 사고 진행 중에 빠른 메모와 상기 사항을 적어 둘 기회를 잡았기를 바란다."** 저자는 사고 대응 중에 메모하라는 조언을 앞에서도 반복합니다 — **"진행하면서 배운 교훈을 15초만 들여 적어 두라. 나중에는 기억하기 어려울 수 있기 때문이다."**

두 가지를 정확히 읽어야 합니다. **첫째, 시점은 "가능한 한 빨리, 단 하룻밤 자고 난 뒤"입니다.** 탈진 상태에서 여는 회고는 감정만 남기고, 2주를 미루면 세부가 사라집니다. **72시간 이내**가 타협점입니다. **둘째, 갱신 대상이 지정되어 있습니다** — 팀 구성, 계획, 절차, 도구, 체크리스트. 회고의 산출물은 "느낀 점"이 아니라 **이 다섯 가지의 변경분**입니다.

### 비난 없는 회고를 실제로 만드는 규칙

비난 없는 사후 검토(blameless postmortem)는 원서가 쓰는 표현은 아니지만, 원서가 요구하는 "다음번에 도움이 될 갱신"을 얻으려면 사실상 전제 조건입니다. **사람을 탓하는 회고에서는 아무도 진실을 말하지 않고, 진실이 없으면 고칠 대상도 찾을 수 없습니다.**

| 규칙 | 나쁜 예 | 좋은 예 |
|---|---|---|
| 사람이 아니라 시스템을 지목한다 | "김 대리가 키를 커밋했다" | "키를 커밋해도 막히지 않는 파이프라인이었다" |
| "왜 그렇게 했나"를 합리적 선택으로 읽는다 | "왜 확인 안 했나" | "그 시점에 확인할 수단이 있었나" |
| 결과가 아니라 과정을 평가한다 | "다행히 큰 피해가 없었다" | "탐지가 늦었고 운으로 피해가 작았다" |
| 사후 확신 편향을 경계한다 | "명백한 징후였다" | "당시 알 수 있던 정보만으로 판단한다" |
| 참석자를 제한하지 않는다 | 관리자만 참석 | 실제 대응한 사람 전원 |

### 타임라인 재구성

회고의 뼈대는 타임라인입니다. **두 개의 시계를 나란히 놓는 것**이 핵심입니다 — 공격자가 무엇을 했는가(공격 타임라인)와 우리가 무엇을 했는가(대응 타임라인).

| 시각(UTC) | 공격자 행위 | 근거 | 우리 행위 | 근거 |
|---|---|---|---|---|
| 08:41 | 노출된 키로 `sts:GetCallerIdentity` | CloudTrail | — | — |
| 08:43 | `s3:ListBuckets` 열거 | CloudTrail | — | — |
| 09:02 | `shopmini-uploads` 대량 다운로드 | S3 데이터 이벤트 | — | — |
| 09:20 | — | — | GuardDuty 결과 생성 | Security Hub |
| 09:47 | — | — | 온콜 확인, 사고 선언 | 채팅 로그 |
| 10:05 | — | — | 키 비활성화·세션 폐기 | CloudTrail |

이 표가 완성되면 **MTTD와 MTTR이 자동으로 나옵니다**(32.6). 08:41에서 09:20까지가 탐지 시간, 09:20에서 10:05까지가 대응 착수 시간입니다. 그리고 **비어 있는 칸이 다음 통제 개선 항목**입니다. 위 예에서 09:02의 대량 다운로드에 대응 행이 비어 있다면, "데이터 반출량 급증 알람이 없다"가 액션 아이템입니다.

타임라인 재구성에 쓰는 도구는 31장과 29장에서 이미 갖췄습니다. CloudTrail Lake의 SQL 질의, Athena, Detective의 행동 그래프를 조합합니다.

```bash
# CloudTrail Lake — 특정 액세스 키의 전체 활동을 시간순으로
# (이벤트 데이터 스토어가 있는 로그 아카이브 계정 프로파일로 실행한다)
aws cloudtrail start-query \
  --query-statement "
    SELECT eventTime, eventName, sourceIPAddress, requestParameters
    FROM 1a2b3c4d-5e6f-7890-abcd-ef1234567890
    WHERE userIdentity.accessKeyId = 'AKIAIOSFODNN7EXAMPLE'
      AND eventTime BETWEEN '2026-09-06 00:00:00' AND '2026-09-07 00:00:00'
    ORDER BY eventTime" \
  --region ap-northeast-2 --profile awssec-logs
```

질의 ID를 받으면 `aws cloudtrail get-query-results --query-id <ID>`로 결과를 가져옵니다.

### 액션 아이템을 통제로 연결하기

**회고의 실패는 대부분 마지막 단계에서 일어납니다.** 좋은 논의를 하고, 좋은 목록을 만들고, 아무도 하지 않습니다. 액션 아이템은 다음 다섯 칸이 모두 채워져야 유효합니다.

| 칸 | 규칙 |
|---|---|
| 무엇을 | 통제 하나로 서술한다. "보안 강화" 금지 |
| 어느 계층 | 예방 / 탐지 / 대응 / 복구 중 하나로 분류 |
| 소유자 | **개인 이름.** 팀 이름은 소유자가 아니다 |
| 기한 | 날짜. "다음 분기" 금지 |
| 검증 방법 | **어떻게 확인할 것인가**. 검증 없는 항목은 완료 판정이 불가능하다 |

분류가 왜 필요한가 하면, **회고 결과가 예방 항목에만 몰리는 편향**을 잡기 위해서입니다. 사고를 겪은 직후에는 "다시는 못 들어오게"에 집중하기 쉽지만, 위 타임라인에서 실제로 손해를 키운 것은 탐지 39분과 대응 착수 45분이었습니다.

| 액션 | 계층 | 소유자 | 기한 | 검증 |
|---|---|---|---|---|
| 업로드 버킷 데이터 반출량 알람 | 탐지 | (이름) | 09-20 | 테스트 반출로 알람 발화 확인 |
| 액세스 키 발급 자체를 SCP로 금지 | 예방 | (이름) | 09-30 | `iam:CreateAccessKey` 거부 확인 |
| 세션 폐기를 원클릭 런북으로 | 대응 | (이름) | 09-25 | 훈련에서 5분 내 실행 |
| 증거 버킷 객체 잠금 사전 구성 | 복구 | (이름) | 09-15 | 삭제 시도가 거부되는지 확인 |

그리고 **다음 탁상 훈련(32.5)의 시나리오를 이번 사고로 만드십시오.** 액션 아이템이 실제로 작동하는지 확인하는 가장 값싼 방법입니다.

원서는 이 주제가 이 책의 범위를 넘는다는 점도 밝힙니다.

> 📖 1·2판 7장: **"사고 대응 팀과 프로세스 전체를 구축하는 것은 큰 주제다. 여기서는 클라우드 환경에 대한 핵심만 다뤘으며, 더 읽을거리로 AT&T의 『Insider's Guide to Incident Response』와 NIST SP 800-61을 추천한다."**(**1판은 같은 문서를 "AlienVault의"로 표기합니다** — AlienVault가 AT&T에 인수된 결과입니다.)

이 장에서 정리한 교훈이 개별 사고의 기록으로 끝나지 않고 **조직의 성숙도로 축적되는 방법**은 39.1에서 다룹니다.

## 이 장의 요약

| 항목 | 핵심 |
|---|---|
| 클라우드 포렌식의 본질 | 중요한 것의 포렌식 사본을 만들고 도구로 분석한다. 사본은 **문서화되고 반복 가능한 방식**으로 |
| 물리 디스크의 부재 | 압수할 하드웨어가 없는 대신 API 한 줄로 완전한 사본을 만든다 |
| 증거의 경계 | 대부분의 증거는 **사고 전에 켜 둔 로그**에서만 나온다. 제공자 계층 로그는 볼 수 없다 |
| 휘발성 순서 | 메모리 · 인스턴스 스토어 → 세션 → EBS → CloudWatch → S3 |
| 증거 보전 5단계 | 스냅샷·태깅 → 메모리 → 로그 범위·복사·잠금 → 해시 → 관리 연속성 |
| KMS의 함정 | AWS 관리형 키로 암호화된 스냅샷은 **공유 불가**. 사고 당일에는 못 고친다 |
| 격리 분석 | 인터넷 없는 포렌식 계정, 게스트 OS 수준 읽기 전용 마운트(`ro,noload` 또는 `blockdev --setro`) |
| 감사 인프라 신뢰도 | 침해된 시스템 안의 로그는 단독 근거가 될 수 없다. 시스템 밖 기록과 교차 검증 |
| 시간 | 모든 타임라인은 **UTC 단일 기준**. 시간대 혼용이 인과를 뒤집는다 |
| 복구 원칙 | **치료하지 말고 재배포한다.** 못 하면 경영진의 위험 수용 서명 |
| 재배포 순서 | 원인 확정 → 원인 제거 → 증거 보전 확인 → 자격 증명 전면 순환 → 재생성 → 데이터 복원 → 전환 → 폐기 |
| 백업 오염 | 침해 시작 시점 **이전** 복구 지점만 후보. 코드는 백업이 아니라 Git·AMI에서 |
| 교훈 정리 | 하룻밤 자고 72시간 내. 산출물은 **팀·계획·절차·도구·체크리스트의 변경분** |

## 🔴 필수 구성 체크리스트

- [ ] 증거 전용 S3 버킷을 **객체 잠금을 켠 상태로 사고 전에** 생성했다
- [ ] EBS 기본 암호화 키가 **고객 관리형 키**이고, 키 정책이 포렌식 계정의 `Decrypt`·`CreateGrant`·`ReEncryptFrom`을 허용한다
- [ ] 포렌식 분석 AMI에 LiME 커널 모듈이 **골든 AMI의 커널 버전에 맞춰** 미리 빌드되어 있다
- [ ] 포렌식 VPC에 IGW·NAT가 없고, SCP로 생성이 금지되어 있다
- [ ] `LegalHold=true` 태그가 붙은 스냅샷의 삭제를 SCP로 차단했다
- [ ] 증거 계정에서 조사자의 행위가 **데이터 이벤트까지** 기록된다
- [ ] 관리 연속성 문서 템플릿이 존재하고, 이관 기록 행이 포함되어 있다
- [ ] 모든 인스턴스가 Amazon Time Sync Service로 시각 동기화되어 있다
- [ ] 애플리케이션 로그가 **타임존 오프셋을 포함한 ISO 8601**로 기록된다
- [ ] 재배포 절차서에 "근본 원인 제거 확인" 게이트가 명시적 단계로 들어 있다
- [ ] 자격 증명 전면 순환 목록에 **서드파티 API 키와 IdP 서명 인증서**가 포함되어 있다
- [ ] 백업 복구 지점 선택 규칙이 "가장 최근"이 아니라 **"침해 시작 이전"** 으로 되어 있다
- [ ] 회고 액션 아이템 양식에 소유자·기한·**검증 방법** 칸이 있다

| 인스턴스를 먼저 종료하고 조사 시작 | 메모리·인스턴스 스토어 영구 소멸 | 격리는 보안 그룹으로. 종료는 메모리 확보 후 |
| 볼륨별로 따로 스냅샷 | 볼륨 간 시점 불일치로 분석 불가 | `create-snapshots`로 인스턴스 단위 일괄 |
| AWS 관리형 키로 암호화된 볼륨 | 스냅샷 공유 불가 — 사고 당일 해결 불가 | 사전에 고객 관리형 키로 기본 암호화 |
| 스냅샷 공유만 받고 복사하지 않음 | 침해된 운영 계정이 증거를 삭제·회수 가능 | 포렌식 계정 키로 `copy-snapshot` |
| `mount -o ro`만으로 읽기 전용 확보 | ext4 저널 재생으로 증거 디스크에 쓰기 발생 | `ro,noload` 또는 `blockdev --setro` |
| 분석 인스턴스에 NAT를 잠깐 붙임 | 분석 중 실행된 샘플이 C2와 통신 | SCP로 IGW·NAT 생성 자체를 금지 |
| 로그 시각을 콘솔 표시값(로컬)으로 옮겨 적음 | 인과가 뒤집힌 타임라인, 조사 신뢰도 붕괴 | 모든 문서 UTC 고정, 병기는 요약본에서만 |
| CloudTrail이 비어 있어 "지웠다"고 결론 | 데이터 이벤트 미설정·전달 지연을 오독 | 이벤트 선택기 설정 이력부터 확인 |
| 침해 시스템의 로컬 로그로 결론을 씀 | 공격자가 편집한 기록을 증거로 채택 | 시스템 밖 독립 기록과 교차 검증 |
| 서비스 압박에 밀려 원인 규명 전 재배포 | 같은 경로로 즉시 재감염 | 원인 확정·제거를 재배포의 선행 게이트로 |
| 멀웨어 스캔 후 원래 시스템을 계속 운영 | 백도어 하나로 공격자 귀환 | 재배포. 불가하면 경영진 위험 수용 서명 |
| 가장 최근 백업으로 복원 | 침해 이후 백업 = 웹셸까지 복원 | 침해 시작 이전 복구 지점 + 격리 환경 검증 |
| 회고에서 담당자 실수를 결론으로 | 다음 사고 때 아무도 사실을 말하지 않음 | 시스템 결함으로 재서술, 통제 개선으로 연결 |

## 다음 장 예고

여기까지가 사람이 하는 사고 대응입니다. 그런데 34장의 절차 중 상당수는 **매번 똑같습니다.** 노출된 키를 비활성화하고, 퍼블릭이 된 버킷을 다시 닫고, 열린 보안 그룹을 되돌리고, 침해 인스턴스를 격리하고 스냅샷을 뜨는 일 — 새벽 3시에 사람이 손으로 할 이유가 없습니다.

35장은 **대응 자동화(SOAR)** 입니다. EventBridge와 Lambda로 탐지에서 조치까지를 잇고, AWS Config 자동 교정과 Security Hub 사용자 지정 작업을 배선합니다. 그리고 가장 중요한 질문을 먼저 다룹니다 — **무엇을 자동화하면 안 되는가.** 오탐 한 번에 서비스를 내리는 자동화는 공격자보다 더 큰 피해를 줍니다. ⚠️ 드라이런, 예외 태그, 서킷 브레이커라는 세 가지 안전장치가 그래서 필요합니다.
