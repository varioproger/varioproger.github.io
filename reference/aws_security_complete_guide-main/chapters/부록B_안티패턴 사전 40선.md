## 사용법 — 자기 환경 역방향 점검 절차

한 번에 40개를 다 보지 마십시오. 아래 순서로 돌리면 하루 안에 1회전이 끝납니다.

📋 **1회전 절차**

- [ ] **1단계 — 범위를 고정한다.** 계정 목록과 리전 목록을 먼저 뽑는다. 점검은 "우리가 쓰는 리전"이 아니라 **조직의 모든 계정 × 모든 리전**이 대상이다. 미사용 리전이야말로 AP-16·AP-19·AP-30이 숨는 곳이다.
- [ ] **2단계 — 매트릭스 좌상단부터 본다.** 아래 2×2 매트릭스에서 **잦음 × 치명** 사분면(15개)을 먼저 전부 확인한다. 여기서 하나라도 "예"가 나오면 나머지 점검을 멈추고 그것부터 처리한다.
- [ ] **3단계 — 증상만 읽고 O/X를 찍는다.** 각 항목의 **증상** 칸만 읽고 우리 환경에 해당하는지 판정한다. 이 단계에서는 "왜 위험한가"를 읽지 않는다. 읽기 시작하면 변명이 생긴다.
- [ ] **4단계 — "예"가 나온 항목만 탐지 명령을 돌린다.** 감이 아니라 **출력**으로 확인한다. 출력이 비어 있으면 안심하지 말고 명령이 옳은 계정·리전을 향했는지부터 본다.
- [ ] **5단계 — 확정된 항목마다 소유자·기한·대체 통제를 적는다.** 오늘 못 고치는 것이 나온다. 그때 필요한 것은 리스크 등록부의 한 줄이지 침묵이 아니다(4.1).
- [ ] **6단계 — 본문 절로 돌아간다.** 각 항목 맨 아래 **본문** 절 번호로 가면 그 통제의 전체 맥락과 실습이 있다.
- [ ] **7단계 — 탐지를 상시화한다.** 1회전에서 "예"가 나온 항목은 Config 규칙·Security Hub 컨트롤·EventBridge 규칙 중 하나로 **상시 평가**로 옮긴다. 사람이 분기마다 도는 점검은 세 번째 분기에 멈춘다.

⚠️ **점검할 때 가장 흔한 자기 기만 두 가지**

1. **"우리는 그렇게 안 합니다"로 넘어가는 것.** 조직이 커질수록 "우리"의 범위는 여러분이 아는 것보다 넓습니다. 반드시 API 출력으로 확인하십시오.
2. **출력이 0건인 것을 통제가 있는 것으로 읽는 것.** 스캔하지 않은 계정은 항상 0건입니다(AP-33). 모든 판정에 **분모**를 붙이십시오.

## B-1. 아이덴티티·권한 (7)

### AP-01. 장기 액세스 키 상시 사용
**증상** — IAM 사용자에게 `AccessKeyId`가 붙어 있고 `CreateDate`가 수개월~수년 전이다. CI 파이프라인, 서버 안의 `~/.aws/credentials`, SaaS 연동 설정에 `AKIA...`로 시작하는 문자열이 들어 있다.
**왜 위험한가** — 액세스 키는 **만료가 없는 전권 문자열**입니다. 저장소에 커밋되거나 로그에 찍히는 순간 스캐너 봇이 수 분 내에 사용하고, 그때부터 리소스 생성·데이터 반출·크립토마이닝이 시작됩니다. 키 자체는 "누가 썼는지"를 구분하지 못하므로 사람과 파이프라인이 키를 공유하면 회수할 때 양쪽이 함께 멈춥니다.
**올바른 구성** — 사람은 IAM Identity Center의 단기 자격 증명, EC2·ECS는 인스턴스 프로파일·태스크 역할, 외부 CI는 OIDC 페더레이션으로 전환합니다. 키 발급 자체를 SCP로 금지하는 것이 관리보다 확실합니다. 유출이 확인되면 삭제가 아니라 **먼저 `Inactive`** 로 두고 CloudTrail 조사를 마친 뒤 삭제합니다.
**탐지 방법**
```bash
aws iam generate-credential-report
aws iam get-credential-report --query Content --output text | base64 -d | cut -d, -f1,9,10,11,14,15,16
```
Config 관리형 규칙 `access-keys-rotated`·`iam-user-mfa-enabled`. CloudTrail 이벤트 `CreateAccessKey`에 상시 알람.
**본문** — 6.4절, 3.4절, 5.6절

### AP-02. 와일드카드 IAM 정책
**증상** — 정책 문서에 `"Action": "*"`, `"Resource": "*"`, 혹은 `"Effect": "Allow"` + `"NotAction"` 조합이 들어 있다. 워크로드 역할에 `AmazonS3FullAccess` 같은 `*FullAccess` 관리형 정책이 붙어 있다.
**왜 위험한가** — `Allow` + `NotAction`은 "지금 존재하는 서비스"뿐 아니라 **앞으로 출시될 모든 서비스**를 자동으로 허용합니다. 워크로드 역할의 `*FullAccess`는 SSRF 하나, 애플리케이션 RCE 하나로 계정의 모든 버킷·모든 테이블이 열리는 것을 뜻합니다. 사람에게만 최소 권한을 적용하고 앱 역할을 방치하는 것이 가장 흔한 형태입니다.
**올바른 구성** — 필요한 `Action`을 **열거**하고 `Resource`를 ARN 접두사까지 좁힙니다. 최소 권한 초안은 Access Analyzer의 정책 생성 기능으로 만들되, 월말·분기 배치와 재해 복구 경로가 관측 기간에 들어갔는지 확인한 뒤 배포합니다. 역할 생성을 IaC로만 허용하고 **권한 경계**로 상한선을 겁니다.
**탐지 방법**
```bash
aws accessanalyzer validate-policy \
  --policy-type IDENTITY_POLICY \
  --policy-document file://policy.json \
  --query 'findings[?findingType!=`SUGGESTION`]'
```
Config 관리형 규칙 `iam-policy-no-statements-with-admin-access`. Security Hub의 IAM 계열 컨트롤 중 "관리자 권한을 부여하는 정책 금지" 성격의 항목.
**본문** — 7.5절, 7.6절, 2.4절

### AP-03. `iam:PassRole` 무제한
**증상** — 정책에 `"Action": "iam:PassRole"`이 `"Resource": "*"`로 들어 있다. 조건 블록이 없다.
**왜 위험한가** — `PassRole`은 단독으로는 조용하지만 **다른 권한과 조합되면 관리자 등가**가 됩니다. 예를 들어 Lambda 생성 권한이나 EC2 시작 권한을 가진 사용자가 `PassRole: *`를 함께 가지면, 계정에서 가장 강한 역할을 자기가 만든 함수·인스턴스에 붙여 그 권한으로 코드를 실행할 수 있습니다. 그 순간 그 사람의 실질 권한 상한은 **계정 최강 역할**이 됩니다.
**올바른 구성** — 전달 가능한 역할을 ARN 또는 ARN 접두사로 한정하고, `iam:PassedToService` 조건으로 어떤 서비스에 넘길 수 있는지까지 고정합니다.
```json
{
  "Effect": "Allow",
  "Action": "iam:PassRole",
  "Resource": "arn:aws:iam::111122223333:role/shopmini-app-*",
  "Condition": {
    "StringEquals": { "iam:PassedToService": "ec2.amazonaws.com" }
  }
}
```
**탐지 방법**
```bash
aws iam get-account-authorization-details --filter Role User Group LocalManagedPolicy \
  --output json > /tmp/iam-dump.json
```
받은 덤프에서 `iam:PassRole`이 들어간 문장의 `Resource`가 `*`인 것을 찾습니다. CloudTrail 이벤트 `PutRolePolicy`·`AttachRolePolicy`·`CreatePolicyVersion`에 알람을 걸어 신규 유입을 잡습니다.
**본문** — 7.5절, 3.4절

### AP-04. 신뢰 정책의 `"AWS":"*"`
**증상** — 역할의 신뢰 정책 `Principal`이 `{"AWS": "*"}`이거나, 크로스 계정 신뢰에 상대 **계정 root만** 적혀 있고 조건이 하나도 없다. 버킷 정책 `Principal`이 `"*"`로 되어 있다.
**왜 위험한가** — 신뢰 정책의 `"*"`는 **전 세계 모든 AWS 계정**이 그 역할을 맡을 수 있다는 선언입니다. 역할 ARN은 비밀이 아니며 열거 가능합니다. 계정 root만 적은 경우도 마찬가지로 상대 계정의 **모든 주체**가 진입할 수 있어, 상대 계정의 말단 사용자 한 명이 침해되면 우리 계정으로 넘어옵니다. 크로스 계정이 안 될 때 임시로 `"*"`로 바꿔 두고 잊는 것이 전형적인 발생 경로입니다.
**올바른 구성** — 상대 역할 ARN을 명시하고, 조직 내부라면 `aws:PrincipalOrgID`를 조건으로 겁니다. 이때 `StringNotEquals` 대신 **`StringNotEqualsIfExists`** 를 쓰고 `aws:PrincipalIsAWSService` 예외를 함께 두지 않으면 CloudTrail 로그 전달·S3 복제 같은 AWS 서비스 경유 경로가 조용히 끊깁니다.
**탐지 방법**
```bash
aws iam list-roles --query 'Roles[].[RoleName,AssumeRolePolicyDocument]' --output json \
  | python3 -c "import sys,json,urllib.parse;d=json.load(sys.stdin);[print(n) for n,p in d if '\"*\"' in json.dumps(p)]"
```
IAM Access Analyzer의 **외부 접근 분석기**를 조직 단위로 하나 만들어 두면 계정 밖으로 열린 역할·버킷·키를 자동으로 올려 줍니다. CloudTrail 이벤트 `UpdateAssumeRolePolicy`·`PutBucketPolicy`.
**본문** — 7.5절, 7.7절, 8.1절

### AP-05. External ID 없는 서드파티 역할
**증상** — 모니터링·비용 관리·보안 SaaS 벤더에게 발급한 역할의 신뢰 정책에 벤더 계정 ID만 있고 `sts:ExternalId` 조건이 없다. 벤더가 준 CloudFormation 템플릿을 그대로 배포했고 권한은 `ReadOnlyAccess`다.
**왜 위험한가** — **혼동된 대리자(Confused Deputy)** 가 성립합니다. 벤더는 수많은 고객의 역할을 맡을 수 있는 위치에 있으므로, 그 벤더의 다른 고객이 우리 역할 ARN을 자기 설정에 입력하면 벤더가 대신 우리 계정에 들어옵니다. `ReadOnlyAccess`에는 `s3:GetObject`가 포함되므로 이것은 곧 조직 전체 데이터 열람입니다.
**올바른 구성** — **벤더가 발급한** 고객별 고유·비추측 External ID를 조건으로 겁니다(우리가 임의로 정하면 벤더가 전송하지 못해 실패합니다). 권한은 벤더 템플릿을 그대로 쓰지 말고 필요한 액션만 재작성하고 권한 경계를 붙입니다.
```json
{
  "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::999988887777:root" },
  "Action": "sts:AssumeRole",
  "Condition": {
    "StringEquals": { "sts:ExternalId": "shopmini-7f3c1a92-prod" }
  }
}
```
⚠️ **AWS 서비스**를 신뢰하는 역할에는 `sts:ExternalId`를 걸면 안 됩니다. 서비스가 값을 보내지 않아 모든 호출이 실패합니다 — 그쪽은 `aws:SourceAccount` + `aws:SourceArn`입니다.
**탐지 방법** — 신뢰 정책에서 `Principal`이 외부 계정인데 `sts:ExternalId` 조건이 없는 역할을 전수 조회합니다. Access Analyzer 외부 접근 결과에서 **조직 밖 계정**으로 분류된 역할이 1차 목록입니다. CloudTrail 이벤트 `UpdateAssumeRolePolicy`와, 해당 역할에 대한 `AssumeRole` 호출의 출발지 계정을 함께 감시합니다.
**본문** — 8.6절, 31.7절, 7.5절

### AP-06. 퇴사자·직무 변경자 권한 미회수
**증상** — IdP에서는 비활성인데 AWS 쪽 그룹 멤버십·권한 집합 할당이 남아 있다. 사용자를 삭제했는데 발급된 세션·액세스 키가 살아 있다. 재검증을 연 1회 설문으로 하고 전원이 "필요합니다"로 회신한다.
**왜 위험한가** — 회수되지 않은 권한은 **소유자가 없는 관리자 계정**입니다. 개인 단말에 남은 자격 증명, 개인 메일로 옮겨 둔 키가 조직의 탐지 범위 밖에서 그대로 유효합니다. 회수 트리거를 "퇴사"만으로 두면 프로젝트 종료·직무 변경 때 권한이 누적되고, 몇 년 뒤 그 사람은 사실상 전사 관리자가 됩니다. 비인간 아이덴티티(서비스 역할·CI 사용자·SaaS 역할)를 재검증에서 빼는 것도 같은 문제입니다.
**올바른 구성** — SCIM 프로비저닝으로 IdP와 AWS를 동기화하고, 할당은 **개인이 아니라 그룹에만** 합니다. 회수 트리거를 ① 퇴사 ② 직무 변경 ③ 프로젝트 종료 세 가지로 정의합니다. 삭제만으로는 부족하므로 **활성 세션 삭제**까지 한 묶음으로 처리하고, 포털 세션 수명을 12시간 이하로 둡니다. 재검증은 설문이 아니라 **미사용 액세스 분석기** 결과를 근거로 합니다.
**탐지 방법**
```bash
aws iam generate-service-last-accessed-details --arn arn:aws:iam::111122223333:role/ROLE_NAME
```
IAM Access Analyzer의 **미사용 액세스 분석기**(미사용 역할·미사용 권한·미사용 키를 결과로 올림). Config 규칙 `access-keys-rotated`. 검토자·일자·회수 건수를 기록으로 남기지 않으면 감사에서는 절차가 없는 것으로 판정됩니다.
**본문** — 9.6절, 9.3절, 6.4절

### AP-07. MFA 강제 정책이 `Bool` 조건으로 우회되는 구성
**증상** — MFA를 요구하는 `Deny` 문장에 `"Bool": {"aws:MultiFactorAuthPresent": "false"}`가 들어 있다. MFA 강제 정책의 `NotAction`에 `sts:GetSessionToken`이 빠져 있다.
**왜 위험한가** — `aws:MultiFactorAuthPresent`는 **키가 없는 요청에서는 존재하지 않는 조건 키**입니다. `Bool`은 키가 없으면 매칭되지 않으므로, 장기 액세스 키로 들어온 호출에서 이 `Deny`가 **발동하지 않습니다**. 즉 막고 싶던 대상(AP-01)이 정확히 통과합니다. 조직 전체에 MFA를 강제했다고 믿는 상태에서 실제로는 아무것도 막고 있지 않은, 가장 조용한 실패입니다.
**올바른 구성** — **`Deny`에는 `BoolIfExists`, `Allow`에는 `Bool`** 이 원칙입니다. 그리고 CLI 사용자가 MFA 승격 세션을 받을 경로를 남기기 위해 `sts:GetSessionToken`을 예외에 넣습니다. 브레이크 글래스 계정은 이 정책 대상에서 분리합니다 — 정상 인증 경로가 막혔을 때 쓸 계정이 함께 잠깁니다.
```json
{
  "Effect": "Deny",
  "NotAction": [
    "iam:ChangePassword", "iam:CreateVirtualMFADevice",
    "iam:EnableMFADevice", "iam:ListMFADevices", "sts:GetSessionToken"
  ],
  "Resource": "*",
  "Condition": {
    "BoolIfExists": { "aws:MultiFactorAuthPresent": "false" }
  }
}
```
**탐지 방법** — 계정 권한 덤프에서 `aws:MultiFactorAuthPresent`를 포함한 문장을 뽑아 `Effect`와 연산자를 대조합니다. `Deny` + `Bool` 조합이 나오면 전부 결함입니다. 실제 효과는 `aws iam simulate-principal-policy`로 확인하되, SCP·리소스 정책은 반영되지 않으므로 개발 계정 실호출로 최종 확인합니다.
**본문** — 7.4절, 9.4절, 5.2절

## B-2. 데이터·암호화 (6)

### AP-08. User Data·환경 변수에 평문 시크릿
**증상** — EC2 User Data 스크립트나 Lambda 환경 변수, ECS 태스크 정의의 `environment` 필드에 DB 비밀번호·API 키가 값 그대로 들어 있다.
**왜 위험한가** — User Data는 인스턴스 메타데이터의 `latest/user-data` 경로로 **인증 없이** 읽힙니다. SSRF 취약점 하나, 또는 `ec2:DescribeInstanceAttribute` 권한 하나면 평문으로 나옵니다(AP-25와 결합하면 경로가 더 짧아집니다). Lambda 환경 변수는 `ReadOnlyAccess` 보유자 전원이 콘솔에서 열람할 수 있고, 크래시 덤프·APM 트레이스·`docker inspect` 출력으로도 새어 나갑니다.
**올바른 구성** — 값이 아니라 **참조**만 환경에 두고 런타임에 조회합니다. Parameter Store `SecureString` 또는 Secrets Manager에 넣고 고객 관리형 키(`alias/shopmini/app`)로 암호화한 뒤, 인스턴스 역할·실행 역할에 읽기 권한만 부여합니다. 이미 넣었던 값은 스크립트를 고치는 것으로 끝나지 않습니다 — **그 값은 이미 유출된 것으로 취급하고 순환**시킨 뒤 인스턴스를 교체합니다.
**탐지 방법**
```bash
aws ec2 describe-instance-attribute --instance-id i-0123456789abcdef0 \
  --attribute userData --query 'UserData.Value' --output text | base64 -d
aws lambda list-functions --query 'Functions[].[FunctionName,Environment.Variables]' --output json
```
Parameter Store에 `--type String`으로 들어간 시크릿은 오류 없이 평문 저장되므로 Config 규칙으로 상시 점검합니다.
**본문** — 22.4절, 11.1절, 11.2절, 24.6절

### AP-09. 코드·이미지에 하드코딩된 시크릿
**증상** — 저장소 히스토리에 `.env`·자격 증명 파일이 있다. Dockerfile에 `ENV DB_PASSWORD=` 또는 `ARG`로 받은 토큰이 레이어에 남아 있다. AMI 안에 `~/.aws/credentials`나 Vault 토큰이 구워져 있다.
**왜 위험한가** — 저장소가 공개되거나 포크되는 순간 스캐너가 즉시 수집합니다. **커밋에서 지워도 히스토리에는 남습니다.** 컨테이너 이미지도 같습니다 — 나중 레이어에서 파일을 지워도 이전 레이어에서 추출할 수 있습니다. AMI에 구워진 자격 증명은 그 AMI로 뜬 모든 인스턴스, 그리고 그 AMI를 공유받은 모든 계정에 복제됩니다(AP-16과 결합하면 회수 불가).
**올바른 구성** — 빌드 시점 주입을 없애고 **실행 시점 조회**로 바꿉니다. ECS는 태스크 정의의 `secrets` 필드(권한은 **실행 역할**에 부여), Kubernetes는 CSI Driver/External Secrets + IRSA, EC2는 인스턴스 역할 + Parameter Store입니다. 순환하는 DB 자격 증명은 `secrets` 필드로 주입하면 태스크 재시작 전까지 옛 값을 쓰게 되므로 SDK 캐싱 조회로 읽습니다. 발견 시 대응은 코드 정리가 아니라 **폐기와 순환**입니다.
**탐지 방법** — CI에 시크릿 스캐너를 넣어 신규 커밋부터 차단하고(기존 코드베이스에 차단 게이트를 한꺼번에 걸면 개발자가 게이트를 꺼 버립니다), 이미지에 대해서는 레지스트리 스캔을 붙입니다. AWS 쪽 신호로는 **GuardDuty의 자격 증명 오용 계열 결과**(역할 자격 증명이 EC2 밖에서 사용됨)가 가장 직접적입니다.
**본문** — 11.1절, 24.2절, 27.4절, 11.6절

### AP-10. 키 정책 락아웃
**증상** — KMS 키 정책에서 `EnableIAMUserPermissions` 문장(계정 root에 `kms:*`를 허용하는 기본 문장)을 지웠거나, 키 관리 권한을 가진 프린시펄이 삭제된 역할 ARN 하나뿐이다.
**왜 위험한가** — KMS 키 정책은 **접근 통제의 최종 관문**입니다. IAM에 `kms:*`가 있어도 키 정책이 허용하지 않으면 통과하지 못합니다. 기본 문장을 지우고 관리 경로까지 잃으면 **그 키는 영구 락아웃**되고, 그 키로 암호화된 모든 데이터가 함께 잠깁니다. AWS Support 외에 복구 경로가 없습니다. 반대 방향의 사고도 있습니다 — 운영 계정 키 하나로 백업까지 암호화해 두면 `ScheduleKeyDeletion` 한 번으로 원본과 백업이 동반 사망합니다(AP-17).
**올바른 구성** — 기본 문장을 **지우지 말고** 조건과 SCP로 좁힙니다. 키 관리자와 키 사용자를 분리하고, 관리자는 2인 이상의 역할로 둡니다. 환경·데이터 등급·파기 단위별로 키를 나눠 하나의 키 사고가 전체로 번지지 않게 합니다.
**탐지 방법**
```bash
aws kms get-key-policy --key-id alias/shopmini/app --policy-name default --output text
aws kms list-aliases --query 'Aliases[].[AliasName,TargetKeyId]' --output table
```
CloudTrail 이벤트 `PutKeyPolicy`에 변경 알람, `ScheduleKeyDeletion`에 **즉시 호출** 경보를 겁니다(대기 기간 7~30일 동안 아무도 모르는 것이 실제 사고 형태입니다).
**본문** — 13.4절, 13.11절, 17.5절, 12.6절

### AP-11. AWS 관리형 키 고착
**증상** — 버킷·볼륨·스냅샷·시크릿이 전부 `alias/aws/s3`, `alias/aws/ebs`, `alias/aws/rds`, `alias/aws/secretsmanager` 같은 AWS 관리형 키로 암호화되어 있다. "암호화 켜져 있음"으로 점검 항목이 닫혀 있다.
**왜 위험한가** — AWS 관리형 키에는 **키 정책이라는 2차 관문이 없습니다.** S3 권한 설정 실수 하나가 곧 평문 유출이 됩니다. 더 실무적인 문제는 **크로스 계정 공유가 원천적으로 불가능**하다는 점입니다 — DR 구성이나 포렌식 계정으로 스냅샷을 넘겨야 하는 날, 전량 재암호화부터 시작해야 합니다. DynamoDB의 AWS 소유 키는 KMS 호출이 CloudTrail에 남지 않아 **사고 조사 자체가 불가능**합니다.
**올바른 구성** — 처음부터 고객 관리형 키를 씁니다. 리전 단위 EBS 기본 암호화를 고객 관리형 키로 지정하고, RDS·EFS·Backup 볼트는 생성 시점에 키를 지정합니다. 키는 **테넌트마다**가 아니라 **신뢰 경계 단위**로 만들고 테넌트 구분은 암호화 컨텍스트로 합니다(키 월정액이 폭증합니다).
**탐지 방법**
```bash
aws ec2 get-ebs-encryption-by-default --region ap-northeast-2
aws ec2 describe-volumes --query 'Volumes[?Encrypted==`false`].[VolumeId,AvailabilityZone]' --output table
aws s3api get-bucket-encryption --bucket shopmini-uploads
```
Config 관리형 규칙 `ec2-ebs-encryption-by-default`, `rds-storage-encrypted`, `s3-default-encryption-kms`, `dynamodb-table-encrypted-kms`.
**본문** — 16.1절, 13.10절, 15.7절, 16.3절

### AP-12. "전용선이라서 / 내부망이라서" 평문 전송
**증상** — Direct Connect 구간에서 평문 프로토콜을 쓴다. RDS가 TLS를 "지원"만 하고 파라미터 그룹으로 강제하지 않는다. EFS를 기본 NFS로(`tls` 옵션 없이) 마운트한다. 버킷 정책에 `aws:SecureTransport` 조건이 없다.
**왜 위험한가** — **Direct Connect는 기본적으로 암호화되지 않습니다.** 전용선이라는 말은 "물리적으로 분리되었다"는 뜻이지 "암호화되었다"는 뜻이 아닙니다. MACsec을 붙여도 그것은 고객 라우터와 AWS DX 장비 사이 **점대점 링크 구간**만 보호하며, 그 앞뒤 구간은 그대로입니다. MACsec을 종단 간 암호화로 오해하는 것이 이 안티패턴의 핵심입니다. RDS TLS도 마찬가지로 "지원"과 "강제"는 다릅니다 — 클라이언트 하나가 평문으로 붙어도 아무도 모릅니다.
**올바른 구성** — 순서는 ① **애플리케이션 계층 TLS**(MACsec 유무와 무관하게) ② MACsec(링크 구간 보조) ③ DX 위 IPsec입니다. RDS는 파라미터 그룹으로 TLS를 강제하고, 클라이언트는 `--ssl-mode=REQUIRED`가 아니라 **`VERIFY_IDENTITY`** + RDS 루트 CA 번들로 서버 신원까지 검증합니다. EFS는 `-o tls,iam,accesspoint=...`로 마운트합니다.
**탐지 방법**
```bash
aws directconnect describe-connections \
  --query 'connections[].[connectionId,location,encryptionMode]' --output table
aws rds describe-db-parameters --db-parameter-group-name shopmini-mysql8 \
  --query 'Parameters[?ParameterName==`require_secure_transport`]'
```
Config 관리형 규칙 `s3-bucket-ssl-requests-only`, `efs-encrypted-check`, `alb-http-to-https-redirection-check`.
**본문** — 21.2절, 16.2절, 16.4절, 13.2절

### AP-13. 생성 시 암호화 누락 — 되돌릴 수 없는 구성
**증상** — RDS 인스턴스의 `StorageEncrypted`가 `false`다. EFS 파일 시스템이 암호화 없이 만들어져 있다. "암호화는 나중에 켜자"는 티켓이 열려 있다.
**왜 위험한가** — **RDS와 EFS는 생성 후 암호화를 켤 수 없습니다.** 나중이 없습니다. 되돌리려면 스냅샷 생성 → 암호화 복사 → 복원 → 엔드포인트 변경, 또는 새 파일 시스템 + DataSync 복사가 필요하고 다운타임이 따라옵니다. 규모가 커진 뒤에 이 사실을 발견하면 "비용이 커서 미룬다"가 되고, 그 상태로 규제 심사를 맞게 됩니다. 볼륨을 암호화로 전환한 뒤 **평문 원본 스냅샷을 남겨 두는 것**도 같은 범주의 실패입니다 — 암호화한 의미가 사라집니다.
**올바른 구성** — 생성 시점에 `--storage-encrypted`(RDS), `--encrypted`(EFS)를 붙이고, 리전 단위 EBS 기본 암호화를 켭니다. 보안 파라미터를 IaC 변수로 노출하지 말고 **코드에 상수로 고정**합니다 — 노출하면 어느 환경에선가 `false`가 되고 잊힙니다. 전환 후에는 원본 스냅샷·볼륨·AMI를 검증 후 삭제합니다.
**탐지 방법**
```bash
aws rds describe-db-instances \
  --query 'DBInstances[?StorageEncrypted==`false`].[DBInstanceIdentifier,Engine]' --output table
aws efs describe-file-systems --query 'FileSystems[?Encrypted==`false`].FileSystemId'
```
Config 관리형 규칙 `rds-storage-encrypted`, `rds-snapshot-encrypted`, `efs-encrypted-check`. 예방 층으로는 미암호화 생성을 막는 SCP를 걸되, `Bool: false` 문장만으로는 **파라미터를 아예 보내지 않은 요청**이 통과하므로 `Null` 문장을 함께 넣습니다.
**본문** — 16.2절, 16.4절, 16.1절, 28.6절

## B-3. S3·스토리지 (5)

### AP-14. 계정 수준 퍼블릭 액세스 차단 미적용
**증상** — `s3control get-public-access-block`이 오류를 내거나 네 플래그 중 일부만 `true`다. 캠페인·배포를 위해 버킷의 BPA를 "잠깐" 껐다. 공개 자산과 사용자 데이터가 한 버킷에 있다.
**왜 위험한가** — 버킷 수준 BPA만 켜면 **새 버킷을 만드는 사람 수만큼 사고 확률이 곱해집니다.** 네 플래그 중 `Block*` 두 개만 켜면 **이미 존재하는** 퍼블릭 ACL·정책은 그대로 살아 있습니다. 임시 해제는 되돌려 놓는 것을 잊게 되어 있고, 그 사이 버킷 전체가 인터넷에 노출됩니다. 공개 자산과 데이터가 같은 버킷에 있으면 `/*` 정책 한 줄로 전부 열립니다.
**올바른 구성** — **계정 수준**에서 네 플래그를 모두 켜고, 해제 액션을 SCP로 잠급니다. 공개 배포가 필요하면 BPA를 끄는 것이 아니라 **CloudFront + OAC**로 해결하고 버킷은 닫아 둡니다. 공개 자산 버킷(`shopmini-assets`)과 데이터 버킷(`shopmini-uploads`)을 분리하고, 가능하면 계정까지 나눕니다.
**탐지 방법**
```bash
aws s3control get-public-access-block --account-id 111122223333
for b in $(aws s3api list-buckets --query 'Buckets[].Name' --output text); do
  echo "== $b"; aws s3api get-public-access-block --bucket "$b" 2>&1 | head -8
done
```
Config 관리형 규칙 `s3-account-level-public-access-blocks-periodic`, `s3-bucket-public-read-prohibited`, `s3-bucket-public-write-prohibited`. Security Hub의 S3 계열 컨트롤 중 "계정·버킷 수준 퍼블릭 액세스 차단" 성격의 항목. CloudTrail에서는 퍼블릭 액세스 차단 설정을 변경·삭제하는 S3 제어 API 호출에 알람을 겁니다.
**본문** — 15.2절, 3.4절, 15.4절

### AP-15. 버전 관리·객체 잠금 없는 버킷
**증상** — `get-bucket-versioning` 출력이 비어 있다. 버전 관리는 켰는데 `s3:DeleteObjectVersion`과 `s3:PutLifecycleConfiguration`이 넓게 허용되어 있다. 객체 잠금이 없다.
**왜 위험한가** — 버전 관리가 없으면 덮어쓰기와 삭제가 **되돌릴 수 없는 조작**이 됩니다. 랜섬웨어 시나리오에서 공격자는 파일을 암호화해 덮어쓴 뒤 원본 버전을 지웁니다. 버전 관리만 켜고 삭제 권한을 잠그지 않으면 `DeleteObjectVersion`으로 전부 지워지고, 삭제 권한만 잠그고 수명 주기 권한을 놔두면 "비현행 버전 1일 후 영구 삭제" 규칙 **한 줄**로 무력화됩니다. 내구성(durability)은 백업이 아닙니다 — 11개의 9은 삭제·덮어쓰기를 막아 주지 않습니다.
**올바른 구성** — 버전 관리 + **객체 잠금** + 삭제·수명 주기 권한의 명시적 `Deny`를 세트로 겁니다. 컴플라이언스 모드는 루트도 AWS도 풀 수 없으므로 개발 계정에서 짧은 값으로 검증 → 거버넌스 모드 → 필요한 프리픽스만 승격의 순서를 지킵니다. MFA Delete는 자동화가 불가능하고 루트 자격 증명을 상시 요구하므로 최고 등급 버킷에만 조합의 한 층으로 씁니다.
**탐지 방법**
```bash
aws s3api get-bucket-versioning --bucket shopmini-uploads
aws s3api get-object-lock-configuration --bucket shopmini-uploads
```
Config 관리형 규칙 `s3-bucket-versioning-enabled`. CloudTrail 이벤트 `PutBucketVersioning`·`PutBucketLifecycle`에 변경 알람, 데이터 이벤트의 `DeleteObjectVersion` 급증에 알람.
**본문** — 15.8절, 15.9절, 17.5절, 2.3절

### AP-16. 퍼블릭 스냅샷·AMI
**증상** — `describe-snapshots --restorable-by-user-ids all`에 우리 스냅샷이 나온다. AMI의 `Public`이 `true`다. "테스트로 잠깐 공개했다"는 기록이 있다.
**왜 위험한가** — 스냅샷·AMI 공개는 **모든 통제를 우회한 데이터 복제**이고, 복사된 사본은 **회수가 불가능**합니다. 더 나쁜 것은 **우리 로그에 흔적이 남지 않는다는 점**입니다 — 다른 계정이 우리 공개 스냅샷을 복사하는 행위는 그쪽 계정의 사건이지 우리 계정의 사건이 아닙니다. 이미지 안에 구워진 자격 증명(AP-09)이 함께 나갑니다. 스냅샷 공유 대화상자에서 "퍼블릭"을 고르는 한 번의 클릭이 발생 경로입니다.
**올바른 구성** — 공유가 필요하면 **계정 ID를 명시**해 공유하고, 고객 관리형 키로 암호화합니다(AWS 관리형 키로 암호화된 것은 애초에 공유가 불가능합니다 — AP-11). 계정 수준에서 스냅샷·이미지의 퍼블릭 공유를 차단하는 블록 설정을 켭니다. 이미 공개되었다면 해제만으로 끝내지 말고 **이미지 안의 모든 시크릿을 순환**시킵니다. AMI 등록 해제 시 스냅샷도 함께 정리합니다.
**탐지 방법**
```bash
aws ec2 describe-snapshots --owner-ids 111122223333 --restorable-by-user-ids all \
  --query 'Snapshots[].[SnapshotId,StartTime,Description]' --output table
aws ec2 describe-images --owners 111122223333 --filters Name=is-public,Values=true \
  --query 'Images[].[ImageId,Name]' --output table
```
Config 관리형 규칙 `ebs-snapshot-public-restorable-check`, `rds-snapshots-public-prohibited`. CloudTrail 이벤트 `ModifySnapshotAttribute`·`ModifyImageAttribute`에 즉시 알람 + SSM Automation 자동 교정.
**본문** — 16.7절, 3.4절, 3.5절

### AP-17. 운영 계정 안에만 있는 백업
**증상** — 백업 볼트가 운영 계정(`111122223333`)에 있고 복사본이 없다. 볼트 잠금이 없거나 거버넌스 모드다. 백업이 운영 계정의 KMS 키로 암호화되어 있다.
**왜 위험한가** — 공격자는 데이터와 백업을 **함께** 지웁니다. 운영 계정 관리자 권한을 잡은 순간 볼트도 그 권한 안에 있습니다. 거버넌스 모드 잠금은 관리자 권한으로 해제할 수 있으므로 방어선이 아닙니다. 리전을 나눈 것으로 격리했다고 보는 것도 오해입니다 — **리전은 권한 경계가 아니며** 같은 자격 증명이 두 리전 모두를 지웁니다. 백업을 운영 계정 키로 암호화했다면 `ScheduleKeyDeletion` 하나로 백업까지 동반 사망합니다(AP-10).
**올바른 구성** — 목적지 볼트를 **별도 계정**(백업/로그 아카이브 계정)에 두고 **컴플라이언스 모드**로 잠급니다. 백업 계정이 소유한 키로 암호화합니다. 백업 대상은 ARN 개별 등록이 아니라 **태그 조건 기반 선택**으로 하고 태그를 강제합니다(개별 등록은 신규 리소스를 영원히 누락시킵니다). 볼트 접근 정책의 예외 ARN은 적용 전에 `assume-role`로 실제 검증하고, 예외 이름 패턴에 대한 `iam:CreateRole` 계열도 함께 `Deny`합니다 — 그러지 않으면 공격자가 같은 이름의 역할을 만들어 통과합니다.
**탐지 방법**
```bash
aws backup list-backup-vaults --query 'BackupVaultList[].[BackupVaultName,NumberOfRecoveryPoints]' --output table
aws backup describe-backup-vault --backup-vault-name shopmini-prod-vault
```
CloudTrail 이벤트 `DeleteBackupVault`·`DeleteRecoveryPoint`·`PutBackupVaultAccessPolicy`에 알람. **대시보드의 초록색은 복원 가능성의 증거가 아닙니다** — 분기 1회 실제 복원 훈련의 기록이 진짜 탐지 수단입니다(AP-33과 같은 착시).
**본문** — 17.4절, 17.5절, 17.2절, 2.3절

### AP-18. 과대 권한으로 발급한 사전 서명 URL
**증상** — 사전 서명 URL을 관리자 역할·배포 역할 세션으로 발급한다. `ExpiresIn`이 시간·일 단위다. 발급 로직이 애플리케이션의 범용 역할에 들어 있다.
**왜 위험한가** — 사전 서명 URL은 **서명자의 권한을 그대로 상속**하고 **취소할 수 없습니다.** URL 문자열 자체가 인증 수단이므로 그것을 가진 누구든 객체에 접근합니다. 관리자 자격으로 서명하면 받은 사람이 사실상 서명자와 동등한 접근을 얻습니다. 역할 세션으로 서명하면서 만료를 길게 주면 세션 만료 시점에 URL이 죽어 **간헐적 실패**로 나타나 원인 추적이 어렵습니다. CloudFront 서명 URL도 같은 구조이며, 오리진 버킷의 OAC를 빠뜨리면 서명 자체가 무의미해집니다.
**올바른 구성** — 발급 **전용 최소 권한 역할**을 만들어 그 세션으로만 서명하고, 만료는 분 단위로 둡니다. 세션 수명 안쪽으로 만료를 설정합니다. 지속적인 공개 배포는 CloudFront + OAC로, 서드파티 상시 접근은 역할 수임으로 해결합니다. 로그의 쿼리 문자열을 마스킹합니다.
**탐지 방법** — 사전 서명 URL의 **발급**은 API 호출이 아니므로 로그에 남지 않습니다. 남는 것은 **사용 시점**입니다. S3 데이터 이벤트에서 `GetObject` 레코드의 `userIdentity`가 관리자·배포 역할인데 `sourceIPAddress`가 외부 대역인 건을 찾습니다. 근본 탐지는 코드 리뷰 — 서명 호출이 어떤 역할 세션에서 일어나는지 확인합니다.
**본문** — 15.6절, 23.7절, 15.2절

### AP-19. `0.0.0.0/0`에 SSH·RDP 개방 (배스천 포함)
**증상** — 보안 그룹 인바운드에 22 또는 3389이 `0.0.0.0/0`으로 열려 있다. 배스천 호스트가 인터넷에 노출되어 있고 "출발지 IP를 제한했으니 안전하다"고 설명한다. 문제 절단용으로 전 포트를 열어 두고 방치했다.
**왜 위험한가** — 인터넷 스캐너는 신규 개방 포트를 **수 분 내에** 발견합니다. 그다음은 자격 증명 공격이고, 성공하면 그 인스턴스의 **IAM 역할 자격 증명**이 넘어갑니다(AP-25와 결합하면 즉시). 사내 IP로 제한한 배스천도 근본 해결이 아닙니다 — 사내 PC 한 대가 침해되면 관리 인터페이스 전체에 도달합니다. 사이트 간 VPN으로 관리 접근을 허용하는 것은 "사내망 전체 = 관리 권한"을 뜻합니다.
**올바른 구성** — **SSM Session Manager**로 전환하고 인바운드 규칙을 **0개**로 만듭니다. 배스천이 불가피하면 출발지를 CIDR이 아니라 **배스천 SG 참조**로 겁니다. Session Manager를 켰다면 **세션 로깅**(S3 + CloudWatch Logs + KMS)을 반드시 함께 구성합니다 — 로깅 없는 Session Manager는 배스천보다 감사가 약합니다. `ssm-user`에 무제한 sudo를 주지 말고 `runAsDefaultUser`로 전용 계정을 씁니다.
**탐지 방법**
```bash
aws ec2 describe-security-groups \
  --filters Name=ip-permission.cidr,Values=0.0.0.0/0 \
  --query 'SecurityGroups[].[GroupId,GroupName,VpcId]' --output table
```
Config 관리형 규칙 `restricted-common-ports`, `vpc-sg-open-only-to-authorized-ports`, `nacl-no-unrestricted-ssh-rdp`. CloudTrail 이벤트 `AuthorizeSecurityGroupIngress`에 `0.0.0.0/0` 조건 알람.
**본문** — 19.3절, 21.5절, 21.6절

### AP-20. 라우팅이 IGW로 걸린 "프라이빗" 서브넷
**증상** — 서브넷 이름은 `*-private`인데 연결된 라우팅 테이블에 `0.0.0.0/0 → igw-*` 경로가 있다. **메인 라우팅 테이블**에 IGW 경로가 들어 있다. 프라이빗 인스턴스에 EIP가 붙어 있다.
**왜 위험한가** — 메인 라우팅 테이블에 IGW 경로를 넣으면 **명시적으로 연결되지 않은 신규 서브넷이 전부 자동으로 퍼블릭**이 됩니다. 이름으로 판단하는 순간 통제는 사라집니다 — 이름은 `private`인데 실제로는 공인 IP를 가진 인스턴스가 인터넷에서 직접 도달 가능한 상태가 되고, 보통 두 달 뒤 GuardDuty 결과로 발견됩니다. 프라이빗 인스턴스에 임시로 붙인 EIP를 떼지 않으면 라우팅과 결합해 완전한 양방향 노출이 됩니다. 위협 모델링에서 "프라이빗 서브넷이니까"를 검증 없이 전제하는 것도 같은 실패입니다.
**올바른 구성** — 퍼블릭 전용 라우팅 테이블을 **분리**하고 메인 테이블에는 로컬 경로만 둡니다. 판단 기준을 이름이 아니라 **라우팅**으로 바꾸고 스크립트로 상시 점검합니다. 서브넷의 자동 공인 IP 할당을 끕니다.
**탐지 방법**
```bash
aws ec2 describe-route-tables \
  --filters Name=route.gateway-id,Values=igw-* \
  --query 'RouteTables[].[RouteTableId,Associations[].SubnetId,Tags[?Key==`Name`].Value|[0]]' \
  --output json
```
Config 관리형 규칙 `no-unrestricted-route-to-igw`, `subnet-auto-assign-public-ip-disabled`, `ec2-instance-no-public-ip`. CloudTrail 이벤트 `CreateRoute`·`ReplaceRoute`·`AttachInternetGateway`.
**본문** — 18.4절, 3.2절, 18.3절

### AP-21. 기본 보안 그룹 사용
**증상** — ENI에 `default` 보안 그룹이 붙어 있다. 기본 SG의 인바운드 규칙이 "자기 자신 참조, 모든 트래픽"으로 남아 있다. SG 인바운드 소스가 서브넷 CIDR로 지정되어 있다.
**왜 위험한가** — 기본 SG의 기본 규칙은 **같은 SG에 속한 모든 리소스 간 전 포트 허용**입니다. 여러 워크로드가 여기에 얹히면 하나의 거대한 평면 네트워크가 되고, 한 인스턴스가 침해되면 측면 이동에 아무 저항이 없습니다. SG 소스를 서브넷 CIDR로 지정하는 것도 같은 결과입니다 — 같은 서브넷에 나중에 생기는 워크로드가 **자동으로 허용**됩니다.
**올바른 구성** — 기본 SG의 **규칙을 전부 비우고**, 붙어 있는 ENI를 찾아 전용 SG로 교체합니다. 소스는 CIDR이 아니라 **SG 참조**로 씁니다(CIDR은 VPC 밖 출발지에만). ALB SG → 앱 SG → DB SG로 이어지는 참조 체인을 만들면 계층 경계가 규칙 자체로 표현됩니다.
**탐지 방법**
```bash
aws ec2 describe-security-groups --group-names default \
  --query 'SecurityGroups[].[GroupId,VpcId,length(IpPermissions),length(IpPermissionsEgress)]' \
  --output table
aws ec2 describe-network-interfaces \
  --filters Name=group-name,Values=default \
  --query 'NetworkInterfaces[].[NetworkInterfaceId,Description]' --output table
```
Config 관리형 규칙 `vpc-default-security-group-closed`, `ec2-security-group-attached-to-eni`.
**본문** — 19.3절, 19.2절, 19.7절

### AP-22. 아웃바운드 전체 허용
**증상** — 모든 SG의 이그레스가 기본값(`0.0.0.0/0`, 전 포트)이다. 이그레스를 "tcp/443 전체 허용"으로 좁힌 것을 통제라고 부른다. 데이터 계층 서브넷에 NAT 경로가 있다.
**왜 위험한가** — 이그레스는 **침해 이후를 결정하는 층**입니다. 아웃바운드가 열려 있으면 C2 통신과 데이터 반출이 정상 트래픽처럼 나갑니다. 공급망 공격(악성 `postinstall`, 오염된 이미지)은 거의 전부 아웃바운드에 의존합니다. `tcp/443 전체 허용`은 통제가 있다는 착각만 남기는데, 목적지가 제한되지 않으면 443은 반출 경로로 완벽합니다. NAT 게이트웨이에는 보안 그룹을 붙일 수 없으므로 "NAT가 막아 준다"도 성립하지 않습니다.
**올바른 구성** — 기본 이그레스 규칙을 제거하고 필요한 것만 추가합니다. **데이터 티어는 인터넷 경로 자체를 없앱니다**(VPC 엔드포인트로 대체). 목적지 제한은 Network Firewall 또는 프록시로, DNS 축은 DNS Firewall + Resolver 쿼리 로깅으로 덮습니다 — 그러지 않으면 격리 서브넷에서도 DNS 터널링으로 나갑니다. 조이는 순서가 중요합니다: **먼저 깨지는 목록을 만들어** 허용 목록에 넣고 조입니다(패치·이미지 pull·NTP가 먼저 깨집니다).
**탐지 방법**
```bash
aws ec2 describe-security-groups \
  --query 'SecurityGroups[?IpPermissionsEgress[?IpRanges[?CidrIp==`0.0.0.0/0`]]].[GroupId,GroupName]' \
  --output table
```
VPC 플로우 로그에서 데이터 티어 → 외부 대역의 `ACCEPT` 레코드를 질의합니다. CloudTrail 이벤트 `AuthorizeSecurityGroupEgress`·`RevokeSecurityGroupEgress`.
**본문** — 19.6절, 20.3절, 27.4절

### AP-23. IPv6 규칙 누락
**증상** — 보안 그룹·NACL 점검을 IPv4만 했다. `0.0.0.0/0` 규칙은 지웠는데 `::/0` 규칙이 남아 있다. 필요 없는 계층에까지 IPv6 CIDR을 붙였다.
**왜 위험한가** — IPv4 규칙만 지우고 "조치 완료"로 보고하면 **`::/0` 규칙이 그 통제를 그대로 우회**합니다. 점검 스크립트가 `ip-permission.cidr` 필터만 쓰면 IPv6 규칙은 출력에 나오지 않으므로 **있는데 안 보이는** 상태가 됩니다. 필요 없는 계층에 IPv6 CIDR을 할당하면 모든 인스턴스가 잠재적 공인 주소를 갖게 되어, NAT 뒤에 있다는 전제가 무너집니다.
**올바른 구성** — 모든 SG·NACL 점검과 조치를 **IPv4·IPv6 쌍**으로 처리합니다. 스크립트는 `IpRanges`와 `Ipv6Ranges`를 모두 조회합니다. IPv6 CIDR은 실제로 필요한 계층에만 할당합니다.
**탐지 방법**
```bash
aws ec2 describe-security-groups \
  --filters Name=ip-permission.ipv6-cidr,Values=::/0 \
  --query 'SecurityGroups[].[GroupId,GroupName]' --output table
aws ec2 describe-security-groups \
  --query 'SecurityGroups[].IpPermissions[].Ipv6Ranges[].CidrIpv6' --output text
```
Config 규칙으로는 포트 제한 계열 규칙이 IPv6도 함께 평가하는지 확인한 뒤 커버리지를 판단합니다.
**본문** — 18.7절, 19.3절

### AP-24. NACL 임시 포트 함정
**증상** — NACL에 요청 방향 규칙만 있고 응답용 임시 포트 규칙이 없다. 임시 포트 범위를 좁게(예: 32768–60999) 잡았다. 새로 만든 NACL을 규칙 없이 서브넷에 바로 연결했다. 규칙 번호를 100부터 1씩 촘촘히 채웠다.
**왜 위험한가** — NACL은 **상태 비저장**입니다. 요청을 허용해도 응답은 별도 규칙이 없으면 차단되어 **규칙은 맞는데 타임아웃**이 납니다. 임시 포트 범위를 좁게 잡으면 클라이언트 OS에 따라 **간헐적으로만** 실패해 원인 추적이 대단히 어렵습니다. 새 NACL은 생성 시 양방향 전부 거부이므로 규칙 없이 연결하면 그 서브넷이 즉시 장애가 납니다. 번호를 촘촘히 채우면 사고 당일 최우선 `Deny`를 끼워 넣을 자리가 없습니다.
**올바른 구성** — 응답용 **1024–65535** 규칙을 양방향에 두고, 세밀한 통제는 상태 저장인 보안 그룹에서 합니다. NACL은 "서브넷 전체에 걸리는 굵은 차단"에만 씁니다. 규칙을 모두 넣은 뒤 `replace-network-acl-association`으로 연결하고, 번호는 **1–99를 비상용으로 예약**하고 100 단위 간격으로 채웁니다.
**탐지 방법**
```bash
aws ec2 describe-network-acls \
  --query 'NetworkAcls[].[NetworkAclId,Entries[?Egress==`false`].[RuleNumber,Protocol,PortRange,CidrBlock,RuleAction]]' \
  --output json
```
CloudTrail 이벤트 `CreateNetworkAclEntry`·`ReplaceNetworkAclEntry`·`ReplaceNetworkAclAssociation`. 증상 자체는 VPC 플로우 로그의 `REJECT` 레코드로 가장 빨리 확인됩니다.
**본문** — 19.4절, 19.1절

## B-5. 컴퓨트·컨테이너 (5)

### AP-25. IMDSv1 방치
**증상** — `describe-instances`의 `HttpTokens`가 `optional`이다. 메타데이터 홉 제한이 2 이상인데 파드에서 IMDS 접근을 막지 않았다. "레거시 호환 때문에" 켜 두었다는 설명이 있다.
**왜 위험한가** — IMDSv1은 **토큰 없이 GET 한 번으로** 인스턴스 역할의 임시 자격 증명을 반환합니다. 애플리케이션의 SSRF 취약점 하나면 공격자가 그 자격 증명을 가져갑니다. 결정적으로 **그 단계는 CloudTrail에 남지 않습니다** — 로그에는 자격 증명이 이미 유출된 이후의 정상적인 API 호출만 보입니다. User Data의 평문 시크릿(AP-08)도 같은 경로로 나갑니다. 홉 제한 2로 두고 파드 차단을 안 하면 파드가 **노드 역할**을 도용합니다.
**올바른 구성** — `HttpTokens=required`(IMDSv2 강제) + **홉 제한 1**(컨테이너 호스트는 태스크 역할·IRSA 전환이 끝날 때까지만 한시적 2). 전환 전에 `MetadataNoToken` 지표가 0인지 확인합니다 — 확인 없이 바꾸면 구버전 SDK와 자체 스크립트가 즉시 실패합니다. EKS는 Pod Identity 또는 IRSA를 쓰고 파드에서 `169.254.169.254`를 네트워크 정책으로 차단합니다. 계정 수준 기본값(`modify-instance-metadata-defaults`)으로 신규 인스턴스를 덮습니다.
**탐지 방법**
```bash
aws ec2 describe-instances \
  --filters Name=metadata-options.http-tokens,Values=optional \
  --query 'Reservations[].Instances[].[InstanceId,MetadataOptions.HttpPutResponseHopLimit]' \
  --output table
```
Config 관리형 규칙 `ec2-imdsv2-check`. CloudTrail 이벤트 `ModifyInstanceMetadataOptions`로 되돌림을 감시합니다.
**본문** — 8.3절, 3.4절, 24.4절

### AP-26. ECS 태스크 역할·실행 역할 혼동
**증상** — 태스크 정의의 `executionRoleArn`에 애플리케이션 권한(S3·DynamoDB 접근 등)이 들어 있다. 여러 태스크 정의가 같은 실행 역할을 공유한다. 반대로 `secrets` 필드 주입 권한을 **태스크 역할**에 넣어 태스크가 기동조차 하지 않는다.
**왜 위험한가** — 실행 역할은 **ECS 에이전트가 컨테이너를 띄우기 위해** 쓰는 역할입니다(이미지 pull, 로그 전송, `secrets` 필드 해석). 여기에 앱 권한을 넣으면 **같은 실행 역할을 쓰는 모든 태스크가 그 권한을 얻습니다.** 태스크 A의 취약점이 태스크 B의 데이터로 이어지고, 최소 권한이 태스크 경계에서 무너집니다. 반대 방향의 혼동은 장애로 즉시 드러나므로 덜 위험하지만, 그때 "권한이 부족하다"며 양쪽에 다 붙이는 것이 최악의 수습입니다.
**올바른 구성** — **태스크 정의마다 전용 태스크 역할**을 만들고 앱 권한은 거기에만 넣습니다. 실행 역할은 이미지 pull·로그·시크릿 해석에 필요한 최소한으로 고정하고 공유하되 절대 넓히지 않습니다. `secrets` 필드 권한은 **실행 역할** 쪽입니다.
**탐지 방법**
```bash
aws ecs describe-task-definition --task-definition shopmini-app \
  --query 'taskDefinition.[family,taskRoleArn,executionRoleArn]' --output table
aws ecs list-task-definitions --query 'taskDefinitionArns' --output text
```
실행 역할 ARN이 여러 태스크 정의에서 반복되는지 세어 보고, 그 역할에 붙은 정책에 앱 액션이 있는지 확인합니다.
**본문** — 24.3절, 8.4절, 11.6절

### AP-27. EKS API 서버 퍼블릭 노출
**증상** — `resourcesVpcConfig.endpointPublicAccess`가 `true`이고 `publicAccessCidrs`가 `0.0.0.0/0`이다(클러스터 생성 기본값). IRSA 신뢰 정책의 `sub` 조건이 `system:serviceaccount:*:*`다. 네트워크 정책이 몇 개만 있다. `aws-auth` ConfigMap을 직접 편집한다.
**왜 위험한가** — 퍼블릭 엔드포인트 + `0.0.0.0/0`은 **IAM 자격 증명 하나가 유출되면 인터넷 어디서든 `kubectl`이 가능**하다는 뜻입니다. IRSA `sub`를 와일드카드로 두면 클러스터 안 **아무 네임스페이스의 아무 서비스 계정**이 그 역할을 맡습니다. 쿠버네티스 네트워크 정책은 **정책이 없는 네임스페이스를 전부 허용**으로 두므로 몇 개만 만들고 격리됐다고 판단하면 실제로는 평면 네트워크입니다. `aws-auth` 직접 편집은 오타 한 줄로 전 관리자가 잠깁니다.
**올바른 구성** — 엔드포인트를 **프라이빗 전용**으로 두거나 `publicAccessCidrs`를 운영 대역으로 제한합니다. IRSA 신뢰 정책의 `sub`를 네임스페이스·서비스 계정 이름까지 `StringEquals`로 고정합니다. 네임스페이스마다 `default-deny-all`을 먼저 배치하고 화이트리스트를 얹습니다. 접근 관리는 `aws-auth` 대신 **액세스 항목(AWS API)** 기반으로 전환합니다. 파드의 IMDS 접근은 차단합니다(AP-25).
**탐지 방법**
```bash
aws eks describe-cluster --name shopmini-prod \
  --query 'cluster.resourcesVpcConfig.[endpointPublicAccess,endpointPrivateAccess,publicAccessCidrs]' \
  --output json
```
CloudTrail 이벤트 `UpdateClusterConfig`로 엔드포인트 설정 변경을 감시합니다. IRSA 신뢰 정책은 `aws iam get-role`로 받아 `sub` 조건에 `*`가 있는지 확인합니다.
**본문** — 24.4절, 8.8절, 8.3절

### AP-28. Lambda 공용 역할
**증상** — `list-functions` 출력에서 수십 개 함수가 같은 실행 역할 ARN을 쓴다. 함수 URL이 `AuthType: NONE`으로 열려 있다. 함수마다 역할을 즉석에서 만들어 수십 개가 검토 없이 쌓여 있다.
**왜 위험한가** — 역할 하나를 40개 함수가 공유하면 그 역할의 권한은 **모든 함수 권한의 합집합**이 됩니다. 함수 하나에서 RCE가 나면 40개 함수 몫의 권한이 한꺼번에 넘어가고, 최소 권한은 이름만 남습니다. 반대로 역할을 즉석에서 만들어 쌓는 것도 문제입니다 — 인벤토리가 무너져 재검증 대상에서 빠집니다(AP-06). `AuthType: NONE` 함수 URL은 인터넷 전체가 호출자가 되어 비용과 데이터 양쪽에서 노출됩니다.
**올바른 구성** — **함수당 실행 역할 1개**를 원칙으로 하고 역할 생성을 IaC로 강제합니다. 권한 경계로 상한을 겁니다. 함수 URL은 `AWS_IAM`으로 보호하거나 API Gateway 뒤에 둡니다. 환경 변수에 비밀을 두지 않습니다(AP-08).
**탐지 방법**
```bash
aws lambda list-functions --query 'Functions[].Role' --output text | tr '\t' '\n' | sort | uniq -c | sort -rn
aws lambda list-function-url-configs --query 'FunctionUrlConfigs[?AuthType==`NONE`].[FunctionArn]' --output table
```
같은 역할이 2회 이상 나오는 줄이 전부 점검 대상입니다.
**본문** — 24.6절, 8.4절, 2.4절

### AP-29. 컴플라이언스 체크박스로 켜 둔 WAF와 우회 가능한 오리진
**증상** — WAF 웹 ACL이 붙어 있지만 관리형 규칙을 기본값 그대로 두고 커스텀 규칙이 하나도 없다. WAF 로그를 켜지 않았거나 아무도 보지 않는다. ALB의 DNS 이름이 인터넷에서 직접 접근 가능하다. 오탐이 나서 규칙 그룹 전체를 비활성화했다.
**왜 위험한가** — 켜져 있기만 한 "깜빡이는 상자" 상태입니다 — **감사도 통과하고 공격도 통과합니다.** 튜닝되지 않은 WAF는 애플리케이션 고유 로직 공격에 무방비이고, 로그를 보지 않으면 몇 주간의 크리덴셜 스터핑을 침해 이후에 발견하게 됩니다. 더 근본적인 문제는 우회입니다 — ALB DNS 이름은 인증서 투명성 로그·서브도메인 열거·과거 DNS 레코드에서 노출되므로, 공격자가 CloudFront를 건너뛰고 오리진을 직접 때리면 **WAF·Shield·캐시를 전부 통과**합니다. 오리진 은닉은 "안 알려주기"로 달성되지 않습니다.
**올바른 구성** — 두 겹입니다. ① **네트워크** — ALB 보안 그룹 인바운드를 CloudFront 관리형 접두사 목록으로 제한합니다. ② **애플리케이션** — 다른 사람의 CloudFront 배포도 같은 IP 대역에서 오므로, CloudFront가 오리진에 붙이는 **커스텀 헤더를 리전 웹 ACL에서 검증**합니다(우선순위 0). 관리형 규칙은 Count로 시작해 단계적으로 Block으로 올리고, 오탐은 그룹 전체 비활성화가 아니라 **규칙 단위 재정의**나 범위 축소 조건으로 처리합니다. WAF 로그는 필수이며 민감 헤더는 마스킹합니다.
**탐지 방법**
```bash
aws wafv2 list-web-acls --scope REGIONAL --region ap-northeast-2
aws wafv2 get-logging-configuration --resource-arn <WEB_ACL_ARN> --region ap-northeast-2
aws elbv2 describe-load-balancers \
  --query 'LoadBalancers[?Scheme==`internet-facing`].[LoadBalancerName,DNSName]' --output table
```
오리진 우회 여부는 **ALB DNS로 직접 요청을 보내 응답이 오는지** 확인하는 것이 가장 확실합니다. `BlockedRequests` 지표에 상·하한 알람을 겁니다 — 갑자기 0이 되는 것도 신호입니다.
**본문** — 23.9절, 4.5절, 23.8절, 26.2절

## B-6. 로깅·탐지 (4)

### AP-30. 운영 계정에만 있는 CloudTrail
**증상** — 트레일의 `S3BucketName`이 그 계정 안의 버킷이다. `IsMultiRegionTrail`이 `false`다. `get-trail-status`의 `IsLogging`이 `false`인데 아무도 모른다. 조직 트레일이 없고 계정마다 각자 만들었다.
**왜 위험한가** — 로그가 그 계정 안에 있으면 **계정 관리자 권한 하나로 로그가 지워집니다.** 침해 조사에서 가장 먼저 없어지는 것이 이것입니다. 단일 리전 트레일은 공격자가 다른 리전에서 벌인 활동을 **한 줄도** 남기지 않습니다 — 미사용 리전이야말로 크립토마이닝의 착륙장입니다. `create-trail`만 하고 `start-logging`을 하지 않으면 트레일은 존재하지만 로그는 쌓이지 않습니다.
**올바른 구성** — **조직 트레일 + 다중 리전 + 로그 아카이브 계정(`777788889999`) 저장 + 객체 잠금**이 한 세트입니다. 트레일 버킷 정책에 `aws:SourceArn` 조건을 넣지 않으면 다른 계정이 우리 버킷을 로그 오염 채널로 쓸 수 있습니다. 저장(로그 계정)과 분석(보안 계정)을 분리합니다 — 분석 도구 침해가 곧 로그 침해가 되지 않게 합니다. CloudTrail은 약 15분 지연되므로 **차단은 SCP·IAM(예방)이 하고 CloudTrail은 증거를 맡습니다.**
**탐지 방법**
```bash
aws cloudtrail describe-trails \
  --query 'trailList[].[Name,IsMultiRegionTrail,IsOrganizationTrail,S3BucketName,HomeRegion]' \
  --output table
aws cloudtrail get-trail-status --name shopmini-org-trail --query '[IsLogging,LatestDeliveryTime]'
```
CloudTrail 이벤트 `StopLogging`·`DeleteTrail`·`UpdateTrail`에 **`us-east-1`에서** 알람을 겁니다(루트 로그인·글로벌 서비스 이벤트가 그쪽으로 배달됩니다). Config 규칙으로 다중 리전 트레일 활성화를 상시 평가합니다.
**본문** — 29.2절, 29.9절, 5.3절, 36.5절

### AP-31. 데이터 이벤트 미설정
**증상** — "CloudTrail을 켰으니 다 기록된다"고 알고 있다. `get-event-selectors` 출력에 데이터 이벤트가 없다. 반대로 `put-event-selectors`로 데이터 이벤트만 설정해 **관리 이벤트가 꺼졌다**. 비용이 커서 데이터 이벤트를 껐다.
**왜 위험한가** — 기본 트레일은 **관리 이벤트만** 기록합니다. `GetObject`·`PutObject`·`DeleteObject`는 **한 건도 남지 않습니다.** 유출 사고에서 "무엇이 얼마나 나갔는가"를 확정할 수 없다는 뜻이고, 규제 통지 국면에서는 **범위를 최대로 가정**해야 합니다. `put-event-selectors`는 선택기를 **덮어쓰므로** 데이터 이벤트만 넣으면 관리 이벤트 로깅이 조용히 꺼집니다. 전체 버킷에 켜면 비용이 급증해 "비싸서 껐다"로 귀결되는 것도 전형적인 실패 경로입니다.
**올바른 구성** — **기밀 등급 버킷만 선별**해 데이터 이벤트를 켭니다(데이터 분류가 선행되어야 하는 이유입니다). 선택기를 수정할 때는 관리 이벤트 선택기를 **항상 함께 포함**합니다. 플로우 로그만 믿지 말고 DNS 쿼리 로깅을 병행합니다 — C2 도메인 조회와 DNS 터널링은 플로우 로그에 보이지 않습니다. IMDS 트래픽(`169.254.169.254`)은 플로우 로그에 기록되지 않으므로 예방(AP-25)으로 덮습니다.
**탐지 방법**
```bash
aws cloudtrail get-event-selectors --trail-name shopmini-org-trail
aws cloudtrail get-trail --name shopmini-org-trail --query 'Trail.[Name,HasCustomEventSelectors]'
```
Config 관리형 규칙 `cloudtrail-s3-dataevents-enabled`. CloudTrail 이벤트 `PutEventSelectors`에 변경 알람.
**본문** — 15.11절, 29.2절, 29.5절, 5.3절

### AP-32. 아무도 안 보는 알람
**증상** — SNS 구독이 `PendingConfirmation`으로 남아 있다. 알람 구독이 개인 이메일 하나다. 15개 보안 알람이 전부 P1 온콜로 연결되어 있다. 오탐이 나서 알람을 껐다. 지표 필터에 `defaultValue`가 없고 알람이 `INSUFFICIENT_DATA`를 오간다.
**왜 위험한가** — 확인되지 않은 구독으로는 알림이 **아무 데도 도달하지 않습니다.** 설정은 완료로 보이고 통제는 존재하지 않습니다. 모든 알람을 P1으로 두면 3주 안에 채널 전체가 무시되고, 그 시점부터 탐지 계층은 비어 있는 것과 같습니다. 오탐이 났다고 알람을 끄면 **그 탐지 유형이 영구히 사라집니다.** `INSUFFICIENT_DATA`를 오가는 알람은 팀에게 "이 알람은 원래 저래"를 학습시킵니다. 로그 유입 알람에 `notBreaching`을 쓰면 파이프라인이 죽어도 `OK`로 남습니다.
**올바른 구성** — 구독 상태 점검을 구성 체크리스트에 넣고 분기마다 실제 발송 테스트를 합니다. 수신은 **그룹 주소 + 채팅/온콜 2경로**로 이중화합니다. 오탐률을 기준으로 심각도를 재배치하고, 오탐은 끄는 대신 주체 제외·임계치 상향·복합 알람으로 처리합니다. 지표 필터에 `defaultValue=0`, 로그 유입 알람에 `breaching`을 지정합니다. IAM·콘솔 로그인 알람은 **`us-east-1`** 에 만듭니다. **튜닝이 먼저이고 자동화는 그다음입니다** — 알람 피로를 자동 대응으로 해결하려 하면 오탐이 사람의 피로가 아니라 서비스 장애가 됩니다.
**탐지 방법**
```bash
aws sns list-subscriptions-by-topic --topic-arn arn:aws:sns:ap-northeast-2:444455556666:shopmini-secops-high \
  --query 'Subscriptions[].[Protocol,Endpoint,SubscriptionArn]' --output table
aws cloudwatch describe-alarms --state-value INSUFFICIENT_DATA \
  --query 'MetricAlarms[].[AlarmName,StateUpdatedTimestamp]' --output table
```
`SubscriptionArn`이 `PendingConfirmation`인 줄이 전부 결함입니다.
**본문** — 30.9절, 30.1절, 30.3절, 30.2절

### AP-33. 스캔하지 않아 취약점 0으로 보이는 착시
**증상** — 취약점 대시보드의 어떤 계정이 0건인데 그 계정에 인스턴스가 있다. 지표가 비율만 있고 분모가 없다. SSM 미관리 인스턴스가 섞여 있는데 패치 준수율은 100%다. Trusted Advisor가 초록불이다. Config·Security Hub를 주 사용 리전에만 켰다.
**왜 위험한가** — **스캔하지 않은 계정은 항상 0건**이고, 그 0건은 대시보드에서 우수 사례로 보입니다. 이것은 지표가 리스크와 반대로 움직이는 상태이며, 투자 결정이 그 위에서 이뤄집니다. SSM 에이전트가 없는 인스턴스는 패치 대상 모수에 들어가지 않으므로 준수율 100%와 "절반이 미관리"가 동시에 성립합니다. Trusted Advisor는 플랜에 따라 **점검 자체가 실행되지 않으므로** 초록불이 근거가 되지 않습니다. 비율만 보고하면 통제를 끄고 범위를 좁혀 지표를 개선하는 경로가 열립니다.
**올바른 구성** — **모든 지표에 커버리지 분모를 병기**합니다("전체 인스턴스 1,240대 중 스캔 대상 1,190대(96%), 발견 취약점 N건"). Inspector 커버리지와 SSM 관리 상태를 패치 규칙보다 **먼저** 점검합니다. Config·Security Hub는 전 리전 활성화하고 미사용 리전은 SCP로 봉인합니다. 억제 규칙에는 사유·승인자·**만료일**을 필수로 하고 분기마다 전수 검토합니다. 보안 점수를 단독 KPI로 쓰지 말고 **비활성화된 컨트롤 수**를 함께 보고합니다.
**탐지 방법**
```bash
aws inspector2 list-coverage --query 'coveredResources[].[resourceType,resourceId,scanStatus.statusCode]' --output table
aws ssm describe-instance-information --query 'InstanceInformationList[].[InstanceId,PingStatus]' --output table
aws configservice describe-compliance-by-config-rule --query 'ComplianceByConfigRules[].[ConfigRuleName,Compliance.ComplianceType]' --output table
```
Config 관리형 규칙 `ec2-instance-managed-by-systems-manager`. EC2 인스턴스 수와 위 출력의 행 수를 **대조**하는 것이 이 항목의 핵심 점검입니다.
**본문** — 25.6절, 26.3절, 26.7절, 39.2절

## B-7. 파이프라인·공급망 (4)

### AP-34. CI/CD 파이프라인의 관리자 권한
**증상** — 배포 역할에 `AdministratorAccess` 또는 `iam:*`가 붙어 있다. 파이프라인 활동이 감사·알람 대상에서 빠져 있다. 빌드 단계와 배포 단계가 같은 자격 증명을 쓴다.
**왜 위험한가** — 파이프라인은 **조직에서 가장 강한 주체**입니다. 사람에게는 승인 절차가 있지만 파이프라인에는 없습니다. 배포 역할에 `iam:*`가 있으면 **자기보다 강한 역할을 만들어 맡을 수 있으므로** 최소 권한이라는 개념 자체가 성립하지 않습니다. 그 강한 주체의 활동이 감사 대상에서 빠져 있으면 이상 행위가 보이지 않습니다. 운영 계정에 개발자 관리자 권한을 상시 부여하는 것도 같은 구조의 문제이며, 그 상태에서는 콘솔 수동 변경(AP-38)이 구조적으로 불가피해집니다.
**올바른 구성** — 배포 역할에 **권한 경계**를 조건으로 걸고, 경계를 떼는 액션(`DeleteRolePermissionsBoundary` 등)을 명시적으로 `Deny`합니다. 빌드와 배포를 **다른 자격 증명**으로 분리합니다. 파이프라인 활동을 특권 사용자와 **동급으로** 로깅·알람합니다. 정상 경로는 자동으로 통과시키고 예외만 사람이 승인합니다 — 모든 배포에 수동 승인 게이트를 두면 게이트를 형식적으로 통과시키는 문화가 생겨 보안 수정까지 지연됩니다.
**탐지 방법**
```bash
aws iam list-attached-role-policies --role-name shopmini-deploy-prod
aws iam list-role-policies --role-name shopmini-deploy-prod
aws iam get-role --role-name shopmini-deploy-prod --query 'Role.PermissionsBoundary'
```
`PermissionsBoundary`가 비어 있고 `AdministratorAccess`가 붙어 있으면 확정입니다. CloudTrail에서 그 역할의 `AssumeRole`과 이후 API 호출을 특권 감사 대상에 넣습니다.
**본문** — 27.6절, 7.2절, 28.4절, 29.1절

### AP-35. 느슨한 GitHub OIDC 신뢰 조건
**증상** — OIDC 신뢰 정책에 `sub` 조건이 없다. `sub`가 `repo:ORG/*:*`나 `repo:ORG/REPO:*`로 되어 있다. 운영 배포를 `ref:refs/heads/main`으로만 제한했다. 또는 아예 CI 시크릿에 장기 액세스 키를 넣어 두었다.
**왜 위험한가** — `sub` 조건이 없으면 **전 세계 모든 GitHub 저장소**가 그 역할을 맡을 수 있습니다. 역할 ARN만 알면 됩니다. `repo:ORG/*:*`는 조직 안 아무 저장소, 아무 브랜치, **포크 PR**까지 통과시킵니다. `ref:refs/heads/main`으로만 제한하면 `main` 푸시 권한이 곧 운영 배포 권한이 되고 승인 게이트를 연동할 수 없습니다. 장기 액세스 키를 CI 시크릿에 넣는 것은 순환·폐기·오프보딩 대상에서 누락된 영구 키를 만드는 일입니다(AP-01).
**올바른 구성** — `aud`와 `sub`를 모두 `StringEquals`로 고정하고, `sub`에 **저장소와 환경**까지 넣습니다. 운영 배포는 브랜치가 아니라 `environment:production`으로 제한해 환경 승인자와 연동합니다.
```json
{
  "Effect": "Allow",
  "Principal": { "Federated": "arn:aws:iam::111122223333:oidc-provider/token.actions.githubusercontent.com" },
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {
    "StringEquals": {
      "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
      "token.actions.githubusercontent.com:sub": "repo:shopmini/app:environment:production"
    }
  }
}
```
**탐지 방법**
```bash
aws iam list-open-id-connect-providers
aws iam get-role --role-name shopmini-deploy-prod --query 'Role.AssumeRolePolicyDocument' --output json
```
신뢰 정책 JSON에 `:sub` 조건이 없거나 값에 `*`가 있으면 확정입니다. CloudTrail 이벤트 `AssumeRoleWithWebIdentity`의 `userIdentity`에서 실제로 어느 저장소·환경이 들어오는지 대조합니다.
**본문** — 27.6절, 8.8절, 6.4절

### AP-36. 빌드 환경에 상주하는 배포 자격 증명
**증상** — 빌드 컨테이너 안에 배포용 자격 증명이 환경 변수로 들어 있다. 빌드 컨테이너의 아웃바운드가 전체 허용이다. CI에서 `npm install`을 쓴다. GitHub Actions가 `actions/xxx@v3` 같은 **태그**를 참조한다. PR 빌드와 릴리스 빌드가 캐시를 공유한다.
**왜 위험한가** — 빌드는 **신뢰할 수 없는 코드를 실행하는 곳**입니다. 의존성의 악성 `postinstall` 한 줄이 그 컨테이너 안의 모든 환경 변수를 읽습니다. 배포 자격 증명이 거기 있으면 그 순간 배포 권한이 넘어갑니다. 아웃바운드가 열려 있으면 유출 경로도 함께 열려 있는 것입니다(AP-22). 액션을 태그로 참조하면 태그 이동 한 번으로 우리 러너에서 공격자 코드가 실행됩니다. `npm install`은 락파일을 조용히 갱신해 재현성과 무결성을 함께 무너뜨립니다. PR 빌드가 캐시를 공유하면 낮은 신뢰 빌드의 오염이 릴리스로 전파됩니다. 로그 마스킹은 `set -x`·인코딩·디버그 출력으로 우회되므로 방어선이 아닙니다.
**올바른 구성** — **빌드 단계와 배포 단계를 분리**해 배포 자격 증명이 빌드 컨테이너에 존재하지 않게 합니다. 빌드 네트워크는 VPC 엔드포인트 + 목적지 제한으로 좁힙니다. 의존성은 `npm ci`(불일치 시 실패해야 정상), 프라이빗 레지스트리에 업스트림 차단과 스코프 선점을 겁니다. 액션은 **커밋 SHA로 고정**하고 버전을 주석으로 답니다. 릴리스 빌드는 캐시 없이, 또는 캐시 키에 신뢰 수준을 포함합니다. Dependabot PR 자동 병합은 하지 않습니다.
**탐지 방법** — AWS 쪽 신호는 **파이프라인 역할의 사용 위치**입니다. CloudTrail에서 배포 역할의 `AssumeRole`이 빌드 단계 시간대에 발생하는지 확인합니다. 워크플로 정의에 대해서는 저장소 쪽 검사가 필요합니다 — `uses:` 줄이 SHA가 아닌 태그를 참조하는지, 배포용 시크릿이 빌드 잡에 노출되는지 정적 검사로 잡습니다.
**본문** — 27.4절, 27.3절, 19.6절

### AP-37. 서명은 하는데 검증은 `Audit`
**증상** — 아티팩트·이미지 서명 파이프라인은 구축했는데 검증 정책이 `Audit`/`Warn` 모드다. 이미지 **태그**에 서명했다. ECR 리포지토리의 태그 불변성이 꺼져 있다.
**왜 위험한가** — 검증이 경고 모드면 **서명 없는 아티팩트도, 변조된 아티팩트도 그대로 배포됩니다.** 서명 인프라는 존재하지만 통제는 존재하지 않는 상태이고, 이것은 감사에서 "서명 체계 있음"으로 보고됩니다. 태그에 서명하는 것은 움직이는 표지판에 도장을 찍는 일입니다 — 태그가 움직이면 서명이 다른 이미지를 가리키고, 스캔·서명한 이미지와 실제 배포된 이미지가 달라집니다. 그러면 롤백도 롤백이 아닙니다.
**올바른 구성** — 서명과 검증 모두 **다이제스트**를 대상으로 합니다. ECR 태그 불변성을 켜고 배포 매니페스트는 다이제스트를 참조합니다. 검증은 `Enforce`로 전환하되 **전환 기한을 정해 문서화**합니다 — 기한 없는 `Audit`은 영구 `Audit`입니다. SBOM도 태그가 아니라 다이제스트를 키로 저장하고, "만든 적 있다"에서 "지금 무엇이 돌고 있다"로 넘어가도록 배포 연결 표를 함께 유지합니다.
**탐지 방법**
```bash
aws ecr describe-repositories \
  --query 'repositories[].[repositoryName,imageTagMutability,imageScanningConfiguration.scanOnPush]' \
  --output table
aws ecr describe-images --repository-name shopmini/app \
  --query 'imageDetails[].[imageDigest,imageTags]' --output json
```
`imageTagMutability`가 `MUTABLE`이면 확정입니다. 검증 모드는 배포 도구(승인 컨트롤러·배포 정책) 설정에서 확인하며, `Enforce`가 아닌 값이 남아 있는지를 IaC 정적 분석 게이트로 잡습니다.
**본문** — 27.5절, 24.2절, 27.2절

## B-8. 거버넌스·멀티 계정 (3)

### AP-38. 콘솔 수동 변경(ClickOps)과 드리프트 방치
**증상** — 장애 대응 중 콘솔에서 고치고 티켓 없이 종료한다. CloudFormation 스택 드리프트 탐지는 켰는데 알림도 조치도 없다. 비준수 목록만 쌓인다. IaC 게이트를 경고 모드로만 운영한다. `useragent` 조건으로 콘솔 접근을 막으려 한다.
**왜 위험한가** — 수동 변경은 **재현 불가 + 감사 추적 단절 + 유령 규칙 잔존**을 동시에 만듭니다. 다음 배포에서 원복되거나, 원복되지 않고 코드와 현실이 갈라집니다. 드리프트를 탐지만 하고 조치하지 않으면 목록이 소음이 되어 아무도 보지 않습니다. 게이트를 경고 모드로 두면 3주 뒤 결과를 보는 사람이 없습니다. `useragent`는 클라이언트가 임의로 설정할 수 있으므로 통제가 아닙니다. 그리고 IaC 자체는 해결책이 아닙니다 — **게이트 없는 IaC는 잘못된 구성을 전 계정에 정확히 복제하는 결함 증폭기**입니다.
**올바른 구성** — 운영 계정 상시 권한을 **읽기 전용**으로 내리고 변경은 브레이크 글래스로만 합니다(상시 관리자 권한이 있으면 ClickOps는 구조적으로 불가피합니다). 긴급 변경은 허용하되 **사후 절차**를 강제합니다 — 티켓 등록 + T+5일 내 코드 반영. 드리프트는 Security Hub로 집계하고 **소유자 알림 + 마감 기한**을 붙입니다. 게이트는 실패 시 머지 불가로 두고, 규칙 파일은 애플리케이션 저장소가 아니라 **별도 저장소**에 둡니다(같은 곳에 있으면 통과가 안 될 때 규칙을 고쳐서 통과시킵니다). 예외는 규칙을 끄는 것이 아니라 리소스별 억제 + 만료일 + 소유자로 처리합니다. 파이프라인 밖 API 직접 호출은 PR 게이트로 막을 수 없으므로 **SCP가 최종 층**입니다.
**탐지 방법**
```bash
aws cloudformation detect-stack-drift --stack-name shopmini-prod-network
aws cloudformation describe-stack-resource-drifts --stack-name shopmini-prod-network \
  --stack-resource-drift-status-filters MODIFIED DELETED
```
Config 관리형 규칙 `cloudformation-stack-drift-detection-check`. CloudTrail에서 `userIdentity.sessionContext`가 콘솔 세션인 쓰기 API 호출을 질의하고, `ConsoleLogin` 이후의 변경 이벤트를 상관 분석합니다.
**본문** — 28.4절, 28.3절, 28.5절, 28.1절

### AP-39. 관리 계정에서 워크로드 운영
**증상** — 기존 운영 계정에서 Organizations를 만들었다. 관리 계정(`123456789012`)에 애플리케이션·개발자 로그인·CloudTrail 로그 버킷이 있다. 조직이 `CONSOLIDATED_BILLING` 기능 세트다. `OrganizationAccountAccessRole`이 기본값 그대로다.
**왜 위험한가** — **관리 계정은 나중에 바꿀 수 없습니다.** 그리고 **관리 계정에는 SCP가 적용되지 않습니다** — 조직 전체를 통제하는 가드레일이 정작 가장 강한 계정에는 걸리지 않습니다. 그 계정에서 자격 증명이 하나 유출되면 조직 전체가 넘어갑니다. 관리 계정에 CloudTrail 로그 버킷을 두면 관리 계정 침해가 곧 증거 소실입니다(AP-30). `OrganizationAccountAccessRole`을 방치하면 관리 계정의 아무 주체나 조건 없이 전 계정 관리자가 되는데, **이 위험은 SCP로 막을 수 없습니다** — 통제 지점은 신뢰 정책과 탐지입니다.
**올바른 구성** — **빈 계정에서 조직을 생성**하고 워크로드 계정을 따로 만듭니다. 처음부터 `--feature-set ALL`로 만듭니다(나중에 승격하려면 전 멤버 동의가 필요합니다). 관리 계정에는 개발자 로그인을 허용하지 않고, 접근은 Identity Center를 통해 멤버 계정으로 직접 갑니다. 로그는 로그 아카이브 계정(`777788889999`), 보안 도구는 보안 계정(`444455556666`)에 둡니다. `OrganizationAccountAccessRole`의 신뢰 정책에 역할 ARN과 MFA 조건을 넣고 사용 알람을 겁니다. Root에 붙이는 SCP에는 **절대 금지 항목만** 둡니다.
**탐지 방법**
```bash
aws organizations describe-organization \
  --query 'Organization.[MasterAccountId,FeatureSet]' --output table
aws sts get-caller-identity --query Account
aws iam get-role --role-name OrganizationAccountAccessRole --query 'Role.AssumeRolePolicyDocument'
```
관리 계정 ID로 로그인한 상태에서 EC2·RDS·Lambda 인벤토리를 조회해 **비어 있는지** 확인하는 것이 가장 직접적인 점검입니다. CloudTrail 이벤트 `AssumeRole` 중 대상이 `OrganizationAccountAccessRole`인 건에 상시 알람.
**본문** — 36.6절, 36.5절, 36.7절, 37.3절

### AP-40. 전 계정을 마비시키는 SCP 오적용
**증상** — SCP를 Root에 바로 붙여 테스트한다. `FullAWSAccess`를 떼고 `Allow`를 붙이지 않았다. 리전 제한 SCP에 글로벌 서비스와 서비스 연결 역할 예외가 없다. 허용 목록(allowlist) 전략으로 시작했다. SCP로 권한을 **부여**하려 한다. 배포 역할까지 함께 잠갔다.
**왜 위험한가** — SCP는 **부여가 아니라 상한**입니다. `Allow`를 넣어도 아무 권한이 생기지 않는데 원인을 찾느라 며칠이 갑니다. `FullAWSAccess`를 떼는 순간 그 지점 아래 **전 계정이 마비**됩니다. 리전 제한에서 글로벌 서비스(IAM·CloudFront·Route 53·STS)를 빼지 않으면 그 작업들이 전부 실패하고, 서비스 연결 역할을 예외 처리하지 않으면 Auto Scaling·ELB가 **조용히** 실패합니다. 허용 목록으로 시작하면 서비스 간 내부 호출이 끊기고 정책 크기 한도에 부딪힙니다. 배포 역할까지 잠그면 그 SCP를 고칠 곳이 관리 계정밖에 남지 않습니다. 사고 대응 중 전면 `Deny` SCP를 거는 것도 같은 함정입니다 — 우리 조사자도 증거를 수집할 수 없게 됩니다.
**올바른 구성** — **거부 목록(denylist) 전략**을 기본으로 하고 `FullAWSAccess`는 유지합니다. `PolicyStaging` OU → 비운영 OU → 일부 운영 → 전체의 4단계로 올립니다. 리전 제한에는 `NotAction`으로 글로벌 서비스를 나열하고 `aws:PrincipalArn`으로 `aws-service-role/*`을 예외 처리합니다. 암호화 강제는 `Bool: false`만으로는 파라미터 미지정 요청이 통과하므로 `Null` 문장을 함께 넣습니다. 예외 목록에 **자기 자신(배포 역할)을 포함**하고, 예외 ARN은 적용 전에 실제로 검증합니다. 조직 탈퇴 금지 SCP를 Root에 빠뜨리지 않습니다 — 침해된 계정이 조직 밖으로 걸어 나갑니다. 마지막으로, SCP만 늘리고 탐지를 하지 않으면 어떤 SCP가 실제로 무엇을 막는지 아무도 모르게 되므로 `AccessDenied`를 지표화합니다.
**탐지 방법**
```bash
aws organizations list-policies --filter SERVICE_CONTROL_POLICY \
  --query 'Policies[].[Id,Name,AwsManaged]' --output table
aws organizations list-policies-for-target --target-id r-examp1e --filter SERVICE_CONTROL_POLICY
aws organizations describe-policy --policy-id p-examp1e --query 'Policy.Content' --output text
```
붙이기 전 검증은 `aws iam simulate-principal-policy`로 하되, 시뮬레이터에 SCP·리소스 정책이 반영되지 않는다는 한계를 감안해 **스테이징 OU의 실제 계정에서 실호출**로 최종 확인합니다. CloudTrail 이벤트 `AttachPolicy`·`DetachPolicy`·`UpdatePolicy`에 알람.
**본문** — 37.3절, 37.1절, 37.2절, 33.3절

## AP 번호 ↔ 부록 A 체크리스트 매핑 안내

부록 A(마스터 100항목)와 이 부록은 **같은 통제를 반대 방향에서** 보는 문서입니다. 부록 A는 "있어야 할 것"을 영역별로 나열하고, 부록 B는 "있으면 안 되는 것"을 보여 줍니다. 두 문서는 항목이 1:1로 대응하지 않습니다 — 하나의 안티패턴이 여러 체크리스트 항목의 실패로 나타나기도 하고(예: AP-19는 보안 그룹·관리 접근·탐지 세 항목에 걸칩니다), 반대로 여러 안티패턴이 한 항목의 서로 다른 실패 형태이기도 합니다(AP-08·AP-09는 모두 "시크릿을 저장소에 두고 참조로만 쓴다"는 한 항목의 위반입니다). 그래서 번호 대 번호가 아니라 **영역 대 영역**으로 씁니다. 부록 B의 **B-1**은 부록 A의 *계정/IAM(20항목)*, **B-2·B-3**은 *데이터(20항목)*, **B-4**는 *네트워크(15항목)*, **B-5**는 *컴퓨트(15항목)*, **B-6**은 *로깅·탐지(15항목)*, **B-7·B-8**은 *거버넌스(15항목)* 에 대응합니다. 실무에서는 이렇게 쓰십시오 — 부록 A로 한 바퀴 돌려 "아니오"가 나온 영역을 찾고, 그 영역에 해당하는 부록 B 분류를 펼쳐 **어떤 형태의 실패인지**를 특정한 다음, 각 항목의 **본문** 절 번호로 돌아가 고칩니다. 반대로 사고나 감사 지적에서 출발할 때는 부록 B에서 해당 안티패턴을 찾아 원인을 확정하고, 같은 영역의 부록 A 항목 전체를 다시 점검해 **같은 뿌리에서 나온 다른 실패가 남아 있는지** 확인하십시오. 안티패턴은 대개 혼자 오지 않습니다.
