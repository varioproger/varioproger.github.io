# 33장. 사고 대응 실행

> **이 장에서 다루는 것**
> - 사이버 킬 체인과 MITRE ATT&CK 클라우드 매트릭스로 "공격자가 지금 어디에 있는지" 읽기
> - OODA 루프 — 클라우드에서 루프가 빨라지는 이유와 느려지는 이유
> - 🔴 무단 접근을 끊는 다섯 가지 초동 조치와 각각의 부작용
> - 🔴 데이터 유출과 C2 통신을 끊는 네트워크·엔드포인트·키 차원의 차단
> - ⚠️ 성급한 종료가 증거를 지우는 방식과 올바른 조치 순서
> - 내부 보고·고객 통지·규제 기관 신고의 시계가 언제부터 도는가
>
> **선행 지식**: 3장(공격 경로), 4장(규제), 19장(트래픽 통제), 20장(엔드포인트 정책), 30장(알람), 31장(GuardDuty), 32장(사고 대응 준비)
> **난이도**: ★★★

32장에서 준비를 마쳤습니다. 팀·플레이북·포렌식 계정·격리용 보안 그룹·봉인된 락다운 SCP가 있습니다. 이 장은 그것들을 **실제로 발동합니다.**

> 📖 *Practical Cloud Security* 2판 7장: **"이 글을 읽는 지금 활성 보안 사고 한가운데에 있지 않기를 바란다. 만약 그렇고, 아직 사고 대응 팀도 계획도 도구도 체크리스트도 없다면, 당신의 첫 우선순위는 증거를 파괴하지 않으면서 사고를 최대한 봉쇄하는 것이어야 한다. 보통 이는 시스템을 종료하거나 격리하고, 암호를 바꾸고, 접근을 취소하고, 네트워크 연결을 차단하는 일의 조합으로 이루어진다."**

이 한 문장에 이 장의 목차가 다 들어 있습니다. **"증거를 파괴하지 않으면서"**(33.5) **"봉쇄"**(33.3, 33.4). 두 요구는 충돌하고, 그 충돌을 어떤 순서로 푸느냐가 대응의 품질을 결정합니다.

원서는 이어서 분류(triage)를 먼저 하라고 못박습니다.

> 📖 2판 7장: **"먼저 사고 대응 팀의 최소한 일부를 동원해 분류를 수행하라. 몇 분 조사해 보니 완전히 봉쇄된 것으로 보이는 악성코드 감염 때문에 서른 명을 잠자리에서 깨우고 싶지는 않을 것이다. 과잉 대응도 과소 대응도 하기 쉬우므로, 미리 정의된 심각도 등급과 등급별 대응 지침이 도움이 되는 지점이 바로 여기다."**

32.2의 심각도 등급표가 여기서 값을 합니다. **등급표가 없으면 모든 알림이 "일단 다 부르자"가 되고, 세 번째 새벽 호출 이후에는 아무도 오지 않습니다.**

## 33.1 사이버 킬 체인과 MITRE ATT&CK for Cloud

### 왜 프레임워크가 필요한가

사고 대응 중 가장 위험한 상태는 "지금 보이는 것"만 보는 것입니다. GuardDuty가 채굴 도메인 질의를 알렸다면 그건 **목표 달성** 단계의 증상이고, 앞에는 초기 접근·실행·지속성 확보가 이미 끝나 있습니다. 프로세스만 죽이면 30분 뒤 다시 뜹니다.

> 📖 1판·2판 7장 공통: **"그런 다음, 킬 체인이나 어택 체인에 근거해 공격자의 목표가 무엇일지 예측하면서, 당신이 구현해 둔 계획을 실행하기 시작하라."**

### 록히드 마틴 사이버 킬 체인 7단계

2판 7장은 절 제목 자체가 **"Cyber Kill Chains and MITRE ATT&CK"** 이며, 킬 체인 7단계를 이렇게 정의합니다.

| 단계 | 📖 원서 2판 7장의 정의 |
|---|---|
| 정찰(Reconnaissance) | "공격자가 무엇에 침입할지 파악하고 도움이 될 만한 취약점을 식별하기 위해 조사한다. 구글 검색부터 쓰레기통 뒤지기, 소셜 엔지니어링, 네트워크 포트 스캔까지 무엇이든 포함될 수 있다." |
| 무기화(Weaponization) | "공격자가 그 취약점을 익스플로잇할 악성코드를 마련한다. 더 진보한 공격자는 맞춤 제작을 하고, 덜 진보한 공격은 이미 나와 있는 것을 쓴다." |
| 전달(Delivery) | "공격자가 피해자로 하여금 그 악성코드를 실행하게 만든다 — 네트워크 공격으로, 이메일로, 또는 다른 수단으로." |
| 익스플로잇(Exploitation) | "악성코드가 실행되어 무단 접근을 획득한다." |
| 설치(Installation) | "악성코드가 지속성, 즉 버티는 힘을 얻는다 (…) 어떤 경우에는 이 지속성 악성코드가 당신의 정상 프로그램보다 더 잘 관리되고 업데이트된다!" |
| 명령 및 제어(C2) | "악성코드가 어떤 종류의 통신 채널을 만들어 공격자가 원격으로 제어할 수 있게 한다 — 리버스 셸, 아웃바운드 웹 연결, **심지어 정상적인 클라우드 파일 저장 서비스에서 명령을 읽어오는 것까지.** 이 시점에 당신의 시스템 접근권이 암시장에서 좋은 값에 팔릴 수도 있다." |
| 목표 달성(Actions on objective) | "공격자가(**원래 공격자가 아닐 수도 있다**) 원하는 무엇이든 한다 — 데이터를 훔치고, 웹사이트를 훼손하고, 고객을 공격하고, 돈을 갈취한다." |

굵게 표시한 두 대목이 실무적으로 중요합니다. **C2 채널이 "정상적인 클라우드 파일 저장 서비스"일 수 있다**면 도메인 평판 기반 차단으로는 잡히지 않습니다 — 19.6의 이그레스를 **허용 목록** 방식으로 짜야 하는 이유입니다. 그리고 **초기 침입자와 데이터를 훔치는 자가 다를 수 있다**면 그 사이에 며칠에서 몇 달의 공백이 생기고, 공백이 로그 보존 기간보다 길면 침입 경로를 영원히 알 수 없습니다 — **29.7의 보존 기간 설정이 곧 사고 대응 역량입니다.**

### MITRE ATT&CK: 2판에서 무게가 옮겨 갔다

1판과 2판을 나란히 놓으면 변화가 뚜렷합니다.

| 항목 | 1판(2019) | 2판(2023) |
|---|---|---|
| 절 제목 | "Cyber Kill Chains" | **"Cyber Kill Chains and MITRE ATT&CK"** |
| 장 도입 사이드바 제목 | "Kill Chains" | **"MITRE ATT&CK and Kill Chains"** (순서가 뒤집힘) |
| MITRE 언급 | ATT&CK을 "다른 인기 있는 체인"으로 한 문장 처리 | **11개 전술을 각각 정의하고 설명** |
| 권고 | "킬 체인 중 최소 하나를 읽고 이해하라" | "킬 체인 모델 하나 + **ATT&CK 클라우드 매트릭스의 TTP 일부**" |
| 원서 전체에서 "ATT&CK" 등장 횟수(목차·색인 포함) | 3회 | **13회** |

> 📖 2판 7장 사이드바: **"MITRE ATT&CK은 일반적으로 킬 체인보다 더 상세하며, 공격의 서로 다른 단계와 서로 다른 컴퓨팅 환경에서 공격자가 사용할 수 있는 각기 다른 전술·기법·절차(TTP)를 보여준다. 킬 체인은 개요에 가까워서, 공격자가 통상 밟는 순서대로 흔한 단계를 나열한다 (…) 사고 대응 팀은 최소한 하나의 킬 체인 모델과 함께 MITRE ATT&CK 클라우드 매트릭스의 TTP 일부를 읽고 이해할 것을 권한다."**
>
> 1판의 같은 자리는 ATT&CK을 한 번 언급한 뒤 폴 폴스(Paul Pols)의 논문 **"The Unified Kill Chain"** 을 저자명까지 들어 소개합니다. 2판은 이 논문을 제목만 남기고 그 자리를 ATT&CK 설명으로 채웠습니다.

그리고 2판은 ATT&CK 전술 11개를 열거합니다 — 초기 접근, 실행, 지속성, 권한 상승, 방어 회피, 자격 증명 접근, 탐색, 측면 이동, 수집, 유출, 임팩트.

> 📖 2판 7장: **"MITRE ATT&CK 전술은 록히드 마틴 사이버 킬 체인 단계보다 덜 선형적이고 더 상세한 경향이 있으며, 프레임워크는 그 전술적 목표를 달성하는 데 쓰일 수 있는 구체적 기법들을 나열한다. 어느 쪽을 쓰든, 공격자가 이미 무엇을 했고 다음에 무엇을 할지 감을 잡을 수 있도록 최소한 하나에는 익숙해지는 것이 좋다."**

> 💡 **원서 이후 보충** — 이 11개는 ATT&CK **Enterprise** 매트릭스의 전체 전술(정찰·자원 개발·명령 및 제어를 포함해 14개)이 아니라 **클라우드(IaaS) 매트릭스**의 구성과 일치합니다. **클라우드 매트릭스에는 '명령 및 제어' 전술이 없습니다** — 훔친 액세스 키로 공격자의 노트북에서 곧장 API를 부르면 되므로 제어 평면 공격에는 C2 채널이 필요 없기 때문입니다. 33.4에서 **네트워크 차단과 자격 증명 차단을 별개의 축으로 다루는 이유**입니다.

### AWS에서의 단계별 탐지 신호와 차단 지점

왼쪽 두 칸으로 지금 위치를 정하고, 오른쪽 두 칸에서 다음 행동을 고릅니다.

| 킬 체인 단계 | ATT&CK 전술(클라우드) | AWS 탐지 신호 | 차단 지점 |
|---|---|---|---|
| 정찰 | (Discovery로 흡수) | `Recon:EC2/Portscan`, `Recon:IAMUser/MaliciousIPCaller`, WAF 로그의 스캐너 UA | 19장 SG/NACL, WAF 속도 기반 규칙, 퍼블릭 노출면 축소 |
| 전달·익스플로잇 | Initial Access (T1078 유효 계정, T1190 공개 앱 익스플로잇) | WAF `Blocked` 급증, ALB 5xx, `UnauthorizedAccess:EC2/SSHBruteForce`, 콘솔 로그인 실패 알람(30.3 #3) | WAF 규칙 즉시 Block 전환, SG 인바운드 폐쇄, 30.3 #2 MFA 없는 로그인 알람 |
| 익스플로잇 | Execution, Credential Access (T1552.005 IMDS 자격 증명) | `UnauthorizedAccess:IAMUser/InstanceCredentialExfiltration.OutsideAWS` | **IMDSv2 강제**, 인스턴스 격리(33.3 ④), 역할 세션 무효화(33.3 ②) |
| 설치 | Persistence (T1098 계정 조작, T1136 계정 생성) | CloudTrail `CreateUser`·`CreateAccessKey`·`AttachUserPolicy`, 30.3 #4 IAM 정책 변경 알람 | 신규 자격 증명 전수 회수(33.3 ③), 락다운 SCP(32.2) |
| 설치 | Privilege Escalation (T1548 권한 상승) | `iam:PassRole`+`ec2:RunInstances` 조합, IAM Access Analyzer 신규 외부 접근 | 권한 경계, SCP, 3.4 ③의 상승 체인 차단 |
| C2 | (클라우드 매트릭스 밖 — 인스턴스 계층) | `Backdoor:EC2/C&CActivity.B!DNS`, `Trojan:EC2/DNSDataExfiltration`, Route 53 Resolver 쿼리 로그 | **DNS Firewall 도메인 차단(33.4)**, 이그레스 폐쇄, 격리 SG |
| C2 | Defense Evasion (T1562.008 클라우드 로그 무력화) | 30.3 #5 CloudTrail 구성 변경·중지 알람, `StopLogging`, GuardDuty `Stealth:IAMUser/CloudTrailLoggingDisabled` | 조직 트레일(29장) — 멤버 계정에서 끌 수 없음 |
| 목표 달성 | Discovery (T1580 클라우드 인프라 탐색, T1619 클라우드 스토리지 객체 탐색) | `Discovery:S3/AnomalousBehavior`, 짧은 시간에 `ListBuckets`·`DescribeInstances` 대량 호출 | 30.6 Athena 질의로 열거 범위 확정 |
| 목표 달성 | Collection·Exfiltration (T1530 클라우드 스토리지 데이터 수집, T1537 클라우드 계정으로 데이터 전송) | `Exfiltration:S3/AnomalousBehavior`, 30.3 #15 S3 대량 다운로드, VPC 플로우 로그 아웃바운드 바이트 급증 | **엔드포인트 정책(20.3), 버킷 정책, KMS 키 비활성(33.4)** |
| 목표 달성 | Impact (T1496 자원 탈취, T1485 데이터 파괴) | `CryptoCurrency:EC2/BitcoinTool.B!DNS`, 비용 이상 알람, 30.3 #12 KMS 키 삭제 예약 | 서비스 할당량, 락다운 SCP, 17장 백업 격리 |

**이 표를 플레이북 첫 장에 붙이십시오.** 사고 중 참조하는 표는 두 페이지를 넘으면 아무도 보지 않습니다.

다만 **정찰 단계는 대응 대상이 아닙니다.** 인터넷에 붙은 자산은 상시 스캔당하고, 포트 스캔을 전부 사고로 올리면 30.9의 알람 피로가 재현됩니다. 정찰은 **추세**로 보고, 침해로 취급하는 것은 익스플로잇 단계부터입니다.

## 33.2 OODA 루프

### 관찰-판단-결정-행동

원서는 대응의 뼈대로 OODA 루프를 제시합니다. 사고 대응이 **공격자와 방어자가 각자 루프를 돌리는 경쟁**이라는 관점입니다.

> 📖 1판·2판 7장 공통: **"당신에게는 계획이 있고, 공격자의 진행 상황과 목표에 대해서도 어느 정도 감이 있다. 이제 대응할 시간이다. 사고 대응에서 인기 있는 개념은 OODA 루프 — 관찰(observe), 판단(orient), 결정(decide), 행동(act)이다."**

| 단계 | 원서의 정의 | ShopMini에서의 실제 |
|---|---|---|
| **관찰** | "클라우드 제공자 로그, 방화벽, 운영체제 로그, 지표 등 여러 곳에서 정보를 모아, 공격자가 무언가 하고 있음을 나타낼 수 있는 이상 행동을 찾는다" | GuardDuty 결과, CloudTrail(30.6 Athena 질의 8종), VPC 플로우 로그, ALB·WAF 로그, CloudWatch 지표 |
| **판단** | "무슨 일이 벌어지고 있고 다음에 무엇이 일어날 수 있는지 이해하려 시도한다. 여기에는 가장 중요한 자산이 어디 있는지에 대한 내부 지식과, 누가 왜 공격하는지에 대한 외부 위협 인텔리전스가 모두 관여할 수 있다" | 12.3의 `DataClass` 태그로 자산 중요도 확인 + 33.1 표로 킬 체인 위치 확정 |
| **결정** | "피해를 최소화하거나 복구를 가능하게 할 다음 전술을 고른다. 예컨대 특정 시스템을 오프라인으로 내리거나, 접근을 취소하거나, 시스템을 격리하거나, 새 환경을 구축하기로 결정할 수 있다" | 32.2 플레이북의 분기 — 격리 / 자격 증명 회수 / 락다운 / 재구축 |
| **행동** | "실제로 그 전술을 실행한다" | 33.3~33.4의 CLI |

**위협 인텔리전스에 반드시 돈이 드는 것은 아니라는 점도 원서가 명시합니다.**

> 📖 2판 7장: **"모든 위협 인텔리전스에 비용이 드는 것은 아니다. 예를 들어 미국 사이버보안 및 인프라 보안국(CISA)은 악의적 활동에 대한 경보를 정기적으로 발표한다. 의심스러운 행동이 보이는데 CISA가 특정 위협 행위자가 특정 전술·기법·절차를 사용해 당신의 산업을 표적으로 삼고 있다는 경보를 냈다면, 그것이 판단에 도움이 될 수 있다."**
>
> 1판은 같은 자리에 **US-CERT**를 들었습니다. US-CERT의 기능이 CISA로 통합된 조직 변화가 판 사이에 반영된 것입니다. 국내에서는 KISA 인터넷침해대응센터의 보안 공지가 같은 역할을 합니다.

### 공격자보다 빠르게 돌아야 한다

> 📖 1판·2판 7장 공통: **"행동한 뒤에는 루프가 다시 시작된다 — 당신이 한 일에 대해 공격자가 어떻게 반응하는지 보기 위해 관찰하고, 판단하고, 결정하고, 다시 행동한다. 이 루프들은 비교적 빨라야 하며, 사고가 해결되었음을 관찰이 알려줄 때까지 계속되어야 한다."**

**차단은 일회성 작업이 아니라 관찰 대상입니다.** 키를 죽인 뒤 볼 것은 "정말 멈췄는가"가 아니라 **"공격자가 어떤 대체 경로로 갈아탔는가"** 입니다. 흔한 전개는 지속성 단계에서 이미 심어 둔 **두 번째 사용자**의 키로 갈아타는 것이고, 관찰하지 않으면 우리는 사고가 끝났다고 믿고 공격자는 그대로 남습니다.

그래서 **조치 직후 반드시 CloudTrail을 다시 훑어야 합니다.** 30.6의 ⑦ "신규 IAM 사용자·키·정책 생성" 질의가 여기서 쓰입니다. 조치 → 재관찰이 붙어야 한 바퀴입니다.

### 클라우드에서 루프가 빨라지는 이유

원서는 행동 단계에서 클라우드가 유리하다고 말합니다.

> 📖 1판·2판 7장 공통: **"여기가 클라우드 인프라를 쓰는 것이 정말 도움이 될 수 있는 지점이다. 특히 클라우드 환경을 시간에 걸쳐 유기적으로 자라게 하는 대신 반복 가능한 방식으로 구축하는 데 투자했다면 그렇다."** 예는 둘입니다. 첫째는 **컴퓨트와 스토리지의 구분이 강해 이미지를 고쳐 전체 인스턴스를 교체하고 데이터 저장소에 다시 붙일 수 있다**는 것, 둘째는 격리입니다. **"스크립트로 API를 호출해 보안 그룹이나 네트워크 ACL을 잠그는 방식으로 시스템을 쉽게 격리할 수도 있다. 전통적 환경이라면 (…) 여러 라우터나 방화벽에 일일이 로그인하거나 케이블을 뽑기 시작해야 했을 것이다."**

**"케이블을 뽑기 시작해야 했을 것"** — 이 대비가 이 장의 전제입니다. 33.3과 33.4의 모든 조치가 한 줄의 API 호출이라는 사실 자체가 클라우드의 대응 이점입니다.

### 그러나 실제로 루프를 느리게 만드는 것들

OODA가 느려지는 원인은 기술이 아니라 대부분 준비 부족입니다.

| 느려지는 지점 | 원인 | 32장에서의 해법 |
|---|---|---|
| 관찰 | CloudTrail 이벤트가 S3에 도착하기까지 시간이 걸림 | 실시간이 필요한 판단은 **EventBridge**(30.5)로, 사후 분석만 S3+Athena로 |
| 관찰 | 로그가 여러 계정·리전에 흩어져 질의 자체가 30분 | 조직 트레일 + 로그 아카이브 계정 집중(29장), 파티션 프로젝션 테이블(30.6) |
| 판단 | 이 인스턴스가 무슨 서비스인지, 누가 소유자인지 모름 | 태그 표준(12.3)과 최신 아키텍처 다이어그램(32.3) |
| 결정 | 서비스 중단 권한이 누구에게 있는지 불명확 | RACI(32.1)에서 **중단 결정권자**를 사전 지정 |
| 행동 | 조사자에게 격리 권한이 없어 권한 요청부터 시작 | 사전 생성된 `IncidentResponder` 역할(32.3 ②) |
| 행동 | 콘솔이 침해 계정 안에 있어 접속을 망설임 | 브레이크 글래스와 별도 관리 경로(32.4) |

**가장 흔한 지연은 "결정"입니다.** 새벽 2시에 "격리해도 됩니까"를 물을 사람을 찾는 데 40분이 걸립니다. 그 40분이면 유출 단계가 완료되기에 충분합니다.

### ① 액세스 키 비활성화 — 삭제가 아니라 비활성화

**먼저 비활성화(`Inactive`)하십시오.** 비활성화는 즉시 효력이 있으면서 키 ID와 생성 시각, `LastUsed` 기록을 남깁니다. 삭제하면 조사에 필요한 메타데이터가 사라집니다.

```bash
# 1) 이 사용자의 모든 키를 먼저 나열한다 — 공격자가 추가한 두 번째 키가 있을 수 있다
aws iam list-access-keys --user-name batch-runner \
  --region ap-northeast-2 --profile awssec-lab

# 2) 마지막 사용 시각·리전·서비스를 기록한다 (조사용, 조치 전 반드시 수집)
aws iam get-access-key-last-used --access-key-id AKIAIOSFODNN7EXAMPLE \
  --region ap-northeast-2 --profile awssec-lab

# 3) 비활성화 — 즉시 효력
aws iam update-access-key \
  --user-name batch-runner \
  --access-key-id AKIAIOSFODNN7EXAMPLE \
  --status Inactive \
  --region ap-northeast-2 --profile awssec-lab
```

> ⚠️ **부작용** — 이 키를 쓰던 배치·CI·서드파티 연동이 즉시 실패합니다. `list-access-keys`는 키가 **어디서 쓰이는지** 알려주지 않으므로, 12.3의 태그와 소유자 정보가 없으면 "무엇이 멈출지 모른 채" 끊게 됩니다.

> ⚠️ **키 비활성화만으로 끝나지 않습니다.** 공격자가 이 키로 이미 `sts:GetSessionToken`·`sts:AssumeRole`을 호출해 **임시 자격 증명을 받아 두었다면**, 그 세션은 만료 시각까지 살아 있습니다. ②가 필요한 이유입니다.

> 💡 **원서 이후 변경** — AWS는 퍼블릭 리포지토리 등에서 노출된 액세스 키를 자동 탐지해 해당 IAM 사용자에게 격리용 관리형 정책(`AWSCompromisedKeyQuarantine` 계열, 버전 번호가 붙습니다)을 부착하는 경우가 있습니다. 이 정책이 붙어 있다면 **AWS가 이미 노출을 인지했다는 뜻**이므로, 지원 케이스를 열고 키를 교체할 때까지 임의로 떼지 마십시오.

### ② 역할 세션 즉시 무효화 — `aws:TokenIssueTime`

IAM 역할의 임시 자격 증명에는 "취소" API가 없습니다. **대신 발급 시각을 기준으로 Deny하는 인라인 정책을 역할에 붙입니다** — 콘솔의 "활성 세션 취소" 버튼이 하는 일이 이것입니다.

`revoke-older-sessions.json`:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyAllOlderThan",
      "Effect": "Deny",
      "Action": "*",
      "Resource": "*",
      "Condition": {
        "DateLessThan": {
          "aws:TokenIssueTime": "2026-09-06T02:14:00Z"
        }
      }
    }
  ]
}
```

```bash
# 현재 UTC 시각을 그대로 쓰면, 지금 이 순간 이전에 발급된 모든 세션이 죽는다
aws iam put-role-policy \
  --role-name ShopMiniAppRole \
  --policy-name DenyAllOlderThan \
  --policy-document file://revoke-older-sessions.json \
  --profile awssec-lab
```

동작 원리를 정확히 알아야 안전하게 씁니다.

| 특성 | 내용 |
|---|---|
| 적용 대상 | `aws:TokenIssueTime` 키가 **존재하는** 요청, 즉 임시 자격 증명(역할 세션)만 |
| 미적용 대상 | IAM 사용자의 장기 액세스 키 요청 — 요청 컨텍스트에 `aws:TokenIssueTime`이 없어 조건이 성립하지 않음(같은 정책을 SCP로 붙여도 사용자 키는 안 걸립니다. ①·③이 따로 필요한 이유) |
| 효력 시점 | 즉시. 다음 API 호출부터 `AccessDenied` |
| 새 세션 | 타임스탬프 **이후** 발급 세션은 정상 동작 |

> ⚠️ **부작용이 큽니다.** 이 역할을 쓰는 **모든 정상 워크로드의 기존 세션도 함께 죽습니다.** ShopMini 앱이 이 역할로 S3·Secrets Manager를 호출 중이었다면 전부 `AccessDenied`입니다. **역할 하나의 폭발 반경이 곧 이 조치의 폭발 반경입니다.**

> ⚠️ **더 중요한 함정** — 공격자가 여전히 인스턴스에서 코드를 실행 중이라면 IMDS에서 **새 자격 증명을 다시 받아 갑니다.** 타임스탬프 이후 발급이므로 Deny에 걸리지 않습니다. **그래서 ②는 반드시 ④(인스턴스 격리) 다음에 해야 합니다.**

보조 조치로 IMDS 엔드포인트 자체를 끌 수 있습니다.

```bash
# 해당 인스턴스에서 IMDS 자체를 차단 — 새 자격 증명 발급 경로를 끊는다
aws ec2 modify-instance-metadata-options \
  --instance-id i-0123456789abcdef0 \
  --http-endpoint disabled \
  --region ap-northeast-2 --profile awssec-lab
```

> ⚠️ 이 인스턴스의 정상 애플리케이션도 즉시 자격 증명을 잃습니다. 이미 격리한 인스턴스에만 쓰십시오.

**복구 시 이 인라인 정책을 반드시 제거하십시오.** 남겨두면 몇 달 뒤 원인 불명의 `AccessDenied`로 되돌아옵니다.

```bash
aws iam delete-role-policy --role-name ShopMiniAppRole \
  --policy-name DenyAllOlderThan --profile awssec-lab
```

### ③ 사용자 로그인 차단과 권한 분리

콘솔 접근이 침해된 경우입니다. **암호 변경이 아니라 로그인 프로파일 삭제**가 확실합니다.

```bash
# 1) 콘솔 로그인 프로파일 삭제 (콘솔 접근 차단)
aws iam delete-login-profile --user-name suspect-user --profile awssec-lab

# 2) 관리형 정책 분리 — 붙어 있는 것을 먼저 기록해 둔다
aws iam list-attached-user-policies --user-name suspect-user --profile awssec-lab
aws iam detach-user-policy --user-name suspect-user \
  --policy-arn arn:aws:iam::aws:policy/PowerUserAccess --profile awssec-lab

# 3) 그룹에서도 제거 (그룹 경유 권한이 남는 실수가 잦다)
aws iam list-groups-for-user --user-name suspect-user --profile awssec-lab
aws iam remove-user-from-group --user-name suspect-user \
  --group-name developers --profile awssec-lab
```

정책을 하나씩 떼는 것보다 **인라인 전면 거부 한 장을 붙이는 편이 빠르고 되돌리기도 쉽습니다.**

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "IncidentContainmentDenyAll",
      "Effect": "Deny",
      "NotAction": [
        "iam:ChangePassword",
        "iam:GetUser"
      ],
      "Resource": "*"
    }
  ]
}
```

```bash
aws iam put-user-policy --user-name suspect-user \
  --policy-name IncidentContainmentDenyAll \
  --policy-document file://deny-all.json --profile awssec-lab
```

> ⚠️ **명시적 Deny는 모든 Allow를 이깁니다.** 이 사용자가 사람이 아니라 서비스 계정이라면 그 서비스가 즉시 멈춥니다. **누구/무엇의 자격 증명인지 확인하기 전에 붙이지 마십시오.**

**IAM Identity Center**를 쓴다면 사용자를 계정 할당에서 제거하고, 이미 발급된 세션은 ②의 방식으로 해당 권한 집합 역할에 Deny를 붙여 끊습니다.

```bash
# 권한 집합 할당 제거 (위임 관리자 계정에서)
aws sso-admin delete-account-assignment \
  --instance-arn arn:aws:sso:::instance/ssoins-EXAMPLE \
  --target-id 111122223333 --target-type AWS_ACCOUNT \
  --permission-set-arn arn:aws:sso:::permissionSet/ssoins-EXAMPLE/ps-EXAMPLE \
  --principal-type USER --principal-id 94481428-EXAMPLE \
  --profile awssec-lab
```

> ⚠️ **할당 제거는 새 세션만 막습니다.** 이미 어시움한 역할 세션은 지속 시간이 끝날 때까지 살아 있으므로 **반드시 ②를 함께 하십시오.**

### ④ 인스턴스 격리 — 순서를 틀리면 증거가 사라진다

32.3 ③에서 만든 `shopmini-quarantine` 보안 그룹을 발동합니다. **다만 순서가 있습니다.** 격리 SG를 먼저 붙이면 ALB 헬스 체크가 실패하고 Auto Scaling이 "비정상"으로 판정해 **종료·교체합니다.** 증거가 자동으로 삭제됩니다.

**🔴 반드시 이 순서로 하십시오.**

```bash
INSTANCE=i-0123456789abcdef0
ASG=shopmini-app-asg
QSG=sg-0a1b2c3d4e5f60718
REGION=ap-northeast-2
PROFILE=awssec-lab

# 1) ASG의 교체 동작을 먼저 정지시킨다 (가장 먼저!)
aws autoscaling suspend-processes \
  --auto-scaling-group-name $ASG \
  --scaling-processes ReplaceUnhealthy Terminate AZRebalance \
  --region $REGION --profile $PROFILE

# 2) ALB 타깃 그룹에서 등록 해제 — 사용자 트래픽을 먼저 끊는다
aws elbv2 deregister-targets \
  --target-group-arn arn:aws:elasticloadbalancing:ap-northeast-2:111122223333:targetgroup/shopmini-app/0123456789abcdef \
  --targets Id=$INSTANCE,Port=8443 \
  --region $REGION --profile $PROFILE

# 3) ASG에서 인스턴스를 분리한다 (용량은 유지 — 정상 인스턴스가 대신 뜬다)
aws autoscaling detach-instances \
  --instance-ids $INSTANCE \
  --auto-scaling-group-name $ASG \
  --no-should-decrement-desired-capacity \
  --region $REGION --profile $PROFILE

# 4) 종료 방지를 켠다
aws ec2 modify-instance-attribute \
  --instance-id $INSTANCE --disable-api-termination \
  --region $REGION --profile $PROFILE

# 5) 이제 격리 보안 그룹으로 교체한다
aws ec2 modify-instance-attribute \
  --instance-id $INSTANCE --groups $QSG \
  --region $REGION --profile $PROFILE

# 6) 증거임을 태그로 못박는다 — 사람이 실수로 지우는 것을 줄인다
aws ec2 create-tags --resources $INSTANCE \
  --tags Key=IncidentId,Value=IR-2026-0906-01 Key=Status,Value=QUARANTINED Key=DoNotTerminate,Value=true \
  --region $REGION --profile $PROFILE
```

3단계의 `--no-should-decrement-desired-capacity`가 중요합니다. **희망 용량을 유지하면 ASG가 정상 인스턴스를 새로 띄워, 서비스를 유지한 채 증거를 확보합니다.**

> ⚠️ **`--disable-api-termination`은 Auto Scaling을 막지 못합니다.** EC2 종료 방지 속성은 사용자의 `TerminateInstances` 호출을 막지만 **Auto Scaling의 종료는 이 속성을 존중하지 않습니다.** 그래서 1·3단계로 ASG에서 먼저 떼어내는 것이 필수입니다.

> ⚠️ **보안 그룹은 상태 저장이라 기존 연결이 즉시 끊기지 않을 수 있습니다.** 확실한 즉시 차단이 필요하면 33.4의 NACL을 병행하십시오. ENI 분리(`detach-network-interface`)도 방법이지만 **기본 인터페이스(eth0)는 분리할 수 없습니다.**

**컨테이너와 서버리스는 조치 대상이 다릅니다.**

| 대상 | 격리 방법 | ⚠️ 주의 |
|---|---|---|
| EC2 | 위 6단계 | ASG·종료 방지 순서 |
| ECS/Fargate 태스크 | 서비스에서 분리 후 태스크 유지, 태스크 역할 세션 무효화(②) | **태스크를 중지하면 컨테이너와 그 안의 모든 것이 사라집니다.** 중지 전에 로그·이미지 다이제스트 확보 |
| EKS 파드 | 네트워크 정책으로 격리 + 노드 코든(cordon) | 파드 삭제는 EC2 종료와 같은 의미 |
| Lambda | 예약 동시성을 0으로 — 즉시 실행 중지 | 함수 코드·환경변수·버전을 먼저 보전 |

```bash
# Lambda 즉시 정지 — 삭제하지 않고 실행만 막는다
aws lambda put-function-concurrency \
  --function-name shopmini-order-processor \
  --reserved-concurrent-executions 0 \
  --region ap-northeast-2 --profile awssec-lab
```

### ⑤ 계정 단위 봉쇄 SCP

계정 전체가 공격자 통제 아래 있다고 판단되면 계정 수준에서 잠급니다. 32.2의 조직 전체 락다운 SCP와 달리 **침해 계정 하나에만 붙이는 표적 정책**입니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ContainCompromisedAccount",
      "Effect": "Deny",
      "NotAction": [
        "ec2:Describe*",
        "ec2:CreateSnapshot*",
        "ec2:CreateTags",
        "iam:Get*",
        "iam:List*",
        "cloudtrail:LookupEvents",
        "logs:Describe*",
        "logs:FilterLogEvents",
        "s3:Get*",
        "s3:List*"
      ],
      "Resource": "*",
      "Condition": {
        "ArnNotLike": {
          "aws:PrincipalArn": "arn:aws:iam::*:role/IncidentResponder"
        }
      }
    }
  ]
}
```

```bash
POLICY_ID=$(aws organizations create-policy \
  --name ContainAccount-111122223333 \
  --type SERVICE_CONTROL_POLICY \
  --description "Incident IR-2026-0906-01 containment" \
  --content file://contain-scp.json \
  --query 'Policy.PolicySummary.Id' --output text --profile awssec-lab)

aws organizations attach-policy \
  --policy-id "$POLICY_ID" --target-id 111122223333 --profile awssec-lab
```

`NotAction`에 조사용 읽기와 스냅샷 생성을 남긴 것이 핵심입니다. **전면 Deny면 우리도 증거를 수집할 수 없습니다.**

> ⚠️ **부작용이 가장 큰 조치입니다.** 해당 계정의 모든 워크로드가 멈춥니다. Lambda 실행 역할·백업 역할·배포 역할처럼 **사람이 만든 서비스 역할이 전부 막히므로 자동화도 함께 정지합니다.** (반대로 **서비스 연결 역할(service-linked role)에는 SCP가 적용되지 않으므로**, 그쪽으로 도는 동작은 살아남아 "일부만 죽은" 혼란스러운 상태가 됩니다.) **32.1에서 지정한 중단 결정권자의 승인 없이 실행하지 마십시오.** SCP는 **관리 계정에는 적용되지 않는다**는 점도 기억하십시오.

### 🔴 이 절의 요약 명령

| # | 조치 | 핵심 CLI | 주된 부작용 |
|---|---|---|---|
| ① | 액세스 키 비활성화 | `iam update-access-key --status Inactive` | 그 키를 쓰던 배치·연동 중단 |
| ② | 역할 세션 무효화 | `iam put-role-policy` + `aws:TokenIssueTime` | 해당 역할의 정상 세션 전부 중단 |
| ③ | 사용자 차단 | `iam delete-login-profile`, `put-user-policy`(Deny) | 서비스 계정이면 서비스 정지 |
| ④ | 인스턴스 격리 | ASG 분리 → 종료 방지 → 격리 SG 교체 | 해당 인스턴스 서비스 이탈 |
| ⑤ | 계정 봉쇄 SCP | `organizations attach-policy` | 계정 전체 워크로드 정지 |

**②를 잊는 조직이 대부분입니다.** 키만 죽이고 세션을 남기면 역할의 최대 세션 지속 시간이 끝날 때까지 공격자가 그대로 활동합니다.

## 33.4 데이터 유출·C2 통신 차단 🔴

> 📖 1판·2판 7장 공통: **"무단 접근 차단의 일환으로 네트워크 통신을 내리지 않았다면, 공격자가 명령·제어 서버로 맺는 연결을 끊거나 진행 중인 데이터 손실을 멈추기 위해 여전히 아웃바운드 통신을 차단해야 할 수 있다."**

서술은 짧지만 요구는 분명합니다. **아웃바운드입니다.** 대부분의 조직은 인바운드 방화벽에만 투자하고 아웃바운드는 `0.0.0.0/0`으로 열어 둡니다(19.6). 그러면 C2도 유출도 막을 방법이 없습니다.

### 차단 지점은 다섯 층이다

유출 경로에 따라 손대는 층이 다릅니다. **잘못된 층을 잠그면 서비스만 죽고 유출은 계속됩니다.**

| 층 | 수단 | 무엇을 막는가 | ⚠️ 부작용 |
|---|---|---|---|
| 인스턴스 | 격리 SG(33.3 ④) | 그 인스턴스의 모든 통신 | 상태 저장이라 기존 연결이 남을 수 있음 |
| 서브넷 | **NACL 광역 Deny** | 서브넷 전체 인·아웃바운드 | 같은 서브넷의 정상 인스턴스도 함께 끊김 |
| DNS | **Route 53 Resolver DNS Firewall** | C2 도메인 이름 해석 | 오탐 시 정상 서비스 장애 |
| AWS API | **엔드포인트 정책, 버킷 정책** | 우리 데이터를 공격자 계정으로 복사 | 정상 크로스 계정 연동 차단 가능 |
| 데이터 | **KMS 키 비활성화** | 암호문 복호화 자체 | **그 키를 쓰는 정상 서비스도 전부 멈춤** |

### ① 서브넷 단위 즉시 차단 — NACL

보안 그룹과 달리 NACL은 상태 비저장이라 **기존 연결에도 즉시 적용됩니다.** 19.4에서 본 대로 규칙 번호가 낮을수록 먼저 평가되므로 1번 자리에 Deny를 꽂습니다.

```bash
NACL=acl-0abc123def4567890

# 인바운드 전체 거부 (규칙 1번 — 다른 어떤 Allow보다 먼저 평가)
aws ec2 create-network-acl-entry \
  --network-acl-id $NACL --rule-number 1 --protocol "-1" \
  --rule-action deny --ingress --cidr-block 0.0.0.0/0 \
  --region ap-northeast-2 --profile awssec-lab

# 아웃바운드 전체 거부 — 유출과 C2를 끊는 쪽이 이것이다
aws ec2 create-network-acl-entry \
  --network-acl-id $NACL --rule-number 1 --protocol "-1" \
  --rule-action deny --egress --cidr-block 0.0.0.0/0 \
  --region ap-northeast-2 --profile awssec-lab
```

IPv6를 쓴다면 `--ipv6-cidr-block ::/0`로 같은 쌍을 추가하십시오. **19.3 ⚠️5의 IPv6 우회는 차단 규칙에서도 똑같이 일어납니다.**

특정 C2 IP만 끊으려면 목적지를 좁힙니다.

```bash
aws ec2 create-network-acl-entry \
  --network-acl-id $NACL --rule-number 5 --protocol "-1" \
  --rule-action deny --egress --cidr-block 203.0.113.77/32 \
  --region ap-northeast-2 --profile awssec-lab
```

> ⚠️ **NACL은 서브넷 전체에 걸립니다.** private-app 서브넷(`10.20.10.0/24`)을 통째로 막으면 그 서브넷의 정상 인스턴스도 전부 죽습니다. **인스턴스 하나가 문제라면 격리 SG가 먼저이고, NACL은 "서브넷 전체가 의심스러울 때" 또는 "SG로 끊었는데 기존 연결이 남아 있을 때"의 수단입니다.**

### ② DNS 층 — C2 도메인 차단

19.6에서 만들어 둔 Route 53 Resolver DNS Firewall 도메인 목록에 **사고 중 확인된 C2 도메인을 추가**합니다. 규칙 그룹을 새로 만들지 않고 기존 목록에 넣는 것이라 즉시 반영됩니다.

```bash
# 사고 중 식별한 C2 도메인을 기존 차단 목록에 추가
aws route53resolver update-firewall-domains \
  --firewall-domain-list-id rslvr-fdl-0123456789abcdef0 \
  --operation ADD \
  --domains "c2.example-malicious.test" "*.exfil.example-malicious.test" \
  --region ap-northeast-2 --profile awssec-lab
```

DNS 차단이 중요한 이유는 **DNS 터널링 유출**(`Trojan:EC2/DNSDataExfiltration`) 때문입니다. 데이터를 서브도메인 이름에 인코딩해 질의로 내보내므로 이그레스 방화벽의 HTTP 규칙에 걸리지 않습니다 — 20.5의 "DNS는 통제되지 않은 이그레스 경로"가 이 뜻입니다.

> ⚠️ **와일드카드 차단은 신중히.** `*.example.com` 형태로 넓게 막으면 그 도메인을 쓰는 정상 SaaS가 함께 끊깁니다. **무엇이 끊길지 목록을 만들어 통보한 뒤에** 하십시오.

### ③ AWS API 층 — 우리 데이터를 남의 계정으로 복사하는 것을 막는다

가장 자주 간과되는 경로입니다. 공격자는 우리 네트워크로 데이터를 내보낼 필요가 없습니다. **우리 자격 증명으로 우리 S3 객체를 자기 계정 버킷에 복사하면 됩니다.** 이 트래픽은 AWS 백본 안에서 일어나 VPC 플로우 로그에도 이그레스 방화벽에도 잡히지 않습니다. 20.3의 엔드포인트 정책을 더 좁힙니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "OnlyOurBucketsDuringIncident",
      "Effect": "Allow",
      "Principal": "*",
      "Action": ["s3:GetObject", "s3:PutObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::shopmini-assets",
        "arn:aws:s3:::shopmini-assets/*",
        "arn:aws:s3:::shopmini-uploads",
        "arn:aws:s3:::shopmini-uploads/*"
      ],
      "Condition": {
        "StringEquals": {
          "aws:PrincipalAccount": "111122223333"
        }
      }
    }
  ]
}
```

```bash
aws ec2 modify-vpc-endpoint \
  --vpc-endpoint-id vpce-0123456789abcdef0 \
  --policy-document file://endpoint-lockdown.json \
  --region ap-northeast-2 --profile awssec-lab
```

버킷 쪽에서도 동시에 잠급니다(20.3의 이중 통제).

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyReadsOutsideOurVpcEndpoint",
      "Effect": "Deny",
      "Principal": "*",
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::shopmini-uploads",
        "arn:aws:s3:::shopmini-uploads/*"
      ],
      "Condition": {
        "StringNotEquals": {
          "aws:SourceVpce": "vpce-0123456789abcdef0"
        },
        "Bool": {
          "aws:ViaAWSService": "false"
        },
        "ArnNotLike": {
          "aws:PrincipalArn": "arn:aws:iam::111122223333:role/IncidentResponder"
        }
      }
    }
  ]
}
```

`aws:ViaAWSService`를 `false`로 한정한 조건이 없으면 복제 같은 **AWS 서비스가 대신 호출하는 정상 경로까지 막힙니다.** 이 한 줄을 빠뜨려 대응 중에 서비스 전체를 내리는 일이 흔합니다. 그리고 이 Deny는 **VPC 밖에서 오는 우리 조사자의 콘솔·CLI 접근도 함께 막으므로**, `IncidentResponder` 역할을 `ArnNotLike`로 예외 처리하지 않으면 스스로 잠깁니다.

계정 전체의 퍼블릭 노출도 함께 봉인합니다.

```bash
aws s3control put-public-access-block \
  --account-id 111122223333 \
  --public-access-block-configuration \
  BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true \
  --profile awssec-lab
```

### ④ 데이터 층 — KMS 키 비활성화 ⚠️

**최후의 수단입니다.** 다른 모든 차단이 실패했다면 **키를 죽여 데이터가 평문이 되지 못하게 합니다.** 이미 밖으로 나간 암호문도 복호화할 수 없습니다.

```bash
aws kms disable-key \
  --key-id alias/shopmini/app \
  --region ap-northeast-2 --profile awssec-lab
```

> ⚠️ **폭발 반경은 그 키가 암호화한 모든 것입니다.** `alias/shopmini/app`으로 암호화된 S3 객체, EBS 볼륨, RDS 스토리지, 시크릿이 전부 접근 불가가 됩니다. 이미 마운트된 볼륨처럼 당분간 동작하는 것도 있어 "부분적으로만 죽는" 혼란스러운 상태가 됩니다. **중단 결정권자 승인 없이 실행하지 마십시오.**

**절대 하지 말아야 할 것: `schedule-key-deletion`.** 비활성화는 되돌릴 수 있지만 삭제는 되돌릴 수 없고, 우리 데이터도 영구히 복구 불가가 됩니다. 사고 중에 쓸 명령은 `disable-key` 하나뿐입니다.

키 정책을 좁혀 **특정 주체만 막는** 방법이 부작용이 훨씬 작으므로 이쪽을 먼저 검토하십시오.

```json
{
  "Sid": "DenyCompromisedPrincipal",
  "Effect": "Deny",
  "Principal": "*",
  "Action": ["kms:Decrypt", "kms:GenerateDataKey*"],
  "Resource": "*",
  "Condition": {
    "ArnLike": {
      "aws:PrincipalArn": "arn:aws:iam::111122223333:role/ShopMiniAppRole"
    }
  }
}
```

### 🔴 반드시 이 순서로 하라

부작용이 작은 것부터 올라갑니다. **한 층을 잠근 뒤 관찰(OODA)로 돌아와 유출이 멈췄는지 확인하고** 다음 층으로 갑니다.

1. **격리 SG 교체** — 인스턴스 하나
2. **DNS Firewall 도메인 추가** — C2 이름 해석 차단
3. **NACL 광역 Deny** — 서브넷 (기존 연결까지 확실히)
4. **엔드포인트 정책 + 버킷 정책** — API 경유 유출
5. **계정 봉쇄 SCP**(33.3 ⑤) — 계정 전체
6. **KMS 키 비활성화** — 최후

각 단계 후 확인할 지표: 플로우 로그의 아웃바운드 바이트, Resolver 쿼리 로그, CloudTrail의 `GetObject`·`CopyObject` 호출량, GuardDuty 신규 결과.

## 33.5 성급한 종료가 증거를 지운다 ⚠️

### 사고 시나리오

새벽 2시, GuardDuty가 `CryptoCurrency:EC2/BitcoinTool.B!DNS`를 알립니다. 당직 엔지니어는 침착하게 판단합니다 — "채굴 인스턴스다. 죽이면 된다." 콘솔에서 종료하고, Auto Scaling이 새 인스턴스를 띄워 서비스가 정상인 것을 확인한 뒤 티켓을 닫습니다.

이틀 뒤 같은 결과가 다시 뜹니다. 조사를 시작하지만 아무것도 없습니다. 악성 프로세스와 복호화된 자격 증명이 있던 **메모리**, 공격자가 도구를 내려받아 둔 **인스턴스 스토어 볼륨**, `DeleteOnTermination=true`(기본값)로 함께 삭제된 **EBS 루트 볼륨** — 전부 사라졌습니다. 남은 것은 CloudTrail과 플로우 로그뿐이라 애플리케이션 계층에서 무슨 취약점이 쓰였는지 알 수 없습니다. **결과: 같은 경로로 다시 들어옵니다.**

### 원인

**첫째, 봉쇄와 증거 보전이 충돌한다는 것을 몰랐습니다.** 원서의 표현대로 **"증거를 파괴하지 않으면서 봉쇄"** 해야 하는데, 종료는 가장 강한 봉쇄이면서 가장 완전한 증거 파괴입니다.

**둘째, 무엇이 휘발성인지 몰랐습니다.**

| 데이터 | 격리 | 중지(stop) | 최대 절전(hibernate) | 종료(terminate) |
|---|---|---|---|---|
| 메모리(RAM) | 유지 | **소멸** | 루트 EBS에 저장 | **소멸** |
| 인스턴스 스토어 | 유지 | **소멸** | **소멸** | **소멸** |
| EBS 볼륨 | 유지 | 유지 | 유지 | `DeleteOnTermination`에 따라 삭제 |
| 실행 중 프로세스·연결 | 유지 | 소멸 | 소멸 | 소멸 |
| CloudTrail·플로우 로그 | 유지 | 유지 | 유지 | 유지(별도 계정) |

**격리 열만 전부 "유지"입니다.** 그래서 격리가 첫 조치입니다. 특히 **인스턴스 스토어는 종료는커녕 중지만 해도 소멸**한다는 점을 기억하십시오.

**셋째, Auto Scaling이 사람 대신 종료했습니다.** 33.3 ④대로, 격리 SG를 붙이는 순간 헬스 체크가 실패하고 ASG가 교체합니다. **선의로 격리했는데 증거를 지우는** 가장 얄궂은 실패입니다.

### 🔴 올바른 순서

> 📖 2판 7장: **"예를 들어 클라우드 환경의 침해된 리눅스 가상 머신에서 메모리와 디스크 포렌식 정보를 수집하는 절차를 원할 수 있다. 그런 절차에는 이를 수행할 정확한 명령들이 담겨야 한다 — 메모리 덤프를 캡처하기 위해 LiME를 실행하고, 덤프의 해시를 생성하고, Volatility로 덤프를 검증하고, 악성 프로그램이 재부팅 전에 뒷정리하는 것을 막기 위해 침해된 머신을 하드 파워오프하고, 디스크의 스냅샷을 뜨는 것."**
>
> **"하드 파워오프"가 메모리 수집보다 나중**이라는 점을 눈여겨보십시오. 정상 종료(graceful shutdown)는 악성코드에 **뒷정리할 기회**를 줍니다.

AWS 명령으로 옮기면 이 순서입니다.

```text
① 격리     — ASG 분리 → 종료 방지 → 격리 SG 교체 (33.3 ④)
② 디스크 스냅샷 — 인스턴스가 살아 있는 상태로 먼저 뜬다
③ 메모리 수집  — SSM으로 덤프 후 포렌식 계정 버킷으로 반출
④ (필요 시) 강제 중지 — stop --force
⑤ 종료      — 조사가 끝나고, 스냅샷 해시 검증이 끝난 뒤에만
```

②가 ③보다 먼저인 것이 AWS 특유의 판단입니다. **스냅샷은 인스턴스를 건드리지 않고 밖에서 뜰 수 있는 유일한 조치**라 실패해도 잃는 것이 없고 가장 빨리 확보됩니다.

```bash
# ② 인스턴스의 모든 볼륨을 한 번에 스냅샷 (부트 볼륨 포함)
aws ec2 create-snapshots \
  --instance-specification InstanceId=$INSTANCE,ExcludeBootVolume=false \
  --description "IR-2026-0906-01 evidence" \
  --copy-tags-from-source volume \
  --tag-specifications 'ResourceType=snapshot,Tags=[{Key=IncidentId,Value=IR-2026-0906-01},{Key=Evidence,Value=true}]' \
  --region ap-northeast-2 --profile awssec-lab

# 포렌식 계정에 볼륨 생성 권한만 공유 (스냅샷을 퍼블릭으로 만들지 않는다)
aws ec2 modify-snapshot-attribute \
  --snapshot-id snap-0123456789abcdef0 \
  --attribute createVolumePermission --operation-type add \
  --user-ids 444455556666 \
  --region ap-northeast-2 --profile awssec-lab
```

> ⚠️ **`modify-snapshot-attribute`에서 `--group-names all`을 쓰지 마십시오.** 스냅샷이 전 세계에 공개됩니다. 3.4 ⑥의 사고 경로를 대응 중에 스스로 만드는 셈입니다.

메모리 수집은 **최대 절전(hibernation)이 사전에 켜져 있었다면** 훨씬 간단합니다. RAM 내용을 암호화된 루트 EBS 볼륨에 기록하므로 스냅샷에 메모리가 함께 담깁니다.

```bash
# 최대 절전이 활성화된 인스턴스에서만 동작한다 (시작 시 설정 필요)
aws ec2 stop-instances --instance-ids $INSTANCE --hibernate \
  --region ap-northeast-2 --profile awssec-lab
```

> 💡 **32.3의 준비 항목에 하나를 더하십시오.** 최대 절전은 **인스턴스 시작 시점에** 활성화되어야 하고, 루트 볼륨 암호화와 볼륨 크기·인스턴스 타입 제약이 따릅니다. 사고 당일에는 켤 수 없습니다. **중요 워크로드의 시작 템플릿에 미리 켜 두면 메모리 확보 난이도가 크게 내려갑니다.** 제약은 사용하는 인스턴스 타입 기준으로 사전 검증하십시오.

최대 절전을 쓸 수 없다면 SSM으로 덤프를 뜹니다.

```bash
aws ssm send-command \
  --instance-ids $INSTANCE \
  --document-name "AWS-RunShellScript" \
  --parameters 'commands=["/opt/forensics/capture-memory.sh s3://shopmini-forensic-evidence/IR-2026-0906-01/"]' \
  --region ap-northeast-2 --profile awssec-lab
```

> ⚠️ **SSM 수집에는 세 가지 대가가 있습니다.** ① 침해된 호스트에서 명령을 실행하므로 **공격자가 그것을 보고** 결과를 위조할 수 있습니다. ② 격리 SG는 아웃바운드가 0이라 SSM 엔드포인트 경로를 예외로 열어야 합니다(20.4의 3개 엔드포인트). ③ 도구 스크립트가 미리 인스턴스에 있어야 합니다. **①은 원리적으로 피할 수 없으므로 메모리 수집은 필수 관문이 아니라 "가능하면 하는 것"입니다.** 스냅샷이 우선입니다.

### Auto Scaling이 증거를 지우는 세 가지 경로

| 경로 | 무슨 일이 일어나는가 | 막는 법 |
|---|---|---|
| 헬스 체크 실패 | 격리 SG로 ALB 헬스 체크가 실패 → 비정상 판정 → 종료·교체 | 격리 **전에** `suspend-processes ReplaceUnhealthy` |
| 스케일 인 | 트래픽이 줄어 축소되면서 하필 침해 인스턴스가 선택됨 | `set-instance-protection --protected-from-scale-in` 또는 ASG에서 분리 |
| 인스턴스 새로 고침 | 배포 파이프라인이 롤링 교체를 진행 | 사고 선언과 동시에 **배포 동결** — 32.2 플레이북에 포함 |

**배포 동결이 플레이북에 없으면, 대응 중에 다른 팀의 정상 배포가 증거를 갈아엎습니다.** 사고 선언 채널에 배포 담당 팀이 포함되어야 하는 이유입니다.

### 언제 종료해도 되는가

**다음 네 가지가 끝나면 종료해도 됩니다.**

- [ ] 모든 연결 볼륨의 스냅샷이 생성되었고, 포렌식 계정에서 볼륨 생성이 확인되었다
- [ ] 스냅샷의 해시(또는 그에 준하는 검증값)가 기록되고 관리 연속성 문서에 남았다(34.2)
- [ ] 메모리 수집을 시도했고, 성공했거나 "불가"로 명시적으로 기록했다
- [ ] 인스턴스 ID·ENI·IAM 역할·태그·시작 시각 등 메타데이터를 별도로 내보냈다

이후 절차 — 해시 검증, 관리 연속성(Chain of Custody), 격리 환경 분석 — 는 **34장**의 몫이고, 침해 인스턴스를 고쳐 쓰지 말고 재구축하라는 원서의 권고는 34.5에서 다룹니다.

### ⚠️ 초기 추정치를 공식 수치처럼 발표하지 말 것

가장 되돌리기 어려운 실수는 기술이 아니라 **잘못된 숫자를 먼저 말한 것**입니다.

**사고 시나리오** — 사고 4시간째, 경영진이 "몇 건입니까"라고 묻습니다. 조사자가 "지금까지 로그로 보면 대략 3만 건"이라고 답합니다. 이 숫자가 그날 저녁 보도자료에 들어갑니다. 사흘 뒤 전체 로그 분석이 끝나고 실제 범위가 **41만 건**으로 확인됩니다.

**원인** — 중간 관찰값과 확정 수치를 구분하지 않았습니다. 초기 숫자는 **아직 열어보지 않은 로그가 있다는 사실**을 반영하지 못합니다. 리전과 계정에 로그가 흩어져 있고 S3 데이터 이벤트를 켜지 않은 버킷이 있을 수 있는 클라우드에서는 특히 그렇습니다.

**🔴 올바른 구성** — 세 가지 규칙으로 고정하십시오.

1. **내부 보고에는 신뢰 수준을 붙입니다.** "현재까지 확인된 최소 3만 건. 미조사 로그 범위 있음. **상향 조정 가능성 높음.**"
2. **외부 발표는 확정된 것과 조사 중인 것을 명시적으로 나눕니다.** "영향 범위는 조사 중이며 확정되는 대로 갱신하겠습니다"는 회피가 아니라 정확한 진술입니다.
3. **숫자를 말할 수 있는 사람을 한 명으로 제한합니다.** 32.1 RACI에서 대외 커뮤니케이션 담당을 지정한 이유입니다.

### 통신 수단 자체가 침해되었을 가능성

침해된 것이 사내 아이덴티티 공급자라면 **대응 논의를 공격자가 읽고 있습니다.** 의심되면 32.1의 대체 수단(별도 계정 메신저, 전화, 개인 단말)으로 즉시 옮기고, **그 사실 자체를 기존 채널에 쓰지 마십시오.**

### 사후 커뮤니케이션

원서가 "홍보 참사"를 언급한 맥락은 **투명성이 결국 싸게 먹힌다**는 것입니다. 최소한 다음을 포함하십시오.

- [ ] 무슨 일이 있었는가 — 기술 세부가 아니라 **영향받은 데이터와 사람** 중심으로
- [ ] 언제 알았고 언제 막았는가 — 타임라인
- [ ] 영향받은 사람이 지금 해야 할 일 — 암호 변경, 결제 수단 모니터링 등 구체적 행동
- [ ] 재발 방지를 위해 무엇을 바꾸는가 — 34.6의 교훈 정리 결과와 연결
- [ ] 문의 창구

**"무엇을 바꾸는가"가 빠진 통지는 신뢰를 회복시키지 못합니다.** 그 답을 만들려면 34장의 사후 검토가 끝나 있어야 합니다.

## 🔴 필수 구성 체크리스트

- [ ] 33.1의 킬 체인–ATT&CK–AWS 매핑 표를 플레이북 첫 장에 배치했다
- [ ] 사고 선언 시각을 타임스탬프로 기록하는 서식이 있다(신고 기한의 기산점)
- [ ] 조치 전 "지금 무엇을 부수는지" 두 줄을 기록하는 서식이 있다
- [ ] 액세스 키는 **삭제가 아니라 비활성화**로 시작하며, 그 전에 `get-access-key-last-used`를 수집한다
- [ ] `aws:TokenIssueTime` 기반 세션 무효화 정책 파일이 **미리 만들어져** 있다
- [ ] 세션 무효화는 **인스턴스 격리 이후**라는 순서가 플레이북에 명시되어 있다
- [ ] 격리 순서(ASG 프로세스 정지 → 타깃 해제 → ASG 분리 → 종료 방지 → SG 교체)가 스크립트화되어 있다
- [ ] EC2 종료 방지가 **Auto Scaling에는 통하지 않는다**는 사실을 대응자 전원이 안다
- [ ] 사고 선언과 동시에 **배포 동결**이 걸리는 절차가 있다
- [ ] 계정 봉쇄 SCP에 조사용 읽기·스냅샷 액션이 `NotAction`으로 남아 있다
- [ ] 아웃바운드 차단 5층이 모두 준비되어 있고, 각 층의 부작용 목록이 있다
- [ ] 버킷 정책의 소스 제한 조건에 `aws:ViaAWSService` 예외가 포함되어 있다
- [ ] 유출 차단용 버킷·엔드포인트 정책에 `IncidentResponder` 예외가 있어 조사자가 스스로 잠기지 않는다
- [ ] KMS는 `disable-key`만 쓰고 `schedule-key-deletion`은 금지어로 지정되어 있다
- [ ] 스냅샷 공유는 `--user-ids`만 쓰고 `--group-names all`은 금지되어 있다
- [ ] 종료 전 4개 관문(스냅샷·해시·메모리 시도 기록·메타데이터) 체크리스트가 있다
- [ ] 통지 대상 7종의 담당자와 기한이 **법무 검토를 거쳐** 확정되어 있다(이 책의 수치가 아니라)
- [ ] 대외 숫자를 말할 수 있는 사람이 한 명으로 지정되어 있다
- [ ] 아이덴티티 침해 시 대응 채널을 옮기는 절차가 있다
