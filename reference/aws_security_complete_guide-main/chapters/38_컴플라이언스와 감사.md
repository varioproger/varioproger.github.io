4장에서 우리는 **"우리에게 무엇이 걸리는가"** 를 한 페이지로 확정했습니다. 5장부터 37장까지는 그 요구를 **실제 통제로 구현**했습니다. 남은 것은 하나입니다 — **그것을 제3자에게 증명하는 일**.

4.5의 결론으로 인용했던 원서 문장에는 뒷부분이 하나 더 있습니다. 이 장은 그 뒷부분에서 시작합니다.

> 📖 *Practical Cloud Security* 1판·2판 2장. **"아주 거칠게 일반화하자면, 컴플라이언스는 제3자에게 당신의 보안을 증명하는 일이며 — 시스템과 데이터를 실제로 안전하게 만들어두었다면 그 일은 훨씬 쉬워진다. 이 책의 정보는 안전해지는 데 도움이 되겠지만, 시스템을 안전하게 만든 **뒤에 완료해야 할 추가적인 컴플라이언스 작업과 문서화**가 있을 것이다."**

이 장은 그 "추가 작업과 문서화"입니다. 시작 전에 하나만 정리합시다. 클라우드에서는 **증명해야 할 대상 자체가 둘로 나뉩니다.** 데이터센터 출입 통제나 하이퍼바이저 격리는 **우리가 증명할 수 없고 증명할 필요도 없습니다** — AWS의 제3자 감사 보고서로 갈음합니다. 반면 IAM 권한, 암호화 키 통제, 로그 보존은 **AWS 보고서에 한 줄도 나오지 않습니다.** 2장의 공동 책임 모델이 증거의 책임까지 나눕니다. 38.1이 앞쪽 절반을, 38.2 이후가 뒤쪽 절반을 다룹니다.

## 38.1 AWS Artifact로 규정 준수 보고서 받기 🧪

### Artifact가 무엇인가

> 📖 *AWS Security Cookbook* 10장 「Using AWS Artifact for compliance reports」: **"AWS Artifact는 AWS의 컴플라이언스 보고서에 접근하기 위한 무료 셀프서비스 포털이다. AWS Artifact는 AWS의 보안·컴플라이언스 보고서와 선택된 온라인 계약(agreements)에 접근하는 데 사용할 수 있다."**

핵심 단어가 셋입니다. **무료 · 셀프서비스 · 계약**. 티켓을 열거나 영업 담당자를 거칠 필요가 없습니다. 감사인이 "AWS의 SOC 2 Type II 보고서를 주십시오"라고 하면 그 자리에서 콘솔을 열어 내려받으면 됩니다. 원서의 절차는 지금도 그대로입니다.

> 📖 같은 절: **"1. 콘솔에서 AWS Artifact 서비스로 간다. 2. 왼쪽 사이드바에서 Reports를 클릭해 이용 가능한 AWS Artifact 보고서를 본다. 3. 왼쪽 사이드바에서 Agreements를 클릭해 계정 계약과 조직(Organization) 계약을 보고 승인한다. (…) Organization의 관리 계정에서 Organization agreements 탭을 클릭하면 관리 계정과 조직 내 모든 멤버 계정의 계약을 관리할 수 있다. 4. Get this artifact를 클릭해 문서를 내려받는다. 5. Terms and conditions 화면이 나타나면, 해당 아티팩트의 약관을 읽고 동의한다는 체크박스를 선택한 뒤 Accept and download를 클릭한다."**

3번과 5번이 실무에서 중요합니다. 3번은 **조직 단위 계약 관리** — HIPAA BAA처럼 계정마다 체결해야 하는 계약을 관리 계정에서 조직 전체에 한 번에 적용할 수 있다는 뜻입니다. 멤버 계정을 늘릴 때마다 잊고 지나가는 항목이 바로 이것입니다. 5번은 다음 항목에서 따로 다룹니다.

### 어떤 보고서를 받을 수 있는가

> 📖 원서는 당시 이용 가능한 보고서 중 **일부**를 이렇게 나열합니다. **"APRA CPG 234 Workbook, BioPhorum IT Control Implementation Responsibilities, BSP 982 Workbook, FedRAMP Partner Package, Global Financial Services Regulatory Principles, Government of Canada (GC) Partner Package, IRAP PROTECTED Package, PCI DSS Attestation of Compliance (AOC) and Responsibility Summary, Quality Management System Overview, Resiliency of the AWS Region in India."**

> 💡 **원서 이후 변경** — 보고서 목록은 계속 늘어나고 갱신됩니다. 원서가 든 목록에는 없지만 현재 Artifact에서 통상 확인할 수 있는 주요 문서군은 **AWS SOC 1/SOC 2/SOC 3 보고서, ISO/IEC 인증서(27001·27017·27018 계열 등), PCI DSS AOC와 책임 요약(Responsibility Summary), 각국 정부·산업 패키지**입니다. **정확한 현재 목록과 각 보고서의 대상 기간·범위 리전은 반드시 콘솔에서 직접 확인하십시오.** 이 책에 목록을 적어두면 그 자체가 곧 낡습니다.

감사 대응에서 실제로 손이 가는 것은 대개 다음 넷입니다.

| 문서 | 감사에서 쓰이는 자리 | 특징 |
|---|---|---|
| **SOC 1** | 재무보고 내부통제(ICFR) 감사. 회계법인이 요구 | 재무제표 관련 통제 중심 |
| **SOC 2 Type II** | 보안 실사와 고객사 벤더 심사에서 가장 자주 요구 | **일정 기간의 운영 효과성**까지 검증 |
| **SOC 3** | 공개 배포 가능한 요약본 | 상세 통제 내역 없음. **NDA 없이 전달 가능** |
| **PCI DSS AOC + 책임 요약** | PCI 심사에서 "AWS 측 범위" 증빙 | 책임 요약이 **어느 요구사항을 AWS가 이미 이행했는지** 알려줌 |

마지막 줄이 PCI 대응 시간을 가장 크게 줄여줍니다. **책임 요약(Responsibility Summary)** 은 AOC와 함께 제공되는 문서로, 요구사항별 책임 소재(AWS 측 / 고객 측 / 공동)를 정리해 줍니다. 우리가 증거를 만들어야 할 항목이 여기서 자동으로 걸러집니다. 다만 **문서 구성과 표기 방식은 개정판마다 다르므로 내려받은 문서의 실제 목차를 확인**하십시오.

### ⚠️ NDA — 받은 보고서를 어디까지 쓸 수 있는가

Artifact 다운로드 시 뜨는 약관 동의 화면(원서 절차 5번)은 형식적인 절차가 아닙니다. **AWS의 SOC 1·SOC 2 보고서는 기밀 문서로 취급되며, 다운로드 시 동의하는 약관이 제3자 재배포를 제한합니다.**

실무에서 사고가 나는 지점은 셋으로 정해져 있습니다. 고객사 보안 담당자가 "AWS SOC 2 보고서를 메일로 보내달라"고 해서 **그대로 첨부해 보내는 것**, 제안서·RFP 부속 문서로 PDF를 통째로 붙이는 것, 사내 위키에 올려 전사 공개하는 것. 셋 다 통제되지 않은 재배포입니다.

**올바른 대응은 셋 중 하나입니다.** ① 공개 배포가 가능한 **SOC 3**를 전달한다. ② 상대방이 AWS 계정 보유자라면 **"Artifact에서 직접 내려받으시라"** 고 안내한다. ③ 상대방과 NDA가 이미 체결되어 있고 AWS 약관이 그 범위를 허용하는지 확인한 뒤 전달한다.

> ⚠️ 약관 문구와 허용 범위는 보고서마다 다르고 개정됩니다. **다운로드 화면에 표시되는 약관 원문을 그때그때 확인**하고, 외부 전달이 필요하면 법무 검토를 거치십시오. "예전에 보내도 괜찮았다"는 근거가 되지 않습니다.

### 🧪 CLI로 받기

> 💡 **원서 이후 변경** — 원서 집필 시점의 Artifact는 콘솔 전용이었습니다. 이후 API/CLI가 추가되어 **보고서 목록 조회와 다운로드를 자동화**할 수 있습니다. 다만 약관 동의는 사라지지 않았고, `get-report`를 호출하려면 **먼저 약관 토큰을 받아야** 합니다. 자동화하더라도 약관에 동의한 사실 자체는 남습니다.

```bash
# 1) 이용 가능한 보고서 목록
aws artifact list-reports \
  --query 'reports[].{id:id,name:name,series:series,category:category,period:periodEnd}' \
  --output table \
  --profile awssec-lab --region ap-northeast-2

# 2) 특정 보고서의 메타데이터 (대상 기간·범위 확인)
aws artifact get-report-metadata \
  --report-id report-EXAMPLE1234567890 \
  --profile awssec-lab --region ap-northeast-2

# 3) 약관 문서와 토큰 받기 — 이 단계를 건너뛸 수 없다
aws artifact get-term-for-report \
  --report-id report-EXAMPLE1234567890 \
  --query '{terms:documentPresignedUrl,token:termToken}' \
  --profile awssec-lab --region ap-northeast-2

# 4) 토큰을 제시하고 보고서 다운로드 URL 받기
aws artifact get-report \
  --report-id report-EXAMPLE1234567890 \
  --term-token EXAMPLE-TERM-TOKEN \
  --query documentPresignedUrl --output text \
  --profile awssec-lab --region ap-northeast-2
```

3단계에서 받은 `documentPresignedUrl`이 **약관 원문**입니다. 자동화 파이프라인에 넣더라도 이 문서를 사람이 최소 1회 읽고 사내 배포 규칙을 정한 뒤에 돌리십시오. 계정에 체결되어 있는 계약 목록은 `aws artifact list-customer-agreements`로 확인합니다.

### 공동 책임 모델 관점 — 보고서로 갈음되는 것과 되지 않는 것

Artifact 보고서를 받아 놓고 가장 흔히 하는 오해가 이것입니다. **"AWS가 PCI DSS 인증을 받았으니 우리 서비스도 PCI 준수다."** 아닙니다. AWS 인증은 **AWS가 책임지는 계층**에 대한 것이고, 그 위에 우리가 올린 것은 인증 범위 밖입니다.

| 감사인의 질문 | 누가 답하는가 | 증거 |
|---|---|---|
| 데이터센터 물리 출입 통제는? | **AWS** | Artifact SOC 2 / ISO 27001 인증서 |
| 하이퍼바이저 격리·매체 폐기 절차는? | **AWS** | Artifact SOC 2 |
| 관리형 서비스의 패치 적용은? | **AWS**(관리형 계층에 한해) | Artifact SOC 2 + 서비스별 공동 책임 문서 |
| EC2 게스트 OS 패치는? | **고객** | Inspector 스캔 결과, 패치 이력 (25~26장) |
| 관리자 계정 목록과 접근 검토 기록은? | **고객** | IAM 자격 증명 보고서, 분기 접근 검토 결과 (9장) |
| 저장 데이터 암호화 키를 누가 통제하는가? | **고객** | KMS 키 정책, CloudTrail `Decrypt` 호출 주체 (13장) |
| 로그를 1년 이상 위·변조 없이 보관하는가? | **고객** | 객체 잠금 설정, 로그 파일 검증 결과 (29장) |
| 변경 관리 절차가 문서화·운영되는가? | **고객** | PR 승인 이력, Config 구성 이력 (28장) |

> 📖 *Practical Cloud Security* 2판 1장은 이 오해가 얼마나 뿌리 깊은지 지적합니다. **"상당한 진전이 있었음에도, 공동 책임 모델은 여전히 자주 오해된다. 많은 IT 의사결정자들은 퍼블릭 클라우드 제공자가 자신들이 제공하는 클라우드 서비스뿐 아니라 **클라우드 안의 고객 애플리케이션과 데이터까지** 보호할 책임이 있다고 여전히 믿는다. 클라우드 제공자와의 계약서를 읽어보면, 이는 사실이 아님을 알게 될 것이다!"**

**감사 준비의 첫 작업은 이 표를 우리 서비스에 맞게 다시 그리는 것**입니다. 왼쪽 칸이 AWS면 Artifact 보고서 파일명을 적고, 고객이면 **누가·어떤 명령으로·언제 증거를 뽑는지**를 적습니다. 후자의 목록이 곧 38.5의 증거 세트가 됩니다.

## 38.2 AWS Audit Manager

> 💡 **원서 범위 밖** — Audit Manager는 근거 원서 3권 어디에도 등장하지 않습니다(원서 집필 시점 이후 서비스). 아래는 원서 인용이 아니라 AWS 서비스 구조에 대한 설명이며, 프레임워크 목록과 세부 기능은 갱신이 잦으므로 도입 전 콘솔에서 현재 상태를 확인하십시오.

### 무엇을 자동화하는가

37.7의 Config 적합성 팩까지 갖추면 "지금 규정을 지키고 있는가"는 상시로 알 수 있습니다. 그런데 감사는 다른 것을 묻습니다. **"지난 6개월 동안 계속 지켰다는 것을, 통제 항목별로 정리된 문서로 제출하라."** 이 간극 — 상시 평가 결과를 **감사 항목 단위의 증거 묶음**으로 재조립하는 일 — 을 자동화하는 것이 Audit Manager이고, 구조는 네 층입니다.

| 층 | 의미 | 실무 대응 |
|---|---|---|
| **프레임워크(Framework)** | 통제 집합의 템플릿. AWS 제공 표준 프레임워크 또는 직접 만든 커스텀 | 표준을 복제해 **우리 범위에 맞게 통제를 빼고 더한다** |
| **평가(Assessment)** | 프레임워크 + 범위(계정·리전·서비스) + 담당자(소유자·감사인) | 감사 주기 단위로 하나씩 생성 |
| **통제(Control)** | 개별 요구 항목. 각각에 데이터 소스가 매핑 | 자동 수집 불가 항목은 **수동 증거 업로드** |
| **증거(Evidence)** | 일자별 폴더로 자동 축적 | 마지막에 **평가 보고서**로 묶어 PDF/파일로 출력 |

증거 수집원은 넷입니다.

| 증거 소스 | 수집되는 것 | 대응하는 감사 질문 |
|---|---|---|
| **AWS Config** | 규칙 평가 결과(준수/미준수)와 판정 시각 | "그 통제가 상시 작동했는가" |
| **AWS Security Hub** | 보안 표준 컨트롤의 통과/실패 결과 | "벤치마크 대비 상태는" |
| **AWS CloudTrail** | 지정한 API 활동 기록 | "누가 무엇을 했는가" |
| **AWS API 호출 스냅샷** | 리소스 구성의 시점 스냅샷 | "그 시점 설정이 이랬는가" |
| (수동 업로드) | 정책 문서, 교육 기록, 계약서, 물리 보안 증빙 | 기술 통제로 답할 수 없는 항목 |

마지막 줄이 중요합니다. **Audit Manager는 기술 통제만 자동으로 모읍니다.** 인사·물리·계약·교육에 해당하는 통제는 사람이 파일을 올려야 하고, 프레임워크에 따라 이런 항목이 **적지 않은 비중**을 차지합니다. 도입 전에 우리가 받을 프레임워크의 통제 목록을 훑어 **자동 수집 가능 항목과 수동 업로드 항목의 실제 비율**을 세어 보십시오 — 이 비율이 곧 투자 대비 효과입니다.

### 🧪 CLI 흐름

```bash
# 0) 서비스 활성화 (조직 위임 관리자 지정 가능)
```

| 상황 | 판단 | 이유 |
|---|---|---|
| 외부 인증(SOC 2·ISO·PCI)을 **정기적으로** 받는다 | **유용** | 증거 수집이 매 주기 반복 노동. 자동화 효과가 큼 |

> ⚠️ **비용과 증거량.** Audit Manager는 평가된 리소스 수에 비례해 과금되며, 증거는 매일 쌓입니다. 범위를 계정·서비스 단위로 좁히지 않고 "전부"로 켜 두면 **읽지도 않을 증거에 매달 비용을 쓰게 됩니다.** 평가 하나를 좁게 만들어 한 달 돌려보고 실제 증거량과 비용을 확인한 뒤 범위를 넓히십시오.

## 38.3 프레임워크별 구현 가이드

4.4에서 만든 4열 번역표(규제 문구 → 통제 목표 → AWS 설정 → 검증)를 프레임워크 단위로 확장합니다. 이번 표의 네 칸은 **대표 요구사항 → 본서 참조 장 → AWS 구성 → 증거 수집 방법**입니다. 목적이 다릅니다. 4장의 표는 **설계용**이었고, 이 표는 **감사 대응용** — 감사인이 항목을 물었을 때 어느 명령으로 무엇을 뽑아 낼지가 오른쪽 끝에 적혀 있어야 합니다.

> ⚠️ **조항 번호를 쓰지 않는 이유.** PCI DSS는 v4 계열로 넘어오면서 요구사항 번호와 문구가 크게 개정되었고, ISO/IEC 27001은 2022년 개정에서 Annex A 통제가 재편되었으며, GDPR과 국내 법령도 조문·부속 고시가 계속 바뀝니다. 아래 표는 **요구사항의 성격**으로 서술합니다. **실제 심사 대응 문서에는 반드시 적용 시점의 표준 원문에서 조항 번호를 직접 확인해 적으십시오.** 이 책의 번호를 옮겨 적는 것이 가장 위험한 사용법입니다.

### PCI DSS

|---|---|---|---|

위 표의 마지막 두 줄이 **AWS 서비스만으로는 채워지지 않는 항목**입니다. 4.3에서 인용한 원서의 두 문장 — 독립적인 제3자 침투 테스트가 PCI DSS에서 요구된다는 것(2판 5장), 파일 무결성 모니터링이 명시적으로 요구되며 감사인에 따라 Windows 레지스트리 변경까지 포함하도록 요구할 수 있다는 것(2판 7장) — 이 여기서 **증거 요구**로 바뀝니다. 침투 테스트는 보고서만이 아니라 **지적 사항의 조치 완료 증적**까지, FIM은 도구 설치 증빙이 아니라 **알람 발생과 처리 기록**까지 요구됩니다.

4.5에서 인용한 WAF 관련 문장(2판 7장, "WAF는 PCI DSS 인증에서 수동 코드 리뷰 대신 사용되는 경우가 많다")도 같은 방식으로 작동합니다. WAF를 코드 리뷰의 대체로 신고했다면 **WAF 로그를 보존·분석하고 있다는 증적이 추가 증거로 붙습니다.** 23장의 WAF 로깅을 켜 두지 않았다면 이 항목에서 막힙니다.

4.3에서 인용한 원서의 HIPAA 설명(1·2판 2장)은 "PHI를 목록에 포함시키고 보호하라"는 두 동사로 요약됩니다. 감사에서 이 둘은 각각 **데이터 인벤토리 산출물**과 **암호화 준수 현황**으로 제출됩니다. 목록화 없이 암호화만 증명하면 "빠진 PHI가 없다는 것은 어떻게 아는가"에서 막힙니다.

| 대표 요구사항(성격) | 참조 장 | AWS 구성 | 증거 수집 |
|---|---|---|---|
| 개인데이터를 **목록화(catalog)** | 12 | 태깅 전략 + Macie 자동 발견 | 데이터 인벤토리, Macie 결과, 처리 활동 기록 |
| **보호(protect)** | 13·15·16 | 고객 관리형 KMS 키, 퍼블릭 차단, 최소 권한 | Config 준수 현황, 버킷 정책 |

| 침해 통지 | 32·33 | 사고 등급 판정 기준과 통지 절차 | 플레이북, 통지 판단 근거 기록 |

표의 위 세 줄은 4.3에서 인용한 원서 문장(1·2판 2장)의 세 동사 **목록화·보호·접근 감사**를 그대로 옮긴 것입니다. 감사 관점에서 셋의 난이도는 제각각입니다. 보호는 Config 준수율 한 장으로 끝나지만, **목록화는 "빠진 것이 없다"를 증명해야 하고 접근 감사는 "실제로 들여다봤다"를 증명해야 합니다.** 전자는 Macie 커버리지와 태깅 미준수 목록으로, 후자는 질의 실행 기록과 알람 처리 이력으로 답합니다.

GDPR 대응에서 기술적으로 가장 어려운 항목은 **삭제권과 로그 보존의 충돌**입니다. 로그에 남은 개인 식별자를 지우면 로그 무결성 체계(29.3)가 깨지고, 안 지우면 삭제권 이행이 불완전합니다. 실무 해법은 **애초에 로그에 식별자를 넣지 않는 것**입니다 — 로그에는 내부 대체 키만 남기고, 대체 키↔개인 매핑 테이블만 삭제하면 로그를 건드리지 않고 재식별 불가 상태를 만들 수 있습니다(4.2의 "암호 삭제"와 같은 발상). 설계 단계에서 정해야 하고, 사후에 바꾸기는 매우 어렵습니다.

> ⚠️ 침해 통지 기한(감독기구 통지는 통상 인지 후 72시간 이내로 알려져 있음)과 그 예외, 정보주체 통지 요건은 **적용 국가의 감독기구 지침과 법무 검토로 확정**하십시오. 이 책의 서술을 근거로 절차를 확정하지 마십시오.

| 공급자 관계 관리 | 27·38.1 | AWS·SaaS 벤더 보고서 수집·평가 | Artifact 보고서, 벤더 실사 기록 |
| 내부 심사와 경영 검토, 시정 조치 | 39 | 정기 리뷰 운영 | 심사 보고서, 부적합·시정 조치 대장 |

ISO 27001의 특징은 **개별 통제보다 순환(PDCA)의 증명**을 본다는 것입니다. Config 규칙이 초록색인 것보다, **미준수가 발견되었고 → 등록되었고 → 조치되었고 → 재발 방지가 반영되었다**는 흐름이 남아 있는 편이 강한 증거입니다. 위반이 0건인 기록은 오히려 "점검을 안 한 것 아니냐"는 질문을 부릅니다.

### SOC 2

| 대표 요구사항(성격) | 참조 장 | AWS 구성 | 증거 수집 |
|---|---|---|---|
| 논리적 접근 통제(공통기준) | 6~9 | IAM Identity Center, MFA 강제, 권한 경계 | 자격 증명 보고서, 접근 검토, 입·퇴사 연동 기록 |
| **변경 관리** | 28 | IaC + PR 승인 + 파이프라인 게이트 | PR 승인 이력, 배포 로그, Config 구성 이력 |
| 시스템 운영·모니터링 | 29~31 | 중앙 로깅, 알람, 탐지 서비스 | 알람 처리 이력, MTTD/MTTR (39.2) |
| 위험 평가 | 4 | 리스크 등록부 | 등록부와 갱신 이력 |
| 사고 대응 | 32~35 | 플레이북, 훈련 | 훈련 기록, 실사고 타임라인 |
| 가용성(선택 범주) | 17 | 백업·복원 테스트 | 복원 테스트 결과 |
| 기밀성(선택 범주) | 12·13·15 | 분류 등급별 통제 | 분류 매트릭스, 암호화 준수율 |

4.3에서 인용한 원서 문장(2판 5장, "문서화된 변경 관리 프로세스는 SOC 2, ISO 27001, PCI DSS를 포함한 여러 산업·규제 인증에서 요구된다")은 SOC 2 표에서 특히 무겁게 걸립니다. **변경 관리는 프레임워크를 넘나드는 최대 공약수이면서, 동시에 증거를 사후에 만들어 낼 수 없는 몇 안 되는 항목**이기 때문입니다. 접근 권한은 지금 정리해 스냅샷을 뜰 수 있지만, 6개월 전 배포의 승인 기록은 그때 남지 않았으면 영원히 없습니다. 28장의 파이프라인 승인 기록이 그 증거를 자동으로 만들어 줍니다.

SOC 2 Type II는 **"선언한 통제가 기간 내내 작동했음"** 을 봅니다. 그래서 감사인은 기간 중 무작위 시점을 골라 표본을 요구합니다(38.5의 샘플링). **감사 직전에 통제를 켜는 방식이 가장 확실하게 실패하는 프레임워크**입니다.

### 다섯 프레임워크의 공통 코어

위 다섯 표를 겹쳐 보면 **어느 프레임워크에서든 반복되는 통제 여덟 개**가 남습니다. 규제가 하나 더 붙어도 새로 만들 것은 많지 않다는 뜻입니다.

| 공통 코어 | 참조 장 | 한 번 만들면 재사용되는 증거 |
|---|---|---|
| 자산 인벤토리와 데이터 분류 | 12 | 인벤토리 스냅샷, 분류 매트릭스 |
| 개별 식별과 최소 권한, 정기 접근 검토 | 6~9 | 자격 증명 보고서, 검토 회차 기록 |
| 저장·전송 암호화와 키 통제 | 13~16·23 | Config 암호화 준수 현황, 키 정책 |
| 중앙 로깅·무결성·보존 | 29 | 검증 결과, 객체 잠금, 보존 설정 |
| 모니터링·알람과 처리 | 30~31 | 알람 통계와 처리 이력 |
| 취약점 관리와 조치 | 25~26 | 커버리지·MTTR 지표 |
| 변경 관리 | 28 | PR 승인·배포 기록 |
| 사고 대응과 훈련 | 32~35 | 플레이북, 훈련·실사고 기록 |

**프레임워크가 늘 때 늘어나는 것은 통제가 아니라 문서와 표본 요구입니다.** 코어를 제대로 만들어 두면 두 번째 인증부터는 대응 비용이 급격히 떨어집니다.

## 38.4 국내 규제 대응

> 💡 **원서 범위 밖** — 이 절 전체가 근거 원서 3권에 없는 내용입니다. 국내 규제는 법률·시행령·고시·인증기준이 각각 별도로 개정되며 주기가 짧습니다. **아래는 아키텍처에 영향을 주는 축을 정리한 것이지 법적 조언이 아닙니다.** 세부 기준·기간·대상 요건·제재 수준은 반드시 **적용 시점의 최신 법령과 고시 원문을 확인**하고 법무·컴플라이언스 부서의 검토를 받으십시오. 이 책에는 조문 번호와 수치 기준을 의도적으로 적지 않습니다.

### ISMS-P — 무엇을 인증하는가

**ISMS-P**(정보보호 및 개인정보보호 관리체계 인증)는 국내에서 운영되는 인증 제도로, 정보보호 관리체계만 다루는 **ISMS**와, 개인정보 보호까지 포함하는 **ISMS-P** 두 갈래로 신청할 수 있습니다. 인증기준은 크게 세 영역으로 구성됩니다.

| 영역 | 성격 | AWS 관점에서 준비할 것 |
|---|---|---|
| **관리체계 수립 및 운영** | 정책·조직·위험관리·사후관리의 순환 | 4장 리스크 등록부, 39장 정기 리뷰 체계 |
| **보호대책 요구사항** | 접근통제·암호화·운영보안·사고대응 등 기술·관리 통제 | 6~35장의 구현 결과 + 그 운영 증거 |
| **개인정보 처리 단계별 요구사항** | 수집·이용·제공·파기 각 단계의 적법성 | 12장 인벤토리·보존·파기, 개인정보 흐름도 |

세부 인증기준 항목 수와 의무 인증 대상 요건(매출·이용자 규모 등)은 고시 개정에 따라 달라지므로 **최신 고시로 확인**해야 합니다.

구조적으로 ISO 27001과 매우 닮았습니다. **위험 평가 → 통제 선택 → 운영 → 점검 → 개선**의 순환을 증명하라는 점이 같습니다. 다만 심사 방식에 국내 특유의 요소가 있습니다.

- **현장 심사 비중이 큽니다.** 심사원이 담당자 앞에서 콘솔을 열어 설정을 직접 확인하는 경우가 흔합니다. 화면을 보여줄 수 있는 **읽기 전용 심사용 역할**을 미리 만들어 두십시오(`ReadOnlyAccess` + `SecurityAudit` 조합에 세션 기록).
- **관리체계 문서의 실재성**을 봅니다. 정책 문서만 있고 시행 기록이 없으면 결함입니다. AWS 쪽 증거(Config 이력, CloudTrail)가 문서의 시행 증거로 직접 쓰입니다.
- **개인정보 흐름도**를 요구합니다. 3장의 데이터 흐름도와 12장의 인벤토리를 개인정보 관점으로 다시 그린 것이 그대로 산출물이 됩니다.

### 개인정보보호법 — 클라우드에서 특히 걸리는 세 축

4.3에서 안전성 확보 조치의 네 항목(저장 암호화·전송 암호화·접속기록 보관과 점검·접근 권한 관리)을 이미 아키텍처 요구로 번역했습니다. 여기서는 **클라우드를 쓸 때 추가로 발생하는** 세 축만 다룹니다.

**① 개인정보 처리 위탁**

클라우드 사용은 통상 **처리 위탁** 구조로 정리됩니다. 위탁자에게는 수탁자에 대한 **관리·감독 의무**가 따르며, 위탁 사실을 개인정보 처리방침 등에 공개해야 합니다. 실무에서 이것이 만드는 작업은 셋입니다.

- **위탁 현황 대장** — AWS뿐 아니라 로그 분석 SaaS, 메일 발송 서비스, CDN, 모니터링 도구까지 전부. 27장의 공급망 인벤토리와 같은 목록입니다.
- **수탁자 관리·감독 증거** — AWS에 대해서는 38.1의 Artifact 보고서 수집·검토 기록이 이 자리에 들어갑니다. **받아만 두면 안 되고 "검토했다"는 기록이 있어야 합니다.**
- **재위탁 파악** — 우리가 쓰는 SaaS가 다시 AWS를 쓰는 구조라면 그 사슬이 드러나야 합니다.

**② 국외 이전**

개인정보를 국외로 이전할 때는 법이 정한 근거(동의 또는 그 밖에 법에서 정한 요건)를 갖춰야 하고, 고지 사항이 정해져 있습니다. AWS에서 이것은 곧 **리전 선택 문제**로 번역됩니다 — 38.6에서 이어집니다.

> ⚠️ **"서울 리전만 쓰면 국외 이전이 아니다"는 단정은 위험합니다.** 리전 안에 리소스를 두었더라도, 지원 요청에 개인정보를 첨부하거나 해외 인력이 운영 접근을 하거나 글로벌 서비스가 데이터를 다른 위치에서 처리하면 별도 검토가 필요할 수 있습니다. **판단은 법무에 맡기고, 엔지니어는 "데이터와 접근이 실제로 어디에 있는지"를 정확히 그려 제출하는 것까지가 역할입니다.**

**③ 접속기록의 보관과 점검**

4.3에서 보존 기간을 다뤘습니다. 여기서 덧붙일 것은 **"점검"** 쪽입니다. 법이 요구하는 것은 보관만이 아니라 **주기적 점검**이고, 심사에서는 **점검을 수행한 기록 자체**를 봅니다. 30장의 알람과 Athena 질의를 돌리고 있더라도, **누가 언제 무엇을 확인했고 이상 여부가 무엇이었는지**를 남기지 않으면 증거가 없습니다. 점검 결과 보고서를 월 1회 자동 생성해 S3에 적재하는 것이 가장 값싼 해법입니다.

### CSAP — 공공 부문의 추가 관문

**클라우드 보안인증(CSAP)** 은 공공 부문에 클라우드 서비스를 제공하려는 사업자를 대상으로 하는 국내 인증 제도입니다. 핵심은 두 가지입니다.

- **인증받은 서비스만 공공에 공급할 수 있습니다.** 규제가 통제 수준이 아니라 **어떤 인프라를 쓸 수 있는지**를 직접 결정합니다.
- **IaaS·SaaS·DaaS 등 유형별로 평가 기준이 다르고**, 등급을 나누어 요구 수준을 차등화하는 방향으로 제도가 개편되어 왔습니다.

> ⚠️ CSAP는 **제도 개편이 특히 잦은 영역**입니다. 등급 구분, 망분리 요구 수준, 물리적 분리 요건, 인증 유효기간, 그리고 **어떤 CSP가 어떤 등급으로 인증을 보유하고 있는지**는 시점에 따라 달라집니다. 공공 사업 참여를 검토한다면 **발주처가 요구하는 등급**과 **대상 CSP·서비스의 현재 인증 현황**을 그때 직접 확인하십시오. 과거 프로젝트의 판단을 재사용하지 마십시오.

아키텍처 관점에서 미리 대비할 수 있는 것은 **환경 분리**입니다. 공공 사업 가능성이 있다면 민간용 워크로드와 공공용 워크로드를 **처음부터 별도 계정·별도 OU**로 갈라 두십시오(36.4). 나중에 인증 범위를 정의할 때, 범위가 계정 경계와 일치하면 심사 난이도와 비용이 크게 낮아집니다. 하나의 계정 안에 섞여 있으면 "이 리소스는 범위 안, 저 리소스는 밖"을 증명하는 데만 몇 주가 듭니다.

### 국내 규제 → AWS 구현 요약

| 규제 축 | AWS 구현 포인트 | 증거 |
|---|---|---|
| 안전성 확보조치(암호화) | 고객 관리형 KMS 키, RDS/S3/EBS 암호화, TLS 강제 | Config 암호화 규칙 준수 현황 |
| 접속기록 보관·위변조 방지 | 로그 계정 분리 + 객체 잠금 + 로그 파일 검증 | 잠금 설정, `validate-logs` 결과 |
| 접속기록 **점검** | 월간 점검 보고서 자동 생성·적재 | 점검 보고서 파일 + 수행자·일시 |
| 접근 권한 관리 | IAM Identity Center, 권한 부여·회수 기록 | 자격 증명 보고서, 접근 검토 대장 |

| 공공(CSAP) | 계정·OU 수준 환경 분리 | 계정 배치도, 범위 정의서 |

## 38.5 감사 대응 실무

### 감사인이 요구하는 표준 증거 세트

프레임워크가 무엇이든 **처음 2주에 요구되는 것은 거의 같습니다.** 미리 만들어 두면 감사 초반의 왕복이 사라집니다.

| 증거 세트 | 감사인이 확인하려는 것 | AWS에서 뽑는 방법 |
|---|---|---|
| **① 계정·범위 목록** | 심사 범위가 무엇인지 | `organizations list-accounts`, OU 배치도, 범위 정의서 |
| **② 권한 목록** | 누가 무엇에 접근 가능한가 | IAM 자격 증명 보고서, `get-account-authorization-details`, Identity Center 할당 내역 |
| **③ 변경 이력** | 무단 변경이 없었는가 | Config 구성 이력, CloudTrail 변경 이벤트, PR 승인 기록 |
| **④ 로그 보존 증명** | 로그가 기간 내내 온전했는가 | `validate-logs` 결과, 객체 잠금 설정, 수명주기 규칙 |
| **⑤ 취약점 조치 이력** | 발견한 것을 고쳤는가 | Inspector·Security Hub 결과 추이, 조치 티켓, MTTR |
| **⑥ 사고 대응 기록** | 사고를 절차대로 처리했는가 | 플레이북, 실사고 타임라인, 훈련 기록 |

여섯 개 중 **①~⑤는 자동으로 뽑을 수 있고, ⑥만 사람이 씁니다.** 자동화 가능한 다섯을 매번 손으로 모으는 조직이 놀랄 만큼 많습니다.

### 🧪 증거 자동 수집 스크립트

29.3에서 만든 로그 검증, 37.7의 Config 준수 현황, Security Hub 결과를 **하나의 날짜별 번들**로 묶습니다. 핵심은 마지막 줄의 **해시 매니페스트** — 제출한 파일이 제출 이후 바뀌지 않았음을 보이는 장치입니다.

```bash
#!/usr/bin/env bash
# collect-audit-evidence.sh — 감사 1차 증거 번들 수집
# 실행 위치: 보안 도구 계정(444455556666)의 감사 전용 읽기 역할
set -euo pipefail

PROFILE="${AWS_PROFILE:-awssec-lab}"
REGION="${AWS_REGION:-ap-northeast-2}"
LOG_BUCKET="shopmini-org-cloudtrail-logs"
TRAIL_ARN="arn:aws:cloudtrail:ap-northeast-2:123456789012:trail/shopmini-org-trail"
OUT="evidence/$(date -u +%Y%m%dT%H%M%SZ)"
AWS="aws --profile ${PROFILE} --region ${REGION} --output json"
mkdir -p "${OUT}"

echo "[1/7] 계정·범위 목록"
${AWS} organizations list-accounts > "${OUT}/01-accounts.json"

echo "[2/7] IAM 자격 증명 보고서"
${AWS} iam generate-credential-report > /dev/null
sleep 15
${AWS} iam get-credential-report --query Content --output text \
  | base64 --decode > "${OUT}/02-credential-report.csv"
${AWS} iam get-account-summary        > "${OUT}/03-account-summary.json"
${AWS} iam get-account-authorization-details > "${OUT}/04-iam-authz-details.json"

echo "[3/7] Config 준수 현황과 스냅샷"
${AWS} configservice describe-compliance-by-config-rule    > "${OUT}/05-config-compliance.json"
${AWS} configservice get-compliance-summary-by-config-rule > "${OUT}/06-config-summary.json"
CHANNEL=$(${AWS} configservice describe-delivery-channels \
  --query 'DeliveryChannels[0].name' --output text)
${AWS} configservice deliver-config-snapshot \
  --delivery-channel-name "${CHANNEL}" > "${OUT}/07-config-snapshot-id.json"

echo "[4/7] Security Hub 미준수 결과"
${AWS} securityhub get-enabled-standards > "${OUT}/08-securityhub-standards.json"
${AWS} securityhub get-findings \
  --filters '{"RecordState":[{"Value":"ACTIVE","Comparison":"EQUALS"}],
              "ComplianceStatus":[{"Value":"FAILED","Comparison":"EQUALS"}]}' \
  --max-items 1000 > "${OUT}/09-securityhub-failed.json"

echo "[5/7] CloudTrail 상태와 로그 파일 무결성"
${AWS} cloudtrail get-trail-status --name "${TRAIL_ARN}" > "${OUT}/10-trail-status.json"
aws --profile "${PROFILE}" --region "${REGION}" cloudtrail validate-logs \
  --trail-arn "${TRAIL_ARN}" \
  --start-time "$(date -u -d '90 days ago' +%Y-%m-%dT%H:%M:%SZ)" \
  > "${OUT}/11-trail-validation.txt"

echo "[6/7] 로그 보존 증명"
${AWS} s3api get-object-lock-configuration --bucket "${LOG_BUCKET}" \
  > "${OUT}/12-object-lock.json"
${AWS} s3api get-bucket-lifecycle-configuration --bucket "${LOG_BUCKET}" \
  > "${OUT}/13-lifecycle.json"

echo "[7/7] 매니페스트 생성"
( cd "${OUT}" && sha256sum ./* > MANIFEST.sha256 )
echo "완료: ${OUT}"
```

**운영 규칙 넷.**

1. **호출마다 계정이 다릅니다.** `organizations list-accounts`는 관리 계정(또는 위임된 계정)에서, `securityhub`·`configservice`는 위임 관리자 계정에서, `iam` 계열은 **평가 대상 계정마다** 실행해야 합니다. 위 스크립트는 한 계정분 골격이므로, 실제로는 계정 목록을 돌며 크로스 계정 역할을 `assume-role`해서 반복하는 바깥 루프를 씌우십시오(36.7).
2. **월 1회 자동 실행**하고 결과를 별도 버킷에 적재하십시오. 감사 시점에 처음 돌리면 "이 값이 원래 이랬는지" 비교할 기준선이 없습니다. 12개월치가 쌓여 있으면 **추세 자체가 강력한 증거**가 됩니다.
3. **수집 역할의 권한은 조회로 한정**하십시오. `generate-credential-report`처럼 동사가 쓰기처럼 보여도 리소스를 바꾸지는 않습니다. 다만 `deliver-config-snapshot`은 **전송 채널 버킷에 파일을 쓰는 동작**이므로, 이것만은 별도 권한으로 분리하거나 스냅샷을 쓰지 않고 `select-resource-config` 질의로 대체하는 편이 깔끔합니다. 수집 역할에 리소스 변경 권한을 주면 **그 역할 자체가 감사 지적 사항**이 됩니다.
4. **매니페스트를 별도로 보관**하십시오. 번들과 같은 곳에만 두면 둘 다 바꿀 수 있어 의미가 없습니다. 해시 목록은 로그 계정(`777788889999`)의 잠긴 버킷으로 보내는 것이 좋습니다.

### 샘플링 대응

감사인은 전수를 보지 않습니다. **모집단을 정의하고 표본을 고릅니다.** 여기서 실무의 승패가 갈립니다.

| 감사인의 표본 요구 | 준비되지 않은 조직 | 준비된 조직 |
|---|---|---|
| "지난 6개월 중 임의의 25건의 프로덕션 배포에 대해 승인 기록을 보여달라" | 배포 목록을 손으로 만드느라 3일 | 파이프라인 실행 이력 ↔ PR 승인 자동 대사 결과 제출 |
| "신규 입사자 10명의 권한 부여 근거를 보여달라" | 티켓과 IAM을 눈으로 대조 | Identity Center 할당 이력 + 승인 티켓 ID 링크 |
| "임의의 날짜 3일치 로그가 존재함을 보여달라" | 버킷을 뒤짐 | 번들의 `validate-logs` 결과에서 해당 일자 확인 |
| "미준수 5건이 어떻게 처리되었는지" | 처리는 했으나 기록이 없음 | Security Hub 워크플로 상태 변경 이력 + 티켓 |

**모집단을 우리가 먼저 정의해 제출하는 것**이 요령입니다. 감사인이 "프로덕션 배포"를 어떻게 셀지 정하기 전에, 우리가 "프로덕션 배포 = 이 파이프라인의 성공 실행"이라고 정의하고 그 목록을 내면, 표본은 그 목록에서 뽑힙니다. 정의를 감사인에게 맡기면 우리가 기록을 갖고 있지 않은 모집단이 정의될 수 있습니다.

### 예외와 보상 통제 문서화

모든 항목을 100% 만족시키는 조직은 없습니다. 감사에서 문제가 되는 것은 **예외가 있다는 사실이 아니라 예외가 관리되지 않는다는 사실**입니다. 예외는 다음 일곱 칸으로 관리하십시오.

| 칸 | 내용 | 나쁜 예 |
|---|---|---|
| **예외 ID·대상** | 어느 통제의, 어느 리소스에 대한 예외인가 | "일부 서버" |
| **사유** | 왜 표준 통제를 적용할 수 없는가 | "어려워서" |
| **리스크 평가** | 4.1의 가능성×영향으로 산정한 잔여 리스크 | 미기재 |
| **보상 통제** | 대신 무엇으로 막는가 | "모니터링 강화"(무엇을 어떻게인지 없음) |
| **승인자** | 리스크를 수용한 사람 — **직급이 리스크 크기에 맞아야** | 담당 엔지니어 |
| **만료일** | 언제까지인가 — **무기한 예외는 예외가 아니라 정책 변경** | 공란 |
| **재검토 이력** | 만료 전 재평가 기록 | 없음 |

가장 자주 비는 칸이 **만료일**과 **보상 통제의 구체성**입니다. "레거시 시스템이라 TLS 1.2를 강제할 수 없다"는 예외라면, 보상 통제는 "모니터링 강화"가 아니라 **"해당 엔드포인트는 특정 소스 IP에서만 접근 가능하도록 SG로 제한하고, SG 변경 시 알람이 발생하며, 2026년 12월 31일까지 애플리케이션을 교체한다"** 여야 하고, 그 SG 규칙과 알람의 존재 증거가 함께 붙어야 합니다.

> ⚠️ **예외 대장을 감추지 마십시오.** 감사인이 예외 대장의 존재를 직접 물었을 때 "없다"고 답한 뒤 심사 중에 예외가 발견되는 것이, 처음부터 관리된 예외 20건을 제출하는 것보다 훨씬 나쁜 결과를 냅니다. 관리되는 예외는 성숙도의 증거이고, 숨겨진 예외는 관리체계 부재의 증거입니다.

## 38.6 데이터 주권과 리전 선택 ⚠️

> 💡 **원서 범위 밖** — 근거 원서 3권은 데이터 주권과 리전 선택을 다루지 않습니다. 다만 GDPR을 소개하며 **"전 세계 어디에 데이터가 있든"** 적용될 수 있다고 짚고, ITAR에 대해 **"그런 서비스는 일부 클라우드 제공자에게서 이용할 수 있으며 미국 인력만이 관리한다"**(1판·2판 2장)고 씁니다. 데이터의 **위치**만이 아니라 **누가 운영에 접근하는가**까지 규제 대상이 될 수 있다는 뜻입니다.

### 사고 시나리오

**시나리오 A — 백업이 국경을 넘었다.**
개인정보를 처리하는 RDS는 `ap-northeast-2`에 있었고, 리전 제한 SCP도 걸려 있었습니다. 그런데 DR 담당자가 AWS Backup 계획에 **교차 리전 복사 규칙**을 추가했습니다. 목적지는 `us-west-2`. SCP는 이 작업을 막지 못했습니다 — **복사 작업 자체는 허용된 리전에서 시작되고, `aws:RequestedRegion`은 API 호출을 받는 리전을 가리키기 때문**입니다. 6개월 뒤 개인정보 국외 이전 실태 점검에서 백업본이 발견됐고, 아무도 그 사실을 몰랐습니다.

**시나리오 B — 로그가 먼저 나갔다.**
중앙 SIEM을 도입하면서 CloudWatch Logs 구독 필터로 로그를 본사(해외) 계정의 Kinesis 스트림으로 흘려보냈습니다. 로그에는 사용자 ID와 IP, 일부 요청 파라미터가 담겨 있었습니다. **로그도 개인정보일 수 있다**는 사실이 검토 대상에서 빠져 있었습니다.

**시나리오 C — "우리는 서울만 씁니다"가 사실이 아니었다.**
콘솔의 리전 선택기는 항상 서울이었습니다. 그런데 CloudFront 접근 로그의 대상 버킷은 다른 리전에 있었고, Route 53 쿼리 로그는 `us-east-1`의 로그 그룹으로 갔습니다. **글로벌 서비스는 리전 선택기와 무관하게 동작합니다.**

### 원인 — 리전 이탈은 "생성"이 아니라 "복제"에서 일어난다

세 시나리오의 공통 구조는 하나입니다. **리소스를 어느 리전에 만드는가는 통제되고 있었지만, 데이터가 어디로 흘러 나가는가는 통제되지 않았습니다.**

37.2의 리전 제한 SCP는 **"허용되지 않은 리전에서 API를 호출하는 것"** 을 막습니다. 이는 강력하지만 다음 경로들은 잡지 못합니다.

| 이탈 경로 | 왜 SCP로 안 막히는가 | 점검 방법 |
|---|---|---|
| S3 교차 리전 복제(CRR) | 복제 설정 API는 **허용 리전에서** 호출된다 | `aws s3api get-bucket-replication --bucket <이름>` |
| AWS Backup 교차 리전 복사 | 백업 계획의 `CopyActions` 목적지가 다른 리전 | `aws backup get-backup-plan --backup-plan-id <id>` |
| CloudWatch Logs 구독 필터 | 목적지가 다른 리전·계정의 스트림 | `aws logs describe-subscription-filters --log-group-name <이름>` |
| DynamoDB 글로벌 테이블 | 복제본 리전이 테이블 속성 | `aws dynamodb describe-table --table-name <이름> --query 'Table.Replicas'` |
| ECR 레지스트리 복제 | 레지스트리 수준 설정 | `aws ecr describe-registry --query replicationConfiguration` |
| KMS 다중 리전 키 | 복제본 키가 다른 리전에 존재 | `aws kms describe-key --key-id <id> --query 'KeyMetadata.MultiRegion'` |
| 스냅샷·AMI 수동 복사 | 대상 리전에서 호출되지만 SCP가 없는 계정이면 통과 | `describe-snapshots` / `describe-images`의 소유·복사 이력 |
| **글로벌 서비스의 로그 목적지** | 애초에 리전 개념 밖 | 아래 표 참조 |

> ⚠️ 위 경로별로 **SCP가 실제로 차단하는지 여부는 서비스와 정책 작성 방식에 따라 다릅니다.** "막힐 것"이라고 가정하지 말고 **시험 계정에서 한 번씩 실제로 시도해 보고 결과를 기록**하십시오. 그 시험 기록 자체가 감사 증거가 됩니다.

**글로벌 서비스의 데이터 위치**는 별도로 확인해야 합니다.

| 서비스 | 성격 | 데이터 위치 관점의 주의점 |
|---|---|---|
| **IAM / Organizations** | 글로벌(엔드포인트 `us-east-1` 계열) | 사용자·역할 메타데이터는 리전 고정 대상이 아님. **자격 증명 자체가 개인정보 판단 대상이 될 수 있음** |
| **CloudFront** | 글로벌 엣지 | 콘텐츠가 전 세계 엣지에 캐시됨. 민감 콘텐츠는 **캐시 금지 + 지리적 제한** 검토 |
| **Route 53** | 글로벌 | 쿼리 로그의 목적지 로그 그룹 리전을 확인 |
| **WAF(CloudFront 스코프)** | 글로벌 | 로그 목적지 설정 위치가 리전 WAF와 다름 |
| **Artifact / Billing / Support** | 글로벌 | **지원 케이스 첨부 파일**에 개인정보를 넣지 않는 규칙 필요 |
| **Shield Advanced / Health** | 글로벌 | 알림 연동 대상 리전 확인 |

### 올바른 구성

**① 리전 선택 기준을 문서로 고정한다.** 감사에서 "왜 이 리전인가"에 답할 수 있어야 합니다.

| 기준 | 판단 내용 |
|---|---|
| **법적 요구** | 데이터 소재 요구가 있는가. 국외 이전 근거를 갖출 수 있는가 |
| **지연 시간** | 주 사용자 위치 |
| **서비스 가용성** | 필요한 서비스·기능이 그 리전에 있는가 (없으면 다른 리전으로 새는 원인이 됨) |
| **DR 요구와의 충돌** | 교차 리전 DR이 필요한데 국외 이전이 금지되면 **같은 국가 내 대안**을 찾거나 DR 전략을 바꿔야 함 |
| **인증 범위** | CSAP 등 인증 대상 인프라가 특정 리전·존으로 한정되는가 |

시나리오 A의 근본 원인은 이 표의 네 번째 줄을 **DR 담당자와 컴플라이언스 담당자가 따로 판단**한 것입니다. 국외 이전이 금지된 데이터에 대해 교차 리전 DR을 요구하면, 답은 "몰래 복사"가 아니라 **RPO/RTO를 재협상하거나 AZ 다중화로 대체하는 것**입니다.

**② 예방은 37.2의 SCP로, 탐지는 이탈 경로 점검으로 이중화한다.** SCP 자체는 37.2에서 다뤘으므로 여기서는 **SCP가 놓치는 부분만 Config로 덮습니다.** S3 복제 설정, 백업 계획의 복사 규칙, 구독 필터 목적지처럼 **"설정 값 안에 리전이 들어 있는" 항목**은 사용자 지정 Config 규칙(Lambda 기반)으로 상시 평가하는 것이 유일하게 확실한 방법입니다.

**③ 분기 1회 리전 이탈 점검을 정례화한다.** 위 표의 CLI를 스크립트로 묶어 38.5의 증거 번들에 포함시키십시오. 점검 자체가 국외 이전 관리·감독의 증거가 됩니다.

**④ 데이터 흐름도에 국경선을 그린다.** 3장의 신뢰 경계 다이어그램에 **국가 경계선**을 하나 더 그으십시오. 선을 넘는 화살표마다 근거(동의·계약·법적 근거)와 담당자를 적습니다. 이 그림 한 장이 국외 이전 관련 질의의 8할에 답합니다.

**⑤ 사람의 접근도 데이터 위치다.** 원서가 ITAR에서 짚은 "미국 인력만이 관리한다"는 제약이 그 예입니다. 해외 개발팀이 운영 콘솔에 접근한다면 데이터가 물리적으로 서울에 있어도 **접근 경로는 국경을 넘습니다.** 9장의 페더레이션 설계에서 접근 주체의 소재를 조건으로 걸 수 있는지, 그것이 규제상 필요한지 확인하십시오.
