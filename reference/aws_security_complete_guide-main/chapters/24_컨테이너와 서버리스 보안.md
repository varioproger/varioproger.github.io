> 📖 *Practical Cloud Security* 2판 3장 「Cloud Asset Management and Protection」: **"네이티브 컨테이너는 일반적으로 VM보다 훨씬 자주 생성되고 파괴된다. 그 말은 컨테이너 자체보다 컨테이너 이미지를 인벤토리하는 것이 더 합리적이라는 뜻이다."**

> 💡 **원서 범위 밖 보강** — 근거 원서 3권은 컨테이너·서버리스를 **개념 수준**(자산 유형, 스캐너, 네트워크 정책)에서만 다룹니다. **서비스별 구현은 원서 범위 밖의 보강**임을 각 절에 명시합니다.

## 24.1 컨테이너 보안의 4C 모델

컨테이너 보안의 정리 틀이 **4C** — 바깥에서 안으로 **Cloud → Cluster → Container → Code** 네 겹입니다. 바깥 겹이 뚫리면 안쪽 겹의 통제는 대부분 무의미해집니다(1.2의 심층 방어).

이 모델이 유용한 이유는 **겹마다 책임 주체와 도구가 다르기 때문**입니다. 같은 "컨테이너 보안"이라는 말 아래 클러스터 운영자, 플랫폼 팀, 앱 개발자가 서로 다른 것을 이야기하다 아무도 담당하지 않는 칸이 생깁니다.

| 겹 | 이 겹에서 지키는 것 | AWS 통제 수단 | 담당 | 본서 절 |
|---|---|---|---|---|
| **Cloud** | 계정 경계, VPC·서브넷, IAM, KMS, 로깅 | 계정 분리·SCP, 서브넷 티어링, 보안 그룹, VPC 엔드포인트, CloudTrail | 클라우드 플랫폼 팀 | 4·7·18·19·20장 |
| **Cluster** | 컨트롤 플레인 접근, 인가, 노드, 클러스터 내부 통신 | EKS 액세스 항목·RBAC, 엔드포인트 접근 제어, 컨트롤 플레인 로깅, 네트워크 정책, ECS 클러스터 IAM | 클러스터 운영 팀 | 24.3·24.4 |
| **Container** | 이미지 내용물, 실행 컨텍스트, 런타임 행위 | ECR 스캔·태그 불변성·서명, `securityContext`, 읽기 전용 루트 FS, GuardDuty Runtime Monitoring | 플랫폼 + 앱 팀 공동 | 24.2·24.5 |
| **Code** | 애플리케이션 취약점, 의존성, 시크릿 취급 | SAST/SCA, SBOM, Secrets Manager, 최소 권한 역할 | 애플리케이션 팀 | 11·26·27장 |

### 4C와 공동 책임선의 관계

2.2의 책임선 이동 위에 4C를 겹치면 **"AWS가 어느 겹까지 맡아주는가"** 가 선택지가 됩니다.

| 실행 방식 | Cloud | Cluster | Container | Code |
|---|---|---|---|---|
| EC2에 직접 Docker | 나 | **나 전부** | 나 | 나 |
| ECS on EC2 | 나 | 컨트롤 플레인은 AWS, **노드·에이전트는 나** | 나 | 나 |
| ECS on Fargate | 나 | **AWS** | 나 | 나 |
| EKS (관리형 노드 그룹) | 나 | **API 서버는 AWS, 노드·kubelet·애드온·RBAC는 나** | 나 | 나 |
| EKS on Fargate | 나 | API 서버 AWS, **노드 없음** | 나 | 나 |
| Lambda | 나 | **해당 없음** | 런타임은 AWS, **의존성은 나** | 나 |

여기서 반복 확인할 한 가지. **어떤 방식을 골라도 Container 겹의 "이미지 내용물"과 Code 겹은 100% 내 책임입니다.** Fargate로 옮겨도 Lambda로 옮겨도, 내가 넣은 라이브러리의 CVE는 내가 고쳐야 합니다(2.3).

### 왜 컨테이너를 유일한 신뢰 경계로 삼으면 안 되는가

Cluster 겹을 소홀히 하고 Container 겹만 조이는 조직이 많습니다. 원서는 이 발상 자체를 경고합니다.

> 📖 *Practical Cloud Security* 2판 3장 「Container Attacks」: **"VM을 돌리는 하이퍼바이저는 공격 표면이 매우 작은 반면, 모든 컨테이너가 공유하는 커널은 훨씬 큰 공격 표면을 갖는다. (…) 이 시스템 콜 중 하나의 취약점이 한 컨테이너에서 실행 중인 코드로 하여금 시스템 전체에 접근할 수 있게 만들 수도 있다. (…) 보안 요구 수준이 크게 다른 컴포넌트들 사이에서 **컨테이너를 유일한 신뢰 경계로 삼지 않도록** 주의해야 한다."**

원서는 같은 곳에서 seccomp로 시스템 콜을 제한하는 것, 그리고 **Firecracker처럼 VM 수준 격리와 컨테이너의 배포 용이성을 결합한 하이브리드** 방식을 완화책으로 듭니다.

AWS로 옮기면, **Fargate는 태스크마다 전용 커널(Firecracker microVM)에서 실행**되어 커널 공유 위험을 없앱니다. 반대로 ECS on EC2나 EKS 관리형 노드에서는 **한 노드 위 파드들이 커널을 공유**합니다.

**설계 규칙**: 신뢰 수준이 다른 워크로드는 컨테이너가 아니라 **노드 그룹 → 클러스터 → 계정** 순으로 나눕니다(1.4 폭발 반경).

## 24.2 이미지 보안 🔴

> 💡 **원서 범위 밖 보강** — 최소 이미지·불변성·스캐닝의 **원칙**은 원서 3·5장에 근거하지만, ECR의 구체적 기능(태그 불변성, 향상 스캔, 리포지토리 정책, 서명)은 원서 범위 밖입니다.

이미지는 이 장에서 유일하게 **배포 전에 완전히 통제할 수 있는 대상**입니다.

### 🔴 반드시 이렇게 구성하라 — 이미지 6원칙

**① 최소 베이스 이미지를 쓴다.** `ubuntu:latest`가 아니라 distroless, alpine, Amazon Linux 2023 최소 이미지에서 시작합니다.

> 📖 *Practical Cloud Security* 2판 5장 「Vulnerability Management」: **"컨테이너의 장점 하나는, 최소 컨테이너 이미지에서 시작해 애플리케이션이 컨테이너 안에서 동작하는 데 필요한 것만 설치하는 경우가 많다는 점이다. 이 과정 자체가 컨테이너를 기본적으로 하드닝한다."**

**안 하면**: 앱과 무관한 `curl`, 패키지 매니저, 셸이 남아, 원격 명령 실행이 생기면 공격자가 이미지 안의 도구로 다음 단계를 진행합니다. CVE 목록도 수십 배가 되어 스캔 결과가 소음이 됩니다.

**② 루트로 실행하지 않는다.** Dockerfile에 `USER`를 명시하고 오케스트레이터에서도 비루트를 강제합니다.

```dockerfile
# 멀티스테이지: 빌드 도구는 최종 이미지에 남기지 않는다
FROM public.ecr.aws/docker/library/golang:1.22 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /out/shopmini-app ./cmd/app

FROM public.ecr.aws/docker/library/alpine:3.20
RUN addgroup -g 10001 app && adduser -u 10001 -G app -S app
COPY --from=build /out/shopmini-app /usr/local/bin/shopmini-app
USER 10001:10001
EXPOSE 8443
ENTRYPOINT ["/usr/local/bin/shopmini-app"]
```

**안 하면**: 컨테이너 내부 UID 0은 호스트 UID 0과 같아, 커널 취약점이나 볼륨 마운트 실수와 결합하면 노드 탈취로 이어집니다. 숫자 UID를 쓰는 것은 `runAsNonRoot` 검사가 UID로 동작하기 때문입니다.

**③ 이미지에 시크릿을 넣지 않는다.** `ENV DB_PASSWORD=...`, `ARG`로 넘긴 토큰, `COPY`한 `.env`는 **레이어에 영구히 남고** 나중 레이어에서 지워도 꺼낼 수 있습니다. 시크릿은 11장의 경로로 **실행 시점에** 주입합니다(24.3·24.6).

**④ 태그 불변성.** **⑤ 푸시 시 스캔 + 지속 스캔.** **⑥ SBOM 생성과 서명**(27장) — 아래에서 이어집니다.

### ⚠️ 태그 불변성 — `:latest`가 만드는 사고

**사고 시나리오.** 롤백을 위해 `shopmini-app:v2.4.1`을 다시 배포했더니 장애가 재현됐습니다. 사흘 전 누군가 같은 태그로 다른 커밋을 푸시했고 ECR이 받아들인 것입니다. **스캔을 통과한 이미지와 실제 배포된 이미지가 다릅니다.**

**원인.** 태그는 **가변 포인터**이고 이미지의 진짜 신원은 다이제스트(`sha256:...`)입니다. 태그가 움직이면 "스캔 통과 → 서명 → 배포" 사슬이 끊깁니다.

> 📖 *Practical Cloud Security* 2판 3장: 네이티브 컨테이너 모델의 조건으로 **"컨테이너는 불변(immutable)이다. (…) 실행 중인 컨테이너를 업데이트하는 대신, 오래된 컨테이너를 파괴하고 갱신된 코드로 새 컨테이너를 만든다."** 를 듭니다.

**올바른 구성.**

```bash
# ① 리포지토리 태그 불변성 활성화 — 같은 태그 재푸시를 거부
aws ecr put-image-tag-mutability \
  --repository-name shopmini-app \
  --image-tag-mutability IMMUTABLE \
  --profile awssec-lab --region ap-northeast-2

# ② 푸시 시 스캔 활성화
aws ecr put-image-scanning-configuration \
  --repository-name shopmini-app \
  --image-scanning-configuration scanOnPush=true \
  --profile awssec-lab --region ap-northeast-2
```

**배포 매니페스트에는 다이제스트를 쓰는 것이 가장 강합니다.**

```
# 약함 — 언제든 다른 것을 가리킬 수 있다
image: 111122223333.dkr.ecr.ap-northeast-2.amazonaws.com/shopmini-app:latest

# 보통 — 태그 불변성이 켜져 있어야만 안전하다
image: 111122223333.dkr.ecr.ap-northeast-2.amazonaws.com/shopmini-app:v2.4.1

# 강함 — 내용이 곧 신원이다
image: 111122223333.dkr.ecr.ap-northeast-2.amazonaws.com/shopmini-app@sha256:9f2c...c1
```

### ECR 이미지 스캔 — 기본과 향상

원서는 컨테이너 스캐너의 두 접근법을 정리합니다.

> 📖 *Practical Cloud Security* 2판 5장 「Container Scanners」: **"첫 번째 접근법은 컨테이너 이미지를 분해해 취약점을 찾는 스캐너를 쓰는 것이다. (…) 취약한 이미지를 식별한 뒤 모든 실행 중인 컨테이너에 대한 인벤토리 정보가 충분히 좋아야 취약한 것을 전부 교체할 수 있다는 단점이 있다. (…) 두 번째 접근법은 각 컨테이너 호스트에 에이전트를 두고 그 시스템의 컨테이너를 스캔해 보고하게 하는 것이다."**

같은 5장은 **"컨테이너가 많으면, VM에서처럼 CPU를 몇 퍼센트 쓰는 무거운 취약점 관리 도구를 모든 컨테이너에 넣을 수는 없다"** 고도 지적합니다. ECR의 두 스캔 유형은 첫 번째 접근법의 두 단계 구현입니다.

| 구분 | 기본 스캔(Basic) | 향상 스캔(Enhanced) |
|---|---|---|
| 엔진 | ECR 자체 (OS 패키지 CVE) | **Amazon Inspector** (26.3) |
| 대상 | OS 패키지만 | OS 패키지 + **애플리케이션 언어 패키지**(Java, Python, Node.js, Go 등) |
| 시점 | 푸시 시(설정 시) / 수동 | 푸시 시 + **지속 재스캔** — 새 CVE 공개 시 기존 이미지에 소급 |
| 결과 위치 | ECR 콘솔·API | Inspector 대시보드 + **Security Hub** 연동 |
| 과금 | 무료 | 스캔한 이미지 수 기준 유료 |

향상 스캔의 핵심 가치는 **소급 재스캔** — 지난달 통과한 이미지가 오늘 공개된 CVE로 취약해지면 알려줍니다. 다만 원서가 지적한 교체의 어려움은 남으므로 **어느 서비스가 어떤 다이제스트를 쓰는지 인벤토리**가 필요합니다.

```bash
# 레지스트리 전체에 향상 스캔 적용 (모든 리포지토리)
aws ecr put-registry-scanning-configuration \
  --scan-type ENHANCED \
  --rules '[{"scanFrequency":"CONTINUOUS_SCAN","repositoryFilters":[{"filter":"*","filterType":"WILDCARD"}]}]' \
  --profile awssec-lab --region ap-northeast-2
```

두 번째 접근법은 AWS에서 GuardDuty Runtime Monitoring이 담당합니다(24.5, 31장).

> 📖 *Practical Cloud Security* 2판 5장의 도구 목록: **"Amazon Inspector는 (…) 에이전트 기반 스캐너이며, 컨테이너·서버리스 스캐너이기도 하다."** — Lambda 스캔(24.6)까지 같은 서비스가 커버합니다.

### 레지스트리 접근 정책

ECR은 **리포지토리 정책**(리소스 기반)과 IAM 자격 증명 정책을 함께 씁니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowProdAndDevPullOnly",
      "Effect": "Allow",
      "Principal": {
        "AWS": [
          "arn:aws:iam::111122223333:root",
          "arn:aws:iam::555555555555:root"
        ]
      },
      "Action": [
        "ecr:BatchCheckLayerAvailability",
        "ecr:GetDownloadUrlForLayer",
        "ecr:BatchGetImage"
      ]
    },
    {
      "Sid": "AllowBuildPipelinePush",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::444455556666:role/shopmini-build-pipeline"
      },
      "Action": [
        "ecr:PutImage",
        "ecr:InitiateLayerUpload",
        "ecr:UploadLayerPart",
        "ecr:CompleteLayerUpload",
        "ecr:BatchCheckLayerAvailability"
      ]
    }
  ]
}
```

⚠️ **함정 셋.** ① `ecr:GetAuthorizationToken`은 레지스트리 수준 액션이라 **리포지토리 정책에 쓸 수 없고** 당기는 쪽의 IAM 정책에 있어야 합니다. ② 크로스 계정은 **양쪽 모두 허용해야** 성립합니다(7장). ③ `Principal: "*"` 는 프라이빗 리포지토리를 사실상 공개합니다 — Config 규칙으로 잡습니다.

### 이미지 서명과 검증

태그 불변성은 "이 이미지가 우리 파이프라인에서 나왔다"까지는 보장하지 못합니다. **AWS Signer**로 Notary Project 형식 서명을 붙이고 승인 컨트롤러나 배포 게이트에서 검증합니다. 서명은 **검증을 강제하지 않으면 장식**입니다(27.5).

## 24.3 ECS 보안

> 💡 **원서 범위 밖 보강** — 이 절 전체는 원서 범위 밖입니다. 24.1·24.2에서 인용한 원칙(불변성, 최소 권한, 컨테이너를 유일 신뢰 경계로 삼지 않기)의 ECS 구현입니다.

### ⚠️ 태스크 역할 vs 태스크 실행 역할 — 가장 흔한 혼동

**사고 시나리오.** ShopMini 팀이 `shopmini-uploads` 접근 오류를 만나 **태스크 실행 역할**에 S3 권한을 추가했더니 동작했습니다. 6개월 뒤 같은 클러스터의 12개 태스크 정의가 모두 그 실행 역할을 재사용하고 있었습니다. **12개 전부가 사용자 업로드 버킷을 읽을 수 있는 상태**입니다.

**원인.** 두 역할의 사용 주체가 완전히 다릅니다.

| | 태스크 역할 (`taskRoleArn`) | 태스크 실행 역할 (`executionRoleArn`) |
|---|---|---|
| **누가 쓰는가** | 컨테이너 **안의 애플리케이션 코드** | 컨테이너 **바깥의 ECS 에이전트/Fargate 인프라** |
| **무엇을 하는가** | S3 읽기, DynamoDB 쓰기, SQS 수신 등 앱의 비즈니스 로직 | ECR 이미지 당기기, CloudWatch Logs 스트림 생성, `secrets` 필드 값 해석 |
| **언제 쓰이는가** | 태스크가 도는 내내 | **태스크 시작 시점** |
| **자격 증명 경로** | 태스크 메타데이터 엔드포인트(`AWS_CONTAINER_CREDENTIALS_RELATIVE_URI`) | 컨테이너에 노출되지 않음 |
| **공유해도 되는가** | 아니오 — **태스크 정의마다 분리** | 관리형 정책 수준이면 공유 가능 |

핵심은 **실행 역할의 권한을 앱 코드가 직접 쓸 수는 없지만 그 역할이 가져온 결과물(이미지, 시크릿 값)은 코드에 도달한다**는 점입니다. 실행 역할에 앱 권한을 넣으면 그것이 클러스터 공용 권한이 됩니다(8.4).

**올바른 구성.** 실행 역할은 `AmazonECSTaskExecutionRolePolicy` + **이 태스크가 참조하는 시크릿 ARN에 한정된** `secretsmanager:GetSecretValue`/`ssm:GetParameters`/`kms:Decrypt`. 태스크 역할은 **태스크 정의 1개당 1개**, 앱이 실제 호출하는 API만.

### 태스크 정의 — 안전한 기본형

```json
{
  "family": "shopmini-app",
  "networkMode": "awsvpc",
  "requiresCompatibilities": ["FARGATE"],
  "cpu": "512",
  "memory": "1024",
  "executionRoleArn": "arn:aws:iam::111122223333:role/shopmini-app-exec",
  "taskRoleArn": "arn:aws:iam::111122223333:role/shopmini-app-task",
  "containerDefinitions": [
    {
      "name": "app",
      "image": "111122223333.dkr.ecr.ap-northeast-2.amazonaws.com/shopmini-app@sha256:9f2c1b7a4e",
      "essential": true,
      "user": "10001:10001",
      "readonlyRootFilesystem": true,
      "privileged": false,
      "portMappings": [{ "containerPort": 8443, "protocol": "tcp" }],
      "linuxParameters": {
        "capabilities": { "drop": ["ALL"] }
      },
      "mountPoints": [
        { "sourceVolume": "tmp", "containerPath": "/tmp", "readOnly": false }
      ],
      "secrets": [
        {
          "name": "DB_PASSWORD",
          "valueFrom": "arn:aws:secretsmanager:ap-northeast-2:111122223333:secret:rds/shopmini:password::"
        }
      ],
      "environment": [
        { "name": "APP_PORT", "value": "8443" }
      ],
      "logConfiguration": {
        "logDriver": "awslogs",
        "options": {
          "awslogs-group": "/ecs/shopmini-app",
          "awslogs-region": "ap-northeast-2",
          "awslogs-stream-prefix": "app"
        }
      }
    }
  ],
  "volumes": [{ "name": "tmp" }]
}
```

읽어야 할 곳이 다섯입니다.

**① `"networkMode": "awsvpc"`** — 태스크마다 전용 ENI가 생기고 **태스크 단위로 보안 그룹이 붙습니다.** 19.2의 SG 참조 체인이 컨테이너에 그대로 적용됩니다. `bridge` 모드는 호스트 ENI를 공유해 SG 세분화가 불가능하고 동적 포트 매핑으로 규칙이 넓어집니다. **Fargate는 `awsvpc`만 지원**합니다.

**② `"secrets"` 필드** — 값이 아니라 **참조**를 씁니다. 실행 역할이 시작 시점에 해석하므로 태스크 정의에도 CloudTrail 이벤트에도 평문이 남지 않습니다. ⚠️ **시작 시점에 한 번만** 읽히므로 **순환 대상 시크릿에는 쓰지 않습니다**(11.6).

**③ `"readonlyRootFilesystem": true`** — 불변성을 런타임에서 강제합니다. 웹셸 투하나 바이너리 덮어쓰기가 쓰기 실패로 끝나고, 쓰기가 필요한 경로만 볼륨으로 엽니다.

**④ `"user"` + `capabilities.drop: ["ALL"]`** — 비루트 실행과 capability 제거. `NET_BIND_SERVICE`가 필요해 보이면 8443처럼 1024 이상 포트를 씁니다. **⑤ 이미지 다이제스트 고정** — 24.2의 결론입니다.

### Fargate vs EC2 — 책임 차이

| 항목 | ECS on EC2 | ECS on Fargate |
|---|---|---|
| 호스트 OS·커널 패치 | **나** (ECS 최적화 AMI 교체 주기 관리) | AWS (플랫폼 버전) |
| ECS 에이전트 버전 | **나** | AWS |
| 커널 격리 | 같은 인스턴스의 태스크가 **커널 공유** | 태스크마다 **전용 microVM** |
| 태스크별 보안 그룹 | `awsvpc` 모드에서만 | 항상 |
| IMDS 접근 | ⚠️ 태스크가 노드 IMDS에 도달 가능 | 태스크 IMDS 없음(태스크 자격 증명만) |
| 호스트 볼륨·`privileged` | 가능 (그래서 위험) | 불가 |
| 데몬셋형 보안 에이전트 | 설치 가능 | 사이드카 또는 GuardDuty Runtime Monitoring |

⚠️ **ECS on EC2의 IMDS 문제.** 8.3의 IMDS 위험이 컨테이너에서 증폭됩니다. 원서도 이 구도를 지적합니다.

> 📖 *Practical Cloud Security* 2판 4장: **"이것은 컨테이너 환경에서 특히 문제가 될 수 있는데, 호스트 시스템 위의 어떤 컨테이너든 아이덴티티 문서를 요청한 뒤 그 호스트 시스템인 척할 수 있기 때문이다. 이런 경우에는 컨테이너가 메타데이터 서비스에 도달하지 못하도록 차단해야 한다."**

```bash
# /etc/ecs/ecs.config — awsvpc 모드 태스크의 IMDS 접근 차단
echo "ECS_AWSVPC_BLOCK_IMDS=true" >> /etc/ecs/ecs.config
```

여기에 인스턴스 프로파일도 최소화합니다. 노드 역할에는 `AmazonEC2ContainerServiceforEC2Role` 수준만 두고 **앱 권한은 절대 노드 역할에 넣지 않습니다.**

### ECS Exec — 예외적 접근의 통제

원서는 네이티브 컨테이너 모델에서도 **"문제 해결을 위해 가끔 긴급 접근을 얻을 방법은 필요하다"** 고 인정합니다(3장). AWS의 답은 SSH가 아니라 `ecs execute-command`입니다.

```bash
aws ecs execute-command \
  --cluster shopmini-prod --task <task-id> --container app \
  --interactive --command "/bin/sh" \
  --profile awssec-lab --region ap-northeast-2
```

① `enableExecuteCommand`는 운영에서 평시 끄고 필요 시에만 켭니다. ② **세션 로깅을 CloudWatch Logs/S3로 보내고 KMS로 암호화**합니다(21.6과 같은 구조). ③ `ecs:ExecuteCommand` 권한은 소수 역할에만 주고 사용 시 알림이 뜨게 합니다. 로깅 없는 ECS Exec는 감사 흔적 없는 프로덕션 셸입니다.

## 24.4 EKS 보안

> 💡 **원서 범위 밖 보강** — 원서는 Kubernetes를 자산 유형·네트워크 정책·감사 로깅 수준에서만 다룹니다. EKS 구현은 원서 범위 밖입니다.

> 📖 *Practical Cloud Security* 2판 3장: **"쿠버네티스 소프트웨어·설정·접근 통제의 취약점은 그 위에서 돌아가는 모든 파드를 침해할 수 있으며, 쿠버네티스는 공격자들의 적극적인 표적이 되어 왔다."**

"설정·접근 통제의 취약점"이 EKS에서 무엇인지가 이 절의 내용입니다.

### ⚠️ API 서버 엔드포인트 퍼블릭 노출

**사고 시나리오.** ShopMini 팀이 EKS 클러스터를 콘솔 기본값(**퍼블릭 엔드포인트 + `publicAccessCidrs = 0.0.0.0/0`**)으로 만들었습니다. 몇 주 뒤 CI 편의를 위해 `system:masters`에 매핑한 IAM 역할이 생겼고, 그 역할을 맡는 사용자의 액세스 키가 유출됐습니다. 공격자는 인터넷에서 곧바로 `kubectl`로 붙었습니다.

**원인.** ① **API 서버가 인터넷 어디서나 도달 가능**했고, ② 인가가 **IAM 하나에만** 의존했으며, ③ 그 주체가 클러스터 관리자였습니다.

**올바른 구성.** 세 단계로 좁힙니다.

```bash
# 1단계 — 퍼블릭 엔드포인트를 유지해야 한다면 CIDR을 반드시 제한
aws eks update-cluster-config --name shopmini-eks \
  --resources-vpc-config \
    endpointPublicAccess=true,endpointPrivateAccess=true,publicAccessCidrs=203.0.113.0/24 \
  --profile awssec-lab --region ap-northeast-2

# 2단계(권장) — 프라이빗 전용. 접근은 VPC 내부(배스천/러너/VPN)에서만
aws eks update-cluster-config --name shopmini-eks \
  --resources-vpc-config endpointPublicAccess=false,endpointPrivateAccess=true \
  --profile awssec-lab --region ap-northeast-2
```

⚠️ 2단계로 갈 때 **CI/CD 러너의 위치**를 먼저 정리해야 합니다. 프라이빗 전용으로 바꾸면 클라우드 호스팅 러너에서 `kubectl`이 끊기므로 VPC 안의 러너로 옮깁니다(21.5).

**3단계 — 컨트롤 플레인 로깅.**

> 📖 *Practical Cloud Security* 2판 7장: **"예를 들어 쿠버네티스 같은 오케스트레이션 플랫폼을 쓰고 있다면 감사(auditing)를 켤 수 있다. 쿠버네티스 문서는 감사 로깅을 켜는 방법과 그 로그를 수집 지점으로 보내는 방법을 설명한다."**

```bash
aws eks update-cluster-config --name shopmini-eks \
  --logging '{"clusterLogging":[{"types":["api","audit","authenticator","controllerManager","scheduler"],"enabled":true}]}' \
  --profile awssec-lab --region ap-northeast-2
```

`audit`와 `authenticator`가 핵심입니다. CloudTrail은 "누가 EKS API를 호출했는가"만 남기고, **클러스터 안에서 누가 무엇을 했는가는 이 감사 로그에만 있습니다**(29·31장).

### IAM과 Kubernetes RBAC — 이중 인가

EKS의 접근 통제는 **두 단계**입니다. 이 구조를 모르면 "IAM 권한은 다 줬는데 `kubectl`이 403"이 설명되지 않습니다.

```
kubectl 요청
   │
   ├─[1단계: 인증] IAM 주체 → 서명된 토큰 → EKS가 STS로 신원 확인
   │                          "너는 arn:aws:iam::111122223333:role/dev-role 이다"
   │
   └─[2단계: 인가] Kubernetes RBAC → 그 신원이 매핑된 그룹의 Role/ClusterRole 확인
                              "그 그룹은 default 네임스페이스의 파드를 읽을 수 있다"
```

**IAM은 "누구인가"만 답하고 "무엇을 할 수 있는가"는 RBAC이 답합니다**(클러스터 자체를 다루는 `eks:*` API는 순수 IAM 영역). 두 단계를 연결하는 매핑 방식은 둘입니다.

| | `aws-auth` ConfigMap (전통) | **액세스 항목(Access Entries)** (신형) |
|---|---|---|
| 저장 위치 | `kube-system` 네임스페이스의 ConfigMap | **EKS 컨트롤 플레인** (AWS API) |
| 변경 수단 | `kubectl edit` — 클러스터 접근이 이미 있어야 함 | `aws eks create-access-entry` — IAM 권한만 있으면 됨 |
| 감사 | Kubernetes 감사 로그 | **CloudTrail** |
| IaC | ConfigMap YAML | CloudFormation/Terraform 리소스 |
| ⚠️ 위험 | **YAML 한 줄 오타로 전원이 잠김**(복구 매우 어려움) | 잘못돼도 AWS API로 복구 |
| 권한 부여 | 그룹 매핑 → 직접 만든 RBAC | AWS 관리형 **액세스 정책** 또는 그룹 매핑 |

`aws-auth` ConfigMap은 **자기 자신을 잠글 수 있습니다** — 매핑을 잘못 저장해 모든 관리자가 빠지면 남는 길은 클러스터 생성자 신원뿐입니다.

```bash
# 클러스터 인증 모드를 액세스 항목 중심으로 전환
aws eks update-cluster-config --name shopmini-eks \
  --access-config authenticationMode=API_AND_CONFIG_MAP \
  --profile awssec-lab --region ap-northeast-2

# 플랫폼 팀 역할에 클러스터 관리자 액세스 정책 부여
aws eks create-access-entry --cluster-name shopmini-eks \
  --principal-arn arn:aws:iam::111122223333:role/shopmini-platform \
  --type STANDARD --profile awssec-lab --region ap-northeast-2

aws eks associate-access-policy --cluster-name shopmini-eks \
  --principal-arn arn:aws:iam::111122223333:role/shopmini-platform \
  --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSClusterAdminPolicy \
  --access-scope type=cluster \
  --profile awssec-lab --region ap-northeast-2
```

개발자에게는 `AmazonEKSViewPolicy`를 **네임스페이스 범위**로 줍니다. 🔴 **`AmazonEKSClusterAdminPolicy`와 `system:masters` 매핑은 상시 사용자가 아니라 브레이크글래스 역할에만 둡니다**(3장).

### IRSA vs EKS Pod Identity — 파드에 IAM 권한 주기

노드 인스턴스 프로파일을 쓰는 것은 **그 노드의 모든 파드에 같은 권한을 주는 것**입니다(8.2). AWS의 해법은 둘입니다.

| | **IRSA** (IAM Roles for Service Accounts) | **EKS Pod Identity** |
|---|---|---|
| 원리 | 클러스터 OIDC 제공자 → 프로젝티드 SA 토큰 → `sts:AssumeRoleWithWebIdentity` | `eks-pod-identity-agent` 애드온 → `sts:AssumeRole` |
| 사전 준비 | **클러스터마다** IAM OIDC 제공자 생성 | 애드온 설치 1회 |
| 역할 신뢰 정책 | `Federated: oidc-provider/...` + `sub` 조건 | `Service: pods.eks.amazonaws.com` |
| 클러스터 여러 개 | **클러스터마다 신뢰 정책에 항목 추가** (한도 문제 발생) | **역할 하나를 여러 클러스터에서 재사용** |
| 연결 방법 | 서비스 계정에 `eks.amazonaws.com/role-arn` 어노테이션 | `aws eks create-pod-identity-association` |
| EKS Fargate | 지원 | **미지원** |
| 권장 | 기존 구성·Fargate | **신규 구성** |

IRSA 신뢰 정책에는 조건 두 개가 반드시 필요합니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::111122223333:oidc-provider/oidc.eks.ap-northeast-2.amazonaws.com/id/EXAMPLED539D4633E53DE1B716D3041E"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "oidc.eks.ap-northeast-2.amazonaws.com/id/EXAMPLED539D4633E53DE1B716D3041E:aud": "sts.amazonaws.com",
          "oidc.eks.ap-northeast-2.amazonaws.com/id/EXAMPLED539D4633E53DE1B716D3041E:sub": "system:serviceaccount:shopmini:shopmini-app-sa"
        }
      }
    }
  ]
}
```

⚠️ **`sub` 조건을 빠뜨리거나 `system:serviceaccount:*:*` 를 쓰면 클러스터 안 어떤 서비스 계정이든 그 역할을 맡습니다** — 개발자가 자기 네임스페이스에 SA 하나만 만들면 운영 데이터 권한을 얻습니다. `aud` 누락도 토큰 재사용 여지를 남깁니다.

Pod Identity의 신뢰 정책은 훨씬 단순합니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "Service": "pods.eks.amazonaws.com" },
      "Action": ["sts:AssumeRole", "sts:TagSession"]
    }
  ]
}
```

```bash
aws eks create-pod-identity-association --cluster-name shopmini-eks \
  --namespace shopmini --service-account shopmini-app-sa \
  --role-arn arn:aws:iam::111122223333:role/shopmini-app-pod \
  --profile awssec-lab --region ap-northeast-2
```

⚠️ 대신 **"어느 파드가 이 역할을 쓰는가"를 연결(association)이 결정합니다** — `eks:CreatePodIdentityAssociation`과 `iam:PassRole`을 함께 제한합니다(7장).

### 🔴 파드의 IMDS 차단

앞서 인용한 원서 4장의 경고가 EKS에서 특히 중요합니다. IRSA나 Pod Identity를 붙여도 **파드가 `169.254.169.254`에 도달하면 노드 역할을 그대로 쓸 수 있습니다** — 공격자는 IMDS를 직접 호출하면 그만입니다.

```bash
# 노드에 IMDSv2 강제 + 홉 제한 1
#  → 파드는 노드와 다른 네트워크 네임스페이스라 홉이 한 단계 더 필요하므로,
#    홉 제한 1이면 파드에서 IMDS에 도달하지 못한다 (노드 자신은 가능)
# 운영에서는 노드 그룹의 시작 템플릿(MetadataOptions)에 같은 값을 넣는다
aws ec2 modify-instance-metadata-options \
  --instance-id i-0a1b2c3d4e5f6a7b8 \
  --http-tokens required --http-put-response-hop-limit 1 \
  --profile awssec-lab --region ap-northeast-2
```

⚠️ 8.3의 함정 — **홉 제한 1은 일부 CNI 구성에서 시스템 파드까지 깨뜨립니다.** 순서는 ① 워크로드를 IRSA/Pod Identity로 옮기고 ② 시스템 파드가 `hostNetwork`로 도는지 확인한 뒤 ③ 홉 제한을 내리는 것입니다. 대안은 네트워크 정책의 `169.254.169.254/32` 이그레스 거부입니다.

### 네트워크 정책 — 클러스터 내부 세그멘테이션

> 📖 *Practical Cloud Security* 2판 6장 「Network Security」: **"경계에는 보통 VPC나 보안 그룹 같은 기존 IaaS 네트워크 통제를 쓰겠지만, 워커 노드에 로컬 방화벽을 걸기 위해 쿠버네티스 네트워크 정책을 쓸 수도 있다. (…) 내부 세그멘테이션에는 네트워크 정책으로 파드를 격리할 수 있다. 예를 들어 데이터베이스 파드가 애플리케이션 서버 파드의 접근만 허용하도록 구성할 수 있다."**

AWS의 선택지는 셋입니다.

| 수단 | 부착 지점 | 특징 |
|---|---|---|
| 보안 그룹(노드) | 노드 ENI | 노드 간 통제만. 같은 노드 안 파드끼리는 못 막음 |
| **Kubernetes 네트워크 정책** | 파드 라벨 | VPC CNI의 네트워크 정책 지원, 또는 Calico/Cilium |
| **파드용 보안 그룹** | 파드 전용 ENI (`SecurityGroupPolicy`) | RDS처럼 **VPC 리소스**로의 접근을 SG 참조로 통제 |

ShopMini에서는 **파드→파드**를 네트워크 정책으로, **파드→RDS**를 파드용 보안 그룹으로 통제합니다(19.2).

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: shopmini
spec:
  podSelector: {}
  policyTypes: ["Ingress", "Egress"]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-alb-to-app
  namespace: shopmini
spec:
  podSelector:
    matchLabels: { app: shopmini-app }
  policyTypes: ["Ingress"]
  ingress:
    - from:
        - ipBlock:
            cidr: 10.20.0.0/24   # 퍼블릭 서브넷(ALB) — 2c는 별도 규칙
      ports:
        - protocol: TCP
          port: 8443
```

🔴 **네임스페이스마다 `default-deny-all`을 먼저 깝니다.** 네트워크 정책은 화이트리스트라 정책이 없는 네임스페이스는 **전부 허용**이며, "정책을 몇 개 만들었으니 격리됐다"가 흔한 착각입니다.

### 파드 보안 표준(PSS)과 승인(PSA)

PodSecurityPolicy는 Kubernetes 1.25에서 제거됐고 후속이 **Pod Security Admission(PSA)** 입니다. 네임스페이스 라벨 하나로 세 등급 중 하나를 강제합니다.

| 등급 | 의미 |
|---|---|
| `privileged` | 제한 없음. 시스템 컴포넌트 전용 |
| `baseline` | 알려진 권한 상승 경로 차단(`privileged`, `hostPID`, `hostNetwork`, 위험한 `hostPath` 등) |
| **`restricted`** | 여기에 더해 **비루트 실행, `allowPrivilegeEscalation: false`, capability 전부 제거, seccomp `RuntimeDefault`** 강제 |

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: shopmini
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/enforce-version: latest
    pod-security.kubernetes.io/warn: restricted
    pod-security.kubernetes.io/audit: restricted
```

**도입 순서**가 중요합니다. 바로 `enforce: restricted`를 걸면 기존 워크로드가 대량 거부되므로, `warn`·`audit`만 먼저 켜 몇 주 관찰하고 고친 뒤 승격합니다(19.6과 같은 순서).

### 시크릿 봉투 암호화

Kubernetes `Secret`은 etcd에 **base64 인코딩**으로 저장됩니다 — 인코딩은 암호화가 아닙니다(11.1). EKS는 etcd를 기본 암호화하지만 여기에 **고객 관리 KMS 키로 한 겹 더** 씌우는 것이 봉투 암호화입니다.

```bash
aws eks associate-encryption-config --cluster-name shopmini-eks \
  --encryption-config '[{"resources":["secrets"],"provider":{"keyArn":"arn:aws:kms:ap-northeast-2:111122223333:key/1234abcd-12ab-34cd-56ef-1234567890ab"}}]' \
  --profile awssec-lab --region ap-northeast-2
```

⚠️ **한 번 연결하면 해제할 수 없고 키를 삭제하면 클러스터를 복구할 수 없습니다.** 키 정책에 EKS 접근을 남기고 삭제 방지를 겁니다(13장).

더 근본적으로는 **AWS 자격 증명을 Kubernetes Secret에 넣지 않는 것**이 정답입니다 — IRSA/Pod Identity를 쓰면 그 시크릿이 애초에 없습니다(11.6).

## 24.5 런타임 보호

> 💡 **원서 범위 밖 보강** — 런타임 이상 행위 탐지의 필요성은 원서 5·7장에 근거하지만, GuardDuty Runtime Monitoring 등 AWS 구현은 원서 범위 밖입니다.

24.2가 "배포 전"이라면 이 절은 "배포 후"입니다. 이미지 스캔은 **알려진** 취약점만 잡고, 자격 증명 탈취로 시작되는 공격은 실행 중에만 드러납니다.

**첫째, 할 수 있는 일을 미리 줄인다(예방).**

| 통제 | Kubernetes | ECS | 막는 것 |
|---|---|---|---|
| 비루트 실행 | `runAsNonRoot: true`, `runAsUser: 10001` | `"user": "10001:10001"` | 컨테이너 내 루트 → 커널 익스플로잇 결합 |
| 권한 상승 차단 | `allowPrivilegeEscalation: false` | (기본 동작 + capability 제거) | `setuid` 바이너리로 권한 얻기 |
| 읽기 전용 루트 FS | `readOnlyRootFilesystem: true` | `"readonlyRootFilesystem": true` | 웹셸 투하, 바이너리 변조, 지속성 확보 |
| capability 제거 | `capabilities: {drop: ["ALL"]}` | `linuxParameters.capabilities.drop` | `CAP_SYS_ADMIN` 등을 통한 탈출 |
| seccomp | `seccompProfile: {type: RuntimeDefault}` | (Fargate 기본 적용) | 원서가 지적한 **시스템 콜 공격 표면** 축소 |
| 특권 모드 금지 | `privileged: false` | `"privileged": false` | 사실상 호스트 루트 |
| 호스트 네임스페이스 금지 | `hostPID/hostIPC/hostNetwork: false` | 호스트 볼륨 금지 | 다른 컨테이너·호스트 프로세스 관측 |

```yaml
# 파드 스펙 — 최소 안전 기본형
securityContext:
  runAsNonRoot: true
  runAsUser: 10001
  fsGroup: 10001
  seccompProfile:
    type: RuntimeDefault
containers:
  - name: app
    image: 111122223333.dkr.ecr.ap-northeast-2.amazonaws.com/shopmini-app@sha256:9f2c1b7a4e
    securityContext:
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      privileged: false
      capabilities:
        drop: ["ALL"]
    volumeMounts:
      - name: tmp
        mountPath: /tmp
volumes:
  - name: tmp
    emptyDir: {}
```

이 스펙은 24.4의 `restricted` 표준을 통과하는 최소 형태입니다. **PSA로 강제하고 개발자에게는 이 YAML을 템플릿으로 준다** — 둘을 같이 해야 정착합니다.

**둘째, 하는 일을 관찰한다(탐지).** 원서의 두 번째 스캐너 접근법이며, AWS에서는 **GuardDuty Runtime Monitoring**이 EKS·ECS(Fargate 포함)·EC2에서 이 역할을 합니다. 컨테이너 안의 프로세스·파일·네트워크 연결을 보고 채굴, 컨테이너 탈출 시도, C2 연결, **파드의 IMDS 호출 시도**(차단해도 시도 자체가 신호)를 탐지합니다.

⚠️ 원서의 경고를 다시 확인해야 합니다 — **"컨테이너가 많으면 무거운 에이전트를 모든 컨테이너에 넣을 수 없다."** GuardDuty Runtime Monitoring은 컨테이너마다가 아니라 **노드에 하나(EKS 애드온), Fargate는 사이드카**로 배치되어 이 문제를 피합니다.

탐지는 대응과 짝을 이뤄야 합니다 — **의심스러운 태스크·파드는 격리하고 교체하면 됩니다.** 원서가 "정기적으로 컨테이너를 교체하면 위협 행위자가 상주하지 못하게 하는 데도 도움이 된다"고 한 것과 같은 논리입니다. 다만 포렌식이 필요하면 교체 전에 로그를 확보합니다(32장).

## 24.6 Lambda 보안 🔴

> 💡 **원서 범위 밖 보강** — 서버리스 자산의 성격(3장)과 네트워크 통제 한계(6장)는 원서 근거가 있습니다. 실행 역할·환경 변수 암호화·코드 서명 등 Lambda 구현은 원서 범위 밖입니다.

원서는 서버리스의 보안 관심사를 두 가지로 압축합니다.

> 📖 *Practical Cloud Security* 2판 3장: **"서버리스 자산에 대해서는 운영체제나 플랫폼 컴포넌트를 인벤토리할 필요가 없다. (…) 그것은 여러분 코드의 취약점을 관리하고 **함수에 대한 접근을 통제하기 위해서**다."**

**코드의 취약점**과 **함수 접근 통제** — 이 둘이 이 절의 뼈대입니다.

### 🔴 함수마다 실행 역할을 따로 만든다

**안 하면 어떻게 되는가.** ShopMini의 Lambda 함수 40개가 모두 `shopmini-lambda-role` 하나를 씁니다. 이 역할에는 40개가 필요로 하는 권한의 **합집합**이 들어 있습니다. 그중 가장 단순한 썸네일 생성 함수에 라이브러리 CVE로 원격 코드 실행이 생기면 **공격자는 40개 함수 권한 전부를 얻습니다.**

공용 역할은 **폭발 반경을 함수 개수만큼 곱하는 구성**입니다(1.4). 함수는 대개 API를 두세 개만 호출하므로 함수별 역할은 정책 10줄이면 끝납니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadUploadedImageOnly",
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::shopmini-uploads/incoming/*"
    },
    {
      "Sid": "WriteThumbnailOnly",
      "Effect": "Allow",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::shopmini-assets/thumbnails/*"
    },
    {
      "Sid": "OwnLogGroupOnly",
      "Effect": "Allow",
      "Action": ["logs:CreateLogStream", "logs:PutLogEvents"],
      "Resource": "arn:aws:logs:ap-northeast-2:111122223333:log-group:/aws/lambda/shopmini-thumbnail:*"
    }
  ]
}
```

⚠️ **`AWSLambdaBasicExecutionRole`은 로그 권한을 모든 로그 그룹에 줍니다.** 엄격한 환경에서는 위처럼 자기 로그 그룹으로 좁힙니다.

### 🔴 환경 변수를 시크릿 저장소로 쓰지 않는다

Lambda 환경 변수는 저장 시 암호화되지만 **`lambda:GetFunctionConfiguration` 권한자는 콘솔·CLI에서 평문으로 봅니다** — ReadOnlyAccess 보유자 전원이 여기 해당합니다.

| 값의 성격 | 어디에 둘 것인가 |
|---|---|
| 설정값(버킷 이름, 로그 레벨, 리전) | 환경 변수 — 문제 없음 |
| 시크릿(DB 비밀번호, API 키) | **Secrets Manager / Parameter Store** + 실행 역할 권한 (11장) |
| 부득이 환경 변수에 둬야 하는 민감값 | **고객 관리 KMS 키**로 암호화 + 키 정책으로 복호화 주체 제한 |

세 번째 경우 Lambda 콘솔의 "전송 중 암호화를 위한 암호화 헬퍼"를 쓰면 값이 **암호문으로 저장**되고 함수 코드에서 `kms:Decrypt`로 풉니다.

```bash
aws lambda update-function-configuration \
  --function-name shopmini-thumbnail \
  --kms-key-arn arn:aws:kms:ap-northeast-2:111122223333:key/1234abcd-12ab-34cd-56ef-1234567890ab \
  --profile awssec-lab --region ap-northeast-2
```

🔴 그래도 **1순위는 환경 변수에 시크릿을 두지 않는 것**입니다. 22.4의 User Data 금지와 같은 이유 — 설정 조회 권한과 시크릿 접근 권한이 분리되지 않습니다.

### 🔴 리소스 기반 정책 — "누가 이 함수를 부를 수 있는가"

원서가 말한 **"함수 접근 통제"** 가 이것입니다. 호출 권한은 두 방향에서 옵니다.

```
[방향 1] 호출자의 IAM 정책이 lambda:InvokeFunction 을 허용   ← 같은 계정 IAM 주체
[방향 2] 함수의 리소스 기반 정책이 호출자를 허용              ← AWS 서비스, 다른 계정
```

S3·API Gateway·EventBridge 같은 **서비스**가 호출할 때는 방향 2만 쓰이고, 여기서 8.6의 Confused Deputy 문제가 재현됩니다.

```bash
# ⚠️ 나쁜 예 — S3 서비스면 누구의 버킷이든 이 함수를 호출할 수 있다
aws lambda add-permission --function-name shopmini-thumbnail \
  --statement-id s3invoke --action lambda:InvokeFunction \
  --principal s3.amazonaws.com

# 올바른 예 — 우리 계정의, 그 버킷에서 온 호출만
aws lambda add-permission --function-name shopmini-thumbnail \
  --statement-id s3invoke-uploads --action lambda:InvokeFunction \
  --principal s3.amazonaws.com \
  --source-arn arn:aws:s3:::shopmini-uploads \
  --source-account 111122223333 \
  --profile awssec-lab --region ap-northeast-2
```

⚠️ **S3 버킷 ARN에는 계정 ID가 없어** `--source-arn`만으로 부족하고 `--source-account`를 함께 줍니다. 같은 이름의 버킷을 자기 계정에 만들어 우리 함수를 호출하는 시나리오를 막는 조건입니다(8.6).

⚠️ **함수 URL의 `AuthType: NONE`** 은 **인터넷 전체에 함수 호출을 허용**합니다. 데모용으로 켜고 잊는 사고가 흔합니다. 기본은 `AWS_IAM`이어야 하고, 공개 API가 필요하면 API Gateway를 앞에 둡니다(24.7).

### VPC 연결 — 언제 필요하고 무엇을 잃는가

> 📖 *Practical Cloud Security* 2판 6장: 서버리스/FaaS 환경에 대해 **"이들은 공유 환경에서 동작하며, 네트워크 통제를 제공하지 않거나 프런트엔드에서만 제공할 수 있다."**

Lambda는 기본적으로 AWS 관리 네트워크에서 실행됩니다. VPC에 연결하면 VPC 안 리소스에 도달할 수 있고 **보안 그룹이 붙습니다** — 원서가 말한 "네트워크 통제 없음"을 넘어서는 지점입니다.

| | VPC 미연결 | VPC 연결 |
|---|---|---|
| RDS·내부 서비스 접근 | 불가(퍼블릭 노출 없이는) | **가능** |
| 보안 그룹 | 없음 | **있음** — 19.2의 SG 참조 체인에 편입 |
| 인터넷 접근 | 기본 가능 | **NAT 게이트웨이 필요** (Lambda ENI에는 퍼블릭 IP 없음) |
| AWS API 호출 | 기본 가능 | **NAT 또는 VPC 엔드포인트 필요** |
| 이그레스 통제 | 사실상 불가 | **가능** — 19.6·20장의 통제가 그대로 적용 |

🔴 **판단 기준**: VPC 리소스에 접근해야 하면 연결하고 아니면 하지 않습니다. 다만 **이그레스 통제가 규제 요건**이면 VPC 연결 + VPC 엔드포인트가 유일한 방법입니다. ⚠️ Lambda ENI가 서브넷 IP를 소모하므로 프라이빗앱 서브넷이 붐빈다면 **전용 서브넷**을 둡니다(18.2).

### 레이어·의존성·코드 서명

**레이어**의 위험은 둘입니다. ① **크로스 계정 레이어** — 다른 계정의 레이어를 참조하면 그 계정이 코드 공급자가 됩니다. **버전을 고정하지 않으면** 공급망 경로가 열리므로 서드파티 레이어는 우리 계정으로 복제해 씁니다. ② **의존성** — Inspector의 **Lambda 표준 스캔**과 **코드 스캔**을 켭니다(26.3).

**코드 서명**은 "이 코드가 승인된 파이프라인에서 나왔는가"를 강제합니다.

```bash
# ① Signer에 서명 프로파일 생성 → ② 코드 서명 구성 생성 → ③ 함수에 연결
aws lambda create-code-signing-config \
  --allowed-publishers SigningProfileVersionArns=arn:aws:signer:ap-northeast-2:111122223333:/signing-profiles/shopmini_prod/AbCdEf \
  --code-signing-policies UntrustedArtifactOnDeployment=Enforce \
  --profile awssec-lab --region ap-northeast-2
```

🔴 `UntrustedArtifactOnDeployment=Enforce`가 핵심입니다. `Warn`이면 서명 없는 코드도 배포되고 경고만 남습니다 — 24.2와 똑같이 **검증을 강제하지 않는 서명은 장식**입니다.

### 동시성 제한 — 가용성이자 보안 통제

Lambda 동시성은 **계정 단위 공유 자원**이라 함수 하나가 폭주하면 같은 계정의 다른 함수가 전부 스로틀링됩니다. **예약된 동시성**은 인터넷에 노출된 함수에 반드시 설정합니다 — 비용 폭주와 RDS 커넥션 고갈도 함께 막습니다. ⚠️ **예약 동시성 0**은 사고 시 즉시 정지 스위치이므로 인시던트 런북에 넣습니다(32장).

## 24.7 API Gateway 보안

> 💡 **원서 범위 밖 보강** — 이 절 전체는 원서 범위 밖이며, 원서가 말한 "프런트엔드에서만 제공되는 통제"(6장)의 그 **프런트엔드**를 다룹니다.

API Gateway는 서버리스 아키텍처의 **유일한 경계 통제 지점**입니다. 인증·인가·속도 제한·WAF가 모두 여기 붙습니다.

### 인증 방식 3종

| 방식 | 호출자 | 동작 | 언제 |
|---|---|---|---|
| **IAM 인증** | AWS 주체(다른 서비스, 내부 클라이언트) | SigV4 서명 검증 + IAM 정책 평가 | 서비스 간 내부 API |
| **Cognito 사용자 풀 권한 부여자** | 최종 사용자 | 사용자 풀이 발급한 JWT 검증 | B2C 앱 (10장) |
| **Lambda 권한 부여자** | 무엇이든 | 우리 코드가 토큰·헤더를 검사해 IAM 정책 문서 반환 | 서드파티 IdP, 커스텀 로직 |

🔴 **핵심은 "인증 없음(`NONE`)이 기본값이 되지 않게 하는 것"** 입니다. 메서드마다 권한 부여자를 지정하지 않으면 열린 상태가 되므로, IaC 템플릿과 리뷰 게이트로 신규 메서드에 자동으로 걸리게 합니다.

⚠️ **API 키는 인증 수단이 아닙니다.** `x-api-key`는 **사용량 계획을 식별할 뿐** 신원을 증명하지 않으며, 클라이언트 앱에 박아 넣은 키는 언제든 추출됩니다.

**Lambda 권한 부여자의 함정** — 반환하는 정책의 `Resource`를 와일드카드로 두면 **한 번 인증에 성공하는 순간 API 전 메서드 허용이 캐시됩니다**(기본 TTL 300초). 사용자별로 정확한 리소스를 반환하거나 캐시를 끄고 메서드별로 판단해야 합니다.

### 리소스 정책 — 어디서 오는 호출을 받을 것인가

REST API에는 리소스 기반 정책을 붙일 수 있습니다 — 프라이빗 API나 IP·계정 제한에 씁니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Deny",
      "Principal": "*",
      "Action": "execute-api:Invoke",
      "Resource": "arn:aws:execute-api:ap-northeast-2:111122223333:a1b2c3d4e5/*",
      "Condition": {
        "StringNotEquals": {
          "aws:SourceVpce": "vpce-0abc12345def67890"
        }
      }
    },
    {
      "Effect": "Allow",
      "Principal": "*",
      "Action": "execute-api:Invoke",
      "Resource": "arn:aws:execute-api:ap-northeast-2:111122223333:a1b2c3d4e5/*"
    }
  ]
}
```

이 정책은 "**지정된 VPC 엔드포인트를 경유하지 않은 모든 호출을 거부**"합니다. 20장의 엔드포인트 정책과 짝을 이뤄 내부 전용 API를 인터넷에서 사라지게 만듭니다.

### 사용량 계획·스로틀링

스로틀링은 가용성 통제이자 **자격 증명 스터핑·열거 공격 통제**입니다.

| 층 | 설정 위치 | 용도 |
|---|---|---|
| 계정 | 리전별 기본 한도 | 최후의 안전판 |
| 스테이지 | 스테이지 설정 | API 전체 보호 |
| 메서드 | 메서드별 재정의 | 무거운 엔드포인트만 더 조이기 |
| **사용량 계획** | API 키 단위 | **클라이언트별** 쿼터/속도 |

🔴 로그인·비밀번호 재설정처럼 **열거가 가능한 엔드포인트에는 메서드 수준 스로틀링을 별도로 겁니다.** 분산 공격은 이것으로 못 막으므로 23.8의 WAF **속도 기반 규칙**을 함께 씁니다.

### WAF와 mTLS

AWS WAF는 API Gateway **REST API의 스테이지**에 직접 연결할 수 있고, 23.8의 관리형 규칙 그룹이 그대로 적용됩니다.

⚠️ **HTTP API(v2)에는 WAF를 직접 연결할 수 없습니다.** REST API를 쓰거나 CloudFront를 앞에 두고 거기에 붙입니다. 후자라면 23.9의 **오리진 직접 접근 차단**이 따라와야 합니다 — 기본 엔드포인트로 직접 오면 WAF를 우회하므로 리소스 정책이나 커스텀 헤더로 CloudFront 경유만 허용합니다.

**mTLS** — 커스텀 도메인에 트러스트스토어(S3의 CA 번들)를 연결하면 **클라이언트 인증서를 요구**할 수 있습니다.

```bash
aws apigatewayv2 update-domain-name \
  --domain-name api.shopmini.example.com \
  --mutual-tls-authentication truststoreUri=s3://shopmini-assets/truststore/ca-bundle.pem \
  --profile awssec-lab --region ap-northeast-2
```

B2B 파트너 연동이나 IoT 디바이스처럼 **클라이언트가 관리 대상일 때** 유용합니다. ⚠️ mTLS는 "이 인증서를 가진 클라이언트"까지만 증명하므로 **인가는 별도로** 해야 하고, 인증서 폐기 목록 관리도 우리 몫입니다.

여기에 **액세스 로깅 + 인증 실패(4xx) 급증 알람**, 그리고 **요청 검증(Request Validation)** 으로 스키마 밖 입력을 게이트웨이에서 거르는 구성을 더합니다.

## 24.8 이벤트 기반 아키텍처의 신뢰 경계

> 💡 **원서 범위 밖 보강** — 이 절 전체는 원서 범위 밖이며, 8.6의 Confused Deputy 원칙을 이벤트 서비스로 확장한 것입니다.

"SQS는 내부 컴포넌트니까 정책을 느슨하게 해도 된다"는 오해가 흔한데, **SQS·SNS·EventBridge는 모두 리전 단위 공개 엔드포인트를 가진 서비스**이고 리소스 정책이 그 앞의 유일한 문입니다.

### 신뢰 경계는 어디에 있는가

```
[S3 shopmini-uploads] --이벤트--> [SQS shopmini-ingest] --폴링--> [Lambda 처리기]
        ①                              ②                             ③
                                        └──실패──> [SQS DLQ]
                                                       ④
```

| 지점 | 통제할 것 | 수단 |
|---|---|---|
| ① S3 → SQS | 우리 버킷의 이벤트만 받는다 | 큐 정책 + `aws:SourceArn`/`aws:SourceAccount` |
| ② 큐 자체 | 누가 메시지를 넣고 뺄 수 있는가 | 큐 정책 Principal 제한 |
| ③ 큐 → Lambda | Lambda 실행 역할이 이 큐만 읽는가 | 실행 역할 Resource 제한 |
| ④ **DLQ** | 실패 메시지 안의 민감 데이터 | 암호화 + 접근 제한 + 보존 기간 |

### ⚠️ 크로스 계정 이벤트의 Confused Deputy

**사고 시나리오.** ShopMini 팀이 S3 이벤트를 SQS로 보내려고 예제를 복사해 큐 정책을 만들었습니다.

```json
{
  "Effect": "Allow",
  "Principal": { "Service": "s3.amazonaws.com" },
  "Action": "sqs:SendMessage",
  "Resource": "arn:aws:sqs:ap-northeast-2:111122223333:shopmini-ingest"
}
```

동작은 합니다. 그런데 이 정책은 **전 세계 어떤 계정의 어떤 S3 버킷이든 이 큐에 메시지를 넣을 수 있다**는 뜻입니다. 공격자가 자기 버킷에 이벤트 알림을 걸어 조작된 메시지를 넣으면 우리 Lambda가 정상 이벤트로 처리하고, 처리기를 계속 실패시키면 DLQ가 채워져 진짜 이벤트가 묻힙니다.

**원인.** `Principal`이 서비스일 때 그 서비스는 **모든 AWS 고객이 공유합니다.** "S3가 호출했다"는 "**우리** S3가 호출했다"를 의미하지 않습니다 — 8.6의 Confused Deputy 구조 그대로입니다.

**올바른 구성.**

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowOnlyOurUploadsBucket",
      "Effect": "Allow",
      "Principal": { "Service": "s3.amazonaws.com" },
      "Action": "sqs:SendMessage",
      "Resource": "arn:aws:sqs:ap-northeast-2:111122223333:shopmini-ingest",
      "Condition": {
        "ArnLike": { "aws:SourceArn": "arn:aws:s3:::shopmini-uploads" },
        "StringEquals": { "aws:SourceAccount": "111122223333" }
      }
    },
    {
      "Sid": "DenyInsecureTransport",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "sqs:*",
      "Resource": "arn:aws:sqs:ap-northeast-2:111122223333:shopmini-ingest",
      "Condition": { "Bool": { "aws:SecureTransport": "false" } }
    }
  ]
}
```

서비스별로 조건 키를 정리하면 이렇습니다.

| 이벤트 소스 | 필요한 조건 | 이유 |
|---|---|---|
| S3 → SQS/SNS/Lambda | `aws:SourceArn` + **`aws:SourceAccount`** | 버킷 ARN에 계정 ID가 없어 이름 선점이 가능 |
| SNS → SQS | `aws:SourceArn`(토픽 ARN) | 토픽 ARN에 계정 ID 포함 — 단독으로 충분 |
| EventBridge 규칙 → 대상 | `aws:SourceArn`(규칙 ARN) | 규칙 ARN에 계정 ID 포함 |
| CloudWatch·Config 등 | `aws:SourceAccount` | 서비스 주체 공유 문제 동일 |

### 큐·토픽 암호화

12장의 데이터 분류를 이벤트 페이로드에도 적용합니다 — 주문 이벤트에는 개인정보가, 인증 이벤트에는 토큰이 들어갑니다.

```bash
aws sqs set-queue-attributes \
  --queue-url https://sqs.ap-northeast-2.amazonaws.com/111122223333/shopmini-ingest \
  --attributes '{"KmsMasterKeyId":"alias/shopmini/app","KmsDataKeyReusePeriodSeconds":"300"}' \
  --profile awssec-lab --region ap-northeast-2
```

⚠️ **SSE-KMS를 켜면 발행자 쪽에서 조용히 실패하는 일이 잦습니다** — 큐 정책만 고치고 **KMS 키 정책을 안 고쳤기 때문**입니다. SNS나 S3가 큐에 쓰려면 그 서비스 주체가 `kms:GenerateDataKey*`와 `kms:Decrypt`를 할 수 있어야 하고(여기에도 `aws:SourceAccount` 조건), 소비자 Lambda 실행 역할에도 `kms:Decrypt`가 필요합니다(13장).

### ⚠️ DLQ — 잊혀진 민감 데이터 저장소

DLQ의 보안 특징은 셋입니다. ① **원본 페이로드가 그대로 들어 있고**, 본 큐와 달리 사람이 치우기 전까지 쌓입니다. ② **보존 기간이 최대치로 설정되고** 재처리를 잊습니다. ③ **접근 권한이 넓습니다** — 장애 조사용으로 준 조회 권한이 회수되지 않습니다.

🔴 **DLQ에는 본 큐와 동일하거나 더 강한 통제를 겁니다.**
- 본 큐와 **같은 KMS 키로 암호화**(안 켜는 실수가 흔합니다)
- `sqs:ReceiveMessage`는 운영 역할로 한정, 조회를 CloudTrail로 감사
- 보존 기간을 재처리 SLA에 맞춰 짧게, DLQ **깊이에 알람**
- 민감 등급이면 **페이로드 대신 참조(객체 키·주문 ID)만 싣는 설계**로 — 가장 근본적인 해법

### 이벤트 버스의 크로스 계정 규칙

EventBridge 커스텀 버스에 다른 계정이 이벤트를 넣게 하려면 버스 정책에 허용하고, 조직 전체라면 `aws:PrincipalOrgID`를 씁니다(20.3).

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowOrgAccountsToPutSecurityEvents",
      "Effect": "Allow",
      "Principal": "*",
      "Action": "events:PutEvents",
      "Resource": "arn:aws:events:ap-northeast-2:444455556666:event-bus/shopmini-security",
      "Condition": {
        "StringEquals": { "aws:PrincipalOrgID": "o-exampleorgid" }
      }
    }
  ]
}
```

⚠️ **`Principal: "*"` + 조건**은 유효한 패턴이지만 조건을 빠뜨리면 그대로 전 세계 공개입니다. IAM Access Analyzer(7장)가 이런 정책을 외부 접근으로 표시하므로 이벤트 버스·큐·토픽 정책을 정기 검토합니다.

|---|---|
| 4C 모델 | Cloud → Cluster → Container → Code. **어떤 실행 방식을 골라도 이미지 내용물과 코드는 100% 내 책임** |
| 신뢰 경계 | 원서: **컨테이너를 유일한 신뢰 경계로 삼지 말 것.** 신뢰 수준이 다르면 노드 그룹 → 클러스터 → 계정으로 분리 |
| 이미지 | 최소 베이스 + 비루트 + 시크릿 없음 + **태그 불변성** + 향상 스캔(Inspector) + 다이제스트 고정 |
| ECS 역할 | **태스크 역할 = 앱 코드 / 태스크 실행 역할 = ECS 에이전트.** 실행 역할에 앱 권한을 넣으면 클러스터 공용 권한이 됨 |
| ECS 네트워크 | `awsvpc` = 태스크별 ENI + 태스크별 보안 그룹. Fargate는 항상 `awsvpc` |
| EKS 인가 | **IAM은 "누구인가"만, RBAC이 "무엇을 할 수 있는가"를 답한다.** 매핑은 `aws-auth`보다 **액세스 항목** |
| EKS 엔드포인트 | 기본값이 **퍼블릭 + `0.0.0.0/0`**. 프라이빗 전용 또는 CIDR 제한 필수. 컨트롤 플레인 `audit` 로깅 필수 |
| 파드 아이덴티티 | 신규는 **Pod Identity**, Fargate·기존은 **IRSA**. IRSA는 `sub`·`aud` 조건 필수 |
| IMDS | 원서: **"컨테이너가 메타데이터 서비스에 도달하지 못하게 차단하라."** ECS는 `ECS_AWSVPC_BLOCK_IMDS`, EKS는 홉 제한 1 |
| 런타임 | `runAsNonRoot` + `allowPrivilegeEscalation: false` + `readOnlyRootFilesystem` + `drop: ALL` + seccomp, PSA `restricted`로 강제 |
| Lambda 역할 | **함수당 1개.** 공용 역할은 폭발 반경을 함수 개수만큼 곱한다 |
| Lambda 접근 | 리소스 정책에 **`--source-arn` + `--source-account`**. 함수 URL `AuthType: NONE` 금지 |
| API Gateway | 인증 3종 중 하나 필수. **API 키는 인증이 아니다.** 스로틀링 + WAF + 우회 경로 차단 |
| 이벤트 신뢰 경계 | 서비스 Principal은 **모든 AWS 고객이 공유**. `aws:SourceArn`/`aws:SourceAccount`로 좁히지 않으면 누구나 우리 큐에 쓴다 |

## 🔴 필수 구성 체크리스트

**이미지**
- [ ] 최소 베이스 이미지이고 셸·패키지 매니저가 최종 이미지에 없다
- [ ] `USER <숫자 UID>`가 있고 루트로 실행되지 않는다
- [ ] 레이어·`ENV`·`ARG`에 시크릿이 없다
- [ ] **태그 불변성이 `IMMUTABLE`**, `scanOnPush=true`, 레지스트리 **향상 스캔** 이 켜져 있다
- [ ] 배포 매니페스트가 **다이제스트**를 참조한다
- [ ] 리포지토리 정책에 `Principal: "*"` 가 없다

**ECS**
- [ ] 태스크 정의마다 **전용 태스크 역할**이 있고 실행 역할에 앱 권한이 없다
- [ ] `networkMode`가 `awsvpc`이고 태스크 SG가 19.2의 참조 체인에 편입되어 있다
- [ ] 시크릿이 `secrets` 필드로 주입되고 **순환 대상 값이 아니다**
- [ ] `readonlyRootFilesystem: true`, `capabilities.drop: ["ALL"]`, `privileged: false`
- [ ] EC2 시작 유형이면 `ECS_AWSVPC_BLOCK_IMDS=true`, ECS Exec는 세션 로깅 + KMS 암호화

**EKS**
- [ ] API 서버 엔드포인트가 프라이빗이거나 `publicAccessCidrs`로 제한되어 있다
- [ ] 컨트롤 플레인 로깅에 `audit`·`authenticator`가 포함되어 있다
- [ ] 인증 모드가 액세스 항목 기반이고 `system:masters`/`ClusterAdminPolicy`가 브레이크글래스에만 있다
- [ ] 모든 워크로드가 **Pod Identity 또는 IRSA**를 쓰고 노드 역할에 앱 권한이 없다
- [ ] IRSA 신뢰 정책의 `:sub`·`:aud` 조건이 와일드카드가 아니다
- [ ] 파드에서 IMDS 도달이 차단되어 있다
- [ ] 네임스페이스마다 `default-deny-all` 네트워크 정책과 `enforce: restricted` 라벨이 있다
- [ ] 시크릿 봉투 암호화(KMS)가 켜져 있고 키에 삭제 방지가 걸려 있다

**Lambda / API Gateway / 이벤트**
- [ ] **함수마다 별도 실행 역할**이며 리소스가 좁혀져 있다
- [ ] 환경 변수에 시크릿이 없다 (있다면 고객 관리 KMS 키로 암호화)
- [ ] 모든 `add-permission`에 `--source-arn`과 (필요 시) `--source-account`가 있다
- [ ] 함수 URL이 없거나 `AuthType: AWS_IAM`이다
- [ ] 코드 서명이 `UntrustedArtifactOnDeployment=Enforce`이다
- [ ] 인터넷 노출 함수에 예약된 동시성이 설정되어 있다
- [ ] API Gateway의 모든 메서드에 권한 부여자가 있고 스로틀링·액세스 로깅이 켜져 있다
- [ ] SQS/SNS/EventBridge 정책에 `aws:SourceArn`/`aws:SourceAccount`/`aws:PrincipalOrgID` 조건이 있다
- [ ] DLQ가 본 큐와 같은 수준으로 암호화·제한되어 있고 깊이 알람이 있다

## ⚠️ 자주 하는 실수

| 실수 | 결과 | 올바른 구성 |
|---|---|---|
| ECS 태스크 실행 역할에 앱 권한 부여 | 같은 실행 역할을 쓰는 **모든 태스크**가 그 권한을 얻음 | 태스크 정의마다 전용 태스크 역할 (24.3) |
| 태그를 가변으로 두고 `:v2.4.1` 배포 | 스캔·서명한 이미지와 배포된 이미지가 다름. 롤백이 롤백이 아님 | 태그 불변성 + 다이제스트 참조 (24.2) |
| `ENV DB_PASSWORD=` 로 이미지에 시크릿 | 레이어에 영구 잔존. 지워도 이전 레이어에서 추출 가능 | `secrets` 필드/Secrets Manager로 실행 시 주입 (11장) |
| EKS 엔드포인트를 기본값(퍼블릭 `0.0.0.0/0`)으로 방치 | IAM 키 하나 유출로 인터넷에서 `kubectl` 가능 | 프라이빗 전용 또는 CIDR 제한 (24.4) |
| IRSA 신뢰 정책 `sub`를 `system:serviceaccount:*:*` | 클러스터 안 **아무 네임스페이스의 아무 SA**가 그 역할을 맡음 | 네임스페이스·SA 이름까지 `StringEquals`로 고정 |
| 파드에 IRSA를 붙였는데 IMDS를 막지 않음 | 공격자가 IMDS 직접 호출로 **노드 역할** 사용 | 홉 제한 1 + 네트워크 정책으로 `169.254.169.254` 차단 |
| 네트워크 정책을 몇 개만 만들고 격리됐다고 판단 | 정책 없는 네임스페이스는 **전부 허용** | `default-deny-all` 선배치 후 화이트리스트 |
| `aws-auth` ConfigMap을 직접 편집 | 오타 한 줄로 전 관리자 잠김, 복구 곤란 | 액세스 항목(AWS API) 기반으로 전환 |
| Lambda 40개가 역할 하나 공유 | 함수 하나의 RCE로 40개 함수 권한 전체 탈취 | 함수당 실행 역할 1개 (24.6) |
| Lambda 환경 변수에 DB 비밀번호 | `ReadOnlyAccess` 보유자 전원이 평문 열람 | Secrets Manager + 실행 역할 (11장) |
| 함수 URL을 `AuthType: NONE`으로 만들고 방치 | 인터넷 전체가 함수를 호출 (비용·데이터 양쪽) | `AWS_IAM` 또는 API Gateway 앞단 |
| 서명은 하는데 검증을 `Warn`으로 둠 | 서명 없는 아티팩트도 그대로 배포됨 | `Enforce` / 승인 컨트롤러에서 차단 (24.2, 24.6) |
| API 키로 인증을 대신함 | 클라이언트에서 추출된 키로 누구나 호출 | IAM/Cognito/Lambda 권한 부여자 + 키는 사용량 계획용 |
| HTTP API에 WAF를 붙였다고 생각 | HTTP API는 WAF 직접 연결 불가 → 무방비 | REST API 사용 또는 CloudFront+WAF+오리진 차단 (23.9) |
| 큐 정책에 `Service: s3.amazonaws.com`만 | **전 세계 어떤 계정의 버킷이든** 우리 큐에 메시지 삽입 | `aws:SourceArn` + `aws:SourceAccount` (8.6, 24.8) |
| SQS SSE-KMS만 켜고 키 정책은 그대로 | 발행 서비스가 조용히 실패 → 이벤트 유실 | 키 정책에 서비스 주체 + `aws:SourceAccount` 추가 |
| DLQ를 암호화·제한 없이 방치 | 개인정보가 담긴 실패 메시지가 14일간 넓은 권한으로 노출 | 본 큐와 동일 통제 + 깊이 알람 + 참조 기반 페이로드 |
