# 39장. 보안 운영 성숙도와 지표

> **이 장에서 다루는 것**
> - **보안 성숙도 모델** — 6개 통제 영역 × 5단계 진단 매트릭스. 우리 조직은 지금 몇 단계인가
> - **경영진에게 보고할 지표 12개** 🔴 — 정의 · AWS 측정법 · 목표값 설정법 · ⚠️ 왜곡되는 방식
> - **보안 챔피언과 조직 구조** — 중앙 집중 vs 임베디드. **게이트키퍼에서 플랫폼 제공자로**
> - **비용과 보안의 균형** — 통제별 비용이 무엇에 비례하는가, 절감 기법, 🔴 **끄면 안 되는 것**
> - **Well-Architected 보안 기둥 리뷰** 🧪 — 7개 설계 원칙 매핑과 정기 리뷰 운영법
>
> **선행 지식**: 25장(취약점 지표), 32장(대응 지표), 36~38장(멀티 계정·가드레일·컴플라이언스)
> **난이도**: ★★★★

---

36~38장에서 우리는 조직 전체에 통제를 강제하는 수단을 다 갖췄습니다. OU와 SCP가 있고, Control Tower가 신규 계정에 베이스라인을 심고, 감사 요구에 답할 증거 수집 경로도 만들었습니다. 그런데 여기까지 오면 반드시 나오는 질문이 하나 있습니다.

**"그래서, 우리는 잘하고 있습니까?"**

이 질문은 경영진이 던지지만, 사실 보안팀 자신이 가장 답하기 어려워하는 질문입니다. "SCP 12개 붙였습니다"는 활동 보고이지 성과 보고가 아닙니다. "GuardDuty 결과가 이번 달 340건입니다"는 숫자이지 의미가 아닙니다. 이 장은 **활동을 성과의 언어로 번역하는 방법**을 다룹니다. 번역에는 두 개의 축이 필요합니다 — **지금 어디에 있는지(성숙도)** 와 **어느 방향으로 움직이는지(지표)** 입니다.

원서는 이 주제에 대해 두 개의 짧지만 단단한 문장을 남겼습니다. 하나는 취약점 관리 장에서, 하나는 사고 대응 장에서 나옵니다.

> 📖 *Practical Cloud Security* 1판·2판 5장: **"취약점 관리 프로그램이 어떻게 되어가고 있는지 측정할 수 없다면, 대개 그 유용성을 정당화할 수도 없고 변화가 필요한지 알 수도 없다."**
>
> 📖 1판·2판 7장 「Example Metrics」: **"다른 업무 프로세스와 마찬가지로, 탐지·대응·복구 활동에 대해 어떤 측정치도 제시할 수 없다면 개선되고 있는지 알기 어렵다."**

두 문장의 공통 구조에 주목하십시오. 측정의 목적이 **평가**가 아니라 **정당화와 변화 판단**입니다. 이 장의 모든 지표는 그 목적에 맞춰 설계됩니다. 누구를 혼내기 위한 숫자는 하나도 없습니다.

## 39.1 보안 성숙도 모델

### 왜 체크리스트만으로는 부족한가

부록 A의 100항목 체크리스트는 강력하지만 한계가 분명합니다. **모든 항목이 이진값**이라는 것입니다. "CloudTrail 조직 트레일이 켜져 있다 — 예"라는 답은 다음 네 상태를 구분하지 못합니다.

- 누군가 콘솔에서 켰고 아무도 그 사실을 모른다
- 켜져 있고 문서에 적혀 있으며 신규 계정에도 수동으로 켠다
- IaC로 정의되어 있고 신규 계정에 자동 적용되며 꺼지면 SCP가 막는다
- 위에 더해 **트레일이 꺼졌을 때 몇 분 안에 알람이 오는지를 분기마다 실측한다**

네 상태의 리스크는 전혀 다릅니다. 그런데 체크리스트에서는 모두 "예"입니다. 성숙도 모델은 **"있다"의 품질을 구분하는 눈금자**입니다. 체크리스트가 커버리지를 재고, 성숙도가 깊이를 잽니다.

> 💡 **이 절의 성숙도 모델은 원서에 없습니다** — 근거 원서 3권 어디에도 5단계 성숙도 모델은 등장하지 않습니다. 아래 모델은 소프트웨어 공정 성숙도 모델(CMM) 계열에서 널리 쓰이는 5단계 어휘를, **이 책이 다룬 6개 통제 영역에 맞춰 재구성한 것**입니다. 원서가 뒷받침하는 것은 두 가지 원칙뿐입니다 — 📖 **"측정할 수 없으면 정당화할 수 없다"**(5장)와 📖 **"용납되지 않는 것은, 자신의 리스크가 무엇인지 전혀 모르거나, 리스크가 무엇인지 알면서도 결과를 따져 보지 않거나 이해관계자의 동의를 얻지 않고 그것을 수용하는 것이다"**(1장). 모델은 이 두 원칙을 진단 가능한 형태로 만드는 도구일 뿐이며, 레벨 숫자 자체에는 아무 권위가 없습니다.

### 5단계의 정의

각 단계는 다섯 개 축(수행 주체 · 문서화 · 자동화 · 측정 · 개선)으로 판정합니다.

| 레벨 | 이름 | 수행 주체 | 문서화 | 자동화 | 측정 | 개선 |
|---|---|---|---|---|---|---|
| **L1** | **임시 대응**(Ad hoc) | 아는 사람 한두 명 | 없음 | 없음(콘솔 수작업) | 없음 | 사고가 나면 그때 |
| **L2** | **반복 가능**(Repeatable) | 지정된 담당자 | 런북·위키 | 스크립트 일부 | 수동 집계 | 담당자 재량 |
| **L3** | **정의됨**(Defined) | 역할로 정의됨(RACI) | 표준·정책 문서 | IaC·파이프라인 | 정기 리포트 | 정기 리뷰 회의 |
| **L4** | **관리됨**(Managed) | 역할 + 백업 담당자 | 정책 + 예외 절차 | **가드레일로 강제** | **목표값 대비 추적** | 지표 이탈 시 자동 트리거 |
| **L5** | **최적화**(Optimizing) | 플랫폼팀 + 챔피언 | 정책이 코드 자체 | 자가 치유(SOAR) | **선행 지표 + 실측 검증** | 실험·훈련으로 상시 개선 |

**세 가지 판정 규칙**을 먼저 못 박습니다. 이 규칙이 없으면 성숙도 자가 진단은 거의 항상 부풀려집니다.

**규칙 ① — 레벨은 연속으로 채워야 인정한다.** L2 항목이 비어 있는데 L4 항목이 있다면 그 영역은 여전히 **L1**입니다. 흔한 예: SOAR 자동 대응(L5 항목)은 구축했는데 사고 대응 연락처가 최신이 아닌 조직(L2 항목 미달). 이것은 L5가 아니라 **비싼 L1**입니다. 도구를 산 것과 성숙한 것은 다릅니다.

**규칙 ② — 조직 전체 레벨은 6영역의 최솟값이다.** 평균이 아닙니다. 아이덴티티가 L4여도 탐지·대응이 L1이면 조직은 L1입니다. **공격자는 평균을 공격하지 않습니다.**

**규칙 ③ — 판정 증거는 API 출력이다.** "그렇게 하고 있습니다"라는 진술은 증거가 아닙니다. 각 항목에 대해 `aws` CLI 한 줄로 확인 가능한 근거를 요구하십시오. 증거를 붙일 수 없는 항목은 자동으로 한 단계 아래입니다.

### 영역 ① 아이덴티티 (2부, 6~11장)

| 레벨 | 판정 기준 |
|---|---|
| L1 | IAM 사용자에 장기 액세스 키를 발급해 쓴다. 루트 사용자를 가끔 쓴다. 퇴사자 계정 정리가 요청 기반 |
| L2 | 루트에 MFA가 있고 봉인되어 있다. 사용자별 MFA를 요구하지만 확인은 수동. 역할 사용이 늘었지만 키도 남아 있다 |
| L3 | IAM Identity Center로 인간 접근을 단일화했다. 워크로드는 역할로만 접근한다. 권한 세트가 IaC로 정의된다 |
| L4 | 인간 계정에 장기 키가 **SCP로 금지**되어 있다. 미사용 권한을 Access Analyzer로 정기 회수한다. 권한 변경이 PR 리뷰를 거친다 |
| L5 | 권한 부여가 기본 만료(JIT)이며, 접근 경로 분석 결과가 자동으로 정책 축소 PR을 만든다. 브레이크 글래스 사용이 분기마다 실측된다 |

### 영역 ② 데이터 (3부, 12~17장)

| 레벨 | 판정 기준 |
|---|---|
| L1 | 어떤 버킷에 어떤 데이터가 있는지 모른다. 암호화는 켜진 것도 있고 아닌 것도 있다. 백업은 있다고 믿는다 |
| L2 | 주요 데이터 저장소 목록이 문서에 있다. 기본 암호화를 켰다. 백업 작업이 돌고 있고 실패하면 메일이 온다 |
| L3 | `DataClass` 태그 표준이 있고 신규 리소스에 강제된다. 고객 관리 KMS 키를 등급별로 분리했다. 보존·삭제 정책이 문서화됐다 |
| L4 | 미분류 데이터 리소스 비율을 지표로 추적한다. 키 정책이 IaC이고 크로스 계정 사용이 조건으로 제한된다. **복원 훈련을 정기 실시**하고 성공률을 기록한다 |
| L5 | Macie 등으로 분류가 상시 검증된다. 논리적 격리 백업(변경 불가)이 자동 검증되고, 데이터 이동 경로가 정책으로 봉인되어 있다 |

### 영역 ③ 네트워크·컴퓨트 (4부, 18~24장)

| 레벨 | 판정 기준 |
|---|---|
| L1 | 보안 그룹에 `0.0.0.0/0`이 여럿 있고 이유를 아는 사람이 없다. SSH로 직접 들어간다. 퍼블릭 서브넷에 DB가 있다 |
| L2 | 3계층 서브넷 분리를 했다. 관리 접근을 배스천 한 곳으로 모았다. 보안 그룹 변경 시 리뷰를 한다 |
| L3 | 서브넷·라우팅·SG가 전부 IaC이며 SSM Session Manager로만 접근한다. VPC 엔드포인트로 프라이빗 경로가 정의됐다 |
| L4 | 인터넷 노출 자산 목록이 자동 산출되고 **승인된 목록과 diff**된다. IMDSv2·암호화 등 인스턴스 기본값이 가드레일로 강제된다 |
| L5 | 노출 표면 변화가 실시간 알람이 되고, 경계 통제가 침투 테스트·공격 표면 관리로 정기 검증된다 |

### 영역 ④ 취약점·공급망 (5부, 25~28장)

| 레벨 | 판정 기준 |
|---|---|
| L1 | 스캔이 없거나 연 1회다. 조치는 사고나 감사 지적 이후에 한다. 어떤 이미지가 어디서 왔는지 모른다 |
| L2 | Inspector 등 스캐너를 켰다. 심각 결과를 티켓으로 만든다. 기한은 있으나 지켜지는지 세지 않는다 |
| L3 | 심각도별 SLA가 정의되고 파이프라인에 스캔 게이트가 있다. 예외에 **만료일**이 붙는다. 기본 이미지가 중앙 관리된다 |
| L4 | **도구 커버리지 지표**를 산출하고 90% 미만이면 다른 지표를 발표하지 않는다. SLA 준수율과 재발률을 추적한다. SBOM을 생성·보관한다 |
| L5 | 패치가 기본 자동이고 사람은 실패분만 본다. 미탐(다른 경로로 발견된 취약점)을 세고 근본 원인을 분석한다. 아티팩트 서명·출처 검증이 배포 조건이다 |

### 영역 ⑤ 탐지·대응 (6부, 29~35장)

| 레벨 | 판정 기준 |
|---|---|
| L1 | CloudTrail이 일부 계정·리전에만 있다. 알람을 보는 사람이 정해져 있지 않다. 대응 계획서가 없다 |
| L2 | 조직 트레일과 중앙 로그 버킷이 있다. GuardDuty를 켰고 결과가 메일로 온다. 대응 담당자가 지정돼 있다 |
| L3 | 로그 아카이브 계정이 분리되고 보존 기간이 정의됐다. 플레이북이 시나리오별로 작성됐다. RACI와 심각도 등급이 있다 |
| L4 | **로그 커버리지와 MTTD/MTTR을 측정**한다. 탁상 훈련을 분기마다 하고 결함에 담당자·마감일이 붙는다. 격리·증거 보전이 런북 한 번 실행으로 끝난다 |
| L5 | 정형 사건은 자동 대응이 처리하고 사람은 판단이 필요한 것만 본다. **미탐 비율**(외부 제보·헌팅으로 발견된 사고 비율)을 추적한다. 사후 리뷰의 액션 아이템이 다음 훈련 시나리오가 된다 |

### 영역 ⑥ 거버넌스 (7부, 36~40장)

| 레벨 | 판정 기준 |
|---|---|
| L1 | 계정이 하나이거나, 여러 개인데 누가 만들었는지 모르는 것이 섞여 있다. 정책이 사람의 기억 속에 있다 |
| L2 | Organizations를 쓰고 OU가 있다. SCP를 몇 개 붙였다. 계정 생성 요청 절차가 문서에 있다 |
| L3 | OU 구조가 정책 경계로 설계됐고 코어 계정이 분리됐다. 신규 계정 베이스라인이 자동 적용된다. 컴플라이언스 매핑표가 있다 |
| L4 | **가드레일 적용 계정 비율을 지표로 추적**하고 예외에 만료일이 있다. Config 적합성 팩이 조직 전체에 배포된다. 감사 증거가 자동 수집된다 |
| L5 | 정책 변경이 코드 리뷰·시뮬레이션·단계 배포를 거친다. Well-Architected 리뷰가 정기 운영되고 그 결과가 로드맵에 직접 반영된다 |

### 진단 결과를 어떻게 쓸 것인가

여섯 영역을 판정하면 대개 **L1~L2에 한두 영역, L3에 대부분, L4에 한 영역**이 흩어진 모양이 나옵니다. 여기서 두 가지 유혹을 경계하십시오.

**유혹 ①: 가장 높은 영역을 더 올리기.** 자신 있는 영역을 L4에서 L5로 올리는 일은 즐겁지만 규칙 ②에 따라 조직 레벨은 변하지 않습니다. **투자는 항상 최솟값 영역에 갑니다.**

**유혹 ②: 모든 영역을 L5로.** L5는 목표가 아닙니다. 유지 비용이 큽니다. 목표 레벨은 다루는 데이터 등급과 규제 환경으로 정합니다.

| 조직 유형 | 아이덴티티 | 데이터 | 네트워크·컴퓨트 | 취약점 | 탐지·대응 | 거버넌스 |
|---|---|---|---|---|---|---|
| 스타트업(단일 계정, 비민감 데이터) | L3 | L2 | L2 | L2 | L2 | L2 |
| 성장 기업(개인정보 취급) | L4 | L4 | L3 | L3 | L3 | L3 |
| 규제 산업(금융·의료) | L5 | L5 | L4 | L4 | L4 | L4 |

L3→L4 사이가 이 표에서 가장 넓은 구간입니다. **L3까지는 "정의하고 자동화하면" 되지만, L4는 "측정해야" 하기 때문입니다.** 측정은 도구를 사서 되는 일이 아니라 분모를 정직하게 세는 일이고, 대부분의 조직이 여기서 멈춥니다. 39.2가 그 벽을 넘는 방법입니다.

진단 자체는 오래 걸리지 않습니다. **반나절짜리 작업으로 설계하십시오.** 여섯 영역을 각각 30분씩 보고, 영역마다 L1부터 아래로 읽어 내려가며 "이 줄의 모든 조건이 참인가"를 묻습니다. 처음 거짓이 나오는 줄의 **바로 위**가 현재 레벨입니다. 조건이 애매하면 낮은 쪽으로 판정하십시오 — 성숙도 진단에서 관대함은 언제나 나중에 사고로 청구됩니다.

기록은 세 칸이면 충분합니다. **판정 레벨 · 근거가 된 API 출력 또는 문서 링크 · 다음 레벨로 가기 위해 빠진 항목 한 줄.** 세 번째 칸이 그대로 다음 분기의 로드맵이 되고, 40.4의 12개월 계획이 여기서 출발합니다. 반기마다 같은 표를 다시 채우고 **이전 판정과 나란히 두면**, 어느 영역이 실제로 움직였고 어느 영역이 말만 바뀌었는지가 한눈에 드러납니다.

> ⚠️ **성숙도 레벨을 KPI로 걸지 마십시오.** 레벨이 인사 평가에 연결되는 순간 자가 진단은 반드시 인플레이션됩니다. 25.6에서 본 "MTTR을 낮추려고 심각도를 낮추는" 현상과 똑같은 구조입니다. 레벨은 **투자 우선순위를 정하는 내부 도구**로만 쓰고, 판정은 해당 영역을 운영하지 않는 사람이 증거를 보고 하도록 교차 검증하십시오.

## 39.2 🔴 경영진에게 보고할 지표

### 운영 지표와 보고 지표는 다르다

25.5는 취약점 관리 여섯 지표를, 32.6은 탐지·대응 네 지표를 다뤘습니다. **이 절은 그것들을 반복하지 않습니다.** 두 절의 지표는 **운영 팀이 자기 프로세스를 고치기 위한** 지표입니다. 경영진 보고 지표는 목적이 다릅니다 — **의사결정과 자원 배분**입니다. 그래서 세 가지 원칙이 다르게 적용됩니다.

**원칙 ① — 모든 지표에 분모를 붙인다.** 25.6의 최대 함정이 그대로 재현되기 때문입니다. "심각 취약점 0건"이 아니라 **"대상 40대 중 40대 스캔, 심각 0건"** 입니다. 분모 없는 숫자는 보고서에서 삭제하십시오.

**원칙 ② — 절대치가 아니라 추세와 목표 대비다.** 경영진은 340이라는 숫자로 아무것도 결정할 수 없습니다. "목표 200, 현재 340, 3개월 전 520"이면 결정할 수 있습니다.

**원칙 ③ — 숫자마다 "그래서 무엇을 결정해 달라는 것인가"가 붙는다.** 결정을 요구하지 않는 지표는 보고서가 아니라 대시보드에 두십시오. 분기 보고서에 지표가 12개라면 결정 요청은 2~3개면 충분합니다.

> 📖 1판·2판 5장은 지표를 **"유용하지만 위험한 것"** 이라 부르고 이렇게 덧붙입니다. **"지표와 결과를 검토하는 프로세스에, 지표가 나쁜 방향으로 가는 데 합당한 정상참작 요인이 있는지 혹은 지표가 어떤 식으로든 조작되고 있는지 점검하는 과정을 반드시 포함시켜라."**
>
> 팀 간 비교에 대한 단서도 함께 봅니다. 📖 **"때로는 약간의 선의의 경쟁이 팀에 동기를 부여하지만, 어떤 팀은 본래 취약점 관리를 따라가기가 다른 팀보다 더 어렵다는 점을 기억하라."** — **경영진 보고서에서 팀별 순위표를 만들 때 이 문장을 반드시 함께 읽으십시오.** 레거시를 떠안은 팀이 항상 꼴찌인 순위표는 개선이 아니라 이직을 만듭니다.

### 🔴 열두 개 지표

**분기 보고서에 이 열두 개를 모두 넣으십시오. 그리고 열세 번째를 만들지 마십시오.** 지표가 늘어날수록 보고서는 읽히지 않고, 읽히지 않는 보고서는 결정을 만들지 못합니다.

| # | 지표 | 정의(경영진에게 하는 한 문장) | AWS에서의 측정 방법 | 목표값 설정 방법 |
|---|---|---|---|---|
| 1 | **보안 표준 준수 점수** | 우리 환경이 업계 표준 통제 목록을 몇 % 통과하는가 | Security Hub 보안 점수 = 통과 컨트롤 수 ÷ 활성 컨트롤 수. 표준별·계정별로 분해 | 현재값에서 시작해 **분기 +5%p**. 100%를 첫 목표로 삼지 말 것 |

**경영진이 실제로 묻는 다섯 질문**은 이 열두 개 위에 이렇게 얹힙니다 — **커버리지**(지표 2·6·8·9), **미조치 위험**(3·12), **탐지·대응 속도**(4·10), **가드레일 적용률**(8), **사고 추세**(4·10). 이 중 **미조치 위험**만은 비율이 아니라 **절대 잔량**으로 함께 보고하십시오. "SLA 준수율 94%"는 좋아 보이지만 "기한을 넘긴 심각 취약점이 지금 몇 건이고 가장 오래된 것이 며칠째인가"에는 답하지 못합니다. 🔴 **지표 3에는 준수율과 함께 ⓐ 기한 초과 건수 ⓑ 최장 경과 일수 ⓒ 전 분기 대비 증감을 반드시 붙이십시오.** 세 숫자가 "지금 우리가 안고 있는 알려진 위험의 크기"이며, 경영진이 예산을 배정할 때 실제로 근거로 삼는 것은 비율이 아니라 이 잔량입니다. 같은 이유로 지표 12의 예외 건수도 **만료 초과 건수와 최장 경과 일수**를 함께 적습니다.

12번 지표를 마지막에 둔 이유가 있습니다. 📖 1판·2판 1장은 리스크에 대해 할 수 있는 일을 네 가지로 정리합니다 — **"리스크를 회피한다 · 완화한다 · 전가한다 · 수용한다."** 그리고 못을 박습니다. 📖 **"이 중 어느 것이든 합리적일 수 있다. 그러나 용납되지 않는 것은, 자신의 리스크가 무엇인지 전혀 모르거나, 리스크가 무엇인지 알면서도 결과를 따져 보지 않거나 이해관계자의 동의를 얻지 않고 그것을 수용하는 것이다. 최소한, 알고 있는 리스크와 취한 조치, 필요한 승인을 상세히 적은 목록을 스프레드시트나 문서 어딘가에 두어야 한다."**

**12번은 그 "이해관계자의 동의"를 분기마다 갱신하는 장치입니다.** 예외 목록을 경영진 보고서에 넣지 않으면, 보안팀이 조용히 떠안은 리스크가 어느 날 경영진의 "왜 몰랐느냐"로 돌아옵니다.

### ⚠️ 각 지표가 왜곡되는 방식

**모든 지표는 조작 가능합니다.** 중요한 것은 조작 경로를 미리 알고 보조 지표로 막는 것입니다.

| # | ⚠️ 이 지표가 왜곡되는 방식 | 함께 봐야 할 보조 지표 |
|---|---|---|
| 1 | 점수가 낮은 표준을 비활성화하거나 컨트롤을 개별 비활성화하면 점수가 오른다 | **활성 컨트롤 수 자체의 추이.** 컨트롤 비활성화 API 호출 건수 |
| 2 | 위반이 많이 나오는 규칙을 삭제하거나 범위(스코프)를 좁히면 준수율이 오른다 | **평가 대상 리소스 수**와 규칙 개수의 추이 |
| 3 | 심각도를 낮추거나 예외 처리하면 SLA 준수율이 오른다(25.6 함정 ②와 동일) | **심각도 하향 건수**, 예외 신규 등록 건수, 재발률 |
| 4 | GuardDuty 보호 플랜을 끄거나 억제 규칙을 남발하면 건수가 준다 | **활성 보호 플랜 수**, 억제 규칙으로 사라진 건수 |
| 5 | 옛 키를 지우지 않고 비활성(Inactive) 상태로만 남기거나, 새 키를 추가 발급해 교체일만 갱신하면 "90일 초과"에서 빠진다 | 계정별 **총 액세스 키 수**(비활성 포함), 서비스 계정 예외 목록 |
| 6 | 분모를 "활성 사용자"로 정의하고 휴면 사용자를 제외하면 100%가 쉽게 나온다 | **전체 프린시펄 수 대비** 비율, 휴면 사용자 정리 건수 |
| 7 | 백업 작업 자체를 줄이거나 실패하는 리소스를 백업 계획에서 빼면 성공률이 오른다 | **백업 대상 리소스 수**(태그 기준 커버리지), 복원 실측 성공률 |
| 8 | 통제가 약한 SCP를 만들어 붙이고 "적용됨"으로 집계한다 | 적용된 SCP의 **실제 Deny 액션 수**, 예외 OU에 있는 계정 수 |
| 9 | 트레일은 켜져 있지만 데이터 이벤트·플로우 로그가 없어 정작 조사가 안 된다 | **로그 유형별** 커버리지 분해, 사고 시 "필요한 로그가 없었던" 횟수 |
| 10 | 탐지 못 한 사고는 계산에 안 들어가므로, 탐지가 나쁠수록 MTTD가 좋아 보인다(32.6) | **미탐 비율** — 외부 제보·감사·헌팅으로 발견된 사고의 비율 |
| 11 | 훈련을 형식적으로 30분 만에 끝내도 "실시함"으로 집계된다 | 훈련당 **도출된 결함 수**와 그 결함의 마감 준수율 |
| 12 | 예외를 등록하지 않고 그냥 방치하면 건수가 0으로 보인다 | 규칙 위반 상태로 **예외 등록 없이 남아 있는** 리소스 수 |

> ⚠️ **왜곡의 공통 구조** — 12개 중 8개가 **분모를 줄이는 방식**입니다. 통제를 끄고, 범위를 좁히고, 대상에서 빼면 거의 모든 비율 지표가 좋아집니다. 그래서 보조 지표의 대부분이 **분모의 추이**입니다. 🔴 **보고서 설계 규칙을 하나만 고르라면 이것입니다 — 모든 비율 옆에 분모의 절대 숫자를 함께 적으십시오.** "98%"가 아니라 **"1,240개 중 1,215개(98%)"** 입니다. 분모가 지난 분기 2,100에서 1,240으로 줄었다면, 98%는 개선이 아니라 은폐입니다.

## 39.3 보안 챔피언과 조직 구조

### 두 모델과 그 사이

| 항목 | 중앙 집중형(Centralized) | 임베디드형(보안 챔피언) | 하이브리드(플랫폼형) |
|---|---|---|---|
| 배치 | 보안팀이 전담 조직으로 존재 | 각 개발팀에 보안 담당 역할 지정 | 중앙 플랫폼팀 + 팀별 챔피언 |
| 의사결정 | 보안팀이 승인·차단 | 팀이 결정, 보안팀은 자문 | **가드레일은 중앙, 그 안에서는 팀 자율** |
| 강점 | 표준 일관성, 전문성 축적, 감사 대응 용이 | 맥락 이해, 속도, 마찰 적음 | 일관성과 속도를 동시에 |
| 약점 | **병목·게이트키퍼화**, 팀 맥락 무지 | 표준 파편화, 챔피언 역량 편차, 우선순위 밀림 | 초기 구축 비용이 큼 |
| 확장성 | 개발팀 수에 선형으로 인력 필요 | 팀이 늘어도 중앙 인력 불변 | 팀이 늘어도 **가드레일 재사용** |
| 실패 신호 | "보안팀 승인 대기 3주" | "그 팀만 유독 사고가 잦다" | 플랫폼이 실제로 안 쓰이고 우회됨 |

| 조직 규모 | 권장 모델 | 최소 구성 |
|---|---|---|
| 개발자 ~20명 | 중앙 집중(겸직 1명) | 보안 겸직 1명 + 외부 자문. **자동화로 인력을 대체** |
| 20~100명 | 중앙 집중 + 챔피언 시작 | 전담 1~3명 + 팀당 챔피언 1명 |
| 100~500명 | 하이브리드 | 플랫폼팀 3~8명 + 챔피언 네트워크 + 대응 온콜 |
| 500명 이상 | 하이브리드 + 기능 분화 | 플랫폼 / 탐지·대응 / 거버넌스·컴플라이언스 분리 |

작은 조직에서 흔한 오해 하나를 짚습니다. **"우리는 보안 전담이 없으니 아무것도 못 한다"는 것은 사실이 아닙니다.** 원서가 반복하는 조언이 정확히 여기에 적용됩니다.

> 📖 2판 5장: **"이 책에서 여러 번 반복했듯이, 가장 큰 효과를 내는 것부터 하라(go for the biggest bang for the buck first) — 조직에서 가장 중요한 영역을 골라 거기서 가치를 얻은 뒤에 다른 영역으로 넘어가라. 흔한 함정은, 어딘가의 모범 사례 목록에 체크 표시를 하려고 네다섯 벌의 서로 다른 도구와 프로세스를 갖춰 두었는데 정작 그중 어느 것도 취약점을 찾고 고치는 데 큰 가치를 주지 못하는 것이다."**

**겸직 1명 조직의 정답은 "도구를 다섯 개 사는 것"이 아니라 "루트 MFA·조직 트레일·GuardDuty·백업·BPA 다섯 개를 켜고 자동화하는 것"입니다.** 40.1이 그 우선순위 목록을 다룹니다.

### 게이트키퍼에서 플랫폼 제공자로

중앙 집중형이 실패하는 지점은 인력 부족이 아니라 **역할 설정**입니다. 보안팀이 "승인하는 사람"이 되면 개발팀에게 보안은 **일정에 붙는 세금**이 되고, 세금은 언제나 회피 대상이 됩니다. 파이프라인 밖에서 콘솔로 리소스를 만드는 행동의 절반은 게으름이 아니라 **회피**입니다.

전환의 핵심은 하나입니다 — **보안팀의 산출물을 "승인"에서 "기본값"으로 바꾸는 것.**

| 게이트키퍼 모델 | 플랫폼 모델 | 이 책의 근거 |
|---|---|---|
| 배포 전에 보안팀이 검토·승인 | **정책이 파이프라인에서 자동 판정**, 사람 승인은 예외 건만 | 28.3 정책 게이트 |
| 신규 계정에 보안 설정을 요청하면 해 줌 | **계정 생성 즉시 베이스라인이 자동 적용** | 37.9 베이스라인 자동화 |
| "이렇게 만들면 안 됩니다" 문서를 배포 | **안전한 모듈·템플릿을 제공**하고 그것을 쓰면 통과 | 28.1 IaC |
| 위반을 발견하면 티켓을 발행 | 위반 발견 시 **수정 PR을 자동 생성** | 26.6 CSPM, 35장 대응 자동화 |
| 예외를 메일로 승인 | 예외를 **코드로 등록**하고 만료일을 강제 | 25.3, 39.2 지표 12 |

전환이 성공했는지는 **보안팀에 오는 요청의 성격**으로 알 수 있습니다. "이거 해 주세요"가 줄고 "이 모듈에 이런 옵션을 추가해 주세요"가 늘면 전환된 것입니다.

**보안팀도 SLA를 공표하십시오.** 개발팀에는 취약점 조치 SLA를 요구하면서 보안팀의 예외 심사·문의 응답에 기한이 없으면, 그 비대칭이 곧 마찰의 원인입니다. 예외 심사 3영업일, 신규 모듈 요청 2주 같은 숫자를 먼저 내걸고 지키십시오.

### 마찰을 줄이는 다섯 가지 실천

보안팀과 개발팀의 마찰은 대개 **의견 차이**가 아니라 **구조**에서 나옵니다. 다섯 가지가 구조를 바꿉니다.

**① 골든 패스를 하나 만든다.** "이 모듈로 만들면 모든 게이트를 통과합니다"라는 경로가 하나 있어야 합니다. 통제가 열 개여도 개발자가 외울 것은 **경로 하나**입니다. 골든 패스 밖으로 나가는 것을 금지하지는 말고, **나가는 순간 리뷰와 설명 의무가 생기게** 하십시오. 금지는 우회를 낳지만, 비용 차이는 선택을 바꿉니다.

**② 실패 메시지에 해결책을 넣는다.** 게이트가 "정책 위반"만 뱉으면 개발자는 보안팀에 문의합니다. **위반한 규칙 이름 · 왜 위험한지 한 줄 · 고치는 방법 · 예외 신청 링크** 네 가지를 실패 메시지에 담으면 문의의 대부분이 사라집니다. 보안팀 시간을 가장 크게 아끼는 투자입니다.

**③ 피드백을 왼쪽으로 옮긴다.** 같은 위반이라도 PR에서 3분 뒤 알려 주는 것과 배포 후 CSPM이 이틀 뒤 티켓을 발행하는 것은 완전히 다른 경험입니다. 후자는 이미 끝난 일을 다시 여는 것이라 **감정적 저항이 가장 큽니다**(28.3).

**④ 예외를 정식 제품으로 취급한다.** 예외 신청이 어렵고 느리면 사람들은 신청하지 않고 그냥 우회합니다. 그러면 39.2의 지표 12가 0으로 보이고, 실제 리스크는 보이지 않는 곳에 쌓입니다. **신청은 쉽게, 만료는 엄격하게** — 이것이 예외 제도의 유일한 설계 원칙입니다.

**⑤ 보안팀도 자기 지표를 공개한다.** 예외 심사 소요 시간, 문의 응답 시간, 게이트 오탐률을 개발팀에게 보여 주십시오. 특히 **게이트 오탐률**은 강력합니다 — 보안팀이 스스로의 도구가 만든 헛수고를 세고 있다는 사실만으로 관계의 성격이 바뀝니다.

### 챔피언 프로그램 운영 실무

| 항목 | 권장 설계 | ⚠️ 흔한 실패 |
|---|---|---|
| 선발 | **자원 + 팀장 동의.** 보안 경력 불필요, 그 팀 코드베이스를 잘 아는 사람 | 신입에게 떠넘김 → 영향력 없음 |
| 시간 | 업무 시간의 **10~20%를 공식 배정** | "관심 있으면 하세요" → 아무도 안 함 |
| 권한 | 예외 1차 승인권, 자기 팀 보안 백로그 우선순위 결정권 | 책임만 있고 권한 없음 → 1분기 만에 소멸 |
| 교육 | 분기 1회 집합 + 실제 사고 사례 공유. **훈련(32.5)에 챔피언 참여** | 온라인 교육 이수증만 수집 |
| 보상 | 인사 평가 항목에 명시, 성과 공개 | 무보수 추가 업무 |
| 네트워크 | 챔피언 전용 채널 + 격주 30분 싱크 | 1:1로만 소통 → 지식이 확산되지 않음 |
| 교체 | **임기 1년 + 후임 인수인계 필수** | 한 사람이 3년째 → 그 사람 퇴사 시 초기화 |

> ⚠️ **챔피언 모델의 실패 시나리오** — 챔피언을 지정하고 6개월 뒤, 보안팀은 "챔피언이 있으니 각 팀이 알아서 한다"고 믿고 손을 뗍니다. 챔피언은 본업에 밀려 아무것도 못 했는데, 이제는 **책임 소재만 챔피언에게 옮겨진 상태**입니다. 사고가 나면 챔피언 개인이 문책 대상이 되고, 다음 챔피언 모집은 실패합니다.
>
> **원인.** 챔피언 모델을 **인력 절감 수단**으로 도입했기 때문입니다. 챔피언은 중앙 보안 역량을 대체하지 않습니다. **가드레일과 플랫폼이 이미 있는 조직에서, 그 위의 판단을 분산시키는 장치**입니다.
>
> **올바른 구성.** 도입 전에 세 가지를 갖추십시오 — **(가)** 자동 판정되는 정책 게이트(28.3), **(나)** 신규 계정·리소스의 안전한 기본값(37.9), **(다)** 챔피언이 답을 찾을 수 있는 문서와 채널. 그리고 챔피언의 성과는 **"우리 팀 위반 건수"가 아니라 "챔피언이 사전에 잡아낸 건수"** 로 측정하십시오. 전자는 숨기게 만들고, 후자는 드러내게 만듭니다.

## 39.4 비용과 보안의 균형

### 평가의 기본 틀

"보안 비용이 너무 많이 나옵니다"라는 말은 대개 **비용의 총액**을 보고 나옵니다. 하지만 결정에 필요한 것은 총액이 아니라 **통제별 단가와 그 통제가 없앤 리스크의 비교**입니다. 원서 1장이 정의한 리스크의 구조를 그대로 씁니다.

> 📖 1판 1장: **"대부분의 리스크 관리 체계에서 리스크의 수준은 그 나쁜 일이 일어날 확률(likelihood)과 일어났을 때 결과가 얼마나 나쁜가(impact)의 조합으로 정해진다."** (2판은 같은 장에서 이를 **"리스크 관리의 가장 쉬운 형태는 나쁜 일이 일어날 확률과 일어났을 때 얼마나 나쁠지를 추정하고, 그 조합에 근거해 결정하는 것"** 으로 다시 씁니다.)

따라서 통제의 가치는 두 가지 중 하나입니다 — **발생 확률을 낮추거나, 영향을 줄이거나.** 평가표는 이렇게 만듭니다.

| 축 | 물어볼 것 |
|---|---|
| 연간 비용 | 무엇에 비례하는가(고정 / 리소스 수 / 데이터량 / 요청 수). **성장하면 얼마나 빨리 늘어나는가** |
| 확률 감소 | 이 통제가 없으면 사고가 더 자주 나는가. 예방 통제인가 |
| 영향 감소 | 사고가 나도 피해가 작아지는가. 조사·복구가 가능해지는가 |
| 대체 가능성 | 더 싼 수단으로 같은 효과를 내는가(예: NAT 대신 엔드포인트) |
| 중단 시 회복 비용 | 껐다가 다시 켤 때, **꺼져 있던 기간의 데이터는 돌아오지 않는가** |

마지막 축이 로그·탐지 계열 서비스의 핵심입니다. WAF는 껐다 켜면 즉시 같은 상태로 돌아오지만, **CloudTrail 데이터 이벤트를 3개월 껐다면 그 3개월은 영원히 조사 불가입니다.** 비용 절감 논의에서 이 두 부류를 반드시 분리하십시오.

> ⚠️ **정밀한 금액을 계산하려 하지 마십시오.** 📖 1판·2판 1장은 **"인간은 리스크를 평가하고 그것에 대해 무엇을 할지 정하는 데 정말 서투르다"** 고 말합니다. 사고 손실액을 소수점까지 추정한 스프레드시트는 정확해 보이지만 근거가 없습니다. **필요한 것은 순위입니다** — 통제 15개를 비용 대비 효과로 줄 세우고, 예산이 끊기는 지점을 표시하는 것으로 충분합니다.

### 통제별 비용의 성격

⚠️ **아래 표에 단가는 없습니다.** AWS 요금은 리전·시점·약정에 따라 바뀌므로, 여기서 외워야 할 것은 **"이 비용이 무엇에 비례해서 커지는가"** 뿐입니다. 실제 금액은 Cost Explorer에서 서비스별로 직접 확인하십시오.

| 통제 | 비용이 비례하는 것 | 성격 | 주요 절감 기법 |
|---|---|---|---|
| **CloudTrail 관리 이벤트** | 조직 트레일 첫 사본은 추가 과금 없음. **중복 트레일**을 만들면 그때부터 비용 | 사실상 고정 | 계정별 개별 트레일을 없애고 **조직 트레일 하나**로 통합 |
| **CloudTrail 데이터 이벤트** | 기록된 **이벤트 건수** — S3 객체 접근·Lambda 호출량에 직결 | 워크로드에 비례해 급증 | **고급 이벤트 셀렉터**로 고가치 리소스만 선별. 로그 버킷 자체의 읽기는 제외 |
| **AWS Config** | 기록된 **구성 항목(CI) 수** + **규칙 평가 수** | 변경이 잦을수록 급증 | 노이즈 리소스 유형 제외, **기록 주기를 일별로** 전환, 미사용 리전 레코더 중지 |
| **Security Hub** | **보안 검사 수** + 수집된 **결과(finding) 수** | 계정·리소스 수에 비례 | 쓰지 않는 표준 비활성화(단, 지표 1의 분모 변화를 보고서에 명시) |
| **GuardDuty** | 분석한 **CloudTrail 관리 이벤트량 · VPC 플로우 로그량 · DNS 쿼리량** + 보호 플랜별 추가 | 트래픽에 비례 | 플로우 로그와 **이중 비용 아님**(GuardDuty는 자체 경로로 수집). 비운영 계정도 끄지 말 것 |
| **Inspector** | 스캔한 **인스턴스 시간 · 컨테이너 이미지 수 · Lambda 함수 수** | 자산 수에 비례 | 이미지 재스캔 기간 조정, 폐기 이미지 정리 |
| **Macie** | 버킷 **인벤토리**(버킷 수) + 민감 데이터 검색 **스캔 GB** | 데이터량에 비례 | 상시 전수 스캔 대신 **샘플링 + 신규 객체 중심**, 대상 버킷 한정 |
| **WAF** | 웹 ACL 수 + **규칙 수** + 처리 **요청 수** | 트래픽에 비례 | 중복 규칙 그룹 정리, 봇 제어는 필요한 리소스에만 |
| **Shield Advanced** | **고정 구독료**(조직 단위) + 보호 리소스 관련 요금. 연 단위 약정 | 완전 고정 | 규모가 작으면 기본 제공되는 Shield 표준 + WAF 요율 기반 규칙으로 대체 검토 |
| **KMS** | **키 수**(월별) + **API 요청 수** | 요청 수가 지배적 | **S3 Bucket Keys**로 요청 수 대폭 감소, 데이터 키 캐싱 |
| **CloudWatch Logs** | **수집 GB** + 저장 GB + 쿼리 **스캔 GB** | 로그량에 비례 | 저빈도 조회 로그 그룹을 **Infrequent Access 클래스**로, 보존 기간 축소 후 S3 아카이브 |
| **NAT 게이트웨이** | **시간당 요금** + **처리 GB** | 아웃바운드 트래픽에 비례 | S3·DynamoDB **게이트웨이 엔드포인트**로 대체(추가 요금 없음) |
| **인터페이스 엔드포인트** | AZ당 **시간당 요금** + 처리 GB | 엔드포인트 개수에 비례 | 트래픽이 적은 서비스는 NAT 경유가 오히려 저렴 — **손익분기 계산** |
| **크로스 계정·리전 로그 복제** | 전송 **GB** | 로그량에 비례 | 원본 리전 집계 후 요약만 복제, 압축·Parquet |

### 절감 기법 여섯 가지

**① 게이트웨이 엔드포인트로 NAT 처리량을 대체한다.** ShopMini의 앱 계층이 `shopmini-uploads`에 쓰는 트래픽이 NAT를 지나면 **시간 요금과 처리 GB를 둘 다** 냅니다. S3·DynamoDB 게이트웨이 엔드포인트는 추가 요금이 없고, 라우팅 테이블에 프리픽스 목록을 추가하는 것으로 끝납니다. **보안과 비용이 같은 방향인 드문 사례** — 트래픽이 인터넷으로 나가지 않으므로 20.3의 데이터 유출 경로도 함께 좁아집니다. 반면 인터페이스 엔드포인트는 AZ마다 시간 요금이 붙으므로, **호출량이 적은 서비스까지 전부 엔드포인트로 만들면 NAT보다 비싸집니다.** "프라이빗 서브넷에서 쓰는 서비스 전부"가 아니라 **트래픽 상위 몇 개**부터 만드십시오.

**② S3 Bucket Keys로 KMS 요청을 줄인다.** SSE-KMS 버킷은 객체마다 KMS를 호출하므로, 객체 수가 많으면 KMS 요청 비용이 스토리지 비용을 넘기기도 합니다. 버킷 키를 켜면 버킷 수준에서 단기 키를 만들어 **KMS 호출 횟수가 크게 줍니다.** 암호화 강도는 유지되고 설정은 버킷 속성 하나입니다. **로그 버킷처럼 객체가 끝없이 쌓이는 곳에 우선 적용하십시오.**

**③ 로그를 계층으로 보존한다.** 29장의 보존 정책을 비용 관점에서 다시 봅니다. 최근 로그는 CloudWatch Logs에서 즉시 검색 가능해야 하지만, 6개월 전 로그는 **Athena로 몇 분 걸려도 됩니다.** 최근 30~90일은 CloudWatch Logs(저빈도 그룹은 Infrequent Access 클래스), 그 이후는 S3, 1년 이후는 아카이브 스토리지 클래스로 내리고, S3에서는 **연·월·일 파티션 + 압축 포맷**으로 저장해 Athena 스캔량을 줄입니다. ⚠️ **보존 기간 자체를 줄여 비용을 맞추지 마십시오.** 38장의 규제 요구와 32장의 조사 가능 기간이 하한선입니다.

**④ Config 기록 범위를 조정한다.** Config 비용의 대부분은 **자주 바뀌는 리소스 유형**에서 나옵니다. Auto Scaling으로 인스턴스가 하루에 수백 번 뜨고 지는 환경이라면 그 유형의 구성 항목이 그만큼 기록됩니다. 세 가지 손잡이가 있습니다 — 기록 대상 리소스 유형 선별, **일별 기록 주기**(연속 기록이 필요 없는 유형), 미사용 리전 레코더 중지. ⚠️ 단, **보안 규칙이 평가하는 리소스 유형은 절대 제외하지 마십시오.** 제외하면 지표 2의 준수율이 조용히 왜곡됩니다(39.2 왜곡 표 #2).

**⑤ CloudTrail 데이터 이벤트를 선별한다.** 모든 S3 버킷의 모든 객체 이벤트를 켜면 비용이 트래픽에 그대로 붙습니다. 고급 이벤트 셀렉터로 **`DataClass=Confidential` 버킷과 시크릿 관련 리소스만** 기록하고, 로그 버킷 자체에 대한 읽기처럼 대량이면서 가치가 낮은 이벤트는 제외합니다. 다만 이 선별은 **명시적 결정으로 문서에 남기십시오** — 사고 조사에서 "왜 이 버킷은 기록이 없습니까"라는 질문이 반드시 옵니다.

**⑥ 플로우 로그를 S3로 직행시킨다.** VPC 플로우 로그를 CloudWatch Logs로 보내면 수집 GB 요금이 붙습니다. 실시간 알람이 필요 없다면 **S3로 직접 전달**하고 압축 포맷·시간 단위 파티션을 쓰는 편이 훨씬 쌉니다. 샘플링 비율을 낮추는 방법도 있지만, **샘플링된 플로우 로그는 사고 조사에서 "그 연결이 있었는지 없었는지"를 답하지 못합니다.** 줄이려면 샘플링이 아니라 **대상 서브넷을 선별**하십시오.

### 🔴 비용 때문에 끄면 안 되는 것

**아래 항목은 비용 절감 대상에서 제외하십시오.** 각 항목의 오른쪽 칸이 껐을 때 실제로 벌어지는 일입니다.

| 통제 | 끄면 벌어지는 일 |
|---|---|
| **조직 CloudTrail(관리 이벤트)** | 사고 조사의 유일한 기준선이 사라진다. 꺼져 있던 기간은 **영원히 복구 불가**. 게다가 첫 사본은 추가 과금이 없다 |
| **로그 아카이브 계정의 객체 잠금·버전 관리** | 공격자가 흔적을 지울 수 있게 된다. 랜섬웨어 시 로그까지 암호화된다 |
| **GuardDuty(모든 계정·리전)** | 미사용 리전이 크립토마이닝의 무대가 된다. **비용이 거의 안 드는 리전을 끄는 것이 가장 흔한 실수** |
| **S3 퍼블릭 액세스 차단** | 비용이 0인데 끄는 사람이 있다. 15장의 최대 사고 유형이 즉시 재현된다 |
| **MFA(모든 인간 계정, 특히 루트)** | 비용 0. 자격 증명 유출이 곧 계정 탈취가 된다 |
| **백업과 복원 검증** | 랜섬웨어·삭제 사고에서 복구 수단이 없어진다. **백업만 있고 복원 검증이 없는 것도 같은 결과** |
| **Config 핵심 규칙군** | 지표 2의 분모가 사라져 준수율이 거짓이 된다. 드리프트를 아무도 모른다 |
| **KMS 고객 관리 키(등급 분리)** | 키 개수를 줄이려고 하나로 합치면 **크로스 계정·크로스 등급 접근 통제가 무너진다** |
| **보안 연락처·예산 알림** | 침해 통보와 이상 과금(크립토마이닝의 첫 신호)을 놓친다 |

> ⚠️ **사고 시나리오** — 비용 절감 과제에서 "거의 조회하지 않는" VPC 플로우 로그와 S3 데이터 이벤트를 끕니다. 4개월 뒤 침해가 확인되고, 조사팀이 "언제부터 어떤 데이터가 나갔는가"에 답해야 합니다. 답할 수 없습니다. 규제 신고서에는 **"유출 범위 확인 불가"** 를 써야 하고, 이 문구는 통지 대상을 **최대 범위로 가정**하게 만듭니다. 통지 비용과 신뢰 손실이 4개월치 로그 비용의 수십 배가 됩니다.
>
> **원인.** 로그 비용을 **"조회 빈도"** 로 평가했기 때문입니다. 로그의 가치는 평소 조회 횟수가 아니라 **사고 한 번에서의 답변 능력**에 있습니다.
>
> **올바른 구성.** 로그는 끄는 것이 아니라 **내리는 것**입니다. 절감 기법 ③·⑥처럼 저장 계층을 낮추고 포맷을 바꾸십시오. 그래도 예산이 부족하면 **범위를 줄이되(데이터 등급 상위 버킷만) 그 결정을 리스크 등록부에 등재하고 만료일을 붙이십시오** — 39.2의 지표 12가 이 결정을 분기마다 다시 꺼내 놓습니다.

## 39.5 🧪 AWS Well-Architected 보안 기둥 리뷰

### Well-Architected Tool이 하는 일

> 📖 *AWS Security Cookbook* 10장은 이 서비스를 한 줄로 소개합니다. **"AWS Well-Architected Tool은 AWS Well-Architected Framework에 기반한 관리 서비스다. 워크로드를 현재의 AWS 모범 사례에 비추어 정의할 수 있고, 이 도구가 우리의 클라우드 아키텍처를 어떻게 개선할지에 대한 지침을 제공한다."**

원서의 언급은 여기까지입니다. 아래의 설계 원칙 매핑과 운영 절차는 **AWS 공식 프레임워크 문서와 실무 관행을 이 책의 구조에 맞춰 정리한 것**이며, 원서 인용이 아닙니다.

### 보안 기둥의 7개 설계 원칙 → 이 책 매핑

| # | 설계 원칙 | 무엇을 요구하는가 | 이 책의 해당 부·장 |
|---|---|---|---|
| 1 | **강력한 아이덴티티 기반 구현**<br>(Implement a strong identity foundation) | 최소 권한, 직무 분리, 중앙 집중 아이덴티티, 장기 자격 증명 제거 | **2부 6~11장** — 특히 7장(정책 평가), 8장(역할·임시 자격 증명), 9장(Identity Center) |
| 2 | **추적성 확보**<br>(Enable traceability) | 모든 행위에 대한 로그·지표·감사, 실시간 알림과 자동 조사 | **6부 29~31장** — CloudTrail·중앙 로깅·GuardDuty·Security Hub |
| 3 | **모든 계층에 보안 적용**<br>(Apply security at all layers) | 엣지·VPC·서브넷·인스턴스·OS·애플리케이션 각각에 통제 | **1부 1장**(심층 방어) + **4부 18~24장** — 특히 19장(SG·NACL), 23장(엣지·WAF) |
| 4 | **보안 모범 사례 자동화**<br>(Automate security best practices) | 코드로 정의된 통제, 버전 관리, 자동 배포·자동 대응 | **5부 28장**(IaC·게이트) + **6부 35장**(SOAR·자동 대응) + **7부 37장**(가드레일) |
| 5 | **전송 중·저장 데이터 보호**<br>(Protect data in transit and at rest) | 분류, 암호화, 토큰화, 접근 통제 | **3부 12~17장** — 13·14장(KMS·키 관리), 15·16장(저장 데이터) + **23장**(전송 중 TLS) |
| 6 | **데이터에 사람 접근 최소화**<br>(Keep people away from data) | 직접 접근·수동 처리를 없애는 메커니즘과 도구 | **3부 12장**(분류·태깅) + **4부 21.6**(Session Manager) + **6부 34장**(포렌식 자동화) |
| 7 | **보안 이벤트 대비**<br>(Prepare for security events) | 대응 정책·플레이북, 시뮬레이션, 탐지·조사·복구 속도 | **6부 32~35장** — 대응 팀·플레이북·훈련·실행·포렌식·자동화 |

> 💡 **명칭에 대한 주의** — 위 영문 명칭은 보안 기둥 백서에서 오래 쓰인 표기입니다. AWS는 프레임워크 문서를 갱신하면서 2번 원칙을 **"Maintain traceability"** 로 표기하기도 합니다. 뜻은 같지만, **리뷰 보고서에 원칙명을 인용할 때는 리뷰 시점의 AWS 문서 표기를 그대로 따르십시오.** 프레임워크 문구는 개정되며, 이 책의 매핑은 개정과 무관하게 유효한 **주제 대응**입니다.

### 🧪 워크로드 리뷰 실행

리뷰는 콘솔에서도 되지만, **정기 운영을 하려면 CLI로 워크로드와 마일스톤을 관리하는 편이 낫습니다.** ShopMini 운영 워크로드를 등록하고 보안 기둥만 리뷰하는 흐름입니다.

```bash
# 1) 워크로드 등록 (보안 도구 계정 또는 워크로드 소유 계정에서)
aws wellarchitected create-workload \
  --workload-name shopmini-prod \
  --description "ShopMini 3-tier production workload (CloudFront/ALB/EC2/RDS/S3)" \
  --environment PRODUCTION \
  --aws-regions ap-northeast-2 \
  --account-ids 111122223333 \
  --lenses wellarchitected \
  --review-owner "security@example.com" \
  --profile awssec-lab --region ap-northeast-2
```

```bash
# 2) 보안 기둥 질문과 현재 답변 상태 조회
#    WID에는 1)의 create-workload 응답에 있는 WorkloadId를 넣는다
WID="EXAMPLEWORKLOADID0123456789abcdef"

aws wellarchitected list-answers \
  --workload-id "$WID" \
  --lens-alias wellarchitected \
  --pillar-id security \
  --profile awssec-lab --region ap-northeast-2
```

```bash
# 3) 답변 기록 — 선택한 모범 사례 ID와 함께 '증거'를 노트에 남긴다
#    QuestionId와 ChoiceId는 2)의 list-answers 응답에서 그대로 복사한다
aws wellarchitected update-answer \
  --workload-id "$WID" \
  --lens-alias wellarchitected \
  --question-id "EXAMPLE_QUESTION_ID" \
  --selected-choices "EXAMPLE_CHOICE_ID_1" "EXAMPLE_CHOICE_ID_2" \
  --notes "근거: 조직 트레일 org-trail 적용 계정 5/5, 39.2 지표 9 = 100%. 본문 29.2" \
  --profile awssec-lab --region ap-northeast-2
```

```bash
# 4) 개선 항목(미선택 모범 사례) 목록 뽑기 — 이것이 백로그가 된다
aws wellarchitected list-lens-review-improvements \
  --workload-id "$WID" \
  --lens-alias wellarchitected \
  --pillar-id security \
  --profile awssec-lab --region ap-northeast-2

# 5) 이번 리뷰를 마일스톤으로 고정 (다음 분기와 비교할 기준선)
aws wellarchitected create-milestone \
  --workload-id "$WID" \
  --milestone-name "2026-Q1-security-review" \
  --profile awssec-lab --region ap-northeast-2

# 6) 리뷰 보고서 내려받기 (Base64 PDF)
aws wellarchitected get-lens-review-report \
  --workload-id "$WID" --lens-alias wellarchitected \
  --query 'LensReviewReport.Base64String' --output text \
  --profile awssec-lab --region ap-northeast-2 | base64 -d > wa-security-review.pdf
```

3번 단계의 `--notes`가 이 절의 핵심입니다. **답변에 증거를 적지 않으면 리뷰는 자기 신고가 되고, 자기 신고는 반드시 후하게 나옵니다.** 노트에는 두 가지를 씁니다 — **39.2 지표의 실측값**과 **이 책의 절 번호(또는 사내 표준 문서 번호)**. 다음 분기 리뷰에서 "지난번에 왜 이렇게 답했는지"를 재구성할 수 있어야 합니다.

### 정기 리뷰 운영법

| 항목 | 권장 | 이유 |
|---|---|---|
| 주기 | **운영 워크로드 반기 1회 + 중대 아키텍처 변경 시** | 분기는 너무 잦아 형식화되고, 연 1회는 변화를 못 따라감 |
| 대상 선정 | 전 워크로드가 아니라 **데이터 등급 상위 + 인터넷 노출** 워크로드부터 | 📖 "가장 큰 효과를 내는 것부터" |
| 참가자 | 워크로드 소유 팀 + 보안 챔피언 + 중앙 보안 1명. **소유 팀이 답하고 보안이 증거를 캐묻는 구조** | 보안팀이 답하면 팀의 학습이 없음 |
| 소요 | 보안 기둥만 **반나절**. 5기둥 전체는 하루 이상이므로 분리 실시 | 한 번에 다 하면 뒤쪽 기둥이 부실해짐 |
| 산출물 | 마일스톤 + 개선 항목 백로그(**담당자·마감일 포함**) + PDF 보고서 | 담당자 없는 개선 항목은 다음 리뷰에 그대로 남음 |
| 연결 | 개선 항목을 **39.1 성숙도 진단**과 **39.2 지표 목표**에 반영 | 리뷰가 별도 문서로 끝나지 않게 함 |
| 재사용 | 리뷰 템플릿·커스텀 렌즈로 사내 표준 질문(예: ISMS-P 항목)을 추가 | 38장의 컴플라이언스 매핑과 한 번에 처리 |

> ⚠️ **Well-Architected 리뷰가 형식이 되는 방식** — 첫 리뷰에서 팀은 대부분의 모범 사례를 "선택함"으로 체크합니다. 점수가 잘 나오고 보고서가 예쁘게 나옵니다. 두 번째 리뷰에서는 지난번 답변을 그대로 복사합니다. 세 번째부터는 30분 만에 끝납니다. **개선 항목이 0개인 리뷰는 리뷰가 아니라 서명입니다.**
>
> **원인.** 답변에 증거를 요구하지 않았고, 미선택 항목이 곧 **일감**이 된다는 것을 참가자가 알기 때문입니다. 정직하게 답할수록 일이 늘어나는 구조에서 정직을 기대할 수 없습니다.
>
> **올바른 구성.** 세 가지를 겁니다. **(가)** 모든 "선택함"에 `--notes`로 증거를 요구하고, 증거가 없으면 미선택으로 되돌립니다. **(나)** 개선 항목의 **전체 해소를 목표로 삼지 않습니다** — 이번 분기에 3개만 처리한다고 미리 정하면 나머지를 정직하게 미선택으로 남길 수 있습니다. **(다)** 리뷰 결과를 인사 평가에 연결하지 않습니다(39.1의 ⚠️와 같은 이유). **리뷰의 산출물은 점수가 아니라 백로그입니다.**

## 🔴 필수 구성 체크리스트

**성숙도**
- [ ] 6개 영역 각각에 대해 현재 레벨을 판정했고, 판정마다 **API 출력 증거**가 붙어 있다
- [ ] 조직 레벨을 **최솟값**으로 산정했고, 투자 우선순위가 그 영역에 있다
- [ ] 조직 유형에 맞는 **목표 레벨**이 영역별로 다르게 정해져 있다
- [ ] 성숙도 레벨이 **인사 평가에 연결되어 있지 않다**
- [ ] 판정을 해당 영역 운영자가 아닌 사람이 교차 검증한다

**지표**
- [ ] 12개 지표가 모두 산출되고 **각각에 분모의 절대 숫자**가 함께 표시된다
- [ ] 미조치 위험을 **비율이 아니라 잔량**으로 본다 — 기한 초과 건수·최장 경과 일수·전 분기 대비 증감
- [ ] 로그 커버리지(9)가 90% 미만이면 다른 지표를 발표하지 않는 규칙이 있다
- [ ] 각 지표에 **보조 지표**가 짝지어져 있고, 분모의 추이를 함께 본다
- [ ] MFA 적용률(6)과 가드레일 적용 계정 비율(8)의 목표가 **100%** 로 설정돼 있다
- [ ] 예외 목록(12)이 경영진 보고서에 포함되고 **만료 초과 건수가 0**이다
- [ ] 분기 보고서에 **결정 요청이 2~3건** 들어 있다
- [ ] 지표 수집이 자동화되어 있고 결과가 시계열로 적재된다

**조직**
- [ ] 조직 규모에 맞는 모델(중앙 집중/하이브리드)이 명시적으로 선택돼 있다
- [ ] 보안팀이 **예외 심사·문의 응답 SLA**를 공표하고 지킨다
- [ ] **골든 패스**(이대로 쓰면 모든 게이트를 통과하는 모듈·템플릿)가 하나 존재한다
- [ ] 게이트 실패 메시지에 **규칙명·위험 이유·수정 방법·예외 신청 링크**가 들어 있다
- [ ] 챔피언에게 **공식 시간 배정과 권한**이 있고 임기와 인수인계 규칙이 있다
- [ ] 챔피언 도입 전에 정책 게이트(28.3)와 베이스라인 자동화(37.9)가 갖춰져 있다

**비용**
- [ ] 통제별 비용이 **무엇에 비례하는지** 문서화돼 있고 Cost Explorer에서 확인 가능하다
- [ ] "끄면 안 되는 것" 목록이 있고, 비용 절감 과제의 **제외 대상**으로 명시돼 있다
- [ ] S3 게이트웨이 엔드포인트와 **S3 Bucket Keys**가 적용돼 있다
- [ ] 로그 보존이 계층화돼 있고, **보존 기간 자체를 줄이는 방식이 아니다**
- [ ] 로그 범위를 줄이는 결정이 있다면 리스크 등록부에 **만료일과 함께** 등재돼 있다

**Well-Architected**
- [ ] 데이터 등급 상위 워크로드가 Well-Architected Tool에 등록돼 있다
- [ ] 보안 기둥 리뷰를 **반기 1회 이상** 실시하고 마일스톤으로 고정한다
- [ ] 모든 "선택함" 답변에 **증거 노트**(지표 실측값 + 문서 번호)가 있다
- [ ] 개선 항목에 **담당자와 마감일**이 붙어 백로그로 관리된다

| 성숙도 자가 진단을 운영 담당자가 직접 하고 증거를 요구하지 않음 | 레벨이 실제보다 1~2단계 높게 나오고, 그 위에서 투자 결정이 이뤄짐 | 증거는 **API 출력**으로, 판정은 **교차 검증**으로 |
| SOAR·CNAPP 같은 고급 도구를 먼저 도입 | L2 항목(연락처·런북·기본 로깅)이 빈 채로 **비싼 L1**이 됨 | 레벨은 **연속으로** 채운다. 도구는 L3 이후의 가속기 |
| 비율 지표만 보고서에 싣고 분모를 생략 | 통제를 끄고 범위를 좁혀 지표를 개선하는 경로가 열림 | 모든 비율 옆에 **분모의 절대 숫자**. 보조 지표로 분모 추이 감시 |
| 팀별 지표 순위표를 경영진 보고서에 게재 | 📖 "어떤 팀은 본래 더 어렵다" — 레거시 담당 팀이 상시 꼴찌가 되고 지표 숨기기가 시작됨 | 팀별 비교는 **개선 폭**으로. 절대 순위는 내부에서만 |
| 챔피언을 지정하고 중앙 보안이 손을 뗌 | 책임만 이전되고 실제 통제는 없음. 사고 시 챔피언 개인이 문책 대상 | 챔피언은 **가드레일 위**에 얹는 것. 게이트·기본값이 먼저 |
| 보안팀이 승인 창구로만 기능 | 승인 대기가 길어지고 개발팀이 파이프라인을 우회 | **승인 → 기본값** 전환. 보안팀도 응답 SLA를 공표 |
| 비용 절감 과제에서 로그·플로우 로그를 끔 | 사고 조사에서 "유출 범위 확인 불가" → 통지 범위 최대 가정 | 로그는 **끄지 말고 내린다**(계층 보존·포맷·파티션) |
| 인터페이스 엔드포인트를 모든 서비스에 생성 | AZ당 시간 요금이 누적되어 NAT보다 비싸짐 | 트래픽 상위 서비스부터. S3·DynamoDB는 **게이트웨이 엔드포인트** |
| Config 비용을 줄이려고 리소스 유형을 광범위 제외 | 지표 2의 준수율이 조용히 왜곡되고 드리프트를 놓침 | **규칙이 평가하는 유형은 제외 금지**. 기록 주기·리전으로 조정 |
| WA 리뷰에서 모범 사례를 전부 "선택함"으로 체크 | 개선 항목 0개. 리뷰가 서명 절차가 됨 | 증거 없는 선택은 **미선택으로 환원**. 이번 분기 처리 개수를 미리 제한 |
