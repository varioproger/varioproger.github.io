## 31.1 Amazon GuardDuty 🧪 🔴

### 로그를 켜지 않아도 된다

**"VPC 플로우 로그를 먼저 켜야 하나요?"** 답은 **아니오**입니다. GuardDuty는 아래 데이터를 **AWS 내부 경로로 직접 소비**합니다 — 트레일이 없어도, 플로우 로그가 꺼져 있어도 분석합니다.

| 기반 데이터 소스 | 별도 활성화 필요? | 저장 비용 발생? | GuardDuty가 여기서 찾는 것 |
|---|---|---|---|
| CloudTrail **관리 이벤트** | 불필요 | 없음 | 비정상 API 호출, 자격 증명 오용, 권한 변경 |
| CloudTrail **S3 데이터 이벤트** | 불필요(S3 Protection) | 없음 | 버킷 대량 열람·삭제, 이상 접근 패턴 |
| **VPC 플로우 로그** | 불필요 | 없음 | 악성 IP 통신, 포트 스캔, 채굴 풀 접속 |
| **DNS 쿼리 로그** | 불필요 | 없음 | C2 도메인, DGA, DNS 터널링 |

⚠️ 단, 이는 **GuardDuty의 탐지에 한해서**입니다. 직접 조사하거나 Athena로 질의하려면(30.6) 여전히 트레일과 플로우 로그를 따로 구성해야 하고, 반대로 로그를 켠다고 GuardDuty 요금이 줄지도 않습니다 — 독립된 파이프라인입니다.

> 💡 **원서 이후 변경 — DNS 로그의 범위** — GuardDuty의 DNS 분석은 **AWS 제공 DNS 리졸버(VPC의 `.2` 주소)를 쓸 때만** 동작합니다. 외부 리졸버나 자체 DNS 서버를 쓰면 그 쿼리는 보이지 않으므로 **VPC DNS 사용을 강제**해야 하며, 가장 자주 놓치는 사각지대입니다.

### 🔴 반드시 이렇게 구성하라

**① 모든 계정, 모든 사용 리전에서 활성화한다.** 쓰지 않는 리전을 끄면 공격자가 계정을 탈취한 뒤 **감시 없는 리전에서** 인스턴스를 띄우는 패턴을 놓칩니다. 미사용 리전은 SCP로 리소스 생성만 봉인하고(37.2) GuardDuty는 켜 둡니다. **② 조직 위임 관리자로 자동 활성화를 건다**(31.2). **③ 결과를 파이프라인으로 보낸다** — EventBridge → Security Hub → 티켓/채널. **④ 고심각도에 대응 SLA를, 저심각도에 검토 주기를 정한다** — 우선순위 없는 결과 수천 건은 없는 것과 같습니다.

**하지 않았을 때**: EC2 인스턴스 역할의 자격 증명이 유출되면 공격자는 그 키로 다른 리전에서 대형 인스턴스를 기동해 채굴합니다. 이 활동은 CloudTrail에 정상 API 호출로 기록되므로 **30.3의 알람 목록으로는 걸리지 않고**, 청구서가 오는 다음 달에야 알게 됩니다. GuardDuty가 있었다면 `InstanceCredentialExfiltration.OutsideAWS`가 **분 단위로** 떴을 것입니다.

### 🧪 활성화

```bash
# 1) 탐지기(detector) 생성 — 리전당 하나
aws guardduty create-detector \
  --enable \
  --finding-publishing-frequency FIFTEEN_MINUTES \
  --region ap-northeast-2 \
  --profile awssec-lab

# 2) 탐지기 ID 확보 (이후 모든 명령에 필요)
DETECTOR_ID=$(aws guardduty list-detectors \
  --region ap-northeast-2 --profile awssec-lab \
  --query 'DetectorIds[0]' --output text)

# 3) 현재 활성 기능 확인
aws guardduty get-detector \
  --detector-id "$DETECTOR_ID" \
  --region ap-northeast-2 --profile awssec-lab
```

`--finding-publishing-frequency`는 **EventBridge와 S3로 결과를 내보내는 주기**입니다(`FIFTEEN_MINUTES` / `ONE_HOUR` / `SIX_HOURS`). 콘솔 표시 시점이 아니라 **자동 대응 파이프라인의 지연 시간**을 결정하므로, 자동 조치(35.2)를 붙일 계획이면 `FIFTEEN_MINUTES`로 두십시오.

### 보호 플랜

> 💡 **원서 이후 변경** — 원서 시점의 GuardDuty는 세 소스만 분석했습니다. 이후 AWS는 보호 대상을 **보호 플랜(protection plan)** 단위로 확장했고, 각각 별도로 켜고 끄며 **별도로 과금**합니다. 아래는 전부 원서 이후 추가분입니다.

| 보호 플랜 | 기능 이름(API) | 무엇을 보는가 | 켜야 하는가 |
|---|---|---|---|
| **S3 Protection** | `S3_DATA_EVENTS` | S3 데이터 이벤트 — 대량 열람·삭제·권한 변경 | 🔴 필수. `shopmini-uploads` 같은 데이터 버킷이 있으면 무조건 |
| **EKS Protection** | `EKS_AUDIT_LOGS` | 쿠버네티스 감사 로그 — 익명 접근, 특권 파드 | EKS를 쓴다면 필수 |
| **Malware Protection** | `EBS_MALWARE_PROTECTION` | 의심 결과 발생 시 EBS 스냅샷을 자동 스캔 | 🔴 권장. 침해 인스턴스 판정을 크게 앞당김 |
| **RDS Protection** | `RDS_LOGIN_EVENTS` | RDS 로그인 시도의 이상 패턴 | 🔴 권장. `rds/shopmini` 자격 증명 유출 탐지 |
| **Lambda Protection** | `LAMBDA_NETWORK_LOGS` | 함수의 네트워크 활동 — 채굴·C2 통신 | 서버리스 비중이 있으면 권장 |
| **Runtime Monitoring** | `RUNTIME_MONITORING` | 에이전트 기반 EC2·ECS·EKS **런타임 행위** | 컨테이너 운영 시 권장. 에이전트 배포 부담 있음 |

```bash
# S3 · RDS · Malware · Runtime 보호 활성화
aws guardduty update-detector \
  --detector-id "$DETECTOR_ID" \
  --features \
    '[{"Name":"S3_DATA_EVENTS","Status":"ENABLED"},
      {"Name":"RDS_LOGIN_EVENTS","Status":"ENABLED"},
      {"Name":"EBS_MALWARE_PROTECTION","Status":"ENABLED"},
      {"Name":"RUNTIME_MONITORING","Status":"ENABLED",
       "AdditionalConfiguration":[
         {"Name":"ECS_FARGATE_AGENT_MANAGEMENT","Status":"ENABLED"}]}]' \
  --region ap-northeast-2 --profile awssec-lab
```

⚠️ **Malware Protection은 스냅샷을 만듭니다.** EBS 볼륨의 복제 스냅샷을 만들어 스캔한 뒤 삭제하므로 **스냅샷 생성을 막는 SCP가 있으면 조용히 실패**합니다. 고객 관리형 키로 암호화된 볼륨은 GuardDuty 서비스 주체에 `kms:Decrypt`·`kms:CreateGrant`를 허용해야 합니다.

### 탐지 유형 분류

결과 유형(finding type) 이름은 `위협목적:리소스유형/위협패밀리.탐지방식` 형태여서 이름만 읽어도 성격을 알 수 있습니다.

| 범주 | 무엇을 의미하는가 | 대표 결과 유형 | 대응의 성격 |
|---|---|---|---|
| **정찰(Recon)** | 공격자가 우리 자산을 훑고 있다 | `Recon:EC2/PortProbeUnprotectedPort`<br>`Recon:EC2/Portscan`<br>`Recon:IAMUser/MaliciousIPCaller` | 아직 침해 아님. **노출면 축소**가 조치(19장) |
| **인스턴스 침해** | EC2가 공격자 통제 아래 있을 가능성 | `Backdoor:EC2/C&CActivity.B!DNS`<br>`CryptoCurrency:EC2/BitcoinTool.B!DNS`<br>`Trojan:EC2/DNSDataExfiltration`<br>`UnauthorizedAccess:EC2/SSHBruteForce` | **격리 → 스냅샷 → 조사**(33장) |
| **계정 침해** | 자격 증명이 공격자 손에 있을 가능성 | `UnauthorizedAccess:IAMUser/InstanceCredentialExfiltration.OutsideAWS`<br>`UnauthorizedAccess:IAMUser/MaliciousIPCaller`<br>`Policy:IAMUser/RootCredentialUsage` | **가장 급함.** 자격 증명 무효화 우선 |
| **버킷 침해** | S3 데이터가 노출·유출되고 있을 가능성 | `Policy:S3/BucketAnonymousAccessGranted`<br>`Policy:S3/BucketBlockPublicAccessDisabled`<br>`Exfiltration:S3/AnomalousBehavior`<br>`Discovery:S3/AnomalousBehavior` | 퍼블릭 차단 복구 + 접근 로그 확보(15장) |
| **악성코드** | 볼륨·컨테이너에서 악성 파일 발견 | `Execution:EC2/MaliciousFile`<br>`Execution:ECS/MaliciousFile` | 이미지·AMI 계보 추적(24장) |

**이 분류가 곧 대응 우선순위입니다.** 계정 침해 → 버킷 침해 → 인스턴스 침해 → 악성코드 → 정찰 순으로 급합니다 — 계정 침해는 **모든 리소스로 번질 수 있는 유일한 범주**이기 때문입니다.

> 📖 *AWS Security Cookbook* 9장: **"GuardDuty는 VPC 플로우 로그를 분석해 침해된 EC2 인스턴스를 탐지할 수 있다 (…) GuardDuty는 악성 IP 접근이나 EC2 외부에서의 EC2 인스턴스 프로파일 사용 등을 통해 우리 자격 증명이 탈취되었는지 탐지할 수 있다."**

**"EC2 외부에서 EC2 인스턴스 프로파일을 사용"** — 8.3의 IMDS 자격 증명 탈취가 성공했을 때 남는 가장 선명한 신호이며, 이 하나만으로도 GuardDuty를 켤 이유가 됩니다.

### 심각도 해석

> 📖 *AWS Security Cookbook* 9장: **"GuardDuty 이벤트는 가장 낮은 것부터 높은 것까지 세 가지 심각도 수준으로 분류되며, 파랑·노랑·빨강 아이콘으로 표시된다."** 숫자 척도로는 다음과 같습니다.

| 심각도 | 점수 | 의미 | 권장 대응 |
|---|---|---|---|
| **Low** | 1.0 – 3.9 | 차단된 시도, 정찰 흔적 | 주간 검토. 반복 패턴이면 노출면 점검 |
| **Medium** | 4.0 – 6.9 | 의심스럽지만 확정 아님 | 영업일 내 분류. 자산 소유자에게 확인 |
| **High** | 7.0 – 8.9 | 침해 가능성이 높음 | **즉시 호출.** 자동 격리 대상 후보(35.2) |

> 💡 **원서 이후 변경 — Critical 심각도** — 원서 시점은 3단계였습니다. 이후 AWS는 **여러 신호를 하나의 공격 시퀀스로 상관 분석해 Critical(9.0 이상) 결과를 생성**하는 기능을 추가했습니다. 개별 결과가 각각 Medium이어도 "자격 증명 이상 사용 → 권한 열거 → 데이터 대량 열람"처럼 **순서가 이어지면** 상위 결과 하나로 묶입니다. **대시보드와 에스컬레이션 등급표에 Critical 칸을 따로 두십시오.**

⚠️ **심각도를 그대로 우선순위로 쓰지 마십시오.** GuardDuty는 **자산의 중요도를 모릅니다.** 격리 서브넷 RDS를 향한 Medium이 Dev 샌드박스의 High보다 급할 수 있습니다.

```
대응 우선순위 = GuardDuty 심각도 × 자산 등급(12.3의 DataClass 태그) × 노출도(퍼블릭 여부)
```

12.3의 `DataClass` 태그가 여기서 값을 합니다. **태그가 없으면 이 계산이 불가능하고, 결국 심각도만 보고 판단하게 됩니다.**

### 🧪 신뢰할 수 있는 IP 목록과 위협 IP 목록

> 📖 *AWS Security Cookbook* 9장: **"GuardDuty는 신뢰할 수 있는 IP 목록에 포함된 IP 주소에 대해서는 결과를 생성하지 않는다. 이는 특히 회사 IP 주소로 인한 오탐을 피하기 위한 것이다. 그러나 공격이 내부에서 올 수도 있다는 점을 염두에 두어야 한다."** 같은 절은 형식(평문·STIX·OTX CSV 등)과 한도도 정리합니다 — **"신뢰할 수 있는 IP 목록에는 최대 2,000줄, 위협 목록에는 최대 250,000줄."**

**"공격은 내부에서 올 수도 있다"** — 사무실 대역을 통째로 신뢰 목록에 넣는 순간 **그 대역을 경유한 공격은 영원히 보이지 않습니다.**

```bash
# 신뢰 IP 목록 등록 (S3에 업로드한 텍스트 파일을 참조)
aws guardduty create-ip-set \
  --detector-id "$DETECTOR_ID" \
  --name shopmini-trusted-egress \
  --format TXT \
  --location https://s3.ap-northeast-2.amazonaws.com/shopmini-gd-lists/trusted-ips.txt \
  --activate \
  --region ap-northeast-2 --profile awssec-lab

# 위협 IP 목록 등록 (사내 위협 인텔 피드)
aws guardduty create-threat-intel-set \
  --detector-id "$DETECTOR_ID" \
  --name shopmini-threat-feed \
  --format TXT \
  --location https://s3.ap-northeast-2.amazonaws.com/shopmini-gd-lists/threat-list.txt \
  --activate \
  --region ap-northeast-2 --profile awssec-lab
```

📋 **신뢰 IP 목록 운영 규칙**

- [ ] **NAT 게이트웨이 EIP만** 넣는다. 사무실·VPN 대역은 넣지 않는다
- [ ] 항목마다 **사유·등록자·재검토일**을 대장에 남기고 분기 전수 재검토한다
- [ ] 목록 파일 버킷을 보안 도구 계정에 두고 **버전 관리와 변경 알람**을 건다
- [ ] 위협 목록 갱신을 자동화한다(피드 → S3 → `update-threat-intel-set`). 6개월 전 피드는 소음일 뿐

⚠️ **목록 파일 자체가 공격 대상입니다.** 공격자가 이 S3 객체에 자기 IP 한 줄을 추가하면 이후 모든 활동이 탐지에서 제외됩니다 — **이 파일을 고치는 것은 탐지를 끄는 것과 같습니다.**

### 🧪 결과 조회와 필터

```bash
# High 이상 결과만 조회
aws guardduty list-findings \
  --detector-id "$DETECTOR_ID" \
  --finding-criteria '{"Criterion":{"severity":{"Gte":7}}}' \
  --region ap-northeast-2 --profile awssec-lab

# 확정 오탐을 자동 보관하는 필터 (샌드박스 계정의 포트 스캔 결과 예)
aws guardduty create-filter \
  --detector-id "$DETECTOR_ID" \
  --name archive-sandbox-portscan \
  --description "Dev 샌드박스의 의도된 스캔 훈련 결과 제외 - 2026-12-31 재검토" \
  --action ARCHIVE \
  --rank 1 \
  --finding-criteria '{
    "Criterion":{
      "type":{"Eq":["Recon:EC2/Portscan"]},
      "accountId":{"Eq":["555555555555"]}
    }}' \
  --region ap-northeast-2 --profile awssec-lab
```

⚠️ 필터의 `ARCHIVE`는 **오탐 튜닝의 정식 수단이자 가장 위험한 기능**입니다. 필터 하나가 탐지 범주 전체를 지울 수 있으므로 **사유·승인자·재검토일을 설명에 적고 분기 검토**하십시오(26.6의 억제 규칙과 같은 원칙).

### 비용 구조

> 📖 *AWS Security Cookbook* 9장: **"GuardDuty 요금은 분석한 데이터 양을 기준으로 한다. VPC 플로우 로그와 DNS 로그 분석은 분석한 데이터의 크기를 기준으로, CloudTrail 이벤트는 분석한 이벤트 수를 기준으로 과금한다."**

이 구조는 지금도 같고 보호 플랜별 축이 추가되었습니다(S3는 데이터 이벤트 수, Malware는 스캔 GB, Runtime Monitoring은 리소스 시간). **단가는 콘솔 사용량 탭에서 확인하십시오.** 비용이 튀면 대개 특정 계정의 플로우 로그 양이 원인입니다.

## 31.2 멀티 계정 GuardDuty 집계 🧪

### 왜 집계하는가

원서의 문제의식은 명확합니다.

> 📖 *AWS Security Cookbook* 9장: **"여러 계정의 결과를 하나의 전용 계정으로 집계하면 모든 계정의 결과를 질의할 수 있는 중앙 지점이 생긴다. 또한 모든 계정에 대한 구성 변경을 한곳에서 수행할 수 있다."**

**중앙 조회**와 **중앙 구성** — 뒤쪽이 더 중요합니다. "새 계정에서 GuardDuty를 켰는가"를 사람이 챙기는 구조는 실패합니다.

> 💡 **원서 이후 변경 — 초대 방식에서 위임 관리자로** — 원서는 **메인 계정에서 초대를 보내고 멤버 콘솔에서 수락**하는 절차를 안내합니다("Click on Invite under the Status column… Click on the ACCEPT button"). 이 방식은 지금도 **Organizations 밖의 계정**에는 동작하지만, **조직 내 계정에는 위임 관리자(delegated administrator) 방식이 표준**입니다. 위임 관리자 방식에는 수락 절차가 없고 **신규 계정이 합류하면 자동 활성화**되며, 용어도 "마스터/멤버"에서 **"관리자/멤버"** 로 바뀌었습니다.

### 🧪 위임 관리자 구성

**보안 도구 계정 `444455556666`** 이 위임 관리자가 됩니다. 관리 계정(`123456789012`)은 위임만 하고 운영에는 관여하지 않습니다 — 관리 계정에 일상 운영 권한을 쌓지 않는 것이 멀티 계정 설계의 기본입니다(36장).

```bash
# ── 관리 계정(123456789012)에서 실행 ──
# 1) 보안 도구 계정을 GuardDuty 위임 관리자로 지정
aws guardduty enable-organization-admin-account \
  --admin-account-id 444455556666 \
  --region ap-northeast-2 \
  --profile awssec-org-mgmt

# ── 이후는 보안 도구 계정(444455556666)에서 실행 ──
DETECTOR_ID=$(aws guardduty list-detectors \
  --region ap-northeast-2 --profile awssec-security \
  --query 'DetectorIds[0]' --output text)

# 2) 조직 자동 활성화 — 신규 계정 포함 전체
aws guardduty update-organization-configuration \
  --detector-id "$DETECTOR_ID" \
  --auto-enable-organization-members ALL \
  --features \
    '[{"Name":"S3_DATA_EVENTS","AutoEnable":"ALL"},
      {"Name":"RDS_LOGIN_EVENTS","AutoEnable":"ALL"},
      {"Name":"EBS_MALWARE_PROTECTION","AutoEnable":"ALL"}]' \
  --region ap-northeast-2 --profile awssec-security

# 3) 조직 내 기존 계정을 멤버로 편입
aws guardduty create-members \
  --detector-id "$DETECTOR_ID" \
  --account-details \
    AccountId=111122223333,Email=prod-owner@example.com \
    AccountId=555555555555,Email=dev-owner@example.com \
    AccountId=777788889999,Email=logarchive-owner@example.com \
  --region ap-northeast-2 --profile awssec-security

# 4) 커버리지 확인 — 빠진 계정이 있는지
aws guardduty list-members \
  --detector-id "$DETECTOR_ID" \
  --only-associated false \
  --region ap-northeast-2 --profile awssec-security
```

`--auto-enable-organization-members`의 값이 설계 결정입니다.

| 값 | 동작 | 언제 쓰는가 |
|---|---|---|
| `ALL` | 기존·신규 계정 모두 자동 활성화 | 🔴 기본값으로 삼을 것 |
| `NEW` | 신규 합류 계정만 자동 활성화 | 기존 계정을 단계적으로 편입할 때만 |
| `NONE` | 자동 활성화 안 함 | 사실상 쓸 이유 없음 |

⚠️ **`--region`을 반복하는 이유** — 위임 관리자 지정과 조직 구성은 **리전별로 따로** 해야 합니다. 서울 리전에서만 설정하면 다른 리전은 무방비이므로 **모든 사용 리전에서 위 스크립트를 반복 실행**하십시오. GuardDuty 도입에서 가장 흔한 누락입니다.

### 📋 멀티 계정 구성 검증

- [ ] 모든 사용 리전에서 위임 관리자가 `444455556666`으로 지정되어 있다
- [ ] `--auto-enable-organization-members ALL`과 보호 플랜 `AutoEnable: ALL`이 **모든 리전에서** 설정되어 있다
- [ ] `list-members --only-associated false` 결과에 **미편입 계정이 없다**
- [ ] 신규 계정을 만들어 **자동 활성화가 실제로 동작하는지 검증**했다
- [ ] 위임 관리자 계정의 GuardDuty 관리 권한이 **보안팀 역할로만 제한**되어 있다

마지막 항목이 중요합니다. **위임 관리자 계정에서 GuardDuty를 끌 수 있는 사람은 조직 전체의 탐지를 끌 수 있습니다.** `guardduty:DeleteDetector`·`UpdateDetector`·`CreateFilter`·`UpdateIPSet`은 SCP로 특정 역할 외에는 금지하고 호출 시 알람하십시오(30.3의 발상과 동일).

### 결과를 S3로 내보내기

> 📖 *AWS Security Cookbook* 9장: **"서로 다른 계정과 리전의 GuardDuty 결과를 Amazon S3 버킷으로 내보내 모든 결과의 집계를 단순화할 수 있다. 이것은 계정 간 결과를 하나의 계정으로 집계하는 것과는 다른, 새로운 기능이다."**

이 내보내기는 지금도 **장기 보존의 수단**입니다. GuardDuty의 내부 결과 보존 기간은 유한하므로 감사 증적이나 사후 분석용으로 쓰려면 반드시 내보내야 합니다.

```bash
aws guardduty create-publishing-destination \
  --detector-id "$DETECTOR_ID" \
  --destination-type S3 \
  --destination-properties \
    DestinationArn=arn:aws:s3:::shopmini-security-findings,\
KmsKeyArn=arn:aws:kms:ap-northeast-2:444455556666:key/EXAMPLE-KEY-ID \
  --region ap-northeast-2 --profile awssec-security
```

버킷 정책과 KMS 키 정책 양쪽에서 `guardduty.amazonaws.com` 서비스 주체를 허용해야 합니다. 이 버킷은 로그 아카이브 계정(`777788889999`)이나 보안 도구 계정에 두고 객체 잠금을 겁니다(29.3).

## 31.3 Amazon Macie 🧪

12.4에서 Macie **활성화와 민감 데이터 발견**을 다뤘습니다. 이 절은 그 다음 — **찾은 다음에 무엇을 하는가**입니다. 발견은 자동화할 수 있지만 **발견을 통제로 바꾸는 일은 자동화되지 않습니다.**

> 📖 *AWS Security Cookbook* 9장: **"Macie와 GuardDuty 모두 API 호출 분석 기능이 겹친다. GuardDuty와 달리 Macie의 초점은 평소보다 많은 데이터를 업로드하거나 다운로드하는 것과 같은 접근 패턴에 더 맞춰져 있다. 일반적으로 더 나은 보호를 위해서는 Macie를 GuardDuty와 함께 쓰는 것이 바람직하다."**

> 💡 **원서 이후 변경** — 현재 Macie는 **S3의 민감 데이터 발견에 집중**하며 원서의 CloudTrail 이벤트 분석과 Platinum/Gold/Silver/Bronze 사용자 등급은 없어졌습니다(12.4). 역할 분담은 더 선명해졌습니다 — Macie는 "**무엇이** 들어 있는가", GuardDuty는 "**누가 어떻게** 접근하는가".

### 결과 처리 흐름 — 발견에서 통제까지

문서화하지 않으면 결과는 대시보드 숫자로만 남습니다.

```text
① 발견        Macie 결과: SensitiveData:S3Object/Personal
                버킷 shopmini-uploads, 개인정보 매치 1,240건
                        │
② 확인        사람이 검증 — 실데이터인가, 테스트 픽스처인가?
                (픽스처면 허용 목록으로 제외 → 종료, 12.4)
                        │
③ 태깅        버킷·객체에 DataClass=Confidential, Owner=<팀> 부여 (12.3)
                → 태그 기반 접근 제어와 비용·감사 추적의 기준점이 생김
                        │
④ 정책 조정   버킷 정책·SCP·KMS 키 정책 조정 (15.4)
                - 퍼블릭 액세스 차단 4종 강제
                - 접근 주체를 해당 팀 역할로 축소
                - aws:SecureTransport / KMS 암호화 강제
                        │
⑤ 알림·검증   담당자에게 티켓, 재스캔으로 조치 확인, 재발 방지 규칙 등록
```

**③이 빠지면 ④를 할 수 없습니다.** 태그가 없으면 "이 버킷에 어떤 정책을 적용할 것인가"의 근거가 없고, 결국 모든 버킷에 같은 정책을 적용하거나 아무것도 하지 않게 됩니다.

### 🧪 결과 조회와 처리

Macie 결과는 두 갈래입니다 — **민감 데이터 발견**과 **정책 위반**.

| 갈래 | 결과 유형 예 | 의미 | 조치 |
|---|---|---|---|
| 민감 데이터 | `SensitiveData:S3Object/Personal` | 개인정보 발견 | 위 ①~⑤ 흐름 |
| 민감 데이터 | `SensitiveData:S3Object/Credentials` | 자격 증명·키 발견 | **즉시 회전**(11장) 후 흐름 |
| 민감 데이터 | `SensitiveData:S3Object/Financial` | 금융 정보 발견 | PCI DSS 범위 재확인(31.5) |
| 정책 위반 | `Policy:IAMUser/S3BucketPublic` | 버킷이 퍼블릭 | 🔴 즉시 차단(35.2 자동화 후보) |
| 정책 위반 | `Policy:IAMUser/S3BlockPublicAccessDisabled` | 퍼블릭 차단이 해제됨 | 🔴 즉시 복구 + 변경자 추적 |
| 정책 위반 | `Policy:IAMUser/S3BucketEncryptionDisabled` | 기본 암호화 없음 | 기본 암호화 강제(15.7) |
| 정책 위반 | `Policy:IAMUser/S3BucketSharedExternally` | 외부 계정과 공유 중 | 의도 확인 후 축소 |

**정책 위반을 먼저 처리하십시오.** 민감 데이터 발견은 "여기 위험한 게 있다"이지만, 정책 위반은 "지금 새고 있다"입니다.

```bash
# 자격 증명 발견 결과만 조회 (가장 급한 갈래)
aws macie2 list-findings \
  --finding-criteria '{
    "criterion":{
      "type":{"eq":["SensitiveData:S3Object/Credentials"]},
      "archived":{"eq":["false"]}
    }}' \
  --region ap-northeast-2 --profile awssec-lab

# 결과 상세 (민감 데이터의 위치와 매치 수를 포함)
aws macie2 get-findings \
  --finding-ids "$FINDING_ID" \
  --region ap-northeast-2 --profile awssec-lab
```

⚠️ **`get-findings` 응답 자체가 민감합니다.** 민감 데이터가 **어느 객체의 어느 위치에** 있는지가 담깁니다 — 공격자에게는 **"어디를 털면 되는지 알려주는 지도"** 입니다. 티켓에는 **버킷 이름·결과 ID·심각도만** 담고 상세는 권한자가 콘솔에서 보게 하십시오.

### 🧪 EventBridge로 흐름 자동화

```bash
# 정책 위반 결과를 즉시 라우팅
aws events put-rule \
  --name macie-policy-violations \
  --event-pattern '{
    "source":["aws.macie"],
    "detail-type":["Macie Finding"],
    "detail":{
      "type":[{"prefix":"Policy:IAMUser/S3"}]
    }}' \
  --region ap-northeast-2 --profile awssec-lab
```

원서는 이 연결을 **CloudWatch Events 규칙(서비스 Macie, 이벤트 유형 Macie Alert) → SNS 주제**로 안내합니다. 현재는 EventBridge에서 `source: aws.macie`로 잡습니다 — **개념은 같고 이름과 스키마만 바뀌었습니다.**

Lambda 대상으로는 **발견 버킷에 `DataClass` 태그 자동 부여**(흐름 ③의 초안 — 최종 등급은 사람이 확정)와 **소유자 태그를 읽어 담당 팀 티켓 자동 생성**이 실용적입니다. 자동 교정(퍼블릭 차단 복구)은 35.2입니다.

> 📖 *AWS Security Cookbook* 9장: **"Macie는 현재 S3 콘텐츠 분류와 CloudTrail 이벤트 처리에 대해 과금한다."**

현재는 CloudTrail 축이 사라지고 **버킷 인벤토리 평가 + 스캔한 객체의 바이트 수** 기준입니다. **스코핑 없는 대용량 버킷 전량 스캔이 가장 비싼 실수**라는 12.4의 경고가 그대로 적용됩니다.

## 31.4 Amazon Detective

> 💡 **원서 범위 밖** — Amazon Detective는 *AWS Security Cookbook*(2020) 집필 이후 일반 공개된 서비스로, 원서에 설명이 없습니다. 이 절은 원서 인용 없이 서술합니다.

### 왜 이 서비스가 있는가

GuardDuty가 `InstanceCredentialExfiltration.OutsideAWS`를 띄웠다고 합시다. 알게 된 것은 **"이 인스턴스 역할의 자격 증명이 EC2 밖에서 쓰였다"** 하나입니다. 대응하려면 더 알아야 합니다 — 그 자격 증명으로 **어떤 API를 호출**했는가, **언제 시작**됐고 지금도 계속되는가, 그 인스턴스는 **누구와 통신**했는가, 같은 IP가 **다른 리소스**도 건드렸는가.

답하려면 CloudTrail·플로우 로그·GuardDuty 결과를 시간축으로 교차 조회해야 합니다. 30.6의 Athena 쿼리로 할 수 있지만 **쿼리를 잘 쓰는 사람이 있어야 하고 시간이 걸립니다.** Detective는 이 상관 분석을 미리 해 둡니다.

### 행동 그래프

Detective는 로그를 지속 수집해 **행동 그래프(behavior graph)** 를 만듭니다. 엔티티(IAM 역할, 인스턴스, IP 주소)를 노드로, 그 사이의 활동을 엣지로 갖는 그래프입니다. 각 엔티티의 **기준선(baseline)** 이 함께 계산되어 "이 역할이 이 API를 호출한 것은 관측 기간 중 처음"과 같은 판단이 즉시 나옵니다.

| 데이터 소스 | 무엇을 제공하는가 |
|---|---|
| CloudTrail **관리 이벤트** | API 호출 이력, 호출 주체, 소스 IP |
| **VPC 플로우 로그** | 인스턴스의 네트워크 통신 상대와 양 |
| **GuardDuty 결과** | 조사의 진입점 |
| **EKS 감사 로그** | 쿠버네티스 내부 활동(EKS 사용 시) |

GuardDuty와 마찬가지로 **이 로그들을 별도로 활성화할 필요가 없습니다.** 보존은 **최대 1년의 롤링 윈도** 라 **"이 침해가 언제 시작됐는가"** 를 되짚는 데 적합합니다.

### 언제 유용한가

| 상황 | Detective가 유용한가 |
|---|---|
| GuardDuty 결과의 진위와 범위를 빠르게 판정해야 할 때 | 🔴 매우 유용. 콘솔에서 결과 → 조사 원클릭 |
| 침해 시작 시점(dwell time)을 역추적할 때 | 🔴 매우 유용. 1년 롤링 데이터 |
| "이 IP가 우리 환경에서 또 무엇을 했나" | 🔴 매우 유용. 그래프 탐색의 본령 |
| 규정 준수 증적 보관 | 아니오. 그건 29장의 로그 아카이브 |
| 커스텀 상관 규칙 작성 | 아니오. SIEM이나 Security Lake(30.7) |
| GuardDuty·Security Hub 없이 단독 도입 | 아니오. 진입점이 없으면 그래프를 헤맴 |

**Detective는 탐지 도구가 아니라 조사 도구입니다.** 새 위협을 알려 주지 않고 이미 뜬 결과의 **맥락**을 줍니다 — 결과가 월 몇 건이라면 Athena 쿼리로 충분합니다.

### 🧪 활성화

```bash
# 관리 계정에서 보안 도구 계정을 위임 관리자로 지정
aws detective enable-organization-admin-account \
  --account-id 444455556666 \
  --region ap-northeast-2 \
  --profile awssec-org-mgmt

# 보안 도구 계정에서 행동 그래프 생성
aws detective create-graph \
  --tags Project=awssec-lab,Chapter=ch31 \
  --region ap-northeast-2 --profile awssec-security

# 조직 계정 자동 편입
GRAPH_ARN=$(aws detective list-graphs \
  --region ap-northeast-2 --profile awssec-security \
  --query 'GraphList[0].Arn' --output text)

aws detective update-organization-configuration \
  --graph-arn "$GRAPH_ARN" \
  --auto-enable \
  --region ap-northeast-2 --profile awssec-security
```

**비용은 계정별 수집 데이터 양 기준**이고 플로우 로그가 많은 계정이 지배합니다. **리전별 서비스**인 점도 GuardDuty와 같습니다.

⚠️ **Detective를 켰다고 조사 역량이 생기지는 않습니다.** 그래프를 읽는 훈련이 필요하고, 그 훈련은 32.5의 테이블탑에서 실제 결과를 놓고 해야 합니다. 도구만 켜 두고 사고 당일 처음 열어 보는 것이 최악입니다.

## 31.5 AWS Security Hub 🔴 🧪

### 이 서비스의 정체

> 📖 *AWS Security Cookbook* 10장 「Setting up and using AWS Security Hub」: **"Security Hub는 Config, GuardDuty, Macie, Inspector 같은 서비스의 결과를 활용해, 보안 경보를 관리하고 규정 준수 점검을 자동화할 수 있는 중앙 뷰를 제공한다. Security Hub는 CIS AWS Foundation Benchmarks를 사용해 자동 규정 준수 점검을 수행할 수 있으며, 이는 Security Hub를 활성화할 때 기본으로 켜진다."**

Security Hub는 **두 가지 일**을 합니다.

| 역할 | 하는 일 | 이 책에서 다루는 곳 |
|---|---|---|
| **① 결과 집계 허브** | 여러 보안 서비스의 결과를 **ASFF 단일 형식**으로 모음 | **31.5 — 이 절** |
| **② 보안 표준 점검** | 계정 설정을 벤치마크에 대조해 **컨트롤별 합격/불합격** 판정 | 26.6(CSPM 관점) + 이 절(운영 관점) |

**26.6은 "어떤 구멍을 보는가"를, 이 절은 "결과를 어떻게 운영하는가"를 다룹니다.** 표준 구독 명령은 26.6에 있으므로 반복하지 않습니다.

### ASFF — 하나의 형식으로 모은다는 것

Security Hub의 핵심은 **AWS Security Finding Format(ASFF)** 입니다. GuardDuty 결과, Inspector의 CVE, Macie의 민감 데이터 발견, Config의 규칙 위반은 원래 **전부 다른 JSON 스키마**인데, Security Hub가 이를 공통 필드로 정규화합니다.

| ASFF 필드 | 담기는 것 | 왜 중요한가 |
|---|---|---|
| `ProductArn` | 결과를 만든 제품 | **어느 도구가 잡았는지** 구분 |
| `Types` | 분류 체계 경로 | 여러 도구의 결과를 같은 축으로 묶음 |
| `Severity.Label` | `INFORMATIONAL`~`CRITICAL` | **도구가 달라도 같은 척도로 비교** |
| `Resources[]` | 영향받은 리소스 ARN·태그 | 자산 등급과 결합해 우선순위 계산 |
| `Compliance.Status` | `PASSED`/`FAILED`/`WARNING` 등 | 표준 컨트롤 판정 |
| `Workflow.Status` | `NEW`/`NOTIFIED`/`RESOLVED`/`SUPPRESSED` | **운영 상태 — 이 필드가 워크플로의 핵심** |
| `RecordState` | `ACTIVE`/`ARCHIVED` | 결과 자체의 생사 |

`Severity.Label`의 정규화가 특히 값집니다. GuardDuty의 7.5, Inspector의 CVSS 8.1, Config의 `NON_COMPLIANT`는 원래 비교할 수 없지만 ASFF에서는 전부 `HIGH`가 되어 **하나의 큐에서 함께 정렬**됩니다.

⚠️ **`Workflow.Status`와 `RecordState`를 혼동하지 마십시오.** `RecordState`는 결과의 생사(해소되면 자동 `ARCHIVED`), `Workflow.Status`는 **사람의 처리 상태**입니다. "미처리 건수"는 `RecordState=ACTIVE AND Workflow.Status=NEW`로 세야 하고, 틀리면 이미 조치한 항목이 계속 미처리로 잡혀 팀이 대시보드를 불신합니다.

### 🔴 반드시 이렇게 구성하라

**① 위임 관리자를 지정하고 중앙 구성으로 운영한다.** 원서는 초대 방식을 안내하지만("An invitation will be sent to the member accounts and they must accept the invitation"), GuardDuty와 같은 이유로 **조직 내 계정에는 위임 관리자 방식**을 씁니다.

```bash
# ── 관리 계정에서 ──
aws securityhub enable-organization-admin-account \
  --admin-account-id 444455556666 \
  --region ap-northeast-2 --profile awssec-org-mgmt

# ── 보안 도구 계정에서 ──
aws securityhub enable-security-hub \
  --enable-default-standards \
  --region ap-northeast-2 --profile awssec-security

# 조직 자동 활성화 + 중앙 구성 모드
aws securityhub update-organization-configuration \
  --auto-enable \
  --auto-enable-standards DEFAULT \
  --organization-configuration ConfigurationType=CENTRAL \
  --region ap-northeast-2 --profile awssec-security
```

`ConfigurationType=CENTRAL`에서는 **어떤 표준·컨트롤을 켤지를 위임 관리자가 정책으로 배포**합니다. `LOCAL`에서는 각 계정이 알아서 정하므로 설정이 제각각이 되고 "우리 조직의 보안 점수"가 의미를 잃습니다.

**② 크로스 리전 집계를 켠다.** 리전마다 결과가 따로 쌓이므로 집계 리전을 지정해 한곳에서 보십시오.

```bash
aws securityhub create-finding-aggregator \
  --region-linking-mode ALL_REGIONS \
  --region ap-northeast-2 --profile awssec-security
```

> 📖 *AWS Security Cookbook* 10장: **"Security Hub는 리전 서비스다. 비용이 제약이 아니라면 모든 리전에서 활성화하는 것이 권장된다."**

**③ 통합 컨트롤 결과를 켠다.** 같은 점검이 FSBP·CIS·PCI DSS에 중복 포함되면 결과가 3건 생깁니다. 이 옵션을 켜면 **컨트롤 하나당 결과 하나**로 합쳐집니다.

```bash
aws securityhub update-security-hub-configuration \
  --control-finding-generator SECURITY_CONTROL \
  --auto-enable-controls \
  --region ap-northeast-2 --profile awssec-security
```

**④ 표준을 최소 두 개 켜되, 켠 표준의 컨트롤을 실제로 검토한다** — 다섯 개를 켜고 안 보는 것보다 두 개를 켜고 전부 처리하는 편이 낫습니다. **⑤ 컨트롤 비활성화와 결과 억제에 만료일을 붙인다.**

**하지 않았을 때**: 결과가 계정·리전별로 흩어지면 "우리 조직 전체에 퍼블릭 버킷이 몇 개인가"에 답할 수 없습니다. 답할 수 없는 질문은 개선할 수도 없고, 감사 때 반드시 나옵니다.

### 보안 표준

> 📖 *AWS Security Cookbook* 10장: **"현재 규정 준수 표준에서는 CIS AWS Foundations Benchmark 컨트롤만 모니터링된다. 약 42개의 벤치마크 컨트롤이 있다."**, **"AWS용 CIS 벤치마크는 자격 증명 및 접근 관리, 로깅, 모니터링, 네트워킹의 네 가지 범주로 분류할 수 있다."**

> 💡 **원서 이후 변경** — 원서 시점에는 CIS 하나뿐이었지만 현재는 아래 표준이 추가되었고 각각 별도로 구독합니다.

| 표준 | 성격 | 언제 켜는가 |
|---|---|---|
| **AWS Foundational Security Best Practices(FSBP)** | AWS가 정의한 서비스별 모범 사례. 컨트롤 수가 가장 많고 서비스 신규 출시에 맞춰 갱신 | 🔴 **모든 조직의 기본** |
| **CIS AWS Foundations Benchmark** | 업계 표준 벤치마크. 감사에서 가장 자주 요구됨 | 🔴 **기본**. 여러 버전이 병존하므로 최신 버전 구독 |
| **PCI DSS** | 카드 결제 데이터 취급 요건 | 카드 데이터를 다루면 |
| **NIST SP 800-53** | 미국 연방 통제 프레임워크. 컨트롤 수가 매우 많음 | 해당 요건이 있을 때만 |

⚠️ **표준 ARN에는 버전 문자열이 들어가고 리전 요소가 표준마다 다릅니다.** 하드코딩하지 말고 `describe-standards` 출력의 ARN을 쓰십시오. 그리고 **NIST SP 800-53을 "더 촘촘하니까" 켜지 마십시오** — 컨트롤 수가 압도적이라 요건이 없으면 대부분이 해석 불가능한 소음이 됩니다.

### 컨트롤 관리와 보안 점수

**보안 점수(security score)** 는 `통과한 컨트롤 수 ÷ 활성 컨트롤 수`의 백분율입니다.

⚠️ **점수는 컨트롤을 비활성화해도 올라갑니다.** 어려운 컨트롤 열 개를 끄면 점수가 뛰지만 리스크는 그대로입니다 — 25.6의 "스캔하지 않으면 취약점이 0으로 보인다"와 같은 왜곡입니다. **점수와 함께 "비활성화된 컨트롤 수"를 반드시 병기**하십시오.

```bash
# 컨트롤 비활성화 — 사유가 필수 인자인 것에 주목
aws securityhub update-standards-control \
  --standards-control-arn "$CONTROL_ARN" \
  --control-status DISABLED \
  --disabled-reason "이 계정은 로그 아카이브 전용으로 EC2를 운영하지 않음. 2026-12-31 재검토(승인: 보안팀장)" \
  --region ap-northeast-2 --profile awssec-security
```

AWS가 `--disabled-reason`을 필수로 만든 것은 우연이 아닙니다. **"불필요"라고만 쓰지 말고 근거·승인자·재검토일을 담으십시오.** 개별 결과를 처리 완료로 넘기거나 억제할 때는 `batch-update-findings`를 씁니다.

```bash
aws securityhub batch-update-findings \
  --finding-identifiers Id="$FINDING_ID",ProductArn="$PRODUCT_ARN" \
  --workflow Status=SUPPRESSED \
  --note Text="테스트 환경의 의도된 구성. 2026-12-31 재검토",UpdatedBy="security-team" \
  --region ap-northeast-2 --profile awssec-security
```

### 통합 — 무엇이 자동으로 들어오는가

> 📖 *AWS Security Cookbook* 10장: **"Security Hub는 현재 Amazon GuardDuty, Amazon Inspector, Amazon Macie, AWS Firewall Manager, IAM Access Analyzer에서 결과를 가져온다. (…) 서비스 통합은 시간이 지남에 따라 늘어날 것으로 예상된다."** 원서의 예상대로 통합은 늘었습니다.

| 소스 | 무엇이 들어오는가 | 이 책의 장 |
|---|---|---|
| **GuardDuty** | 위협 탐지 결과 전체 | 31.1 |
| **Inspector** | EC2·ECR·Lambda의 CVE | 26.3 |
| **Macie** | 민감 데이터·정책 위반 | 12.4, 31.3 |
| **IAM Access Analyzer** | 외부 공유 리소스, 미사용 액세스 | 7.7, 26.6 |
| **AWS Config** | 규칙 위반(대부분의 컨트롤이 여기 의존) | 29.8, 26.6 |
| **Firewall Manager** | 정책 미준수 리소스 | 23장(WAF·방화벽 정책) |
| **Health / Systems Manager Patch Manager 등** | 운영 이슈, 패치 미준수 | 22장 |

⚠️ **Config가 없으면 Security Hub 컨트롤의 상당수가 판정 불가로 남습니다.** 원서도 Security Hub가 CloudWatch·SNS·Config·CloudTrail을 사용해 규정 준수 점검을 수행한다고 적습니다. **Security Hub를 켜기 전에 Config를 전 계정·전 리전에서 켜십시오**(26.6 ①).

> 📖 같은 절: **"IAM Access Analyzer는 논리 기반 추론을 사용해 AWS 환경의 리소스 기반 정책을 분석하여, 계정의 어떤 리소스가 외부 주체와 공유되고 있는지 알려 준다."**

### 사용자 지정 작업 — 콘솔에서 대응으로

> 📖 *AWS Security Cookbook* 10장: **"설정 페이지의 Custom actions 탭으로 가면 선택한 인사이트와 결과를 Amazon CloudWatch Events로 보낼 수 있다."**

**사용자 지정 작업(custom action)** 은 분석가가 콘솔에서 결과를 선택하고 버튼을 눌러 **EventBridge 이벤트를 발생시키는** 기능으로, **"오탐 시 피해가 큰 조치"를 사람 승인 아래 두면서 실행은 자동화**합니다(35.1).

```bash
aws securityhub create-action-target \
  --name "격리 SG 적용" \
  --description "선택한 EC2 인스턴스를 격리 보안 그룹으로 전환" \
  --id IsolateInstance \
  --region ap-northeast-2 --profile awssec-security
```

이 작업의 ARN을 EventBridge 규칙에서 잡습니다.

```json
{
  "source": ["aws.securityhub"],
  "detail-type": ["Security Hub Findings - Custom Action"],
  "resources": ["arn:aws:securityhub:ap-northeast-2:444455556666:action/custom/IsolateInstance"]
}
```

이어지는 Lambda 구현과 안전장치는 **35.4**에서 다룹니다.

### 비활성화의 대가와 비용 구조

> 📖 *AWS Security Cookbook* 10장: **"비활성화하면 Security Hub는 결과 수집을 중단하고 새로운 규정 준수 점검을 수행하지 않는다. 기존 결과와 Security Hub 구성을 모두 잃게 되며 나중에 복구할 수 없다."**

**"나중에 복구할 수 없다"** — 이 문장 때문에 `securityhub:DisableSecurityHub`는 SCP로 봉인해야 합니다. 비용 절감으로 잠시 껐다 켜면 억제 규칙·비활성화 컨트롤·워크플로 상태가 사라져 팀이 처리한 수천 건이 다시 `NEW`로 돌아옵니다.

과금은 **① 컨트롤 검사 수**와 **② 수집한 결과 수** 두 축입니다(원서도 설정 페이지 Usage 탭에서 예상 비용을 확인하는 절차를 안내합니다). 대개 **컨트롤 검사 수**가 비용을 지배하며 계정 × 리전 × 활성 컨트롤 수에 비례합니다 — **불필요한 표준이 비용과 소음을 함께 늘리는 이유**입니다.

## 31.6 CloudWatch와 CloudTrail 통합 🧪

CloudTrail은 기본적으로 **S3에 로그 파일을 떨굽니다.** 그것만으로는 알람을 걸 수 없습니다 — S3 객체에는 지표도 임계값도 없습니다. **CloudWatch Logs로도 보내야** 지표 필터와 알람이 됩니다.

> 📖 *AWS Security Cookbook* 8장 「Integrating CloudWatch and CloudTrail」: **"통합하고 나면 CloudTrail 로그를 기반으로 CloudWatch 안에서 지표 필터와 알람을 만들 수 있다."**

이 절은 **통합 배선 자체**에 집중합니다. 어떤 알람을 걸지는 **30.3의 목록**에 있고, 여기서 다루는 것은 그 목록의 전제 조건입니다.

### 배선의 구조

```text
CloudTrail 트레일
    ├─→ S3 버킷 (로그 아카이브 계정 777788889999)   ← 장기 보존·무결성·Athena 질의 (29장)
    │
    └─→ CloudWatch Logs 로그 그룹                    ← 실시간 지표·알람 (30장)
            │
            └─→ 지표 필터 (필터 패턴으로 이벤트 매칭)
                    │
                    └─→ CloudWatch 알람 → SNS 주제 → 이메일/채널/PagerDuty
```

**두 경로는 서로를 대체하지 않습니다.** S3는 보존과 조사, CloudWatch Logs는 실시간 탐지입니다. **Logs 경로에는 비용이 붙으므로 로그 그룹 보존을 짧게(30~90일) 두고 장기 보존은 S3에 맡기는 것**이 표준 설계입니다(29.6).

### 🧪 통합 구성

> 📖 *AWS Security Cookbook* 8장: **"CloudTrail은 우리 계정의 API 활동과 관련된 CloudTrail 이벤트를 우리 로그 그룹으로 전달할 권한을 요청했다. 다음 권한이 부여되었다 — 지정한 로그 그룹에 로그 스트림을 만드는 `CreateLogStream`, CloudTrail 이벤트를 로그 스트림에 전달하는 `PutLogEvents`."**

CLI로는 역할을 직접 만들어야 합니다. 아래는 **로그 아카이브 계정(`777788889999`)을 CloudTrail 위임 관리자로 두고 조직 트레일을 운영하는 구성**으로, 로그 그룹·역할·트레일이 같은 계정에 있어야 합니다.

```bash
# 1) 로그 그룹 생성 (보존 기간 명시 — 기본은 무기한이라 비용이 샌다)
aws logs create-log-group \
  --log-group-name /aws/cloudtrail/shopmini-org-trail \
  --region ap-northeast-2 --profile awssec-logs

aws logs put-retention-policy \
  --log-group-name /aws/cloudtrail/shopmini-org-trail \
  --retention-in-days 90 \
  --region ap-northeast-2 --profile awssec-logs
```

CloudTrail이 사용할 역할의 신뢰 정책과 권한 정책입니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowCloudTrailAssumeRole",
      "Effect": "Allow",
      "Principal": { "Service": "cloudtrail.amazonaws.com" },
      "Action": "sts:AssumeRole",
      "Condition": {
        "StringEquals": { "aws:SourceAccount": "777788889999" },
        "ArnLike": {
          "aws:SourceArn": "arn:aws:cloudtrail:ap-northeast-2:777788889999:trail/shopmini-org-trail"
        }
      }
    }
  ]
}
```

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowCloudTrailToWriteLogs",
      "Effect": "Allow",
      "Action": [
        "logs:CreateLogStream",
        "logs:PutLogEvents"
      ],
      "Resource": "arn:aws:logs:ap-northeast-2:777788889999:log-group:/aws/cloudtrail/shopmini-org-trail:log-stream:*"
    }
  ]
}
```

⚠️ **신뢰 정책의 `aws:SourceArn`·`aws:SourceAccount` 조건을 빼지 마십시오.** 서비스 주체를 조건 없이 신뢰하면 혼동된 대리인(confused deputy) 문제에 노출됩니다 — 8.6의 원칙이 서비스 주체에도 적용됩니다.

```bash
# 2) 트레일에 CloudWatch Logs 연결
aws cloudtrail update-trail \
  --name shopmini-org-trail \
  --cloud-watch-logs-log-group-arn \
    "arn:aws:logs:ap-northeast-2:777788889999:log-group:/aws/cloudtrail/shopmini-org-trail:*" \
  --cloud-watch-logs-role-arn \
    "arn:aws:iam::777788889999:role/CloudTrailToCloudWatchLogs" \
  --region ap-northeast-2 --profile awssec-logs

# 3) 지표 필터 — 루트 계정 사용 (30.3 목록의 1번)
aws logs put-metric-filter \
  --log-group-name /aws/cloudtrail/shopmini-org-trail \
  --filter-name RootAccountUsage \
  --filter-pattern '{ $.userIdentity.type = "Root" && $.userIdentity.invokedBy NOT EXISTS && $.eventType != "AwsServiceEvent" }' \
  --metric-transformations \
    metricName=RootAccountUsageCount,metricNamespace=ShopMiniSecurity,metricValue=1,defaultValue=0 \
  --region ap-northeast-2 --profile awssec-logs

# 4) 알람 연결
aws cloudwatch put-metric-alarm \
  --alarm-name shopmini-root-account-usage \
  --alarm-description "루트 계정 사용 감지 - 즉시 확인" \
  --metric-name RootAccountUsageCount \
  --namespace ShopMiniSecurity \
  --statistic Sum \
  --period 300 \
  --threshold 1 \
  --comparison-operator GreaterThanOrEqualToThreshold \
  --evaluation-periods 1 \
  --treat-missing-data notBreaching \
  --alarm-actions "arn:aws:sns:ap-northeast-2:444455556666:security-alerts" \
  --region ap-northeast-2 --profile awssec-logs
```

`--treat-missing-data notBreaching`가 중요합니다. 이런 보안 지표는 **평소에 데이터 포인트가 아예 없어서**(루트 로그인이 없으니까) 기본 설정으로 두면 알람이 계속 `INSUFFICIENT_DATA`에 머물고, 팀은 그 알람을 무시하게 됩니다.

### 원서의 CloudFormation 템플릿과 SNS 구독

> 📖 *AWS Security Cookbook* 8장: **"AWS가 제공하는 CloudFormation 템플릿을 사용해 보안 및 네트워크 관련 API 활동에 대한 CloudWatch 알람을 설정했다. CloudFormation 스택을 삭제하면 모든 알람도 함께 삭제된다."**

원서는 CloudTrail 콘솔의 링크로 AWS 제공 템플릿을 배포해 알람 세트를 한 번에 만듭니다. **시작점으로는 유용하지만 그대로 운영하기엔 부족합니다** — 30.3의 목록을 모두 덮지 않고 알람 이름·SNS 대상·임계값이 조직 규약과 맞지 않습니다. **IaC 저장소로 옮겨 관리하십시오**(37.9).

> 📖 같은 절: **"SNS는 구독을 수동으로 확인하기 전까지 알림을 보내지 않으므로, 이메일 주소를 확인해 이메일 구독을 확인해야 했다."**

⚠️ **미확인 구독은 조용히 아무것도 하지 않습니다.** 알람이 `ALARM`으로 바뀌어도 메일은 오지 않고 콘솔에서는 정상으로 보입니다. 구독 상태가 `PendingConfirmation`이 아닌지 확인하고 분기마다 테스트 발송으로 검증하십시오.

## 31.7 서드파티 도구 연동 ⚠️

### AWS가 채우지 못하는 칸

> 📖 *AWS Security Cookbook* 10장 「Using security products from AWS Marketplace」: **"AWS가 우리에게 필요한 모든 보안 제품을 제공하지 못할 수도 있다."** 같은 절은 공백도 구체적으로 짚습니다 — **"AWS는 완전한 네트워크 패킷 검사를 수행할 수 없고 IDS·IPS의 기능이 부족하다. 다만 AWS Marketplace의 솔루션을 사용할 수 있다."**

> 💡 **원서 이후 변경** — IDS/IPS 공백은 **AWS Network Firewall**(Suricata 규칙 기반)로 상당 부분 메워졌습니다(19.5). 다만 고급 위협 인텔 피드, 특화 프로토콜 분석, 온프레미스 정책 재사용 같은 요구는 여전히 서드파티 영역입니다. 또한 원서는 Marketplace 제품을 주로 **EC2 AMI 형태**로 설명하지만 현재는 **SaaS 구독 형태**가 더 흔하며, 이 차이가 아래 위험 구조를 바꿉니다.

> 📖 *Practical Cloud Security* 2판 7장은 SIEM·네트워크 IDS·파일 무결성 모니터링·특권 접근 관리·포렌식 도구를 예시로 열거하며 **"이들을 포함시킨다고 해서 특정 도구를 보증하는 것도 아니다"** 라고 밝힙니다. **도구 이름을 외우는 것은 의미가 없습니다** — 중요한 것은 **그 범주가 메우는 공백**과 도입할 때 **무엇을 내주게 되는가**입니다.

### ⚠️ 사고 시나리오 — 보안 도구가 침해 경로가 된다

**시나리오.** SaaS형 CSPM 제품을 도입했습니다. 벤더가 준 CloudFormation 템플릿을 실행하면 크로스 계정 역할이 만들어지고 벤더 계정이 그 역할로 조직 전체를 스캔합니다. 담당자는 템플릿의 정책을 열어 보지 않았습니다. 6개월 뒤 벤더의 SaaS 플랫폼이 침해되고 공격자가 벤더의 고객 자격 증명 저장소에 접근합니다. 공격자는 **여러분 조직 전체를 읽을 수 있는 역할**을 손에 넣었습니다.

**원인.** **① 권한 범위 미확인.** 템플릿의 정책은 `ReadOnlyAccess`였습니다. 이름은 순하지만 **`dynamodb:GetItem`·`lambda:GetFunction`(코드 다운로드 URL 포함) 같은 데이터 접근이 상당수 들어 있습니다.** "읽기 전용"은 "덜 위험함"이 아닙니다 — **데이터 유출에는 읽기 권한이면 충분합니다.**

**② External ID 미사용.** 신뢰 정책이 벤더 계정만 지정하고 External ID 조건이 없으면 **같은 벤더의 다른 고객이 역할 ARN을 알아내는 것만으로 접근할 수 있습니다**(8.6의 혼동된 대리인 문제).

**③ 데이터 반출 경로 미확인.** 이 제품은 스캔 결과를 벤더 클라우드에 저장했습니다. 결과에는 **버킷 이름, IAM 주체 이름, 보안 그룹 규칙, 태그** 가 담깁니다 — 공격자에게는 완성된 정찰 보고서입니다.

**올바른 구성.**

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowVendorAssumeWithExternalId",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::210987654321:root" },
      "Action": "sts:AssumeRole",
      "Condition": {
        "StringEquals": {
          "sts:ExternalId": "shopmini-vendor-a1b2c3d4e5f6"
        }
      }
    }
  ]
}
```

External ID는 **고객마다 다르고 추측할 수 없는 값**이어야 합니다. 벤더가 모든 고객에게 같은 값을 주거나 "고객사 이름을 넣으세요"라고 안내한다면 그 자체가 **평가 감점 사유**입니다. 여기에 **권한 최소 재작성**(액션 목록을 주지 못하는 벤더는 탈락), **권한 경계**(7.2), **역할 사용 감시**(`AssumeRole` 호출을 CloudTrail로 추적하고 예정된 스캔 주기 밖의 사용에 알람)를 더합니다.

### 📋 서드파티 보안 도구 평가 체크리스트

**권한**
- [ ] 벤더가 요구하는 **정확한 IAM 액션 목록**을 문서로 받았다
- [ ] `ReadOnlyAccess` 같은 광범위 관리형 정책 대신 **최소 권한 정책을 직접 작성**했다
- [ ] `iam:PassRole`·`kms:Decrypt`·`secretsmanager:GetSecretValue` 요구가 있다면 **사유를 확인**했다
- [ ] **External ID가 고객별 고유·비추측 값**으로 발급된다(8.6)
- [ ] 역할에 **권한 경계**를 적용했고, 사용을 CloudTrail로 감시한다

**데이터**
- [ ] 벤더가 **어떤 데이터를 자사 인프라로 반출**하는지 목록으로 확인했다
- [ ] 반출 데이터에 **고객 데이터(S3 객체 내용, DB 레코드)가 포함되는지** 확인했다
- [ ] 반출 데이터의 **저장 리전과 보존 기간**을 확인했다(국내 규제 대상이면 필수)
- [ ] 계약 종료 시 **데이터 삭제 절차와 증빙**이 계약서에 있다

**운영**
- [ ] 벤더의 **보안 인증·침해 이력·취약점 공개 정책**을 확인했다(27장)
- [ ] 제품 결과를 **Security Hub로 보낼 수 있다**(ASFF) — 콘솔이 하나 더 늘면 26.1의 결과 누수가 시작된다
- [ ] **AWS 네이티브 서비스로 이미 덮이는 기능이 아닌지** 확인했다(중복 비용)
- [ ] 결과를 처리할 **담당자와 큐**, 배포 에이전트의 **패치 책임자**가 정해졌다

마지막 항목은 **Marketplace AMI 방식**에서 특히 중요합니다. 원서는 **"Marketplace AMI는 소프트웨어가 미리 구성된 EC2 인스턴스라고 볼 수 있다"** 고 설명합니다 — 그 인스턴스도 **패치 대상이고, 침해되면 VPC 안의 발판이 됩니다.**

### 다층 탐지의 원칙

> 📖 *Practical Cloud Security* 2판 7장: **"이런 도구들이 모든 공격을 막는 데 100% 효과적일 것이라고 확신할 수 없다. (…) 이런 서비스의 로그를 수집하고 분석해야 하며, 그렇지 않으면 큰 조기 경보 이점을 포기하는 것이다."**

**GuardDuty 하나로 충분하지 않습니다.** GuardDuty는 계정과 네트워크, Macie는 데이터 내용, Inspector는 워크로드 내부, Config는 설정, WAF는 애플리케이션 요청을 봅니다. **Security Hub는 이 결과들을 한 화면으로 모아 사각지대의 경계를 보이게 하는 장치**입니다.

## 이 장의 요약

| 항목 | 핵심 |
|---|---|
| **GuardDuty** | CloudTrail·플로우 로그·DNS를 **별도 활성화 없이** 소비. 전 계정·전 리전 필수 |
| **보호 플랜** | S3·EKS·Malware·RDS·Lambda·Runtime — 전부 원서 이후 추가분, 별도 과금 |
| **탐지 유형** | 계정 침해 > 버킷 침해 > 인스턴스 침해 > 악성코드 > 정찰 순으로 급함 |
| **심각도** | Low 1–3.9 / Medium 4–6.9 / High 7–8.9. **자산 등급과 곱해야 실제 우선순위** |
| **신뢰 IP 목록** | 사무실·VPN 대역을 넣지 말 것. 목록 파일 변경 = 탐지 무력화 |
| **멀티 계정** | 위임 관리자 + `auto-enable ALL`. ⚠️ **모든 리전에서** 반복 설정 |
| **Macie 운영** | 발견 → 확인 → 태깅(12.3) → 정책 조정(15.4) → 알림·검증. 정책 위반이 민감 데이터보다 급함 |
| **Detective** | 탐지가 아니라 **조사** 도구. GuardDuty 결과가 진입점, 1년 롤링 |
| **Security Hub** | ASFF 정규화 + 표준 점검. `ConfigurationType=CENTRAL`, 크로스 리전 집계 필수 |
| **보안 점수** | 컨트롤을 끄면 올라감. **비활성화 컨트롤 수를 반드시 병기** |
| **CloudTrail↔CloudWatch** | S3 경로(보존·조사)와 Logs 경로(실시간 알람)는 **서로 대체 불가** |
| **서드파티** | 권한 범위·External ID·데이터 반출 경로 — 이 셋을 확인 못 하면 도입하지 말 것 |
| **비용 축** | GuardDuty=분석량 / Macie=스캔 바이트 / Detective=수집량 / Security Hub=컨트롤 검사·결과 수 |

## 🔴 필수 구성 체크리스트

**GuardDuty**
- [ ] 조직 위임 관리자가 보안 도구 계정(`444455556666`)으로 지정되어 있다
- [ ] `--auto-enable-organization-members ALL`이 **모든 사용 리전에서** 설정되어 있다
- [ ] S3·Malware·RDS Protection이 조직 기본으로 켜져 있다
- [ ] 미사용 리전도 켜져 있다(SCP로 리소스 생성만 봉인)
- [ ] VPC가 **AWS 제공 DNS 리졸버**를 쓰도록 구성되어 DNS 탐지가 동작한다
- [ ] 신뢰 IP 목록에 사무실·VPN 대역이 없고, 목록 파일 변경에 알람이 걸려 있다
- [ ] 결과가 S3로 내보내져 장기 보존된다
- [ ] `guardduty:DeleteDetector`·`UpdateDetector`·`UpdateIPSet`이 SCP로 제한된다

**Security Hub**
- [ ] 위임 관리자 + `ConfigurationType=CENTRAL`로 구성되어 있다
- [ ] 크로스 리전 결과 집계(`create-finding-aggregator`)가 설정되어 있다
- [ ] 통합 컨트롤 결과(`SECURITY_CONTROL`)가 켜져 있다
- [ ] FSBP + CIS가 켜져 있고, 표준 ARN을 `describe-standards`로 확인해 썼다
- [ ] AWS Config가 **전 계정·전 리전**에서 켜져 있다(컨트롤의 전제 조건)
- [ ] 비활성화 컨트롤마다 `--disabled-reason`에 근거·승인자·재검토일이 있다
- [ ] `securityhub:DisableSecurityHub`가 SCP로 봉인되어 있다

**Macie·Detective·통합**
- [ ] Macie 정책 위반이 민감 데이터 결과보다 먼저 처리되는 큐 구조다
- [ ] Macie 발견 → 태깅 → 정책 조정 흐름의 각 단계에 담당자가 있다
- [ ] Detective 위임 관리자와 자동 편입이 설정되어 있다
- [ ] CloudTrail이 S3와 CloudWatch Logs **양쪽**으로 전달된다
- [ ] CloudTrail용 역할 신뢰 정책에 `aws:SourceArn` 조건이 있다
- [ ] 로그 그룹에 보존 기간이 설정되어 있다(무기한 방치 금지)
- [ ] SNS 구독이 `PendingConfirmation`이 아니고 분기 테스트 발송으로 검증된다

## ⚠️ 자주 하는 실수

| 실수 | 결과 | 올바른 구성 |
|---|---|---|
| GuardDuty용으로 플로우 로그·DNS 로깅을 따로 켬 | 저장 비용 이중 지출, GuardDuty 요금은 그대로 | GuardDuty는 직접 소비. 로그는 **조사 목적**으로만 별도 구성(29장) |
| 인스턴스가 외부 DNS 리졸버를 쓰도록 방치 | DNS 기반 탐지(C2·DGA·터널링)가 통째로 사각지대 | VPC 제공 DNS 사용을 강제 |
| 비용 때문에 미사용 리전 GuardDuty를 끔 | 공격자가 그 리전에서 채굴 인스턴스를 띄워도 무탐지 | 전 리전 활성화 + 미사용 리전은 SCP 봉인(37.2) |
| 서울 리전에서만 위임 관리자를 설정 | 다른 리전은 계정별 개별 관리 상태로 방치 | **모든 사용 리전에서** 위임·자동 활성화 반복 |
| 사무실 대역을 신뢰 IP 목록에 등록 | 그 대역을 경유한 내부자·탈취 계정 활동이 영구 면제 | NAT EIP만. 원서도 "공격은 내부에서 올 수 있다"고 경고 |
| GuardDuty 심각도를 그대로 대응 순서로 사용 | Dev 샌드박스의 High가 운영 DB의 Medium보다 먼저 처리됨 | 심각도 × 자산 등급(`DataClass`) × 노출도 |
| 원서대로 GuardDuty 멤버 계정을 초대·수락 | 계정이 늘어날수록 누락 발생, 신규 계정 자동 미적용 | 위임 관리자 + `auto-enable ALL` |
| 오탐 필터를 사유 없이 대량 생성 | 탐지 범주 전체가 조용히 사라짐 | 필터마다 사유·승인자·재검토일, 분기 검토 |
| Macie 결과 상세를 티켓 본문·채팅에 붙여 넣음 | 민감 데이터 위치 지도가 넓게 유출 | 티켓에는 버킷·결과 ID·심각도만 |
| 민감 데이터 결과부터 처리하고 정책 위반은 나중에 | "위험한 게 있다"를 보는 동안 실제로 새고 있음 | 정책 위반(`Policy:IAMUser/S3*`) 우선 |
| Config 없이 Security Hub만 활성화 | 컨트롤 상당수가 판정 불가, 보안 점수가 왜곡 | Config 전 계정·전 리전 선행(26.6) |
| 보안 점수를 단독 KPI로 사용 | 어려운 컨트롤을 꺼서 점수를 올리는 유인 | 점수 + **비활성화 컨트롤 수** 병기 |
| NIST SP 800-53을 요건 없이 활성화 | 결과 폭증 → 대시보드 불신 + 컨트롤 검사 비용 증가 | 요건이 있을 때만. 기본은 FSBP + CIS |
| 표준 ARN을 문서에서 복사해 하드코딩 | 버전 불일치로 구독 실패 | `describe-standards` 출력 사용 |
| `Workflow.Status`와 `RecordState`를 혼동 | 처리 완료 항목이 계속 미처리로 집계 | `RecordState=ACTIVE AND Workflow.Status=NEW` |
| 비용 절감으로 Security Hub를 잠시 비활성화 | 억제 규칙·워크플로 상태 **영구 소실**(복구 불가) | `DisableSecurityHub`를 SCP로 봉인 |
| Detective를 켜 두고 사고 당일 처음 열어 봄 | 그래프를 읽을 줄 몰라 조사 시간이 더 걸림 | 테이블탑 훈련에서 실제 결과로 연습(32.5) |
| CloudTrail을 S3로만 보내고 알람 구성 | 지표 필터를 만들 수 없어 30.3 목록이 전부 불가 | CloudWatch Logs 경로도 연결 |
| 로그 그룹 보존 기간을 설정하지 않음 | 무기한 보존으로 CloudWatch Logs 비용 급증 | 30~90일 + 장기 보존은 S3(29.6) |
| 보안 알람에 `treat-missing-data` 기본값 사용 | 상시 `INSUFFICIENT_DATA` → 팀이 알람을 무시 | `notBreaching` 지정 |
| SNS 구독 확인 없이 알람 구성 완료로 처리 | 알람은 뜨는데 아무도 통보받지 못함 | 구독 상태 확인 + 분기 테스트 발송 |
| 벤더 CloudFormation 템플릿을 그대로 배포 | `ReadOnlyAccess`로 조직 전체 데이터 열람 가능한 역할 상시 존재 | 최소 권한 재작성 + 권한 경계 + External ID(8.6) |
| 벤더 역할에 External ID 미적용 | 같은 벤더의 다른 고객이 역할 ARN만으로 접근 가능 | 고객별 고유·비추측 External ID 필수 |
| Marketplace 보안 어플라이언스를 패치 대상에서 제외 | 보안 도구가 VPC 내부 발판이 됨 | 자산 등록 + 패치·스캔 대상 포함(22·26장) |
