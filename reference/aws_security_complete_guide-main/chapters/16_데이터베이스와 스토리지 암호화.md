# 16장. 데이터베이스와 스토리지 암호화

> **이 장에서 다루는 것**
> - 암호화를 **어느 계층에서 할 것인가** — 디스크·플랫폼·애플리케이션 세 층위의 방어 범위와 대가
> - **EBS 암호화** 🧪 — 🔴 리전 단위 기본 암호화, 스냅샷 암호화 상속, 미암호화 볼륨 전환 절차
> - **RDS/Aurora** — 생성 시에만 켤 수 있는 저장 암호화, TLS 강제, IAM 데이터베이스 인증, ⚠️ 퍼블릭 액세스
> - **DynamoDB / EFS / FSx** — 키 유형 선택, `LeadingKeys` 행 단위 격리, 접근 지점과 파일 시스템 정책
> - **Glacier Vault Lock** 🧪 — 되돌릴 수 없는 보존 정책과 24시간 규칙
> - **토큰화 vs 암호화**, 그리고 ⚠️ 퍼블릭으로 공유된 스냅샷·AMI 사고
>
> **선행 지식**: 12장(데이터 자산 분류), 13장(KMS 키 관리), 15장(S3 보안)
> **난이도**: ★★☆

---

13장에서 키를 만들고 15장에서 그 키를 S3에 붙였습니다. 이 장은 **나머지 저장소 전부** — 블록 스토리지, 관계형 DB, NoSQL, 파일 시스템, 아카이브 — 에 같은 일을 합니다.

그런데 "암호화를 켠다"는 말은 서비스마다 방어하는 위협이 다릅니다. 원서는 이를 데이터베이스 애플리케이션 예제로 정리합니다.

> 📖 *Practical Cloud Security* 2판 2장은 암호화 지점을 세 계층으로 나눕니다. **"① 디스크가 들어가는 스토리지 시스템 — 디스크에 보내기 전에 데이터를 암호화할 수 있다. ② DBaaS 플랫폼 — 스토리지 시스템에 보내기 전에 암호화할 수 있다. ③ 애플리케이션 — 데이터베이스에 보내기 전에 암호화할 수 있다."**
>
> 그리고 각 계층의 잔여 위험을 못 박습니다. 디스크 계층에 대해서는 **"공격자가 디스크가 들어가는 스토리지 시스템의 관리자를 사칭할 수 있다면? 복호화는 스토리지 서브시스템이 수행하므로, 그 계층(또는 그 위)의 공격자는 암호화되지 않은 데이터를 볼 수 있다."** 플랫폼 계층에 대해서는 **"더 큰 위험은 애플리케이션이 데이터베이스와 통신할 때 쓰는 API 키를 공격자가 얻으면, 애플리케이션이 할 수 있는 모든 읽기·쓰기를 공격자도 할 수 있다는 것이다."** 애플리케이션 계층에 대해서는 대가를 분명히 합니다. **"데이터베이스가 평문 데이터를 볼 수 없기 때문에 특정 항목을 검색하거나 정렬하거나 리포팅할 수 없다. (…) 나는 일반적으로 애플리케이션이 처리하는 가장 민감한 데이터에만 애플리케이션 수준 암호화를 적용하고, 나머지는 하위 계층이 처리하게 하는 것을 권한다."**

이 장의 16.1~16.5는 대부분 **①·② 계층**입니다. AWS가 대신 해주므로 켜기만 하면 되고, 켜지 않으면 얻는 것이 0입니다. 16.6은 **③ 계층**과 그 대안인 토큰화를, 16.7은 **암호화를 다 켜도 무너지는 지점** — 공유 설정 — 을 다룹니다.

**원칙 하나를 미리 말해 둡니다.** 이 장의 서비스 중 RDS, Aurora, EFS는 **암호화를 나중에 켤 수 없습니다.** "일단 만들고 나중에"는 통하지 않습니다.

## 16.1 EBS 암호화 🧪

### 왜 블록 스토리지인가

> 📖 *Practical Cloud Security* 2판 3장 「Storage Assets」은 블록 스토리지를 **"클라우드 버전의 하드 드라이브"** 라고 정의하고, 위협을 한 문장으로 요약합니다. **"블록 스토리지의 주된 보안 관심사는 접근 관리다. 블록 스토리지에 직접 접근한 공격자는 그 스토리지를 사용하는 서버에 걸어둔 운영체제 수준의 통제를 모두 우회하기 때문이다."**

이 문장이 EBS 암호화의 존재 이유입니다. EC2 안에서 아무리 파일 권한을 잠가도, **`CreateVolume` + `AttachVolume` 권한을 가진 사람은 스냅샷에서 볼륨을 만들어 자기 인스턴스에 붙이고 `mount` 한 번으로 전부 읽습니다.** OS 계정도, sudo도, SELinux도 개입하지 않습니다.

EBS 암호화는 이 경로에 **KMS 키 정책이라는 두 번째 관문**을 세웁니다. EC2 권한만으로는 부족하고, 해당 KMS 키에 대한 `kms:Decrypt`·`kms:CreateGrant`가 있어야 합니다.

> 📖 *AWS Security Cookbook* 6장 「Using KMS to encrypt data in EBS」는 EBS 암호화가 KMS에 종속됨을 지적합니다. **"KMS는 리전별 서비스이므로, 암호화·복호화에 키를 사용해야 하는 바로 그 AWS 리전 안에 KMS 키를 만들어야 한다."** 또한 흔한 오해를 정리합니다. **"EC2 키 페어로는 EBS 볼륨을 암호화할 수 없다는 점이 중요하다. EC2 키 페어는 비대칭 키이며 SSH에 쓰인다. KMS 키는 대칭 키이며 EBS 볼륨·S3 등의 데이터 암호화에 쓰인다."**

### 🔴 반드시 이렇게 하라 — 리전 단위 기본 암호화

원서는 인스턴스를 만들 때 콘솔에서 체크박스를 켜는 방법을 보여줍니다. **개별 리소스에서 켜는 방식은 규모가 커지면 반드시 샙니다.** 사람이 만드는 볼륨, Auto Scaling이 만드는 볼륨, CI가 만드는 임시 볼륨 — 이 중 하나만 빠져도 미암호화 볼륨이 생기고, 그 볼륨의 스냅샷도 미암호화입니다.

**계정×리전 단위로 기본 암호화를 켜십시오.** 그 리전에서 새로 만들어지는 모든 EBS 볼륨이 암호화되고, **미암호화 스냅샷에서 복원한 볼륨조차 암호화됩니다.**

```bash
# 1) 기본 암호화에 쓸 고객 관리형 키를 지정 (기본값은 aws/ebs)
aws ec2 modify-ebs-default-kms-key-id \
  --kms-key-id alias/shopmini/app \
  --region ap-northeast-2 --profile awssec-lab

# 2) 리전 기본 암호화 활성화
aws ec2 enable-ebs-encryption-by-default \
  --region ap-northeast-2 --profile awssec-lab

# 3) 확인
aws ec2 get-ebs-encryption-by-default --region ap-northeast-2 --profile awssec-lab
aws ec2 get-ebs-default-kms-key-id     --region ap-northeast-2 --profile awssec-lab
```

**설정은 리전마다 따로입니다.** 쓰지 않는 리전이야말로 감시가 없어 위험하므로 전 리전에 일괄 적용하십시오.

```bash
for r in $(aws ec2 describe-regions --query 'Regions[].RegionName' --output text --profile awssec-lab); do
  aws ec2 enable-ebs-encryption-by-default --region "$r" --profile awssec-lab >/dev/null \
    && echo "OK  $r" || echo "FAIL $r"
done
```

그리고 **SCP로 잠급니다.** 기본 암호화는 `ec2:DisableEbsEncryptionByDefault` 한 번이면 풀립니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyUnencryptedEbsVolume",
      "Effect": "Deny",
      "Action": "ec2:CreateVolume",
      "Resource": "arn:aws:ec2:*:*:volume/*",
      "Condition": {
        "Bool": { "ec2:Encrypted": "false" }
      }
    },
    {
      "Sid": "DenyDisablingDefaultEncryption",
      "Effect": "Deny",
      "Action": "ec2:DisableEbsEncryptionByDefault",
      "Resource": "*"
    }
  ]
}
```

**안 했을 때 벌어지는 일**: 미암호화 볼륨은 오류도 경고도 없이 조용히 생깁니다. 몇 달 뒤 감사에서 드러날 때는 이미 그 볼륨에서 파생된 스냅샷·AMI가 여러 계정에 흩어져 있고, **전환에는 반드시 다운타임이 따릅니다**(아래 절차 참고). 그리고 16.7에서 보듯, 미암호화 스냅샷은 실수로 퍼블릭 공유가 **가능한** 유일한 스냅샷입니다.

> 💡 **원서 이후 변경** — 리전 기본 암호화(`EnableEbsEncryptionByDefault`)는 2020년판 원서 집필 이후 널리 쓰이게 된 기능입니다. 또한 AWS Organizations의 **선언적 정책(declarative policies)** 으로 조직 단위에서 EBS 기본 암호화 상태를 강제할 수 있습니다. SCP가 "행위를 금지"하는 것과 달리 선언적 정책은 "설정값 자체를 고정"하므로, 둘을 함께 쓰면 방어가 겹칩니다.

### 스냅샷 암호화 상속 규칙

실수가 가장 많이 나오는 지점입니다. 표로 고정해 두십시오.

| 작업 | 원본 | 결과 | 키 |
|---|---|---|---|
| 암호화 볼륨 → 스냅샷 | 암호화 | **암호화** | 볼륨과 동일 키 |
| 암호화 스냅샷 → 볼륨 | 암호화 | **암호화** | 스냅샷과 동일 키 |
| 미암호화 스냅샷 → 볼륨 (기본 암호화 **켬**) | 미암호화 | **암호화** | 리전 기본 키 |
| 미암호화 스냅샷 → 볼륨 (기본 암호화 **끔**) | 미암호화 | 미암호화 | — |
| 스냅샷 복사 `--encrypted --kms-key-id` | 미암호화/암호화 | **암호화** | 지정한 키(**키 교체 가능**) |
| 암호화 볼륨 → 암호화 해제 | 암호화 | **불가** | — |

핵심은 두 줄입니다. **한 번 암호화한 볼륨은 되돌릴 수 없고**, **키를 바꾸는 유일한 방법은 스냅샷 복사입니다.**

### 미암호화 볼륨을 암호화로 전환하기 🧪

기존 볼륨을 제자리에서 암호화하는 API는 **없습니다.** 다음 4단계가 유일한 경로이며, 3단계에서 **볼륨 교체를 위한 중지 시간**이 발생합니다.

```bash
VOL=vol-0123456789abcdef0
AZ=ap-northeast-2a

# 1) 원본 스냅샷 (미암호화)
SNAP=$(aws ec2 create-snapshot --volume-id $VOL \
  --description "pre-encryption baseline" \
  --tag-specifications 'ResourceType=snapshot,Tags=[{Key=Project,Value=awssec-lab},{Key=Chapter,Value=ch16},{Key=AutoDelete,Value=true}]' \
  --query SnapshotId --output text --profile awssec-lab)
aws ec2 wait snapshot-completed --snapshot-ids $SNAP --profile awssec-lab

# 2) 암호화하며 복사 (여기서 평문 → 암호문 전환이 일어난다)
ENC=$(aws ec2 copy-snapshot \
  --source-region ap-northeast-2 --source-snapshot-id $SNAP \
  --encrypted --kms-key-id alias/shopmini/app \
  --description "encrypted copy" \
  --query SnapshotId --output text --profile awssec-lab)
aws ec2 wait snapshot-completed --snapshot-ids $ENC --profile awssec-lab

# 3) 암호화 볼륨 생성 → 인스턴스 중지 → detach 원본 → attach 신규 → 기동
aws ec2 create-volume --availability-zone $AZ --snapshot-id $ENC \
  --volume-type gp3 --profile awssec-lab

# 4) 확인 후 미암호화 스냅샷/볼륨 삭제 — 이 단계를 빠뜨리면 평문 사본이 남는다
aws ec2 delete-snapshot --snapshot-id $SNAP --profile awssec-lab
```

**4단계를 반드시 하십시오.** 전환 작업의 절반은 "평문 사본을 지우는 것"입니다. 1단계 스냅샷, 원본 볼륨, 그 볼륨으로 만든 AMI가 전부 평문입니다.

루트 볼륨이라면 스냅샷 대신 **AMI 복사**(`aws ec2 copy-image --encrypted --kms-key-id ...`)로 암호화 AMI를 만들고 인스턴스를 재생성하는 편이 안전합니다. 원서는 과거 루트 볼륨 암호화에 이 우회가 필요했다고 기록하면서 **"현재는 이런 추가 단계를 거칠 필요가 없다"**(*AWS Security Cookbook* 6장) 고 적었는데, 이는 **신규 인스턴스** 이야기입니다. **이미 존재하는 미암호화 루트 볼륨**에는 여전히 이 우회가 필요합니다.

### 기본 키 vs 고객 관리형 키

| 항목 | `aws/ebs` (AWS 관리형) | `alias/shopmini/app` (고객 관리형) |
|---|---|---|
| 준비 비용 | 없음, 자동 생성 | 키 생성·정책 관리 필요 |
| 키 정책 편집 | **불가** | 가능 — 계정 밖 접근을 정책으로 차단 |
| 스냅샷 크로스 계정 공유 | **불가** | 가능(키도 함께 공유) |
| 스냅샷 퍼블릭 공유 | 불가 | 불가 |
| 키 순환·폐기 제어 | AWS 자동, 폐기 불가 | 직접 제어(암호 삭제 가능) |
| CloudTrail에 남는 주체 | 동일 | 동일 |
| 권장 | 실습·비운영 | **운영 전량** |

운영 계정에서는 고객 관리형 키를 기본값으로 지정하십시오. 이유는 세 번째 줄입니다. **`aws/ebs`로 암호화한 스냅샷은 다른 계정과 공유할 수 없어**, 재해 복구용 백업 계정 구성에서 반드시 막힙니다. 그때는 이미 수백 개 스냅샷이 쌓여 있어 전량 재암호화 복사를 해야 합니다.

키 정책에는 EC2 경유만 허용하는 조건을 넣어 두십시오(13장).

```json
{
  "Sid": "AllowEbsUseViaEc2Only",
  "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::111122223333:role/shopmini-app-instance" },
  "Action": [
    "kms:Encrypt", "kms:Decrypt", "kms:ReEncrypt*",
    "kms:GenerateDataKeyWithoutPlaintext", "kms:DescribeKey", "kms:CreateGrant"
  ],
  "Resource": "*",
  "Condition": {
    "StringEquals": { "kms:ViaService": "ec2.ap-northeast-2.amazonaws.com" },
    "Bool": { "kms:GrantIsForAWSResource": "true" }
  }
}
```

`kms:CreateGrant`는 EC2가 볼륨을 붙일 때 내부적으로 필요합니다. 빼면 인스턴스가 기동하지 않으며, 오류 메시지가 KMS를 가리키지 않아 원인 파악에 시간이 걸립니다.

## 16.2 RDS/Aurora 보안

ShopMini의 회원·주문 데이터 전량이 여기 있습니다. 3장 위협 모델에서 가장 큰 자산입니다.

### ⚠️ 저장 암호화는 생성 시에만 켤 수 있다

**RDS 인스턴스와 Aurora 클러스터의 저장 암호화는 생성 시점에만 설정할 수 있습니다.** `modify-db-instance`로 나중에 켜는 옵션은 없습니다. 전환 경로는 **스냅샷 → 암호화 복사 → 복원**뿐이고, **엔드포인트가 바뀌므로 애플리케이션 전환 작업이 따라붙습니다.**

```bash
# 1) 스냅샷
aws rds create-db-snapshot \
  --db-instance-identifier shopmini-prod-mysql \
  --db-snapshot-identifier shopmini-preenc --profile awssec-lab
aws rds wait db-snapshot-available --db-snapshot-identifier shopmini-preenc --profile awssec-lab

# 2) 암호화하며 복사
aws rds copy-db-snapshot \
  --source-db-snapshot-identifier shopmini-preenc \
  --target-db-snapshot-identifier shopmini-enc \
  --kms-key-id alias/shopmini/app --profile awssec-lab

# 3) 새 인스턴스로 복원 (엔드포인트가 달라진다)
aws rds restore-db-instance-from-db-snapshot \
  --db-instance-identifier shopmini-prod-mysql-enc \
  --db-snapshot-identifier shopmini-enc \
  --db-subnet-group-name shopmini-isolated-data \
  --no-publicly-accessible --profile awssec-lab
```

Aurora는 클러스터 단위 설정이며, 절차는 `copy-db-cluster-snapshot` → `restore-db-cluster-from-snapshot`으로 동일합니다. **읽기 전용 복제본은 원본과 다른 암호화 상태를 가질 수 없습니다.**

암호화가 켜지면 **인스턴스 스토리지, 자동 백업, 읽기 복제본, 스냅샷이 모두 같은 키로 암호화**됩니다. 다만 원서 경고대로, **DB 사용자와 애플리케이션 API 키를 얻은 공격자에게는 아무 방어도 되지 않습니다.** 그래서 다음 세 가지가 필요합니다.

### 전송 중 암호화 강제

TLS "지원"과 "강제"는 다릅니다. 기본 상태에서는 클라이언트가 평문으로 접속해도 DB가 받아줍니다. **파라미터 그룹에서 강제하십시오.**

| 엔진 | 파라미터 | 값 | 적용 |
|---|---|---|---|
| RDS for MySQL / MariaDB, Aurora MySQL | `require_secure_transport` | `ON` | DB 파라미터 그룹(엔진 기본 그룹은 수정 불가 → 사용자 그룹 생성) |
| RDS for PostgreSQL, Aurora PostgreSQL | `rds.force_ssl` | `1` | 동일 |
| RDS for SQL Server | `rds.force_ssl` | `1` | 동일 |

```bash
aws rds create-db-parameter-group \
  --db-parameter-group-name shopmini-mysql8-tls \
  --db-parameter-group-family mysql8.0 \
  --description "force TLS" --profile awssec-lab

aws rds modify-db-parameter-group \
  --db-parameter-group-name shopmini-mysql8-tls \
  --parameters "ParameterName=require_secure_transport,ParameterValue=ON,ApplyMethod=immediate" \
  --profile awssec-lab
```

⚠️ **강제하기 전에 클라이언트를 먼저 고치십시오.** 파라미터를 켜는 순간 평문 접속은 즉시 거부됩니다. 그리고 클라이언트는 **인증서 검증까지** 해야 의미가 있습니다. `--ssl-mode=REQUIRED`는 암호화만 확인하고 서버 신원은 확인하지 않으므로, `VERIFY_IDENTITY`(MySQL) / `verify-full`(PostgreSQL)에 RDS 루트 CA 번들을 지정하십시오. 11장 예제에서 `ssl={"ca": ...}` 를 넣었던 이유입니다.

### IAM 데이터베이스 인증

11장의 결론은 "보관할 시크릿을 줄이는 것"이었습니다. RDS에서 이를 실현하는 기능이 IAM 데이터베이스 인증입니다. **DB 비밀번호 대신 IAM 자격 증명으로 15분짜리 토큰을 발급받아 접속합니다.**

```bash
# 1) 인스턴스에서 기능 활성화
aws rds modify-db-instance \
  --db-instance-identifier shopmini-prod-mysql \
  --enable-iam-database-authentication --apply-immediately --profile awssec-lab
```

```sql
-- 2) DB 안에서 IAM 인증 전용 사용자 생성 (MySQL)
CREATE USER 'shopmini_app'@'%' IDENTIFIED WITH AWSAuthenticationPlugin AS 'RDS';
GRANT SELECT, INSERT, UPDATE, DELETE ON shopmini.* TO 'shopmini_app'@'%';
-- PostgreSQL이라면: GRANT rds_iam TO shopmini_app;
```

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowIamDbConnectAsAppUserOnly",
      "Effect": "Allow",
      "Action": "rds-db:connect",
      "Resource": "arn:aws:rds-db:ap-northeast-2:111122223333:dbuser:db-ABCDEFGHIJKL01234/shopmini_app"
    }
  ]
}
```

```bash
# 3) 토큰 발급 후 접속 (유효 15분)
TOKEN=$(aws rds generate-db-auth-token \
  --hostname shopmini-prod-mysql.abcdefghijkl.ap-northeast-2.rds.amazonaws.com \
  --port 3306 --username shopmini_app --region ap-northeast-2 --profile awssec-lab)

mysql --host=shopmini-prod-mysql.abcdefghijkl.ap-northeast-2.rds.amazonaws.com \
      --port=3306 --user=shopmini_app --password="$TOKEN" \
      --ssl-ca=/etc/pki/tls/certs/rds-combined-ca-bundle.pem --ssl-mode=VERIFY_IDENTITY
```

리소스 ARN의 `db-ABCDEFGHIJKL01234`는 인스턴스 이름이 아니라 **`DbiResourceId`** 입니다(`describe-db-instances --query 'DBInstances[].DbiResourceId'`). 이름을 바꿔 권한을 우회하는 일이 불가능합니다.

**한계도 함께 알아두십시오.**

| 얻는 것 | 잃는 것·제약 |
|---|---|
| 저장할 DB 비밀번호가 사라진다 | 토큰 발급이 IAM API 호출이라 **연결 생성 속도에 상한**이 있다 |
| 접속 주체가 IAM 프린시펄로 CloudTrail에 남는다 | 대량 커넥션 풀·서버리스 폭발 트래픽에는 부적합 |
| 권한 회수가 IAM 정책 한 줄 | `rds-db:connect`는 **인증만** — DB 안 권한(GRANT)은 별도 |
| TLS가 사실상 필수라 전송 암호화가 따라온다 | 관리자 계정, 마이그레이션 도구 등은 여전히 비밀번호 사용 |

**실무 권장**: 사람의 접속은 IAM DB 인증으로 전환하고, 애플리케이션의 상시 커넥션 풀은 Secrets Manager + 자동 순환(11.5)을 유지하는 조합이 안정적입니다.

### ⚠️ 퍼블릭 액세스 — 사고 시나리오

**시나리오.** ShopMini 개발팀이 로컬 PC의 DB 클라이언트로 스테이징 DB를 보려고 `Publicly accessible`을 `Yes`로 바꾸고 보안 그룹에 자기 IP를 열었습니다. 3주 뒤 다른 팀원이 "접속이 안 된다"며 같은 보안 그룹에 `0.0.0.0/0`을 추가했고, 2개월 뒤 이 스테이징 DB에 대량 조회 흔적이 발견됩니다. 스테이징에는 운영 DB를 복사해 마스킹하지 **않은** 회원 데이터가 들어 있었습니다.

**원인.** 세 가지가 겹쳤습니다. ① `PubliclyAccessible=true`는 RDS 엔드포인트에 **퍼블릭 IP를 부여**합니다. ② 보안 그룹의 `0.0.0.0/0`은 단독으로는 위험하지 않지만 ①과 만나면 인터넷 전체에 3306을 여는 것입니다. ③ 스테이징이 운영 데이터를 담고 있었습니다(12장).

**올바른 구성.**

```bash
aws rds modify-db-instance \
  --db-instance-identifier shopmini-staging-mysql \
  --no-publicly-accessible --apply-immediately --profile awssec-lab
```

- DB는 `isolated-data` 서브넷(`10.20.20.0/24`, `10.20.21.0/24`)에만 두고, 이 서브넷 라우팅 테이블에 IGW·NAT 경로를 두지 않습니다.
- DB 보안 그룹의 인바운드는 **앱 보안 그룹 참조**만 허용합니다(CIDR 금지).
- 로컬에서 봐야 한다면 **SSM Session Manager 포트 포워딩**을 씁니다(22장).
- Config 규칙 `rds-instance-public-access-check`에 자동 교정을 붙입니다.

### 스냅샷 공유 시 KMS 키를 함께 공유해야 한다

크로스 계정 백업이나 데이터 이관에서 반드시 걸리는 지점입니다.

```bash
# 운영(111122223333) → 보안 도구 계정(444455556666)으로 스냅샷 공유
aws rds modify-db-snapshot-attribute \
  --db-snapshot-identifier shopmini-enc \
  --attribute-name restore --values-to-add 444455556666 --profile awssec-lab
```

이것만으로는 **대상 계정이 복원에 실패합니다.** 스냅샷이 `alias/shopmini/app`으로 암호화되어 있고 444455556666은 그 키를 쓸 수 없기 때문입니다. 키 정책에 대상 계정의 `kms:Decrypt`·`kms:CreateGrant`·`kms:DescribeKey`를 추가해야 합니다(13장).

**`aws/rds` 같은 AWS 관리형 키로 암호화한 스냅샷은 공유 자체가 불가능합니다.** EBS와 같은 제약입니다.

⚠️ **암호화된 스냅샷은 `all`(퍼블릭)로 공유할 수 없습니다.** 뒤집어 말하면, **퍼블릭으로 새어 나가는 스냅샷은 항상 미암호화 스냅샷**입니다. 16.1의 기본 암호화가 16.7의 사고를 구조적으로 막는 이유입니다.

### Performance Insights와 로그 내보내기의 민감정보

암호화를 다 켜도 **옆문으로 빠져나가는 경로**가 둘 있습니다.

| 경로 | 무엇이 새는가 | 통제 |
|---|---|---|
| **Performance Insights** | 실행된 SQL 텍스트. 상세 수준에 따라 `WHERE email='...'` 같은 **리터럴 값이 그대로** 수집될 수 있다 | 활성화 시 **고객 관리형 KMS 키 지정**(나중에 변경 불가), `pi:GetResourceMetrics`·`pi:DescribeDimensionKeys` 권한을 DBA로 한정, 보존 기간 검토 |
| **로그 내보내기**(`--enable-cloudwatch-logs-exports`) | general log·audit log·slow query log에는 **쿼리 전문**이 남는다. 감사 로그에는 접속 사용자·IP도 포함 | 로그 그룹을 로그 아카이브 계정(`777788889999`)으로 보내고 KMS 암호화, 보존 기간 설정, 읽기 권한 분리(29장) |

Performance Insights의 KMS 키는 **활성화 시점에만 지정 가능**하고 이후 변경할 수 없습니다. 저장 암호화와 같은 함정입니다.

## 16.3 DynamoDB 보안

### 저장 암호화 — 세 가지 키 유형

DynamoDB는 **모든 테이블이 항상 저장 암호화**되어 있습니다. 켜고 끄는 선택은 없고 **어떤 키를 쓸지**만 고릅니다.

| 키 유형 | 계정에 보이는가 | CloudTrail | 크로스 계정 | KMS 요금 | 언제 |
|---|---|---|---|---|---|
| **AWS 소유 키**(기본값) | 아니오 | 남지 않음 | 불가 | 없음 | 비민감 데이터, 세션·캐시 테이블 |
| **AWS 관리형 키**(`aws/dynamodb`) | 예 | 남음 | 불가 | 있음 | 감사 기록만 필요할 때 |
| **고객 관리형 키** | 예 | 남음 | 가능 | 있음 | **개인정보·결제 관련 테이블** |

기본값인 AWS 소유 키는 **KMS CloudTrail 이벤트가 남지 않습니다.** "누가 언제 복호화했는가"에 답할 수 없다는 뜻입니다. ShopMini의 주문·회원 테이블이라면 고객 관리형 키로 바꾸십시오.

```bash
aws dynamodb update-table \
  --table-name ShopMiniOrders \
  --sse-specification Enabled=true,SSEType=KMS,KMSMasterKeyId=alias/shopmini/app \
  --profile awssec-lab
```

전환은 온라인으로 진행되며 테이블은 계속 사용 가능합니다. 다만 **키를 폐기하면 테이블 접근이 즉시 불가능해집니다** — 13장의 "암호 삭제(cryptographic erasure)"가 DynamoDB에서 작동하는 방식이자, 가장 위험한 버튼입니다.

> 📖 *Practical Cloud Security* 2판 2장: **"대량의 데이터를 확실히 파기하는 것은 사실 어렵다. (…) 이것을 암호 삭제로 해결할 수 있다. 평문 데이터를 디스크에 저장하는 대신 암호화된 버전만 저장한다. 그런 다음 데이터를 복구 불가능하게 만들고 싶을 때 KMS의 키 암호화 키를 지우거나 접근을 취소하면, 그 키로 '래핑된' 모든 데이터 암호화 키가 세계 어디에 있든 쓸모없어진다."**

### 세분화 접근 제어 — `LeadingKeys`로 행 단위 격리

DynamoDB의 진짜 강점은 **IAM 정책으로 "이 사용자는 자기 행만 읽을 수 있다"** 를 표현할 수 있다는 점입니다. RDS라면 애플리케이션 코드에 의존해야 하는 통제를 IAM 계층으로 내립니다.

`ShopMiniOrders` 테이블의 파티션 키가 `CustomerId`이고, 10장의 Cognito 자격 증명 풀로 발급한 임시 자격 증명을 모바일 앱이 쓴다고 합시다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "OwnRowsOnly",
      "Effect": "Allow",
      "Action": [
        "dynamodb:GetItem",
        "dynamodb:Query",
        "dynamodb:PutItem",
        "dynamodb:UpdateItem",
        "dynamodb:DeleteItem",
        "dynamodb:BatchGetItem",
        "dynamodb:BatchWriteItem"
      ],
      "Resource": [
        "arn:aws:dynamodb:ap-northeast-2:111122223333:table/ShopMiniOrders",
        "arn:aws:dynamodb:ap-northeast-2:111122223333:table/ShopMiniOrders/index/*"
      ],
      "Condition": {
        "ForAllValues:StringEquals": {
          "dynamodb:LeadingKeys": [
            "${cognito-identity.amazonaws.com:sub}"
          ],
          "dynamodb:Attributes": [
            "CustomerId", "OrderId", "OrderDate", "Status", "TotalAmount"
          ]
        },
        "StringEqualsIfExists": {
          "dynamodb:Select": "SPECIFIC_ATTRIBUTES"
        }
      }
    }
  ]
}
```

읽는 법:

- **`dynamodb:LeadingKeys`** — 요청의 **파티션 키 값**이 `${cognito-identity.amazonaws.com:sub}`(요청자의 Cognito 신원 ID)와 같아야 합니다. 다른 고객의 `CustomerId`를 넣으면 `AccessDeniedException`입니다.
- **`dynamodb:Attributes`** — 속성을 화이트리스트로 제한합니다. `InternalRiskScore` 같은 내부 속성은 자기 행이어도 못 봅니다.
- **`dynamodb:Select`** — 속성 제한을 우회하는 "전체 속성 반환"을 막습니다. 이 조건이 없으면 `Attributes` 제한이 무력해집니다.
- ⚠️ **`Scan`은 목록에 없습니다.** `Scan`은 파티션 키를 지정하지 않아 `LeadingKeys`로 제한할 수 없습니다. 최종 사용자 정책에 절대 넣지 마십시오.

**전제는 파티션 키가 곧 테넌트/사용자 식별자라는 것**이며, 이는 테이블 설계 시점에 정해집니다. **접근 통제 요구사항을 스키마 설계에 반영해야 하고, 나중에 붙일 수 없습니다.**

### PITR과 백업

| 기능 | 무엇 | 활성화 | 한계 |
|---|---|---|---|
| **PITR**(시점 복구) | 최근 **35일** 내 초 단위 시점으로 복구 | `update-continuous-backups` | 35일을 넘는 보존 불가. 항상 **새 테이블**로 복원 |
| **온디맨드 백업** | 수동/스케줄 전체 스냅샷, 무기한 보존 | `create-backup` | 개별 항목 복구 불가 |
| **AWS Backup 연동** | 조직 차원 백업 계획·크로스 계정 복사 | 백업 계획 | 17장에서 다룸 |

```bash
aws dynamodb update-continuous-backups \
  --table-name ShopMiniOrders \
  --point-in-time-recovery-specification PointInTimeRecoveryEnabled=true \
  --profile awssec-lab
```

PITR은 **랜섬웨어·잘못된 배포로 인한 대량 삭제에 대한 유일한 방어선**입니다(17장). 비용이 저렴하니 운영 테이블 전량에 켜고 Config 규칙 `dynamodb-pitr-enabled`로 감시하십시오.

⚠️ **복원한 새 테이블의 암호화 설정과 IAM 정책은 원본을 자동으로 따라오지 않을 수 있습니다.** 복원 직후 `describe-table`로 SSE 설정을 확인하고, 리소스 ARN이 바뀌므로 정책을 다시 붙이십시오. 사고 대응 중 이 단계를 빠뜨려 복원 테이블이 넓은 권한에 노출되는 일이 흔합니다.

> 💡 **원서 이후 변경** — DynamoDB에도 **테이블 리소스 기반 정책**이 추가되어 S3 버킷 정책처럼 테이블 쪽에서 접근을 제어할 수 있습니다. 다만 권한을 **넓히는** 방향으로 쉽게 열리므로 15장의 검토 절차를 그대로 적용하십시오. DAX 클러스터를 쓴다면 **DAX의 저장·전송 암호화를 별도로 켜야** 합니다 — 테이블이 암호화되어 있어도 캐시 계층은 별개입니다.

## 16.4 EFS / FSx 암호화와 접근 지점(Access Point)

### 파일 스토리지의 고유 위협

> 📖 *Practical Cloud Security* 2판 3장은 파일 스토리지의 함정을 정확히 짚습니다. **"블록 스토리지와 마찬가지로 주된 관심사는 접근 관리다. 파일 시스템 자체가 파일에 대한 접근 제어 목록을 제공하는 경우가 많지만, 이것은 파일 스토리지가 아니라 운영체제가 강제한다. 파일 스토리지에 접근할 수 있는 공격자는 거기 저장된 모든 파일을 읽을 수 있다."**

이것이 **EFS 접근 지점(Access Point)이 필요한 이유**입니다. EFS를 마운트한 인스턴스의 root는 파일 시스템 전체를 봅니다. POSIX 권한은 그 인스턴스의 커널이 판단하므로 **인스턴스를 장악한 공격자에게는 아무 의미가 없습니다.** 통제를 EFS 쪽으로 옮겨야 합니다.

### EFS 저장·전송 암호화

⚠️ **EFS의 저장 암호화도 생성 시에만 설정할 수 있습니다.** 전환하려면 새 파일 시스템을 만들고 DataSync 등으로 복사해야 합니다.

```bash
aws efs create-file-system \
  --encrypted --kms-key-id alias/shopmini/app \
  --performance-mode generalPurpose --throughput-mode elastic \
  --tags Key=Name,Value=shopmini-uploads-efs Key=Project,Value=awssec-lab Key=Chapter,Value=ch16 Key=AutoDelete,Value=true \
  --profile awssec-lab
```

전송 중 암호화는 **마운트 옵션**입니다. 기본 NFS 마운트는 평문이며, `amazon-efs-utils`의 `tls` 옵션이 TLS 터널을 만듭니다.

```bash
sudo mount -t efs -o tls,iam,accesspoint=fsap-0123456789abcdef0 \
  fs-0a1b2c3d4e5f67890:/ /mnt/uploads
```

- `tls` — 전송 중 암호화
- `iam` — 마운트 주체를 인스턴스 역할로 인증(파일 시스템 정책 평가의 전제)
- `accesspoint` — 아래의 접근 지점 경유

### 접근 지점 — POSIX 사용자와 루트 디렉터리 강제

접근 지점은 **클라이언트가 무엇을 요청하든 EFS 쪽에서 UID/GID와 루트 경로를 덮어씁니다.**

```bash
aws efs create-access-point \
  --file-system-id fs-0a1b2c3d4e5f67890 \
  --posix-user 'Uid=1000,Gid=1000' \
  --root-directory 'Path=/shopmini/uploads,CreationInfo={OwnerUid=1000,OwnerGid=1000,Permissions=0750}' \
  --tags Key=Project,Value=awssec-lab Key=Chapter,Value=ch16 \
  --profile awssec-lab
```

1. **UID 강제** — 인스턴스에서 root(uid 0)로 접근해도 EFS는 uid 1000으로 취급합니다. 컨테이너가 root로 뜨는 흔한 구성에서도 다른 서비스의 파일을 건드릴 수 없습니다.
2. **루트 디렉터리 제한** — 클라이언트에게 `/shopmini/uploads`가 `/`로 보입니다. `..`로 상위를 탐색할 수 없어 **하나의 EFS를 여러 서비스가 안전하게 나눠 씁니다.**

Config 규칙 `efs-access-point-enforce-user-identity`와 `efs-access-point-enforce-root-directory`로 "둘 다 설정된 접근 지점만 존재"를 강제하십시오.

### 파일 시스템 정책

접근 지점만으로는 부족합니다. **접근 지점을 쓰지 않고 직접 마운트하는 경로가 남기 때문입니다.** 파일 시스템 정책으로 그 경로를 닫습니다.

```json
{
  "Version": "2012-10-17",
  "Id": "shopmini-efs-policy",
  "Statement": [
    {
      "Sid": "AllowAppTaskViaAccessPointOnly",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::111122223333:role/shopmini-app-task" },
      "Action": [
        "elasticfilesystem:ClientMount",
        "elasticfilesystem:ClientWrite"
      ],
      "Resource": "arn:aws:elasticfilesystem:ap-northeast-2:111122223333:file-system/fs-0a1b2c3d4e5f67890",
      "Condition": {
        "StringEquals": {
          "elasticfilesystem:AccessPointArn": "arn:aws:elasticfilesystem:ap-northeast-2:111122223333:access-point/fsap-0123456789abcdef0"
        }
      }
    },
    {
      "Sid": "DenyUnencryptedTransport",
      "Effect": "Deny",
      "Principal": { "AWS": "*" },
      "Action": "*",
      "Resource": "arn:aws:elasticfilesystem:ap-northeast-2:111122223333:file-system/fs-0a1b2c3d4e5f67890",
      "Condition": {
        "Bool": { "aws:SecureTransport": "false" }
      }
    }
  ]
}
```

주목할 점 두 가지입니다. **`elasticfilesystem:ClientRootAccess`를 아무에게도 주지 않았습니다** — 이 권한이 있어야 클라이언트의 root가 EFS에서도 root로 동작하며, 백업 도구 외에는 필요 없습니다. 두 번째 문장은 15장 S3 버킷 정책의 `aws:SecureTransport` 패턴을 옮긴 것으로 **평문 NFS 마운트를 거부**합니다.

⚠️ 정책을 적용하면 **명시적으로 허용되지 않은 모든 마운트가 거부**됩니다. 적용 전에 기존 마운트 주체를 전부 파악하십시오.

```bash
aws efs put-file-system-policy \
  --file-system-id fs-0a1b2c3d4e5f67890 \
  --policy file://efs-policy.json --profile awssec-lab
```

### FSx — 요약

| 서비스 | 저장 암호화 | 전송 중 암호화 | 접근 통제 |
|---|---|---|---|
| **FSx for Windows File Server** | 항상 활성(KMS) | SMB 3.0 암호화 — 공유/파일 시스템 단위로 강제 가능 | Active Directory 기반 NTFS ACL |
| **FSx for Lustre** | KMS(영구 파일 시스템은 기본 활성) | 지원 인스턴스 타입 간 자동 | POSIX + IAM |
| **FSx for NetApp ONTAP** | KMS | NFS/SMB 각각 설정 | 볼륨별 내보내기 정책, AD |
| **FSx for OpenZFS** | KMS | NFS | 내보내기 정책 |

FSx 계열의 공통 원칙은 EFS와 같습니다. **① 생성 시 고객 관리형 키 지정, ② 전송 중 암호화를 "지원"이 아니라 "강제"로 설정, ③ 파일 시스템에 붙는 모든 주체를 열거해 최소 권한 적용.** 특히 FSx for Windows는 AD 계정 관리가 곧 데이터 접근 통제입니다.

## 16.5 Glacier와 Vault Lock 🧪

### 먼저 용어부터 — 이름이 같은 서로 다른 두 가지

혼동이 잦은 지점이므로 표로 고정합니다.

| | **S3 Glacier(볼트 기반 서비스)** | **S3 Glacier 스토리지 클래스** |
|---|---|---|
| 저장 단위 | **볼트(vault)** 안의 **아카이브** | 일반 **S3 버킷** 안의 **객체** |
| API | `glacier:*` (`UploadArchive`, `InitiateJob` …) | `s3:*` (`PutObject`, `GetObject` …) |
| 이름 | 아카이브 ID(시스템 생성, 사람이 못 읽음) | 객체 키(사용자 지정) |
| 목록 조회 | 볼트 인벤토리 작업(수 시간) | `ListObjectsV2`(즉시) |
| 불변 보존 | **Vault Lock 정책** | **S3 Object Lock**(15.9) |
| 클래스 | — | Glacier Instant Retrieval / Flexible Retrieval / Deep Archive |
| 현재 권장 | 기존 자산 유지용 | **신규 아카이브의 기본 선택** |

**신규 설계라면 볼트가 아니라 S3 스토리지 클래스를 쓰십시오.** 그럼에도 Vault Lock을 다루는 이유는 ① 오래된 규제 대응 아카이브가 여전히 볼트에 남아 있고, ② **"초안 → 검증 → 완료 후 영구 불변"** 이라는 설계가 불변 보존 통제의 원형이어서 S3 Object Lock과 AWS Backup Vault Lock에 그대로 반복되기 때문입니다.

### Vault Lock 정책 걸기 🧪

> 📖 *AWS Security Cookbook* 10장 「Protecting S3 Glacier vaults with Vault Lock」은 동작을 이렇게 설명합니다. **"Vault Lock 프로세스를 시작하면 Vault Lock 정책이 설치되고 Lock ID를 받는다. 이 정책을 검증하고 24시간 안에 Lock ID로 잠금 프로세스를 완료해야 한다. (…) Vault Lock 프로세스가 완료되면 정책을 변경할 수 없다. 24시간 안에 잠금 프로세스를 완료하지 않으면 Lock ID가 만료되고 정책은 삭제된다."** 완료 화면에 나오는 확인 문구도 그대로 옮겨 두었습니다. **"Vault Lock이 의도한 대로 구성되었으며 Vault Lock 프로세스를 완료하는 것은 되돌릴 수 없음을 인지합니다."**

정책은 원서 예제와 같은 형태입니다. "생성 후 365일이 지나지 않은 아카이브는 누구도 삭제할 수 없다".

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "deny-delete-if-archive-age-less-than-year",
      "Principal": "*",
      "Effect": "Deny",
      "Action": "glacier:DeleteArchive",
      "Resource": "arn:aws:glacier:ap-northeast-2:777788889999:vaults/shopmini-audit-archive",
      "Condition": {
        "NumericLessThan": {
          "glacier:ArchiveAgeInDays": "365"
        }
      }
    }
  ]
}
```

`Principal: "*"` 와 `Effect: Deny`의 조합이 핵심입니다. **계정 루트 사용자도, 조직 관리 계정도 예외가 아닙니다.** 이것이 "규제 대응 보존"의 정의입니다.

`initiate-vault-lock`의 `--policy`는 정책 문서를 **문자열로 감싼** 형태를 요구하므로 `jq`로 변환합니다.

```bash
VAULT=shopmini-audit-archive

# 1) 정책 문서를 API 형식({"Policy":"<escaped json>"})으로 변환
jq -Rs '{Policy: .}' vault-lock-policy.json > vault-lock-request.json

# 2) 잠금 시작 → lockId 발급, 상태는 InProgress
aws glacier initiate-vault-lock --account-id - --vault-name "$VAULT" \
  --policy file://vault-lock-request.json --profile awssec-lab
# {"lockId": "AE863rKkWZU53SLW5be4DUcW"}

# 3) 24시간 안에 반드시 검증한다 (이 단계를 건너뛰지 말 것)
aws glacier get-vault-lock --account-id - --vault-name "$VAULT" --profile awssec-lab
#   → State: InProgress, ExpirationDate 확인
#   → 실제로 아카이브 삭제를 시도해 Deny 되는지, 정상 업로드는 되는지 테스트

# 4a) 검증 실패 시 — 취소 (이때만 되돌릴 수 있다)
aws glacier abort-vault-lock --account-id - --vault-name "$VAULT" --profile awssec-lab

# 4b) 검증 성공 시 — 완료. 이 명령 이후 정책은 영원히 바뀌지 않는다
aws glacier complete-vault-lock --account-id - --vault-name "$VAULT" \
  --lock-id AE863rKkWZU53SLW5be4DUcW --profile awssec-lab
```

⚠️ **3단계를 형식적으로 넘기지 마십시오.** Vault Lock의 24시간은 유예가 아니라 **검증 시간**입니다. 흔한 실패 사례 둘:

- **너무 넓게 잠갔다** — `"Action": "glacier:*"` 로 Deny를 걸어 정상 업로드까지 막힌 채 영구 고정. 볼트를 버리는 것 외에 방법이 없습니다.
- **너무 좁게 잠갔다** — `DeleteArchive`만 막고 `DeleteVault`를 빠뜨리면 볼트째 삭제해 보존이 무의미해집니다. 원서는 지원 액션 전체를 나열하므로(`DeleteVault`, `DeleteVaultAccessPolicy`, `SetVaultAccessPolicy` 등), **막을 액션을 그 목록에서 직접 골라 열거하십시오.**

**24시간이 지나면 Lock ID가 만료되고 정책이 사라집니다.** 아무 일도 없던 상태로 조용히 돌아가므로, `get-vault-lock`으로 `State: Locked`를 확인하는 절차를 체크리스트에 넣으십시오.

> 💡 **원서 이후 변경** — 오늘 새로 불변 보존을 설계한다면 **S3 Object Lock(15.9)** 이 사실상 표준입니다. 컴플라이언스 모드 + 보존 기간 + 버전 관리 조합으로 같은 보증을 얻으면서, 일반 S3 API로 목록·조회가 즉시 가능하고 라이프사이클로 Glacier 스토리지 클래스에 자동 전환됩니다. 백업 대상이 AWS 리소스라면 **AWS Backup Vault Lock**이 같은 모델을 백업 볼트에 제공합니다(17장). Glacier Vault Lock은 **이미 볼트에 자산이 있는 경우**로 한정하십시오.

## 16.6 데이터 토큰화 vs 암호화

### 원서의 정의

> 📖 *Practical Cloud Security* 1판·2판 2장은 토큰화를 이렇게 정의합니다. **"공격자에게는 쓸모없으면서 데이터와 비슷하게 기능하는 무언가를 저장할 수 있다면, 왜 데이터 자체를 저장하는가? 신용카드 번호에 가장 자주 쓰이는 토큰화는 민감한 데이터 조각을 (보통 무작위로 생성된) 토큰으로 대체한다. 토큰이 원본 데이터와 같은 특성(예: 16자리 길이)을 갖는다는 이점이 있어서, 그 데이터를 받도록 만들어진 하위 시스템을 수정할 필요가 없다. 오직 한 곳('토큰 서비스')만이 실제 민감 데이터를 안다. 토큰화는 단독으로 쓸 수도 있고 암호화와 함께 쓸 수도 있다."**
>
> 구현 형태도 제시합니다. **"브라우저와 함께 동작해 데이터를 보내기 전에 민감 데이터를 토큰화하는 클라우드 서비스, 그리고 브라우저와 애플리케이션 사이에 위치해 민감 데이터가 애플리케이션에 도달하기 전에 토큰화하는 클라우드 서비스가 예다."**

여기에 이 절의 전부가 있습니다. **"오직 한 곳만이 실제 데이터를 안다"** 와 **"하위 시스템을 수정할 필요가 없다"** 입니다.

### 결정적인 차이

| | **암호화** | **토큰화** |
|---|---|---|
| 원본 복원 방법 | **키**로 수학적 복호화 | **토큰 볼트의 매핑 테이블** 조회 |
| 토큰/암호문과 원본의 관계 | 수학적 관계 존재 — 키가 새면 전부 복원 | **관계 없음** — 볼트 없이는 복원 불가 |
| 형식 유지 | 깨짐(길이·문자셋 변경) | **유지**(16자리 → 16자리) |
| 하위 시스템 수정 | 스키마·검증 로직 변경 필요 | 대개 불필요 |
| 검색·정렬·조인 | 불가(애플리케이션 계층 암호화 시) | 토큰 기준으로 **가능** |
| 확장성 | 무상태, 무한 확장 | 볼트가 단일 병목·단일 실패점 |
| 규제 관점 | 암호문도 규제 대상 데이터로 볼 여지가 남음 | 토큰 보관 시스템을 **규제 범위에서 제외**할 근거가 된다 |
| 주된 위험 | 키 유출 | **볼트 침해 = 전부 유출** |

세 번째 줄과 마지막 줄이 짝을 이룹니다. 토큰과 원본 사이에 수학적 관계가 없다는 것은 **볼트를 털지 않는 한 안전하다**는 뜻이자, **볼트를 털면 끝**이라는 뜻입니다. 토큰화는 위험을 없애는 것이 아니라 **한 곳으로 모으는 것**이며, 그 한 곳을 지킬 자신이 있을 때만 이득입니다.

### 언제 토큰화가 유리한가

1. **규제 범위(scope) 축소가 목적일 때.** 결제 카드 데이터가 스무 개 시스템을 흘러다닌다면 스무 개 전부에 카드 데이터 취급 통제를 적용해야 합니다. 진입 지점에서 토큰으로 바꾸면 **원본은 볼트 한 곳에만 존재**하고 감사·통제 대상이 1/20로 줄어듭니다. 토큰화의 가장 큰 실질 이득입니다.
2. **하위 시스템을 고칠 수 없을 때.** 형식이 유지되므로 16자리 숫자를 전제로 만들어진 레거시 배치·정산을 **수정 없이** 씁니다. 애플리케이션 계층 암호화라면 스키마부터 바꿔야 합니다.
3. **분석 시스템이 원본을 알 필요가 없을 때.** "같은 고객인가"만 판단하면 되는 파이프라인에는 토큰으로 충분합니다.

반대로 **원본을 자주, 여러 곳에서 복원해야 한다면 볼트 호출 비용과 가용성 문제만 남습니다.** 그때는 암호화가 맞습니다.

### AWS에서의 구현 접근

**AWS에는 범용 토큰화 관리형 서비스가 없습니다.** 다음에서 고릅니다.

| 접근 | 구성 | 적합한 경우 |
|---|---|---|
| **자체 토큰 볼트** | 전용 계정 + DynamoDB(고객 관리형 키) 매핑 테이블 + API Gateway/Lambda 토큰 서비스. 앱은 `Tokenize`/`Detokenize` API만 호출 | 토큰화 대상이 명확하고 트래픽을 감당할 수 있을 때 |
| **필드 단위 클라이언트 측 암호화** | **AWS Database Encryption SDK**(DynamoDB용)로 특정 속성만 앱에서 암호화. 파티션 키는 평문 유지 | 토큰화까지 필요 없고 "가장 민감한 몇 개 필드"만 가릴 때 |
| **서드파티 토큰화 서비스** | 결제 PG·마켓플레이스 제품 | 카드 데이터를 아예 자기 환경에 들이고 싶지 않을 때 — **가장 권장** |
| **결제 암호 연산 전용** | AWS Payment Cryptography(결제 카드 암호 연산·키 관리 전용 서비스) | 결제 처리 자체를 직접 수행할 때 |

자체 볼트를 만든다면 최소한 이 다섯 가지를 지키십시오.

- 볼트를 **별도 계정**에 두고 앱 계정에서는 토큰 서비스 API만 호출한다(네트워크·IAM 이중 격리).
- 매핑 테이블은 **고객 관리형 KMS 키**로 암호화하고 키 정책에 토큰 서비스 역할만 넣는다.
- `Detokenize`는 **호출자·건수를 로그로 남기고 임계치 경보**를 건다. 대량 역토큰화는 그 자체가 침해 신호다.
- 토큰은 **암호학적 난수**로 생성한다. 원본에서 유도(해시 등)하면 사전 공격으로 역산된다.
- 볼트의 백업·복구 설계를 먼저 끝낸다. **볼트가 죽으면 전 시스템이 원본을 잃는다.**

원서가 말한 **"토큰화는 암호화와 함께 쓸 수도 있다"** 가 결론입니다. 실무에서는 **토큰화(범위 축소) 위에 저장 암호화(16.1~16.5)와 전송 암호화를 겹쳐** 씁니다. 둘 중 하나를 고르는 문제가 아닙니다.

## 16.7 ⚠️ 스냅샷·AMI·백업의 공유 설정 사고

### 사고 시나리오

ShopMini가 신규 결제 파트너와 연동 테스트를 하게 되었습니다. 파트너 엔지니어가 "테스트용 앱 이미지를 공유해 달라"고 요청했고, 담당자는 AMI의 **Modify Image Permissions**를 열었습니다. 파트너 계정 ID를 물어보는 사이 회의가 길어졌고, 담당자는 일단 **Public**을 선택해 저장한 뒤 "나중에 계정 ID 받으면 바꾸자"고 생각했습니다.

그 AMI의 루트 볼륨은 **미암호화**였고, 안에는 개발 편의로 남겨둔 `.env` 파일과 CI 배포용 IAM 액세스 키가 들어 있었습니다. 5주 뒤 GuardDuty가 **처음 보는 리전에서 대량 EC2 기동**을 탐지했고, 조사 결과 유출된 키로 채굴 인스턴스가 기동된 것으로 확인됩니다. 이 시점에 해당 AMI는 이미 여러 사용자가 자기 계정으로 복사한 상태였습니다.

### 원인

**첫째, 공유 설정은 "한 번의 실수"가 즉시 전 세계 공개가 되는 소수의 설정 중 하나입니다.** 잘못된 보안 그룹은 공격자가 접근을 시도해야 피해가 나지만, 퍼블릭 AMI·스냅샷은 **검색 가능한 목록에 올라갑니다.**

**둘째, "나중에 되돌린다"가 성립하지 않습니다.** 퍼블릭 해제는 원본만 되돌리고 **이미 복사된 사본은 회수할 수 없습니다.** 3장의 위협 모델 표에서 "퍼블릭 스냅샷·AMI"에 "로그가 남지 않는다"고 적은 이유이기도 합니다 — 누가 복사했는지 알 수 없습니다.

**셋째, 이미지에 시크릿이 들어 있었습니다.** 원서가 정확히 경고한 상황입니다.

> 📖 *Practical Cloud Security* 2판 3장 「Images」: **"조직 안에는 이미지의 내용에 접근하고 그것으로 인스턴스를 만들 수 있는 사람이 많은 경우가 흔하다. 이 때문에 이미지는 인스턴스 실행에 필요한 모든 정보를 담아서는 안 된다. 예를 들어 이미지에는 비밀번호나 API 키 같은 민감한 정보가 들어가면 안 되는데, 이미지를 만들거나 볼 수 있는 모든 사람이 그 시크릿을 알아야 하는 것은 아니기 때문이다. 이미지는 그 사본(인스턴스)이 시작될 때 아주 소수만 접근할 수 있는 안전한 위치에서 시크릿을 가져오도록 구성되어야 한다."**

11.1의 "시크릿을 두면 안 되는 7곳" 중 4번(AMI/이미지 레이어)이 그대로 실현된 것입니다.

**넷째, 미암호화였기 때문에 가능했습니다.** **암호화된 EBS·RDS 스냅샷은 퍼블릭 공유가 아예 불가능합니다.** 16.1의 리전 기본 암호화가 켜져 있었다면 이 사고는 API 수준에서 차단되었습니다.

### 탐지 — 지금 당장 확인하기

```bash
ACCT=111122223333

# ① 퍼블릭으로 열린 내 EBS 스냅샷 (--restorable-by-user-ids all = 퍼블릭)
aws ec2 describe-snapshots --restorable-by-user-ids all --owner-ids $ACCT \
  --query 'Snapshots[].{Id:SnapshotId,Vol:VolumeId,Time:StartTime,Enc:Encrypted,Desc:Description}' \
  --output table --profile awssec-lab

# ② 퍼블릭으로 열린 내 AMI
aws ec2 describe-images --owners self --filters Name=is-public,Values=true \
  --query 'Images[].{Id:ImageId,Name:Name,Date:CreationDate}' \
  --output table --profile awssec-lab

# ③ 외부 계정에 공유한 RDS 수동 스냅샷
for s in $(aws rds describe-db-snapshots --snapshot-type manual \
             --query 'DBSnapshots[].DBSnapshotIdentifier' --output text --profile awssec-lab); do
  v=$(aws rds describe-db-snapshot-attributes --db-snapshot-identifier "$s" \
        --query 'DBSnapshotAttributesResult.DBSnapshotAttributes[?AttributeName==`restore`].AttributeValues[]' \
        --output text --profile awssec-lab)
  [ -n "$v" ] && echo "SHARED  $s -> $v"
done
```

③에서 `all`이 출력되면 **그 스냅샷은 전 세계에 공개된 데이터베이스 백업**입니다. ①②는 리전별 API이므로 `describe-regions` 루프로 감싸고, 조직 전체는 보안 도구 계정(`444455556666`)의 감사 역할로 순회하십시오.

### 즉시 조치

```bash
# EBS 스냅샷 퍼블릭 해제
aws ec2 modify-snapshot-attribute --snapshot-id snap-0123456789abcdef0 \
  --attribute createVolumePermission --operation-type remove --group-names all --profile awssec-lab

# AMI 퍼블릭 해제
aws ec2 modify-image-attribute --image-id ami-0123456789abcdef0 \
  --launch-permission "Remove=[{Group=all}]" --profile awssec-lab

# RDS 스냅샷 퍼블릭 해제
aws rds modify-db-snapshot-attribute --db-snapshot-identifier shopmini-2026-03 \
  --attribute-name restore --values-to-remove all --profile awssec-lab
```

**해제로 끝내지 마십시오.** 노출 기간에 사본이 만들어졌다고 가정하고 **그 이미지·스냅샷에 담긴 모든 자격 증명을 순환**하십시오(11장). 유출된 시크릿은 삭제가 아니라 순환으로만 무효화됩니다.

### 예방 — 3중 방어

**① 계정·리전 단위 퍼블릭 공유 차단 (가장 강력)**

> 💡 **원서 이후 변경** — EBS 스냅샷과 AMI에 **계정·리전 단위 퍼블릭 액세스 차단** 스위치가 추가되었습니다. 15장 S3의 퍼블릭 액세스 차단과 같은 개념으로 개별 리소스 설정보다 상위에서 작동합니다.

```bash
# EBS 스냅샷: 기존 퍼블릭 스냅샷까지 즉시 비공개 처리
aws ec2 enable-snapshot-block-public-access --state block-all-sharing \
  --region ap-northeast-2 --profile awssec-lab

# AMI: 신규 퍼블릭 공유 차단
aws ec2 enable-image-block-public-access \
  --image-block-public-access-state block-new-sharing \
  --region ap-northeast-2 --profile awssec-lab
```

EBS 쪽 `block-all-sharing`은 **이미 퍼블릭인 스냅샷도 즉시 비공개**로 만듭니다. **전 리전 루프**로 적용하십시오.

**② SCP로 잠그기**

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyPublicEbsSnapshotSharing",
      "Effect": "Deny",
      "Action": "ec2:ModifySnapshotAttribute",
      "Resource": "*",
      "Condition": {
        "StringEquals": { "ec2:Add/group": "all" }
      }
    },
    {
      "Sid": "DenyTurningOffPublicAccessBlocks",
      "Effect": "Deny",
      "Action": [
        "ec2:DisableSnapshotBlockPublicAccess",
        "ec2:DisableImageBlockPublicAccess"
      ],
      "Resource": "*",
      "Condition": {
        "ArnNotLike": {
          "aws:PrincipalArn": "arn:aws:iam::*:role/BreakGlassStorageAdmin"
        }
      }
    },
    {
      "Sid": "RestrictRdsSnapshotSharing",
      "Effect": "Deny",
      "Action": [
        "rds:ModifyDBSnapshotAttribute",
        "rds:ModifyDBClusterSnapshotAttribute"
      ],
      "Resource": "*",
      "Condition": {
        "ArnNotLike": {
          "aws:PrincipalArn": "arn:aws:iam::*:role/DataSharingApprover"
        }
      }
    }
  ]
}
```

`ec2:Add/group` 조건 키가 핵심입니다. **"공유 대상에 `all`을 추가하는 행위"만 콕 집어 거부**하므로 특정 계정과의 정당한 공유는 그대로 허용됩니다. RDS에는 대응하는 조건 키가 없어 **공유 API 자체를 지정 역할로 한정**합니다.

**③ 상시 감지 — Config + Trusted Advisor**

| 통제 | 규칙/체크 | 대상 |
|---|---|---|
| AWS Config | `ebs-snapshot-public-restorable-check` | 퍼블릭 복원 가능한 EBS 스냅샷 |
| AWS Config | `rds-snapshots-public-prohibited` | 퍼블릭 RDS 스냅샷 |
| AWS Config | `rds-instance-public-access-check` | 퍼블릭 액세스 DB 인스턴스 |
| AWS Config | `encrypted-volumes` / `ec2-ebs-encryption-by-default` | 미암호화 EBS |
| AWS Config | `rds-storage-encrypted` / `rds-snapshot-encrypted` | 미암호화 RDS |
| AWS Config | `dynamodb-table-encrypted-kms` / `dynamodb-pitr-enabled` | DynamoDB |
| AWS Config | `efs-encrypted-check`, `efs-access-point-enforce-user-identity`, `efs-access-point-enforce-root-directory` | EFS |
| Trusted Advisor | Amazon EBS Public Snapshots / Amazon RDS Public Snapshots | 퍼블릭 스냅샷 |

> 📖 *AWS Security Cookbook* 10장은 Trusted Advisor의 **무료 Basic 플랜에서도 쓸 수 있는** 보안 점검을 나열하는데, 여기에 **"Amazon EBS Public Snapshots"** 와 **"Amazon RDS Public Snapshots"** 가 포함됩니다. 지원 플랜 등급과 무관하게 오늘 바로 확인할 수 있다는 뜻입니다. 같은 책 8장은 Config 점검 예시로 **"데이터베이스가 암호화되었는지"** 를 꼽고 **"AWS Config는 규칙에 대해 자동 교정 작업을 수행할 수 있다"** 고 덧붙입니다.

Config 규칙은 **자동 교정(remediation)까지 붙여야 의미가 있습니다.** 탐지 후 티켓 처리에 하루가 걸린다면 그 하루가 노출 시간입니다. SSM Automation 문서로 해제를 자동 실행하십시오.

### 올바른 공유 절차

1. **무엇을 공유하는지 확인** — 스냅샷/AMI 안의 데이터 등급(12장)과 시크릿 포함 여부를 검사한다.
2. **전용 사본을 만든다** — 운영 스냅샷을 직접 공유하지 않고, 필요한 데이터만 담은 사본을 만든다.
3. **고객 관리형 키로 암호화한다** — 암호화하면 퍼블릭 공유가 물리적으로 불가능해진다.
4. **계정 ID를 명시해 공유하고, KMS 키 정책에도 같은 계정을 추가한다.**
5. **만료를 정한다** — 해제 날짜를 태그로 남기고 EventBridge 스케줄로 자동 해제한다.
6. **CloudTrail에서 `ModifySnapshotAttribute`·`ModifyImageAttribute`·`ModifyDBSnapshotAttribute`를 알람 대상으로 둔다.**

| EBS | 🔴 **리전 단위 기본 암호화 + 고객 관리형 키**. 전 리전 일괄, SCP로 잠금. 스냅샷은 상속, 키 교체는 복사로만 |

| DynamoDB | 항상 암호화 — **키 유형만 선택**. 민감 테이블은 고객 관리형 키. `LeadingKeys`로 행 단위 격리, `Scan` 금지 |
| EFS | 저장 암호화는 **생성 시에만**. `tls,iam,accesspoint` 마운트 + 접근 지점(UID·루트 강제) + 파일 시스템 정책 |
| Glacier | 볼트 서비스 ≠ S3 스토리지 클래스. Vault Lock은 24시간 안에 **검증**하고 완료. 신규는 S3 Object Lock |
| 토큰화 | 원본을 한 곳에만 둬 **규제 범위를 축소**. 형식 유지가 이점, 볼트가 단일 실패점. 암호화와 함께 쓴다 |
| 공유 사고 | 암호화된 스냅샷은 퍼블릭 공유 **불가**. 계정 단위 차단 + SCP(`ec2:Add/group`) + Config 자동 교정 3중 |

- [ ] `ec2:DisableEbsEncryptionByDefault`와 `ec2:CreateVolume`(`ec2:Encrypted=false`)를 SCP로 거부했다
- [ ] 미암호화 볼륨·스냅샷 목록이 0이고, 전환 후 **평문 원본을 삭제**했다
- [ ] 모든 RDS/Aurora가 `StorageEncrypted=true`이고 고객 관리형 키를 쓴다
- [ ] `require_secure_transport`/`rds.force_ssl`이 강제되고 클라이언트가 **인증서 검증**까지 한다
- [ ] 모든 DB 인스턴스가 `PubliclyAccessible=false`이고 격리 서브넷에 있다
- [ ] 사람의 DB 접속이 IAM 데이터베이스 인증 또는 Session Manager 경유다
- [ ] Performance Insights·로그 내보내기의 KMS 키와 열람 권한이 지정되어 있다
- [ ] 민감 DynamoDB 테이블이 고객 관리형 키이고 **PITR이 켜져 있다**
- [ ] DynamoDB 최종 사용자 정책에 `Scan`이 없고 `LeadingKeys`로 제한된다
- [ ] EFS가 암호화되어 있고 `tls` 마운트 + 접근 지점 + 파일 시스템 정책 3중이다
- [ ] `ClientRootAccess`를 가진 주체가 백업 도구뿐이다
- [ ] Vault Lock을 쓴다면 `get-vault-lock` 상태가 `Locked`다
- [ ] `enable-snapshot-block-public-access`·`enable-image-block-public-access`가 전 리전에 적용됐다
- [ ] 퍼블릭 EBS 스냅샷·AMI·RDS 스냅샷이 **전 계정·전 리전에서 0건**이고 Config가 상시 감시한다
- [ ] 스냅샷·AMI 공유 API 호출이 CloudTrail 알람 대상이다

## ⚠️ 자주 하는 실수

| 실수 | 결과 | 올바른 구성 |
|---|---|---|
| EBS 암호화를 인스턴스 생성 화면에서만 챙긴다 | ASG·CI·마켓플레이스 AMI 경로로 미암호화 볼륨이 샌다 | 리전 단위 기본 암호화 + SCP (16.1) |
| 기본 암호화를 서울 리전에만 켠다 | 쓰지 않는 리전에 감시 없는 평문 볼륨이 생긴다 | `describe-regions` 루프로 전 리전 (16.1) |
| `aws/ebs`·`aws/rds`를 그대로 쓴다 | 스냅샷 **크로스 계정 공유 불가** — DR 구성 시점에 전량 재암호화 | 처음부터 고객 관리형 키 (16.1, 16.2) |
| 볼륨 전환 후 원본 스냅샷을 남긴다 | 평문 사본이 그대로 존재 — 암호화한 의미가 없다 | 검증 후 원본 스냅샷·볼륨·AMI 삭제 (16.1) |
| RDS를 만들고 "암호화는 나중에" 한다 | **나중이 없다.** 스냅샷→복사→복원 + 엔드포인트 변경 | 생성 시 `--storage-encrypted` (16.2) |
| TLS를 "지원"만 하고 강제하지 않는다 | 클라이언트 하나가 평문으로 붙어도 아무도 모른다 | 파라미터 그룹으로 강제 (16.2) |
| `--ssl-mode=REQUIRED`로 만족한다 | 암호화는 되지만 서버 신원 미검증 — 중간자 공격 가능 | `VERIFY_IDENTITY` + RDS 루트 CA 번들 (16.2) |
| 로컬 접속 편의로 `PubliclyAccessible=true`로 바꾼다 | SG 실수 하나와 겹쳐 DB가 인터넷에 노출 (16.2 시나리오) | Session Manager 포트 포워딩 (16.2, 22장) |
| 암호화 스냅샷만 공유하고 KMS 키를 안 준다 | 대상 계정 복원 실패 — 원인 파악에 시간 소모 | 키 정책에 대상 계정 추가 (16.2, 13장) |
| Performance Insights를 기본 키로 켠다 | KMS 키는 **활성화 시에만 지정 가능**, SQL 리터럴이 수집됨 | 고객 관리형 키 지정 + 열람 권한 한정 (16.2) |
| DynamoDB는 "자동 암호화니까" 두고 본다 | AWS 소유 키는 **CloudTrail 기록이 없어** 조사 불가 | 민감 테이블은 고객 관리형 키 (16.3) |
| 최종 사용자 정책에 `dynamodb:Scan`을 넣는다 | `LeadingKeys`가 적용되지 않아 **전 고객 데이터 조회** | Scan 제외, Query/GetItem만 (16.3) |
| `dynamodb:Attributes`만 쓰고 `Select` 조건을 뺀다 | 전체 속성 반환으로 화이트리스트 무력화 | `dynamodb:Select=SPECIFIC_ATTRIBUTES` 병행 (16.3) |
| PITR 복원 테이블의 설정을 확인하지 않는다 | 암호화·정책이 원본과 달라 복원본이 넓게 노출 | 복원 직후 `describe-table` 검증 (16.3) |
| EFS를 만들고 암호화를 나중에 켜려 한다 | **불가능.** 새 파일 시스템 + DataSync 복사 | 생성 시 `--encrypted` (16.4) |
| EFS를 기본 NFS로 마운트한다 | 전송 구간 평문 — VPC 내부라도 노출 | `-o tls,iam,accesspoint=...` (16.4) |
| 접근 지점만 만들고 파일 시스템 정책을 안 건다 | 직접 마운트 경로가 열려 있어 접근 지점이 우회된다 | 정책으로 `AccessPointArn` 조건 강제 (16.4) |
| Vault Lock을 시작하고 24시간 안에 완료하지 않는다 | Lock ID 만료 → **정책이 조용히 사라진다** | `get-vault-lock`으로 `Locked` 확인 (16.5) |
| Vault Lock 정책을 `glacier:*` Deny로 건다 | 정상 업로드까지 영구 차단 — 되돌릴 수 없다 | 막을 액션만 열거, 24시간 안에 실제 테스트 (16.5) |
| 토큰 볼트를 앱과 같은 계정·같은 DB에 둔다 | 앱 침해가 곧 원본 전량 유출 — 토큰화 이점 소멸 | 전용 계정 + API 경유 + 역토큰화 감사 (16.6) |
| 토큰을 원본 해시로 만든다 | 사전 공격으로 카드번호 역산 | 암호학적 난수 + 매핑 테이블 (16.6) |
| AMI를 임시로 Public으로 열고 "나중에 바꾼다" | 복사된 사본은 **회수 불가**, 시크릿 유출 (16.7 시나리오) | 계정 ID 명시 공유 + 계정 단위 차단 (16.7) |
| 퍼블릭 해제만 하고 조치를 끝낸다 | 유출된 자격 증명이 계속 유효 | 이미지 내 모든 시크릿 **순환** (16.7, 11장) |
| Config 규칙만 켜고 자동 교정을 안 붙인다 | 탐지에서 조치까지의 시간이 그대로 노출 시간 | SSM Automation 자동 교정 연결 (16.7) |
