# 22장. 컴퓨트(EC2) 보안

> **이 장에서 다루는 것**
> - **인스턴스 시작 시점의 결정** 🧪 — 서브넷 배치, 퍼블릭 IP 자동 할당 비활성화, 종료 방지, 상세 모니터링. 나중에 못 바꾸는 것과 바꿀 수 있는 것
> - **키 페어의 근본 문제** 🧪 ⚠️ — 자체 생성 키 임포트, 그리고 "유출된 키는 회수되지 않는다"는 사실. 키 없는 접근으로의 전환
> - **인스턴스 프로파일 운영** 🧪 🔴 — 무중단 역할 교체, 한 인스턴스에 여러 앱이 있을 때의 경계 붕괴
> - **User Data의 평문 노출** 🧪 ⚠️ — IMDS에서 누구나 읽는다. 16KB 제한과 `cloud-init` 디버깅
> - **골든 AMI 파이프라인** 🧪 — EC2 Image Builder, AMI 위생과 수명 주기
> - **패치 관리** 🔴 — SSM Patch Manager 베이스라인·패치 그룹·유지 관리 기간·규정 준수 보고
> - **호스트 수준 보호** — EDR, 파일 무결성 모니터링, CWPP/CNAPP
> - **불변 인프라로의 전환** 🔴 — SSH로 접속할 일 자체를 없애는 것이 이 장의 도착점
>
> **선행 지식**: 8장(인스턴스 프로파일·IMDS), 11장(시크릿 관리), 16장(EBS 암호화·AMI 공유), 19장(보안 그룹), 21장(Session Manager)
> **난이도**: ★★☆

---

18~21장에서 ShopMini의 네트워크 경계를 만들었습니다. 이제 그 경계 **안쪽**으로 들어갑니다.

EC2는 공동 책임 모델에서 소비자 책임이 가장 무거운 지점입니다. S3에서는 AWS가 스토리지 소프트웨어를 통째로 책임지지만, EC2에서는 커널 위의 모든 것이 우리 몫입니다.

> 📖 *Practical Cloud Security* 2판 3장 「Compute Assets」: **"너무나 많은 서로 다른 구성 요소가 뒤섞여 하나의 VM을 이루기 때문에, 우리는 서버의 각 계층마다 취약점 관리·접근 관리·구성 관리에 주의를 기울여야 한다. 공격에 성공한 자는 그 VM이 접근할 수 있는 모든 데이터에 접근할 수 있다. 또한 침해된 VM을 발판으로 나머지 인프라를 공격하거나 다른 조직을 공격할 수도 있다."**

이 장은 시간 순서를 따라갑니다. 인스턴스를 **시작하는 순간**(22.1~22.4) → 시작할 **이미지를 만드는 과정**(22.5) → 살아 있는 동안의 **유지**(22.6~22.7) → 유지 자체를 없애는 방향(22.8)입니다.

## 22.1 EC2 인스턴스 시작과 서브넷 배치 🧪

### 서브넷 배치가 첫 번째 보안 결정이다

> 📖 *AWS Security Cookbook* 6장 「Launching an EC2 instance into a VPC」: **"일반적으로 퍼블릭 서브넷은 웹 서버처럼 인터넷에서 접근 가능한 애플리케이션을 호스팅하고, 프라이빗 서브넷은 데이터베이스 서버처럼 퍼블릭 서브넷에서만 접근 가능한 애플리케이션을 호스팅한다."** 그리고 **"현실의 시나리오에서는 일반적으로 특정 IP 범위에 접근을 주거나, 점프 호스트 또는 배스천 호스트라고 불리는 별도의 전용 머신에 접근을 준다."**

원서가 2020년에 "현실에서는 배스천을 쓴다"고 한 지점을, 이 책은 21.5에서 **관리 포트를 아예 열지 않는 구성**으로 한 걸음 더 밀었습니다. ShopMini의 배치는 이렇게 됩니다.

| 계층 | 서브넷 | 퍼블릭 IP | 인바운드 |
|---|---|---|---|
| ALB | `10.20.0.0/24`, `10.20.1.0/24` (public) | ALB가 소유(인스턴스 아님) | CloudFront 접두사 목록에서 443 |
| 앱 EC2 | `10.20.10.0/24`, `10.20.11.0/24` (private-app) | **없음** | `alb-sg`에서 8443만 |
| RDS | `10.20.20.0/24`, `10.20.21.0/24` (isolated-data) | 없음 | `app-sg`에서 3306만 |

앱 인스턴스에 퍼블릭 IP가 없다는 것이 핵심입니다. 인터넷에서 오는 인바운드 연결 시도 자체가 도달할 수 없으므로, 보안 그룹 오설정 한 번이 곧바로 인터넷 노출로 이어지는 상황이 만들어지지 않습니다.

### 서브넷 기본값부터 확인한다

인스턴스마다 챙기는 대신 서브넷 속성으로 못 박습니다. 18.3에서 6개 서브넷 모두 `--no-map-public-ip-on-launch`로 설정했으니, 여기서는 그 상태가 유지되고 있는지부터 확인합니다.

```bash
# 퍼블릭 IP 자동 할당이 켜진 서브넷이 있으면 나열된다 — 결과가 비어 있어야 정상
aws ec2 describe-subnets \
  --filters "Name=vpc-id,Values=$VPC_ID" \
  --query "Subnets[?MapPublicIpOnLaunch==\`true\`].[SubnetId,CidrBlock,Tags[?Key=='Name']|[0].Value]" \
  --output table --profile awssec-lab
```

### 시작 템플릿으로 시작한다

`run-instances`에 옵션을 나열하는 방식은 실습에는 좋지만 운영에는 나쁩니다. 사람마다 빠뜨리는 옵션이 다르기 때문입니다. **시작 템플릿(Launch Template)** 하나에 보안 기본값을 박고, Auto Scaling과 사람이 모두 그 템플릿을 쓰게 합니다.

```bash
# sg-0app... 는 19.2에서 만든 $SG_APP 의 값으로 바꾼다
cat > /tmp/lt-app.json <<'JSON'
{
  "ImageId": "ami-0a1b2c3d4e5f60011",
  "InstanceType": "m6i.large",
  "IamInstanceProfile": { "Name": "ShopMiniAppInstanceProfile" },
  "SecurityGroupIds": ["sg-0app0000000000000"],
  "MetadataOptions": {
    "HttpTokens": "required",
    "HttpPutResponseHopLimit": 1,
    "HttpEndpoint": "enabled"
  },
  "Monitoring": { "Enabled": true },
  "DisableApiTermination": true,
  "InstanceInitiatedShutdownBehavior": "stop",
  "BlockDeviceMappings": [
    {
      "DeviceName": "/dev/xvda",
      "Ebs": {
        "VolumeSize": 30,
        "VolumeType": "gp3",
        "Encrypted": true,
        "KmsKeyId": "alias/shopmini/app",
        "DeleteOnTermination": true
      }
    }
  ],
  "TagSpecifications": [
    {
      "ResourceType": "instance",
      "Tags": [
        { "Key": "Name",        "Value": "shopmini-app" },
        { "Key": "Project",     "Value": "awssec-lab" },
        { "Key": "Chapter",     "Value": "ch22" },
        { "Key": "Patch Group", "Value": "shopmini-prod-app" },
        { "Key": "DataClass",   "Value": "confidential" }
      ]
    }
  ]
}
JSON

aws ec2 create-launch-template \
  --launch-template-name shopmini-app \
  --version-description "golden AMI 2024-11, IMDSv2 required" \
  --launch-template-data file:///tmp/lt-app.json \
  --profile awssec-lab

# 프라이빗앱 서브넷으로 1대 시작 — 서브넷만 지정하면 나머지는 템플릿이 결정한다
aws ec2 run-instances \
  --launch-template LaunchTemplateName=shopmini-app,Version='$Latest' \
  --subnet-id "$SN_APP_A" --count 1 --profile awssec-lab
```

보안 그룹을 `SecurityGroupIds`(최상위)로 넣고 `NetworkInterfaces`를 쓰지 않은 것은 의도적입니다. 템플릿에 `NetworkInterfaces`가 있으면 `run-instances --subnet-id`나 ASG의 서브넷 지정과 충돌해 요청이 거부됩니다. 퍼블릭 IP 억제는 서브넷 속성이 이미 담당하고 있으므로 템플릿에서 다시 지정할 필요가 없습니다.

각 항목이 왜 거기 있는지는 다음과 같습니다.

| 설정 | 값 | 안 하면 |
|---|---|---|
| 퍼블릭 IP(서브넷 속성) | `MapPublicIpOnLaunch=false` | 프라이빗 서브넷에 두고도 IGW 경로가 생기면 인터넷 노출 |
| `HttpTokens: required` | IMDSv2 강제 | SSRF 한 번으로 역할 자격 증명 탈취 (8.3) |
| `HttpPutResponseHopLimit: 1` | 홉 제한 | 컨테이너가 호스트 인스턴스의 역할을 훔쳐 씀 |
| `DisableApiTermination` | `true` | 오타 하나로 운영 인스턴스 영구 삭제. EBS까지 함께 사라짐 |
| `InstanceInitiatedShutdownBehavior` | `stop` | 게스트 OS의 `shutdown -h`가 인스턴스를 종료(삭제)시킴 |
| `Monitoring.Enabled` | `true`(1분 간격) | 기본 5분 간격 지표로는 짧은 스파이크·비정상 트래픽을 놓침 |
| `Encrypted` + `KmsKeyId` | 고객 관리형 키 | 스냅샷·AMI가 평문으로 남음 (16.1) |
| `Patch Group` 태그 | 패치 그룹 | Patch Manager가 이 인스턴스를 대상으로 잡지 못함 (22.6) |

`DisableApiTermination`은 종료 **방지**일 뿐 종료 **불가**가 아닙니다. 해제 권한이 있으면 두 단계로 삭제됩니다. 실질적 방어는 SCP나 권한 경계로 `ec2:TerminateInstances`를 제한하는 것이고, 종료 방지는 "실수로 인한 삭제"만 막는 안전장치입니다.

> 💡 **원서 이후 변경** — 2020년 이후 EC2 기본값이 여러 번 강화됐습니다. 계정·리전 단위 EBS 기본 암호화(16.1), IMDSv2 기본값, 그리고 `aws ec2 enable-allowed-images-settings`로 계정에서 시작 가능한 AMI 공급자를 제한하는 **Allowed AMIs** 통제가 추가됐습니다.

시작 후 점검은 AWS Config에 맡깁니다. `ec2-instance-no-public-ip`, `ec2-imdsv2-check`, `ec2-instance-detailed-monitoring-enabled`, `ec2-instance-profile-attached`, `ec2-instance-managed-by-systems-manager`를 조직 단위로 배포하면 템플릿을 우회해 콘솔에서 만든 인스턴스가 드러납니다.

## 22.2 키 페어 관리 🧪 ⚠️

### 사고 시나리오

ShopMini 팀은 3년 전 `shopmini-prod.pem`을 만들어 운영 인스턴스에 넣고 계속 써 왔습니다. 그동안 이런 일이 있었습니다.

- 개발자 4명이 각자 노트북에 사본을 두고 있습니다. 그중 한 명은 퇴사했습니다.
- 배포 파이프라인용으로 CI 서버의 환경 변수에도 같은 키가 들어 있습니다.
- 이 키가 든 인스턴스로 골든 AMI를 만들었고, 그 AMI에서 200번쯤 인스턴스가 시작됐습니다.
- 6개월 전 한 개발자가 실수로 사내 위키에 붙여 넣었다가 지웠습니다.

어느 날 보안팀이 "그 키를 폐기하라"고 지시합니다. 팀은 콘솔에서 키 페어를 삭제합니다. **그래도 아무것도 변하지 않습니다.**

### 원인 — 키 페어 삭제는 회수가 아니다

EC2 키 페어는 인스턴스가 **시작될 때 한 번** 공개 키를 게스트 OS의 `authorized_keys`에 복사할 뿐입니다. 그 뒤로 AWS는 관여하지 않습니다.

> 📖 *AWS Security Cookbook* 6장 「Using our own private and public keys with EC2」: **"인스턴스의 터미널에서 `/home/ec2-user/.ssh/authorized_keys`로 가면 EC2 인스턴스에 연결된 공개 키들을 볼 수 있다."** **"해당 키 페어의 공개 키를 `/home/ec2-user/.ssh/authorized_keys` 파일에 덧붙이면 EC2 인스턴스에 키 페어를 더 추가할 수 있다."**

즉 콘솔의 키 페어 목록은 **"AWS가 대신 보관해 주는 공개 키 카탈로그"**일 뿐 접근 통제 지점이 아닙니다. 삭제해도 실행 중인 200대의 `authorized_keys`는 그대로이고 AMI에 구워진 것도 그대로입니다. 진짜 회수를 하려면 200대에 접속해 파일을 고치거나 AMI를 다시 만들어 전부 교체해야 합니다. **키 페어에는 만료도, 순환도, 폐기 목록도 없습니다.**

### 올바른 구성 (1) — 그래도 키를 쓴다면, 자체 생성 후 임포트

> 📖 *AWS Security Cookbook* 6장: **"AWS는 AWS 밖에서 키 페어를 생성한 뒤 공개 키를 임포트하는 것도 허용한다. 이 레시피에서 우리는 로컬 머신에서 OpenSSL로 개인 키와 공개 키를 생성하고, 공개 키만 AWS에 업로드했다. 따라서 AWS는 우리의 개인 키를 볼 기회가 전혀 없었다."**

원서는 OpenSSL(`openssl genpkey -algorithm RSA ... rsa_keygen_bits:2048`)을 썼지만, 지금은 `ssh-keygen`으로 ED25519 키를 만드는 쪽이 낫습니다. EC2가 정식 지원합니다.

```bash
# 1) 로컬에서 키 생성 — 개인 키에 반드시 패스프레이즈를 건다
ssh-keygen -t ed25519 -f ~/.ssh/shopmini-break-glass -C "shopmini break-glass 2025-09"
chmod 400 ~/.ssh/shopmini-break-glass

# 2) 공개 키만 AWS에 임포트 (개인 키는 절대 올라가지 않는다)
#    주의: fileb://~/... 는 셸이 ~ 를 확장하지 않는다. $HOME 을 쓴다
aws ec2 import-key-pair \
  --key-name shopmini-break-glass-2025-09 \
  --public-key-material "fileb://$HOME/.ssh/shopmini-break-glass.pub" \
  --tag-specifications 'ResourceType=key-pair,Tags=[{Key=Project,Value=awssec-lab},{Key=Owner,Value=secops},{Key=ExpiresOn,Value=2025-12-31}]' \
  --profile awssec-lab

# 3) 지문 확인 — 로컬 키와 AWS에 등록된 키가 같은지 대조한다
ssh-keygen -lf ~/.ssh/shopmini-break-glass.pub
aws ec2 describe-key-pairs --key-names shopmini-break-glass-2025-09 \
  --query 'KeyPairs[0].[KeyName,KeyFingerprint,CreateTime]' --profile awssec-lab
```

AWS가 생성해 주는 키(`create-key-pair`)는 개인 키가 API 응답으로 한 번 흘러갑니다. CloudTrail 본문에는 남지 않지만 터미널 스크롤백·셸 히스토리·CI 로그에는 남을 수 있습니다. **개인 키가 네트워크를 타는 경로를 없애는 것**이 임포트 방식의 유일하고 충분한 이유입니다.

### 올바른 구성 (2) — 결론은 키를 없애는 것

세 접근 방식을 비교하면 답이 분명해집니다.

| 방식 | 자격 증명의 실체 | 회수 방법 | 감사 기록 | 22번 포트 |
|---|---|---|---|---|
| EC2 키 페어 | 인스턴스 디스크의 `authorized_keys` | **사실상 없음**(전 인스턴스 재작업) | 없음(OS 로그뿐) | 필요 |
| EC2 Instance Connect | IAM 권한 → 60초 유효 임시 공개 키 주입 | IAM 정책 수정 즉시 | CloudTrail에 `SendSSHPublicKey` | 필요(엔드포인트 쓰면 불필요) |
| SSM Session Manager | IAM 권한 + SSM 에이전트 | IAM 정책 수정 즉시 | CloudTrail + S3/CloudWatch 세션 로그 | **불필요** |

**EC2 Instance Connect**는 SSH를 유지하면서 키 관리만 IAM으로 옮기는 중간 단계입니다. `aws ec2-instance-connect send-ssh-public-key`로 일회용 공개 키를 60초간 주입하고 그 창 안에 SSH로 붙습니다. 영구 키가 디스크에 남지 않고, 누가 언제 접속했는지가 CloudTrail에 남습니다. **EC2 Instance Connect Endpoint**를 쓰면 퍼블릭 IP나 배스천 없이 프라이빗 서브넷에도 붙습니다.

최종 목적지는 21.6의 **Session Manager**입니다. 22번 포트를 열지 않고, 키가 존재하지 않으며, 세션 전체가 KMS로 암호화되어 기록됩니다. 그래서 이 책의 표준 구성은 **시작 템플릿에 `KeyName`을 넣지 않는 것**입니다. 키 없이 시작된 인스턴스는 `authorized_keys`가 비어 있습니다. 비상용 키 하나만 `ExpiresOn` 태그와 함께 별도 관리하고 정기 점검합니다.

```bash
# 전체 키 페어를 생성일·소유자와 함께 나열한다 — Owner 가 비었거나 오래된 것이 점검 대상
aws ec2 describe-key-pairs \
  --query 'KeyPairs[].[KeyName,KeyType,CreateTime,Tags[?Key==`Owner`]|[0].Value,Tags[?Key==`ExpiresOn`]|[0].Value]' \
  --output table --profile awssec-lab

# 시작 템플릿에 KeyName 이 박혀 있는지 확인 (있으면 제거 대상)
aws ec2 describe-launch-template-versions \
  --launch-template-name shopmini-app --versions '$Latest' \
  --query 'LaunchTemplateVersions[0].LaunchTemplateData.KeyName' --profile awssec-lab
```

## 22.3 IAM 역할 부착 🔴 🧪

8.2에서 인스턴스 프로파일을 만들고 붙이는 법을 이미 다뤘습니다. 이 절은 그 위에서 **운영 중에 생기는 문제들**만 다룹니다.

> 📖 *AWS Security Cookbook* 6장 「Creating and attaching an IAM role to an EC2 instance」: **"이 레시피에서 우리는 EC2 인스턴스에 S3 접근 권한을 부여했다. 이제 자격 증명을 구성하지 않고도 EC2 인스턴스에서 지원되는 S3 작업을 실행할 수 있다. 대안은 EC2 머신 안에 AWS 자격 증명을 구성해 두는 것인데, 누군가 그 머신에 침입하면 이 자격 증명이 노출된다."**

원서 실습은 `AmazonS3FullAccess`를 붙이지만 이 책은 8.2에서 최소 권한 인라인 정책으로 대체했습니다. 여기서는 그다음 이야기입니다.

### 🔴 반드시 이렇게 하라 (1) — 역할 교체는 인스턴스 중단 없이

권한을 좁히거나 역할을 나눌 때 인스턴스를 재시작할 필요가 없습니다. 연결을 **교체**하면 됩니다.

```bash
# 현재 연결 확인 — AssociationId 를 얻는다
aws ec2 describe-iam-instance-profile-associations \
  --filters "Name=instance-id,Values=i-0a1b2c3d4e5f6a7b8" \
  --query 'IamInstanceProfileAssociations[].[AssociationId,IamInstanceProfile.Arn,State]' \
  --output table --profile awssec-lab

# 무중단 교체 — 새 인스턴스 프로파일로 바꾼다
aws ec2 replace-iam-instance-profile-association \
  --association-id iip-assoc-0123456789abcdef0 \
  --iam-instance-profile Name=ShopMiniAppInstanceProfile-v2 \
  --profile awssec-lab
```

주의할 점이 둘입니다. 첫째, 교체 직후 IMDS가 새 자격 증명을 반환하기까지 **수 분의 지연**이 있을 수 있고 SDK는 캐시된 자격 증명을 만료 전까지 재사용합니다. 즉 권한을 **좁히는** 교체는 즉시 반영되지 않습니다. 침해 대응이라면 역할에 Deny 정책을 붙이거나 발급된 세션 자체를 무효화하는 편이 확실합니다.

둘째, 프로파일 대신 **역할 정책만 고치는** 방법은 반영이 즉시지만 같은 역할을 쓰는 모든 인스턴스에 영향을 줍니다. 선택은 그 역할의 공유 범위에 달렸습니다.

### 🔴 반드시 이렇게 하라 (2) — 한 인스턴스에 한 워크로드

**IAM 역할은 인스턴스 단위로 붙습니다. 프로세스 단위가 아닙니다.** 이것이 인스턴스 프로파일의 가장 큰 구조적 한계입니다. ShopMini 앱 인스턴스에 이런 것들이 함께 돌고 있다고 해 봅시다.

- 앱 프로세스: `shopmini-uploads` 버킷에 쓰기, `rds/shopmini` 시크릿 읽기
- 로그 수집 에이전트: CloudWatch Logs 쓰기
- 배치 잡: `shopmini-assets` 버킷 읽기
- 운영자가 임시로 실행한 스크립트

이 넷은 **모두 같은 역할의 모든 권한**을 갖습니다. IMDS는 인스턴스 내 모든 로컬 프로세스가 동등하게 접근할 수 있는 링크 로컬 주소이기 때문입니다. 앱에 원격 코드 실행 취약점이 하나 생기면 배치 잡의 권한까지 통째로 넘어갑니다.

해결은 세 방향입니다.

| 상황 | 대응 |
|---|---|
| 워크로드가 분리 가능 | **인스턴스를 나눈다.** 역할 경계 = 인스턴스 경계로 만든다 |
| 한 호스트에 여러 컨테이너 | ECS **태스크 역할**(24장)로 컨테이너마다 다른 역할. 호스트 역할은 최소로, 홉 제한 1 |
| 에이전트류(CloudWatch·SSM) | 앱 역할에 합치지 말고, 관리형 정책(`CloudWatchAgentServerPolicy`, `AmazonSSMManagedInstanceCore`)을 **역할에 함께 부착**하되 앱 권한과 리소스 범위를 분리해 기술 |

에이전트 권한을 프로세스 단위로 분리할 수 없다는 점은 인스턴스 프로파일의 본질적 제약입니다. EC2에서는 "역할 하나 = 그 인스턴스에서 돌아가는 모든 것의 최대 권한"이라고 읽고, 그 최대치가 감당 가능한지를 기준으로 설계해야 합니다.

### 🔴 반드시 이렇게 하라 (3) — 실제 사용량으로 권한을 좁힌다

역할은 넓게 만들어지고 좁혀지지 않습니다. 90일마다 다음을 돌립니다.

```bash
# 이 역할이 최근에 실제로 쓴 서비스만 보여 준다
JOB=$(aws iam generate-service-last-accessed-details \
        --arn arn:aws:iam::111122223333:role/ShopMiniAppRole \
        --query JobId --output text --profile awssec-lab)

aws iam get-service-last-accessed-details --job-id "$JOB" \
  --query 'ServicesLastAccessed[?TotalAuthenticatedEntities>`0`].[ServiceName,LastAuthenticated]' \
  --output table --profile awssec-lab
```

한 번도 쓰이지 않은 서비스가 정책에 있다면 지웁니다. CloudTrail 이력으로 정책 초안을 만드는 Access Analyzer 정책 생성은 7.6에서 다뤘습니다.

## 22.4 사용자 데이터(User Data) 🧪 ⚠️

### 원서의 실습을 8443으로

> 📖 *AWS Security Cookbook* 6장 「Using EC2 user data to launch an instance with a web server」: **"이 레시피에서 우리는 OS를 업데이트하고 간단한 Apache 웹 서버를 구성했다. OS를 최신으로 유지하는 것은 언제나 인스턴스 보안의 핵심이다."**

원서 스크립트는 80번 포트의 Apache 기본 페이지까지였습니다. ShopMini는 ALB에서 8443(HTTPS)으로 받으므로 이렇게 바뀝니다.

```bash
#!/bin/bash
set -euxo pipefail

dnf update -y
dnf install -y httpd mod_ssl awscli-2

# ALB → 앱 구간도 TLS. 인증서는 부팅 시 Parameter Store 에서 가져온다 (11장)
install -d -m 0700 /etc/pki/shopmini
aws ssm get-parameter --name /shopmini/prod/app/tls-cert --with-decryption \
  --query Parameter.Value --output text --region ap-northeast-2 \
  > /etc/pki/shopmini/server.crt
aws ssm get-parameter --name /shopmini/prod/app/tls-key --with-decryption \
  --query Parameter.Value --output text --region ap-northeast-2 \
  > /etc/pki/shopmini/server.key
chmod 400 /etc/pki/shopmini/server.key

sed -i 's/^Listen 443 https/Listen 8443 https/' /etc/httpd/conf.d/ssl.conf
sed -i 's#^SSLCertificateFile.*#SSLCertificateFile /etc/pki/shopmini/server.crt#' /etc/httpd/conf.d/ssl.conf
sed -i 's#^SSLCertificateKeyFile.*#SSLCertificateKeyFile /etc/pki/shopmini/server.key#' /etc/httpd/conf.d/ssl.conf

systemctl enable --now httpd
```

시크릿은 스크립트 안이 아니라 **Parameter Store에서 인스턴스 역할로 꺼내 옵니다.** 그 이유가 이 절의 핵심입니다.

### 사고 시나리오

한 팀이 시간에 쫓겨 User Data에 DB 비밀번호를 하드코딩했습니다. 프라이빗 서브넷에 있고 22번 포트도 닫혀 있으니 안전하다고 판단했습니다.

몇 달 뒤 앱의 이미지 프록시 기능에서 SSRF 취약점이 발견됩니다. 공격자는 앱에게 `http://169.254.169.254/latest/user-data`를 요청하게 만듭니다. 응답은 **부팅 스크립트 전문, 평문 그대로**입니다.

두 번째 경로도 있습니다. 읽기 전용 감사자에게 흔히 주는 `ec2:DescribeInstanceAttribute` 권한만 있으면 API로도 조회됩니다.

```bash
# 콘솔/CLI 경로 — 읽기 권한만으로 부팅 스크립트 전문이 나온다
aws ec2 describe-instance-attribute --instance-id i-0a1b2c3d4e5f6a7b8 \
  --attribute userData --query 'UserData.Value' --output text --profile awssec-lab | base64 -d
```

### 원인

**User Data는 시크릿 저장소가 아닙니다.** 저장 시 암호화되지 않고, IMDS 경로(`/latest/user-data`)에서 인스턴스 내 모든 프로세스가 읽으며, API로도 노출됩니다. IMDSv2 강제로 SSRF 난이도는 크게 올라가지만(8.3), API 경로는 그대로 남습니다.

### 올바른 구성

| 넣어도 되는 것 | 절대 넣지 말 것 |
|---|---|
| 패키지 설치·서비스 기동 명령 | 비밀번호, API 키, 토큰 |
| Parameter Store/Secrets Manager **참조 이름** | 개인 키(TLS·SSH), 인증서 개인 키 |
| 리전·환경 이름 같은 비민감 설정 | 내부 호스트 자격 증명, DB 접속 문자열의 비밀번호 부분 |
| 에이전트 등록 명령 | 조인 토큰·부트스트랩 시크릿 |

새 규칙을 만들기 전에 **지금 뭐가 들어 있는지**부터 확인합니다.

```bash
# 실행 중인 모든 인스턴스의 User Data 에서 시크릿 의심 패턴을 찾는다
for ID in $(aws ec2 describe-instances \
      --filters "Name=instance-state-name,Values=running" \
      --query 'Reservations[].Instances[].InstanceId' --output text --profile awssec-lab); do
  UD=$(aws ec2 describe-instance-attribute --instance-id "$ID" --attribute userData \
        --query 'UserData.Value' --output text --profile awssec-lab 2>/dev/null)
  [ "$UD" = "None" ] && continue
  if echo "$UD" | base64 -d 2>/dev/null | \
     grep -Eiq 'password|passwd|secret|api[_-]?key|token|AKIA[0-9A-Z]{16}|BEGIN [A-Z ]*PRIVATE KEY'; then
    echo "SUSPECT: $ID"
  fi
done
```

`SUSPECT` 인스턴스는 User Data를 고치는 것으로 끝나지 않습니다. **그 값은 이미 유출된 것으로 간주하고 시크릿을 순환**시켜야 합니다(11.5). User Data는 인스턴스를 **중지한 상태에서만** 수정할 수 있으므로, 실질적으로는 시작 템플릿을 고쳐 새 인스턴스로 교체하는 것이 답입니다.

### 운영 시 알아야 할 세 가지

**16KB 제한.** User Data는 base64 인코딩 **전** 원본 기준 16KB를 넘을 수 없습니다. S3에 스크립트를 두고 내려받아 실행하는 형태로 줄일 수 있지만, 스크립트가 16KB에 근접했다는 것 자체가 AMI로 옮길 때가 됐다는 신호입니다(22.5).

**기본은 부팅 1회 실행.** `cloud-init`은 최초 부팅에서만 User Data 스크립트를 실행합니다. 재부팅마다 실행하려면 `#cloud-boothook`을 쓰거나 `cloud-init` 설정을 바꿔야 합니다.

**디버깅은 로그 두 개.** 인스턴스가 헬스 체크를 통과하지 못할 때 볼 곳은 정해져 있습니다.

```bash
# Session Manager 로 접속해서 (21.6) — SSH 가 아니다
sudo cat /var/log/cloud-init-output.log   # 스크립트의 표준 출력/에러. 대부분 여기서 원인이 보인다
sudo cat /var/log/cloud-init.log          # cloud-init 자체의 단계별 진행 로그
sudo cloud-init status --long             # done / error / running
```

스크립트 첫 줄의 `set -euxo pipefail`은 실패 지점에서 즉시 멈추고 실행된 명령을 그대로 로그에 남깁니다. 이 한 줄이 없으면 "중간 한 줄이 실패했는데 스크립트는 성공한 것처럼 끝난" 상태가 만들어집니다.

## 22.5 골든 AMI 파이프라인 🧪

### 원서의 논지 — User Data 대신 AMI

> 📖 *AWS Security Cookbook* 10장 「Creating an AMI instead of using EC2 user data」: **"AMI로부터 만든 인스턴스는 EC2 User Data로 같은 구성을 정의한 인스턴스보다 부팅이 빠르다. 이는 AMI에는 패키지를 미리 설치해 둘 수 있는 반면, User Data로는 시작 시점에 설치해야 하기 때문이다."**

부팅 속도는 표면적인 이유입니다. 보안 관점의 진짜 이유는 셋입니다.

1. **시작 시점의 외부 의존이 사라진다.** User Data 방식은 매 부팅이 새로운 공급망 위험입니다. AMI 방식은 그 위험을 **이미지 빌드 시점 한 번**으로 압축하고 거기서 스캔합니다.
2. **인스턴스마다 다른 상태가 생기지 않는다.** 같은 스크립트라도 실행 시점에 따라 다른 패키지 버전이 설치되어 200대가 200가지 상태를 갖습니다. AMI는 비트 단위로 동일합니다.
3. **검증 지점이 생긴다.** 이미지에 취약점 스캔·CIS 벤치마크 검사를 돌리고, 통과한 것만 배포에 씁니다.

> 📖 *Practical Cloud Security* 2판 3장: **"VM 자체(흔히 '인스턴스'라 부르는 것)를 추적하는 것에 더해, 새 VM을 만들기 위해 복제되는 '이미지' 또는 템플릿도 추적해야 한다. 시작 직후 빠르게 패치된다 하더라도, 새 서버가 심각한 취약점을 가진 채로 올라오기를 원하지는 않을 것이다."**

### EC2 Image Builder로 파이프라인 만들기

원서의 실습은 인스턴스에 SSH로 붙어 수동 구성한 뒤 `Create Image`를 누르는 방식입니다. 사람 손이 들어간 이미지는 재현이 안 되고, 그 손이 무엇을 했는지 아무도 모릅니다. **EC2 Image Builder**는 이 과정을 코드로 만듭니다. 빌드 단계를 정의하는 컴포넌트부터 작성합니다.

```yaml
# component-shopmini-app.yaml
name: ShopMiniAppHardening
description: ShopMini 앱 계층 - 강화 및 런타임 설치
schemaVersion: 1.0
phases:
  - name: build
    steps:
      - name: UpdateAll
        action: ExecuteBash
        inputs:
          commands:
            - dnf update -y
      - name: InstallRuntime
        action: ExecuteBash
        inputs:
          commands:
            - dnf install -y httpd mod_ssl amazon-cloudwatch-agent
      - name: Harden
        action: ExecuteBash
        inputs:
          commands:
            # 원서가 말한 "필요 없는 것 끄기"
            - systemctl disable --now rpcbind avahi-daemon 2>/dev/null || true
            - systemctl mask ctrl-alt-del.target
            - sed -i 's/^#\?PermitRootLogin.*/PermitRootLogin no/' /etc/ssh/sshd_config
            - sed -i 's/^#\?PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config
  - name: validate
    steps:
      - name: CheckHttpd
        action: ExecuteBash
        inputs:
          commands:
            - systemctl is-enabled httpd
  - name: test
    steps:
      - name: NoLeftoverCredentials
        action: ExecuteBash
        inputs:
          commands:
            # 이 검사가 실패하면 AMI 가 만들어지지 않는다
            - test ! -s /root/.ssh/authorized_keys
            - test ! -s /home/ec2-user/.ssh/authorized_keys
            - test ! -e /root/.aws/credentials
            - test ! -e /home/ec2-user/.aws/credentials
            - test ! -s /root/.bash_history
            - test ! -s /home/ec2-user/.bash_history
```

```bash
# 1) 컴포넌트 등록
aws imagebuilder create-component \
  --name ShopMiniAppHardening --semantic-version 1.0.0 \
  --platform Linux --data file://component-shopmini-app.yaml \
  --profile awssec-lab

# 2) 레시피 — 부모 이미지 + 컴포넌트 조합. 여기서 EBS 암호화도 지정한다
aws imagebuilder create-image-recipe \
  --name shopmini-app-recipe --semantic-version 1.0.0 \
  --parent-image "arn:aws:imagebuilder:ap-northeast-2:aws:image/amazon-linux-2023-x86/x.x.x" \
  --components componentArn=arn:aws:imagebuilder:ap-northeast-2:111122223333:component/shopminiapphardening/1.0.0/1 \
  --block-device-mappings '[{"deviceName":"/dev/xvda","ebs":{"volumeSize":30,"volumeType":"gp3","encrypted":true,"kmsKeyId":"alias/shopmini/app","deleteOnTermination":true}}]' \
  --profile awssec-lab

# 3) 빌드 인프라 — 빌드용 인스턴스는 격리된 서브넷에서, 최소 권한 프로파일로
aws imagebuilder create-infrastructure-configuration \
  --name shopmini-build-infra \
  --instance-profile-name ImageBuilderInstanceProfile \
  --instance-types m6i.large \
  --subnet-id "$SN_BUILD" --security-group-ids "$SG_BUILD" \
  --terminate-instance-on-failure \
  --profile awssec-lab

# 4) 파이프라인 — 주 1회 자동 재빌드 + 이미지 테스트 필수
aws imagebuilder create-image-pipeline \
  --name shopmini-app-pipeline \
  --image-recipe-arn arn:aws:imagebuilder:ap-northeast-2:111122223333:image-recipe/shopmini-app-recipe/1.0.0 \
  --infrastructure-configuration-arn arn:aws:imagebuilder:ap-northeast-2:111122223333:infrastructure-configuration/shopmini-build-infra \
  --image-tests-configuration 'imageTestsEnabled=true,timeoutMinutes=90' \
  --schedule 'scheduleExpression=cron(0 3 ? * SUN *),pipelineExecutionStartCondition=EXPRESSION_MATCH_AND_DEPENDENCY_UPDATES_AVAILABLE' \
  --profile awssec-lab
```

`pipelineExecutionStartCondition`을 `EXPRESSION_MATCH_AND_DEPENDENCY_UPDATES_AVAILABLE`로 두면 **부모 이미지나 컴포넌트가 갱신됐을 때만** 빌드합니다. Amazon Linux 기본 AMI가 보안 패치로 갱신되면 새 골든 AMI가 자동으로 만들어집니다.

빌드 인스턴스에는 `EC2InstanceProfileForImageBuilder`와 `AmazonSSMManagedInstanceCore`가 필요합니다. 여기에 **운영 리소스 접근 권한을 절대 추가하지 마십시오.** 빌드 인스턴스는 인터넷에서 패키지를 받아 실행하는, 이 아키텍처에서 가장 신뢰도가 낮은 실행 환경입니다.

### ⚠️ AMI 위생 — 이미지에 남으면 안 되는 것

AMI는 디스크 전체의 스냅샷입니다. 만들 때 남아 있던 것이 그대로 복제됩니다.

| 남기면 안 되는 것 | 왜 |
|---|---|
| `authorized_keys`의 SSH 공개 키 | 22.2의 회수 불가 문제가 200배로 증폭 |
| `~/.aws/credentials`, 환경 변수 파일 | 정적 자격 증명이 모든 인스턴스에 복제 |
| 빌드 중 받은 임시 토큰, 저장소 인증 정보 | 이미지 공유 시 조직 밖으로 유출 |
| `/var/log/*`, 셸 히스토리(`.bash_history`) | 빌드 과정의 명령·경로·계정 정보 노출 |
| 호스트 SSH 키(`/etc/ssh/ssh_host_*`) | 모든 인스턴스가 같은 호스트 키 → 중간자 공격 탐지 불가 |
| `/etc/machine-id` | 인스턴스 식별자 충돌, 일부 에이전트 오작동 |

위 컴포넌트의 `test` 단계가 바로 이 검사입니다. **테스트를 통과하지 못하면 AMI가 등록되지 않습니다.** 사람의 체크리스트가 아니라 파이프라인의 게이트로 만드는 것이 요점입니다.

### 태깅과 수명 주기

> 📖 *AWS Security Cookbook* 10장: **"AMI는 기본적으로 우리 계정과 리전에 대해 프라이빗이다. 다른 AWS 계정이 사용하도록 AMI를 퍼블릭으로 만들거나 AWS 마켓플레이스를 통해 판매할 수 있다."** 그리고 **"신뢰하는 퍼블릭 AMI만 사용해야 한다."**

퍼블릭 공유 사고 대응은 16.7에서 다뤘습니다. 여기서는 수명 주기입니다.

```bash
# AMI 표준 태그 — 무엇으로부터 언제 만들어졌는지가 이미지에 붙어 있어야 한다
# (…0011 = 이번 달 골든 AMI, …0008 = 3개월 전 것)
aws ec2 create-tags --resources ami-0a1b2c3d4e5f60011 \
  --tags Key=Project,Value=awssec-lab Key=Tier,Value=app \
         Key=BaseImage,Value=al2023 Key=BuildDate,Value=2024-11-03 \
         Key=Approved,Value=true Key=CIS,Value=passed --profile awssec-lab

# 오래된 AMI 는 삭제 전에 먼저 '더 이상 쓰지 말 것'으로 표시한다
aws ec2 enable-image-deprecation --image-id ami-0a1b2c3d4e5f60008 \
  --deprecate-at 2025-01-01T00:00:00Z --profile awssec-lab

# 현재 쓰이는 AMI 는 실수로 등록 해제되지 않게 보호한다
aws ec2 enable-image-deregistration-protection \
  --image-id ami-0a1b2c3d4e5f60011 --profile awssec-lab

# 자기 계정 AMI 를 승인 태그와 함께 나열한다 — 마지막 열이 비면 승인되지 않은 이미지다
aws ec2 describe-images --owners self \
  --query "Images[].[ImageId,Name,CreationDate,Tags[?Key=='Approved']|[0].Value]" \
  --output table --profile awssec-lab
```

AMI를 등록 해제해도 **뒤에 있는 EBS 스냅샷은 남습니다.** 요금도 계속 나가고 그 스냅샷이 퍼블릭이면 데이터도 계속 노출되므로, AMI 정리는 항상 스냅샷 정리와 짝을 이뤄야 합니다(16.7). Config 규칙 `approved-amis-by-tag`를 배포하면 승인되지 않은 이미지로 시작된 인스턴스가 드러납니다.

### 셋 중 무엇을 쓸 것인가

| 방식 | 적합한 내용 | 부적합한 내용 |
|---|---|---|
| **AMI에 굽는다** | OS 패치, 런타임·에이전트, 강화 설정, 커널 파라미터 | 환경마다 다른 값, 자주 바뀌는 앱 코드 |
| **User Data** | 환경 식별, 설정 파일 렌더링, Parameter Store 조회 | 시크릿, 패키지 설치, 긴 스크립트 |
| **SSM State Manager** | 실행 중 인스턴스의 드리프트 교정, 에이전트 설정 강제 | 최초 부팅에 반드시 있어야 하는 것 |

## 22.6 패치 관리 🔴

### 원서가 말하는 두 가지 방향

> 📖 *Practical Cloud Security* 2판 5장: **"수정(fix)은 새로운 문제를 야기하거나 환경의 요구사항과 맞지 않을 경우 가용성을 해칠 수 있다. 가능하다면 제자리에서 고치려 하기보다, 그 취약점을 갖고 있지 않은 완전히 새로운 시스템을 롤아웃하는 편이 낫다."**

도구에 대해서는 이렇게 씁니다.

> 📖 *Practical Cloud Security* 2판 5장: **"AWS Systems Manager(SSM)는 인벤토리, 구성 관리, 패치 관리를 포함한 여러 영역을 다루는 보안 관리 도구다. State Manager 컴포넌트는 구성을 강제하는 데 쓸 수 있고, Patch Manager 컴포넌트는 패치를 설치하는 데 쓸 수 있다. 이 두 기능 모두 인스턴스에 설치된 SSM 에이전트가 실행한다."**

또한 OS 계층의 책임은 패치만이 아니라고 못 박습니다.

> 📖 *Practical Cloud Security* 2판 5장 「Operating System」: **"운영체제는 환경에서 필요하지 않은 여러 구성 요소를 함께 배포하는 경향이 있다. 이런 구성 요소를 실행 중인 인스턴스에 남겨 두면 버그나 오설정으로 인한 취약점의 큰 원천이 될 수 있으므로, 필요하지 않은 것은 무엇이든 끄는 것이 중요하다. 이를 흔히 강화(hardening)라고 부른다."**

두 인용은 모순이 아니라 **역할 분담**입니다. 정상 경로는 22.5의 AMI 재빌드 + 22.8의 인스턴스 교체입니다. Patch Manager는 그 위에서 두 역할을 맡습니다. **(1)** 재빌드 주기 사이에 터진 긴급 취약점을 즉시 막는 안전망, **(2)** "우리 인스턴스가 지금 패치되어 있는가"를 감사인에게 증명하는 규정 준수 보고.

### 🔴 반드시 이렇게 구성하라

**1단계 — 패치 베이스라인.** 무엇을 며칠 뒤에 승인할지 정의합니다.

```bash
aws ssm create-patch-baseline \
  --name "ShopMini-AL2023-Security" \
  --operating-system AMAZON_LINUX_2023 \
  --description "보안 분류 Critical/Important 만, 검증 5일 후 자동 승인" \
  --approval-rules '{
    "PatchRules": [{
      "PatchFilterGroup": {
        "PatchFilters": [
          {"Key": "CLASSIFICATION", "Values": ["Security"]},
          {"Key": "SEVERITY", "Values": ["Critical", "Important"]}
        ]
      },
      "ApproveAfterDays": 5,
      "ComplianceLevel": "CRITICAL",
      "EnableNonSecurity": false
    }]
  }' \
  --rejected-patches-action BLOCK \
  --profile awssec-lab
```

`ApproveAfterDays: 5`는 "출시 5일이 지난 패치는 자동 승인"이라는 뜻입니다. 0이면 검증 없이 즉시 반영되고, 너무 길면 알려진 취약점을 방치합니다. 개발 0일 / 운영 5~7일로 나눠 개발 환경이 먼저 맞아 보게 하는 것이 일반적입니다.

**2단계 — 패치 그룹.** 인스턴스의 `Patch Group` 태그(공백을 포함해 키 이름이 정확히 이것이어야 합니다)로 베이스라인을 연결합니다.

```bash
aws ssm register-patch-baseline-for-patch-group \
  --baseline-id pb-0123456789abcdef0 \
  --patch-group "shopmini-prod-app" --profile awssec-lab
```

**3단계 — 유지 관리 기간.** 아무 때나 재부팅되면 그것이 장애입니다.

```bash
# 매주 일요일 KST 02:00, 4시간 창, 종료 1시간 전부터 새 작업 시작 금지
MW=$(aws ssm create-maintenance-window \
  --name "shopmini-prod-patch" \
  --schedule "cron(0 2 ? * SUN *)" --schedule-timezone "Asia/Seoul" \
  --duration 4 --cutoff 1 --no-allow-unassociated-targets \
  --query WindowId --output text --profile awssec-lab)

TGT=$(aws ssm register-target-with-maintenance-window --window-id "$MW" \
  --resource-type INSTANCE \
  --targets "Key=tag:Patch Group,Values=shopmini-prod-app" \
  --query WindowTargetId --output text --profile awssec-lab)

# 한 번에 20% 씩. 10% 이상 실패하면 중단한다 — 전체 동시 재부팅을 막는 안전장치
aws ssm register-task-with-maintenance-window --window-id "$MW" \
  --task-type RUN_COMMAND --task-arn "AWS-RunPatchBaseline" \
  --targets "Key=WindowTargetIds,Values=$TGT" \
  --max-concurrency "20%" --max-errors "10%" \
  --service-role-arn arn:aws:iam::111122223333:role/ShopMiniMaintenanceWindowRole \
  --task-invocation-parameters '{
    "RunCommand": {
      "Parameters": {"Operation": ["Install"], "RebootOption": ["RebootIfNeeded"]},
      "OutputS3BucketName": "shopmini-ssm-logs"
    }
  }' --profile awssec-lab
```

**4단계 — 규정 준수 보고.** 패치를 돌리는 것과 패치됐음을 아는 것은 다른 일입니다.

```bash
# 패치 그룹 단위 요약 — 미설치 개수가 0이 아닌 인스턴스가 문제다
aws ssm describe-instance-patch-states-for-patch-group \
  --patch-group "shopmini-prod-app" \
  --query 'InstancePatchStates[].[InstanceId,MissingCount,FailedCount,CriticalNonCompliantCount,OperationEndTime]' \
  --output table --profile awssec-lab

# 계정 전체 미준수 목록
aws ssm list-resource-compliance-summaries \
  --filters "Key=ComplianceType,Values=Patch" "Key=Status,Values=NON_COMPLIANT" \
  --query 'ResourceComplianceSummaryItems[].[ResourceId,Status,NonCompliantSummary.SeveritySummary.CriticalCount]' \
  --output table --profile awssec-lab
```

### 안 하면 어떻게 되는가

- SSM 에이전트가 없거나 인스턴스 프로파일에 `AmazonSSMManagedInstanceCore`가 없는 인스턴스는 **Patch Manager의 시야에 아예 들어오지 않습니다.** 보고서상 100% 준수인데 실제로는 관리 대상 밖 인스턴스가 절반인 상황이 흔합니다. `ec2-instance-managed-by-systems-manager` Config 규칙이 패치 규칙보다 먼저 필요한 이유입니다.
- 프라이빗 서브넷 인스턴스는 SSM 엔드포인트에 도달할 경로가 있어야 합니다. NAT 게이트웨이 또는 `ssm`·`ssmmessages`·`ec2messages` 인터페이스 엔드포인트(20.2)입니다. 없으면 에이전트는 조용히 오프라인이 됩니다.
- 유지 관리 기간 없이 즉시 패치를 돌리면 전 인스턴스가 동시에 재부팅됩니다. `--max-concurrency`는 선택 사항이 아닙니다.

## 22.7 호스트 수준 보호

네트워크 통제(19장)와 접근 통제(21장)를 뚫고 들어온 뒤 인스턴스 안에서 벌어지는 일을 보는 계층입니다. 여기서는 **EC2 호스트에 무엇을 얹을 것인가**만 다루고, 취약점을 조직 차원에서 추적·처리하는 프로세스와 스캐너 선택은 25~26장이 맡습니다.

### 안티멀웨어와 EDR

> 📖 *Practical Cloud Security* 2판 7장: **"자산 관리 시스템에 있는 대상 범위 시스템 중 안티바이러스 소프트웨어를 실행하고 있지 않은 것이 있거나 멀웨어가 발견되면 반드시 알림을 받도록 하라."** 영리한 공격자는 탐지되지 않을 커스텀 멀웨어를 쓴다고 지적하면서도, 저자는 **"100% 효과적이지 않다는 이유로 도구를 거부하지 말라!"**고 덧붙입니다.

안티멀웨어와 EDR의 역할 차이는 비유로 정리됩니다.

> 📖 *Practical Cloud Security* 2판 7장: **"전통적인 안티멀웨어 소프트웨어가 주로 악성 활동을 차단하는 데 집중한다면, EDR(endpoint detection and response) 소프트웨어는 1차 방어선을 뚫고 들어온 위협을 팀이 조사하고 대응할 수 있게 하는 데 더 집중한다. 안티바이러스 소프트웨어가 물리적 건물의 방염 자재라면, EDR 소프트웨어는 화재 감지기와 스프링클러 시스템이다."**

EDR은 실행된 바이너리의 해시와 네트워크 연결 이력을 축적해 두었다가, 새 C2 서버나 멀웨어 시그니처가 알려졌을 때 **과거로 소급해** 감염 여부를 판정합니다. 시그니처 공개 시점에는 이미 감염된 지 몇 달이 지난 경우가 대부분이므로, 이 소급 조회가 결정적 차이입니다.

| 원서의 도구 범주 | AWS 서비스 | 무엇을 보는가 |
|---|---|---|
| 에이전트 기반 취약점 스캐너 | **Amazon Inspector** | 미설치 패치, 취약한 패키지 버전. SSM 에이전트를 통해 동작 |
| 안티멀웨어 | **GuardDuty Malware Protection for EC2** | EBS 스냅샷을 떠서 사이드카 방식으로 스캔(호스트에 부하 없음) |
| EDR | **GuardDuty Runtime Monitoring** | 인스턴스 내 프로세스·파일·네트워크 이벤트를 eBPF 에이전트로 수집 |
| 파일 무결성 모니터링 | AWS 네이티브 서비스 없음 | 서드파티 또는 OS 도구 |
| 통합 대시보드 | **Security Hub** | 위 결과의 집계·중복 제거·심각도 정규화 |

> 📖 *Practical Cloud Security* 2판 5장: **"Amazon Inspector는 Linux와 Windows 시스템의 미설치 패치와 잘못된 구성을 스캔할 수 있는 에이전트 기반 스캐너이며, 컨테이너 및 서버리스 스캐너이기도 하다."** 7장: **"Amazon GuardDuty는 당신의 AWS 계정이나 시스템에서 비정상적이거나 의심스러운 활동을 찾아낼 수 있다."**

### 파일 무결성 모니터링(FIM)

> 📖 *Practical Cloud Security* 2판 7장: **"OSSEC, Tripwire, AIDE, Netwrix Change Tracker, Fidelis CloudPassage Halo, Qualys를 비롯한 많은 제품과 서비스가 전통적인 또는 클라우드 기반의 파일 무결성 모니터링 솔루션을 제공한다."**

FIM은 `/etc`, `/usr/bin`, 웹 루트처럼 "변하면 안 되는" 경로의 해시를 주기적으로 비교해 변경을 알립니다. 22.8의 불변 인프라를 제대로 하면 FIM 알림은 거의 완벽한 신호가 됩니다. 불변 인스턴스에서 시스템 파일이 바뀌었다면 오탐이 아니라 침해이거나 규율 위반이기 때문입니다.

### 에이전트를 어디에 넣을 것인가

> 📖 *Practical Cloud Security* 2판 6장: **"클라우드 환경의 호스트 기반 IDS/IPS 솔루션도 전통적인 환경의 대응물과 유사하게 동작하지만, 이미 설치된 운영체제에 배포하는 것보다 가상 머신 이미지나 컨테이너 레이어에 미리 구워 넣는 편이 훨씬 쉬운 경우가 많다."** 그리고 **"각 시스템 이미지에 호스트 기반 IDS/IPS 에이전트를 구워 넣고, 에이전트들이 중앙 로깅 서버로 보고하도록 하는 것을 권장한다."**

이것이 골든 AMI가 보안 도구의 배포 수단이 되는 이유입니다. 새 에이전트를 200대에 밀어 넣는 대신 AMI에 넣고 인스턴스를 교체하면, 에이전트가 빠진 인스턴스가 생길 수 없습니다.

> 📖 *Practical Cloud Security* 2판 5장: **"에이전트 기반 시스템은 인바운드 연결을 전혀 허용하지 않고 아웃바운드 연결만 만들 수 있다."** 그리고 **"나는 보통 에이전트 기반 모델을 선호하지만 양쪽 모두에 좋은 논거가 있으며, 가장 중요한 것은 구성 관리와 취약점 관리를 실제로 수행하는 것이다."**

인바운드가 필요 없다는 점이 중요합니다. 에이전트리스 스캐너는 스캔 대상 전체의 특권 자격 증명을 갖고 인바운드로 접속하는데, 그 스캐너 자체가 매우 매력적인 공격 표적이 됩니다.

### CWPP / CNAPP

2판에서 새로 추가된 범주입니다.

> 📖 *Practical Cloud Security* 2판 5장 「Cloud Workload Protection Platforms」: **"클라우드 워크로드 보호 플랫폼(CWPP) 범주의 도구는 클라우드 제공자와 서드파티 양쪽이 제공한다. 이들은 보통 에이전트나 에이전트리스 방식으로, 또는 배포 파이프라인이나 서드파티 도구로부터 구성 및 취약점 관리 정보를 수집한다. 제공자들은 보통 접근 관리, 구성 관리, 그리고 개발·배포 단계 전반의 취약점 관리를 포함한 여러 보안 기능을 위한 '원스톱 대시보드'로 마케팅한다. (…) 때때로 클라우드 네이티브 애플리케이션 보호 플랫폼(CNAPP)이라고도 불린다."**

**"원스톱 대시보드로 마케팅한다"**는 표현 자체가 경계 신호입니다. 저자는 같은 장의 결론에서 못을 박습니다.

> 📖 *Practical Cloud Security* 2판 5장: **"모든 벤더는 자기 도구가 당신을 위해 모든 것을 해 줄 것이라고 설득하려 할 것이다. 그런 경우는 거의 없다. (…) 각 도구에 대해, 그것이 어떤 종류의 취약점을 찾아낼 것인지 명확히 설명할 수 있어야 한다."**

CWPP 도입 여부의 판단 기준은 하나입니다. **"이 도구가 어떤 취약점을 찾아 주는지 한 문장으로 말할 수 있는가."** 말할 수 없다면 대시보드를 하나 더 사는 것일 뿐입니다.

### 호스트 방화벽

> 📖 *Practical Cloud Security* 2판 6장: **"자체 호스트 방화벽을 운영하는 대신, 보안 그룹 규칙만 정의하면 가상 호스트를 위한 서비스로 구현된다."**

보안 그룹이 호스트 방화벽을 대체합니다. `firewalld`·`iptables`를 따로 관리하면 이중 관리가 되고 장애 원인 추적이 어려워집니다. 예외는 둘입니다. **(1)** 규제 요건이 호스트 수준 방화벽을 명시적으로 요구할 때, **(2)** 같은 인스턴스 안의 프로세스 간 통신을 제한해야 할 때(보안 그룹은 ENI 단위라 인스턴스 내부 트래픽에 관여하지 않습니다). 이 경우에도 규칙은 AMI에 구워 넣습니다.

## 22.8 불변 인프라로의 전환 🔴

### 목표: SSH 접속할 일이 없는 상태

22.1~22.7은 "인스턴스를 잘 관리하는 법"이었습니다. 마지막 절은 방향을 뒤집습니다. **가장 잘 관리되는 인스턴스는 아무도 손대지 않는 인스턴스입니다.**

업계에서는 이 전환을 **"애완동물(pets) vs 가축(cattle)"** 비유로 설명합니다. 애완동물은 이름이 있고 아프면 치료합니다 — `web-01`에 SSH로 들어가 설정을 고치는 운영입니다. 가축은 번호로 관리하고 아프면 교체합니다 — 인스턴스에 문제가 있으면 종료하고 새로 띄웁니다.

이것이 왜 **보안** 문제인지는 원서가 컨테이너를 설명하며 짚습니다.

> 📖 *Practical Cloud Security* 2판 3장: **"컨테이너는 불변(immutable)이다. 즉 시간이 지나도 변하지 않는다. (…) 컨테이너는 자기 코드를 스스로 업데이트하지 않고, 누구도 로그인해서 바꾸지 않는다."** **"실행 중인 컨테이너를 업데이트하는 대신, 옛 컨테이너는 파괴되고 업데이트된 코드로 새 컨테이너가 생성된다."** 그리고 **"네이티브한 불변 컨테이너는 일상적인 유지 관리를 위해 관리자가 로그인할 필요가 없어야 한다. 다만 트러블슈팅을 위해 가끔 긴급 접근을 얻을 수단은 아마 필요할 것이다. 컨테이너 로그인이 일반적으로 허용되지 않는다면, 컨테이너에 대한 접근 관리는 서버의 경우보다 위험이 작아진다."**

마지막 문장이 핵심입니다. **로그인이 존재하지 않으면 접근 관리라는 위험 범주 자체가 축소됩니다.** 이 성질은 컨테이너의 전유물이 아니며, EC2에 적용한 것이 불변 인프라입니다.

> 📖 *Practical Cloud Security* 2판 5장 결론: **"덧붙여, 클라우드와 함께 불변 인프라와 지속적 전달(continuous delivery)의 철학이 종종 채택되는데, 이는 변경으로 인한 장애 위험을 상당히 줄여 준다. 이는 운영 위험과 보안 위험 사이의 균형을 바꾼다. 보안 수정을 적용하는 것도 변경이고, 이제 변경을 더 안전하게 할 수 있으므로, 시스템을 다운시킬 위험 없이 보안 수정을 더 빨리 롤아웃할 수 있다."**

패치를 미루는 진짜 이유는 "귀찮아서"가 아니라 "깨질까 봐"입니다. 불변 인프라는 그 두려움의 근거를 제거합니다. 새 AMI로 몇 대만 띄워 보고, 문제가 있으면 옛 AMI로 되돌리면 되기 때문입니다.

### 🔴 반드시 이렇게 구성하라

**1. 변경은 오직 새 인스턴스로만 들어간다.**

```bash
# 시작 템플릿의 AMI 를 새 골든 AMI 로 올린다 (22.5 파이프라인이 만든 것)
aws ec2 create-launch-template-version \
  --launch-template-name shopmini-app --source-version '$Latest' \
  --version-description "golden AMI 2024-12, CVE-2024-xxxx 대응" \
  --launch-template-data '{"ImageId":"ami-0a1b2c3d4e5f60012"}' \
  --profile awssec-lab

aws ec2 modify-launch-template --launch-template-name shopmini-app \
  --default-version '$Latest' --profile awssec-lab

# Auto Scaling 그룹의 인스턴스를 순차 교체 — 이것이 유일한 배포 수단이다
aws autoscaling start-instance-refresh \
  --auto-scaling-group-name shopmini-app-asg \
  --preferences '{
    "MinHealthyPercentage": 90,
    "InstanceWarmup": 300,
    "CheckpointPercentages": [20, 50, 100],
    "CheckpointDelay": 600,
    "AutoRollback": true
  }' --profile awssec-lab
```

`CheckpointPercentages`로 20% → 50% → 100% 단계별 교체 사이에 10분을 기다리고, `AutoRollback`이 문제 발생 시 이전 시작 템플릿 버전으로 되돌립니다. **패치 배포가 코드 배포와 같은 파이프라인을 타게 되는 것**이 이 구성의 목적입니다.

**2. 인스턴스 최대 수명을 강제한다.** 오래 살아남은 인스턴스에는 드리프트가 쌓이고, 침해되면 공격자의 지속성 거점이 됩니다.

```bash
# 30일이 지난 인스턴스는 자동으로 교체된다 (초 단위)
aws autoscaling update-auto-scaling-group \
  --auto-scaling-group-name shopmini-app-asg \
  --max-instance-lifetime 2592000 --profile awssec-lab
```

**3. 드리프트를 탐지하고 교정한다.** 사람이 손댄 흔적은 반드시 남습니다.

```bash
# SSM State Manager — 원하는 상태를 정의하고 주기적으로 준수 여부를 기록한다
aws ssm create-association --name "AWS-RunPatchBaseline" \
  --association-name "shopmini-app-scan" \
  --targets "Key=tag:Patch Group,Values=shopmini-prod-app" \
  --parameters '{"Operation":["Scan"]}' \
  --schedule-expression "rate(1 day)" \
  --compliance-severity CRITICAL --profile awssec-lab

# 인벤토리 수집 — 이미지에 없던 패키지가 설치된 인스턴스를 찾을 근거가 된다
aws ssm create-association --name "AWS-GatherSoftwareInventory" \
  --targets "Key=tag:Project,Values=awssec-lab" \
  --schedule-expression "rate(12 hours)" --profile awssec-lab
```

**4. 접속 자체를 예외 상황으로 만든다.** Session Manager 세션 시작은 CloudTrail의 `StartSession` 이벤트로 남으므로, EventBridge 규칙으로 운영 계정의 세션 시작을 보안 채널에 즉시 알립니다. **알림이 울리는 것 자체가 비정상인 상태**를 만드는 것이 목표입니다.

### 성숙도 단계

한 번에 갈 수 없습니다. 지금 어디에 있는지부터 정합니다.

| 단계 | 상태 | 다음 한 걸음 |
|---|---|---|
| 0. 애완동물 | 이름 붙은 인스턴스에 SSH로 들어가 손으로 고침. 키 페어 공유 | Session Manager 도입, 22번 포트 폐쇄 (21.5) |
| 1. 자동화된 애완동물 | 구성 관리 도구로 실행 중 인스턴스를 고침 | 골든 AMI 파이프라인 구축 (22.5) |
| 2. 교체 가능 | AMI로 새로 띄울 수 있지만 여전히 접속해서 고침 | ASG + 인스턴스 새로 고침을 유일한 배포 경로로 (22.8) |
| 3. 불변 | 변경은 새 AMI로만. 접속은 조사 목적의 예외 | 최대 수명 강제, 세션 시작 알림, 드리프트 탐지 |
| 4. 가축 | 인스턴스 ID를 아무도 모름. 문제 인스턴스는 격리 후 교체 | 이 상태의 유지를 IaC로 강제 (28장) |

### 남는 문제 — 상태를 어디에 두는가

불변 인프라의 유일한 진짜 어려움은 "인스턴스가 언제든 사라져도 되게 만드는 것"입니다. 로컬 디스크의 로그, 세션 상태, 업로드된 파일이 인스턴스에 묶여 있으면 교체할 수 없습니다. 그래서 불변 인프라는 항상 상태 외부화와 짝을 이룹니다 — 로그는 CloudWatch Logs, 세션은 외부 저장소, 파일은 S3(`shopmini-uploads`)로. 설정 변경이 아니라 아키텍처 변경이며, 이 장에서 가장 오래 걸리는 항목입니다.

그리고 이 모든 구성이 **코드로 표현되고 검토되어야** 합니다. 시작 템플릿, ASG 정책, 패치 베이스라인, Image Builder 파이프라인이 콘솔에서 손으로 만들어졌다면 그 자체가 드리프트입니다. 28장에서 이 전체를 IaC로 옮깁니다.

## 🔴 필수 구성 체크리스트

- [ ] 앱 인스턴스에 **퍼블릭 IP가 없고**, 프라이빗앱 서브넷의 `MapPublicIpOnLaunch`가 `false`다
- [ ] 모든 인스턴스가 **시작 템플릿**을 통해 시작된다 (콘솔 직접 시작은 Config로 탐지)
- [ ] 시작 템플릿에 IMDSv2 강제(`HttpTokens=required`)와 **홉 제한 1**이 있다
- [ ] 운영 인스턴스에 **종료 방지**와 상세 모니터링이 켜져 있다
- [ ] 루트 볼륨이 **고객 관리형 KMS 키**로 암호화된다
- [ ] 시작 템플릿에 **`KeyName`이 없다** (키 없이 시작한다)
- [ ] 남아 있는 키 페어에 `Owner`·`ExpiresOn` 태그가 있고 만료 점검이 돈다
- [ ] 모든 인스턴스에 **인스턴스 프로파일이 붙어 있고**, 정적 자격 증명 파일이 없다
- [ ] 역할 권한을 90일마다 `get-service-last-accessed-details`로 재검토한다
- [ ] **User Data에 시크릿이 없다** — 전체 인스턴스를 실제로 스캔해 확인했다
- [ ] User Data 부팅 스크립트가 `set -euxo pipefail`로 시작한다
- [ ] 골든 AMI가 **파이프라인으로** 만들어지고, `test` 단계가 자격 증명·SSH 키 잔존을 검사한다
- [ ] AMI에 `Approved`·`BuildDate` 태그가 있고, 만료 AMI에 `enable-image-deprecation`이 적용된다
- [ ] 모든 인스턴스가 **SSM 관리형 인스턴스**다 (`ec2-instance-managed-by-systems-manager`)
- [ ] 패치 베이스라인 + `Patch Group` 태그 + 유지 관리 기간이 구성되어 있다
- [ ] 유지 관리 기간 작업에 `--max-concurrency`와 `--max-errors`가 설정되어 있다
- [ ] 패치 준수 보고를 **주기적으로 읽는 사람**이 있다 (보고서 생성만으로는 통제가 아니다)
- [ ] Inspector와 GuardDuty(Malware Protection·Runtime Monitoring)가 켜져 있고 Security Hub로 모인다
- [ ] 보안 에이전트가 **AMI에 포함**되어 있다 (실행 중 인스턴스에 밀어 넣지 않는다)
- [ ] ASG에 `max-instance-lifetime`이 설정되어 있다
- [ ] 배포가 **인스턴스 새로 고침**으로만 이뤄지고, `AutoRollback`이 켜져 있다
- [ ] 운영 인스턴스의 Session Manager **세션 시작이 알림으로 이어진다**

## ⚠️ 자주 하는 실수

| 실수 | 결과 | 올바른 구성 |
|---|---|---|
| 키 페어를 삭제하고 "회수됐다"고 판단 | 실행 중 인스턴스와 AMI의 `authorized_keys`는 그대로 → 유출 키가 계속 유효 | 키 없는 시작 + Session Manager. 유출 시 **인스턴스 교체**가 유일한 회수 |
| 개인 키를 CI 환경 변수·위키·채팅에 공유 | 회수 불가능한 자격 증명이 통제 밖으로 확산 | 임포트 방식으로 개인 키를 로컬에만 두거나, 애초에 키를 쓰지 않음 |
| User Data에 DB 비밀번호 하드코딩 | SSRF 한 번 또는 `DescribeInstanceAttribute` 권한만으로 평문 유출 | Parameter Store/Secrets Manager + 인스턴스 역할 (11장) |
| User Data를 고쳐서 시크릿을 지움 | 이미 노출된 값이 그대로 유효 | 시크릿을 **순환**시키고 인스턴스를 교체 |
| 인스턴스 프로파일에 `AmazonS3FullAccess` | 침해 시 계정의 모든 버킷이 노출 | 버킷·프리픽스·액션을 명시한 인라인 정책 (8.2) |
| 한 인스턴스에 앱·배치·에이전트를 함께 배치 | 앱 취약점 하나로 모든 권한이 함께 넘어감 | 인스턴스 분리, 또는 컨테이너 태스크 역할 (24장) |
| 부팅 실패를 SSH로 들어가 조사 | 관리 포트를 다시 열게 되고, 그 규칙이 남음 | `cloud-init-output.log`를 Session Manager로 확인 |
| 사람이 SSH로 구성한 인스턴스에서 AMI 생성 | 재현 불가, 자격 증명·로그·호스트 키가 이미지에 잔존 | Image Builder 컴포넌트로 코드화 + `test` 단계 게이트 |
| AMI만 등록 해제하고 스냅샷 방치 | 요금 누수 + 퍼블릭 스냅샷이면 데이터 계속 노출 | AMI 정리와 스냅샷 정리를 항상 함께 (16.7) |
| SSM 에이전트 없는 인스턴스가 섞여 있음 | 패치 준수율 100%인데 실제로는 절반이 미관리 | `ec2-instance-managed-by-systems-manager`를 패치 규칙보다 먼저 |
| 유지 관리 기간 없이 즉시 패치 | 전 인스턴스 동시 재부팅 → 서비스 중단 | 유지 관리 기간 + `--max-concurrency 20%` + `--max-errors 10%` |
| `ApproveAfterDays=0`을 운영에 적용 | 검증 안 된 패치가 바로 운영에 반영 | 개발 0일 / 운영 5~7일로 단계 분리 |
| 실행 중 인스턴스에 보안 에이전트를 밀어 넣음 | 반드시 빠지는 인스턴스가 생기고, 그것을 모름 | AMI에 구워 넣고 인스턴스를 교체 |
| CWPP 대시보드를 도입하고 통제로 간주 | 알림이 쌓이고 아무도 안 봄 | "어떤 취약점을 찾는가"를 도구별로 문장화. 후속 처리 담당자 지정 |
| 인스턴스에 로컬 상태(로그·세션·파일) 저장 | 교체할 수 없으므로 불변 인프라가 불가능 | 로그는 CloudWatch Logs, 파일은 S3, 세션은 외부 저장소 |
| 인스턴스를 몇 달~몇 년 그대로 유지 | 드리프트 누적 + 침해 시 공격자 지속성 거점 | `max-instance-lifetime` + 정기 인스턴스 새로 고침 |

## 다음 장 예고

22장은 인스턴스 **안쪽**을 다뤘습니다. 23장은 다시 밖으로 나가, 사용자의 브라우저에서 앱 인스턴스까지의 경로를 봅니다.

ACM으로 인증서를 발급하고 자동 갱신하는 법, ALB에서 TLS를 종료할 때와 백엔드까지 다시 암호화(8443)해야 할 때의 판단 기준, CloudFront 오리진을 ALB로 잠그는 법, WAF 규칙으로 애플리케이션 계층 공격을 막는 법을 다룹니다. 22.4의 부팅 스크립트가 Parameter Store에서 꺼내 오던 그 인증서를, 23장에서는 ACM이 대신 관리하게 만듭니다.
