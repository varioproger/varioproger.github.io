36장에서 만든 것은 **뼈대**입니다. 조직도 OU도 코어 계정도 제자리에 있지만, 그 OU가 무엇을 금지하는지는 비어 있습니다. 이 장은 그 빈칸을 코드로 채웁니다. 핵심 질문은 하나입니다 — **"조직에서 가장 권한이 큰 사람이 실수하거나 침해당해도, 절대 일어나서는 안 되는 일이 무엇인가?"** 그 목록이 곧 가드레일이며, 가드레일은 사람의 성실함이 아니라 **API 거부 응답**으로 작동합니다.

> 📖 *Practical Cloud Security* 2판 4장은 인가의 두 축을 최소 권한과 직무 분리로 정리하면서, 클라우드에서의 직무 분리를 이렇게 옮깁니다. **"일반적으로 이것은 어느 한 사람도 환경 전체의 보안을 완전히 무너뜨릴 수 없도록 만드는 것으로 번역된다. 예를 들어 시스템에 변경을 가할 수 있는 사람이 그 시스템의 로그를 변경할 수 있어서도, 그 로그를 검토할 책임을 져서도 안 된다."**

같은 문장이 1판 4장에도 있습니다. AWS에서 이를 **기술적으로 강제하는 단 하나의 수단**이 SCP입니다. 계정 관리자에게 `AdministratorAccess`를 주면서도 "CloudTrail만은 끌 수 없다"를 만들 수 있는 층은 여기뿐입니다.

## 37.1 🔴 서비스 제어 정책(SCP) 설계

### 대전제: SCP는 권한을 주지 않는다

7.2에서 이미 한 번 못을 박았지만, 이 장의 모든 것이 여기서 출발하므로 다시 확인합니다.

> 📖 *AWS Security Cookbook* 1장은 두 문장으로 정리합니다. **"우리는 SCP를 사용해 조직 내 계정들의 루트 계정, IAM 사용자, IAM 역할에 대해 AWS 서비스 액션을 제한할 수 있다."** 그리고 **"SCP는 접근을 거부만 할 수 있으며, 허용할 수는 없다."**

이어서 같은 장은 상한이 겹칠 때의 규칙을 명시합니다.

> 📖 *AWS Security Cookbook* 1장: **"권한 경계(IAM 기능)와 SCP가 모두 존재하는 경우, 권한 경계와 SCP와 아이덴티티 기반 정책이 모두 그 액션을 허용할 때에만 해당 액션이 허용된다."**

정리하면 이렇습니다.

| 질문 | 답 |
|---|---|
| SCP에 `Allow`를 쓰면 권한이 생기는가 | **아니오.** 계정 안에서 "허용될 자격이 있는 액션의 집합"을 좁히는 필터일 뿐 |
| SCP만 있고 IAM 정책이 없으면 | 아무것도 못 함 |
| IAM 정책은 허용, SCP는 미허용이면 | 거부 |
| SCP에 명시적 `Deny`가 있으면 | **무조건 거부** — 계정 관리자도, 루트 사용자도 뚫지 못함 |

🔴 **SCP를 "권한 부여 도구"로 쓰려는 시도는 전부 실패합니다.** 개발자에게 권한을 주는 것은 Identity Center 권한 집합(9장)의 일이고, SCP는 **"그 권한 집합이 아무리 넓어도 여기는 못 넘는다"** 를 정하는 천장입니다.

### `FullAWSAccess`와 교집합 구조

조직을 만들면 Root와 모든 OU·계정에 AWS 관리형 SCP인 **`FullAWSAccess`** 가 기본 부착됩니다. 내용은 `"Effect": "Allow", "Action": "*", "Resource": "*"` 한 문장입니다. 이것이 있어야 "SCP 층에서 허용된 집합"이 전체가 되고, 그 위에 우리가 붙이는 `Deny` 문장들이 구멍을 뚫습니다.

어떤 계정에 실제로 걸리는 SCP는 **Root → 상위 OU → 하위 OU → 계정**에 붙은 모든 SCP의 **교집합**입니다. 각 층에서 허용된 집합을 차례로 곱해 나가고, 어느 층에서든 `Deny`가 걸리면 아래에서 무엇을 해도 되살아나지 않습니다.

```
Root SCP            : FullAWSAccess + Deny(루트 사용자 액션, 조직 탈퇴)
  └ Workloads OU    : FullAWSAccess + Deny(미승인 리전, 비암호화 리소스)
      └ Prod OU     : FullAWSAccess + Deny(IAM 사용자 생성, 베이스라인 역할 변경)
          └ 111122223333 에서 실제 가능한 것 = 세 층의 교집합
```

⚠️ **`FullAWSAccess`를 떼는 순간 그 지점 아래 전부가 죽습니다.** 허용 목록 전략(뒤에 설명)에서만 의도적으로 떼며, 뗄 때는 대체 Allow 문장이 **먼저** 붙어 있어야 합니다.

### 허용 목록 vs 거부 목록

| 항목 | 거부 목록(Deny list) | 허용 목록(Allow list) |
|---|---|---|
| 구성 | `FullAWSAccess` 유지 + `Deny` 문장 추가 | `FullAWSAccess` 제거 + 필요한 서비스만 `Allow` |
| 기본 태도 | "명시적으로 금지한 것 외에는 가능" | "명시적으로 허용한 것 외에는 불가" |
| 신규 AWS 서비스 출시 시 | **자동으로 사용 가능** (통제 공백 발생) | 자동으로 차단 (요청·승인 후 추가) |
| 운영 부담 | 낮음 — 금지 목록만 관리 | 높음 — 서비스 추가 요청이 상시 발생 |
| 정책 크기 압박 | 낮음 | **높음** — 서비스가 늘수록 문서가 커짐 |
| 사고 위험 | 금지를 빠뜨림(과소 차단) | 필요한 것을 빠뜨림(**전 계정 마비**) |
| 적합한 곳 | 대부분의 조직, 특히 Workloads OU | 규제 환경, Sandbox OU, Suspended OU |

🔴 **대부분의 조직은 거부 목록으로 시작하십시오.** 허용 목록은 이론적으로 우월하지만(1.1의 "deny by default") 실무에서 무너집니다. AWS 서비스는 내부적으로 서로를 호출하므로 CloudFormation 하나를 허용해도 그것이 부르는 수십 개 네임스페이스를 나열해야 하고, 곧 정책 크기 한도에 부딪힙니다.

> 📖 *Practical Cloud Security* 2판 6장은 네트워크 문맥에서 같은 트레이드오프를 짚습니다. **"일반적으로 우리는 우스꽝스러워지지 않는 선에서 가능한 한 제한적이기를 원하므로, 실현 가능하다면 허용 목록을 쓰고자 한다."** 조직 전체 SCP에서는 그 **"우스꽝스러워지지 않는 선"** 이 거부 목록 쪽에 있습니다.

**절충안이 실무의 정답입니다.** Root와 Workloads OU에는 거부 목록, Sandbox·Suspended·규제 OU에는 허용 목록을 씁니다. 서비스 허용 목록이 꼭 필요하면 `Deny` + `NotAction`으로 표현해 `FullAWSAccess`를 떼지 않고 같은 효과를 냅니다.

### 한도와 설계 규칙

SCP에는 **정책 문서 크기 한도**와 **한 엔터티(Root·OU·계정)당 부착 개수 한도**가 있습니다. 둘 다 실제 조직에서 부딪히는 수준이니 정확한 값은 AWS 조직 할당량 문서에서 확인하고 설계 전에 예산을 잡으십시오(원서도 이 지점에서 서비스 한도 문서 링크를 안내합니다). 크기 압박을 줄이는 실무 규칙 넷입니다.

1. **주제별로 4~6개 묶음으로 쪼갠다** — "보안 서비스 보호", "리전·암호화", "아이덴티티", "로그·백업 보호".
2. **배포 산출물은 압축(minify)한다.** 크기 계산에 공백도 포함됩니다. 관리는 주석이 가능한 IaC 소스에서 합니다.
3. **와일드카드로 액션 나열을 줄인다**(`guardduty:Delete*`). 의도치 않은 액션이 잡히지 않는지 확인은 필수입니다.
4. **정책은 Git에 두고 파이프라인으로 배포한다.** 콘솔에서 손으로 고치는 조직은 "지금 실제로 걸린 규칙"을 아무도 모르게 됩니다(28.4).

> 💡 **원서 이후 변경 — 리소스 제어 정책(RCP)** — SCP가 **내 조직의 주체**를 제한한다면, RCP는 반대 방향으로 **내 조직의 리소스에 누가 접근할 수 있는지**를 조직 차원에서 제한합니다. 버킷 정책마다 `aws:PrincipalOrgID` 조건을 넣는 대신 한 번에 강제하는 용도입니다. 거부만 가능하고 기본 부착 정책은 `RCPFullAWSAccess`이며, 지원 서비스가 SCP보다 좁으니 도입 전 확인하십시오. 둘은 대체가 아니라 **직교 관계**입니다.

## 37.2 🔴 반드시 넣어야 할 SCP 10가지

아래 10개는 **어떤 조직이든 논쟁 없이 넣을 수 있는 최소 집합**입니다. 원서는 SCP 레시피에서 `cloudtrail:StopLogging` 거부 하나를 예시로 들며 "이 정책은 해당 OU 내의 누구든 제한한다"고 설명하는데, 이 장은 그 한 문장을 실무 집합으로 확장한 것입니다. **각 SCP에는 반드시 부작용이 있으므로** 모든 항목에 부작용과 예외 처리를 병기합니다.

### ① 루트 사용자 사용 차단

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyAllRootUserActions",
      "Effect": "Deny",
      "Action": "*",
      "Resource": "*",
      "Condition": {
        "StringLike": { "aws:PrincipalArn": "arn:aws:iam::*:root" }
      }
    }
  ]
}
```

**부작용** — 루트로만 가능한 소수의 작업(일부 결제 설정, 특정 지원 요청)이 막힙니다. **예외 처리** — 5.1대로 루트가 봉인되어 있으면 정상 운영에 영향이 없습니다. 루트가 꼭 필요한 날에는 계정을 Exceptions OU로 옮겼다 되돌리고 그 이동을 감사 흔적으로 씁니다. ⚠️ **관리 계정의 루트에는 걸리지 않습니다**(37.3).

### ② CloudTrail 중지·삭제 금지

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ProtectCloudTrail",
      "Effect": "Deny",
      "Action": [
        "cloudtrail:StopLogging",
        "cloudtrail:DeleteTrail",
        "cloudtrail:UpdateTrail",
        "cloudtrail:PutEventSelectors",
        "cloudtrail:DeleteEventDataStore",
        "cloudtrail:UpdateEventDataStore"
      ],
      "Resource": "*",
      "Condition": {
        "ArnNotLike": {
          "aws:PrincipalArn": "arn:aws:iam::*:role/stacksets-exec-*"
        }
      }
    }
  ]
}
```

**부작용** — 멤버 계정이 **자기 계정용 추가 트레일**을 관리하는 것도 막힙니다. 조직 트레일 하나로 통일한다는 29.2의 전제가 필요합니다. **예외 처리** — StackSets 실행 역할만 예외로 둡니다. ⚠️ 조직 트레일 자체는 관리 계정에 있어 이 SCP로 보호되지 않습니다(36.6).

### ③ 보안 서비스 비활성화 금지

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyDisablingSecurityServices",
      "Effect": "Deny",
      "Action": [
        "guardduty:DeleteDetector",
        "guardduty:UpdateDetector",
        "guardduty:DeleteMembers",
        "guardduty:StopMonitoringMembers",
        "guardduty:DisassociateFromAdministratorAccount",
        "securityhub:DisableSecurityHub",
        "securityhub:DeleteMembers",
        "securityhub:BatchDisableStandards",
        "securityhub:DisassociateFromAdministratorAccount",
        "config:DeleteConfigurationRecorder",
        "config:StopConfigurationRecorder",
        "config:DeleteDeliveryChannel",
        "config:DeleteConfigRule",
        "config:DeleteConformancePack",
        "config:DeleteRetentionConfiguration",
        "macie2:DisableMacie",
        "access-analyzer:DeleteAnalyzer",
        "inspector2:Disable",
        "detective:DeleteGraph"
      ],
      "Resource": "*",
      "Condition": {
        "ArnNotLike": {
          "aws:PrincipalArn": [
            "arn:aws:iam::*:role/stacksets-exec-*",
            "arn:aws:iam::444455556666:role/SecurityToolingAdmin"
          ]
        }
      }
    }
  ]
}
```

**부작용** — `config:DeleteConfigRule`을 막으면 계정 팀이 **자기 계정에 추가한 규칙**도 못 지웁니다. 로컬 규칙을 허용하려면 이 액션만 빼십시오. **예외 처리** — 위임 관리자 계정(`444455556666`)의 보안팀 역할과 베이스라인 배포 역할을 제외합니다. ⚠️ 조직 자동 활성화(31.2)를 쓰면 이 SCP는 **2차 방어선**입니다.

### ④ 미승인 리전 차단

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyUnapprovedRegions",
      "Effect": "Deny",
      "NotAction": [
        "iam:*",
        "sts:*",
        "organizations:*",
        "account:*",
        "cloudfront:*",
        "route53:*",
        "route53domains:*",
        "waf:*",
        "wafv2:*",
        "shield:*",
        "support:*",
        "budgets:*",
        "ce:*",
        "cur:*",
        "health:*",
        "trustedadvisor:*",
        "artifact:*",
        "networkmanager:*"
      ],
      "Resource": "*",
      "Condition": {
        "StringNotEquals": {
          "aws:RequestedRegion": ["ap-northeast-2", "us-east-1"]
        },
        "ArnNotLike": {
          "aws:PrincipalArn": "arn:aws:iam::*:role/aws-service-role/*"
        }
      }
    }
  ]
}
```

**부작용** — 이 장에서 **가장 자주 사고를 내는 SCP**입니다. `NotAction`에서 글로벌 서비스를 빠뜨리면 IAM 역할 생성, CloudFront 배포, Route 53 변경이 전부 실패합니다(5.5, 37.3). **예외 처리** — `us-east-1`은 반드시 남기고(결제 지표·루트 사인인·글로벌 범위 API), 서비스 연결 역할을 제외해 AWS 내부 호출이 깨지지 않게 합니다. ⚠️ 옵트인 리전은 계정 수준 **비활성화**가 더 강한 통제입니다(5.5).

### ⑤ 비암호화 리소스 생성 차단

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyUnencryptedEbs",
      "Effect": "Deny",
      "Action": ["ec2:CreateVolume", "ec2:RunInstances"],
      "Resource": "arn:aws:ec2:*:*:volume/*",
      "Condition": { "Bool": { "ec2:Encrypted": "false" } }
    },
    {
      "Sid": "DenyEbsWhenEncryptionNotSpecified",
      "Effect": "Deny",
      "Action": ["ec2:CreateVolume", "ec2:RunInstances"],
      "Resource": "arn:aws:ec2:*:*:volume/*",
      "Condition": { "Null": { "ec2:Encrypted": "true" } }
    },
    {
      "Sid": "DenyS3PutWithWrongSse",
      "Effect": "Deny",
      "Action": "s3:PutObject",
      "Resource": "*",
      "Condition": {
        "Null": { "s3:x-amz-server-side-encryption": "false" },
        "StringNotEquals": { "s3:x-amz-server-side-encryption": "aws:kms" }
      }
    }
  ]
}
```

**부작용과 그 이유** — 두 번째 문장이 핵심입니다. `Bool: false`만 쓰면 **`Encrypted` 파라미터가 요청에 아예 없을 때** 조건이 성립하지 않아 통과합니다(37.3의 네 번째 함정). `Null: true`가 그 미지정 요청까지 막습니다. S3는 반대 방향입니다 — `StringNotEquals`만 쓰면 헤더를 생략한 정상 업로드까지 막히므로 `Null: false`를 함께 걸어 "헤더를 썼다면 반드시 `aws:kms`"로 좁혔습니다. **예외 처리** — 암호화 파라미터를 명시하지 않는 배포 자동화가 있으면 IaC를 먼저 고칩니다.

> ⚠️ **RDS 저장 암호화는 이 SCP에 넣지 않았습니다.** **모든 생성 API가 자기 파라미터를 조건 키로 노출하지는 않습니다.** 지원하지 않는 액션에 조건을 걸면 정책은 **문법적으로 유효한 채로 아무것도 막지 않습니다**(37.3 함정 4). 그런 정책이 가장 위험합니다 — 콘솔에 "적용됨"으로 보이고 39.2의 가드레일 적용률에도 1건으로 잡히지만 실제로는 구멍입니다. **조건을 걸기 전에 그 액션이 그 조건 키를 지원하는지 확인하고, 확인되지 않으면 SCP가 아니라 다른 층에 맡기십시오.** RDS 암호화는 Config 규칙 `RDS_STORAGE_ENCRYPTED`(37.7)로 탐지하고 파이프라인 게이트(28.3)로 예방합니다 — **예방으로 못 막으면 탐지로 덮는다**(37.4).

> 💡 **원서 이후 변경** — S3는 2023년부터 모든 신규 객체에 SSE-S3를 **기본 적용**하고, EBS도 리전별 계정 설정으로 **기본 암호화**를 켤 수 있습니다. 그래서 이 SCP의 실질 목적은 "암호화 여부"보다 **"고객 관리 KMS 키를 쓰게 만드는 것"**(13장)에 가깝습니다.

## 37.3 ⚠️ SCP의 함정

### 사고 시나리오

ShopMini 보안팀은 금요일 오후 리전 제한 SCP를 만들었습니다 — `Deny`, `aws:RequestedRegion`이 `ap-northeast-2`가 아닌 모든 요청, `Action: "*"`. 서울 리전만 쓰니 문제될 것이 없어 보였고, 검토도 거쳤습니다. Root에 붙였습니다.

3분 뒤 전 계정에서 장애가 시작됐습니다. Auto Scaling이 인스턴스를 띄우지 못했고(서비스 연결 역할의 IAM 호출 실패), CloudFront 배포 업데이트가 거부됐고, Identity Center 로그인이 깨졌고, 파이프라인의 `sts:AssumeRole`이 전부 실패했습니다. SCP를 떼려고 관리 계정에 들어가려는데 — 그 로그인 경로도 Identity Center였습니다.

**원인은 다섯 가지가 겹친 것입니다.**

### 함정 1 — 관리 계정에는 적용되지 않는다

SCP는 조직의 **멤버 계정**에만 적용됩니다. 관리 계정(`123456789012`)의 어떤 주체에도 — 루트 사용자든 IAM 역할이든 — 걸리지 않습니다.

버그가 아니라 **설계**입니다. 관리 계정이 스스로를 잠글 수 있다면 잘못된 SCP를 되돌릴 곳이 없어집니다. 동시에 36.6의 결론이 다시 못 박힙니다 — **관리 계정은 유일하게 가드레일이 없는 계정입니다.** 여기에 워크로드나 개발자 접근이 있으면 이 장의 10개 SCP가 전부 무효이고, 앞서 인용한 직무 분리 원칙도 성립하지 않습니다. **통제 수단은 ① 접근 주체를 2인 이하로 줄이는 것과 ② 모든 행위에 알람을 거는 것** 둘뿐입니다.

### 함정 2 — 서비스 연결 역할(SLR)까지 막혀 서비스가 고장 난다

Auto Scaling, ELB, RDS, GuardDuty 등 상당수의 AWS 서비스는 계정 안의 **서비스 연결 역할**(`arn:aws:iam::계정:role/aws-service-role/...`)을 assume해 동작합니다. SLR도 IAM 주체이므로 **SCP가 그대로 적용됩니다.**

증상이 고약한 이유는 **실패가 사용자에게 직접 보이지 않기** 때문입니다. Auto Scaling은 조용히 확장에 실패하고, 30분 뒤 트래픽이 몰릴 때 장애로 드러납니다. 대응은 둘입니다.

```json
{
  "Condition": {
    "ArnNotLike": {
      "aws:PrincipalArn": "arn:aws:iam::*:role/aws-service-role/*"
    }
  }
}
```

또는 AWS 서비스가 **서비스 주체로 직접** 호출하는 경우를 제외하려면 `aws:PrincipalIsAWSService`를 씁니다.

```json
{
  "Condition": {
    "BoolIfExists": { "aws:PrincipalIsAWSService": "false" }
  }
}
```

(두 블록은 `Statement` 안에 넣을 조각입니다. 바깥의 `Effect`·`Action`·`Resource`는 생략했습니다.)

⚠️ 두 예외는 **바이패스 경로이기도 합니다.** SLR을 만들 수 있는 사람은 이 예외를 악용할 여지가 있으므로, `iam:CreateServiceLinkedRole`을 별도로 통제하거나 최소한 30장 알람 대상에 넣으십시오.

### 함정 3 — `aws:RequestedRegion` Deny가 글로벌 엔드포인트를 막는다

IAM, STS, Organizations, CloudFront, Route 53, WAF(글로벌), Shield, Support, Billing 계열은 **글로벌 서비스**이며 API 엔드포인트가 대체로 `us-east-1`입니다. 리전 Deny에서 이들을 제외하지 않으면 `aws:RequestedRegion`이 `us-east-1`로 평가되어 **전부 거부**됩니다.

그래서 37.2 ④의 `NotAction` 목록이 필요합니다. 목록을 짤 때 규칙은 하나입니다 — **"리전 개념이 없는 서비스는 전부 뺀다."** 뺀 서비스에 대한 통제는 리전이 아니라 다른 조건(액션·리소스·태그)으로 걸어야 합니다.

### 함정 4 — 조건 키를 지원하지 않는 액션에 조건을 걸면 무력화된다

가장 조용하고 가장 위험한 함정입니다. **요청 컨텍스트에 조건 키가 없을 때 조건이 어떻게 평가되는지**가 연산자에 따라 정반대입니다.

| 상황 | 예 | 키가 없을 때 | 결과 |
|---|---|---|---|
| `Deny` + 긍정 연산자 | `Bool: {"ec2:Encrypted": "false"}` | 조건 **미성립** | **차단 안 됨** — 통제에 구멍 |
| `Deny` + 부정 연산자 | `StringNotEquals: {"aws:RequestedRegion": "..."}` | 조건 **성립** | **과잉 차단** — 정상 요청까지 막음 |
| `Null` 연산자 | `Null: {"ec2:Encrypted": "true"}` | 키 부재를 **직접 검사** | 의도대로 |
| `...IfExists` 접미사 | `BoolIfExists` | 키 없으면 **성립** | 의도적으로 과잉 차단 방향 |

🔴 **모든 조건부 Deny를 쓰기 전에 이 표로 자문하십시오.** "이 액션이 이 조건 키를 지원하지 않으면, 내 정책은 과소 차단인가 과잉 차단인가?" 37.2 ⑤에서 EBS에는 `Null: true`를 더하고 S3에는 `Null: false`를 더한 이유가 정확히 이것입니다. 방향이 반대여서 처방도 반대입니다.

### 함정 5 — 잘못 적용하면 전 계정이 마비된다

앞의 네 함정이 겹치면 시나리오처럼 됩니다. Root에 붙인 SCP는 **관리 계정을 제외한 모든 계정**에 즉시, 예고 없이, 롤백 버튼 없이 적용됩니다.

### 🔴 단계적 적용 절차

SCP는 **배포 대상이 조직 전체인 코드**입니다. 코드 배포에 스테이징이 있듯 SCP에도 있어야 합니다.

**0단계 — 영향 사전 분석.** 붙이기 전에 "지난 90일 동안 이 SCP에 걸렸을 요청이 몇 건이고 누가 냈는지"를 29.6의 Athena 테이블에 묻습니다.

```sql
-- 지난 90일간 승인 리전 밖에서 발생한 성공 API 호출 (④번 SCP의 영향 예측)
SELECT useridentity.arn AS principal,
       awsregion,
       eventsource,
       count(*) AS calls
FROM cloudtrail_logs
WHERE awsregion NOT IN ('ap-northeast-2', 'us-east-1')
  AND errorcode IS NULL
  AND from_iso8601_timestamp(eventtime) > current_timestamp - interval '90' day
GROUP BY 1, 2, 3
ORDER BY calls DESC
LIMIT 100;
```

여기 나온 주체 목록이 **그대로 예외 처리 목록의 후보**입니다. 0건이면 안심하고, 수천 건이면 SCP가 아니라 워크로드를 먼저 고쳐야 합니다.

**1~4단계 — 확산.**

| 단계 | 대상 | 관찰 기간 | 통과 기준 |
|---|---|---|---|
| 1 | **PolicyStaging OU**(36.4) 또는 Sandbox OU | 1~3일 | 의도한 액션만 `AccessDenied`, 의도하지 않은 실패 0건 |
| 2 | 개발 OU(NonProd) | 1주 | 파이프라인 전 단계 통과, 개발팀 이슈 접수 0건 |
| 3 | 운영 OU 중 계정 1개(카나리) | 1주 | 배포·오토스케일링·백업·모니터링 정상 |
| 4 | 전체 OU / Root | — | 롤백 절차 문서화 후 적용 |

**각 단계의 관찰 방법.** CloudTrail의 `errorCode = AccessDenied`이면서 `errorMessage`에 서비스 제어 정책으로 인한 거부임이 표시되는 이벤트를 EventBridge로 잡아 SNS로 보내고 30장의 지표로 만드십시오. **적용 후 이 알람이 예상보다 많이 울리면 즉시 롤백입니다.**

**롤백 절차를 미리 써 두십시오.** ① 정책 분리(`detach-policy`)가 1차, ② 정책 내용 되돌리기가 2차입니다. 두 작업 모두 관리 계정에서만 가능하므로, **관리 계정 접근 경로가 Identity Center 하나뿐이면 안 됩니다** — 36.6의 브레이크 글래스 IAM 경로가 이 순간을 위해 존재합니다.

```bash
# [관리 계정 123456789012] 긴급 롤백
aws organizations detach-policy \
  --policy-id p-examplescp1 \
  --target-id ou-abcd-11111111 \
  --profile awssec-lab
```

## 37.4 예방(Preventive) vs 탐지(Detective) vs 대응(Responsive) 가드레일

### 3분류

가드레일은 SCP만이 아닙니다. **같은 요구사항도 어느 층에 놓느냐에 따라 비용과 확실성이 달라집니다.**

| 분류 | 하는 일 | AWS 수단 | 언제 작동 | 강점 | 약점 |
|---|---|---|---|---|---|
| **예방(Preventive)** | 잘못된 상태가 **생기지 못하게** | SCP·RCP, 권한 경계, Config **프로액티브** 규칙, CloudFormation Hooks, 파이프라인 게이트(28.3) | 요청 시점 / 배포 전 | 노출 창 = 0 | 커버리지가 좁음, 잘못 만들면 서비스 중단 |
| **탐지(Detective)** | 이미 생긴 것을 **찾아냄** | Config 규칙·적합성 팩, Security Hub(31.5), GuardDuty(31.1), Access Analyzer(7.7), CSPM(26.6) | 생성 후 수 분~수 시간 | 커버리지가 넓음, 안전함 | 노출 창이 존재 |
| **대응(Responsive)** | 찾은 것을 **되돌림** | Config 자동 교정(35.3), EventBridge+Lambda(35.2), Security Hub 사용자 지정 작업(35.4) | 탐지 후 수 초~수 분 | 노출 창을 분 단위로 압축 | 오작동 시 정상 리소스 파괴(35.5) |

### 어디에 놓을 것인가 — 결정 기준

같은 요구사항을 세 층 모두에 놓을 필요는 없습니다. 다음 네 질문으로 배치를 결정하십시오.

1. **잘못된 상태가 단 한 순간이라도 존재하면 안 되는가?** (예: 퍼블릭 S3 버킷, 비암호화 백업) → **예방 필수.** 탐지·대응은 보조.
2. **예방으로 막으면 정상 업무가 깨질 가능성이 있는가?** → 먼저 **탐지로 3개월 관찰**하고 위반이 0에 수렴하면 예방으로 승격합니다. 이것이 SCP를 안전하게 늘리는 정석 경로입니다.
3. **위반의 원인이 사람인가 코드인가?** 코드면 28.3의 파이프라인 게이트가 가장 싸고, 사람이면 SCP만이 답입니다.
4. **되돌리는 조치가 파괴적인가?** 파괴적이면(리소스 삭제·인스턴스 종료) 자동 대응을 걸지 말고 티켓 생성까지만 자동화합니다(35.1).

### 28.3의 4층과의 정합

28.3에서 게이트를 4층으로 나눴습니다 — 로컬 훅 / PR / 파이프라인 / **계정**. 위 3분류를 그 위에 겹치면 그림이 완성됩니다.

| 28.3의 층 | 3분류 | 이 장에서의 위치 |
|---|---|---|
| 1~3층(로컬·PR·파이프라인) | 예방 | 빠르고 친절한 피드백. **우회 가능** |
| 4층(계정) | 예방 | **SCP·RCP·프로액티브 규칙 — 우회 불가.** 37.2 |
| — | 탐지 | Config 적합성 팩(37.7), Security Hub(31.5) |
| — | 대응 | 자동 교정(35.3) |

🔴 **"파이프라인에서 막고 있으니 괜찮다"는 틀린 문장입니다.** 파이프라인 밖에서 API를 직접 호출하면 1~3층은 전부 무력화됩니다. 4층이 최종 방어선입니다.

## 37.5 AWS Control Tower 🧪

> 💡 **원서 범위 밖 보강** — Control Tower는 *AWS Security Cookbook* 10장의 "추가 서비스" 목록에 **한 문단만** 등장합니다. 아래 인용이 원서가 말하는 전부이며, 구성 요소·컨트롤 분류·계정 팩토리·드리프트는 AWS 문서와 실무 기준으로 보강한 것입니다.

> 📖 *AWS Security Cookbook* 10장: **"AWS Control Tower는 보안과 컴플라이언스 모범 사례에 기반해 멀티 계정 AWS 환경을 구성하고 통치하도록 돕는다. 최종 사용자는 중앙에서 수립된 전사 컴플라이언스 정책을 따라 새 계정을 프로비저닝할 수 있고, 클라우드 관리자는 랜딩 존 전체를 조망할 수 있다. 랜딩 존은 컴플라이언스를 지켜야 하는 우리의 모든 OU, 계정, 사용자, 그 밖의 리소스를 담는 컨테이너다. 랜딩 존은 조직의 비멤버 계정에 있어야 한다."**

마지막 문장이 중요합니다 — **랜딩 존은 조직에 아직 속하지 않은 계정에서 시작해야 한다.** 기존 조직 위에 얹을 수도 있지만 제약이 따릅니다(아래).

### 랜딩 존 구성 요소

Control Tower가 "설정"하는 것은 결국 우리가 36장에서 손으로 만든 것들입니다.

| 구성 요소 | 내용 | 이 책의 해당 절 |
|---|---|---|
| AWS Organizations | 조직, Security OU, Sandbox OU | 36.2, 36.4 |
| 로그 아카이브 계정 | 조직 CloudTrail·Config 로그 집중 버킷 | 36.5, 29.2 |
| 감사(Audit) 계정 | 보안 알림, 크로스 계정 감사 역할 | 36.5(보안 도구 계정) |
| IAM Identity Center | 권한 집합·디렉터리 | 9장 |
| 조직 CloudTrail | 전 계정·전 리전 트레일 | 29.2 |
| AWS Config | 관리 대상 리전 전체 레코더 + 집계자 | 29.8 |
| 컨트롤(가드레일) | SCP(예방) + Config 규칙(탐지) + CloudFormation Hooks(프로액티브) | 37.2, 37.7 |
| Account Factory | 표준화된 계정 프로비저닝 | 37.9 |
| 드리프트 감지 | 랜딩 존이 기준선에서 벗어났는지 감시 | 28.4 |

### 컨트롤 3분류

Control Tower의 컨트롤은 **강제 수준**으로 세 가지입니다.

| 분류 | 성격 | 예 | 해제 가능 여부 |
|---|---|---|---|
| **필수(Mandatory)** | 랜딩 존 설치와 함께 자동 적용 | 로그 아카이브 버킷 삭제 금지, 로그 아카이브 버킷 정책 변경 금지, CloudTrail 구성 변경 금지 | **불가** |
| **강력 권장(Strongly recommended)** | 모범 사례. 선택 적용이지만 사실상 필수 | EBS 볼륨 암호화 미적용 탐지, 루트 사용자 MFA 미설정 탐지, S3 퍼블릭 읽기 금지 | 가능 |
| **선택(Elective)** | 조직 정책에 따라 | S3 버킷 버전 관리 삭제 금지, 특정 리전 사용 제한 | 가능 |

동작 방식으로 다시 나누면 **예방(SCP 기반)·탐지(Config 규칙 기반)·프로액티브(CloudFormation Hooks 기반)** 이며, 이는 37.4의 3분류와 정확히 대응합니다.

```bash
# [관리 계정 123456789012] 사용 가능한 컨트롤 목록 조회
aws controlcatalog list-controls --profile awssec-lab

# OU에 컨트롤 활성화 (컨트롤 식별자는 위 명령의 결과에서 확인)
aws controltower enable-control \
  --control-identifier "arn:aws:controltower:ap-northeast-2::control/AWS-GR_ENCRYPTED_VOLUMES" \
  --target-identifier "arn:aws:organizations::123456789012:ou/o-exampleorgid/ou-abcd-11111111" \
  --profile awssec-lab

# 현재 OU에 걸린 컨트롤 확인
aws controltower list-enabled-controls \
  --target-identifier "arn:aws:organizations::123456789012:ou/o-exampleorgid/ou-abcd-11111111" \
  --profile awssec-lab
```

### 계정 팩토리(Account Factory)

계정 팩토리는 Service Catalog 제품으로 노출되는 **계정 프로비저닝 창구**입니다. 요청자가 계정 이름·이메일·OU를 입력하면 계정 생성 → OU 배치 → 컨트롤 적용 → Identity Center 접근 부여가 한 번에 진행됩니다. **Account Factory Customization**을 붙이면 생성 직후 지정한 CloudFormation 청사진이 자동 배포됩니다 — 37.9의 Control Tower판입니다.

🔴 **팩토리를 도입했다면 다른 계정 생성 경로를 전부 막으십시오.** `organizations:CreateAccount`를 관리 계정의 특정 역할로 제한하지 않으면, 팩토리를 우회해 만든 계정이 컨트롤·트레일·베이스라인 밖에 남습니다(12장).

### ⚠️ 드리프트와 기존 조직 위에 얹을 때의 제약

**드리프트**는 Control Tower가 만든 상태를 누군가 밖에서 바꿨을 때 생깁니다. 대표 유형 다섯입니다.

| 드리프트 유형 | 원인 |
|---|---|
| SCP 변경 | Control Tower가 만든 SCP를 Organizations 콘솔에서 직접 수정 |
| OU/계정 이동 | Control Tower 밖에서 계정을 다른 OU로 이동 |
| 계정 삭제·이탈 | 코어 계정을 조직에서 제거 |
| 역할 삭제·변경 | `AWSControlTowerExecution` 역할 변경 |
| 리전 거부 설정 불일치 | 관리 대상 리전 밖 설정 변경 |

드리프트가 생겨도 Control Tower는 **자동으로 고치지 않습니다.** 콘솔에 표시할 뿐이고 관리자가 랜딩 존 복구를 실행해야 합니다. 그동안 컨트롤은 **걸린 것처럼 보이지만 실제로는 걸려 있지 않을 수 있습니다**(28.4).

```bash
# 랜딩 존 상태와 드리프트 확인
aws controltower list-landing-zones --profile awssec-lab
aws controltower get-landing-zone \
  --landing-zone-identifier "<위 명령의 결과 ARN>" \
  --profile awssec-lab
```

**기존 조직 위에 얹을 때의 제약**은 넷입니다.

- 기존 계정은 자동 편입되지 않습니다. 계정마다 **등록(enroll)** 절차를 밟아야 하고 `AWSControlTowerExecution` 역할이 필요합니다.
- 기존 CloudTrail·Config 설정과 충돌합니다. 중복 트레일·레코더는 비용과 혼란을 함께 만듭니다.
- 관리 대상 리전 밖의 리소스는 시야 밖입니다.
- 기존 SCP와 Control Tower가 만드는 SCP는 **교집합**으로 겹쳐 예상치 못한 거부가 납니다.

⚠️ **등록도 37.3의 단계적 적용 절차를 따르십시오.** 계정 단위로 되므로 중요도가 낮은 계정부터 하나씩이 원칙입니다.

## 37.6 커스텀 랜딩 존 구축

Control Tower가 항상 답은 아닙니다. 다음 중 하나라도 해당하면 IaC로 직접 구성하는 편이 낫습니다.

- 이미 성숙한 Terraform/CloudFormation 기반 조직 관리 코드가 있다
- Control Tower가 지원하지 않는 리전이 주 운영 리전이다
- 랜딩 존 구성 자체를 코드 리뷰·승인 흐름에 넣어야 한다(28.5)
- 여러 클라우드에 걸친 공통 거버넌스 도구 체인을 이미 쓰고 있다

### 선택 기준 비교

| 항목 | Control Tower | 커스텀(IaC) 랜딩 존 |
|---|---|---|
| 초기 구축 속도 | **빠름** — 수 시간 | 느림 — 수 주 |
| 커스터마이징 자유도 | 제한적(필수 컨트롤 해제 불가) | **완전** |
| 리전 지원 | Control Tower 지원 리전 한정 | 제약 없음 |
| 코드 리뷰 대상 | 컨트롤 활성화 설정만 | **랜딩 존 전체가 코드** |
| 업그레이드 | AWS가 새 버전 제공, 랜딩 존 업데이트 실행 | **직접 유지보수** |
| 드리프트 관리 | 내장 감지(수동 복구) | `drift-detection` / `terraform plan` 직접 구성 |
| 운영 인력 | 적음 | **상시 담당자 필요** |
| 적합한 조직 | 대부분, 특히 소·중규모 | 플랫폼 팀이 있는 조직, 특수 요구 |

### 커스텀 랜딩 존의 최소 구성

직접 만든다면 다음 여섯 가지가 **빠져서는 안 되는 항목**입니다. 각각 이 책의 다른 장에서 이미 다뤘고, 여기서는 **조직 전체에 코드로 배포한다**는 점만 다릅니다.

| # | 항목 | 배포 수단 |
|---|---|---|
| 1 | 조직·OU·SCP | Organizations API를 IaC로(CloudFormation `AWS::Organizations::*`, Terraform `aws_organizations_*`) |
| 2 | 조직 CloudTrail + 로그 아카이브 버킷(객체 잠금) | 관리 계정 + 로그 계정 스택 |
| 3 | 전 계정 Config 레코더 + 집계자 | **StackSets 자동 배포** |
| 4 | GuardDuty·Security Hub·Access Analyzer 조직 활성화 | 위임 관리자 계정 스택 |
| 5 | 계정 베이스라인(역할·알람·예산) | **StackSets 자동 배포**(37.9) |
| 6 | 계정 생성 워크플로 | Service Catalog 또는 자체 파이프라인 |

3번과 5번의 **StackSets 자동 배포**가 커스텀 랜딩 존의 심장입니다.

```bash
# [관리 계정 또는 CloudFormation 위임 관리자]
aws cloudformation create-stack-set \
  --stack-set-name shopmini-account-baseline \
  --template-body file://baseline.yaml \
  --permission-model SERVICE_MANAGED \
  --auto-deployment Enabled=true,RetainStacksOnAccountRemoval=false \
  --capabilities CAPABILITY_NAMED_IAM \
  --profile awssec-lab

aws cloudformation create-stack-instances \
  --stack-set-name shopmini-account-baseline \
  --deployment-targets OrganizationalUnitIds=ou-abcd-11111111 \
  --regions ap-northeast-2 \
  --operation-preferences FailureTolerancePercentage=0,MaxConcurrentPercentage=25 \
  --profile awssec-lab
```

🔴 **`--auto-deployment Enabled=true`가 핵심입니다.** 이 옵션이 있으면 **해당 OU에 새 계정이 들어오는 순간** 스택이 자동으로 배포됩니다. 이벤트 처리 코드를 한 줄도 쓰지 않고 "신규 계정 즉시 베이스라인"이 성립합니다.

⚠️ Terraform은 이 자동 배포에 해당하는 기능이 없어, 계정 목록을 상태 파일이 알아야 합니다. Terraform으로 랜딩 존을 만들 때도 **계정 베이스라인만은 StackSets에 맡기는 하이브리드**가 실무에서 흔합니다.

## 37.7 AWS Config 적합성 팩(Conformance Pack) 🧪

> 💡 **원서 범위 밖 보강** — 적합성 팩은 원서 3권에 등장하지 않습니다. 원서가 다루는 것은 Config 자체이며, 아래는 그 조직 확장판입니다.

> 📖 *AWS Security Cookbook* 8장은 Config로 할 수 있는 검사로 **"MFA가 켜져 있는지, S3 버킷이 퍼블릭이 아닌지, 데이터베이스가 암호화되어 있는지, VPC 플로우 로그가 켜져 있는지"** 를 들고, 이어서 **"여러 계정에 걸쳐 동일한 Config 규칙 집합을 사용해 모두가 공통 규칙을 따르게 할 수 있다"**, **"집계자(aggregator)를 만들어 여러 계정과 전 리전의 리소스 인벤토리나 규칙 준수 상태를 볼 수 있다"** 고 설명합니다.

**적합성 팩은 저 두 문장을 하나의 배포 단위로 만든 것입니다.** 규칙과 교정 액션·파라미터를 한 CloudFormation 템플릿으로 묶어 조직 단위로 배포하고 준수율을 팩 단위로 집계합니다.

### 역할 분리 — 26.6 · 31.5와 무엇이 다른가

| 도구 | 이 책의 절 | 역할 |
|---|---|---|
| Config 규칙 개별 | 29.8 | 리소스 구성 변경을 기록·평가하는 **엔진** |
| **적합성 팩** | **37.7** | 규칙 묶음을 **조직 전체에 배포하고 팩 단위로 준수율을 보는 배포·거버넌스 단위** |
| Security Hub | 31.5 | 여러 소스(GuardDuty·Inspector·Config·Macie)의 **결과를 한 곳에 모으는 집계·워크플로 층** |
| CSPM(26.6) | 26.6 | 설정 오류를 **취약점 관리 관점**에서 스캔 |
| 자동 교정 | 35.3 | 비준수를 **되돌리는 실행** |

한 문장으로: **적합성 팩은 "무엇을 검사할지"를 배포하고, Security Hub는 "검사 결과"를 모읍니다.** 둘을 혼동하면 규칙이 중복 평가되어 비용만 늘어납니다 — 원서 8장이 명시하듯 Config는 **평가 횟수로 과금**됩니다.

### 조직 단위 배포

```bash
# [Config 위임 관리자 = 보안 도구 계정 444455556666]
aws configservice put-organization-conformance-pack \
  --organization-conformance-pack-name shopmini-ops-best-practices \
  --template-s3-uri s3://shopmini-conformance-templates/ops-best-practices.yaml \
  --delivery-s3-bucket awsconfigconforms-shopmini-777788889999 \
  --excluded-accounts 123456789012 \
  --profile awssec-lab
```

⚠️ **`--delivery-s3-bucket`의 버킷 이름에는 접두사 제약이 있습니다**(`awsconfigconforms`로 시작해야 하는 경우가 있습니다). 배포가 알 수 없는 이유로 실패하면 버킷 이름부터 확인하십시오. `--excluded-accounts`로 관리 계정을 빼는 것은 관례입니다.

### 커스텀 팩 작성

AWS는 CIS, NIST CSF, PCI DSS, HIPAA 등에 대응하는 **운영 모범 사례(Operational Best Practices)** 샘플 팩을 제공합니다. 다만 샘플 팩은 규칙이 수백 개여서 평가 비용과 노이즈가 크므로, 실무에서는 **필요한 규칙만 뽑아 자체 팩을 만드는 편**이 낫습니다.

```yaml
# ops-best-practices.yaml (발췌)
Parameters:
  RequiredTagKey:
    Type: String
    Default: Owner

Resources:
  EncryptedVolumes:
    Type: AWS::Config::ConfigRule
    Properties:
      ConfigRuleName: shopmini-encrypted-volumes
      Source:
        Owner: AWS
        SourceIdentifier: ENCRYPTED_VOLUMES

  S3PublicReadProhibited:
    Type: AWS::Config::ConfigRule
    Properties:
      ConfigRuleName: shopmini-s3-public-read-prohibited
      Source:
        Owner: AWS
        SourceIdentifier: S3_BUCKET_PUBLIC_READ_PROHIBITED

  RdsStorageEncrypted:
    Type: AWS::Config::ConfigRule
    Properties:
      ConfigRuleName: shopmini-rds-storage-encrypted
      Source:
        Owner: AWS
        SourceIdentifier: RDS_STORAGE_ENCRYPTED

  RequiredTags:
    Type: AWS::Config::ConfigRule
    Properties:
      ConfigRuleName: shopmini-required-tags
      InputParameters:
        tag1Key: !Ref RequiredTagKey
      Scope:
        ComplianceResourceTypes:
          - AWS::EC2::Instance
          - AWS::EC2::Volume
          - AWS::RDS::DBInstance
          - AWS::S3::Bucket
      Source:
        Owner: AWS
        SourceIdentifier: REQUIRED_TAGS
```

`RequiredTags` 규칙이 37.2 ⑨ SCP의 짝입니다. SCP가 **생성 시점**에 막고(예방), 이 규칙이 **SCP가 지원하지 않는 API로 만들어진 리소스**를 사후에 잡습니다(탐지) — 12.3의 3층 강제가 여기서 완성됩니다.

원서 8장이 안내하는 Lambda 기반 **커스텀 규칙**도 팩에 넣을 수 있지만 계정마다 Lambda가 필요합니다. Config의 커스텀 정책 규칙(28.2의 Guard 언어)이 관리하기 쉽습니다.

### 결과 집계

```bash
# 조직 전체 팩 배포 상태
aws configservice describe-organization-conformance-pack-statuses \
  --organization-conformance-pack-names shopmini-ops-best-practices \
  --profile awssec-lab

# 계정별 상세 상태 (어느 계정에서 실패했는지)
aws configservice get-organization-conformance-pack-detailed-status \
  --organization-conformance-pack-name shopmini-ops-best-practices \
  --filters Status=CREATE_FAILED \
  --profile awssec-lab
```

준수율 추이는 39장의 보안 지표로 이어집니다. **한 번 100%를 만드는 것보다 "새 위반이 며칠 만에 0으로 돌아오는가"** 가 성숙도 지표입니다.

## 37.8 태그 정책과 백업 정책

SCP는 Organizations 정책의 **한 종류**일 뿐입니다. 전체 지형은 이렇습니다.

| 정책 유형 | 무엇을 강제하는가 | 강제 방식 | 이 책의 절 |
|---|---|---|---|
| **서비스 제어 정책(SCP)** | 조직 주체가 할 수 있는 액션의 상한 | **거부** | 37.1~37.3 |
| **리소스 제어 정책(RCP)** | 조직 리소스에 접근할 수 있는 주체의 상한 | **거부** | 37.1 💡 |
| **태그 정책** | 태그 키 표기와 허용 값 | 보고 + `enforced_for` 지정 시 **차단** | 12.3, 아래 |
| **백업 정책** | 백업 계획을 하위 계정에 배포 | **배포**(하위에서 수정 불가) | 17.3, 아래 |
| **AI 서비스 옵트아웃 정책** | AWS AI 서비스의 콘텐츠 학습 이용 거부 | 설정 강제 | 아래 |
| **챗봇 정책** | 채팅 도구(Slack·Teams)에서의 AWS 접근 범위 | 제한 | 아래 |
| **선언적 정책** | 서비스의 계정 수준 설정 자체를 고정 | 설정 고정 | 아래 💡 |

정책 유형은 각각 **Root에서 개별적으로 활성화**해야 합니다.

```bash
aws organizations enable-policy-type --root-id "$ROOT_ID" --policy-type TAG_POLICY
aws organizations enable-policy-type --root-id "$ROOT_ID" --policy-type BACKUP_POLICY
aws organizations enable-policy-type --root-id "$ROOT_ID" --policy-type AISERVICES_OPT_OUT_POLICY
```

### 태그 정책 — 강제 vs 보고

12.3에서 상세히 다뤘으므로 여기서는 **거버넌스 관점의 결론 세 가지**만 확인합니다.

1. **태그 정책은 "이 태그를 반드시 달아라"를 강제하지 않습니다.** 값의 표기를 고정할 뿐이며, 태그 자체의 존재는 SCP(37.2 ⑨)와 Config `required-tags`(37.7)의 몫입니다.
2. **`enforced_for`를 지정하지 않으면 보고만 됩니다.** 위반이 "비준수"로 표시될 뿐 차단되지 않습니다. 지정하면 규정 위반 태그 부착 요청이 실제로 거부됩니다.
3. **하위 OU의 재정의를 통제하는 연산자를 명시하십시오.** `@@operators_allowed_for_child_policies`에 `@@none`을 넣으면 하위에서 값을 넓힐 수 없습니다.

> 📖 *Practical Cloud Security* 2판 2장: **"문제는 명확하다 — 조직의 모든 사람이 서로 다른 태그를 쓰면 태그는 별로 쓸모가 없다! 태그를 쓰는 정책을 두라. 이 정책을 뒷받침하기 위해 태그 표준을 만들어라 — 어떤 태그가 있고 언제 써야 하는지 설명을 붙인 목록을 만들고, 여러 클라우드 제공자에 걸쳐 같은 태그를 쓰고, 클라우드 리소스를 만드는 모든 자동화 도구가 그 태그를 적용하도록 요구하라."**

마지막 조항 — **"자동화 도구가 태그를 적용하도록 요구하라"** — 이 37.2 ⑨ SCP를 붙이기 **전에** 해야 할 일입니다. 순서를 뒤집으면 파이프라인이 전부 멈춥니다.

### 백업 정책

17.3에서 조직 백업 정책을 켰습니다. 정책 문서의 형태는 이렇습니다.

```json
{
  "plans": {
    "shopmini-org-daily": {
      "regions": { "@@assign": ["ap-northeast-2"] },
      "rules": {
        "daily-35day": {
          "schedule_expression": { "@@assign": "cron(0 17 ? * * *)" },
          "start_backup_window_minutes": { "@@assign": "60" },
          "complete_backup_window_minutes": { "@@assign": "600" },
          "target_backup_vault_name": { "@@assign": "shopmini-org-vault" },
          "lifecycle": {
            "delete_after_days": { "@@assign": "35" }
          },
          "copy_actions": {
            "arn:aws:backup:ap-northeast-2:777788889999:backup-vault:shopmini-airgap-vault": {
              "target_backup_vault_arn": {
                "@@assign": "arn:aws:backup:ap-northeast-2:777788889999:backup-vault:shopmini-airgap-vault"
              },
              "lifecycle": { "delete_after_days": { "@@assign": "365" } }
            }
          }
        }
      },
      "selections": {
        "tags": {
          "select-by-backup-tag": {
            "iam_role_arn": {
              "@@assign": "arn:aws:iam::$account:role/service-role/AWSBackupDefaultServiceRole"
            },
            "tag_key": { "@@assign": "Backup" },
            "tag_value": { "@@assign": ["daily"] }
          }
        }
      }
    }
  }
}
```

🔴 **`selections`가 태그 기반이라는 점을 눈여겨보십시오.** 백업 대상은 `Backup=daily` 태그로 선택됩니다 — 태그가 없으면 **백업이 안 됩니다.** 태그 거버넌스(12장·37.2 ⑨)가 무너지면 조용히 백업 사각지대가 생깁니다. 이것이 태그 정책과 백업 정책을 한 절에 묶은 이유입니다. `$account`는 계정 ID로 치환되는 변수입니다.

⚠️ 백업 정책이 만든 계획은 하위 계정에서 수정·삭제할 수 없지만, **대상 볼트가 존재하지 않으면 백업 작업이 실패**합니다. 볼트는 StackSets로 먼저 배포하십시오(37.9).

### AI 서비스 옵트아웃 정책과 챗봇 정책

**AI 서비스 옵트아웃 정책**은 AWS의 일부 AI/ML 서비스가 고객 콘텐츠를 서비스 개선에 이용하는 것을 조직 차원에서 거부합니다. 기밀 이상 데이터(4.2)를 다루면 **기본으로 켭니다.**

```json
{
  "services": {
    "@@operators_allowed_for_child_policies": ["@@none"],
    "default": {
      "@@operators_allowed_for_child_policies": ["@@none"],
      "opt_out_policy": { "@@assign": "optOut" }
    }
  }
}
```

`default`에 걸면 개별 서비스를 나열하지 않고 전체에 적용되며, `@@none`으로 하위 OU의 재정의를 막습니다.

**챗봇 정책**은 Slack·Microsoft Teams 같은 채팅 도구에서 AWS 계정에 접근하는 범위를 조직 차원에서 제한합니다. 30장에서 알림 채널로 채팅을 쓰기 시작했다면 **"알림은 받되 명령은 실행하지 못하게"** 를 여기서 정합니다.

> 💡 **원서 이후 변경 — 선언적 정책(Declarative Policies)** — SCP가 "액션을 거부"한다면 선언적 정책은 **서비스의 계정 수준 설정 자체를 고정**합니다. EC2의 퍼블릭 IP 자동 할당 기본값 같은 설정을 조직 전체에 못 박고 신규 계정·신규 리전에도 자동 적용하므로, 리전이 늘 때마다 새는 구멍을 메우는 데 유용합니다. 지원 서비스가 아직 좁으니 도입 전 대상 목록을 확인하십시오.

## 37.9 🔴 신규 계정 베이스라인 자동화

### 왜 이것이 7부의 결론인가

> 📖 *Practical Cloud Security* 2판 3장은 자산 관리를 배관에 비유합니다. **"대부분의 조직에는 서비스와 인프라를 프로비저닝하는 길목에 자연스러운 통제 지점(control points)이 있다. 조직마다 다르겠지만, 여러분은 그 통제 지점들을 찾아내 조여서 모든 클라우드 자산을 파악하고 리스크를 적절히 관리해야 한다. (…) 자산이 중요한 보안 활동에서 누락되게 만드는 모든 '누수(leak)'를 막으려 해야 한다."**

멀티 계정 조직에서 **가장 큰 누수 지점은 "새로 만든 계정"** 입니다. 계정 생성부터 베이스라인 적용까지의 시간이 곧 사각지대이고, 체크리스트를 사람이 실행하는 조직에서 그 시간은 며칠에서 영원까지 늘어납니다.

🔴 **신규 계정의 베이스라인 적용 시간을 0에 수렴시키십시오.** 목표는 "계정 생성 API가 성공한 시점에 이미 베이스라인이 적용 중"입니다.

### 세 가지 구현 경로

| 경로 | 트리거 | 지연 | 커버리지 | 적합 |
|---|---|---|---|---|
| **StackSets 자동 배포** | **OU에 계정이 들어오는 것 자체** | 수 분 | 해당 OU 전체 — 신규·기존·이동 모두 | 🔴 **기본 선택** |
| Control Tower Account Factory Customization | 팩토리를 통한 계정 생성 | 수 분 | 팩토리로 만든 계정만 | Control Tower 사용 조직 |
| EventBridge + Lambda | `CreateAccountResult` / Control Tower 라이프사이클 이벤트 | 수 초~수 분 | 이벤트가 발생한 경우만 | 위 둘로 안 되는 커스텀 작업 |

**StackSets 자동 배포가 기본인 이유**는 유일하게 **"계정을 어떻게 만들었는가"에 의존하지 않기** 때문입니다. 콘솔이든 CLI든 초대 편입이든 OU에 들어오면 배포됩니다. 이벤트 기반은 반드시 놓치는 경로가 생기므로, CloudFormation으로 표현되지 않는 작업(계정 별칭·대체 연락처)만 EventBridge로 보완합니다.

```json
{
  "source": ["aws.organizations"],
  "detail-type": ["AWS Service Event via CloudTrail"],
  "detail": {
    "eventSource": ["organizations.amazonaws.com"],
    "eventName": ["CreateAccountResult"],
    "serviceEventDetails": {
      "createAccountStatus": { "state": ["SUCCEEDED"] }
    }
  }
}
```

⚠️ 두 가지를 동시에 틀리기 쉽습니다. 첫째, `CreateAccountResult`는 사람이 호출한 API가 아니라 **AWS가 비동기로 발행하는 서비스 이벤트**라서 `detail-type`이 `AWS API Call via CloudTrail`이 아니라 **`AWS Service Event via CloudTrail`** 입니다. 둘째, Organizations API는 `us-east-1`에서 처리되므로 이 규칙도 **`us-east-1`에 만들어야** 합니다. 둘 중 하나라도 틀리면 규칙은 만들어지지만 영원히 울리지 않고, 아무도 그 사실을 눈치채지 못합니다.

🔴 **표에서 "StackSets"로 표시된 항목이 곧 베이스라인 템플릿의 내용입니다.** 이 템플릿 하나가 조직의 계정 표준이며, 변경은 반드시 PR과 리뷰를 거쳐야 합니다(28.5).

**안 하면 어떻게 되는가.** 베이스라인이 자동화되지 않은 조직을 점검하면 거의 예외 없이 **Config가 꺼져 있고 예산 알림이 없는 계정이 몇 개** 나옵니다. 사고는 항상 그 계정에서 나고, 아무도 보고 있지 않았기 때문에 커집니다.

### 베이스라인 준수 여부 지속 검증

배포했다고 유지되는 것이 아닙니다. 세 층으로 검증합니다.

| 층 | 무엇을 보는가 | 수단 | 주기 |
|---|---|---|---|
| **① 배포 상태** | StackSets 인스턴스가 모든 계정에 `CURRENT`인가 | `list-stack-instances` + `detect-stack-set-drift` | 주 1회 |
| **② 설정 상태** | 배포된 리소스가 실제로 그 값인가 | Config 적합성 팩(37.7) | 상시 |
| **③ 조직 상태** | 모든 계정이 OU에 속하고 정책이 붙었는가 | `list-accounts-for-parent`, `list-policies-for-target` | 주 1회 |

```bash
# ① 베이스라인이 실제로 안 깔린 계정 찾기
aws cloudformation list-stack-instances \
  --stack-set-name shopmini-account-baseline \
  --query 'Summaries[?Status!=`CURRENT`].[Account,Region,Status,StatusReason]' \
  --output table \
  --profile awssec-lab

# ① 드리프트 감지 시작
aws cloudformation detect-stack-set-drift \
  --stack-set-name shopmini-account-baseline \
  --profile awssec-lab

# ③ Root 바로 아래에 계정이 있는지 (있으면 결함 — 36.4)
aws organizations list-accounts-for-parent \
  --parent-id "$ROOT_ID" \
  --query 'Accounts[].[Id,Name]' \
  --output table \
  --profile awssec-lab
```

세 명령의 출력이 모두 **비어 있거나 전부 `CURRENT`** 인 상태가 정상입니다. 이 세 줄을 주간 자동 리포트로 만들어 보안팀 채널에 올리는 것이 이 장 전체를 살아 있게 유지하는 방법입니다.

## 🔴 필수 구성 체크리스트

**SCP 설계**
- [ ] 조직 기능 세트가 `ALL`이고 Root에서 `SERVICE_CONTROL_POLICY`가 활성화되어 있다
- [ ] 모든 SCP가 Git에 있고 파이프라인으로 배포된다 — 콘솔 직접 수정 0건
- [ ] Root SCP에는 "어떤 계정에서도 절대 안 되는 것"만 있다
- [ ] `FullAWSAccess`를 떼어 낸 지점이 없다(허용 목록 OU 제외)
- [ ] 각 SCP에 예외 주체(배포 역할·위임 관리자)가 명시되어 있다
- [ ] **배포 역할이 자기 자신을 잠그지 않는지** 확인했다

**필수 10개 SCP**
- [ ] ① 루트 사용자 액션 전면 거부
- [ ] ② CloudTrail 중지·삭제·변경 금지
- [ ] ③ GuardDuty·Config·Security Hub·Macie·Access Analyzer 비활성화 금지
- [ ] ④ 미승인 리전 차단 — **글로벌 서비스 `NotAction` 목록과 SLR 예외 검증 완료**
- [ ] ⑤ 비암호화 EBS·S3 업로드 차단 — **`Null` 조건으로 미지정 요청까지 차단**
- [ ] ⑤-보조 SCP로 막을 수 없는 항목(RDS 저장 암호화 등)이 **Config 규칙 + 파이프라인 게이트로 덮여 있다**
- [ ] ⑥ `organizations:LeaveOrganization` · `account:CloseAccount` 거부
- [ ] ⑦ IAM 사용자·액세스 키·로그인 프로파일 생성 금지
- [ ] ⑧ 로그 버킷·백업 볼트 삭제·정책 변경 금지 (Root 부착)
- [ ] ⑨ 필수 태그 없는 리소스 생성 차단 + 거버넌스 태그 제거 금지
- [ ] ⑩ 베이스라인 역할·권한 경계 정책 변경 금지

**적용 절차**

- [ ] PolicyStaging → NonProd → 카나리 → 전체 순서를 지킨다
