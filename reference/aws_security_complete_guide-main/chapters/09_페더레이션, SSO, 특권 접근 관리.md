## 9.1 페더레이티드 아이덴티티의 원리

### 개념: 신원을 만들지 않고 빌려 쓴다

> 📖 *Practical Cloud Security* 1판·2판 4장 「Federated Identity」는 이것이 기술이 아니라 개념이라고 못 박습니다. **"페더레이티드 아이덴티티는 특정 기술이 아니라 개념이다. 서로 다른 두 시스템에 신원을 가질 수 있고, 두 시스템의 관리자가 그 신원들을 연결하는 기술을 쓰기로 합의하면 각 시스템에 별도 계정을 수동으로 만들 필요가 없다는 뜻이다. 사용자 관점에서 당신은 하나의 신원만 갖는다."**
>
> 회사 B가 인증을 회사 A에 맡기면, A는 토큰을 돌려주며 말합니다. **"그렇다, 이 사용자는 정말로 user@company-a.com이다. 내가 검증했고, 이것이 나임을 증명하는 내 서명이다. 그리고 당신은 @company-a.com으로 끝나는 식별자를 가진 사용자의 인증을 나에게 맡기기로 이미 합의했다."**

이 문장에 페더레이션의 세 요소가 전부 들어 있습니다. **주장(assertion)**, **서명**, **사전 합의된 신뢰**. AWS에서는 각각 SAML 응답, IdP 인증서, IAM SAML 공급자 객체로 구현됩니다.

> 📖 같은 장 「Single Sign-On」 — **"SSO는 페더레이티드 아이덴티티 개념에 의존하는 기술 구현의 집합이다."** 저자는 이점을 흔치 않은 조합이라고 표현합니다. **"사용자에게 더 쉬우면서 동시에 더 나은 보안을 제공하는 것은 좀처럼 찾기 어렵다. (…) 그 자격 증명은 오직 아이덴티티 공급자만 보기 때문에 개별 사이트가 침해되어도 사용자의 자격 증명은 침해되지 않는다."**
>
> 2판은 제로 트러스트 관점을 덧붙였습니다. **"SSO 공급자는 관리되지 않거나 오래된 기기가 사용되고 있는지, 또는 사용자의 자격 증명이 서로 다른 두 국가에서 동시에 사용되고 있는지 확인하는 등 (…) 통제를 구현할 수 있다. 이런 종류의 통제는 애플리케이션마다 개별적으로 구현하기가 매우 어렵다."**

IdP 단일화를 아키텍처 결정으로 삼아야 하는 이유가 이것입니다. 기기 상태 검사·이상 위치 탐지는 **인증 지점이 하나일 때만** 붙일 수 있습니다.

### SAML 2.0의 5단계

> 📖 1판·2판 4장 「SAML and OIDC」의 단순화 버전입니다.
> 1. 접근하려는 웹 페이지(서비스 공급자, SP)에 브라우저를 향한다.
> 2. SP가 말한다. **"이봐, 너는 SAML 쿠키가 없어서 네가 누군지 모르겠다. 저기 아이덴티티 공급자 페이지로 가서 하나 받아와."**
> 3. IdP에 가서 사용자 이름과 암호, 그리고 바라건대 두 번째 요소 **또는 패스워드리스 방식**으로 로그인한다.
> 4. IdP는 **"나는 아이덴티티 공급자이고 이 사용자는 인증되었다"** 는 서명된 XML "주장"이 담긴 쿠키를 준다.
> 5. 브라우저가 그 쿠키를 SP에 건네고, SP는 서명을 검증한 뒤 말한다. **"당신은 IdP에게 신원을 납득시켰으니 나에게도 충분하다. 들어오라."**
>
> 저자는 두 가지를 짚습니다. **"처음의 웹 페이지와 아이덴티티 공급자 사이에 직접 통신은 전혀 없었다 — 브라우저가 모든 힘든 일을 했다."** 그리고 **"SAML은 설계상 신원 정보만 제공한다. 로그인하거나 다른 작업을 할 권한이 있는지는 별개의 문제"** 입니다. 3번의 "패스워드리스"는 2판에서 추가된 표현으로, 1판에는 **"아마도 두 번째 요소"** 까지만 있었습니다.

**둘째 지적이 AWS 설계의 핵심입니다.** SAML 주장은 "누구인가"만 말하고 "무엇을 할 수 있는가"는 AWS 쪽 역할·권한 세트가 정합니다. **IdP 그룹을 AWS 역할에 매핑하는 규칙**이 사실상 인가 설계의 절반입니다.

> 📖 2판 4장 — **"OpenID Connect는 OAuth 2.0 위에 얹힌 훨씬 새로운 인증 계층으로 2014년에 확정되었다. XML 대신 JSON 웹 토큰(JWT)을 사용하고, 다소 다른 용어를 쓴다(SAML의 '서비스 공급자'를 OIDC에서는 보통 '신뢰 당사자relying party'라고 부른다)."** 그리고 — **"큰 조직에서는 두 표준을 함께 쓰는 것이 매우 흔하고, 대부분의 IdP가 둘 다 지원한다."**

| 항목 | SAML 2.0 | OIDC |
|---|---|---|
| 확정 시점 | 2005년(원서 서술) | 2014년(원서 서술) |
| 토큰 형식 | 서명된 XML 주장 | JWT(JSON) |
| SP 측 용어 | 서비스 공급자(SP) | 신뢰 당사자(RP) |
| AWS의 주 용도 | 사람의 콘솔·CLI 접근 | 워크로드·CI/CD의 단기 자격 증명 |
| AWS API | `sts:AssumeRoleWithSAML` | `sts:AssumeRoleWithWebIdentity` |
| 대표 사례 | ADFS·Okta·Entra ID로 콘솔 로그인 | GitHub Actions → 배포 역할, EKS 서비스 계정 |

### AWS에서의 두 경로

사람을 AWS에 들이는 페더레이션 경로는 두 개뿐이고, **선택 기준은 계정 개수**입니다.

| | 경로 A: IAM SAML 공급자 | 경로 B: IAM Identity Center |
|---|---|---|
| 구성 위치 | **계정마다** SAML 공급자 + 역할 생성 | 조직에 **한 번** 구성 |
| 신원-권한 매핑 | IdP가 역할 ARN을 주장에 실어 보냄 | 권한 세트 + 계정 할당 |
| 계정 10개 확장 시 | SAML 공급자 10개, 역할 수십 개, IdP 앱 10개 | 권한 세트 재사용, 할당만 추가 |
| CLI 사용 | IdP 응답을 직접 처리해야 함(도구 필요) | `aws sso login` 기본 지원 |
| 적합한 상황 | 단일 계정, 기존 ADFS 자산 활용, 특수 클레임 요구 | **멀티 계정 — 사실상 모든 조직** |

경로 A의 신뢰 정책은 이렇게 생깁니다. `SAML:aud` 조건이 없으면 같은 IdP가 다른 용도로 발급한 주장이 재사용될 수 있으므로 **반드시 넣습니다.**

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "TrustCorpIdPForConsoleAndCli",
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::111122223333:saml-provider/CorpIdP"
      },
      "Action": "sts:AssumeRoleWithSAML",
      "Condition": {
        "StringEquals": {
          "SAML:aud": "https://signin.aws.amazon.com/saml"
        }
      }
    }
  ]
}
```

> 📖 *AWS Security Cookbook* 3장이 경로 A의 절차를 요약해 둡니다. ADFS 서버에서 `FederationMetadata.xml`을 내려받아 IAM에 공급자 유형 **SAML**로 등록하고, 신뢰 주체 유형이 **SAML 2.0 페더레이션**인 역할을 만듭니다. 저자는 조건을 붙입니다. **"(아이덴티티 공급자에 정의된) 사용자는 로그인 과정에서 AWS 역할을 맡아야 한다."**

경로 A는 관리 비용이 계정 수에 비례해 커집니다. 그래서 이 장의 나머지는 경로 B를 표준으로 놓고 씁니다.

> 📖 SSO를 지원하지 않는 레거시 앱 앞에 리버스 프록시를 두는 방식도 2판에 있는데, 조건이 강합니다. **"레거시 애플리케이션은 이 프런트엔드 서비스가 인증을 수행할 것이라고 신뢰하겠지만, 그 애플리케이션이 다른 어떤 것으로부터도 연결을 받아들이지 않는 것이 매우 중요하다."** AWS에서는 ALB 인증(OIDC/Cognito) + 앱 보안 그룹이 ALB 보안 그룹만 참조하도록 잠그는 조합이 대응합니다(19.2, 23장).

## 9.2 🔴 IAM Identity Center(구 AWS SSO) 도입 🧪

> 💡 **원서 이후 변경 — 서비스 명칭** *AWS Security Cookbook* 10장의 레시피 제목은 「Setting up and using AWS SSO」이고 본문 전체가 **AWS SSO**라는 이름을 씁니다. 이 서비스는 이후 **AWS IAM Identity Center**로 이름이 바뀌었고 콘솔 구성도 달라졌으므로, 아래 실습은 원서 레시피의 흐름을 유지하면서 현재 명칭과 CLI(`sso-admin`, `identitystore`) 기준으로 갱신했습니다. 다만 API 접두사와 IAM 액션 이름에는 여전히 `sso:`/`sso-admin:`이 남아 있습니다.

> 📖 *AWS Security Cookbook* 10장 — **"AWS SSO는 여러 AWS 계정과 다른 애플리케이션에 대한 SSO 접근을 쉽게 관리하도록 돕는 클라우드 서비스다."** 주요 용도는 **"AWS Organization 내 모든 AWS 계정, 비즈니스 애플리케이션, 커스텀 SAML 2.0 기반 애플리케이션에 걸쳐 SSO를 설정·관리"** 하고 **"기업 Microsoft Active Directory 인스턴스의 사용자와 그룹에 SSO 접근을 사용"** 하는 것입니다. 동작 원리도 짚어둡니다. **"콘솔에서 AWS SSO 서비스를 활성화하면, AWS SSO가 우리 AWS Organization 멤버 계정 각각에 역할을 만드는 것을 허용하게 된다."**

마지막 문장이 중요합니다. Identity Center는 각 멤버 계정에 `AWSReservedSSO_<권한세트이름>_<해시>` 역할을 자동으로 만들고 관리합니다. **그 역할을 사람이 손으로 고치면 안 됩니다** — 이 절 마지막의 SCP가 그것을 막습니다.

### 구성 요소 네 개

| 요소 | 하는 일 | 비유 |
|---|---|---|
| **인스턴스(Instance)** | 조직당 하나. 관리 계정에서 활성화, 위임 관리자 계정 지정 가능 | 통제실 |
| **아이덴티티 소스** | 사용자·그룹이 어디에 사는가 — Identity Center 디렉터리 / Active Directory / 외부 IdP | 인사 명부 |
| **권한 세트(Permission Set)** | 계정에서 무엇을 할 수 있는가 = IAM 정책 + **세션 지속 시간** + 권한 경계 | 직무 기술서 |
| **계정 할당(Assignment)** | *누가*(그룹) × *어디서*(계정) × *무엇을*(권한 세트) | 배치 명령 |

핵심은 **곱셈 구조**입니다. 권한 세트 8개 × 계정 12개면 조합은 96개지만 관리할 정책 문서는 8개입니다. 경로 A에서라면 역할 96개를 만들었을 겁니다.

### 🧪 실습: 권한 세트부터 CLI 로그인까지

관리 계정(`123456789012`) 또는 위임 관리자로 지정된 보안 도구 계정(`444455556666`)에서 진행합니다.

```bash
# 0) 인스턴스 확인
aws sso-admin list-instances --profile awssec-lab --region ap-northeast-2
# → InstanceArn / IdentityStoreId 두 값을 받아 아래에서 재사용
IDC_ARN=arn:aws:sso:::instance/ssoins-1111222233334444
IDS_ID=d-1234567890
```

```bash
# 1) 그룹 생성 (아이덴티티 소스가 Identity Center 디렉터리인 경우)
aws identitystore create-group --identity-store-id "$IDS_ID" \
  --display-name shopmini-prod-readonly \
  --description "ShopMini 운영 계정 읽기 전용"
# 외부 IdP + SCIM을 쓰면 이 단계는 IdP에서 자동으로 채워진다 (9.3)
```

```bash
# 2) 권한 세트 생성 — 세션은 1시간, 콘솔 진입 지점 지정
aws sso-admin create-permission-set --instance-arn "$IDC_ARN" \
  --name ProdReadOnly \
  --description "운영 계정 읽기 전용" \
  --session-duration PT1H \
  --relay-state "https://ap-northeast-2.console.aws.amazon.com/cloudwatch/home" \
  --tags Key=Project,Value=awssec-lab Key=Chapter,Value=ch09
PS_ARN=arn:aws:sso:::permissionSet/ssoins-1111222233334444/ps-aaaabbbbccccdddd
```

```bash
# 3) 권한 부여 + 권한 경계로 상한 고정
aws sso-admin attach-managed-policy-to-permission-set --instance-arn "$IDC_ARN" \
  --permission-set-arn "$PS_ARN" \
  --managed-policy-arn arn:aws:iam::aws:policy/ReadOnlyAccess

aws sso-admin put-permissions-boundary-to-permission-set --instance-arn "$IDC_ARN" \
  --permission-set-arn "$PS_ARN" \
  --permissions-boundary '{"ManagedPolicyArn":"arn:aws:iam::aws:policy/PowerUserAccess"}'
```

```bash
# 4) 계정 할당 — 그룹 × 운영 계정 × 권한 세트
aws sso-admin create-account-assignment --instance-arn "$IDC_ARN" \
  --target-id 111122223333 --target-type AWS_ACCOUNT \
  --permission-set-arn "$PS_ARN" \
  --principal-type GROUP --principal-id 90671234-abcd-4321-9876-1234567890ab
```

이제 사용자 쪽입니다. `aws configure sso`는 액세스 포털에 브라우저 로그인을 띄우고, 접근 가능한 계정·역할 목록을 받아 프로파일을 만들어 줍니다.

```bash
aws configure sso --profile shopmini-prod-ro
# SSO session name (Recommended): awssec-idc
# SSO start URL [None]: https://d-1234567890.awsapps.com/start
# SSO region [None]: ap-northeast-2
# SSO registration scopes [sso:account:access]: (엔터)
```

결과로 `~/.aws/config`에 두 블록이 생깁니다. **세션 블록을 계정별 프로파일이 공유**하므로, 로그인 한 번으로 여러 계정 프로파일을 함께 씁니다.

```ini
[sso-session awssec-idc]
sso_start_url = https://d-1234567890.awsapps.com/start
sso_region = ap-northeast-2
sso_registration_scopes = sso:account:access

[profile shopmini-prod-ro]
sso_session = awssec-idc
sso_account_id = 111122223333
sso_role_name = ProdReadOnly
region = ap-northeast-2
output = json
```

```bash
aws sso login --sso-session awssec-idc
aws sts get-caller-identity --profile shopmini-prod-ro
# Arn: arn:aws:sts::111122223333:assumed-role/AWSReservedSSO_ProdReadOnly_1a2b3c4d5e6f7a8b/hong@example.com
aws sso logout    # 캐시된 토큰 폐기
```

`get-caller-identity`의 출력이 이 절의 결론입니다. **디스크에 저장된 장기 자격 증명이 없습니다.** 캐시에는 만료 시각이 박힌 SSO 토큰만 있고, 실제 호출은 그때그때 임시 자격 증명으로 이뤄집니다. 6.4의 "장기 액세스 키를 없애라"가 여기서 실현됩니다.

### 세션 지속 시간은 두 개다

| 종류 | 설정 위치 | 의미 | 권장 |
|---|---|---|---|
| **권한 세트 세션** | 권한 세트 `SessionDuration`(PT1H~PT12H) | 역할 자격 증명의 수명 | 일반 1~4시간, **관리자 권한은 1시간** |
| **액세스 포털 세션** | Identity Center 설정 → 인증 | 재인증 없이 포털을 다시 쓸 수 있는 기간 | 8~12시간. 며칠·몇 주로 늘리지 말 것 |

포털 세션을 길게 두면 권한 세트 세션을 1시간으로 조여도 의미가 옅어집니다. IdP 계정을 비활성화해도 **살아 있는 포털 세션은 만료까지 새 역할 자격 증명을 계속 발급받을 수 있기 때문**입니다. 9.6의 회수 절차에 "활성 세션 삭제"가 들어가야 하는 이유입니다.

### 🔴 반드시 이렇게 구성하라

- [ ] **관리 계정에서 활성화한 뒤 일상 운영은 위임 관리자 계정에서.** 관리 계정 로그인 빈도를 줄이는 것이 36.6의 원칙입니다.
- [ ] **사람용 IAM 사용자를 새로 만들지 않는다.** 기존 사용자는 마이그레이션 목록에 올리고 기한을 정해 삭제합니다.
- [ ] **관리자급 권한 세트의 세션은 1시간**, 반드시 **MFA 요구**(9.4)와 함께.
- [ ] **권한 세트마다 권한 경계**를 걸어 정책 실수의 상한을 고정합니다.
- [ ] **할당은 개인이 아니라 그룹에.** 개인 할당은 퇴사 시 누락되는 첫 번째 항목입니다.
- [ ] **권한 세트와 할당을 IaC로 관리**합니다(28장). 콘솔에서 손으로 만든 할당은 리뷰도 회수도 되지 않습니다.
- [ ] **`AWSReservedSSO_*` 역할을 SCP로 보호**합니다.

마지막 항목을 빼면, `AdministratorAccess` 권한 세트를 받은 사람이 자기 역할에 인라인 정책을 붙이거나 신뢰 정책을 바꿔 **할당을 해제해도 살아남는 뒷문**을 만들 수 있습니다. 다음 SCP가 그 경로를 닫습니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ProtectIdentityCenterManagedRoles",
      "Effect": "Deny",
      "Action": [
        "iam:AttachRolePolicy",
        "iam:DetachRolePolicy",
        "iam:PutRolePolicy",
        "iam:DeleteRolePolicy",
        "iam:PutRolePermissionsBoundary",
        "iam:DeleteRolePermissionsBoundary",
        "iam:UpdateAssumeRolePolicy",
        "iam:UpdateRole",
        "iam:DeleteRole"
      ],
      "Resource": "arn:aws:iam::*:role/aws-reserved/sso.amazonaws.com/*",
      "Condition": {
        "ArnNotLike": {
          "aws:PrincipalArn": "arn:aws:iam::*:role/OrgBreakGlassRole"
        }
      }
    }
  ]
}
```

## 9.3 기업 IdP 연동

### 아이덴티티 소스 세 가지

> 📖 *AWS Security Cookbook* 10장은 선택지와 로그인 흐름을 함께 정리합니다. **"Active Directory 옵션에서는 AWS Managed Microsoft AD를 쓸 수도 있고, AWS Managed Microsoft AD나 AD Connector를 통해 기존 Active Directory를 쓸 수도 있다. 외부 아이덴티티 공급자 옵션에서는 사용자, 그룹, 자격 증명, MFA 등을 외부 아이덴티티 공급자로 관리한다."** 그리고 **"AWS SSO와 Active Directory 옵션에서는 사용자가 AWS SSO 사용자 포털을 통해 로그인한다. 외부 아이덴티티 공급자 옵션에서는 사용자가 아이덴티티 공급자의 로그인 페이지를 통해 로그인해 AWS SSO 사용자 포털에 접근한다."**

이 차이는 취향 문제가 아닙니다. **외부 IdP를 쓰면 MFA·기기 검사·조건부 접근이 전부 IdP에서 강제**되고 AWS는 결과만 받습니다. 9.1의 제로 트러스트 통제를 실제로 쓰려면 이 배치여야 합니다.

| 소스 | 언제 | 장점 | 함정 |
|---|---|---|---|
| Identity Center 디렉터리 | IdP가 없는 소규모, 학습·PoC | 즉시 시작, 추가 비용 없음 | **인사 시스템과 단절** — 퇴사 반영이 수동 |
| Active Directory (Managed AD) | AD가 이미 표준이고 AWS 내 워크로드도 AD를 씀 | 기존 그룹 재사용, 도메인 조인 연계 | 디렉터리 운영 비용, 다중 포리스트 설계 |
| Active Directory (AD Connector) | 온프레미스 AD를 그대로 쓰고 복제하지 않음 | 사용자 복제 없음, 온프레미스가 원본 | **온프레미스 AD·회선 가용성에 AWS 로그인이 종속** |
| 외부 IdP (Okta·Entra ID·Google Workspace 등) | IdP가 이미 전사 표준 | MFA·조건부 접근·SCIM 일원화 | SAML 메타데이터·인증서 갱신 누락 시 전면 장애 |

> 💡 **원서 이후 변경 — 명칭** 원서가 쓴 **Azure Active Directory**는 이후 **Microsoft Entra ID**로 이름이 바뀌었습니다. 이 책은 Entra ID로 표기하되, 원서 인용 부분은 원문 명칭을 유지합니다.

### SCIM: 프로비저닝은 보안 통제다

외부 IdP 연동은 두 개의 채널로 이뤄집니다. 한쪽만 붙이는 것이 가장 흔한 미완성 구성입니다.

| 채널 | 프로토콜 | 무엇이 흐르는가 | 빠졌을 때 |
|---|---|---|---|
| 인증 | SAML 2.0 | 로그인 시점의 신원 주장 | 로그인 자체가 안 됨 — **즉시 발견됨** |
| 프로비저닝 | **SCIM 2.0** | 사용자·그룹 생성·수정·**비활성화**를 상시 동기화 | 퇴사자 계정과 그룹 멤버십이 AWS에 남음 — **사고 날 때까지 발견 안 됨** |

**SAML만 붙이고 SCIM을 생략하는 구성이 9.6 회수 누락의 구조적 원인입니다.** SCIM이 없으면 퇴사 처리가 "IdP 담당자가 AWS 쪽에도 잊지 않고 알려주는" 사람의 기억에 의존합니다. SCIM이 있으면 IdP에서 비활성화한 순간 Identity Center 사용자도 비활성화되고, 그룹에서 빠지면 계정 할당의 효력도 사라집니다.

연동 시 반드시 확정할 것:

- **그룹 이름 규칙.** `aws-<계정별칭>-<역할>`(예: `aws-shopmini-prod-readonly`)을 권장합니다. IdP 그룹 이름이 곧 AWS 권한의 구분선이므로, 규칙 없이 시작하면 6개월 뒤 어떤 그룹이 무슨 권한인지 아무도 모릅니다.
- **동기화 범위를 필요한 그룹으로 좁히기.** 전사 사용자를 다 밀어 넣으면 접근 권한 없는 사용자가 수천 명 쌓여 재검증 목록이 무의미해집니다.
- **SAML 서명 인증서 만료 알람.** 갱신을 놓치면 전 계정 로그인이 동시에 막힙니다 — 32.4 브레이크글래스가 필요해지는 대표 사례입니다.
- **속성 매핑.** `email`·`userName`, 그리고 ABAC를 쓴다면 `Department` 같은 속성을 세션 태그로 전달해 `aws:PrincipalTag/...` 조건으로 씁니다(8.7).
- 자동 프로비저닝 지원 범위는 IdP 제품마다 다르므로, **그룹 동기화가 실제로 되는지 연동 직후 사용자 한 명으로 검증**합니다.
- ⚠️ **아이덴티티 소스는 처음에 확정하십시오.** 소스를 나중에 바꾸면 기존 사용자·그룹 멤버십과 계정 할당이 그대로 유지되지 않을 수 있습니다. 전환이 불가피하다면 **현재 할당을 먼저 내보내고 재구성 계획을 세운 뒤** 진행하고, 전환 중 접근이 끊길 것을 전제로 브레이크글래스 경로를 확보해 두십시오(32.4).

## 9.4 다중 인증(MFA)의 진화

### 세 가지 요소와 그 조합

> 📖 *Practical Cloud Security* 1판·2판 4장 「Multi-Factor Authentication」 — **"다중 인증은 취약하거나 탈취된 자격 증명을 막는 최선의 방법 중 하나이며, 제대로 구현하면 사용자에게 아주 작은 추가 부담만 지운다."** 요소는 **아는 것**(암호·PIN), **가진 것**(배지·휴대전화·무작위 개인 키), **자신인 것**(지문·얼굴·망막) 셋이고, 같은 종류를 두 개 쓰는 것은 의미가 없습니다. **"두 개의 서로 다른 암호처럼 같은 요소를 두 개 쓰는 것은 큰 도움이 되지 않는다. 같은 공격으로 두 암호를 모두 얻을 수 있기 때문이다!"**
>
> 2판은 노트를 덧붙였습니다. **"2FA는 두 요소 중 하나가 암호일 것을 요구하지 않는다. 두 요소를 갖춘 패스워드리스 로그인(가진 물리 기기와 그 기기를 잠금 해제하는 지문 같은 것)은 암호 인증보다 상당히 더 안전하고 편리할 수 있다."**

### 방법별 비교 — 원서의 열거를 AWS 문맥으로

> 📖 2판 4장의 방법별 서술에서 판단 근거만 뽑으면 다음과 같습니다.

| 방법 | 요소 | 원서의 평가 | AWS에서 |
|---|---|---|---|
| 암호·패스프레이즈 | 아는 것 | **"이제 그만 쓸 때가 한참 지났지만, 변화는 어렵다"** | 루트·IAM 사용자 콘솔. 사람 접근에서 제거 대상 |
| PIN | 아는 것 | **"PIN은 특정 물리 기기와 짝을 이룰 때만 유용하다"** — 기기 없이 PIN만 알아내도 접근 불가 | FIDO2 인증기 잠금 해제 요소 |
| SMS | 가진 것 | SIM 복제·번호 이동·메시지 가로채기로 **"선호에서 밀려났다. 새 구현은 쓰지 말아야 하고, 기존 구현은 다른 방법으로 옮겨야 한다"** | **쓰지 않습니다** |
| TOTP | 가진 것 | 초기 시크릿 전달 후 네트워크 불필요. 단점은 **"덜 편리하고 '피싱 가능phishable'하다 — 가짜 사이트에 암호와 패스코드를 둘 다 입력하게 속이면 공격자가 접근할 수 있다"** | 인증기 앱. 최소 기준선 |
| HOTP | 가진 것 | TOTP와 장단점이 비슷하되 시계 동기화 불필요, 다만 **"코드를 너무 많이 생성하고 쓰지 않으면 동기가 깨질 수 있다"** | 하드웨어 OTP 토큰 |
| 푸시 알림 | 가진 것 | **"교묘한 위조 사이트로, 또는 많은 요청으로 사용자를 지치게 해서 예라고 답하게 만들 수 있다"** | IdP 측 기능 |
| 생체 | 자신인 것 | **"충분한 노력을 들이면 속일 수 있지만 구현은 계속 개선되고 있고, 대부분의 보안 요구를 충족할 단일 요소로는 충분히 좋다"** | FIDO2 인증기 잠금 해제 |
| **FIDO2 / 패스키** | 가진 것(+아는 것/자신인 것) | 아래 인용 참조 — **"단연 최선의 선택"** | 하드웨어 보안 키, 노트북·휴대전화 내장 인증기 |

> 📖 2판 4장의 FIDO2 항목이 이 절의 핵심입니다. **"FIDO U2F는 두 번째 인증 요소일 뿐이고 일반적으로 암호와 함께 쓰이지만, FIDO2는 결합된 다중 인증 기기로 기능해 패스워드리스 인증을 가능하게 한다. FIDO2 기기는 패스키라고도 불린다. 이것은 단연 최선의 선택인데, 패스키는 자신이 어떤 애플리케이션과 통신하고 있는지 알기 때문에 가짜 사이트에 속을 수 없다. (…) 이제 이 기술은 대부분의 노트북과 모바일 기기에 내장되어 있다. (…) FIDO2 기기는 PIN이나 생체 요소로 잠금을 해제할 수 있어, 두 요소를 하나의 기기에 결합해 매우 강력하고 피싱에 저항하는 패스워드리스 인증을 제공한다."**
>
> **1판에는 이 서술이 없습니다.** 1판은 **"FIDO U2F 표준을 준수하는 것과 같은 하드웨어 기기"** 한 줄로 끝납니다. 2판 서문도 갱신 항목으로 **"패스워드리스 기술과 패스키 같은 인증 기법의 진전"** 을 명시합니다.

결론은 **"피싱 저항"이 새 기준선**이라는 것입니다. TOTP는 실시간 중계 피싱에 뚫리고, 패스키는 오리진에 묶여 뚫리지 않습니다. 관리자 접근에는 패스키를 요구하십시오. 그럼에도 우회는 남습니다.

> 📖 2판의 경고 노트 — **"'가진 것'을 검증하는 이 방법들 중 다수는 거짓 구실로 사용자에게 전화해 일회용 패스코드를 물어보는 것 같은 사회적 공격에 취약하다! FIDO2처럼 가장 강력한 형태의 인증조차, 사용자가 가짜 사이트에 가서 '그건 안 되네요, 다른(더 약한) 방법을 시도해 보세요'라는 말을 들으면 다운그레이드 공격의 대상이 될 수 있다. 다중 인증을 배포하는 것과 더불어, 흔한 공격을 알아차릴 수 있도록 사용자에게 최소한의 교육을 제공해야 한다."**

**다운그레이드 공격 방어는 정책 문제입니다.** Identity Center MFA 설정에서 허용 MFA 유형을 좁히고 "MFA 기기가 없으면 로그인 차단"으로 두면, 사용자에게 "더 약한 방법"이라는 선택지가 아예 없습니다.

> 📖 원서는 위험 기반 강화에 이름을 붙입니다. **"더 높은 위험의 활동에 추가 인증을 요구하는 것을 단계적 인증step-up authentication이라고 한다."** 그리고 — **"클라우드 환경을 관리한다면 클라우드 포털이나 API에 대한 무단 관리자 접근은 당신에게 매우 높은 위험이다. 그런 접근을 가진 공격자는 보통 그것을 이용해 당신의 모든 데이터를 침해할 수 있기 때문이다."**

### AWS에서의 구현

> 💡 **원서 이후 변경 — AWS의 MFA 지원** ① 루트·IAM 사용자 모두 **FIDO2 인증기**(하드웨어 보안 키, 내장 패스키)를 MFA로 등록할 수 있습니다. ② 한 사용자에 **여러 MFA 기기를 동시 등록**할 수 있으니 백업 기기를 반드시 등록하십시오. ③ AWS는 루트 사용자 MFA 등록을 **단계적으로 의무화**하고 있습니다. ④ IAM Identity Center는 **MFA 요구 시점**(매 로그인 / 컨텍스트 변화 시 / 요구 안 함), **허용 MFA 유형**(보안 키·내장 인증기 / 인증기 앱 / RADIUS MFA), **미등록 사용자 처리**(등록 요구 / 로그인 차단)를 설정할 수 있습니다.

Identity Center를 표준으로 세워도 IAM 사용자 경로는 계정에 남습니다. 이 경로를 SCP로 닫아야 MFA 강제가 실효를 갖습니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyIamUserActionsWithoutMFA",
      "Effect": "Deny",
      "NotAction": [
        "iam:ChangePassword",
        "iam:GetUser",
        "iam:ListMFADevices",
        "iam:ListVirtualMFADevices",
        "iam:CreateVirtualMFADevice",
        "iam:EnableMFADevice",
        "iam:ResyncMFADevice",
        "sts:GetSessionToken"
      ],
      "Resource": "*",
      "Condition": {
        "BoolIfExists": {
          "aws:MultiFactorAuthPresent": "false"
        },
        "StringLike": {
          "aws:PrincipalArn": "arn:aws:iam::*:user/*"
        }
      }
    },
    {
      "Sid": "DenyNewHumanCredentialPaths",
      "Effect": "Deny",
      "Action": [
        "iam:CreateUser",
        "iam:CreateLoginProfile",
        "iam:CreateAccessKey"
      ],
      "Resource": "*",
      "Condition": {
        "ArnNotLike": {
          "aws:PrincipalArn": "arn:aws:iam::*:role/OrgBreakGlassRole"
        }
      }
    }
  ]
}
```

두 가지를 짚습니다. 첫째, `Bool`이 아니라 **`BoolIfExists`** 입니다. `aws:MultiFactorAuthPresent` 키는 요청에 없을 수 있고, `Bool`을 쓰면 키가 없는 요청에서 조건이 매칭되지 않아 Deny가 통과합니다(7.4). 둘째, `aws:PrincipalArn`을 `user/*`로 좁혀 **Identity Center 역할 세션과 워크로드 역할이 영향을 받지 않게** 했습니다.

> ⚠️ **조건 키에 MFA 강제를 전부 맡기지 마십시오.** `aws:MultiFactorAuthPresent`는 IAM 사용자가 MFA로 STS 세션을 얻은 경로에서 신뢰할 수 있습니다. 반면 SAML·Identity Center 같은 **페더레이션 역할 세션에서는 이 키의 존재와 값이 연동 방식에 따라 달라져 통제 지점으로 삼기에 적합하지 않습니다.** 페더레이션 경로의 MFA는 **IdP 또는 Identity Center 설정에서 강제**하고, 조건 키는 위 SCP처럼 **잔존 IAM 사용자 경로 차단**에 쓰십시오.

## 9.5 특권 접근 관리(PAM)

### 2판이 새로 들여온 주제

> 📖 *Practical Cloud Security* 2판 4장 「Shared IDs」에서 PAM이라는 이름이 처음 등장합니다. **"root처럼 ID를 공유해야 한다면, 그 공유 ID를 사용하는 시스템은 누가 그것을 쓰고 있었는지 구별할 방법이 없다. 그것은 곧 공유 자격 증명을 체크아웃하고 반납할 때 그것을 변경하는 별도의 프로세스와 도구가 필요하다는 뜻이다. 이 도구를 보통 특권 접근 관리(PAM) 또는 특권 아이덴티티 관리(PIM) 시스템이라고 부르며, 세션을 기록하거나 일부 명령의 사용을 금지하는 등의 다른 기능도 수행할 수 있다."**
>
> 같은 장의 도구 치트시트는 목적을 좁혀 정의합니다. **"자격 증명 볼트, 특권 접근 관리 시스템 (…) 의 핵심은 개인별 책임 추적성individual accountability을 보장해, 어느 시점에 어떤 주체가 자격 증명을 쓰고 있는지 알 수 있게 하는 것이다."** 2판 서문은 이것을 갱신 항목으로 명시합니다 — **"클라우드 환경을 보호하기 위한 특권 접근 관리 도구의 사용."** 1판에는 PAM 서술이 없습니다.

**AWS에는 "AWS PAM"이라는 서비스가 없습니다.** 원서가 말한 PAM의 기능들이 여러 구성요소에 흩어져 있고, 그것을 조립하는 것이 이 절입니다.

| 원서가 말한 PAM 기능 | AWS에서의 대응 |
|---|---|
| 자격 증명 체크아웃 | Identity Center 권한 세트 **일시 할당** / 승격 역할 `AssumeRole` |
| 개인별 책임 추적성 | 역할 세션 이름 = 사용자 식별자, CloudTrail `userIdentity`(29.2) |
| 세션 기록 | SSM Session Manager 세션 로깅(21.6), CloudTrail 관리 이벤트 |
| 명령 제한 | IAM 권한 경계·SCP, Session Manager 문서 제한 |
| 반납 시 자격 증명 변경 | 임시 자격 증명이므로 **불필요** — 만료가 반납을 대신함 |

마지막 행이 클라우드의 이점입니다. 온프레미스 PAM은 공유 암호를 회수하고 바꿔야 했지만, AWS의 역할 세션은 **시간이 지나면 스스로 소멸**합니다. AWS에서 PAM 설계의 무게중심은 자격 증명 보관이 아니라 **권한 부여의 수명과 승인**입니다.

### 상시 관리자 권한 제거

| | 상시(Standing) 관리자 | Just-In-Time 승격 |
|---|---|---|
| 권한 상태 | 항상 부여됨 | 기본은 없음, 요청 시 한시 부여 |
| 자격 증명 탈취 시 | 즉시 관리자 권한 확보 | **승인 절차를 통과해야 함** |
| 실수의 폭발 반경 | 언제나 최대 | 승격 창 안에서만 |
| CloudTrail 관점 | 관리자 활동이 일상 소음에 섞임 | **승격 자체가 이벤트** — 알람 대상 |
| 감사 증거 | "누가 관리자인가" 명단만 | 요청·승인·사용·만료 기록 일체 |

핵심 전환은 네 번째 행입니다. 상시 관리자 체제에서는 관리자 API 호출이 하루 수천 건이라 악성 하나를 골라낼 수 없습니다. JIT 체제에서는 **관리자 권한의 존재 자체가 드문 이벤트**가 되어 승격에 알람을 걸 수 있습니다(30.3).

### JIT 구현 세 가지 패턴

| 패턴 | 구현 | 승인 지연 | 적합 |
|---|---|---|---|
| ① 승격 역할 | 읽기 전용 세션에서 `AdministratorAccess` 역할을 `AssumeRole`. 신뢰 정책에 MFA·소스 조건 | 없음(사후 알람) | 소규모, 운영 긴급성이 높은 조직 |
| ② 할당 자동화 | 승인 시 자동화가 `sso-admin create-account-assignment` 실행, 만료 시각에 `delete-account-assignment` | 분 단위 | **표준 권장** |
| ③ 그룹 멤버십 자동화 | 승인 시 `identitystore create-group-membership`, 만료 시 삭제. IdP 그룹으로 하는 변형도 동일 | 분 단위 | IdP 그룹 체계가 이미 견고한 조직 |

②·③은 자동화가 강력한 권한(`sso:CreateAccountAssignment` 또는 `identitystore:CreateGroupMembership`)을 갖게 되므로, **그 자동화 역할이 새로운 최고 권한 주체가 되지 않도록** 처리해야 합니다.

- 자동화가 부여할 수 있는 **권한 세트 목록을 화이트리스트로 고정**합니다.
- 자동화의 코드·구성 변경을 **자동화 자신이 할 수 없게** 합니다(승인 우회 방지).
- 사람이 직접 `create-account-assignment`를 호출하지 못하도록, SCP에서 자동화 역할과 브레이크글래스 역할 외의 주체를 거부합니다.
- **만료 처리 실패를 알람**합니다. 부여는 성공하고 회수가 실패하면 조용히 상시 권한이 됩니다.

> 💡 **원서 이후 — AWS의 참조 구현** AWS는 IAM Identity Center를 대상으로 하는 임시 권한 승격 관리의 오픈소스 참조 구현을 공개해 두었습니다. 요청·승인·기한부 할당·자동 회수·감사 기록의 뼈대를 쓸 수 있으니 자체 구축 전에 검토하십시오.

### 승인 워크플로에 반드시 담을 것

"개인별 책임 추적성"을 만드는 것은 워크플로가 남기는 기록입니다. 요청 하나마다 다음이 남아야 합니다.

**요청자 · 대상 계정 · 요청 권한 세트 · 사유(변경 티켓 번호) · 승인자 · 승인 시각 · 만료 시각 · 실제 회수 시각**

**만료 시각과 실제 회수 시각을 분리 기록**하는 것이 요령입니다. 두 값이 벌어진 건수가 자동화 고장의 지표이고, 감사에서 "권한이 실제로 회수되었음"을 증명하는 유일한 증거입니다.

> 📖 2판 4장 「Approve」 — **"조직 내부에서는 대부분의 접근 요청이 명시적으로 승인되어야 한다. 많은 경우 두 번의 승인이 합리적이다 — 예컨대 사용자의 직속 상급자와, 접근이 요청된 시스템의 소유자. 중요한 것은 승인자가 요청된 접근이 합리적이고 필요한지 알 수 있는 위치에 있어야 한다는 점이다."** 2판 7장은 이 원칙을 **"네 눈의 원칙, 2인 규칙"** 이라고도 부릅니다.

### 세션 기록과 브레이크글래스

> 📖 2판 7장 「Session Recording Tools」 — **"특권 접근 관리나 특권 아이덴티티 관리 시스템에 보통 포함되는 기능 중 하나는 세션 관리다. 특권 세션을 기록하고, 특권 사용자가 무엇을 하는지 실시간으로 지켜보고, 의심스러운 세션을 끊는 능력이다."** 중앙 집중은 단일 실패 지점이 되고, 로컬 에이전트는 **"특권 사용자가 에이전트를 끌 권한을 흔히 갖는다"** 는 단점이 있습니다. 결론은 — **"일반적으로 나는 중앙 집중식 세션 기록을 권하며, 세션 기록 인프라가 다운되었을 때 접근할 수 있는 브레이크글래스 프로세스를 함께 두라고 권한다."**
>
> 같은 장은 관리 활동 로그를 **독성 로그(toxic logs)** 와 **살균된 로그(sanitized logs)** 로 나눕니다. 전자는 암호나 API 키가 섞일 수 있는 로그로, **"의심되는 사고 중에만, 또는 (…) 작고 감시되는 팀에 의해서만 접근되어야 한다"** 고 못 박습니다. 셸 세션 로그가 그 예이고, 콘솔·API 작업 기록은 후자입니다.

AWS에서 **API 수준 특권 활동**은 CloudTrail이(29.2), **OS 수준 세션**은 SSM Session Manager 세션 로깅이(21.6) 기록합니다. 세션 로그는 독성 로그로 분류해 별도 계정·별도 KMS 키에 두고, 열람 자체를 알람 대상으로 삼습니다.

브레이크글래스 절차 — IdP나 Identity Center가 다운되었을 때의 최후 경로 — 는 **32.4에서 별도로 다룹니다.** 여기서는 하나만 기억하십시오. **9.4의 SCP에서 `OrgBreakGlassRole`을 예외로 남겼다면, 그 역할의 사용은 즉시 알람되어야 합니다.**

## 9.6 🔴 아이덴티티 라이프사이클 ⚠️

### 사고 시나리오

개발 계정(`555555555555`)에서 야간에 대량의 EC2 인스턴스가 기동됩니다. 크립토마이닝입니다. CloudTrail의 호출 주체는 2년 전 퇴사한 외주 개발자 이름의 IAM 사용자이고, 액세스 키는 3년 전에 만들어져 한 번도 교체되지 않았습니다. 인사 시스템에는 퇴사가 기록되어 있었고 회사 IdP 계정도 퇴사일에 비활성화되었습니다.

**원인은 세 겹입니다.** ① 그 계정은 Identity Center 연동 전에 만들어진 IAM 사용자를 갖고 있었습니다 — IdP 비활성화가 닿지 않는 경로입니다. ② 회수 트리거가 "퇴사"뿐이었고 "프로젝트 종료"는 없었습니다. ③ 2년 동안 **아무도 그 계정의 자격 증명 목록을 보지 않았습니다.** ①과 ②는 실수지만 ③은 **절차의 부재**입니다.

### 원서의 5단계

> 📖 *Practical Cloud Security* 1판·2판 4장 「Life Cycle for Identity and Access」 — **"많은 사람이 IAM을 인증과 인가만으로 생각하는 실수를 한다. 둘 다 매우 중요하지만, IAM에는 아이덴티티 라이프사이클의 다른 부분들도 포함된다."** 그리고 **"많은 조직이 이것을 제대로 하지 못한다. 아이덴티티 요청은 관리자에게 전화하거나 메시지를 보내는 식으로 이뤄지고, 관리자는 아무 기록도 남기지 않고 승인하고 아이덴티티를 만든다."**
>
> 이어서 무게중심을 뒤로 옮깁니다. **"더욱 중요한 것은 라이프사이클의 뒷단이다. (…) 누군가를 해고하는 불쾌한 일을 치른 뒤 한 달이 지나서야 사람의 실수로 그 사람이 여전히 중요한 시스템에 접근할 수 있다는 사실을 깨닫는 상황을 상상해보라!"** 다만 **"반드시 화려한 자동화 시스템이 필요한 것은 아니다"** — 요청자와 승인자가 적으면 일관된 수동 프로세스로도 됩니다.
>
> 놓치기 쉬운 대상도 짚습니다. **"애플리케이션처럼 시스템 안의 사람이 아닌 것들의 아이덴티티도 잊지 마라. (…) 많은 팀이 사람에 대한 접근 통제는 훌륭하게 하면서, 자동화가 무엇을 할 권한이 있는지에 대해서는 매우 느슨한 통제를 갖고 있다."**

원서의 단계를 ShopMini 운영 절차로 옮기면 다음과 같습니다. **각 단계에 "증거" 열이 있는 것이 핵심입니다** — 감사는 절차의 존재가 아니라 증거를 요구합니다.

| 단계 | 원서 서술 | AWS 운영 절차 | 남아야 할 증거 |
|---|---|---|---|
| **① 요청(Request)** | 신원 생성·삭제, 접근 부여·회수 네 가지 요청. **"조직 내부에서는 익명 요청을 원하지 않는다"** | IdP 그룹 가입 요청 티켓. **"클라우드 환경에서는 요청 프로세스가 클라우드 IAM 시스템과 무관하게 조직 내부에서 대역 외로 일어나는 경우가 많다"**(원서) | 티켓 번호, 요청자, 요청 사유 |
| **② 승인(Approve)** | 상급자 + 시스템 소유자 2인 승인 | 티켓 승인 기록. 특권 권한 세트는 예외 없이 명시적 승인 | 승인자, 승인 시각 |
| **③ 부여/회수(Create·Delete·Grant·Revoke)** | **"자동화가 바람직하다. 특히 자주 요청되는 항목에 대해서는 사람의 실수 가능성을 줄이기 때문"** | SCIM 프로비저닝 + IaC로 관리되는 권한 세트·할당 | CloudTrail, IaC 커밋 |
| **④ 인증·인가** | 아이덴티티 저장소와 인증 프로토콜의 구분 | IdP(MFA·기기 검사) + Identity Center 권한 세트 | 로그인 로그, `sts` 이벤트 |
| **⑤ 재검증(Revalidate)** | 자동 재검증 + 사람 판단 재검증 | 아래 절차 | 검토자, 검토 결과, 조치 내역 |

### 재검증 — 감사 지적 1순위

> 📖 1판·2판 4장 「Revalidate」 — **"재검증 단계는 전통적 환경과 클라우드 환경 모두에서 매우 중요하지만, 클라우드 환경에서는 접근 회수를 잊었을 때 당신을 구해줄 추가 통제(물리적 건물 접근이나 네트워크 통제 같은 것)가 전혀 없을 수 있다."**
>
> 자동 재검증에는 구체적 요구가 붙습니다. **"단순히 사용자의 아이덴티티를 삭제하는 것만으로는 충분하지 않을 수 있다. 그 사용자가 로그인 능력 없이도 사용할 수 있는 액세스 토큰 같은 캐시된 자격 증명을 갖고 있을 수 있기 때문이다. 이런 상황에서는 오프보딩 피드offboarding feed — 접근이 회수되어야 하는 주체의 목록 — 가 필요하다. 수명이 긴 자격 증명을 발급하는 시스템은 이 오프보딩 피드를 최소한 매일 처리하고 그 주체들의 접근을 즉시 회수해야 한다."**
>
> 사람 판단 재검증은 둘입니다. **긍정 확인** — **"더 강하다. 누군가 '이 접근은 여전히 필요하다'고 명시적으로 말하지 않으면 접근을 잃는다"** — 와 **부정 확인** — **"더 약하다. 누군가 '이 접근은 더 이상 필요하지 않다'고 말하지 않으면 접근이 유지된다."** 배분 기준은 **"비즈니스에 영향이 큰 유형의 접근에는 긍정 확인을 사용해야 한다"** 입니다.
>
> 재검증이 무엇을 상대하는지도 말합니다. **"재검증이 다루는 가장 큰 리스크는 (아마도 다툼이 있는 상황에서) 조직을 떠난 사람이 시스템에 대한 접근을 유지하는 것이다. 그 외에도 접근은 시간이 지나며 부엌 잡동사니 서랍(당신도 아는 그 서랍)에 물건이 쌓이듯 축적되는 경향이 있다. 재검증은 이 잡동사니를 치운다."**
>
> 마지막 조언은 반직관적이지만 결정적입니다. **"접근을 얻기가 어렵다면, 사용자들은 더 이상 필요하지 않아도 여전히 필요하다고 주장하는 일이 흔하다. 필요할 때 빠르고 쉽게 접근을 부여하는 프로세스가 함께 있다면 재검증 노력이 불필요한 접근을 잘라내는 데 훨씬 효과적일 것이다."**

**마지막 문장이 9.5와 9.6을 하나로 묶습니다.** JIT 승격이 5분이면 사람들은 상시 권한을 순순히 내놓고, 3일이 걸리면 모든 재검증 설문에 "필요합니다"라고 답합니다. **회수의 성공률은 부여의 속도에 달려 있습니다.**

### 🧪 재검증에 쓰는 명령

```bash
# 1) 자격 증명 보고서 — 계정 내 모든 IAM 사용자의 MFA·키 사용 이력
aws iam generate-credential-report --profile awssec-lab
aws iam get-credential-report --profile awssec-lab \
  --query Content --output text | base64 -d > credential-report.csv
# 확인 열: password_enabled, password_last_used, mfa_active,
#          access_key_1_last_used_date, access_key_2_last_used_date
```

`password_last_used`와 `access_key_*_last_used_date`가 90일 이상 과거인 행이 회수 후보입니다. 앞의 사고는 이 명령을 분기마다 돌렸다면 발생하지 않았습니다.

```bash
# 2) IAM Access Analyzer 미사용 액세스 분석기 — 조직 전체를 상시 감시
aws accessanalyzer create-analyzer \
  --analyzer-name org-unused-access \
  --type ORGANIZATION_UNUSED_ACCESS \
  --configuration '{"unusedAccess":{"unusedAccessAge":90}}' \
  --profile awssec-lab --region ap-northeast-2

aws accessanalyzer list-findings-v2 \
  --analyzer-arn "$ANALYZER_ARN" --max-results 50
# 결과 유형: 미사용 역할 / 미사용 액세스 키 / 미사용 콘솔 암호 / 미사용 권한
```

미사용 액세스 분석기는 재검증을 **연 1회 설문에서 상시 탐지로 바꿉니다.** 결과를 Security Hub로 모아 소유자 티켓으로 흘리면(31.5), 사람 판단이 필요한 항목만 사람에게 남습니다.

```bash
# 3) 역할에 붙은 권한 중 실제로 쓰인 것만 남기기
aws iam generate-service-last-accessed-details \
  --arn arn:aws:iam::111122223333:role/DataEngineer
aws iam get-service-last-accessed-details --job-id "$JOB_ID"
```

```bash
# 4) 회수 — SCIM이 없거나 SCIM 범위 밖일 때의 수동 절차
aws identitystore delete-group-membership \
  --identity-store-id "$IDS_ID" --membership-id "$MEMBERSHIP_ID"
aws sso-admin delete-account-assignment --instance-arn "$IDC_ARN" \
  --target-id 111122223333 --target-type AWS_ACCOUNT \
  --permission-set-arn "$PS_ARN" \
  --principal-type USER --principal-id "$USER_ID"
aws identitystore delete-user --identity-store-id "$IDS_ID" --user-id "$USER_ID"
# 그리고 콘솔에서 해당 사용자의 활성 세션을 삭제한다 — 삭제만으로는
# 이미 발급된 포털 세션이 만료 전까지 살아 있을 수 있다 (9.2)
```

### 🔴 이렇게 구성하라

- [ ] **회수 트리거를 세 개로 정의합니다** — 퇴사, **부서·직무 변경**, **프로젝트·계약 종료**. 세 번째가 빠진 조직이 대부분입니다.
- [ ] **오프보딩 피드를 하루 1회 이상 처리합니다.** SCIM 연동이 이 요구를 자동으로 충족합니다(9.3).
- [ ] **삭제 후 활성 세션까지 확인합니다.** 원서가 말한 "캐시된 자격 증명"이 AWS에서는 포털 세션과 역할 세션입니다.
- [ ] **관리자급·기밀 데이터 접근은 긍정 확인**, 그 외는 부정 확인으로. 주기는 최소 분기.
- [ ] **비인간 아이덴티티도 같은 목록에** 넣습니다 — 서비스 역할, 액세스 키를 가진 CI 사용자, 크로스 계정 신뢰, 외부 SaaS에 준 역할(8.6).
- [ ] **재검증 증거를 남깁니다** — 검토 일자, 검토자, 회수 건수. 기록이 없으면 절차가 있어도 감사에서는 없는 것으로 판정됩니다.

> ⚠️ **재검증을 하지 않으면 무엇이 남는가.** 권한은 한 방향으로만 자랍니다. 새 프로젝트마다 추가되고, 끝난 프로젝트의 것은 남습니다. 3년이 지나면 조직의 절반이 사실상 관리자가 되고, **그때는 최소 권한 정책을 아무리 정교하게 써도 의미가 없습니다.** 실제 권한은 정책 문서가 아니라 그 정책이 붙어 있는 주체의 목록으로 결정되기 때문입니다.

## 9.7 📋 IAM 아키텍처 리뷰 체크리스트

2부(6~11장) 전체를 총괄하는 점검 목록입니다. 계정 하나가 아니라 **조직 전체**를 대상으로, 분기마다 이 목록으로 리뷰하십시오.

**아이덴티티와 자격 증명**
- [ ] 사람용 접근이 **전부 IAM Identity Center 또는 SAML 페더레이션**을 경유한다. 사람용 IAM 사용자 잔존 수를 숫자로 답할 수 있다 (9.2)
- [ ] 모든 계정의 **루트 사용자에 MFA가 등록**되어 있고 액세스 키가 없다 (5.1)
- [ ] 루트 사용자와 관리자급 권한에 **FIDO2 인증기(패스키)** 가 등록되어 있고, **백업 MFA 기기**가 함께 등록되어 있다 (9.4)
- [ ] SMS MFA를 쓰지 않는다 (9.4)
- [ ] **잔존 IAM 사용자 경로를 SCP로 막는다** — 신규 사용자·로그인 프로파일·액세스 키 생성 거부 (9.4, 37.2)
- [ ] 워크로드가 장기 액세스 키를 쓰지 않는다 — 인스턴스 프로파일·태스크 역할·IRSA·OIDC (6.4, 8.2, 8.4)
- [ ] 90일 이상 미사용 자격 증명이 0건이다 — `get-credential-report`로 검증 (9.6)

**권한 설계**
- [ ] 할당이 **개인이 아니라 그룹**에 되어 있다 (9.2)
- [ ] 권한 세트·역할에 **권한 경계**가 걸려 있다 (7.2, 9.2)
- [ ] `"Action": "*"` + `"Resource": "*"` 조합의 정책이 사람에게 상시 부여되어 있지 않다 (7.5)
- [ ] `iam:PassRole`이 리소스 제한 없이 허용된 정책이 없다 (7.5)
- [ ] 신뢰 정책에 `"Principal": {"AWS": "*"}` 가 없고, 서드파티 역할에 **External ID**가 있다 (7.5, 8.6)
- [ ] 리소스 기반 정책의 크로스 계정 허용이 **`aws:PrincipalOrgID`로 제한**되어 있다 (7.4, 20.3)
- [ ] IAM Access Analyzer **외부 접근 분석기**가 전 계정에 켜져 있고 결과가 0건 또는 승인 목록에 있다 (7.7)
- [ ] IAM Access Analyzer **미사용 액세스 분석기**가 조직 단위로 켜져 있다 (7.7, 9.6)
- [ ] IMDSv2가 전 인스턴스에 강제되어 있다 (8.3)

**세션과 특권 접근**
- [ ] 관리자급 권한 세트의 **세션이 1시간**, 액세스 포털 세션이 12시간 이하다 (9.2)
- [ ] **상시 관리자 권한 보유자 수를 숫자로 답할 수 있고**, 그 수가 감소 추세다 (9.5)
- [ ] 관리자 권한이 **JIT 승격**으로 부여되고, 요청·승인·만료·실제 회수 시각이 기록된다 (9.5)
- [ ] **승격 이벤트와 브레이크글래스 역할 사용에 알람**이 걸려 있다 (9.5, 30.3, 32.4)
- [ ] `AWSReservedSSO_*` 역할 변조가 SCP로 차단되어 있다 (9.2)
- [ ] OS 수준 관리 접근이 **SSM Session Manager 경유**이고 세션이 기록된다. 세션 로그는 독성 로그로 분리 보관된다 (9.5, 21.6)

**라이프사이클**
- [ ] 외부 IdP 연동에 **SAML과 SCIM이 모두** 구성되어 있다 (9.3)
- [ ] 회수 트리거가 **퇴사·직무 변경·프로젝트 종료** 세 가지로 정의되어 있다 (9.6)
- [ ] 회수 절차에 **활성 세션 삭제**가 포함되어 있다 (9.2, 9.6)
- [ ] 재검증이 분기마다 실행되고 **검토자·결과·조치 증거**가 남는다. 특권 접근은 긍정 확인이다 (9.6)
- [ ] **비인간 아이덴티티**(서비스 역할, CI 사용자, 크로스 계정 신뢰, 외부 SaaS 역할)가 재검증 목록에 포함되어 있다 (9.6)
- [ ] SAML 서명 인증서 만료일이 캘린더와 알람에 등록되어 있다 (9.3)

**고객 아이덴티티와 시크릿** (10·11장 선행 점검)
- [ ] 고객용 인증이 애플리케이션 자체 암호 검증이 아니라 Cognito 등 관리형 서비스를 쓴다 (10장)
- [ ] 시크릿이 코드·환경 변수·User Data·AMI·컨테이너 레이어에 없다 (11.1, 22.4)

## 이 장의 요약

| 항목 | 핵심 |
|---|---|
| **페더레이션의 정의** | "특정 기술이 아니라 개념"(원서 1·2판 4장). 주장 + 서명 + 사전 합의된 신뢰 |
| **SSO의 이점** | "사용자에게 더 쉬우면서 동시에 더 나은 보안" — 자격 증명은 IdP만 본다 |
| **SAML의 한계** | "설계상 신원 정보만 제공한다" — 인가는 AWS 쪽 역할·권한 세트가 정한다 |
| **AWS의 두 경로** | 계정마다 SAML 공급자 + `AssumeRoleWithSAML` / 조직에 한 번 Identity Center |
| **Identity Center 구조** | 권한 세트(정책+세션) × 계정 할당(그룹) — 정책 8개로 조합 96개를 관리 |
| **명칭** | 원서의 "AWS SSO" = 현재 **IAM Identity Center**. API 접두사는 `sso:`/`sso-admin:` 유지 |
| **CLI** | `aws configure sso` → `aws sso login` → 디스크에 장기 키 없음 |
| **세션 두 개** | 권한 세트 세션(PT1H~PT12H)과 액세스 포털 세션. 후자를 길게 두면 회수가 늦어진다 |
| **SCIM** | SAML만 붙이면 회수가 사람의 기억에 의존. SCIM이 오프보딩 피드를 자동화한다 |
| **MFA 기준선** | SMS 폐기, TOTP는 "피싱 가능", **FIDO2/패스키가 "단연 최선의 선택"**(2판 신규) |
| **다운그레이드 공격** | "다른(더 약한) 방법을 시도해 보세요" — 허용 MFA 유형을 좁혀 선택지를 없앤다 |
| **조건 키의 한계** | `aws:MultiFactorAuthPresent`는 **`BoolIfExists`** 로, 그리고 IAM 사용자 경로 차단에만 |
| **PAM** | AWS에 PAM 서비스는 없다. 체크아웃=일시 할당, 반납=만료. "개인별 책임 추적성"이 목표 |
| **JIT** | 관리자 권한이 드문 이벤트가 되어야 승격에 알람을 걸 수 있다 |
| **회수의 속도 의존** | "필요할 때 빠르고 쉽게 부여하는 프로세스가 있어야 재검증이 효과적"(원서) |
| **재검증 2종** | 영향 큰 접근은 **긍정 확인**, 나머지는 부정 확인 |
| **감사 지적 1순위** | 퇴사·프로젝트 종료 시 회수 누락과 재검증 미실시. 증거가 없으면 절차도 없는 것 |

## 🔴 필수 구성 체크리스트

- [ ] 사람용 접근을 **Identity Center로 통일**하고, 잔존 IAM 사용자에 삭제 기한을 부여했다
- [ ] Identity Center를 관리 계정에서 활성화하고 **위임 관리자**로 일상 운영을 옮겼다
- [ ] 관리자급 권한 세트의 **세션 지속 시간이 1시간**이다
- [ ] **액세스 포털 세션이 12시간 이하**다
- [ ] 권한 세트마다 **권한 경계**가 걸려 있다
- [ ] 할당이 **그룹 단위**이고, 권한 세트와 할당이 **IaC로 관리**된다
- [ ] `AWSReservedSSO_*` 역할 변조를 막는 **SCP가 적용**되어 있다
- [ ] 신규 IAM 사용자·액세스 키 생성을 막는 **SCP가 적용**되어 있고 브레이크글래스만 예외다
- [ ] 외부 IdP에 **SAML + SCIM 두 채널**이 모두 구성되어 있다
- [ ] IdP 그룹 **이름 규칙**이 문서로 확정되어 있고, **아이덴티티 소스가 초기에 확정**되었다
- [ ] SAML 서명 인증서 **만료 알람**이 걸려 있다
- [ ] 관리자 접근에 **FIDO2/패스키**를 요구하고 허용 MFA 유형에서 약한 방법을 제외했다
- [ ] 모든 사용자에 **백업 MFA 기기**가 등록되어 있다
- [ ] MFA 조건 키를 **`BoolIfExists`** 로 썼다
- [ ] **상시 관리자 권한 보유자 수**를 숫자로 답할 수 있다
- [ ] 관리자 권한이 **JIT 승격 + 명시적 승인**으로만 부여된다
- [ ] JIT 자동화 역할이 부여 가능한 **권한 세트가 화이트리스트로 고정**되어 있다
- [ ] **만료 처리 실패에 알람**이 걸려 있다
- [ ] 승격 이벤트와 브레이크글래스 사용에 **즉시 알람**이 걸려 있다
- [ ] 회수 트리거가 **퇴사·직무 변경·프로젝트 종료** 세 가지다
- [ ] 회수 절차에 **활성 세션 삭제**가 포함되어 있다
- [ ] **미사용 액세스 분석기**가 조직 단위로 켜져 있다
- [ ] 재검증이 **분기 주기**로 실행되고 증거가 남는다
- [ ] 특권 접근 재검증이 **긍정 확인**이다
- [ ] **비인간 아이덴티티**가 재검증 목록에 있다

## ⚠️ 자주 하는 실수

| 실수 | 결과 | 올바른 구성 |
|---|---|---|
| 계정마다 SAML 공급자와 역할을 만든다 | 계정 10개에 역할 수십 개 — 회수 시 어디를 지워야 할지 모름 | Identity Center로 조직에 한 번 구성 (9.1, 9.2) |
| SAML 신뢰 정책에 `SAML:aud` 조건이 없다 | 같은 IdP의 다른 용도 주장이 AWS 로그인에 재사용될 수 있음 | `SAML:aud`를 명시 (9.1) |
| 권한 세트 세션은 1시간인데 포털 세션이 7일이다 | IdP 계정을 막아도 7일간 새 자격 증명이 계속 발급됨 | 포털 세션 12시간 이하 + 활성 세션 삭제 (9.2, 9.6) |
| `AWSReservedSSO_*` 역할을 SCP로 보호하지 않는다 | 관리자가 역할에 뒷문을 만들어 할당 해제 후에도 접근 유지 | 변조 차단 SCP 적용 (9.2) |
| 할당을 개인에게 직접 한다 | 퇴사 시 그룹만 정리하고 개인 할당이 남음 | 그룹에만 할당 (9.2) |
| SAML만 붙이고 SCIM을 생략한다 | 퇴사자 계정·그룹 멤버십이 AWS에 남고, 사고 날 때까지 발견되지 않음 | SCIM 프로비저닝을 필수 구성으로 (9.3) |
| 전사 사용자를 전부 SCIM으로 밀어 넣는다 | 접근 권한 없는 사용자 수천 명 — 재검증 목록이 무의미해짐 | 동기화 범위를 필요한 그룹으로 (9.3) |
| SAML 인증서 만료를 관리하지 않는다 | 전 계정 로그인이 동시에 차단 | 만료 알람 + 브레이크글래스 준비 (9.3, 32.4) |
| 운영 중에 아이덴티티 소스를 바꾼다 | 기존 사용자·그룹 멤버십·계정 할당이 유지되지 않아 접근이 끊김 | 소스는 처음에 확정. 전환 시 할당 내보내기 + 재구성 계획 (9.3) |
| SMS MFA를 계속 쓴다 | SIM 복제·번호 이동으로 우회 — 원서가 명시적으로 폐기 권고 | FIDO2/패스키, 최소 TOTP (9.4) |
| TOTP만으로 관리자 접근을 보호한다 | 실시간 중계 피싱에 그대로 뚫림 | 관리자에는 패스키 요구 (9.4) |
| 허용 MFA 유형을 넓게 열어둔다 | "다른 방법을 시도해 보세요" 다운그레이드 공격이 성립 | 허용 유형을 좁히고 미등록 시 로그인 차단 (9.4) |
| MFA 기기를 하나만 등록한다 | 분실 시 계정 잠김 → 브레이크글래스 남용 | 백업 기기 등록 (9.4) |
| MFA 조건을 `Bool`로 쓴다 | 키가 없는 요청에서 조건이 매칭되지 않아 Deny가 통과 | `BoolIfExists` (9.4, 7.4) |
| 페더레이션 세션 MFA를 IAM 조건 키로 강제하려 한다 | 연동 방식에 따라 통제가 성립하지 않음 | IdP/Identity Center 설정에서 강제 (9.4) |
| 운영 인력 전원에게 `AdministratorAccess`를 상시 부여한다 | 자격 증명 하나 탈취 = 즉시 계정 장악, 관리자 활동이 소음에 묻힘 | JIT 승격 + 알람 (9.5) |
| JIT 자동화 역할에 제한을 두지 않는다 | 자동화가 새로운 최고 권한 주체가 되어 승인을 우회 | 권한 세트 화이트리스트 + 자기 변경 금지 (9.5) |
| 만료 처리 실패를 알람하지 않는다 | 부여만 성공하고 회수는 실패 — 조용히 상시 권한이 됨 | 회수 실패 알람 + 만료/실제 회수 시각 분리 기록 (9.5) |
| 세션 로그를 일반 로그와 같은 곳에 둔다 | 암호·키가 섞인 독성 로그가 넓게 노출 | 독성/살균 로그 분리, 열람 알람 (9.5, 29장) |
| 회수 트리거를 "퇴사"만으로 둔다 | 프로젝트 종료·직무 변경 시 권한이 그대로 누적 | 트리거 3종 정의 (9.6) |
| 사용자 삭제로 회수를 끝낸다 | 이미 발급된 포털·역할 세션이 만료까지 살아 있음 | 활성 세션 삭제까지 (9.6) |
| 재검증을 연 1회 설문으로만 한다 | "필요합니다"로 전부 회신 — 아무것도 정리되지 않음 | 미사용 액세스 분석기로 상시 탐지 + 긍정 확인 (9.6) |
| 승격이 3일 걸린다 | 사용자가 상시 권한을 내놓지 않음 — 재검증이 무력화 | 부여를 빠르게 만드는 것이 회수의 전제 (9.5, 9.6) |
| 비인간 아이덴티티를 재검증에서 뺀다 | 사람 통제는 훌륭하지만 자동화가 무제한 권한 보유(원서 경고) | 서비스 역할·CI 사용자·SaaS 역할 포함 (9.6) |
| 재검증 증거를 남기지 않는다 | 절차가 있어도 감사에서 없는 것으로 판정 | 검토자·일자·회수 건수 기록 (9.6) |

## 다음 장 예고

이 장까지가 **직원의 신원**입니다. 회사 IdP가 판정하고, Identity Center가 계정으로 나눠주고, 라이프사이클이 회수합니다.

10장은 상대를 바꿉니다. **고객의 신원** — ShopMini에 가입하는 수십만 명 — 은 회사 IdP에 없고, 인사 시스템도 퇴사를 알려주지 않습니다. 9.1에서 인용한 원서의 권고("암호 해시를 직접 저장하고 검증하지 마라")를 AWS에서 실현하는 서비스가 **Amazon Cognito**입니다. 사용자 풀과 자격 증명 풀의 차이, 가입·확인·인증 플로우의 세 가지 패턴, 그리고 클라이언트에 앱 시크릿을 두면 안 되는 이유를 다룹니다.
