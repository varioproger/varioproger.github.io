# 17장. 백업·복원력·랜섬웨어 대비

> **이 장에서 다루는 것**
> - **백업은 IT 운영 항목이 아니라 보안 통제다** 🔴 — CIA 삼요소에서 가용성·무결성 침해에 대응하는 마지막 방어선
> - 전통 **3-2-1 규칙의 클라우드 번역** — 매체 다양성 대신 실패 도메인 다양성, 오프사이트 대신 별도 계정, 논리적 에어갭
> - **AWS Backup 중앙화** 🧪 — 백업 계획·규칙·볼트, 태그 기반 리소스 할당, **백업 볼트 잠금**, 크로스 계정·크로스 리전 복사
> - **백업 계정 분리** 🔴 — 운영 계정 관리자가 백업을 지울 수 없는 구조. 볼트 접근 정책과 SCP

> - **복구 테스트** ⚠️ — 테스트하지 않은 백업은 백업이 아니다. RTO/RPO 검증과 복원 실패 4대 원인
>
> **선행 지식**: 13장(KMS·키 정책), 15장(S3 버전 관리·객체 잠금), 16장(스토리지 암호화·Vault Lock)
> **난이도**: ★★☆

3부의 12~16장은 한 방향의 질문에 답했습니다. **"공격자가 데이터를 읽지 못하게 하려면?"** — 분류하고(12장), 암호화하고(13·14장), 접근을 막고(15·16장).

이 장의 질문은 반대쪽입니다. **"공격자가 데이터를 읽는 대신 지워버리면?"**

기밀성 통제는 여기서 아무 도움이 되지 않습니다. 완벽하게 암호화되고, 퍼블릭 액세스가 차단되고, 최소 권한이 걸린 S3 버킷도 관리자 자격 증명 하나가 털리면 30초 만에 비워집니다. 그리고 그 순간, ShopMini의 복구 가능성은 **사고 이전에 만들어둔 백업이 어디에 있었는가** 하나로 결정됩니다.

## 17.1 백업은 보안 통제다 🔴

### 백업이 지키는 것은 기밀성이 아니다

*Practical Cloud Security* 2판은 데이터 자산 관리를 CIA 삼요소로 시작합니다.

> 📖 *Practical Cloud Security* 2판 2장: **"가장 널리 쓰이는 정보보안 모델 중 하나가 CIA 삼요소, 즉 기밀성·무결성·가용성이다. 데이터 기밀성을 침해하려는 위협 행위자는 데이터를 훔치려 하고, 대개 돈을 벌거나 당신을 곤란하게 만들기 위해서다. 데이터 무결성을 침해하려는 위협 행위자는 데이터를 바꾸려 한다 — 예를 들어 은행 잔고를 변조하는 식이다. (…) 데이터 가용성을 침해하려는 위협 행위자는 재미로 또는 돈을 위해 당신을 오프라인으로 만들거나, **랜섬웨어를 써서 당신의 파일을 암호화**하려 한다."**
>
> 그리고 각주에서 랜섬웨어의 성격을 정확히 규정합니다. **"랜섬웨어는 가용성 침해이면서 동시에 무결성 침해다. 데이터를 사용 불가능하게 만들기 위해 데이터에 대한 무단 변경을 사용하기 때문이다."**

이 분류가 실무에서 갖는 의미는 큽니다. 대부분의 보안 통제 목록 — IAM 정책, 암호화, 네트워크 격리, 로깅 — 은 **기밀성** 쪽으로 심하게 기울어 있습니다. 가용성과 무결성 침해에 대응하는 통제는 목록에서 잘 보이지 않고, 대개 "인프라 운영팀이 알아서 하는 것"으로 넘어갑니다.

**그 결과가 이것입니다: 백업 정책은 있는데 백업 정책의 소유자가 보안팀이 아니다.** 백업 주기와 보존 기간은 RDS 콘솔 기본값이고, 백업이 운영 계정 안에 있고, 누가 백업을 지울 수 있는지 아무도 모릅니다.

### 🔴 반드시 이렇게 구성하라

1. **백업을 보안 통제 목록에 등재하라.** 백업 계획·볼트·보존 기간·삭제 권한은 데이터 분류 등급(12.2)별 필수 통제 매트릭스의 한 행이어야 합니다. "가용성" 열이 비어 있는 매트릭스는 완성된 것이 아닙니다.
2. **백업의 위협 모델을 "디스크 고장"이 아니라 "관리자 자격 증명 탈취"로 두라.** 디스크 고장은 AWS가 이미 해결했습니다. 남은 위협은 사람과 자격 증명입니다.
3. **백업 삭제 권한을 백업 생성 권한과 분리하라.** 17.4에서 구조로 만듭니다.
4. **백업 자체를 기밀성 자산으로 취급하라.** 백업은 운영 데이터의 완전한 사본입니다. 접근 통제가 느슨한 백업은 **기밀성 우회 경로**가 됩니다. 실수로 퍼블릭 공유된 스냅샷 문제(16.7)가 정확히 이 유형입니다.

**하지 않았을 때의 결과는 단순합니다.** 사고 대응의 마지막 단계인 복구가 성립하지 않습니다.

> 📖 *Practical Cloud Security* 2판 7장 「Redeploying IT Systems」: **"IT 관점에서 복구하는 가장 단순하고 효과적인 방법은 영향받은 모든 시스템을 재배포하는 것이다. 이것 역시 클라우드에서 조금 더 쉬운데, 새 물리 하드웨어를 구매할 필요가 없고 클라우드 제공자에게 용량이 있기 때문이다. 침해된 클라우드 시스템은 모두 재생성되어야 하고, 운영 트래픽은 새 시스템으로 전환되어야 한다."** 저자는 여기에 에일리언의 대사를 덧붙입니다. **"궤도에서 사이트 전체를 핵으로 날려버려라. 그것이 확실한 유일한 방법이다."**

이 재배포 전략(34.5에서 절차로 다룹니다)은 **인프라는 코드로, 데이터는 백업으로** 되살린다는 전제 위에 있습니다. 인프라 쪽 절반은 IaC(28장)가 담당합니다. 데이터 쪽 절반이 없으면 "재배포"는 "재창업"이 됩니다.

| CIA 축 | 대표 위협 | 주 통제 | 이 책의 장 | 백업의 역할 |
|---|---|---|---|---|
| 기밀성 | 유출, 무단 열람 | 암호화, 접근 통제 | 13~16장 | 통제 대상 (백업도 유출 자산) |
| 무결성 | 변조, 암호화 공격 | 버전 관리, 객체 잠금, 로그 무결성 | 15.8~15.9, 29.3 | **변조 이전 시점 복원** |
| 가용성 | 삭제, 서비스 중단 | 다중 AZ, 다중 리전, **백업** | 17장 | **마지막 방어선** |

## 17.2 3-2-1 규칙의 클라우드 버전

전통적인 3-2-1 규칙은 이렇습니다. **사본 3개 · 매체 2종 · 오프사이트 1개.** 테이프와 물리 서버 시대의 규칙이지만, 규칙이 진짜로 말하는 것은 매체나 장소가 아니라 **"하나의 사고가 모든 사본을 동시에 죽일 수 없게 하라"** 입니다. 이 원칙을 클라우드 어휘로 번역하면 다음과 같습니다.

| 전통 3-2-1 | 원래 의도 | 클라우드 번역 | AWS 구현 |
|---|---|---|---|
| 사본 **3개** | 단일 사본 손실 대비 | 원본 + 로컬 백업 + 격리 사본 | 운영 리소스 + 운영 계정 볼트 + 백업 계정 볼트 |
| 매체 **2종** | 매체 고유 결함 회피 | **실패 도메인 2종** — 매체가 아니라 "같이 죽는 범위"가 달라야 함 | 서비스 스냅샷 + AWS Backup 볼트, 서로 다른 계정·리전 |
| 오프사이트 **1개** | 화재·수해 등 물리 재해 | **관리 경계 밖 1개** — 클라우드의 재해는 물리적이지 않다 | **별도 AWS 계정** + 별도 리전 |
| (추가) **불변 1개** | — | 권한이 있어도 지울 수 없는 사본 | 볼트 잠금 컴플라이언스 모드, 객체 잠금 |
| (추가) **오류 0** | — | 복원이 실제로 되는지 검증 | 복구 테스트 (17.6) |

핵심 전환은 두 번째 행입니다. **클라우드에서 "매체 다양성"은 거의 의미가 없습니다.** EBS 스냅샷도 S3 객체도 같은 AWS 스토리지 기반 위에 있습니다. 대신 물어야 할 질문은 이것입니다 — **"한 번의 사고로 동시에 사라지는 범위는 어디까지인가?"**

| 실패 도메인 | 무엇이 동시에 사라지는가 | 이것을 넘어서려면 |
|---|---|---|
| 리소스 | 그 인스턴스/버킷 하나 | 같은 계정 안의 백업으로 충분 |
| **IAM 권한 경계** | 그 자격 증명이 삭제 가능한 **모든 것** | **별도 계정** (17.4) |
| KMS 키 | 그 키로 암호화된 모든 데이터 (17.5) | 백업을 **다른 계정의 다른 키**로 암호화 |
| 리전 | 그 리전의 모든 리소스 | 크로스 리전 복사 (17.3) |
| 조직(Organizations) | 관리 계정이 침해되면 전부 | 볼트 잠금 컴플라이언스 모드, 조직 외부 사본 |

**"IAM 권한 경계"가 클라우드의 진짜 실패 도메인입니다.** 운영 계정 관리자 자격 증명이 탈취되면, 그 계정 안에서 리전을 나누든 서비스를 나누든 아무 소용이 없습니다. 같은 자격 증명이 전부 지울 수 있기 때문입니다.

그래서 클라우드에서 사본을 셀 때는 **"몇 개인가"가 아니라 "몇 개의 권한 경계에 걸쳐 있는가"** 를 세야 합니다. RDS 자동 백업 7일치, 수동 스냅샷 3개, 서울과 도쿄에 각각 복사본 — 전부 운영 계정 안에 있다면 **사본은 하나입니다.** 하나의 `AdministratorAccess`가 전부를 삭제할 수 있으므로, 실패 도메인 관점에서 이들은 서로 독립이 아닙니다. 3-2-1의 "3"을 만족시키는 것은 사본의 개수가 아니라 **삭제 권한자가 서로 다르다는 사실**입니다.

### 논리적 에어갭

물리 에어갭(air gap)은 백업 매체를 네트워크에서 물리적으로 분리하는 것입니다. 클라우드에는 뽑을 케이블이 없으므로, 대신 **권한으로 갭을 만듭니다.**

논리적 에어갭이 성립하려면 세 조건이 모두 필요합니다.

1. **다른 자격 증명 경계** — 운영 계정의 어떤 프린시펄도 백업을 삭제할 수 없다.
2. **단방향 경로** — 백업은 운영 → 백업 방향으로만 흐른다. 백업 계정에서 운영 계정으로 가는 상시 접근 경로는 없다.
3. **복구 시에만 열리는 문** — 복원은 승인된 절차와 별도 역할을 통해서만 일어난다.

> 💡 **원서 이후 변경** — AWS Backup은 **논리적 에어갭 볼트(logically air-gapped vault)** 를 별도 볼트 유형으로 제공합니다. 이 볼트는 생성 시점부터 볼트 잠금 컴플라이언스 모드가 적용되고, AWS 소유 키로 암호화되며(계정의 KMS 키 삭제와 운명을 함께하지 않습니다 — 17.5의 시나리오에서 중요합니다), AWS RAM으로 다른 계정에 공유해 **원본 계정이 완전히 소실된 상태에서도** 복구 계정에서 직접 복원할 수 있습니다. 생성은 `aws backup create-logically-air-gapped-backup-vault`로, 최소·최대 보존 기간이 필수 인자입니다. 다만 지원 리소스 유형과 리전이 일반 볼트보다 좁으므로 도입 전 확인이 필요합니다.

## 17.3 AWS Backup 중앙화 🧪

각 서비스마다 백업 기능이 따로 있습니다 — EBS 스냅샷, RDS 자동 백업, DynamoDB PITR, EFS 백업. 이것을 서비스별로 관리하면 **"모든 운영 리소스가 백업되고 있는가"** 라는 질문에 답할 수 없습니다. AWS Backup은 이 질문에 답할 수 있게 만드는 서비스입니다.

### 구성 요소

| 구성 요소 | 역할 | 어디에 만드는가 |
|---|---|---|
| **백업 볼트(Vault)** | 복구 지점(recovery point)을 담는 컨테이너. KMS 키와 접근 정책의 단위 | 운영 계정 + **백업 계정** 양쪽 |
| **백업 계획(Plan)** | 규칙의 묶음 | 운영 계정 (또는 조직 백업 정책으로 배포) |
| **규칙(Rule)** | 일정, 대상 볼트, 보존 기간, **복사 동작(CopyActions)** | 계획 안 |
| **선택(Selection)** | 어떤 리소스를 이 계획에 넣을지 — **태그 조건** 또는 ARN 목록 | 계획에 연결 |
| **볼트 잠금(Vault Lock)** | 볼트의 보존 정책을 불변으로 고정 | 백업 계정 볼트에 **필수** |

### 볼트 생성과 백업 계획

```bash
# [운영 계정 111122223333] 로컬 볼트 — 고객 관리형 KMS 키로 암호화
aws backup create-backup-vault \
  --backup-vault-name shopmini-prod-vault \
  --encryption-key-arn arn:aws:kms:ap-northeast-2:111122223333:key/1234abcd-12ab-34cd-56ef-1234567890ab \
  --backup-vault-tags Project=awssec-lab,Chapter=ch17 \
  --profile awssec-lab --region ap-northeast-2
```

```json
{
  "BackupPlanName": "shopmini-prod-daily",
  "Rules": [
    {
      "RuleName": "daily-35d-with-cross-account-copy",
      "TargetBackupVaultName": "shopmini-prod-vault",
      "ScheduleExpression": "cron(0 17 * * ? *)",
      "ScheduleExpressionTimezone": "Asia/Seoul",
      "StartWindowMinutes": 60,
      "CompletionWindowMinutes": 720,
      "EnableContinuousBackup": false,
      "Lifecycle": {
        "DeleteAfterDays": 35
      },
      "RecoveryPointTags": {
        "Project": "awssec-lab",
        "DataClass": "confidential"
      },
      "CopyActions": [
        {
          "DestinationBackupVaultArn": "arn:aws:backup:ap-northeast-1:777788889999:backup-vault:shopmini-archive-vault",
          "Lifecycle": {
            "MoveToColdStorageAfterDays": 90,
            "DeleteAfterDays": 730
          }
        }
      ]
    }
  ]
}
```

```bash
aws backup create-backup-plan --backup-plan file://plan.json \
  --profile awssec-lab --region ap-northeast-2
```

이 한 규칙이 3-2-1의 세 요소를 동시에 만듭니다. `TargetBackupVaultName`이 로컬 사본, `CopyActions`의 목적지가 **계정도 리전도 다른** 격리 사본입니다. 목적지를 `ap-northeast-1`(도쿄)로 둔 것은 서울 리전 전체 장애를 실패 도메인에서 빼기 위해서입니다.

> ⚠️ `Lifecycle.DeleteAfterDays`는 `MoveToColdStorageAfterDays`보다 최소 90일 이상 커야 합니다. 콜드 스토리지로 전환된 복구 지점에는 최소 90일 보관 제약이 있어, 이 조건을 어기면 계획 생성 자체가 실패합니다.

### 태그 기반 리소스 할당

리소스를 ARN으로 하나씩 등록하면 새로 만든 리소스는 영원히 백업되지 않습니다. **태그 조건으로 걸어야 합니다.**

```json
{
  "SelectionName": "backup-tagged-resources",
  "IamRoleArn": "arn:aws:iam::111122223333:role/service-role/AWSBackupDefaultServiceRole",
  "Resources": ["*"],
  "Conditions": {
    "StringEquals": [
      { "ConditionKey": "aws:ResourceTag/Backup", "ConditionValue": "daily" }
    ],
    "StringNotEquals": [
      { "ConditionKey": "aws:ResourceTag/Environment", "ConditionValue": "dev" }
    ]
  }
}
```

```bash
aws backup create-backup-selection \
  --backup-plan-id "$PLAN_ID" \
  --backup-selection file://selection.json \
  --profile awssec-lab --region ap-northeast-2
```

이 구조는 12.3의 태깅 전략과 직결됩니다. **`Backup` 태그를 붙이지 않으면 백업되지 않으므로, 태그 강제(Tag Policy + SCP)가 곧 백업 커버리지 보장이 됩니다.** 반대 방향의 감시도 필요합니다 — AWS Backup Audit Manager의 `BACKUP_RESOURCES_PROTECTED_BY_BACKUP_PLAN` 통제는 "어떤 백업 계획에도 속하지 않은 리소스"를 상시 검출합니다.

### 백업 볼트 잠금

볼트 잠금은 **볼트의 보존 정책을 정책으로 고정**해, 그 안의 복구 지점을 조기 삭제할 수 없게 만듭니다.

```bash
# [로그 아카이브 계정 777788889999] 컴플라이언스 모드 잠금
aws backup put-backup-vault-lock-configuration \
  --backup-vault-name shopmini-archive-vault \
  --min-retention-days 35 \
  --max-retention-days 2555 \
  --changeable-for-days 3 \
  --region ap-northeast-1
```

| 항목 | 거버넌스(Governance) 모드 | 컴플라이언스(Compliance) 모드 |
|---|---|---|
| 지정 방법 | `--changeable-for-days` **생략** | `--changeable-for-days` 지정 (최소 3일) |
| 해제 가능 여부 | `backup:DeleteBackupVaultLockConfiguration` 권한자가 언제든 해제 | **유예 기간 종료 후 누구도 해제 불가** |
| AWS 지원팀 개입 | 해당 없음 | **불가능** — 계정을 닫아도 보존 기간까지 유지 |
| 용도 | 실수 방지, 내부 통제 | **랜섬웨어·내부자 방어, 규제 대응** |

**유예 기간(`--changeable-for-days`)의 의미를 정확히 이해해야 합니다.** 잠금을 건 시점부터 이 일수가 지나기 전까지는 설정을 바꾸거나 해제할 수 있지만, 지나면 **되돌릴 방법이 존재하지 않습니다.** 최소 보존 기간을 3,650일로 잘못 입력하고 유예 기간을 넘기면 그 볼트의 모든 복구 지점을 10년간 보관하며 비용을 내야 합니다.

> 🔴 **컴플라이언스 모드는 반드시 개발 계정에서 짧은 값(`--min-retention-days 7 --changeable-for-days 3`)으로 한 번 리허설한 뒤 운영에 적용하십시오.** 그리고 잠금을 걸기 전에 `aws backup describe-backup-vault`로 설정을 다시 읽어 확인하십시오.

> ⚠️ **16.5의 S3 Glacier Vault Lock과 이름이 비슷하지만 다른 기능입니다.** Glacier Vault Lock은 S3 Glacier 볼트에 불변 **접근 정책**(예: `glacier:ArchiveAgeInDays` 조건으로 1년 미만 아카이브 삭제 거부)을 고정하는 것이고, AWS Backup 볼트 잠금은 AWS Backup 볼트의 **보존 기간 범위**를 고정하는 것입니다. 두 서비스를 섞어 문서화하면 감사에서 반드시 지적받습니다.

### 조직 단위 중앙화

계정마다 사람이 계획을 만들면 반드시 빠지는 계정이 생깁니다. AWS Organizations의 **백업 정책(backup policy)** 으로 배포하십시오.

```bash
# [관리 계정 123456789012]
aws organizations enable-policy-type \
  --root-id "$ROOT_ID" --policy-type BACKUP_POLICY

# 백업 계정을 위임 관리자로 등록
aws organizations register-delegated-administrator \
  --account-id 777788889999 \
  --service-principal backup.amazonaws.com

# 크로스 계정 백업·복사 활성화
aws backup update-global-settings \
  --global-settings isCrossAccountBackupEnabled=true
```

백업 정책은 OU에 붙으며, 하위 계정에 백업 계획을 자동 생성합니다. **하위 계정 관리자는 조직이 배포한 계획을 수정하거나 삭제할 수 없습니다** — 이것이 17.4로 이어지는 첫 번째 구조적 장치입니다.

## 17.4 백업 계정 분리 🔴

### 원서가 두 번 강조하는 것

*Practical Cloud Security*는 로그와 백업에 대해 **같은 구조**를 요구합니다. 먼저 로그 쪽에서 원칙을 세우고,

> 📖 *Practical Cloud Security* 1판·2판 7장은 과거에 중요한 로그를 종이로 인쇄해 물리적으로 안전한 장소로 보냈다는 이야기를 한 뒤 이렇게 잇습니다. **"클라우드에서는 로그 집계 서비스를 별도의 클라우드 계정에 다른 관리 자격 증명으로 두는 것만으로 같은 이점 대부분을 훨씬 쉽게 얻을 수 있다. 주 시스템에 접근 권한이 있는 사람이 로그를 지워버릴 수 없게 되기 때문이다. (이것은 뒤에서 다룰 백업에도 마찬가지로 좋은 생각이다.)"**

같은 장 뒤쪽에서 백업으로 돌아와 못을 박습니다.

> 📖 *Practical Cloud Security* 2판 7장: **"사고 대응 계획의 일부에는 데이터와 기능을 복원하는 데 사용할 수 있는 백업을 갖추는 것이 포함되어야 한다. 백업이 운영 데이터와 **분리된 클라우드 계정, 분리된 관리 자격 증명**으로 되어 있는지 확인하라. 공격자가 운영 데이터뿐 아니라 **운영 계정에서 접근 가능한 모든 백업까지 함께 지워버린 사례들이 문서화되어 있다.**"**

마지막 문장이 이 절의 전부입니다. **공격자는 백업을 지운 다음에 데이터를 지웁니다.** 백업이 운영 계정 안에 있다면, 그것은 백업이 아니라 "지워질 순서가 첫 번째인 데이터"입니다.

### 🔴 반드시 이렇게 구성하라

1. **백업 사본의 최종 목적지를 운영 계정 밖에 두라.** ShopMini 기준으로 로그 아카이브 계정(`777788889999`) 또는 전용 백업 계정입니다.
2. **운영 계정의 어떤 역할에도 목적지 볼트에 대한 삭제 권한을 주지 마라.** 크로스 계정 복사는 `backup:CopyIntoBackupVault` **쓰기 전용 경로**입니다.
3. **목적지 볼트에 컴플라이언스 모드 잠금을 걸어라.** 백업 계정 관리자조차 조기 삭제할 수 없게 만듭니다.
4. **목적지 볼트의 KMS 키를 백업 계정이 소유하게 하라.** 운영 계정의 키 관리자가 키를 삭제 예약해도 백업은 살아남아야 합니다(17.5).
5. **복구 경로를 별도 역할로 분리하고, 그 역할의 사용을 즉시 경보하라.** 브레이크 글래스 절차(32.4)와 같은 패턴입니다.

### 목적지 볼트 접근 정책

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowCopyIntoVaultFromOrganization",
      "Effect": "Allow",
      "Principal": { "AWS": "*" },
      "Action": "backup:CopyIntoBackupVault",
      "Resource": "*",
      "Condition": {
        "StringEquals": { "aws:PrincipalOrgID": "o-exampleorgid" }
      }
    },
    {
      "Sid": "DenyDeletionExceptBackupBreakGlass",
      "Effect": "Deny",
      "Principal": { "AWS": "*" },
      "Action": [
        "backup:DeleteRecoveryPoint",
        "backup:UpdateRecoveryPointLifecycle",
        "backup:DeleteBackupVault",
        "backup:PutBackupVaultAccessPolicy",
        "backup:DeleteBackupVaultAccessPolicy",
        "backup:DeleteBackupVaultLockConfiguration"
      ],
      "Resource": "*",
      "Condition": {
        "ArnNotEquals": {
          "aws:PrincipalArn": "arn:aws:iam::777788889999:role/BackupBreakGlassRole"
        }
      }
    }
  ]
}
```

```bash
aws backup put-backup-vault-access-policy \
  --backup-vault-name shopmini-archive-vault \
  --policy file://vault-policy.json --region ap-northeast-1
```

첫 번째 문장이 운영 계정의 복사를 받아들이고, 두 번째 문장이 **백업 계정 자신을 포함한 모든 프린시펄**의 삭제를 막습니다.

> ⚠️ **`backup:DeleteBackupVaultAccessPolicy`를 Deny 목록에 넣을 때는 예외 프린시펄이 실제로 존재하고 사용 가능한지 먼저 확인하십시오.** 예외 ARN에 오타가 있으면 정책을 지울 수 있는 프린시펄이 하나도 남지 않고, 볼트 접근 정책은 그 상태로 고정됩니다. 이 JSON을 적용하기 전에 반드시 `aws sts assume-role`로 `BackupBreakGlassRole`을 실제로 맡아보십시오.

### 운영 계정 SCP

볼트 접근 정책은 목적지 쪽 방어이고, SCP는 출발지 쪽 방어입니다. 두 개를 다 걸어야 합니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyBackupDestruction",
      "Effect": "Deny",
      "Action": [
        "backup:DeleteRecoveryPoint",
        "backup:DeleteBackupVault",
        "backup:DeleteBackupVaultAccessPolicy",
        "backup:DeleteBackupVaultLockConfiguration",
        "backup:UpdateRecoveryPointLifecycle",
        "backup:DeleteBackupPlan",
        "backup:DeleteBackupSelection",
        "backup:PutBackupVaultAccessPolicy",
        "backup:StopBackupJob",
        "backup:DisassociateRecoveryPoint"
      ],
      "Resource": "*",
      "Condition": {
        "ArnNotLike": {
          "aws:PrincipalArn": "arn:aws:iam::*:role/OrgBackupAdminRole"
        }
      }
    },
    {
      "Sid": "DenyKeyDestruction",
      "Effect": "Deny",
      "Action": [
        "kms:ScheduleKeyDeletion",
        "kms:DisableKey",
        "kms:DisableKeyRotation",
        "kms:PutKeyPolicy"
      ],
      "Resource": "*",
      "Condition": {
        "ArnNotLike": {
          "aws:PrincipalArn": "arn:aws:iam::*:role/OrgKeyAdminRole"
        }
      }
    }
  ]
}
```

두 번째 문장의 이유는 17.5에서 설명합니다. SCP는 **계정의 루트 사용자에게도 적용되므로**, 운영 계정 관리자 자격 증명이 전부 탈취되어도 이 두 문장은 유지됩니다(관리 계정 자체가 침해되지 않는 한).

> ⚠️ **`ArnNotLike`로 예외를 두는 SCP에는 자기 무력화 경로가 있습니다.** 운영 계정에 IAM 역할 생성 권한이 있는 공격자는 `OrgBackupAdminRole`이라는 **이름의 역할을 스스로 만들어** 예외를 통과할 수 있습니다. 이것을 막으려면 예외 역할 이름 패턴에 대한 `iam:CreateRole`·`iam:PutRolePolicy`·`iam:AttachRolePolicy`·`iam:UpdateAssumeRolePolicy`를 같은 SCP에서 **함께 Deny** 해야 합니다. 예외를 두는 모든 SCP에 공통으로 적용되는 원칙입니다(37장에서 가드레일 패턴으로 다시 다룹니다).

> 🔴 여기에 더해 `ec2:DeleteSnapshot`, `rds:DeleteDBClusterSnapshot`, `rds:DeleteDBSnapshot`, `dynamodb:DeleteBackup`처럼 **서비스 고유의 스냅샷 삭제 액션**도 함께 통제하십시오. AWS Backup으로 중앙화했다고 해서 서비스별 스냅샷이 사라지는 것은 아닙니다.

**이 구조를 만들지 않으면 어떻게 되는가.** 운영 계정 관리자 역할 하나가 탈취되는 순간 — 피싱, 노출된 액세스 키, 침해된 CI 러너 어느 경로든 — RDS 스냅샷·EBS 스냅샷·AWS Backup 복구 지점이 API 호출 몇 번으로 전부 사라집니다. 그 다음 데이터가 암호화됩니다. **탐지가 아무리 빨라도 되돌릴 대상이 없습니다.**

## 17.5 랜섬웨어 시나리오 대비

### 클라우드 랜섬웨어의 실제 흐름

클라우드 랜섬웨어는 워크스테이션 랜섬웨어와 다릅니다. 악성코드가 파일을 하나씩 암호화하는 대신, **API를 호출합니다.**

| 단계 | 공격자의 행동 | 남는 흔적 | 이 책의 대응 장 |
|---|---|---|---|
| 1. 초기 접근 | 액세스 키 유출, 피싱, 침해된 CI 파이프라인 | CloudTrail 비정상 발신지, 신규 UserAgent | 6~9장, 27장 |
| 2. 정찰 | `ListBuckets`, `DescribeDBSnapshots`, `ListBackupVaults` | 짧은 시간의 대량 List/Describe | 31장 |
| 3. 권한 상승·지속성 | 신규 IAM 사용자·역할·키 생성 | `CreateUser`, `CreateAccessKey`, `AttachRolePolicy` | 7장, 31장 |
| 4. **백업 무력화** | 스냅샷·복구 지점 삭제, 버전 관리 중단, **KMS 키 삭제 예약** | `DeleteRecoveryPoint`, `PutBucketVersioning`, `ScheduleKeyDeletion` | **17.3~17.4** |
| 5. 파괴·암호화 | 객체 삭제, 자체 키로 재암호화(SSE-C), DB 인스턴스 삭제 | `DeleteObjects`, `PutObject`(SSE-C), `DeleteDBInstance` | 15장, 16장 |
| 6. 협박 | 몸값 요구 | — | 32.2, 33.6 |

**4단계가 이 장의 표적입니다.** 4단계를 실패하게 만들면 5단계는 여전히 아프지만 회복 가능한 사고가 됩니다. 4단계가 성공하면 5단계는 곧 폐업입니다.

### ⚠️ KMS 키 삭제 예약 시나리오

#### 사고 시나리오

ShopMini의 CI 파이프라인에서 장기 액세스 키가 유출되었습니다. 그 키에 붙은 역할은 배포용이었지만 `AdministratorAccess`가 붙어 있었습니다. 공격자는 데이터를 지우지 않았습니다. 대신 **세 개의 API를 호출하고 사라졌습니다.**

```bash
# 공격자가 실행한 것 (재현 금지)
aws kms schedule-key-deletion --key-id alias/shopmini/app --pending-window-in-days 7
aws kms disable-key           --key-id alias/shopmini/app
# 그리고 운영 계정 볼트의 복구 지점 전체에 대해
aws backup delete-recovery-point --backup-vault-name shopmini-prod-vault \
  --recovery-point-arn "$RP_ARN"
```

아무 데이터도 삭제되지 않았고, 서비스는 정상 동작했습니다(이미 발급된 데이터 키가 캐시되어 있었기 때문입니다). 7일 뒤 새벽, RDS 인스턴스가 정지하고 S3 객체가 읽히지 않으며 EBS 볼륨이 마운트되지 않습니다. **암호문은 전부 그대로 있지만 복호화할 방법이 사라졌습니다.**

#### 원인

공격자는 원서가 정당한 데이터 파기 기법으로 설명하는 것을 그대로 무기로 썼습니다.

> 📖 *Practical Cloud Security* 2판 2장 「Cryptographic erasure」: **"대량의 데이터를 확실하게 파기하는 것은 사실 어렵다. 데이터를 완전히 덮어쓰는 데는 시간이 오래 걸리고, 그렇게 해도 다른 사본이 남아 있을 수 있다. 우리는 이것을 암호학적 소거로 해결할 수 있다. (…) 데이터를 복구 불가능하게 만들고 싶을 때 KMS에서 키 암호화 키를 지우거나 접근을 취소하면, 그 키 암호화 키로 '래핑된' 모든 데이터 키가 세상 어디에 있든 쓸모없게 된다. (…) 다중 테라바이트 파일을 256비트 키 하나를 덮어쓰는 것만으로 사실상 복구 불가능하게 만들 수 있다."**

**공격자에게 이것은 "테라바이트를 지우지 않고 테라바이트를 파괴하는" 가장 효율적인 경로입니다.** 그리고 13.11에서 다룬 삭제 대기 기간(7~30일)이 방어 시간을 주는 동시에, 아무도 보지 않으면 **7일간 조용히 익어가는 시한폭탄**이 됩니다.

세 가지가 겹쳐 사고가 됐습니다. **첫째,** 배포 역할에 `kms:ScheduleKeyDeletion`이 있었습니다. **둘째,** `ScheduleKeyDeletion` 호출에 아무 경보가 없었습니다. **셋째** — 가장 중요한 —**백업이 같은 키로 암호화되어 있었습니다.** 백업이 살아남았더라도 복호화할 수 없었을 것입니다.

#### 올바른 구성

| 통제 | 구체적 구성 |
|---|---|
| 권한 축소 | 키 정책에서 `kms:ScheduleKeyDeletion`·`kms:PutKeyPolicy`를 전용 키 관리자에게만. 배포 역할에는 `Encrypt`/`Decrypt`/`GenerateDataKey`만 (13.4) |
| SCP | 17.4의 `DenyKeyDestruction` 문장 — 루트 사용자에게도 적용 |
| 대기 기간 | `--pending-window-in-days 30` 을 기본으로. 짧게 예약하는 시도 자체를 조건 키로 통제 |
| **탐지** | `ScheduleKeyDeletion`·`DisableKey`·`PutKeyPolicy`에 대한 EventBridge 규칙 → **P1 즉시 호출** |
| **키 분리** | 백업 계정 볼트는 **백업 계정 소유 키**로 암호화. 논리적 에어갭 볼트는 AWS 소유 키 사용 |
| 되돌리기 | 대기 기간 중에는 `kms:CancelKeyDeletion`으로 복구 가능. 플레이북에 명시 (32.2) |

```json
{
  "source": ["aws.kms"],
  "detail-type": ["AWS API Call via CloudTrail"],
  "detail": {
    "eventSource": ["kms.amazonaws.com"],
    "eventName": [
      "ScheduleKeyDeletion",
      "DisableKey",
      "DisableKeyRotation",
      "PutKeyPolicy",
      "DeleteAlias"
    ]
  }
}
```

> 🔴 **이 경보는 "확인 후 처리" 대상이 아니라 즉시 호출 대상입니다.** 정상 운영에서 운영 계정의 KMS 키가 삭제 예약되는 일은 거의 없습니다. 오탐 몇 건을 감수하고 최고 심각도로 두십시오.

### 방어 조합표

랜섬웨어 방어는 단일 통제가 아니라 **각 단계를 막는 통제의 조합**입니다. 개별 기능은 15·16장에서 다뤘으므로, 여기서는 조합 관점으로 정리합니다.

| 통제 | 무엇을 막는가 | 못 막는 것 | 상세 |
|---|---|---|---|
| **S3 버전 관리** | 덮어쓰기·단순 삭제(삭제 마커만 생성) | 버전 지정 삭제(`DeleteObjectVersion`), 버전 관리 중단 | 15.8 |
| **MFA Delete** | 버전 지정 삭제, 버전 관리 중단 | 루트 MFA 자체가 탈취되면 무력. 루트 자격 증명 필요라 자동화 불가 | 15.8 |
| **S3 객체 잠금(컴플라이언스)** | 보존 기간 내 **모든** 삭제·덮어쓰기 | 신규 객체 추가(비용 공격), 버킷 자체가 아닌 계정 수준 위협 | 15.9 |
| **AWS Backup 볼트 잠금** | 복구 지점 조기 삭제, 보존 기간 단축 | 백업 계획 자체가 꺼진 경우 | 17.3 |
| **별도 계정** | 운영 계정 자격 증명으로 하는 **모든** 삭제 | 조직 관리 계정 침해 | 17.4 |
| **별도 리전** | 리전 단위 장애·삭제 | 자격 증명 기반 공격(리전은 권한 경계가 아님) | 17.3 |
| **KMS 키 분리** | 운영 키 삭제로 인한 백업 동반 사망 | 백업 계정 키 관리 실패 | 17.5 |
| **GuardDuty 탐지** | 4단계 진입을 **알려줌** | 막지는 못함 — 조합의 눈이지 벽이 아님 | 31장 |
| **CloudTrail 로그(별도 계정)** | 사후 재구성 가능성 | 실시간 차단 | 29.9 |

**표에서 읽어야 할 것은 "못 막는 것" 열입니다.** 어떤 한 줄도 단독으로는 4단계를 막지 못합니다. 실무에서 흔한 실패는 "S3 버전 관리를 켰으니 랜섬웨어는 대비됐다"는 판단입니다 — 버전 관리는 **`DeleteObjectVersion` 권한이 있는 공격자 앞에서 아무 저항도 하지 않습니다.**

ShopMini의 최소 조합은 이렇습니다.

```text
shopmini-uploads (운영 계정)
  ├─ 버전 관리 ON + 객체 잠금(거버넌스, 30일)      ← 실수·단순 삭제
  ├─ 복제 → shopmini-uploads-vault (백업 계정, 객체 잠금 컴플라이언스 90일)
  └─ CloudTrail 데이터 이벤트 → 로그 계정          ← 사후 추적

RDS / EBS (운영 계정)
  ├─ AWS Backup 일 1회 → 운영 볼트 (35일)          ← 빠른 복구
  └─ CopyActions → 백업 계정 볼트 (도쿄, 볼트 잠금 컴플라이언스, 730일)
                                                    ← 랜섬웨어 방어선

KMS
  ├─ 운영: alias/shopmini/app (운영 계정 소유)
  └─ 백업: 백업 계정 소유 키 — 운영 계정에서 삭제 예약 불가
```

### 탐지: 4단계에서 울려야 하는 것

GuardDuty(31.1)에서 이 흐름과 직접 관련되는 탐지 유형은 다음과 같습니다.

| GuardDuty 탐지 유형 | 대응하는 단계 |
|---|---|
| `CredentialAccess:IAMUser/AnomalousBehavior` | 1~2단계 — 탈취된 자격 증명의 이상 행동 |
| `Discovery:S3/AnomalousBehavior` | 2단계 — 대량 정찰 |
| `Impact:S3/AnomalousBehavior.Delete` | 5단계 — 비정상 대량 삭제 |
| `Impact:S3/AnomalousBehavior.Permission` | 4단계 — 버킷 정책·ACL 변경 |
| `Impact:IAMUser/AnomalousBehavior` | 4~5단계 — 파괴적 API 호출 패턴 |

여기에 CloudTrail 기반 자체 경보를 반드시 더하십시오. GuardDuty가 학습 기반이라 **초기 며칠은 조용할 수 있고**, `backup:DeleteRecoveryPoint`나 `kms:ScheduleKeyDeletion` 같은 결정적 이벤트에는 전용 규칙이 더 빠릅니다.

> 랜섬웨어 사고 발생 후의 **대응 절차**(격리, 통신, 몸값 지불 여부 판단)는 32.2의 플레이북과 33장에서 다룹니다. 이 장의 범위는 **사고 전에 만들어두어야 복구가 가능해지는 구조**입니다.

## 17.6 복구 테스트 ⚠️

### 사고 시나리오

ShopMini 팀은 17.3~17.5를 모두 구성했습니다. 백업 계정, 크로스 리전 복사, 컴플라이언스 모드 볼트 잠금까지 있었고, AWS Backup 대시보드는 14개월간 초록색이었습니다.

실제 사고가 났습니다. 운영 계정에서 RDS 인스턴스가 삭제되었고, 팀은 도쿄 리전 백업 계정 볼트에서 복원을 시작했습니다.

- **1시간차** — `start-restore-job`이 `AccessDenied`로 실패합니다. 복원 역할에 `iam:PassRole`이 없었습니다. 계정에 IAM 변경 권한이 있는 사람이 휴가 중이었습니다.
- **4시간차** — 권한을 고치고 재시도. 이번엔 KMS 오류. 복구 지점은 백업 계정 키로 암호화되어 있는데, 복원 대상 계정에서 그 키를 쓸 권한이 없었습니다.
- **9시간차** — 복원 성공. 그런데 애플리케이션이 뜨지 않습니다. **DB 서브넷 그룹과 파라미터 그룹이 도쿄 리전에 없었습니다.** 이것들은 백업 대상이 아니었습니다.
- **14시간차** — 서비스 재개. 계약상 RTO는 4시간이었습니다.

### 원인: 복원 실패의 4대 유형

| 유형 | 증상 | 근본 원인 | 사전 검증 방법 |
|---|---|---|---|
| **권한 부족** | `AccessDenied`, `iam:PassRole` 오류 | 복원 역할이 복원 시점에 처음 사용됨 | 분기 복구 훈련에서 **실제 그 역할로** 복원 |
| **KMS 키 접근 불가** | `KMSKeyNotAccessibleFault`, 복호화 실패 | 키 정책에 복원 대상 계정 프린시펄 없음, 리전 불일치 | 크로스 계정 복원 리허설 (13.10의 3중 확인) |
| **스냅샷 암호화 키 미공유** | 크로스 계정 복사 자체가 실패 | AWS 관리형 키로 암호화된 스냅샷은 공유 불가 | 백업 대상 리소스를 **고객 관리형 키**로 암호화 (16.1) |
| **의존 리소스 누락** | 복원은 성공, 애플리케이션은 기동 실패 | 서브넷 그룹·파라미터 그룹·보안 그룹·시크릿·DNS는 백업 대상이 아님 | 대상 리전에 IaC로 상시 유지 (28장) |

여기에 다섯 번째, 원서가 별도로 지적하는 유형이 있습니다 — **시간.**

> 📖 *Practical Cloud Security* 2판 7장: **"복원이 얼마나 오래 걸릴지 이해하는 것도 중요하다. 때로는 완벽하게 합리적인 복구 전략을 갖고 있는데, 다만 그것이 온 세상이 일주일간 멈춰 있기를 요구하는 경우가 있다. 복구가 진행되는 동안 100%로 기능할 필요는 없다 — 청구서 발송을 늦추거나 나중에 IT 시스템에 입력할 내용을 손으로 적어두는 것은 완벽히 합리적일 수 있다. 하지만 핵심 업무 기능은 수행할 수 있어야 한다."**

**"백업이 있다"와 "정해진 시간 안에 복구된다"는 완전히 다른 명제입니다.** 콜드 스토리지로 전환된 복구 지점은 복원 전 해동에 수 시간이 걸리고, 수 TB짜리 크로스 리전 복사본은 전송 자체가 수 시간입니다. 이 시간을 계약과 대조하지 않으면 RTO는 숫자 놀음입니다.

### RTO/RPO를 백업 규칙으로 번역하기

| 용어 | 정의 | 백업 설계로의 번역 |
|---|---|---|
| **RPO** (Recovery Point Objective) | 허용 가능한 **데이터 손실 시간** | 백업 **주기**를 결정. RPO 15분 → 일 1회 스냅샷으로는 불가능, 지속적 백업(PITR) 필요 |
| **RTO** (Recovery Time Objective) | 허용 가능한 **복구 소요 시간** | 백업 **저장 계층·위치**를 결정. RTO 4시간 → 콜드 스토리지 사본만으로는 불가능 |

ShopMini에 적용하면 이렇게 갈라집니다.

| 데이터 | RPO | RTO | 구성 |
|---|---|---|---|
| RDS 주문 데이터 | 5분 | 2시간 | 지속적 백업(`EnableContinuousBackup: true`) + 동일 리전 볼트. 크로스 계정 사본은 **2차 방어선** |
| S3 사용자 업로드 | 15분 | 8시간 | 버전 관리 + 크로스 계정 복제 |
| S3 정적 자산 | 24시간 | 24시간 | 일 1회 백업. IaC로 재생성 가능하므로 우선순위 낮음 |
| EC2 앱 서버 | — | 30분 | **백업 대상 아님.** IaC + AMI로 재배포 (34.5) |

마지막 행이 중요합니다. **모든 것을 백업하려 들면 RTO가 무너집니다.** 코드에서 재생성 가능한 것은 백업하지 말고 재배포하십시오. 백업은 **재생성이 불가능한 상태**에만 쓰는 자원입니다.

### 복구 훈련 절차

원서는 사고 대응 계획 전반에 대해 훈련을 권합니다.

> 📖 *Practical Cloud Security* 2판 7장: **"아직 사고 대응 계획을 테스트해볼 기회가 없었다면, 테이블탑 훈련을 해보는 것을 고려하라. 그럴듯한 시나리오를 만들어 테스트 환경에서 실행해보는 방식으로 사내에서 할 수 있다."**

백업에 관한 한 테이블탑으로는 부족합니다. **실제로 복원해야 합니다.** 분기 1회 이상, 다음 순서로 진행하십시오.

1. **무작위 선택** — 대상 복구 지점을 담당자가 고르지 않고 무작위로 뽑습니다. "잘 되는 것"을 고르면 훈련의 의미가 없습니다.
2. **평시 권한으로 시작** — 훈련용 임시 권한을 미리 주지 마십시오. 권한 부족이야말로 가장 흔한 실패 원인이고, 훈련은 그것을 발견하기 위한 것입니다.
3. **격리 계정으로 복원** — 운영에 영향을 주지 않는 별도 계정/VPC로 복원합니다(34.3의 포렌식 환경과 같은 패턴).
4. **데이터 검증** — 복원된 DB에서 실제 쿼리를 돌려 행 수와 최신 레코드 타임스탬프를 확인합니다. **"복원 작업 성공"은 데이터가 온전하다는 증거가 아닙니다.**
5. **시간 기록** — 각 단계 소요 시간을 기록하고 RTO와 대조합니다. 이 숫자가 다음 분기의 개선 목표입니다.
6. **정리** — 복원된 리소스를 삭제합니다(`AutoDelete=true` 태그).

> 💡 **원서 이후 변경** — AWS Backup은 이 과정을 자동화하는 **복원 테스트(restore testing)** 를 제공합니다. 일정에 따라 복구 지점을 자동 복원하고, 성공 여부와 소요 시간을 기록한 뒤 정리까지 수행합니다.

```bash
aws backup create-restore-testing-plan --restore-testing-plan '{
  "RestoreTestingPlanName": "shopmini_monthly_restore_test",
  "ScheduleExpression": "cron(0 2 1 * ? *)",
  "ScheduleExpressionTimezone": "Asia/Seoul",
  "StartWindowHours": 6,
  "RecoveryPointSelection": {
    "Algorithm": "RANDOM_WITHIN_WINDOW",
    "IncludeVaults": ["*"],
    "RecoveryPointTypes": ["SNAPSHOT"],
    "SelectionWindowDays": 30
  }
}' --profile awssec-lab --region ap-northeast-2
```

`Algorithm`을 `RANDOM_WITHIN_WINDOW`로 둔 것이 1번 원칙의 자동화입니다. 다만 자동 복원 테스트는 **복원 작업의 성공까지만** 검증합니다. 4번(데이터 검증)과 3번(평시 권한으로 사람이 수행)은 여전히 사람의 훈련으로 남겨야 합니다.

- [ ] 훈련용 추가 권한 없이, 평시 복원 역할로만 수행했다
- [ ] 크로스 계정·크로스 리전 복원을 **실제로** 수행했다(동일 계정 복원만으로 끝내지 않았다)
- [ ] KMS 키 접근이 복원 계정에서 성공했다
- [ ] 서브넷 그룹·파라미터 그룹·보안 그룹 등 **의존 리소스가 대상 리전에 존재**했다
- [ ] 복원된 데이터에 실제 쿼리를 돌려 행 수·최신 타임스탬프를 확인했다
- [ ] 단계별 소요 시간을 기록하고 RTO와 대조했다
- [ ] 볼트 잠금이 걸린 상태에서 복원이 정상 동작함을 확인했다
- [ ] 발견된 문제를 티켓으로 등록하고 다음 훈련 전까지 닫았다
- [ ] 훈련 결과를 백업 정책 문서에 반영했다

| 항목 | 핵심 |
|---|---|

| 클라우드 3-2-1 | 매체 다양성 → **실패 도메인 다양성**. 오프사이트 → **별도 계정**. 여기에 불변 1개 + 검증 |

| AWS Backup | 계획 → 규칙 → 볼트 → 태그 기반 선택. `CopyActions`로 크로스 계정·크로스 리전 사본 |
| 볼트 잠금 | 거버넌스는 해제 가능, **컴플라이언스는 유예 기간 후 영구 불변** — AWS도 못 푼다 |
| 백업 계정 분리 | 원서: 백업은 **분리된 계정, 분리된 관리 자격 증명**. 공격자가 백업까지 지운 사례가 문서화됨 |
| 방어 구조 | 목적지 볼트 접근 정책(들어오는 쪽) + 운영 계정 SCP(나가는 쪽), 둘 다 필요 |
| 랜섬웨어 4단계 | 백업 무력화. 이 단계를 실패시키면 사고, 성공시키면 폐업 |
| KMS 키 삭제 | 원서의 **암호학적 소거**를 뒤집은 공격. 백업을 **다른 계정의 다른 키**로 암호화해야 생존 |
| 복구 테스트 | 권한 부족 / KMS 접근 불가 / 키 미공유 / 의존 리소스 누락 — 그리고 **시간** |

## 🔴 필수 구성 체크리스트

- [ ] 백업이 데이터 분류 등급별 **필수 통제 매트릭스의 한 행**으로 등재되어 있다
- [ ] 모든 운영 리소스가 **태그 조건**으로 백업 계획에 자동 포함된다(ARN 개별 등록이 아니다)
- [ ] 백업 계획에 **`CopyActions`로 크로스 계정 + 크로스 리전** 사본이 정의되어 있다
- [ ] 목적지 볼트에 **볼트 잠금 컴플라이언스 모드**가 적용되어 있다
- [ ] 컴플라이언스 모드 잠금을 개발 계정에서 **짧은 값으로 리허설**한 뒤 적용했다
- [ ] 목적지 볼트 접근 정책이 `backup:CopyIntoBackupVault`만 허용하고 삭제 계열은 Deny한다
- [ ] Deny 정책의 **예외 역할을 실제로 `assume-role` 해봤다**(오타로 잠기지 않음을 확인)
- [ ] 운영 계정 SCP가 `backup:Delete*`·`UpdateRecoveryPointLifecycle`·`kms:ScheduleKeyDeletion`을 차단한다
- [ ] 서비스 고유 스냅샷 삭제 액션(`ec2:DeleteSnapshot` 등)도 함께 통제된다
- [ ] SCP 예외 역할 이름에 대한 **`iam:CreateRole` 계열도 함께 Deny** 되어 자기 무력화가 불가능하다
- [ ] 목적지 볼트가 **백업 계정 소유 KMS 키**(또는 논리적 에어갭 볼트)로 암호화되어 있다
- [ ] `kms:ScheduleKeyDeletion` 호출에 **즉시 호출 수준의 경보**가 걸려 있다
- [ ] 백업 대상 리소스가 **고객 관리형 키**로 암호화되어 크로스 계정 공유가 가능하다
- [ ] 데이터 유형별 **RTO/RPO가 문서화**되고 백업 주기·저장 계층에 반영되어 있다
- [ ] 분기 1회 이상 **크로스 계정 복원 훈련**을 실제로 수행하고 시간을 기록한다
- [ ] 복원 대상 리전에 **서브넷 그룹·파라미터 그룹 등 의존 리소스**가 IaC로 상시 유지된다
- [ ] AWS Backup Audit Manager로 **백업 계획에 속하지 않은 리소스**를 상시 검출한다

## ⚠️ 자주 하는 실수

| 실수 | 결과 | 올바른 구성 |
|---|---|---|
| 백업을 운영 계정 안에만 둔다 | 원서가 경고한 그대로 — 공격자가 데이터와 백업을 함께 삭제 | 별도 계정 + 볼트 잠금 (17.4) |
| "리전을 나눴으니 격리됐다"고 본다 | 리전은 권한 경계가 아니다. 같은 자격 증명이 두 리전 모두 삭제 | 계정을 나눈다 (17.2 실패 도메인 표) |
| 백업 대상을 ARN으로 개별 등록한다 | 신규 리소스가 영원히 백업되지 않는다 | 태그 조건 기반 선택 + 태그 강제 (17.3, 12.3) |
| 볼트 잠금을 거버넌스 모드로만 건다 | 관리자 권한 탈취 시 잠금 해제 후 삭제 — 방어선이 아니다 | 목적지 볼트는 컴플라이언스 모드 (17.3) |
| 컴플라이언스 모드를 리허설 없이 운영에 적용한다 | 오입력한 보존 기간을 되돌릴 수 없어 수년치 비용 발생 | 개발 계정에서 짧은 값으로 검증 (17.3) |
| 볼트 접근 정책 Deny의 예외 ARN에 오타를 낸다 | 정책을 수정할 프린시펄이 사라져 볼트가 잠긴다 | 적용 전 `assume-role`로 예외 역할 검증 (17.4) |
| SCP 예외 역할 이름만 지정하고 역할 생성을 막지 않는다 | 공격자가 같은 이름의 역할을 만들어 SCP를 통과 | 예외 이름 패턴에 대한 `iam:CreateRole` 계열도 함께 Deny (17.4, 37장) |
| 백업을 운영 계정의 KMS 키로 암호화한다 | 운영 키 삭제 예약 하나로 백업까지 동반 사망 | 백업 계정 소유 키 / 논리적 에어갭 볼트 (17.5) |
| 백업 대상을 AWS 관리형 키로 암호화한다 | 크로스 계정 복사·공유가 원천적으로 불가 | 고객 관리형 키 (16.1, 13.10) |
| `kms:ScheduleKeyDeletion`에 경보가 없다 | 대기 기간 7~30일 동안 아무도 모르다가 일괄 사망 | EventBridge 즉시 호출 경보 (17.5) |
| 배포 역할에 `AdministratorAccess`를 붙인다 | 키 삭제·백업 삭제가 모두 그 역할의 권한 안에 들어온다 | 키 관리 액션 분리 + SCP (13.4, 17.4) |
| "S3 버전 관리를 켰으니 랜섬웨어 대비 완료"로 본다 | `DeleteObjectVersion` 권한자 앞에서 무력 | 객체 잠금 + 별도 계정 복제 조합 (17.5) |
| MFA Delete만 믿는다 | 루트 자격 증명 필요라 자동화 불가, 루트 침해 시 무력 | 조합의 한 층으로만 사용 (15.8) |
| 대시보드 초록색을 복구 가능성의 증거로 본다 | 백업 성공과 복원 성공은 다른 명제 | 분기 복구 훈련 + 자동 복원 테스트 (17.6) |
| 훈련 시 담당자가 복구 지점을 고른다 | "잘 되는 것"만 검증되고 문제 있는 사본은 영원히 발견 안 됨 | 무작위 선정 / `RANDOM_WITHIN_WINDOW` (17.6) |
| 훈련용 임시 권한을 미리 부여한다 | 가장 흔한 실패 원인(권한 부족)을 훈련이 놓친다 | 평시 복원 역할로만 수행 (17.6) |
| 복원 작업 성공만 확인하고 끝낸다 | 데이터가 비어 있거나 시점이 어긋난 것을 사고 때 발견 | 행 수·최신 타임스탬프 쿼리 검증 (17.6) |
| 의존 리소스를 백업 대상에서 빼놓는다 | 복원은 성공하는데 애플리케이션이 안 뜬다 | 대상 리전에 IaC로 상시 유지 (28장) |
| 모든 것을 백업하려 한다 | 비용 폭증 + 복구 우선순위 상실로 RTO 초과 | 재생성 가능한 것은 재배포, 백업은 상태 전용 (34.5) |
| RTO/RPO를 계약서에만 쓰고 검증하지 않는다 | 원서 경고대로 "세상이 일주일 멈춰야 하는" 복구 전략 | 훈련에서 시간 측정 후 대조 (17.6) |
