# 2장. 공동 책임 모델 (Shared Responsibility Model)

> **이 장에서 다루는 것**
> - "클라우드의 보안(security **of** the cloud)"과 "클라우드 **안에서의** 보안(security **in** the cloud)"이 갈리는 지점
> - EC2 → ECS/EKS/RDS → Lambda/S3/DynamoDB로 갈수록 책임선이 어떻게 이동하는지의 계층별 매핑표

> - 관리형 서비스를 쓰면 정말 안전해지는가: 줄어드는 책임 면적과 커지는 설정 오류(misconfiguration) 표면
> - 새 AWS 서비스를 도입할 때 던져야 할 18개 질문
>
> **선행 지식**: 0장(예제 애플리케이션 ShopMini), 1장(심층 방어·폭발 반경)
> **난이도**: ★☆☆

1장에서 다섯 개의 원칙을 세웠습니다. 그런데 원칙을 적용하기 전에 먼저 답해야 할 질문이 있습니다. **이 중에서 어디까지가 내 일인가.**

이 질문을 건너뛰면 어떤 일이 벌어지는지, 원서는 아주 짧은 한 문장으로 정리합니다.

> 📖 *Practical Cloud Security* 1판·2판 1장은 똑같은 문장으로 이렇게 말합니다. **"많은 보안 사고의 근본 원인은 클라우드 제공자가 알아서 처리하고 있을 것이라는 가정이었고, 알고 보니 아무도 처리하고 있지 않았다는 것이다."** 저자는 이 오해에서 비롯된 실제 사고의 대표적 예로 **열려 있는 Amazon S3 버킷**을 듭니다. "S3 스토리지는 안전하고 암호화되어 있다. 하지만 접근 통제를 제대로 설정하지 않으면 그중 어느 것도 도움이 되지 않는다"는 것입니다. 그리고 이 오해로 유실된 데이터 목록을 나열합니다 — 1억 9,800만 명의 미국 유권자 데이터, 차량 추적 회사 기록, 무선 통신 고객 기록, 300만 건이 넘는 인구통계 설문 기록, 5만 명이 넘는 인도 시민의 신용 보고서. **2판은 여기에 두 항목을 더 얹었습니다** — 10만 명이 넘는 학생의 성적과 개인정보, 그리고 사적인 대화가 담긴 수천 시간 분량의 음성·영상 녹음. 목록 끝에 저자는 "예는 훨씬 더 많다"고 덧붙입니다. 2판은 그동안 상당한 진전이 있었음에도 공동 책임 모델이 여전히 자주 오해되며, **많은 IT 의사결정자가 퍼블릭 클라우드 제공자가 자신들이 제공하는 클라우드 서비스뿐 아니라 고객의 애플리케이션과 데이터까지 지켜준다고 믿고 있다**고 지적합니다. 두 판 모두 같은 문장으로 끝맺는데, 그것이 이 장 전체의 요지입니다. **"클라우드 제공자와 맺은 계약서를 읽어보면, 그것이 사실이 아님을 알게 될 것이다."**

이 장에는 새로운 AWS 서비스가 거의 나오지 않습니다. 대신 **표가 많습니다.** 앞으로 이 책에서 다룰 모든 통제는 "이건 AWS가 해주는 게 아니라 내가 해야 한다"는 판정에서 출발하기 때문입니다.

## 2.1 "클라우드의 보안" vs "클라우드 안에서의 보안"

AWS는 자사의 책임과 고객의 책임을 두 개의 전치사로 구분합니다. **security *of* the cloud**(클라우드의 보안)는 AWS의 몫이고, **security *in* the cloud**(클라우드 안에서의 보안)는 고객의 몫입니다.

> 📖 *AWS Security Cookbook* 1장은 이 구분을 이렇게 요약합니다. "AWS 공동 책임 모델은 AWS 클라우드에서 우리의 솔루션을 보호하는 데 있어 AWS와 그 고객의 책임을 정의한다. 요약하면, **클라우드의 보안** — 예컨대 글로벌 인프라, 하드웨어, 네트워킹을 보호하는 것 — 은 AWS의 책임이고, **클라우드 안에서의 보안** — 예컨대 우리가 프로비저닝한 서버의 업데이트와 보안 패치, 자격 증명과 키의 보호 — 은 고객의 책임이다."

### 피자 비유가 말하는 것

원서는 이 경계를 설명하는 데 유명한 비유를 씁니다.

> 📖 *Practical Cloud Security* 2판 1장은 **"Pizza as a Service"** 비유를 씁니다(2014년 Albert Barron의 글에서 가져온 개념이라고 각주로 밝히고 있습니다). 피자를 먹는 방법에는 여러 선택지가 있습니다. 집에서 직접 만들거나(온프레미스), 마트에서 반조리 제품을 사 와 오븐에 굽거나(IaaS), 배달을 시키거나(PaaS), 식당에 가서 앉아 주문하거나(SaaS). 저자는 SaaS에 대해 이렇게 말합니다. **"모든 것이 다 되어 있는 것처럼 보인다. 하지만 그렇지 않다. 당신에게는 여전히 안전하게 먹을 책임이 있고, 당신이 음식에 목이 막히더라도 식당은 책임지지 않는다."** 그리고 SaaS 세계에서 이 "안전하게 먹을 책임"은 **대체로 접근 통제를 제대로 관리하는 것으로 귀결된다**고 정리합니다.

이 비유에서 실무자가 가져가야 할 것은 "IaaS는 책임이 많고 SaaS는 적다"는 상식이 아닙니다. **어떤 모델에서도 고객 책임이 0이 되는 층이 하나 남는다**는 점입니다. 그 층이 바로 데이터 접근 통제입니다.

### 계층별 책임 판정

원서는 기술 계층별로 책임을 나눈 그림을 제시하고, 각 층을 다음과 같이 설명합니다. 이를 AWS 문맥으로 옮기면 이렇습니다.

| 계층 | 원서의 판정 | AWS에서의 실체 | ShopMini에서 누가 하는가 |
|---|---|---|---|
| **물리 인프라** | 제공자 책임(예외 없음) | 리전·AZ의 데이터센터, 출입 통제, 경비 | AWS. 고객은 **AWS Artifact**로 감사 보고서를 확인할 뿐 |
| **가상화 인프라** | 제공자 책임 | 하이퍼바이저(Nitro), 테넌트 격리 | AWS |
| **네트워크** | IaaS에서 **공유** | AWS 백본은 AWS / VPC·서브넷·SG·NACL·TLS는 고객 | VPC `shopmini-prod` 설계는 전부 고객 |
| **운영체제** | IaaS는 고객, PaaS/SaaS는 제공자 | EC2의 AMI·커널·패키지 | EC2 앱 티어는 고객, RDS·Lambda는 AWS |
| **미들웨어** | PaaS에서 **공유** | DB 엔진, 앱 서버, 큐 | RDS 엔진 패치는 AWS, **파라미터 그룹 설정은 고객** |
| **애플리케이션** | SaaS는 제공자, 그 외 고객 | ShopMini 코드, 의존성 라이브러리 | 전부 고객 |
| **데이터 접근** | **거의 항상 고객** | IAM 정책, 버킷 정책, KMS 키 정책 | 전부 고객 |

> 📖 *Practical Cloud Security* 2판 1장은 물리 계층에 대해 "제공자의 통제가 종종 **많은 기업이 온프레미스에서 현실적으로 할 수 있는 수준을 넘어선다**"고 인정합니다. 생체 인식 출입, 동반 침입(tailgating) 방지, 경비 인력, 슬래브-투-슬래브 차단벽 같은 것들입니다. 반대편 끝인 데이터 접근 계층에 대해서는 이렇게 씁니다. **"당신이 클라우드 제공자에게 특정 데이터에 대한 접근을 허용하라고 잘못 지시했다면 — 예컨대 오브젝트 스토리지 권한이나 미들웨어 권한, SaaS 권한을 잘못 부여했다면 — 제공자가 할 수 있는 일은 그 문제를 탐지해서 경고해주려 시도하는 것 외에는 사실상 없다."**(1판은 같은 자리에서 더 단호하게 "제공자가 할 수 있는 일은 정말로 아무것도 없다"고 씁니다.)

이 마지막 문장은 AWS의 실제 동작과 정확히 일치합니다. S3 콘솔이 퍼블릭 버킷에 빨간 배지를 달아주고, IAM Access Analyzer가 외부 접근 가능 리소스를 찾아주고, Trusted Advisor가 경고를 띄웁니다. **그러나 어느 것도 당신 대신 정책을 고쳐주지는 않습니다.**

### 🔴 한 문장 판별법

원서는 회색 지대를 판정하는 매우 실용적인 경험칙 하나를 제시합니다.

> 📖 *Practical Cloud Security* 1판·2판 1장은 운영체제 계층을 설명하며 이렇게 씁니다. **"일반적인 경험칙으로, 당신이 그것을 망가뜨릴 능력이 있다면 대개 그것을 보호할 책임도 당신에게 있다."**(원문: *if you have the ability to break it, you usually have the responsibility for securing it*)

AWS에서 이 문장은 이렇게 번역됩니다. **콘솔·API·SSH로 내가 바꿀 수 있는 설정은 전부 내 책임입니다.**

- RDS 인스턴스에 SSH로 들어갈 수 없다 → OS 패치는 내 책임이 아니다.
- 그러나 RDS의 **파라미터 그룹은 내가 바꿀 수 있다** → `require_secure_transport` 를 끄면 평문 연결이 허용되고, 그건 내 책임이다.
- Lambda 런타임의 커널을 내가 바꿀 수 없다 → 커널 CVE는 내 책임이 아니다.
- 그러나 **배포 패키지에 넣은 라이브러리 버전은 내가 정한다** → 의존성 취약점은 내 책임이다.

이 판별법을 쓰면 뒤에 나오는 대부분의 회색 지대가 정리됩니다.

## 2.2 서비스 모델별 책임선 이동

### 원서가 서비스 모델을 다루는 방식

> 📖 *Practical Cloud Security* 2판 1장 "Cloud Service Delivery Models" 절은 IaaS/PaaS/SaaS를 짧게 정의합니다. **IaaS는 가상 컴퓨터·스토리지·네트워크를 만들 수 있게 해주는 서비스, PaaS는 데이터베이스처럼 애플리케이션을 만들 수 있게 해주는 더 상위 수준의 서비스, SaaS는 최종 사용자가 쓰는 애플리케이션**입니다. 그런데 저자는 곧바로 이 분류의 한계를 지적합니다. **"이 서비스 모델은 개념을 일반적으로 이해하는 데에만 유용하다. 특히 IaaS와 PaaS 사이의 선은 점점 더 흐려지고 있다."** 콘텐츠를 인터넷 곳곳에 캐싱해 사용자 가까이 두는 CDN 서비스는 PaaS인가 IaaS인가? 저자의 답은 이렇습니다. **"그건 중요하지 않다. 중요한 것은 그 서비스가 무엇을 제공하고 무엇을 제공하지 않는지를 당신이 이해하는 것이지, 그것이 어떤 범주에 깔끔하게 들어맞는지가 아니다."**

이 지적은 AWS에서 특히 중요합니다. AWS에는 200개가 넘는 서비스가 있고, 그중 상당수가 IaaS/PaaS로 딱 잘리지 않습니다. Fargate는 IaaS인가 PaaS인가? EKS는? 답을 정할 필요가 없습니다. **필요한 것은 "이 서비스에서 각 계층을 누가 패치하고 누가 설정하는가"를 아는 것뿐입니다.**

2판은 컴퓨트 자산을 분류하며 IaaS/PaaS 외에 두 가지를 더 구분합니다.

> 📖 2판 3장은 **aPaaS(Application Platform as a Service)** 를 "AWS Elastic Beanstalk, Google App Engine처럼 **VM을 직접 프로비저닝하지 않고 코드를 배포할 수 있게 해주는 서비스**"로 정의하고, 이 경우 "**기반이 되는 컴퓨트 자원이나 스토리지 자원에 대해서는 아무것도 인벤토리에 넣을 필요가 없다. 당신의 통제 밖이기 때문이다**"라고 씁니다. **서버리스 함수**(AWS Lambda 등)에 대해서는 "aPaaS와 다른 점은 **서비스가 요청되기 전에는 아무것도 실행되지 않는다**는 것"이며, "서버리스 자산에 대해서는 **운영체제나 플랫폼 컴포넌트를 인벤토리에 넣을 필요가 전혀 없고**, 코드의 취약점을 관리하고 함수에 대한 접근을 통제할 수 있도록 서버리스 배포 자체만 인벤토리에 넣으면 된다"고 정리합니다.

### 🔴 AWS 서비스별 책임 매핑표

원서의 계층 구분을 실제 AWS 서비스에 매핑하면 다음과 같습니다. **A = AWS 책임, C = 고객 책임, A/C = 공유(AWS가 기반을, 고객이 설정을)**

| IAM·리소스 정책 | **C** | **C** | **C** | **C** | **C** | **C** | **C** |
| 로깅 활성화 | **C** | **C** | **C** | **C** | **C** | **C** | **C** |

이 표에서 세로로 읽으면 "이 서비스를 쓰면 내가 뭘 해야 하나"가 나오고, **가로로 읽으면 더 중요한 사실이 보입니다.** 맨 아래 세 행 — **IAM·리소스 정책, 로깅 활성화, 그리고 사실상 데이터 암호화 강제** — 는 어떤 서비스를 쓰든 **전부 C**입니다. 서비스 모델을 아무리 위로 올려도 이 세 행은 절대 AWS로 넘어가지 않습니다.

### ShopMini에 적용하기

0장에서 정한 예제 애플리케이션에 이 표를 적용해 봅니다.

```
사용자 → CloudFront → ALB(public subnet) → 앱 EC2/컨테이너(private-app, 8443)
                                              ├→ RDS MySQL 3306 (isolated-data)
```

## 2.3 🔴 가장 많이 오해되는 경계 5가지

이 절의 다섯 항목은 각각 **"AWS가 해준다는 착각 → 실제 사고 시나리오 → 고객이 해야 할 구성"** 순으로 씁니다. 다섯 개 모두 "안 하면 설계 결함"에 해당합니다.

### ① 데이터 암호화는 언제나 고객 책임이다

**착각** — "AWS는 데이터를 암호화해서 저장한다고 하니 암호화는 끝났다."

**무엇이 사실인가** — AWS가 자동으로 해주는 것은 **암호화 연산과 키 저장의 인프라**이지, **어떤 키로 무엇을 암호화할지, 암호화되지 않은 저장·전송을 거부할지**의 결정이 아닙니다.

> 📖 *Practical Cloud Security* 2판 2장은 이 지점을 이렇게 설명합니다. **"좋은 소식은, 이 키 관리의 대부분을 당신이 직접 할 필요는 없다는 것이다."** 제공자의 스토리지와 KMS를 쓰고 스토리지 인스턴스에 KMS 암호화를 켜면, 스토리지 서비스가 데이터 암호화 키를 자동으로 만들고 KMS에서 관리하는 키 암호화 키로 그것을 감싸(wrap) 데이터와 함께 저장한다는 것입니다(서버 사이드 암호화). 그러나 저자가 같은 장의 결론에서 강조하는 것은 다음입니다. **"가능하다면 데이터를 저장하는 클라우드 리소스를 만들기 전에 암호화 전략을 결정해야 한다. 나중에 바꾸기가 어려울 수 있기 때문이다."** 그리고 **"키에 접근할 수 있는 사용자와 시스템을 신중하게 통제하고, 키가 비정상적인 방식으로 접근될 때 알려주는 알림을 설정하라"** 고 덧붙입니다.

**사고 시나리오** — ShopMini 운영팀이 RDS MySQL 인스턴스를 급하게 만들면서 "저장 암호화" 체크박스를 넘겼습니다. 6개월 뒤 컴플라이언스 감사에서 지적을 받습니다. 그런데 **RDS의 저장 암호화는 인스턴스 생성 시점에만 켤 수 있습니다.** 이미 운영 중인 인스턴스를 암호화하려면 스냅샷을 뜨고, 암호화된 복사본을 만들고, 그것으로 새 인스턴스를 복원한 뒤 전환해야 합니다. 즉 **다운타임을 동반한 마이그레이션**입니다. 원서가 "리소스를 만들기 전에 결정하라"고 한 이유가 이것입니다.

두 번째 시나리오는 전송 구간입니다. RDS는 TLS 연결을 지원하지만 **강제하지는 않습니다.** 파라미터 그룹에서 `require_secure_transport` 를 켜지 않으면 앱이 평문으로 붙어도 조용히 성공합니다. 1장에서 본 제로 트러스트 원칙대로, `10.20.10.0/24` 안에 있다는 사실은 신뢰의 근거가 되지 못합니다.

**고객이 해야 할 구성**

```bash
# 1) 계정 단위로 EBS 기본 암호화를 켠다 — 리전별 설정이므로 리전마다 반복
aws ec2 enable-ebs-encryption-by-default \
  --region ap-northeast-2 --profile awssec-lab
aws ec2 get-ebs-encryption-by-default \
  --region ap-northeast-2 --profile awssec-lab

# 2) RDS는 "생성 시점"에만 켤 수 있다
aws rds create-db-instance \
  --db-instance-identifier shopmini-prod-mysql \
  --engine mysql --db-instance-class db.r6g.large \
  --allocated-storage 100 \
  --storage-encrypted --kms-key-id alias/shopmini/app \
  --backup-retention-period 14 --multi-az \
  --region ap-northeast-2 --profile awssec-lab
```

S3는 여기서 한 걸음 더 나아가야 합니다. 기본 암호화가 켜져 있어도 **클라이언트가 다른 방식(예: SSE-S3)으로 올리는 것을 막지는 않습니다.** 지정한 KMS 키를 쓰지 않은 업로드와 비-TLS 접근을 **버킷 정책으로 거부**해야 합니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyUnEncryptedObjectUploads",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::shopmini-uploads/*",
      "Condition": {
        "StringNotEquals": {
          "s3:x-amz-server-side-encryption": "aws:kms"
        }
      }
    },
    {
      "Sid": "DenyWrongKmsKey",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::shopmini-uploads/*",
      "Condition": {
        "StringNotEquals": {
          "s3:x-amz-server-side-encryption-aws-kms-key-id":
            "arn:aws:kms:ap-northeast-2:111122223333:alias/shopmini/app"
        }
      }
    },
    {
      "Sid": "DenyInsecureTransport",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::shopmini-uploads",
        "arn:aws:s3:::shopmini-uploads/*"
      ],
      "Condition": {
        "Bool": { "aws:SecureTransport": "false" }
      }
    }
  ]
}
```

> 💡 **원서 이후 변경** — 2023년 1월부터 S3에 새로 업로드되는 모든 객체는 **SSE-S3(S3 관리형 키)로 기본 암호화**됩니다. 이 변경은 "암호화되지 않은 객체"라는 문제는 없앴지만, **"내가 통제하는 키로 암호화되었는가"** 라는 문제는 그대로 남깁니다. 폭발 반경 관점(1.4)에서 중요한 것은 후자입니다. AWS 관리형 키는 내가 접근을 끊을 수 없지만, 고객 관리형 KMS 키(`alias/shopmini/app`)는 키 정책으로 접근을 끊을 수 있고, 키를 비활성화하면 데이터 전체를 한 번에 무력화할 수 있습니다. 위 버킷 정책이 필요한 이유입니다. DynamoDB도 마찬가지로 저장 암호화를 끌 수 없지만, **기본값은 AWS 소유 키**이고 고객 관리형 키로 바꾸는 것은 고객의 선택입니다.

### ② 패치 책임은 서비스마다 다르다 — "관리형이니까 자동"이 아니다

**착각** — "관리형 서비스는 AWS가 알아서 패치한다."

**무엇이 사실인가** — 원서는 이 지점을 정확히 짚습니다.

> 📖 *Practical Cloud Security* 2판 5장은 미들웨어 계층을 "IaaS와 일부 PaaS에서 소비자 책임"으로 표시하고 이렇게 씁니다. **"컴포넌트가 클라우드 제공자에 의해 서비스로 제공된다면, 대개 제공자가 패치 책임을 진다. 그런데 함정이 있다! 어떤 경우에는 업데이트가 자동으로 푸시되지 않는다. 서비스 중단을 일으킬 수 있기 때문이다. 그런 경우 당신은 여전히 테스트하고, 편한 시점에 배포 버튼을 누를 책임을 진다."** 그리고 패치와 별개의 문제를 덧붙입니다. **"패치를 적용하는 것 외에도, PaaS 환경에서조차 미들웨어가 어떻게 설정되어 있는지를 걱정해야 한다."** 저자가 든 실제 예는 이렇습니다 — 웹 서버가 실수로 패스워드 파일을 볼 수 있게 설정된 경우, **데이터베이스가 올바른 인증 유형으로 설정되지 않아 누구나 DB 관리자로 행세할 수 있는 경우**, Java 애플리케이션 서버가 디버그 출력을 내보내도록 설정되어 버그 발생 시 패스워드가 노출되는 경우.

컨테이너에 대해서도 별도의 판정이 있습니다.

> 📖 2판 5장은 가상화 인프라 계층을 "제공자 책임"으로 두면서도 단서를 붙입니다. **"그러나 컨테이너 기반 환경에서는 클라우드 제공자가 제공하는 것 위에 올라간 가상화 인프라 또는 플랫폼에 대해 당신이 보안 책임을 질 수 있다. 예컨대 Docker 같은 컨테이너 런타임이나 Kubernetes 같은 오케스트레이션 계층의 잘못된 설정이나 누락된 패치가 취약점의 원인이 될 수 있다."** 또한 컨테이너의 장점으로 "**최소한의 컨테이너 이미지에서 시작해 애플리케이션 실행에 필요한 것만 설치하기 때문에 기본적으로 하드닝된 상태로 출발한다**"는 점을 들면서도, "많은 컨테이너가 운영체제의 사용자 공간(userspace) 부분을 포함하므로 **운영체제 취약점 관리와 구성 관리가 컨테이너 보안에도 그대로 작용한다**"고 못박습니다.

**사고 시나리오** — ShopMini 팀이 앱 티어를 EKS로 옮겼습니다. "관리형 Kubernetes니까 AWS가 다 한다"고 생각했습니다. 실제로는 세 곳에 구멍이 생겼습니다. 첫째, **워커 노드의 AMI**는 팀이 직접 갱신해야 하는데 6개월째 그대로였습니다. 둘째, **컨테이너 베이스 이미지**에 오래된 OpenSSL이 들어 있었습니다. 셋째, RDS의 `auto minor version upgrade` 를 껐던 것을 잊었습니다. 결과적으로 "관리형 서비스 3개를 쓰는데 패치되는 게 하나도 없는" 상태가 됐습니다.

**고객이 해야 할 구성**

| 서비스 | AWS가 패치하는 것 | 고객이 반드시 해야 하는 것 |
|---|---|---|
| EC2 | 하이퍼바이저만 | AMI 갱신, Systems Manager Patch Manager 패치 베이스라인·유지 관리 기간, 골든 AMI 재빌드 |
| ECS on EC2 | 하이퍼바이저 | ECS 최적화 AMI 교체, ECS 에이전트 버전, **컨테이너 이미지** |
| ECS/EKS on Fargate | 플랫폼 버전(호스트 OS·런타임) | **컨테이너 이미지 재빌드·재배포**. 플랫폼 버전을 `LATEST` 로 두어도 이미지는 안 바뀜 |
| EKS | 컨트롤 플레인 | 노드 그룹 AMI 갱신, 클러스터 버전 업그레이드(**지원 종료 전에**), 애드온 버전, 이미지 |
| RDS | OS와 DB 엔진 바이너리 | `auto minor version upgrade` 활성화, 메이저 버전 업그레이드 계획, **인증서(CA) 교체**, 파라미터 그룹 점검 |
| Lambda | 런타임과 그 아래 전부 | **런타임 지원 종료(deprecation) 추적**, 배포 패키지·레이어의 의존성 갱신 |

```bash
# 지원 종료가 임박한 Lambda 런타임 찾기
aws lambda list-functions --profile awssec-lab --region ap-northeast-2 \
  --query 'Functions[].{Name:FunctionName,Runtime:Runtime}' --output table

# 마이너 버전 자동 업그레이드가 꺼진 RDS 인스턴스 찾기
aws rds describe-db-instances --profile awssec-lab --region ap-northeast-2 \
  --query 'DBInstances[?AutoMinorVersionUpgrade==`false`].DBInstanceIdentifier'

# 패치가 밀린 EC2 인스턴스 확인
aws ssm describe-instance-patch-states \
  --instance-ids i-0abcd1234efgh5678 \
  --profile awssec-lab --region ap-northeast-2
```

컨테이너 이미지 취약점은 Amazon ECR의 이미지 스캔(Amazon Inspector 연동)으로 상시 감시합니다. 상세한 취약점 관리 파이프라인은 5부에서 다룹니다.

### ③ 백업과 복원은 고객 책임이다 — 그리고 "백업"보다 "복원"이 문제다

**착각** — "RDS는 자동 백업이 있으니 괜찮다. S3는 11 나인의 내구성이니 안전하다."

**무엇이 사실인가** — 내구성(durability)은 **하드웨어 고장으로 데이터가 사라지지 않는다**는 뜻이지, **사람이나 공격자가 지운 데이터가 돌아온다**는 뜻이 아닙니다. `aws s3 rm --recursive` 는 11 나인의 내구성으로 안전하게 삭제됩니다.

> 📖 *Practical Cloud Security* 2판 7장은 사고 대응 계획에 백업을 포함시키면서 두 가지를 특히 강조합니다. 첫째, **"백업이 운영 데이터와는 별개의 관리 자격 증명을 가진 별도의 클라우드 계정에 있는지 확인하라. 공격자가 운영 데이터뿐 아니라 운영 계정에서 접근 가능한 백업까지 전부 지워버린 사례가 문서로 남아 있다."** 둘째, **"복원이 얼마나 걸리는지 이해하는 것도 중요하다. 때로는 완벽하게 합리적인 복구 전략을 갖고 있는데, 다만 그것이 온 세상이 일주일간 멈춰줄 것을 요구하는 경우가 있다."** 저자는 복구 중에 100% 기능할 필요는 없지만 **핵심 업무는 수행할 수 있어야 한다**고 정리합니다.

이 두 문장은 CANON에서 로그 아카이브 계정 `777788889999` 와 보안 도구 계정 `444455556666` 을 운영 계정 `111122223333` 과 분리한 이유이기도 합니다.

**사고 시나리오** — ShopMini 운영 계정의 CI/CD 파이프라인 역할 자격 증명이 유출됐습니다. 공격자는 RDS 인스턴스를 **최종 스냅샷 생성을 건너뛰고** 삭제한 뒤, 같은 계정에 남아 있던 보존 자동 백업과 수동 스냅샷까지 이어서 지웁니다. **백업이 운영 계정 안에만 있었기 때문에 운영 계정 자격 증명 하나로 데이터와 복구 수단이 동시에 사라진 것**입니다. `shopmini-uploads` 버킷은 버저닝이 꺼져 있어 덮어쓴 객체를 되돌릴 수 없습니다. DynamoDB 테이블은 PITR이 기본값인 **꺼짐** 상태였습니다. 원서가 "문서로 남아 있는 사례"라고 말한 패턴 그대로입니다.

**고객이 해야 할 구성**

- **RDS**: 자동 백업 보존 기간을 명시적으로 설정합니다(기본값에 의존하지 않기). 다만 자동 백업은 **어디까지나 같은 계정 안에 있습니다.** 인스턴스를 지워도 보존 기간 동안은 남지만(보존된 자동 백업), 그 계정에 권한이 있는 공격자는 그것도 지울 수 있고 보존 기간이 지나면 자동으로 만료됩니다. 원서가 말한 "별도의 관리 자격 증명을 가진 별도 계정"을 만족하려면 **수동 스냅샷 또는 AWS Backup의 교차 계정 복사로 백업 볼트를 `777788889999` 에 두어야** 합니다.
- **S3**: 버저닝을 켜고, MFA Delete 또는 Object Lock(규정 준수 모드)으로 삭제를 막습니다. 복제(Replication)로 별도 계정에 사본을 둡니다.
- **DynamoDB**: PITR을 명시적으로 켭니다.
- **삭제 방지 통제**: 운영 계정에서 백업 볼트를 지울 수 없도록 SCP로 막습니다(7부).
- **가장 중요한 것 — 복원 훈련**: 분기마다 실제로 복원해 보고 **RTO를 측정**합니다. 원서의 표현대로, 측정하지 않은 복구 전략은 "온 세상이 멈춰주기를 요구하는" 전략일 수 있습니다.

```bash
# S3 버저닝 켜기 (기본값은 꺼짐)
aws s3api put-bucket-versioning --bucket shopmini-uploads \
  --versioning-configuration Status=Enabled \
  --profile awssec-lab --region ap-northeast-2

# DynamoDB PITR 켜기 (기본값은 꺼짐)
aws dynamodb update-continuous-backups \
  --table-name shopmini-sessions \
  --point-in-time-recovery-specification PointInTimeRecoveryEnabled=true \
  --profile awssec-lab --region ap-northeast-2
```

### ④ IAM 설정은 100% 고객 책임이다

**착각** — "AWS가 IAM 서비스를 운영하니 권한 관리도 어느 정도는 AWS 몫이다."

**무엇이 사실인가** — AWS는 **IAM이라는 인가 엔진의 가용성과 정확성**을 책임집니다. 정책 평가 로직이 틀리지 않게 하는 것, 서명 검증이 뚫리지 않게 하는 것. 그것뿐입니다. **누구에게 무엇을 허용할지는 전부 고객이 씁니다.** 2.1의 표에서 데이터 접근 계층이 모든 서비스 모델에서 고객 책임이었던 것이 여기에 대응합니다.

> 📖 이것이 2.1에서 인용한 원서의 문장 — **"제공자가 할 수 있는 일은 그 문제를 탐지해서 경고해주려 시도하는 것 외에는 사실상 없다"** — 의 정확한 의미입니다. 원서는 또한 SaaS 세계의 고객 책임이 **"대체로 접근 통제를 제대로 관리하는 것으로 귀결된다"** 고 명시합니다. 즉 서비스 모델을 아무리 위로 올려도 이 책임만은 남습니다.

**사고 시나리오** — ShopMini의 앱 EC2 인스턴스 프로파일에 `AmazonS3FullAccess` 관리형 정책이 붙어 있습니다. 앱은 `shopmini-uploads` 하나만 쓰지만, 정책은 계정의 **모든 버킷**을 허용합니다. 애플리케이션에 SSRF 취약점이 발견되고, 공격자는 인스턴스 메타데이터 서비스에서 임시 자격 증명을 꺼내 `shopmini-assets` 를 포함한 모든 버킷을 나열하고 내려받습니다. AWS는 이 요청들을 전부 **정상적으로 인가**합니다. 정책이 그렇게 쓰여 있기 때문입니다. CloudTrail에는 성공한 API 호출로 깔끔하게 기록됩니다.

> 💡 **원서 이후 변경** — 2023년 4월부터 새로 만드는 S3 버킷은 **퍼블릭 액세스 차단(Block Public Access)이 기본 활성화**되고 **ACL이 기본 비활성화**됩니다. 원서가 든 "열린 S3 버킷" 사고 유형의 가장 흔한 경로 하나가 기본값 차원에서 막힌 것입니다. 다만 이것은 **새 버킷의 기본값이 바뀐 것**일 뿐, ⓐ 기존 버킷의 설정은 그대로이고, ⓑ 차단을 해제할 권한이 있는 사람은 여전히 해제할 수 있으며, ⓒ **버킷 정책으로 특정 외부 계정에 광범위한 권한을 주는 실수**는 전혀 막지 못합니다. 조직 차원에서 강제하려면 SCP나 AWS Config 규칙이 필요합니다(37장). 기본값 개선은 고객 책임을 줄여주지 않고, **실수의 난이도만 조금 올려줍니다.**

**고객이 해야 할 구성** — 이것이 이 책 2부(6~11장) 전체의 주제입니다. 이 장에서 기억할 것은 **범위**입니다.

| 대상 | 고객이 결정해야 하는 것 | 다루는 장 |
|---|---|---|
| 사람의 접근 | Identity Center 권한 세트, MFA 강제, 상시 관리자 제거 | 9장 |
| 워크로드의 접근 | 인스턴스 프로파일·태스크 역할·Lambda 실행 역할의 최소화 | 8장 |
| 리소스 쪽 방어 | 버킷 정책, KMS 키 정책, VPC 엔드포인트 정책 | 7·13·15장 |
| 조직 상한선 | SCP, 리소스 컨트롤 정책, 권한 경계 | 37장 |
| 상시 검증 | IAM Access Analyzer, 마지막 액세스 정보 기반 축소 | 7장 |

### ⑤ 가용 영역과 이중화 설계는 고객 책임이다

**착각** — "AWS는 가용성이 높으니 인스턴스를 하나만 띄워도 AWS가 알아서 살려준다."

**무엇이 사실인가** — AWS가 제공하는 것은 **여러 AZ라는 재료**입니다. 그 재료를 어떻게 쓸지는 고객의 설계입니다. RDS의 Multi-AZ는 체크박스이고, **기본값은 꺼짐**입니다. Auto Scaling 그룹에 서브넷을 하나만 넣으면 그 AZ와 함께 죽습니다.

가용성이 보안 주제인 이유도 원서에 명확히 있습니다.

> 📖 *Practical Cloud Security* 2판 2장은 CIA 3요소를 설명하며 **"데이터 가용성을 침해하려는 위협 행위자는 재미로든 돈을 위해서든 당신을 오프라인으로 만들거나, 랜섬웨어로 파일을 암호화하려 한다"** 고 씁니다. 각주에서는 **"랜섬웨어는 가용성 침해이자 무결성 침해다. 데이터를 사용 불가능하게 만들기 위해 무단 변경을 사용하기 때문"** 이라고 정리합니다. 즉 **가용성 설계는 보안 설계의 일부**입니다.

원서는 이중화 실패의 성격도 짚습니다.

> 📖 2판 1장의 각주는 리스크가 **상호작용하거나 합산(aggregate)** 될 수 있다고 지적합니다. **"각각은 발생 가능성이 낮고 영향이 제한적인 두 개의 리스크가 있을 수 있지만, 그것들이 함께 발생할 가능성이 높고 영향이 합쳐지면 훨씬 심각해질 수 있다. 예컨대 이중화된 전원 회선 중 하나가 나가는 영향은 무시할 만하지만, 둘 다 나가는 영향은 정말 나쁠 수 있다."** 저자는 이런 것을 미리 예상하기가 종종 어렵다고 덧붙입니다.

**사고 시나리오** — ShopMini는 ALB를 두 AZ에 걸쳐 두었지만, 비용 절감을 위해 **NAT 게이트웨이를 `ap-northeast-2a` 한 곳에만** 두고 두 AZ의 프라이빗 서브넷 라우팅 테이블이 모두 그것을 가리키게 했습니다. `2a` 에 장애가 발생하자, `2c` 의 앱 인스턴스는 살아 있는데도 외부 API 호출과 패키지 다운로드가 전부 실패합니다. 게다가 RDS는 Single-AZ였고, 그 인스턴스도 `2a` 에 있었습니다. "ALB는 이중화했다"는 안심이 나머지를 보지 못하게 만든 것입니다. 원서가 말한 **리스크 합산**의 전형입니다.

**고객이 해야 할 구성**

- RDS는 운영 환경에서 **Multi-AZ 필수**. 이것은 백업의 대체재가 아니라 별개의 통제입니다(Multi-AZ는 장애 조치이지 실수 복구가 아님).
- 모든 서브넷 계층(public / private-app / isolated-data)을 **`ap-northeast-2a` 와 `2c` 양쪽에** 만듭니다. CANON의 서브넷 배정이 처음부터 AZ 쌍으로 정의된 이유입니다.
- **NAT 게이트웨이는 AZ마다 하나**씩, 라우팅 테이블도 AZ별로 분리합니다.
- Auto Scaling 그룹·ECS 서비스에 **두 AZ의 서브넷을 모두** 지정하고 최소 용량을 2 이상으로 둡니다.
- VPC에 붙인 Lambda는 **여러 AZ의 서브넷**을 지정합니다(VPC 밖 Lambda는 AWS가 알아서 분산하지만, VPC에 붙이는 순간 서브넷 선택은 고객 몫이 됩니다).
- AWS Config 관리형 규칙 `rds-multi-az-support` 로 위반을 상시 탐지합니다.

```bash
# Multi-AZ가 아닌 운영 RDS 인스턴스 찾기
aws rds describe-db-instances --profile awssec-lab --region ap-northeast-2 \
  --query 'DBInstances[?MultiAZ==`false`].[DBInstanceIdentifier,AvailabilityZone]' \
  --output table

# Auto Scaling 그룹이 몇 개 AZ에 걸쳐 있는지 확인
aws autoscaling describe-auto-scaling-groups --profile awssec-lab \
  --region ap-northeast-2 \
  --query 'AutoScalingGroups[].{Name:AutoScalingGroupName,AZs:AvailabilityZones}'
```

## 2.4 관리형 서비스를 쓸수록 안전해지는가

짧은 답: **책임의 총량은 줄어들지만, 남은 책임의 밀도는 높아집니다.**

원서는 이 이동을 리스크 관리의 언어로 설명합니다.

> 📖 *Practical Cloud Security* 2판 1장은 알려진 리스크를 다루는 네 가지 방법(회피·완화·전가·수용) 중 **전가(transfer)** 를 이렇게 설명합니다. **"누군가에게 돈을 지불해 관리를 맡겨서 그 리스크가 그들의 문제가 되게 하는 것이다. 이것은 클라우드에서 아주 많이 일어난다. 시스템의 하위 계층을 관리하는 리스크의 상당 부분을 클라우드 제공자에게 전가하는 것이다."**

즉 관리형 서비스로 옮기는 것은 **보안 통제**가 아니라 **리스크 전가**입니다. 전가된 리스크는 사라지지 않고 AWS에게 갑니다. 그리고 **전가되지 않은 리스크는 그대로 남습니다.**

### ShopMini 앱 티어로 비교하기

앱 티어를 세 가지 방식으로 구현했을 때 무엇이 넘어가고 무엇이 남는지 봅니다.

| | **EC2** | **ECS on Fargate** | **Lambda + API Gateway** |
|---|---|---|---|
| 내가 관리하는 계층 수 | 7개 (OS·런타임·미들웨어·코드·네트워크·IAM·데이터) | 5개 (이미지·코드·네트워크·IAM·데이터) | 3개 (코드·IAM·데이터) |
| 없어지는 실수 유형 | — | SSH 키 유출, OS 패치 누락, IMDSv1 노출 | 위 전부 + 컨테이너 이미지 CVE |
| **새로 생기거나 커지는 실수 유형** | — | 태스크 역할 과잉 권한, `assignPublicIp=ENABLED` 로 퍼블릭 노출, 이미지 안 시크릿 | 함수마다 실행 역할이 흩어져 **권한 검토 누락**, 리소스 기반 정책의 `Principal:"*"`, 환경 변수 평문 시크릿, 함수 수십~수백 개로 인한 인벤토리 붕괴 |
| 실수 하나의 폭발 반경 | 인스턴스 1대 | 태스크 1개 → 태스크 역할이 닿는 전 범위 | 함수 1개 → 실행 역할이 닿는 전 범위 |
| 탐지 난이도 | 높음(호스트 로그 필요) | 중간 | 낮음(전부 API 호출이라 CloudTrail에 남음) |

여기서 드러나는 것이 관리형 서비스의 **비대칭**입니다.

1. **실수의 개수는 줄지만, 남은 실수의 치명도는 올라갑니다.** EC2에서 OS 패치를 놓치면 공격자가 인스턴스에 침투해야 데이터에 닿습니다. Lambda 실행 역할에 `dynamodb:*`, `Resource: "*"` 를 주면 코드 한 줄의 취약점이 곧바로 전 테이블 접근입니다. 중간 단계가 사라졌기 때문입니다.
2. **모든 것이 API 호출이 됩니다.** 이것은 방어자에게 유리합니다(CloudTrail에 다 남습니다). 동시에 공격자에게도 유리합니다. **자격 증명 하나가 곧 인프라 전체에 대한 리모컨**입니다. 1장의 "콘솔 접근은 신과 같은 권한"이라는 지적이 그대로 적용됩니다.
3. **설정 표면이 코드 표면을 대체합니다.** 관리형 서비스에서 사고의 원인은 버퍼 오버플로가 아니라 **체크박스**입니다. 그리고 체크박스는 코드 리뷰를 거치지 않습니다 — IaC로 옮기지 않는 한.

### 원서가 미들웨어에 대해 한 말이 그대로 적용된다

> 📖 2판 5장은 PaaS 환경의 설정 관리에 대해 이렇게 처방합니다. **"사용하는 각 컴포넌트에 대해, 사용 가능한 설정들을 살펴보고 보안과 관련된 설정 목록과 올바른 값이 무엇인지를 만들어야 한다. 이것들은 컴포넌트가 처음 서비스에 투입될 때 강제되어야 하고, 그 후로도 정기적으로 점검해서 전부 여전히 올바르게 설정되어 있는지 확인하고 '구성 드리프트(configuration drift)'를 방지해야 한다."** 저자는 이런 점검을 벤치마킹·헬스 체크·구성 관리라고 부르며, 처음부터 직접 쓰기보다 **CIS 벤치마크** 같은 공통 모범 사례에서 출발할 것을 권합니다. 커뮤니티 기반이라 새로운 위협과 새 버전을 반영한 최신 점검 항목의 혜택을 볼 가능성이 높다는 이유입니다.

이 처방을 AWS 관리형 서비스에 옮기면 이렇게 됩니다.

| 원서의 처방 | AWS에서의 실행 |
|---|---|
| 보안 관련 설정 목록을 만든다 | 서비스별 "필수 설정 목록"을 팀 표준으로 문서화(2.5의 체크리스트가 출발점) |
| 서비스 투입 시 강제한다 | IaC 모듈에 안전한 기본값을 박아 넣고, 그 모듈로만 배포. SCP·리소스 컨트롤 정책으로 우회 차단 |
| 정기적으로 점검한다 | AWS Config 규칙 + Security Hub 보안 표준(CIS AWS Foundations Benchmark 포함) |
| 드리프트를 방지한다 | CloudFormation 드리프트 탐지, Config 자동 교정(remediation) |

**결론**: 관리형 서비스는 안전해지는 지름길이 아니라 **책임을 재배치하는 선택**입니다. 재배치 후 내 손에 남은 것이 무엇인지 목록화하지 않으면, "AWS가 해주겠지"라는 원서의 그 가정으로 되돌아갑니다.

## 2.5 📋 서비스 도입 시 책임선 확인 체크리스트

새로운 AWS 서비스를 ShopMini에 도입하기 전, 아래 18개 질문에 답합니다. **하나라도 "모르겠다"가 있으면 아직 도입 준비가 안 된 것입니다.**

**데이터**
- [ ] 이 서비스는 어떤 데이터를 저장·처리하는가? 4장의 데이터 분류 등급으로 몇 등급인가?
- [ ] 저장 데이터 암호화가 **기본으로 켜져 있는가**, 아니면 생성 시 선택해야 하는가?
- [ ] 암호화 키는 AWS 소유 키인가, AWS 관리형 키인가, **고객 관리형 KMS 키를 쓸 수 있는가**? 키 정책으로 접근을 끊을 수 있는가?
- [ ] **생성 후에 암호화를 켤 수 있는가**, 아니면 재생성이 필요한가? (RDS·EFS처럼 생성 시점 전용인 경우 지금이 마지막 기회)
- [ ] 전송 구간 TLS를 **강제**할 수 있는가? 어떤 조건 키·파라미터로 강제하는가?

**패치와 취약점**
- [ ] 이 서비스에서 **내가 패치해야 하는 것**은 무엇인가? (OS / 런타임 / 이미지 / 의존성 / 없음)
- [ ] AWS가 패치하는 부분은 **자동 적용인가, 내가 승인 버튼을 눌러야 하는가**? 유지 관리 기간은 언제인가?
- [ ] 버전 **지원 종료(EOL/deprecation) 일정**을 어디서 확인하고, 누가 추적하는가?

**접근 통제**
- [ ] 이 서비스에 **리소스 기반 정책**이 있는가? 있다면 IAM 정책과 별개로 반드시 작성해야 한다
- [ ] 이 서비스가 사용하는 IAM 역할(실행 역할·서비스 역할)에 어떤 권한이 필요한가? **AWS 관리형 정책을 그대로 붙이지 않고** 최소화했는가?
- [ ] 이 서비스가 **다른 서비스를 대신 호출**하는가(서비스 연계 역할)? 그 경로로 권한이 확대되지 않는가?
- [ ] 실수로 **퍼블릭 노출**될 수 있는 설정이 있는가? (버킷 ACL, `assignPublicIp`, 리소스 정책의 `Principal: "*"`, 스냅샷 공개 공유) 그것을 조직 차원에서 막을 수단이 있는가?

**가용성과 복구**
- [ ] 이 서비스는 **리전 단위인가 AZ 단위인가**? AZ 단위라면 내가 AZ를 분산해야 한다
- [ ] 백업 기능이 있는가? **기본으로 켜져 있는가?** 보존 기간의 기본값은?
- [ ] 백업을 **다른 계정(`777788889999`)으로 복사**할 수 있는가? 운영 계정 침해 시에도 살아남는가?
- [ ] **복원 절차를 실제로 수행해 봤는가?** RTO를 측정했는가?

**관측과 거버넌스**
- [ ] 이 서비스의 API 호출이 **CloudTrail에 기록되는가**? 데이터 이벤트는 별도 활성화가 필요한가? 서비스 자체 로그(액세스 로그·감사 로그)는 켰는가?
- [ ] 이 서비스의 오설정을 탐지하는 **AWS Config 관리형 규칙 또는 Security Hub 컨트롤**이 있는가? 없다면 무엇으로 대체할 것인가?

> 이 18개 질문의 답을 서비스별로 한 페이지 표로 만들어 팀 위키에 두는 것을 권합니다. 새 서비스가 추가될 때마다 같은 양식으로 채우면, 그것이 곧 조직의 **공동 책임 대장(responsibility register)** 이 됩니다. 이 대장이 없으면 3장의 위협 모델링에서 신뢰 경계를 그릴 수 없습니다.

## 이 장의 요약

| 항목 | 핵심 |
|---|---|
| **두 개의 전치사** | security **of** the cloud = AWS / security **in** the cloud = 고객 |
| **가장 중요한 한 문장** | "많은 보안 사고의 근본 원인은 클라우드 제공자가 처리하고 있으리라는 가정이었고, 알고 보니 아무도 처리하고 있지 않았다"(*Practical Cloud Security* 1·2판 1장) |
| **회색 지대 판별법** | "망가뜨릴 능력이 있으면 보호할 책임도 있다" — 콘솔·API로 내가 바꿀 수 있으면 내 책임 |
| **서비스 모델과 무관하게 항상 고객 책임** | ① 데이터 접근 통제(IAM·리소스 정책) ② 로깅 활성화 ③ 암호화 강제 정책 ④ 백업·복원 검증 ⑤ AZ 분산 설계 |
| **관리형 서비스의 효과** | 리스크 **전가**이지 리스크 **제거**가 아님. 실수 개수↓, 실수 하나의 폭발 반경↑ |
| **관리형 서비스의 대표 실패 유형** | 코드 취약점이 아니라 **설정 오류**. 그래서 IaC + Config 규칙으로 코드 리뷰 대상에 올려야 함 |
| **도입 절차** | 새 서비스마다 2.5의 18개 질문 → 답을 표로 남겨 조직의 공동 책임 대장으로 축적 |

## 🔴 필수 구성 체크리스트

- [ ] ShopMini의 모든 구성요소에 대해 **"이 계층은 AWS가 패치하는가, 내가 하는가"** 를 표로 답할 수 있다
- [ ] RDS `shopmini-prod-mysql` 은 **저장 암호화가 켜진 상태로 생성**되었다 (생성 후에는 못 켠다)
- [ ] RDS 파라미터 그룹에서 **`require_secure_transport` 가 켜져** 평문 연결이 거부된다
- [ ] `shopmini-uploads` 버킷 정책에 **비-KMS 업로드 거부 + `aws:SecureTransport: false` 거부**가 있다
- [ ] 계정·리전 단위로 **EBS 기본 암호화**가 활성화되어 있다
- [ ] `auto minor version upgrade` 가 꺼진 RDS 인스턴스가 **없다**
- [ ] **지원 종료된 Lambda 런타임**을 쓰는 함수가 없다
- [ ] 컨테이너 이미지가 **정기적으로 재빌드·재배포**된다 (Fargate는 이미지를 갱신해주지 않는다)
- [ ] S3 **버저닝**과 DynamoDB **PITR**이 켜져 있다 (둘 다 기본값은 꺼짐)
- [ ] 백업 사본이 **운영 계정 밖(`777788889999`)** 에 존재한다
- [ ] 최근 3개월 안에 **실제 복원을 수행하고 RTO를 측정**했다
- [ ] 운영 RDS는 **Multi-AZ**이고, 모든 서브넷 계층이 `2a`·`2c` 양쪽에 존재한다
- [ ] **NAT 게이트웨이가 AZ마다** 있고 라우팅 테이블이 AZ별로 분리되어 있다
- [ ] 워크로드 역할에 **AWS 관리형 광범위 정책**(`AmazonS3FullAccess` 등)이 붙어 있지 않다
- [ ] 새 서비스 도입 시 2.5의 **18개 질문 답변이 문서로 남는다**

## ⚠️ 자주 하는 실수

| 실수 | 결과 | 올바른 구성 |
|---|---|---|
| "AWS가 암호화한다"로 암호화 항목을 끝낸다 | AWS 소유 키로 암호화되어 **접근 차단 수단이 없음**, 평문 전송도 허용됨 | 고객 관리형 KMS 키 + 버킷 정책·파라미터로 강제 (2.3①) |
| RDS를 만든 뒤 암호화를 켜려 한다 | 생성 후 불가 — 스냅샷 복원 마이그레이션과 다운타임 필요 | 생성 시 `--storage-encrypted` (2.3①) |
| "관리형이니까 패치는 자동"이라고 믿는다 | Fargate 플랫폼은 갱신돼도 **이미지 안 라이브러리는 그대로** | 서비스별 패치 책임표를 만들고 이미지 재빌드 파이프라인 구성 (2.3②) |
| EKS를 쓰면서 노드 AMI를 방치한다 | 컨트롤 플레인만 최신, **워커 노드는 수개월 미패치** | 노드 그룹 AMI 갱신 주기와 클러스터 버전 EOL 추적 (2.3②) |
| 내구성(durability)을 백업으로 오해한다 | 삭제·덮어쓰기·랜섬웨어에 무방비 | 버저닝·PITR·Object Lock + 교차 계정 백업 (2.3③) |
| 백업을 운영 계정 안에만 둔다 | 운영 계정 침해 시 백업까지 삭제됨 | 백업 볼트를 `777788889999` 로 분리 (2.3③) |
| 백업만 하고 복원을 안 해본다 | 사고 당일에야 복원이 며칠 걸린다는 것을 알게 됨 | 분기별 복원 훈련 + RTO 측정 (2.3③) |
| 워크로드 역할에 `*FullAccess` 를 붙인다 | SSRF 하나로 계정의 모든 버킷이 노출 | 리소스·액션 한정 인라인 정책 (2.3④) |
| ALB만 이중화하고 NAT·RDS는 단일 AZ | AZ 하나가 죽으면 **전체가 죽음** (리스크 합산) | 모든 계층을 `2a`·`2c` 쌍으로, NAT는 AZ별 (2.3⑤) |
| 관리형 서비스로 옮기고 보안 검토를 줄인다 | 설정 오류 표면이 커진 상태에서 검토가 사라짐 | IaC + Config 규칙 + Security Hub로 설정을 코드 리뷰 대상에 올림 (2.4) |
| Lambda 함수마다 역할을 즉석에서 만든다 | 수십 개 역할이 검토 없이 누적 → 인벤토리 붕괴 | 역할 생성을 IaC로 강제하고 권한 경계로 상한선 설정 (2.4, 7·37장) |

## 다음 장 예고

이제 "무엇이 내 책임인가"의 목록이 생겼습니다. 다음 질문은 **"그 책임 범위 안에서 누가 나를 공격하는가, 그리고 어디를 먼저 지켜야 하는가"** 입니다. 3장에서는 위협 행위자를 네 부류로 나누고, ShopMini의 데이터 흐름도를 그려 신뢰 경계(trust boundary)를 표시합니다. 원서의 표현대로, **선이 신뢰 경계를 가로지르는 모든 지점이 가장 먼저 지켜야 할 곳**입니다. 노출된 액세스 키, 퍼블릭 S3 버킷, IMDS 악용, 크로스 계정 신뢰 오설정 같은 클라우드 특유의 공격 경로도 함께 다룹니다.
