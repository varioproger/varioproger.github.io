# 12장. 데이터 자산 식별·분류·태깅

> **이 장에서 다루는 것**
> - "내 데이터가 어디 있는지 모른다"가 클라우드에서 구조적으로 발생하는 이유와, 역설적으로 클라우드가 그 해답을 쥐고 있는 이유
> - **식별·분류의 실행 절차** 🔴 — 열거 → 매핑 → 등급 할당 → 태그 부착 → 상시 재검증
> - **태깅 전략 설계** 🔴 — 필수 태그 5종, 강제 3층(태그 정책 / SCP / Config 규칙)
> - **Amazon Macie** 🧪 — 자동 검색, 분류 작업, 사용자 지정 데이터 식별자, EventBridge → Security Hub
> - **자산 관리 파이프라인의 4가지 누수** ⚠️ — 조달·처리·도구·결과 누수와 각각의 탐지법
> - 데이터 보존과 파기 — 라이프사이클 규칙, 암호 삭제(cryptographic erasure), 백업과의 충돌
>
> **선행 지식**: 4장(데이터 분류 4단계, 규제 지형), 8장(ABAC과 태그 조건 키), 11장(시크릿도 데이터 자산이다)
> **난이도**: ★★☆

---

3부가 시작됩니다. 2부는 "누가 무엇을 할 수 있는가"에 답했습니다. 이제 질문은 **"무엇을 지켜야 하는가"** 입니다.

보통은 지킬 것을 먼저 정하고 접근 통제를 걸지만, 실제 조직에서 이 순서는 거의 지켜지지 않습니다. IAM은 계정 첫날부터 필요해 급하게 세워지고, 데이터 인벤토리는 "언젠가 할 일"로 남습니다. 그리고 침해 사고가 나면 가장 먼저 무너지는 것이 **"무엇이 유출되었습니까?"** 라는 질문입니다.

> 📖 *Practical Cloud Security* 1판·2판 2장은 자산 관리를 두 갈래로 나눕니다. **"데이터 자산은 고객 이름과 주소, 신용카드 정보, 또는 그런 데이터에 접근하는 자격 증명처럼 당신이 가진 중요한 정보다. 클라우드 자산은 그 데이터를 저장하고 처리하는 것들 — 컴퓨트 자원, 스토리지, 데이터베이스나 큐 같은 플랫폼 인스턴스 — 이다."** 그리고 **"나는 데이터 자산에서 시작하는 것이 더 쉽다고 본다"** 고 순서를 권합니다.

4장에서 **무엇을 어떤 등급으로 부를지**(공개/내부/기밀/극비)는 이미 정했습니다. 이 장은 그 등급을 **실제 AWS 리소스에 붙이고, 붙지 않은 것을 찾아내고, 붙은 것을 강제하는** 일을 다룹니다.

## 12.1 "내 데이터가 어디 있는지 모른다" 문제

### 조달 장벽이 사라졌다

온프레미스 시대에 서버 한 대를 늘리는 일은 어려웠고, 그 어려움이 곧 통제였습니다.

> 📖 *Practical Cloud Security* 1판·2판 3장은 이 변화를 정확히 짚습니다. **"전통적인 IT 환경에서 서버 같은 자산을 만드는 일은 종종 어렵고 시간이 많이 걸린다. (…) 섀도 IT(숨겨져 있거나 공식적으로 사용 승인되지 않은 IT 자원)를 만드는 데는 자연적인 장벽이 있는데, IT가 통상 자본 자산을 필요로 하기 때문이다."**
>
> 그리고 클라우드가 그 장벽을 없앴다고 씁니다. **"비즈니스의 어느 영역에 있는 누구든 신용카드 한 장만으로(때로는 그것조차 없이) 엄청난 수의 IT 자원을 쉽게 프로비저닝할 수 있다. (…) 클라우드 시대에 이 문제는 종종 훨씬 더 심각하며, 그 자산은 서버만이 아니다."**

마지막 문장이 핵심입니다. **자산은 서버만이 아닙니다.** ShopMini 개발자가 디버깅을 위해 운영 DB를 덤프해 임시 S3 버킷에 올리는 데는 승인도 결재도 필요 없습니다. 그 버킷은 인벤토리에 없고, 태그가 없고, 스캐너 대상이 아니며, 라이프사이클 규칙도 없습니다. **누구도 잘못한 사람이 없는데 기밀 데이터가 통제 밖에 놓입니다.**

### 그런데 클라우드가 답도 쥐고 있다

> 📖 같은 원서 2장 「Data Asset Management in the Cloud」는 이렇게 씁니다. **"클라우드 제공자는 당신이 데이터를 식별하고 분류하는 것을 도울 수 있는 독특한 위치에 있다. 우선, 그들은 당신이 데이터를 저장하고 있는 모든 곳을 알려줄 수 있다. 저장에 대해 요금을 청구하고 싶어 하기 때문이다!"**
>
> 이어서 표준화의 이점을 덧붙입니다. **"많은 경우 클라우드에 있는 당신의 영구 데이터는 객체 스토리지, 파일 스토리지, 블록 스토리지, 클라우드 데이터베이스, 클라우드 메시지 큐 중 하나에 있게 되며, 여러 물리 서버에 붙은 수천 개의 서로 다른 디스크에 흩어져 있지 않다."**

온프레미스에서 "우리 데이터가 어디 있나"는 창고를 뒤져야 답이 나왔습니다. AWS에서는 **API 호출 몇 번이면 계정 안의 모든 저장소가 열거됩니다.** 문제는 그 API를 아무도 정기적으로 호출하지 않는다는 것입니다.

| 온프레미스 | AWS |
|---|---|
| 자산 생성에 조달·결재 장벽이 있음 → 자연적 통제 | 장벽 없음 → 섀도 리소스가 기본값 |
| 데이터 위치가 물리적으로 흩어짐 → 열거 불가능 | 저장 서비스가 유한하게 표준화됨 → **열거 가능** |
| 인벤토리는 수작업 스프레드시트 | Config·Resource Explorer·Tagging API로 **자동화 가능** |
| 데이터 내용 파악은 사실상 불가 | Macie가 **내용까지 스캔** |

**클라우드에서 인벤토리가 없는 것은 불가능해서가 아니라 하지 않아서입니다.** 이 장의 나머지는 "하는 방법"입니다.

### 보이지 않는 데이터 자산

인벤토리를 만들 때 가장 흔한 실패는 **"데이터베이스와 업로드 버킷"만 세는 것**입니다.

> 📖 원서 1판·2판 2장은 노트 박스로 먼저 경고합니다. **"중요한 데이터를 식별할 때, 그 데이터를 읽거나 수정하는 데 쓸 수 있는 비밀번호, API 키, 그 밖의 시크릿을 잊지 말라!"** 그리고 데이터베이스 외의 자산을 짚습니다. **"웹 서버에는 당신의 고객을 식별하는 데 쓰일 수 있는 로그 데이터가 있다. 웹 서버에는 TLS 인증서의 사설 키가 있는데, 그것과 약간의 DNS 또는 BGP 하이재킹만 있으면 누구든 당신의 사이트인 척하고 고객이 로그인하려 할 때 비밀번호를 훔칠 수 있다."** 그리고 정리합니다. **"이렇게 정말 단순한 애플리케이션에서조차 보호해야 할 비자명한 것들이 많이 있다."**

ShopMini로 옮기면 이렇습니다.

| 누구나 세는 자산 | 거의 항상 빠지는 자산 | 등급 |
|---|---|---|
| RDS MySQL(회원·주문) | RDS **스냅샷**, 자동 백업, 읽기 전용 복제본 | 기밀 |
| `shopmini-uploads` 버킷 | ALB **액세스 로그**·CloudFront 로그(IP·UA·쿠키 포함) | 기밀 |
| — | CloudWatch Logs의 애플리케이션 로그(예외 스택에 실린 파라미터) | 기밀 |
| — | ACM 인증서와 앱이 직접 들고 있는 **TLS 사설 키** | 극비 |
| — | 비밀번호 해시(자체 인증을 쓴다면), 세션 서명 키 | 극비 |
| — | `rds/shopmini` 시크릿, Parameter Store `SecureString` (11장) | 극비 |
| — | **AMI와 EBS 스냅샷** — 만들 당시 디스크의 데이터가 그대로 | 기밀~극비 |
| — | SQS 큐 메시지, Kinesis 스트림, DynamoDB 테이블 | 기밀 |
| — | 분석용 Athena 결과 버킷, Glue 데이터 카탈로그 | 기밀 |
| — | 개발자 노트북에서 만든 임시 덤프 버킷 | **미지수** |

마지막 줄이 가장 위험합니다. **등급을 모르는 자산은 최고 등급으로 간주해야 합니다.**

## 12.2 데이터 식별과 분류 실행 🔴

4.2에서 `DataClass` 태그 키와 네 개의 값(`Public` / `Internal` / `Confidential` / `Restricted`), 등급별 필수 통제 매트릭스를 확정했습니다. 이 절은 그 정의를 반복하지 않고 **실제 계정에 적용하는 5단계 절차**만 다룹니다.

### 🔴 반드시 이 순서로 하십시오

| 단계 | 하는 일 | 산출물 | 도구 |
|---|---|---|---|
| ① **열거** | 계정·리전별로 데이터를 담을 수 있는 모든 리소스를 뽑는다 | 원시 리소스 목록 | Config 어그리게이터, Resource Explorer, Tagging API |
| ② **매핑** | 각 저장소에 어떤 데이터 유형이 들어가는지 소유자에게 확인한다 | 데이터 인벤토리 대장 | 사람 — 자동화 불가 |
| ③ **할당** | 유형을 4등급 중 하나로 매핑한다. 한 저장소에 여러 유형이 섞이면 **가장 높은 등급** | 등급이 달린 대장 | 4.2 매트릭스 |
| ④ **부착** | `DataClass` 등 필수 태그를 실제 리소스에 붙인다 | 태그가 달린 리소스 | Tagging API, IaC |
| ⑤ **재검증** | 태그 누락·오기·신규 리소스를 상시 탐지한다 | Config 비준수 목록 | Config `required-tags`, Macie |

**①과 ④·⑤는 자동화하고, ②·③은 자동화하지 마십시오.** Macie는 "이 버킷에 주민등록번호처럼 보이는 문자열이 있다"까지 말해줄 뿐, **그것이 실제로 고유식별정보인지, 소유자가 누구인지, 어느 규제 대상인지는 기계가 답할 수 없습니다.**

### ① 열거 — 실제 명령

가장 넓은 그물은 Resource Groups Tagging API입니다. 태그 유무와 무관하게 리전 내 리소스를 열거하고 **태그가 없는 것을 그대로 드러냅니다.**

```bash
# 리전의 모든 리소스 ARN과 태그를 덤프
aws resourcegroupstaggingapi get-resources \
  --region ap-northeast-2 \
  --profile awssec-lab \
  --output json > /tmp/inventory-apne2.json

# DataClass 태그가 없는 리소스만 추출
jq -r '.ResourceTagMappingList[]
       | select((.Tags | map(.Key) | index("DataClass")) == null)
       | .ResourceARN' /tmp/inventory-apne2.json
```

조직 전체는 Config 어그리게이터 고급 쿼리로 계정·리전을 가로질러 조회합니다.

```bash
aws configservice select-aggregate-resource-config \
  --configuration-aggregator-name shopmini-org-aggregator \
  --expression "SELECT accountId, awsRegion, resourceType, resourceId, tags
                WHERE resourceType IN (
                  'AWS::S3::Bucket',
                  'AWS::RDS::DBInstance',
                  'AWS::RDS::DBSnapshot',
                  'AWS::DynamoDB::Table',
                  'AWS::EC2::Volume',
                  'AWS::EC2::Snapshot',
                  'AWS::EFS::FileSystem'
                )" \
  --profile awssec-lab
```

> 📖 원서 1판·2판 3장 「Processing Leaks」는 클라우드별 감사 수단을 표로 정리하면서 AWS 항목에 **"API, 포털, 명령줄, AWS Systems Manager Inventory"** 를 적었습니다. 인스턴스 **내부**까지 봐야 할 때는 SSM Inventory가 필요합니다. 인벤토리 자격 증명의 권한 범위에 대한 각주도 명확합니다. **"인벤토리 시스템은 메타데이터 외에는 아무것도 읽을 필요가 없고, 태그 외에는 아무것도 수정할 필요가 없다."**

마지막 문장을 그대로 실행하십시오. 인벤토리 역할에는 `ReadOnlyAccess`가 아니라 **메타데이터 조회 + `tag:GetResources` + 태그 쓰기 권한만** 부여합니다. `ReadOnlyAccess`에는 `s3:GetObject`가 포함되어 있어 이 역할이 침해되면 그 자체로 데이터 유출 경로가 됩니다.

### ② ③ 매핑과 할당 — 데이터 인벤토리 대장

대장은 스프레드시트여도 되지만 **반드시 소유자 열이 있어야 합니다.** 소유자 없는 행은 6개월 뒤 아무도 손대지 못합니다.

| 저장소 | 데이터 유형 | 등급 | 소유자 | 규제 | 보존 |
|---|---|---|---|---|---|
| `shopmini-assets` | 상품 이미지·정적 자산 | Public | 프론트엔드팀 | — | 무기한 |
| `shopmini-uploads` | 회원 업로드(리뷰 사진, 반품 증빙) | Confidential | 커머스팀 | 개인정보보호법 | 5년 |
| RDS `shopmini-prod` | 회원·주문·배송지 | Confidential | 커머스팀 | 개인정보보호법·ISMS-P | 5년(회원 탈퇴 시 파기) |
| RDS 자동 백업·스냅샷 | 위와 동일 | **Confidential** | 플랫폼팀 | 동일 | 35일 |
| ALB/CloudFront 액세스 로그 | IP·User-Agent·요청 경로 | Confidential | 플랫폼팀 | 개인정보보호법 | 1년 |
| CloudWatch Logs `/shopmini/app` | 애플리케이션 로그 | Confidential | 백엔드팀 | — | 1년 |
| Secrets Manager `rds/shopmini` | DB 자격 증명 | Restricted | 플랫폼팀 | — | 순환 주기 |
| KMS `alias/shopmini/app` | 키 자료 | Restricted | 보안팀 | — | 영구 |

**"RDS 자동 백업·스냅샷"이 별도 행이라는 점이 이 표의 핵심입니다.** 원본 DB에 통제를 걸고 스냅샷은 잊는 것이 가장 흔한 사고 경로입니다(16.7).

### ⑤ 재검증 — 이것이 없으면 앞의 넷은 1회성 프로젝트

> 📖 원서 1판·2판 2장은 자동 검증을 권합니다. **"일부 클라우드 제공자는 태그가 제대로 적용되었는지 확인하는 자동화까지 제공한다. 그래서 태그가 없거나 잘못 달린 리소스를 조기에 찾아 바로잡을 수 있다."**

AWS에서 그 자동화는 **Config 관리형 규칙 `required-tags`(식별자 `REQUIRED_TAGS`)** 이고, 구성은 12.3에서 다룹니다.

**⑤를 빼면** 분류는 3개월짜리 프로젝트로 끝나고, 6개월 뒤 신규 서비스와 그에 딸린 버킷·큐는 대장에 없습니다. **인벤토리는 프로젝트가 아니라 상시 통제입니다.**

## 12.3 태깅 전략 설계 🔴

### 태그 표준이 없으면 태그는 노이즈다

> 📖 *Practical Cloud Security* 1판·2판 2장 「Tagging Cloud Resources」는 문제를 한 문장으로 요약합니다. **"문제는 분명하다. 조직의 모든 사람이 서로 다른 태그를 쓰면 태그는 별로 쓸모가 없다!"** 1판은 **"언제 반드시 사용해야 하는지에 대한 설명이 붙은 태그 목록을 만들고, 리소스가 생성될 때 자동화 도구가 그것을 적용하도록 요구하라"** 고 처방하며, 2판은 여기에 **"태그를 사용하라는 정책을 두라"** 와 **"큰 조직에서는 이 태그 표준을 담당 소유자가 지정되고 주기적으로 검토되는, 버전이 매겨진 하위 호환 표준으로 다루어야 한다"** 를 더합니다.
>
> 그리고 실무에서 반드시 아프게 만드는 한 줄이 노트로 붙어 있습니다(1판·2판 3장). **"많은 클라우드 제공자에서 태그는 대소문자를 구분하므로 `ApplicationA`와 `applicationA`는 일치하지 않는다."**

마지막 경고를 AWS로 옮기면 이렇습니다. **`DataClass`, `dataclass`, `Data-Class`가 각각 존재하는 계정에서는 태그 기반 IAM 조건도, Config 규칙도, 비용 배분 리포트도 전부 조용히 빗나갑니다.** 정책은 오류 없이 평가되고 단지 아무것도 매칭하지 않습니다.

### 🔴 필수 태그 5종

**모든 리소스에 다음 5개 태그를 붙이고, 값 도메인은 열거형으로 고정하십시오. 자유 입력을 허용하지 마십시오.**

| 태그 키 | 허용 값 | 용도 | 없으면 |
|---|---|---|---|
| `Owner` | 팀 별칭 또는 메일 그룹 (`commerce@`, `platform@`) | 사고 시 연락 대상, 비준수 리소스 정리 책임 | 리소스를 지울 수도 살릴 수도 없어 영구 방치 |
| `DataClass` | `Public` / `Internal` / `Confidential` / `Restricted` | 4.2 통제 매트릭스의 진입점. IAM·SCP 조건 키 | 통제 수준이 담당자의 감으로 결정됨 |
| `Environment` | `prod` / `stage` / `dev` / `sandbox` | 환경별 정책 분기, "운영 데이터가 dev에 있는가" 탐지 | 운영 데이터가 개발 환경에 복사돼도 못 찾음 |
| `CostCenter` | 회계 코드 (`CC-1042`) | 비용 배분 → **조달 누수 탐지의 축**(12.5) | 정체불명의 비용이 "기타"로 뭉개짐 |
| `Compliance` | `pci` / `pii` / `none` (복수는 하이픈 결합) | 규제 범위 산정, 감사 증적 추출 | 감사 때마다 전수 조사 |

> 📖 원서 1판·2판 3장 「Tagging Cloud Assets」는 그 밖의 태그 유형으로 **"자산의 기능 / 환경 유형 / 애플리케이션 또는 프로젝트 / 자산을 책임지는 부서 / 버전 번호 / 자동화 태그"** 를 열거하고, 일관성을 강조합니다. **"컴퓨트 자산에서 처리되는 데이터 유형을 나타내는 데 2장의 동일한 데이터 태그를 쓰는 것이 중요하다."**

따라서 `DataClass`는 저장소에만 붙이는 태그가 아닙니다. **기밀 데이터를 처리하는 EC2 인스턴스·Lambda 함수에도 같은 값을 붙이십시오.** 저장소에만 붙이면 데이터가 흘러가는 곳을 놓칩니다.

> 📖 원서 1판·2판 3장은 이 태그로 만드는 자동화를 예시합니다. **"민감한 데이터는 개발·테스트 시스템에 저장되거나 접근되어서는 안 된다는 아주 합리적인 정책이 있다고 하자. 이를 강제하기 위해 (…) `dataclass:sensitive-data` 태그와 `environment:development` 또는 `environment:test` 태그를 함께 가진 자산의 리포트를 만든다."**

AWS에서는 Config 고급 쿼리 한 줄입니다.

```bash
aws configservice select-aggregate-resource-config \
  --configuration-aggregator-name shopmini-org-aggregator \
  --expression "SELECT accountId, awsRegion, resourceType, resourceId
                WHERE tags.key = 'DataClass' AND tags.value = 'Confidential'" \
  --profile awssec-lab
```

결과를 `Environment=dev`인 집합과 교집합하면 **"기밀 데이터가 개발 환경에 있다"** 는 보고서가 나옵니다. 여기에 행이 나오면 사고 직전입니다.

### 🔴 태그 강제 3층

태그는 **붙이라고 말해서는 절대 붙지 않습니다.** 세 층을 모두 쓰십시오 — 하나만으로는 반드시 구멍이 남습니다.

| 층 | 수단 | 작동 시점 | 막는 것 | 한계 |
|---|---|---|---|---|
| ① 값 표준화 | **Organizations 태그 정책** | 태그 부착 시점 | `DataClass=confidental` 같은 **오기·대소문자 불일치** | **태그가 아예 없는 것은 못 막음.** 지원 리소스 유형 한정 |
| ② 생성 차단 | **SCP + `aws:RequestTag` / `aws:TagKeys`** | 리소스 **생성 요청** 시점 | 태그 없이 만드는 행위 자체 | `aws:RequestTag`를 지원하지 않는 API가 있음(대표: `s3:CreateBucket`) |
| ③ 사후 탐지 | **Config 규칙 `required-tags`** | 생성 후 수 분 | ①②를 빠져나간 모든 것 | 이미 만들어진 뒤 — 예방이 아님 |

#### ① Organizations 태그 정책

태그 정책은 **태그 키의 표기와 허용 값 집합을 조직 차원에서 고정**합니다.

```json
{
  "tags": {
    "DataClass": {
      "tag_key": { "@@assign": "DataClass" },
      "tag_value": {
        "@@assign": ["Public", "Internal", "Confidential", "Restricted"]
      },
      "enforced_for": {
        "@@assign": [
          "ec2:instance",
          "ec2:volume",
          "s3:bucket",
          "rds:db",
          "dynamodb:table",
          "secretsmanager:secret"
        ]
      }
    },
    "Environment": {
      "tag_key": { "@@assign": "Environment" },
      "tag_value": { "@@assign": ["prod", "stage", "dev", "sandbox"] }
    },
    "Owner": {
      "tag_key": { "@@assign": "Owner" }
    }
  }
}
```

```bash
aws organizations create-policy \
  --name shopmini-tag-standard \
  --type TAG_POLICY \
  --description "ShopMini 필수 태그 값 표준" \
  --content file://tag-policy.json \
  --profile awssec-lab
```

`enforced_for`에 나열한 리소스 유형은 **규정을 어기는 태그 부착 요청이 거부됩니다.** 나열하지 않으면 위반이 "비준수"로 **보고만** 되고 차단되지 않습니다.

⚠️ **가장 많이 오해하는 지점: 태그 정책은 "이 태그를 반드시 달아라"를 강제하지 않습니다.** `Owner`처럼 `tag_value` 없이 키만 선언하면 표기법만 고정될 뿐, `Owner` 없이 리소스를 만드는 것은 자유입니다. 필수성은 ②와 ③의 몫입니다.

#### ② SCP로 생성 시점에 차단

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyCreateWithoutDataClass",
      "Effect": "Deny",
      "Action": [
        "ec2:RunInstances",
        "ec2:CreateVolume",
        "rds:CreateDBInstance",
        "rds:CreateDBCluster",
        "dynamodb:CreateTable",
        "lambda:CreateFunction",
        "secretsmanager:CreateSecret"
      ],
      "Resource": "*",
      "Condition": {
        "Null": {
          "aws:RequestTag/DataClass": "true"
        }
      }
    },
    {
      "Sid": "DenyInvalidDataClassValue",
      "Effect": "Deny",
      "Action": "*",
      "Resource": "*",
      "Condition": {
        "StringNotEqualsIfExists": {
          "aws:RequestTag/DataClass": [
            "Public",
            "Internal",
            "Confidential",
            "Restricted"
          ]
        }
      }
    },
    {
      "Sid": "DenyRemovalOfGovernedTags",
      "Effect": "Deny",
      "Action": [
        "ec2:DeleteTags",
        "rds:RemoveTagsFromResource",
        "dynamodb:UntagResource",
        "lambda:UntagResource",
        "kms:UntagResource",
        "secretsmanager:UntagResource"
      ],
      "Resource": "*",
      "Condition": {
        "ForAnyValue:StringEquals": {
          "aws:TagKeys": ["DataClass", "Owner", "Compliance"]
        },
        "ArnNotLike": {
          "aws:PrincipalArn": "arn:aws:iam::*:role/ShopMiniTagAdminRole"
        }
      }
    }
  ]
}
```

세 문장의 역할은 각각 다릅니다.

- **`DenyCreateWithoutDataClass`** — `Null` 연산자로 "요청에 `DataClass` 태그 키가 **없으면**"을 표현합니다(7.4 조건 연산자 표). 값과 무관하게 **존재**를 강제합니다.
- **`DenyInvalidDataClassValue`** — `IfExists` 접미사가 없으면 `DataClass` 태그를 보내지 않는 모든 API 호출(예: `s3:ListBucket`)이 조건을 만족해 **계정 전체가 잠깁니다.** 첫 문장이 존재를, 둘째 문장이 값의 유효성을 담당하도록 나눈 이유입니다.
- **`DenyRemovalOfGovernedTags`** — 붙이게 만들어놓고 떼는 것을 막지 않으면 통제는 우회 한 번으로 무력화됩니다. `ArnNotLike`로 태그 관리 역할만 예외 처리합니다.

⚠️ **`s3:CreateBucket`이 목록에 없는 이유.** S3는 버킷 생성 요청에 태그를 실을 수 없고 태그는 별도의 `s3:PutBucketTagging` 호출로 붙습니다. 따라서 `aws:RequestTag`로 "태그 없는 버킷 생성"을 막는 SCP는 **작동하지 않습니다.** 이 구멍은 ③으로만 메웁니다. "SCP를 걸었으니 됐다"고 넘어가면 하필 가장 많이 유출되는 리소스 유형이 통제 밖에 남습니다.

#### ③ Config 규칙으로 사후 탐지

```bash
aws configservice put-config-rule \
  --config-rule '{
    "ConfigRuleName": "shopmini-required-tags",
    "Description": "필수 태그 5종 및 DataClass 값 도메인 검증",
    "Source": {
      "Owner": "AWS",
      "SourceIdentifier": "REQUIRED_TAGS"
    },
    "Scope": {
      "ComplianceResourceTypes": [
        "AWS::S3::Bucket",
        "AWS::RDS::DBInstance",
        "AWS::EC2::Instance",
        "AWS::EC2::Volume",
        "AWS::DynamoDB::Table"
      ]
    },
    "InputParameters": "{\"tag1Key\":\"Owner\",\"tag2Key\":\"DataClass\",\"tag2Value\":\"Public,Internal,Confidential,Restricted\",\"tag3Key\":\"Environment\",\"tag3Value\":\"prod,stage,dev,sandbox\",\"tag4Key\":\"CostCenter\",\"tag5Key\":\"Compliance\"}"
  }' \
  --profile awssec-lab
```

`tagNValue`는 쉼표로 구분된 허용 값 목록이고, 생략하면 **키의 존재만** 검사합니다. `CostCenter`처럼 값이 계속 늘어나는 태그는 값을 지정하지 않습니다.

비준수 리소스 교정은 Config 자동 교정(remediation)에 SSM Automation 문서를 연결해 처리합니다. 다만 **태그 값을 기계가 정할 수는 없으므로** 실무에서 쓸 만한 교정은 "소유자 알림 + 72시간 내 미조치 시 격리"입니다(구성은 35.3).

### 태그 부착과 확인

```bash
# 버킷에 필수 태그 부착
aws s3api put-bucket-tagging \
  --bucket shopmini-uploads \
  --tagging '{
    "TagSet": [
      {"Key": "Owner",       "Value": "commerce@example.com"},
      {"Key": "DataClass",   "Value": "Confidential"},
      {"Key": "Environment", "Value": "prod"},
      {"Key": "CostCenter",  "Value": "CC-1042"},
      {"Key": "Compliance",  "Value": "pii"},
      {"Key": "Project",     "Value": "awssec-lab"},
      {"Key": "Chapter",     "Value": "ch12"}
    ]
  }' \
  --profile awssec-lab

# 여러 리소스에 한 번에 붙이기 (ARN 목록 기반)
aws resourcegroupstaggingapi tag-resources \
  --resource-arn-list \
    arn:aws:rds:ap-northeast-2:111122223333:db:shopmini-prod \
    arn:aws:dynamodb:ap-northeast-2:111122223333:table/shopmini-sessions \
  --tags Owner=platform@example.com,DataClass=Confidential,Environment=prod \
  --profile awssec-lab
```

⚠️ **`put-bucket-tagging`은 기존 태그 집합을 전부 교체합니다.** `get-bucket-tagging`으로 먼저 읽어 병합하지 않으면 다른 팀이 붙인 태그가 조용히 사라집니다. `tag-resources`는 병합 방식이라 이 위험이 없습니다.

### 태그로 접근을 통제하기

`DataClass`를 IAM 조건 키로 읽어 접근을 가르는 방식 — ABAC — 은 **8.7에서 다뤘습니다.** `aws:ResourceTag/DataClass`, `aws:PrincipalTag`, 세션 태그와 `--transitive-tag-keys`를 그대로 이 장의 태그 표준에 적용하면 됩니다.

한 가지만 강조합니다. **ABAC은 태그가 정확하다는 전제 위에서만 통제입니다.** 태그가 없는 리소스에는 조건이 매칭되지 않고, Allow 정책이라면 **접근이 막히고** Deny 정책이라면 **접근이 열립니다.** 그래서 태그 강제 3층이 ABAC보다 먼저 서야 합니다.

## 12.4 Amazon Macie로 민감 데이터 자동 발견 🧪

### 원서의 Macie와 지금의 Macie는 다른 서비스다

> 💡 **원서 이후 변경** — *AWS Security Cookbook*(2020) 9장 「Setting up and using Amazon Macie」가 기술한 Macie와 현재의 Macie는 사실상 다른 서비스입니다. 원서의 Macie는 **CloudTrail 이벤트 분석과 S3 콘텐츠 분류를 함께** 수행했고, 사용자를 **Platinum / Gold / Silver / Bronze** 로 등급화했으며, RESEARCH 탭에서 **Apache Lucene 질의 구문**으로 결과를 검색했습니다. 원서는 **"이 글을 쓰는 시점에 Macie는 US East(버지니아 북부)와 US West(오리건)에서만 사용 가능하다"** 고 적었고, 알림은 **CloudWatch Events 규칙 → SNS 주제** 로 연결했습니다.
>
> 현재 Macie는 **S3의 민감 데이터 발견에 집중**하고, CloudTrail 기반 사용자 행위 분석과 사용자 등급 개념은 없어졌습니다(그 영역은 GuardDuty와 CloudTrail Lake가 담당합니다). 리전도 서울(`ap-northeast-2`)을 포함해 대부분의 리전에서 쓸 수 있고, 결과는 **EventBridge와 Security Hub로 직접 전달**됩니다. 아래 실습은 현재 API(`macie2`) 기준입니다. 원서의 콘솔 절차를 그대로 따라 하면 화면이 존재하지 않습니다.

> 📖 *AWS Security Cookbook* 9장: **"Macie는 S3 버킷의 데이터를 분석해 개인식별정보(PII), API 키, 소스 코드 같은 민감 정보를 찾아내고 이를 서로 다른 보안 등급으로 분류할 수 있다."** 그리고 **"일반적으로 더 나은 보호를 위해서는 Macie를 GuardDuty와 함께 쓰는 것이 바람직하다"** — 두 서비스가 서로를 대체하지 않는다는 점은 지금도 같습니다.

과금은 **버킷 인벤토리 평가 + 스캔한 객체의 바이트 수** 기준이며, **스코핑 없이 대용량 버킷을 전량 스캔하는 것이 이 장에서 가장 비싼 실수**입니다.

### 🧪 활성화와 자동 민감 데이터 검색

```bash
# 1) Macie 활성화 (보안 계정에서 위임 관리자로 운영하는 것을 권장)
aws macie2 enable-macie \
  --finding-publishing-frequency FIFTEEN_MINUTES \
  --status ENABLED \
  --region ap-northeast-2 \
  --profile awssec-lab

# 2) 조직 전체를 하나의 계정에서 보려면 위임 관리자 지정 (관리 계정에서 실행)
aws organizations register-delegated-administrator \
  --account-id 444455556666 \
  --service-principal macie.amazonaws.com

aws macie2 enable-organization-admin-account \
  --admin-account-id 444455556666 \
  --region ap-northeast-2

# 3) 자동 민감 데이터 검색 활성화 — 버킷을 표본 추출해 지속 평가
aws macie2 update-automated-discovery-configuration \
  --status ENABLED \
  --region ap-northeast-2 \
  --profile awssec-lab
```

**자동 민감 데이터 검색과 분류 작업(job)은 목적이 다릅니다** — 둘 다 켜십시오.

| | 자동 민감 데이터 검색 | 분류 작업(classification job) |
|---|---|---|
| 대상 | 계정의 **모든** S3 버킷 | 지정한 버킷·접두사 |
| 방식 | 객체를 **표본 추출**해 지속 평가 | 범위 내 객체를 정해진 규칙으로 스캔 |
| 주기 | 상시(일 단위 갱신) | 1회(`ONE_TIME`) 또는 예약(`SCHEDULED`) |
| 비용 | 상대적으로 낮음 | 스캔 바이트에 비례 — **스코핑 필수** |
| 쓰임 | "어느 버킷이 위험한가" 넓게 훑기 | "이 버킷에 정확히 무엇이 있나" 확정 |

자동 검색으로 후보를 좁힌 뒤 후보 버킷에만 분류 작업을 겁니다. 반대로 하면 비용이 통제되지 않습니다. 버킷 수준 현황부터 보십시오 — 이 명령은 객체를 스캔하지 않습니다.

```bash
aws macie2 describe-buckets \
  --criteria '{"publicAccess.effectivePermission":{"eq":["PUBLIC"]}}' \
  --region ap-northeast-2 \
  --profile awssec-lab
```

### 🧪 사용자 지정 데이터 식별자

관리형 데이터 식별자는 신용카드 번호, AWS 시크릿 액세스 키, 각종 사설 키, 국가별 신분증 번호 등을 다룹니다. 목록은 하드코딩하지 말고 조회해서 쓰십시오.

```bash
aws macie2 list-managed-data-identifiers --region ap-northeast-2 --profile awssec-lab
```

관리형 식별자로 덮이지 않는 **조직 고유 형식**은 사용자 지정 데이터 식별자로 만듭니다.

```bash
aws macie2 create-custom-data-identifier \
  --name "korea-rrn" \
  --description "주민등록번호 형식 (6자리-7자리)" \
  --regex '[0-9]{6}-[1-8][0-9]{6}' \
  --keywords "주민등록번호" "주민번호" "RRN" \
  --maximum-match-distance 50 \
  --severity-levels '[{"occurrencesThreshold":1,"severity":"HIGH"}]' \
  --region ap-northeast-2 \
  --profile awssec-lab
```

세 옵션이 오탐을 결정합니다.

- **`--keywords`** — 정규식 매칭 주변에 이 단어가 있어야 결과로 인정합니다. 주민등록번호 형식은 다른 숫자 조합과 우연히 일치하기 쉬워 키워드 없이 쓰면 오탐이 쏟아집니다.
- **`--maximum-match-distance`** — 키워드와 매칭 사이의 최대 문자 거리. 너무 크면 필터가 의미를 잃습니다.
- **`--severity-levels`** — 발견 건수 임계값별 심각도.

응답의 `customDataIdentifierId` 값을 아래 분류 작업에서 `$CDI_ID`로 씁니다. 테스트 픽스처처럼 **일부러 넣어둔 형식 문자열**이 계속 걸린다면 허용 목록(allow list)으로 제외합니다.

```bash
aws macie2 create-allow-list \
  --name "shopmini-test-fixtures" \
  --criteria '{"regex":"000000-0000000"}' \
  --client-token shopmini-ch12-allow-001 \
  --region ap-northeast-2 \
  --profile awssec-lab
```

### 결과를 통제로 연결하기

**Macie를 켜놓고 콘솔에서만 보는 것이 12.5의 "결과 누수"입니다.** 다음 흐름으로 연결하십시오.

```text
Macie 분류 작업 / 자동 검색
        │
        ├─→ Security Hub  (동일 계정·리전에서 둘 다 활성화 시 자동 연동)
        │        └─→ 31.5의 통합 대시보드에서 다른 결과와 함께 우선순위화
        │
        └─→ EventBridge  (source: aws.macie, detail-type: "Macie Finding")
                 ├─→ SNS      : 고심각도 즉시 통보
                 └─→ Lambda   : 발견된 버킷에 DataClass=Confidential 자동 태깅
                                + 소유자 티켓 자동 생성
```

```bash
aws events put-rule \
  --name macie-high-severity-findings \
  --event-pattern '{
    "source": ["aws.macie"],
    "detail-type": ["Macie Finding"],
    "detail": {
      "severity": {
        "description": ["High"]
      }
    }
  }' \
  --region ap-northeast-2 \
  --profile awssec-lab
```

결과를 장기 보관하려면 S3로 내보냅니다. Macie 내부 보존 기간은 유한하므로 **감사 증적으로 쓰려면 내보내기가 필수입니다.**

```bash
aws macie2 put-classification-export-configuration \
  --configuration '{
    "s3Destination": {
      "bucketName": "shopmini-macie-results",
      "keyPrefix": "findings/",
      "kmsKeyArn": "arn:aws:kms:ap-northeast-2:444455556666:key/EXAMPLE-KEY-ID"
    }
  }' \
  --region ap-northeast-2 \
  --profile awssec-lab
```

⚠️ **결과 내보내기 버킷 자체가 민감 데이터입니다.** Macie 결과에는 발견된 값의 위치와 컨텍스트가 담깁니다. 이 버킷은 `DataClass=Restricted`로 태깅하고 보안 계정(`444455556666`)에 두고 고객 관리형 KMS 키로 암호화하십시오. **민감 데이터를 찾으려고 만든 시스템이 새 민감 데이터 저장소가 되는 것**이 가장 흔한 자충수입니다.

### 📋 Macie 도입 점검

- [ ] 보안 계정을 위임 관리자로 지정해 **조직 전체** 결과를 한곳에서 본다
- [ ] 자동 민감 데이터 검색으로 전체 버킷을 넓게 훑는다
- [ ] 분류 작업에 **접두사·객체 크기 스코핑**을 반드시 건다
- [ ] 국내 고유 형식은 **사용자 지정 식별자 + 키워드**로 오탐을 줄인다
- [ ] 테스트 픽스처는 **허용 목록**으로 제외한다
- [ ] 결과를 Security Hub·EventBridge로 내보내고 **처리 담당자를 지정**한다
- [ ] 결과 내보내기 버킷을 `Restricted`로 취급한다
- [ ] Macie가 붙인 등급이 아니라 **사람이 확정한 등급**을 `DataClass`에 기록한다

## 12.5 자산 관리 파이프라인의 4가지 누수 ⚠️

> 📖 *Practical Cloud Security* 1판·2판 3장은 자산 추적을 배관에 비유합니다. **"당신의 여러 클라우드 자산을 담고 있는 파이프라인이 클라우드 제공자로부터 흘러나와 여러 보안 시스템으로 이어진다고 상상해보라. 자산이 중요한 보안 활동에서 누락되게 만들 수 있는 모든 '누수'를 막으려고 노력해야 한다."** 그리고 **"당신은 그 통제 지점을 찾아 조여서 모든 클라우드 자산을 파악하고 리스크를 적절히 관리해야 한다"** 고 전제를 깝니다.

네 개의 누수를 **사고 시나리오 → 원인 → 올바른 구성** 으로 번역합니다.

### 누수 ① 조달 누수 — 섀도 IT 계정

> 📖 원서: **"여기서의 '누수'는 대개 지출을 보지 못했거나 무료 서비스이기 때문에 클라우드 제공자 하나를 통째로 놓쳤다는 뜻이다."** 대응은 조달에서 시작합니다. **"IT 청구서를 훑어보라. 각 클라우드 지출마다 그 비용을 발생시킨 담당자를 찾아가 제한된 감사 자격 증명을 받아라."**

**사고 시나리오.** 마케팅팀이 캠페인 랜딩 페이지를 띄우려고 팀 법인카드로 별도 AWS 계정을 만들고, 참가자 명단(이름·연락처)이 그 계정의 S3 버킷에 쌓입니다. 이 계정은 Organizations 밖이라 **SCP가 걸리지 않고, Config 어그리게이터에 잡히지 않고, GuardDuty·Macie 대상이 아니며, 조직 트레일도 없습니다.** 6개월 뒤 유출이 발생하고, 보안팀은 그 계정의 존재를 사고 후에 알게 됩니다.

**원인.** AWS에서 "제공자 하나를 통째로 놓치는" 사건은 **조직 밖 계정**으로 나타나며, **무료 등급이 있어 청구서에도 한동안 잡히지 않습니다.**

**🔴 올바른 구성.**

| 통제 | 방법 |
|---|---|
| 신규 계정 생성 경로 단일화 | Organizations + Control Tower **Account Factory** 이외의 계정 생성 금지를 사규로 정하고, IAM 정책으로 `organizations:CreateAccount` 를 관리 계정의 특정 역할로 제한 |
| 기존 외부 계정 흡수 | Organizations 초대(invite)로 조직에 편입 → SCP·조직 트레일·Config·GuardDuty가 자동 적용 |
| 재무 데이터로 역탐지 | 회계 시스템에서 **AWS/클라우드 결제 건**을 카드·벤더 기준으로 정기 추출해 조직 계정 목록과 대조 |
| 조직 내 정체불명 비용 탐지 | Cost Explorer에서 `CostCenter` 태그 **미할당** 비용을 월별 추적. 이 값이 늘어나면 어딘가에 미등록 리소스가 있다 |

```bash
# 조직에 속한 계정 전체 목록 — 회계 결제 목록과 대조할 기준선
aws organizations list-accounts \
  --query 'Accounts[].{Id:Id,Name:Name,Status:Status,Email:Email}' \
  --output table
```

### 누수 ② 처리 누수 — 조회했지만 다 보지 못했다

> 📖 원서의 정의는 구체적입니다. **"여기서의 '누수'는 클라우드 제공자에게 자산을 질의했지만 그 제공자의 클라우드 자산 일부를 인벤토리에 넣지 않았다는 뜻이다. 예를 들어 가상 머신은 전부 인벤토리에 넣었지만 팀이 프로비저닝한 객체 스토리지 버킷은 놓쳤을 수 있다. (…) 그러면 하위 도구는 그 버킷의 접근이 제대로 통제되고 있는지 확인할 수 없다."** 자산 안의 자산도 경고합니다. **"VM 안의 컨테이너 안에 웹 서버가 있을 수 있다."**

**사고 시나리오.** 인벤토리 스크립트가 `ap-northeast-2`의 EC2와 S3만 조회하는데, 데이터 분석팀이 `us-east-1`에 만든 DynamoDB 테이블과 Kinesis 스트림에 회원 행동 로그가 흐릅니다. 스크립트에는 존재하지 않는 데이터이고, 국외 이전 검토도 등급 부여도 없었습니다.

**원인.** **(가) 리전 누락** — 스크립트가 특정 리전만 순회합니다. **(나) 리소스 유형 누락** — S3·RDS·EC2는 보는데 DynamoDB·Kinesis·SQS·EFS·ECR은 보지 않습니다. **(다) 중첩 자산 누락** — EKS 노드는 세지만 파드가 마운트한 EFS 액세스 포인트는 세지 않습니다.

**🔴 올바른 구성.**

```bash
# (가) 전 리전 순회 — 리전 목록을 하드코딩하지 않는다
for R in $(aws ec2 describe-regions --all-regions \
             --query 'Regions[].RegionName' --output text); do
  echo "=== $R ==="
  aws resourcegroupstaggingapi get-resources \
    --region "$R" --profile awssec-lab \
    --query 'length(ResourceTagMappingList)'
done
```

- **(가)** 사용하지 않는 리전은 SCP `aws:RequestedRegion` 조건으로 잠그십시오(37장). **잠근 리전은 세지 않아도 되고, 잠그지 않은 리전은 반드시 세야 합니다.**
- **(나)** Config 레코더를 **모든 리소스 유형 기록**으로 설정하십시오. 유형을 열거하는 방식은 새 서비스가 나올 때마다 누수가 됩니다.
- **(다)** 컨테이너·인스턴스 내부는 SSM Inventory와 레지스트리 스캔으로 별도 계층에서 봅니다(26장).

### 누수 ③ 도구 누수 — 알고 있었지만 검사하지 않았다

> 📖 원서: **"세 번째 단계는 자산의 보안을 점검하는 각 도구가 이 자산 인벤토리에 연결되어 자기 일을 하는 데 필요한 정보를 얻을 수 있게 하는 것이다. (…) 이 영역에서의 '누수'는 일부 자산을 알고는 있었지만 도구나 프로세스가 그 자산의 보안 문제를 점검하도록 하지 않았다는 뜻이다. 도구가 알지 못하는 자산에서 보안 문제를 찾아낼 방법은 정말로 없다."**

**사고 시나리오.** `shopmini-uploads`는 인벤토리에 있고 `DataClass=Confidential` 태그도 붙어 있습니다. 그런데 Macie는 보안 계정에만 켜져 있고 위임 관리자 설정이 누락되어 운영 계정의 이 버킷을 보지 못합니다. GuardDuty S3 보호도 신규 계정 자동 적용이 꺼져 있습니다. **버킷은 대장에 있는데 어떤 스캐너도 보고 있지 않습니다.**

**원인.** 인벤토리와 도구 커버리지를 **별개로 관리**했기 때문입니다. "어떤 도구가 이 리소스를 보는가"를 대장에 적지 않으면 공백은 사고 전에 드러나지 않습니다.

**🔴 올바른 구성 — 커버리지 매트릭스를 대장의 열로 만드십시오.**

| 자산 유형 | Config | GuardDuty | Macie | Inspector | Security Hub |
|---|---|---|---|---|---|
| S3 버킷 | ○ | ○(S3 보호) | ○ | — | 집계 |
| RDS | ○ | ○(RDS 보호) | — | — | 집계 |
| EC2 | ○ | ○ | — | ○ | 집계 |
| Lambda | ○ | ○(Lambda 보호) | — | ○ | 집계 |
| ECR 이미지 | ○ | — | — | ○ | 집계 |
| DynamoDB | ○ | — | — | — | 집계 |

그리고 **커버리지 자체를 점검**하십시오.

```bash
# GuardDuty 위임 관리자에서: 신규 계정 자동 등록 여부 확인
aws guardduty describe-organization-configuration \
  --detector-id "$DETECTOR_ID" \
  --region ap-northeast-2 --profile awssec-lab

# Macie 위임 관리자에서: 조직 내 계정별 Macie 상태
aws macie2 describe-organization-configuration \
  --region ap-northeast-2 --profile awssec-lab
```

🔴 **신규 계정 자동 등록(auto-enable)을 반드시 켜십시오.** 사람이 계정마다 켜는 방식은 반드시 누락됩니다(상세 구성은 31장).

### 누수 ④ 결과 누수 — 찾았지만 아무도 처리하지 않았다

> 📖 원서: **"마지막 단계는 도구 시스템에서 나온 발견 사항을 실제로 처리하고 있는지 확인하는 것이다. 당연해 보일 수 있지만 실제로는 이 발견 사항들이 무시되는 경우가 많다. 특히 오탐을 많이 만들어내는 '시끄러운' 스캔 시스템에서 그렇다."** 그리고 수용과 무시를 구분합니다. **"발견 사항(리스크)을 고치지 않고 수용하기로 결정하는 것은 전적으로 괜찮다. 그러나 아무런 검토 없이 무시하는 것은 '누수'다."**

**사고 시나리오.** Macie가 3개월 전 `shopmini-uploads`의 `returns/`에서 주민등록번호 패턴을 HIGH로 보고했고 결과는 Security Hub에 들어와 있습니다. 하지만 미해결 항목이 4,000건이고 아무도 필터를 걸어 보지 않습니다. 유출 후 조사에서 **"3개월 전에 이미 알고 있었다"** 는 사실이 드러납니다. 규제 대응에서 이것은 몰랐던 것보다 나쁩니다.

**원인.** 원서가 지적한 그대로 **검토 없는 무시**이고, 근본 원인은 대개 **소유자 부재**입니다. `Owner` 태그가 없으면 티켓을 누구에게 보낼지 정하는 사람이 없고, 배정 없는 티켓은 아무도 닫지 않습니다.

**🔴 올바른 구성.**

- **모든 결과는 티켓이 된다.** Security Hub 결과를 EventBridge로 받아 이슈 트래커에 자동 생성하고 담당자는 `Owner` 태그로 결정합니다. **이것이 `Owner` 태그를 필수로 만든 진짜 이유입니다.**
- **수용은 기록으로 남긴다.** 워크플로 상태를 `SUPPRESSED`로 바꾸되 **수용 사유·승인자·재검토 예정일**을 4.1의 리스크 등록부에 남깁니다. 기록이 없으면 감사에서 근거가 없습니다.
- **오탐은 규칙을 고쳐서 없앤다.** 같은 오탐이 반복되면 무시 습관이 생깁니다. Macie는 허용 목록으로, Security Hub는 억제 규칙(suppression rule)으로 **발생 자체를 줄이십시오.**
- **미처리 결과 수를 지표로 관리한다.** "고심각도 미처리 건수"와 "최장 경과일"을 주간 보고하십시오.

### 4가지 누수 요약

|---|---|---|---|

## 12.6 데이터 보존과 파기 정책

### 안 지워진 데이터는 계속 위험 자산이다

보존 정책은 스토리지 비용 이야기로 오해되지만 **가장 효과적인 데이터 보호 통제 중 하나**입니다. **없는 데이터는 유출되지 않습니다.** 4.2에서 극비 등급에 "애초에 두지 않는 것이 최선"이라는 규칙을 붙인 것을 시간 축으로 확장한 것이 보존 정책입니다.

보존 기간은 **최소 보존**(규제가 요구하는 하한)과 **최대 보유**(규제가 금지하는 상한) 양쪽에서 제약됩니다. 상한이 있다는 사실이 자주 잊힙니다.

| 데이터 | 최소 보존 | 최대 보유 | 근거(4.3 참조) |
|---|---|---|---|
| 회원 개인정보 | — | **보유 목적 달성 시까지** | 개인정보보호법 — 목적 달성 후 지체 없이 파기 |
| 전자상거래 계약·청약철회 기록 | 5년 | — | 전자상거래법 |
| 대금결제·재화 공급 기록 | 5년 | — | 전자상거래법 |
| 소비자 불만·분쟁 처리 기록 | 3년 | — | 전자상거래법 |
| 접속 기록(로그) | 1년 이상 | — | 개인정보보호법 시행령 계열 안전성 확보조치 |
| 카드소지자 데이터 | — | **저장 최소화**(승인 데이터 저장 금지 항목 존재) | PCI DSS |
| CloudTrail·감사 로그 | 사고 조사 기간 이상 | — | 조직 정책(29장에서 상세) |

⚠️ **"5년 보존"과 "목적 달성 시 파기"는 충돌합니다.** 정답은 **분리 보관**입니다. 5년 보존이 의무인 것은 거래 기록이지 회원 프로필 전체가 아닙니다. 탈퇴 회원의 거래 기록만 최소 항목으로 분리 보존하고 나머지는 파기하십시오. **테이블 하나를 5년 통째로 들고 있는 설계가 가장 흔한 위반**입니다.

### 🧪 S3 라이프사이클 규칙

```json
{
  "Rules": [
    {
      "ID": "shopmini-uploads-retention",
      "Filter": { "Prefix": "reviews/" },
      "Status": "Enabled",
      "Transitions": [
        { "Days": 90, "StorageClass": "STANDARD_IA" },
        { "Days": 365, "StorageClass": "GLACIER_IR" }
      ],
      "Expiration": { "Days": 1825 },
      "NoncurrentVersionExpiration": { "NoncurrentDays": 90 },
      "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 7 }
    },
    {
      "ID": "expire-temp-objects",
      "Filter": { "Prefix": "tmp/" },
      "Status": "Enabled",
      "Expiration": { "Days": 7 }
    }
  ]
}
```

```bash
aws s3api put-bucket-lifecycle-configuration \
  --bucket shopmini-uploads \
  --lifecycle-configuration file://lifecycle.json \
  --profile awssec-lab
```

세 항목이 보안 관점에서 중요합니다.

- **`NoncurrentVersionExpiration`** — 버전 관리를 켠 버킷에서 객체를 "삭제"하면 이전 버전이 남습니다. **이 규칙이 없으면 파기했다고 보고한 데이터가 계속 존재합니다.**
- **`AbortIncompleteMultipartUpload`** — 실패한 멀티파트 조각은 객체 목록(`ListObjects`)에 나타나지 않으면서 저장되어 있습니다. 인벤토리에도 파기 대상에도 잡히지 않는 데이터입니다.
- **`Expiration`** — 버전 관리 버킷에서 만료는 삭제 표시(delete marker)를 만들 뿐이고, 실제 제거는 비현행 버전 만료가 담당합니다.

⚠️ **라이프사이클 규칙과 S3 Object Lock은 충돌합니다.** 보존 기간이 걸린 객체는 만료되지 않고 규칙은 조용히 아무 일도 하지 않습니다(15.9). "규칙을 걸었으니 지워졌겠지"라고 가정하지 말고 실제 객체 수를 확인하십시오.

### 안전한 삭제 — 암호 삭제

> 📖 *Practical Cloud Security* 1판·2판 2장 「Cryptographic erasure」는 이렇게 씁니다. **"대량의 데이터를 확실하게 파괴하는 것은 사실 어렵다. (…) 데이터를 복구 불가능하게 만들고 싶을 때 KMS의 키 암호화 키를 지우거나 접근을 취소하면, 그 키 암호화 키로 '래핑'된 모든 데이터 암호화 키가 세상 어디에 있든 쓸모없게 된다. (…) 수 테라바이트짜리 파일을 256비트 키 하나를 덮어쓰는 것만으로 사실상 복구 불가능하게 만들 수 있다."**

AWS에서는 **KMS 키 삭제 예약**입니다.

```bash
aws kms schedule-key-deletion \
  --key-id arn:aws:kms:ap-northeast-2:111122223333:key/EXAMPLE-KEY-ID \
  --pending-window-in-days 30 \
  --profile awssec-lab
```

🔴 **암호 삭제를 파기 수단으로 쓰려면 세 가지가 선행되어야 합니다.**

1. **파기 단위마다 키를 분리한다.** 계정 전체가 `alias/shopmini/app` 하나를 쓰면 그 키를 지우는 순간 파기 대상이 아닌 데이터까지 복구 불가가 됩니다. **키의 입도가 곧 파기의 입도입니다.**
2. **모든 복사본이 그 키로 암호화되어 있어야 한다.** 백업이 다른 키로 재암호화되어 있거나 다른 리전으로 복제되며 리전 키로 다시 감싸졌다면, 원본 키를 지워도 **백업은 그대로 복호화됩니다.** 암호 삭제의 유일한 실패 지점입니다.
3. **키 삭제는 되돌릴 수 없다.** 대기 기간(7~30일) 중에만 취소할 수 있습니다. 4.2 매트릭스가 극비 등급에 **대기기간 30일**을 요구한 이유이며, `kms:ScheduleKeyDeletion` 호출에 알람을 걸어두십시오.

### ⚠️ 보존 정책과 백업의 충돌

**"개인정보를 파기했다"고 보고한 뒤 백업 볼트에 그 데이터가 90일치 남아 있는 상황** — 데이터 파기에서 가장 흔한 실무 사고입니다.

| 충돌 지점 | 무슨 일이 벌어지나 | 처리 |
|---|---|---|
| RDS 자동 백업(보존 기간 내) | 파기 후에도 시점 복원으로 되살아남 | 파기 완료 시점을 **백업 보존 기간 이후**로 정의하고 대장에 명시 |
| RDS 수동 스냅샷 | 자동 만료 없음 — 무기한 잔존 | 스냅샷에도 `DataClass` 태그 부착 + 만료 정책 별도 운영 |
| AWS Backup 볼트 잠금 | 잠긴 복구 지점은 **삭제 자체가 불가** | 개인정보를 담은 리소스에 **컴플라이언스 모드 볼트 잠금을 걸지 않는다**(17.3) |
| 교차 리전 복제본 | 원본 삭제가 복제본으로 전파되지 않을 수 있음 | 복제 대상에 동일 라이프사이클 규칙 적용 |
| 로그(CloudWatch Logs·S3) | 로그에 실린 개인정보는 파기 대상에서 누락되기 쉬움 | 애초에 **로그에 개인정보를 남기지 않는 것**이 유일한 실효적 통제 |

마지막 행이 가장 중요합니다. **로그는 파기하기 가장 어려운 데이터입니다** — 중앙 로그 계정으로 복제되고, SIEM으로 인덱싱되고, 규제상 1년 이상 보존해야 하기 때문입니다. 11.6의 접속 문자열 마스킹과 같은 이유입니다.

**파기 증적을 남기십시오.** 무엇을(리소스 ARN·객체 접두사·레코드 범위), 언제, 어떤 방법으로(라이프사이클 만료 / 명시적 삭제 / 암호 삭제), 누가 승인했는지를 기록합니다. **파기는 "했다"가 아니라 "했음을 증명할 수 있다"까지가 요구사항입니다.**

## 🔴 필수 구성 체크리스트

- [ ] 인벤토리 대장에 **소유자 열**이 있고 모든 행에 값이 있다
- [ ] 대장에 **스냅샷·AMI·로그·시크릿**이 별도 행으로 존재한다
- [ ] 인벤토리 역할은 **메타데이터 읽기 + 태그 쓰기**만 가진다(`ReadOnlyAccess` 금지)
- [ ] 필수 태그 5종의 **키 표기와 허용 값**이 문서로 확정되고 소유자가 지정되어 있다
- [ ] Organizations **태그 정책**에 `enforced_for`가 지정되어 있다
- [ ] SCP에 **태그 없는 생성 차단** + **잘못된 값 차단**(`IfExists`) + **태그 제거 차단**이 모두 있다
- [ ] Config `required-tags`가 **S3 버킷을 포함해** 걸려 있다(SCP로 못 막는 유형)
- [ ] `DataClass`가 **저장소뿐 아니라 처리 컴퓨트에도** 붙는다
- [ ] Macie가 **조직 위임 관리자**로 구성되고 신규 계정 자동 등록이 켜져 있다
- [ ] Macie 분류 작업에 **스코핑**이 걸려 있다
- [ ] Macie 결과가 **Security Hub·EventBridge**로 나가고 담당자가 `Owner`로 결정된다
- [ ] Macie 결과 내보내기 버킷이 `Restricted`로 취급된다
- [ ] 조직 계정 목록과 **회계 결제 내역**을 정기 대조한다
- [ ] 인벤토리 스크립트가 **전 리전을 동적으로 순회**하고, 미사용 리전은 SCP로 차단되어 있다
- [ ] 각 보안 서비스의 **신규 계정 자동 등록**이 켜져 있다
- [ ] 고심각도 **미처리 건수와 최장 경과일**이 주간 지표로 보고된다
- [ ] S3 라이프사이클에 **비현행 버전 만료**와 **미완료 멀티파트 중단**이 있다
- [ ] 암호 삭제를 쓴다면 **파기 단위별로 KMS 키가 분리**되어 있다
- [ ] 파기 대상 데이터의 **백업 잔존 기간**이 대장에 기록되어 있다

## 다음 장 예고

이 장에서 `DataClass` 태그를 붙였습니다. 4.2의 매트릭스는 태그 값마다 다른 암호화를 요구합니다 — 기밀은 고객 관리형 키, 극비는 용도별 전용 키에 암호화 컨텍스트까지.

13장은 그 요구사항을 실제로 만드는 방법입니다. 대칭·비대칭 키, **봉투 암호화(Envelope Encryption)** 와 키 계층, KMS의 키 종류와 데이터 키, 그리고 **IAM 정책만으로는 KMS 키에 접근할 수 없는 이유** — 키 정책이라는 최종 관문을 다룹니다. 이 장 마지막의 암호 삭제가 왜 성립하는지도 그때 이해하게 됩니다.
