# 부록 C. 사고 대응 플레이북 템플릿 6종

32.2에서 플레이북 표준 구조 9단과 시나리오 6종의 골격을 정했습니다. **이 부록은 그 여섯 개를 실제 문서로 채운 것입니다.** 조직 이름과 연락처, 리소스 식별자만 바꾸면 오늘 초안으로 쓸 수 있는 형태를 목표로 했습니다.

여섯 플레이북은 모두 같은 11개 절(0~10)로 되어 있습니다. 구조를 똑같이 맞춘 이유는 하나입니다 — **훈련이 누적되게 하기 위해서입니다.** PB-01로 한 번 훈련한 팀은 PB-04의 4절이 어디에 있는지 이미 압니다. 새벽 3시에 목차를 찾는 시간이 사라집니다.

> ⚠️ **이 부록은 템플릿이지 완성품이 아닙니다.** 아래 세 가지는 조직마다 반드시 달라집니다 — **연락처와 승인권자**, **리소스 식별자**(계정 ID·버킷명·역할 ARN·보안 그룹 ID), **법정 통지 기한**. 특히 세 번째는 이 책의 어떤 수치도 근거로 삼지 마시고 **법무 검토로 확정**해 채우십시오(4.3, 33.6).

## C.0 사용법

### 이 템플릿을 우리 것으로 만드는 4단계

| 단계 | 하는 일 | 소요 | 완료 판정 |
|---|---|---|---|
| ① 조직 정보 시트 작성 | 아래 「조직 정보 시트」와 「에스컬레이션 표」의 빈칸을 채운다 | 반나절 | 빈칸 0개 |
| ② 리소스 식별자 치환 | 본문의 `shopmini-*`·계정 ID·역할 ARN을 우리 값으로 일괄 치환 | 1일 | 모든 CLI가 **복사해서 그대로 실행 가능** |
| ③ 드라이런 검증 | 각 플레이북 3절(초기 확인)의 조회 명령을 **실제로 실행**해 권한과 결과를 확인 | 1일 | 3절 명령 전부 성공 |
| ④ 훈련 반영 | 32.5 테이블톱에서 막힌 지점을 플레이북에 되먹인다 | 분기 1회 | 미해결 질문 0개 |

**②가 끝나지 않은 플레이북은 없는 것과 같습니다.** "계정 ID를 확인해서 넣으세요"라고 적힌 명령은 새벽 3시에 아무도 실행하지 못합니다. 32.2가 지적한 "플레이북에 '조사한다'라고만 적음"의 다른 얼굴입니다.

**③을 건너뛰면 권한 부족이 사고 당일에 발견됩니다.** 32.5의 「훈련이 드러내는 4대 결함」 1번이 정확히 이것입니다. 3절 명령은 전부 **읽기 전용**이라 언제 실행해도 안전하므로, 오늘 바로 돌려 보십시오.

### 에스컬레이션 표

각 플레이북 2절의 "에스컬레이션 대상"은 이 표를 가리킵니다. 시간 축과 사실 축 두 가지로 굴러갑니다.

| 심각도 | 1차 응답 SLA | 소집 범위 | 즉시 통보 | 미응답 시 다음 단계 |
|---|---|---|---|---|
| **SEV1** | 15분 | IC + 기술 분석 전원 + 비즈니스 의사결정자 + 법무 | 경영진 `________` | 15분 → 예비 IC / 30분 → 경영진 직통 |
| **SEV2** | 1시간 | IC + 해당 영역 기술 분석 | 보안 리더 `________` | 30분 → 예비 담당자 / 60분 → IC |
| **SEV3** | 영업일 4시간 | 담당 분석가 | 주간 보고 | 4시간 → 팀 리드 |

**사실 축 — 다음 중 하나라도 확인되면 시간과 무관하게 즉시 SEV1로 올립니다.**

- [ ] 루트 또는 조직 관리자 권한의 예정 없는 사용
- [ ] 로그 파이프라인의 중단·삭제·변조(`StopLogging`, `DeleteTrail`, `StopConfigurationRecorder`)
- [ ] 개인정보 저장소의 비정상 대량 읽기 또는 외부 반출
- [ ] 백업·스냅샷의 삭제, 보존 정책 단축, 외부 공유 설정 변경
- [ ] KMS 키의 비활성화 또는 삭제 예약
- [ ] 위 어느 것이든 **조치 후 재발**

### 훈련에 쓰는 법 (32.5 연결)

플레이북은 읽으라고 만드는 문서가 아니라 **훈련 교재**입니다. 각 플레이북을 그대로 테이블톱 시나리오로 바꾸는 방법은 다음과 같습니다.

| 훈련 요소 | 플레이북의 어느 부분에서 뽑는가 |
|---|---|
| T+0 인젝트 | **1절 트리거**의 항목 하나를 그대로 읽어 준다 |
| T+15분 인젝트 | **3절 초기 확인**의 조회 결과를 진행자가 지어내어 건넨다 |
| T+40분 인젝트 | **10절 흔한 실수** 중 하나를 참가자가 저지르도록 유도하는 상황 |
| T+70분 인젝트 | **8절 통지**를 강제하는 상황(기자 문의, 고객 문의) |
| T+85분 인젝트 | 법무 질문 — "개인정보가 유출되었습니까? 기한 시계는 언제부터입니까?" |
| 채점 기준 | **2절 심각도 판정**을 몇 분 만에, 표와 같게 내렸는가 |
| 산출물 | 4절·6절에서 "권한이 없다 / 모르겠다"가 나온 지점 목록 |

**분기마다 여섯 개 중 하나씩 돌리면 1년 반에 한 바퀴입니다.** 여섯 개를 다 만들 여력이 없다면 PB-01과 PB-02부터입니다 — AWS에서 가장 자주 발생하고, 나머지 넷의 초기 단계도 대부분 이 둘로 시작합니다(32.2).

**훈련에서 실제로 실행해 볼 것 두 가지**를 정해 두십시오. 말로만 하는 훈련은 권한 결함을 드러내지 못합니다.

- 3절의 모든 조회 명령을 `IncidentResponder` 역할로 **진짜 실행**한다.
- 4절의 격리 조치 하나를 **비운영 환경에서 진짜 실행**한다(예: 테스트 인스턴스에 격리 SG 교체).

## C.1 공통 전제 — 여섯 플레이북이 모두 가정하는 것

아래 여섯 가지는 **사고 전에 준비되어 있어야** 하는 것들입니다. 각 플레이북에서 반복하지 않고 여기를 참조합니다. **하나라도 없으면 해당 플레이북의 절반이 실행 불가능해집니다.**

### 전제 ① 역할과 RACI — 32.1

다섯 역할(사고 지휘관·기술 분석·커뮤니케이션·법무/규제·경영진)이 **주·예비로** 지정되어 있고, 다음 두 경계가 문서로 확정되어 있어야 합니다.

- **격리 조치의 최종 책임(A)은 사고 지휘관**입니다. 경영진 승인을 기다리지 않습니다.
- **서비스 중단 결정의 최종 책임(A)은 경영진**입니다. 사고 지휘관이 단독으로 내리지 않습니다.

각 플레이북 4절의 조치에는 이 경계가 `[IC 단독]` / `[중단 결정권자 승인 필요]`로 표시되어 있습니다.

### 전제 ② 포렌식 계정과 도구 — 32.3

| 자산 | 이 책의 값 | 없으면 막히는 절 |
|---|---|---|
| 포렌식 계정 | `444455556666` (IGW·NAT 없는 VPC, 도구 AMI 상시 유지) | 모든 플레이북 5절 |
| 조사 역할 | `IncidentResponder` (MFA·ExternalId 조건, `NeverDestroy` Deny 포함) | 모든 플레이북 3·4·5절 |
| 격리용 보안 그룹 | `shopmini-quarantine` (인바운드 0 + **기본 아웃바운드 규칙 제거됨**) | PB-01·03·04 4절 |
| 증거 버킷 | `shopmini-forensic-evidence` (**객체 잠금을 켠 상태로 사전 생성**) | 모든 플레이북 5절 |
| 스냅샷 보전 스크립트 | `create-snapshots` + `modify-snapshot-attribute` | 모든 플레이북 5절 |
| 락다운 SCP | 작성 완료, **붙이지 않은 채 보관** | PB-01·03·04 4절 |
| 계정 봉쇄 SCP | 조사용 읽기·스냅샷을 `NotAction`으로 남긴 표적 정책 | PB-01·04 4절 |

> ⚠️ **KMS를 사고 전에 확인하십시오.** EBS 기본 암호화 키가 **AWS 관리형 키**(`aws/ebs`)이면 스냅샷을 포렌식 계정에 **공유할 수 없고, 사고 당일에는 고칠 수 없습니다**(34.2). 고객 관리형 키로 바꾸고 키 정책에서 포렌식 계정의 `kms:Decrypt`·`kms:DescribeKey`·`kms:CreateGrant`·`kms:ReEncryptFrom`을 허용해 두십시오(16.7).

### 전제 ③ 브레이크 글래스 — 32.4

인증 경로가 죽었거나 침해되었을 때 쓰는 최후 경로입니다. 일곱 요건(별도 경로·하드웨어 MFA·분리 봉인·즉시 알람·사용 후 재발급·분기 점검·사후 정당화)이 모두 성립해야 합니다.

**여섯 플레이북 중 브레이크 글래스가 발동될 가능성이 높은 것은 PB-01(관리자 자격 증명 침해)과 PB-05(내부자가 IdP 관리자인 경우)입니다.** 두 플레이북의 4절에 진입 조건을 명시했습니다.

### 전제 ④ 심각도 등급 — 32.2

각 플레이북의 2절은 아래 4등급으로 판정합니다. **"공격의 정교함"이 아니라 "데이터에 무슨 일이 일어났는가"로 판정한다**는 원칙이 모든 판정표의 전제입니다.

| 등급 | 정의 |
|---|---|
| **SEV1** | 데이터 손실·파괴가 있는 성공한 공격 |
| **SEV2** | 데이터 손실 없는 성공한 공격(무단 접근 성립) |
| **SEV3** | 확인된 실패한 공격 |
| **SEV4** | 미확인·오탐 후보 |

> ⚠️ 각 플레이북의 판정표는 **초기 판정**입니다. 조사가 진행되면서 등급은 **올라갈 수 있고, 내려갈 수는 없습니다.** 한 번 SEV1으로 올린 사고를 조사 중에 내리지 마십시오 — 내리는 판단은 사후 검토에서 합니다.

### 전제 ⑤ 사건 ID와 기록

```bash
# 모든 플레이북의 첫 줄. 이 값이 스냅샷 태그·버킷 프리픽스·문서 파일명에 전부 들어간다
export CASE_ID="IR-2026-0906-01"          # IR-YYYY-MMDD-NN
export REGION="ap-northeast-2"
export PROFILE="awssec-lab"               # 실제로는 IncidentResponder 프로파일
export FORENSIC_ACCT="444455556666"
export EVIDENCE_BUCKET="shopmini-forensic-evidence"
export DECLARED_AT="$(date -u +%Y-%m-%dT%H:%M:%SZ)"   # 🔴 통지 기한의 기산점
echo "${CASE_ID} declared at ${DECLARED_AT}" | tee -a "${CASE_ID}-timeline.txt"
```

**`DECLARED_AT`이 가장 중요한 한 줄입니다.** 33.6에서 본 대로 규제 신고 기한의 시계는 "인지한 때"부터 돕니다. 그 시각을 **나중에 기억으로 복원하면 다툼이 생깁니다.** 선언 즉시 기록하십시오.

### 전제 ⑥ 모든 플레이북 공통 — 선언 직후 4줄 🔴

시나리오가 무엇이든 사고 선언 직후 네 가지를 **동시에** 겁니다. 각 플레이북 4절은 이 네 줄이 이미 걸려 있다고 가정합니다.

| # | 조치 | 이유 | 누가 |
|---|---|---|---|
| 1 | **배포 동결** — 모든 파이프라인 중지, 배포 채널에 공지 | 롤링 교체가 증거를 갈아엎는다(33.5) | IC |
| 2 | **Auto Scaling 교체 동작 정지** — 대상 ASG에 `suspend-processes` | 헬스 체크 실패 → 종료·교체 = 증거 소멸 | 기술 분석 |
| 3 | **기록 시작** — 타임라인 파일 개설, 조치 전 2줄 기록 규칙 발동(33.3) | 사후 재구성과 관리 연속성의 출발점 | 기록자 |

### 2. 심각도 판정

**판정에 필요한 질문은 세 개입니다.** 5분 안에 답하십시오.

1. 그 자격 증명으로 **성공한** API 호출이 있는가? (`errorcode IS NULL`)
2. 성공한 호출 중 **데이터에 닿은 것**이 있는가? (`GetObject`, `GetSecretValue`, `SelectObjectContent`, DB 접근)
3. **새 자격 증명·새 권한**이 만들어졌는가? (지속성 확보)

| 조건 | 등급 | 에스컬레이션 |
|---|---|---|
| 데이터 반출 또는 대량 열람이 확인됨 | **SEV1** | 전원 + 경영진 + 법무 즉시 |
| 루트 또는 관리자 권한 주체의 자격 증명 | **SEV1** | 전원 + 경영진. 브레이크 글래스 대기 |
| 성공한 호출 있음 + 지속성 확보(신규 사용자·키·역할·신뢰 정책 변경) | **SEV1** | 전원 + 경영진 |
| 성공한 호출 있음, 데이터 미접근, 지속성 없음 | **SEV2** | IC + 기술 분석 |
| 호출 전부 `AccessDenied`, 키는 유효 | **SEV2** | IC + 기술 분석 (키는 이미 유출됨) |
| 키가 이미 비활성/삭제 상태였고 호출 실패만 | **SEV3** | 담당 분석가 |
| 알림만 있고 해당 키·주체를 특정할 수 없음 | **SEV4** → 3절 재수행 | — |

> ⚠️ **"AccessDenied만 있으니 SEV3"은 틀린 판정입니다.** 유효한 키가 조직 밖에 있다는 사실 자체가 무단 접근의 성립 요건입니다. 권한이 작아서 실패한 것이지 자격 증명이 무사한 것이 아닙니다.

> ⚠️ **B3의 폭발 반경은 그 역할의 폭발 반경입니다.** ShopMini 앱이 이 역할로 S3·Secrets Manager를 호출 중이었다면 전부 `AccessDenied`가 됩니다. **중단 결정권자 승인 대상입니다.**

> ⚠️ **B3은 IAM 사용자의 장기 키에는 걸리지 않습니다.** 요청 컨텍스트에 `aws:TokenIssueTime`이 없기 때문입니다. 경로 A와 B는 서로를 대체하지 못합니다.

> 🔴 **복구 시 B3의 인라인 정책을 반드시 제거하십시오.** 남겨두면 몇 달 뒤 원인 불명의 `AccessDenied`로 돌아옵니다. — `aws iam delete-role-policy --role-name ShopMiniAppRole --policy-name DenyAllOlderThan`

#### 공통 — 확산 차단

| # | 조건 | 조치 | 권한 |
|---|---|---|---|
| C1 | Identity Center 사용자가 침해됨 | `sso-admin delete-account-assignment`로 할당 제거 **+ 반드시 B3 병행**(할당 제거는 새 세션만 막는다) | [IC 단독] |
| C2 | 해당 주체에 MFA 기기가 등록되어 있음 | `iam deactivate-mfa-device`로 공격자가 등록한 기기 제거. **어느 것이 정상인지 확인 후** | [IC 단독] |
| C3 | 데이터 반출이 진행 중 | PB-02 4절의 API 층 차단(엔드포인트·버킷 정책)을 병행 | [중단 결정권자] |
| C4 | 계정 전체가 통제 아래 | 계정 봉쇄 SCP 부착(33.3 ⑤). `NotAction`에 조사용 읽기·스냅샷이 남아 있는지 확인 | [중단 결정권자] |
| C5 | 조직 전체가 의심 | 락다운 SCP 발동(32.2). **관리 계정에는 SCP가 적용되지 않는다**는 점 인지 | [경영진] |

**각 조치 후 33.2의 OODA로 돌아옵니다.** 볼 것은 "멈췄는가"가 아니라 **"공격자가 어떤 대체 경로로 갈아탔는가"** 입니다. 3절 ⑦ 질의를 조치 직후 다시 던지십시오.

### 5. 증거 보전

34.2의 5단계를 이 시나리오에 맞춰 우선순위를 정하면 다음과 같습니다. **자격 증명 유출에서 가장 먼저 사라지는 것은 디스크가 아니라 로그와 세션 컨텍스트입니다.**

| 순위 | 무엇을 | 왜 먼저 | 방법 |
|---|---|---|---|
| 1 | **IAM 상태 스냅샷** | 근절 단계에서 우리가 직접 바꿔 버린다 | `iam get-account-authorization-details` 전체를 JSON으로 덤프 |
| 2 | **자격 증명 보고서** | 마지막 사용 시각·MFA 상태가 조치로 덮인다 | `iam generate-credential-report` → `get-credential-report` |
| 3 | **CloudTrail 사고 기간 로그** | 수명 주기 정책으로 사라질 수 있다 | 증거 버킷 복사 + 법적 보존 |
| 4 | 인스턴스 스냅샷(경로 B) | `DeleteOnTermination`·ASG 교체 | `create-snapshots` |
| 5 | 메모리(경로 B, 가능하면) | 인스턴스 중지·종료 시 소멸 | SSM + LiME. **불가하면 "불가"로 명시 기록** |

```bash
# 1·2 ── 조치로 덮이기 전에 IAM 현재 상태를 통째로 고정한다
aws iam get-account-authorization-details --profile "$PROFILE" \
  > "${CASE_ID}-iam-authz-before.json"

aws iam generate-credential-report --profile "$PROFILE"
aws iam get-credential-report --query Content --output text --profile "$PROFILE" \
  | base64 -d > "${CASE_ID}-credential-report.csv"

sha256sum "${CASE_ID}-iam-authz-before.json" "${CASE_ID}-credential-report.csv" \
  | tee -a "${CASE_ID}-hashes.txt"
```

```bash
# 3 ── 사고 기간 CloudTrail 을 증거 버킷으로 복사하고 법적 보존을 건다
aws s3 cp \
  s3://shopmini-org-cloudtrail-logs/AWSLogs/o-exampleorgid/111122223333/CloudTrail/ap-northeast-2/2026/09/ \
  "s3://${EVIDENCE_BUCKET}/${CASE_ID}/cloudtrail/" \
  --recursive --checksum-algorithm SHA256 --profile "$PROFILE"

aws s3api put-object-legal-hold --bucket "$EVIDENCE_BUCKET" \
  --key "${CASE_ID}/cloudtrail/2026/09/06/000000.json.gz" \
  --legal-hold Status=ON --profile "$PROFILE"
```

```bash
# 4 ── 경로 B에서만. 인스턴스의 모든 볼륨을 한 시점으로
aws ec2 create-snapshots \
  --instance-specification "InstanceId=${INSTANCE},ExcludeBootVolume=false" \
  --description "Evidence ${CASE_ID}" --copy-tags-from-source volume \
  --tag-specifications "ResourceType=snapshot,Tags=[{Key=IncidentId,Value=${CASE_ID}},{Key=Evidence,Value=true},{Key=LegalHold,Value=true}]" \
  --region "$REGION" --profile "$PROFILE"
```

> ⚠️ **스냅샷 공유는 `--user-ids`로 포렌식 계정만 지정합니다.** `--group-names all`은 스냅샷을 전 세계에 공개합니다(33.5). 그리고 공유만 받지 말고 **포렌식 계정 키로 `copy-snapshot`** 해 소유권을 가져오십시오 — 침해된 운영 계정이 원본을 삭제할 수 있습니다(34.2).

**관리 연속성 기록**은 C.3 양식에 각 증거마다 한 행씩 그 자리에서 채웁니다.

### 6. 근절 (Eradication)

**공격자의 재진입 수단을 전부 제거하는 단계입니다.** 3절 ⑦ 질의의 결과가 이 단계의 작업 목록이 됩니다. 아래 표를 순서대로 확인하십시오 — **하나라도 빠지면 그것이 재진입 경로입니다.**

| # | 확인 대상 | 확인 방법 | 흔한 백도어 형태 |
|---|---|---|---|
| 1 | 신규 IAM 사용자 | 3절 ⑦의 `CreateUser` | 이름이 정상 계정과 비슷함(`batch-runner2`) |
| 2 | 신규 액세스 키 | `CreateAccessKey` + 모든 사용자 키 전수 조사 | **정상 사용자에 키 하나 추가** — 가장 흔함 |
| 3 | 신규 로그인 프로파일 | `CreateLoginProfile`, `UpdateLoginProfile` | 서비스 계정에 콘솔 암호를 붙임 |
| 4 | 신규·변경된 역할 신뢰 정책 | `CreateRole`, `UpdateAssumeRolePolicy` | **외부 계정 ARN이 Principal에 추가됨** |
| 5 | 인라인·관리형 정책 부착 | `AttachUserPolicy`, `PutUserPolicy`, `AttachRolePolicy`, `CreatePolicyVersion` | 기존 정책의 **새 버전**으로 권한 추가 |
| 6 | MFA 기기 등록·해제 | `iam list-mfa-devices`를 전 사용자에 대해 | 공격자 소유 가상 MFA 등록 |
| 7 | 리소스 기반 정책의 외부 주체 | IAM Access Analyzer 외부 접근 발견(7.7) | S3·KMS·Lambda·SQS에 외부 계정 허용 |
| 8 | 페더레이션 신뢰 | `UpdateAssumeRolePolicy`, OIDC/SAML 공급자 추가 | **GitHub OIDC 신뢰에 `*` 조건** (27.6) |
| 9 | 이벤트 기반 지속성 | EventBridge 규칙, Lambda 함수, Config 규칙 추가 | 삭제되면 다시 만드는 자가 복구 백도어 |
| 10 | 다른 리전의 리소스 | 3절 ⑧ 질의 + `ec2 describe-regions`로 전 리전 순회 | 안 쓰는 리전의 인스턴스·사용자 |

```bash
# 7 ── 외부에 열린 리소스 기반 정책을 한 번에 본다
aws accessanalyzer list-findings \
  --analyzer-arn "$ANALYZER_ARN" \
  --filter '{"status":{"eq":["ACTIVE"]}}' \
  --region "$REGION" --profile "$PROFILE"
```

```bash
# 10 ── 전 리전에서 실행 중 인스턴스를 훑는다 (은닉 리소스 확인)
for R in $(aws ec2 describe-regions --query 'Regions[].RegionName' --output text --profile "$PROFILE"); do
  echo "== $R"
  aws ec2 describe-instances --region "$R" --profile "$PROFILE" \
    --filters Name=instance-state-name,Values=running \
    --query 'Reservations[].Instances[].{Id:InstanceId,Type:InstanceType,Launch:LaunchTime}' \
    --output text
done
```

**그리고 최초 침입 경로를 막습니다.** 근절은 백도어 제거만이 아니라 **"어떻게 키가 나갔는가"를 닫는 것**입니다.

| 유출 경로 | 근절 조치 | 재발 방지 통제 |
|---|---|---|
| 소스 저장소 커밋 | 이력에서 제거 + 키 폐기. **이력 제거만으로는 부족 — 키는 이미 유출됨** | 사전 커밋 훅·시크릿 스캐닝, 27.3 |
| CI 로그·빌드 출력 | 로그 삭제 + 마스킹 설정 | 27.4 ③ 빌드 시크릿 최소화 |
| IMDS 탈취(SSRF 등) | **IMDSv2 강제**, 홉 제한 1 | 8.3, Config `ec2-imdsv2-check` |
| 피싱·세션 탈취 | 해당 사용자 자격 증명 전면 재발급 | 9.4 MFA 강화, 피싱 저항 인증 |
| 서드파티 연동 | 연동처에서 재발급 + External ID 적용 | 8.6 Confused Deputy |
| 장기 키 자체의 존재 | **키를 없애고 역할로 전환** | 6.4, SCP로 `iam:CreateAccessKey` 금지 |

**마지막 행이 근본 해법입니다.** 유출될 장기 키가 없으면 이 플레이북의 경로 A 자체가 사라집니다.

### 7. 복구 (Recovery)

34.5의 재구축 원칙을 적용합니다. **경로 B(인스턴스 역할 유출)는 침해된 인스턴스를 치료하지 않고 재배포합니다.**

| 단계 | 할 일 | 건너뛰면 |
|---|---|---|
| ① | 근본 원인 확정·제거 확인(6절 완료) | 같은 문을 열어 둔 채 재배포 → 즉시 재감염 |
| ② | 자격 증명 **전면 순환** — 아래 목록 전부 | 공격자가 새 시스템으로 그대로 로그인 |
| ③ | 골든 AMI·IaC로 재생성(22.5, 28장). **침해 인스턴스를 고쳐 쓰지 않음** | 손으로 만든 시스템 = 검증 불가 |
| ④ | 트래픽 전환 후 구 인스턴스는 **격리 상태 유지** | 롤백 불가 |
| ⑤ | 봉쇄 조치 해제 — `DenyAllOlderThan` 인라인 정책 제거, 임시 Deny 정책 제거 | 몇 달 뒤 원인 불명 `AccessDenied` |
| ⑥ | 구 인스턴스·스냅샷 정리(증거 보전 확인 후) | 잊힌 침해 인스턴스가 계속 살아 있음 |

**② 자격 증명 전면 순환 목록** — 34.5의 목록을 이 시나리오 기준으로 좁힌 것입니다.

- [ ] 침해 사용자의 액세스 키 전부(비활성화 후 삭제, 신규 발급)
- [ ] 침해 사용자의 콘솔 비밀번호 + **MFA 재등록**
- [ ] 해당 역할의 세션(발급 시각 기준 폐기 — 이미 4절 B3에서 수행)
- [ ] Secrets Manager 시크릿 즉시 순환(`rotate-secret`. 자동 주기를 기다리지 않음, 11.5)
- [ ] RDS 마스터·앱 계정 비밀번호 변경 + 앱 재배포
- [ ] 인스턴스에 남아 있던 SSH 키 페어(신규 이미지에서 제외, 22.2)
- [ ] **서드파티 API 키·웹훅 URL** — AWS 밖이라 목록에서 가장 자주 누락됨
- [ ] 애플리케이션 세션 서명 키(사용자 세션 일괄 무효화)
- [ ] 침해가 IdP까지 닿았다면 **SAML/OIDC 서명 인증서 교체**

#### 🔴 완료 판정 기준

아래가 전부 참이어야 사고 종료를 선언합니다.

- [ ] 유출된 자격 증명으로 가능한 모든 호출이 실패함을 **실제로 확인**했다(비활성 키로 `sts:GetCallerIdentity` 시도)
- [ ] 6절 표 10개 항목을 모두 확인했고, 발견된 백도어를 전부 제거했다
- [ ] 조치 후 **24시간 동안** 3절 ⑤·⑦ 질의에서 새 이상 활동이 없다
- [ ] GuardDuty에 같은 계열 신규 발견이 없다
- [ ] 재배포된 인스턴스가 IMDSv2 강제·최소 권한 역할로 뜬 것을 확인했다
- [ ] 봉쇄용 임시 Deny 정책이 전부 제거되었고, 정상 워크로드가 복구되었다

### 8. 통지

| 대상 | 언제 | 무엇을 | 누가 |
|---|---|---|---|
| 내부 경영진 | 사고 **선언 즉시** | 무슨 일이, 서비스 영향, 지금 하는 조치 | IC |
| 내부 법무·홍보 | 데이터 접근 가능성이 **보이는 순간** | 데이터 유형과 **잠정** 범위 | IC |
| AWS | 자격 증명 노출·남용이 확인되면 | 지원 케이스. 키 격리 정책이 붙었다면 필수 | 기술 분석 |
| 서드파티 연동처 | 우리 키로 그쪽 자원에 접근 가능했다면 | 계약상 통지 조항대로 | 법무 |
| 규제 기관 | 개인정보 접근이 확인된 경우, **관할 법령 기한 내** | 법령이 정한 서식 | 법무 / 개인정보 보호책임자 |
| 고객·정보주체 | 관할 법령 또는 계약상 기한 | 사전 승인 템플릿(32.3 ⑥) | 홍보 / 고객 지원 |
| 사이버보험사 | 약관상 기한(대개 매우 짧음) | 약관 서식 | 재무 / 법무 |

> ⚠️ **법정 기한은 이 책에서 확정하지 않습니다.** EU GDPR은 감독기관 신고를 "인지 후 72시간 이내"로 규정하는 것으로 널리 알려져 있고(제33조), 국내 개인정보보호법에도 정보주체 통지와 감독기관 신고 의무가 있습니다. **그러나 구체적 기한·대상·서식은 개정이 잦고 적용 요건도 사안마다 다릅니다. 반드시 최신 법령 원문과 법무 검토로 확인해 조직 정보 시트에 채우십시오**(4.3, 33.6).

> 🔴 **기산점은 `DECLARED_AT`입니다.** "인지한 때"의 해석은 다툼의 여지가 있으므로, 침해로 판단한 시각을 기록으로 고정하고 그때부터 계산합니다.

**숫자 규칙 세 가지**(33.6)를 이 시나리오에도 그대로 적용하십시오 — 내부 보고에 신뢰 수준 병기, 외부 발표는 확정분과 조사 중인 것을 분리, **대외 숫자를 말하는 사람은 한 명**.

### 9. 사후 (Post-Incident)

**72시간 이내, 단 하룻밤 자고 난 뒤**에 엽니다(34.6).

**타임라인 재구성** — C.2 양식에 두 시계를 나란히 놓습니다. 자격 증명 유출 사고에서 채워야 할 최소 행은 다음과 같습니다.

| 반드시 확정할 시각 | 근거 |
|---|---|
| 키가 유출된 시각(커밋·빌드·피싱 시각) | Git 이력, CI 로그, 메일 헤더 |
| 공격자의 최초 호출 | CloudTrail `eventTime` |
| 최초 성공한 데이터 접근 | S3 데이터 이벤트 |
| 지속성 확보 | `CreateUser`·`CreateAccessKey` |
| 우리의 최초 인지 | GuardDuty `createdAt` 또는 제보 접수 |
| 사고 선언 | `DECLARED_AT` |
| 최초 봉쇄 조치 | `UpdateAccessKey`·`PutRolePolicy` |

**지표 산출**(32.6) — 최초 호출 → 인지 = MTTD, 인지 → 최초 봉쇄 = MTTC. **비어 있는 칸이 다음 통제 개선 항목입니다.**

**재발 방지 통제 후보** — 액션 아이템은 계층별로 고르게 나눕니다.

| 액션 | 계층 | 본문 |
|---|---|---|
| 장기 액세스 키 발급 자체를 SCP로 금지 | 예방 | 6.4, 37.2 |
| IMDSv2를 SCP·Config로 강제 | 예방 | 8.3, 22.x, `ec2-imdsv2-check` |
| 저장소·CI 시크릿 스캐닝을 병합 차단으로 | 예방 | 27.3, 28.3 |

### 10. 이 시나리오의 흔한 실수 ⚠️

| 실수 | 결과 | 올바른 구성 |

## PB-02. 퍼블릭 데이터 노출

> S3 버킷·객체, EBS 스냅샷, AMI, RDS 스냅샷·인스턴스가 의도치 않게 공개된 상황.

### 0. 한눈에 보기

| 항목 | 값 |
|---|---|
| **트리거** | Config `s3-bucket-public-read-prohibited` 등 비준수, GuardDuty `Policy:S3/*`, Macie 발견, 외부 제보·보안 연구자 연락 |
| **심각도 기본값** | **SEV2**. 민감 데이터 포함 **또는** 외부 접근 흔적 확인 시 **SEV1** |
| **목표 봉쇄 시간** | 노출 차단 **15분**. 단, **접근 로그를 확인한 뒤** 차단 |
| **필요 역할** | IC, 기술 분석(S3·데이터), 법무·개인정보 보호책임자(**초기부터**), 커뮤니케이션 |
| **본문 참조** | 15.2(계정 수준 BPA), 15.4(버킷 정책), 15.11(액세스 로깅·데이터 이벤트), 16.7(스냅샷·AMI 공유 사고), 12.2·12.4(데이터 분류·Macie), 33.4(유출 차단), 4.3(규제) |
| **이 시나리오의 급소** | **노출 기간과 실제 접근 여부**를 확정해야 통지 범위가 정해진다. 급히 닫으면서 증거를 덮는 것이 가장 큰 실수 |

### 1. 트리거 — 무엇이 이 플레이북을 발동시키는가

| 원천 | 구체적 신호 | 대상 |
|---|---|---|
| AWS Config | `s3-bucket-public-read-prohibited` 비준수 | S3 버킷 |
| AWS Config | `s3-bucket-public-write-prohibited` 비준수 | S3 버킷 — **쓰기 공개는 더 심각** |
| AWS Config | `s3-account-level-public-access-blocks` 비준수 | 계정 수준 BPA가 꺼짐 |
| AWS Config | `ebs-snapshot-public-restorable-check` 비준수 | EBS 스냅샷 |
| AWS Config | `rds-snapshots-public-prohibited` 비준수 | RDS 스냅샷 |
| AWS Config | `rds-instance-public-access-check` 비준수 | RDS 인스턴스가 퍼블릭 접근 가능 |
| GuardDuty | `Policy:S3/BucketAnonymousAccessGranted` | 익명 접근이 **허용됨** |
| GuardDuty | `Policy:S3/BucketBlockPublicAccessDisabled` | 버킷의 BPA가 해제됨 |
| GuardDuty | `Policy:IAMUser/S3BlockPublicAccessDisabled` | 주체가 BPA를 껐다 |
| GuardDuty | `Policy:IAMUser/S3BucketPublic`, `Policy:IAMUser/S3BucketSharedExternally` | 버킷이 공개/외부 공유됨 |

| 알람(30.3) | #11 S3 버킷 정책·ACL 변경 / #15 대량 다운로드 | 변경 시점과 반출 시점 |
| Macie(31.3, 12.4) | 퍼블릭 버킷에서 민감 데이터 유형 발견 | **심각도를 SEV1으로 올리는 결정적 근거** |
| IAM Access Analyzer(7.7) | 외부 접근 신규 발견 | S3·KMS·스냅샷·Lambda 등 |
| 외부 | 보안 연구자 연락, 고객 제보, 언론 문의, 데이터가 제3자 사이트에 게시됨 | **가장 흔한 실제 트리거** |

> ⚠️ **외부 제보로 들어오는 경우, 제보자에게 "무엇을 보았는지"를 먼저 확보하십시오.** 파일명·객체 키·스크린샷은 노출 범위를 특정하는 가장 빠른 단서이고, 제보자가 이미 사본을 갖고 있는지도 8절 통지 판단에 영향을 줍니다. **제보자를 적대적으로 대하지 마십시오** — 26.5의 제보 창구 운영이 여기서 값을 합니다.

### 2. 심각도 판정

**질문 세 개.**

1. 노출된 데이터에 **개인정보·인증정보·영업비밀**이 있는가? (12.2의 분류, 12.3의 `DataClass` 태그)
2. **외부에서 실제로 접근한 기록**이 있는가? (S3 서버 액세스 로그, CloudTrail 데이터 이벤트)
3. 노출 상태가 **얼마나 오래** 지속되었는가?

| 조건 | 등급 | 에스컬레이션 |
|---|---|---|
| 민감 데이터 + 외부 접근 기록 확인 | **SEV1** | 전원 + 경영진 + 법무. **통지 시계 시작** |
| 민감 데이터 노출, 접근 기록은 **확인 불가**(로깅 없음) | **SEV1** | 전원 + 법무. ⚠️ "없다"가 아니라 "모른다"로 취급 |
| 쓰기 공개(익명 `PutObject`·`DeleteObject` 가능) | **SEV1** | 전원. 데이터 변조·악성 파일 업로드 가능성 |
| 민감 데이터 아님 + 외부 접근 기록 있음 | **SEV2** | IC + 기술 분석 |
| 민감 데이터 아님 + 접근 기록 없음 | **SEV2** | IC + 기술 분석 |
| 공개 의도가 명확한 자산(`shopmini-assets` 같은 CDN 오리진) | **SEV3** | 담당 분석가. 단, **대상이 맞는지 재확인** |
| 설정 오류 경보이나 실제 공개는 성립하지 않음(상위 BPA가 막음) | **SEV3** | 담당 분석가 |

> 🔴 **"접근 기록이 없다"와 "접근 로그가 없다"를 절대 혼동하지 마십시오.** S3 서버 액세스 로깅과 CloudTrail 데이터 이벤트가 꺼져 있었다면, 우리는 접근 여부를 **알 수 없습니다.** 그 경우 법무는 "접근이 없었다"를 전제로 판단할 수 없고, 대부분의 조직은 보수적으로 통지합니다. **15.11을 사고 전에 켜는 것이 곧 통지 비용을 줄이는 일입니다.**

```bash
aws s3api put-public-access-block --bucket "$BUCKET" \
  --public-access-block-configuration \
  BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true \
  --profile "$PROFILE"
```

```bash
# D5 — 퍼블릭 스냅샷 전부 해제 (3절 ⑦의 목록을 그대로 받는다)
```

> ⚠️ **D1은 조직에서 가장 넓은 폭발 반경을 가진 "안전한" 명령입니다.** 계정 수준 BPA를 켜면 **의도적으로 공개인 모든 버킷이 함께 막힙니다.** ShopMini에서 `shopmini-assets`가 퍼블릭 버킷 정책으로 서비스되고 있었다면 CDN이 죽습니다. 그래서 **평상시에 D1을 이미 켜 두고 CloudFront는 OAC로 접근하게 만드는 것**이 정답입니다(15.2, 23.7). 그 상태라면 이 사고는 애초에 발생하지 않습니다.

> ⚠️ **D3에서 버킷 정책을 통째로 지우지 마십시오.** `shopmini-uploads`의 정책에는 TLS 강제·VPC 엔드포인트 제한 같은 **보안 문장**도 들어 있습니다(15.4). 공개 문장만 제거한 수정본을 `put-bucket-policy`로 올리고, 원본은 3절 ①에서 이미 증거로 남겨 두었습니다.

> 🔴 **공개 해제 후 실제로 막혔는지 확인하십시오.** 자격 증명 없이 접근해 보는 것이 가장 확실합니다.
> ```bash
> aws s3api head-object --bucket shopmini-uploads --key path/to/known-object \
>   --no-sign-request --region ap-northeast-2
> # 403 또는 오류가 나야 정상. 성공하면 아직 공개 상태다.
> ```

### 5. 증거 보전

**이 시나리오에서 가장 먼저 사라지는 증거는 접근 로그입니다.** 수명 주기 정책으로 지워지고, 노출 기간이 수개월이면 이미 일부가 없습니다.

| 순위 | 무엇을 | 왜 먼저 | 방법 |
|---|---|---|---|
| 1 | **변경 전 구성 원본** | 4절에서 우리가 직접 바꾼다 | 3절 ①의 출력 파일 + 해시 |
| 2 | **S3 서버 액세스 로그** | 수명 주기 정책으로 소멸. 보존 기간이 짧은 경우가 많다 | 증거 버킷 복사 + 법적 보존 |
| 3 | **CloudTrail 데이터 이벤트** | 같음 | 증거 버킷 복사 + 법적 보존 |
| 4 | **Config 구성 이력** | 노출 기간 확정의 유일한 근거 | JSON 내보내기 + 해시 |
| 5 | **노출된 객체 목록과 버전** | 6절에서 정리·이동할 수 있다 | `list-object-versions` 전체 목록 보존 |
| 6 | Macie 발견 결과 | 민감 데이터 판정 근거 | JSON 내보내기 |

```bash
aws s3 cp \
```

```bash
# 4 ── 노출 기간 확정 근거를 파일로 고정
```

### 6. 근절 (Eradication)

**이 시나리오의 근절은 "공격자를 쫓아내는 것"이 아니라 "같은 노출이 다시 생기지 않게 만드는 것"입니다.** 대부분 설정 오류이지 침입이 아니기 때문입니다.

| # | 확인·조치 | 방법 |
|---|---|---|
| 1 | **누가·왜 공개로 바꿨는지** 확정 | 3절 ③의 CloudTrail. 사람인지 IaC인지 자동화인지 |
| 2 | 침입에 의한 변경이었다면 → **PB-01 병행** | `PutBucketPolicy` 호출 주체의 자격 증명을 의심 |
| 3 | IaC 템플릿에 반영 | 콘솔에서만 고치면 다음 배포가 되돌린다(28.4 드리프트) |
| 4 | **같은 패턴의 다른 리소스 전수 조사** | 3절 ⑦~⑨를 전 계정·전 리전에서 |
| 5 | 쓰기 공개였다면 **업로드된 객체 검사** | 노출 기간 중 `PutObject`된 객체를 전수 확인. 웹셸·피싱 페이지·불법 콘텐츠 |
| 6 | 공개 URL이 외부에 캐시되었는지 | 검색엔진 색인, 제3자 아카이브. 삭제 요청 경로 확인 |
| 7 | 예방 통제 부착 | 아래 표 |

**5번을 빠뜨리지 마십시오.** 쓰기 공개 버킷은 **남의 데이터를 우리 비용으로 호스팅하는 통로**가 됩니다. 불법 콘텐츠가 올라와 있으면 그 자체가 별도의 법적 문제가 됩니다.

| 예방 통제 | 구현 | 본문 |
|---|---|---|
| 계정 수준 BPA 상시 ON | 신규 계정 베이스라인에 포함 | 15.2, 37.9 |
| BPA 해제를 SCP로 금지 | `s3:PutAccountPublicAccessBlock`·`s3:PutBucketPublicAccessBlock` Deny | 37.2 |
| 스냅샷·AMI 공개를 SCP로 금지 | `ec2:ModifySnapshotAttribute`·`ec2:ModifyImageAttribute`에 조건 | 16.7, 37.2 |
| RDS 스냅샷 공개 금지 | `rds:ModifyDBSnapshotAttribute` 조건 | 37.2 |
| 배포 전 정책 게이트 | 퍼블릭 리소스를 만드는 IaC를 병합 차단 | 28.2, 28.3 |
| Config 자동 교정 | 비준수 발견 시 자동으로 BPA 재적용 | 35.3. ⚠️ 예외 태그 필수(35.5) |
| Access Analyzer 상시 감시 | 외부 접근 신규 발견을 알람으로 | 7.7 |

### 7. 복구 (Recovery)

**재배포 대상이 있는 시나리오가 아닙니다.** 데이터는 그 자리에 있고, 바뀌어야 하는 것은 접근 통제입니다. 다만 **쓰기 공개였다면 데이터 무결성 복구가 필요합니다.**

| 상황 | 복구 절차 |
|---|---|
| 읽기 공개만 | 4절의 차단이 곧 복구. 정상 접근 경로(CloudFront OAC, VPC 엔드포인트)가 동작하는지 확인 |
| 쓰기 공개 | 노출 기간 중 추가·변경된 객체를 **버전 관리 이력으로 판별해 원복**(15.8). 판별 불가하면 노출 이전 버전으로 복원 |
| 노출된 것이 **자격 증명**이었다면 | **PB-01 7절의 전면 순환**을 수행. 공개 버킷의 설정 파일·백업에 키가 들어 있는 경우가 흔하다 |
| 노출된 것이 **스냅샷·AMI**였다면 | 그 이미지에 들어 있던 모든 시크릿·키 페어를 폐기(22.2, 22.4). **이미지는 회수할 수 없다** |
| 노출된 것이 **RDS 스냅샷**이었다면 | DB 계정 비밀번호 전면 변경. 스냅샷 사본은 이미 복사되었을 수 있다고 가정 |

> 🔴 **공개되었던 이미지·스냅샷은 "회수"되지 않습니다.** 공개 상태였던 동안 누군가 복사했다면 그 사본은 영원히 남습니다. 따라서 그 안의 **모든 비밀은 유출된 것으로 간주하고 전부 교체**해야 합니다. 16.7이 이 시나리오를 다룹니다.

#### 🔴 완료 판정 기준

- [ ] 계정 수준 BPA 네 값이 모두 `true`이고, 전 계정·전 리전에서 확인되었다
- [ ] 3절 ⑦~⑨를 다시 돌려 퍼블릭 스냅샷·AMI·RDS 스냅샷이 **0개**임을 확인했다
- [ ] `--no-sign-request` 접근이 403으로 거부되는 것을 실제로 확인했다
- [ ] Config 규칙 4종이 모두 `COMPLIANT`로 전환되었다
- [ ] IaC 템플릿에 수정이 반영되어 다음 배포가 되돌리지 않는다(드리프트 재발 없음)
- [ ] 쓰기 공개였다면 노출 기간 중 업로드된 객체를 전수 검사·처리했다
- [ ] 노출 자산에 포함된 시크릿을 전부 교체했다
- [ ] 노출 기간·노출 객체 목록·외부 접근 여부가 **문서로 확정**되어 법무에 전달되었다

### 8. 통지

**이 플레이북에서 통지는 부차적 절차가 아니라 주 절차입니다.** 기술적 봉쇄는 15분이면 끝나고, 남은 며칠은 전부 "누구에게 무엇을 알릴 것인가"입니다.

| 대상 | 언제 | 무엇을 | 누가 |
|---|---|---|---|
| 내부 법무·개인정보 보호책임자 | **3절이 끝나는 즉시** | 데이터 유형, 노출 기간 추정, 접근 기록 유무 | IC |
| 내부 경영진 | 선언 즉시 | 서비스 영향, 통지 가능성 | IC |
| 규제 기관 | 개인정보 노출이 확인된 경우, **관할 법령 기한 내** | 법령이 정한 서식 | 법무 / 개인정보 보호책임자 |
| 정보주체·고객 | 관할 법령 또는 계약상 기한 | 사전 승인 템플릿(32.3 ⑥) | 홍보 / 고객 지원 |
| 계약 상대방·파트너 | 그들의 데이터가 포함되었다면 계약 통지 조항대로 | 계약이 정한 범위 | 법무 |
| 제보자 | 확인 후 신속히 | 접수 사실, 조치 완료 사실. **감사 표시** | 커뮤니케이션 |
| 사이버보험사 | 약관상 기한 | 약관 서식 | 재무 / 법무 |
| 검색엔진·아카이브 | 색인이 확인되면 | 삭제 요청 | 기술 분석 |

**통지 판단에 필요한 세 가지 사실**을 법무에 넘기십시오. 이것이 없으면 법무는 판단할 수 없습니다.

1. **무엇이** 노출되었는가 — 데이터 유형과 항목(12.2의 분류 체계로 표현)
2. **얼마나 오래** — 노출 시작·종료 시각(UTC). 3절 ②의 Config 이력이 근거
3. **접근되었는가** — 외부 접근 기록의 유무와, **로그가 없어서 판단 불가한 구간이 있는지**

> ⚠️ **법정 기한은 이 책에서 확정하지 않습니다.** 개인정보 노출의 신고·통지 의무는 관할 법령마다 기한·대상·서식이 다르고 개정이 잦습니다. **반드시 최신 법령 원문과 법무 검토로 확인**하십시오(4.3, 33.6). 기산점은 `DECLARED_AT`으로 고정합니다.

> ⚠️ **"노출 건수"를 초기에 발표하지 마십시오.** 객체 목록과 접근 로그 분석이 끝나기 전의 숫자는 거의 항상 낮게 나오고, 나중에 올라갑니다(33.6). 내부 보고에는 "현재까지 확인된 최소 N건, 미조사 구간 있음, 상향 가능성 높음"으로 씁니다.

### 9. 사후 (Post-Incident)

**타임라인 재구성 — 이 시나리오는 시각 확정이 통지의 근거가 되므로 특히 엄밀해야 합니다.**

| 반드시 확정할 시각 | 근거 |
|---|---|
| 공개 설정으로 바뀐 시각 | CloudTrail `PutBucketPolicy`·`PutBucketAcl`·`DeletePublicAccessBlock` |
| 최초 외부 접근 | S3 서버 액세스 로그 / 데이터 이벤트 |
| 최다 접근 구간 | 같음 |
| 우리의 최초 인지 | Config 비준수 생성, GuardDuty `createdAt`, 제보 접수 |
| 공개 차단 완료 | `PutPublicAccessBlock` 호출 시각 |
| 노출 기간 총계 | 위 1번과 5번의 차 — **통지문에 들어갈 값** |

**액션 아이템 후보**

| 액션 | 계층 | 본문 |
|---|---|---|
| 계정 수준 BPA를 신규 계정 베이스라인에 강제 | 예방 | 15.2, 37.9 |
| BPA 해제·스냅샷 공개를 SCP로 금지 | 예방 | 37.2, 16.7 |
| 퍼블릭 리소스를 만드는 IaC를 병합 차단 | 예방 | 28.2, 28.3 |
| 민감 버킷에 **S3 데이터 이벤트와 서버 액세스 로깅 둘 다** 활성화 | 탐지 | 15.11, 29.2 |
| Macie 정기 분류 작업으로 민감 데이터 위치 상시 파악 | 탐지 | 12.4, 31.3 |
| Config 자동 교정으로 공개 설정 즉시 원복 | 대응 | 35.3 |
| 외부 제보 창구를 공식화하고 응답 SLA를 정함 | 대응 | 26.5 |
| "무엇이 어디 있는지"의 데이터 인벤토리 갱신 | 복구 | 12.1, 12.3 |

**탐지 계층 항목이 두 개 들어간 것에 주목하십시오.** 이 사고에서 가장 비쌌던 것은 노출 자체가 아니라 **"접근되었는지 알 수 없다"** 는 상태였습니다.

### 10. 이 시나리오의 흔한 실수 ⚠️

| 실수 | 결과 | 올바른 구성 |
|---|---|---|
| 접근 로그를 확인하기 **전에** 버킷을 급히 닫음 | 노출 기간·접근 여부의 증거가 덮임 → 통지 범위를 정할 수 없음 | 3절 ①~⑤를 먼저. 단 쓰기 공개·민감 데이터면 D1 선행 |

| 버킷 하나만 닫고 종료 | 같은 계정의 스냅샷·AMI·RDS 스냅샷이 여전히 공개 | 3절 ⑦~⑨를 **전 리전**에서 |
| 노출된 객체를 삭제해 "해결" | 통지 범위 산정 불가, 증거 소멸 | 목록·해시 먼저, 필요하면 이동 |
| 버킷 정책을 통째로 삭제 | TLS 강제·VPC 제한 같은 보안 문장까지 사라짐 | 공개 문장만 제거한 수정본으로 교체 |
| 콘솔에서만 고침 | 다음 IaC 배포가 공개 설정을 되돌림 | 템플릿에 반영, 드리프트 탐지(28.4) |
| 공개되었던 AMI·스냅샷을 "회수했다"고 판단 | 그 안의 키·시크릿이 유출된 채 남음 | 포함된 모든 비밀을 교체(16.7, 22.4) |
| 쓰기 공개인데 업로드 객체를 안 봄 | 웹셸·불법 콘텐츠가 그대로 호스팅됨 | 노출 기간 `PutObject` 전수 검사 |
| 계정 수준 BPA를 사고 때 처음 켬 | 정상 공개 버킷(CDN 오리진)이 함께 죽음 | 평상시 ON + CloudFront OAC(15.2, 23.7) |
| 제보자를 법적으로 위협 | 다음 제보가 언론으로 감 | 제보 창구 공식화, 감사 표시(26.5) |
| 초기 노출 건수를 대외 발표 | 상향 정정 → 신뢰 상실 | 확정분과 조사 중인 것을 분리해 발표 |
| 법무를 봉쇄 완료 후에 부름 | 통지 기한 시계를 이미 몇 시간 까먹음 | **3절이 끝나는 즉시** 법무 투입 |

### 2. 심각도 판정

**질문 세 개.**

1. 채굴이 **어떤 자원**에서 돌고 있는가? 기존 워크로드 인스턴스인가, 공격자가 **새로 띄운** 인스턴스인가?
2. 공격자가 **인스턴스를 띄울 권한**을 가졌는가? (`RunInstances` 성공 기록)
3. 같은 자격 증명으로 **데이터에 접근한** 흔적이 있는가?

```bash
  --tag-specifications "ResourceType=snapshot,Tags=[{Key=IncidentId,Value=${CASE_ID}},{Key=Evidence,Value=true},{Key=LegalHold,Value=true}]" \
  --region "$REGION" --profile "$PROFILE"
```

```bash
# 6 ── 발견 원문을 파일로. Service.Action 에 채굴 풀 도메인·IP 가 들어 있다
aws guardduty get-findings --detector-id "$DETECTOR_ID" --finding-ids "$FINDING_ID" \
  --region "$REGION" --profile "$PROFILE" > "${CASE_ID}-guardduty-findings.json"
```

> ⚠️ **경로 A(공격자가 띄운 인스턴스)의 스냅샷을 건너뛰기 쉽습니다.** "우리 것이 아니니 그냥 지우면 된다"고 생각하기 때문입니다. 그러나 그 인스턴스의 사용자 데이터·설치 스크립트·접속 이력이 **공격자의 도구와 인프라를 알려주는 가장 좋은 자료**입니다. 반드시 스냅샷을 뜨십시오.

### 6. 근절 (Eradication)

**이 절이 이 플레이북의 핵심입니다.** 마이닝 프로세스를 죽이는 것은 근절이 아닙니다. **"왜 띄울 수 있었는가"를 닫는 것이 근절입니다.**

**침입 경로를 먼저 특정하십시오.** 3절 ③의 결과가 첫 갈림길입니다.

| 3절 ③의 결과 | 침입 경로 | 근절 |
|---|---|---|
| 공격자 주체가 `RunInstances` 성공 | **자격 증명 침해** | **PB-01 6절 전체를 수행**. 이것이 진짜 사고다 |
| 우리 배포 역할이 정상적으로 띄운 인스턴스가 감염 | **애플리케이션·이미지 침해** | 아래 표 |
| 컨테이너 이미지가 감염 | **공급망** | **PB-06 병행** |
| 기록 없음 | 로깅 공백 | 34.4 — 이벤트 선택기·트레일 범위부터 확인 |

**애플리케이션 계층 근절 체크리스트**

| # | 확인 | 방법 |
|---|---|---|
| 1 | 최초 실행 경로 | 스냅샷을 포렌식 계정에서 읽기 전용 마운트(34.3) → 웹셸·크론·systemd 유닛 확인 |
| 2 | 지속성 | `cron`, `systemd` timer, `rc.local`, 사용자 `authorized_keys`, 커널 모듈 |
| 3 | 공개 취약점 | 26.3 Inspector 결과, 실행 중이던 패키지 버전 |
| 4 | 노출된 관리 포트 | `describe-security-groups`로 `0.0.0.0/0` 인바운드 전수 조사 |
| 5 | 약한 인증 | SSH 비밀번호 인증, 기본 자격 증명, 노출된 관리 콘솔 |
| 6 | IMDS 경유 자격 증명 탈취 | IMDSv2 강제 여부(8.3) |
| 7 | 컨테이너 이미지 | 이미지 다이제스트 확인 → 레지스트리에서 같은 이미지 스캔(24.2, 26.3) |

```bash
# 4 ── 인터넷에 열린 인바운드 규칙 전수 조사
aws ec2 describe-security-groups \
  --filters Name=ip-permission.cidr,Values=0.0.0.0/0 \
  --query 'SecurityGroups[].{Id:GroupId,Name:GroupName,Vpc:VpcId,
           Open:IpPermissions[?contains(IpRanges[].CidrIp,`0.0.0.0/0`)].{P:IpProtocol,F:FromPort,T:ToPort}}' \
  --region "$REGION" --profile "$PROFILE"
```

```bash
# 7 ── 스냅샷의 멀웨어를 AWS 관리 환경에서 스캔한다 (재배포 전 1차 관문)
aws guardduty start-malware-scan --resource-arn \
  "arn:aws:ec2:ap-northeast-2:111122223333:instance/${INSTANCE}" \
  --region "$REGION" --profile "$PROFILE"
```

**그리고 공격자가 만든 모든 리소스를 정리합니다.** 2절 경로 A였다면 아래가 근절의 큰 부분입니다.

- [ ] 전 리전의 공격자 인스턴스 — **스냅샷 확보 후** 종료
- [ ] 공격자가 만든 시작 템플릿·ASG·Spot 요청·Fleet
- [ ] 공격자가 만든 보안 그룹·키 페어·인스턴스 프로파일
- [ ] 공격자가 만든 IAM 사용자·역할·키(PB-01 6절)
- [ ] 증설된 서비스 할당량 요청 취소
- [ ] 다른 리전의 VPC·서브넷 — 안 쓰는 리전에 새 VPC가 생겼는지

### 7. 복구 (Recovery)

**감염 인스턴스는 치료하지 않고 재배포합니다**(34.5). 채굴 악성코드는 지속성 메커니즘을 여럿 심는 것이 일반적이라 "프로세스를 죽이고 파일을 지웠다"로는 끝나지 않습니다.

| 단계 | 할 일 | 건너뛰면 |
|---|---|---|
| ① | 침입 경로 확정·제거 확인(6절) | 재배포 즉시 재감염 |
| ② | 취약점 패치·설정 수정을 **골든 AMI와 IaC에** 반영(22.5, 28장) | 새 인스턴스가 같은 취약점을 갖고 태어남 |
| ③ | 인스턴스 역할의 자격 증명 순환(PB-01 7절 ②) | 공격자가 새 시스템으로 그대로 접속 |
| ④ | 골든 AMI로 재생성, **IMDSv2 강제**로 기동 | 같은 경로로 자격 증명 재탈취 |
| ⑤ | 트래픽 전환 후 구 인스턴스는 격리 유지 | 롤백 불가 |
| ⑥ | 봉쇄 SCP·NACL·격리 SG 해제 | 정상 운영 복귀 불가 |
| ⑦ | 구 인스턴스 종료(**증거 4관문 통과 후만**, 33.5) | 증거 소멸 |
| ⑧ | 비용 정리 — AWS 지원 케이스로 부정 사용분 문의 | 청구 그대로 확정 |

**⑧을 잊지 마십시오.** 계정 침해로 발생한 비용에 대해서는 AWS 지원 케이스를 통해 상황을 설명하고 처리 방법을 문의할 수 있습니다. **보장된 결과는 없지만 문의하지 않으면 가능성도 없습니다.** 사이버보험 약관에 해당 항목이 있는지도 확인하십시오.

#### 🔴 완료 판정 기준

- [ ] 3절 ②(전 리전 인스턴스 목록)를 다시 돌려 **예상 밖 인스턴스가 0개**임을 확인했다
- [ ] 3절 ⑤(일별 비용)가 사고 이전 수준으로 돌아왔다 — **최소 3일 연속 관찰**
- [ ] GuardDuty에 `CryptoCurrency:*`·`Backdoor:*` 신규 발견이 72시간 동안 없다
- [ ] Resolver 쿼리 로그에서 채굴 풀 도메인 질의가 0이다
- [ ] 재배포된 인스턴스가 IMDSv2 강제·최소 권한 역할로 떴음을 확인했다
- [ ] 6절 「공격자가 만든 리소스」 체크리스트가 전부 처리되었다
- [ ] 침입 경로가 **문서로 특정**되었다. "불명"이면 축소 구성으로만 운영(34.5)

### 8. 통지

**데이터 유출이 없다면 대외 통지 의무가 없는 경우가 많은 시나리오입니다.** 다만 다음 셋은 반드시 확인하십시오.

| 대상 | 언제 | 무엇을 | 누가 |
|---|---|---|---|
| 내부 경영진·재무 | 선언 즉시 | 추정 비용, 서비스 영향, 조치 | IC |
| AWS | 계정 침해가 확인되면 | 지원 케이스 — 부정 사용 비용과 자격 증명 침해 사실 | 기술 분석 |
| 내부 법무 | **데이터 접근 흔적이 하나라도 보이면** | 데이터 유형과 잠정 범위 | IC |
| 규제 기관·고객 | 데이터 접근이 확인된 경우에만 | PB-01·PB-02의 8절을 따른다 | 법무 |
| 사이버보험사 | 약관상 기한 | 약관 서식 | 재무 / 법무 |
| 제3자 | **우리 자산이 외부를 공격했다면**(스캔·DDoS 참여) | 피해 조직·AWS 남용 신고 창구 | IC / 법무 |

> ⚠️ **"채굴이니까 데이터는 안전하다"고 단정하지 마십시오.** 인스턴스에서 코드를 실행할 수 있었던 공격자는 **그 인스턴스의 IAM 역할로 무엇이든 할 수 있었습니다.** 3절 결과에 데이터 접근이 없더라도, 데이터 이벤트가 꺼져 있었다면 "없다"가 아니라 "모른다"입니다(PB-02 2절과 같은 원칙).

> ⚠️ 법정 통지 기한은 이 책에서 확정하지 않습니다. 데이터 접근이 확인된 경우 **법무 검토로 확인**하십시오(4.3, 33.6).

| 비용 알람에만 의존 | 며칠을 잃음 | GuardDuty + 안 쓰는 리전 질의 병행 |
| 데이터 접근 조사를 생략 | 데이터 이벤트가 꺼져 있어 "모른다"인데 "없다"로 보고 | 8절 ⚠️ — 로그 부재는 무혐의가 아니다 |
| ECS 태스크를 중지해 조사 | 컨테이너 내부 증거 전부 소멸 | 서비스에서 분리, 태스크는 유지(33.3) |
| 격리 SG를 먼저 붙임 | 헬스 체크 실패 → ASG가 종료·교체 | `suspend-processes` 선행(전제 ⑥ 2번) |
| 부정 사용 비용을 그냥 확정 | 회수 가능성을 스스로 포기 | AWS 지원 케이스 + 보험 약관 확인 |
| 이그레스는 열어 둔 채 도메인만 차단 | 채굴 풀은 IP 직결로 우회 가능 | 19.6 허용 목록 이그레스 |

## PB-04. 랜섬웨어 / 데이터 파괴

> 데이터가 암호화·삭제되거나, 백업이 파괴되거나, KMS 키가 삭제 예약된 상황.

### 0. 한눈에 보기

| 항목 | 값 |
|---|---|
| **트리거** | KMS `ScheduleKeyDeletion`·`DisableKey` 알람(30.3 #12), S3 대량 삭제, 백업 복구 지점 삭제, 몸값 요구, GuardDuty `Impact:S3/*` |
| **심각도 기본값** | **SEV1** — 예외 없음 |
| **목표 봉쇄 시간** | 백업 생존 확인 **15분**, 파괴 진행 정지 **30분**, KMS 삭제 예약 취소 **즉시** |
| **필요 역할** | IC, 기술 분석(데이터·KMS·백업), 경영진(**협상·중단 결정**), 법무, 커뮤니케이션 |
| **본문 참조** | 17.3~17.6(백업·랜섬웨어·복구 테스트), 13.11(KMS 운영 함정), 15.8·15.9(버전 관리·객체 잠금), 33.4 ④(KMS), 34.5(재배포·백업 오염), 30.3 #12 |
| **이 시나리오의 급소** | **백업이 살아 있는지 먼저 확인한다.** 그리고 운영 계정 자격 증명으로 확인하지 않는다 |

### 1. 트리거 — 무엇이 이 플레이북을 발동시키는가

| 원천 | 구체적 신호 | 단계(17.5) |
|---|---|---|
| 알람(30.3 #12) | CloudTrail `ScheduleKeyDeletion`, `DisableKey` | **4단계 — 최우선 신호** |
| 알람 | `PutKeyPolicy`, `DisableKeyRotation`, `DeleteAlias` | 4단계 — 키 접근 경로 차단 |
| GuardDuty | `Impact:S3/AnomalousBehavior.Delete` | 5단계 — 비정상 대량 삭제 |
| GuardDuty | `Impact:S3/AnomalousBehavior.Permission` | 4단계 — 버킷 정책·ACL 변경 |
| GuardDuty | `Impact:IAMUser/AnomalousBehavior` | 4~5단계 — 파괴 계열 이상 행동 |
| GuardDuty | `Discovery:S3/AnomalousBehavior`, `Discovery:IAMUser/AnomalousBehavior` | 2단계 — 정찰. **여기서 잡으면 가장 싸다** |
| CloudTrail | `DeleteRecoveryPoint`, `DeleteBackupVault`, `PutBackupVaultAccessPolicy` | 4단계 — 백업 무력화 |
| CloudTrail | `PutBucketVersioning`(Suspended), `PutBucketLifecycleConfiguration` | 4단계 — 버전 관리 중단 |
| CloudTrail | `DeleteDBInstance`, `DeleteDBCluster`, `DeleteDBSnapshot` | 5단계 |
| CloudTrail | `PutObject`에 SSE-C 헤더 급증 | 5단계 — **공격자 키로 재암호화** |
| 알람(30.3) | #11 S3 버킷 정책·ACL 변경 / #15 대량 다운로드 | 4~5단계 |
| AWS Config | `kms-cmk-not-scheduled-for-deletion` 비준수 | **4단계의 결정적 신호** |
| AWS Config | `s3-bucket-versioning-enabled`, `backup-recovery-point-manual-deletion-disabled` 비준수 | 4단계 준비 실패 |
| 운영 | 서비스 장애 — 객체를 읽을 수 없음, DB가 뜨지 않음, 볼륨 마운트 실패 | 5단계가 **이미 지난** 상태 |
| 외부 | 몸값 요구 메일·객체, 랜섬 노트 파일, 콘솔 스크린샷 | 6단계 |

> 🔴 **`ScheduleKeyDeletion`은 확인 후 처리 대상이 아니라 즉시 호출 대상입니다**(17.5). 정상 운영에서 운영 계정의 KMS 키가 삭제 예약되는 일은 거의 없습니다. 그리고 **대기 기간 안에는 되돌릴 수 있습니다** — 이 플레이북에서 시간이 가장 비싼 항목입니다.

### 2. 심각도 판정

**이 플레이북의 기본값은 SEV1입니다.** 판정표는 등급을 나누기 위한 것이 아니라 **무엇을 먼저 할지**를 가르기 위한 것입니다.

| 조건 | 등급 | 최우선 조치 |
|---|---|---|
| KMS 키 삭제 예약됨 | **SEV1** | **`cancel-key-deletion` 즉시**(4절 F1) |
| 백업 볼트·복구 지점이 삭제됨 | **SEV1** | 백업 계정 볼트 생존 확인(4절 F2) |
| 운영 데이터가 삭제·암호화됨 | **SEV1** | 파괴 진행 정지(4절 F3~F5) |
| 버전 관리가 중단됨 / 객체 잠금이 없는 상태 확인 | **SEV1** | 같음 |
| 정찰 단계에서 포착(대량 `List*`·`Describe*`만) | **SEV1** | **진행 중 공격.** 자격 증명 차단(PB-01) |
| 몸값 요구만 있고 실제 파괴가 확인되지 않음 | **SEV1** | 사실 확인 + 백업 생존 확인. **허위 협박일 수 있으나 등급은 유지** |
| 사용자 실수로 인한 대량 삭제(악의 없음 확인) | **SEV2** | 복구 절차. 단, **확인 전에는 SEV1** |

> ⚠️ **"실수였다"는 판정을 서둘러 내리지 마십시오.** 공격자가 정상 배포 역할을 탈취해 삭제한 경우와 사람이 잘못 실행한 경우는 CloudTrail 상에서 처음에는 똑같이 보입니다. **주체가 사람임을 본인 확인으로 검증하기 전까지는 SEV1을 유지합니다.**

> 🔴 **협상 여부는 기술 판단이 아닙니다.** 몸값 지불 여부는 경영진·법무의 결정이며, 법역에 따라 지불 자체가 법적 문제가 될 수 있습니다. **기술팀은 "복구 가능성"과 "예상 복구 시간"이라는 사실만 제공하십시오.**

### 6. 근절 (Eradication)

**근절 전에 답해야 하는 질문: 공격자가 아직 안에 있는가?** 랜섬웨어는 대개 침입 후 수 주가 지난 뒤에 실행됩니다. 파괴 시점이 아니라 **최초 침입 시점**을 찾아야 합니다.

| # | 확인 | 방법 |
|---|---|---|
| 1 | 파괴에 쓰인 자격 증명의 정체와 유출 경로 | **PB-01 3·6절 전체를 수행** |
| 2 | 최초 침입 시점 | CloudTrail 역추적. 조사가 진행될수록 계속 앞으로 당겨진다 |
| 3 | 지속성 메커니즘 | PB-01 6절 표 10개 항목 |
| 4 | 파괴 권한이 왜 있었는가 | 해당 주체의 정책에서 `kms:ScheduleKeyDeletion`, `backup:Delete*`, `s3:DeleteObjectVersion` 확인 |
| 5 | 백업 계정으로의 경로가 있었는가 | 백업 계정 볼트 접근 정책, 크로스 계정 역할 신뢰 관계(17.4) |
| 6 | 감염 인스턴스·컨테이너 | PB-03 6절. 웹셸·백도어 |
| 7 | 다른 리전·계정의 동일 패턴 | 3절 ④ 질의를 전 계정·전 리전으로 확대 |

**4번이 이 사고의 근본 원인인 경우가 대부분입니다.** 17.5의 사고 시나리오가 정확히 그렇습니다 — **배포 역할에 `AdministratorAccess`가 붙어 있었습니다.**

**권한 근절 — 파괴 권한을 일상 역할에서 제거합니다.**

| 권한 | 누구에게만 | 본문 |
|---|---|---|
| `kms:ScheduleKeyDeletion`, `kms:PutKeyPolicy` | 전용 키 관리자만. 배포 역할에는 `Encrypt`/`Decrypt`/`GenerateDataKey`만 | 13.4, 17.5 |
| `backup:DeleteRecoveryPoint`, `backup:DeleteBackupVault` | 백업 계정의 전용 역할만 | 17.4 |
| `s3:DeleteObjectVersion`, `s3:PutBucketVersioning` | 없음. 객체 잠금으로 대체 | 15.8, 15.9 |
| `rds:DeleteDBInstance`, `rds:DeleteDBCluster` | 승인 게이트 뒤에만 | 28.5 |
| 루트 사용자의 파괴 액션 | **SCP로 루트에도 적용되는 `DenyKeyDestruction`** | 17.4, 37.2 |

### 7. 복구 (Recovery)

**34.5의 재배포 원칙이 이 시나리오에서 가장 엄격하게 적용됩니다.** 그리고 34.5의 「백업 자체가 오염되었을 가능성」이 여기서 실제 문제가 됩니다.

#### 🔴 복구 지점 선택 규칙

| 규칙 | 구체적으로 |
|---|---|
| **침해 시작 시점을 먼저 확정한다** | 6절 2번의 결과. **"가장 최근"이 아니라 "침해 이전"** |
| 후보를 격리 환경에서 먼저 검증한다 | 포렌식 계정에서 복원 → IOC 스캔 → 통과분만 운영 복원 |
| 코드와 데이터를 분리해 복원한다 | **코드는 백업이 아니라 Git·골든 AMI에서** 온다 |
| 사용자 업로드 파일은 별도 검사 | `shopmini-uploads` 객체를 멀웨어 스캔 후 반입 |
| 데이터베이스는 변경 이력을 대조한다 | 침해 이전 스냅샷과 스키마·계정·트리거 비교 |

> ⚠️ **침해 시작 시점이 백업 보존 기간보다 오래되었다면**, 모든 복구 지점이 오염 후보입니다. 이때는 **가장 오래된 깨끗한 지점으로 돌아가되 그 사이의 데이터 손실을 감수**하거나, **오염된 지점을 정리해 쓰되 경영진의 위험 수용 서명**을 받습니다(34.5). 기술팀이 단독으로 결정할 사안이 아닙니다.

#### 재구축 순서

| 단계 | 할 일 | 건너뛰면 |
|---|---|---|
| ① | KMS 키 상태 정상화(F1 + `enable-key`) 확인 | 복원해도 복호화 불가 |
| ② | 근본 원인 확정·제거(6절) | 복원 직후 재파괴 |
| ③ | 증거 보전 완료 확인(5절) | 복원이 증거를 덮음 |
| ④ | **자격 증명 전면 순환**(PB-01 7절 ②) | 공격자가 복원된 시스템을 다시 파괴 |
| ⑤ | 인프라를 골든 AMI·IaC로 재생성 | 손으로 만든 시스템 = 검증 불가 |
| ⑥ | **침해 이전 복구 지점**에서 데이터 복원 | 웹셸까지 함께 복원 |
| ⑦ | 복원 데이터 무결성 검증(체크섬, 건수, 스키마) | 부분 복원을 완전 복원으로 착각 |
| ⑧ | 트래픽 전환 | — |
| ⑨ | 봉쇄 SCP 해제 | 정상 운영 복귀 불가 |

```bash
# ⑥ ── 백업 계정 볼트에서 복원. 🔴 KMS 권한이 여기서 자주 막힌다(17.6)
aws backup start-restore-job \
  --recovery-point-arn "$CLEAN_RP_ARN" \
  --iam-role-arn arn:aws:iam::111122223333:role/AWSBackupDefaultServiceRole \
  --metadata file://restore-metadata.json \
  --profile awssec-backup --region ap-northeast-1
```

> ⚠️ **복원이 권한·KMS 문제로 실패하는 것은 예외가 아니라 통상입니다**(17.6). 17.6의 사고 시나리오 — 14개월간 초록색이던 백업이 실제 복원에서 권한과 KMS로 두 번 막힘 — 가 그대로 재현됩니다. **복원 테스트를 해 본 조직만 이 단계를 시간 안에 통과합니다.**

#### 🔴 완료 판정 기준

- [ ] KMS 키가 `Enabled` 상태이고, 삭제 예약이 없다
- [ ] 복원된 데이터의 **건수·체크섬이 침해 이전 기준값과 일치**한다
- [ ] 복원 원본이 **침해 시작 시점 이전**의 복구 지점임이 문서로 확인되었다
- [ ] 복원 데이터에 대해 IOC·멀웨어 스캔을 수행했고 통과했다
- [ ] 파괴에 쓰인 자격 증명이 무효화되었고, 6절의 권한 근절이 반영되었다
- [ ] 백업 계정 볼트가 잠금 상태이고 복구 지점이 정상 생성되고 있다
- [ ] **복원 후 72시간 동안** 신규 파괴 행위·이상 발견이 없다
- [ ] 봉쇄 SCP가 해제되었고 정상 워크로드가 전부 복구되었다

### 9. 사후 (Post-Incident)

**타임라인에서 확정할 시각** — 이 시나리오는 "침해 시작 시점"이 복구 지점 선택의 근거가 되므로 가장 중요합니다.

| "암호화만 되었고 유출은 없다"고 보고 | 이중 갈취를 놓치고 통지 의무를 오판 | 반출 흔적 별도 조사, 로그 부재는 "모른다" |

| 복원 테스트를 한 번도 안 해 봄 | 권한·KMS로 막혀 복구가 몇 시간씩 지연 | 분기 1회 실제 복원(17.6) |
| 근본 원인 규명 전에 서비스 복구 | 같은 자격 증명으로 재파괴 | 6절을 재배포의 선행 게이트로(34.5) |
| 서비스 중단 공지와 유출 통지를 한 덩어리로 관리 | 한쪽 기한을 놓침 | 두 축을 분리해 각각 관리 |

### 2. 심각도 판정

**판정 전에 반드시 확인할 것: 이것이 내부자 사건인가, 내부자의 자격 증명을 탈취한 외부자 사건인가?** 두 경우의 대응은 완전히 다릅니다.

| 질문 | 내부자 | 외부자(자격 증명 탈취) |
|---|---|---|
| 접속 IP·기기 | 평소와 같음 | 평소와 다름, 해외·VPN·Tor |
| 접근 패턴 | 업무 권한 범위 안이 많음 | 열거·권한 상승 시도 |
| 시간대 | 근무 시간과 겹침 | 새벽·주말에 집중 |
| 본인 확인 | **본인이 "내가 했다"고 말함** | 본인이 부인 |

**⚠️ 확인 방법에 주의하십시오.** 내부자 사건이 의심되는 상황에서 **본인에게 직접 묻는 것은 조사 계획의 일부여야 합니다.** 인사·법무와 상의 없이 묻지 마십시오 — 증거 인멸의 신호가 됩니다.

| 조건 | 등급 | 에스컬레이션 |
|---|---|---|
| 대량 데이터 반출이 확인됨 | **SEV1** | IC + 인사 + 법무 + 경영진. **제한된 인원만** |
| 로그 삭제·중지 시도 | **SEV1** | 같음. 은폐 시도는 고의의 강한 정황 |
| 권한을 스스로 상승시킴 | **SEV1** | 같음 |
| 업무 범위를 벗어난 조회가 반복됨 | **SEV2** | IC + 인사 + 법무 |
| 퇴사 예정자의 평소보다 많은 다운로드 | **SEV2** | IC + 인사. **업무상 정당 사유 확인 먼저** |
| 외부자의 자격 증명 탈취로 판명 | **→ PB-01로 전환** | PB-01의 판정표 적용 |
| 업무상 정당 사유가 확인됨 | **SEV4 종결** | 기록만 남기고 종결. **조사 사실을 유출하지 않음** |

> 🔴 **오탐일 때의 처리가 이 플레이북의 품질을 결정합니다.** 정당한 업무였던 것으로 확인되면 **조사했다는 사실을 대상자와 주변에 알리지 않고 종결**하고, 기록은 인사·법무가 보관합니다. 이 절차가 없으면 다음부터 아무도 제보하지 않습니다.

### 4. 봉쇄 (Containment) 🔴

**이 플레이북의 봉쇄는 다른 다섯과 다릅니다. 즉시 차단이 항상 정답이 아닙니다.**

| 판단 | 조치 방향 |
|---|---|
| **파괴·반출이 진행 중** | 즉시 차단. 증거보다 피해 정지가 우선 |
| **반출이 이미 끝났고 재발 위험 낮음** | **차단을 미루고 관찰.** 인사·법무 절차와 시점을 맞춘다 |
| **대상자가 아직 재직 중이고 업무가 걸려 있음** | 인사와 합의한 시점에 **권한 축소부터** |
| **퇴사 확정, 최종 출근일 지정됨** | 9.6의 오프보딩 절차를 **정시에, 빠짐없이** |

> 🔴 **차단 시점은 기술팀이 단독으로 정하지 않습니다.** 대상자에게 조사 사실이 드러나는 순간이 곧 차단 시점이 되므로, **인사·법무와 시점을 합의**하십시오. 통상은 인사 면담과 동시에 권한이 끊깁니다.

| # | 조치 | 명령 | ⚠️ 부작용 | 권한 |
|---|---|---|---|---|
| G1 | 진행 중 반출 즉시 정지 | PB-02 4절 D9 + 버킷 정책으로 해당 주체 Deny | 대상자가 즉시 알아챔 | [IC + 인사 합의] |
| G2 | 권한 축소(전면 차단 아님) | 민감 데이터 접근 권한만 제거 | 업무 일부 중단 | [IC + 인사 합의] |
| G3 | 콘솔·CLI 전면 차단 | PB-01 4절 경로 A의 A1·A3·A4 | 업무 전면 중단. **면담과 동시에** | [인사 결정] |
| G4 | Identity Center 할당 제거 + 세션 폐기 | `sso-admin delete-account-assignment` + `aws:TokenIssueTime` Deny | 같음 | [인사 결정] |
| G5 | 대상자가 관리자급이면 로그 보호 강화 | 로그 계정 접근 권한 즉시 회수, 조직 트레일 확인 | — | [IC 단독 — 즉시] |
| G6 | 공유된 스냅샷·AMI 공유 회수 | `modify-snapshot-attribute --operation-type remove --user-ids` | 정상 공유였다면 파트너 영향 | [IC 단독] |

### 5. 증거 보전

**이 시나리오의 증거는 인사·법적 절차에서 쓰일 가능성이 가장 높습니다.** 따라서 34.2의 관리 연속성이 가장 엄격하게 요구됩니다. **누가 언제 무엇을 조회했는지까지 기록하십시오** — 조사자의 행위도 증거의 일부입니다.

| 순위 | 무엇을 | 왜 | 방법 |
|---|---|---|---|
| 1 | **대상 주체의 IAM 현재 상태** | 4절에서 우리가 바꾼다 | `get-account-authorization-details` + 개별 조회 |
| 2 | **CloudTrail 전 기간 활동** | 보존 기간 만료. 조사 기간이 길다 | 증거 버킷 복사 + 법적 보존 |
| 3 | **S3 데이터 이벤트·서버 액세스 로그** | 반출 규모의 유일한 근거 | 같음 |
| 4 | **Athena 질의 결과 자체** | 재현 가능성과 함께 산출물로 보존 | 결과 CSV + 질의문 + 실행 시각 |
| 5 | 대상자 사용 인스턴스·워크스테이션 | 인사·법무 판단에 따라 | 스냅샷. **법무 승인 후** |
| 6 | 조사자 행위 기록 | 조사의 무결성 | 증거 계정의 데이터 이벤트(34.2) |

### 6. 근절 (Eradication)

**이 시나리오의 근절은 "사람"이 아니라 "그 사람이 그것을 할 수 있었던 구조"를 대상으로 합니다.**

| # | 확인·조치 | 방법 |
|---|---|---|
| 1 | 대상자의 모든 접근 경로 회수 | 9.6 오프보딩 체크리스트 전체 |
| 2 | 대상자가 만든 자격 증명·역할·공유 | PB-01 6절 표 10개 항목을 대상자 기준으로 |
| 3 | 대상자가 알고 있던 공유 자격 증명 | 팀 공용 키·계정·API 토큰 전부 순환(11.5) |
| 4 | 대상자가 접근할 수 있던 서드파티 | SaaS·저장소·CI의 계정 회수. **AWS 밖이라 가장 자주 누락** |
| 5 | **권한이 과도했던 이유** | 역할 설계 재검토. 직무와 권한의 불일치 |
| 6 | 데이터 반출이 왜 탐지되지 않았는가 | 30.3 #15 알람의 임계값·주체 제외 설정 재검토 |
| 7 | 반출된 데이터의 후속 처리 | 법무 — 계약·영업비밀·개인정보 각각 다른 조치 |

**9.6 오프보딩 체크리스트** — 내부자 사건의 절반은 **오프보딩 누락**에서 시작합니다.

- [ ] IAM 사용자 비활성화(삭제는 조사 종료 후), 액세스 키 전부 비활성화
- [ ] Identity Center 사용자 비활성화 + 모든 계정 할당 제거 + **기존 세션 폐기**
- [ ] 그룹·권한 집합에서 제거
- [ ] 대상자가 소유자인 역할의 신뢰 정책 확인
- [ ] SSH 키 페어·인증서 폐기(22.2)
- [ ] 공유 시크릿 순환 — 대상자가 열람할 수 있었던 모든 것(11.5)
- [ ] 서드파티 SaaS·저장소·CI 계정 회수
- [ ] 개인 계정으로 공유된 스냅샷·AMI·버킷 정책 회수
- [ ] 대상자 이름이 들어간 알람 구독·온콜 로테이션 정리
- [ ] **회수 완료를 인사와 상호 확인하고 기록**

### 7. 복구 (Recovery)

**재구축 대상이 있는 시나리오가 아닙니다.** 복구의 대상은 시스템이 아니라 **통제 구조와 조직의 신뢰**입니다.

| 영역 | 복구 내용 |
|---|---|
| 접근 통제 | 6절 5번의 역할 재설계 반영. 직무별 최소 권한으로(1.1, 7.6) |
| 데이터 | 삭제·변조가 있었다면 PB-04 7절의 복구 지점 선택 규칙 적용 |
| 서드파티 | 회수 완료를 각 서비스에서 확인 |
| 시크릿 | 순환 완료 확인, 애플리케이션 정상 동작 검증 |
| 조직 | **오탐이었다면 대상자의 명예 회복이 복구의 일부**입니다 |
| 절차 | 조사 절차 자체의 문제점을 인사·법무와 함께 정리 |

> ⚠️ **조사가 오탐으로 끝난 경우의 처리를 미리 정해 두십시오.** 조사 사실이 일부에게 알려진 상태에서 흐지부지 끝나면 조직에 오래 남는 상처가 됩니다. 인사가 주관해 **공식적으로 종결**하고, 조사 기록의 보관·파기 규칙도 사전에 정합니다(12.6).

#### 🔴 완료 판정 기준

- [ ] 9.6 오프보딩 체크리스트가 전부 완료되었고 **인사와 상호 확인**되었다
- [ ] 대상자의 자격 증명으로 어떤 접근도 불가능함을 실제로 확인했다
- [ ] 대상자가 만든 자격 증명·공유·역할이 전부 정리되었다
- [ ] 공유 시크릿·서드파티 계정 순환이 완료되었고 서비스가 정상이다
- [ ] 반출 범위가 **문서로 확정**되어 법무에 전달되었다
- [ ] 관리 연속성 문서(C.3)가 모든 증거에 대해 완성되었다
- [ ] 조사 종결이 인사·법무 절차상으로도 종결 처리되었다

### 9. 사후 (Post-Incident)

**이 플레이북의 회고는 34.6의 비난 없는 원칙을 지키기가 가장 어렵습니다.** 실제로 한 사람의 고의가 있었기 때문입니다. **그래도 회고의 대상은 사람이 아니라 구조입니다.**

| 나쁜 결론 | 좋은 결론 |
|---|---|
| "박 과장이 데이터를 빼돌렸다" | "한 사람이 3만 건을 다운로드해도 아무 알람이 울리지 않는 구조였다" |

| "권한을 줄이겠다" | "이 직무에 왜 이 권한이 있었는지 설명할 수 있는 사람이 없었다" |

### 2. 심각도 판정

**질문 세 개.**

1. 우리가 그것을 **쓰는가**? (SBOM 인덱스 조회 — 27.2 ④)
2. 쓴다면 **운영에 배포되어 돌고 있는가**? (배포 연결 표 — 27.2 ③)
3. 그 아티팩트가 **고객에게 전달되었는가**? (SaaS 내부 사용인지, 배포 제품인지)

| 조건 | 등급 | 에스컬레이션 |
|---|---|---|
| 오염 아티팩트가 **고객에게 배포됨** | **SEV1** | 전원 + 경영진 + 법무 + 커뮤니케이션 |
| 오염 아티팩트가 **운영에서 실행 중**, 실행 흔적(C2·채굴·반출) 확인 | **SEV1** | 전원 + 경영진. **PB-01·PB-03 병행** |
| 오염 아티팩트가 운영에서 실행 중, 실행 흔적은 미확인 | **SEV1** | 전원. 흔적 부재 ≠ 무해 |
| **배포 자격 증명이 탈취됨** | **SEV1** | 전원 + 경영진. **PB-01 즉시 병행** |
| 빌드했지만 운영 배포 전(레지스트리에만 존재) | **SEV2** | IC + 기술 분석 + 개발 리드 |
| 개발·테스트 환경에만 존재 | **SEV2** | IC + 기술 분석 |
| 조회 결과 우리는 해당 구성 요소를 쓰지 않음 | **SEV3** 종결 | **근거를 문서로 남긴다** — 다음 공지 때 재사용 |
| SBOM이 없어 영향 범위를 알 수 없음 | **SEV2** 유지 + 조사 지속 | ⚠️ 이 상태 자체가 액션 아이템 |

> 🔴 **"쓰지 않는다"는 결론도 근거가 필요합니다.** 27.2의 인덱스 조회 결과를 스크린샷이나 질의 결과 파일로 남기십시오. 다음번 같은 공지가 왔을 때 **같은 조사를 반복하지 않게** 됩니다. 그리고 감사에서 요구받습니다(38.5).

### 5. 증거 보전

**이 시나리오의 증거는 아티팩트 그 자체와 빌드 기록입니다.** 그리고 **다이제스트가 신원**입니다 — 태그는 움직이므로 증거가 되지 못합니다(24.2).

| 순위 | 무엇을 | 왜 | 방법 |
|---|---|---|---|
| 1 | **오염 아티팩트의 다이제스트와 매니페스트** | 태그가 움직이면 대응이 끊긴다 | `ecr batch-get-image`로 매니페스트 확보 |
| 2 | **이미지 레이어 원본** | 근절 과정에서 지워질 수 있다 | 증거 프리픽스로 복사, 삭제 금지 태그 |
| 3 | **빌드 로그와 빌드 정의** | CodeBuild 로그 보존 기간 만료 | `batch-get-builds` + CloudWatch Logs 내보내기 |
| 4 | **SBOM 원본** | 영향 범위 산정의 근거 | `shopmini-sbom-archive`에서 증거 버킷으로 |
| 5 | **CloudTrail 사고 기간 로그** | 누가 밀어 넣었는가 | 증거 버킷 복사 + 법적 보존 |
| 6 | 실행 중이던 인스턴스·태스크 | 오염 코드가 무엇을 했는가 | PB-03 5절 |

### 6. 근절 (Eradication)

**침해된 계층을 먼저 특정하십시오.** 27.1의 네 유형 중 어디인가에 따라 근절 대상이 완전히 다릅니다.

| 유형 | 근절 대상 | 조치 |
|---|---|---|
| **① 의존성 오염** | 의존성 자체 | 안전한 버전으로 고정, 락파일 재생성, **프라이빗 레지스트리 캐시에서도 제거**(27.3) |
| ① 의존성 혼동 | 이름 해석 경로 | 내부 스코프 고정, 업스트림 프록시 우선순위 수정(27.3) |
| **② 빌드 시스템 침해** | 빌드 러너·플러그인 | 러너 재생성(27.4 ①), 서드파티 액션 **SHA 고정**(27.4 ④), 빌드 캐시 폐기(27.4 ⑤) |
| **③ 아티팩트 변조** | 레지스트리 | 오염 이미지 격리, 태그 불변성, 리포지토리 정책, **서명 검증 강제**(27.5) |
| **④ 배포 자격 증명 탈취** | 자격 증명 | **PB-01 6절 전체**. OIDC 신뢰 조건 고정(27.6) |

**공통 근절 체크리스트**

- [ ] 오염된 아티팩트 다이제스트 목록이 확정되었고, 전부 차단 목록에 올라갔다
- [ ] 그 아티팩트를 만든 **빌드 번호 범위**가 특정되었다 — 언제부터 언제까지
- [ ] 같은 빌드 러너에서 나온 **다른 아티팩트도** 전부 재검토 대상에 포함되었다
- [ ] 빌드 캐시가 폐기되었다(오염이 캐시에 남으면 깨끗한 빌드가 다시 오염됨, 27.4 ⑤)
- [ ] 프라이빗 레지스트리·풀 스루 캐시에서 오염 패키지·베이스 이미지가 제거되었다
- [ ] 서드파티 액션·플러그인이 **태그가 아니라 SHA로** 고정되었다(27.4 ④)
- [ ] 빌드에 주입되던 시크릿이 전부 순환되었다(27.4 ③, 11.5)
- [ ] 빌드·배포 역할의 권한이 재검토되었다 — 빌드 역할에 **배포 권한이 없는지**(27.6)
- [ ] OIDC 신뢰 정책에 와일드카드가 없고 저장소·환경이 고정되었다
- [ ] 오염 아티팩트가 **실행되었던 호스트**가 전부 식별되었고 PB-03 6절이 적용되었다

> 🔴 **"같은 빌드 러너에서 나온 다른 아티팩트"를 빠뜨리지 마십시오.** 빌드 시스템이 침해되었다면 오염은 한 패키지에만 머물지 않습니다. **의심되는 기간의 모든 빌드 산출물을 재빌드**하는 것이 정석이고, 그것이 불가능하면 무엇을 검증 없이 남겼는지 문서로 남기십시오.

**오염 코드가 무엇을 했는지 조사하십시오.** 공급망 침해의 목적은 대개 **자격 증명 탈취**입니다.

```sql
-- 오염 기간 동안 빌드·런타임 역할이 접근한 시크릿
SELECT eventtime, useridentity.arn AS actor, eventname,
       json_extract_scalar(requestparameters, '$.secretId') AS secret,
       sourceipaddress
FROM org_cloudtrail
WHERE dt BETWEEN '2026/08/01' AND '2026/09/06'
  AND eventsource = 'secretsmanager.amazonaws.com'
  AND eventname IN ('GetSecretValue', 'DescribeSecret', 'ListSecrets')
ORDER BY eventtime;
```

### 7. 복구 (Recovery)

**34.5의 원칙이 그대로 적용됩니다 — 오염된 아티팩트로 만들어진 것은 치료하지 않고 재배포합니다.** 다만 이 시나리오에는 한 단계가 더 있습니다: **깨끗한 빌드 파이프라인을 먼저 확보해야 합니다.**

| 단계 | 할 일 | 건너뛰면 |
|---|---|---|
| ① | 근본 원인 확정·제거(6절) | 재빌드가 다시 오염됨 |
| ② | **빌드 환경을 먼저 재생성** — 러너, 캐시, 베이스 이미지 | 깨끗한 재빌드가 불가능 |
| ③ | 의존성 고정 — 안전한 버전으로 락파일 재생성, **해시 고정**(27.3) | 다음 빌드에서 다시 오염 버전을 당겨옴 |
| ④ | **자격 증명 전면 순환** — 빌드에 주입되던 모든 시크릿 | 오염 코드가 이미 가져간 키가 그대로 유효 |
| ⑤ | 재빌드 → **서명**(27.5) → 새 다이제스트 확보 | 검증 없는 아티팩트 배포 |
| ⑥ | 승인 컨트롤러의 **검증을 거부 모드로** 확인 | 감사 모드는 아무것도 막지 않는다(27.5) |
| ⑦ | 오염 아티팩트를 쓰던 워크로드 전부 재배포 | 오염 컨테이너가 계속 돎 |
| ⑧ | 배포 동결 해제, 파이프라인 정상화 | — |
| ⑨ | SBOM 인덱스·배포 연결 표 갱신(27.2 ④-c) | "조치 완료"를 판정할 수 없음 |

**④ 순환 대상** — 빌드 환경에 있었던 모든 것이 유출된 것으로 간주합니다.

- [ ] 빌드 역할·배포 역할의 임시 자격 증명(세션 폐기)
- [ ] CodeArtifact·패키지 레지스트리 토큰
- [ ] 컨테이너 레지스트리 자격 증명
- [ ] 빌드에 주입되던 Secrets Manager·Parameter Store 값 전부(11.5)
- [ ] 서명 키(침해가 의심되면 **재발급 + 구 키로 서명된 아티팩트 재검증**, 27.5)
- [ ] 서드파티 API 키·웹훅(AWS 밖 — 가장 자주 누락)
- [ ] 소스 저장소 배포 키·PAT

> 🔴 **⑨를 완료 조건에 넣으십시오.** 27.2가 말한 대로, 새 다이제스트가 인덱스에 들어오고 **옛 다이제스트가 배포 연결 표에서 사라져야** 조치 완료입니다. "재배포했다"는 선언이 아니라 데이터로 확인되어야 합니다.

#### 🔴 완료 판정 기준

- [ ] 오염 다이제스트가 **어느 환경의 배포 연결 표에도 없다**
- [ ] 새 아티팩트가 재생성된 빌드 환경에서, 고정된 의존성으로 빌드되었다
- [ ] 새 아티팩트에 서명이 있고, 승인 컨트롤러가 **거부 모드**로 검증한다
- [ ] 빌드 환경에 있던 모든 시크릿이 순환되었다
- [ ] 서드파티 액션·플러그인이 SHA로 고정되었다
- [ ] 오염 아티팩트가 실행되던 호스트가 전부 재배포되었다
- [ ] 배포 동결이 해제되었고 정상 배포가 성공했다
- [ ] SBOM 인덱스와 배포 연결 표가 갱신되어 조회로 확인 가능하다
- [ ] 우리가 배포자였다면 다운스트림 통지와 안전 버전 배포가 완료되었다

### 8. 통지

**우리가 소비자인지 배포자인지에 따라 통지의 무게가 완전히 다릅니다.**

| 대상 | 언제 | 무엇을 | 누가 |
|---|---|---|---|
| 내부 경영진 | 선언 즉시 | 영향 범위(운영 가동 여부), 배포 동결 사실 | IC |
| 개발팀 전체 | 배포 동결과 동시에 | **동결 사실과 긴급 배포 경로.** 원인은 최소한으로 | IC |
| 내부 법무 | 데이터 접근·유출 가능성이 보이면 | 데이터 유형과 잠정 범위 | IC |
| **다운스트림 고객·사용자** | **우리가 배포자라면 확인 즉시** | 영향 버전, 조치 방법, 안전 버전 | 커뮤니케이션 + 법무 |

| 규제 기관 | 개인정보 유출이 확인된 경우, 관할 법령 기한 내 | 법령이 정한 서식 | 법무 |
| 계약 상대방 | 계약의 보안 사고 통지 조항대로 | 계약이 정한 범위 | 법무 |
| AWS | 배포 자격 증명 침해가 확인되면 | 지원 케이스 | 기술 분석 |
| 사이버보험사 | 약관상 기한 | 약관 서식 | 재무 / 법무 |

> 🔴 **우리가 배포자인 경우, 통지 속도가 곧 피해 규모를 결정합니다.** 우리 아티팩트를 쓰는 조직들은 우리가 알려 주기 전까지 자기가 영향받는지 모릅니다. 27.2가 SBOM을 "곧 계약서에 들어올 산출물"이라 한 이유가 이것입니다 — **고객이 우리에게 SBOM을 요구하는 날은 이 통지를 받는 날입니다.**

> ⚠️ 법정 통지 기한은 이 책에서 확정하지 않습니다. **최신 법령 원문과 법무 검토로 확인**하십시오(4.3, 33.6).

### 9. 사후 (Post-Incident)

**이 플레이북의 핵심 지표는 하나입니다 — "우리가 그것을 쓰는가"에 답하는 데 걸린 시간.** 27.2의 Log4Shell 시계가 그것입니다.

**타임라인에서 확정할 시각**

| 시각 | 근거 |
|---|---|
| 상위 공급자가 침해된 시점(공지 기준) | 외부 공지 |
| 오염 아티팩트가 **우리 빌드에 들어온** 시점 | 빌드 기록, 락파일 이력 |
| 오염 아티팩트가 **운영에 배포된** 시점 | 배포 연결 표, 파이프라인 기록 |

| 공지를 인지한 시점 | 접수 기록 |
| **영향 범위 산정이 끝난 시점** | 3절 ①의 완료 시각 |
| 배포 동결 | `disable-stage-transition` |
| 안전 버전 배포 완료 | 배포 기록 |

**"인지 → 영향 범위 산정 완료" 구간을 별도 지표로 기록하십시오.** 이것이 다음 공급망 사건에서의 대응 속도를 예측합니다. 목표는 **분 단위**입니다(27.2).

### 10. 이 시나리오의 흔한 실수 ⚠️

| 실수 | 결과 | 올바른 구성 |
|---|---|---|
| SBOM이 없어 영향 범위 산정에 몇 주 | 그 사이 환경이 바뀌어 목록이 이미 낡음 | 빌드 시점 SBOM + 인덱스 + 배포 연결 표(27.2) |
| "빌드했다"만 보고 "운영에서 돈다"를 안 봄 | 우선순위를 잘못 잡아 엉뚱한 것부터 고침 | 배포 연결 표와 조인(3절 ①-b) |
| 배포를 동결하지 않고 조사 | 조사보다 빠르게 오염 범위가 자람 | 3절 ⓪ — 조사보다 동결이 먼저 |
| 오염 이미지를 즉시 삭제 | 레이어가 증거인데 사라짐 | 정책으로 차단, 보존은 유지 |
| 태그로 아티팩트를 추적 | 태그가 움직여 대응 대상이 어긋남 | **다이제스트가 신원**(24.2) |
| 오염 패키지만 교체하고 재빌드 | 빌드 캐시에 오염이 남아 다시 들어옴 | 캐시 폐기 + 러너 재생성(27.4 ⑤) |
| 같은 러너의 다른 아티팩트를 안 봄 | 오염이 한 패키지에만 머물지 않음 | 기간 내 전체 산출물 재검토 |
| 빌드 시크릿을 순환하지 않음 | 오염 코드가 가져간 키가 그대로 유효 | 7절 ④ 전면 순환 |
| 서명을 도입했지만 감사 모드로 운영 | 검증이 아무것도 막지 않음 | **거부 모드로 전환**(27.5) |
| OIDC 신뢰에 와일드카드를 남김 | 다른 저장소·브랜치에서 배포 역할 탈취 | 저장소·환경까지 고정(27.6) |
| 빌드 역할에 배포 권한이 붙어 있음 | 빌드 침해 = 운영 배포 장악 | 역할 분리(27.6) |
| 다운스트림 통지를 미룸 | 고객이 영향받는지도 모른 채 계속 사용 | 배포자라면 **확인 즉시** 통지 |
| "쓰지 않는다"는 결론을 구두로만 | 다음 공지 때 같은 조사를 반복 | 조회 결과를 근거 파일로 보존 |
| 조치 완료를 "재배포했다"로 판정 | 옛 다이제스트가 어딘가에서 계속 돎 | 배포 연결 표에서 사라진 것을 데이터로 확인 |

## C.3 관리 연속성(Chain of Custody) 양식

34.2 5단계의 양식입니다. **증거 하나마다 한 장**을 만들고, **모든 행위를 그 자리에서** 채웁니다. 나중에 기억으로 채운 기록은 기록이 아닙니다.

### C.3.5 📋 관리 연속성 완결성 점검

- [ ] 사건의 모든 증거가 `EV-NNN`으로 등록되어 있고 누락이 없다
- [ ] 각 증거의 **수집 명령 전문**이 기록되어 있다
- [ ] 각 증거에 검증값과 그 산출 방법이 기록되어 있다
- [ ] 증거가 **포렌식 계정 소유**로 복사되었다(공유만 받은 상태가 아니다)
- [ ] 모든 증거에 객체 잠금·법적 보존 또는 `LegalHold` 태그와 SCP 보호가 걸려 있다
- [ ] 이관 기록에 **끊긴 구간이 없다** — 수집부터 현재 보관자까지 연속적이다
- [ ] 증거 계정의 조사자 행위가 **데이터 이벤트까지** 기록된다
- [ ] 모든 시각이 UTC로 통일되어 있다
- [ ] 원본을 변경한 행위가 있었다면 사유와 함께 기록되어 있다

### 📋 플레이북 자체 점검 — 여섯 개 모두에 대해

- [ ] 0절의 「본문 참조」 절 번호가 현재 목차와 일치한다
- [ ] 1절의 GuardDuty 발견 유형·Config 규칙명이 **현재 실재하는** 이름이다
- [ ] 2절의 판정표가 우리 조직의 데이터 분류 체계(4.2, 12.2)와 연결된다
- [ ] 3절의 모든 명령이 **복사해서 그대로 실행 가능**하다(빈칸 없음)
- [ ] 4절의 모든 조치에 부작용과 승인 권한이 병기되어 있다
- [ ] 5절이 34.2의 5단계와 어긋나지 않는다
- [ ] 8절의 통지 대상에 **보험사와 계약 상대방**이 들어 있다
- [ ] 8절의 법정 기한이 단정이 아니라 **법무 확인 항목**으로 표시되어 있다
- [ ] 9절의 액션 아이템 양식에 소유자·기한·**검증 방법** 칸이 있다
- [ ] 10절의 실수 목록이 지난 훈련·사고에서 실제로 나온 것으로 갱신되었다
