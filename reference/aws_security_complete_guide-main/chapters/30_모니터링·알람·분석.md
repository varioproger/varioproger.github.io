# 30장. 모니터링·알람·분석

> **이 장에서 다루는 것**
> - **SNS 알림 채널** 🧪 — 주제 생성·구독, 🔴 발행 주체를 제한하는 주제 정책, KMS 암호화 시 반드시 걸리는 함정
> - **지표 필터 → 알람 → SNS 파이프라인** 🧪 — CloudTrail 로그에서 지표를 뽑는 방법, 복합 알람, 이상 탐지 알람, "로그가 끊겼다" 알람

> - **CloudWatch 대시보드와 EventBridge** 🧪 — JSON으로 보안 운영 대시보드 만들기, 이벤트 패턴 문법, 크로스 계정 이벤트 버스

> - **파싱·상관 분석·SIEM·위협 헌팅** — 알람을 기다리지 않고 찾아 나서는 절차
> - **알람 피로** ⚠️ — 아무도 안 보는 알람은 없는 것과 같다
>
> **선행 지식**: 5장(루트 알람), 7장(정책 평가), 15장(S3), 19장(트래픽 통제), 29장(로깅 아키텍처)

29장에서 로그를 모았습니다. 조직 트레일이 켜져 있고, 로그는 운영 계정 관리자가 손댈 수 없는 로그 아카이브 계정의 S3 버킷에 쌓이고, 무결성 검증이 붙어 있고, 보존 기간이 정해져 있습니다.

**그런데 지금 이 상태에서는 아무 일도 일어나지 않습니다.** 누군가 루트로 로그인해도, CloudTrail을 끄더라도, 30분 동안 버킷 하나를 통째로 내려받아도, 그 사실은 S3 객체 하나로 기록될 뿐입니다. 아무도 읽지 않으면 로그는 사고 이후에 "그때 이런 일이 있었군요"를 확인해 주는 용도밖에 되지 않습니다.

## 30.1 SNS 주제로 알림 보내기 🧪

알람이 실제로 사람에게 도달하려면 채널이 필요합니다. AWS에서 그 채널의 표준 진입점은 SNS(Simple Notification Service) 주제입니다.

> 📖 *AWS Security Cookbook* 8장 「Creating an SNS topic to send emails」에서는 SNS를 "여러 엔드포인트와 함께 쓸 수 있는 관리형 발행/구독 메시징 서비스"로 소개하며, 지원 프로토콜로 **HTTP, HTTPS, Email, Email-JSON, Amazon SQS, AWS Lambda, 플랫폼 애플리케이션 엔드포인트, SMS**를 열거합니다. 또한 스팸 방지를 위해 **이메일 주소 소유를 수동으로 확인해야** 구독이 `Confirmed` 상태가 된다는 점을 강조합니다.

Cookbook은 콘솔 절차를 설명하지만, 보안 알림 채널은 여러 계정·여러 리전에 반복 생성해야 하므로 CLI/IaC로 다루는 편이 낫습니다.

### 주제 생성과 구독

```bash
PROFILE=awssec-lab
REGION=ap-northeast-2

TOPIC_ARN=$(aws sns create-topic \
  --name shopmini-secops-critical \
  --attributes DisplayName="ShopMini SecOps" \
  --tags Key=Project,Value=awssec-lab Key=Chapter,Value=ch30 \
  --region $REGION --profile $PROFILE \
  --query TopicArn --output text)

aws sns subscribe \
  --topic-arn "$TOPIC_ARN" \
  --protocol email \
  --notification-endpoint secops@example.com \
  --region $REGION --profile $PROFILE

# 확인 메일 클릭 전까지 PendingConfirmation 상태로 남습니다
aws sns list-subscriptions-by-topic \
  --topic-arn "$TOPIC_ARN" \
  --region $REGION --profile $PROFILE \
  --query 'Subscriptions[].[Protocol,Endpoint,SubscriptionArn]' --output table
```

`SubscriptionArn` 이 `PendingConfirmation` 인 구독은 **메시지를 받지 못합니다.** 알람을 만들어 놓고 "테스트했는데 메일이 안 온다"는 상황의 절대다수가 이것입니다.

### 🔴 주제 정책으로 발행 주체를 제한하라

SNS 주제를 만들면 기본 정책은 **같은 계정의 모든 주체**에게 발행을 허용합니다. 보안 알림 주제에 개발 계정 Lambda가 아무 메시지나 밀어 넣을 수 있다면, 공격자는 알람을 지우지 않고도 **가짜 알림으로 채널을 덮어** 진짜 알람을 묻어 버릴 수 있습니다.

발행 주체를 서비스 주체 수준까지 좁힙니다.

```json
{
  "Version": "2012-10-17",
  "Id": "shopmini-secops-topic-policy",
  "Statement": [
    {
      "Sid": "AllowCloudWatchAndEventBridgePublish",
      "Effect": "Allow",
      "Principal": {
        "Service": ["cloudwatch.amazonaws.com", "events.amazonaws.com"]
      },
      "Action": "sns:Publish",
      "Resource": "arn:aws:sns:ap-northeast-2:444455556666:shopmini-secops-critical",
      "Condition": {
        "StringEquals": { "aws:SourceAccount": "444455556666" }
      }
    },
    {
      "Sid": "AllowSecurityAdminManage",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::444455556666:role/SecurityAdmin"
      },
      "Action": ["sns:Publish", "sns:Subscribe", "sns:SetTopicAttributes"],
      "Resource": "arn:aws:sns:ap-northeast-2:444455556666:shopmini-secops-critical"
    },
    {
      "Sid": "DenyInsecureTransport",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "sns:*",
      "Resource": "arn:aws:sns:ap-northeast-2:444455556666:shopmini-secops-critical",
      "Condition": { "Bool": { "aws:SecureTransport": "false" } }
    }
  ]
}
```

```bash
aws sns set-topic-attributes \
  --topic-arn "$TOPIC_ARN" \
  --attribute-name Policy \
  --attribute-value file://sns-topic-policy.json \
  --region $REGION --profile $PROFILE
```

`aws:SourceAccount` 조건이 핵심입니다. 이 조건이 없으면 **다른 AWS 계정의 CloudWatch 알람도** 이 주제로 발행할 수 있습니다(서비스 주체는 계정 경계를 가지지 않습니다). 크로스 계정 알람을 실제로 받아야 한다면 `aws:SourceAccount` 를 목록으로 열거하거나 `aws:SourceArn` 으로 특정 알람만 허용하십시오.

### 🔴 KMS 암호화와 그 함정

SNS 주제 본문에는 계정 ID, 리소스 ARN, 사용자 이름, 소스 IP 같은 정보가 그대로 들어갑니다. 저장 시 암호화를 켜십시오.

```bash
aws sns set-topic-attributes \
  --topic-arn "$TOPIC_ARN" \
  --attribute-name KmsMasterKeyId \
  --attribute-value alias/shopmini/secops \
  --region $REGION --profile $PROFILE
```

> ⚠️ **AWS 관리형 키(`alias/aws/sns`)를 쓰면 알람이 조용히 실패합니다.**
> CloudWatch 알람이나 EventBridge가 암호화된 주제로 발행하려면 **KMS 키 정책에서 해당 서비스 주체에게 `kms:GenerateDataKey*` 와 `kms:Decrypt` 를 허용**해야 합니다. AWS 관리형 키는 키 정책을 수정할 수 없으므로 이 허용을 추가할 방법이 없습니다. 결과는 예외도, 알람 상태 변화 실패도 아닌 **메시지 누락**입니다. 반드시 고객 관리형 키를 쓰고 아래 문장을 키 정책에 넣으십시오.

```json
{
  "Sid": "AllowServicesToPublishEncrypted",
  "Effect": "Allow",
  "Principal": {
    "Service": ["cloudwatch.amazonaws.com", "events.amazonaws.com"]
  },
  "Action": ["kms:GenerateDataKey*", "kms:Decrypt"],
  "Resource": "*",
  "Condition": {
    "StringEquals": { "aws:SourceAccount": "444455556666" }
  }
}
```

### 채널 설계

이메일 하나로 모든 알람을 받는 구성은 30.9에서 다룰 알람 피로의 출발점입니다. 처음부터 심각도별로 주제를 나누십시오.

| 주제 | 대상 | 구독 엔드포인트 |
|---|---|---|
| `shopmini-secops-critical` | 즉시 사람이 봐야 하는 것 (루트 사용, 트레일 중지) | 온콜 호출 시스템(HTTPS), 보안팀 메일 |
| `shopmini-secops-high` | 근무 시간 내 확인 (IAM/SG 변경) | 채팅 연동 Lambda, 메일 |
| `shopmini-secops-audit` | 집계·리포트용 | SQS → 분석 파이프라인 |

## 30.2 CloudWatch 지표와 알람 🧪

> 📖 *AWS Security Cookbook* 8장은 CloudWatch를 **CloudWatch(알람·지표·대시보드), CloudWatch Logs(로그 그룹·스트림), CloudWatch Events(알림과 Lambda 자동 교정)** 세 컴포넌트로 나누어 설명하고, 알람 상태를 **`INSUFFICIENT DATA`, `OK`, `ALARM`** 셋으로 정의합니다. 또 알람 생성 시 **평가 기간, 평가할 기간의 수, 임계치를 넘어야 하는 데이터 포인트 수**를 지정한다고 설명합니다.

CPU 사용률 같은 기본 지표는 그대로 알람에 걸 수 있습니다. 그러나 **보안 이벤트에 대한 지표는 기본 제공되지 않습니다.** "IAM 정책이 변경된 횟수"라는 지표는 AWS가 만들어 주지 않습니다. 그래서 보안 알람은 거의 항상 다음 파이프라인을 거칩니다.

```
CloudTrail → (29.6) CloudWatch Logs 로그 그룹 → 지표 필터 → 사용자 지정 지표 → 알람 → SNS
```

> 📖 *AWS Security Cookbook* 8장 「Integrating CloudWatch and CloudTrail」은 트레일을 CloudWatch Logs에 연결하면 "CloudTrail 로그를 기반으로 CloudWatch 안에서 지표 필터와 알람을 만들 수 있다"고 설명하며, CloudTrail에 부여되는 권한이 **`CreateLogStream`** 과 **`PutLogEvents`** 두 개임을 밝힙니다. 같은 레시피는 AWS가 제공하는 CloudFormation 템플릿으로 보안·네트워크 API 활동 알람 묶음을 한 번에 만드는 방법도 안내합니다. 30.3의 15가지 알람은 이 묶음을 실전 기준으로 재구성한 것입니다.

### 지표 필터 만들기

```bash
LOG_GROUP="/aws/cloudtrail/shopmini-org-trail"
NS="ShopMini/Security"

aws logs put-metric-filter \
  --log-group-name "$LOG_GROUP" \
  --filter-name IAMPolicyChanges \
  --filter-pattern '{ ($.eventName = PutRolePolicy) || ($.eventName = AttachRolePolicy) || ($.eventName = CreatePolicyVersion) }' \
  --metric-transformations \
      metricName=IAMPolicyChangeCount,metricNamespace=$NS,metricValue=1,defaultValue=0 \
  --region $REGION --profile $PROFILE
```

`defaultValue=0` 이 중요합니다. 이것이 없으면 이벤트가 없는 기간에는 **데이터 포인트 자체가 생기지 않아** 알람이 `INSUFFICIENT_DATA` 를 오갑니다.

### 알람 만들기

```bash
aws cloudwatch put-metric-alarm \
  --alarm-name shopmini-iam-policy-changes \
  --alarm-description "IAM policy modified" \
  --namespace "$NS" \
  --metric-name IAMPolicyChangeCount \
  --statistic Sum \
  --period 300 \
  --evaluation-periods 1 \
  --threshold 1 \
  --comparison-operator GreaterThanOrEqualToThreshold \
  --treat-missing-data notBreaching \
  --alarm-actions "$TOPIC_ARN" \
  --region $REGION --profile $PROFILE
```

⚠️ `--ok-actions` 를 같은 주제에 붙이지 마십시오. 알람이 해제될 때마다 "정상 복귀" 메일이 한 통 더 갑니다. 보안 알람은 발생 사실이 중요하지 해제 사실은 대개 중요하지 않으며, 이런 메일이 30.9의 알람 피로를 두 배로 만듭니다.

`--treat-missing-data` 의 네 가지 값(`breaching`, `notBreaching`, `ignore`, `missing`)은 보안 알람에서 의미가 갈립니다. **"일이 일어나면 알린다"** 형태의 알람은 `notBreaching` 이 맞습니다. 반대로 **"일이 계속 일어나야 정상"** 인 알람 — 다음에 볼 로그 유입 알람 — 은 `breaching` 이어야 합니다.

### 🔴 로그가 끊긴 것도 보안 사건이다

> 📖 *Practical Cloud Security* 2판 7장: **"로그가 흐르지 않게 되었을 때도 알람이 필요하다는 것을 잊지 마라. 그것도 보안 문제다. 많은 경우 뭔가가 오작동한다는 뜻일 뿐이고, 그것은 앞으로의 문제를 못 보게 만들 수 있다. 그러나 어떤 경우에는 실제로 진행 중인 공격의 지표일 수도 있다."**

CloudWatch Logs는 로그 그룹별로 `AWS/Logs` 네임스페이스의 `IncomingLogEvents` 지표를 제공합니다. 이것이 0이 되면 파이프라인이 죽은 것입니다.

```bash
aws cloudwatch put-metric-alarm \
  --alarm-name shopmini-trail-log-flow-stopped \
  --namespace AWS/Logs \
  --metric-name IncomingLogEvents \
  --dimensions Name=LogGroupName,Value="$LOG_GROUP" \
  --statistic Sum \
  --period 3600 \
  --evaluation-periods 2 \
  --threshold 1 \
  --comparison-operator LessThanThreshold \
  --treat-missing-data breaching \
  --alarm-actions "$TOPIC_ARN" \
  --region $REGION --profile $PROFILE
```

### 복합 알람 — 오탐을 줄이는 도구

단일 조건 알람은 오탐이 많습니다. 복합 알람은 여러 알람의 상태를 불리언 식으로 조합합니다.

```bash
aws cloudwatch put-composite-alarm \
  --alarm-name shopmini-credential-compromise-suspected \
  --alarm-rule "ALARM(shopmini-console-login-failures) AND ALARM(shopmini-unauthorized-api-calls)" \
  --alarm-actions "$TOPIC_ARN" \
  --region $REGION --profile $PROFILE
```

로그인 실패가 몰리는 것만으로는 흔한 일이지만, **로그인 실패 급증과 권한 거부 급증이 같은 창에서 함께 일어나면** 자격 증명 추측 후 탐색이 진행 중이라는 신호에 훨씬 가깝습니다. `ALARM()`, `OK()`, `INSUFFICIENT_DATA()` 함수와 `AND`/`OR`/`NOT` 을 조합할 수 있고, 배포·점검 창에서는 억제 알람(actions suppressor)을 지정해 조치만 잠시 멈출 수도 있습니다.

### 이상 탐지 알람 — 임계치를 모를 때

"S3 다운로드가 몇 건이면 비정상인가"에는 정답이 없습니다. 서비스마다, 요일마다 다릅니다. 이럴 때는 고정 임계치 대신 학습된 정상 대역을 씁니다.

```bash
aws cloudwatch put-anomaly-detector \
  --single-metric-anomaly-detector '{"Namespace":"ShopMini/Security","MetricName":"S3GetObjectCount","Stat":"Sum"}' \
  --region $REGION --profile $PROFILE

aws cloudwatch put-metric-alarm \
  --alarm-name shopmini-s3-download-anomaly \
  --comparison-operator GreaterThanUpperThreshold \
  --evaluation-periods 2 \
  --threshold-metric-id ad1 \
  --treat-missing-data notBreaching \
  --alarm-actions "$TOPIC_ARN" \
  --metrics '[
    {"Id":"m1","MetricStat":{"Metric":{"Namespace":"ShopMini/Security","MetricName":"S3GetObjectCount"},"Period":300,"Stat":"Sum"},"ReturnData":true},
    {"Id":"ad1","Expression":"ANOMALY_DETECTION_BAND(m1, 3)","ReturnData":true}
  ]' \
  --region $REGION --profile $PROFILE
```

⚠️ 이상 탐지에는 두 가지 한계가 있습니다. 첫째, 학습에 시간이 걸립니다(대략 2주치 데이터가 있어야 대역이 안정됩니다). 둘째, **공격이 학습 기간 내내 진행 중이었다면 그 공격이 정상 대역에 포함됩니다.** 이상 탐지는 고정 임계치 알람을 대체하는 것이 아니라 보완합니다.

## 30.3 🔴 반드시 설정해야 할 보안 알람 15가지

**이 절은 선택 사항이 아닙니다.** 아래 15개는 CIS AWS Foundations Benchmark의 모니터링 항목과 실제 사고 대응 경험이 겹치는 지점이고, 하나라도 빠지면 그 사고 유형에 대해 조직은 **사후에도 알 수 없습니다.**

구성 원칙 세 가지를 먼저 정합니다.

1. **모든 지표 필터는 조직 트레일이 연결된 단일 로그 그룹 위에 만든다.** 계정마다 알람을 흩어 두면 관리가 무너집니다(29.9, 30.5의 크로스 계정 참조).
2. **글로벌 이벤트(IAM, STS, 콘솔 로그인, CloudFront)는 `us-east-1` 로 배달된다.** 서울 리전에만 규칙을 만들면 루트 로그인은 절대 잡히지 않습니다(5.1에서 이미 다룬 함정).
3. **심각도별로 다른 SNS 주제를 쓴다.** 15개 전부를 온콜 호출로 보내면 3주 안에 아무도 보지 않게 됩니다.

### 알람 목록

`P1`은 즉시 호출, `P2`는 근무 시간 내 확인, `P3`은 일일 리뷰 대상입니다.

| # | 무엇을 탐지 | 핵심 이벤트 | 심각도 | 오탐 가능성 |
|---|---|---|---|---|
| 1 | **루트 계정 사용** | `userIdentity.type = Root` 인 모든 이벤트 | P1 | 매우 낮음. 사전 공지된 계정 설정 변경·지원 케이스만 정당 |
| 2 | **MFA 없는 콘솔 로그인** | `ConsoleLogin` + `MFAUsed != Yes` | P1 | 낮음. 아이덴티티 센터(SSO) 로그인은 기록 방식이 달라 필터를 IAM 사용자로 한정 |
| 3 | **콘솔 로그인 실패 반복** | `ConsoleLogin` + `Failed authentication`, 5회/5분 | P2 | 중간. 오타·만료된 저장 자격 증명이 흔함. #14와 복합 알람 권장 |
| 4 | **IAM 정책 변경** | `Put*Policy`, `Delete*Policy`, `Attach*Policy`, `Detach*Policy`, `CreatePolicyVersion` 등 16종 | P2 | **높음**. CI/CD가 IAM을 배포하면 매 배포마다 발생. 배포 역할 ARN 제외 필수 |
| 5 | **CloudTrail 구성 변경·중지** | `CreateTrail`, `UpdateTrail`, `DeleteTrail`, `StartLogging`, `StopLogging` | P1 | 매우 낮음. `StopLogging`·`DeleteTrail`은 사실상 오탐 없음 |
| 6 | **보안 그룹 변경** | `AuthorizeSecurityGroup*`, `RevokeSecurityGroup*`, `CreateSecurityGroup`, `DeleteSecurityGroup` | P2 | **높음**. IaC 배포마다 발생. `0.0.0.0/0` 포함 규칙만 별도 P1로 분리 |
| 7 | **네트워크 ACL 변경** | `CreateNetworkAcl(Entry)`, `DeleteNetworkAcl(Entry)`, `ReplaceNetworkAclEntry`, `ReplaceNetworkAclAssociation` | P2 | 낮음. NACL은 자주 바뀌지 않음 |
| 8 | **네트워크 게이트웨이 변경** | `Create/Delete/Attach/DetachInternetGateway`, `Create/DeleteCustomerGateway` | P1 | 매우 낮음. 격리 서브넷에 IGW가 붙는 것은 명백한 이상 |
| 9 | **라우팅 테이블 변경** | `CreateRoute`, `DeleteRoute`, `ReplaceRoute`, `Create/DeleteRouteTable`, `ReplaceRouteTableAssociation`, `DisassociateRouteTable` | P1 | 낮음. 트래픽 우회는 데이터 반출의 전형적 준비 단계 |
| 10 | **VPC 변경** | `CreateVpc`, `DeleteVpc`, `ModifyVpcAttribute`, `*VpcPeeringConnection` 4종 | P1 | 낮음. 피어링 **수락**(`AcceptVpcPeeringConnection`)이 특히 중요 |
| 11 | **S3 버킷 정책·ACL 변경** | `PutBucketPolicy`, `PutBucketAcl`, `DeleteBucketPolicy`, `PutBucketCors`, `PutBucketReplication`, `PutBucketLifecycle` 등 | P1 | 중간. 배포 파이프라인 제외 필요. 로그 버킷 대상은 예외 없이 P1 |
| 12 | **KMS 키 비활성화·삭제 예약** | `DisableKey`, `ScheduleKeyDeletion` | P1 | 매우 낮음. 랜섬웨어형 공격의 직접 신호 |
| 13 | **AWS Config 변경** | `StopConfigurationRecorder`, `DeleteDeliveryChannel`, `PutDeliveryChannel`, `PutConfigurationRecorder` | P1 | 매우 낮음 |
| 14 | **권한 없는 API 호출 급증** | `errorCode` 가 `AccessDenied*` 또는 `*UnauthorizedOperation`, 20회/5분 | P2 | **높음**. 정상 앱의 존재 확인 호출이 대량 발생. 임계치+주체 제외로 반드시 튜닝 |
| 15 | **대량 S3 다운로드·데이터 반출** | 데이터 이벤트 `GetObject` 이상 탐지, 또는 GuardDuty `Exfiltration:S3/AnomalousBehavior` | P1 | 중간. 배치·백업 주체 제외 필수. 고정 임계치보다 이상 탐지 권장(30.2) |

### 지표 필터 패턴 전문

`aws logs put-metric-filter --filter-pattern` 에 그대로 넣는 값입니다. 1~2번은 `us-east-1` 의 로그 그룹에 만드십시오.

```text
# 1. 루트 계정 사용
{ $.userIdentity.type = "Root" && $.userIdentity.invokedBy NOT EXISTS && $.eventType != "AwsServiceEvent" }

# 2. MFA 없는 콘솔 로그인
{ ($.eventName = "ConsoleLogin") && ($.additionalEventData.MFAUsed != "Yes") && ($.userIdentity.type = "IAMUser") && ($.responseElements.ConsoleLogin = "Success") }

# 3. 콘솔 로그인 실패
{ ($.eventName = "ConsoleLogin") && ($.errorMessage = "Failed authentication") }

# 4. IAM 정책 변경
{ ($.eventName=PutRolePolicy)||($.eventName=PutUserPolicy)||($.eventName=PutGroupPolicy)||($.eventName=DeleteRolePolicy)||($.eventName=DeleteUserPolicy)||($.eventName=DeleteGroupPolicy)||($.eventName=CreatePolicy)||($.eventName=DeletePolicy)||($.eventName=CreatePolicyVersion)||($.eventName=DeletePolicyVersion)||($.eventName=AttachRolePolicy)||($.eventName=DetachRolePolicy)||($.eventName=AttachUserPolicy)||($.eventName=DetachUserPolicy)||($.eventName=AttachGroupPolicy)||($.eventName=DetachGroupPolicy) }

# 5. CloudTrail 구성 변경·중지
{ ($.eventName = CreateTrail) || ($.eventName = UpdateTrail) || ($.eventName = DeleteTrail) || ($.eventName = StartLogging) || ($.eventName = StopLogging) }

# 6. 보안 그룹 변경
{ ($.eventName = AuthorizeSecurityGroupIngress) || ($.eventName = AuthorizeSecurityGroupEgress) || ($.eventName = RevokeSecurityGroupIngress) || ($.eventName = RevokeSecurityGroupEgress) || ($.eventName = CreateSecurityGroup) || ($.eventName = DeleteSecurityGroup) }

# 7. 네트워크 ACL 변경
{ ($.eventName = CreateNetworkAcl) || ($.eventName = CreateNetworkAclEntry) || ($.eventName = DeleteNetworkAcl) || ($.eventName = DeleteNetworkAclEntry) || ($.eventName = ReplaceNetworkAclEntry) || ($.eventName = ReplaceNetworkAclAssociation) }

# 8. 네트워크 게이트웨이 변경
{ ($.eventName = CreateInternetGateway) || ($.eventName = DeleteInternetGateway) || ($.eventName = AttachInternetGateway) || ($.eventName = DetachInternetGateway) || ($.eventName = CreateCustomerGateway) || ($.eventName = DeleteCustomerGateway) }

# 9. 라우팅 테이블 변경
{ ($.eventName = CreateRoute) || ($.eventName = DeleteRoute) || ($.eventName = ReplaceRoute) || ($.eventName = CreateRouteTable) || ($.eventName = DeleteRouteTable) || ($.eventName = ReplaceRouteTableAssociation) || ($.eventName = DisassociateRouteTable) }

# 10. VPC 변경
{ ($.eventName = CreateVpc) || ($.eventName = DeleteVpc) || ($.eventName = ModifyVpcAttribute) || ($.eventName = CreateVpcPeeringConnection) || ($.eventName = AcceptVpcPeeringConnection) || ($.eventName = DeleteVpcPeeringConnection) || ($.eventName = RejectVpcPeeringConnection) }

# 11. S3 버킷 정책·ACL 변경
{ ($.eventSource = s3.amazonaws.com) && (($.eventName = PutBucketPolicy) || ($.eventName = PutBucketAcl) || ($.eventName = DeleteBucketPolicy) || ($.eventName = PutBucketCors) || ($.eventName = DeleteBucketCors) || ($.eventName = PutBucketReplication) || ($.eventName = DeleteBucketReplication) || ($.eventName = PutBucketLifecycle) || ($.eventName = DeleteBucketLifecycle)) }

# 12. KMS 키 비활성화·삭제 예약
{ ($.eventSource = kms.amazonaws.com) && (($.eventName = DisableKey) || ($.eventName = ScheduleKeyDeletion)) }

# 13. AWS Config 변경
{ ($.eventSource = config.amazonaws.com) && (($.eventName = StopConfigurationRecorder) || ($.eventName = DeleteDeliveryChannel) || ($.eventName = PutDeliveryChannel) || ($.eventName = PutConfigurationRecorder)) }

# 14. 권한 없는 API 호출
{ ($.errorCode = "*UnauthorizedOperation") || (($.errorCode = "AccessDenied*") && ($.sourceIPAddress != "delivery.logs.amazonaws.com") && ($.eventName != "HeadBucket")) }

# 15. S3 대량 다운로드 (데이터 이벤트 로그 그룹)
{ ($.eventSource = "s3.amazonaws.com") && ($.eventName = "GetObject") }
```

### 이 표를 쓰는 법

- **1·5·8·9·10·12·13번은 튜닝 없이 그대로 켜십시오.** 오탐이 거의 없고, 발생하면 거의 항상 진짜입니다.
- **4·6·11·14·15번은 튜닝 없이 켜면 알람 피로를 만듭니다.** 배포 역할 ARN과 배치 주체를 필터에서 제외한 뒤 켜고, 제외 목록은 코드로 관리하십시오. 제외 목록이 코드 밖에 있으면 시간이 지나며 아무도 왜 제외했는지 모르게 됩니다.
- **오탐 가능성이 "높음"인 항목은 P1으로 두지 마십시오.** 30.9에서 다루겠지만 P1의 오탐률이 20%를 넘으면 그 채널 전체가 무시됩니다.

**안 했을 때의 결과.** 5번을 안 켜면 침입자가 트레일을 멈춘 뒤의 모든 활동이 기록조차 남지 않습니다. 12번을 안 켜면 키 삭제 대기 기간(최소 7일)이 지나 데이터가 영구히 복호화 불가능해진 뒤에야 알게 됩니다. 8·9번을 안 켜면 격리 서브넷에서 인터넷으로 나가는 경로가 생겨도 다음 아키텍처 리뷰까지 아무도 모릅니다.

## 30.4 CloudWatch 대시보드 구성 🧪

> 📖 *AWS Security Cookbook* 8장 「Creating a dashboard in CloudWatch」는 대시보드를 "관련 지표를 한곳에서 볼 수 있게 해 주는 것"으로 설명하며 **성능, 보안, 네트워킹, 비용 최적화** 같은 관련성 기준으로 대시보드를 나누라고 권합니다. 또 **알람은 지표 하나만 선택할 수 있지만 대시보드 위젯은 여러 서비스의 지표를 함께 담아 사용량을 상호 연관 지어 볼 수 있다**는 점을 대시보드의 고유 가치로 짚습니다.

콘솔에서 위젯을 클릭해 만들 수도 있지만, 보안 대시보드는 **계정마다 동일해야** 의미가 있으므로 JSON으로 정의해 배포하는 것이 맞습니다.

### 보안 운영 대시보드에 들어가야 할 것

| 영역 | 위젯 | 답하는 질문 |
|---|---|---|
| 알람 현황 | `alarm` 위젯 (P1 알람 전체) | "지금 울리는 것이 있는가?" |
| 인증 | ConsoleLogin 성공/실패 시계열 | "로그인 패턴이 평소와 다른가?" |
| 권한 | AccessDenied 건수, IAM 변경 건수 | "탐색 활동이 있는가?" |
| 네트워크 | SG/NACL/라우팅 변경 건수, VPC 플로우 로그 거부 상위 | "경계가 바뀌었는가?" |
| 로그 건전성 | 로그 그룹별 `IncomingLogEvents` | "우리가 여전히 보고 있는가?" |
| 탐지 서비스 | GuardDuty 결과 건수(심각도별) | "관리형 탐지가 뭘 봤는가?" (31장) |

**로그 건전성 위젯을 반드시 넣으십시오.** 다른 모든 위젯이 조용한 것과 파이프라인이 죽어서 조용한 것은 화면상 구분되지 않습니다.

### JSON으로 대시보드 만들기


## 30.5 EventBridge(CloudWatch Events)로 실시간 대응 🧪

> 📖 *AWS Security Cookbook* 8장 「Working with CloudWatch events」는 CloudWatch Events를 "다양한 AWS 리소스로부터 시스템 이벤트를 거의 실시간 스트림으로 제공하며, 이벤트 데이터에 기반해 조치를 취하는 규칙을 만들 수 있는 것"으로 설명하고, 대상 유형으로 **Lambda 함수, SNS 주제, SQS 큐, Step Functions 상태 머신, SSM Automation, SSM Run Command, ECS 태스크, Kinesis 스트림, 다른 AWS 계정의 이벤트 버스** 등을 열거합니다. 또한 이벤트 패턴 대신 **스케줄**을 선택해 cron처럼 대상을 호출할 수 있다는 점, 그리고 대상 구성 시 **CloudWatch Events가 필요한 권한을 자동으로 부여**한다는 점을 짚습니다.

> 💡 **원서 이후 변경** — CloudWatch Events는 이후 **Amazon EventBridge**로 확장·개명되었습니다. 규칙·이벤트 패턴·대상의 동작은 그대로이고, **사용자 지정 이벤트 버스, 파트너 이벤트 소스, 스키마 레지스트리, API 대상(API destination), EventBridge Pipes, EventBridge Scheduler** 가 추가되었습니다. 콘솔의 "CloudWatch Events"는 EventBridge로 통합되었습니다.

### 지표 필터 vs EventBridge — 언제 무엇을 쓰나

30.3의 알람은 두 방식 어느 쪽으로도 구현할 수 있습니다. 선택 기준이 다릅니다.

| 기준 | 지표 필터 + 알람 | EventBridge 규칙 |
|---|---|---|
| 지연 | 수 분 (CloudTrail → Logs 배달 + 평가 기간) | 거의 실시간 |
| 임계치·횟수 조건 | **가능** (5분에 20회 등) | 불가 (개별 이벤트 단위) |
| 필요 전제 | 트레일 → CloudWatch Logs 연결 (로그 수집 비용 발생) | 리전에 활성 트레일 존재 |
| 이벤트 본문 전달 | 지표 값만 전달 — 누가 했는지 알람에 없음 | 이벤트 전문 전달 |
| 자동 조치 연결 | 알람 액션 제한적 | Lambda·SSM·Step Functions 등 자유 |
| 관리형 탐지 결과 수신 | 불가 | GuardDuty·Security Hub·Macie·Config 결과 직접 수신 |

**실무 기준**: "N회 이상"이 조건이면 지표 필터, "이 일이 일어나면 즉시"가 조건이면 EventBridge. 30.3의 3·14번은 지표 필터, 나머지는 EventBridge가 자연스럽습니다.

### 이벤트 패턴 문법

패턴은 이벤트 JSON의 **부분 집합**으로 씁니다. 명시한 필드만 비교하고, 값은 배열(OR)로 씁니다.

```json
{
  "source": ["aws.kms"],
  "detail-type": ["AWS API Call via CloudTrail"],
  "detail": {
    "eventSource": ["kms.amazonaws.com"],
    "eventName": ["ScheduleKeyDeletion", "DisableKey"]
  }
}
```

단순 일치를 넘는 조건은 콘텐츠 필터를 씁니다.

```json
{
  "detail-type": ["AWS API Call via CloudTrail"],
  "detail": {
    "eventName": [{ "prefix": "Delete" }],
    "userIdentity": {
      "arn": [{ "anything-but": { "prefix": "arn:aws:sts::111122223333:assumed-role/shopmini-deploy/" } }]
    },
    "sourceIPAddress": [{ "anything-but": { "prefix": "10.20." } }],
    "errorCode": [{ "exists": false }]
  }
}
```

사용 가능한 연산자는 `prefix`, `suffix`, `anything-but`, `numeric`, `exists`, `cidr`, `equals-ignore-case`, `wildcard` 이고 `$or` 로 묶을 수 있습니다. 위 패턴은 "배포 역할이 아니고, 사내 VPC 대역 밖에서 온, 성공한 삭제 API 호출"을 잡습니다 — 이 한 줄이 30.3의 여러 항목을 대체합니다.

⚠️ `anything-but` 안에 중첩할 수 있는 것은 `prefix`·`suffix`·`equals-ignore-case`·`wildcard` 입니다. IP 대역 제외는 `cidr` 중첩이 아니라 위처럼 문자열 접두사로 쓰거나, 규칙에서는 넓게 잡고 대상 Lambda에서 걸러야 합니다.

```bash
aws events put-rule \
  --name shopmini-external-delete-calls \
  --event-pattern file://external-delete-pattern.json \
  --state ENABLED \
  --region $REGION --profile $PROFILE

aws events put-targets \
  --rule shopmini-external-delete-calls \
  --targets "Id=sns,Arn=$TOPIC_ARN" \
  --region $REGION --profile $PROFILE
```

### 입력 변환기 — 읽을 수 있는 알림 만들기

SNS로 이벤트 JSON 전문을 그대로 보내면 메일 본문이 200줄이 됩니다. 필요한 필드만 뽑아 문장으로 만드십시오.

```json
{
  "Id": "sns",
  "Arn": "arn:aws:sns:ap-northeast-2:444455556666:shopmini-secops-critical",
  "InputTransformer": {
    "InputPathsMap": {
      "who": "$.detail.userIdentity.arn",
      "what": "$.detail.eventName",
      "ip": "$.detail.sourceIPAddress",
      "when": "$.detail.eventTime",
      "acct": "$.account"
    },
    "InputTemplate": "\"[P1] <acct> 계정에서 <who> 가 <when> 에 <ip> 에서 <what> 을 호출했습니다.\""
  }
}
```

### 크로스 계정 이벤트 버스

계정마다 규칙을 만들면 관리가 무너집니다. 각 계정의 기본 버스에서 **보안 도구 계정의 버스로 이벤트를 전달**하고, 규칙과 대응 로직은 한곳에만 둡니다.

```bash
# 보안 계정(444455556666)의 버스에 조직 전체 전달 허용
aws events put-permission \
  --event-bus-name default \
  --statement-id AllowOrgAccountsToPutEvents \
  --action events:PutEvents \
  --principal "*" \
  --condition Type=StringEquals,Key=aws:PrincipalOrgID,Value=o-exampleorgid \
  --region $REGION --profile security-admin

# 운영 계정(111122223333)에서 보안 계정 버스로 전달하는 규칙
aws events put-targets \
  --rule shopmini-forward-security-events \
  --targets "Id=secbus,Arn=arn:aws:events:ap-northeast-2:444455556666:event-bus/default,RoleArn=arn:aws:iam::111122223333:role/EventBridgeCrossAccountForward" \
  --region $REGION --profile prod-admin
```

`aws:PrincipalOrgID` 조건이 없으면 **인터넷상의 임의 계정이 여러분의 보안 이벤트 버스에 이벤트를 밀어 넣을 수 있습니다.** 가짜 GuardDuty 결과를 만들어 대응 자동화를 오작동시키는 것이 가능해집니다.

### 스케줄 규칙

탐지가 아니라 **점검**에도 씁니다. "매일 09시에 만료 임박 인증서·미사용 액세스 키·퍼블릭 리소스를 조사해 보고"는 스케줄 규칙 + Lambda로 구현합니다.

```bash
aws events put-rule \
  --name shopmini-daily-posture-check \
  --schedule-expression "cron(0 0 * * ? *)" \
  --description "매일 09:00 KST(00:00 UTC) 보안 상태 점검" \
  --region $REGION --profile $PROFILE
```

> **자동 조치는 35장으로 위임합니다.** 이 절은 "이벤트를 잡아 사람에게 전달하는 것"까지만 다룹니다. EventBridge가 Lambda를 불러 퍼블릭 버킷을 자동으로 닫거나 노출된 키를 자동 비활성화하는 패턴, 그리고 그 자동화가 스스로 장애를 만드는 위험은 35장에서 다룹니다.

## 30.6 🔴 Athena로 CloudTrail 로그 질의 🧪

> 📖 *AWS Security Cookbook* 8장 「Using Athena to query CloudTrail logs in S3」는 Athena를 쓰는 이유를 구체적으로 밝힙니다: **"CloudTrail 콘솔에서는 계정 ID 기준으로 필터링할 수 없다. 여러 계정이 같은 S3 버킷으로 로그를 보내고 있어도 그렇다. 그러나 Athena를 쓰면 계정 ID 기준으로 CloudTrail의 S3 버킷 로그를 질의할 수 있다."** 또한 **Athena는 S3 데이터만 질의할 수 있고 CloudTrail을 직접 질의하지는 못한다**는 점, **서버리스이며 실행한 질의에 대해서만 과금된다**는 점을 명시합니다.

사고가 나면 콘솔의 이벤트 기록은 무력합니다. 90일 제한이 있고, 집계가 안 됩니다. **조사는 SQL로 합니다.**

### 파티션 프로젝션 테이블 만들기

Cookbook이 쓰는 콘솔 자동 생성 테이블은 파티션이 없어 질의마다 버킷 전체를 스캔합니다. 조직 트레일이면 수 TB입니다. **파티션 프로젝션**을 쓰면 파티션을 미리 등록하지 않고도 경로 패턴에서 파티션을 유추합니다.

```sql
CREATE EXTERNAL TABLE org_cloudtrail (
  eventversion STRING,
  useridentity STRUCT<
    type: STRING,
    principalid: STRING,
    arn: STRING,
    accountid: STRING,
    invokedby: STRING,
    accesskeyid: STRING,
    username: STRING,
    sessioncontext: STRUCT<
      attributes: STRUCT<mfaauthenticated: STRING, creationdate: STRING>,
      sessionissuer: STRUCT<type: STRING, principalid: STRING, arn: STRING,
                            accountid: STRING, username: STRING>>>,
  eventtime STRING,
  eventsource STRING,
  eventname STRING,
  awsregion STRING,
  sourceipaddress STRING,
  useragent STRING,
  errorcode STRING,
  errormessage STRING,
  requestparameters STRING,
  responseelements STRING,
  additionaleventdata STRING,
  requestid STRING,
  eventid STRING,
  resources ARRAY<STRUCT<arn: STRING, accountid: STRING, type: STRING>>,
  eventtype STRING,
  apiversion STRING,
  readonly STRING,
  recipientaccountid STRING,
  serviceeventdetails STRING,
  sharedeventid STRING,
  vpcendpointid STRING
)
PARTITIONED BY (account STRING, region STRING, dt STRING)
ROW FORMAT SERDE 'com.amazon.emr.hive.serde.CloudTrailSerde'
STORED AS INPUTFORMAT 'com.amazon.emr.mapred.CloudTrailInputFormat'
OUTPUTFORMAT 'org.apache.hadoop.hive.ql.io.HiveIgnoreKeyTextOutputFormat'
LOCATION 's3://shopmini-org-trail-777788889999/AWSLogs/o-exampleorgid/'
TBLPROPERTIES (
  'projection.enabled' = 'true',
  'projection.account.type' = 'enum',
  'projection.account.values' = '123456789012,111122223333,444455556666,555555555555,777788889999',
  'projection.region.type' = 'enum',
  'projection.region.values' = 'ap-northeast-2,us-east-1,ap-northeast-1',
  'projection.dt.type' = 'date',
  'projection.dt.range' = '2024/01/01,NOW',
  'projection.dt.format' = 'yyyy/MM/dd',
  'projection.dt.interval' = '1',
  'projection.dt.interval.unit' = 'DAYS',
  'storage.location.template' =
    's3://shopmini-org-trail-777788889999/AWSLogs/o-exampleorgid/${account}/CloudTrail/${region}/${dt}'
);
```

🔴 **모든 질의에 `dt` 조건을 반드시 넣으십시오.** 파티션 프로젝션을 만들어 두고도 `WHERE dt` 를 빠뜨리면 전체 스캔이 됩니다.

### 사고 조사 실전 쿼리 8개

**① 특정 액세스 키의 전체 활동** — 키 유출 의심 시 가장 먼저 던지는 질의입니다.

```sql
SELECT eventtime, recipientaccountid, awsregion, eventsource, eventname,
       sourceipaddress, useragent, errorcode
FROM org_cloudtrail
WHERE dt BETWEEN '2026/09/01' AND '2026/09/06'
  AND useridentity.accesskeyid = 'AKIAIOSFODNN7EXAMPLE'
ORDER BY eventtime;
```

**② AccessDenied 상위 주체** — 탐색(reconnaissance)의 흔적을 찾습니다.

```sql
SELECT useridentity.arn AS principal, eventsource, eventname,
       count(*) AS denials, min(eventtime) AS first_seen, max(eventtime) AS last_seen
FROM org_cloudtrail
WHERE dt BETWEEN '2026/09/01' AND '2026/09/06'
  AND (errorcode LIKE '%AccessDenied%' OR errorcode LIKE '%UnauthorizedOperation%')
GROUP BY useridentity.arn, eventsource, eventname
ORDER BY denials DESC
LIMIT 50;
```

**③ 특정 IP에서 온 모든 호출** — 위협 인텔리전스에서 받은 IP나 이상 로그인의 소스를 넓힙니다.

```sql
SELECT eventtime, recipientaccountid, useridentity.arn AS principal,
       eventname, errorcode
FROM org_cloudtrail
WHERE dt BETWEEN '2026/09/01' AND '2026/09/06'
  AND sourceipaddress = '203.0.113.42'
ORDER BY eventtime;
```

**④ 역할 위임 추적** — 어떤 주체가 어떤 역할로 갈아탔는지, 그리고 그 세션이 받은 키가 무엇인지 잇습니다.

```sql
SELECT eventtime,
       useridentity.arn AS caller,
       json_extract_scalar(requestparameters, '$.roleArn')        AS assumed_role,
       json_extract_scalar(requestparameters, '$.roleSessionName') AS session_name,
       json_extract_scalar(responseelements, '$.credentials.accessKeyId') AS issued_key,
       sourceipaddress
FROM org_cloudtrail
WHERE dt BETWEEN '2026/09/01' AND '2026/09/06'
  AND eventsource = 'sts.amazonaws.com'
  AND eventname IN ('AssumeRole', 'AssumeRoleWithWebIdentity', 'AssumeRoleWithSAML')
  AND errorcode IS NULL
ORDER BY eventtime;
```

여기서 얻은 `issued_key` 를 ①에 다시 넣으면 위임 이후의 활동이 이어집니다. **이 두 질의의 연결이 클라우드 사고 조사의 기본기입니다.**

**⑤ S3 대량 다운로드** — 데이터 이벤트가 켜져 있어야 합니다(29.2).

```sql
SELECT useridentity.arn AS principal,
       sourceipaddress,
       json_extract_scalar(requestparameters, '$.bucketName') AS bucket,
       count(*) AS gets,
       approx_distinct(json_extract_scalar(requestparameters, '$.key')) AS distinct_keys
FROM org_cloudtrail
WHERE dt BETWEEN '2026/09/01' AND '2026/09/06'
  AND eventsource = 's3.amazonaws.com'
  AND eventname = 'GetObject'
GROUP BY useridentity.arn, sourceipaddress,
         json_extract_scalar(requestparameters, '$.bucketName')
HAVING count(*) > 1000
ORDER BY gets DESC;
```

**⑥ 콘솔 로그인 이력** — MFA 사용 여부와 성공/실패를 함께 봅니다.

```sql
SELECT eventtime, useridentity.arn AS principal, sourceipaddress,
       json_extract_scalar(additionaleventdata, '$.MFAUsed')     AS mfa,
       json_extract_scalar(responseelements, '$.ConsoleLogin')   AS result,
       errormessage
FROM org_cloudtrail
WHERE dt BETWEEN '2026/09/01' AND '2026/09/06'
  AND eventname = 'ConsoleLogin'
ORDER BY eventtime DESC;
```

**⑦ 신규 IAM 사용자·키·정책 생성** — 지속성(persistence) 확보 시도를 찾습니다.

```sql
SELECT eventtime, recipientaccountid, useridentity.arn AS actor, eventname,
       json_extract_scalar(requestparameters, '$.userName') AS target_user,
       sourceipaddress
FROM org_cloudtrail
WHERE dt BETWEEN '2026/09/01' AND '2026/09/06'
  AND eventsource = 'iam.amazonaws.com'
  AND eventname IN ('CreateUser', 'CreateAccessKey', 'CreateLoginProfile',
                    'UpdateLoginProfile', 'AttachUserPolicy', 'PutUserPolicy',
                    'CreateRole', 'UpdateAssumeRolePolicy')
  AND errorcode IS NULL
ORDER BY eventtime;
```

**⑧ 사용하지 않는 리전의 활동** — 크립토마이닝과 은닉 리소스의 전형적 신호입니다.

```sql
SELECT awsregion, recipientaccountid, useridentity.arn AS principal,
       eventname, count(*) AS calls
FROM org_cloudtrail
WHERE dt BETWEEN '2026/09/01' AND '2026/09/06'
  AND awsregion NOT IN ('ap-northeast-2', 'us-east-1')
  AND readonly = 'false'
GROUP BY awsregion, recipientaccountid, useridentity.arn, eventname
ORDER BY calls DESC;
```

### 비용 절감

Athena는 **스캔한 데이터 양**으로 과금됩니다. 조사 중 같은 질의를 스무 번 고쳐 던지므로 비용이 빠르게 붙습니다.

| 방법 | 효과 |
|---|---|
| `dt`/`account`/`region` 파티션 조건을 항상 명시 | 가장 큰 절감. 하루치만 보면 스캔량이 수백분의 1 |
| `SELECT *` 대신 필요한 컬럼만 | CloudTrail JSON은 행 지향이라 효과가 제한적이지만 결과 전송량은 줄어듦 |
| 자주 쓰는 기간을 CTAS로 Parquet 변환 | 열 지향 + 압축으로 스캔량 10분의 1 수준. 장기 조사 시 필수 |
| 작업 그룹(work group)에 질의당 스캔 한도 설정 | 실수로 전체 스캔하는 질의를 차단 |
| 질의 결과 재사용 활성화 | 같은 질의 반복 시 재스캔하지 않음 |

```sql
CREATE TABLE ct_incident_202609
WITH (format = 'PARQUET', parquet_compression = 'SNAPPY',
      partitioned_by = ARRAY['dt'])
AS SELECT * FROM org_cloudtrail
   WHERE dt BETWEEN '2026/09/01' AND '2026/09/06';
```

> 💡 **원서 이후 변경** — CloudTrail Lake가 추가되어 Athena 테이블을 만들지 않고도 관리형 이벤트 데이터 스토어에 SQL을 던질 수 있습니다. 설정이 훨씬 간단한 대신 보존 요금 체계가 다르고, S3의 원본 로그와 별개 사본이 생깁니다. **원본 로그를 로그 아카이브 계정 S3에 두는 29장의 구조는 어느 쪽을 택하든 유지하십시오.**

## 30.7 로그 파싱·상관 분석·SIEM

### 파싱 — 필드가 없으면 질의도 없다

> 📖 *Practical Cloud Security* 2판 7장 「Parsing Logs」: **"로그 파서는 서로 다른 유형의 이벤트에서 특정 정보 조각(필드)을 뽑아낸다."** 원서는 OS 이벤트에서 타임스탬프·시스템 이름·이벤트 텍스트를, 방화벽 로그에서 출발지/목적지 IP와 허용/거부 결과를, 안티바이러스 로그에서 호스트명과 악성코드 발견 여부를 뽑는 예를 들고, **"로그 형식은 수천 가지"** 라며 syslog(RFC 3164/5424), CLF/ELF, CEF, CADF를 공통 형식으로 소개합니다.

AWS에서는 이 문제의 절반이 이미 해결되어 있습니다. **CloudTrail, VPC 플로우 로그, Config, GuardDuty는 모두 구조화된 JSON**이라 파서를 짤 필요가 없습니다. 파싱 문제가 남는 곳은 정확히 그 밖의 영역입니다.

| 로그 | 형식 | AWS에서의 파싱 |
|---|---|---|
| CloudTrail / Config / GuardDuty | JSON | 불필요 |
| VPC 플로우 로그 | 공백 구분 고정 필드 | 필드 순서를 커스터마이징했으면 스키마 정의 필요 |
| ALB / CloudFront 액세스 로그 | 공백 구분 (ELF 계열) | Athena SerDe 정규식 필요 |
| EC2 OS 로그 (`/var/log/secure` 등) | syslog | CloudWatch Agent 수집 후 파싱 필요 |
| 애플리케이션 로그 | 자유 형식 | **개발 단계에서 JSON 구조화 로깅을 강제하는 것이 유일한 해법** |

> ⚠️ 원서(📖 *Practical Cloud Security* 2판 7장)가 「How to Watch」 서두에서 강조하는 시각 동기화 문제 — **"NTP로 모든 시스템의 시각을 동기화하고, 모든 타임스탬프에 타임존 정보를 넣거나 모든 로그에 GMT 같은 동일 타임존을 쓰라"** — 는 AWS에서도 그대로 유효합니다. CloudTrail의 `eventTime` 은 UTC지만, EC2 안의 애플리케이션 로그가 KST 로컬 시각을 타임존 표기 없이 찍고 있으면 상관 분석에서 **9시간 어긋난 사건 두 개**가 만들어집니다. Amazon Time Sync Service를 쓰고, 로그는 전부 UTC + 타임존 표기로 남기십시오.

### 상관 분석 — 한 로그로는 알 수 없는 것

> 📖 같은 장 「Searching and Correlation」: **"로그가 집계되고 파싱되면, 파싱된 필드로 검색하고 서로 다른 시스템 사이의 이벤트를 상관 지을 수 있다."** 원서는 "같은 사용자에 대해 VPN 연결 없이 성공한 로그인", "악성코드 탐지에 이어진 로그인" 같은 예를 들고, **"여러 사람이 동시에 다급하게 검색을 던질 때 시스템이 견디는지 사고 한복판이 아닐 때 시험해 보라"** 고 경고합니다. 또 **핫 스토리지는 즉시 질의 가능하지만 콜드 스토리지는 꺼내어 다시 적재해야** 한다는 점을 짚습니다.

이 핫/콜드 구분은 AWS에서 그대로 비용 구조가 됩니다.

| 계층 | 서비스 | 질의 지연 | 성격 |
|---|---|---|---|
| 핫 | CloudWatch Logs Insights, OpenSearch | 초 단위 | 최근 며칠~몇 주 |
| 웜 | Athena on S3 Standard | 수십 초~분 | 수개월 |
| 콜드 | Athena on S3 Glacier 계열 | **복원 필요(수 시간)** | 규정 보존분 |

🔴 **수명 주기 정책은 "조사에 실제로 필요한 기간"을 기준으로 정하십시오.** 30일 뒤 Glacier로 보내는 정책은 비용상 매력적이지만, 침해가 몇 달 뒤에 발견되는 경우 **가장 중요한 로그가 정확히 꺼내기 어려운 곳에** 있게 됩니다.

### SIEM — 필요한가

> 📖 같은 장 「Security Information and Event Managers」와 「To SIEM or Not to SIEM」: SIEM은 **앞 단계들(집계·파싱·검색·상관·알림)의 일부 또는 전부를 수행**하며, 규칙으로 **두 곳에서 일어난 사건을 상관 짓거나 현재 데이터와 과거 데이터를 비교해** 위험을 탐지합니다. 원서가 든 예 중 몇 가지: *"데이터베이스 트래픽이 월평균보다 200% 늘었다"*, *"어떤 계정에서 150번의 로그인 실패 뒤 성공이 있었다"*, *"300개 계정에서 각 1회씩 실패한 뒤 301번째 계정에서 성공했다 — 패스워드 스프레이인가"*, *"John은 원래 새벽 3시에, 그 나라에서 로그인하지 않는다"*, *"업무 시간 외에 새 관리자 계정이 만들어졌다"*.
> 필요성에 대한 원서의 답은 조건부입니다: **소규모 조직은 간단한 알람을 만드는 로그 집계 시설만으로도 버틸 수 있지만**, 여러 로그 형식에서 관련 데이터를 뽑고 상관 짓고 흔한 공격의 모양을 알고 위협 인텔리전스 피드를 받는 **로직과 규칙은 매우 복잡해 내부에서 재현하기 어렵다**는 것입니다.

원서가 든 SIEM 질문 목록은 그대로 AWS 로그로 번역됩니다.

| 원서의 SIEM 질문 | AWS에서 답하는 로그 조합 |
|---|---|
| 150회 실패 후 성공 = 무차별 대입? | CloudTrail `ConsoleLogin` 실패/성공 시퀀스 |
| 300개 계정 각 1회 실패 후 성공 = 패스워드 스프레이? | CloudTrail `ConsoleLogin` 을 **주체가 아닌 소스 IP 기준**으로 집계 |
| John이 평소와 다른 시각·국가에서 로그인 | CloudTrail `sourceIPAddress` + GeoIP + 주체별 기준선 |
| DB 트래픽이 평균보다 200% | RDS 지표 + VPC 플로우 로그 바이트 수 |
| 알려진 위협 IP로 나가는 아웃바운드 연결 | VPC 플로우 로그·Route 53 리졸버 로그 + GuardDuty |
| 새 관리자 계정이 업무 시간 외에 생성 | CloudTrail IAM 이벤트 + 시각 조건 (30.6 ⑦) |

### AWS에서의 선택지

| 선택지 | 성격 | 적합한 조직 |
|---|---|---|
| CloudWatch + EventBridge + Athena | 이 장에서 만든 것. 규칙은 직접 작성 | 계정 수가 적고 전담 인력이 1~2명 |
| GuardDuty + Security Hub | 관리형 탐지 + 결과 집계 (31장) | 대부분의 조직의 기본값 |
| OpenSearch Service 자체 구축 | 완전한 유연성, 대시보드·검색 강력 | 로그 파이프라인을 운영할 인력이 있는 조직 |
| 서드파티 SIEM | 위협 인텔리전스·상관 규칙·온프레미스 통합 포함 | 온프레미스와 멀티 클라우드가 섞인 조직 |

> 💡 **원서 이후 변경 — Amazon Security Lake와 OCSF** — 근거 원서 3권 어디에도 나오지 않는, 이후 등장한 서비스입니다. Security Lake는 CloudTrail·VPC 플로우 로그·Route 53 리졸버 로그·Security Hub 결과 등을 조직 계정에서 자동 수집해, **OCSF(Open Cybersecurity Schema Framework)** 라는 개방 스키마로 정규화한 Parquet 파일로 로그 아카이브 계정 S3에 적재합니다. 구독자는 Lake Formation 권한을 통해 Athena나 서드파티 SIEM으로 읽습니다.
> 이것이 해결하는 문제가 정확히 원서가 말한 파싱·정규화 문제입니다. 원서의 CADF 언급 — "클라우드 제공자를 바꿔도 로그 집계·파싱 시스템을 바꾸지 않게 하려는 표준" — 과 같은 동기의, 실제로 채택된 후속 표준으로 이해하면 됩니다. **다만 Security Lake를 쓴다고 29장의 원본 트레일을 꺼서는 안 됩니다.** 정규화된 사본과 무결성 검증이 붙은 원본은 역할이 다릅니다.

## 30.8 위협 헌팅(Threat Hunting)

> 📖 *Practical Cloud Security* 1·2판 7장 「Threat Hunting」은 두 판 모두 같은 문장으로 순서를 못 박습니다: **"기본기를 갖춘 뒤에야 — 즉 보안 관련 로그와 지표를 수집하고, 파싱하고, 시스템이 만든 알람에 대응하고 있어야 — 위협 헌팅으로 넘어가야 한다."**
> 2판은 위협 헌팅을 **"특정 알람에 반응하는 대신 '문제를 찾아 나서도' 되는 몇 안 되는 경우"** 로 규정하고 절차를 이렇게 설명합니다: **"'혹시 내가 APT 12345의 표적이 된 것은 아닐까' 또는 '누군가 내 우주선의 비밀 설계도를 노리는 것은 아닐까' 같은 가설을 세우는 것에서 시작한다. 그런 다음 수집해 둔 데이터를 질의하고, 필요하면 새 데이터를 수집해, 그 가설을 입증하거나 반증할 증거를 모은다."**

이 순서 규정이 중요합니다. 30.3의 15개 알람이 안 켜져 있는데 위협 헌팅을 하는 것은 순서가 뒤바뀐 것입니다. **헌팅은 자동 탐지가 놓친 것을 찾는 활동이지, 자동 탐지의 대체재가 아닙니다.**

### 헌팅 절차

| 단계 | 하는 일 | 산출물 |
|---|---|---|
| ① 가설 수립 | "우리 환경에서 X가 일어났다면 어떤 흔적이 남는가" | 한 문장의 가설 |
| ② 데이터 확인 | 그 흔적을 담을 로그가 실제로 있는가 | 없으면 **여기서 멈추고 수집부터** (29장) |
| ③ 질의 | Athena/Logs Insights로 후보 추출 | 결과 집합 |
| ④ 선별 | 정상으로 설명되는 것을 걷어냄 | 잔여 이상 건 |
| ⑤ 결론 | 사고인가, 설정 오류인가, 정상인가 | 사고면 32장, 아니면 ⑥ |
| ⑥ 자산화 | 이 질의를 알람·Config 규칙·대시보드 위젯으로 고정 | **다음엔 헌팅 없이 잡힘** |

⑥이 헌팅의 진짜 가치입니다. 매번 손으로 뒤지는 것은 확장되지 않습니다. **헌팅 한 번은 탐지 규칙 하나를 남겨야 합니다.** 반대로 ②에서 "그 로그가 없다"는 결론이 반복해서 나온다면, 그것 자체가 29장으로 돌아가야 한다는 신호입니다.

### AWS 로그로 수행하는 헌팅 질문 6개

**① "우리가 모르는 자격 증명이 살아 있는가?"**
IAM 자격 증명 보고서에서 90일 이상 미사용 액세스 키를 뽑고, CloudTrail에서 그 키의 최근 활동을 봅니다. **미사용인 줄 알았는데 활동이 있는 키**가 가장 나쁜 결과입니다.

**② "역할 신뢰 관계 중 외부 계정을 향한 것이 있는가?"**
`iam:ListRoles` 결과의 `AssumeRolePolicyDocument` 에서 조직 밖 계정 ID나 `"Principal": "*"` 를 찾고, IAM Access Analyzer 결과와 대조합니다(8장). 그리고 CloudTrail ④번 질의로 **그 역할이 실제로 위임된 적이 있는지** 확인합니다.

**③ "정상 사용자 에이전트가 아닌 호출이 있는가?"**
`useragent` 를 집계해 꼬리를 봅니다. AWS 콘솔·SDK·CLI가 아닌 값, 특히 공개된 공격 도구의 기본 문자열이 그대로 남아 있는 경우가 있습니다. ⚠️ `useragent` 는 클라이언트가 임의로 설정할 수 있으므로 **차단 근거로는 쓸 수 없고 헌팅 단서로만** 씁니다.

**④ "우리 VPC에서 나가서는 안 되는 곳으로 나가는 트래픽이 있는가?"**
VPC 플로우 로그의 목적지를 집계해, 격리 데이터 서브넷(`10.20.20.0/24`, `10.20.21.0/24`)에서 출발한 인터넷 방향 `ACCEPT` 흐름이 있는지 봅니다. 설계상 0건이어야 하므로 1건이라도 나오면 조사 대상입니다.

**⑤ "사용하지 않는 리전에 리소스가 있는가?"**
30.6 ⑧의 질의를 돌리고, 리전별 실행 중 인스턴스·NAT 게이트웨이·Lambda를 세어 봅니다. 비용 리포트에서 예상 밖 리전이 보이는 것이 가장 흔한 첫 단서입니다.

**⑥ "권한이 조용히 늘어난 주체가 있는가?"**
지난 90일간 `AttachRolePolicy`/`PutRolePolicy`/`CreatePolicyVersion` 을 주체별로 집계해, **자기 자신 또는 자기가 위임 가능한 역할의 권한을 넓힌** 사례를 찾습니다. 권한 상승은 대개 단발 사건이 아니라 며칠에 걸친 작은 변경들의 누적입니다.

## 30.9 ⚠️ 알람 피로(Alert Fatigue)

### 사고 시나리오

금요일 새벽 2시 47분, 운영 계정에서 `StopLogging` 이벤트가 발생하고 P1 알람이 온콜 담당자의 휴대폰을 울립니다. 담당자는 알림을 밀어 넘기고 다시 잠듭니다. 월요일 아침, 지난 3일간 온 알람 412건 중 하나로 그 알람이 목록에 남아 있습니다. 아무도 열어 보지 않습니다.

3주 뒤 고객사로부터 데이터 유출 통보를 받고 조사를 시작합니다. 그제야 그 금요일 새벽 이후 **CloudTrail이 꺼져 있었다**는 사실을 발견합니다. 이후 3일간 무슨 일이 있었는지는 영원히 알 수 없습니다.

### 원인

알람이 없어서가 아닙니다. **알람은 정확히 작동했습니다.** 문제는 그 알람이 도착한 채널이 이미 신뢰를 잃었다는 것입니다.

> 📖 *Practical Cloud Security* 2판 7장 「Alerting and Automated Response」: **"바로 여기에 로그 분석의 기예가 있다. 시스템을 너무 민감하게 튜닝해서 보안팀이 끊임없이 오탐 알람을 받게 되면, 모든 알람이 금세 무시된다. 반대로 정기적으로 알람을 조금도 받지 못하고 있다면, 확인했어야 할 무언가를 놓치고 있는 것이다."** 원서는 이어서 **"각 오탐 유형마다 피드백 루프가 필요하다 — 그런 유형의 이벤트를 걸러낼지, 임계치를 올릴지, 다른 조치를 취할지 판단하기 위해서다"**, 그리고 **"알람이 무시되고 있지 않은지 확인하기 위해, 알람이 발생할 것을 알고 있는 테스트를 주기적으로 돌려 보는 것을 고려하라"** 고 권합니다.

이 마지막 문장이 이 절의 핵심 실천 항목입니다.

### 올바른 구성

**① 알람마다 소유자가 있어야 한다.** 소유자 없는 알람은 반드시 무시됩니다. 알람 태그에 소유 팀을 넣고, 소유자가 정해지지 않은 알람은 만들지 않습니다.

```bash
aws cloudwatch tag-resource \
  --resource-arn "arn:aws:cloudwatch:ap-northeast-2:444455556666:alarm:shopmini-iam-policy-changes" \
  --tags Key=Owner,Value=platform-security Key=Severity,Value=P2 Key=Runbook,Value=RB-014 \
  --region $REGION --profile $PROFILE
```

**② 심각도별 에스컬레이션 경로를 미리 정한다.**

| 심각도 | 채널 | 응답 목표 | 미응답 시 | 예시 |
|---|---|---|---|---|
| P1 | 온콜 호출(전화/푸시) | 15분 내 확인 | 30분 뒤 2차 온콜, 60분 뒤 보안 책임자 | 루트 사용, 트레일 중지, KMS 삭제 예약 |
| P2 | 팀 채팅 + 티켓 자동 생성 | 근무일 4시간 내 | 24시간 뒤 P1 승격 | IAM/SG 변경, 로그인 실패 급증 |
| P3 | 일일 다이제스트 메일 | 주간 리뷰 | 없음 | AccessDenied 집계, 태그 미준수 |

> 📖 같은 절: **"알람은 발사 후 잊어버리는 활동이어서는 안 된다. 아무도 항상 대기하고 싶어 하지 않으므로 사람들을 교대로 넣고 뺄 방법이 필요하고, 일정 시간 안에 알람이 확인(acknowledge)되었는지, 아니면 처리할 다른 사람에게 에스컬레이션되었는지 보장할 방법이 필요하다."** 원서는 또 대규모 조직이 24×7 SOC를 직접 만들거나 MSSP와 계약하며, **낮은 수준의 모니터링은 MSSP가 맡고 중요한 알람만 사내 인력으로 에스컬레이션하는 혼합 모델**이 흔하다고 설명합니다.

**③ 튜닝 절차를 정례화한다.**

1. 주간으로 알람별 **발생 건수와 실제 조치로 이어진 비율**을 집계합니다.
2. 오탐률이 높은 알람은 세 갈래로 처리합니다 — **원인 주체를 필터에서 제외**(배포 역할 등), **임계치 상향**, 또는 **복합 알람으로 조건 결합**. 알람을 그냥 끄는 것은 마지막 수단입니다.
3. **한 달간 한 번도 울리지 않은 알람은 고장을 의심합니다.** 지표 필터의 로그 그룹이 바뀌었거나, 필터 패턴이 이벤트 형식 변경으로 더 이상 맞지 않을 수 있습니다.
4. 제외 목록·임계치는 IaC로 관리해 변경 이력이 남게 합니다(28장).

**④ 분기마다 알람 실사(fire drill)를 한다.** 원서가 권한 "알람이 발생할 것을 아는 테스트"를 실제로 돌립니다. 격리된 테스트 계정에서 의도적으로 `StopLogging` 을 호출하고, **알람이 몇 분 만에 누구의 화면에 도착했는지** 기록합니다. 도착하지 않았다면 그것이 이번 분기의 최우선 수정 과제입니다.

**⑤ 자동 대응은 신중하게.**

> 📖 같은 절: **"자동 대응은 원칙적으로는 좋게 들리지만 비즈니스를 마비시킬 잠재력이 실재한다. 잘못된 대응이나 자동화된 과잉 반응이 일으키는 장애에 더해, 자동 대응 시스템은 공격자에게 의도적으로 이용되어 장애를 유발할 수 있다. 서비스 거부 공격을 막으려고 상당한 돈을 쓰고 나서, 정작 공격자가 단순한 포트 스캐너나 몇 번의 로그인 실패만으로 쉬운 서비스 거부를 일으킬 수 있게 만들었다는 것을 깨닫는 일은 즐겁지 않다."**

이 경고의 구체적 대응은 35장에서 다룹니다. 이 장의 범위에서 기억할 것은 하나입니다 — **알람 피로를 자동 대응으로 해결하려 들지 마십시오.** 사람이 보지 않는 알람을 자동화에 연결하면, 오탐이 사람의 피로가 아니라 **서비스 장애**로 바뀔 뿐입니다. 튜닝이 먼저입니다.

## 🔴 필수 구성 체크리스트

**알림 채널**
- [ ] 심각도별 SNS 주제가 분리되어 있고 모든 구독이 `Confirmed` 상태다
- [ ] 주제 정책이 발행 주체를 서비스 주체 + `aws:SourceAccount` 로 제한한다
- [ ] 주제가 **고객 관리형** KMS 키로 암호화되고, 키 정책에 `cloudwatch`/`events` 주체 허용이 있다

**알람**
- [ ] 30.3의 15개 알람이 전부 존재한다
- [ ] IAM·STS·콘솔 로그인 관련 알람이 `us-east-1` 에 있다
- [ ] 모든 지표 필터에 `defaultValue=0` 이 있다
- [ ] 로그 그룹별 `IncomingLogEvents` 중단 알람이 `treat-missing-data=breaching` 으로 있다
- [ ] 모든 알람에 `Owner`·`Severity`·`Runbook` 태그가 있다

**분석**
- [ ] 조직 CloudTrail용 Athena 테이블이 **파티션 프로젝션**으로 만들어져 있다
- [ ] 30.6의 8개 조사 질의가 저장되어 있고 사고 대응 절차서에서 참조된다
- [ ] Athena 작업 그룹에 질의당 스캔 한도가 걸려 있다
- [ ] 로그의 핫/웜/콜드 전환 시점이 "조사에 필요한 기간"을 기준으로 정해져 있다

**운영**
- [ ] 심각도별 에스컬레이션 경로와 미응답 시 승격 규칙이 문서화되어 있다
- [ ] 주간 알람 튜닝 리뷰가 정례화되어 있다
- [ ] 분기 1회 알람 실사를 수행하고 도달 시간을 기록한다

## 다음 장 예고

29장에서 로그를 모았고, 30장에서 그것을 보고 알리고 질의했습니다. 그런데 이 장에서 만든 탐지 규칙은 전부 **우리가 미리 생각해 낸 것**입니다. 30.3의 15개는 우리가 아는 공격 패턴이고, 30.8의 헌팅 질문도 우리가 세운 가설입니다. **우리가 상상하지 못한 공격은 여전히 지나갑니다.**
