## 36.1 🔴 왜 계정을 나누는가

"계정 하나로 태그와 IAM만 잘 쓰면 되지 않느냐"는 질문은 거의 모든 조직이 한 번은 합니다. 답은 **아니오**이고, 다섯 이유 모두 **계정 안에서는 원리적으로 해결되지 않는** 문제입니다.

### 이유 1 — 폭발 반경: 계정은 AWS에서 가장 단단한 경계다

1.4의 네 경계 단위(계정·VPC·KMS 키·IAM 역할) 중 계정만이 **기본값이 완전 차단**입니다. 같은 계정 안에서는 IAM 정책 한 줄을 잘못 쓰면 즉시 접근이 열리지만, 다른 계정의 리소스는 **양쪽이 모두 허용해야** 접근됩니다(7.3). 실수가 사고로 번지려면 두 번 틀려야 합니다.

> 📖 *Practical Cloud Security* 2판 1장은 클라우드 콘솔의 권한을 이렇게 설명합니다. **"많은 제공자에서, 당신의 클라우드 콘솔에 접근할 수 있는 사람은 기본적으로 그 클라우드 제공자가 관리하는 모든 것에 대해 신과 같은(godlike) 권한을 갖게 된다. 여기에는 프로비저닝된 시스템의 운영체제에 어떤 통제가 걸려 있든 상관없이, 클라우드 환경의 어느 부분에서든 데이터를 읽고 수정하고 파괴하는 능력이 포함될 수 있다."**

"신과 같은 권한"의 **사정거리**를 정하는 것이 계정 분리입니다. 자격 증명 하나가 유출되었을 때 잃는 것이 "회사의 모든 것"인지 "개발 환경 하나"인지는 IAM 정책이 아니라 **계정 경계**가 결정합니다.

### 이유 2 — 권한 격리: IAM만으로는 "절대 못 하게" 만들 수 없다

같은 계정 안에서 "이 팀은 이 리소스만"을 만들려면 ABAC(8.7)와 권한 경계(7.6)를 겹쳐야 하는데, **정책을 수정할 수 있는 사람은 그 제약을 스스로 풉니다.** `iam:PutRolePolicy` 하나를 잘못 주면 격리가 사라집니다. 계정을 나누면 다른 계정의 IAM은 아예 다른 IAM이고, 그 위의 **SCP**(37장)가 계정 관리자조차 넘을 수 없는 상한을 긋습니다.

### 이유 3 — 과금 분리: 비용은 가장 정직한 자산 대장이다

태그 기반 비용 배분은 **태그가 빠진 리소스를 놓치지만** 계정 단위 집계는 새는 곳이 없습니다.

> 📖 *Practical Cloud Security* 2판 3장은 자산 관리를 "배관"에 비유하며 **"대부분의 조직에는 서비스와 인프라를 프로비저닝하는 길목에 자연스러운 통제 지점(natural control points)이 있다. 이것은 조직마다 다르지만, 당신은 그 통제 지점을 찾아 조여야 한다"** 고 말하고, 첫 통제 지점으로 **조달(procurement)** 을 듭니다. **"대부분의 경우 이 자산들에 대해 요금이 청구된다. 그렇다면 조달 프로세스를 살펴보는 것이 좋은 첫걸음인 경우가 많다."** 같은 장은 섀도 IT가 클라우드에서 더 나빠졌다고 지적합니다. **"사업의 어느 영역에 있는 누구든 신용카드 한 장만으로(때로는 그것조차 없이) 엄청난 수의 IT 리소스를 손쉽게 프로비저닝할 수 있다."**

계정을 조직에 편입시키는 것은 보안 기능이기 이전에 **섀도 IT를 조달 통제 지점 안으로 끌어들이는 자산 관리 조치**입니다.

### 이유 4 — 서비스 한도: 쿼터는 대부분 계정×리전 단위다

AWS의 서비스 쿼터는 대다수가 **계정별·리전별**입니다. VPC 개수, 보안 그룹 규칙 수, Lambda 동시 실행, EC2 vCPU, KMS 키 요청률 — 전부 계정 안에서 나눠 씁니다.

### 이유 5 — 규제 범위 축소: 감사 대상을 물리적으로 줄인다

PCI DSS·HIPAA·개인정보 감사에서 가장 비싼 것은 **범위(scope)** 입니다. 카드 데이터가 지나는 시스템이 계정 하나에 격리되어 있으면 감사 범위는 그 계정이고, 같은 계정에 마케팅 배치 잡이 섞여 있으면 그것도 증적 대상입니다.

> 📖 *Practical Cloud Security* 2판 2장은 규제가 설계에 앞서 영향을 준다고 말합니다. **"일부 컴플라이언스 요구사항은 당신의 보안 설계에 정보를 준다. 그래서 이 이른 단계에서도 몇 가지 산업·규제 요구사항을 기록해 두는 것이 중요하다."** 이어 GDPR·FISMA/FedRAMP·ITAR·PCI DSS·HIPAA를 열거합니다.

### 다섯 이유의 구체 사례

| 이유 | 단일 계정에서 벌어지는 일 | 계정을 나눴을 때 |
|---|---|---|
| 폭발 반경 | 유출된 CI 자격 증명으로 운영 RDS 스냅샷을 떠 외부 계정에 공유 | 파이프라인이 개발 `555555555555`에 있으면 운영 `111122223333`으로 가려면 **명시적 배포 역할 하나**를 더 뚫어야 함 |
| 권한 격리 | 관리자 권한을 가진 누구든 정책을 고쳐 CloudTrail을 끌 수 있음 | OU에 `cloudtrail:StopLogging` 거부 SCP → **루트 사용자조차** 못 끔 |
| 과금 분리 | 개인 카드로 만든 PoC 계정이 조직 트레일·GuardDuty·Config 어디에도 안 잡힘 | 조직 편입 즉시 전부 자동 부착(37.9) |
| 서비스 한도 | 개발 부하 테스트가 Lambda 동시 실행 쿼터를 소진 → **운영이 스로틀링** | 쿼터가 계정별이므로 간섭 자체가 발생하지 않음 |
| 규제 범위 | 카드 데이터와 마케팅 배치 잡이 같은 계정 → 둘 다 감사 증적 대상 | 계정 경계가 곧 "이 밖은 범위 밖"이라는 증거 |

### 🔴 그래서 반드시 이렇게 하라

1. **환경(운영/비운영)은 무조건 계정으로 나눈다.** VPC 분리로 대체하지 마십시오. 쿼터와 IAM이 섞입니다.
2. **로그와 백업의 최종 목적지는 워크로드 계정 밖에 둔다.** 운영 계정 관리자가 지울 수 있는 로그는 증거가 아닙니다(29.9, 17.4).
3. **보안 도구의 운영 주체를 워크로드 계정 밖에 둔다.** 감시자와 피감시자가 같은 계정에 있으면 안 됩니다.
4. **규제 데이터는 전용 계정에 가둔다.** 나중에 떼는 것이 처음부터 나누는 것보다 몇 배 비쌉니다.
5. **계정을 나눈 만큼 중앙 강제 수단(Organizations + SCP)을 같이 도입한다.** 강제 수단 없이 계정만 늘리면 관리 불가능한 파편이 됩니다.

계정 하나에 모든 것이 든 조직은 결국 "운영에 영향을 줄까 봐 아무것도 못 고치는" 상태가 되고, 그때는 분리 비용이 이미 신규 구축 비용보다 커져 있습니다.

## 36.2 AWS Organizations 구성 🧪

계정을 나누기로 했다면 그것들을 하나의 조직으로 묶는 수단이 AWS Organizations입니다.

> 📖 *AWS Security Cookbook* 1장 「Creating a master account for AWS Organizations」: **"많은 조직이 개발, 배포(운영) 등을 위해 여러 개의 AWS 계정을 갖고 있다. AWS Organizations 서비스는 우리의 모든 AWS 계정을 중앙에서 관리하도록 도와준다."**

같은 레시피의 "There's more"에 실무에서 계속 발목을 잡는 성질들이 압축되어 있습니다.

> 📖 같은 장: **"AWS Organizations 서비스는 모든 리전에서 지원되지만, 엔드포인트는 상용 조직의 경우 US East(N. Virginia)에, AWS GovCloud(US) 조직의 경우 AWS GovCloud(US-West)에 위치한다. (…) AWS Organizations 서비스는 글로벌 서비스다. 조직 엔터티를 만들 때 리전을 선택하거나 지정할 필요가 없다. (…) AWS Organizations 사용에 추가 비용은 없다. (…) 어떤 조직의 멤버도 아닌 AWS 계정에서만 새 조직의 생성을 시작할 수 있다. 한 번 만든 관리 계정은 변경할 수 없다. (…) 한 계정은 한 번에 하나의 조직에만 속할 수 있고, 조직 안에서 한 계정은 한 번에 하나의 OU에만 속할 수 있다. (…) OU와 계정의 계층은 루트를 포함해 5단계까지 중첩할 수 있다."**

🔴 **"한 번 만든 관리 계정은 변경할 수 없다"** 를 가볍게 넘기지 마십시오. 조직 생성은 되돌리기 가장 어려운 결정이며, 36.6이 그 대가를 다룹니다.

### 조직 생성과 기능 세트

```bash
# 조직 생성 — 반드시 ALL(전체 기능)로 만든다
aws organizations create-organization \
  --feature-set ALL \
  --profile awssec-lab

# 확인
aws organizations describe-organization --profile awssec-lab
# → { "Organization": { "Id": "o-exampleorgid",
#      "MasterAccountId": "123456789012", "FeatureSet": "ALL", ... } }
```

기능 세트는 둘뿐이고 선택은 사실상 정해져 있습니다.

| 기능 세트 | 값 | 할 수 있는 것 | 판단 |
|---|---|---|---|
| 통합 결제만 | `CONSOLIDATED_BILLING` | 청구 통합, 계정 목록 관리 | ⚠️ **정책을 붙일 수 없다.** SCP·태그 정책·백업 정책 전부 불가 |
| 전체 기능 | `ALL` | 위 + SCP, 태그/백업 정책, 신뢰할 수 있는 액세스, 위임 관리자 | 🔴 **항상 이것** |

통합 결제 모드로 만든 조직도 나중에 승격할 수 있지만 **모든 멤버 계정의 동의**가 필요합니다. 계정이 수십 개가 된 뒤에 하면 몇 주가 걸립니다.

```bash
# 통합 결제 모드로 시작한 조직을 전체 기능으로 승격 (멤버 전원 수락 필요)
aws organizations enable-all-features --profile awssec-lab
```

> 📖 같은 장: **"SCP는 접근을 거부할 수만 있고, 허용할 수는 없다."** 그리고 **"권한 경계(IAM 기능)와 SCP가 함께 있을 때, 해당 작업은 권한 경계와 SCP와 자격 증명 기반 정책이 **모두** 허용해야만 허용된다."**

### 신뢰할 수 있는 액세스(Trusted Access)

조직 전체를 대상으로 동작하는 AWS 서비스는 조직 데이터를 읽고 멤버 계정에 서비스 연결 역할을 만들 수 있어야 합니다. 이 통로를 여는 것이 **신뢰할 수 있는 액세스**입니다.

> 📖 같은 장: **"우리는 지원되는 서비스를 AWS Organizations와 통합해 여러 계정에 걸쳐 서비스를 관리할 수 있다. 통합 가능한 서비스의 현재 목록에는 AWS Artifact, AWS CloudTrail, Amazon CloudWatch Events, AWS Config, AWS Directory Service, AWS Firewall Manager, AWS License Manager, AWS RAM, AWS Service Catalog, AWS Single Sign-On이 포함된다."**

> 💡 **원서 이후 변경** — 이 목록은 이후 크게 늘어났습니다. GuardDuty, Security Hub, Macie, Detective, IAM Access Analyzer, AWS Backup, Systems Manager, Audit Manager, Control Tower, Inspector, Resource Explorer 등이 추가되었고, 원서의 "AWS Single Sign-On"은 현재 **IAM Identity Center**(9장)입니다.

```bash
# 신뢰할 수 있는 액세스 활성화 — 관리 계정에서 실행
for SP in cloudtrail.amazonaws.com \
          guardduty.amazonaws.com \
          securityhub.amazonaws.com \
          config.amazonaws.com \
          access-analyzer.amazonaws.com \
          ram.amazonaws.com \
          sso.amazonaws.com \
          backup.amazonaws.com; do
  aws organizations enable-aws-service-access \
    --service-principal "$SP" --profile awssec-lab
done

# 현재 열려 있는 목록 확인 — 감사 항목이다
aws organizations list-aws-service-access-for-organization --profile awssec-lab
```

⚠️ **이것은 조직 전체를 대상으로 하는 권한 통로입니다.** 필요한 서비스만 열고 목록을 정기 점검하며, 쓰지 않게 된 서비스는 `disable-aws-service-access`로 닫습니다.

### 위임 관리자(Delegated Administrator)

신뢰할 수 있는 액세스를 켜면 **관리 계정에서** 조직 전체가 보입니다. 그런데 36.6이 말하듯 관리 계정에는 사람이 자주 들어가면 안 됩니다. 이 모순을 푸는 것이 위임 관리자 — 조직 전체 관리 권한을 **지정한 멤버 계정 하나에 넘기는 것**입니다.

```bash
# 관리 계정에서 — 보안 도구 계정을 위임 관리자로 등록
for SP in guardduty.amazonaws.com \
          securityhub.amazonaws.com \
          macie.amazonaws.com \
          detective.amazonaws.com \
          access-analyzer.amazonaws.com \
          config-multiaccountsetup.amazonaws.com; do
  aws organizations register-delegated-administrator \
    --account-id 444455556666 \
    --service-principal "$SP" --profile awssec-lab
done

aws organizations list-delegated-administrators --profile awssec-lab
```

⚠️ 탐지 서비스는 **여기서 끝나지 않습니다.** GuardDuty·Security Hub·Macie·Detective는 각 서비스의 `enable-organization-admin-account` API로 관리자 계정을 한 번 더 지정해야 조직 전체 위임이 완성됩니다(12.5, 31.2·31.6). Access Analyzer·Config·Backup은 위 등록만으로 동작합니다(7.7, 17.3).

| 서비스 계열 | 위임 대상 | 근거 |
|---|---|---|
| GuardDuty · Security Hub · Macie · Detective · Access Analyzer | 보안 도구 `444455556666` | 탐지 운영 주체(31, 34) |
| CloudTrail 조직 트레일의 로그 목적지 | 로그 아카이브 `777788889999` | 위임 관리자가 아니라 **버킷 소유 계정**(29.9) |
| AWS Backup | 백업 담당 계정 | 볼트 정책의 소유자(17.3) |
| IAM Identity Center | 운영 편의상 별도 계정 가능 | 활성화는 관리 계정에서만(9.2) |

⚠️ 위임 관리자 계정은 **그 서비스에 한해 조직 전체의 관리자**이므로, 지정하는 순간 새로운 고가치 표적이 됩니다. 접근은 Identity Center 임시 자격 증명으로만 열고(9장), 그 계정의 CloudTrail은 반드시 로그 계정으로 보내십시오.

## 36.3 조직 하위 계정 생성과 이동 🧪

### CLI로 만들기 — 비동기라는 점이 핵심

> 📖 *AWS Security Cookbook* 1장 「Creating a new account under an AWS Organization」: **"이 명령은 비동기로 동작하며 요청 ID와 함께 즉시 반환된다. 요청 ID를 제공해 `describe-create-account-status` 서브커맨드로 요청 상태를 확인할 수 있다. 계정이 생성되었는지 확인하려면 AWS CloudTrail 로그에서 `CreateAccountResult` 이벤트를 확인하면 된다."**

```bash
# 1) 계정 생성 요청 — 즉시 반환된다. 계정이 만들어진 것이 아니다.
aws organizations create-account \
  --email aws-shopmini-prod@example.com \
  --account-name "ShopMini-Prod" \
  --role-name OrganizationAccountAccessRole \
  --iam-user-access-to-billing DENY \
  --tags Key=Project,Value=awssec-lab Key=Chapter,Value=ch36 \
  --profile awssec-lab
# → { "CreateAccountStatus": { "Id": "car-exampleid1111", "State": "IN_PROGRESS", ... } }

# 2) 상태 확인
aws organizations describe-create-account-status \
  --create-account-request-id car-exampleid1111 \
  --profile awssec-lab
# → State: SUCCEEDED, AccountId: 111122223333
```

> 📖 같은 장: **"`role-name` 파라미터는 새 멤버 계정에 자동으로 사전 구성될 IAM 역할의 이름을 지정한다. 이 역할은 멤버 계정에 대한 관리자 권한을 제공하고 관리 계정을 신뢰한다. (…) 기본값은 `OrganizationAccountAccessRole`이다. (…) `iam-user-access-to-billing` 파라미터는 IAM 사용자가 계정 청구 정보에 접근하게 하려면 `ALLOW`로 설정해야 한다. `DENY`로 설정하면 루트 사용자만 계정 청구 정보에 접근할 수 있다. 기본값은 `ALLOW`다."**

두 파라미터 모두 기본값을 그대로 쓰면 안 됩니다. `role-name`은 36.7에서 다룹니다. 청구 정보는 관리 계정과 재무 담당이 보는 것이 정상이므로 멤버 계정에서는 `DENY`를 기본으로 하고 필요한 계정에만 열어 줍니다.

### OU 생성과 계정 이동

```bash
# 3) 루트 ID 조회
aws organizations list-roots --profile awssec-lab \
  --query 'Roots[0].Id' --output text
# → r-exam

# 4) OU 생성
aws organizations create-organizational-unit \
  --parent-id r-exam --name Workloads --profile awssec-lab
# → ou-exam-workloads

aws organizations create-organizational-unit \
  --parent-id ou-exam-workloads --name Prod --profile awssec-lab
# → ou-exam-prod

# 5) 계정이 현재 어디에 붙어 있는지 확인 (source-parent-id가 필요하다)
aws organizations list-parents --child-id 111122223333 --profile awssec-lab

# 6) 이동
aws organizations move-account \
  --account-id 111122223333 \
  --source-parent-id r-exam \
  --destination-parent-id ou-exam-prod \
  --profile awssec-lab
# 성공 시 아무것도 출력하지 않는다

# 7) 검증 — OU 아래 계정 목록
aws organizations list-accounts-for-parent \
  --parent-id ou-exam-prod --profile awssec-lab
```

⚠️ **`move-account`는 조용합니다.** 출력이 없으니 7번 검증을 생략하지 마십시오. 계정을 옮기는 순간 **적용되는 SCP 집합이 통째로 바뀌므로**, 운영 계정의 OU 이동은 배포와 같은 급의 변경입니다(37.3).

### 콘솔 절차와 기존 계정 초대

콘솔은 **AWS Organizations → AWS 계정** 화면 하나에서 생성·초대·이동을 모두 처리하며, 계정 생성 시 역할 이름 기본값이 `OrganizationAccountAccessRole`로 채워집니다. 이미 존재하는 계정은 **초대**합니다.

```bash
# 기존 계정 초대 (관리 계정에서)
aws organizations invite-account-to-organization \
  --target Id=555555555555,Type=ACCOUNT \
  --notes "ShopMini 조직 통합 - 플랫폼팀" \
  --profile awssec-lab

# 초대받은 계정에서 수락
aws organizations accept-handshake \
  --handshake-id h-exampleid2222 --profile dev-admin
```

🔴 **초대로 들어온 계정에는 `OrganizationAccountAccessRole`이 자동으로 생기지 않습니다.** 생성 계정과 초대 계정의 가장 큰 실무 차이입니다. 편입 후 별도로 크로스 계정 역할을 만들지 않으면 "조직에는 들어왔는데 아무도 관리할 수 없는 계정"이 됩니다.

### ⚠️ 계정은 만들기는 쉽고 없애기는 어렵다

> 📖 같은 장: **"조직에서 계정을 제거하면 그 계정을 독립(standalone) 계정으로 운영할 수 있다. 방금 만든 계정을 지금 제거하려고 하면, 그 계정의 가입(sign-in) 절차가 완료되지 않았다는 오류가 발생한다. 독립 계정으로 동작하려면 루트 사용자로 로그인해 신용카드 정보를 포함한 추가 정보를 제공해야 한다."**

**조직에서 빼는 것(remove)** 과 **계정을 없애는 것(close)** 은 다른 일이고, 둘 다 마찰이 있습니다.

| 동작 | CLI | 결과 | 마찰 |
|---|---|---|---|
| 조직에서 제거 | `remove-account-from-organization` | 독립 계정으로 남음 | 결제 수단·연락처 등 가입 정보가 완비되어야 함 |
| 멤버가 스스로 탈퇴 | `leave-organization` | 독립 계정으로 남음 | 위와 동일 |
| 계정 폐쇄 | `close-account` | 계정 종료 | 30일 롤링 기준 폐쇄 가능 수 제한, 폐쇄 후 유예 기간 존재 |

> 💡 **원서 이후 변경** — 원서 집필 시점에는 계정 폐쇄를 루트 사용자로 콘솔에서만 할 수 있었습니다. 현재는 관리 계정에서 `aws organizations close-account --account-id <id>`로 멤버 계정을 닫을 수 있습니다. 다만 **롤링 30일 기간에 닫을 수 있는 멤버 계정 수에 제한**이 있고(멤버 계정의 10%, 최소 10개), 폐쇄한 계정은 **유예 기간(약 90일)** 동안 복구 가능한 상태로 남습니다.

🔴 **그래서 계정 생성 전에 다음 세 가지를 먼저 정하십시오.**

1. **루트 이메일 규칙.** 계정마다 **전역적으로 유일한 이메일**이 필요합니다. 개인 이메일을 쓰면 퇴사와 함께 계정 통제권이 사라집니다. `aws-shopmini-prod@example.com` 형태로 **회사 도메인 + 배포 리스트**를 쓰고 수신자를 최소 2명 이상으로 유지하십시오.
2. **루트 자격 증명 처리.** 생성 직후의 계정은 루트에 비밀번호가 없어 **그 이메일 수신함만 가지면 "비밀번호 찾기"로 누구든 접근할 수 있는 상태**입니다. 즉시 비밀번호를 재설정하고 MFA를 등록한 뒤 봉인하십시오(5장). 이메일 수신함 보안이 곧 계정 보안입니다.
3. **폐기 경로.** 실습·PoC 계정은 처음부터 Sandbox OU에 넣고, 폐기 대신 **Suspended OU로 이동해 전면 거부 SCP를 씌우는 것**을 기본 경로로 삼습니다(36.4). 닫는 것보다 빠르고 되돌릴 수 있습니다.

## 36.4 🔴 권장 OU 구조

### 원칙: OU는 조직도가 아니라 정책 경계다

가장 흔한 실패는 OU를 회사 조직도대로 만드는 것입니다. `플랫폼팀`·`커머스팀`·`데이터팀` — 자연스러워 보이지만 **1년 뒤 조직 개편과 함께 무너집니다.** 더 근본적으로, OU에 붙이는 것은 SCP이고 SCP는 **"이 계정들에는 같은 제약이 걸려야 한다"** 는 뜻입니다. 커머스팀과 데이터팀에 같은 제약이 걸려야 할 이유는 없습니다.

🔴 **OU를 나누는 기준은 딱 하나입니다: "여기 들어오는 계정에는 어떤 가드레일이 걸리는가."** 답이 같으면 같은 OU, 다르면 다른 OU입니다. 팀 소속은 태그로 표현하십시오.

원서는 **"우리는 OU 안에 하위 OU를 만들 수 있다"** 고, 앞서 인용한 대로 **"루트를 포함해 5단계까지"** 중첩 가능하다고 밝힙니다. 그러나 깊이보다 **폭**을 쓰십시오. 3단계를 넘어가면 어떤 SCP가 실제로 적용되는지 사람이 추적하지 못합니다.

### 권장 구조

```
Root (o-exampleorgid)
│   ※ Root에 붙인 SCP는 관리 계정을 제외한 모든 계정에 적용된다
│
├── Security                      [보안 기능 계정 — 삭제·중지 금지 가드레일]
│     ├── 로그 아카이브  777788889999
│     └── 보안 도구      444455556666
│
├── Infrastructure                [공유 인프라 — 네트워크·백업·공유 서비스]
│     ├── 네트워크 계정 (TGW, Resolver, 공유 VPC 소유)
│     └── 백업 계정     (에어갭 볼트)
│
├── Workloads                     [실제 서비스가 도는 곳]
│     ├── Prod         111122223333   [변경 통제 최강, 수동 접근 최소]
│     └── NonProd      555555555555   [개발·테스트, 비용 상한, 데이터 반입 금지]
│
├── Sandbox                       [자유 실험 — 조직 네트워크와 연결 금지]
│
├── PolicyStaging                 [새 SCP를 실계정에 붙이기 전 검증]
│
├── Suspended                     [폐기 예정 — 전면 거부 SCP]
│
└── Exceptions                    [예외 승인된 계정 — 기간 한정, 재심사 필수]
```

### 각 OU의 정책 성격

| OU | 여기 들어오는 계정 | 걸어야 할 가드레일 성격 | 대표 SCP(37.2) |
|---|---|---|---|
| **Security** | 로그 아카이브, 보안 도구 | 보안 기능 자체를 지키는 것. 다른 어떤 OU보다 **삭제·비활성화 금지**가 강함 | CloudTrail 중지 금지, 로그 버킷·볼트 삭제 금지, GuardDuty/Config 비활성화 금지 |
| **Infrastructure** | 네트워크, 백업, 공유 서비스 | 여러 계정이 의존하는 자산의 **변경 통제**. 워크로드 계정이 여기 리소스를 못 바꾸게 | TGW·Resolver 규칙 변경 제한, RAM 외부 공유 금지, 백업 볼트 잠금 해제 금지 |
| **Workloads/Prod** | 운영 워크로드 | 리전·서비스 허용 목록, 암호화 강제, 루트 사용 차단, IAM 사용자 생성 억제 | 미승인 리전 차단, 암호화 없는 리소스 생성 차단, 루트 액션 거부 |
| **Workloads/NonProd** | 개발·테스트 | Prod와 **같은 뼈대에 비용 통제 추가**. 운영 데이터 반입 금지 | 리전 제한, 고비용 인스턴스 유형 제한, 운영 계정으로의 크로스 계정 접근 금지 |
| **Sandbox** | 개인 실험 | 조직 네트워크에서 **격리**. 나가는 연결만 허용, 조직 공유 리소스 접근 금지 | VPC 피어링·TGW 연결 금지, 데이터 이전 서비스 제한, 예산 알림 강제 |
| **PolicyStaging** | 검증용 빈 계정 | 새 SCP를 여기 먼저 붙여 부작용을 본다 | (검증 대상 SCP 자체) |
| **Suspended** | 폐기·격리 대상 | **전면 거부**. 로그 조회 외 아무것도 못 함 | 모든 액션 Deny(+ 조사용 읽기 예외) |
| **Exceptions** | 승인된 예외 | 상위 가드레일 중 일부만 완화. **만료일 필수** | 완화 대상 SCP를 제외한 나머지 유지 |

### 🔴 반드시 지킬 세 가지

1. **Root에는 최소한만 붙인다.** Root SCP는 관리 계정을 제외한 전부에 걸리므로 실수하면 조직 전체가 멈춥니다(37.3). "어떤 계정에서도 절대 안 되는 것"만 — 루트 사용자 액션 차단, CloudTrail 중지 금지 정도입니다.
2. **Suspended OU를 먼저 만들어 둔다.** 계정을 격리해야 하는 날 OU와 SCP를 그 자리에서 만들 시간은 없습니다. 32장의 락다운 절차가 **"계정을 Suspended OU로 옮긴다"** 한 줄로 끝나야 합니다.
3. **Exceptions OU의 모든 계정에 만료일 태그를 붙인다.** 만료일이 없는 예외는 영구 예외가 되고, 1년 뒤 아무도 왜 예외인지 모릅니다.

⚠️ OU 없이 계정을 Root 바로 아래 평평하게 두면 새 계정마다 SCP를 개별 부착해야 하고, 반드시 빠뜨린 계정에서 사고가 납니다. **계정이 OU 없이 존재하는 상태 자체가 결함입니다.**

## 36.5 🔴 필수 코어 계정

OU가 정책의 틀이라면 코어 계정은 **기능의 틀**입니다. ShopMini의 다섯 계정은 각각 "다른 계정에 있으면 안 되는 이유"를 하나씩 갖고 있습니다.

### 계정별 정의

| 계정 | ID | 존재 이유(한 문장) | 접근 주체 | 주 사용 빈도 |
|---|---|---|---|---|
| **관리(Management)** | `123456789012` | 조직·SCP·결제의 유일한 통제점 | 브레이크 글래스 2인 + 감사자 읽기 | **월 단위** — 거의 안 들어감 |
| **로그 아카이브** | `777788889999` | 운영 계정 관리자가 지울 수 없는 증거 보관소 | 사람 접근 없음. 서비스 쓰기 + 감사자 읽기 | 사실상 0 |
| **보안 도구** | `444455556666` | 감시자가 피감시자와 같은 계정에 있으면 안 됨 | 보안팀(Identity Center) | 일 단위 |
| **운영(Prod)** | `111122223333` | ShopMini 서비스 | 파이프라인 역할 + 온콜 임시 승격 | 배포마다 |
| **개발(Dev)** | `555555555555` | 운영과 쿼터·IAM·데이터를 분리 | 개발팀(Identity Center) | 상시 |

### 계정별 "안에 두는 것 / 두지 않는 것"

| 계정 | 🔴 반드시 안에 있어야 할 것 | 절대 두지 말아야 할 것 |
|---|---|---|
| 관리 `123456789012` | 조직 루트·OU·SCP, 통합 결제, Identity Center 인스턴스 활성화, 계정 팩토리, 조직 트레일의 **설정**(로그 목적지는 아님) | 워크로드, 개발자 접근, 데이터, IAM 사용자, 애플리케이션 파이프라인, 도메인·인증서 등 운영 자산 |

### 로그와 백업이 반드시 밖에 있어야 하는 이유

> 📖 *Practical Cloud Security* 2판 7장은 사고 대응 계획을 논하면서 이렇게 경고합니다. **"백업을 별도의 클라우드 계정에, 운영 데이터와는 분리된 관리자 자격 증명으로 두어야 한다. 공격자가 운영 데이터뿐 아니라 운영 계정에서 접근 가능했던 모든 백업까지 지워 버린 문서화된 사례들이 있다."**

같은 문장이 1판 7장에도 거의 동일하게 나옵니다(1판 "separate account", 2판 "separate cloud account"). 저자가 두 판에 걸쳐 반복했다는 사실 자체가 이 항목의 무게입니다. **"접근 가능했던 모든 백업"** 이 핵심입니다 — 백업이 같은 계정에 있으면 계정 하나의 침해가 곧 복구 능력의 상실입니다. 로그도 같은 논리이며, 그래서 로그 아카이브 계정에서 **운영 계정의 어떤 역할도 삭제 권한을 갖지 않아야** 합니다.

### 네트워크 계정과 백업 계정

다섯 계정은 **최소 구성**입니다. 조직이 커지면 둘이 더 필요해집니다.

**네트워크 계정** — Transit Gateway, Route 53 Resolver 규칙·엔드포인트, 이그레스 검사 VPC, 공유 서브넷을 소유합니다. 21.3대로 TGW를 운영 계정에 두면 운영 계정 관리자가 조직 전체의 라우팅 도메인을 바꿀 수 있습니다. 네트워크 계정에 두고 RAM으로 공유하면(36.8) 각 계정은 **자기 VPC를 붙일 수만 있고 라우팅 테이블은 못 건드립니다.**

**백업 계정** — AWS Backup 목적지 볼트, 볼트 잠금, 백업 전용 KMS 키를 소유합니다(17.4). 소규모 조직은 로그 아카이브 계정을 겸용해도 되지만, 로그와 백업은 보존 정책·접근 주체·복구 절차가 달라 규모가 커지면 반드시 갈라집니다.

| 신호 | 추가할 계정 |
|---|---|
| VPC가 3개를 넘고 계정 간 통신이 필요해짐 | 네트워크 |
| 백업 보존 요구가 규제로 명시됨 / 볼트 잠금 컴플라이언스 모드 필요 | 백업 |
| 사고 조사에 격리된 작업 공간이 반복적으로 필요 | 포렌식(32.3 — 보안 도구 계정에서 분리) |
| 공통 AMI·컨테이너 이미지·Service Catalog 제품을 여러 계정이 씀 | 공유 서비스 |

⚠️ **계정을 늘릴 때마다 "이 계정을 잊어버리면 어떻게 되는가"를 물으십시오.** 새 계정이 조직 트레일·GuardDuty·Config·Security Hub·백업 정책에 자동 편입되지 않는다면 계정이 아니라 **사각지대를 늘린 것**입니다. 자동 편입을 만드는 방법이 37.9입니다.

## 36.6 ⚠️ 관리 계정에서 워크로드를 돌리지 마라

### 사고 시나리오

ShopMini 팀은 계정 하나로 시작해 그 계정에 VPC와 서비스를 올렸습니다. 1년 뒤 계정을 나누기로 하고 결제 정보와 도메인이 이미 있다는 이유로 **그 계정에서** `create-organization`을 실행했습니다. 계정을 세 개 더 만들어 새 워크로드를 옮겼지만 원래 있던 운영 서비스는 DB 마이그레이션이 부담스러워 **"나중에"** 남겨 두었고, 개발자들은 여전히 그 계정에 로그인해 배포했습니다.

여섯 달 뒤 한 개발자의 액세스 키가 공개 저장소에 커밋되었습니다. 관리 계정 IAM 사용자의 키였고 배포를 위해 넓은 권한을 갖고 있었습니다.

1. 공격자가 그 키로 관리 계정에 접근했습니다. **관리 계정에는 SCP가 적용되지 않으므로**, 조직 전체에 걸어 둔 "미승인 리전 차단"도 "CloudTrail 중지 금지"도 이 계정에서는 아무 효과가 없었습니다.
2. 공격자는 `organizations:ListAccounts`로 조직의 전 계정 목록을 얻었습니다.
3. 각 멤버 계정의 `OrganizationAccountAccessRole`을 차례로 맡았습니다. 이 역할은 계정 생성 시 자동으로 만들어졌고, **관리 계정 전체를 신뢰**하며, `AdministratorAccess`를 갖고 있었습니다.
4. 조직 전체가 한 자격 증명으로 넘어갔습니다. 로그 아카이브 계정을 분리해 둔 것만이 유일하게 작동한 통제였습니다.

### 원인

**첫째, 관리 계정에는 SCP가 적용되지 않습니다.** 버그가 아니라 설계입니다 — 적용된다면 잘못된 SCP 하나로 그것을 되돌릴 수단까지 잠겨 조직이 영구히 복구 불능이 됩니다. 그 대가로 **관리 계정은 조직에서 유일하게 예방적 가드레일이 없는 계정**이 됩니다(37.3).

**둘째, 관리 계정은 조직 전체에 대한 권한을 갖습니다.** 계정 생성·이동·SCP 부착·`OrganizationAccountAccessRole` 인수가 전부 여기서 됩니다. 관리 계정 침해는 계정 하나의 침해가 아니라 **조직의 침해**입니다.

**셋째, 그 계정에 워크로드가 있어 사람이 매일 로그인했습니다.** 앞의 둘은 AWS의 성질이지만 이것은 설계 선택이고, 그래서 실제 원인입니다. 관리 계정에 로그인할 이유가 없으면 자격 증명이 유출될 표면 자체가 없습니다.

### 🔴 올바른 구성

**1. 관리 계정에서만 해야 하는 일 — 이 목록 밖의 일은 하지 않는다**

- 조직·OU 생성 및 계정 이동
- SCP·태그 정책·백업 정책의 생성과 부착
- 계정 생성(`create-account`)과 초대
- 신뢰할 수 있는 액세스 활성화, **위임 관리자 등록**
- IAM Identity Center 인스턴스 활성화(일상 운영은 위임 관리자로)
- 통합 결제·예산·비용 배분 태그 활성화
- 조직 CloudTrail 트레일의 **생성 설정**(로그는 로그 계정 버킷으로)

공통점은 **드물게, 계획해서, 승인받고 하는 일**이라는 것 — 매일 할 일이 하나도 없습니다.

**2. 관리 계정에 두지 않는다**

| 두지 않을 것 | 옮길 곳 |
|---|---|
| 애플리케이션 워크로드, VPC, 데이터베이스 | Workloads OU 계정 |
| 개발자·운영자 상시 접근 | Identity Center로 멤버 계정에 직접 |
| CI/CD 파이프라인, 아티팩트 저장소 | 공유 서비스 또는 각 워크로드 계정 |
| 보안 도구 운영(GuardDuty 콘솔 작업 등) | 보안 도구 계정(위임 관리자) |
| CloudTrail 로그의 저장 버킷 | 로그 아카이브 계정 |
| IAM 사용자와 장기 액세스 키 | 없앤다. 브레이크 글래스 루트만 남긴다(5장, 32.4) |
| 도메인·ACM 인증서 등 운영 자산 | 해당 워크로드 계정 또는 네트워크 계정 |

**3. 관리 계정 접근을 통제한다** — SCP를 못 쓰는 계정이므로 통제는 전부 **탐지·절차**입니다.

- 루트에 하드웨어 MFA 등록 후 봉인. 비밀번호와 MFA 기기 보관자를 분리합니다(32.4).
- IAM 사용자 0개. 사람 접근은 Identity Center 임시 자격 증명만.
- **모든 콘솔 로그인과 `AssumeRole`에 알람.** 정상이면 월 1회 미만이어야 하고, 자주 울린다면 그 자체가 설계 결함 신호입니다.
- 감사자에게는 `ReadOnlyAccess` + `ViewOnlyAccess` 수준만.

**4. 이미 관리 계정에 워크로드가 있다면**

**워크로드를 새 계정으로 옮기십시오.** 관리 계정 자체를 바꾸는 것은 원서 인용대로 불가능합니다.

1. 새 워크로드 계정을 만들고 IaC로 인프라를 재구축합니다(1.5).
2. 데이터를 이전합니다 — RDS는 스냅샷 공유 또는 DMS, S3는 크로스 계정 복제.
3. DNS로 트래픽을 전환합니다.
4. 관리 계정에 남은 리소스를 **전량** 삭제합니다. "혹시 몰라 남겨둔" 것이 다음 사고의 진입점입니다.
5. 관리 계정의 IAM 사용자·액세스 키를 삭제하고 로그인 알람을 켭니다.

⚠️ **이전이 당장 불가능하다면 최소한 셋만은 하십시오.** 장기 액세스 키 제거, 관리 계정 API 호출 전량에 대한 CloudTrail 알람, 멤버 계정 `OrganizationAccountAccessRole` 신뢰 정책 좁히기(36.7). 이 셋이 앞 시나리오의 2·3·4단계를 끊습니다.

## 36.7 계정 간 역할 전환 🧪

크로스 계정 `AssumeRole`의 메커니즘(신뢰 정책, `ExternalId`, MFA 조건, 프로파일 체이닝)은 8.5~8.6에서 다뤘습니다. 여기서는 **조직 관점** — Organizations가 자동으로 만드는 접근 경로와 그 통제 — 만 봅니다.

### 🔴 자동 생성되는 역할의 정확한 성질

> 📖 *AWS Security Cookbook* 1장은 이 역할을 이렇게 설명합니다. **"이 역할은 멤버 계정에 대한 관리자 권한을 제공하고 관리 계정을 신뢰한다. 이것은 관리 계정의 사용자들이 이 역할을 맡을 수 있다는 뜻이다 — 관리 계정 관리자가 그것을 허용하는 한. (…) 자식 계정에 로그인해 `OrganizationAccountAccessRole` 역할을 확인해 보면 `AdministratorAccess` 정책이 붙어 있는 것을 볼 수 있다. `Trust relationships` 섹션을 확인해 보면 우리 관리 계정이 신뢰할 수 있는 엔터티로 추가되어 있다."**

정책 언어로 옮기면 이렇게 됩니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::123456789012:root" },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

⚠️ **조건이 하나도 없습니다.** `:root`는 "관리 계정 전체"를 뜻하므로(8.5), **관리 계정에서 `sts:AssumeRole`을 얻은 누구든** 이 역할로 멤버 계정의 관리자가 됩니다. MFA 요구도, 소스 IP 제한도, 시간 제한도 없습니다.

결정적으로 — **이 경로는 SCP로 막을 수 없습니다.** SCP는 요청 주체가 속한 계정에 적용되는데 이 호출의 주체는 관리 계정에 있고, 관리 계정에는 SCP가 적용되지 않기 때문입니다. 멤버 계정에 아무리 강한 SCP를 걸어도 소용없습니다. **통제 지점은 그 역할의 신뢰 정책과 탐지뿐입니다.**

### 🔴 통제 방법 네 가지

**① 신뢰 정책을 좁힌다 — 가장 효과적**

멤버 계정에서 `:root`를 특정 역할 ARN으로 바꾸고 MFA를 요구합니다.

```bash
cat > oaar-trust.json <<'JSON'
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "BreakGlassFromMgmtOnly",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::123456789012:role/OrgBreakGlassAdmin"
      },
      "Action": "sts:AssumeRole",
      "Condition": {
        "Bool": { "aws:MultiFactorAuthPresent": "true" },
        "NumericLessThan": { "aws:MultiFactorAuthAge": "3600" }
      }
    }
  ]
}
JSON

aws iam update-assume-role-policy \
  --role-name OrganizationAccountAccessRole \
  --policy-document file://oaar-trust.json \
  --profile prod-admin
```

`aws:MultiFactorAuthAge`는 **MFA 인증 후 경과 시간(초)** 이므로 3600이면 한 시간보다 오래된 MFA 세션으로는 맡을 수 없습니다. 8.5대로 `Effect: Allow` 문에서는 `Bool`을 씁니다.

**② 역할 이름을 바꾼다** — 계정 생성 시 `--role-name`으로 조직마다 다른 이름을 써서, 공격자와 자동화 도구가 가정하는 기본 이름을 무력화합니다.

```bash
aws organizations create-account \
  --email aws-shopmini-newsvc@example.com \
  --account-name "ShopMini-NewService" \
  --role-name ShopMiniOrgBootstrapRole \
  --iam-user-access-to-billing DENY \
  --profile awssec-lab
```

⚠️ 이름 변경은 **은폐(obscurity)** 이지 통제가 아니므로 ①과 함께 써야 합니다. Control Tower 등이 기본 이름을 가정하니 사전에 의존성을 확인하십시오.

**③ 사용을 상시 감시한다** — 조직 트레일 위에 탐지 규칙을 얹습니다.

```bash
# 조직 트레일 대상 EventBridge 규칙 — OrganizationAccountAccessRole 인수 탐지
aws events put-rule \
  --name detect-org-access-role-assume \
  --event-pattern '{
    "source": ["aws.sts"],
    "detail-type": ["AWS API Call via CloudTrail"],
    "detail": {
      "eventSource": ["sts.amazonaws.com"],
      "eventName": ["AssumeRole"],
      "requestParameters": {
        "roleArn": [{ "wildcard": "*:role/OrganizationAccountAccessRole" }]
      }
    }
  }' \
  --profile security-admin

aws events put-targets \
  --rule detect-org-access-role-assume \
  --targets Id=sec-alert,Arn=arn:aws:sns:ap-northeast-2:444455556666:security-critical \
  --profile security-admin
```

🔴 **이 알람은 "울리면 즉시 확인"이 아니라 "울리면 사고로 간주"입니다.** 정상 운영에서 이 역할이 쓰일 일은 브레이크 글래스밖에 없어야 하기 때문입니다.

**④ 필요 없으면 삭제한다 — 단, 조건이 있다**

일상 접근이 전부 Identity Center로 옮겨졌고 각 계정에 별도 관리 경로가 있다면 삭제할 수 있습니다.

```bash
aws iam detach-role-policy \
  --role-name OrganizationAccountAccessRole \
  --policy-arn arn:aws:iam::aws:policy/AdministratorAccess \
  --profile prod-admin

aws iam delete-role \
  --role-name OrganizationAccountAccessRole \
  --profile prod-admin
```

⚠️ 이 역할은 멤버 계정의 IAM이 망가졌을 때의 **마지막 복구 경로**이기도 합니다. 삭제 후 Identity Center 권한 집합까지 깨지면 남는 길은 루트 로그인뿐이므로, 실무적으로는 **삭제보다 ①의 좁히기 + ③의 알람 조합**을 권합니다.

### 조직에서의 일상 접근 경로

> 📖 같은 장: **"실제 현장에서 관리자들은 서로 다른 자식 계정에 서로 다른 역할(Dev, Testing, Prod 등)을 만들고, 관리 계정의 사용자 그룹에 그 계정들의 해당 역할에 대한 접근 권한을 부여할 것이다."**

이 구조를 IAM 사용자 그룹 대신 **Identity Center 권한 집합(Permission Set)** 으로 구현한 것이 현재 표준입니다(9장).

| 경로 | 자격 증명 | 용도 | 권장도 |
|---|---|---|---|
| Identity Center 권한 집합 | 임시(SSO) | **모든 일상 접근** | 🔴 기본 |
| 목적별 크로스 계정 역할(8.5) | 임시(AssumeRole) | 파이프라인, 감사자, 특정 자동화 | 필요 시 |
| `OrganizationAccountAccessRole` | 임시(AssumeRole) | 브레이크 글래스, 신규 계정 부트스트랩 | ⚠️ 예외만 |
| 계정별 IAM 사용자 | 장기 키 | — | 쓰지 않는다(6장) |

🔴 **판단 기준은 하나입니다 — "이 접근이 조직의 어느 계정을 볼 수 있는가."** `OrganizationAccountAccessRole`은 답이 "전부"라 일상에서 쓰면 안 되고, Identity Center 권한 집합은 "할당된 계정만"이라 일상에서 씁니다.

## 36.8 AWS Resource Access Manager로 리소스 공유 🧪

계정을 나누면 반대 문제가 생깁니다. **나눈 계정들이 같은 인프라를 써야 할 때**입니다. 계정마다 Transit Gateway와 Resolver 엔드포인트를 만들면 비용도 관리 부담도 계정 수만큼 늘어납니다.

> 📖 *AWS Security Cookbook* 10장 「Setting up and using AWS Resource Access Manager」: **"AWS RAM은 AWS 리소스를 다른 AWS 계정이나 우리 AWS Organization 안에서 안전하게 공유할 수 있게 해준다. 공유할 수 있는 리소스에는 AWS Transit Gateway, 서브넷, AWS License Manager 구성, Amazon Route 53 Resolver 규칙 등이 포함된다."**

> 📖 같은 장은 실습 말미에 당시의 전체 목록을 열거합니다. **"우리는 RAM으로 서브넷 리소스 유형을 공유했다. 현재 사용 가능한 리소스 유형 목록은 다음과 같다: Aurora DB 클러스터, 용량 예약, CodeBuild 프로젝트, CodeBuild 리포트 그룹, 전용 호스트, Image Builder 컴포넌트, Image Builder 이미지 레시피, Image Builder 이미지, 라이선스 구성, Resolver 규칙, 트래픽 미러 대상, Transit Gateway."**

> 💡 **원서 이후 변경** — 지원 리소스 유형은 계속 늘고 있습니다. VPC 접두사 목록(prefix list), Network Firewall 규칙 그룹, AWS Private CA, VPC IPAM 풀, Outposts, Glue 데이터 카탈로그, Systems Manager 문서 등이 추가되었습니다. 현재 목록은 `aws ram list-resource-types`로 확인하십시오.

### 🔴 1단계 — 조직 내 공유 활성화

> 📖 같은 장: **"조직 내 공유를 활성화하지 않으면, 우리가 추가하는 계정들은 우리 조직의 일부이더라도 외부 계정으로 간주되며, 이는 오류를 일으킬 수 있다."** 그리고 **"AWS Organizations와의 공유는 관리 계정에서만 활성화할 수 있다."**

```bash
# 관리 계정에서 한 번만 — 조직 내 공유 활성화
aws ram enable-sharing-with-aws-organization --profile awssec-lab

# 전제: RAM에 대한 신뢰할 수 있는 액세스가 켜져 있어야 한다 (36.2)
aws organizations enable-aws-service-access \
  --service-principal ram.amazonaws.com --profile awssec-lab
```

### 2단계 — 공유 VPC 패턴: 네트워크 계정이 서브넷을 소유한다

**네트워크 계정이 VPC와 서브넷을 소유하고, 워크로드 계정은 그 서브넷 안에 자기 리소스를 만듭니다.** 아래 네트워크 계정 ID `222233334444`는 CANON 밖의 보조 더미값입니다.

```
─── 네트워크 계정 (소유자) ────────────────────────────────
   VPC shopmini-shared 10.20.0.0/16
     ├ Private-App 10.20.10.0/24 (2a) ─┐
     └ Private-App 10.20.11.0/24 (2c) ─┤  RAM 공유
   라우팅 테이블 · NAT · TGW 연결 · 플로우 로그  ← 네트워크팀만 변경
──────────────────────────────────────┼───────────────────
─── 운영 계정 111122223333 (참여자) ───┘
   공유받은 서브넷 안에 ECS 태스크 · ALB · RDS 생성
   서브넷 자체는 수정·삭제 불가. 다른 참여자의 리소스는 보이지 않음
```

```bash
# 네트워크 계정에서 실행 — 서브넷 2개를 Workloads/Prod OU에 공유
aws ram create-resource-share \
  --name shopmini-prod-subnets \
  --resource-arns \
    arn:aws:ec2:ap-northeast-2:222233334444:subnet/subnet-0aa1prodapp2a \
    arn:aws:ec2:ap-northeast-2:222233334444:subnet/subnet-0bb2prodapp2c \
  --principals arn:aws:organizations::123456789012:ou/o-exampleorgid/ou-exam-prod \
  --no-allow-external-principals \
  --tags key=Project,value=awssec-lab key=Chapter,value=ch36 \
  --profile network-admin

# 공유 현황 확인
aws ram get-resource-shares --resource-owner SELF --profile network-admin

# 참여자 계정에서 확인
aws ram get-resource-shares --resource-owner OTHER-ACCOUNTS --profile prod-admin
aws ec2 describe-subnets \
  --filters Name=owner-id,Values=222233334444 --profile prod-admin
```

이 패턴의 가치는 **책임이 갈라진다**는 점입니다.

| 항목 | 소유자(네트워크 계정) | 참여자(워크로드 계정) |
|---|---|---|
| 서브넷 생성·수정·삭제 | 가능 | 불가 |
| 라우팅 테이블·NACL 변경 | 가능 | 불가 |
| VPC 플로우 로그 설정 | 가능 | 불가 |
| 서브넷 안에 EC2·ECS·RDS 생성 | 가능 | 가능 |
| 자기가 만든 리소스의 보안 그룹 | 가능 | 가능 |
| **다른 참여자의 리소스 조회** | 일부 가능 | 불가 |

**네트워크 통제는 중앙에, 워크로드 자유도는 각 팀에** 남습니다. 21.3에서 TGW를 네트워크 계정에 두라고 한 것과 같은 논리입니다.

### ⚠️ 3단계 — 공유 범위를 조직/OU로 제한하라

`--principals`에는 세 종류를 넣을 수 있고 위험도가 완전히 다릅니다.

| 프린시펄 형태 | 예시 | 위험도 |
|---|---|---|
| 조직 전체 | `arn:aws:organizations::123456789012:organization/o-exampleorgid` | 낮음 (다만 광범위) |
| OU | `arn:aws:organizations::123456789012:ou/o-exampleorgid/ou-exam-prod` | 🔴 **권장** |
| 계정 ID | `111122223333` | 낮음(조직 내) / ⚠️ 높음(조직 밖) |

🔴 **`--no-allow-external-principals`를 기본값으로 삼으십시오.** 반대(`--allow-external-principals`)이면 조직 밖 계정 ID도 프린시펄이 될 수 있어, 계정 ID를 한 자리 틀리게 입력하면 **모르는 타인의 계정에 서브넷이 공유됩니다.**

```bash
# 기존 공유의 외부 프린시펄 허용 여부 점검 — 정기 감사 항목
aws ram get-resource-shares --resource-owner SELF \
  --query 'resourceShares[?allowExternalPrincipals==`true`].[name,resourceShareArn]' \
  --output table --profile network-admin
```

리소스 기반 정책에는 `aws:PrincipalOrgID`를 함께 겁니다(7.4). RAM 공유와 리소스 정책은 다른 층이라, RAM으로 좁혀도 리소스 정책이 열려 있으면 의미가 없습니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "OrgOnlyAccess",
      "Effect": "Allow",
      "Principal": "*",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::shopmini-shared-artifacts/*",
      "Condition": {
        "StringEquals": { "aws:PrincipalOrgID": "o-exampleorgid" }
      }
    }
  ]
}
```

⚠️ 3.4대로 이 조건에 `aws:PrincipalIsAWSService` 가드를 함께 두지 않으면 로그 전달·복제 같은 서비스 주체 호출이 조용히 끊깁니다.

### ⚠️ 4단계 — 공유받은 리소스의 책임 경계는 모호하다

RAM의 가장 큰 함정은 기술이 아니라 **책임 소재**입니다.

**사고 시나리오.** 감사에서 "공유 서브넷의 아웃바운드가 왜 열려 있느냐"는 지적이 나왔습니다. 네트워크팀은 "서브넷만 줬으니 워크로드팀 책임", 워크로드팀은 "라우팅과 NAT는 우리가 못 건드린다"고 합니다. **둘 다 맞고, 그래서 아무도 고치지 않습니다.**

**원인.** RAM 공유는 **제어권**은 나누지만 **책임**은 나누지 않습니다. 로그도 갈라집니다 — 플로우 로그는 소유자 계정에, API 호출 CloudTrail은 각 참여자 계정에 남아 조사 시 두 계정을 조인해야 합니다.

🔴 **올바른 구성.**

1. **공유마다 RACI를 문서로 고정한다.** "서브넷 라우팅 = 네트워크팀 / 보안 그룹 = 워크로드팀 / NACL = 네트워크팀"처럼 리소스 유형별 담당을 적습니다.
2. **공유 리소스에 `Owner`·`SharedWith`·`ReviewDate` 태그를 태그 정책으로 강제한다**(37.8).
3. **소유자 계정의 플로우 로그를 로그 아카이브 계정으로 보낸다.** 참여자 계정의 CloudTrail과 같은 곳에 모여야 조인이 됩니다(29.9).
4. **분기마다 `get-resource-shares`로 전체 목록을 뽑아 미사용 공유를 회수한다.** 쓰이지 않는 공유는 잊혀진 접근 경로입니다.
5. **Sandbox OU에는 공유하지 않는다.** 실험 계정이 공유 네트워크에 붙는 순간 격리가 사라집니다(36.4).

## 🔴 필수 구성 체크리스트

**조직 기반**
- [ ] 조직을 `--feature-set ALL`로 생성했다
- [ ] 관리 계정에 워크로드가 없다(있다면 이전 계획에 착수했다)
- [ ] 신뢰할 수 있는 액세스를 필요한 서비스에만 열고 문서화했다
- [ ] 보안 도구 계정(`444455556666`)을 탐지 서비스 위임 관리자로 등록했다

**계정 관리**
- [ ] 루트 이메일이 **회사 도메인 + 수신자 2인 이상 배포 리스트**다
- [ ] 계정 생성 직후 루트 비밀번호 재설정 + MFA 등록 + 봉인을 수행한다
- [ ] `--iam-user-access-to-billing DENY`를 기본값으로 쓴다
- [ ] 초대로 편입한 계정에 관리 경로를 별도로 만들었다
- [ ] Root 바로 아래에 계정이 하나도 없다(전부 OU 소속)

**OU**
- [ ] Security / Infrastructure / Workloads(Prod·NonProd) / Sandbox / Suspended OU가 있다
- [ ] **Suspended OU와 전면 거부 SCP를 사고 전에 미리 만들어 두었다**
- [ ] Exceptions OU의 모든 계정에 만료일 태그가 있다
- [ ] OU 깊이가 3단계를 넘지 않는다

**관리 계정 보호**
- [ ] IAM 사용자와 장기 액세스 키가 0개다
- [ ] 루트에 하드웨어 MFA가 등록되고 보관자가 분리되어 있다
- [ ] 콘솔 로그인·`AssumeRole`에 알람이 걸려 있고 월 1회 미만 울린다

**역할 전환**
- [ ] 모든 멤버 계정의 `OrganizationAccountAccessRole` 신뢰 정책에 **MFA 조건과 특정 역할 ARN**이 있다
- [ ] 이 역할의 `AssumeRole`에 즉시 알람이 걸려 있다
- [ ] 일상 접근은 **전부** Identity Center 권한 집합으로 이뤄진다

**RAM**
- [ ] 조직 내 공유가 활성화되어 있다(`enable-sharing-with-aws-organization`)
- [ ] 모든 공유가 `allowExternalPrincipals=false`다
- [ ] 프린시펄이 계정 ID 나열이 아니라 **OU ARN**이다
- [ ] Sandbox OU에 공유된 리소스가 없다
- [ ] 분기 1회 공유 목록을 검토하고 미사용 공유를 회수한다

| 관리 계정에 개발자 로그인을 허용 | SCP가 없는 계정에서 자격 증명이 유출 → 조직 전체 침해 | Identity Center로 멤버 계정에 직접 (36.6) |
| 관리 계정에 CloudTrail 로그 버킷을 둔다 | 관리 계정 침해가 곧 증거 소실 | 로그 아카이브 계정 `777788889999` (36.5, 29.9) |
| OU를 조직도대로 만든다 | 조직 개편마다 재설계, 같은 SCP를 붙일 근거가 없음 | 가드레일 기준으로 묶고 팀은 태그로 (36.4) |
| Root SCP에 세부 규칙을 잔뜩 넣는다 | 한 번 실수하면 조직 전체가 마비 | Root에는 절대 금지 항목만 (36.4, 37.3) |
| 사고가 난 뒤에 Suspended OU를 만든다 | 격리까지 수십 분~수 시간 소요 | OU와 전면 거부 SCP를 미리 준비 (36.4, 32.2) |
| 계정 루트 이메일을 담당자 개인 메일로 | 퇴사·부재 시 계정 통제권 상실 | 회사 도메인 배포 리스트, 수신자 2인 이상 (36.3) |
| 계정 생성 후 루트를 방치 | 이메일 수신함만 있으면 비밀번호 재설정으로 접근 가능 | 즉시 비밀번호 재설정 + MFA + 봉인 (36.3, 5장) |
| 실습 계정을 대량 생성 후 한꺼번에 폐쇄 | 30일 롤링 폐쇄 한도에 걸려 정리 불가 | Sandbox OU + Suspended OU 이동으로 관리 (36.3) |
| 초대 계정에 관리 경로를 안 만든다 | 조직에는 있으나 아무도 관리할 수 없는 계정 | 편입 직후 크로스 계정 역할 생성 (36.3) |
| `OrganizationAccountAccessRole`을 기본값 그대로 방치 | 관리 계정 주체 누구나 조건 없이 전 계정 관리자 | 신뢰 정책에 역할 ARN + MFA 조건, 사용 알람 (36.7) |
| 이 역할의 위험을 SCP로 막으려 한다 | SCP는 관리 계정 주체에 적용되지 않아 무효 | 통제 지점은 **신뢰 정책과 탐지** (36.7, 37.3) |
| RAM 조직 내 공유를 켜지 않고 계정 ID로 공유 | 조직 내 계정도 외부로 취급되어 오류 | 📖 관리 계정에서 `enable-sharing-with-aws-organization` (36.8) |
| RAM 공유에 외부 프린시펄을 허용해 둔다 | 계정 ID 오타 하나로 타인에게 리소스 공유 | `--no-allow-external-principals` 기본 (36.8) |
| 공유 리소스의 책임 주체를 정하지 않는다 | 소유자·참여자 모두 "우리 책임 아니다" | 공유별 RACI 문서화 + 태그 강제 (36.8, 37.8) |
| 미사용 RAM 공유를 방치 | 잊혀진 접근 경로가 남음 | 분기 1회 전량 검토·회수 (36.8) |

## 다음 장 예고

구조는 세웠습니다. 조직이 있고, OU가 있고, 코어 계정이 제자리에 있고, 계정 사이의 접근 경로가 명시적으로 정해졌습니다. 그런데 이 구조에는 아직 **강제력이 없습니다.** OU에 계정을 넣었을 뿐 그 OU가 무엇을 금지하는지는 비어 있어서, 개발 계정에서 도쿄 리전에 인스턴스를 띄워도 운영 계정 관리자가 CloudTrail을 꺼도 막히지 않습니다.

37장은 그 빈칸을 채웁니다. **SCP 설계 전략**(허용 목록 vs 거부 목록), **반드시 넣어야 할 SCP 10가지**, ⚠️ **SCP의 함정** — 이 장에서 두 번 말한 "관리 계정에는 적용되지 않는다"가 왜 그렇게 설계되었는지, 잘못 적용된 SCP 하나가 어떻게 전 계정을 마비시키는지. 이어 Control Tower 랜딩 존, Config 적합성 팩, 태그·백업 정책, 그리고 **신규 계정 베이스라인 자동화**로 마무리합니다.
