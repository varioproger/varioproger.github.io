# 15장. S3 보안 완전 정복

> **이 장에서 다루는 것**
> - S3 접근 통제의 **4중 구조** 🔴 — BPA → 버킷 정책 → IAM → ACL, "어느 하나라도 Deny면 거부"
> - **계정 수준 퍼블릭 액세스 차단** 🔴 과 예외가 필요할 때의 안전한 처리
> - ACL 사용 중단과 **Object Ownership = Bucket owner enforced** 🧪
> - 버킷 정책 실전 🧪 — `aws:SecureTransport`, `aws:SourceVpce`, `aws:PrincipalOrgID`, 비암호화 업로드 거부
> - 크로스 계정의 **객체 소유권 함정** ⚠️, 사전 서명 URL, 암호화 3종, 버전 관리·MFA Delete
> - **객체 잠금(Object Lock)** 🔴, CRR, 액세스 로깅과 CloudTrail 데이터 이벤트
>
> **선행 지식**: 7장(IAM 정책 평가), 8장(역할과 임시 자격 증명), 12장(데이터 분류), 13장(KMS)
> **난이도**: ★★☆

공개적으로 알려진 대규모 클라우드 데이터 유출을 유형별로 묶으면 압도적으로 많은 것이 **"객체 스토리지를 실수로 공개해 둔 것"** 입니다. 침투도 익스플로잇도 없습니다. 누군가 체크박스 하나를 해제했고, 몇 달 뒤 누군가 그것을 찾아냈을 뿐입니다.

> 📖 *Practical Cloud Security* 2판 3장. **"대부분의 오브젝트 스토리지는 (…) 여러 계층의 접근 통제를 제공한다. 오브젝트 스토리지 버킷 정책이 공개 접근으로 설정되어 발생한 주목할 만한 데이터 유출이 많았으므로, 오브젝트 스토리지 자산과 각각의 접근 통제 정책을 추적하는 것이 매우 중요하다."**

> 📖 *Practical Cloud Security* 2판 2장. **"Amazon S3 버킷을 퍼블릭 액세스에 열어두어 발생한 데이터 유출 사례는 아주 많다. 만약 이것들이 회사 방화벽 뒤에 있는, 사내 누구에게나 열린 파일 공유였다면 인터넷의 공격자나 연구자에게 발견되지 않았을 수도 있다. (…) 인터넷에 노출되어 있을 때 공격 가능성은 더 높아진다."**

핵심은 **노출 반경**입니다. 잘못된 사내 파일 공유는 사내에서 끝나지만, 잘못된 버킷 설정 하나는 곧바로 전 세계에 열립니다.

> 💡 **원서 이후 변경 — 이 장 전체를 읽기 전에 반드시 알아야 할 3가지**
>
> *AWS Security Cookbook* 은 2020년 책이고 S3 보안의 기본값은 그 이후 크게 바뀌었습니다. 다음 셋은 이 장 전체의 전제입니다.
>
> 1. **2023년 4월부터 새 버킷은 BPA 4개 설정이 기본 활성화**됩니다. 원서가 "Block all public access의 두 항목을 해제하고 시작하라"고 안내하는 것은 2020년 기준이며, 지금 그 해제는 **의도적인 위험 행위**입니다.
> 2. **2023년 4월부터 새 버킷은 Object Ownership이 `Bucket owner enforced`로 설정되어 ACL이 비활성화**됩니다. 원서 첫 레시피 "ACL로 모두에게 READ 부여하기"는 기본 설정 버킷에서 **`AccessControlListNotSupported` 오류로 실패**합니다.
> 3. **2023년 1월부터 모든 신규 객체는 별도 설정 없이 SSE-S3(AES-256)로 기본 암호화**됩니다. 질문은 "암호화를 켰는가"가 아니라 "**누가 통제하는 키로** 암호화되는가"입니다.
>
> 세 변경은 **기본값만** 바꿨습니다. **기존 버킷은 자동으로 바뀌지 않습니다** — 2023년 이전 버킷은 여전히 ACL이 켜져 있고 BPA가 꺼져 있을 수 있습니다. 15.12가 필요한 이유입니다.

## 15.1 S3 접근 통제의 4중 구조 🔴

S3 접근 판정이 어려운 이유는 **판정에 참여하는 장치가 넷(실제로는 다섯)** 이고 성격이 각각 다르기 때문입니다.

> 📖 *AWS Security Cookbook* 2장 「Comparing ACLs, bucket policies, and IAM policies」. **"ACL은 버킷·객체·그 ACL에 대한 기본적인 읽기/쓰기 권한만 제공한다. (…) ACL은 AWS 계정과 사전 정의된 그룹에만 접근을 부여할 수 있고, IAM 사용자에게는 권한을 부여할 수 없다. (…) ACL은 권한을 부여만 할 수 있다. 버킷 정책과 IAM 정책은 명시적으로 접근을 거부할 수 있다. ACL은 조건부로 허용하거나 거부할 수 없다. (…) ACL은 내부적으로 XML 문서로 표현되고, 버킷 정책과 IAM 정책은 JSON 문서로 표현된다."**

여기에 원서가 다루지 않는 **계정 수준 BPA**와 **SCP**를 얹으면 실제 평가 그림이 나옵니다.

```
요청:  GetObject  s3://shopmini-uploads/orders/2026-09.csv
       (프린시펄: arn:aws:iam::111122223333:role/shopmini-app)
   │
   ▼
[0] 계정 수준 퍼블릭 액세스 차단 (s3control PublicAccessBlock)
       └ 퍼블릭 부여 자체를 무효화·차단. 아래 어떤 층이 "*"에게 Allow해도 소용없음
   │
   ▼
[1] SCP / RCP  (조직 차원 권한 상한 — 4장)
       └ 여기서 벗어난 권한은 계정 안에서 무엇을 하든 부여되지 않음
   │
   ▼
[2] 버킷 정책 (리소스 기반)          ── 명시적 Deny ⇒ 즉시 거부
   │
   ▼
[3] IAM 정책 / 권한 경계 / 세션 정책  ── 명시적 Deny ⇒ 즉시 거부
   │
   ▼
[4] ACL (버킷 ACL / 객체 ACL)
       └ Object Ownership = Bucket owner enforced 이면 이 층은 존재하지 않음
   │
   ▼
최종 판정
```

판정 규칙은 두 줄입니다.

- **어느 한 층이라도 명시적 Deny를 내면, 다른 모든 층의 Allow와 무관하게 거부됩니다.** (Deny 우선)
- 명시적 Deny가 없을 때, **[2]·[3]·[4] 중 최소 한 곳에서 Allow가 나와야** 허용됩니다.

계정 경계가 개입하면 규칙이 하나 더 붙습니다.

> 📖 *AWS Security Cookbook* 2장. **"ACL, 버킷 정책, IAM 정책을 섞어 쓸 수 있다. 버킷과 사용자가 같은 계정 안에 있다면 모든 정책은 동시에 평가된다."**

즉 **같은 계정**이면 세 장치 중 하나만 Allow해도 통과하지만, **다른 계정**이면 **요청자 계정의 IAM 정책과 버킷 소유 계정의 리소스 정책 양쪽 모두에서 Allow**가 나와야 합니다.

> 📖 *AWS Security Cookbook* 2장. **"계정 A가 (…) 계정 B의 사용자 testuser에게 버킷 정책으로 PutObject 권한을 직접 부여했다. testuser는 계정 B에서 추가 권한 없이 업로드할 수 있는가? 아니다. 계정 B 안의 사용자 정책으로도 PutObject 권한을 부여받아야 한다."** 위임의 한계도 못 박습니다. **"계정 B의 관리자가 계정 A로부터 받은 것보다 더 많은 권한을 위임할 수 있는가? 오류가 나지는 않지만 아무 효과가 없다. 권한은 계정 A에서 다시 평가되기 때문이다."**

### 🔴 이렇게 구성하라

| 층 | 무엇에 쓰는가 | 무엇에 쓰지 않는가 |
|---|---|---|
| [0] 계정 BPA | **모든 계정, 예외 없이 4개 전부 ON** (15.2) | 예외를 만들기 위해 끄는 용도 |
| [1] SCP/RCP | 조직 차원의 "절대 금지" — BPA 해제 금지, 비암호화 거부 | 일상적 권한 부여 |
| [2] 버킷 정책 | **데이터 경계 강제** — TLS, VPCE, OrgID, 암호화 (15.4) | 개인별 세밀 권한 |
| [3] IAM 정책 | **누가 무엇을 할 수 있는가** — 역할별 최소 권한 | 익명·크로스 계정 부여 |
| [4] ACL | **쓰지 않는다** — `Bucket owner enforced`로 끈다 (15.3) | 모든 것 |

**하지 않으면**: 감사에서 "이 객체에 누가 접근할 수 있는가"에 답할 수 없습니다. 버킷 정책은 팀 A가, IAM은 팀 B가, ACL은 3년 전 퇴사자가 설정한 상태에서 유효 권한 계산은 불가능에 가깝습니다. **층을 줄이는 것 자체가 통제**입니다.

## 15.2 퍼블릭 액세스 차단(Block Public Access)을 계정 수준에서 켜라 🔴⚠️

### 사고 시나리오

ShopMini 마케팅팀이 캠페인 랜딩 이미지를 빠르게 배포하려고 `shopmini-assets` 버킷에서 "Block all public access"를 해제하고 `Principal: "*"` 버킷 정책을 붙였습니다. 캠페인은 2주 만에 끝났고 정책은 남았습니다.

그 사이 데이터팀이 **같은 버킷의 `exports/` 프리픽스**에 일별 주문 집계 CSV를 떨어뜨리기 시작했습니다. 버킷 정책의 리소스는 `arn:aws:s3:::shopmini-assets/*` 였습니다. 여덟 달 뒤, 인터넷 스캐너를 돌리던 연구자가 `exports/` 아래 CSV 목록을 받아갑니다.

### 원인

1. **한 버킷을 두 용도로 썼습니다.** 공개 자산과 비공개 데이터가 한 네임스페이스에 있으면 `/*` 하나로 전부 열립니다.
2. **예외를 "끄기"로 처리했습니다.** BPA는 스위치가 아니라 **안전망**입니다. 안전망을 걷어내 예외를 만들면, 예외의 수명이 끝나도 안전망은 돌아오지 않습니다.
3. **계정 수준 BPA가 없었습니다.** 버킷 수준만 관리하면 버킷을 만드는 사람 수만큼 사고 확률이 곱해집니다.

### 올바른 구성

BPA는 네 개의 독립 스위치이고 각각이 막는 것이 다릅니다.

| 설정 | 막는 것 | 이미 있는 퍼블릭 설정은? |
|---|---|---|
| `BlockPublicAcls` | 퍼블릭 ACL을 **새로 설정**하는 것, 퍼블릭 ACL이 붙은 객체 업로드 | 기존 것은 남아 있고 그대로 동작 |
| `IgnorePublicAcls` | 버킷·객체에 **이미 붙어 있는** 퍼블릭 ACL을 **무시** | 무시됨(사실상 무력화) |
| `BlockPublicPolicy` | 퍼블릭 부여가 포함된 **버킷 정책을 새로 넣는 것** | 기존 정책은 남아 있고 그대로 동작 |
| `RestrictPublicBuckets` | 퍼블릭 정책이 이미 있어도 **익명·크로스 계정 접근을 거부** (같은 계정 프린시펄과 AWS 서비스 프린시펄만 허용) | 차단됨 |

앞의 둘(`Block*`)은 **미래를 막고**, 뒤의 둘(`Ignore*`, `Restrict*`)은 **과거를 무력화**합니다. **넷을 다 켜야 의미가 있습니다.**

계정 수준 설정은 그 계정의 **모든 버킷**에 우선 적용되므로 여기부터 켭니다.

```bash
# 계정 수준 BPA — 운영 계정(111122223333)
aws s3control put-public-access-block \
  --account-id 111122223333 \
  --public-access-block-configuration \
      BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true \
  --profile awssec-lab

# 확인
aws s3control get-public-access-block \
  --account-id 111122223333 --profile awssec-lab
```

버킷 수준도 함께 켭니다(계정 수준이 꺼지는 사고 대비).

```bash
aws s3api put-public-access-block \
  --bucket shopmini-uploads \
  --public-access-block-configuration \
      BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true \
  --profile awssec-lab
```

그리고 **누구도 끄지 못하게** SCP로 잠급니다(4장). 브레이크 글래스 역할만 예외입니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyDisablingBlockPublicAccess",
      "Effect": "Deny",
      "Action": [
        "s3:PutAccountPublicAccessBlock",
        "s3:PutBucketPublicAccessBlock",
        "s3:DeleteBucketPolicy",
        "s3:PutBucketAcl"
      ],
      "Resource": "*",
      "Condition": {
        "ArnNotLike": {
          "aws:PrincipalArn": "arn:aws:iam::*:role/OrgBreakGlassAdmin"
        }
      }
    }
  ]
}
```

### 그래도 공개가 필요하다면 — BPA를 끄지 않고 공개하는 법

"진짜로 공개해야 하는 정적 자산"은 존재합니다. 하지만 **버킷 공개가 유일한 방법이 아닙니다.** `shopmini-assets`는 CloudFront 오리진이므로, 정답은 **버킷은 비공개로 두고 CloudFront에만 열어주는 것**입니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowCloudFrontOACOnly",
      "Effect": "Allow",
      "Principal": { "Service": "cloudfront.amazonaws.com" },
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::shopmini-assets/*",
      "Condition": {
        "StringEquals": {
          "AWS:SourceArn": "arn:aws:cloudfront::111122223333:distribution/E1SHOPMINIDIST"
        }
      }
    }
  ]
}
```

이 정책은 **퍼블릭 정책이 아닙니다.** `Principal`이 `*`가 아니라 CloudFront 서비스 프린시펄이고 `AWS:SourceArn`으로 특정 배포에 한정되므로 `BlockPublicPolicy`가 켜져 있어도 적용됩니다. 버킷은 인터넷에서 열거·직접 조회가 불가능해 프리픽스 유출이 차단되고, CloudFront에서 WAF·지리 차단·서명된 URL·액세스 로그를 붙일 수 있으며(23.7), 공개 범위가 **배포 단위**로 명시되어 감사 가능해집니다.

> **⚠️ 같이 고칠 것**: 사고의 절반은 "한 버킷 두 용도"였습니다. **공개 자산 버킷과 데이터 버킷은 분리**하고 가능하면 **계정도 분리**합니다. `shopmini-assets`와 `shopmini-uploads`가 애초에 둘로 나뉜 이유입니다.

## 15.3 ACL의 이해와 (사실상) 사용 중단 🧪

ACL이 무엇이었는지는 알아야 합니다. **끄기 위해서**, 그리고 **2023년 이전 버킷을 정리하려면**입니다.

> 📖 *AWS Security Cookbook* 2장. **"ACL은 버킷/객체에 다음 권한을 부여할 수 있다. READ: 버킷의 객체 목록 조회, 객체와 메타데이터 읽기. WRITE: 버킷에 대한 객체 생성·덮어쓰기·삭제(객체에는 적용되지 않음). READ_ACP: 버킷 또는 객체의 ACL 읽기. WRITE_ACP: 버킷 또는 객체의 ACL 쓰기. FULL_CONTROL: 앞의 모든 권한."** 사전 정의 그룹 URI도 명시합니다 — `.../groups/global/AuthenticatedUsers`, `.../groups/global/AllUsers`, `.../groups/s3/LogDelivery`.

위험의 정체는 여기 있습니다. **`AllUsers` 그룹에 READ를 주면 그것이 곧 "전 세계 공개"** 이고, 이 부여는 **객체 하나하나에 개별적으로** 붙습니다. 버킷 정책을 아무리 잘 써도 3년 전 스크립트가 `--acl public-read`로 올린 객체 12만 개는 그와 무관하게 공개입니다. 원서 다음 레시피가 그 동작을 그대로 보여줍니다 — 그렇게 올린 객체를 권한이 전혀 없는 `testuser`가 다운로드합니다.

> 💡 **원서에는 이렇게 나오지만, 지금은 이렇게 한다**
> 원서 2장 첫 레시피는 "**ACL 관련 Block all public access 두 항목의 체크를 해제하라**"고 지시하고 콘솔 ACL 탭에서 `Everyone`에게 `List objects`를 부여합니다. **이 실습은 재현하지 마십시오.** 기본값 버킷은 ACL이 비활성화되어 `put-bucket-acl`이 실패하며, 재현하려면 BPA를 끄고 ACL을 되살리는 두 단계 후퇴가 필요합니다. 개념은 위 인용으로 충분합니다.

### Object Ownership 3가지 설정

| 설정 | ACL | 크로스 계정 업로드 객체의 소유자 | 권장 |
|---|---|---|---|
| `ObjectWriter` (구 기본값) | 활성 | **업로드한 계정** | × 소유권 함정의 근원 (15.5) |
| `BucketOwnerPreferred` | 활성 | `bucket-owner-full-control` ACL로 올리면 버킷 소유자 | △ 전환 중간 단계로만 |
| `BucketOwnerEnforced` | **비활성** | **항상 버킷 소유자** | 🔴 **이것을 쓴다** |

`BucketOwnerEnforced`로 설정하면 ACL 층 자체가 사라집니다. 모든 ACL은 무시되고 접근 판정은 **버킷 정책과 IAM 정책만으로** 이뤄집니다. 15.1의 4층이 3층이 되고, 그만큼 유효 권한을 사람이 추론할 수 있습니다.

```bash
# ACL 끄기 (Bucket owner enforced)
aws s3api put-bucket-ownership-controls \
  --bucket shopmini-uploads \
  --ownership-controls 'Rules=[{ObjectOwnership=BucketOwnerEnforced}]' \
  --profile awssec-lab

# 확인
aws s3api get-bucket-ownership-controls \
  --bucket shopmini-uploads --profile awssec-lab
```

**전환 전 확인할 것**: 기존 버킷을 무작정 끄면 ACL에 의존하던 접근이 **조용히 끊깁니다**.

1. **서버 액세스 로그 / CloudTrail 데이터 이벤트**를 며칠 수집해 어떤 프린시펄이 이 버킷을 쓰는지 목록화합니다(15.11).
2. `BucketOwnerPreferred`로 먼저 바꿔 소유권 문제를 해소하고 접근이 유지되는지 관찰합니다.
3. 접근 주체마다 정책으로 **동등한 권한을 명시 부여**한 뒤 `BucketOwnerEnforced`로 넘어갑니다.
4. 신규 버킷은 처음부터 `BucketOwnerEnforced` — **기본값을 그대로 두면 됩니다.**

**ACL을 끄면 깨지는 것**: 서버 액세스 로깅의 대상 버킷은 전통적으로 `LogDelivery` 그룹 ACL로 쓰기 권한을 받았습니다. ACL을 끈 버킷을 로그 대상으로 쓰려면 **버킷 정책**으로 `logging.s3.amazonaws.com`에 권한을 줘야 합니다(15.11).

## 15.4 버킷 정책 작성 🧪

> 📖 *AWS Security Cookbook* 2장. **"버킷 정책 문장은 Sid, Principal, Effect, Action, Resource, Condition 요소를 가질 수 있다. Principal을 제외한 나머지는 IAM 정책과 동일하다."** 리소스 표기도 못 박습니다. **"버킷 ARN은 `arn:aws:s3:::bucket_name` 형식이어야 한다. 객체 리소스는 `arn:aws:s3:::bucket_name/key_name` 형식으로 표현된다. 버킷 안의 모든 객체를 나타내려면 `arn:aws:s3:::bucket_name/*` 을 쓸 수 있다."**

이 구분이 가장 흔한 오류의 원인이고, 원서도 그 오류를 보여줍니다.

> 📖 *AWS Security Cookbook* 2장. **"리소스를 객체 작업(예: `s3:GetObject`) 없이 `arn:aws:s3:::awsseccookbook/*` 로 바꾸면, 해당 액션이 어떤 리소스에도 적용되지 않는다는 오류가 발생한다. 버킷에 프리픽스를 붙이면 객체 작업으로 간주되는데, 우리는 아직 객체 작업을 정의하지 않았기 때문이다."** 프린시펄에도 제약이 있습니다. **"S3 버킷 정책에는 IAM 그룹을 프린시펄로 지정할 수 없다. 사용자 대신 그룹을 넣으면 `Invalid principal in policy` 오류가 발생한다."**

**`s3:ListBucket`은 버킷 ARN**(`/*` 없음), **객체 액션은 객체 ARN**(`/*` 있음)입니다. 둘을 한 문장에 몰아넣으면 반드시 한쪽이 무력화됩니다.

### 🔴 모든 데이터 버킷에 기본으로 붙일 4개 문장

아래 **가드레일 정책**은 **권한을 부여하지 않고 거부만 합니다.** 권한 부여는 IAM 정책이 하고, 버킷 정책은 "어떤 경로로 오든 이 선을 넘지 못한다"는 경계를 담당합니다.

```json
{
  "Version": "2012-10-17",
  "Id": "ShopMiniUploadsGuardrail",
  "Statement": [
    {
      "Sid": "DenyInsecureTransport",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::shopmini-uploads",
        "arn:aws:s3:::shopmini-uploads/*"
      ],
      "Condition": {
        "Bool": { "aws:SecureTransport": "false" }
      }
    },
    {
      "Sid": "DenyOutsideOrganization",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::shopmini-uploads",
        "arn:aws:s3:::shopmini-uploads/*"
      ],
      "Condition": {
        "StringNotEqualsIfExists": {
          "aws:PrincipalOrgID": "o-exampleorgid"
        },
        "BoolIfExists": {
          "aws:PrincipalIsAWSService": "false"
        }
      }
    },
    {
      "Sid": "DenyOutsideVpcEndpoint",
      "Effect": "Deny",
      "Principal": "*",
      "Action": [
        "s3:GetObject",
        "s3:PutObject",
        "s3:DeleteObject",
        "s3:ListBucket"
      ],
      "Resource": [
        "arn:aws:s3:::shopmini-uploads",
        "arn:aws:s3:::shopmini-uploads/*"
      ],
      "Condition": {
        "StringNotEqualsIfExists": {
          "aws:SourceVpce": "vpce-0a1b2c3d4e5f67890"
        },
        "BoolIfExists": {
          "aws:PrincipalIsAWSService": "false"
        }
      }
    },
    {
      "Sid": "DenyWrongKmsKey",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::shopmini-uploads/*",
      "Condition": {
        "StringNotEqualsIfExists": {
          "s3:x-amz-server-side-encryption-aws-kms-key-id":
            "arn:aws:kms:ap-northeast-2:111122223333:key/1a2b3c4d-5e6f-4a3b-8c9d-0e1f2a3b4c5d"
        }
      }
    }
  ]
}
```

| Sid | 조건 키 | 막는 것 | 주의 |
|---|---|---|---|
| `DenyInsecureTransport` | `aws:SecureTransport` | 평문 HTTP 요청 전부 | 원서도 동일 패턴 제시 |
| `DenyOutsideOrganization` | `aws:PrincipalOrgID` | 조직 밖 계정·익명 접근 | 서비스 프린시펄은 이 키가 없으므로 `IfExists` + `PrincipalIsAWSService` 예외 필수 |
| `DenyOutsideVpcEndpoint` | `aws:SourceVpce` | 인터넷 경로 접근(자격 증명이 유출돼도 VPC 밖에선 못 씀) | 콘솔 접근도 막히므로 예외 역할 설계 필요 |
| `DenyWrongKmsKey` | `s3:x-amz-server-side-encryption-aws-kms-key-id` | 다른 KMS 키로 올리는 것 | 헤더 없는 요청은 막지 않음(아래 설명) |

원서도 `aws:SecureTransport` 패턴과 S3 고유 조건 키 목록을 제시합니다.

> 📖 *AWS Security Cookbook* 2장. **"기본적으로 S3는 데이터에 대한 HTTP와 HTTPS 접근을 모두 허용한다. HTTPS는 다음 조건 요소를 가진 버킷 정책으로 강제할 수 있다: `"Condition": {"Bool": {"aws:SecureTransport": "false"}}`. 이 조건이 있으면 HTTPS가 아닌 모든 요청은 실패한다."**

> 📖 *AWS Security Cookbook* 2장. **"정책의 조건에서 사용할 수 있는 S3 전용 조건 키에는 다음이 있다: `s3:x-amz-acl`, `s3:x-amz-copy-source`, `s3:x-amz-metadata-directive`, `s3:x-amz-server-side-encryption`, `s3:VersionId`, `s3:LocationConstraint`, `s3:delimiter`, `s3:max-keys`, `s3:prefix`, `s3:x-amz-server-side-encryption-aws-kms-key-id`, `s3:ExistingObjectTag/<tag-key>`, `s3:RequestObjectTagKeys`, `s3:RequestObjectTag/<tag-key>`, `s3:object-lock-remaining-retention-days`, `s3:object-lock-mode`, `s3:object-lock-retain-until-date`, `s3:object-lock-legal-hold`."**

### ⚠️ 암호화 강제 조건의 함정

비암호화 업로드를 거부할 때 흔히 쓰는 문장은 다음 둘입니다.

```json
{
  "Sid": "DenyNonKmsEncryptionHeader",
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:PutObject",
  "Resource": "arn:aws:s3:::shopmini-uploads/*",
  "Condition": {
    "StringNotEquals": { "s3:x-amz-server-side-encryption": "aws:kms" }
  }
}
```

```json
{
  "Sid": "DenyMissingEncryptionHeader",
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:PutObject",
  "Resource": "arn:aws:s3:::shopmini-uploads/*",
  "Condition": {
    "Null": { "s3:x-amz-server-side-encryption": "true" }
  }
}
```

첫 번째는 **헤더가 있는데 값이 다를 때**, 두 번째는 **헤더가 아예 없을 때** 거부합니다. 조건 키는 **요청 헤더**를 평가하므로, 두 번째를 넣으면 **기본 암호화에 의존해 헤더 없이 올리는 정상 클라이언트도 실패**합니다. 즉 이 문장은 "암호화 여부"가 아니라 "**클라이언트가 암호화를 명시 선언했는가**"를 강제하는 선택입니다.

- 기본 암호화를 SSE-KMS로 설정했다면 → **두 번째는 넣지 말고** 첫 번째와 `DenyWrongKmsKey`만 씁니다.
- 클라이언트 실수를 원천 차단하려면 → 둘 다 넣되 **모든 업로드 경로가 헤더를 붙이도록 먼저 수정**합니다.

정책은 원서와 동일한 명령으로 붙입니다.

```bash
aws s3api put-bucket-policy \
  --bucket shopmini-uploads \
  --policy file://shopmini-uploads-guardrail.json \
  --profile awssec-lab
```

## 15.5 크로스 계정 접근 🧪⚠️

### 사고 시나리오

개발 계정(`555555555555`)의 배치 잡이 운영 계정(`111122223333`)의 `shopmini-uploads`에 일별 리포트를 올립니다. 6개월간 잘 돌았습니다. 그런데 운영 계정 **관리자**가 그 파일을 열려니 `Access Denied`가 납니다. **버킷 소유자가 자기 버킷 안의 객체를 못 읽는** 상황입니다.

### 원인 — 객체 소유권

> 📖 *AWS Security Cookbook* 2장. **"계정 A의 사용자가 계정 B의 버킷(계정 B 소유)에 객체를 업로드하면, 계정 B는 버킷 소유자임에도 그 객체에 대해 아무런 접근 권한을 갖지 못한다. 다만 계정 A는 `bucket-owner-read` 또는 `bucket-owner-full-control` 캐너드 ACL을 사용해 (…) 권한을 부여할 수 있다."** 원서는 이 상태의 기묘함까지 확인합니다. **"버킷 소유자 계정의 관리자 사용자가 그 객체를 읽을 수 있는가? 아니다. (…) 삭제할 수 있는가? 그렇다."**

**읽지는 못하는데 지울 수는 있는** 상태입니다. 버킷 권한(삭제)과 객체 ACL(읽기)이 분리된 탓입니다.

### 원서의 해법 — 버킷 정책으로 캐너드 ACL 강제

> 📖 *AWS Security Cookbook* 2장. **"ACL로는 '계정 B가 항상 계정 A에 권한을 부여해야 한다'와 같은 제약을 강제할 방법이 없다. 그러나 이는 버킷 정책으로 강제할 수 있다."**

`s3:x-amz-acl` 조건이 그 방법입니다.

```json
{
  "Version": "2012-10-17",
  "Id": "LegacyCrossAccountPut",
  "Statement": [
    {
      "Sid": "AllowPutOnlyWithBucketOwnerFullControl",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::555555555555:role/shopmini-report-writer"
      },
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::shopmini-uploads/reports/*",
      "Condition": {
        "StringEquals": { "s3:x-amz-acl": "bucket-owner-full-control" }
      }
    }
  ]
}
```

원서는 상대 계정에 필요한 권한도 명시합니다. **"`s3:PutObjectAcl` 액션은 나중에 캐너드 ACL을 사용하기 위해 필요하다."** 업로드 쪽 IAM 정책에 `s3:PutObject`와 `s3:PutObjectAcl`이 **둘 다** 있어야 하고 명령마다 `--acl bucket-owner-full-control`이 필요합니다. **하나라도 빠지면 조용히 소유권이 어긋납니다.**

### 🔴 지금의 근본 해법 — Object Ownership

> 💡 **원서 이후 변경** — 위의 캐너드 ACL 강제는 2020년 기준의 최선이었고 지금은 **필요 없습니다.** 15.3의 `BucketOwnerEnforced` 설정 한 줄이면 **업로더가 무엇을 하든 모든 객체의 소유자는 버킷 소유자**가 됩니다. `s3:PutObjectAcl` 권한도, `--acl` 플래그도, `s3:x-amz-acl` 조건도 전부 사라집니다.

전환 후 크로스 계정 정책은 조건 없이 단순해집니다.

```json
{
  "Version": "2012-10-17",
  "Id": "CrossAccountPutModern",
  "Statement": [
    {
      "Sid": "AllowDataAccountReportUpload",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::555555555555:role/shopmini-report-writer"
      },
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::shopmini-uploads/reports/*"
    }
  ]
}
```

| 항목 | 원서(2020) 방식 | 지금 방식 |
|---|---|---|
| 객체 소유자 | 업로드한 계정 | **항상 버킷 소유자** |
| 업로더 IAM에 필요한 권한 | `s3:PutObject` + `s3:PutObjectAcl` | `s3:PutObject` |
| 업로드 명령 | `--acl bucket-owner-full-control` 필수 | 플래그 불필요 |
| 버킷 정책 조건 | `s3:x-amz-acl` 강제 | 불필요 |
| 실수했을 때 | **조용히** 소유권 어긋남 | 발생하지 않음 |

15.1의 원칙은 여전히 유효합니다. **크로스 계정은 양쪽 모두에서 Allow가 필요합니다.** 버킷 정책만 고치고 상대 계정 IAM 정책을 빼먹으면 아무 일도 일어나지 않습니다.

또한 원서가 제시한 세 번째 방식 — **역할 수임(AssumeRole)** — 이 대개 더 낫습니다.

> 📖 *AWS Security Cookbook* 2장. **"계정 A의 관리자가 계정 A의 S3 리소스에 필요한 권한을 가진 역할을 만든다. 그 역할은 계정 B를 신뢰 주체로 하는 신뢰 관계를 갖는다. (…) 계정 B의 사용자는 그 역할을 수임해 계정 A의 S3 리소스에 접근할 수 있다."**

역할 수임이면 **모든 접근이 계정 A의 CloudTrail에 역할 세션으로 기록**되고, 세션 태그·`ExternalId`·세션 정책 같은 8장의 도구를 쓸 수 있습니다. **버킷 정책에 상대 계정 ARN을 나열하는 방식은 대상이 늘수록 관리 불가능해집니다.**

## 15.6 사전 서명 URL(Pre-signed URL) 🧪

사전 서명 URL은 **자격 증명이 없는 사람에게 특정 객체에 대한 시간 제한 접근을 주는** 장치입니다. 버킷을 열지 않고도 "이 파일만, 5분간, 이 사람에게" 줄 수 있습니다. 다만 편리함이 곧 위험입니다 — URL 자체가 인증 수단이므로 그 문자열을 가진 누구든 객체에 접근합니다. 원서는 CLI와 Python 두 방식을 시연합니다.

```bash
# 원서 레시피(CLI). 현재 CLI의 옵션 이름은 --expires-in (초, 기본 3600, 최대 604800)
aws s3 presign s3://shopmini-uploads/reports/2026-09.csv \
  --expires-in 300 \
  --profile awssec-lab
```

```python
import boto3

boto3.setup_default_session(profile_name='awssec-lab')
s3_client = boto3.client('s3', region_name='ap-northeast-2')

url = s3_client.generate_presigned_url(
    'get_object',
    Params={'Bucket': 'shopmini-uploads', 'Key': 'reports/2026-09.csv'},
    ExpiresIn=300,
)
print(url)
```

`aws s3 presign`은 GET만 지원하므로 업로드용 URL은 SDK로 만듭니다. 업로드에는 **크기·콘텐츠 타입 조건을 서버가 강제할 수 있는** `generate_presigned_post`가 더 안전합니다. 단순 PUT 서명 URL은 어떤 크기의 무엇을 올리든 막을 수 없어, 업로드 창구가 그대로 무료 파일 서버가 되는 사고로 이어집니다.

```python
post = s3_client.generate_presigned_post(
    Bucket='shopmini-uploads',
    Key='inbox/${filename}',
    Fields={'x-amz-server-side-encryption': 'aws:kms'},
    Conditions=[
        {'x-amz-server-side-encryption': 'aws:kms'},
        ['content-length-range', 1, 10485760],   # 1B ~ 10MB
        ['starts-with', '$Content-Type', 'image/'],
    ],
    ExpiresIn=300,
)
```

### ⚠️ 사전 서명 URL의 4가지 함정

> 📖 *AWS Security Cookbook* 2장. **"유효한 자격 증명을 가진 누구나 사전 서명 URL을 생성할 수 있다. 그러나 그 사용자가 의도한 작업(예: `get_object`)을 수행할 권한이 없다면 그 작업은 결국 실패한다."**

결정적인 함의가 나옵니다. **URL의 권한은 URL을 만든 주체의 권한이고, 판정은 URL을 만들 때가 아니라 쓸 때 이뤄집니다.** 서명자의 권한이 회수되면 배포된 URL도 함께 죽고, 서명자의 권한이 넓으면 URL도 그만큼 넓어집니다.

| 함정 | 무슨 일이 벌어지는가 | 대응 |
|---|---|---|
| **권한 상속** | 관리자 자격으로 만든 URL은 관리자 권한으로 동작. URL을 받은 사람은 그 객체에 대해 서명자와 동등한 권한을 가짐 | URL 발급 전용 역할을 만들고 **해당 프리픽스에 대한 최소 권한만** 부여 |
| **만료 시간 오해** | IAM 사용자 장기 키로는 최대 7일. 그러나 **역할 세션(임시 자격 증명)으로 서명하면 세션 만료 시점에 URL도 무효화** — `ExpiresIn=604800`을 줘도 1시간 뒤 죽음 | Lambda·EC2 역할로 서명한다면 **세션 수명 내로** 만료를 잡거나, 짧게 발급 후 재발급 |
| **취소 불가** | 발급된 URL은 개별 폐기 수단이 없음. 유출되면 만료까지 유효 | 만료를 **분 단위로** 짧게. 긴급 시에는 서명자의 권한을 회수하거나 객체를 이동/삭제 |
| **URL 자체가 자격 증명** | 서명이 쿼리 문자열에 있어 **액세스 로그·프록시 로그·Referer 헤더·브라우저 히스토리에 그대로 남음** | 로그에서 쿼리 문자열 마스킹, 짧은 만료, 민감 객체는 CloudFront 서명된 쿠키로 대체 |

**원칙**: 사전 서명 URL은 "임시로, 한 객체를, 한 사람에게" 줄 때만 씁니다. 지속적인 공개 배포는 **CloudFront + OAC**(15.2)로, 서드파티에 대한 상시 접근은 **역할 수임**(15.5)으로 해결합니다.

## 15.7 S3 암호화 3가지 🧪

> 📖 *AWS Security Cookbook* 2장. **"서버 측 암호화는 세 가지 방식으로 할 수 있다: S3 관리형 키를 사용하는 서버 측 암호화(SSE-S3), KMS 관리형 키를 사용하는 서버 측 암호화(SSE-KMS), 고객 제공 키를 사용하는 서버 측 암호화(SSE-C)."** 그리고 **"서버 측 암호화 방식 중 SSE-S3와 SSE-KMS는 봉투 암호화(envelope encryption)를 따르지만 SSE-C는 봉투 암호화를 사용하지 않는다."**

| 항목 | SSE-S3 | SSE-KMS | SSE-C |
|---|---|---|---|
| 키 관리 주체 | AWS (전적으로) | **고객이 KMS 키 정책으로 통제** | **고객이 직접 보관·전달** |
| CLI 지정 | `--sse AES256` | `--sse aws:kms --sse-kms-key-id <id>` | `--sse-c AES256 --sse-c-key <32바이트>` |
| 봉투 암호화 | ○ | ○ | × |
| 키 정책으로 접근 거부 | × (S3 권한만이 관문) | **○ (13.4의 2차 관문)** | × |
| 감사 추적 | S3 API 로그만 | **KMS `Decrypt` 호출이 CloudTrail에 남음** | 없음(AWS가 키를 모름) |
| 키 순환 | AWS 자동 | 자동/수동 선택 (13.6) | 고객이 전량 재암호화 |
| 크로스 계정 | 별도 고려 불필요 | **키 정책에 상대 계정 추가 필요** (13.10) | 상대에게 키를 전달해야 함 — 사실상 불가 |
| CRR 복제 | 가능 | 가능(추가 설정 필요) | **복제 불가** |
| 비용 | 무료 | **KMS API 요청 비용 발생** | 무료(대신 운영 부담) |

원서는 SSE-KMS의 이점을 요약합니다. **"마스터 키와 데이터 키 생성, 마스터 키 비활성화와 순환 등 키에 대한 더 많은 통제권을 갖는다. (…) CloudTrail로 KMS API 호출을 모니터링해 더 나은 감사가 가능하다. 무료가 아니다."** SSE-C는 운영이 무겁습니다. **"고객이 데이터와 함께 키를 제공한다. S3는 이 키로 암호화하고 키를 삭제한다. 복호화할 때도 반드시 키를 제공해야 한다. (…) AWS는 HTTPS 사용을 강제한다."**

> **결론**: ShopMini 데이터 버킷은 **SSE-KMS + 고객 관리형 키(`alias/shopmini/app`)** 를 씁니다. 이유는 비용이나 알고리즘이 아니라 **13.4의 "2차 관문"** 입니다. S3 권한이 잘못 부여되어도 KMS 키 정책이 `Decrypt`를 막으면 평문은 나가지 않습니다. SSE-S3에는 이 두 번째 문이 없습니다. SSE-C는 키를 직접 배포·보관·순환해야 하고 복제도 안 되므로 규제 요구가 아니면 쓰지 않습니다.

### 🔴 기본 암호화 설정 + S3 버킷 키

> 💡 **원서 이후 변경** — 원서는 **"S3 기본 암호화는 (…) 기존 객체에는 영향이 없고 새로 업로드되는 객체에만 적용된다"** 고 설명합니다. 2023년 1월부터는 **기본 암호화가 꺼진 버킷이 없습니다.** 지금 할 일은 "켜기"가 아니라 **"SSE-S3에서 고객 관리형 KMS 키로 올리기"** 입니다. **DSSE-KMS**(이중 계층, `--sse aws:kms:dsse`)도 2023년에 추가되었습니다.

```bash
aws s3api put-bucket-encryption \
  --bucket shopmini-uploads \
  --server-side-encryption-configuration '{
    "Rules": [
      {
        "ApplyServerSideEncryptionByDefault": {
          "SSEAlgorithm": "aws:kms",
          "KMSMasterKeyID": "arn:aws:kms:ap-northeast-2:111122223333:alias/shopmini/app"
        },
        "BucketKeyEnabled": true
      }
    ]
  }' \
  --profile awssec-lab
```

`BucketKeyEnabled: true`가 **S3 버킷 키**입니다. 켜지 않으면 S3는 **객체 하나마다 KMS를 호출**합니다 — 하루 500만 객체면 KMS 요청도 500만 건입니다. 켜면 S3가 **버킷 수준 중간 키를 짧게 캐시**해 KMS 호출을 크게 줄입니다.

| 항목 | 버킷 키 OFF | 버킷 키 ON |
|---|---|---|
| KMS 요청 수 | 객체 작업 1건당 1회 | 대폭 감소(대량 워크로드에서 최대 99% 수준까지) |
| CloudTrail의 KMS 로그 | 객체 단위로 남음 | **버킷 키 갱신 시점에만 남음** |
| 암호화 강도 | 동일 | 동일 |

**⚠️ 트레이드오프**: 버킷 키는 KMS 비용을 낮추지만 **객체 단위 복호화 감사 로그의 해상도를 떨어뜨립니다.** 객체 단위 KMS 감사가 규제 요구인 버킷은 끄고, 일반 로그·자산 버킷은 켭니다.

> **13장과의 경계**: 키 정책 작성, 순환, 그랜트, `kms:ViaService`·암호화 컨텍스트는 13장에서 다룹니다. 이 절은 **S3가 그 키를 어떻게 쓰는가**만 다룹니다. `alias/shopmini/app` 키 정책에 S3 사용을 허용하는 문장이 없으면 이 절의 모든 설정은 KMS 접근 거부로 실패합니다.

## 15.8 버전 관리와 MFA Delete 🧪🔴

> 📖 *AWS Security Cookbook* 2장. **"버전 관리가 활성화된 상태에서 객체를 삭제하면, 삭제 마커(delete marker)가 그 객체의 최신 버전으로 추가된다. (…) 버전 ID를 지정해 특정 버전을 삭제할 수 있다. 버전을 삭제할 때는 삭제 마커가 삽입되지 않는다."** 그리고 **"일단 버전 관리를 활성화하면 비활성화할 수 없고 일시 중지(suspend)만 가능하다. (…) 이전 버전들은 모두 그대로 남아 있다."**

이것이 **랜섬웨어 방어의 1차 층**인 이유입니다. 공격자가 `DeleteObject`를 호출해도 원본 버전은 남고 삭제 마커만 얹힙니다. 암호화된 내용으로 덮어써도 이전 버전은 남습니다. **진짜로 지우려면 `DeleteObjectVersion`으로 버전 ID를 하나하나 지워야 합니다.**

따라서 방어의 핵심은 **`s3:DeleteObjectVersion` 권한을 거의 아무에게도 주지 않는 것**입니다.

```json
{
  "Sid": "DenyVersionDeletionExceptBreakGlass",
  "Effect": "Deny",
  "Principal": "*",
  "Action": [
    "s3:DeleteObjectVersion",
    "s3:PutBucketVersioning",
    "s3:PutLifecycleConfiguration"
  ],
  "Resource": [
    "arn:aws:s3:::shopmini-uploads",
    "arn:aws:s3:::shopmini-uploads/*"
  ],
  "Condition": {
    "ArnNotLike": {
      "aws:PrincipalArn": "arn:aws:iam::111122223333:role/DataBreakGlassAdmin"
    }
  }
}
```

`s3:PutLifecycleConfiguration`을 같이 막는 이유는 **수명 주기 규칙 한 줄("비현재 버전 1일 후 영구 삭제")로 버전 관리가 무력화**되기 때문입니다. 삭제 권한을 아무리 잠가도 수명 주기 편집 권한이 열려 있으면 소용없습니다.

### MFA Delete

> 📖 *AWS Security Cookbook* 2장. **"`versioning-configuration`은 두 개의 파라미터를 갖는다: MFA Delete의 상태를 나타내는 `MFADelete`(Enabled 또는 Disabled)와 버전 관리 상태를 나타내는 `Status`(Enabled 또는 Suspended)."** 그리고 **"MFA Delete로 버전을 보호할 수 있다. 버전 관리에 대한 MFA Delete를 켜면 버전을 삭제할 때 추가 인증 계층이 요구된다."**

```bash
# ⚠️ 이 명령은 반드시 '루트 사용자' 자격 증명으로 실행해야 한다. IAM 사용자·역할은 불가.
aws s3api put-bucket-versioning \
  --bucket shopmini-uploads \
  --versioning-configuration Status=Enabled,MFADelete=Enabled \
  --mfa "arn:aws:iam::111122223333:mfa/root-account-mfa-device 123456"
```

| MFA가 필요한 작업 | MFA가 필요 없는 작업 |
|---|---|
| **객체 버전 영구 삭제**(`DeleteObjectVersion`) | 객체 삭제(삭제 마커 생성) |
| **버전 관리 상태 변경**(중지/재활성화) | 새 버전 업로드·덮어쓰기 |
| **MFA Delete 자체 해제** | 객체 읽기 |

**⚠️ MFA Delete 도입 전에 반드시 검토할 제약 3가지**

1. **루트 자격 증명이 필요합니다.** 6장의 원칙("루트는 봉인한다")과 충돌합니다. 켜는 것도 끄는 것도 루트여야 하므로 **루트 MFA 기기 보관과 절차 문서화**가 전제입니다.
2. **수명 주기 만료 규칙을 쓸 수 없습니다.** 오래된 버전이 무한히 쌓여 **스토리지 비용이 계속 증가**합니다.
3. **자동화와 충돌합니다.** CI/CD·IaC로 버킷 설정을 관리한다면 MFA 토큰이 필요한 작업은 파이프라인에서 할 수 없습니다.

> **🔴 실무 권고**: 이 제약들 때문에 **대부분의 운영 버킷에는 MFA Delete 대신 15.9의 객체 잠금이 낫습니다.** MFA Delete는 **변경이 드문 최고 등급 버킷**에 한정합니다. 다만 "버전 관리 + `DeleteObjectVersion` 명시적 Deny"는 **모든 데이터 버킷의 기본값**이어야 합니다.

## 15.9 객체 잠금(Object Lock)과 불변 스토리지 🔴

> 📖 *AWS Security Cookbook* 2장. **"S3 객체 잠금 속성은 객체가 삭제되거나 덮어쓰이는 것을 막는 데 사용할 수 있다. 이는 WORM(Write-Once-Read-Many) 모델에 유용하다."**

버전 관리는 "지워도 되돌릴 수 있게" 하지만, 객체 잠금은 **"애초에 지울 수 없게"** 합니다. 공격자가 관리자 권한까지 탈취한 상황에서 마지막까지 남는 것은 이것뿐입니다.

### 두 가지 모드

| 항목 | 거버넌스 모드(GOVERNANCE) | 컴플라이언스 모드(COMPLIANCE) |
|---|---|---|
| 보존 기간 중 삭제 | `s3:BypassGovernanceRetention` 권한 보유자는 가능 | **불가능** |
| 보존 기간 단축 | 위 권한 보유자는 가능 | **불가능** |
| 보존 기간 연장 | 가능 | 가능 |
| **계정 루트 사용자** | 우회 가능(권한 부여 시) | **⚠️ 우회 불가** |
| **AWS 지원팀** | — | **⚠️ 해제 불가** |
| 용도 | 실수·내부 위협 방어, 운영 유연성 필요 | 규제 준수, 확정적 불변성 |

**⚠️ 컴플라이언스 모드는 되돌릴 수 없습니다.** 루트 사용자도 AWS 지원팀도 보존 기간을 앞당기거나 객체를 지울 수 없습니다. 실수로 **보존 기간 10년**을 걸고 매일 10TB를 쓰면 **10년치 스토리지 비용을 내는 것 외에 방법이 없습니다.** 다음 순서로 도입하십시오.

1. 개발 계정에서 **1일 보존**으로 동작을 검증한다.
2. 운영에 **거버넌스 모드**로 먼저 적용하고 우회 권한은 브레이크 글래스 역할에만 준다.
3. 규제 요구가 명확한 프리픽스에 한해 컴플라이언스 모드로 승격한다. **버킷 전체에 걸지 않는다.**

### 설정

객체 잠금은 **버전 관리가 전제**입니다.

```bash
# 1) 버전 관리 활성화
aws s3api put-bucket-versioning \
  --bucket shopmini-uploads \
  --versioning-configuration Status=Enabled \
  --profile awssec-lab

# 2) 객체 잠금 활성화 + 버킷 기본 보존 규칙(거버넌스 30일)
aws s3api put-object-lock-configuration \
  --bucket shopmini-uploads \
  --object-lock-configuration '{
    "ObjectLockEnabled": "Enabled",
    "Rule": {
      "DefaultRetention": { "Mode": "GOVERNANCE", "Days": 30 }
    }
  }' \
  --profile awssec-lab
```

기본 보존 규칙은 **이후 업로드되는 새 객체 버전**에만 적용됩니다. 기존 객체에는 개별로 겁니다.

```bash
# 특정 객체 버전에 컴플라이언스 모드 보존 설정
aws s3api put-object-retention \
  --bucket shopmini-uploads \
  --key audit/2026-09-evidence.json \
  --version-id 3sL4kqtJlcpXroDTDmJ0000example \
  --retention '{"Mode":"COMPLIANCE","RetainUntilDate":"2033-09-06T00:00:00Z"}' \
  --profile awssec-lab
```

### 법적 보존(Legal Hold)

보존 기간과 **독립적으로** 동작하는 별도의 잠금입니다.

| 항목 | 보존 기간(Retention) | 법적 보존(Legal Hold) |
|---|---|---|
| 만료 | 지정한 날짜에 자동 해제 | **만료 없음 — 명시적으로 풀 때까지 유지** |
| 해제 | 모드에 따라 다름 | `s3:PutObjectLegalHold` 권한으로 `OFF` 설정 |
| 용도 | 규제 보존 기간 | **소송·조사 중 증거 동결** |

```bash
aws s3api put-object-legal-hold \
  --bucket shopmini-uploads \
  --key audit/2026-09-evidence.json \
  --legal-hold Status=ON \
  --profile awssec-lab
```

보존 기간이 만료된 객체라도 법적 보존이 `ON`이면 삭제되지 않습니다. **해제 행위 자체가 CloudTrail에 기록**됩니다.

### 🔴 반드시 이렇게 구성하라

- **감사 증적·로그 아카이브 버킷**(로그 계정 `777788889999`): **컴플라이언스 모드**, 보존 기간은 규제 요구와 일치. 이 버킷의 불변성이 곧 사고 조사의 신뢰성입니다(29장).
- **운영 데이터 버킷**(`shopmini-uploads`): 버전 관리 + **거버넌스 모드**, 우회 권한은 브레이크 글래스 역할에만.
- **백업 볼트**: 17장의 AWS Backup Vault Lock과 조합. 원리는 동일합니다.
- 15.4에서 인용한 `s3:object-lock-mode`, `s3:object-lock-retain-until-date`, `s3:object-lock-remaining-retention-days`, `s3:object-lock-legal-hold`를 쓰면 "**보존 기간 30일 미만으로는 올릴 수 없다**"를 버킷 정책으로 강제할 수 있습니다.

**하지 않으면**: 관리자 자격 증명을 탈취한 공격자가 버전 삭제, 수명 주기 조작, 버킷 삭제를 차례로 실행합니다. 백업이 같은 계정에 있으면 백업도 함께 사라집니다. 객체 잠금은 **관리자 권한 탈취를 전제해도 유효한, 몇 안 되는 통제**입니다.

## 15.10 크로스 리전 복제(CRR) 🧪

> 📖 *AWS Security Cookbook* 2장. **"크로스 리전 복제의 전제 조건은 다음과 같다. 1) 원본과 대상 버킷은 버전 관리가 활성화되어 있어야 하고 서로 다른 리전에 있어야 한다. 2) 복제는 단일 대상 버킷으로만 가능하다. 3) S3가 대상 버킷에 복제할 권한을 가져야 한다."** 자동 생성 역할은 **"원본 버킷에 대한 `s3:Get*`과 `s3:ListBucket` 권한, 대상 버킷에 대한 `s3:ReplicateObject`, `s3:ReplicateDelete`, `s3:ReplicateTags`, `s3:GetObjectVersionTagging` 권한"** 을 갖습니다.

원서는 복제의 **한계**도 정직하게 나열합니다.

> 📖 *AWS Security Cookbook* 2장. **"크로스 리전 복제 활성화 이후에 추가된 객체만 복제된다. (…) SSE-C로 암호화된 객체는 현재 복제되지 않는다. SSE-KMS로 암호화된 객체를 복제하려면, S3가 객체를 복호화할 수 있도록 하나 이상의 KMS 키를 제공해야 한다. (…) 원본 버킷에서 버전을 삭제해도 대상 버킷의 버전은 삭제되지 않는다. 이는 데이터에 추가적인 보호를 제공한다."**

마지막 문장이 CRR을 **보안 통제**로 만드는 핵심이고, 원서도 크로스 계정 복제의 목적을 그렇게 설명합니다. **"다른 AWS 계정으로 객체를 복제하면, 누군가 원본 버킷에 불법적으로 접근해 데이터와 그 복제본을 삭제하는 것과 같은 상황에 대해 추가적인 보호를 제공한다."**

> 💡 **원서 이후 변경 2가지**
> 1. 원서는 **"새 스키마는 삭제 마커 복제를 지원하지 않는다"** 고 적고 있으나, 현재 V2 스키마는 규칙마다 `DeleteMarkerReplication.Status`로 선택합니다. **보안 목적이라면 반드시 `Disabled`** — 활성화하면 원본 삭제가 사본으로 전파되어 방어 효과가 사라집니다.
> 2. 원서 시점에는 활성화 이전 객체를 복제할 수 없었지만, 현재는 **S3 배치 복제(Batch Replication)** 로 소급 복제할 수 있습니다.

### 크로스 계정 복제 구성

```json
{
  "Role": "arn:aws:iam::111122223333:role/shopmini-s3-replication",
  "Rules": [
    {
      "ID": "ReplicateUploadsToLogAccount",
      "Priority": 1,
      "Status": "Enabled",
      "Filter": { "Prefix": "" },
      "DeleteMarkerReplication": { "Status": "Disabled" },
      "SourceSelectionCriteria": {
        "SseKmsEncryptedObjects": { "Status": "Enabled" }
      },
      "Destination": {
        "Bucket": "arn:aws:s3:::shopmini-uploads-dr",
        "Account": "777788889999",
        "StorageClass": "STANDARD_IA",
        "AccessControlTranslation": { "Owner": "Destination" },
        "EncryptionConfiguration": {
          "ReplicaKmsKeyID": "arn:aws:kms:ap-northeast-1:777788889999:alias/shopmini/dr"
        }
      }
    }
  ]
}
```

```bash
aws s3api put-bucket-replication \
  --bucket shopmini-uploads \
  --replication-configuration file://crr-config.json \
  --profile awssec-lab
```

대상 계정 버킷 정책은 원서와 동일한 구조입니다.

```json
{
  "Version": "2012-10-17",
  "Id": "AllowReplicationFromProd",
  "Statement": [
    {
      "Sid": "AllowReplicationInbound",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::111122223333:role/shopmini-s3-replication"
      },
      "Action": [
        "s3:GetBucketVersioning",
        "s3:PutBucketVersioning",
        "s3:ReplicateObject",
        "s3:ReplicateDelete",
        "s3:ObjectOwnerOverrideToBucketOwner"
      ],
      "Resource": [
        "arn:aws:s3:::shopmini-uploads-dr",
        "arn:aws:s3:::shopmini-uploads-dr/*"
      ]
    }
  ]
}
```

> 📖 *AWS Security Cookbook* 2장. **"객체 소유권을 대상 버킷 소유자로 변경하는 옵션을 선택했으므로 — 이는 크로스 계정 크로스 리전 복제에 필요하다 — 대상 정책에 `s3:ObjectOwnerOverrideToBucketOwner` 액션이 포함되었다. 소유자 재정의가 없으면 대상 버킷 계정은 복제된 파일이나 그 속성에 접근할 수 없다."**

### 🔴 보안 목적 복제의 필수 조건 4가지

| 조건 | 이유 |
|---|---|
| **다른 계정**으로 복제한다 | 원본 계정 침해가 사본에 미치지 않아야 한다 |
| `DeleteMarkerReplication: Disabled` | 삭제가 전파되면 방어가 아니다 |
| 대상 버킷에 **객체 잠금**을 건다(15.9) | 대상 계정 침해에도 사본이 남는다 |
| 대상 계정에서 **원본 계정 역할의 삭제 권한을 부여하지 않는다** | 복제 역할에는 `Replicate*`만. `s3:DeleteObjectVersion`은 절대 금지 |

**⚠️ CRR은 백업이 아닙니다.** 복제는 비동기이고(원서: **"복제는 비동기로 일어나기 때문에, 큰 객체는 복제에 몇 시간이 걸릴 수도 있다"**) 논리적 오류도 그대로 복제합니다. 시점 복구는 17장의 백업 설계가 담당합니다.

## 15.11 S3 액세스 로깅과 CloudTrail 데이터 이벤트 🔴

> 📖 *AWS Security Cookbook* 2장. **"버킷에 대해 서버 액세스 로깅(Server Access Logging)을 활성화하면, S3는 버킷으로 들어오는 요청에 대한 상세 레코드를 기록한다. CloudTrail 데이터 이벤트 기능을 사용해 객체 수준 API 활동을 기록할 수 있다."**

원서 8장은 데이터 이벤트가 **기본으로 꺼져 있다**는 점을 강조합니다. **"기본적으로 CloudTrail API 이벤트 로그는 90일간 제공된다. S3 버킷 작업이나 Lambda 호출 같은 데이터 이벤트는 기본적으로 기록되지 않는다."** 그리고 **"(…) 데이터 이벤트에는 추가 비용이 발생한다."**

**이것이 S3 보안의 가장 흔한 사각지대입니다.** CloudTrail을 켜 두었으니 다 기록된다고 믿지만 `GetObject`·`PutObject`·`DeleteObject`는 **한 건도 남지 않습니다.** 유출 조사에서 "무엇이 언제 누구에게 나갔는가"에 끝내 답하지 못하는 이유입니다.

### 두 로깅의 비교

| 항목 | S3 서버 액세스 로깅 | CloudTrail 데이터 이벤트 |
|---|---|---|
| 비용 | 기능 자체는 무료(스토리지만) | **요청 건당 과금 — 대량 버킷은 비쌈** |
| 지연 | 최선 노력, 수 시간까지 | 보통 수 분 |
| 완전성 | 최선 노력(일부 누락 가능) | 높음 |
| 익명·거부된 요청 | **기록됨** | 기록됨 |
| 프리픽스 단위 필터 | × (버킷 전체) | **○ (고급 이벤트 선택기)** |
| 무결성 검증 | × | **○ (로그 파일 검증)** |
| 연계 | Athena 쿼리 | EventBridge, Athena, Security Lake, GuardDuty |
| 포함 필드 | 요청자, 작업, HTTP 상태, 오류 코드, 전송 바이트, 소요 시간, Referer, User-Agent | 프린시펄 ARN, 세션 컨텍스트, 소스 IP, VPCE ID, 요청 파라미터 |

**둘 다** 켭니다. 서버 액세스 로깅은 값싸게 전수를 남기고, 데이터 이벤트는 탐지·대응 파이프라인에 연결됩니다.

### 서버 액세스 로깅 활성화 (ACL 없이)

```bash
aws s3api put-bucket-logging \
  --bucket shopmini-uploads \
  --bucket-logging-status '{
    "LoggingEnabled": {
      "TargetBucket": "shopmini-s3-access-logs",
      "TargetPrefix": "shopmini-uploads/"
    }
  }' \
  --profile awssec-lab
```

> 💡 **원서 이후 변경** — 15.3에서 인용했듯 원서 시점에는 로그 대상 버킷이 `LogDelivery` 그룹 **ACL**로 쓰기 권한을 받았습니다. ACL을 비활성화한(`BucketOwnerEnforced`) 버킷을 대상으로 쓰려면 **버킷 정책**으로 바꿔야 합니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowS3ServerAccessLogsDelivery",
      "Effect": "Allow",
      "Principal": { "Service": "logging.s3.amazonaws.com" },
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::shopmini-s3-access-logs/shopmini-uploads/*",
      "Condition": {
        "StringEquals": { "aws:SourceAccount": "111122223333" },
        "ArnLike": { "aws:SourceArn": "arn:aws:s3:::shopmini-uploads" }
      }
    }
  ]
}
```

### CloudTrail 데이터 이벤트 활성화

비용 때문에 전체 버킷을 켜기 어렵다면 **고급 이벤트 선택기로 대상을 좁힙니다.** 아래는 `shopmini-uploads`는 전부, 나머지 버킷은 쓰기 계열만 남기는 예입니다.

```bash
aws cloudtrail put-event-selectors \
  --trail-name shopmini-org-trail \
  --advanced-event-selectors '[
    {
      "Name": "S3DataEventsForUploadsBucket",
      "FieldSelectors": [
        { "Field": "eventCategory", "Equals": ["Data"] },
        { "Field": "resources.type", "Equals": ["AWS::S3::Object"] },
        { "Field": "resources.ARN", "StartsWith": ["arn:aws:s3:::shopmini-uploads/"] }
      ]
    },
    {
      "Name": "S3WriteEventsEverywhereElse",
      "FieldSelectors": [
        { "Field": "eventCategory", "Equals": ["Data"] },
        { "Field": "resources.type", "Equals": ["AWS::S3::Object"] },
        { "Field": "readOnly", "Equals": ["false"] }
      ]
    }
  ]' \
  --profile awssec-lab
```

### 🔴 반드시 이렇게 구성하라

- **조직 트레일**을 만들고 로그는 **로그 아카이브 계정(`777788889999`)** 으로 보냅니다. 운영 계정 관리자가 자기 흔적을 지울 수 없어야 합니다(29장).
- 로그 대상 버킷에 **버전 관리 + 객체 잠금(컴플라이언스)** 을 겁니다(15.9).
- 로그 파일 검증(`--enable-log-file-validation`)과 **SSE-KMS** 를 켭니다.
- 다음 이벤트 이름에 **즉시 경보**: `PutBucketPolicy`, `DeleteBucketPolicy`, `PutBucketAcl`, `PutBucketPublicAccessBlock`, `DeleteBucketPublicAccessBlock`, `PutAccountPublicAccessBlock`, `DeleteAccountPublicAccessBlock`, `PutBucketVersioning`, `PutObjectLockConfiguration`, `PutLifecycleConfiguration`.
- **IAM Access Analyzer의 S3 분석**으로 퍼블릭·크로스 계정 접근 가능 버킷을 상시 감시합니다.

**하지 않으면**: 사고 시 "몇 건이 유출되었는가"에 답할 수 없습니다. 각국 개인정보 규제는 대부분 **영향받은 정보주체를 특정해 통지**할 것을 요구하는데, 데이터 이벤트가 없으면 **전체 대상 통지**를 해야 합니다. 로깅 비용과 비교되지 않는 대가입니다.

## 15.12 📋 S3 버킷 보안 점검 20항목

새 버킷 생성 시와 기존 버킷 분기 점검에 씁니다. 괄호 안은 절 번호입니다.

**접근 통제 (1~7)**
- [ ] 1. 계정 수준 BPA 4개가 모두 `true`이고 SCP로 해제가 차단된다 (15.2)
- [ ] 2. 버킷 수준 BPA 4개도 모두 `true`다 (15.2)
- [ ] 3. Object Ownership이 `BucketOwnerEnforced`이고 ACL이 비활성화되어 있다 (15.3)
- [ ] 4. 버킷 정책에 `Principal: "*"` Allow 문장이 없다(서비스 프린시펄 한정 문장은 예외) (15.2, 15.4)
- [ ] 5. `s3:ListBucket`은 버킷 ARN에, 객체 액션은 `/*` ARN에 붙어 있다 (15.4)
- [ ] 6. IAM Access Analyzer에 퍼블릭·크로스 계정 findings가 없다(있다면 승인·문서화됨) (15.11)
- [ ] 7. 크로스 계정 접근이 버킷 정책 나열이 아니라 **역할 수임**으로 구성되어 있다 (15.5)

**데이터 경계 (8~11)**
- [ ] 8. `aws:SecureTransport: false` 거부 문장이 있다 (15.4)
- [ ] 9. `aws:PrincipalOrgID`로 조직 밖 프린시펄이 거부된다 (15.4)
- [ ] 10. VPC 내부 전용 버킷은 `aws:SourceVpce`로 제한된다 (15.4)
- [ ] 11. 공개 자산은 버킷 공개가 아니라 **CloudFront + OAC**로 제공된다 (15.2)

**암호화 (12~14)**
- [ ] 12. 기본 암호화가 **SSE-KMS + 고객 관리형 키**(`alias/shopmini/app`)다 (15.7)
- [ ] 13. `BucketKeyEnabled`가 의도적으로 설정되어 있다(비용 vs 감사 해상도) (15.7)
- [ ] 14. 다른 KMS 키로의 업로드를 거부하는 문장이 있다 (15.4, 15.7)

**변경·삭제 방어 (15~17)**
- [ ] 15. 버전 관리가 `Enabled`다 (15.8)
- [ ] 16. `s3:DeleteObjectVersion`·`s3:PutBucketVersioning`·`s3:PutLifecycleConfiguration`이 브레이크 글래스 외에는 거부된다 (15.8)
- [ ] 17. 등급에 맞는 객체 잠금이 걸려 있다(로그·증적은 컴플라이언스, 운영은 거버넌스) (15.9)

**복제·로깅 (18~20)**
- [ ] 18. 중요 버킷은 **다른 계정**으로 복제되고 `DeleteMarkerReplication`이 `Disabled`다 (15.10)
- [ ] 19. 서버 액세스 로깅과 데이터 이벤트가 **둘 다** 켜져 있고 로그는 로그 계정으로 간다 (15.11)
- [ ] 20. 버킷 정책·BPA·버전 관리·객체 잠금 변경에 실시간 경보가 있다 (15.11)

## 이 장의 요약

| 항목 | 핵심 |
|---|---|
| 4중 구조 | BPA → 버킷 정책 → IAM → ACL. **어느 하나라도 Deny면 거부**, 같은 계정은 한 곳의 Allow로 충분, 크로스 계정은 양쪽 모두 필요 |
| BPA | 계정 수준에서 4개 전부 ON + SCP로 잠금. 예외는 **끄는 것이 아니라 CloudFront OAC로 우회** |
| ACL | `BucketOwnerEnforced`로 **끈다**. 층을 줄이는 것 자체가 통제 |
| 버킷 정책 | 권한 부여가 아니라 **경계 강제** — TLS, OrgID, VPCE, KMS 키 고정 |
| 크로스 계정 | 소유권 함정은 Object Ownership으로 근본 해결. 상시 접근은 **역할 수임** |
| 사전 서명 URL | 서명자의 권한을 상속하고 **취소할 수 없다**. 분 단위 만료, 발급 전용 최소 권한 역할 |
| 암호화 | SSE-KMS + 고객 관리형 키 = **13.4의 2차 관문**. 버킷 키로 KMS 비용 절감(감사 해상도와 트레이드오프) |
| 버전 관리 | 랜섬웨어 1차 방어. 진짜 방어는 **`DeleteObjectVersion`과 수명 주기 권한을 잠그는 것** |
| 객체 잠금 | **관리자 권한 탈취를 전제해도 유효한 통제.** ⚠️ 컴플라이언스 모드는 루트도 해제 불가 |
| CRR | 다른 계정 + 삭제 마커 복제 끄기 + 대상 객체 잠금. **백업이 아니다** |
| 로깅 | 데이터 이벤트는 **기본 OFF**. 켜지 않으면 유출 규모를 영원히 알 수 없다 |

## 🔴 필수 구성 체크리스트

- [ ] 모든 계정에서 계정 수준 BPA 4개가 `true`이고 SCP로 해제가 금지된다
- [ ] 신규 버킷이 `BucketOwnerEnforced`로 생성되고 기존 버킷은 전환 계획이 있다
- [ ] 모든 데이터 버킷에 TLS 강제 + OrgID 제한 가드레일 정책이 붙어 있다
- [ ] 기본 암호화가 고객 관리형 KMS 키이고 다른 키 업로드가 거부된다
- [ ] 모든 데이터 버킷에 버전 관리가 켜져 있고 `DeleteObjectVersion`이 잠겨 있다
- [ ] 로그·증적 버킷에 객체 잠금 컴플라이언스 모드가 걸려 있다
- [ ] 중요 버킷이 별도 계정으로 복제되고 삭제 마커 복제가 꺼져 있다
- [ ] CloudTrail 데이터 이벤트가 켜져 있고 로그가 로그 계정으로 전달된다
- [ ] 버킷 정책·BPA 변경에 실시간 경보가 있다
- [ ] 공개 자산 버킷과 데이터 버킷이 분리되어 있다(가능하면 계정도)

## ⚠️ 자주 하는 실수

| 실수 | 결과 | 올바른 구성 |
|---|---|---|
| 임시 공개를 위해 BPA를 끈다 | 캠페인이 끝나도 안전망은 돌아오지 않는다 — 15.2 시나리오 | CloudFront + OAC. **BPA는 절대 끄지 않는다** (15.2) |
| 공개 자산과 데이터를 한 버킷에 둔다 | `/*` 정책 하나로 전부 열린다 | 버킷 분리, 가능하면 계정 분리 (15.2) |
| 버킷 수준 BPA만 켠다 | 새 버킷을 만드는 사람 수만큼 사고 확률이 곱해진다 | 계정 수준 BPA + SCP 잠금 (15.2) |
| BPA 4개 중 `Block*` 두 개만 켠다 | **이미 있는** 퍼블릭 ACL·정책은 그대로 살아 있다 | 4개 전부 (15.2) |
| 정리 없이 `BucketOwnerEnforced`로 바꾼다 | ACL에 의존하던 접근이 **조용히** 끊긴다 | 로그로 접근 주체 파악 → 정책 부여 → 전환 (15.3) |
| ACL을 끈 버킷을 액세스 로그 대상으로 지정한다 | `LogDelivery` ACL 부여가 실패해 로그가 안 쌓인다 | `logging.s3.amazonaws.com` 버킷 정책 (15.11) |
| `s3:ListBucket`을 `arn:...:버킷/*`에 붙인다 | 원서가 지적한 그대로, 액션이 어떤 리소스에도 적용되지 않는다 | 버킷 액션은 버킷 ARN, 객체 액션은 `/*` (15.4) |
| 버킷 정책 `Principal`에 IAM 그룹을 넣는다 | `Invalid principal in policy` 오류 | 사용자/역할 ARN 또는 계정 ARN (15.4) |
| `aws:PrincipalOrgID` Deny에 `IfExists`를 안 붙인다 | 이 키가 없는 **AWS 서비스 프린시펄까지 차단** — 복제·로깅이 죽는다 | `StringNotEqualsIfExists` + `aws:PrincipalIsAWSService` 예외 (15.4) |
| `Null: {"s3:x-amz-server-side-encryption": "true"}` Deny를 무심코 넣는다 | 기본 암호화에 의존하는 정상 업로드가 전부 실패 | 기본 암호화를 쓰면 이 문장은 넣지 않는다 (15.4) |
| 크로스 계정 업로드에서 `--acl bucket-owner-full-control`을 빠뜨린다 | 버킷 소유자가 자기 버킷 객체를 **읽지 못하는데 지울 수는 있는** 상태 | `BucketOwnerEnforced`로 근본 해결 (15.5) |
| 버킷 정책만 고치고 상대 계정 IAM을 안 고친다 | 크로스 계정은 양쪽 Allow 필요 — 아무 일도 일어나지 않음 | 양쪽 동시 구성 (15.1, 15.5) |
| 관리자 자격으로 사전 서명 URL을 만든다 | 받은 사람이 서명자와 동등한 권한을 갖는다 | 발급 전용 최소 권한 역할 (15.6) |
| 역할 세션으로 서명하고 `ExpiresIn`을 길게 준다 | 세션 만료 시점에 URL이 죽어 간헐적 실패 | 세션 수명 내로 만료 설정 (15.6) |
| SSE-S3로 충분하다고 판단한다 | 키 정책이라는 **2차 관문이 없다** — S3 권한 실수가 곧 평문 유출 | SSE-KMS + 고객 관리형 키 (15.7) |
| 결제 정보 버킷에 버킷 키를 켠다 | 객체 단위 KMS 복호화 감사 로그가 사라진다 | 등급별로 켜고 끈다 (15.7) |
| 버전 관리만 켜고 삭제 권한을 안 잠근다 | 공격자가 `DeleteObjectVersion`으로 전부 지운다 | 명시적 Deny + 브레이크 글래스 (15.8) |
| 삭제 권한만 잠그고 수명 주기 권한을 놔둔다 | "비현재 버전 1일 후 영구 삭제" 규칙 한 줄로 무력화 | `s3:PutLifecycleConfiguration`도 함께 (15.8) |
| 검증 없이 컴플라이언스 모드 + 긴 보존을 건다 | **루트도 AWS도 못 푼다.** 보존 기간 내내 비용 지불 | 개발 검증 → 거버넌스 → 프리픽스 한정 승격 (15.9) |
| MFA Delete를 모든 버킷에 건다 | 수명 주기 만료 불가로 비용 증가, 자동화 불가, 루트 상시 필요 | 최고 등급 버킷 한정. 나머지는 객체 잠금 (15.8, 15.9) |
| CRR을 켜고 삭제 마커 복제를 활성화한다 | 원본 삭제가 사본으로 전파 — 방어 효과 소멸 | `DeleteMarkerReplication: Disabled` (15.10) |
| CRR을 백업으로 여긴다 | 논리적 오류도 그대로 복제되고, 시점 복구가 없다 | 복제 + 별도 백업 설계 (15.10, 17장) |
| CloudTrail을 켰으니 다 기록된다고 믿는다 | `GetObject`/`PutObject`가 **한 건도 안 남는다** | 데이터 이벤트 명시적 활성화 (15.11) |
| 로그를 같은 계정 버킷에 쌓는다 | 침해 시 공격자가 흔적을 지운다 | 로그 계정 + 객체 잠금 (15.11, 29장) |

## 다음 장 예고

16장은 같은 원칙 — **저장 암호화, 전송 강제, 실수로 공개되는 공유 설정** — 을 나머지 저장소에 적용합니다. EBS 리전 기본 암호화, RDS/Aurora의 TLS 강제와 IAM 데이터베이스 인증, DynamoDB의 `LeadingKeys` 조건, EFS 접근 지점, Glacier Vault Lock을 다룹니다.
