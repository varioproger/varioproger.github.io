# 1장. 클라우드 보안의 5대 원칙

> **이 장에서 다루는 것**
> - 이 책 전체가 되돌아올 다섯 개의 원칙 — 최소 권한, 심층 방어, 제로 트러스트, 폭발 반경 최소화, 자동화 우선
> - 각 원칙이 AWS에서 **어떤 서비스·설정으로 실체화되는지**의 매핑표 (이후 전 장의 로드맵)
> - 심층 방어의 AWS 4개 통제층: 조직 SCP → 계정 IAM → 네트워크 SG/NACL → 리소스 정책/KMS 키 정책
> - 계정·VPC·키·역할 네 가지 경계 단위로 폭발 반경을 나누는 기준
> - 원칙끼리 충돌할 때(가용성 vs 격리, 개발 속도 vs 통제) 무엇을 근거로 판단할 것인가
>
> **선행 지식**: 0장 (예제 애플리케이션 ShopMini의 구조와 계정 배정)
> **난이도**: ★☆☆

보안 통제는 하나씩 놓고 보면 전부 그럴듯해 보입니다. MFA를 켠다, 버킷을 비공개로 둔다, 보안 그룹을 좁힌다 — 반대할 이유가 없습니다. 문제는 예산도 시간도 유한하다는 점입니다. 어떤 통제를 먼저 넣을지, 어디까지 하면 충분한지, 두 통제가 서로 부딪칠 때 무엇을 포기할지를 결정하려면 통제 목록이 아니라 **판단 기준**이 필요합니다. 이 장의 다섯 원칙이 그 기준입니다.

> 📖 *Practical Cloud Security* 2판 1장은 이 원칙들을 먼저 다루는 이유를 이렇게 설명합니다. 최소 권한을 모르면 클라우드 서비스의 인가 방식을 잘 이해하고도 계정이나 민감 데이터가 든 데이터베이스에 과도한 접근을 허용하게 되고, 심층 방어를 모르면 인증·네트워크 접근 통제·암호화를 **여러 겹으로 두는 것이 왜 쓸모 있는지** 이해하지 못한다는 것입니다. 저자는 이 개념적 공백(conceptual gap)이 실제 보안 사고로 이어진다고 봅니다.

이 다섯 원칙 중 앞의 셋은 원서에 명시적으로 정리되어 있고, 뒤의 둘은 원서 곳곳에 흩어진 논의를 AWS 문맥으로 묶은 것입니다. 각 절 끝에는 **원칙 → AWS 구현 매핑표**를 두었습니다. 이 표들이 이 책의 목차를 원칙별로 다시 정렬한 로드맵 역할을 합니다.

## 1.1 최소 권한 (Least Privilege)

> 📖 *Practical Cloud Security* 1판·2판 1장은 최소 권한을 "사람이나 자동화 도구가 **자기 일을 하는 데 필요한 것만** 접근할 수 있어야 하고, 그 이상은 안 된다"로 정의합니다. 저자가 특히 강조하는 것은 **자동화 부분을 잊기 쉽다**는 점입니다. 예로 든 것이 데이터베이스에 접근하는 컴포넌트인데, 쓰기가 필요 없다면 쓰기 권한이 있는 자격 증명을 쓰면 안 된다고 말합니다. 그리고 최소 권한을 실무에 적용하면 접근 정책이 **기본 거부(deny by default)** 형태가 되며, 사용자는 기본적으로 아무 권한도(혹은 아주 적은 권한만) 갖고 시작해 필요한 권한마다 요청·승인 절차를 거치게 된다고 정리합니다.

AWS의 IAM은 이 원칙에 맞게 설계되어 있습니다. 아무 정책도 붙지 않은 IAM 주체(principal)는 아무것도 할 수 없습니다. 즉 **암묵적 거부(implicit deny)** 가 출발점입니다. 그래서 AWS에서 최소 권한이 깨지는 지점은 "기본값이 느슨해서"가 아니라 거의 항상 **사람이 넓은 권한을 명시적으로 붙였기 때문**입니다. `AdministratorAccess` 관리형 정책을 붙이고 넘어가거나, `"Action": "s3:*"`, `"Resource": "*"` 로 시작해 끝내 좁히지 않는 식입니다.

### 사람·워크로드·서비스에 각각 적용하기

최소 권한은 세 종류의 주체 모두에 적용됩니다. 그런데 실무에서는 사람에게만 신경 쓰고 나머지 둘을 놓치는 경우가 많습니다.

| 주체 | ShopMini에서의 예 | 흔한 과잉 권한 | 최소 권한 형태 |
|---|---|---|---|
| **사람** | 운영 담당자, 개발자, 감사자 | 상시 `AdministratorAccess` 보유 | Identity Center 권한 세트로 역할 분리, 관리자 권한은 필요할 때만 승격(9.5) |
| **워크로드** | 앱 EC2/컨테이너, Lambda | 인스턴스 프로파일에 `s3:*` 부여 | `shopmini-uploads` 프리픽스 한정 `s3:GetObject`/`s3:PutObject` 만(8.2) |
| **AWS 서비스** | CloudFront가 S3 오리진 접근 | 버킷을 퍼블릭으로 열어 해결 | OAC + 버킷 정책에서 해당 배포만 허용(23.7) |

> 📖 2판 1장은 클라우드 콘솔 접근의 위험성을 따로 지적합니다. 많은 제공자에서 콘솔 접근 권한을 가진 사람은 기본적으로 그 제공자가 관리하는 모든 것에 대해 **"신과 같은(godlike)" 권한**을 갖게 되며, 여기에는 프로비저닝된 시스템의 운영체제에 어떤 통제가 걸려 있든 상관없이 클라우드 환경 어느 부분의 데이터든 읽고 수정하고 파괴할 수 있는 능력이 포함될 수 있다는 것입니다. 그래서 온프레미스에서 물리 데이터센터 출입을 엄격히 통제하듯 콘솔 접근과 권한을 엄격히 통제하고, **이 사용자들이 무엇을 하는지 기록**해야 한다고 말합니다.

AWS 문맥으로 옮기면 이 문장은 두 가지 요구가 됩니다. 첫째, 콘솔에 상시 관리자로 로그인하는 사람이 없어야 합니다(9.5의 특권 접근 관리). 둘째, 콘솔·API에서 일어난 모든 일이 CloudTrail에 남고 그 로그를 운영 계정 관리자가 지울 수 없어야 합니다(29.9의 중앙 로그 계정).

### "필요한 동안만"이라는 시간 축

최소 권한은 범위(무엇을)뿐 아니라 시간(얼마나 오래)에도 적용됩니다. AWS에서 이 시간 축을 담당하는 것이 STS 임시 자격 증명입니다. 액세스 키는 만들면 삭제할 때까지 유효하지만, `sts:AssumeRole`로 얻은 자격 증명은 세션 시간이 지나면 자동으로 무효가 됩니다. 유출 사고의 피해 크기가 근본적으로 달라지는 지점입니다.

## 1.2 심층 방어 (Defense in Depth) 🔴

> 📖 *Practical Cloud Security* 2판 1장은 심층 방어를 "거의 **모든** 보안 통제가 실패할 수 있다는 사실의 인정"이라고 정의합니다. 실패 이유는 두 가지로, 공격자가 충분히 집요하고 숙련되었거나, 그 통제의 **구현 방식에 문제**가 있기 때문입니다. 그래서 겹치는 통제를 여러 겹 만들어 하나가 실패해도 그 뒤의 통제가 공격자를 잡을 수 있게 한다고 설명합니다.
>
> 저자는 판단 기준도 함께 제시합니다. 가지고 있는 보안 통제 아무거나 하나를 짚고 **"이게 실패하면 어떻게 되지?"** 라고 물었을 때 답이 받아들일 수 없는 수준이라면, 심층 방어가 부족한 것입니다. 또 하나의 실패가 여러 개의 통제를 한꺼번에 무력화할 수 있다면 — 예로 든 것이 자산 관리(인벤토리) 문제 때문에 여러 도구가 동시에 문제를 놓치는 경우입니다 — 그것도 심층 방어가 부족한 신호입니다. 동시에 저자는 심층 방어를 **우스울 정도로 극단까지** 밀어붙일 수 있다는 점도 지적하며, 그래서 자신이 실제로 마주할 위협이 무엇인지 이해하는 것이 중요하다고 말합니다.

### 🔴 반드시 이렇게 구성하라: AWS의 4개 통제층

AWS에서 심층 방어는 추상적인 구호가 아니라 **평가 시점이 서로 다른 네 개의 층**을 전부 채우는 일입니다. 네 층은 각각 다른 곳에서, 다른 사람이, 다른 주기로 관리되기 때문에 하나가 뚫려도 나머지가 남습니다.

```
[층 1] 조직 경계 — SCP (AWS Organizations)
          ↓ 계정 안의 누구도 넘을 수 없는 권한 상한선
[층 2] 계정 경계 — IAM 아이덴티티 정책 / 권한 경계 / 신뢰 정책
          ↓ "이 역할은 무엇을 할 수 있는가"
[층 3] 네트워크 경계 — 보안 그룹 / NACL / VPC 엔드포인트 정책
          ↓ "이 패킷이 저기까지 갈 수 있는가"
[층 4] 리소스 경계 — 버킷 정책 / KMS 키 정책 / 리소스 정책
          ↓ "이 리소스가 이 요청을 받아들이는가"
```

ShopMini의 사용자 업로드 버킷 `shopmini-uploads` 를 예로 네 층을 모두 채워 보겠습니다. 목표는 하나입니다. **운영 계정(`111122223333`)의 앱 역할만, VPC 엔드포인트를 통해, TLS로, KMS 암호화된 객체만 올릴 수 있게 한다.**

**층 1 — 조직 SCP.** 계정 안에서 무슨 일이 벌어지든 넘을 수 없는 천장을 칩니다. 서울 리전 밖 사용 금지와 CloudTrail 변조 금지가 대표적입니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyOutsideSeoulRegion",
      "Effect": "Deny",
      "NotAction": [
        "iam:*",
        "sts:*",
        "organizations:*",
        "cloudfront:*",
        "route53:*",
        "support:*",
        "budgets:*"
      ],
      "Resource": "*",
      "Condition": {
        "StringNotEquals": {
          "aws:RequestedRegion": "ap-northeast-2"
        }
      }
    },
    {
      "Sid": "DenyCloudTrailTampering",
      "Effect": "Deny",
      "Action": [
        "cloudtrail:StopLogging",
        "cloudtrail:DeleteTrail",
        "cloudtrail:PutEventSelectors"
      ],
      "Resource": "*"
    }
  ]
}
```

`NotAction` 에 나열된 것들은 글로벌 서비스라 리전 조건으로 막으면 계정이 마비되기 때문에 예외로 둡니다. 한 가지만 미리 기억해 두십시오. **SCP는 권한을 주지 않고 제한만 하며, 조직 관리 계정(`123456789012`)에는 적용되지 않습니다.** 그래서 관리 계정에 워크로드를 두면 층 1이 통째로 사라집니다. SCP의 설계 원칙과 함정은 37장에서 본격적으로 다룹니다.

**층 2 — 계정 IAM.** 앱 역할 `shopmini-app` 에 필요한 최소 액션만 줍니다. 버킷 전체가 아니라 프리픽스까지 좁히고, 리스트 권한과 객체 권한의 리소스 ARN이 다르다는 점에 주의합니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AppCanWriteOwnPrefix",
      "Effect": "Allow",
      "Action": ["s3:PutObject", "s3:GetObject"],
      "Resource": "arn:aws:s3:::shopmini-uploads/incoming/*"
    },
    {
      "Sid": "AppCanListOwnPrefix",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::shopmini-uploads",
      "Condition": {
        "StringLike": { "s3:prefix": "incoming/*" }
      }
    }
  ]
}
```

**층 3 — 네트워크.** 앱은 인터넷을 거치지 않고 S3 게이트웨이 엔드포인트로 나갑니다. 그리고 앱 계층으로 들어오는 트래픽은 CIDR이 아니라 **ALB의 보안 그룹을 참조**해서 8443 포트만 엽니다.

```bash
aws ec2 authorize-security-group-ingress \
  --group-id sg-0a1b2c3d4e5f67890 \
  --ip-permissions 'IpProtocol=tcp,FromPort=8443,ToPort=8443,UserIdGroupPairs=[{GroupId=sg-0f9e8d7c6b5a43210,Description="ALB to app 8443"}]' \
  --region ap-northeast-2 \
  --profile awssec-lab
```

보안 그룹 참조 체인(ALB SG → App SG → DB SG)을 CIDR 대신 쓰는 이유는 19.2에서, 엔드포인트 정책으로 "우리 조직 버킷에만" 을 강제하는 방법은 20.3에서 다룹니다.

**층 4 — 리소스 정책과 키 정책.** 마지막 관문은 리소스 자신입니다. 앞의 세 층이 전부 잘못 설정되어도, 버킷이 평문 HTTP 요청과 비암호화 업로드를 거부합니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyInsecureTransport",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::shopmini-uploads",
        "arn:aws:s3:::shopmini-uploads/*"
      ],
      "Condition": {
        "Bool": { "aws:SecureTransport": "false" }
      }
    },
    {
      "Sid": "DenyUnencryptedUpload",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::shopmini-uploads/*",
      "Condition": {
        "StringNotEquals": {
          "s3:x-amz-server-side-encryption": "aws:kms"
        }
      }
    }
  ]
}
```

> 💡 **원서 이후 변경** — 현재 S3는 모든 버킷에 기본 암호화(SSE-S3)가 항상 적용됩니다. 따라서 위 `DenyUnencryptedUpload` 문장의 목적은 "암호화 여부"를 강제하는 것이 아니라, **AWS 관리형 키가 아닌 우리 고객 관리형 KMS 키(`aws:kms`)를 쓰도록** 강제하는 것입니다. 키를 우리가 통제해야 1.4의 폭발 반경 경계가 성립하기 때문입니다.

그리고 KMS 키 `alias/shopmini/app` 의 키 정책이 한 겹 더 있습니다. **IAM 정책만으로는 KMS 키를 쓸 수 없습니다.** 키 정책이 허용해야 합니다.

```json
{
  "Sid": "AllowAppRoleViaS3Only",
  "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::111122223333:role/shopmini-app" },
  "Action": ["kms:Decrypt", "kms:GenerateDataKey"],
  "Resource": "*",
  "Condition": {
    "StringEquals": {
      "kms:ViaService": "s3.ap-northeast-2.amazonaws.com"
    }
  }
}
```

`kms:ViaService` 조건 덕분에, 앱 역할의 자격 증명이 유출되어도 공격자가 그 키로 **직접** `Decrypt` 를 호출할 수는 없습니다. S3를 경유한 호출만 허용되기 때문입니다. 키 정책과 IAM의 결합 평가는 13.4에서, 조건 키 활용은 13.8에서 다룹니다.

### 🔴 이 구성을 하지 않으면 벌어지는 일

각 층을 빠뜨렸을 때 어떤 단일 실수가 사고로 직결되는지 정리하면 이렇습니다.

| 빠진 층 | 단 하나의 실수 | 결과 |
|---|---|---|
| 층 1(SCP) 없음 | 운영 계정 관리자가 CloudTrail을 끔 | 사고가 나도 무슨 일이 있었는지 **재구성 불가** |
| 층 2(IAM) 느슨함 | 앱 역할에 `s3:*`, `Resource: "*"` | SSRF로 자격 증명이 새면 전 버킷 열람·삭제 |
| 층 3(네트워크) 없음 | 보안 그룹에 `0.0.0.0/0` 8443 | 인터넷에서 ALB를 건너뛰고 앱에 직접 도달, WAF 우회 |
| 층 4(리소스) 없음 | 실수로 버킷 정책을 넓게 수정 | IAM이 아무리 좁아도 **다른 계정에서 접근 가능** |

> 📖 2판 1장이 말한 "하나의 실패가 여러 통제를 한꺼번에 무력화하는" 경우가 AWS에도 그대로 있습니다. 예를 들어 자산 관리가 부실해서 어떤 VPC의 존재를 아무도 모르면, GuardDuty도 Config도 Inspector도 그 VPC를 보지 않습니다. 이 문제는 12장에서 다룹니다.

## 1.3 제로 트러스트 (Zero Trust)

제로 트러스트는 1판에는 없고 **2판에서 새로 들어온 원칙**입니다. 4년 사이에 이 개념이 클라우드 보안 논의의 중심으로 이동했다는 뜻이기도 하고, 동시에 그만큼 마케팅 용어로 오염되었다는 뜻이기도 합니다.

> 📖 *Practical Cloud Security* 2판 1장은 이 용어에 대해 이례적으로 비판적입니다. 저자는 이름 자체가 혼란스럽다고 말합니다. 제로 트러스트는 **아무것도 신뢰하지 않는다는 뜻이 아니며**, 너무 많은 마케팅 목적으로 쓰이면서 혼란이 더 커졌다는 것입니다. 그러면서 이 용어는 사실 "**제로 암묵적 신뢰(zero implicit trust)**" 나 "타당한 이유 없이 가정된 신뢰는 없음(zero assumed trust without a good reason)" 같은 다른 이름으로 불렸어야 한다고 말합니다. 핵심 원칙은 사용자나 다른 시스템으로부터의 신뢰는 **주어지는 것이 아니라 획득되어야 한다**는 것입니다 — 단지 네트워크상으로 나에게 도달할 수 있다는 이유로, 혹은 회사 소유 기기를 쓴다는 이유로, 혹은 그 밖의 잘 통제되지 않는 기준으로 신뢰를 주어서는 안 된다는 것입니다.
>
> 저자는 세 가지 구현 예를 듭니다. ① 신뢰된다고 여겨지는 네트워크 안에서 시작해서 안에서 끝나는 연결까지 포함해 **모든 연결에 암호화와 인증을 요구**하는 것 — 이것은 원래도 좋은 생각이었지만, 경계가 덜 엄격하게 설계되고 인터넷 연결이 쉬운 클라우드 환경에서는 더 중요해졌다고 말합니다. ② 사용자의 네트워크 접근을 **필요한 애플리케이션으로만** 제한하는 것 — 로그인은 못 하더라도 모든 사용자가 모든 애플리케이션에 연결은 할 수 있어야 한다는 암묵적 신뢰에 도전하는 것입니다. ③ **다중 인증**과, 주기적으로 혹은 더 위험한 트랜잭션이 요청될 때의 재인증 — 계정의 비밀번호를 가진 사람이나 특정 세션을 통제하는 사람이 곧 의도된 사용자라는 암묵적 신뢰에 도전하는 것입니다.
>
> 저자 스스로 이것이 최소 권한·심층 방어와 상당히 겹친다고 인정하며, 결론을 이렇게 정리합니다. 제로 트러스트 원칙을 따른다면 **강한 인증, 인가, 올바른 구성의 증거처럼 그 신뢰가 정당하다는 강력한 증거가 있을 때만** 상호작용을 신뢰해야 합니다. 그 증거는 자신이 직접 통제하는 것(자체 인증 시스템이나 기기 관리 시스템)에서 오거나, 자신을 대신해 신뢰 판단을 내릴 역량이 있다고 **명시적으로 평가한** 제3자에게서 와야 합니다.

### AWS에서 제로 트러스트는 이미 기본값에 가깝다

여기서 AWS 사용자에게 유리한 점이 하나 있습니다. AWS API는 처음부터 제로 트러스트 방식으로 만들어졌습니다. VPC 안에서 호출하든 인터넷에서 호출하든, 모든 API 호출은 서명(SigV4)으로 **인증**되고 IAM으로 **인가**되며 TLS로 **암호화**됩니다. "우리 VPC 안이니까 괜찮다"는 개념 자체가 컨트롤 플레인에는 존재하지 않습니다.

문제는 데이터 플레인, 즉 우리가 직접 만드는 애플리케이션 계층입니다. 여기서는 여전히 "프라이빗 서브넷 안이니까 HTTP로 해도 되겠지", "같은 VPC니까 인증 없이 호출해도 되겠지" 같은 암묵적 신뢰가 흔합니다.

> 📖 2판 6장(네트워크 보안)은 클라우드 환경 네트워크를 지킬 때 제로 트러스트에서 가장 중요한 부분은, **통신이 전적으로 자기 경계 안에서 일어나더라도** 클라우드 환경 리소스 간 통신을 인증·인가·암호화로 보호하는 것이라고 못 박습니다. 예로 든 것이 "localhost 전용" 통신을 제외한 모든 연결에 TLS를 쓰는 것입니다. 그리고 이런 연결 보호는 보통 **마이크로세그멘테이션**과 결합되는데, 클라우드에서는 온프레미스보다 네트워크 세그먼트를 더 많이 만드는 것이 쉽고 저렴하기 때문이라고 설명합니다.

ShopMini에 적용하면 구체적인 요구 세 가지가 나옵니다.

1. **ALB → 앱이 8443 HTTPS인 이유가 여기 있습니다.** VPC 내부 구간이라도 평문으로 두지 않습니다. TLS 종료 위치 결정은 23.5에서 다룹니다.
2. **앱 → RDS 연결도 TLS를 강제**하고, 가능하면 비밀번호 대신 IAM 데이터베이스 인증을 씁니다(16.2).
3. **앱 → S3는 VPC 엔드포인트를 지나되**, 엔드포인트를 지났다는 사실만으로 신뢰하지 않습니다. 여전히 IAM 역할로 인증하고 버킷 정책으로 인가합니다.

### 제로 트러스트 → AWS 구현 매핑

| 제로 트러스트 요구 | AWS 구현 | 다루는 장 |
|---|---|---|
| 모든 요청을 인증한다 | SigV4 서명, IAM 역할 기반 워크로드 아이덴티티 | 8.8 |
| 네트워크 위치를 신뢰하지 않는다 | 내부 구간도 TLS, 보안 그룹 참조 기반 마이크로세그멘테이션 | 19.2, 19.7 |
| 사람의 신원을 반복 검증한다 | MFA, 패스키/패스워드리스, 위험 트랜잭션 재인증 | 9.4 |
| 기기·컨텍스트를 판단에 넣는다 | 조건 키(`aws:SourceIp`, `aws:SourceVpce`, `aws:PrincipalOrgID`) | 7.4 |
| 신뢰를 명시적으로만 부여한다 | 신뢰 정책, External ID, Confused Deputy 방어 | 8.6 |
| 사용자 접근을 앱 단위로 제한한다 | Identity Center 권한 세트, API Gateway 인가 | 9.2, 24.7 |
| 관리 접근에도 암묵적 신뢰 없음 | SSM Session Manager (SSH 포트 개방 대체) | 21.5, 21.6 |

## 1.4 폭발 반경 최소화 (Blast Radius) 🔴

앞의 세 원칙이 "뚫리지 않게 하는" 쪽이라면, 이 원칙은 **뚫린 다음을 설계하는** 쪽입니다. 전제가 다릅니다. 공격자가 어딘가 한 곳에는 들어온다고 가정하고, 그때 잃는 것의 크기를 미리 정해 둡니다.

> 💡 **원서 이후 보충** — "폭발 반경(blast radius)"이라는 표현 자체는 근거 원서 세 권에 등장하지 않습니다. 다만 *Practical Cloud Security* 2판 1장의 신뢰 경계(trust boundary) 논의가 같은 이야기를 다른 이름으로 하고 있습니다. 저자는 신뢰 경계를 그릴 때의 사고방식을 이렇게 설명합니다. **공격자가 신뢰 경계의 한 부분에 들어오면 결국 그 안의 모든 것을 완전히 통제하게 된다고 가정하는 것이 합리적**이므로, 각 신뢰 경계를 통과하는 데는 어느 정도 노력이 들어야 한다는 것입니다. 같은 경계 안에 여러 웹 서버를 그렸다면 그것은 "이 서버들끼리는 서로 신뢰해도 좋다"는 뜻이고, 한 대에 접근한 사람은 사실상 전부에 접근한 것이며, 한 대가 침해되어도 **나머지가 함께 침해되는 것으로 추가 피해가 생기지 않는다**는 뜻입니다. 그리고 제로 트러스트 원칙은 이 신뢰 경계를 **합리적으로 가능한 가장 작은 크기**로 줄이도록 이끈다고 덧붙입니다.

이 문장을 AWS로 번역하면 이렇게 됩니다. **"이 자격 증명 하나가 유출되면 무엇을 잃는가"를 답할 수 있어야 하고, 그 답이 너무 크면 경계를 하나 더 그어야 한다.**

### 🔴 반드시 이렇게 구성하라: 네 개의 경계 단위

AWS에는 성격이 다른 네 개의 경계 단위가 있습니다. 중요한 것은 **각 경계가 무엇을 막고 무엇을 못 막는지** 구분하는 일입니다.

| 경계 단위 | 무엇을 격리하는가 | 이 경계가 막지 **못하는** 것 | ShopMini 적용 |
|---|---|---|---|
| **계정(Account)** | IAM 권한, 서비스 한도, 과금, 규제 범위 | 계정 간 명시적으로 연결한 신뢰(크로스 계정 역할, 공유 리소스) | 운영 `111122223333` / 개발 `555555555555` / 보안 `444455556666` / 로그 `777788889999` 분리 |
| **VPC / 서브넷** | 네트워크 도달 범위 | IAM 권한 (VPC가 달라도 같은 계정 자격 증명이면 API 호출 가능) | `shopmini-prod`(`10.20.0.0/16`) 안에서 public / private-app / isolated-data 3계층 |
| **KMS 키** | 복호화 가능한 데이터 범위 | 키를 쓸 수 있는 역할이 침해된 경우 | 환경별·데이터 등급별로 키 분리, `alias/shopmini/app` 은 운영 앱 전용 |
| **IAM 역할** | 하나의 워크로드가 할 수 있는 일 | 역할을 넘겨받을 수 있는 권한(`iam:PassRole`)이 넓으면 무의미 | 앱 역할 / 배포 파이프라인 역할 / 백업 역할을 각각 분리 |

이 표에서 가장 자주 오해되는 칸은 **VPC 행의 세 번째 열**입니다. "DB를 격리 서브넷에 넣었으니 안전하다"고 말하는 설계를 자주 보는데, 침해된 것이 앱 인스턴스의 IAM 역할이라면 공격자는 네트워크를 지날 필요가 없습니다. RDS 스냅샷을 API로 떠서 다른 계정에 공유하면 그만입니다. **네트워크 경계는 IAM 경계를 대신하지 못합니다.** 그 반대도 마찬가지입니다. 그래서 1.2의 4개 층이 전부 필요합니다.

### 어디에 선을 그을 것인가

경계를 무한히 늘릴 수는 없습니다. 계정을 100개로 나누면 폭발 반경은 작아지지만 관리가 불가능해집니다. 판단 기준은 세 가지입니다.

- **데이터 등급이 다르면 나눈다.** 결제 정보와 마케팅 로그가 같은 계정·같은 키 아래 있으면 안 됩니다.
- **침해 시 신뢰할 수 없게 되는 범위가 다르면 나눈다.** 운영 계정이 침해되어도 **로그와 백업은 여전히 믿을 수 있어야** 합니다. 이것이 로그 아카이브 계정과 백업 계정을 따로 두는 유일한 이유입니다.
- **변경 주기와 담당자가 다르면 나눈다.** 개발자가 매일 배포하는 것과 분기에 한 번 바뀌는 것을 같은 경계에 두면 둘 중 하나가 반드시 느슨해집니다.

> **이 절의 상세 구현은 36장으로 넘깁니다.** OU 설계, 필수 코어 계정 구성(관리·로그 아카이브·보안 도구·네트워크·백업), 계정 생성·이동, 크로스 계정 역할 전환, RAM 기반 리소스 공유는 전부 36장의 주제입니다. 여기서는 **왜** 나누는지만 세워 두고 갑니다.

## 1.5 자동화 우선과 불변 인프라

앞의 네 원칙은 "무엇을 구성할 것인가"에 대한 것이고, 이 원칙은 **"그 구성이 시간이 지나도 유지되는가"** 에 대한 것입니다. 완벽하게 설계한 보안 그룹도 누군가 콘솔에서 한 줄 고치면 무너집니다. 그리고 그 변경은 대개 금요일 밤 장애 대응 중에 일어납니다.

> 📖 *Practical Cloud Security* 2판 5장은 클라우드와 함께 **불변 인프라(immutable infrastructure)와 지속적 배포** 철학이 함께 채택되는 경우가 많고, 이것이 변경으로 인한 장애 위험을 상당히 줄여 준다고 말합니다. 저자가 여기서 끌어내는 결론이 흥미롭습니다. 이것이 **운영 리스크와 보안 리스크의 균형을 바꾼다**는 것입니다. 보안 수정을 적용하는 것도 하나의 변경인데, 변경을 더 안전하게 할 수 있게 되었으므로 시스템을 다운시킬 위험 없이 **보안 수정을 더 빨리 롤아웃할 여유가 생긴다**는 것입니다. 그래서 클라우드 환경에서는 취약점 관리·패치 관리·변경 관리 프로세스 자체를 온프레미스와 다르게 가져가야 한다고 정리합니다.

> 📖 2판 3장은 불변 컨테이너를 이렇게 정의합니다. 컨테이너는 시간이 지나도 **변하지 않으며**, 다른 컴포넌트(예: 스토리지 서비스)에 데이터를 쓸 수는 있지만 그 스토리지는 컨테이너와 별도로 관리됩니다. 컨테이너는 수명 동안 이미지에 담긴 코드의 완벽한 사본을 유지합니다 — **스스로 코드를 업데이트하지 않고, 아무도 로그인해서 바꾸지 않습니다.** 실행 중인 컨테이너를 업데이트하는 대신, 옛 컨테이너를 파괴하고 새 코드가 담긴 새 컨테이너를 만듭니다. 그리고 5장에서는 컨테이너를 정기적으로 교체하는 것 자체가 **위협 행위자가 네트워크에 지속(persist)하는 것을 막는 데 도움이 된다**고 덧붙입니다. 침해되더라도 일주일쯤 뒤면 지워지고, 새 컨테이너에는 침해의 원인이 된 문제가 수정되어 있으리라는 것입니다.

마지막 문장이 이 원칙의 보안적 핵심입니다. 불변 인프라는 배포 편의를 위한 것이 아니라 **지속성(persistence) 방어 통제**입니다. 공격자가 인스턴스에 백도어를 심어도, 그 인스턴스가 일주일 뒤 교체되면 백도어도 사라집니다.

### AWS에서 "사람의 손"을 제거하는 지점

## 1.6 ⚠️ 원칙이 충돌할 때

여기까지는 원칙들이 서로 돕는 것처럼 보였습니다. 실무에서는 자주 부딪칩니다. 이 절은 **부딪쳤을 때 무엇을 근거로 결정할 것인가**를 다룹니다.

> 📖 2판 1장 자체가 이 긴장을 인정합니다. 심층 방어에 대해 저자는 "우스울 정도의 극단까지 갈 수 있다"고 말하고, 제로 트러스트에 대해서도 "이 장의 다른 원칙들과 마찬가지로 **극단으로 밀어붙이면 사용자 경험을 해칠 수 있다**"고 덧붙입니다. 원칙은 최대화의 대상이 아니라 위협 수준에 맞춰 조절하는 대상이라는 뜻입니다.

### 사고 시나리오 → 원인 → 올바른 구성

**시나리오 A. 가용성 vs 격리.**
ShopMini 운영팀이 장애 대응 속도를 높이려고, 개발 계정 `555555555555` 의 개발자 역할이 운영 계정 `111122223333` 의 조회 권한을 상시로 가질 수 있게 크로스 계정 신뢰를 열었습니다. 6개월 뒤 개발자 한 명의 노트북이 침해되면서 공격자가 운영 데이터베이스 스냅샷 목록과 S3 객체 목록을 그대로 열람합니다.

- **원인** — 가용성(빠른 장애 대응)을 근거로 계정 경계를 상시로 뚫었습니다. 경계를 뚫은 것 자체보다, **뚫린 상태가 기본값이 된 것**이 문제입니다.
- **올바른 구성** — 경계는 유지하되 **통과 절차를 빠르게** 만듭니다. 크로스 계정 역할은 유지하고, 상시 부여 대신 승인 기반 임시 승격(9.5)으로 바꿉니다. 세션 시간을 1시간으로 두고, `AssumeRole` 이벤트에 알람을 겁니다(30.3). 브레이크 글래스 절차(32.4)를 따로 정의해 진짜 긴급 상황을 대비합니다.

**시나리오 B. 개발 속도 vs 통제.**
보안팀이 SCP로 미승인 리전을 전부 차단했는데, 개발팀이 새 기능에 `us-east-1` 전용 서비스를 쓰려다 막혔습니다. 티켓 처리에 2주가 걸리자 개발팀은 조직 밖에 개인 신용카드로 별도 AWS 계정을 만들어 씁니다. 그 계정에는 CloudTrail도 GuardDuty도 없습니다.

- **원인** — 통제가 강해서가 아니라 **예외 처리 경로가 느려서** 새도우 IT가 생겼습니다. 통제를 우회하는 비용이 통제를 따르는 비용보다 싸지면 사람은 반드시 우회합니다.
- **올바른 구성** — 통제 강도는 유지하고 **예외 경로의 지연 시간을 줄입니다.** 샌드박스 OU를 만들어 실험은 그 안에서 자유롭게 하되 조직 안에 두어 로깅·탐지 커버리지를 유지합니다(36.4). 예외 요청은 IaC PR로 받아 자동 검증 후 머지되게 합니다(28.3).

### ⚠️ 트레이드오프 판단 기준

충돌할 때마다 매번 처음부터 논쟁하지 않으려면 미리 정해 둔 기준이 필요합니다.

| 충돌 축 | 기울여야 하는 쪽 | 판단 기준 | 그래도 반대로 가야 하는 예외 |
|---|---|---|---|
| **가용성 vs 격리** | 상황에 따라 다름 | ① 침해 시 복구 가능한가(데이터는 복구 불가, 서비스 중단은 복구 가능) ② 규제 대상 데이터인가 | 인명·안전 관련 시스템은 가용성 우선. 단, 우회 경로를 **사전 정의**하고 사용 시 알람 |
| **개발 속도 vs 통제** | 통제(단, 예외 경로를 빠르게) | 통제를 따르는 비용 < 우회하는 비용이 성립하는가 | 초기 실험 단계는 샌드박스 OU에서 완화. 운영 승격 시 전면 검증 |
| **심층 방어 vs 복잡도** | 최소 4개 층까지는 무조건 | "이 통제가 실패하면?"의 답이 수용 가능한가 | 층 자체가 새 취약점이 되는 경우(관리 안 되는 프록시 등)는 제거가 정답 |
| **제로 트러스트 vs 사용자 경험** | 위험도에 비례 | 트랜잭션 위험도(조회 vs 이체 vs 권한 변경) | 저위험 조회에 매번 MFA를 요구하면 사용자가 MFA 자체를 회피 |
| **최소 권한 vs 운영 부담** | 최소 권한 | 권한 요청→승인 리드타임이 하루 이내인가 | 리드타임이 길면 사람들이 넓은 권한을 "미리" 받아 둔다. 리드타임 단축이 먼저 |
| **자동 조치 vs 오탐 피해** | 되돌릴 수 있으면 자동, 없으면 사람 승인 | 조치가 가역적인가, 서비스 영향이 있는가 | 인스턴스 종료·계정 비활성화는 사람 승인 유지(35.5) |

### 판단이 서지 않을 때의 세 가지 질문

1. **"이게 실패하면 어떻게 되지?"** — 2판 1장이 준 질문 그대로입니다. 답이 "전부 잃는다"면 층이 부족합니다.
2. **"침해되어도 여전히 믿을 수 있는 것이 남는가?"** — 로그와 백업이 여기 해당합니다. 남지 않는다면 경계가 부족합니다.
3. **"통제를 우회하는 게 따르는 것보다 쉬운가?"** — 그렇다면 통제 강도가 아니라 **통제의 사용성**을 고쳐야 합니다.

## 🔴 필수 구성 체크리스트

- [ ] ShopMini의 각 워크로드에 대해 **"이 역할의 자격 증명이 유출되면 무엇을 잃는가"** 를 한 문장으로 답할 수 있다
- [ ] 심층 방어 4개 층(SCP / IAM / 네트워크 / 리소스·키 정책)이 각각 **무엇을 막는지** 구분해 설명할 수 있다
- [ ] `shopmini-uploads` 버킷에 층 4(리소스 정책)가 존재한다 — IAM만 믿지 않는다
- [ ] KMS 키 접근은 **IAM 정책만으로는 불가능**하고 키 정책이 필요하다는 것을 이해했다
- [ ] VPC 내부 구간(ALB → 앱 8443, 앱 → RDS)도 **암호화·인증**된다
- [ ] 네트워크 경계가 IAM 경계를 **대신하지 못한다**는 것을 이해했다
- [ ] 운영 계정 관리자가 **로그와 백업을 삭제할 수 없는** 구조인지 확인했다(구현은 17·29·36장)
- [ ] 계정을 나누는 기준 세 가지(데이터 등급 / 침해 시 신뢰 범위 / 변경 주기)를 팀 문서로 정했다
- [ ] 콘솔에서 손으로 바꾼 구성이 **드리프트로 탐지되는지** 확인했다(구현은 28.4)
- [ ] 권한 요청부터 부여까지의 **리드타임**을 측정했고, 하루를 넘지 않는다
- [ ] 통제 예외 요청 경로(샌드박스 OU, 긴급 승격, 브레이크 글래스)가 **문서로 존재**한다

| 저위험 작업에까지 MFA를 매번 요구한다 | 사용자가 MFA 자체를 우회·공유 | 위험도 비례 재인증 (1.6, 9.4) |

## 다음 장 예고

이 장의 다섯 원칙은 "무엇을 지킬 것인가"를 정했습니다. 그런데 그중 일부는 애초에 내 책임이 아닙니다. 2장에서는 공동 책임 모델(Shared Responsibility Model)을 다룹니다. EC2·RDS·Lambda로 갈수록 책임선이 어떻게 이동하는지, 그리고 가장 많이 오해되는 다섯 개의 경계 — 데이터 암호화, 패치, 백업, IAM 설정, 가용 영역 설계 — 가 실제로 어느 쪽에 있는지를 비교표로 정리합니다. 관리형 서비스를 쓸수록 안전해지는지, 대신 어떤 리스크가 커지는지도 함께 봅니다.
