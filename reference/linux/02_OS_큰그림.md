# 2장. OS 큰 그림: 커널, 시스템 콜, 스케줄러

## 2.1 커널 모드와 유저 모드

CPU에는 최소 두 가지 특권 수준이 있다. x86-64에서는 ring 0(커널)과 ring 3(유저)이다.

- **유저 모드**: 내 프로그램이 도는 곳. 자기 가상 주소 공간의 메모리만 접근할 수 있고, 하드웨어에 직접 명령을 내릴 수 없다.
- **커널 모드**: 커널이 도는 곳. 모든 메모리와 하드웨어에 접근할 수 있다.

유저 모드 코드가 커널 모드로 들어가는 길은 정확히 세 가지뿐이다.

1. **시스템 콜** — 프로그램이 명시적으로 커널에 요청 (`read`, `write`, `mmap`...)
2. **인터럽트** — 하드웨어가 알림 (네트워크 패킷 도착, 타이머 틱, 디스크 I/O 완료)
3. **예외/폴트** — CPU가 명령 실행 중 문제를 감지 (페이지 폴트, 0으로 나누기, 잘못된 주소 접근)

이 세 가지 외에는 유저 코드가 커널을 "부를" 방법이 없다. 반대로 커널은 언제든(인터럽트로) 유저 코드를 중단시키고 다른 일을 할 수 있다. 이 비대칭이 "격리와 보호"의 근간이다.

## 2.2 시스템 콜: 프로그램이 커널에 말하는 유일한 방법

```c
ssize_t n = read(fd, buf, 4096);
```

이 한 줄에서 실제로 벌어지는 일:

```
유저 모드                              커널 모드
────────────────────────────────────────────────────────────
read(fd, buf, 4096)   ← glibc 래퍼 함수
  │ rax = 0 (SYS_read), rdi=fd, rsi=buf, rdx=4096
  │ syscall 명령         ────────────▶  entry_SYSCALL_64
  │                                      ├ 인자 검증 (buf가 정말 유저 메모리인가?)
  │                                      ├ fd → struct file 조회
  │                                      ├ 파일시스템/소켓/파이프의 read 구현 호출
  │                                      │   (데이터가 없으면 여기서 프로세스를 잠재움)
  │                                      └ 결과를 rax에 담아 복귀
  │ ◀──────────────────────────────────  sysret
  │ rax < 0 이면 errno = -rax, 반환값 -1
  ▼
n
```

기억할 것:

- **비용**: 시스템 콜 하나는 함수 호출보다 훨씬 비싸다(수십~수백 ns, Spectre 완화 패치가 있으면 더). 그래서 `read`를 1바이트씩 호출하는 코드는 느리고, stdio가 버퍼링을 하는 이유도 이것이다 ([7장](07_파일시스템과_IO.md)).
- **glibc는 래퍼일 뿐**: `read()`, `malloc()`, `printf()`는 시스템 콜이 아니라 라이브러리 함수다. `malloc`은 내부적으로 가끔만 `brk`/`mmap` 시스템 콜을 부르고, `printf`는 버퍼가 찰 때만 `write`를 부른다. **어떤 함수가 실제로 커널을 부르는지**를 구분하는 감각이 성능 분석의 시작이다.
- **`strace`로 보면 다 나온다**: `strace -c ./myprog`는 프로그램이 부른 시스템 콜을 종류별로 집계해준다 ([9장](09_디버깅과_도구.md)).

## 2.3 errno: 커널의 실패 통보 규약

시스템 콜은 실패하면 -1을 반환하고 전역(정확히는 스레드 로컬) 변수 `errno`에 이유를 넣는다.

```c
int fd = open("data.txt", O_RDONLY);
if (fd == -1) {
    perror("open");            // "open: No such file or directory"
    // errno == ENOENT
}
```

프로그래머가 반드시 알아야 할 errno 몇 가지:

| errno | 의미 | 실무에서 만나는 상황 |
|---|---|---|
| `EINTR` | 시그널에 의해 시스템 콜이 중단됨 | 블로킹 `read`/`accept` 중 시그널 도착. **재시도해야 한다** ([8장](08_시그널.md)) |
| `EAGAIN` / `EWOULDBLOCK` | 지금은 데이터가 없음(논블로킹) | 논블로킹 소켓에서 정상적인 상황. 에러가 아니다 ([6장](06_네트워크.md)) |
| `EMFILE` | 프로세스의 fd 한도 초과 | `ulimit -n` 기본 1024. 커넥션 많은 서버에서 흔함 |
| `ENOMEM` | 메모리 부족 | 실제로는 거의 안 나온다. 오버커밋 때문에 ([5장](05_메모리.md)) |
| `EPIPE` | 닫힌 파이프/소켓에 쓰기 | 상대가 끊었는데 `write`. 기본은 `SIGPIPE`로 프로세스가 죽는다 |
| `ECONNRESET` | 상대가 RST를 보냄 | 클라이언트가 비정상 종료 |
| `EADDRINUSE` | 주소가 이미 사용 중 | `TIME_WAIT` 소켓, `SO_REUSEADDR` 누락 |

`errno`는 성공한 호출에서는 변경되지 않을 뿐 **초기화도 안 된다**. 실패를 확인한 직후에만 읽어야 한다.

## 2.4 인터럽트와 "커널이 내 CPU 시간을 쓰는" 순간

네트워크 카드에 패킷이 도착하면 CPU에 인터럽트가 걸린다. 그 순간 어떤 프로세스가 돌고 있었건 CPU는 커널의 인터럽트 핸들러로 점프한다. 핸들러가 패킷을 큐에 넣고 복귀하면 원래 프로세스가 재개된다.

프로그래머에게 이게 왜 중요한가:

- `top`의 **`%si`(softirq)**, **`%hi`(hardirq)** 컬럼이 높다면 내 코드가 아니라 커널이 인터럽트 처리에 CPU를 쓰고 있다는 뜻이다. 패킷이 초당 수백만 개 들어오는 서버에서 흔하다.
- 내 스레드가 "아무것도 안 했는데" 지연이 튄다면, 인터럽트나 다른 프로세스에 CPU를 빼앗긴 것일 수 있다. 시스템 전체 관점 없이 내 코드만 프로파일링하면 원인을 못 찾는다.

## 2.5 스케줄러: 코어보다 많은 스레드를 어떻게 돌리나

리눅스 스케줄러의 단위는 **태스크(task)**다. 커널은 프로세스와 스레드를 구분하지 않고 모두 `task_struct` 하나로 다룬다([4장](04_스레드와_동시성.md)). 스케줄러는 "실행 가능한(runnable)" 태스크들 사이에서 CPU 시간을 나눈다.

### 태스크의 상태

```
          fork/clone
              │
              ▼
   ┌──────▶ Runnable (R) ──── 스케줄러가 선택 ────▶ Running
   │            ▲                                     │
   │            │ 이벤트 발생(데이터 도착, 락 해제 등)    │ I/O 대기, sleep, 락 대기
   │            │                                     ▼
   │        Sleeping ◀────────────────────────────────┘
   │         (S: interruptible / D: uninterruptible)
   │
   └──── 타임슬라이스 소진 또는 더 급한 태스크 등장(preemption)

   종료 → Zombie (Z) → 부모가 wait() → 소멸
```

`ps`/`top`의 STAT 컬럼이 이것이다. 프로그래머가 알아야 할 상태:

- **R**: 실행 중이거나 실행 대기 중. CPU를 원하는 태스크의 수가 코어 수보다 많으면 `load average`가 올라간다.
- **S**: 인터럽트 가능한 대기. `read`로 데이터를 기다리거나 `sleep` 중. 시그널로 깨울 수 있다. 서버 프로세스의 대부분은 평소에 이 상태다.
- **D**: 인터럽트 불가능한 대기. 주로 디스크 I/O나 NFS. **`kill -9`로도 안 죽는다**. D 상태 프로세스가 많으면 I/O 병목이다. load average에도 포함된다는 점을 기억하자. CPU는 놀고 있는데 load가 높은 이유.
- **Z**: 좀비. 종료했지만 부모가 회수하지 않음 ([3장](03_프로세스.md)).

### CFS와 EEVDF

리눅스는 오랫동안 **CFS(Completely Fair Scheduler)**를 썼고, 6.6부터 **EEVDF**로 교체됐다. 두 가지 모두 핵심 아이디어는 같다.

- 각 태스크의 **가상 실행 시간(vruntime)**을 추적하고, 가장 적게 실행된 태스크를 다음에 고른다. "공평하게 나눈다"가 기본값이다.
- **nice 값(-20 ~ +19)**은 가중치다. nice가 낮을수록 vruntime이 느리게 쌓여 더 많은 CPU를 받는다. `nice -n 10 ./batch_job`은 "다른 것들에 양보하라"는 뜻이다.
- 고정된 타임슬라이스는 없다. 실행 가능한 태스크 수에 따라 동적으로 정해진다(기본 목표 지연 6ms 정도, 태스크가 많으면 최소 0.75ms 정도까지 줄어듦).

프로그래머에게 중요한 결과:

- **I/O 바운드 태스크는 자연히 우선권을 얻는다.** 자주 잠들어서 vruntime이 적게 쌓이기 때문이다. 대화형 프로그램이 배치 작업 옆에서도 반응이 좋은 이유.
- **스레드를 코어 수보다 훨씬 많이 만들면 얻는 게 없다.** CPU 바운드 작업이라면 스레드 수 = 코어 수가 상한이다. 그 이상은 컨텍스트 스위칭 비용만 늘린다.
- **`SCHED_FIFO`/`SCHED_RR`(실시간 정책)**은 CFS 태스크들보다 항상 우선한다. 잘못 쓰면 시스템이 멈춘다. 일반 서버 코드에서는 쓸 일이 거의 없다.

### 컨텍스트 스위칭의 진짜 비용

한 태스크에서 다른 태스크로 전환하는 직접 비용(레지스터 저장/복원)은 1~2µs 정도로 크지 않다. 진짜 비용은 **간접 비용**이다.

- **CPU 캐시 오염**: 새 태스크가 L1/L2를 자기 데이터로 채우면서 이전 태스크의 캐시가 밀려난다. 다시 돌아왔을 때 캐시 미스가 쏟아진다.
- **TLB 플러시**: 다른 프로세스로 전환하면 주소 공간이 바뀌므로 TLB가 무효화된다(같은 프로세스의 스레드 간 전환은 이 비용이 없다) ([5장](05_메모리.md)).

`vmstat 1`의 `cs` 컬럼으로 초당 컨텍스트 스위치 수를 볼 수 있다. 수만~수십만이면 "스레드가 너무 많거나 락 경합이 심하다"는 신호다.

## 2.6 컨테이너 시대의 스케줄러: cgroup CPU 제한

도커의 `--cpus=2`는 **cgroup의 CPU 대역폭 제어**다. 100ms 주기마다 200ms의 CPU 시간(2코어분)을 쿼터로 준다. 쿼터를 다 쓰면 다음 주기까지 컨테이너 안의 모든 태스크가 **스로틀링**된다.

함정: 컨테이너에 스레드가 16개인데 `--cpus=2`라면, 16개가 동시에 뛰어들어 12.5ms 만에 쿼터를 소진하고 나머지 87.5ms를 통째로 멈춘다. 지연 시간이 들쭉날쭉해지는 전형적인 원인이다.

- 확인: `cat /sys/fs/cgroup/cpu.stat` 의 `nr_throttled`, `throttled_usec`
- 대응: 스레드 풀 크기를 실제 쿼터에 맞춘다. 많은 런타임(Java 10+, Go 1.25+, .NET)이 cgroup 한도를 자동 인식하지만, 직접 `nproc`이나 `sysconf(_SC_NPROCESSORS_ONLN)`으로 코어 수를 읽는 코드는 **호스트의 코어 수**를 얻는다는 점을 기억해야 한다.

## 2.7 /proc과 /sys: 커널 속을 들여다보는 창

리눅스는 커널 내부 상태를 **파일처럼 읽을 수 있게** 노출한다. `/proc`은 가상 파일시스템이며, 디스크에 없다.

```bash
cat /proc/self/status        # 지금 이 셸 프로세스의 상태 (VmRSS, Threads, State...)
ls -l /proc/self/fd          # 열린 파일 디스크립터 목록
cat /proc/self/maps          # 가상 주소 공간 레이아웃
cat /proc/cpuinfo            # CPU 정보
cat /proc/meminfo            # 시스템 메모리 통계
cat /proc/loadavg            # load average
cat /proc/sys/fs/file-max    # 시스템 전체 fd 한도 (쓰기도 가능 — 커널 파라미터 변경)
```

`ps`, `top`, `free`, `lsof` 같은 도구는 전부 `/proc`을 읽어서 보여주는 것이다. 도구가 없는 최소 컨테이너 환경에서도 `cat /proc/...`만은 항상 된다. 이 책의 모든 장에서 `/proc`이 등장한다.

## 2.9 다른 OS에서는

| 개념 | Linux | Windows |
|---|---|---|
| 커널 진입 | `syscall` 명령, glibc 래퍼 | `syscall`, ntdll.dll 래퍼 (Nt* 함수) |
| 에러 통보 | 반환값 -1 + `errno` | 반환값 + `GetLastError()`, NTSTATUS |
| 스케줄링 단위 | 태스크(`task_struct`) | 스레드(KTHREAD) |
| 스케줄러 | CFS/EEVDF (공정 분배, nice 가중치) | 우선순위 기반 선점형 (0~31 레벨) |
| 커널 상태 관찰 | `/proc`, `/sys` | WMI, Performance Counters, ETW |
| CPU 제한 | cgroup cpu.max | Job Object |

**더 깊이**: TLPI 2~3장(기본 개념, 시스템 콜), 35장(스케줄링), 12장(`/proc`). *How Linux Works* 1장, 8장.
