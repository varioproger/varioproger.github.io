# 7장. 파일시스템과 I/O

## 7.1 파일 디스크립터의 세 계층

`open()`이 반환하는 정수 하나 뒤에는 세 개의 커널 테이블이 있다.

```
프로세스 A의 fd 테이블        시스템 전체 open file table          inode 테이블
┌────┬──────┐              ┌─────────────────────────┐        ┌──────────────┐
│ 0  │  ────┼──────────▶   │ 오프셋=0, 플래그=O_RDONLY  ├──────▶ │ inode 1234    │
│ 1  │  ────┼──────┐       ├─────────────────────────┤        │ (크기, 권한,   │
│ 2  │  ────┼──────┤       │ 오프셋=512, O_WRONLY|APPEND├──┐    │  블록 위치...)  │
│ 3  │  ────┼───┐  └─────▶ │ 오프셋=0, O_RDWR          │  │    └──────────────┘
└────┴──────┘   │          └─────────────────────────┘  │
                │                       ▲                │    ┌──────────────┐
프로세스 B (A를 fork)                    │                └──▶ │ inode 5678    │
┌────┬──────┐   │                       │                     └──────────────┘
│ 3  │  ────┼───┴───────────────────────┘  ← fork로 복제된 fd는 같은 open file을 가리킴
└────┴──────┘                                 → 오프셋을 공유한다!
```

1. **fd 테이블(프로세스별)**: 정수 → open file 항목 포인터. `fork`하면 복사되고, `dup`하면 같은 항목을 가리키는 새 번호가 생긴다.
2. **open file table(시스템 전체)**: 파일 오프셋, 열기 플래그(`O_APPEND`, `O_NONBLOCK`), inode 포인터. **오프셋이 여기 있다**는 것이 중요하다.
3. **inode**: 파일의 실체. 크기, 권한, 소유자, 타임스탬프, 데이터 블록 위치. **파일 이름은 여기 없다.** 이름은 디렉터리 항목(dentry)이 가진다.

이 구조가 설명하는 현상들:

- **`fork` 후 부모와 자식이 같은 파일에 쓰면 오프셋을 공유**하므로 서로 덮어쓰지 않고 이어 쓴다. 셸에서 `(echo a; echo b) > f`가 동작하는 원리.
- 반대로 **같은 파일을 두 번 `open`하면 오프셋이 각각**이다. 두 프로세스가 로그 파일을 따로 열고 `write`하면 서로 덮어쓴다. `O_APPEND`가 필요한 이유(아래 7.5).
- `dup2(fd, 1)`으로 stdout을 파일로 바꾸는 리다이렉션은 fd 테이블의 항목 1을 바꾸는 것뿐이다.
- **열린 파일을 `rm`해도 디스크 용량이 안 줄어든다.** `rm`은 디렉터리 항목만 지운다(`unlink`). inode는 링크 수가 0이고 **열고 있는 fd도 0**일 때 해제된다. 로그를 `rm`했는데 용량이 안 돌아오면 `lsof | grep deleted`로 아직 열고 있는 프로세스를 찾아라. 그 프로세스를 재시작하거나 `> /proc/<pid>/fd/N`으로 비운다. 반대로 이 성질을 이용해 임시 파일을 만들자마자 `unlink`하면 프로세스가 죽어도 자동으로 사라진다.

**fd 누수**: 에러 경로에서 `close`를 빠뜨리면 fd가 쌓여 `EMFILE`(Too many open files)로 죽는다. `ls /proc/<pid>/fd | wc -l`을 시간에 따라 보면 잡힌다.

## 7.2 "모든 것은 파일이다"의 실제 의미

| 것 | 어떻게 fd가 되나 | 무엇을 할 수 있나 |
|---|---|---|
| 일반 파일 | `open` | read/write/mmap/fsync |
| 디렉터리 | `open` + `getdents` | 항목 열람, `openat`의 기준점 |
| 파이프/FIFO | `pipe`, `open` | read/write, epoll |
| 소켓 | `socket`, `accept` | read/write/send/recv, epoll |
| 디바이스 (`/dev/sda`, `/dev/null`, `/dev/urandom`) | `open` | read/write/ioctl |
| 타이머 | `timerfd_create` | read(만료 횟수), epoll |
| 시그널 | `signalfd` | read(시그널 정보), epoll |
| 프로세스 | `pidfd_open` | poll(종료 대기), `pidfd_send_signal` |
| 이벤트 카운터 | `eventfd` | read/write, epoll |
| 익명 메모리 | `memfd_create` | mmap, fd 전달로 공유 메모리 |
| 커널 내부 상태 | `/proc`, `/sys` | read/write(설정 변경) |

이 통일성 덕분에 이벤트 루프 하나가 "소켓에 데이터가 왔거나, 타이머가 울렸거나, SIGTERM이 왔거나, 자식이 죽었거나"를 `epoll_wait` 한 번으로 기다릴 수 있다.

## 7.3 VFS: 파일시스템이 여러 개인데 API는 하나인 이유

`read()`는 ext4, xfs, btrfs, tmpfs, NFS, overlayfs(도커 이미지 레이어), procfs 어디에서나 같다. 커널의 **VFS(Virtual File System)** 계층이 공통 인터페이스(`struct file_operations`)를 정의하고 각 파일시스템이 구현한다. 프로그래머에게 중요한 결과:

- 성능 특성은 파일시스템마다 다르다. tmpfs는 RAM이고, NFS는 네트워크이며, overlayfs는 첫 쓰기 시 파일 전체를 상위 레이어로 복사한다(도커 컨테이너 안에서 큰 파일을 수정하면 느린 이유. 볼륨을 써라).
- `mount`로 트리 어디든 다른 파일시스템을 붙일 수 있다. `/proc`, `/sys`, `/dev/shm`(tmpfs)이 그렇다.
- `df`는 마운트 지점별 용량이고, `du`는 디렉터리 트리 합계다. 둘이 다르면 삭제된 열린 파일(7.1)이나 마운트로 가려진 디렉터리다.

## 7.4 I/O 버퍼링: write()는 디스크에 쓰지 않는다

```
printf("log line\n")          ← 1. stdio 버퍼 (유저 공간, 보통 4~8KB)
   │ fflush() 또는 버퍼 가득/줄바꿈(터미널일 때)
   ▼
write(fd, ...)                ← 2. 페이지 캐시 (커널 메모리). 여기서 write()는 성공 반환
   │ 커널 writeback 스레드 (수 초 후) 또는 fsync()
   ▼
디스크 컨트롤러 캐시            ← 3. 디스크 자체 캐시 (fsync는 여기까지 플러시 요청)
   │
   ▼
플래터/NAND                   ← 4. 진짜 영속
```

각 층의 함정:

**1층, stdio 버퍼**: `printf`로 쓴 로그가 크래시 직전 내용이 안 보이는 이유. stdout이 터미널이면 줄 단위 버퍼링, **파일이나 파이프면 전체 버퍼링**이다. 컨테이너에서 `docker logs`에 파이썬 출력이 안 나오는 고전적 문제가 이것이다(`PYTHONUNBUFFERED=1`, `setvbuf`, `stderr` 사용). `_exit()`나 시그널로 죽으면 stdio 버퍼는 플러시되지 않는다.

**2층, 페이지 캐시**: `write` 성공은 "커널이 받았다"는 뜻이다. 정전이면 사라진다. 기본 최대 30초(`dirty_expire_centisecs`)까지 메모리에만 있다. 또 dirty 페이지가 `dirty_ratio`(기본 20%)를 넘으면 **`write`가 갑자기 블로킹**된다. 대량 쓰기 중 지연이 튀는 원인.

**3층, fsync**: `fsync(fd)`는 그 파일의 dirty 페이지와 메타데이터를 디스크에 쓰고 디스크 캐시도 플러시하라고 요청한 뒤 **완료까지 기다린다.** 수 ms(SSD)~수십 ms(HDD). DB가 커밋마다 하는 것이 이것이며, DB 쓰기 성능의 하한을 정한다. `fdatasync`는 메타데이터(mtime 등)를 빼고 데이터만 보장하므로 조금 빠르다.

**중요한 함정: 새 파일을 만들었으면 디렉터리도 fsync해야 한다.** 파일 내용을 fsync해도 그 파일의 **이름(디렉터리 항목)**은 디렉터리 inode에 속하므로 별도다. 크래시 후 "파일은 있는데 디렉터리에 없는" 상태가 될 수 있다.

**`O_DIRECT`**: 페이지 캐시를 우회해 유저 버퍼에서 디스크로 직접 간다. 자기 캐시를 가진 DB(PostgreSQL은 안 쓰고, MySQL InnoDB는 씀)가 이중 캐시를 피하려 쓴다. 버퍼 정렬 제약(512B/4KB)이 있고, 커널 readahead의 이득을 잃는다. 일반 애플리케이션은 쓸 이유가 없다.

## 7.5 원자성: 크래시 후에도 파일이 깨지지 않게

POSIX가 보장하는 원자 연산은 몇 개뿐이다. 그것을 조합하는 것이 신뢰성 있는 파일 코드의 전부다.

- **`O_APPEND` 쓰기**: "끝으로 이동 + 쓰기"가 원자적이다. 여러 프로세스가 같은 로그 파일에 append하면 줄이 섞이지 않는다(단일 `write` 호출이 `PIPE_BUF`(4KB) 이하일 때 실질적으로). `lseek(END)` + `write`는 원자적이지 **않다.**
- **`rename(old, new)`**: 같은 파일시스템 안에서 원자적이다. `new`가 이미 있으면 교체된다. 관찰자는 옛 파일 또는 새 파일만 보고, 중간 상태를 보지 않는다.
- **`O_CREAT | O_EXCL`**: "없으면 만들고, 있으면 실패"가 원자적이다. 락 파일에 쓴다. (NFS에서는 옛 버전에서 보장되지 않는다.)
- **`link`, `unlink`, `mkdir`**: 각각 원자적.

### 설정 파일 안전하게 덮어쓰기

```c
// 나쁜 예: 쓰는 도중 크래시하면 config.json이 절반만 남는다
fd = open("config.json", O_WRONLY | O_TRUNC);
write(fd, data, n);
close(fd);

// 올바른 패턴: 임시 파일에 쓰고 fsync한 뒤 rename
fd = open("config.json.tmp", O_WRONLY | O_CREAT | O_TRUNC, 0644);
write(fd, data, n);
fsync(fd);                       // 데이터가 디스크에
close(fd);
rename("config.json.tmp", "config.json");   // 원자적 교체
dfd = open(".", O_RDONLY);
fsync(dfd);                      // 디렉터리 항목 변경도 디스크에
close(dfd);
```

이 패턴이 텍스트 에디터의 "저장", 패키지 매니저, DB의 체크포인트에 쓰인다. `rename`을 안 하고 제자리에 쓰면 절반짜리 파일이 남을 수 있다.

## 7.6 파일 락

여러 프로세스가 같은 파일을 조율하려면 락이 필요하다. 리눅스에는 서로 호환되지 않는 세 종류가 있다.

| 종류 | API | 특징 |
|---|---|---|
| BSD 락 | `flock(fd, LOCK_EX)` | 파일 전체. **open file 항목**에 붙음(fork 후 공유). 단순. NFS 지원은 최근 |
| POSIX 레코드 락 | `fcntl(F_SETLK)` | 바이트 범위. **프로세스**에 붙음. **같은 프로세스가 그 파일의 어떤 fd든 닫으면 락이 풀린다**(악명 높은 함정). 스레드 간 동작 안 함 |
| Open file description 락 | `fcntl(F_OFD_SETLK)` | 레코드 락의 함정을 고친 리눅스 버전. 새 코드에서 권장 |

모두 **권고(advisory) 락**이다. 락을 확인하지 않는 프로세스는 그냥 쓸 수 있다. 참여자 모두가 같은 락을 쓰기로 약속해야 한다. "이미 실행 중인지 확인"하는 PID 파일 패턴은 `flock`으로 락 파일을 잡는 것이 `O_EXCL` 파일 생성보다 낫다. 프로세스가 죽으면 커널이 자동으로 락을 놓기 때문이다.

## 7.7 디렉터리, 링크, 경로

- **하드 링크**: 같은 inode를 가리키는 다른 이름. `ln a b`. 링크 수가 2가 되고, 둘 다 지워야 inode가 해제된다. 디렉터리에는 못 만들고, 파일시스템 경계를 못 넘는다.
- **심볼릭 링크**: 경로 문자열을 담은 별도 파일. 대상이 없어도 존재할 수 있다(dangling). `open`은 따라가고, `lstat`/`readlink`는 링크 자체를 본다. 보안 함정: 권한 있는 프로세스가 `/tmp/foo`를 열 때 공격자가 그 자리에 `/etc/passwd`로의 심볼릭 링크를 만들어둘 수 있다. `O_NOFOLLOW`, `openat2`의 `RESOLVE_*` 플래그로 막는다.
- **`openat(dirfd, "relative", ...)`**: 디렉터리 fd 기준의 상대 경로. 경로 해석 중 상위 디렉터리가 바뀌는 레이스(TOCTOU)를 막고, 스레드마다 다른 "현재 디렉터리"를 흉내 낼 수 있다(프로세스의 cwd는 스레드 간 공유다).
- 경로 해석 비용: 경로 요소마다 dentry 캐시 조회. 깊은 경로의 수십만 파일을 다루는 코드는 `openat`으로 디렉터리 fd를 재사용하면 빨라진다.

## 7.8 파일 변경 감시: inotify

폴링 대신 커널이 알려준다. `inotify_init` → `inotify_add_watch(fd, "/path", IN_MODIFY|IN_CREATE|...)` → fd를 `read`(또는 epoll). 파일 동기화 도구, 핫 리로드, 로그 수집기가 쓴다. 한계: **재귀적이지 않다**(하위 디렉터리마다 watch 필요), watch 수 한도(`fs.inotify.max_user_watches`, VS Code가 "ENOSPC" 내는 원인), NFS/FUSE 미지원. `fanotify`가 더 넓은 범위를 다룬다.

## 7.9 디스크 I/O 성능 감각

| 매체 | 순차 처리량 | 임의 4KB 읽기 지연 | 초당 임의 IOPS |
|---|---|---|---|
| HDD | 150~250 MB/s | ~10 ms | 100~200 |
| SATA SSD | ~550 MB/s | ~100 µs | 수만 |
| NVMe SSD | 3~7 GB/s | ~20 µs | 수십만~백만 |
| 클라우드 네트워크 디스크(EBS gp3) | 125~1000 MB/s | ~1 ms | 3000~16000 (프로비저닝) |

- HDD는 **순차 vs 임의 접근**이 100배 차이다. LSM 트리, WAL(로그 선행 기록)이 존재하는 이유. SSD에서는 차이가 줄지만 여전히 순차가 빠르다.
- 클라우드 디스크는 **IOPS 한도**가 걸려 있다. 작은 임의 쓰기(예: fsync가 잦은 DB)가 처리량이 아니라 IOPS로 막힌다. `iostat -x 1`의 `%util`, `aqu-sz`, `r_await`/`w_await`로 확인한다.
- 커널은 **readahead**로 순차 읽기를 미리 가져온다. 임의 접근이라면 `posix_fadvise(POSIX_FADV_RANDOM)`으로 끄고, 한 번만 읽을 큰 파일은 `POSIX_FADV_DONTNEED`로 캐시에서 빨리 빼라고 힌트를 줄 수 있다.

## 7.10 직접 확인해보기

```bash
ls -l /proc/<pid>/fd; ls /proc/<pid>/fd | wc -l      # 열린 fd, fd 수 (누수 감시)
lsof -p <pid>; lsof +L1                              # 삭제됐지만 열려 있는 파일
stat file; ls -li                                    # inode 번호, 링크 수
cat /proc/<pid>/fdinfo/<fd>                          # 오프셋, 플래그
grep -E 'Dirty|Writeback' /proc/meminfo              # 아직 디스크에 안 쓴 페이지
iostat -x 1                                          # 디스크별 사용률, 대기 시간
strace -e trace=file,desc -p <pid>                   # open/read/write/close 추적
df -h; du -sh /var/log                               # 마운트별 용량 vs 디렉터리 합계
```

## 7.12 다른 OS에서는

| 개념 | Linux | Windows |
|---|---|---|
| 참조자 | fd (작은 정수) | HANDLE |
| 열린 채 삭제 | 가능. 링크 수 0 + fd 0일 때 해제 | 기본 불가(공유 위반). `FILE_SHARE_DELETE` 필요 |
| 원자적 교체 | `rename` | `MoveFileEx(MOVEFILE_REPLACE_EXISTING)`, `ReplaceFile` |
| 디스크 반영 강제 | `fsync`, `fdatasync` | `FlushFileBuffers` |
| 캐시 우회 | `O_DIRECT` | `FILE_FLAG_NO_BUFFERING` |
| 파일 락 | `flock`/`fcntl` (권고) | `LockFileEx` (강제) |
| 변경 감시 | `inotify`, `fanotify` | `ReadDirectoryChangesW` |
| 경로 구분자, 대소문자 | `/`, 구분함 | `\`, 구분 안 함 |

**더 깊이**: TLPI 4~5장(파일 I/O), 13장(버퍼링), 14~15장(파일시스템, 속성), 18장(디렉터리와 링크), 19장(inotify), 55장(파일 락). *How Linux Works* 3~4장(디바이스, 디스크와 파일시스템).
