# Terraform · Docker · Kubernetes · AWS EKS 구조 이해

> 전체 학습 후에는 [최종 이해도 문제집](../../03_최종_이해도_문제집/README.md)으로 구조 이해, 흐름 추적, 장애 진단과 설계 능력을 점검하세요.

> 목표: 도구 이름을 외우는 대신, 웹 서비스 하나가 만들어지고 실행되고 복구되는 과정을 그림으로 설명한다.

## 먼저 기억할 한 문장

**Docker로 실행할 이미지를 만들고, Kubernetes로 그 이미지의 실행 상태를 유지하고, EKS로 Kubernetes 운영의 일부를 AWS에 맡기며, Terraform으로 그 기반 자원을 코드로 관리한다.**

네 가지가 순서대로 요청을 전달하는 일렬의 서버들은 아니다. **만드는 흐름, 제어하는 흐름, 요청이 흐르는 길**이 서로 다르다.

## 학습 범위와 기준

예시는 **Linux 컨테이너, 일반 EKS + EC2 Managed Node Group, Amazon VPC CNI, AWS Load Balancer Controller, ALB IP target**을 기준으로 한다. 이 구성을 먼저 이해하고, EKS Auto Mode처럼 AWS가 더 많은 작업을 맡는 방식은 차이만 확인한다. 모든 EKS 클러스터가 이 구성인 것은 아니다.

이 교재는 설치 매뉴얼이나 실제 AWS 배포 프로젝트가 아니다. 짧은 설정 예시는 각 도구가 무엇을 입력받는지 읽기 위한 것이다. AWS 자원 생성이나 계정 변경은 수행하지 않았다.

## 자료를 어떻게 재구성했는가

현재 폴더의 PDF 7개 **5,527쪽 전체에 텍스트 추출과 주제 검색**을 수행하고, 목차·핵심 본문·대표 도해를 대조했다. 모든 문장을 순서대로 정독하거나 모든 실습 코드를 실행한 것은 아니다. 구조 이해에 필요한 부분을 선별해 설명하고, 전체 자료의 주요 주제는 독서 지도에 분류했다.

교체된 Terraform 원본 592쪽도 포함했다. 특히 **7장의 AWS + Kubernetes provider 통합 예제**가 네 도구의 연결을 직접 보여 주므로, 기본 교재를 읽은 뒤 찾아갈 우선 구간으로 지정했다. 오래된 API·실행 환경 설명은 공식 문서와 대조했다.

원문을 번역해 이어 붙이는 대신, 여러 자료의 공통 개념을 하나의 서비스 예시로 연결했다. 기존 PDF와 파일명은 유지했다. 출처 페이지는 **PDF 뷰어의 1부터 시작하는 페이지 번호**이며, 종이에 인쇄된 쪽수와 다를 수 있다. 공식 웹 문서 확인일은 2026-09-05다.

## 공부를 마쳤다고 판단하는 기준

다음 질문에 그림을 그리며 답할 수 있으면 첫 학습 목표를 달성한 것이다.

1. Terraform 실행이 끝났는데 Pod는 누가 계속 관리하는가?
2. Docker Engine이 없는 노드에서 Docker로 만든 이미지는 왜 실행되는가?
3. EKS의 Kubernetes API 주소와 사용자가 접속하는 서비스 주소는 왜 다른가?
4. Pod IP가 바뀌어도 서비스에 접속할 수 있는 이유는 무엇인가?
5. Pod를 늘렸는데 왜 노드나 IP가 부족할 수 있는가?
6. AWS가 EKS를 관리해도 애플리케이션 장애와 데이터 백업이 왜 내 책임으로 남는가?

### 답변할 때 사용할 문장 틀

‘어떤 도구 때문이다’에서 멈추지 말고 **누가 → 무엇을 관찰하거나 입력받고 → 무엇을 바꾸는가**를 말한다. 예를 들어 ‘Service가 알아서 한다’보다 ‘EndpointSlice controller가 selector와 Pod 상태를 보고 대상 목록을 갱신하고, kube-proxy 등이 전달 규칙을 갱신한다’가 원리를 설명하는 답이다.

Node는 장소, kubelet·containerd는 프로그램, OCI·CRI는 규격·인터페이스라는 구분부터 확인한다. 화살표가 **포함 관계인지, 요청인지, 파일 전달인지**도 함께 말한다.
