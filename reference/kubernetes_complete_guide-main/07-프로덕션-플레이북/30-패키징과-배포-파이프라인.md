# 30장. 패키징과 배포 파이프라인

> **학습목표**
> - Helm 차트를 작성하고 릴리스를 관리할 수 있다.
> - Kustomize 오버레이로 환경별 구성을 표현할 수 있다.
> - 두 도구의 차이와 조합 방법을 안다.
> - GitOps의 원칙을 이해하고 Argo CD나 Flux로 구현할 수 있다.
> - 프로그레시브 딜리버리로 자동 롤백을 구성할 수 있다.
> - 배포 파이프라인 전체를 설계할 수 있다.

---

## 들어가며

지금까지 `kubectl apply -f`로 배포했다. 프로덕션에서는 이것으로 부족하다.

- 환경마다 다른 값(replica 수, 이미지 태그, 리소스)을 어떻게 관리하나?
- 누가 언제 무엇을 배포했는지 어떻게 추적하나?
- 클러스터의 실제 상태가 의도한 상태와 같은지 어떻게 아나?
- 배포가 잘못됐을 때 어떻게 되돌리나?

이 장은 그 답이다.

## 30.1 Helm

### 개념

**차트(chart)** 는 쿠버네티스 매니페스트의 템플릿 묶음이다. **값(values)** 을 주입해 렌더링하고, 그 결과를 **릴리스(release)** 로 설치한다.

```
차트 + 값  →  렌더링  →  매니페스트  →  클러스터
                              ↓
                        릴리스로 추적
```

### 차트 구조

```bash
helm create webapp
```

```
webapp/
├── Chart.yaml           # 메타데이터
├── values.yaml          # 기본값
├── values.schema.json   # 값 검증 (선택)
├── charts/              # 하위 차트
├── crds/                # CRD (특별 취급, 28.6절)
└── templates/
    ├── _helpers.tpl     # 재사용 템플릿
    ├── deployment.yaml
    ├── service.yaml
    ├── ingress.yaml
    ├── hpa.yaml
    ├── serviceaccount.yaml
    ├── NOTES.txt        # 설치 후 안내 메시지
    └── tests/
        └── test-connection.yaml
```

**Chart.yaml**

```yaml
apiVersion: v2
name: webapp
description: A web application
type: application
version: 1.2.3              # ★ 차트 버전 (SemVer)
appVersion: "2.4.0"         # ★ 앱 버전 (독립적)
dependencies:
  - name: postgresql
    version: "15.x.x"
    repository: https://charts.bitnami.com/bitnami
    condition: postgresql.enabled
```

**`version`과 `appVersion`은 다르다.** 차트만 고쳐도 `version`은 올라가지만 `appVersion`은 그대로일 수 있다.

### 템플릿 작성

```yaml
# templates/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "webapp.fullname" . }}
  labels:
    {{- include "webapp.labels" . | nindent 4 }}
spec:
  {{- if not .Values.autoscaling.enabled }}
  replicas: {{ .Values.replicaCount }}
  {{- end }}
  selector:
    matchLabels:
      {{- include "webapp.selectorLabels" . | nindent 6 }}
  template:
    metadata:
      annotations:
        # ★ 7.6절의 체크섬 패턴 — 설정 변경 시 자동 롤아웃
        checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}
        {{- with .Values.podAnnotations }}
        {{- toYaml . | nindent 8 }}
        {{- end }}
      labels:
        {{- include "webapp.selectorLabels" . | nindent 8 }}
    spec:
      serviceAccountName: {{ include "webapp.serviceAccountName" . }}
      securityContext:
        {{- toYaml .Values.podSecurityContext | nindent 8 }}
      containers:
        - name: {{ .Chart.Name }}
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag | default .Chart.AppVersion }}"
          imagePullPolicy: {{ .Values.image.pullPolicy }}
          securityContext:
            {{- toYaml .Values.securityContext | nindent 12 }}
          ports:
            - name: http
              containerPort: {{ .Values.service.targetPort }}
          {{- with .Values.env }}
          env:
            {{- toYaml . | nindent 12 }}
          {{- end }}
          livenessProbe:
            {{- toYaml .Values.livenessProbe | nindent 12 }}
          readinessProbe:
            {{- toYaml .Values.readinessProbe | nindent 12 }}
          resources:
            {{- toYaml .Values.resources | nindent 12 }}
      {{- with .Values.nodeSelector }}
      nodeSelector:
        {{- toYaml . | nindent 8 }}
      {{- end }}
      {{- with .Values.topologySpreadConstraints }}
      topologySpreadConstraints:
        {{- toYaml . | nindent 8 }}
      {{- end }}
```

### 릴리스 관리

```bash
# 렌더링 확인 (설치 안 함)
helm template myapp ./webapp --values values-prod.yaml
helm install myapp ./webapp --dry-run --debug

# 설치
helm install myapp ./webapp -n prod --create-namespace \
  --values values-prod.yaml \
  --set image.tag=2.4.1 \
  --wait --timeout 5m

# 업그레이드
helm upgrade myapp ./webapp -n prod \
  --values values-prod.yaml \
  --set image.tag=2.4.2 \
  --atomic                       # ★ 실패 시 자동 롤백
  --wait --timeout 5m

# 이력과 롤백
helm history myapp -n prod
helm rollback myapp 3 -n prod

# 차이 확인 (플러그인)
helm plugin install https://github.com/databus23/helm-diff
helm diff upgrade myapp ./webapp -n prod --values values-prod.yaml
```

**`--atomic`이 중요하다.** 업그레이드가 실패하면 이전 상태로 자동 복구한다.

### 훅

```yaml
# templates/migration-job.yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: {{ include "webapp.fullname" . }}-migrate
  annotations:
    "helm.sh/hook": pre-upgrade,pre-install
    "helm.sh/hook-weight": "-5"
    "helm.sh/hook-delete-policy": before-hook-creation,hook-succeeded
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          command: ["./manage.py", "migrate"]
```

| 훅 | 시점 |
|---|---|
| `pre-install` / `post-install` | 설치 전후 |
| `pre-upgrade` / `post-upgrade` | 업그레이드 전후 |
| `pre-delete` / `post-delete` | 삭제 전후 |
| `pre-rollback` / `post-rollback` | 롤백 전후 |
| `test` | `helm test` 실행 시 |

**DB 마이그레이션에 유용하다.** 다만 8.2절에서 말했듯 **롤백으로 마이그레이션이 되돌아가지는 않는다.**

### Helm의 한계

> **⚠️ CRD 업그레이드 문제**
> 28.6절에서 언급한 그것이다. `helm upgrade`는 **`crds/` 디렉터리를 무시한다.**
> ```bash
> kubectl apply -f charts/myoperator/crds/     # 수동
> helm upgrade myoperator ./charts/myoperator
> ```
> 대안: CRD를 `templates/`에 두고 `helm.sh/resource-policy: keep` 애노테이션을 붙이는 방법도 있지만, 삭제 시 남는 문제가 생긴다.

**다른 한계들**

- **템플릿이 문자열 조작이다.** YAML 구조를 이해하지 못하므로 들여쓰기 오류가 나기 쉽다
- **릴리스 상태가 Secret에 저장된다.** 그 Secret이 손상되면 복구가 번거롭다
- **`helm upgrade`가 실패한 상태(`pending-upgrade`)** 에 빠지면 수동 개입이 필요하다

```bash
# 멈춘 릴리스 복구
helm rollback myapp -n prod
# 또는
kubectl delete secret -n prod -l owner=helm,status=pending-upgrade
```

## 30.2 Kustomize

### 접근이 다르다

Helm이 **템플릿**이라면 Kustomize는 **패치**다. 원본 YAML은 그대로 두고 오버레이로 수정한다.

```
base/                    ← 유효한 YAML (그대로 apply 가능)
  kustomization.yaml
  deployment.yaml
  service.yaml
overlays/
  dev/
    kustomization.yaml
    patch-replicas.yaml
  prod/
    kustomization.yaml
    patch-replicas.yaml
    patch-resources.yaml
```

**base/kustomization.yaml**

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

resources:
  - deployment.yaml
  - service.yaml

commonLabels:
  app.kubernetes.io/name: webapp

images:
  - name: webapp
    newName: registry.example.com/webapp
    newTag: "2.4.0"
```

**overlays/prod/kustomization.yaml**

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

namespace: prod
namePrefix: prod-

resources:
  - ../../base
  - hpa.yaml                     # prod에만 있는 리소스
  - pdb.yaml

commonLabels:
  environment: production

images:
  - name: webapp
    newTag: "2.4.1"              # ★ 이미지 태그만 오버라이드

replicas:
  - name: webapp
    count: 10

# ★ 내용 해시가 이름에 붙는다 (7.6절)
configMapGenerator:
  - name: app-config
    literals:
      - LOG_LEVEL=info
      - FEATURE_X=true

secretGenerator:
  - name: app-secret
    envs:
      - secrets.env

patches:
  # ① 전략적 병합 패치
  - path: patch-resources.yaml
    target:
      kind: Deployment
      name: webapp

  # ② JSON 패치 (인라인)
  - target:
      kind: Deployment
      name: webapp
    patch: |-
      - op: add
        path: /spec/template/spec/topologySpreadConstraints
        value:
          - maxSkew: 1
            topologyKey: topology.kubernetes.io/zone
            whenUnsatisfiable: ScheduleAnyway
            labelSelector:
              matchLabels:
                app.kubernetes.io/name: webapp
```

**patch-resources.yaml**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: webapp
spec:
  template:
    spec:
      containers:
        - name: webapp             # ★ 이름으로 매칭된다
          resources:
            requests: { cpu: 500m, memory: 1Gi }
            limits:   { memory: 2Gi }
```

```bash
kubectl kustomize overlays/prod
kubectl apply -k overlays/prod
kubectl diff -k overlays/prod
```

### ConfigMap 해시 — Kustomize의 킬러 기능

7.6절에서 다룬 문제를 자동으로 해결한다.

```bash
kubectl kustomize overlays/prod | grep -A2 "name: prod-app-config"
```
```yaml
name: prod-app-config-7d9f8b2c4k
```

**내용이 바뀌면 이름이 바뀌고, Deployment의 참조도 자동 갱신되어 롤아웃이 일어난다.** 게다가 이전 ConfigMap이 남아 있어 롤백도 된다.

### Helm vs Kustomize

| | **Helm** | **Kustomize** |
|---|---|---|
| 방식 | 템플릿 렌더링 | YAML 패치 |
| base 파일 | 그 자체로는 유효하지 않음 | **유효한 YAML** |
| 배포 | 별도 도구 필요 | **`kubectl -k` 내장** |
| 릴리스 추적 | ✅ (history, rollback) | ❌ |
| 패키지 배포 | ✅ (레지스트리, 버전) | 제한적 |
| 조건문/반복 | ✅ 강력 | ❌ 없음 |
| 서드파티 앱 설치 | ✅ 표준 | 어려움 |
| ConfigMap 해시 | 수동 (checksum) | **자동** |
| 학습 곡선 | 중간~높음 | 낮음 |

**실무에서는 둘 다 쓴다.**

```
서드파티 앱 (Prometheus, cert-manager, ingress-nginx)
  → Helm (제공되는 차트를 그대로)

우리 애플리케이션
  → Kustomize (환경별 오버레이)
```

### 조합하기

Kustomize가 Helm 차트를 렌더링해 패치할 수 있다.

```yaml
# kustomization.yaml
helmCharts:
  - name: prometheus
    repo: https://prometheus-community.github.io/helm-charts
    version: 25.8.0
    releaseName: prom
    namespace: monitoring
    valuesFile: values-prom.yaml

patches:
  - target:
      kind: Deployment
      name: prom-server
    patch: |-
      - op: add
        path: /spec/template/spec/nodeSelector
        value: {workload: monitoring}
```

```bash
kubectl kustomize --enable-helm .
```

**Helm 차트의 값으로 노출되지 않은 부분을 패치로 수정**할 수 있다. 매우 실용적이다.

## 30.3 Carvel 툴킷

VMware가 만든 도구 모음이다. 각 도구가 한 가지 일만 한다.

| 도구 | 역할 |
|---|---|
| **ytt** | YAML 템플릿 (구조를 이해하는 템플릿) |
| **kbld** | 이미지 참조를 다이제스트로 해석 |
| **kapp** | 배포와 리소스 추적 |
| **imgpkg** | OCI 레지스트리에 설정 패키징 |
| **vendir** | 외부 설정 동기화 |
| **kapp-controller** | 클러스터 안에서 패키지 관리 |

### ytt — 구조를 이해하는 템플릿

```yaml
#@ load("@ytt:data", "data")
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: #@ data.values.name
spec:
  replicas: #@ data.values.replicas
  template:
    spec:
      containers:
        - name: app
          image: #@ "{}:{}".format(data.values.image, data.values.tag)
          #@ if data.values.resources:
          resources: #@ data.values.resources
          #@ end
```

**Helm과 달리 문자열 조작이 아니라 YAML AST를 다룬다.** 들여쓰기 오류가 원천적으로 없다.

### kbld — 이미지 고정

```bash
kbld -f manifests/
```

```yaml
# 변환 전
image: registry.example.com/webapp:2.4.1

# 변환 후
image: registry.example.com/webapp@sha256:5f2c9e...a31b
```

**2.2절에서 권장한 다이제스트 고정을 자동화한다.** 재현성이 보장된다.

### kapp — 배포와 추적

```bash
kapp deploy -a webapp -f manifests/ --diff-changes
```

```
Changes
Namespace  Name     Kind        Conds.  Age  Op      Wait to    Rs  Ri
prod       webapp   Deployment  2/2 t   3d   update  reconcile  ok  -
prod       webapp   Service     -       3d   -       -          ok  -

Op:      0 create, 1 delete, 1 update, 2 noop
Wait to: 2 reconcile, 1 delete, 0 noop

Continue? [yN]:
```

**kapp의 강점**
- **변경 사항을 미리 보여 준다** (`--diff-changes`)
- **리소스 간 순서를 이해한다** (CRD 먼저, 그다음 CR)
- **`kubectl apply`가 하지 못하는 삭제 추적**을 한다 — 매니페스트에서 제거된 리소스를 실제로 지운다

```bash
kapp inspect -a webapp        # 이 앱이 소유한 리소스 전체
kapp delete -a webapp         # 전부 삭제
```

**Helm의 릴리스 추적과 Kustomize의 단순함을 합친 느낌**이다. 다만 생태계가 작다.

## 30.4 GitOps

### 원칙

```
① 선언적       — 시스템 상태가 선언적으로 기술된다
② 버전 관리    — 그 선언이 Git에 저장되고 불변 이력을 갖는다
③ 자동 적용    — 승인된 변경이 자동으로 적용된다
④ 지속적 조정  — 에이전트가 드리프트를 감지하고 교정한다
```

**④가 CI/CD 파이프라인과의 결정적 차이다.**

```
전통적 CI/CD (push)          GitOps (pull)
─────────────────────        ─────────────────────
CI가 kubectl apply           에이전트가 Git을 폴링
  ↓                            ↓
클러스터 자격증명이            에이전트가 클러스터 안에 있다
CI 시스템에 있다               → 자격증명이 밖으로 나가지 않는다
  ↓                            ↓
누가 손으로 바꾸면             드리프트를 감지하고
알 수 없다                     자동으로 되돌린다
```

**보안 이점이 크다.** 클러스터 자격증명을 CI 시스템에 두지 않아도 된다.

### 저장소 구조

**앱 저장소와 설정 저장소를 분리하는 것이 표준이다.**

```
app-repo/                    ← 개발자가 작업
  src/
  Dockerfile
  .github/workflows/ci.yaml  ← 빌드, 테스트, 이미지 푸시
                                그리고 config-repo의 태그를 업데이트

config-repo/                 ← 배포 상태의 진실
  apps/
    webapp/
      base/
      overlays/
        dev/
        staging/
        prod/
  infrastructure/
    cert-manager/
    ingress-nginx/
    monitoring/
  clusters/
    dev-cluster/
    prod-cluster/
```

**왜 분리하는가**
- 앱 코드 변경과 배포 설정 변경의 권한을 다르게 줄 수 있다
- 앱 저장소의 커밋이 배포를 촉발하지 않는다 (의도적 승격)
- 여러 앱의 배포 상태를 한 곳에서 본다

**Application 정의**

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: webapp-prod
  namespace: argocd
  finalizers:
    - resources-finalizer.argocd.argoproj.io    # 4.2절
spec:
  project: default
  source:
    repoURL: https://github.com/myorg/config-repo
    targetRevision: main
    path: apps/webapp/overlays/prod
  destination:
    server: https://kubernetes.default.svc
    namespace: prod
  syncPolicy:
    automated:
      prune: true          # ★ Git에서 지운 리소스를 클러스터에서도 삭제
      selfHeal: true       # ★ 드리프트를 자동 교정
      allowEmpty: false
    syncOptions:
      - CreateNamespace=true
      - PruneLast=true
      - ServerSideApply=true          # 25.3절
    retry:
      limit: 5
      backoff:
        duration: 5s
        factor: 2
        maxDuration: 3m
  # ★ 16.6절의 HPA replicas 충돌 해결
  ignoreDifferences:
    - group: apps
      kind: Deployment
      jsonPointers:
        - /spec/replicas
```

**`ignoreDifferences`가 실무에서 필수다.** HPA가 replicas를 바꾸는데 Argo CD가 Git의 값으로 되돌리면 플래핑이 일어난다.

### Argo CD vs Flux

| | **Argo CD** | **Flux** |
|---|---|---|
| UI | **뛰어난 웹 UI** | 없음 (CLI + Grafana) |
| 구조 | 단일 컨트롤러 | **모듈형** (source, kustomize, helm, image, notification) |
| 멀티 테넌시 | AppProject | 네임스페이스 + RBAC |
| 이미지 자동 갱신 | 별도(Argo CD Image Updater) | **내장** |
| Helm 지원 | 렌더링 (릴리스 없음) | **HelmRelease** (실제 Helm) |
| 프로그레시브 딜리버리 | Argo Rollouts | Flagger |
| 학습 곡선 | 낮음 (UI 덕분) | 중간 |

**UI가 필요하고 여러 팀이 쓴다면 Argo CD**, **GitOps 순수주의와 자동화를 원하면 Flux**가 대략의 기준이다.

## 30.5 프로그레시브 딜리버리

8.2절에서 replica 비율로, 11.4절에서 인그레스 가중치로 카나리를 했다. **자동 판단과 롤백**이 빠져 있었다.

### Argo Rollouts

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: webapp
spec:
  replicas: 10
  strategy:
    canary:
      canaryService: webapp-canary
      stableService: webapp-stable
      trafficRouting:
        nginx:
          stableIngress: webapp
      analysis:
        templates:
          - templateName: success-rate
        startingStep: 2
        args:
          - name: service-name
            value: webapp-canary
      steps:
        - setWeight: 5
        - pause: { duration: 2m }
        - setWeight: 20
        - pause: { duration: 5m }
        - setWeight: 50
        - pause: { duration: 10m }
        - setWeight: 100
  selector:
    matchLabels: { app: webapp }
  template:
    # 일반 Pod 템플릿
```

**분석 템플릿**

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: success-rate
spec:
  args:
    - name: service-name
  metrics:
    - name: success-rate
      interval: 1m
      count: 5
      successCondition: result[0] >= 0.99
      failureLimit: 2                       # ★ 2번 실패하면 롤백
      provider:
        prometheus:
          address: http://prometheus.monitoring:9090
          query: |
            sum(rate(http_requests_total{service="{{args.service-name}}",status!~"5.."}[2m]))
            /
            sum(rate(http_requests_total{service="{{args.service-name}}"}[2m]))

    - name: latency-p99
      interval: 1m
      count: 5
      successCondition: result[0] <= 0.5
      provider:
        prometheus:
          address: http://prometheus.monitoring:9090
          query: |
            histogram_quantile(0.99,
              sum(rate(http_request_duration_seconds_bucket{service="{{args.service-name}}"}[2m]))
              by (le))
```

**에러율이 1%를 넘거나 P99 지연이 500ms를 넘으면 자동으로 롤백된다.** 사람이 대시보드를 보고 있을 필요가 없다.

```bash
kubectl argo rollouts get rollout webapp --watch
kubectl argo rollouts promote webapp        # 수동 승격
kubectl argo rollouts abort webapp          # 수동 중단
```

### Flagger

Flux 생태계의 대응물이다.

```yaml
apiVersion: flagger.app/v1beta1

spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment

      - name: request-duration
```

**`webhooks`로 부하 테스트를 자동 실행**할 수 있다. 트래픽이 적은 환경에서도 통계적으로 의미 있는 판단이 가능해진다.

### 언제 도입하는가

| 상황 | 권장 |
|---|---|
| 배포 빈도가 낮고 수동 검증이 가능 | 롤링 업데이트로 충분 (8.2절) |
| 배포가 잦고 사람이 지켜볼 수 없다 | **프로그레시브 딜리버리** |
| 메트릭이 없다 | **먼저 관측성부터**(31장) |

**메트릭 없이는 자동 판단이 불가능하다.** 31장이 선행 조건이다.

## 30.6 전체 파이프라인 설계

### 흐름

```
개발자가 코드 푸시
    ↓
┌──────────── CI (앱 저장소) ────────────┐
│ ① 린트, 단위 테스트                     │
│ ② 이미지 빌드 (2.2절 멀티 스테이지)      │
│ ③ 취약점 스캔 (18.5절 Trivy)           │
│ ④ SBOM 생성 (syft)                    │
│ ⑤ 이미지 서명 (cosign 키리스)           │
│ ⑥ 레지스트리 푸시 (다이제스트로)         │
│ ⑦ config-repo의 이미지 태그 업데이트 PR  │
└───────────────────────────────────────┘
    ↓
┌──────── 매니페스트 검증 (config-repo) ────┐
│ ⑧ kustomize build / helm template        │
│ ⑨ kubeconform (스키마 검증)               │
│ ⑩ kube-linter / Kyverno CLI (정책)       │
│ ⑪ 매니페스트 diff를 PR에 코멘트            │
└──────────────────────────────────────────┘
    ↓ 머지
┌──────────── CD (GitOps) ─────────────────┐
│ ⑫ Argo CD/Flux가 변경 감지                │
│ ⑬ dev에 자동 동기화                       │
│ ⑭ staging에 자동 동기화                   │
│ ⑮ prod는 수동 승인 또는 자동              │
│ ⑯ Argo Rollouts가 카나리 진행             │
│ ⑰ 메트릭 기반 자동 승격 또는 롤백           │
└──────────────────────────────────────────┘
```

### GitHub Actions 예시

```yaml
# app-repo/.github/workflows/ci.yaml
name: CI
on:
  push:
    branches: [main]

permissions:
  contents: read
  packages: write
  id-token: write            # ★ cosign 키리스 서명에 필요

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Login to registry
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Build and push
        id: build
        uses: docker/build-push-action@v5
        with:
          push: true
          tags: ghcr.io/${{ github.repository }}:${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

      - name: Scan image
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: ghcr.io/${{ github.repository }}:${{ github.sha }}
          format: sarif
          output: trivy.sarif
          severity: CRITICAL,HIGH
          exit-code: '1'

      - name: Generate SBOM
        uses: anchore/sbom-action@v0
        with:
          image: ghcr.io/${{ github.repository }}:${{ github.sha }}
          format: spdx-json

      - name: Sign image
        uses: sigstore/cosign-installer@v3
      - run: |
          cosign sign --yes \
            ghcr.io/${{ github.repository }}@${{ steps.build.outputs.digest }}

      - name: Update config repo
        run: |
          git clone https://x:${{ secrets.CONFIG_REPO_TOKEN }}@github.com/myorg/config-repo
          cd config-repo/apps/webapp/overlays/dev
          kustomize edit set image webapp=ghcr.io/${{ github.repository }}@${{ steps.build.outputs.digest }}
          git config user.name "ci-bot"
          git config user.email "ci@example.com"
          git commit -am "chore(dev): update webapp to ${{ github.sha }}"
          git push
```

**다이제스트로 참조하는 것**에 주목하자. 2.2절과 18.5절에서 강조한 재현성이다.

### 매니페스트 검증

```yaml
# config-repo/.github/workflows/validate.yaml
name: Validate
on: [pull_request]

jobs:
  validate:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        overlay: [dev, staging, prod]
    steps:
      - uses: actions/checkout@v4

      - name: Build manifests
        run: |
          kubectl kustomize apps/webapp/overlays/${{ matrix.overlay }} > out.yaml

      - name: Schema validation
        run: |
          kubeconform -strict -summary \
            -schema-location default \
            -schema-location 'https://raw.githubusercontent.com/datreeio/CRDs-catalog/main/{{.Group}}/{{.ResourceKind}}_{{.ResourceAPIVersion}}.json' \
            out.yaml

      - name: Best practice lint
        run: kube-linter lint out.yaml

      - name: Policy check
        run: |
          kyverno apply policies/ --resource out.yaml
```

**18.6절의 정책을 CI에서 미리 검사한다.** 클러스터에 도달하기 전에 걸러진다.

### 환경 승격 전략

```
① 같은 이미지 다이제스트를 환경 간에 승격
   dev → staging → prod
   (재빌드하지 않는다 — 테스트한 것과 같은 산출물)

② 승격은 config-repo의 커밋
   overlays/staging/kustomization.yaml 의 태그 변경

③ 승인 게이트
   · dev:     자동
   · staging: 자동 (테스트 통과 시)
   · prod:    PR 리뷰 + Argo CD 수동 sync
```

**"같은 이미지를 승격한다"가 핵심 원칙이다.** 7장에서 말한 "같은 이미지, 다른 설정"이 여기서 실현된다.

## 실습 과제

**과제 1 — Helm 차트 작성과 검증**
2장의 `hello` 앱을 위한 Helm 차트를 만들고 `values.schema.json`으로 검증을 추가한다. 잘못된 값(음수 replicas 등)으로 설치를 시도해 거부되는 것을 확인한다.

**과제 2 — Kustomize ConfigMap 해시 효과**
Kustomize로 ConfigMap을 생성하는 오버레이를 만들고, 값을 바꿨을 때 Deployment가 자동으로 롤아웃되는 것을 확인한다. 7.6절에서 수동으로 한 체크섬 패턴과 비교한다.

**과제 3 — Helm + Kustomize 조합**
ingress-nginx Helm 차트를 Kustomize의 `helmCharts`로 가져오고, 차트 값으로 노출되지 않은 필드(예: 특정 애노테이션)를 패치로 수정한다.

**과제 4 — GitOps 드리프트 교정 확인**
Argo CD로 앱을 배포한 뒤 `kubectl scale`로 replicas를 손으로 바꾼다. `selfHeal: true`에서 얼마 만에 되돌아오는지 측정하고, `false`로 바꿔 OutOfSync 상태만 표시되는 것을 비교한다.

**과제 5 — 자동 롤백 시나리오**
Argo Rollouts로 카나리를 구성하고, 의도적으로 500 에러를 반환하는 이미지를 배포한다. 분석이 실패를 감지하고 자동 롤백하는 전 과정을 관찰한다. (Prometheus가 필요하므로 31장 실습 후에 해도 좋다.)

## 요약

- **Helm은 템플릿, Kustomize는 패치**다. Helm은 서드파티 앱 설치와 릴리스 추적에, Kustomize는 우리 앱의 환경별 오버레이에 적합하다. **실무에서는 둘 다 쓰고, Kustomize가 Helm 차트를 렌더링해 패치할 수도 있다.**
- **Kustomize의 ConfigMap/Secret 해시 이름**이 7.6절의 롤아웃 유도 문제를 자동으로 해결한다.
- **`helm upgrade`는 `crds/` 디렉터리를 무시한다.** 오퍼레이터 배포에서 가장 흔한 함정이다.
- **Carvel의 kbld는 이미지를 다이제스트로 고정**하고, **kapp은 변경을 미리 보여 주며 삭제까지 추적**한다.
- **GitOps의 핵심은 네 번째 원칙인 지속적 조정**이다. 에이전트가 클러스터 안에서 Git을 폴링하므로 **자격증명이 CI 시스템으로 나가지 않고**, 손으로 바꾼 변경이 자동 교정된다.
- Argo CD에서 **`ignoreDifferences`로 HPA의 replicas를 제외하는 것이 필수**다(16.6절). 없으면 HPA와 GitOps가 서로 값을 되돌리며 플래핑한다.
- **Argo CD는 UI와 멀티팀 운영에, Flux는 모듈성과 이미지 자동 갱신에** 강하다. 시크릿은 ESO, Sealed Secrets, 또는 SOPS로 처리한다.
- **프로그레시브 딜리버리**(Argo Rollouts, Flagger)는 메트릭을 보고 자동으로 승격하거나 롤백한다. **메트릭이 없으면 불가능하므로 관측성이 선행 조건**이다.
- 파이프라인의 원칙: **같은 이미지 다이제스트를 환경 간에 승격**한다. 재빌드하지 않아야 "테스트한 것과 배포한 것이 같다"가 보장된다.

**다음 장에서는** 그 메트릭을 만든다. 로그·메트릭·트레이스를 수집하고, SLI/SLO 기반으로 알림을 설계하는 방법을 다룬다.
