# 24장. 확장 지점 지도

> **학습목표**
> - "쿠버네티스를 프로그래밍한다"는 것의 의미를 설명할 수 있다.
> - 확장 지점을 제어 평면·데이터 평면으로 분류하고 지도를 그릴 수 있다.
> - 컨트롤러와 오퍼레이터의 관계를 정확히 구분한다.
> - 오퍼레이터 성숙도 모델로 목표 수준을 설정할 수 있다.
> - 요구사항에 맞는 확장 방식을 결정 트리로 선택할 수 있다.

---

## 들어가며

5부에서 쿠버네티스의 내부를 봤다. 21장에서 컨트롤러가 **Informer → 워크큐 → 조정 함수** 패턴으로 동작한다는 것도 확인했다.

6부는 그 패턴을 **직접 구현한다.**

핵심 통찰은 이것이다.

> **쿠버네티스의 내장 컨트롤러와 우리가 만들 컨트롤러 사이에는 아무런 특권 차이가 없다.**

Deployment 컨트롤러도 API를 watch하고 조정할 뿐이다. 우리도 똑같이 할 수 있다.

## 24.1 "쿠버네티스를 프로그래밍한다"는 것

### 세 가지 층위

**① 쿠버네티스 *위에서* 개발한다**

앱을 컨테이너로 만들고 매니페스트를 쓴다. 1~4부에서 한 일이다. 쿠버네티스는 실행 환경일 뿐이다.

**② 쿠버네티스를 *사용해* 프로그래밍한다**

client-go 같은 라이브러리로 API를 호출한다. CI 도구가 Deployment를 만들거나, 대시보드가 Pod 목록을 보여 주는 경우다. **쿠버네티스는 데이터 소스이자 실행 엔진**이다.

**③ 쿠버네티스를 *확장해* 프로그래밍한다**

새로운 리소스 종류를 정의하고, 그것을 조정하는 컨트롤러를 만든다. **쿠버네티스의 어휘 자체를 늘리는 일**이다.

이 장부터 다루는 것은 ③이다.

### 왜 확장하는가

**동기 예시: 데이터베이스 운영 자동화**

팀에 PostgreSQL 클러스터가 20개 있다고 하자. 각각에 대해 사람이 하는 일:

```
· StatefulSet, Service, ConfigMap, Secret, PVC 만들기
· 프라이머리/레플리카 설정
· 프라이머리가 죽으면 레플리카를 승격
· 매일 백업하고 S3에 업로드
· 버전 업그레이드 시 순서대로 재시작
· 디스크가 차면 볼륨 확장
```

**이것을 코드로 옮기면** 이렇게 된다.

```yaml
apiVersion: db.example.com/v1
kind: PostgresCluster
metadata:
  name: orders-db
spec:
  version: "16.2"
  replicas: 3
  storage:
    size: 100Gi
    class: fast-ssd
  backup:
    schedule: "0 3 * * *"
    retention: 30d
    destination: s3://backups/orders-db
```

**운영 지식이 선언적 API가 되는 것**이 확장의 본질이다. 사람이 매번 판단하던 것을 조정 루프가 대신한다.

### 다르게 말하면

1장에서 본 조정 루프를 다시 가져온다.

```
관찰(observe) → 비교(diff) → 조치(act)
```

**확장한다는 것은 이 루프를 하나 더 추가하는 일이다.** 쿠버네티스는 이 패턴을 위한 인프라(API 서버, watch, etcd, RBAC)를 제공하고, 우리는 도메인 로직만 채우면 된다.

## 24.2 확장 지점 지도

### 전체 그림

```
┌──────────────────── 제어 평면 (Control Plane) ────────────────────┐
│                                                                  │
│  ① API 확장                                                       │
│     · CustomResourceDefinition (CRD)          → 26장              │
│     · API 어그리게이션 (커스텀 API 서버)          → 28장              │
│                                                                  │
│  ② 어드미션 확장                                                    │
│     · ValidatingAdmissionPolicy (CEL)         → 17.5절            │
│     · Mutating/Validating Webhook             → 28장              │
│                                                                  │
│  ③ 컨트롤러 확장                                                    │
│     · 커스텀 컨트롤러 / 오퍼레이터               → 25, 27장           │
│                                                                  │
│  ④ 인증·인가 확장                                                   │
│     · Webhook 토큰 인증                        → 17.2절            │
│     · Webhook 인가                             → 17.3절            │
│                                                                  │
│  ⑤ 스케줄링 확장                                                    │
│     · 스케줄러 프레임워크 플러그인                → 15.8절            │
│     · 커스텀 스케줄러 / 여러 프로파일             → 15.8절            │
│                                                                  │
│  ⑥ kubectl 확장                                                   │
│     · 플러그인 (krew)                          → 3.4절             │
└──────────────────────────────────────────────────────────────────┘

┌──────────────────── 데이터 평면 (Data Plane) ─────────────────────┐
│                                                                  │
│  ⑦ 런타임         CRI                          → 20.4절            │
│  ⑧ 네트워크       CNI                          → 23장              │
│  ⑨ 스토리지       CSI                          → 12.4절            │
│  ⑩ 하드웨어       Device Plugin                → 20.4절            │
│  ⑪ 메트릭         custom/external metrics API  → 16.3절            │
│  ⑫ 자격증명       Credential Provider           → 클라우드 연동       │
└──────────────────────────────────────────────────────────────────┘
```

**대부분의 사람이 만드는 것은 ①+③의 조합**, 즉 **CRD + 컨트롤러 = 오퍼레이터**다. 이 장 이후는 그것에 집중한다.

### CRD vs 어그리게이션 API

새 API를 추가하는 방법은 두 가지다.

| | **CRD** | **어그리게이션 API 서버** |
|---|---|---|
| 구현 난이도 | **YAML 하나** | Go 서버 구현 필요 |
| 저장소 | 클러스터 etcd | **선택 가능** (별도 etcd, 외부 DB, 메모리) |
| 검증 | OpenAPI 스키마 + 웹훅 | 임의의 Go 코드 |
| 커스텀 동작 | 제한적 | 완전한 제어 |
| 별도 프로세스 | 불필요 | **필요** (가용성 관리) |
| 성능 | 일반 리소스와 동일 | 구현에 따라 |
| protobuf | ❌ JSON만 | ✅ 가능 |

**결론: 99%는 CRD로 충분하다.**

어그리게이션이 필요한 좁은 경우들:

- **etcd에 저장하고 싶지 않다.** 메트릭처럼 휘발성이거나 양이 많은 데이터 (metrics-server가 이 경우다, 21.1절)
- **외부 시스템이 진실의 원천**이다. 기존 DB의 데이터를 쿠버네티스 API로 노출
- **CRD가 표현할 수 없는 동작**이 필요하다. 커스텀 `exec` 서브리소스 같은 것
- **매우 높은 처리량**이 필요하다

28장에서 어그리게이션을 다루지만, 실무에서 쓸 일은 드물다.

## 24.3 컨트롤러와 오퍼레이터

### 정의

용어가 혼용되지만 구분이 있다.

```
┌──────────────────────────────────────────────────┐
│  컨트롤러 (Controller)                             │
│    조정 루프를 도는 프로그램.                        │
│    · 리소스를 watch                                │
│    · 원하는 상태와 현재 상태를 비교                   │
│    · 차이를 줄이는 조치                             │
│                                                  │
│    예: Deployment 컨트롤러, ReplicaSet 컨트롤러      │
└──────────────────────────────────────────────────┘
                       ⊃
┌──────────────────────────────────────────────────┐
│  오퍼레이터 (Operator)                             │
│    CRD + 컨트롤러 조합으로                          │
│    **특정 애플리케이션의 운영 지식**을 인코딩한 것      │
│                                                  │
│    예: Prometheus Operator, CloudNativePG,        │
│        Strimzi(Kafka), cert-manager               │
└──────────────────────────────────────────────────┘
```

**오퍼레이터는 컨트롤러의 부분집합**이다. 모든 오퍼레이터는 컨트롤러이지만, 모든 컨트롤러가 오퍼레이터는 아니다.

**내장 리소스만 다루는 컨트롤러**도 유용하다.

```
· 모든 네임스페이스에 기본 NetworkPolicy를 만드는 컨트롤러
· Secret을 여러 네임스페이스에 복제하는 컨트롤러
· 특정 라벨의 Pod를 자동으로 정리하는 컨트롤러
```

이런 것들은 CRD 없이 컨트롤러만 있으면 된다.

### 오퍼레이터 성숙도 모델

Operator Framework가 제안한 5단계다. **목표 수준을 정하는 데 유용하다.**

```
Level 1  기본 설치
         · 앱을 배포할 수 있다
         · 설정 가능한 파라미터를 CRD로 노출

Level 2  원활한 업그레이드
         · 앱 버전 업그레이드
         · 오퍼레이터 자신의 업그레이드

Level 3  전체 생명주기
         · 백업과 복구
         · 페일오버
         · 스케일링

Level 4  깊은 통찰(Insights)
         · 메트릭과 알림 노출
         · 로그 집계
         · 워크로드 분석

Level 5  자동 조종(Auto Pilot)
         · 수평/수직 자동 스케일링
         · 이상 감지와 자동 튜닝
         · 자동 스케줄링 최적화
```

**대부분의 조직에는 Level 1~2로 충분하다.** Level 4~5는 상용 오퍼레이터나 오픈소스 대형 프로젝트의 영역이다.

**주의**: 성숙도를 높이는 것이 항상 옳지는 않다. 자동 페일오버가 오히려 스플릿 브레인을 만들 수도 있다. **자동화할수록 그 자동화 자체를 검증해야 한다.**

### 오퍼레이터가 적합한 경우

| 신호 | 예 |
|---|---|
| **상태 저장 앱의 복잡한 운영** | 데이터베이스, 메시지 큐, 분산 스토리지 |
| **여러 리소스를 묶어 관리** | 앱 하나에 Deployment + Service + Ingress + Secret + CronJob |
| **동일한 패턴의 반복 배포** | 팀마다 같은 구조의 환경을 반복 생성 |
| **런북(runbook)이 존재한다** | 문서화된 운영 절차가 있다면 코드화할 수 있다 |
| **도메인 특화 추상화가 필요** | "테넌트", "환경", "파이프라인" 같은 개념 |

**핵심 판단**: **"우리 팀의 위키에 적힌 운영 절차 문서가 있는가?"** 있다면 그것이 오퍼레이터의 명세다.

### 오퍼레이터가 과한 경우

```
❌ 매니페스트 몇 개를 묶는 것이 전부다
   → Helm 차트나 Kustomize로 충분하다 (30장)

❌ 배포만 하고 이후 운영이 없다
   → GitOps로 충분하다 (30장)

❌ 이미 성숙한 오퍼레이터가 있다
   → CloudNativePG, Strimzi, cert-manager 등을 쓰자

❌ 팀에 Go 개발 역량이 없고 유지보수 계획도 없다
   → 오퍼레이터는 소프트웨어다. 만들면 유지해야 한다
```

> **오퍼레이터의 숨은 비용**
> 오퍼레이터는 클러스터에서 **높은 권한**으로 돌고, **버그가 나면 그것이 관리하는 모든 워크로드에 영향**을 준다. 조정 루프에 무한 루프 버그가 있으면 API 서버를 마비시킬 수도 있다(21.2절의 APF가 이런 상황을 완화한다).
>
> 만들기 전에 물어야 할 것: **"이것을 3년간 유지보수할 사람이 있는가?"**

## 24.4 확장 방식 선택 결정 트리

```
무엇을 하려는가?
│
├─ 매니페스트를 재사용·파라미터화하고 싶다
│   → Helm / Kustomize (30장). 확장이 아니다
│
├─ 리소스가 특정 규칙을 지키도록 강제하고 싶다
│   ├─ 단순한 검증 (필드 존재, 값 범위, 정규식)
│   │   → ValidatingAdmissionPolicy (CEL) — 17.5절
│   │      서버 불필요, 가용성 문제 없음
│   ├─ 기본값 주입이나 필드 수정
│   │   → Kyverno mutate 또는 Mutating Webhook — 18.6절, 28장
│   └─ 외부 시스템 조회가 필요한 복잡한 로직
│       → Validating Webhook — 28장
│
├─ 새로운 리소스 종류를 만들고 싶다
│   ├─ 데이터만 저장하면 된다 (설정 저장소로 활용)
│   │   → CRD만 — 26장
│   ├─ 그 리소스에 반응해 무언가를 해야 한다
│   │   → CRD + 컨트롤러 = 오퍼레이터 — 26, 27장
│   └─ etcd에 저장하고 싶지 않거나 특수 동작이 필요
│       → 어그리게이션 API 서버 — 28장
│
├─ 기존 리소스를 감시해 자동화하고 싶다
│   → 컨트롤러 (CRD 없이) — 25, 27장
│
├─ Pod 배치 방식을 바꾸고 싶다
│   ├─ 기존 기능으로 표현 가능
│   │   → 어피니티, 테인트, 토폴로지 분산 — 15장
│   ├─ 스코어링 방식만 바꾸면 된다
│   │   → 스케줄러 프로파일 — 15.8절
│   └─ 완전히 다른 알고리즘
│       → 스케줄러 플러그인 또는 커스텀 스케줄러 — 15.8절
│
├─ 새로운 종류의 스토리지/네트워크/하드웨어를 지원하고 싶다
│   → CSI / CNI / Device Plugin — 12.4절, 23장, 20.4절
│
└─ kubectl에 명령을 추가하고 싶다
    → kubectl 플러그인 (실행 파일 이름을 kubectl-* 로) — 3.4절
```

## 24.5 실전 사례로 보는 확장

### 사례 1: cert-manager (CRD + 컨트롤러 + 웹훅)

11.3절에서 쓴 도구다. 확장의 모범 사례라 할 만하다.

```
CRD:
  Certificate, CertificateRequest, Issuer, ClusterIssuer,
  Order, Challenge

컨트롤러:
  · Ingress를 watch → 애노테이션을 보고 Certificate 생성
  · Certificate를 watch → CertificateRequest 생성
  · ACME 챌린지 수행 → 임시 Ingress/DNS 레코드 생성
  · 발급된 인증서를 Secret에 저장
  · 만료 30일 전 자동 갱신

웹훅:
  · Validating: Issuer 설정 검증
  · Conversion: CRD 버전 변환 (v1alpha2 → v1)
```

**주목할 점**: 애노테이션 하나(`cert-manager.io/cluster-issuer`)가 전체 워크플로를 촉발한다. **사용자 인터페이스가 극도로 단순하다.** 좋은 오퍼레이터의 특징이다.

### 사례 2: Prometheus Operator

31장에서 쓸 도구다.

```
CRD:
  Prometheus, Alertmanager, ServiceMonitor, PodMonitor,
  PrometheusRule, ThanosRuler

해결하는 문제:
  Prometheus 설정 파일을 손으로 관리하면
  · 새 서비스를 추가할 때마다 중앙 설정 파일을 수정해야 한다
  · 그 파일을 소유한 팀이 병목이 된다

오퍼레이터의 해결:
  각 팀이 자기 네임스페이스에 ServiceMonitor를 만든다
  → 오퍼레이터가 그것들을 모아 Prometheus 설정을 생성
  → Prometheus에 리로드 신호
```

**중앙 설정을 분산 가능한 리소스로 바꾼 것**이 핵심 가치다.

### 사례 3: CloudNativePG

8.3절에서 "StatefulSet보다 오퍼레이터를 먼저 검토하라"고 한 이유를 보여 준다.

```
CRD: Cluster, Backup, ScheduledBackup, Pooler

StatefulSet이 안 해 주는 것을 모두 한다:
  · 프라이머리 선출과 자동 페일오버
  · 스트리밍 복제 설정
  · 연속 아카이빙(WAL)과 시점 복구(PITR)
  · 롤링 업그레이드 시 스위치오버
  · 커넥션 풀러(PgBouncer) 관리
  · 백업 스케줄과 보존 정책
```

**StatefulSet은 이름·스토리지·순서만 준다**(8.3절). 나머지 운영 지식이 오퍼레이터에 들어 있다.

### 사례 4: 사내 오퍼레이터 — 환경 프로비저닝

기업에서 흔히 만드는 유형이다.

```yaml
apiVersion: platform.example.com/v1
kind: DevEnvironment
metadata:
  name: alice-feature-x
spec:
  owner: alice@example.com
  ttl: 72h
  services:
    - name: api
      image: registry.example.com/api:pr-1234
    - name: web
      image: registry.example.com/web:pr-1234
  database:
    seedFrom: staging-snapshot
```

**오퍼레이터가 하는 일**
- 네임스페이스 생성 + ResourceQuota + NetworkPolicy (13장)
- 각 서비스의 Deployment, Service 생성
- 데이터베이스 생성과 시드 데이터 로드
- Ingress 생성 (`alice-feature-x.dev.example.com`)
- **TTL 만료 시 전체 정리**
- Slack으로 준비 완료 알림

**개발자는 CR 하나만 만들면 된다.** 플랫폼 팀의 운영 지식이 코드가 됐다.

### Go를 모른다면

**client-go와 controller-runtime은 Go 라이브러리다.** 다른 언어 선택지도 있다.

| 언어 | 프레임워크 |
|---|---|
| **Go** | client-go, controller-runtime, Kubebuilder ★ 생태계 최대 |
| Python | kopf, kubernetes-client |
| Java | Java Operator SDK, Fabric8 |
| Rust | kube-rs |
| .NET | KubeOps |
| **YAML/CEL** | Metacontroller, Kyverno, Crossplane Compositions |

**Go를 권장하는 이유**
- 쿠버네티스 자체가 Go로 작성되어 타입을 그대로 쓸 수 있다
- 생성된 클라이언트 코드, 타입 안전성
- 커뮤니티 자료와 예제가 압도적으로 많다
- controller-runtime이 보일러플레이트를 크게 줄여 준다

**이 책은 Go를 기준으로 하되**, 27.5절에서 다른 접근법도 다룬다.

**과제 3 — 오퍼레이터 성숙도 평가**
클러스터에 설치된 오퍼레이터 하나를 24.3절의 5단계로 평가한다. 어떤 기능이 있고 없는지 근거를 들어 판정한다.

## 요약

- **쿠버네티스를 확장한다는 것은 조정 루프를 하나 더 추가하는 일**이다. 내장 컨트롤러와 우리가 만드는 컨트롤러 사이에 특권 차이는 없다.
- 확장 지점은 **제어 평면**(API, 어드미션, 컨트롤러, 인증·인가, 스케줄링, kubectl)과 **데이터 평면**(CRI, CNI, CSI, Device Plugin, 메트릭)으로 나뉜다. 대부분이 만드는 것은 **CRD + 컨트롤러 = 오퍼레이터**다.
- **99%의 경우 CRD로 충분하다.** 어그리게이션 API 서버는 etcd에 저장하고 싶지 않거나 외부 시스템이 진실의 원천일 때만 필요하다.
- **오퍼레이터는 컨트롤러의 부분집합**이며, 특정 애플리케이션의 **운영 지식을 인코딩**한 것이다. CRD 없이 내장 리소스만 다루는 컨트롤러도 유용하다.
- 오퍼레이터 성숙도는 **설치 → 업그레이드 → 생명주기 → 통찰 → 자동 조종** 5단계다. **대부분 Level 1~2로 충분하며**, 자동화 수준을 높일수록 그 자동화 자체의 검증 부담이 커진다.
- 만들기 전에 물어야 할 것: **"팀 위키에 운영 절차 문서가 있는가?"**(있다면 오퍼레이터의 명세다) 그리고 **"3년간 유지보수할 사람이 있는가?"**
- 매니페스트 묶기는 Helm/Kustomize로, 단순 검증은 ValidatingAdmissionPolicy로 충분하다. **오퍼레이터를 만들기 전에 더 가벼운 선택지를 먼저 확인한다.**

**다음 장에서는** 실제 코드로 들어간다. client-go로 API 서버와 대화하고, 21.3절에서 개념으로 본 Informer와 워크큐를 직접 사용해 첫 컨트롤러를 만든다.
