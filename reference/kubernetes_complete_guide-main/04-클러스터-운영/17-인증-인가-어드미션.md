# 17장. 인증, 인가, 어드미션

> **학습목표**
> - API 요청이 통과하는 세 관문의 순서와 역할을 설명할 수 있다.
> - 쿠버네티스에 "사용자"가 없다는 사실과 그 의미를 이해한다.
> - RBAC의 네 리소스를 조합해 최소 권한 역할을 설계할 수 있다.
> - ServiceAccount 토큰의 동작과 워크로드 아이덴티티를 안다.
> - 클라우드 IAM 연동(IRSA, Workload Identity)의 원리를 설명할 수 있다.
> - 어드미션 컨트롤러가 요청을 어떻게 변형·검증하는지 안다.

---

## 들어가며

4장에서 API 서버가 클러스터의 유일한 진입점이라고 했다. 모든 요청이 한 곳을 지나므로, **접근 통제도 한 곳에서 이루어진다.**

이 장은 그 관문을 다룬다. 잘못 설계하면 개발자가 프로덕션을 지우거나, 침해된 Pod 하나가 클러스터 전체를 장악한다.

## 17.1 요청 처리 파이프라인

### 세 개의 관문

```
kubectl / Pod / 컨트롤러
        │
        ▼  HTTPS 요청
┌───────────────────────────────────────────────────┐
│                  kube-apiserver                    │
│                                                    │
│  ① 인증 (Authentication)                           │
│     "당신은 누구입니까?"                             │
│     → 실패 시 401 Unauthorized                     │
│                                                    │
│  ② 인가 (Authorization)                            │
│     "그 행동을 할 권한이 있습니까?"                   │
│     → 실패 시 403 Forbidden                        │
│                                                    │
│  ③ 어드미션 제어 (Admission Control)                │
│     ③-a Mutating  : 요청을 수정한다                 │
│     ③-b 스키마 검증 : OpenAPI 스펙에 맞는가          │
│     ③-c Validating: 정책에 맞는가                   │
│     → 실패 시 400 / 403                            │
│                                                    │
│  ④ etcd에 저장                                     │
└───────────────────────────────────────────────────┘
```

**401과 403의 차이**를 구분하면 진단이 빨라진다.
- **401**: 신원을 확인하지 못했다 → 인증서·토큰·kubeconfig 문제
- **403**: 신원은 확인됐지만 권한이 없다 → RBAC 문제

### 확인 명령

```bash
# 나는 누구인가
kubectl auth whoami

# 내가 이것을 할 수 있는가
kubectl auth can-i create pods
kubectl auth can-i delete deployments -n prod
kubectl auth can-i '*' '*'                    # cluster-admin인가?

# 다른 주체의 권한 확인 (impersonate 권한 필요)
kubectl auth can-i list secrets \
  --as=system:serviceaccount:default:my-sa

# 내가 할 수 있는 모든 것
kubectl auth can-i --list -n default
```

`kubectl auth can-i --list`는 권한 설계를 검증할 때 매우 유용하다.

## 17.2 인증

### 쿠버네티스에는 사용자 오브젝트가 없다

가장 놀라운 사실이다.

```bash
kubectl get users        # error: the server doesn't have a resource type "users"
```

**쿠버네티스는 사용자를 저장하지 않는다.** 대신 요청에 담긴 증거(인증서, 토큰)를 검증해 **문자열로 된 사용자 이름과 그룹 목록**을 추출할 뿐이다.

```
인증 성공 후 API 서버가 아는 것:
  username: "alice@example.com"
  groups:   ["dev-team", "system:authenticated"]
  uid:      "..."
  extra:    {...}
```

**결과**: 사용자 생성·삭제·비밀번호 변경 같은 기능이 없다. 그것은 외부 시스템(인증서 CA, OIDC 제공자, 클라우드 IAM)의 일이다.

**예외는 ServiceAccount다.** 이것은 실제 API 오브젝트다.

```bash
kubectl get serviceaccounts
```

**두 종류의 주체**

| | **일반 사용자** | **ServiceAccount** |
|---|---|---|
| 대상 | 사람, 외부 시스템 | 클러스터 내 워크로드 |
| API 오브젝트 | ❌ 없음 | ✅ 있음 |
| 관리 | 외부 (CA, OIDC, IAM) | 쿠버네티스 |
| 이름 형식 | 임의 문자열 | `system:serviceaccount:<ns>:<name>` |
| 네임스페이스 | 없음 | 있음 |

### 인증 방식들

API 서버는 여러 인증기를 순서대로 시도하고, **하나라도 성공하면 통과**시킨다.

**① X.509 클라이언트 인증서**

```bash
# 인증서의 내용이 곧 신원
openssl x509 -in client.crt -noout -subject
# subject=CN=alice, O=dev-team, O=platform
```

```
CN (Common Name)      → username
O  (Organization)     → groups (여러 개 가능)
```

kubeconfig에 담긴다(3.4절).

```yaml
users:
  - name: alice
    user:
      client-certificate-data: LS0tLS1CRUdJTi...
      client-key-data: LS0tLS1CRUdJTi...
```

**인증서 발급 절차**

```bash
# ① 키와 CSR 생성
openssl genrsa -out alice.key 2048
openssl req -new -key alice.key -out alice.csr \
  -subj "/CN=alice/O=dev-team"

# ② 쿠버네티스 CSR 오브젝트로 제출
cat <<EOF | kubectl apply -f -
apiVersion: certificates.k8s.io/v1
kind: CertificateSigningRequest
metadata:
  name: alice
spec:
  request: $(cat alice.csr | base64 | tr -d '\n')
  signerName: kubernetes.io/kube-apiserver-client
  expirationSeconds: 7776000        # 90일
  usages:
    - client auth
EOF

# ③ 승인
kubectl certificate approve alice

# ④ 인증서 추출
kubectl get csr alice -o jsonpath='{.status.certificate}' | base64 -d > alice.crt
```

> **⚠️ 인증서 인증의 치명적 약점**
> **폐기(revocation)가 불가능하다.** 쿠버네티스는 CRL이나 OCSP를 지원하지 않는다. 인증서가 유출되면 **만료될 때까지 유효하다.**
>
> 대응: ① 유효기간을 짧게(30~90일) ② 유출 시 CA를 교체(모든 인증서 재발급) ③ **애초에 OIDC를 쓴다.**
>
> 인증서는 부트스트랩이나 긴급 접근(break-glass) 용도로 제한하는 것이 좋다.

**② OIDC (OpenID Connect) — 사람 인증의 정답**

Google, Okta, Keycloak, Entra ID 같은 ID 제공자와 연동한다.

```yaml
# kube-apiserver 플래그
--oidc-issuer-url=https://accounts.google.com
--oidc-client-id=<client-id>
--oidc-username-claim=email
--oidc-username-prefix="oidc:"
--oidc-groups-claim=groups
--oidc-groups-prefix="oidc:"
```

```yaml
# kubeconfig
users:
  - name: alice
    user:
      exec:
        apiVersion: client.authentication.k8s.io/v1
        command: kubelogin
        args: ["get-token", "--oidc-issuer-url=...", "--oidc-client-id=..."]
```

**장점**
- 중앙 집중식 ID 관리 (입퇴사 처리가 한 곳에서)
- MFA 적용 가능
- **토큰이 짧게 유지되고 폐기 가능**
- 그룹 정보를 IdP에서 관리

**프로덕션의 사람 인증은 OIDC가 표준이다.**

**③ ServiceAccount 토큰**

워크로드용이다. 17.4절에서 상세히 다룬다.

**④ Webhook 토큰 인증**

외부 서비스에 토큰 검증을 위임한다. 클라우드 매니지드 서비스가 이 방식으로 IAM과 연동한다.

```
EKS: aws-iam-authenticator → AWS IAM
GKE: Google Cloud IAM
AKS: Entra ID
```

**⑤ 정적 토큰 파일 / 기본 인증**

```
--token-auth-file=/etc/kubernetes/tokens.csv
--basic-auth-file=...    # v1.19에서 제거됨
```

> **⚠️ 절대 쓰지 말 것.** 파일에 평문으로 저장되고, 변경하려면 API 서버를 재시작해야 하며, 폐기가 불가능하다.

### 익명 요청과 시스템 그룹

```
system:anonymous          인증되지 않은 요청
system:unauthenticated    익명 요청의 그룹
system:authenticated      인증된 모든 요청이 속하는 그룹
system:masters            ★ cluster-admin과 동등. RBAC를 우회한다
```

> **⚠️ `system:masters` 그룹**
> 이 그룹에 속하면 **RBAC 검사를 건너뛰고 모든 것을 할 수 있다.** 인가 단계에서 하드코딩되어 있어 RBAC로 제한할 수 없다.
>
> kubeadm이 만드는 `admin.conf`의 인증서가 `O=system:masters`다. **이 파일은 금고에 넣어 두고 평소에는 쓰지 않아야 한다.** 유출되면 클러스터 전체가 넘어가고, 폐기할 방법도 없다.

## 17.3 RBAC

### 네 개의 리소스

```
        네임스페이스 스코프          클러스터 스코프
       ┌──────────────────┐      ┌──────────────────┐
권한   │      Role        │      │   ClusterRole    │
       └────────┬─────────┘      └────────┬─────────┘
                │                         │
       ┌────────▼─────────┐      ┌────────▼─────────┐
연결   │   RoleBinding    │      │ClusterRoleBinding│
       └──────────────────┘      └──────────────────┘
```

**조합 규칙**

| Binding | Role 참조 | 적용 범위 |
|---|---|---|
| RoleBinding | Role | 그 네임스페이스 |
| RoleBinding | **ClusterRole** | **그 네임스페이스에만** ★ 매우 유용 |
| ClusterRoleBinding | ClusterRole | 클러스터 전체 |
| ClusterRoleBinding | Role | ❌ 불가능 |

**두 번째 조합이 실무의 핵심이다.** ClusterRole 하나를 정의하고 여러 네임스페이스에서 RoleBinding으로 재사용한다.

### Role 정의

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: developer
  namespace: dev
rules:
  # 워크로드 관리
  - apiGroups: ["", "apps", "batch"]
    resources: ["pods", "deployments", "statefulsets", "jobs", "cronjobs"]
    verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]

  # 로그와 exec — 서브리소스 (4.1절)
  - apiGroups: [""]
    resources: ["pods/log", "pods/exec", "pods/portforward"]
    verbs: ["get", "create"]

  # 설정 조회만
  - apiGroups: [""]
    resources: ["configmaps"]
    verbs: ["get", "list", "watch"]

  # 특정 리소스만 (resourceNames)
  - apiGroups: [""]
    resources: ["secrets"]
    resourceNames: ["app-config-secret"]
    verbs: ["get"]
```

**`apiGroups`의 빈 문자열 `""`은 코어 그룹**이다(4.1절). Pod, Service, ConfigMap, Secret이 여기 속한다.

**동사(verbs)**

| verb | 의미 |
|---|---|
| `get` | 단일 조회 |
| `list` | 목록 조회 ★ |
| `watch` | 변경 스트림 구독 |
| `create` | 생성 |
| `update` | 전체 교체 (PUT) |
| `patch` | 부분 수정 (PATCH) |
| `delete` | 삭제 |
| `deletecollection` | 여러 개 한 번에 삭제 |
| `impersonate` | 다른 사용자로 가장 |
| `escalate` / `bind` | 권한 상승 관련 (아래 참조) |

> **⚠️ `get`과 `list`의 큰 차이**
>
> `get`은 이름을 알아야 하나씩 조회한다. `list`는 **모든 오브젝트를 한 번에** 가져온다.
>
> ```
> secrets에 list 권한 = 그 네임스페이스의 모든 시크릿을 덤프할 수 있다
> ```
>
> `resourceNames`로 제한하려 해도 **`list`와 `watch`에는 적용되지 않는다.** 이름을 알아야 필터링할 수 있는데, list는 이름 없이 전체를 요청하기 때문이다.
>
> ```yaml
> # ❌ 의도대로 동작하지 않는다
> - resources: ["secrets"]
>   resourceNames: ["my-secret"]
>   verbs: ["list"]              # resourceNames가 무시됨
> ```

### 내장 ClusterRole

```bash
kubectl get clusterroles | grep -v '^system:'
```

| 이름 | 권한 |
|---|---|
| `cluster-admin` | **모든 것.** ClusterRoleBinding으로 주면 슈퍼유저 |
| `admin` | 네임스페이스 안의 모든 것 + RBAC 관리. 쿼터·네임스페이스 자체는 제외 |
| `edit` | 네임스페이스 안의 리소스 읽기/쓰기. **RBAC 관리는 제외** |
| `view` | 읽기 전용. **Secret 제외** ★ |

**`view`가 Secret을 못 본다는 점이 중요하다.** "읽기만 하니까 안전하겠지"라며 view를 주는 것이 실제로도 안전한 이유다.

**재사용 패턴**

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-team-edit
  namespace: dev
subjects:
  - kind: Group
    name: "oidc:dev-team"           # OIDC에서 온 그룹
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole                 # ★ ClusterRole을 참조
  name: edit
  apiGroup: rbac.authorization.k8s.io
```

**`edit` ClusterRole의 권한을 `dev` 네임스페이스에서만** 갖는다.

### 애그리게이션

ClusterRole에 라벨 셀렉터를 두면 다른 ClusterRole의 규칙을 자동으로 흡수한다.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: monitoring
  labels:
    rbac.authorization.k8s.io/aggregate-to-view: "true"    # ★
rules:
  - apiGroups: ["monitoring.coreos.com"]
    resources: ["servicemonitors", "prometheusrules"]
    verbs: ["get", "list", "watch"]
```

**이제 `view` ClusterRole에 이 규칙이 자동으로 추가된다.** CRD를 설치할 때 기존 역할에 권한을 더하는 표준 방법이다. 오퍼레이터들이 이 패턴을 많이 쓴다.

### 주체(Subject) 세 종류

```yaml
subjects:
  - kind: User
    name: alice@example.com              # 인증에서 나온 문자열
    apiGroup: rbac.authorization.k8s.io

  - kind: Group
    name: dev-team
    apiGroup: rbac.authorization.k8s.io

  - kind: ServiceAccount
    name: build-bot
    namespace: ci                        # ★ 네임스페이스 필수
```

**그룹 기반 바인딩을 권장한다.** 사람이 들어오고 나갈 때마다 RBAC을 고치는 대신, IdP에서 그룹 멤버십만 바꾸면 된다.

### 권한 상승 방지

RBAC에는 **자기보다 큰 권한을 만들 수 없다**는 규칙이 있다.

```
Role/ClusterRole을 만들거나 수정하려면:
  · 그 안의 모든 권한을 이미 갖고 있거나
  · `escalate` 동사 권한이 있어야 한다

RoleBinding을 만들려면:
  · 참조하는 Role의 권한을 이미 갖고 있거나
  · 그 Role에 대한 `bind` 권한이 있어야 한다
```

이것이 없으면 `edit` 권한만 가진 사용자가 `cluster-admin` RoleBinding을 만들어 스스로 승격할 수 있다.

```bash
# 권한이 부족하면 이런 에러가 난다
Error from server (Forbidden): roles.rbac.authorization.k8s.io "x" is forbidden:
user "alice" ... attempting to grant RBAC permissions not currently held
```

### 실습: 최소 권한 역할 설계

**① 사용자용 kubeconfig 만들기**

```bash
# 키와 CSR
openssl genrsa -out dev-alice.key 2048
openssl req -new -key dev-alice.key -out dev-alice.csr -subj "/CN=alice/O=dev-team"

# CSR 제출과 승인
cat <<EOF | kubectl apply -f -
apiVersion: certificates.k8s.io/v1
kind: CertificateSigningRequest
metadata:
  name: dev-alice
spec:
  request: $(base64 -w0 < dev-alice.csr)
  signerName: kubernetes.io/kube-apiserver-client
  expirationSeconds: 86400
  usages: ["client auth"]
EOF

kubectl certificate approve dev-alice
kubectl get csr dev-alice -o jsonpath='{.status.certificate}' | base64 -d > dev-alice.crt
```

**② kubeconfig 구성**

```bash
kubectl config set-credentials alice \
  --client-certificate=dev-alice.crt --client-key=dev-alice.key --embed-certs=true

kubectl config set-context alice-ctx \
  --cluster=kind-k8s-guide --user=alice --namespace=dev
```

**③ 권한 없음 확인**

```bash
kubectl create namespace dev
kubectl --context=alice-ctx get pods -n dev
```
```
Error from server (Forbidden): pods is forbidden:
User "alice" cannot list resource "pods" in API group "" in the namespace "dev"
```

**④ Role과 RoleBinding 생성**

```yaml
# rbac-dev.yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: dev-workloads
  namespace: dev
rules:
  - apiGroups: ["", "apps"]
    resources: ["pods", "services", "deployments", "replicasets", "configmaps"]
    verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
  - apiGroups: [""]
    resources: ["pods/log", "pods/exec"]
    verbs: ["get", "create"]
  # Secret은 의도적으로 제외
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-team-binding
  namespace: dev
subjects:
  - kind: Group
    name: dev-team                      # 인증서의 O=dev-team
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: dev-workloads
  apiGroup: rbac.authorization.k8s.io
```

```bash
kubectl apply -f rbac-dev.yaml
```

**⑤ 권한 검증**

```bash
kubectl --context=alice-ctx get pods -n dev              # ✓
kubectl --context=alice-ctx create deployment web --image=nginx -n dev   # ✓
kubectl --context=alice-ctx get secrets -n dev           # ✗ Forbidden
kubectl --context=alice-ctx get pods -n default          # ✗ Forbidden
kubectl --context=alice-ctx get nodes                    # ✗ Forbidden

# 전체 권한 목록
kubectl --context=alice-ctx auth can-i --list -n dev
```

**⑥ 다른 사용자로 가장해 검증** (관리자 권한으로)

```bash
kubectl auth can-i get secrets -n dev --as=alice --as-group=dev-team
# no
kubectl auth can-i create pods -n dev --as=alice --as-group=dev-team
# yes
```

**이 방법이 RBAC 검증의 표준 도구다.** 실제 사용자 kubeconfig를 만들지 않고도 확인할 수 있다.

**⑦ 정리**

```bash
kubectl delete -f rbac-dev.yaml
kubectl delete csr dev-alice
kubectl config delete-context alice-ctx
kubectl config delete-user alice
kubectl delete namespace dev
```

### RBAC 설계 원칙

**① 최소 권한**
필요한 것만. 특히 `secrets`의 `list`/`watch`와 `pods/exec`은 신중하게.

**② 그룹 기반**
개인이 아니라 그룹에 바인딩한다.

**③ 네임스페이스 스코프 우선**
ClusterRoleBinding은 정말 필요할 때만. `cluster-admin`은 극소수에게만.

**④ 위험한 권한 목록**

| 권한 | 왜 위험한가 |
|---|---|
| `secrets` `list`/`get` | 자격증명 유출 |
| `pods/exec`, `pods/attach` | 컨테이너 침투 |
| `pods` `create` | **hostPath 마운트, 특권 컨테이너로 노드 장악 가능** |
| `nodes/proxy` | kubelet API 직접 호출 |
| `escalate`, `bind`, `impersonate` | 권한 상승 |
| `certificatesigningrequests/approval` | 임의 인증서 발급 |
| `serviceaccounts/token` | 임의 SA 토큰 발급 |

**`pods` `create` 권한이 사실상 노드 루트와 같다**는 점이 중요하다. 18장의 Pod Security Admission이 이것을 막는다.

**⑤ 감사 도구**

```bash
# 오픈소스 도구들
rakkess resolve                       # 권한 매트릭스
kubectl-who-can create pods           # 누가 이 권한을 갖고 있나
krane report                          # RBAC 위험 분석
```

## 17.4 ServiceAccount와 워크로드 아이덴티티

### ServiceAccount 기본

모든 Pod는 ServiceAccount를 갖는다. 지정하지 않으면 네임스페이스의 `default`가 쓰인다.

```yaml
spec:
  serviceAccountName: my-app
  automountServiceAccountToken: false     # ★ 필요 없으면 끄자
```

```bash
kubectl create serviceaccount my-app
kubectl get sa
```

**토큰은 어떻게 전달되는가**

v1.24부터 방식이 크게 바뀌었다.

| | **v1.24 이전** | **v1.24 이후 (현재)** |
|---|---|---|
| 저장 | SA마다 Secret 자동 생성 | **Secret 없음** |
| 만료 | 없음 (영구) | **1시간, 자동 갱신** |
| 대상 제한 | 없음 | `audience` 지정 가능 |
| 전달 | Secret 볼륨 | **projected 볼륨** |

```yaml
# 자동으로 주입되는 볼륨 (v1.24+)
volumes:
  - name: kube-api-access-xyz
    projected:
      sources:
        - serviceAccountToken:
            path: token
            expirationSeconds: 3607
            audience: ""              # 비면 API 서버용
        - configMap:
            name: kube-root-ca.crt
        - downwardAPI:
            items:
              - path: namespace
                fieldRef: { fieldPath: metadata.namespace }
```

```bash
kubectl exec <pod> -- ls /var/run/secrets/kubernetes.io/serviceaccount/
# ca.crt  namespace  token
```

**영구 토큰이 필요하다면** (CI 시스템 등) 명시적으로 만들어야 한다.

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: ci-token
  annotations:
    kubernetes.io/service-account.name: ci-bot
type: kubernetes.io/service-account-token
```

**하지만 권장되지 않는다.** 대신 단기 토큰을 요청한다.

```bash
kubectl create token ci-bot --duration=1h
```

### `automountServiceAccountToken: false`를 켜라

대부분의 애플리케이션은 쿠버네티스 API를 호출하지 않는다. 그런데 토큰이 자동 마운트되어 있으면, **Pod가 침해됐을 때 공격자가 그 토큰으로 API에 접근**할 수 있다.

```yaml
# ServiceAccount 수준에서 끄기
apiVersion: v1
kind: ServiceAccount
metadata:
  name: my-app
automountServiceAccountToken: false
---
# 또는 Pod 수준에서
spec:
  automountServiceAccountToken: false
```

**API 접근이 필요 없다면 반드시 끄자.** 보안 기본 원칙이다.

### 클라우드 IAM 연동 — 시크릿 없는 인증

7장에서 "시크릿을 아예 만들지 않는 것이 최선"이라고 했다. 그 구현이 워크로드 아이덴티티다.

**동작 원리 (공통)**

```
① Pod가 ServiceAccount 토큰(JWT)을 받는다
     · 발급자: 클러스터의 OIDC 발급자 URL
     · audience: 클라우드 IAM (예: sts.amazonaws.com)
        ↓
② 앱이 그 토큰을 클라우드 STS에 제시
        ↓
③ STS가 클러스터의 OIDC 공개키로 토큰을 검증
   "이 토큰은 정말 그 클러스터의 그 ServiceAccount가 맞다"
        ↓
④ 임시 클라우드 자격증명 발급 (1시간 등)
        ↓
⑤ 앱이 그 자격증명으로 S3, DB 등에 접근
```

**정적 액세스 키가 어디에도 없다.** 토큰은 짧고 자동 갱신된다.

**AWS — IRSA (IAM Roles for Service Accounts)**

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: s3-reader
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::123456789012:role/S3ReaderRole
```

IAM 역할의 신뢰 정책:
```json
{
  "Effect": "Allow",
  "Principal": { "Federated": "arn:aws:iam::123456789012:oidc-provider/oidc.eks.ap-northeast-2.amazonaws.com/id/ABC123" },
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {
    "StringEquals": {
      "oidc.eks...:sub": "system:serviceaccount:default:s3-reader",
      "oidc.eks...:aud": "sts.amazonaws.com"
    }
  }
}
```

**`sub` 조건이 핵심이다.** 특정 네임스페이스의 특정 SA만 이 역할을 맡을 수 있다.

**GCP — Workload Identity**

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: gcs-reader
  annotations:
    iam.gke.io/gcp-service-account: gcs-reader@project.iam.gserviceaccount.com
```

```bash
gcloud iam service-accounts add-iam-policy-binding \
  gcs-reader@project.iam.gserviceaccount.com \
  --role roles/iam.workloadIdentityUser \
  --member "serviceAccount:project.svc.id.goog[default/gcs-reader]"
```

**Azure — Workload Identity**

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: kv-reader
  annotations:
    azure.workload.identity/client-id: <client-id>
---
apiVersion: apps/v1
kind: Deployment
spec:
  template:
    metadata:
      labels:
        azure.workload.identity/use: "true"      # ★ 라벨 필요
```

**어느 클라우드든 원리는 같다: OIDC 신뢰를 통한 토큰 교환.**

### SPIFFE / SPIRE

클라우드 종속 없이 같은 개념을 구현하는 표준이다. 워크로드마다 **SVID**(SPIFFE Verifiable Identity Document)라는 X.509 인증서나 JWT를 발급한다.

```
spiffe://example.org/ns/production/sa/payment-api
```

서비스 메시(11.6절)의 mTLS가 이 아이덴티티를 기반으로 동작한다. 멀티 클라우드·하이브리드 환경에서 일관된 워크로드 아이덴티티가 필요할 때 검토한다.

## 17.5 어드미션 컨트롤

### 위치와 순서

인가를 통과한 요청이 etcd에 저장되기 **직전**에 개입한다.

```
인가 통과
    ↓
① Mutating Admission     ← 요청을 수정한다
    · 내장 플러그인들
    · MutatingAdmissionWebhook
    ↓
② 스키마 검증 (OpenAPI)
    ↓
③ Validating Admission   ← 거부할 수 있다
    · 내장 플러그인들
    · ValidatingAdmissionPolicy (CEL)
    · ValidatingAdmissionWebhook
    ↓
etcd 저장
```

**Mutating이 먼저인 이유**: 기본값을 주입한 뒤에 검증해야 하기 때문이다. 13장의 LimitRange가 기본값을 넣고, ResourceQuota가 그 값으로 총량을 검사하는 순서가 이것이다.

### 주요 내장 플러그인

```bash
docker exec k8s-guide-control-plane \
  grep enable-admission-plugins /etc/kubernetes/manifests/kube-apiserver.yaml
```

| 플러그인 | 역할 | 관련 장 |
|---|---|---|
| `NamespaceLifecycle` | 없거나 종료 중인 네임스페이스에 생성 거부 | 13장 |
| `LimitRanger` | 기본값 주입, 범위 검사 | 13장 |
| `ResourceQuota` | 쿼터 검사 | 13장 |
| `ServiceAccount` | SA 토큰 볼륨 주입 | 17.4절 |
| `PodSecurity` | Pod Security Standards 강제 | 18장 |
| `DefaultStorageClass` | PVC에 기본 SC 주입 | 12장 |
| `DefaultTolerationSeconds` | 기본 톨러레이션 추가 | 15장 |
| `NodeRestriction` | kubelet이 자기 노드/Pod만 수정하도록 제한 | 20장 |
| `Priority` | PriorityClass 검증과 값 주입 | 15장 |
| `MutatingAdmissionWebhook` | 외부 웹훅 호출 (변형) | 28장 |
| `ValidatingAdmissionWebhook` | 외부 웹훅 호출 (검증) | 28장 |

**`NodeRestriction`이 특히 중요하다.** 침해된 노드의 kubelet이 다른 노드의 Pod를 조작하는 것을 막는다. 20장에서 다룬다.

### ValidatingAdmissionPolicy — 웹훅 없는 정책

v1.30에서 GA된 기능이다. **CEL**(Common Expression Language) 표현식으로 정책을 작성하며, 외부 웹훅 서버가 필요 없다.

```yaml
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: require-resource-limits
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
      - apiGroups: ["apps"]
        apiVersions: ["v1"]
        operations: ["CREATE", "UPDATE"]
        resources: ["deployments"]
  validations:
    - expression: |
        object.spec.template.spec.containers.all(c,
          has(c.resources) && has(c.resources.limits) &&
          has(c.resources.limits.memory))
      message: "모든 컨테이너에 memory limit이 필요합니다"

    - expression: |
        object.spec.template.spec.containers.all(c,
          !c.image.endsWith(":latest"))
      message: "latest 태그는 사용할 수 없습니다"
---
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata:
  name: require-resource-limits-binding
spec:
  policyName: require-resource-limits
  validationActions: [Deny]        # Deny | Warn | Audit
  matchResources:
    namespaceSelector:
      matchLabels:
        environment: production
```

**웹훅 대비 장점**
- 별도 서버를 운영할 필요가 없다 → **가용성 문제가 없다**
- API 서버 안에서 실행 → **지연이 없다**
- `validationActions: Warn`으로 **경고만 하며 점진 도입** 가능

**한계**: 외부 데이터를 조회하거나 복잡한 로직은 불가능하다. 그런 경우는 여전히 웹훅이 필요하다(28장).

**MutatingAdmissionPolicy**도 v1.32에서 알파로 도입되어 발전 중이다.

### 웹훅과 정책 엔진

복잡한 정책은 여전히 웹훅이 필요하다. 직접 만들 수도 있지만(28장), 대개는 정책 엔진을 쓴다.

- **OPA Gatekeeper**: Rego 언어. 성숙하고 표현력이 높다
- **Kyverno**: YAML로 정책 작성. 학습 곡선이 낮다

18장에서 다룬다.

> **⚠️ 웹훅의 위험**
> `failurePolicy: Fail`인 웹훅 서버가 죽으면 **해당 리소스의 모든 생성/수정이 차단된다.** 클러스터 전체가 마비될 수 있다.
>
> **필수 대비책**
> - `namespaceSelector`로 `kube-system` 제외
> - 웹훅 서버 자체를 다중화
> - `timeoutSeconds`를 짧게(5~10초)
> - 처음에는 `failurePolicy: Ignore`로 시작

## 실습 과제

**과제 1 — 위험한 권한 실험**
`pods` `create` 권한만 가진 사용자를 만들고, hostPath로 `/`를 마운트한 Pod를 만들어 노드 파일 시스템에 접근되는 것을 확인한다. 이것이 왜 "노드 루트와 같다"고 하는지 체험한 뒤, 18장의 Pod Security Admission으로 차단해 본다.

**과제 2 — resourceNames와 list의 한계**
`resourceNames`로 특정 Secret만 `get`할 수 있는 Role을 만들고, `get`은 제한되지만 `list`를 추가하면 모든 Secret이 보이는 것을 확인한다.

**과제 3 — ClusterRole 재사용 패턴**
하나의 ClusterRole을 만들고 세 개의 네임스페이스에 각각 RoleBinding으로 연결한다. `kubectl auth can-i --as=...`로 각 네임스페이스에서의 권한을 검증한다.

**과제 4 — automountServiceAccountToken 효과**
토큰이 마운트된 Pod와 그렇지 않은 Pod에서 각각 API 서버 호출을 시도한다.
```bash
kubectl exec <pod> -- sh -c '
  TOKEN=$(cat /var/run/secrets/kubernetes.io/serviceaccount/token)
  curl -s --cacert /var/run/secrets/kubernetes.io/serviceaccount/ca.crt \
    -H "Authorization: Bearer $TOKEN" \
    https://kubernetes.default.svc/api/v1/namespaces/default/pods | head -20'
```

**과제 5 — ValidatingAdmissionPolicy 작성**
`latest` 태그를 금지하는 정책을 만들고, `validationActions: [Warn]`으로 먼저 배포해 경고만 나오는 것을 확인한 뒤 `[Deny]`로 바꿔 차단되는 것을 확인한다.

## 요약

- API 요청은 **인증 → 인가 → 어드미션** 세 관문을 지난다. **401은 신원 문제, 403은 권한 문제**다.
- **쿠버네티스에는 사용자 오브젝트가 없다.** 인증기가 요청에서 username과 groups 문자열을 추출할 뿐이며, 사용자 관리는 외부(CA, OIDC, 클라우드 IAM)의 일이다. ServiceAccount만 실제 오브젝트다.
- **클라이언트 인증서는 폐기할 수 없다.** 프로덕션의 사람 인증은 **OIDC**가 표준이다. `system:masters` 그룹은 RBAC를 우회하므로 `admin.conf`는 금고에 보관한다.
- RBAC은 **Role/ClusterRole(권한) × RoleBinding/ClusterRoleBinding(연결)** 네 리소스다. **RoleBinding + ClusterRole 조합**으로 역할을 정의해 여러 네임스페이스에서 재사용하는 것이 실무 패턴이다.
- **`list`는 `get`보다 훨씬 위험하다.** `resourceNames`는 `list`/`watch`에 적용되지 않는다. `secrets` `list`는 네임스페이스 전체 자격증명 덤프와 같다.
- **`pods` `create` 권한은 사실상 노드 루트 권한**이다. hostPath와 특권 컨테이너로 노드를 장악할 수 있다. 18장의 Pod Security Admission이 이를 막는다.
- ServiceAccount 토큰은 v1.24부터 **1시간 만료, 자동 갱신되는 projected 볼륨**으로 전달된다. **API 접근이 필요 없는 워크로드는 `automountServiceAccountToken: false`로 꺼야 한다.**
- **워크로드 아이덴티티**(IRSA, GKE Workload Identity, Azure Workload Identity)는 SA 토큰을 클라우드 STS에서 임시 자격증명으로 교환한다. **정적 액세스 키가 사라진다.**
- 어드미션은 **Mutating → 스키마 검증 → Validating** 순서다. **ValidatingAdmissionPolicy(CEL)** 는 웹훅 서버 없이 정책을 강제하므로 가용성 문제가 없고, `Warn`으로 점진 도입할 수 있다.
- **`failurePolicy: Fail`인 웹훅 서버가 죽으면 클러스터가 마비된다.** `kube-system` 제외, 다중화, 짧은 타임아웃이 필수다.

**다음 장에서는** 이 권한 체계 위에서 워크로드 자체를 단단하게 만든다. 컨테이너·Pod·노드 각 층위의 공격 표면을 줄이고, 네트워크를 잠그고, 이미지 공급망을 검증하는 방법을 다룬다.
