# 9장. 마무리

## 9.1 이 책에서 반복된 하나의 패턴

돌이켜보면 모든 장에서 같은 구조가 반복됐다.

> **"프로그래머에게는 단순한 추상화로 보이지만, 그 아래에서 OS는 훨씬 복잡한 일을 하고 있으며, 그 복잡함이 새어나오는 지점(leaky abstraction)이 바로 버그와 성능 문제가 생기는 곳이다."**

- 프로세스: "그냥 프로그램 하나 실행"처럼 보이지만 → 주소 공간 구성, 핸들 테이블, IPC 격리
- 스레드: "그냥 동시에 실행"처럼 보이지만 → 컨텍스트 스위칭 비용, 메모리 가시성, 데드락
- 메모리: "그냥 할당"처럼 보이지만 → 가상/물리 분리, commit/reserve, 페이지 폴트, 캐시 지역성
- 네트워크: "그냥 send/recv"처럼 보이지만 → 스트림 vs 메시지, 블로킹의 확장성 한계, 완료/준비 모델

## 9.2 핵심 개념 한 장 요약

| 장 | 한 문장 요약 |
|---|---|
| 2. OS 큰 그림 | 유저 코드는 시스템 콜/인터럽트를 통해서만 커널에 개입을 요청할 수 있고, 스케줄러가 CPU 시간을 잘라 나눠준다 |
| 3. 프로세스 | 프로세스는 격리된 주소 공간 + 핸들 테이블의 묶음이고, 실행은 스레드가 담당한다 |
| 4. 스레드/동시성 | 힙을 공유하는 스레드들 사이의 순서/가시성은 명시적 동기화 없이는 보장되지 않는다 |
| 5. 메모리 | 프로세스가 보는 주소는 가상이며, "할당"과 "실제 물리 메모리 사용"은 다른 시점의 다른 사건이다 |
| 6. 네트워크 | 소켓은 스트림/메시지 경계를 대신 챙겨주지 않으며, 커넥션이 많아질수록 블로킹+스레드 모델은 한계에 부딪힌다 |
| 7. 파일/IO | 파일 쓰기는 여러 겹의 버퍼(라이브러리, 커널 캐시)를 거치며, 실제 디스크 반영 시점은 명시적으로 요구해야 한다 |
| 8. 도구 | 이론으로 세운 가설을 프로파일러/디버거로 검증하는 습관이 감으로 최적화하는 것보다 빠르다 |

## 9.3 더 공부하고 싶다면

이 폴더에 이미 있는 참고서로 더 깊이 들어갈 수 있다.

- **Windows Internals (Part 1/2)** — 이 책의 Windows 관련 내용(EPROCESS, 페이지 관리자, IOCP 내부 구현 등)을 훨씬 깊게 다룬다. 특히 메모리 관리자 장과 프로세스/스레드 내부 구조 장을 추천한다.
- **Windows via C/C++** — 이 책에서 코드로 언급한 API들(`CreateProcess`, `VirtualAlloc`, 동기화 프리미티브, IOCP)의 실제 사용법과 함정을 코드 레벨로 다룬다.

플랫폼 무관하게 더 보고 싶다면:

- *Operating Systems: Three Easy Pieces* (무료, 온라인) — 가상화/동시성/영속성이라는 이 책과 거의 같은 3축 구조로 더 학술적으로 깊게 다룬다.
- 리눅스 쪽 실전 지식은 *The Linux Programming Interface*(Michael Kerrisk)가 이 책의 "Windows via C/C++"에 대응하는 위치에 있다.

## 9.4 마지막으로

이 책의 목표는 "OS 전문가"를 만드는 게 아니라, **평소에 쓰는 API 뒤에서 벌어지는 일에 대한 정확한 멘탈 모델**을 갖추는 것이었다. 다음에 이상한 성능 문제나 동시성 버그를 만나면, "감"이 아니라 이 책에서 다룬 메커니즘(가상 메모리, 스케줄러, 동기화, I/O 모델) 중 어디가 관련 있는지부터 짚어보길 바란다.
