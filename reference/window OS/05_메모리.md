# 5장. 메모리

이 책에서 가장 오해가 많은 주제다. "메모리 사용량"이라는 숫자 하나에 최소 3~4가지 다른 의미가 섞여 있다.

## 5.1 가상 메모리: 모든 것의 시작

프로세스가 보는 주소(예: `0x00007FF6A2340000`)는 **실제 물리 메모리 주소가 아니다.** CPU의 MMU(Memory Management Unit)가 **페이지 테이블**을 통해 가상 주소를 물리 주소로 변환한다.

```
가상 주소 공간 (프로세스별 독립)     물리 메모리 (전체 시스템 공유)
┌─────────────┐                    ┌─────────────┐
│ 0x1000 페이지 │ ─────────────────▶│  물리 페이지 A │
│ 0x2000 페이지 │ ─────────────────▶│  물리 페이지 B │
│ 0x3000 페이지 │ ─(아직 매핑 안됨)   │  ...         │
└─────────────┘                    └─────────────┘
   (프로세스 A의 뷰)
```

**왜 이렇게 하는가**: (1) 각 프로세스가 독립된 주소 공간을 갖게 되어 서로의 메모리를 못 봄(격리/보안), (2) 물리 메모리보다 큰 주소 공간을 쓸 수 있음(오버커밋, 스와핑), (3) 물리적으로 흩어진 메모리를 논리적으로 연속된 것처럼 보이게 할 수 있음(단편화 완화).

**페이지 폴트**: 가상 주소에 접근했는데 대응하는 물리 페이지가 아직 없으면(디스크에 있거나, 아직 할당 안 됨) CPU가 예외를 던지고, 커널이 페이지를 채운 뒤 실행을 재개한다 ([2장](02_OS_큰그림.md) 참고). 이게 "느리게 느껴지는 첫 접근"의 원인이다 — 프로세스를 처음 실행하거나 큰 배열에 처음 접근할 때 느린 이유.

## 5.2 "할당했다"와 "실제로 쓴다"는 다르다: Commit vs Reserve

```c
// Windows
void* p = VirtualAlloc(NULL, 100 * 1024 * 1024, MEM_RESERVE, PAGE_NOACCESS);
// 이 시점: 주소 공간 100MB를 "예약"만 함. 물리 메모리 0바이트 사용.

VirtualAlloc(p, 4096, MEM_COMMIT, PAGE_READWRITE);
// 이 시점: 4KB(1페이지)만 실제로 커밋. 아직 이 페이지를 "읽거나 쓰기" 전까지는
// 물리 페이지가 배정 안 될 수도 있음(demand paging).
```

리눅스의 `mmap(..., MAP_PRIVATE | MAP_ANONYMOUS, ...)`도 비슷하다 — 매핑 자체는 가상 주소 공간에 예약만 해두고, 실제 물리 페이지는 **처음 쓰기(또는 읽기)가 일어나는 순간**(demand paging)에야 배정된다.

이래서 `malloc(1GB)`를 해도 "실제 물리 메모리 사용량"(RSS, Resident Set Size / Working Set)은 거의 안 늘어나는 경우가 흔하다. **가상 메모리 크기(Virtual Size)와 실제 상주 메모리(RSS/Working Set)는 다른 숫자다** — 작업 관리자/`top`에서 헷갈리기 쉬운 지점.

## 5.3 힙(Heap)과 스택(Stack)

| | 스택 | 힙 |
|---|---|---|
| 할당 단위 | 함수 호출 프레임 (자동) | `malloc`/`new`/`VirtualAlloc` (수동/런타임 관리) |
| 크기 | 스레드당 고정(보통 1~8MB), 초과 시 스택 오버플로 | 프로세스 전체가 공유, 가상 주소 공간 한계까지 |
| 속도 | 매우 빠름 (포인터만 이동) | 상대적으로 느림 (할당자 로직, 락 필요 가능) |
| 해제 | 함수 리턴 시 자동 | 명시적 해제 필요 (또는 GC/스마트 포인터) |
| 생명주기 | 함수 실행 동안 | 명시적으로 해제할 때까지 |

**스택 오버플로**는 대개 (1) 재귀 함수가 종료 조건 없이 깊어질 때, (2) 스택에 거대한 배열을 지역 변수로 선언할 때 발생한다. 큰 버퍼는 힙에 할당해야 한다.

**힙 할당자(allocator)**는 그 자체로 하나의 작은 메모리 관리자다 — 사용자 프로그램의 `malloc`/`free` 호출을 받아 내부적으로 청크를 관리하고, 필요할 때만 `VirtualAlloc`/`mmap`/`brk`로 OS에게 더 큰 블록을 요청한다. 그래서 `free()`를 호출해도 **OS에 즉시 메모리가 반환되지 않는 경우가 많다** — 할당자가 재사용을 위해 들고 있는 것.

## 5.4 메모리 누수와 "커밋되었지만 안 쓰이는" 메모리

메모리 누수는 두 가지 다른 현상을 뭉뚱그려 부르는 말이다.

1. **진짜 누수**: 참조를 잃어서 다시는 `free`할 수 없는 메모리 (C/C++의 고전적 문제)
2. **비대해진 캐시/풀**: 논리적으로는 "쓰고 있는" 상태지만 실제로는 거의 안 쓰이는데 계속 들고 있는 것 (예: 캐시에 만료 정책이 없음)

둘 다 프로세스의 Working Set을 계속 늘리지만, 해결책은 다르다 — 1번은 버그 수정, 2번은 캐시 정책/메모리 압박 대응 로직이 필요하다.

## 5.5 캐시와 TLB: 왜 "메모리 접근 패턴"이 성능을 좌우하는가

CPU는 메인 메모리보다 훨씬 빠른 다단계 캐시(L1/L2/L3)를 가진다. 데이터가 캐시에 있으면(cache hit) 수 ns, 메인 메모리까지 가야 하면(cache miss) 수십~수백 ns가 걸린다 — **자릿수가 다른 차이**다.

```c
// 캐시 친화적 (연속 접근)
for (int i = 0; i < N; i++) sum += arr[i];

// 캐시 비친화적 (같은 데이터, 다른 접근 패턴 — 2차원 배열을 열 우선으로 순회)
for (int j = 0; j < N; j++)
    for (int i = 0; i < N; i++)
        sum += matrix[i][j];   // 캐시 라인을 매번 새로 가져옴
```

**TLB(Translation Lookaside Buffer)**는 가상→물리 주소 변환 결과를 캐싱하는 작은 캐시다. 컨텍스트 스위칭이 일어나면(특히 프로세스 전환) TLB가 무효화될 수 있어, 이것도 컨텍스트 스위칭 비용의 일부다. "거대 페이지(Huge Page/Large Page)"를 쓰면 TLB 엔트리 하나가 더 넓은 범위를 커버해서 TLB 미스를 줄일 수 있다 — 대용량 메모리를 다루는 DB/캐시 서버에서 종종 쓰는 최적화.

## 5.6 캐시 라인과 거짓 공유(False Sharing)

캐시는 메모리를 바이트 단위가 아니라 **캐시 라인(보통 64바이트)** 단위로 옮긴다. 이 때문에 스레드 두 개가 **완전히 다른 변수**를 쓰더라도, 그 변수들이 우연히 같은 캐시 라인에 있으면 서로의 캐시를 계속 무효화시키는 일이 생긴다.

```c
struct Counters {
    long counterA;   // Thread A가 계속 증가
    long counterB;   // Thread B가 계속 증가 (A와 같은 캐시 라인에 위치할 확률이 높음)
};
```

`counterA`와 `counterB`는 서로 다른 변수라 락도 필요 없고 레이스 컨디션도 없지만, 같은 캐시 라인에 있으면 한쪽이 쓸 때마다 다른 코어의 캐시에 있던 그 라인이 무효화되어 계속 메인 메모리까지 왕복하게 된다 — **데이터 경쟁은 없는데 캐시 경쟁 때문에 락을 쓴 것처럼 느려지는** 현상이다. 해결책은 성능이 중요한 변수들을 캐시 라인 크기만큼 패딩을 넣어 분리하는 것(`alignas(64)` 등). [4장](04_스레드와_동시성.md)에서 본 "멀티스레드인데 이상하게 느리다"의 원인 중 락 경쟁 다음으로 흔한 것이 이 거짓 공유다.

## 5.7 프로세스 가상 주소 공간의 모습 (Windows x64 예시)

x64에서는 가상 주소가 64비트 전체를 다 쓰는 게 아니라, CPU가 상위 비트를 부호 확장한 **canonical 주소**만 유효하다(현재 세대 CPU는 보통 48비트 유효). 그 결과 유저 공간과 커널 공간은 딱 붙어있는 게 아니라, 둘 사이에 **아예 접근할 수 없는 거대한 구멍(non-canonical 영역)**이 있다.

```
0xFFFFFFFFFFFFFFFF ┌───────────────────┐
                    │   커널 공간         │  ← 0xFFFF8000`00000000 부터, 유저 코드는 접근 불가
0xFFFF800000000000  ├───────────────────┤
                    │                    │
                    │  (non-canonical,   │  ← 어떤 프로세스도 매핑할 수 없는 구간
                    │   존재하지 않는 주소) │
                    │                    │
0x00007FFFFFFFFFFF  ├───────────────────┤
                    │   유저 공간 상단     │
                    │   (스택들, 보통      │
                    │    높은 주소에서     │
                    │    아래로 자람)      │
                    ├───────────────────┤
                    │   힙 (동적 할당)     │
                    │   ↑ 위로 성장       │
                    ├───────────────────┤
                    │   DLL/공유 라이브러리 │
                    ├───────────────────┤
                    │   데이터/BSS (전역)  │
                    ├───────────────────┤
                    │   코드(.text)      │
0x0000000000000000  └───────────────────┘
```

이 그림에서 중요한 함의 두 가지: (1) 스택과 힙이 서로 다른 방향에서 자라도록 배치해서, 둘이 충돌하려면 아주 많이 커져야 한다. (2) 유저 공간 최상단 주소(`0x00007FFFFFFFFFFF`)를 넘어서면 바로 커널이 아니라, 절대 매핑되지 않는 non-canonical 구간을 거쳐야 커널 주소(`0xFFFF8000...`)에 닿는다 — 그래서 커널 포인터는 항상 매우 큰(음수처럼 보이는) 값으로 나타난다. 32비트 시절에는 4GB 공간을 유저/커널이 기본 2GB씩(또는 `/3GB` 옵션으로 3GB/1GB) 나눠 썼는데, 이때는 정말로 경계선 하나로 붙어있었다.

또한 주소 공간 배치(스택/힙/DLL의 정확한 위치)는 매 실행마다 무작위화된다(**ASLR, Address Space Layout Randomization**) — 보안(버퍼 오버플로 공격 완화) 목적이며, 위 그림은 상대적 배치 순서만 보여주는 단순화된 그림이다.

## 5.8 스와핑(Swapping)/페이징 파일

물리 메모리가 부족하면 OS는 당장 안 쓰는 페이지를 디스크(Windows의 페이지 파일 `pagefile.sys`, 리눅스의 swap)로 밀어내고 그 물리 페이지를 다른 데 재사용한다. 나중에 그 페이지에 다시 접근하면 페이지 폴트가 나서 디스크에서 다시 읽어온다.

**실무 함의**: 시스템이 스와핑을 심하게 하기 시작하면("스래싱, thrashing") 디스크 I/O가 CPU보다 압도적으로 느리므로 시스템 전체가 급격히 느려진다. "메모리가 부족한데 CPU 사용률은 낮고 응답이 느리다"는 스와핑을 의심할 신호다.

## 5.9 가비지 컬렉션(GC) 언어에서는 무엇이 다른가

Java/C#/Go/Python처럼 GC가 있는 언어를 쓰더라도 이 장의 내용은 그대로 적용된다 — 다만 "누가 `free`를 호출하는가"만 런타임으로 옮겨갈 뿐이다.

- **힙 자체는 여전히 OS가 관리한다**: GC 런타임도 내부적으로 `VirtualAlloc`/`mmap`으로 큰 메모리 블록을 받아와서, 그 안에서 자체적으로 객체를 배치한다. `-Xmx`(JVM), `GOGC`(Go), 프로세스 메모리 상한 같은 설정은 결국 "런타임이 OS에게 얼마나 크게 요청할지"를 조절하는 것이다.
- **GC가 메모리를 회수해도 OS에 돌려주지 않는 경우가 흔하다**: 5.3절의 "`free()`해도 할당자가 들고 있는다"와 같은 이유로, GC 런타임도 회수한 공간을 다음 할당을 위해 계속 들고 있는 경우가 많다. 그래서 "GC가 실행됐는데 왜 프로세스 메모리(Working Set/RSS)가 안 줄어들지?"는 버그가 아니라 정상적인 경우가 대부분이다.
- **GC 일시정지(Stop-the-World)와 스케줄러**: GC가 힙을 정리하는 동안 애플리케이션 스레드를 잠깐 멈추는 방식(특히 오래된 GC 알고리즘)은 [4장](04_스레드와_동시성.md)의 컨텍스트 스위칭/스케줄링과 얽힌다 — GC 스레드 우선순위, 코어 수, 다른 프로세스와의 CPU 경쟁이 GC 정지 시간에 영향을 준다.
- **거짓 공유는 GC 언어에서도 그대로 발생한다**: 객체 배치를 런타임이 결정하므로 개발자가 직접 캐시 라인 정렬을 통제하기 어렵지만, 핫스팟 필드를 별도 객체/패딩으로 분리하는 최적화가 여전히 유효하다(예: Java의 `@Contended`).

## 5.10 실전 체크리스트

- [ ] "메모리 사용량이 높다"고 할 때 Virtual Size, Committed, Working Set/RSS 중 무엇을 보고 있는지 구분했는가?
- [ ] 큰 배열/버퍼를 스택에 선언하고 있지 않은가?
- [ ] 캐시/풀 구조에 만료·상한 정책이 있는가, 아니면 무한정 자라는가?
- [ ] 성능이 중요한 반복문에서 메모리 접근 패턴(연속 접근 vs 산발적 접근)을 고려했는가?
- [ ] `free`/`delete`(또는 GC) 이후에도 프로세스의 Working Set이 안 줄어드는 게 "정상"이라는 걸 알고 있는가? (할당자/런타임이 재사용을 위해 들고 있을 수 있음)
- [ ] 멀티스레드 성능이 이상하게 안 나올 때, 락 경쟁이 아니라 거짓 공유(5.6절) 가능성도 점검했는가?

## 5.11 다른 OS에서는

| 개념 | Windows | Linux |
|---|---|---|
| 예약/커밋 | `VirtualAlloc` (MEM_RESERVE/MEM_COMMIT) | `mmap` (매핑 시점) / 실제 커밋은 demand paging |
| 상주 메모리 지표 | Working Set | RSS (Resident Set Size) |
| 스왑 공간 | 페이지 파일 (`pagefile.sys`) | Swap 파티션/파일 |
| 메모리 매핑 파일 | `CreateFileMapping` + `MapViewOfFile` | `mmap` |
| 메모리 부족 시 대응 | Working Set 트리밍, 필요시 프로세스 종료 | OOM Killer가 점수 기반으로 프로세스 강제 종료 |
