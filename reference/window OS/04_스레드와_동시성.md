# 4장. 스레드와 동시성

이 장은 이 책에서 가장 실무 버그와 직결되는 장이다. 데드락, 레이스 컨디션, "가끔씩만 실패하는" 버그는 대부분 여기서 설명하는 내용을 놓쳐서 생긴다.

## 4.1 스레드란 무엇인가

스레드는 "프로세스 안에서 독립적으로 실행되는 흐름"이다. 같은 프로세스의 스레드들은 다음을 **공유**한다.

- 가상 주소 공간 (힙, 전역 변수, 코드)
- 핸들/파일 디스크립터 테이블

반면 다음은 스레드마다 **독립적으로 가진다**.

- 스택 (Windows 기본 1MB, 리눅스 기본 8MB 등 — 조정 가능)
- 레지스터 상태 (프로그램 카운터, 스택 포인터 등)
- Thread-Local Storage(TLS)
- 스케줄링 상태(우선순위, 실행/대기 상태)

**"같은 힙을 공유한다"는 사실이 동시성 문제의 근원이다** — 두 스레드가 동시에 같은 변수를 건드리면 순서가 보장되지 않는다.

## 4.2 컨텍스트 스위칭은 공짜가 아니다

스레드를 바꿔 끼울 때 커널은:

1. 현재 스레드의 레지스터 상태를 저장
2. 다음 스레드의 레지스터 상태를 복원
3. (필요시) TLB 플러시, 캐시 지역성 손실

이 비용 때문에 "스레드를 1000개 만들면 1000배 빨라진다"는 착각은 틀렸다. **코어 수보다 훨씬 많은 CPU 바운드 스레드**는 컨텍스트 스위칭 오버헤드만 늘리고 실질적인 처리량은 늘지 않거나 오히려 줄어든다. (단, I/O 대기가 많은 스레드는 다르다 — 대기 중엔 스케줄러가 다른 스레드에게 CPU를 주므로 스레드 수를 늘리는 게 이득일 수 있다.)

## 4.3 레이스 컨디션(Race Condition)

```c
// 두 스레드가 동시에 실행
counter++;   // 실제로는: load counter → add 1 → store counter (원자적이지 않음!)
```

`counter++`는 하나의 명령어처럼 보이지만 실제로는 **읽기-수정-쓰기(read-modify-write)** 3단계다. 두 스레드가 동시에 이걸 하면 한쪽 증가분이 사라질 수 있다.

```
Thread A: load counter (=5)
Thread B: load counter (=5)
Thread A: add 1 → store (6)
Thread B: add 1 → store (6)   ← 원래 7이 되어야 했는데 6이 됨
```

이런 버그는 **재현이 안 되고 타이밍에 따라 가끔만 발생**하기 때문에 디버깅이 특히 괴롭다.

## 4.4 동기화 프리미티브

| 프리미티브 | Windows | POSIX | 특징 |
|---|---|---|---|
| 뮤텍스/락 | `CRITICAL_SECTION`, `Mutex` | `pthread_mutex_t` | 한 번에 하나의 스레드만 진입, 소유권 개념 |
| 읽기/쓰기 락 | `SRWLOCK` | `pthread_rwlock_t` | 읽기는 여러 개 동시, 쓰기는 배타적 |
| 세마포어 | `Semaphore` | `sem_t` | N개까지 동시 진입 허용 (자원 풀 제한에 적합) |
| 조건 변수 | `CONDITION_VARIABLE` | `pthread_cond_t` | "조건이 될 때까지 대기" + 락 해제/재획득을 원자적으로 |
| 원자적 연산 | `InterlockedIncrement` 등 | `std::atomic`, `__atomic_*` | 락 없이 CPU 명령어로 원자성 보장 (CAS 등) |
| 이벤트 | `Event` | 조건변수로 흉내 | 신호 대기(생산자-소비자 등) |

**CRITICAL_SECTION vs Mutex**: `CRITICAL_SECTION`은 유저 모드에서만 동작하며(경쟁이 없을 때 시스템 콜 없이 바로 처리, 스핀 후 커널 대기로 전환 가능) 같은 프로세스 내에서만 쓸 수 있다. `Mutex`는 커널 객체라 프로세스 간 공유가 가능하지만 매번 커널 모드 전환 비용이 있다. **"프로세스 내부에서만 쓸 락이면 CRITICAL_SECTION/std::mutex, 프로세스 간 공유가 필요하면 named Mutex"**가 기본 선택 기준이다.

## 4.5 데드락(Deadlock)

두 개 이상의 락을 서로 다른 순서로 잡으면 데드락이 난다.

```
Thread A: lock(L1); ... lock(L2);   // L1 잡고 L2 기다림
Thread B: lock(L2); ... lock(L1);   // L2 잡고 L1 기다림  → 영원히 대기
```

**해결책**: 모든 곳에서 **락을 잡는 순서를 일관되게 정한다**(예: 항상 주소가 작은 락부터). 또는 하나의 락만 잡고 끝내는 설계로 단순화한다. 데드락은 코드 리뷰로 잡기 어렵고, 락 순서 규칙을 팀 컨벤션으로 강제하는 게 현실적이다.

## 4.6 데드락과 헷갈리는 사촌들: 라이브락, 기아, 우선순위 역전

- **라이브락(Livelock)**: 스레드들이 멈춰있진 않고 계속 뭔가 "실행"은 하는데, 서로 양보만 하다가 전체적으로 진행이 안 되는 상태. 예: 두 스레드가 락 충돌을 감지하면 둘 다 "내가 양보할게"하며 물러났다가 다시 동시에 시도하기를 반복.
- **기아(Starvation)**: 특정 스레드가 락/CPU를 계속 못 얻어서 영원히(혹은 아주 오래) 진행을 못하는 상태. 데드락과 달리 시스템 전체는 멈추지 않지만, 그 스레드 입장에서는 멈춘 것과 같다. 우선순위가 낮은 스레드가 우선순위 높은 스레드들에 밀려 CPU를 못 받는 경우가 대표적.
- **우선순위 역전(Priority Inversion)**: 낮은 우선순위 스레드가 락을 잡고 있는데, 높은 우선순위 스레드가 그 락을 기다리면서 대기 — 이때 중간 우선순위 스레드가 CPU를 계속 뺏어가면, 정작 락을 풀어줘야 할 낮은 우선순위 스레드가 실행을 못 받아 높은 우선순위 스레드까지 덩달아 무한정 대기하는 현상. 1997년 화성 탐사선 Mars Pathfinder가 실제로 이 버그로 재부팅을 반복했던 유명한 사례가 있다. 리눅스의 `PTHREAD_PRIO_INHERIT` 뮤텍스 속성은 정식으로 **우선순위 상속(priority inheritance)** 프로토콜을 구현한다. Windows는 이와 똑같은 이름의 메커니즘을 문서화하고 있진 않지만, 락을 소유한 스레드가 락을 반납할 때 대기 중인 스레드에게 임시로 우선순위를 부여하는 "우선순위 부스트(priority boost)"를 스케줄러 차원에서 적용해 비슷한 효과(기아·역전 완화)를 낸다(*Windows Internals* 7판, 4장 "Priority boosts" 참고).

## 4.7 메모리 가시성(Memory Visibility)과 메모리 모델

레이스 컨디션과 별개로, 컴파일러/CPU의 **명령어 재배치**와 **캐시** 때문에 한 스레드가 쓴 값이 다른 스레드에 "언제" 보이는지가 보장되지 않는다.

```c
// Thread A                  // Thread B
data = 42;                   while (!ready) { }   // 무한 대기할 수 있음!
ready = true;                use(data);
```

컴파일러나 CPU가 `data = 42`와 `ready = true`의 순서를 바꿔도(둘 사이에 의존관계가 없어 보이므로) 프로그램 의미상 문제없다고 판단할 수 있다. 그러면 Thread B가 `ready`를 먼저 보고도 `data`는 옛 값을 볼 수 있다.

**해결책**: 원자적 변수 + 적절한 메모리 순서(memory order)를 쓴다. C++의 `std::atomic<bool> ready` (기본 `memory_order_seq_cst`)나, Windows의 `Interlocked*` 계열, 혹은 락으로 감싸는 것이 안전하다. "일반 변수 + `volatile`만으로 스레드 동기화를 하려는 시도"는 흔한 안티패턴이다 — `volatile`은 컴파일러 최적화만 막을 뿐 CPU 재배치나 원자성을 보장하지 않는다.

## 4.8 스레드 풀과 비동기 실행

스레드를 매번 새로 만드는 비용(스택 할당, 커널 객체 생성)을 피하려고 **스레드 풀**을 쓴다. Windows는 `Thread Pool API`(`CreateThreadpoolWork` 등), .NET은 `ThreadPool`/`Task`, 리눅스 진영은 보통 직접 구현하거나 libuv/asio 같은 라이브러리를 쓴다. 스레드 풀 크기를 코어 수보다 훨씬 크게 잡아야 하는 경우는 **작업이 I/O 대기를 많이 포함할 때**뿐이다. CPU 바운드 작업 풀은 보통 "코어 수" 근처가 최적이다.

**참고**: 스레드 수를 늘렸는데 오히려 느려졌다면, 컨텍스트 스위칭 비용 외에도 [5장](05_메모리.md)에서 다룰 **거짓 공유(False Sharing)** — 서로 다른 스레드가 각자 다른 변수를 쓰는데 그 변수들이 같은 캐시 라인에 있어서 캐시가 계속 무효화되는 현상 — 이 원인일 수 있다.

## 4.9 실전 체크리스트

- [ ] 공유 변수에 접근할 때 락/원자적 연산 없이 그냥 읽고 쓰는 곳이 있는가? (있다면 레이스 컨디션 후보)
- [ ] 락을 여러 개 잡는 코드에서, 모든 스레드가 같은 순서로 잡는가?
- [ ] 스레드 풀 크기를 "많을수록 좋다"는 감으로 정했는가, 아니면 CPU 바운드/I/O 바운드 비율을 보고 정했는가?
- [ ] `volatile`로 스레드 간 동기화를 시도하는 코드가 있는가? (있다면 위험 신호)
- [ ] "느려졌는데 락 경쟁도 아니고 CPU도 안 바쁜" 멀티스레드 성능 저하라면, 거짓 공유([5장](05_메모리.md))를 의심해봤는가?

## 4.10 다른 OS에서는

| 개념 | Windows | Linux |
|---|---|---|
| 경량 동기화 | CRITICAL_SECTION | futex 기반 pthread_mutex |
| 스레드 생성 | `CreateThread` | `pthread_create` (내부적으로 `clone`) |
| 스케줄링 단위 | 스레드 | 리눅스 커널은 스레드도 "task"로 통일 관리 |
