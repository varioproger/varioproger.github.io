# 8장. 디버깅과 도구

아는 개념을 실제 눈으로 확인하고, 문제가 생겼을 때 "감"이 아니라 도구로 진단하는 법을 짧게 정리한다.

## 8.1 프로세스/스레드/메모리 들여다보기

| 목적 | Windows | Linux |
|---|---|---|
| 프로세스별 자원 사용 실시간 | Process Explorer, 작업 관리자 | `top`/`htop` |
| 핸들/열린 파일 누가 잡고 있나 | Process Explorer의 Handle Search (Ctrl+F) | `lsof`, `fuser` |
| 가상 메모리 구조 상세 | VMMap | `pmap -x <pid>`, `/proc/<pid>/maps` |
| 프로세스 트리, 스레드 목록 | Process Explorer, `pslist` | `ps -eLf`, `pstree` |
| 시스템 콜 추적 | Process Monitor (procmon) | `strace` |
| 시스템 전반 이벤트(스케줄링, I/O, 페이지폴트 등) | ETW (Event Tracing for Windows) + Windows Performance Recorder/Analyzer | `perf`, `ftrace` |
| 커널/유저 크래시 덤프 분석 | WinDbg | `gdb`, `coredumpctl` |
| 네트워크 소켓/연결 상태 | `netstat -ano`, TCPView | `ss`, `netstat` |

**핸들 누수 의심될 때**: Process Explorer로 해당 프로세스의 Handle Count가 시간이 지날수록 계속 늘어나는지 관찰 — [3장](03_프로세스.md)의 핸들 누수를 실제로 확인하는 방법이다.

**"메모리가 새는지" 의심될 때**: 작업 관리자의 "메모리(비공개 작업 집합)" 또는 VMMap의 Private Bytes를 시간에 따라 추적. Virtual Size가 아니라 Committed/Private 항목을 봐야 한다 ([5장](05_메모리.md)의 함정).

## 8.2 데드락/스레드 멈춤 진단

프로세스가 응답 없음(hang) 상태일 때:

- **Windows**: WinDbg로 프로세스에 붙어(`.attach`) `~*k` (모든 스레드 콜스택 덤프) → 여러 스레드가 각자 다른 락을 기다리며 서로를 블로킹하는 패턴이 보이면 데드락 확정. Process Explorer도 스레드별 스택을 보여준다.
- **Linux**: `gdb -p <pid>` 후 `thread apply all bt` — 마찬가지로 전체 스레드 콜스택을 한 번에 본다.

[4장](04_스레드와_동시성.md)에서 설명한 "락을 서로 다른 순서로 잡아서 생기는 데드락"은 이 방법으로 스택을 보면 바로 원인을 특정할 수 있다 — 이론(4장)과 실전 도구(이 절)가 바로 연결되는 지점이다.

## 8.3 CPU 프로파일링: 어디서 시간을 쓰는지

"느리다"는 느낌만으로 최적화하면 대개 틀린 곳을 고친다. 프로파일러로 **실제로 CPU 시간이 어디서 소비되는지** 측정해야 한다.

- Windows: Visual Studio Profiler, Windows Performance Analyzer (ETW 기반)
- Linux: `perf record` / `perf report`, `valgrind --tool=callgrind`

프로파일링 결과를 볼 때 [2장](02_OS_큰그림.md)에서 배운 구분을 적용하자: 시간이 유저 코드(연산)에 쓰이는지, 시스템 콜/커널(I/O, 컨텍스트 스위칭)에 쓰이는지를 나눠서 봐야 한다 — `perf`는 이걸 "user" / "kernel" 시간으로 구분해서 보여준다.

## 8.4 실전 진단 흐름 예시

**증상: "서버가 몇 시간 지나면 응답이 느려지고 결국 멈춘다"**

1. `top`/작업 관리자로 CPU/메모리 추이 확인 → 메모리가 계속 우상향? → [5장](05_메모리.md) 누수 의심, VMMap/힙 프로파일러로 누가 잡고 있는지 추적
2. CPU는 낮은데 응답만 느림 → 스와핑(디스크 I/O 급증) 또는 락 경쟁 의심 → `iostat`/리소스 모니터로 디스크 확인, 안 그러면 스레드 스택 덤프로 락 대기 확인
3. 특정 시점부터 갑자기 멈춤(hang) → 데드락 의심 → 전체 스레드 콜스택 덤프
4. 커넥션 수가 늘수록 느려짐 → [6장](06_네트워크.md)의 커넥션당 스레드 모델 한계 의심 → 스레드 수 vs 커넥션 수 비교

## 8.5 마지막 조언

도구는 "이론이 맞는지 확인하는 수단"이다. 이 책의 2~7장에서 각 메커니즘의 **왜**를 이해했다면, 도구가 보여주는 숫자(핸들 수, Working Set, 스레드 스택, syscall 목록)가 무엇을 의미하는지 스스로 해석할 수 있다. 반대로 메커니즘을 모르고 도구만 쓰면 "숫자가 이상하다"는 것만 알고 원인을 못 찾는다.
