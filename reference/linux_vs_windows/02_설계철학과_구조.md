# 2장. 설계 철학과 구조

## 2.1 커널 구조: 모놀리식과 하이브리드

**리눅스: 모놀리식 커널 + 동적 모듈**

리눅스 커널은 스케줄러, 메모리 관리자, 파일 시스템, 네트워크 스택, 디바이스 드라이버가 모두 하나의 커널 주소 공간에서 같은 특권 레벨(ring 0)로 실행된다. 드라이버나 파일 시스템은 커널 모듈(`.ko`)로 컴파일해 실행 중에 `insmod`/`modprobe`로 넣고 뺄 수 있지만, 로드된 뒤에는 커널 본체와 구분 없이 함수 호출로 직접 연결된다.

장점은 단순함과 속도다. 서브시스템 사이의 호출이 그냥 함수 호출이므로 메시지 전달 비용이 없다. 단점은 드라이버 하나의 버그가 커널 전체를 죽인다는 점인데, 리눅스는 이것을 "코드를 공개하고 리뷰로 잡는다"는 방식으로 대응한다.

**Windows: 하이브리드 커널 (NT 커널 + Executive)**

Windows NT는 설계 당시 마이크로커널을 지향했다. 커널 모드 안에서도 계층이 나뉜다.

- **HAL(Hardware Abstraction Layer)**: 하드웨어 차이를 감춘다.
- **NT 커널(ntoskrnl.exe의 아래층, "Kernel")**: 스레드 스케줄링, 인터럽트와 예외 디스패치, 저수준 동기화(스핀락, 디스패처 오브젝트). 매우 작다.
- **Executive(같은 파일의 위층)**: 오브젝트 관리자, 메모리 관리자, 프로세스 관리자, I/O 관리자, 보안 참조 모니터, 캐시 관리자 등. 각각이 `Ob`, `Mm`, `Ps`, `Io`, `Se`, `Cc` 접두사를 가진 독립 컴포넌트처럼 설계되어 있다.
- **드라이버**: I/O 관리자가 정의한 IRP(I/O Request Packet) 규약으로 통신한다. 드라이버는 계층을 쌓을 수 있다(필터 드라이버).
- **Win32k.sys**: 원래 사용자 모드였던 GUI 서브시스템을 성능 때문에 커널로 내린 것. "하이브리드"라고 부르는 이유 중 하나다.

결과적으로 Windows도 드라이버가 ring 0에서 돌지만, 컴포넌트 사이가 함수 포인터 테이블과 IRP라는 명시적 규약으로 분리되어 있다. 리눅스보다 구조가 형식적이고, 그만큼 문서화된 드라이버 모델(WDM, KMDF)이 있다.

**프로그래머에게 무슨 의미인가**

- 리눅스에서는 커널 내부를 `/proc`, `/sys`, `ftrace`, eBPF로 거의 무제한 관찰할 수 있다. Windows는 ETW(Event Tracing for Windows)와 커널 디버거로 관찰하지만, 내부 구조체는 심볼 파일(PDB)에 의존하고 공식 문서가 없는 것이 많다.
- 리눅스 커널 소스를 읽으면 "왜 이렇게 동작하는지"를 확정할 수 있다. Windows는 *Windows Internals*와 리버스 엔지니어링이 그 역할을 대신한다.

## 2.2 시스템 콜: 공개 ABI인가, 비공개 구현인가

**리눅스: 시스템 콜이 곧 공개 인터페이스**

리눅스 시스템 콜 번호는 아키텍처별로 고정되어 있고 절대 바뀌지 않는다. x86-64에서 `read`는 0번, `write`는 1번, `open`은 2번이다. 이 번호와 인자 규약은 커널의 공식 ABI이고, 리누스 토르발스가 가장 강하게 지키는 원칙이 "사용자 공간을 깨지 마라"다.

```c
// glibc 없이 직접 시스템 콜 (x86-64)
static long sys_write(int fd, const void *buf, unsigned long len) {
    long ret;
    __asm__ volatile ("syscall"
        : "=a"(ret)
        : "a"(1), "D"(fd), "S"(buf), "d"(len)
        : "rcx", "r11", "memory");
    return ret;
}
```

이것이 가능하기 때문에:

- Go 런타임은 libc를 거치지 않고 시스템 콜을 직접 호출한다(`CGO_ENABLED=0`으로 완전 정적 바이너리 생성).
- 정적 링크한 바이너리가 어떤 배포판의 어떤 커널에서든 돌아간다.
- 컨테이너는 호스트 커널을 그대로 쓰고 사용자 공간(libc, 배포판)만 바꿔 끼울 수 있다. Alpine(musl)과 Ubuntu(glibc)가 같은 커널 위에서 공존하는 이유다.

**Windows: 시스템 콜은 비공개, Win32 API가 계약**

Windows의 실제 시스템 콜(`NtCreateFile`, `NtReadFile` 같은 `Nt*`/`Zw*` 함수)은 번호가 빌드마다 바뀐다. Windows 10의 어느 업데이트에서 `NtCreateFile`이 0x55였다면 다음 업데이트에서 0x56이 될 수 있다. 마이크로소프트는 이 번호를 문서화하지 않고, 응용 프로그램이 직접 호출하는 것을 지원하지 않는다.

대신 계약은 사용자 모드 DLL 계층에 있다.

```
내 코드
  → kernel32.dll  (CreateFileW)         공개 API, 문서화됨, 영구 호환
    → kernelbase.dll
      → ntdll.dll (NtCreateFile)        시스템 콜 스텁, 번호는 여기서 해석
        → syscall 명령 → ntoskrnl.exe
```

`ntdll.dll`은 커널과 함께 배포되므로 항상 커널과 번호가 맞는다. 응용 프로그램은 `kernel32.dll` 이상만 보면 된다.

이것이 의미하는 것:

- Windows에서 "완전 정적 링크"는 개념적으로 불가능하다. 최소한 `ntdll.dll`과 `kernel32.dll`은 동적으로 로드해야 한다. Go도 Windows에서는 `syscall.NewLazyDLL("kernel32.dll")`로 DLL을 로드한다.
- Windows 컨테이너는 호스트와 커널 빌드가 맞아야 한다(프로세스 격리 모드). 이 제약이 없는 Hyper-V 격리 모드는 사실상 경량 VM이다.
- 대신 Win32 API는 30년 가까이 하위 호환이 유지된다. 1995년의 `CreateFileA`가 2025년에도 그대로 동작한다.

## 2.3 자원 추상화: "모든 것은 파일" vs "모든 것은 오브젝트"

이 절이 이 책에서 가장 중요하다. 이후 모든 장의 차이가 여기서 파생된다.

**리눅스: 파일 디스크립터**

파일 디스크립터(fd)는 프로세스별 테이블의 인덱스인 작은 정수다. 0, 1, 2는 stdin, stdout, stderr로 예약되고, 새로 여는 것은 사용 가능한 가장 낮은 번호를 받는다.

핵심은 fd가 가리키는 것이 무엇이든 **같은 시스템 콜이 통한다**는 점이다.

| fd가 가리키는 것 | 만드는 방법 | read/write | poll/epoll | close |
|---|---|---|---|---|
| 일반 파일 | `open` | O | O (항상 ready) | O |
| 소켓 | `socket`, `accept` | O | O | O |
| 파이프 | `pipe` | O | O | O |
| 터미널, 디바이스 | `open("/dev/...")` | O | O | O |
| 타이머 | `timerfd_create` | O (만료 횟수) | O | O |
| 시그널 | `signalfd` | O (siginfo) | O | O |
| 이벤트 카운터 | `eventfd` | O | O | O |
| 프로세스 | `pidfd_open` | X | O (종료 시) | O |
| epoll 인스턴스 자체 | `epoll_create` | X | O | O |

이 통일성 때문에 리눅스 이벤트 루프는 `epoll` 하나로 소켓, 타이머, 시그널, 자식 프로세스 종료를 모두 기다린다. 커널이 새 종류의 자원을 추가할 때도 "fd로 만들면 기존 도구가 다 통한다"는 원칙을 따른다.

내부 구조는 3단계다.

```
프로세스의 fd 테이블  →  시스템 전체의 open file table  →  inode (또는 socket 구조체)
  (fd 정수)              (파일 오프셋, 플래그, 참조 카운트)      (실제 대상)
```

`fork`하면 fd 테이블이 복사되어 부모와 자식이 **같은 open file 엔트리**를 가리킨다. 그래서 오프셋을 공유한다. `dup`도 같은 엔트리를 가리키는 새 fd를 만든다. 이것이 셸 리디렉션(`2>&1`)의 원리다.

**Windows: 커널 오브젝트와 핸들**

Windows 커널의 **오브젝트 관리자**(Object Manager, `Ob*`)는 프로세스, 스레드, 파일, 이벤트, 뮤텍스, 세마포어, 섹션(파일 매핑), 타이머, 잡, 토큰, 키(레지스트리) 등을 모두 "오브젝트"라는 공통 헤더를 가진 구조체로 관리한다. 오브젝트마다 타입 오브젝트가 있고, 타입이 열기/닫기/삭제/보안 검사 같은 공통 동작을 정의한다.

핸들(`HANDLE`)은 프로세스별 핸들 테이블의 인덱스다. fd처럼 프로세스 안에서만 의미가 있고, 값 자체는 4의 배수인 불투명한 정수다. 핸들 테이블 엔트리에는 오브젝트 포인터와 함께 **접근 마스크**(이 핸들로 무엇을 할 수 있는가)와 상속 여부 같은 속성이 저장된다.

fd와 결정적으로 다른 점은 다음 세 가지다.

1. **오브젝트마다 API가 다르다.** 파일은 `ReadFile`/`WriteFile`, 이벤트는 `SetEvent`/`ResetEvent`, 뮤텍스는 `ReleaseMutex`, 프로세스는 `TerminateProcess`. 소켓(`SOCKET`)은 커널 파일 오브젝트를 감싸지만 Winsock이라는 별도 API를 통해야 한다. `ReadFile`은 통하지만 권장하지 않는다.
2. **모든 오브젝트가 "시그널 상태"를 가진다.** 이벤트는 `SetEvent`되면, 뮤텍스는 소유자가 없으면, 프로세스와 스레드는 종료되면, 타이머는 만료되면, 파일과 소켓은 I/O가 완료되면 시그널된다. 그래서 `WaitForSingleObject`/`WaitForMultipleObjects`가 종류를 가리지 않고 통한다.
3. **오브젝트에 이름과 보안 기술자가 있다.** `CreateMutexW(NULL, FALSE, L"Global\\MyApp")`처럼 이름을 붙이면 다른 프로세스가 같은 이름으로 열 수 있다. 각 오브젝트에는 ACL이 붙어서 "누가 이 뮤텍스를 열 수 있는가"를 커널이 검사한다. 오브젝트 네임스페이스(`\Device\`, `\BaseNamedObjects\`, `\Sessions\`)는 파일 시스템과 별개의 커널 내부 트리다.

```c
// Windows: 종류가 다른 오브젝트를 한 번에 기다린다
HANDLE h[3];
h[0] = hProcess;   // 자식 프로세스 종료
h[1] = hEvent;     // 다른 스레드의 신호
h[2] = hTimer;     // 대기 가능 타이머
DWORD r = WaitForMultipleObjects(3, h, FALSE, INFINITE);
switch (r - WAIT_OBJECT_0) { case 0: ...; case 1: ...; case 2: ...; }
```

```c
// 리눅스: 같은 일을 하려면 전부 fd로 바꿔서 epoll에 넣는다
int ep = epoll_create1(0);
int pfd = pidfd_open(child_pid, 0);            // 프로세스 → fd
int efd = eventfd(0, EFD_NONBLOCK);            // 신호 → fd
int tfd = timerfd_create(CLOCK_MONOTONIC, 0);  // 타이머 → fd
// epoll_ctl(ep, EPOLL_CTL_ADD, ...) 각각 등록 후 epoll_wait
```

두 코드는 같은 결과를 내지만 방향이 반대다. Windows는 "모든 오브젝트가 대기 가능하다"는 성질을 공통 헤더에 넣었고, 리눅스는 "대기 가능한 것은 fd다"라고 정하고 모든 것을 fd로 노출한다.

**비교표**

| 항목 | fd (리눅스) | HANDLE (Windows) |
|---|---|---|
| 값 | 0부터 시작하는 작은 정수, 가장 낮은 번호 재사용 | 4의 배수 불투명 값, 재사용 순서 비공개 |
| 유효 범위 | 프로세스 내부 | 프로세스 내부 |
| 상속 | `fork` 시 전부 복사 (`O_CLOEXEC`로 exec 시 닫기) | `CreateProcess`의 `bInheritHandles`와 핸들별 상속 플래그 |
| 다른 프로세스로 전달 | UNIX 도메인 소켓의 `SCM_RIGHTS` | `DuplicateHandle(hSrcProcess, ..., hDstProcess, ...)` |
| 권한 | 열 때의 `O_RDONLY` 등 플래그와 파일 모드 비트 | 핸들별 접근 마스크 + 오브젝트의 DACL |
| 이름 | 파일 시스템 경로(파일만), 추상 소켓 이름 등 | 오브젝트 네임스페이스의 이름(모든 종류 가능) |
| 공통 연산 | read, write, close, poll, fcntl | CloseHandle, WaitForSingleObject, DuplicateHandle |
| 누수 시 | 프로세스별 `ulimit -n` 한계(기본 1024) 도달, `EMFILE` | 프로세스당 약 1600만 개 한계, 그 전에 커널 메모리 압박 |

## 2.4 파일 시스템과 경로

이 주제는 7장에서 깊게 다루지만, 철학 차이의 사례로 여기서 짧게 짚는다.

| 항목 | 리눅스 | Windows |
|---|---|---|
| 루트 | `/` 하나. 다른 디스크는 `mount`로 트리 어딘가에 붙인다 | 드라이브 문자 `C:\`, `D:\`. 실제로는 `\Device\HarddiskVolume1`의 심볼릭 링크 |
| 구분자 | `/` | `\` (대부분의 API는 `/`도 받지만 UNC 경로, `\\?\` 접두사에서는 `\`만) |
| 대소문자 | 구분함 (ext4, xfs). `a.txt`와 `A.txt`는 다른 파일 | 구분 안 함 (NTFS는 저장은 하되 비교는 무시). 디렉터리 단위로 켤 수는 있음 |
| 최대 경로 | 컴포넌트 255바이트, 전체 4096바이트 | 전통적으로 260자(`MAX_PATH`). `\\?\` 접두사 또는 매니페스트 설정으로 32767자 |
| 금지 문자 | `/`와 NUL만 | `< > : " / \ | ? *`와 제어 문자, 예약 이름(`CON`, `NUL`, `COM1` 등) |
| 열린 파일 삭제 | 가능. 디렉터리 엔트리만 사라지고 inode는 마지막 fd가 닫힐 때 해제 | 기본 불가. 열 때 `FILE_SHARE_DELETE`를 지정해야 다른 프로세스가 지울 수 있음 |
| 실행 권한 | 파일 모드의 `x` 비트 | 확장자(`.exe`, `.bat`)와 ACL의 Execute 권한 |
| 숨김 파일 | 이름이 `.`으로 시작 | 파일 속성 비트 `FILE_ATTRIBUTE_HIDDEN` |

"열린 파일 삭제" 차이는 로그 로테이션, 자기 업데이트 프로그램, 임시 파일 정리에서 매번 문제가 된다. 리눅스는 파일 이름과 파일 내용(inode)이 분리되어 있어 이름을 지우는 것과 내용을 해제하는 것이 별개 사건이다. Windows는 파일 오브젝트를 열 때 "다른 사람이 이 파일에 무엇을 할 수 있는가"를 공유 모드로 명시하는 모델이라, 지정하지 않으면 삭제가 거부된다.

## 2.5 문자열, 인코딩, 줄바꿈

**리눅스**: 커널은 경로와 문자열을 바이트 배열로만 본다. 인코딩을 해석하지 않는다. 사용자 공간 관례가 UTF-8이고, 파일 이름은 NUL과 `/`만 아니면 어떤 바이트든 허용된다. 줄바꿈은 `\n`.

**Windows**: 커널과 NTFS는 UTF-16(정확히는 초기에는 UCS-2)으로 문자열을 저장한다. Win32 API는 거의 모든 함수가 두 버전으로 존재한다.

```c
CreateFileA(const char*  path, ...);   // "ANSI": 현재 코드 페이지로 해석 → 내부에서 UTF-16으로 변환
CreateFileW(const wchar_t* path, ...); // Wide: UTF-16 그대로 전달
```

`A` 버전은 시스템 로캘의 코드 페이지(한국어 Windows는 CP949)로 해석하기 때문에, 코드 페이지에 없는 문자가 들어간 파일 이름은 `A` 함수로는 열 수 없다. Windows 10 1903부터 애플리케이션 매니페스트로 프로세스의 ANSI 코드 페이지를 UTF-8로 설정할 수 있지만, 기본은 아니다. 크로스 플랫폼 코드에서 "Windows에서만 한글 파일명이 깨진다"는 버그의 대부분이 여기서 온다.

줄바꿈은 `\r\n`이다. C 표준 라이브러리는 텍스트 모드(`fopen(..., "r")`)에서 `\r\n`을 `\n`으로 자동 변환하지만, 바이너리 모드나 직접 `ReadFile`을 쓰면 변환하지 않는다. 리눅스에서는 텍스트 모드와 바이너리 모드가 동일하다.

## 2.6 에러 보고

| 항목 | 리눅스 | Windows |
|---|---|---|
| 방식 | 반환값 `-1`(또는 `NULL`) + 스레드 지역 `errno` | 반환값 `FALSE`/`INVALID_HANDLE_VALUE`/`NULL` + 스레드 지역 `GetLastError()` |
| 코드 | `EACCES`, `ENOENT`, `EAGAIN` 등 약 130개 | `ERROR_ACCESS_DENIED`(5), `ERROR_FILE_NOT_FOUND`(2) 등 수천 개 |
| 소켓 | 같은 `errno` | 별도 `WSAGetLastError()`, `WSAEWOULDBLOCK` 등 |
| 문자열 변환 | `strerror`, `perror` | `FormatMessage` |
| 성공 시 | `errno`를 0으로 초기화하지 않음 (실패 시에만 설정) | 대부분 `SetLastError(0)`을 안 함. 성공 후 값은 신뢰 불가 |
| NTAPI | 해당 없음 | `NTSTATUS` (0xC0000034 같은 32비트 상태 코드). `RtlNtStatusToDosError`로 Win32 코드로 변환 |

두 OS 모두 에러는 **호출 직후에** 읽어야 한다. 그 사이에 다른 API를 부르면 덮어쓰인다. 특히 Windows는 `CloseHandle`이나 로그 출력 함수도 마지막 에러를 바꿀 수 있다.

## 2.7 설정과 상태의 저장소

**리눅스**: 시스템 설정은 `/etc` 아래 텍스트 파일, 사용자 설정은 홈 디렉터리의 dotfile이나 `~/.config`(XDG 규약), 런타임 상태는 `/run`과 `/var`. 커널 파라미터는 `/proc/sys`(sysctl). 모두 파일이므로 `cat`, `grep`, 버전 관리로 다룰 수 있다.

**Windows**: 시스템과 애플리케이션 설정의 중심은 **레지스트리**다. 계층형 키-값 데이터베이스이고 `HKEY_LOCAL_MACHINE`(시스템 전체), `HKEY_CURRENT_USER`(사용자별), `HKEY_CLASSES_ROOT`(파일 연결, COM 등록)으로 나뉜다. 레지스트리 키도 커널 오브젝트라서 핸들로 열고 ACL로 보호된다. 사용자 파일 설정은 `%APPDATA%`, `%LOCALAPPDATA%`, `%PROGRAMDATA%`.

프로그래머에게 실질적 차이는 다음과 같다.

- 리눅스에서 "이 프로그램이 설정을 어디서 읽나"는 `strace -e openat`로 바로 보인다. Windows는 Process Monitor로 파일과 레지스트리 접근을 함께 봐야 한다.
- Windows에서 서비스 등록, 파일 연결, COM 컴포넌트 등록, 자동 실행은 모두 레지스트리 쓰기다. 설치 프로그램이 필요한 이유의 절반이 이것이다.
- 32비트 프로세스가 64비트 Windows에서 레지스트리를 읽으면 `Wow6432Node`로 리디렉션된다. 파일 시스템도 `System32`가 `SysWOW64`로 리디렉션된다. 이 리디렉션을 모르면 "분명 키가 있는데 안 읽힌다"는 문제를 만난다.

## 2.8 이식할 때 부딪히는 문제

1. **fd를 정수로 가정한 코드**: 소켓을 `int`에 담고, `close()`로 닫고, `fcntl`로 논블로킹을 거는 코드는 Windows에서 `SOCKET`(포인터 크기), `closesocket()`, `ioctlsocket()`로 바꿔야 한다. 크로스 플랫폼 라이브러리는 대부분 자기 타입(`uv_os_sock_t`, `SOCKET` 매크로)을 정의한다.
2. **경로 결합과 비교**: `path + "/" + name`은 대체로 동작하지만, 대소문자 구분과 예약 이름은 그렇지 않다. `strcmp`로 경로를 비교하는 코드는 Windows에서 거짓 불일치를 낸다.
3. **문자열 API 선택**: Windows에서 `char*` 기반 API를 그대로 쓰면 비ASCII 경로에서 깨진다. `W` 함수를 쓰고 UTF-8 ↔ UTF-16 변환을 경계에서 한 번만 하는 것이 정석이다.
4. **`errno`만 보는 에러 처리**: Windows CRT는 `errno`를 흉내 내지만 값이 부분적이다. 소켓 에러는 `errno`에 안 들어간다.
5. **"설정 파일은 항상 파일"이라는 가정**: Windows 배포에서는 레지스트리에 저장된 값을 읽어야 하는 경우가 있다(프록시 설정, 인증서 저장소, 시간대).

## 2.9 런타임에서는

- **Go**: `os.File`이 리눅스에서는 fd, Windows에서는 HANDLE을 감싼다. `syscall` 패키지가 OS별로 완전히 다르고, `internal/poll`이 epoll과 IOCP를 각각 구현한다. 경로는 `filepath` 패키지가 구분자와 대소문자를 처리한다.
- **Rust**: `std::os::unix::io::AsRawFd`와 `std::os::windows::io::AsRawHandle`이 별개 트레이트다. `OsString`이 "OS 네이티브 문자열은 UTF-8이 아닐 수 있다"를 타입으로 강제한다. Windows에서는 WTF-8로 내부 표현한다.
- **.NET**: `SafeHandle`이 HANDLE과 fd를 모두 감싼다. `Path.DirectorySeparatorChar`가 OS별로 다르고, `StringComparison.OrdinalIgnoreCase`를 파일 시스템 비교에 쓰는 관례가 Windows 기원이다.
- **Node.js (libuv)**: `uv_handle_t`가 두 OS의 자원을 하나로 추상화한다. `fs.watch`가 리눅스(inotify)와 Windows(`ReadDirectoryChangesW`)에서 다른 이벤트를 내는 것이 대표적인 누출이다.
- **Python**: `os.open`은 두 OS 모두 정수를 반환하지만, Windows에서는 CRT가 HANDLE을 정수 fd로 매핑한 것이다. `msvcrt.get_osfhandle`로 진짜 HANDLE을 꺼낼 수 있다. `select.select`는 Windows에서 소켓에만 통하고 파일에는 안 통한다.
