# 10장. 마무리

## 10.1 네 개의 갈림길로 돌아가서

1장에서 이 책 전체를 관통하는 차이를 네 가지로 예고했다. 각 장을 지나온 지금 그것들이 어떻게 드러났는지 정리한다.

**갈림길 1: 자원을 무엇으로 추상화하는가.** "모든 것은 파일"과 "모든 것은 오브젝트"는 2장에서 fd와 HANDLE의 차이로 시작해, 5장에서 `epoll`과 `WaitForMultipleObjects`의 대기 모델 차이로, 6장에서 소켓이 fd인지 별도 타입인지로, 7장에서 `/proc`과 오브젝트 네임스페이스로 반복해서 나타났다. 리눅스는 새 자원을 만들면 fd로 노출해 기존 도구가 통하게 하고, Windows는 새 자원을 오브젝트로 만들어 대기 가능하게 한다.

**갈림길 2: 비동기 알림을 어떻게 전달하는가.** readiness와 completion은 6장의 핵심이었고, 9장에서 크로스 플랫폼 런타임들이 어느 쪽을 기준으로 삼았는지로 이어졌다. `io_uring`이 이 갈림길을 좁히고 있다.

**갈림길 3: 프로세스를 어떻게 만들고 제어하는가.** `fork`의 존재와 부재는 4장에서 프로세스 생성뿐 아니라 3장의 오버커밋 정책(fork를 살리기 위한), 5장의 멀티스레드 fork 문제, 9장의 워커 모델 재설계까지 영향을 미쳤다. 시그널의 부재는 4장의 종료 프로토콜, 5장의 `EINTR` 없는 세계, 7장의 `SIGPIPE` 없는 소켓 쓰기로 나타났다.

**갈림길 4: 안정된 경계가 어디인가.** 시스템 콜 ABI가 공개인지는 2장에서 정적 링크와 컨테이너의 차이로, 8장에서 glibc 버전 문제와 VC++ 재배포 문제라는 서로 다른 형태의 호환성 고통으로 나타났다.

## 10.3 반복해서 나타난 원리

표를 외우는 것보다 중요한 것은 표 뒤의 원리다. 이 책에서 반복된 것은 다음 네 가지다.

**원리 1: 명시성 vs 암묵성.** Windows는 대체로 명시적이다. 커밋을 명시하고, 공유 모드를 명시하고, 자식에게 넘길 것을 명시하고, 내보낼 심볼을 명시하고, 스레드 풀과 서비스 프로토콜을 OS가 정의한다. 리눅스는 대체로 암묵적이다. 접근하면 커밋되고, 열려 있어도 지울 수 있고, fork하면 다 상속되고, 심볼은 다 보이고, 데몬은 그냥 포그라운드 프로그램이다. 명시성은 예측 가능성과 안전성을 주고, 암묵성은 단순함과 조합 가능성을 준다. 어느 쪽이 옳은 것이 아니고, 이식할 때는 **암묵적으로 얻던 것을 명시적으로 요청하거나, 명시적으로 요청하던 것이 이미 되어 있음을 확인하는** 작업을 하게 된다.

**원리 2: 통일의 축이 다르다.** 리눅스는 인터페이스(fd, read/write/poll)를 통일하고 그 뒤에 무엇이 있든 상관하지 않는다. Windows는 오브젝트의 공통 성질(시그널 상태, 보안 기술자, 이름)을 통일하고 인터페이스는 오브젝트마다 둔다. 그래서 리눅스는 "새 자원을 fd로 만들면 모든 도구가 통한다"는 확장성을 갖고, Windows는 "모든 오브젝트를 한 함수로 기다리고 한 모델로 보호한다"는 일관성을 갖는다.

**원리 3: 시간의 흐름이 두 OS를 가깝게 만든다.** `io_uring`은 completion을 리눅스에 들여왔고, `WaitOnAddress`는 futex를 Windows에 들여왔다. `pidfd`는 프로세스를 fd로 만들어 Windows의 프로세스 핸들 대기와 같은 일을 하고, Windows의 `AF_UNIX`와 POSIX 삭제 의미는 리눅스 동작을 Windows에 가져왔다. 컨테이너와 잡 오브젝트, cgroup과 사일로도 서로를 닮아 간다. 두 OS는 서로의 좋은 점을 꾸준히 흡수해 왔다. 오늘의 차이표는 10년 뒤에는 더 짧아질 것이다.

**원리 4: 런타임이 대부분을 감추지만, 새는 곳은 항상 같은 곳이다.** fork, 시그널, 열린 파일 삭제, 커맨드라인 이스케이프, 경로 대소문자, 파일 감시, 스택 크기. 9장의 표는 어떤 언어를 쓰든 결국 같은 목록이다. 새 프로젝트를 시작할 때 이 목록을 미리 점검하는 것이 이 책을 읽은 실질적 결과여야 한다.

## 10.4 다음에 읽을 것

이 책은 두 OS를 가로로 비교했다. 각 OS를 세로로 깊이 파려면 다음 순서를 권한다.

**리눅스**
1. Brian Ward, *How Linux Works* (3rd, 2021): 시스템 전체 동작. 부팅, systemd, 디바이스, 네트워크 설정까지. 프로그래머가 시스템 관리자 관점을 얻는 데 좋다.
2. Michael Kerrisk, *The Linux Programming Interface* (2010): API 레벨 정본. 1500쪽이지만 목차를 레퍼런스로 두고 필요한 장만 읽어도 된다. `io_uring`, `pidfd`, cgroup v2 같은 2010년 이후 기능은 없으므로 `man 7` 페이지와 LWN.net 기사로 보충한다.
3. Brendan Gregg, *Systems Performance* (2nd, 2020): 관측과 튜닝. eBPF 도구 사용법은 같은 저자의 *BPF Performance Tools*.
4. Robert Love, *Linux Kernel Development* (3rd, 2010) 또는 커널 소스 자체: 스케줄러, 메모리 관리자 내부.

**Windows**
1. Jeffrey Richter, *Windows via C/C++* (5th, 2007): Win32 API 관점의 프로세스, 스레드, 메모리, I/O, DLL, SEH. 오래됐지만 Win32 핵심은 그대로다. Vista 이후 기능(SRWLock, 조건 변수, 스레드 풀 API)까지 포함되어 있다.
2. Pavel Yosifovich 외, *Windows Internals Part 1* (7th, 2017), *Part 2* (7th, 2021): NT 커널 내부. 프로세스/스레드/메모리/보안/I/O가 Part 1, 파일 시스템/캐시/부팅/진단이 Part 2. Sysinternals 도구로 직접 관찰하는 실험이 각 장에 있다.
3. Mario Hewardt, Daniel Pravat, *Advanced Windows Debugging* (2007): WinDbg로 힙 손상, 핸들 누수, 데드락을 추적하는 방법.
4. Anthony Jones, Jim Ohlund, *Network Programming for Microsoft Windows* (2nd, 2002): Winsock2와 IOCP의 정본. 오래됐지만 IOCP 설계는 그대로다.

**두 OS 공통**
- Randal Bryant, David O'Hallaron, *Computer Systems: A Programmer's Perspective* (3rd): OS 아래 하드웨어와 컴파일러까지 프로그래머 관점으로.
- Remzi & Andrea Arpaci-Dusseau, *Operating Systems: Three Easy Pieces*: 무료. 가상화, 동시성, 지속성이라는 세 축으로 OS 원리를 설명. 이 책의 "OS가 풀어야 하는 문제" 절들이 이 책의 관점을 따랐다.
- Andrew Baumann 외, "A fork() in the road" (HotOS 2019): 짧은 논문. fork의 역사와 문제, spawn 모델 옹호.

## 10.5 마지막으로

한쪽 OS에서 오래 일한 개발자가 다른 쪽을 처음 만나면 "왜 이렇게 이상하게 만들었나"라고 느낀다. 이 책을 끝까지 읽었다면 그 느낌이 "다른 목표를 위한 다른 선택"으로 바뀌었기를 바란다.

Windows에 fork가 없는 것은 결함이 아니라 DLL 초기화 모델과 오브젝트 기반 보안을 지키기 위한 선택이었다. 리눅스에 공유 모드가 없는 것은 결함이 아니라 이름과 내용을 분리해 재부팅 없는 업데이트를 가능하게 한 선택이었다. IOCP와 epoll은 각각 "커널이 읽어 준다"와 "준비되면 알려 준다"라는 정합적인 세계관이고, 두 세계관 모두 수십 년 동안 세계 최대 규모의 서버를 굴려 왔다.

두 세계관을 모두 이해하는 개발자는 어느 한쪽의 "당연함"에 갇히지 않는다. 그 개발자는 리눅스에서 코드를 짤 때도 "이 fd를 누가 닫는가"를 명시적으로 생각하고, Windows에서 코드를 짤 때도 "이 핸들을 fd처럼 통일된 루프에 넣을 수 없을까"를 생각한다. 비교해서 배우는 이유는 결국 그것이다. 두 개를 알면 하나를 더 잘 알게 된다.
