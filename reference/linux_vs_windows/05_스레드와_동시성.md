# 5장. 스레드와 동시성

## 5.1 OS가 풀어야 하는 문제

스레드는 "같은 주소 공간 안에서 독립적으로 스케줄되는 실행 흐름"이다. OS는 다음을 제공해야 한다.

1. **생성과 종료**: 스택과 레지스터 컨텍스트를 갖는 실행 단위를 만들고 없앤다.
2. **스케줄링**: 코어보다 많은 스레드를 시분할한다. 우선순위와 공정성을 조율한다.
3. **동기화 프리미티브**: 뮤텍스, 조건 변수, 세마포어, 이벤트 같은 "기다리고 깨우는" 수단. 경합이 없을 때는 커널을 거치지 않아야 빠르다.
4. **대기의 통합**: 여러 조건 중 하나가 만족될 때까지 기다리는 방법.
5. **스레드 지역 저장소(TLS)**: 스레드마다 다른 값을 갖는 전역 변수.

하드웨어 수준(원자적 명령, 메모리 배리어, 캐시 일관성)은 같은 CPU라 동일하다. 차이는 커널이 스레드를 어떤 개체로 보는가, 그리고 동기화 프리미티브를 어떤 형태로 노출하는가에 있다.

## 5.2 커널의 관점: 스레드는 무엇인가

**리눅스: 스레드 = 주소 공간을 공유하는 태스크**

리눅스 커널에는 "스레드"라는 별도 개체가 없다. 스케줄링 단위는 `task_struct`이고, 프로세스도 스레드도 모두 태스크다. `clone()` 시스템 콜에 어떤 자원을 공유할지 플래그로 지정한다.

```c
// fork(): 아무것도 공유하지 않는 clone
clone(SIGCHLD, ...);

// pthread_create(): 거의 모든 것을 공유하는 clone
clone(CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD
      | CLONE_SYSVSEM | CLONE_SETTLS | CLONE_PARENT_SETTID | CLONE_CHILD_CLEARTID, ...);
```

`CLONE_VM`은 주소 공간 공유, `CLONE_FILES`는 fd 테이블 공유, `CLONE_THREAD`는 "같은 스레드 그룹(TGID)에 속한다"다. 우리가 "프로세스 ID"라고 부르는 것은 TGID이고, 각 스레드는 고유한 TID(커널 관점의 PID)를 가진다. `getpid()`는 TGID를, `gettid()`는 TID를 반환한다.

이 설계의 결과:

- `/proc/<pid>/task/<tid>/`에 스레드가 각각 보인다. `ps -L`, `top -H`로 스레드별 CPU 사용량을 볼 수 있다.
- 스레드별로 나이스 값과 스케줄링 정책을 다르게 설정할 수 있다(`sched_setscheduler(tid, ...)`).
- 스레드도 시그널의 대상이 될 수 있다(`tgkill`). 프로세스로 보낸 시그널은 마스크가 열린 임의의 스레드 하나가 받는다.
- 이론적으로 주소 공간만 공유하고 fd 테이블은 분리한 "반쯤 스레드"도 만들 수 있다. 실제로는 컨테이너 런타임이 네임스페이스 진입에 이 유연성을 쓴다.

**Windows: 프로세스와 스레드는 별개 오브젝트**

NT 커널은 처음부터 프로세스(`EPROCESS`)와 스레드(`ETHREAD`/`KTHREAD`)를 별개의 커널 오브젝트로 설계했다. 프로세스는 주소 공간, 핸들 테이블, 토큰을 담는 컨테이너이고 스스로는 실행되지 않는다. 스레드가 유일한 스케줄링 단위다.

- 스레드는 자기 핸들이 있고, 대기 가능하고(종료 시 시그널), 보안 기술자가 있고, 다른 프로세스가 열 수 있다(`OpenThread`).
- 스레드는 자기 프로세스와 다른 **토큰**을 가질 수 있다(가장, 4.7절). 리눅스에서 스레드별 uid는 원칙적으로 불가능하다(glibc가 `setuid`를 모든 스레드에 전파한다).
- 프로세스 생성(`CreateProcess`)은 첫 스레드를 `CREATE_SUSPENDED` 상태로 만들 수 있고, 다른 프로세스에 스레드를 주입할 수 있다(`CreateRemoteThread`). 디버거, 안티치트, DLL 인젝션이 이것을 쓴다. 리눅스에서 비슷한 일은 `ptrace`로 훨씬 우회적으로 한다.
- 스레드 ID(TID)는 시스템 전체에서 고유하고 PID와 같은 번호 공간을 쓴다(둘 다 4의 배수). 리눅스 TID도 PID 공간을 쓰지만 이유는 다르다(태스크가 곧 PID 소유자).

**파이버(Fiber) / 사용자 모드 스케줄링**: Windows는 커널이 모르는 협력적 실행 단위인 파이버(`CreateFiber`, `SwitchToFiber`)를 API로 제공한다. 리눅스에는 `makecontext`/`swapcontext`(POSIX, 사실상 폐기)와 `ucontext`가 있지만 표준 API로 밀지 않고, 코루틴은 언어 런타임이 각자 구현한다. Windows 7~8의 UMS(User-Mode Scheduling)는 커널이 협력하는 사용자 스케줄링이었으나 거의 쓰이지 않았다.

## 5.3 생성과 종료 API

| 항목 | pthreads (리눅스) | Win32 |
|---|---|---|
| 생성 | `pthread_create(&t, &attr, fn, arg)` | `CreateThread(sa, stackSize, fn, arg, flags, &tid)` 또는 CRT의 `_beginthreadex` |
| 함수 시그니처 | `void *fn(void *)` | `DWORD WINAPI fn(LPVOID)` |
| 반환값 | `void *`, `pthread_join`으로 회수 | `DWORD` 종료 코드, `GetExitCodeThread`로 회수 |
| 대기 | `pthread_join(t, &ret)` (딱 한 번, 한 스레드만) | `WaitForSingleObject(h, INFINITE)` (여러 번, 여러 대기자 가능) |
| 분리 | `pthread_detach` 또는 `PTHREAD_CREATE_DETACHED` | `CloseHandle(h)` (오브젝트는 스레드가 끝나면 사라짐) |
| 자원 누수 조건 | join도 detach도 안 함 | 핸들을 안 닫음 |
| 자기 종료 | `pthread_exit(ret)` 또는 fn 반환 | `ExitThread(code)` 또는 fn 반환. C++에서는 `ExitThread`가 소멸자를 부르지 않으므로 반환 권장 |
| 강제 종료 | `pthread_cancel` (취소 지점에서만, 정리 핸들러 실행) | `TerminateThread` (즉사, 스택 해제 안 됨, 락 소유 그대로. 절대 쓰지 말 것) |
| 스택 크기 | `pthread_attr_setstacksize`, 기본 `RLIMIT_STACK`(8MB) | `dwStackSize`, 기본 링커 설정(1MB) |
| 시작 지연 | 없음 (필요하면 직접 동기화) | `CREATE_SUSPENDED` 후 `ResumeThread` |
| 이름 | `pthread_setname_np` (15자 제한) | `SetThreadDescription` (Win10 1607+), 이전엔 디버거 예외 트릭 |
| 자기 ID | `pthread_self()` (불투명), `gettid()` | `GetCurrentThread()` (의사 핸들), `GetCurrentThreadId()` |

**`_beginthreadex` vs `CreateThread`**: Windows에서 C 런타임을 쓰는 스레드는 `_beginthreadex`로 만들어야 한다. CRT가 스레드별 `errno`, `strtok` 상태, 로캘 정보를 초기화하고, 스레드 종료 시 해제하기 때문이다. `CreateThread`로 만든 스레드에서 CRT 함수를 쓰면 (현대 CRT는 지연 초기화로 대체로 동작하지만) 원칙적으로 누수가 난다. pthreads에는 이 구분이 없다. glibc가 곧 스레드 라이브러리이기 때문이다.

**`pthread_cancel` vs `TerminateThread`**: 둘 다 "밖에서 스레드를 죽이는" API지만 의미가 다르다. `pthread_cancel`은 취소 지점(대부분의 블로킹 시스템 콜)에 도달했을 때 취소 예외처럼 스택을 풀며 `pthread_cleanup_push`로 등록한 핸들러를 실행한다. C++에서는 glibc가 `abi::__forced_unwind` 예외로 구현해 소멸자도 실행된다. `TerminateThread`는 스레드를 그 자리에서 멈춘다. 스택이 해제되지 않고, 잡고 있던 CRITICAL_SECTION은 영원히 잠긴 채 남고, DLL이 스레드 분리 알림을 받지 못한다. 마이크로소프트 문서 자체가 "최후의 수단으로만"이라고 쓴다. 두 OS 모두 정석은 **플래그나 이벤트로 종료를 요청하고 스레드가 스스로 빠져나오게 하는 것**이다.

## 5.4 동기화 프리미티브

**리눅스: futex 위에 쌓은 pthreads**

리눅스 동기화의 기반은 `futex`(fast userspace mutex) 시스템 콜 하나다. futex는 "이 사용자 공간 주소의 값이 X이면 잠들어라"(`FUTEX_WAIT`)와 "이 주소에서 자는 스레드 N개를 깨워라"(`FUTEX_WAKE`)만 한다. 뮤텍스, 조건 변수, 세마포어, 읽기-쓰기 락, 배리어가 모두 사용자 공간의 원자적 연산 + futex로 만들어진다.

```c
// pthread_mutex_lock의 골격 (단순화)
if (atomic_cmpxchg(&m->lock, 0, 1) == 0)
    return;                                    // 경합 없음: 커널 안 감
while (atomic_xchg(&m->lock, 2) != 0)          // 2 = "대기자 있음"
    futex(&m->lock, FUTEX_WAIT, 2, ...);       // 경합: 커널에서 잠듦
```

경합이 없으면 시스템 콜이 없다. 이것이 "fast"의 의미다. 커널은 futex 주소를 키로 해시 테이블에 대기 큐를 관리하고, 뮤텍스 오브젝트 자체를 알지 못한다. 그래서 pthread 뮤텍스는 그냥 사용자 메모리의 구조체이고, `pthread_mutex_t`를 공유 메모리에 놓으면 프로세스 간에도 쓸 수 있다(`PTHREAD_PROCESS_SHARED`).

pthreads 프리미티브:

| 프리미티브 | 타입 | 특징 |
|---|---|---|
| 뮤텍스 | `pthread_mutex_t` | 기본은 비재귀. `PTHREAD_MUTEX_RECURSIVE`, `ERRORCHECK`, 우선순위 상속(`PTHREAD_PRIO_INHERIT`), 견고 뮤텍스(`ROBUST`: 소유자가 죽으면 `EOWNERDEAD`) |
| 조건 변수 | `pthread_cond_t` | 뮤텍스와 짝. 스퓨리어스 웨이크업 허용 → 항상 루프로 조건 재확인 |
| 읽기-쓰기 락 | `pthread_rwlock_t` | 쓰기 우선/읽기 우선 설정 가능 |
| 스핀락 | `pthread_spinlock_t` | 커널 안 감. 짧은 임계 구역 전용 |
| 세마포어 | `sem_t` | POSIX. `sem_open`으로 이름 붙여 프로세스 간 사용 |
| 배리어 | `pthread_barrier_t` | N개 스레드가 모두 도착할 때까지 대기 |
| 원스 | `pthread_once_t` | 단 한 번 초기화 |
| 이벤트 | 없음 | 조건 변수 + 플래그로 직접 만든다. 또는 `eventfd` |

**Windows: 두 계층의 프리미티브**

Windows는 프리미티브가 두 계층으로 나뉜다.

**(a) 커널 오브젝트 (디스패처 오브젝트)**: 핸들로 다루고, 이름을 붙일 수 있고, 프로세스 간에 통하고, `WaitForMultipleObjects`에 넣을 수 있다. 대가는 **모든 획득/해제가 시스템 콜**이라는 점이다. 경합이 없어도 커널을 다녀온다.

| 오브젝트 | API | 특징 |
|---|---|---|
| Mutex | `CreateMutex`, `WaitForSingleObject`, `ReleaseMutex` | 항상 재귀적(같은 스레드는 재획득 가능). 소유자 스레드가 죽으면 대기자에게 `WAIT_ABANDONED` (견고 뮤텍스에 해당) |
| Semaphore | `CreateSemaphore`, `ReleaseSemaphore` | 카운트 세마포어 |
| Event | `CreateEvent`, `SetEvent`, `ResetEvent`, `PulseEvent` | **수동 리셋**(Set되면 Reset까지 모든 대기자 통과) / **자동 리셋**(대기자 하나만 통과 후 자동 Reset). 리눅스에 없는 프리미티브 |
| Waitable Timer | `CreateWaitableTimer`, `SetWaitableTimer` | 시각/주기에 시그널. `timerfd`에 해당 |
| Process, Thread | 생성 시 얻음 | 종료 시 시그널 |
| File, Socket (오버랩드) | `CreateFile`, `socket` | I/O 완료 시 시그널 |

**(b) 사용자 모드 프리미티브**: 프로세스 내부 전용, 핸들 없음, 이름 없음, `WaitForMultipleObjects` 불가. 경합이 없으면 커널을 안 간다(futex 방식).

| 프리미티브 | API | 특징 |
|---|---|---|
| CRITICAL_SECTION | `InitializeCriticalSection`, `EnterCriticalSection`, `LeaveCriticalSection` | 재귀적. 경합 시 스핀 후 내부 이벤트/키드 이벤트로 대기. 원래 40바이트 구조체 |
| SRWLock (Slim Reader/Writer) | `AcquireSRWLockExclusive/Shared`, `Release...` | 포인터 크기(8바이트). 비재귀. Vista+. CRITICAL_SECTION보다 빠르고 작아 현대 코드의 기본 뮤텍스 |
| Condition Variable | `SleepConditionVariableCS/SRW`, `WakeConditionVariable`, `WakeAllConditionVariable` | Vista+. CRITICAL_SECTION 또는 SRWLock과 짝 |
| One-time init | `InitOnceExecuteOnce` | `pthread_once`에 해당 |
| Interlocked | `InterlockedIncrement`, `InterlockedCompareExchange` 등 | 원자적 연산 (C11 `<stdatomic.h>`, C++ `std::atomic` 이전 방식) |
| WaitOnAddress | `WaitOnAddress`, `WakeByAddressSingle/All` | **Windows 8+의 futex**. 정확히 같은 의미. Rust, C++20 `std::atomic::wait`가 이것 위에 있다 |
| Synchronization Barrier | `EnterSynchronizationBarrier` | Windows 8+ |

**대응표**

| 개념 | 리눅스 | Windows (프로세스 내) | Windows (프로세스 간) |
|---|---|---|---|
| 뮤텍스 | `pthread_mutex_t` | SRWLock(비재귀) / CRITICAL_SECTION(재귀) | Mutex 오브젝트 |
| 조건 변수 | `pthread_cond_t` | CONDITION_VARIABLE | 없음 (이벤트 + 뮤텍스로 흉내) |
| 읽기-쓰기 락 | `pthread_rwlock_t` | SRWLock | 없음 |
| 세마포어 | `sem_t` (이름 있으면 프로세스 간) | Semaphore 오브젝트 | Semaphore 오브젝트 (이름) |
| 이벤트 | `eventfd`, 또는 cond+flag | Event 오브젝트 (커널 경유) | Event 오브젝트 (이름) |
| futex | `futex` | `WaitOnAddress` | 없음 |
| 원스 | `pthread_once` | `InitOnceExecuteOnce` | 해당 없음 |
| 견고 뮤텍스 | `PTHREAD_MUTEX_ROBUST` | 해당 없음 | Mutex의 `WAIT_ABANDONED` |

**성능 감각**

- 경합 없는 획득/해제: 리눅스 pthread 뮤텍스 ≈ Windows SRWLock ≈ CRITICAL_SECTION ≈ 20~50ns (원자 연산 한두 개). Windows Mutex 오브젝트 ≈ 1~2μs (시스템 콜 두 번). **커널 뮤텍스를 프로세스 내부 동기화에 쓰면 50배 느리다.** Windows 초심자의 가장 흔한 실수다.
- 경합 시: 둘 다 커널 대기로 떨어지며 수 μs. 컨텍스트 스위치 비용이 지배한다.
- 리눅스 pthread 뮤텍스를 `PTHREAD_PROCESS_SHARED`로 공유 메모리에 놓으면 프로세스 간에도 경합 없을 때 시스템 콜이 없다. Windows에서 프로세스 간 동기화는 항상 커널 오브젝트라 항상 시스템 콜이다.

**재귀성의 기본값 차이**: pthread 뮤텍스는 기본 비재귀(같은 스레드가 다시 잠그면 데드락 또는 미정의 동작), Windows CRITICAL_SECTION과 Mutex는 항상 재귀. 리눅스 코드를 Windows로 옮기면 재귀로 인해 숨어 있던 버그가 안 보이고, 반대로 Windows 코드를 리눅스로 옮기면 재귀 획득에서 즉시 데드락이 난다. SRWLock은 비재귀라 pthread와 같다.

**이벤트의 부재**: Windows 코드는 Event 오브젝트를 아주 자주 쓴다("작업 완료됨", "종료 요청됨"). 이것을 pthreads로 옮길 때 조건 변수 + 뮤텍스 + bool 플래그 세 개가 필요하다. 반대로 `PulseEvent`처럼 경쟁 조건이 내재된 API는 옮기지 말고 재설계해야 한다. `eventfd`는 카운터 기반이라 자동 리셋 이벤트에 가깝다.

## 5.5 대기의 통합: `WaitForMultipleObjects` vs `epoll`

이 절은 2.3절에서 시작한 "모든 것은 오브젝트 vs 모든 것은 파일"의 스레드 관점 결론이다.

**Windows: 종류를 가리지 않는 대기**

```c
HANDLE h[4] = { hShutdownEvent, hWorkQueueSemaphore, hChildProcess, hTimer };
for (;;) {
    DWORD r = WaitForMultipleObjects(4, h, FALSE /* any */, INFINITE);
    switch (r) {
    case WAIT_OBJECT_0 + 0: return;           // 종료 요청
    case WAIT_OBJECT_0 + 1: process_work();   // 큐에 작업 도착
    case WAIT_OBJECT_0 + 2: reap_child();     // 자식 종료
    case WAIT_OBJECT_0 + 3: on_tick();        // 주기 타이머
    }
}
```

- 최대 `MAXIMUM_WAIT_OBJECTS` = 64개. 더 필요하면 스레드를 나누거나 IOCP를 쓴다.
- `bWaitAll = TRUE`면 모두 시그널될 때까지 대기(원자적으로 모두 획득).
- `MsgWaitForMultipleObjects`는 윈도우 메시지 도착도 함께 기다린다. GUI 스레드의 표준 루프.
- `WaitForMultipleObjectsEx`의 `bAlertable`이 APC(비동기 프로시저 호출)를 허용한다. APC는 "특정 스레드가 alertable 대기 상태일 때 실행되는 콜백"으로, 시그널 핸들러와 비슷하지만 스레드가 명시적으로 허용한 시점에만 실행된다. Overlapped I/O 완료 루틴이 APC로 전달된다.
- 자동 리셋 이벤트나 뮤텍스가 대기에 성공하면 **대기 함수가 오브젝트 상태를 바꾼다**(이벤트 리셋, 뮤텍스 획득). 이것이 "대기 = 획득"이라는 Windows 관념이다.

**리눅스: 모든 것을 fd로 바꿔서 하나의 fd 집합을 대기**

```c
int ep = epoll_create1(EPOLL_CLOEXEC);
int shutdown_fd = eventfd(0, EFD_NONBLOCK);
int work_fd     = eventfd(0, EFD_NONBLOCK | EFD_SEMAPHORE);   // 세마포어 의미
int child_fd    = pidfd_open(child_pid, 0);
int timer_fd    = timerfd_create(CLOCK_MONOTONIC, TFD_NONBLOCK);
// 각각 epoll_ctl(ep, EPOLL_CTL_ADD, fd, &ev) 등록

struct epoll_event evs[16];
for (;;) {
    int n = epoll_wait(ep, evs, 16, -1);
    for (int i = 0; i < n; i++) {
        int fd = evs[i].data.fd;
        if (fd == shutdown_fd) return;
        if (fd == work_fd)  { uint64_t v; read(work_fd, &v, 8); process_work(); }
        if (fd == child_fd) { waitid(P_PIDFD, child_fd, ...); }
        if (fd == timer_fd) { uint64_t exp; read(timer_fd, &exp, 8); on_tick(); }
    }
}
```

- fd 수 제한은 실질적으로 없다(수십만 개).
- `epoll`은 대기 성공 시 오브젝트 상태를 바꾸지 않는다. **대기와 소비가 분리**된다. `read`로 이벤트를 소비해야 다음 `epoll_wait`에서 다시 안 뜬다(level-triggered일 때). "대기 = 준비됨 알림"이라는 리눅스 관념이다.
- 뮤텍스나 조건 변수는 fd가 아니므로 `epoll`에 넣을 수 없다. "락을 얻을 수 있거나 소켓에 데이터가 오거나"를 한 번에 기다릴 수는 없다. 대신 `eventfd`로 신호를 보내는 설계로 바꾼다.
- 시그널을 이 루프에 통합하려면 `signalfd`, 또는 `epoll_pwait`로 대기 중에만 시그널 마스크를 푸는 기법(self-pipe trick의 현대판)을 쓴다.

**두 모델의 결과**

| 관점 | `WaitForMultipleObjects` | `epoll` |
|---|---|---|
| 대기 대상 | 커널 오브젝트 (뮤텍스, 이벤트, 프로세스, 스레드, 타이머, 파일, 소켓) | fd (소켓, 파이프, 타이머fd, 이벤트fd, 시그널fd, pidfd, 일반 파일은 항상 ready) |
| 개수 한계 | 64 | 사실상 무제한 |
| 대기와 소비 | 통합 (대기 성공 = 획득) | 분리 (대기 성공 = 준비됨, 이후 read로 소비) |
| 여러 대기자 | 자동 리셋 이벤트/뮤텍스는 하나만 깨움 | 기본은 모두 깨움. `EPOLLEXCLUSIVE`로 하나만 |
| 락과 통합 | 뮤텍스를 대기 목록에 넣을 수 있음 | 불가 |
| 확장 경로 | IOCP (완료 큐, 스레드 풀 통합) | 그대로 epoll (C10K 이후 표준) |
| 설계 철학 | "무엇이든 기다린다" | "무엇이든 fd로 만든다" |

## 5.6 스케줄러

**리눅스: CFS → EEVDF**

- 일반 태스크는 `SCHED_OTHER`(=`SCHED_NORMAL`). 커널 6.6부터 CFS(Completely Fair Scheduler)가 EEVDF(Earliest Eligible Virtual Deadline First)로 대체되었다. 둘 다 "가중치에 비례해 CPU 시간을 공정 분배"가 목표이고, EEVDF는 지연 시간 보장이 추가되었다.
- 우선순위는 **나이스 값** -20(높음)~+19(낮음). 가중치로 변환되어 CPU 시간 비율을 정한다. 나이스 0과 나이스 5의 시간 비율은 약 3:1.
- 실시간 정책 `SCHED_FIFO`, `SCHED_RR`은 우선순위 1~99로 일반 태스크보다 항상 먼저 실행된다. root 또는 `CAP_SYS_NICE` 필요. `SCHED_DEADLINE`은 주기와 데드라인을 명시.
- `SCHED_IDLE`, `SCHED_BATCH`는 낮은 우선순위 배치용.
- 타임슬라이스는 고정이 아니라 러너블 태스크 수와 가중치에 따라 동적. `sched_min_granularity`, `sched_latency` 계열 튜너블(EEVDF에서는 `base_slice`).
- 코어 간 로드 밸런싱은 스케줄링 도메인(SMT → 코어 → 패키지 → NUMA) 계층에 따라 주기적으로 실행. `sched_setaffinity`로 CPU 고정.
- cgroup `cpu.weight`, `cpu.max`로 그룹 단위 비율/상한. 컨테이너 `--cpus=1`이 `cpu.max`를 100ms 주기에 100ms 쿼터로 설정하고, 초과하면 **스로틀링**된다. 8스레드 프로그램이 `--cpus=1`에서 이상하게 느린 이유가 이것이다(8개가 12.5ms씩 쓰고 나머지 87.5ms 동안 전부 멈춤).
- 스레드는 태스크이므로 모든 설정이 스레드 단위다.

**Windows: 우선순위 기반 선점 스케줄러**

- 32단계 우선순위. 0은 제로 페이지 스레드 전용, 1~15가 **동적 범위**(일반), 16~31이 **실시간 범위**.
- 스레드의 우선순위 = 프로세스의 **우선순위 클래스**(`IDLE`, `BELOW_NORMAL`, `NORMAL`, `ABOVE_NORMAL`, `HIGH`, `REALTIME`)와 스레드의 **상대 우선순위**(`IDLE`, `LOWEST`, `BELOW_NORMAL`, `NORMAL`, `ABOVE_NORMAL`, `HIGHEST`, `TIME_CRITICAL`)의 조합. `NORMAL` 클래스 + `NORMAL` 상대 = 8.
- 스케줄링은 **엄격한 우선순위**다. 높은 우선순위의 러너블 스레드가 있으면 낮은 것은 실행되지 않는다. 같은 우선순위 안에서만 라운드 로빈. 공정성 개념이 없다. 그래서 **동적 부스트**가 필수다: I/O 완료 시(디스크 +1, 키보드 +6, 사운드 +8), 대기에서 깨어날 때, 포그라운드 프로세스 창의 스레드, 락 컨보이 완화, 오래 굶은 스레드(밸런스 셋 매니저가 4초 이상 굶은 스레드를 15로 잠시 올림). 부스트는 퀀텀마다 1씩 감소해 기본값으로 돌아온다.
- 퀀텀(타임슬라이스)은 클라이언트 Windows에서 2 클록 틱(약 20~30ms), 포그라운드 프로세스는 3배. 서버는 12 틱(약 180ms). `SystemParametersInfo`나 레지스트리 `Win32PrioritySeparation`으로 조정.
- 실시간 범위(16~31)는 `REALTIME_PRIORITY_CLASS` 프로세스에서만 가능하며 `SeIncreaseBasePriorityPrivilege` 필요. 부스트 없음. 잘못 쓰면 시스템이 멎는다.
- 멀티코어: 스레드마다 **ideal processor**가 있고, 마지막 실행 코어와 ideal을 우선 고려. 코어별 준비 큐(Win7+). `SetThreadAffinityMask`, `SetThreadIdealProcessor`. Windows 10부터 CPU 세트(`SetProcessDefaultCpuSets`)로 "선호"를 표현. 이기종 코어(P/E 코어)는 Windows 11의 Thread Director 통합.
- 잡 오브젝트 `JOB_OBJECT_CPU_RATE_CONTROL`로 그룹 단위 상한. cgroup `cpu.max`와 같은 스로틀링 방식.
- **MMCSS(Multimedia Class Scheduler Service)**: 오디오/비디오 스레드에 `AvSetMmThreadCharacteristics`로 "Pro Audio" 같은 태스크를 등록하면 실시간 근처 우선순위를 안전하게 주고 CPU 점유율을 제한한다. 리눅스의 `SCHED_FIFO` + 오디오 그룹 rtprio 한도에 대응.

**비교표**

| 항목 | 리눅스 | Windows |
|---|---|---|
| 일반 스레드 정책 | 가중치 비례 공정 분배 (EEVDF) | 엄격 우선순위 + 동적 부스트 |
| 우선순위 표현 | 나이스 -20~19 (일반), 1~99 (RT) | 1~15 (동적), 16~31 (RT) |
| 우선순위의 의미 | CPU 시간 **비율** | 실행 **순서** (높은 것이 항상 먼저) |
| 굶주림 방지 | 공정성에 내재 | 부스트와 밸런스 셋 매니저의 보정 |
| 타임슬라이스 | 동적 | 고정 퀀텀 (클라이언트/서버, 포그라운드 차등) |
| I/O 보상 | 대기했던 태스크는 vruntime이 작아 자연히 먼저 | 명시적 부스트 (+1~+8) |
| 그룹 제한 | cgroup `cpu.weight`, `cpu.max` | Job Object CPU rate control |
| 코어 고정 | `sched_setaffinity` (스레드별) | `SetThreadAffinityMask`, CPU sets |
| 실시간 | `SCHED_FIFO/RR/DEADLINE` | 우선순위 16~31, MMCSS |
| 관측 | `/proc/<pid>/sched`, `perf sched`, `top -H` | Process Explorer 스레드 탭, ETW `CSwitch` 이벤트, WPA |

**프로그래머에게 의미**: 리눅스에서 "이 스레드가 더 중요하다"는 나이스 값을 낮추는 것이고, 결과는 CPU 시간 비율이 조금 커지는 것이다. Windows에서 `THREAD_PRIORITY_HIGHEST`를 주면 그 스레드가 러너블인 동안 같은 코어의 낮은 스레드는 **전혀** 실행되지 않는다. Windows에서 우선순위를 올린 스레드가 스핀 대기를 하면 낮은 우선순위 스레드가 락을 못 풀어 우선순위 역전 데드락이 생긴다(부스트가 4초 뒤에 구해 주지만 그 사이 멎는다). 리눅스로 옮길 때는 반대로 우선순위 설정이 기대만큼 효과가 없다고 느낀다.

## 5.7 스레드 풀

**리눅스**: 커널이나 glibc가 제공하는 표준 스레드 풀이 없다. 각 언어 런타임(Go 스케줄러, Java `ForkJoinPool`, .NET `ThreadPool`, Rust `rayon`/`tokio`, libuv 워커 풀)이 자기 것을 구현한다. C에서는 직접 만들거나 GLib, libdispatch(Apple 기원, 리눅스 포트) 같은 라이브러리를 쓴다.

**Windows**: OS가 스레드 풀 API를 제공한다(Vista+ 새 API, `Tp*`).

```c
PTP_POOL pool = CreateThreadpool(NULL);
SetThreadpoolThreadMaximum(pool, 8);
TP_CALLBACK_ENVIRON env; InitializeThreadpoolEnvironment(&env);
SetThreadpoolCallbackPool(&env, pool);

PTP_WORK work = CreateThreadpoolWork(WorkCallback, ctx, &env);
SubmitThreadpoolWork(work);                    // 작업 하나
PTP_TIMER timer = CreateThreadpoolTimer(TimerCb, ctx, &env);   // 타이머 콜백
PTP_WAIT wait = CreateThreadpoolWait(WaitCb, ctx, &env);       // 핸들이 시그널되면 콜백
SetThreadpoolWait(wait, hEvent, NULL);
PTP_IO io = CreateThreadpoolIo(hFile, IoCb, ctx, &env);        // I/O 완료 시 콜백 (IOCP 통합)
```

작업, 타이머, 핸들 대기, I/O 완료를 모두 같은 풀에서 콜백으로 받는다. 풀은 부하에 따라 스레드 수를 자동 조절하고, 내부적으로 IOCP를 사용한다. .NET `ThreadPool`, C++ PPL/Concurrency Runtime, WinRT 비동기가 이 위에 있거나 유사 구조다.

이것이 가능한 이유도 "모든 것은 오브젝트"다. 핸들 대기를 풀에 위임할 수 있다(`RegisterWaitForSingleObject`). 리눅스에서 같은 것을 하려면 `epoll` 루프 스레드가 fd를 감시하고 워커 큐에 넘기는 구조를 직접 짜야 한다.

## 5.8 스레드 지역 저장소(TLS)

| 항목 | 리눅스 | Windows |
|---|---|---|
| 컴파일러 지원 | `__thread`, C11 `_Thread_local`, C++11 `thread_local` | `__declspec(thread)`, C11/C++11 키워드 |
| 동적 API | `pthread_key_create`, `pthread_setspecific/getspecific` (키 최대 1024) | `TlsAlloc`, `TlsSetValue/GetValue` (슬롯 최대 1088), `FlsAlloc`(파이버 지역, 소멸자 콜백 지원) |
| 구현 | ELF TLS 세그먼트, `fs` 레지스터가 TCB를 가리킴. 동적 로드 `.so`의 TLS는 `__tls_get_addr` 경유 | PE `.tls` 섹션, `gs` 레지스터가 TEB를 가리킴, TEB의 `ThreadLocalStoragePointer` |
| 소멸자 | `pthread_key_create`의 소멸자 콜백. `thread_local` 객체 소멸자 지원 | `TlsAlloc`은 소멸자 없음. `FlsAlloc`은 있음. C++ `thread_local` 소멸자는 CRT가 `DLL_THREAD_DETACH`로 처리 |
| 동적 로드 DLL의 `__declspec(thread)` | 해당 없음 (리눅스는 항상 동작) | XP 이전에는 `LoadLibrary`한 DLL에서 미동작. Vista+에서 해결. 여전히 암묵적 TLS 슬롯 한계 있음 |
| 접근 비용 | 실행 파일/초기 `.so`의 TLS: `fs:offset` 한 명령. 동적 로드: 함수 호출 | `.exe`와 정적 임포트 DLL: 몇 명령. 동적 로드 DLL: 약간 더 |

두 OS 모두 `thread_local`이 표준이고 성능도 유사하다. 함정은 Windows에서 **TLS 소멸자가 `DllMain(DLL_THREAD_DETACH)`에 의존**한다는 점이다. `TerminateThread`로 죽은 스레드나, `ExitProcess` 중 다른 스레드는 이 알림을 못 받아 소멸자가 실행되지 않는다.

## 5.9 메모리 모델과 원자적 연산

CPU가 같으므로 하드웨어 메모리 모델(x86-64 TSO, ARM64 약한 순서)은 동일하다. C11/C++11 `<atomic>`을 쓰면 컴파일러가 두 OS에서 같은 코드를 낸다. 차이는 컴파일러 고유 확장과 옛 API에 있다.

| 항목 | gcc/clang (리눅스) | MSVC (Windows) |
|---|---|---|
| 표준 원자 | `std::atomic`, `_Atomic` | 동일 |
| 컴파일러 내장 | `__atomic_*`, `__sync_*` | `_Interlocked*`, `_ReadWriteBarrier`(폐기), `MemoryBarrier` |
| OS API | 없음 | `InterlockedIncrement`, `InterlockedCompareExchange128` 등 |
| `volatile` 의미 | 컴파일러 재배치 금지만. 원자성/순서 보장 없음 | `/volatile:ms`(x86/x64 기본)에서는 acquire/release 의미 부여. `/volatile:iso`에서는 표준 의미. ARM64는 기본 iso |
| 정렬 요구 | 자연 정렬 | 동일. `InterlockedCompareExchange128`은 16바이트 정렬 필수 |

`volatile`의 의미 차이가 이식 시 실제 버그를 만든다. MSVC x64에서 `volatile bool done;`로 스레드 간 플래그를 만들면 동작하지만(비표준 확장), gcc에서는 순서 보장이 없어 다른 스레드가 영원히 못 볼 수 있다(실제로 x86에서는 대체로 보이지만 컴파일러 최적화에 따라 루프 밖으로 끌어올려질 수 있다). `std::atomic<bool>`로 통일해야 한다.

## 5.10 이식할 때 부딪히는 문제

1. **프로세스 내부 동기화에 커널 Mutex 오브젝트 사용** (Windows → 리눅스는 문제없지만, Windows 자체 성능 문제). SRWLock이나 CRITICAL_SECTION으로 바꾼다.
2. **재귀 뮤텍스 가정**: Windows CRITICAL_SECTION에 익숙한 코드가 같은 스레드에서 중첩 잠금을 한다. pthread 기본 뮤텍스에서는 데드락. `PTHREAD_MUTEX_RECURSIVE`로 바꾸거나(권장하지 않음) 중첩을 제거한다.
3. **Event 오브젝트 패턴**: `SetEvent`/`WaitForSingleObject`로 스레드 간 신호를 보내는 코드가 리눅스에는 직접 대응물이 없다. 조건 변수 + 뮤텍스 + 플래그로 재작성. `PulseEvent`는 두 OS 모두에서 버그의 원인이므로 제거.
4. **`WaitForMultipleObjects`로 이질적 대기**: 리눅스에서는 모두 fd로 바꿔 `epoll`에 넣거나, 뮤텍스/조건 변수 하나로 모든 이벤트를 큐에 밀어 넣는 구조로 바꾼다.
5. **`WAIT_ABANDONED` 처리**: 프로세스 간 뮤텍스에서 소유자 프로세스가 죽었을 때. 리눅스 견고 뮤텍스(`EOWNERDEAD` → `pthread_mutex_consistent`)로 대응.
6. **우선순위 의미 차이**: Windows에서 `THREAD_PRIORITY_HIGHEST`로 실시간성을 얻던 오디오/게임 스레드는 리눅스에서 `SCHED_FIFO` + `rtprio` 한도(`/etc/security/limits.conf`) 설정이 필요하다. 반대로 리눅스 나이스 값 조정은 Windows에서 클래스/상대 우선순위 조합으로 바꿔야 하고, 효과가 훨씬 강하게 나타난다.
7. **스택 크기** (3.8절): Windows 1MB 기본이 리눅스 8MB 코드를 터뜨린다.
8. **`pthread_cancel`**: Windows 대응물이 없다(`TerminateThread`는 아니다). 협력적 취소(플래그 + 이벤트)로 재설계. 사실 리눅스에서도 `pthread_cancel`은 피하는 것이 좋다.
9. **`fork` 후 스레드 상태** (4.2절): 리눅스에서 멀티스레드 프로세스가 `fork`하면 자식에 스레드 하나만 남는다. Windows에는 이 상황 자체가 없다.
10. **CRT 스레드 시작**: Windows에서 `CreateThread` 대신 `_beginthreadex`. C++ `std::thread`를 쓰면 라이브러리가 처리한다.
11. **컨테이너 CPU 제한**: 리눅스 `--cpus=N`은 쿼터 스로틀링이라 스레드 수를 `nproc`(호스트 코어 수)로 정하는 코드가 과도한 스레드를 만들고 스로틀링에 걸린다. `sched_getaffinity`나 cgroup `cpu.max`를 읽어야 한다(JVM, .NET, Go 1.25+가 자동 인식). Windows 잡 오브젝트 CPU rate control도 같은 문제를 만들지만 컨테이너 사용이 적어 덜 드러난다.

## 5.11 런타임에서는

- **Go**: 고루틴은 사용자 모드 스케줄링(M:N)이라 OS 스레드 차이가 대부분 감춰진다. 런타임은 리눅스에서 `futex`, Windows에서 `WaitForSingleObject`/`SetEvent`(스레드별 이벤트)로 M(OS 스레드)을 재운다. `GOMAXPROCS`는 리눅스에서 cgroup 한도를 1.25부터 인식. Windows에서 타이머 해상도가 15.6ms라 `time.Sleep(1ms)`이 부정확했던 문제가 있었고, 런타임이 고해상도 타이머를 요청하도록 바뀌었다.
- **Rust**: `std::sync::Mutex`가 리눅스에서는 futex 기반, Windows에서는 SRWLock 기반(1.62 이후 리눅스도 futex 직접 사용). `std::thread::spawn`의 기본 스택은 2MB로 두 OS에서 통일(`RUST_MIN_STACK`). `parking_lot`은 두 OS 모두 자체 파킹 구현. Tokio는 리눅스 epoll, Windows IOCP(`mio` 경유).
- **.NET**: `lock`(Monitor)은 두 OS 모두 CLR 자체 구현(스핀 → 커널 이벤트). `Mutex` 클래스는 커널 오브젝트(느림, 프로세스 간). `ThreadPool`은 자체 구현이나 Windows에서 I/O 스레드는 IOCP 기반. `Thread.Priority`는 Windows에서는 그대로, 리눅스에서는 나이스 값으로 매핑되지만 권한이 없으면 무시된다.
- **JVM**: `synchronized`와 `ReentrantLock`은 JVM 자체 구현(스핀 → `park`). `park`는 리눅스에서 pthread 조건 변수(futex), Windows에서 이벤트 오브젝트. 가상 스레드(JDK 21+)는 두 OS 공통 M:N. `Thread.setPriority`는 리눅스에서 기본적으로 **무시**된다(`-XX:ThreadPriorityPolicy=1` + root 필요). Windows에서는 동작한다. 이 차이로 "리눅스에서 우선순위가 안 먹는다"는 질문이 반복된다.
- **Node.js**: 단일 메인 스레드 + libuv 워커 풀(기본 4개, `UV_THREADPOOL_SIZE`). `worker_threads`는 V8 isolate별 OS 스레드. libuv가 리눅스 pthread, Windows CRITICAL_SECTION/CONDITION_VARIABLE로 동기화를 추상화한다.
- **Python**: GIL 때문에 CPython 스레드는 한 번에 하나만 바이트코드를 실행한다(3.13 free-threaded 빌드 제외). GIL은 리눅스에서 pthread 조건 변수, Windows에서 이벤트 오브젝트로 구현. `threading.Thread`는 OS 스레드다. `signal` 핸들러는 메인 스레드에서만 실행되고, Windows에서 Ctrl+C가 `time.sleep` 중인 메인 스레드를 깨우지 못하던 문제가 오래 있었다.

## 실전 체크리스트

- [ ] Windows 빌드에서 프로세스 내부 잠금에 커널 Mutex를 쓰는 곳이 있는가? SRWLock/CRITICAL_SECTION으로 바꿀 수 있는가?
- [ ] 같은 스레드가 뮤텍스를 중첩 획득하는 경로가 있는가? 두 OS에서 재귀성 기본값이 같은가?
- [ ] Event 오브젝트나 `WaitForMultipleObjects`에 의존하는 대기 구조가 있는가? 리눅스 대응 설계(조건 변수 큐 또는 epoll + eventfd)가 있는가?
- [ ] 스레드 우선순위를 조정하는가? 리눅스에서 권한이 있는가, Windows에서 굶주림을 일으키지 않는가?
- [ ] 스레드를 밖에서 죽이는 코드(`pthread_cancel`, `TerminateThread`)가 있는가? 협력적 취소로 바꿀 수 있는가?
- [ ] 스레드 수를 코어 수로 정하는가? 컨테이너/잡 오브젝트의 CPU 제한을 읽는가?
- [ ] `volatile`을 스레드 간 통신에 쓰는가? `std::atomic`으로 바꿨는가?
- [ ] 스레드 스택 크기가 두 OS에서 충분한가?
- [ ] TLS 소멸자에 의존하는 정리 로직이 있는가? Windows에서 `DLL_THREAD_DETACH`를 못 받는 경로가 있는가?
- [ ] 프로세스 간 뮤텍스에서 소유자 사망(`WAIT_ABANDONED`/`EOWNERDEAD`)을 처리하는가?
