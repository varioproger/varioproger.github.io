# 3장. 메모리

## 3.1 OS가 풀어야 하는 문제

메모리 관리에서 OS가 해결해야 하는 문제는 두 OS가 동일하다.

1. **가상화**: 각 프로세스가 자기만의 연속된 주소 공간을 가진 것처럼 보이게 한다. 물리 메모리는 페이지(4KB) 단위로 쪼개져 여기저기 흩어져 있다.
2. **격리**: 프로세스 A가 프로세스 B의 메모리를 읽거나 쓸 수 없게 한다.
3. **과할당**: 물리 RAM보다 많은 메모리를 프로세스들이 요구할 때 어떻게 할 것인가. 디스크로 내보낼(스왑) 것인가, 거부할 것인가, 나중에 죽일 것인가.
4. **캐싱**: 남는 RAM을 디스크 캐시로 활용해 파일 I/O를 빠르게 한다.
5. **공유**: 같은 라이브러리 코드나 파일을 여러 프로세스가 물리 페이지 하나로 공유한다.

하드웨어 메커니즘(페이지 테이블, TLB, MMU)은 같은 x86-64 CPU를 쓰므로 동일하다. 차이는 **정책**, 그리고 프로그래머에게 노출되는 **API의 형태**에 있다.

## 3.2 가상 주소 공간의 레이아웃

**공통점**: 64비트 x86에서 두 OS 모두 하위 128TB를 사용자 공간, 상위 128TB를 커널 공간으로 쓴다(48비트 주소, 5단계 페이징에서는 더 크다). 사용자 프로세스가 커널 주소에 접근하면 페이지 폴트 → 세그폴트(리눅스) 또는 액세스 위반(Windows)이다.

**리눅스 사용자 공간 레이아웃**

```
높은 주소
  [스택]            메인 스레드 스택, 아래로 자람, ulimit -s (기본 8MB)
  [mmap 영역]       공유 라이브러리, 익명 mmap, 스레드 스택, 대형 malloc
  ...
  [힙 (brk)]        위로 자람, 소형 malloc
  [.bss / .data]    전역 변수
  [.text]           코드
낮은 주소            (0x400000 근처 또는 PIE면 무작위)
```

`/proc/<pid>/maps`를 읽으면 이 레이아웃이 그대로 보인다.

```
$ cat /proc/self/maps
55d0c8a00000-55d0c8a02000 r--p 00000000 08:01 1234  /usr/bin/cat
...
7f3a1c000000-7f3a1c021000 rw-p 00000000 00:00 0     [heap? no: malloc arena]
7f3a1c400000-7f3a1c5c5000 r--p 00000000 08:01 5678  /usr/lib/libc.so.6
7ffd5e3c0000-7ffd5e3e1000 rw-p 00000000 00:00 0     [stack]
```

**Windows 사용자 공간 레이아웃**

Windows는 고정된 "힙 영역"이 없다. 모든 것이 `VirtualAlloc`으로 확보한 영역 안에 있고, 실행 파일 이미지, DLL, 힙, 스레드 스택이 주소 공간에 흩어져 배치된다(ASLR).

```
높은 주소
  [ntdll.dll, kernel32.dll ...]   시스템 DLL, 부팅 시 무작위 위치가 결정되고 모든 프로세스가 같은 주소를 공유
  [스레드 스택들]                  각각 예약 1MB (기본), 커밋은 첫 페이지부터
  [힙 세그먼트들]                  프로세스 기본 힙 + 추가 힙
  [매핑된 파일]
  [애플리케이션 DLL]
  [EXE 이미지]                    기본 0x140000000 (64비트), ASLR로 이동
  [64KB 예약 영역]                NULL 포인터 접근 감지용, 항상 접근 불가
낮은 주소
```

VMMap(Sysinternals)이 이 레이아웃을 시각화해 준다. 리눅스의 `/proc/<pid>/maps`에 해당하는 API는 `VirtualQueryEx`로 주소 공간을 순회하는 것이다.

**32비트 호환 이슈**: 32비트 Windows 프로세스는 기본 2GB 사용자 공간이고, 링커 플래그 `/LARGEADDRESSAWARE`를 켜면 64비트 OS에서 4GB를 쓴다. 리눅스 32비트 프로세스는 기본 3GB다. 32비트 레거시 바이너리를 다루는 게임 업계에서는 이 차이가 실제로 문제가 된다.

## 3.3 할당 API: 예약, 커밋, 그리고 그 사이의 철학

이 절이 메모리 장의 핵심이다.

**리눅스: `mmap`과 `brk`**

```c
// 익명 메모리 1GB 확보
void *p = mmap(NULL, 1UL << 30, PROT_READ | PROT_WRITE,
               MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
```

이 호출은 즉시 성공하고, 거의 즉시 반환된다. 커널은 VMA(Virtual Memory Area) 구조체 하나를 만들어 "이 범위는 유효하다"고 기록할 뿐, 물리 페이지를 하나도 할당하지 않는다. 첫 번째 쓰기 접근이 일어날 때 페이지 폴트가 발생하고, 그때 커널이 물리 페이지를 하나 배정한다(demand paging). 읽기만 하면 모든 페이지가 커널의 "제로 페이지" 하나를 공유한다.

리눅스에는 "예약"과 "커밋"의 구분이 API에 없다. `mmap`은 두 가지를 동시에 한 것처럼 보이지만, 실제로는 예약만 하고 커밋은 접근 시 자동으로 일어난다.

`brk`/`sbrk`는 힙 끝을 옮기는 옛 방식이다. glibc `malloc`은 작은 요청에 `brk`를, 큰 요청(기본 128KB 이상, `M_MMAP_THRESHOLD`)에 `mmap`을 쓴다.

관련 API:

| 함수 | 역할 |
|---|---|
| `mmap` / `munmap` | 영역 매핑/해제. 파일 매핑과 익명 매핑 모두 |
| `mprotect` | 페이지 권한 변경 (JIT가 W → X로 바꿀 때) |
| `madvise` | 힌트. `MADV_DONTNEED`(페이지 즉시 반납), `MADV_FREE`(느긋한 반납), `MADV_HUGEPAGE` |
| `mlock` | 스왑 아웃 금지 (암호 키 보관) |
| `mremap` | 매핑을 이동/크기 변경 (realloc 최적화) |

**Windows: `VirtualAlloc`의 2단계**

```c
// 1단계: 예약 (Reserve) — 주소 범위만 확보, 물리 자원 없음
void *p = VirtualAlloc(NULL, 1ULL << 30, MEM_RESERVE, PAGE_NOACCESS);

// 2단계: 커밋 (Commit) — 실제로 쓸 부분만 백킹 스토어 확보
VirtualAlloc(p, 64 * 1024, MEM_COMMIT, PAGE_READWRITE);

// 둘을 한 번에
void *q = VirtualAlloc(NULL, size, MEM_RESERVE | MEM_COMMIT, PAGE_READWRITE);
```

Windows는 예약과 커밋을 명시적으로 분리한다.

- **예약**은 주소 공간의 범위를 확보한다. 물리 메모리도 페이지 파일도 소비하지 않는다. 64KB 단위 정렬(allocation granularity).
- **커밋**은 그 범위의 일부에 "백킹 스토어를 보장한다". 물리 페이지가 즉시 배정되는 것은 아니지만(여기서도 demand paging), **시스템 전체 커밋 한도**(물리 RAM + 페이지 파일 크기)에서 그만큼을 차감한다. 한도를 넘으면 `VirtualAlloc(MEM_COMMIT)`은 실패한다.

이것이 **커밋 차지(commit charge)** 모델이다. Windows는 "커밋했다면 나중에 접근할 때 물리 페이지가 반드시 있다"를 약속한다. 그 약속을 지키려면 커밋 시점에 자원을 확인해야 하고, 그래서 실패할 수 있다.

관련 API:

| 함수 | 역할 |
|---|---|
| `VirtualAlloc` / `VirtualFree` | 예약, 커밋, 디커밋(`MEM_DECOMMIT`), 해제(`MEM_RELEASE`) |
| `VirtualProtect` | 페이지 권한 변경 |
| `VirtualLock` | 워킹 셋에 고정 (mlock에 해당) |
| `DiscardVirtualMemory` / `OfferVirtualMemory` | `madvise(MADV_DONTNEED/FREE)`에 해당 (Windows 8.1+) |
| `VirtualAlloc2` | 특정 정렬, 플레이스홀더 (Windows 10+) |
| `CreateFileMapping` + `MapViewOfFile` | 파일 매핑과 공유 메모리 (mmap의 파일 매핑 역할) |

## 3.4 오버커밋 vs 커밋 차지: 실패는 언제 일어나는가

**리눅스: 오버커밋 허용이 기본**

`/proc/sys/vm/overcommit_memory`가 정책을 정한다.

| 값 | 의미 |
|---|---|
| 0 (기본) | 휴리스틱. 명백히 말도 안 되는 요청(물리 RAM + 스왑보다 큰 단일 요청)만 거부 |
| 1 | 항상 허용. 얼마를 요구해도 `mmap`이 성공 |
| 2 | 엄격. 총 커밋이 `스왑 + RAM × overcommit_ratio%`를 넘으면 거부. Windows와 유사 |

기본값 0에서 `malloc(64GB)`는 RAM이 16GB라도 성공한다. 문제는 프로세스들이 실제로 그 페이지를 건드리기 시작해 물리 RAM과 스왑이 모두 찰 때 일어난다. 이때 커널은 **OOM Killer**를 발동해 `oom_score`가 가장 높은 프로세스(대체로 가장 큰 프로세스)를 `SIGKILL`로 죽인다.

```
# dmesg
Out of memory: Killed process 12345 (java) total-vm:32GB, anon-rss:15GB ...
```

프로그래머 관점에서 이것은 "할당 시점에는 실패를 알 수 없고, 나중에 임의의 시점에 내 프로세스(또는 무관한 다른 프로세스)가 예고 없이 죽는다"는 의미다. `malloc`의 반환값을 검사하는 것은 리눅스에서 거의 의미가 없다.

이 정책의 근거는 `fork`다. 10GB 프로세스가 `fork`하면 이론적으로 10GB가 추가로 필요하지만 COW 덕분에 실제로는 거의 안 쓴다. 엄격한 커밋 모델에서는 이 `fork`가 실패한다. 오버커밋은 `fork` + `exec` 패턴을 살리기 위한 선택이다.

**Windows: 커밋 차지가 한도를 넘으면 즉시 실패**

Windows에는 오버커밋이 없다. 시스템 커밋 한도 = 물리 RAM + 모든 페이지 파일 크기. 모든 프로세스의 커밋 합계가 이 한도에 도달하면 다음 `VirtualAlloc(MEM_COMMIT)`, 즉 `HeapAlloc`, `malloc`, `new`가 실패한다. 페이지 파일이 "시스템 관리" 설정이면 Windows가 페이지 파일을 키우려 시도하고, 그래도 안 되면 "가상 메모리가 부족합니다" 알림이 뜬다.

OOM Killer는 없다. 대신 할당이 실패하고, 그것을 처리하는 것은 애플리케이션 책임이다. C++에서 `new`는 `std::bad_alloc`을 던지고, .NET은 `OutOfMemoryException`을 던진다.

**두 모델의 트레이드오프**

| 관점 | 오버커밋 (리눅스) | 커밋 차지 (Windows) |
|---|---|---|
| 할당 실패 | 거의 없음 | 발생함, 처리 필요 |
| 메모리 부족 시 | OOM Killer가 프로세스 강제 종료 | 할당 실패, 프로세스는 살아 있음 |
| 큰 희소 배열 (대부분 안 쓰는) | 자연스럽게 저렴 | 예약만 하고 필요 부분만 커밋해야 저렴 |
| `fork` | 가능 | 해당 없음 (fork 없음) |
| 예측 가능성 | 낮음 (언제 죽을지 모름) | 높음 (실패 지점이 명확) |
| 페이지 파일 없이 운영 | 스왑 없이도 RAM 이상 예약 가능 | 커밋 한도 = RAM. 실제 사용보다 커밋이 커서 RAM 여유가 있어도 실패 가능 |

마지막 행이 실무에서 자주 오해되는 부분이다. Windows에서 "물리 메모리는 50%밖에 안 썼는데 왜 할당이 실패하나"는 커밋 차지가 한도에 도달했기 때문이다. 작업 관리자의 "커밋됨(Committed)" 수치를 봐야 한다. 대형 배열을 커밋만 하고 안 쓰는 프로그램(예: 큰 `std::vector::reserve`, 큰 스레드 스택 다수)이 원인이다.

## 3.5 힙 구현: malloc 아래에는 무엇이 있나

**리눅스: glibc ptmalloc2**

- **아레나(arena)**: 스레드 경합을 줄이기 위해 여러 아레나를 둔다. 메인 아레나는 `brk`, 나머지는 `mmap`으로 64MB 힙 세그먼트를 잡는다. 아레나 수는 기본 코어 수 × 8(64비트). 스레드가 많은 서버에서 RSS가 부풀어 보이는 원인 중 하나다(`MALLOC_ARENA_MAX`로 제한).
- **bin**: 크기별 프리 리스트(fastbin, smallbin, largebin, unsorted, tcache).
- **tcache**: glibc 2.26부터 스레드별 캐시. 잠금 없이 작은 할당을 처리.
- **큰 할당**: 128KB 이상은 `mmap`으로 직접. `free` 시 `munmap`으로 즉시 반환.
- **trim**: 힙 상단의 빈 공간이 128KB 이상이면 `brk`로 축소. 중간의 빈 공간은 반환하지 않는다(이것이 "free했는데 RSS가 안 줄어든다"의 원인). `malloc_trim(0)`으로 강제 가능.
- **교체 가능**: `LD_PRELOAD=libjemalloc.so`로 재컴파일 없이 jemalloc, tcmalloc, mimalloc으로 바꿀 수 있다. Redis, Rust(과거), Firefox가 jemalloc을 쓴다.

**Windows: NT 힙과 CRT**

- **프로세스 기본 힙**: 모든 프로세스가 하나를 갖는다(`GetProcessHeap()`). Win32 API 내부가 이 힙을 쓴다.
- **추가 힙**: `HeapCreate`로 원하는 만큼 만든다. "이 서브시스템의 모든 할당을 힙 하나에 몰고, 끝나면 `HeapDestroy`로 통째로 해제"하는 패턴이 가능하다. 리눅스에는 이런 "힙 오브젝트" 개념이 없다.
- **LFH(Low Fragmentation Heap)**: Vista 이후 기본으로 켜지는 프론트엔드. 크기별 버킷으로 단편화를 줄인다. 리눅스의 bin과 유사.
- **Segment Heap**: Windows 10부터 UWP와 일부 시스템 프로세스에 쓰이는 새 구현. mimalloc과 설계가 비슷하다.
- **CRT malloc**: MSVC의 `malloc`은 결국 `HeapAlloc(_crtheap, ...)`이다. 별도 아레나 계층이 없다. 그래서 여러 DLL이 각기 다른 CRT 버전을 정적 링크하면 "A의 malloc으로 할당한 것을 B의 free로 해제"할 때 크래시가 난다. 리눅스에서는 libc가 하나라 이 문제가 없다.
- **교체**: `malloc`을 바꾸려면 링크 시점에 교체해야 한다(`LD_PRELOAD` 같은 것이 없다). mimalloc은 `mimalloc-redirect.dll`로 IAT 패치를 해서 이를 흉내 낸다.
- **디버그 지원**: `HeapSetInformation(HeapEnableTerminationOnCorruption)`, PageHeap(`gflags /p`), Application Verifier가 힙 손상을 잡는다. 리눅스의 `MALLOC_CHECK_`, ASan, Valgrind에 해당.

**"free했는데 메모리가 안 줄어든다" 비교**

두 OS 모두 힙은 페이지를 OS에 즉시 반납하지 않는다. 다만:

- 리눅스 glibc는 힙 상단만 trim한다. 중간 구멍은 `madvise(MADV_DONTNEED)`를 힙이 스스로 호출하지 않으면 RSS에 남는다. jemalloc은 주기적으로 반납한다.
- Windows 힙은 빈 세그먼트를 `VirtualFree(MEM_DECOMMIT)`로 비교적 적극적으로 디커밋한다. 다만 LFH 버킷에 남은 부분은 반납하지 않는다. `HeapCompact`로 강제 가능.

## 3.6 페이지 캐시 vs 캐시 매니저와 워킹 셋

**리눅스: 통합 페이지 캐시**

리눅스는 남는 RAM을 전부 파일 캐시로 쓴다. `free` 명령의 `buff/cache`가 수십 GB인 것이 정상이다. 프로세스가 메모리를 요구하면 캐시를 즉시 회수한다. 파일을 `read`하면 페이지 캐시에서 복사하고, `mmap`하면 페이지 캐시의 페이지를 프로세스 주소 공간에 직접 매핑한다. 두 경로가 같은 물리 페이지를 본다(unified page cache).

프로세스 메모리와 캐시 사이의 균형은 LRU 리스트 두 개(active/inactive)와 `swappiness`(0~200, 기본 60)로 조절된다. 컨테이너에서는 cgroup `memory.max`가 프로세스 RSS + 그 프로세스가 만든 페이지 캐시를 합쳐 제한하기 때문에, "파일을 많이 읽었더니 컨테이너가 OOM으로 죽었다"는 상황이 실제로 발생한다.

**Windows: 캐시 매니저 + 워킹 셋 관리자**

Windows도 파일 캐시에 남는 RAM을 쓰지만 구조가 다르다.

- **캐시 매니저(Cc)**는 파일 시스템 드라이버가 사용하는 커널 컴포넌트다. 시스템 주소 공간에 파일을 256KB 뷰 단위로 매핑하고, 실제 페이지 관리는 메모리 관리자에게 맡긴다.
- **워킹 셋(working set)**: 각 프로세스가 "현재 물리 메모리에 올라와 있는 페이지 집합"이다. 프로세스별로 최소/최대 워킹 셋 크기가 있고, 메모리 압박이 오면 **워킹 셋 관리자**가 프로세스별로 오래 안 쓴 페이지를 워킹 셋에서 빼서 **스탠바이 리스트**(standby list)로 옮긴다. 스탠바이 리스트의 페이지는 내용이 유지되므로 다시 접근하면 소프트 폴트로 즉시 복귀한다.
- **Modified 리스트**: 워킹 셋에서 빠졌지만 아직 디스크에 안 쓴 더티 페이지. Modified Page Writer가 백그라운드로 쓴다.

리눅스의 시스템 전체 LRU와 달리, Windows는 **프로세스 단위로 트리밍**한다. 그래서 "오랫동안 안 쓴 GUI 앱을 다시 클릭하면 잠깐 버벅인다"가 Windows에서 더 두드러진다. 작업 관리자의 "메모리(작업 집합)"이 워킹 셋이고, RSS에 해당한다.

**측정 지표 대응**

| 개념 | 리눅스 | Windows |
|---|---|---|
| 프로세스가 점유한 물리 메모리 | RSS (`ps`, `/proc/<pid>/status`의 VmRSS) | Working Set (작업 집합) |
| 프로세스가 예약한 가상 주소 | VSZ (VmSize) | Virtual Size (VMMap의 Size) |
| 프로세스가 "보장받은" 메모리 | 개념 없음 (오버커밋) | Private Bytes / Commit Size (커밋 크기) |
| 공유 페이지 공정 배분 | PSS (`/proc/<pid>/smaps_rollup`) | 직접 대응 없음. Private WS vs Shareable WS |
| 시스템 파일 캐시 | `buff/cache` | Standby + Modified + 캐시 매니저 |
| 스왑 | 스왑 파티션/파일, `swapon` | 페이지 파일 `pagefile.sys` |

Windows에서 "메모리 누수"를 찾을 때는 워킹 셋이 아니라 **Private Bytes(커밋)**를 봐야 한다. 워킹 셋은 OS가 트리밍하므로 누수가 있어도 줄어들 수 있다. 리눅스에서는 RSS와 함께 `smaps`의 `Anonymous` 합계를 본다.

## 3.7 공유 메모리와 파일 매핑

**리눅스**

```c
// POSIX 공유 메모리: /dev/shm 아래의 tmpfs 파일
int fd = shm_open("/myshm", O_CREAT | O_RDWR, 0600);
ftruncate(fd, size);
void *p = mmap(NULL, size, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);

// 파일 매핑: 그냥 일반 파일을 mmap
int f = open("data.bin", O_RDWR);
void *q = mmap(NULL, size, PROT_READ | PROT_WRITE, MAP_SHARED, f, 0);

// 부모-자식만 공유: 익명 + MAP_SHARED 후 fork
void *r = mmap(NULL, size, PROT_READ | PROT_WRITE, MAP_SHARED | MAP_ANONYMOUS, -1, 0);
```

`MAP_PRIVATE`는 COW라서 쓰기가 프로세스 사적 복사본을 만들고 파일에는 반영되지 않는다. `MAP_SHARED`는 페이지 캐시의 페이지를 직접 매핑하므로 쓰기가 파일에 반영된다(`msync`로 디스크 반영 시점 제어). System V `shmget`도 남아 있지만 새 코드에서는 쓰지 않는다.

**Windows**

```c
// 이름 있는 공유 메모리: 페이지 파일을 백킹으로 하는 섹션 오브젝트
HANDLE hMap = CreateFileMappingW(INVALID_HANDLE_VALUE, NULL, PAGE_READWRITE,
                                 0, size, L"Local\\MyShm");
void *p = MapViewOfFile(hMap, FILE_MAP_ALL_ACCESS, 0, 0, size);

// 파일 매핑
HANDLE hFile = CreateFileW(L"data.bin", GENERIC_READ | GENERIC_WRITE, 0, NULL,
                           OPEN_EXISTING, 0, NULL);
HANDLE hMap2 = CreateFileMappingW(hFile, NULL, PAGE_READWRITE, 0, 0, NULL);
void *q = MapViewOfFile(hMap2, FILE_MAP_WRITE, 0, 0, 0);
```

커널 내부에서 이것은 **섹션 오브젝트**(section object)다. 실행 파일과 DLL을 로드하는 것도 이미지 섹션을 매핑하는 것이므로, Windows에서 파일 매핑은 메모리 관리자의 핵심 메커니즘이다. `MapViewOfFile`의 오프셋은 64KB 정렬이어야 하고(allocation granularity), 리눅스 `mmap`은 4KB 정렬이다.

이름 공간에 `Local\`(세션 내)과 `Global\`(전체 시스템) 접두사를 붙이는 것은 터미널 서비스 세션 격리 때문이다. 리눅스의 `/dev/shm`은 마운트 네임스페이스로 격리된다.

**COW 매핑**: Windows는 `PAGE_WRITECOPY`로 `MAP_PRIVATE`에 해당하는 동작을 한다. DLL의 데이터 섹션이 이 방식으로 매핑되어, 프로세스가 전역 변수를 수정하면 그 페이지만 사적 복사본이 된다.

## 3.8 스택

| 항목 | 리눅스 | Windows |
|---|---|---|
| 메인 스레드 기본 크기 | 8MB (`ulimit -s`, 실행 시 변경 가능) | 1MB (링커 `/STACK:reserve,commit`, 빌드 시 결정) |
| 새 스레드 기본 크기 | `RLIMIT_STACK` 값 (대체로 8MB), `pthread_attr_setstacksize`로 변경 | 1MB, `CreateThread`의 `dwStackSize`로 변경 |
| 자라는 방식 | 메인 스레드: 커널이 폴트 시 자동 확장(MAP_GROWSDOWN). 다른 스레드: 고정 mmap | 예약된 범위 내에서 가드 페이지를 만나면 한 페이지씩 커밋 확장 |
| 오버플로 감지 | 가드 영역 아래 접근 → SIGSEGV. 시그널 핸들러에 `sigaltstack` 필요 | 가드 페이지 → `STATUS_GUARD_PAGE_VIOLATION`, 마지막 페이지 → `STATUS_STACK_OVERFLOW` 예외. SEH로 잡을 수 있으나 복구는 어려움 |
| 깊은 재귀의 위험 | 8MB라 상대적으로 여유 | 1MB라 리눅스에서 돌던 재귀 코드가 Windows에서만 터지는 경우가 있음 |

마지막 행은 이식 시 실제로 자주 만나는 문제다. 특히 Python(재귀 한도 1000이 1MB 스택 기준으로 정해짐), Rust(테스트 스레드 스택이 작아 Windows에서 먼저 오버플로), 재귀 하강 파서가 영향을 받는다.

## 3.9 큰 페이지(Huge Pages / Large Pages)

TLB 미스를 줄이기 위해 2MB(또는 1GB) 페이지를 쓰는 기능이다. 데이터베이스와 JVM에서 주로 쓴다.

**리눅스**: 두 가지 경로가 있다.
- **HugeTLB**: 부팅 시 또는 `/proc/sys/vm/nr_hugepages`로 미리 예약. `mmap(MAP_HUGETLB)` 또는 `hugetlbfs` 마운트. 확정적이지만 유연성이 없다.
- **THP(Transparent Huge Pages)**: 커널이 자동으로 4KB 페이지를 2MB로 합친다. `always`/`madvise`/`never` 설정. `khugepaged`가 백그라운드로 합친다. 편리하지만 지연 시간이 튈 수 있어 Redis, MongoDB는 끄기를 권장한다.

**Windows**: `VirtualAlloc(MEM_LARGE_PAGES)`. 호출자에게 `SeLockMemoryPrivilege`(메모리 페이지 잠금 권한)가 필요하고 기본적으로 관리자에게도 없어서 로컬 보안 정책에서 부여해야 한다. 큰 페이지는 항상 잠기며(스왑 불가), 연속된 물리 메모리를 찾아야 하므로 부팅 후 시간이 지나면 실패율이 올라간다. 투명한 자동 병합은 없다.

## 3.10 NUMA

멀티 소켓 서버에서 CPU마다 가까운 메모리가 다르다.

- **리눅스**: `numactl`, `mbind`, `set_mempolicy`, `libnuma`. 기본 정책은 "폴트를 일으킨 CPU의 노드에 할당"(first-touch). `/sys/devices/system/node/`에 토폴로지가 노출된다.
- **Windows**: `VirtualAllocExNuma`, `GetNumaHighestNodeNumber`, `GetNumaProcessorNode`. 기본 정책도 first-touch에 가깝다("ideal node"). 스레드의 ideal processor와 연동된다.

개념은 같고 API 이름만 다르다. 크로스 플랫폼 코드에서는 hwloc 같은 라이브러리로 추상화한다.

## 3.11 이식할 때 부딪히는 문제

1. **"크게 잡고 안 쓰면 공짜" 가정**: 리눅스에서 `malloc(16GB)`로 희소 배열을 만들던 코드는 Windows에서 커밋 실패한다. `VirtualAlloc(MEM_RESERVE)` 후 필요한 부분만 `MEM_COMMIT`하도록 바꾸거나, 리눅스에서도 `mmap(PROT_NONE)` + `mprotect`로 명시적 커밋 패턴을 써서 두 OS를 통일한다.
2. **할당 실패 처리 부재**: 리눅스에서는 `malloc` 반환값을 안 보는 습관이 통하지만 Windows에서는 실제로 `NULL`이 온다. 최소한 치명 에러로 즉시 종료하는 경로는 있어야 한다.
3. **스택 크기**: 깊은 재귀나 큰 지역 배열(`char buf[2 * 1024 * 1024]`)이 Windows 1MB 스택에서 터진다. 링커 옵션 또는 스레드 생성 시 스택 크기를 늘리거나 힙으로 옮긴다.
4. **RSS를 누수 지표로 사용**: Windows에서는 워킹 셋이 아니라 Private Bytes를 봐야 한다. 리눅스에서는 RSS가 페이지 캐시 매핑을 포함하므로 `smaps`의 `Anonymous`를 본다.
5. **`mmap` 오프셋 정렬**: 4KB 정렬로 파일의 임의 위치를 매핑하던 코드는 Windows에서 64KB 정렬로 바꿔야 한다.
6. **`fork` 기반 COW 스냅샷**: Redis의 BGSAVE처럼 `fork`해서 자식이 스냅샷을 쓰는 패턴은 Windows에 대응물이 없다. 별도 스레드 + 애플리케이션 레벨 COW, 또는 `CreateFileMapping`으로 스냅샷을 직접 구현해야 한다.
7. **여러 CRT 혼용**: Windows에서 DLL 경계를 넘어 `malloc`/`free`를 짝 맞추지 않으면 크래시. 라이브러리가 자기 해제 함수를 제공하거나, 모든 모듈이 같은 동적 CRT(`/MD`)를 쓰도록 한다.
8. **큰 페이지**: 리눅스 THP에 의존하던 성능이 Windows에서는 명시적 권한 설정 없이는 나오지 않는다.

## 3.12 런타임에서는

- **JVM**: 리눅스에서는 `-Xmx`만큼 `mmap`으로 예약하고 커밋은 `-Xms`부터 점진적으로 한다. Windows에서도 `VirtualAlloc(MEM_RESERVE)` 후 커밋하므로 동작이 유사하다. 다만 Windows에서 `-Xmx`를 너무 크게 잡으면 힙이 그만큼 커졌을 때 커밋 실패로 `OutOfMemoryError`가 아니라 JVM 크래시가 날 수 있다. 큰 페이지는 `-XX:+UseLargePages`로 두 OS 모두 지원하지만 Windows에서는 권한 설정이 필요하다.
- **Go**: 리눅스에서는 큰 아레나를 `mmap(PROT_NONE)`으로 예약하고 필요할 때 `mprotect`한다. Windows에서는 `VirtualAlloc(MEM_RESERVE)`/`MEM_COMMIT`을 쓴다. GC가 반납할 때 리눅스는 `madvise(MADV_FREE)`(또는 `DONTNEED`), Windows는 `VirtualFree(MEM_DECOMMIT)`. `GODEBUG=madvdontneed=1`이 리눅스에만 있는 이유다.
- **.NET**: GC 힙은 세그먼트(또는 .NET 7+의 리전)를 `VirtualAlloc`/`mmap`으로 예약한다. Windows에서 `OutOfMemoryException`이 더 자주, 더 일찍 발생하는 경향이 있다. 리눅스에서는 컨테이너 cgroup 한도를 GC가 인식해 힙 상한을 정한다.
- **Node.js (V8)**: V8은 두 OS 모두 예약/커밋을 명시적으로 구분하는 `PageAllocator` 추상화를 쓴다. `--max-old-space-size`는 커밋 상한이다.
- **Python**: `pymalloc`은 256KB 아레나를 `mmap`(리눅스) 또는 `VirtualAlloc`(Windows)으로 잡는다. 큰 객체는 시스템 `malloc`으로 가므로 위의 glibc/NT 힙 차이가 그대로 드러난다. `multiprocessing`의 fork 방식이 Windows에서 spawn으로 바뀌면서 부모 메모리 공유가 없어지는 것이 가장 큰 차이다.
- **Rust**: 기본 할당자는 시스템 `malloc`이다. `#[global_allocator]`로 jemalloc, mimalloc 교체가 두 OS 모두 링크 시점에 가능하다.
