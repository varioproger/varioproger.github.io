# 5장. 컨트롤러 매니저와 컨트롤러 패턴

> **학습목표**
> - Informer의 내부 파이프라인(Reflector → DeltaFIFO → Indexer)을 구성 요소별로 설명할 수 있다.
> - SharedInformerFactory가 왜 캐시를 공유하는지, resync가 무슨 역할을 하는지 안다.
> - workqueue가 키만 저장하고 중복을 제거하며 레이트 리밋하는 내부 동작을 설명할 수 있다.
> - 멱등성과 레벨 트리거 원칙에 따라 조정 함수를 설계할 수 있다.
> - 리더 선출이 Lease와 낙관적 동시성 제어로 구현되는 방식을 안다.
> - ownerReferences 그래프와 파이널라이저로 가비지 컬렉션이 동작하는 원리를 이해한다.

## 들어가며

4장에서 스케줄러 하나의 조정 루프를 자세히 뜯어봤다. `kube-controller-manager`는 그런 루프를 **수십 개** 한 프로세스 안에 돌린다. Deployment, ReplicaSet, Job, Namespace, GC, HPA... 이름은 다 다르지만, 그 안을 열어 보면 거의 예외 없이 같은 뼈대를 쓴다.

```
Informer(로컬 캐시) → 워크큐(키, 중복 제거, 레이트 리밋) → 조정 함수
```

이 장은 이 뼈대를 **자료구조 수준**에서 파헤친다. "컨트롤러를 어떻게 작성하는가"는 8장(client-go 활용)과 10장(오퍼레이터 프레임워크)의 몫이다. 여기서는 그보다 한 겹 아래, **client-go가 이미 만들어 둔 기계 장치**가 어떻게 움직이는지 본다. 이 장을 이해하고 나면 8장의 코드가 "왜 그렇게 짜여 있는지"가 자명해진다.

```bash
kubectl get pods -n kube-system -l component=kube-controller-manager
```

```
NAME                                             READY   STATUS
kube-controller-manager-k8s-guide-control-plane  1/1     Running
```

**이 프로세스 하나 안에 40개가 넘는 컨트롤러 고루틴이 돌고 있다.** 이들이 전부 공유하는 것이 이 장의 주제다.

## 5.1 Informer 내부 자료구조

### 왜 컨트롤러가 API 서버를 직접 호출하지 않는가

가장 단순한 컨트롤러는 이렇게 짤 수 있을 것 같다.

```
반복:
    obj := apiServer.Get(name)
    조정(obj)
    sleep(1초)
```

컨트롤러가 40개, 감시 대상 리소스가 각각 다르고, 클러스터에 오브젝트가 수만 개면 이 방식은 API 서버를 순식간에 무너뜨린다. 그래서 client-go는 **Informer**라는 계층을 둔다. Informer의 역할은 단 하나, "API 서버의 특정 리소스 타입 전체를 로컬 메모리에 실시간으로 복제해 둔다"는 것이다. 컨트롤러는 그 복제본만 읽는다.

Informer는 하나의 부품이 아니라 파이프라인이다.

```
┌───────────────────────────────────────────────────────────────────┐
│                          SharedInformer                            │
│                                                                     │
│   apiserver                                                        │
│      │  List (초기 전체 목록)                                        │
│      │  Watch (이후 변경분)                                          │
│      ▼                                                              │
│  ┌───────────┐        Delta{Added,   obj}                          │
│  │ Reflector │  ───▶  Delta{Updated, obj}   ┌───────────────┐      │
│  └───────────┘        Delta{Deleted, obj}   │   DeltaFIFO   │      │
│                        Delta{Sync,    obj} ─▶│  (키별 큐)    │      │
│                                              └───────┬───────┘      │
│                                                      │ Pop()        │
│                                                      ▼              │
│                                          ┌────────────────────┐    │
│                                          │  처리 루프 (내부)     │    │
│                                          │  1) Indexer 갱신     │    │
│                                          │  2) 이벤트 핸들러 호출 │    │
│                                          └──────────┬─────────┘    │
│                                                      │              │
│                              ┌───────────────────────┼──────┐       │
│                              ▼                       ▼      │       │
│                     ┌─────────────────┐   ┌───────────────┐│       │
│                     │ Indexer (Store) │   │ 이벤트 핸들러들 ││       │
│                     │  = 로컬 캐시     │   │ OnAdd/OnUpdate ││       │
│                     └─────────────────┘   │ OnDelete       ││       │
│                                            └───────┬───────┘│       │
└────────────────────────────────────────────────────┼────────┘       │
                                                       ▼               │
                                              워크큐에 키를 넣는다        │
                                              (namespace/name)         │
```

네 부분을 순서대로 뜯어본다.

### Reflector — List와 Watch를 캡슐화

**Reflector**는 정확히 한 가지 리소스 타입에 대해 `ListerWatcher` 인터페이스(`List()`, `Watch()`)를 반복 호출한다.

```go
// client-go/tools/cache 패키지의 개념적 구조
type ListerWatcher interface {
    List(options metav1.ListOptions) (runtime.Object, error)
    Watch(options metav1.ListOptions) (watch.Interface, error)
}
```

동작 순서는 2장에서 본 watch cache의 클라이언트 쪽 대응이다.

```
① List() 로 현재 전체 상태를 받는다 → resourceVersion을 기억
② Watch(resourceVersion=그 값) 로 그 이후 변경분을 스트리밍으로 받는다
③ 이벤트마다 DeltaFIFO에 Delta를 넣는다
④ watch 연결이 끊기면 마지막 resourceVersion부터 재접속
⑤ 410 Gone (2장 참고) 을 받으면 → 처음부터 다시 List (relist)
```

**Reflector가 바로 "Informer가 410 Gone을 자동으로 처리한다"고 2장에서 예고한 그 코드다.** relist는 비용이 크므로(전체 목록 재전송) Bookmark 이벤트가 이를 줄여 준다는 것도 2장에서 다뤘다.

### DeltaFIFO — 순서 있는 변경 큐

Reflector가 받은 이벤트는 바로 캐시에 반영되지 않는다. 먼저 **DeltaFIFO**에 쌓인다. DeltaFIFO는 이름 그대로 두 가지의 조합이다.

- **Delta**: `{Type, Object}` 쌍. `Type`은 `Added` / `Updated` / `Deleted` / `Replaced`(relist 결과) / `Sync`(주기적 재동기화, 5.2절) 중 하나.
- **FIFO**: 키(기본적으로 `namespace/name`, `MetaNamespaceKeyFunc`)별로 **Deltas 슬라이스**를 들고 있는 큐. 같은 키에 이벤트가 연달아 오면 같은 슬라이스에 추가된다.

```
키 "default/web-7f9c" 에 대한 Deltas:
  [ {Added, web-7f9c v1} ]
       │ (Update 이벤트 도착)
       ▼
  [ {Added, web-7f9c v1}, {Updated, web-7f9c v2} ]
```

**왜 여러 개를 쌓아 두는가?** 처리 루프가 느려서 한 키에 이벤트가 여러 번 밀려도, **소비할 때 최신 것부터 순서대로** 처리할 수 있어야 하기 때문이다. 다만 `Deleted` 뒤에 다시 `Added`가 오는 등 압축 가능한 경우 내부적으로 정리된다.

처리 루프는 `Pop()`으로 키 하나(의 전체 Deltas)를 꺼내 순서대로 처리하고, 그 결과로 Indexer를 갱신한 뒤 등록된 이벤트 핸들러를 호출한다. **이 처리 루프가 끝나야 다음 키를 꺼낸다** — 즉 Informer 내부 처리는 단일 고루틴 직렬 처리다. 이벤트 핸들러 안에서 무거운 작업을 하면 안 되는 이유가 여기 있다(그래서 핸들러는 보통 워크큐에 키만 넣고 즉시 반환한다).

### Indexer — 스레드 세이프 로컬 캐시

**Indexer**(내부적으로 `ThreadSafeStore`)가 바로 "컨트롤러가 실제로 읽는" 캐시다. 오브젝트를 키(`namespace/name`)로 저장할 뿐 아니라, **커스텀 인덱스 함수**로 보조 인덱스를 만들 수 있다.

```go
// 예: Pod를 nodeName으로 빠르게 찾기 위한 인덱스
func nodeNameIndexFunc(obj interface{}) ([]string, error) {
    pod := obj.(*v1.Pod)
    return []string{pod.Spec.NodeName}, nil
}

indexer.AddIndexers(cache.Indexers{
    "byNode": nodeNameIndexFunc,
})

// 조회: "이 노드에 스케줄된 Pod 전부" — 전체 스캔 없이 O(1)에 가깝다
pods, err := indexer.ByIndex("byNode", "k8s-guide-worker")
```

kube-controller-manager 내부의 여러 컨트롤러가 정확히 이런 인덱스를 쓴다. 예를 들어 endpointslice 컨트롤러는 Service의 셀렉터에 맞는 Pod를 매번 전체 스캔하지 않고 네임스페이스 인덱스로 좁힌 뒤 라벨을 비교한다.

**타입별로 얇게 감싼 것이 Lister다.** `PodLister`, `DeploymentLister` 같은 코드 생성 타입은 내부적으로 Indexer를 호출할 뿐이며, **항상 로컬 캐시에서 읽고 API 서버에 절대 접근하지 않는다.** 8장에서 이 Lister를 직접 사용하는 코드를 본다.

> **자료구조 요약**
>
> | 구성 요소 | 역할 | 스레드 |
> |---|---|---|
> | Reflector | apiserver List+Watch → DeltaFIFO에 적재 | 전용 고루틴 1개 |
> | DeltaFIFO | 키별 순서 있는 변경 이력 큐 | Reflector가 쓰고, 처리 루프가 읽음 |
> | Indexer | 스레드 세이프 로컬 캐시 + 보조 인덱스 | 다수의 리더 고루틴이 동시 접근 |
> | Lister | Indexer를 감싼 타입 세이프 읽기 API | - |
> | 이벤트 핸들러 | Delta 처리 후 호출됨. 보통 워크큐에 키만 넣음 | - |

## 5.2 SharedInformerFactory와 캐시 공유

### 문제 — 컨트롤러 40개가 각자 watch를 열면

Deployment 컨트롤러도 Pod를 보고, ReplicaSet 컨트롤러도 Pod를 보고, HPA 컨트롤러도 Pod를 보고, 가비지 컬렉터도 Pod를 본다. 각자가 **독립적인 Reflector**를 만들어 Pod 리소스에 watch를 연다면?

```
컨트롤러 A ─┐
컨트롤러 B ─┼─ 각자 watch("/api/v1/pods") ──▶ apiserver watch cache
컨트롤러 C ─┤    (같은 데이터를 N번 직렬화해 N번 전송)
컨트롤러 D ─┘
```

같은 클러스터, 같은 Pod 목록인데 N배의 직렬화·네트워크·메모리 비용이 든다. 노드 수가 늘고 컨트롤러가 늘수록 이 낭비는 선형으로 커진다.

### 해결 — 리소스 타입당 Informer 하나

**SharedInformerFactory**는 GVR(GroupVersionResource)마다 **Reflector+DeltaFIFO+Indexer 세트를 정확히 하나만** 만들고, 이를 여러 컨트롤러가 나눠 쓰게 한다.

```go
factory := informers.NewSharedInformerFactory(clientset, 30*time.Second)

podInformer := factory.Core().V1().Pods().Informer()   // 처음 호출 시 생성
// 다른 컨트롤러가 같은 줄을 호출하면 새로 만들지 않고 같은 인스턴스를 돌려준다

deployController.AddEventHandler(...)   // 같은 podInformer에 핸들러만 추가
gcController.AddEventHandler(...)       // 같은 podInformer에 핸들러만 추가

factory.Start(stopCh)                   // 팩토리가 관리하는 모든 Informer를 한 번에 시작
factory.WaitForCacheSync(stopCh)        // 모든 Informer의 초기 List가 끝날 때까지 대기
```

```
                     ┌──────────── SharedInformerFactory ────────────┐
                     │                                                │
apiserver ──watch──▶ │  Pod Informer (Reflector+DeltaFIFO+Indexer) 1개│
                     │        │                                       │
                     │        ▼ sharedProcessor (fan-out)             │
                     │   ┌────┴────┬─────────┬─────────┐              │
                     │   ▼         ▼         ▼         ▼              │
                     │ Deploy   ReplicaSet  HPA       GC              │
                     │ 핸들러    핸들러      핸들러     핸들러           │
                     └────────────────────────────────────────────────┘
```

내부적으로 이 fan-out은 **`sharedProcessor`**가 담당한다. 각 컨트롤러가 등록한 핸들러마다 `processorListener`가 하나씩 생기고, 각각 자기 버퍼 채널과 자기 고루틴을 갖는다. 그래서 **핸들러 하나가 느려도 다른 핸들러들이 즉시 막히지는 않는다**(버퍼가 다 차면 결국 영향을 주지만, 완전한 순차 결합보다는 훨씬 낫다). Indexer는 하나뿐이므로 모든 컨트롤러가 **완전히 동일한 캐시 스냅숏**을 본다.

### resync — 왜 아무것도 안 바뀌었는데 다시 알려주는가

`NewSharedInformerFactory(clientset, 30*time.Second)`의 두 번째 인자가 **resync 주기**다. 이 주기마다 Informer는 Indexer에 있는 **모든 오브젝트**를 다시 한번 DeltaFIFO에 `Sync` 타입 Delta로 넣고, 이벤트 핸들러(`OnUpdate`)를 재호출한다. **API 서버에 다시 요청을 보내는 것이 아니다** — 이미 로컬에 있는 캐시 내용을 재생(replay)하는 것뿐이다.

**왜 필요한가?** watch 이벤트는 이론적으로 유실될 수 있고(네트워크 단절, 컨트롤러 재시작 사이의 짧은 간극 등), 조정 함수 자체에 버그가 있어 상태를 놓쳤을 수도 있다. resync는 "무슨 일이 있었는지"와 무관하게 **주기적으로 전체를 다시 검토**하게 강제하는 안전망이다. 5.4절에서 다룰 레벨 트리거 원칙의 구현체가 바로 이 resync다.

**컨트롤러가 여러 개면 resync 주기도 각자 다르게 설정할 수 있다.** 일부 컨트롤러는 30초, 일부는 아예 0(비활성화)으로 둔다. 잦은 resync는 안전하지만 조정 함수가 무거우면 CPU를 소모하므로 트레이드오프가 있다.

> **`WaitForCacheSync`를 기다리지 않으면 생기는 일**
>
> 컨트롤러가 시작 직후 캐시가 채워지기 전에 조정을 시작하면, Lister가 빈 결과를 돌려준다. "리소스가 아직 없다"고 오판해 불필요한 생성 요청을 보낼 수 있다. **모든 표준 컨트롤러는 초기 List가 끝날 때까지 조정을 미룬다.** 8장에서 `WaitForCacheSync`를 직접 호출하는 코드를 다룬다.

## 5.3 Workqueue 내부

### 왜 오브젝트가 아니라 키만 넣는가

이벤트 핸들러가 워크큐에 넣는 것은 오브젝트 전체가 아니라 **`namespace/name` 문자열 하나**다.

```go
func (c *Controller) onUpdate(oldObj, newObj interface{}) {
    key, _ := cache.MetaNamespaceKeyFunc(newObj)
    c.workqueue.Add(key)   // 오브젝트가 아니라 키
}
```

이유는 두 가지다.

1. **최신성**: 큐에 오브젝트를 넣으면, 워커가 그것을 꺼내 처리할 때쯤엔 이미 낡은 버전일 수 있다. 키만 넣고, 처리 시점에 **Indexer에서 다시 읽으면** 항상 최신 캐시 상태로 조정한다.
2. **자연스러운 중복 제거**: 같은 오브젝트가 1초에 100번 바뀌어도, 큐에는 같은 키가 계속 들어오려 하지만 뒤에서 볼 것처럼 이미 있으면 무시된다. 조정은 한 번(혹은 소수 번)만 일어난다.

### `Type`(기본 큐)의 내부 — dirty/processing 두 집합

`workqueue.Interface`의 기본 구현은 슬라이스 하나가 아니라 **집합 두 개 + 큐 하나**로 되어 있다.

```
type Type struct {
    queue      []t              // 처리 순서 (FIFO)
    dirty      set[t]           // "다시 봐야 할" 항목들
    processing set[t]           // "지금 워커가 처리 중"인 항목들
}
```

```
Add(key):
    if key in processing:
        dirty.add(key)              # 처리 중인데 또 바뀜 → 끝나면 다시 하도록 표시만
        return
    if key in dirty:
        return                      # 이미 대기 중 → 중복 추가 안 함  ★ 핵심
    dirty.add(key)
    queue.append(key)

Get() -> key:
    key = queue.pop_front()
    processing.add(key)
    dirty.remove(key)
    return key

Done(key):
    processing.remove(key)
    if key in dirty:                # 처리하는 동안 또 이벤트가 왔었다면
        queue.append(key)           # 즉시 다시 큐에 넣는다
        dirty.add(key)
```

이 상태 전이가 **동시 처리 중 유실 없이, 그러나 중복 없이** 이벤트를 흡수하는 전부다. 워커가 키 X를 처리하는 도중에 X가 다시 바뀌면, 그 사실은 `dirty` 플래그로만 기록되고 `Done(X)` 호출 시점에 큐로 되돌아간다 — **한 번 더 조정될 뿐, 큐에 X가 세 개, 네 개 쌓이는 일은 없다.**

### 레이트 리미터 — 실패한 키를 어떻게 늦추는가

성공적으로 처리된 항목은 `Forget(key)`를 호출해 실패 카운트를 지운다. 실패한 항목은 즉시 재시도하지 않고 `AddRateLimited(key)`로 지연시켜 넣는다.

```go
queue.AddRateLimited(key)     // 실패 → 지연 후 재추가
// ...
queue.Forget(key)             // 성공 → 실패 카운트 초기화
queue.NumRequeues(key)        // 지금까지 몇 번 재시도했는지
```

`AddRateLimited`가 계산하는 지연 시간은 **레이트 리미터 조합**이 결정한다.

| 레이트 리미터 | 알고리즘 |
|---|---|
| `ItemExponentialFailureRateLimiter` | 키별 실패 횟수(`NumRequeues`)에 따라 `baseDelay × 2^실패횟수`, `maxDelay`로 상한 |
| `BucketRateLimiter` | 토큰 버킷(`golang.org/x/time/rate`) — 키와 무관하게 **전체 처리 속도**의 상한을 건다 |
| `ItemFastSlowRateLimiter` | 초반 N회는 짧은 지연, 이후는 긴 지연으로 전환 |
| `MaxOfRateLimiter` | 여러 리미터의 지연 시간 중 **가장 큰 값**을 채택 |

기본 컨트롤러 레이트 리미터는 지수 백오프와 전역 토큰 버킷을 **`MaxOf`로 합친 것**이다.

```go
workqueue.DefaultControllerRateLimiter()
// = MaxOfRateLimiter(
//     ItemExponentialFailureRateLimiter(5ms, 1000s),  // 개별 키: 5ms → ... → 최대 1000초
//     BucketRateLimiter(10 QPS, burst 100),            // 전체: 초당 10개, 버스트 100개
//   )
```

```
키 X 처리 실패 이력:
  1회 실패 → 5ms 후 재시도
  2회 실패 → 10ms
  3회 실패 → 20ms
  ...
  10회 실패 → 약 2.5s
  ...
  충분히 실패 누적 → 상한 1000s에서 유지
성공 → Forget(X) → 카운터 0으로 초기화
```

**영구적으로 실패하는 키(예: 존재할 수 없는 이미지 참조)가 CPU와 API 서버 요청을 무한정 소모하지 않는 이유가 이것이다.** 반대로 일시적 오류(네트워크 순단)는 몇 초 내에 회복돼 빠르게 재시도된다.

> **`AddAfter`와의 차이**
> `AddRateLimited`는 실패 이력에 기반한 지연이고, `AddAfter(key, duration)`는 "이 시간이 지나면 무조건 다시 봐라"는 명시적 예약이다. 예를 들어 인증서 만료 30일 전에 갱신하는 컨트롤러는 만료 시각을 계산해 `AddAfter`로 예약해 둔다. 둘 다 동일한 dirty/processing 중복 제거 규칙을 따른다.

## 5.4 조정 함수 설계 원칙

### 멱등성 — 같은 조정을 두 번 실행해도 결과가 같아야 한다

레이트 리밋 재시도, resync, 워커 재시작 등 온갖 이유로 **같은 키가 여러 번 조정될 수 있다.** 조정 함수 내부에서 "생성"을 무조건 실행하면 두 번째 실행에서 중복 생성 에러가 난다.

```go
// 나쁜 예 — 두 번째 호출에서 실패한다
func reconcile(key string) error {
    return apiClient.Create(&v1.Pod{...})
}

// 좋은 예 — 이미 있으면 통과
func reconcile(key string) error {
    _, err := lister.Pods(ns).Get(name)
    if err == nil {
        return nil            // 이미 존재 — 할 일 없음
    }
    if !errors.IsNotFound(err) {
        return err
    }
    _, err = apiClient.Create(&v1.Pod{...})
    return err
}
```

### 레벨 트리거 vs 엣지 트리거

**엣지 트리거**는 "무엇이 바뀌었는가"라는 **이벤트**에 반응한다. "Pod가 삭제됐다"는 이벤트를 놓치면, 그 사실을 영영 알 수 없다.

**레벨 트리거**는 "지금 상태가 어떠한가"라는 **현재 값**을 본다. 이벤트를 몇 개를 놓치든, 다음 조정에서 현재 상태를 다시 관찰하면 스스로 바로잡힌다.

형식적으로 적으면 이렇다.

```
엣지 트리거:  f(event) → action
레벨 트리거:  f(observe(현재 상태), desired) → action
```

예를 들어 ReplicaSet 컨트롤러의 조정 함수는 "Pod가 삭제됐다"는 이벤트 자체를 처리 로직에 담지 않는다. 대신 이렇게 판단한다.

```go
func reconcile(rsKey string) error {
    rs, err := rsLister.Get(rsKey)
    if errors.IsNotFound(err) {
        return nil
    }
    pods, _ := podLister.List(labelSelectorFrom(rs))
    diff := len(pods) - int(*rs.Spec.Replicas)

    switch {
    case diff < 0:
        createPods(-diff)   // 부족 — 만든다
    case diff > 0:
        deletePods(diff)    // 초과 — 지운다
    }
    return nil   // diff == 0 이면 아무것도 안 한다
}
```

Pod가 어떤 이유로 삭제되었는지(사람이 지웠는지, 노드가 죽었는지, 축출됐는지)는 **중요하지 않다.** 지금 개수가 desired보다 적다는 사실만 본다. **이벤트 핸들러의 역할은 오직 "이 키를 다시 봐야 할 수도 있다"고 워크큐에 알리는 트리거일 뿐, 조정 로직 자체는 항상 현재 상태 전체를 다시 계산한다.** 이것이 "쿠버네티스는 이벤트 유실에 강하다"는 말의 정확한 의미다.

### 캐시에서 읽고, status만 쓴다

| 원칙 | 이유 |
|---|---|
| 읽기는 Lister(캐시)에서 | API 서버 직접 호출은 부하와 지연을 유발한다. 캐시는 최대 resync 주기만큼만 오래될 수 있고, 그마저 watch로 대개 즉시 갱신된다 |
| 쓰기는 실제로 바뀔 때만 | `status`가 이미 desired와 같으면 업데이트를 생략한다. 불필요한 쓰기는 `resourceVersion`을 올리고 이는 다시 watch 이벤트로 다른 컨트롤러들에 전파되어 **연쇄적인 조정 폭풍**을 유발할 수 있다 |
| `spec`은 건드리지 않는다 | `spec`은 사용자(또는 상위 컨트롤러)의 의도다. 컨트롤러는 `status` 서브리소스만 쓴다 |
| 충돌은 재시도로 처리 | `status` 업데이트가 `resourceVersion` 충돌(409 Conflict)로 실패하면, 최신 버전을 다시 읽어 재계산 후 재시도한다. 이것도 낙관적 동시성 제어의 응용이다 |

```go
func reconcile(key string) error {
    obj, err := lister.Get(key)          // ① 캐시에서 읽기
    if errors.IsNotFound(err) {
        return nil                        // 삭제됨 — GC가 정리(5.6절)
    }

    desired := computeDesiredStatus(obj)  // ② 원하는 상태 계산
    if reflect.DeepEqual(obj.Status, desired) {
        return nil                        // ③ 이미 일치 — 쓰기 생략
    }

    updated := obj.DeepCopy()
    updated.Status = desired
    _, err = client.UpdateStatus(updated) // ④ status만, 실제로 다를 때만
    return err
}
```

## 5.5 리더 선출 내부

### 왜 필요한가

HA 구성에서는 `kube-controller-manager`와 `kube-scheduler`가 여러 인스턴스로 뜬다. 모두 동시에 조정하면 같은 ReplicaSet에 대해 여러 프로세스가 각자 "Pod가 부족하다"고 판단해 Pod를 중복 생성할 수 있다. **한 번에 정확히 하나만 활성(active)이어야 한다.**

### Lease 오브젝트와 낙관적 동시성

```bash
kubectl get lease -n kube-system kube-controller-manager -o yaml
```

```yaml
apiVersion: coordination.k8s.io/v1
kind: Lease
metadata:
  name: kube-controller-manager
  namespace: kube-system
spec:
  holderIdentity: k8s-guide-control-plane_a1b2c3d4
  leaseDurationSeconds: 15
  acquireTime: "2026-09-01T10:00:00.000000Z"
  renewTime: "2026-09-01T10:24:03.000000Z"
  leaseTransitions: 1
```

client-go의 `leaderelection` 패키지가 구현하는 `tryAcquireOrRenew` 루프는 대략 이렇다.

```
매 retryPeriod(기본 2초)마다:
    lease := get(Lease)

    if lease가 없다:
        create(Lease{holderIdentity: 나, ...})  → 성공하면 리더

    else if lease.holderIdentity == 나:
        lease.renewTime = now()
        update(lease)                             → 리더 유지(갱신)

    else if now() - lease.renewTime > leaseDurationSeconds:
        # 기존 리더가 죽었거나 갱신에 실패한 것으로 간주
        lease.holderIdentity = 나
        lease.leaseTransitions += 1
        update(lease)   ← resourceVersion이 그 사이 바뀌었으면 충돌 → 실패
        성공하면 리더가 된다

    else:
        # 유효한 다른 리더가 있음 — 대기
```

**핵심은 `update(lease)`의 낙관적 동시성 제어다.** 여러 대기자가 동시에 리더가 되려고 시도해도, `resourceVersion`이 기대값과 다르면 API 서버가 그 쓰기를 거부한다(4장·2장에서 다룬 등록 규칙과 동일). 즉 **동시에 여러 대기자가 경합해도 정확히 하나만 성공한다** — 별도의 분산 락 서비스 없이 etcd/API 서버의 낙관적 동시성만으로 리더 선출이 완성된다.

리더 쪽에서는 별도로 **`renewDeadline`(기본 10초)** 안에 갱신에 성공하지 못하면 **스스로 리더십을 포기하고 프로세스를 종료**한다. 네트워크가 끊긴 리더가 "나는 아직 리더다"라고 착각한 채 조정을 계속하는 상황(split-brain)을 막기 위해서다.

```
--leader-elect=true
--leader-elect-lease-duration=15s   # 이 시간 갱신이 없으면 리더 만료로 간주
--leader-elect-renew-deadline=10s   # 리더가 이 시간 내 갱신 못 하면 스스로 포기
--leader-elect-retry-period=2s      # 대기자가 Lease를 확인하는 주기
```

### 리더 전환 중의 공백

```
리더 프로세스 크래시 (t=0)
        │
        │  기존 리더의 renewTime이 갱신되지 않음
        │  (leaseDurationSeconds = 15초)
        ▼
t=15s   대기자들이 "만료"를 감지, 낙관적 동시성으로 경합
        │
        ▼
t=~15~17s  새 리더가 Lease를 획득, 조정 재개
```

**이 공백 동안 아무도 조정하지 않는다.** 이것이 문제가 되지 않는 이유는 정확히 5.4절의 레벨 트리거 원칙 때문이다 — 새 리더는 이벤트 이력이 아니라 **그 시점의 실제 상태**를 관찰하고 조정하므로, 공백 동안 무슨 일이 있었든 이어서 처리할 수 있다. `leaseDurationSeconds`를 지나치게 짧게 설정하면 일시적인 GC 정지나 네트워크 지연에도 불필요한 리더 전환(`leaseTransitions` 증가)이 발생해 오히려 불안정해진다.

**직접 만든 오퍼레이터도 이 패턴이 필요하다.** 10장에서 controller-runtime의 `LeaderElection` 설정을 다룬다.

## 5.6 가비지 컬렉터와 파이널라이저

### ownerReferences 의존 그래프

`garbage-collector` 컨트롤러는 다른 컨트롤러와 조금 다르게 동작한다. 특정 리소스 타입 하나를 조정하는 게 아니라, **거의 모든 리소스 타입에 대해 자체 Informer(GraphBuilder)를 두고 `ownerReferences`만 추출**해 메모리 안에 **의존 그래프**를 유지한다.

```bash
kubectl get replicaset -l app=web -o jsonpath='{.items[0].metadata.ownerReferences}' | jq
```

```json
[
  {
    "apiVersion": "apps/v1",
    "kind": "Deployment",
    "name": "web",
    "uid": "1a2b3c4d-...",
    "controller": true,
    "blockOwnerDeletion": true
  }
]
```

```
Deployment(web)
   └── owns → ReplicaSet(web-7f9c)
                 └── owns → Pod(web-7f9c-abcde)
                 └── owns → Pod(web-7f9c-fghij)
```

소유자가 삭제되면, GC는 그래프를 따라 자식들을 **삭제 대상 워크큐**에 넣는다. 이 워크큐도 5.3절과 같은 dirty/processing 구조를 그대로 쓴다 — GC 역시 "컨트롤러의 공통 패턴"의 인스턴스일 뿐이다.

### 삭제 전파 정책 세 가지

`kubectl delete`나 API 호출 시 `propagationPolicy`로 지정한다.

| 정책 | 동작 |
|---|---|
| **Background**(기본값) | 소유자를 **즉시** 삭제하고, 자식들은 GC가 **비동기로** 나중에 정리한다. API 호출은 빨리 끝나지만 잠시 "소유자 없는 자식"이 존재하는 창이 생긴다 |
| **Foreground** | 소유자에 `foregroundDeletion` 파이널라이저를 걸고, **자식들을 먼저 모두 지운 뒤** 소유자를 지운다. 소유자는 `deletionTimestamp`가 찍힌 채로 남아 있다가 자식이 다 없어져야 실제로 사라진다 |
| **Orphan** | 자식들에서 `ownerReferences`만 제거하고, 소유자만 지운다. 자식은 고아로 남아 계속 존재한다 |

```bash
kubectl delete deployment web --cascade=orphan     # Orphan
kubectl delete deployment web --cascade=foreground  # Foreground
kubectl delete deployment web                       # Background (기본)
```

### 파이널라이저 — 삭제를 가로막는 훅

파이널라이저는 `metadata.finalizers`에 담긴 문자열 배열이다. **이 배열이 비어 있지 않으면, API 서버는 etcd에서 오브젝트를 실제로 지우지 않는다.** 대신 `metadata.deletionTimestamp`만 채운다 — 일종의 소프트 삭제 신호다.

```
kubectl delete pvc data-0
        │
        ▼
① API 서버: finalizers가 비어있지 않음
   → deletionTimestamp만 설정, 오브젝트는 etcd에 남아 있음
        ▼
② 관련 컨트롤러가 watch로 deletionTimestamp != nil을 감지
   → 정리 작업 수행 (예: 이 PVC를 쓰던 볼륨을 detach)
        ▼
③ 정리가 끝나면 컨트롤러가 자신의 파이널라이저 문자열을 제거
   → 배열이 비면 API 서버가 실제로 삭제 완료
```

```bash
kubectl get pvc data-0 -o jsonpath='{.metadata.finalizers}'
```

```
["kubernetes.io/pvc-protection"]
```

```bash
kubectl get namespace terminating-ns -o jsonpath='{.spec.finalizers}'
```

```
["kubernetes"]
```

**파이널라이저가 제거되지 않으면 오브젝트는 `Terminating` 상태로 영원히 남는다.** 흔한 원인은 파이널라이저를 등록한 컨트롤러가 죽었거나, 그 컨트롤러의 정리 로직이 실패를 반복하는 경우다. 직접 만든 CRD/오퍼레이터에 파이널라이저를 쓸 때 가장 많이 발생하는 실수이기도 하다(10장·11장에서 다시 다룬다).

### 고아 탐지

GraphBuilder는 `ownerReferences`가 가리키는 UID가 실제로 존재하는지도 주기적으로 확인한다. 소유자가 이미 삭제됐는데(예: 캐시 동기화 틈에 이벤트를 놓쳐) 자식에 여전히 참조가 남아 있으면, GC가 이를 **고아**로 판단해 `ownerReferences`를 제거하거나(참조가 애초에 `blockOwnerDeletion: false`였다면) 정리한다. `absentOwnerCache`라는 짧은 TTL 캐시로 "방금 확인했는데 없었다"는 조회 결과를 잠깐 기억해 반복 조회를 줄인다.

## 실습: 워크큐와 파이널라이저 관찰

**① 조정 활동을 로그로 관찰**

```bash
docker exec k8s-guide-control-plane bash -c \

sleep 20
```

다른 터미널에서 스케일 조정을 발생시킨다.

```bash
kubectl scale deployment wq-demo --replicas=1
```

로그에서 ReplicaSet 컨트롤러가 `diff`를 계산해 Pod를 만들고 지우는 조정 호출이 반복적으로 보인다. 원복한다.

```bash
docker exec k8s-guide-control-plane bash -c \
  "sed -i 's/- --v=4/- --v=2/' /etc/kubernetes/manifests/kube-controller-manager.yaml"
```

**② 워크큐 깊이 메트릭 관찰**

```bash
kubectl get --raw /metrics | grep 'workqueue_depth{' | grep -i replicaset
```

```bash
# 부하를 걸며 관찰
for i in $(seq 1 20); do kubectl scale deployment wq-demo --replicas=$((RANDOM % 5 + 1)); done
kubectl get --raw /metrics | grep -E 'workqueue_(depth|adds_total|queue_duration)' | grep -i replicaset
```

`workqueue_adds_total`은 계속 증가하지만(모든 Add 시도를 카운트), `workqueue_depth`는 대개 낮게 유지되는 것을 확인한다 — 중복 제거 덕분이다.

**③ 파이널라이저로 삭제가 막히는 것 관찰**

```bash
kubectl create namespace finalizer-demo
kubectl -n finalizer-demo apply -f - <<'EOF'
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data-demo
spec:
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 1Gi
EOF

kubectl get pvc data-demo -n finalizer-demo -o jsonpath='{.metadata.finalizers}'
# ["kubernetes.io/pvc-protection"]
```

이 PVC를 사용하는 Pod를 띄운 채로 삭제를 시도하면 `Terminating`에 머무는 것을 볼 수 있다.

```bash
kubectl -n finalizer-demo run consumer --image=busybox --restart=Never \
  --overrides='{"spec":{"volumes":[{"name":"v","persistentVolumeClaim":{"claimName":"data-demo"}}],"containers":[{"name":"c","image":"busybox","command":["sleep","3600"],"volumeMounts":[{"name":"v","mountPath":"/data"}]}]}}'

kubectl delete pvc data-demo -n finalizer-demo --wait=false
kubectl get pvc data-demo -n finalizer-demo
# STATUS: Terminating  (Pod가 쓰는 동안 pvc-protection 파이널라이저가 삭제를 막는다)

kubectl delete pod consumer -n finalizer-demo --now
sleep 5
kubectl get pvc data-demo -n finalizer-demo
# 사라짐 — Pod가 없어지자 파이널라이저가 제거되고 실제 삭제가 완료됨
```


## 실습 과제

**과제 1 — 중복 제거 직접 확인**
`kube-controller-manager`의 `-v=4` 로그를 켠 상태에서 같은 Deployment를 1초 안에 여러 번 스케일 조정(`replicas=3` → `5` → `2` → `4`)한 뒤, 실제로 몇 번의 조정 로그가 찍히는지 세어 본다. 요청 횟수보다 조정 횟수가 적게 나오는 이유를 워크큐의 dirty 집합으로 설명한다.

**과제 2 — 레벨 트리거 검증**
`kube-controller-manager` 컨테이너를 30초간 정지시킨 뒤 그동안 Pod를 여러 개 수동으로 삭제한다. 컨트롤러가 복귀했을 때 이벤트를 하나도 받지 못했음에도 올바른 개수로 복구되는 것을 확인한다.

```bash
docker exec k8s-guide-control-plane crictl stop \
  $(docker exec k8s-guide-control-plane crictl ps -q --name kube-controller-manager)
```

**과제 3 — 리더 선출 강제 전환**
`kube-controller-manager`의 Lease를 관찰하며(`kubectl get lease kube-controller-manager -n kube-system -w`) 컨테이너를 강제 종료해 `leaseTransitions`가 증가하는 시점과 `renewTime`이 멈췄다가 갱신되기까지 걸리는 시간을 측정한다. `leaseDurationSeconds`와 비교한다.

**과제 4 — Foreground 삭제 관찰**
자식 Pod가 여러 개인 Deployment를 `--cascade=foreground`로 삭제하며 Deployment 오브젝트 자체가 `deletionTimestamp`를 가진 채 잠시 남아 있는 것을 `kubectl get deployment <name> -o yaml`로 관찰한다.

**과제 5 — 레이트 리미터 관찰**
존재하지 않는 이미지 레지스트리를 참조하는 Pod를 계속 실패하게 만들고(`ImagePullBackOff`), `kubectl describe pod`의 이벤트에서 재시도 간격이 지수적으로 늘어나는 것을 관찰한다. 이것이 kubelet 쪽의 워크큐/백오프이지만 5.3절과 같은 원리임을 확인한다.

## 요약

- **Informer 파이프라인**은 `Reflector`(apiserver List+Watch) → `DeltaFIFO`(키별 순서 있는 변경 큐) → 처리 루프가 `Indexer`(로컬 캐시) 갱신과 이벤트 핸들러 호출을 수행하는 구조다. Lister는 항상 이 로컬 캐시만 읽는다.
- **SharedInformerFactory**는 리소스 타입당 Informer를 정확히 하나만 만들어 여러 컨트롤러가 `sharedProcessor`를 통해 공유한다. **resync**는 API를 다시 호출하지 않고 로컬 캐시를 주기적으로 재생해 이벤트 유실에 대한 안전망을 제공한다.
- **워크큐에는 키만 들어간다.** 내부는 `dirty`/`processing` 두 집합으로 되어 있어 이미 대기 중인 키는 다시 추가되지 않고(중복 제거), 처리 중 재변경은 `Done()` 시점에 자동으로 재큐잉된다.
- **레이트 리미터**는 `ItemExponentialFailureRateLimiter`(키별 지수 백오프)와 `BucketRateLimiter`(전역 토큰 버킷)를 `MaxOf`로 합쳐, 실패가 반복되는 키만 선택적으로 늦춘다. `Forget()`으로 성공 시 카운터를 초기화한다.
- 조정 함수는 **멱등적**이어야 하고 **레벨 트리거**여야 한다 — "무엇이 바뀌었나"가 아니라 "지금 상태가 어떤가"를 본다. 읽기는 캐시에서, 쓰기는 실제로 다를 때만 `status` 서브리소스에만 한다.
- **리더 선출**은 `Lease` 오브젝트와 `resourceVersion` 기반 낙관적 동시성 제어만으로 구현된다. 리더가 죽으면 `leaseDurationSeconds`만큼 공백이 있지만, 레벨 트리거 덕분에 새 리더가 이어서 처리할 수 있다.
- **가비지 컬렉터**는 `ownerReferences`로 의존 그래프를 유지하며 `Background`/`Foreground`/`Orphan` 세 가지 전파 정책으로 삭제를 처리한다. **파이널라이저**는 `deletionTimestamp`만 찍고 실제 삭제를 미루는 훅으로, 컨트롤러가 정리를 끝내고 자신의 파이널라이저를 제거해야 완전히 사라진다.

**다음 장에서는** 1부의 마지막으로, 이 모든 컨트롤 플레인의 결정을 실제 컨테이너로 바꾸는 노드 쪽 삼총사 — kubelet, 컨테이너 런타임, kube-proxy — 를 개괄한다.
