# 11장. 어드미션 웹훅과 정책 프레임워크

> **학습목표**
> - 어드미션 체인에서 Mutating/Validating 웹훅이 정확히 어느 위치에 있는지 설명할 수 있다.
> - `AdmissionReview` 요청/응답 형식을 이해하고 웹훅 핸들러를 구현할 수 있다.
> - `failurePolicy`, `timeoutSeconds`, `sideEffects` 등으로 웹훅의 가용성 위험을 통제할 수 있다.
> - CEL 기반 `ValidatingAdmissionPolicy`로 웹훅 없이 검증을 구현할 수 있다.
> - CEL 기반 `MutatingAdmissionPolicy`로 웹훅 없이 표준적인 변형(mutation)을 구현할 수 있다.
> - OPA/Gatekeeper, Kyverno 같은 정책 엔진과 직접 웹훅을 만드는 것 사이에서 올바른 선택을 할 수 있다.

---

## 들어가며

10장에서 만든 오퍼레이터는 **자신이 소유한 리소스**만 조정했다. 그런데 클러스터 전체에 규칙을 강제하고 싶을 때가 있다. "모든 Pod에 `team` 라벨이 있어야 한다", "`latest` 태그는 금지한다", "특정 네임스페이스의 Deployment는 replica 10개를 넘을 수 없다" 같은 것들이다.

이런 규칙은 리소스가 **API 서버에 저장되기 전에** 검사하거나 고쳐야 한다. 이것이 이 장의 주제인 **어드미션(admission)** 단계다.

2장에서 요청 처리 경로를 다뤘다. 그 파이프라인의 뒷부분을 다시 가져온다.

```
인증 (Authentication)
    ↓
인가 (Authorization)
    ↓
┌──────────────────────────────────────────────┐
│ 어드미션 체인                                    │
│  ① Mutating Admission                         │
│     · 내장 플러그인 (DefaultStorageClass 등)      │
│     · MutatingAdmissionPolicy (CEL)   ← 이 장    │
│     · MutatingAdmissionWebhook       ← 이 장    │
│  ② 스키마 검증 (OpenAPI + CEL, 9장)               │
│  ③ Validating Admission                       │
│     · 내장 플러그인 (ResourceQuota, PSA 등)       │
│     · ValidatingAdmissionPolicy (CEL) ← 이 장   │
│     · ValidatingAdmissionWebhook      ← 이 장   │
└────────────────────┬───────────────────────────┘
                     ▼
                 스토리지 계층 (etcd)
```

**Mutating이 먼저, Validating이 나중이다.** 변형된 결과가 검증을 받는다는 뜻이다. 이 장에서는 웹훅으로 이 체인에 직접 코드를 끼워 넣는 법, 그리고 웹훅 없이 같은 일을 하는 CEL 기반 대안을 다룬다.

## 11.1 어드미션 체인에서의 위치

### 왜 두 단계로 나뉘는가

Mutating이 먼저 실행되는 이유는 단순하다. **사용자가 생략한 값을 채워 넣은 다음에 검증해야, 검증이 의미가 있다.** 예를 들어 웹훅이 `resources.requests`의 기본값을 주입한다면, 그 기본값이 채워진 이후에 "requests가 설정되어 있는가"를 검증해야 한다.

```
CREATE 요청 (Pod, requests 없음)
    │
    ▼
Mutating: 기본 requests 주입 ──→ requests: {cpu: 100m, memory: 128Mi}
    │
    ▼
스키마 검증 (OpenAPI 타입, CEL) — 9장에서 다룬 x-kubernetes-validations
    │
    ▼
Validating: "requests가 있는가?" 검사 ──→ 있음, 통과
    │
    ▼
etcd 저장
```

**Mutating 안에서도 웹훅이 여러 개면 순서가 보장되지 않는다.** 여러 Mutating 웹훅이 같은 필드를 건드리면 예측하기 어려운 결과가 나올 수 있으므로, 서로 겹치지 않는 필드를 다루도록 설계해야 한다.

### 내장 플러그인과 웹훅의 관계

`kube-apiserver`의 `--enable-admission-plugins`로 활성화되는 내장 플러그인(`NamespaceLifecycle`, `LimitRanger`, `ResourceQuota`, `PodSecurity` 등)은 이 장에서 만드는 웹훅과 **같은 체인의 일부**다. 다만 내장 플러그인은 API 서버 프로세스 안에서 실행되므로 네트워크 왕복이 없고, 웹훅은 별도 프로세스(대개 별도 Pod)로 실행되므로 네트워크 호출이 끼어든다. **이 네트워크 호출이 11.3절에서 다룰 위험의 근원이다.**

## 11.2 웹훅 서버 구현

### AdmissionReview 프로토콜

API 서버가 `AdmissionReview`를 POST하고, 웹훅이 같은 타입으로 응답한다. 매우 얇은 프로토콜이라 어떤 언어로도 구현할 수 있다.

**요청**

```json
{
  "apiVersion": "admission.k8s.io/v1",
  "kind": "AdmissionReview",
  "request": {
    "uid": "705ab4f5-6393-11e8-b7cc-42010a800002",
    "kind": {"group": "", "version": "v1", "kind": "Pod"},
    "resource": {"group": "", "version": "v1", "resource": "pods"},
    "namespace": "default",
    "name": "web-abc123",
    "operation": "CREATE",
    "userInfo": {"username": "alice", "groups": ["dev-team"]},
    "object": { "...": "생성하려는 전체 오브젝트" },
    "oldObject": null,
    "dryRun": false
  }
}
```

**응답 — Validating, 허용**

```json
{
  "apiVersion": "admission.k8s.io/v1",
  "kind": "AdmissionReview",
  "response": { "uid": "705ab4f5-6393-11e8-b7cc-42010a800002", "allowed": true }
}
```

**응답 — Validating, 거부**

```json
{
  "response": {
    "uid": "705ab4f5-6393-11e8-b7cc-42010a800002",
    "allowed": false,
    "status": { "code": 403, "message": "team 라벨이 필요합니다" }
  }
}
```

**응답 — Mutating, JSONPatch로 변형**

```json
{
  "response": {
    "uid": "705ab4f5-6393-11e8-b7cc-42010a800002",
    "allowed": true,
    "patchType": "JSONPatch",
    "patch": "W3sib3AiOiJhZGQiLCJwYXRoIjoiL21ldGFkYXRhL2xhYmVscy90ZWFtIiwidmFsdWUiOiJwbGF0Zm9ybSJ9XQ=="
  }
}
```

`patch` 필드는 base64로 인코딩된 JSON Patch(RFC 6902)다. 위 값을 디코딩하면 다음과 같다.

```json
[
  {"op": "add", "path": "/metadata/labels/team", "value": "platform"}
]
```

### Go 핸들러 스케치

controller-runtime의 `webhook/admission` 패키지를 쓰면 디코딩/인코딩과 HTTP 서버 배선을 대신해 준다.

```go
// internal/webhook/pod_defaulter.go
package webhook

import (
    "context"
    "encoding/json"
    "net/http"

    corev1 "k8s.io/api/core/v1"
    "sigs.k8s.io/controller-runtime/pkg/webhook/admission"
)

// +kubebuilder:webhook:path=/mutate-v1-pod,mutating=true,failurePolicy=ignore,sideEffects=None,groups="",resources=pods,verbs=create,versions=v1,name=mpod.example.com,admissionReviewVersions=v1

type PodLabeler struct {
    decoder admission.Decoder
}

func (a *PodLabeler) Handle(ctx context.Context, req admission.Request) admission.Response {
    pod := &corev1.Pod{}
    if err := a.decoder.Decode(req, pod); err != nil {
        return admission.Errored(http.StatusBadRequest, err)
    }

    original, err := json.Marshal(pod)
    if err != nil {
        return admission.Errored(http.StatusInternalServerError, err)
    }

    if pod.Labels == nil {
        pod.Labels = map[string]string{}
    }
    if _, ok := pod.Labels["injected-by"]; !ok {
        pod.Labels["injected-by"] = "pod-labeler-webhook"
    }

    marshaled, err := json.Marshal(pod)
    if err != nil {
        return admission.Errored(http.StatusInternalServerError, err)
    }

    // ★ controller-runtime이 원본과 수정본의 diff를 JSON Patch로 만들어 준다
    return admission.PatchResponseFromRaw(original, marshaled)
}
```

```go
// internal/webhook/pod_validator.go
type PodValidator struct {
    decoder admission.Decoder
}

func (v *PodValidator) Handle(ctx context.Context, req admission.Request) admission.Response {
    pod := &corev1.Pod{}
    if err := v.decoder.Decode(req, pod); err != nil {
        return admission.Errored(http.StatusBadRequest, err)
    }

    if _, ok := pod.Labels["team"]; !ok {
        return admission.Denied("team 라벨이 필요합니다")
    }
    for _, c := range pod.Spec.Containers {
        if c.Image == "" || hasLatestTag(c.Image) {
            return admission.Denied("latest 태그는 허용되지 않습니다: " + c.Image)
        }
    }
    return admission.Allowed("")
}
```

```go
// cmd/main.go
mgr.GetWebhookServer().Register("/mutate-v1-pod",
    &webhook.Admission{Handler: &PodLabeler{decoder: admission.NewDecoder(mgr.GetScheme())}})
mgr.GetWebhookServer().Register("/validate-v1-pod",
    &webhook.Admission{Handler: &PodValidator{decoder: admission.NewDecoder(mgr.GetScheme())}})
```

**경고만 보내고 차단하지 않는 것**도 가능하다. 점진 도입에 유용하다.

```go
return admission.Allowed("").WithWarnings(
    "latest 태그 사용은 v2.0부터 차단될 예정입니다",
)
```

```bash
kubectl apply -f pod.yaml
# Warning: latest 태그 사용은 v2.0부터 차단될 예정입니다
# pod/web created
```

## 11.3 실패 정책, 타임아웃, 사이드 이펙트

> 이 절이 이 장에서 가장 중요하다. **웹훅 서버 하나가 클러스터 전체를 마비시킬 수 있다.**

### failurePolicy — 가용성과 안전성의 트레이드오프

```yaml
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingWebhookConfiguration
metadata:
  name: pod-policy-webhook
webhooks:
  - name: vpod.example.com
    admissionReviewVersions: ["v1"]
    sideEffects: None
    failurePolicy: Fail          # 또는 Ignore
    timeoutSeconds: 5
    matchPolicy: Equivalent
    clientConfig:
      service:
        namespace: policy-system
        name: pod-policy-webhook
        path: /validate-v1-pod
        port: 443
      caBundle: <base64>
    rules:
      - apiGroups: [""]
        apiVersions: ["v1"]
        operations: ["CREATE", "UPDATE"]
        resources: ["pods"]
        scope: Namespaced
    namespaceSelector:
      matchExpressions:
        - key: kubernetes.io/metadata.name
          operator: NotIn
          values: [kube-system, policy-system]
```

| 값 | 웹훅 호출이 실패(타임아웃, 네트워크 오류, 5xx)하면 |
|---|---|
| `Fail` | 요청을 **거부**한다 — 정책이 반드시 지켜져야 할 때 |
| `Ignore` | 요청을 **허용**한다 — 웹훅이 죽어도 클러스터가 계속 동작해야 할 때 |

**실제 사고 시나리오**

```
① failurePolicy: Fail인 웹훅이 Pod 리소스에 적용되어 있다
② 웹훅 서버 Pod가 노드 장애로 함께 죽는다
③ 새 웹훅 Pod를 스케줄링하려면 새 Pod 생성 요청이 필요하다
④ 그 Pod 생성 요청도 같은 웹훅을 거쳐야 한다
⑤ 웹훅이 없으므로 거부된다
⑥ 데드락 — 웹훅을 고치려면 Pod가 필요한데, Pod를 만들려면 웹훅이 필요하다
```

**대비책**

```yaml
# ① 자기 자신의 네임스페이스와 시스템 네임스페이스를 반드시 제외
namespaceSelector:
  matchExpressions:
    - key: kubernetes.io/metadata.name
      operator: NotIn
      values: [kube-system, kube-public, policy-system]

# ② 짧은 타임아웃 — API 서버가 무한정 기다리지 않도록
timeoutSeconds: 5     # 1~30, 기본 10

# ③ 도입 초기에는 Ignore로 시작해 영향을 관찰한 뒤 Fail로 전환
failurePolicy: Ignore
```

웹훅 서버 자체도 다중화한다.

```yaml
spec:
  replicas: 3
  template:
    spec:
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: kubernetes.io/hostname
          whenUnsatisfiable: DoNotSchedule
          labelSelector: { matchLabels: { app: pod-policy-webhook } }
      priorityClassName: system-cluster-critical
```

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: pod-policy-webhook-pdb }
spec:
  minAvailable: 2
  selector: { matchLabels: { app: pod-policy-webhook } }
```

### matchPolicy, objectSelector, namespaceSelector로 범위 좁히기

| 필드 | 역할 |
|---|---|
| `matchPolicy` | `Exact`는 rules에 명시한 버전만 매칭, `Equivalent`(권장)는 동등한 다른 버전 요청도 매칭 |
| `namespaceSelector` | 어떤 네임스페이스에 적용할지 — **자기 자신과 kube-system은 반드시 제외** |
| `objectSelector` | 어떤 라벨의 오브젝트에만 적용할지 — 옵트인 방식으로 사고 반경을 줄인다 |

```yaml
objectSelector:
  matchLabels:
    policy.example.com/enforce: "true"
```

**옵트인 방식**(라벨이 있는 오브젝트만 웹훅을 거침)은 옵트아웃 방식(모든 오브젝트에 적용하고 예외만 제외)보다 안전하다. 새로운 워크로드가 의도치 않게 웹훅에 걸리는 사고를 막는다.

### sideEffects와 dry-run

```yaml
sideEffects: None
```

`sideEffects: None`은 **이 웹훅이 클러스터 밖에 부수 효과를 일으키지 않는다**는 선언이다. 이렇게 선언한 웹훅은 `kubectl apply --dry-run=server`나 `dryRun: true` 요청에도 호출된다. 실제로 부수 효과(외부 시스템에 로그 기록, 카운터 증가 등)가 있는데 `None`으로 잘못 선언하면, dry-run 요청이 **실제 부수 효과를 일으키는** 사고가 난다. 정확히 `Some`으로 선언하면 dry-run에서는 호출되지 않는다.

### 무한 변형 방지

```go
// ❌ 매번 다른 값 — 매 조정마다 오브젝트가 바뀌어 watch 이벤트 재발생
pod.Annotations["mutated-at"] = time.Now().String()

// ✅ 멱등적 — 이미 설정되어 있으면 건드리지 않는다
if _, ok := pod.Labels["injected-by"]; !ok {
    pod.Labels["injected-by"] = "pod-labeler-webhook"
}
```

Mutating 웹훅이 여러 개 등록되어 있을 때 `reinvocationPolicy: IfNeeded`를 쓰면, 다른 웹훅이 오브젝트를 바꾼 뒤 이 웹훅을 다시 호출한다. 이때 웹훅이 멱등하지 않으면 무한 루프가 될 수 있다.

### 지연 문제

**어드미션은 요청 경로 안에 있다.** 웹훅이 200ms 걸리면, 그 리소스에 대한 모든 관련 요청이 200ms씩 느려진다.

```
Deployment 롤아웃으로 Pod 100개를 순차 생성
  × 웹훅 200ms
  = 20초의 추가 지연
```

```bash
kubectl get --raw /metrics | grep apiserver_admission_webhook_admission_duration_seconds | head
```

**대책**: 웹훅 로직을 가볍게 유지하고, 외부 시스템 조회가 필요하면 캐싱하며, `objectSelector`로 대상을 최소화한다.

## 11.4 CEL 기반 ValidatingAdmissionPolicy

### 왜 웹훅의 대안이 필요한가

11.3절에서 본 위험들 — 가용성, 지연, 순환 의존 — 은 모두 **웹훅이 네트워크 호출이라는 사실**에서 나온다. 그런데 검증 로직의 상당수는 사실 단순한 필드 비교("replicas가 10 이하인가", "특정 라벨이 있는가")다. 이런 검증에 매번 네트워크 왕복이 필요할 이유가 없다.

**`ValidatingAdmissionPolicy`**(v1.30+ GA)는 CEL(Common Expression Language) 표현식을 **API 서버 프로세스 안에서** 평가한다. 네트워크 호출이 없으므로 11.3절의 위험이 대부분 사라진다.

```
웹훅 방식                              ValidatingAdmissionPolicy
┌─────────────┐                      ┌─────────────────────┐
│ API 서버      │  HTTP POST          │  API 서버              │
│  → 별도 Pod로  │ ──────────────▶     │   CEL 표현식을 그 자리에서│
│    네트워크 호출 │                    │   프로세스 내에서 평가    │
└─────────────┘                      └─────────────────────┘
     지연/가용성 위험 있음                    네트워크 호출 없음
```

### 정의

```yaml
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: deployment-replica-limit
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
      - apiGroups: ["apps"]
        apiVersions: ["v1"]
        operations: ["CREATE", "UPDATE"]
        resources: ["deployments"]
  validations:
    - expression: "object.spec.replicas <= 10"
      message: "replicas는 10을 초과할 수 없습니다"
    - expression: >
        !has(object.spec.template.spec.containers[0].resources.limits) ||
        has(object.spec.template.spec.containers[0].resources.limits.memory)
      message: "컨테이너에 memory limit이 필요합니다"
      reason: Invalid
```

**바인딩**으로 어떤 네임스페이스/오브젝트에 적용할지 정한다. 정책(규칙)과 바인딩(적용 범위)을 분리해, 같은 정책을 여러 범위에 재사용할 수 있다.

```yaml
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata:
  name: deployment-replica-limit-binding
spec:
  policyName: deployment-replica-limit
  validationActions: ["Deny"]     # Deny | Warn | Audit
  matchResources:
    namespaceSelector:
      matchExpressions:
        - key: kubernetes.io/metadata.name
          operator: NotIn
          values: [kube-system]
```

**파라미터화**도 지원한다. 정책 로직은 그대로 두고, 네임스페이스마다 다른 한도를 적용할 수 있다.

```yaml
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: replica-limit-parametrized
spec:
  paramKind:
    apiVersion: v1
    kind: ConfigMap
  matchConstraints:
    resourceRules:
      - apiGroups: ["apps"]
        apiVersions: ["v1"]
        operations: ["CREATE", "UPDATE"]
        resources: ["deployments"]
  validations:
    - expression: "object.spec.replicas <= int(params.data['maxReplicas'])"
      message: "네임스페이스별 replica 한도를 초과했습니다"
```

```yaml
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata:
  name: replica-limit-team-a
spec:
  policyName: replica-limit-parametrized
  paramRef:
    name: team-a-limits
    namespace: team-a
    parameterNotFoundAction: Deny
  validationActions: ["Deny"]
  matchResources:
    namespaceSelector:
      matchLabels: { team: team-a }
```

### CEL 표현식 예시 모음

```
object.spec.replicas <= 10
object.metadata.labels['team'] != ''
!object.spec.template.spec.containers.exists(c, c.image.endsWith(':latest'))
object.spec.type != 'LoadBalancer' || has(object.metadata.annotations['lb-approved'])
oldObject == null || object.spec.tier == oldObject.spec.tier || object.spec.tier == 'production'
```

`object`는 현재 요청의 오브젝트, `oldObject`는 UPDATE 시 이전 상태, `request`는 `operation`/`userInfo` 등 요청 메타데이터를 노출한다. 다른 리소스를 조회하는 것은 CEL만으로는 불가능하다 — 이것이 CEL의 한계이자 11.6절에서 웹훅/정책 엔진이 여전히 필요한 이유다.

### 웹훅과의 선택 기준

| | ValidatingAdmissionPolicy (CEL) | ValidatingAdmissionWebhook |
|---|---|---|
| 실행 위치 | API 서버 프로세스 내부 | 별도 서버 (네트워크 호출) |
| 지연 | 거의 없음 | 네트워크 왕복만큼 |
| 가용성 위험 | 없음 (API 서버가 살아있으면 항상 동작) | 있음 (11.3절) |
| 다른 리소스 조회 | 불가능 | 가능 |
| 외부 시스템 연동 | 불가능 | 가능 |
| Mutating | 없음 (Validating 전용 — Mutating은 `MutatingAdmissionPolicy`, 11.5절 참고) | 가능 |
| 배포 단위 | YAML 하나 | 서버 구현 + 배포 + 인증서 |

**단순한 필드 검증이라면 CEL을 우선 고려한다.** 웹훅 서버를 만들고, 배포하고, 인증서를 관리하고, 가용성을 지켜야 하는 운영 부담이 통째로 사라지기 때문이다.

## 11.5 CEL 기반 MutatingAdmissionPolicy

### ValidatingAdmissionPolicy와 같은 동기, Mutating에도 적용

11.4절에서 본 동기 — **웹훅은 네트워크 호출이므로 지연·가용성 위험이 따른다** — 는 Validating에만 해당하는 이야기가 아니다. 11.2절의 `PodLabeler`처럼 "라벨을 기본값으로 채운다", "누락된 필드에 기본값을 넣는다" 같은 **단순한 변형(mutation)**도 대부분 필드 하나를 보고 필드 하나를 채우는 수준이라, 굳이 별도 웹훅 서버와 네트워크 왕복이 필요할 이유가 없다.

**`MutatingAdmissionPolicy`**(v1.36부터 안정화)는 `ValidatingAdmissionPolicy`와 같은 CEL 엔진을 쓰되, 결과가 "허용/거부"가 아니라 **오브젝트에 적용할 변경**이라는 점만 다르다. `ValidatingAdmissionPolicy`가 CEL로 웹훅 없는 검증을 가능하게 한 것과 정확히 같은 방식으로, `MutatingAdmissionPolicy`는 CEL로 **웹훅 없는 변형**을 가능하게 한다.

```
Mutating 웹훅 방식                       MutatingAdmissionPolicy
┌─────────────┐                      ┌─────────────────────┐
│ API 서버      │  HTTP POST          │  API 서버              │
│  → 별도 Pod로  │ ──────────────▶     │   CEL 표현식이 그 자리에서│
│    JSONPatch  │                    │   패치/적용 구성을 계산   │
│    계산해 응답  │                    │   (프로세스 내부)        │
└─────────────┘                      └─────────────────────┘
     지연/가용성 위험 있음                    네트워크 호출 없음
```

### 정의

`MutatingAdmissionPolicy`도 `ValidatingAdmissionPolicy`와 같은 두 오브젝트 모델을 따른다 — **정책**(변형 로직)과 **바인딩**(적용 범위)을 분리한다. 다만 `validations` 대신 **`mutations`** 목록을 쓰고, 각 항목은 `patchType`으로 두 가지 표현 방식 중 하나를 고른다.

| `patchType` | 표현 방식 |
|---|---|
| `ApplyConfiguration` | 서버 사이드 적용(SSA)과 같은 병합 방식으로 "이 필드는 이 값이어야 한다"를 CEL로 선언 |
| `JSONPatch` | CEL 표현식이 JSON Patch(RFC 6902) 연산 배열 자체를 반환 — 11.2절에서 웹훅이 `admission.PatchResponseFromRaw`로 만들던 것과 같은 형태 |

11.2절의 `PodLabeler` 웹훅(Pod에 `injected-by` 라벨을 기본값으로 채우는 예시)을 그대로 CEL로 옮기면 다음과 같다.

```yaml
apiVersion: admissionregistration.k8s.io/v1
kind: MutatingAdmissionPolicy
metadata:
  name: pod-labeler-policy.example.com
spec:
  matchConstraints:
    resourceRules:
      - apiGroups: [""]
        apiVersions: ["v1"]
        operations: ["CREATE"]
        resources: ["pods"]
  failurePolicy: Fail
  reinvocationPolicy: IfNeeded
  mutations:
    - patchType: "ApplyConfiguration"
      applyConfiguration:
        expression: >
          Object{
            metadata: Object.metadata{
              labels: Object.metadata.labels + {"injected-by": "pod-labeler-policy"}
            }
          }
---
apiVersion: admissionregistration.k8s.io/v1
kind: MutatingAdmissionPolicyBinding
metadata:
  name: pod-labeler-policy-binding
spec:
  policyName: pod-labeler-policy.example.com
  matchResources:
    namespaceSelector:
      matchExpressions:
        - key: kubernetes.io/metadata.name
          operator: NotIn
          values: [kube-system]
```

`Object{...}` 리터럴은 `ApplyConfiguration` 패치 타입 전용 CEL 문법으로, "이 경로에 이 값을 병합해라"를 선언적으로 표현한다. `Object.metadata.labels`는 대상 오브젝트의 **기존** 라벨 맵을 가리키므로, `+ {"injected-by": ...}`는 "기존 라벨은 유지하면서 이 라벨만 추가"한다는 뜻이다 — 웹훅 버전에서 `if _, ok := pod.Labels["injected-by"]; !ok { ... }`로 멱등성을 직접 챙기던 것과 달리, 병합 방식 자체가 멱등하다.

`reinvocationPolicy`는 11.3절에서 본 웹훅의 같은 필드와 의미가 동일하다 — 다른 Mutating 정책/웹훅이 오브젝트를 바꾼 뒤 이 정책을 다시 평가해야 하는지를 결정한다.

### 웹훅과의 선택 기준

| | MutatingAdmissionPolicy (CEL) | MutatingAdmissionWebhook |
|---|---|---|
| 실행 위치 | API 서버 프로세스 내부 | 별도 서버 (네트워크 호출) |
| 가용성 위험 | 없음 | 있음 (11.3절) |
| 다른 리소스 조회·외부 시스템 연동 | 불가능 | 가능 |
| 복잡한 절차적 로직(반복 계산, 조건 분기가 깊은 변형) | 표현하기 어려움 | 가능 |
| 배포 단위 | YAML 하나 | 서버 구현 + 배포 + 인증서 |

**단순한 기본값 채우기, 라벨/어노테이션 주입처럼 "필드를 보고 필드를 채우는" 수준의 변형이라면 `MutatingAdmissionPolicy`가 직접 만든 웹훅보다 낫다.** 반면 사이드카 컨테이너를 조건에 따라 복잡하게 구성하거나, 외부 시스템을 조회해 값을 채우거나, 다른 리소스의 상태를 참조해야 하는 변형은 여전히 웹훅의 몫이다. **선택 순서는 검증과 동일하다 — CEL(`MutatingAdmissionPolicy`) → 그래도 안 되면 직접 웹훅.**

## 11.6 정책 엔진 비교

CEL로 표현하기 어려운 복잡한 정책(여러 규칙의 조합, 조직 전체의 정책 라이브러리, 감사 리포트)을 위해 **정책 엔진**이 존재한다. 둘 다 내부적으로는 이 장에서 다룬 **Validating/Mutating 웹훅 메커니즘 위에 구축**되어 있다 — 사용자가 직접 웹훅 서버를 짜지 않아도 되게 감싸 주는 것이다.

### OPA/Gatekeeper

Rego라는 범용 정책 언어로 규칙을 작성한다.

```rego
package k8srequiredlabels

violation[{"msg": msg}] {
    required := input.parameters.labels
    provided := input.review.object.metadata.labels
    missing := required[_]
    not provided[missing]
    msg := sprintf("라벨 %v가 필요합니다", [missing])
}
```

```yaml
apiVersion: constraints.gatekeeper.sh/v1beta1
kind: K8sRequiredLabels
metadata:
  name: require-team-label
spec:
  match:
    kinds: [{ apiGroups: [""], kinds: ["Pod"] }]
  parameters:
    labels: ["team"]
```

Gatekeeper는 **`ConstraintTemplate`(규칙 정의)과 `Constraint`(적용 범위)를 분리**하는 모델이 특징이며, OPA 자체가 클라우드 인프라 전반(Terraform, CI 파이프라인 등)에서 널리 쓰이는 범용 정책 엔진이라는 것이 강점이다.

### Kyverno

YAML만으로 정책을 표현한다. 별도 언어를 배울 필요가 없다는 것이 Gatekeeper와의 가장 큰 차이다.

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: require-team-label
spec:
  validationFailureAction: Enforce
  rules:
    - name: check-team-label
      match:
        any:
          - resources: { kinds: ["Pod"] }
      validate:
        message: "team 라벨이 필요합니다"
        pattern:
          metadata:
            labels:
              team: "?*"
```

Kyverno는 검증뿐 아니라 **변형(mutate), 생성(generate — 네임스페이스 생성 시 기본 NetworkPolicy를 함께 생성하는 등), 정리(cleanup)** 규칙까지 하나의 YAML 모델로 표현한다.

### 비교와 선택 기준

| 상황 | 권장 |
|---|---|
| 단순한 필드 비교, 값 범위 검증 | **ValidatingAdmissionPolicy (CEL)** — 배포가 가장 가볍다 |
| 조직 전체에 걸친 정책 라이브러리, 감사 리포트, 예외 관리 UI 필요 | **Kyverno** (YAML 친화적) 또는 **Gatekeeper** (Rego, OPA 생태계 연동) |
| 다른 리소스 조회, 외부 시스템 연동, 매우 특수한 로직 | **직접 웹훅** — 다른 방법으로 표현할 수 없을 때만 |
| 클러스터 리소스 자동 생성(네임스페이스 생성 시 기본 리소스 세팅) | **Kyverno의 generate 규칙** |

> **웹훅은 최후의 수단이다.** CEL로 되면 CEL로, 조직 차원의 정책이 여러 개 필요하면 정책 엔진으로, 그래도 안 되는 것(다른 리소스 조회, 외부 API 연동)만 직접 웹훅으로 만든다. 직접 만든 웹훅은 **11.3절의 모든 가용성 위험을 스스로 책임져야 한다**는 것을 기억한다.

## 실습: Mutating 웹훅과 CEL 정책 비교

**① 인증서 준비** — 실습 클러스터(kind)에서는 자체 서명 인증서를 빠르게 만든다. 프로덕션에서는 cert-manager를 쓰는 것이 정석이다.

```bash
openssl req -x509 -newkey rsa:2048 -nodes -days 365 \
  -keyout tls.key -out tls.crt \
  -subj "/CN=pod-labeler-webhook.default.svc" \
  -addext "subjectAltName=DNS:pod-labeler-webhook.default.svc"

kubectl create secret tls pod-labeler-webhook-cert \
  --cert=tls.crt --key=tls.key -n default
```

**② 웹훅 서버 배포** — 11.2절의 `PodLabeler`를 담은 이미지를 빌드해 배포하고, Service로 노출한다.

```bash
kubectl apply -f - <<'EOF'
apiVersion: v1
kind: Service
metadata:
  name: pod-labeler-webhook
spec:
  selector: { app: pod-labeler-webhook }
  ports: [{ port: 443, targetPort: 9443 }]
EOF
```

**③ MutatingWebhookConfiguration 등록**

```bash
CA_BUNDLE=$(base64 -w0 tls.crt)
kubectl apply -f - <<EOF
apiVersion: admissionregistration.k8s.io/v1
kind: MutatingWebhookConfiguration
metadata:
  name: pod-labeler
webhooks:
  - name: mpod.example.com
    admissionReviewVersions: ["v1"]
    sideEffects: None
    failurePolicy: Ignore
    timeoutSeconds: 5
    clientConfig:
      service:
        namespace: default
        name: pod-labeler-webhook
        path: /mutate-v1-pod
        port: 443
      caBundle: ${CA_BUNDLE}
    rules:
      - apiGroups: [""]
        apiVersions: ["v1"]
        operations: ["CREATE"]
        resources: ["pods"]
        scope: Namespaced
    namespaceSelector:
      matchExpressions:
        - key: kubernetes.io/metadata.name
          operator: NotIn
          values: [kube-system]
EOF
```

**④ 검증**

```bash
kubectl run test-pod --image=nginx:alpine
kubectl get pod test-pod -o jsonpath='{.metadata.labels}'
# {"injected-by":"pod-labeler-webhook","run":"test-pod"}
```

**⑤ 동일 규칙을 ValidatingAdmissionPolicy로 비교** — 라벨을 "주입"할 수는 없지만(CEL은 Validating만), "라벨이 없으면 거부"하는 동등한 검증 규칙을 만들어 본다.

```bash
kubectl apply -f - <<EOF
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: require-injected-label
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
      - apiGroups: [""]
        apiVersions: ["v1"]
        operations: ["CREATE"]
        resources: ["pods"]
  validations:
    - expression: "has(object.metadata.labels['injected-by'])"
      message: "injected-by 라벨이 필요합니다"
---
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata:
  name: require-injected-label-binding
spec:
  policyName: require-injected-label
  validationActions: ["Deny"]
  matchResources:
    namespaceSelector:
      matchExpressions:
        - key: kubernetes.io/metadata.name
          operator: NotIn
          values: [kube-system]
EOF

kubectl run no-label-pod --image=nginx:alpine
# 웹훅이 라벨을 주입한 뒤이므로 통과한다 — 웹훅을 잠시 삭제하고 다시 시도해 차단을 확인한다
kubectl delete mutatingwebhookconfiguration pod-labeler
kubectl run no-label-pod-2 --image=nginx:alpine
# denied: injected-by 라벨이 필요합니다
```

두 메커니즘이 같은 자리(어드미션 체인)에서 다른 방식(네트워크 호출 대 인프로세스 CEL)으로 동작한다는 것을 직접 확인한다.

## 실습 과제

**과제 1 — 웹훅 가용성 사고 재현**
`failurePolicy: Fail`로 바꾸고 웹훅 Deployment를 0으로 스케일한 뒤 새 Pod를 만들어 본다. 어떤 에러가 나는지 확인하고, `namespaceSelector`로 자기 네임스페이스를 제외하지 않았을 때의 위험을 서술한다.

**과제 2 — Validating 웹훅으로 확장**
`PodValidator`를 구현해 `team` 라벨이 없는 Pod를 거부하도록 등록한다. `admission.Warnings`로 먼저 경고만 내보내는 버전과, `admission.Denied`로 차단하는 버전을 각각 시도해 점진 도입 방식의 차이를 비교한다.

**과제 3 — CEL로 같은 규칙 표현하기**
과제 2의 `team` 라벨 필수 규칙을 `ValidatingAdmissionPolicy`의 CEL 표현식으로 다시 작성하고, 웹훅 버전과 동작이 동일한지 비교한다. 어느 쪽이 다른 리소스를 조회해야 하는 규칙으로 확장하기 쉬운지 설명한다.

**과제 4 — 순환 의존 재현**
웹훅의 `namespaceSelector`에서 자기 네임스페이스 제외 조건을 제거하고 웹훅 Pod를 재시작해 데드락을 재현한다. `kubectl edit mutatingwebhookconfiguration`으로 `failurePolicy: Ignore`로 임시 변경해 복구하는 절차를 연습한다.

**과제 5 — 파라미터화된 정책**
네임스페이스별로 다른 `maxReplicas` 값을 갖는 `ValidatingAdmissionPolicy` + `ValidatingAdmissionPolicyBinding` + `ConfigMap` 파라미터 조합을 만들고, 두 네임스페이스에서 서로 다른 한도가 적용되는 것을 확인한다.

**과제 6 — MutatingAdmissionPolicy로 라벨 주입 재구현**
11.5절의 `pod-labeler-policy`를 클러스터에 적용하고, `pod-labeler` `MutatingWebhookConfiguration`은 삭제한 상태에서 Pod를 생성해 `injected-by` 라벨이 웹훅 없이도 채워지는지 확인한다. 그다음 `ApplyConfiguration` 대신 `JSONPatch` `patchType`으로 같은 동작을 다시 작성해 두 표현 방식의 차이를 비교한다.

## 요약

- 어드미션 체인은 **Mutating → 스키마 검증(9장) → Validating** 순서다. Mutating이 먼저이므로 변형된 결과가 검증을 받는다.
- 웹훅은 **`AdmissionReview`** JSON을 주고받는다. Mutating 응답은 **base64 인코딩된 JSON Patch**를, Validating 응답은 `allowed`와 거부 사유를 담는다. **`warnings`로 차단 없이 경고만 보낼 수 있어 점진 도입에 유용하다.**
- **웹훅의 가장 큰 위험은 가용성이다.** `failurePolicy: Fail`인 웹훅 서버가 죽으면 해당 리소스의 모든 변경이 막히고, 자기 자신을 복구할 수 없는 **데드락**이 생길 수 있다. **`namespaceSelector`로 시스템·자기 네임스페이스를 제외**하는 것이 가장 중요한 대비책이다.
- `timeoutSeconds`는 짧게, `sideEffects`는 정확히 선언하고(`None`이면 dry-run에도 호출됨), `objectSelector`로 옵트인 범위를 좁히면 사고 반경이 줄어든다.
- **`ValidatingAdmissionPolicy`(CEL)** 는 API 서버 프로세스 내부에서 평가되어 네트워크 호출이 없다. 단순한 필드 검증이라면 웹훅보다 가용성·지연 위험이 없는 CEL을 우선 고려한다. 다만 **다른 리소스 조회나 외부 연동은 CEL로 불가능**하다.
- **`MutatingAdmissionPolicy`(v1.36부터 안정화)** 는 `ValidatingAdmissionPolicy`와 같은 CEL 엔진으로 **웹훅 없는 변형**을 가능하게 한다. `ApplyConfiguration`(병합 방식) 또는 `JSONPatch` 두 가지 `patchType`으로 표현하며, 단순한 기본값 채우기·라벨 주입이라면 직접 만든 Mutating 웹훅보다 우선 고려할 대안이다. 다만 외부 시스템 연동이나 복잡한 절차적 로직은 여전히 웹훅이 필요하다.
- **OPA/Gatekeeper**(Rego, `ConstraintTemplate`/`Constraint` 분리)와 **Kyverno**(YAML 기반, mutate/validate/generate 통합)는 둘 다 웹훅 메커니즘 위에 구축된 정책 엔진이다. 조직 전체의 정책 라이브러리가 필요하면 직접 웹훅보다 이런 검증된 엔진을 우선 고려한다.
- 선택 순서는 **CEL(Validating/MutatingAdmissionPolicy) → 정책 엔진 → 직접 웹훅**이다. 직접 웹훅은 다른 방법으로 표현할 수 없을 때의 최후 수단이며, 그만큼 가용성 책임도 스스로 져야 한다.
