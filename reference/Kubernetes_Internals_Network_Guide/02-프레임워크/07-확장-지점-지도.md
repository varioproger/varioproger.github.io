# 7장. 확장 지점 지도

> **학습목표**
> - 쿠버네티스를 확장하는 8가지 방법을 각각 정의하고 구분할 수 있다.
> - 각 확장 방법의 개발 복잡도·배포 형태·지연시간·전형적 용도를 비교할 수 있다.
> - 요구사항에서 출발해 올바른 확장 방법을 선택하는 결정 트리를 적용할 수 있다.
> - 확장 개발의 로컬 루프(작성 → 배포 → 테스트)가 어떻게 생겼는지 개관한다.
> - 클러스터에 이미 설치된 확장 지점을 커맨드 한 줄로 찾아낼 수 있다.

---

## 들어가며

1부에서 쿠버네티스 내부를 열어봤다. kube-apiserver가 요청을 어떻게 처리하는지(2장), etcd가 상태를 어떻게 저장하는지(3장), 스케줄러가 어떻게 배치를 결정하는지(4장), 컨트롤러 매니저가 어떻게 조정 루프를 도는지(5장) 봤다.

이제부터는 그 컨트롤 플레인을 **어떻게 확장하는가**를 다룬다. "확장"이라는 단어가 가리키는 범위는 생각보다 넓다. `Deployment`처럼 보이지만 실제로는 사용자 정의 리소스를 다루는 컨트롤러부터, 파드가 생성되기 직전에 끼어드는 웹훅, 배치 결정 자체에 개입하는 스케줄러 플러그인, 심지어 API 서버처럼 동작하는 완전히 별도의 서버까지 — 이 모든 것이 "쿠버네티스 확장"이라는 이름 아래 있다.

문제는 **초심자가 이 선택지들을 구분하지 못한 채 뛰어든다는 것**이다. CRD로 충분한 문제를 어그리게이션 API 서버로 풀려다 몇 주를 낭비하거나, 반대로 웹훅으로 처리해야 할 것을 억지로 컨트롤러 폴링으로 흉내 내다 지연시간 문제에 부딪힌다. 이 장은 8~12장에서 각각을 깊게 다루기 전에, **먼저 지도를 그려서** 어디로 가야 할지 알게 하는 것이 목적이다.

```
2부 전체 구조

7장  확장 지점 지도           ← 지금 여기 (선택 기준)
  │
  ├─ 8장  client-go와 API Machinery     (모든 확장의 공통 기반)
  ├─ 9장  CRD와 커스텀 리소스            (① 새 리소스 타입)
  ├─ 10장 오퍼레이터 프레임워크           (① + 도메인 로직)
  ├─ 11장 어드미션 웹훅과 정책            (③ 요청 가로채기)
  └─ 12장 스케줄러 플러그인·어그리게이션   (④ 배치 개입, ⑧ 완전한 API)
```

## 7.1 쿠버네티스 확장의 8가지 방법

쿠버네티스는 처음부터 "확장 가능한 플랫폼"으로 설계됐다. 그 결과 확장 지점이 하나가 아니라 여러 층에 흩어져 있다. 요청이 API 서버에 도달하기 **전에** 개입하는 방법, API 서버 **안에서** 새로운 리소스로 참여하는 방법, 스케줄러의 **결정 과정**에 개입하는 방법, kubelet이 관리하는 **노드 리소스**에 참여하는 방법까지 층위가 다르다.

### ① CRD + 커스텀 컨트롤러

`CustomResourceDefinition`으로 새로운 리소스 타입을 API 서버에 등록하고, 그 리소스를 watch하며 조정하는 컨트롤러를 작성하는 방법이다. 5장에서 본 Deployment/ReplicaSet 컨트롤러와 정확히 같은 패턴이지만, 대상이 내장 리소스가 아니라 사용자가 정의한 리소스다.

```yaml
apiVersion: example.com/v1
kind: WebApp     # ← 내가 만든 리소스 타입
metadata:
  name: my-site
spec:
  image: nginx:alpine
  replicas: 3
```

**핵심**: CRD는 리소스를 "선언"할 뿐이고, 그 선언을 실제로 실현하는 것은 별도로 작성한 컨트롤러다. 컨트롤러 없는 CRD는 그저 etcd에 저장되는 구조화된 데이터일 뿐이다. 9장에서 CRD 정의를, 10장에서 컨트롤러를 다룬다.

### ② 오퍼레이터 패턴

오퍼레이터는 ①의 특수한 경우다. **"사람 운영자가 하던 도메인 지식을 코드로 옮긴" 컨트롤러**를 오퍼레이터라고 부른다. 예를 들어 PostgreSQL 오퍼레이터는 단순히 Pod 개수를 맞추는 것이 아니라 "리더가 죽으면 레플리카 중 가장 최신 WAL을 가진 것을 승격시키고, 나머지를 새 리더에 재동기화한다"는 백업/복구/장애조치 지식까지 담는다.

```
일반 CRD 컨트롤러                오퍼레이터
────────────────────           ────────────────────
"원하는 상태 = 3개 Pod"          "원하는 상태 = 정상 동작하는
 → Pod 3개 만들면 끝               PostgreSQL 클러스터"
                                 → 백업, 장애조치, 마이너 버전
                                   업그레이드, 복제 재구성까지
```

기술적으로는 ①과 동일한 Informer/워크큐/조정 패턴을 쓴다. 차이는 **조정 함수 안에 담기는 지식의 깊이**뿐이다. 10장에서 controller-runtime과 Kubebuilder로 이 패턴을 구조화하는 법을 다룬다.

### ③ 어드미션 웹훅

2장에서 본 요청 처리 경로의 "④ 어드미션 체인" 단계에 외부 HTTP 서비스로 끼어드는 방법이다. API 서버가 오브젝트를 etcd에 쓰기 **직전에** 내 서버에 물어본다.

```
요청 → 인증/인가 → Mutating 웹훅 → 스키마 검증 → Validating 웹훅 → etcd
                        │                              │
                        ▼                              ▼
                  "이 필드를 채워줘"              "이 요청을 거부해"
```

- **Mutating**: 오브젝트를 수정한다 (기본값 주입, 사이드카 자동 삽입 등)
- **Validating**: 승인/거부만 한다 (정책 위반 시 거부)

**요청 경로에 직접 끼어들기 때문에 지연시간과 가용성에 민감하다.** 웹훅 서버가 느리거나 죽으면 관련된 모든 쓰기 요청이 멈춘다. 11장에서 상세히 다룬다.

### ④ 커스텀 스케줄러 / 스케줄러 플러그인

4장에서 본 스케줄링 프레임워크(Filter/Score/Bind)의 확장점에 직접 코드를 꽂는 방법이다. "이 워크로드는 특정 랙에 몰아서 배치해야 한다", "GPU 토폴로지를 고려해야 한다" 같은 표준 스케줄러가 모르는 배치 로직을 넣을 때 쓴다.

```
kube-scheduler (표준)              커스텀 스케줄러 플러그인
──────────────────────          ──────────────────────
내장 Filter/Score 플러그인만        내 Filter/Score/Permit
사용                              플러그인을 같은 바이너리에 컴파일
                                  (인프로세스 확장, 아웃오브프로세스 아님)
```

완전히 별도의 스케줄러 바이너리를 `pod.spec.schedulerName`으로 지정해 띄우는 것도 가능하지만, 실무에서는 스케줄러 프레임워크에 플러그인만 추가해 표준 스케줄러를 재빌드하는 방식이 더 흔하다. 12장에서 다룬다.

### ⑤ 디바이스 플러그인

kubelet이 관리하는 **노드 리소스 목록**(CPU, 메모리는 내장)에 GPU, FPGA, InfiniBand NIC 같은 특수 하드웨어를 노출하는 방법이다. gRPC로 kubelet과 통신하는 별도 데몬(대개 DaemonSet)으로 배포된다.

```
디바이스 플러그인 (DaemonSet, 노드마다 하나)
    │ gRPC (Unix 소켓, /var/lib/kubelet/device-plugins/)
    ▼
kubelet
    │ ListAndWatch로 사용 가능한 디바이스 목록 수신
    ▼
node.status.capacity에 반영
    nvidia.com/gpu: 4
```

Pod가 `resources.limits: {nvidia.com/gpu: 1}`을 요청하면 스케줄러가 이 값을 일반 리소스처럼 취급해 배치하고, kubelet이 디바이스 플러그인에 `Allocate`를 호출해 실제 디바이스를 컨테이너에 연결한다. 6장에서 kubelet 개관을 봤다면 이 흐름이 자연스럽게 이어진다.

### ⑥ CNI 플러그인

**Container Network Interface** — 파드에 네트워크를 붙이는 표준이다. kubelet이 파드 샌드박스를 만들 때 CNI 플러그인 바이너리를 실행해 "이 네트워크 네임스페이스에 인터페이스를 만들고 IP를 할당해라"고 지시한다.

```
kubelet → 컨테이너 런타임 → CNI 플러그인 실행 (바이너리 exec)
                                  │
                                  ▼
                          veth pair 생성, IP 할당,
                          라우트/iptables 규칙 추가
```

Calico, Cilium, Flannel이 대표적이다. **13장에서 CNI 스펙 전체를 상세히 다룬다.** 이 장에서는 "네트워크 연결을 새로 구현하고 싶다면 이 방법"이라는 위치만 잡아둔다.

### ⑦ CSI 플러그인

**Container Storage Interface** — 스토리지 프로비저닝/마운트를 표준화한 인터페이스다. CNI와 이름은 비슷하지만 계층이 다르다: 별도 컨트롤러(볼륨 생성/삭제, 대개 Deployment)와 노드 플러그인(마운트/언마운트, 대개 DaemonSet)으로 나뉜다.

```
CSI 컨트롤러 플러그인 (중앙)         CSI 노드 플러그인 (노드마다)
────────────────────            ────────────────────
CreateVolume                     NodeStageVolume
DeleteVolume                     NodePublishVolume
클라우드 API로 실제 볼륨 생성        블록 디바이스를 파드 경로에 마운트
```

이 책은 네트워크에 집중하므로 CSI는 깊게 다루지 않지만, "확장 지점 지도"에서 빠뜨리면 안 되는 항목이라 여기 포함한다. CNI와의 대칭 구조를 이해하는 것만으로 충분하다.

### ⑧ 어그리게이션 API 서버

`APIService` 오브젝트로 **완전히 별도의 API 서버**를 kube-apiserver에 등록하는 방법이다. `metrics.k8s.io`가 대표적 예시로, 2장에서 이미 봤다.

```
kubectl get --raw /apis/metrics.k8s.io/v1
    │
    ▼
kube-apiserver가 자신이 처리하지 않고
metrics-server로 프록시
```

CRD와 근본적으로 다르다. **CRD는 여전히 etcd에 저장되고 kube-apiserver가 직접 서빙**하지만, 어그리게이션 API 서버는 **완전히 다른 저장소, 완전히 다른 의미론**을 가질 수 있다. metrics.k8s.io는 etcd에 저장되지 않고 매 요청마다 실시간으로 계산된 값을 반환한다. 12장에서 직접 만들어 본다.

## 7.2 각 방법의 트레이드오프

| 방법 | 개발 복잡도 | 배포 형태 | 지연시간/치명도 | 전형적 용도 |
|---|---|---|---|---|
| ① CRD + 컨트롤러 | 중 | 클러스터 내 Pod (Deployment) | 낮음 — 비동기 조정, 실패해도 재시도 | 선언적 리소스 관리 (앱 배포, 설정 배포) |
| ② 오퍼레이터 | 중~높음 | 클러스터 내 Pod | 낮음 — ①과 동일 | 상태 저장 시스템 자동 운영 (DB, 메시지 큐) |
| ③ 어드미션 웹훅 | 중 | 클러스터 내 Pod (Service로 노출) | **높음** — 모든 관련 쓰기 요청 경로에 동기 개입 | 정책 강제, 기본값 주입, 사이드카 삽입 |
| ④ 스케줄러 플러그인 | 높음 | 스케줄러 바이너리에 컴파일 또는 별도 스케줄러 Pod | **높음** — 매 스케줄링 사이클에 개입 | 특수 배치 로직 (토폴로지, 갱 스케줄링) |
| ⑤ 디바이스 플러그인 | 중 | 노드마다 DaemonSet (gRPC) | 중 — 파드 시작 시점에만 개입 | GPU/FPGA 등 특수 하드웨어 노출 |
| ⑥ CNI 플러그인 | 높음 | 노드 바이너리 + 대개 DaemonSet 에이전트 | **매우 높음** — 모든 파드 생성/삭제에 개입, 실패하면 파드가 안 뜸 | 네트워크 연결, 정책 강제 |
| ⑦ CSI 플러그인 | 높음 | 컨트롤러 Deployment + 노드 DaemonSet | 높음 — 볼륨 마운트 실패 시 파드가 안 뜸 | 스토리지 프로비저닝/마운트 |
| ⑧ 어그리게이션 API 서버 | **매우 높음** | 클러스터 내 별도 API 서버 Pod | 중 — 해당 API 그룹 요청에만 영향 | 비-CRUD 의미론, 커스텀 저장 백엔드가 필요한 API |

**읽는 법**

- **개발 복잡도**는 "처음부터 끝까지 만드는 데 드는 노력"이다. CRD 컨트롤러는 client-go 하나로 시작할 수 있지만, CNI/CSI/어그리게이션 API 서버는 프로토콜 자체를 구현해야 해서 진입 장벽이 높다.
- **지연시간/치명도**는 "이 확장이 느리거나 죽으면 클러스터에 어떤 영향을 주는가"다. 어드미션 웹훅과 CNI/CSI는 **동기적으로 요청 경로에 있어서** 장애가 즉시 전파된다. 반면 CRD 컨트롤러는 **비동기 조정**이므로 잠시 멈춰도 나중에 따라잡는다(5장의 레벨 트리거 원칙).
- **배포 형태**가 "클러스터 내 Pod"인 것들은 일반적인 쿠버네티스 배포/RBAC 지식으로 관리할 수 있다. "노드 바이너리"인 것들(CNI, CSI 노드 플러그인)은 호스트 파일시스템/네트워크 네임스페이스에 접근해야 해서 배포와 권한 모델이 다르다.

> **왜 어드미션 웹훅과 CNI가 특히 위험한가**
>
> 두 방법 모두 **요청 경로의 필수 관문**이 된다. 어드미션 웹훅이 응답하지 않으면 `failurePolicy: Fail` 설정에 따라 해당 리소스의 생성/수정이 전부 막힌다. CNI 플러그인이 실패하면 파드가 `ContainerCreating` 상태에서 멈춘다. **이 두 확장점을 만들 때는 반드시 타임아웃과 장애 시 동작(fail open vs fail closed)을 설계 초기에 결정해야 한다.** 11장과 13장에서 각각 상세히 다룬다.

## 7.3 선택 결정 트리

"내 문제를 어떤 방법으로 풀어야 하는가"를 질문 순서로 정리하면 다음과 같다.

```
                        새로운 요구사항이 생겼다
                                │
                                ▼
                  ┌─────────────────────────────┐
```

**결정 트리를 쓸 때 흔한 실수**

1. **"CRD로 상태를 저장하고 어드미션 웹훅으로 검증하면 되지 않나?"** — 맞다. 실제로 많은 시스템이 CRD(①)와 검증 웹훅(③)을 함께 쓴다. 결정 트리는 **배타적 선택이 아니라 각 요구사항 조각에 대한 답**이다. 큰 시스템은 여러 가지를 조합한다.
2. **"단순 CRUD인데 어그리게이션 API 서버로 만들었다"** — CRD로 충분한 경우 대부분이다. 어그리게이션 API 서버는 **커스텀 저장 백엔드가 필요하거나(예: 시계열 DB), CRUD가 아닌 의미론(예: `TokenReview`처럼 저장 없이 계산만 하는 API)이 필요할 때만** 정당화된다. "그냥 우리가 직접 API 서버를 만들고 싶어서"는 정당한 이유가 아니다.
3. **"배치 결정에 관여해야 하는데 어드미션 웹훅으로 파드를 수정했다"** — Mutating 웹훅으로 `nodeSelector`를 주입하는 식의 편법은 가능하지만, 스케줄러의 Score 단계에서 다른 파드들과의 상대적 우선순위를 고려하는 것과는 다르다. **진짜 배치 로직이면 스케줄러 플러그인으로 가야 한다.**

## 7.4 확장 개발 워크플로우 개관

8~12장에서 각 방법을 구현할 때 반복적으로 마주치는 개발 루프를 미리 정리한다.

### 로컬 개발 루프

```
┌─────────────────────────────────────────────────────────┐
│ ① 로컬 kind 클러스터                                       │
│    kind create cluster --name ext-dev                    │
│                                                           │
│ ② 코드 수정 → 이미지 빌드 → kind에 로드                      │
│    docker build -t my-controller:dev .                   │
│    kind load docker-image my-controller:dev --name ext-dev│
│                                                           │
│ ③ 매니페스트 적용 → 로그 확인                                │
│    kubectl apply -f deploy.yaml                           │
│    kubectl logs -f deployment/my-controller               │
└─────────────────────────────────────────────────────────┘
```

이 루프에서 ②의 "빌드 → 로드 → 재배포"가 가장 느린 구간이다. **Tilt**나 **Skaffold** 같은 도구는 파일 변경을 감지해 이 과정을 자동화하고, 일부는 바이너리를 실행 중인 컨테이너에 직접 주입해(hot reload) 재빌드 없이 반영한다. 이 책은 특정 도구 사용법을 다루지는 않지만, **컨트롤러/웹훅 개발 초기부터 이런 자동화 없이 매번 수동으로 반복하면 개발 속도가 급격히 떨어진다는 점만 기억해두자.**

컨트롤러를 클러스터 밖에서 실행하며 `kubeconfig`로 원격 클러스터에 연결하는 방법도 있다(8장 실습에서 쓴 `rest.InClusterConfig()` 폴백 패턴). 웹훅처럼 **API 서버가 직접 호출해야 하는 확장**은 이 방법이 까다롭다 — API 서버가 개발자의 로컬 머신에 도달할 네트워크 경로가 있어야 하기 때문이다(터널링 도구나 `ngrok` 같은 것을 임시로 쓰기도 한다). 반면 CRD 컨트롤러는 클러스터 밖에서도 문제없이 개발할 수 있다.

### 테스트 전략 개관

| 계층 | 도구 | 확인하는 것 |
|---|---|---|
| 단위 테스트 | `fake` 클라이언트 (8.5절) | 조정 로직 자체 (API 호출 없이) |
| 통합 테스트 | `envtest` (10장에서 상세) | 실제 API 서버 + etcd 동작, RBAC, 어드미션까지 포함하되 kubelet/스케줄러는 없음 |
| E2E 테스트 | kind + 실제 클러스터 | 전체 스택, 실제 파드 생성까지 |

`envtest`는 controller-runtime 프로젝트가 제공하는 도구로, **실제 kube-apiserver와 etcd 바이너리를 다운로드해 로컬에서 띄우고** 그 위에서 컨트롤러를 테스트한다. kubelet이나 스케줄러는 없으므로 파드가 실제로 뜨지는 않지만, **CRD 등록·검증·어드미션·RBAC까지 실제 동작**을 검증할 수 있어 단위 테스트와 E2E 테스트 사이의 간극을 메운다. 10장에서 오퍼레이터 테스트 전략을 다룰 때 자세히 설명한다.

### 패키징: Helm 차트

확장을 배포 가능한 형태로 묶을 때 대부분 **Helm 차트**를 쓴다. CRD 매니페스트, 컨트롤러 Deployment, RBAC(ServiceAccount/ClusterRole/ClusterRoleBinding), 웹훅이 있다면 `Certificate`(cert-manager 연동)와 `MutatingWebhookConfiguration`까지 하나의 차트로 묶는다.

```
mychart/
├── Chart.yaml
├── crds/                          # Helm이 특별 취급하는 디렉터리
│   └── webapp-crd.yaml            #   (helm upgrade 시 기본적으로 갱신 안 됨 — 주의)
└── templates/
    ├── deployment.yaml
    ├── rbac.yaml
    ├── webhook.yaml
    └── service.yaml
```

**주의할 점 하나**: Helm은 `crds/` 디렉터리의 내용을 **최초 설치 시에만** 적용하고 `helm upgrade`에서는 갱신하지 않는다. CRD 스키마를 변경했다면 별도로 `kubectl apply`해야 한다. 9장에서 CRD 버저닝을 다룰 때 이 문제를 다시 짚는다.

이 절에서 다룬 로컬 루프·테스트·패키징은 8~12장 각 장에서 해당 확장 방법에 맞게 구체화된다.

## 실습: 클러스터에 이미 설치된 확장 지점 찾기

새 확장을 만들기 전에, **지금 클러스터에 이미 어떤 확장이 설치되어 있는지** 파악하는 습관을 들이자. kind 클러스터든 운영 클러스터든 이 점검은 항상 유효하다.

**① CRD 목록**

```bash
kubectl get crds -o custom-columns=NAME:.metadata.name,GROUP:.spec.group
```

```
NAME                              GROUP
certificates.cert-manager.io      cert-manager.io
webapps.example.com               example.com
```

**② 어드미션 웹훅 설정**

```bash
kubectl get validatingwebhookconfigurations
kubectl get mutatingwebhookconfigurations -o custom-columns=NAME:.metadata.name,WEBHOOKS:.webhooks[*].name
```

```
NAME                                    WEBHOOKS
cert-manager-webhook                    webhook.cert-manager.io
```

각 웹훅의 `failurePolicy`와 `clientConfig`(어디로 호출을 보내는지)를 확인하면 어떤 요청이 어떤 조건에서 가로채지는지 알 수 있다.

```bash
kubectl get validatingwebhookconfigurations cert-manager-webhook -o yaml | grep -E 'failurePolicy|service|url'
```

**③ 어그리게이션 API 서버**

```bash
kubectl get apiservices | grep -v "Local"
```

```
NAME                     SERVICE                      AVAILABLE
v1.metrics.k8s.io        kube-system/metrics-server   True
v1beta1.metrics.k8s.io   kube-system/metrics-server   True
```

`SERVICE` 컬럼이 비어 있으면(`Local`) 내장 API이고, 채워져 있으면 어그리게이션 API다. (`metrics.k8s.io`는 v1.37에서 `v1`으로 GA 승격했지만, 기존 클라이언트 호환을 위해 `v1beta1`도 당분간 함께 서빙된다 — 같은 방식으로 두 GroupVersion이 각각 별도의 `APIService`로 등록된다.)

**④ 사용 중인 스케줄러 이름**

```bash
kubectl get pods -A -o custom-columns=NS:.metadata.namespace,NAME:.metadata.name,SCHEDULER:.spec.schedulerName | sort -u -k3
```

기본값은 `default-scheduler`다. 다른 값이 보인다면 커스텀 스케줄러가 그 파드들을 담당하고 있다는 뜻이다.

**⑤ 디바이스 플러그인**

```bash
kubectl get nodes -o json | jq '.items[].status.capacity | with_entries(select(.key | test("k8s.io/|com/") and (.key | test("cpu|memory|pods|ephemeral") | not)))'
```

`cpu`, `memory`, `pods`가 아닌 리소스(예: `nvidia.com/gpu`)가 보이면 디바이스 플러그인이 등록한 것이다.

**⑥ CNI/CSI 확인**

```bash
# CNI
kubectl get pods -n kube-system -o wide | grep -iE 'calico|cilium|flannel|weave'

# CSI 드라이버
kubectl get csidrivers
```

## 실습 과제

**과제 1 — 확장 지점 인벤토리 작성**
실습에서 쓴 명령어들을 조합해, 현재 클러스터에 설치된 모든 확장(CRD, 웹훅, 어그리게이션 API, 커스텀 스케줄러, 디바이스 플러그인, CNI, CSI)을 표로 정리한다. 각 항목이 8가지 분류 중 어디에 속하는지 표시한다.

**과제 2 — 결정 트리 적용**
다음 세 가지 가상 요구사항 각각에 대해 7.3절의 결정 트리를 따라가며 어떤 확장 방법을 선택할지, 그리고 왜 다른 방법은 부적합한지 서술한다.
  (a) "특정 라벨이 붙은 파드는 반드시 리소스 limit이 설정되어 있어야 한다"
  (b) "여러 팀이 공유하는 배치 작업 큐 시스템을 만들고, 큐 상태를 `kubectl get jobqueue`로 조회하고 싶다"
  (c) "GPU가 있는 노드에 한해 특정 워크로드를 랙 단위로 분산 배치하고 싶다"

**과제 3 — 트레이드오프 표 검증**
7.2절의 표에서 "지연시간/치명도"가 "높음"으로 표시된 항목(③, ④, ⑥, ⑦) 중 하나를 골라, 해당 확장이 실패했을 때 클러스터에 어떤 구체적 증상이 나타나는지 (예: 파드가 `ContainerCreating`에 멈춘다, 리소스 생성이 거부된다) 조사해 서술한다.

**과제 4 — CRD vs 어그리게이션 API 서버 사례 찾기**
실제 오픈소스 프로젝트 중 CRD를 쓰는 것 하나와 어그리게이션 API 서버를 쓰는 것 하나를 찾아, 각각이 그 방법을 선택한 이유(문서나 설계 노트에서)를 조사해 비교한다.

**과제 5 — 워크플로우 재현**
kind 클러스터를 하나 만들고, 7.4절의 로컬 개발 루프를 그대로 따라 아주 단순한 컨트롤러(예: 특정 이름의 ConfigMap이 생기면 로그만 남기는 컨트롤러)를 빌드·로드·배포까지 해본다. 이 경험은 8장 실습의 준비 운동이 된다.

## 요약

- 쿠버네티스 확장은 8가지로 분류된다: **CRD+컨트롤러, 오퍼레이터, 어드미션 웹훅, 스케줄러 플러그인, 디바이스 플러그인, CNI, CSI, 어그리게이션 API 서버.** 각각이 개입하는 계층(API 서버 앞/안, 스케줄러, kubelet, 완전히 별도 서버)이 다르다.
- **CRD는 여전히 etcd에 저장되고 kube-apiserver가 직접 서빙**하지만, **어그리게이션 API 서버는 완전히 다른 저장소와 의미론을 가질 수 있다.** 이 차이가 9장과 12장을 가르는 기준이다.
- **어드미션 웹훅과 CNI/CSI는 요청 경로의 동기적 관문이다.** 실패하면 즉시 클러스터에 영향을 준다. **CRD 컨트롤러는 비동기 조정이라 일시적 장애를 흡수한다**(5장의 레벨 트리거 원칙).
- 결정은 **"새 리소스 타입이 필요한가 → 기존 요청을 가로채야 하는가 → 배치 결정에 관여하는가 → 노드 리소스를 노출하는가 → 네트워크/스토리지 드라이버인가"** 순서로 좁혀간다. 큰 시스템은 여러 방법을 조합해서 쓴다.
- 개발 워크플로우는 **로컬 kind 클러스터 → 빌드/로드/배포 루프 → 단위(`fake` 클라이언트)/통합(`envtest`)/E2E 테스트 → Helm 차트 패키징**의 공통 패턴을 따른다.
- 새 확장을 만들기 전에 **`kubectl get crds/validatingwebhookconfigurations/mutatingwebhookconfigurations/apiservices/csidrivers`**로 클러스터에 이미 무엇이 설치되어 있는지 확인하는 습관을 들인다.

**다음 장에서는** 모든 확장 방법의 공통 기반이 되는 **client-go와 API Machinery**를 연다. ClientSet, Informer, 워크큐를 직접 코드로 다루며, 이 장에서 지도로만 본 "① CRD + 컨트롤러"를 실제로 구현할 준비를 갖춘다.
