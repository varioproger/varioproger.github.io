# 부록 D. 성능 상수 표 — 연산별 대략 비용, 캐시 지연 시간, 할당 비용

> **이 부록의 위치** — 61장부터 72장까지 열두 개 장에 걸쳐 메모리 계층, 힙 구조, 할당, GC, 측정, `Span<T>`, 데이터 지향 설계, 시스템 레벨 성능을 해부했다. 그 과정에서 나온 **숫자들**은 각자의 문맥 안에 흩어져 있다. 이 부록은 그것을 한 자리에 모은 참조표다. 새로운 사실은 없다. 표마다 "이 값이 어디서 왔는가"를 캡션에 밝히고, 본문의 어느 절에 설명이 있는지를 `(NN.M절)` 형태로 붙였다.
>
> **선수 지식** — 54장(타입 시스템의 런타임 표현), 61장(메모리의 기초), 62장(.NET 힙의 구조), 63장(할당), 67장(측정 없이 최적화 없다)
>
> **이 부록에서 다루지 않는 것** — 각 숫자의 **메커니즘**은 본문이 담당한다. 캐시 계층의 하드웨어 구조는 61.4절, 힙 분할 규칙은 62장, 할당 경로는 63장, GC 단계별 동작은 64장, 벤치마킹 방법론 전체는 67장, 컬렉션 내부 구조는 24장이다. 진단 명령의 조작법은 부록 C, 메모리 관리 규칙 스물여섯 개는 부록 B에 있다.

## D.1 이 표를 읽는 법

### ⚠️ 먼저 이것부터 읽어라 — 이 부록의 절대값을 믿지 마라

이 부록에 있는 **모든 절대 수치는 특정 기계에서 특정 시점에 특정 런타임 버전으로 측정된 한 번의 관측**이다. 당신의 하드웨어에서 같은 값이 나올 이유가 없다.

> **⚠️ 이 부록의 절대값을 믿지 말고 자기 하드웨어에서 측정하라**
>
> 이 표의 숫자가 당신의 기계에서 달라지는 이유는 최소한 다음과 같다.
>
> - **CPU가 다르다.** 클록 주파수, 캐시 크기, 캐시 지연 사이클 수, 분기 예측기 품질, 메모리 컨트롤러가 전부 다르다. D.2절의 지연 표는 2.30 GHz Haswell 노트북 값이다. 5 GHz 최신 데스크톱에서는 나노초 값이 절반 이하일 수 있고, 사이클 수는 오히려 늘 수 있다.
> - **런타임 버전이 다르다.** D.4절의 값 대부분은 .NET 8 기준이다. JIT은 버전마다 코드를 다르게 만들고(55장), BCL 구현은 버전마다 벡터화된다(71.5절), GC 동작도 바뀐다(65.7절 DATAS).
> - **부하 상태가 다르다.** 벤치마크가 독점하는 캐시와, 옆에서 다른 요청 200개가 도는 프로덕션의 캐시는 같은 캐시가 아니다.
> - **컨테이너와 클라우드가 다르다.** vCPU 공유, cgroup 메모리 제한, 하이퍼바이저 스텝오버가 전부 노이즈를 만든다(65.8절, 72.8절).
>
> **그래서 이 부록의 올바른 사용법은 하나뿐이다 — 절대값이 아니라 "자릿수"와 "상대 순서"만 가져가고, 결정을 내리기 전에 자기 환경에서 다시 재라.** 이 경고는 D.2절부터 D.7절까지 각 절 첫머리에 반복해 두었다. 반복이 지겨우면 그것이 이 부록의 목적이다.

### 무엇이 측정 대상이고 무엇이 아닌가

성능 숫자를 볼 때 가장 먼저 물어야 할 것은 "이 숫자가 무엇을 포함하는가"다. 같은 이름의 연산도 무엇을 세느냐에 따라 열 배가 달라진다.

| 이름 | 측정 대상 | 흔한 오해 |
|---|---|---|
| **힙 할당 비용** | 범프 포인터 이동 + 필드 0 초기화 + (컨텍스트 소진 시) 새 할당 컨텍스트 확보 | "할당은 공짜다" — 나중의 GC 비용이 여기 안 들어 있다 |
| **GC 비용** | 마킹 + 계획 + 재배치 + 압축 + EE 일시 중지·재개 | 할당 지점에서 측정되지 않고 **다른 스레드의 다른 시점**에 나타난다 |
| **가상 호출 비용** | 간접 참조 한두 번 | 진짜 비용은 **인라이닝이 막히는 것**이며 후속 최적화 전부가 함께 사라진다(55.4절) |
| **박싱 비용** | 힙 할당 + 값 복사 | 언박싱 시 타입 검사, 그리고 GC 압력이 뒤따른다 |
| **예외 비용** | 객체 할당 + 2단계 처리 + (접근 시) 스택 트레이스 문자열 | `try` 블록이 있기만 한 비용과 **실제로 던지는** 비용은 전혀 다른 이야기다(32.12절) |
| **`lock` 비용** | 무경합이면 원자적 연산 몇 개, 경합이면 커널 대기 | 두 경우의 차이가 자릿수 단위다(D.4절) |

> **📌 나노초 · 클록 사이클 · 상대 배수의 관계**
>
> 세 단위는 서로 변환할 수 있지만 **이식성이 서로 다르다.**
>
> - **클록 사이클**은 CPU 마이크로아키텍처에 묶인다. 주파수가 달라져도 "L2 접근은 12사이클"은 같은 세대 칩에서 대체로 유지된다.
> - **나노초**는 주파수까지 반영한 실제 시간이다. 사용자가 체감하는 것은 이쪽이다.
> - **상대 배수**는 둘 다 버리고 순서만 남긴다. **가장 오래 살아남는 정보**이며, 이 부록에서 가장 신뢰할 만한 열이기도 하다.
>
> 변환식은 단순하다. `나노초 = 사이클 수 ÷ (GHz 단위 주파수)`. 2.30 GHz 기계에서 한 사이클은 대략 **0.4 ns**다(61.4절). 5.0 GHz면 0.2 ns다. 같은 "12사이클"이 4.8 ns가 되기도 하고 2.4 ns가 되기도 한다.

### 마이크로벤치마크가 거짓말하는 네 가지 방식

67.4절에서 자세히 다룬 내용의 요약이다. 이 부록의 표를 자기 손으로 재현하려 할 때 **가장 먼저 만나는 함정들**이라 여기에도 적어 둔다.

| 거짓말 | 증상 | 방어 |
|---|---|---|
| **JIT 워밍업** | 첫 호출이 100배 느리다. 계층형 컴파일 때문에 처음 수십 번은 Tier-0 코드다(55.2절) | 워밍업 반복을 충분히 돌린다. BenchmarkDotNet이 자동으로 한다 |
| **죽은 코드 제거** | "이 연산은 0 ns"라는 결과. JIT이 결과를 안 쓰는 계산을 통째로 지웠다 | 결과를 반환하거나 `Consumer`에 넘긴다 |
| **분기 예측** | 정렬된 입력에서만 빠르다. 벤치마크가 같은 분기를 백만 번 반복해 예측기를 훈련시킨다 | 실제 데이터 분포를 쓴다. 최소한 정렬/비정렬 두 벌을 잰다 |
| **캐시 상태** | 벤치마크 안에서만 데이터가 L1에 상주한다. 프로덕션에서는 매번 콜드 미스다 | 작업 집합 크기를 실제와 맞춘다. `[Params]`로 크기를 훑는다(D.2절 그래프 형태) |

> **⚠️ "이 표를 외웠다"가 가장 위험한 상태다**
>
> 성능 상수표의 최악의 사용법은 **코드 리뷰에서 이 표를 인용하며 반대표를 던지는 것**이다. "박싱은 4.3 ns니까 이 코드는 느립니다" 같은 문장은 두 가지를 동시에 틀린다. 첫째, 그 4.3 ns는 특정 기계의 특정 벤치마크 값이다. 둘째, 그 연산이 초당 몇 번 실행되는지를 말하지 않으면 4.3 ns는 아무 의미가 없다.
>
> 초당 100번 호출되는 경로에서 4.3 ns를 아끼면 **1초에 430 나노초**를 아낀다. 그것은 측정 오차보다 작다. D.8절이 이 문제만 따로 다룬다.

### 재현용 최소 골격 — BenchmarkDotNet

이 부록의 어떤 숫자든 자기 기계에서 다시 재려면 다음이 최소 골격이다. 옵션의 의미와 함정 전체는 67.3절과 67.4절에 있다.

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net8.0</TargetFramework>
    <!-- 릴리스 빌드가 아니면 측정값이 무의미하다 -->
    <Optimize>true</Optimize>
    <!-- 서버 GC 여부는 측정 결과를 바꾼다. 프로덕션과 맞춰라 -->
    <ServerGarbageCollection>false</ServerGarbageCollection>
  </PropertyGroup>
  <ItemGroup>
    <PackageReference Include="BenchmarkDotNet" Version="0.13.12" />
  </ItemGroup>
</Project>
```

```csharp
using BenchmarkDotNet.Attributes;
using BenchmarkDotNet.Running;

// [MemoryDiagnoser] 는 할당량을 함께 보고한다 (67.5절).
// 시간 측정에는 영향을 주지 않고 추가 반복을 한 번 더 돈다.
[MemoryDiagnoser]
public class AllocationCost
{
    private sealed class Node { public int Value; }
    private struct NodeStruct { public int Value; }

    // 반환값이 있어야 죽은 코드 제거를 피한다
    [Benchmark(Baseline = true)]
    public int ConsumeStruct()
    {
        var s = new NodeStruct();
        s.Value = 42;
        return s.Value;
    }

    [Benchmark]
    public int ConsumeClass()
    {
        var c = new Node();
        c.Value = 42;
        return c.Value;
    }
}

public static class Program
{
    // BenchmarkSwitcher 를 쓰면 명령줄 인자를 그대로 받는다 (67.3절)
    public static void Main(string[] args) =>
        BenchmarkSwitcher.FromAssembly(typeof(Program).Assembly).Run(args);
}
```

```bash
# 릴리스 구성이 아니면 BenchmarkDotNet이 경고하고 결과를 신뢰하지 말라고 말한다
dotnet run -c Release -- --filter '*AllocationCost*'
```

> **💡 골격에 반드시 넣어야 할 세 가지**
>
> 1. **`-c Release`.** 디버그 빌드 측정은 측정이 아니다. BenchmarkDotNet이 경고를 내지만 경고는 읽히지 않는 경향이 있다.
> 2. **반환값.** `[Benchmark]` 메서드가 `void`이고 결과를 아무 데도 안 쓰면 JIT이 본문을 지울 수 있다.
> 3. **`[MemoryDiagnoser]`.** 시간만 보면 "왜 느린가"를 알 수 없다. 할당량이 함께 있어야 원인이 GC 압력인지 아닌지가 갈린다.
>
> 그리고 결과에서 `Mean`만 보지 말고 **`StdDev`와 경고 목록**을 보라. 표준편차가 평균의 10%를 넘으면 그 측정은 아직 안정되지 않은 것이다.

### 이 부록의 표 읽기 규약

표마다 다음 세 가지를 캡션이나 각주에 밝힌다.

| 표기 | 뜻 |
|---|---|
| **[측정]** | 원천 도서 또는 본문 장에 실제 측정값이 있는 항목. 측정 환경을 함께 적었다 |
| **[구조]** | 측정이 아니라 자료구조·명세에서 나오는 값(객체 크기, 임계값, 정렬 규칙 등). 하드웨어를 타지 않는다 |
| **[예시]** | 원천에 절대값이 없어 **자릿수 또는 상대 순서만** 적은 항목. 절대값을 채우지 않았다 |

**빈칸(`—`)은 "0"이 아니라 "원천에 값이 없어 비워 뒀다"는 뜻이다.** 이 부록은 빈칸을 그럴듯한 숫자로 채우지 않는다.

## D.2 메모리 계층 지연 시간

> **⚠️ 이 절의 절대값을 믿지 말고 자기 하드웨어에서 측정하라**
>
> 아래 나노초 값은 **Intel Core i7-4712MQ(Haswell) 2.30 GHz 노트북 한 대**의 값이다. 캐시 지연은 마이크로아키텍처마다 다르고, 같은 칩에서도 접근 유형(로드/스토어, 정렬/비정렬, 프리페치 적중 여부)에 따라 다르다. **가져갈 것은 열 사이의 배수이지 나노초가 아니다.**

### 지연 시간 기준표

| 접근 대상 | 지연 시간 | 대략 사이클(2.30 GHz) | 주 메모리 대비 | 근거 |
|---|---|---|---|---|
| **레지스터** | 지연 없음 | 1 사이클 안 | — | [구조] |
| **L1 캐시** | < 2.0 ns | 5 사이클 미만 | 30배 이상 빠름 | [측정] |
| **L2 캐시** | 4.8 ns | 약 12 사이클 | 약 15배 빠름 | [측정] |
| **L3 캐시** | 14.4 ns | 약 36 사이클 | 약 5배 빠름 | [측정] |
| **주 메모리(DRAM)** | 71.4 ns | 약 178 사이클 | 1배(기준) | [측정] |
| **HDD** | 150,000 ns | 약 375,000 사이클 | 약 2,100배 느림 | [측정] |
| **NVMe SSD** | — | — | — | 원천에 값 없음 |
| **같은 데이터센터 네트워크 왕복** | — | — | — | 원천에 값 없음 |
| **인터넷 대륙 간 왕복** | — | — | — | 원천에 값 없음 |

> **출처** — 지연 시간 열은 원천 도서 2장 표 2-2. 측정 환경은 Intel Core i7-4712MQ(Haswell) 2.30 GHz. 사이클 열은 한 사이클을 **0.4 ns**(≈ 1/2.30 GHz)로 놓고 이 책이 환산한 **대략값**이다. 같은 표가 61.4절에 있다.

> **⚠️ NVMe와 네트워크 행은 의도적으로 비워 뒀다**
>
> 원천 도서의 표는 HDD까지만 다룬다. "NVMe는 100 μs쯤"이나 "데이터센터 왕복 0.5 ms" 같은 값은 널리 인용되지만 **이 책의 원천에는 없다.** 그럴듯한 숫자를 채워 넣으면 이 부록 전체의 신뢰도가 무너진다.
>
> 필요하면 직접 재라. 디스크는 `dd`/`fio`, 네트워크 왕복은 `ping`과 애플리케이션 레벨 계측(75장)이 답을 준다. **자기 인프라의 값이 어차피 인용값보다 정확하다.**

### 시각적 스케일 비유

나노초 단위의 차이는 직관이 작동하지 않는다. 1 사이클을 **1초**로 늘려 보면 격차가 보인다.

```text
── 1 CPU 사이클 = 1초 로 환산했을 때 (2.30 GHz 기준, 0.4 ns/사이클) ──

  레지스터        │ 1초                    지금 손에 들고 있다
                  │
  L1 캐시         │ 5초 미만               책상 위 메모지
                  │
  L2 캐시         │ 12초                   서랍을 연다
                  │
  L3 캐시         │ 36초                   자리에서 일어나 옆 책장
                  │
  주 메모리       │ 3분(178초)             엘리베이터 타고 다른 층 창고
                  │
  HDD             │ 4일 8시간(375,000초)   서류를 우편으로 신청한다
                  │
                  └──────────────────────────────────────────────
                    ※ 사이클 수는 0.4 ns/사이클 환산의 대략값이다.
                       HDD 값은 원천 도서의 150,000 ns를 환산한 것이다.
```

이 비유의 요점은 하나다. **L1과 DRAM 사이에 약 35배가 있고, DRAM과 디스크 사이에 약 2,100배가 있다.** 그래서 최적화의 우선순위도 대체로 그 순서다 — 디스크를 안 건드리는 것이 먼저고, 그다음이 DRAM을 덜 건드리는 것이다.

### 캐시 구조 상수

| 항목 | 값 | 근거 |
|---|---|---|
| **캐시 라인 크기** | 64바이트(오늘날 대부분의 컴퓨터) | [구조] |
| **한 번의 DRAM 전송 폭** | 64비트 = 8바이트 | [구조] |
| **캐시 라인 하나를 채우는 데 필요한 전송 횟수** | 8회 | [구조] |
| **L1 캐시(i7-4770K)** | 64 KiB (명령 32 KiB + 데이터 32 KiB) | [측정] |
| **L2 캐시(i7-4770K)** | 256 KiB | [측정] |
| **L3 캐시(i7-4770K)** | 8 MiB | [측정] |
| **일반적 페이지 크기(x86 · x64 · ARM)** | 4 kB | [구조] |
| **Windows 할당 단위(allocation granularity)** | 64 kB | [구조] |
| **Linux 할당 단위** | 페이지 크기(보통 4 kB) | [구조] |

> **출처** — 원천 도서 2장. 캐시 크기는 Intel i7-4770K 사양이며 원천 도서가 "시장 표준을 꽤 잘 반영한다"고 서술한 값이다. 상세 설명은 61.4절.

> **⚠️ 캐시 라인은 최소 전송 단위다 — 1비트를 읽어도 64바이트가 온다**
>
> 메모리에서 캐시 라인보다 작은 데이터를 읽거나 쓰는 것은 **불가능하다.** 1비트를 원해도 64바이트 라인 전체가 채워진다. 그래서 다음 두 문장이 성립한다.
>
> - **64바이트보다 작은 모든 메모리 접근은 비싼 자원의 낭비다.**
> - 데이터는 64바이트 경계에 정렬되므로, **연속된 두 바이트가 라인 경계에 걸치면 라인 두 개(총 128바이트)를 소비한다.**
>
> 거짓 공유(false sharing)가 왜 그렇게 파괴적인지도 여기서 나온다(70.6절). 서로 다른 스레드가 같은 64바이트 안의 서로 다른 변수를 쓰기만 해도 라인이 계속 무효화된다.

### 접근 패턴이 만드는 차이 — 실측

같은 알고리즘, 같은 데이터 양, 접근 순서만 바꾼 결과다.

| 접근 패턴 | PC | 노트북 | Raspberry Pi 2 |
|---|---|---|---|
| **행 단위(순차)** | 52 ms | 127 ms | 918 ms |
| **열 단위(비순차)** | 401 ms | 413 ms | 2,001 ms |
| **배수** | 약 7.7배 | 약 3.3배 | 약 2.2배 |

> **출처** — 원천 도서 2장 표 2-1. `n, m = 5000`인 `int` 2차원 배열에 순차/비순차로 쓰기. 세 기계는 PC(Intel Core i7-4770K 3.5 GHz), 노트북(Intel Core i7-4712MQ 2.3 GHz), Raspberry Pi 2(ARM Cortex-A7 0.9 GHz)다. 상세는 61.5절.

> **📌 배수가 기계마다 다른 것이 이 표의 핵심이다**
>
> 같은 코드가 PC에서는 7.7배, Raspberry Pi 2에서는 2.2배 차이를 낸다. 캐시가 크고 빠를수록 **캐시를 잘 쓰는 것과 못 쓰는 것의 격차도 커진다.** 그래서 "내 노트북에서 3배 개선"이 서버에서 7배가 되기도 하고, 반대로 컨테이너의 좁은 캐시 몫에서는 1.5배로 줄기도 한다.
>
> 이것이 D.1절 경고의 구체적 형태다. **개선의 크기 자체가 하드웨어에 따라 변한다.**

## D.3 CPU 연산 상대 비용

> **⚠️ 이 절의 절대값을 믿지 말고 자기 하드웨어에서 측정하라**
>
> 그리고 이 절에는 **비워 둔 칸이 가장 많다.** 정수 나눗셈이나 분기 예측 실패의 사이클 수 같은 값은 이 책의 원천 도서에 없다. CPU 제조사의 최적화 매뉴얼이나 직접 측정이 유일한 답이다.

### 상대 비용 순서표

| 연산 | 대략 비용 | 근거 |
|---|---|---|
| **레지스터 간 정수 산술(add, sub, and, or)** | 1 사이클대 | [예시] 자릿수만 |
| **정수 곱셈** | 정수 덧셈보다 여러 배 | [예시] 절대값 없음 |
| **정수 나눗셈 / 나머지** | 곱셈보다 다시 여러 배 — CPU 연산 중 가장 비싼 산술 | [예시] 절대값 없음 |
| **부동소수점 덧셈·곱셈** | 정수와 같은 자릿수 | [예시] 절대값 없음 |
| **부동소수점 나눗셈** | 부동소수점 산술 중 가장 비쌈 | [예시] 절대값 없음 |
| **L1 히트** | < 2.0 ns (D.2절) | [측정] |
| **분기 예측 성공** | 사실상 무료(파이프라인 유지) | [예시] |
| **분기 예측 실패** | — | 원천에 값 없음 |
| **L3 히트** | 14.4 ns (D.2절) | [측정] |
| **캐시 미스 → DRAM** | 71.4 ns (D.2절) | [측정] |
| **원자적 연산(`Interlocked`), 무경합** | — (D.4절 상대 측정 참조) | 절대값 없음 |
| **메모리 배리어** | — | 원천에 값 없음 |
| **시스템 콜** | — | 원천에 값 없음 |
| **컨텍스트 스위치** | — | **원천이 명시적으로 추정을 거부한다**(아래 박스) |

> **⚠️ 컨텍스트 스위치 비용에 숫자를 붙이지 마라 — 원천이 그러기를 거부했다**
>
> 원천 도서 중 하나는 이 문제를 정면으로 다루면서 다음과 같이 적었다. **"컨텍스트 스위치를 수행하는 데 걸리는 시간은 CPU 아키텍처와 속도에 따라 다르다. 각 컨텍스트 스위치에 얼마의 시간 오버헤드가 드는지 절대적인 수치는커녕 추정치조차 제시할 수 없다."**
>
> 대신 원천이 확정적으로 말하는 것은 이것이다.
>
> - **Windows는 약 30 ms마다 컨텍스트 스위치를 수행한다.** 이것은 오버헤드의 크기가 아니라 **빈도**다.
> - **컨텍스트 스위치는 순수한 오버헤드다.** 메모리 이득도 성능 이득도 없다. 최종 사용자에게 응답성을 주기 위해 존재한다.
> - 스위치 후 새 스레드는 **CPU 캐시가 자기 데이터로 채워질 때까지 느리게 실행된다.** 이 캐시 재구성이 스위치의 숨은 비용이다.
> - 스레드가 자기 시간 조각이 끝나기 전에 스스로 양보하고, 그때 실행할 다른 스레드가 없으면 Windows는 **컨텍스트 스위치를 하지 않는다.** 같은 스레드를 계속 돌린다.
>
> 실무 결론은 숫자 없이도 나온다. **CPU 코어 수보다 많은 스레드를 만들면 컨텍스트 스위치가 도입되고 성능이 나빠진다.** 코어당 스레드 하나면 스위치가 없고 스레드는 전속력으로 돈다(45.4절, 46장).

> **📌 왜 이 절의 절대값을 채우지 않았는가**
>
> "정수 나눗셈은 20~40사이클", "분기 예측 실패는 15~20사이클" 같은 값은 인터넷에 흔하다. 하지만 그 값들은 **특정 마이크로아키텍처의 최적화 매뉴얼에서 온 것**이고, 이 책의 원천 도서에는 없다. 여기에 적으면 이 부록의 다른 표(출처가 분명한 표)와 구분이 되지 않는다.
>
> 정말 필요하면 두 곳을 보라. **CPU 제조사의 최적화 참조 매뉴얼**(명령별 지연·처리량 표를 제공한다), 그리고 **자기 코드의 실측**(71장의 벡터화 판단이 이런 값에 직접 의존한다).

### 대신 확실하게 말할 수 있는 것 — 상대 순서

절대값은 없어도 순서는 안전하게 말할 수 있다. 이 순서는 하드웨어를 크게 타지 않는다.

```text
── 비용의 자릿수 사다리 (사이클 기준, 대략) ────────────────

   1사이클대   │ 정수 add/sub, 레지스터 이동, 예측 성공한 분기
               │
   ~5사이클    │ L1 히트
               │
   ~12사이클   │ L2 히트
               │
   ~36사이클   │ L3 히트
               │
   ~178사이클  │ DRAM 접근 (= 캐시 미스)
               │
   수백 사이클 │ 예외 던지기 (원천: "수백 클록 사이클 이상")
    이상       │
               │
   자릿수      │ 시스템 콜, 컨텍스트 스위치, GC 일시 중지
    미상       │ (원천에 값 없음 — D.4절의 상대 측정만 있다)
               │
   150,000 ns  │ HDD 접근
               └──────────────────────────────────────────
                 ※ 사이클 값은 D.2절 표를 0.4 ns/사이클로 환산한
                    대략값이다. 절대 기준으로 쓰지 마라.
```

> **⚠️ 캐시 미스 하나가 산술 명령 100개보다 비싸다**
>
> 위 사다리에서 가장 실무적인 함의가 이것이다. DRAM 접근 한 번(약 178사이클)은 정수 덧셈 100회 이상과 맞먹는다. 그래서 **"연산 횟수를 줄였는데 느려졌다"** 는 일이 자주 일어난다 — 연산은 줄었지만 메모리 접근 패턴이 나빠진 경우다.
>
> 70장 전체가 이 문제를 다룬다. AoS를 SoA로 바꾸는 것(70.3절), 첫 캐시 라인에 필요한 데이터를 다 넣는 것(70.1절)이 산술 최적화보다 먼저인 이유다.

### 원자적 연산과 잠금 — 경합이 만드는 차이

절대값은 없지만 **경합 상황의 상대 비용**은 실측이 있다.

| 방식 | 반복 10,000회 | 반복 100,000회 | 반복 1,000,000회 | 할당(1,000,000회) |
|---|---|---|---|---|
| `Interlocked.Increment` | 1.900 ms | 92.672 ms | 715.166 ms | 4.71 KB |
| `lock` (`Monitor`) | 13.274 ms | 139.899 ms | 1,323.899 ms | 5.04 KB |
| `ThreadLocal<long>` 집계 | 1.944 ms | 3.614 ms | 23.600 ms | 20.43 KB |

> **출처** — 원천 도서 13장 리스팅 13-12. BenchmarkDotNet, .NET 8. **스레드 32개**가 같은 카운터를 동시에 증가시키는 극단적 경합 상황이다. 원천 도서 자신이 "이것은 극단적 예이며 실제 시나리오에서는 결과가 더 대비될 것이므로 반드시 직접 측정하라"고 덧붙였다. 같은 표가 45.5절에 있고, `Interlocked`와 잠금의 메커니즘은 48.4절·48.9절이다.

> **⚠️ 이 표에서 읽어야 할 것은 "배수"가 아니라 "곡선의 모양"이다**
>
> 반복 10,000회에서 `Interlocked`는 `lock`보다 7배 빠르다. 그런데 1,000,000회에서는 1.85배로 좁혀진다. 반대로 `ThreadLocal`은 10,000회에서 `Interlocked`와 같지만 1,000,000회에서는 **30배 빠르다.**
>
> 즉 **어느 것이 빠른가는 경합 강도에 따라 순서가 바뀐다.** "Interlocked가 lock보다 빠르다"는 문장은 이 표의 첫 행에서만 크게 참이다. 스레드 수, 반복 횟수, 임계 구역 길이 중 하나만 바뀌어도 결론이 달라진다.
>
> `ThreadLocal<T>`에도 대가가 있다 — 할당이 네 배 이상이고, 파이널라이저를 가지며, 생성·정리 때 전역 잠금을 얻는다. 인스턴스를 많이 만들면 그 자체가 경합원이 된다.

## D.4 .NET 런타임 연산 비용

> **⚠️ 이 절의 절대값을 믿지 말고 자기 하드웨어에서 측정하라**
>
> 이 절의 실측값은 대부분 **BenchmarkDotNet, .NET 8** 기준이다. 런타임 버전이 바뀌면 값이 바뀌고, 특히 JIT 최적화(55장)와 BCL 벡터화(71.5절)의 영향을 크게 받는다. .NET 6에서 잰 값과 .NET 9에서 잰 값이 다른 것은 정상이다.

### 힙 할당 — 범프 포인터

| 항목 | 값 | 근거 |
|---|---|---|
| `ConsumeStruct`(구조체, 할당 없음) | **0.0327 ns** | [측정] |
| `ConsumeClass`(작은 클래스 인스턴스 1개 할당) | **4.3562 ns**, 32 B 할당 | [측정] |
| 배수 | 약 **133배** (다만 아래 박스를 읽어라) | — |

> **출처** — 원천 도서 4장 표 4-1. BenchmarkDotNet, .NET 8. `int` 필드 하나를 가진 클래스/구조체를 하나 만들고 필드에 대입한 뒤 읽는 메서드. 할당 경로의 메커니즘은 63.1절·63.3절.

> **⚠️ "할당은 133배 느리다"로 읽으면 안 된다**
>
> 분모가 0.0327 ns다. 이것은 **JIT이 구조체 버전을 사실상 레지스터 두 개짜리 코드로 줄여 버렸다**는 뜻이지 "구조체 사용이 0.03 ns"라는 뜻이 아니다. 원천 도서 자신도 이 결과를 "클래스 버전이 네 배 이상 느리다"라고 서술했다 — 133배가 아니라. (원천은 다른 문맥의 비교를 함께 서술했다.)
>
> 안전한 독법은 이것이다. **범프 포인터 할당 자체는 나노초 단위이며 매우 싸다.** 그런데도 구조체와 격차가 벌어지는 이유는 할당 그 자체가 아니라 ① 할당자 함수 호출, ② 필드 0 초기화, ③ **나중에 지불할 GC 비용**이다. 세 번째는 이 벤치마크가 거의 재지 못한다.

> **📌 할당의 진짜 비용은 다른 시점에 청구된다**
>
> 범프 포인터 할당은 포인터 하나를 더하는 일이다(63.1절). 그것만 보면 싸다. 비용은 **할당 예산이 소진되어 GC가 트리거될 때**(63.6절) 다른 형태로 나타난다 — 모든 관리 스레드가 멈추고(64.12절), 살아 있는 객체를 마킹하고, 필요하면 압축한다.
>
> 그래서 할당 최적화의 지표는 "할당 한 번의 나노초"가 아니라 **초당 할당 바이트(alloc-rate)와 gen0/gen1/gen2 수집 횟수**다. `dotnet-counters`로 보는 것들이다(66.8절, 부록 C).

### GC 비용 — 세대별

| 항목 | 값 | 근거 |
|---|---|---|
| 관측된 평균 GC 일시 중지(워크스테이션 GC, 특정 부하 테스트) | **4.33 ms** (627회 수집의 평균) | [측정] |
| "자주 발생하면 경보를 울려야 하는" 단일 일시 중지 | **수십 ms 초과** | [측정 아님 — 원천의 판단 기준] |
| "정규 웹 애플리케이션에서 경보 수준"인 GC CPU 점유율 | **10% 초과가 지속될 때** | [측정 아님 — 원천의 판단 기준] |
| gen0 수집 비용 | — | 원천에 세대별 절대값 없음 |
| gen1 수집 비용 | — | 원천에 세대별 절대값 없음 |
| gen2(전체) 수집 비용 | — | 원천에 세대별 절대값 없음 |

> **출처** — 평균 4.33 ms는 원천 도서 7장의 ETW CPU 프로파일링 부하 테스트 결과(워크스테이션 GC, 테스트 중 627회 수집). 판단 기준 두 줄은 원천 도서 11장의 서술. 세대별 비용은 원천이 절대값으로 제시하지 않았다. 메커니즘은 64장, 모드별 트레이드오프는 65.3절.

> **⚠️ "gen0은 싸고 gen2는 비싸다"에 숫자를 붙이려 하지 마라**
>
> 세대별 GC 비용은 **살아 있는 객체의 양에 비례**하지 세대 번호에 비례하지 않는다(64.2절). 대부분의 객체가 gen0에서 죽는 정상적인 애플리케이션에서는 gen0 수집이 싸다. 하지만 gen0의 객체 대부분이 살아남는 상황(중년기 위기 패턴, 66.12절)에서는 gen0 수집도 비싸진다 — 마킹할 것이 많고 승격할 것이 많기 때문이다.
>
> 그래서 이 표의 빈칸은 "아직 못 채웠다"가 아니라 **"채울 수 없는 성질의 값"** 이다. 자기 애플리케이션의 값은 `dotnet-counters`의 `time-in-gc`와 PerfView의 GCStats가 알려 준다(부록 C).

### 파이널라이저 — 할당 경로가 느려진다

| 객체 수(N) | 파이널라이저 없음 | 파이널라이저 있음 | 배수 |
|---|---|---|---|
| 1 | 2.777 ns | 132.138 ns | 약 48배 |
| 10 | 30.667 ns | 1,342.092 ns | 약 44배 |
| 100 | 316.633 ns | 13,607.436 ns | 약 43배 |
| 1,000 | 3,244.837 ns | 131,725.089 ns | 약 41배 |

> **출처** — 원천 도서 12장 리스팅 12-11·12-12. BenchmarkDotNet. `int` 필드 네 개짜리 클래스를 N개 만드는 루프. 두 버전의 JIT 결과 어셈블리는 **호출하는 할당자 함수만 다르다.** 원천 도서는 이를 "작은 파이널라이즈 가능 객체 할당이 일반 객체보다 약 40배 느리다"고 요약했다. 할당량은 양쪽 모두 동일(N당 32 B). 파이널라이제이션 메커니즘은 34.2절.

> **⚠️ 파이널라이저는 할당 시점부터 비용을 만든다**
>
> 흔한 오해는 "파이널라이저는 수집될 때만 비싸다"는 것이다. 위 표가 반박한다. **할당 자체가 느려진다** — 할당자가 파이널라이제이션 큐를 조작해야 하기 때문이다. 게다가 gen1 수집이 추가로 발생한다(객체가 추가 승격되므로).
>
> 실무 규칙은 명확하다. **할당 빈도가 높고 성능이 중요한 경로의 타입에 파이널라이저를 붙이기 전에 두 번 생각하라.** 비관리 자원을 잡고 있지 않다면 파이널라이저는 필요 없다(33장, 34.3절).

### 박싱

| 항목 | 값 | 근거 |
|---|---|---|
| 박싱 1회의 비용 | — | 절대값 없음 |
| 박싱이 하는 일 | 힙 할당 + 값 복사 + 객체 헤더·`MethodTable` 참조 부착 | [구조] |
| 박스 객체의 최소 크기(64비트) | **24 B** (헤더 8 + MT 8 + 데이터 자리 8) | [구조] |
| 박스 객체의 최소 크기(32비트) | **12 B** | [구조] |

> **출처** — 크기는 원천 도서 4장(D.6절 참조). 박싱 비용의 절대값은 원천에 없다. 원천은 "박스 인스턴스가 할당되고 데이터 복사가 추가 클록 사이클을 쓴다. 더 나쁜 것은 이 박스 인스턴스가 언젠가 수집되어야 하므로 GC에 압력을 준다"고만 서술한다. 문법·IL·회피 체크리스트는 15.2절·15.7절, 힙 표현은 54.6절.

> **💡 박싱을 잴 때는 시간이 아니라 할당량을 보라**
>
> 박싱 한 번의 나노초를 재려는 시도는 대체로 실패한다 — JIT이 최적화해 버리거나, 값이 측정 오차에 묻힌다. **`[MemoryDiagnoser]`의 `Allocated` 열이 훨씬 정직한 지표다.** 박싱이 있으면 할당이 있고, 없으면 없다.
>
> 이것이 67.5절이 "시간보다 할당을 먼저 보라"고 말하는 이유다. 할당량은 하드웨어를 타지 않는다. **같은 코드는 어느 기계에서도 같은 바이트를 할당한다.**

### 호출 방식 — 직접 / 가상 / 인터페이스 / 델리게이트

| 호출 방식 | 간접 참조 | 인라이닝 | 절대 비용 | 근거 |
|---|---|---|---|---|
| **정적·비가상 직접 호출** | 없음 | 가능 | — | [구조] |
| **가상 호출** | 객체 → `MethodTable` → 슬롯 → 코드 (2회) | 역가상화 성공 시에만 | — | [구조] |
| **인터페이스 호출** | 위 + 가상 스텁 디스패치(VSD) | 역가상화 성공 시에만 | — | [구조] |
| **델리게이트 호출** | 대상 객체 + 함수 포인터 경유 | 일반적으로 불가 | — | [구조] |

> **출처** — 구조 열은 54.1절·55.5절. `ClassAccess` 실측은 원천 도서 13장 리스팅 13-55(BenchmarkDotNet). **호출 방식별 절대 비용은 원천에 없어 비워 뒀다.**

> **⚠️ 호출 방식의 비용을 "간접 참조 몇 번"으로 세지 마라**
>
> 가상 호출의 직접 비용(간접 참조 두 번)은 D.2절 기준으로 캐시에 있으면 몇 사이클이다. 그것만 보면 무시할 만하다.
>
> **진짜 비용은 인라이닝이 막히는 것이다.** 어떤 구현이 불릴지 모르면 무엇을 펼쳐 넣을지도 모르고, 인라이닝이 막히면 그 뒤에 올 최적화 전부(상수 전파, 경계 검사 제거, 루프 최적화)가 함께 사라진다(55.4절·55.6절). 그래서 손해가 "간접 참조 두 번"이 아니라 **최적화 사슬 전체**가 된다.
>
> 동적 PGO의 가드된 역가상화(GDV)가 이 문제를 상당 부분 해결한다 ※.NET 8에서 기본 활성화(55.5절). 그래서 이 표의 빈칸은 **런타임 버전에 따라 답이 크게 달라지는 칸**이기도 하다.

### `Span<T>` — 런타임에 따라 결론이 뒤집힌다

| 방법 | .NET 8.0 | .NET Framework 4.8 |
|---|---|---|
| `SpanAccess` | **50.66 ns** (± 0.386) | **96.56 ns** (± 1.813) |
| `ArrayAccess` | 63.23 ns (± 0.540) | 66.49 ns (± 1.092) |

> **출처** — 원천 도서 14장 리스팅 14-16·14-17. BenchmarkDotNet. 128바이트 배열을 인덱스로 순회하며 합산. 상세는 68.3절.

> **⚠️ .NET Framework에서는 `Span<T>`가 배열보다 느리다 — 이것은 버그가 아니라 설계다**
>
> 이 표가 이 부록에서 가장 중요한 표일 수 있다. **같은 코드가 런타임에 따라 결론이 뒤집힌다.**
>
> .NET Core 계열에는 `Span<T>`를 위한 **런타임 지원**(내부 `ByReference<T>` 필드)이 있어 "fast span"이 된다. .NET Framework에는 그 지원이 없어 `System.Memory` NuGet 패키지의 "slow span" 구현이 쓰이고, 이는 관리 포인터 대신 객체 참조와 오프셋을 들고 다닌다(68.3절).
>
> **.NET Framework 전용 동작이다.** 멀티 타깃 라이브러리를 만들면서 `Span<T>`로 리팩터링했다면, `net48` 타깃에서 성능이 나빠지지 않았는지 반드시 따로 재라.

### 잠금 획득 — 무경합과 경합의 자릿수 차이

| 상황 | 무슨 일이 일어나는가 | 비용 |
|---|---|---|
| **무경합 `lock`** | 객체 헤더의 싱크 블록 인덱스를 원자적으로 갱신. 커널로 내려가지 않는다 | 원자적 연산 몇 개 수준 |
| **가벼운 경합** | 스핀 대기로 짧게 버틴다. 여전히 사용자 모드 | 스핀 횟수에 비례 |
| **본격 경합** | 커널 동기화 객체에서 대기. 스레드가 잠들고 깨어난다 | **컨텍스트 스위치가 개입한다**(D.3절) |

> **출처** — 구조 서술은 48.5절·48.12절, 싱크 블록의 위치는 54.2절. **절대 비용은 원천에 없어 비워 뒀다.** D.3절의 `Interlocked` / `lock` / `ThreadLocal` 비교표가 이 부록에 있는 유일한 경합 실측이며, 그것도 스레드 32개라는 극단 조건이다.

> **⚠️ 무경합 잠금이 싸다는 사실이 "잠그고 봐도 된다"는 뜻은 아니다**
>
> 무경합 `lock`은 실제로 싸다. 그런데 **잠금은 경합이 생기는 순간 자릿수가 바뀌는 종류의 비용**이다. 부하 테스트에서 스레드 네 개로 잰 값이 프로덕션의 스레드 200개에서 유지될 이유가 없다.
>
> 그리고 잠금의 진짜 위험은 성능이 아니라 정확성이다 — 데드락(48.8절), 잠금 범위 오류(48.6절), 이중 검사 잠금의 잘못된 구현(48.13절). **성능 표를 보고 잠금 설계를 하지 마라.**
>
> 경합을 재는 지표는 `dotnet-counters`의 `monitor-lock-contention-count`다(66.8절, 부록 C).

### 리플렉션 — 자릿수만

| 호출 경로 | 직접 호출 대비 자릿수 | 호출당 할당 |
|---|---|---|
| 직접 호출 | 1배(기준) | 없음 |
| 델리게이트(`CreateDelegate`) / 컴파일된 식 트리 | **같은 자릿수**(나노초) | 없음 |
| `[UnsafeAccessor]` ※.NET 8 | **같은 자릿수** | 없음 |
| `MethodInvoker.Invoke` ※.NET 8 | **두 자릿수 느림**(수십 나노초) | 있다(값 타입 인수 박싱) |
| 캐시된 `MethodInfo.Invoke` | **두 자릿수 느림** | 있다(인수 배열 + 박싱) |
| 매번 `GetMethod` + `Invoke` | **세 자릿수 느림**(마이크로초) | 가장 많다 |

> **출처** — 57.12절의 표. **그 절 자체가 "이 표의 절대값을 인용하지 마라, 읽어야 할 것은 비율의 자릿수"라고 밝히고 있으므로, 이 부록은 자릿수 열만 옮기고 나노초 값을 옮기지 않았다.** 원천 도서의 서술도 절대값 없이 이유만 열거한다 — 메타데이터 문자열 검색(대소문자 무시면 더 느리다), 인수를 배열로 포장했다가 스레드 스택으로 다시 푸는 작업, 인수 타입 검사, 접근성 검사.

| 리플렉션 API | 무엇을 하는가 | 캐싱 가능성 |
|---|---|---|
| `obj.GetType()` | `MethodTable` 참조에서 `Type`을 얻는다. 문자열 검색 없음 | 가장 싸다 |
| `typeof(T)` | 컴파일 타임에 토큰이 박힌다 | 사실상 무료 |
| `Type.GetType("이름")` | **문자열로 메타데이터를 스캔한다** | 결과를 반드시 캐싱 |
| `Type.GetProperty` / `GetMethod` | 문자열 검색 + 오버로드 해석 | 결과(`PropertyInfo`/`MethodInfo`)를 정적 필드에 캐싱 |
| `MethodInfo.Invoke` | 인수 포장·검사·언박싱 | **호출 자체는 캐싱해도 남는다** |

> **⚠️ "리플렉션을 캐싱했다"가 "리플렉션 비용을 없앴다"는 뜻은 아니다**
>
> `MethodInfo`를 정적 필드에 캐싱하면 **조회 비용**(세 자릿수 → 두 자릿수)은 사라진다. 그러나 **호출 비용**은 남는다 — 인수 배열 할당, 값 타입 박싱, 타입 검사, 접근성 검사는 매 호출마다 다시 한다.
>
> 조회를 캐싱해도 자릿수가 하나만 줄어든다. 나머지 하나를 마저 없애려면 **델리게이트로 바꿔야 한다**(57.13절) — `CreateDelegate`나 컴파일된 식 트리, 또는 아예 소스 생성기로 리플렉션을 제거하는 것(57.15절)이다.
>
> 그리고 트리밍·Native AOT 환경에서는 성능 이전에 **동작 자체가 깨질 수 있다**(57.14절, 55.7절).

### `async` 상태 기계

| 상황 | 상태 기계 할당 | 태스크 할당 | 근거 |
|---|---|---|---|
| **`await`에 한 번도 도달하지 않고 동기 완료** | **0** — 상태 기계는 `struct`이며 스택에서 태어나 스택에서 죽는다 | `Task<T>`는 남는다. 논제네릭 `Task`는 캐시된 완료 태스크를 재사용한다 | [구조] |
| **한 번이라도 일시 정지** | **1** — 상태 기계당 정확히 한 번만 힙으로 올라간다 | .NET Core 2.1+에서는 상자 자체가 `Task<TResult>`를 상속하므로 **상자 하나**로 끝난다 | [구조] |
| **두 번째 이후의 `await`에서 일시 정지** | 추가 할당 없음(이미 힙에 있다) | — | [구조] |
| **디버그 빌드** | 상태 기계가 처음부터 `class`다 — **항상 힙 할당** | — | [구조] |

> **출처** — 47.7절·47.8절. 상태 기계 생성과 박싱 댄스의 전 과정이 그 두 절에 있다. **절대 시간 비용은 원천에 없어 비워 뒀다.**

> **⚠️ 디버그 빌드로 `async` 할당을 측정하면 릴리스와 다른 숫자가 나온다**
>
> 릴리스 빌드에서 컴파일러가 만드는 상태 기계는 `struct`다. 디버그 빌드에서는 디버거 경험(특히 편집하며 계속하기)을 위해 `class`로 만든다. **즉 디버그 빌드에서는 박싱 댄스가 아예 일어나지 않고 처음부터 힙에 있다.**
>
> D.1절 체크리스트의 "릴리스 빌드에서 쟀는가"가 여기서 구체적 형태를 얻는다. `async` 메서드의 할당을 디버그로 재면 **없는 할당을 보게 된다.**

> **💡 `async` 메서드의 진짜 성능 함정은 할당이 아니라 인라이닝이다**
>
> `async` 변환은 메서드 하나를 상태 기계 타입 하나로 통째로 재작성한다. 그 결과 코드가 팽창하고, **작은 `async` 메서드조차 JIT이 인라이닝하지 못한다**(47.7절). `ValueTask<T>`로 할당을 0으로 만든 메서드도 마찬가지다.
>
> 그래서 "아주 짧고 대체로 동기 완료하는 작업"을 `async`로 감싸는 것은 할당 이전에 호출 비용 문제다. 동기 경로가 압도적이면 동기 오버로드를 따로 두는 편이 나은 경우가 있다(47.13절).

### 예외

| 항목 | 값 | 근거 |
|---|---|---|
| 예외를 **던지지 않을 때** `try`/`catch`의 비용 | 정확히 결정할 수 없다(플랫폼·JIT마다 다름) | [측정 아님] |
| 예외를 **던질 때** | **수백 클록 사이클 이상** | [측정 아님 — 원천의 서술] |
| 스택 깊이의 영향 | 1단계 탐색과 2단계 언와인딩 모두 **프레임 수에 비례** | [구조] |
| `StackTrace` 문자열 생성 | 접근하지 않으면 지불하지 않는다 | [구조] |

> **출처** — "수백 클록 사이클 이상"은 원천 도서의 서술("relatively expensive to handle, taking hundreds of clock cycles or more"). 32.12절이 이 주제 전체를 다룬다.

> **💡 예외 비용의 실무적 형태는 "초당 몇 개인가"다**
>
> 예외 하나가 수백 사이클이라면 초당 10개는 아무 문제가 아니다. 초당 10,000개면 심각하다. 그래서 봐야 할 지표는 예외 하나의 나노초가 아니라 **`dotnet-counters`의 `exception-count`** 다(66.8절).
>
> 그리고 흔한 사고 형태는 성능이 아니라 **제어 흐름 오용**이다. 정상 경로에서 예외를 던지는 코드는 느린 것보다 읽기 어려운 것이 더 큰 문제다. `TryXXX` 패턴이 답이다(32.9절).

## D.5 컬렉션 연산 복잡도표

> **⚠️ Big-O는 하드웨어를 타지 않지만, 실제 시간은 전적으로 하드웨어를 탄다**
>
> 이 절의 복잡도 표는 **[구조]** 값이라 어느 기계에서도 같다. 그러나 "그래서 어느 것이 빠른가"의 답은 D.2절의 캐시 상수가 결정한다. 임계점은 반드시 자기 데이터·자기 하드웨어에서 재라(67장).

### Big-O 요약

| 컬렉션 | 순서 | 연속 저장 | 조회 | 삽입/삭제 | 인덱스 접근 |
|---|---|---|---|---|---|
| `T[]` | 인덱스 | O | 값: O(N) / 인덱스: O(1) | 불가(고정 크기) | O(1) |
| `List<T>` | 삽입 순 | O | 값: O(N) / 인덱스: O(1) | 끝: 분할상환 O(1) / 중간: O(N) | O(1) |
| `LinkedList<T>` | 삽입 순 | X | O(N) | 노드를 알 때 O(1) | 불가 |
| `Queue<T>` | FIFO | O | 앞: O(1) | O(1) | 불가 |
| `Stack<T>` | LIFO | O | 위: O(1) | O(1) | 불가 |
| `Dictionary<K,V>` | 없음 | O | 키: O(1) | O(1) | 불가 |
| `HashSet<T>` | 없음 | O | 키: O(1) | O(1) | 불가 |
| `SortedDictionary<K,V>` | 키 순 | X | 키: O(log N) | O(log N) | 불가 |
| `SortedList<K,V>` | 키 순 | O | 키: O(log N) | O(N) | O(1) |
| `SortedSet<T>` | 값 순 | X | O(log N) | O(log N) | 불가 |
| `ConcurrentDictionary<K,V>` | 없음 | O | 키: O(1) | O(1) | 불가 |
| `ImmutableList<T>` | 인덱스 | X | O(log N) | O(log N) (구조 공유) | O(log N) |
| `ImmutableArray<T>` | 인덱스 | O | 인덱스: O(1) | O(N) (전체 복사) | O(1) |
| `FrozenDictionary<K,V>` | 없음 | O | 키: O(1)이면서 상수가 작다 | 불가 | 불가 |

> **출처** — 24.15절의 표를 그대로 옮기고 `ConcurrentDictionary` 행을 더했다. 원천 도서의 딕셔너리 계열 요약("`Hashtable`·`Dictionary`·`OrderedDictionary`는 O(1), `SortedDictionary`·`SortedList`는 O(log n), `ListDictionary`와 비딕셔너리 타입은 O(n)")과도 일치한다. 각 타입의 내부 구조는 24.4·24.5·24.6·24.7·24.8·24.10·24.11·24.12절.

### 왜 상수 인자가 다른가 — 연속 메모리 vs 포인터 추적

같은 O(1), 같은 O(log N)이라도 실제 시간이 열 배씩 갈리는 이유는 **한 연산이 캐시 라인을 몇 개 건드리느냐**다.

```text
── 같은 "원소 8개 순회", 자료구조에 따른 캐시 라인 소비 ──

  int[8] (연속)
  ┌───────────────────────────────────────────────┐
  │ [0][1][2][3][4][5][6][7]  ← 32바이트, 캐시 라인 1개 │
  └───────────────────────────────────────────────┘
    메모리 접근: 1회.  프리페처가 다음 라인도 미리 가져온다.

  LinkedList<int> 노드 8개 (포인터 추적)
  ┌──────┐   ┌──────┐   ┌──────┐        ┌──────┐
  │ node │──▶│ node │──▶│ node │─ ... ─▶│ node │
  └──────┘   └──────┘   └──────┘        └──────┘
     ▲          ▲          ▲               ▲
     └ 힙의 서로 다른 곳에 흩어져 있을 수 있다
    메모리 접근: 최악의 경우 8회.  각 노드는 24 B 헤더 + 필드.
    다음 노드 주소를 읽기 전까지 프리페처가 할 일이 없다
    (포인터 추적은 예측 가능한 패턴이 아니다).
```

| 자료구조 성질 | 상수 인자에 미치는 영향 | 관련 절 |
|---|---|---|
| **연속 저장** | 캐시 라인 하나에 여러 원소. 프리페처가 작동한다 | 61.5절, 70.1절 |
| **포인터 추적** | 원소마다 캐시 미스 가능. 프리페처가 무력하다 | 61.6절 |
| **노드마다 객체 헤더** | 64비트에서 노드당 최소 24 B 오버헤드 | 54.3절, D.6절 |
| **해시 계산** | O(1)의 "1"에 해시 함수 비용이 들어 있다. 문자열 키는 길이에 비례 | 24.7절 |
| **버킷 + 엔트리 두 배열** | 조회 한 번에 서로 다른 두 배열을 건드린다 | 24.7절 |
| **트리 균형 유지** | O(log N)의 각 단계가 포인터 추적이다 | 24.8절 |
| **동시성 자료구조** | 원자적 연산·잠금 분할·메모리 배리어가 상수에 더해진다 | 24.12절, 48.4절 |

> **⚠️ 작은 N에서는 O(N) 배열 탐색이 O(1) 딕셔너리를 이긴다**
>
> `Dictionary` 조회는 해시 계산 → 버킷 인덱스 계산 → 버킷 배열 접근 → 엔트리 배열 접근 → 키 비교다. 배열 8개 선형 탐색은 캐시 라인 하나를 읽고 예측이 잘 맞는 루프를 도는 것이다.
>
> **임계점의 구체적 숫자는 키 타입과 하드웨어에 따라 달라지므로 이 부록은 값을 적지 않는다.** 방향만 확실하다 — 원소가 수십 개 이하이고 조회가 핫 경로가 아니면, `Dictionary`로 바꾸는 것이 이득이 아닐 수 있다. 72.6절이 이 주제를 다룬다.

> **📌 `SortedList`와 `SortedDictionary`는 같은 O(log N)이 아니다**
>
> 둘 다 조회가 O(log N)이지만 자료구조가 다르다. `SortedList`는 **정렬된 배열 두 개**(키·값)를 유지하며 이진 탐색한다 — 연속 메모리라 조회 상수가 작지만 **중간 삽입이 O(N)** 이다(뒤를 전부 민다). `SortedDictionary`는 **균형 이진 트리**라 삽입도 O(log N)이지만 조회마다 포인터를 추적한다.
>
> 그래서 선택 기준은 복잡도가 아니라 **삽입/조회 비율**이다. 한 번 채우고 계속 읽으면 `SortedList`, 계속 섞어 쓰면 `SortedDictionary`(24.8절).

> **⚠️ 인터페이스로 받으면 구조체 열거자가 박싱된다**
>
> `List<T>`, `Dictionary<K,V>`, `HashSet<T>`, `Queue<T>` 등의 `GetEnumerator()`는 **구조체 열거자**를 반환한다. `foreach`가 이걸 직접 쓰면 할당이 없다. 그런데 변수 타입이 `IEnumerable<T>`가 되는 순간 구조체 열거자가 인터페이스로 박싱되고, `MoveNext`/`Current`가 인터페이스 호출이 되며, 인라이닝이 막힌다.
>
> Big-O는 그대로다. 바뀌는 것은 상수와 할당량뿐이다. 그래서 이 함정은 **복잡도 표를 아무리 봐도 보이지 않는다.** 72.6절에 코드 형태가 있다.

## D.6 타입·객체 크기표

>

### 객체 헤더 구조 — 64비트 / 32비트

```text
── 힙 객체의 최소 구성 (64비트 CoreCLR) ──────────────────

           ┌────────────────────────────────┐  ← 참조 - 16
    -16    │ 정렬 패딩              (4B)     │  ┐ 객체 헤더 8B
    -12    │ 싱크 블록 인덱스        (4B)     │  ┘ (실제로 쓰는 것은 4B)
           ├════════════════════════════════┤
참조 ─────▶│ MethodTable 참조       (8B)     │  ← 참조가 가리키는 곳
     +8    ├────────────────────────────────┤
           │ 선택적 데이터 자리      (8B)     │  ← 첫 필드 / 배열 길이 /
           │                                │     free object 크기로 재사용
           └────────────────────────────────┘
             합계 24 B — 필드가 하나도 없어도 이것이 최소다
```

| 구성 요소 | 64비트 | 32비트 |
|---|---|---|
| 객체 헤더(싱크 블록 인덱스 + 정렬 패딩) | 8 B (실사용 4 B + 패딩 4 B) | 4 B |
| `MethodTable` 참조 | 8 B | 4 B |
| 최소 한 개의 포인터 크기 데이터 자리 | 8 B | 4 B |
| **최소 객체 크기** | **24 B** | **12 B** |
| 정렬 | 8 B 배수 | 4 B 배수 |

> **출처** — 원천 도서 4장. .NET 소스의 `MIN_OBJECT_SIZE` 정의(`2 * TARGET_POINTER_SIZE + OBJHEADER_SIZE`)와 그 주석("세대별 GC는 모든 객체가 최소 12바이트일 것을 요구한다")이 근거다. 54.2절·54.3절이 이 구조를 다룬다.

> **⚠️ 필드 1바이트짜리 클래스도 힙에서 24바이트다**
>
> 원천 도서의 표현이 정확하다 — **"스택에 할당된 단일 바이트 구조체는 그 1바이트만 차지한다. 64비트 런타임에서 단일 바이트를 담은 클래스는 힙에서 24바이트를 차지한다."**
>
> 객체 하나가 24바이트인 것 자체는 문제가 아니다. 문제는 **작은 객체가 아주 많을 때**다. 참조 둘과 `int` 하나를 가진 노드 백만 개는 데이터가 노드당 20 B인데 실제 점유는 40 B다 — 절반이 메타데이터와 정렬이다(54.3절).

### 클래스 인스턴스 크기 실측표

| 정의 | 필드 데이터 | 32비트 힙 크기 | 64비트 힙 크기 |
|---|---|---|---|
| `class Empty {}` | 0 B | 12 B | 24 B |
| `class OneByte { byte b; }` | 1 B | 12 B | 24 B |
| `class OneInt { int i; }` | 4 B | 12 B | 24 B |
| `class TwoInts { int a, b; }` | 8 B | 16 B | 24 B |
| `class ThreeInts { int a, b, c; }` | 12 B | 20 B | 32 B |
| `class FourInts { int a,b,c,d; }` | 16 B | 24 B | 32 B |
| `class OneRef { object o; }` | 4 또는 8 B | 12 B | 24 B |

> **출처** — 54.3절의 표. 계산식은 `헤더 + MT 참조 + max(필드 합계, 포인터 크기)`를 정렬 단위로 올림한 것이다.

### 문자열 크기 계산식

| 런타임 | 공식 | `""` | `"A"` | `"Hello, World!"` (13자) |
|---|---|---|---|---|
| 64비트 | (22 + 2×길이)를 **8의 배수**로 올림 | 24 B | 24 B | 48 B |
| 32비트 | (14 + 2×길이)를 **4의 배수**로 올림 | 16 B | 16 B | 40 B |

> **출처** — 54.7절. 64비트의 22 B는 헤더 8 + `MethodTable` 참조 8 + `_stringLength` 4 + 널 종결자 2다. 문자 하나는 UTF-16 2바이트다.

> **⚠️ 문자열의 메모리 비용을 문자 수로 어림하지 마라**
>
> 빈 문자열이 24바이트다. **세 글자짜리 문자열 100만 개는 문자 데이터로는 6 MB지만 실제 힙 점유는 32 MB다.** 짧은 문자열이 딕셔너리 키로 대량 존재하는 애플리케이션에서는 오버헤드가 데이터보다 크다.
>
> 대응은 셋이다 — 인터닝, 자체 중복 제거, 그리고 **애초에 문자열을 만들지 않기**(`ReadOnlySpan<char>` 슬라이싱, 68.5절).

### 배열·가변 길이 타입

| 항목 | 값 | 근거 |
|---|---|---|
| 크기 계산식 | `BaseSize + ComponentSize × 요소 개수` | [구조] |
| `ComponentSize` | 요소 하나의 크기. 일반 클래스에서는 0 | [구조] |
| 1차원 배열의 요소 개수 저장 위치 | 객체의 "선택적 데이터 자리"를 재사용 | [구조] |

> **출처** — 54.3절·54.7절. `MethodTable`의 `BaseSize`/`ComponentSize` 필드가 이 계산을 수행한다(54.1절).

### 구조체 레이아웃 — 정렬과 패딩의 실제 비용

| 정의 | 레이아웃 | 필드 데이터 | 실제 크기 | 패딩 |
|---|---|---|---|---|
| `struct { byte B; double D; int I; }` | Sequential(기본) | 13 B | **24 B** | 11 B (45%) |
| 같은 필드 + `[StructLayout(Auto)]` | Auto | 13 B | **16 B** | 3 B (19%) |
| 같은 필드 + `Pack = 1` | Sequential, Pack=1 | 13 B | **13 B** | 0 B |
| 같은 필드 + `object O` 추가 | Auto(강제) | 21 B | **24 B** | 3 B |
| `struct { byte×4, double×4 }` | Sequential(기본) | 36 B | **64 B** | 28 B (44%) |
| 같은 필드 + `[StructLayout(Auto)]` | Auto | 36 B | **40 B** | 4 B (10%) |
| `class { byte B; double D; int I; }` | Auto(강제) | 13 B | **32 B** (힙) | 헤더 16 + 패딩 3 |

> **출처** — 54.4절의 계산표. C# 컴파일러는 참조 타입에 `LayoutKind.Auto`, unmanaged 구조체에 `LayoutKind.Sequential`을 기본값으로 고른다.

> **💡 필드 순서를 크기 내림차순으로 쓰는 습관**
>
> `Sequential` 레이아웃에서 필드 순서는 개발자가 쓴 그대로 유지된다. 그래서 `byte, double, int` 순서는 45%를 패딩으로 날리고, `double, int, byte` 순서면 그렇지 않다.
>
> 상호운용용이 아닌 구조체라면 `[StructLayout(LayoutKind.Auto)]`를 붙여 CLR에게 재배치 권한을 주는 것이 더 간단하다. 다만 **`Auto`는 필드 순서가 보장되지 않으므로 P/Invoke 구조체에는 절대 쓰면 안 된다**(60장).

## D.7 임계값 표

> **⚠️ 이 절의 값은 대부분 [구조]지만, 몇몇은 런타임 버전에 따라 바뀐다**
>
> 특히 세그먼트 크기와 할당 예산은 .NET 7의 리전 도입(62.6절)과 .NET 8의 DATAS(65.7절)로 크게 달라졌다. **아래 값이 자기 런타임에서도 맞는지는 `GC.GetConfigurationVariables()`와 `GC.GetGCMemoryInfo()`로 확인하라**(65.8절).

### 힙 분할 임계값

| 항목 | 값 | 비고 |
|---|---|---|
| **LOH 임계값** | **85,000바이트** | 이 값 **이상**이면 LOH. `85 × 1024`가 아니다 |
| LOH 임계값 조정 | `System.GC.LOHThreshold` 런타임 구성으로 **증가만** 가능 | 62.3절 |
| LOH 임계값이 적용되는 크기 | 객체의 **얕은 크기(shallow size)** | 참조로 매달린 그래프 크기가 아니다 |
| **32비트에서 `double[]`의 특수 규칙** | 요소 **1,000개 이상**이면 크기와 무관하게 LOH(8,000바이트여도 LOH) | 정렬 문제 회피. 64비트에는 없다 |
| NonGC 힙에 들어갈 수 있는 리터럴 최대 크기 | **64 KB 미만** | 초과하면 일반 객체로 — 85,000바이트 미만이면 gen0, 이상이면 LOH (62.5절) |
| LOH 정렬 | 비트 수와 무관하게 **8바이트** | 62.3절 |

> **출처** — 원천 도서 5장·6장, 62.3절·62.5절. 원천 도서의 경고를 그대로 옮긴다 — **"이 임계값은 85,000바이트이지만, 사람들이 85 × 1024 = 85 KiB로 잘못 해석하는 경향이 있다."**

> **⚠️ `List<T>`의 내부 배열은 조용히 LOH로 넘어간다**
>
> 참조 타입 원소 8,192개면 64비트에서 내부 배열이 65,536바이트다. 이 정도까지는 SOH지만 **배증을 한 번 더 하면 131,072바이트가 되어 LOH를 넘는다.** LOH는 기본적으로 압축되지 않고 gen2와 함께 수집된다(62.3절).
>
> 큰 리스트를 반복해서 만들고 버리는 코드는 LOH 단편화를 만든다. 대안은 `ArrayPool<T>`(69.3절)나 스트리밍 처리다.

### 크기·개수 한계

| 항목 | 값 | 비고 |
|---|---|---|
| **기본 최대 객체 크기** | **2 GB** | .NET 초기부터의 값 |
| 2 GB 초과 배열 허용 | `gcAllowVeryLargeObjects` (.NET Framework 4.5+) | 다른 한계는 바꾸지 않는다 |
| **배열의 최대 요소 개수** | **2,147,483,591** | |
| **단일 차원 최대 인덱스** (`byte[]`·단일바이트 구조체 배열) | **2,147,483,591** (0x7FFFFFC7) | |
| **단일 차원 최대 인덱스** (그 외 타입) | **2,146,435,071** (0x7FEFFFFF) | |
| 문자열·비배열 객체의 최대 크기 | `gcAllowVeryLargeObjects`로도 바뀌지 않는다 | |
| **최소 객체 크기** | 24 B(64비트) / 12 B(32비트) | D.6절 |

> **출처** — 원천 도서 6장. `gcAllowVeryLargeObjects`는 **.NET Framework 구성 파일 설정**이며, 최신 .NET에서는 대응 런타임 구성 노브를 확인해야 한다.

### 스택 관련 임계값

| 항목 | 값 | 비고 |
|---|---|---|
| **`stackalloc` 실무 권장 상한** | **1 kB 이하** | 원천 도서의 명시적 권고 |
| Windows(ARM64·x86·x64) 기본 스레드 스택 | **1 MB** | 실행 파일 헤더에서 온다 |
| .NET 런타임이 계산하는 기본값(32비트 / 64비트 빌드) | **1 MB / 4 MB** | 고정 상수가 아니다 |
| 전형적 최신 Linux | **8 MB** | `ulimit -a`로 확인 |
| `localloc` 스택 프레임 증가 반올림 단위 | 32비트 8 B / **64비트 16 B** | x64 ABI의 16바이트 정렬 요구 |

> **출처** — `stackalloc` 상한은 원천 도서 6장("작은 버퍼에만, 1 kB를 넘지 않게"). 스택 크기 표는 45.4절, `localloc` 반올림은 63.7절.

> **⚠️ `StackOverflowException`은 잡을 수 없다 — 프로세스가 죽는다**
>
> `stackalloc`의 위험은 다른 실패와 성격이 다르다. **`StackOverflowException`은 `try`/`catch`로 막을 수 없는 예외이며, 완화 가능성 없이 애플리케이션 전체를 죽인다.**
>
> 그래서 요소 개수를 런타임에 받는 `stackalloc`은 **반드시 상한 분기**를 넣어야 한다. 크기가 작을 때만 `stackalloc`, 크면 힙 배열이나 `ArrayPool<T>`로 폴백하는 삼항 패턴이 표준이다(63.7절·68.9절).
>
> 그리고 **루프와 재귀 안에서는 절대 쓰지 않는다.** `stackalloc`한 메모리는 메서드가 끝날 때까지 반환되지 않으므로, 루프 안의 `stackalloc`은 반복 횟수만큼 스택을 소비한다.

| 페이지 크기(x86·x64·ARM) | **4 kB** |
| Windows 할당 단위 | **64 kB** |
| Linux 할당 단위 | 페이지 크기 경계(보통 4 kB) |
| DRAM 전송 폭 | 64비트 = 8 B |
| Windows 컨텍스트 스위치 주기 | 약 **30 ms** |

> **출처** — 원천 도서 2장(D.2절과 동일 근거), 컨텍스트 스위치 주기는 원천 도서의 스레딩 장.

### GC 할당 예산 (참고 — 버전 의존성이 크다)

| 항목 | 값 | 조건 |
|---|---|---|
| gen0 **최소** 할당 예산 | **8 MB(워크스테이션) / 10 MB(서버)** | **L3 캐시 16 MB 가정.** 칩마다 다르게 계산된다 |
| gen0 **최대** 할당 예산 | **8~200 MB** | 워크스테이션+동시 GC는 8 MB. 그 외는 임시 세그먼트 절반, 최소 6 MB·최대 200 MB |

| 힙 | 워크스테이션 32비트 | 워크스테이션 64비트 | 서버 32비트 | 서버 64비트 |
|---|---|---|---|---|
| SOH | 16 MB | 256 MB | 64 MB(≤4코어) / 32 MB(≤8코어) / 16 MB(>8코어) | 4 GB(≤4코어) / 2 GB(≤8코어) / 1 GB(>8코어) |

> **출처** — 원천 도서 5장 표 5-3. **이 표는 세그먼트 기반 GC(~.NET 6)의 것이다.** .NET 7부터 기본이 리전으로 바뀌었고 크기 체계가 다르다(62.6절).

### 리전 기본 크기 (※.NET 7 이상 — 64비트 전용)

| 항목 | 값 | 비고 |
|---|---|---|
| 기본 리전 크기 | **4 MB** | 하나의 리전은 하나의 세대만 담는다 |
| 대형 리전 크기 | **32 MB** | |
| 대형 리전보다 큰 할당 | **거대 리전(huge region)** 이 만들어지며 여전히 LOH로 취급 | |
| 32비트 런타임 | 리전이 아니라 **세그먼트** — 위 표가 그대로 적용된다 | 62.6절 |

> **출처** — 62.6절. 리전 도입으로 "ephemeral 세그먼트"라는 개념 자체가 64비트에서 사라졌다. 버전을 밝히지 않은 세그먼트 설명은 .NET 6 이하를 전제한 것으로 읽어야 한다.

### 카드 테이블·카드 번들 (세대 간 참조 추적)

| 단위 | 덮는 힙 영역 (64비트) | 32비트 | 근거 |
|---|---|---|---|
| 카드 1개 (비트 1개) | **256 B** | 128 B | [구조] |
| 카드 테이블의 바이트 1개 (8카드) | **2,048 B** | 1,024 B | [구조] |
| 카드 워드 1개 (DWORD, 32카드) | **8,192 B** | 4,096 B | [구조] |
| 카드 번들 비트 1개 (카드 워드 32개) | **256 kB** | — | [구조] |
| 카드 번들 바이트 1개 | **2 MB** | — | [구조] |
| 카드 번들 워드 1개 (4바이트) | **8 MB** | — | [구조] |

> **출처** — 62.7절. 쓰기 장벽의 `shr rcx, 0Bh`(2¹¹ = 2,048로 나누기)가 이 표의 두 번째 행을 코드에서 확인해 준다. 늙은 세대가 2 GB면 카드 테이블은 1 MB, 카드 번들 테이블은 1,024 B다.

> **⚠️ 예약(reserve)과 커밋(commit)을 혼동하면 이 표를 오해한다**
>
> 원천 도서의 사례가 이 함정을 잘 보여 준다. 8코어 64비트 서버 GC로 도는 ASP.NET 애플리케이션은 SOH 세그먼트 8개(각 2 GB)와 LOH 세그먼트 8개(각 256 MB)를 잡아 **약 18 GB가 예약**되어 보인다. 그런데 **실제 사용(커밋)은 8 MB**였다.
>
> 모니터링이 가상 바이트를 보고 경보를 울리는 사고가 여기서 나온다. 봐야 할 것은 커밋된 바이트와 워킹 세트다(61.3절, 62.2절).

## D.8 최적화 판단 기준

> **⚠️ 이 절에는 절대 수치가 거의 없다 — 그것이 정확한 상태다**
>
> "이 정도 차이는 무시해도 된다"의 선은 하드웨어가 아니라 **애플리케이션의 요구사항**이 긋는다. 그래서 이 절은 숫자 대신 질문 목록을 제공한다.

### 신경 쓸 가치가 있는가 — 판정 순서

### 선을 어디에 긋는가 — 자릿수별 판단

| 절감 규모 | 대체로 이런 뜻이다 | 판단 |
|---|---|---|
| **나노초 단위, 초당 수백 회 실행** | 1초에 마이크로초를 아낀다 | 무시한다. 가독성이 이긴다 |
| **나노초 단위, 초당 수백만 회 실행** | 1초에 수십~수백 ms를 아낀다 | 볼 만하다. 재고 결정한다 |
| **마이크로초 단위, 요청당 1회** | 요청 지연에 마이크로초 | 무시한다 |
| **밀리초 단위, 요청당 1회** | 요청 지연에 직접 반영 | 본다 |
| **할당 제거** | 시간 절감은 작아도 GC 압력이 준다 | **실행 횟수가 많으면 시간보다 중요할 수 있다** |
| **알고리즘 복잡도 개선** | N이 커질수록 배수가 커진다 | 항상 우선한다 |
| **I/O 왕복 제거** | D.2절 기준 자릿수가 다르다 | **거의 항상 최우선** |

> **⚠️ 할당 제거는 시간 표로 판단하면 안 된다**
>
> 할당 하나를 없애 4 ns를 아낀다고 하자. 초당 1,000회면 4 μs다 — 무시할 값이다. 그런데 **할당 32 B × 1,000회 = 초당 32 KB**이고, 이것은 gen0 예산(D.7절 기준 8 MB대)을 지속적으로 갉아먹는다. GC가 더 자주 돌면 그 비용은 **다른 스레드의 일시 중지**로 나타난다.
>
> 그래서 할당의 판단 기준은 시간 표가 아니라 **`alloc-rate`와 gen0 수집 빈도**다(66.8절). "시간은 거의 같은데 할당이 절반"이면 그것은 대체로 개선이다.

> **⚠️ "느린 것"과 "느려 보이는 것"을 구분하라**
>
> D.4절의 표에서 `ClassArrayAccess`가 `StructArrayAccess`보다 4.6배 느리다. 이 숫자만 보고 도메인 모델 전체를 구조체로 바꾸는 것이 이 부록이 만들 수 있는 최악의 결과다.
>
> 그 벤치마크는 **큰 배열을 순회하며 필드 하나만 읽는** 특수한 형태다. 그 형태가 아니라면 4.6배는 나오지 않는다. 게다가 구조체 전환에는 대가가 있다 — 복사 비용(D.4절의 값/참조 전달 표), 박싱 위험, 가변 구조체의 함정(16.2절). 69.1절의 손익 계산표가 이 판단을 위해 존재한다.

## 이 부록의 요약

- **이 부록의 절대값은 전부 특정 기계·특정 런타임의 관측 하나다.** 자릿수와 상대 순서만 가져가고, 결정 전에 자기 환경에서 다시 재라. 이 경고를 각 절 첫머리에 반복해 둔 것은 실수가 아니다.

- **메모리 계층의 격차는 L1과 DRAM 사이 약 35배, DRAM과 디스크 사이 약 2,100배다.** 최적화 우선순위도 대체로 그 순서다. 캐시 미스 한 번이 산술 명령 100개보다 비싸므로, "연산을 줄였는데 느려졌다"는 흔한 일이다.

- **캐시 라인은 64바이트이며 최소 전송 단위다.** 1비트를 읽어도 64바이트가 온다. 64바이트보다 작은 접근은 전부 낭비이고, 거짓 공유가 파괴적인 이유도 여기 있다.

- **CPU 연산의 절대 사이클 수는 이 부록의 원천에 없어 비워 뒀다.** 특히 컨텍스트 스위치는 원천이 명시적으로 추정을 거부했다. 대신 확실한 것은 코어 수보다 많은 스레드가 스위치를 도입한다는 사실이다.

- **할당의 진짜 비용은 할당 시점이 아니라 GC 시점에 청구된다.** 그래서 지표는 "할당 한 번의 나노초"가 아니라 초당 할당 바이트와 세대별 수집 횟수다. 파이널라이저는 할당 자체를 약 40배 느리게 만든다.

- **같은 코드의 결론이 런타임에 따라 뒤집힌다.** `Span<T>`는 .NET 8에서 배열보다 빠르지만 .NET Framework 4.8에서는 느리다. 멀티 타깃 라이브러리에서 반드시 따로 재야 하는 이유다.

- **Big-O가 같아도 실제 시간이 열 배 갈리는 이유는 캐시 라인 소비량이다.** 연속 저장은 프리페처가 돕고, 포인터 추적은 원소마다 캐시 미스 후보다. 작은 N에서 배열 선형 탐색이 딕셔너리를 이기는 것도 같은 이유다.

- **64비트에서 필드 없는 객체도 24바이트, 빈 문자열도 24바이트다.** 작은 객체가 많을 때 메타데이터가 데이터보다 커진다. 세 글자 문자열 100만 개는 문자 데이터 6 MB에 힙 점유 32 MB다.

- **LOH 임계값은 85,000바이트이지 85 KiB가 아니고, `stackalloc`의 실무 상한은 1 kB다.** 후자를 어기면 잡을 수 없는 `StackOverflowException`으로 프로세스가 죽는다.

- **"신경 쓸 가치"의 선은 절감량이 아니라 절감량 × 실행 횟수가 긋는다.** 그리고 그 값이 측정 잡음보다 작으면 하지 않는 것이 옳다. 최적화 전 체크리스트 열두 개 중 1번(목표)과 11번(병목 확인)만 지켜도 대부분의 헛수고가 사라진다.

## 연습 문제

1. D.1절의 BenchmarkDotNet 골격을 그대로 실행해 `ConsumeStruct` / `ConsumeClass`를 재라. D.4절의 표(0.0327 ns / 4.3562 ns)와 자기 값을 비교하고, **배수가 얼마나 다른지** 기록하라. 그다음 `[Benchmark]` 메서드의 반환값을 `void`로 바꿔 다시 돌리고 결과가 어떻게 변하는지 확인하라(67.4절의 죽은 코드 제거).

2. D.2절의 계층별 지연을 자기 기계에서 근사하라. 크기를 `[Params(1_000, 10_000, 100_000, 1_000_000, 10_000_000)]`으로 훑으며 64바이트 간격으로 배열을 순차 읽는 벤치마크를 작성하고, **원소당 평균 시간이 꺾이는 지점**을 찾아라. 그 지점이 자기 CPU의 L2·L3 크기와 맞는지 대조하라.

3. D.2절의 행/열 접근 표(52 ms vs 401 ms)를 재현하라. `n, m = 5000`인 2차원 배열에 행 단위와 열 단위로 쓰기를 수행하고 자기 기계의 배수를 구하라. 그다음 배열 크기를 줄여 L2에 들어가게 만들고 배수가 어떻게 변하는지 관찰하라.

4. D.4절의 파이널라이저 벤치마크를 재현하라. `int` 필드 네 개짜리 클래스를 파이널라이저 있는 버전과 없는 버전으로 만들고 `[Params(1, 10, 100, 1000)]`으로 재라. **배수가 N에 따라 일정한지** 확인하고, `[MemoryDiagnoser]`의 Gen1 열이 파이널라이저 버전에서만 0이 아닌 이유를 설명하라(34.2절).

5. D.4절의 문자열 표 두 개를 자기 기계에서 재현하라. 시나리오 A(64회 반복 추가)와 시나리오 B(조각 서너 개 포매팅)를 각각 만들고, **어느 시나리오에서 `StringBuilder`가 지는지** 확인하라. 그다음 `string.Create` 버전을 추가해 세 방법의 코드 복잡도와 성능을 함께 평가하라(69.5절).

6. D.6절의 객체 크기표를 WinDbg + SOS로 검증하라. `class Empty {}`부터 `class FourInts`까지 인스턴스를 만들어 붙잡아 두고, `!dumpheap -type`으로 찾은 뒤 `!objsize`로 크기를 확인하라. 표의 값과 다르면 어느 필드에서 정렬 패딩이 생겼는지 `!dumpobj`로 추적하라(54.10절).

7. D.7절의 LOH 임계값을 실험으로 확인하라. `new byte[N]`을 `N = 84_000`부터 `86_000`까지 100씩 늘려 가며 만들고, 각각에 대해 `GC.GetGeneration(obj)`과 `GC.GetGCMemoryInfo()`의 LOH 크기 변화를 기록하라. 경계가 정확히 85,000바이트인지, 그리고 **배열 헤더 크기 때문에 요소 개수 기준 경계가 어디인지** 계산하라.

8. D.8절의 체크리스트를 자기 팀의 최근 성능 개선 PR 하나에 적용하라. 열두 항목 중 **실제로 지켜진 것이 몇 개인지** 세고, 지켜지지 않은 항목 때문에 그 개선이 무효화될 가능성이 있는지 판단하라. 특히 12번(회귀 테스트)이 없다면 지금 추가하라(67.8절).
