# 부록 B. 메모리 관리 규칙 26개 요약

> **이 부록의 위치** — 61장부터 70장까지 열 개 장에 걸쳐 .NET의 메모리 관리를 해부했다. 원천 도서는 각 장 끝에 그 장에서 얻은 교훈을 **규칙(Rule)** 이라는 이름의 짧은 항목으로 정리해 두었고, 이 책도 해당 장의 끝에서 그것을 소개했다. 이 부록은 흩어져 있는 스물여섯 개를 **한 자리에 모아 주제별로 재배열한 것**이다. 새로운 사실을 가르치려는 것이 아니다. 코드 리뷰 중에, 성능 회의 중에, 프로덕션 사고 대응 중에 펼쳐 놓고 "지금 어느 규칙을 어기고 있는가"를 빠르게 짚기 위한 목록이다.
>
> **선수 지식** — 61장(메모리의 기초), 62장(.NET 힙의 구조), 63장(할당), 64장(GC 알고리즘 완전 해부), 65장(GC 모드와 튜닝), 66장(메모리 문제 진단), 67장(측정 없이 최적화 없다)
>
> **이 부록에서 다루지 않는 것** — 각 규칙의 **근거가 되는 메커니즘**은 본문이 담당한다. 이 부록은 규칙마다 "왜"를 두세 문단으로 압축하고 나머지는 절 번호로 돌린다. 규칙에서 언급하는 회피 기법의 구현(풀링, `Span<T>`, `string.Create` 등)은 68·69장에, 진단 도구의 조작법은 66장에, 벤치마킹 방법론은 67장에 있다. `IDisposable`과 파이널라이저의 문법·패턴은 33장과 34장이다.

## B.1 이 목록을 쓰는 법

### 규칙 목록이 위험한 물건인 이유

성능에 관한 규칙 목록은 **읽는 사람을 게으르게 만드는 부작용**을 반드시 동반한다. "박싱을 피하라"는 여섯 글자를 외운 사람이 코드 리뷰에서 `object`를 볼 때마다 반대표를 던지기 시작하면, 그 팀은 규칙을 얻은 대신 판단력을 잃는다.

이 목록의 규칙은 전부 **조건부 명제**다. 원천 도서가 각 규칙에 "적용 범위(Applicability)"를 붙여 둔 이유가 그것이다. 어떤 규칙은 "가능한 한 일반적"이고, 어떤 규칙은 "극도로 저수준인 성능 지향 코드"에만 해당한다. 이 구분을 지우면 규칙 26개는 그냥 26개의 미신이 된다.

> **⚠️ 규칙을 맥락 없이 적용하면 규칙을 어기는 것보다 나쁘다**
>
> 대표적인 사고 형태가 셋 있다.
>
> **첫째, 구조체 전환.** "규칙 8 — 구조체 사용을 고려하라"를 읽고 도메인 모델 전체를 `struct`로 바꾸는 경우다. 16.8절과 69.1절의 손익 계산표가 존재하는 이유가 이것이다. 큰 구조체를 컬렉션에 담고 자주 복사하면 힙 할당 하나를 없앤 대가로 복사 비용을 수백 번 지불한다.
>
> **둘째, 풀링.** "규칙 15 — 과도한 UOH 할당을 피하라"를 읽고 모든 배열을 `ArrayPool<T>`로 감싸는 경우다. 반납을 잊은 버퍼는 누수가 되고, 반납 후에도 참조를 들고 있는 버퍼는 **조용한 데이터 손상**이 된다(69.3절). 풀링은 GC 압력을 수동 수명 관리와 맞바꾸는 거래다.
>
> **셋째, 명시적 GC.** "규칙 21 — 메모리 누수를 피하라"를 읽고 누수가 의심되는 지점마다 `GC.Collect()`를 뿌리는 경우다. 이것은 규칙 20을 정면으로 어긴다. 누수는 `GC.Collect()`로 고쳐지지 않는다 — 고쳐진다면 애초에 누수가 아니었다.
>
> 세 사고의 공통점은 **측정 없이 규칙을 적용했다**는 것이다.

### 순서가 있다 — 측정 우선

스물여섯 개는 평등하지 않다. **네 개는 나머지 스물두 개보다 먼저 적용되어야 한다.**

```text
   ┌────────────────────────────────────────────────────────────┐
   │  0단계 — 알고 있는가                                        │
   │  규칙 1 (스스로를 교육하라)                                 │
   │  → 무엇을 측정해야 하는지 모르면 측정해도 소용없다           │
   └───────────────────────────┬────────────────────────────────┘
                               ▼
   ┌────────────────────────────────────────────────────────────┐
   │  1단계 — 재고 있는가                                        │
   │  규칙 6 (프로그램을 측정하라)                               │
   │  규칙 5 (GC를 일찍 측정하라)                                │
   │  → 기준선 없이는 개선도 악화도 판정할 수 없다                │
   └───────────────────────────┬────────────────────────────────┘
                               ▼
   ┌────────────────────────────────────────────────────────────┐
   │  2단계 — 문제가 있다고 확인했는가                            │
   │  규칙 7 (누수가 있다/없다고 가정하지 마라)                   │
   │  규칙 11·13·17·19 (세대·세그먼트·중단·단편화 관찰)          │
   │  → 증상 없이 처방하지 않는다                                │
   └───────────────────────────┬────────────────────────────────┘
                               ▼
   ┌────────────────────────────────────────────────────────────┐
   │  3단계 — 코드를 고친다                                      │
   │  규칙 8·9·10·12·14·15·16·18·21·22·25·26                    │
   │  → 여기서부터가 "최적화"다                                  │
   └───────────────────────────┬────────────────────────────────┘
                               ▼
   ┌────────────────────────────────────────────────────────────┐
   │  4단계 — 그래도 부족하면 런타임을 만진다                     │
   │  규칙 23·24·20·4                                            │
   │  → 설정 변경은 코드 개선보다 나중이다                        │
   └────────────────────────────────────────────────────────────┘
```

이 순서가 이 부록의 실질적인 결론이다. **4단계를 3단계보다 먼저 하는 팀이 매우 많다.** GC 모드를 서버로 바꾸고, 지연 시간 모드를 만지고, 힙 개수를 조정하는 것은 코드를 고치지 않아도 되니 매력적으로 보인다. 그러나 65.10절이 반복해서 말한 대로, **배열 하나를 풀링하는 것이 GC 설정 다섯 개를 조정하는 것보다 거의 항상 효과가 크다.**

> **💡 규칙 목록을 코드 리뷰 체크리스트로 바꾸지 마라**
>
> "이 PR은 규칙 10을 어겼다"라는 형태의 리뷰 코멘트는 대개 무익하다. 유익한 형태는 질문이다 — **이 경로가 초당 몇 번 실행되는가.** 핫 패스라면 여기 박싱이 하나 있다는 지적이 의미를 갖고(15.2절), 아니라면 지금 형태가 더 읽기 좋다는 결론이 나온다.
>
> 규칙은 **판결문이 아니라 질문지**다. 규칙 하나마다 "③ 언제 예외인가" 칸을 둔 이유가 이것이다.

## B.2 할당 — 규칙 14 · 16 · 9

가장 먼저 손대게 되는 영역이다. GC의 일은 전적으로 할당의 함수이므로, **할당을 줄이면 GC 오버헤드는 자동으로 줄어든다.** 반대 방향은 성립하지 않는다 — GC 설정을 조정해도 할당은 줄지 않는다.

### 규칙 14 — 핫 패스에서 힙 할당을 피하라

**① 규칙**
성능이 중요한 경로에서는 힙 할당을 만들지 마라. 명시적 할당과 숨은 할당 모두를 대상으로 한다.

**② 왜**
"할당은 싸다"는 말은 절반만 맞다. 빠른 경로는 실제로 어셈블리 명령 예닐곱 개로 끝나고 락도 시스템 호출도 없다(63.1절). 그러나 그 문장이 감추는 것이 셋 있다.

- **할당은 메모리 트래픽을 만든다.** 할당한 만큼 캐시가 밀려나고, 새 객체는 차가운 캐시 라인에 놓인다(61.4절).
- **할당은 예산을 소모한다.** GC는 자리가 없어서 도는 것이 아니라 **할당 예산이 소진되어** 돈다(63.6절). 할당량이 곧 GC 횟수다.
- **모든 할당이 빠른 경로를 타지는 않는다.** 할당 컨텍스트가 소진되면 느린 경로로 내려가 프리 리스트 순회, 페이지 커밋, 0 채우기를 지불한다(63.2절).

그래서 할당 회피는 GC 튜닝의 상위 개념이다. 할당이 0인 코드에는 조정할 GC 설정이 없다.

**③ 언제 예외인가**
"핫 패스에서"라는 한정이 규칙의 절반이다. **핫 패스가 아닌 곳에서 이 규칙을 적용하면 거의 항상 손해다.** 69장이 정리한 다섯 가지 손해 사례가 그대로 예외 목록이 된다 — 측정이 지목하지 않은 코드, 가독성 손실이 이득보다 큰 변경, 풀 관리 버그의 기대 비용이 더 큰 경우, 버퍼 수명이 추적되지 않는 비동기 경로, 런타임이 이미 하고 있는 최적화를 되돌리는 코드.

그리고 **애플리케이션 시작 시 한 번 만들어지는 객체는 아무리 커도 이 규칙의 대상이 아니다.** 대상은 "자주 실행되는 코드"이지 "큰 객체"가 아니다.

**④ 본문 참조**
숨은 할당 카탈로그는 (63.9절), 라이브러리 내부의 할당을 찾는 방법은 (63.10절), 할당을 실제로 없애는 기법 전체는 (69장), 핫 패스에서 0으로 만드는 워크스루는 (69.9절). 할당량 측정은 (67.5절).

> **⚠️ "할당이 없다"는 벤치마크 결과를 그대로 믿지 마라**
>
> BenchmarkDotNet의 `Allocated` 열은 `stackalloc`, 비관리 할당, **다른 스레드의 할당**을 세지 않는다(67.5절). `Allocated`가 0인데 프로덕션에서 GC가 도는 상황은 흔하고, 대개 원인은 비동기 경로에서 다른 스레드로 넘어간 할당이다.

### 규칙 16 — 적절할 때 스택에 할당하라

**① 규칙**
클래스를 기본 선택지로 두지 말고, 값 타입과 `stackalloc`으로 스택에 놓을 수 있는지를 먼저 검토하라.

**② 왜**
스택 할당의 이점은 셋이다. **할당 비용이 0에 가깝고**(스택 포인터를 미는 것이 전부다, 61.1절), **해제 비용도 0이며**(메서드 반환 시 SP가 올라간다), **지역성이 좋다**(같은 프레임의 데이터가 같은 캐시 라인에 놓일 확률이 높다, 61.5절). 여기에 하나가 더 붙는다 — 참조 필드가 없는 값 타입은 **쓰기 장벽을 발생시키지 않는다**(64.11절).

`stackalloc`과 `Span<T>`의 결합(68.9절)은 이 규칙을 실행 가능한 형태로 만든 결정적 도구다. `unsafe` 없이 스택 버퍼를 안전하게 다룰 수 있게 되면서 규칙 16의 적용 범위가 크게 넓어졌다.

**③ 언제 예외인가**
스택은 **희소 자원**이다. .NET 스레드 스택 기본 크기는 32비트에서 1 MB, 64비트에서 4 MB다(61.1절). 실무 기준선은 `stackalloc` 1 kB 이하이고, 크기가 런타임 값이면 반드시 상한 분기를 넣는다(63.7절).

그리고 세 가지 상황에서는 이 규칙을 적용하면 안 된다.

- **루프나 재귀 안의 `stackalloc`.** 블록은 반복이 끝나도 회수되지 않는다 — 회수 시점은 메서드 반환이다(68.9절). 결과는 `StackOverflowException`이고, 그 예외는 잡을 수 없다.
- **비동기 메서드 경계를 넘는 버퍼.** `ref struct`는 `await`를 넘지 못한다(68.1절). 넘겨야 한다면 `Memory<T>`와 풀이 답이다.
- **큰 구조체를 자주 복사하는 코드.** 힙 할당 하나를 없앤 대가로 복사를 수백 번 하게 되면 순손해다(69.1절).

**④ 본문 참조**
스택 할당과 `stackalloc`은 (63.7절), `Span<T>`와의 결합은 (68.9절), `ref struct`의 제약은 (68.1절), 인라인 배열은 (68.10절), 손익 계산표는 (69.1절).

> **⚠️ `stackalloc` 실패는 잡을 수 없다**
>
> `stackalloc`이 스택을 넘기면 `StackOverflowException`이 나고, .NET에서 이 예외는 **`catch`로 잡을 수 없으며 프로세스가 즉시 종료된다**(63.7절). 힙 할당 실패(`OutOfMemoryException`)와 실패 모드 자체가 다르다는 뜻이다. 그래서 크기가 런타임 값이면 반드시 상한 분기를 넣고, 상한을 넘으면 `ArrayPool`로 떨어지는 형태가 표준 관용구다.
>
> ```csharp
> // 표준 관용구 — 작으면 스택, 크면 풀
> const int StackLimit = 256;
> byte[] rented = null;
> Span<byte> buffer = length <= StackLimit
>     ? stackalloc byte[StackLimit]
>     : (rented = ArrayPool<byte>.Shared.Rent(length));
> try
> {
>     Span<byte> work = buffer[..length];
>     // ... work 사용
> }
> finally
> {
>     if (rented is not null) ArrayPool<byte>.Shared.Return(rented);
> }
> ```
>
> 이 형태가 규칙 16과 규칙 15를 동시에 만족시키는 이유는, **작은 경우에 할당을 없애고 큰 경우에 UOH 할당을 없애기** 때문이다.

### 규칙 9 — 문자열 인터닝을 고려하라

**① 규칙**
같은 내용의 문자열이 메모리에 대량으로 중복되어 있다면, 명시적 인터닝으로 중복을 제거하는 것을 검토하라.

**② 왜**
문자열은 거의 모든 프로그램에서 가장 흔한 타입 중 하나다. 내용이 같은 문자열을 여러 개 들고 있는 것은 순수한 낭비이고, 문자열이 불변이므로 하나로 합쳐도 의미가 달라지지 않는다(35.1절). 런타임은 **리터럴에 대해서는 이 최적화를 이미 하고 있다** — 같은 문자 시퀀스를 참조하는 두 `ldstr`의 결과는 같은 객체임이 보장된다(35.5절). 규칙 9는 그 최적화를 **런타임에 만들어진 문자열로 확장하라**는 제안이다. 파일이나 HTTP 요청에서 읽어 온 문자열이 대상이다.

**③ 언제 예외인가**
**이 규칙은 이 목록에서 가장 위험한 규칙이다.** 인터닝된 문자열은 런타임 내부 구조가 참조를 붙들고 있으므로 **애플리케이션이 끝날 때까지 절대 수집되지 않는다.** 평범한 관리 힙 객체이므로 결국 세대 2로 승격되어 거기 영원히 남는다(35.5절). 즉 **인터닝은 의도적으로 만드는 메모리 누수**다.

원천 도서가 제시하는 판별 질문은 정확히 하나다.

| 상황 | 인터닝 |
|---|---|
| 중복된 문자열이 **수 분~수 시간 동안 살아 있다** | 검토할 가치가 있다 |
| 입력 처리 중 **짧게 폭발했다 사라진다** | 적용하면 손해다 — 죽었어야 할 문자열이 영구히 산다 |

그리고 인터닝 대상이 사용자 입력이면 **공격 벡터**가 된다. 서로 다른 문자열을 계속 보내는 것만으로 프로세스 메모리를 무한히 키울 수 있다.

**④ 본문 참조**
인터닝의 동작과 저장 위치, 누수처럼 보이는 이유는 (35.5절). 인터닝 풀을 키우지 않고 중복만 제거하는 `IsInterned` 패턴도 같은 절이다. 문자열 자체의 할당을 없애는 쪽이 대개 더 낫고, 그 기법은 (69.5절).

> **💡 규칙 9보다 먼저 시도할 것**
>
> 중복 문자열이 문제라면 인터닝 전에 두 가지를 먼저 본다. **첫째, 애초에 문자열을 만들지 않는 경로**가 있는가 — `Span` 슬라이싱으로 파싱하면 중간 문자열 자체가 생기지 않는다(69.5절). **둘째, 도메인 타입으로 바꿀 수 있는가** — 반복되는 몇 개의 값이라면 열거형이나 심볼 객체가 정답이다(35.10절의 string-ly typed API 논의). 인터닝은 이 둘이 모두 불가능할 때의 마지막 수단이다.

## B.3 수명과 참조 — 규칙 11 · 12 · 18

.NET GC의 성능은 **세대 가설이 성립하는가**에 전적으로 달려 있다. 이 절의 세 규칙은 모두 "가설이 깨지는 것을 감지하고 막아라"는 하나의 이야기다.

### 규칙 11 — 세대 크기를 관찰하라

**① 규칙**
세대 0·1·2와 LOH의 크기가 시간에 따라 어떻게 변하는지를 상시 관찰하라.

**② 왜**
약한 세대 가설 — 객체는 젊어서 죽거나 아주 오래 산다 — 이 .NET 세대별 GC의 토대다(62.4절). 그런데 **가설이 성립하는지는 프로그램마다 다르다.** 비정상적인 객체 생성 패턴을 가진 프로그램은 가설을 위반하고, 그 순간 세대별 GC의 이점이 전부 사라진다.

세대 크기 추이는 그 위반을 가장 싸게 감지하는 지표다. 두 가지 이상 신호가 있다.

| 신호 | 의미 |
|---|---|
| 한 세대 이상이 **계속 증가한다** (GC가 여러 번 돈 뒤에도) | 메모리 누수 가능성 |
| 한 세대 이상이 **매우 빈번하게 변한다** | 승격·사망으로 인한 큰 메모리 트래픽. 비싼 GC를 유발한다 |

**③ 언제 예외인가**
**세대 크기만 보는 것은 함정이다.** 세대 2의 크기가 안정적인데도 그 안에서 객체가 격렬하게 교체되는(churn) 상황이 있다. 크기는 평평한데 세대 2 GC에 시간을 다 쓰는 것이다. 그래서 세대 크기 관찰은 **`% Time in GC` 같은 CPU 오버헤드 지표와 항상 함께** 해야 한다(62.4절, 66.12절).

또한 세대 크기의 **절댓값에는 정상 범위가 없다.** 판단 근거는 언제나 추세와 이전 버전과의 비교다.

**④ 본문 참조**
세대와 세대 가설은 (62.4절), 승격과 강등의 실제 동작은 (64.6절), 세대별 인식 분석은 (66.13절), 중년기 위기의 식별은 (66.12절).

> **📌 세대 크기와 함께 봐야 할 짝 지표**
>
> 규칙 11을 실제로 운영하려면 지표를 짝으로 묶어야 한다. 하나만 보면 반드시 오독한다.
>
> | 세대 크기 지표 | 반드시 함께 볼 것 | 짝을 안 보면 놓치는 것 |
> |---|---|---|
> | gen0 크기 | 할당률, gen0 GC 횟수 | 예산이 커져서 크기가 큰 것인지, 살아남는 게 많은 것인지 |
> | gen1 크기 | gen1 → gen2 승격량 | 중년기 위기의 전조 |
> | gen2 크기 | `% Time in GC`, gen2 GC 횟수 | 크기는 평평한데 churn이 심한 상태 |
> | LOH 크기 | 단편화 비율 | 실제 객체가 아니라 구멍이 차지한 공간 |
>
> 이 표의 오른쪽 열이 전부 "크기만으로는 알 수 없는 것"이다. 그래서 규칙 11의 실제 문장은 "세대 크기를 관찰하라"가 아니라 **"세대 크기를 CPU 오버헤드와 함께 관찰하라"** 로 읽어야 한다.

### 규칙 12 — 불필요한 힙 참조를 피하라

**① 규칙**
특히 오래 사는 버퍼·캐시에서, 없어도 되는 객체 참조를 만들지 마라.

**② 왜**
세대별 GC는 세대 사이의 참조를 추적해야 한다. .NET은 이를 **쓰기 장벽 + 카드 테이블**로 구현한다(62.7절, 64.11절). 참조 하나를 필드에 저장할 때마다 쓰기 장벽 코드가 실행되고, 카드 테이블의 해당 바이트가 더럽혀지며, 다음 GC에서 그 영역이 다시 스캔된다. 구현이 매우 정교하지만, **가장 좋은 세대 간 참조는 존재하지 않는 참조**다.

효과는 두 시점에 나타난다. **쓰기 시점**에 장벽 코드가 사라지고, **GC 시점**에 스캔할 카드가 줄어든다. 참조 필드가 0개인 구조체가 특히 이득이 큰 이유가 이것이다(69.1절).

원천 도서가 드는 전형적인 변환은 이진 트리다. 노드가 자식 노드의 **참조**를 들고 있는 대신, 노드를 배열에 담고 **인덱스**를 들고 있게 만드는 것이다.

```csharp
// 참조 기반 — 노드마다 참조 두 개. 저장할 때마다 쓰기 장벽이 붙는다.
class Node
{
    Data d;
    Node left;
    Node right;
}

// 인덱스 기반 — 참조가 사라진다. 노드는 배열에 담긴다.
class Node
{
    Data d;
    uint leftIndex;
    uint rightIndex;
}
```

**③ 언제 예외인가**
이 변환은 **공짜가 아니다.** 원천 도서 자신이 경고하는 대로, 이 변경은 코드 전반에 파급된다 — 노드 배열은 어떻게 할당할 것인가, 노드마다 배열 조회가 하나씩 늘어나는데 그래프 순회 성능은 어떻게 되는가. **오직 견실한 벤치마킹만이 이 규칙의 적용이 이득인지 답할 수 있다.**

그리고 적용 대상이 좁다. 대상은 **오래 사는 대규모 자료 구조**다. 일반적인 도메인 객체 사이의 참조를 인덱스로 바꾸는 것은 가독성만 파괴한다. 데이터 지향 설계(70장)의 사고방식이 필요한 규모에서만 성립한다.

**④ 본문 참조**
기억 집합과 카드 테이블은 (62.7절), 쓰기 장벽의 실제 비용과 세분성은 (64.11절), 참조 없는 자료 구조 설계는 (70.3절), 구조체 전환의 손익은 (69.1절).

> **📌 규칙 12는 규칙 2·3과 같은 뿌리에서 나온다**
>
> 노드를 배열에 모으면 세대 간 참조만 사라지는 것이 아니라 **데이터가 연속 배치된다.** 즉 규칙 12를 적용하면 규칙 3(지역성)이 덤으로 따라온다. 반대도 성립한다 — SoA 전환(70.3절)을 하면 참조 수가 줄어드는 경우가 많다. 이 셋은 "메모리를 연속된 값의 배열로 다뤄라"는 하나의 원칙의 세 얼굴이다.

### 규칙 18 — 중년기 위기를 피하라

**① 규칙**
세대 2까지 승격되고서 거기서 곧 죽는 객체를 만들지 마라.

**② 왜**
**중년기 위기(mid-life crisis)** 는 세대 가설 위반의 가장 흔한 형태다. 객체가 세대 0에서 죽을 만큼 짧게 살지도, 세대 2에 남을 만큼 오래 살지도 않고 **애매하게 오래 살아서 세대 2까지 승격된 뒤 거기서 죽는다.** 이것은 세대 2가 설계된 목적과 정확히 반대다.

대가가 크다. 세대 2 수집은 여러 세그먼트/리전에 걸치므로 훨씬 비싸고(64.8절), 세대 2에 쌓인 시체를 치우려면 그 비싼 수집을 자주 돌려야 한다. 증상은 메모리 크기가 아니라 **`% Time in GC`** 로 먼저 나타난다.

원인은 대개 둘이다. **임시 데이터를 너무 오래 붙들고 있는 것**과 **파이널라이저**다. 파이널라이저를 가진 객체는 GC를 한 번 더 살아남으므로, 세대 1에서 죽었어야 할 객체가 세대 2로 올라간다(34.2절). 규칙 25가 규칙 18의 하위 규칙인 셈이다.

**③ 언제 예외인가**
이 규칙은 **반응적으로만 적용한다.** 복잡한 애플리케이션에서 객체 수명을 사전에 추론하는 것은 사실상 불가능하고, 시도하면 설계가 망가진다. 원천 도서의 지시가 명확하다 — **`% Time in GC`가 높다는 것을 관측한 뒤에** 진단을 시작하라.

그리고 **캐시는 이 규칙의 대상이 아니다.** 의도적으로 오래 살리는 객체가 세대 2에 있는 것은 정상이다. 문제는 "오래 사는 객체가 세대 2에 있는 것"이 아니라 "세대 2에서 **죽는** 객체가 많은 것"이다. 이 둘을 구분하지 못하면 캐시를 없애는 잘못된 처방으로 간다.

**④ 본문 참조**
중년기 위기의 식별과 해소는 (66.12절), 승격 메커니즘은 (64.6절), 파이널라이저가 수명을 늘리는 방식은 (34.2절), 세대 2를 condemn하는 이유의 추적은 (66.7절), 세대별 인식 분석은 (66.13절).

> **⚠️ 중년기 위기는 메모리가 평평해도 존재한다**
>
> 세대 2에 들어온 만큼 나가고 있으면 힙 크기 그래프는 완벽하게 평평하다. 메모리 대시보드만 보는 팀은 이 문제를 영원히 못 본다. **관측되는 지표는 `% Time in GC`이고, 확정 도구는 PerfView의 `Gen 2 Object Deaths`다**(66.12절).

## B.4 값 타입과 참조 타입 — 규칙 8 · 10 · 2 · 3

이 네 규칙은 "데이터를 어떤 모양으로 메모리에 놓을 것인가"라는 하나의 질문을 네 방향에서 다룬다.

### 규칙 8 — 구조체 사용을 고려하라

**① 규칙**
클래스를 반사적으로 선택하지 말고, 값 타입이 맞는 자리인지를 의식적으로 판단하라.

**② 왜**
C#에서 클래스는 너무 잘 동작해서 **기본 선택지가 되어 버렸다.** 그러나 구조체는 이유가 있어 존재한다. 값 타입은 힙 할당을 만들지 않고, 지역성이 좋고, 참조 필드가 없으면 쓰기 장벽도 없다. 그리고 JIT의 최적화 여지가 크다.

여기에 C#이 지난 몇 세대에 걸쳐 붙인 도구들이 있다 — `readonly struct`(방어적 복사 제거, 16.5절), `in`·`ref`·`ref readonly` 매개변수, `ref` 지역 변수와 `ref` 반환(68.12절). **구조체 복사가 두려워서 클래스를 쓰던 시절은 끝났다.**

**③ 언제 예외인가**
"고려하라"가 규칙의 전부다. **"전부 바꿔라"가 아니다.** 69.1절의 손익 계산표는 아홉 항목을 본다 — 크기, 복사 빈도, 박싱 위험, 컬렉션 저장, 가변성, 참조 필드 유무, 캐시 지역성, 수명, 다형성 요구. **하나라도 치명 칸에 걸리면 적용하지 않는다.**

특히 세 가지가 자주 사고를 낸다.

- **가변 구조체.** 값 의미론과 결합하면 "고쳤는데 안 고쳐진" 버그가 된다(16.2절).
- **인터페이스로 다루는 구조체.** 박싱이 발생하므로 힙 할당을 없애려던 목적이 정확히 뒤집힌다(18.6절).
- **0이 유효하지 않은 구조체.** 기본값을 막을 방법이 없다(16.4절).

그리고 기대치를 조정해야 한다. 69.1절의 실측에서 클래스를 구조체로 바꿨을 때 `Mean`은 348.8 us에서 344.7 us로 거의 그대로였고, 줄어든 것은 `Allocated`(62.60 KB → 39.13 KB)였다. **구조체 전환의 1차 효과는 속도가 아니라 GC 압력이다.**

**④ 본문 참조**
구조체의 규칙과 복사 의미론은 (16.1절, 16.2절), `readonly struct`는 (16.5절), 선택 기준은 (16.8절), 전환 손익 계산표와 실측은 (69.1절), `ValueTuple`·`ValueTask`는 (69.2절).

> **⚠️ 구조체 전환이 정확히 반대 결과를 내는 세 지점**
>
> | 하는 일 | 의도 | 실제로 벌어지는 일 |
> |---|---|---|
> | 구조체를 `IComparable` 등 인터페이스로 받는 메서드에 넘긴다 | 할당 제거 | **박싱** — 힙 할당이 그대로 생긴다 (18.6절) |
> | 큰 구조체를 `List<T>`에 담고 인덱서로 필드를 읽는다 | 지역성 개선 | 인덱서가 **복사본**을 반환해 원본이 안 바뀐다 (16.2절) |
> | 구조체에 `Equals`/`GetHashCode`를 재정의하지 않고 `Dictionary` 키로 쓴다 | 값 의미론 활용 | 기본 구현이 리플렉션 경로를 타 **매우 느리다** (16.7절) |
>
> 세 경우 모두 컴파일도 되고 테스트도 통과한다. **드러나는 시점은 프로덕션의 부하 구간**이다. 그래서 규칙 8을 적용한 PR에는 `[MemoryDiagnoser]`를 붙인 벤치마크가 함께 있어야 한다(67.5절).

### 규칙 10 — 박싱을 피하라

**① 규칙**
값 타입이 참조 타입으로 변환되는 지점을 알아보고, 핫 패스에서는 제거하라.

**② 왜**
박싱은 **숨은 할당**이다. 값 타입 인스턴스를 담을 참조 타입 인스턴스가 힙에 새로 생긴다(15.2절). 규칙 14가 이 목록에서 가장 중요한 최적화 원칙 중 하나이므로, 박싱 회피는 그 직접적인 하위 항목이 된다.

박싱이 특히 문제인 이유는 **대부분이 암묵적**이라는 것이다. 코드에 `box`라고 쓰여 있지 않다. 인터페이스로 다뤄진 구조체, `object`를 받는 오버로드, `params object[]`, 제네릭이 아닌 컬렉션, 문자열 보간의 옛 형태, `Enum`의 일부 API — 전부 조용히 박싱한다(63.9절).

**③ 언제 예외인가**
**박싱 한 번이 문제인 경우는 없다.** 문제는 초당 수만 번 실행되는 경로에 박싱이 있는 경우다. 로깅 한 줄, 예외 메시지 조립, 시작 시 설정 파싱에서 박싱을 제거하는 리팩터링은 순수한 시간 낭비다.

그리고 **박싱을 없애려다 더 나쁜 것을 만드는 경우**가 흔하다. 제네릭 오버로드를 타입마다 복제하거나, 인터페이스를 없애려고 `switch` 문을 손으로 펼치는 식이다. 15.7절의 체크리스트는 "이 지점이 핫 패스인가"를 먼저 묻는다.

**④ 본문 참조**
박싱의 문법·IL·비용은 (15.2절), 최소화 체크리스트는 (15.7절), 구조체가 인터페이스를 구현할 때의 박싱은 (18.6절), 널 가능 값의 박싱은 (21.3절), 힙 표현은 (54.6절), 숨은 할당으로서의 박싱은 (63.9절).

> **💡 박싱은 IL에서만 확실히 셀 수 있다**
>
> 소스를 읽어서 박싱을 찾는 것은 신뢰할 수 없다. Release IL에서 `box` 명령을 세는 것이 유일하게 확실한 방법이다(부록 A의 A.3절). 자동화하고 싶다면 Visual Studio의 **Clr Heap Allocation Analyzer** 확장이나 ReSharper의 **Heap Allocations Viewer** 플러그인이 편집기에서 실시간으로 표시해 준다 — 원천 도서가 규칙 10과 14 양쪽에서 추천하는 도구다.

### 규칙 2 — 무작위 접근을 피하고 순차 접근을 권장하라

**① 규칙**
데이터를 순차적으로 훑는 접근 패턴을 만들고, 예측 불가능한 점프를 피하라.

**② 왜**
근거가 전적으로 하드웨어에 있다. 프로세서는 데이터를 **64바이트 캐시 라인 단위**로 읽는다(61.4절). 64바이트보다 작은 접근은 비싼 자원을 낭비하는 것이다. 더 중요한 것은 **프리페처**다 — 프로세서는 접근 패턴에서 규칙성을 찾아 다음에 필요할 데이터를 미리 가져오는데, 무작위 접근에는 찾을 규칙이 없다.

여기서 "무작위"는 난수를 뜻하지 않는다. **탐지 가능한 패턴에 맞지 않는 모든 접근**을 뜻한다. 이중 연결 리스트 순회가 전형적인 예다 — 코드는 순차적으로 보이지만 메모리 접근은 힙 전역에 흩어진다.

효과의 크기는 61.4절의 실측이 보여 준다. 같은 배열을 행 우선이 아니라 열 우선으로 훑는 것만으로 최대 7.7배 느려진다.

**③ 언제 예외인가**
적용 범위가 명시되어 있다 — **주로 저수준·성능 지향 코드**다. 웹 요청 하나가 데이터베이스를 두 번 부르고 JSON을 직렬화하는 코드에서 캐시 라인을 논하는 것은 의미가 없다. 병목이 I/O나 락 대기에 있다면 접근 패턴을 바꿔도 총 시간은 그대로다.

그리고 **자료 구조 선택을 지역성만으로 하면 안 된다.** 배열은 순차 접근에 최적이지만 중간 삽입이 O(n)이다. 삽입·삭제가 지배적인 워크로드에서 연결 리스트를 배열로 바꾸면 캐시는 좋아지고 알고리즘 복잡도는 나빠진다.

**④ 본문 참조**
캐시 계층과 캐시 라인은 (61.4절), 지역성과 정렬은 (61.5절), 프리페칭은 (61.6절), 비순차 접근 회피의 실전 형태는 (70.5절), AoS→SoA 전환은 (70.3절).

### 규칙 3 — 공간적·시간적 데이터 지역성을 개선하라

**① 규칙**
자료 구조를 설계할 때 **함께 쓰이는 데이터를 가깝게 놓고**, 같은 데이터를 짧은 시간 안에 재사용하도록 만들어라.

**② 왜**
규칙 2가 "어떻게 읽을 것인가"라면 규칙 3은 "어떻게 놓을 것인가"다. 공간적 지역성(함께 쓰는 것을 가까이)과 시간적 지역성(쓴 것을 곧 다시)은 캐시가 성립하는 두 기둥이다. 둘을 지키면 캐시가 효율적으로 동작하고, 어기면 성능이 크게 떨어진다(61.5절).

실용적으로는 세 가지로 압축된다. **자료 구조를 합리적으로 작게 만들고, 미리 할당하고, 반복해서 재사용하라.** 세 번째가 풀링(69.3절, 69.4절)의 근거이기도 하다.

**③ 언제 예외인가**
규칙 2와 같은 적용 범위 제한이 그대로 적용된다. 여기에 하나가 더 붙는다 — **지역성 최적화는 비직관적인 코드를 만든다.** 70.3절의 AoS→SoA 전환은 "하나의 개체"라는 객체지향의 기본 단위를 해체한다. 그 대가로 얻는 것이 측정된 성능 향상이 아니라면 순수한 손해다.

그리고 **거짓 공유(false sharing)** 라는 반대 방향의 함정이 있다. 멀티스레드 코드에서는 데이터를 가깝게 놓는 것이 오히려 재앙이 된다 — 서로 다른 스레드가 쓰는 변수가 같은 캐시 라인에 있으면 라인이 계속 무효화된다. 61.4절의 실측은 배열 인덱스를 캐시 라인 하나만큼 미는 것만으로 벤치마크가 5.0초에서 0.7초로 바뀌는 것을 보여 준다. **규칙 3은 단일 스레드 관점의 규칙이고, 멀티스레드에서는 70.6절의 패딩이 규칙 3을 부분적으로 뒤집는다.**

**④ 본문 참조**
공간적·시간적 지역성은 (61.5절), 첫 캐시 라인 설계는 (70.1절), 캐시 레벨에 맞는 크기 설계는 (70.2절), 거짓 공유와 패딩은 (70.6절), 풀링은 (69.3절, 69.4절).

## B.5 대형 객체와 LOH — 규칙 15 · 19 · 13

대형 객체는 .NET GC에서 **별도의 규칙이 적용되는 영역**이다. 자동 압축이 없고, 할당 비용의 성격이 다르며, 단편화의 결과가 오래 남는다.

### 규칙 15 — 과도한 UOH 할당을 피하라

**① 규칙**
85,000바이트 이상의 객체를 자주 만들지 마라. 필요하다면 풀링하라.

**② 왜**
.NET에서 할당이 항상 싸지 않다면, **LOH 할당은 더 비싸다.** 이유가 구조적이다. LOH 할당은 드물고 크다고 가정되었으므로 **미리 공간을 준비해 두지 않는 설계**를 택했다. 그래서 UOH(LOH + POH)에는 **빠른 경로 자체가 없다**(63.4절). 항상 프리 리스트 → 커밋 → 예약 순으로 자리를 찾는다.

그리고 비용의 대부분이 **메모리를 0으로 채우는 시간**이다. 100 MB 배열 하나를 만드는 비용은 할당자를 찾는 시간이 아니라 100 MB를 쓰는 시간이 지배한다(63.4절). 이것은 GC 통계에 거의 나타나지 않으면서 지연 시간을 망가뜨린다.

여기에 규칙 19가 이어진다 — LOH는 자동으로 압축되지 않으므로 잦은 대형 할당은 단편화를 남긴다.

**③ 언제 예외인가**
**큰 객체를 자주 만든다는 것은 대개 정말 필요해서다.** 그 할당을 그냥 없앨 수는 없다. 값 타입으로 대체하는 것도 스택 공간 한계와 복사 비용 때문에 거의 불가능하다. 그래서 이 규칙의 실질적인 처방은 하나뿐이다 — **풀링**.

그리고 풀링에는 고유한 대가가 있다. `ArrayPool<T>.Rent`는 요청보다 큰 배열을 줄 수 있고, 반환한 배열을 계속 쓰는 것을 아무도 막지 않으며, 참조 타입 원소 배열을 `clearArray: true` 없이 반납하면 풀이 그 객체들을 영구히 붙잡는다(69.3절). **풀링은 GC 압력을 수동 수명 관리와 맞바꾼 것이고, 그 거래가 항상 이득은 아니다.**

**④ 본문 참조**
SOH/LOH 경계와 `double[]` 예외는 (62.3절), UOH 할당 경로와 0 채우기 비용은 (63.4절), `ArrayPool`·`MemoryPool`은 (69.3절), 오브젝트 풀과 `RecyclableMemoryStream`은 (69.4절), GC 관점의 배열 풀링은 (65.10절).

> **⚠️ 경계는 85,000바이트이지 85 KiB가 아니다**
>
> 그리고 **32비트 런타임에서 원소 1,000개 이상인 `double[]`은 8,000바이트여도 LOH로 간다** — 8바이트 정렬 때문이다(62.3절). `LOHThreshold`로 경계를 올릴 수는 있어도 내릴 수는 없다.

### 규칙 19 — 오래된 세대와 LOH 단편화를 피하라

**① 규칙**
세대 2와 LOH의 단편화 비율을 관찰하고, 통제 불능이 되지 않게 하라.

**② 왜**
**단편화 자체는 나쁜 것이 아니다.** 할당자는 빈 공간을 재사용한다(63.2절). 나쁜 것은 **통제되지 않은 단편화**다 — 해당 세대의 GC가 돌았는데도 단편화 비율이 떨어지지 않는 상황. 이때 프로그램의 메모리 사용량은 실제로 쓰는 객체 수와 무관하게 예측 불가능하게 커진다.

세대별로 심각도가 다르다.

| 영역 | 단편화의 결과 |
|---|---|
| 임시 세대(0·1) | 압축이 빠르므로 대개 문제가 아니다 |
| 세대 2 | 압축이 여러 세그먼트/리전에 걸쳐 매우 비싸다. 세그먼트/리전 수가 늘면 GC 자체가 더 비싸진다 |
| LOH | **자동 압축이 없다.** 명시적으로 요청해야 하고, 그 압축은 매우 비싸다 |

**③ 언제 예외인가**
단편화를 관측했다고 바로 처방하면 안 된다. 순서가 있다.

1. 단편화 비율을 관측한다(`GC.GetGCMemoryInfo()`의 `FragmentedBytes`, 또는 ETW/EventPipe 세션).
2. **그것이 실제로 문제인지 판단한다** — GC 오버헤드를 크게 만들고 있는가, 메모리 사용량을 걱정스러운 수준으로 올리고 있는가.
3. 둘 다 아니면 **아무것도 하지 않는다.**

그리고 **단편화 진단에는 황금률이 없다.** 원천 도서 자신이 그렇게 밝힌다. 완화책도 하나뿐이다 — 단편화의 원인(대개 각종 배열)을 풀링하는 것.

LOH 압축을 유도하는 `GCConserveMemory` 설정에도 함정이 있다. 이 설정은 **누적 단편화 비율**을 보므로, gen2가 크고 깨끗하면 LOH 단편화가 90%여도 압축이 일어나지 않을 수 있다(65.6절).

**④ 본문 참조**
압축 결정 로직은 (64.8절), Sweep과 프리 리스트 구성은 (64.9절), 보수적 모드와 `GCConserveMemory`는 (65.6절), `GCSettings.LargeObjectHeapCompactionMode`는 (65.8절), LOH 단편화 진단 시나리오는 (66.11절), 배열 풀링은 (65.10절).

> **💡 단편화 대응의 우선순위**
>
> 단편화가 확인되었을 때 손대는 순서가 있다. 아래로 갈수록 비싸고 되돌리기 어렵다.
>
> | 순서 | 조치 | 비용 |
> |---|---|---|
> | 1 | **단편화의 원인이 되는 배열을 풀링한다** | 코드 변경. 대개 국소적이다 |
> | 2 | 대형 버퍼의 크기를 고정해 재사용 가능하게 만든다 | 설계 변경 |
> | 3 | `GCConserveMemory`로 압축을 유도한다 | 처리량 손실. 누적 단편화 기준이라 안 먹을 수 있다 (65.6절) |
> | 4 | `LargeObjectHeapCompactionMode.CompactOnce`를 요청한다 | **매우 비싸다.** 한 번만 적용된다 (65.8절) |
>
> 4번이 매력적으로 보이는 이유는 코드를 안 고쳐도 되기 때문이다. 그러나 4번은 **증상 완화이지 원인 제거가 아니다.** 다음 날 같은 상태로 돌아온다.

### 규칙 13 — 세그먼트 사용을 관찰하라

**① 규칙**
필요할 때 세그먼트/리전의 배치를 들여다볼 수 있어야 한다.

**② 왜**
세그먼트(그리고 .NET 7+의 리전)는 관리 힙의 **물리적 구성 방식**이며, 원래는 완전히 감춰져 있어야 하는 구현 세부사항이다(62.6절). 대부분의 경우 알 필요가 없다.

그러나 예외가 있다. 메모리 사용 문제를 분석할 때 **세그먼트 배치가 진단 단서를 준다.** 세대가 어느 세그먼트의 어디에 놓여 있는지를 아는 것은 WinDbg 같은 저수준 도구로 분석할 때 특히 유용하다. 그리고 드물게는 세그먼트 자체가 문제를 일으킨다 — **좁은 32비트 환경**에서 특히 그렇다.

**③ 언제 예외인가**
이 규칙은 이 목록에서 **적용 빈도가 가장 낮다.** 상시 모니터링 대상이 아니라 "필요할 때 볼 줄 알아야 한다"는 성격의 규칙이다.

그리고 .NET 7에서 세그먼트가 리전으로 대체되면서 이 규칙의 구체적인 관찰 대상이 바뀌었다(62.6절). 세그먼트 시절의 지식(임시 세그먼트가 하나뿐이라는 등)을 리전 기반 런타임에 그대로 적용하면 틀린 결론이 나온다. **런타임 버전을 먼저 확인해야 하는 규칙이다.**

**④ 본문 참조**
세그먼트에서 리전으로의 전환은 (62.6절), 세그먼트/리전 재사용과 힙 해부 실습은 (62.8절), WinDbg + SOS의 `!eeheap`은 (66.9절), 어셈블리 수가 늘 때의 메모리 증가는 (62.9절).

## B.6 파이널라이저와 Dispose — 규칙 25 · 26

두 규칙은 사실상 하나의 문장이다 — **비관리 리소스는 명시적으로, 결정적으로 정리하라.**

### 규칙 25 — 파이널라이저를 피하라

**① 규칙**
파이널라이저를 쓰지 마라. 불가피하면 극도로 좁은 래퍼에만 두어라.

**② 왜**
파이널라이저는 아주 구체적인 목적으로 설계되었다 — **비관리 리소스의 암묵적 정리.** 그런데 명시적 정리가 불가능한 경우는 실무에서 거의 없다. 그리고 대가가 크다.

- **좋은 파이널라이저를 쓰는 것 자체가 어렵다.** 재진입, 멀티스레드, 부분 실행 가능성, 아예 실행되지 않을 가능성까지 전부 고려해야 한다.
- **수명이 한 세대 늘어난다.** 파이널라이즈 가능한 객체는 GC를 한 번 더 살아남고, 그 과정에서 승격된다. **승격은 그 객체가 참조하는 객체 전체로 전염된다**(34.2절).
- **할당 자체가 느려진다.** 34.2절의 실측에서 파이널라이저가 있는 타입의 할당은 없는 타입 대비 약 40배 느렸다. 할당 크기는 같다 — 차이는 전적으로 런타임 등록 비용이다.
- **파이널라이저 스레드는 하나뿐이다.** 거기서 락을 잡거나 I/O를 하면 힙 전체가 멈춘다(66.11절).

원천 도서가 제시하는 대안은 셋이다 — **`SafeHandle`**(런타임 지원을 받는 잘 설계된 핸들 표현), **Dispose 패턴**(대개 파이널라이저를 아예 없앨 수 있다), **임계 파이널라이제이션**(해제가 정말 결정적으로 중요할 때).

**③ 언제 예외인가**
파이널라이저가 정당한 경우가 없지는 않다. **비관리 핸들을 직접 감싸는 타입이 `Dispose` 누락에 대비한 안전망을 원할 때**다. 이 경우에도 원천 도서가 제시하는 여섯 가지 실무 지침을 지켜야 한다.

| 지침 | 이유 |
|---|---|
| 비관리 리소스만 감싸는 **작은 래퍼**로 만든다. 관리 참조를 두지 않는다 | 승격 전염을 막는다 |
| 파이널라이저에서 **메모리를 할당하지 않는다** | 거기서 `OutOfMemoryException`이 나면 대응할 방법이 없다 |
| **정말 그 리소스를 소유했는지 확인한다** | 생성자가 예외를 던지면 불완전하게 초기화된 객체의 파이널라이저가 실행될 수 있다 |
| **스레드 컨텍스트를 가정하지 않는다.** 동기화로 블로킹하지 않는다 | 어느 스레드가 실행할지 보장이 없다 |
| **예외를 던지지 않는다.** 서드파티 코드의 예외도 새어 나가지 않게 `try`/`catch`로 감싼다 | 파이널라이저의 예외는 프로세스를 죽인다 |
| **가상 멤버를 호출하지 않는다** | 위의 모든 문제를 다시 불러들인다 |

**④ 본문 참조**
파이널라이저의 동작 순서와 F-reachable 큐, 실측 비용은 (34.2절), 파이널라이저에서 `Dispose` 호출은 (34.3절), 부활과 임계 파이널라이저는 (34.4절), `SafeHandle`은 (33.7절), 파이널라이제이션 루트는 (64.3절), 파이널라이저 큐 적체 진단은 (66.11절).

> **⚠️ 파이널라이저는 조용한 중년기 위기 제조기다**
>
> 요청마다 하나씩 만드는 래퍼 클래스에 무심코 `~T()`를 넣으면, 그 객체 전부가 세대 1 이상으로 승격된다(34.2절). 메모리 그래프는 정상으로 보이는데 `% Time in GC`만 올라간다. **규칙 25를 어기면 규칙 18도 자동으로 어기게 된다.**

### 규칙 26 — 명시적 정리를 선호하라

**① 규칙**
리소스는 `IDisposable`과 `using`으로 결정적인 시점에 정리하라.

**② 왜**
결정적 정리는 **정리 시점이 명확하고, 잘 설계했다면 가능한 한 이르다.** 제한된 리소스(파일 핸들, 소켓, 데이터베이스 연결, 락)를 다룰 때 이것이 결정적으로 중요하다. 비결정적 정리는 "언젠가 풀린다"는 보장만 주는데, 핸들 고갈은 그 "언젠가"를 기다려 주지 않는다.

대가는 개발자의 규율이다. 리소스를 만들어 놓고 잊어버릴 수 없고, 초기화한 것을 반드시 해제해야 한다. **관리 환경이 약속한 것과 다소 반대다.** 그러나 비관리 리소스는… 비관리 리소스다.

C#은 이 규율을 문법으로 뒷받침한다 — `using` 문과 `using` 선언(33.5절), `await using`(33.6절), 그리고 편집기·분석기의 경고들.

**③ 언제 예외인가**
`Dispose`가 필요 없는 타입에 `IDisposable`을 붙이는 것은 그 자체로 비용이다. 소유권 사슬이 늘어나고, 호출자가 `using`을 써야 하고, 제네릭 코드에서 처리가 번거로워진다(33.9절).

그리고 **`Dispose`가 항상 "해제"를 뜻하지는 않는다.** `IDbConnection`처럼 나중에 다시 열어야 하는 객체는 `Close`를 불러야지 `Dispose`를 부르면 안 된다(33.4절). 33.1절의 세 규칙 중 규칙 1("폐기된 객체는 되돌릴 수 없다")과 충돌하는 경우다.

**④ 본문 참조**
리소스 관리 모델은 (33.1절), 표준 정리 의미론은 (33.2절), 표준 Dispose 패턴은 (33.3절), `using` 문·선언은 (33.5절), `IAsyncDisposable`은 (33.6절), `Dispose`를 부르지 않았을 때 벌어지는 일은 (33.8절), 타이머가 만드는 누수는 (34.10절).

> **⚠️ `Dispose`는 메모리를 해제하지 않는다**
>
> 규칙 26을 메모리 규칙으로 오해하는 것이 가장 흔한 혼동이다. **`Dispose`는 관리 메모리를 한 바이트도 회수하지 않는다.** 객체의 메모리는 도달 불가능해진 뒤 GC가 회수한다(61.9절, 64.2절). `Dispose`가 회수하는 것은 파일 핸들, 소켓, 네이티브 버퍼, 락 같은 **비관리 리소스**다.
>
> 그래서 다음 두 문장은 둘 다 참이다.
>
> - `Dispose`를 부르지 않아도 **관리 메모리 누수는 생기지 않는다** — 객체가 도달 불가능해지면 회수된다.
> - `Dispose`를 부르지 않으면 **핸들 고갈과 비관리 메모리 증가가 생긴다** — 그리고 파이널라이저가 있다면 수명이 한 세대 늘어난다(34.2절).
>
> 두 번째 항목 때문에 규칙 26이 이 메모리 규칙 목록에 들어와 있다. 66.1절의 판별 기준 — 작업 집합은 오르는데 `gc-heap-size`는 평평하다 — 이 가리키는 원인 중 하나가 정확히 이것이다.

> **💡 두 타이머의 누수 방향은 정반대다**
>
> `System.Timers.Timer`는 정리를 잊으면 **객체가 영원히 살고**, `System.Threading.Timer`는 정리를 잊으면 **너무 일찍 수집된다**(34.10절, 66.11절). 증상이 정반대인데 처방은 같다 — `Dispose`. 규칙 26이 "메모리 규칙"인 이유가 여기 있다.

## B.7 GC 구성과 튜닝 — 규칙 23 · 24 · 17 · 4

이 네 규칙은 **코드를 고친 다음에** 오는 것이다. B.1절의 흐름도에서 4단계에 놓인 이유다.

### 규칙 23 — GC 모드를 의식적으로 선택하라

**① 규칙**
기본값을 쓰더라도, 그것이 기본값이라서가 아니라 **선택한 결과**여야 한다.

**② 왜**
.NET GC의 주요 파라미터는 사용자 통제 아래 있다 — 힙 개수, GC 스레드 수, 공격성, 워크스테이션/서버, 동시/비동시(65.1절, 65.2절, 65.5절). **대부분의 경우 기본값이 적절하다.** 그러나 대안이 무엇인지, 어떤 판단 근거로 고르는지는 알고 있어야 한다.

첫 결정은 앱의 성격이 정한다 — 서버인가 클라이언트인가, 일시 정지 시간이 중요한가 아닌가. 이건 이미 알고 있는 정보이므로 큰 노력이 들지 않는다. 문제는 그다음이다. **각 모드는 CPU와 메모리 사용에서 서로 다른 트레이드오프를 갖고, 그 영향은 애플리케이션마다 다르다.** 측정 없이는 어느 것이 맞는지 알 수 없다.

**③ 언제 예외인가**
**GC 설정을 만지기 전에 할당을 줄여라.** 65.10절이 이 논점을 정면으로 다룬다 — 배열 풀링 하나가 LOH 단편화, 동시 스윕 중 블록, 압축 비용을 한 번에 없앤다. 설정 변경으로 얻는 것보다 대개 크다.

그리고 측정 방법론에 함정이 있다. **평균으로 GC 지표를 비교하면 안 된다.** 짧은 gen0 GC와 긴 gen2 GC가 섞인 다봉 분포이기 때문이다(66.3절, 67.1절). 원천 도서가 이 규칙에서 특별히 강조하는 것이 **백분위수 사용**이다.

마지막으로 환경적 함정이 셋 있다.

- **논리 코어가 1개면 `gcServer` 설정이 무시된다**(65.1절).
- **환경 변수의 숫자 값은 16진수다.** `DOTNET_GCHeapHardLimitPercent=50`은 50%가 아니라 80%다(65.5절).
- **환경 변수가 `runtimeconfig.json`을 이긴다.** 설정 후 `GC.GetConfigurationVariables()`로 실제 값을 확인하라.

**④ 본문 참조**
워크스테이션 vs 서버는 (65.1절), 비동시 vs 백그라운드는 (65.2절), 힙 하드 리밋·힙 개수·어피니티는 (65.5절), DATAS와 컨테이너는 (65.7절), 모드 선택 판단 흐름도는 (65.11절), 배열 풀링 우선 논의는 (65.10절).

> **⚠️ 설정을 바꿨는데 안 바뀐 세 가지 이유**
>
> 규칙 23을 적용하려다 "바꿨는데 아무 일도 안 일어난다"에 빠지는 경로가 정해져 있다.
>
> | 증상 | 원인 | 확인 방법 |
> |---|---|---|
> | `gcServer`를 켰는데 힙이 하나다 | **논리 코어가 1개면 설정이 무시된다** (65.1절) | 코어 수 확인 |
> | `runtimeconfig.json`을 고쳤는데 반영이 안 된다 | **환경 변수가 이긴다** (65.5절) | 환경 변수 확인 |
> | 퍼센트 값이 이상하게 동작한다 | **환경 변수의 숫자 값은 16진수다.** `50`은 80%다 (65.5절) | 값을 16진수로 다시 계산 |
>
> 세 경우 모두 **`GC.GetConfigurationVariables()`가 실제 반영된 값을 준다.** 설정을 만졌으면 이 한 줄을 시작 로그에 찍는 것이 규칙 23의 가장 싼 실천이다.

### 규칙 24 — 지연 시간 모드를 기억하라

**① 규칙**
저지연 모드는 **항상 한시적으로** 쓴다. 기대가 강할수록 짧게.

**② 왜**
네 가지 GC 모드 외에 **지연 시간 모드**로 GC의 공격성을 조절할 수 있다. 이들은 GC가 블로킹 수집을 얼마나 기꺼이 실행할지를 통제한다. 결과는 명확한 균형이다 — **응답성(짧은 블로킹 정지만 허용)과 메모리 사용량(비압축 백그라운드 GC로 인한 단편화 누적) 사이의 거래.**

용도는 두 갈래다. **상호작용형 애플리케이션**에서 최대 유창성이 필요한 짧은 구간(키보드 입력 등)에 쓰거나, **일부 서버 애플리케이션**(트레이딩 앱이 대표적)이 거래 시간 동안 전체 블로킹 GC의 방해를 받지 않겠다고 선언하기 위해 `SustainedLowLatency`를 쓴다.

핵심 통찰은 이것이다 — **지연 시간 모드는 "빨라져라"가 아니라 "무엇을 금지할 것인가"다**(65.4절). `LowLatency`는 모든 gen2 GC를 막고, `SustainedLowLatency`는 비동시 전체 GC만 막는다.

**③ 언제 예외인가**
**전형적인 애플리케이션에는 이런 정밀 튜닝이 필요 없다.** 성능 요구사항의 한계에 다다랐을 때만 관심을 가질 대상이다.

강도와 지속 시간이 반비례해야 한다.

| 모드 | 유지 가능한 시간 | 금지하는 것 |
|---|---|---|
| `SustainedLowLatency` | 길게 유지해도 된다 | 비동시 전체 GC만 |
| `LowLatency` | 짧게. **워크스테이션 GC 전용** | 모든 일반 gen2 GC |
| NoGC 영역 | 아주 짧게 | 모든 GC |

NoGC 영역에는 추가 함정이 있다. **`TryStartNoGCRegion`은 `EndNoGCRegion`과 반드시 짝을 이뤄야 한다.** 짝이 없으면 다음 호출이 `InvalidOperationException`으로 실패한다. 할당 한도를 넘겨 모드가 자동 해제된 뒤에도 `EndNoGCRegion` 호출은 필요하고, 그 호출도 던진다(65.4절, 65.8절).

**④ 본문 참조**
지연 시간 모드 전체는 (65.4절), `GCSettings`와 `TryStartNoGCRegion` API는 (65.8절), 일시 정지 시간과 오버헤드의 트레이드오프는 (65.3절), GC 알림과 프로그래밍적 제어는 (65.9절).

### 규칙 17 — 런타임 중단을 지켜보라

**① 규칙**
EE 일시 중단(suspension) 시간을 측정하고, 비정상적으로 길면 조사하라.

**② 왜**
런타임 중단은 GC가 관리 스레드를 멈춰 안전한 작업 기반을 만드는 서비스다. 비동시 GC 동안 사용자 스레드가 GC가 조작 중인 메모리를 건드리면 안 되기 때문이다(64.12절). 이 과정은 극도로 최적화되어 있어 **정상이면 밀리초의 몇 분의 일**로 끝난다.

그래서 이 지표는 **훌륭한 이상 감지기**다. 중단이 일관되게 오래 걸린다면 무언가 잘못된 것이고, 그것은 GC의 문제가 아니라 사용자 코드의 문제일 가능성이 높다 — 안전 지점에 도달하지 못하는 스레드가 있다는 뜻이기 때문이다.

**③ 언제 예외인가**
원천 도서가 이 규칙에 붙인 적용 범위가 **"일반적이지만 드묾"** 이다. 상시 대시보드에 올릴 지표가 아니라, GC 시간이 이상한데 원인이 안 잡힐 때 확인할 지표다.

판단 기준은 명확하다 — **1 ms를 넘는 중단 시간은 주의를 끌어야 한다.** 그 이상이 관측되면 중단 구간에 네이티브 프로파일러를 붙여 조사한다. 흔한 원인은 **높은 우선순위 스레드의 실행**과 **동기적으로 실행되는 매우 긴 I/O 작업**이다.

**④ 본문 참조**
EE 일시 중단과 안전 지점은 (64.12절), 일시 정지 시간 트레이드오프는 (65.3절), `GC.GetGCMemoryInfo`의 `PauseDurations`는 (65.8절), PerfView GCStats로 중단 시간을 보는 방법은 (66.7절).

> **📌 `PauseDurations`가 STW 구간을 분리해서 준다**
>
> 백그라운드 GC는 긴 정지 하나를 짧은 정지 두 개로 쪼갠다(65.2절). 그래서 "GC가 얼마나 걸렸나"와 "애플리케이션이 얼마나 멈췄나"는 다른 질문이다. `GC.GetGCMemoryInfo()`의 `PauseDurations`는 후자를 구간별로 나눠 준다(65.8절). 규칙 17을 코드에서 자동화하려면 여기서 시작한다.

### 규칙 4 — 더 고급 가능성을 고려하라

**① 규칙**
런타임이 제공하는 일반적 메커니즘으로 부족하다면, 운영체제 수준의 저수준 메커니즘을 검토하라.

**② 왜**
.NET 런타임은 가능한 한 **일반적인** 방식으로 구현되어 있다. 다양한 시나리오에서 올바르게 동작하는 것이 목표이기 때문이다. 그러나 애플리케이션을 쓰는 사람은 자기 핫스팟이 어디인지 안다. 극단적으로 빠른 메모리 관련 코드가 필요하다면 — 직렬화기, 메시징 버퍼, 초고속 이벤트 프로세서를 만든다면 — 대용량 페이지나 비일시적(non-temporal) 메모리 접근 같은 시스템 API가 도움이 될 수 있다.

**③ 언제 예외인가**
원천 도서가 이 규칙에 붙인 경고가 규칙 본문보다 길다. 요약하면 **"거의 모든 사람에게 이 규칙은 해당되지 않는다"** 이다.

- 코드가 매우 복잡해진다. **쓰기 고통스럽고, 당신 말고는 아무도 유지보수하고 싶어 하지 않을 것이다.**
- 운영체제의 저수준 API를 쓰므로 **OS 업데이트나 버전 변경 후에 문제를 일으킬 수 있다.**
- 극도의 주의가 필요하고, 실수하기 매우 쉽다. **실수하면 성능이 올라가는 대신 급격히 떨어진다.**

적용 범위가 **"극도로 저수준인 성능 지향 코드"** 인 이유다. 이 규칙에 도달하기 전에 규칙 14·15·16과 68·69장의 도구를 전부 소진했어야 한다.

**④ 본문 참조**
대용량 페이지와 가상 메모리는 (61.2절), Windows/Linux 메모리 관리는 (61.3절), 프리페칭과 비일시적 접근은 (61.6절), NUMA와 CPU 그룹은 (61.7절), 대용량 페이지 GC 설정은 (65.6절), 커스텀 GC는 (65.12절), 하드웨어 내장 함수는 (71장).

### 규칙 5 — GC를 일찍 측정하라

**① 규칙**
개발 주기 초기부터 GC 지표를 측정하고, 프로덕션에서 상시 모니터링하라.

**② 왜**
서로 다른 지표를 지속적으로 관찰하면 **"나에게 메모리 문제가 있는가"** 라는 질문에 개발 주기 초기에 답할 수 있다. 더 중요한 것은 **추세**를 볼 수 있다는 점이다 — 성능이 서서히 나빠지고 있다는 사실은 한 시점의 측정으로는 절대 드러나지 않는다.

목표는 상시 모니터링이다. 작은 환경의 첫 배포부터 프로덕션의 지속 관찰까지, 측정하는 습관을 들이는 것이 이 규칙의 전부다. 원천 도서가 "잘 설계된 시스템이라면 반드시 측정하고 있을 것"이라고 말하는 두 가지가 있다.

- **프로세스가 얼마나 많은 메모리를 소비하며, 시간이 지나면서 통제 불능으로 증가하는가**
- **GC가 얼마나 자주, 얼마나 오래 호출되며, 프로세스 성능에 눈에 띄는 오버헤드가 있는가**

**③ 언제 예외인가**
"무엇을 측정할 것인가"에는 정답이 없다 — **당신의 사정에 따라 다르다.** 모니터링 프로세스의 엄격도에 달렸다.

그리고 **절댓값에는 의미가 없다.** "gen2가 400 MB"는 좋지도 나쁘지도 않다. 판단 근거는 추세와 이전 버전과의 비교뿐이다(66.1절). 임계값 기반 알람을 세우려면 반드시 자기 애플리케이션의 기준선을 먼저 쌓아야 한다.

플랫폼별로 도구가 갈린다는 점도 주의해야 한다. **`.NET CLR *` 성능 카운터는 .NET Framework 전용이고, `dotnet-counters`는 .NET(Core) 전용이다**(66.8절). 그리고 성능 카운터 값은 **GC 시점에만 갱신되므로 현재 값이 아니라 변화를 봐야 한다.**

**④ 본문 참조**
이벤트 추적(ETW/EventPipe/`dotnet-trace`)은 (66.6절), PerfView 워크플로는 (66.7절), `dotnet-counters` 계열 도구는 (66.8절), 오버헤드와 침습성 판단은 (66.2절), CI에서 성능 회귀를 잡는 방법은 (67.8절).

> **💡 CI 게이트는 시간이 아니라 할당량부터 건다**
>
> 할당량은 결정론적이고 시간은 아니다(67.5절). `GC.GetAllocatedBytesForCurrentThread()` 기반 어서션 테스트를 Release CI에 넣으면 규칙 5를 자동화한 첫 걸음이 된다(69.9절). 시간 기반 게이트는 거짓 경보를 반복하기 쉽고, **게이트가 거짓 경보를 반복하면 팀은 게이트를 무시하기 시작하며, 그 시점부터 게이트는 없는 것보다 나쁘다**(67.8절).

### 규칙 6 — 프로그램을 측정하라

**① 규칙**
"내 프로그램은 몇 MB인가"에 정확히 답할 수 있어야 한다.

**② 왜**
측정할 줄 모르면 프로그램이 메모리를 많이 쓰는지 아닌지 알 방법이 없다. 그런데 이 질문은 생각보다 어렵다. **볼 수 있는 지표가 여러 개이고, 그 의미를 이해하지 못하면 그냥 길을 잃는다.** 두 프로그램의 크기를 비교하는 방법도, 고객에게 확인을 요청하는 방법도 모르게 된다.

메모리 관련 문제를 분석할 때는 **언제나 크기와 그 시간적 변화부터 조사한다.** 컨테이너 환경에서 가장 골치 아픈 크기 — **물리 RAM을 얼마나 소비하는지**를 나타내는 지표 — 부터 보고, 프라이빗 바이트와 가상 바이트도 함께 본다. 이 측정값들을 알고 나서야 더 깊은 분석으로 넘어갈 맥락이 생긴다.

**③ 언제 예외인가**
이 규칙 자체에는 예외가 없다. 다만 **어느 지표를 볼지는 질문에 달렸다.**

| 질문 | 봐야 할 지표 |
|---|---|
| 컨테이너가 OOM으로 죽는가 | 작업 집합(물리 RAM 소비) |
| 관리 힙이 새고 있는가 | `gc-heap-size` |
| 단편화가 문제인가 | `gc-heap-size` vs `gc-committed`의 간격 |
| 비관리 쪽이 새고 있는가 | 작업 집합은 오르는데 `gc-heap-size`가 평평한가 |

66.1절의 누수 판별 절차가 이 표를 두 관문으로 정식화한다.

그리고 **성능 목표를 먼저 정하지 않으면 이 측정도 소용없다.** 67.1절이 지적하듯 메모리 축은 **저량(작업 집합)과 유량(할당률)** 으로 다시 갈라야 하고, 둘은 다른 문제다.

**④ 본문 참조**
프로세스 메모리 영역 전반은 (62.2절), 누수 판별의 두 관문은 (66.1절), 최적화 대상 정하기는 (67.1절), 크기의 세 가지 의미(얕은/전체/유지)는 (66.5절), Windows/Linux 메모리 레이아웃은 (61.3절).

> **📌 "크기"라는 단어가 가리키는 것이 최소 여섯 개다**
>
> 규칙 6이 어려운 진짜 이유가 이것이다. 같은 회의에서 여섯 사람이 "메모리"라고 말할 때 서로 다른 것을 가리키고 있을 수 있다.
>
> | 용어 | 무엇을 세는가 | 어디서 보는가 |
> |---|---|---|
> | 가상 바이트 | 예약된 주소 공간 | OS 도구 (62.2절) |
> | 프라이빗 커밋 바이트 | 실제로 커밋된 프로세스 전용 메모리 | OS 도구 (62.2절) |
> | 작업 집합 | 지금 물리 RAM에 올라와 있는 양 | OS 도구, 컨테이너 OOM의 기준 |
> | `gc-heap-size` | 관리 힙의 객체 크기 합 | `dotnet-counters` (66.8절) |
> | 얕은 / 전체 / 유지 크기 | 객체 하나 / 그래프 / "지우면 사라지는 양" | 힙 분석 도구 (66.5절) |
> | `Allocated` | 연산 1회당 누적 할당 바이트 | BenchmarkDotNet (67.5절) |
>
> 마지막 두 줄이 특히 자주 혼동된다. **`Allocated`는 저량이 아니라 유량이다** — 지금 얼마나 쓰고 있는지가 아니라 얼마나 만들어 냈다 버렸는지를 센다(67.1절). 누수 진단에는 쓸 수 없고, GC 압력 진단에는 이것이 정답이다.

### 규칙 7 — 메모리 누수가 있다(없다)고 가정하지 마라

**① 규칙**
"관리 환경이니 누수는 없다"도, "메모리가 느니 누수다"도 둘 다 가정하지 마라. 절차로 확인하라.

**② 왜**
관리 환경에서 메모리 누수가 없다고 믿기 쉽다. 메모리가 자동으로 회수되는데 왜 신경 쓰겠는가. **거의 언제나 맞는 말이고, 런타임 설계자들의 대단한 공학적 성취다.** 그러나 최악의 시점에, 대개 고객의 프로덕션 환경에서 당신을 치는 시나리오가 여전히 여럿 존재한다.

반대 방향도 마찬가지다. **큰 메모리 소비가 항상 누수를 뜻하지는 않는다.** GC는 가용 메모리를 "최적화"하는 자체 휴리스틱을 갖고 있다. 놀고 있는 메모리를 굳이 반납하지 않는 것은 정상 동작이다.

그래서 원천 도서는 누수 주장을 검증하는 절차를 제시한다.

```csharp
// 원천 도서가 제시하는 누수 검증 절차 (단계 2~4)
GC.Collect();                      // 압축 gen2 수집 — 미참조 객체를 남김없이 제거
GC.WaitForPendingFinalizers();     // 파이널라이즈 대상까지 정리 (34장)
GC.Collect();                      // 파이널라이즈된 객체를 회수
```

전체 절차는 다섯 단계다.

1. **프라이빗 커밋 바이트가 자라는 것을 볼 만큼 충분히 기다린다.** 메모리 소비는 GC가 트리거될 때까지 계속 증가한다는 것을 기억하라.
2. 압축 gen2 GC를 트리거해 미참조 객체가 남지 않게 한다.
3. `GC.WaitForPendingFinalizers()`로 파이널라이즈 가능한 객체까지 정리한다.
4. 다시 압축 gen2 GC를 트리거해 파이널라이즈된 객체를 회수한다.
5. **그래도 프라이빗 커밋 바이트가 계속 자라는지 확인하고,** 이 단계를 반복해 시간에 따른 증가를 검증한다.

**③ 언제 예외인가**
**이 절차의 `GC.Collect()`는 규칙 20의 예외다.** 진단 목적으로 한 번 부르는 것과 프로덕션 코드에 넣는 것은 다르다. 진단이 끝나면 지워야 한다.

더 나은 방법도 있다. 66.1절이 소개하는 대로, gen2 GC를 기다리거나 강제 호출을 심는 대신 **`Microsoft-Windows-DotNETRuntime:800000` 키워드를 구독하면 런타임이 GC를 강제해 준다.** 프로덕션에서 코드 변경 없이 같은 검증을 할 수 있다.

그리고 **작고 불가피한 누수는 그냥 두는 것이 옳을 때가 있다.** 메모리 증가가 실질적으로 애플리케이션을 해치지 않을 만큼 작다면, 그리고 며칠에 한 번 새 빌드 배포로 프로세스를 재시작한다면, 더 나쁜 성능 문제를 조사하는 데 시간을 쓰는 편이 낫다. 원천 도서는 이런 "용인된 누수"가 대개 **고칠 수 없는 서드파티 코드**에서 온다고 지적한다.

**④ 본문 참조**
누수 판별 기준과 "누수가 없다"는 가정의 위험은 (66.1절), 대표 누수 시나리오 여섯 가지는 (66.11절), 루트 경로 추적은 (66.5절), `!gcroot`는 (66.9절), 도달 가능성과 생존성의 어긋남은 (61.9절).

> **⚠️ 누수 진단의 첫 질문은 "GC가 왜 안 도나"가 아니다**
>
> 도달 가능성 판정에는 오류가 없다. 관리 메모리가 늘어난다면 **무언가가 계속 참조를 붙들고 있는 것**이다(66.1절). "숨은 루트"의 후보는 정해져 있다 — 정적 변수, 이벤트 구독, 잘못 구성된 IoC 컨테이너, 정리하지 않은 타이머, 인터닝된 문자열. `!gcroot`가 답을 준다.

### 규칙 1 — 스스로를 교육하라

**① 규칙**
알아야 할 것을 계속 배워라. 이 목록에서 가장 일반적인 규칙이고, 메모리 관리보다 훨씬 넓은 범위에 적용된다.

**② 왜**
정보에 즉시 접근할 수 있는 시대에도 **지식은 저절로 오지 않는다. 벌어야 한다.** 지루하고 시간이 걸리고 힘든 과정이라 계속 스스로를 동기 부여해야 한다. 일상 업무가 어느 정도 가르쳐 주는 것은 사실이지만, 안전지대 밖으로 나가려면 **의식적인 행동**이 필요하다.

원천 도서가 이 규칙의 근거로 드는 개념이 **기계 공감(Mechanical Sympathy)** 이다. 랠리 드라이버 Jackie Stewart가 만들고 Martin Thompson이 IT 세계에 들여왔다.

> 레이싱 드라이버가 되기 위해 엔지니어일 필요는 없다. 그러나 기계 공감은 있어야 한다.

정비공이 아니어도 레이싱 드라이버가 될 수 있다. 그러나 차가 어떻게 동작하는지, 엔진이 어떻게 도는지, 어떤 힘이 작용하는지에 대한 깊은 지식 없이 좋은 레이싱 드라이버가 되기는 어렵다. **차와 조화롭게 일하려면 "차를 느껴야" 한다.** 프로그래머도 같다. .NET이라는 프레임워크만 알고 거기서 멈추면, 핸들과 페달 몇 개의 관점에서만 차를 보는 일요일 운전자와 같아진다.

**③ 언제 예외인가**
이 규칙에 예외는 없다. 다만 **방향은 있다.** 무작정 저수준으로 파고드는 것이 답은 아니다. 규칙 4가 경고하듯, 알 필요 없는 저수준 지식을 코드에 적용하면 해를 끼친다.

이 목록의 나머지 스물다섯 개가 그 방향을 준다. **규칙마다 "왜"가 붙어 있는 이유가 이것이다** — 규칙을 외우는 것이 아니라 근거를 이해하는 것이 규칙 1의 실천이다.

**④ 본문 참조**
수동 관리 vs 자동 관리의 트레이드오프는 (61.8절), 추적 수집기와 정밀 GC 선택의 연쇄는 (61.9절), 런타임 소스를 직접 읽는 방법은 (83장), 자기 검증 체크리스트는 (84장).

## B.9 안티패턴 — 규칙 20 · 21 · 22

세 규칙은 모두 "하지 마라"의 형태다. 그리고 셋 다 **가끔은 해야 하는** 것들이라 판단이 필요하다.

### 규칙 20 — 명시적 GC를 피하라

**① 규칙**
`GC.Collect()`를 부르지 마라. 부르기 전에 두 번, 세 번 생각하라.

**② 왜**
명시적으로 GC를 트리거하는 것은 **GC의 작업을 방해하는 것**이다. GC가 내부적으로 어떤 튜닝을 하고 있든, 명시적 호출은 그것을 전부 우회하고 그 시점에 수집을 강제한다. 정당한 시나리오가 몇 가지 있지만, **대부분의 경우는 정당하지 않다.**

이 규칙을 지키는 방법은 GC를 배우는 것이다. **왜, 어떻게, 언제 도는지**를 이해하면, 명시적 수집이 지금 겪는 문제의 옳은 해법이 아닌 경우가 압도적으로 많다는 것을 알게 된다.

**③ 언제 예외인가**
정당한 경우가 아주 없지는 않다. 대표적인 것이 **애플리케이션이 한동안 잠드는 경우**다(65.8절). 하루에 한 번 깨어나 몇 분 일하고 다시 자는 서비스를 생각해 보자. 활동이 끝나면 24시간 동안 아무 할당도 없으므로 **GC가 활성화될 기회 자체가 없다.** 객체 그래프가 비었는데도 활동 중 소비한 메모리를 그대로 붙들고 있게 된다. 이 경우 활동 직후의 `GC.Collect`가 옳은 해법이다.

다른 정당한 경우들.

| 상황 | 근거 |
|---|---|
| 잠들기 직전의 배치·타이머 기반 애플리케이션 | 위 설명 |
| LOH 압축을 명시적으로 요청할 때 | `LargeObjectHeapCompactionMode.CompactOnce`는 다음 블로킹 GC에서만 적용된다 (65.8절) |
| 규칙 7의 누수 검증 절차 | 진단 목적. 코드에 남기지 않는다 |
| 파이널라이저를 가진 타입의 단위 테스트 | `Collect` → `WaitForPendingFinalizers` → `Collect` (34장) |
| 자체 메모리 회계 임계값 기반 트리거 | **측정으로 뒷받침되어야 한다** (65.8절) |

**④ 본문 참조**
`GC.Collect` 오버로드와 정당한 사용 사례는 (65.8절), `GCCollectionMode.Aggressive`도 같은 절, 명시적 GC가 GC 트리거 사유 중 하나로 기록되는 방식은 (63.6절), `AddMemoryPressure`는 (65.8절), 진단 목적의 강제 GC 대안은 (66.1절).

> **⚠️ `GC.Collect()`는 `OutOfMemoryException`을 고치지 않는다**
>
> `OutOfMemoryException`은 GC가 이미 여러 번 돈 뒤의 마지막 결정이다(63.8절). 예외를 잡아 `GC.Collect()`를 부르고 재시도하는 코드는 아무것도 개선하지 않는다. **유일한 예외가 LOH 할당 중 발생한 경우**로, 이때는 LOH 압축을 명시적으로 요청하고 GC를 한 번 더 도는 것을 고려할 만하다(63.8절, 65.8절).

### 규칙 21 — 메모리 누수를 피하라

**① 규칙**
관리 환경에서도 누수는 생긴다. 만들지 마라.

**② 왜**
원천 도서의 근거 문단이 이 목록에서 가장 짧다 — **"메모리 누수는 나쁘다. 끝."** 프로그램을 못 쓰게 만들거나, 시간이 지나면서 너무 느려져 재시작해야 하게 만들고, 최악의 경우 그냥 죽는다.

.NET 세계에서 가장 흔한 누수 형태는 하나다 — **도달 가능한 객체 수의 통제되지 않은 증가.** 무언가가 참조를 붙들고 있다. 당신은 그 객체들이 더 이상 쓰이지 않고 한참 전에 죽었어야 한다고 생각하는데, 실제로는 살아 있다. 이 어긋남 — 생존성은 알 수 없고 도달 가능성만 알 수 있다는 것 — 이 관리 환경 누수의 본질이다(61.9절).

"숨은 루트"의 종류는 정해져 있다 — **정적 변수, 이벤트, 잘못 구성된 IoC 컨테이너**, 그리고 그 밖의 여럿.

**③ 언제 예외인가**
규칙 7에서 본 대로, **작고 불가피한 누수는 용인할 수 있다.** 메모리 증가가 실질적으로 문제를 일으키지 않을 만큼 작고, 며칠에 한 번 배포로 프로세스가 재시작되고, 원인이 고칠 수 없는 서드파티 코드라면, 더 나쁜 문제를 조사하는 편이 낫다.

그리고 **의도적인 "누수"가 있다.** 캐시가 그렇다. 인터닝된 문자열도 그렇다(규칙 9). 이들은 누수가 아니라 설계 결정이고, 판별 기준은 **상한이 있는가**다. 상한 없는 정적 캐시는 누수이고, 크기나 시간으로 제한된 캐시는 아니다(66.11절).

**④ 본문 참조**
누수 판별은 (66.1절), 대표 시나리오 여섯 가지 — 이벤트 미해제, 상한 없는 정적 캐시, 정리 안 한 타이머, LOH 단편화, 파이널라이저 큐 적체, 어셈블리·로더 힙 누적 — 는 (66.11절), 지배자 분석과 루트 경로 추적은 (66.5절), 약한 참조를 이용한 캐시는 (34.6절), `ConditionalWeakTable`은 (34.9절), 타이머 누수는 (34.10절), 이벤트 구독 해제는 (27장).

> **📌 GC는 변하지 않지만 프레임워크는 변한다**
>
> 원천 도서가 이 규칙에서 특별히 지적하는 점이다. WCF나 WPF 같은 특정 기술의 누수 패턴은 다루지 않는다 — 그런 것들은 시대와 함께 바뀐다. 반면 **GC는 훨씬 느린 속도로 변하고, `dotnet-gcdump`·WinDbg·SOS·PerfView 같은 핵심 도구는 계속 유효하다.** 그래서 특정 프레임워크의 누수 목록을 외우는 것보다 진단 방법을 익히는 것이 오래간다.

> **⚠️ 숨은 루트 다섯 개와 각각의 확정 방법**
>
> 규칙 21의 실무적 내용은 "누수는 나쁘다"가 아니라 **"루트를 찾아라"** 다. 후보는 사실상 정해져 있다.
>
> | 숨은 루트 | 전형적 형태 | 확정 방법 |
> |---|---|---|
> | 정적 변수·정적 캐시 | 상한 없는 `static Dictionary` | `!gcroot` 경로가 **고정 핸들 → `System.Object[]` → 타입**으로 시작한다 (66.9절) |
> | 이벤트 구독 | 오래 사는 게시자가 짧게 사는 구독자를 붙든다 | 구독자 타입의 인스턴스 수가 계속 증가 (66.11절, 27장) |
> | 정리 안 한 타이머 | `System.Timers.Timer`를 `Dispose` 안 함 | 콜백이 참조하는 객체가 누적 (34.10절) |
> | IoC 컨테이너 오구성 | 싱글턴 수명으로 등록된 요청 범위 서비스 | 컨테이너 등록 검토 + 스냅샷 비교 (66.4절) |
> | 인터닝된 문자열 | 사용자 입력을 `string.Intern`에 넣음 | 문자열 인스턴스 수가 단조 증가 (35.5절) |
>
> 다섯 번째가 이 목록에 있다는 사실이 규칙 9의 위험성을 다시 말해 준다 — **규칙 9를 잘못 적용하면 규칙 21을 어기게 된다.**

### 규칙 22 — 고정을 신중히 쓰라

**① 규칙**
고정(pinning)은 필요할 때만, 가능한 한 짧게. 또는 아예 POH에 할당하라.

**② 왜**
고정이 나쁜 이유는 둘이다. **단편화를 유발할 수 있고**(규칙 19와 이어진다), **GC 자체의 오버헤드 원인**이 된다. 고정된 객체는 옮길 수 없으므로 Plan 단계가 크게 복잡해진다 — pre-plug/post-plug 복사 비용, 고정 plug가 일반 객체 하나만큼 확장되는 문제, 힙을 순차적으로 걸을 수 없게 되는 문제(64.7절).

그러나 **모든 고정이 똑같이 나쁜 것은 아니다.** 원천 도서의 분석이 정교하다.

| 고정의 수명 | 영향 |
|---|---|
| **짧은 수명** | 세대 0에서 죽기 전에 큰 단편화를 만들 기회가 없다. 대체로 괜찮다 |
| **긴 수명(gen2)** | 동시 GC에서 대부분의 gen2 수집이 백그라운드 GC(비압축)이므로 영향이 작다 |
| **중간 수명** | **가장 나쁘다.** 오래된 세대로 승격될 만큼 살아서 세대 계획의 자유를 제한하고, 임시 세그먼트를 쓸모없게 만들 수 있다 |

**③ 언제 예외인가**
고정은 필요할 때가 실제로 있다 — 비관리 코드에 버퍼를 넘길 때가 대표적이다(60장). 이 규칙은 "쓰지 마라"가 아니라 "어떻게 쓰느냐"에 관한 것이다.

원칙은 셋이다.

- **가능하면 POH에 직접 할당한다.** `GC.AllocateArray<T>(length, pinned: true)`가 있는 런타임에서는 이것이 가장 좋은 답이다(62.5절).
- **짧게 고정한다.** 아주 작은 범위의 `fixed` 블록이 이상적이다. `fixed`는 메서드의 GCInfo에 영향을 줄 뿐이므로, **그 메서드 실행 중에 GC가 일어나지 않으면 오버헤드가 전혀 없다**(64.4절, 64.7절).
- **길게 살 고정 버퍼를 만들어 재사용한다.** 수명이 길어져 gen2에 자리 잡으면 오버헤드가 작아지고, 흩어지는 대신 모여 있게 되어 지역성도 좋아진다.

그리고 **고정을 발견했다고 즉시 없애려 하지 마라.** 일반적인 애플리케이션에서는 단편화를 크게 만들지 않는 한 걱정할 것이 없다. 밀리초를 다투는 고성능 프로그램에서만 고정 객체 하나하나를 파악할 가치가 있다.

**④ 본문 참조**
POH와 NonGC 힙은 (62.5절), 고정이 계획 단계에 미치는 영향과 강등은 (64.6절, 64.7절), GCInfo와 `fixed`의 관계는 (64.4절), 상호운용에서의 고정은 (60장), 단편화 진단은 (66.11절).

> **⚠️ 규칙 22와 규칙 19는 같은 문제의 두 얼굴이다**
>
> 고정이 나쁜 첫 번째 이유가 단편화이므로, 규칙 22를 어기면 규칙 19가 자동으로 따라온다. 반대로 세대 2 단편화를 조사하다 보면 원인이 고정인 경우가 많다. **두 규칙을 함께 확인하라.**

## 이 부록의 요약

- **스물여섯 개는 평등하지 않다.** 규칙 1·5·6·7이 나머지보다 먼저 온다. 측정으로 문제를 확정하기 전에 나머지 스물두 개를 적용하는 것은 최적화가 아니라 추측이다.

- **규칙은 전부 조건부 명제다.** 원천 도서가 각 규칙에 적용 범위를 붙인 이유가 그것이다. 규칙 4는 "극도로 저수준인 성능 지향 코드"에만, 규칙 18~21은 "일반적이며 매우 흔한" 상황에 해당한다. 이 구분을 지우면 규칙은 미신이 된다.

- **코드 수정이 런타임 설정 변경보다 먼저다.** GC 모드를 바꾸는 것은 코드를 안 고쳐도 되니 매력적이지만, 배열 하나를 풀링하는 것이 설정 다섯 개를 조정하는 것보다 거의 항상 효과가 크다(65.10절).

- **규칙들은 서로 얽혀 있다.** 규칙 25(파이널라이저)를 어기면 규칙 18(중년기 위기)이 따라오고, 규칙 22(고정)를 어기면 규칙 19(단편화)가 따라온다. 규칙 12(힙 참조)를 적용하면 규칙 3(지역성)이 덤으로 온다. **하나를 고치면 여럿이 따라 움직인다.**

- **가장 위험한 규칙은 9(인터닝)와 15(풀링)다.** 둘 다 "GC의 자동 수명 관리를 수동 관리로 바꾸는" 거래이고, 잘못하면 회수 불가능한 메모리나 조용한 데이터 손상을 만든다. 적용 전 판별 질문이 명확히 정해져 있다.

- **규칙 20(명시적 GC)의 예외는 목록으로 관리하라.** 잠드는 애플리케이션, LOH 압축 요청, 누수 검증 절차, 파이널라이저 단위 테스트, 측정으로 뒷받침된 자체 회계. 이 다섯 외의 `GC.Collect()`는 리뷰에서 근거를 요구할 만하다.

- **절댓값에는 정상 범위가 없다.** 세대 크기도, 할당량도, GC 횟수도 마찬가지다. 판단 근거는 언제나 자기 애플리케이션의 기준선, 추세, 이전 버전과의 비교다.

- **이 목록의 마지막 규칙은 규칙 1이다.** 스물다섯 개를 외우는 것보다 각 규칙의 "왜"를 이해하는 편이 오래가고, 그것이 기계 공감이다.

## 연습 문제

1. 자기 팀의 서비스 하나를 골라 B.1절의 5단계 흐름도에서 **현재 어느 단계에 있는지** 판정하라. 0~2단계를 건너뛰고 3~4단계의 작업을 하고 있다면, 건너뛴 단계를 채우는 데 필요한 작업을 목록으로 만들어라.

2. `dotnet-counters`로 자기 애플리케이션의 `gc-heap-size`, `gc-committed`, `working-set`, `time-in-gc`를 10분간 수집하라(66.8절). B.10절의 "상황별 진입점" 표에서 자기 데이터에 해당하는 행이 있는지 찾고, 없다면 왜 없는지 적어라.

3. 규칙 7의 다섯 단계 검증 절차를 스크립트로 구현하라. 그다음 같은 검증을 **`GC.Collect()` 없이** 66.1절의 `Microsoft-Windows-DotNETRuntime:800000` 키워드 구독으로 다시 하고, 두 방법의 결과가 일치하는지 확인하라.

4. 파이널라이저가 있는 타입과 없는 타입을 각각 만들어 BenchmarkDotNet으로 할당만 벤치마킹하라(34.2절). `Gen1` 열에 값이 생기는지 확인하고, `SuppressFinalize`를 호출하는 버전을 추가해 세 결과를 비교하라. 규칙 25와 규칙 18의 연결을 자기 숫자로 설명하라.

5. `ArrayPool<T>`를 쓰는 코드 경로를 하나 골라 **반납을 일부러 빠뜨린 버전**과 **참조 타입 배열을 `clearArray: false`로 반납하는 버전**을 만들고, 각각 `dotnet-gcdump`로 스냅샷을 떠 무엇이 살아남는지 확인하라(69.3절). 규칙 15가 "왜 조건부인가"를 직접 관측하라.

6. 자기 코드베이스에서 `GC.Collect()` 호출을 전부 찾아라. B.9절의 정당한 경우 표와 대조해 각 호출을 **정당함 / 진단 잔여물 / 근거 없음**으로 분류하고, 근거 없는 것을 제거한 뒤 성능 지표가 어떻게 변하는지 측정하라.

7. B.10절의 요약표에서 규칙 다섯 개를 골라, 각각에 대해 **자기 프로젝트에서 그 규칙을 어겨도 되는 구체적인 이유**를 한 문장으로 쓰라. 쓸 수 없는 규칙이 있다면 그것이 지금 손봐야 할 규칙이다.
