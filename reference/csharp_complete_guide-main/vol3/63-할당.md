# 63장. 할당

> **이 장의 위치** — 62장에서 관리 힙의 지도를 그렸다. 세그먼트와 리전, SOH·LOH·POH, 세대 0/1/2. 이제 그 지도 위에 **객체가 실제로 놓이는 순간**을 본다. `new` 한 줄이 IL의 `newobj`가 되고, JIT이 고른 할당 헬퍼가 되고, 최종적으로 어셈블리 명령 예닐곱 개가 되는 경로 전체를 따라간다. 그리고 이 장의 후반부는 이 책에서 가장 실무적인 부분이다 — **당신이 쓰지 않았다고 생각한 할당들의 카탈로그**.
>
> **선수 지식** — 54장(타입 시스템의 런타임 표현), 61장(메모리의 기초), 62장(.NET 힙의 구조), 26장(델리게이트와 람다)
>
> **이 장에서 다루지 않는 것** — 할당 예산이 소진된 다음 GC가 실제로 무엇을 하는지(Mark/Plan/Sweep/Compact)는 64장에서, 워크스테이션/서버·백그라운드 모드 선택과 `GC.Collect` 같은 API는 65장에서, 할당 추적 도구의 전체 사용법은 66장에서, `Span<T>`와 `stackalloc`의 언어적 세부는 68장에서, 할당 회피의 실무 심화는 69장에서 다룬다. 파이널라이저의 동작과 F-reachable 큐는 34장에서 이미 다뤘다.

## 63.1 범프 포인터 할당과 할당 컨텍스트

### 관리 환경이 OS 앞에 층을 하나 더 두는 이유

C/C++는 운영체제의 할당 메커니즘에 직접 기댄다. Windows의 Heap API, Linux의 `mmap`/`sbrk` 조합이다. `malloc`/`new`는 결국 그 위에 얹힌 얇은 층이다.

.NET은 다르다. 런타임이 **운영체제와 프로그램 사이에 층을 하나 더 넣는다.** 큰 연속 메모리 블록을 미리 확보해 두고, 그 안에서 자체 할당 메커니즘을 돌린다. 이유는 단순하다. 객체를 만들 때마다 OS에 메모리를 요청하는 것보다 **훨씬 빠르기 때문이다.** 시스템 호출은 비싸고, 객체 생성은 아주 흔하다. 콘솔 애플리케이션은 당신의 첫 줄이 실행되기 전에 이미 수많은 보조 객체를 만든다.

62장에서 본 구조를 할당의 관점에서 다시 정리하면 이렇다. 사용자 코드의 할당이 **일어날 수 있는 곳은 네 군데뿐**이다.

| 할당 위치 | 조건 | 물리적 위치 |
|---|---|---|
| **SOH 세대 0** | 85,000바이트 미만 객체 | ephemeral 세그먼트 / gen0 리전 |
| **LOH** | 85,000바이트 이상 객체 | LOH 세그먼트/리전. 세대로 더 쪼개지지 않는다 |
| **POH** | `GC.AllocateArray`/`AllocateUninitializedArray`에 `pinned: true` | POH 리전 |
| **NonGC 힙** | 읽기 전용 리터럴 문자열 등 런타임 내부 특수 케이스 | 동결(frozen) 영역 |

Book of the Runtime의 요약이 이 차이를 한 문장으로 말한다. "큰 객체를 할당할 때마다 **대형 객체 힙 전체**가 고려된다. 작은 객체 할당은 **ephemeral 세그먼트만** 고려한다."

할당자를 구현하는 방식은 크게 두 가지가 있고, .NET은 **둘 다** 쓴다. 순차 할당(sequential allocation)과 프리 리스트 할당(free-list allocation)이다. 순차 할당부터 본다.

### 포인터 하나를 밀면 그게 할당이다

세그먼트 안에서 메모리를 확보하는 가장 단순하고 빠른 방법은, "현재까지 할당된 부분이 어디서 끝나는가"를 가리키는 포인터 하나를 밀어 버리는 것이다. 이 포인터를 **할당 포인터(allocation pointer)** 라 한다. 만들려는 객체 크기만큼 포인터를 옮기고, 옮기기 전 위치를 돌려주면 그게 새 객체의 주소다.

```text
(a) 할당 전
  ┌────────┬────────┬────────┬─────────────────────────────────
  │ 객체 1 │ 객체 2 │ 객체 3 │           미사용
  └────────┴────────┴────────┴─────────────────────────────────
                             ▲
                             alloc_ptr

(b) 객체 A(40바이트) 할당 후
  ┌────────┬────────┬────────┬──────────┬──────────────────────
  │ 객체 1 │ 객체 2 │ 객체 3 │  객체 A  │        미사용
  └────────┴────────┴────────┴──────────┴──────────────────────
                             ▲          ▲
                    반환된 주소         alloc_ptr (+40)
```

의사 코드로 쓰면 세 줄이다.

```text
PTR Allocator.Allocate(amount)
{
     PTR result = alloc_ptr;
     alloc_ptr += amount;
     return result;
}
```

이것이 **범프 포인터 할당(bump pointer allocation)** 이다. 포인터를 "밀어서(bump)" 메모리를 준다. 성질이 두 가지 있다.

- **순차적이다.** 할당할 때 포인터는 항상 같은 방향으로만 움직인다. 이것이 **데이터 지역성**을 만든다. 한 번에 여러 객체를 만들면 그 객체들은 서로 의존하는 자료 구조일 가능성이 높고, 그것들이 메모리에서 가까이 놓인다. 61.5절에서 본 시간적·공간적 지역성이 그대로 이득으로 돌아온다.
- **메모리가 무한하다고 가정한다.** 당연히 거짓이다. 하지만 포인터의 **왼쪽에서 마법을 부릴 수 있다면** 이야기가 달라진다. 죽은 객체를 걷어내고 구멍을 압축하는 것 — 그것이 GC다. 수집 후 할당 포인터는 뒤로 "되감긴다".

> **📌 "할당은 싸다"는 말의 출처**
>
> .NET에서 할당이 싸다고들 하는 근거가 바로 이 세 줄이다. 어셈블리로 옮기면 명령어 예닐곱 개다. 뒤에서 실제 코드를 볼 것이다. 다만 이 말은 **빠른 경로가 성립할 때만** 참이다. 이 장의 절반은 그 단서 조항에 대한 이야기다.

### 0으로 채우는 비용, 그리고 할당 컨텍스트의 탄생

객체 A가 놓일 자리의 메모리 내용은 어떻게 되는가? 새 객체는 깨끗한 상태여야 한다. 필드 일부는 생성자가 채우지만(그건 실행 엔진의 일이지 GC의 일이 아니다), **나머지는 0이어야 한다.** 그러면 할당 함수는 이렇게 되어야 한다.

```text
PTR Allocator.Allocate(amount)
{
     PTR result = alloc_ptr;
     ZeroMemory(alloc_ptr, amount);
     alloc_ptr += amount;
     return result;
}
```

0으로 채우는 것은 공짜가 아니다. 객체 생성처럼 극도로 흔한 연산에서는 무시할 수 없다. 그래서 **미리 0으로 채워 둔 메모리를 준비해 두는** 전략을 쓴다. 위 코드는 느린 경로로 밀어 두고, 평소에는 앞의 세 줄짜리 빠른 경로만 실행한다. 덤으로, 미리 0을 쓰면 그 영역이 CPU 캐시에 "데워져" 있게 되므로 캐시 활용도까지 좋아진다.

여기서 두 번째 포인터가 등장한다. **할당 한계(allocation limit)** 는 미리 0으로 채워 둔 영역이 어디서 끝나는지를 가리킨다. 할당 포인터와 할당 한계 사이의 구간을 **할당 컨텍스트(allocation context)** 라 한다.

```text
             ← 할당 컨텍스트 (0으로 채워진 즉시 사용 가능 영역) →
  ┌────────┬────────┬═════════════════════════════════════┬────────────
  │ 객체 1 │ 객체 2 ║           준비된 메모리              ║  미커밋/미정리
  └────────┴────────┴═════════════════════════════════════┴────────────
                    ▲                                     ▲
                    alloc_ptr                             alloc_limit

   할당 = alloc_ptr을 오른쪽으로 민다
   alloc_ptr + 크기 > alloc_limit  →  느린 경로로 빠진다
```

실제 할당자는 이 두 포인터를 비교하는 분기를 하나 갖는다.

```text
PTR Allocator.Allocate(amount)
{
   if (alloc_ptr + amount <= alloc_limit)
   {
      // 빠른 경로 — 포인터를 밀 공간이 있다
      PTR result = alloc_ptr;
      alloc_ptr += amount;
      return result;
   }
   else
   {
      // 느린 경로 — 할당 컨텍스트(alloc_ptr, alloc_limit)를 요청 크기에 맞게 바꾼다.
      // 최소한 할당 퀀텀만큼 키운다.
      if (!try_allocate_more_space())
      {
         throw OutOfMemoryException;
      }
      PTR result = alloc_ptr;
      alloc_ptr += amount;
      return result;
   }
}
```

할당 컨텍스트가 부족할 때 늘어나는 단위를 **할당 퀀텀(allocation quantum)** 이라 한다.

### 퀀텀과 커밋의 어긋남

62.6절에서 세그먼트는 예약 후 필요할 때 페이지를 커밋한다고 했다. 그런데 커밋된 페이지가 전부 즉시 0으로 정리되는 것은 아니다. **커밋 단위와 0 채우기 단위는 다르다.**

| 항목 | 기본값 | 비고 |
|---|---|---|
| **할당 퀀텀** (SOH) | **8 kB** | 상황에 따라 **1,024~8,096바이트** 사이에서 동적으로 조정된다 |
| **세그먼트 커밋 단위** | **16페이지 = 보통 64 kB** | 한 번에 16페이지씩 커밋한다 |

즉 할당 컨텍스트는 커밋된 영역의 끝까지 뻗어 있지 않다. 컨텍스트가 소진되면 이미 커밋된 페이지 안에서 다음 퀀텀만큼만 정리해서 컨텍스트를 다시 잡는다. OS에 페이지 커밋을 요청하지 않고도 컨텍스트를 계속 이어 갈 수 있다는 뜻이다. **준비 비용과 준비 이득 사이의 타협**이다.

> **📌 퀀텀은 고정값이 아니다**
>
> 기본 할당 퀀텀은 8 kB지만 현재 CLR 구현은 **할당 속도(rate of allocations)와 활성 컨텍스트 개수**에 따라 1,024~8,096바이트 범위에서 값을 바꾼다. 스레드가 아주 많고 각각 조금씩만 할당하는 애플리케이션에서 8 kB짜리 컨텍스트를 스레드마다 잡아 주면 낭비가 되기 때문이다.

할당 컨텍스트가 항상 커밋 영역의 끝에만 생기는 것도 아니다. **기존 객체들 사이의 빈 공간 안에 놓일 수도 있다.** 그 경우 할당 포인터는 빈 공간의 시작, 할당 한계는 그 끝을 가리킨다. 어느 빈 공간을 쓸지는 다음 절의 프리 리스트가 결정한다.

### 스레드 친화성 — 락이 없는 진짜 이유

할당 컨텍스트에 관해 가장 중요한 사실은 이것이다. **할당 컨텍스트는 스레드 친화성(thread affinity)을 갖는다.** 관리 코드를 실행하는 각 관리 스레드는 **자기만의 할당 컨텍스트**를 갖는다.

Book of the Runtime의 표현: "할당 컨텍스트와 퀀텀의 스레드 친화성은 주어진 할당 퀀텀에 쓰는 스레드가 항상 단 하나임을 보장한다. 그 결과, 현재 할당 컨텍스트가 소진되지 않는 한 **객체 할당에 락이 필요 없다.**"

이것이 성능상 결정적이다. 컨텍스트가 스레드 간에 공유되었다면 `Allocate`는 동기화되어야 했고, 그 오버헤드가 모든 객체 생성에 붙었을 것이다.

구현은 **스레드 지역 저장소(TLS, thread local storage)** 위에 있다. 정확히는 각 스레드가 `ThreadLocalInfo` 구조체 인스턴스를 갖고, 그것이 `Thread` 클래스 인스턴스를 담고, 그 안에 할당 컨텍스트가 있다. Java 진영에서 **TLAB(Thread Local Allocation Buffer)** 라 부르는 것과 같은 기법이다.

> **⚠️ 논리 프로세서가 하나면 전역 컨텍스트를 쓴다 — 단, Windows에서만**
>
> 논리 프로세서가 하나뿐인 머신에서는 할당 컨텍스트도 하나만 만들어진다. 이 경우 여러 스레드가 같은 전역 컨텍스트에 접근하므로 **동기화가 필요하다.** 다만 어느 시점에도 스레드 하나만 실행되므로 동기화 비용 자체는 매우 싸다. **Linux에서는 코어가 하나여도 전역 할당 컨텍스트를 절대 쓰지 않는다.** 단일 코어 컨테이너에서 Windows와 Linux의 할당 경로가 다르다는 뜻이므로, 마이크로 벤치마크를 플랫폼 간에 비교할 때 주의하라.

그래서 세그먼트 하나 안의 실제 그림은 다음과 같다.

```text
   ephemeral 세그먼트 (gen0 + gen1, 초기에는 gen2까지)
  ┌──────────────────────────────────────────────────────────────────┐
  │ 객체 객체 ░░░░ 객체 객체 객체 ░░░░░░ 객체 객체 ▓▓▓▓▓▓▓▓▓         │
  │           ↑↑                  ↑↑                ↑↑               │
  │        컨텍스트 A          컨텍스트 B        컨텍스트 C           │
  │        (스레드 T1)         (스레드 T2)       (스레드 T3)          │
  │        빈 공간 재사용      빈 공간 재사용    세그먼트 끝에서      │
  └──────────────────────────────────────────────────────────────────┘
     ░ = 스윕이 남긴 빈 공간(프리 리스트 항목)
     ▓ = 커밋되었으나 아직 컨텍스트로 잡히지 않은 영역
```

리전(.NET 7+)에서도 설명은 그대로 적용된다. 다만 할당 컨텍스트는 **gen0 리전 안에** 살고, 리전 시작부에 `segment_info`가 없다. 리전 하나는 정확히 한 세대의 객체만 담는다.

### 범프 포인터의 약점과 .NET의 대응

순수한 범프 포인터 할당에는 결함이 하나 있다. **스윕 방식의 수집이 돌면 단편화가 생긴다.** 할당 포인터 왼쪽에 빈 구멍이 잔뜩 생기는데, 순진한 범프 포인터 할당자는 그 구멍의 존재를 모른다. 메모리를 계속 앞으로만 먹는다.

가장 단순한 해법은 **압축 수집을 트리거하는 것**이다. 생존 객체들을 나란히 붙이면 할당 컨텍스트가 뒤로 밀려난다. 하지만 압축은 메모리 복사 비용이 크다.

.NET은 더 나은 길을 택했다. **빈 공간 안에 할당 컨텍스트를 만든다.** 단편화가 만든 구멍을 재사용하는 것이다. 그리고 이따금 GC가 압축을 결정하면, 그때 모든 할당 컨텍스트가 자연스럽게 세그먼트 끝쪽으로 재편된다.

```text
(a) 압축 전 — 컨텍스트 세 개가 흩어져 있다
  ┌───┬░░░░┬───┬───┬░░░░░┬───┬░░░┬─────────────────────┐
  │ A │ C1 │ B │ C │ C2  │ D │C3 │      미사용          │
  └───┴────┴───┴───┴─────┴───┴───┴─────────────────────┘

(b) 압축 후 — 생존 객체가 앞으로 몰리고 컨텍스트가 끝에 재배치된다
  ┌───┬───┬───┬───┬─────┬─────┬─────┬─────────────────┐
  │ A │ B │ C │ D │ C1  │ C2  │ C3  │     미사용       │
  └───┴───┴───┴───┴─────┴─────┴─────┴─────────────────┘
```

> **💡 할당 컨텍스트를 눈으로 확인하는 법**
>
> WinDbg에서 `!eeheap -gc`를 실행하면 `ephemeral segment allocation context:` 줄이 보인다. 유휴 상태의 단순 콘솔 앱에서는 `none`으로 찍히지만, 활발히 할당 중인 프로세스를 덤프하면 실제 `alloc_ptr`/`alloc_limit` 쌍이 나온다. 두 값의 차이가 그 스레드에 남은 빠른 경로 용량이다. 스레드가 수백 개인 서버에서 이 값들을 훑어보면, 왜 스레드를 무한정 늘리는 것이 관리 힙에 부담인지 바로 보인다 — 스레드마다 최대 8 kB짜리 컨텍스트가 붙는다.

## 63.2 프리 리스트 할당

### 발상 자체는 시시하다

런타임이 GC에게 N바이트를 요청하면, GC는 **프리 리스트(free-list)를 뒤져서 N바이트가 들어갈 만큼 큰 빈 구멍을 찾는다.** 그게 전부다. 문제는 "뒤지는 방식"이다. 61장에서 본 두 전략이 여기서도 그대로 등장한다.

| 전략 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **최적 적합(best-fit)** | 요구 크기 이상인 것 중 **가장 작은** 구멍 | 남는 자투리가 최소 | 순진하게 구현하면 리스트 전체를 훑어야 한다 |
| **최초 적합(first-fit)** | 맞는 구멍을 **찾는 즉시** 중단 | 빠르다 | 단편화 관점에서 결과가 나쁘다 |

Microsoft 구현은 **버킷(bucket)** 으로 절충한다. 크기 구간별로 프리 리스트를 여러 개 두면, 빠르게 훑으면서도 단편화 최적화를 크게 훼손하지 않는다. 버킷 개수가 곧 조절 손잡이다.

- 버킷이 **하나**뿐이면(크기와 무관하게 전부 거기 들어가면) 사실상 순진한 최초 적합이다.
- 버킷이 **아주 많으면**(크기 구간이 촘촘하면) 최적 적합에 가까워진다.

그리고 뒤에서 보겠지만, **버킷 개수는 세대마다 다르다.**

### 빈 공간도 힙 위의 객체다

힙을 훑다가 빈 공간을 만나면, 다음 유효 객체로 건너뛰기 위해 그 빈 공간의 크기를 알아야 한다. 프리 리스트에서 해당 항목을 찾아 크기를 읽어 올 수도 있지만, 그러면 힙과 프리 리스트 사이를 왔다 갔다 해야 한다. 오버헤드가 상당하다.

그래서 .NET은 **빈 공간의 시작 위치에 더미 객체를 직접 심는다.** 이 더미 객체는 특별한 "free object" 메서드 테이블을 가진 **평범한 배열처럼 생겼다.**

```text
     "free object" — 빈 공간을 표현하는 더미 배열
  ┌────────────┬────────────────┬────────────┬───────────────────────┐
  │  undo 또는  │  MT 포인터     │  요소 개수 │   실제 빈 바이트들     │
  │  객체 헤더  │ (g_pFreeObject │  = 빈 공간 │                       │
  │            │  MethodTable)  │  바이트 수 │                       │
  └────────────┴────────────────┴────────────┴───────────────────────┘
        ↑                              ↑
    일부 세대에서는 헤더 대신      요소 크기가 1바이트이므로
    "undo" 필드로 쓰인다           개수 = 바이트 수가 된다
```

요소 크기가 **1바이트**이므로 요소 개수가 곧 빈 공간의 바이트 크기가 된다. 힙을 훑을 때는 free object의 길이만 읽어 그만큼 건너뛰면 된다. 영리한 설계다.

일부 세대에서는 free object에 불필요한 객체 헤더 대신 **"undo"** 라는 요소가 들어간다. 리스트를 조작하는 동안 다른 프리 리스트 항목의 주소를 임시로 담아 두는 자리다. 용도는 뒤에서 설명한다.

> **📌 소스 코드에서 free object를 따라가는 법**
>
> `gc_heap::make_unused_array` 메서드가 free object를 준비한다. 이 메서드는 `SetFree`를 호출하고, `SetFree`는 전역 정적 포인터 `g_pFreeObjectMethodTable`을 새 MT로 사용한다. 구멍을 프리 리스트에 넣는 것은 `allocator::thread_item(gap_start, size)` 또는 `allocator::thread_item_front(gap_start, size)`다. **이 작업은 최소 객체 크기의 두 배보다 큰 구멍에 대해서만 수행된다.** 작은 항목은 무시해서 리스트 관리 오버헤드를 줄인다.

### 버킷 구성 — 세대마다 다르다

각 세대의 할당자는 버킷 리스트를 유지한다. 첫 버킷은 "첫 버킷 크기"(`first_bucket_bits` 필드에 인코딩됨)보다 작은 항목들의 리스트다. 그다음 버킷마다 이 크기가 **두 배씩** 커지고, 마지막 버킷은 상한 없이 가장 큰 것들을 담는다.

| 영역 | 첫 버킷 크기 | 버킷 개수 |
|---|---|---|
| **세대 0, 1** | Int.Max | **1** |
| **세대 2** | 256 B (64비트) / 128 B (32비트) | **12** |
| **LOH** | 64 kB | **7** |
| **POH** | 256 B | **19** |

세대 0과 1은 버킷이 **하나**다. 크기를 가리지 않고 전부 한 리스트에 들어간다. 왜 그런가는 조금 뒤에 답한다.

64비트 세대 2를 예로 들면 GC는 256 B, 512 B, 1 kB, 2 kB, 4 kB, 8 kB 미만, 그리고 8 kB 초과용 버킷들을 유지한다.

리스트 자체는 힙 위의 free object들을 서로 연결해 만든다. **별도의 리스트 자료 구조를 두지 않는다.** 힙의 일부가 이미 캐시에 올라와 있으므로 순회가 빠르다.

- **세대 2**: 이중 연결 리스트
- **그 외(세대 0, 1, UOH)**: 단일 연결 리스트

> **📌 세대 2만 이중 연결 리스트인 이유 ※.NET 6**
>
> .NET 6 이전에는 **모든 세대의 프리 리스트가 동시 스윕(Concurrent Sweep) 단계 시작 시 초기화**되었다. 문제는 세대 2 동시 스윕 도중에도 SOH에는 일반 할당이 계속 일어난다는 것이다. 그러다 "포그라운드 GC"가 트리거되어 세대 1을 압축 수집하면, 승격되는 객체를 세대 2의 구멍에 넣으려 한다. 그런데 리스트가 이미 비워진 상태라 재사용을 못 한다. 결과는 **세대 2의 불필요한 성장** — 승격된 객체는 결국 세대 2의 끝에 "할당"되어야 하니까.
>
> .NET 6부터 세대 2 프리 리스트는 GC 시작 시 초기화되지 않는다. 대신 리스트가 커질 수 있으므로, 연결·해제가 빠른 **이중 연결 리스트**로 바꾼 것이다.

> **⚠️ "세대마다 할당자가 있다"는 말과 "사용자는 gen0에만 할당한다"는 말은 모순이 아니다**
>
> 사용자 코드는 세대 0, LOH, POH에만 할당한다. 그런데 왜 세대 1, 2에도 할당자와 프리 리스트가 있는가? **GC가 승격시킬 때 그것도 "할당"이기 때문이다.** 세대 1 생존자를 세대 2로 옮기는 것은 세대 2 할당자가 자리를 찾는 일이다. 이 구분을 놓치면 64장의 Plan 단계 설명이 통째로 안 읽힌다.

### 버킷 기반 할당 알고리즘

```text
PTR Allocator.Allocate(amount)
{
   foreach (bucket in buckets)
   {
      if (amount < bucket.BucketSize)  // 항목이 너무 작은 버킷은 건너뛴다
      {
         foreach (freeItem in bucket.FreeItemList)
         {
            if (size < freeItem.Size)
            {
               UnlinkItem(freeItem);
               ZeroMemory(freeItem.Start, amount);
               if (RemainingFreeSpaceBigEnough())
                  LinkRemainingFreeSpace(freeItem, amount);
               return freeItem.Start;
            }
         }
      }
   }
}
```

적절한 첫 버킷부터 시작해 맞는 항목을 찾는다. 필요한 만큼 떼어 쓰고 나면 자투리가 남는데, 그 자투리가 **객체 두 개의 최소 크기보다 크면**(64비트에서 **48바이트**) 새 free item을 만들어 리스트에 다시 넣는다. 그보다 작으면 **사용 불가능한 단편화**로 계산된다.

> **⚠️ 프리 리스트 할당의 0 채우기는 조건부다**
>
> 위 의사 코드의 `ZeroMemory`는 **사용자 할당일 때만** 필요하다. 새 객체는 깨끗한 상태여야 하니까. 반면 **승격 중 오래된 세대에 할당할 때는 생략된다** — 어차피 승격되는 객체 내용으로 덮어써질 것이기 때문이다. .NET은 정확히 이렇게 구현되어 있다. 프로파일러에서 "GC 중 메모리 0 채우기 비용"을 찾을 때 이 비대칭을 모르면 숫자가 안 맞는다.

세대 0과 1에는 규칙이 하나 더 있다. **요구 크기에 맞지 않는 free item은 그냥 버려진다.** 사용 불가능한 단편화 메모리가 되어 버린다. 즉 이 두 세대에서 각 free item은 **딱 한 번만 검사된다.** 프리 리스트 유지 비용과 단편화 허용 비용 사이의 또 다른 타협이다. 근거는 명확하다 — **가장 어린 두 세대는 자주 압축되므로 프리 리스트가 자주 재구성된다.** 정성껏 관리해 봐야 곧 버려진다.

이제 세대 0·1의 버킷이 하나뿐인 이유도 설명된다. 어차피 한 번만 보고 버릴 리스트에 정교한 크기 분류를 붙일 이유가 없다.

### undo 필드의 정체

free object의 "undo" 요소는 GC의 **Plan 단계**에서 쓰인다. 어린 세대에서 승격될 객체를 담을 자리로 오래된 세대의 free item 하나를 쓰기로 결정했을 때, GC는 그 항목을 단일 연결 리스트에서 "연결 해제"한다.

```text
   해제 전:   [ item1 ] ──next──▶ [ item2 ] ──next──▶ [ item3 ]

   item2를 쓰기로 결정:
     · item2의 주소를 item1의 "undo"에 저장한다 (이전 항목이 있다면)
     · item1의 next를 item3으로 바꾼다

   해제 후:   [ item1 ] ──next──────────────────────▶ [ item3 ]
                 └ undo = &item2
```

왜 되돌릴 수단이 필요한가? **Plan 단계가 끝날 때 GC는 압축 대신 스윕을 하기로 마음을 바꿀 수 있기 때문이다.** 스윕이면 오래된 세대는 건드리지 않으므로, 계획했던 할당들을 전부 취소해야 한다. 그때 undo에 저장해 둔 주소로 원래 리스트를 복원한다. 이 단계들의 관계는 64.6절과 64.9절에서 자세히 본다.

> **💡 프리 리스트가 언제 쓰이는지 한 줄로**
>
> 사용자 코드 관점에서 프리 리스트가 쓰이는 순간은 **세 가지**다. (1) SOH 느린 경로에서 새 할당 컨텍스트 자리를 찾을 때, (2) LOH·POH 할당에서 객체 자리를 직접 찾을 때, (3) GC가 승격 대상을 오래된 세대에 배치할 때. 빠른 경로에서는 프리 리스트를 보지 않는다 — 그래서 빠르다.

## 63.3 새 객체가 만들어지는 전체 경로 (`newobj` → 할당자 → 초기화)

두 가지 할당 기법을 알았으니, 이제 그것들이 실제로 어떻게 조합되는지 본다. C# 한 줄에서 어셈블리까지 끝까지 내려간다.

### 1단계 — C#에서 IL로

배열이 아닌 참조 타입 객체를 `new`로 만들면 CIL 명령 `newobj`가 나온다.

```csharp
var obj = new SomeClass();
```

```il
newobj instance void SomeClass::.ctor()
```

배열이면 `newarr`가 나온다. `newarr`에도 여러 변종이 있다 — 1차원 객체 배열용, 1차원 값 타입 배열용 등으로 최적화되어 있다. 다만 그 아래의 할당 구현은 본질적으로 같으므로 여기서는 `newobj`로 이야기를 진행한다.

### 2단계 — JIT이 할당 헬퍼를 고른다

JIT 컴파일러는 `newobj`에 대해 **여러 조건에 따라 적절한 함수 호출을 방출한다.** 가장 흔한 경우는 **할당 헬퍼(allocation helper)** 중 하나를 쓰는 것이다. 결정 트리는 다음과 같다.

```text
                        getNewHelper
                             │
              ┌──────────────┴──────────────┐
              │  크기 > LargeObjectSize     │
              │            또는             │
              │      파이널라이저 있음       │
              └──────────────┬──────────────┘
                   True      │      False
              ┌──────────────┘      └──────────────┐
              ▼                                    ▼
        ┌───────────┐                        ┌──────────┐
        │  JIT_New  │                        │ 플랫폼?  │
        │ (범용·느림)│                        └────┬─────┘
        └───────────┘             Windows ────────┴──────── 비-Windows
                                     │                          │
                                     ▼                          ▼
                          ┌────────────────────┐   ┌──────────────────────────┐
                          │ 서버 GC 또는        │   │ JIT_NewS_MP_FastPortable │
                          │ 논리 프로세서 다수? │   │  (할당 컨텍스트 사용)     │
                          └─────┬────────┬─────┘   └──────────────────────────┘
                          True  │        │  False
                                ▼        ▼
        JIT_TrialAllocSFastMP_InlineGetThread   JIT_TrialAllocSFastMP
```

핵심 갈래는 둘이다.

- 객체가 **대형 객체 임계값을 넘거나**(→ LOH행), **파이널라이저를 가지면** 범용이면서 조금 느린 `JIT_New` 헬퍼를 쓴다.
- 그 외에는 더 빠른 헬퍼를 쓴다. 어느 버전인지는 **플랫폼과 GC 모드**가 결정한다.

> **📌 이 결정 트리는 실행 중에 평가되지 않는다**
>
> 결정은 전부 **JIT 컴파일 시점**(혹은 그보다 이른 런타임 시작 시점)에 알 수 있는 조건에 기반한다. 즉 프로그램이 도는 동안에는 이 분기 비용이 **전혀 없다.** JIT이 이미 고른 헬퍼 호출 하나가 코드에 박혀 있을 뿐이다.

> **📌 .NET 소스에서 이 경로를 따라가는 법**
>
> JIT 임포터의 `CEE_NEWOBJ` 처리(`importer.cpp`의 `Compiler::impImportBlockCode`)에서 시작한다. 배열인지, 문자열인지, 값 타입인지, 참조 타입인지에 따라 할 일이 갈린다. 문자열과 배열이 아닌 참조 타입이면 `CEEInfo::getNewHelper`를 호출하고, 이것이 위 결정 트리의 앞부분을 수행한다. 느리고 범용인 헬퍼는 상수 `CORINFO_HELP_NEWFAST`, 빠른 쪽은 `CORINFO_HELP_NEWSFAST`로 표현된다. 이 상수들이 어느 함수로 연결되는지는 시작 시점의 `InitJITHelpers1` 메서드가 결정한다 — 결정 트리의 나머지 절반이 여기 있다.

### 3단계 — 빠른 경로의 실제 x64 코드

파이널라이저가 없는 SOH 객체를, 서버 GC 모드이거나 논리 프로세서가 여럿인 머신에서 만들 때 실행되는 코드다. **이것이 "할당은 싸다"의 실물이다.**

```asm
; 입력: rcx = MethodTable 포인터
; 출력: rax = 새 객체의 주소
LEAF_ENTRY JIT_TrialAllocSFastMP_InlineGetThread, _TEXT
    ; 객체 크기를 edx로 읽는다
    mov     edx, [rcx + OFFSET__MethodTable__m_BaseSize]
    ; m_BaseSize는 8의 배수임이 보장된다.
    ; 스레드 지역 저장소 주소를 r11으로 읽는다
    INLINE_GETTHREAD r11
    ; alloc_limit을 r10으로 읽는다
    mov     r10, [r11 + OFFSET__Thread__m_alloc_context__alloc_limit]
    ; alloc_ptr을 rax로 읽는다
    mov     rax, [r11 + OFFSET__Thread__m_alloc_context__alloc_ptr]
    add     rdx, rax          ; rdx = alloc_ptr + size
    cmp     rdx, r10          ; rdx가 alloc_limit보다 작은가
    ja      AllocFailed
    ; TLS의 alloc_ptr을 갱신한다
    mov     [r11 + OFFSET__Thread__m_alloc_context__alloc_ptr], rdx
    ; alloc_ptr 주소에 MT를 저장한다 (새 객체를 세운다)
    mov     [rax], rcx
    ret
AllocFailed:
    jmp     JIT_NEW           ; 빠른 경로 실패 — 느린 경로로 점프
LEAF_END JIT_TrialAllocSFastMP_InlineGetThread, _TEXT
```

한 줄씩 읽으면 이 장의 앞 두 절이 전부 여기 들어 있다.

| 명령 | 무슨 일인가 | 대응 개념 |
|---|---|---|
| `mov edx, [rcx+BaseSize]` | 메서드 테이블에서 **인스턴스 기본 크기**를 읽는다 | 54.1절의 `MethodTable` |
| `INLINE_GETTHREAD r11` | TLS에서 현재 스레드 구조체를 얻는다 | 할당 컨텍스트의 스레드 친화성 |
| `mov r10, [...alloc_limit]` | 이 스레드 컨텍스트의 **끝** | 할당 한계 |
| `mov rax, [...alloc_ptr]` | 이 스레드 컨텍스트의 **현재 위치** = 반환값 후보 | 할당 포인터 |
| `add rdx, rax` / `cmp rdx, r10` | 밀어도 되는지 **비교 한 번** | 빠른 경로 판정 |
| `mov [...alloc_ptr], rdx` | 포인터를 민다 | 범프 |
| `mov [rax], rcx` | 새 객체의 **첫 워드에 MT 포인터를 쓴다** | 객체 초기화의 시작 |
| `jmp JIT_NEW` | 실패 시 느린 경로 | 63.3 4단계 |

산술 하나, 비교 하나, 저장 두 번. **락 없음, 시스템 호출 없음, 분기 예측이 거의 항상 맞는 조건 분기 하나.** 이것이 관리 런타임의 할당이 C의 `malloc`보다 빠를 수 있는 이유다.

> **⚠️ 단일 프로세서 버전은 락을 건다**
>
> 단일 프로세서 머신용 버전은 `JIT_TrialAllocSFastSP`이며, 하나뿐인 전역 할당 컨텍스트에 안전하게 접근하기 위해 **잠금 메커니즘을 포함한다.** 위 코드와 명령 개수부터 다르다. 1코어 컨테이너에서 측정한 할당 성능을 4코어 환경에 그대로 대입하지 마라.

### 4단계 — 객체 초기화

어셈블리 코드는 MT 포인터를 쓰는 데서 끝난다. 나머지는 어디로 갔는가?

1. **객체 헤더(싱크 블록 인덱스)** — 할당 컨텍스트의 메모리는 이미 0으로 채워져 있다. 헤더의 초기값은 0이므로 따로 쓸 필요가 없다.
2. **메서드 테이블 포인터** — 위 코드의 마지막 `mov [rax], rcx`.
3. **인스턴스 필드** — 전부 0/`null`/`false`. 역시 미리 0으로 채워 둔 덕분에 공짜다.
4. **생성자 호출** — `newobj`는 할당 후 `.ctor`를 호출한다. 여기부터는 GC가 아니라 실행 엔진의 몫이다.

즉 **"0으로 채우기"를 할당 컨텍스트 준비 시점으로 앞당긴 대가로, 객체 생성 시점에는 필드 초기화가 사실상 공짜가 된다.** 이 설계 하나가 C# 프로그램의 체감 속도를 통째로 바꾼다.

> **⚠️ 그래서 필드 초기화를 "생략"해도 빨라지지 않는다**
>
> `int count = 0;`을 `int count;`로 바꾸면 빨라진다는 미신이 있다. C# 컴파일러는 애초에 기본값 대입을 IL로 방출하지 않고, 런타임은 이미 0으로 채워진 메모리를 준다. 값 타입 지역 변수의 `.locals init` 제거(`[SkipLocalsInit]`)는 다른 이야기이고, 그건 스택 이야기다(69.8절).

### 5단계 — 빠른 경로가 실패하면

할당 컨텍스트에 자리가 없으면 `jmp JIT_NEW`로 빠진다. `JIT_NEW`는 파이널라이저가 있는 객체나 LOH 객체에 쓰이는 바로 그 범용 헬퍼이며, **느린 경로 코드**를 담고 있다. **"할당은 싸다"가 항상 참이 아니게 되는 지점이 정확히 여기다.**

느린 경로는 자리를 찾으려 애쓰는 꽤 복잡한 상태 기계다. `a_state_start`에서 시작해 무조건 `a_state_try_fit`으로 넘어가고, 여기서 `gc_heap::soh_try_fit()`을 호출하면서 모험이 시작된다.

```text
                     soh_try_fit
                          │
              ┌───────────▼────────────┐
              │  a_fit_free_list_p     │
              │  프리 리스트에 맞는     │  ── 찾음 ──▶ 한계 조정 + 0 채우기
              │  항목이 있는가?         │              can_use_existing = True
              └───────────┬────────────┘
                       못 찾음
              ┌───────────▼────────────┐
              │  a_fit_segment_end_p   │
              │  커밋된 영역에          │  ── 들어감 ──▶ can_use_existing = True
              │  들어가는가?            │
              └───────────┬────────────┘
                       안 들어감
              ┌───────────▼────────────┐
              │  예약 영역에 들어가는가?│ ── 예 ──▶ 페이지를 더 커밋한다
              └───────────┬────────────┘
                        아니오
                          ▼
                 can_use_existing = False
                (GC 트리거 → 재시도 → OOM)
```

정리하면 느린 경로는 다음 순서다.

1. **ephemeral 세그먼트의 미사용 공간을 써 본다.**
   - 프리 리스트에서 새 할당 컨텍스트에 맞는 빈 구멍을 찾는다.
   - 이미 커밋된 메모리 안에 충분한 공간이 있는지 본다.
   - 예약된 메모리에서 페이지를 더 커밋해 본다.
2. 전부 실패하면 **가비지 컬렉션이 트리거된다.** 조건에 따라 **여러 번** 호출될 수도 있다.
3. 그래도 실패하면 **`OutOfMemoryException`** 이다.

SOH 느린 경로 코드는 `gc_heap::allocate_soh` 메서드에 있다.

> **📌 CLR 이벤트에서 이 트리거를 알아보는 법**
>
> SOH 할당 때문에 발생한 GC(가장 흔한 경우)는 CLR 이벤트 데이터에서 **`AllocSmall`** 이라는 이유(reason)로 기록된다. PerfView의 GCStats 뷰나 `dotnet-trace` 결과에서 GC 원인 열을 보면 대부분 이 값이다. LOH 할당이 트리거한 것은 `AllocLarge`로 구분된다. 66.7절에서 다시 본다.

> **⚠️ 느린 경로는 GC를 부르지 않아도 이미 비싸다**
>
> 위 흐름도에서 GC 트리거는 마지막 카드다. 그 전에 이미 프리 리스트 순회, 빈 구멍 크기 판정, 페이지 커밋(= 시스템 호출), 새 컨텍스트의 0 채우기가 벌어진다. **GC가 한 번도 안 돌았는데 할당 지연이 튀는 현상**의 정체가 대개 이것이다. "GC 시간이 0%인데 왜 P99가 나쁜가"라는 질문의 답이기도 하다.

> **💡 파이널라이저 하나가 할당 경로를 통째로 바꾼다**
>
> 결정 트리의 첫 번째 분기를 다시 보라. **파이널라이저가 있으면 크기와 무관하게 느린 범용 헬퍼로 간다.** 여기에 34.2절의 파이널라이제이션 큐 등록 비용이 더해진다. `~MyClass()`를 습관적으로 붙이는 코드베이스는 자기도 모르게 빠른 할당 경로를 포기하고 있는 셈이다. 정리가 목적이라면 파이널라이저가 아니라 `IDisposable`(33장)과 `SafeHandle`(33.7절)이 답이다.

## 63.4 LOH·POH 할당 경로

### UOH — 두 힙이 코드를 공유한다

놀랍게도 CLR은 **LOH 할당과 POH 할당의 코드를 대부분 공유한다.** .NET 소스에서 이름에 `uoh`가 붙은 함수와 변수를 자주 만나게 되는데, **UOH는 User Old Heap**의 약자다. LOH와 POH에 할당되는 객체는 **사용자 코드가 직접 할당하며 오래된 세대 2의 일부로 식별된다**는 사실에서 나온 이름이다.

할당 위치를 지정하는 `GC_ALLOC_FLAGS` 플래그 정의가 둘의 유사성을 그대로 보여 준다.

```text
    GC_ALLOC_LARGE_OBJECT_HEAP  = 32,
    GC_ALLOC_PINNED_OBJECT_HEAP = 64,
    GC_ALLOC_USER_OLD_HEAP      = GC_ALLOC_LARGE_OBJECT_HEAP | GC_ALLOC_PINNED_OBJECT_HEAP,
```

차이는 두 가지뿐이다.

| 항목 | LOH | POH |
|---|---|---|
| 객체 이동(압축) | 기본은 안 하지만 **가능** | **불가능**. 고정이 전제다 |
| 할당 시 정렬 | **정렬 필요** | 정렬 불필요 |
| 임계값 초과 배열 | 85,000바이트 이상이면 여기로 | **고정 배열은 크기와 무관하게 POH로** |

마지막 줄이 자주 오해되는 지점이다. **고정 배열은 LOH 임계값보다 커도 LOH가 아니라 POH에 간다.**

### 빠른 경로가 아예 없다

UOH 할당에는 **빠른 경로가 없다.** 할당 컨텍스트 기반 최적화도 없다. 함수들 사이로 할당 컨텍스트가 전달되긴 하지만, 그건 객체가 놓일 주소를 추적하는 용도일 뿐이다.

이유는 계산해 보면 자명하다. LOH의 최소 크기 85,000바이트는 **일반적인 할당 컨텍스트 크기(8 kB)보다 열 배 이상 크다.** 그렇게 큰 덩어리를 0으로 채우는 비용 앞에서 컨텍스트 최적화의 이득은 무의미해진다. POH는 조금 덜 자명하지만, 고정 버퍼도 대개 컨텍스트 최적화를 논할 필요 없을 만큼 크다(게다가 LOH와 코드를 공유하는 이점도 있다).

그래서 UOH 할당자는 **항상 같은 경로**를 탄다. SOH의 느린 경로와 매우 비슷하다.

1. **기존의 미사용 공간을 써 본다** (`uoh_try_fit`).
   - **LOH 또는 POH를 담은 각 세그먼트에 대해** 프리 리스트에서 맞는 빈 구멍을 찾는다.
   - 이미 커밋된 메모리 안에 충분한 공간이 있는지 본다.
   - 예약된 메모리에서 페이지를 더 커밋해 본다.
2. 전부 실패하면 **가비지 컬렉션이 트리거된다.** 조건에 따라 여러 번 호출될 수 있다.
3. 그래도 실패하면 **`OutOfMemoryException`** 이다. 심각한 상황이다.

UOH 코드는 `gc_heap::allocate_uoh` 메서드에 있고, 상태 기계는 SOH보다 **더 복잡하다.**

### 0으로 채우는 비용이 지배한다

할당 컨텍스트를 쓰지 않더라도 할당자는 여전히 **객체가 깨끗한 상태로 태어나도록 보장해야 한다.** 즉 메모리는 0으로 채워져야 한다. 그리고 큰 객체에서는 이 비용이 상당하다.

61.4절의 메모리 접근 지연 시간 표를 기억한다면 계산이 된다. **수 메가바이트짜리 객체를 0으로 채우는 데 수십 밀리초가 걸릴 수 있다.** 애플리케이션 입장에서 이건 아주 긴 시간이다.

> **⚠️ `new byte[100_000_000]` 한 줄이 수십 밀리초를 먹는다**
>
> LOH 할당은 GC를 트리거하지 않아도 이미 비싸다. 100 MB 배열 하나를 만드는 비용의 대부분은 **할당자를 찾는 시간이 아니라 100 MB를 0으로 쓰는 시간**이다. 대용량 버퍼를 요청마다 새로 만드는 코드는 GC 통계상 아무 문제가 없어 보이면서도 지연 시간을 망가뜨린다. 이것이 규칙 15의 근거다.
>
> 0 채우기를 건너뛰고 싶다면 `GC.AllocateUninitializedArray<T>(length)`가 있다. 다만 **내용이 이전 데이터라는 뜻이므로**, 전 영역을 즉시 덮어쓸 것이 확실한 경우에만 쓴다.

> **📌 LOH 할당자는 계속 개선되어 왔다**
>
> .NET GC는 지속적으로 개선되고 있으며, 종종 새 런타임 버전이 중요한 개선을 들여온다. 예를 들어 **.NET 4.5(그리고 .NET Core 1.0)부터 LOH 할당자는 앞서 설명한 버킷 방식의 프리 리스트를 훨씬 잘 활용하도록 크게 개선되었다.** "LOH는 무조건 끝에만 붙는다"는 오래된 통념은 이제 사실이 아니다.

### 만들 수 있는 가장 큰 객체

.NET이 만들 수 있는 최대 객체 크기는 처음부터 **2 GB**였다. 흔한 요구는 아니지만 그보다 큰 배열이 필요한 시나리오가 존재한다. .NET Framework 4.5부터 `gcAllowVeryLargeObjects` 설정이 추가되어, 64비트 부호 있는 `long` 범위(에서 아주 작은 값을 뺀 만큼)에 들어가는 크기의 객체를 만들 수 있게 되었다.

```xml
<configuration>
  <runtime>
    <gcAllowVeryLargeObjects enabled="true" />
  </runtime>
</configuration>
```

2 GB 제한이 풀린다고 해서 **다른 제한까지 풀리는 것은 아니다.**

| 제한 항목 | 값 |
|---|---|
| 배열의 최대 요소 개수 | **2,147,483,591** (= `0x7FFFFFC7`) |
| 단일 차원의 최대 인덱스 — `byte[]`와 1바이트 구조체 배열 | **2,147,483,591** (0x7FFFFFC7) |
| 단일 차원의 최대 인덱스 — 그 외 타입 | **2,146,435,071** (0x7FEFFFFF) |
| 문자열과 배열이 아닌 객체의 최대 크기 | **변경되지 않는다** |

이런 거대 객체는 두말할 것 없이 LOH 세그먼트 중 하나에 만들어지며, 그만한 크기가 남아 있는 세그먼트가 있을 리 없으므로 **십중팔구 새 세그먼트가 통째로 만들어진다.** 그리고 앞서 말한 대로, 그런 객체 하나를 할당하는 데 메모리 접근 지연 때문에 **몇 초**가 걸릴 수 있다.

> **⚠️ `gcAllowVeryLargeObjects`는 .NET Framework의 `app.config` 설정이다**
>
> 위 XML은 **.NET Framework 구성 파일 문법**이다. .NET(Core 계열)에서는 `runtimeconfig.json`이나 `csproj` 속성으로 런타임 구성을 준다. 그리고 최신 .NET에서는 이 스위치가 별도로 필요하지 않은 경우가 대부분이다 — 여전히 **배열 요소 개수 상한은 그대로 남아 있으므로**, 20억 개 넘는 요소를 담고 싶다면 배열 하나가 아니라 청크로 쪼갠 자료 구조(또는 `Memory<T>` 조각)를 써야 한다.

### POH 할당 API

**POH에는 배열만 할당할 수 있다** (※.NET 5부터). 방법은 `GC` 클래스의 두 메서드뿐이고, `pinned` 인자를 `true`로 주는 것이다.

```csharp
using System;

// 0으로 초기화된 고정 배열
byte[] pinnedBuffer = GC.AllocateArray<byte>(length: 4096, pinned: true);

// 0 채우기를 건너뛴 고정 배열 — 내용은 쓰레기다
byte[] fastBuffer = GC.AllocateUninitializedArray<byte>(length: 4096, pinned: true);

Console.WriteLine(GC.GetGeneration(pinnedBuffer));  // 2 (POH는 논리적으로 gen2)
```

요소 타입에는 제약이 있었다. **참조 타입 필드를 하나도 갖지 않은 값 타입**만 가능했다 — `bool`, 숫자 타입, 값 타입 필드만 가진 구조체 등이다.

> **⚠️ 조건 위반은 컴파일 오류가 아니라 런타임 예외다 — 그리고 .NET 8에서 조건이 사라졌다**
>
> 위 조건을 만족하지 않는 타입의 배열을 고정 할당하려 하면 **컴파일은 멀쩡히 되고, 런타임에 `ArgumentException`이 던져진다.** 제네릭 코드에서 이 API를 호출하면 특정 타입 인자에서만 터지는 형태로 나타나므로 찾기 까다롭다.
>
> **※.NET 8에서 이 제약은 제거되었다.** 따라서 대상 프레임워크를 낮추거나 멀티 타깃 라이브러리를 쓸 때는 여전히 조건을 지켜야 한다. "내 개발 머신에서는 되는데 배포 대상에서는 터진다"의 전형적인 사례다.

> **💡 POH의 존재 이유를 할당 관점에서 다시 보기**
>
> 62.5절에서 POH는 "고정 객체를 한군데로 몰아 SOH 단편화를 막는다"고 했다. 할당 관점에서 보면 이득이 하나 더 있다. POH의 프리 리스트는 **첫 버킷 256 B에 버킷 19개**로, 네 영역 중 가장 촘촘하다. 크기가 제각각인 고정 버퍼들이 반복적으로 나고 죽어도 구멍 재사용률이 높게 유지되도록 설계된 것이다. 반대로 말하면, POH에 **매번 다른 크기의** 버퍼를 던지면 그 촘촘한 버킷 구조도 못 버틴다. 고정 버퍼는 **크기를 규격화해서** 쓰는 것이 정답이다.

## 63.5 힙 밸런싱 (서버 GC)

### 힙은 어떻게 코어에 배정되는가

62.6절에서 본 대로, 서버 모드의 GC는 **관리 힙을 여러 개** 관리한다. 기본값은 런타임이 쓸 수 있는 논리 프로세서 수만큼이다. 힙이 여러 개라는 것은 ephemeral 세그먼트도 여러 개, LOH 세그먼트도 여러 개라는 뜻이다. 그리고 애플리케이션에는 관리 스레드도 여러 개 있다. 이 둘은 어떤 관계인가?

먼저 답해야 할 질문은 **힙이 논리 프로세서에 어떻게 배정되는가**다. CLR의 목표는 관리 힙을 특정 논리 CPU(코어)에 접근 시간 기준으로 최대한 "가깝게" 두고, 그들 사이의 동기화 오버헤드를 없애는 것이다. 그래서 다음 설계 결정이 내려졌다.

| 상황 | 배정 방식 |
|---|---|
| OS가 "현재 스레드를 어느 코어가 실행 중인지" 알려주는 경우 (Windows와 대부분의 Linux·macOS) | 각 논리 CPU에 **차례대로** 관리 힙을 배정하고, 이 배정은 **절대 바뀌지 않는다** |
| OS가 그런 정보를 주지 않는 경우 | **마이크로 벤치마크를 실행**해서 특정 코어에 어느 힙의 접근 시간이 가장 좋은지 경험적으로 조사한다 |
| 머신이 **NUMA 그룹**을 쓰는 경우 | 힙 배정은 **단일 그룹 안에서** 유지된다 |

첫 번째 방식이 CPU 캐시 효율을 최대화한다. 지역성이 올라가고 캐시 일관성 프로토콜 오버헤드가 사라진다(61.4절, 61.7절).

> **📌 마이크로 벤치마크는 어디에 있나**
>
> `heap_select::access_time` 정적 함수에서 시작하면 이 벤치마크가 어떻게 수행되는지 볼 수 있다.

관리 스레드가 할당을 시작하면 **그 스레드가 실행 중인 프로세서에 배정된 힙**이 스레드에 배정된다.

```text
     CPU #1                              CPU #2
  ┌──────────┐                        ┌──────────┐
  │  T1  T2  │                        │    T3    │
  └────┬─────┘                        └────┬─────┘
       │ 할당                              │ 할당
       ▼                                   ▼
  ┌─────────────────────────┐        ┌─────────────────────────┐
  │  SOH1                   │        │  SOH2                   │
  │  ▓T1컨텍스트 ▓T2컨텍스트 │        │  ▓T3컨텍스트            │
  ├─────────────────────────┤        ├─────────────────────────┤
  │  LOH1 (컨텍스트 없음)    │        │  LOH2 (컨텍스트 없음)    │
  └─────────────────────────┘        └─────────────────────────┘
```

세그먼트는 두 CPU 사이에 **공유되지 않는다.** 물론 메모리 자체에 CPU별 물리적 칸막이가 있는 것은 아니다. OS나 하드웨어의 지원도 없다. 하지만 세그먼트라는 개념으로 주소 공간을 격리해 두면, 각 CPU가 자기 세그먼트만 자주·배타적으로 만지게 되므로 **캐시 활용이 좋아진다.** LOH에는 할당 컨텍스트가 쓰이지 않으므로 그림에도 나오지 않는다.

> **⚠️ 힙 개수를 코어 수보다 적게 설정하면 코어끼리 힙을 공유한다**
>
> 어떤 이유로든 GC 힙 개수를 논리 프로세서 수보다 적게 구성하면(65.5절의 `GCHeapCount`), 코어들이 힙을 공유하게 된다. 위 설계가 노린 격리가 그만큼 깨진다. 컨테이너에서 CPU 할당량을 소수점으로 준 경우에도 비슷한 상황이 벌어진다.

### 불균형은 어떻게 생기고 왜 나쁜가

스레드가 만들어질 때 어느 논리 프로세서에서 실행할지는 **운영체제가 결정한다.** 모든 관리 스레드가 비슷한 양을 할당한다면 문제가 없다. 그런데 한두 스레드가 나머지보다 **훨씬 많이** 할당하기 시작하면 힙이 불균형해진다.

```text
   불균형 상태
  ┌─────────────────────────┐        ┌─────────────────────────┐
  │  SOH1                   │        │  SOH2                   │
  │  ▒▒▒░░░░░░░░░░░░░░░░░░░ │        │  ▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒░ │
  │  T1, T2 — 조금 할당      │        │  T3, T4 — 폭발적으로 할당 │
  └─────────────────────────┘        └─────────────────────────┘
                                       ▲ 곧 자리가 없다
```

이 상황이 나쁜 이유는 셋이다.

1. **두 번째 SOH에 곧 메모리 부족이 온다.** GC가 트리거되고, 결국 새 SOH 세그먼트를 만들어야 한다.
2. **CPU 캐시 활용이 불균형해진다.**
3. **SOH1을 수집하는 스레드가 할 일이 더 많아진다.** (원문의 서술 그대로다 — 수집 작업량 자체가 힙마다 달라져 GC 스레드 간 부하가 어긋난다.)

### 재배치, 그리고 OS에 스레드 이동을 요청한다

GC는 **느린 경로로 할당할 때** 힙 밸런스 검사를 수행한다. 불균형을 발견하면 **가장 많이 할당하는 스레드의 힙을 재배정한다.** 그 스레드의 할당 컨텍스트가 다른 힙으로 옮겨진다는 뜻이다.

그런데 이러면 앞서 세운 설계 원칙이 깨진다. 한 논리 코어에서 도는 스레드가 다른 코어에 배정된 힙을 쓰게 되기 때문이다. 그래서 GC는 **즉시 운영체제에 그 스레드의 실행을 해당 논리 CPU로 옮겨 달라고 요청한다.**

```text
   밸런싱 후
  ┌─────────────────────────┐        ┌─────────────────────────┐
  │  SOH1                   │        │  SOH2                   │
  │  ▒▒▒▒▒▒▒▒▒▒░░░░░░░░░░░░ │        │  ▒▒▒▒▒▒▒▒▒▒▒▒░░░░░░░░░░ │
  │  T1, T2, T4              │        │  T3                     │
  └─────────────────────────┘        └─────────────────────────┘
      ▲ T4가 이쪽 힙으로 옮겨 왔고,
        OS에 T4를 CPU #1로 옮겨 달라고 요청했다
```

> **⚠️ 스레드 재배치는 현재 Windows에서만 동작한다**
>
> 이 동작은 `SetThreadIdealProcessorEx` 함수 호출로 구현되어 있으며, **현재 Windows에서만 지원된다.** 다른 운영체제는 동등한 API를 제공하지 않는 경우가 있기 때문이다. 즉 **Linux 서버에서는 힙 재배정은 일어나되 스레드는 원래 코어에 남는다.** 같은 애플리케이션·같은 서버 GC 설정이라도 Windows와 Linux의 캐시 지역성 특성이 달라질 수 있다는 뜻이다. 두 플랫폼의 벤치마크가 미묘하게 다르게 나오는 원인 중 하나다.

> **📌 LOH도 밸런싱된다 ※.NET Framework 4.5+**
>
> **.NET 4.5부터 LOH 힙도 밸런싱된다.** 이것이 할당 성능에 상당한 개선을 가져왔다. 기법은 SOH와 동일하다.

> **💡 힙 밸런싱은 워크스테이션 GC에는 없는 개념이다**
>
> 힙이 하나뿐이니 균형을 맞출 대상이 없다. 그래서 "서버 GC로 바꿨더니 특정 스레드의 할당 지연이 튀는 패턴이 생겼다"는 현상은 워크스테이션 GC에서는 재현되지 않는다. 재배치는 **느린 경로에서만** 검사되므로, 빠른 경로만 타는 구간에서는 불균형이 방치된다는 점도 기억해 둘 만하다. 모드 선택 자체는 65.1절에서 다룬다.

## 63.6 할당 예산(allocation budget)과 GC 트리거

### 할당자와 GC를 잇는 숫자 하나

앞 절들에서 "느린 경로에서 GC가 트리거된다"고 여러 번 말했다. 그런데 GC는 **자리가 없어야만** 도는 것이 아니다. 실제로는 그보다 훨씬 자주, **예산이 소진되면** 돈다.

GC는 각 세대(LOH·POH 포함)에 대해 동적 데이터를 유지하는데, 할당 관점에서 중요한 것은 두 개다.

| 속성 | 의미 |
|---|---|
| **할당 예산(allocation budget)** — "desired allocation"이라고도 부른다 | 그 세대의 **다음 GC까지 허용할 총 할당량** |
| **남은 예산(remaining budget)** — 내부 필드명 `new_allocation` | 다음 GC까지 남은 공간. **할당 컨텍스트가 하나 잡힐 때마다 차감된다** |

핵심 문장은 이것이다. **남은 예산이 음수가 되면 할당 예산이 초과된 것이고, 그 세대에 대한 가비지 컬렉션이 트리거된다.**

여기서 놓치기 쉬운 디테일이 있다. **차감은 객체 하나를 만들 때마다가 아니라, 할당 컨텍스트가 하나 잡힐 때마다 일어난다.** 즉 빠른 경로에서 포인터를 미는 동안에는 예산 계산이 전혀 일어나지 않는다. 예산 회계는 느린 경로에서만 갱신된다. 이것이 할당이 그렇게 싼 이유의 나머지 절반이다.

```text
   [빠른 경로]  alloc_ptr 밀기 · 밀기 · 밀기 ... 예산 회계 없음
        │
        ▼ 컨텍스트 소진
   [느린 경로]  새 컨텍스트 확보(퀀텀 ≈ 8 kB)
        │        remaining_budget -= 확보한 크기
        ▼
   remaining_budget < 0 ?  ── 예 ──▶  GC 트리거 (reason = AllocSmall)
        │
       아니오 → 계속
```

> **⚠️ 사용자 코드는 gen0에만 할당하는데 왜 gen1·gen2에도 예산이 있나**
>
> 예산은 **모든 세대에 대해** 추적된다. 이유는 63.2절에서 본 것과 같다. **세대 간 승격은 오래된 세대에서의 "할당"으로 간주된다.** GC는 내부 할당자로 승격 객체가 놓일 자리를 찾고, 그 할당도 해당 세대의 예산을 소비한다. 그래서 "gen2 GC가 왜 지금 도는가"를 설명할 때, 사용자 코드의 큰 객체 할당뿐 아니라 **승격량**도 같이 봐야 한다.

### 예산의 하한과 상한 — 실측값

예산의 최소·최대값은 런타임 시작 시 정해지는 **정적 데이터**에 들어 있다. 이 값들은 GC 지연 시간 모드 구성에 따라 조정되며(65.4절), 현재는 두 모드가 있다.

| 지연 시간 모드 | 성격 |
|---|---|
| **Balanced** | 일시 중지가 더 예측 가능하고 더 잦다. 지연 시간과 메모리 사용량의 **균형**에 최적화. **기본값** |
| **Memory footprint** | 메모리 사용량 최소화에 최적화. 일시 중지가 **길고 더 잦을 수 있다** |

Balanced 모드에서 L3 캐시 16 MB인 머신을 가정할 때의 값이다.

| 항목 | 값 | 근거 |
|---|---|---|
| **세대 0 최소 할당 예산** | **8 MB (워크스테이션) / 10 MB (서버)** | **CPU 캐시 크기에 의존한다.** 칩마다 다르게 계산된다 |
| **세대 0 최대 할당 예산** | **8~200 MB** | 워크스테이션+동시 GC는 8 MB. 서버 GC와 워크스테이션+비동시는 **ephemeral 세그먼트 크기의 절반**, 단 6 MB 이상 200 MB 이하 |
| **세대 1 최대 할당 예산** | ephemeral 세그먼트 크기 의존 | 워크스테이션+동시는 6 MB. 그 외는 세그먼트 절반, 6 MB 이상 |
| **세대 2 / LOH 최대 예산** | `SSIZE_T_MAX` (워드 크기의 절반) | 사실상 **무제한** |
| **LOH·POH 최소 예산** | **3 MB** | 둘의 정적 데이터 행이 같다 |

이 숫자들에는 이유가 있다.

- **세대 0의 최소 예산이 CPU 캐시 크기에 연동된 것**은 61.4절을 읽었다면 당연하게 들려야 한다. 가장 많은 트래픽을 받는 세대 0이 **CPU 캐시의 합리적인 몫을 차지하도록** 보장하는 설정이다.
- **ephemeral 세대(0, 1)의 최대 예산이 ephemeral 세그먼트 크기에 연동된 것**도 62.6절의 물리 구성을 보면 자명하다. 세그먼트가 작은 워크스테이션과 32비트 서버 모드에서 특히 중요하다.
- **세대 2와 LOH의 최대 예산이 논리적으로 무제한인 것**은 오래 사는 객체가 전부 거기 모이기 때문이다. 물론 실제로는 RAM·페이지 파일·주소 공간이 물리적 상한을 건다.

> **📌 예산 상한을 직접 만질 수 있다**
>
> `GCGen0MaxBudget`과 `GCGen1MaxBudget` 구성 설정으로 세대 0·1의 최대 예산을 지정할 수 있다. 다만 이 값들은 **깊이 숨겨진 구현 세부 사항**이며 이후 프레임워크 버전에서 바뀌지 않는다는 보장이 전혀 없다. 실측 없이 손대는 것은 거의 항상 손해다.

### 예산은 생존율에 따라 매번 다시 계산된다

할당 예산은 고정값이 아니다. **그 세대를 수집하는 GC마다 동적으로 바뀐다.** 새 값은 대부분 **그 세대의 생존율(survival rate)** 에 기반한다. 생존율은 살아남은 객체의 크기를 전체 객체 크기로 나눈 값이다.

- **생존율이 높으면**(많이 살아남았으면) 예산을 **더 공격적으로 늘린다.** 다음 GC까지의 시간을 미뤄서, 그때는 죽은 객체 대 산 객체 비율이 더 낫기를 기대하는 것이다. 어떤 임계 비율을 넘으면 새 예산은 **항상 최대 예산**이 된다.
- **생존율이 충분히 낮으면** 예산은 **최소 예산 근처**로 설정될 수 있다.

계산된 값은 때때로 선형 모델로 한 번 더 보정된다. 경계 생존율 구간에서는 현재 예산과 이전 예산을 비례적으로 섞는다.

```text
  새 예산
   max ┤                        ┌──────────────────
       │                       /
       │                      /   ← 기울기와 임계점은 정적 데이터의
       │                     /       limit / max_limit 값이 결정한다
       │                    /
   min ┤────────────────────
       └────────────────────────────────────────▶ 생존율
       0                                        1
```

어린 세대일수록 생존율에 **훨씬 민감하게** 반응한다. 특히 세대 0은 반응이 아주 예민해서, 새 예산이 **최소 아니면 최대**라는 경계값으로 튀는 경우를 자주 본다.

> **⚠️ 그래서 "GC 횟수"만 보고 판단하면 안 된다**
>
> 세대 0 GC 횟수가 줄었다고 좋아할 일이 아니다. 생존율이 올라가서 예산이 최대로 튄 결과일 수 있다. 그 경우 GC는 덜 돌지만 **한 번의 GC가 훨씬 오래 걸리고**, 승격량이 늘어 세대 1·2 압력이 커진다. 항상 **할당률(allocation rate) · GC 횟수 · 승격량 · 일시 중지 시간**을 함께 본다. 66장의 GCStats가 이 네 숫자를 한 화면에 보여 준다.

### 예산을 실제로 관측하기

`dotnet-counters`가 예산을 직접 보여 준다.

```text
$ dotnet-counters monitor -p 1234

[System.Runtime]
    % Time in GC since last GC (%)                                       0
    Allocation Rate (B / 1 sec)                                    122,824
    GC Committed Bytes (MB)                                         44.876
    GC Fragmentation (%)                                             1.396
    GC Heap Size (MB)                                               37.409
    Gen 0 GC Budget (MB)                                                16
    Gen 0 GC Count (Count / 1 sec)                                       0
    Gen 0 Size (B)                                                       0
    Gen 1 Size (B)                                               2,526,584
    Gen 2 Size (B)                                              24,857,672
```

`Gen 0 GC Budget (MB)`가 바로 현재 세대 0 할당 예산이다. `Allocation Rate (B / 1 sec)`와 함께 보면 **다음 세대 0 GC까지 대략 몇 초 남았는지**를 손으로 계산할 수 있다. 위 화면이라면 16 MB ÷ 약 123 kB/s ≈ 130초다.

Windows 성능 모니터에서는 카운터 이름이 헷갈린다.

```text
\.NET CLR Memory(<프로세스명>)\Gen 0 heap size
```

> **⚠️ `Gen 0 heap size`는 세대 0의 크기가 아니다**
>
> 레거시 사정 때문에 이 카운터는 진짜 세대 0 크기가 아니라 **할당 예산**을 보여 준다. 세대 크기를 합산하려고 이 값을 더하면 결과가 크게 틀어진다. 62.2절에서도 같은 경고를 했다. `dotnet-counters`의 `Gen 0 Size (B)`도 같은 이유로 0으로 찍히는 경우가 흔하다.
>
> 실제 부하 테스트에서 이 카운터를 관찰하면 **4,194,300과 6,291,456바이트 사이를 계속 오가는** 모습을 볼 수 있다. 세대 0이 커졌다 작아졌다 하는 것이 아니라 **예산이 생존율에 따라 재계산되고 있는 것**이다. 이 값이 시간에 따라 **계속 커지기만 한다면** 그건 봐야 할 신호다.

> **💡 예산을 코드에서 직접 세는 법**
>
> 애플리케이션 안에서 할당률을 추적하고 싶다면 가장 단순한 해법이 `GC.GetAllocatedBytesForCurrentThread()` 정적 메서드다. 현재 스레드가 살아 있는 동안 할당한 바이트 수를 **정확히** 알려 준다. 요청 처리 전후로 한 번씩 호출해 차이를 로그로 남기면, 프로파일러 없이도 "어떤 요청이 할당 폭탄인가"를 실서비스에서 잡아낼 수 있다. 오버헤드가 매우 낮아 상시 켜 둘 수 있다는 점이 프로파일러와의 결정적 차이다.
>
> ```csharp
> long before = GC.GetAllocatedBytesForCurrentThread();
> await HandleRequestAsync(context);
> long allocated = GC.GetAllocatedBytesForCurrentThread() - before;
> if (allocated > 1_000_000)
>     _logger.LogWarning("요청 {Path}가 {Bytes:N0}바이트를 할당했다", context.Request.Path, allocated);
> ```
>
> `async` 메서드에서는 이어 실행 스레드가 바뀔 수 있으므로 값이 음수가 되거나 무의미해질 수 있다. 스레드가 바뀌지 않는 동기 구간에서 쓰는 것이 정확하다. 전체 프로세스 기준이 필요하면 `GC.GetTotalAllocatedBytes(precise: true)`를 쓴다.

## 63.7 스택 할당과 `stackalloc`

### 스택은 원래 더 빠르다

지금까지는 GC 관리 힙 위의 할당만 다뤘다. 압도적으로 흔한 방식이고, 이를 빠르게 만들기 위해 얼마나 큰 노력이 들어갔는지도 봤다. 그런데 **스택 할당과 해제는 기본적으로 그보다도 빠르다.** 스택 포인터를 움직이는 것이 전부이고, **GC에는 아무 부담도 주지 않는다.**

값 타입은 상황에 따라 스택에 놓인다. 그리고 어떤 조건에서는 **명시적으로 스택 할당을 요청**할 수도 있다. 규칙 14("핫 패스에서 힙 할당을 피하라")를 생각하면 아주 유용한 선택지다.

C#에서 명시적 스택 할당은 `stackalloc` 연산자다. 요청한 크기의 메모리 영역을 가리키는 **포인터**를 돌려준다. 포인터 타입이므로 `unsafe` 문맥이 필요하다 — `Span<T>`를 쓰지 않는다면.

```csharp
static unsafe void Test(int t)
{
   SomeStruct* array = stackalloc SomeStruct[20];
   // ...
}
```

> **⚠️ `stackalloc`이 준 메모리는 0으로 채워져 있지 않다**
>
> 새로 할당된 메모리의 내용은 **정의되지 않았다.** 0이라고 가정하면 안 된다. 힙 할당에 익숙한 사람이 가장 자주 밟는 지뢰다. `Span<T>`로 받았다면 `span.Clear()`를 호출하거나, 쓰기 전에 읽지 않도록 코드를 짜야 한다.
>
> 예외적으로 컴파일러가 `.locals init` 플래그를 켜 두면 0으로 채워지지만, `[SkipLocalsInit]`(69.8절)을 적용하면 그 보장이 사라진다. **명세에 기대라, 관측된 동작에 기대지 마라.**

### `localloc`으로 번역된다

`stackalloc`은 CIL 명령 `localloc`으로 번역된다.

```il
ldc.i4.s 20
conv.u
sizeof SomeStruct
mul.ovf.un
localloc
```

ECMA 표준의 설명은 이렇다. `localloc`은 "**지역 동적 메모리 풀(local dynamic memory pool)** 로부터 size 바이트를 할당한다. 현재 메서드가 반환하면 지역 메모리 풀은 재사용 가능해진다."

**스택이라는 말이 한마디도 없다는 점**에 주목하라. ECMA 표준은 기술 중립적이려고 애쓰며 스택이나 힙 같은 개념을 피한다. CIL이 보장하는 것은 **메모리 블록 하나**뿐이다.

> **📌 JIT은 `localloc`을 어떻게 번역하는가**
>
> JIT은 `localloc`을 일련의 `push`와 `sub rsp, [size]` 명령으로 옮겨 스택 프레임을 그만큼 키운다. 이 증가량은 32비트에서 8바이트, **64비트에서 16바이트 단위로 반올림된다.** 따라서 `int` 두 개(8바이트)를 `stackalloc`해도 x64에서는 스택 프레임이 16바이트 늘어난다. x64 ABI가 스택을 16바이트 경계에 정렬하도록 요구하기 때문이다.

### 무엇을 스택에 올릴 수 있는가

ECMA 표준은 `localloc`에 대해 "지정한 바이트 수의 블록"만 약속한다. 그래서 CLR은 현재 그 블록을 **단순 데이터 타입의 컨테이너 이상으로는 쓰지 못한다.** C# 언어 명세의 `stackalloc` 정의가 제약을 구체적으로 말한다. **`unmanaged_type`의 배열만** 가능하며, `unmanaged_type`은 다음 중 하나다.

- 기본 타입: `sbyte`, `byte`, `short`, `ushort`, `int`, `uint`, `long`, `ulong`, `char`, `float`, `double`, `decimal`, `bool`
- 모든 열거형 타입
- 모든 포인터 타입
- **구성된 타입(constructed type, 즉 타입 인자를 포함한 제네릭 타입)이 아니면서** 필드가 전부 `unmanaged_type`인 사용자 정의 구조체

> **⚠️ 참조 필드가 하나만 있어도 `stackalloc` 대상이 될 수 없다**
>
> `struct Point { public double X, Y; }`는 되지만, `struct Item { public string Name; public int Id; }`는 안 된다. `string` 필드 하나가 전체를 실격시킨다. 스택 메모리에는 GC가 추적할 수 있는 참조를 둘 수 없기 때문이다. 컴파일 오류로 잡히므로 사고는 안 나지만, 리팩터링 중에 구조체에 참조 필드를 하나 추가했다가 `stackalloc` 코드가 전부 깨지는 일은 흔하다.

### 두 가지 이득

1. **해제가 스택 포인터 이동만큼 빠르다.** 힙 할당 헬퍼도, 느린 경로도, GC도 전혀 개입하지 않는다.
2. **주소가 암묵적으로 고정(pinned)된다.** 스택 프레임은 절대 이동하지 않기 때문이다. 따라서 **고정 오버헤드 없이** 비관리 코드에 포인터를 넘길 수 있다. 다만 **함수가 반환한 뒤에 비관리 코드가 그 메모리를 쓰지 않도록** 보장해야 한다.

이 두 번째 성질은 60장의 상호 운용과 62.5절의 POH를 함께 읽으면 의미가 커진다. 짧은 P/Invoke 호출용 버퍼라면 POH도 `GCHandle` 고정도 필요 없다.

### `Span<T>`와 결합하면 `unsafe`가 사라진다

`stackalloc`이 C# 세계에서 희귀한 존재였던 이유는 단순하다. 많은 개발자가 이 기능을 모르거나, **포인터를 받는 API가 없어서** 어떻게 써야 할지 몰랐기 때문이다. `Span<T>`가 이 상황을 바꿨다(68장).

```csharp
static void Test(int t)
{
   Span<SomeStruct> array = stackalloc SomeStruct[20];
   // ...
}
```

**C# 7.2 / .NET Core 2.1 이후**로 `unsafe` 없이 안전하게 쓸 수 있다. 인덱스 범위 검사도 붙는다.

### 실측 — LINQ 대신 `stackalloc`

리스트를 받아 임시 리스트로 변환하고 통계를 내는 전형적인 메서드다. LINQ 기반 코드는 임시 객체를 잔뜩 만든다.

```csharp
public double ProcessEnumerable(List<BigData> list)
{
   double avg = ProcessData1(list.Select(x => new DataClass()
      { Age = x.Age, Sex = Helper(x.Description) ? Sex.Female : Sex.Male }));
   _logger.Debug("Result: {0}", avg / _items);
   return avg;
}
```

이것을 구조체와 `stackalloc`으로 바꾼다.

```csharp
public double ProcessStackalloc(List<BigData> list)
{
   // 위험하지만 unsafe 코드는 없다
   Span<DataStruct> data = stackalloc DataStruct[list.Count];
   for (int i = 0; i < list.Count; ++i)
   {
      data[i].Age = list[i].Age;
      data[i].Sex = Helper(list[i].Description) ? Sex.Female : Sex.Male;
   }
   return ProcessData2(data);
}

// 수정하지 않는다는 것을 명시하려고 읽기 전용 Span으로 넘긴다
public double ProcessData2(ReadOnlySpan<DataStruct> list) { /* ... */ return result; }
```

요소 100개 기준 BenchmarkDotNet 결과다.

| 메서드 | Mean | Allocated |
|---|---|---|
| ProcessEnumerable | 1,169.9 ns | 3,272 B |
| ProcessStackalloc | 443.2 ns | **0 B** |

**할당이 완전히 사라지고 약 4배 빨라졌다.** 핫 패스에 이런 코드가 있다면 검토할 가치가 충분하다.

### 안전 한계 — 여기서부터가 중요하다

`stackalloc`으로 할당한 메모리를 **명시적으로 해제할 방법은 없다.** 메서드가 끝나면 암묵적으로 반환된다. 그래서 스택을 격하게 쓰면 **`StackOverflowException`** 으로 끝날 수 있다.

> **⚠️ `StackOverflowException`은 잡을 수 없다**
>
> `StackOverflowException`은 **잡을 수 없는 예외** 중 하나다. `try`/`catch`로 완화할 방법 없이 **애플리케이션 프로세스 전체를 죽인다.** ASP.NET Core 서버라면 진행 중이던 모든 요청이 함께 죽는다. 힙 할당 실패(`OutOfMemoryException`)와 위험 등급 자체가 다르다. **버퍼를 너무 크게 잡는 것은 그래서 위험하다.**

특히 위험한 것은 위 예제의 `stackalloc DataStruct[list.Count]`처럼 **요소 개수를 사전에 알 수 없는** 경우다. 안전하게 하려면 개수를 검사해서 작을 때만 `stackalloc`을 쓰는 패턴을 쓴다.

```csharp
public double ProcessStackalloc(List<BigData> list)
{
   Span<DataStruct> data = list.Count < 100
       ? stackalloc DataStruct[list.Count]
       : new DataStruct[list.Count];
   // ... 위와 동일하게 채운 뒤
   return ProcessData2(data);
}
```

이 삼항 연산자 패턴이 사실상 업계 표준이다. .NET 런타임 자신의 코드가 곳곳에서 이 형태를 쓴다.

큰 데이터를 스택에 올리는 것은 **성능 관점에서도 좋지 않다.** 스레드 스택의 큰 영역을 실제로 건드리면 그 페이지들이 프로세스 작업 집합으로 끌려 들어온다(페이지 폴트 발생). 그 페이지들은 다른 스레드와 공유되지 않으므로 낭비다.

### 얼마나 커도 되는가

`StackOverflowException`이 절대 없다고 100% 확신하고 싶다면 `RuntimeHelpers.TryEnsureSufficientExecutionStack()` 또는 `RuntimeHelpers.EnsureSufficientExecutionStack()`을 쓰고 싶어질 것이다. 문서의 표현은 "남은 스택 공간이 **평균적인 .NET 함수**를 실행하기에 충분한지 보장한다"이며, 현재 값은 **32비트 64 kB, 64비트 128 kB**다.

바꿔 말하면 `TryEnsureSufficientExecutionStack()`이 `true`를 반환하면 **128 kB 미만 버퍼를 `stackalloc`해도 아마 안전하다.** "아마"라고 쓴 이유는 이 값들이 구현 세부 사항이고 보장되지 않기 때문이다. 보장되는 것은 "평균적인 .NET 함수를 위한 공간"뿐이며, 거기에 큰 `stackalloc`은 포함되지 않는다.

> **💡 실무 기준은 1 kB다**
>
> 원서의 권고를 그대로 옮긴다. **`stackalloc`은 작은 버퍼에만 쓴다 — 1 kB를 넘지 않는 것이 안전한 값이다.** 128 kB는 이론적 상한이지 실무 기준이 아니다.
>
> 판단 기준을 하나 더 준다. **크기가 컴파일 시점 상수가 아니면 반드시 상한 검사를 넣는다.** 사용자 입력이 크기를 결정하는 `stackalloc`은 그 자체로 **원격 서비스 거부 취약점**이다. 검사 없는 `stackalloc buffer[header.Length]`가 그 예다.

| 크기 | 판단 |
|---|---|
| ~1 kB, 컴파일 상수 | 안전. 마음껏 쓴다 |
| 1~16 kB, 컴파일 상수 | 호출 깊이를 알고 있고 재귀가 없다면 검토 가능 |
| 크기가 런타임 값 | **반드시 상한 분기.** 초과 시 `ArrayPool` 또는 힙 배열로 폴백 |
| 재귀 함수 안 | **쓰지 마라.** 깊이 × 버퍼 크기가 곱해진다 |
| `async` 메서드 안 | `Span<T>`는 `await`을 건널 수 없다. 애초에 컴파일되지 않는다 |
| 루프 안 | **쓰지 마라.** `localloc`은 메서드가 끝날 때까지 해제되지 않으므로 반복마다 스택이 누적된다 |

마지막 두 줄이 특히 중요하다. 루프 안의 `stackalloc`은 컴파일은 되지만 **반복 횟수만큼 스택을 먹는다.** 스택 할당 메모리는 메서드 종료 시에만 회수되기 때문이다.

## 63.8 `OutOfMemoryException`이 나는 진짜 이유

### 언제 던져지는가

할당자 결정 트리에서 봤듯이 요청한 만큼의 메모리를 확보하지 못하는 경우가 있다. 이때 벌어지는 일은 **자주 오해된다.**

`OutOfMemoryException`은 할당 경로의 **가장 마지막 결정**이다. 그 말은 다음을 의미한다.

**첫째, 가비지 컬렉터는 이미 트리거되었다.** 한 번이 아니라 여러 번, **전체 압축 GC까지 포함해서** 실행되었을 수 있다. 따라서 SOH 단편화는 문제가 아니어야 한다. 당신의 문제가 하필 그 순간에만 나타나는 간헐적이고 변덕스러운 것이어서 GC를 한 번 더 돌리면 해결될 확률은 **아주 낮다.**

> **⚠️ `OutOfMemoryException`의 원인은 "런타임이 GC 호출을 깜빡한 것"이 절대 아니다**
>
> 이 오해가 `catch (OutOfMemoryException) { GC.Collect(); }` 같은 코드를 낳는다. GC는 이미 여러 번 돌았다. 수동 트리거는 도움이 안 되며, 예외 처리기 안에서 전체 압축 GC를 돌리는 것은 **상황을 더 나쁘게** 만든다.
>
> 유일한 예외가 있다. **LOH 할당 중에 발생한 경우**라면 명시적으로 **LOH 압축**을 요청하고(65.8절의 `GCSettings.LargeObjectHeapCompactionMode`) GC를 한 번 더 돌리는 것을 고려할 만하다.

**둘째, 할당자가 주어진 크기의 메모리 영역을 준비하는 데 실패했다.** 이유는 둘 중 하나다.

| 원인 | 무슨 일인가 | 전형적 상황 |
|---|---|---|
| **가상 메모리 고갈** | 할당자가 충분히 큰 영역을 **예약(reserve)** 할 수 없다 (예: 새 세그먼트 생성) | 주로 **가상 메모리 단편화**. 특히 32비트 런타임 |
| **물리 백업 저장소 고갈** | 할당자가 충분한 메모리를 **커밋(commit)** 할 수 없다 (예: 기존 세그먼트 확장) | RAM과 페이지/스왑 파일이 모두 압박 상태 |

첫 번째의 함정이 큰데, 단편화는 메모리를 비효율적으로 쓰게 만들기 때문에 **`OutOfMemoryException`이 나는 순간에도 시스템에는 상당량의 free RAM이 보일 수 있다.** 61.2절의 32비트 주소 공간 한계를 떠올려라. **32비트 런타임은 RAM이 아무리 많은 64비트 시스템에서도 자기 몫으로 2 GB 또는 3 GB의 가상 주소 공간밖에 못 쓴다.**

두 번째도 마찬가지다. 운영체제는 **시스템의 모든 프로세스를 함께 고려해서** 메모리를 관리한다. free RAM이 조금 보이는데도 당신의 애플리케이션 전체 메모리 소비(RAM + 디스크)가 시스템을 한계로 밀어붙이고 있어서 OS가 추가 커밋을 거절하는 것은 **완벽하게 정상적인 상황**이다.

> **⚠️ "메모리가 남아 있는데 OOM이 났다"는 버그 리포트는 대개 정상 동작이다**
>
> 결론 두 개를 강조한다.
> 1. `OutOfMemoryException`을 만났을 때 **수동 GC 트리거는 도움이 되지 않는다** (대형 객체 할당 중이라면 LOH 압축은 예외).
> 2. `OutOfMemoryException` 발생 시 **free RAM이 얼마간 보이는 것은 정상이다.**

### 어떻게 고치는가

메모리 누수를 먼저 잡은 뒤(66장), 다음 중 하나 이상을 취한다.

| 대책 | 내용 |
|---|---|
| **객체를 덜 할당한다** | 메모리 사용을 조사해 불필요한 할당을 잘라 낸다. 이 장의 후반부가 통째로 이 이야기다 — 당신이 인지조차 못 하는 할당 출처가 많다 |
| **오브젝트 풀링을 쓴다** | 단편화를 줄이는 해법 중 하나가 재사용이다. 바로 쓸 수 있는 풀이 이미 있고, 직접 만들 수도 있다 |
| **VM 호딩(hoarding)을 쓴다** | 62장에서 설명한 세그먼트 재사용. 특히 32비트 런타임에서 |
| **64비트로 다시 빌드한다** | 이게 전부일 수도 있다. 충분히 큰 가상 주소 공간이 생긴다 |

> **📌 던져질 예외 객체 자신은 어떻게 할당되나**
>
> `OutOfMemoryException`도 던져지기 전에 **할당되어야 한다.** 그런데 지금은 공간이 없는 상황이다. CLR이 쓰는 마법은 단순하다. **런타임 시작 시 `OutOfMemoryException` 인스턴스를 미리 할당해 두고**, 새 예외를 할당할 수 없으면 그것을 쓴다. `StackOverflowException`과 `ExecutionEngineException`에도 같은 수법을 쓴다. 구현 세부는 `SystemDomain::CreatePreallocatedExceptions`와 `GetBestOutOfMemoryException` 함수 코드에 있다.
>
> 부작용이 하나 있다. **미리 할당된 예외 인스턴스는 재사용되므로 스택 트레이스가 신뢰할 수 없거나 비어 있을 수 있다.** OOM 로그에 스택이 없다고 당황하지 마라.

### 시나리오 — 재현되지 않는 OOM 잡기

**상황**: .NET 프로세스 하나가 운영 환경에서 간헐적으로 `OutOfMemoryException`으로 죽는다. 다른 환경에서는 재현되지 않는다. 발생 빈도가 너무 낮아 정교한 모니터링 도구를 붙여 둘 수도 없다. 전체 메모리 덤프를 떠서 분석하고 싶은데, 다음 예외가 언제 올지 예측할 수 없다.

**분석**: `OutOfMemoryException` 발생 시 **전체 메모리 덤프를 자동으로 캡처할 수 있다.** 이 방법은 Windows에서 .NET Framework와 .NET Core 모두에 동작한다.

**1단계** — `procdump`를 머신 전역으로 설치한다.

```text
procdump -i C:\Dumps -ma
```

`-i`는 사후 디버거로 설치, `-ma`는 전체 덤프를 뜻한다. 이제부터 프로세스가 감시되고 `OutOfMemoryException`이 발생하면 전체 덤프가 생긴다.

> **⚠️ 조사가 끝나면 반드시 `-u`로 제거하라**
>
> 이 설치는 **머신의 모든 크래시 프로세스**에 대해 덤프를 만든다. 잊고 두면 하드 디스크가 덤프로 가득 찬다. `procdump -u`로 제거한다.

**2단계** — WinDbg로 덤프를 열고 상단의 `!analyze -v` 링크를 클릭한다.

```text
> !analyze -v
...
STACK_TEXT:
02b7ee0c 273b25dd TestOOM!TestOOM.Program.TestOOM+0x3d
02b7ee1c 273b1992 TestOOM!TestOOM.Program.Main+0x82
...
FAULTING_SOURCE_LINE:  C:\Book\code\TestOOM\Program.cs
FAULTING_SOURCE_FILE:  C:\Book\code\TestOOM\Program.cs
FAULTING_SOURCE_LINE_NUMBER:  89
FAULTING_SOURCE_CODE:
    86:             List<byte[]> bytes = new List<byte[]>();
    87:             while (true)
    88:             {
>   89:                bytes.Add(new byte[1024 * 1024 * 1024]);
    90:             }
    91:         }
```

`STACK_TEXT`가 예외를 일으킨 스레드의 콜스택이다. 심볼(pdb)과 함께 빌드했다면 `FAULTING_SOURCE_CODE`에서 **마지막 할당이 실패한 소스 코드 줄**까지 볼 수 있다.

**3단계** — .NET Framework라면 `!analyzeoom`으로 GC 관점의 정보를 얻는다.

```text
0:000> !analyzeoom
Managed OOM occured after GC #2 (Requested to allocate 0 bytes)
Reason: Didn't have enough memory to allocate an LOH segment
Detail: LOH: Failed to reserve memory (1090519040 bytes)
```

> **⚠️ `!analyzeoom`은 .NET Core에서 동작하지 않는다**
>
> 집필 시점 기준으로 이 SOS 명령은 **.NET Framework 전용**이다. .NET(Core 계열)에서는 `!analyze -v`의 결과와 일반적인 힙 분석(`!dumpheap -stat`, `!eeheap -gc`)으로 대신해야 한다.

> **💡 예외를 던진 코드가 범인이라는 보장은 없다**
>
> `OutOfMemoryException`을 트리거한 코드가 **문제의 직접 원인이 아닐 수 있다.** 할당자가 자리를 찾지 못한 그 순간에 불운하게 걸린 스레드일 뿐일 수 있다. 메모리 압박의 진짜 출처는 다른 곳일 가능성이 높다. 따라서 덤프에서 **가장 개수가 많은 객체, 가장 큰 객체, 세대별 분포**를 반드시 함께 본다. 위 예제처럼 1 GB 배열을 무한 루프로 만드는 코드가 스택에 딱 찍히는 경우는 오히려 운이 좋은 편이다.

## 63.9 숨은 할당 카탈로그 — 델리게이트, 클로저, 박싱, `yield`, `params`, 문자열 연결·포매팅, LINQ, 열거자

### 왜 이 절이 이 장의 절반인가

여기까지 오면서 "할당은 싸다"가 조건부 참임을 확인했다. 정리하면 이렇다.

- **빠른 경로를 타는 한 싸다.** 하지만 할당 컨텍스트는 때때로, 그리고 **예측할 수 없이** 가득 찬다. 그러면 더 복잡하고 느린 경로가 돈다.
- **그 복잡한 경로는 때때로 GC를 트리거한다.**
- **LOH의 큰 객체 할당은 느리다.** 주로 0 채우기 비용 때문이다.
- **많이 할당하면 GC의 일이 늘어난다.** 임시 객체를 많이 만들수록 객체 수명에 관한 **세대 가설이 깨질 확률**이 올라간다.

그래서 .NET에서 가장 효과적인 메모리 최적화 하나는 **할당을 피하거나 최소한 의식하는 것**이다. 할당이 적으면 GC 압력이 낮고, 메모리 접근이 싸지고, OS와의 통신이 줄어든다. 성능을 의식하는 .NET 개발자가 반드시 가져야 할 지식은 **할당의 출처를 아는 것**이다.

> **⚠️ 그러나 모든 줄을 이렇게 뜯지 마라**
>
> "이른 최적화는 만악의 근원"이라는 남용되는 문장이 있다. 프로그램의 모든 줄을 할당 개수 관점에서 분석하는 것은 **불필요하다.** 1분에 한 번 실행되는 코드가 800바이트 대신 200바이트를 할당하는 게 중요한가? 대개 아니다.
>
> **가장 성능이 중요한 코드 경로의 할당부터 분석한다.** 그리고 규칙 5("GC를 일찍 측정하라")를 적용한다. 측정만이 엉뚱한 곳을 최적화하는 것을 막아 준다. 이 카탈로그의 목적은 코드 리뷰 때 **눈에 띄게 만드는 것**이지, 강박을 만드는 것이 아니다.

명시적 할당 — 당신이 `new`를 쓴 것 — 은 눈에 보인다. 문제는 **숨은 할당**이다. 특정 연산이 암묵적으로 객체를 만든다. 알지 못하면 코드에서 튀어 보이지 않는다. 지금부터 그 목록을 만든다.

> **📌 검증 도구**
>
> 아래 예제들의 "컴파일 결과"는 **dnSpy**(또는 ILSpy)로 디컴파일한 것이다. IDE 확장으로 실시간 확인도 가능하다 — Visual Studio의 **Clr Heap Allocation Analyzer**, Rider의 **Heap Allocations Viewer**가 코드를 쓰는 동안 숨은 할당에 밑줄을 그어 준다. 이 절을 읽고 나서 설치하면 그 밑줄들이 전부 읽힌다.

### 1. 델리게이트 할당

**새 델리게이트를 만들 때마다 할당이 일어난다.** 인기 있는 `Func`와 `Action`도 예외가 아니다. 메서드 그룹(이름으로 참조)에서 만들든, 람다 식에서 만들든 마찬가지다.

```csharp
// 메서드 그룹에서 — 숨은 할당
Func<double> action = ProcessWithLogging;
// 위 줄이 실제로 하는 일
Func<double> action = new Func<double>(this.ProcessWithLogging);
```

```csharp
// 람다에서 — 숨은 할당 (람다는 컴파일러 생성 메서드가 된다)
Func<double> action = () => ProcessWithLogging();
// 위 줄이 실제로 하는 일
Func<double> action = new Func<double>(this.<SomeMethod>b__31_0);
```

IL 수준에서는 `ldftn` + `newobj` 쌍으로 나타난다. `newobj`가 보이면 할당이다.

```il
ldarg.0
ldftn     instance float64 Program::ProcessWithLogging()
newobj    instance void class [System.Runtime]System.Func`1<float64>::.ctor(object, native int)
```

**회피법**: 이 할당을 없앨 방법은 없다. 대신 **재사용하거나 캐시한다.** 특히 **루프 안에서 델리게이트를 반복 생성하지 마라.** 루프 밖에서 한 번 만들어 지역 변수에 담는다.

> **📌 컴파일러가 대신 캐시해 주는 경우가 있다**
>
> 람다 식이 아무 데이터도 **캡처하지 않으면**, C# 컴파일러는 그 델리게이트 인스턴스를 **정적 필드에 캐시하는 코드를 생성한다.** 즉 최초 사용 시 한 번만 할당된다. **※.NET 8부터는 이 최적화가 메서드 그룹에도 적용된다.**
>
> 그래서 `list.Where(x => x > 0)`는 호출할 때마다 델리게이트를 만들지 않지만, `list.Where(x => x > threshold)`는 매번 만든다. 차이는 캡처 여부 하나다.

### 2. 클로저 — 디스플레이 클래스

클로저(closure)는 계산의 상태를 관리하는 메커니즘이다. 위키백과의 정의를 빌리면 "함수와, 그 함수의 비지역 변수를 위한 참조 환경을 함께 묶은 것"이다. 26.10절에서 문법 관점으로 봤고, 여기서는 **힙 관점**으로 본다.

```csharp
private IEnumerable<string> Closures(int value)
{
   var filteredList = _list.Where(x => x > value);
   var result = filteredList.Select(x => x.ToString());
   return result;
}
```

여기까지 읽었다면 델리게이트 두 개가 보일 것이다. `Where`와 `Select`가 `Func<>`를 기대하니까. 그런데 **더 중요한 할당 출처가 하나 더 있다.** 컴파일러는 위 코드를 `<>c__DisplayClass1_0`이라는 클래스를 쓰는 더 복잡한 구조로 바꾼다.

```csharp

{
   Program.<>c__DisplayClass1_0 <>c__DisplayClass1_ = new Program.<>c__DisplayClass1_0();
   <>c__DisplayClass1_.value = value;
   return this._list.Where(new Func<int, bool>(<>c__DisplayClass1_.<Closures>b__0))
```

두 가지를 짚는다.

- **클로저는 클래스로 구현된다. 따라서 할당이다.** `Closures` 메서드가 실행될 때마다 `<>c__DisplayClass1_0` 인스턴스 하나가 힙에 생긴다.
- **캡처된 지역 변수는 이 클로저 크기에 합산된다.** 위 예에서는 `int value` 하나다. **변수를 많이 캡처할수록 "클로저 클래스"가 커진다.**

또한 앞서 말한 캐시 최적화 때문에 **델리게이트는 하나만 할당된다.** `Where`에 넘긴 것만이다. `Select`에 넘긴 람다는 아무것도 캡처하지 않으므로 컴파일러가 캐시한다 — 위 코드의 `Program.<>c.<>9.<Closures>b__1_1`이 그 캐시된 인스턴스다.

무엇이 언제 캡처되는지는 미묘하다.

```csharp
Func<double> action1 = () => InstanceMethodNotUsingThis();  // 캡처 없음 (this도 아니다)
Func<double> action2 = () => InstanceMethodUsingThis();     // 캡처 없음 (여전히 this도 아니다)
Func<double> action3 = () => StaticMethod();                // 캡처 없음
Func<double> action4 = () => StaticMethodUsingLocalVariable(ss);  // ss를 캡처

// ss와 this를 함께 캡처한다 — 내부에서 this.<>4__this.ProcessSomeStruct(this.ss)를
// 호출해야 하므로. ss 인자가 없었다면 아무것도 캡처되지 않는다(this 단독 캡처는 없다)
Func<double> action6 = () => InstanceMethodUsingLocalVariable(ss);
```

> **⚠️ 캡처 규칙을 외우려 하지 마라 — 디컴파일해서 확인하라**
>
> 광범위한 컴파일러 최적화 때문에 규칙과 예외가 너무 많다. 원서의 표현을 그대로 옮기면, 무엇이 언제 캡처되는지에 대한 모든 조사는 결국 "**순수한 마법**"이라는 결론에 도달한다. 좀 더 진지하게 말하면 **현재 적용되는 최적화의 깊은 구현 세부 사항**이다. 확신이 필요하면 dnSpy로 디컴파일해서 눈으로 본다.

**회피법 1** — `static` 람다 ※C# 9로 **의도치 않은 캡처를 컴파일 오류로 만든다.**

```csharp
// 캡처하면 컴파일 오류가 난다 — 실수로 클로저가 생기는 것을 막는다
var result = _list.Where(static x => x > 0);
```

**회피법 2** — 람다를 아예 쓰지 않는다.

```csharp
private IEnumerable<string> WithoutClosures(int value)
{
   List<string> result = new List<string>();
   foreach (int x in _list)
      if (x > value) result.Add(x.ToString());
   return result;
}
```

> **⚠️ 이 "회피법"이 더 나쁠 수도 있다**
>
> 위 코드는 이제 **결과 리스트를 할당해야 한다.** 클로저 하나(수십 바이트)를 없애려고 리스트 하나와 그 내부 배열(재할당 포함)을 만든 것이다. **원본보다 비효율적일 수 있다.** 할당 최적화가 항상 "할당 개수를 세는 게임"이 아닌 이유다. 지연 평가를 유지하려면 `yield return`을 쓰는 쪽이 낫다 — 그것도 할당이지만 더 작다(아래 4번).

**지역 함수도 똑같다.** C# 7.0의 지역 함수는 람다와 비슷하며 클로저 할당을 유발할 수 있다.

```csharp
private IEnumerable<string> ClosuresWithLocalFunction(int value)
{
   bool WhereCondition(int x) => x > value;
   string SelectAction(int x) => x.ToString();
   var filteredList = _list.Where(WhereCondition);
   var result = filteredList.Select(SelectAction);
   return result;
}
```

컴파일러 생성 코드에는 **여전히 클로저 캡처가 있다.**

```csharp

{
   Program.<>c__DisplayClass26_0 <>c__DisplayClass26_ = new Program.<>c__DisplayClass26_0();
```

> **💡 지역 함수가 진짜로 이기는 한 가지 경우**
>
> 클로저가 **힙에 할당되지 않는** 경우가 딱 하나 있다.
>
> ```csharp
> public int Lambda(int x)
> {
>     var add = (int value) => x + value;
>     return add(10);
> }
>
> public int LocalFunction(int x)
> {
>     int Add(int value) => x + value;
>     return Add(10);
> }
> ```
>
> 두 메서드 모두 `x`를 캡처한다. 그런데 디컴파일해 보면 **지역 함수용으로 방출된 클로저는 클래스가 아니라 구조체다.** 조건은 두 가지다 — **지역 함수가 부모 함수에서만 호출되고, 델리게이트로 밖에 나가지 않을 것.** 이 조건이 만족되면 클로저는 스택에 남는다. 26.12절의 "람다 vs 지역 함수" 비교의 실체가 이것이다. 핫 패스에서 콜백을 쓸 일이 있다면 **델리게이트로 넘기지 않는 지역 함수**를 먼저 검토하라.

### 3. 박싱

54.6절에서 박싱의 IL과 힙 표현을 봤다. .NET 메모리 규칙 중 첫손에 꼽히는 것이 **박싱을 피하라**다. 문제는 **대부분의 박싱이 암묵적으로 일어나 인지조차 못 한다**는 점이다. 흔한 발생 지점을 훑는다.

**(a) 값 타입이 `object`가 기대되는 자리에 쓰일 때**

`string.Format`, `string.Concat` 등 `System.Object` 인스턴스를 받는 오버로드가 대표적이다.

```csharp
int i = 123;
return string.Format("{0}", i);
```

```il
ldc.i4.s 123
stloc.0
ldstr "{0}"
ldloc.0
box System.Int32
call string System.String::Format(string, object)
```

`box System.Int32` 한 줄이 힙 할당이다. `i.ToString()`을 미리 호출하면 박싱은 피하지만 **`ToString`이 새 문자열을 할당한다.** 더 나은 해법은 보간 문자열이며, 아래 6번에서 다룬다.

일반 원칙으로 **`object`를 매개변수로 받는 메서드는 가능한 한 피한다.** .NET Framework 2.0에서 제네릭이 도입되기 전에는 대부분의 컬렉션이 데이터를 `object` 참조로 저장했다 — `ArrayList.Add(Object value)` 같은 것들이다. 제네릭 덕분에 이 문제는 사라졌다. `List<T>`는 `List<int>`로 특수화 컴파일되고 박싱이 필요 없다.

**(b) 값 타입이 자신이 구현한 인터페이스로 쓰일 때**

인터페이스는 참조 타입이므로 박싱이 필요하다.

```csharp
public string Main(string args)
{
  SomeStruct some;
  return Helper(some);
}

string Helper(ISomeInterface data) => data.GetMessage();
```

```il
ldloc.0
box SomeStruct
call instance string Program::Helper(class ISomeInterface)
```

**회피법**: 원하는 인터페이스를 **제네릭 타입 제약**으로 받는 제네릭 메서드로 바꾼다.

```csharp
string Helper<T>(T data) where T : ISomeInterface => data.GetMessage();
```

제네릭 메서드는 그 값 타입 인자에 대해 특수화 컴파일되므로 박싱이 사라진다.

```il
ldloc.0
call instance string Program::Helper<valuetype SomeStruct>(!!0)
```

**(c) `foreach`가 `IEnumerable<T>`를 순회할 때 — 열거자 박싱**

가장 흔하면서 가장 안 보이는 사례다.

```csharp
public int Main(string args)
{
      List<int> list = new List<int>() {1, 2, 3};
      Print(list);
      return list.Count;
}

public void Print(IEnumerable<int> list)
{
      foreach (var x in list) Console.WriteLine(x);
}
```

무슨 일이 벌어지는가. `foreach`는 열거자 개념 위에 구현된다 — 컬렉션의 `GetEnumerator()`를 호출하고 `Current`와 `MoveNext()`를 반복 호출한다. `Print` 안에서 `list`는 `IEnumerable<int>`로 보이므로 `IEnumerable<int>.GetEnumerator()`가 호출되고, 이는 `IEnumerator<int>`를 반환해야 한다.

그런데 `List<T>.GetEnumerator()`가 반환하는 `Enumerator`는 **구조체다.** 이 구조체가 `IEnumerator<int>`로 쓰이므로, **`foreach` 루프 시작 시점에 박싱이 한 번 일어난다.**

**회피법**: 매개변수를 구체 타입으로 받는다.

```csharp
public void Print(List<int> list)   // IEnumerable<int>가 아니라 List<int>
```

이러면 `foreach`가 `List<int>.GetEnumerator()`를 호출하고 `List<int>.Enumerator` 구조체가 **지역 변수로** 만들어진다. 박싱이 없다.

> **⚠️ 여기서 좋은 설계와 최적화가 정면으로 충돌한다**
>
> 일반적으로 `Print`는 아무 `IEnumerable<T>`나 받도록 설계하는 것이 좋고, 구체 `List<T>` 구현에 묶지 않는 것이 좋다. 그런데 그게 박싱을 유발한다. **둘 중 하나를 선택해야 한다.**
>
> 판단 기준은 명확하다. 박싱 **한 번**은 `foreach` 루프 안에서 벌어지는 연산들에 압도적으로 묻힌다. 이게 문제가 되는 것은 **핫 패스에서 그런 `foreach`를 수없이 반복할 때뿐이다.** 늘 그렇듯 먼저 측정하라 — `Enumerator` 할당 개수를 세어 보면 된다.

> **📌 그러면 왜 애초에 열거자를 구조체로 만들었나**
>
> 답은 단순하다. **압도적 다수의 사용 사례는 열거자를 지역 변수로 쓴다.** 값 타입이면 스택에 싸고 빠르게 만들 수 있다. 이 이득이 인터페이스 경유 시의 박싱 문제를 압도한다.

**(d) 덜 알려진 세 가지 박싱 출처**

| 상황 | 설명 |
|---|---|
| `valueType.GetHashCode()` / `valueType.ToString()` | 해당 값 타입이 이 **가상 메서드를 재정의하지 않았을 때** 박싱된다 |
| `valueType.GetType()` | **항상** 박싱된다. 예외 없다 |
| 값 타입 메서드로 델리게이트를 만들 때 | 박싱된다 |

세 번째의 증거다.

```csharp
SomeStruct valueType;
Func<double> action2 = valueType.SomeMethod;
```

```il
ldarg.1
box       CoreCLR.Program.SomeStruct
ldftn     instance float64 CoreCLR.Program.SomeStruct::SomeMethod()
newobj    instance void class [System.Runtime]System.Func`1<float64>::.ctor(object, native int)
callvirt  instance !0 class [System.Runtime]System.Func`1<float64>::Invoke()
```

**할당이 두 번**이다. 박싱 하나, 델리게이트 하나.

> **💡 구조체를 만들면 `Equals`·`GetHashCode`·`ToString`을 재정의하라**
>
> 위 표의 첫 줄 때문이다. 재정의하지 않으면 `Dictionary<TKey, TValue>`의 키로 쓰는 순간 조회마다 박싱이 터진다. `record struct`를 쓰면 컴파일러가 값 기반 `Equals`/`GetHashCode`를 생성해 주므로 이 문제를 자동으로 피한다. 메모리 관리 관점에서 `record struct`와 `struct`는 아무 차이가 없다 — 둘 다 그냥 구조체다.

### 4. `yield return`

`async` 메서드와 클로저 외에 컴파일러가 보조 클래스를 만들어 숨은 할당을 유발하는 메커니즘이 하나 더 있다. **`yield return`** 이다. 반복자 메서드를 빠르고 편하게 만들어 주는 대신, 반복 상태를 담을 반복자 클래스 생성이라는 무거운 일을 컴파일러에 떠넘긴다.

```csharp
private IEnumerable<string> WithoutClosures(int value)
{
   foreach (int x in _list)
      if (x > value)
         yield return x.ToString();
}
```

컴파일 결과다.

```csharp
[IteratorStateMachine(typeof(Program.<WithoutClosures>d__26))]
private IEnumerable<string> WithoutClosures(int value)
{
      Program.<WithoutClosures>d__26 expr_07 = new Program.<WithoutClosures>d__26(-2);
      expr_07.<>4__this = this;
      expr_07.<>3__value = value;
      return expr_07;
}
```

**반복자 상태를 표현하는 임시 객체 하나가 할당된다.** 그리고 `value` 변수뿐 아니라 **`this` 참조까지 캡처한다.**

> **💡 그래도 LINQ보다는 낫다**
>
> 앞의 LINQ 버전은 클로저 + 델리게이트 + `Where`/`Select`가 만드는 열거자들까지 할당했다. `yield return` 버전은 **객체 하나**다. "람다를 없앴더니 오히려 손해"라는 앞의 경고와 달리, `yield return`은 대개 **덜 할당하는 대안**이다.
>
> 다만 `this`를 캡처한다는 사실은 기억해 둘 만하다. 열거를 오래 붙잡고 있으면 **`this`가 가리키는 객체 그래프 전체가 함께 살아남는다.** 66장의 누수 시나리오에 자주 등장하는 패턴이다.

### 5. 매개변수 배열(`params`)

C# 2.0 시절부터 `params` 키워드로 가변 개수 매개변수를 받을 수 있다. **이것은 컴파일러를 위한 문법 설탕일 뿐이다.** 내부적으로 인자는 그냥 **객체 배열**이다.

```csharp
public void MethodWithParams(string str, params object[] args)
{
      Console.WriteLine(str, args);
}
```

호출할 때마다 **새 `object[]` 배열이 할당된다.**

```csharp
SomeClass sc;
MethodWithParams("Log {0}", sc);       // 요소 하나짜리 object[] 새로 할당

int counter;
MethodWithParams("Counter {0}", counter); // 정수를 박싱 + object[] 새로 할당

p.MethodWithParams("Hello!");          // 할당 없음 — 정적 Array.Empty<object>()를 쓴다
```

세 번째 줄이 컴파일러의 유일한 최적화다. **인자가 하나도 없으면 배열을 만들지 않고 `Array.Empty<object>()`를 쓴다.**

**회피법**: 대부분의 호출이 인자 몇 개만 쓴다는 사실을 이용해, **자주 쓰는 개수에 대해 오버로드를 제공한다.** 객체 형태로든 제네릭 메서드로든 가능하다.

```csharp
public void MethodWithParams(string str, object arg1)
      => Console.WriteLine(str, arg1);

public void MethodWithParams(string str, object arg1, object arg2)
      => Console.WriteLine(str, arg1, arg2);

public void GenericMethodWithParams<T1>(string str, T1 arg1)
      => Console.WriteLine(str, arg1);

public void GenericMethodWithParams<T1, T2>(string str, T1 arg1, T2 arg2)
      => Console.WriteLine(str, arg1, arg2);
```

**제네릭 오버로드가 더 낫다.** 배열 할당뿐 아니라 **값 타입 인자의 박싱까지 함께 제거하기 때문이다.** 로깅 라이브러리들이 `LogInformation<T0, T1>(...)` 같은 제네릭 오버로드를 잔뜩 제공하는 이유가 바로 이것이다.

> **⚠️ 로거 호출 한 줄이 할당 두 개다**
>
> `_logger.LogDebug("count={0}", count)`는 `params object[]` 오버로드로 바인딩되면 **배열 하나 + `count` 박싱 하나**를 할당한다. 그리고 **로그 레벨이 꺼져 있어도 할당은 이미 일어난 뒤다.** 인자 평가는 메서드 호출 전에 끝나기 때문이다. 이것이 `LoggerMessage.Define`이나 소스 제너레이터 기반 로깅(`[LoggerMessage]` ※.NET 6)이 존재하는 이유다.

### 6. 문자열 연결과 포매팅

문자열이 불변으로 설계된 이유와 그 결과는 54.7절에서 다뤘다. 여기서는 **할당 관점**만 본다.

```csharp
// 임시 문자열 "Hello " + otherString이 만들어진다
string str = "Hello " + otherString + "!";

// str + " you are welcome"를 새로 할당한다 (이전 str은 쓰레기가 된다)
str += " you are welcome";
```

세 가지 접근을 벤치마크한다. 64회 반복해서 문자열을 만든다.

```csharp
[Benchmark]
public static string StringConcatenation()
{
      string result = string.Empty;
      for (int num = 0; num < 64; num++) result += string.Format("{0:D4}", num);
      return result;
}

[Benchmark]
public static string StringBuilder()
{
      StringBuilder sb = new StringBuilder();
      for (int num = 0; num < 64; num++) sb.AppendFormat("{0:D4}", num);
      return sb.ToString();
}

[Benchmark]
public static string StringBuilderCached()
{
      StringBuilder sb = StringBuilderCache.Acquire(2 * 4 * 64);
      for (int num = 0; num < 64; num++) sb.AppendFormat("{0:D4}", num);
      return StringBuilderCache.GetStringAndRelease(sb);
}
```

세 번째는 `StringBuilderCache`를 쓴다. 공개 타입은 아니지만 .NET Framework 소스에서 그대로 복사해 쓸 수 있다.

| 메서드 | Mean | Gen 0 | Allocated |
|---|---|---|---|
| StringConcatenation | 7.604 us | 2.5940 | 21.22 KB |
| StringBuilder | 3.133 us | 0.3815 | 3.13 KB |
| StringBuilderCached | 2.442 us | 0.2441 | 2.02 KB |

**메모리 소비가 열 배 차이 난다.** GC 오버헤드도 열 배다. 이 테스트 케이스에서는 사소해 보이지만, 초당 수천 요청을 처리하는 웹 애플리케이션에서는 실제 차이를 만든다.

> **⚠️ 그렇다고 두세 조각 연결에까지 `StringBuilder`를 쓰지 마라**
>
> 작은 조각을 많이 이어 붙여 큰 텍스트를 만드는 경우에는 `StringBuilder`가 최선이다. 하지만 **두세 조각만 붙이는 단순한 경우라면 그냥 `+` 연산자가 낫다.** 내부적으로 `string.Concat`이 호출되고, 이것은 문자열 데이터를 **직접 조작해서** 효율적으로 연결한다.
>
> ```csharp
> public static String Concat(String str0, String str1)
> {
>    if (IsNullOrEmpty(str0)) { return IsNullOrEmpty(str1) ? String.Empty : str1; }
>    if (IsNullOrEmpty(str1)) { return str0; }
>    int str0Length = str0.Length;
>    String result = FastAllocateString(str0Length + str1.Length);
>    FillStringChecked(result, 0,        str0);
>    FillStringChecked(result, str0Length, str1);
>    return result;
> }
> ```
>
> 결과 길이를 한 번에 계산해 **딱 한 번 할당하고** 채운다. `StringBuilder`를 쓰면 오히려 빌더 객체 + 내부 배열 + 최종 문자열로 할당이 늘어난다.

**보간 문자열** ※.NET 6은 이 그림을 크게 바꿨다. 네 개의 정수를 이어 붙이는 경우를 비교한다.

```csharp
public string StringFormat(int i1, int i2, int i3, int i4)
{
    return string.Format("{0:D4}{1:D4}{2:D4}{3:D4}", i1, i2, i3, i4);
}

public string StringInterpolation(int i1, int i2, int i3, int i4)
{
    return $"{i1:D4}{i2:D4}{i3:D4}{i4:D4}";
}
```

보간 문자열의 첫 번째 이점은 명백하다 — **변수의 개수와 순서를 틀릴 수 없다.** 두 번째는 성능이다. `string.Format` 호출에 필요한 **숨은 배열 할당(`params object[]`!)이 사라지고**, 문자열이 만들어지는 방식 자체가 달라진다. 컴파일러는 `StringInterpolation`을 이렇게 바꾼다.

```csharp
public string StringInterpolation(int i1, int i2, int i3, int i4)
{
    System.Runtime.CompilerServices.DefaultInterpolatedStringHandler handler
        = new System.Runtime.CompilerServices.DefaultInterpolatedStringHandler(0, 4);
    handler.AppendFormatted(i1, "D4");
    handler.AppendFormatted(i2, "D4");
    handler.AppendFormatted(i3, "D4");
    handler.AppendFormatted(i4, "D4");
    return handler.ToStringAndClear();
}
```

`DefaultInterpolatedStringHandler`는 **"보간 문자열 핸들러"** 패턴의 BCL 구현이다. `StringBuilder`로 하던 일을, 포맷 가능한 여러 조각으로부터 효율적으로 문자열을 만드는 방식으로 바꾼 것이다.

여기서 더 밀어붙일 수 있다. **핸들러에 스택 할당 버퍼를 직접 주는 것**이다.

```csharp
public string WithHandler(int i1, int i2, int i3, int i4)
{
    var handler = new DefaultInterpolatedStringHandler(
        0, 4, CultureInfo.InvariantCulture, stackalloc char[16]);
    handler.AppendFormatted<int>(i1, "D4");
    handler.AppendFormatted<int>(i2, "D4");
    handler.AppendFormatted<int>(i3, "D4");
    handler.AppendFormatted<int>(i4, "D4");
    return handler.ToStringAndClear();
}
```

스택 버퍼에 더해 **제네릭 `AppendFormatted` 헬퍼를 호출해서 정수 박싱까지 피한다.**

마지막 수단이 하나 더 있다. **문자열이 만들어지기 전에 그 버퍼를 채우는 것**이다. 불변성을 그렇게 강조해 놓고 무슨 소리인가 싶겠지만, 요령은 **생성 시점에 채우는** `String.Create`다.

```csharp
public static string Create<TState>(int length, TState state,
                                    System.Buffers.SpanAction<char, TState> action)
```

```csharp
public string StringCreate(int i1, int i2, int i3, int i4)
{
    return string.Create(16, (i1, i2, i3, i4), (span, state) =>
    {
        var pos = 0;
        int length = 0;
        state.i1.TryFormat(span.Slice(pos, 4), out length, "D4"); pos += length;
        state.i2.TryFormat(span.Slice(pos, 4), out length, "D4"); pos += length;
        state.i3.TryFormat(span.Slice(pos, 4), out length, "D4"); pos += length;
        state.i4.TryFormat(span.Slice(pos, 4), out length, "D4");
    });
}
```

각 조각은 `TryFormat` 헬퍼로 스팬에 직접 쓰인다. `TryFormat`은 `DateTime`, `Guid`를 포함한 대부분의 기본 타입이 제공한다.

| 메서드 | Mean | Gen 0 | Allocated |
|---|---|---|---|
| StringConcatenation | 295.53 ns | 0.0439 | 368 B |
| StringBuilder | 211.07 ns | 0.0305 | 256 B |
| StringFormat | 204.65 ns | 0.0248 | 208 B |
| StringInterpolation | 131.92 ns | 0.0067 | 56 B |
| WithHandler | 101.64 ns | 0.0067 | 56 B |
| StringCreate | 80.32 ns | 0.0067 | 56 B |

`StringBuilder` 기반 코드조차 핸들러와 `String.Create`에 진다. **적재적소에 맞는 도구를 쓰라는, 그리고 기술적 선택은 언제나 측정으로 확인하라는 상기**다. 마지막 세 행의 56 B는 **최종 문자열 자체**의 크기다. 그 밑으로는 내려갈 수 없다.

> **⚠️ `String.Create`는 길이를 정확히 알아야 한다**
>
> 가장 큰 제약이다. **완성된 문자열의 정확한 길이를 미리 알아야 한다.** 그리고 **문자를 전부 채우는 것은 당신 책임이다.** 채우지 않으면 결과는 정의되지 않는다 — 초기화되지 않은 문자가 그대로 문자열에 남는다는 뜻이며, 메모리 내용 유출로 이어질 수 있다.

> **💡 커스텀 보간 핸들러**
>
> 보간 문자열 핸들러를 직접 만들 수도 있다. 대표적 활용은 **로그 레벨에 따라 런타임에 메시지 문자열 자체를 만들지 않는 로거**다. `LogDebug($"x={x}")`에서 Debug 레벨이 꺼져 있으면 **보간 자체를 수행하지 않는다.** 앞의 `params` 함정을 언어 차원에서 해결한 것이다. 자세한 안내는 Microsoft의 보간 문자열 핸들러 튜토리얼에 있다.

### 7. 문자열 인코딩

.NET 문자열은 첫날부터 **UTF-16**으로 인코딩되어 있다. 문자 하나가 메모리에서 **2바이트**를 차지한다. 더 저렴한 인코딩은 오래전부터 있었다 — 영어 대소문자와 구두점, 제어 코드로 제한된 7비트 ASCII, 그리고 웹에서 사실상 표준이 된 8비트 가변 길이 **UTF-8**이다.

이 인코딩들과 변환하려면 `System.Text`의 `UTF8Encoding` 같은 헬퍼 클래스를 쓴다. **ASCII나 UTF-8 인코딩 문자열을 표현하는 전용 관리 타입은 없다.** 대신 C# 11부터 **UTF-8 문자열 리터럴**이 생겼다. 리터럴 뒤에 `u8`을 붙이면 자동으로 그 UTF-8 인코딩을 담은 `ReadOnlySpan<byte>`가 된다. ※C# 11

```csharp
ReadOnlySpan<byte> contentType = "application/json"u8;   // 힙 할당 없음
```

`System.Text.Unicode.Utf8` 정적 클래스가 `ReadOnlySpan<byte>`를 문자열처럼 다루는 헬퍼를 제공한다. `TryWrite` 메서드들은 `TryWriteInterpolatedStringHandler`를 활용해서 스팬 내용을 손쉽게 포매팅한다.

```csharp
int i1 = 1, i2 = 2, i3 = 3, i4 = 4;
byte[] utf8buffer = new byte[4*4 + 3 + 1];   // 네 자리 숫자 4개 + 구분자 3개 + \0
Span<byte> utf8span = utf8buffer.AsSpan();
if (Utf8.TryWrite(utf8span, CultureInfo.InvariantCulture,
                  $"{i1:X4}.{i2:X4}.{i3:X4}.{i4:X4}", out int bytesWritten))
{
    // ...
}
```

`System.IUtf8SpanFormattable` 인터페이스에도 `TryWrite`가 정의되어 있고, `Guid`, `Version`, 날짜 관련 타입을 포함한 모든 기본 타입이 이를 구현한다. UTF-8 스팬을 조각조각 조립할 때 쓴다.

`ReadOnlySpan<byte>`를 `System.String`으로 바꿔야 할 때는 `Utf8.ToUtf16`을 쓴다.

```csharp
Span<char> utf16Version = new char[utf8buffer.Length].AsSpan();
var result = Utf8.ToUtf16(utf8span, utf16Version, out int bRead, out int cWritten);
if (result == OperationStatus.Done)
    Console.WriteLine(utf16Version.ToString());
```

반환값은 `System.Buffers.OperationStatus` 열거형의 네 값 중 하나다.

| 값 | 의미 |
|---|---|
| `Done` | 성공 |
| `DestinationTooSmall` | 대상 `Span<char>`가 부족했다. **버퍼를 키워 재시도할 수 있다** |
| `NeedMoreData` | 입력 스팬의 바이트 시퀀스가 불완전해 처리가 중단되었다 |
| `InvalidData` | 입력 스팬의 바이트 시퀀스가 유효하지 않아 처리가 중단되었다 |

반대 방향은 `Utf8.FromUtf16`이다.

```csharp
string utf16String = "1234567890";
Span<byte> utf8Span = new byte[utf16String.Length + 1].AsSpan();
var status = Utf8.FromUtf16(utf16String.AsSpan(), utf8Span,
                            out var charsRead, out var bytesWritten);
if (status == System.Buffers.OperationStatus.Done) { /* 성공 */ }
```

> **⚠️ `Length + 1`짜리 버퍼는 ASCII에서만 맞는다**
>
> UTF-8은 **가변 길이 인코딩**이다. 8비트를 넘는 문자(프랑스어 악센트 등)가 들어 있으면 인코딩에 **문자당 1바이트 이상**이 필요하다. 위 코드의 `new byte[utf16String.Length + 1]`은 순수 ASCII 문자열에서만 충분하다.
>
> ```csharp
> string frenchString = "élémentaire à repérer";
> var span = frenchString.AsSpan();
> byte[] utf8Buffer = new byte[frenchString.Length + 1];
> var status = Utf8.FromUtf16(span, utf8Buffer.AsSpan(), out var read, out var written);
> if (status == System.Buffers.OperationStatus.DestinationTooSmall)
> {
>     // 버퍼 크기를 늘려 재시도한다
>     utf8Buffer = new byte[frenchString.Length + frenchString.Length / 2 + 1];
>     status = Utf8.FromUtf16(span, utf8Buffer.AsSpan(), out read, out written);
> }
> ```
>
> **버퍼를 키워 재시도하면 그 재시도가 곧 추가 할당이다.** 인코딩 변환을 핫 패스에 두면 "성공한 경로"보다 "재시도 경로"의 비용이 훨씬 크다는 점을 잊지 마라. 애초에 `Encoding.UTF8.GetMaxByteCount(charCount)`로 상한을 잡고 `ArrayPool`에서 빌리는 것이 정답이다.

> **💡 인코딩 변환 자체를 없애는 것이 최선이다**
>
> HTTP 파이프라인은 바이트로 들어와 바이트로 나간다. 중간에서 `string`으로 바꿨다가 다시 UTF-8로 되돌리는 코드는 **왕복 변환 두 번과 할당 두 번**을 낸다. `"application/json"u8` 같은 UTF-8 리터럴과 `Utf8` 헬퍼로 **바이트 상태를 유지한 채** 처리하면 그 비용이 통째로 사라진다. 69.7절에서 실무 패턴을 다룬다.

### 8. `async` 메서드의 상태 기계와 `Task`

C# 5.0에서 `async`가 도입된 뒤 비동기 코드는 어디에나 있다. 이것이 메모리 소비에 어떤 영향을 주는지 알아 둘 가치가 있다.

```csharp
public async Task<string> ReadFileAsync(string filename)
{
   if (!File.Exists(filename))
      return string.Empty;
   return await File.ReadAllTextAsync(filename);
}
```

`async` 키워드가 메서드를 꽤 복잡한 상태 기계로 바꾼다는 것은 대부분 안다. 컴파일러가 만든 코드를 보면 이렇다.

```csharp
[AsyncStateMachine(typeof(Program.<ReadFileAsync>d__14))]
public Task<string> ReadFileAsync(string filename)
{
   Program.<ReadFileAsync>d__14 stateMachine = default(Program.<ReadFileAsync>d__14);
   stateMachine.filename = filename;
   stateMachine.<>t__builder = AsyncTaskMethodBuilder<string>.Create();
   stateMachine.<>1__state = -1;
   stateMachine.<>t__builder.Start(ref stateMachine);
   return stateMachine.<>t__builder.Task;
}
```

메모리 관점에서 중요한 사실은 셋이다.

- **전부 구조체다.** `<ReadFileAsync>d__14`도, `AsyncTaskMethodBuilder<string>`도. 클래스를 쓰고 싶어지는 자리에 의식적으로 구조체를 쓴 좋은 예다. 단, **디버그 모드로 컴파일하면 상태 기계가 참조 타입으로 바뀐다**(디버깅 편의를 위해 성능을 내준다). 자기 어셈블리를 디컴파일했을 때 클래스가 나와도 놀라지 마라.
- **비동기 연산이 즉시 끝나지 않으면 상태 기계가 박싱된다.** `AwaitUnsafeOnCompleted` 안에서 벌어진다. 그 경우 "상태"는 현재 메서드를 탈출해야 한다 — 비동기 연산이 시작된 스레드와 다른 스레드에서 이어질 수 있기 때문이다. 따라서 스택이 아니라 힙에 있어야 한다. 그래도 구조체로 만든 것은 의미가 있다. **박싱이 일어나지 않는 흔한 경로가 존재하기 때문이다** — 위 예에서 `File.Exists`가 `false`를 반환하는 경우.
- **상태 기계는 메서드의 필요한 지역 변수를 전부 기억(캡처)한다.** 위 예의 `filename`이다. 상태 기계가 힙에 올라가면 **그 변수들의 수명도 크게 늘어난다.**

> **📌 .NET Core 2.1부터 "박싱"이 아니다**
>
> 정확히 말하면 .NET Core 2.1부터는 상태 기계가 박싱되는 대신, **클래스의 강타입 필드로 힙에 옮겨진다.** 힙으로 간다는 결론은 같지만 구현이 다르다. 프로파일러에서 `<...>d__N` 타입 이름이 직접 보이는 이유가 이것이다.

**두 번째 함정**이 있다. 위 코드에서 파일이 존재하지 않는 경우를 따라가면, `goto` 뒤에 `AsyncTaskMethodBuilder<string>` 구조체의 `SetResult`가 호출된다. 이론적으로는 비동기 대기 오버헤드가 전혀 없는 아주 빠른 동기 경로다. **그런데 `SetResult`가 결과를 담을 `Task` 객체를 할당할 수 있다.**

```csharp
public struct AsyncTaskMethodBuilder<TResult>
{
   // ...
   public void SetResult(TResult result)
   {
      if (this.m_task == null)
      {
         this.m_task = Task.FromResult<TResult>(result);   // 여기서 할당된다
         return;
      }
      // ...
   }
}
```

`Task.FromResult`는 대부분의 경우 결과를 감싼 새 `Task`를 할당한다. 성능을 위한 예외가 몇 가지 있다.

| 타입 | 캐시 동작 |
|---|---|
| `Task<bool>` | `true`/`false` 두 개의 **캐시된 객체** 반환 |
| `Task<int>` | **-1부터 9까지**는 캐시된 객체. 그 외 값은 새 `Task` |
| 다수의 수치 `Task<T>` | 값 **0**에 대해 캐시된 객체 |
| `null` 결과 | 전용 캐시 태스크 |
| 그 외 | **새 `Task` 생성** |

결과값을 돌려주려고 `Task` 객체를 할당하는 것은 효율적이지 않다. `async` 메서드가 아주 자주 호출되고 **대개 동기적으로 완료된다면**, 불필요한 `Task` 할당을 잔뜩 만들고 있는 것이다.

**회피법**: `ValueTask<T>`. 반환 타입만 바꾸면 컴파일러가 `AsyncTaskMethodBuilder` 대신 `AsyncValueTaskMethodBuilder`를 쓴다.

```csharp
public async ValueTask<string> ReadFileAsync2(string filename)
{
   if (!File.Exists(filename))
      return string.Empty;
   return await File.ReadAllTextAsync(filename);
}
```

`ValueTask`는 구조체이며 **판별 공용체(discriminated union)** 로 만들어졌다. 세 가지 값 중 하나를 가진다.

```csharp
public struct ValueTask<TResult>
{
   // _result에 결과가 있으면 null, 아니면 Task<TResult> 또는 IValueTaskSource<TResult>
   internal readonly object _obj;
   internal readonly TResult _result;
   // ...
}
```

1. **즉시 사용 가능한 결과** — 연산이 동기적으로 성공한 경우
2. **평범한 `Task`** — 대기할 수 있는 것
3. **`IValueTaskSource<T>`** — 이것을 구현하면 태스크 객체를 풀링해서 할당을 최소화할 수 있다

소비하는 쪽은 그냥 `await`하면 된다. 아주 빡빡한 루프의 절대적으로 중요한 성능 경로에서만, 완료 여부를 먼저 확인하는 방식을 추가로 쓴다.

```csharp
var valueTask = ReadFileAsync2();
if (valueTask.IsCompleted)
   return valueTask.Result;
else
   return await valueTask.AsTask();
```

> **⚠️ `ValueTask`를 `Task`의 기본 대체품으로 쓰지 마라**
>
> 문서가 설명하는 트레이드오프를 그대로 옮긴다.
>
> - "`ValueTask<TResult>`는 성공 결과를 동기적으로 얻을 수 있을 때 할당을 피하게 해 주지만, **필드가 두 개다.** 참조 타입인 `Task<TResult>`는 필드 하나다. 즉 메서드 호출이 필드 하나가 아니라 **두 개 분량의 데이터를 반환**하게 되고, 복사할 데이터가 늘어난다. 또한 이것을 반환하는 메서드를 `async` 메서드 안에서 `await`하면, **그 `async` 메서드의 상태 기계가 더 커진다** — 참조 하나가 아니라 필드 두 개짜리 구조체를 저장해야 하므로."
> - "나아가 `await`으로 비동기 연산 결과를 소비하는 것 외의 용도에서는 `ValueTask<TResult>`가 **더 뒤엉킨 프로그래밍 모델**로 이어지고, 그것이 오히려 **할당을 늘릴 수 있다.** 예를 들어 소비자가 결과를 `Task.WhenAll`이나 `Task.WhenAny`에 쓰려고 `Task<TResult>`로 다루고 싶다면, `AsTask`로 변환해야 하고 그 순간 할당이 발생한다 — 처음부터 캐시된 `Task<TResult>`를 썼다면 없었을 할당이다."
>
> 또한 `ValueTask`는 **한 번만 `await`할 수 있다.** 두 번 대기하거나, 대기 전에 `.Result`를 읽거나, 여러 곳에 저장해 두면 정의되지 않은 동작이다. `Task`에는 없는 제약이다.

세 번째 형태인 `IValueTaskSource<T>`까지 가면 **비동기 경로의 `Task` 할당도 없앨 수 있다.** 그 인스턴스를 캐시하거나 풀링하는 것이다.

```csharp
public ValueTask<string> ReadFileAsync3(string filename)
{
   if (!File.Exists(filename))
      return new ValueTask<string>("!");
   var cachedOp = pool.Rent();          // 태스크 소스 자체를 풀링한다
   return cachedOp.RunAsync(filename, pool);
}
```

`IValueTaskSource<T>`를 구현하려면 `GetResult`, `GetStatus`, `OnCompleted` 세 메서드가 필요하다. 편의상 연산을 시작하는 메서드와 완료에 반응하는 메서드도 있어야 한다.

> **⚠️ `IValueTaskSource`를 직접 구현하는 것은 거의 항상 나쁜 생각이다**
>
> 완전히 동작하고 스레드 안전한 `IValueTaskSource` 구현은 **전혀 사소하지 않다.** 실제로 이것을 구현해야 하는 개발자는 극소수다. 필요하다면 `System.Threading.Tasks.Sources.ManualResetValueTaskSourceCore<T>` 같은 BCL의 조립 부품부터 검토하고, 그래도 직접 만들어야 한다면 동시성 테스트에 충분한 시간을 배정하라.

## 63.10 라이브러리 내부의 숨은 할당 찾기

명시적이든 암묵적이든 할당 출처가 그렇게 많다는 것은, **BCL과 다른 라이브러리를 쓰는 것 자체가 인지하지 못한 할당의 위험을 동반한다**는 뜻이다. 모든 경우를 설명하는 것은 불가능하다 — 인기 있는 라이브러리 전부를 해부해야 하니까. 여기서는 BCL에서 가장 흔한 출처만 본다.

### `System.Collections.Generic` — 배열의 얼굴을 한 컬렉션들

`System.Collections.Generic`의 흔한 컬렉션 중 상당수는 **배열의 래퍼**로 볼 수 있다. 압도적으로 많이 쓰이는 `List<T>`를 보자.

```csharp
public class List<T> : IList<T>, IList, IReadOnlyList<T>
{
   private const int _defaultCapacity = 4;
   private T[] _items;
   // ...
```

내부적으로는 미리 정해진 크기의 요소 배열을 담고 있을 뿐이다(생성자에 용량을 주지 않았다면). `Add`로 리스트가 자라면 이 배열이 너무 작아진다 — **새 배열이 만들어지고 기존 항목이 전부 복사된다.** `List<T>`뿐 아니라 `Stack<T>`, `SortedList<T>`, `Queue<T>` 같은 컬렉션들이 채워지는 동안 내부 배열을 **여러 번 재할당한다.**

```csharp
// 나쁨 — 4 → 8 → 16 → ... → 1024까지 배열을 9번 새로 만들고 9번 복사한다
var list = new List<int>();
for (int i = 0; i < 1000; i++) list.Add(i);

// 좋음 — 배열을 딱 한 번 만든다
var list = new List<int>(capacity: 1000);
for (int i = 0; i < 1000; i++) list.Add(i);
```

**항목 수를 대략이라도 안다면 항상 용량을 받는 생성자 오버로드를 써라.** 컬렉션이 그 정보를 최적으로 쓸 것이라고 믿어도 된다.

> **⚠️ 버려진 중간 배열들은 LOH로 갈 수도 있다**
>
> 요소 22,000개짜리 `List<object>`를 용량 없이 채우면, 중간에 만들어졌다 버려지는 배열 중 뒤쪽 것들은 **85,000바이트를 넘어 LOH로 간다.** 그러면 63.4절에서 본 대로 0 채우기 비용이 붙고, LOH는 기본적으로 압축되지 않으므로 단편화까지 남는다. **용량 미지정 컬렉션 하나가 LOH 단편화의 원인이 되는 것은 흔한 시나리오다.**

> **💡 `EnsureCapacity`와 `TrimExcess`**
>
> 항목 수를 나중에 알게 되는 경우에는 `list.EnsureCapacity(n)`으로 한 번에 키운다. 반대로 오래 살 컬렉션을 다 채우고 나면 `TrimExcess()`로 남는 배열 공간을 반납할 수 있다. 장시간 상주하는 캐시 컬렉션에서 실제로 의미 있는 차이를 만든다.

### LINQ — 델리게이트

LINQ는 우아하고 즐겁다. 복잡한 데이터 조작을 몇 줄로 간결하게 쓸 수 있다. **그리고 C#에서 가장 할당이 많은 메커니즘 중 하나다.** 델리게이트, 클로저 등 숨은 할당 출처가 잔뜩 있다. LINQ 메서드는 델리게이트 기반이므로 델리게이트를 많이 만들게 된다.

```csharp
// 람다에 대한 델리게이트를 할당한다
var linq = list.Where(x => x.X > 0);
return linq;
```

다만 앞서 설명한 대로, 실행되는 함수가 아무것도 캡처하지 않으면 **그 델리게이트는 내부적으로 캐시된다.** 한 번만 할당된다.

```csharp
return System.Linq.Enumerable.Where(
    list,
    Program.<>c.<>9__5_0 ?? (Program.<>c.<>9__5_0 = new System.Func<SomeClass, bool>(Program.<>c.<>9.<DelegateWithLambda>b__5_0)));
```

`??` 패턴이 보이면 "캐시된 델리게이트"라는 신호다. 이것이 보이지 않고 매번 `new Func<...>`가 있으면 **캡처가 있다는 뜻이고, 근처에 디스플레이 클래스 할당도 있다.**

### LINQ — 익명 타입 생성

LINQ 쿼리를 쓸 때 임시 익명 타입을 만들고 싶어진다. 이미 많은 할당 위에 하나를 더 얹는 셈이다.

```csharp
public IEnumerable<Double> Main(List<SomeClass> list) {
   var linq = from x in list
      let s = x.X + x.Y
      select s;
   return linq;
}
```

**`let` 문이 실제로는 임시 익명 객체를 만든다.**

```csharp
[CompilerGenerated]
private sealed class <>c
{
   internal <>f__AnonymousType0<SomeClass, double> <Main>b__0_0(SomeClass x)
   {
      return new <>f__AnonymousType0<SomeClass, double>(x, x.X + x.Y);
   }
   // ...
}
public IEnumerable<double> Main(List<SomeClass> list)
{
   return list.Select(<>c.<>9__0_0 ?? (<>c.<>9__0_0 = <>c.<>9.<Main>b__0_0))
              .Select(<>c.<>9__0_1 ?? (<>c.<>9__0_1 = <>c.<>9.<Main>b__0_1));
}
```

**요소 하나당 익명 객체 하나**다. 1만 개짜리 리스트라면 익명 객체 1만 개다.

우아한 LINQ 쿼리를 위해 이런 임시 타입이 정말 필요할 때도 있다. 하지만 **정말 필요한 것인지, 아니면 그저 편하고 보기 좋아서인지**를 늘 물어야 한다. 위 예에서는 명백히 불필요하다. 합을 바로 반환하면 된다.

```csharp
public IEnumerable<Double> Main(List<SomeClass> list) {
   var linq = list.Select(x => x.X + x.Y);
   return linq;
}
```

```csharp
public IEnumerable<double> Main(List<SomeClass> list)
{
   return list.Select(<>c.<>9__0_0 ?? (<>c.<>9__0_0 = <>c.<>9.<Main>b__0_0));
}
```

`Select` 호출 하나가 사라지고 익명 타입 할당도 사라졌다.

### LINQ — 열거자

LINQ 메서드가 사실은 **열거 가능 객체(enumerable)의 사슬을 만든다**는 것은 덜 알려져 있다. 그 열거 가능 객체들은 **대부분 힙에 할당되어야 한다.** 가장 단순한 `Enumerable.Range`조차 그렇다.

```csharp
// System.Linq.Enumerable/'<RangeIterator>d__111'을 할당한다
var range = Enumerable.Range(0, 100);
```

`Where`나 `Select` 같은 인기 메서드도 자기 반복자를 할당한다. `Where`는 호출 대상에 따라 다음 셋 중 하나를 만든다.

| 반복자 | 조건 |
|---|---|
| `WhereArrayIterator` | 배열에 호출된 경우 |
| `WhereListIterator` | `List`에 호출된 경우 |
| `WhereEnumerableIterator` | 그 외 일반적인 경우 |

이 반복자들은 **약 48바이트**다. 소스 컬렉션 참조, 선택용 델리게이트, 스레드 ID 등을 담기 때문이다(.NET 버전에 따라 달라질 수 있다). 메서드 하나 안에서 LINQ 때문에 48바이트를 몇 번 할당하는 게 문제인가 아닌가 — 늘 그렇듯 **당신의 성능 요구사항에 달렸다.**

LINQ 내부에는 가능한 경우 반복자를 **결합하는** 최적화가 있다. 그런데 안타깝게도 그것이 할당을 없애 주지는 않는다. 인기 있는 `Where`+`Select` 조합에서는 결합된 `WhereSelectArrayIterator`가 쓰이지만, **중간의 `WhereArrayIterator`도 함께 만들어진다.**

```csharp
string[] FilterStrings(string[] inputs, int min, int max, int charIndex)
{
      var results = inputs.Where(x => x.Length >= min && x.Length <= max)
                      .Select(x => x.ToLower());
      return results.ToArray();
}
```

이 사소한 메서드가 할당하는 것을 세어 보자.

| 할당물 | 크기 | 비고 |
|---|---|---|
| `WhereArrayIterator` | **48바이트** | 수명이 아주 짧다. 곧 다음 것으로 대체된다 |
| `WhereSelectArrayIterator` | **56바이트** | |
| 델리게이트 | | `Where`에 넘긴 람다 |
| 클로저(디스플레이 클래스) | | 정수 두 개(`min`, `max`)를 캡처한다 |
| `ToArray()`의 결과 배열 | | 그리고 그 과정의 중간 버퍼들 |

**다섯 종류 이상이다.** 게다가 각 요소마다 `x.ToLower()`가 새 문자열을 만든다.

> **💡 LINQ를 쓰면서 할당을 줄이는 도구**
>
> 케이크를 먹으면서 가질 수도 있다. **LINQ 쿼리를 절차적 코드로 자동 재작성해 주는 라이브러리**들이 있다. 대표적으로 **roslyn-linq-rewrite**와 **LinqOptimizer**다. 컴파일 시점에 `Where`+`Select` 사슬을 단일 `foreach` 루프로 바꿔 반복자와 델리게이트 할당을 제거한다.
>
> 다만 도입 전에 반드시 측정하라. 그리고 대안이 하나 더 있다 — **핫 패스에서만 LINQ를 손으로 푸는 것**이다. 코드베이스 전체의 LINQ를 없애는 것은 거의 항상 나쁜 거래다.

> **📌 불변 컬렉션이 "느리다"는 벤치마크에 속지 마라**
>
> `System.Collections.Immutable`의 `ImmutableArray<T>`나 `ImmutableList<T>`에 객체를 무수히 추가하며 가변 `List<T>`와 속도를 겨루는 벤치마크가 흔하다. 불변 컬렉션은 변경마다 새 내용을 담은 구조를 만들어야 하니 당연히 느리다(실제 구현은 공통 부분을 재사용하므로 순진한 복사보다는 영리하다).
>
> **그것은 이 컬렉션들을 비교하는 방법이 아니다.** 불변성의 이점은 멀티스레드 세계에 있다. 읽기 전용 데이터에 대한 **안전한 락 프리 접근**은 경합이 심한 시나리오에서 불변성 자체의 오버헤드보다 훨씬 큰 이득이 되고, 변하지 않는 성질 덕에 **캐시 일관성 오버헤드 없이 CPU 캐시를 잘 활용한다.** 문제에 맞는 도구를 고르는 문제이지, 설계 용도가 아닌 일을 시킨 벤치마크에 의미를 부여할 일이 아니다.

### 할당 추적 실전 절차

지금까지 본 카탈로그는 **무엇을 찾을지**를 알려 준다. 이제 **어떻게 찾을지**를 정리한다. 순서를 지키는 것이 중요하다. 처음부터 프로파일러를 붙이는 것은 낭비다.

**1단계 — 할당률을 먼저 본다.**

```text
$ dotnet-counters monitor -p <pid>
    Allocation Rate (B / 1 sec)                                  200,000,000
```

`Allocation Rate`가 곧바로 답을 주지는 않는다. 초당 200 MB가 좋은 값인지 나쁜 값인지는 **비교 대상 없이는 말할 수 없다.** 하지만 이 숫자가 **평소보다 갑자기 뛴 시점**은 확실한 신호다. 절대값이 아니라 추세를 본다.

**2단계 — `dotnet-trace`로 할당을 표본 수집한다.**

.NET 앱의 할당 측정에 가장 좋은 도구 중 하나가 **`gc-verbose` 프로파일을 쓴 `dotnet-trace`** 다. 할당 샘플링을 하지만 대부분의 전형적인 경우를 커버할 만큼 세밀하다. 게다가 **멀티플랫폼**이라 Windows·Mac·Linux 어디에 배포하든 쓸 수 있다.

시작 시점부터 추적하려면 `dotnet-trace`가 대상 애플리케이션을 직접 실행하게 한다.

```text
dotnet-trace collect --profile gc-verbose --show-child-io -- \
    .\WordStatsApp\bin\Release\net8.0\WordStatsApp.exe --pages 5
```

**3단계 — PerfView로 결과 `nettrace` 파일을 분석한다.**

1. PerfView를 실행한다.
2. Memory 그룹에서 **GC Heap Alloc Ignore Free (Coarse Sampling) Stacks** 를 선택한다.
3. 뜨는 Broken Stacks 대화 상자는 무시해도 된다.

여기서 두 갈래로 조사한다.

**갈래 1 — 할당의 큰 그림.** By Name 탭에서 **Exc 열 기준 내림차순 정렬**을 한다. 가장 영향이 큰 할당 출처가 즉시 보인다. 타입만이 아니라 **집계된 출처(스택 트레이스)** 도 똑같이 유용하다. 예를 들어 최상위 `System.CharEnumerator` 타입이 어디서 할당되는지 보려면 컨텍스트 메뉴에서 **Goto → Goto Item in Callers** 를 선택한다. 조사 중 알아 둘 것이 둘 있다.

- 이름 없는 모듈(`<<microsoft.codeanalysis.csharp!?>>`처럼 `?!`로 끝나는 것)은 컨텍스트 메뉴의 **Lookup Symbols** 로 심볼을 불러올 수 있다.
- 컨텍스트 메뉴의 **Grouping → Group Module** 로 모듈을 묶을 수 있다. 외부 모듈을 묶어 두면 **내 코드의 할당**만 남아 보기 좋다.

**갈래 2 — 특정 메서드의 할당.**

1. By Name 탭의 GroupPats에 `[No grouping]`을 선택한다 — 전부 풀어서 상세히 본다.
2. Find 텍스트 상자에 함수 이름을 입력한다 — 예를 들어 `TryNormalize`.
3. 찾은 항목의 컨텍스트 메뉴에서 **Goto → Goto Item in Callees** 를 클릭한다. 그 메서드와 그것이 호출하는 모든 것의 할당이 보인다.

이 절차로 다음 코드에서 **`Char[]`만 200 MB 넘게**, 그리고 호출된 `Any`와 `Trim`에서 더 많은 할당이 나오는 것을 확인한 실제 사례가 있다.

```csharp
private static bool TryNormalize(string word, out string result)
{
    result = word.ToLowerInvariant()
        .Trim('.', ',', ';', '!', '?', '"', ':', '(', ')', '_', '[', ']');

    if (result.Any(c => !char.IsLetter(c)))
        return false;

    return true;
}
```

이 장을 읽었다면 할당 출처가 전부 보여야 한다.

| 코드 조각 | 할당 |
|---|---|
| `word.ToLowerInvariant()` | 새 문자열 하나 |
| `.Trim(...)` | **`params char[]` 배열** + 잘린 새 문자열 |
| `result.Any(c => ...)` | LINQ 열거자 + `string`의 `IEnumerable<char>` 열거(= `CharEnumerator` 박싱) |
| 람다 `c => !char.IsLetter(c)` | 캡처가 없으므로 델리게이트는 캐시된다 |

`Trim`의 `char[]`는 **호출마다 새로 만들어진다.** 정적 `readonly` 배열로 빼는 것만으로도 큰 차이가 난다. `Any` 대신 `foreach` 루프로 바꾸면 열거자 박싱과 LINQ 반복자가 사라진다.

> **💡 메모리가 곧 돈인 환경 — Azure Functions**
>
> Azure Functions는 **GB-초(GB-s) 단위의 초당 리소스 소비와 실행 횟수**로 과금된다. 함수가 쓴 메모리는 **가장 가까운 128 MB 단위로 올림**되고(최대 1,536 MB), 실행 시간은 1 ms 단위로 올림된다. 단일 실행의 최소 실행 시간과 메모리는 각각 **100 ms와 128 MB**다. 즉 함수 호출 하나가 최소 **0.0125 GB-s**(0.1초 × 0.125 GB)를 소비한다. 월 **400,000 GB-s와 100만 회 실행**의 무료 한도가 있다.
>
> 계산이 명확하다. 함수가 메모리를 낭비하면 무료 한도를 넘어설 수 있고, **메모리 사용이 또 다른 128 MB를 넘을 때마다 비용이 배수로 뛴다.** .NET 세계에서 메모리 사용이 이렇게 직접적으로 돈으로 환산되는 곳은 드물다.
>
> Azure는 Application Insights로 Function Execution Units를 추적할 수 있게 해 준다. 단위는 **MB-ms**이므로 GB-s로 환산해야 한다. 다만 비용 모니터링에는 쓸 수 있어도 **함수 메모리 사용에 대한 깊은 통찰은 주지 않는다.** 프로파일링과 최적화는 개발 환경에서 하는 것이 낫다 — 로컬에서 함수를 실행하면 위 3단계 절차를 그대로 쓸 수 있다.

### 라이브러리가 주는 해독제 — 할당 회피 도구

숨은 할당을 찾았다면 이제 없앨 차례다. .NET은 이를 위한 도구를 이미 제공한다. 각 도구의 실무 적용은 **69장에서 심화**하고, 여기서는 지도를 그린다.

| 도구 | 무엇을 대체하나 | 언제 쓰나 | 함정 |
|---|---|---|---|
| **`struct` / `record struct`** | 작은 데이터 전달용 `class` | 메서드 안에서만 살고 힙 자료 구조에 저장되지 않는 데이터 | 크면 복사 비용. `ref`/`in`으로 전달 |
| **`ValueTuple`** `(A, B)` | `Tuple<T1,T2>`, 익명 타입 | 메서드에서 값 여러 개를 반환할 때 | 필드가 public이라 캡슐화가 약하다 |
| **`stackalloc` + `Span<T>`** | 작은 임시 배열 | **1 kB 이하** 고정 크기 버퍼 | 크기가 런타임 값이면 반드시 상한 분기. 루프·재귀 금지 |
| **`ArrayPool<T>`** | 반복 생성되는 `T[]` | 큰 버퍼를 자주 빌리고 반납할 때 | `Rent`는 **요청보다 큰 배열을 준다**. `Return` 누락 = 조용한 성능 저하 |
| **`RecyclableMemoryStream`** | `MemoryStream` | 스트림을 격하게 쓰는 코드 | 매니저를 **정적으로 하나** 두고 재사용해야 의미가 있다 |
| **오브젝트 풀** | 자주 만들어지는 무거운 객체 | 초기화 비용이 크거나 mid-life crisis가 있는 객체 | 스레드 안전한 풀을 잘못 만들면 할당보다 느리다 |
| **`ValueTask<T>`** | `Task<T>` | **대개 동기적으로 완료되는** `async` 메서드 | 한 번만 `await` 가능. `WhenAll`에 쓰려면 `AsTask()`(= 할당) |

각 도구의 핵심 사실을 짧게 덧붙인다.

**`ValueTuple`** — `Tuple`과 익명 타입은 **참조 타입이므로 항상 힙에 만들어진다.** C# 7.0의 값 튜플은 구조체다.

```csharp
// 전부 힙 할당
var tuple1 = new Tuple<int, double>(0, 0.0);
var tuple2 = Tuple.Create(0, 0.0);
var tuple3 = new { A = 1, B = 0.0 };

// 힙 할당 없음
var tuple4 = (0, 0.0);
var tuple5 = (A: 0, B: 0.0);
tuple5.A = 3;
```

`Tuple<ResultDesc, ResultData>`를 반환하던 메서드를 `(ResultDescStruct, ResultDataStruct)`로 바꾼 결과다.

| 메서드 | Mean | Allocated |
|---|---|---|
| ProcessData1 (`Tuple` + 클래스) | 18.380 ns | 88 B |
| ProcessData2 (값 튜플 + 구조체) | 4.472 ns | **0 B** |

**할당이 완전히 사라지고 네 배 이상 빨라졌다.** 값 튜플은 **분해(deconstruction)** 도 지원하고, 관심 없는 요소는 폐기(discard)로 표시할 수 있다.

```csharp
(ResultDescStruct desc, _) = ProcessData2(list);
```

**`ArrayPool<T>`** — `System.Buffers`의 재사용 가능한 관리 배열 풀이다. 추상 클래스이며 팩토리처럼 동작한다. `Shared` 속성이 내부 `SharedArrayPool` 인스턴스를 반환하고, 이것이 주어진 타입의 다양한 크기 배열을 버킷으로 묶어 관리한다. **`SharedArrayPool`의 버킷은 27개이며, 첫 버킷이 16요소 배열, 그다음부터 두 배씩** — 16, 32, 64, 128, ... 이다. 배열은 **요청 시에만** 만들어진다.

```csharp
var pool = ArrayPool<int>.Shared;
int[] buffer = pool.Rent(minLength);
try     { Consume(buffer); }
finally { pool.Return(buffer); }
```

> **⚠️ `Rent`는 요청한 길이보다 큰 배열을 준다**
>
> `Rent`는 **최소한** 지정한 길이의 배열을 반환한다. 버킷 크기로 올림되므로 대개 더 크다. **`buffer.Length`를 데이터 길이로 착각하면 조용한 버그가 된다.** 512바이트를 요청해 1024바이트를 받았다면, 복사 작업을 1024바이트 청크로 수행해서 그 이점을 살리는 편이 낫다.
>
> 그리고 `Return`은 **`finally` 블록에 넣어라.** 예외 경로에서 반납을 빠뜨리면 풀이 비어 가고, 모든 `Rent`가 조용히 새 배열 할당으로 폴백한다. 오류가 아니라 **성능 저하**로만 나타나므로 발견이 늦다.

`ArrayPool<T>.Create(int maxArrayLength, int maxArraysPerBucket)`로 만드는 `ConfigurableArrayPool<T>`도 있다. 스레드 지역 저장소를 쓰지 않는 더 단순한 버킷 구현이다. 캐시되는 배열의 기본 최대 길이는 **1024×1024×1024(1,073,741,824)요소**이며(※.NET 6에서 늘었다. 이전에는 1,048,576요소), 버킷당 기본 배열 개수는 **CPU 코어 수의 32배**다. 환경 변수로 조정한다.

| 환경 변수 | 의미 |
|---|---|
| `DOTNET_SYSTEM_BUFFERS_SHAREDARRAYPOOL_MAXPARTITIONCOUNT` | 파티션 개수. 기본값은 CPU 코어 수 |
| `DOTNET_SYSTEM_BUFFERS_SHAREDARRAYPOOL_MAXARRAYSPERPARTITION` | 파티션당 최대 배열 개수 |

풀 사용은 **`System.Buffers.ArrayPoolEventSource`** ETW 공급자로 모니터링한다. PerfView의 Collect 대화 상자 Additional Providers 필드에 다음을 입력한다.

```text
*System.Buffers.ArrayPoolEventSource
*System.Buffers.ArrayPoolEventSource:::@StacksEnabled=true
```

**특히 `BufferAllocated` 이벤트의 `OverMaximumSize`와 `PoolExhausted` 사유에 주목한다.** 자주 발생한다면 현재 구성이 요구에 맞지 않는다는 뜻이다 — `OverMaximumSize`가 잦으면 최대 풀 크기가 너무 작고, `PoolExhausted`가 잦으면 버킷당 배열 개수를 늘릴 만하다.

`ArrayPool`은 **※.NET 5부터 트리밍 메커니즘**을 갖는다. gen 2 GC를 모니터링(`Gen2GcCallback` 클래스)하다가 휴리스틱으로 트리밍 필요 여부를 판단한다. 정확한 알고리즘은 복잡하고 버전마다 바뀔 수 있지만, **풀 안 배열의 나이, 요소 크기, 머신의 전반적 메모리 부하**에 의존한다는 점은 알아 둘 만하다.

**`RecyclableMemoryStream`** — `System.IO.MemoryStream`을 격하게 쓴다면 이 객체들의 풀을 고려해야 한다. `Microsoft.IO.RecyclableMemoryStream` 패키지의 `RecyclableMemoryStream`과 `RecyclableMemoryStreamManager` 클래스가 그 구현이다. `MemoryStream`의 격한 사용에는 다음 부작용이 따른다.

| 부작용 | 내용 |
|---|---|
| **메모리 낭비** | 내부 버퍼가 작아지면 **크기를 두 배로** 늘린다. 메모리가 계속 자라고 점점 더 큰 배열을 반복 할당한다 |
| **LOH 할당** | 내부 버퍼가 너무 커지면 LOH에 할당된다. 할당과 회수 모두 비싸다 |
| **메모리 복사** | 자랄 때마다 모든 바이트가 새 버퍼로 복사된다. 메모리 트래픽이 크다 |
| **단편화** | 내부 버퍼의 끊임없는 재생성이 단편화로 이어진다 |

`RecyclableMemoryStream` 클래스 주석의 설명이 정확하다. "스트림은 **균일한 크기의 블록 시리즈** 위에 구현된다. 스트림 길이가 자라면 메모리 매니저에서 추가 블록을 가져온다. **풀링되는 것은 스트림 객체 자체가 아니라 이 블록들이다.** 가장 까다로운 부분은 `GetBuffer()`가 호출될 때다. 이때는 연속된 단일 버퍼가 필요하다. 사용 중인 블록이 하나뿐이면 그 블록을 반환한다. 여러 블록이 사용 중이면 메모리 매니저에서 더 큰 버퍼를 가져온다. 이 큰 버퍼들도 크기별로 나뉘어 풀링된다 — **청크 크기(기본 1 MB)의 배수**다."

```csharp
static RecyclableMemoryStreamManager manager =
       new RecyclableMemoryStreamManager(new RecyclableMemoryStreamManager.Options(
                                 blockSize: 128 * 1024,
                                 largeBufferMultiple: 1024 * 1024,
                                 maximumBufferSize: 128 * 1024 * 1024,
                                 maximumSmallPoolFreeBytes: 0,
                                 maximumLargePoolFreeBytes: 0));

public string SerializeXmlWithRecyclableMemoryStream<T>(T obj)
{
   using var ms = manager.GetStream();               // 풀에서 빌린다
   using var xw = XmlWriter.Create(ms, XmlWriterSettings);
   var serializer = new DataContractSerializer(obj.GetType()); // 캐시할 수 있다!
   serializer.WriteObject(xw, obj);
   xw.Flush();
   ms.Seek(0, SeekOrigin.Begin);
   return new StreamReader(ms).ReadToEnd();
}
```

| 매개변수 | 의미 |
|---|---|
| `blockSize` | 풀링되는 각 블록의 크기 |
| `largeBufferMultiple` | 각 대형 버퍼는 이 값의 배수 크기를 갖는다 |
| `maximumBufferSize` | 이 임계값보다 큰 버퍼는 풀링되지 않는다 |

`GetStream`이 돌려주는 스트림은 **`Dispose` 시 메모리를 풀에 반납하도록** `IDisposable`을 구현한다. 모니터링용 ETW 공급자는 `Microsoft-IO-RecyclableMemoryStream`이며, **`MemoryStreamOverCapacity` 이벤트**가 최대 버퍼 크기를 넘는 요청을 알려 준다.

> **⚠️ 이 ETW 공급자는 이름이 아니라 GUID로 활성화해야 한다**
>
> PerfView의 Additional Provider로 추가할 때 **`Microsoft-IO-RecyclableMemoryStream`이라는 이름이 아니라 GUID `B80CD4E4-890E-468D-9CBA-90EB7C82DFC7`로** 활성화해야 한다. 이름으로 넣으면 조용히 아무 이벤트도 수집되지 않는다.

> **📌 스트림을 많이 쓴다면 `System.IO.Pipelines`도 보라**
>
> 스트림을 집중적으로 사용한다면 `System.IO.Pipelines` API도 고려할 만하다. 스트림보다 훨씬 효율적인 대안이며 할당이 더 적다. 그 기반이 되는 `Memory<T>`와 `IMemoryOwner<T>`는 68.6절에서 다룬다.

**오브젝트 풀** — 컬렉션과 마찬가지로, 어떤 타입의 객체를 아주 많이 쓴다면 그 타입의 풀을 고려한다. 다만 **객체를 잔뜩 만들고 곧 버리는 것 자체는 세대 가설에 부합한다.** GC가 세대 0에서 빠르게 치울 것이므로 그냥 괜찮을 수도 있다. 풀링을 고려해야 하는 경우는 셋이다.

1. **CPU 사이클 하나가 중요한 핫 패스**에서 객체가 할당될 때. 할당(특히 느린 경로)을 피하고 더 안정적인 메커니즘을 제공하는 것이 이득이 된다. 잘 작성된 오브젝트 풀은 CPU 캐시를 잘 활용하므로 풀링된 객체 조작이 매우 빠를 수 있다.
2. **객체 초기화 비용이 클 때.** 필드 초기화가 아주 복잡하다면 계속 새로 만들고 싶지 않을 것이다.
3. **객체 수명이 짧지만 세대 1이나 2로 승격될 만큼은 긴 경우.** GC가 최적으로 동작하려면 객체는 두 종류만 있는 것이 좋다 — **세대 0에서 빨리 죽는 것**과 **세대 2에서 오래 사는 것**. 최악은 **세대 2로 승격될 만큼만 살고 직후에 죽는 것**이며, 이를 **중년기 위기(mid-life crisis)** 라 한다. 오브젝트 풀링은 그 객체들의 수명을 재사용으로 연장해서 이 문제를 해결한다.

> **⚠️ 좋은 오브젝트 풀을 쓰는 것은 사소하지 않다**
>
> 단일 스레드 환경이라면 쉽다. 하지만 **동기화 오버헤드 없이 스레드 안전한 오브젝트 풀을 만드는 것은 쉽지 않다.** 많은 순진한 구현이 **원래의 객체 할당보다 성능을 더 해친다.** 직접 만들지 말고 `Microsoft.Extensions.ObjectPool` NuGet 패키지를 써라. 사용법이 간단하면서 확장성이 좋다.

```csharp
public class MyObject : IResettable
{
    public byte[] Buffer { get; set; }

    public bool TryReset()
    {
        Array.Clear(Buffer);   // 풀에 반납될 때 버퍼를 비운다
        return true;
    }
}

private static ObjectPool<MyObject> _pool = ObjectPool.Create<MyObject>();

public static void DoSomeWork()
{
    MyObject instance = _pool.Get();
    // 작업 수행
    _pool.Return(instance);
}
```

풀링 대상 객체는 선택적으로 `IResettable`을 구현할 수 있다. 유일한 메서드 `TryReset`이 **반납 시점에 호출되어** 인스턴스를 재사용 가능한 상태로 준비한다. `IPooledObjectPolicy<T>` 인터페이스로 커스텀 정책(새 인스턴스를 어떻게 만드는지, 어떤 조건에서 반납을 허용하는지)을 줄 수도 있다. 객체가 `IDisposable`이면 **풀이 가득 차서 인스턴스가 폐기될 때 `Dispose`가 자동 호출된다.**

### 이 장이 남기는 세 가지 규칙

#### 규칙 14 — 핫 패스에서 힙 할당을 피하라

**근거**: .NET에서 할당은 싸다고들 한다. 그러나 이 장이 보여 준 대로 항상 그런 것은 아니다. 할당의 잠재 비용을 인지해야 한다. 그 비용이 유의미한지 아닌지는 **당신의 성능 맥락**이 결정한다. 다만 할당은 **메모리 트래픽 발생, 운영체제와의 통신, 심지어 가비지 컬렉션 트리거**를 의미한다는 점을 기억하라. 객체를 많이 할당할수록 GC에 일을 더 준다. 따라서 성능이 매우 중요한 코드에서 최선의 최적화는 **할당을 피하는 것**이다.

**적용법**: 할당이 일어나는 시나리오만큼이나 회피법도 많다. 이 장의 63.9절과 63.10절이 그 목록이다. 어떤 할당은 명시적이다 — 당신이 온전히 인지하고 있다. 그래도 오브젝트 풀이나 값 타입으로 없애고 싶을 수 있다. 어떤 할당은 숨어 있다 — 여러 라이브러리와 기법이 당신도 모르게 만들어 낸다. 피하려면 **먼저 식별해야 한다.** 가장 흔한 숨은 할당 출처를 익혀서 코드에서 빠르게 알아볼 수 있어야 한다. 사소하지 않은 것들은 진단 도구나 IDE 확장(Visual Studio의 **Clr Heap Allocation Analyzer** 등)으로 추적하라.

**관련 시나리오**: 이 장의 할당 추적 절차, Azure Functions 사례.

#### 규칙 15 — 과도한 UOH 할당을 피하라

**근거**: .NET에서 할당이 늘 싸지 않다면, **대형 객체 힙에서의 할당은 더욱 비싸다.** LOH 할당이 드물다는 가정과 크기가 크다는 사실이 "미리 공간을 준비해 두지 않는다"는 설계 결정을 낳았다. 그 결과 LOH 객체 할당은 **메모리를 0으로 채우는 비용이 지배할 수 있다.** 정말 큰 객체를 자주 쓴다면 재사용 가능한 객체 풀을 관리하는 것이 좋다. 메모리 사용이 안정되고, 할당 비용뿐 아니라 GC의 일도 조금 줄어든다.

**적용법**: 큰 객체를 자주 할당한다는 것은 대개 **정말 필요해서**이므로 그 할당을 그냥 없앨 수는 없다. 값 타입으로 대체하는 것도 스택 공간 한계와 복사 비용 때문에 거의 불가능하다. 최선의 해법은 **풀링 메커니즘**이다 — 이 장의 `ArrayPool`, `RecyclableMemoryStream`, 오브젝트 풀 항목을 보라.

#### 규칙 16 — 적절할 때 스택에 할당하라

**근거**: .NET에서 클래스는 근본적인 데이터 타입이다. C#을 배우는 순간부터 클래스가 기본 building block이었다. "자료 구조"라고 생각하면 즉시 "클래스"를 떠올린다. 개발할 때 클래스를 만들고 쓰는 것이 기본 결정이다. 반면 구조체는 대개 초반에 배우고 잊어버리는 이국적인 무언가로 남는다. 낯설고 이해하기 어려워 보인다. 그러나 구조체는 정말 가치 있는 것들을 준다 — **더 나은 메모리 지역성, 힙 할당 회피, 컴파일러와 JIT의 강력한 최적화 가능성.**

**적용법**: 구조체를 조금 더 배워서 일상 도구함에 넣어라. 새 기능을 구현할 때 자문하라 — **이 메서드가 정말 클래스를 써야 하나, 단순한 구조체면 충분한가?** 객체 컬렉션이 필요한가, 작은 구조체 배열이면 충분한가? **구조체 복사를 두려워하지 마라** — 점점 강력해지는 C#의 참조 전달 기능들(`ref`, `in`, `ref readonly`, `ref` 지역 변수)을 쓰면 된다. 물론 단순한 것을 과잉 설계하지는 마라. **자주 실행되고 체감 성능이나 리소스 사용에 큰 영향을 주는, 성능이 중요한 코드 부분에서만** 이렇게 하라.

## 이 장의 요약

- **할당의 빠른 경로는 어셈블리 명령 예닐곱 개다.** 스레드마다 자기 할당 컨텍스트(TLS에 보관)를 갖고, `alloc_ptr`을 밀고 `alloc_limit`과 비교하는 것이 전부다. 락도 시스템 호출도 없다. "할당은 싸다"는 말의 출처가 정확히 이 코드다.
- **미리 0으로 채워 둔 덕분에 객체 초기화가 사실상 공짜다.** 대신 그 준비 비용은 할당 퀀텀(기본 8 kB, 1,024~8,096바이트 사이에서 동적 조정) 단위로 느린 경로가 지불한다. 세그먼트 커밋은 16페이지(약 64 kB)씩 별도로 일어난다.
- **느린 경로는 GC를 부르지 않아도 이미 비싸다.** 프리 리스트 순회, 페이지 커밋, 0 채우기가 벌어진다. 프리 리스트는 버킷 기반이며 세대 0·1은 버킷 하나, 세대 2는 12개, LOH는 7개, POH는 19개다. 빈 공간은 힙 위에 "free object"라는 1바이트 요소 배열로 심어진다.
- **LOH·POH(UOH)에는 빠른 경로 자체가 없다.** 항상 프리 리스트 → 커밋 → 예약 순으로 자리를 찾고, **비용의 대부분은 메모리를 0으로 채우는 시간**이다. 수 MB 객체 하나에 수십 밀리초가 걸릴 수 있다.
- **GC는 자리가 없어서가 아니라 예산이 소진되어 돈다.** 남은 예산은 할당 컨텍스트가 잡힐 때마다 차감되고, 음수가 되면 그 세대의 GC가 트리거된다. 세대 0 최소 예산은 CPU 캐시 크기에 연동되며(16 MB L3 기준 워크스테이션 8 MB, 서버 10 MB), 최대는 8~200 MB 범위에서 ephemeral 세그먼트 크기를 따른다. 예산은 **생존율에 따라 매 GC마다 재계산된다.**
- **서버 GC는 힙을 논리 코어에 고정 배정하고, 불균형이 감지되면 느린 경로에서 스레드의 힙을 재배정한다.** 그때 OS에 스레드 이동까지 요청하는데, 이 부분은 **Windows에서만** 동작한다(`SetThreadIdealProcessorEx`).
- **`stackalloc`은 0으로 채워지지 않고, 실패하면 잡을 수 없는 `StackOverflowException`이다.** 실무 기준은 1 kB 이하이며, 크기가 런타임 값이면 반드시 상한 분기를 넣는다. 루프와 재귀 안에서는 쓰지 않는다.
- **`OutOfMemoryException`은 GC가 이미 여러 번 돈 뒤의 마지막 결정이다.** 수동 `GC.Collect()`는 도움이 되지 않으며(LOH 압축은 예외), **free RAM이 남아 있는 것이 정상이다.** 원인은 가상 주소 공간 예약 실패 또는 커밋 실패다.
- **숨은 할당은 아홉 갈래다** — 델리게이트, 클로저(디스플레이 클래스), 박싱(특히 인터페이스로 쓰인 열거자), `yield return` 반복자, `params` 배열, 문자열 연결·포매팅, 인코딩 변환 재시도, `async` 상태 기계와 `Task`, 그리고 LINQ의 델리게이트·익명 타입·반복자(48~56바이트). **IL이나 디컴파일 결과에서 `newobj`와 `box`를 찾는 것이 유일하게 확실한 검증법이다.**
- **회피 도구는 이미 다 있다** — 구조체와 `ValueTuple`, `stackalloc`+`Span<T>`, `ArrayPool<T>`, `RecyclableMemoryStream`, 오브젝트 풀, `ValueTask<T>`. 각각의 함정도 명확하다. 그리고 **먼저 측정하지 않고 적용하면 거의 항상 손해다.**

## 연습 문제

1. 콘솔 애플리케이션에서 `GC.GetAllocatedBytesForCurrentThread()`를 이용해 다음 세 줄이 각각 몇 바이트를 할당하는지 측정하라. `string.Format("{0}", 42)`, `$"{42}"`, `string.Create(2, 42, (s, v) => v.TryFormat(s, out _))`. 이 장의 표(63.9절)와 자릿수가 맞는지 확인하고, 맞지 않는다면 대상 프레임워크 버전을 바꿔 가며 다시 측정하라.

2. `[MemoryDiagnoser]`를 붙인 BenchmarkDotNet 프로젝트를 만들어, `void Print(IEnumerable<int> list)`와 `void Print(List<int> list)`에 같은 `List<int>`를 넘겨 `foreach`로 순회하는 두 벤치마크를 비교하라. Allocated 열의 차이가 몇 바이트인가? 그 값이 `List<int>.Enumerator` 구조체 크기와 어떤 관계인지 설명하라(54.3절의 최소 객체 크기를 함께 고려하라).

3. `dotnet-counters monitor -p <pid>`로 `Gen 0 GC Budget (MB)`와 `Allocation Rate (B / 1 sec)`를 동시에 관찰하면서, 임시 객체를 계속 만드는 루프와 대부분의 객체를 정적 리스트에 붙잡아 두는 루프를 각각 돌려라. **두 경우에 예산이 어떻게 다르게 움직이는지** 기록하고, 63.6절의 생존율-예산 그래프로 설명하라.

4. 크기를 인자로 받아 `Span<byte> buffer = stackalloc byte[size];`를 수행하는 메서드를 작성하고, `size`를 1 kB에서 시작해 두 배씩 늘려 가며 호출하라. 어느 값에서 프로세스가 죽는가? 그다음 63.7절의 삼항 연산자 폴백 패턴을 적용하고 같은 실험을 반복하라. `try`/`catch`로 첫 번째 버전의 죽음을 막을 수 있는지도 확인하라.

5. `WhereArrayIterator`와 `WhereSelectArrayIterator`를 직접 관찰하라. `inputs.Where(...).Select(...).ToArray()` 코드를 `dotnet-trace collect --profile gc-verbose`로 추적하고 PerfView의 **GC Heap Alloc Ignore Free (Coarse Sampling) Stacks** 에서 타입 이름과 크기를 확인하라. 같은 로직을 `foreach` 루프로 다시 써서 할당 목록이 어떻게 줄어드는지 비교하라.

6. `List<object>`를 용량 지정 없이 채워, 내부 배열이 LOH로 넘어가는 순간을 잡아라. `GC.GetGeneration(field)`로 내부 배열의 세대를 확인할 수는 없으므로, `GC.CollectionCount(2)`와 `dotnet-counters`의 `LOH Size (B)`를 관찰하는 방식으로 접근하라. 그다음 `new List<object>(capacity)`로 바꿔 LOH 크기 변화가 사라지는 것을 확인하라.

7. `ArrayPool<byte>.Shared`를 쓰면서 의도적으로 `Return`을 호출하지 않는 코드를 작성하고, PerfView에서 `*System.Buffers.ArrayPoolEventSource:::@StacksEnabled=true`로 이벤트를 수집하라. `BufferAllocated` 이벤트의 사유가 `PoolExhausted`로 바뀌는 지점을 찾고, 그때의 처리량 변화를 측정하라. **오류 없이 조용히 느려지는 것**을 눈으로 확인하는 것이 목적이다.
