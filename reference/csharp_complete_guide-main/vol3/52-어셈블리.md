# 52장. 어셈블리

> **이 장의 위치** — Part X「CLR 내부 구조」의 첫 장이다. 3장에서 "소스가 IL이 되고 어셈블리로 묶인다"고만 말하고 넘어간 것을, 여기서 끝까지 판다. 어셈블리는 .NET의 **배포 단위**이자 **타입 해석의 경계**이고, 런타임이 "이 타입이 뭐지"라고 물을 때 답을 찾아가는 출발점이다. 이 장을 이해하지 못하면 54장(타입 시스템의 런타임 표현)도, 57장(리플렉션)도 공중에 뜬다.
>
> **선수 지식** — 3장(첫 프로그램이 실행되기까지), 4장(프로젝트와 대상 프레임워크), 12장(네임스페이스)
>
> **이 장에서 다루지 않는 것** — 리소스와 위성 어셈블리는 53장에서, 메타데이터를 리플렉션으로 읽는 방법은 57장에서, 동적으로 어셈블리를 만드는 방법은 58장에서 다룬다.

## 52.1 어셈블리 안에는 무엇이 있는가

어셈블리는 .NET의 기본 배포 단위이자 모든 타입의 컨테이너다. 컴파일된 타입의 IL 코드, 런타임 리소스, 그리고 버전 관리와 다른 어셈블리 참조를 돕는 정보를 담는다. 동시에 **타입 해석의 경계**를 정의한다.

.NET에서 어셈블리는 `.dll` 확장자를 가진 단일 파일이다.

> **📌 .NET과 .NET Framework의 차이**
>
> .NET에서 실행 가능한 애플리케이션을 빌드하면 파일이 **두 개** 나온다.
>
> - `MyApp.dll` — 어셈블리
> - `MyApp.exe` — 대상 플랫폼에 맞는 실행 런처
>
> .NET Framework은 다르다. PE(portable executable) 어셈블리 하나를 만들고, 이 `.exe` 파일이 어셈블리와 애플리케이션 런처 역할을 **동시에** 한다. PE 하나가 32비트와 64비트 Windows를 동시에 대상으로 삼을 수 있었다.
>
> 이 차이는 사소해 보이지만 실무에서 자주 헷갈린다. .NET 앱의 `bin` 폴더에서 `.exe`를 ILSpy로 열면 아무것도 안 나온다. 열어야 할 것은 `.dll`이다.

### 어셈블리를 구성하는 네 가지

어셈블리는 다음 네 종류를 담는다.

| 구성 요소 | 역할 | 필수 여부 |
|---|---|---|
| **어셈블리 매니페스트** | CLR에게 어셈블리 이름·버전·참조하는 다른 어셈블리를 알려준다 | **필수** |
| **애플리케이션 매니페스트** | OS에게 배포 방식과 관리자 권한 필요 여부를 알려준다 | 선택 |
| **컴파일된 타입** | 어셈블리 안에 정의된 타입의 IL 코드와 메타데이터 | 사실상 필수 |
| **리소스** | 이미지, 지역화 가능한 텍스트 등 어셈블리에 임베드된 데이터 | 선택 |

이 중 **어셈블리 매니페스트만이 유일한 필수 항목**이다. 다만 컴파일된 타입이 하나도 없는 어셈블리는 실무에서 거의 없다 — 예외는 **리소스 어셈블리**(위성 어셈블리)로, 이건 53장에서 다룬다.

이 장에서 주로 쓰는 타입은 다음 네임스페이스에 있다.

```csharp
using System.Reflection;        // Assembly, AssemblyName
using System.Runtime.Loader;    // AssemblyLoadContext, AssemblyDependencyResolver
using System.Resources;         // ResourceManager (53장)
using System.Globalization;     // CultureInfo (53장)
```

## 52.2 어셈블리 매니페스트와 메타데이터 테이블 구조

### 매니페스트의 두 가지 역할

어셈블리 매니페스트는 두 가지 일을 한다.

1. **관리 호스팅 환경(CLR)에게 어셈블리를 설명한다.**
2. **어셈블리 안의 모듈·타입·리소스에 대한 디렉터리 역할을 한다.**

이 둘 덕분에 어셈블리는 **자기 설명적(self-describing)** 이다. 소비자는 추가 파일 없이 어셈블리 하나만으로 그 안의 모든 데이터·타입·함수를 발견할 수 있다. COM 시대에 레지스트리를 뒤져야 했던 것과 대비된다. 이 자기 설명성이야말로 .NET 애플리케이션이 Windows 레지스트리 없이도 다른 OS에서 돌아갈 수 있는 이유이고, 한 머신에서 여러 .NET 버전이 공존할 수 있는 이유다.

> **📌 매니페스트는 만드는 게 아니라 생기는 것**
>
> 매니페스트를 어셈블리에 "추가"하는 작업 같은 건 없다. 컴파일 과정의 일부로 자동으로 임베드된다.

### 매니페스트가 저장하는 것

기능적으로 의미 있는 데이터부터 보자.

- 어셈블리의 **단순 이름(simple name)**
- **버전 번호** (`AssemblyVersion`)
- 강력한 이름이 있다면, **공개 키**와 어셈블리의 **서명된 해시**
- **참조하는 어셈블리 목록** — 각각의 버전과 공개 키 포함
- 어셈블리 안에 **정의된 타입 목록**
- 위성 어셈블리라면 **대상 문화권** (`AssemblyCulture`)

정보성(informational) 데이터도 저장할 수 있다.

- 제목과 설명 (`AssemblyTitle`, `AssemblyDescription`)
- 회사와 저작권 정보 (`AssemblyCompany`, `AssemblyCopyright`)
- 표시용 버전 (`AssemblyInformationalVersion`)
- 커스텀 데이터를 위한 추가 특성

이 데이터 중 일부는 컴파일러 인자에서 온다(참조 어셈블리 목록, 서명용 공개 키). 나머지는 괄호 안에 표시한 **어셈블리 특성**에서 온다.

### 어셈블리 특성 지정하기

Visual Studio에서는 프로젝트 속성 페이지의 Package 탭에서 흔히 쓰는 특성을 지정할 수 있고, 그 설정은 `.csproj`에 들어간다.

```xml
<PropertyGroup>
  <AssemblyVersion>2.5.6.7</AssemblyVersion>
  <FileVersion>2.5.6.7</FileVersion>
  <InformationalVersion>2.5.6 Beta 2</InformationalVersion>
  <Company>Contoso</Company>
  <Copyright>© 2026 Contoso</Copyright>
</PropertyGroup>
```

Package 탭이 지원하지 않는 특성이거나 `.csproj`를 쓰지 않는다면 소스 코드에서 지정한다. 관행적으로 `AssemblyInfo.cs`라는 파일에 모은다. 이 파일은 `using` 문과 어셈블리 특성 선언만 담는다.

```csharp
using System.Runtime.CompilerServices;

// internal 타입을 단위 테스트 프로젝트에 노출한다 (17.2절 참조)
[assembly: InternalsVisibleTo("MyUnitTestProject")]
```

> **⚠️ SDK 스타일 프로젝트의 함정**
>
> SDK 스타일 프로젝트는 기본적으로 `AssemblyVersion`, `AssemblyCompany` 같은 특성을 **자동 생성**한다. `AssemblyInfo.cs`에 같은 특성을 수동으로 쓰면 "특성이 중복 정의되었다"는 컴파일 오류(CS0579)가 난다. 수동으로 관리하고 싶다면 다음을 꺼야 한다.
>
> ```xml
> <GenerateAssemblyInfo>false</GenerateAssemblyInfo>
> ```

### 매니페스트 메타데이터 테이블

여기서 한 층 더 내려가자. 매니페스트는 추상적인 개념이 아니라 **구체적인 메타데이터 테이블 묶음**이다. 관리 모듈을 어셈블리로 만들어주는 테이블은 다음 네 개다.

| 테이블 | 내용 |
|---|---|
| **AssemblyDef** | 이 모듈이 어셈블리를 식별한다면 항목 하나. 어셈블리 이름(경로·확장자 제외), 버전(major/minor/build/revision), 문화권, 플래그, 해시 알고리즘, 게시자의 **전체 공개 키**(null일 수 있음) |
| **FileDef** | 어셈블리에 속한 각 PE·리소스 파일마다 항목 하나. 파일 이름과 확장자(경로 제외), 해시 값, 플래그. 매니페스트를 담은 파일 자신은 AssemblyDef에 있으므로 제외 — 단일 파일 어셈블리라면 이 테이블은 **비어 있다** |
| **ManifestResourceDef** | 어셈블리에 속한 각 리소스마다 항목 하나. 리소스 이름, 플래그(어셈블리 밖에서 보이면 public, 아니면 private), 그 리소스를 담은 파일을 가리키는 FileDef 인덱스. 리소스가 독립 파일이 아니라면 PE 파일 안의 스트림이며, 이 경우 항목에 PE 파일 내 시작 오프셋도 포함 |
| **ExportedTypesDef** | 어셈블리의 모든 PE 모듈에서 내보내는 public 타입마다 항목 하나. 타입 이름, 그 타입을 구현한 파일을 가리키는 FileDef 인덱스, TypeDef 인덱스. **파일 크기를 아끼기 위해**, 매니페스트를 담은 파일이 내보내는 타입은 이 테이블에 반복 기재하지 않는다(TypeDef 테이블로 이미 알 수 있으므로) |

여기에 하나가 더 있다.

**AssemblyRef 테이블** — 매니페스트를 담은 파일에는 AssemblyRef 테이블도 있다. 이 어셈블리의 **모든 파일이 참조하는 모든 어셈블리**의 항목이 들어간다. 덕분에 도구는 매니페스트만 열어보고도 참조 어셈블리 집합을 알 수 있다. 다른 파일을 열 필요가 없다. 이것도 자기 설명성을 위한 설계다.

### 공개 키 토큰이 존재하는 이유

AssemblyRef 항목에 참조 어셈블리의 **전체 공개 키**를 넣는다고 생각해보자. 공개 키는 아주 큰 수이고(기본 RSA 키 기준 공개 키 blob은 160바이트다), 어셈블리 하나가 수십 개를 참조할 수 있다. 결과 파일 크기의 상당 부분이 공개 키로 채워진다.

그래서 Microsoft는 공개 키를 해시하고 **해시 값의 마지막 8바이트**만 취한다. 이 축소된 값이 **공개 키 토큰(public key token)** 이고, AssemblyRef 테이블에는 이것이 저장된다.

```text
AssemblyRef #1 (23000001)
-------------------------------------------------------
    Token: 0x23000001
    Public Key or Token: b7 7a 5c 56 19 34 e0 89
    Name: mscorlib
    Version: 4.0.0.0
    Locale: <null>
```

> **⚠️ ILDasm은 Culture를 "Locale"이라고 잘못 쓴다**
>
> 위 덤프의 `Locale: <null>`은 사실 **Culture**를 뜻한다. ILDasm이 용어를 잘못 쓰고 있는 것이다. `<null>`은 `Culture=neutral`에 해당한다.

같은 어셈블리의 AssemblyDef를 보면 대조가 명확해진다.

```text
Assembly
-------------------------------------------------------
    Token: 0x20000001
    Name : SomeClassLibrary
    Public Key    :
    Hash Algorithm : 0x00008004
    Version: 3.0.0.0
    Locale: <null>
```

이건 다음과 같다.

```text
"SomeClassLibrary, Version=3.0.0.0, Culture=neutral, PublicKeyToken=null"
```

`Public Key` 필드가 **비어 있다.** 이 어셈블리가 공개/개인 키 쌍으로 서명되지 않았기 때문이며, 이런 어셈블리를 **약한 이름(weakly named) 어셈블리**라고 한다. `sn.exe`로 키 파일을 만들어 `/keyfile` 스위치로 컴파일했다면 `Public Key` 필드 뒤에 바이트가 나타나고 강력한 이름 어셈블리가 된다.

정리하면 이렇다.

- **AssemblyDef** (나 자신) → **전체 공개 키** 저장. 파일 변조 여부를 검사하려면 전체 키가 필요하다.
- **AssemblyRef** (내가 참조하는 것) → **공개 키 토큰** 저장. 식별만 하면 되므로 8바이트로 충분하다.

> **⚠️ 공개 키 토큰은 신뢰 판단에 쓰이지 않는다**
>
> CLR은 보안이나 신뢰 결정을 내릴 때 공개 키 토큰을 **절대 사용하지 않는다**. 여러 개의 서로 다른 공개 키가 같은 토큰으로 해시될 수 있기 때문이다. 토큰은 식별자일 뿐 인증 수단이 아니다.

### 매니페스트를 직접 보기

`ildasm.exe`로 매니페스트 내용을 볼 수 있다.

```text
ildasm MyLibrary.dll
```

트리에서 `MANIFEST`를 더블클릭하면 다음과 같은 것이 보인다.

```text
.assembly extern System.Runtime
{
  .publickeytoken = (B0 3F 5F 7F 11 D5 0A 3A )
  .ver 8:0:0:0
}
.assembly MyLibrary
{
  .custom instance void [System.Runtime]System.Runtime.Versioning
          .TargetFrameworkAttribute::.ctor(string) = ( ... )
  .ver 1:0:0:0
}
.module MyLibrary.dll
```

같은 일을 코드로 하는 방법은 57장에서 다룬다.

## 52.3 애플리케이션 매니페스트(Windows)와 모듈

### 애플리케이션 매니페스트

애플리케이션 매니페스트는 **OS에게** 어셈블리에 대한 정보를 전달하는 XML 파일이다. 어셈블리 매니페스트가 CLR을 위한 것이라면, 이건 Windows를 위한 것이다.

빌드 과정에서 시작 실행 파일에 Win32 리소스로 임베드된다. 존재한다면 **CLR이 어셈블리를 로드하기 전에** 읽히고 처리되며, Windows가 애플리케이션 프로세스를 어떻게 시작할지에 영향을 줄 수 있다.

루트 요소는 `assembly`이고 XML 네임스페이스는 `urn:schemas-microsoft-com:asm.v1`이다.

```xml
<?xml version="1.0" encoding="utf-8"?>
<assembly manifestVersion="1.0" xmlns="urn:schemas-microsoft-com:asm.v1">
  <!-- 매니페스트 내용 -->
</assembly>
```

다음은 OS에게 관리자 권한 상승을 요청하는 매니페스트다.

```xml
<?xml version="1.0" encoding="utf-8"?>
<assembly manifestVersion="1.0" xmlns="urn:schemas-microsoft-com:asm.v1">
  <trustInfo xmlns="urn:schemas-microsoft-com:asm.v2">
    <security>
      <requestedPrivileges>
        <requestedExecutionLevel level="requireAdministrator" />
      </requestedPrivileges>
    </security>
  </trustInfo>
</assembly>
```

Visual Studio에서는 프로젝트 우클릭 → 추가 → 새 항목 → **응용 프로그램 매니페스트 파일**로 추가한다. 빌드하면 출력 어셈블리에 임베드된다.

> **📌 ildasm은 애플리케이션 매니페스트를 보지 못한다**
>
> `ildasm.exe`는 임베드된 애플리케이션 매니페스트의 존재를 감지하지 못한다. Visual Studio는 솔루션 탐색기에서 어셈블리를 더블클릭하면 임베드된 애플리케이션 매니페스트가 있는지 알려준다.

UWP 애플리케이션은 훨씬 정교한 매니페스트를 `Package.appxmanifest` 파일에 둔다. 여기에는 프로그램의 **기능(capability)** 선언이 포함되고, 이것이 OS가 부여하는 권한을 결정한다.

### 모듈 — 어셈블리와 파일 사이의 한 층

어셈블리의 내용은 사실 **모듈(module)** 이라는 중간 컨테이너에 담긴다. 모듈은 어셈블리 내용을 담은 파일에 대응한다.

왜 이런 층이 하나 더 있을까? 어셈블리가 **여러 파일에 걸칠 수 있게** 하기 위해서다. 이 기능은 .NET Framework에는 있었고 .NET 5+ / .NET Core에는 없다.

```text
┌─────────────────────────────────────┐
│           어셈블리                   │
│  ┌───────────────────────────────┐  │
│  │      모듈 (MyLib.dll)          │  │
│  │  ┌─────────┐  ┌────────────┐  │  │
│  │  │ 매니페스트│  │ IL + 메타데이터│  │  │
│  │  └─────────┘  └────────────┘  │  │
│  └───────────────────────────────┘  │
└─────────────────────────────────────┘
        단일 파일 어셈블리 (.NET)
```

.NET이 다중 파일 어셈블리를 지원하지 않더라도, 모듈이라는 추가 층은 알아둬야 한다. 주된 시나리오는 **리플렉션**이다(57.10절, 58.6절).

#### 다중 파일 어셈블리 — .NET Framework의 유산

.NET Framework 시대에 다중 파일 어셈블리를 쓰는 이유는 세 가지였다.

1. **점진적 다운로드.** 자주 쓰지 않는 타입을 별도 파일에 두면, 클라이언트가 그 타입을 쓰지 않는 한 파일을 다운로드하지 않는다. 구매·설치하는 애플리케이션의 **부분적(piecemeal) 패키징과 배포**도 가능해진다. 다중 파일 어셈블리의 다운로드는 구성 파일의 `codeBase` 요소로 설정하며, CLR은 파일을 로드할 때 먼저 머신의 다운로드 캐시를 확인하고 없으면 URL이 가리키는 위치에서 캐시로 내려받는다. 그래도 찾지 못하면 `FileNotFoundException`을 던진다.
2. **리소스·데이터 파일 추가.** 보험 계산 타입이 계리 테이블을 필요로 한다고 하자. 테이블을 소스에 박아 넣는 대신 Assembly Linker(`AL.exe`) 같은 도구로 데이터 파일을 어셈블리의 일부로 만들 수 있다. 형식은 무엇이든 좋다 — 애플리케이션이 파싱할 줄만 알면 된다.
3. **여러 언어로 구현한 타입을 하나로.** 일부 타입은 C#으로, 일부는 Visual Basic으로 작성하고 도구로 모듈들을 하나의 어셈블리로 합칠 수 있다. 사용자는 서로 다른 언어가 쓰였다는 사실조차 모른다.

빌드 방법도 알아두자. 자주 쓰지 않는 타입을 `RUT.cs`에, 자주 쓰는 타입을 `FUT.cs`에 두었다면,

```text
csc /t:module RUT.cs
csc /out:MultiFileLibrary.dll /t:library /addmodule:RUT.netmodule FUT.cs
```

`/t:module`은 매니페스트 메타데이터 테이블이 **없는** PE 파일을 만든다. 항상 DLL PE 파일이고 기본 확장자는 `.netmodule`이다. CLR은 이 파일을 단독으로 로드할 수 없다. `/addmodule` 스위치는 컴파일러에게 그 파일을 어셈블리의 일부로 간주하라고 지시한다 — 구체적으로는 FileDef 테이블에 파일을 추가하고, 그 파일이 내보내는 public 타입을 ExportedTypesDef 테이블에 추가한다.

매니페스트를 담을 PE 파일은 **하나를 골라야** 하고, 원한다면 **매니페스트만 담은 별도 PE 파일**을 만들 수도 있다.

Visual Studio IDE는 다중 파일 어셈블리 생성을 지원하지 않는다. 만들려면 명령행 도구를 써야 한다.

> **📌 개별 파일에는 소속 정보가 없다**
>
> 매니페스트를 담은 파일의 메타데이터는 **어떤 파일들이 이 어셈블리에 속하는지** 알려준다. 그러나 개별 파일 자신은 **"내가 어느 어셈블리에 속한다"는 메타데이터를 갖지 않는다.** 이 비대칭이 매니페스트 파일을 특별하게 만든다.

> **📌 빌드할 때와 실행할 때가 다르다**
>
> 다중 파일 어셈블리를 소비하는 쪽은 `/r:MultiFileLibrary.dll`로 컴파일한다. 이때 **참조 어셈블리의 모든 파일이 존재해야** 한다 — 없으면 `fatal error CS0009`가 난다.
>
> 그러나 **실행 시에는 모든 파일이 필요하지 않다.** CLR은 아직 로드되지 않은 파일의 타입을 참조하는 메서드가 **처음 호출될 때** 비로소 그 파일을 로드한다. 이 지연 로딩이 점진적 다운로드 시나리오를 가능하게 하는 실제 메커니즘이다.

AL.exe(Assembly Linker)는 여기서 말한 용도 외에도 **서로 다른 컴파일러가 만든 모듈을 결합**하거나 **리소스만 담은 위성 어셈블리를 생성**하는 데 쓴다(53장).

> **💡 성능 관점**
>
> 버전 번호와 보안 설정을 공유할 수 있는 타입이 여럿이라면, **파일을 나누지 말고 한 파일에 모으는 편이 낫다.** 이유는 성능이다. 파일·어셈블리를 로드하려면 CLR과 OS가 어셈블리를 찾고, 로드하고, 초기화하는 시간이 든다. 로드하는 파일이 적을수록 working set이 줄고 프로세스 주소 공간의 단편화도 줄어든다. 게다가 `NGen.exe`(당시의 AOT 컴파일러)는 큰 파일을 처리할 때 더 나은 최적화를 할 수 있다.
>
> 이 원칙은 .NET에서도 유효하다. 프로젝트를 잘게 쪼개는 습관은 논리적 응집도를 위해서라면 좋지만, "일단 나누고 보자"는 시작 시간을 늘린다.

## 52.4 `Assembly` 클래스로 자기 자신을 들여다보기

`System.Reflection.Assembly`는 런타임에 어셈블리 메타데이터에 접근하는 관문이다.

### Assembly 객체 얻기

가장 간단한 방법은 `Type`의 `Assembly` 속성이다.

```csharp
Assembly a = typeof(Program).Assembly;
```

정적 메서드도 있다.

| 메서드 | 반환하는 것 |
|---|---|
| `Assembly.GetExecutingAssembly()` | 현재 실행 중인 함수를 정의한 타입의 어셈블리 |
| `Assembly.GetCallingAssembly()` | 현재 실행 중인 함수를 **호출한** 함수의 어셈블리 |
| `Assembly.GetEntryAssembly()` | 애플리케이션의 원래 진입 메서드를 정의한 어셈블리 |

> **⚠️ `GetExecutingAssembly()`보다 `typeof(X).Assembly`를 선호하라**
>
> `GetExecutingAssembly()`는 스택 워크가 필요해서 상대적으로 느리다. 컴파일 타임에 어떤 어셈블리인지 안다면 `typeof(X).Assembly`가 더 빠르고 명확하다.
>
> `GetCallingAssembly()`는 여기에 더해 **인라이닝에 취약하다.** JIT이 호출자를 인라이닝하면 "호출한 어셈블리"가 달라진다. 이 메서드에 의존하는 메서드에는 `[MethodImpl(MethodImplOptions.NoInlining)]`을 붙여야 한다(52.10절의 `Assembly.Load` 구현 예를 보라).
>
> `GetEntryAssembly()`는 진입점이 없는 컨텍스트(예: 네이티브 호스트가 로드한 라이브러리, 일부 테스트 러너)에서 `null`을 반환할 수 있다. 반드시 null 검사를 하라.

### Assembly의 주요 멤버

| 멤버 | 목적 | 자세히 |
|---|---|---|
| `FullName`, `GetName()` | 정규화된 이름 또는 `AssemblyName` 객체 | 52.6절 |
| `Location`, `CodeBase` | 어셈블리 파일의 위치 | 52.9절 |
| `Load`, `LoadFrom`, `LoadFile` | 어셈블리를 메모리에 수동 로드 | 52.10절, 52.13절 |
| `GetSatelliteAssembly` | 주어진 문화권의 위성 어셈블리를 찾음 | 53장 |
| `GetType`, `GetTypes` | 어셈블리에 정의된 타입 하나 또는 전부 | 57.1절 |
| `EntryPoint` | 애플리케이션의 진입 메서드를 `MethodInfo`로 | 57.5절 |
| `GetModule`, `GetModules`, `ManifestModule` | 어셈블리의 모듈 전부 또는 주 모듈 | 57.10절 |
| `GetCustomAttribute(s)` | 어셈블리의 특성 | 57.11절 |

실용적인 예를 보자. 애플리케이션이 자기 버전을 로그에 남기는 코드다.

```csharp
using System.Reflection;

var asm = typeof(Program).Assembly;
var name = asm.GetName();

Console.WriteLine($"이름:        {name.Name}");
Console.WriteLine($"어셈블리버전: {name.Version}");
Console.WriteLine($"파일버전:     {asm.GetCustomAttribute<AssemblyFileVersionAttribute>()
                                      ?.Version}");
Console.WriteLine($"표시버전:     {asm.GetCustomAttribute<AssemblyInformationalVersionAttribute>()
                                      ?.InformationalVersion}");
Console.WriteLine($"위치:        {asm.Location}");
```

> **⚠️ 단일 파일 배포에서 `Location`은 빈 문자열이다**
>
> `PublishSingleFile`로 게시하거나 스트림에서 로드한 어셈블리는 디스크상의 파일이 없으므로 `Location`이 `""`가 된다. `Location`을 기준으로 설정 파일 경로를 계산하는 코드는 단일 파일 배포에서 조용히 깨진다. 대신 `AppContext.BaseDirectory`를 써라.

## 52.5 강력한 이름과 어셈블리 서명, 지연 서명, 변조 방지

### 강력한 이름이 무엇이었나

강력한 이름을 붙인 어셈블리는 **고유한 신원(identity)** 을 갖는다. 매니페스트에 두 가지 메타데이터를 추가해서 동작한다.

1. 어셈블리 저작자에게 속하는 **고유한 수**
2. 그 고유한 수의 소유자가 이 어셈블리를 만들었음을 증명하는 **어셈블리의 서명된 해시**

이를 위해 공개/개인 키 쌍이 필요하다. 공개 키가 고유 식별 번호를 제공하고, 개인 키가 서명을 가능하게 한다.

공개 키는 어셈블리 참조의 고유성을 보장하는 데 값어치가 있다. 강력한 이름 어셈블리는 공개 키를 자기 신원에 포함시킨다.

.NET Framework에서 개인 키는 어셈블리를 변조로부터 보호했다. 개인 키가 없으면 서명을 깨뜨리지 않고 수정된 버전을 배포할 수 없다. 실무적으로 이건 어셈블리를 .NET Framework의 **전역 어셈블리 캐시(GAC)** 에 설치할 때 의미가 있었다.

> **⚠️ .NET 5+에서 강력한 이름은 훨씬 덜 중요하다**
>
> .NET Framework에서 강력한 이름은 두 가지 이유로 중요했다.
>
> 1. 어셈블리를 **전역 어셈블리 캐시(GAC)** 에 로드할 수 있게 했다.
> 2. 다른 강력한 이름 어셈블리가 **참조할 수 있게** 했다.
>
> .NET 5+와 .NET Core에서는 두 이유가 모두 사라졌다. 이 런타임들에는 GAC가 없고, 두 번째 제약도 부과하지 않는다. **서명은 검사되지 않기 때문에** .NET 5+에서 서명 자체는 거의 쓸모가 없다.
>
> 그렇다면 왜 알아야 하나? (1) 레거시 .NET Framework 코드를 유지보수할 때, (2) NuGet에 라이브러리를 배포할 때 소비자가 강력한 이름을 요구할 수 있어서, (3) 어셈블리 신원 4요소 중 하나이므로 이름 해석 규칙을 이해하는 데 필요해서다.

> **⚠️ 나중에 붙이면 신원이 바뀐다**
>
> 이미 "약한 이름"인 어셈블리에 강력한 이름을 추가하면 **신원이 바뀐다.** 즉 그 어셈블리를 참조하던 모든 것이 깨진다. 그래서 미래에 강력한 이름이 필요할 것 같다면 **처음부터** 붙여두는 편이 낫다.

강력한 이름 서명과 Authenticode 서명은 **다른 것**이다. Authenticode는 52.7절에서 다룬다.

### 강력한 이름 붙이기

먼저 `sn.exe` 유틸리티로 공개/개인 키 쌍을 생성한다.

```text
sn.exe -k MyKeyPair.snk
```

새 키 쌍이 만들어져 `MyKeyPair.snk` 파일에 저장된다.

> **⚠️ 이 파일을 잃어버리면 끝이다**
>
> 이 파일을 잃어버리면 **같은 신원으로 어셈블리를 다시 컴파일할 능력을 영구히 잃는다.** 소스 저장소가 아니라 별도의 안전한 곳에 백업하라(공개 저장소에 개인 키를 커밋하는 것도 당연히 금물이다).

> **📌 `sn.exe`는 어디에 있나**
>
> Visual Studio는 "Developer Command Prompt for VS" 바로가기를 설치한다. 이 프롬프트의 `PATH`에는 `sn.exe` 같은 개발 도구가 들어 있다.

이 파일로 어셈블리에 서명하려면 프로젝트 파일을 갱신한다.

```xml
<PropertyGroup>
  <SignAssembly>true</SignAssembly>
  <AssemblyOriginatorKeyFile>MyKeyPair.snk</AssemblyOriginatorKeyFile>
</PropertyGroup>
```

Visual Studio에서는 프로젝트 속성 → 서명 탭 → "어셈블리 서명" 체크 → `.snk` 파일 선택이다.

같은 키 쌍으로 여러 어셈블리에 서명할 수 있다. 단순 이름이 다르면 여전히 서로 다른 신원을 갖는다.

### 지연 서명 (delayed signing)

조직에서 개인 키는 스마트카드 같은 하드웨어 장치에 보관하고, 소수의 사람만 접근할 수 있게 하는 것이 보통이다. 그런데 개발자는 매일 빌드해야 한다. 이 모순을 푸는 것이 **지연 서명(delayed signing 또는 partial signing)** 이다.

지연 서명이 노리는 것은 이것이다. 공개 키만 있어도,

- 이 어셈블리를 참조하는 **다른 어셈블리가 자기 AssemblyRef 테이블에 올바른 공개 키 토큰을 기록**할 수 있다.
- 어셈블리를 **GAC에 배치**해 테스트할 수 있다.

즉 최종 서명 없이도 개발·테스트 사이클 전체가 정상적으로 돌아간다.

> **⚠️ 지연 서명 중에는 변조 방지가 전혀 없다**
>
> 지연 서명된 어셈블리는 **파일 내용이 해시되지 않고 디지털 서명도 임베드되지 않는다.** 강력한 이름이 주는 변조 방지 기능을 **전부** 잃은 상태다. 그래서 다음 2단계에서 검증을 끄는 것이고, 그래서 지연 서명된 바이너리는 절대 배포하면 안 된다. 서명 공간의 크기는 공개 키 크기로부터 결정된다.

절차는 이렇다.

**1단계 — 개발 중.** 회사의 **공개 키만** 담긴 파일을 받아서 `/keyfile`과 `/delaysign` 스위치로 컴파일한다.

```text
csc /keyfile:MyCompany.PublicKey /delaysign MyAssembly.cs
```

컴파일러는 공개 키를 AssemblyDef에 넣고, 서명이 들어갈 **공간만 예약**해둔다. 실제 서명은 비어 있다.

**2단계 — 검증 끄기.** 서명이 비어 있으므로 어셈블리는 변조된 것처럼 보인다. 그대로면 GAC 설치도, 로드도 실패한다. 그래서 이 어셈블리에 한해 무결성 검사를 건너뛰도록 시스템에 알려야 한다.

```text
sn.exe -Vr MyAssembly.dll
```

이 명령은 CLR에게 로드 시 해시 값 검사를 생략하라고 지시한다. 내부적으로는 어셈블리 신원을 다음 레지스트리 키 아래 등록한다.

```text
HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\StrongName\Verification
```

이 명령은 **머신당 한 번만** 실행하면 된다. 빌드할 때마다 할 필요는 없다.

**3단계 — 배포 전 실제 서명.** 개발과 테스트가 끝나면 회사의 개인 키로 정식 서명한다.

```text
sn.exe -Ra MyAssembly.dll MyCompany.PrivateKey
```

`-R` 계열 스위치는 파일 내용을 해시하고, 개인 키로 서명하고, 앞서 예약해둔 공간에 RSA 디지털 서명을 임베드한다.

**4단계 — 검증 되돌리기.** 개발·테스트 머신에서 이 어셈블리의 검증을 다시 켠다.

```text
sn.exe -Vu MyAssembly.dll
```

`-Vu` 대신 `-Vx`를 써도 검증 설정을 제거할 수 있다.

> **⚠️ `SN.exe`의 스위치는 대소문자를 구분한다**
>
> `-Vr`과 `-vr`은 다르다. 자주 쓰는 것들을 정리해두자.
>
> | 스위치 | 하는 일 |
> |---|---|
> | `-k <file>` | 새 공개/개인 키 쌍 생성 |
> | `-p <in> <out>` | 키 쌍 파일에서 **공개 키만** 추출 |
> | `-tp <file>` | 공개 키와 공개 키 토큰 표시 |
> | `-Vr <asm>` | 이 어셈블리의 검증 건너뛰기 등록 |
> | `-Vu` / `-Vx` | 검증 건너뛰기 해제 |
> | `-Ra <asm> <key>` | 개인 키로 최종 서명 |
> | `-Rc <asm> <container>` | CSP 컨테이너의 키로 최종 서명 |

> **⚠️ 64비트 머신에서는 64비트 유틸리티를 써라**
>
> 레지스트리를 건드리는 유틸리티는 비트 수가 맞아야 한다. 32비트 도구는 WoW64 레지스트리 리디렉션 때문에 다른 키를 건드린다.

조직은 키 쌍을 디스크 파일에 저장하지 않기 위해 **암호화 서비스 공급자(CSP)** 의 컨테이너를 쓴다. Microsoft 자신도 접근 시 하드웨어 장치에서 개인 키를 가져오는 CSP 컨테이너를 쓴다.

CSP 컨테이너를 쓰면 위 절차의 스위치가 이렇게 바뀐다.

| 파일 기반 | CSP 컨테이너 기반 |
|---|---|
| `csc /keyfile:...` | `csc /keycontainer:...` |
| `AL /keyfile:...` | `AL /keyname:...` |
| `sn -Ra ...` | `sn -Rc ...` |

> **💡 지연 서명의 또 다른 용도 — 빌드 후 처리**
>
> 난독화(obfuscation) 같은 **빌드 후 작업**이 있다면 지연 서명이 필수다. 완전 서명된 어셈블리를 난독화하면 파일 내용이 바뀌어 해시가 깨지고, 어셈블리가 변조된 것으로 간주된다. 순서는 반드시 **빌드(지연 서명) → 난독화 → 최종 서명**이어야 한다.

## 52.6 어셈블리 이름 — 정규화된 이름, `AssemblyName`, 정보·파일 버전

### 어셈블리 신원의 네 요소

어셈블리의 "신원"은 매니페스트에 있는 네 개의 메타데이터로 구성된다.

| 요소 | 없을 때 기본값 | 출처 |
|---|---|---|
| **단순 이름(simple name)** | (필수) | 원래 컴파일된 **파일 이름**(확장자 제외) |
| **버전** | `0.0.0.0` | `AssemblyVersion` 특성 |
| **문화권(culture)** | `neutral` | `AssemblyCulture` 특성 (위성 어셈블리일 때만) |
| **공개 키 토큰** | `null` | 컴파일 시 제공한 강력한 이름 |

> **📌 단순 이름은 특성에서 오지 않는다**
>
> 단순 이름은 어떤 특성에서도 오지 않는다. 원래 컴파일된 **파일 이름**(확장자 제외)에서 온다. 그래서 `System.Xml.dll` 어셈블리의 단순 이름은 `System.Xml`이다. **파일 이름을 나중에 바꿔도 단순 이름은 바뀌지 않는다.** 이건 실무에서 혼란의 원인이 되곤 한다 — 파일을 `Foo.dll`로 리네임했는데 로드하려니 `Bar`라는 이름으로 찾더라, 같은 상황이다.

버전 번호는 `AssemblyVersion` 특성에서 오고, 마침표로 나뉜 네 부분이다.

```text
major.minor.build.revision
```

```csharp
[assembly: AssemblyVersion("2.5.6.7")]
```

또는 SDK 스타일 프로젝트에서,

```xml
<AssemblyVersion>2.5.6.7</AssemblyVersion>
```

### 정규화된 이름

정규화된 어셈블리 이름은 네 식별 요소를 모두 포함한 문자열이다.

```text
simple-name, Version=version, Culture=culture, PublicKeyToken=public-key
```

예를 들어 `System.Private.CoreLib.dll`의 정규화된 이름은 이렇다.

```text
System.Private.CoreLib, Version=4.0.0.0, Culture=neutral, PublicKeyToken=7cec85d7bea7798e
```

`AssemblyVersion` 특성이 없으면 버전은 `0.0.0.0`으로 나타난다. 서명되지 않았으면 공개 키 토큰은 `null`로 나타난다.

`Assembly` 객체의 `FullName` 속성이 정규화된 이름을 반환한다. **컴파일러는 매니페스트에 어셈블리 참조를 기록할 때 항상 정규화된 이름을 쓴다.**

> **⚠️ 정규화된 이름에 경로는 없다**
>
> 정규화된 어셈블리 이름에는 디스크에서 그것을 찾는 데 도움이 될 **디렉터리 경로가 포함되지 않는다.** 다른 디렉터리에 있는 어셈블리를 찾는 것은 완전히 별개의 문제이고, 52.9~52.15절에서 다룬다.

### `AssemblyName` 클래스

`AssemblyName`은 정규화된 어셈블리 이름의 네 요소 각각에 대해 타입이 지정된 속성을 가진 클래스다. 두 가지 목적이 있다.

1. 정규화된 어셈블리 이름을 **파싱하거나 조립한다.**
2. 어셈블리를 **해석(찾기)** 하는 데 도움이 되는 추가 데이터를 저장한다.

`AssemblyName` 객체를 얻는 세 가지 방법.

```csharp
// 1. 정규화된 이름을 주고 생성
var n1 = new AssemblyName("System.Xml, Version=4.0.0.0");

// 2. 기존 Assembly에 GetName 호출
var n2 = typeof(string).Assembly.GetName();

// 3. 디스크상 어셈블리 파일 경로로부터
var n3 = AssemblyName.GetAssemblyName(@"c:\temp\foo.dll");
```

인자 없이 인스턴스화한 뒤 각 속성을 설정해서 정규화된 이름을 조립할 수도 있다. 이렇게 만든 `AssemblyName`은 **가변(mutable)** 이다.

핵심 속성과 메서드는 다음과 같다.

```csharp
string      FullName    { get; }        // 정규화된 이름
string      Name        { get; set; }   // 단순 이름
Version     Version     { get; set; }   // 어셈블리 버전
CultureInfo CultureInfo { get; set; }   // 위성 어셈블리용
string      CodeBase    { get; set; }   // 위치

byte[] GetPublicKey();                          // 160 바이트
void   SetPublicKey(byte[] key);
byte[] GetPublicKeyToken();                     // 8 바이트 버전
void   SetPublicKeyToken(byte[] publicKeyToken);
```

`Version` 자체가 강력하게 타입 지정된 표현이고 `Major`, `Minor`, `Build`, `Revision` 속성을 갖는다. `GetPublicKey`는 전체 암호학적 공개 키를, `GetPublicKeyToken`은 신원 확립에 쓰이는 **마지막 8바이트**를 반환한다.

```csharp
// 단순 이름 얻기
Console.WriteLine(typeof(string).Assembly.GetName().Name);
// System.Private.CoreLib

// 버전 얻기
string v = myAssembly.GetName().Version.ToString();
```

### 정보 버전과 파일 버전

버전 관련 정보를 표현하는 어셈블리 특성이 두 개 더 있다. `AssemblyVersion`과 달리 이 둘은 **어셈블리의 신원에 영향을 주지 않으며**, 따라서 컴파일 타임에도 런타임에도 아무 효과가 없다.

| 특성 | 용도 | Windows 파일 속성 대화상자 표시 | 형식 제약 |
|---|---|---|---|
| `AssemblyInformationalVersion` | 최종 사용자에게 보여주는 버전 | **제품 버전** | 아무 문자열 (`"5.1 Beta 2"` 같은 것도 가능) |
| `AssemblyFileVersion` | 해당 어셈블리의 빌드 번호 | **파일 버전** | 마침표로 나뉜 최대 4개 숫자 |

보통 애플리케이션의 모든 어셈블리에 같은 정보 버전 번호를 부여한다.

> **💡 실무 관례**
>
> 세 버전을 이렇게 나눠 쓰는 것이 일반적이다.
>
> - `AssemblyVersion` — **거의 바꾸지 않는다.** `1.0.0.0`으로 고정하고 메이저 파괴적 변경 때만 올린다. 이걸 바꾸면 참조하는 모든 어셈블리를 재컴파일해야 하기 때문이다.
> - `AssemblyFileVersion` — CI 빌드마다 올린다. `1.0.2026.904` 같은 식.
> - `AssemblyInformationalVersion` — 시맨틱 버전 + 프리릴리스 태그 + 커밋 해시. `2.3.1-rc.2+a1b2c3d`.
>
> SDK 스타일 프로젝트에서 `<Version>`만 설정하면 세 개 모두에 반영된다. 따로 제어하려면 `<AssemblyVersion>`, `<FileVersion>`, `<InformationalVersion>`을 각각 설정한다.

## 52.7 Authenticode 서명

Authenticode는 **게시자의 신원을 증명**하는 것이 목적인 코드 서명 시스템이다.

Authenticode와 강력한 이름 서명은 **독립적**이다. 둘 중 하나로 서명할 수도, 둘 다로 서명할 수도 있다.

강력한 이름 서명은 어셈블리 A, B, C가 **같은 당사자**에게서 왔음을 증명할 수 있다(개인 키가 유출되지 않았다는 전제하에). 하지만 그 당사자가 **누구인지**는 알려주지 못한다. 그게 Joseph Albahari인지 Microsoft Corporation인지 알려면 Authenticode가 필요하다.

Authenticode가 유용한 경우:

- 인터넷에서 프로그램을 다운로드할 때 — 인증 기관(CA)이 지명한 자에게서 왔고 전송 중 수정되지 않았음을 보증한다.
- 다운로드한 애플리케이션을 처음 실행할 때 나오는 "알 수 없는 게시자" 경고를 막는다.
- Windows Store에 앱을 제출할 때 요구사항이다.

Authenticode는 .NET 어셈블리뿐 아니라 비관리 실행 파일, `.msi` 배포 파일 같은 바이너리에도 적용된다. 물론 Authenticode가 프로그램이 맬웨어가 아님을 보장하지는 않는다 — 다만 가능성을 낮춘다. 어떤 개인이나 법인이 (여권이나 법인 서류로 뒷받침된) 자기 이름을 그 실행 파일에 걸었다는 뜻이니까.

> **📌 CLR은 Authenticode 서명을 신원으로 취급하지 않는다**
>
> CLR은 Authenticode 서명을 어셈블리 신원의 일부로 **취급하지 않는다.** 다만 필요할 때 읽고 검증할 수는 있다.

### 인증서 얻기

CA에 개인 신원 증명(또는 회사 설립 서류 등)을 제출해야 한다. CA가 서류를 확인하면 보통 1~5년 유효한 **X.509 코드 서명 인증서**를 발급한다. 이걸로 `signtool` 유틸리티를 써서 어셈블리에 서명할 수 있다.

`makecert` 유틸리티로 인증서를 직접 만들 수도 있지만, 그 인증서를 명시적으로 설치한 컴퓨터에서만 인식된다.

자체 서명이 아닌 인증서가 아무 컴퓨터에서나 동작하는 것은 **공개 키 기반 구조(PKI)** 덕분이다. 내 인증서는 CA에 속한 다른 인증서로 서명되어 있고, 모든 CA는 OS에 로드되어 있으므로 신뢰된다. CA는 인증서가 유출되면 게시자의 인증서를 폐기할 수 있고, 그래서 Authenticode 서명 검증은 CA에게 주기적으로 최신 폐기 목록을 요청하는 과정을 포함한다.

> **📌 코드 서명 인증서는 어디서 사나**
>
> Windows에 루트 인증 기관으로 미리 로드된 코드 서명 CA는 몇 개 안 된다. Comodo, GoDaddy, GlobalSign, DigiCert, Thawte, Symantec 등이다. 이들의 인증서를 할인 판매하는 리셀러(K Software 등)도 있다.
>
> **SSL용 인증서는 일반적으로 Authenticode 서명에 쓸 수 없다.** 같은 X.509 인프라를 쓰는데도 그렇다. SSL 인증서는 도메인 소유권을 증명하는 것이고, Authenticode는 당신이 누구인지를 증명하는 것이기 때문이다.

### 인증서 획득과 설치

첫 단계는 CA에서 코드 서명 인증서를 받는 것이다. 그다음 인증서를 다루는 방법이 둘이다.

1. **암호로 보호된 파일**로 다룬다.
2. **컴퓨터의 인증서 저장소**에 로드한다.

**2번이 낫다.** 암호를 지정하지 않고 서명할 수 있기 때문이다. 자동 빌드 스크립트나 배치 파일에 암호가 노출되는 것을 막아준다.

인증서를 컴퓨터의 인증서 저장소에 로드하려면 인증서 관리자를 열고(Windows 제어판 검색창에 "certificate" 입력 → 관리 도구 섹션의 "컴퓨터 인증서 관리"), **개인(Personal)** 폴더를 열고, 그 아래 **인증서(Certificates)** 폴더를 우클릭한 뒤 **모든 작업 → 가져오기**를 선택한다. 마법사가 안내한다.

가져오기가 끝나면 인증서의 **보기** 버튼을 누르고 **자세히** 탭으로 가서 인증서의 **지문(thumbprint)** 을 복사해둔다. 이것이 SHA-256 해시이고, 나중에 서명할 때 인증서를 식별하는 데 필요하다.

> **📌 벤더 간 차이**
>
> K Software, Comodo, GoDaddy, GlobalSign이 발급하는 Authenticode 인증서는 **비(非)Microsoft 프로그램에도 서명할 수 있다는 점에서 덜 제한적**이라고 광고된다. 그 점을 빼면 모든 벤더의 제품은 기능적으로 동등하다.

### `signtool.exe`로 서명하기

`signtool`은 Visual Studio와 함께 설치된다(Program Files 아래 `Microsoft SDKs\ClickOnce\SignTool` 폴더).

```text
signtool sign /n "Joseph Albahari" /fd sha256 LINQPad.exe
```

컴퓨터의 My Store에 있는 "Joseph Albahari" 인증서로, 안전한 SHA-256 해싱 알고리즘을 써서 서명한다.

설명과 제품 URL도 지정할 수 있다.

```text
... /d LINQPad /du http://www.linqpad.net
```

### 타임스탬프 — 반드시 하라

인증서가 만료되면 더는 프로그램에 서명할 수 없다. 하지만 **만료 전에 서명한 프로그램은 계속 유효하다** — 서명할 때 `/tr` 스위치로 타임스탬프 서버를 지정했다면.

```text
... /tr http://timestamp.comodoca.com/authenticode /td SHA256
```

CA가 이 목적의 URI를 제공한다. 타임스탬프를 빠뜨리면 인증서 만료와 함께 이미 배포한 바이너리까지 신뢰를 잃는다.

> **⚠️ 순서가 중요하다: 강력한 이름 서명 → Authenticode 서명**
>
> 어셈블리에 강력한 이름 서명도 하려면 **Authenticode 서명보다 먼저** 해야 한다. CLR은 Authenticode 서명의 존재를 알지만 그 반대는 아니기 때문이다. Authenticode 서명 후에 강력한 이름 서명을 하면, Authenticode 쪽에서는 CLR의 강력한 이름이 추가된 것을 **허가되지 않은 수정**으로 보고 어셈블리가 변조된 것으로 간주한다.

서명 여부를 확인하는 가장 쉬운 방법은 Windows 탐색기에서 파일 속성을 보는 것이다(디지털 서명 탭). `signtool` 유틸리티에도 확인 옵션이 있다.

암호화, 해싱, 서명 자체에 대해서는 44장에서 다룬다.

## 52.8 런타임의 타입 참조 해석 과정

이제 이 장의 핵심으로 들어간다. **CLR은 IL 안의 타입 참조를 어떻게 실제 타입으로 바꾸는가?**

다음의 뻔한 코드를 보자.

```csharp
public sealed class Program {
    public static void Main() {
        System.Console.WriteLine("Hi");
    }
}
```

이 코드를 컴파일해 `Program.exe`를 만들고 실행하면, CLR이 로드·초기화되고, 어셈블리의 CLR 헤더를 읽어 진입점 메서드(`Main`)를 식별하는 `MethodDefToken`을 찾는다. MethodDef 메타데이터 테이블에서 메서드 IL 코드의 파일 내 오프셋을 찾고, 네이티브 코드로 JIT 컴파일하며(타입 안전성 검증 포함), 실행을 시작한다.

`Main`의 IL은 이렇게 생겼다.

```text
.method public hidebysig static void Main() cil managed
{
  .entrypoint
  .maxstack 8
  IL_0000: /* 72 | (70)000001 */  ldstr  "Hi"
  IL_0005: /* 28 | (0A)000003 */  call   void [mscorlib]System.Console::WriteLine(string)
  IL_000a: /* 2A |            */  ret
}
```

### 토큰을 따라가는 여정

JIT 컴파일 중에 CLR은 타입과 멤버에 대한 모든 참조를 감지하고, 아직 로드되지 않은 정의 어셈블리를 로드한다.

위 IL의 `call` 명령은 메타데이터 토큰 `0A000003`을 참조한다. 이 토큰을 읽는 법은 이렇다.

- 상위 바이트 `0A` = **MemberRef** 테이블
- 나머지 `000003` = 그 테이블의 3번 항목

메타데이터 토큰은 항상 4바이트이고, 이 구조는 모든 토큰에 공통이다.

| 상위 바이트 | 테이블 |
|---|---|
| `0x01` | TypeRef |
| `0x02` | TypeDef |
| `0x0A` | MemberRef |
| `0x23` | AssemblyRef |
| `0x26` | File |
| `0x27` | ExportedType |

하위 3바이트는 그 테이블의 행 번호다. **대부분의 테이블은 1부터 시작하지만 TypeDef 테이블만 2부터 시작한다** — 1번 행은 컴파일러가 만드는 `<Module>` 유사 타입이 차지하기 때문이다.

CLR이 하는 일을 순서대로 따라가면,

1. **MemberRef 항목 3번**을 찾는다.
2. 그 항목의 한 필드가 **TypeRef 테이블** 항목을 가리킨다 → `System.Console` 타입.
3. TypeRef 항목에서 **AssemblyRef 항목**으로 안내된다 → `"mscorlib, Version=4.0.0.0, Culture=neutral, PublicKeyToken=b77a5c561934e089"`.

이 시점에서 CLR은 **어떤 어셈블리가 필요한지** 안다. 이제 그것을 **찾아서 로드**해야 한다.

### 참조된 타입이 있을 수 있는 세 곳

CLR이 참조된 타입을 찾을 수 있는 곳은 셋이다.

| 위치 | CLR의 동작 |
|---|---|
| **같은 파일** | 컴파일 타임에 결정된다(early bound). 파일에서 직접 타입을 로드하고 실행을 계속한다 |
| **다른 파일, 같은 어셈블리** | 참조 대상 파일이 현재 어셈블리 매니페스트의 **ModuleRef 테이블**에 실제로 있는지 확인한다. 어셈블리 매니페스트 파일이 로드된 디렉터리를 찾는다. 파일을 로드하고, **해시 값을 검사해 무결성을 확인**하고, 타입 멤버를 찾고, 실행을 계속한다 |
| **다른 파일, 다른 어셈블리** | 참조된 어셈블리의 매니페스트를 담은 파일을 로드한다. 그 파일에 타입이 없으면 적절한 파일을 로드한다. 타입 멤버를 찾고 실행을 계속한다 |

```text
        IL이 멤버를 참조
              ↓
        IL이 타입을 참조
              ↓
     TypeRef 항목이 가리키는 것은?
      ┌───────┼────────────────┐
      ↓       ↓                ↓
  ModuleDef  ModuleRef      AssemblyRef
  같은 파일   다른 파일       다른 파일
  같은 어셈블리 같은 어셈블리   다른 어셈블리
      │       ↓                ↓
      │  ModuleRef 테이블   AssemblyRef 항목이
      │  검사 후 해당 파일   가리키는 것은?
      │  로드            ┌────┴─────┐
      │       │          ↓          ↓
      │       │     약한 이름     강력한 이름
      │       │     어셈블리      어셈블리
      │       │          ↓          ↓
      │       │     AppBase에서   GAC 다음 AppBase
      │       │     어셈블리 검색  에서 검색
      │       │          └────┬─────┘
      │       │               ↓
      │       │        매니페스트 파일 로드
      │       │               ↓
      │       │      ExportedTypesDef 항목이
      │       │        가리키는 것은?
      │       │      ┌────────┴────────┐
      │       │      ↓                 ↓
      │       │  매니페스트 파일에   매니페스트 파일에
      │       │  타입 있음          타입 없음
      │       │      │                 ↓
      │       │      │             해당 파일 로드
      └───────┴──────┴─────────────────┘
                     ↓
              내부 타입 구조 생성

  ※ 어떤 단계든 실패하면 적절한 예외가 던져진다.
```

> **⚠️ 이 흐름도는 .NET Framework 기준이다**
>
> "강력한 이름 어셈블리 → GAC 다음 AppBase에서 검색" 분기는 **GAC가 존재하는 .NET Framework의 동작**이다. .NET 5+와 .NET Core에는 GAC가 없으므로 이 분기가 사라지고, 그 자리를 `AssemblyLoadContext`의 해석 절차가 대신한다(52.10절, 52.15절). 토큰을 따라가는 앞부분 — MemberRef → TypeRef → AssemblyRef, 그리고 "참조된 타입이 있을 수 있는 세 곳" — 은 두 런타임에서 동일하다.

> **📌 확장자를 붙이는 것은 시스템이다**
>
> ModuleDef, ModuleRef, FileDef 메타데이터 테이블은 파일을 **이름 + 확장자**로 참조한다. 그러나 AssemblyRef 테이블은 어셈블리를 **확장자 없는 파일 이름**으로 참조한다. 어셈블리에 바인딩할 때 시스템이 자동으로 `.dll`과 `.exe` 확장자를 덧붙이며 디렉터리를 프로빙한다.

무엇 하나라도 실패하면 — 파일을 못 찾거나, 로드할 수 없거나, 해시가 안 맞거나 — 적절한 예외가 던져진다.

> **📌 실패를 가로채는 콜백**
>
> 원한다면 `System.AppDomain`의 다음 이벤트에 콜백 메서드를 등록해 바인딩 문제를 해결하고 예외 없이 애플리케이션을 계속 실행시킬 수 있다.
>
> | 이벤트 | 발생 시점 |
> |---|---|
> | `AssemblyResolve` | 어셈블리 해석에 실패했을 때 |
> | `ReflectionOnlyAssemblyResolve` | 리플렉션 전용 컨텍스트에서 해석에 실패했을 때 (.NET Framework 전용) |
> | `TypeResolve` | 타입 해석에 실패했을 때 |
>
> .NET 5+에서는 `AssemblyLoadContext`의 `Resolving` 이벤트가 정석이고(52.10절), `AppDomain.AssemblyResolve`는 폴백 체인의 마지막 단계로 남아 있다.

### 통합(unification)

위 설명에는 중요한 예외가 하나 있다.

.NET Framework과 함께 배포되지 않는 어셈블리에 정의된 메서드·타입 참조라면 위 설명이 정확하다. 그러나 **.NET Framework 어셈블리(`MSCorLib.dll` 포함)는 실행 중인 CLR의 버전과 밀접하게 묶여 있다.** .NET Framework 어셈블리를 참조하는 어떤 어셈블리든 항상 **CLR 버전에 맞는 버전에 바인딩된다.**

이걸 **통합(unification)** 이라고 한다. Microsoft가 이렇게 하는 이유는 특정 CLR 버전으로 모든 .NET Framework 어셈블리를 테스트하기 때문이다. 코드 스택을 통합하면 애플리케이션이 올바르게 동작할 가능성이 높아진다.

그래서 위 예제에서 `System.Console.WriteLine`에 대한 참조는, 어셈블리의 AssemblyRef 메타데이터 테이블에 어떤 `MSCorLib.dll` 버전이 참조되어 있든 상관없이, **CLR 버전과 일치하는 `MSCorLib.dll`에 바인딩된다.**

### CPU 아키텍처가 개입하는 지점

이야기가 한 겹 더 있다. CLR에게 모든 어셈블리는 **이름, 버전, 문화권, 공개 키**로 식별된다. 그러나 GAC는 여기에 **CPU 아키텍처**를 더해 어셈블리를 식별한다.

GAC에서 어셈블리를 찾을 때 CLR은 애플리케이션이 현재 어떤 종류의 프로세스에서 실행 중인지 파악한다 — 32비트 x86(WoW64 사용 가능성 포함), 64비트 x64, 32비트 ARM. 그리고 GAC를 검색할 때 **먼저 CPU 아키텍처별 버전**을 찾고, 일치하는 게 없으면 **CPU 무관(agnostic) 버전**을 찾는다.

### 타입 전달 — `TypeForwardedTo`

CLR은 타입(클래스, 구조체, 열거형, 인터페이스, 델리게이트)을 **한 어셈블리에서 다른 어셈블리로 옮기는 기능**을 지원한다.

예를 들어 .NET 3.5에서 `System.TimeZoneInfo` 클래스는 `System.Core.dll` 어셈블리에 정의되어 있었다. .NET 4.0에서 Microsoft는 이 클래스를 `MSCorLib.dll`로 옮겼다. 보통 타입을 이렇게 옮기면 애플리케이션이 깨진다.

이를 위해 CLR은 `System.Runtime.CompilerServices.TypeForwardedToAttribute`를 제공한다. 원래 어셈블리(위 예에서는 `System.Core.dll`)에 적용한다. 생성자에 전달하는 인자는 `System.Type` 타입이며, 애플리케이션이 이제 써야 할 새 타입(이제 `MSCorLib.dll`에 정의된)을 가리킨다. CLR의 바인더가 이 정보를 이용한다.

```csharp
// System.Core.dll 안에
[assembly: TypeForwardedTo(typeof(System.TimeZoneInfo))]
```

`TypeForwardedToAttribute`의 생성자가 `Type`을 받으므로, 이 특성을 담은 어셈블리는 타입을 새로 정의한 어셈블리에 **의존하게 된다.**

이 기능을 쓴다면, 새 어셈블리의 타입에 `System.Runtime.CompilerServices.TypeForwardedFromAttribute`도 적용하고, 그 타입을 예전에 정의했던 어셈블리의 전체 이름을 문자열로 전달해야 한다.

```csharp
// MSCorLib.dll 안에
[TypeForwardedFrom("System.Core, Version=3.5.0.0, Culture=neutral, PublicKeyToken=...")]
public sealed class TimeZoneInfo { ... }
```

이 특성은 주로 도구, 유틸리티, 직렬화에 쓰인다. `TypeForwardedFromAttribute`의 생성자는 `String`을 받으므로, 이 특성을 담은 어셈블리는 예전에 타입을 정의했던 어셈블리에 **의존하지 않는다.** 이 비대칭이 설계의 핵심이다.

## 52.9 `AssemblyLoadContext` — AppDomain을 대체한 격리 모델

### 로딩과 해석은 다른 일이다

용어부터 정확히 하자.

- **어셈블리 로딩(assembly loading)** — 알려진 위치에서 어셈블리를 로드한다. 비교적 단순한 과정이다.
- **어셈블리 해석(assembly resolution)** — 전체 이름(또는 단순 이름)만 알고 어셈블리를 로드한다. 해석은 로딩과 달리 **먼저 어셈블리를 찾아야** 한다.

어셈블리 해석은 두 시나리오에서 촉발된다.

1. **CLR이** 의존성을 해석해야 할 때
2. **명시적으로** `Assembly.Load(AssemblyName)` 같은 메서드를 호출할 때

첫 번째 시나리오를 보자. 주 어셈블리와 정적으로 참조된 라이브러리 집합으로 구성된 애플리케이션이 있다.

```text
AdventureGame.dll     // 주 어셈블리
Terrain.dll           // 참조된 어셈블리
UIEngine.dll          // 참조된 어셈블리
```

"정적으로 참조"란 `AdventureGame.dll`이 `Terrain.dll`과 `UIEngine.dll`에 대한 참조를 갖고 컴파일되었다는 뜻이다. **컴파일러 자신은 어셈블리 해석을 할 필요가 없다** — 어디서 찾을지 (명시적으로 또는 MSBuild를 통해) 들었기 때문이다. 컴파일 중에 컴파일러는 `Terrain`과 `UIEngine` 어셈블리의 **전체 이름을** `AdventureGame.dll`의 메타데이터에 기록하지만, **어디서 찾을지에 대한 정보는 기록하지 않는다.** 그래서 런타임에 `Terrain`과 `UIEngine` 어셈블리는 반드시 **해석되어야** 한다.

### ALC — 로딩·해석·격리의 세 가지 역할

어셈블리 로딩과 해석은 **어셈블리 로드 컨텍스트(ALC)** 가 처리한다. 구체적으로는 `System.Runtime.Loader.AssemblyLoadContext` 클래스의 인스턴스다.

`AdventureGame.dll`이 애플리케이션의 주 어셈블리이므로, CLR은 **기본 ALC**(`AssemblyLoadContext.Default`)를 사용해 그 의존성을 해석한다.

프로그램 실행 중에 **어셈블리를 동적으로 추가 로드**할 수도 있다. 예를 들어 선택적 기능을 별도 어셈블리로 패키징해서 그 기능을 구매한 고객에게만 배포하고, 파일이 있을 때만 `Assembly.Load(AssemblyName)`으로 로드하는 식이다.

더 복잡한 예가 **플러그인 시스템**이다. 사용자가 제공한 제3자 어셈블리를 애플리케이션이 런타임에 탐지하고 로드해 기능을 확장한다. 복잡해지는 이유는 **각 플러그인이 자기만의 의존성을 가질 수 있고 그것도 해석되어야 하기 때문**이다.

`AssemblyLoadContext`를 서브클래싱하고 어셈블리 해석 메서드(`Load`)를 오버라이드하면 플러그인이 자기 의존성을 어떻게 찾을지 통제할 수 있다. 예를 들어 각 플러그인이 자기 폴더에 있고 그 의존성도 같은 폴더에 있어야 한다고 정할 수 있다.

ALC의 역할은 셋이다.

1. **로딩** — 경로나 스트림에서 어셈블리를 메모리에 올린다.
2. **해석** — 이름만으로 어셈블리를 찾아 로드한다.
3. **격리** — 각 (플러그인 + 그 의존성)마다 별도의 ALC를 만들면, 서로 간섭하지 않고(호스트 애플리케이션과도) 독립적으로 로드된다. 예를 들어 각자 자기 버전의 JSON.NET을 가질 수 있다.

특정 조건에서는 ALC를 **언로드**해 메모리를 해제할 수도 있다(52.12절).

> **📌 .NET Framework에는 ALC가 없었나**
>
> `AssemblyLoadContext` 클래스는 .NET 5+와 .NET Core에 새로 생긴 것이다. .NET Framework에도 ALC는 존재했지만 **제한적이고 감춰져 있었다.** ALC를 만들고 상호작용하는 유일한 방법은 `Assembly` 클래스의 정적 메서드 `LoadFile(string)`, `LoadFrom(string)`, `Load(byte[])`를 통한 간접적 방식이었다. ALC API에 비하면 이 메서드들은 유연하지 않고, 특히 의존성을 다룰 때 놀라운 결과를 낳을 수 있다. 그래서 .NET 5+와 .NET Core에서는 **명시적인 `AssemblyLoadContext` API를 쓰는 편이 낫다.**

### 모든 어셈블리는 정확히 하나의 ALC에 속한다

```csharp
Assembly assem = Assembly.GetExecutingAssembly();
AssemblyLoadContext context = AssemblyLoadContext.GetLoadContext(assem);
Console.WriteLine(context.Name);
```

반대로 ALC가 어셈블리를 "담고" 있거나 "소유"한다고 생각할 수도 있고, `Assemblies` 속성으로 얻을 수 있다.

```csharp
foreach (Assembly a in context.Assemblies)
    Console.WriteLine(a.FullName);
```

정적 `All` 속성은 모든 ALC를 열거한다.

```csharp
foreach (var alc in AssemblyLoadContext.All)
    Console.WriteLine($"{alc.Name}: {alc.Assemblies.Count()}개");
```

새 ALC는 `AssemblyLoadContext`를 인스턴스화하고 이름을 주면 만들어진다(이름은 디버깅에 도움이 된다). 하지만 더 흔한 경우는 먼저 `AssemblyLoadContext`를 **서브클래싱**해서 의존성 해석 로직 — 즉 이름으로부터 어셈블리를 로드하는 로직 — 을 구현하는 것이다.

### 어셈블리 로드하기

`AssemblyLoadContext`는 어셈블리를 컨텍스트에 명시적으로 로드하는 두 메서드를 제공한다.

```csharp
public Assembly LoadFromAssemblyPath(string assemblyPath);
public Assembly LoadFromStream(Stream assembly, Stream assemblySymbols);
```

첫 번째는 파일 경로에서, 두 번째는 `Stream`(메모리에서 직접 올 수도 있다)에서 로드한다. 두 번째 매개변수는 선택적이며 프로젝트 디버그(`.pdb`) 파일의 내용에 해당한다. 이걸 주면 코드 실행 시 스택 트레이스에 소스 코드 정보가 포함된다(예외 보고에 유용하다).

**두 메서드 모두 해석은 일어나지 않는다.**

```csharp
var alc = new AssemblyLoadContext("Test");
Assembly assem = alc.LoadFromAssemblyPath(@"c:\temp\foo.dll");
```

### 규칙 하나: ALC 안에서 단순 이름은 유일해야 한다

어셈블리가 유효하다면 로딩은 항상 성공한다 — **한 가지 중요한 규칙만 지키면.** 어셈블리의 **단순 이름은 그 ALC 안에서 유일해야 한다.**

즉 같은 이름의 어셈블리를 여러 버전으로 하나의 ALC에 로드할 수 **없다.** 그렇게 하려면 ALC를 추가로 만들어야 한다.

```csharp
var alc2 = new AssemblyLoadContext("Test 2");
Assembly assem2 = alc2.LoadFromAssemblyPath(@"c:\temp\foo.dll");
```

> **⚠️ 다른 `Assembly` 객체에서 온 타입은 서로 호환되지 않는다**
>
> 어셈블리가 그 외 모든 면에서 동일하더라도, **서로 다른 `Assembly` 객체에서 유래한 타입은 호환되지 않는다.** 위 예에서 `assem`의 타입은 `assem2`의 타입과 호환되지 않는다.
>
> 이것이 플러그인 시스템에서 가장 흔한 함정이다. `InvalidCastException: Unable to cast object of type 'IPlugin' to type 'IPlugin'`처럼 도무지 말이 안 되는 예외 메시지를 보게 된다. 같은 이름의 타입이 두 ALC에 각각 로드된 것이다. 해법은 52.14절에서 다룬다.

로드된 어셈블리는 **ALC를 언로드하지 않는 한 언로드할 수 없다**(52.12절). CLR은 로드되어 있는 동안 파일 잠금을 유지한다.

> **📌 파일 잠금을 피하는 방법과 그 대가**
>
> 바이트 배열로 어셈블리를 로드하면 파일 잠금을 피할 수 있다.
>
> ```csharp
> byte[] bytes = File.ReadAllBytes(@"c:\temp\foo.dll");
> var ms = new MemoryStream(bytes);
> var assem = alc.LoadFromStream(ms);
> ```
>
> 단점이 둘 있다.
>
> - 어셈블리의 `Location` 속성이 **빈 문자열**이 된다. 어디서 로드되었는지 아는 것이 유용할 때가 있고, 일부 API는 이 값이 채워져 있어야 동작한다.
> - **private 메모리 사용량이 어셈블리 전체 크기만큼 즉시 증가한다.** 파일 이름으로 로드하면 CLR은 **메모리 매핑 파일**을 쓰고, 덕분에 지연 로딩과 프로세스 간 공유가 가능해진다. 게다가 메모리가 부족해지면 OS가 그 메모리를 해제했다가 필요할 때 다시 읽어올 수 있다 — 페이지 파일에 쓰지 않고.

## 52.10 기본 ALC, "현재" ALC, `Assembly.Load`와 컨텍스트

### 해석 메서드

```csharp
public Assembly LoadFromAssemblyName(AssemblyName assemblyName);
```

앞의 두 메서드와 달리 어셈블리가 어디 있는지 알려주는 정보를 넘기지 않는다. 대신 ALC에게 어셈블리를 **해석하라고 지시**한다.

### 해석의 5단계

이 메서드는 어셈블리 해석을 촉발한다. CLR도 의존성을 로드할 때 어셈블리 해석을 촉발한다. 예를 들어 어셈블리 A가 어셈블리 B를 정적으로 참조한다면, 참조 B를 해석하기 위해 CLR은 **어셈블리 A가 로드된 ALC**에서 어셈블리 해석을 촉발한다.

> **📌 기본 ALC와 커스텀 ALC의 차이는 규칙을 누가 쓰느냐다**
>
> CLR은 촉발 어셈블리가 기본 ALC에 있든 커스텀 ALC에 있든 어셈블리 해석을 촉발해 의존성을 해석한다. 차이는 기본 ALC에서는 **해석 규칙이 하드코딩되어 있고**, 커스텀 ALC에서는 **당신이 규칙을 직접 쓴다**는 점이다.

일어나는 일은 다음과 같다.

1. CLR은 먼저 그 ALC에서 **동일한 해석이 이미 일어났는지** 확인한다(전체 어셈블리 이름 일치). 그렇다면 이전에 반환한 `Assembly`를 반환한다.
2. 아니면 ALC의 (virtual protected) **`Load` 메서드**를 호출한다. 이 메서드가 어셈블리를 찾아 로드하는 일을 한다. 기본 ALC의 `Load` 메서드는 「기본 ALC」에서 설명하는 규칙을 적용한다. 커스텀 ALC라면 어셈블리를 어떻게 찾을지는 전적으로 당신에게 달렸다. 예를 들어 어떤 폴더를 뒤지고 찾으면 `LoadFromAssemblyPath`를 호출할 수 있다. 같은 ALC나 다른 ALC에서 **이미 로드된 어셈블리를 반환하는 것도 완전히 합법이다**(52.14절에서 이를 활용한다).
3. 2단계가 `null`을 반환하면, CLR은 **기본 ALC의 `Load` 메서드**를 호출한다(.NET 런타임 어셈블리와 흔한 애플리케이션 어셈블리를 해석하는 유용한 "폴백" 역할을 한다).
4. 3단계가 `null`을 반환하면, CLR은 **두 ALC 모두에서 `Resolving` 이벤트를 발생시킨다** — 먼저 기본 ALC, 그다음 원래 ALC.
5. (.NET Framework 호환을 위해) 그래도 해석되지 않으면 `AppDomain.CurrentDomain.AssemblyResolve` 이벤트가 발생한다.

> **📌 마지막 온전성 검사**
>
> 이 과정이 끝나면 CLR은 로드된 어셈블리의 이름이 요청된 것과 호환되는지 "온전성 검사(sanity check)"를 한다.
>
> - **단순 이름은 일치해야 한다.**
> - **공개 키 토큰은 지정되었다면 일치해야 한다.**
> - **버전은 일치하지 않아도 된다** — 요청한 것보다 높아도 낮아도 된다.
>
> 마지막 항목이 중요하다. .NET에서 버전 불일치가 조용히 넘어가는 이유가 여기 있다. 로드는 성공하고, 문제는 없는 멤버를 실제로 호출하는 순간 `MissingMethodException`으로 터진다.

### 커스텀 ALC에서 해석을 구현하는 두 가지 방법

- **ALC의 `Load` 메서드를 오버라이드한다.** 당신의 ALC가 "첫 발언권"을 갖는다. 보통 이쪽이 바람직하고, 격리가 필요할 때는 필수다.
- **ALC의 `Resolving` 이벤트를 처리한다.** 기본 ALC가 어셈블리 해석에 실패한 **후에만** 발생한다.

> **📌 `Resolving` 이벤트 핸들러가 여럿이면**
>
> `Resolving` 이벤트에 여러 핸들러를 붙이면 **가장 먼저 null이 아닌 값을 반환한 것이 이긴다.**

예를 들어 보자. 메인 애플리케이션이 컴파일 타임에 전혀 모르는 어셈블리 `foo.dll`을 `c:\temp`(애플리케이션 폴더와 다른 곳)에서 로드하려고 한다. `foo.dll`은 `bar.dll`에 대한 private 의존성을 갖는다. `c:\temp\foo.dll`을 로드하고 그 코드를 실행할 때 `c:\temp\bar.dll`이 올바르게 해석되기를 바라고, `foo`와 그 private 의존성 `bar`가 메인 애플리케이션에 간섭하지 않기를 바란다.

`Load`를 오버라이드하는 커스텀 ALC부터 보자.

```csharp
using System.IO;
using System.Runtime.Loader;

class FolderBasedALC : AssemblyLoadContext
{
    readonly string _folder;
    public FolderBasedALC(string folder) => _folder = folder;

    protected override Assembly Load(AssemblyName assemblyName)
    {
        // 어셈블리를 찾아본다
        string targetPath = Path.Combine(_folder, assemblyName.Name + ".dll");

        if (File.Exists(targetPath))
            return LoadFromAssemblyPath(targetPath);   // 어셈블리 로드

        return null;   // 못 찾음: .NET 런타임 어셈블리일 수 있다
    }
}
```

> **⚠️ `null` 반환이 왜 결정적으로 중요한가**
>
> `Load` 메서드에서 어셈블리 파일이 없으면 `null`을 반환하는 이 검사가 **중요하다.** `foo.dll`은 .NET BCL 어셈블리에 대한 의존성도 갖기 때문이다. 즉 `System.Runtime` 같은 어셈블리에 대해서도 `Load`가 호출된다. `null`을 반환하면 CLR이 기본 ALC로 폴백하고, 기본 ALC가 이들을 올바르게 해석한다.
>
> **.NET 런타임 BCL 어셈블리를 자기 ALC에 로드하려고 시도하지 마라.** 이 시스템 어셈블리들은 기본 ALC 밖에서 실행되도록 설계되지 않았고, 자기 ALC에 로드하려는 시도는 잘못된 동작, 성능 저하, 예상치 못한 타입 비호환을 낳을 수 있다.

사용법은 이렇다.

```csharp
var alc = new FolderBasedALC(@"c:\temp");
Assembly foo = alc.LoadFromAssemblyPath(@"c:\temp\foo.dll");
```

이후 `foo` 어셈블리의 코드를 호출하기 시작하면, 어느 시점에 CLR이 `bar.dll` 의존성을 해석해야 한다. 이때 커스텀 ALC의 `Load` 메서드가 발생하고 `c:\temp`에서 `bar.dll`을 성공적으로 찾는다.

이 경우 `Load` 메서드는 `foo.dll`도 해석할 수 있으므로 이렇게 간단히 쓸 수도 있다.

```csharp
var alc = new FolderBasedALC(@"c:\temp");
Assembly foo = alc.LoadFromAssemblyName(new AssemblyName("foo"));
```

대안으로 `Resolving` 이벤트를 쓸 수도 있다.

```csharp
var alc = new AssemblyLoadContext("test");
alc.Resolving += (loadContext, assemblyName) =>
{
    string targetPath = Path.Combine(@"c:\temp", assemblyName.Name + ".dll");
    return alc.LoadFromAssemblyPath(targetPath);
};
Assembly foo = alc.LoadFromAssemblyName(new AssemblyName("foo"));
```

이제는 어셈블리가 존재하는지 검사할 필요가 없다. `Resolving` 이벤트는 기본 ALC가 어셈블리를 해석할 기회를 가진 **후에만**(그리고 실패했을 때만) 발생하므로, .NET BCL 어셈블리에 대해서는 핸들러가 발생하지 않는다.

**하지만 단점이 있다.** 이 시나리오에서 메인 애플리케이션은 `foo.dll`이나 `bar.dll`을 컴파일 타임에 몰랐다. 즉 메인 애플리케이션 자신이 `foo.dll`이나 `bar.dll`이라는 이름의 어셈블리에 의존할 **가능성**이 있다. 그런 일이 생기면 `Resolving` 이벤트는 아예 발생하지 않고 애플리케이션의 `foo`, `bar` 어셈블리가 대신 로드된다. **격리 달성에 실패하는 것이다.**

> **📌 `FolderBasedALC`는 교육용이다**
>
> `FolderBasedALC` 클래스는 어셈블리 해석 개념을 설명하기엔 좋지만 실무에서는 쓸모가 적다. **플랫폼별 의존성**과 (라이브러리 프로젝트의 경우) **개발 시점 NuGet 의존성**을 다루지 못하기 때문이다. 해법은 52.11절의 `AssemblyDependencyResolver`이고, 완전한 예제는 52.14절에 있다.

### 기본 ALC

애플리케이션이 시작되면 CLR은 특별한 ALC를 정적 `AssemblyLoadContext.Default` 속성에 할당한다. 기본 ALC는 **시작 어셈블리**가 로드되는 곳이고, 그 **정적 참조 의존성**과 **.NET 런타임 BCL 어셈블리**도 여기 로드된다.

기본 ALC는 어셈블리를 자동 해석하기 위해 먼저 **기본 프로빙 경로**를 본다(52.15절). 이는 보통 애플리케이션의 `.deps.json`과 `.runtimeconfig.json` 파일이 가리키는 위치에 해당한다.

기본 프로빙 경로에서 어셈블리를 찾지 못하면 `Resolving` 이벤트가 발생한다. 이 이벤트를 처리하면 다른 위치에서 어셈블리를 로드할 수 있고, 따라서 애플리케이션의 의존성을 하위 폴더, 공유 폴더, 심지어 호스트 어셈블리 안의 바이너리 리소스 같은 추가 위치에 배포할 수 있다.

```csharp
AssemblyLoadContext.Default.Resolving += (loadContext, assemblyName) =>
{
    // assemblyName을 찾아 Assembly 객체나 null을 반환한다.
    // 보통 파일을 찾은 뒤 LoadFromAssemblyPath를 호출한다.
    // ...
};
```

기본 ALC의 `Resolving` 이벤트는 **커스텀 ALC가 해석에 실패하고**(즉 그 `Load` 메서드가 `null`을 반환하고) **기본 ALC도 어셈블리를 해석할 수 없을 때**도 발생한다.

`Resolving` 이벤트 밖에서 기본 ALC에 어셈블리를 로드할 수도 있다. 하지만 그 전에 별도 ALC를 쓰거나 다음 절의 접근법(실행 중인 ALC, 컨텍스트 ALC)으로 문제를 더 잘 풀 수 있는지 먼저 판단하라.

> **⚠️ 기본 ALC에 하드코딩하면 코드가 부서지기 쉬워진다**
>
> 기본 ALC에 하드코딩하면 코드 전체를 격리할 수 없게 된다(예: 단위 테스트 프레임워크나 LINQPad에 의해). 이건 실제로 문제가 된다 — 테스트 러너가 여러 테스트를 격리하려 할 때 당신의 라이브러리만 기본 ALC를 고집하면 격리가 깨진다.

그래도 진행하겠다면, **로딩 메서드(`LoadFromAssemblyPath`)보다 해석 메서드(`LoadFromAssemblyName`)를 호출하는 편이 낫다** — 특히 어셈블리가 정적으로 참조된 경우에. 어셈블리가 이미 로드되어 있을 가능성이 있는데, 그 경우 `LoadFromAssemblyName`은 이미 로드된 어셈블리를 반환하지만 `LoadFromAssemblyPath`는 **예외를 던지기** 때문이다. (`LoadFromAssemblyPath`는 ALC의 기본 해석 메커니즘이 찾을 위치와 **다른 곳에서** 어셈블리를 로드할 위험도 있다.)

어셈블리가 ALC가 자동으로 찾지 못할 위치에 있다면, 위 절차를 따르면서 **추가로 ALC의 `Resolving` 이벤트도 처리하면 된다.**

`LoadFromAssemblyName`을 호출할 때 전체 이름을 줄 필요는 없다. 단순 이름으로 충분하고, 어셈블리가 강력한 이름을 가져도 유효하다.

```csharp
AssemblyLoadContext.Default.LoadFromAssemblyName(new AssemblyName("System.Xml"));
```

다만 이름에 공개 키 토큰을 포함시켰다면, 로드된 것과 일치해야 한다.

> **⚠️ 문자열 오버로드는 없다**
>
> `LoadFromAssemblyName`의 시그니처는 `AssemblyLoadContext`가 제공하는 유일한 형태인 `LoadFromAssemblyName(AssemblyName)` 하나뿐이다. 문자열을 바로 넘기는 오버로드는 존재하지 않으므로 `new AssemblyName(...)`으로 감싸야 한다. 문자열을 바로 받는 것은 `Assembly.Load(string)` 쪽이다(뒤에서 다룬다).

### "현재" ALC

앞 절에서 기본 ALC에 명시적으로 어셈블리를 로드하는 것을 경고했다. 보통 원하는 것은 **"현재" ALC**에 로드/해석하는 것이다.

대부분의 경우 "현재" ALC는 현재 실행 중인 어셈블리를 담은 ALC다.

```csharp
var executingAssem = Assembly.GetExecutingAssembly();
var alc = AssemblyLoadContext.GetLoadContext(executingAssem);

Assembly assem = alc.LoadFromAssemblyName(...);   // 이름으로 해석
// 또는: = alc.LoadFromAssemblyPath(...);          // 경로로 로드
```

더 유연하고 명시적인 방법은 이렇다.

```csharp
var myAssem = typeof(SomeTypeInMyAssembly).Assembly;
var alc = AssemblyLoadContext.GetLoadContext(myAssem);
```

때로는 "현재" ALC를 **추론할 수 없다.** .NET 바이너리 직렬화기를 당신이 작성한다고 하자. 직렬화기는 직렬화하는 타입의 전체 이름(어셈블리 이름 포함)을 기록하고, 이는 역직렬화 시 해석되어야 한다. 문제는 **어떤 ALC를 써야 하느냐**다. 실행 중인 어셈블리에 의존하면 **역직렬화기를 담은 어셈블리**가 반환되지, **역직렬화기를 호출하는 어셈블리**가 반환되지 않는다.

최선의 해법은 추측하지 말고 **묻는 것**이다.

```csharp
public object Deserialize(Stream stream, AssemblyLoadContext alc)
{
    ...
}
```

명시적으로 만들면 유연성이 최대가 되고 실수 가능성이 최소가 된다. 이제 호출자가 무엇을 "현재" ALC로 볼지 결정할 수 있다.

```csharp
var assem = typeof(SomeTypeThatIWillBeDeserializing).Assembly;
var alc = AssemblyLoadContext.GetLoadContext(assem);
var obj = Deserialize(someStream, alc);
```

### `Assembly.Load`와 컨텍스트 ALC

현재 실행 중인 ALC에 어셈블리를 로드하는 흔한 경우를 돕기 위해, Microsoft는 `Assembly` 클래스에 다음 메서드를 정의했다.

```csharp
public static Assembly Load(string assemblyString);
public static Assembly Load(AssemblyName assemblyRef);
```

> **⚠️ 레거시 `Load(byte[])`와 혼동하지 마라**
>
> 이 메서드들을 레거시 `Load(byte[])` 메서드와 **혼동하면 안 된다.** 완전히 다르게 동작한다(52.13절).

`LoadFromAssemblyName`처럼 단순 이름, 부분 이름, 전체 이름 중 무엇을 지정해도 된다.

```csharp
Assembly a = Assembly.Load("System.Private.Xml");
```

.NET에서는 다음 문자열들도 모두 유효하고 같은 결과를 낸다.

```text
"System.Private.Xml, PublicKeyToken=cc7b13ffcd2ddd51"
"System.Private.Xml, Version=4.0.1.0"
"System.Private.Xml, Version=4.0.1.0, PublicKeyToken=cc7b13ffcd2ddd51"
```

공개 키 토큰을 지정하기로 했다면 로드된 것과 일치해야 한다.

> **📌 MSDN의 경고는 .NET Framework 이야기다**
>
> MSDN은 부분 이름으로 어셈블리를 로드하지 말고 정확한 버전과 공개 키 토큰을 지정하라고 경고한다. 그 근거는 전역 어셈블리 캐시와 코드 접근 보안(CAS)의 효과 같은 **.NET Framework에 해당하는 요인**들이다. .NET 5+와 .NET Core에는 이런 요인이 없으므로 단순 이름이나 부분 이름으로 로드해도 일반적으로 안전하다.

이 두 메서드는 **엄격히 해석용**이므로 파일 경로를 지정할 수 없다. (`AssemblyName` 객체의 `CodeBase` 속성을 채워도 무시된다.)

> **⚠️ 정적 참조된 어셈블리를 `Assembly.Load`로 로드하지 마라**
>
> 이 경우 필요한 것은 그 어셈블리의 타입 하나를 참조하고 그로부터 어셈블리를 얻는 것뿐이다.
>
> ```csharp
> Assembly a = typeof(System.Xml.Formatting).Assembly;
> ```
>
> 심지어 이렇게도 할 수 있다.
>
> ```csharp
> Assembly a = System.Xml.Formatting.Indented.GetType().Assembly;
> ```
>
> 이렇게 하면 어셈블리 이름을 하드코딩하지 않으면서(나중에 바뀔 수 있다) `Assembly.Load`와 동일하게 실행 코드의 ALC에서 어셈블리 해석을 촉발한다.

`Assembly.Load` 메서드를 직접 작성한다면 (거의) 이렇게 생겼을 것이다.

```csharp
[MethodImpl(MethodImplOptions.NoInlining)]
Assembly Load(string name)
{
    Assembly callingAssembly = Assembly.GetCallingAssembly();
    var callingAlc = AssemblyLoadContext.GetLoadContext(callingAssembly);
    return callingAlc.LoadFromAssemblyName(new AssemblyName(name));
}
```

`[MethodImpl(MethodImplOptions.NoInlining)]`가 붙은 이유를 놓치지 말자. 인라이닝되면 `GetCallingAssembly()`가 엉뚱한 어셈블리를 반환한다.

### `EnterContextualReflection`

`Assembly.Load`가 호출 어셈블리의 ALC 컨텍스트를 쓰는 전략은, `Assembly.Load`가 **중개자**(역직렬화기나 단위 테스트 러너 등)를 통해 호출될 때 실패한다. 중개자가 다른 어셈블리에 정의되어 있다면 **호출자의 로드 컨텍스트 대신 중개자의 로드 컨텍스트**가 쓰인다.

이런 시나리오에서도 `Assembly.Load`가 동작하게 하려고, Microsoft는 `AssemblyLoadContext`에 `EnterContextualReflection`이라는 메서드를 추가했다. 이 메서드는 ALC를 `AssemblyLoadContext.CurrentContextualReflectionContext`에 할당한다.

정적 속성이지만 값은 `AsyncLocal` 변수에 저장되므로, **스레드마다 다른 값을 가지면서도 비동기 연산 전반에 걸쳐 보존된다**(49.9절에서 `AsyncLocal<T>`를 다룬다).

이 속성이 `null`이 아니면 `Assembly.Load`는 호출 ALC보다 이것을 **우선해서** 자동으로 사용한다.

```csharp
Method1();

var myALC = new AssemblyLoadContext("test");
using (myALC.EnterContextualReflection())
{
    Console.WriteLine(
        AssemblyLoadContext.CurrentContextualReflectionContext.Name);  // test
    Method2();
}

// Dispose되고 나면 EnterContextualReflection()은 더 이상 효과가 없다.
Method3();

void Method1() => Assembly.Load("...");   // 호출 ALC 사용
void Method2() => Assembly.Load("...");   // myALC 사용
void Method3() => Assembly.Load("...");   // 호출 ALC 사용
```

컨텍스트 리플렉션 컨텍스트를 고려한 더 정확한 `Load` 구현은 이렇다.

```csharp
[MethodImpl(MethodImplOptions.NoInlining)]
Assembly Load(string name)
{
    var alc = AssemblyLoadContext.CurrentContextualReflectionContext
           ?? AssemblyLoadContext.GetLoadContext(Assembly.GetCallingAssembly());

    return alc.LoadFromAssemblyName(new AssemblyName(name));
}
```

컨텍스트 리플렉션 컨텍스트는 레거시 코드를 돌아가게 하는 데 유용하지만, **더 견고한 해법은 `Assembly.Load`를 호출하는 코드를 수정해서 호출자가 넘긴 ALC의 `LoadFromAssemblyName`을 호출하게 하는 것이다.**

> **📌 .NET Framework에는 왜 이게 없나**
>
> .NET Framework에는 같은 `Assembly.Load` 메서드가 있으면서도 `EnterContextualReflection`에 해당하는 것이 없고, 필요하지도 않다. .NET Framework에서 격리는 주로 ALC가 아니라 **애플리케이션 도메인**으로 이루어지기 때문이다. 애플리케이션 도메인은 더 강한 격리 모델을 제공하며, 각 애플리케이션 도메인이 **자기만의 기본 로드 컨텍스트**를 갖는다. 그래서 기본 로드 컨텍스트만 써도 격리가 동작한다.

## 52.11 비관리 라이브러리 로딩과 해석, `AssemblyDependencyResolver`

### 네이티브 라이브러리 해석

ALC는 네이티브 라이브러리도 로드하고 해석할 수 있다. 네이티브 해석은 `[DllImport]` 특성이 붙은 외부 메서드를 호출할 때 촉발된다.

```csharp
[DllImport("SomeNativeLibrary.dll")]
static extern int SomeNativeMethod(string text);
```

`[DllImport]` 특성에 전체 경로를 지정하지 않았으므로, `SomeNativeMethod`를 호출하면 **`SomeNativeMethod`가 정의된 어셈블리를 담은 ALC**에서 해석이 촉발된다.

ALC의 가상 해석 메서드는 `LoadUnmanagedDll`, 로딩 메서드는 `LoadUnmanagedDllFromPath`다.

```csharp
protected override IntPtr LoadUnmanagedDll(string unmanagedDllName)
{
    // unmanagedDllName의 전체 경로를 찾는다...
    string fullPath = ...;
    return LoadUnmanagedDllFromPath(fullPath);   // DLL 로드
}
```

파일을 찾지 못하면 `IntPtr.Zero`를 반환한다. 그러면 CLR이 ALC의 `ResolvingUnmanagedDll` 이벤트를 발생시킨다.

흥미롭게도 `LoadUnmanagedDllFromPath` 메서드는 `protected`라서 `ResolvingUnmanagedDll` 이벤트 핸들러에서는 보통 호출할 수 없다. 하지만 정적 `NativeLibrary.Load`를 호출하면 같은 결과를 얻는다.

```csharp
someALC.ResolvingUnmanagedDll += (requestingAssembly, unmanagedDllName) =>
{
    return NativeLibrary.Load("(비관리 DLL의 전체 경로)");
};
```

> **⚠️ 네이티브 라이브러리는 ALC에 속하지 않는다**
>
> 네이티브 라이브러리는 보통 ALC가 해석하고 로드하지만, ALC에 **"속하지" 않는다.** 로드된 후 네이티브 라이브러리는 독립적으로 서고, 자신이 가질 수 있는 전이적 의존성을 스스로 해석할 책임을 진다.
>
> 게다가 네이티브 라이브러리는 **프로세스 전역**이다. 따라서 파일 이름이 같은 네이티브 라이브러리를 두 가지 버전으로 로드하는 것은 **불가능하다.** 관리 어셈블리는 ALC를 나누면 버전 격리가 되지만 네이티브는 안 된다. 플러그인 두 개가 서로 다른 버전의 같은 네이티브 라이브러리를 필요로 하면 방법이 없다 — 이것이 ALC 격리의 근본적 한계다.

### `AssemblyDependencyResolver`

52.15절에서 보겠지만, 기본 ALC는 `.deps.json`과 `.runtimeconfig.json` 파일을 읽어 플랫폼별 의존성과 개발 시점 NuGet 의존성을 어디서 찾을지 결정한다.

플랫폼별 또는 NuGet 의존성이 있는 어셈블리를 커스텀 ALC에 로드하려면 이 로직을 어떻게든 재현해야 한다. 설정 파일을 파싱하고 플랫폼별 모니커 규칙을 조심스럽게 따라가면 되겠지만, **어렵기만 한 게 아니라 나중 .NET 버전에서 규칙이 바뀌면 당신이 쓴 코드가 깨진다.**

`AssemblyDependencyResolver` 클래스가 이 문제를 푼다. 의존성을 조사하고 싶은 어셈블리의 경로로 인스턴스화한다.

```csharp
var resolver = new AssemblyDependencyResolver(@"c:\temp\foo.dll");
```

의존성의 경로를 찾으려면 `ResolveAssemblyToPath`를 호출한다.

```csharp
string path = resolver.ResolveAssemblyToPath(new AssemblyName("bar"));
```

`.deps.json` 파일이 없거나 `bar.dll`과 관련된 내용이 없으면 결과는 `c:\temp\bar.dll`이 된다.

비관리 의존성도 `ResolveUnmanagedDllToPath`로 비슷하게 해석할 수 있다.

### 왜 필요한지 보여주는 예제

더 복잡한 시나리오를 보자. `ClientApp`이라는 새 콘솔 프로젝트를 만들고 `Microsoft.Data.SqlClient` NuGet 참조를 추가한다.

```csharp
using Microsoft.Data.SqlClient;

namespace ClientApp
{
    public class Program
    {
        public static SqlConnection GetConnection() => new SqlConnection();
        static void Main() => GetConnection();   // 해석되는지 테스트
    }
}
```

빌드하고 출력 폴더를 보면 `Microsoft.Data.SqlClient.dll` 파일이 보인다. **그런데 이 파일은 실행 시 절대 로드되지 않는다.** 명시적으로 로드하려고 하면 예외가 난다.

실제로 로드되는 어셈블리는 `runtimes\win`(또는 `runtimes/unix`) 하위 폴더에 있다. 기본 ALC는 `ClientApp.deps.json`을 파싱하기 때문에 그것을 로드할 줄 안다.

다른 애플리케이션에서 `ClientApp.dll` 어셈블리를 로드하려 한다면, 그 의존성 `Microsoft.Data.SqlClient.dll`을 해석할 수 있는 ALC를 작성해야 한다. 이때 `ClientApp.dll`이 있는 폴더만 뒤지는 것으로는 **불충분하다**(`FolderBasedALC`가 하던 방식). 대신 `AssemblyDependencyResolver`로 현재 플랫폼에서 그 파일이 어디 있는지 알아내야 한다.

```csharp
string path = @"C:\source\ClientApp\bin\Debug\net8.0\ClientApp.dll";
var resolver = new AssemblyDependencyResolver(path);
var sqlClient = new AssemblyName("Microsoft.Data.SqlClient");
Console.WriteLine(resolver.ResolveAssemblyToPath(sqlClient));
```

Windows 머신에서는 다음이 출력된다.

```text
C:\source\ClientApp\bin\Debug\net8.0\runtimes\win\lib\netcoreapp2.1\Microsoft.Data.SqlClient.dll
```

> **📌 마지막 폴더 이름은 패키지 버전에 따라 다르다**
>
> `netcoreapp2.1` 부분은 그 NuGet 패키지가 내부적으로 어떤 TFM으로 라이브러리를 배포하느냐에 달렸다. 최신 `Microsoft.Data.SqlClient`라면 `net8.0`이나 `netstandard2.0`이 나올 수 있다. 중요한 것은 경로의 **모양** — `runtimes\<RID>\lib\<TFM>\` — 이지 구체적 값이 아니다.

이것이 `FolderBasedALC` 같은 순진한 구현이 실무에서 실패하는 이유다.

## 52.12 ALC 언로드와 수집 가능(collectible) 어셈블리

### 어셈블리를 언로드하고 싶은 이유

어셈블리는 자기가 참조하는 다른 어셈블리를 매니페스트에 기술한다. 표준 CLR 동작은 **참조된 모든 어셈블리를 주 애플리케이션 도메인에 로드하는 것** — 즉 프로그램 실행 내내 살아 있을 도메인에 로드하는 것이다. 대부분의 경우 괜찮지만, 어셈블리의 수명을 더 통제하고 싶은 경우가 있다.

- **스크립팅** — 애플리케이션에서 사용자 정의 스크립트를 실행할 수 있게 한다면(예: Roslyn API로 컴파일), 스크립트를 임시 어셈블리로 컴파일하고 더는 필요 없어지면 삭제하는 것이 이상적이다.
- **객체 관계 매핑(ORM)** — 데이터베이스 데이터를 .NET 객체로 매핑하되, 애플리케이션 전체 수명 동안 유지할 필요는 없을 수 있다. 특히 여러 다른 소스에 일시적으로 연결하는 애플리케이션이라면 더욱.
- **직렬화기** — 다양한 엔티티(파일이든 HTTP 요청이든)를 직렬화/역직렬화할 때, 많은 직렬화기가 성능을 위해 임시 어셈블리를 만든다. 더는 필요 없는 임시 어셈블리를 정리할 수 있으면 좋다.
- **플러그인** — 사용자 제공 플러그인을 로드해 확장성을 제공한다면, 필요에 따라 로드하고 언로드할 수 있어야 한다.

.NET Framework에서는 어셈블리가 로드된 **애플리케이션 도메인 전체를 언로드**함으로써 간접적으로 어셈블리를 언로드할 수 있었다. 사용자 정의 스크립트를 다루는 전형적 시나리오는 동적 애플리케이션 도메인을 만들고, 컴파일된 스크립트로 어셈블리를 방출하고, 임시 도메인에 로드하고, 코드를 실행하고, 결국 그 도메인을 언로드하는 것이었다. 완벽히 동작하는 해법이었지만 나름의 함정이 있었다 — 특히 **애플리케이션 도메인 간 리모팅 통신 비용**이 문제였다.

> **⚠️ 그래서 실무에서는 언로드를 포기했다**
>
> 앞서 말한 오버헤드 때문에 동적 어셈블리는 종종 **주 애플리케이션 도메인에 로드된다** — 나중에 언로드할 수 없다는 것을 감수하고서(언로드하려면 애플리케이션 자체를 언로드해야 하므로). .NET에서 흔히 만나는 `XmlSerializer`가 이 경우에 해당해 메모리 누수로 이어질 수 있다. 다만 조건부다 — `XmlSerializer(Type)` 같은 기본 생성자로 만든 직렬화기는 내부 캐시가 재사용하지만, `XmlRootAttribute`나 추가 타입 배열을 받는 생성자는 호출할 때마다 새 어셈블리를 방출한다. 루프 안에서 그런 생성자를 호출하면 어셈블리가 계속 쌓인다.

### 수집 가능 어셈블리

그래서 더 가벼운 **수집 가능 어셈블리(collectible assembly)** 라는 아이디어가 나왔다. 수집 가능 어셈블리는 **자신이 사는 애플리케이션 도메인을 언로드하지 않고도 언로드할 수 있는 동적 어셈블리**다. 앞서 말한 모든 시나리오에서 완벽하게 말이 된다.

**.NET Core 3.0부터 수집 가능 `AssemblyLoadContext`를 통해 어셈블리를 로드하고 언로드할 수 있다.**

> **📌 .NET Framework의 부분적 구현**
>
> .NET Framework에도 수집 가능 어셈블리가 구현되어 있지만 **부분적으로만** — `Reflection.Emit`으로 코드를 수동 방출하는 경우에 한해서다. Microsoft 문서의 표현을 빌리면 "리플렉션 방출이 수집 가능 어셈블리를 로드하기 위해 지원되는 유일한 메커니즘이다. 다른 어떤 형태의 어셈블리 로딩으로 로드된 어셈블리도 언로드할 수 없다."

### 언로드하는 법

기본이 아닌 `AssemblyLoadContext`를 언로드해 메모리를 해제하고 그것이 로드한 어셈블리에 대한 파일 잠금을 푸는 것이 단순한 경우에는 가능하다. 이것이 동작하려면 ALC가 `isCollectible` 매개변수를 `true`로 해서 인스턴스화되었어야 한다.

```csharp
var alc = new AssemblyLoadContext("test", isCollectible: true);
```

그다음 ALC의 `Unload` 메서드를 호출해 언로드 과정을 시작한다.

```csharp
alc.Unload();
```

### 협력적 언로드의 의미

언로드 모델은 **선점적(preemptive)이 아니라 협력적(cooperative)** 이다.

- ALC의 어셈블리 중 어떤 메서드라도 실행 중이면, 그 메서드들이 끝날 때까지 언로드가 **연기된다.**
- 실제 언로드는 **가비지 컬렉션 중에** 일어난다.
- ALC 외부의 무언가가 ALC 내부의 무언가에 대해 (약한 참조가 아닌) 참조를 하나라도 갖고 있으면 **언로드는 일어나지 않는다.** 객체, 타입, 어셈블리 모두 포함이다.

더 정확히 말하면, 언로드는 다음 두 조건이 만족된 후에 완료된다.

1. **어떤 스레드도** 해당 `AssemblyLoadContext`에 로드된 어셈블리의 메서드를 호출 스택에 갖고 있지 않다.
2. 해당 `AssemblyLoadContext`의 타입 인스턴스에 대한 **핸들과 참조가 더 이상 없다**(약한 참조 제외).

> **⚠️ 언로드 실패는 진단하기 어렵다**
>
> API(BCL의 것 포함)가 정적 필드나 딕셔너리에 객체를 캐싱하거나 이벤트를 구독하는 일은 드물지 않고, 이것이 언로드를 막는 참조를 만들기 쉽다. 특히 ALC 안의 코드가 ALC 밖의 API를 사소하지 않은 방식으로 쓴다면 더욱 그렇다.
>
> **실패한 언로드의 원인을 알아내는 것은 어렵고 WinDbg 같은 도구가 필요하다.** 66장에서 다루는 `!gcroot` 명령이 여기서 쓰인다.
>
> 실무적으로는, 수집 가능 ALC를 도입하기 전에 "정말 언로드가 필요한가, 아니면 별도 프로세스로 격리하는 편이 나은가"를 먼저 물어야 한다. Microsoft 자신도 .NET Core에서 격리를 위해 **프로세스나 컨테이너**를 쓰라고 권한다.

### 참고: AppDomain은 어디로 갔나

.NET Framework은 어셈블리를 애플리케이션 도메인(AppDomain)으로 격리했다. 보안, 신뢰성, 버전 관리 필요 때문에 이런 분리를 원할 수 있었고, **프로세스 주소 공간에서 어셈블리를 언로드하는 유일한 방법**이기도 했다.

.NET Core를 작게 유지하려면 일부 기능을 잘라내야 했고, AppDomain이 그중 하나였다. 제공하는 기능에 비해 유지 비용이 너무 컸다. 그래서 .NET Core에는 **추가 도메인을 만들고 언로드하는 API**(`AppDomain.CreateDomain`, `AppDomain.Unload`)가 제공되지 않는다. 호출하면 `PlatformNotSupportedException`이 난다. 다만 런타임 자신이 내부적으로 도메인을 사용하므로 관련 코드는 여전히 남아 있고, `AppDomain.CurrentDomain`과 그 위의 `AssemblyResolve` 이벤트·`GetAssemblies()` 같은 멤버는 .NET 5+에서도 정상 동작한다(52.13절에서 실제로 쓴다).

.NET 런타임은 여전히 몇 개의 도메인을 만든다.

| 도메인 | 담기는 것 |
|---|---|
| **Shared Domain** | 도메인 간 공유되는 모든 코드. BCL 어셈블리, `System` 네임스페이스 타입 등. .NET Framework에서는 GAC에 저장된 어셈블리도 포함 |
| **System Domain** | 다른 도메인을 만들고 초기화하는 책임을 졌던 곳. 핵심 런타임 컴포넌트가 로드된다. **프로세스 전역 인터닝 문자열 리터럴**도 여기 보관된다(35.5절) |
| **Default Domain** (예: Domain 1) | 사용자 코드가 로드되는 곳 |
| **Dynamic domains** | .NET Framework 애플리케이션이 `AppDomain.CreateDomain`으로 원하는 만큼 만들고 삭제할 수 있었던 도메인. **.NET Core에는 설계상 이 기능이 없다** |

.NET Core에서는 추가 애플리케이션 도메인을 만들 수 없다. 모든 공유 코드를 위한 Shared Domain 하나와 모든 사용자 코드를 위한 기본 AppDomain 하나가 여전히 있을 뿐이다.

## 52.13 레거시 로딩 메서드와 그 함정

.NET Framework을 여전히 쓰고 있다면(또는 .NET Standard를 대상으로 하는 라이브러리를 작성하면서 .NET Framework을 지원하고 싶다면) `AssemblyLoadContext` 클래스를 쓸 수 없다. 대신 다음 메서드로 로딩한다.

```csharp
public static Assembly LoadFrom(string assemblyFile);
public static Assembly LoadFile(string path);
public static Assembly Load(byte[] rawAssembly);
```

| 메서드 | 격리 | 로드되는 곳 |
|---|---|---|
| `LoadFrom(string)` | **없음** | 기본 ALC |
| `LoadFile(string)` | **있음** | 새 ALC (어셈블리당 하나) |
| `Load(byte[])` | **있음** | 새 ALC |

해석은 애플리케이션 도메인의 `AssemblyResolve` 이벤트를 처리해서 이루어지며, 기본 ALC의 `Resolving` 이벤트와 같은 방식으로 동작한다. `Assembly.Load(string)` 메서드도 해석을 촉발하며 비슷하게 동작한다.

### `LoadFrom`

`LoadFrom`은 주어진 경로의 어셈블리를 **기본 ALC**에 로드한다. `AssemblyLoadContext.Default.LoadFromAssemblyPath`를 호출하는 것과 비슷하되 다음이 다르다.

- 같은 단순 이름의 어셈블리가 이미 기본 ALC에 있으면, **예외를 던지는 대신 그 어셈블리를 반환한다.**
- 같은 단순 이름의 어셈블리가 아직 없어서 로드가 일어나면, 그 어셈블리에 특별한 **"LoadFrom" 상태**가 부여된다. 이 상태는 기본 ALC의 해석 로직에 영향을 준다 — 그 어셈블리가 **같은 폴더에** 의존성을 갖는다면 그 의존성들이 **자동으로 해석된다.**

> **⚠️ `LoadFrom`의 편리함이 곧 위험이다**
>
> `LoadFrom`이 전이적 동일 폴더 의존성을 자동 해석하는 능력은 편리하다 — **로드하면 안 되는 어셈블리를 로드하기 전까지는.** 이런 시나리오는 디버깅이 어렵기 때문에, `Load(string)`이나 `LoadFile`을 쓰고 애플리케이션 도메인의 `AssemblyResolve` 이벤트를 처리해 전이적 의존성을 해석하는 편이 나을 수 있다. 그러면 각 어셈블리를 어떻게 해석할지 직접 결정할 수 있고, 이벤트 핸들러 안에 중단점을 걸어 디버깅할 수 있다.

> **📌 .NET Framework에는 GAC가 먼저다**
>
> .NET Framework에는 전역 어셈블리 캐시(GAC)가 있다. 어셈블리가 GAC에 있으면 CLR은 **항상 거기서 로드한다.** 이는 세 로딩 메서드 모두에 적용된다.

### `LoadFile`과 `Load(byte[])`

`LoadFile`과 `Load(byte[])`는 주어진 파일 경로나 바이트 배열에서 어셈블리를 **새 ALC**에 로드한다. `LoadFrom`과 달리 이 메서드들은 격리를 제공하고 같은 어셈블리의 여러 버전을 로드할 수 있게 한다. 다만 주의할 점이 둘 있다.

- **동일한 경로로 `LoadFile`을 다시 호출하면 이전에 로드된 어셈블리가 반환된다.**
- .NET Framework에서는 두 메서드 모두 **먼저 GAC를 확인하고**, 어셈블리가 거기 있으면 거기서 로드한다.

`LoadFile`과 `Load(byte[])`를 쓰면 (위 주의점을 제외하면) **어셈블리마다 별도의 ALC**가 생긴다. 격리는 되지만 관리는 더 번거로워진다.

의존성을 해석하려면 AppDomain의 `AssemblyResolve` 이벤트를 처리한다. 이 이벤트는 **모든 ALC에서** 발생한다.

```csharp
AppDomain.CurrentDomain.AssemblyResolve += (sender, args) =>
{
    string fullAssemblyName = args.Name;
    // Assembly 객체나 null을 반환
    ...
};
```

`args` 변수에는 `RequestingAssembly` 속성도 있어 어떤 어셈블리가 해석을 촉발했는지 알려준다. 어셈블리를 찾은 뒤에는 `Assembly.LoadFile`을 호출해 로드하면 된다.

> **📌 현재 로드된 모든 어셈블리 열거하기**
>
> ```csharp
> AppDomain.CurrentDomain.GetAssemblies()
> ```
>
> 이건 .NET 5+에서도 동작하며 다음과 동등하다.
>
> ```csharp
> AssemblyLoadContext.All.SelectMany(a => a.Assemblies)
> ```

## 52.14 플러그인 시스템 직접 만들기

이 절의 개념을 완전히 보여주기 위해, **언로드 가능한 ALC로 각 플러그인을 격리하는 플러그인 시스템**을 만들어보자.

데모 시스템은 세 개의 .NET 프로젝트로 구성된다.

| 프로젝트 | 종류 | 역할 |
|---|---|---|
| `Plugin.Common` | 라이브러리 | 플러그인이 구현할 인터페이스를 정의 |
| `Capitalizer` | 라이브러리 | 텍스트를 대문자로 바꾸는 플러그인 |
| `Plugin.Host` | 콘솔 앱 | 플러그인을 찾아 호출 |

프로젝트가 다음 디렉터리에 있다고 가정하자.

```text
c:\source\PluginDemo\Plugin.Common
c:\source\PluginDemo\Capitalizer
c:\source\PluginDemo\Plugin.Host
```

세 프로젝트 모두 `Plugin.Common` 라이브러리를 참조하고, **다른 프로젝트 간 참조는 없다.**

> **⚠️ Host가 Capitalizer를 참조하면 플러그인 시스템이 아니다**
>
> `Plugin.Host`가 `Capitalizer`를 참조한다면 우리는 플러그인 시스템을 만드는 게 아니다. 핵심 아이디어는 **`Plugin.Host`와 `Plugin.Common`이 게시된 후에 제3자가 플러그인을 작성한다**는 것이다.
>
> Visual Studio를 쓴다면 데모를 위해 세 프로젝트를 한 솔루션에 넣는 것이 편하다. 그렇게 한다면 `Plugin.Host` 프로젝트를 우클릭 → 빌드 종속성 → 프로젝트 종속성 → `Capitalizer` 체크. 이러면 **참조를 추가하지 않고도** `Plugin.Host`를 실행할 때 `Capitalizer`가 빌드된다.

### Plugin.Common

플러그인은 아주 단순한 일을 한다 — 문자열을 변환한다.

```csharp
namespace Plugin.Common
{
    public interface ITextPlugin
    {
        string TransformText(string input);
    }
}
```

`Plugin.Common`은 이게 전부다.

### Capitalizer (플러그인)

`Capitalizer` 플러그인은 `Plugin.Common`을 참조하고 클래스 하나를 담는다.

```csharp
public class CapitalizerPlugin : Plugin.Common.ITextPlugin
{
    public string TransformText(string input) => input.ToUpper();
}
```

두 프로젝트를 빌드하고 `Capitalizer`의 출력 폴더를 보면 어셈블리가 둘 있다.

```text
Capitalizer.dll       // 플러그인 어셈블리
Plugin.Common.dll     // 참조된 어셈블리
```

### Plugin.Host — 커스텀 ALC

`Plugin.Host`는 클래스 둘을 가진 콘솔 애플리케이션이다. 첫 번째는 플러그인을 로드하는 커스텀 ALC다.

```csharp
class PluginLoadContext : AssemblyLoadContext
{
    AssemblyDependencyResolver _resolver;

    public PluginLoadContext(string pluginPath, bool collectible)
        // 디버깅에 도움이 되도록 친숙한 이름을 준다
        : base(name: Path.GetFileName(pluginPath), collectible)
    {
        // 의존성을 찾도록 도와줄 resolver를 만든다
        _resolver = new AssemblyDependencyResolver(pluginPath);
    }

    protected override Assembly Load(AssemblyName assemblyName)
    {
        // ★ 핵심: 공통 인터페이스 어셈블리는 호스트 것을 쓰게 한다
        if (assemblyName.Name == typeof(ITextPlugin).Assembly.GetName().Name)
            return null;

        string target = _resolver.ResolveAssemblyToPath(assemblyName);
        if (target != null)
            return LoadFromAssemblyPath(target);

        // BCL 어셈블리일 수 있다. 기본 컨텍스트가 해석하게 한다.
        return null;
    }

    protected override IntPtr LoadUnmanagedDll(string unmanagedDllName)
    {
        string path = _resolver.ResolveUnmanagedDllToPath(unmanagedDllName);
        return path == null
            ? IntPtr.Zero
            : LoadUnmanagedDllFromPath(path);
    }
}
```

**`Load` 메서드 첫 줄이 이 예제 전체에서 가장 중요한 세 줄이다.**

```csharp
if (assemblyName.Name == typeof(ITextPlugin).Assembly.GetName().Name)
    return null;
```

`Capitalizer`의 출력 폴더에는 `Plugin.Common.dll` 사본이 있다. 이걸 그대로 플러그인 ALC에 로드하면, 플러그인의 `ITextPlugin`과 호스트의 `ITextPlugin`이 **서로 다른 타입**이 된다(52.9절의 경고). 호스트가 플러그인 인스턴스를 `ITextPlugin`으로 캐스팅하려 하면 이런 예외를 만난다.

```text
InvalidCastException: Unable to cast object of type
'CapitalizerPlugin' to type 'Plugin.Common.ITextPlugin'.
```

메시지만 보면 말이 안 되지만, 실제로는 **이름만 같은 두 개의 다른 타입**이다. `null`을 반환해 기본 ALC로 폴백시키면 호스트와 플러그인이 **같은** `ITextPlugin` 타입을 공유하게 된다.

> **⚠️ 실제로 터지는 예외는 코드에 따라 다르다**
>
> 위 코드처럼 `ExportedTypes.Single(t => typeof(ITextPlugin).IsAssignableFrom(t))`로 타입을 **찾는** 방식이라면, 조건을 만족하는 타입이 하나도 없으므로 캐스팅에 도달하기 전에 `Single()`이 먼저 `InvalidOperationException`("Sequence contains no matching element")을 던진다. 타입 이름을 직접 지정해 찾은 뒤 캐스팅하는 방식이라면 `InvalidCastException`이 난다.
>
> 어느 쪽이든 증상은 같다 — **"플러그인이 인터페이스를 구현하지 않았다"고 호스트가 주장한다.** 예외 타입이 아니라 이 증상을 기억하라.

> **📌 `null` 대신 `typeof(ITextPlugin).Assembly`를 반환해도 된다**
>
> 위 `Load` 메서드에서 `null` 대신 호스트가 이미 로드한 어셈블리를 그대로 반환해도 똑같이 동작한다.
>
> ```csharp
> if (assemblyName.Name == typeof(ITextPlugin).Assembly.GetName().Name)
>     return typeof(ITextPlugin).Assembly;
> ```
>
> 왜 그것이 **호스트의 ALC에서** 해석된다고 확신할 수 있을까? `PluginLoadContext` 클래스가 `Plugin.Host` 어셈블리에 정의되어 있기 때문이다. 이 클래스에서 정적으로 참조한 타입은 **`Plugin.Host`가 로드된 ALC**에서 해석을 촉발한다(52.10절의 "현재 ALC" 규칙). 이 장 전체를 관통하는 규칙 — **해석은 참조가 발생한 어셈블리의 ALC에서 일어난다** — 을 확인시켜주는 대목이다.

> **💡 플러그인 시스템 설계 원칙**
>
> 호스트와 플러그인이 **공유해야 하는 계약 어셈블리**는 반드시 기본 ALC에서 로드되어야 하고, 플러그인의 **고유한 구현과 그 의존성**은 격리된 ALC에서 로드되어야 한다. 이 경계를 명확히 긋는 것이 플러그인 아키텍처 설계의 전부다.

### Plugin.Host — 호출부

```csharp
static string TransformText(string pluginPath, string input, bool unload)
{
    var alc = new PluginLoadContext(pluginPath, collectible: unload);
    try
    {
        // 플러그인 어셈블리를 로드
        Assembly assem = alc.LoadFromAssemblyPath(pluginPath);

        // ITextPlugin을 구현하는 유일한 public 타입을 찾는다
        Type pluginType = assem.ExportedTypes
            .Single(t => typeof(ITextPlugin).IsAssignableFrom(t));

        var plugin = (ITextPlugin)Activator.CreateInstance(pluginType);
        return plugin.TransformText(input);
    }
    finally
    {
        if (unload) alc.Unload();
    }
}
```

```csharp
string pluginPath =
    @"c:\source\PluginDemo\Capitalizer\bin\Debug\net8.0\Capitalizer.dll";

Console.WriteLine(TransformText(pluginPath, "hello world", unload: true));
// HELLO WORLD
```

> **⚠️ 언로드가 실제로 일어나려면**
>
> 위 코드에서 `alc.Unload()`를 호출해도, `plugin` 변수나 `pluginType`, `assem`에 대한 참조가 살아 있는 한 실제 언로드는 일어나지 않는다. 그래서 실무에서는 다음 패턴을 쓴다.
>
> - 플러그인과 상호작용하는 코드 전체를 별도 메서드로 분리하고, `[MethodImpl(MethodImplOptions.NoInlining)]`을 붙인다(JIT이 지역 변수 수명을 늘리지 않도록).
> - `WeakReference`로 ALC를 잡아두고 `GC.Collect()` + `GC.WaitForPendingFinalizers()`를 반복하며 `IsAlive`가 `false`가 되는지 확인한다.
>
> 이 검증 없이 "언로드했다"고 믿으면, 플러그인을 100번 로드한 뒤 메모리가 왜 안 줄어드는지 알 수 없게 된다. 자세한 진단 절차는 66장에서 다룬다.

> **💡 반복 호출한다면 ALC를 캐시하라**
>
> 위 `TransformText`는 호출할 때마다 ALC를 만들고 언로드한다. 데모로는 명확하지만 실무에서는 낭비다. **`TransformText`를 반복 호출해야 한다면 매번 언로드하지 말고 ALC를 캐시하는 편이 낫다.** 어셈블리 로드와 JIT 컴파일을 매번 다시 하기 때문이다. 언로드는 플러그인을 교체하거나 비활성화할 때만 하면 된다.

### 의존성 추가 — 격리가 실제로 동작하는지 보기

지금까지 만든 플러그인은 의존성이 없어서 격리의 이점이 드러나지 않는다. 실제로 확인해보자.

`Capitalizer` 프로젝트에 **Humanizer.Core 2.6.2** 패키지 참조를 추가하고 코드를 이렇게 바꾼다.

```csharp
using Humanizer;

public class CapitalizerPlugin : Plugin.Common.ITextPlugin
{
    public string TransformText(string input) => input.ToUpper();
}
```

그리고 `Pluralizer`라는 두 번째 플러그인 프로젝트를 만들되, **Humanizer.Core 2.7.9**(다른 버전)를 참조하게 한다.

```csharp
using Humanizer;

public class PluralizerPlugin : Plugin.Common.ITextPlugin
{
    public string TransformText(string input) =>
        string.Join(" ", input.Split(' ').Select(w => w.Pluralize()));
}
```

이제 호스트에서 두 플러그인을 **동시에** 로드하고 로드된 어셈블리를 열거해보자.

```csharp
var alc1 = new PluginLoadContext(capitalizerPath, collectible: false);
var alc2 = new PluginLoadContext(pluralizerPath,  collectible: false);

// 각 플러그인을 한 번씩 실행해 Humanizer 의존성이 실제로 해석되게 한다
RunPlugin(alc1, capitalizerPath, "hello world");
RunPlugin(alc2, pluralizerPath,  "hello world");

foreach (var alc in AssemblyLoadContext.All)
    foreach (var a in alc.Assemblies)
        if (a.GetName().Name.StartsWith("Humanizer"))
            Console.WriteLine($"[{alc.Name}] {a.FullName}");
```

출력은 이렇다.

```text
[Capitalizer.dll] Humanizer, Version=2.6.0.0, Culture=neutral, PublicKeyToken=979442b78dfc278e
[Pluralizer.dll]  Humanizer, Version=2.7.0.0, Culture=neutral, PublicKeyToken=979442b78dfc278e
```

**같은 단순 이름의 어셈블리가 서로 다른 버전으로 두 개 로드되어 나란히 살아 있다.** 하나의 ALC 안에서는 불가능한 일이(52.9절의 규칙) ALC를 나눔으로써 가능해졌다. 이것이 격리의 실증이다.

> **💡 버전이 같아도 격리는 이득이다**
>
> 두 플러그인이 **같은 버전**의 Humanizer를 쓰더라도, 어셈블리를 분리하면 각자 **자기만의 정적 변수**를 갖게 된다. 플러그인 A가 설정한 정적 상태가 플러그인 B에 새어 나가지 않는다는 뜻이다. 버전 충돌이 없는 상황에서도 ALC 격리를 쓸 이유가 여기 있다.

## 52.15 어셈블리 탐색 순서, `deps.json`, 프로빙

### GAC는 어디로 갔나

이전 버전의 .NET(Framework)은 프레임워크 파일을 **전역 어셈블리 캐시(GAC)** 에 설치했고, 모든 .NET Framework 애플리케이션이 프레임워크 파일을 어떻게 찾는지 알고 있었다.

그러나 **GAC는 .NET Core의 나란히 실행(side-by-side) 능력을 방해한다.** 그래서 .NET에는 런타임·프레임워크 파일의 단일 저장소가 없다. 대신 프레임워크를 구성하는 파일들이 버전별로 나뉘어 함께 설치된다.

```text
C:\Program Files\dotnet\shared\Microsoft.NETCore.App\8.0.0\
C:\Program Files\dotnet\shared\Microsoft.NETCore.App\9.0.0\
```

애플리케이션의 버전(`.csproj`에 지정된)에 따라 해당 버전 디렉터리에서 필요한 런타임·프레임워크 파일이 로드된다.

### 다섯 개의 프로빙 속성

런타임 버전이 시작될 때, 런타임 호스트는 애플리케이션의 의존성을 찾는 데 쓸 **프로빙 경로 집합**을 제공한다. 다섯 개의 프로빙 속성이 있고 각각은 선택적이다.

| 속성 | 의미 |
|---|---|
| `TRUSTED_PLATFORM_ASSEMBLIES` | 플랫폼·애플리케이션 어셈블리 **파일 경로** 목록 |
| `PLATFORM_RESOURCE_ROOTS` | 위성 리소스 어셈블리를 검색할 **디렉터리 경로** 목록 |
| `NATIVE_DLL_SEARCH_DIRECTORIES` | 비관리(네이티브) 라이브러리를 검색할 디렉터리 경로 목록 |
| `APP_PATHS` | 관리 어셈블리를 검색할 디렉터리 경로 목록 |
| `APP_NI_PATHS` | 관리 어셈블리의 네이티브 이미지를 검색할 디렉터리 경로 목록 |

`AppContext.GetData`로 직접 확인할 수 있다.

```csharp
Console.WriteLine("*** 프로빙 경로 ***");

var list = AppContext.GetData("TRUSTED_PLATFORM_ASSEMBLIES")
                     .ToString()
                     .Split(Path.PathSeparator);   // Windows는 ';', 그 외는 ':'
foreach (var dir in list)
    Console.WriteLine(dir);

Console.WriteLine($"PLATFORM_RESOURCE_ROOTS: "
                + $"{AppContext.GetData("PLATFORM_RESOURCE_ROOTS")}");
Console.WriteLine($"NATIVE_DLL_SEARCH_DIRECTORIES: "
                + $"{AppContext.GetData("NATIVE_DLL_SEARCH_DIRECTORIES")}");
Console.WriteLine($"APP_PATHS: {AppContext.GetData("APP_PATHS")}");
Console.WriteLine($"APP_NI_PATHS: {AppContext.GetData("APP_NI_PATHS")}");
```

실행하면 대부분의 값이 `TRUSTED_PLATFORM_ASSEMBLIES`에서 온다는 것을 알 수 있다. 이 프로젝트의 어셈블리 외에도 현재 런타임 디렉터리(`C:\Program Files\dotnet\shared\Microsoft.NETCore.App\8.0.0` 같은)의 기본 클래스 라이브러리 목록이 보인다.

애플리케이션이 직접 참조하는 각 파일과, 애플리케이션에 필요한 런타임 파일이 목록에 추가된다. **런타임 라이브러리 목록은 .NET 런타임과 함께 로드되는 하나 이상의 `*.deps.json` 파일이 채운다.** SDK 설치 디렉터리(소프트웨어 빌드용)와 런타임 설치 디렉터리(소프트웨어 실행용)에 여러 개가 있다. 단순한 예제라면 쓰이는 파일은 `Microsoft.NETCore.App.deps.json` 하나뿐이다.

애플리케이션이 복잡해질수록 `TRUSTED_PLATFORM_ASSEMBLIES`의 파일 목록도 길어진다. 예를 들어 `Microsoft.EntityFrameworkCore` 패키지 참조를 추가해보자.

```text
dotnet add package Microsoft.EntityFrameworkCore
```

패키지를 추가한 뒤 애플리케이션을 다시 실행하면 목록에 파일이 훨씬 많아진 것을 볼 수 있다. **새 참조는 하나만 추가했는데도** `Microsoft.EntityFrameworkCore` 패키지가 자기 의존성을 갖고 있고, 그것들이 신뢰 파일 목록에 들어가기 때문이다.

### 기본 프로빙 경로

기본 프로빙 경로는 보통 다음으로 구성된다.

- **`AppName.deps.json`에 지정된 경로** (`AppName`은 애플리케이션 주 어셈블리의 이름). 이 파일이 없으면 **애플리케이션 기본 폴더**가 대신 쓰인다.
- **.NET 런타임 시스템 어셈블리를 담은 폴더** (애플리케이션이 프레임워크 종속이라면).

MSBuild가 `AppName.deps.json` 파일을 자동 생성하고, 여기에 모든 의존성을 어디서 찾을지 기술한다. 여기에는 **플랫폼 무관 어셈블리**(애플리케이션 기본 폴더에 놓인다)와 **플랫폼별 어셈블리**(`runtimes\` 하위 디렉터리의 `win`이나 `unix` 같은 하위 폴더에 놓인다)가 포함된다.

생성된 `.deps.json`의 경로는 **애플리케이션 기본 폴더 기준 상대 경로**이거나, `AppName.runtimeconfig.json` 및/또는 `AppName.runtimeconfig.dev.json` 설정 파일의 `additionalProbingPaths` 섹션에 지정한 추가 폴더 기준이다(후자는 개발 환경 전용이다).

```json
// AppName.runtimeconfig.dev.json
{
  "runtimeOptions": {
    "additionalProbingPaths": [
      "C:\\Users\\me\\.nuget\\packages",
      "C:\\Program Files\\dotnet\\sdk\\NuGetFallbackFolder"
    ]
  }
}
```

### 정리 — 전체 해석 흐름

```text
  타입/멤버 참조 발생
        ↓
  AssemblyRef에서 어셈블리 이름 확보
        ↓
  참조가 발생한 어셈블리의 ALC 결정
        ↓
  ┌─────────────────────────────────┐
  │ 1. 이 ALC에서 이미 해석했나?     │→ 예 → 캐시된 Assembly 반환
  └─────────────────────────────────┘
        ↓ 아니오
  ┌─────────────────────────────────┐
  │ 2. ALC.Load() 호출               │
  │    · 기본 ALC → deps.json 기반   │→ 성공 → 반환
  │      프로빙 경로 검색             │
  │    · 커스텀 ALC → 내가 쓴 규칙   │
  └─────────────────────────────────┘
        ↓ null
  ┌─────────────────────────────────┐
  │ 3. 기본 ALC의 Load() 호출        │→ 성공 → 반환
  └─────────────────────────────────┘
        ↓ null
  ┌─────────────────────────────────┐
  │ 4. Resolving 이벤트              │
  │    기본 ALC → 원래 ALC 순서      │→ 성공 → 반환
  └─────────────────────────────────┘
        ↓ null
  ┌─────────────────────────────────┐
  │ 5. AppDomain.AssemblyResolve     │→ 성공 → 반환
  │    (.NET Framework 호환)         │
  └─────────────────────────────────┘
        ↓ null
     FileNotFoundException

  ── "성공 → 반환" 경로는 모두 아래를 거친다 ──

  ┌─────────────────────────────────┐
  │ 온전성 검사                       │
  │  · 단순 이름 일치 (필수)          │
  │  · 공개 키 토큰 일치 (지정 시)    │
  │  · 버전은 불일치해도 통과 ★       │
  └─────────────────────────────────┘
        ↓
     Assembly 반환
```

★ 표시가 실무에서 가장 많은 사고를 만드는 지점이다. 버전이 달라도 로드는 성공하고, 문제는 **없는 메서드를 호출하는 순간** `MissingMethodException`으로 터진다. 컴파일 타임에 참조한 버전과 런타임에 로드된 버전이 다를 수 있다는 사실을 항상 염두에 둬야 한다.

## 이 장의 요약

- **어셈블리는 배포 단위이자 타입 해석의 경계**다. 어셈블리 매니페스트, (선택적) 애플리케이션 매니페스트, 컴파일된 타입, 리소스로 구성되며 매니페스트만 필수다.
- **매니페스트는 네 개의 메타데이터 테이블**(AssemblyDef, FileDef, ManifestResourceDef, ExportedTypesDef)과 AssemblyRef 테이블로 이루어진다. AssemblyDef에는 전체 공개 키가, AssemblyRef에는 8바이트 공개 키 토큰이 들어간다.
- **어셈블리 신원은 네 요소** — 단순 이름, 버전, 문화권, 공개 키 토큰. 단순 이름은 원래 컴파일된 파일 이름에서 오며 리네임해도 바뀌지 않는다.
- **강력한 이름은 .NET 5+에서 중요도가 크게 떨어졌다.** GAC가 없고 서명도 검사되지 않는다. Authenticode는 별개의 시스템으로 게시자 신원을 증명한다.
- **타입 참조 해석**은 IL의 메타데이터 토큰 → MemberRef → TypeRef → AssemblyRef를 따라간다. .NET Framework 어셈블리는 통합(unification)에 의해 CLR 버전에 맞는 것으로 바인딩된다.
- **`AssemblyLoadContext`가 AppDomain을 대체했다.** 로딩·해석·격리 세 역할을 한다. 모든 어셈블리는 정확히 하나의 ALC에 속하고, ALC 안에서 단순 이름은 유일해야 하며, 다른 ALC의 동명 타입은 서로 호환되지 않는다.
- **해석은 5단계**를 거치고, 마지막 온전성 검사에서 **버전 불일치는 통과시킨다.**
- **수집 가능 ALC**(`isCollectible: true`)로 언로드할 수 있지만, 협력적 모델이라 외부 강한 참조가 하나라도 있으면 실패한다.
- **플러그인 시스템의 핵심**은 공유 계약 어셈블리를 기본 ALC에서 로드하고 플러그인 구현만 격리 ALC에 두는 것이다.
