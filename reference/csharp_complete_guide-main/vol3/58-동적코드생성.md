# 58장. 동적 코드 생성

> **이 장의 위치** — 56장에서 IL을 **읽는** 법을, 57장에서 메타데이터를 **읽는** 법을 배웠다. 이 장은 그 둘을 뒤집는다. 런타임에 새 IL을 만들고, 새 타입을 만들고, 그것을 즉시 실행한다. `System.Reflection.Emit`이 그 도구다. 정규식의 `RegexOptions.Compiled`, Entity Framework Core의 지연 로딩 프록시, 대부분의 고성능 직렬화기와 DI 컨테이너가 전부 이 API 위에 서 있다. 57.13절에서 "식 트리로 리플렉션을 대체한다"고 했는데, 그 식 트리 컴파일러가 내부에서 부르는 것도 결국 이것이다.
>
> **선수 지식** — 52장(어셈블리), 56장(CIL 읽기), 57장(리플렉션과 메타데이터), 31장(식 트리와 해석되는 쿼리)
>
> **이 장에서 다루지 않는 것** — IL 옵코드 자체의 의미와 `ildasm` 사용법은 56장에서 끝냈다. 이미 존재하는 메서드의 IL을 **읽어서 파싱**하는 방법(`GetMethodBody`, 디스어셈블러 작성)은 56.9절이다. `dynamic` 키워드와 DLR은 59장, 소스 생성기의 작성법 자체는 57.15절에서 개괄했다.

## 58.1 `DynamicMethod`로 IL 생성하기

### 왜 런타임에 코드를 만드는가

컴파일 타임에 알 수 없는 것이 있고, 그것이 **뜨거운 경로**에 있을 때 동적 코드 생성이 답이 된다.

- **정규식** — `RegexOptions.Compiled`를 주면 .NET은 그 패턴 전용으로 튜닝된 타입을 방출한다. 패턴을 해석하는 루프 대신 패턴 자체가 코드가 된다.
- **ORM** — Entity Framework Core는 지연 로딩(lazy loading)을 위해 엔티티를 상속한 프록시 클래스를 `Reflection.Emit`으로 만든다.
- **직렬화기** — 타입마다 "필드를 읽어 스트림에 쓰는" 코드를 한 번 만들어 캐싱한다. 리플렉션을 100만 번 부르는 것과 전용 메서드를 100만 번 부르는 것의 차이는 두 자릿수다(57.12절).
- **DI 컨테이너** — 생성자 주입 대상의 `new` 호출을 컴파일한다.

공통점은 하나다. **바인딩 비용을 한 번만 내고 실행 비용을 0으로 만든다.** 57.13절에서 `Delegate.CreateDelegate`와 식 트리로 같은 목표를 달성했다. `Reflection.Emit`은 그 사다리의 맨 아래 칸이고, 유일하게 **모든 IL을 표현할 수 있는** 칸이다.

### 가장 가벼운 도구 — `DynamicMethod`

`System.Reflection.Emit`에서 가장 먼저 만날 타입은 `DynamicMethod`다. `TypeBuilder`와 달리 동적 어셈블리와 모듈, 타입을 먼저 세팅할 필요가 없다. 메서드 **하나만** 필요할 때 쓰는 물건이다.

```csharp
using System.Reflection;
using System.Reflection.Emit;

public class Test
{
    static void Main()
    {
        var dynMeth = new DynamicMethod("Foo", null, null, typeof(Test));
        ILGenerator gen = dynMeth.GetILGenerator();
        gen.EmitWriteLine("Hello world");
        gen.Emit(OpCodes.Ret);

        dynMeth.Invoke(null, null);      // Hello world
    }
}
```

네 개의 생성자 인수는 각각 **메서드 이름**, **반환 타입**, **매개변수 타입 배열**, **소유자 타입**이다. 반환 타입과 매개변수 타입에 `null`을 주면 각각 `void`와 매개변수 없음을 뜻한다.

`OpCodes`에는 모든 IL 옵코드에 대응하는 정적 읽기 전용 필드가 있다. 기능의 대부분이 옵코드로 노출되지만, `ILGenerator`는 레이블·지역 변수·예외 처리를 위한 전용 메서드도 갖고 있다. **메서드는 항상 `OpCodes.Ret`으로 끝나야 한다** — 아니면 분기나 예외 던지기 같은 다른 제어 이전 명령으로 끝나야 한다.

`EmitWriteLine`은 여러 개의 저수준 옵코드를 방출하는 지름길이다. 직접 풀어 쓰면 이렇다.

```csharp
MethodInfo writeLineStr = typeof(Console).GetMethod("WriteLine",
                                                    new Type[] { typeof(string) })!;
gen.Emit(OpCodes.Ldstr, "Hello world");    // 문자열을 스택에 로드
gen.Emit(OpCodes.Call, writeLineStr);      // 메서드 호출
gen.Emit(OpCodes.Ret);
```

즉 `EmitWriteLine("...")`은 `ldstr` + `call`의 축약이다. `EmitWriteLine`은 `LocalBuilder`나 `FieldInfo`를 받는 오버로드도 있어서, 방출 도중 디버깅용 출력을 끼워 넣기에 좋다.

> **📌 `DynamicMethod`는 수집된다**
>
> `DynamicMethod`와 그것이 만든 IL은 **더 이상 참조되지 않으면 가비지 컬렉션된다.** 그래서 동적 메서드를 반복 생성해도 메모리가 차오르지 않는다. 동적 **어셈블리**로 같은 효과를 보려면 `AssemblyBuilderAccess.RunAndCollect` 플래그가 필요하다(58.6절).
>
> 다만 델리게이트를 만들어 캐싱해 두면 그 델리게이트가 `DynamicMethod`를 살려 두므로 수집되지 않는다. 이건 버그가 아니라 정상 — 캐싱의 목적 자체가 살려 두는 것이다.

### 소유자 타입과 접근성 — `owner`와 `skipVisibility`

생성자에 넘긴 `typeof(Test)`가 무엇을 하는지가 중요하다. 이 인수는 **동적 메서드가 논리적으로 어느 타입에 속하는가**를 정하고, 그 결과로 **그 타입의 비공개 멤버에 접근할 수 있게** 한다.

```csharp
public class Test
{
    static void Main()
    {
        var dynMeth = new DynamicMethod("Foo", null, null, typeof(Test));
        ILGenerator gen = dynMeth.GetILGenerator();

        MethodInfo privateMethod = typeof(Test).GetMethod("HelloWorld",
            BindingFlags.Static | BindingFlags.NonPublic)!;

        gen.Emit(OpCodes.Call, privateMethod);   // private 메서드를 호출한다
        gen.Emit(OpCodes.Ret);

        dynMeth.Invoke(null, null);              // Hello world
    }

    static void HelloWorld()      // private인데도 호출된다
    {
        Console.WriteLine("Hello world");
    }
}
```

생성자 오버로드는 여러 개다. 실무에서 쓸 만한 것을 정리한다.

| 생성자 시그니처(요약) | 접근 범위 |
|---|---|
| `DynamicMethod(string, Type?, Type[]?)` | 익명 호스트 어셈블리에 놓인다. **공개 멤버만** 접근 가능 |
| `DynamicMethod(string, Type?, Type[]?, Type owner)` | `owner` 타입에 논리적으로 소속. `owner`의 **비공개 멤버 접근 가능** |
| `DynamicMethod(string, Type?, Type[]?, Type owner, bool skipVisibility)` | 위와 같되 `skipVisibility=true`면 **JIT의 가시성 검사 자체를 생략** |
| `DynamicMethod(string, Type?, Type[]?, Module m)` | 모듈에 소속. 그 모듈의 `internal` 멤버 접근 가능 |
| `DynamicMethod(string, Type?, Type[]?, Module m, bool skipVisibility)` | 위와 같되 가시성 검사 생략 |
| `DynamicMethod(string, MethodAttributes, CallingConventions, Type?, Type[]?, Module, bool)` | 호출 규약까지 지정하는 완전한 형태 |

> **⚠️ `owner`에 아무 타입이나 넣지 마라**
>
> 원서 예제에는 `new DynamicMethod("Foo", typeof(int), new[]{ typeof(int), typeof(int) }, typeof(void))` 처럼 `typeof(void)`를 소유자로 넘기는 코드가 있다. 동작은 하지만 의미가 없고, `owner` 타입에 **인터페이스·배열·제네릭 매개변수·`ByRef` 타입**을 넘기면 `ArgumentException`이 난다.
>
> 소유자를 지정할 때는 **자신이 통제하는 구체 클래스**를 넘겨라. 남의 타입(특히 BCL 타입)을 소유자로 지정하고 `skipVisibility=true`를 주는 것은 그 타입의 캡슐화를 런타임에 뚫는 행위다. 동작하기는 한다. 하지만 그 타입의 내부 필드 이름이 다음 .NET 버전에서 바뀌면 조용히 깨진다(57.7절에서 같은 경고를 했다).

`skipVisibility`는 **CAS(코드 접근 보안)가 사라진 .NET에서도 유효**하다. 이건 보안 검사가 아니라 JIT이 수행하는 **가시성 검사**를 끄는 스위치이기 때문이다. `private` 필드를 직접 `ldfld`로 읽는 접근자를 만들 때 필요하다.

### 델리게이트로 만들기 — `CreateDelegate`

`Invoke`를 부르는 것은 여전히 리플렉션 호출이다. 인수를 `object[]`에 담고, 값 타입은 박싱되고, 반환값은 `object`로 나온다(57.12절의 비용 표 그대로다). 목적이 성능이라면 **델리게이트로 변환해야** 한다.

```csharp
var func = (Func<int, int, int>) dynMeth.CreateDelegate(typeof(Func<int, int, int>));
int result = func(3, 4);        // 7

// ※.NET 5 부터는 제네릭 오버로드가 있다
var func2 = dynMeth.CreateDelegate<Func<int, int, int>>();
```

> **💡 `Invoke`는 개발 중에만, 운영 코드는 `CreateDelegate`**
>
> `DynamicMethod.Invoke`는 편하지만 호출당 마이크로초 단위의 오버헤드가 있고, 무엇보다 **인수 타입이 틀려도 런타임까지 모른다**. 반면 `CreateDelegate`는 시그니처가 맞지 않으면 그 자리에서 `ArgumentException`을 던진다 — 방출 직후 바로 실패하므로 디버깅이 훨씬 쉽다.
>
> 실무 패턴은 "생성 → `CreateDelegate` → `ConcurrentDictionary`에 캐싱"이다. 생성 비용은 첫 호출에서만 내고, 이후는 델리게이트 호출 비용(간접 호출 한 번)만 남는다.

### IL을 손으로 짜지 말고 베껴라

IL을 처음부터 머리로 짜는 것은 시간 낭비다. 실무 절차는 이렇다. **① 만들고 싶은 코드를 C#으로 먼저 쓴다 → ② Release 빌드로 컴파일한다**(Debug의 `nop`과 여분 분기가 섞이면 혼란스럽다 — 56.2절) **→ ③ `ildasm`·ILSpy·LINQPad·SharpLab으로 IL을 뽑는다**(56.8절, 55.8절) **→ ④ 그 IL을 `gen.Emit(...)` 호출로 기계적으로 옮긴다 → ⑤ 변하는 부분(타입·메서드·상수)만 런타임 값으로 바꾼다.**

> **💡 SharpLab의 "IL" 출력이 가장 빠르다**
>
> sharplab.io에 C# 코드를 붙여 넣고 출력 형식을 IL로 바꾸면 즉시 IL이 나온다. 도구 설치도 프로젝트 생성도 필요 없고 Release 최적화 옵션도 있다. 방출할 IL의 초안을 잡는 데 이보다 빠른 방법은 없다.

## 58.2 평가 스택 다루기와 인수 전달

### 평가 스택 복습

IL의 중심에는 **평가 스택(evaluation stack)** 이 있다(56.2절). 인수가 있는 메서드를 호출하려면 먼저 인수를 스택에 **푸시(로드)** 하고 메서드를 호출한다. 메서드는 필요한 인수를 스택에서 **팝**한다.

정수 하나를 출력하는 예를 보자.

```csharp
var dynMeth = new DynamicMethod("Foo", null, null, typeof(Program));
ILGenerator gen = dynMeth.GetILGenerator();

MethodInfo writeLineInt = typeof(Console).GetMethod("WriteLine",
                                                    new Type[] { typeof(int) })!;

// Ldc_* 옵코드는 여러 타입·크기의 숫자 리터럴을 로드한다.
gen.Emit(OpCodes.Ldc_I4, 123);      // 4바이트 정수를 스택에 푸시
gen.Emit(OpCodes.Call, writeLineInt);
gen.Emit(OpCodes.Ret);

dynMeth.Invoke(null, null);          // 123
```

두 수를 더하려면 각각을 스택에 올리고 `Add`를 부른다. `Add`는 두 값을 팝하고 결과를 다시 푸시한다.

```csharp
gen.Emit(OpCodes.Ldc_I4, 2);          // 4바이트 정수 2를 푸시
gen.Emit(OpCodes.Ldc_I4, 2);          // 4바이트 정수 2를 푸시
gen.Emit(OpCodes.Add);                // 둘을 팝하고 합을 푸시
gen.Emit(OpCodes.Call, writeLineInt); // 합을 팝해서 출력
```

### 스택 추적 — 한 명령씩

`10 / 2 + 1`을 계산하는 방출을 스택 상태와 함께 추적한다. 왼쪽이 바닥, 오른쪽이 꼭대기다.

```text
 방출한 명령                   동작                          실행 후 스택
──────────────────────────────────────────────────────────────────────
 Emit(Ldc_I4, 10)     상수 10 푸시                          [ 10 ]
 Emit(Ldc_I4, 2)      상수 2 푸시                           [ 10, 2 ]
 Emit(Div)            둘 팝, 10/2 푸시                      [ 5 ]
 Emit(Ldc_I4, 1)      상수 1 푸시                           [ 5, 1 ]
 Emit(Add)            둘 팝, 5+1 푸시                       [ 6 ]
 Emit(Call, WriteLine) 하나 팝, void라 푸시 없음             [ ]
 Emit(Ret)            void 메서드 — 스택이 비었으므로 OK      [ ]
```

`1`을 먼저 깔아 두고 `10 / 2`를 나중에 계산하는 순서로도 결과는 같다. 다만 그쪽은 **최대 스택 깊이**가 3이다(위 순서는 2). `ILGenerator`가 `.maxstack`을 자동으로 계산해 주므로 직접 신경 쓸 필요는 없지만, 깊이가 얕은 쪽이 JIT에게 친절하다.

> **⚠️ 이항 연산의 피연산자 순서는 뒤집을 수 없다**
>
> `Div`와 `Sub`는 **먼저 푸시한 값이 좌항**이다. `10 / 2`를 원한다면 반드시 `ldc.i4 10` → `ldc.i4 2` → `div` 순서다. 반대로 하면 `2 / 10`이 되어 정수 나눗셈에서 0이 나온다. 조용히 틀린 값을 내는 전형적 사고이므로, 이항 연산을 방출할 때는 항상 스택 그림을 그려라.
>
> `Add`, `Mul`, `And`, `Or`, `Xor`는 교환법칙이 성립하므로 순서가 무관하다. `Sub`, `Div`, `Rem`, `Shl`, `Shr`, 그리고 `Clt`/`Cgt` 같은 비교는 **순서가 결정적이다.**

### 인수 전달 — `Ldarg` 계열

`Ldarg`와 `Ldarg_XXX` 옵코드가 메서드에 전달된 인수를 스택에 올린다. 값을 반환하려면 메서드가 끝날 때 **정확히 하나의 값**을 스택에 남긴다. 이게 동작하려면 `DynamicMethod` 생성자에서 반환 타입과 매개변수 타입을 지정해야 한다.

**완전한 예제 1 — 두 수를 더하는 `DynamicMethod`**

```csharp
using System.Reflection.Emit;

DynamicMethod dynMeth = new DynamicMethod(
    "Add",
    typeof(int),                                  // 반환 타입 = int
    new[] { typeof(int), typeof(int) },           // 매개변수 타입 = int, int
    typeof(Program));                             // 소유자 타입

ILGenerator gen = dynMeth.GetILGenerator();
gen.Emit(OpCodes.Ldarg_0);      // 첫 인수를 평가 스택에 푸시
gen.Emit(OpCodes.Ldarg_1);      // 둘째 인수를 평가 스택에 푸시
gen.Emit(OpCodes.Add);          // 둘을 더한다 (결과가 스택에 남는다)
gen.Emit(OpCodes.Ret);          // 스택에 값 하나를 남긴 채 반환

// 1) 리플렉션 호출 — 느리다
int r1 = (int) dynMeth.Invoke(null, new object[] { 3, 4 })!;      // 7

// 2) 델리게이트 호출 — 빠르다
var add = dynMeth.CreateDelegate<Func<int, int, int>>();
int r2 = add(3, 4);                                               // 7

Console.WriteLine($"{r1} {r2}");   // 7 7
```

방출된 IL은 다음과 같다.

```il
.method public static int32 Add(int32 A_0, int32 A_1) cil managed
{
  .maxstack  2
  IL_0000:  ldarg.0
  IL_0001:  ldarg.1
  IL_0002:  add
  IL_0003:  ret
}
```

C# `static int Add(int a, int b) => a + b;`를 Release로 컴파일한 IL과 **정확히 같다.** 그래서 JIT이 만들어 내는 기계어도 같고, 인라이닝 여부만 다르다.

> **⚠️ 종료 시 스택 상태를 어기면 CLR이 실행을 거부한다**
>
> 메서드를 빠져나갈 때 평가 스택에는 **정확히 0개 또는 1개**의 항목만 있어야 한다(반환값 유무에 따라). 이를 어기면 CLR이 메서드 실행을 거부한다 — 대개 첫 호출 시점, 즉 JIT이 그 메서드를 컴파일하려는 순간에 `System.InvalidProgramException`이 난다.
>
> 값을 처리하지 않고 스택에서 없애려면 `OpCodes.Pop`을 방출하라. 반환값을 무시하는 C# 한 줄이 IL에서는 `pop` 한 개다(56.2절).

### 인수 인덱스와 옵코드 크기

`Ldarg`에는 크기가 다른 변종이 있다. 정확한 선택이 IL 크기와 유효성을 좌우한다.

| 옵코드 | 피연산자 | 쓰는 경우 |
|---|---|---|
| `Ldarg_0` ~ `Ldarg_3` | 없음 (인덱스가 옵코드에 내장) | 인덱스 0~3. **1바이트**로 가장 작다 |
| `Ldarg_S` | `byte` (0~255) | 인덱스 4~255 |
| `Ldarg` | `short` (부호 없는 16비트) | 인덱스 256 이상 |
| `Ldarga_S` / `Ldarga` | `byte` / `short` | 인수의 **주소**가 필요할 때 (`ref` 반환, 값 타입 메서드 호출) |
| `Starg_S` / `Starg` | `byte` / `short` | 인수 슬롯에 값을 **저장** |

> **⚠️ `Emit(OpCodes.Ldarg, 1)`은 깨진 IL을 만든다**
>
> `ILGenerator.Emit`에는 `int`를 받는 오버로드와 `short`를 받는 오버로드가 **둘 다** 있다. `Ldarg`의 피연산자는 16비트인데 `Emit(OpCodes.Ldarg, 1)`처럼 `int` 리터럴을 넘기면 컴파일러가 `Emit(OpCode, int)`를 고르고 **4바이트를 그대로 기록한다.** 남는 2바이트가 다음 명령으로 해석되어 IL 스트림 전체가 어긋난다.
>
> `ILGenerator`는 이것을 검증하지 않는다. 결과는 `InvalidProgramException`이거나, 운이 나쁘면 접근 위반이다.
>
> 인수 로드는 항상 헬퍼를 통해라.
>
> ```csharp
> static void EmitLdarg(ILGenerator g, int index)
> {
>     switch (index)
>     {
>         case 0: g.Emit(OpCodes.Ldarg_0); return;
>         case 1: g.Emit(OpCodes.Ldarg_1); return;
>         case 2: g.Emit(OpCodes.Ldarg_2); return;
>         case 3: g.Emit(OpCodes.Ldarg_3); return;
>         default:
>             if (index <= byte.MaxValue) g.Emit(OpCodes.Ldarg_S, (byte) index);
>             else                        g.Emit(OpCodes.Ldarg, (short) index);
>             return;
>     }
> }
> ```
>
> 같은 함정이 `Ldloc`/`Stloc`/`Ldc_I4_S`에도 있다. `Ldc_I4_S`의 피연산자는 `sbyte`이므로 `Emit(OpCodes.Ldc_I4_S, (sbyte) n)`이라야 한다.

### 상수 로드 — `Ldc_I4` 계열 고르기

정수 상수도 마찬가지다. `-1`부터 `8`까지는 1바이트 전용 옵코드가 있다.

```csharp
static readonly OpCode[] _ldcShort =
{
    OpCodes.Ldc_I4_M1, OpCodes.Ldc_I4_0, OpCodes.Ldc_I4_1, OpCodes.Ldc_I4_2,
    OpCodes.Ldc_I4_3,  OpCodes.Ldc_I4_4, OpCodes.Ldc_I4_5, OpCodes.Ldc_I4_6,
    OpCodes.Ldc_I4_7,  OpCodes.Ldc_I4_8
};

static void EmitLdcI4(ILGenerator g, int value)
{
    if (value >= -1 && value <= 8)                              g.Emit(_ldcShort[value + 1]);
    else if (value >= sbyte.MinValue && value <= sbyte.MaxValue) g.Emit(OpCodes.Ldc_I4_S, (sbyte) value);
    else                                                         g.Emit(OpCodes.Ldc_I4, value);
}
```

`Emit(OpCodes.Ldc_I4, 6)`도 **유효하다** — `Ldc_I4`의 피연산자가 32비트 정수이므로 `Emit(OpCode, int)` 오버로드가 정확히 맞는다. 다만 5바이트를 쓸 자리에 1바이트로 끝낼 수 있다는 차이만 있다. 방출 코드가 뜨거운 경로라면(예: 인터프리터를 컴파일하는 경우) 이 크기 차이가 JIT 시간과 명령 캐시에 영향을 준다.

> **📌 `ILGenerator`는 최적화하지 않는다**
>
> C# 컴파일러는 `ldc.i4.6`을 알아서 고르지만 `ILGenerator`는 시키는 대로 정확히 방출한다. `Reflection.Emit`에는 **피프홀 최적화가 없다.** 좋은 소식은 JIT이 결국 같은 기계어를 만든다는 것이고, 나쁜 소식은 IL이 커지면 JIT 시간과 인라이닝 판정(55.4절의 IL 크기 임계값)이 불리해진다는 것이다.

## 58.3 지역 변수 생성과 분기

### 지역 변수 — `DeclareLocal`

`ILGenerator.DeclareLocal`이 지역 변수를 선언하고 `LocalBuilder` 객체를 돌려준다. 이 객체를 `Ldloc`(지역 변수 로드)이나 `Stloc`(지역 변수 저장) 같은 옵코드와 함께 쓴다. `Ldloc`은 스택에 푸시하고 `Stloc`은 팝한다.

다음 C# 코드를 방출해 보자.

```csharp
int x = 6;
int y = 7;
x *= y;
Console.WriteLine(x);
```

```csharp
var dynMeth = new DynamicMethod("Test", null, null, typeof(Program));
ILGenerator gen = dynMeth.GetILGenerator();

LocalBuilder localX = gen.DeclareLocal(typeof(int));    // x 선언
LocalBuilder localY = gen.DeclareLocal(typeof(int));    // y 선언

gen.Emit(OpCodes.Ldc_I4, 6);        // 리터럴 6을 스택에 푸시
gen.Emit(OpCodes.Stloc, localX);    // localX에 저장
gen.Emit(OpCodes.Ldc_I4, 7);        // 리터럴 7을 스택에 푸시
gen.Emit(OpCodes.Stloc, localY);    // localY에 저장

gen.Emit(OpCodes.Ldloc, localX);    // localX를 스택에 푸시
gen.Emit(OpCodes.Ldloc, localY);    // localY를 스택에 푸시
gen.Emit(OpCodes.Mul);              // 곱한다
gen.Emit(OpCodes.Stloc, localX);    // 결과를 localX에 저장

gen.EmitWriteLine(localX);          // localX의 값을 출력
gen.Emit(OpCodes.Ret);

dynMeth.Invoke(null, null);          // 42
```

`Emit(OpCode, LocalBuilder)` 오버로드가 있기 때문에 `Ldloc`/`Stloc`에는 앞 절의 크기 함정이 없다. **`ILGenerator`가 `LocalBuilder`의 인덱스를 보고 알아서 `ldloc.0`~`ldloc.3`/`ldloc.s`/`ldloc`을 골라 준다.** 인수(`Ldarg`)에는 이런 편의가 없다는 점이 비대칭이고, 그래서 앞 절의 헬퍼가 필요하다.

> **📌 `InitLocals` — 지역 변수를 0으로 초기화할 것인가**
>
> `.locals init` 디렉티브가 붙으면 CLR이 메서드 진입 시 지역 변수 슬롯을 0으로 채운다(56.2절). `ILGenerator`는 기본으로 이것을 켠다. `MethodBuilder.InitLocals` 또는 `DynamicMethod.InitLocals`를 `false`로 두면 초기화를 생략해 큰 스택 프레임에서 시간을 아낄 수 있지만, **모든 지역 변수를 읽기 전에 반드시 쓴다**는 보장을 직접 져야 한다. 참조 타입 슬롯을 초기화하지 않으면 GC가 쓰레기 포인터를 따라가 프로세스가 죽는다. 확신이 없으면 건드리지 마라.

### 지역 변수의 주소 — `Ldloca`

값 타입의 메서드를 호출하거나 `ref`로 넘기려면 값이 아니라 **주소**가 필요하다.

```csharp
LocalBuilder pt = gen.DeclareLocal(typeof(DateTime));

gen.Emit(OpCodes.Ldloca, pt);                 // DateTime 지역의 주소를 푸시
gen.Emit(OpCodes.Initobj, typeof(DateTime));  // 그 자리를 default(DateTime)으로

gen.Emit(OpCodes.Ldloca, pt);                 // 다시 주소를 푸시
gen.Emit(OpCodes.Call, typeof(DateTime).GetProperty("Year")!.GetGetMethod()!);
```

값 타입의 인스턴스 메서드는 **관리 포인터(`this`)를 받는다**(56.2절). 그래서 `Ldloc`이 아니라 `Ldloca`다. 값을 푸시하고 인스턴스 메서드를 부르면 IL이 유효하지 않다.

### 분기 — 레이블과 `goto`

IL에는 `while`, `do`, `for`가 없다. 전부 **레이블**과 `goto`/조건부 `goto`로 처리한다. `Br`(무조건 분기), `Brtrue`(스택 값이 참이면 분기), `Blt`(첫 값이 둘째보다 작으면 분기) 같은 분기 옵코드가 그 일을 한다. 분기 대상을 정하려면 `DefineLabel`로 `Label` 객체를 얻고, 고정하고 싶은 위치에서 `MarkLabel`을 호출한다.

다음 C# 코드를 방출한다.

```csharp
int x = 5;
while (x <= 10) Console.WriteLine(x++);
```

```csharp
ILGenerator gen = dynMeth.GetILGenerator();

Label startLoop = gen.DefineLabel();       // 레이블 선언
Label endLoop   = gen.DefineLabel();

LocalBuilder x = gen.DeclareLocal(typeof(int));    // int x
gen.Emit(OpCodes.Ldc_I4, 5);
gen.Emit(OpCodes.Stloc, x);                        // x = 5

gen.MarkLabel(startLoop);
gen.Emit(OpCodes.Ldc_I4, 10);              // 10을 스택에 로드
gen.Emit(OpCodes.Ldloc, x);                // x를 스택에 로드
gen.Emit(OpCodes.Blt, endLoop);            // if (10 < x) goto endLoop

gen.EmitWriteLine(x);                      // Console.WriteLine(x)

gen.Emit(OpCodes.Ldloc, x);                // x를 로드
gen.Emit(OpCodes.Ldc_I4, 1);               // 1을 로드
gen.Emit(OpCodes.Add);                     // 더한다
gen.Emit(OpCodes.Stloc, x);                // 결과를 x에 저장

gen.Emit(OpCodes.Br, startLoop);           // 루프 시작으로 되돌아간다

gen.MarkLabel(endLoop);
gen.Emit(OpCodes.Ret);
```

`Blt`가 `if (10 < x) goto endLoop`인 이유는 **먼저 푸시한 값이 좌항**이기 때문이다. `10`을 먼저, `x`를 나중에 푸시했으므로 `10 < x`, 즉 `x > 10`일 때 루프를 빠져나간다. 앞 절에서 경고한 순서 문제가 여기서 실제로 작동한다.

> **⚠️ `MarkLabel`을 잊으면 방출 시점이 아니라 나중에 터진다**
>
> `DefineLabel`로 만든 레이블을 분기 대상으로 쓰고도 `MarkLabel`을 호출하지 않으면, `ILGenerator`는 그 자리에 오프셋을 채워 넣지 못한다. 오류는 `Emit` 시점이 아니라 **IL을 확정하는 시점** — `DynamicMethod.CreateDelegate`/`Invoke`나 `TypeBuilder.CreateType` — 에 나며, 메시지는 대개 `ArgumentException`("Bad label content in ILGenerator")이다.
>
> 같은 레이블에 `MarkLabel`을 **두 번** 호출해도 예외다. 방출 루프에서 레이블을 재사용할 때 흔히 저지른다.

> **⚠️ `.s`(short form) 분기를 직접 고르지 마라**
>
> `Br_S`, `Blt_S` 같은 짧은 형식은 분기 거리가 **-128~127바이트** 안일 때만 유효하다. 방출 시점에는 앞으로 나올 IL의 크기를 모르므로 거리를 예측할 수 없다.
>
> `ILGenerator`는 긴 형식(`Br`, `Blt`)을 넘기면 그대로 4바이트 오프셋으로 방출한다. 안전하다. 반대로 `Br_S`를 넘겼는데 실제 거리가 127을 넘으면 오프셋이 잘려 **엉뚱한 위치로 점프한다.** 손으로 방출할 때는 **항상 긴 형식**을 써라. IL 몇 바이트를 아끼려다 디버깅 불가능한 버그를 만든다.

### `ILGenerator` 메서드 정리

방출에 쓰는 `ILGenerator`의 멤버를 정리한다.

| 멤버 | 하는 일 |
|---|---|
| `Emit(OpCode)` | 피연산자가 없는 옵코드를 방출 |
| `Emit(OpCode, byte/sbyte/short/int/long/float/double)` | 숫자 피연산자를 가진 옵코드를 방출. **크기를 옵코드에 맞춰야 한다** |
| `Emit(OpCode, string)` | `Ldstr`용. 문자열 리터럴을 `#US` 힙에 넣는다 |
| `Emit(OpCode, Type)` | `Box`, `Unbox_Any`, `Castclass`, `Isinst`, `Newarr`, `Initobj`, `Constrained` 등 |
| `Emit(OpCode, MethodInfo)` / `Emit(OpCode, ConstructorInfo)` | `Call`, `Callvirt`, `Newobj`, `Ldftn` 등 |
| `Emit(OpCode, FieldInfo)` | `Ldfld`, `Stfld`, `Ldsfld`, `Stsfld`, `Ldflda` |
| `Emit(OpCode, LocalBuilder)` | `Ldloc`, `Stloc`, `Ldloca` — 짧은 형식을 알아서 고른다 |
| `Emit(OpCode, Label)` / `Emit(OpCode, Label[])` | 분기 / `Switch` |
| `Emit(OpCode, SignatureHelper)` | `Calli`(간접 호출)용 시그니처 |
| `EmitCall(OpCode, MethodInfo, Type[])` | `varargs` 메서드 호출용. 일반 호출에는 `Emit`으로 충분하다 |
| `EmitCalli(...)` | 함수 포인터를 통한 간접 호출 |
| `EmitWriteLine(string/LocalBuilder/FieldInfo)` | `Console.WriteLine` 호출을 통째로 방출. **디버깅에 유용** |
| `DeclareLocal(Type)` / `DeclareLocal(Type, bool pinned)` | 지역 변수 선언. `pinned`는 GC 고정 |
| `DefineLabel()` | 레이블 생성 |
| `MarkLabel(Label)` | 레이블을 현재 위치에 고정 |
| `BeginExceptionBlock()` | `try` 시작. 결과로 `Label`(블록 끝)을 돌려준다 |
| `BeginCatchBlock(Type)` | `catch` 시작 |
| `BeginExceptFilterBlock()` | 예외 필터(`when`) 시작 |
| `BeginFaultBlock()` | `fault` 블록 시작 (C#에 대응 문법 없음) |
| `BeginFinallyBlock()` | `finally` 시작 |
| `EndExceptionBlock()` | 예외 블록 종료 |
| `BeginScope()` / `EndScope()` | 어휘 범위 시작/종료 (디버그 정보용) |
| `ThrowException(Type)` | 예외를 던지는 코드 방출 |
| `UsingNamespace(string)` | 디버거의 지역 변수 평가에 쓸 네임스페이스 지정 |
| `ILOffset` | 현재까지 방출된 IL의 바이트 오프셋. **로그를 남길 때 유용** |

> **💡 `ILOffset`으로 방출 로그를 남겨라**
>
> `ILGenerator`는 방출한 IL을 다시 읽어 주는 API를 제공하지 않는다. 그래서 실무에서는 `ILGenerator`를 감싸는 얇은 래퍼를 만들어 `Emit` 호출마다 `(ILOffset, opcode, operand)`를 리스트에 적어 둔다. `InvalidProgramException`이 났을 때 이 로그가 사실상 유일한 단서다(58.10절에서 다시 다룬다).

## 58.4 객체 생성과 인스턴스 메서드 호출

### `Newobj` — IL의 `new`

C# `new`에 대응하는 옵코드는 `Newobj`다. 생성자를 받아 생성된 객체를 평가 스택에 올린다.

```csharp
var dynMeth = new DynamicMethod("Test", null, null, typeof(Program));
ILGenerator gen = dynMeth.GetILGenerator();

ConstructorInfo ci = typeof(StringBuilder).GetConstructor(Type.EmptyTypes)!;
gen.Emit(OpCodes.Newobj, ci);
```

객체를 스택에 올린 뒤에는 `Call`이나 `Callvirt`로 그 객체의 인스턴스 메서드를 호출할 수 있다. `StringBuilder`의 `MaxCapacity` 프로퍼티를 get 접근자 호출로 읽어 출력해 보자.

```csharp
gen.Emit(OpCodes.Callvirt, typeof(StringBuilder)
                            .GetProperty("MaxCapacity")!.GetGetMethod()!);
gen.Emit(OpCodes.Call, typeof(Console).GetMethod("WriteLine",
                                                 new[] { typeof(int) })!);
gen.Emit(OpCodes.Ret);

dynMeth.Invoke(null, null);      // 2147483647
```

### `Call` vs `Callvirt` — C#의 호출 의미를 흉내 내기

C#의 호출 규칙을 IL로 재현하는 규칙은 간단하다.

- **정적 메서드**와 **값 타입의 인스턴스 메서드**는 `Call`.
- **참조 타입의 인스턴스 메서드**는 (가상 선언 여부와 무관하게) `Callvirt`.

위 예제에서 `MaxCapacity`는 가상이 아닌데도 `Callvirt`를 썼다. 오류가 아니다 — 단지 비가상 호출을 수행할 뿐이다. **참조 타입의 인스턴스 메서드를 항상 `Callvirt`로 부르면 반대 실수를 피할 수 있다.** 즉 가상 메서드를 `Call`로 부르는 사고를 막는다. 그 위험은 실재한다 — 대상 메서드의 작성자가 나중에 선언을 바꿀 수 있기 때문이다. `Callvirt`에는 **수신자가 `null`이 아닌지 검사한다**는 이점도 있다.

> **⚠️ 가상 메서드를 `Call`로 부르면 타입 안전성이 깨진다**
>
> 가상 메서드를 `Call`로 호출하면 가상 디스패치를 우회하고 그 메서드를 **직접** 부른다. 원하는 경우는 거의 없고, 사실상 타입 안전성을 위반한다.
>
> 예를 들어 `typeof(object).GetMethod("ToString")`을 `Call`로 부르면 `StringBuilder`의 `ToString` 재정의를 건너뛰고 `object.ToString()`이 실행된다 — 결과는 내용이 아니라 `"System.Text.StringBuilder"`라는 타입 이름이다. 조용히 틀린 값을 내는 종류의 버그다.
>
> 반대로 `base.Method()` 호출을 방출할 때는 **반드시 `Call`이어야 한다.** `Callvirt`로 방출하면 자기 자신을 다시 부르는 무한 재귀가 되어 `StackOverflowException`으로 프로세스가 죽는다. 프록시나 데코레이터를 방출할 때 가장 흔한 실수다.

인수를 받는 생성자와 인스턴스 메서드를 연달아 부르는 예다. `new StringBuilder("Hello", 1000)`을 만들고 `", world!"`를 덧붙인 뒤 `ToString`을 호출한다.

```csharp
// new StringBuilder ("Hello", 1000) 를 호출한다
ConstructorInfo ci = typeof(StringBuilder).GetConstructor(
    new[] { typeof(string), typeof(int) })!;

gen.Emit(OpCodes.Ldstr, "Hello");        // 문자열을 스택에 로드
gen.Emit(OpCodes.Ldc_I4, 1000);          // 정수를 스택에 로드
gen.Emit(OpCodes.Newobj, ci);            // StringBuilder를 생성

Type[] strT = { typeof(string) };
gen.Emit(OpCodes.Ldstr, ", world!");
gen.Emit(OpCodes.Call, typeof(StringBuilder).GetMethod("Append", strT)!);
gen.Emit(OpCodes.Callvirt, typeof(object).GetMethod("ToString")!);
gen.Emit(OpCodes.Call, typeof(Console).GetMethod("WriteLine", strT)!);
gen.Emit(OpCodes.Ret);

dynMeth.Invoke(null, null);              // Hello, world!
```

스택 추적으로 보면 `Append`가 왜 값을 남기는지가 분명해진다.

```text
 방출한 명령                            실행 후 스택
────────────────────────────────────────────────────────────
 Ldstr "Hello"                        [ "Hello" ]
 Ldc_I4 1000                          [ "Hello", 1000 ]
 Newobj StringBuilder(string,int)     [ sb ]            ← 인수 2개 팝, 객체 1개 푸시
 Ldstr ", world!"                     [ sb, ", world!" ]
 Call StringBuilder.Append(string)    [ sb ]            ← Append는 자기 자신을 반환한다
 Callvirt object.ToString()           [ "Hello, world!" ]
 Call Console.WriteLine(string)       [ ]
 Ret                                  [ ]
```

`Append`가 `StringBuilder`를 반환하기 때문에 스택 깊이가 유지된다. 만약 `void`를 반환하는 메서드였다면 스택이 비어 `ToString` 호출이 실패했을 것이다. **호출을 방출할 때는 반드시 그 메서드의 반환 타입을 확인하라.**

`StringBuilder`의 `ToString`을 직접 지정해도 같은 결과가 나온다.

```csharp
gen.Emit(OpCodes.Callvirt, typeof(StringBuilder).GetMethod("ToString",
                                                           Type.EmptyTypes)!);
```

빈 타입 배열이 필요한 이유는 `StringBuilder`가 `ToString`을 다른 시그니처로 오버로드하고 있기 때문이다(57.5절의 오버로드 해석 규칙과 같다).

### 값 타입 다루기 — `Box`, `Unbox_Any`, `Constrained`

동적 코드 생성에서 가장 자주 틀리는 곳이 값 타입이다. 세 옵코드를 구분해야 한다.

| 옵코드 | 하는 일 | 언제 |
|---|---|---|
| `Box` | 스택 위의 값 타입을 힙에 복사하고 참조를 푸시 | 값 타입을 `object`로 반환할 때 |
| `Unbox_Any` | 박싱된 참조를 값 타입으로 되돌린다. 참조 타입에 쓰면 `Castclass`와 같다 | `object`를 원래 타입으로 되돌릴 때 |
| `Unbox` | 박싱된 객체 **안의 값에 대한 관리 포인터**를 푸시 (복사하지 않는다) | 박스 내부를 제자리에서 수정할 때 |
| `Constrained.` + `Callvirt` | 수신자가 값 타입이면 박싱 없이, 참조 타입이면 가상 호출로 | 제네릭 `T`에 대해 인터페이스 메서드를 부를 때 |

> **⚠️ `Unbox_Any`와 `Castclass`를 바꿔 쓰면 안 된다**
>
> 값 타입에 `Castclass`를 쓰면 IL 검증에 실패하고, 참조 타입에 `Unbox`를 쓰면 `InvalidCastException`이 난다. `object`를 `targetType`으로 되돌릴 때는 `targetType.IsValueType ? Unbox_Any : Castclass`, 반대로 무언가를 `object`로 만들 때는 값 타입이면 `Box`, 참조 타입이면 아무것도 하지 않는다.
>
> 제네릭 매개변수 `T`처럼 **값 타입인지 컴파일 타임에 모르는** 경우에도 `Box`/`Unbox_Any`를 그대로 방출하면 된다 — 런타임이 실제 타입을 보고 처리한다. `IsValueType` 분기는 `Type` 객체가 손에 있을 때의 최적화다.

### 자주 쓰는 옵코드 정리

방출할 때 실제로 손에 잡히는 옵코드를 용도별로 묶는다. 전체 목록과 의미는 56.3절에 있다.

**① 로드·저장**

|---|---|---|
| `Ldarg_0`~`Ldarg_3`, `Ldarg_S`, `Ldarg` | `ldarg.*` | 인수를 푸시. 인스턴스 메서드면 0번이 `this` |

| `Ldfld`, `Stfld`, `Ldflda` | `ldfld`, `stfld`, `ldflda` | 인스턴스 필드. **먼저 `this`를 푸시해야 한다** |

|---|---|---|
| `Call` | `call` | 정적 메서드, 값 타입 인스턴스 메서드, `base` 호출 |
| `Callvirt` | `callvirt` | 참조 타입 인스턴스 메서드. null 검사 포함 |
| `Newobj` | `newobj` | 생성자 호출 후 객체를 푸시 |

| `Stind_I4`, `Stind_R8`, `Stind_Ref` 등 | `stind.*` | 관리 포인터가 가리키는 자리에 저장 |

> **📌 `Ldftn` + `Newobj`로 델리게이트를 만든다**
>
> C# `new Action(obj.Method)`는 IL에서 세 명령이다 — 대상 객체 로드(정적이면 `ldnull`), `ldftn`으로 함수 포인터 로드, 그리고 `newobj Action::.ctor(object, native int)`. 방출할 때도 똑같다. 가상 메서드라면 `Ldftn` 대신 `Ldvirtftn`을 쓰고, 그 앞에서 대상 객체를 `Dup`으로 복제해야 한다 — `Ldvirtftn`이 수신자를 팝하기 때문이다.

### 완전한 예제 2 — 프로퍼티 게터를 컴파일해 리플렉션 대체하기

57.12절에서 `PropertyInfo.GetValue`가 왜 느린지 정리했다. 문자열 검색은 캐싱으로 없앨 수 있지만 **인수 패키징, 박싱, 접근성 검사, 예외 감싸기**는 호출마다 반복된다. 이 비용을 없애는 표준 기법이 "게터를 `Func<object, object>`로 컴파일해 캐싱"하는 것이다.

목표는 다음 C# 코드와 같은 IL을 방출하는 것이다.

```csharp
// 대상: class Person { public string Name { get; set; } }
static object GetName(object instance) => (object) ((Person) instance).Name;
```

방출 코드는 이렇다.

```csharp
using System.Collections.Concurrent;
using System.Reflection;
using System.Reflection.Emit;

public static class FastAccessor
{
    static readonly ConcurrentDictionary<PropertyInfo, Func<object, object?>> _cache = new();

    public static Func<object, object?> GetGetter(PropertyInfo prop)
        => _cache.GetOrAdd(prop, BuildGetter);

    static Func<object, object?> BuildGetter(PropertyInfo prop)
    {
        MethodInfo getter = prop.GetGetMethod(nonPublic: true)
            ?? throw new ArgumentException($"{prop.Name}에 get 접근자가 없다", nameof(prop));

        Type declaring = prop.DeclaringType!;

        // 소유자를 선언 타입으로 지정하고 가시성 검사를 끈다 →
        // private 프로퍼티의 게터도 호출할 수 있다.
        var dm = new DynamicMethod(
            $"__get_{declaring.Name}_{prop.Name}",
            typeof(object),                     // 반환 타입
            new[] { typeof(object) },           // 매개변수: 인스턴스
            declaring,                          // 소유자
            skipVisibility: true);

        ILGenerator il = dm.GetILGenerator();

        if (getter.IsStatic)
        {
            il.Emit(OpCodes.Call, getter);                  // 인스턴스가 필요 없다
        }
        else
        {
            il.Emit(OpCodes.Ldarg_0);                       // object instance
            if (declaring.IsValueType)
            {
                // 값 타입: 박스를 풀어 내부 주소를 얻고 Call 로 부른다
                il.Emit(OpCodes.Unbox, declaring);          // → 관리 포인터
                il.Emit(OpCodes.Call, getter);
            }
            else
            {
                il.Emit(OpCodes.Castclass, declaring);      // (Person) instance
                il.Emit(OpCodes.Callvirt, getter);          // .Name
            }
        }

        if (prop.PropertyType.IsValueType)
            il.Emit(OpCodes.Box, prop.PropertyType);        // object 로 반환하려면 박싱

        il.Emit(OpCodes.Ret);

        return dm.CreateDelegate<Func<object, object?>>();
    }
}
```

사용은 이렇다.

```csharp
public class Person
{
    public string Name { get; set; } = "";
    public int Age { get; set; }
}

var p = new Person { Name = "Ada", Age = 36 };

var nameGetter = FastAccessor.GetGetter(typeof(Person).GetProperty("Name")!);
var ageGetter  = FastAccessor.GetGetter(typeof(Person).GetProperty("Age")!);

Console.WriteLine(nameGetter(p));    // Ada
Console.WriteLine(ageGetter(p));     // 36
```

참조 타입 프로퍼티에 대해 방출되는 IL은 다음과 같다.

```il
.method public static object __get_Person_Name(object A_0) cil managed
{
  .maxstack  1
  IL_0000:  ldarg.0
  IL_0001:  castclass  Person
  IL_0006:  callvirt   instance string Person::get_Name()
  IL_000b:  ret
}
```

`string`은 참조 타입이라 `box`가 없다. `Age`(=`int`)에 대해서는 `callvirt` 뒤에 `box [System.Runtime]System.Int32`가 붙는다.

스택 추적으로 확인한다.

```text
 명령                        동작                                실행 후 스택
──────────────────────────────────────────────────────────────────────────
 ldarg.0             object 인스턴스를 푸시                       [ obj ]
 castclass Person    팝, 캐스트, 다시 푸시 (실패 시 예외)           [ person ]
 callvirt get_Age    수신자 팝, int 푸시                          [ 36 ]
 box int32           int 팝, 힙에 복사, 참조 푸시                  [ (object)36 ]
 ret                 값 하나를 남긴 채 반환 — OK                   [ ]
```

> **💡 이 기법을 언제 쓰는가**
>
> 이 정도 코드는 **식 트리로도 똑같이 만들 수 있고**(57.13절), 코드가 절반이며 읽기 쉽다. `Emit`을 골라야 하는 이유는 셋 중 하나다. ① 식 트리가 표현하지 못하는 IL이 필요하다(`ref` 지역, `stackalloc`, 값 타입 제자리 수정, `calli`). ② 크고 트리밍에 불리한 `System.Linq.Expressions` 의존성을 피하고 싶다. ③ **생성 시간 자체가 병목이다** — 식 트리는 내부적으로 `Reflection.Emit`을 부르므로 트리 구축 + IL 방출 두 단계를 거친다. 수천 개의 접근자를 시작 시점에 만든다면 직접 방출이 뚜렷하게 빠르다.
>
> 셋 중 어느 것도 아니면 식 트리를 써라. `Emit` 코드는 유지 보수 비용이 훨씬 비싸다.

> **⚠️ 값 타입 인스턴스의 프로퍼티는 `Unbox` + `Call`이다**
>
> 위 코드에서 `declaring.IsValueType` 경로를 보라. `Unbox`(관리 포인터를 얻는다)이지 `Unbox_Any`(값을 복사한다)가 아니고, `Callvirt`가 아니라 `Call`이다. `Unbox_Any` 뒤에는 스택에 **값**이 있는데 값 타입의 인스턴스 메서드는 **주소**를 요구하므로 IL이 유효하지 않다.
>
> 단, `Unbox`로 얻은 포인터로 필드를 **쓰면** 박싱된 사본이 바뀔 뿐 원본 구조체는 그대로다. 게터에는 문제없지만 세터를 같은 방식으로 만들면 조용히 아무 일도 일어나지 않는 코드가 된다.

## 58.5 예외 처리 코드 방출

### `try`/`catch`/`finally`를 방출하는 법

`ILGenerator`는 예외 처리를 위한 전용 메서드를 제공한다. 옵코드를 직접 다루는 대신 **블록 구조**를 선언하면 `ILGenerator`가 메서드의 예외 처리 절(exception handling clause) 테이블을 만들어 준다.

다음 C# 코드를

```csharp
try     { throw new NotSupportedException(); }
catch (NotSupportedException ex) { Console.WriteLine(ex.Message); }
finally { Console.WriteLine("Finally"); }
```

이렇게 방출한다.

```csharp
MethodInfo getMessageProp = typeof(NotSupportedException)
    .GetProperty("Message")!.GetGetMethod()!;
MethodInfo writeLineString = typeof(Console).GetMethod("WriteLine",
    new[] { typeof(object) })!;

gen.BeginExceptionBlock();
ConstructorInfo ci = typeof(NotSupportedException).GetConstructor(Type.EmptyTypes)!;
gen.Emit(OpCodes.Newobj, ci);
gen.Emit(OpCodes.Throw);

gen.BeginCatchBlock(typeof(NotSupportedException));
gen.Emit(OpCodes.Callvirt, getMessageProp);
gen.Emit(OpCodes.Call, writeLineString);

gen.BeginFinallyBlock();
gen.EmitWriteLine("Finally");

gen.EndExceptionBlock();
```

C#과 마찬가지로 `catch` 블록을 여러 개 둘 수 있다 — `BeginCatchBlock`을 여러 번 부르면 된다. 같은 예외를 다시 던지려면 `OpCodes.Rethrow`를 방출한다.

### `catch` 블록에 진입할 때 스택 상태

여기가 손으로 IL을 쓸 때 가장 헷갈리는 지점이다.

**`catch` 블록에 진입하는 순간, 평가 스택에는 예외 객체가 이미 하나 올라와 있다.** CLR이 넣어 준 것이다. 그래서 위 예제에서 `gen.Emit(OpCodes.Callvirt, getMessageProp)`이 곧바로 동작한다 — `ldarg`도 `ldloc`도 없이 예외의 `Message`를 읽는다.

```text
 위치                        동작                              스택
──────────────────────────────────────────────────────────────────────
 BeginExceptionBlock()   try 진입 — 스택은 비어야 한다           [ ]
 Newobj NSE()            예외 객체 생성                          [ ex ]
 Throw                   팝하고 던진다                           [ ]
 BeginCatchBlock(NSE)    CLR이 예외를 푸시해 준다                 [ ex ]
 Callvirt get_Message    팝, 문자열 푸시                         [ msg ]
 Call WriteLine(object)  팝                                     [ ]
 BeginFinallyBlock()     finally 진입 — 스택은 비어야 한다        [ ]
 EmitWriteLine("Finally")                                       [ ]
 EndExceptionBlock()     endfinally / leave 를 자동 방출          [ ]
```

예외 객체가 필요 없다면 **명시적으로 `Pop`을 방출해야 한다.** 그러지 않으면 `catch` 블록이 끝날 때 스택이 비어 있지 않아 IL이 무효가 된다.

```csharp
gen.BeginCatchBlock(typeof(Exception));
gen.Emit(OpCodes.Pop);                 // 예외 객체를 버린다
gen.EmitWriteLine("실패했지만 무시한다");
gen.EndExceptionBlock();
```

> **⚠️ 보호 블록의 경계에서 스택은 반드시 비어 있어야 한다**
>
> `try`, `catch`, `filter`, `finally` 블록에 **진입할 때**와 **빠져나갈 때** 평가 스택은 비어 있어야 한다(진입 시 CLR이 넣어 주는 예외 객체는 예외다). 계산 중간 값을 `try` 블록 밖으로 스택에 담아 나갈 수 없다.
>
> 값을 블록 밖으로 전달하려면 **지역 변수를 거쳐야 한다.** C# 컴파일러가 `try` 안에서 계산한 값을 임시 지역 변수에 넣고 밖에서 다시 읽는 IL을 만드는 이유가 이것이다(56.6절의 `using` 낮추기와 같은 패턴이다).
>
> ```csharp
> LocalBuilder result = gen.DeclareLocal(typeof(int));
> gen.BeginExceptionBlock();
> //   ... 계산 ...
> gen.Emit(OpCodes.Stloc, result);      // 스택을 비운다
> gen.BeginCatchBlock(typeof(Exception));
> gen.Emit(OpCodes.Pop);
> gen.Emit(OpCodes.Ldc_I4_M1);
> gen.Emit(OpCodes.Stloc, result);
> gen.EndExceptionBlock();
> gen.Emit(OpCodes.Ldloc, result);      // 블록 밖에서 읽는다
> gen.Emit(OpCodes.Ret);
> ```

### `BeginExceptionBlock`이 돌려주는 `Label`

`BeginExceptionBlock()`은 **예외 블록 전체가 끝나는 지점**을 가리키는 `Label`을 반환한다. `try` 블록 안에서 조기 탈출해야 할 때 `Emit(OpCodes.Leave, endLabel)`로 쓴다. `try` 밖으로 나가는 유일한 정상 경로가 `leave`이며 `br`이나 `ret`으로 보호 블록을 벗어나면 IL이 무효다. **`ILGenerator`가 블록 종료 시 필요한 `leave`를 자동으로 넣어 주므로** 직접 방출할 일은 블록 중간에서 나가는 경우뿐이다.

> **⚠️ `try` 블록 안에서 `Ret`을 방출하지 마라**
>
> C#에서는 `try` 안에 `return`을 쓸 수 있지만, 컴파일러가 그것을 "값을 임시 변수에 저장 → `leave` → 블록 밖에서 로드 → `ret`"으로 낮춘다. IL 수준에서는 **보호 블록 안의 `ret`이 금지**다(`ret`은 `finally` 실행을 건너뛸 수 있기 때문이다). 어기면 `InvalidProgramException`이다. `try` 안에서 반환하고 싶으면 위의 지역 변수 패턴을 써라.

### 예외 필터 — `when`을 방출하기

C#의 `catch (Exception e) when (조건)`은 IL의 **필터 블록**이다. `ILGenerator`로는 이렇게 표현한다.

```csharp
gen.BeginExceptionBlock();
// ... 보호할 코드 ...

gen.BeginExceptFilterBlock();
//   진입 시 스택에 예외 객체가 있다. 1(처리) 또는 0(무시)을 남겨야 한다.
gen.Emit(OpCodes.Isinst, typeof(InvalidOperationException));
gen.Emit(OpCodes.Ldnull);
gen.Emit(OpCodes.Cgt_Un);              // != null 이면 1

gen.BeginCatchBlock(null!);            // 필터 뒤의 catch 는 타입이 null 이다
gen.Emit(OpCodes.Pop);
gen.EmitWriteLine("필터가 통과시킨 예외를 처리");

gen.EndExceptionBlock();
```

필터 블록은 **정확히 정수 하나(0 또는 1)를 스택에 남겨야** 하고, 그 뒤의 `BeginCatchBlock`에는 예외 타입 대신 `null`을 넘긴다. 필터가 있는 `catch`에서 타입 인수를 주면 `ArgumentException`이 난다.

> **📌 필터는 스택을 풀기 전에 실행된다**
>
> 예외 필터의 진짜 가치는 여기에 있다. 필터 식은 **스택 되감기(unwind)가 일어나기 전에** 실행되므로, 필터 안에서 예외를 로깅하면 원래 던져진 지점의 스택 프레임이 아직 살아 있다. 이 성질 때문에 로깅 프레임워크가 `when (Log(e))` 같은 관용구를 쓴다. 방출 코드로 진단 계층을 만들 때도 같은 이유로 유용하다.

### `ThrowException`의 함정

`ILGenerator`에는 `ThrowException(Type)`이라는 도우미가 있다. 지정한 예외 타입의 매개변수 없는 생성자를 찾아 `newobj` + `throw`를 방출한다. 원서는 이 메서드에 **`DynamicMethod`와 함께 쓸 수 없게 하는 버그가 있다**고 지적한다 — `MethodBuilder`에서만 동작한다고. 런타임 버전에 따라 동작이 달라질 수 있는 영역이므로, 어차피 두 줄이면 되는 일을 도우미에 맡길 이유가 없다.

```csharp
// ThrowException(typeof(NotSupportedException)) 대신
gen.Emit(OpCodes.Ldstr, "지원하지 않는 타입이다");
gen.Emit(OpCodes.Newobj,
         typeof(NotSupportedException).GetConstructor(new[] { typeof(string) })!);
gen.Emit(OpCodes.Throw);
```

> **⚠️ `Throw` 뒤의 코드는 도달 불가능하지만 스택 규칙은 여전히 적용된다**
>
> `throw`는 제어를 이전하므로 그 뒤에 `ret`이 없어도 된다. 그러나 `throw` 다음 위치가 **다른 곳에서 분기해 들어오는 지점**이라면, 그 지점의 스택 깊이는 다른 경로와 일치해야 한다(56.2절의 스택 균형 규칙).
>
> 실무에서는 "조건 검사 → 실패하면 `throw` → 성공하면 계속"을 방출할 때 이 문제가 나온다. 실패 경로를 메서드 **끝**에 몰아 두고 성공 경로를 직선으로 유지하면 스택 균형을 맞추기가 훨씬 쉽다. C# 컴파일러도 같은 배치를 쓴다.

## 58.6 `Reflection.Emit` 객체 모델 — 동적 어셈블리와 타입

### `DynamicMethod`의 한계

`DynamicMethod`는 편리하지만 **메서드만** 만들 수 있다. 타입이나 다른 구조를 방출해야 한다면 무거운 API 전체를 써야 한다. 즉 동적 **어셈블리**와 **모듈**을 만들어야 한다.

타입은 어셈블리 안의 모듈에 살아야 하므로 순서가 정해져 있다. 어셈블리 → 모듈 → 타입이다.

```csharp
using System.Reflection;
using System.Reflection.Emit;

AssemblyName aname = new AssemblyName("MyDynamicAssembly");
AssemblyBuilder assemBuilder =
    AssemblyBuilder.DefineDynamicAssembly(aname, AssemblyBuilderAccess.Run);
ModuleBuilder modBuilder = assemBuilder.DefineDynamicModule("DynModule");
```

모듈이 생겼으면 `TypeBuilder`로 타입을 만든다.

```csharp
TypeBuilder tb = modBuilder.DefineType("Widget", TypeAttributes.Public);
```

멤버를 채우고

```csharp
MethodBuilder methBuilder = tb.DefineMethod("SayHello",
                                            MethodAttributes.Public,
                                            null, null);
ILGenerator gen = methBuilder.GetILGenerator();
gen.EmitWriteLine("Hello world");
gen.Emit(OpCodes.Ret);
```

**타입을 생성(굽기)** 한다. 이 호출이 정의를 확정한다.

```csharp
Type t = tb.CreateType()!;
```

이후에는 평범한 리플렉션으로 조사하고 늦은 바인딩으로 호출한다(57.3절, 57.6절).

```csharp
object o = Activator.CreateInstance(t)!;
t.GetMethod("SayHello")!.Invoke(o, null);      // Hello world
```

> **📌 "굽는다(baking)"는 공식 용어다**
>
> `CreateType()`이 하는 일을 문서와 커뮤니티에서 **베이킹**이라고 부른다. `TypeBuilder`와 그 모든 멤버를 **봉인**해 더 이상 추가·변경할 수 없게 만들고, 실체화된 `Type`을 돌려준다. 오븐에 넣기 전에 재료를 다 넣어야 한다는 비유가 정확하다 — 58.10절의 순환 의존성 문제가 정확히 이 성질에서 나온다.

### 객체 모델 계층

`System.Reflection.Emit`의 각 타입은 CLR 구조 하나를 기술하고, `System.Reflection`의 대응물을 **상속**한다. 그래서 타입을 만드는 도중에 방출 중인 구조를 일반 구조가 올 자리에 그대로 쓸 수 있다.

```text
   어셈블리 → 모듈 → 타입 → 멤버. 바깥이 만들어져야 안이 만들어진다.

┌────────────────────────────────────────────────────────────────┐
│ AssemblyBuilder : Assembly                                     │
│   AssemblyBuilder.DefineDynamicAssembly(name, access)          │
│   ↓ DefineDynamicModule("MainModule")                          │
│ ┌────────────────────────────────────────────────────────────┐ │
│ │ ModuleBuilder : Module                                     │ │
│ │   ↓ DefineType("Widget", TypeAttributes.Public)            │ │
│ │ ┌────────────────────────────────────────────────────────┐ │ │
│ │ │ TypeBuilder : Type                                     │ │ │
│ │ │   ↓ DefineMethod / DefineField / DefineProperty / ...  │ │ │
│ │ │ ┌────────────────────────────────────────────────────┐ │ │ │
│ │ │ │ MethodBuilder      : MethodInfo                    │ │ │ │
│ │ │ │ ConstructorBuilder : ConstructorInfo               │ │ │ │
│ │ │ │ FieldBuilder       : FieldInfo                     │ │ │ │
│ │ │ │ PropertyBuilder    : PropertyInfo                  │ │ │ │
│ │ │ │ EventBuilder                                       │ │ │ │
│ │ │ └────────────────────────────────────────────────────┘ │ │ │
│ │ │   CreateType() → Type    ← 여기서 봉인된다("굽기")       │ │ │
│ │ └────────────────────────────────────────────────────────┘ │ │
│ └────────────────────────────────────────────────────────────┘ │
└────────────────────────────────────────────────────────────────┘
```

각 빌더는 부모 빌더의 `Define*` 팩터리 메서드에서만 나온다. `MethodBuilder`/`ConstructorBuilder`에서 `GetILGenerator()`로 `ILGenerator`를 얻고, 거기서 `DeclareLocal`이 `LocalBuilder`를, `DefineLabel`이 `Label`을 만든다. `PropertyBuilder`는 `SetGetMethod`/`SetSetMethod`로, `EventBuilder`는 `SetAddOnMethod`/`SetRemoveOnMethod`로 접근자 `MethodBuilder`와 연결한다. `CustomAttributeBuilder`는 이들 대부분의 `SetCustomAttribute`에 부착한다.

오른쪽에 적은 `: Assembly`, `: Type`, `: MethodInfo`는 **기반 클래스**다. 즉 `MethodBuilder`는 `MethodInfo`이고, `TypeBuilder`는 `Type`이다.

이 상속 관계가 실용적으로 중요하다. 앞서 `Console.WriteLine`을 이렇게 호출했다.

```csharp
MethodInfo writeLine = typeof(Console).GetMethod("WriteLine",
                                                 new Type[] { typeof(string) })!;
gen.Emit(OpCodes.Call, writeLine);
```

같은 자리에 `MethodInfo` 대신 `MethodBuilder`를 넘겨 **방금 방출한 메서드**를 호출할 수 있다. 이게 없으면 같은 타입 안에서 한 동적 메서드가 다른 동적 메서드를 부를 방법이 없다.

### `AssemblyBuilderAccess`와 수명

`DefineDynamicAssembly`에는 접근 모드를 지정해야 한다. .NET(Core)에서 의미 있는 값은 둘이다.

| 값 | 의미 |
|---|---|
| `Run` | 메모리에서 실행만 한다. **수집되지 않는다** — 프로세스가 끝날 때까지 메모리에 남는다 |
| `RunAndCollect` | 수집 가능. 더 이상 참조되지 않으면 GC가 회수한다 |

> **⚠️ .NET Framework의 `Save`/`RunAndSave`는 .NET Core에 없다**
>
> .NET Framework의 `AssemblyBuilderAccess`에는 `Save`, `RunAndSave`, `ReflectionOnly` 값이 있었고 `AssemblyBuilder.Save("x.dll")`로 동적 어셈블리를 디스크에 쓸 수 있었다. **.NET Core / .NET 5~8에는 이 기능이 없다.** `AssemblyBuilder`에 `Save` 메서드 자체가 없고 `AssemblyBuilderAccess`에도 `Save`/`RunAndSave`/`ReflectionOnly` 값이 없다 — 즉 런타임 실패가 아니라 **컴파일 오류**로 드러난다.
>
> 인터넷의 오래된 예제 대부분이 `RunAndSave`를 쓰고 있으므로, 그대로 복사하면 런타임에 실패한다. .NET Framework 시절 코드를 이식할 때 가장 먼저 걸리는 지점이다.

> **📌 ※.NET 9 — `PersistedAssemblyBuilder`로 저장 기능이 돌아왔다**
>
> .NET 9에서 `System.Reflection.Emit.PersistedAssemblyBuilder`가 추가되어 **동적 어셈블리를 다시 디스크에 저장할 수 있게** 되었다.
>
> ```csharp
> var ab = new PersistedAssemblyBuilder(new AssemblyName("MyEmitted"),
>                                       typeof(object).Assembly);
> ModuleBuilder mod = ab.DefineDynamicModule("MainModule");
> TypeBuilder tb = mod.DefineType("Widget", TypeAttributes.Public);
> MethodBuilder mb = tb.DefineMethod("SayHello", MethodAttributes.Public, null, null);
> ILGenerator il = mb.GetILGenerator();
> il.EmitWriteLine("Hello world");
> il.Emit(OpCodes.Ret);
> tb.CreateType();
>
> ab.Save("MyEmitted.dll");        // ※.NET 9
> ```
>
> 둘째 생성자 인수(`coreAssembly`)는 `object`, `int` 같은 **핵심 타입의 참조를 어느 어셈블리로 기록할지** 정한다. 보통 `typeof(object).Assembly`를 넘긴다.
>
> `PersistedAssemblyBuilder`는 **실행되지 않는다.** 저장만 한다. 만든 타입을 그 자리에서 쓰려면 저장한 파일을 다시 로드하거나(52.13절) 실행용 `AssemblyBuilder`를 따로 써야 한다. `.exe`로 저장하려면 `GenerateMetadata`로 메타데이터를 받아 `System.Reflection.Metadata`의 `ManagedPEBuilder`로 PE를 직접 조립해야 한다 — 진입점을 지정할 방법이 그것뿐이다.
>
> 이 기능의 실무적 가치는 배포가 아니라 **디버깅**이다. 방출한 IL을 파일로 떨궈 ILSpy나 `ildasm`으로 열어 볼 수 있게 되었다(58.10절).

기존 어셈블리에 타입을 **추가할 수는 없다.** 어셈블리는 생성된 뒤 불변이므로 "로드된 어셈블리에 메서드를 하나 끼워 넣기"는 `Reflection.Emit`으로 할 수 없는 일이다. 새 동적 어셈블리를 만드는 것만 가능하다.

### 수집 가능 동적 어셈블리와 ALC ※

`AssemblyBuilderAccess.Run`으로 만든 동적 어셈블리는 **가비지 컬렉션되지 않고 프로세스가 끝날 때까지 메모리에 남는다.** 타입을 계속 만들어 내는 서버 프로세스에서는 이것이 그대로 메모리 누수다. `XmlSerializer`가 임시 어셈블리로 메모리를 먹는 고전적 사례를 52.12절에서 다뤘다.

해결책은 `RunAndCollect`다.

```csharp
AssemblyBuilder ab = AssemblyBuilder.DefineDynamicAssembly(
    new AssemblyName("Ephemeral"), AssemblyBuilderAccess.RunAndCollect);
```

이렇게 만든 어셈블리는 **자기 자신의 로더 할당자(loader allocator)** 를 갖고, 그 안의 타입·메서드·정적 필드를 가리키는 참조가 모두 사라지면 GC가 통째로 회수한다.

52.12절에서 본 수집 가능 `AssemblyLoadContext`와 결합하면 더 큰 단위로 관리할 수 있다.

```csharp
using System.Runtime.Loader;

var alc = new AssemblyLoadContext("codegen", isCollectible: true);

// 코드 생성기 자체를 수집 가능 ALC 안으로 넣는다.
// 그 안에서 만들어진 동적 어셈블리는 ALC와 수명을 함께한다.
Assembly gen = alc.LoadFromAssemblyPath("/app/plugins/Generator.dll");
Type genType = gen.GetType("Generator.Emitter")!;
genType.GetMethod("Run")!.Invoke(Activator.CreateInstance(genType), null);

alc.Unload();          // 사용이 끝나면
```

> **⚠️ 동적 어셈블리는 "만든 코드가 사는 ALC"에 따라간다**
>
> 동적 어셈블리를 특정 ALC에 넣는 별도 API는 없다. **`DefineDynamicAssembly`를 호출하는 코드가 어느 ALC에 로드되어 있는지**가 결과를 결정한다. 기본 ALC의 코드에서 호출하면 기본 ALC에 생기고, 그러면 아무리 `alc.Unload()`를 불러도 그 동적 어셈블리는 해제되지 않는다. 그래서 위 예제처럼 **생성기 코드 자체를 대상 ALC에 로드해서** 그 안에서 방출하게 만들어야 한다.
>
> 52.12절에서 강조한 협력적 언로드 규칙도 그대로 적용된다. 방출한 타입의 인스턴스나 그것을 감싼 델리게이트를 ALC 밖의 정적 캐시가 하나라도 잡고 있으면 언로드는 **조용히 일어나지 않는다.** 진단하려면 `!gcroot`가 필요하다(66장).

> **⚠️ Native AOT에서는 `Reflection.Emit`이 전부 막힌다**
>
> Native AOT는 JIT이 아예 없다(55.7절). 런타임에 IL을 실행할 수단이 없으므로 `DynamicMethod`도 `AssemblyBuilder`도 동작하지 않고, 시도하면 `PlatformNotSupportedException`이 난다. 코드에서 미리 확인하려면 런타임 기능 스위치를 본다.
>
> ```csharp
> using System.Runtime.CompilerServices;
>
> if (RuntimeFeature.IsDynamicCodeSupported)
>     _accessor = BuildWithEmit(prop);        // 빠른 경로
> else
>     _accessor = o => prop.GetValue(o);      // 폴백: 느리지만 동작한다
> ```
>
> `RuntimeFeature.IsDynamicCodeSupported`는 AOT 컴파일러가 **컴파일 타임 상수 `false`로 치환**하므로 `BuildWithEmit` 경로 전체가 트리밍으로 제거된다. 폴백을 함께 두는 것이 AOT 대응의 기본 패턴이다.
>
> `Emit`을 쓰는 공개 API에는 `[RequiresDynamicCode]`(※.NET 7)를 붙여라. 호출자가 AOT 게시에서 **IL3050 경고**를 보고 대비할 수 있다(57.14절). 경고를 지우려고 특성을 떼는 것은 문제를 숨기는 것일 뿐이다.
>
> 같은 이유로 `RegexOptions.Compiled`는 AOT에서 해석 모드로 조용히 폴백하고, `LambdaExpression.Compile()`도 동적 코드가 불가능한 환경에서는 인터프리터 경로를 쓰도록 설계되어 있다. "동작은 하는데 느리다"가 AOT에서 `Emit` 기반 최적화가 맞는 전형적 결말이다.

## 58.7 메서드·필드·프로퍼티·생성자 방출

이 절의 모든 예제는 다음과 같이 `TypeBuilder tb`가 준비되었다고 가정한다.

```csharp
AssemblyName aname = new AssemblyName("MyEmissions");
AssemblyBuilder assemBuilder = AssemblyBuilder.DefineDynamicAssembly(
    aname, AssemblyBuilderAccess.Run);
ModuleBuilder modBuilder = assemBuilder.DefineDynamicModule("MainModule");
TypeBuilder tb = modBuilder.DefineType("Widget", TypeAttributes.Public);
```

### `TypeAttributes` — 타입의 성격 정하기

`DefineType`의 둘째 인수인 `TypeAttributes` 플래그 열거형은 `ildasm`으로 타입을 디스어셈블할 때 보이는 CLR 타입 한정자에 대응한다. 멤버 가시성 플래그 외에 `Abstract`, `Sealed`, 인터페이스 정의를 위한 `Interface`, `[Serializable]`에 대응하는 `Serializable`, `[StructLayout(LayoutKind.Explicit)]`에 대응하는 `Explicit`이 있다.

| 만들고 싶은 것 | 지정 방법 |
|---|---|
| 클래스 | `TypeAttributes.Public` (기본 타입 생략 시 `object`) |
| 구조체 | 기반 타입으로 `typeof(System.ValueType)` 지정 |
| 인터페이스 | `TypeAttributes.Interface \| TypeAttributes.Abstract` |
| 델리게이트 | 기반 타입으로 `typeof(System.MulticastDelegate)` (추가 작업 다수 필요) |
| 인터페이스 구현 | 인터페이스 타입 배열을 받는 `DefineType` 오버로드, 또는 `AddInterfaceImplementation` |
| 봉인 클래스 | `TypeAttributes.Public \| TypeAttributes.Sealed` |
| 중첩 타입 | `tb.DefineNestedType(...)` + `NestedPublic`/`NestedPrivate` 등 |

중첩 타입의 가시성 플래그는 이름이 다르다 — `NestedPublic`, `NestedAssembly`(= `internal`), `NestedPrivate`, `NestedFamily`(= `protected`), `NestedFamORAssem`(= `protected internal`), `NestedFamANDAssem`(= `private protected`)이다.

> **⚠️ 중첩 타입에 `Public`을 쓰면 `TypeLoadException`이 난다**
>
> `DefineNestedType`에 `TypeAttributes.Public`을 넘기면 방출은 성공하지만 **타입을 로드할 때** 실패한다. 중첩 타입의 가시성은 반드시 `Nested*` 계열이어야 한다. 반대로 최상위 타입에 `NestedPublic`을 주는 실수도 같은 결과를 낸다.

### 메서드 방출

`DefineMethod`는 `DynamicMethod` 생성자와 같은 방식으로 반환 타입과 매개변수 타입을 받는다.

```csharp
public static double SquareRoot(double value) => Math.Sqrt(value);
```

를 방출하면 이렇다.

```csharp
MethodBuilder mb = tb.DefineMethod("SquareRoot",
    MethodAttributes.Static | MethodAttributes.Public,
    CallingConventions.Standard,
    typeof(double),                       // 반환 타입
    new[] { typeof(double) });            // 매개변수 타입

mb.DefineParameter(1, ParameterAttributes.None, "value");   // 이름 지정

ILGenerator gen = mb.GetILGenerator();
gen.Emit(OpCodes.Ldarg_0);                                  // 첫 인수 로드
gen.Emit(OpCodes.Call, typeof(Math).GetMethod("Sqrt")!);
gen.Emit(OpCodes.Ret);

Type realType = tb.CreateType()!;
double x = (double) tb.GetMethod("SquareRoot")!.Invoke(null, new object[] { 10.0 })!;
Console.WriteLine(x);            // 3.1622776601683795
```

`DefineParameter` 호출은 선택 사항이고, 보통 매개변수에 **이름을 주기 위해** 쓴다. 인수 `1`은 첫 매개변수를 가리킨다(`0`은 반환값을 가리킨다). `DefineParameter`를 호출하지 않으면 매개변수 이름은 암묵적으로 `__p1`, `__p2` 같은 형태가 된다. 이름을 붙이는 것은 어셈블리를 디스크에 쓸 계획이라면 의미가 있다 — 소비자에게 친절해진다.

`DefineParameter`는 `ParameterBuilder`를 반환하고, 여기에 `SetCustomAttribute`로 특성을 붙일 수 있다(58.8절).

### `ref`와 `out` 매개변수

```csharp
public static void SquareRoot(ref double value) => value = Math.Sqrt(value);
```

`ref` 매개변수를 방출하려면 매개변수 타입에 `MakeByRefType()`을 호출한다.

```csharp
MethodBuilder mb = tb.DefineMethod("SquareRoot",
    MethodAttributes.Static | MethodAttributes.Public,
    CallingConventions.Standard,
    null,
    new Type[] { typeof(double).MakeByRefType() });

mb.DefineParameter(1, ParameterAttributes.None, "value");

ILGenerator gen = mb.GetILGenerator();
gen.Emit(OpCodes.Ldarg_0);           // 관리 포인터를 푸시 (저장 대상 주소)
gen.Emit(OpCodes.Ldarg_0);           // 다시 푸시 (읽기용)
gen.Emit(OpCodes.Ldind_R8);          // 포인터가 가리키는 8바이트 실수를 로드
gen.Emit(OpCodes.Call, typeof(Math).GetMethod("Sqrt")!);
gen.Emit(OpCodes.Stind_R8);          // 결과를 포인터 자리에 저장
gen.Emit(OpCodes.Ret);

Type realType = tb.CreateType()!;
object[] args = { 10.0 };
tb.GetMethod("SquareRoot")!.Invoke(null, args);
Console.WriteLine(args[0]);          // 3.1622776601683795
```

여기 쓰인 옵코드는 같은 C# 메서드를 디스어셈블해 베낀 것이다. 참조로 전달된 매개변수에 접근하는 의미가 다르다는 점에 주목하라. `Ldind`와 `Stind`는 각각 "간접 로드", "간접 저장"이고, `R8` 접미사는 8바이트 부동소수점을 뜻한다.

`Ldarg_0`을 두 번 방출하는 이유는 `stind`가 **주소와 값을 함께 팝하기** 때문이다. 첫 번째는 저장 대상 주소로, 두 번째는 `ldind`가 읽을 원본으로 쓰인다.

`out` 매개변수를 방출하는 과정은 같고, `DefineParameter`만 다르다.

```csharp
mb.DefineParameter(1, ParameterAttributes.Out, "value");
```

### 인스턴스 메서드와 인수 인덱스

인스턴스 메서드는 **기본값**이다. `MethodAttributes`에는 `Instance`라는 값이 없고 — `Static`의 **부재**가 곧 인스턴스를 뜻한다 — `DefineMethod` 호출에서 `MethodAttributes.Static`을 빼면 된다.

```csharp
MethodBuilder mb = tb.DefineMethod("SquareRoot",
    MethodAttributes.Public,          // Static 을 지정하지 않으면 인스턴스 메서드다
    // ...
```

인스턴스 메서드에서 **인수 0은 암묵적으로 `this`** 이고 나머지 인수는 1부터 시작한다. 즉 `Ldarg_0`은 `this`를 스택에 올리고, `Ldarg_1`이 첫 실제 인수다.

> **⚠️ 정적/인스턴스를 바꾸면 모든 `Ldarg` 인덱스가 한 칸씩 밀린다**
>
> 방출 코드를 리팩터링하면서 `MethodAttributes.Static`을 붙이거나 떼는 순간, 그 메서드의 모든 인수 인덱스가 어긋난다. 컴파일러는 아무 말도 하지 않고, `Ldarg_1`이 존재하지 않는 인수를 가리키면 IL이 무효가 된다. 운이 나쁘면 인덱스가 우연히 유효 범위 안이라 **타입이 다른 값을 읽어** 엉뚱하게 동작한다.
>
> 방어책은 간단하다. 인수 인덱스를 상수로 쓰지 말고 `int argBase = mb.IsStatic ? 0 : 1;` 같은 변수에서 계산하라.

### 메서드 재정의와 `HideBySig`

기반 클래스의 가상 메서드를 재정의하는 것은 쉽다. 이름·시그니처·반환 타입이 동일한 메서드를 정의하면서 `DefineMethod` 호출에 `MethodAttributes.Virtual`을 지정하면 된다. 인터페이스 메서드를 구현할 때도 마찬가지다.

`TypeBuilder`에는 `DefineMethodOverride`도 있다. **이름이 다른** 메서드로 재정의할 때 쓰는데, 이는 명시적 인터페이스 구현에서만 의미가 있다. 그 외의 경우에는 `DefineMethod`를 쓴다.

다른 타입을 상속한다면 메서드를 정의할 때 `MethodAttributes.HideBySig`를 거의 항상 지정할 가치가 있다. `HideBySig`는 **C# 방식의 메서드 숨기기 의미론**을 적용한다 — 서브타입이 동일한 시그니처의 메서드를 정의할 때만 기반 메서드가 숨겨진다. `HideBySig`가 없으면 메서드 숨기기가 **이름만** 고려하므로, 서브타입의 `Foo(string)`이 기반 타입의 `Foo()`를 숨긴다. 대개 원하지 않는 결과다.

인터페이스를 구현하는 메서드에 필요한 플래그 조합을 정리한다.

| 플래그 | 왜 필요한가 |
|---|---|
| `Public` | 암묵적 구현이면 공개여야 한다 |
| `Virtual` | 인터페이스 메서드는 항상 가상 슬롯에 들어간다. **없으면 구현으로 인정되지 않는다** |
| `Final` | 파생 타입이 다시 재정의하지 못하게 한다(C#의 암묵적 구현과 같은 의미) |
| `NewSlot` | 기반 클래스의 동명 가상 메서드를 재정의하지 않고 **새 슬롯**을 만든다 |
| `HideBySig` | 시그니처 기준 숨기기 |

### 미생성 타입의 멤버는 리플렉션으로 못 얻는다

`CreateType`을 부르기 전의 `TypeBuilder`와 그 멤버는 **미생성(uncreated)** 상태다. 이 상태에서 할 수 있는 일에는 큰 제약이 있다. 특히 `GetMembers`, `GetMethod`, `GetProperty`처럼 `MemberInfo`를 반환하는 멤버는 **전부 예외를 던진다.**

미생성 타입의 멤버를 참조해야 한다면 **원래의 빌더 객체**를 써야 한다.

```csharp
TypeBuilder tb = ...
MethodBuilder method1 = tb.DefineMethod("Method1", ...);
MethodBuilder method2 = tb.DefineMethod("Method2", ...);
ILGenerator gen1 = method1.GetILGenerator();

// method1 이 method2 를 호출하게 하려면:
gen1.Emit(OpCodes.Call, method2);                     // 맞다
gen1.Emit(OpCodes.Call, tb.GetMethod("Method2")!);    // 틀리다 — 예외
```

`CreateType`을 호출한 뒤에는 반환된 `Type`뿐 아니라 **원래의 `TypeBuilder` 객체에도** 리플렉션을 걸고 인스턴스를 만들 수 있다. `TypeBuilder`가 실제 `Type`의 프록시로 **변신**하기 때문이다. 이 성질이 왜 중요한지는 58.10절에서 드러난다.

### 필드 방출

`TypeBuilder`의 `DefineField`에 이름·타입·가시성을 넘긴다.

```csharp
FieldBuilder field = tb.DefineField("length", typeof(int), FieldAttributes.Private);
```

자주 쓰는 `FieldAttributes` 조합은 다음과 같다.

| 조합 | C# 대응 |
|---|---|
| `Private` | `private int _x;` |
| `Public` | `public int X;` |
| `Assembly` | `internal int X;` |
| `Family` | `protected int X;` |
| `Private \| InitOnly` | `private readonly int _x;` |
| `Public \| Static` | `public static int X;` |
| `Public \| Static \| Literal` + `SetConstant(v)` | `public const int X = v;` |

### 프로퍼티 방출

프로퍼티나 인덱서를 만들려면 단계가 몇 개 더 필요하다. 먼저 `TypeBuilder`의 `DefineProperty`에 이름과 타입을 준다.

```csharp
PropertyBuilder prop = tb.DefineProperty(
    "Text",                    // 프로퍼티 이름
    PropertyAttributes.None,
    typeof(string),            // 프로퍼티 타입
    new Type[0]);              // 인덱서 타입
```

인덱서를 쓴다면 마지막 인수가 인덱서 타입의 배열이다. **프로퍼티 자체의 가시성은 지정하지 않는다는 점에 주목하라** — 가시성은 접근자 메서드에서 개별적으로 정한다.

다음 단계는 get/set 메서드를 작성하는 것이다. 관례상 이름 앞에 `get_` 또는 `set_`을 붙인다. 그런 다음 `PropertyBuilder`의 `SetGetMethod`와 `SetSetMethod`로 프로퍼티에 연결한다.

다음 필드와 프로퍼티 선언을

```csharp
string _text;
public string Text
{
    get          => _text;
    internal set => _text = value;
}
```

동적으로 만든다.

```csharp
FieldBuilder field = tb.DefineField("_text", typeof(string), FieldAttributes.Private);

PropertyBuilder prop = tb.DefineProperty(
    "Text",
    PropertyAttributes.None,
    typeof(string),
    new Type[0]);

MethodBuilder getter = tb.DefineMethod(
    "get_Text",
    MethodAttributes.Public | MethodAttributes.SpecialName,
    typeof(string),                          // 반환 타입
    new Type[0]);                            // 매개변수 타입

ILGenerator getGen = getter.GetILGenerator();
getGen.Emit(OpCodes.Ldarg_0);                // "this"를 스택에 로드
getGen.Emit(OpCodes.Ldfld, field);           // 필드 값을 스택에 로드
getGen.Emit(OpCodes.Ret);

MethodBuilder setter = tb.DefineMethod(
    "set_Text",
    MethodAttributes.Assembly | MethodAttributes.SpecialName,
    null,                                    // 반환 타입
    new Type[] { typeof(string) });          // 매개변수 타입

ILGenerator setGen = setter.GetILGenerator();
setGen.Emit(OpCodes.Ldarg_0);                // "this"를 스택에 로드
setGen.Emit(OpCodes.Ldarg_1);                // 둘째 인수, 즉 value 를 로드
setGen.Emit(OpCodes.Stfld, field);           // 값을 필드에 저장
setGen.Emit(OpCodes.Ret);

prop.SetGetMethod(getter);                   // get 메서드를 프로퍼티에 연결
prop.SetSetMethod(setter);                   // set 메서드를 프로퍼티에 연결
```

테스트한다.

```csharp
Type t = tb.CreateType()!;
object o = Activator.CreateInstance(t)!;
t.GetProperty("Text")!.SetValue(o, "Good emissions!", new object[0]);
Console.WriteLine(t.GetProperty("Text")!.GetValue(o, null));   // Good emissions!
```

접근자의 `MethodAttributes`에 `SpecialName`을 포함한 것에 주목하라. 이 플래그는 어셈블리를 정적으로 참조할 때 **컴파일러가 이 메서드에 직접 바인딩하지 못하게** 지시한다. 또 리플렉션 도구와 Visual Studio의 IntelliSense가 접근자를 적절히 다루도록 보장한다.

> **⚠️ `SetGetMethod`를 잊으면 프로퍼티가 아니라 메서드 두 개가 남는다**
>
> `DefineProperty`와 `DefineMethod("get_Text", ...)`는 서로 아무 관계가 없다. `SetGetMethod`/`SetSetMethod`로 명시적으로 묶어 주지 않으면 메타데이터에 **프로퍼티 항목과 `get_Text` 메서드가 따로** 존재하게 된다. `Type.GetProperty("Text")`는 프로퍼티를 찾아내지만 `GetGetMethod()`가 `null`을 돌려주고, `GetValue`를 호출하면 `ArgumentException`이 난다.
>
> 조용히 잘못되는 종류의 버그이므로, 프로퍼티를 방출한 뒤에는 `CreateType()` 직후에 `t.GetProperty(name)!.GetGetMethod() != null`을 확인하는 자기 점검을 넣어 두면 좋다.

이벤트도 비슷한 방식으로 방출한다. `TypeBuilder`의 `DefineEvent`를 호출한 다음, 명시적 이벤트 접근자 메서드를 작성하고 `EventBuilder`의 `SetAddOnMethod`와 `SetRemoveOnMethod`로 연결한다.

### 생성자 방출

`TypeBuilder`의 `DefineConstructor`로 생성자를 정의한다. 정의하지 않아도 되는데, 정의하지 않으면 **매개변수 없는 기본 생성자가 자동으로 제공**되기 때문이다. 이 기본 생성자는 C#과 마찬가지로 서브타입이라면 기반 클래스 생성자를 호출한다. 생성자를 하나라도 정의하면 이 기본 생성자는 사라진다. 되살리려면 `tb.DefineDefaultConstructor(MethodAttributes.Public)`를 호출한다.

필드를 초기화해야 한다면 생성자가 적절한 자리다. 사실 **유일한** 자리다 — C#의 필드 초기화 구문에는 특별한 CLR 지원이 없다. 생성자에서 필드에 값을 대입하는 것의 문법적 지름길일 뿐이다.

```csharp
class Widget
{
    int _capacity = 4000;
}
```

를 재현하려면 생성자를 정의한다.

```csharp
FieldBuilder field = tb.DefineField("_capacity", typeof(int), FieldAttributes.Private);

ConstructorBuilder c = tb.DefineConstructor(
    MethodAttributes.Public,
    CallingConventions.Standard,
    new Type[0]);              // 생성자 매개변수

ILGenerator gen = c.GetILGenerator();
gen.Emit(OpCodes.Ldarg_0);          // "this"를 스택에 로드
gen.Emit(OpCodes.Ldc_I4, 4000);     // 4000을 스택에 로드
gen.Emit(OpCodes.Stfld, field);     // 필드에 저장
gen.Emit(OpCodes.Ret);
```

### 기반 생성자 호출

다른 타입을 상속한다면 위 생성자는 **기반 클래스 생성자를 건너뛴다.** C#과 다른 지점이다. C#에서는 직접적이든 간접적이든 기반 클래스 생성자가 항상 호출된다.

```csharp
class A { public A() { Console.Write("A"); } }
class B : A { public B() {} }
```

컴파일러는 사실상 둘째 줄을 이렇게 번역한다.

```csharp
class B : A { public B() : base() {} }
```

IL을 생성할 때는 그렇지 않다. **기반 생성자를 실행하고 싶다면 명시적으로 호출해야 한다** — 거의 항상 그러길 원한다.

```csharp
gen.Emit(OpCodes.Ldarg_0);
ConstructorInfo baseConstr = typeof(A).GetConstructor(new Type[0])!;
gen.Emit(OpCodes.Call, baseConstr);
```

인수가 있는 생성자를 호출하는 것은 메서드와 똑같다.

> **⚠️ 기반 생성자를 빼먹으면 오늘은 되고 내일 깨진다**
>
> `object`를 직접 상속한 타입이라면 `object..ctor()`를 부르지 않아도 대개 동작한다 — `object`의 생성자가 아무 일도 하지 않기 때문이다. 그래서 이 실수는 **테스트를 통과한다.**
>
> 문제는 나중에 기반 타입이 `object`가 아닌 것으로 바뀌었을 때다. 필드 초기화나 유효성 검사를 하는 기반 생성자가 건너뛰어져 객체가 반쯤 초기화된 상태로 살아난다. 게다가 IL 검증 규칙상 생성자는 기반 생성자나 같은 타입의 다른 생성자를 **반드시** 호출해야 하므로, 검증이 활성화된 환경에서는 아예 로드에 실패할 수 있다.
>
> 생성자를 방출할 때는 예외 없이 첫 세 명령을 `ldarg.0` / `call base..ctor` / (인수가 있다면 그 앞에 인수 로드)로 시작하는 습관을 들여라.

### 완전한 예제 3 — 인터페이스를 구현하는 프록시 타입 방출

지금까지의 조각을 모아 실무에서 실제로 쓰는 것을 만든다. **임의의 인터페이스를 받아, 그 인터페이스를 구현하면서 모든 호출을 내부 구현으로 전달하되 호출을 로깅하는 프록시 타입**을 방출한다. Castle DynamicProxy나 EF Core의 지연 로딩 프록시가 하는 일의 축소판이다.

대상 인터페이스와 실제 구현은 이렇다.

```csharp
public interface ICalculator
{
    int Add(int a, int b);
    string Describe(string prefix);
}

public class Calculator : ICalculator
{
    public int Add(int a, int b) => a + b;
    public string Describe(string prefix) => $"{prefix}: 계산기";
}
```

방출 코드다.

```csharp
using System.Reflection;
using System.Reflection.Emit;

public static class ProxyFactory
{
    static readonly ModuleBuilder _module = AssemblyBuilder
        .DefineDynamicAssembly(new AssemblyName("ProxyAsm"),
                               AssemblyBuilderAccess.RunAndCollect)
        .DefineDynamicModule("ProxyModule");

    public static Type CreateLoggingProxy(Type interfaceType)
    {
        if (!interfaceType.IsInterface)
            throw new ArgumentException("인터페이스여야 한다", nameof(interfaceType));

        TypeBuilder tb = _module.DefineType(
            interfaceType.Name + "LoggingProxy",
            TypeAttributes.Public | TypeAttributes.Class | TypeAttributes.Sealed,
            typeof(object),                       // 기반 타입
            new[] { interfaceType });             // 구현할 인터페이스

        // private readonly TInterface _inner;
        FieldBuilder inner = tb.DefineField("_inner", interfaceType,
            FieldAttributes.Private | FieldAttributes.InitOnly);

        EmitConstructor(tb, inner, interfaceType);

        MethodInfo writeLine = typeof(Console)
            .GetMethod(nameof(Console.WriteLine), new[] { typeof(string) })!;

        foreach (MethodInfo m in interfaceType.GetMethods())
            EmitForwarder(tb, inner, interfaceType, m, writeLine);

        return tb.CreateType()!;
    }

    // public XxxLoggingProxy(TInterface inner) : base() { _inner = inner; }
    static void EmitConstructor(TypeBuilder tb, FieldBuilder inner, Type ifaceType)
    {
        ConstructorBuilder ctor = tb.DefineConstructor(
            MethodAttributes.Public,
            CallingConventions.Standard,
            new[] { ifaceType });

        ILGenerator g = ctor.GetILGenerator();
        g.Emit(OpCodes.Ldarg_0);
        g.Emit(OpCodes.Call, typeof(object).GetConstructor(Type.EmptyTypes)!);  // base()
        g.Emit(OpCodes.Ldarg_0);
        g.Emit(OpCodes.Ldarg_1);
        g.Emit(OpCodes.Stfld, inner);
        g.Emit(OpCodes.Ret);
    }

    static void EmitForwarder(TypeBuilder tb, FieldBuilder inner, Type ifaceType,
                              MethodInfo m, MethodInfo writeLine)
    {
        Type[] paramTypes = Array.ConvertAll(m.GetParameters(), p => p.ParameterType);

        MethodBuilder mb = tb.DefineMethod(
            m.Name,
            MethodAttributes.Public   | MethodAttributes.Virtual |
            MethodAttributes.Final    | MethodAttributes.HideBySig |
            MethodAttributes.NewSlot,
            m.ReturnType,
            paramTypes);

        ILGenerator g = mb.GetILGenerator();

        // Console.WriteLine("-> ICalculator.Add");
        g.Emit(OpCodes.Ldstr, $"-> {ifaceType.Name}.{m.Name}");
        g.Emit(OpCodes.Call, writeLine);

        // return _inner.Add(a, b);
        g.Emit(OpCodes.Ldarg_0);
        g.Emit(OpCodes.Ldfld, inner);
        for (int i = 0; i < paramTypes.Length; i++)
            EmitLdarg(g, i + 1);                  // 인스턴스 메서드라 1부터
        g.Emit(OpCodes.Callvirt, m);
        g.Emit(OpCodes.Ret);

        tb.DefineMethodOverride(mb, m);           // 명시적으로 연결
    }

    // 인수 로드 — 58.2절의 헬퍼와 같다.
    static void EmitLdarg(ILGenerator g, int index)
    {
        if      (index == 0) g.Emit(OpCodes.Ldarg_0);
        else if (index == 1) g.Emit(OpCodes.Ldarg_1);
        else if (index == 2) g.Emit(OpCodes.Ldarg_2);
        else if (index == 3) g.Emit(OpCodes.Ldarg_3);
        else if (index <= byte.MaxValue) g.Emit(OpCodes.Ldarg_S, (byte) index);
        else                             g.Emit(OpCodes.Ldarg, (short) index);
    }
}
```

사용은 이렇다.

```csharp
Type proxyType = ProxyFactory.CreateLoggingProxy(typeof(ICalculator));

ICalculator real  = new Calculator();
ICalculator proxy = (ICalculator) Activator.CreateInstance(proxyType, real)!;

Console.WriteLine(proxy.Add(3, 4));
Console.WriteLine(proxy.Describe("결과"));
```

출력이다.

```text
-> ICalculator.Add
7
-> ICalculator.Describe
결과: 계산기
```

방출된 `Add` 전달 메서드의 IL은 다음과 같다.

```il
.method public final hidebysig newslot virtual
        instance int32 Add(int32 A_1, int32 A_2) cil managed
{
  .maxstack  3
  IL_0000:  ldstr      "-> ICalculator.Add"
  IL_0005:  call       void [System.Console]System.Console::WriteLine(string)
  IL_000a:  ldarg.0
  IL_000b:  ldfld      class ICalculator ICalculatorLoggingProxy::_inner
  IL_0010:  ldarg.1
  IL_0011:  ldarg.2
  IL_0012:  callvirt   instance int32 ICalculator::Add(int32, int32)
  IL_0017:  ret
}
```

> **⚠️ 이 프록시가 다루지 못하는 것들**
>
> 예제는 의도적으로 단순하다. 실무 프록시로 쓰려면 다음을 더 처리해야 한다.
>
> - **상속된 인터페이스** — `interfaceType.GetMethods()`는 그 인터페이스가 **직접 선언한** 메서드만 돌려준다. `ICalculator : IDisposable`이라면 `Dispose`가 빠져 `TypeLoadException`("메서드가 구현을 갖지 않는다")이 난다. `GetInterfaces()`를 순회해 전부 구현해야 한다.
> - **프로퍼티와 이벤트** — 메타데이터상으로는 `get_X`/`set_X`/`add_X`/`remove_X` 메서드이므로 위 루프가 본문은 만들어 준다. 그러나 `DefineProperty` + `SetGetMethod`로 프로퍼티 항목을 만들지 않으면 프록시 타입에 프로퍼티가 보이지 않는다.
> - **제네릭 메서드** — `m.IsGenericMethodDefinition`이면 `DefineGenericParameters`로 타입 매개변수를 먼저 만들어야 한다(58.9절).
> - **`ref`/`out`/`in` 매개변수** — `p.ParameterType`이 이미 `ByRef` 타입이라 전달 자체는 되지만, `out`은 `ParameterAttributes.Out`을 다시 붙여야 소비자가 C#에서 `out`으로 인식한다.
> - **`ref struct` 매개변수** — 박싱도 저장도 불가능하므로 인터셉션 계층에서 특별 취급이 필요하다.
>
> Castle DynamicProxy 같은 성숙한 라이브러리가 존재하는 이유가 이 목록이다. **직접 방출하기 전에 그것으로 충분한지 먼저 확인하라.**

## 58.8 특성 부착

동적 구조에 커스텀 특성을 붙이려면 `CustomAttributeBuilder`를 만들어 `SetCustomAttribute`에 넘긴다. 다음 특성 선언을 필드나 프로퍼티에 붙이고 싶다고 하자.

```csharp
[XmlElement("FirstName", Namespace = "http://test/", Order = 3)]
```

이는 문자열 하나를 받는 `XmlElementAttribute` 생성자에 의존한다. `CustomAttributeBuilder`를 쓰려면 그 생성자와, 설정하려는 두 프로퍼티(`Namespace`와 `Order`)를 조회해야 한다.

```csharp
using System.Xml.Serialization;

Type attType = typeof(XmlElementAttribute);
ConstructorInfo attConstructor = attType.GetConstructor(
    new Type[] { typeof(string) })!;

var att = new CustomAttributeBuilder(
    attConstructor,                          // 생성자
    new object[] { "FirstName" },            // 생성자 인수
    new PropertyInfo[]                       // 프로퍼티
    {
        attType.GetProperty("Namespace")!,
        attType.GetProperty("Order")!
    },
    new object[] { "http://test/", 3 });     // 프로퍼티 값

myFieldBuilder.SetCustomAttribute(att);
// 또는 propBuilder.SetCustomAttribute(att);
// 또는 typeBuilder.SetCustomAttribute(att);
```

`SetCustomAttribute`는 `AssemblyBuilder`, `ModuleBuilder`, `TypeBuilder`, `MethodBuilder`, `ConstructorBuilder`, `FieldBuilder`, `PropertyBuilder`, `EventBuilder`, `ParameterBuilder`, `GenericTypeParameterBuilder`에 모두 있다. 즉 C#에서 특성을 붙일 수 있는 거의 모든 자리에 붙일 수 있다.

생성자 인수 → 명명 프로퍼티 → 명명 필드 순서로 여섯 개 인수를 받는 오버로드도 있다(`new CustomAttributeBuilder(ctor, ctorArgs, namedProperties, propertyValues, namedFields, fieldValues)`).

> **⚠️ 생성자 인수 타입은 정확히 일치해야 한다**
>
> `CustomAttributeBuilder`는 인수 배열의 각 값이 생성자 매개변수 타입과 **정확히** 맞기를 요구한다. `int` 자리에 `long`을, `object` 자리에 값 타입을 그냥 넣으면 `ArgumentException`이 난다. 열거형 인수는 열거형 값 자체를 넘겨야 하고, 기저 정수를 넘기면 안 된다.
>
> 그리고 특성 인수로 허용되는 것은 상수·`Type`·열거형·이들의 1차원 배열뿐이다. 임의의 객체를 넘길 수 없다는 C#의 제약이 여기에도 그대로 적용된다.

> **📌 실무에서 특성 방출이 필요한 순간**
>
> 방출한 타입을 **다른 프레임워크가 리플렉션으로 읽을 때**다. `XmlSerializer`, `System.Text.Json`, ASP.NET Core 모델 바인딩, 유효성 검사기는 전부 특성을 보고 동작한다(57.11절). 반대로 `[StructLayout]`, `[MethodImpl]`, `[FieldOffset]`처럼 **런타임 동작에 직접 영향을 주는** 특성도 있는데, 이 중 상당수는 `TypeAttributes`/`MethodImplAttributes`나 `FieldBuilder.SetOffset` 같은 전용 API로도 지정할 수 있고 그쪽이 더 안전하다.

## 58.9 제네릭 메서드·제네릭 타입 방출

### 제네릭 메서드 정의

제네릭 메서드를 방출하는 절차는 셋이다.

1. `MethodBuilder`의 `DefineGenericParameters`를 호출해 `GenericTypeParameterBuilder` 배열을 얻는다.
2. 이 제네릭 타입 매개변수를 써서 `MethodBuilder`의 `SetSignature`를 호출한다.
3. 선택적으로 매개변수에 이름을 붙인다.

다음 제네릭 메서드를

```csharp
public static T Echo<T>(T value)
{
    return value;
}
```

이렇게 방출한다.

```csharp
TypeBuilder tb = modBuilder.DefineType("Widget", TypeAttributes.Public);
MethodBuilder mb = tb.DefineMethod("Echo", MethodAttributes.Public |
                                           MethodAttributes.Static);

GenericTypeParameterBuilder[] genericParams = mb.DefineGenericParameters("T");

mb.SetSignature(genericParams[0],      // 반환 타입
                null, null,
                genericParams,          // 매개변수 타입
                null, null);

mb.DefineParameter(1, ParameterAttributes.None, "value");    // 선택 사항

ILGenerator gen = mb.GetILGenerator();
gen.Emit(OpCodes.Ldarg_0);
gen.Emit(OpCodes.Ret);
```

`DefineGenericParameters`는 원하는 제네릭 타입 이름에 해당하는 문자열을 개수 제한 없이 받는다. 위 예제에서는 `T` 하나만 필요했다.

`GenericTypeParameterBuilder`는 `System.Type`을 상속하므로, 옵코드를 방출할 때 `TypeBuilder`가 올 자리에 그대로 쓸 수 있다.

> **⚠️ `DefineMethod` 시점에는 시그니처를 줄 수 없다**
>
> 제네릭 메서드에서는 `DefineMethod` 호출에 반환 타입과 매개변수 타입을 **넘길 수 없다.** 그 타입들이 아직 존재하지 않는 `T`를 참조하기 때문이다. 그래서 이름과 `MethodAttributes`만 주는 오버로드를 쓰고, `DefineGenericParameters`로 `T`를 만든 뒤 `SetSignature`로 시그니처를 나중에 채운다.
>
> 순서를 어겨 `DefineMethod`에 타입을 주고 나서 `DefineGenericParameters`를 호출하면 `InvalidOperationException`이 난다. **`DefineGenericParameters`는 시그니처가 아직 설정되지 않은 메서드에만 호출할 수 있다.**

### 제약 지정

`GenericTypeParameterBuilder`로 기반 타입 제약과 인터페이스 제약을 지정한다.

```csharp
genericParams[0].SetBaseTypeConstraint(typeof(Foo));            // where T : Foo
genericParams[0].SetInterfaceConstraints(typeof(IComparable));  // where T : IComparable

// where T : IComparable<T>
genericParams[0].SetInterfaceConstraints(
    typeof(IComparable<>).MakeGenericType(genericParams[0]));
```

다른 종류의 제약은 `SetGenericParameterAttributes`에 `GenericParameterAttributes` 열거형 멤버를 넘긴다.

| 값 | C# 대응 |
|---|---|
| `DefaultConstructorConstraint` | `where T : new()` |
| `NotNullableValueTypeConstraint` | `where T : struct` |
| `ReferenceTypeConstraint` | `where T : class` |
| `Covariant` | 타입 매개변수의 `out` 한정자 |
| `Contravariant` | 타입 매개변수의 `in` 한정자 |

### 제네릭 타입 정의

제네릭 타입도 비슷하게 정의한다. 차이는 `DefineGenericParameters`를 `MethodBuilder`가 아니라 `TypeBuilder`에서 호출한다는 것이다.

```csharp
public class Widget<T>
{
    public T Value;
}
```

를 재현하려면 이렇게 한다.

```csharp
TypeBuilder tb = modBuilder.DefineType("Widget", TypeAttributes.Public);
GenericTypeParameterBuilder[] genericParams = tb.DefineGenericParameters("T");
tb.DefineField("Value", genericParams[0], FieldAttributes.Public);
```

제네릭 제약은 메서드에서와 똑같이 추가할 수 있다.

> **📌 백틱 표기는 자동으로 붙는다**
>
> `DefineType("Widget", ...)` 뒤에 `DefineGenericParameters("T")`를 호출하면 타입의 CLR 이름은 `Widget`1`이 된다(56.3절의 백틱 규칙). `DefineType`에 직접 백틱을 적으면 두 번 붙는다. 만든 제네릭 타입을 닫을 때는 평범하게 `MakeGenericType`을 쓴다 — `tb.CreateType()!.MakeGenericType(typeof(int))`.

## 58.10 까다로운 방출 대상 — 미생성 닫힌 제네릭, 순환 의존성

### 미생성 타입으로 닫은 제네릭

닫힌 제네릭 타입(`List<int>`)을 지역 변수로 쓰는 정적 메서드를 방출한다고 하자.

```csharp
TypeBuilder tb = modBuilder.DefineType("Widget", TypeAttributes.Public);
MethodBuilder mb = tb.DefineMethod("Test", MethodAttributes.Public |
                                           MethodAttributes.Static);
ILGenerator gen = mb.GetILGenerator();

Type variableType = typeof(List<int>);
ConstructorInfo ci = variableType.GetConstructor(new Type[0])!;
LocalBuilder listVar = gen.DeclareLocal(variableType);
gen.Emit(OpCodes.Newobj, ci);
gen.Emit(OpCodes.Stloc, listVar);
gen.Emit(OpCodes.Ret);
```

이제 `List<int>` 대신 `List<Widget>`을 원한다고 하자.

```csharp
public class Widget
{
    public static void Test() { var list = new List<Widget>(); }
}
```

이론상 한 줄만 바꾸면 된다.

```csharp
Type variableType = typeof(List<>).MakeGenericType(tb);
```

그런데 이렇게 하면 뒤이은 `GetConstructor` 호출에서 `NotSupportedException`이 난다. **미생성 타입 빌더로 닫은 제네릭 타입에는 `GetConstructor`를 호출할 수 없다.** `GetField`, `GetMethod`도 마찬가지다.

해결책은 직관적이지 않다. `TypeBuilder`에는 정적 메서드 세 개가 있다.

```csharp
public static ConstructorInfo GetConstructor (Type, ConstructorInfo);
public static FieldInfo       GetField       (Type, FieldInfo);
public static MethodInfo      GetMethod      (Type, MethodInfo);
```

이름만 봐서는 알 수 없지만, 이 메서드들은 **미생성 타입 빌더로 닫힌 제네릭 타입의 멤버를 얻기 위해 존재한다.** 첫 매개변수는 닫힌 제네릭 타입이고, 둘째 매개변수는 **열린(unbound) 제네릭 타입에서 원하는 멤버**다.

```csharp
ILGenerator gen = mb.GetILGenerator();

Type variableType = typeof(List<>).MakeGenericType(tb);
ConstructorInfo unbound = typeof(List<>).GetConstructor(new Type[0])!;
ConstructorInfo ci = TypeBuilder.GetConstructor(variableType, unbound);

LocalBuilder listVar = gen.DeclareLocal(variableType);
gen.Emit(OpCodes.Newobj, ci);
gen.Emit(OpCodes.Stloc, listVar);
gen.Emit(OpCodes.Ret);
```

> **⚠️ 이 세 메서드는 오직 그 목적에만 쓸 수 있다**
>
> `TypeBuilder.GetMethod(closedType, openMethod)`에 **이미 생성된** 타입으로 닫은 제네릭을 넘기면 예외가 난다. 즉 "제네릭 타입의 멤버를 얻는 일반 도구"가 아니라 미생성 빌더 전용 우회로다. 방출 코드에서 타입이 생성 전인지 후인지에 따라 다른 경로를 타야 한다는 뜻이고, 이 조건 분기를 빠뜨리는 것이 흔한 실수다.
>
> 둘째 인수에는 **열린 제네릭 정의의 멤버**를 넘겨야 한다. `typeof(List<int>).GetConstructor(...)`가 아니라 `typeof(List<>).GetConstructor(...)`다.

### 순환 의존성

서로를 참조하는 두 타입을 만들고 싶다고 하자.

```csharp
class A { public B Bee; }
class B { public A Aye; }
```

동적으로는 이렇게 생성한다.

```csharp
var publicAtt = FieldAttributes.Public;
TypeBuilder aBuilder = modBuilder.DefineType("A");
TypeBuilder bBuilder = modBuilder.DefineType("B");

FieldBuilder bee = aBuilder.DefineField("Bee", bBuilder, publicAtt);
FieldBuilder aye = bBuilder.DefineField("Aye", aBuilder, publicAtt);

Type realA = aBuilder.CreateType()!;
Type realB = bBuilder.CreateType()!;
```

**두 객체를 모두 채운 뒤에야 `CreateType`을 호출했다는 점**에 주목하라. 원칙은 이렇다. **먼저 전부 연결하고, 그다음 각 타입 빌더에서 `CreateType`을 호출한다.**

흥미롭게도 `realA` 타입은 `bBuilder`에서 `CreateType`을 호출하기 전까지는 유효하지만 제 기능을 하지 못한다 — 그 전에 필드 `Bee`에 접근하려 하면 예외가 난다. `bBuilder`가 `realB`를 만든 뒤 `realA`를 고쳐 주는 것이 아니라, **`realA`가 다음번에 사용될 때 스스로를 고친다.** `CreateType` 호출 후 `TypeBuilder`가 실제 런타임 타입의 프록시로 변신하기 때문에, `bBuilder`에 대한 참조를 가진 `realA`가 필요한 메타데이터를 얻어 자신을 갱신할 수 있다.

### 값 타입이 끼면 순환이 깨진다

이 방식은 타입 빌더가 미생성 타입에 **미리 결정 가능한 단순한 정보**(타입·멤버·객체 참조)만 요구할 때 작동한다. `realA`를 만들 때 타입 빌더는 `realB`가 메모리에서 몇 바이트를 차지할지 알 필요가 없다. 그러나 `realB`가 **구조체**라면 다르다 — `realB`의 최종 크기가 `realA`를 만드는 데 결정적인 정보가 된다.

관계가 비순환적이라면, 예컨대

```csharp
struct A { public B Bee; }
struct B {                }
```

구조체 `B`를 먼저 만들고 `A`를 만들면 해결된다. 그러나 다음은 다르다.

```csharp
struct A { public B Bee; }
struct B { public A Aye; }
```

두 구조체가 서로를 담는 것은 무의미하므로 방출하지 않는다(C#도 컴파일 오류를 낸다). 하지만 다음 변형은 합법적이고 유용하다.

```csharp
public struct S<T> { }      // S는 비어 있어도 이 예제는 성립한다

class A { S<B> Bee; }
class B { S<A> Aye; }
```

`A`를 만들 때 타입 빌더가 `B`의 메모리 크기를 알아야 하고, 그 반대도 마찬가지다. 구조체 `S`가 정적으로 정의되어 있다고 가정하고 클래스 `A`와 `B`를 방출해 보자.

```csharp
var pub = FieldAttributes.Public;
TypeBuilder aBuilder = modBuilder.DefineType("A");
TypeBuilder bBuilder = modBuilder.DefineType("B");

aBuilder.DefineField("Bee", typeof(S<>).MakeGenericType(bBuilder), pub);
bBuilder.DefineField("Aye", typeof(S<>).MakeGenericType(aBuilder), pub);

Type realA = aBuilder.CreateType();     // 오류: 타입 B를 로드할 수 없다
Type realB = bBuilder.CreateType();
```

이제 `CreateType`은 **어느 순서로 호출하든** `TypeLoadException`을 던진다.

- `aBuilder.CreateType`을 먼저 부르면 "타입 B를 로드할 수 없다"고 한다.
- `bBuilder.CreateType`을 먼저 부르면 "타입 A를 로드할 수 없다"고 한다.

해결하려면 `realA`를 만드는 **도중에** 타입 빌더가 `realB`를 만들 수 있게 허용해야 한다. `CreateType`을 호출하기 직전에 `AppDomain` 클래스의 `TypeResolve` 이벤트를 처리하면 된다. 마지막 두 줄을 이렇게 바꾼다.

```csharp
TypeBuilder[] uncreatedTypes = { aBuilder, bBuilder };

ResolveEventHandler handler = delegate (object? o, ResolveEventArgs args)
{
    var type = uncreatedTypes.FirstOrDefault(t => t.FullName == args.Name);
    return type == null ? null : type.CreateType()!.Assembly;
};

AppDomain.CurrentDomain.TypeResolve += handler;
Type realA = aBuilder.CreateType()!;
Type realB = bBuilder.CreateType()!;
AppDomain.CurrentDomain.TypeResolve -= handler;
```

`TypeResolve` 이벤트는 `aBuilder.CreateType` 호출 도중, 즉 `bBuilder`에서 `CreateType`을 호출해 달라고 요청하는 시점에 발생한다.

중첩 타입을 정의할 때 중첩 타입과 부모 타입이 서로를 참조하는 경우에도 이 예제처럼 `TypeResolve` 이벤트를 처리해야 한다.

> **⚠️ `TypeResolve` 핸들러는 반드시 떼라**
>
> `AppDomain.CurrentDomain`은 프로세스 수명 내내 살아 있다(52.12절). 핸들러를 등록만 하고 해제하지 않으면 **핸들러가 캡처한 `TypeBuilder` 배열과 그것이 속한 동적 어셈블리 전체가 영구히 살아남는다.** 수집 가능 어셈블리를 쓰는 의미가 사라지고, 수집 가능 ALC를 언로드하려는 시도도 실패한다.
>
> 위 코드처럼 `try`/`finally`로 감싸 반드시 해제하라. 방출 도중 예외가 나면 `-=`가 실행되지 않는다.

### 방출한 IL이 `InvalidProgramException`을 낼 때

`Reflection.Emit`으로 만든 코드는 컴파일러의 검증을 받지 않는다. 잘못된 IL은 방출 시점이 아니라 **JIT이 그 메서드를 컴파일하려는 순간** 터진다.

```text
System.InvalidProgramException:
  Common Language Runtime detected an invalid program.
```

메시지에는 어떤 명령이 문제인지, 어디인지가 **전혀 없다.** 순서대로 확인할 목록이 필요하다.

**1단계 — 스택 균형을 손으로 추적한다.** 압도적으로 가장 흔한 원인이다. 방출 순서대로 표를 그려 각 명령 뒤의 스택 깊이를 적어라(이 장에서 계속 해 온 형식이다). 확인할 것은 셋이다.

- `ret` 시점의 깊이가 반환 타입과 맞는가 (`void`면 0, 아니면 1).
- 호출한 메서드의 **반환값을 버렸는가** — `void`가 아닌 메서드를 부르고 `Pop`하지 않으면 깊이가 어긋난다.
- 분기 합류 지점의 깊이가 모든 경로에서 같은가(56.2절).

**2단계 — 타입 불일치를 본다.** 스택 깊이가 맞아도 타입이 틀리면 무효다.

| 증상 | 원인 |
|---|---|
| 값 타입을 `object` 자리에 넘겼다 | `Box` 누락 |
| `object`를 값 타입 자리에 넘겼다 | `Unbox_Any` 누락 |
| 값 타입 인스턴스 메서드가 실패한다 | 값 대신 주소가 필요 — `Ldloca`/`Ldarga`/`Unbox` |
| `int`를 `long` 매개변수에 넘겼다 | `Conv_I8` 누락 (IL은 암묵적 확대 변환을 하지 않는다) |
| 필드 접근이 실패한다 | 인스턴스 필드인데 `this`를 안 올렸거나, 정적인데 올렸다 |

**3단계 — 옵코드 피연산자 크기를 본다.** 58.2절의 `Emit(OpCodes.Ldarg, 1)` 함정이다. `Ldarg`/`Ldc_I4_S`/`Br_S` 계열에 잘못된 크기의 리터럴을 넘겼는지 확인하라. 이 오류는 IL 스트림 전체를 어긋나게 하므로 증상이 무작위로 보인다.

**4단계 — 정적/인스턴스, `Call`/`Callvirt`를 본다.** 인스턴스 메서드를 방출하면서 `Ldarg_0`을 첫 인수로 착각했는지, `base` 호출에 `Callvirt`를 써서 무한 재귀를 만들었는지 확인한다.

도구로 좁히는 방법은 다음과 같다.

| 방법 | 어떻게 |
|---|---|
| **방출 로그** | `ILGenerator`를 래퍼로 감싸 `Emit` 호출마다 `(ILOffset, OpCode, operand)`를 기록한다. 사후 분석의 기본 자료다 |
| **`PersistedAssemblyBuilder.Save`** ※.NET 9 | 방출 결과를 `.dll`로 저장해 ILSpy/`ildasm`으로 연다. **가장 강력한 방법** |
| **`ILVerify`** ※ | `dotnet tool install -g dotnet-ilverify` 후 저장한 어셈블리를 검증한다. 스택 불균형·타입 불일치를 위치와 함께 알려준다 |
| **`MethodBuilder` 우선 개발** | `DynamicMethod`는 저장할 수 없다. 개발 중에는 `TypeBuilder`/`MethodBuilder`로 만들어 저장·검증하고, 완성 후 `DynamicMethod`로 옮긴다 |
| **`EmitWriteLine` 삽입** | 의심 구간 앞뒤에 로그를 넣어 어디까지 실행되는지 확인한다. 단, 스택이 비어 있는 지점에만 넣어야 한다 |
| **최소 재현** | 방출 루프에서 메서드를 하나씩 줄여 가며 어느 메서드가 원인인지 이분 탐색한다 |

> **⚠️ `InvalidProgramException`이 아닌 다른 증상들**
>
> 잘못된 IL이 항상 `InvalidProgramException`으로 나타나는 것은 아니다. 증상마다 원인이 다르다.
>
> | 예외 | 대표 원인 |
> |---|---|
> | `InvalidProgramException` | 스택 불균형, 잘못된 피연산자 크기, 보호 블록 규칙 위반 |
> | `TypeLoadException` | 인터페이스 메서드 미구현, 중첩 타입 가시성 오류, 순환 의존성 |
> | `BadImageFormatException` | 저장한 어셈블리의 메타데이터가 손상 |
> | `NotSupportedException` | 미생성 `TypeBuilder`에 `GetMethod`/`GetMembers` 등을 호출 |
> | `MissingMethodException` | 방출한 IL이 실제로 존재하지 않는 멤버를 참조 |
> | `MemberAccessException` | `skipVisibility` 없이 비공개 멤버 접근 |
> | `StackOverflowException` | `base` 호출을 `Callvirt`로 방출해 자기 재귀 |
> | **프로세스 즉사(AV)** | `.NET`은 완전 신뢰 코드의 IL을 전부 검증하지 않는다. 타입 안전성을 깨는 IL은 검증 대신 **접근 위반**으로 나타날 수 있다 |
>
> 마지막 줄이 이 API의 본질이다. **`Reflection.Emit`은 관리 코드 안에 있는 비관리 코드에 가깝다.** 실수의 대가가 예외가 아니라 프로세스 종료일 수 있다.

## 58.11 Emit vs 식 트리 vs 소스 생성기 — 선택 기준

### 다섯 가지 선택지

같은 문제 — "컴파일 타임에 모르는 타입을 빠르게 다루기" — 를 푸는 도구가 다섯 있고, 이 책은 각각을 다른 장에서 다뤘다.

| 도구 | 다룬 곳 | 코드가 만들어지는 시점 | 표현력 | 난이도 |
|---|---|---|---|---|
| **리플렉션 + 캐싱** | 57.12절 | 없음 (해석 실행) | 전체 | 낮음 |
| **델리게이트 (`CreateDelegate`)** | 57.13절 | 런타임 (바인딩만) | 시그니처가 정확히 맞을 때만 | 낮음 |
| **식 트리 (`Expression.Compile`)** | 31장, 57.13절 | 런타임 (IL 생성) | C# 식 대부분 | 중간 |
| **소스 생성기** | 57.15절 | **컴파일 타임** | C# 전체 | 중간 |
| **`Reflection.Emit`** | 이 장 | 런타임 (IL 생성) | **IL 전체** | 높음 |

### 결정 흐름

```text
 컴파일 타임에 대상 타입을 아는가?
   │
   ├─ 예 ──▶ 소스 생성기 (57.15절)
   │           시작 비용 0, AOT 완전 호환, 생성된 C#에 중단점을 찍을 수 있다.
   │
   └─ 아니오
        │
        ├─ 호출이 뜨겁지 않은가? ──▶ 리플렉션 + MemberInfo 캐싱 (57.12절)
        │
        ├─ 시그니처가 컴파일 타임에 고정되는가?
        │      └─ 예 ──▶ Delegate.CreateDelegate (57.13절)
        │
        ├─ C# 식으로 표현 가능한가?
        │      └─ 예 ──▶ 식 트리 Compile() (31장)
        │
        └─ 아니오 ──▶ Reflection.Emit (이 장)
                        ref 지역, calli, 값 타입 제자리 수정,
                        타입 자체를 만들어야 하는 경우.
```

### 식 트리가 못 하는 것

식 트리 컴파일러는 내부적으로 `Reflection.Emit`을 쓰지만, `Expression` 노드로 표현 가능한 것만 방출한다. 다음은 `Emit`이어야 한다.

- **새 타입 자체를 만드는 일** — 인터페이스를 구현하는 프록시, 동적 DTO. 식 트리는 메서드 본문만 만든다.
- **`ref` 지역 변수와 `ref` 반환** — `Expression`에 대응 노드가 없다.
- **`calli`(간접 호출)와 함수 포인터**.
- **`localloc`(`stackalloc`)**.
- **값 타입을 박싱 없이 제자리에서 수정하기** — 식 트리는 값 의미론을 지키느라 복사를 넣는다.
- **`fault` 블록, 예외 필터의 세밀한 제어**.
- **명시적 인터페이스 구현, 특성이 붙은 멤버 방출**.

반대로 식 트리가 압도적으로 유리한 점도 분명하다. 코드가 **절반 이하**이고 읽을 수 있으며, 타입 검사를 **트리 구축 시점**에 해 준다 — 잘못된 조합은 `Expression.Call`에서 바로 `ArgumentException`이지만 `Emit`은 JIT까지 조용하다. `ExpressionVisitor`로 트리를 변형·최적화할 수 있고, `expr.ToString()`으로 사람이 읽을 수 있는 형태를 얻어 디버깅이 비교 불가하게 쉽다.

> **💡 실무 기본값: 소스 생성기 → 식 트리 → Emit**
>
> `Emit`을 처음부터 고르는 것은 거의 항상 조기 최적화다. 순서를 지켜라.
>
> 1. **소스 생성기로 될 일인가** 먼저 묻는다. `System.Text.Json`, `[GeneratedRegex]`, `LoggerMessage`, `[LibraryImport]`가 전부 이 길을 택했고, 그 결과 AOT와 트리밍에서 자유롭다.
> 2. 안 되면 **식 트리**로 만든다. 코드 리뷰가 가능한 수준을 유지한다.
> 3. 식 트리로 표현할 수 없는 것이 남았을 때만 **`Emit`** 으로 내려간다. 그때도 전체가 아니라 **그 부분만** 내린다.
>
> 그리고 `Emit`을 쓰기로 했다면, 팀에 그 코드를 유지 보수할 사람이 몇 명인지 세어 보라. 한 명이라면 그 사람이 퇴사하는 날 그 코드는 동결된다.

### 성능 — 무엇이 실제로 다른가

세 축을 구분해야 한다.

| 축 | 리플렉션 | 식 트리 | `Emit` | 소스 생성기 |
|---|---|---|---|---|
| **시작(생성) 비용** | 낮음 (조회만) | **높음** (트리 구축 + IL 방출 + JIT) | 중간 (IL 방출 + JIT) | **0** |
| **호출당 비용** | 높음 | 낮음 (직접 호출 수준) | 낮음 (직접 호출 수준) | **0** (진짜 직접 호출) |
| **메모리** | 낮음 | 동적 메서드 + 클로저 | 동적 메서드 | **0** |

식 트리와 `Emit`의 호출당 비용은 사실상 같다 — **같은 IL이 나오기 때문이다.** 차이는 **생성 비용**에 있다. 시작 시점에 수천 개의 접근자를 만드는 ORM이나 직렬화기라면 이 차이가 시작 시간으로 나타나고, 몇 개만 만든다면 측정되지 않는다.

> **⚠️ "Emit이 더 빠르다"는 말의 범위**
>
> `Emit`이 식 트리보다 빠른 것은 **코드를 만드는 시간**이지 **만들어진 코드의 실행 속도**가 아니다. 벤치마크를 잘못 설계해 생성 비용을 호출 비용에 섞으면 정반대 결론이 나온다.
>
> 그리고 어느 쪽이든 **첫 호출에는 JIT 비용이 붙는다.** 동적으로 만든 메서드는 R2R 이미지에 없으므로(55.7절) 반드시 Tier-0 JIT을 거치고, 뜨거워지면 Tier-1로 재컴파일된다(55.2절). 시작 시간을 재는 벤치마크라면 이 비용이 지배적이다.

## 이 장의 요약

- **`System.Reflection.Emit`은 런타임에 메타데이터와 IL을 만드는 API다.** 정규식 컴파일, ORM 프록시, 직렬화기, DI 컨테이너가 전부 이 위에 서 있다. 목적은 하나다 — 바인딩 비용을 한 번만 내고 실행 비용을 직접 호출 수준으로 낮추는 것.
- **`DynamicMethod`는 가벼운 진입점이다.** 어셈블리·모듈·타입 없이 메서드 하나를 만들고, 참조가 사라지면 GC된다. `owner` 타입과 `skipVisibility`로 비공개 멤버에 접근할 수 있다. 운영 코드에서는 반드시 `CreateDelegate`로 감싼다.
- **모든 것이 평가 스택 위에서 일어난다.** 인수를 푸시하고, 명령이 팝하고, 결과를 다시 푸시한다. `ret` 시점에 스택은 반환 타입과 정확히 맞아야 하고, 분기 합류 지점의 깊이는 모든 경로에서 같아야 한다. 이 규칙을 어기면 `InvalidProgramException`이다.
- **옵코드의 피연산자 크기를 맞춰야 한다.** `Emit(OpCodes.Ldarg, 1)`처럼 `int`를 16비트 피연산자 자리에 넘기면 IL 스트림 전체가 어긋난다. `ILGenerator`는 검증하지 않는다.
- **참조 타입 인스턴스 메서드는 `Callvirt`, 정적·값 타입 메서드와 `base` 호출은 `Call`이다.** `base`를 `Callvirt`로 방출하면 무한 재귀로 프로세스가 죽는다.
- **완전한 타입을 만들려면 `AssemblyBuilder` → `ModuleBuilder` → `TypeBuilder` → 멤버 빌더 순서를 거친다.** `CreateType()`이 타입을 굽고, 그 전까지 `GetMethod` 같은 리플렉션 조회는 예외를 던진다. 미생성 타입의 멤버는 빌더 객체로만 참조한다.
- **디스크 저장은 .NET Core에서 사라졌다가 ※.NET 9의 `PersistedAssemblyBuilder`로 돌아왔다.** 배포보다 **디버깅**을 위한 기능이다 — 방출한 IL을 파일로 떨궈 ILSpy와 `ILVerify`로 확인할 수 있다.
- **미생성 타입 빌더로 닫은 제네릭에는 `TypeBuilder.GetConstructor/GetField/GetMethod` 정적 메서드를 써야 한다.** 순환 참조는 "전부 연결한 뒤 굽기"로 해결하되, 값 타입이 끼면 `AppDomain.TypeResolve` 이벤트가 필요하고 그 핸들러는 반드시 해제해야 한다.
- **Native AOT에서는 전부 막힌다.** `RuntimeFeature.IsDynamicCodeSupported`로 분기하고 폴백 경로를 두며, 공개 API에는 `[RequiresDynamicCode]`를 붙인다. 수집 가능성이 필요하면 `RunAndCollect`와 수집 가능 ALC를 쓴다.
- **선택 순서는 소스 생성기 → 식 트리 → `Emit`이다.** `Emit`이 식 트리보다 빠른 것은 코드를 **만드는** 시간이지 만들어진 코드가 도는 속도가 아니다. 유지 보수 비용까지 계산에 넣어라.

## 연습 문제

1. `int` 두 개를 받아 큰 쪽을 반환하는 `DynamicMethod`를 만들어라. `Clt`와 `Brtrue`를 써서 분기하고, `CreateDelegate<Func<int,int,int>>`로 호출해 결과를 확인하라. 그다음 `Pop`을 하나 빼거나 `Ret`을 빼서 어떤 예외가 언제 나는지 관찰하라.
2. `FastAccessor`(58.4절)를 확장해 **세터**도 만들어라. `Action<object, object?>`를 반환하고, 값 타입 프로퍼티에 대해 `Unbox_Any`가 필요한 이유를 스택 추적으로 설명하라. `int` 프로퍼티에 `string`을 넘겼을 때 나는 예외를 확인하라.
3. 58.4절의 게터 방출 코드, 같은 일을 하는 식 트리(57.13절), `PropertyInfo.GetValue`를 BenchmarkDotNet으로 비교하라. **생성 비용**과 **호출당 비용**을 별도 벤치마크로 분리해서 재고, 두 결과가 왜 반대 방향을 가리키는지 설명하라.
4. 58.7절의 프록시 팩터리를 고쳐 **상속된 인터페이스**(`interfaceType.GetInterfaces()`)와 **프로퍼티**(`DefineProperty` + `SetGetMethod`)를 지원하게 하라. `IDisposable`을 상속한 인터페이스로 테스트해 수정 전에는 어떤 예외가 나는지 먼저 확인하라.
5. `AppDomain.TypeResolve` 없이 58.10절의 `S<T>` 순환 예제를 실행해 `TypeLoadException` 메시지를 두 순서 모두에서 확인하라. 그다음 핸들러를 붙이되 `try`/`finally` 없이 방출 도중 예외를 던져, 핸들러가 남았을 때 다음 방출이 어떻게 오염되는지 관찰하라.
6. ※.NET 9 환경에서 `PersistedAssemblyBuilder`로 위 프록시 타입을 `.dll`로 저장하고 ILSpy로 열어 방출한 IL이 예상과 같은지 확인하라. 그다음 `dotnet-ilverify`로 검증하고, 일부러 `Ldarg_1`을 `Ldarg_2`로 바꿔 어떤 진단이 나오는지 보라.
7. `RuntimeFeature.IsDynamicCodeSupported`로 분기하는 접근자 팩터리를 만들고, 같은 프로젝트를 일반 게시와 `PublishAot=true` 게시로 각각 빌드하라. AOT 빌드에서 IL3050 경고가 어디에 나는지, `[RequiresDynamicCode]`를 붙이면 경고가 어떻게 이동하는지 확인하라.
