## 72.1 `System.IO.Pipelines`로 제로 카피 파싱

### `Stream`으로는 왜 부족한가

`Stream`은 .NET이 처음 나온 날부터 있었다(40.1절). 일을 하기는 한다. 그러나 고성능 코드에는 맞지 않는다. 이유는 세 가지다.

- **할당이 많다.** 읽을 때마다 버퍼가 필요하고, 그 버퍼는 대개 `new byte[N]`이다.
- **복사가 많다.** OS 버퍼 → 스트림 내부 버퍼 → 사용자 버퍼로 데이터가 두 번 이상 옮겨 다닌다.
- **다중 스레드에서 동기화 오버헤드가 있다.** 생산자와 소비자를 분리하려면 직접 잠금을 걸어야 한다.

버퍼를 쓰는 효율적인 코드를 위해서는 새로운 것이 필요했다. 그렇게 나온 것이 **파이프라인(pipelines, 처음 이름은 channels)** 이다. Kestrel 웹 서버 팀의 성능 작업에서 태어났고, 지금은 범용 라이브러리로 노출되어 있다. .NET Framework 4.6.2와 .NET 6 이상에서 `System.IO.Pipelines` 패키지로 쓸 수 있다.

그런데 "할당과 복사"보다 더 근본적인 문제가 있다. **스트림 위에서 프로토콜을 올바르게 파싱하는 코드는 놀랍도록 쓰기 어렵다.** 다음 코드를 보자. 소켓에서 줄 단위로 데이터를 읽는, 흔히 볼 수 있는 코드다.

```csharp
// 이 코드는 틀렸다. 어디가 틀렸는지 찾아보라.
async Task ProcessLinesBrokenAsync(Socket socket)
{
    var stream = new NetworkStream(socket);
    var buffer = new byte[1024];

    while (true)
    {
        int read = await stream.ReadAsync(buffer, 0, buffer.Length);
        if (read == 0) break;

        // 버퍼에서 개행을 찾아 한 줄을 처리한다
        int index = Array.IndexOf(buffer, (byte)'\n', 0, read);
        if (index >= 0)
            ProcessLine(buffer.AsSpan(0, index));
    }
}
```

틀린 곳이 최소 네 군데다.

| 결함 | 무엇이 깨지는가 |
|---|---|
| **메시지가 여러 read에 걸쳐 도착한다** | `"Hello\n"`이 `"Hel"`과 `"lo\n"` 두 번에 나뉘어 도착하면 첫 read에서 개행을 못 찾고, 다음 read가 `"Hel"`을 덮어써 버린다 |
| **한 read에 메시지가 여러 개 들어온다** | `"A\nB\nC\n"`이 한 번에 오면 `"A"`만 처리하고 `"B"`, `"C"`는 버려진다 |
| **버퍼보다 긴 줄** | 1024바이트를 넘는 줄이 오면 영원히 개행을 못 찾는다. 버퍼를 키우려면 재할당·복사가 필요하다 |
| **백프레셔가 없다** | 생산자(네트워크)가 소비자(파싱)보다 빠르면 버퍼가 무한히 커지거나 데이터가 유실된다 |

이걸 전부 고치면 코드는 100줄이 넘어가고, **버퍼 관리 로직과 프로토콜 로직이 뒤엉킨다.** 파이프라인의 존재 이유가 정확히 이것이다. **스트림과 소켓 데이터를 올바르게 파싱하는 일의 복잡도를 줄이는 것.**

### 파이프라인의 세 가지 설계 원칙

파이프라인은 처음부터 고성능·고확장성을 전제로 설계됐다.

- **내부 버퍼를 풀링한다.** 힙 할당을 피한다(69.3절의 `MemoryPool<T>`가 그대로 쓰인다).
- **API 수준에서 `Span<T>`와 `Memory<T>`를 전면 사용한다.** 내부 버퍼를 슬라이싱해서 넘겨주므로 **복사가 일어나지 않는다.**
- **비동기이며, 효율적인 방식으로 스레드 안전하다.** 읽기 쪽과 쓰기 쪽이 서로 다른 스레드에 있어도 된다.

```text
파이프라인의 구조

  생산자 스레드                                   소비자 스레드
  ┌──────────────┐                              ┌──────────────┐
  │ 소켓 / 파일   │                              │ 프로토콜 파서 │
  └──────┬───────┘                              └──────▲───────┘
         │ GetMemory(sizeHint)                         │ ReadAsync()
         │ Advance(n)                                  │ AdvanceTo(consumed, examined)
         ▼                                             │
  ┌─────────────────────────────────────────────────────────────┐
  │  Pipe — 풀링된 세그먼트의 연결 리스트                          │
  │                                                             │
  │  ┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐          │
  │  │ seg 0  │──▶│ seg 1  │──▶│ seg 2  │──▶│ seg 3  │          │
  │  └────────┘   └────────┘   └────────┘   └────────┘          │
  │       ▲                         ▲            ▲              │
  │    consumed                 examined      쓰기 위치          │
  │                                                             │
  │  쓰기 - 읽기 > PauseWriterThreshold → FlushAsync가 대기      │
  └─────────────────────────────────────────────────────────────┘
```

`Pipe`는 세그먼트의 연결 리스트다. 소비자에게 넘어가는 `ReadOnlySequence<byte>`는 **이 세그먼트들을 가리키는 뷰**이지 복사본이 아니다. 그래서 "제로 카피"다.

### 최소 예제 — 그리고 왜 이게 안티패턴인가

먼저 파이프를 만든다.

```csharp
using System.Buffers;
using System.IO.Pipelines;

var pool = MemoryPool<byte>.Shared;
var options = new PipeOptions(pool);
var pipe = new Pipe(options);
```

`Pipe`는 `Writer`와 `Reader` 두 속성을 노출한다. 가장 단순한 사용은 이렇다.

```csharp
static async Task AsynchronousBasicUsage(Pipe pipe)
{
    // 쓰기
    pipe.Writer.Write(new byte[] { 1, 2, 3 }.AsSpan());
    await pipe.Writer.FlushAsync();

    // 읽기
    ReadResult result = await pipe.Reader.ReadAsync();
    byte[] data = result.Buffer.ToArray();
    pipe.Reader.AdvanceTo(result.Buffer.End);

    Console.WriteLine(string.Join(",", data));   // 1,2,3
}
```

두 가지 규칙이 여기서 드러난다.

- **쓰는 쪽은 `FlushAsync`를 명시적으로 호출해야 한다.** 그래야 데이터가 읽는 쪽에 보인다.
- **읽는 쪽은 `AdvanceTo`로 읽기 위치를 명시적으로 갱신해야 한다.** 그래야 파이프가 "이 버퍼는 이제 필요 없다"는 것을 알고 세그먼트를 풀에 돌려준다.

그런데 이 코드는 **입문용으로만 쓸모 있고 실전에서는 안티패턴이다.**

- 쓰는 쪽이 데이터를 보내기 전에 `byte[]`를 힙에 할당했다.
- 읽는 쪽이 `ToArray()`로 힙에 배열을 할당하고 데이터를 복사했다.

파이프라인을 쓰는 이유가 정확히 이 둘을 없애는 것인데, 둘 다 하고 있다.

> **⚠️ `result.Buffer.ToArray()`가 보이면 파이프라인을 쓰는 의미가 없다**
>
> 초보자가 파이프라인 코드를 쓸 때 가장 흔히 하는 일이 `ToArray()`다. 그 순간 풀링도, 제로 카피도 전부 사라진다. `Stream`을 쓰는 것보다 오히려 느려질 수 있다 — 파이프의 관리 오버헤드는 그대로 내면서 이득은 하나도 못 가져가기 때문이다.
>
> `ToArray()`는 **디버깅용**이거나, 시퀀스가 짧고 어차피 배열이 필요한 경계에서만 쓴다.

### 쓰기 쪽 제로 카피 — `GetSpan` / `GetMemory`

할당을 없애려면 파이프에서 **버퍼를 얻어와서** 거기에 직접 쓴다.

```csharp
static void SynchronousGetSpanUsage(Pipe pipe)
{
    Span<byte> span = pipe.Writer.GetSpan(2);
    span[0] = 1;
    span[1] = 2;
    pipe.Writer.Advance(2);
    pipe.Writer.FlushAsync().GetAwaiter().GetResult();

    var readResult = pipe.Reader.ReadAsync().GetAwaiter().GetResult();
    byte[] data = readResult.Buffer.ToArray();
    pipe.Reader.AdvanceTo(readResult.Buffer.End);
    pipe.Reader.Complete();
}
```

`GetSpan(sizeHint)`은 내부 버퍼의 슬라이스를 반환한다. 할당이 없다. 데이터를 쓴 뒤에는 **`Advance(실제로 쓴 바이트 수)`** 로 쓰기 위치를 갱신한다.

문제는 `Span<T>`가 `async` 메서드 안에서 살아남을 수 없다는 것이다(68.1절). 그래서 위 코드는 `GetAwaiter().GetResult()`로 동기 대기를 한다. **이건 하면 안 된다.**

> **⚠️ sync-over-async는 확장성을 죽인다**
>
> `.GetAwaiter().GetResult()`나 `.Result`로 비동기 작업을 동기 대기하면 스레드 풀 스레드가 블로킹된다. 파이프라인을 쓰고 있다는 것은 확장성에 신경 쓰고 있다는 뜻인데, 그 자리에서 확장성을 버리는 셈이다. 서버 코드에서는 스레드 풀 고갈로 이어진다.
>
> 해법은 **`Span<T>`를 만지는 부분만 동기 지역 함수로 분리하는 것**이다.

```csharp
static async Task AsynchronousGetSpanUsage(Pipe pipe)
{
    // Span을 쓰는 부분만 동기 지역 함수로 격리한다
    static void WriteData(PipeWriter writer)
    {
        Span<byte> span = writer.GetSpan(2);
        span[0] = 1;
        span[1] = 2;
        writer.Advance(2);
    }

    WriteData(pipe.Writer);
    await pipe.Writer.FlushAsync();

    ReadResult readResult = await pipe.Reader.ReadAsync();
    // ... 읽기 처리
    pipe.Reader.AdvanceTo(readResult.Buffer.End);
    pipe.Reader.Complete();
}
```

`Memory<byte>`를 반환하는 `GetMemory`는 `async` 메서드 안에서도 쓸 수 있다. 대신 `Span`보다 접근이 한 단계 더 든다.

### `Advance`에 거짓말하면 쓰레기가 읽힌다

`GetSpan`/`GetMemory`가 돌려주는 블록에는 **최소 크기**가 있다. 2바이트를 요청해도 훨씬 큰 메모리가 돌아온다. 풀에서 오는 것이므로 힙 할당은 없다.

```csharp
static async Task AsynchronousGetMemoryUsage(Pipe pipe)
{
    Memory<byte> memory = pipe.Writer.GetMemory(sizeHint: 2);
    memory.Span[0] = 1;
    memory.Span[1] = 2;
    Console.WriteLine(memory.Length);   // 4096 이 찍힌다
    pipe.Writer.Advance(4);             // ← 2바이트만 썼는데 4라고 했다
    await pipe.Writer.FlushAsync();

    Memory<byte> memory2 = pipe.Writer.GetMemory(2);
    memory2.Span[0] = 3;
    memory2.Span[1] = 4;
    pipe.Writer.Advance(4);             // ← 여기도
    await pipe.Writer.FlushAsync();

    ReadResult readResult = await pipe.Reader.ReadAsync();
    byte[] data = readResult.Buffer.ToArray();
    pipe.Reader.AdvanceTo(readResult.Buffer.End);
    // 1,2,0,0,3,4,0,0
}
```

`sizeHint: 2`로 요청했는데 `memory.Length`는 4096이다. 최소 세그먼트 크기의 기본값이다.

> **⚠️ 반환된 메모리는 0으로 초기화되어 있지 않다**
>
> 파이프가 돌려주는 블록은 **재사용되는 버퍼**다. 이전에 쓴 데이터가 그대로 남아 있을 수 있다. 위 예제에서 `0,0`이 나온 것은 우연히 그 자리가 0이었기 때문이지 보장이 아니다.
>
> 그래서 **`Advance`에는 반드시 실제로 쓴 바이트 수를 정확히 넘겨야 한다.** 크게 넘기면 이전 요청의 잔여 데이터가 프로토콜 스트림에 섞여 나간다. 네트워크 코드에서 이건 단순한 버그가 아니라 **정보 유출**이 될 수 있다.

### 읽기 쪽 제로 카피 — `ReadOnlySequence<byte>`

읽기 쪽의 `readResult.Buffer`는 `ReadOnlySequence<byte>` 타입이다. 이름 그대로 **바이트의 시퀀스**이고, 하나 이상의 세그먼트로 이루어진다.

| 멤버 | 의미 |
|---|---|
| `Length` | 전체 바이트 수 |
| `IsSingleSegment` | 세그먼트가 하나뿐인가 |
| `First` | 첫 세그먼트를 `ReadOnlyMemory<byte>`로 |
| `FirstSpan` | 첫 세그먼트를 `ReadOnlySpan<byte>`로 |
| `Start` / `End` | 시작/끝 `SequencePosition` |
| `Slice(...)` | 부분 시퀀스 (복사 없음) |
| `GetPosition(offset, origin)` | 상대 위치 계산 |
| `PositionOf(value)` | 특정 바이트의 위치 검색 |
| `foreach` | `ReadOnlyMemory<byte>` 세그먼트 열거 |

세그먼트가 여럿인 이유는 **네트워크에서 데이터가 조각으로 오기 때문**이다. `"GET /index.html HTTP/1.1\r\n"` 한 줄이 세 개의 세그먼트에 걸쳐 있을 수 있다. `ReadOnlySequence<byte>`는 그 조각들을 **복사해서 붙이지 않고** 논리적으로 하나로 보여준다.

전형적인 소비 패턴은 이렇다.

```csharp
static async Task Process(Pipe pipe)
{
    PipeReader reader = pipe.Reader;
    ReadResult readResult = await reader.ReadAsync();
    ReadOnlySequence<byte> readBuffer = readResult.Buffer;

    ProcessBuffer(in readBuffer, out SequencePosition consumed,
                                 out SequencePosition examined);
    reader.AdvanceTo(consumed, examined);
}

private static void ProcessBuffer(
    in ReadOnlySequence<byte> sequence,
    out SequencePosition consumed,
    out SequencePosition examined)
{
    consumed = sequence.Start;
    examined = sequence.End;

    if (sequence.IsSingleSegment)
    {
        // 단일 스팬으로 처리하는 빠른 경로
        ReadOnlySpan<byte> span = sequence.First.Span;
        Consume(in span);
    }
    else
    {
        // 여러 세그먼트를 순회
        foreach (ReadOnlyMemory<byte> segment in sequence)
        {
            ReadOnlySpan<byte> span = segment.Span;
            Consume(in span);
        }
    }
}

// ReadOnlySpan은 readonly struct이므로 방어적 복사가 생기지 않는다
private static void Consume(in ReadOnlySpan<byte> span)
{
    // ...
}
```

이 코드에서는 **할당이 하나도 일어나지 않는다.** 읽은 데이터는 슬라이스된 `ReadOnlyMemory<byte>`와 `ReadOnlySpan<byte>` 구조체로 표현된다.

### `consumed`와 `examined` — 파이프라인의 핵심 개념

`AdvanceTo`는 인자를 두 개 받는 오버로드가 있고, 이것이 파이프라인 설계의 핵심이다.

| 위치 | 의미 | 다음 `ReadAsync`에서 |
|---|---|---|
| **`consumed`** | 여기까지는 **소비했다.** 다시 줄 필요 없다 | 반환되지 **않는다.** 버퍼가 풀에 반납될 수 있다 |
| **`examined`** | 여기까지는 **봤다.** 그런데 부족했다 | `consumed`부터 다시 반환된다. 새 데이터가 뒤에 붙어서 |

이게 왜 필요한가. `"Hel"`만 도착한 상황을 생각해 보자. 개행이 없으니 한 줄을 완성할 수 없다. 그렇다고 데이터를 버릴 수도 없다.

- `consumed = 시작` — 아직 아무것도 소비하지 못했다.
- `examined = 끝` — 3바이트를 전부 검사했지만 개행이 없었다.

파이프는 이제 안다. "이 소비자는 3바이트를 다 봤고 부족하다고 한다. **새 데이터가 올 때까지 `ReadAsync`를 완료시키지 않겠다.**" 이것이 `examined`의 존재 이유다.

> **⚠️ `examined`를 잘못 주면 무한 루프 또는 영구 정지가 된다**
>
> 두 가지 실수가 흔하다.
>
> - **`examined`를 버퍼 끝보다 앞에 준다** → 파이프는 "아직 안 본 데이터가 있다"고 판단해 `ReadAsync`를 즉시 완료시킨다. 같은 데이터가 계속 돌아오면서 **CPU를 태우는 무한 루프**가 된다.
> - **`consumed`만 주는 단일 인자 오버로드를 쓴다** → `AdvanceTo(consumed)`는 `examined = consumed`와 같다. 부분 메시지를 처리할 때 이걸 쓰면 파이프가 "아직 안 본 데이터가 있다"고 보고 즉시 깨운다. 역시 무한 루프다.
>
> 규칙은 단순하다. **다음 `ReadAsync`에서 새 데이터를 기다리고 싶다면 `examined`는 반드시 `buffer.End`여야 한다.**

### 완전한 프로토콜 파서 — 길이 접두사 프레이밍

이제 실제로 동작하는 것을 만들자. 텍스트 줄 단위 프로토콜은 예제로는 흔하지만 실무에서는 **길이 접두사(length-prefixed) 프레이밍**이 더 흔하다. 형식은 이렇다.

```text
프레임 레이아웃

  ┌─────────────┬──────────┬────────────────────────────┐
  │ 길이 (4B)   │ 타입(1B) │ 페이로드 (길이만큼)          │
  │ big-endian  │          │                            │
  └─────────────┴──────────┴────────────────────────────┘
   ← 헤더 5바이트 →
```

파서는 이런 상황을 전부 견뎌야 한다.

- 헤더 5바이트가 다 안 왔다.
- 헤더는 왔지만 페이로드가 일부만 왔다.
- 한 번의 읽기에 프레임이 세 개 들어 있고 네 번째가 반쯤 걸쳐 있다.
- 프레임이 세그먼트 경계를 넘어간다.

먼저 프레임을 표현할 타입과 파싱 결과 열거형을 정의한다.

```csharp
using System.Buffers;
using System.Buffers.Binary;
using System.IO.Pipelines;
using System.Net;
using System.Net.Sockets;
using System.Text;

public readonly struct Frame
{
    public byte Type { get; }
    public ReadOnlySequence<byte> Payload { get; }

    public Frame(byte type, ReadOnlySequence<byte> payload)
    {
        Type = type;
        Payload = payload;
    }
}
```

핵심은 **`Payload`가 `byte[]`가 아니라 `ReadOnlySequence<byte>`** 라는 점이다. 복사하지 않는다. 대신 이 값은 `AdvanceTo` 호출 이후에는 무효가 된다 — 파서를 쓰는 쪽이 지켜야 할 계약이다.

파싱 함수는 `SequenceReader<byte>`를 쓴다. 이건 `ReadOnlySequence<T>` 위를 순회하며 세그먼트 경계를 알아서 처리해 주는 `ref struct`다.

```csharp
public static class FrameParser
{
    public const int HeaderSize = 5;      // 길이 4 + 타입 1
    public const int MaxPayloadSize = 1024 * 1024;   // 1MB 상한

    /// <summary>
    /// 버퍼에서 프레임 하나를 떼어낸다.
    /// 성공하면 buffer가 프레임 뒤로 전진한다.
    /// </summary>
    public static bool TryParseFrame(ref ReadOnlySequence<byte> buffer,
                                     out Frame frame)
    {
        frame = default;

        var reader = new SequenceReader<byte>(buffer);

        // 헤더가 다 왔는가
        if (reader.Remaining < HeaderSize)
            return false;

        // 길이 4바이트(big-endian)를 읽는다.
        // TryReadBigEndian은 세그먼트 경계를 알아서 넘어간다.
        if (!reader.TryReadBigEndian(out int payloadLength))
            return false;

        if (payloadLength < 0 || payloadLength > MaxPayloadSize)
            throw new InvalidDataException(
                $"프레임 길이가 범위를 벗어났다: {payloadLength}");

        if (!reader.TryRead(out byte type))
            return false;

        // 페이로드가 다 왔는가
        if (reader.Remaining < payloadLength)
            return false;

        // 여기서부터 페이로드. 복사 없이 슬라이스만 한다.
        ReadOnlySequence<byte> payload =
            buffer.Slice(reader.Position, payloadLength);

        frame = new Frame(type, payload);

        // 버퍼를 프레임 뒤로 전진시킨다
        buffer = buffer.Slice(buffer.GetPosition(payloadLength, reader.Position));
        return true;
    }
}
```

`SequenceReader<byte>.TryReadBigEndian`이 하는 일을 직접 쓰면 이렇게 된다.

```csharp
// SequenceReader가 없다면 이런 코드를 직접 써야 한다
static bool TryReadInt32BigEndian(ref ReadOnlySequence<byte> buffer, out int value)
{
    if (buffer.Length < 4) { value = 0; return false; }

    ReadOnlySequence<byte> slice = buffer.Slice(0, 4);
    if (slice.IsSingleSegment)
    {
        // 빠른 경로 — 한 세그먼트 안에 들어 있다
        value = BinaryPrimitives.ReadInt32BigEndian(slice.FirstSpan);
    }
    else
    {
        // 느린 경로 — 세그먼트를 넘어간다. 스택에 모은다.
        Span<byte> tmp = stackalloc byte[4];
        slice.CopyTo(tmp);
        value = BinaryPrimitives.ReadInt32BigEndian(tmp);
    }
    return true;
}
```

이 "빠른 경로 / 느린 경로" 분기가 `SequenceReader<T>`의 모든 `TryRead*` 안에 들어 있다. 직접 쓰지 마라.

이제 읽기 루프다.

```csharp
public static async Task ProcessFramesAsync(PipeReader reader,
                                            CancellationToken ct = default)
{
    while (true)
    {
        ReadResult result = await reader.ReadAsync(ct);
        ReadOnlySequence<byte> buffer = result.Buffer;

        try
        {
            // 버퍼에서 뽑을 수 있는 프레임을 전부 뽑는다
            while (FrameParser.TryParseFrame(ref buffer, out Frame frame))
            {
                HandleFrame(in frame);
            }
        }
        catch (InvalidDataException)
        {
            // 프로토콜 위반. 연결을 끊는다.
            await reader.CompleteAsync();
            throw;
        }

        // buffer는 TryParseFrame이 전진시켜 놓았다.
        //   consumed = buffer.Start  → 뽑아낸 프레임까지는 소비했다
        //   examined = buffer.End    → 남은 조각은 전부 검사했고 부족했다
        reader.AdvanceTo(buffer.Start, buffer.End);

        if (result.IsCompleted)
        {
            if (buffer.Length > 0)
                throw new InvalidDataException("불완전한 프레임으로 스트림이 끝났다");
            break;
        }
    }

    await reader.CompleteAsync();
}

static void HandleFrame(in Frame frame)
{
    // 페이로드를 문자열로 볼 때도 복사를 최소화한다
    string text = frame.Payload.IsSingleSegment
        ? Encoding.UTF8.GetString(frame.Payload.FirstSpan)
        : DecodeMultiSegment(frame.Payload);

    Console.WriteLine($"[type={frame.Type}] {text}");
}

static string DecodeMultiSegment(in ReadOnlySequence<byte> payload)
{
    // 여러 세그먼트에 걸친 경우에만 임시 버퍼를 빌린다
    int len = checked((int)payload.Length);
    byte[] rented = ArrayPool<byte>.Shared.Rent(len);
    try
    {
        payload.CopyTo(rented);
        return Encoding.UTF8.GetString(rented, 0, len);
    }
    finally
    {
        ArrayPool<byte>.Shared.Return(rented);
    }
}
```

`AdvanceTo(buffer.Start, buffer.End)`가 이 루프의 심장이다. `TryParseFrame`이 `buffer`를 전진시켰으므로 `buffer.Start`는 "다 뽑아낸 지점"이고, `buffer.End`는 "남은 조각의 끝"이다. 정확히 앞에서 정의한 `consumed`/`examined`의 의미다.

이제 소켓에 붙이면 완성이다.

```csharp
public static async Task RunServerAsync(int port, CancellationToken ct = default)
{
    using var listenSocket = new Socket(SocketType.Stream, ProtocolType.Tcp);
    listenSocket.Bind(new IPEndPoint(IPAddress.Loopback, port));
    listenSocket.Listen(120);
    Console.WriteLine($"포트 {port}에서 대기 중");

    while (!ct.IsCancellationRequested)
    {
        Socket socket = await listenSocket.AcceptAsync(ct);
        _ = HandleConnectionAsync(socket, ct);   // 의도적 fire-and-forget
    }
}

static async Task HandleConnectionAsync(Socket socket, CancellationToken ct)
{
    Console.WriteLine($"[{socket.RemoteEndPoint}] 연결됨");
    try
    {
        await using var stream = new NetworkStream(socket, ownsSocket: true);

        PipeReader reader = PipeReader.Create(stream, new StreamPipeReaderOptions(
            pool: MemoryPool<byte>.Shared,
            bufferSize: 8192,
            minimumReadSize: 1024,
            leaveOpen: false));

        await ProcessFramesAsync(reader, ct);
    }
    catch (Exception ex) when (ex is IOException or InvalidDataException or SocketException)
    {
        Console.WriteLine($"[{socket.RemoteEndPoint}] 오류: {ex.Message}");
    }
    finally
    {
        Console.WriteLine("연결 종료");
    }
}
```

클라이언트 쪽 쓰기도 `PipeWriter`로 대칭적으로 만들 수 있다.

```csharp
public static async ValueTask WriteFrameAsync(PipeWriter writer,
                                              byte type,
                                              ReadOnlyMemory<byte> payload,
                                              CancellationToken ct = default)
{
    // 헤더를 파이프 내부 버퍼에 직접 쓴다 — 할당 없음
    WriteHeader(writer, type, payload.Length);
    // 페이로드는 PipeWriter가 알아서 복사/청크 처리한다
    writer.Write(payload.Span);

    FlushResult flush = await writer.FlushAsync(ct);
    if (flush.IsCompleted)
        throw new IOException("상대가 읽기를 중단했다");

    static void WriteHeader(PipeWriter writer, byte type, int length)
    {
        Span<byte> header = writer.GetSpan(FrameParser.HeaderSize);
        BinaryPrimitives.WriteInt32BigEndian(header, length);
        header[4] = type;
        writer.Advance(FrameParser.HeaderSize);
    }
}
```

`WriteHeader`가 다시 **지역 정적 함수**인 것에 주목하라. `Span<byte>`를 `async` 메서드 본문에 둘 수 없기 때문이다. 이 패턴이 파이프라인 코드 전체에 반복된다.

> **📌 Kestrel의 HTTP 파서가 정확히 이 패턴이다**
>
> ASP.NET Core의 Kestrel 서버 안에 있는 `HttpParser.ParseRequestLine`은 위 `TryParseFrame`과 구조가 같다. `consumed`/`examined`를 `out`으로 돌려주고, 첫 세그먼트에서 `\n`을 찾고, 못 찾으면 `IsSingleSegment`인지 확인하고, 여러 세그먼트라면 `PositionOf`로 다시 찾는다. 찾지 못하면 `false`를 반환해 "새 데이터를 더 달라"고 말한다.
>
> 요청 줄을 찾으면 `examined = consumed`로 설정한다. 다음 파싱(헤더)을 위해 그 뒤부터 다시 보겠다는 뜻이다.

### 백프레셔 — 생산자를 멈추는 법

파이프라인이 `Stream`보다 나은 가장 실용적인 점이 **백프레셔(backpressure)** 다. 소비자가 느리면 생산자를 자동으로 멈춘다.

```csharp
var options = new PipeOptions(
    pool: MemoryPool<byte>.Shared,
    readerScheduler: PipeScheduler.ThreadPool,
    writerScheduler: PipeScheduler.ThreadPool,
    pauseWriterThreshold: 1024 * 1024,      // 1MB 쌓이면 쓰기를 멈춘다
    resumeWriterThreshold: 512 * 1024,      // 512KB로 줄면 재개
    minimumSegmentSize: 4096,
    useSynchronizationContext: false);

var pipe = new Pipe(options);
```

동작은 이렇다.

```text
백프레셔 상태 전이

  버퍼에 쌓인 바이트
       ▲
   1MB ├─────────────────  PauseWriterThreshold
       │        ╱╲              → FlushAsync()가 완료되지 않고 대기한다
       │      ╱    ╲               (생산자 스레드가 자연히 느려진다)
 512KB ├────╱────────╲───  ResumeWriterThreshold
       │  ╱            ╲        → 대기 중이던 FlushAsync()가 완료된다
     0 └╱────────────────╲──▶ 시간
```

`PauseWriterThreshold`를 넘으면 **`FlushAsync()`가 반환하는 `ValueTask<FlushResult>`가 완료되지 않는다.** 생산자가 `await`하고 있으므로 자연스럽게 멈춘다. 소비자가 `AdvanceTo`로 데이터를 소비해서 `ResumeWriterThreshold` 아래로 내려가면 그 `ValueTask`가 완료된다.

기본값은 `PipeOptions.Default` 기준으로 일시 정지 임계값 64KB, 재개 임계값 32KB, 최소 세그먼트 크기 4096바이트다.

| 옵션 | 기본값 | 언제 바꾸는가 |
|---|---|---|
| `pauseWriterThreshold` | 65536 | 메시지 하나가 64KB를 넘길 수 있다면 키운다 |
| `resumeWriterThreshold` | 32768 | 보통 pause의 절반 |
| `minimumSegmentSize` | 4096 | 메시지가 아주 작고 개수가 많으면 줄인다 |
| `readerScheduler` | `PipeScheduler.ThreadPool` | 인라인 실행(`PipeScheduler.Inline`)은 스택 오버플로/데드락 위험이 있다 |
| `useSynchronizationContext` | `true` | 서버 코드에서는 **`false`로 두는 것이 낫다** |

> **⚠️ `pauseWriterThreshold`를 0으로 두면 백프레셔가 사라진다**
>
> `0`은 "제한 없음"이다. 소비자가 느려도 파이프가 무한히 커진다. 악의적 클라이언트가 데이터를 밀어넣으면 OOM이다. **네트워크에서 오는 데이터를 받는 파이프에는 반드시 유한한 임계값을 둔다.**
>
> 그리고 `pauseWriterThreshold`는 **메시지 하나보다 커야 한다.** 임계값이 64KB인데 메시지가 100KB라면, 메시지를 다 쓰기 전에 쓰기가 멈추고 소비자는 완성된 메시지가 없어서 소비하지 못하는 **교착 상태**에 빠진다.

> **💡 언제 파이프라인을 쓰고 언제 쓰지 않는가**
>
> 파이프라인은 **저수준 라이브러리 작성자**를 위한 도구다. 다음이 전부 참일 때만 값을 한다.
>
> - 프로토콜 프레이밍을 직접 다뤄야 한다 (커스텀 바이너리 프로토콜, 프록시, 파서).
> - 처리량이 초당 수천~수만 메시지 이상이다.
> - 할당이 실제 병목임을 67.5절의 `MemoryDiagnoser`로 확인했다.
>
> 그렇지 않다면 `Stream` + `StreamReader`가 낫다. 코드가 1/5이고 읽기 쉽다. 애플리케이션 계층(비즈니스 로직)에 `ReadOnlySequence<byte>`가 등장하기 시작하면 설계가 잘못된 것이다. 파이프라인은 **인프라 계층에 봉인**해야 한다.
>
> 프로듀서/컨슈머 구조 자체가 필요한 것이라면 `System.Threading.Channels`가 더 적합하다(51.1절). 파이프라인은 **바이트**를 위한 것이고, 채널은 **객체**를 위한 것이다.

## 72.2 소켓 · HTTP 성능과 커넥션 관리

### 네트워크 계층을 왜 알아야 하는가

동작하는 네트워크 소프트웨어를 짜는 데 네트워크 지식이 꼭 필요하지는 않다. 그러나 **성능을 개선하려면** 어느 계층에서 무슨 일이 일어나는지 알아야 한다. OSI 참조 모델의 7계층은 개념적인 것이고, 실무에서 실제로 쓰이는 것은 TCP/IP 4계층 모델이다.

| TCP/IP 계층 | OSI 대응 | .NET에서 만나는 것 |
|---|---|---|
| **응용(Application)** | 응용 + 표현 + 세션 | `HttpClient`, `SmtpClient`, gRPC, SignalR |
| **전송(Transport)** | 전송 | `Socket`, `TcpClient`, `UdpClient`, `NetworkStream` |
| **인터넷(Internet)** | 네트워크 | `IPAddress`, 라우팅, ICMP(`Ping`) |
| **네트워크 인터페이스** | 데이터 링크 + 물리 | `NetworkInterface`, MTU, NIC 속도 |

성능 문제는 이 중 어느 계층에서든 생긴다. 그리고 **가장 흔한 원인은 응용 계층의 커넥션 관리 실수**다.

### `HttpClient`를 매번 만들지 마라

이건 .NET에서 가장 유명한 성능 함정이다.

```csharp
// 절대 하면 안 되는 코드
public async Task<string> GetDataBadAsync(string url)
{
    using var client = new HttpClient();      // ← 매번 새로 만든다
    return await client.GetStringAsync(url);
}
```

`HttpClient`는 `IDisposable`이므로 `using`을 쓰는 것이 자연스러워 보인다. 그런데 `HttpClient`를 `Dispose`해도 **밑에 있는 TCP 소켓이 즉시 해제되지 않는다.** TCP 규격상 소켓은 닫힌 뒤 `TIME_WAIT` 상태로 일정 시간(플랫폼에 따라 다르지만 보통 수십 초) 남는다. 초당 수십 번 호출하면 사용 가능한 포트가 고갈된다.

증상은 이렇게 나타난다.

```text
System.Net.Sockets.SocketException (10048):
Only one usage of each socket address (protocol/network address/port)
is normally permitted.
```

또는 Linux에서는 연결이 조용히 느려지다가 타임아웃이 난다. `netstat -an | grep TIME_WAIT | wc -l`로 수천 개가 잡히면 확진이다.

> **⚠️ `HttpClient`를 정적 필드에 넣는 것만으로도 부족하다**
>
> "그럼 `static readonly HttpClient`로 두면 되겠네"가 다음 단계다. 소켓 고갈은 해결된다. 그런데 새 문제가 생긴다.
>
> **DNS 변경을 영원히 반영하지 않는다.** `HttpClient`가 연결을 계속 재사용하면 최초 해석된 IP 주소를 계속 쓴다. 서비스가 페일오버해서 DNS 레코드가 바뀌어도 클라이언트는 죽은 IP로 계속 붙는다. 클라우드 환경에서 이건 실제로 장애를 만든다.
>
> 해법은 `SocketsHttpHandler.PooledConnectionLifetime`이다.

```csharp
// 권장 — 커넥션 수명을 제한한 단일 HttpClient
static readonly HttpClient Client = new HttpClient(new SocketsHttpHandler
{
    // 커넥션을 2분마다 폐기하고 다시 맺는다 → DNS 갱신이 반영된다
    PooledConnectionLifetime = TimeSpan.FromMinutes(2),

    // 유휴 커넥션을 얼마나 유지할지
    PooledConnectionIdleTimeout = TimeSpan.FromMinutes(1),

    // 서버당 동시 커넥션 상한 (HTTP/1.1)
    MaxConnectionsPerServer = 20,

    // 연결 수립 타임아웃 (기본은 무한)
    ConnectTimeout = TimeSpan.FromSeconds(5),

    // 응답 압축 자동 해제
    AutomaticDecompression = System.Net.DecompressionMethods.All,
})
{
    Timeout = TimeSpan.FromSeconds(30),
};
```

ASP.NET Core에서는 `IHttpClientFactory`가 이 관리를 대신해 준다(43.7절). 팩터리는 핸들러를 풀링하고 기본적으로 2분마다 교체한다.

```csharp
builder.Services.AddHttpClient<InventoryClient>(c =>
{
    c.BaseAddress = new Uri("https://inventory.internal/");
    c.Timeout = TimeSpan.FromSeconds(10);
})
.ConfigurePrimaryHttpMessageHandler(() => new SocketsHttpHandler
{
    PooledConnectionLifetime = TimeSpan.FromMinutes(2),
    EnableMultipleHttp2Connections = true,
})
.SetHandlerLifetime(TimeSpan.FromMinutes(5));
```

> **⚠️ `IHttpClientFactory`를 쓰면서 `PooledConnectionLifetime`도 짧게 두면 이중으로 낭비다**
>
> 팩터리의 `SetHandlerLifetime`과 `PooledConnectionLifetime`은 목적이 겹친다. 둘 다 짧게 잡으면 커넥션이 계속 재수립되면서 TLS 핸드셰이크 비용만 늘어난다. **하나만 쓰는 것이 낫다** — 최근 지침은 `PooledConnectionLifetime`을 쓰고 핸들러 수명은 무한(`Timeout.InfiniteTimeSpan`)으로 두는 쪽이다.

### `SocketsHttpHandler` 설정 지도

| 속성 | 기본값 | 성능적 의미 |
|---|---|---|
| `PooledConnectionLifetime` | `Timeout.InfiniteTimeSpan` | DNS 갱신 반영 주기. 클라우드에서는 1~5분 |
| `PooledConnectionIdleTimeout` | 1분 | 유휴 커넥션 유지 시간. 트래픽이 간헐적이면 늘린다 |
| `MaxConnectionsPerServer` | `int.MaxValue` | HTTP/1.1에서 동시성 상한. 무제한이면 상대 서버를 죽일 수 있다 |
| `ConnectTimeout` | `Timeout.InfiniteTimeSpan` | **반드시 설정하라.** 기본이 무한이라 죽은 호스트에 영원히 매달린다 |
| `EnableMultipleHttp2Connections` | `false` | HTTP/2에서 스트림 상한에 도달하면 커넥션을 추가로 연다 |
| `AutomaticDecompression` | `None` | gzip/brotli 자동 해제. 켜면 CPU와 대역폭을 맞바꾼다 |
| `KeepAlivePingDelay` | `Timeout.InfiniteTimeSpan` | HTTP/2 유휴 커넥션이 중간 장비에 끊기는 것을 방지 |
| `ResponseDrainTimeout` | 2초 | 응답 본문을 다 읽지 않고 버릴 때 커넥션 재사용을 위한 배출 시간 |

> **💡 `ConnectTimeout`은 항상 설정하라**
>
> `HttpClient.Timeout`은 **요청 전체**에 걸리는 타임아웃이다. 연결 수립 단계에 별도 제한이 없다는 뜻이 아니라, 연결이 안 되는 호스트를 빨리 포기하고 다른 인스턴스로 재시도하고 싶을 때 구분이 필요하다는 뜻이다. `ConnectTimeout`을 짧게(2~5초), `Timeout`을 길게(30초) 두면 "연결은 빨리 포기하되 응답은 기다린다"는 정책이 표현된다.

### HTTP/1.1, HTTP/2, HTTP/3

| 항목 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 전송 | TCP | TCP | **QUIC (UDP)** |
| 동시 요청 | 커넥션당 1개(파이프라이닝은 사실상 사장) | **한 커넥션에 다중 스트림** | 다중 스트림 |
| 헤더 | 평문, 반복 전송 | HPACK 압축 | QPACK 압축 |
| HOL 블로킹 | 커넥션 수준 | **TCP 수준에 남아 있다** | **없다** |
| 커넥션 수립 | TCP + TLS | TCP + TLS | **QUIC 1-RTT / 0-RTT** |
| .NET 지원 | 전부 | .NET Core 3.0+ | .NET 7+ (플랫폼 조건 있음) |

HTTP/2의 **다중화(multiplexing)** 는 마이크로서비스 간 통신에서 특히 크다. 커넥션 하나에 요청 100개를 동시에 실을 수 있으므로 커넥션 풀 압박이 사라진다. gRPC가 HTTP/2 위에 지어진 이유이기도 하다.

```csharp
// 요청별로 버전을 지정한다
var request = new HttpRequestMessage(HttpMethod.Get, "https://api.example.com/v1/items")
{
    Version = HttpVersion.Version20,
    VersionPolicy = HttpVersionPolicy.RequestVersionOrHigher,
};
using HttpResponseMessage response = await Client.SendAsync(request);
Console.WriteLine($"협상된 버전: {response.Version}");

// 클라이언트 기본값으로 지정한다
static readonly HttpClient Http3Client = new(new SocketsHttpHandler())
{
    DefaultRequestVersion = HttpVersion.Version30,
    DefaultVersionPolicy = HttpVersionPolicy.RequestVersionOrLower,
};
```

> **⚠️ HTTP/2의 head-of-line 블로킹은 사라지지 않았다**
>
> HTTP/2는 **HTTP 수준**의 HOL 블로킹을 없앴지만, 밑에 TCP가 있는 한 **TCP 수준**의 HOL 블로킹은 남아 있다. 패킷 하나가 유실되면 그 커넥션의 **모든 스트림**이 재전송을 기다린다. 패킷 손실률이 높은 모바일 네트워크에서는 HTTP/2가 HTTP/1.1보다 느려지는 구간이 실제로 존재한다.
>
> HTTP/3이 QUIC(UDP 기반)로 간 이유가 정확히 이것이다. 스트림마다 독립적으로 재전송한다.

> **⚠️ HTTP/3은 켠다고 항상 쓰이지 않는다**
>
> `HttpVersionPolicy.RequestVersionOrLower`(기본값)를 쓰면 서버가 HTTP/3을 알려주지 않는 한 폴백한다. Linux에서는 `libmsquic`이 설치되어 있어야 하고, 중간 방화벽이 UDP 443을 막으면 아예 동작하지 않는다. `response.Version`을 로그로 남겨 **실제로 어떤 버전이 협상되었는지** 확인하지 않으면 켠 줄 알고 안 켜진 채로 운영하게 된다.

### gRPC — 텍스트 대신 이진 계약

gRPC는 오픈 소스 RPC 프레임워크로, 전송에 HTTP/2를, 메시지 직렬화에 **프로토콜 버퍼(Protobuf)** 를 쓴다. Protobuf는 언어 중립적 계약 언어이기도 하다.

```protobuf
syntax = "proto3";
option csharp_namespace = "Inventory.Grpc";
package inventory;

service Inventory {
  rpc GetItem (ItemRequest) returns (ItemReply);
  rpc StreamItems (ItemRequest) returns (stream ItemReply);
}

message ItemRequest { string sku = 1; }
message ItemReply   { string name = 1; int32 quantity = 2; }
```

`.proto` 파일에서 강타입 클라이언트와 메시지 클래스가 코드 생성된다. 생성물은 `obj\Debug\net8.0\Protos` 아래에 숨어 있다.

성능 차이는 실측으로 확인된다. Blazor 기본 템플릿의 데이터 페이지는 JSON 백엔드를 쓰는데, 이 JSON의 데이터 크기가 **627바이트**다. 같은 데이터를 gRPC로 바꾸면 **309바이트**가 된다. 절반 이하다. 전송할 바이트가 적으므로 왕복이 빨라지고, **스로틀링에 걸리기 전에 더 많은 요청을 보낼 수 있다.**

| 항목 | HTTP + JSON REST API | gRPC |
|---|---|---|
| 인코딩 | 텍스트(사람이 읽음) | 이진(기계가 읽음) |
| 계약 | 코드 우선 (Swagger를 나중에 생성) | **계약 우선** (`.proto`가 먼저) |
| 페이로드 크기 | 크다 | 작다 (예: 627B → 309B) |
| 디버깅 | 쉽다 (도구만 있으면 눈으로 읽힘) | 도구가 필요하다 |
| 저수준 제어 | 높다 (URL, 메서드, 라우팅 직접) | 낮다 (프레임워크가 숨김) |
| 개발자 접근성 | 가장 넓다 | 좁다 |
| 스트리밍 | SSE/WebSocket을 별도로 | **프로토콜에 내장** |

웹 브라우저는 gRPC의 HTTP/2 프레임에 직접 접근할 수 없다. 그래서 **gRPC-Web**이라는 래퍼가 있다. HTTP/1.1과 HTTP/2 양쪽과 호환되는 종단 간 파이프라인을 만들 수 있고, `HttpClient`의 HTTP/2 지원이 없는 .NET 플랫폼에서도 동작한다. 프로세스 간 통신(IPC)에서는 TCP 외에 명명된 파이프와 유닉스 도메인 소켓(UDS)도 쓸 수 있다.

```csharp
// gRPC-Web 클라이언트 (Blazor WebAssembly 등)
using var channel = GrpcChannel.ForAddress("https://localhost:7272/",
    new GrpcChannelOptions
    {
        HttpHandler = new GrpcWebHandler(new HttpClientHandler())
    });

var client = new Inventory.InventoryClient(channel);
ItemReply reply = await client.GetItemAsync(new ItemRequest { Sku = "A-1001" });
```

서버 쪽에서는 메시지 크기 상한을 잊지 말아야 한다.

```csharp
builder.Services.AddGrpc(options =>
{
    options.EnableDetailedErrors = true;
    options.MaxReceiveMessageSize = 2 * 1024 * 1024;   // 2 MB
    options.MaxSendMessageSize = 5 * 1024 * 1024;      // 5 MB
});
```

> **📌 gRPC는 트리밍과 궁합이 좋다**
>
> .NET 6부터 애플리케이션은 적극적인 트리밍으로 작아진다. gRPC는 **코드 생성 기반**이라 리플렉션 의존이 적어 트리밍이 잘 먹는다. 같은 이유로 Native AOT와도 궁합이 좋다. 반면 런타임에 타입을 뒤지는 직렬화기(리플렉션 기반 JSON)는 트리밍에 취약하다(55.7절, 72.7절).

### 전송 바이트 자체를 줄이기

프로토콜을 바꾸지 않아도 줄일 수 있는 것들이 있다.

- **압축.** 대부분의 웹 서버가 deflate/gzip 압축을 제공한다. IIS라면 Windows **동적 콘텐츠 압축** 기능을 켠다. 텍스트 응답에서는 거의 항상 이득이다.
- **미니피케이션.** HTML/CSS/JS에서 공백·주석·미사용 코드를 제거한다. webpack 같은 도구가 한다. 이미지는 포맷(JPEG/PNG/GIF)과 압축률을 콘텐츠에 맞춰 실험해서 고른다.
- **서버 측 필터링과 페이징.** 큰 데이터셋은 서버에서 걸러 필요한 부분집합만 보낸다. 그래도 크면 페이지로 나눠 요청될 때만 보낸다.
- **불필요한 리소스 제거.** 광고·분석·상태 모니터링 서비스는 그 자체로 네트워크 트래픽과 로드 시간을 늘린다.

> **💡 압축은 CPU와 대역폭의 교환이다**
>
> `AutomaticDecompression = DecompressionMethods.All`은 거의 항상 켤 만하다. 그러나 **서버 측 압축**은 다르다. 이미 압축된 콘텐츠(JPEG, ZIP, 이미 gzip된 것)를 다시 압축하면 CPU만 쓰고 크기는 줄지 않는다. 그리고 초저지연이 목표라면 압축 시간 자체가 지연 시간에 더해진다. 마이크로서비스 간 내부 통신처럼 대역폭이 넉넉하고 지연이 중요한 경로에서는 압축을 끄는 것이 나을 때가 있다.

| 삽입 | Dapper SP (1.841 ms) | EF Core SP (396.509 ms) | 약 215× |
| 스칼라 읽기 | Dapper 원시 (1.403 ms) | EF Core LINQ (396.509 ms) | 약 283× |
| 목록 읽기 | ADO.NET SP (1.078 ms) | Dapper 원시 (199.910 ms) | 약 185× |
| 수정 | ADO.NET SP (1.562 ms) | EF Core LINQ (5,304.279 ms) | 약 3,396× |
| 삭제 | ADO.NET SP (1.760 ms) | EF Core LINQ (386.716 ms) | 약 220× |

성능이 정말 중요하다면 **하이브리드 접근**이 답이다. 프레임워크 하나를 골라 모든 데이터 연산에 쓰는 대신, 연산마다 가장 빠른 것을 쓴다. 위 벤치마크대로라면 ADO.NET과 Dapper 두 개를 함께 쓰게 된다.

> **⚠️ 이 표를 당신의 환경에 그대로 옮기지 마라**
>
> 이 숫자들은 **노트북 한 대에서, 특정 스키마와 특정 쿼리로** 측정된 것이다. 다음이 달라지면 순위가 뒤집힐 수 있다.
>
> - SQL Server가 원격에 있으면 네트워크 왕복이 지배적이 되어 프레임워크 차이가 묻힌다.
> - EF Core 버전. `ExecuteUpdate`/`ExecuteDelete`(EF Core 7)를 쓰면 수정·삭제 숫자가 완전히 달라진다.
> - 워밍업. EF Core는 첫 쿼리에서 모델을 빌드하고 쿼리를 컴파일한다. 벤치마크가 이 비용을 어떻게 처리했는지가 결과를 크게 흔든다.
> - 반환 행 수. 필터 목록 벤치마크에서 Dapper가 199.910ms로 튄 것은 매핑 대상 행 수와 매핑 방식의 상호작용을 시사한다.
>
> **읽어야 할 교훈은 "숫자"가 아니라 "편차의 크기"다.** 같은 논리적 작업의 구현 방식이 200배 차이를 만들 수 있다는 것. 그러니 **당신의 워크로드로 직접 재라**(67장).

> **⚠️ 원천의 스칼라 표에는 의심스러운 값이 있다**
>
> `ReadScalarProductEF = 396.509 ms`는 `InsertProductEFSP`의 값과 **소수점까지 완전히 같다.** 서로 다른 벤치마크가 소수 셋째 자리까지 일치할 확률은 사실상 0이다. 원천 보고서를 옮기는 과정의 전사 오류로 보인다. 이 값 하나만 따로 인용하지 말 것.

### 왜 밀리초 차이가 중요한가

1~2ms 차이가 무슨 대수인가 싶다면 규모를 넣어 보면 된다. 2020년 기준 통계로, Google은 초당 40,000건 이상의 쿼리를 받는다. 하루로 환산하면 34억 5,600만 건이다. WhatsApp 비즈니스 앱 메시지는 하루 650억 건이 오간다. 하루는 86,400,000밀리초다.

위 벤치마크 머신(i5-6300U 노트북)에서 WhatsApp 규모의 메시지를 SQL Server에 넣는다면, 어떤 삽입 방식을 쓰느냐에 따라 **1,385.01157일에서 298,299.595일** 사이가 걸린다. Google 검색 결과를 조회한다면 **43.12일에서 7,996.4일** 사이다.

클라우드 비용으로 환산하면 더 직접적이다. West US 리전, 소비 계층, 메모리 128MB의 Azure Function이 데이터 연산을 수행한다고 하자.

| 실행 시간 | 월 65,000,000,000회 실행 시 요금 |
|---|---|
| 1.078 ms | US$13,133.54 |
| 396.509 ms | US$64,539.57 |

같은 논리적 작업인데 월 5만 달러 규모의 차이가 난다. 그리고 이건 **SQL Server 인스턴스 비용을 포함하지 않은 금액**이다. 클라우드에서는 코드가 빨리 끝날수록 싸고, 오래 걸릴수록 비싸다. 성능이 곧 비용이다.

> **📌 코드 튜닝에는 한계가 있다**
>
> 큰 데이터셋을 코드로 주무르는 것은 어느 지점까지만 통한다. 서버 컴퓨터가 일반 워크스테이션보다 프로세서·디스크·메모리를 훨씬 많이 갖는 이유가 그것이다. 성능 계획을 세울 때는 **실험하고 벤치마크하되, 물리적 인프라도 함께 고른다.**

## 72.4 EF Core 성능 함정 — N+1, 추적 오버헤드, 지연 로딩, 컴파일된 쿼리

72.3절의 숫자는 EF Core를 나쁘게 보이게 한다. 그러나 실무에서 EF Core를 버리는 것이 답인 경우는 드물다. 생산성 이득이 크기 때문이다. 문제는 **EF Core가 조용히 비싼 일을 하는 지점을 모르고 쓰는 것**이다. 그 지점들을 하나씩 본다.

### N+1 문제

가장 흔하고 가장 비싸다.

```csharp
// 재앙. 주문이 1,000건이면 쿼리가 1,001번 나간다.
List<Order> orders = await db.Orders
    .Where(o => o.OrderDate >= from)
    .ToListAsync();

foreach (Order order in orders)
{
    // 이 접근 하나하나가 별도의 SELECT다 (지연 로딩이 켜져 있다면)
    Console.WriteLine($"{order.Id}: {order.Customer.Name}");
}
```

쿼리 1번으로 주문을 가져오고, 주문마다 고객을 가져오는 쿼리가 N번 더 나간다. 그래서 **N+1**이다. 각 쿼리는 왕복 하나이므로, 데이터베이스가 원격이라면 1,000번의 네트워크 왕복이다.

해법은 `Include`로 미리 가져오는 것이다.

```csharp
List<Order> orders = await db.Orders
    .Include(o => o.Customer)               // JOIN으로 함께 가져온다
    .Where(o => o.OrderDate >= from)
    .ToListAsync();
```

> **⚠️ 지연 로딩(lazy loading)은 N+1을 자동으로 만드는 기계다**
>
> `UseLazyLoadingProxies()`를 켜고 탐색 속성을 `virtual`로 선언하면, 속성에 접근하는 순간 EF Core가 쿼리를 날린다. 코드는 깔끔해 보이는데 뒤에서 쿼리 폭탄이 터진다.
>
> 더 나쁜 것은, `foreach` 안에서 지연 로딩이 일어나면 **어떤 코드가 쿼리를 유발하는지 소스만 봐서는 알 수 없다**는 점이다. `order.Customer.Name`은 그냥 속성 접근처럼 생겼다.
>
> **지연 로딩은 기본적으로 끄고, 필요한 곳에서 명시적으로 `Include`하라.** EF Core는 지연 로딩이 기본으로 꺼져 있다 — 켜지 마라.

### 카티션 폭발과 `AsSplitQuery`

`Include`가 항상 답인 것도 아니다. 컬렉션 탐색을 여러 개 `Include`하면 JOIN 결과가 곱해진다.

```csharp
// 주문 1건에 항목 10개, 배송 5개 → 행이 50개 나온다
var orders = await db.Orders
    .Include(o => o.Items)
    .Include(o => o.Shipments)
    .ToListAsync();
```

주문 컬럼이 50번 중복되어 전송된다. 주문이 1,000건이면 50,000행이다. 이것이 **카티션 폭발(cartesian explosion)** 이다.

```csharp
// 쿼리를 나눠서 보낸다 — 왕복은 3번, 전송 바이트는 훨씬 적다
var orders = await db.Orders
    .Include(o => o.Items)
    .Include(o => o.Shipments)
    .AsSplitQuery()
    .ToListAsync();
```

```csharp
// 컨텍스트 전역 기본값으로 지정할 수도 있다
options.UseSqlServer(cs, o => o.UseQuerySplittingBehavior(
    QuerySplittingBehavior.SplitQuery));
```

| 방식 | 왕복 | 전송량 | 일관성 |
|---|---|---|---|
| `AsSingleQuery` (기본) | 1회 | 중복으로 폭증 가능 | 한 스냅숏 |
| `AsSplitQuery` | 컬렉션 수 + 1회 | 중복 없음 | **쿼리 사이에 데이터가 변할 수 있다** |

> **⚠️ `AsSplitQuery`는 일관성을 포기하는 대가로 성능을 얻는다**
>
> 분할 쿼리는 서로 다른 시점에 실행되는 여러 SQL이다. 그 사이에 다른 트랜잭션이 데이터를 바꾸면 **부분적으로 어긋난 객체 그래프**를 받게 된다. 정합성이 중요하다면 명시적 트랜잭션(스냅숏 격리 등)으로 감싸거나 단일 쿼리를 쓴다.

### 변경 추적 오버헤드

EF Core는 기본적으로 쿼리로 가져온 모든 엔터티의 **스냅숏을 뜨고, `SaveChanges` 시점에 원본과 비교**한다. 읽기만 하는 쿼리에서 이건 순수 낭비다.

```csharp
// 읽기 전용 쿼리 — 추적할 이유가 없다
List<ProductDto> products = await db.Products
    .AsNoTracking()
    .Where(p => p.CategoryId == categoryId)
    .Select(p => new ProductDto(p.Id, p.Name, p.Price))
    .ToListAsync();
```

효과는 두 가지다. **스냅숏 할당이 사라지고**, `DbContext`가 엔터티를 붙들고 있지 않으므로 **메모리가 빨리 회수된다**.

| 모드 | 스냅숏 | 아이덴티티 해석 | 용도 |
|---|---|---|---|
| 기본(추적) | 있음 | 있음 | 수정하고 저장할 엔터티 |
| `AsNoTracking()` | 없음 | **없음** (같은 행이 두 객체로) | 읽기 전용 |
| `AsNoTrackingWithIdentityResolution()` | 없음 | 있음 | 읽기 전용인데 참조 동일성이 필요할 때 |

컨텍스트 전체를 읽기 전용으로 두는 것도 가능하다.

```csharp
services.AddDbContext<ReadOnlyDbContext>(o =>
{
    o.UseSqlServer(cs);
    o.UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking);
});
```

> **⚠️ `AsNoTracking()`으로 가져온 엔터티를 수정해도 저장되지 않는다**
>
> 조용히 아무 일도 일어나지 않는다. 예외도 없다. `SaveChanges()`가 `0`을 반환할 뿐이다. 읽기용 컨텍스트와 쓰기용 컨텍스트를 나누는 CQRS 스타일 분리(72.10절)가 이 실수를 구조적으로 막아준다.

> **⚠️ `Select` 없이 `AsNoTracking()`만 붙이는 것은 절반만 한 것이다**
>
> 추적을 끄더라도 **엔터티 전체 컬럼**을 가져오면 전송량은 그대로다. 열 40개짜리 테이블에서 이름과 가격만 필요하다면 `Select`로 투영해야 SQL의 `SELECT` 목록 자체가 줄어든다. 투영 결과가 엔터티가 아니면 EF Core는 애초에 추적하지도 않는다.

### 클라이언트 평가 — 조용한 재앙

```csharp
// SQL로 번역할 수 없는 메서드
var results = await db.Products
    .Where(p => IsEligible(p))       // 사용자 정의 메서드
    .ToListAsync();
```

EF Core 3.0 이후로는 이런 `Where`가 **예외**를 던진다. 다행이다. 그런데 이런 형태는 통과한다.

```csharp
// 이건 통과한다. 그리고 테이블 전체를 메모리로 가져온다.
var results = (await db.Products.ToListAsync())
    .Where(p => IsEligible(p))
    .ToList();
```

`ToListAsync()`가 먼저 실행되어 **전체 테이블이 클라이언트로 온다.** 그다음에 LINQ to Objects가 필터링한다. 코드 한 줄 차이인데 결과는 재앙이다.

> **💡 `IQueryable`이 `IEnumerable`로 바뀌는 지점을 항상 의식하라**
>
> `ToList()`, `ToArray()`, `AsEnumerable()`, `foreach` — 이 순간부터는 SQL이 아니라 C# 메모리 연산이다. 코드 리뷰에서 이 경계를 눈으로 좇는 습관이 N+1보다 큰 사고를 막는다.
>
> 로깅을 켜서 실제 SQL을 보는 것이 확실하다. 개발 환경에서만.
>
> ```csharp
> options.LogTo(Console.WriteLine, LogLevel.Information)
>        .EnableSensitiveDataLogging();   // 프로덕션 금지 — 파라미터 값이 로그에 남는다
> ```

### 컴파일된 쿼리

EF Core는 LINQ 식 트리를 SQL로 번역하고, 그 결과를 내부 캐시에 담는다. 캐시 조회 자체도 공짜는 아니다 — 식 트리를 순회하며 캐시 키를 만들어야 한다. 초당 수천 번 실행되는 핫 쿼리에서는 이 비용이 보인다.

```csharp
// 정적 필드에 컴파일된 쿼리를 담아 둔다
private static readonly Func<AppDbContext, int, Task<Product?>> GetProductById =
    EF.CompileAsyncQuery((AppDbContext db, int id) =>
        db.Products.AsNoTracking().FirstOrDefault(p => p.Id == id));

public Task<Product?> FindAsync(int id) => GetProductById(_db, id);
```

컬렉션을 반환하는 형태는 이렇게 쓴다.

```csharp
private static readonly Func<AppDbContext, int, IAsyncEnumerable<Product>> ByCategory =
    EF.CompileAsyncQuery((AppDbContext db, int categoryId) =>
        db.Products.AsNoTracking().Where(p => p.CategoryId == categoryId));

await foreach (Product p in ByCategory(_db, 7))
{
    // ...
}
```

> **⚠️ 컴파일된 쿼리는 형태를 바꿀 수 없다**
>
> 컴파일된 쿼리는 **하나의 고정된 식 트리**다. 조건을 동적으로 붙이는 검색 화면 같은 곳에는 못 쓴다. 파라미터만 달라지는 쿼리에만 쓴다.
>
> 그리고 이건 **마지막 몇 퍼센트를 짜내는 최적화**다. N+1 하나를 잡는 것이 컴파일된 쿼리 전부보다 크다. 순서를 지켜라.

### 대량 수정과 삭제

72.3절에서 `UpdateProductEF`가 5.3초, `DeleteProductEF`가 386ms였던 이유는 EF Core의 전통적인 방식이 **가져와서 → 바꾸고 → 저장**이기 때문이다. 행 1,000개를 지우려면 1,000개를 메모리로 가져와 추적하고 `DELETE` 1,000개를 보낸다.

EF Core 7부터는 이 왕복이 필요 없다.

```csharp
// 단일 UPDATE 문으로 나간다. 엔터티를 가져오지도, 추적하지도 않는다.
int updated = await db.Products
    .Where(p => p.CategoryId == oldCategory)
    .ExecuteUpdateAsync(s => s
        .SetProperty(p => p.CategoryId, newCategory)
        .SetProperty(p => p.UpdatedAt, DateTime.UtcNow));

// 단일 DELETE 문
int deleted = await db.Orders
    .Where(o => o.CreatedAt < cutoff && o.Status == OrderStatus.Abandoned)
    .ExecuteDeleteAsync();
```

> **⚠️ `ExecuteUpdate`/`ExecuteDelete`는 변경 추적기를 우회한다**
>
> 이 메서드들은 SQL을 직접 보내므로 **`DbContext`의 변경 추적기는 아무것도 모른다.** 같은 컨텍스트에 이미 로드된 엔터티가 있다면 그 객체는 낡은 값을 들고 있다. 그리고 **`SaveChanges`가 필요 없고, 저장 인터셉터·감사(audit) 로직·`SaveChanges` 오버라이드가 실행되지 않는다.**
>
> 감사 로그를 `SaveChanges` 오버라이드로 구현했다면, 대량 연산에서 감사 기록이 통째로 빠진다. 조용히.

### EF Core 성능 체크리스트

| 함정 | 증상 | 대응 |
|---|---|---|
| N+1 | 쿼리 수가 결과 행 수에 비례 | `Include` / 투영 |
| 지연 로딩 | 소스에 안 보이는 쿼리 | **끈다** |
| 카티션 폭발 | 반환 행 수 = 컬렉션 크기의 곱 | `AsSplitQuery` |
| 추적 오버헤드 | 읽기 전용 쿼리에서 GC 압력 | `AsNoTracking` |
| 전체 컬럼 조회 | 네트워크 전송량 과다 | `Select` 투영 |
| 클라이언트 평가 | 테이블 전체가 메모리로 | `IQueryable` 경계 확인 |
| 쿼리 번역 비용 | 핫 경로에서 CPU | `EF.CompileQuery` |
| 대량 수정/삭제 | 왕복 수천 회 | `ExecuteUpdate` / `ExecuteDelete` |
| 모델 빌드 지연 | 첫 요청이 느림 | 컴파일된 모델 (72.7절) |
| 컨텍스트 수명 과다 | 메모리 증가, 낡은 데이터 | 요청당 하나 |

> **💡 EF Core를 버릴 시점의 판단 기준**
>
> EF Core를 쓰지 말아야 할 곳은 **모양이 정해진 대량 연산**이다. ETL 배치, 리포트 집계, 벌크 임포트. 여기서는 Dapper나 ADO.NET, 또는 SQL Server의 `SqlBulkCopy`가 압도적이다.
>
> 반대로 도메인 로직이 있는 트랜잭션 처리 — 여러 엔터티를 로드하고 검증하고 함께 저장하는 — 에서는 EF Core의 변경 추적이 실제로 코드를 줄여준다. **애플리케이션 하나에 둘 다 쓰는 것이 정상이다**(81.7절).

## 72.5 캐싱 계층 — 메모리 캐시, 분산 캐시, 캐시 무효화

### 캐싱이 사는 이유

캐싱은 **자주 접근하는 리소스를 가까운 곳에 임시 저장**하는 것이다. 리소스를 다시 요청하면 원격 대신 로컬 저장분을 쓴다. 접근·로드 시간이 줄고, 네트워크 트래픽도 줄어 다른 사용자를 위한 대역폭이 남는다. 병목과 스로틀링을 예방한다.

캐시된 리소스는 세 경우에 갱신된다. 원본이 바뀌었을 때, 캐시 기간이 만료되었을 때, 사용자가 캐시를 비웠을 때다.

.NET에는 계층이 세 개 있다.

```text
캐시 계층

  요청
   │
   ▼
  ┌──────────────────────────────┐
  │ L1: 인프로세스 메모리 캐시     │  IMemoryCache
  │  · ns~us 접근                 │  · 프로세스 재시작 시 소멸
  │  · 직렬화 없음(객체 그대로)     │  · 인스턴스마다 별도
  └──────────┬───────────────────┘
             │ 미스
             ▼
  ┌──────────────────────────────┐
  │ L2: 분산 캐시                 │  IDistributedCache (Redis 등)
  │  · 네트워크 왕복 1회           │  · 인스턴스 간 공유
  │  · 직렬화 필요(byte[])         │  · 재시작을 견딤
  └──────────┬───────────────────┘
             │ 미스
             ▼
  ┌──────────────────────────────┐
  │ 원본: DB / 외부 API           │
  └──────────────────────────────┘
```

### 메모리 캐시

`Microsoft.Extensions.Caching.Memory` 패키지가 제공하는 `IMemoryCache`가 표준이다.

```csharp
builder.Services.AddControllersWithViews();
builder.Services.AddMemoryCache();
```

```csharp
public class HomeController : Controller
{
    private readonly ILogger<HomeController> _logger;
    private readonly IMemoryCache _memoryCache;

    public HomeController(ILogger<HomeController> logger, IMemoryCache memoryCache)
    {
        _logger = logger;
        _memoryCache = memoryCache;
    }

    private DateTime GetMemoryCacheTime()
    {
        if (!_memoryCache.TryGetValue("CachedTime", out DateTime currentTime))
        {
            currentTime = DateTime.UtcNow.ToLocalTime();
            var options = new MemoryCacheEntryOptions()
                .SetSlidingExpiration(TimeSpan.FromMinutes(5));
            _memoryCache.Set("CachedTime", currentTime, options);
        }
        return currentTime;
    }

    [HttpGet]
    public string Index()
    {
        DateTime cached = GetMemoryCacheTime();
        return $"현재: {DateTime.UtcNow.ToLocalTime()}\n캐시: {cached}";
    }
}
```

페이지를 새로 고치면 현재 시각은 계속 바뀌지만 캐시 시각은 유지된다. 만료되면 다시 같아진다.

만료 정책이 세 가지 있고, 의미가 다르다.

| 옵션 | 의미 | 위험 |
|---|---|---|
| `SetAbsoluteExpiration(TimeSpan)` | 생성 후 N 뒤에 무조건 만료 | 많은 항목이 동시에 만료되면 스탬피드 |
| `SetSlidingExpiration(TimeSpan)` | 마지막 접근 후 N 동안 미접근 시 만료 | **계속 접근되면 영원히 안 늙는다** |
| 둘 다 설정 | 슬라이딩하되 절대 상한이 있음 | 권장 조합 |

```csharp
var options = new MemoryCacheEntryOptions()
    .SetSlidingExpiration(TimeSpan.FromMinutes(5))       // 5분간 미접근 시 만료
    .SetAbsoluteExpiration(TimeSpan.FromHours(1))        // 그래도 1시간이면 무조건
    .SetPriority(CacheItemPriority.Normal)
    .SetSize(1);                                          // SizeLimit을 쓸 때 필수
```

> **⚠️ 슬라이딩 만료만 쓰면 데이터가 영원히 낡는다**
>
> 인기 있는 항목일수록 계속 접근되므로 절대 만료되지 않는다. 상품 가격을 슬라이딩 5분으로 캐시했는데 그 상품이 인기 상품이라면, **가격을 바꿔도 며칠째 옛날 값이 나갈 수 있다.** 슬라이딩에는 항상 절대 상한을 붙인다.

> **⚠️ `IMemoryCache`에 크기 제한을 걸지 않으면 그것은 메모리 누수다**
>
> 기본 `MemoryCache`는 **크기 제한이 없다.** 캐시 키를 사용자 입력에서 만드는 코드(`$"user:{userId}:search:{query}"` 같은)에 제한이 없으면 힙이 무한정 자란다. GC는 캐시가 붙들고 있는 객체를 회수할 수 없다.
>
> ```csharp
> builder.Services.AddMemoryCache(o =>
> {
>     o.SizeLimit = 10_000;              // 단위는 당신이 정한다
>     o.CompactionPercentage = 0.25;     // 넘치면 25% 축출
> });
> ```
>
> `SizeLimit`을 설정하면 **모든 항목이 `Size`를 지정해야 한다.** 하나라도 빠뜨리면 `InvalidOperationException`이 난다.

### 분산 캐시

분산 캐싱은 로컬 캐싱의 개념을 **여러 컴퓨터로 확장**한 것이다. 트랜잭션 데이터의 스케일링을 가능하게 한다. 주로 데이터베이스에 있는 애플리케이션 데이터와 웹 세션 관련 데이터를 저장하는 데 쓴다.

Redis가 표준 선택지다. 인메모리 데이터 구조 저장소로, 분산 인메모리 키-값 데이터베이스이자 캐시이자 메시지 브로커이며, 선택적 지속성을 제공한다.

```csharp
// 현재 권장 패키지
builder.Services.AddStackExchangeRedisCache(o =>
{
    o.Configuration = builder.Configuration.GetConnectionString("Redis");
    o.InstanceName = "inventory:";
});
```

```csharp
private readonly IDistributedCache _distributedCache;

public HomeController(ILogger<HomeController> logger,
                      IMemoryCache memoryCache,
                      IDistributedCache distributedCache)
{
    _logger = logger;
    _memoryCache = memoryCache;
    _distributedCache = distributedCache;
}

private async Task<string> GetDistributedCacheStringAsync()
{
    string? data = await _distributedCache.GetStringAsync("StringValue");
    if (data is null)
    {
        data = $"Hello, World! {DateTime.UtcNow.ToLocalTime()}";
        await _distributedCache.SetStringAsync("StringValue", data,
            new DistributedCacheEntryOptions
            {
                AbsoluteExpiration = DateTimeOffset.UtcNow.AddMinutes(10),
            });
    }
    return data;
}
```

> **⚠️ `Microsoft.Extensions.Caching.Redis`는 더 이상 쓰지 않는다**
>
> 오래된 예제에서 자주 보이는 `Microsoft.Extensions.Caching.Redis`(2.x)는 **폐기(deprecated)** 되었다. 후속은 `Microsoft.Extensions.Caching.StackExchangeRedis`이고 등록 메서드도 `AddStackExchangeRedisCache`다. 옛 패키지는 오래된 Redis 클라이언트를 물고 들어온다.

> **⚠️ `IDistributedCache`는 `byte[]`만 안다**
>
> 인터페이스는 `byte[]`와 `string`만 다룬다. 객체를 넣으려면 **직렬화해야 한다.** 그리고 이 직렬화 비용이 캐싱 이득을 잡아먹는 경우가 실제로 있다. 캐시 히트마다 JSON 역직렬화가 일어난다면, 원본이 로컬 DB일 때는 캐시가 오히려 느릴 수 있다.
>
> 그래서 실무에서는 L1(메모리) + L2(분산) 조합을 쓴다. L1 히트에서는 직렬화가 아예 없다.

### 캐시 스탬피드

캐시 항목 하나가 만료되는 순간, 그 키를 요청하던 **모든 동시 요청이 동시에 원본으로 몰린다.** 이것이 **캐시 스탬피드(cache stampede)** 또는 dogpile이다.

```text
스탬피드

  시각 t-1         t (만료)          t+1
  ────────────────┼─────────────────────────
  캐시 히트 1000/s │  캐시 미스 1000/s
                   │  → DB 쿼리 1000개 동시 발사
                   │  → DB가 죽는다
                   │  → 전부 같은 답을 계산해서 1000번 캐시에 쓴다
```

수동으로 막으려면 키별 잠금이 필요하다.

```csharp
private static readonly SemaphoreSlim Gate = new(1, 1);

private async Task<Product?> GetProductAsync(int id, CancellationToken ct)
{
    string key = $"product:{id}";
    if (_memoryCache.TryGetValue(key, out Product? cached))
        return cached;

    await Gate.WaitAsync(ct);
    try
    {
        // 이중 검사 — 대기하는 동안 다른 스레드가 채웠을 수 있다
        if (_memoryCache.TryGetValue(key, out cached))
            return cached;

        Product? loaded = await _db.Products.AsNoTracking()
            .FirstOrDefaultAsync(p => p.Id == id, ct);

        _memoryCache.Set(key, loaded, new MemoryCacheEntryOptions()
            .SetAbsoluteExpiration(TimeSpan.FromMinutes(5)));
        return loaded;
    }
    finally
    {
        Gate.Release();
    }
}
```

이 코드에는 결함이 있다. 세마포어가 **전역 하나**라서 서로 다른 상품 ID를 조회하는 요청까지 직렬화된다. 키별 세마포어 딕셔너리를 만들면 그건 그것대로 정리 문제가 생긴다.

### `HybridCache` ※.NET 9

.NET 9에서 이 문제들을 한꺼번에 정리한 것이 **`HybridCache`** 다. L1(인프로세스) + L2(분산)를 하나의 API로 묶고, **스탬피드 방지가 내장**되어 있다.

```csharp
// Microsoft.Extensions.Caching.Hybrid 패키지
builder.Services.AddStackExchangeRedisCache(o =>
    o.Configuration = builder.Configuration.GetConnectionString("Redis"));

builder.Services.AddHybridCache(options =>
{
    options.DefaultEntryOptions = new HybridCacheEntryOptions
    {
        Expiration = TimeSpan.FromMinutes(10),        // L2 만료
        LocalCacheExpiration = TimeSpan.FromMinutes(2) // L1 만료(더 짧게)
    };
    options.MaximumPayloadBytes = 1024 * 1024;        // 1MB 초과는 캐시하지 않음
    options.MaximumKeyLength = 512;
});
```

```csharp
public sealed class ProductService(HybridCache cache, AppDbContext db)
{
    public async ValueTask<Product?> GetAsync(int id, CancellationToken ct = default)
    {
        return await cache.GetOrCreateAsync(
            $"product:{id}",
            factory: async token => await db.Products
                .AsNoTracking()
                .FirstOrDefaultAsync(p => p.Id == id, token),
            tags: ["products", $"category:{id}"],
            cancellationToken: ct);
    }

    public async Task InvalidateCategoryAsync(int categoryId)
    {
        // 태그 단위 무효화 — 개별 키를 몰라도 된다
        await cache.RemoveByTagAsync($"category:{categoryId}");
    }
}
```

`GetOrCreateAsync`가 주는 것은 다음과 같다.

| 기능 | 직접 구현하면 |
|---|---|
| L1 → L2 → 팩터리 순서 조회 | 조건문 세 겹 |
| **동일 키 동시 요청 병합** | 키별 세마포어 + 정리 로직 |
| 직렬화기 선택 (기본 JSON, `IHybridCacheSerializer`로 교체) | 직접 |
| 태그 기반 무효화 | 별도 인덱스 유지 |
| L1/L2 만료 분리 | 두 API를 따로 호출 |

> **📌 L1 만료를 L2보다 짧게 두는 이유**
>
> L1은 인스턴스마다 따로 있다. 인스턴스 A가 L1에 10분짜리를 담고 있는데 인스턴스 B가 L2를 갱신하면, A는 10분 동안 낡은 값을 낸다. **L1을 짧게(수십 초~2분), L2를 길게(수 분~수 시간)** 두면 이 불일치 창이 L1 만료 시간으로 제한된다.

> **⚠️ 태그 무효화는 즉각적이지 않다**
>
> `RemoveByTagAsync`는 L2와 호출한 인스턴스의 L1에는 즉시 작용하지만, **다른 인스턴스의 L1은 각자의 만료를 기다린다.** "즉시 반영"이 필요하면 캐시가 아니라 pub/sub 기반 무효화 알림을 별도로 설계해야 한다.

### 무효화 전략

캐시 무효화는 컴퓨터 과학의 어려운 문제 두 개 중 하나로 불린다. 실무에서 쓰는 전략은 넷이다.

| 전략 | 방법 | 적합 |
|---|---|---|
| **TTL 만료** | 시간이 지나면 버린다 | 약간 낡아도 되는 데이터. 가장 단순하고 가장 흔하다 |
| **쓰기 시 무효화** | 데이터를 바꾸는 코드가 캐시 키를 지운다 | 쓰기 경로가 한 곳으로 모여 있을 때 |
| **쓰기 관통(write-through)** | 쓰면서 캐시도 같이 갱신 | 읽기가 쓰기보다 훨씬 많고 최신성이 중요할 때 |
| **버전 키** | 키에 버전을 넣고 버전을 올린다 (`product:42:v7`) | 무효화 대신 새 키를 쓴다. 옛 키는 TTL로 자연 소멸 |

> **💡 캐시하기 전에 두 가지를 먼저 물어라**
>
> 1. **이 데이터가 얼마나 낡아도 되는가.** "절대 낡으면 안 된다"면 캐시하지 마라. 그 답이 "1분"이면 TTL 1분이면 끝난다. 복잡한 무효화 로직의 절반은 이 질문을 안 해서 생긴다.
> 2. **원본이 정말 느린가.** 인덱스 하나로 20ms가 2ms가 되는 쿼리를 캐시로 덮으면, 캐시 계층의 복잡도와 정합성 위험을 영구히 떠안게 된다. **캐시는 최적화의 마지막 수단이지 첫 수단이 아니다.**

## 72.6 컬렉션 선택이 만드는 차이 — Big-O 너머의 상수

24.15절에서 컬렉션의 Big-O 표를 이미 봤다. 이 절은 **그 표가 말하지 않는 것**만 다룬다. 점근 복잡도가 같아도 실측이 열 배 차이 나는 이유들이다.

### 상수가 지수를 이기는 구간

`Dictionary<K,V>` 조회는 O(1)이고 배열 선형 탐색은 O(n)이다. 그런데 n이 작으면 배열이 이긴다.

```text
왜 작은 n에서 선형 탐색이 이기는가

  Dictionary 조회 1회:
    해시 계산 → 버킷 인덱스 계산(나눗셈) → 버킷 배열 접근(캐시 미스 가능)
    → 엔트리 배열 접근(캐시 미스 가능) → 키 비교 → 충돌 시 체인 순회

  배열 선형 탐색 n=8:
    캐시 라인 하나에 int 16개가 들어온다 → 메모리 접근 1회로 8개 전부 비교
    분기 예측이 잘 맞는 단순 루프
```

핵심은 **캐시 지역성**이다(61장, 70.1절). 배열 8개는 캐시 라인 하나에 들어오지만, `Dictionary`는 버킷 배열과 엔트리 배열 두 곳을 건드린다. 해시 계산 비용도 있다.

임계점은 키 타입과 하드웨어에 따라 다르므로 숫자를 외우지 말고 **재라**(67장). 다만 방향은 분명하다. **원소가 수십 개 이하이고 조회가 핫 경로가 아니라면, `Dictionary`로 바꾸는 것이 이득이 아닐 수 있다.**

### 문자열 키 비교자

`Dictionary<string, T>`의 기본 비교자는 문화권 인지 여부와 무관하게 서수 비교를 쓰지만, 해시 계산 방식에 차이가 있다. 명시적으로 지정하는 편이 예측 가능하다.

```csharp
// 서수 비교 — 가장 빠르다
var byOrdinal = new Dictionary<string, int>(StringComparer.Ordinal);

// 대소문자 무시 서수 — 여전히 빠르다
var byOrdinalIgnoreCase = new Dictionary<string, int>(StringComparer.OrdinalIgnoreCase);

// 문화권 인지 — 느리다. 정렬에는 필요하지만 키 조회에는 거의 필요 없다
var byCulture = new Dictionary<string, int>(StringComparer.CurrentCultureIgnoreCase);
```

> **⚠️ 사용자 입력이 키가 되는 딕셔너리는 해시 충돌 공격 표면이다**
>
> 공격자가 같은 버킷으로 해시되는 문자열 수천 개를 보내면 조회가 O(1)에서 O(n)으로 퇴화한다. .NET의 `string` 해시는 프로세스마다 무작위화된 시드를 쓰고, `Dictionary<string,V>`는 충돌이 임계값을 넘으면 무작위화 해시로 전환한다. 이 방어는 **기본 비교자를 쓸 때** 작동한다. 직접 만든 `IEqualityComparer<string>`으로 교체하면 그 방어를 스스로 꺼버릴 수 있다.

### 읽기 전용 조회 테이블은 frozen으로 ※.NET 8

한 번 만들고 그 뒤로는 읽기만 하는 딕셔너리라면 `FrozenDictionary`가 있다(24.11절). 생성이 느린 대신 **조회를 위해 자료구조를 분석해서 최적화**한다.

```csharp
using System.Collections.Frozen;

// 애플리케이션 시작 시 한 번
private static readonly FrozenDictionary<string, StatusCode> StatusMap =
    new Dictionary<string, StatusCode>(StringComparer.Ordinal)
    {
        ["ok"] = StatusCode.Ok,
        ["pending"] = StatusCode.Pending,
        ["failed"] = StatusCode.Failed,
    }.ToFrozenDictionary(StringComparer.Ordinal);
```

| 컬렉션 | 생성 비용 | 조회 비용 | 변경 |
|---|---|---|---|
| `Dictionary<K,V>` | 낮음 | 낮음 | 가능 |
| `FrozenDictionary<K,V>` | **높음** | **가장 낮음** | 불가 |
| `ImmutableDictionary<K,V>` | 중간 | 높음(트리 순회) | 새 인스턴스 반환 |
| `ReadOnlyDictionary<K,V>` | 낮음(래퍼) | `Dictionary`와 동일 + 간접 호출 | 불가(원본은 변할 수 있음) |

> **⚠️ 요청마다 `ToFrozenDictionary()`를 호출하면 정반대 효과다**
>
> frozen 컬렉션의 생성은 일반 `Dictionary` 생성보다 훨씬 비싸다. **정적 필드나 싱글턴에서 한 번 만드는 것**이 전제다. 메서드 안에서 만들면 최적화 분석 비용을 매번 내고 조회는 한두 번 하는, 최악의 조합이 된다.

### 인터페이스로 받으면 열거자가 박싱된다

`List<T>`, `Dictionary<K,V>`, `HashSet<T>`, `Queue<T>` 등의 `GetEnumerator()`는 **구조체 열거자**를 반환한다. `foreach`가 이걸 직접 쓰면 할당이 없다.

```csharp
static int SumFast(List<int> items)
{
    int sum = 0;
    foreach (int x in items) sum += x;   // List<int>.Enumerator (struct) — 할당 0
    return sum;
}

static int SumSlow(IEnumerable<int> items)
{
    int sum = 0;
    foreach (int x in items) sum += x;   // IEnumerator<int>로 박싱 — 할당 1
    return sum;
}
```

`IEnumerable<T>`로 받는 순간 구조체 열거자가 인터페이스로 박싱되고, `MoveNext`와 `Current`가 **인터페이스 가상 호출**이 된다. 인라이닝도 막힌다.

> **💡 API 설계와 성능의 타협점**
>
> 24.16절의 "인터페이스로 받을 것인가"는 설계 질문이었다. 성능 관점의 답은 이렇다.
>
> - **공개 API 경계**에서는 `IEnumerable<T>`/`IReadOnlyList<T>`를 받는다. 유연성이 크고, 이 경계는 대개 핫 경로가 아니다.
> - **내부 핫 경로**에서는 구체 타입(`List<T>`, `T[]`, `Span<T>`)을 받는다.
> - 둘을 잇는 곳에서 한 번 변환한다.
>
> 라이브러리 전체를 구체 타입으로 도배하는 것은 67장의 측정 없이는 정당화되지 않는다.

### 용량을 미리 잡아라

`List<T>`와 `Dictionary<K,V>`는 가득 차면 내부 배열을 **두 배로 키우고 전부 복사**한다(24.4절). 1,000개를 넣으면 재할당이 열 번쯤 일어나고, 중간 크기 배열들이 전부 쓰레기가 된다.

```csharp
// 나쁘다 — 재할당과 복사가 반복된다
var list = new List<Order>();
foreach (var row in rows) list.Add(Map(row));

// 낫다 — 한 번에 잡는다
var list = new List<Order>(rows.Count);
foreach (var row in rows) list.Add(Map(row));

// 이미 만들어진 리스트에 대량 추가할 때
list.EnsureCapacity(list.Count + additional.Count);
```

`Dictionary`도 마찬가지다. 생성자에 예상 개수를 준다.

```csharp
var index = new Dictionary<int, Order>(orders.Count);
```

> **⚠️ `List<T>`의 큰 내부 배열은 LOH로 간다**
>
> 내부 배열이 **85,000바이트**를 넘는 순간 **대형 객체 힙(LOH)** 으로 간다(62장). 64비트에서 참조 타입 원소라면 약 10,600개, `int`라면 약 21,200개가 그 경계다. LOH는 기본적으로 압축되지 않고 gen2와 함께 수집된다. 큰 리스트를 반복해서 만들고 버리는 코드는 LOH 단편화를 만든다.
>
> 대안은 `ArrayPool<T>`(69.3절)나, 애초에 리스트를 만들지 않고 스트리밍으로 처리하는 것이다.

### 딕셔너리 이중 조회 없애기

```csharp
using System.Runtime.InteropServices;

// 해시를 두 번 계산한다
if (counts.ContainsKey(key)) counts[key]++; else counts[key] = 1;

// 한 번 — 조회와 쓰기가 각각 한 번
counts.TryGetValue(key, out int c);
counts[key] = c + 1;

// .NET 6+ — 참조를 얻어 제자리에서 수정한다. 해시 계산 1회.
ref int slot = ref CollectionsMarshal.GetValueRefOrAddDefault(counts, key, out _);
slot++;
```

`ConcurrentDictionary`에서는 다른 함정이 있다.

```csharp
// factory 델리게이트가 state를 캡처하면 호출마다 클로저가 할당된다
cache.GetOrAdd(key, k => Load(k, tenantId));

// 상태를 인자로 넘기는 오버로드 — 클로저 없음
cache.GetOrAdd(key, static (k, state) => Load(k, state), tenantId);
```

### `List<T>`를 `Span<T>`으로 보기

```csharp
using System.Runtime.InteropServices;

Span<Order> span = CollectionsMarshal.AsSpan(orders);
for (int i = 0; i < span.Length; i++)
{
    // 경계 검사가 JIT에 의해 제거될 수 있다 (55.6절)
    span[i].Total = span[i].Quantity * span[i].UnitPrice;
}
```

> **⚠️ `CollectionsMarshal.AsSpan`으로 얻은 스팬은 리스트 변경으로 무효화된다**
>
> 스팬이 살아 있는 동안 `Add`, `Remove`, `Clear`를 호출하면 내부 배열이 교체되거나 크기가 바뀔 수 있다. 그러면 스팬은 **이미 버려진 배열**을 가리키게 된다. 컴파일러도 런타임도 막아주지 않는다. `Marshal`이라는 이름이 붙은 이유가 있다 — 안전 장치를 스스로 벗은 것이다.

### 실무 판단표

| 상황 | 선택 |
|---|---|
| 원소 수십 개, 키로 조회 | 배열/`List<T>` 선형 탐색을 먼저 재 보라 |
| 시작 후 불변인 조회 테이블 | `FrozenDictionary` / `FrozenSet` ※.NET 8 |
| 반복 생성·폐기되는 큰 버퍼 | `ArrayPool<T>` (69.3절) |
| 요소 수를 미리 안다 | 생성자에 용량 지정 |
| 값 타입 원소를 제자리 수정 | `CollectionsMarshal.AsSpan` |
| 스레드 간 공유 + 읽기 압도적 | `ImmutableArray<T>` 교체 or `FrozenDictionary` 재생성 |
| 스레드 간 공유 + 쓰기 많음 | `ConcurrentDictionary` (상태 전달 오버로드로) |
| 큐잉 + 백프레셔 | `Channel<T>` (51.1절), `BlockingCollection`이 아니다 |

## 72.7 시작 시간 최적화 — R2R, Native AOT, 트리밍

55.7절에서 R2R과 Native AOT가 **무엇을 어떻게 컴파일하는지**를 끝냈다. 이 절은 그 위에서 애플리케이션 운영자의 질문에 답한다. **내 앱의 시작 시간은 무엇으로 이루어져 있고, 어느 스위치가 그중 무엇을 줄이며, 대가는 무엇인가.**

### 시작 시간은 하나의 숫자가 아니다

"시작 시간"이라는 말이 가리키는 것이 사람마다 다르다. 최소 네 가지를 구분해야 한다.

| 구간 | 무슨 일이 일어나는가 | 줄이는 수단 |
|---|---|---|
| **프로세스 시작 → `Main` 진입** | 호스트가 런타임을 로드하고 어셈블리를 매핑하고 GC 힙을 초기화한다 | Native AOT, 자체 포함 단일 파일, 어셈블리 수 감소 |
| **`Main` → DI 컨테이너 구축 완료** | 서비스 등록, 구성 바인딩, 옵션 검증 | 등록 개수 줄이기, 지연 초기화 |
| **컨테이너 구축 → 첫 요청 수락** | 미들웨어 파이프라인 구성, 라우트 테이블 빌드, EF 모델 빌드, 로깅·원격 측정 초기화 | EF 컴파일된 모델, 원본 생성기 |
| **첫 요청 → 정상 처리량 도달** | Tier-0 코드가 도는 워밍업 구간. Tier-1 승격까지 | R2R, 워밍업 요청, `TieredPGO` 고려 |

앞의 세 구간을 "콜드 스타트", 마지막 구간을 "워밍업"이라고 부른다. **R2R은 주로 네 번째와 세 번째를, Native AOT는 첫 번째부터 전부를 공격한다.**

### 먼저 재라

```csharp
// Program.cs 맨 앞
using System.Diagnostics;

var processStart = Process.GetCurrentProcess().StartTime.ToUniversalTime();
var sw = Stopwatch.StartNew();

var builder = WebApplication.CreateBuilder(args);
// ... 서비스 등록
var app = builder.Build();
Console.WriteLine($"[startup] 빌드 완료 {sw.ElapsedMilliseconds} ms");

app.Lifetime.ApplicationStarted.Register(() =>
{
    var hostReady = DateTime.UtcNow;
    Console.WriteLine(
        $"[startup] 프로세스 시작~수락 준비 {(hostReady - processStart).TotalMilliseconds:F0} ms, " +
        $"Main 이후 {sw.ElapsedMilliseconds} ms");
});

app.Run();
```

두 숫자의 **차이**가 런타임 로드와 호스트 초기화 비용이다. 이 차이가 크면 Native AOT가 답이고, `Main` 이후가 크면 애플리케이션 초기화 코드가 문제다. 스위치를 켜기 전에 어느 쪽인지부터 알아야 한다.

JIT 활동은 카운터로 본다(73.9절).

```text
dotnet-counters monitor --process-id <PID> --counters System.Runtime
```

`methods-jitted-count`, `il-bytes-jitted`, `time-in-jit`을 보면 워밍업 구간에서 JIT이 얼마나 일하는지 보인다. R2R을 켰는데 `methods-jitted-count`가 그대로라면 R2R 이미지가 안 쓰이고 있는 것이다.

### 배포 형태별 실측 감각

같은 콘솔 앱을 여러 방식으로 게시했을 때의 산출물 크기다.

| 방식 | 실행 파일 | publish 폴더 전체 |
|---|---|---|
| 자체 포함 (win10-x64) | 154 KB | **68.3 MB** |
| 자체 포함 (osx.11.0-arm64) | 125 KB | 약 73.9 MB |
| 자체 포함 + `PublishSingleFile` | **62.6 MB** | 62.6 MB + pdb 11 KB |
| Native AOT (win-x64) | **약 1.2 MB** | 1.2 MB + pdb |

Native AOT 실행 파일이 자체 포함 단일 파일의 **50분의 1**이다. 트리밍이 걸리고 런타임과 JIT이 통째로 빠졌기 때문이다. 트리밍만으로도 상당히 줄어든다 — Hello World 콘솔 앱에서 `System.Console.dll` 하나가 61.5 KB에서 31.5 KB로 줄었다는 것이 .NET 5 시절의 사례다.

크기가 왜 시작 시간과 관련이 있는가. **로드해야 할 파일 수와 매핑해야 할 바이트가 줄기 때문**이다. 컨테이너에서는 여기에 **이미지 풀 시간**까지 더해진다. 오토스케일링으로 파드가 뜨는 시간에 이미지 크기가 직접 반영된다.

### 애플리케이션 유형별 선택

| 유형 | 시작 시간의 중요도 | 권장 |
|---|---|---|
| **장기 실행 웹 서비스** (하루에 몇 번 배포) | 낮음 | JIT + 계층형. R2R은 롤링 배포 중 지연 스파이크가 문제일 때만 |
| **자동 확장되는 웹 서비스** | 중간 | **R2R**. 새 인스턴스가 뜨자마자 정상 지연 시간을 내야 한다 |
| **서버리스 함수** | **매우 높음** | **Native AOT**(가능하면) 또는 R2R + 항상 대기 인스턴스 |
| **CLI 도구** | **매우 높음** | **Native AOT**. 사용자가 매번 프로세스를 띄운다 |
| **데스크톱 앱** | 높음(체감) | R2R. 시작 화면으로 체감을 가린다(72.9절) |
| **배치 작업 / ETL** | 낮음 | JIT. 처리량이 전부다. AOT는 오히려 손해 |

> **⚠️ Native AOT는 최고 처리량을 포기하는 것이다**
>
> Native AOT는 **동적 PGO와 가드된 역가상화(GDV)가 없다**(55.5절). Tier-1 JIT은 실행 중에 관찰한 실제 타입 분포로 가상 호출을 직접 호출로 바꾸고 인라이닝한다. AOT는 그 정보를 게시 시점에 가질 수 없다.
>
> 그래서 **오래 도는 처리량 중심 워크로드에서는 JIT이 AOT보다 빠르다.** "AOT가 무조건 빠르다"는 오해는 시작 시간과 정상 처리량을 섞어서 생긴다. 배치 처리를 AOT로 게시하고 느려졌다며 놀라는 일이 실제로 있다.

> **⚠️ EF Core와 컨트롤러 기반 ASP.NET Core는 AOT로 못 간다**
>
> .NET 8 기준으로 ASP.NET Core MVC(컨트롤러 기반 Web API 포함)와 EF Core는 **런타임 코드 생성**에 의존한다. AOT 지원은 **Minimal API에 대한 기본 지원**까지다.
>
> 데이터 접근이 있는 서비스를 AOT로 만들려면 Dapper나 ADO.NET + 원본 생성 직렬화로 가야 한다. 72.3절의 하이브리드 접근이 여기서 다른 이유로 다시 정당화된다.

### 트리밍이 조용히 깨뜨리는 것

트리밍은 사용되지 않는 어셈블리·타입·멤버를 제거한다. 문제는 **"사용된다"의 판정이 정적 분석**이라는 점이다. 리플렉션으로만 접근되는 멤버는 제거된다.

```csharp
// 트리머는 이 타입이 쓰인다는 것을 알 수 없다
var type = Type.GetType(config["HandlerType"]!);
object handler = Activator.CreateInstance(type!)!;
```

게시 후 런타임에 `null`이 나오거나 `MissingMethodException`이 난다. **개발 중에는 멀쩡하다.** 이것이 트리밍 관련 사고의 표준 시나리오다.

방어선은 셋이다.

```csharp
// 1) 트리머에게 알려준다
static object Create(
    [DynamicallyAccessedMembers(DynamicallyAccessedMemberTypes.PublicConstructors)]
    Type t) => Activator.CreateInstance(t)!;
```

```xml
<!-- 2) 경고를 오류로 승격해 CI에서 막는다 -->
<PropertyGroup>
  <PublishTrimmed>true</PublishTrimmed>
  <TrimmerSingleWarn>false</TrimmerSingleWarn>
  <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
  <EnableTrimAnalyzer>true</EnableTrimAnalyzer>
</PropertyGroup>
```

3) **게시된 산출물로 통합 테스트를 돌린다.** `dotnet run`으로 통과한 테스트는 트리밍된 바이너리에 대해 아무것도 증명하지 않는다. 게시본을 컨테이너에 넣고 스모크 테스트를 돌리는 것이 유일하게 신뢰할 수 있는 검증이다.

### 애플리케이션 코드로 줄이는 시작 시간

스위치를 켜기 전에 코드로 줄일 수 있는 것들이 있고, 대개 이쪽이 더 크다.

| 항목 | 조치 |
|---|---|
| **EF Core 모델 빌드** | `dotnet ef dbcontext optimize` 로 컴파일된 모델 생성. 엔터티가 수백 개면 초 단위로 줄어든다 |
| **정규식 컴파일** | `RegexOptions.Compiled`는 시작 시 IL을 생성한다. `[GeneratedRegex]` 원본 생성기로 대체하면 그 비용이 빌드 타임으로 간다 |
| **JSON 직렬화** | `JsonSerializerContext` 원본 생성기. 리플렉션 기반 메타데이터 구축이 사라지고 트리밍·AOT 호환도 얻는다 |
| **DI 등록** | 어셈블리 스캔(`Scrutor` 등)은 시작 시 모든 타입을 리플렉션한다. 명시적 등록으로 대체 |
| **싱글턴 즉시 생성** | `IHostedService`에서 무거운 초기화를 하면 첫 요청이 막힌다. 백그라운드로 미루거나 지연 초기화 |
| **설정 검증** | `ValidateOnStart()`는 유용하지만 비싸다. 필요한 옵션에만 |

> **💡 서버리스의 콜드 스타트는 "덜 하기"로 이긴다**
>
> Azure Functions 소비 계층처럼 스케일 투 제로가 있는 환경에서는 콜드 스타트가 사용자에게 그대로 노출된다. 여기서 효과 순서는 대체로 이렇다.
>
> 1. **의존성 줄이기** — 로드할 어셈블리가 적을수록 빠르다. 함수 하나를 위해 EF Core 전체를 끌고 오지 마라.
> 2. **원본 생성기로 리플렉션 제거** — JSON, 정규식, 로깅.
> 3. **R2R 게시**.
> 4. 그래도 부족하면 **항상 대기(pre-warmed) 인스턴스**를 돈으로 산다.
>
> Native AOT는 4번보다 싸지만, 함수 런타임과 바인딩이 지원하는 범위 안에서만 가능하다.

## 72.8 컨테이너 메모리 제한과 GC 설정

65.5절에서 힙 하드 리밋 설정을, 65.7절에서 DATAS를 다뤘다. 그리고 65.7절 마지막에서 "자세한 것은 72.8절"이라고 미뤘다. 여기서 마무리한다. 이 절의 주제는 **cgroup이 정한 한계와 .NET GC가 믿는 한계가 어긋날 때 무슨 일이 벌어지는가**다.

### GC는 컨테이너 한계를 자동으로 감지한다

컨테이너 안에서 실행되면 GC는 환경의 메모리 제한을 자동으로 감지한다. 그런데 GC가 통제하는 것은 **관리 메모리뿐**이다. 메서드를 JIT하는 데 쓰는 메모리, 네이티브 코드의 할당, 스레드 스택은 GC의 관할 밖이다.

그래서 GC는 모든 힙의 누적 크기를 **컨테이너에 할당된 총 메모리의 일정 비율**로 제한한다. 기본값은 **75%** 다.

```text
1 GB 제한 컨테이너에서의 기본 배분

  ┌────────────────────────────────────────────────────────┐
  │                    컨테이너 제한 1024 MB                 │
  ├──────────────────────────────────────────┬─────────────┤
  │  GC 관리 힙 상한   768 MB (75%)           │  나머지     │
  │                                          │  256 MB     │
  │  · SOH / LOH / POH                       │  · 런타임   │
  │  · 넘으면 OutOfMemoryException            │  · JIT      │
  │                                          │  · 스택     │
  │                                          │  · 네이티브 │
  │                                          │  · 사이드카 │
  └──────────────────────────────────────────┴─────────────┘
                                              넘으면 OOMKilled
```

두 실패 모드가 **완전히 다르다**는 것이 이 절의 핵심이다.

| 실패 | 원인 | 증상 |
|---|---|---|
| **`OutOfMemoryException`** | 관리 힙이 GC 하드 리밋(75%)에 닿았다 | .NET 예외. 스택 트레이스가 남는다. 프로세스가 살아 있을 수도 있다 |
| **OOMKilled (SIGKILL)** | 프로세스 전체가 cgroup 한계를 넘었다 | **커널이 죽인다.** 로그도, 예외도, 종료 훅도 없다. 파드가 조용히 재시작된다 |

> **⚠️ 파드가 로그 없이 재시작되면 GC 예외를 찾지 마라**
>
> `kubectl describe pod`에 `Reason: OOMKilled`, `Exit Code: 137`이 보이면 그건 .NET 예외가 아니다. 커널의 OOM 킬러가 SIGKILL을 보낸 것이다. 애플리케이션 로그에는 **아무것도 남지 않는다.**
>
> 이 경우 범인은 대개 **GC 힙이 아니라 나머지 25% 쪽**이다. 네이티브 라이브러리, 대량의 스레드 스택, 같은 컨테이너의 다른 프로세스, 또는 파일 캐시. `dotnet-counters`의 `gc-heap-size`가 여유로운데 파드가 죽는다면 확진이다.

### 비율을 조정하는 두 가지 방법

기본 75%가 맞지 않는 경우가 양쪽으로 있다.

- **너무 높다** — 네이티브 코드나 같은 컨테이너의 다른 프로세스가 남은 256 MB보다 많이 쓴다. 그래서 OOM 킬을 당한다.
- **너무 낮다** — 프로세스가 거의 순수 관리 코드인데 800~900 MB를 쓰고 싶다. 250 MB가 낭비된다.

```json
// runtimeconfig.json — 비율로 지정
{
  "configProperties": {
    "System.GC.HeapHardLimitPercent": 85
  }
}
```

```text
# 환경 변수 — 절대값으로 지정. 16진수이고 0x 접두사는 붙이지 않는다.
# 800 MB = 838860800 = 0x32000000
DOTNET_GCHeapHardLimit=32000000
```

```xml
<!-- .csproj -->
<PropertyGroup>
  <ServerGarbageCollection>true</ServerGarbageCollection>
  <ConcurrentGarbageCollection>true</ConcurrentGarbageCollection>
</PropertyGroup>
```

세대별로 나눠 거는 것도 가능하다. `GCHeapHardLimitSOH` / `GCHeapHardLimitLOH` / `GCHeapHardLimitPOH`와 각각의 `...Percent` 형태다. 고급 시나리오에서만 쓴다.

> **⚠️ `GCHeapHardLimit`을 쓰면 GC가 요청한 크기의 두 배를 커밋한다**
>
> `GCLargePages`와 함께 쓸 때 관찰된 동작이다. `GCHeapHardLimit`으로 하드 리밋을 걸면 GC가 **요청한 크기의 두 배를 커밋한다**(여분을 쓰지는 않는다). 이 동작의 이유는 불명확하며 버그일 가능성이 높다.
>
> 대신 **힙별로 제한하는 것을 권한다.** `GCHeapHardLimitSOH`, `GCHeapHardLimitLOH`, `GCHeapHardLimitPOH` **세 개를 모두** 설정해야 하며, 하나라도 빠지면 초기화가 오류 코드 `0x8013200D`로 실패한다. 세 개를 다 주면 필요한 만큼만 커밋한다.
>
> 참고로 `GCLargePages`를 켜려면 하드 리밋 설정이 **필수**다. 안 하면 `0x8013200E`(`CLR_E_GC_LARGE_PAGE_MISSING_HARD_LIMIT`)로 실패한다.

### 런타임에 한계 바꾸기 ※.NET 8

.NET 8부터는 프로세스를 재시작하지 않고 메모리 한계를 갱신할 수 있다.

```csharp
// 컨테이너 한계가 수직 확장으로 늘어났을 때
AppContext.SetData("GCHeapHardLimit", (ulong)(1600L * 1024 * 1024));
GC.RefreshMemoryLimit();
```

`GC.RefreshMemoryLimit()`은 갱신된 설정을 읽어 GC의 내부 한계를 다시 계산한다. 컨테이너 오케스트레이터가 리소스를 동적으로 조정하는 환경에서 쓸모가 있다.

### CPU 제한이 만드는 두 번째 함정

메모리만 문제가 아니다. 서버 GC는 **가용 코어마다 힙 하나**를 만든다(65.1절). 컨테이너의 CPU 할당량은 코어 개수가 아니라 **시간 슬라이스 비율**이다. `cpu: "500m"`은 "코어 0.5개"라는 뜻이지 "코어 0.5개만 보인다"는 뜻이 아니다.

| 상황 | 결과 |
|---|---|
| CPU가 1개로 감지되는 컨테이너 | **서버 GC 설정이 무시되고** 워크스테이션 GC가 강제된다 |
| CPU 할당량 500m, 노드는 64코어 | .NET 6 이상은 cgroup 할당량을 반영해 `Environment.ProcessorCount`를 낮춘다 |
| 할당량 없이 노드 전체를 보는 파드 | 힙 64개가 만들어지고 유휴 시에도 메모리를 붙들고 있다 |

> **⚠️ `gcServer=true`를 켜 놓고 1 CPU 컨테이너에 넣으면 아무 일도 안 일어난다**
>
> 설정 파일에는 서버 GC라고 적혀 있는데 실제로는 워크스테이션 GC로 돌고 있다. 성능 문제를 디버깅할 때 이 불일치를 모르면 몇 시간을 날린다. **믿지 말고 확인하라.**
>
> ```csharp
> Console.WriteLine($"ServerGC={System.Runtime.GCSettings.IsServerGC}, " +
>                   $"Latency={System.Runtime.GCSettings.LatencyMode}, " +
>                   $"CPU={Environment.ProcessorCount}");
> ```
>
> 프로세스가 실제로 어떤 설정으로 도는지는 `GC.GetConfigurationVariables()`(65.8절)나 EventPipe 런다운 이벤트로도 확인할 수 있다.

### 컨테이너 설정 조합표

| 배포 형태 | 권장 조합 |
|---|---|
| **다중 인스턴스 마이크로서비스** (.NET 8+) | 서버 GC + **DATAS 켬**(.NET 9는 기본). `GCHeapCount` 수동 지정 금지 |
| **처리량 우선 전용 워커** | 서버 GC + 백그라운드, **DATAS 끔**. 필요하면 `GCHeapCount`를 CPU 할당량에 맞춰 고정 |
| **네이티브 의존이 큰 서비스** | `HeapHardLimitPercent`를 60~70%로 **낮춘다** |
| **거의 순수 관리 코드** | `HeapHardLimitPercent`를 80~85%로 올린다 |
| **작은 사이드카 / CLI** | 워크스테이션 GC, 비동시. GC 전용 스레드 0개 |
| **메모리 스파이크가 큰 배치** | 요청(request)과 한계(limit)를 같게 잡아 QoS를 Guaranteed로 |

> **💡 Kubernetes에서 요청과 한계를 같게 잡아라**
>
> `requests.memory < limits.memory`인 파드는 QoS 클래스가 Burstable이다. 노드가 메모리 압박을 받으면 **Guaranteed 파드보다 먼저 축출된다.** .NET GC는 한계(75%)를 기준으로 힙을 키우므로, 요청보다 훨씬 많이 쓰다가 축출되는 패턴에 잘 걸린다.
>
> 지연 시간이 중요한 서비스는 `requests == limits`로 두는 것이 안전하다. 비용은 더 들지만 예측 가능성을 산다.

## 72.9 응답성 있는 UI — 긴 작업의 배경 실행

여기서 말하는 "응답성"은 화면 크기에 맞춰 레이아웃이 바뀌는 반응형 디자인이 아니다. **작업이 도는 동안에도 사용자 입력이 막히지 않는 것**이다.

### 규칙은 하나다

**UI 스레드에서는 아무것도 기다리지 않는다.** 60fps를 유지하려면 프레임당 예산이 16.7ms다. UI 스레드를 그보다 오래 붙들면 사용자는 끊김을 본다. 수백 밀리초를 붙들면 "응답 없음"이 뜬다.

`Thread.Sleep`, `.Result`, `.Wait()`, 동기 I/O, 동기 DB 호출 — 전부 UI 스레드에서 금지다(51.5절).

### `BackgroundWorker` — 레거시지만 여전히 만난다

WinForms 코드베이스에는 `BackgroundWorker`가 많다. 이벤트 세 개로 이루어진다.

```csharp
public partial class MainForm : Form
{
    private int _operationNumber;

    public MainForm()
    {
        InitializeComponent();
        var w = LongRunningProcessBackgroundWorker;
        w.WorkerReportsProgress = true;        // 없으면 ReportProgress가 InvalidOperationException
        w.WorkerSupportsCancellation = true;   // 없으면 CancelAsync가 InvalidOperationException
        w.DoWork += LongRunningProcessBackgroundWorker_DoWork;
        w.ProgressChanged += LongRunningProcessBackgroundWorker_ProgressChanged;
        w.RunWorkerCompleted += LongRunningProcessBackgroundWorker_RunWorkerCompleted;
        if (!w.IsBusy) w.RunWorkerAsync();
    }

    // 워커 스레드에서 실행된다 — 여기서 UI를 만지면 안 된다
    private void LongRunningProcessBackgroundWorker_DoWork(object sender, DoWorkEventArgs e)
    {
        var worker = (BackgroundWorker)sender;
        for (int i = 1; i <= 100; i++)
        {
            if (worker.CancellationPending) { e.Cancel = true; break; }
            _operationNumber = i;
            Thread.Sleep(100);            // 실제 작업을 대신한 지연
            worker.ReportProgress(i);
        }
    }

    // UI 스레드로 마셜링되어 실행된다
    private void LongRunningProcessBackgroundWorker_ProgressChanged(
        object sender, ProgressChangedEventArgs e)
    {
        StatusLabel.Text = $"진행: {e.ProgressPercentage}%";
        TaskProgressBar.Value = e.ProgressPercentage;
    }

    private void LongRunningProcessBackgroundWorker_RunWorkerCompleted(
        object sender, RunWorkerCompletedEventArgs e)
    {
        StatusLabel.Text = e.Cancelled ? "취소됨"
                         : e.Error != null ? $"오류: {e.Error.Message}"
                         : "완료";
        LongRunningOperationCancelButton.Visible = false;
        StatusBar.Visible = false;
    }

    private void LongRunningOperationCancelButton_Click(object sender, EventArgs e)
    {
        if (LongRunningProcessBackgroundWorker.WorkerSupportsCancellation)
            LongRunningProcessBackgroundWorker.CancelAsync();
    }
}
```

구조 자체는 옳다. **작업은 워커 스레드에서, 진행 보고와 완료 처리는 UI 스레드에서.** 그런데 `BackgroundWorker`에는 문제가 있다.

| 문제 | 내용 |
|---|---|
| **스레드 하나를 통째로 점유한다** | I/O 대기 중에도 스레드가 블로킹된다. 비동기 I/O의 이점이 사라진다 |
| **취소가 협조적이지 않다** | `CancellationToken`을 아래로 전파할 수 없다 |
| **예외가 삼켜진다** | `RunWorkerCompleted`에서 `e.Error`를 확인하지 않으면 조용히 사라진다 |
| **작업을 조합할 수 없다** | 여러 작업을 연달아 또는 병렬로 엮기 어렵다 |

### 현대적 대체 — `async` + `IProgress<T>` + `CancellationToken`

```csharp
private CancellationTokenSource? _cts;

private async void StartButton_Click(object sender, EventArgs e)
{
    _cts = new CancellationTokenSource();
    StartButton.Enabled = false;
    CancelButton.Enabled = true;

    // Progress<T>는 생성된 스레드의 동기화 컨텍스트(=UI 스레드)로 콜백을 보낸다
    var progress = new Progress<int>(pct =>
    {
        TaskProgressBar.Value = pct;
        StatusLabel.Text = $"진행: {pct}%";
    });

    try
    {
        await ImportAsync(progress, _cts.Token);
        StatusLabel.Text = "완료";
    }
    catch (OperationCanceledException)
    {
        StatusLabel.Text = "취소됨";
    }
    catch (Exception ex)
    {
        StatusLabel.Text = $"오류: {ex.Message}";
    }
    finally
    {
        StartButton.Enabled = true;
        CancelButton.Enabled = false;
        _cts.Dispose();
        _cts = null;
    }
}

private void CancelButton_Click(object sender, EventArgs e) => _cts?.Cancel();

private static async Task ImportAsync(IProgress<int> progress, CancellationToken ct)
{
    for (int i = 1; i <= 100; i++)
    {
        ct.ThrowIfCancellationRequested();
        await Task.Delay(100, ct);       // 진짜 I/O라면 await 지점에서 스레드가 반납된다
        progress.Report(i);
    }
}
```

`Progress<T>`는 **생성된 시점의 동기화 컨텍스트**를 붙잡아 두었다가 거기로 콜백을 보낸다. UI 스레드에서 만들었으므로 `Report`는 UI 스레드에서 실행된다. `Invoke`/`BeginInvoke`를 직접 쓸 필요가 없다.

CPU 바운드 작업이라면 `Task.Run`으로 스레드 풀에 넘긴다.

```csharp
byte[] result = await Task.Run(() => ComputeHeavy(input, ct), ct);
```

> **⚠️ `Application.DoEvents()`는 응답성 해법이 아니다**
>
> 스플래시 화면 예제에서 자주 보이는 패턴이다.
>
> ```csharp
> for (int x = 1; x <= 10; x++)
> {
>     Thread.Sleep(500);
>     splashScreen.Update($"로딩 {x}");
>     Application.DoEvents();        // ← 이것
> }
> ```
>
> `DoEvents()`는 메시지 큐를 강제로 처리한다. 화면은 갱신되지만 **재진입(reentrancy)** 이 생긴다. 루프가 도는 동안 사용자가 같은 버튼을 다시 누르면 핸들러가 중첩 실행된다. 폼을 닫으면 이미 파괴된 컨트롤을 만지게 된다. 재현이 어려운 버그의 온상이다.
>
> 스플래시 화면이 필요하다면 **초기화를 `await`하고 그동안 스플래시를 띄운다.** `DoEvents`는 레거시 코드에서 만나면 제거 대상이지 참고 대상이 아니다.

### 데이터 페이징과 가상화

100건이든 100만 건이든 화면에 보이는 것은 20행이다. 전부 로드하고 전부 렌더링하는 것은 순수 낭비다.

```csharp
private const int PageSize = 20;
private int _currentPage = 1;
private int _totalPages;

private async Task LoadPageAsync(int page, CancellationToken ct)
{
    _currentPage = Math.Clamp(page, 1, _totalPages);

    // 서버에서 잘라 온다. 클라이언트 Skip/Take가 아니다.
    List<ProductDto> items = await _repo.GetPageAsync(_currentPage, PageSize, ct);

    DataTable.DataSource = items;
    PageTextBox.Text = $"{_currentPage} / {_totalPages} 페이지";
    FirstButton.Enabled = PrevButton.Enabled = _currentPage > 1;
    NextButton.Enabled = LastButton.Enabled = _currentPage < _totalPages;
}
```

WPF에서는 `VirtualizingStackPanel`이 기본으로 켜져 있지만, `ScrollViewer`로 감싸거나 `ItemsControl`을 그냥 쓰면 **꺼진다.** 목록이 느려졌다면 가상화가 살아 있는지부터 확인한다.

### 웹의 응답성 — 부분 갱신과 푸시

웹에서는 "UI 스레드"가 브라우저의 단일 JS 스레드다. 원칙은 같다. 그리고 도구가 셋 있다.

| 기술 | 방향 | 용도 |
|---|---|---|
| **AJAX** | 클라이언트 → 서버 (요청 시) | 페이지 일부만 갱신. 전체 리로드를 없앤다 |
| **WebSocket** | 양방향, 단일 TCP 커넥션 | 서버 폴링을 없앤다. 이벤트 기반으로 만든다 (RFC 6455) |
| **SignalR** | 양방향 (WebSocket → SSE → 롱 폴링 폴백) | 실시간 알림·채팅·대시보드. 전송 협상을 대신해 준다 |

```csharp
// SignalR 허브
public class ChatHub : Hub
{
    public async Task SendMessage(string user, string message)
        => await Clients.All.SendAsync("ReceiveMessage", user, message);
}
```

```javascript
"use strict";
const connection = new signalR.HubConnectionBuilder().withUrl("/chatHub").build();
connection.on("ReceiveMessage", (user, message) => {
    const li = document.createElement("li");
    li.textContent = `${user} says ${message}`;
    document.getElementById("messagesList").appendChild(li);
});
connection.start()
    .then(() => { document.getElementById("sendButton").disabled = false; })
    .catch(err => console.error(err.toString()));
```

> **⚠️ 폴링은 서버를 조용히 죽인다**
>
> "5초마다 새로고침"은 구현이 쉽다. 그런데 동시 사용자 10,000명이면 **초당 2,000요청**이 아무 일도 없을 때조차 나간다. 응답 대부분은 "변한 것 없음"이다. 대역폭, CPU, DB 커넥션이 전부 낭비된다.
>
> 갱신이 드물고 사용자가 많다면 **푸시(WebSocket/SignalR)가 폴링보다 압도적으로 싸다.** 반대로 사용자가 적고 갱신이 잦다면 폴링이 더 단순하다. 사용자 수 × 폴링 빈도를 계산해 보고 결정한다.

> **💡 응답성은 체감이 실측을 이긴다**
>
> 3초 걸리는 작업을 2.5초로 줄이는 것보다, **즉시 진행률을 보여주고 취소 버튼을 주는 것**이 사용자 만족에 더 크게 기여한다. 스플래시 화면, 스켈레톤 UI, 낙관적 업데이트가 전부 이 원리다.
>
> 다만 이건 **진짜 최적화를 대신하지 못한다.** 진행률 표시줄로 가린 3초는 여전히 3초다. 체감 개선은 실측 개선 위에 얹는 것이지 그 대체물이 아니다.

## 72.10 분산 시스템의 성능 고려사항

### 성능 문제가 코드 밖에 있을 때

분산 시스템에서 "느리다"의 원인은 종종 C#과 무관하다. 실무에서 반복적으로 만나는 목록이다.

| 원인 | 증상 | 확인 |
|---|---|---|
| **IP 주소 충돌** | 간헐적 타임아웃, 예측 불가능한 동작 | 같은 네트워크에 중복 주소가 없는지 |
| **DNS 해석 지연** | 첫 요청만 느림, 또는 전부 느림 | `nslookup`, DNS 서버 순서, DNS 접미사, DHCP에서 DNS를 받는지 |
| **방화벽 설정** | 리소스가 아예 안 보임 | 분산 방화벽 → 서버 방화벽 → 클라이언트 방화벽 순서로 |
| **백신 실시간 검사** | 파일·네트워크 접근이 전부 느림 | 애플리케이션 폴더를 예외로 등록 |
| **코드 서명 없음** | DLL이 격리(quarantine)됨 | 오탐. 서명하거나 예외 등록 |
| **네트워크 케이블·NIC** | 대량 전송에서만 느림 | Cat-5는 일반 인터넷용. 대량 파일·데이터라면 Cat-6a/Cat-7 |
| **백업 스케줄 충돌** | 특정 시간대에만 느림 | 백업을 비업무 시간으로 |

SQL Server에는 별도의 함정 목록이 있다. 동적 포트가 충돌할 수 있고, 많은 네트워크에서 **명명된 파이프와 TCP 프로토콜을 모두 활성화**해야 동작한다. SQL Server 구성 관리자에서 프로토콜을 바꾼 뒤에는 해당 인스턴스와 **SQL Server Browser 서비스를 재시작**해야 한다. 방화벽이 있다면 인스턴스 실행 파일을 예외로 등록하거나 포트를 연다 — 표준 포트는 TCP 1433, UDP 1434다. 그래도 인스턴스가 안 보이면 연결 문자열을 `IP_ADDRESS,PORT_NUMBER\INSTANCE_NAME` 형식으로 다시 만드는 것이 우회책이다. 그리고 특정 버전의 SQL Server 네이티브 클라이언트를 쓰면 **모든 클라이언트 컴퓨터에 그 버전을 배포해야 한다** — Windows에 기본 설치되는 SQL Server 드라이버를 쓰면 이 문제가 사라진다.

> **⚠️ "코드가 느리다"는 결론을 내리기 전에 네트워크를 먼저 배제하라**
>
> 프로파일러는 프로세스 안만 본다. 왕복 시간의 90%가 DNS 재시도에서 오고 있다면 프로파일러에는 "`SendAsync`에서 대기 중"으로만 보인다. 분산 시스템의 성능 조사는 **바깥에서 안으로** 좁혀 들어가는 것이 순서다.

### 왕복 수를 줄여라

분산 시스템 성능의 제1원칙이다. 한 번의 왕복이 프로세스 내부 호출보다 수만~수백만 배 비싸므로, **호출 하나를 최적화하는 것보다 호출 하나를 없애는 것이 항상 크다.**

```csharp
// 나쁘다 — 네트워크 N+1. 72.4절의 문제가 서비스 경계로 옮겨온 것이다.
var orders = await _orderApi.GetOrdersAsync(customerId);
foreach (var o in orders)
    o.Customer = await _customerApi.GetCustomerAsync(o.CustomerId);   // 왕복 N회
```

```csharp
// 낫다 — 배치 엔드포인트로 한 번에
var orders = await _orderApi.GetOrdersAsync(customerId);
int[] ids = orders.Select(o => o.CustomerId).Distinct().ToArray();
Dictionary<int, Customer> map = await _customerApi.GetCustomersAsync(ids);   // 왕복 1회
foreach (var o in orders) o.Customer = map[o.CustomerId];
```

독립적인 호출이라면 병렬로 보낸다.

```csharp
// 세 서비스가 서로 독립이라면 순차로 기다릴 이유가 없다
Task<Inventory> inv = _inventoryApi.GetAsync(sku, ct);
Task<Pricing> price = _pricingApi.GetAsync(sku, ct);
Task<Reviews> rev = _reviewApi.GetAsync(sku, ct);
await Task.WhenAll(inv, price, rev);
// 총 지연 = 셋 중 가장 느린 것 (합이 아니라)
```

### CQRS — 읽기와 쓰기를 분리한다

**명령 질의 책임 분리(CQRS, Command Query Responsibility Separation)** 는 단순한 원칙에서 출발한다. **명령(command)은 동작을 수행하는 메서드이고, 질의(query)는 데이터를 반환하는 메서드다.** 명령은 질의를 수행하지 않고, 질의는 명령을 수행하지 않는다. 명령은 질의와 별개의 모델을 가질 수 있다.

```csharp
public class CqrsBasedClass
{
    // 명령 — 동작만 하고 값을 반환하지 않는다
    public void SleepCommand(int milliseconds) => Thread.Sleep(milliseconds);

    // 질의 — 값만 반환하고 상태를 바꾸지 않는다
    public DateTime DateTimeQuery() => DateTime.Now;
}
```

가장 단순한 형태는 이렇게 사소하다. 그런데 이 분리가 **성능 관점에서 강력한 이유**는, 읽기와 쓰기의 최적화 방향이 정반대이기 때문이다.

| 축 | 쓰기(명령) 측 | 읽기(질의) 측 |
|---|---|---|
| 정규화 | 정규화된 스키마 | **비정규화된 읽기 모델** |
| 일관성 | 강한 일관성, 트랜잭션 | 최종 일관성 허용 |
| 인덱스 | 최소 (쓰기 비용) | 최대 (조회 속도) |
| 프레임워크 | EF Core (변경 추적이 값을 함) | Dapper / 원시 SQL (72.3절) |
| 확장 | 수직 확장 경향 | **수평 확장 + 캐시** |

읽기가 쓰기보다 압도적으로 많은 시스템(대부분의 시스템이 그렇다)에서 이 분리는 읽기 쪽을 독립적으로 확장할 수 있게 한다.

### 이벤트 소싱

이벤트 소싱은 상태를 **상태 변경 이벤트의 시퀀스**로 저장한다. 현재 상태는 이벤트를 재생해서 얻는다. CQRS와 함께 쓰이는 경우가 많지만 서로 독립적인 패턴이다.

성능 관점에서 유의할 점은 둘이다.

- **쓰기는 순수 추가(append-only)** 라서 매우 빠르다. 잠금 경합이 적다.
- **읽기는 재생 비용이 있다.** 이벤트가 수만 개 쌓인 집합체를 매번 재생하면 느려진다. 스냅숏을 주기적으로 떠서 "스냅숏 + 그 이후 이벤트"만 재생하는 것이 표준 대응이다.

### 컨테이너 vs 서버리스

현대적인 마이크로서비스 구현은 Docker·Kubernetes 같은 컨테이너화에 덜 의존하고 Azure Functions 같은 순수 서버리스 쪽으로 이동하는 경향이 있다. 서버리스 함수는 **호출되는 동안만 활성**이고, 끝나면 잠든다. 컨테이너 솔루션보다 컴퓨팅 자원과 전력을 덜 쓴다. 단점은 함수 개수가 늘면 관리가 어려워진다는 것 — 컨테이너와 마찬가지로 오케스트레이션이 필요해진다.

| 축 | 컨테이너 | 서버리스 |
|---|---|---|
| **레거시 이전** | 코드를 다시 쓰지 않고 감싸서 배포 가능 | 재작성 필요 |
| **서드파티 의존** | Docker Hub에서 즉시 가져다 쓴다 | PaaS 가용성과 비용에 제약 |
| **로컬 개발** | Docker Compose로 여러 서비스 한 번에 | 로컬 에뮬레이터 필요 |
| **유휴 비용** | **클러스터 노드가 항상 돈다 → 비용 발생** | **스케일 투 제로 → 0** |
| **스케일 아웃 속도** | 노드 프로비저닝 시간 | **빠르다.** 실행 시간만 과금 |
| **개발 방식** | 기존(무거운) 기법을 유도하기 쉽다 | 이벤트 기반, 재작성·폐기가 쉽다 |
| **보안** | Ingress 컨트롤러로 노출 최소화 | 함수 자체의 보안을 별도로 챙겨야 한다 |

Azure Functions는 상태를 갖는 오케스트레이션을 위해 **Durable Functions** 확장을 제공한다. 함수 유형이 넷(활동, 오케스트레이터, 엔터티, 클라이언트)이고, 패턴이 여섯(집계자, 비동기 HTTP API, 팬아웃/팬인, 함수 체이닝, 사람 개입, 모니터링)이다. 성능 관점에서 중요한 것은 **팬아웃/팬인** — 함수를 병렬로 실행하고 결과를 모은다 — 과 **비동기 HTTP API** — 오래 걸리는 작업의 상태 관리를 런타임이 대신한다 — 다.

> **⚠️ 활동 함수는 최소 한 번(at-least-once) 실행된다**
>
> Durable Task 프레임워크는 활동 함수가 **적어도 한 번** 실행되는 것만 보장한다. 몇 번 호출될지 알 수 없으므로 Microsoft는 활동 함수를 가능한 한 **멱등(idempotent)** 하게 만들 것을 권한다.
>
> 이건 서버리스만의 이야기가 아니다. 메시지 큐, 재시도 정책, 로드 밸런서 뒤의 재전송 — 분산 시스템에서 "정확히 한 번"은 거의 항상 환상이다. **중복 실행을 견디는 설계**가 재시도를 안전하게 만들고, 재시도가 안전해야 공격적인 타임아웃을 걸 수 있고, 공격적인 타임아웃이 꼬리 지연 시간을 줄인다. 세 가지가 하나로 엮여 있다.

### 확장 — 수직인가 수평인가

현재 시스템이 워크로드를 감당하지 못하면 선택지는 둘이다. **수직 확장(scale up)** 은 물리적 컴퓨팅 용량을 늘리는 것이고, **수평 확장(scale out)** 은 서버를 더 붙이는 것이다. 오늘날 많은 기업의 방향은 서버 VM과 컨테이너를 쓰고, Azure·AWS·Google Cloud 같은 클라우드 위에서 Docker·Kubernetes로 컨테이너를 관리하는 쪽이다.

리소스 한 곳에 커넥션이 몰려 클라이언트가 접속조차 못 하는 상황은 **로드 밸런싱**으로 푼다. 특정 서버가 임계치에 도달하면 클라이언트를 다른 서버로 보낸다. SQL Server라면 Always On 가용성 그룹과 장애 조치 클러스터로 서버가 내려가도 연결을 유지한다.

그리고 코드 쪽에서는, 큰 라이브러리와 실행 파일을 Azure Functions 같은 마이크로서비스로 쪼개면 작아진다. 이런 온라인 서비스는 필요할 때만 실행되고 알아서 늘었다 줄어들므로 전기와 장비 비용까지 절약된다.

> **💡 확장하기 전에 왕복부터 세라**
>
> "서버를 늘리자"는 결론은 대개 두 번째로 나와야 한다. 요청 하나가 내부 서비스를 15번 호출하고 있다면, 서버를 두 배로 늘려도 그 15번은 그대로다. **호출 수를 8번으로 줄이는 것**이 서버 대수를 줄이는 가장 확실한 방법이다.
>
> 분산 추적(OpenTelemetry)으로 요청 하나의 스팬 개수를 세어 보라. 예상보다 훨씬 많을 것이다.

> **⚠️ 데이터베이스 쿼리가 마이크로서비스 성능의 진짜 병목인 경우가 가장 많다**
>
> 같은 결과를 내는 쿼리도 작성 방법에 따라 성능이 크게 달라진다. 조인이 많고 결과 집합이 클수록 차이가 커지고, 동적 SQL도 느려질 수 있다. SQL Server Profiler와 실행 계획으로 병목을 찾아 쿼리를 다시 쓰고, 누락된 인덱스를 추가하고, 잘못된 인덱스를 고치고, 미리 컴파일된 저장 프로시저를 쓴다. 72.3절의 숫자가 이 조언을 뒷받침한다.

## 이 장의 요약

- **프로세스 경계를 넘는 비용이 지배한다.** 71장까지의 최적화가 다루던 나노초·마이크로초 세계와, 이 장이 다루는 밀리초 세계는 자릿수가 다르다. 마이크로 최적화 전에 왕복 하나를 없애는 것이 항상 크다.
- **`System.IO.Pipelines`는 버퍼 관리와 프로토콜 로직을 분리한다.** `Stream` 위에서 프레이밍을 직접 하면 부분 메시지·다중 메시지·버퍼 초과·백프레셔 네 가지를 전부 직접 처리해야 한다. 파이프라인의 `consumed`/`examined` 이원 위치가 그 복잡도를 흡수한다. 다만 저수준 인프라 코드에만 쓴다 — `ToArray()`가 등장하면 쓰는 의미가 없다.
- **`HttpClient`는 재사용하되 커넥션 수명은 제한한다.** 매번 만들면 소켓이 고갈되고, 정적으로 두기만 하면 DNS 변경을 영원히 놓친다. `PooledConnectionLifetime`이 두 문제를 동시에 푼다. `ConnectTimeout`은 기본이 무한이므로 반드시 설정한다.
- **데이터 접근 프레임워크는 연산마다 승자가 다르다.** 같은 논리적 작업이 구현에 따라 200배 이상 차이 났다. 하나로 통일하지 말고 하이브리드로 간다. 그리고 그 숫자는 당신의 환경에서 다시 재야 한다.
- **EF Core의 비용은 대부분 조용하다.** N+1, 지연 로딩, 카티션 폭발, 추적 오버헤드, 클라이언트 평가는 컴파일 오류를 내지 않는다. 실제 SQL을 로그로 보는 습관이 이 다섯 개를 전부 잡는다. 대량 연산은 `ExecuteUpdate`/`ExecuteDelete`로.
- **캐시는 계층이고, 각 계층의 실패 모드가 다르다.** L1은 인스턴스 간 불일치를, L2는 직렬화 비용을 낸다. 슬라이딩 만료만 쓰면 데이터가 영원히 늙지 않고, 크기 제한 없는 `IMemoryCache`는 메모리 누수다. .NET 9의 `HybridCache`가 스탬피드 방지와 태그 무효화를 내장으로 제공한다.
- **컬렉션에서는 Big-O보다 상수가 자주 이긴다.** 원소 수십 개에서는 선형 탐색이 해시 조회를 이길 수 있고, 인터페이스로 받으면 구조체 열거자가 박싱되며, 용량을 미리 잡지 않으면 재할당과 LOH 승격이 따라온다.
- **시작 시간은 네 개의 서로 다른 구간이다.** 어느 구간이 문제인지 재기 전에 R2R이나 AOT를 켜는 것은 추측이다. AOT는 시작을 얻는 대신 동적 PGO를 잃고, 트리밍은 크기를 얻는 대신 리플렉션을 잃는다. 그리고 그 손실은 **게시 후에만** 드러난다.
- **컨테이너에서 GC 힙 한계와 cgroup 한계는 다른 것이다.** `OutOfMemoryException`은 .NET이 던지고 로그가 남지만, OOMKilled는 커널이 죽여서 아무것도 남지 않는다. 기본 75%가 맞는지는 네이티브 메모리 사용량에 달렸다.
- **응답성은 "UI 스레드에서 아무것도 기다리지 않는다" 하나로 요약된다.** `Application.DoEvents()`는 해법이 아니라 재진입 버그의 원천이다. 그리고 폴링은 사용자 수를 곱해 보기 전까지 싸 보인다.
- **분산 시스템의 성능 문제는 절반이 코드 밖에 있다.** DNS, 방화벽, 백신, IP 충돌, 인덱스 누락. 프로파일러는 프로세스 안만 본다. 바깥에서 안으로 좁혀 들어가라.

## 연습 문제

1. 72.1절의 길이 접두사 프레임 파서를 그대로 구현하고, 클라이언트에서 **프레임을 1바이트씩 나눠 보내는** 테스트를 작성하라. 파서가 부분 프레임을 올바르게 누적하는지 확인하고, `AdvanceTo(buffer.Start, buffer.Start)`로 바꿨을 때 CPU 사용률이 어떻게 되는지 관찰하라.
2. `PipeOptions`의 `pauseWriterThreshold`를 8192로 낮추고, 소비자 쪽에 `await Task.Delay(50)`을 넣어 인위적으로 느리게 만들어라. 생산자의 `FlushAsync()`가 반환하는 `ValueTask`가 완료되기까지 걸리는 시간을 측정해 백프레셔가 실제로 걸리는 것을 확인하라.
3. 같은 URL을 1,000번 호출하는 프로그램을 두 벌 만들어라. 하나는 `using var client = new HttpClient()`를 반복하고, 하나는 정적 `HttpClient`를 쓴다. 실행 중 `netstat`(또는 `ss -tan`)으로 `TIME_WAIT` 소켓 수를 세어 비교하라.
4. 로컬 SQL Server(또는 SQLite)에 대해 72.3절과 같은 구조의 벤치마크를 BenchmarkDotNet으로 작성하라 — ADO.NET, Dapper, EF Core로 삽입·조회·수정·삭제. 순위가 본문의 표와 같은지 다른지 확인하고, 다르다면 왜 다른지 설명하라.
5. EF Core로 `Include`를 두 개 건 쿼리와 `AsSplitQuery()`를 건 쿼리의 **실제 SQL과 반환 행 수**를 로그로 확인하라. 컬렉션 크기를 10 → 100으로 늘렸을 때 두 방식의 전송 행 수가 각각 어떻게 변하는지 표로 정리하라.
6. `IMemoryCache`에 `SizeLimit` 없이 사용자 입력 기반 키를 계속 넣는 프로그램을 만들고, `dotnet-counters`로 `gc-heap-size`가 단조 증가하는 것을 관찰하라. 그다음 `SizeLimit`과 `Size`를 설정해 상한이 지켜지는지 확인하라.
7. 콘솔 앱 하나를 네 가지로 게시하라 — 프레임워크 종속, 자체 포함, 자체 포함 + `PublishTrimmed`, Native AOT. 각각의 산출물 크기와 **프로세스 시작부터 첫 출력까지의 시간**을 10회씩 측정해 중앙값을 비교하라.
8. `Docker`로 메모리 제한 512MB 컨테이너를 띄우고 관리 메모리를 계속 할당하는 앱을 실행하라. `OutOfMemoryException`이 나는 시점의 힙 크기를 확인하고, `DOTNET_GCHeapHardLimitPercent`를 바꿨을 때 그 시점이 어떻게 이동하는지 기록하라. 이어서 대량의 `byte[]`를 네이티브로 할당(`Marshal.AllocHGlobal`)해서 **OOMKilled**를 재현하고 두 실패의 차이를 확인하라.
