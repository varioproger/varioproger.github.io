# 62장. .NET 힙의 구조

> **이 장의 위치** — Part XI「메모리와 가비지 컬렉션」의 두 번째 장이다. 61장에서 가상 메모리·페이지·캐시라는 하드웨어와 OS의 층을 봤다면, 이 장은 그 위에 .NET 런타임이 얹은 **관리 힙(Managed Heap)의 지도**를 그린다. 힙이 왜 하나가 아니라 여러 조각으로 쪼개져 있는지, 그 조각들의 이름이 무엇이고 경계가 어디인지를 여기서 끝낸다. 이 장의 지도가 없으면 63장(할당)도 64장(GC 알고리즘)도 읽을 수 없다. 할당자와 수집기는 모두 "지금 어느 조각을 다루고 있는가"를 기준으로 동작하기 때문이다.
>
> **선수 지식** — 54장(타입 시스템의 런타임 표현), 61장(메모리의 기초)
>
> **이 장에서 다루지 않는 것** — 객체가 실제로 어떻게 할당되는지(범프 포인터, 할당 컨텍스트, 할당 예산)는 63장에서, Mark/Plan/Sweep/Compact 각 단계의 내부는 64장에서, 워크스테이션/서버·백그라운드 GC 같은 모드 선택은 65장에서, 누수 진단 도구의 사용법은 66장에서 다룬다. 고정(pinning)의 문법과 `fixed` 문은 60.8절에 있다.

## 62.1 뮤테이터 / 할당자 / 수집기 모델

### 세 명의 배우

메모리 관리를 이야기할 때 등장인물을 먼저 정리해두면 이후 모든 설명이 짧아진다. 자동 메모리 관리 문헌은 프로세스 안에서 벌어지는 일을 세 역할로 나눈다.

| 역할 | 원어 | 하는 일 | .NET에서의 실체 |
|---|---|---|---|
| **뮤테이터** | mutator | 객체를 읽고 쓰고 참조를 바꿔 객체 그래프를 **변형(mutate)** 한다 | 당신이 작성한 코드가 실행되는 스레드 |
| **할당자** | allocator | 새 객체를 담을 바이트를 힙에서 떼어준다 | CLR의 GC 할당자 (`JIT_TrialAllocSFastMP_InlineGetThread` 등) |
| **수집기** | collector | 더 이상 도달할 수 없는 객체의 메모리를 회수한다 | .NET GC |

이름은 거창하지만 의미는 단순하다. **뮤테이터는 "애플리케이션"의 다른 이름**이다. GC의 관점에서 애플리케이션이 하는 유일하게 중요한 일은 객체 그래프를 계속 바꿔대는 것이고, 그래서 mutator라고 부른다.

이 세 역할이 왜 중요한가. 셋이 **같은 데이터 구조를 동시에 만지기** 때문이다. 뮤테이터가 참조 필드를 쓰는 순간 수집기가 만들고 있던 도달 가능성 그래프가 무효가 될 수 있다. 그래서 런타임은 뮤테이터의 쓰기 연산에 몰래 코드를 끼워 넣는다. 이것이 **쓰기 장벽(write barrier)** 이고, 62.7절에서 그 실제 어셈블리 코드를 볼 것이다.

```csharp
// 이 세 줄에 세 배우가 모두 등장한다
var buffer = new byte[1024];   // 할당자: 1024+헤더 바이트를 떼어준다
list.Items = buffer;           // 뮤테이터: 그래프를 변형한다 → 쓰기 장벽이 낀다
GC.Collect();                  // 수집기: 도달 불가능한 것을 회수한다
```

> **📌 "mutator"라는 용어를 만나면**
>
> GC 논문과 .NET 런타임 소스에서 이 단어는 항상 "애플리케이션 스레드"를 뜻한다. `Mutator.Write(address, value)` 같은 의사코드는 "애플리케이션이 어떤 주소에 값을 쓴다"는 뜻일 뿐이다. C#의 `Mutator` 타입 같은 것은 존재하지 않는다.

### 프로세스 안의 여러 힙 중 하나

61.3절에서 본 것처럼 .NET 프로세스 안에는 메모리 영역이 아주 많다. 그중 "힙"이라 불리는 것만 해도 여러 종류다.

- 실행 엔진이 타입 설명을 담아두는 **도메인 힙**(Low Frequency Heap, High Frequency Heap, Stub Heap 등)
- OS의 네이티브 힙(`malloc`/`new`가 쓰는 것)
- 그리고 **GC 관리 힙(GC Managed Heap)**

이 장이 다루는 것은 마지막 하나다. `new`로 만든 객체가 들어가는 곳, CLI 명세가 "자유 저장소(free store)"라고 부르는 곳, 수집기가 유일하게 책임지는 곳이다. 앞으로 이 책에서 그냥 "힙"이라고 하면 GC 관리 힙을 뜻한다. 다른 힙을 가리킬 때는 반드시 이름을 붙인다.

### 왜 힙을 쪼개는가

GC 힙은 수십, 심지어 수백 기가바이트까지 자랄 수 있다. 할당자에게는 별문제가 아니다. 포인터를 앞으로 밀기만 하면 되니까. 문제는 수집기다.

**수집기 설계에서 가장 중요한 지표는 오버헤드**다. 스레드를 얼마나 오래 멈추는가, CPU를 얼마나 먹는가. 이상적으로는 일시 중지가 밀리초 미만이어야 한다. 그런데 61.4절에서 본 메모리 접근 지연을 떠올려보라. 수 기가바이트를 읽는 데는 밀리초 몇 개로는 어림도 없다.

그래서 모든 실용적인 GC의 핵심 설계 결정은 **메모리 분할 전략(memory partitioning strategy)** 이 된다. 힙 전체를 작은 조각으로 나눠 **독립적으로 다룰 수 있게** 만드는 것이다. 잘만 나누면 수집기 작업 시간이 극적으로 줄어든다. 프로그램이 실행되는 동안 모든 데이터를 똑같이 취급할 필요가 전혀 없기 때문이다.

### 나눌 수 있는 기준 다섯 가지

객체가 가진 속성 중 무엇을 기준으로 삼을 수 있을까. 이론적으로는 다음 다섯 가지가 후보다.

| 기준 | 발상 | 채택 여부 |
|---|---|---|
| **크기(size)** | 작은 객체와 아주 큰 객체를 다르게 다룬다. 큰 객체를 복사해 압축하면 오버헤드가 크므로, 작은 것만 압축하고 큰 것은 스윕만 한다 | **채택** |
| **수명(lifetime)** | 아주 짧게 사는 객체와 애플리케이션 수명 내내 사는 객체를 나눈다. 미래를 알 수는 없지만 "오래 산 것"과 "방금 만들어진 것"은 구별할 수 있다 | **채택** |
| **가변성(mutability)** | 한번 만들어지면 바뀌지 않는(불변) 객체를 따로 둔다 | 미채택 |
| **타입(type)** | 문자열 전용 힙, 정수 전용 힙 같은 식으로 타입별로 나눈다 | 미채택 |
| **종류(kind)** | 나가는 참조가 있는가 없는가, 고정(pinning)되었는가 아닌가로 나눈다 | **부분 채택** |

Microsoft의 .NET 구현과 Mono 구현 모두 원칙적으로 **처음 두 가지만** 선택했다. 두 런타임의 GC는 객체의 타입이나 가변성에 관심이 없다. "새 객체를 위해 N바이트를 달라"는 요청을 받아 적절한 바이트 수를 관리할 뿐이다.

그러나 GC 설계는 계속 진화한다. 문자열 리터럴과 고정 배열을 위한 최적화가 나중에 추가되었고, 그 결과가 **NonGC 힙**과 **고정 객체 힙**이다. 이것이 "종류 기준의 부분 채택"에 해당한다.

> **⚠️ "고정된 객체만 모아두면 되지 않나"가 간단하지 않은 이유**
>
> 종류 분할이 자명해 보이지만 실제로는 훨씬 복잡하다. .NET에서 객체는 **고정된 상태로 태어나지 않는다.** 만들어진 뒤 아무 때나 고정하고 아무 때나 풀 수 있다. 그러니 "현재 고정된 객체들의 영역"을 따로 두면 고정/해제할 때마다 객체를 앞뒤로 복사해야 해서 역효과가 난다.
>
> 이 문제를 .NET 5는 다른 각도로 풀었다. 나중에 고정하는 대신 **처음부터 고정된 상태로 태어나는 배열**을 만들 수 있게 한 것이다(62.5절).

### 이 장의 지도 — 네 개의 분할 축

.NET의 관리 힙은 실제로 **네 개의 서로 다른 축**으로 동시에 나뉜다. 이 넷은 서로 배타적이지 않고 겹쳐 있다. 한 객체는 네 축 모두에서 좌표를 갖는다.

```text
                      ┌──────────────────────────────┐
                      │      GC 관리 힙 (전체)        │
                      └──────────────┬───────────────┘
                                     │
     ┌───────────────┬───────────────┼───────────────┬───────────────┐
     ↓               ↓               ↓               ↓               │
┌─────────┐   ┌─────────────┐  ┌───────────┐  ┌────────────┐         │
│ ① 크기  │   │  ② 수명     │  │ ③ 종류    │  │ ④ 물리     │         │
│ (62.3)  │   │  (62.4)     │  │ (62.5)    │  │ (62.6)     │         │
└────┬────┘   └──────┬──────┘  └─────┬─────┘  └──────┬─────┘         │
     │               │               │               │               │
     ↓               ↓               ↓               ↓               │
  SOH  LOH        gen0            POH             세그먼트           │
 (<85K)(≥85K)     gen1         NonGC 힙          (~.NET 6)          │
                  gen2        (=Frozen)             ↓                │
                    ↑                             리전               │
              SOH 안에서만                       (.NET 7+)            │
              적용된다                                                │
                                                                     │
  ──────────────────────────────────────────────────────────────     │
  한 객체의 좌표 예:                                                  │
    new byte[100]      → SOH / gen0 / 일반 / gen0 리전               │
    new byte[100_000]  → LOH / (gen3, 논리적으로 gen2) / 일반 / LOH 리전 │
    GC.AllocateArray<byte>(100, pinned: true)                        │
                       → SOH 크기 / (gen4) / POH / POH 리전          │
    "리터럴"           → NonGC 힙 (GC 대상 아님)                     │
```

- **① 크기 분할**은 85,000바이트라는 단 하나의 임계값으로 힙을 **소형 객체 힙(SOH)** 과 **대형 객체 힙(LOH)** 으로 물리적으로 갈라놓는다.
- **② 수명 분할**은 SOH **안에서만** 적용된다. 세대 0/1/2가 그것이다. LOH는 논리적으로 세대 2에 속한다.
- **③ 종류 분할**은 고정 객체 힙(POH)과 NonGC 힙(NGCH)이라는 두 개의 특수 영역을 만든다.
- **④ 물리 분할**은 위 논리적 구획들이 실제 가상 주소 공간에 어떤 덩어리로 놓이는가의 문제다. .NET 6까지는 **세그먼트**, .NET 7부터 64비트에서는 **리전**이다.

> **💡 순서를 지켜 읽어라**
>
> 이 네 축은 서로 참조한다. "gen0 리전"이라는 말은 ②와 ④를 동시에 쓰고 있다. 처음 읽을 때는 62.3 → 62.4 → 62.5 → 62.6 순서를 지키는 편이 훨씬 빠르다. 62.7(카드 테이블)은 ②의 부산물이므로 반드시 62.4를 읽은 뒤에 봐야 한다.

## 62.2 프로세스 메모리 영역 — 내 프로그램은 실제로 몇 MB인가

### 답하기 전에 질문을 고쳐야 한다

"우리 애플리케이션이 RAM을 얼마나 쓰나요?"는 고객이 가장 자주 하는 질문이자, 팀에서 가장 자주 싸움이 나는 질문이다. 각자 다른 도구를 켜고 다른 숫자를 들이밀기 때문이다. 작업 관리자, VMMap, 성능 모니터, `top`이 다 다른 숫자를 보여준다.

싸움이 나는 이유는 도구가 틀려서가 아니라 **"메모리 사용량"이라는 단일한 값이 존재하지 않기** 때문이다. 최소한 세 가지를 구별해야 한다.

| 측정치 | Windows 이름 | 의미 | 언제 보는가 |
|---|---|---|---|
| **개인 작업 집합** | Working Set - Private | 이 프로세스가 점유한 **물리 RAM**의 양 | 컨테이너 메모리 한도의 병목. **가장 먼저 볼 것** |
| **개인 바이트(커밋 크기)** | Private Bytes / Commit Size | 물리 RAM + 페이지 파일로 밀려난 것 = **커밋된 전체** | 작업 집합보다 훨씬 크면 과도한 페이징을 의심 |
| **가상 바이트** | Virtual Bytes | 커밋 + **예약만 된 것** 전부 | 32비트에서만 실질적 의미. 64비트에서는 놀라지 말 것 |

61.2절에서 본 **예약(reserve)과 커밋(commit)의 차이**가 여기서 결정적이다. 64비트 .NET은 주소 공간을 테라바이트 단위로 예약한다. 그 숫자를 "메모리 사용량"이라고 보고하면 아무 의미가 없다.

> **⚠️ 가상 바이트가 2TB로 나와도 정상이다**
>
> 64비트 .NET Core는 시작 시점에 거대한 주소 공간을 예약한다. 62.6절에서 보겠지만 .NET 7+ 리전 구현은 기본적으로 **256GB를 예약**한다. 작업 관리자의 "커밋 크기"가 아니라 이 값을 보고 "메모리 누수다"라고 결론 내리는 일이 대단히 흔하다. 예약된 주소 공간은 물리 메모리도 페이지 파일도 소비하지 않는다. 32비트에서만 2GB 한계에 부딪히는지 확인할 가치가 있다.

### VMMap으로 본 .NET 프로세스 전체 지도

Windows에서 SysInternals의 VMMap을 켜고 "Hello World" 수준의 .NET 8 콘솔 앱을 열면 다음과 같은 영역들이 보인다. 아래 수치는 64비트 .NET 8에서 측정된 실제 값이다.

| 영역 유형 | 크기(대략) | 무엇인가 | .NET 관점에서의 의미 |
|---|---|---|---|
| **Free** | ≈ 128 TB | 아직 아무것도 없는 주소 공간 | 64비트 사용자 모드 주소 공간 그 자체 |
| **Shareable** | ≈ 2 GiB | 공유 가능 메모리. 100 MiB 커밋, 물리 상주는 2 MiB | 시스템 관리용. .NET과 무관하니 신경 쓰지 말 것 |
| **Mapped files** | ≈ 4 MiB | 폰트·지역화 파일 등의 매핑 | 런타임이 소비하지만 문제를 일으키지 않는다 |
| **Images** | ≈ 43 MiB | 바이너리 이미지 — 런타임 자체, 참조 어셈블리, 시스템 DLL | 대부분 **공유**되며 개인 작업 집합은 988 KiB뿐 |
| **Stacks** | ≈ 7 MiB | 스레드 스택. Hello World에도 스레드가 5개 | 예약은 7 MiB지만 실제 커밋은 168 KiB |
| **Heap / Private Data** | ≈ 6 MiB 커밋 | 런타임 내부용 네이티브 영역 | **카드 테이블·마크 리스트·문자열 인터닝·JIT 임시 버퍼**가 여기 산다 |
| **Managed Heaps** | 62.6절 참조 | GC 힙 + NonGC 힙 + 도메인 힙들 | **이 장의 주제** |
| **Unusable** | > 2 MiB | 할당 세분성 때문에 못 쓰게 된 자투리 | 61.2절의 64 KiB 세분성이 만든 손실 |

이 표에서 실무적으로 가장 중요한 사실 세 가지를 뽑으면 이렇다.

1. **Images는 거의 공유된다.** 43 MiB가 보여도 이 프로세스가 실제로 차지한 물리 메모리는 1 MiB 미만이다. 같은 머신에서 .NET 프로세스를 10개 띄워도 런타임 DLL은 한 벌만 물리 메모리에 있다.
2. **Heap/Private Data 안에 GC의 보조 자료구조가 있다.** 카드 테이블(62.7절)은 관리 힙이 아니라 여기 산다. 관리 힙 크기가 안정적인데 프로세스 메모리가 늘어나면 이쪽을 봐야 한다.
3. **마지막 두 Private Data 영역은 Execute/Read/Write 보호 플래그를 갖는다.** JIT 컴파일러가 기계어를 뿜어내는 영역이다. 실행 가능해야 하니 Execute 플래그가 붙는다. **애플리케이션이 JIT을 과도하게 하면 이 EXECUTE/READ/WRITE 개인 영역이 계속 자란다.** 62.9절에서 이 패턴을 다시 본다.

### Managed Heaps 안의 구획들

VMMap의 "Managed Heap" 줄을 펼치면 다시 여러 종류가 나온다. 여기가 이 장의 실제 무대다.

```text
Managed Heaps
 │
 ├─ GC Heap ─────────── 이 장의 62.3 ~ 62.8이 전부 여기 이야기다
 │     SOH (gen0/1/2), LOH, POH
 │
 ├─ NonGC Heap ──────── 구 Frozen heap. 읽기 전용 관리 객체
 │     문자열 리터럴, System.Type 인스턴스,
 │     단순 타입의 static readonly 인스턴스
 │
 └─ Domain heaps ────── AppDomain마다 한 벌씩
       ├─ High Frequency Heap  자주 접근하는 타입 메타데이터, 기본 static 데이터
       ├─ Low Frequency Heap   EEClass 등 덜 쓰이는 메타데이터, JIT/리플렉션/타입 로딩용
       ├─ Stub Heap            CAS·COM 래퍼 호출·P/Invoke를 돕는 스텁
       └─ Virtual Call Stub    인터페이스 디스패치(VSD)용
             Cache Entry / Dispatch / Indirection Cell / Lookup / Resolve Heap
```

High Frequency, Low Frequency, Stub, 그리고 여러 Virtual Call Stub 힙을 묶어 **로더 힙(Loader Heap)** 이라고 부른다.

> **⚠️ "로더 힙"이라는 메모리 영역은 존재하지 않는다**
>
> 흔히 듣는 것과 달리 `Loader Heap`이라는 이름의 메모리 영역이 만들어지는 일은 없다. 타입 시스템에 필요한 데이터를 담는 여러 영역을 **묶어 부르는 개념**일 뿐이다. VMMap에서 "Loader Heap"을 찾으려 해도 나오지 않는다.

이 힙들은 기본적으로 아주 작다. .NET Core의 기본 크기 정의는 다음과 같다.

```text
#define LOW_FREQUENCY_HEAP_RESERVE_SIZE        (3 * GetOsPageSize())
#define LOW_FREQUENCY_HEAP_COMMIT_SIZE         (1 * GetOsPageSize())
#define HIGH_FREQUENCY_HEAP_RESERVE_SIZE       (10 * GetOsPageSize())
#define HIGH_FREQUENCY_HEAP_COMMIT_SIZE        (1 * GetOsPageSize())
#define STUB_HEAP_RESERVE_SIZE                 (3 * GetOsPageSize())
#define STUB_HEAP_COMMIT_SIZE                  (1 * GetOsPageSize())
```

페이지 몇 개, 대개 64 KiB 규모다. 수천 개의 인터페이스를 가진 애플리케이션에서도 Virtual Call Stub 힙들은 수백 KiB 정도에 그친다.

> **⚠️ 로더 힙에 올라간 타입은 AppDomain이 언로드될 때까지 내려오지 않는다**
>
> 한번 로드된 타입은 해당 AppDomain이 언로드되기 전까지 로더 힙에서 회수되지 않는다. 그리고 **기본 AppDomain은 프로세스가 죽기 전에는 절대 언로드되지 않는다.** 동적으로 어셈블리를 만들거나 로드하는 코드가 있으면 관리 힙은 멀쩡한데 프로세스 메모리만 계속 자라는 상황이 벌어진다. 62.9절이 이 시나리오다.

### 절차: 내 프로그램은 몇 MB인가

실무 절차로 정리한다. 순서를 지키는 것이 중요하다. 처음부터 힙 덤프를 뜨는 것은 낭비다.

**1단계 — 큰 그림 세 숫자를 시간에 따라 기록한다.**

Windows라면 성능 모니터로 다음 카운터를 기록한다.

```text
\Process(<프로세스명>)\Working Set - Private
\Process(<프로세스명>)\Private Bytes
\Process(<프로세스명>)\Virtual Bytes
\.NET CLR Memory(<프로세스명>)\# Total committed Bytes
```

절대값보다 **추세**가 중요하다. 마지막 카운터가 관리 힙 사용량이므로, 앞의 세 개와 비교하면 문제가 관리 힙 안에 있는지 밖에 있는지 즉시 갈린다.

**2단계 — 크로스 플랫폼이라면 `dotnet-counters`를 쓴다.**

```text
dotnet-counters monitor -p <프로세스 ID>
```

`System.Runtime` 공급자가 다음을 보여준다.

```text
[System.Runtime]
    GC Committed Bytes (MB)                    44.876
    GC Fragmentation (%)                        1.396
    GC Heap Size (MB)                          37.409
    Gen 0 GC Budget (MB)                           16
    Gen 0 Size (B)                                  0
    Gen 1 Size (B)                          2,526,584
    Gen 2 Size (B)                         24,857,672
    LOH Size (B)                              491,712
    POH (Pinned Object Heap) Size (B)          33,760
    Number of Assemblies Loaded                18,570
    Number of Methods Jitted                  129,956
    Working Set (MB)                        1,081.278
```

관리 힙 크기는 `GC Heap Size` 하나로 보는 것이 가장 간단하다. 세대별 카운터를 더해서 총량을 재구성하려 들지 마라 — 위 목록의 `Gen 0 Size (B)`가 0으로 찍혀 있듯 세대별 카운터는 그대로 합산할 수 있는 값이 아니다(바로 아래 상자 참조). `GC Committed Bytes`는 **커밋된** 바이트라서 `GC Heap Size`(살아 있는 객체가 차지한 크기)보다 크며, 그 차이가 프리 리스트와 단편화로 비어 있는 공간이다. 둘을 나란히 보면 `GC Fragmentation (%)`이 어디서 나온 값인지도 함께 읽힌다.

> **⚠️ `Gen 0 Size`를 더하지 마라**
>
> 위 목록에서 `Gen 0 Size (B)`가 0으로 찍힌 것이 보일 것이다. 이 자리의 값은 레거시 사정 때문에 진짜 세대 0 크기가 아니다 — 대응하는 성능 카운터 `Gen 0 heap size`는 세대 0의 크기가 아니라 **할당 예산(allocation budget)** 을 보고하며, `dotnet-counters` 쪽 값도 그대로 믿을 수 없다. 62.4절에서 자세히 다룬다. 어느 쪽이든 세대 0은 총량 합산에서 빼는 것이 맞다.

**3단계 — 관리 힙이 범인이 아니면 VMMap(또는 `dotnet-dump`)으로 내려간다.**

위 표의 영역들을 시간에 따라 관찰해 무엇이 자라는지 찾는다. 자라는 영역별 진단 방향은 다음과 같다.

| 자라는 영역 | 의심 원인 | 다음 도구 |
|---|---|---|
| Heap (Private Data) | 네이티브 힙 API 남용 (`malloc`, C++ `new`) | PerfView의 Heap 공급자로 호출 스택 수집 |
| Private Data + Unusable 폭증 | `VirtualAlloc`을 페이지 단위로 호출 — 64 KiB 세분성 낭비 | PerfView의 VirtAlloc 공급자 |
| Managed Heap의 Domain 1 Low/High Frequency | 동적 어셈블리 누적 | 62.9절 |
| Managed Heap의 GC 영역 | 진짜 관리 누수 | 66장 |
| EXECUTE/READ/WRITE Private Data | 과도한 JIT | JIT 카운터, ReadyToRun 검토 |

### Linux와 컨테이너에서

VMMap은 Windows 전용 도구다. 다른 플랫폼에서는 다음으로 대체한다.

| 목적 | Windows | Linux / 컨테이너 |
|---|---|---|
| 큰 그림 세 숫자 | 작업 관리자, 성능 모니터 | `top`, `/proc/<pid>/status` |
| .NET 카운터 | 성능 모니터의 `.NET CLR Memory` | `dotnet-counters monitor -p <pid>` |
| 메모리 영역 지도 | VMMap | `/proc/<pid>/maps`, `/proc/<pid>/smaps` |
| 힙 덤프 | WinDbg + SOS | `dotnet-dump collect` → `dotnet-dump analyze` |
| GC 이벤트 추적 | PerfView (ETW) | `dotnet-trace` (EventPipe) |

`dotnet-counters`와 `dotnet-dump`는 Windows에서도 동작하므로, **플랫폼을 가리지 않는 진단 절차를 만들고 싶다면 이 둘을 기본으로 삼는 것이 낫다.** SOS 명령(`!eeheap`, `!dumpheap`, `!gcroot`)은 `dotnet-dump analyze` 안에서 그대로 쓸 수 있다.

```text
$ dotnet-dump collect -p 1234
$ dotnet-dump analyze core_20260904_120000
> eeheap -gc
> dumpheap -stat
```

> **⚠️ `dotnet-dump analyze`에서는 `!` 접두사가 없다**
>
> WinDbg에서 `!eeheap`으로 쓰던 것을 `dotnet-dump analyze`에서는 `eeheap`으로 쓴다. `!`를 붙여도 대개 동작하지만, 문서와 명령 형식이 조금씩 다르다는 점을 염두에 두라. 또한 `eeheap`은 인자 없이 쓰면 로더 힙까지 전부 출력하므로, GC 힙만 보려면 `-gc` 옵션을 준다.

> **💡 컨테이너에서는 힙 하드 리밋이 모든 계산을 바꾼다**
>
> 이 장에서 본 리전 예약 크기 계산(`max(물리 메모리 × 2, 256 GB)`)은 `GCHeapHardLimit`가 설정되면 무시된다. 예약 블록이 **한도와 같은 크기**가 되기 때문이다. 컨테이너에서는 런타임이 cgroup 한도를 읽어 하드 리밋을 자동 설정하므로, 같은 애플리케이션이라도 컨테이너 안팎에서 힙 구조가 다르게 잡힌다. 자세한 내용은 65.5절과 65.7절에서 다룬다.

> **📌 Unusable이 37 GB인 실제 사례**
>
> 한 애플리케이션에서 가상 바이트가 40 GB를 넘어갔는데 그중 **약 37 GB가 Unusable**로 잡힌 사례가 있다. 원인은 P/Invoke로 `VirtualAlloc`을 호출하면서 페이지 하나(보통 4 KiB)씩만 할당한 코드였다. Windows의 할당 세분성은 64 KiB이므로 호출 한 번마다 60 KiB가 못 쓰는 자투리로 남았다. 관리 힙은 완벽히 정상이었고 개인 작업 집합도 안정적이었다. 이런 문제는 VMMap의 Unusable 줄을 보지 않으면 절대 찾을 수 없다.

> **💡 컨테이너에서는 개인 작업 집합만 본다**
>
> 컨테이너 메모리 한도에 걸려 OOM Killer에게 죽는 것은 물리 메모리 기준이다. 예약 크기나 가상 바이트는 아무 영향이 없다. 쿠버네티스 환경의 메모리 이슈를 조사할 때는 `Working Set (MB)` 하나만 놓고 시작하고, 그다음에 `GC Committed Bytes`와의 차이를 본다. 그 차이가 크면 관리 힙 밖에 원인이 있다는 뜻이다. GC의 컨테이너 대응(하드 리밋, DATAS)은 65.5절과 65.7절에서 다룬다.

## 62.3 크기 분할 — SOH와 LOH (85,000바이트 경계, double 배열 예외)

### 임계값 하나로 갈리는 두 세계

첫 번째 분할 축은 크기다. 이유는 62.1절에서 말한 대로 **압축 수집 시의 메모리 복사 비용**이다. 100바이트 객체를 옮기는 것과 10 MB 배열을 옮기는 것은 완전히 다른 이야기다.

크기 구간을 여러 개로 나눌 특별한 이유는 없었으므로, 딱 **하나의 임계값**이 선택되었다. GC 힙은 물리적으로 분리된 두 영역으로 나뉜다.

| 힙 | 조건 | 압축 |
|---|---|---|
| **소형 객체 힙(SOH, Small Object Heap)** | 85,000바이트 **미만** 객체 | 압축(compact) 또는 스윕(sweep). Plan 단계에서 결정 |
| **대형 객체 힙(LOH, Large Object Heap)** | 85,000바이트 **이상** 객체 | 기본은 스윕만. 명시적 요청 시 압축 가능 |

로직과 코드의 대부분은 두 힙이 공유하지만, 위 표의 마지막 열이 결정적 차이를 만든다.

- **SOH**는 압축해도 된다. 작은 객체 복사 비용이 낮기 때문이다. 실제로 스윕 수집과 인플레이스 압축 수집이 모두 구현되어 있고, GC의 Plan 단계에서 어느 쪽을 실행할지 결정한다(64.8절).
- **LOH**는 메모리 제약이 없는 환경(즉 메모리 한도가 걸린 컨테이너가 아닌 곳)에서 기본적으로 **스윕만** 한다. 큰 객체 복사 비용 때문이다. LOH 압축을 강제하는 방법은 따로 있다(65.8절).

> **⚠️ 85,000은 85 KiB가 아니다**
>
> 이 임계값을 `85 * 1024 = 87,040`으로 오해하는 사람이 대단히 많다. **정확히 85,000바이트**다. 십진수 85,000이며, 85 KiB(= 87,040)보다 2,040바이트 작다. 게다가 판정에 쓰이는 것은 배열 길이가 아니라 **객체 헤더까지 포함한 전체 크기**다. 64비트에서 배열 하나의 헤더는 24바이트이므로 `new byte[85000]`은 85,024바이트가 되어 LOH로 가고, 경계 바로 아래를 노려 크기를 맞추는 코드는 이 헤더 몫을 빼먹으면 틀린다.
>
> 이 값은 `LOHThreshold` 설정으로 **올릴 수는 있지만 내릴 수는 없다.**

```csharp
using System.Runtime.CompilerServices;

// 85,000 경계를 직접 확인한다 (64비트 기준)
var small = new byte[84_000];
var large = new byte[85_000];

Console.WriteLine(GC.GetGeneration(small));  // 0  → SOH
Console.WriteLine(GC.GetGeneration(large));  // 2  → LOH (논리적으로 gen2)
```

```json
// runtimeconfig.json — 임계값을 100,000바이트로 올린다
{
  "configProperties": {
    "System.GC.LOHThreshold": 100000
  }
}
```

### 왜 하필 85,000인가

공학과 역사가 섞인 답이 나온다. 가장 단순한 답은 이렇다. **.NET 개발 초기에 수많은 테스트를 통해 실험적으로 선택된 값**이다. Microsoft 내부 팀과 외부 팀에서 다양한 시나리오를 모아 측정한 결과 나온 숫자이지, 어떤 우아한 공식에서 유도된 값이 아니다.

> **📌 임계값은 어떤 크기를 재는가**
>
> 85,000바이트는 객체의 **얕은 크기(shallow size)** 에 적용된다. 참조 필드는 그것이 가리키는 객체의 크기가 아니라 **포인터 하나의 크기**로만 센다. 그래서 LOH에 들어가는 것은 사실상 **배열과 긴 문자열**뿐이다. 얕은 크기가 85,000바이트를 넘는 일반 클래스를 상상하기는 어렵다 — 필드를 만 개쯤 선언해야 한다.
>
> 뒤집어 말하면 **거대한 배열을 필드로 가진 객체 자체는 큰 객체가 아니다.** 그 필드는 배열을 가리키는 작은 참조일 뿐이다. 객체는 SOH에, 배열은 LOH에 각각 놓인다.

### 정렬(alignment)의 차이

SOH의 메모리 정렬은 플랫폼에 따라 다르다.

| | SOH 정렬 | LOH 정렬 |
|---|---|---|
| 32비트 런타임 | 4바이트 | **8바이트** |
| 64비트 런타임 | 8바이트 | **8바이트** |

**LOH는 비트 수와 무관하게 언제나 8바이트로 정렬한다.** 64비트에서는 자연스럽지만 32비트에서는 왜일까. 주된 이유는 **double 배열이 8바이트 정렬을 요구하기 때문**이다. 그리고 큰 객체 하나의 크기에 비하면 8바이트 정렬의 낭비는 무시할 만하다.

이 정렬 이야기가 다음 항목의 배경이 된다.

### double 배열 예외 — 32비트 런타임의 특수 규칙

LOH에서 발견할 수 있는 가장 유명한 예외다.

**32비트 .NET 런타임에서는(64비트 머신 위에서 실행되더라도) 원소가 1,000개 이상인 `double[]`이 LOH에 할당된다.**

`double`은 항상 8바이트이므로, 이 규칙은 LOH가 겨우 8,000바이트짜리 배열을 담을 수 있다는 뜻이다. "85,000바이트 이상만 담는다"는 규칙이 정면으로 깨진다.

```csharp
// 32비트 .NET 런타임에서 실행하면 각각 0과 2를 출력한다
double[] array1 = new double[999];
Console.WriteLine(GC.GetGeneration(array1));      // 0  → SOH
double[] array2 = new double[1000];
Console.WriteLine(GC.GetGeneration(array2));      // 2  → LOH
```

왜 이런 이상하고 구체적인 예외가 만들어졌는가. 이유는 다시 정렬이다.

`double`은 8바이트이고, **double에 대한 비정렬 접근(unaligned access)은 대단히 비싸다.** 정수 타입의 비정렬 접근보다 훨씬 비싸다. 64비트 환경은 SOH도 LOH도 8바이트 정렬이므로 문제가 없다. 그러나 **32비트 SOH는 4바이트 정렬**이라 double 배열이 반쪽 정렬 상태로 놓일 수 있다.

그래서 이런 배열을 언제나 8바이트로 정렬되는 LOH에 넣어 큰 배열에서의 비정렬 접근 비용을 피한다.

그렇다면 왜 32비트에서 double 배열을 **항상** LOH에 넣지 않는가. LOH에는 그 나름의 단점이 있기 때문이다. **LOH는 압축되지 않으므로** 작은 객체가 많이 들어오면 원치 않는 단편화가 생긴다. 일정 크기 이상의 배열만 LOH에 넣기로 한 것은 **비정렬 접근 비용과 단편화 비용 사이의 타협**이다. 1,000이라는 임계값 역시 실험적으로 선택되었다.

> **⚠️ 32비트에서 double 배열을 반복 생성하면 LOH가 조각난다**
>
> 1,000개가 넘는 double 배열을 계속 만들고 버리면 그 조각들이 LOH 전체에 흩어진다. LOH는 압축되지 않으므로 이 단편화는 저절로 해소되지 않는다. 이런 상황이면 **재사용 가능한 배열 풀**을 써야 한다. `ArrayPool<double>`이 정확히 이 용도이며 69.3절에서 다룬다.
>
> 64비트 런타임을 쓴다면 이 예외 자체가 적용되지 않는다. 대부분의 신규 애플리케이션은 이 함정을 만나지 않지만, 유지보수 중인 32비트 데스크톱 애플리케이션이나 32비트 응용 프로그램 풀에서 도는 웹 애플리케이션은 여전히 만난다.

### SOH가 다시 쪼개지는 이유

SOH는 압도적으로 붐비는 영역이다. 우리가 만드는 객체 대부분이 85,000바이트보다 작기 때문에, SOH의 객체 수는 LOH보다 보통 **수십~수백 배 이상** 많다.

그런데 객체 수가 많으면 GC 성능이 나빠진다. Mark 단계에서 거대한 그래프를 순회해야 하기 때문이다. 그래서 이 영역을 **더 작은 조각으로 또 나누는** 결정이 내려졌다. 그 기준이 수명이고, 그 결과가 세대다. 62.4절의 주제다.

### LOH는 세대 3이다

LOH는 GC 구현 내부에서 **세대 3**으로 추적된다. 개념은 단순하다. 85,000바이트 이상인 객체를 모아둔다.

> **📌 세대 3인데 왜 `GetGeneration`은 2를 반환하는가**
>
> 수집기 관점에서 **LOH의 큰 객체는 논리적으로 세대 2에 속한다.** 세대 2를 수집할 때만 함께 수집되기 때문이다. 그래서 `GC.GetGeneration`은 LOH 객체에 대해 2를 반환한다.
>
> 런타임 내부는 정보를 **세대 번호(0~4)** 로도, **객체 힙 인덱스(0~2)** 로도 추적한다. 후자는 SOH(0), LOH(1), POH(2)에 대응하고, `gen_to_oh()` 헬퍼 함수가 둘 사이를 변환한다.

LOH 설계에는 **"큰 객체 할당은 드물다"** 는 가정이 깔려 있다. 대부분의 프로그램은 크고 수명이 짧은 자료구조를 많이 필요로 하지 않는다는 것이다. 이 가정이 깨지는 경우가 있다. 대표적인 것이 **거대한 JSON 문자열 페이로드**다. 요청마다 수백 KB짜리 문자열을 만들어 던지면 LOH가 계속 커지고 조각나며, 그때마다 세대 2 수집이 유발되어 성능이 급격히 나빠진다. 이 주제는 63.4절(LOH 할당 경로)과 69장에서 더 다룬다.

> **📌 Mono는 8,000바이트다**
>
> 대안 런타임인 Mono(6.12 기준)의 임계값은 **8,000바이트**다. 그보다 큰 객체는 Mono에서 **LOS(Large Object Space)** 라 불리는 영역에 할당된다. 작은 객체는 **Nursery**에 할당되고 GC에서 살아남으면 **Major Heap**으로 승격된다. .NET과 마찬가지로 작은 객체 공간은 압축될 수 있고 LOS는 스윕으로만 정리된다.

### 실무 — LOH에 무엇이 들어 있는지 확인하기

이론보다 중요한 것은 "내 애플리케이션의 LOH에 실제로 무엇이 있는가"다. 확인 절차는 짧다.

```text
> !dumpheap -stat -min 85000
```

`-min` 옵션으로 크기 하한을 주면 큰 객체만 통계가 나온다. 여기서 보이는 타입은 거의 항상 다음 범주 중 하나다.

| LOH에서 자주 보이는 것 | 왜 생기는가 | 대응 |
|---|---|---|
| `byte[]` | 파일·네트워크 버퍼, 이미지 데이터, 직렬화 버퍼 | `ArrayPool<byte>` (69.3절), 스트리밍 처리 |
| `System.String` | 응답 본문 전체를 문자열로 받는 코드, 거대한 JSON·XML | `Utf8JsonReader`, `Span<char>` 슬라이싱 (69.5절, 69.7절) |
| `char[]` | `StringBuilder`의 내부 청크가 커진 경우 | 초기 용량 지정, `string.Create` |
| `Object[]` / `T[]` | `List<T>`가 계속 자라 내부 배열이 재할당된 경우 | 생성 시 용량 지정 |
| 익명 타입 배열, 딕셔너리 버킷 | 해시 테이블 리사이즈 | 예상 크기로 초기화 |

> **⚠️ `List<T>`는 조용히 LOH로 넘어간다**
>
> `List<T>`는 내부 배열이 가득 차면 **용량을 두 배로 늘려 새 배열을 할당하고 복사**한다. 64비트에서 참조 원소 하나가 8바이트이므로, 원소 1만 개를 조금 넘는 지점부터 내부 배열이 85,000바이트 경계를 넘어 **LOH로 넘어간다**(용량이 2의 거듭제곱으로 자라므로 실제로는 16,384 용량 단계에서 넘어간다). 그 뒤로는 리사이즈할 때마다 LOH에 더 큰 배열이 하나씩 생기고, 직전 배열은 LOH 쓰레기가 된다.
>
> 최종 크기를 대략이라도 안다면 `new List<T>(capacity)`로 시작하는 것만으로 이 문제 대부분이 사라진다. 62.3절의 내용 중 실무에서 가장 자주 돌려주는 것이 이 한 줄이다.

> **💡 LOH를 만나면 먼저 "안 만드는 길"을 찾아라**
>
> LOH 문제의 해결책 순서는 거의 항상 같다. ① 애초에 큰 배열을 만들지 않는다(스트리밍 처리, `Span<T>` 슬라이싱), ② 만들어야 한다면 재사용한다(`ArrayPool<T>`, `RecyclableMemoryStream` — 69.3절, 69.4절), ③ 그래도 안 되면 LOH 압축을 켠다(65.8절). `LOHThreshold`를 올려 문제를 SOH로 밀어 넣는 것은 마지막 수단이며, 대개는 SOH 압축 비용을 늘려 상황을 악화시킨다.

## 62.4 수명 분할 — 세대(0/1/2)와 세대 가설

### 수명을 어떻게 잴 것인가

SOH를 수명으로 나누기로 했다면 다음 질문은 "수명을 무엇으로 재는가"다. 두 가지 방법이 있다.

| 방식 | 재는 법 | 문제 |
|---|---|---|
| **절대 시간** | 객체 생성 이후 흐른 CPU 클럭 틱 수 | "긴 수명"이 몇 초인가? 프로그램마다 다르다. 자기 학습 메커니즘을 만들 수는 있지만 과도하게 복잡해진다 |
| **상대 시간** | 특정 사건(가비지 컬렉션)을 기준으로, 이 객체가 **GC를 몇 번 살아남았는가** | 단순하고 프로그램 특성에 자동으로 적응한다 |

.NET은 **상대 시간**을 택했다. 규칙은 한 문장으로 끝난다.

> **객체가 가비지 컬렉션에서 살아남으면 다음 세대로 승격된다.**

> **📌 세 번째 방법도 상상할 수 있다**
>
> 수집기와 할당자가 "객체를 절대 더 낮은 주소로 옮기지 않는다"는 성질을 갖도록 설계한다면, 객체의 나이를 **주소의 차이**로 계산할 수도 있다. 실제로 채택된 방식은 아니지만, 수명 측정이 시간에만 의존할 이유가 없다는 것을 보여주는 예다.

### 세대 가설 — 왜 이게 통하는가

"세대별 GC"라는 말은 어디서나 들리지만, 왜 나이로 객체를 나누고 다르게 취급하는 것이 합리적인지를 설명하는 글은 드물다. 근거는 **세대 가설(generational hypothesis)** 이라는 관찰이다. 강약 두 버전이 있고, 둘을 합친 것이 세대별 GC의 토대다.

| 가설 | 내용 | 검증 상태 |
|---|---|---|
| **약한 세대 가설**<br>(영아 사망, infant mortality) | 대부분의 젊은 객체는 짧게 산다. 프로그램이 할당하는 객체 대부분은 금방 쓸모없어진다 | 여러 컴퓨터 과학 연구에서 **폭넓게 확인**됨 |
| **강한 세대 가설** | 객체가 오래 살아왔을수록 앞으로도 계속 살 가능성이 높다 | **완전히 확인되지는 않음.** 객체 수명 특성은 이보다 훨씬 복잡하고, 이 가설에 대한 보편적 정의조차 없다 |

약한 가설의 대상은 지역 변수로 표현되는 임시 객체, 컴파일러가 숨겨 만든 할당, 짧게 끝나는 처리 과정에서 생긴 것들이다. 강한 가설의 대상은 오래 사는 캐시, "매니저", "헬퍼", 객체 풀, 비즈니스 워크플로 같은 것들이다.

인간의 삶에 비유하면 반직관적이다. 사람은 태어난 직후에 가장 많이 죽지 않는다. 그러나 프로그램 객체는 그렇다.

**여기서 이득이 나온다.** 대부분의 젊은 객체가 금방 죽는다면, 젊은 객체를 "젊은 세대"로 분리해 **자주** 회수하는 것이 이득이다. 오래된 객체가 거의 안 죽는다면, 오래된 객체를 "늙은 세대"로 분리해 **훨씬 덜 자주** 회수하는 것이 이득이다. 물론 그 사이에 중간 세대를 몇 개든 둘 수 있다.

### 승격을 구현하는 두 가지 방법

객체를 세대별로 묶었다면 "승격"이 실제로 무엇을 의미하는지가 남는다. 구현 방식이 두 가지이고, 이것이 GC 구현마다 성격이 갈리는 지점이다.

**(가) 복사 방식** — 세대마다 별도의 메모리 영역을 두고 승격 시 객체를 **복사**한다.

```text
(a) 실행 초기          (b) GC 발생, A는 도달 불가        (c) D 할당
   ┌─────┐              ┌─────┐                        ┌─────┐
gen0│A B C│           gen0│     │                    gen0│D    │
   └─────┘              └─────┘                        └─────┘
   ┌─────┐              ┌─────┐   B,C를 복사           ┌─────┐
gen1│     │           gen1│B C  │◄──────                gen1│B C  │
   └─────┘              └─────┘                        └─────┘
   ┌─────┐              ┌─────┐                        ┌─────┐
gen2│     │           gen2│     │                    gen2│     │
   └─────┘              └─────┘                        └─────┘
```

Mono가 이 방식이다. Nursery에서 살아남은 객체를 old generation으로 복사한다.

**(나) 논리 경계 방식** — 하나의 연속된 메모리 블록을 두고, 세대를 **주소 경계**로만 정의한다. 승격은 객체를 옮기는 것이 아니라 **경계를 옮기는 것**이다.

```text
(a) 실행 초기
  ┌──────────────────────────────────────┐
  │ A    B    C                          │
  └──────────────────────────────────────┘
  └gen2┘└gen1┘└──────── gen0 ────────────┘   gen1/gen2는 크기 0에 가깝다

(b) GC 발생 — A는 도달 불가, 스윕으로 회수. B와 C는 살아남아 gen1이 된다
  ┌──────────────────────────────────────┐
  │ ····  B    C                         │
  └──────────────────────────────────────┘
  └gen2┘└─── gen1 ───┘└──── gen0 ────────┘   경계만 옮겼다. 복사 없음

(c) D 할당 → 항상 gen0에
  ┌──────────────────────────────────────┐
  │ ····  B    C    D                    │
  └──────────────────────────────────────┘
  └gen2┘└─── gen1 ───┘└──── gen0 ────────┘

(d) 다시 GC — B가 도달 불가. 경계 재조정: D는 gen1로, C는 gen2로
  ┌──────────────────────────────────────┐
  │ ····  ····  C    D                   │
  └──────────────────────────────────────┘
  └── gen2 ────┘└gen1┘└──── gen0 ────────┘
```

**경계를 갱신하는 데는 사실상 시간이 들지 않으므로 복사 방식보다 훨씬 빠르다.** 살아남은 객체를 압축할 수도, 하지 않을 수도 있다(압축하면 구현이 훨씬 복잡해진다). .NET 런타임이 채택한 것이 이 방식이다.

### .NET의 세대 구성

.NET은 세대를 **세 개** 만들었고, 이름은 그냥 연속된 숫자다.

| 세대 | 별칭 | 무엇이 있는가 | 얼마나 자주 수집되나 |
|---|---|---|---|
| **0** | 젊은 세대, ephemeral | 새로 할당된 객체. GC가 한 번도 검사하지 않은 것 | 가장 자주 |
| **1** | 완충 세대, ephemeral | gen0 GC를 한 번 살아남은 객체 | 중간 |
| **2** | 늙은 세대 | gen1 GC까지 살아남은 객체. 오래 사는 캐시·정적 데이터 | 가장 드물게 |
| (3) | LOH | 85,000바이트 이상 객체. 논리적으로 gen2 | gen2와 함께 |
| (4) | POH | 고정 객체 힙 (62.5절) | gen2와 함께 |

세대 0과 1을 합쳐 **ephemeral 세대(임시 세대)** 라고 부른다. 이 용어는 GC 구현 곳곳에 등장하며 62.7절의 쓰기 장벽 코드에서도 다시 만난다.

객체가 세대 N의 수집을 살아남으면 세대 N+1에 속하게 된다. 즉 **gen0 GC 한 번과 gen1 GC 한 번을 겪으면 세대 2에 도달**할 수 있고, 그 뒤로는 필요 없어질 때까지 거기 머문다.

> **⚠️ 승격에는 예외가 있다 — 강등(demotion)**
>
> "살아남으면 승격"에는 예외가 있다. 승격되지 않거나 오히려 **강등(demotion)** 되는 경우가 있다. 대표적 원인은 고정(pinning)이다. 고정된 객체 때문에 압축이 불가능해지면 GC는 해당 영역의 객체를 원래 세대로 되돌릴 수 있다. 이 메커니즘은 Plan 단계와 밀접하게 얽혀 있어 64.6절에서 다룬다. .NET 7+ 리전 구현이 도입한 **동적 승격·강등(DPAD, Dynamic Promotion And Demotion)** 도 이 범주다.

### 수집 범위 — 왜 "gen1만"은 없는가

수집기가 어떤 세대를 수집할지 결정할 때, 가능한 조합은 다음 셋뿐이다.

- 세대 **0만**
- 세대 **0과 1**
- 세대 **0, 1, 2와 LOH** (전체 가비지 컬렉션, full GC)

"세대 1만 수집" 같은 것은 없다. Microsoft 문서의 표현대로 **"한 세대를 수집한다는 것은 그 세대와 그보다 젊은 모든 세대를 수집하는 것"** 이다.

왜인가. 62.7절에서 자세히 볼 텐데, 짧게 말하면 **늙은→젊은 참조를 추적하는 자료구조만 존재하고 젊은→늙은 참조를 추적하는 자료구조는 없기 때문**이다. 후자까지 구현하는 것은 비용이 너무 커서, 대신 "젊은 세대를 항상 함께 수집한다"는 단순한 결정을 내린 것이다.

### 세대 크기를 관찰하는 법

**세대 크기 관찰은 메모리 누수 여부를 확인하는 가장 쉬운 방법**이다. 세 가지 경로가 있고 모두 **GC 직후의 힙 상태**를 잰다.

| 세대 | GC 이벤트 (`GCHeapStats_V2`) | 성능 카운터 (`\.NET CLR Memory(<프로세스명>)`) / `dotnet-counters` |
|---|---|---|
| 0 | `GenerationSize0` | `Gen 0 heap size` ("할당 예산") / `Gen 0 Size (B)` |
| 1 | `GenerationSize1` | `Gen 1 heap size` / `Gen 1 Size (B)` |
| 2 | `GenerationSize2` | `Gen 2 heap size` / `Gen 2 Size (B)` |
| 3 (LOH) | `GenerationSize3` | `Large Object Heap size` / `LOH Size (B)` |
| 4 (POH) | `GenerationSize4` | `Pinned Object Heap size` / `POH (Pinned Object Heap) Size (B)` |

주의할 점이 두 가지 있다.

> **⚠️ `Gen 0 heap size` 카운터는 세대 0의 크기가 아니다**
>
> 레거시 사정 때문에 이 카운터는 진짜 세대 0 크기가 아니라 **할당 예산(allocation budget)** 을 보여준다. 할당 예산이란 "해당 세대에 이만큼 할당되면 GC를 트리거한다"는 바이트 수다(63.6절). 이 카운터를 세대 0 크기로 읽으면 잘못된 결론에 도달한다. 세대 0 크기를 정말 추적해야 한다면 ETW(`GCHeapStats_V2` 이벤트)를 써야 한다.

> **⚠️ 성능 모니터의 최대 샘플링 주기는 1초다**
>
> 밑단 데이터가 아무리 자주 갱신되어도 성능 모니터는 초당 한 번까지만 표본을 딴다. 1초 안에 GC가 여러 번 일어나면 화면의 증가폭이 실제보다 크게 보인다. 다행히 자주 수집되는 세대 0과 1은 대체로 작아서 큰 문제가 되지 않는다.

### 시나리오 — 이 프로그램은 건강한가

**상황.** 웹 애플리케이션의 부하 테스트 중 세대 크기를 관찰해 메모리 누수를 미리 잡아내고 싶다. 침습적이지 않은 방법이어야 한다. 대상은 오픈 소스 전자상거래 플랫폼 nopCommerce의 기본 설치본이고, 초당 약 7건의 요청을 **170분** 동안 보낸다.

**절차.** 먼저 62.2절의 큰 그림 카운터 네 개를 기록한다. 그다음 위 표의 세대별 카운터를 붙인다. 결과 요약은 다음과 같았다.

| 세대 | 최소(바이트) | 최대(바이트) | 판정 |
|---|---|---|---|
| 0 | 4,194,300 | 6,291,456 | 두 값 사이를 계속 오간다. 실제로는 할당 예산이지만 **안정적**이라는 신호 |
| 1 | 18,268 | 7,384,704 | 중간 세대라 변동이 크다. **상승 추세가 없으므로** 건강하다 |
| 2 | 52,654,336 | 447,385,748 | 톱니 모양. 오래된 객체가 쌓이다 가끔 회수된다 |
| LOH | 36,000 | 38,826,368 | 완만한 증가 |

**해석.** 세대 2의 톱니 패턴을 보고 놀랄 필요는 없다. GC는 전체 가비지 컬렉션을 정말 필요할 때까지 미루므로 **가장 오래된 세대에 객체가 누적되는 것은 정상**이다. 웹 애플리케이션에서는 상당수 객체의 도달 가능성이 사용자 세션 수명과 데이터 캐싱에 묶여 있어 더욱 그렇다.

봐야 할 것은 **최대치의 추세**다. 세대 2의 최댓값이 시간이 갈수록 계속 커진다면 문제 신호이고, 더 긴 기간 관찰해야 한다. 또한 `% Time in GC` 카운터를 함께 봐서 GC가 프로세스 전체에 주는 부담을 확인해야 한다(65.3절).

**판정: 건강함.** 세대 0과 1이 모두 작으므로 그쪽 변동은 신경 쓸 필요가 없다. **메모리 누수는 거의 항상 가장 오래된 세대의 지속적 증가로 나타난다.** 오래 사는 객체가 계속 늘어나기 때문이다.

> **📌 ETW와 성능 카운터의 차이를 눈으로 보기**
>
> 성능 카운터는 초당 한 번 표본을 뜨지만 `GCHeapStats_V2` 이벤트는 **모든 GC의 끝에서** 발생하므로 빠짐이 없다. 위 부하 테스트에서 20초 구간만 확대해 두 데이터를 겹쳐보면 이렇게 갈린다.
>
> - **세대 0**: 두 데이터가 완전히 다르다. 앞서 말한 할당 예산 문제 때문이다.
> - **세대 1**: 카운터 표본 일부가 ETW 데이터와 일치하지만, 그 사이에 훨씬 많은 일이 벌어진다. 세대 1의 변화가 얼마나 역동적인지 보인다.
> - **세대 2**: 두 데이터가 거의 완전히 일치한다. 전체 GC가 워낙 드물어 놓치는 표본이 거의 없다.
>
> PerfView의 저부담 "GC Collect Only" 옵션으로 수집한 뒤 CSV로 내보내면 직접 확인할 수 있다.

### 세대를 눈으로 확인하기

세대 승격은 추상적으로만 이해하기 쉬운 주제라 직접 관찰해보는 편이 낫다.

```csharp
using System;

class Probe { public byte[] Payload = new byte[64]; }

class Program
{
    static void Main()
    {
        var alive = new Probe();      // 계속 참조를 유지한다

        Console.WriteLine($"생성 직후:      gen {GC.GetGeneration(alive)}");

        GC.Collect(0, GCCollectionMode.Forced, blocking: true);
        Console.WriteLine($"gen0 GC 후:     gen {GC.GetGeneration(alive)}");

        GC.Collect(1, GCCollectionMode.Forced, blocking: true);
        Console.WriteLine($"gen1 GC 후:     gen {GC.GetGeneration(alive)}");

        GC.Collect(2, GCCollectionMode.Forced, blocking: true);
        Console.WriteLine($"gen2 GC 후:     gen {GC.GetGeneration(alive)}");

        Console.WriteLine($"MaxGeneration:  {GC.MaxGeneration}");   // 2
        Console.WriteLine($"gen0 수집 횟수: {GC.CollectionCount(0)}");
        Console.WriteLine($"gen2 수집 횟수: {GC.CollectionCount(2)}");

        GC.KeepAlive(alive);
    }
}
```

출력은 대체로 `0 → 1 → 2 → 2`가 된다. 세대 2가 최대이므로 그 이상으로는 올라가지 않는다.

> **⚠️ 이런 코드를 실제 애플리케이션에 넣지 마라**
>
> `GC.Collect`를 명시적으로 호출하는 것은 학습과 진단 목적에서만 정당하다. 실행 코드에서는 GC의 자기 조율(self-tuning)을 망가뜨린다. 특히 `GC.Collect(2)`는 전체 가비지 컬렉션을 강제하므로, 습관처럼 넣으면 애플리케이션 처리량이 눈에 띄게 떨어진다. `GC.Collect`의 정당한 사용 사례는 65.8절에서 다룬다.
>
> 또한 `GC.CollectionCount(N)`은 **N세대 이상의 수집 횟수**를 반환한다는 점에 주의하라. gen2 수집도 gen0 수집 횟수에 포함된다.

### 세대별 GC의 대가

세대별 GC에는 뚜렷한 단점이 하나 있다. **세대 가설이 그 토대인 만큼, 애플리케이션이 가설을 위반하면 심하게 불리한 동작이 나온다.**

가장 유명한 위반 패턴이 **중년기 위기(mid-life crisis)** 다. 객체가 "죽기에는 너무 오래 살고, 승격되기에는 너무 짧게 사는" 구간에 몰리는 경우다. 이런 객체들은 gen0에서 gen1로, gen1에서 gen2로 계속 복사·승격된 뒤 곧바로 쓰레기가 된다. 젊은 세대 GC의 비용은 다 치르면서 이득은 하나도 못 얻는 최악의 패턴이다. 식별과 해소는 66.12절에서 다룬다.

여기서 중요한 결론이 나온다. **세대 가설에 부합하는 건강한 시스템에서는 세대가 늙을수록 덜 자주 수집되어야 한다.** 이 관계가 뒤집혀 있다면 무언가 잘못된 것이다.

> **💡 세대 크기만 보지 마라**
>
> 세대 2의 크기가 안정적인데도 그 안에서 객체가 격렬하게 교체되는(churn) 상황이 있을 수 있다. 크기는 그대로인데 세대 2 GC에 시간을 다 쓰는 것이다. 그래서 세대 크기 관찰과 **CPU 오버헤드 관찰(`% Time in GC`)** 은 항상 함께 해야 한다. 이것이 다음 규칙의 핵심이다.

> **💡 Rule 11 — 세대 크기를 관찰하라**
>
> **근거.** 약한 세대 가설이 .NET 런타임에 구현된 세대별 GC의 토대다. 흔치 않은(또는 잘못된) 객체 생성 패턴 때문에 이 가설을 위반하는 프로그램은 GC 성능에 심각한 영향을 받을 수 있다.
>
> **적용 방법.** 세대 0·1·2와 LOH의 크기가 시간에 따라 어떻게 변하는지 측정하라. 주의를 끌어야 할 잘못된 거동은 둘이다. ① **한 세대 이상이 계속 자란다** — 그것이 오랜 시간에 걸쳐 천천히, 많은 GC 뒤에 벌어지더라도 마찬가지다. 메모리 누수의 신호다. ② **한 세대 이상이 아주 빈번하게 변한다** — 승격과 사망으로 인한 큰 메모리 트래픽의 신호이며, 비싼 가비지 컬렉션을 유발한다.
>
> 다만 세대 크기 자체가 유일한 측정치는 아니다. 위에서 말한 churn 때문에, **CPU 오버헤드 측정(`% Time in GC` 카운터)이 세대 크기 관찰만큼은 중요하다.**

## 62.5 종류 분할 — POH(고정 객체 힙), NonGC 힙

크기와 수명이라는 두 축 외에, .NET은 특수한 성질을 가진 객체를 위해 두 개의 영역을 더 만들었다. 하나는 **절대 움직이지 않는 객체**를 위한 것이고, 다른 하나는 **절대 죽지 않는 객체**를 위한 것이다.

| 영역 | 정식 이름 | 도입 | 담는 것 | GC 대상 |
|---|---|---|---|---|
| **POH** | Pinned Object Heap | ※.NET 5 | 처음부터 고정된 blittable 타입 배열 | 그렇다 (내부 세대 4) |
| **NGCH** | NonGC Heap (구 Frozen heap) | ※.NET 8에 정식 명명 | 문자열 리터럴, 런타임 타입 객체 등 읽기 전용 객체 | **아니다** |

### 고정 객체 힙(POH)이 존재하는 이유

60.8절에서 본 것처럼 고정(pinning)은 GC가 객체를 옮기지 못하게 막는 것이다. P/Invoke로 네이티브 코드에 버퍼 주소를 넘기려면 그동안 객체가 움직이면 안 되므로 반드시 필요하다.

문제는 **오래 사는 고정 객체가 힙 여기저기 흩어져 있으면 GC 일을 방해한다**는 것이다. 압축 단계에서 고정 객체 주위를 피해 다녀야 하므로 단편화가 유발된다(64.7절).

여기서 특정 시나리오가 눈에 들어온다. **만들자마자 곧바로 고정할 목적으로 할당되는 객체들**이다. 이런 것들은 애초에 일반 gen0이 아닌 별도 영역에 직접 할당하는 편이 훨씬 효율적이다. 그것이 POH다.

```csharp
// ※.NET 5 — 처음부터 고정된 배열을 만든다
byte[] buffer = GC.AllocateArray<byte>(4096, pinned: true);

// 초기화(0으로 채우기)를 건너뛰는 버전 — 어차피 덮어쓸 버퍼라면 이쪽
byte[] fast = GC.AllocateUninitializedArray<byte>(4096, pinned: true);

Console.WriteLine(GC.GetGeneration(buffer));   // 2  (내부적으로는 세대 4)
```

두 메서드 모두 마지막 `bool` 매개변수로 할당자에게 "이 배열은 고정 상태여야 한다"고 알린다.

> **📌 목표는 커널 호출용 버퍼 풀이었다**
>
> POH 설계의 목표 시나리오는 **P/Invoke 호출에 쓰는 고정 버퍼 풀**의 구현이었다. ASP.NET Core의 Kestrel 서버, 그리고 `System.Net.Sockets`의 비동기 네이티브 버퍼 최적화가 실제 사용처다. 이런 버퍼는 언제나 바이트 배열이다.

### POH의 제약 — blittable 배열만

POH 설계 과정에서 **blittable 타입 배열만 지원**하기로 결정되었다. blittable이란 참조 타입 필드를 포함하지 않는 타입을 말한다(60.3절). 즉 클래스 배열이나 참조를 포함하는 타입의 배열은 POH에 할당할 수 없다.

```csharp
// 컴파일은 되지만 런타임에 System.ArgumentException이 난다
var bad = GC.AllocateArray<string>(10, pinned: true);
// 메시지: Cannot use type 'System.String'.
//         Only value types without pointers or references are supported.
```

이 검사는 `System.Private.CoreLib`의 관리 코드에서 `RuntimeHelpers.IsReferenceOrContainsReferences<T>()`를 호출해 수행된다.

> **⚠️ .NET 8에서 이 검사가 사라졌다 — 그래도 의존하지 마라**
>
> ※.NET 8에서 관리 코드 쪽 검사가 제거되었다. 그리고 실제 할당을 담당하는 CLR의 네이티브 코드는 이 조건을 다시 확인하지 않으므로, 참조 타입 배열이 POH에 할당되는 것을 받아들인다.
>
> 이것은 **설계상의 보장이 아니라 구현 상태**다. 참조를 담은 배열을 POH에 넣으면 GC가 그 배열 안의 참조를 추적해야 하는데, POH의 설계 전제와 어긋난다. 런타임 버전이 올라가면서 다시 막힐 수도 있다. **런타임 버전에 따라 예외가 나기도 하고 안 나기도 하는 코드**를 작성하지 마라.

> **⚠️ POH는 고정 문제의 해결책이지 만능이 아니다**
>
> POH는 "만들자마자 고정하고 오래 쓰는 버퍼"에만 맞다. 짧게 쓰고 버리는 버퍼를 POH에 넣으면 압축되지 않는 영역에 쓰레기를 쌓는 셈이라 오히려 나쁘다. 일반적인 임시 버퍼는 `ArrayPool<T>`(69.3절)나 `stackalloc`(63.7절)이 맞다.

### POH 안에 있는 CLR 자신의 데이터

POH에는 우리가 만든 버퍼만 있는 것이 아니다. **런타임 자신도 내부 데이터를 여기 저장한다.** 그 통로가 `PinnedHeapHandleTable`이라는 자료구조다.

`PinnedHeapHandleTable`은 런타임이 자기 목적으로 POH에 할당한 객체 배열들을 관리한다. 구조는 다음과 같다.

```text
 PinnedHeapHandleTable
   │
   ├─ bucket #1 ──┬─ m_pArrayDataPtr ───► ┌──────────────────────┐
   │              │                       │ Object[]  (POH 안)    │
   │              ├─ m_currentPos = 37    │ [0][1][2] ... [n]     │
   │              │                       └──────────────────────┘
   │              └─ m_pNext ─┐              고정 핸들로 붙잡혀 있다
   │                          │
   ├─ bucket #2 ◄─────────────┘
   │      ...
   └─ (마지막 bucket의 m_pNext = null)
```

- **각 bucket은 POH에 할당된 `Object[]` 배열 하나**를 나타낸다.
- 이 배열들은 고정되어 있어 GC가 절대 옮기지 않는다. **CLR의 비관리 부분이 배열 원소의 주소를 직접 들고 있기 때문**이다. GC가 옮긴다면 그 포인터를 전부 갱신해야 하는 불필요한 작업이 생긴다.
- 각 bucket은 편의상 배열 데이터의 시작 포인터(`m_pArrayDataPtr`)와 아직 쓰지 않은 원소의 현재 인덱스(`m_currentPos`)를 함께 들고 있다. 배열은 여유 공간을 두고 미리 만들어진다.
- 원소를 다 쓰면 새 bucket이 생긴다. 즉 **POH에 새 `Object[]`가 하나 더 할당된다.**
- bucket들은 `m_pNext` 포인터로 단일 연결 리스트를 이룬다.

주 용도는 두 가지다.

1. **전역 문자열 리터럴 맵**(문자열 인터닝 풀) — 하나의 `PinnedHeapHandleTable`이 관리하며 최소 한 개의 bucket을 갖는다.
2. **도메인별 정적 필드 저장소** — `BaseDomain`의 `PinnedHeapHandleTable`이 관리하며 역시 최소 한 개의 bucket을 갖는다.

여기에 하나 더 있다. 리플렉션 관련 데이터다. `GetType`, `typeof`를 비롯한 리플렉션 API를 쓰면 그 밑의 `RuntimeType`과 관련 정보도 이 핸들 테이블을 통해 저장된다. 그래서 POH를 덤프하면 타입 관련 객체가 꽤 많이 보인다.

> **📌 SystemDomain의 핸들 테이블은 쓰이지 않는다**
>
> `SystemDomain`도 `BaseDomain`을 상속하므로 `m_pPinnedHeapHandleTable` 필드를 갖고 있지만 사용되지 않는다. System Domain에는 관리 모듈이 없어 정적 멤버가 필요 없기 때문이다.

> **📌 .NET 7 이전에는 LOH에 있었다**
>
> 이 내부 데이터는 .NET 7 이전에는 `LargeHeapHandle` 구조를 통해 **LOH**에 저장되었다. 저장 위치를 제외한 나머지 설명은 그대로 적용된다. 옛 버전의 힙 덤프에서 LOH에 정체 모를 `Object[]`가 보이는 이유가 이것이다.

### WinDbg로 POH 들여다보기

`!eeheap` 명령으로 GC 관련 메모리 영역을 나열한 뒤, POH의 주소 범위를 `!dumpheap`에 넘긴다.

```text
> !eeheap
...
Pinned object heap
         segment            begin        allocated        committed allocated size   committed size
    0257b989ec40     0217a5c00028     0217a5c07ff0     0217a5c11000     0x7fc8 (32712)  0x11000 (69632)

> !dumpheap 217a5c00028 0217a5c07ff0
         Address               MT           Size
    0217a5c00028     7ff7c58dc470          8,184
    0217a5c02020     7ff7c58dc470          8,184
    0217a5c04018     7ff7c58dc470         16,344
```

`7ff7c58dc470`은 `Object[]`의 메서드 테이블 주소다. 단순한 "Hello world" 콘솔 프로그램인데도 **`Object[]` 배열이 세 개** 있다.

1. Domain 1의 핸들 테이블 (대부분의 라이브러리·모듈과 우리 프로그램이 여기 속한다)
2. 문자열 인터닝 풀
3. Shared Domain의 핸들 테이블 (단순 콘솔 앱이라면 `System.Private.CoreLib.dll` 모듈만 담긴다)

> **⚠️ 어떤 배열이 어떤 용도인지 알아내는 직접적인 방법은 없다**
>
> 현재로서는 각 배열의 내용을 `!dumparray`로 하나씩 들여다보며 추정하는 수밖에 없다. 인터닝 풀이라면 인터닝된 문자열 참조가 들어 있고, 나머지 둘은 주로 라이브러리와 우리 코드의 정적 멤버가 들어 있다.

`PinnedHeapHandleTable`이 실무에서 문제가 되는 일은 드물다. 문제가 되려면 정적 멤버를 동적으로 대량 생성하거나, 동적 AppDomain을 아주 많이 로드하거나, 문자열을 대량으로 인터닝해야 한다. **오직 고정 핸들만이 루트인 커다란 `Object[]`가 POH에 잔뜩 보인다면** 그 드문 상황에 들어선 것일 수 있다. 다만 이 배열들은 참조만 담으므로, 실제 객체들이 다른 곳에서 먼저 눈에 띄는 것이 보통이다.

### NonGC 힙(NGCH) — 죽지 않는 객체를 위한 곳

초기 문서와 소스 코드 일부에서는 이것을 **Frozen heap(고정 힙)** 이라고 부른다. 여기 담기는 것은 이런 것들이다.

- **64K 미만의 `readonly` 문자열 리터럴**
- `typeof()`나 `GetType()`이 반환하는 **런타임 타입 객체**
- 단순 타입(예: `Object`나 단순 타입 배열)의 **`static readonly` 인스턴스**

이 객체들은 **영원히 산다.** 그러니 가비지 컬렉터의 감시 대상 밖에 두는 것이 합리적이다. 그래서 이름이 NonGC 힙이다.

```csharp
// 문자열 리터럴은 NonGC 힙에 있다 (64K 미만인 경우)
string literal = "hello";

// ※.NET 8에서는 int.MaxValue를 출력한다
Console.WriteLine(GC.GetGeneration(literal));
```

> **⚠️ `GC.GetGeneration`의 반환값이 .NET 8에서 바뀌었다**
>
> NonGC 힙 객체에 대해 **.NET 8 이전에는 2를 반환**했지만, **※.NET 8부터는 `0x7FFFFFFF`(= `int.MaxValue`)를 반환**한다. 세대 번호를 정수로 비교하는 진단 코드나 테스트 코드가 있다면 .NET 8로 올리는 순간 조용히 깨진다. `GC.MaxGeneration`(= 2)과 비교하는 코드가 특히 위험하다.

> **📌 64 KB를 넘는 문자열은 어디로 가는가**
>
> 필요한 크기가 64 KB보다 크면 NonGC 힙에 할당되지 않는다. **85,000바이트 미만이면 gen0에, 이상이면 LOH에** 일반 객체로 할당된다. 즉 아주 긴 리터럴 문자열은 "영원한 객체" 취급을 받지 못한다.

### NonGC 힙의 뿌리 — 읽기 전용 세그먼트

NonGC 힙에는 긴 역사가 있다. 원래 세그먼트에는 네 가지 유형이 있었다.

| 세그먼트 유형 | 상태 |
|---|---|
| Small Object Heap | 현역 |
| Large Object Heap | 현역 |
| **Read-Only Heap** | .NET Framework 3.5부터, 그리고 .NET Core에서 **폐기**. .NET Native만 사용 |
| Pinned Object Heap | ※.NET 5부터 |

읽기 전용 힙 세그먼트는 **객체 동결(object freezing)** 기능이 쓰던 것이다. 어셈블리에 `StringFreezingAttribute`를 붙이고 Ngen.exe로 네이티브 이미지를 만들면, 모든 문자열 리터럴이 관리 객체 형태 그대로 이미지에 미리 컴파일된다. 그 문자열들이 놓인 이미지 안의 메모리 영역을 읽기 전용 세그먼트로 등록하면 **할당 없이 즉시 사용 가능**해진다.

문자열 인터닝(35.5절)과의 차이가 여기 있다. 인터닝은 런타임에 정규 문자열 할당을 요구하지만, 동결은 그것조차 없다.

> **⚠️ 동결된 문자열이 있는 네이티브 이미지는 언로드되지 않는다**
>
> Microsoft 문서의 경고 그대로다. 힙의 어떤 객체든 동결된 문자열을 참조할 수 있으므로, CLR은 동결 문자열을 가진 네이티브 이미지를 **언로드할 수 없다.** 그래서 `StringFreezingAttribute`는 해당 네이티브 이미지가 아주 많이 공유되는 경우에만 쓰라고 권고된다.

**※.NET 8부터 읽기 전용 세그먼트는 공식적으로 NonGC 힙이라고 불린다.** 다만 ETW 이벤트와 소스 코드에는 옛 이름이 여전히 남아 있다. `GCCreateSegment` 이벤트의 `GCSegmentType` 페이로드는 `SmallObjectHeapMapMessage`, `LargeObjectHeapMapMessage`, `PinnedObjectHeapMapMessage`, 그리고 `ReadOnlyHeapMapMessage` 값을 가질 수 있다. SOS의 `!eeheap` 출력에서도 NonGC 힙은 **"Frozen object heap"** 으로 표시된다.

### NonGC 힙이 주는 실질적 이득

이 힙의 존재 이유는 단지 "GC 대상에서 빼기" 위해서가 아니다. 진짜 이득은 JIT 쪽에 있다.

**리터럴 문자열과 읽기 전용 런타임 타입 객체는 애플리케이션 수명 내내 절대 움직이지 않는다.** 그러므로 JIT은 이들의 **주소를 코드에 직접 박아 넣을 수 있고, 쓰기 장벽 호출을 붙이지 않아도 된다.** 62.7절에서 쓰기 장벽의 비용을 보면 이것이 얼마나 큰 이득인지 알게 될 것이다.

> **💡 "왜 내 힙 덤프에 문자열 리터럴이 안 보이나"**
>
> 최신 런타임에서 힙 덤프를 뜨고 문자열을 세는데 소스에 있는 리터럴이 안 보인다면 버그가 아니다. NonGC 힙에 있기 때문이다. 도구에 따라 이 영역을 기본으로 포함하지 않는다. 문자열 관련 메모리를 조사할 때는 도구가 NonGC 힙을 세는지 먼저 확인해야 한다.

## 62.6 물리 분할 — 세그먼트(~.NET 6) → 리전(.NET 7+)

지금까지는 논리적 구획을 봤다. SOH와 LOH, 세대 0/1/2, POH와 NonGC 힙. 남은 질문은 **이것들이 실제 가상 주소 공간에 어떤 덩어리로 놓이는가**다.

### 먼저: 관리 힙은 하나가 아닐 수 있다

물리 구조를 보기 전에 하나 짚어야 한다. Microsoft 구현의 가비지 컬렉터는 두 가지 모드로 동작한다.

| 모드 | 관리 힙 개수 |
|---|---|
| **워크스테이션(Workstation)** | 관리 힙 **하나** |
| **서버(Server)** | 관리 힙 **여러 개**. 기본값은 애플리케이션이 쓸 수 있는 논리 코어 수만큼 |

두 모드의 나머지 차이는 65.1절에서 다룬다. 지금 필요한 것은 힙 개수뿐이다. 서버 모드에서 아래 나올 모든 구조가 **코어 수만큼 복제된다**고 생각하면 된다.

### 두 구현 방식 대조

물리 구현은 .NET 버전에 따라 완전히 다르다.

```text
━━━━━━━━━━━━━━━━━ 세그먼트 (~ .NET 6) ━━━━━━━━━━━━━━━━━━

  하나의 거대한 예약 블록
  ┌────────────────────────────────────────┬──────────────────┐
  │           SOH 세그먼트 (256 MB)         │  LOH 세그먼트     │
  │  ┌────┬────┬─────────────────────────┐ │   (128 MB)       │
  │  │gen2│gen1│         gen0            │ │                  │
  │  └────┴────┴─────────────────────────┘ │                  │
  │  └──── 반드시 연속. 이것이 ephemeral ───┘ │                  │
  │       세그먼트다                         │                  │
  └────────────────────────────────────────┴──────────────────┘
   · 세그먼트 하나는 SOH 아니면 LOH(또는 POH ※.NET 5) 중 하나에 속한다
   · SOH 세그먼트가 여럿이면 딱 하나만 ephemeral 세그먼트이고 나머지는 전부 gen2 전용
   · 세그먼트가 크다 → 비어야만 반환할 수 있어 재사용이 굼뜨다

━━━━━━━━━━━━━━━━━ 리전 (.NET 7+, 64비트) ━━━━━━━━━━━━━━━

  하나의 거대한 예약 블록 (기본 256 GB)
  ┌──────┬──────┬──────┬──────┬──────┐        ┌────────┐
  │ POH  │ gen2 │ gen1 │ gen0 │ LOH  │  ...   │ NGCH   │
  │32 MB │ 4 MB │ 4 MB │ 4 MB │32 MB │        │ 4 MB   │
  └──────┴──────┴──────┴──────┴──────┘        └────────┘
   기본 리전 4 MB, 대형 리전 = 기본 × 8       주소 공간의 다른 곳에
                                              필요할 때 만들어진다
   · 하나의 리전은 정확히 하나의 세대/힙에 속한다
   · ephemeral 세그먼트라는 개념이 사라졌다
   · 리전이 작다 → 자유 리전 풀에서 세대 간 재사용이 가능하다
```

이 대조표가 두 방식의 차이 전부다.

| 항목 | 세그먼트 (~.NET 6) | 리전 (.NET 7+) |
|---|---|---|
| 크기 | 워크스테이션 64비트 SOH 256 MB / LOH 128 MB. 서버는 GB 단위 | 기본 리전 보통 **4 MB**, 대형 리전 32 MB |
| 한 덩어리에 담기는 세대 | ephemeral 세그먼트는 gen0·gen1(경우에 따라 gen2)을 **함께** 담는다 | **정확히 하나**의 세대만 담는다 |
| ephemeral 세그먼트 | 있다. 구현 곳곳에서 특별 취급 | **없다** |
| 세대 간 연속성 | gen2→gen1→gen0이 반드시 연속이어야 한다 | 연속일 필요 없다 |
| 재사용 | VM Hoarding으로 세그먼트 통째 재사용 (기본 꺼짐) | 자유 리스트에서 **세대를 넘나들며** 재사용 |
| 비트 수 | 32비트/64비트 모두 | **64비트 전용** |
| 도입 | 초기부터 | ※.NET 7 |

> **📌 이름은 그대로 남았다**
>
> 리전으로 바뀐 뒤에도 API와 내부 구현은 여전히 `segment`라는 이름을 쓴다. 리전을 표현하는 클래스도 그대로 `heap_segment`다. SOS의 `!eeheap` 출력에서 열 이름이 `segment`인 것도 이 때문이다. 새 SOS 버전에서 바뀔 수 있다.

### 세그먼트 구현 (~.NET 6)

.NET 런타임이 시작될 때 무슨 일이 일어나는지 따라가면 가장 잘 이해된다. 워크스테이션 모드의 가장 단순한 시나리오다.

1. **런타임이 하나의 연속된 메모리 블록을 예약한다.** 초기 세그먼트들을 위한 것이며, 세그먼트들을 붙여 두기 위한 최적화다. 그런 연속 가상 주소 공간이 없으면 세그먼트들은 떨어져 배치된다.
2. **SOH용과 LOH용 세그먼트 두 개를 만든다.** (※.NET 5부터는 POH용 세그먼트도 함께 만든다.) 새로 예약한 블록을 논리적으로 둘로 갈라 그 안에 만든다.
3. **SOH 세그먼트 안에 세대 0, 1, 2가 만들어진다.** 일정량의 메모리를 커밋해서 만든다. LOH에도 일정량이 커밋된다.

VMMap으로 단순 콘솔 애플리케이션을 열면 이 구조가 그대로 보인다.

- Gen0(259 KB), Gen1(24바이트), Gen2(24바이트)에 해당하는 **약 260 KB**
- SOH 세그먼트의 나머지 **거의 256 MB가 예약** 상태
- **72 KB**의 Large Object Heap
- LOH 세그먼트의 나머지 **거의 128 MB가 예약** 상태

### 기본 세그먼트 크기

세그먼트 크기는 GC 모드와 런타임 비트 수로 정해진다.

| | 워크스테이션 32비트 | 워크스테이션 64비트 | 서버 32비트 | 서버 64비트 |
|---|---|---|---|---|
| **SOH** | 16 MB | 256 MB | 64 MB (코어≤4)<br>32 MB (코어≤8)<br>16 MB (코어>8) | 4 GB (코어≤4)<br>2 GB (코어≤8)<br>1 GB (코어>8) |
| **LOH** | 16 MB | 128 MB | 32 MB | 256 MB |

서버 모드에서 **코어가 많을수록 세그먼트가 작아진다**는 점에 주목하라. 힙 개수가 코어 수만큼 늘어나므로 세그먼트 하나하나는 줄여야 총량이 감당된다.

8코어 머신의 64비트 서버 모드 ASP.NET 애플리케이션을 VMMap으로 보면, **하나의 거대한 연속 블록** 안에 SOH 세그먼트 8개가 먼저 오고 그 뒤에 LOH 세그먼트 8개가 온다. 크기는 위 표대로 SOH 2 GB, LOH 256 MB다.

> **⚠️ 18 GB짜리 관리 힙이 실제로는 8 MB다**
>
> 위 구성의 총 예약량은 8×2 GB + 8×256 MB ≈ **18 GB**다. 그런데 실제 사용량(커밋된 메모리)은 **8 MB**다. 61.2절의 예약/커밋 구분을 모르면 이 화면을 보고 "웹 앱이 18기가를 먹는다"고 보고하게 된다. 실제로 매우 자주 벌어지는 오해다.

### 세 가지 초기 배치 패턴

지금까지 본 두 사례는 공통점이 있다. 모든 세그먼트가 하나의 연속 블록 안에 만들어졌다. 이것을 **all-at-once** 패턴이라 하고, 가장 흔한 초기 형태다. 그러나 두 가지가 더 있다.

| 패턴 | 형태 | 언제 |
|---|---|---|
| **all-at-once** | 블록 하나에 모든 세그먼트 | 기본. 가장 흔하다 |
| **two-stage** | SOH용 블록 하나 + LOH용 블록 하나 | 연속 블록 예약에 실패했을 때 |
| **each-block** | 세그먼트마다 별도 블록 | two-stage마저 실패했을 때. **서버 모드에서만** |

연속된 가상 메모리 블록을 예약하지 못하면 two-stage가 시도되고, 그것도 실패하면 서버 모드에서는 더 잘게 쪼갠 each-block이 선택된다. 워크스테이션 모드에서는 two-stage와 each-block이 사실상 같은 형태다.

애플리케이션이 돌면서 ephemeral 세그먼트나 LOH가 가득 차면 **추가 세그먼트가 할당된다.** 이 세그먼트 구성은 Windows와 Linux에서 동일하다.

> **📌 Mono의 물리 구성**
>
> Mono(6.12 기준)는 조금 다르다. 작은 객체는 두 종류 영역에 저장된다. **Nursery**(젊은 세대)는 **4 MB**의 연속 블록이며 동적으로 변하지 않지만 시작 시 설정할 수 있다. 여기서는 빠른 범프 포인터 할당이 쓰인다. 늙은 세대는 **16 kB 블록**으로 조직되며(단편화를 피하려고 더 큰 덩어리 단위로 할당한다) 전체를 Major Heap이라 부른다. Large Object Space의 큰 객체는 **1 MB 섹션**으로 조직되고, 더 큰 객체는 `VirtualAlloc` 호출로 직접 할당한 뒤 단일 연결 리스트로 기억한다.

### 리전 구현 (.NET 7+)

※.NET 7부터 **64비트**에서는 세그먼트가 **리전**으로 대체되었다. 초기화 과정은 이렇다.

1. 주소 공간에 **거대한 연속 블록 하나**를 예약한다.
2. 예약 블록 안에 **POH용 리전 하나, gen2용 하나, gen1용 하나, gen0용 하나, LOH용 하나**를 만든다. LOH와 POH 리전은 SOH 리전보다 **8배 크다.**
3. **NGCH 리전은 주소 공간의 다른 곳에 필요할 때 만들어진다.**
4. 각 리전의 시작에 **페이지 하나가 커밋된다.**

단순 콘솔 .NET 8 애플리케이션을 VMMap으로 보면 이렇다.

- **256 GB 블록**이 예약되고, 그 안에 POH(32 MB), SOH들(각 4 MB), LOH(32 MB) 리전이 만들어진다.
- **4 MB 리전**이 주소 공간의 다른 곳에 만들어져 NGCH를 담는다.

### 리전 크기는 어떻게 정해지는가

리전은 세 종류다.

| 종류 | 크기 | 용도 |
|---|---|---|
| **기본 리전(basic region)** | 보통 4 MB. 설정에 따라 1 MB 또는 2 MB | gen0 / gen1 / gen2 |
| **대형 리전(large region)** | 기본 리전의 **8배** | LOH, POH |
| **거대 리전(huge region)** | 임의 크기 | 대형 리전보다 큰 LOH 할당 |

기본 리전 크기는 주소 공간에 예약한 블록 크기에서 유도된다. `GCHeapHardLimit`가 설정되어 있으면 예약 블록은 그 한도와 같은 크기가 된다. 아니라면 다음 둘 중 **작은 쪽**이다.

- 가상 주소 공간의 절반 (Windows 64비트라면 128 TB의 절반)
- `max(물리 메모리 크기 × 2, 256 GB)`

오늘날 Windows Server 2022가 지원하는 최대 물리 메모리가 48 TB이므로 실질적으로는 항상 두 번째 항이 적용된다. 64 GB 머신이면 256 GB, 256 GB 머신이면 512 GB가 예약된다.

기본 리전 크기 계산 코드는 다음과 같다.

```text
#define LARGE_REGION_FACTOR (8)

// = 19
const int min_regions_per_heap =
    ((ephemeral_generation_count + 1) +
     ((total_generation_count - uoh_start_generation) * LARGE_REGION_FACTOR));

size_t max_region_size = gc_heap::regions_range / 2 / nhp / min_regions_per_heap;

if (max_region_size >= (4 * 1024 * 1024))
{
    gc_region_size = 4 * 1024 * 1024;
}
else if (max_region_size >= (2 * 1024 * 1024))
{
    gc_region_size = 2 * 1024 * 1024;
}
else
{
    gc_region_size = 1 * 1024 * 1024;
}
```

먼저 "힙 개수만큼 19배 곱했을 때 예약 블록의 절반을 채우는 리전 크기"를 구하고, 그 값으로 기본 리전 크기를 정한다. 4 MB 이상이면 4 MB, 2 MB 이상이면 2 MB, 아니면 1 MB다.

> **📌 실질적으로 언제나 4 MB다**
>
> 위 계산을 따라가 보면, GC 설정을 건드리지 않는 한 기본 리전 크기는 **항상 4 MB**가 된다. 4 MB보다 작아지려면 머신에 코어가 **1,724개보다 많아야** 한다.

4코어 머신의 서버 모드에서 CLR은 32 MB짜리 POH 리전 4개, 4 MB짜리 gen2·gen1·gen0 SOH 리전을 각각 4개씩, 그리고 32 MB짜리 LOH 리전 4개를 만든다. VMMap에서 보면 관리 힙들이 주소 공간 128 TB 중 **256 GB를 예약**하고 있지만 실제 사용량은 **272 KB**다. 예약과 커밋의 차이가 여기서도 결정적이다.

> **⚠️ 리전은 64비트 전용이다**
>
> 32비트 런타임에는 리전이 없다. 32비트에서 .NET 7+를 쓰더라도 세그먼트 구현이 그대로 동작한다. 32비트 애플리케이션의 힙 구조를 조사할 때는 항상 세그먼트 기준으로 읽어야 한다.

> **⚠️ 리전이 문제를 일으키면 되돌릴 수 있다 — 그러나 임시방편이다**
>
> .NET 7+에서 옛 세그먼트 구현을 쓰려면 환경 변수를 설정한다.
>
> ```text
> Windows:      DOTNET_GCName=clrgc.dll
> Linux/macOS:  DOTNET_GCName=libclrgc.so
> ```
>
> 이것은 독립형(standalone) GC를 로드하는 메커니즘이며(65.12절), 리전 전환 직후 회귀 문제를 겪는 애플리케이션의 **임시 우회책**이다. 이 설정에 영구히 의존하면 이후 릴리스의 GC 개선을 전부 놓친다.

### 왜 리전으로 바꿨는가

세그먼트의 문제는 두 가지였다.

1. **세그먼트가 너무 크다.** 특히 서버 모드에서는 GB 단위다. 세그먼트를 반환하려면 **통째로 비어야** 하는데, 그럴 일이 좀처럼 없다.
2. **ephemeral 세그먼트 안에서 gen2 → gen1 → gen0이 반드시 연속이어야 한다.** 이 제약이 GC 구현 전반을 옥죈다.

리전은 두 문제를 동시에 푼다. 리전은 작고, 하나의 리전은 하나의 세대만 담는다. 그 결과 **자유 리전을 풀에 모아 세대를 넘나들며 재사용할 수 있다.** gen1으로 쓰이던 자유 리전을 필요하면 gen0으로 쓸 수 있다는 뜻이다.

또한 세대가 연속일 필요가 없어진 덕분에 **동적 승격·강등(DPAD)** 같은 최적화가 가능해졌다(64.6절).

대형 리전보다 큰 할당은 어떻게 하는가. **거대 리전(huge region)** 이 만들어지며 여전히 LOH로 취급된다.

> **💡 버전을 밝히지 않은 "세그먼트" 설명은 의심하라**
>
> 인터넷에 있는 .NET 힙 구조 설명의 대다수는 세그먼트 시대에 쓰였다. "ephemeral 세그먼트", "SOH 세그먼트는 256 MB" 같은 서술을 보면 그 글이 .NET 6 이하를 전제한다고 봐야 한다. 진단할 때 이 차이를 놓치면 `!eeheap` 출력조차 해석이 안 된다.

### .NET 버전별 힙 구조 연표

이 장에서 다룬 버전 의존적 사실을 한자리에 모은다. 진단 문서를 읽거나 쓸 때 이 표를 먼저 확인하면 절반은 해결된다.

| 시점 | 무엇이 바뀌었나 | 이 장의 절 |
|---|---|---|
| 초기 ~ | SOH / LOH, 세대 0/1/2, **세그먼트**. 읽기 전용 힙 세그먼트 존재 | 62.3, 62.4, 62.6 |
| .NET Framework 3.5 | 읽기 전용 힙 세그먼트 **폐기**(.NET Native만 계속 사용) | 62.5 |
| **※.NET 5** | **POH(고정 객체 힙)** 도입. `GC.AllocateArray(..., pinned: true)`<br>카드 번들 write watch가 Windows·Linux 모두 **동일 구현**으로 통일 | 62.5, 62.7 |
| **※.NET 7** | 64비트에서 세그먼트 → **리전**. ephemeral 세그먼트 소멸<br>`PinnedHeapHandleTable` 저장 위치가 LOH → **POH** | 62.5, 62.6 |
| **※.NET 8** | 읽기 전용 힙이 **NonGC 힙**으로 정식 명명<br>NonGC 힙 객체의 `GC.GetGeneration`이 2 → **`int.MaxValue`**<br>POH 배열의 blittable 검사가 관리 코드에서 제거 | 62.5 |

> **⚠️ 32비트에서는 여전히 세그먼트다**
>
> 위 표의 "리전"은 **64비트 전용**이다. 32비트 런타임에서 .NET 8을 쓰더라도 힙은 세그먼트로 구성된다. 32비트 애플리케이션을 진단하면서 리전 기준으로 `!eeheap` 출력을 읽으려 하면 아무것도 맞지 않는다.

### NonGC 힙의 별도 취급

지금까지 설명한 초기화에 NGCH가 빠져 있다는 것을 눈치챘을 것이다. 의도된 것이다. **NGCH에는 전역 초기화가 없다.**

`FrozenObjectHeapManager`라는 전역 네이티브 객체가 **첫 읽기 전용 객체가 할당될 때 지연 생성된다.** 이 매니저가 읽기 전용 객체를 담을 세그먼트를 만든다. 각 읽기 전용 세그먼트는 `FrozenObjectSegment`라는 네이티브 인스턴스로 식별되며, 매니저가 목록으로 들고 있다. 각각은 GC가 관리하는 표준 `heap_segment`에 매핑된다.

```text
       SystemDomain
            │
            ▼
  ┌──────────────────────────┐
  │ FrozenObjectHeapManager  │  (전역 유일, 지연 생성)
  │   list of segments       │
  └────────┬─────────────────┘
           │
     ┌─────┴─────┬─────────────┐
     ▼           ▼             ▼
 ┌─────────┐ ┌─────────┐  ┌─────────┐
 │ Frozen  │ │ Frozen  │  │ Frozen  │
 │ Segment │ │ Segment │  │ Segment │  ← 가득 차면 크기를 2배로 늘려 새로 만든다
 │  4 MB   │ │  8 MB   │  │ 16 MB   │
 └────┬────┘ └────┬────┘  └────┬────┘
      ▼           ▼            ▼
   heap_segment (GC가 관리하는 표준 구조에 매핑)
```

첫 읽기 전용 세그먼트는 **4 MB가 예약**되고 각각 **처음 64 KB가 커밋**된다. 세그먼트가 가득 차면 **직전 크기의 두 배**로 새 세그먼트가 만들어진다.

## 62.7 기억 집합(remembered set), 카드 테이블, 카드 번들

### 세대별 GC가 스스로 만든 문제

62.4절에서 세대를 나눴다. 이제 대가를 치를 차례다.

64.2절에서 자세히 볼 Mark 단계는 **루트에서 출발해 객체 그래프를 순회하며** 도달 가능성을 판정한다. 애플리케이션의 모든 객체를 담은 전체 그래프를 다 순회한다면 완벽하게 동작한다. 그런데 우리는 **일부만 수집하고 싶다.** 젊은 세대만 수집하려면 어떻게 해야 하나.

다음 상황을 보자.

```text
   루트(스택)
     │  │
     ▼  ▼
 ┌───────────────────────────────────────────┐
 │ 세대 0                                     │
 │   A ──► B          C            D          │
 │   ▲                ▲            │          │
 └───┼────────────────┼────────────┼──────────┘
     │직접 루트됨      │            │
 ┌───┼────────────────┼────────────┼──────────┐
 │ 세대 1             │            ▼          │
 │   E ───────────────┘   F        G          │
 │   ▲                                        │
 └───┼────────────────────────────────────────┘
     │직접 루트됨
```

- **세대 0**: A는 직접 루트되어 있고 B를 참조한다. C는 **더 늙은 세대의 객체(E)만이** 참조한다. D는 아무도 참조하지 않는다(진짜 도달 불가).
- **세대 1**: E는 직접 루트되어 있고 **더 젊은 세대의 C**를 참조한다. F는 아무도 참조하지 않는다. G는 **더 젊은 세대의 D**가 참조한다.

세대 간 참조는 양방향 모두 지극히 정상이다.

- **젊은→늙은**: 방금 만든 객체가 이미 존재하던 늙은 객체를 참조한다 (D → G)
- **늙은→젊은**: 예전에 만든 객체에 새로 만든 객체의 참조를 넣는다 (E → C)

이제 순진하게 **젊은 세대만 마킹**해보자. 루트에서 출발하되 젊은 세대가 아닌 객체를 만나면 멈춘다.

- 루트에서 출발 → **A와 B만 마킹된다.**
- E는 루트되어 있어도 늙은 세대라 무시된다.
- **C는 방문되지 않는다.** 루트도, 다른 젊은 객체도 C를 참조하지 않기 때문이다. E가 참조한다는 사실이 보이지 않는다.
- 결과: **C와 D가 도달 불가로 판정된다.**

D는 정말 도달 불가이니 회수해도 된다. 그러나 **C는 E가 여전히 쓰고 있는데도 수집된다.** 재앙이다.

**결론: 늙은→젊은 세대 간 참조는 반드시 별도로 추적해야 한다.**

### 기억 집합

이 문제를 푸는 기법이 **기억 집합(remembered set)** 이다. 일반적으로 기억 집합은 서로 다른 객체 집합 사이의 참조를 따로 관리하는 컬렉션이다. .NET의 경우 **늙은 세대에서 젊은 세대로 향하는 참조를 기억하는 세대 간 자료구조 집합**이며, Mark 단계에서 사용된다.

젊은 세대 GC에서는 **루트와 기억 집합에 저장된 참조 양쪽에서** 순회를 시작한다. 위 예제라면 E→C 참조가 기억 집합에 있으므로 C가 올바르게 살아남는다.

> **📌 젊은 세대만 수집할 때 G는 어떻게 되나**
>
> 위 시나리오에서 D는 올바르게 수집되고, 그러면 G는 잠시 아무도 참조하지 않는 상태가 된다. 하지만 G는 늙은 세대에 있으므로 이번 GC에서 건드려지지 않는다. **나중에 늙은 세대 GC가 일어날 때 도달 불가로 표시되어 회수된다.** D와 G 모두 결국은 수집되지만 시점이 다를 뿐이다.

### 왜 "gen1만 수집"이 없는지에 대한 답

반대로 **늙은 세대만** 수집하려 하면 같은 문제를 반대 방향에서 만난다. D가 G를 참조한다는 사실을 알아채지 못한다. 그러려면 **젊은→늙은 참조를 위한 또 하나의 기억 집합**이 필요하다.

기억 집합 구현은 결코 사소하지 않으므로, 대신 훨씬 단순한 결정이 내려졌다. Microsoft 문서의 문장이 그 결정이다.

> "한 세대를 수집한다는 것은 그 세대와 그보다 젊은 모든 세대의 객체를 수집한다는 뜻이다."

이것이 62.4절에서 본 "가능한 수집 범위는 세 가지뿐"의 진짜 이유다.

### 기억 집합은 언제 갱신되는가 — 쓰기 장벽

기억 집합에 참조를 넣고 빼는 시점은 언제인가. 흔한 해법은 **참조가 만들어지는 순간을 기억하는 것**이고, 그것은 주로 필드 대입에서 일어난다.

```csharp
E e = new E();
// ... 시간이 흘러 e가 더 늙은 세대로 승격된다 ...
C c = new C();
e.SomeField = c;      // ← 늙은→젊은 참조가 만들어지는 순간
```

마지막 줄이 기억하기 좋은 지점이다. 그런데 이 문제를 더 일반적으로 봐야 한다. C#의 필드는 참조를 담는 여러 방법 중 **하나**일 뿐이고, 그것도 C# 명세가 정한 것이다. 기억 집합 메커니즘이 특정 언어에 묶여서는 안 된다. 앞으로 C#이든 아직 없는 언어든 참조를 저장하는 다른 방법이 생길 수 있다.

그래서 런타임 수준의 더 낮은 기법이 쓰인다. **쓰기 장벽(write barrier)** 이다. 뮤테이터가 어떤 주소에 값을 저장할 때마다 실행되는 연산에 코드를 끼워 넣는다.

```text
Mutator.Write(address, value)
{
   *address = value;
   if (AreWriteBarrierConditionMeet(address, value))
   {
      RememberedSet.AddOrUpdate(address, value);
   }
}
```

문제는 이것이 **엄청나게 빈번한 연산**이라는 점이다. 여기에 뭘 하나 추가하면 오버헤드가 어마어마해진다. 쓰기 장벽을 설계할 때는 극도로 조심해야 한다.

다행히 쓰기 장벽을 **호출해야만 하는 조건은 정확히 정해져 있다.**

- 저장하는 값이 **관리 객체에 대한 참조**여야 한다.
- 쓰기 연산의 대상 주소가 **관리 힙 안**에 있고 유효한 객체 필드여야 한다.
- 그 주소가 **값이 가리키는 객체보다 늙은 세대**에 있어야 한다.

### JIT이 미리 결정한다

이 조건들을 매번 런타임에 검사하면 오버헤드가 감당되지 않는다. 그러나 **대부분은 JIT 컴파일 시점에 미리 판정할 수 있다.** JIT 컴파일러는 IL 코드만 봐도 "지금 관리 객체 참조를 다른 관리 객체의 필드에 저장하는가"를 정확히 안다. 그래서 어셈블리 코드를 생성할 때 **쓰기 장벽이 필요한 버전과 필요 없는 버전 중 맞는 쪽을 선택해 방출한다.** .NET 런타임이 취한 접근이 정확히 이것이다.

```csharp
ClassA someClass = new ClassA();
ClassB otherClass = new ClassB();
someClass.FieldB = otherClass;
```

이 코드는 다음 CIL로 컴파일된다(중요하지 않은 부분은 생략).

```il
newobj ClassA::.ctor
newobj ClassB::.ctor
stfld  ClassA::FieldB
```

`stfld`는 평가 스택의 첫 값을 두 번째 값(객체)의 필드에 저장한다. x64에서 JIT을 거치면 이렇게 된다.

```text
; ClassA 객체 할당과 생성자 호출
mov     rcx, 7FFCC4BA6600h                 ; MT: ClassA
call    coreclr!JIT_TrialAllocSFastMP_InlineGetThread
mov     rdi, rax                           ; rdi = ClassA 참조
mov     rcx, rdi
call    System_Private_CoreLib+0xc04060    ; System.Object..ctor()

; ClassB 객체 할당과 생성자 호출
mov     rcx, 7FFCC4BA67B8h                 ; MT: ClassB
call    coreclr!JIT_TrialAllocSFastMP_InlineGetThread
mov     rsi, rax                           ; rsi = ClassB 참조
mov     rcx, rsi
call    System_Private_CoreLib+0xc04060    ; System.Object..ctor()

; stfld → 쓰기 장벽 호출로 번역되었다
lea     rcx, [rdi+8]                       ; rcx = ClassA의 FieldB 주소
mov     rdx, rsi                           ; rdx = ClassB 참조
call    coreclr!JIT_WriteBarrier
```

`stfld` 한 줄이 `JIT_WriteBarrier` **함수 호출**로 바뀌었다. 여기서는 검사(checked) 버전이 쓰이지 않았는데, 대상이 관리 객체임을 JIT이 알고 있기 때문이다.

> **📌 소스 코드에서 따라가려면**
>
> `CodeGen::genCodeForTreeNode`의 `GT_STOREIND` 처리에서 시작한다. 이것이 `CodeGen::genCodeForStoreInd`를 호출하고, 여기서 `gcIsWriteBarrierCandidate`를 불러 쓰기 장벽이 필요한지 판정한다. 필요하면 `CodeGen::genGCWriteBarrier`가 `CORINFO_HELP_ASSIGN_REF` 또는 `CORINFO_HELP_CHECKED_ASSIGN_REF` 헬퍼의 어셈블리를 방출한다. 전자는 대상이 관리 힙 안에 있음을 JIT이 확신할 때, 후자는 그렇지 않을 때 쓴다. 두 헬퍼는 각각 `JIT_WriteBarrier`와 `JIT_CheckedWriteBarrier` 함수에 대응한다. 이 판정은 전부 **JIT 컴파일 시점**에 끝나고, 런타임에는 둘 중 하나가 호출될 뿐이다.

### 카드 테이블 — 정확성을 버리고 속도를 산다

여기서 심각한 문제가 하나 남는다. 세대 간 참조를 **하나하나 전부** 기억 집합에 저장한다면?

앞의 예제에서는 참조가 하나뿐이었다. 현실의 애플리케이션은 수십만, 수백만 객체가 서로를 참조한다. 게다가 .NET에는 세대가 셋이라 가능한 세대 간 참조 조합이 더 많고, 참조를 바꾸는 것은 매우 흔한 연산이다. **모든 세대 간 참조를 순진하게 모아두는 컬렉션은 오버헤드가 감당이 안 된다.**

늘 그렇듯 타협이 필요하다. 컬렉션 관리 오버헤드를 줄이기 위해 **개별 참조를 추적하지 않고 정확성을 버린다.** 대신 메모리를 **고정 크기 블록 단위**로 추적한다. 이 기법이 **카드 테이블(card table)** 이다.

발상은 단순하다. 늙은 세대를 **일정 크기의 연속 블록**으로 자른다. 각 블록은 카드 테이블의 **카드 항목(card entry) 하나**로 표현된다. 처음에는 모든 카드가 깨끗하다(clean, 비트값 0). **깨끗한 카드는 그 블록 안에 늙은→젊은 참조가 없다는 뜻**이다.

```text
【대입 전 — 모든 카드가 깨끗하다】

 늙은 세대  ┌──────┬──────┬──────┬──────┬───
           │ (빈)  │  E   │ F 앞 │ F 뒤 │ ...
           └──────┴──────┴──────┴──────┴───
 카드 테이블 │  0   │  0   │  0   │  0   │
            └──────┴──────┴──────┴──────┘

【 e.SomeField = c 실행 후 — E가 속한 카드가 더러워진다 】

 늙은 세대  ┌──────┬──────┬──────┬──────┬───
           │ (빈)  │  E ──┼──────┼──────┼──► C (세대 0)
           └──────┴──────┴──────┴──────┴───
 카드 테이블 │  0   │  1   │  0   │  0   │
            └──────┴──▲───┴──────┴──────┘
                      └── "set" 또는 "dirty" 상태
```

세 번째 블록에는 어떤 객체의 **일부만** 들어 있는 것에 주목하라. 객체가 블록 경계에 걸치는 일은 얼마든지 있다.

**다음 GC에서 더러운 카드 안의 모든 객체는 추가 루트 후보로 취급된다.** 젊은 세대 GC가 일어나면 객체 그래프를 루트에서, 그리고 수집 대상보다 늙은 세대의 더러운 카드 안 모든 객체에서 함께 순회한다. 위 예제에서 C가 도달 가능하다고 발견되는 경로가 이것이다.

> **⚠️ 객체가 카드 경계에 걸치면 어느 카드를 더럽히는가**
>
> 세 번째 카드에서 시작하는 객체 F의 **마지막 필드**를 바꾸면, 그 필드는 네 번째 카드에 있다. 쓰기 장벽은 최대한 가벼워야 하므로 **바뀐 주소에 해당하는 네 번째 카드만** 더럽힌다. 나중에 Mark 단계에서 그 카드의 시작 주소를 포함하는 객체(여기서는 F)를 찾아내야 하는데, 이때 쓰이는 것이 **브릭 테이블(brick table)** 기법이다. 64.6절에서 다룬다.

당연히 대가가 있다. **늙은→젊은 참조 하나 때문에 카드 안의 모든 객체와 그 참조를 방문해야 한다.** 성능과 정확성의 맞바꿈이다. 이 균형은 카드 크기로 조절할 수 있다.

- 카드가 아주 작아 객체 하나만 담는다면 → 모든 참조를 추적하는 **순수 기억 집합**과 같아진다.
- 카드가 아주 커서 세대 전체를 덮는다면 → **전체 그래프 순회**와 같아진다.

### .NET의 카드 테이블 크기

```text
【64비트 .NET 카드 테이블 구성】

 카드 워드 (DWORD, 4바이트) = 32개 카드 = 8,192바이트의 힙
 ┌───────────────────────────────────────────────────────────┐
 │  byte 0    │  byte 1    │  byte 2    │  byte 3            │
 │ 8개 카드    │ 8개 카드    │ 8개 카드    │ 8개 카드            │
 │ = 2,048B   │ = 2,048B   │ = 2,048B   │ = 2,048B           │
 └───────────────────────────────────────────────────────────┘
      │
      └─► 비트 하나 = 카드 하나 = 힙의 256바이트 (32비트에서는 128바이트)
```

| 단위 | 크기 | 대응하는 힙 영역 (64비트) | 32비트 |
|---|---|---|---|
| 카드 1개 (비트 1개) | 1비트 | **256바이트** | 128바이트 |
| 카드 테이블의 바이트 1개 | 8카드 | **2,048바이트** | 1,024바이트 |
| 카드 워드 1개 (DWORD) | 32카드 | **8,192바이트** | 4,096바이트 |

즉 128바이트(32비트) 또는 256바이트(64비트) 영역 어디든 참조가 쓰이면 해당 카드가 set 된다.

### 쓰기 장벽의 실제 코드

이제 `JIT_WriteBarrier` 안을 볼 수 있다. 흥미로운 사실이 하나 있다. **이 함수의 코드 영역은 자리 표시자(placeholder)에 불과하다.** 여러 구체적 구현 중 하나를 그 위에 복사해 덮어쓰는 방식으로 런타임에 교체된다(물론 프로그램 실행이 중단된 상태에서). 자리 표시자의 크기는 가장 큰 구현의 크기와 같아서 어느 것이든 들어간다.

> **📌 x64의 쓰기 장벽 변종들**
>
> - **`JIT_WriteBarrier_PreGrow64` / `JIT_WriteBarrier_PostGrow64`** — 워크스테이션 GC 모드에서 쓴다. 앞의 것은 세대 0과 1이 기본 위치에 있을 때, 런타임이 이들을 다른 곳으로 옮기기로 결정한 뒤에는 뒤의 것이 주입된다.
> - **`JIT_WriteBarrier_SVR64`** — 서버 GC 모드용. 힙이 여럿이라 세대 0과 1도 여럿이다. 참조가 그중 어디에 속하는지 검사하는 것은 너무 느리므로 **조건 없이 카드를 set 한다.**
> - **`..._WriteWatch_...`** 접두사가 붙은 세 변종 — 뒤에서 설명할 write watch 기법을 쓰는 대응 버전.
>
> 런타임이 쓰기 장벽을 교체할 때는 `WriteBarrierManager::ChangeWriteBarrierTo`를 호출하며, 내부적으로 현재 구현의 코드를 `memcpy`로 덮어쓴다.

가장 단순한 버전 하나만 보면 충분하다. 나머지도 거의 같다.

```text
01. LEAF_ENTRY JIT_WriteBarrier_PostGrow64, _TEXT
02.         align 8
03.         mov     [rcx], rdx              ; rcx 주소에 rdx 값을 저장 (본래의 일)
04.         NOP_3_BYTE                      ; 상수 정렬용 패딩
05. PATCH_LABEL JIT_WriteBarrier_PostGrow64_Patch_Label_Lower
06.         mov     rax, 0F0F0F0F0F0F0F0F0h ; 런타임에 실제 주소로 패치된다
07.         cmp     rdx, rax                ; ephemeral 하한 검사
08.         jb      Exit                    ;   rdx < rax 면 종료
09.         nop
10. PATCH_LABEL JIT_WriteBarrier_PostGrow64_Patch_Label_Upper
11.         mov     r8, 0F0F0F0F0F0F0F0F0h  ; 런타임에 패치
12.         cmp     rdx, r8                 ; ephemeral 상한 검사
13.         jae     Exit                    ;   rdx >= r8 면 종료
14.         nop
15. PATCH_LABEL JIT_WriteBarrier_PostGrow64_Patch_Label_CardTable
16.         mov     rax, 0F0F0F0F0F0F0F0F0h ; 카드 테이블 주소로 패치된다
17.         shr     rcx, 0Bh                ; 대상 주소를 2048로 나눈다
18.         cmp     byte ptr [rcx + rax], 0FFh
19.         jne     UpdateCardTable
20.         REPRET
21.     UpdateCardTable:
22.         mov     byte ptr [rcx + rax], 0FFh
23.         ret
24.     align 16
25.     Exit:
26.         REPRET
27. LEAF_END_MARKED JIT_WriteBarrier_PostGrow64, _TEXT
```

한 줄씩 읽어보자.

- `rcx`에 대상 주소(`Mutator.Write`의 `address`), `rdx`에 저장할 참조(`value`)가 들어온다.
- **3행**이 본래의 일을 한다. 주어진 주소에 값을 쓴다.
- 카드 테이블을 건드릴 필요는 `rdx`가 **젊은 세대에 속할 때만** 있다. 런타임은 늙은→젊은 참조만 관심 있고, 세대 0과 1을 젊은 것으로, 세대 2를 늙은 것으로 본다.
- **6~14행**이 참조가 **ephemeral 세대**(세대 0과 1)에 속하는지 하한·상한으로 검사한다. 아니면 함수가 그냥 끝난다.
- **16행**은 카드 테이블 주소를 `rax`에 넣는다. `0F0F0F0F0F0F0F0F0h`라는 이상한 상수는 런타임에 실제 값으로 패치된다.
- **17행**의 `shr rcx, 0Bh`는 `rcx`를 11비트 오른쪽 시프트한다. n비트 시프트는 2ⁿ으로 나누는 것이고, 2¹¹ = **2,048**이다. 즉 주소를 2,048로 나눠 카드 테이블 안의 **바이트 인덱스**를 얻는다.
- **18~22행**이 그 바이트를 `FFh`와 비교하고, 아직 set 되지 않았으면 `FFh`로 저장한다.

> **⚠️ 비트 하나가 아니라 바이트 전체를 set 한다**
>
> 중요한 지점이다. 카드 하나(비트 하나)만 set 하면 될 것을 **8개 카드를 나타내는 바이트 전체**를 set 한다. 성능 때문이다. 바이트 하나를 비교하고 저장하는 것은 명령 하나로 끝나지만, 비트 조작은 마스크를 준비하고 다뤄야 한다.
>
> 결과적으로 256바이트짜리 카드 하나가 아니라 **2,048바이트에 해당하는 8개 카드가 한꺼번에 더러워진다.** 또 하나의 성능 맞바꿈이다.

> **⚠️ 쓰기 장벽은 대상이 늙은 세대인지 검사하지 않는다**
>
> 위 코드는 **원본 참조(`rdx`)가 젊은 세대에 속하는지만** 검사한다. **대상 주소(`rcx`)가 늙은 세대에 속하는지는 확인하지 않는다.** 그래서 젊은→젊은 참조에 대해서도 카드가 더러워진다. 이것이 허용되는 이유는 두 가지다.
>
> - Mark 단계에서 카드 테이블은 **늙은 세대에 속하는 주소에 대해서만** 조회된다. 젊은→젊은 참조 때문에 생긴 표시는 그냥 무시된다.
> - 쓰기 장벽 안에서 `rcx`가 늙은 세대인지 검사하는 것은 너무 복잡하다. 필요한 검사를 다 하느니 그냥 더럽히는 편이 빠르다.

### 카드 번들 — 한 단계 더

카드 테이블로 기억 집합을 최적화했지만 최적화의 여지가 더 있다.

서버에서 도는 전형적인 웹 애플리케이션을 생각해보자. 메모리를 몇 기가바이트 쓰고 **늙은 세대가 2 GB**라고 하자. 카드 테이블의 바이트 하나가 2 kB를 표현하므로, 늙은 세대 전체를 덮으려면 **1 MB짜리 카드 테이블**이 필요하다.

얼핏 크지 않아 보인다. 그러나 이 1 MB는 **젊은 세대를 수집할 때마다 전부 스캔**해야 한다. 젊은 세대 수집은 극도로 빨라야 하는데, 이만한 카드 테이블 스캔은 과하다. 몇 밀리초라 해도 **가비지 컬렉션 전체 시간보다 길어질 수 있다.** 게다가 카드 테이블은 대체로 **성기다(sparse)**. set 되지 않은 카드가 set 된 카드 사이에 잔뜩 끼어 있다.

그래서 관측 계층이 하나 더 추가되었다. **카드 번들(card bundle)** 이다. 카드 워드가 여러 카드를 묶었듯, **카드 번들 워드는 여러 카드 워드를 묶는다.** 훨씬 촘촘하게 설계되어 훨씬 큰 메모리 영역을 덮는다.

```text
【64비트 .NET 카드 번들 테이블 구성】

 카드 번들 워드 (4바이트) = 32비트 = 8 MB의 힙
 ┌───────────────────────────────────────────────────────────┐
 │  byte 0    │  byte 1    │  byte 2    │  byte 3            │
 │  = 2 MB    │  = 2 MB    │  = 2 MB    │  = 2 MB            │
 └───────────────────────────────────────────────────────────┘
      │
      └─► 비트 하나 = 카드 워드 32개 = 힙의 256 kB
```

| 단위 | 덮는 영역 |
|---|---|
| 카드 번들 비트 1개 | 카드 워드 32개 = **256 kB** |
| 카드 번들 바이트 1개 | **2 MB** |
| 카드 번들 워드 1개 (4바이트) | **8 MB** |

**두 단계 스캔**이 된다. 먼저 카드 번들 테이블을 훑어 더러운 큰 영역을 찾고, **그 안에서만** 카드 테이블을 정밀 스캔한다. 앞의 2 GB 늙은 세대 예제라면 카드 번들 테이블은 **겨우 1,024바이트**면 된다. 캐시에 통째로 들어가므로 스캔이 매우 빠르다. 어느 비트가 set 되어 있으면 대응하는 카드 워드 32개만 훑어 set 된 카드를 찾는다.

### 카드 번들은 누가 더럽히는가

앞의 쓰기 장벽 코드에는 카드 번들을 건드리는 부분이 없었다. 누가 하는가. **운영체제에 따라 달랐다.**

**.NET 5 이전 Windows**에서는 OS의 **write-watch** 메커니즘을 썼다. 카드 테이블 영역의 페이지를 Virtual API로 예약할 때 특별한 `MEM_WRITE_WATCH` 플래그를 준다. 나중에 (쓰기 장벽이 카드를 set 해서) 페이지가 수정되면 Windows 내부 구조에 더러운 것으로 기록된다. 더러운 페이지 목록은 `GetWriteWatch` API로 얻을 수 있다. .NET 런타임은 Mark 단계 시작 시점에 `gc_heap::update_card_table_bundle()` 안에서 이 함수를 호출해 목록을 받아 카드 번들 테이블의 대응 비트를 set 했다.

**Linux**에서는 .NET Core 팀이 신뢰할 만한 OS 수준 write-watch를 찾지 못했다. 그래서 **쓰기 장벽 안에 직접 구현**했다(원래 백그라운드 GC를 지원하려고 만든 write watch를 재사용한 것이다).

```text
#ifdef FEATURE_MANUALLY_MANAGED_CARD_BUNDLES
      // rcx는 이미 0xB만큼 시프트되었으므로 0xA만큼 더 시프트한다
      shr     rcx, 0Ah
      NOP_2_BYTE
PATCH_LABEL JIT_WriteBarrier_PreGrow64_Patch_Label_CardBundleTable
      mov     rax, 0xF0F0F0F0F0F0F0F0
      // 카드 번들을 건드린다. 이미 더럽지 않다면.
      cmp     byte ptr [rcx + rax], 0FFh
      jne     UpdateCardBundleTable
      REPRET
  UpdateCardBundleTable:
      mov     byte ptr [rcx + rax], 0FFh
#endif
```

여기서도 **바이트 전체가 더럽게 표시된다.** 따라서 Linux 기반 .NET Core의 카드 번들은 **2 MB 세분성**으로 동작한다.

> **📌 ※.NET 5부터 두 OS가 같은 구현을 쓴다**
>
> .NET 5부터는 Windows와 Linux 모두 위의 수동 구현을 사용한다. OS 의존성이 사라져 동작이 일관되어졌다.

> **⚠️ 큰 배열 원소를 갱신하면 배열 전체가 스캔되는가**
>
> 늙은 세대에 있는 거대한 객체 배열이 여러 카드, 심지어 여러 카드 번들에 걸쳐 있다고 하자. 그 원소 하나에 새 객체를 대입하면 어떻게 되나. 카드 워드의 대응 바이트 하나와 카드 번들 워드의 대응 비트 하나만 더러워진다.
>
> Mark 단계는 **set 된 카드에 해당하는 배열 부분만** 스캔한다. 배열 전체를 훑지 않는다. 큰 배열을 캐시로 쓰는 코드가 그나마 견딜 만한 이유다.

### 카드 테이블의 비용은 어디에 나타나는가

카드 테이블은 이론적 장치가 아니라 실제로 메모리와 CPU를 쓴다. 어디서 보이는지 알아두면 진단이 쉬워진다.

**메모리 쪽.** 62.2절에서 본 것처럼 **카드 테이블은 관리 힙이 아니라 Heap/Private Data 영역에 산다.** 그러니 `GC Heap Size`에도 `# Total committed Bytes`에도 잡히지 않는다. 늙은 세대 크기의 약 1/2,048이 카드 테이블로, 그 위에 카드 번들 테이블이 다시 1/1,024 비율로 붙는다. 늙은 세대가 2 GB면 카드 테이블 1 MB, 카드 번들 테이블 1 KB다. **관리 힙 크기 대비로는 미미하지만 "관리 힙 밖의 .NET 메모리"가 무엇인지 설명해야 할 때 이 항목이 등장한다.**

**CPU 쪽.** 비용은 두 군데서 발생한다.

| 지점 | 무엇을 하는가 | 언제 커지는가 |
|---|---|---|
| 참조 필드 대입 시 | 쓰기 장벽 실행 — ephemeral 범위 비교 2회 + 카드 바이트 비교/저장 | 참조 필드에 쓰는 연산이 많을수록 |
| 젊은 세대 GC 시 | 카드 번들 → 카드 테이블 2단계 스캔, 더러운 카드 안의 모든 객체를 추가 루트로 순회 | 늙은 세대가 클수록, 더러운 카드가 많을수록 |

두 번째가 특히 중요하다. **늙은 세대가 커지면 gen0 GC도 함께 느려진다.** "gen0 GC는 항상 싸다"는 통념이 깨지는 지점이며, 세대 2에 오래 사는 컬렉션을 잔뜩 쌓아두고 거기에 계속 새 객체를 대입하는 코드가 정확히 이 비용을 문다.

> **⚠️ 서버 GC는 조건 없이 카드를 더럽힌다**
>
> 앞서 본 `JIT_WriteBarrier_SVR64`는 힙이 여럿이라 "참조가 젊은 세대에 속하는가"를 검사하는 비용이 너무 커서 **조건 검사 없이 무조건 카드를 set 한다.** 결과적으로 서버 GC에서는 카드 테이블이 워크스테이션 모드보다 훨씬 더럽게 유지되고, 젊은 세대 GC의 스캔 대상도 늘어난다. 서버 GC를 켰는데 gen0 일시 중지가 기대만큼 짧지 않다면 이 요인을 고려할 가치가 있다. 모드 선택 전반은 65.1절에서 다룬다.

> **💡 값 타입 필드는 쓰기 장벽을 부르지 않는다**
>
> 쓰기 장벽이 필요한 조건 첫 번째는 "저장하는 값이 **관리 객체에 대한 참조**"였다. `int`, `double`, 참조를 담지 않은 `struct` 필드에 값을 쓰는 것은 쓰기 장벽을 전혀 유발하지 않는다. 69.1절에서 `struct` 전환의 손익을 계산할 때, **참조 필드가 사라지면 쓰기 장벽과 카드 테이블 오염도 함께 사라진다**는 점을 이득 항목에 넣어야 한다. 다만 이 이득은 대개 할당 제거 이득보다 작으므로 단독 근거로 삼지는 마라.

### 실무적 함의 — Rule 12

지금까지 본 것은 .NET GC를 굴러가게 하는 핵심 메커니즘이면서, 문서에 가장 덜 설명된 것이기도 하다. 이유는 아마도 **아주 잘 최적화되어 있어 문제를 일으키지 않기 때문**일 것이다. 그러나 함의는 있다.

> **💡 Rule 12 — 불필요한 힙 참조를 피하라**
>
> **근거.** 세대별 GC에는 세대 간 참조를 추적하는 특수 기법이 필요하다. .NET은 쓰기 장벽과 카드 테이블로 이를 구현하며, 오버헤드를 최소화하려 매우 정교하게 만들어져 있다. **그러나 가장 좋은 세대 간 참조는 존재하지 않는 참조다.**
>
> **적용 방법.** 오래 사는 버퍼나 캐시를 만들 때 새로 만든 객체를 거기 대입하는 것이 전형적인 패턴이다. 이것이 세대 간 참조를 만들고 카드 테이블 메커니즘을 유발한다. 피할 수 있는 경우가 있다. 예를 들어 이진 트리를 설계할 때 노드 참조를 들고 있는 대신
>
> ```csharp
> class Node
> {
>     Data d;
>     Node left;
>     Node right;
> }
> ```
>
> 노드를 배열에 담고 **인덱스만** 저장할 수 있다.
>
> ```csharp
> class Node
> {
>     Data d;
>     uint leftIndex;
>     uint rightIndex;
> }
> ```
>
> **다만 이런 변경은 코드 전반에 파급된다.** 노드 배열은 어떻게 할당할 것인가? 노드마다 배열 조회가 하나씩 추가되는데 그래프 순회 성능은 어떻게 되는가? **오직 견실한 벤치마킹만이** 이 규칙을 적용할 가치가 있는지 답해준다. 참조를 줄이겠다고 코드를 알아보기 어렵게 만드는 것은 대부분의 경우 손해다.

## 62.8 세그먼트/리전 재사용과 힙 해부 실습

### 세그먼트 한 개의 해부

리전 이전의 .NET에서 세그먼트는 관리 힙의 물리적 표현 그 자체였고, 내부 구조는 단순하다.

```text
        ┌──────────────────────────────────────────────────┐
        │ heap_segment 구조체 (수십 바이트)                  │
 segment│  · mem        객체 할당이 시작되는 주소             │  ← 페이지 하나(4,096바이트)
 주소 ──►│  · allocated  현재 할당된 객체의 끝 주소           │     전체가 커밋된다
        │  · reserved / committed 경계                      │
        ├──────────────────────────────────────────────────┤
 begin ─►│ 객체 객체 객체 객체 ...                            │  ← 커밋된 영역
        │                                                  │
 allocated►                                                │
        │           (커밋되었지만 아직 안 쓴 부분)            │
        ├──────────────────────────────────────────────────┤
        │                                                  │
        │           예약만 된 영역                           │
        │                                                  │
        └──────────────────────────────────────────────────┘
```

62.6절의 `!eeheap` 출력에서 세그먼트 주소가 `0x0000026700000000`인데 begin이 `0x0000026700001000`이었던 이유가 이것이다. **처음 4,096바이트(16진수 `0x1000`)가 런타임이 관리하는 세그먼트 정보를 담는다.**

- 세그먼트 시작에 `heap_segment` 클래스 인스턴스가 저장된다. 이 클래스는 수십 바이트에 불과하지만 **대개 페이지 하나 전체가 커밋된다.** 백그라운드 GC를 위한 성능 최적화다(65.2절).
- 객체는 소스 코드의 `mem` 필드에 저장된 주소부터 할당된다. `!eeheap` 출력에서는 이 주소가 `begin`으로 나온다. 63장에서 보겠지만 세그먼트의 예약 메모리는 객체 하나가 아니라 **여러 페이지 단위로** 커밋되므로, 현재 객체들이 필요로 하는 것보다 커밋된 메모리가 조금 더 많다.
- 현재 할당된 객체의 끝 주소는 `allocated` 필드에 저장된다.

**세그먼트는 낮은 주소에서 높은 주소 방향으로 소비된다.** 객체를 많이 할당할수록 세그먼트 안에서 커밋되는 메모리가 늘어난다.

리전으로 바뀌어도 **클래스 이름은 `heap_segment` 그대로**다. `gen_num` 필드가 어느 세대를 나타내는지 저장하고, `flags` 필드가 SOH·LOH·POH 리전을 구별한다. `mem` 같은 나머지 필드는 그대로다. 결정적 차이는 하나다.

> **⚠️ 리전에서는 `heap_segment` 인스턴스가 리전 안에 있지 않다**
>
> 세그먼트 시절에는 `heap_segment` 인스턴스가 각 세그먼트의 맨 앞에 놓였다. **리전에서는 주소 공간의 다른 영역에 배열로 모여 저장된다.** WinDbg에서 주소 계산으로 세그먼트 헤더를 찾던 옛 습관은 .NET 7+에서 통하지 않는다.

### GC 핵심 클래스의 관계

.NET 소스 코드를 직접 읽을 생각이라면 다음 네 클래스의 관계를 알아두는 것이 출발점이다.

| 클래스 | 역할 | 인스턴스 개수 |
|---|---|---|
| **`GCHeap`** | 가비지 컬렉터와 실행 엔진 사이의 **인터페이스** 역할을 하는 고수준 클래스. `Alloc`, `GarbageCollect` 같은 메서드를 갖는다. 전역 인스턴스 `g_pGCHeap`, `g_theGCHeap` | 워크스테이션: 1개<br>서버: 1 + 코어 수 |
| **`gc_heap`** | 단일 관리 힙의 **저수준 API**. GC의 실제 작업을 전부 담는다. `allocate`, `garbage_collect`, `make_gc_heap`, `make_heap_segment` 등 | 워크스테이션: **0개**(관련 메서드가 전부 static)<br>서버: 코어 수만큼 |
| **`generation`** | 단일 세대를 표현. 그 세대를 담은 세그먼트/리전 정보, 할당 관련 정보 등 | 힙마다 세대 수만큼 |
| **`heap_segment`** | 단일 세그먼트/리전 정보. 같은 세대의 세그먼트들은 **단일 연결 리스트**로 이어진다 | 가변 |

워크스테이션 모드에서 `gc_heap` 인스턴스가 아예 없다는 점이 재미있다. 힙이 하나뿐이니 인스턴스를 만들 이유가 없고 모든 메서드를 static으로 만든 것이다.

리전이 도입된 뒤 런타임이 시작할 때 리전들은 `g_gc_lowest_address`와 `g_gc_highest_address` 전역 변수가 가리키는 **하나의 예약 주소 범위** 안에 만들어진다. 리전은 처음에 종류별로 묶여 배치된다. POH 리전이 먼저, 그다음 gen2·gen1·gen0 리전, 마지막에 LOH 리전이다.

### `GC.GetGeneration`의 구현이 달라졌다

이 지식이 있으면 `GC.GetGeneration`의 구현 변화를 읽을 수 있다.

**세그먼트 시절:**

```text
// 객체의 세대 번호를 반환한다. 객체가 유효하다고 가정한다.
// LOH 객체에 대해서는 max_generation을 반환한다는 점에 주의.
int gc_heap::object_gennum (uint8_t* o)
{
    if (in_range_for_segment (o, ephemeral_heap_segment) &&
        (o >= generation_allocation_start (generation_of (max_generation-1))))
    {
        // ephemeral 세대 안에 있다.
        for ( int i = 0; i < max_generation-1; i++)
        {
            if ((o >= generation_allocation_start (generation_of (i))))
                return i;
        }
        return max_generation-1;
    }
    else
    {
        return max_generation;
    }
}
```

**주소 비교로 세대를 판정한다.** ephemeral 세그먼트 안에 있고 세대 경계보다 위인지 차례로 비교한다. 62.4절에서 본 "세대는 논리적 주소 경계"라는 설명이 코드로 그대로 드러난다.

**리전 시절:**

```text
// NonGC 힙의 객체에 대해서는 INT32_MAX를 반환한다는 점에 주의.
int GCHeap::WhichGeneration(Object* object)
{
    uint8_t* o = (uint8_t*)object;
    // 관리 힙 밖이면 NGCH에 있는 것이다
    if (!((o < g_gc_highest_address) && (o >= g_gc_lowest_address)))
    {
        return INT32_MAX;
    }
    gc_heap* hp = gc_heap::heap_of (o);
    unsigned int g = hp->object_gennum (o);
    return g;
}

// UOH 객체에 대해서는 max_generation을 반환한다.
int gc_heap::object_gennum (uint8_t* o)
{
    // 주소와 region_info 사이의 매핑을 정의하는 내부 자료구조를 조회한다.
    // 세대는 비트 필드의 하위 2비트에 저장되어 있다.
    return get_region_gen_num (o);
}
```

62.5절에서 예고한 **NonGC 힙 객체가 `int.MaxValue`를 반환하는 이유**가 여기 있다. 객체 주소가 예약된 관리 힙 범위 밖이면 곧바로 `INT32_MAX`를 반환한다. 세대 판정 자체가 이제는 주소 비교가 아니라 **리전 메타데이터 조회**다.

### 세그먼트는 반환되는가 — VM Hoarding

프로그램이 실행되면서 세그먼트가 계속 늘어난다. 없어지기도 하는가. 답은 "그렇다"지만 늘 그렇듯 더 복잡하다.

먼저 **런타임이 세그먼트를 제거하기로 결정하는 상황은 단 하나**다. **가비지 컬렉션 후 세그먼트가 완전히 비었을 때**(객체가 하나도 없을 때)다.

그렇다면 "세그먼트를 제거한다"는 것은 무엇인가. 가장 단순하게는 세그먼트의 예약 주소 범위 전체에 `VirtualFree`(또는 Linux 대응)를 호출해 OS에 반환하는 것이다.

```text
(a) 초기 상태 — 세대 2가 커서 세그먼트 두 개를 쓴다
  ┌───────┬───────┬───────┬───────┐
  │ seg1  │ seg2  │ seg3  │ seg4  │
  │ gen2  │ gen2  │ ephem │ LOH   │
  └───────┴───────┴───────┴───────┘

(b) 압축 GC 발생 — 세대 2 객체가 많이 사라져 seg2가 통째로 비었다
  ┌───────┬───────┬───────┬───────┐
  │ seg1  │(비었음)│ ephem │ LOH   │   ← 하지만 메모리는 여전히 커밋된 상태
  └───────┴───────┴───────┴───────┘

(c) 방법 1 — 그냥 해제한다
  ┌───────┐       ┌───────┬───────┐
  │ seg1  │  ✕    │ ephem │ LOH   │   ← OS에 반환. 다음에 필요하면 다시 예약
  └───────┘       └───────┴───────┘

(d) 방법 2 — VM Hoarding: 예약은 유지하고 커밋만 해제해 재사용 목록에 넣는다
  ┌───────┬───────┬───────┬───────┐
  │ seg1  │ 예약만 │ ephem │ LOH   │   ← 재사용 목록에 보관
  └───────┴───────┴───────┴───────┘
```

(c)는 합리적으로 보이지만 중대한 단점이 있다. **세그먼트를 계속 만들고 없애면 단편화 문제가 생긴다.** 가상 메모리 공간이 넉넉하지 않은 32비트 애플리케이션, 특히 오래 도는 웹 애플리케이션에서 심각했다. .NET 2.0과 ASP.NET 2.0 시절에는 거의 모든 애플리케이션이 32비트였고, 그래서 더 영리한 처리 방식인 **VM Hoarding**이 도입되었다.

빈 세그먼트를 완전히 해제하지 않고 나중에 재사용하려고 쌓아두는(hoard) 것이다. 이 경우

- 세그먼트 메모리 전체가 **예약 상태로 유지**된다.
- 세그먼트 메모리의 대부분이 **커밋 해제**된다(물리 메모리를 쓰지 않는다). 세그먼트 정보를 포함한 앞부분 소량만 커밋 상태로 남는다.
- 세그먼트가 **재사용 가능 목록**에 보관된다. 새 세그먼트가 필요하면 이 목록부터 확인하고, 찾으면 새 세그먼트로 초기화해 쓴다.

> **⚠️ VM Hoarding은 기본적으로 꺼져 있다**
>
> 64비트에서는 주소 공간이 훨씬 넓어 hoarding의 중요성이 떨어진다. 그리고 런타임은 쓰지 않는 가상 메모리를 (예약만이라도) 붙잡고 있기를 원하지 않는다. **평범한 데스크톱이나 콘솔 .NET 애플리케이션(호스팅 API를 쓰지 않는)에서 VM Hoarding은 그냥 비활성이다.**
>
> 다만 세그먼트를 아주 많이 만들고 없애는 역동적인 시나리오라면 64비트에서도 이미 예약된 메모리를 재사용하는 편이 OS에 새로 요청하는 것보다 빠르다. 켤 가치가 있을 수 있다.

설정 방법은 다음과 같다.

```text
환경 변수 또는 레지스트리:  GCRetainVM
runtimeconfig.json:        System.GC.RetainVM
```

```json
{
  "configProperties": {
    "System.GC.RetainVM": true
  }
}
```

**IIS에서 호스팅되는 ASP.NET 웹 애플리케이션은 이것을 기본으로 켠다.** .NET 런타임을 호스팅하는 프로세스가 `System.GC.RetainVM` 설정을 쓸 수 있기 때문이다.

세그먼트가 언제, 왜 만들어지고 사라지는지 추적하고 싶다면 다음 ETW 이벤트를 스택 추적과 함께 켜는 것이 가장 쉽다.

| 이벤트 | 페이로드 |
|---|---|
| `GCCreateSegment_V1` | Address, Size, ClrInstanceID, Type |
| `GCFreeSegment_V1` | Address, ClrInstanceID |

`Type`은 `SmallObjectHeap`, `LargeObjectHeap`, `PinnedObjectHeap` 중 하나이며, NGCH 세그먼트라면 앞서 말한 `ReadOnlyHeap` 값이 나올 수도 있다.

### 리전의 재사용

리전에서도 메커니즘은 비슷하지만 훨씬 유연하다.

각 힙은 빈 리전을 **자유 리스트 배열**(소스 코드의 `region_free_list`)로 추적한다. 세 개다.

1. 기본 SOH 리전용
2. 대형 LOH/POH 리전용
3. 거대 리전용

**비동시 가비지 컬렉션 중에 참조되는 객체가 하나도 없는 리전은 크기에 따라 이 자유 리스트에 추가된다.** 이 자유 리전의 커밋된 부분은 그 GC가 끝날 때까지 커밋 상태로 남고, GC 종료 시점에 어떤 메모리를 커밋 해제할지 결정된다.

할당 중에 새 리전이 필요해지면(63장), 충분히 큰 자유 리전이 있으면 그것을 쓰고, 없으면 예약 구역에서 새로 할당한다.

자유 리스트의 리전에는 **나이(age)** 가 있다. GC가 일어날 때마다 1씩 증가하며 최대 99까지 올라간다. 비동시 GC의 끝에서, 나이가 `max(20, 힙 개수)`보다 큰 리전은 자유 리스트에서 제거되고 커밋된 메모리가 커밋 해제된다. 대응하는 `heap_segment`는 초기화되지만 **예약 구역의 해당 메모리 범위는 절대 해제되지 않는다.**

여기에 더해 GC 종료 시점에 **힙마다 gen0 리전 하나와 gen1 리전 하나의 끝부분이 부분적으로 커밋 해제된다.**

> **📌 리전에는 hoarding 설정이 적용되지 않는다**
>
> 리전은 64비트에서만 쓰이므로 주소 공간 부족이 문제가 아니다. 32비트 세그먼트처럼 가상 메모리에서 반드시 해제해야 할 이유가 없다. 그래서 예약 범위를 아예 반환하지 않는 설계가 가능했고, `GCRetainVM` 같은 hoarding 설정도 의미가 없다.
>
> 리전이 만들어지고 삭제될 때도 동일하게 `GCCreateSegment_V1`과 `GCFreeSegment_V1` 이벤트가 발생한다. POH 리전이면 `PinnedObjectHeap`(= 3) 값이 나온다.

### 시나리오 — LOH가 메모리를 낭비하는가

**상황.** 64비트 워크스테이션 애플리케이션에서 거대한 객체 목록을 처리하는 "빅데이터" 작업을 한다. 전처리 단계에서 전처리된 객체에 대한 참조를 담은 **큰 배열들의 리스트**를 만든다. 각 블록은 **1,000만 개의 참조**를 담는다. 그런데 얼마 뒤 `OutOfMemoryException`이 나고, 예외는 이 배열들을 할당하는 도중에 발생한다.

**1차 분석.** 예외 직전에 VMMap으로 프로세스를 보면 메모리가 정말 엄청나게 소비되고 있다. **개인 작업 집합이 약 15 GB**로, 16 GB인 이 머신의 물리 메모리를 거의 다 썼다. 페이지 파일(`pagefile.sys`)은 **거의 32 GB**로 시스템 관리자가 설정한 최댓값에 도달했다. 배열을 더 만들 여유 메모리가 없다.

**2차 분석 — 눈에 띄는 이상 현상.** LOH 세그먼트 소비가 심상치 않다. **LOH 세그먼트가 아주 많은데, 각각 크기의 절반 정도만 커밋되어 있고 나머지는 예약 상태다.** 왜인가.

62.6절의 표를 보면 64비트 워크스테이션 GC의 **LOH 세그먼트는 128 MB**다. 우리는 1,000만 개의 참조를 담은 배열을 만든다. 참조 하나가 8바이트이므로 배열 하나가 **약 76 MB**를 요구한다.

```text
LOH 세그먼트 (128 MB)
┌────────────────────────────────┬───────────────────┐
│  배열 1개 (76 MB)               │  남은 52 MB       │
└────────────────────────────────┴───────────────────┘
                                   ↑
                       다음 76 MB 배열이 들어가지 못한다
                       → 새 세그먼트를 만들어야 한다
                       → 52 MB가 세그먼트마다 "낭비"된다
```

새 배열을 할당할 때 기존 LOH 세그먼트에는 약 52 MB만 남아 있어 들어가지 않는다. 따라서 **배열을 만들 때마다 새 세그먼트가 만들어지고**, 세그먼트마다 52 MB가 "낭비"된다(작은 객체를 LOH에 활발히 만들어 이 공간을 채우지 않는다는 가정하에).

**3차 분석 — 그런데 이 추론에는 함정이 있다.** 61.2절을 떠올려라. **예약된 가상 메모리는 물리 메모리를 직접 소비하지 않는다.** VMMap 화면을 자세히 보면 LOH 세그먼트의 예약된 부분은 Committed에도 Private에도 계산되지 않는다. **실제 메모리를 낭비하고 있는 것이 아니다.** 이 측정치에 속으면 안 된다. 진짜 원인은 그냥 가용 메모리를 전부 쓰고 있는 것이고, 배열을 한꺼번에 덜 만드는 것 말고는 할 수 있는 일이 없다.

> **⚠️ 그래도 32비트에서는 진짜 문제다**
>
> 실제 메모리를 낭비하지 않더라도 **가상 주소 공간은 낭비하고 있다.** 64비트에서는 주소 공간이 넘쳐나니 문제가 아니다. 그러나 **32비트 .NET 런타임에서는 심각한 문제**가 될 수 있다. 이 상황이라면 처리 데이터를 더 작은 배열로 쪼개서 단일 LOH 세그먼트를 더 잘 채우고 단편화를 피해야 한다.
>
> 참고로 .NET 7+ 리전에서는 대형 리전이 32 MB이고 그보다 큰 할당에는 **거대 리전**이 크기에 맞춰 만들어지므로, 이 특정 낭비 패턴은 훨씬 완화된다.

### 실습 — 힙을 직접 해부하기

지금까지 배운 것을 확인하는 절차다. Windows + WinDbg + SOS 기준이며, 크로스 플랫폼이라면 `dotnet-dump analyze`에서 같은 SOS 명령을 쓸 수 있다.

**1단계 — GC 힙 전체 지도를 뽑는다.**

```text
> !eeheap
```

여기서 확인할 것.

- `Number of GC Heaps` — 1이면 워크스테이션, 여러 개면 서버 모드다.
- 출력 형태 — `generation 0 starts at ...` 형식이면 **세그먼트**, `generation 0:` 아래 세그먼트 줄이 나오면 **리전**이다.
- `Frozen object heap` 항목의 유무 — NonGC 힙이다.
- `Pinned object heap` 항목 — POH다. .NET 5 미만이면 아예 없다.

**2단계 — 세대별 크기와 자유 공간을 본다.**

```text
> !heapstat
Heap             Gen0         Gen1         Gen2          LOH
Heap0         9719400       280232   1217024356     38826368
Free space:                                                 Percentage
Heap0         7042304         1152     10981728     12587408SOH:  1% LOH: 32%
```

이 출력이 말하는 것은 이렇다. **세대 2가 약 1.2 GB로 거대**하고, 그 안의 자유 공간은 약 11 MB뿐이다. **단편화는 문제가 아니다** — 진짜로 살아 있는 객체가 1.2 GB를 차지하고 있다는 뜻이다. 반면 **LOH는 32%가 자유 공간**이므로 이쪽은 단편화를 의심할 만하다.

**3단계 — 세그먼트/리전 크기로 런타임 구성을 역추론한다.**

세그먼트 목록에서 크기가 `0xffefe0`(약 16 MB) 근처로 반복된다면, 62.6절 표에 따라 **32비트 워크스테이션 GC**다. 주소가 8자리로 짧은 것(`024c0000` 같은)도 32비트의 증거다. ephemeral 세그먼트가 하나뿐인 것도 워크스테이션 모드를 시사한다.

확인 사살은 두 명령이다.

```text
> !eeversion
4.7.2117.0 retail
Workstation mode
SOS Version: 4.7.2117.0 retail build

> lmf
...
72f70000 73656000   clr      C:\Windows\Microsoft.NET\Framework\v4.0.30319\clr.dll
...
```

`Framework64`가 아니라 `Framework` 경로에서 `clr.dll`이 로드되었으므로 32비트가 확실하다.

**4단계 — 의심되는 영역의 객체 통계를 본다.**

```text
> !dumpheap -stat 122b1000 132affe0
      MT    Count    TotalSize Class Name
...
04aa58e4    33795       946260 Microsoft.Extensions.Primitives.IChangeToken[]
0b542680    33808       946624 Microsoft.Extensions.Caching.Memory.PostEvictionCallbackRegistration[]
089f26fc    33818      1082176 Microsoft.Extensions.Caching.Memory.PostEvictionDelegate
71f91d64    34858      4327314 System.String
089e2b70    33786      4459752 Microsoft.Extensions.Caching.Memory.CacheEntry
Total 431540 objects
```

주소 범위를 지정하면 **특정 세그먼트 안의 객체만** 통계 낼 수 있다. 오래된 객체를 보려면 **가장 앞쪽(가장 오래된) 세그먼트**를 고르는 것이 요령이다.

**5단계 — 루트를 추적한다.**

```text
> !gcroot 132afd08
Thread 6d5c:
    ...
            ->  0ac5df50 Nop.Services.Catalog.ProductTagService
            ->  033dbacc Nop.Core.Caching.MemoryCacheManager
            ->  033db504 Microsoft.Extensions.Caching.Memory.MemoryCache
                  ...
                  ->  132afd08 Microsoft.Extensions.Caching.Memory.CacheEntry
```

`MemoryCache` 안에 캐시 항목이 33,786개 쌓여 있다는 사실과 이 경로가 합쳐지면 결론이 나온다. **캐시 키가 잘못 설계되어 항목이 무한히 늘어나고 있다.** 실제 사례에서는 캐시 키에 익명 사용자의 쿠키 기반 고객 ID가 들어갔는데, 부하 테스트 스크립트가 쿠키를 관리하지 않아 **모든 요청이 새 고객으로 취급**된 것이 원인이었다.

> **💡 VMMap으로 조사를 시작하지 마라**
>
> 위 실습에서 VMMap을 쓴 것은 이 장의 물리 구조를 눈으로 확인하기 위해서다. **실무에서 메모리 누수 조사를 VMMap으로 시작하는 것은 일반적이지 않다.** 성능 카운터로 큰 그림을 확인한 다음에는 곧바로 WinDbg나 PerfView(또는 `dotnet-gcdump`, dotMemory)로 가는 것이 정석이다.
>
> VMMap의 함정도 있다. Domain 1 Low/High Frequency 힙이 수십 개 보인다고 해서 그것만으로는 아무 문제도 아니다. 프레임워크가 동적 타입을 많이 만들면 자연스럽게 그렇게 된다. **개수가 시간에 따라 늘어나는지**를 확인해야 하고, 그 확인은 `\.NET CLR Loading\Current Assemblies` 같은 카운터로 하는 편이 훨씬 빠르다. 62.9절이 그 이야기다.

> **💡 Rule 13 — 세그먼트 사용을 관찰하라**
>
> **근거.** 세그먼트(그리고 리전)는 관리 힙이 어떻게 조직되는지에 대한 구현 세부사항이다. 대부분의 경우 완벽하게 감춰져 있어 알 필요조차 없다. 그러나 예외가 있다. **세그먼트와 그 배치는 메모리 사용 문제를 분석할 때 진단 단서를 준다.** 드물게는 그 자체가 문제를 일으키기도 한다 — 특히 빠듯한 32비트 환경에서.
>
> **적용 방법.** 조사 중인 프로세스를 가끔 WinDbg 명령이나 VMMap으로 들여다볼 가치가 있다. GC가 만든 세그먼트를 분석하면 실마리를 얻을 수 있다. **세대가 어느 세그먼트에 있는지 아는 것**은 WinDbg 같은 저수준 분석에서 특히 유용하다. 위 실습의 3단계처럼 세그먼트 크기만으로 런타임 비트 수와 GC 모드를 역추론할 수 있는 것이 좋은 예다.

## 62.9 어셈블리 수가 늘어날 때의 메모리 증가

### 관리 힙은 멀쩡한데 프로세스가 자란다

이 장을 마무리하며 다룰 것은, 62.2절의 지도를 갖고 있어야만 풀 수 있는 종류의 문제다. 증상은 이렇다.

- 프로세스의 개인 작업 집합, 개인 바이트, 가상 바이트가 **모두 계속 자란다.**
- 그런데 `\.NET CLR Memory\# Total committed Bytes`(관리 힙 크기)는 **안정적이다.**
- 결국 `OutOfMemoryException`으로 죽는다.

관리 힙이 안정적이니 관리 누수가 아니라고 결론 내리고 네이티브 쪽을 뒤지기 시작하면 몇 주를 날린다. 진짜 원인은 **관리 힙 바깥에 있는 .NET 데이터**, 즉 62.2절에서 본 **로더 힙**이다.

### VMMap이 보여주는 것

프로세스를 VMMap으로 들여다보면 Managed Heap의 개인 작업 집합이 계속 자란다. 관리와 관련된 문제라는 뜻이다. 그런데 Managed Heap 유형 목록을 펼치면 이상한 것이 보인다.

- **GC로 표시된 영역**(우리 애플리케이션이 할당한 객체가 사는 곳)은 아주 천천히 자란다.
- 반면 **`Domain 1`, `Domain 1 Low Frequency Heap`, `Domain 1 High Frequency Heap` 영역이 수십 개** 있다.

**추가 어셈블리가 잔뜩 로드되고 있다는 뜻**이고, 십중팔구 동적 어셈블리 생성이 원인이다.

### 확인 — 카운터 네 개

추측을 확인하는 것이 다음 단계다. 성능 모니터에 로더 관련 카운터를 추가한다.

```text
\.NET CLR Loading(<프로세스명>)\Bytes in Loader Heap
\.NET CLR Loading(<프로세스명>)\Current Classes Loaded
\.NET CLR Loading(<프로세스명>)\Current Assemblies
\.NET CLR Loading(<프로세스명>)\Current appdomains
```

`dotnet-counters`라면 다음 둘이 같은 역할을 한다.

```text
Number of Assemblies Loaded
Number of Methods Jitted
```

> **⚠️ 카운터가 안 움직인다고 무죄는 아니다 — 반대의 경우**
>
> 62.8절 실습에 나온 nopCommerce 사례에서는 Low/High Frequency 힙이 VMMap에 수십 개 보였는데, 위 로더 카운터들은 **몇 시간을 테스트해도 값이 변하지 않았다.** 단서가 거짓이었던 것이다. 프레임워크가 동적 타입을 많이 만들면 힙 영역이 많아지는 것은 정상이고, **개수가 늘지 않는다면 문제가 아니다.**
>
> 반대로 카운터가 계속 증가한다면 그때는 진짜다. **VMMap의 영역 개수가 아니라 카운터의 추세로 판단하라.** 이것이 이 두 사례가 가르치는 교훈이다.

값이 계속 자란다면 다음과 같은 상황을 보게 된다. 실제 진단 사례의 수치다.

```text
Number of Assemblies Loaded              75,000 이상
Number of Methods Jitted                500,000 이상
```

**어셈블리 7만 5천 개와 JIT된 메서드 50만 개는 정상적인 상황의 징후가 결코 아니다.**

### 원인 추적 — ETW로 어셈블리 로드 스택 잡기

어느 코드가 어셈블리를 만들고 있는지 찾아야 한다. PerfView에서 어셈블리 로딩 관련 이벤트를 켠다. Collect 대화상자의 Additional Providers 항목에 다음을 입력한다.

```text
Microsoft-Windows-DotNETRuntime:LoaderKeyword:Always:@StacksEnabled=true
```

로더 관련 이벤트에 관심이 있고, 각 이벤트의 호출 스택을 기록하겠다는 뜻이다. `Current Assemblies` 카운터로 새 어셈블리가 몇 개 로드되는 것이 보일 만한 시간 동안 수집한다.

수집을 멈추고 처리가 끝나면 Events 목록에서 프로세스의 `Microsoft-Windows-DotNETRuntime/Loader/AssemblyLoad` 이벤트를 찾는다. 하나를 고른 뒤 **Time MSec 열에서** 우클릭해 Open Any Stacks를 선택한다(다른 열에서 우클릭하면 스택이 나오지 않는다). 런타임 모듈(`clr`, `mscoree`, `mscoreei`)은 그룹으로 묶고 내 모듈은 그룹을 풀면 범인이 드러난다.

### 가장 흔한 범인 — `XmlSerializer`

실제 사례에서 나온 스택은 `XmlSerializerLeak.Run()` 안의 **`XmlSerializer` 생성자**를 가리켰다. Microsoft 문서가 이 동작을 명시하고 있다.

> 성능을 높이기 위해 XML 직렬화 인프라는 지정된 타입을 직렬화·역직렬화하는 어셈블리를 **동적으로 생성한다.** 인프라는 그 어셈블리를 찾아 재사용한다. 이 동작은 다음 생성자를 쓸 때만 일어난다.
>
> - `XmlSerializer.XmlSerializer(Type)`
> - `XmlSerializer.XmlSerializer(Type, String)`
>
> 다른 생성자를 쓰면 **같은 어셈블리의 여러 버전이 생성되고 절대 언로드되지 않아** 메모리 누수와 성능 저하로 이어진다.

> **⚠️ `XmlSerializer`의 생성자 선택이 메모리 누수를 만든다**
>
> 가장 쉬운 해법은 위의 두 생성자 중 하나를 쓰는 것이다. 다른 생성자를 반드시 써야 한다면 **생성된 `XmlSerializer` 인스턴스를 직접 캐시**해야 한다(`Dictionary`나 `ConcurrentDictionary`에 타입별로 보관).
>
> ```csharp
> // 위험: 루프나 요청 처리 경로에서 매번 호출하면 어셈블리가 쌓인다
> var s = new XmlSerializer(typeof(Order), extraTypes);
>
> // 안전: 타입별로 한 번만 만들어 재사용한다
> private static readonly ConcurrentDictionary<Type, XmlSerializer> Cache = new();
> var s = Cache.GetOrAdd(typeof(Order), t => new XmlSerializer(t));
> ```

> **📌 같은 함정의 다른 얼굴들**
>
> 동적 어셈블리 생성과 관련된 다른 상황에서도 똑같은 원인 진단이 통한다. 언로드하지 않은 채 `AppDomain.CreateDomain`을 반복 호출하는 경우(.NET Framework 전용), 컴파일된 스크립트마다 어셈블리를 만드는 각종 스크립트 엔진, 그리고 `Expression.Compile`이나 `Emit` 기반 코드 생성기가 모두 후보다.

### 수집 가능 어셈블리인데도 언로드되지 않는 경우

.NET Core 이후의 변종 문제가 하나 더 있다. 52장에서 본 **수집 가능 `AssemblyLoadContext`** 로 플러그인을 로드·언로드하도록 만들었는데도 메모리가 끝없이 자라는 경우다.

`dotnet-counters`로 관찰하면 특징이 뚜렷하다.

```text
    GC Committed Bytes (MB)                          44.876
    GC Heap Size (MB)                                37.409
    Number of Assemblies Loaded                      18,570
    Number of Methods Jitted                        129,956
    Time spent in JIT (ms / 1 sec)                  822.663
    Working Set (MB)                              1,081.278
```

**작업 집합이 1 GB를 넘는데 관리 힙은 겨우 37 MB다.** 그리고 로드된 어셈블리 수가 18,570개로 끝없이 늘어난다. 초당 822 ms를 JIT에 쓰고 있다는 것도 비정상이다. 누수되는 메모리는 관리 힙이 아니라 **런타임과 어셈블리 데이터** 쪽에 있다.

```csharp
private IEnumerable<ICommand> LoadPluginCommands(string path)
{
    var assemblyLocation = typeof(Program).Assembly.Location;
    var programPath = Path.GetDirectoryName(assemblyLocation);
    var absolutePath = Path.Combine(programPath, path);

    var pluginContext = new PluginAssemblyLoadContext(absolutePath);
    var assemblyName = AssemblyName.GetAssemblyName(absolutePath);
    var assembly = pluginContext.LoadFromAssemblyName(assemblyName);

    foreach (Type type in assembly.GetTypes())
    {
        if (typeof(ICommand).IsAssignableFrom(type))
        {
            var command = Activator.CreateInstance(type) as ICommand;
            yield return command;
        }
    }
}
```

`pluginContext.Unload()` 호출이 빠진 것처럼 보이지만 **그것이 원인이 아니다.** 어셈블리가 수집 가능하므로 `PluginAssemblyLoadContext` 인스턴스가 가비지 컬렉트되면 언로드가 자동으로 시작된다.

52장에서 본 것처럼 수집 가능 어셈블리는 **협력적 언로드**를 쓴다. 어셈블리와 관련 데이터는 **그 어셈블리에 대한 모든 참조가 사라진 뒤에야** 언로드된다. 어셈블리가 절대 언로드되지 않는다는 것은 곧 **프로그램 안의 무언가가 로드된 어셈블리 내부의 인스턴스를 계속 살려두고 있다**는 뜻이다.

> **⚠️ 어셈블리 누수 조사는 일반 누수 조사와 요령이 다르다**
>
> 이 시점부터는 일반적인 메모리 누수처럼 접근하되(66장), **로드된 수집 가능 어셈블리에서 온 객체의 개수 증가**를 콕 집어 봐야 한다. 그냥 "개수나 메모리 점유가 시간에 따라 늘어나는 객체"를 보면 혼란스럽다. **어셈블리 로딩 자체가 관리 객체를 잔뜩 누적시키기 때문**이다. 어셈블리·런타임 관련 객체가 상위를 도배해서 진짜 원인이 묻힌다.
>
> 실제 사례에서 두 스냅샷을 비교했더니 크기 순위 상위는 전부 어셈블리·런타임 객체였고, 진짜 원인은 눈에 잘 안 띄는 줄에 있었다. `BasePlugin` 인프라에서 온 **`CommandExecuted` 델리게이트가 수천 개**였고, 보유 경로를 따라가니 `OnCommandExecuted` **이벤트가 붙잡고 있었다.** 구독 해제하지 않은 이벤트 핸들러가 플러그인 전체의 언로드를 막고 있던 것이다.

> **💡 진단 순서를 고정해두라**
>
> 이 절의 두 사례를 하나의 절차로 정리하면 이렇다.
>
> 1. 관리 힙 크기와 프로세스 크기를 **동시에** 본다. 둘의 추세가 갈리면 원인은 관리 힙 밖이다.
> 2. `Number of Assemblies Loaded`와 `Bytes in Loader Heap`을 본다. **증가하면** 어셈블리 문제다.
> 3. 어셈블리가 늘어나는 이유가 **생성**인지(`XmlSerializer`, `Emit`, 스크립트 엔진) **언로드 실패**인지(수집 가능 ALC) 구분한다.
> 4. 생성이면 캐시로, 언로드 실패면 **참조를 붙잡고 있는 것**을 찾는다. 대개 이벤트 구독, 정적 필드, 스레드 로컬이다.

## 이 장의 요약

- **GC 힙은 네 개의 축으로 동시에 분할된다.** 크기(SOH/LOH), 수명(세대 0/1/2), 종류(POH/NonGC 힙), 물리(세그먼트/리전). 한 객체는 네 축 모두에서 좌표를 갖는다. .NET이 채택하지 않은 축은 가변성과 타입이다.
- **크기 경계는 정확히 85,000바이트**이며 85 KiB가 아니다. 얕은 크기를 기준으로 하므로 실질적으로 LOH에 가는 것은 배열과 긴 문자열뿐이다. `LOHThreshold`로 올릴 수는 있어도 내릴 수는 없다. **32비트 런타임에서 원소 1,000개 이상인 `double[]`은 8,000바이트여도 LOH로 간다** — 8바이트 정렬 때문이다.
- **세대의 근거는 약한 세대 가설**(대부분의 젊은 객체는 금방 죽는다)이다. 강한 가설은 완전히 확인되지 않았다. .NET은 세대를 **논리적 주소 경계**로 구현하므로 승격이 곧 경계 이동이며 복사가 필요 없다. 수집 범위는 gen0만 / gen0+1 / 전체 셋뿐이다.
- **늙은→젊은 참조는 카드 테이블로 추적한다.** 64비트에서 카드 하나는 256바이트를 덮지만, 쓰기 장벽이 바이트 단위로 set 하므로 실제 세분성은 2,048바이트다. 그 위에 **카드 번들**이 있어 비트 하나가 256 kB, 바이트 하나가 2 MB를 덮으며, 2 GB짜리 늙은 세대를 1,024바이트로 요약한다.
- **POH는 ※.NET 5부터**, 처음부터 고정된 blittable 배열을 위한 영역이다. 목표 시나리오는 P/Invoke용 고정 버퍼 풀이었다. 런타임 자신도 `PinnedHeapHandleTable`을 통해 인터닝 풀과 정적 필드 저장소를 여기 둔다(.NET 7 이전에는 LOH에 있었다).
- **NonGC 힙(구 Frozen heap)** 은 64K 미만 문자열 리터럴과 런타임 타입 객체를 담으며 GC 대상이 아니다. 절대 움직이지 않으므로 JIT이 주소를 코드에 박고 쓰기 장벽을 생략할 수 있다. `GC.GetGeneration`은 **※.NET 8부터 `int.MaxValue`를 반환**한다.
- **세그먼트는 크고 세대가 뒤엉켜 있었고, 리전은 작고 세대마다 하나씩이다.** ※.NET 7 64비트부터 리전이 기본이며 기본 리전 4 MB, 대형 리전 32 MB, 예약 블록은 보통 256 GB다. ephemeral 세그먼트 개념이 사라져 자유 리전을 세대 간에 재사용할 수 있게 되었다.
- **예약과 커밋을 구분하지 못하면 모든 수치가 거짓말이 된다.** 서버 모드 세그먼트 구성은 18 GB를 예약하고 8 MB만 쓸 수 있고, 리전 구성은 256 GB를 예약하고 272 KB만 쓸 수 있다.
- **관리 힙 크기가 안정적인데 프로세스가 자라면 로더 힙을 의심하라.** `Number of Assemblies Loaded`가 답을 준다. 원인은 동적 어셈블리 생성이거나 수집 가능 ALC의 언로드 실패다.
- **Rule 11** 세대 크기를 관찰하라 / **Rule 12** 불필요한 힙 참조를 피하라 / **Rule 13** 세그먼트 사용을 관찰하라.

## 연습 문제

1. `byte[84_000]`, `byte[85_000]`, `new string('x', 42_000)` 세 객체를 만들고 각각 `GC.GetGeneration`을 출력하라. 세 번째가 어느 쪽으로 가는지 예측한 뒤 실행해 확인하고, 문자열 하나가 차지하는 바이트 수를 계산해 경계와 비교하라(54.7절 참고).
2. `runtimeconfig.json`에 `System.GC.LOHThreshold`를 100,000으로 설정한 뒤 1번을 다시 실행하라. 무엇이 달라지는가. 반대로 50,000으로 낮추면 어떻게 되는지도 확인하라.
3. `dotnet-counters monitor`를 켜고 애플리케이션을 실행하면서 `Gen 0 Size (B)`와 `Gen 0 GC Budget (MB)`를 나란히 관찰하라. 두 값의 관계를 62.4절의 설명과 대조해 설명하라.
4. `GC.AllocateArray<byte>(4096, pinned: true)`로 만든 배열과 일반 `new byte[4096]`의 `GC.GetGeneration` 결과를 비교하고, `dotnet-counters`의 `POH (Pinned Object Heap) Size (B)`가 실제로 늘어나는지 확인하라. 그다음 `GC.AllocateArray<string>(10, pinned: true)`를 실행해 사용 중인 런타임 버전에서 예외가 나는지 확인하라.
5. `dotnet-dump collect`로 덤프를 뜬 뒤 `dotnet-dump analyze`에서 `!eeheap`을 실행하라. 출력이 세그먼트 형식인가 리전 형식인가. `Frozen object heap`과 `Pinned object heap` 항목이 있는가. 그 결과로 런타임 버전과 비트 수를 역추론하고 실제와 대조하라.
6. 환경 변수 `DOTNET_GCName`을 설정해 세그먼트 구현으로 되돌린 뒤 5번을 반복하고, `!eeheap` 출력이 어떻게 달라지는지 두 결과를 나란히 비교하라.
7. 루프 안에서 `new XmlSerializer(typeof(SomeType), new Type[] { typeof(Other) })`를 반복 호출하는 프로그램을 작성하고, `dotnet-counters`로 `Number of Assemblies Loaded`와 `GC Heap Size (MB)`, `Working Set (MB)`를 동시에 관찰하라. 세 값의 추세가 어떻게 갈리는지 기록한 뒤, 생성자를 `new XmlSerializer(typeof(SomeType))`으로 바꿔 다시 측정하고 비교하라.
