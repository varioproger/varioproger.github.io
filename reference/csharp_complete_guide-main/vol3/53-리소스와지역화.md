# 53장. 리소스와 지역화

> **이 장의 위치** — 52장에서 어셈블리를 구성하는 네 가지 중 **리소스**만 남겨두고 넘어갔다. 매니페스트의 `ManifestResourceDef` 테이블이 존재한다는 것(52.2절), `Assembly.GetSatelliteAssembly`라는 메서드가 있다는 것(52.4절), `PLATFORM_RESOURCE_ROOTS`라는 프로빙 속성이 있다는 것(52.15절)까지만 말하고 미뤘다. 이 장에서 그 셋을 하나로 잇는다. `.resx` 파일 하나가 어떻게 `.resources` 스트림이 되고, 그것이 어떻게 위성 어셈블리라는 별도의 `.dll`로 갈라져 나가며, 런타임이 사용자의 언어에 맞는 것을 어떤 순서로 찾는지가 이 장의 전부다.
>
> **선수 지식** — 52장(어셈블리), 38장(포매팅과 파싱, 국제화), 4장(프로젝트와 대상 프레임워크)
>
> **이 장에서 다루지 않는 것** — 숫자·날짜의 문화권별 포매팅 규칙과 `IFormatProvider`는 38장에서 이미 다뤘다. 리소스를 리플렉션으로 열거하는 저수준 API는 57.10절에서, 문자열 비교의 문화권 의존성은 35.4절에서 다룬다.

## 53.1 리소스를 직접 임베드하기

### 리소스란 무엇인가

애플리케이션은 실행 코드만으로 이루어지지 않는다. 텍스트, 이미지, XML 파일 같은 콘텐츠가 함께 간다. .NET에서는 이런 콘텐츠를 **리소스(resource)** 로 어셈블리 안에 담을 수 있다.

리소스를 쓰는 이유는 크게 두 가지로 갈린다. 이 둘은 겹치지만 요구사항이 다르고, 이 장의 구성도 그 차이를 따라간다.

1. **소스 코드에 넣을 수 없는 데이터를 넣기 위해.** 이미지, 폰트, 인증서, 룩업 테이블 같은 것들이다.
2. **다국어 애플리케이션에서 번역이 필요할 수 있는 데이터를 담기 위해.** UI 문자열, 오류 메시지, 라이선스 고지문 같은 것들이다.

첫 번째 용도는 단순하다. 두 번째 용도가 이 장의 나머지 전부를 잡아먹는다.

정의는 아주 간단하게 내릴 수 있다.

> 어셈블리 리소스는 **이름이 붙은 바이트 스트림**이다.

어셈블리를 "문자열을 키로 하고 바이트 배열을 값으로 하는 사전"이라고 생각해도 좋다. 실제로 그렇게 생겼다. `banner.jpg`와 `data.xml`이라는 리소스를 담은 어셈블리를 `ildasm`으로 디스어셈블하면 다음이 보인다.

```il
.mresource public banner.jpg
{
  // Offset: 0x00000F58 Length: 0x000004F6
}
.mresource public data.xml
{
  // Offset: 0x00001458 Length: 0x0000027E
}
```

`Offset`과 `Length`가 눈에 띈다. 52.2절에서 본 **ManifestResourceDef 테이블**의 항목이 그대로 드러난 것이다. 그 테이블에는 리소스 이름, 공개 여부 플래그, 리소스를 담은 파일을 가리키는 FileDef 인덱스, 그리고 **PE 파일 내 시작 오프셋**이 들어 있다고 했다. `.mresource public`의 `public`이 그 플래그이고, 주석의 두 숫자가 오프셋과 길이다.

즉 임베드된 리소스는 별도의 파일이 아니라 **PE 파일 안의 연속된 바이트 구간**이다. 어셈블리를 로드하면 OS가 그 파일을 메모리 매핑하고, 리소스를 읽는다는 것은 그 매핑된 영역의 특정 오프셋부터 읽는다는 뜻이다. 이 사실은 뒤에서 성능을 이야기할 때 다시 나온다.

> **📌 `public`과 `private` 리소스**
>
> ManifestResourceDef 항목의 플래그는 리소스가 어셈블리 밖에서 보이는지를 정한다. `ildasm` 덤프에 `.mresource public`이 아니라 `.mresource private`로 나오는 리소스도 있다. C# 컴파일러는 `/resource:` 스위치로 넣은 리소스를 public으로, `/linkresource:`로 연결한 것도 public으로 만든다. MSBuild의 `EmbeddedResource` 항목은 기본이 public이다. 실무에서 private 리소스를 만들 일은 거의 없고, `Assembly.GetManifestResourceStream`은 어느 쪽이든 잘 읽는다.

### 직접 임베드하기 — 빌드 작업 `Embedded Resource`

가장 단순한 방법이다. Visual Studio에서는 두 단계로 끝난다.

1. 파일을 프로젝트에 추가한다.
2. 파일의 **빌드 작업(Build Action)** 을 `Embedded Resource`로 바꾼다.

SDK 스타일 프로젝트에서는 `.csproj`에 직접 쓰는 편이 명확하다.

```xml
<ItemGroup>
  <EmbeddedResource Include="pictures\banner.jpg" />
  <EmbeddedResource Include="data.xml" />
</ItemGroup>
```

와일드카드도 쓸 수 있다.

```xml
<ItemGroup>
  <EmbeddedResource Include="Assets\**\*.json" />
</ItemGroup>
```

### 리소스 이름은 어떻게 정해지는가

여기서 첫 번째 함정이 나온다. **파일 이름이 곧 리소스 이름이 아니다.**

Visual Studio(정확히는 MSBuild)는 리소스 이름 앞에 항상 **프로젝트의 기본 네임스페이스(`RootNamespace`)** 를 붙이고, 그다음 파일이 들어 있는 **하위 폴더 이름들**을 붙인다.

프로젝트의 기본 네임스페이스가 `Westwind.Reports`이고 파일이 `pictures` 폴더 안의 `banner.jpg`라면, 리소스 이름은 이렇게 된다.

```text
Westwind.Reports.pictures.banner.jpg
```

경로 구분자가 점(`.`)으로 바뀌었을 뿐이다. 규칙을 표로 정리하면 다음과 같다.

| 요소 | 값 | 결과 기여분 |
|---|---|---|
| `RootNamespace` | `Westwind.Reports` | `Westwind.Reports` |
| 하위 폴더 | `pictures` | `.pictures` |
| 파일 이름 | `banner.jpg` | `.banner.jpg` |
| **최종 리소스 이름** | | `Westwind.Reports.pictures.banner.jpg` |

> **⚠️ 리소스 이름은 대소문자를 구분한다**
>
> `GetManifestResourceStream("Westwind.Reports.Pictures.banner.jpg")`는 폴더 이름이 실제로 `pictures`라면 `null`을 반환한다. 예외가 아니라 `null`이다.
>
> 이 규칙 때문에 **Visual Studio의 프로젝트 하위 폴더 이름이 사실상 대소문자를 구분하게 된다.** Windows 파일 시스템은 대소문자를 구분하지 않으므로 폴더 이름을 `Pictures`에서 `pictures`로 바꿔도 파일 시스템은 아무 말이 없지만, 빌드된 리소스 이름은 바뀌고 런타임에 조용히 `null`이 나온다. Git에서 폴더 이름의 대소문자만 바뀐 커밋이 들어왔을 때 이 사고가 잘 난다.

두 번째 함정은 폴더나 파일 이름이 C# 식별자로 쓸 수 없는 문자를 담고 있을 때다.

> **⚠️ 하이픈과 숫자로 시작하는 폴더 이름**
>
> MSBuild의 리소스 이름 생성 로직은 폴더 이름을 네임스페이스 조각처럼 다루면서 유효하지 않은 식별자 문자를 `_`로 치환한다. 폴더가 `my-assets`라면 리소스 이름 조각은 `my_assets`가 되고, 폴더가 `2024`라면 `_2024`가 된다.
>
> 규칙을 외우려 하지 마라. **빌드한 뒤 `GetManifestResourceNames()`로 실제 이름을 찍어보는 것**이 유일하게 믿을 만한 방법이다.

이름 생성 규칙에 의존하기 싫다면 `LogicalName` 메타데이터로 이름을 직접 지정할 수 있다. 이쪽이 훨씬 안전하다.

```xml
<ItemGroup>
  <EmbeddedResource Include="pictures\banner.jpg" LogicalName="banner.jpg" />
</ItemGroup>
```

이제 리소스 이름은 정확히 `banner.jpg`다. 접두사도 없고 폴더 이름도 없다.

> **💡 리소스가 서너 개를 넘어가면 `LogicalName`을 써라**
>
> 자동 생성된 이름은 `RootNamespace`를 바꾸거나 파일을 다른 폴더로 옮기는 순간 함께 바뀐다. 그리고 그 변화는 **컴파일 오류를 내지 않는다.** 리소스 이름은 문자열 리터럴이기 때문이다. 라이브러리를 배포하는 입장이라면 `LogicalName`으로 이름을 고정해두는 편이 리팩터링 사고를 원천 차단한다.
>
> 더 나은 방법은 이름 상수를 한곳에 모으고, 그것이 실제로 존재하는지 검증하는 단위 테스트를 하나 두는 것이다. 53.5절에서 이 패턴을 다시 본다.

### 리소스 읽기 — `GetManifestResourceStream`

리소스를 꺼내려면 그 리소스를 담은 어셈블리에서 `GetManifestResourceStream`을 호출한다. 반환값은 `Stream`이고, 다른 스트림과 똑같이 읽으면 된다.

```csharp
using System.Reflection;
using System.Xml;

Assembly a = Assembly.GetEntryAssembly()!;

using (Stream s = a.GetManifestResourceStream("TestProject.data.xml")!)
using (XmlReader r = XmlReader.Create(s))
{
    // ... XML 읽기
}
```

이미지도 마찬가지다. 다음은 Windows Forms 계열에서 쓰는 형태다.

```csharp
using System.Drawing;   // System.Drawing.Common 패키지 필요, Windows 전용

System.Drawing.Image image;
using (Stream s = a.GetManifestResourceStream("TestProject.banner.jpg")!)
    image = System.Drawing.Image.FromStream(s);
```

반환되는 스트림은 **탐색 가능(seekable)** 하다. 즉 `Length`를 물어볼 수 있고 `Position`을 옮길 수 있다. 그래서 바이트 배열로 통째로 읽는 것도 간단하다.

```csharp
byte[] data;
using (Stream s = a.GetManifestResourceStream("TestProject.banner.jpg")!)
    data = new BinaryReader(s).ReadBytes((int)s.Length);
```

### 네임스페이스 접두사를 타입으로 대신하기

Visual Studio로 리소스를 임베드했다면 앞서 본 네임스페이스 접두사를 잊지 말고 붙여야 한다. 오타를 줄이려면 접두사를 **타입으로** 지정하는 오버로드를 쓴다. 그 타입의 네임스페이스가 접두사로 쓰인다.

```csharp
using (Stream s = a.GetManifestResourceStream(typeof(X), "data.xml")!)
{
    // ...
}
```

`X`는 원하는 네임스페이스를 가진 아무 타입이면 된다. 보통은 리소스 파일과 **같은 프로젝트 폴더에 있는 타입**을 고른다. 그러면 파일과 타입이 같이 움직이므로 폴더를 옮겨도 어긋나지 않는다.

> **⚠️ 타입 오버로드는 폴더 구조와 네임스페이스가 일치할 때만 맞는다**
>
> 이 오버로드는 `typeof(X).Namespace + "." + name`을 조립할 뿐이다. 리소스 이름 생성은 **폴더 경로**를 기준으로 하고, 타입의 네임스페이스는 **소스 코드에 쓰인 `namespace` 선언**을 기준으로 한다. 둘이 다르면(예: 폴더는 `Assets`인데 클래스는 `namespace MyApp;`으로 선언) 이 오버로드는 틀린 이름을 만든다.
>
> SDK 스타일 프로젝트에서 `<RootNamespace>`를 프로젝트 이름과 다르게 바꿔놓은 경우에도 어긋나기 쉽다.

### 리소스 목록 확인과 메타데이터

디버깅에 가장 유용한 멤버를 정리하면 다음과 같다.

| 멤버 | 반환 | 용도 |
|---|---|---|
| `GetManifestResourceNames()` | `string[]` | 어셈블리 안 모든 리소스 이름 |
| `GetManifestResourceStream(string)` | `Stream?` | 리소스를 스트림으로. 없으면 `null` |
| `GetManifestResourceStream(Type, string)` | `Stream?` | 타입의 네임스페이스를 접두사로 사용 |
| `GetManifestResourceInfo(string)` | `ManifestResourceInfo?` | 리소스의 위치 정보(`ResourceLocation`, 파일 이름, 참조 어셈블리) |

리소스 이름을 몰라서 헤맬 때는 이 한 줄이면 끝난다.

```csharp
foreach (string name in Assembly.GetExecutingAssembly().GetManifestResourceNames())
    Console.WriteLine(name);
```

`GetManifestResourceInfo`는 리소스가 실제로 어디에 있는지 알려준다. `ManifestResourceInfo.ResourceLocation`은 `ResourceLocation` 열거형이고, `Embedded`(이 PE 안에 있음), `ContainedInAnotherAssembly`, `ContainedInManifestFile` 플래그의 조합이다.

```csharp
var info = Assembly.GetExecutingAssembly()
                   .GetManifestResourceInfo("TestProject.data.xml");
Console.WriteLine(info?.ResourceLocation);   // 예: Embedded, ContainedInManifestFile
```

> **📌 `ContainedInAnotherAssembly`는 다중 파일 어셈블리의 유물**
>
> 52.3절에서 본 다중 파일 어셈블리(.NET Framework 전용)에서는 리소스가 매니페스트를 담은 파일이 아닌 다른 모듈에 있을 수 있었다. 그럴 때 이 플래그가 켜졌다. .NET 5+에서는 어셈블리가 항상 단일 파일이므로 사실상 볼 일이 없다.

### 임베드 리소스의 런타임 동작과 비용

리소스를 읽을 때 무슨 일이 일어나는지 한 층 내려가 보자.

1. `GetManifestResourceStream`은 ManifestResourceDef 테이블에서 이름으로 항목을 찾는다. 이건 메타데이터 조회라 빠르다.
2. 항목이 가리키는 오프셋을 PE 파일의 메모리 매핑 뷰에 더해 시작 주소를 구한다.
3. 그 주소와 길이로 `UnmanagedMemoryStream`을 만들어 반환한다.

핵심은 **3번에서 데이터를 복사하지 않는다**는 것이다. 반환된 스트림은 매핑된 페이지를 직접 가리킨다. 실제 디스크 I/O는 그 페이지를 처음 읽을 때 페이지 폴트로 일어난다. 그래서 5MB짜리 리소스가 있어도 어셈블리 로드가 느려지지는 않는다. 읽는 순간에만 비용이 든다.

반면 `new BinaryReader(s).ReadBytes((int)s.Length)`처럼 바이트 배열로 통째로 읽으면 **그 순간 힙에 5MB가 할당된다.** 큰 리소스를 다룰 때는 스트림을 그대로 쓰는 편이 훨씬 낫다.

| 접근 방식 | 관리 힙 할당 | 적합한 경우 |
|---|---|---|
| 스트림을 그대로 소비 (`XmlReader.Create(s)` 등) | 없음(파서 버퍼만) | 큰 파일, 한 번만 읽는 경우 |
| `ReadBytes((int)s.Length)` | 전체 크기 | 작은 파일, 반복해서 쓰는 경우 |
| `s.CopyTo(memoryStream)` | 전체 크기 × 재할당 | 피하라. 위 둘 중 하나가 낫다 |

> **⚠️ 임베드 리소스는 어셈블리 크기를 그대로 키운다**
>
> 리소스는 압축되지 않는다. 20MB짜리 동영상을 임베드하면 `.dll`이 20MB 커진다. 그리고 그 어셈블리는 **로드할 때마다 통째로 매핑된다.** 컨테이너 이미지 크기, 콜드 스타트 시간, NuGet 패키지 크기가 모두 영향을 받는다.
>
> 판단 기준은 단순하다. **배포 단위와 반드시 함께 움직여야 하는 것만** 임베드하라. 나머지는 `Content` 빌드 작업으로 파일로 두고 `AppContext.BaseDirectory` 기준으로 읽는 편이 낫다. 다만 `PublishSingleFile` 단일 파일 배포에서는 `Content` 파일이 실행 파일 옆에 따로 놓이므로, "정말 파일 하나로 배포"가 목표라면 임베드가 답이다.

### 다른 빌드 작업과 헷갈리지 말 것

`Embedded Resource`와 이름이 비슷하거나 역할이 겹쳐 보이는 빌드 작업이 여럿 있다. 이 표를 기억해두면 53.2절이 훨씬 쉬워진다.

| 빌드 작업 | 결과물 | 접근 방법 |
|---|---|---|
| `Embedded Resource` | 어셈블리 안 독립 리소스 스트림 | `Assembly.GetManifestResourceStream` |
| `Content` | 출력 폴더에 복사된 별도 파일 | `File.OpenRead`, 상대 경로 |
| `None` | 아무것도 안 함(기본) | — |
| `Resource` (**WPF 전용**) | `<AssemblyName>.g.resources` 컨테이너 안 항목 | pack URI, `Application.GetResourceStream` |
| `Page` (**WPF 전용**) | 컴파일된 XAML(`.baml`), 역시 `.g.resources` 안 | XAML 로더가 자동 처리 |

> **⚠️ WPF의 `Resource`는 `Embedded Resource`가 아니다**
>
> WPF 애플리케이션에서 항목의 빌드 작업을 `Resource`로 설정하는 것은 `Embedded Resource`로 설정하는 것과 **전혀 다르다.** 전자는 항목을 `<AssemblyName>.g.resources`라는 `.resources` 파일 안에 넣고, 그 내용은 WPF의 `Application` 클래스를 통해 **URI를 키로** 접근한다. 자세한 것은 53.2절에서 다룬다.
>
> 혼란을 더하는 것은 WPF가 "리소스"라는 용어를 한 번 더 오버로드한다는 사실이다. XAML의 **정적 리소스(`StaticResource`)와 동적 리소스(`DynamicResource`)** 는 어셈블리 리소스와 아무 관계가 없다. 그것들은 `ResourceDictionary`에 든 객체를 XAML에서 참조하는 메커니즘일 뿐이다. 같은 프로젝트 안에 세 가지 "리소스"가 공존한다.

> **⚠️ Windows Store(UWP) 앱은 어셈블리 임베드 리소스를 지원하지 않는다**
>
> UWP에서는 어셈블리에 리소스를 임베드하는 방식이 지원되지 않는다. 대신 추가 파일을 **배포 패키지**에 넣고, 애플리케이션의 `StorageFolder`(`Package.Current.InstalledLocation`)에서 읽어야 한다. 데스크톱 코드를 UWP로 옮길 때 조용히 깨지는 대표적인 지점이다.

## 53.2 `.resources` 파일과 `.resx` 파일

### `.resources`는 리소스 안의 리소스다

앞 절에서 리소스를 "이름 붙은 바이트 스트림"이라고 정의했다. `.resources` 파일은 그 정의를 그대로 만족한다. `.resources` 파일도 결국 **어셈블리 안의 임베디드 리소스 하나**로 끝난다. 다른 종류의 파일과 다를 게 없다.

다른 것은 두 가지다.

1. **콘텐츠를 먼저 `.resources` 파일로 패키징해야 한다.**
2. **접근을 `GetManifestResourceStream`이 아니라 `ResourceManager`나 pack URI로 한다.**

왜 이런 층을 하나 더 두는가? `.resources` 파일은 **번역이 필요할 수 있는 콘텐츠를 담기 위해 설계된 컨테이너**이기 때문이다. 하나의 `.resources` 안에 수백 개의 이름/값 쌍이 들어가고, 그것 전체를 언어별로 통째 갈아 끼우는 것이 목표다. 리소스 하나하나를 독립 임베디드 리소스로 두면 이 교체가 불가능하다.

구조를 그림으로 보면 이렇다.

```text
┌──────────────────────────── MyApp.dll ────────────────────────────┐
│                                                                   │
│  ManifestResourceDef 테이블                                        │
│  ┌─────────────────────────────────────────────────────────┐      │
│  │ "MyApp.banner.jpg"        → offset 0x0F58, len 0x04F6    │      │
│  │ "MyApp.data.xml"          → offset 0x1458, len 0x027E    │      │
│  │ "MyApp.welcome.resources" → offset 0x16D8, len 0x0912    │──┐   │
│  └─────────────────────────────────────────────────────────┘  │   │
│                                                               │   │
│  ┌───────────── welcome.resources (바이너리 컨테이너) ─────────┐│   │
│  │  "Greeting"        → "hello"                             │◄┘   │
│  │  "DefaultFontSize" → (Int32) 10                          │     │
│  │  "Farewell"        → "goodbye"                           │     │
│  └──────────────────────────────────────────────────────────┘     │
└───────────────────────────────────────────────────────────────────┘
```

바깥쪽 사전은 CLR 메타데이터(ManifestResourceDef)이고, 안쪽 사전은 `.resources` 포맷이 정의한 자체 인덱스다. `ResourceManager`가 읽는 것은 안쪽 사전이다.

`.resources` 파일은 **바이너리 구조**라서 사람이 편집할 수 없다. 그래서 .NET과 Visual Studio가 제공하는 도구에 의존해야 한다. 문자열이나 단순 데이터 타입을 다루는 표준적인 접근법은 **`.resx` 형식**을 쓰는 것이고, 이것을 Visual Studio나 `resgen` 도구가 `.resources` 파일로 변환한다.

### `.resx` — 디자인 타임 형식

`.resx` 파일은 `.resources` 파일을 만들기 위한 **디자인 타임 형식**이다. XML이고, 이름/값 쌍으로 구조화되어 있다. 뼈대만 보면 이렇다.

```xml
<root>
  <data name="Greeting">
    <value>hello</value>
  </data>
  <data name="DefaultFontSize" type="System.Int32, mscorlib">
    <value>10</value>
  </data>
</root>
```

`type` 특성이 없으면 값은 문자열로 취급된다. `type`이 있으면 그 타입의 `TypeConverter`가 문자열을 파싱한다.

실제 Visual Studio가 만드는 `.resx`는 앞에 XSD 스키마와 `resheader` 요소들이 붙는다.

```xml
<?xml version="1.0" encoding="utf-8"?>
<root>
  <xsd:schema id="root" xmlns:xsd="http://www.w3.org/2001/XMLSchema"
              xmlns:msdata="urn:schemas-microsoft-com:xml-msdata">
    <!-- ... 스키마 본문 ... -->
  </xsd:schema>
  <resheader name="resmimetype">
    <value>text/microsoft-resx</value>
  </resheader>
  <resheader name="version">
    <value>2.0</value>
  </resheader>
  <resheader name="reader">
    <value>System.Resources.ResXResourceReader, System.Windows.Forms, ...</value>
  </resheader>
  <resheader name="writer">
    <value>System.Resources.ResXResourceWriter, System.Windows.Forms, ...</value>
  </resheader>

  <data name="Greeting" xml:space="preserve">
    <value>hello</value>
  </data>
</root>
```

> **⚠️ `xml:space="preserve"`가 없으면 앞뒤 공백이 사라진다**
>
> `<value>` 안의 문자열에서 선행·후행 공백을 살리려면 `<data>`에 `xml:space="preserve"`가 있어야 한다. Visual Studio 디자이너는 이걸 자동으로 붙이지만, 스크립트로 `.resx`를 생성하거나 번역 업체가 되돌려준 파일을 병합할 때 빠지기 쉽다.
>
> `"항목 "` 뒤에 값을 이어붙이는 식의 문자열이라면 이 한 칸이 사라진 채 배포된다. 애초에 그런 문자열 조립을 하지 않는 것이 답이고(53.5절), 차선책은 `.resx`를 커밋할 때 `xml:space` 유무를 검사하는 것이다.

Visual Studio에서 `.resx` 파일을 만들려면 프로젝트 항목 유형 **Resources File**을 추가한다. 나머지는 자동으로 처리된다.

- 올바른 헤더가 생성된다.
- 문자열, 이미지, 파일, 기타 데이터를 추가할 수 있는 디자이너가 제공된다.
- 컴파일 시 `.resx` 파일이 `.resources` 형식으로 **자동 변환되어 어셈블리에 임베드된다.**
- 나중에 데이터에 접근하는 것을 돕는 **클래스가 자동 생성된다.**

> **⚠️ 리소스 디자이너는 이미지를 `System.Drawing.Image`로 넣는다**
>
> `.resx` 디자이너로 이미지를 추가하면 바이트 배열이 아니라 **타입이 지정된 `Image` 객체**(`System.Drawing.dll`)로 저장된다. 이 때문에 WPF 애플리케이션에는 부적합하다. WPF는 `System.Drawing.Image`를 모르고, 애초에 `System.Drawing.Common`은 .NET 7 이후 Windows 전용으로 못 박혔다.
>
> WPF에서 URI로 참조해야 하는 이미지나 유사 콘텐츠는 `.resx`가 아니라 Visual Studio의 **`Resource` 빌드 작업**을 써야 한다. 지역화가 필요한지 여부와 무관하게 그렇다.

### 빌드 파이프라인 전체

`.resx` 한 개가 어셈블리 안의 바이트 구간이 되기까지의 경로를 단계별로 따라가 보자. 이 파이프라인을 이해하면 이 장의 나머지가 전부 따라온다.

```text
  [1] Greeting.resx                      개발자가 편집하는 XML
        │
        │  MSBuild: GenerateResource 태스크
        │  (.NET Framework SDK에서는 resgen.exe)
        ▼
  [2] obj\Debug\net8.0\
        MyApp.Greeting.resources          바이너리 컨테이너
        │
        │  csc /resource:obj\...\MyApp.Greeting.resources
        ▼
  [3] bin\Debug\net8.0\MyApp.dll
        ManifestResourceDef 항목 하나
        이름 = "MyApp.Greeting.resources"
        │
        │  런타임: new ResourceManager("MyApp.Greeting", asm)
        ▼
  [4] ResourceManager
        └─ GetManifestResourceStream("MyApp.Greeting.resources")
           └─ ResourceReader가 내부 인덱스를 파싱
              └─ GetString("Hello") → "안녕"
```

각 단계에서 이름이 어떻게 변형되는지가 핵심이다.

| 단계 | 이름 |
|---|---|
| 소스 파일 | `Greeting.resx` |
| 중간 산출물 | `MyApp.Greeting.resources` (RootNamespace + 폴더 + 파일명) |
| 매니페스트 리소스 이름 | `MyApp.Greeting.resources` |
| `ResourceManager`의 `baseName` | `MyApp.Greeting` (**확장자 없음**) |

> **⚠️ `baseName`에 `.resources`를 붙이면 안 된다**
>
> `ResourceManager`의 첫 번째 인자는 **확장자를 뺀** 이름이다. `ResourceManager`가 내부에서 `baseName + ".resources"`를 조립해 매니페스트 리소스를 찾기 때문이다. `new ResourceManager("MyApp.Greeting.resources", asm)`라고 쓰면 `MyApp.Greeting.resources.resources`를 찾다가 실패한다.
>
> 실패 시점도 함정이다. 생성자는 예외를 던지지 않는다. **첫 `GetString` 호출에서** `MissingManifestResourceException`이 난다.

`.NET Framework` SDK에는 명령줄 도구 `resgen.exe`가 있고, `.resx`와 `.resources`를 서로 변환한다.

```text
resgen Greeting.resx Greeting.resources
resgen Greeting.resources Greeting.resx
```

> **📌 .NET SDK에는 `resgen.exe`가 없다**
>
> `resgen.exe`는 .NET Framework SDK(그리고 Windows SDK) 도구다. .NET 5+ SDK에는 없다. 대신 MSBuild의 `GenerateResource` 태스크가 같은 일을 인프로세스로 처리한다. 그래서 `dotnet build`만 하면 `.resx` 변환이 알아서 일어나고, 별도 도구를 호출할 일이 없다. 반대로 **CI에서 `.resx`를 직접 변환하려던 스크립트가 .NET SDK만 설치된 머신에서 깨지는** 일이 종종 생긴다.

### `ResourceManager`로 읽기

`ResourceManager` 클래스는 어셈블리에 임베드된 `.resources` 파일을 읽는다.

```csharp
using System.Reflection;
using System.Resources;

ResourceManager r = new ResourceManager("welcome",
                                        Assembly.GetExecutingAssembly());
```

첫 번째 인자는 Visual Studio에서 컴파일된 리소스라면 **네임스페이스 접두사가 붙어야 한다.** 앞의 표에서 본 대로다.

내용에 접근할 때는 `GetString`이나 `GetObject`(캐스팅 필요)를 호출한다.

```csharp
string greeting = r.GetString("Greeting")!;
int fontSize    = (int)r.GetObject("DefaultFontSize")!;
Image image     = (Image)r.GetObject("flag.png")!;
```

`.resources` 파일의 내용을 열거하려면 `ResourceSet`을 얻는다.

```csharp
using System.Globalization;
using System.Collections;

ResourceManager r = new ResourceManager("welcome", Assembly.GetExecutingAssembly());
ResourceSet set = r.GetResourceSet(CultureInfo.CurrentUICulture,
                                   createIfNotExists: true,
                                   tryParents: true)!;

foreach (DictionaryEntry entry in set)
    Console.WriteLine(entry.Key);
```

`tryParents: true`가 중요하다. 이 플래그가 폴백 체인을 따라 부모 문화권까지 올라간다. 폴백 규칙은 53.4절에서 자세히 본다.

`ResourceManager`의 주요 멤버를 정리한다.

| 멤버 | 설명 |
|---|---|
| `GetString(string)` | 현재 UI 문화권 기준으로 문자열 조회. 없으면 `null` |
| `GetString(string, CultureInfo)` | 문화권을 명시해 조회 |
| `GetObject(string)` | 임의 타입 조회. `object?` 반환 |
| `GetStream(string)` | 바이너리 리소스를 `UnmanagedMemoryStream`으로 |
| `GetResourceSet(CultureInfo, bool, bool)` | 특정 문화권의 전체 집합 |
| `ReleaseAllResources()` | 캐시된 `ResourceSet`을 모두 해제 |
| `IgnoreCase` | 키 조회 시 대소문자 무시 여부(기본 `false`) |
| `BaseName` | 생성 시 준 `baseName` |
| `CreateFileBasedResourceManager(...)` | **정적**. 어셈블리 대신 디스크의 `.resources` 파일을 직접 읽는 매니저 생성 |

> **⚠️ `GetString`은 키가 없으면 `null`을, 리소스 집합 자체가 없으면 예외를 던진다**
>
> 두 실패 모드가 다르다는 것을 알아야 진단이 빨라진다.
>
> - **키만 없음** → `null` 반환. 조용하다.
> - **`.resources` 컨테이너를 못 찾음** → `MissingManifestResourceException`. 시끄럽다.
>
> 즉 `GetString("Greetng")`(오타)은 `null`을 주고, `new ResourceManager("Welcome", ...)`(대소문자 틀림)은 예외를 준다. 프로덕션에서 `null` 참조 예외가 UI 문자열 자리에서 터진다면 십중팔구 첫 번째다.

> **💡 `IgnoreCase = true`는 쓰지 마라**
>
> 대소문자 사고를 막아주는 것처럼 보이지만, 대가로 조회가 느려지고(내부적으로 대소문자 무시 비교용 해시 테이블을 따로 만든다) 무엇보다 **"어느 쪽이 정본인지"가 흐려진다.** 키 이름 규칙을 정하고 코드 생성으로 강제하는 편이 낫다. 강력한 형식의 래퍼(바로 아래)를 쓰면 이 문제 자체가 사라진다.

### 자동 생성되는 강력한 형식 래퍼

Visual Studio에서 `.resx` 파일을 만들면 **같은 이름의 클래스가 자동 생성된다.** 각 항목을 조회하는 속성이 붙는다. `Greeting.resx`를 만들면 `Greeting.Designer.cs`가 함께 생기고, 대략 다음과 같은 코드가 들어간다.

```csharp
// <auto-generated/> — Greeting.Designer.cs (요약)
namespace MyApp
{
    internal class Greeting
    {
        private static global::System.Resources.ResourceManager resourceMan;
        private static global::System.Globalization.CultureInfo resourceCulture;

        internal static global::System.Resources.ResourceManager ResourceManager
        {
            get
            {
                if (object.ReferenceEquals(resourceMan, null))
                {
                    var temp = new global::System.Resources.ResourceManager(
                        "MyApp.Greeting", typeof(Greeting).Assembly);
                    resourceMan = temp;
                }
                return resourceMan;
            }
        }

        internal static global::System.Globalization.CultureInfo Culture
        {
            get { return resourceCulture; }
            set { resourceCulture = value; }
        }

        internal static string Hello
        {
            get { return ResourceManager.GetString("Hello", resourceCulture); }
        }
    }
}
```

이제 문자열 리터럴 없이 이렇게 쓴다.

```csharp
Console.WriteLine(Greeting.Hello);
```

키 오타가 **컴파일 오류**가 된다는 것이 이 방식의 가장 큰 이득이다.

SDK 스타일 프로젝트에서 생성기를 켜려면 `.csproj`에 다음을 넣는다.

```xml
<ItemGroup>
  <EmbeddedResource Update="Greeting.resx">
    <Generator>ResXFileCodeGenerator</Generator>
    <LastGenOutput>Greeting.Designer.cs</LastGenOutput>
  </EmbeddedResource>
  <Compile Update="Greeting.Designer.cs">
    <DesignTime>True</DesignTime>
    <AutoGen>True</AutoGen>
    <DependentUpon>Greeting.resx</DependentUpon>
  </Compile>
</ItemGroup>
```

> **⚠️ `ResXFileCodeGenerator`는 Visual Studio(또는 `dotnet` SDK의 대응 태스크)가 돌린다**
>
> `Generator` 메타데이터는 **Visual Studio의 단일 파일 생성기**를 지정하는 것이다. 순수하게 `dotnet build`만 하는 CI 환경에서는 `.Designer.cs`가 **재생성되지 않는다.** 즉 `.resx`에 키를 추가하고 `.Designer.cs`를 커밋하지 않으면 CI 빌드는 옛 키만 아는 코드를 컴파일한다.
>
> 규칙은 하나다. **`.Designer.cs`는 반드시 소스 관리에 커밋한다.** 자동 생성 파일이라고 `.gitignore`에 넣으면 안 된다.
>
> 생성기가 만든 클래스는 기본이 `internal`이다. 라이브러리에서 리소스를 외부에 노출해야 한다면 `PublicResXFileCodeGenerator`를 쓴다.

> **📌 `Culture` 속성의 용도**
>
> 생성된 클래스의 `Culture` 정적 속성은 `GetString`에 넘길 문화권을 강제로 고정한다. `null`이면(기본) `CultureInfo.CurrentUICulture`가 쓰인다. 테스트에서 특정 언어의 리소스를 확인할 때 스레드 문화권을 건드리지 않고 이것만 바꾸면 되니 편하다. 다만 **정적 상태**라서 병렬 테스트에서는 서로 간섭한다.

### `ResourceReader`와 `ResourceWriter` — 한 층 더 아래

`ResourceManager`를 거치지 않고 `.resources` 스트림을 직접 파싱할 수도 있다.

```csharp
using System.Resources;
using System.Collections;

using Stream s = typeof(Program).Assembly
    .GetManifestResourceStream("MyApp.Greeting.resources")!;
using var reader = new ResourceReader(s);

foreach (DictionaryEntry e in reader)
    Console.WriteLine($"{e.Key} = {e.Value}");
```

`ResourceReader`는 `IResourceReader`를 구현하고 `IDictionaryEnumerator`를 준다. 값 타입까지 알아야 한다면 `GetResourceData(string, out string resourceType, out byte[] data)`로 역직렬화 없이 원시 바이트를 얻을 수도 있다.

쓰기는 사정이 다르다.

> **⚠️ .NET(Core)에서 `ResourceWriter`는 공유 프레임워크에 없다**
>
> `System.Resources.ResourceWriter`는 .NET Framework의 `mscorlib`에 있었지만, .NET Core 이후 공유 프레임워크에서 빠졌다. 런타임에 `.resources` 파일을 **생성**해야 한다면 `System.Resources.Writer` NuGet 패키지를 참조해야 한다. 읽기 쪽(`ResourceReader`)은 프레임워크에 남아 있다.
>
> 애초에 런타임에 `.resources`를 만들 일은 거의 없다. 빌드 타임 도구를 만드는 게 아니라면 이 패키지를 참조하고 있다는 사실 자체를 의심해봐야 한다.

### 문자열이 아닌 리소스와 `System.Resources.Extensions`

`.resx`에 이미지나 임의 객체를 넣으면 그 값은 직렬화되어야 한다. 전통적으로 이 직렬화는 `BinaryFormatter`가 했고, `.resx`에 다음과 같은 형태로 남는다.

```xml
<data name="Logo" type="System.Drawing.Bitmap, System.Drawing"
      mimetype="application/x-microsoft.net.object.bytearray.base64">
  <value>iVBORw0KGgoAAAANSUhEUg...</value>
</data>
```

.NET Core 이후 `BinaryFormatter`가 보안 이유로 단계적으로 제거되면서, SDK는 `System.Resources.Extensions` 어셈블리의 `PreserializedResourceWriter` / `DeserializingResourceReader`를 쓰는 경로를 도입했다. MSBuild 속성으로 켠다.

```xml
<PropertyGroup>
  <GenerateResourceUsePreserializedResources>true</GenerateResourceUsePreserializedResources>
</PropertyGroup>
```

> **⚠️ 문자열이 아닌 `.resx` 항목은 .NET 8+에서 특히 조심하라**
>
> `BinaryFormatter`는 .NET 8에서 기본 비활성화를 넘어 .NET 9에서 사실상 제거 수순을 밟았다. `.resx`에 `BinaryFormatter`로 직렬화된 객체가 들어 있으면 런타임 역직렬화에서 실패할 수 있다. ※.NET 8
>
> 실무 지침은 명확하다. **`.resx`에는 문자열만 넣어라.** 이미지·폰트·바이너리는 `Embedded Resource`(53.1절)나 WPF의 `Resource` 빌드 작업으로 따로 관리하고, `.resx`는 번역 대상 텍스트 전용으로 쓴다. 이렇게 하면 번역 워크플로도 훨씬 깔끔해진다(53.5절).

### WPF — `Resource` 빌드 작업과 pack URI

WPF 애플리케이션에서 XAML 파일은 리소스를 **URI로** 접근할 수 있어야 한다.

```xml
<Button>
  <Image Height="50" Source="flag.png"/>
</Button>
```

리소스가 다른 어셈블리에 있다면 이렇게 쓴다.

```xml
<Button>
  <Image Height="50" Source="UtilsAssembly;Component/flag.png"/>
</Button>
```

여기서 `Component`는 **리터럴 키워드**다. 어셈블리 이름 뒤에 그대로 쓴다.

이런 식으로 로드될 수 있는 리소스를 만들려면 `.resx`를 쓸 수 없다. 대신 파일을 프로젝트에 추가하고 빌드 작업을 **`Resource`**(`Embedded Resource`가 아니다)로 설정해야 한다. 그러면 Visual Studio는 그것들을 `<AssemblyName>.g.resources`라는 `.resources` 파일로 컴파일한다. 컴파일된 XAML(`.baml`) 파일도 같은 곳에 들어간다.

URI를 키로 하는 리소스를 코드에서 로드하려면 `Application.GetResourceStream`을 호출한다.

```csharp
using System.Windows;
using System.Windows.Resources;

Uri u = new Uri("flag.png", UriKind.Relative);
using (Stream s = Application.GetResourceStream(u).Stream)
{
    // ...
}
```

상대 URI를 썼다는 데 주의하라. 절대 URI도 다음 형식 그대로 쓸 수 있다(**쉼표 세 개는 오타가 아니다**).

```csharp
Uri u = new Uri("pack://application:,,,/flag.png");
```

pack URI 형태를 정리하면 다음과 같다.

| 형태 | 의미 |
|---|---|
| `flag.png` | 같은 어셈블리, 상대 경로 |
| `/Assets/flag.png` | 같은 어셈블리, 루트 기준 |
| `pack://application:,,,/flag.png` | 같은 어셈블리, 절대 |
| `pack://application:,,,/UtilsAssembly;component/flag.png` | 참조 어셈블리의 리소스 |
| `pack://siteoforigin:,,,/flag.png` | 어셈블리가 아니라 **실행 파일 옆 파일**(`Content` 빌드 작업) |

> **⚠️ `pack://application`과 `pack://siteoforigin`은 완전히 다른 것을 가리킨다**
>
> `application`은 어셈블리 **안에 컴파일된** 리소스(`Resource` 빌드 작업)를, `siteoforigin`은 어셈블리 **바깥 디스크의 파일**(`Content` 빌드 작업, "출력 디렉터리로 복사" 설정)을 가리킨다. 빌드 작업을 `Content`로 두고 `pack://application:,,,/`로 참조하면 런타임에 `IOException`(리소스를 찾을 수 없음) 계열로 실패한다. 반대도 마찬가지다.

`Assembly` 객체를 직접 지정하고 싶다면 `ResourceManager`로도 같은 내용을 꺼낼 수 있다. `.g.resources`도 결국 `.resources` 파일이기 때문이다.

```csharp
Assembly a = Assembly.GetExecutingAssembly();
ResourceManager r = new ResourceManager(a.GetName().Name + ".g", a);
using (Stream s = r.GetStream("flag.png")!)
{
    // ...
}
```

`baseName`이 `"<어셈블리단순이름>.g"`라는 점을 눈여겨보라. `.resources` 확장자를 뺀 이름이므로 `.g`가 남는 것이다. `ResourceManager`로 접근하면 특정 어셈블리 안의 `.g.resources` 컨테이너 내용을 **열거**하는 것도 가능하다. pack URI로는 열거가 안 된다.

> **💡 `.g.resources`의 키는 소문자로 정규화된다**
>
> WPF 빌드 파이프라인은 `Resource` 항목의 경로를 `.g.resources` 안에 **소문자 상대 경로**로 넣는다. `Assets/Flag.png`를 추가했다면 키는 `assets/flag.png`가 된다. `ResourceManager.GetStream("Assets/Flag.png")`가 `null`을 주고 당황하는 원인이 이것이다. 위 코드로 `GetResourceSet`을 열거해 실제 키를 확인해보면 바로 보인다.

### 세 가지 리소스 방식 정리

여기까지 나온 것을 한 표에 모은다. 이 표가 53.1~53.2절의 요약이다.

| | `Embedded Resource` | `.resx` → `.resources` | WPF `Resource` |
|---|---|---|---|
| 매니페스트 리소스 이름 | `RootNamespace.폴더.파일명.확장자` | `RootNamespace.폴더.파일명.resources` | `<AssemblyName>.g.resources` |
| 항목 단위 | 파일 하나 = 리소스 하나 | 컨테이너 하나에 N개 항목 | 컨테이너 하나에 N개 항목 |
| 읽는 API | `GetManifestResourceStream` | `ResourceManager` | pack URI / `Application.GetResourceStream` |
| 지역화 지원 | 없음 | **있음**(위성 어셈블리) | WPF 전용 지역화 워크플로 |
| 강력한 형식 래퍼 | 없음 | 자동 생성 | 없음 |
| 적합한 콘텐츠 | 바이너리, 설정 파일 | **UI 문자열** | XAML이 참조하는 이미지·아이콘 |

## 53.3 위성 어셈블리와 어셈블리 버전 리소스 정보

### 위성 어셈블리가 푸는 문제

`.resources`에 임베드된 데이터는 **지역화가 가능하다.** 리소스 지역화는 애플리케이션이 다른 언어로 모든 것을 표시하도록 만들어진 Windows 버전에서 실행될 때 의미가 있다. 일관성을 위해 애플리케이션도 같은 언어를 써야 한다.

전형적인 구성은 이렇다.

- **주 어셈블리**가 기본(폴백) 언어의 `.resources`를 담는다.
- **별도의 위성 어셈블리**들이 각 언어로 번역된 `.resources`를 담는다.

애플리케이션이 실행되면 .NET은 현재 OS의 언어를 조사한다(`CultureInfo.CurrentUICulture`). `ResourceManager`로 리소스를 요청할 때마다 런타임은 지역화된 위성 어셈블리를 찾는다. 하나가 있고 요청한 리소스 키를 담고 있다면, 주 어셈블리의 버전 대신 그것이 쓰인다.

이 설계의 결정적인 이득은 다음 한 줄에 있다.

> **새 위성을 추가하는 것만으로 언어 지원을 확장할 수 있다 — 주 어셈블리를 건드리지 않고.**

프랑스어 지원이 필요해졌다면 `fr` 폴더에 `MyApp.resources.dll` 하나를 떨어뜨리면 끝이다. 재컴파일도, 재서명도, 재배포도 없다.

> **⚠️ 위성 어셈블리는 실행 코드를 담을 수 없다**
>
> 위성 어셈블리는 리소스만 담는다. 코드는 안 된다. 기술적으로는 코드를 담은 어셈블리에 `AssemblyCulture`를 붙이는 것이 불가능하지 않지만(52장에서 본 AssemblyDef의 문화권 필드에 값이 들어간다), Microsoft는 이 관행을 명시적으로 **권장하지 않는다.**
>
> 그리고 실행 파일에는 아예 막혀 있다. `.exe` 프로젝트에 `[assembly: AssemblyCulture("de")]`를 붙이면 C# 컴파일러가 오류를 낸다.
>
> ```text
> error CS7059: Executables cannot be satellite assemblies;
>               culture should always be empty
> ```

52장의 언어로 다시 말하면 이렇다. 위성 어셈블리는 **AssemblyDef 테이블의 문화권 필드가 채워져 있고, TypeDef 테이블이 사실상 비어 있으며, ManifestResourceDef 테이블만 채워져 있는** 어셈블리다.

### 배포 디렉터리 구조와 CLR의 탐색 규칙

위성 어셈블리는 주 어셈블리 폴더의 **하위 디렉터리**에 배포된다.

```text
programBaseFolder\MyProgram.exe
                 \MyLibrary.dll
                 \XX\MyProgram.resources.dll
                 \XX\MyLibrary.resources.dll
```

`XX`는 두 글자 언어 코드(독일어면 `de`) 또는 언어-지역 코드(영국 영어면 `en-GB`)다. **이 명명 체계 덕분에 CLR이 올바른 위성 어셈블리를 자동으로 찾아 로드한다.**

실제 빌드 출력을 보면 이렇게 생겼다.

```text
bin/Debug/net8.0/
├── MyApp.dll                     ← 주 어셈블리(기본 언어 리소스 포함)
├── MyApp.exe
├── MyApp.deps.json
├── MyApp.runtimeconfig.json
├── de/
│   └── MyApp.resources.dll       ← 독일어
├── de-AT/
│   └── MyApp.resources.dll       ← 오스트리아 독일어
├── fr/
│   └── MyApp.resources.dll       ← 프랑스어
└── ko-KR/
    └── MyApp.resources.dll       ← 한국어(한국)
```

> **⚠️ 위성 어셈블리 파일 이름은 모든 문화권에서 똑같다**
>
> `MyApp.de.resources.dll`이 아니라 그냥 `MyApp.resources.dll`이다. 문화권을 구별하는 것은 **파일 이름이 아니라 폴더 이름**이다. 그리고 어셈블리 신원 관점에서는 파일 이름이 아니라 매니페스트의 문화권 필드가 구별한다(52.6절의 "어셈블리 신원은 네 요소" — 단순 이름, 버전, **문화권**, 공개 키 토큰).
>
> 결과적으로 배포 스크립트가 파일을 평평하게(flat) 한 폴더에 모으면 **위성끼리 서로 덮어쓴다.** 파일 복사 방식으로 배포하는 파이프라인에서 실제로 발생하는 사고다. 반드시 디렉터리 구조를 보존해야 한다.

CLR이 위성을 찾는 순서는 52.15절에서 본 프로빙 규칙의 특수한 경우다.

```text
ResourceManager.GetString("Hello")  요청 문화권 = de-AT
        │
        ▼
┌───────────────────────────────────────────────────────────┐
│ 1. ResourceManager 내부 캐시에 de-AT ResourceSet이 있나?   │
│    있으면 즉시 반환 (여기서 끝나는 것이 대부분)             │
└───────────────────────────────────────────────────────────┘
        │ 없음
        ▼
┌───────────────────────────────────────────────────────────┐
│ 2. Assembly.GetSatelliteAssembly(de-AT) 요청               │
│    → ALC(52.9절)에게 어셈블리 해석을 맡긴다                 │
│      이름 = "MyApp.resources"                              │
│      Culture = "de-AT"                                     │
└───────────────────────────────────────────────────────────┘
        │
        ▼
┌───────────────────────────────────────────────────────────┐
│ 3. 기본 ALC의 위성 탐색                                     │
│    각 후보 루트 + "de-AT\MyApp.resources.dll"               │
│      · PLATFORM_RESOURCE_ROOTS의 경로들                     │
│      · APP_PATHS(앱 기준 폴더)                              │
└───────────────────────────────────────────────────────────┘
        │ 못 찾음
        ▼
   4. 폴백: 부모 문화권(de)로 2번부터 다시 (53.4절)
```

`PLATFORM_RESOURCE_ROOTS`는 52.15절 표에 나왔던 프로빙 속성이다. "위성 리소스 어셈블리를 검색할 디렉터리 경로 목록"이라고만 하고 넘어갔는데, 바로 이 3단계가 그것을 소비하는 곳이다.

그 목록이 어디서 오는가 하면 `deps.json`이다. 호스트가 `deps.json`의 `resources` 항목을 읽어 위성이 놓인 디렉터리들을 `PLATFORM_RESOURCE_ROOTS`로 넘겨준다. 즉 `deps.json`은 별도의 탐색 단계가 아니라 **탐색 경로의 공급원**이다. NuGet 패키지가 제공하는 위성이 있을 때 특히 중요해진다.

```json
{
  "targets": {
    ".NETCoreApp,Version=v8.0": {
      "MyLibrary/1.0.0": {
        "runtime": { "lib/net8.0/MyLibrary.dll": {} },
        "resources": {
          "lib/net8.0/de/MyLibrary.resources.dll": { "locale": "de" },
          "lib/net8.0/fr/MyLibrary.resources.dll": { "locale": "fr" }
        }
      }
    }
  }
}
```

> **📌 사용자 정의 ALC와 위성 어셈블리**
>
> 위성 어셈블리도 어셈블리다. 따라서 52.9절에서 본 ALC 규칙이 그대로 적용된다. 플러그인을 격리 ALC에 로드했다면(52.14절), 그 플러그인의 위성도 같은 ALC가 해석해야 한다. 사용자 정의 ALC의 `Load` 오버라이드는 `AssemblyName.Name == "MyPlugin.resources"`이고 `CultureName`이 채워진 요청을 받게 된다.
>
> `AssemblyDependencyResolver`(52.11절)는 `ResolveAssemblyToPath`로 위성 경로도 해석해준다. 플러그인 시스템에서 지역화가 필요하다면 이 조합이 정답이다.

### 위성 어셈블리 빌드하기

53.2절의 `.resx` 예제를 다시 보자.

```xml
<root>
  ...
  <data name="Greeting">
    <value>hello</value>
  </data>
</root>
```

런타임에는 이렇게 꺼냈다.

```csharp
ResourceManager r = new ResourceManager("welcome",
                                        Assembly.GetExecutingAssembly());
Console.Write(r.GetString("Greeting"));
```

독일어 버전 Windows에서 실행하면 대신 `hallo`가 나오게 하고 싶다고 하자. 첫 단계는 `hello`를 `hallo`로 바꾼 **`welcome.de.resx`** 라는 이름의 `.resx` 파일을 추가하는 것이다.

```xml
<root>
  <data name="Greeting">
    <value>hallo</value>
  </data>
</root>
```

Visual Studio에서는 이게 전부다. 다시 빌드하면 `de`라는 하위 디렉터리에 `MyApp.resources.dll`이라는 위성 어셈블리가 자동으로 생성된다.

명명 규칙만 지키면 SDK가 알아서 한다.

| `.resx` 파일 이름 | 대상 문화권 | 산출물 |
|---|---|---|
| `welcome.resx` | 중립(기본) | 주 어셈블리에 임베드 |
| `welcome.de.resx` | `de` | `de/MyApp.resources.dll` |
| `welcome.de-AT.resx` | `de-AT` | `de-AT/MyApp.resources.dll` |
| `welcome.pt-BR.resx` | `pt-BR` | `pt-BR/MyApp.resources.dll` |

> **⚠️ 파일 이름에 점이 두 번 들어가면 SDK가 문화권으로 오해한다**
>
> `Order.Details.resx`라는 파일을 만들면 SDK는 `Details`를 문화권 코드로 해석하려 시도한다. 유효한 문화권 이름이 아니면 대개 무시하고 중립 리소스로 처리하지만, 하필 유효한 코드와 겹치면(`Order.no.resx` — `no`는 노르웨이어다) **의도치 않게 위성 어셈블리가 생긴다.** 그리고 노르웨이어 Windows에서만 UI가 이상해진다.
>
> 규칙: `.resx` 파일 이름에는 점을 문화권 구분자 용도로만 쓴다.

빌드 파이프라인이 실제로 무엇을 하는지 한 단계 더 보자.

```text
welcome.de.resx
    │  GenerateResource 태스크
    ▼
obj\...\MyApp.welcome.de.resources
    │
    │  SDK가 생성한 임시 소스 파일:
    │     [assembly: AssemblyCulture("de")]
    │     [assembly: AssemblyVersion("1.0.0.0")]
    │  + csc /target:library
    │        /resource:MyApp.welcome.de.resources
    │        /out:de\MyApp.resources.dll
    ▼
bin\...\de\MyApp.resources.dll
```

> **📌 .NET Framework 시절에는 `AL.exe`가 이 일을 했다**
>
> 52.3절에서 언급한 Assembly Linker(`AL.exe`)의 대표적인 용도가 바로 위성 어셈블리 생성이었다. 코드가 없으므로 컴파일러를 쓸 이유가 없었고, `AL.exe`가 리소스만 담은 PE를 직접 조립했다.
>
> ```text
> al /embed:welcome.de.resources /culture:de ^
>    /out:de\MyApp.resources.dll /template:MyApp.exe
> ```
>
> `/c[ulture]:text` 스위치가 문화권을 지정한다. `/template`은 주 어셈블리에서 버전 등의 메타데이터를 물려받게 한다. `AL.exe`는 .NET Framework SDK 도구이고, .NET 5+ SDK에는 없다. 지금은 SDK가 Roslyn으로 코드 없는 라이브러리를 만든다.

`AL.exe`를 쓰지 않고 특성으로 문화권을 지정할 수도 있다.

```csharp
// 어셈블리의 문화권을 스위스 독일어로 설정
[assembly: AssemblyCulture("de-CH")]
```

### 문화권 중립 원칙

여기서 중요한 설계 원칙이 하나 나온다.

일반적으로 **코드를 담은 어셈블리에는 문화권을 지정하지 않는다.** 코드에는 보통 문화권 특유의 가정이 들어 있지 않기 때문이다. 문화권이 지정되지 않은 어셈블리를 **문화권 중립(culture neutral)** 이라고 한다.

문화권별 리소스가 있는 애플리케이션을 설계한다면 Microsoft의 강력한 권고는 이렇다.

1. **코드와 애플리케이션의 기본(폴백) 리소스를 담은 어셈블리 하나**를 만든다. 이 어셈블리를 빌드할 때 문화권을 지정하지 않는다. 다른 어셈블리들이 참조하는 것은 이 어셈블리다.
2. **문화권별 리소스만 담고 코드는 전혀 없는** 별도 어셈블리를 하나 이상 만든다. 각 위성 어셈블리에는 그 안에 든 리소스의 문화권을 정확히 반영하는 문화권을 지정한다. 지원하려는 문화권마다 위성 어셈블리를 하나씩 만든다.

> **⚠️ 어셈블리는 위성 어셈블리를 참조하면 안 된다**
>
> 어셈블리의 AssemblyRef 항목은 모두 **문화권 중립 어셈블리**를 가리켜야 한다. 위성 어셈블리에 든 타입이나 멤버에 접근해야 한다면(그럴 일이 있어서는 안 되지만) 리플렉션을 써야 한다(57장).
>
> 컴파일 타임에 위성을 참조하는 순간, 그 위성이 없는 환경에서 앱이 시작조차 못 한다. 위성의 존재 이유(있으면 쓰고 없으면 폴백)가 무너진다.

### 위성 어셈블리 배포 제어 — `SatelliteResourceLanguages`

NuGet 패키지 중에는 수십 개 언어의 위성 어셈블리를 함께 배포하는 것들이 있다. 그대로 두면 출력 폴더가 언어 폴더로 뒤덮이고 배포 크기가 커진다.

`SatelliteResourceLanguages` MSBuild 속성으로 걸러낼 수 있다.

```xml
<PropertyGroup>
  <!-- 영어와 한국어 위성만 출력 폴더로 복사한다 -->
  <SatelliteResourceLanguages>en;ko</SatelliteResourceLanguages>
</PropertyGroup>
```

> **⚠️ `SatelliteResourceLanguages`는 자기 프로젝트의 위성도 거른다**
>
> 이 속성은 NuGet 패키지의 위성뿐 아니라 **현재 프로젝트가 생성한 위성**에도 적용된다. `en;ko`로 설정해두고 나중에 `Messages.ja.resx`를 추가하면, 파일은 컴파일되지만 위성 어셈블리가 출력 폴더로 복사되지 않는다. 빌드는 성공하고 경고도 없다. 일본어 환경에서만 UI가 영어로 나온다.
>
> 이 속성을 쓴다면 **`.resx` 파일을 추가할 때 함께 갱신하는 것**을 팀 규칙으로 못 박아야 한다.

### 강력한 이름과 위성 어셈블리

주 어셈블리에 강력한 이름을 붙였다면(52.5절), 위성 어셈블리도 **같은 키로 서명해야 한다.** SDK가 자동으로 처리하므로 보통 신경 쓸 일은 없다.

.NET Framework에서는 이 서명 검사가 실제로 수행되었다. 서명이 다르거나 없으면 위성 로드가 실패했다. **.NET 5+에서는 강력한 이름 서명 자체가 검사되지 않으므로**(52.5절) 이 검사도 사실상 무의미하다. 그래도 SDK는 여전히 서명하고, 구조적 일관성 때문에 그 편이 낫다.

버전 문제는 조금 더 성가시다.

> **⚠️ 주 어셈블리 버전을 올리면 위성이 무효화될 수 있다**
>
> 위성 어셈블리의 AssemblyRef는 없지만, `ResourceManager`는 주 어셈블리의 버전과 **일치하는** 버전의 위성을 찾는다(강력한 이름 어셈블리 기준, 주로 .NET Framework에서 문제가 됐다). 주 어셈블리를 1.0.0.0에서 1.0.0.1로 올리면 기존 위성들이 무시된다.
>
> 해결책은 `SatelliteContractVersionAttribute`다.
>
> ```csharp
> [assembly: AssemblyVersion("1.0.1.0")]
> [assembly: System.Resources.SatelliteContractVersion("1.0.0.0")]
> ```
>
> 이러면 주 어셈블리를 서비스 릴리스로 올려도 `1.0.0.0` 버전의 위성이 계속 쓰인다. 위성을 다시 빌드하고 다시 번역 검수를 받지 않아도 된다는 뜻이다.

### 위성 어셈블리 테스트하기

다른 언어의 OS에서 실행되는 상황을 시뮬레이션하려면 `Thread` 클래스를 통해 `CurrentUICulture`를 바꿔야 한다.

```csharp
System.Threading.Thread.CurrentThread.CurrentUICulture
    = new System.Globalization.CultureInfo("de");
```

원서(구 .NET Framework 기준)는 "`CultureInfo.CurrentUICulture`는 같은 속성의 읽기 전용 버전"이라고 설명한다. 이 서술은 지금은 맞지 않는다.

> **📌 `CultureInfo.CurrentUICulture`는 이제 쓰기 가능하다** ※.NET Framework 4.6, ※.NET Core 1.0+
>
> .NET Framework 4.6 이후와 .NET Core / .NET 5+에서는 `CultureInfo.CurrentCulture`와 `CultureInfo.CurrentUICulture`에 **setter가 있다.**
>
> ```csharp
> CultureInfo.CurrentUICulture = new CultureInfo("de");   // 지금은 유효하다
> ```
>
> `Thread.CurrentThread.CurrentUICulture`와 같은 저장소를 가리킨다. 어느 쪽을 써도 동일하다. 옛 문서나 예제가 `Thread.CurrentThread`를 경유하는 것은 순전히 역사적 이유다. 새 코드는 `CultureInfo` 쪽을 쓰는 편이 읽기 좋다.

Visual Studio의 디자이너는 컴포넌트와 시각 요소의 지역화를 확장 지원한다. WPF 디자이너는 자체 지역화 워크플로를 갖고 있고, 그 밖의 컴포넌트 기반 디자이너들은 **디자인 타임 전용 속성**을 써서 컴포넌트나 Windows Forms 컨트롤에 `Language` 속성이 있는 것처럼 보이게 한다. 다른 언어에 맞게 커스터마이즈하려면 `Language` 속성을 바꾸고 컴포넌트를 수정하기 시작하면 된다. `Localizable`로 특성 지정된 컨트롤의 모든 속성이 그 언어의 `.resx` 파일에 저장된다. `Language` 속성만 바꾸면 언제든 언어를 전환할 수 있다.

### 어셈블리 버전 리소스 정보

여기서 이름이 비슷해서 계속 혼동되는 다른 종류의 "리소스"를 정리하고 가자. **Win32 버전 리소스**다.

`AL.exe`나 `CSC.exe`가 PE 파일 어셈블리를 만들 때, PE 파일에 **표준 Win32 버전 리소스**도 함께 임베드한다. 사용자는 파일 속성을 열어 이 리소스를 볼 수 있다. 애플리케이션 코드도 런타임에 `System.Diagnostics.FileVersionInfo`의 정적 메서드 `GetVersionInfo`에 어셈블리 경로명을 넘겨 이 정보를 얻고 조사할 수 있다.

```csharp
using System.Diagnostics;

var info = FileVersionInfo.GetVersionInfo(typeof(Program).Assembly.Location);

Console.WriteLine(info.FileDescription);      // AssemblyTitle
Console.WriteLine(info.Comments);             // AssemblyDescription
Console.WriteLine(info.CompanyName);          // AssemblyCompany
Console.WriteLine(info.ProductName);          // AssemblyProduct
Console.WriteLine(info.LegalCopyright);       // AssemblyCopyright
Console.WriteLine(info.FileVersion);          // AssemblyFileVersion
Console.WriteLine(info.ProductVersion);       // AssemblyInformationalVersion
```

어셈블리를 빌드할 때는 소스 코드에서 어셈블리 수준에 적용하는 커스텀 특성으로 버전 리소스 필드를 설정해야 한다.

```csharp
using System.Reflection;

// FileDescription 버전 정보
[assembly: AssemblyTitle("MultiFileLibrary.dll")]

// Comments 버전 정보
[assembly: AssemblyDescription("This assembly contains MultiFileLibrary's types")]

// CompanyName 버전 정보
[assembly: AssemblyCompany("Wintellect")]

// ProductName 버전 정보
[assembly: AssemblyProduct("Wintellect (R) MultiFileLibrary's Type Library")]

// LegalCopyright 버전 정보
[assembly: AssemblyCopyright("Copyright (c) Wintellect 2013")]

// LegalTrademarks 버전 정보
[assembly: AssemblyTrademark("MultiFileLibrary is a registered trademark of Wintellect")]

// AssemblyVersion 버전 정보
[assembly: AssemblyVersion("3.0.0.0")]

// FILEVERSION/FileVersion 버전 정보
[assembly: AssemblyFileVersion("1.0.0.0")]

// PRODUCTVERSION/ProductVersion 버전 정보
[assembly: AssemblyInformationalVersion("2.0.0.0")]

// Language 필드 설정 (앞의 문화권 논의 참조)
[assembly: AssemblyCulture("")]
```

버전 리소스 필드와 대응하는 특성을 표로 정리한다. `AL.exe`를 쓴다면 커스텀 특성 대신 명령줄 스위치로 지정할 수도 있다. C# 컴파일러는 이 스위치들을 제공하지 않으며, 일반적으로 커스텀 특성을 쓰는 것이 권장되는 방식이다.

| Win32 버전 리소스 필드 | `AL.exe` 스위치 | 대응하는 커스텀 특성 / 설명 |
|---|---|---|
| `FILEVERSION` | `/fileversion` | `AssemblyFileVersionAttribute` |
| `PRODUCTVERSION` | `/productversion` | `AssemblyInformationalVersionAttribute` |
| `FILEFLAGSMASK` | (없음) | 항상 `VS_FFI_FILEFLAGSMASK`(`WinVer.h`에 `0x0000003F`로 정의) |
| `FILEFLAGS` | (없음) | 항상 `0` |
| `FILEOS` | (없음) | 현재 항상 `VOS__WINDOWS32` |
| `FILETYPE` | `/target` | `/target:exe`나 `/target:winexe`면 `VFT_APP`, `/target:library`면 `VFT_DLL` |
| `FILESUBTYPE` | (없음) | 항상 `VFT2_UNKNOWN`(`VFT_APP`·`VFT_DLL`에는 의미 없음) |
| `AssemblyVersion` | `/version` | `AssemblyVersionAttribute` |
| `Comments` | `/description` | `AssemblyDescriptionAttribute` |
| `CompanyName` | `/company` | `AssemblyCompanyAttribute` |
| `FileDescription` | `/title` | `AssemblyTitleAttribute` |
| `FileVersion` | `/version` | `AssemblyFileVersionAttribute` |
| `InternalName` | `/out` | 지정한 출력 파일 이름(확장자 제외) |
| `LegalCopyright` | `/copyright` | `AssemblyCopyrightAttribute` |
| `LegalTrademarks` | `/trademark` | `AssemblyTrademarkAttribute` |
| `OriginalFilename` | `/out` | 지정한 출력 파일 이름(경로 제외) |
| `PrivateBuild` | (없음) | 항상 비어 있음 |
| `ProductName` | `/product` | `AssemblyProductAttribute` |
| `ProductVersion` | `/productversion` | `AssemblyInformationalVersionAttribute` |
| `SpecialBuild` | (없음) | 항상 비어 있음 |

> **⚠️ 탐색기 속성 대화상자에는 `AssemblyVersion`이 표시되지 않는다**
>
> Windows 탐색기의 파일 속성 대화상자는 일부 특성에 해당하는 항목이 **빠져 있다.** 특히 `AssemblyVersion` 특성의 값이 표시되면 좋을 텐데 그렇지 않다. CLR은 어셈블리를 로드할 때 바로 이 값을 사용하는데도 그렇다(52.8절).
>
> 탐색기가 보여주는 "파일 버전"은 `AssemblyFileVersion`이고, "제품 버전"은 `AssemblyInformationalVersion`이다. **바인딩에 쓰이는 값은 셋 중 어느 것도 아닌 `AssemblyVersion`이다.** 배포 사고를 조사할 때 탐색기 화면만 보고 판단하면 안 되는 이유다. `AssemblyVersion`을 확인하려면 `ildasm`으로 매니페스트를 보거나 `Assembly.GetName().Version`을 찍어야 한다.

> **⚠️ 이 Win32 버전 리소스는 어셈블리 리소스가 아니다**
>
> `FileVersionInfo`가 읽는 것은 PE 파일의 **Win32 리소스 섹션**(`.rsrc`)이고, `Assembly.GetManifestResourceStream`이 읽는 것은 **CLR 메타데이터의 ManifestResourceDef**가 가리키는 구간이다. 물리적으로도 논리적으로도 별개다.
>
> `ildasm`으로는 Win32 버전 리소스가 보이지 않고, 탐색기 속성 대화상자로는 어셈블리 리소스가 보이지 않는다. 서로 다른 도구가 필요하다.

> **⚠️ 단일 파일 배포와 네이티브 AOT에서의 위성 어셈블리**
>
> `PublishSingleFile=true`로 게시하면 위성 어셈블리도 번들에 포함되며, 런타임 번들 프로버가 이를 해석한다. 다만 `IncludeAllContentForSelfExtract` 같은 설정에 따라 동작이 갈릴 수 있으므로 **반드시 게시본으로 실제 테스트해야 한다.**
>
> 네이티브 AOT(`PublishAot=true`)는 사정이 더 까다롭다. AOT 게시본은 관리 어셈블리를 런타임에 로드하지 않으므로 별도의 위성 `.dll`을 로드하는 모델이 성립하지 않는다. 지역화가 필요한 AOT 앱이라면 리소스를 주 이미지 안으로 끌어들이는 구성이 필요하고, `InvariantGlobalization` 설정과의 상호작용도 확인해야 한다(53.4절).
>
> 요약하면 **"개발 빌드에서 됐으니 게시본에서도 되겠지"가 성립하지 않는 영역**이다.

## 53.4 문화권과 하위 문화권, 폴백 규칙

### 문화권과 하위 문화권

문화권은 **문화권(culture)** 과 **하위 문화권(subculture)** 으로 나뉜다. 문화권은 특정 언어를, 하위 문화권은 그 언어의 지역적 변형을 나타낸다.

.NET 런타임은 **RFC 1766** 표준을 따르며, 이 표준은 문화권과 하위 문화권을 두 글자 코드로 표현한다. 영어와 독일어 문화권의 코드는 다음과 같다.

```text
en
de
```

호주 영어와 오스트리아 독일어 하위 문화권의 코드는 다음과 같다.

```text
en-AU
de-AT
```

어셈블리 문화권 태그의 예를 정리하면 이렇다.

| 기본 태그 | 보조 태그 | 문화권 |
|---|---|---|
| `de` | (없음) | 독일어 |
| `de` | `AT` | 오스트리아 독일어 |
| `de` | `CH` | 스위스 독일어 |
| `en` | (없음) | 영어 |
| `en` | `GB` | 영국 영어 |
| `en` | `US` | 미국 영어 |

> **📌 RFC 1766에서 BCP 47로**
>
> 원서가 말하는 RFC 1766은 지금은 BCP 47(RFC 5646)로 대체되었고, .NET도 사실상 BCP 47을 따른다. 실무에서 달라지는 지점은 두 글자를 벗어나는 태그가 정상적으로 존재한다는 것이다.
>
> - `zh-Hans`, `zh-Hant` — 스크립트(문자 체계) 태그
> - `zh-Hans-CN`, `sr-Latn-RS` — 언어-스크립트-지역
> - `nb-NO`, `nn-NO` — 세 글자 언어 코드가 아닌 별개 언어
> - `qps-ploc` — Windows의 의사 로캘(53.5절)
>
> 즉 **"두 글자 + 하이픈 + 두 글자"를 가정한 파싱 코드는 틀렸다.** 문화권 이름을 직접 파싱하지 말고 `CultureInfo`에게 물어라.

문화권은 .NET에서 `System.Globalization.CultureInfo` 클래스로 표현된다. 애플리케이션의 현재 문화권을 다음과 같이 조사할 수 있다.

```csharp
Console.WriteLine(System.Threading.Thread.CurrentThread.CurrentCulture);
Console.WriteLine(System.Threading.Thread.CurrentThread.CurrentUICulture);
```

호주용으로 지역화된 컴퓨터에서 이것을 실행하면 두 값의 차이가 드러난다.

```text
en-AU
en-US
```

### `CurrentCulture` vs `CurrentUICulture`

이 둘의 차이가 이 절에서 가장 중요하다.

`CurrentCulture`는 **Windows 제어판의 지역 설정**을 반영하고, `CurrentUICulture`는 **OS의 언어**를 반영한다.

지역 설정에는 시간대, 통화와 날짜의 서식 같은 것들이 포함된다. `CurrentCulture`는 `DateTime.Parse` 같은 함수의 기본 동작을 결정한다. 지역 설정은 특정 문화권을 더 이상 닮지 않을 정도로 사용자 지정될 수 있다.

`CurrentUICulture`는 **컴퓨터가 사용자와 소통하는 언어**를 결정한다. 호주는 이 목적으로 별도의 영어 버전이 필요하지 않으므로 그냥 미국 것을 쓴다. 오스트리아에서 몇 달 일한다면 제어판에서 `CurrentCulture`를 오스트리아 독일어로 바꿀 것이다. 하지만 독일어를 못한다면 `CurrentUICulture`는 미국 영어로 남을 것이다.

표로 정리한다.

| | `CurrentCulture` | `CurrentUICulture` |
|---|---|---|
| 무엇을 반영하나 | 지역 설정(제어판) | OS 표시 언어 |
| 영향을 주는 것 | 숫자·날짜·통화 서식, 파싱, 정렬 | **리소스 조회**, 위성 어셈블리 선택 |
| 대표적인 소비자 | `ToString()`, `Parse`, `string.Compare` | `ResourceManager.GetString` |
| 중립 문화권 허용 | 특정 문화권이어야 자연스러움 | 중립 문화권(`de`)도 정상 |
| 사용자 지정 가능성 | 매우 높음(달력·구분자를 개별 변경 가능) | 낮음(언어 팩 단위) |
| 관련 절 | 38.2절, 38.3절 | 이 절, 53.3절 |

> **⚠️ 두 값이 같을 것이라고 가정하지 마라**
>
> 개발자 머신에서는 대개 둘이 같다. 그래서 이 버그는 개발 중에 절대 드러나지 않는다.
>
> 실제로 흔한 조합은 다음과 같다.
>
> - 한국 사무실의 영어 Windows: `CurrentCulture = ko-KR`, `CurrentUICulture = en-US`
> - 미국 서버에 배포된 한국 서비스: `CurrentCulture = en-US`, `CurrentUICulture = en-US`, 하지만 사용자는 한국인
> - Linux 컨테이너: `LANG` 환경 변수 하나가 둘 다 결정하고, 대개 `C`/`POSIX`라 **불변 문화권**이 된다
>
> 마지막 경우가 특히 위험하다. 컨테이너에서 날짜가 갑자기 `MM/dd/yyyy`로 나오는 사고의 원인이 이것이다.

`ResourceManager`는 기본적으로 현재 스레드의 `CurrentUICulture` 속성을 사용해 로드할 올바른 위성 어셈블리를 결정한다.

### 문화권을 코드로 설정하기

문화권을 설정하는 방법은 세 층위가 있다.

```csharp
using System.Globalization;
using System.Threading;

// 1. 현재 스레드에만 적용
CultureInfo.CurrentUICulture = new CultureInfo("de");
Thread.CurrentThread.CurrentUICulture = new CultureInfo("de");   // 동일한 저장소

// 2. 스스로 문화권을 설정하지 않은 모든 스레드의 기본값 (프로세스 전역)
CultureInfo.DefaultThreadCurrentCulture   = new CultureInfo("ko-KR");
CultureInfo.DefaultThreadCurrentUICulture = new CultureInfo("ko");

// 3. 호출 단위로 명시 (가장 안전)
string s = value.ToString(CultureInfo.InvariantCulture);
string t = rm.GetString("Hello", new CultureInfo("de"));
```

> **⚠️ `DefaultThreadCurrentCulture`는 "이미 자기 문화권을 정한" 스레드를 되돌리지 못한다**
>
> 이 속성은 폴백 값이다. `CurrentCulture`를 읽을 때 그 스레드(또는 실행 컨텍스트)에 명시적으로 대입된 값이 없으면 이 값이 쓰이고, 그것도 없으면 OS 사용자 기본값이 쓰인다. 따라서 **아직 아무도 문화권을 대입하지 않은 스레드라면 이미 돌고 있던 스레드 풀 스레드에도 적용된다.** 반대로 어딘가에서 이미 `CurrentCulture`를 대입해버린 실행 흐름은 이 속성을 나중에 바꿔도 그대로다(38.10절).
>
> 애플리케이션 시작 시점(가능한 한 첫 줄)에 설정하는 것이 관행인 이유가 이것이다 — 아무도 값을 정하기 전에 정해두면 예외가 없다. ASP.NET Core라면 이런 전역 설정 대신 요청 지역화 미들웨어를 쓰는 것이 맞다(53.5절).

> **📌 문화권은 `async`/`await`를 따라 흐른다** ※.NET Framework 4.6+, .NET Core 전체
>
> .NET Core에서 `CultureInfo.CurrentCulture`와 `CurrentUICulture`는 내부적으로 `AsyncLocal<CultureInfo>`에 저장된다. 따라서 `await` 이후 다른 스레드에서 재개되어도 문화권이 유지된다.
>
> .NET Framework 4.5 이하에서는 그렇지 않았다. 스레드마다 독립적이었고, `Task.Run` 안에서는 기본 문화권으로 돌아갔다. 4.6에서 이 동작이 바뀌었고, 옛 동작이 필요하면 `AppContext` 스위치로 되돌릴 수 있었다. **.NET Framework 4.5 이하를 대상으로 하는 레거시 코드를 읽을 때는 이 차이를 염두에 둬야 한다.**

### 중립 문화권, 특정 문화권, 불변 문화권

세 가지를 구별해야 한다.

| 종류 | 예 | `Name` | `IsNeutralCulture` | 서식 정보 |
|---|---|---|---|---|
| **불변(invariant)** | `CultureInfo.InvariantCulture` | `""` | `false` | 있음(영어권 기반, 고정) |
| **중립(neutral)** | `new CultureInfo("de")` | `"de"` | `true` | 있지만 임의 지역 기반 |
| **특정(specific)** | `new CultureInfo("de-AT")` | `"de-AT"` | `false` | 있음 |

중립 문화권은 "언어는 알지만 지역은 모른다"는 상태다. 리소스 조회에는 완벽히 적합하지만(번역은 언어 단위로 하므로), 통화 기호나 날짜 형식을 정하기에는 부족하다.

```csharp
var neutral = new CultureInfo("de");
Console.WriteLine(neutral.IsNeutralCulture);            // True

// 중립 문화권에서 특정 문화권을 얻는다
var specific = CultureInfo.CreateSpecificCulture("de"); // de-DE
Console.WriteLine(specific.Name);                       // de-DE
```

부모 체인은 `Parent` 속성으로 따라간다. 이것이 곧 폴백 체인의 뼈대다.

```csharp
var c = new CultureInfo("de-AT");
while (true)
{
    Console.WriteLine($"[{c.Name}] {c.DisplayName}");
    if (c.Equals(CultureInfo.InvariantCulture)) break;
    c = c.Parent;
}
```

```text
[de-AT] German (Austria)
[de] German
[] Invariant Language (Invariant Country)
```

### 폴백 알고리즘

`ResourceManager`는 리소스를 로드할 때 **폴백 메커니즘**을 사용한다. 하위 문화권 어셈블리가 정의되어 있으면 그것이 쓰이고, 그렇지 않으면 일반 문화권으로 폴백한다. 일반 문화권이 없으면 **주 어셈블리의 기본 문화권**으로 폴백한다.

전체 흐름을 그리면 다음과 같다. `CurrentUICulture`가 `de-AT`이고 키 `"Hello"`를 요청하는 상황이다.

```text
                  GetString("Hello"),  CurrentUICulture = de-AT
                                │
        ┌───────────────────────▼────────────────────────┐
        │  1단계: de-AT                                   │
        │  de-AT\MyApp.resources.dll 을 로드 시도          │
        └───────────────────────┬────────────────────────┘
                    성공 & 키 있음 │ 실패 or 키 없음
              ┌─────────────────┘        │
              ▼                          ▼
         "Servus" 반환      ┌────────────────────────────────┐
                            │  2단계: de  (Parent)            │
                            │  de\MyApp.resources.dll 로드    │
                            └───────────────┬────────────────┘
                                성공 & 키 있음 │ 실패 or 키 없음
                          ┌──────────────────┘       │
                          ▼                          ▼
                     "Hallo" 반환    ┌───────────────────────────────┐
                                     │  3단계: 궁극적 폴백             │
                                     │  NeutralResourcesLanguage 가   │
                                     │  가리키는 곳                    │
                                     │   · MainAssembly(기본)         │
                                     │     → 주 어셈블리의 중립 리소스  │
                                     │   · Satellite                  │
                                     │     → 지정 문화권의 위성        │
                                     └───────────────┬───────────────┘
                                          찾음 │      │ 못 찾음
                                    ┌───────────┘      ▼
                                    ▼        MissingManifestResourceException
                               "Hello" 반환    또는 MissingSatelliteAssemblyException
```

단계별로 무엇을 찾는지 표로 다시 정리한다.

| 단계 | 찾는 위치 | 실패 시 |
|---|---|---|
| 1 | `de-AT/MyApp.resources.dll` 안의 `MyApp.Greeting.resources` | 2단계로 |
| 2 | `de/MyApp.resources.dll` 안의 `MyApp.Greeting.resources` | 3단계로 |
| 3 | 주 어셈블리 `MyApp.dll` 안의 `MyApp.Greeting.resources` | 예외 |

> **⚠️ 폴백은 "어셈블리 단위"가 아니라 "키 단위"다**
>
> `de-AT` 위성이 존재하더라도 그 안에 `"Hello"` 키가 없으면 폴백은 계속된다. 즉 **위성 어셈블리는 부분 번역이어도 된다.** 번역이 끝난 키만 넣고 나머지는 비워두면 자동으로 상위 문화권 값이 쓰인다.
>
> 이건 강력한 기능이지만 동시에 함정이기도 하다. **번역 누락이 조용히 폴백으로 가려진다.** UI 절반이 독일어, 절반이 영어인 화면이 프로덕션에 나가고도 아무도 모른다. 53.5절의 의사 지역화 테스트가 이 문제를 잡는 방법이다.

> **⚠️ 폴백 탐색은 매번 일어나지 않는다 — 그리고 그게 함정일 수 있다**
>
> `ResourceManager`는 문화권별로 로드한 `ResourceSet`을 내부 사전에 **캐시한다.** 첫 조회에서 위성을 못 찾으면 "없음"이라는 사실도 캐시된다. 따라서 실행 중에 `de/MyApp.resources.dll` 파일을 나중에 떨어뜨려도 그 프로세스는 계속 폴백 값을 쓴다.
>
> 캐시를 비우려면 `ReleaseAllResources()`를 호출해야 한다. 플러그인을 동적으로 로드하는 시스템에서 지역화 리소스가 갱신되지 않는 문제의 원인이 대개 이것이다.
>
> 반대로 이 캐시 덕분에 `GetString` 호출 자체는 매우 싸다. 사전 조회 두 번(문화권 → `ResourceSet`, 키 → 값) 수준이다. UI 렌더링 루프에서 `GetString`을 부르는 것을 두려워할 필요는 없다.

### `NeutralResourcesLanguage` — 폴백의 시작점을 앞당기기

주 어셈블리에 든 기본 리소스가 어떤 언어인지 런타임에 알려주는 특성이 있다.

```csharp
using System.Resources;

[assembly: NeutralResourcesLanguage("en")]
```

이 특성이 있으면 `ResourceManager`의 폴백 체인이 **그 중립 언어 단계에 도달하는 순간 주 어셈블리로 직행한다.** `CurrentUICulture`가 정확히 `en`이면 위성을 찾는 시도가 아예 일어나지 않고, `en-US`나 `en-GB`이면 그 하위 문화권 위성만 한 번 확인한 뒤 `en` 위성은 건너뛰고 곧바로 주 어셈블리를 쓴다. 없는 파일을 찾느라 디스크를 뒤지는 비용이 그만큼 사라진다.

두 번째 인자로 궁극적 폴백 위치를 지정할 수도 있다.

```csharp
[assembly: NeutralResourcesLanguage("en", UltimateResourceFallbackLocation.Satellite)]
```

| `UltimateResourceFallbackLocation` | 의미 |
|---|---|
| `MainAssembly` (기본) | 최종 폴백은 주 어셈블리 안의 리소스 |
| `Satellite` | 최종 폴백은 지정한 문화권의 **위성 어셈블리** |

> **⚠️ `UltimateResourceFallbackLocation.Satellite`는 주 어셈블리를 비워야 한다**
>
> 이 옵션을 쓰면 주 어셈블리에는 리소스를 넣지 않고 **모든 언어를 위성에 두는** 구조가 된다. 배포 시 기본 언어 위성을 빠뜨리면 `MissingSatelliteAssemblyException`이 난다. `MissingManifestResourceException`이 아니다.
>
> 이득(주 어셈블리 크기 감소)이 위험(폴백이 통째로 사라짐)에 비해 크지 않다. **특별한 이유가 없으면 기본값 `MainAssembly`를 유지하라.**

> **💡 `NeutralResourcesLanguage`는 거의 항상 붙이는 게 낫다**
>
> 비용이 0이고 이득이 두 가지다. 첫째, 기본 언어 사용자에게서 불필요한 어셈블리 프로빙이 사라진다. 둘째, **주 어셈블리 리소스가 어떤 언어인지 코드에 명시적으로 기록된다.** 3년 뒤 이 프로젝트를 인수한 사람이 `Greeting.resx`의 값이 영어인지 독일어인지 추측하지 않아도 된다.

### 조회 실패 시 나오는 예외들

| 예외 | 언제 | 흔한 원인 |
|---|---|---|
| (없음, `null` 반환) | 키가 어느 단계에도 없음 | 키 오타, 번역 누락 |
| `MissingManifestResourceException` | 주 어셈블리에서 `.resources` 컨테이너를 못 찾음 | `baseName` 오타·대소문자, `.resources` 확장자를 붙임, `EmbeddedResource` 등록 누락 |
| `MissingSatelliteAssemblyException` | `UltimateResourceFallbackLocation.Satellite`인데 그 위성이 없음 | 배포 누락 |
| `CultureNotFoundException` | `new CultureInfo("xx")`가 알 수 없는 이름 | 오타, 불변 전역화 모드 |
| `FileNotFoundException` | `GetSatelliteAssembly`를 직접 호출했는데 없음 | 위성 미배포 |

`MissingManifestResourceException`의 메시지는 대체로 다음과 같다.

```text
System.Resources.MissingManifestResourceException:
  Could not find any resources appropriate for the specified culture or the
  neutral culture. Make sure "MyApp.Greeting.resources" was correctly embedded
  or linked into assembly "MyApp" at compile time, or that all the satellite
  assemblies required are loadable and fully signed.
```

메시지가 친절하게도 **찾으려던 정확한 이름**을 알려준다. 이 문자열을 `GetManifestResourceNames()` 출력과 대조하면 원인이 1분 안에 나온다.

> **💡 진단 스니펫 하나를 프로젝트에 심어둬라**
>
> 리소스 문제는 매번 같은 방식으로 진단된다. 다음 메서드를 유틸리티로 두면 좋다.
>
> ```csharp
> public static void DumpResources(Assembly asm)
> {
>     Console.WriteLine($"== {asm.GetName().Name} ==");
>     foreach (string n in asm.GetManifestResourceNames())
>         Console.WriteLine($"  {n}");
>
>     Console.WriteLine($"CurrentCulture   = {CultureInfo.CurrentCulture.Name}");
>     Console.WriteLine($"CurrentUICulture = {CultureInfo.CurrentUICulture.Name}");
>
>     var c = CultureInfo.CurrentUICulture;
>     while (!c.Equals(CultureInfo.InvariantCulture))
>     {
>         try
>         {
>             var sat = asm.GetSatelliteAssembly(c);
>             Console.WriteLine($"  위성 [{c.Name}] → {sat.Location}");
>         }
>         catch (FileNotFoundException)
>         {
>             Console.WriteLine($"  위성 [{c.Name}] → 없음");
>         }
>         c = c.Parent;
>     }
> }
> ```
>
> `GetSatelliteAssembly`가 없을 때 `FileNotFoundException`을 던진다는 점에 주의하라. 폴백처럼 조용히 `null`을 주지 않는다.

### 불변 전역화 모드

.NET 8에서 네이티브 AOT 게시를 켠 채로 콘솔 앱을 만들면(Visual Studio의 "Enable native AOT publish" 체크, 또는 `dotnet new console --aot`) 프로젝트 파일에 다음이 들어간다.

```xml
<PropertyGroup>
  <TargetFramework>net8.0</TargetFramework>
  <PublishAot>true</PublishAot>
  <InvariantGlobalization>true</InvariantGlobalization>
</PropertyGroup>
```

`InvariantGlobalization`을 명시적으로 `true`로 설정하는 것은 **.NET 8 콘솔 앱 프로젝트 템플릿에서 새로 도입된 것**이다. ※.NET 8 이 설정은 콘솔 앱을 문화권 비의존적으로 만들어 전 세계 어디에 배포해도 같은 동작을 하도록 설계되었다. 이 속성을 `false`로 설정하거나 요소가 없으면, 콘솔 앱은 호스팅되는 현재 컴퓨터의 문화권을 기본값으로 쓴다.

> **📌 모든 콘솔 프로젝트에 이 줄이 들어가는 것은 아니다**
>
> 위 마크업은 AOT 옵션을 켰을 때 나오는 형태다. 옵션을 켜지 않은 프로젝트에는 `PublishAot`도 `InvariantGlobalization`도 없을 수 있다. 어느 쪽인지는 **자기 `.csproj`를 직접 열어 확인**하는 것이 유일하게 확실한 방법이고, 지역화하는 앱이라면 반드시 확인해야 한다.

확인해 보자.

```csharp
using System.Globalization;   // CultureInfo 사용

Console.WriteLine("Current culture: {0}", CultureInfo.CurrentCulture.DisplayName);
Console.WriteLine("OS version: {0}", Environment.OSVersion);
```

`InvariantGlobalization=true`인 상태로 실행하면 다음이 나온다.

```text
Current culture: Invariant Language (Invariant Country)
OS version: Microsoft Windows NT 10.0.22621.0
```

> **⚠️ 불변 전역화 모드는 지역화를 사실상 무력화한다**
>
> 이 모드에서는 다음이 모두 달라진다.
>
> - `CultureInfo.CurrentCulture`가 항상 불변 문화권
> - 문화권 인식 문자열 비교·정렬이 사실상 서수(ordinal) 비교로 동작(35.4절)
> - 시간대 이름, 통화 기호, 달력이 영어권 고정값
> - **`new CultureInfo("de")`가 `CultureNotFoundException`을 던진다** — `PredefinedCulturesOnly`가 기본으로 `true`가 되기 때문이다 ※.NET 6+
>
> 마지막 항목이 특히 잔인하다. 지역화된 라이브러리를 참조하는 순간, 그 라이브러리 내부의 `new CultureInfo(...)` 호출이 예외로 터진다. 원인 추적이 매우 어렵다.
>
> 컨테이너 이미지 크기를 줄이려고 `InvariantGlobalization=true`를 켰다가 지역화가 통째로 죽는 사고가 실제로 자주 일어난다. **지역화하는 앱에서는 켜지 마라.** 굳이 ICU 데이터를 줄여야 한다면 `PredefinedCulturesOnly=false`로 예외만이라도 막을 수 있지만, 그래도 서식과 정렬은 불변으로 남는다.

> **📌 ICU와 NLS** ※.NET 5+
>
> .NET 5부터 전역화 데이터의 출처가 Windows의 NLS에서 **ICU**(International Components for Unicode)로 바뀌었다. 모든 플랫폼에서 동일한 라이브러리를 쓰므로 동작이 일관되지만, .NET Framework나 .NET Core 3.1에서 올라올 때 **정렬 순서와 일부 서식이 미묘하게 달라진다.**
>
> Windows에서 옛 동작이 필요하면 되돌릴 수 있다.
>
> ```xml
> <PropertyGroup>
>   <UseNls>true</UseNls>
> </PropertyGroup>
> ```
>
> 이건 마이그레이션 중 임시방편으로만 써야 한다. Linux에서는 애초에 선택지가 없다.

## 53.5 지역화 워크플로 설계

여기서부터는 API가 아니라 **프로세스** 이야기다. 지역화가 실패하는 이유는 대부분 `ResourceManager`를 몰라서가 아니라, 번역이 코드베이스와 어긋난 채로 흘러가기 때문이다.

### 원칙 1 — 리소스 키에 규칙을 정한다

키 이름은 코드에서 100번 읽히고 번역자도 본다. 규칙 없이 늘어나면 3개월 뒤에 통제 불능이 된다.

권장하는 형태는 **`영역_요소_역할`** 이다.

```text
Login_SubmitButton_Text
Login_SubmitButton_Tooltip
Login_UsernameField_Label
Login_Error_InvalidCredentials
Order_Summary_TotalWithTax
Common_Cancel
Common_Retry
```

피해야 할 형태도 명확하다.

| 나쁜 키 | 문제 |
|---|---|
| `Msg1`, `Msg2`, `Str_017` | 번역자가 문맥을 알 수 없다 |
| `Please_enter_your_password` | 원문이 바뀌면 키를 바꿔야 한다 |
| `저장` | 코드에서 IME 전환이 필요하고 정렬이 깨진다 |
| `btnSaveText` | 헝가리안 표기가 UI 프레임워크에 종속된다 |

> **💡 키를 문장 자체로 쓰는 방식(`IStringLocalizer` 스타일)의 장단점**
>
> ASP.NET Core의 `IStringLocalizer`는 **영어 원문을 키로 쓰는** 방식을 기본으로 밀고 있다.
>
> ```csharp
> _localizer["Please enter your password"]
> ```
>
> 장점은 리소스가 없어도 영어가 그대로 나온다는 것(폴백이 항상 성공)이고, 단점은 **원문 오타 하나 고치면 모든 번역이 끊긴다**는 것이다. 문구를 자주 다듬는 제품이라면 이 방식은 지속 가능하지 않다.
>
> 판단 기준: **언어가 2~3개이고 문구가 안정적**이면 문장 키가 편하다. **언어가 5개 이상이거나 카피라이팅이 자주 바뀌면** 반드시 심볼릭 키를 써라.

### 원칙 2 — 문자열을 조립하지 않는다

이것이 지역화에서 가장 자주, 가장 크게 깨지는 지점이다.

```csharp
// 절대 하지 마라
string msg = Res.Order_Found + " " + count + " " + Res.Order_Items;
```

언어마다 어순이 다르고, 숫자 뒤에 오는 조사·복수형이 다르다. 반드시 **자리표시자를 포함한 완전한 문장**을 하나의 리소스로 둬야 한다.

```xml
<data name="Order_FoundItems" xml:space="preserve">
  <value>Found {0} items in your order.</value>
</data>
```

```csharp
string msg = string.Format(CultureInfo.CurrentCulture, Res.Order_FoundItems, count);
```

> **⚠️ 리소스 문자열에는 보간 문자열(`$"..."`)을 쓸 수 없다**
>
> 보간 문자열은 컴파일 타임에 해석된다. 리소스에서 읽어온 `"{0} items"`는 런타임 문자열이므로 `string.Format`이나 `CompositeFormat`으로 처리해야 한다. 이 차이를 잊고 리소스 값에 `{count}`처럼 이름을 쓰면 `FormatException`이 난다.
>
> ※.NET 8부터는 `System.Text.CompositeFormat`으로 형식 문자열을 미리 파싱해둘 수 있다. 반복 호출되는 자리에서 유용하다.
>
> ```csharp
> private static readonly CompositeFormat FoundItems =
>     CompositeFormat.Parse(Res.Order_FoundItems);
>
> string msg = string.Format(CultureInfo.CurrentCulture, FoundItems, count);
> ```

> **⚠️ 자리표시자 순서는 언어마다 바뀐다**
>
> `"{0} of {1}"`이 어떤 언어에서는 `"{1} 중 {0}"`이 된다. 번역자가 순서를 바꾸는 것은 정상이고 허용해야 한다. 그래서 **자리표시자에는 반드시 번호를 붙여야 하고**(`{0}`, `{1}`), 번역 지침에 각 자리표시자가 무엇인지 설명을 넣어야 한다.
>
> `.resx`의 `<comment>` 요소가 그 자리다.
>
> ```xml
> <data name="Order_ItemOfTotal" xml:space="preserve">
>   <value>{0} of {1}</value>
>   <comment>{0} = 현재 항목 번호, {1} = 전체 개수. 순서 변경 가능.</comment>
> </data>
> ```
>
> `<comment>`는 `.resources`로 컴파일될 때 버려지므로 런타임 비용이 0이다. 아끼지 말고 써라.

### 원칙 3 — 레이아웃은 문자열 길이 변화를 견뎌야 한다

영어를 기준으로 다른 언어의 길이는 상당히 달라진다. 대략적인 경험칙은 다음과 같다.

| 원문 영어 길이 | 독일어·프랑스어 예상 확장률 | 한국어·중국어·일본어 |
|---|---|---|
| 1~10자 | +100~200% | −20~40% (짧아짐) |
| 11~20자 | +80~100% | −20~40% |
| 21~50자 | +40~60% | −10~30% |
| 51자 이상 | +30~40% | −10~20% |

버튼 하나에 "OK"(2자)를 쓰면 독일어로는 "Einverstanden"(13자)이 될 수 있다. **고정 폭 버튼은 지역화의 적이다.**

> **💡 UI 리뷰는 독일어 또는 의사 지역화 문자열로 하라**
>
> 영어 화면만 보고 레이아웃을 확정하면 반드시 깨진다. 실제 번역을 기다릴 수 없다면 **의사 지역화(pseudo-localization)** 로 대신할 수 있다. 다음 항목에서 다룬다.

### 원칙 4 — 의사 지역화로 미리 깨뜨려본다

번역이 도착하기 전에 지역화 결함을 잡는 표준 기법이 **의사 지역화**다. 원문을 기계적으로 변형해 다음 세 가지를 동시에 테스트한다.

1. **하드코딩된 문자열 탐지** — 변형되지 않은 채 그대로 나오는 문자열은 리소스화되지 않은 것이다.
2. **레이아웃 확장 내성** — 문자열을 30~40% 늘려 잘림을 유도한다.
3. **비ASCII 문자 처리** — 인코딩·폰트·정렬 문제를 드러낸다.

원서가 제안하는 전략은 **여전히 영어로 읽히지만 표준 로마자 유니코드 문자를 쓰지 않는 단어로 지역화하는 것**이다.

```text
원문:      Save changes
의사 번역:  [!!! Ѕàvé çhàñgéѕ ‼‼‼ !!!]
```

앞뒤 대괄호가 잘림을 즉시 드러내고, 느낌표 패딩이 길이를 늘리며, 액센트 문자가 인코딩 문제를 드러낸다. 그러면서도 사람이 읽을 수는 있다.

의사 지역화 리소스는 **문화권 이름 하나를 정해 위성으로 만든다.** Windows에는 이 용도의 의사 로캘이 예약되어 있다.

| 코드 | 용도 |
|---|---|
| `qps-ploc` | 기본 의사 로캘. 액센트 문자 + 길이 확장 |
| `qps-ploca` | 아시아 문자 계열 의사 로캘 |
| `qps-plocm` | 오른쪽에서 왼쪽(RTL) 미러링 테스트 |

> **⚠️ `qps-ploc`을 모든 환경에서 만들 수 있다고 가정하지 마라**
>
> `new CultureInfo("qps-ploc")`이 Windows에서는 대개 동작하지만, ICU 데이터가 축소된 Linux 컨테이너나 `PredefinedCulturesOnly=true` 환경에서는 `CultureNotFoundException`이 날 수 있다.
>
> 안전한 대안은 런타임이 실제로 아는 문화권 코드 중 제품이 절대 쓰지 않을 것 하나를 의사 지역화 전용으로 정하는 것이다(예: `haw`, `mi`, `cy`). 팀 문서에 "이 코드는 의사 지역화 전용"이라고 못 박아두면 된다.

`.resx`를 의사 번역으로 변환하는 것은 스크립트로 자동화한다. 빌드 파이프라인에 한 단계 끼워 넣으면 된다.

```csharp
// 빌드 도구용 콘솔 앱 (요약)
// 사용: PseudoLoc Messages.resx Messages.qps-ploc.resx
using System.Xml.Linq;
using System.Text;

var src = XDocument.Load(args[0]);

static string Pseudo(string s)
{
    // 자리표시자({0}, {1} ...)와 XML 태그는 건드리지 않는다
    var sb = new StringBuilder("[!!! ");
    bool inPlaceholder = false;
    foreach (char c in s)
    {
        if (c == '{') inPlaceholder = true;
        if (c == '}') { inPlaceholder = false; sb.Append(c); continue; }
        if (inPlaceholder) { sb.Append(c); continue; }

        sb.Append(c switch
        {
            'a' => 'à', 'e' => 'é', 'i' => 'ï', 'o' => 'ô', 'u' => 'ü',
            'A' => 'À', 'E' => 'É', 'I' => 'Ï', 'O' => 'Ô', 'U' => 'Ü',
            's' => 'ѕ', 'S' => 'Ѕ', 'n' => 'ñ', 'c' => 'ç',
            _   => c
        });
    }
    // 길이를 약 40% 늘려 잘림을 유도한다
    int pad = Math.Max(3, s.Length * 2 / 5);
    sb.Append(' ').Append(new string('‼', pad)).Append(" !!!]");
    return sb.ToString();
}

foreach (var data in src.Root!.Elements("data"))
{
    var value = data.Element("value");
    if (value is null) continue;
    if ((string?)data.Attribute("mimetype") is not null) continue;   // 바이너리는 건너뛴다
    value.Value = Pseudo(value.Value);
}

src.Save(args[1]);
```

> **💡 의사 지역화는 CI에서 매 빌드 생성하고, 커밋하지 않는다**
>
> `Messages.qps-ploc.resx`를 소스 관리에 넣으면 원문이 바뀔 때마다 손으로 갱신해야 한다. 대신 **빌드 타깃에서 `Messages.resx`로부터 생성**하게 하면 항상 최신이다.
>
> ```xml
> <Target Name="GeneratePseudoLoc" BeforeTargets="PrepareResources"
>         Condition="'$(GeneratePseudoLoc)' == 'true'">
>   <Exec Command="dotnet run --project ../tools/PseudoLoc -- Messages.resx obj/Messages.qps-ploc.resx" />
>   <ItemGroup>
>     <EmbeddedResource Include="obj/Messages.qps-ploc.resx" />
>   </ItemGroup>
> </Target>
> ```
>
> 릴리스 빌드에서는 `GeneratePseudoLoc`을 끄면 의사 로캘 위성이 배포되지 않는다.

### 원칙 5 — 번역 외주 흐름을 정의한다

번역을 외부에 맡길 때 실무 흐름은 대략 이렇다.

```text
  개발자                     빌드/도구                     번역 벤더
    │                           │                            │
    │ Messages.resx 수정          │                            │
    ├──────────────────────────►│                            │
    │                           │ 신규/변경 키 추출            │
    │                           │ (resx diff)                 │
    │                           ├───────────────────────────►│
    │                           │   .xlf / .xliff 또는        │  번역
    │                           │   .resx 사본 전달            │  검수
    │                           │                            │
    │                           │◄───────────────────────────┤
    │                           │  번역된 파일 회수            │
    │                           │                            │
    │                           │ Messages.de.resx 병합        │
    │                           │ (기존 키 보존, 신규만 반영)   │
    │◄──────────────────────────┤                            │
    │  PR 리뷰 → 머지            │                            │
    │                           │                            │
    │ 빌드 → de/MyApp.resources.dll                           │
```

핵심은 **개발자가 `Messages.de.resx`를 직접 편집하지 않는다**는 것이다. 편집하는 순간 다음 번역 라운드에서 덮어써진다.

| 교환 형식 | 장점 | 단점 |
|---|---|---|
| `.resx` 사본 | 도구 없이 바로 빌드 가능 | 번역 메모리(TM) 도구 지원이 약함 |
| XLIFF (`.xlf`) | 업계 표준, 대부분의 CAT 도구 지원 | 변환 단계가 필요 |
| CSV / 스프레드시트 | 벤더 진입장벽이 가장 낮음 | 이스케이프·인코딩 사고가 잦음 |

> **⚠️ 스프레드시트로 번역을 주고받으면 반드시 사고가 난다**
>
> 자주 겪는 실패는 다음과 같다.
>
> - Excel이 `{0}`을 그대로 두지만 앞뒤 공백을 잘라낸다
> - 선행 `+`, `-`, `=`가 수식으로 해석된다
> - UTF-8 BOM 없이 저장되어 한글이 깨진다
> - 줄바꿈이 포함된 문자열이 여러 행으로 쪼개진다
>
> 어쩔 수 없이 CSV를 써야 한다면 **왕복 변환 테스트**(resx → csv → resx가 원본과 바이트 단위로 같은지)를 CI에 넣어라.

### 원칙 6 — 키 누락을 CI에서 잡는다

폴백이 조용하다는 것은(53.4절) 번역 누락이 배포까지 살아남는다는 뜻이다. 검사를 자동화해야 한다.

```csharp
// 테스트 프로젝트에 두는 검증
using System.Resources;
using System.Xml.Linq;
using Xunit;

public class ResourceCompletenessTests
{
    static HashSet<string> KeysOf(string resxPath) =>
        XDocument.Load(resxPath).Root!.Elements("data")
                 .Select(d => (string)d.Attribute("name")!)
                 .ToHashSet(StringComparer.Ordinal);

    [Theory]
    [InlineData("Messages.de.resx")]
    [InlineData("Messages.ko.resx")]
    [InlineData("Messages.ja.resx")]
    public void 모든_문화권이_기본_키를_전부_담는다(string localized)
    {
        var baseKeys  = KeysOf("Messages.resx");
        var localKeys = KeysOf(localized);

        var missing = baseKeys.Except(localKeys).OrderBy(k => k).ToList();
        var extra   = localKeys.Except(baseKeys).OrderBy(k => k).ToList();

        Assert.True(missing.Count == 0,
            $"{localized}에 빠진 키: {string.Join(", ", missing)}");
        Assert.True(extra.Count == 0,
            $"{localized}에 남은 죽은 키: {string.Join(", ", extra)}");
    }
}
```

같은 방식으로 **자리표시자 개수 검증**도 넣는 것이 좋다. 번역자가 `{1}`을 빠뜨리면 런타임에 `FormatException`이 나는데, 그것도 그 언어 사용자에게만 난다.

```csharp
static IEnumerable<int> PlaceholderIndices(string s)
{
    for (int i = 0; i < s.Length - 1; i++)
        if (s[i] == '{' && char.IsDigit(s[i + 1]))
            yield return s[i + 1] - '0';
}

// 기본 리소스와 번역본의 자리표시자 집합이 같은지 비교한다
```

> **💡 "죽은 키"도 함께 잡아라**
>
> 위 테스트의 `extra` 검사가 그것이다. 기능이 제거되면 `Messages.resx`에서 키를 지우지만, 번역본에는 남아 있기 마련이다. 방치하면 번역 비용이 계속 발생하고 파일이 비대해진다.
>
> 더 나아가 **소스 코드에서 참조되지 않는 키**를 찾는 검사도 넣을 수 있다. 강력한 형식 래퍼를 쓰면 이건 IDE의 "사용되지 않는 멤버" 분석으로 거의 공짜다.

### 원칙 7 — 리소스 어셈블리를 어떻게 쪼갤 것인가

`.resx` 하나에 모든 문자열을 넣는 것과, 기능별로 쪼개는 것 중 어느 쪽이 나은가.

| 구성 | 장점 | 단점 |
|---|---|---|
| 단일 `.resx` | 관리 단순, `ResourceManager` 하나 | 파일 병합 충돌 빈발, 부분 로드 불가 |
| 기능별 `.resx` | 팀별 소유권 분리, 충돌 감소 | `ResourceManager` 인스턴스 증가 |
| 프로젝트별 `.resx` | 라이브러리 단위 재사용 | 공통 문자열 중복 |

> **💡 실무 기본값: 프로젝트마다 하나, 그 안에서 200~300키를 넘으면 기능별로 쪼갠다**
>
> `.resx`는 XML이고 Git이 병합할 수 없는 구조는 아니지만, 여러 사람이 동시에 문자열을 추가하면 충돌이 매우 잦다. 200키를 넘어가면 `Messages.Orders.resx`, `Messages.Billing.resx` 식으로 나누는 편이 낫다.
>
> 반대로 `ResourceManager`를 수십 개 만드는 것도 좋지 않다. 각 인스턴스가 자기 `ResourceSet` 캐시를 따로 들고 있으므로 메모리가 중복된다. 실무적으로는 **10개 안쪽**이 적당하다.

공통 문자열(`Common_Cancel`, `Common_OK`)은 별도 라이브러리 프로젝트에 두고 참조하는 편이 낫다. 다만 그 라이브러리의 위성 어셈블리도 함께 배포되어야 한다는 점을 잊지 마라. `SatelliteResourceLanguages`(53.3절)에 걸리기 쉬운 지점이다.

### ASP.NET Core의 지역화 계층

웹 애플리케이션에서는 `ResourceManager`를 직접 쓰는 대신 `Microsoft.Extensions.Localization`의 추상화를 쓰는 것이 표준이다. 내부적으로는 결국 `ResourceManager`와 위성 어셈블리를 쓰므로, 지금까지 본 모든 규칙이 그대로 적용된다.

| 타입 | 역할 |
|---|---|
| `IStringLocalizer` | 리소스 조회. 인덱서로 `LocalizedString` 반환 |
| `IStringLocalizer<T>` | 타입 `T`를 기준으로 리소스 경로를 결정 |
| `IStringLocalizerFactory` | 이름/위치로 로컬라이저 생성 |
| `LocalizedString` | 값 + `ResourceNotFound` 플래그 |
| `RequestLocalizationOptions` | 요청별 문화권 결정 규칙 |

등록과 사용은 다음과 같다.

```csharp
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddLocalization(options => options.ResourcesPath = "Resources");

var app = builder.Build();

var supported = new[] { "en", "de", "ko" };
app.UseRequestLocalization(new RequestLocalizationOptions()
    .SetDefaultCulture("en")
    .AddSupportedCultures(supported)      // CurrentCulture (서식)
    .AddSupportedUICultures(supported));  // CurrentUICulture (리소스)
```

```csharp
public class HomeController : Controller
{
    private readonly IStringLocalizer<HomeController> _loc;

    public HomeController(IStringLocalizer<HomeController> loc) => _loc = loc;

    public IActionResult Index()
    {
        ViewData["Title"] = _loc["Home_Title"];
        return View();
    }
}
```

`ResourcesPath = "Resources"`로 두면 `HomeController`의 리소스 파일 위치는 다음 둘 중 하나다.

```text
Resources/Controllers.HomeController.de.resx      (점 구분)
Resources/Controllers/HomeController.de.resx      (폴더 구분)
```

> **⚠️ `IStringLocalizer`는 키가 없어도 예외를 던지지 않는다**
>
> 반환되는 `LocalizedString`은 리소스가 없으면 **키 문자열 자체를 값으로** 담고 `ResourceNotFound = true`를 설정한다. 즉 화면에 `Home_Title`이라는 날것의 키가 그대로 표시된다. 예외도, 로그도 없다.
>
> 이것을 잡으려면 명시적으로 확인해야 한다.
>
> ```csharp
> var s = _loc["Home_Title"];
> if (s.ResourceNotFound)
>     _logger.LogWarning("리소스 누락: {Name}", s.Name);
> ```
>
> 개발/스테이징 환경에서만 켜지는 진단 미들웨어로 이 검사를 중앙화하면 좋다.

> **⚠️ `AddSupportedCultures`와 `AddSupportedUICultures`를 혼동하지 마라**
>
> 전자는 `CurrentCulture`(숫자·날짜 서식)를, 후자는 `CurrentUICulture`(리소스 조회)를 제어한다. 53.4절의 구분이 그대로 살아 있다.
>
> 흔한 사고: `AddSupportedCultures`만 설정하고 `AddSupportedUICultures`를 빠뜨리면, 날짜는 독일식으로 나오는데 **UI 문자열은 영어로 남는다.** 반대로 `AddSupportedUICultures`만 설정하면 UI는 독일어인데 숫자 구분자가 영어식이다.
>
> 두 목록이 달라야 할 이유는 거의 없다. 같은 배열을 양쪽에 넘겨라.

요청 문화권을 결정하는 기본 공급자는 다음 순서로 동작한다.

| 순서 | 공급자 | 출처 |
|---|---|---|
| 1 | `QueryStringRequestCultureProvider` | `?culture=de&ui-culture=de` |
| 2 | `CookieRequestCultureProvider` | `.AspNetCore.Culture` 쿠키 |
| 3 | `AcceptLanguageHeaderRequestCultureProvider` | `Accept-Language` 헤더 |

> **💡 쿼리 문자열 공급자는 QA에 매우 유용하다**
>
> `?culture=de&ui-culture=de`를 URL에 붙이는 것만으로 브라우저 설정을 건드리지 않고 언어를 전환할 수 있다. 의사 지역화 로캘과 조합하면 QA가 한 번의 클릭으로 레이아웃 문제를 확인한다.
>
> 다만 프로덕션에서는 이 공급자를 제거하는 것을 고려하라. 캐시 키에 문화권이 안 들어가는 구성이라면 CDN 캐시 오염의 통로가 된다.

### 트리밍과 AOT 고려사항

배포 크기를 줄이려고 트리밍을 켜면 리소스 쪽에서 몇 가지가 걸린다.

- `PublishTrimmed=true`는 기본적으로 위성 어셈블리를 제거하지 않지만, `SatelliteResourceLanguages`와 조합되면 예상과 다르게 동작할 수 있다.
- 강력한 형식 래퍼 클래스는 `ResourceManager`를 문자열 `baseName`으로 생성한다. 이건 리플렉션이 아니라 리소스 조회이므로 트리머가 끊지는 않지만, **`GetObject`로 임의 타입을 꺼내는 코드는 그 타입이 트리밍될 수 있다.**
- 네이티브 AOT에서는 위성 어셈블리 모델 자체가 성립하지 않는다(53.3절).

> **💡 지역화가 필요한 앱은 트리밍·AOT를 켜기 전에 반드시 게시본을 실행해보라**
>
> 이 조합의 문제는 전부 **게시 이후에만** 드러난다. `dotnet run`으로는 절대 재현되지 않는다. CI 파이프라인에 "게시본을 각 지원 문화권으로 한 번씩 실행하고 대표 문자열 하나를 검증하는" 스모크 테스트를 넣는 것이 가장 확실한 방어다.

### 지역화 체크리스트

마지막으로 새 프로젝트를 시작할 때 훑을 목록을 정리한다.

| 항목 | 확인 |
|---|---|
| `[assembly: NeutralResourcesLanguage("...")]`를 붙였는가 | 53.4절 |
| `.resx`에 문자열만 넣었는가(바이너리는 별도) | 53.2절 |
| 키 명명 규칙을 문서화했는가 | 53.5절 |
| `.Designer.cs`를 소스 관리에 커밋했는가 | 53.2절 |
| 문자열 조립 대신 자리표시자를 썼는가 | 53.5절 |

## 이 장의 요약

- **어셈블리 리소스는 이름 붙은 바이트 스트림**이다. 매니페스트의 ManifestResourceDef 테이블(52.2절)이 이름 → (오프셋, 길이) 사전 역할을 하고, `Assembly.GetManifestResourceStream`이 그 구간을 가리키는 스트림을 복사 없이 돌려준다.
- **리소스 이름은 `RootNamespace` + 폴더 + 파일명**으로 자동 조립되며 대소문자를 구분한다. `LogicalName` 메타데이터로 고정하는 편이 리팩터링에 안전하다.
- **`.resx`는 디자인 타임 XML, `.resources`는 바이너리 컨테이너**다. `.resx` → (`GenerateResource`/`resgen`) → `.resources` → (`csc /resource`) → 어셈블리 임베드 리소스로 이어지는 파이프라인의 각 단계에서 이름이 어떻게 변형되는지가 대부분 사고의 원인이다. `ResourceManager`의 `baseName`에는 `.resources` 확장자를 붙이지 않는다.
- **WPF의 `Resource` 빌드 작업은 `Embedded Resource`와 다르다.** 전자는 `<AssemblyName>.g.resources` 컨테이너에 들어가고 pack URI로 접근한다. 여기에 XAML의 `StaticResource`/`DynamicResource`까지 더해 한 프로젝트에 "리소스"가 세 종류 공존한다.
- **위성 어셈블리는 코드 없이 리소스만 담은 어셈블리**로, `AssemblyDef`의 문화권 필드가 채워져 있다. 파일 이름은 모든 문화권에서 `<주어셈블리>.resources.dll`로 같고, **폴더 이름이 문화권을 구별한다.** 배포 시 디렉터리 구조를 반드시 보존해야 한다.
- **`CurrentCulture`는 서식을, `CurrentUICulture`는 리소스 조회를 결정한다.** 두 값은 다를 수 있고 개발 머신에서는 대개 같아서 버그가 늦게 발견된다.
- **폴백은 특정 문화권 → 중립 문화권 → 주 어셈블리 순으로, 키 단위로** 일어난다. 부분 번역이 허용되는 대신 번역 누락이 조용히 가려진다. `NeutralResourcesLanguage`로 기본 언어 사용자의 불필요한 프로빙을 없앨 수 있다.
- **`InvariantGlobalization=true`는 지역화를 무력화한다.** .NET 8의 AOT 콘솔 템플릿이 이 줄을 넣어주므로, 지역화하는 앱이라면 `.csproj`를 열어 확인하고 꺼야 한다. `PredefinedCulturesOnly` 때문에 `new CultureInfo("de")`가 예외를 던진다.
- **지역화 실패의 대부분은 API가 아니라 프로세스 문제**다. 키 명명 규칙, 문자열 조립 금지, 자리표시자 주석, 의사 지역화 빌드, 키 누락 CI 검사 — 이 다섯 가지가 있으면 나머지는 대체로 따라온다.

## 연습 문제

1. 아무 프로젝트에나 `Assets/logo.png`를 추가하고 빌드 작업을 `Embedded Resource`로 설정한 뒤, `GetManifestResourceNames()`를 출력해 실제 리소스 이름을 확인하라. 그다음 폴더 이름을 `my-assets`로 바꾸고 다시 확인해 하이픈이 어떻게 처리되는지 관찰하라.
2. `Greeting.resx`를 만들어 `Hello = "hello"`를 넣고, `Greeting.de.resx`에 `Hello = "hallo"`를 넣어 빌드하라. `bin` 폴더에서 `de/` 하위 디렉터리와 위성 어셈블리를 확인하고, `ildasm`으로 그 위성의 매니페스트를 열어 `.assembly` 블록에 `Culture`가 어떻게 기록되었는지 확인하라. TypeDef가 비어 있는지도 보라.
3. 2번의 앱에서 `CultureInfo.CurrentUICulture`를 `de-AT`로 바꾸고 실행하라. `de-AT` 위성이 없는데도 `hallo`가 나오는 것을 확인하고, `de` 폴더를 삭제한 뒤 다시 실행해 무엇이 나오는지 비교하라.
4. `ResourceManager`의 `baseName`에 일부러 `.resources`를 붙여 `MissingManifestResourceException`을 유발하라. 예외 메시지가 알려주는 리소스 이름과 `GetManifestResourceNames()` 출력을 나란히 놓고 차이를 확인하라.
5. `CurrentCulture`와 `CurrentUICulture`를 서로 다르게 설정한 뒤(`ko-KR` / `en-US`), `DateTime.Now.ToString()`과 `ResourceManager.GetString(...)`의 결과가 각각 어느 쪽을 따르는지 실측하라. 그다음 `Task.Run` 안에서 같은 값을 출력해 문화권이 흘러가는지 확인하라.
6. 프로젝트에 `<InvariantGlobalization>true</InvariantGlobalization>`을 추가하고 2번의 앱을 다시 실행하라. `new CultureInfo("de")`에서 어떤 예외가 나는지 확인하고, `<PredefinedCulturesOnly>false</PredefinedCulturesOnly>`를 추가하면 무엇이 달라지는지 비교하라.
7. 53.5절의 의사 지역화 스크립트를 실행해 `Messages.qps-ploc.resx`를 만들고, 그것으로 빌드한 위성으로 앱을 실행하라. 리소스화되지 않은 하드코딩 문자열이 몇 개나 남아 있는지 세어보라.
8. `SatelliteResourceLanguages`를 `en`으로 설정한 상태에서 `Messages.de.resx`를 추가하고 빌드하라. 경고 없이 위성이 사라지는 것을 확인하고, `bin` 폴더 목록과 `obj` 폴더 목록을 비교해 어느 단계에서 걸러지는지 파악하라.
