# 82장. 사고 실험 — 하나의 기능을 다섯 번 고쳐 쓰기

> **이 장의 위치** — Part XVI의 마지막 장이자 3권 전체의 종합 연습이다. 61장부터 72장까지 배운 것 — 캐시, 할당, GC, 벤치마킹, `Span`, 데이터 배치, 벡터화 — 은 각각 따로 익혔다. 실무에서는 그것들이 **하나의 함수 위에 순서대로 쌓인다.** 이 장은 이론을 다시 설명하지 않는다. 하나의 현실적인 문제를 잡고, 다섯 번 고쳐 쓰면서 매 단계마다 무엇을 얻고 무엇을 잃었는지 기록하는 **작업 일지**다.
>
> **선수 지식** — 67장(측정 없이 최적화 없다), 68장(`Span`과 `Memory`), 69장(할당 줄이기), 71장(벡터화와 하드웨어 가속), 80장(테스트 가능한 코드)
>
> **이 장에서 다루지 않는 것** — 벤치마크 방법론 자체는 67.3~67.4절에서 끝냈다. 여기서는 그 규칙을 **적용만** 한다. 문자열 처리 계열의 무할당화 워크스루는 69.9절에 이미 있으므로 이 장은 다른 영역을 고른다. 런타임 소스를 직접 읽어 확인하는 방법은 83장에서 다룬다.

## 82.1 요구사항 정의와 기준선(baseline) 측정

### 문제

**텔레메트리 수집기의 프레임 디코더**를 만든다. 요구사항은 한 문단이다.

> 장비가 TCP 소켓으로 고정 형식의 바이너리 프레임을 연속해서 보낸다. 프레임은 동기 마커로 시작하고, 길이·채널 번호·시퀀스 번호를 담은 헤더와 16비트 정수 샘플의 배열, 그리고 체크섬으로 끝난다. 수집기는 바이트 스트림을 받아 프레임 경계를 찾고, 체크섬이 맞지 않는 프레임은 버리고, **채널별로** 프레임 수·샘플 수·샘플 합계·최솟값·최댓값과 **시퀀스 번호가 끊긴 횟수**를 집계해야 한다. 스트림 중간에 잡음이 섞여 동기가 깨질 수 있으므로, 깨지면 다음 동기 마커를 찾아 복구해야 한다. 소켓 읽기 단위와 프레임 경계는 일치하지 않는다.

이 문제를 고른 이유는 세 가지다.

1. **요구사항이 짧고 정답이 명확하다.** 최적화된 버전이 정확한지 아닌지를 기계적으로 판정할 수 있다. 성능 작업에서 이건 사치가 아니라 전제 조건이다.
2. **다섯 단계가 자연스럽게 나온다.** 평범하게 짜면 알고리즘 결함이 생기고, 그걸 고치면 할당이 남고, 그걸 지우면 파싱 자체가 병목이 되고, 마지막에 산술이 남는다. 억지로 단계를 만들 필요가 없다.
3. **바이트 지향이다.** 69.9절의 워크스루는 문자열·텍스트 계열이었다. 여기서는 정렬·엔디언·재해석·SIMD 같은 다른 근육을 쓴다.

### 프레임 형식

```text
   0        2        4        6              10          10+LEN     12+LEN
   ┌────────┬────────┬────────┬──────────────┬───────────┬────────┐
   │ SYNC   │ LEN    │ CH     │ SEQ          │ PAYLOAD   │ CKSUM  │
   │ 2 B    │ 2 B    │ 2 B    │ 4 B          │ LEN B     │ 2 B    │
   │ AA 55  │ u16 LE │ u16 LE │ u32 LE       │ i16 LE ×N │ u16 LE │
   └────────┴────────┴────────┴──────────────┴───────────┴────────┘
   └──────────────── 헤더 10 B ─────────────┘└─ N = LEN/2 ─┘
   └────────────── 체크섬 계산 대상 ──────────────────────┘
```

| 필드 | 크기 | 형식 | 의미와 제약 |
|---|---|---|---|
| `SYNC` | 2 B | 고정 `0xAA 0x55` | 프레임 시작 표지. 페이로드 안에도 우연히 나타날 수 있다 |
| `LEN` | 2 B | u16 LE | 페이로드 바이트 수. **짝수**이고 `2 ≤ LEN ≤ 2048` |
| `CH` | 2 B | u16 LE | 채널 번호. `0 ≤ CH < 1024` |
| `SEQ` | 4 B | u32 LE | 채널별 시퀀스. 정상이면 1씩 증가 |
| `PAYLOAD` | `LEN` B | i16 LE × `LEN/2` | 샘플 |
| `CKSUM` | 2 B | u16 LE | 헤더 + 페이로드를 u16 LE 워드로 보고 전부 더한 값 (mod 2¹⁶) |

체크섬이 워드 단위 단순 합인 것은 실제 산업용 프로토콜에서 흔하다. 계산이 싸고, 나중에 보겠지만 **벡터화가 자명하다.** CRC였다면 5차의 이야기가 완전히 달라진다 — 그 차이는 82.6절과 82.8절에서 다시 다룬다.

### 성공 기준 — 무엇을 최적화하고 무엇을 포기하는가

67.1절의 규칙대로, 최적화를 시작하기 전에 **세 축 중 무엇을 최적화하는지** 못 박는다.

| 항목 | 결정 | 근거 |
|---|---|---|
| **주 목표** | **처리량**(MB/s). 한 코어가 초당 처리하는 입력 바이트 수 | 수집기는 배치가 아니라 상시 스트림을 받는다. 코어당 처리량이 필요한 서버 대수를 정한다 |
| **부 목표** | **할당 0에 가까울 것** | 24시간 상시 동작. gen2 GC 한 번이 수집 지연을 만든다(64장) |
| 지연 시간 | 목표 없음 | 프레임 하나의 처리 지연은 마이크로초 단위이고 아무도 보지 않는다 |
| **포기하는 것 ①** | 프레임 재정렬 지원 | 채널별 순서는 TCP가 보장한다. 재정렬은 요구사항이 아니다 |
| **포기하는 것 ②** | 디코딩 결과의 보존 | 집계만 하면 된다. 개별 프레임을 메모리에 남길 필요가 없다 |
| **포기하는 것 ③** | 범용성 | 이 한 프로토콜만 처리한다. 플러그인 가능한 디코더가 아니다 |
| **포기하지 않는 것** | 정확성 | 어떤 최적화도 결과를 바꿔서는 안 된다. 이것만은 협상 대상이 아니다 |

포기 목록을 먼저 쓰는 것이 중요하다. 나중에 "프레임 객체를 없애도 되나?"라는 질문이 나왔을 때, 답은 이미 여기에 적혀 있다.

> **💡 성능 작업의 첫 산출물은 코드가 아니라 이 표다**
>
> "빠르게 해 달라"는 요청을 받으면 코드부터 열지 말고 이 표부터 채워라. 채우다 보면 "그런데 왜 빨라야 하죠?"에서 막히는 경우가 절반이다. 거기서 막히면 최적화할 이유가 없는 것이고, 그 사실을 발견한 것만으로 그날의 일은 끝났다.
>
> 이 표는 82.8절에서 "어디서 멈출 것인가"를 판단할 때 다시 쓰인다. 목표가 적혀 있지 않으면 멈출 지점도 없다.

### 입력 데이터

측정에 쓸 데이터를 결정론적으로 만든다. **고정 시드**를 쓰는 것이 핵심이다 — 실행할 때마다 데이터가 바뀌면 버전 간 비교가 무의미해진다(67.4절).

| 항목 | 값 | 비고 |
|---|---|---|
| 총 입력 크기 | 16 MiB | L3 캐시를 확실히 넘긴다(61.4절) |
| 프레임 수 | 약 61,400개 | 프레임당 평균 272 B |
| 채널 수 | 1,024개 | 균등 분포. 프레임이 채널별로 뒤섞여 온다 |
| 프레임당 샘플 수 | 128개 (`LEN` = 256) | 82.6절에서 이 값을 8·32·128·512로 흔들어 본다 |
| 체크섬 오류 | 전체의 0.5% | 재동기 경로를 실제로 밟게 한다 |
| 시퀀스 결손 | 전체의 0.2% | 결손 검출 경로를 밟게 한다 |
| 프레임 사이 잡음 | 전체의 0.1% 위치에 1~7 B | 재동기 스캔이 죽은 코드가 되지 않게 한다 |
| 소켓 읽기 단위 | 64 KiB | 프레임 경계와 일치하지 않는다 |

인코더와 데이터 생성기는 다음과 같다. 이 코드는 **테스트와 벤치마크가 공유**한다.

```csharp
using System.Buffers.Binary;

public static class FrameCodec
{
    public const int HeaderSize  = 10;
    public const int TrailerSize = 2;
    public const int MaxPayload  = 2048;
    public const int MaxChannels = 1024;

    // 헤더 + 페이로드를 u16 LE 워드의 합(mod 2^16)으로 본다
    public static ushort Checksum(ReadOnlySpan<byte> headerAndPayload)
    {
        ushort sum = 0;
        for (int i = 0; i + 1 < headerAndPayload.Length; i += 2)
            sum = (ushort)(sum + BinaryPrimitives.ReadUInt16LittleEndian(headerAndPayload[i..]));
        return sum;
    }

    /// <summary>프레임 하나를 dest에 기록하고 총 바이트 수를 반환한다.</summary>
    public static int Write(Span<byte> dest, ushort channel, uint seq, ReadOnlySpan<short> samples)
    {
        int len   = samples.Length * 2;
        int total = HeaderSize + len + TrailerSize;
        if (dest.Length < total)
            throw new ArgumentException("버퍼가 프레임보다 작다", nameof(dest));

        dest[0] = 0xAA;
        dest[1] = 0x55;
        BinaryPrimitives.WriteUInt16LittleEndian(dest[2..], (ushort)len);
        BinaryPrimitives.WriteUInt16LittleEndian(dest[4..], channel);
        BinaryPrimitives.WriteUInt32LittleEndian(dest[6..], seq);

        for (int i = 0; i < samples.Length; i++)
            BinaryPrimitives.WriteInt16LittleEndian(dest[(HeaderSize + i * 2)..], samples[i]);

        ushort ck = Checksum(dest[..(HeaderSize + len)]);
        BinaryPrimitives.WriteUInt16LittleEndian(dest[(HeaderSize + len)..], ck);
        return total;
    }
}
```

```csharp
public static class TestStream
{
    /// <summary>결정론적 입력 스트림을 만든다. seed가 같으면 바이트가 완전히 같다.</summary>
    public static byte[] Build(int targetBytes, int samplesPerFrame, int seed = 20260905)
    {
        var rng   = new Random(seed);
        var seqs  = new uint[FrameCodec.MaxChannels];
        var buf   = new byte[targetBytes + FrameCodec.MaxPayload + 32];
        var frame = new byte[FrameCodec.MaxPayload + 32];
        var samples = new short[samplesPerFrame];
        int pos = 0;

        while (pos < targetBytes)
        {
            ushort ch = (ushort)rng.Next(FrameCodec.MaxChannels);

            // 0.2% 확률로 시퀀스를 건너뛴다 (결손 시뮬레이션)
            if (rng.NextDouble() < 0.002) seqs[ch] += (uint)rng.Next(2, 5);

            for (int i = 0; i < samples.Length; i++)
                samples[i] = (short)rng.Next(short.MinValue, short.MaxValue + 1);

            int n = FrameCodec.Write(frame, ch, seqs[ch]++, samples);

            // 0.5% 확률로 페이로드 한 바이트를 뒤집는다 (체크섬 오류 시뮬레이션)
            if (rng.NextDouble() < 0.005)
                frame[FrameCodec.HeaderSize + rng.Next(samples.Length * 2)] ^= 0x01;

            Buffer.BlockCopy(frame, 0, buf, pos, n);
            pos += n;

            // 0.1% 확률로 프레임 사이에 잡음을 끼워 넣는다 (재동기 경로)
            if (rng.NextDouble() < 0.001)
            {
                int noise = rng.Next(1, 8);
                for (int i = 0; i < noise; i++) buf[pos + i] = (byte)rng.Next(256);
                pos += noise;
            }
        }
        return buf[..pos];
    }
}
```

> **⚠️ 잡음 바이트가 우연히 `AA 55`가 될 수 있다**
>
> `rng.Next(256)`로 채운 잡음은 확률적으로 `0xAA 0x55` 쌍을 만든다. 그러면 디코더는 그 자리를 프레임 시작으로 오인하고, 뒤따르는 바이트를 `LEN`으로 읽고, 대부분 길이 검증이나 체크섬에서 걸러진다.
>
> **이건 결함이 아니라 이 데이터의 존재 이유다.** 실제 스트림에서도 같은 일이 일어나고, 디코더는 그 상황에서 무한 루프에 빠지지 않고 전진해야 한다. 잡음을 넣지 않은 "깨끗한" 데이터로만 벤치마크하면 재동기 코드가 통째로 죽은 코드가 되어 측정에서 사라진다(67.4절 사례 1). **잘못 측정하는 가장 흔한 방법은 잘못된 데이터를 쓰는 것이다.**

### 측정 하네스

BenchmarkDotNet 설정 자체는 67.3절에서 끝냈으므로 여기서는 이 문제에 특화된 부분만 본다.

```csharp
using BenchmarkDotNet.Attributes;
using BenchmarkDotNet.Engines;
using BenchmarkDotNet.Running;

[MemoryDiagnoser]
public class DecoderBench
{
    private byte[] _stream = null!;
    private byte[] _chunk  = null!;      // 소켓 읽기 버퍼 (재사용)

    [Params(128)]                        // 82.6절에서 8, 32, 128, 512로 늘린다
    public int SamplesPerFrame { get; set; }

    private const int ChunkSize = 64 * 1024;

    [GlobalSetup]
    public void Setup()
    {
        _stream = TestStream.Build(16 * 1024 * 1024, SamplesPerFrame);
        _chunk  = new byte[ChunkSize];
    }

    // 소켓 읽기를 흉내낸다. 스트림을 64 KiB씩 잘라 디코더에 밀어 넣는다.
    private void Pump(Action<byte[], int> feed)
    {
        for (int off = 0; off < _stream.Length; off += ChunkSize)
        {
            int n = Math.Min(ChunkSize, _stream.Length - off);
            Buffer.BlockCopy(_stream, off, _chunk, 0, n);
            feed(_chunk, n);
        }
    }

    [Benchmark(Baseline = true)]
    public object V1_Naive()
    {
        var d = new DecoderV1();
        Pump((b, n) => d.Feed(b[..n]));
        return d.Aggregate();            // ★ 반드시 반환한다 (67.4절)
    }
}

public static class Program
{
    public static void Main(string[] args)
        => BenchmarkSwitcher.FromAssembly(typeof(Program).Assembly).Run(args);
}
```

세 가지가 이 하네스에서 의도적이다.

- **입력 버퍼를 재사용한다.** 소켓에서 읽을 때 매번 새 배열을 만드는 코드는 그 자체로 잘못이고(69.3절), 그 비용이 디코더 비용을 가려서는 안 된다.
- **`Pump`가 디코더 밖에 있다.** 모든 버전이 같은 방식으로 데이터를 받으므로, 버전 간 차이는 순수하게 디코더 내부의 차이다.
- **결과를 반환한다.** `Aggregate()`의 반환값을 버리면 JIT이 집계 전체를 죽은 코드로 지울 수 있다(67.4절).

> **⚠️ `Pump`가 받는 `Action<byte[], int>`는 벤치마크 대상이 아니지만 측정에는 들어간다**
>
> 델리게이트 호출은 인라이닝되지 않고, 청크마다 한 번씩 일어난다. 16 MiB / 64 KiB = 256번이므로 전체 시간에서 무시할 수 있는 수준이다. 그러나 **청크 크기를 512 B로 줄이면 32,768번**이 되고, 그때는 델리게이트 비용이 결과를 오염시킨다.
>
> 벤치마크 하네스 자체의 오버헤드가 측정 대상보다 커지는 지점이 어디인지 항상 의식해야 한다. 확인하는 방법은 단순하다 — **아무 일도 하지 않는 디코더**를 하나 만들어 같은 하네스로 돌려 보면 하네스의 바닥값이 나온다.

### 반복의 기록 규약

다섯 번 고쳐 쓸 것이므로, 매 단계마다 **똑같은 네 칸**을 채운다. 이 규율이 없으면 세 번째쯤에서 "지금 왜 이걸 하고 있지"를 잃는다.

| 칸 | 기록할 것 |
|---|---|
| **적용한 것** | 3권의 어느 절에서 온 기법인지. 절 번호를 반드시 적는다 |
| **결과** | Mean / Allocated / Ratio. 기준선 대비 |
| **새로 생긴 위험** | 이 단계에서 새로 가능해진 버그, 잃은 가독성, 추가된 제약 |
| **채택 여부** | 실무 코드에 넣을 것인가. 넣는다면 어떤 조건에서 |

네 번째 칸이 가장 중요하다. **성능 실험과 채택 결정은 다른 일이다.** 실험은 다섯 번 다 해도 되지만, 채택은 두 번에서 멈출 수 있다.

## 82.2 1차: 정확하게 동작하는 코드

### 테스트를 먼저 쓴다

다섯 번 고쳐 쓸 코드다. 매 단계에서 결과가 바뀌지 않았음을 **기계가 확인해 주지 않으면** 이 작업은 불가능하다. 그러니 디코더를 쓰기 전에 테스트를 쓴다(80.1절).

```csharp
using Xunit;

public class DecoderContractTests
{
    // 프레임 하나를 만들어 스트림 하나로 만드는 도우미
    private static byte[] One(ushort ch, uint seq, params short[] samples)
    {
        var buf = new byte[FrameCodec.HeaderSize + samples.Length * 2 + FrameCodec.TrailerSize];
        FrameCodec.Write(buf, ch, seq, samples);
        return buf;
    }

    [Fact]
    public void 단일_프레임을_해독한다()
    {
        var d = new DecoderV1();
        d.Feed(One(7, 100, 1, 2, 3, -4));
        var stats = d.Aggregate();

        Assert.Single(stats);
        var s = stats[7];
        Assert.Equal(1, s.Frames);
        Assert.Equal(4, s.Samples);
        Assert.Equal(2, s.Sum);          // 1 + 2 + 3 - 4
        Assert.Equal(-4, s.Min);
        Assert.Equal(3, s.Max);
        Assert.Equal(0, s.Gaps);
    }

    [Fact]
    public void 앞에_붙은_잡음을_건너뛴다()
    {
        var frame = One(1, 0, 10, 20);
        var noisy = new byte[] { 0x01, 0xAA, 0xFF, 0x55, 0x00 }.Concat(frame).ToArray();

        var d = new DecoderV1();
        d.Feed(noisy);
        Assert.Equal(1, d.Aggregate()[1].Frames);
    }

    [Fact]
    public void 체크섬이_틀린_프레임은_버린다()
    {
        var bad = One(1, 0, 10, 20);
        bad[FrameCodec.HeaderSize] ^= 0xFF;         // 페이로드 훼손

        var d = new DecoderV1();
        d.Feed(bad);
        d.Feed(One(1, 1, 30, 40));                  // 뒤 프레임은 살아야 한다

        var stats = d.Aggregate();
        Assert.Equal(1, stats[1].Frames);
        Assert.Equal(1, d.BadChecksums);
    }

    [Fact]
    public void 시퀀스_결손을_센다()
    {
        var d = new DecoderV1();
        d.Feed(One(3, 10, 1));
        d.Feed(One(3, 11, 1));
        d.Feed(One(3, 15, 1));                      // 12,13,14 결손
        d.Feed(One(3, 16, 1));
        Assert.Equal(1, d.Aggregate()[3].Gaps);     // 끊긴 "횟수"이지 프레임 수가 아니다
    }

    [Theory]
    [InlineData(1)] [InlineData(2)] [InlineData(3)] [InlineData(5)]
    [InlineData(7)] [InlineData(11)] [InlineData(13)] [InlineData(64)]
    public void 어떤_크기로_잘라_넣어도_결과가_같다(int chunk)
    {
        var stream = TestStream.Build(200 * 1024, samplesPerFrame: 16);

        var whole = new DecoderV1();
        whole.Feed(stream);

        var pieces = new DecoderV1();
        for (int off = 0; off < stream.Length; off += chunk)
            pieces.Feed(stream[off..Math.Min(off + chunk, stream.Length)]);

        Assert.Equal(whole.Aggregate(), pieces.Aggregate());
    }
}
```

마지막 `[Theory]`가 이 장 전체를 지탱하는 테스트다. **경계에서 잘린 프레임을 올바르게 이어 붙이는가**를 확인하며, 1바이트씩 넣는 극단까지 밟는다. 프레임 디코더의 버그는 거의 전부 여기에 산다.

> **⚠️ 청크 크기 1은 사치스러운 테스트가 아니라 필수 테스트다**
>
> `chunk = 1`이면 `SYNC`의 두 바이트가 서로 다른 `Feed` 호출에 걸린다. 남은 데이터를 다음 호출까지 보관하지 않고 버리는 구현은 여기서 **조용히 프레임을 통째로 잃는다.** 예외도 나지 않고, 로그도 없고, 그냥 개수가 모자란다.
>
> 실제 소켓에서 1바이트 읽기가 일어나느냐고 묻는다면 — **일어난다.** TCP는 스트림이고, 세그먼트 경계는 언제든 어디로든 떨어진다. 부하가 높거나 네트워크가 나쁠 때 정확히 이 상황이 생기고, 그때는 이미 프로덕션이다.

여기에 하나를 더 붙인다. 뒤에 나올 네 버전을 검증할 **차분 테스트(differential test)** 다.

**1차 구현이 이 장의 명세다.** 뒤의 네 버전은 성능만 다르고 결과는 같아야 한다. 그 사실을 200개의 서로 다른 무작위 스트림으로 매번 확인한다. 씨드를 인자로 받으므로, 어떤 씨드에서 깨지면 그 씨드 하나만 다시 돌려 디버깅할 수 있다.

> **💡 5단계 최적화를 살아남게 하는 것은 벤치마크가 아니라 차분 테스트다**
>
> 최적화 작업에서 사람들은 벤치마크 하네스에 공을 들이고 테스트에는 안 들인다. 순서가 거꾸로다. **벤치마크가 없으면 헛수고를 하는 것이고, 테스트가 없으면 사고를 치는 것이다.** 헛수고는 되돌릴 수 있지만 사고는 아니다.
>
> 이 차분 테스트를 CI에 걸어 두면(67.8절, 80.6절), 5차 벡터화 코드에서 잔여 루프 경계를 하나 잘못 쓴 순간 빌드가 빨갛게 된다. 그게 없으면 그 버그는 "특정 길이의 프레임에서만 최댓값이 틀린" 형태로 6개월 뒤에 발견된다.

### V1 — 평범한 구현

이제 코드다. 목표는 **명확함**이고, 성능은 고려하지 않는다. 신입에게 이 요구사항을 주면 나올 법한 코드다.

```csharp
using System.Buffers.Binary;

public sealed record Frame(ushort Channel, uint Sequence, byte[] Payload, short[] Samples);

public sealed record ChannelStats(int Frames, long Samples, long Sum,
                                  short Min, short Max, int Gaps);

public sealed class DecoderV1
{
    private readonly List<byte>  _pending = new();
    private readonly List<Frame> _frames  = new();

    public int BadChecksums { get; private set; }
    public int ResyncBytes  { get; private set; }

    public void Feed(byte[] chunk)
    {
        _pending.AddRange(chunk);

        while (true)
        {
            int sync = FindSync(_pending);
            if (sync < 0)
            {
                // 마지막 바이트는 SYNC의 앞 절반일 수 있으므로 남긴다
                if (_pending.Count > 1)
                {
                    ResyncBytes += _pending.Count - 1;
                    _pending.RemoveRange(0, _pending.Count - 1);
                }
                return;
            }
            if (sync > 0)
            {
                ResyncBytes += sync;
                _pending.RemoveRange(0, sync);                       // ①
            }

            if (_pending.Count < FrameCodec.HeaderSize + FrameCodec.TrailerSize) return;

            int len = _pending[2] | (_pending[3] << 8);
            if (len < 2 || len > FrameCodec.MaxPayload || (len & 1) != 0)
            {
                _pending.RemoveRange(0, 2);                          // ② 잘못된 길이 → 재동기
                ResyncBytes += 2;
                continue;
            }

            int total = FrameCodec.HeaderSize + len + FrameCodec.TrailerSize;
            if (_pending.Count < total) return;                      // 아직 다 안 왔다

            byte[] frameBytes = _pending.GetRange(0, total).ToArray();  // ③
            if (!VerifyChecksum(frameBytes))
            {
                BadChecksums++;
                _pending.RemoveRange(0, 2);                          // ④ 2바이트만 버리고 재동기
                continue;
            }

            _frames.Add(Parse(frameBytes));                          // ⑤
            _pending.RemoveRange(0, total);                          // ⑥
        }
    }

    private static int FindSync(List<byte> b)
    {
        for (int i = 0; i + 1 < b.Count; i++)
            if (b[i] == 0xAA && b[i + 1] == 0x55) return i;
        return -1;
    }

    private static bool VerifyChecksum(byte[] f)
    {
        int len = BitConverter.ToUInt16(f, 2);
        ushort sum = 0;
        for (int i = 0; i < FrameCodec.HeaderSize + len; i += 2)
            sum = (ushort)(sum + BitConverter.ToUInt16(f, i));
        return sum == BitConverter.ToUInt16(f, FrameCodec.HeaderSize + len);
    }

    private static Frame Parse(byte[] f)
    {
        int len = BitConverter.ToUInt16(f, 2);
        byte[] payload = f.Skip(FrameCodec.HeaderSize).Take(len).ToArray();

        short[] samples = new short[len / 2];
        for (int i = 0; i < samples.Length; i++)
            samples[i] = BitConverter.ToInt16(payload, i * 2);

        return new Frame(BitConverter.ToUInt16(f, 4), BitConverter.ToUInt32(f, 6),
                         payload, samples);
    }

    public Dictionary<int, ChannelStats> Aggregate()
    {
        var result = new Dictionary<int, ChannelStats>();

        foreach (var g in _frames.GroupBy(f => (int)f.Channel))
        {
            var ordered = g.OrderBy(f => f.Sequence).ToList();          // ⑦
            var all     = ordered.SelectMany(f => f.Samples).ToList();  // ⑧

            int gaps = 0;
            for (int i = 1; i < ordered.Count; i++)
                if (ordered[i].Sequence != ordered[i - 1].Sequence + 1) gaps++;

            result[g.Key] = new ChannelStats(
                Frames:  ordered.Count,
                Samples: all.Count,
                Sum:     all.Sum(s => (long)s),                        // ⑨
                Min:     all.Min(),                                    // ⑩
                Max:     all.Max(),                                    // ⑪
                Gaps:    gaps);
        }
        return result;
    }
}
```

이 코드는 **정확하다.** 앞의 테스트를 전부 통과한다. 읽기 쉽고, 각 줄이 요구사항의 한 문장에 대응한다. 실무에서 이런 코드가 배포되고, 대부분의 경우 그대로 잘 돌아간다.

### 무엇이 문제인지 먼저 세어 본다

번호를 붙여 둔 열한 곳을 성격별로 분류한다. 지금은 고치지 않고 **목록만** 만든다.

| # | 위치 | 성격 | 비용 | 관련 절 |
|---|---|---|---|---|
| ① | `RemoveRange(0, sync)` | 알고리즘 | 남은 바이트 전부 복사 | 24.4절 |
| ② | `RemoveRange(0, 2)` | 알고리즘 | 위와 같음 | 24.4절 |
| ③ | `GetRange().ToArray()` | 할당 | `List<byte>` 하나 + `byte[]` 하나 | 63.9절 |
| ④ | `RemoveRange(0, 2)` | 알고리즘 | 위와 같음 | 24.4절 |
| ⑤ | `_frames.Add(...)` | 알고리즘 + 메모리 | 입력 크기에 비례해 무한히 자란다 | 24.4절 |
| ⑥ | `RemoveRange(0, total)` | **알고리즘** | **프레임마다 남은 바이트 전부 복사** | 24.4절 |
| ⑦ | `OrderBy(f => f.Sequence)` | 알고리즘 | 채널마다 O(F log F) 정렬 | 24.3절 |
| ⑧ | `SelectMany(...).ToList()` | 할당 | 전체 샘플의 사본 하나 | 63.9절 |
| ⑨⑩⑪ | `Sum` / `Min` / `Max` | 알고리즘 | 같은 데이터를 **세 번** 순회 | 63.9절 |
| — | `Frame` 레코드 | 할당 | 프레임마다 클래스 + `byte[]` + `short[]` | 63.9절 |
| — | 델리게이트 `f => f.Channel` 등 | 할당 | LINQ 람다와 열거자 | 63.9절 |

⑥번이 이 코드의 심장을 찌른다. `List<T>.RemoveRange(0, k)`는 뒤에 남은 원소를 앞으로 **전부 옮긴다**(24.4절). 64 KiB 청크 안에 240개의 프레임이 있다면 청크 하나를 처리하는 데 평균 32 KiB × 240 = **약 7.7 MB의 memcpy**가 일어나고, 청크 256개면 누적 **약 2 GB의 복사**다. 이것이 512 ms의 대부분이며, **입력의 128배를 복사하고 있다.**

> **⚠️ `List<T>`를 큐처럼 쓰는 것은 가장 흔한 O(n²) 함정이다**
>
> 스트리밍 파서를 짤 때 "받은 걸 리스트에 쌓고 처리한 만큼 앞에서 지운다"는 발상은 지극히 자연스럽다. 그리고 지극히 느리다. `RemoveRange(0, k)`, `RemoveAt(0)`, `list = list.Skip(k).ToList()` 는 전부 같은 함정이며, 마지막 것은 복사에 더해 할당까지 한다.
>
> 더 나쁜 것은 **작은 입력에서는 전혀 티가 나지 않는다**는 점이다. 개발 중 쓰는 1 KB 테스트 파일에서는 즉시 끝나고, 프로덕션의 64 KiB 청크에서 갑자기 30배 느려진다. 그리고 청크를 1 MiB로 키우면 16배가 아니라 **256배** 느려진다 — O(n²)의 정의 그대로다.
>
> `Queue<T>`도 답이 아니다. `Queue<byte>`는 바이트마다 개별 원소이므로 대량 복사·슬라이싱이 안 된다. 답은 **원형 버퍼 또는 커서**이며, 82.3절이 그것이다.

> **📌 ⑤번은 성능 문제이기 전에 설계 문제다**
>
> `_frames`는 처리한 모든 프레임을 영원히 들고 있다. 16 MiB 스트림이면 6만 개, 하루치면 수십억 개다. 실제 수집기에 넣으면 **몇 분 안에 `OutOfMemoryException`이 난다**(63.8절). 82.1절의 "포기하는 것 ②"에 이미 답이 적혀 있었다 — 개별 프레임을 남길 필요가 없다. 성능 최적화에서 얻는 첫 이득은 대개 기법이 아니라 **"이거 왜 하고 있지"** 에서 나온다.

### 1차 결과

**예시 측정 결과** (환경: .NET 8.0.6, x64 RyuJIT AVX2, DefaultJob, 입력 16 MiB / 128 샘플 프레임)

| Method | Mean | Ratio | Gen0 | Gen1 | Gen2 | Allocated | Alloc Ratio |
|---|---:|---:|---:|---:|---:|---:|---:|
| **V1_Naive** | **512.4 ms** | **1.00** | 26,000 | 12,000 | 3,000 | **152.7 MB** | **1.000** |

Gen2가 3,000이라는 것에 주목한다(67.3절: 연산 1,000회당 GC 횟수). `_frames`가 계속 자라면서 그 안의 `Frame`·`byte[]`·`short[]`가 전부 gen2까지 승격되고 있다. **이건 순수한 최적화 대상이 아니라 메모리 누수에 가까운 구조다.**

> **⚠️ 이 표의 수치는 예시다 — Gen2 열은 특히 환경 의존적이다**
>
> gen2 GC 횟수는 힙 크기, GC 모드(워크스테이션/서버), 컨테이너 메모리 제한(72.8절), 배경 GC 설정에 따라 크게 달라진다. 같은 코드가 서버 GC에서는 gen2 횟수가 절반으로 보이고, 대신 각 GC가 더 오래 걸릴 수 있다.
>
> 여기서 읽어야 할 것은 "3,000"이라는 값이 아니라 **"gen2가 0이 아니다"** 라는 사실 하나뿐이다. 상시 동작하는 수집기에서 gen2가 계속 발생한다면 그것만으로 설계를 다시 봐야 한다(64장).

| **적용한 것** | 없음. 이것이 기준선이다. 테스트만 먼저 썼다(80.1절) |
| **결과** | 512.4 ms / 152.7 MB / Ratio 1.00 (예시) |
| **새로 생긴 위험** | `_frames` 무한 성장으로 장시간 구동 시 OOM(63.8절). 청크 크기를 키우면 처리 시간이 제곱으로 증가 |
| **채택 여부** | **요구 처리량이 30 MB/s 미만이고 스트림이 유한하다면 이대로 둔다.** 상시 수집기라면 ⑤번만이라도 고쳐야 한다 |

## 82.3 2차: 알고리즘과 자료구조 교체

### 이 단계에서 얻어야 할 것

성능 작업의 순서에는 이유가 있다. **알고리즘을 먼저 고치는 이유는 그것이 나머지 모든 최적화의 상한을 정하기 때문이다.** O(n²)을 그대로 두고 `Span`을 아무리 붙여도 상수만 줄어들 뿐, 청크 크기를 두 배로 하는 순간 이득이 전부 사라진다.

2차에서 고칠 것은 앞의 목록에서 "알고리즘"으로 분류한 것 전부다. 할당은 **한 개도 건드리지 않는다.** 한 번에 한 종류만 바꾸는 것이 이 장의 규칙이다 — 그래야 어느 변경이 어느 이득을 냈는지 알 수 있다.

| 고칠 것 | 방법 | 근거 절 |
|---|---|---|
| ①②④⑥ `RemoveRange` | 커서(`_start`/`_end`) + `Feed`당 1회 압축 | 24.4절 |
| ⑤ `List<Frame>` 무한 성장 | 스트리밍 집계 — 프레임을 즉시 소비하고 버린다 | 24.15절 |
| ⑦ `OrderBy` | 삭제. 요구사항이 정렬을 요구하지 않는다 | 24.3절 |
| ⑧⑨⑩⑪ 3회 순회 | 프레임당 1회 순회로 합계·최소·최대 동시 계산 | 61.5절 |
| `Dictionary<int, …>` | `ChannelStats[1024]` — 조밀한 정수 키는 배열이 이긴다 | 24.15절 |

### 커서 버퍼 — O(n²)를 O(n)으로

핵심 아이디어는 단순하다. **읽은 만큼 앞을 지우는 대신, 어디까지 읽었는지만 기억한다.**

```text
  Feed 직후                                    프레임 3개를 처리한 뒤
  ┌───────────────────────────────────┐        ┌───────────────────────────────────┐
  │ F1 │ F2 │ F3 │ F4 │ F5 │ (미사용) │        │ .. │ .. │ .. │ F4 │ F5 │ (미사용) │
  └───────────────────────────────────┘        └───────────────────────────────────┘
    ↑                    ↑                                    ↑         ↑
  _start                _end                               _start     _end

  다음 Feed 때 공간이 모자라면 그때 한 번만 앞으로 당긴다 (압축)
  ┌───────────────────────────────────┐
  │ F4 │ F5 │ (새 데이터가 들어갈 자리)  │
  └───────────────────────────────────┘
    ↑         ↑
  _start=0  _end
```

압축은 `Feed`마다 최대 한 번, 그것도 **남은 꼬리 바이트만** 옮긴다. 꼬리는 최대 한 프레임 크기(2 KiB 남짓)이므로, 청크 하나당 복사량이 64 KiB × 240회에서 2 KiB × 1회로 떨어진다.

### V2 — 전체 코드

```csharp
using System.Buffers.Binary;

public struct ChannelStatsV2                 // record class → struct (69.1절)
{
    public int   Frames;
    public long  Samples;
    public long  Sum;
    public short Min;
    public short Max;
    public int   Gaps;
    public uint  LastSeq;
    public bool  Seen;
}

public sealed class DecoderV2
{
    private byte[] _buf = new byte[128 * 1024];
    private int    _start;                    // 유효 구간 [_start, _end)
    private int    _end;

    private readonly ChannelStatsV2[] _stats = new ChannelStatsV2[FrameCodec.MaxChannels];

    public int BadChecksums { get; private set; }
    public int ResyncBytes  { get; private set; }

    public DecoderV2()
    {
        for (int i = 0; i < _stats.Length; i++)
        {
            _stats[i].Min = short.MaxValue;
            _stats[i].Max = short.MinValue;
        }
    }

    public void Feed(byte[] chunk, int count)
    {
        EnsureRoom(count);
        Buffer.BlockCopy(chunk, 0, _buf, _end, count);
        _end += count;
        Drain();
    }

    // 남은 꼬리를 앞으로 당기고, 그래도 모자라면 버퍼를 키운다. Feed당 최대 1회.
    private void EnsureRoom(int count)
    {
        if (_end + count <= _buf.Length) return;

        int remaining = _end - _start;
        if (remaining + count <= _buf.Length)
        {
            Buffer.BlockCopy(_buf, _start, _buf, 0, remaining);
        }
        else
        {
            int size = _buf.Length;
            while (size < remaining + count) size *= 2;
            var bigger = new byte[size];
            Buffer.BlockCopy(_buf, _start, bigger, 0, remaining);
            _buf = bigger;
        }
        _start = 0;
        _end   = remaining;
    }

    private void Drain()
    {
        while (true)
        {
            int sync = FindSync(_buf, _start, _end);
            if (sync < 0)
            {
                // 마지막 1바이트는 SYNC 앞 절반일 수 있으므로 남긴다
                int keep = _end - _start > 0 ? 1 : 0;
                ResyncBytes += _end - _start - keep;
                _start = _end - keep;
                return;
            }
            ResyncBytes += sync - _start;
            _start = sync;

            int avail = _end - _start;
            if (avail < FrameCodec.HeaderSize + FrameCodec.TrailerSize) return;

            int len = _buf[_start + 2] | (_buf[_start + 3] << 8);
            if (len < 2 || len > FrameCodec.MaxPayload || (len & 1) != 0)
            {
                _start += 2; ResyncBytes += 2; continue;
            }

            int total = FrameCodec.HeaderSize + len + FrameCodec.TrailerSize;
            if (avail < total) return;

            if (!VerifyChecksum(_buf, _start, len))
            {
                BadChecksums++; _start += 2; ResyncBytes += 2; continue;
            }

            Consume(_buf, _start, len);       // 프레임을 즉시 소비한다. 저장하지 않는다.
            _start += total;
        }
    }

    private static int FindSync(byte[] b, int from, int to)
    {
        for (int i = from; i + 1 < to; i++)
            if (b[i] == 0xAA && b[i + 1] == 0x55) return i;
        return -1;
    }

    private static bool VerifyChecksum(byte[] b, int off, int len)
    {
        ushort sum = 0;
        int end = off + FrameCodec.HeaderSize + len;
        for (int i = off; i < end; i += 2)
            sum = (ushort)(sum + (ushort)(b[i] | (b[i + 1] << 8)));
        return sum == (ushort)(b[end] | (b[end + 1] << 8));
    }

    // 프레임 하나를 통계에 반영한다. 샘플 배열을 만들지 않고 제자리에서 읽는다.
    private void Consume(byte[] b, int off, int len)
    {
        int ch = b[off + 4] | (b[off + 5] << 8);
        if (ch >= FrameCodec.MaxChannels) return;               // 명세 위반 프레임은 버린다

        uint seq = (uint)(b[off + 6] | (b[off + 7] << 8) | (b[off + 8] << 16) | (b[off + 9] << 24));

        ref ChannelStatsV2 s = ref _stats[ch];                  // 해시 없음, 복사 없음
        if (s.Seen && seq != s.LastSeq + 1) s.Gaps++;
        s.Seen    = true;
        s.LastSeq = seq;
        s.Frames++;

        int p = off + FrameCodec.HeaderSize;
        int n = len / 2;
        long sum = 0;
        short min = short.MaxValue, max = short.MinValue;

        for (int i = 0; i < n; i++)                             // 한 번만 순회한다
        {
            short v = (short)(b[p] | (b[p + 1] << 8));
            p += 2;
            sum += v;
            if (v < min) min = v;
            if (v > max) max = v;
        }

        s.Samples += n;
        s.Sum     += sum;
        if (min < s.Min) s.Min = min;
        if (max > s.Max) s.Max = max;
    }

    public Dictionary<int, ChannelStats> Aggregate()
    {
        var result = new Dictionary<int, ChannelStats>(FrameCodec.MaxChannels);
        for (int ch = 0; ch < _stats.Length; ch++)
        {
            ref ChannelStatsV2 s = ref _stats[ch];
            if (s.Frames == 0) continue;
            result[ch] = new ChannelStats(s.Frames, s.Samples, s.Sum, s.Min, s.Max, s.Gaps);
        }
        return result;
    }
}
```

### 무엇이 왜 빨라졌는가

| 변경 | 이전 | 이후 | 성격 |
|---|---|---|---|
| 버퍼 관리 | 프레임당 O(남은 바이트) 복사 | `Feed`당 O(꼬리) 복사 | **O(n²) → O(n)** |
| 프레임 보관 | 전부 보관 | 즉시 소비 후 폐기 | O(F) 메모리 → O(1) |
| 채널 조회 | `Dictionary<int, …>` 해시 | 배열 인덱싱 | 상수 |
| 통계 갱신 | 사전에서 꺼내 새 레코드 생성 | `ref`로 제자리 갱신 | 상수 + 할당 제거 |
| 정렬 | 채널마다 O(F log F) | 삭제 | 알고리즘 |
| 샘플 순회 | `SelectMany` + `Sum`/`Min`/`Max` = 4회 | 1회 | 상수 4배 + 캐시(61.4절) |

배열 인덱싱과 4회 → 1회 순회는 형식상 "상수 개선"이지만, 실제 효과는 상수 이상이다. **`SelectMany`로 만든 780만 개짜리 `List<short>`를 세 번 훑는 것**은 16 MB를 세 번 DRAM에서 읽어 오는 일이다. 프레임 하나(256 B)를 캐시에 올린 김에 한 번에 처리하면 그 트래픽이 통째로 사라진다(61.4절, 70.5절).

`ref ChannelStatsV2 s = ref _stats[ch];`도 그냥 문법 설탕이 아니다. `ChannelStatsV2`는 40바이트 구조체이므로, `ref` 없이 `var s = _stats[ch]`로 받으면 **복사본을 고치고 원본은 그대로 남는다** — 조용히 틀린 결과다.

> **⚠️ 값 타입을 컬렉션에서 꺼내 고치는 코드는 `ref`가 없으면 조용히 틀린다**
>
> ```csharp
> var s = _stats[ch];        // 복사
> s.Frames++;                // 복사본을 고친다
> // _stats[ch]는 변하지 않았다 — 예외도 경고도 없다
> ```
>
> `T[]`는 `ref` 반환 인덱서를 제공하므로 `ref var s = ref _stats[ch]`가 가능하다. 그러나 **`List<T>`는 그렇지 않다.** `list[i].Field = x`는 컴파일 오류(CS1612)로 잡히지만, 위처럼 지역 변수를 거치면 컴파일은 되고 결과만 틀린다.
>
> `List<T>`에서 같은 일을 해야 한다면 `CollectionsMarshal.AsSpan(list)`로 스팬을 얻어 인덱싱하라 ※.NET 5. `Dictionary<TKey,TValue>`라면 `CollectionsMarshal.GetValueRefOrAddDefault` ※.NET 6다(69.9절).

### 정렬을 지운 것이 정말 안전한가

⑦번 `OrderBy(f => f.Sequence)`를 지웠다. 이건 순수한 성능 변경이 아니라 **의미 변경**이므로 근거가 필요하다.

- 요구사항: "시퀀스 번호가 끊긴 횟수를 센다."
- 프로토콜: 채널별 프레임은 하나의 TCP 연결로 순서대로 온다.
- 따라서 도착 순서 = 시퀀스 순서이고, 정렬은 항등 변환이다.

**그리고 정렬은 애초에 요구사항을 잘못 구현하고 있었다.** V1은 채널의 모든 프레임을 모아 정렬한 뒤 결손을 셌으므로, "1, 2, 5, 3, 4"가 오면 정렬 후 "1,2,3,4,5"가 되어 결손 0을 보고한다. V2는 도착 순서대로 보므로 2→5에서 한 번, 5→3에서 또 한 번을 센다.

어느 쪽이 맞는가? **요구사항에 따라 다르다.** 여기서는 "스트림에 구멍이 생겼는지"를 알고 싶은 것이므로 V2가 맞다. 그러나 이 판단은 코드가 아니라 사람이 내린 것이고, 문서로 남겨야 한다.

> **⚠️ "불필요한 정렬 제거"는 성능 변경이 아니라 명세 변경일 수 있다**
>
> 정렬을 지워서 빨라지는 코드는 흔하다. 그리고 지운 정렬이 정말 불필요했는지는 **성능 측정으로는 절대 알 수 없다.** 차분 테스트도 못 잡는다 — 테스트 데이터가 이미 정렬되어 있으면 두 버전이 같은 답을 낸다.
>
> V1과 V2가 갈라지는 입력(순서가 뒤집힌 시퀀스)을 **일부러 만들어** 테스트에 넣고, 어느 쪽이 맞는지를 명시적으로 못 박아라.
>
> ```csharp
> [Fact]
> public void 도착_순서가_뒤집히면_결손으로_센다()
> {
>     var d = new DecoderV2();
>     Push(d, One(3, 1, 0)); Push(d, One(3, 2, 0));
>     Push(d, One(3, 5, 0)); Push(d, One(3, 3, 0));
>     // 2→5 한 번, 5→3 한 번. 정렬했다면 0이었을 것이다.
>     Assert.Equal(2, d.Aggregate()[3].Gaps);
> }
> ```
>
> 이 테스트가 있어야 6개월 뒤에 누군가 "결손 수가 이상한데요"라고 물었을 때 **의도된 동작임을 5초 만에 증명**할 수 있다.

> **📌 `Dictionary<int, T>`를 `T[]`로 바꾸는 판단 기준**
>
> 24.15절의 표를 이 문제에 적용하면 이렇다. 키가 **조밀한 정수**이고, **범위 상한이 작고 알려져 있고**, 대부분의 슬롯이 실제로 쓰인다면 배열이 사전을 이긴다. 여기서는 채널 0~1023이 명세로 고정되어 있으므로 세 조건이 모두 참이다.
>
> 반대 상황이면 이 교체는 손해다. 채널 번호가 `uint` 전 범위라면 4 GB짜리 배열이 필요하고, 실제로 쓰이는 채널이 다섯 개뿐이라면 배열은 캐시를 낭비한다(61.4절). **`FrozenDictionary`(24.11절)가 답인 경우도 있다** — 키 집합이 시작 시점에 고정되고 이후 조회만 한다면.

### 2차 결과

**예시 측정 결과** (환경: .NET 8.0.6, x64 RyuJIT AVX2, DefaultJob, 입력 16 MiB / 128 샘플 프레임)

| Method | Mean | Ratio | Gen0 | Gen1 | Gen2 | Allocated | Alloc Ratio |
|---|---:|---:|---:|---:|---:|---:|---:|
| V1_Naive | 512.4 ms | 1.00 | 26,000 | 12,000 | 3,000 | 152.7 MB | 1.000 |
| **V2_Algorithm** | **68.9 ms** | **0.134** | 31.25 | 0 | **1.30** | **244 KB** | **0.002** |

처리량 약 31 MB/s → **약 232 MB/s**. 1 Gbps NIC를 한 코어로 따라잡았다.

여기서 예상하지 못한 일이 두 가지 벌어졌다.

첫째, **할당이 152.7 MB에서 244 KB로 떨어졌다.** 3차에서 하려던 일의 대부분이 2차에서 끝나 버린 것이다. 이유는 명확하다 — `Frame` 객체와 `short[]`·`byte[]` 사본은 "프레임을 저장한다"는 **알고리즘 결정**에서 파생된 것이었고, 그 결정을 지우자 파생물도 같이 사라졌다.

둘째, **`Gen2`가 0이 아니다.** 244 KB밖에 할당하지 않는데 연산 1,000회당 gen2 GC가 1.3회 일어난다. 이건 계산이 맞지 않는다. 3차에서 이 모순부터 푼다.

> **⚠️ 이 표의 수치는 예시다 — 특히 이 단계의 배수는 데이터에 극도로 민감하다**
>
> V1의 O(n²)는 **청크 크기와 프레임 밀도**에 좌우된다. 청크가 4 KiB였다면 V1이 훨씬 덜 느렸을 것이고, 1 MiB였다면 훨씬 더 느렸을 것이다. 즉 "7.4배"라는 값은 이 벤치마크의 청크 크기 64 KiB가 만든 숫자이지 코드의 속성이 아니다.
>
> 반드시 **자신의 청크 크기와 프레임 크기 분포로** 재라. 그리고 청크 크기를 두세 가지로 `[Params]` 걸어서 곡선의 기울기를 보라 — O(n²)인지 O(n)인지는 배수 하나가 아니라 기울기가 말해준다.

> **💡 "할당 최적화를 했더니 빨라졌다"의 절반은 사실 알고리즘 개선이다**
>
> 할당을 줄이면 빨라지는 것은 맞다. 그러나 큰 이득이 났다면, 대개 할당 자체가 아니라 **할당을 유발하던 구조**가 함께 사라진 것이다. 여기서는 "모든 프레임을 리스트에 보관"이라는 구조가 사라지면서 객체 6만 개, 배열 12만 개, 그리고 그것들을 gen2까지 끌고 가던 GC 작업이 통째로 없어졌다(64장).
>
> 그래서 순서가 중요하다. **알고리즘을 먼저 고치면 할당 최적화가 할 일이 줄어든다.** 반대로 하면, 결국 지울 구조에 `ArrayPool`을 정성껏 붙이는 헛수고를 하게 된다.

| **새로 생긴 위험** | ① 정렬 제거로 결손 계수 의미가 바뀜(문서화 필요) ② 커서 관리 오류 시 프레임 유실 또는 무한 루프 ③ `ref` 없이 구조체를 꺼내면 조용히 틀림 ④ 채널 번호 상한이 명세에 하드코딩됨 |
| **채택 여부** | **거의 항상 채택한다.** 코드 줄 수는 늘었지만 각 줄이 여전히 평범하고, 팀의 누구나 읽을 수 있다. 여기까지가 "최적화"가 아니라 "제대로 짜기"다 |

## 82.4 3차: 할당 제거

### 남은 244 KB의 정체를 분해한다

`MemoryDiagnoser`의 `Allocated`는 총량만 알려준다. 어디서 나오는지는 알려주지 않는다. 분해하는 방법은 두 가지다.

**방법 1 — 코드를 읽고 후보 목록을 만든다.** 63.9절의 숨은 할당 카탈로그를 손에 들고 V2를 한 줄씩 훑는다.

| # | 위치 | 종류 | 1회당 크기 | 발생 빈도 |
|---|---|---|---|---|
| A | `new byte[128 * 1024]` (생성자) | `byte[]` | 131,072 B | 디코더당 1회 |
| B | `new ChannelStatsV2[1024]` (생성자) | `ChannelStatsV2[]` | 40,984 B | 디코더당 1회 |
| C | `Aggregate()`의 `Dictionary` | 버킷 + 엔트리 배열 | 약 28 KB | 호출당 1회 |
| D | `Aggregate()`의 `new ChannelStats(...)` | `record` 클래스 × 1,024 | 49,152 B | 호출당 1회 |
| E | `Pump`의 `(b, n) => d.Feed(b, n)` | 클로저 + 델리게이트 | 약 100 B | 호출당 1회 |
| F | `EnsureRoom`의 버퍼 성장 | `byte[]` | 배가 | 거의 없음 |

**방법 2 — 입력 크기를 흔들어 O(1)과 O(n)을 가른다.** 이것이 훨씬 강력하다.

```csharp
[MemoryDiagnoser]
public class AllocationShapeBench
{
    [Params(1, 4, 16, 64)]                       // MiB
    public int InputMiB { get; set; }

    private byte[] _stream = null!;
    private byte[] _chunk  = new byte[64 * 1024];

    [GlobalSetup]
    public void Setup() => _stream = TestStream.Build(InputMiB * 1024 * 1024, 128);

    [Benchmark]
    public object V2()
    {
        var d = new DecoderV2();
        for (int off = 0; off < _stream.Length; off += _chunk.Length)
        {
            int n = Math.Min(_chunk.Length, _stream.Length - off);
            Buffer.BlockCopy(_stream, off, _chunk, 0, n);
            d.Feed(_chunk, n);
        }
        return d.Aggregate();
    }
}
```

**예시 측정 결과** (환경: .NET 8.0.6, x64 RyuJIT AVX2, DefaultJob)

| Method | InputMiB | Mean | Allocated | 입력 MiB당 할당 |
|---|---:|---:|---:|---:|
| V2 | 1 | 4.3 ms | 244 KB | 244 KB |
| V2 | 4 | 17.2 ms | 244 KB | 61 KB |
| V2 | 16 | 68.9 ms | 244 KB | 15 KB |
| V2 | 64 | 275.4 ms | 244 KB | 4 KB |

**`Allocated`가 입력 크기와 무관하게 일정하다.** 이것이 결정적인 정보다 — 남은 244 KB는 전부 **고정 비용**이고, **핫 패스에는 할당이 하나도 없다.**

> **⚠️ 이 표의 수치는 예시다 — 그러나 여기서 볼 것은 값이 아니라 "일정하다"는 사실이다**
>
> 244 KB라는 절대값은 버퍼 크기와 채널 수가 정한 것이므로 설정만 바꿔도 달라진다. 네 행에서 값이 **변하지 않는다**는 관계만이 결론을 지지한다. 자신의 코드에서도 값을 인용하지 말고 기울기를 확인하라.

> **💡 `Allocated` 총량이 아니라 `Allocated`의 기울기를 보라**
>
> "할당 244 KB"는 그 자체로는 좋지도 나쁘지도 않다. 중요한 것은 **입력이 두 배가 될 때 할당도 두 배가 되는가**다.
>
> - 기울기가 0이면 → 시작 비용이다. 프로세스 수명 동안 한 번 내면 된다. **최적화 가치가 거의 없다.**
> - 기울기가 양수이면 → 핫 패스 할당이다. 트래픽이 늘면 GC 압력이 선형으로 는다. **여기가 진짜 표적이다.**
>
> `[Params]`로 입력 크기를 두세 단계 흔드는 데 드는 비용은 벤치마크 실행 시간뿐이고, 얻는 정보는 "어디를 고쳐야 하는가"라는 답 그 자체다. 총량 하나만 보고 최적화 대상을 고르는 것은 눈을 감고 고르는 것과 같다.

그렇다면 V2의 `Gen2 = 1.30`은 어디서 왔는가.

### 발견 — 128 KiB 버퍼는 LOH로 간다

```csharp
private byte[] _buf = new byte[128 * 1024];      // 131,072 바이트
```

**85,000 바이트 이상의 배열은 대형 객체 힙(LOH)에 할당된다**(63.4절). LOH 할당은 gen2 예산에 계상되고, LOH는 기본적으로 압축되지 않으며, LOH를 회수하려면 **gen2 GC** — 즉 전체 힙을 훑는 가장 비싼 GC — 가 필요하다(64장).

디코더 인스턴스를 계속 만드는 코드라면 이 한 줄이 gen2 GC를 주기적으로 유발한다. 벤치마크가 연산마다 `new DecoderV2()`를 하고 있으므로 정확히 그 상황이고, `Gen2 = 1.30`이 그 증거다.

> **⚠️ LOH 임계값은 85,000 바이트이지 85 KiB(87,040)가 아니다**
>
> 정확한 경계는 **85,000 바이트**다. `byte[85000]`은 객체 헤더 때문에 이미 넘고, 실무에서 안전한 상한은 대략 `byte[84_000]` 근처다. 원소 크기가 큰 배열은 훨씬 빨리 넘는다 — `long[10625]`가 벌써 85,000 바이트다.
>
> `double[]`에는 **예외**가 있다. .NET에서 `double[]`은 정렬 때문에 1,000개 이상이면 LOH로 간다(x86 한정 동작이었으나 구현 세부에 의존하므로 크기를 직접 계산하는 편이 안전하다).
>
> 그리고 이 임계값은 `System.GC.LOHThreshold` 구성으로 **올릴 수는** 있지만(62.3절 — 기본값 아래로 내리지는 못한다), **버퍼 크기를 임계값에 맞춰 코드를 고치는 편이 거의 언제나 낫다.** 구성은 프로세스 전체에 영향을 주고, 배포 환경마다 잊혀진다.

### V3 — 고정 비용까지 걷어내기

세 가지를 바꾼다.

1. **버퍼를 LOH 아래로.** 필요한 최소 크기는 "최대 프레임 하나 + 한 청크"다. 청크 64 KiB + 프레임 2,060 B = 약 68 KiB로 충분하다. 여유를 둬 `72 * 1024`(73,728 B)로 잡으면 85,000 아래다.
2. **출력 API에서 할당을 걷어낸다.** `Aggregate()`가 사전과 레코드 1,024개를 만드는 것은 **호출자가 그 형태를 요구했기 때문**이다. 형태를 바꾼다.
3. **디코더를 재사용 가능하게 만든다.** `Reset()`을 추가해서, 상시 구동 수집기가 인스턴스를 한 번만 만들도록 한다.

```csharp
public readonly record struct ChannelStats(                 // class → struct (69.1절)
    int Channel, int Frames, long Samples, long Sum, short Min, short Max, int Gaps);

public sealed class DecoderV3
{
    // 85,000 바이트 미만 → LOH를 피한다 (63.4절)
    private const int BufferSize = 72 * 1024;

    private readonly byte[] _buf = new byte[BufferSize];
    private int _start, _end;

    private readonly ChannelStatsV2[] _stats = new ChannelStatsV2[FrameCodec.MaxChannels];

    public int BadChecksums { get; private set; }
    public int ResyncBytes  { get; private set; }

    public DecoderV3() => Reset();

    /// <summary>인스턴스를 재사용하기 위해 상태만 초기화한다. 배열은 그대로 쓴다.</summary>
    public void Reset()
    {
        Array.Clear(_stats);
        for (int i = 0; i < _stats.Length; i++)
        {
            _stats[i].Min = short.MaxValue;
            _stats[i].Max = short.MinValue;
        }
        _start = _end = 0;
        BadChecksums = ResyncBytes = 0;
    }

    public void Feed(byte[] chunk, int count)
    {
        if (count > BufferSize - (FrameCodec.MaxPayload + 32))
            throw new ArgumentOutOfRangeException(nameof(count), "청크가 버퍼 설계 한계를 넘는다");

        EnsureRoom(count);
        Buffer.BlockCopy(chunk, 0, _buf, _end, count);
        _end += count;
        Drain();
    }

    // 버퍼를 키우지 않는다. 꼬리를 앞으로 당기기만 한다.
    private void EnsureRoom(int count)
    {
        if (_end + count <= _buf.Length) return;

        int remaining = _end - _start;
        Buffer.BlockCopy(_buf, _start, _buf, 0, remaining);
        _start = 0;
        _end   = remaining;
    }

    private void Drain()
    {
        while (true)
        {
            int sync = FindSync(_buf, _start, _end);
            if (sync < 0)
            {
                int keep = _end - _start > 0 ? 1 : 0;
                ResyncBytes += _end - _start - keep;
                _start = _end - keep;
                return;
            }
            ResyncBytes += sync - _start;
            _start = sync;

            int avail = _end - _start;
            if (avail < FrameCodec.HeaderSize + FrameCodec.TrailerSize) return;

            int len = _buf[_start + 2] | (_buf[_start + 3] << 8);
            if (len < 2 || len > FrameCodec.MaxPayload || (len & 1) != 0)
            {
                _start += 2; ResyncBytes += 2; continue;
            }

            int total = FrameCodec.HeaderSize + len + FrameCodec.TrailerSize;
            if (avail < total) return;

            if (!VerifyChecksum(_buf, _start, len))
            {
                BadChecksums++; _start += 2; ResyncBytes += 2; continue;
            }

            Consume(_buf, _start, len);
            _start += total;
        }
    }

    private static int FindSync(byte[] b, int from, int to)
    {
        for (int i = from; i + 1 < to; i++)
            if (b[i] == 0xAA && b[i + 1] == 0x55) return i;
        return -1;
    }

    private static bool VerifyChecksum(byte[] b, int off, int len)
    {
        ushort sum = 0;
        int end = off + FrameCodec.HeaderSize + len;
        for (int i = off; i < end; i += 2)
            sum = (ushort)(sum + (ushort)(b[i] | (b[i + 1] << 8)));
        return sum == (ushort)(b[end] | (b[end + 1] << 8));
    }

    private void Consume(byte[] b, int off, int len)
    {
        int ch = b[off + 4] | (b[off + 5] << 8);
        if (ch >= FrameCodec.MaxChannels) return;

        uint seq = (uint)(b[off + 6] | (b[off + 7] << 8) | (b[off + 8] << 16) | (b[off + 9] << 24));

        ref ChannelStatsV2 s = ref _stats[ch];
        if (s.Seen && seq != s.LastSeq + 1) s.Gaps++;
        s.Seen = true; s.LastSeq = seq; s.Frames++;

        int p = off + FrameCodec.HeaderSize;
        int n = len / 2;
        long sum = 0;
        short min = short.MaxValue, max = short.MinValue;

        for (int i = 0; i < n; i++)
        {
            short v = (short)(b[p] | (b[p + 1] << 8));
            p += 2;
            sum += v;
            if (v < min) min = v;
            if (v > max) max = v;
        }

        s.Samples += n;
        s.Sum     += sum;
        if (min < s.Min) s.Min = min;
        if (max > s.Max) s.Max = max;
    }

    // ── 출력: 사전도 레코드도 만들지 않는다 ──────────────────────────────

    /// <summary>활성 채널의 통계를 호출자 버퍼에 채우고 개수를 반환한다.</summary>
    public int CopyStatsTo(Span<ChannelStats> dest)
    {
        int k = 0;
        for (int ch = 0; ch < _stats.Length; ch++)
        {
            ref ChannelStatsV2 s = ref _stats[ch];
            if (s.Frames == 0) continue;
            if (k >= dest.Length) throw new ArgumentException("버퍼가 작다", nameof(dest));
            dest[k++] = new ChannelStats(ch, s.Frames, s.Samples, s.Sum, s.Min, s.Max, s.Gaps);
        }
        return k;
    }

    /// <summary>단일 채널 조회. 대시보드가 특정 채널만 볼 때 쓴다.</summary>
    public bool TryGetStats(int channel, out ChannelStats stats)
    {
        ref ChannelStatsV2 s = ref _stats[channel];
        if (s.Frames == 0) { stats = default; return false; }
        stats = new ChannelStats(channel, s.Frames, s.Samples, s.Sum, s.Min, s.Max, s.Gaps);
        return true;
    }
}
```

`ChannelStats`가 `readonly record struct`가 되면서 `CopyStatsTo`는 **호출자의 배열에 값을 직접 쓴다.** 1,024개의 힙 객체가 사라졌고, `Equals`·`GetHashCode`·`ToString`은 레코드 문법이 그대로 생성해 주므로 차분 테스트의 `Assert.Equal`도 그대로 동작한다.

> **⚠️ `readonly record struct`의 `Equals`는 필드별 비교이지 참조 비교가 아니다 — 그래서 느릴 수 있다**
>
> `record struct`의 컴파일러 생성 `Equals`는 필드를 하나씩 비교한다. 이 타입처럼 필드가 일곱 개면 비교 한 번에 일곱 번의 분기다. 테스트에서는 아무 문제가 없지만, **이 타입을 `HashSet`이나 `Dictionary`의 키로 쓰면** 그 비용이 조회마다 발생한다.
>
> 그리고 `record struct`는 기본적으로 `IEquatable<T>`를 구현하므로 박싱은 없다. 반면 **`record struct`가 아닌 평범한 `struct`** 는 `IEquatable<T>`를 구현하지 않으면 `ValueType.Equals`로 떨어지고, 그 구현은 리플렉션 경로를 탈 수 있어 훨씬 느리며 박싱도 한다(63.9절). 값 타입을 만들면 `IEquatable<T>`를 구현하거나 `record struct`를 쓰는 것이 기본이다.

### 벤치마크도 고쳐야 한다

디코더를 재사용 가능하게 만들었으므로, 벤치마크도 **상시 구동 상태**를 재야 한다. `[GlobalSetup]`에서 디코더를 한 번 만들고, 각 연산은 `Reset()`부터 시작한다(67.3절의 `[IterationSetup]`과 `[GlobalSetup]` 구분을 그대로 적용한다).

```csharp
private DecoderV3 _v3 = null!;
private ChannelStats[] _out = null!;

[GlobalSetup]
public void SetupV3()
{
    _v3  = new DecoderV3();
    _out = new ChannelStats[FrameCodec.MaxChannels];
}

[Benchmark]
public int V3_NoAlloc()
{
    _v3.Reset();
    for (int off = 0; off < _stream.Length; off += ChunkSize)
    {
        int n = Math.Min(ChunkSize, _stream.Length - off);
        Buffer.BlockCopy(_stream, off, _chunk, 0, n);
        _v3.Feed(_chunk, n);
    }
    return _v3.CopyStatsTo(_out);          // 반환값을 돌려준다 (67.4절)
}
```

> **⚠️ 인스턴스를 재사용하는 벤치마크는 "첫 실행 비용"을 감춘다**
>
> V3의 `Allocated`가 0에 가까운 것은 **버퍼와 통계 배열을 `[GlobalSetup]`에서 미리 만들었기 때문**이다. 실제 서비스에서 디코더를 연결마다 새로 만든다면 그 비용은 여전히 발생한다.
>
> 이건 벤치마크의 거짓말이 아니라 **측정 대상의 선택**이다. 상시 구동 수집기를 모델링한다면 재사용이 옳고, 짧은 연결이 계속 생겼다 사라지는 서비스를 모델링한다면 `[IterationSetup]`에서 새로 만드는 쪽이 옳다. **둘 다 재고 어느 쪽이 자기 서비스인지 결정하라.** 하나만 재고 다른 쪽을 결론짓는 것이 사고의 원인이다.

### 할당 0을 테스트로 고정한다

69.9절에서 쓴 것과 같은 어서션을 이 디코더에도 건다.

```csharp
[Fact]
public void V3는_정상_경로에서_아무것도_할당하지_않는다()
{
    var d      = new DecoderV3();
    var chunk  = new byte[64 * 1024];
    var stats  = new ChannelStats[FrameCodec.MaxChannels];
    var stream = TestStream.Build(2 * 1024 * 1024, 128);

    Pump(d, stream, chunk);          // 워밍업 — JIT과 첫 접근 비용을 여기서 낸다
    d.Reset();

    long before = GC.GetAllocatedBytesForCurrentThread();
    Pump(d, stream, chunk);
    d.CopyStatsTo(stats);
    long after = GC.GetAllocatedBytesForCurrentThread();

    Assert.Equal(0, after - before);
}
```

`GC.GetAllocatedBytesForCurrentThread()`의 의미와 Release 구성 제약은 69.9절에서 다룬 그대로다. 이 테스트를 CI의 Release 잡에 넣으면(67.8절, 80.6절), 누군가 `Consume` 안에 `string.Format`을 한 줄 넣는 순간 빌드가 깨진다.

**예시 측정 결과** (환경: .NET 8.0.6, x64 RyuJIT AVX2, DefaultJob, 입력 16 MiB / 128 샘플 프레임, 디코더 재사용)

> **💡 할당을 0으로 만들어도 처리량은 거의 안 늘 수 있다 — 그리고 그건 실패가 아니다**
>
> 2차 이후 이미 핫 패스에는 할당이 없었다. 3차가 지운 것은 **연산당 244 KB의 고정 비용**뿐이고, 그것은 62 ms 중 7 ms 남짓이었다. 처리량 관점에서 3차는 거의 성과가 없다.
>
> 그렇다면 3차는 헛수고인가? 아니다. **다른 축에서 성과를 냈다.**
>
> - **`Gen2`가 0이 되었다.** LOH 할당이 사라졌고, 이제 이 디코더는 상시 구동해도 전체 힙 GC를 유발하지 않는다. 이것은 처리량이 아니라 **꼬리 지연 시간**과 **안정성**의 문제다(67.1절).
> - **할당 0이 테스트로 고정되었다.** 회귀가 원천 차단된다.
> - **인스턴스 재사용이 가능해졌다.** 수집기가 연결 수만큼 LOH 버퍼를 만들지 않는다.
>
> 82.1절에서 "부 목표: 할당 0에 가까울 것"을 명시해 뒀기 때문에 이 단계를 성공으로 판정할 수 있다. **목표를 미리 적어 두지 않았다면 이 결과를 보고 "10%밖에 안 빨라졌으니 되돌리자"고 했을 것이다.**

> **⚠️ 이 표의 수치는 예시다 — `Allocated = 0 B`는 특히 조건부다**
>
> `0 B`는 "이 벤치마크가 이 경로를 도는 동안"의 값이다. 예외가 던져지면 예외 객체가 할당되고, `ArgumentOutOfRangeException` 경로를 밟으면 메시지 문자열이 만들어진다. 로깅을 한 줄이라도 넣으면 사라진다.
>
> "할당 0"은 코드의 속성이 아니라 **특정 실행 경로의 속성**이다. 그 경로가 실제 트래픽의 어느 비율인지 모른 채 0을 자랑하는 것은 의미가 없다.

### 3차 기록

| 칸 | 내용 |
|---|---|
| **적용한 것** | 67.5절(`MemoryDiagnoser`), 63.4절(LOH 임계값), 63.9절(숨은 할당 카탈로그), 69.1절(`record class` → `readonly record struct`), 78장(출력 API를 호출자 버퍼로), 80.6절(할당 어서션 테스트) |

## 82.5 4차: `Span`과 풀링 적용

### 3차가 남긴 진짜 병목

3차의 `Consume`은 샘플 하나를 이렇게 읽는다.

```csharp
short v = (short)(b[p] | (b[p + 1] << 8));
p += 2;
```

여기서 CPU가 하는 일을 세어 보자.

| 연산 | 횟수 | 비고 |
|---|---|---|
| 배열 요소 로드 | 2 | `b[p]`, `b[p+1]` |
| 경계 검사 | 2 | `p`가 상수가 아니고 루프 상한과 무관하므로 JIT이 못 지운다(55.6절) |
| 시프트 | 1 | `<< 8` |
| OR | 1 | |
| `short` 부호 확장 | 1 | |

샘플 하나에 최소 일곱 개의 명령이다. 그런데 **x64는 메모리에서 16비트를 한 번에 읽는 명령(`movzx`/`movsx`)을 가지고 있다.** 우리가 해야 할 일은 명령 하나다. 나머지 여섯 개는 "`byte[]`를 바이트 단위로 인덱싱했다"는 표현 방식이 만든 비용이다.

체크섬 루프도 정확히 같은 낭비를 한다.

`Span<T>`가 푸는 것이 바로 이 문제다. **`MemoryMarshal.Cast`는 같은 메모리를 다른 원소 타입으로 재해석한다** — 복사 없이, 할당 없이(68.4절).

### 무엇을 어떻게 바꾸는가

| 대상 | 기법 | 근거 절 |
|---|---|---|
| 샘플 읽기 | `MemoryMarshal.Cast<byte, short>` | 68.4절 |
| 체크섬 워드 읽기 | `MemoryMarshal.Cast<byte, ushort>` | 68.4절 |
| 헤더 필드 읽기 | `BinaryPrimitives.Read*LittleEndian` | 68.5절 |
| 재동기 스캔 | `span.IndexOf(ReadOnlySpan<byte>)` | 68.4절, 71.5절 |
| 루프 경계 검사 | `for (i = 0; i < span.Length; i++)` 패턴 | 55.6절 |
| 작업 버퍼 | `ArrayPool<byte>.Shared` | 69.3절 |
| 입력 인자 | `byte[] chunk, int count` → `ReadOnlySpan<byte>` | 68.13절 |

### V4 — 전체 코드

```csharp
using System.Buffers;
using System.Buffers.Binary;
using System.Runtime.InteropServices;

public sealed class DecoderV4 : IDisposable
{
    private const int BufferSize = 72 * 1024;          // 청크 64 KiB + 최대 프레임 여유

    private byte[]? _buf;                               // ArrayPool에서 빌린다
    private int _start, _end;

    private readonly ChannelStatsV2[] _stats = new ChannelStatsV2[FrameCodec.MaxChannels];

    public int BadChecksums { get; private set; }
    public int ResyncBytes  { get; private set; }

    // ※C# 12 — 정적 읽기 전용 데이터를 가리킨다. 할당도 stackalloc도 아니다.
    private static ReadOnlySpan<byte> SyncPattern => [0xAA, 0x55];

    public DecoderV4()
    {
        _buf = ArrayPool<byte>.Shared.Rent(BufferSize);
        Reset();
    }

    public void Dispose()
    {
        byte[]? b = _buf;
        _buf = null;
        if (b is not null) ArrayPool<byte>.Shared.Return(b);   // clearArray 불필요 — 참조 없음
    }

    public void Reset()
    {
        Array.Clear(_stats);
        for (int i = 0; i < _stats.Length; i++)
        {
            _stats[i].Min = short.MaxValue;
            _stats[i].Max = short.MinValue;
        }
        _start = _end = 0;
        BadChecksums = ResyncBytes = 0;
    }

    public void Feed(ReadOnlySpan<byte> chunk)
    {
        byte[] buf = _buf ?? throw new ObjectDisposedException(nameof(DecoderV4));
        if (chunk.Length > BufferSize - (FrameCodec.MaxPayload + 32))
            throw new ArgumentOutOfRangeException(nameof(chunk), "청크가 버퍼 설계 한계를 넘는다");

        if (_end + chunk.Length > buf.Length)
        {
            buf.AsSpan(_start, _end - _start).CopyTo(buf);      // 꼬리를 앞으로
            _end  -= _start;
            _start = 0;
        }
        chunk.CopyTo(buf.AsSpan(_end));
        _end += chunk.Length;

        Drain(buf);
    }

    private void Drain(byte[] buf)
    {
        while (true)
        {
            ReadOnlySpan<byte> window = buf.AsSpan(_start, _end - _start);

            int sync = window.IndexOf(SyncPattern);             // BCL의 벡터화 검색 (71.5절)
            if (sync < 0)
            {
                int keep = window.Length > 0 ? 1 : 0;           // SYNC 앞 절반 보존
                ResyncBytes += window.Length - keep;
                _start = _end - keep;
                return;
            }
            ResyncBytes += sync;
            _start += sync;
            window  = window[sync..];

            if (window.Length < FrameCodec.HeaderSize + FrameCodec.TrailerSize) return;

            int len = BinaryPrimitives.ReadUInt16LittleEndian(window[2..]);
            if (len < 2 || len > FrameCodec.MaxPayload || (len & 1) != 0)
            {
                _start += 2; ResyncBytes += 2; continue;
            }

            int total = FrameCodec.HeaderSize + len + FrameCodec.TrailerSize;
            if (window.Length < total) return;

            ReadOnlySpan<byte> frame = window[..total];
            if (!VerifyChecksum(frame, len))
            {
                BadChecksums++; _start += 2; ResyncBytes += 2; continue;
            }

            Consume(frame, len);
            _start += total;
        }
    }

    private static bool VerifyChecksum(ReadOnlySpan<byte> frame, int len)
    {
        int covered = FrameCodec.HeaderSize + len;                 // 항상 짝수
        ushort expected = BinaryPrimitives.ReadUInt16LittleEndian(frame[covered..]);

        if (BitConverter.IsLittleEndian)
        {
            // 같은 바이트를 u16 배열로 재해석한다. 복사 없음.
            ReadOnlySpan<ushort> words = MemoryMarshal.Cast<byte, ushort>(frame[..covered]);
            ushort sum = 0;
            for (int i = 0; i < words.Length; i++)                 // 경계 검사 제거됨 (55.6절)
                sum = (ushort)(sum + words[i]);
            return sum == expected;
        }
        else
        {
            ushort sum = 0;
            for (int i = 0; i < covered; i += 2)
                sum = (ushort)(sum + BinaryPrimitives.ReadUInt16LittleEndian(frame[i..]));
            return sum == expected;
        }
    }

    private void Consume(ReadOnlySpan<byte> frame, int len)
    {
        int ch = BinaryPrimitives.ReadUInt16LittleEndian(frame[4..]);
        if (ch >= FrameCodec.MaxChannels) return;

        uint seq = BinaryPrimitives.ReadUInt32LittleEndian(frame[6..]);

        ref ChannelStatsV2 s = ref _stats[ch];
        if (s.Seen && seq != s.LastSeq + 1) s.Gaps++;
        s.Seen = true; s.LastSeq = seq; s.Frames++;

        ReadOnlySpan<byte> payload = frame.Slice(FrameCodec.HeaderSize, len);
        ReadOnlySpan<short> samples = BitConverter.IsLittleEndian
            ? MemoryMarshal.Cast<byte, short>(payload)
            : default;

        long sum = 0;
        short min = short.MaxValue, max = short.MinValue;

        if (!samples.IsEmpty)
        {
            for (int i = 0; i < samples.Length; i++)               // 경계 검사 제거됨
            {
                short v = samples[i];
                sum += v;
                if (v < min) min = v;
                if (v > max) max = v;
            }
            s.Samples += samples.Length;
        }
        else                                                        // 빅엔디언 폴백
        {
            int n = len / 2;
            for (int i = 0; i < n; i++)
            {
                short v = BinaryPrimitives.ReadInt16LittleEndian(payload[(i * 2)..]);
                sum += v;
                if (v < min) min = v;
                if (v > max) max = v;
            }
            s.Samples += n;
        }

        s.Sum += sum;
        if (min < s.Min) s.Min = min;
        if (max > s.Max) s.Max = max;
    }

    public int CopyStatsTo(Span<ChannelStats> dest)
    {
        int k = 0;
        for (int ch = 0; ch < _stats.Length; ch++)
        {
            ref ChannelStatsV2 s = ref _stats[ch];
            if (s.Frames == 0) continue;
            if (k >= dest.Length) throw new ArgumentException("버퍼가 작다", nameof(dest));
            dest[k++] = new ChannelStats(ch, s.Frames, s.Samples, s.Sum, s.Min, s.Max, s.Gaps);
        }
        return k;
    }
}
```

### `MemoryMarshal.Cast`는 공짜가 아니라 계약이다

`Cast<byte, short>`는 **바이트를 복사하지 않고 같은 메모리를 다른 눈으로 본다.** 그래서 빠르다. 그리고 그 대가로 세 가지 계약이 생긴다.

| 계약 | 내용 | 어기면 |
|---|---|---|
| **엔디언** | 재해석은 **기계 바이트 순서**로 이뤄진다 | 빅엔디언 기계에서 모든 값이 바이트 스왑된 채 읽힌다 |
| **길이 절삭** | 결과 길이는 `바이트수 / sizeof(T)`로 **내림**한다. 예외가 아니다 | 홀수 길이의 마지막 바이트가 조용히 무시된다 |
| **참조 금지** | `T`에 관리 참조가 들어 있으면 안 된다 | 런타임에 `ArgumentException` |

> **⚠️ `Cast`의 엔디언 의존은 x64/ARM64에서만 개발하면 영원히 안 보인다**
>
> 오늘날 실무에서 쓰는 CPU는 사실상 전부 리틀엔디언이므로 `BitConverter.IsLittleEndian` 분기는 죽은 코드처럼 보인다. 그러나 이 코드가 도는 곳이 IBM zSeries나 일부 임베디드 빅엔디언 타깃이면 **결과가 전부 틀리고 예외는 나지 않는다.**
>
> 판단은 둘 중 하나다. **지원 플랫폼을 리틀엔디언으로 못 박고 정적 생성자에서 검사하든가**(`if (!BitConverter.IsLittleEndian) throw new PlatformNotSupportedException(...)`), **폴백 경로를 쓰고 유지하든가.** 최악은 폴백 경로를 쓰되 아무도 테스트하지 않는 것이다 — 위 코드의 빅엔디언 분기는 어떤 CI에서도 실행되지 않고, 그래서 언젠가 조용히 썩는다. 테스트할 수 없는 분기라면 차라리 `PlatformNotSupportedException`이 정직하다.

> **⚠️ `Cast`의 길이 절삭은 예외가 아니라 무시다**
>
> `MemoryMarshal.Cast<byte, short>(스팬 길이 7)`은 길이 3의 `Span<short>`를 돌려주고, **7번째 바이트는 사라진다.** 예외도 경고도 없다.
>
> 이 디코더에서는 `LEN`이 짝수임을 파싱 시점에 검증했기 때문에 안전하다. 그 검증(`(len & 1) != 0`)을 지우면 마지막 샘플이 통계에서 조용히 빠진다 — 그리고 그 버그는 `LEN`이 홀수인 프레임이 실제로 도착해야만 드러난다.
>
> **`Cast`를 쓰는 코드에는 길이 불변식을 검증하는 지점이 반드시 있어야 하고, 그 검증에 테스트가 붙어 있어야 한다.**

### 어느 변경이 얼마나 기여했나

네 가지를 한꺼번에 바꿨으므로, 하나씩 켜 가며 잰다. **여러 변경을 묶어서 재고 "4차가 빨라졌다"고 기록하면 다음에 무엇을 되돌려도 되는지 알 수 없다.**

**예시 측정 결과** (환경: .NET 8.0.6, x64 RyuJIT AVX2, DefaultJob, 입력 16 MiB / 128 샘플 프레임)

| 누적 변경 | Mean | 직전 대비 | 판정 |
|---|---:|---:|---|
| V3 (기준) | 62.1 ms | — | — |
| \+ 샘플을 `Cast<byte, short>`로 | 43.2 ms | −30% | **효과가 크다** |
| \+ 체크섬을 `Cast<byte, ushort>`로 | 33.5 ms | −22% | **효과가 크다** |
| \+ 재동기를 `IndexOf`로 | 33.5 ms | 0% | **효과 없음** |
| \+ 버퍼를 `ArrayPool`로 | 33.5 ms | 0% | **시간 효과 없음** |

**네 개 중 두 개는 시간을 전혀 줄이지 않았다.** 이건 예상해야 할 결과였다.

> **⚠️ 이 표의 수치는 예시다 — 기여도 순위는 자신의 데이터에서 다시 재라**
>
> 잡음 비율이 0.1%가 아니라 20%인 스트림이라면 `IndexOf`의 기여도가 1위로 올라간다. 기여도는 코드의 속성이 아니라 **코드와 데이터의 조합**이 만든다. 변경을 하나씩 켜 가며 재는 절차만 그대로 따르고, 순위는 직접 얻어라.

- **`IndexOf`가 효과가 없는 이유**: 정상 스트림에서는 프레임이 붙어 있으므로 `SYNC`가 항상 오프셋 0에 있다. `IndexOf`는 즉시 0을 반환하고 벡터화된 검색 루프는 **한 번도 돌지 않는다.** 도움이 되는 것은 잡음 구간을 건너뛸 때뿐이고, 그건 전체의 0.1%다.
- **`ArrayPool`이 효과가 없는 이유**: 디코더 인스턴스 하나가 버퍼 하나를 수명 내내 들고 있다. 빌리고 반납하는 일이 프로세스 수명에 한 번뿐이므로 시간에 영향이 없다. 그렇다고 무가치한 것은 아니다 — **다른 시나리오에서 값을 낸다.**

> **💡 `ArrayPool`의 이득은 시간이 아니라 동시성 규모에서 나온다**
>
> 이 벤치마크는 디코더 하나를 잰다. 실제 수집기는 **동시 연결 5,000개**를 처리한다. 그러면 72 KiB × 5,000 = **351 MB**의 버퍼가 상주하고, 연결이 붙었다 떨어질 때마다 그만큼이 할당·수거된다.
>
> 풀을 쓰면 실제 동시 활성 연결 수만큼만 살아 있고 나머지는 재사용된다. **`Mean` 열에는 절대 나타나지 않는 이득**이며, `dotnet-counters`의 GC 힙 크기와 `working set`에서만 보인다(67.6절, 73장).
>
> 반대로 말하면, 연결이 하나뿐인 CLI 도구에서 `ArrayPool`을 쓰는 것은 순수한 복잡도 증가다. **`ArrayPool`은 "빌린 것을 반드시 반납해야 한다"는 계약을 코드 전체에 퍼뜨린다**(69.3절). 그 계약을 감당할 이유가 없으면 쓰지 마라.

> **⚠️ 풀에서 빌린 배열은 반납한 뒤 절대 만지면 안 된다 — 그리고 그건 컴파일러가 못 막는다**
>
> `Dispose()`에서 `_buf = null`을 먼저 하고 반납하는 이유가 이것이다. 반납한 배열을 다른 스레드가 이미 빌려 갔을 수 있고, 거기에 쓰면 **남의 데이터를 덮어쓴다.** 예외는 나지 않는다.
>
> 더 위험한 것은 **이중 반납**이다. 같은 배열을 두 번 `Return`하면 풀이 같은 배열을 두 소비자에게 동시에 빌려주고, 그 시점부터 두 코드가 같은 메모리를 서로 모른 채 쓴다. 재현 불가능한 데이터 오염이 되고, 원인 규명에 며칠이 걸린다.
>
> `Return(array, clearArray: true)`는 참조를 담은 배열에서만 필요하다. `byte[]`는 참조가 없으므로 지우지 않는 편이 빠르지만, **버퍼에 비밀 값(토큰, 키)이 지나갔다면 지워야 한다** — 다음 대여자가 그 바이트를 읽을 수 있다.

### `stackalloc`은 여기에 쓸 자리가 없다

3권에서 `stackalloc`을 배웠으니 어딘가에 써야 할 것 같지만, **이 문제의 핫 패스에는 쓸 자리가 없다.** 이유는 명확하다 — 디코더가 다루는 모든 데이터는 이미 호출자의 버퍼 안에 연속으로 있고, 우리는 그것을 슬라이스로 볼 뿐이다. **임시 사본을 만들 일이 없으면 스택에 만들 일도 없다.**

굳이 쓴다면 호출자 쪽이다.

```csharp
// 대시보드가 활성 채널 통계를 한 번 훑는다. 힙 할당 없음.
Span<ChannelStats> snapshot = stackalloc ChannelStats[64];
int n = decoder.CopyStatsTo(snapshot);
for (int i = 0; i < n; i++)
    Report(snapshot[i]);
```

`ChannelStats`는 관리 참조를 담지 않는 `readonly record struct`이므로 `stackalloc`이 가능하다(68.9절).

> **⚠️ `stackalloc`의 크기는 상수여야 안전하다 — 변수를 넣는 순간 스택 오버플로가 가능해진다**
>
> ```csharp
> Span<ChannelStats> s = stackalloc ChannelStats[channelCount];   // 위험
> ```
>
> `channelCount`가 1,024면 1,024 × 32 = **32 KB**를 스택에서 가져간다. 기본 스레드 스택이 1 MB이므로 한 번은 견디지만, 이 함수가 재귀 안에 있거나 깊은 호출 사슬 밑에 있으면 `StackOverflowException`이 난다. **그리고 이 예외는 `catch`할 수 없다 — 프로세스가 즉시 죽는다**(63.7절).
>
> 규칙은 단순하다. **`stackalloc` 크기는 컴파일 타임 상수로 고정하고, 그보다 크면 `ArrayPool`로 넘긴다.**
>
> ```csharp
> const int StackLimit = 128;
> ChannelStats[]? rented = null;
> Span<ChannelStats> buf = n <= StackLimit
>     ? stackalloc ChannelStats[StackLimit]
>     : (rented = ArrayPool<ChannelStats>.Shared.Rent(n));
> try { /* ... */ }
> finally { if (rented is not null) ArrayPool<ChannelStats>.Shared.Return(rented); }
> ```
>
> 이 하이브리드 패턴이 BCL 전역에 등장하는 이유가 그것이다. `stackalloc` 영역의 0 초기화 비용이 신경 쓰인다면 `[SkipLocalsInit]`이 있지만, 그 대가와 위험은 69.8절에서 다뤘다.

> **💡 기법을 배웠다고 쓸 자리를 만들지 마라**
>
> 이 절에서 `stackalloc`을 억지로 끼워 넣었다면 코드는 길어지고 위험은 늘고 성능은 그대로였을 것이다. **`Span`·`ArrayPool`·`stackalloc`은 각각 다른 문제를 푼다.**
>
> - `Span` — 복사 없이 부분을 가리키고, 복사 없이 재해석한다.
> - `ArrayPool` — **수명이 짧고 큰** 버퍼가 **많이** 생길 때 쓴다.
> - `stackalloc` — **작고 크기가 고정된** 임시 버퍼를 힙 밖에서 만든다.
>
> 자기 문제에 셋 중 몇 개가 해당하는지 세어 보고, 해당하는 것만 써라. 여기서는 `Span`이 전부였고, `ArrayPool`은 확장성을 위한 보험이었고, `stackalloc`은 필요 없었다.

## 82.6 5차: 벡터화

### 남은 것은 산술뿐이다

4차의 33.5 ms에서 시간이 어디로 가는지 프로파일러로 보면(67.6절) 두 루프가 거의 전부를 차지한다.

| 루프 | 원소당 하는 일 | 16 MiB당 반복 |
|---|---|---|
| `VerifyChecksum`의 워드 합 | u16 로드 1 + 덧셈 1 | 약 840만 |
| `Consume`의 샘플 순회 | i16 로드 1 + 덧셈 1 + 비교 2 | 약 786만 |

둘 다 **lane 독립적이고, 분기가 없고, 연속 메모리를 순차로 읽는다.** 71.3절이 말하는 벡터화의 세 가지 조건을 정확히 만족한다.

### V5 — 벡터화한 두 루프

디코더의 나머지 구조는 V4와 동일하고, 두 정적 메서드만 바뀐다.

```csharp
using System.Runtime.CompilerServices;
using System.Runtime.InteropServices;
using System.Runtime.Intrinsics;

internal static class VectorKernels
{
    /// <summary>u16 LE 워드의 합(mod 2^16). 리틀엔디언 전용.</summary>
    public static ushort ChecksumWords(ReadOnlySpan<byte> bytes)
    {
        ReadOnlySpan<ushort> words = MemoryMarshal.Cast<byte, ushort>(bytes);
        ref ushort p = ref MemoryMarshal.GetReference(words);
        int n = words.Length;
        int i = 0;
        ushort sum = 0;

        if (Vector256.IsHardwareAccelerated && n >= Vector256<ushort>.Count * 2)
        {
            int w = Vector256<ushort>.Count;                 // AVX2에서 16
            var acc0 = Vector256<ushort>.Zero;
            var acc1 = Vector256<ushort>.Zero;

            // 누산기를 둘로 나눠 의존 사슬을 끊는다 (명령 수준 병렬성)
            for (; i <= n - 2 * w; i += 2 * w)
            {
                acc0 += Vector256.LoadUnsafe(ref p, (nuint)i);
                acc1 += Vector256.LoadUnsafe(ref p, (nuint)(i + w));
            }

            Vector256<ushort> acc = acc0 + acc1;
            // 수평 축약은 루프 밖에서 딱 한 번 (71.6절 손해 유형 6)
            // u16 덧셈은 mod 2^16으로 감싸므로, u32로 넓혀 더한 뒤 잘라도 결과가 같다
            sum = (ushort)(Vector256.Sum(Vector256.WidenLower(acc))
                         + Vector256.Sum(Vector256.WidenUpper(acc)));
        }
        else if (Vector128.IsHardwareAccelerated && n >= Vector128<ushort>.Count)
        {
            int w = Vector128<ushort>.Count;                 // 8
            var acc = Vector128<ushort>.Zero;
            for (; i <= n - w; i += w)
                acc += Vector128.LoadUnsafe(ref p, (nuint)i);
            sum = (ushort)(Vector128.Sum(Vector128.WidenLower(acc))
                         + Vector128.Sum(Vector128.WidenUpper(acc)));
        }

        for (; i < n; i++)                                   // 잔여 처리
            sum = (ushort)(sum + Unsafe.Add(ref p, i));

        return sum;
    }

    /// <summary>i16 샘플의 합·최소·최대를 한 번에 구한다.</summary>
    public static void Accumulate(ReadOnlySpan<short> s,
                                  out long sum, out short min, out short max)
    {
        ref short p = ref MemoryMarshal.GetReference(s);
        int n = s.Length;
        int i = 0;
        long total = 0;
        short lo = short.MaxValue, hi = short.MinValue;

        if (Vector256.IsHardwareAccelerated && n >= Vector256<short>.Count)
        {
            int w = Vector256<short>.Count;                  // 16
            var vmin  = Vector256.Create(short.MaxValue);
            var vmax  = Vector256.Create(short.MinValue);
            var accLo = Vector256<int>.Zero;                 // i16 합은 넘칠 수 있으므로 i32로
            var accHi = Vector256<int>.Zero;

            for (; i <= n - w; i += w)
            {
                Vector256<short> v = Vector256.LoadUnsafe(ref p, (nuint)i);
                vmin  = Vector256.Min(vmin, v);
                vmax  = Vector256.Max(vmax, v);
                accLo += Vector256.WidenLower(v);
                accHi += Vector256.WidenUpper(v);
            }

            total = (long)Vector256.Sum(accLo) + Vector256.Sum(accHi);

            // lane별 최소/최대를 스칼라로 접는다. 프레임당 고정 비용 32회.
            Span<short> tmp = stackalloc short[Vector256<short>.Count];
            vmin.CopyTo(tmp);
            for (int k = 0; k < tmp.Length; k++) if (tmp[k] < lo) lo = tmp[k];
            vmax.CopyTo(tmp);
            for (int k = 0; k < tmp.Length; k++) if (tmp[k] > hi) hi = tmp[k];
        }

        for (; i < n; i++)
        {
            short v = Unsafe.Add(ref p, i);
            total += v;
            if (v < lo) lo = v;
            if (v > hi) hi = v;
        }

        sum = total; min = lo; max = hi;
    }
}
```

`Consume`과 `VerifyChecksum`은 이 커널을 부르기만 한다.

```csharp
private static bool VerifyChecksum(ReadOnlySpan<byte> frame, int len)
{
    int covered = FrameCodec.HeaderSize + len;
    ushort expected = BinaryPrimitives.ReadUInt16LittleEndian(frame[covered..]);
    return VectorKernels.ChecksumWords(frame[..covered]) == expected;
}

// Consume 안에서
VectorKernels.Accumulate(samples, out long sum, out short min, out short max);
s.Samples += samples.Length;
s.Sum     += sum;
if (min < s.Min) s.Min = min;
if (max > s.Max) s.Max = max;
```

세 가지가 설계 결정이다.

- **누산기를 둘로 쪼갰다.** `acc0`/`acc1`은 서로 독립이므로 CPU가 두 덧셈을 동시에 발행할 수 있다. 하나면 매 반복이 직전 결과를 기다린다.
- **수평 축약을 루프 밖으로 뺐다.** lane을 가로지르는 연산은 비싸다(71.6절 손해 유형 6).
- **`i32` 누산기를 썼다.** `i16` lane에 그대로 더하면 `LEN`이 큰 프레임에서 넘친다. `LEN ≤ 2048`이므로 샘플 1,024개, lane당 최대 64 × 32,767 = 약 210만으로 `int` 안에 안전하게 들어간다.

> **⚠️ 잔여 루프와 폴백 경로는 차분 테스트 없이는 반드시 틀린다**
>
> 이 커널에는 실행 경로가 넷이다 — AVX2 본체, AVX2 잔여, SSE 본체, 완전 스칼라. 그리고 대부분의 개발 머신에서는 **첫 두 개만 실행된다.** `Vector128` 분기와 완전 스칼라 분기는 CI에서도 안 돌 수 있다.
>
> 82.2절의 차분 테스트가 여기서 값을 한다. 씨드 200개 × 프레임 길이가 제각각인 데이터를 흘리면 `n % 16`의 모든 나머지가 밟히고, 잔여 루프 경계 오류(`i <= n - w`를 `i < n - w`로 쓰는 것 같은)가 즉시 드러난다.
>
> 폴백 경로까지 강제로 밟으려면 환경 변수로 명령 집합을 끄고 테스트를 한 번 더 돌려라.
>
> ```text
> DOTNET_EnableAVX2=0 DOTNET_EnableAVX=0 dotnet test -c Release
> ```
>
> 이 변수들은 진단·테스트 용도이며 프로덕션 설정이 아니다. **CI에 이 잡 하나를 추가하는 데 드는 비용은 몇 분이고, 없을 때 치르는 비용은 "특정 서버에서만 최댓값이 틀린" 버그다.**

### 그래서 이득인가 — 이 문제의 구조적 한계

벡터화를 하기 전에 71.6절의 손해 유형표를 이 문제에 대입했어야 한다. 사후에라도 해 보자.

| 71.6절 손해 유형 | 이 문제에서 | 판정 |
|---|---|---|
| ① 짧은 데이터 | 프레임당 128 샘플. AVX2 폭 16이므로 벡터 반복 8회 | 경계선. `LEN`이 작아지면 즉시 손해 |
| ② 분기가 많은 로직 | 없음. 합·최소·최대뿐 | 문제없음 |
| ③ 메모리 대역폭 | 워드당 연산 1~4개. 산술 강도가 낮다 | **이득의 상한을 정한다** |
| ④ 데이터 배치 | 페이로드가 연속. 완벽 | 문제없음 |
| ⑤ 부동소수점 재현성 | 정수 연산이므로 해당 없음 | 문제없음 |
| ⑥ 수평 연산 | **프레임마다 한 번씩 필요하다** | **구조적 한계** |

⑥번이 이 문제의 천장이다. 최소·최대는 **채널별** 값인데 프레임은 채널이 뒤섞여 온다. 그래서 벡터 누산기를 프레임 경계 너머로 들고 갈 수 없고, **프레임마다 수평 축약 + 32회의 스칼라 접기**를 해야 한다. 그 고정 비용은 프레임 길이와 무관하다.

```text
  프레임당 비용 =  고정 비용(진입 검사 + 상수 준비 + 수평 축약 + 접기)
                 + ⌈N/16⌉ × 벡터 반복 비용
                 + (N mod 16) × 스칼라 비용

  N이 작으면 고정 비용이 전부를 지배한다
```

이 관계를 실제로 재려면 `[Params]`로 프레임 길이를 흔든다. **총 입력 바이트 수는 16 MiB로 고정**하므로, 샘플 수가 적으면 프레임 수가 그만큼 늘어난다.

| 프레임당 샘플 | 프레임 수 | V4 (스칼라) | V5 (벡터) | 배수 | 판정 |
|---:|---:|---:|---:|---:|---|
| 8 | 약 559,000 | 48.2 ms | 51.6 ms | **0.93×** | **손해** |
| 32 | 약 215,000 | 30.4 ms | 28.9 ms | 1.05× | 차이 없음 |
| 128 | 약 61,400 | 33.5 ms | 19.8 ms | 1.69× | 이득 |
| 512 | 약 16,200 | 31.1 ms | 12.4 ms | 2.51× | 큰 이득 |

**프레임이 짧으면 벡터화가 오히려 느리다.** 샘플 8개짜리 프레임에서는 벡터 루프가 아예 돌지 않고(8 < 16), 진입 검사와 폴백 진입 비용만 순수하게 추가된다.

> **⚠️ 이 표의 수치는 예시다 — 그리고 이 표에서 배울 것은 숫자가 아니라 곡선의 모양이다**
>
> 절대값은 CPU의 SIMD 처리량, 메모리 대역폭, 캐시 크기에 따라 완전히 달라진다. AVX-512 서버에서는 교차점이 왼쪽으로 옮겨가고, ARM64 NEON(128비트)에서는 오른쪽으로 옮겨간다.
>
> 여기서 가져갈 것은 하나다. **"벡터화하면 빨라진다"는 명제가 아니라 함수다.** 입력 길이 분포에 따라 값이 바뀌고, 어떤 구간에서는 1보다 작다. 자기 데이터의 **길이 히스토그램**을 뽑기 전에는 이 질문에 답할 수 없다(71.6절).

> **💡 우리 데이터가 프레임당 8샘플이었다면 5차는 채택하지 않는다**
>
> 이 문제에서 벡터화를 채택할지 말지는 **코드 품질의 문제가 아니라 데이터의 문제**다. 장비가 보내는 프레임 길이 분포를 하루치 로그에서 뽑아 보고, 중앙값이 128 이상이면 채택하고 32 이하면 채택하지 않는다.
>
> 더 나쁜 경우가 있다. **길이가 섞여 있을 때** — 8샘플이 70%, 512샘플이 30%라면 벡터 경로가 프레임의 70%를 느리게 만든다. 길이별로 분기를 두면(`if (n >= 64) 벡터 else 스칼라`) 양쪽을 다 얻지만, 코드 경로가 하나 더 늘고 테스트해야 할 조합이 두 배가 된다.
>
> **그리고 이 판단은 요구사항이 바뀌면 뒤집힌다.** 장비 펌웨어가 프레임을 잘게 쪼개도록 업데이트되는 순간, 5차는 이득에서 손해로 바뀌고 아무도 그 사실을 모른다. 82.8절이 이 위험을 다룬다.

### 5차 결과

**예시 측정 결과** (환경: .NET 8.0.6, x64 RyuJIT AVX2, DefaultJob, 입력 16 MiB / 128 샘플 프레임)

| Method | Mean | Ratio | Allocated | 처리량 | 직전 대비 |
|---|---:|---:|---:|---:|---:|
| V1_Naive | 512.4 ms | 1.00 | 152.7 MB | 31 MB/s | — |
| V2_Algorithm | 68.9 ms | 0.134 | 244 KB | 232 MB/s | 7.44× |
| V3_NoAlloc | 62.1 ms | 0.121 | 0 B | 258 MB/s | 1.11× |
| V4_Span | 33.5 ms | 0.065 | 0 B | 478 MB/s | 1.85× |
| **V5_Simd** | **19.8 ms** | **0.039** | **0 B** | **809 MB/s** | **1.69×** |

> **⚠️ 이 표의 수치는 예시다 — 그리고 `Ratio 0.039`를 "26배 빨라졌다"고 인용하면 안 된다**
>
> 이 26배는 **V1의 O(n²)가 만든 숫자**다. V1이 그렇게까지 나쁘지 않은 구현이었다면 전체 배수는 5~6배에 그쳤을 것이다. "이 기법들을 쓰면 26배 빨라진다"는 문장은 이 장의 어디에도 없고, 만들 수도 없다.
>
> 정직한 요약은 이렇다. **알고리즘 결함을 고치면 이 예시에서 7배 남짓, 나머지 세 단계를 다 밟으면 추가로 3.5배 남짓이 나왔다.** 그리고 그 3.5배는 데이터 형태가 바뀌면 사라질 수 있다.

## 82.7 각 단계의 코드 복잡도 vs 성능 이득 그래프

### 두 축을 나란히 놓는다

성능만 그린 그래프는 항상 "더 가라"고 말한다. 복잡도를 같은 그림에 올려야 판단이 가능해진다.

**예시 측정 결과 기준** (환경: .NET 8.0.6, x64, 입력 16 MiB / 128 샘플 프레임. 줄 수는 테스트를 제외한 디코더 구현부만 센 값)

```text
누적 성능 배수 (V1 = 1.0)                        구현 줄 수
                                                 
V5 ████████████████████████████ 25.9×            ██████████████████████ 226
V4 ████████████████ 15.3×                        ███████████████ 158
V3 ████████ 8.3×                                 ██████████████ 141
V2 ███████ 7.4×                                  ███████████ 118
V1 █ 1.0×                                        █████████ 92
   └──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴   └──┴──┴──┴──┴──┴──┴──┴──┴
   0        5       10       15       20      25  0    50   100  150  200

  ★ V1→V2 구간에서 배수의 29%가 나오고 줄 수의 11%만 쓴다
  ★ V4→V5 구간에서 배수의 41%가 나오고 줄 수의 30%를 쓴다
```

숫자로 다시 보면 이렇다.

| 구간 | 절감한 시간 | 늘어난 줄 수 | **줄당 절감(ms/줄)** | 인지 부하 | 유지보수 가능한 팀원 |
|---|---:|---:|---:|:---:|---|
| V1 → V2 (알고리즘) | 443.5 ms | +26 | **17.06** | ★☆☆☆☆ | 전원 |
| V2 → V3 (할당 제거) | 6.8 ms | +23 | **0.30** | ★★☆☆☆ | 전원 |
| V3 → V4 (`Span`·풀링) | 28.6 ms | +17 | **1.68** | ★★★★☆ | 절반 |
| V4 → V5 (벡터화) | 13.7 ms | +68 | **0.20** | ★★★★★ | 한두 명 |

"줄당 절감" 열이 이 장의 결론을 압축한다. **1차 → 2차가 다음 세 단계를 전부 합친 것보다 스무 배 이상 효율적이다.**

### 인지 부하는 줄 수보다 중요하다

줄 수는 세기 쉬워서 쓰는 대리 지표일 뿐이다. 실제로 팀을 아프게 하는 것은 다른 것이다.

| 단계 | 새로 도입된 개념 | 새 개념을 모르면 생기는 일 |
|---|---|---|
| V2 | 커서 버퍼, `ref` 반환 인덱서 | 구조체를 복사해 고치고 결과가 조용히 틀린다 |
| V3 | LOH 임계값, 인스턴스 재사용, `Reset` 계약 | `Reset`을 잊어 통계가 누적된다 |
| V4 | 스팬 수명, `Cast` 엔디언·절삭, 풀 반납 계약 | 이중 반납으로 재현 불가 데이터 오염 |
| V5 | 벡터 폭, 잔여 루프, 폴백 경로, 수평 축약 | 특정 길이·특정 CPU에서만 결과가 틀린다 |

아래로 갈수록 **실패가 조용해진다.** V1의 실패는 느린 것이고, V5의 실패는 틀린 것이다. 이 차이가 줄 수 68이라는 숫자보다 훨씬 무겁다.

> **💡 성능 그래프에 "실패했을 때 얼마나 시끄러운가" 축을 하나 더 그려라**
>
> 최적화 단계를 평가할 때 흔히 성능과 복잡도만 본다. 세 번째 축이 필요하다. **이 코드가 잘못 수정되면 무엇으로 드러나는가.**
>
> - 느려진다 → 벤치마크가 잡는다. 안전하다.
> - 예외가 난다 → 테스트와 로그가 잡는다. 안전하다.
> - **값이 틀린다** → 아무도 못 잡는다. **여기서만 사고가 난다.**
>
> V4와 V5는 세 번째 범주의 실패 방식을 새로 도입한다. 그래서 이 두 단계는 차분 테스트(82.2절)와 짝을 이루지 않으면 채택해서는 안 된다. **테스트 없이 채택할 수 있는 마지막 단계는 V2다.**

> **⚠️ 이 그래프의 형태는 문제마다 다르다 — 다만 "첫 단계가 가장 싸다"는 경향은 흔하다**
>
> 여기서 V1→V2가 압도적인 것은 기준선에 O(n²) 결함이 있었기 때문이다. 기준선이 이미 알고리즘적으로 건전했다면 첫 막대가 낮았을 것이고, 그래프의 모양이 완전히 달라졌을 것이다.
>
> 그래도 실무의 기준선에는 이런 결함이 **매우 자주** 있다. 프로파일러를 처음 붙였을 때 나오는 1위가 `List.RemoveAt(0)`이나 N+1 쿼리(72.4절)나 재계산되는 정렬인 경우가, `Span`을 안 쓴 경우보다 훨씬 많다. **그래서 순서가 알고리즘 → 할당 → `Span` → 벡터화인 것이다.**

## 82.8 어디서 멈춰야 하는가

### 멈출 지점은 성능이 아니라 요구사항이 정한다

82.1절에서 목표를 적어 뒀다. 그 목표에 각 단계를 비춰 보면 답이 나온다.

| 요구 처리량(코어당) | 필요한 최소 단계 | 이유 |
|---|---|---|
| ~30 MB/s (파일 배치 처리) | **V1** | 이미 만족한다. 손대지 마라 |
| ~200 MB/s (1 Gbps NIC 여유) | **V2** | 알고리즘 결함만 고치면 도달한다 |
| ~450 MB/s (10 Gbps NIC 일부) | **V4** | `Cast` 두 줄이 이득의 전부다 |
| ~800 MB/s (서버 대수 절감) | **V5** | 프레임이 길 때만 |

그리고 이 표에 없는 축이 하나 더 있다. **V3은 처리량 표에 등장하지 않는다.** 처리량으로는 V2와 거의 같기 때문이다. V3을 채택하는 이유는 다른 데 있다.

| V3을 채택하는 이유 | 해당하는가 |
|---|---|
| 프로세스가 며칠 이상 산다 | 상시 수집기 → **예** |
| gen2 GC 일시 정지가 SLA에 걸린다 | p99 목표가 있다면 → 예 |
| 동시 연결이 수천 개다 | LOH 버퍼가 곱해진다 → 예 |
| 하루짜리 배치 도구다 | → **아니오. 채택하지 마라** |

### 유지보수 비용을 숫자로 환산해 본다

성능 이득은 ms로 재고, 유지보수 비용은 재지 않는 것이 보통이다. 대충이라도 같은 단위로 놓아 보면 판단이 선명해진다.

| 단계 | 연간 절감 (서버 비용 환산) | 연간 비용 (리뷰·디버깅·교육) | 순이득 |
|---|---|---|---|
| V2 | 서버 8대 → 2대 | 거의 0. 코드가 더 짧고 명확하다 | **매우 큼** |
| V3 | 서버 대수 변화 없음. p99 개선 | 낮음. `Reset` 계약 하나 | 상황에 따라 |
| V4 | 서버 2대 → 1대 | 중간. 스팬 수명·풀 반납 리뷰 부담 | 서버 비용이 클 때만 |
| V5 | 서버 1대 → 0.6대 | **높음.** 리뷰 가능한 사람이 한두 명, 변경 때마다 폴백 경로 4개 검증 | **대부분 음수** |

V5의 순이득이 음수인 것이 핵심이다. **한 대분의 서버 비용을 아끼려고 시니어 엔지니어의 시간을 매년 며칠씩 쓰는 것은 거의 언제나 손해다.** 이 계산이 뒤집히는 경우는 서버가 한 대가 아니라 300대일 때다.

> **💡 "팀에서 이 코드를 고칠 수 있는 사람이 몇 명인가"가 가장 정직한 복잡도 지표다**
>
> 순환 복잡도나 줄 수는 도구가 세 주지만 이 질문에는 답하지 못한다. 그리고 실제로 배포를 막는 것은 이 질문이다.
>
> 답이 **1명**이면 그 코드는 이미 위험하다. 그 사람이 휴가를 가면 아무도 못 고치고, 그 사람이 퇴사하면 팀은 그 코드를 통째로 되돌리거나 손대지 못한 채 방치한다. 실무에서 고성능 코드가 죽는 가장 흔한 방식이 이것이다 — 느려서가 아니라 **아무도 못 건드려서**다.
>
> 그래서 V5를 채택한다면 반드시 두 가지를 함께 한다. **① 스칼라 참조 구현(V4)을 지우지 않고 남긴다. ② 차분 테스트가 두 구현을 계속 비교한다.** 그러면 최악의 경우 벡터 경로를 지우고 V4로 되돌리는 것이 5분짜리 작업이 된다.

### 요구사항 변화에 얼마나 취약한가

가장 자주 간과되는 축이다. 각 단계가 **어떤 요구사항 변경에 무너지는지** 미리 적어 둔다.

| 요구사항 변경 | V2 | V3 | V4 | V5 |
|---|:---:|:---:|:---:|:---:|
| 채널 번호 상한이 65,535로 확대 | 배열 교체 | 배열 교체 | 배열 교체 | 배열 교체 |
| 체크섬이 CRC-16으로 변경 | 함수 교체 | 함수 교체 | 함수 교체 | **커널 폐기** |
| 페이로드가 `float32`로 변경 | 타입 교체 | 타입 교체 | `Cast` 타입 교체 | **재현성 문제 발생**(71.6절) |
| 프레임에 가변 길이 TLV 확장 추가 | 파싱 추가 | 파싱 추가 | 파싱 추가 | **고정 오프셋 가정 붕괴** |
| 프레임 길이가 8샘플로 축소 | 영향 없음 | 영향 없음 | 영향 없음 | **이득이 손해로 반전** |
| 채널별 중앙값도 요구 | 자료구조 추가 | 자료구조 추가 | 자료구조 추가 | 벡터화 불가 |
| 재정렬된 프레임 허용 | **결손 계수 재설계** | 재설계 | 재설계 | 재설계 |

V5 열에만 "폐기"와 "반전"이 있다. **최적화가 깊어질수록 코드는 특정 데이터 형태에 더 강하게 결합된다.** 그것이 최적화의 본질이다 — 일반성을 팔아 속도를 산다.

> **⚠️ 벡터화된 코드는 요구사항이 아니라 데이터 형태에 계약을 건다 — 그리고 그 계약은 어디에도 적혀 있지 않다**
>
> V5는 "프레임당 샘플이 16개 이상이다"라는 조건에서만 이득이다. 그 조건은 코드 어디에도 쓰여 있지 않고, 타입 시스템도, 테스트도, 컴파일러도 확인해 주지 않는다. **장비 펌웨어 업데이트 한 번으로 조용히 깨지고, 아무도 모른다.**
>
> 최소한의 방어는 이렇다. **가정을 코드에 적고, 벤치마크로 감시한다.**
>
> ```csharp
> // 이 커널은 프레임당 샘플 수 중앙값이 16 이상일 때만 스칼라 대비 이득이다.
> // 회귀 감시: PayloadSizeSensitivityBench (CI 야간 잡)
> ```
>
> 그리고 실제 트래픽의 프레임 길이 히스토그램을 메트릭으로 내보내라(75장). 분포가 왼쪽으로 옮겨가는 것이 보이면, 그때가 V4로 되돌릴 때다.

### 이 장의 결정

다섯 개를 다 만들었지만 배포하는 것은 하나다. 이 문제에 대한 저자의 판단은 이렇다.

- **V2를 기본으로 배포한다.** 이득의 29%를 줄 수의 11%로 얻고, 팀 전원이 읽을 수 있고, 요구사항 변화에 가장 강하다.
- **V4를 브랜치가 아니라 같은 저장소에 함께 둔다.** 처리량 요구가 올라가면 구성 플래그로 전환한다. 차분 테스트가 두 구현을 계속 묶어 준다.
- **V5는 만들되 배포하지 않는다.** 프레임 길이 분포가 지금 그대로이고 서버가 수백 대가 되는 날, 그때 다시 꺼낸다. 그때까지는 "가능하다는 것을 확인했고 비용을 안다"는 지식으로 남긴다.
- **V1과 V3은 지운다.** V1은 V2로 완전히 대체됐고, V3은 V4의 중간 단계일 뿐 독립적인 가치가 없다.

> **💡 최적화 작업의 산출물은 빠른 코드가 아니라 "어디까지 갈 수 있는지에 대한 지식"이다**
>
> 다섯 번 고쳐 쓰고 하나만 배포하는 것은 낭비처럼 보인다. 아니다. **이제 이 팀은 "이 디코더를 최대 얼마나 빠르게 만들 수 있고, 그 대가가 무엇인지"를 안다.** 다음에 처리량 요구가 두 배로 올라왔을 때, 회의에서 추측하는 대신 이미 측정된 표를 꺼낸다.
>
> 그 지식의 유효기간은 데이터 형태가 유지되는 동안이다. 그래서 이 장의 벤치마크와 차분 테스트를 저장소에 남기는 것이 최종 산출물이다 — **코드가 아니라 측정 장치가 남는다.**

## 이 장의 요약

- **최적화의 순서는 알고리즘 → 할당 → `Span`·풀링 → 벡터화다.** 이 순서에는 이유가 있다. 앞 단계가 뒤 단계의 상한을 정하고, 앞 단계를 건너뛰면 뒤 단계의 노력이 헛수고가 된다.
- **가장 큰 이득은 거의 언제나 알고리즘에서 나온다.** 이 예시에서 1차 → 2차가 전체 배수의 29%를 줄 수의 11%로 만들었고, 나머지 세 단계를 합친 것보다 스무 배 이상 효율적이었다.
- **할당 0이 처리량 개선을 뜻하지는 않는다.** 3차는 시간을 10%만 줄였다. 그러나 gen2 GC를 없애고 회귀를 테스트로 고정했다 — 목표를 미리 적어 두지 않았다면 이 단계를 실패로 오판했을 것이다.
- **`Allocated` 총량이 아니라 기울기를 보라.** 입력 크기를 `[Params]`로 흔들어 O(1) 고정 비용과 O(n) 핫 패스 할당을 구분하는 것이, 총량 하나를 보고 표적을 고르는 것보다 압도적으로 낫다.
- **`Span`의 이득은 `MemoryMarshal.Cast`에서 나왔고, `ArrayPool`과 `IndexOf`는 시간을 전혀 줄이지 않았다.** 여러 변경을 묶어 재면 이 사실을 알 수 없다. 하나씩 켜 가며 재라.
- **벡터화의 이득은 명제가 아니라 함수다.** 같은 코드가 프레임 128샘플에서 1.69배 이득, 8샘플에서 0.93배 손해였다. 길이 히스토그램 없이 벡터화 여부를 결정하는 것은 추측이다.
- **단계가 깊어질수록 실패가 조용해진다.** V1의 실패는 느린 것이고 V5의 실패는 값이 틀린 것이다. **테스트 없이 채택할 수 있는 마지막 단계는 2차다.**
- **다섯 번 고쳐 쓰되 배포는 하나만 한다.** 나머지는 "어디까지 갈 수 있고 대가가 얼마인지"에 대한 측정된 지식으로 남는다. 최종 산출물은 코드가 아니라 벤치마크와 차분 테스트다.

## 연습 문제

1. 82.1절의 `TestStream.Build`와 82.2절의 `DecoderV1`을 그대로 옮겨 자신의 환경에서 벤치마크를 돌려라. 이 장의 예시 표와 배수가 얼마나 다른지 기록하고, 다른 이유를 하나 이상 설명하라(CPU, GC 모드, .NET 버전 중 무엇인가).

2. `DecoderBench`의 청크 크기를 `[Params(4096, 16384, 65536, 262144)]`로 흔들어 V1과 V2를 재라. V1의 `Mean`이 청크 크기에 대해 선형인지 제곱인지 그래프로 확인하고, V2는 어떤지 비교하라.

3. 82.4절의 `AllocationShapeBench`를 V1에 적용하라. V1의 `Allocated`는 입력 크기에 대해 어떤 기울기를 갖는가. 그 기울기가 82.4절에서 V2에 대해 관찰한 것과 어떻게 다른지 설명하라.

4. `DecoderV3`의 `BufferSize`를 `72 * 1024`에서 `128 * 1024`로 되돌리고 벤치마크를 다시 돌려라. `Gen2` 열이 어떻게 바뀌는가. `dotnet-counters`로 LOH 크기를 관찰해 원인을 확인하라(67.6절, 73장).

5. `DecoderV4`의 `VerifyChecksum`에서 `MemoryMarshal.Cast`를 쓰는 분기만 원래의 바이트 단위 루프로 되돌려 재라. 82.5절의 기여도 표와 같은 방향의 결과가 나오는가. `[DisassemblyDiagnoser]`로 두 버전의 생성 코드를 비교해 경계 검사가 실제로 사라졌는지 확인하라(55.8절).

6. `VectorKernels.ChecksumWords`의 잔여 루프 조건 `i <= n - 2 * w`를 `i < n - 2 * w`로 일부러 바꾸고 차분 테스트를 돌려라. 몇 개의 씨드에서 실패하는가. 그다음 `DOTNET_EnableAVX2=0`으로 다시 돌려 실패가 사라지는 것을 확인하고, 그 사실이 무엇을 의미하는지 설명하라.

7. 프레임 형식을 바꿔 페이로드를 `float` 샘플로 만들고, `VectorKernels.Accumulate`를 `Vector256<float>`로 다시 써라. 같은 입력에 대해 스칼라 합계와 벡터 합계가 비트 단위로 일치하는가. 일치하지 않는다면 그 사실이 이 디코더의 요구사항에 문제가 되는지 판단하고 근거를 적어라(71.6절).
