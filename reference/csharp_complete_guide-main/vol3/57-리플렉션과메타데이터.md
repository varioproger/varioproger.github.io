# 57장. 리플렉션과 메타데이터

> **이 장의 위치** — 52장에서 어셈블리가 **자기 설명적**이라고 했다. 매니페스트와 메타데이터 테이블이 어셈블리 안의 모든 타입과 멤버를 기술한다고. 이 장은 그 메타데이터를 **런타임에 읽고 쓰는 API**를 끝까지 판다. 컴파일 타임에 이름조차 몰랐던 타입을 만들고, 이름이 문자열로 주어진 메서드를 호출하고, 특성에 적힌 선언적 정보를 실행 동작으로 바꾼다. 직렬화·의존성 주입·ORM·테스트 러너·데이터 바인딩이 전부 이 위에 서 있다.
>
> **선수 지식** — 20장(열거형과 특성), 52장(어셈블리), 54장(타입 시스템의 런타임 표현)
>
> **이 장에서 다루지 않는 것** — 어셈블리를 **로드**하는 방법과 `AssemblyLoadContext`는 52장에서 끝냈다. `MethodTable`의 실제 메모리 레이아웃은 54장, Native AOT의 전반적 동작은 55.7절, IL 명령 자체는 56장에서 다뤘다. 런타임에 **새 IL을 만들어내는** `Reflection.Emit`은 58장, `dynamic`과 DLR은 59장 몫이다.

## 57.1 타입 얻기와 타입 이름 규칙

리플렉션(reflection)은 런타임에 메타데이터와 컴파일된 코드를 들여다보는 일이다. 어셈블리에 담긴 컴파일 결과에는 원본 소스의 내용이 거의 그대로 남아 있다. 지역 변수 이름, 주석, 전처리 지시문 같은 일부는 소실되지만 나머지는 대부분 복원 가능하다 — 디컴파일러를 쓸 수 있는 이유가 이것이다(56.8절).

리플렉션 API는 `System.Reflection` 네임스페이스에 있다. 다만 이 장의 출발점인 `Type`만은 예외적으로 `System` 네임스페이스에 산다. 너무 널리 쓰이기 때문이다.

```csharp
using System;
using System.Reflection;
```

### `Type` 인스턴스를 얻는 네 가지 경로

`System.Type` 인스턴스 하나는 어떤 타입의 **메타데이터 전체로 향하는 창**이다. 얻는 방법은 크게 넷이다.

```csharp
// 1. 인스턴스로부터 — 런타임에 결정
Type t1 = DateTime.Now.GetType();

// 2. typeof 연산자 — 컴파일 타임에 결정
Type t2 = typeof(DateTime);

// 3. Assembly 객체로부터 — 이름 문자열
Type t3 = Assembly.GetExecutingAssembly().GetType("Demos.TestProgram");

// 4. 어셈블리 정규화 이름으로부터 — 어셈블리가 암묵적으로 로드된다
Type t4 = Type.GetType("System.Int32, System.Private.CoreLib");
```

`typeof`는 배열 타입과 제네릭 타입에도 쓸 수 있다.

```csharp
Type t5 = typeof(DateTime[]);              // 1차원 배열
Type t6 = typeof(DateTime[,]);             // 2차원 배열
Type t7 = typeof(Dictionary<int, int>);    // 닫힌 제네릭 타입
Type t8 = typeof(Dictionary<,>);           // 언바운드 제네릭 타입
```

`Type`을 손에 넣으면 그때부터 이름·어셈블리·기저 타입·가시성 같은 것을 물어볼 수 있다.

```csharp
Type stringType = typeof(string);
string name     = stringType.Name;       // String
Type baseType   = stringType.BaseType;   // typeof(object)
Assembly assem  = stringType.Assembly;   // System.Private.CoreLib
bool isPublic   = stringType.IsPublic;   // true
```

> **📌 `typeof`가 돌려주는 것은 `RuntimeType`이다**
>
> `System.Type`은 추상 클래스다. 따라서 `typeof` 연산자가 실제로 돌려주는 것은 `Type`의 서브클래스이고, CLR이 쓰는 그 서브클래스의 이름은 `RuntimeType`이다. `internal`이라 이름으로 참조할 수는 없지만 디버거에서는 자주 보인다. 상속 계보는 `Type` → `TypeInfo` → `RuntimeType`이다.
>
> `RuntimeType` 객체 하나는 프로세스 안에서 타입당 하나뿐이다. 그래서 `o1.GetType() == o2.GetType()` 같은 참조 비교가 "두 객체가 같은 타입인가"를 정확히 판정한다.

> **⚠️ `Type.GetType("int")`는 `null`을 돌려준다**
>
> C# 컴파일러가 아는 별칭 — `int`, `string`, `bool` — 은 CLR에게 아무 의미가 없다. CLR이 아는 이름은 `System.Int32`, `System.String`, `System.Boolean`이다. `Type.GetType("int")`는 컴파일은 되고 런타임에 조용히 `null`을 반환한다. **리플렉션이 컴파일 타임 타입 안전성을 잃는다**는 말의 가장 흔한 실례다.
>
> 오버로드에 따라 실패 동작이 다르다. `Type.GetType(string)`은 `null`을 반환하고, `Type.GetType(string, throwOnError: true)`는 `TypeLoadException`(또는 어셈블리를 못 찾으면 `FileNotFoundException`)을 던진다. 조용한 `null`이 싫으면 두 번째 오버로드를 써라.

`Type.GetType`에 어셈블리를 명시하지 않으면 **호출한 어셈블리**를 먼저 뒤지고, 없으면 코어 라이브러리를 뒤진다. 그래서 다른 어셈블리의 타입을 문자열로 찾을 때는 어셈블리 정규화 이름이 필요하다.

```csharp
Type a = Type.GetType("CarLibrary.SportsCar");               // 현재 어셈블리
Type b = Type.GetType("CarLibrary.SportsCar, CarLibrary");   // 외부 어셈블리
Type c = Type.GetType("CarLibrary.JamesBondCar+SpyOptions"); // 중첩 타입은 +
```

> **💡 `typeof`를 쓸 수 있으면 `typeof`를 써라**
>
> `Type.GetType(string)`은 메타데이터를 문자열 검색한다. `typeof`는 IL의 `ldtoken` + `Type.GetTypeFromHandle` 한 쌍으로 컴파일되어 핸들을 직접 해석한다(56.6절에서 본 그대로다). 성능 차이가 크다 — 조회 비용의 자릿수가 다르다. 컴파일 타임에 타입을 안다면 문자열을 쓸 이유가 없다.

### `Type`과 `TypeInfo`

개념적으로 `Type`은 타입 **참조**(가벼운 핸들 — 이름과 신원만 있으면 된다)이고, `TypeInfo`는 타입 **정의**(멤버·플래그·기저 타입까지 아는 완전한 기술)다. `type.GetTypeInfo()`로 변환하고, `typeInfo.AsType()`으로 되돌린다. `TypeInfo`를 얻는 순간 CLR은 그 타입을 정의한 어셈블리가 로드되도록 **타입을 해석(resolve)** 한다 — 참조만 필요한데 정의를 요구하면 그만큼 비용이 든다.

> **📌 현대 .NET에서는 신경 쓰지 않아도 된다**
>
> .NET Core 1.x와 구형 Windows Store 프로필에서는 `Type`의 멤버 상당수가 없어서 `GetTypeInfo()`를 거쳐야 했다. .NET 5+에서 `TypeInfo`는 `Type`을 상속하고 `Type`에도 예전 멤버가 전부 돌아왔다. 새 코드에서 `GetTypeInfo()`를 부를 이유는 `DeclaredMembers` 계열의 `IEnumerable<T>` 반환 API를 쓰고 싶을 때뿐이다 — 이쪽이 LINQ와 잘 어울린다.

### 배열·중첩·포인터 타입 만들기와 되돌리기

원소 타입에서 배열 타입을 만들고, 다시 되돌릴 수 있다.

```csharp
Type simpleArrayType = typeof(int).MakeArrayType();
Console.WriteLine(simpleArrayType == typeof(int[]));   // True

Type cubeType = typeof(int).MakeArrayType(3);          // 3차원
Console.WriteLine(cubeType == typeof(int[,,]));        // True

Type e = typeof(int[]).GetElementType();               // typeof(int)
int rank = typeof(int[,,]).GetArrayRank();             // 3

// 중첩 타입 — System.Environment+SpecialFolder 가 출력된다
foreach (Type t in typeof(System.Environment).GetNestedTypes())
    Console.WriteLine(t.FullName);
```

`MakeByRefType`, `MakePointerType`, `MakeGenericType`도 같은 계열이다.

> **⚠️ 중첩 타입의 `IsPublic`은 `false`다**
>
> CLR은 중첩 타입에 별도의 "중첩 접근성" 등급을 매긴다. `public`으로 선언한 중첩 타입도 `IsPublic`은 `false`이고, `IsNestedPublic`이 `true`다.
>
> ```csharp
> Type t = typeof(System.Environment.SpecialFolder);
> Console.WriteLine(t.IsPublic);        // False
> Console.WriteLine(t.IsNestedPublic);  // True
> ```
>
> "public 타입만 걸러내자"는 필터를 `IsPublic`으로만 짜면 중첩된 public 타입이 조용히 빠진다. `t.IsPublic || t.IsNestedPublic`이거나, 어셈블리 수준이라면 `Assembly.ExportedTypes`를 쓰는 편이 낫다.

### 타입 이름 규칙 — 두 가지 예외와 세 가지 접미사

`Type`은 `Namespace`, `Name`, `FullName` 세 프로퍼티를 갖고, 보통 `FullName`은 앞의 둘을 이은 것이다.

```csharp
Type t = typeof(System.Text.StringBuilder);
t.Namespace;   // System.Text
t.Name;        // StringBuilder
t.FullName;    // System.Text.StringBuilder
```

`FullName`이 `Namespace` + `Name`의 단순 결합이 **아닌** 진짜 예외는 둘 — 중첩 타입과 닫힌 제네릭 타입 — 이다. 나머지 셋은 이름 자체에 붙는 접미사 규칙이다. 리플렉션 코드가 문자열로 타입을 다룰 때 사고가 나는 지점이 전부 이 표 안에 있다.

| 구분 | `Name` | `FullName` | 표기 규칙 |
|---|---|---|---|
| 중첩 타입 | `SpecialFolder` | `System.Environment+SpecialFolder` | 바깥 타입과 `+`로 구분 |
| 언바운드 제네릭 | ``Dictionary`2`` | ``System.Collections.Generic.Dictionary`2`` | 백틱 + 타입 매개변수 **개수** |
| 닫힌 제네릭 | ``Dictionary`2`` | 백틱 뒤에 `[[각 인수의 어셈블리 정규화 이름]]` | 인수까지 완전 식별 |
| 배열 | `Int32[]`, `Int32[,]` | `System.Int32[,]` | `typeof` 표기와 동일 |
| 포인터 / `ref`·`out` | `Byte*` / `Int32&` | 동일 | `*`는 포인터, `&`는 참조 전달 |

닫힌 제네릭의 `FullName`이 얼마나 길어지는지 직접 보자.

```csharp
Console.WriteLine(typeof(Dictionary<int, string>).FullName);
```

```text
System.Collections.Generic.Dictionary`2[[System.Int32, System.Private.CoreLib,
Version=8.0.0.0, Culture=neutral, PublicKeyToken=7cec85d7bea7798e],[System.String,
System.Private.CoreLib, Version=8.0.0.0, Culture=neutral,
PublicKeyToken=7cec85d7bea7798e]]
```

이렇게까지 하는 이유는 `AssemblyQualifiedName`(= `FullName` + `, ` + 어셈블리 전체 이름)만으로 제네릭 타입과 그 타입 인수를 **전부** 식별할 수 있어야 하기 때문이다. 이 문자열을 그대로 `Type.GetType`에 넘기면 같은 타입이 나온다.

`ref`/`out` 매개변수의 `&` 접미사는 실제로 이렇게 관찰된다.

```csharp
public void RefMethod(ref int p)
{
    Type t = MethodInfo.GetCurrentMethod().GetParameters()[0].ParameterType;
    Console.WriteLine(t.Name);      // Int32&
}
```

> **📌 타입 이름 문법에는 공식 BNF가 있다**
>
> Microsoft는 리플렉션 메서드에 넘길 타입 이름과 어셈블리 정규화 타입 이름의 **Backus-Naur Form 문법**을 정의해 두었다. 중첩 타입·제네릭 타입·제네릭 메서드·참조 매개변수·배열을 문자열로 조합해야 한다면 이 문법을 찾아보는 편이 빠르다. 문자열을 손으로 조립하는 대신 `MakeArrayType` / `MakeByRefType` / `MakeGenericType` / `MakePointerType`을 쓰면 실수가 줄어든다.

> **⚠️ 어셈블리 정규화 이름은 "기본 로딩 컨텍스트 안에서만" 유일하다**
>
> `AssemblyQualifiedName`이 타입을 유일하게 식별한다는 말은 **기본 ALC 안에서** 성립한다. 52.9절에서 봤듯 같은 어셈블리를 서로 다른 ALC에 로드하면 동일한 정규화 이름을 가진 **서로 호환되지 않는** 두 타입이 생긴다. 플러그인 호스트에서 타입을 문자열로 캐싱하면 이 지점에서 `InvalidCastException`이 난다.

## 57.2 기본 타입과 인터페이스 조회

### 상속 계보 따라가기

```csharp
Type base1 = typeof(System.String).BaseType;        // Object
Type base2 = typeof(System.IO.FileStream).BaseType; // Stream
```

`object`의 `BaseType`은 `null`이고, 인터페이스의 `BaseType`도 `null`이다. 계보를 끝까지 훑는 관용구는 `for (Type? cur = t; cur != null; cur = cur.BaseType)`이다.

`GetInterfaces`는 구현하는 인터페이스를 돌려준다. `typeof(Guid).GetInterfaces()`는 `IFormattable`, `IComparable`, ``IComparable`1``, ``IEquatable`1``, `ISpanFormattable` 등을 준다.

> **⚠️ `GetInterfaces`는 "직접 구현한 것"만 주지 않는다**
>
> **평탄화된 전체 집합**을 돌려준다 — 기저 클래스가 구현한 인터페이스, 인터페이스가 상속한 인터페이스가 전부 포함된다. "직접 선언한 것만" 필요하다면 기저 타입과 상위 인터페이스의 결과를 빼야 한다.
>
> ```csharp
> var direct = t.GetInterfaces()
>               .Except(t.BaseType?.GetInterfaces() ?? Type.EmptyTypes)
>               .Except(t.GetInterfaces().SelectMany(i => i.GetInterfaces()));
> ```
>
> 그리고 반환 순서는 **정의되어 있지 않다.** 순서에 의존하는 코드는 런타임 업그레이드에서 깨진다.

`GetInterfaceMap`은 인터페이스의 각 멤버가 클래스/구조체의 어떤 멤버로 구현되었는지를 알려주는 구조체를 돌려준다. 명시적 구현을 찾아내는 유일한 일반적 수단이며, 57.9절에서 정적 추상 인터페이스 멤버를 호출할 때 결정적으로 쓴다.

### `is`의 동적 대응물 셋

C#의 정적 `is` 연산자에 대응하는 리플렉션 API는 셋이다 — `IsInstanceOfType`, `IsAssignableFrom`, 그리고 .NET 5의 `IsAssignableTo`. 인터페이스를 제외하는 `IsSubclassOf`까지 함께 정리하면 이렇다.

| API | 인수 | 의미 |
|---|---|---|
| `Type.IsInstanceOfType(object)` | 타입 + 인스턴스 | `obj is T`와 동등 |
| `Type.IsAssignableFrom(Type)` | 타입 + 타입 | "이 타입 변수에 저 타입 값을 넣을 수 있나" |
| `Type.IsAssignableTo(Type)` ※.NET 5 | 타입 + 타입 | `IsAssignableFrom`의 방향 반대 |
| `Type.IsSubclassOf(Type)` | 타입 + 타입 | 클래스 상속만. **인터페이스는 제외** |

```csharp
object obj = Guid.NewGuid();
Type target = typeof(IFormattable);

bool isTrue   = obj is IFormattable;            // 정적 연산자
bool alsoTrue = target.IsInstanceOfType(obj);   // 동적 대응물

Type src = typeof(string);
Console.WriteLine(typeof(IComparable).IsAssignableFrom(src));   // True
Console.WriteLine(src.IsAssignableTo(typeof(IComparable)));     // True (.NET 5+)
```

> **⚠️ 세 가지 함정**
>
> 1. **`IsSubclassOf`는 인터페이스를 보지 않는다.** `typeof(string).IsSubclassOf(typeof(IComparable))`은 `false`다. 인터페이스까지 포함하려면 `IsAssignableFrom`을 써라.
> 2. **언바운드 제네릭에는 통하지 않는다.** `typeof(IEnumerable<>).IsAssignableFrom(typeof(List<int>))`은 `false`다 — `List<int>`가 구현하는 것은 `IEnumerable<int>`이지 `IEnumerable<>`이 아니다. 정석 해법은 57.8절에 있다.
> 3. **`Nullable<T>`가 개입하면 직관이 깨진다.** `typeof(int).IsAssignableFrom(typeof(int?))`은 `false`다.
>
> 그리고 두 타입이 **서로 다른 ALC에서 온 동명 타입**이면 당연히 `false`다. 플러그인 호스트에서 "인터페이스를 구현하는데 왜 안 걸리지"라는 증상은 거의 항상 이것이다(52.9절).

> **💡 타입 필터의 표준형**
>
> 플러그인·DI 컨테이너·테스트 러너가 "이 인터페이스를 구현하는 구체 타입"을 찾을 때의 관용구는 다음과 같다. 추상 클래스와 인터페이스 자신을 반드시 빼야 한다.
>
> ```csharp
> var impls = assembly.GetTypes()
>     .Where(t => t.IsClass
>              && !t.IsAbstract
>              && !t.IsGenericTypeDefinition
>              && typeof(IPlugin).IsAssignableFrom(t));
> ```

## 57.3 타입 인스턴스화 — `Activator`, 생성자 호출

타입에서 객체를 동적으로 만드는 방법은 둘이다.

1. 정적 `Activator.CreateInstance` 호출
2. `Type.GetConstructor`로 얻은 `ConstructorInfo`에 `Invoke` 호출 (고급)

### `Activator.CreateInstance`

```csharp
int i = (int) Activator.CreateInstance(typeof(int));
DateTime dt = (DateTime) Activator.CreateInstance(typeof(DateTime), 2000, 1, 1);
```

`CreateInstance`는 `Type`과 생성자에 넘길 인수를 받는다. 오버로드에 따라 타입을 로드할 어셈블리, 비공개 생성자에 바인딩할지 여부 등도 지정할 수 있다. 적당한 생성자를 못 찾으면 `MissingMethodException`을 던진다. 제네릭 오버로드 `Activator.CreateInstance<T>()`는 `T`의 매개변수 없는 public 생성자를 부르며 `new()` 제약과 짝을 이룬다.

> **⚠️ 예외가 두 겹으로 싸인다**
>
> 생성자 본문에서 예외가 나면 `Activator.CreateInstance`는 그것을 **`TargetInvocationException`으로 감싸서** 던진다. 진짜 원인은 `InnerException`에 있다. `catch (ArgumentException)`으로 잡으려던 코드가 아무것도 못 잡고 통과하는 사고가 여기서 난다.
>
> 반면 **인수 타입이 맞지 않아 생성자를 고르지 못한 경우**는 감싸지 않고 `MissingMethodException`이나 `ArgumentException`이 바로 나온다. 즉 "생성자에 도달하기 전 실패"와 "생성자 안에서 실패"의 예외 모양이 다르다.
>
> .NET Core 2.1+에서는 `BindingFlags.DoNotWrapExceptions`를 넘겨 감싸기를 끌 수 있다(단, 이 플래그를 받는 오버로드에서만).

> **📌 동적 생성은 마이크로초 단위 비용이다**
>
> 동적 인스턴스화는 객체 생성 시간에 수 마이크로초를 더한다. 상대적으로는 아주 큰 값이다 — 작은 클래스에 대한 단순 `new`는 수십 나노초 영역이다(54.3절). **동적 생성은 정적 생성보다 두세 자릿수 느리다.** 루프 안에서는 쓰지 마라 — 대안은 57.13절이다.

### `ConstructorInfo`가 필요한 경우

인수 값만으로 오버로드를 구분할 수 없을 때는 `ConstructorInfo`를 직접 골라야 한다. 클래스 `X`에 `string`을 받는 생성자와 `StringBuilder`를 받는 생성자가 있고 `null`을 넘기고 싶다고 하자. `Activator.CreateInstance(typeof(X), null)`은 대상이 모호하다.

```csharp
// string 하나를 받는 생성자를 명시적으로 가져온다
ConstructorInfo ci = typeof(X).GetConstructor(new[] { typeof(string) });

// 그 오버로드로 null을 넘겨 생성한다
object foo = ci.Invoke(new object[] { null });
```

`ref`/`out` 매개변수를 받는 생성자도 같은 방식이다. 매개변수 타입은 `&` 접미사를 가진 by-ref 타입이다.

```csharp
// public SomeType(ref int x) { x *= 2; }
Type ctorArg = typeof(int).MakeByRefType();   // 또는 Type.GetType("System.Int32&")
ConstructorInfo ctor = typeof(SomeType).GetConstructors()
    .First(c => c.GetParameters()[0].ParameterType == ctorArg);

object[] args = { 12 };
object obj = ctor.Invoke(args);
Console.WriteLine(args[0]);     // 24 — 인수 배열의 원소가 갱신되어 돌아온다
```

by-ref 인수의 결과는 **인수 배열의 해당 원소에 되쓰인다.** 이 규칙은 메서드 호출에도 그대로 적용된다(57.6절).

비공개 생성자를 부르려면 `BindingFlags`가 필요하다(57.7절).

### 델리게이트를 동적으로 만들기

`Delegate.CreateDelegate`는 인스턴스 델리게이트와 정적 델리게이트 양쪽을 만들 수 있다.

```csharp
delegate int IntFunc(int x);

static int Square(int x) => x * x;      // 정적 메서드
int Cube(int x) => x * x * x;           // 인스턴스 메서드

Delegate staticD = Delegate.CreateDelegate(
    typeof(IntFunc), typeof(Program), "Square");
Delegate instanceD = Delegate.CreateDelegate(
    typeof(IntFunc), new Program(), "Cube");

Console.WriteLine(staticD.DynamicInvoke(3));     // 9
Console.WriteLine(instanceD.DynamicInvoke(3));   // 27
```

`DynamicInvoke`로 부를 수도 있지만, **강타입 델리게이트로 캐스팅해서 부르는 편이 훨씬 빠르다.**

```csharp
IntFunc f = (IntFunc) staticD;
Console.WriteLine(f(3));      // 9 — 그러나 훨씬 빠르다
```

메서드 이름 문자열 대신 `MethodInfo`를 넘길 수도 있다. 이것이 57.13절에서 리플렉션을 델리게이트로 대체하는 전략의 뿌리다.

> **💡 `Activator`가 느린 이유와 우회로**
>
> `Activator.CreateInstance(Type)`는 매번 생성자를 탐색하고 접근성을 검사한다. 같은 타입을 반복해서 만든다면 **컴파일된 팩터리 델리게이트**(`Expression.New(ctor)` → `Compile()`, 57.13절), **`ConstructorInvoker.Create(ci)` 캐싱**(※.NET 8), 또는 **제네릭 오버로드 `Activator.CreateInstance<T>()`** 를 써라.
>
> `RuntimeHelpers.GetUninitializedObject`는 생성자를 **건너뛰고** 객체를 만든다 — 직렬화 라이브러리가 쓰는 방식이며, 필드 초기화가 되지 않은 객체가 나오므로 일반 코드에서는 쓰면 안 된다.

## 57.4 제네릭 타입 리플렉션

`Type`은 **닫힌(closed)** 제네릭 타입과 **언바운드(unbound)** 제네릭 타입을 모두 표현할 수 있다. 컴파일 타임과 마찬가지로 닫힌 타입은 인스턴스화할 수 있고 언바운드 타입은 할 수 없다.

```csharp
Type closed = typeof(List<int>);
List<int> list = (List<int>) Activator.CreateInstance(closed);   // OK

Type unbound = typeof(List<>);
object anError = Activator.CreateInstance(unbound);              // 런타임 오류
```

### 닫기와 열기

```csharp
Type unbound = typeof(List<>);
Type closed = unbound.MakeGenericType(typeof(int));      // List<int>
Type unbound2 = closed.GetGenericTypeDefinition();       // List<> (unbound와 동일)
```

관련 프로퍼티는 다음과 같다.

| 멤버 | 의미 |
|---|---|
| `IsGenericType` | 제네릭 타입인가 (닫힌 것도 언바운드도 `true`) |
| `IsGenericTypeDefinition` | 언바운드인가 (`typeof(List<>)`만 `true`) |
| `IsConstructedGenericType` | 닫힌 제네릭인가 |
| `IsGenericParameter` | 이 `Type`이 `T` 같은 **자리 표시자**인가 |
| `GetGenericArguments()` | 닫힌 타입이면 실제 타입 인수, 언바운드면 자리 표시자 |
| `GetGenericTypeDefinition()` | 닫힌 타입 → 언바운드 |
| `MakeGenericType(...)` | 언바운드 → 닫힌 타입 |

널 가능 값 타입 판별의 정석은 이것이다.

```csharp
Type nullable = typeof(bool?);
bool isNullable = nullable.IsGenericType
    && nullable.GetGenericTypeDefinition() == typeof(Nullable<>);   // True
```

실무에서는 `Nullable.GetUnderlyingType(t) != null`을 더 자주 쓴다. 같은 판정을 한 줄로 한다.

```csharp
Console.WriteLine(typeof(List<int>).GetGenericArguments()[0]);   // System.Int32
Console.WriteLine(typeof(bool?).GetGenericArguments()[0]);       // System.Boolean
Console.WriteLine(typeof(List<>).GetGenericArguments()[0]);      // T
```

언바운드 타입의 `GetGenericArguments`가 돌려주는 것은 **의사 타입(pseudotype)** 이다. 이름은 `T`이고 `IsGenericParameter`가 `true`이며, 여기에 대고 인스턴스를 만들 수는 없다.

> **📌 런타임에 "열린" 제네릭 타입은 없다**
>
> 런타임에 모든 제네릭 타입은 **언바운드거나 닫혀 있다.** `typeof(Foo<>)` 같은 (비교적 드문) 표현식에서만 언바운드가 나오고, 그 외에는 전부 닫혀 있다. 컴파일러가 모든 열린 타입을 닫아준다. 그래서 다음 클래스의 메서드는 **항상 `False`를 출력한다.**
>
> ```csharp
> class Foo<T>
> {
>     public void Test() => Console.Write(GetType().IsGenericTypeDefinition);
> }
> ```
>
> `new Foo<int>().Test()`는 `Foo<int>`의 `Type`을 보고, 그것은 닫힌 타입이다.

### 제네릭 타입의 멤버

언바운드 타입과 닫힌 타입 양쪽에서 멤버 메타데이터를 얻을 수 있지만, **얻어지는 객체는 항상 서로 다르다.**

```csharp
PropertyInfo unbound = typeof(IEnumerator<>).GetProperty("Current");
PropertyInfo closed  = typeof(IEnumerator<int>).GetProperty("Current");

Console.WriteLine(unbound);      // T Current
Console.WriteLine(closed);       // Int32 Current

Console.WriteLine(unbound.PropertyType.IsGenericParameter);   // True
Console.WriteLine(closed.PropertyType.IsGenericParameter);    // False
```

시그니처에 타입 매개변수가 전혀 없는 멤버도 마찬가지다. `typeof(List<>).GetProperty("Count")`와 `typeof(List<int>).GetProperty("Count")`는 둘 다 `Int32 Count`를 기술하지만 `==` 비교는 `False`다.

> **⚠️ 언바운드 제네릭 타입의 멤버는 동적으로 호출할 수 없다**
>
> `typeof(List<>).GetProperty("Count").GetValue(someList)`는 실패한다. 호출하려면 먼저 `MakeGenericType`으로 닫아야 한다. 이 규칙 때문에 "런타임에 어떤 `IGrouping<,>`의 `Key`를 읽는다" 같은 요구가 까다로워진다 — 57.8절이 그 문제를 정면으로 다룬다.

> **⚠️ Native AOT에서 `MakeGenericType`은 실패할 수 있다**
>
> `MakeGenericType`으로 **값 타입** 인수를 가진 새 인스턴스화를 만들면, CLR은 그 인스턴스화 전용 코드를 새로 JIT해야 한다(54.1절에서 본, 값 타입마다 별도 `MethodTable`이 생기는 이유). Native AOT에는 JIT이 없으므로 게시 시점에 존재하지 않던 인스턴스화는 만들 수 없고, 런타임에 예외가 난다.
>
> 참조 타입 인수는 공유 정규 코드(canonical code)를 쓰므로 대개 통과한다. 즉 **`MakeGenericType(typeof(string))`은 되고 `MakeGenericType(typeof(int))`은 안 되는** 비대칭이 생긴다. 이 지점은 57.14절에서 `[RequiresDynamicCode]`와 함께 다시 본다.

## 57.5 멤버 조회 — `MemberInfo` 계층, C# 멤버 vs CLR 멤버

### `GetMembers`가 실제로 돌려주는 것

```csharp
class Walnut
{
    private bool cracked;
    public void Crack() { cracked = true; }
}

foreach (MemberInfo m in typeof(Walnut).GetMembers())
    Console.WriteLine(m);
```

```text
Void Crack()
System.Type GetType()
System.String ToString()
Boolean Equals(System.Object)
Int32 GetHashCode()
Void .ctor()
```

인수 없는 `GetMembers()`는 **타입과 그 기저 타입의 모든 public 멤버**를 돌려준다. `object`에서 상속한 것도 전부 들어 있고, 기본 생성자 `.ctor`도 멤버다. 반면 `private bool cracked`는 없다 — 기본값이 public만 보기 때문이다.

`TypeInfo`의 `DeclaredMembers`는 다른 프로토콜을 쓴다. 배열 대신 `IEnumerable<MemberInfo>`를 돌려주고, **상속 멤버를 제외한다.** `typeof(Walnut).GetTypeInfo().DeclaredMembers`는 `Void Crack()`, `Void .ctor()`, `Boolean cracked` 셋을 준다 — 비공개 필드가 나오고 `object`의 멤버가 빠진다. `DeclaredProperties`, `DeclaredMethods` 같은 종류별 프로퍼티와 `GetDeclaredMethod` 같은 이름 조회 메서드도 있다. 후자는 오버로드된 메서드에 쓸 수 없으므로(매개변수 타입을 지정할 방법이 없다) LINQ 질의를 쓴다.

```csharp
MethodInfo method = typeof(int).GetTypeInfo().DeclaredMethods
    .FirstOrDefault(m => m.Name == "ToString" && m.GetParameters().Length == 0);
```

### `MemberInfo` 계층

```text
System.Object
   │
   └─ System.Reflection.MemberInfo               (abstract)
        │
        ├─ System.Type                           (abstract) ← 중첩 타입도 "멤버"다
        │    └─ System.Reflection.TypeInfo       (abstract)
        │         └─ RuntimeType                 (internal, CLR 구현체)
        │
        ├─ System.Reflection.FieldInfo           (abstract)
        │
        ├─ System.Reflection.MethodBase          (abstract)
        │    ├─ System.Reflection.ConstructorInfo
        │    └─ System.Reflection.MethodInfo
        │
        ├─ System.Reflection.PropertyInfo        (abstract)
        │
        └─ System.Reflection.EventInfo           (abstract)

  ※ System.Reflection.ParameterInfo 는 MemberInfo 를 상속하지 않는다 —
     매개변수는 CLR에서 "멤버"가 아니라 멤버 시그니처의 일부다.
```

`Type`이 `MemberInfo`를 상속한다는 사실이 처음에는 이상해 보이지만, **중첩 타입이 바깥 타입의 멤버**이기 때문에 필연적이다. `MemberInfo.MemberType`은 `MemberTypes` 플래그 열거형이고 값은 다음과 같다.

```text
All   Constructor   Custom   Event   Field   Method   NestedType   Property   TypeInfo
```

`GetMembers`에 `MemberTypes`를 넘겨 종류를 제한할 수도 있고, `GetMethods` / `GetFields` / `GetProperties` / `GetEvents` / `GetConstructors` / `GetNestedTypes`로 처음부터 좁혀도 된다. 각각 단수형(`GetMethod`, `GetField`, ...)이 있다.

### 리플렉션 객체 모델 전체 지도

```text
ALC ─┬─ Assembly ─┬─ Module ─┬─ TypeInfo ─┬─ FieldInfo
     │            │          │            ├─ ConstructorInfo
     │            │          │            ├─ MethodInfo ─┬─ ParameterInfo[]
     │            │          │            │              └─ ReturnParameter
     │            │          │            ├─ PropertyInfo ─ get/set MethodInfo
     │            │          │            ├─ EventInfo ──── add/remove MethodInfo
     │            │          │            └─ (중첩) TypeInfo
     │            │          └─ TypeInfo ...
     │            └─ Module ...     ※ 다중 모듈은 .NET Framework 전용
     └─ Assembly ...

  어느 노드에서든 GetCustomAttributes() 로 특성 집합을 얻을 수 있다.
```

> **📌 네임스페이스는 이 계층에 없다**
>
> 네임스페이스는 타입을 문법적으로 묶는 장치일 뿐 CLR의 실체가 아니다. 어셈블리에 정의된 네임스페이스 목록을 얻으려면 모든 타입을 열거해 `Namespace` 프로퍼티를 모아야 한다 — `asm.GetTypes().Select(t => t.Namespace).Distinct()`.

### `DeclaringType` vs `ReflectedType`

`MemberInfo`에는 `Name` 외에 `Type` 프로퍼티가 둘 있다.

- **`DeclaringType`** — 그 멤버를 **정의한** 타입
- **`ReflectedType`** — `GetMembers`를 **호출한** 타입

기저 타입에서 정의된 멤버를 파생 타입으로 조회하면 둘이 갈라진다.

```csharp
MethodInfo test = typeof(Program).GetMethod("ToString");
MethodInfo obj  = typeof(object) .GetMethod("ToString");

Console.WriteLine(test.DeclaringType);   // System.Object
Console.WriteLine(obj.DeclaringType);    // System.Object
Console.WriteLine(test.ReflectedType);   // Program
Console.WriteLine(obj.ReflectedType);    // System.Object
Console.WriteLine(test == obj);          // False
```

> **⚠️ 같은 메서드인데 `MethodInfo`가 다르다**
>
> `test`와 `obj`는 `ReflectedType`이 다르므로 **같지 않다.** 하지만 이 차이는 순전히 리플렉션 API의 조작이다 — 밑바닥 타입 시스템에 `Program.ToString`이라는 별개의 메서드는 없다. 두 객체가 같은 메서드를 가리키는지는 `test.MethodHandle == obj.MethodHandle`(프로세스 안에서 메서드마다 유일)이나 `test.MetadataToken == obj.MetadataToken && test.Module == obj.Module`(모듈 안의 모든 타입·멤버에 걸쳐 유일)로 확인한다. 둘 다 `True`다.
>
> 이 함정은 실무에서 `MethodInfo`를 `Dictionary` 키로 쓸 때 터진다. 조회 경로가 다르면 같은 메서드에 두 개의 캐시 항목이 생긴다. 키로는 `MethodHandle`이나 `(MetadataToken, Module)` 쌍을 써라.

모든 `*Info` 인스턴스는 리플렉션 API가 **첫 사용 시 캐싱한다.** 같은 경로로 두 번 조회하면 같은 객체가 나온다.

```csharp
MethodInfo method = typeof(Walnut).GetMethod("Crack");
MemberInfo member = typeof(Walnut).GetMember("Crack")[0];
Console.WriteLine(method == member);     // True
```

캐싱은 객체 신원을 보존할 뿐 아니라, 원래 느린 이 API의 성능을 그나마 지켜준다.

> **📌 현재 실행 중인 메서드 얻기**
>
> `MethodBase.GetCurrentMethod()`는 지금 실행 중인 메서드의 `MethodBase`를 돌려준다. 로깅에 쓰고 싶은 유혹이 있지만, 스택 워크가 필요해 느리고 인라이닝에 취약하다. 메서드 이름만 필요하면 `[CallerMemberName]`(20.11절)이 컴파일 타임에 문자열을 박아 넣으므로 비교할 수 없이 낫다.

### C# 멤버 vs CLR 멤버 — 대응이 1:1이 아니다

C#의 여러 구문 요소는 CLR 입장에서 **꾸며낸 것(contrivance)** 이다. CLR과 리플렉션 API는 모든 .NET 언어를 염두에 두고 설계되었기 때문이다.

| C# 구문 | 사용할 메서드 | 넘길 이름 | 결과 타입 |
|---|---|---|---|
| 메서드 | `GetMethod` | (메서드 이름) | `MethodInfo` |
| 프로퍼티 | `GetProperty` | (프로퍼티 이름) | `PropertyInfo` |
| 인덱서 | `GetDefaultMembers` | — | `MemberInfo[]` (C# 컴파일이면 `PropertyInfo`) |
| 필드 | `GetField` | (필드 이름) | `FieldInfo` |
| 열거형 멤버 | `GetField` | (멤버 이름) | `FieldInfo` |
| 이벤트 | `GetEvent` | (이벤트 이름) | `EventInfo` |
| 생성자 | `GetConstructor` | — | `ConstructorInfo` |
| 종료자 | `GetMethod` | `"Finalize"` | `MethodInfo` |
| 연산자 | `GetMethod` | `"op_" + 연산자 이름` | `MethodInfo` |
| 중첩 타입 | `GetNestedType` | (타입 이름) | `Type` |

구체적으로 이렇게 번역된다.

- **인덱서** → 인수를 하나 이상 받는 프로퍼티. 타입에 `[DefaultMember]` 특성이 붙고, C# 컴파일러가 붙이는 기본 이름은 `Item`이다.
- **열거형** → `System.Enum`의 서브타입. 각 멤버는 정적 필드다.
- **연산자** → `op_`로 시작하는 특별한 이름의 정적 메서드. 예: `op_Addition`, `op_Implicit`, `op_Equality`.
- **종료자** → `Finalize`를 재정의하는 메서드.

### 프로퍼티와 이벤트는 "둘"이다

프로퍼티와 이벤트는 사실 두 가지로 구성된다.

1. 프로퍼티/이벤트를 기술하는 **메타데이터** (`PropertyInfo` / `EventInfo`)
2. 하나 또는 두 개의 **백킹 메서드**

C# 소스에서는 백킹 메서드가 프로퍼티 정의 안에 감싸여 있지만, IL로 컴파일되면 **평범한 메서드**로 나타난다(56.6절에서 IL을 직접 봤다). 그래서 `GetMethods`는 백킹 메서드까지 함께 돌려준다.

```csharp
class Test { public int X { get { return 0; } set {} } }

foreach (MethodInfo mi in typeof(Test).GetMethods())
    Console.Write(mi.Name + " ");
// 출력: get_X set_X GetType ToString Equals GetHashCode
```

C# 컴파일러가 생성하는 백킹 메서드의 이름 규칙은 다음과 같다.

| C# 구문 | 멤버 타입 | IL의 메서드 이름 |
|---|---|---|
| 프로퍼티 `XXX` | `Property` | `get_XXX`, `set_XXX` |
| 인덱서 | `Property` | `get_Item`, `set_Item` |
| 이벤트 `XXX` | `Event` | `add_XXX`, `remove_XXX` |
| 연산자 `+` | (메서드) | `op_Addition` |
| 종료자 | (메서드) | `Finalize` |

이 메서드들은 `MethodInfo.IsSpecialName`이 `true`다. `IsSpecialName`은 프로퍼티·인덱서·이벤트 접근자와 연산자에 대해 `true`이고, **평범한 C# 메서드와 `Finalize`에 대해서만 `false`** 다.

프로퍼티/이벤트 ↔ 메서드 사이의 이동은 이렇게 한다.

```csharp
PropertyInfo pi = typeof(Console).GetProperty("Title");
MethodInfo getter = pi.GetGetMethod();     // get_Title
MethodInfo setter = pi.GetSetMethod();     // set_Title
MethodInfo[] both = pi.GetAccessors();     // Length == 2
```

`EventInfo`는 `GetAddMethod`, `GetRemoveMethod`가 같은 일을 한다. 반대 방향 — `MethodInfo`에서 `PropertyInfo`로 — 는 API가 없으므로 질의해야 한다.

```csharp
PropertyInfo p = mi.DeclaringType.GetProperties()
    .First(x => x.GetAccessors(true).Contains(mi));
```

> **⚠️ "메서드 목록"을 사용자에게 보여주는 코드는 대부분 틀렸다**
>
> `GetMethods()`를 그대로 출력하면 `get_X`, `set_X`, `add_Y`, `op_Addition` 같은 것이 줄줄이 섞여 나온다. 코드 생성기·문서 도구·프록시 생성기를 만든다면 반드시 걸러야 한다.
>
> ```csharp
> var realMethods = t.GetMethods()
>     .Where(m => !m.IsSpecialName);      // 접근자와 연산자 제외
> ```
>
> 반대로 **동적 프록시**를 만든다면 접근자도 재정의해야 하므로 걸러내면 안 된다. 어느 쪽인지 먼저 정하고 코드를 짜라.

### `init` 전용 프로퍼티 판별 ※C# 9

**CLR 입장에서 `init` 접근자는 평범한 `set` 접근자와 동일하다.** 차이는 `set` 메서드의 반환 타입에 붙은 플래그뿐이고 그것은 컴파일러에게만 의미가 있다. 이 플래그는 특성이 아니라 **`modreq`(required custom modifier)** 로 인코딩되는데, 새 `modreq`를 모르는 **이전 버전의 C# 컴파일러가 그 접근자를 무시하게** 만들기 위해서다 — 프로퍼티를 쓰기 가능한 것으로 잘못 취급하지 않는다. `modreq`의 이름은 `IsExternalInit`이다.

```csharp
bool IsInitOnly(PropertyInfo pi) => pi
    .GetSetMethod()
    .ReturnParameter
    .GetRequiredCustomModifiers()
    .Any(t => t.Name == "IsExternalInit");
```

> **⚠️ 리플렉션은 `init` 전용 프로퍼티를 막지 않는다**
>
> `pi.SetValue(obj, value)`는 `init` 전용 프로퍼티에도 **성공한다** — CLR에게는 그냥 `set` 접근자다. 언어가 막는 것을 리플렉션은 막지 않는다. 직렬화 라이브러리가 이 성질을 쓴다.
>
> 그러나 `record`의 `init` 프로퍼티를 사후 변경하면 값 기반 `Equals`/`GetHashCode`와의 계약이 깨진다. 이미 `Dictionary`의 키로 쓰인 객체를 이렇게 수정하면 그 항목은 영원히 찾을 수 없게 된다.

### 널 허용 정보 읽기 ※.NET 6

.NET 6부터 `NullabilityInfoContext`로 필드·프로퍼티·이벤트·매개변수의 널 허용 주석을 읽을 수 있다.

```csharp
void PrintPropertyNullability(PropertyInfo pi)
{
    var info = new NullabilityInfoContext().Create(pi);
    Console.WriteLine(pi.Name + " read "  + info.ReadState);
    Console.WriteLine(pi.Name + " write " + info.WriteState);
    // info.Element 로 배열 원소의 널 허용 정보를 얻는다
}
```

`ReadState`와 `WriteState`는 `NullabilityState` 열거형(`NotNull`, `Nullable`, `Unknown`)이다. `string?`과 `string`은 런타임에 **같은 타입**이고 널 허용 주석은 특성으로만 인코딩되므로, 이 API 없이는 특성 바이트를 직접 해석해야 한다.

> **⚠️ 널 허용 컨텍스트가 꺼진 어셈블리는 `Unknown`이다**
>
> `<Nullable>disable</Nullable>`로 컴파일된 멤버는 전부 `Unknown`을 돌려준다. 유효성 검사기를 이 위에 짓는다면 `Unknown`을 "널 허용"으로 볼지 "널 불가"로 볼지 반드시 명시적으로 정해야 한다.

## 57.6 멤버 동적 호출과 메서드 매개변수

`MethodInfo`, `PropertyInfo`, `FieldInfo`를 손에 넣으면 그것을 동적으로 호출하거나 값을 읽고 쓸 수 있다. 컴파일 타임이 아니라 런타임에 어떤 멤버를 호출할지 정하므로 이를 **늦은 바인딩(late binding)** 이라고 한다.

정적 바인딩:

```csharp
string s = "Hello";
int length = s.Length;
```

같은 일을 늦은 바인딩으로:

```csharp
object s = "Hello";
PropertyInfo prop = s.GetType().GetProperty("Length");
int length = (int) prop.GetValue(s, null);      // 5
```

### 멤버 종류별 호출 방법

| 멤버 타입 | 호출 방법 |
|---|---|
| `FieldInfo` | `GetValue` / `SetValue` |
| `ConstructorInfo` | `Invoke` — 인스턴스를 만들고 생성자를 부른다 |
| `MethodInfo` | `Invoke` |
| `PropertyInfo` | `GetValue` / `SetValue` (내부적으로 접근자 `MethodInfo`를 호출) |
| `EventInfo` | `AddEventHandler` / `RemoveEventHandler` |

첫 인수는 인스턴스이고, 정적 멤버라면 `null`이다. 인덱서는 `"Item"`이라는 이름의 프로퍼티에 접근하는 것과 같되, `GetValue`/`SetValue`의 인덱스 인수 배열에 인덱서 값을 넘긴다.

`PropertyInfo`에는 `CanRead`, `CanWrite`, `PropertyType` 읽기 전용 프로퍼티가 있고, 접근자를 직접 주는 `GetMethod` / `SetMethod` 프로퍼티도 있다. `EventInfo`에는 이벤트의 델리게이트 타입을 주는 `EventHandlerType`과 `AddMethod` / `RemoveMethod`가 있다.

### 매개변수가 있는 메서드

`string.Substring`을 동적으로 부르는 예다.

```csharp
Type type = typeof(string);
Type[] parameterTypes = { typeof(int) };
MethodInfo method = type.GetMethod("Substring", parameterTypes);

object[] arguments = { 2 };
object returnValue = method.Invoke("stamp", arguments);
Console.WriteLine(returnValue);      // "amp"
```

`Substring`이 오버로드되어 있으므로 `GetMethod`에 매개변수 타입 배열을 넘겨 어느 것인지 알려야 한다. 안 넘기면 `AmbiguousMatchException`이 난다.

`MethodBase`(= `MethodInfo`와 `ConstructorInfo`의 기저 클래스)의 `GetParameters`는 매개변수 메타데이터를 준다.

```csharp
foreach (ParameterInfo x in method.GetParameters())
    Console.WriteLine($"{x.Position} {x.Name} {x.ParameterType} " +
                      $"optional={x.IsOptional} hasDefault={x.HasDefaultValue}");
// 출력: 0 startIndex System.Int32 optional=False hasDefault=False
```

반환 타입은 `MethodInfo.ReturnType`, 반환값의 메타데이터(특성·`modreq` 포함)는 `ReturnParameter`로 얻는다.

> **💡 조회는 가능한 한 구체적으로 하라**
>
> 메서드를 이름만으로 가져오면, 나중에 그 메서드에 오버로드가 추가되는 순간 코드가 `AmbiguousMatchException`으로 깨진다. **매개변수 타입을 전부 명시하면** 라이브러리가 진화해도 살아남는다. 이는 라이브러리 저자에게도 시사점이 있다 — 오버로드 추가는 소스 호환이지만 리플렉션 호환은 아니다.

### `ref` / `out` 매개변수 넘기기

`MakeByRefType`으로 by-ref 타입을 만들어 메서드를 찾고, 인수 배열을 넘긴 뒤 **그 배열을 다시 읽는다.**

```csharp
// int x;
// bool successfulParse = int.TryParse("23", out x);

object[] args = { "23", 0 };
Type[] argTypes = { typeof(string), typeof(int).MakeByRefType() };
MethodInfo tryParse = typeof(int).GetMethod("TryParse", argTypes);

bool successfulParse = (bool) tryParse.Invoke(null, args);
Console.WriteLine(successfulParse + " " + args[1]);      // True 23
```

`ref`와 `out` 모두 같은 방식이다. `Invoke`가 반환된 뒤 `args[1]`에 결과가 들어 있다는 것이 핵심이다.

> **⚠️ `Invoke`는 예외를 `TargetInvocationException`으로 감싼다**
>
> 대상 메서드가 던진 예외는 `TargetInvocationException`의 `InnerException`에 들어간다. 이것을 모르면 다음 코드가 조용히 실패한다.
>
> ```csharp
> try { pi.SetValue(obj, 0, null); }
> catch (ArgumentOutOfRangeException) { /* 절대 도달하지 않는다 */ }
> ```
>
> 올바른 형태:
>
> ```csharp
> catch (TargetInvocationException e)
>     when (e.InnerException is ArgumentOutOfRangeException) { ... }
> ```
>
> `BindingFlags.DoNotWrapExceptions`(.NET Core 2.1+)를 넘기면 감싸지 않는다. 다만 그러면 스택 트레이스가 호출 경계에서 잘린다 — 어느 쪽이든 트레이드오프가 있다.
>
> 참고로 **델리게이트를 통한 호출은 감싸지 않는다.** 57.13절의 컴파일된 델리게이트로 옮기면 이 문제 자체가 사라진다.

`Invoke`에서 나올 수 있는 예외를 정리하면 이렇다. 어떤 것이 나오는지는 실패 지점에 달렸다.

| 예외 | 언제 |
|---|---|
| `TargetInvocationException` | 대상 메서드 **본문**이 예외를 던졌다 |
| `TargetParameterCountException` | 인수 개수가 시그니처와 다르다 |
| `ArgumentException` | 인수 타입이 변환 불가능하다 |
| `TargetException` | 인스턴스 메서드에 `null`이나 엉뚱한 타입의 인스턴스를 넘겼다 |
| `MemberAccessException` 계열 | 접근 권한이 없다 (`MethodAccessException`, `FieldAccessException`) |
| `InvalidOperationException` | 언바운드 제네릭 정의를 호출하려 했다 |

### 이벤트 붙였다 떼기

```csharp
EventInfo ei = obj.GetType().GetEvent("SomeEvent");
EventHandler eh = new EventHandler(EventCallback);   // ei.EventHandlerType 참조
ei.AddEventHandler(obj, eh);
ei.RemoveEventHandler(obj, eh);
```

델리게이트 타입을 컴파일 타임에 모른다면 `Delegate.CreateDelegate(ei.EventHandlerType, target, methodInfo)`로 만들어 넘긴다. 내부적으로 이 두 메서드는 `AddMethod` / `RemoveMethod`를 호출하는 편의 래퍼다.

> **⚠️ 붙일 때 쓴 델리게이트를 반드시 보관하라**
>
> `AddEventHandler`에 넘긴 델리게이트와 **동등한** 델리게이트로만 `RemoveEventHandler`가 동작한다. 매번 새로 `Delegate.CreateDelegate`를 부르면 델리게이트 동등성(대상 + 메서드가 같으면 `Equals`가 `true`)에 기대게 되는데, 클로저가 끼면 그 동등성이 깨진다. 참조를 잃으면 구독이 남아 **메모리 누수**가 된다.

## 57.7 비공개 멤버 접근

메타데이터를 탐색하는 모든 메서드(`GetProperty`, `GetField`, `GetMethod`, `GetMembers` ...)에는 `BindingFlags` 열거형을 받는 오버로드가 있다. 이 열거형은 **메타데이터 필터**로서 기본 선택 기준을 바꾼다. 가장 흔한 용도가 비공개 멤버 조회다.

```csharp
class Walnut
{
    private bool cracked;
    public void Crack() { cracked = true; }
    public override string ToString() => cracked.ToString();
}
```

호두를 다시 붙여보자.

```csharp
Type t = typeof(Walnut);
Walnut w = new Walnut();
w.Crack();

FieldInfo f = t.GetField("cracked",
    BindingFlags.NonPublic | BindingFlags.Instance);
f.SetValue(w, false);

Console.WriteLine(w);      // False
```

### `BindingFlags` 조합표

`BindingFlags`는 비트 조합이다. **매치를 하나라도 얻으려면 다음 네 조합 중 하나로 시작해야 한다.**

```csharp
BindingFlags.Public    | BindingFlags.Instance
BindingFlags.Public    | BindingFlags.Static
BindingFlags.NonPublic | BindingFlags.Instance
BindingFlags.NonPublic | BindingFlags.Static
```

`NonPublic`은 `internal`, `protected`, `protected internal`, `private`, `private protected`를 전부 포함한다.

| 플래그 | 효과 | 결과 집합 |
|---|---|---|
| `Public` | public 멤버 포함 | 확대 |
| `NonPublic` | private/protected/internal 멤버 포함 | 확대 |
| `Instance` | 인스턴스 멤버 포함 | 확대 |
| `Static` | 정적 멤버 포함 | 확대 |
| `FlattenHierarchy` | **기저 타입의 정적 멤버**도 포함 | 확대 |
| `DeclaredOnly` | 기저 타입에서 상속한 멤버 **제외**(재정의한 것은 남음) | **축소** |
| `IgnoreCase` | 이름 비교를 대소문자 무시로 | 확대 |
| `ExactBinding` | 인수 타입의 암묵적 변환 없이 정확히 일치하는 것만 | 축소 |
| `DoNotWrapExceptions` | `Invoke`가 `TargetInvocationException`으로 감싸지 않음 | (호출 동작) |
| `InvokeMethod` / `GetProperty` / `SetProperty` / `GetField` / `SetField` / `CreateInstance` | `Type.InvokeMember`에서 어떤 연산인지 지정 | (호출 동작) |

> **⚠️ `DeclaredOnly`만 방향이 반대다**
>
> 다른 모든 플래그가 결과 집합을 **넓히는데** `DeclaredOnly`만 **좁힌다.** 플래그를 OR로 쌓으면 결과가 늘어난다는 직관이 여기서 깨진다.

### 인수 없는 기본값이 빠뜨리는 것

`GetMethods()`처럼 인수 없이 부르면 기본값은 `Public | Instance | Static`이다. 여기서 빠지는 것을 정확히 알아야 한다.

| 조회 대상 | `GetMethods()` 기본값 | 필요한 플래그 |
|---|---|---|
| public 인스턴스 메서드 (자신) | 포함 | — |
| public 인스턴스 메서드 (상속) | 포함 | — |
| public 정적 메서드 (자신) | 포함 | — |
| **public 정적 메서드 (기저 타입에서 상속)** | **빠진다** | `FlattenHierarchy` |
| **private / internal / protected 멤버 (자신)** | **빠진다** | `NonPublic` |
| **private 멤버 (기저 타입)** | **빠진다** | 어떤 플래그로도 안 됨 — 아래 참조 |
| 명시적 인터페이스 구현 | 빠진다 | `NonPublic` (이름이 `Ns.IFoo.Method` 형태) |
| 생성자 | 빠진다 | `GetConstructors`를 따로 호출 |

> **⚠️ 기저 타입의 private 멤버는 `NonPublic`으로도 나오지 않는다**
>
> `BindingFlags`의 가장 악명 높은 함정이다. `NonPublic | Instance`는 **그 타입이 직접 선언한** 비공개 멤버만 준다 — private 멤버는 애초에 파생 타입에서 보이지 않으므로 상속 개념 자체가 없다. 기저 타입의 private 필드까지 찾으려면 계보를 직접 걸어야 한다.
>
> ```csharp
> static FieldInfo? FindField(Type type, string name)
> {
>     const BindingFlags Flags =
>         BindingFlags.Instance | BindingFlags.Static |
>         BindingFlags.Public   | BindingFlags.NonPublic |
>         BindingFlags.DeclaredOnly;
>
>     for (Type? t = type; t != null; t = t.BaseType)
>     {
>         FieldInfo? f = t.GetField(name, Flags);
>         if (f != null) return f;
>     }
>     return null;
> }
> ```
>
> `DeclaredOnly`를 넣은 이유는 각 단계에서 중복 없이 그 타입만 보기 위해서다. 직렬화 라이브러리와 객체 복사기가 전부 이 모양의 루프를 갖고 있다.

> **⚠️ 명시적 인터페이스 구현은 이름이 다르다**
>
> `void IDisposable.Dispose()`를 명시적으로 구현하면 IL의 메서드 이름이 `System.IDisposable.Dispose`이고 접근성은 `private`이다. `GetMethod("Dispose")`로는 절대 찾을 수 없다. 그 전체 이름에 `NonPublic | Instance`를 넘겨 찾거나, **`t.GetInterfaceMap(typeof(IDisposable))`로 인터페이스 메서드 → 대상 메서드 매핑을 얻는 편**(권장 — 이름 규칙에 의존하지 않는다)이 낫다. 57.9절에서 이 기법을 본격적으로 쓴다.

### 위험성

비공개 멤버 접근은 강력하지만 캡슐화를 우회하고 **타입의 내부 구현에 관리 불가능한 의존성**을 만든다. 라이브러리 저자에게 private 필드 이름은 언제든 바꿀 수 있는 것이고, 실제로 바꾼다.

> **💡 정말 필요하다면 방어적으로 짜라**
>
> 조회 결과가 `null`인지 반드시 검사하고 **의미 있는 예외**를 던져라 — `NullReferenceException`이 열 프레임 뒤에서 터지는 것보다 낫다. 조회는 `static readonly` 필드에 캐싱해 런타임 중간이 아니라 **타입 초기화 시점에 실패**하게 만들어라.
>
> 그전에 대안을 확인하라. `InternalsVisibleTo`(52.2절)로 `internal`을 열어주면 리플렉션이 필요 없다. .NET 8 이상이라면 `[UnsafeAccessor]`(57.12절)가 낫다 — **런타임이 JIT 시점에 해석하므로 비용이 0이고 트리밍 분석기도 이해한다.**

> **⚠️ 코드 접근 보안(CAS)은 .NET Framework 전용이었다**
>
> .NET Framework에는 부분 신뢰 환경에서 리플렉션의 비공개 멤버 접근을 막는 CAS가 있었다. .NET Core / .NET 5+에는 **CAS가 없다** — `ReflectionPermission` 같은 타입은 남아 있지만 아무 일도 하지 않는다. 현대 .NET에서 리플렉션은 프로세스 안에서 무엇이든 열어볼 수 있다고 가정해야 한다. 신뢰 경계는 프로세스 경계지 타입 경계가 아니다.

## 57.8 제네릭 메서드와 제네릭 인터페이스 멤버의 익명 호출

### 제네릭 메서드는 닫아야 호출된다

제네릭 메서드를 직접 호출할 수는 없다.

```csharp
class Program
{
    public static T Echo<T>(T x) => x;

    static void Main()
    {
        MethodInfo echo = typeof(Program).GetMethod("Echo");
        Console.WriteLine(echo.IsGenericMethodDefinition);   // True
        echo.Invoke(null, new object[] { 123 });             // 예외
    }
}
```

`MakeGenericMethod`로 구체적 타입 인수를 지정해 닫아야 한다. 이 호출은 **또 다른 `MethodInfo`** 를 돌려주고, 그것을 호출한다.

```csharp
MethodInfo echo = typeof(Program).GetMethod("Echo");
MethodInfo intEcho = echo.MakeGenericMethod(typeof(int));

Console.WriteLine(intEcho.IsGenericMethodDefinition);        // False
Console.WriteLine(intEcho.Invoke(null, new object[] { 3 })); // 3
```

### 제네릭 오버로드 골라내기

`GetMethod`에 매개변수 타입을 명시하면 오버로드를 구분할 수 있다고 했지만, **제네릭 매개변수 타입은 명시할 수 없다.** `System.Linq.Enumerable`의 `Where`를 보자.

```csharp
public static IEnumerable<TSource> Where<TSource>(
    this IEnumerable<TSource> source, Func<TSource, bool> predicate);

public static IEnumerable<TSource> Where<TSource>(
    this IEnumerable<TSource> source, Func<TSource, int, bool> predicate);
```

특정 오버로드를 얻으려면 전부 가져와서 손으로 골라야 한다. 첫 번째 오버로드를 찾는 질의다.

```csharp
var unboundMethod = (
    from m in typeof(Enumerable).GetMethods()
    where m.Name == "Where" && m.IsGenericMethod
    let parameters = m.GetParameters()
    where parameters.Length == 2
    let genArg = m.GetGenericArguments().First()
    let enumerableOfT = typeof(IEnumerable<>).MakeGenericType(genArg)
    let funcOfTBool = typeof(Func<,>).MakeGenericType(genArg, typeof(bool))
    where parameters[0].ParameterType == enumerableOfT
       && parameters[1].ParameterType == funcOfTBool
    select m
).Single();
```

핵심은 **자리 표시자 `T`로 기대 시그니처를 조립해서 비교**하는 것이다. `genArg`는 `MethodInfo`가 가진 의사 타입이고, `MakeGenericType(genArg)`로 `IEnumerable<T>`를 만들면 실제 매개변수 타입과 참조 동등 비교가 성립한다.

이제 닫고 호출한다.

```csharp
var closedMethod = unboundMethod.MakeGenericMethod(typeof(int));

int[] source = { 3, 4, 5, 6, 7, 8 };
Func<int, bool> predicate = n => n % 2 == 1;

var query = (IEnumerable<int>) closedMethod.Invoke(
    null, new object[] { source, predicate });

foreach (int element in query) Console.Write(element + "|");    // 3|5|7|
```

> **💡 식 트리 API를 쓰면 이 고생이 필요 없다**
>
> `System.Linq.Expressions`로 식을 조립한다면 `Expression.Call`이 닫힌 타입 인수를 직접 받는 오버로드를 제공한다.
>
> ```csharp
> var sourceExpr = Expression.Constant(source);
> var predicateExpr = Expression.Constant(predicate);
> var callExpression = Expression.Call(
>     typeof(Enumerable), "Where",
>     new[] { typeof(int) },          // 닫힌 제네릭 인수 타입
>     sourceExpr, predicateExpr);
> ```
>
> 오버로드 해석은 인수 식의 타입으로 알아서 된다.

### 제네릭 인터페이스 멤버를 익명으로 호출하기

런타임까지 타입 인수를 모르는 상태에서 제네릭 인터페이스의 멤버를 불러야 할 때가 있다. LINQ 질의 결과를 임의 깊이로 풀어 출력하는 `ToStringEx(object value)`를 만든다고 하자. `ToStringEx<T>(IEnumerable<T>)`로 시작하면 중첩 컬렉션·그룹핑·프로젝션마다 오버로드가 늘어나 정적 해법이 실용성을 잃는다. 그래서 `object`를 받고 싶은데, 다음은 **컴파일되지 않는다.**

```csharp
if (value is List<>)                                           // 오류
    sb.Append("List of " + ((List<>) value).Count + " items");  // 오류

if (value is IGrouping<,>)                                     // 오류
    sb.Append("Group with key=" + ((IGrouping<,>) value).Key);  // 오류
```

**언바운드 제네릭 타입의 멤버는 호출할 수 없다**(57.4절).

`List<>`는 우회로가 있다. `List<T>`의 설계자가 제네릭 `IList<T>`뿐 아니라 고전 `IList`도 구현해 둔 덕분이다.

```csharp
if (value is IList)
    sb.AppendLine("A list with " + ((IList) value).Count + " items");
```

> **💡 비제네릭 폴백 인터페이스를 제공하라**
>
> 이 원칙은 자기 제네릭 타입을 설계할 때도 고려할 가치가 있다. **소비자가 기댈 수 있는 비제네릭 인터페이스나 기저 클래스**를 함께 제공하면 리플렉션 곡예를 크게 줄여준다. `IEnumerable<T> : IEnumerable`, `IList<T>`와 `IList`, `Task<T> : Task`가 전부 그 설계다.

`IGrouping<,>`은 그렇게 간단하지 않다.

```csharp
public interface IGrouping<TKey, TElement> : IEnumerable<TElement>, IEnumerable
{
    TKey Key { get; }
}
```

`Key`에 접근할 수 있는 비제네릭 타입이 없다. 여기서 리플렉션이 필요하다. **해법은 언바운드 제네릭 타입의 멤버를 호출하는 것(불가능)이 아니라, 런타임에 타입 인수가 확정된 닫힌 제네릭 타입의 멤버를 호출하는 것이다.**

```csharp
public static string ToStringEx(object value)
{
    if (value == null) return "<null>";
    if (value.GetType().IsPrimitive) return value.ToString();

    StringBuilder sb = new StringBuilder();

    if (value is IList)
        sb.Append("List of " + ((IList) value).Count + " items: ");

    // 이 객체가 구현하는 "닫힌" IGrouping<,> 을 찾는다
    Type closedIGrouping = value.GetType().GetInterfaces()
        .Where(t => t.IsGenericType &&
                    t.GetGenericTypeDefinition() == typeof(IGrouping<,>))
        .FirstOrDefault();

    if (closedIGrouping != null)
    {
        PropertyInfo pi = closedIGrouping.GetProperty("Key");
        object key = pi.GetValue(value, null);
        sb.Append("Group with key=" + key + ": ");
    }

    if (value is IEnumerable)
        foreach (object element in ((IEnumerable) value))
            sb.Append(ToStringEx(element) + " ");

    if (sb.Length == 0) sb.Append(value.ToString());

    return "\r\n" + sb.ToString();
}
```

`ToStringEx(new List<int> { 5, 6, 7 })`는 `List of 3 items: 5 6 7`을, `ToStringEx("xyyzzz".GroupBy(c => c))`는 `Group with key=x: x` / `Group with key=y: y y` / `Group with key=z: z z z`를 출력한다.

이 방식은 견고하다. `IGrouping<,>`이 암묵적으로 구현되었든 명시적으로 구현되었든 동작한다 — 인터페이스 타입에서 `GetProperty`를 했기 때문이다.

> **📌 이 문제는 `dynamic`으로 더 간단히 풀린다**
>
> "타입 체조"를 하고 있다는 느낌이 들면 그것이 동적 바인딩을 쓸 신호다. 59장에서 같은 문제를 `dynamic` 키워드로 훨씬 짧게 푼다. 리플렉션이 더 나은 경우는 타입·멤버 **목록**을 얻어야 하거나, 문자열에서 온 이름으로 객체를 만들어야 하거나, 어셈블리를 즉석에서 만들어야 할 때다. 특정 멤버 하나를 부르는 것이 목적이라면 `dynamic`이 낫다.

> **⚠️ 닫힌 인터페이스를 찾는 코드에서 `IsGenericType` 검사를 빼먹지 마라**
>
> `t.GetGenericTypeDefinition()`은 제네릭이 아닌 타입에 대해 `InvalidOperationException`을 던진다. `GetInterfaces()`의 결과에는 `IEnumerable`, `IDisposable` 같은 비제네릭 인터페이스가 섞여 있으므로, `IsGenericType` 검사를 앞에 두지 않으면 반드시 터진다. LINQ의 `&&` 단락 평가에 의존하는 위 코드의 순서에 의미가 있다.

## 57.9 정적 가상·추상 인터페이스 멤버 호출 ※C# 11

.NET 7 / C# 11부터 인터페이스가 **정적 가상(static virtual)·정적 추상(static abstract) 멤버**를 정의할 수 있다. 대표적인 예가 `IParsable<TSelf>`다.

```csharp
public interface IParsable<TSelf> where TSelf : IParsable<TSelf>
{
    static abstract TSelf Parse(string s, IFormatProvider provider);
    // ...
}
```

제약된 타입 매개변수를 통하면 정적 추상 멤버를 다형적으로 부를 수 있다.

```csharp
T ParseAny<T>(string s) where T : IParsable<T> => T.Parse(s, null);
```

이 코드에서 `T.Parse`는 IL의 `constrained.` 접두사 + `call`로 컴파일되며, JIT이 실제 타입의 구현으로 해석한다(56.3절의 `constrained.`를 참조).

### 리플렉션으로 부르려면 구체 타입에서 시작해야 한다

정적 추상 인터페이스 멤버를 리플렉션으로 부르려면, **인터페이스가 아니라 그 인터페이스를 구현한 구체 타입에서** `MethodInfo`를 얻어야 한다. 인터페이스의 `MethodInfo`는 구현이 없으므로 호출할 수 없다.

가장 직관적인 방법은 시그니처로 구체 멤버를 찾는 것이다.

```csharp
MethodInfo GetParseMethod(Type concreteType) =>
    concreteType.GetMethod("Parse",
        new[] { typeof(string), typeof(IFormatProvider) });
```

> **⚠️ 이 방법은 명시적 구현에서 실패한다**
>
> 인터페이스 멤버를 **명시적으로** 구현하면 IL 이름이 `System.IParsable<T>.Parse` 형태가 되고 접근성이 private이 된다. 위 `GetMethod`는 `null`을 돌려준다. 그리고 `float`, `int` 같은 BCL 타입은 상황에 따라 구현 방식이 다르다 — "지금 되니까 괜찮다"는 판단은 위험하다.

### `GetInterfaceMap`을 쓰는 일반해

인터페이스 메서드가 구체 타입의 어느 메서드로 구현되었는지를 알려주는 것이 `Type.GetInterfaceMap`이다. 반환하는 `InterfaceMapping` 구조체에는 `InterfaceMethods`와 `TargetMethods` 두 `MethodInfo[]`가 있고, **두 배열은 길이가 같으며 같은 인덱스끼리 대응한다**(`InterfaceType`, `TargetType` 필드도 있다). 이것으로 "지정한 인터페이스 메서드를 구현하는 구체 타입의 `MethodInfo`"를 찾는 함수를 쓸 수 있다.

```csharp
MethodInfo GetImplementedInterfaceMethod(Type concreteType,
    Type interfaceType, string methodName, Type[] paramTypes)
{
    var map = concreteType.GetInterfaceMap(interfaceType);

    return map.InterfaceMethods
        .Zip(map.TargetMethods)
        .Single(m => m.First.Name == methodName &&
                     m.First.GetParameters().Select(p => p.ParameterType)
                            .SequenceEqual(paramTypes))
        .Second;
}
```

LINQ의 `Zip`으로 두 배열의 원소를 짝지어, 원하는 시그니처의 인터페이스 메서드에 대응하는 대상 메서드를 뽑는다. 이제 리플렉션 기반 `ParseAny`를 쓸 수 있다.

```csharp
object ParseAny(Type type, string value)
{
    MethodInfo parseMethod = GetImplementedInterfaceMethod(type,
        type.GetInterface("IParsable`1"),
        "Parse",
        new[] { typeof(string), typeof(IFormatProvider) });

    return parseMethod.Invoke(null, new[] { value, null });
}

Console.WriteLine(ParseAny(typeof(float), ".2"));      // 0.2
```

`GetImplementedInterfaceMethod`에는 **닫힌** 인터페이스 타입을 넘겨야 한다. 위에서는 `type.GetInterface("IParsable`1")`로 얻었다. 이 시나리오처럼 인터페이스를 컴파일 타임에 안다면 다음 표현식이 더 명확하다.

```csharp
typeof(IParsable<>).MakeGenericType(type)
```

> **📌 `GetInterfaceMap`은 인스턴스 메서드에도 통한다**
>
> 정적 추상 멤버 전용이 아니다. 평범한 인스턴스 메서드에도 그대로 동작하며 **명시적 인터페이스 구현을 이름에 의존하지 않고 찾아내는** 정석 도구다(57.7절). 정적 추상 멤버에서 특히 유용해 보이는 이유는 그 경우 다른 대안이 아예 없기 때문이다.

> **⚠️ 정적 추상 멤버는 인터페이스 `MethodInfo`로 호출할 수 없다**
>
> ```csharp
> MethodInfo m = typeof(IParsable<float>).GetMethod("Parse");
> m.Invoke(null, new object[] { ".2", null });    // 실패한다
> ```
>
> 인터페이스의 `MethodInfo`는 구현 본문이 없는 추상 선언이다. `Invoke`는 어느 구현을 부를지 알 수 없다. C#에서 `T.Parse`가 동작하는 이유는 **컴파일러가 `T`를 알고 `constrained.` 접두사를 붙여주기** 때문이며, 리플렉션에는 그 `T`가 없다.

> **⚠️ 정적 추상 멤버 + 제네릭 수학은 AOT에서 무겁다**
>
> `INumber<T>` 계열의 제네릭 수학 인터페이스를 리플렉션으로 닫아 쓰면, 값 타입 인수마다 별도 코드가 필요하다(57.4절의 `MakeGenericType` 경고와 같은 이유). Native AOT에서는 게시 시점에 존재하지 않은 조합은 만들 수 없다. 이런 코드가 필요하다면 **미리 쓸 타입 목록을 정해 두고** 소스 생성기로 정적 디스패치 테이블을 만드는 편이 안전하다(57.15절).

> **💡 매 호출마다 리플렉션하지 마라**
>
> 위 `ParseAny`가 정말 필요한지 먼저 물어라. 호출자가 타입을 컴파일 타임에 안다면 `ParseAny<T>()` 제네릭 메서드로 충분하다. `Type` 객체만 있다면, `static object ParseCore<T>(string s) where T : IParsable<T> => T.Parse(s, null)` 같은 헬퍼를 `MakeGenericMethod(type)`으로 한 번 닫아 `Func<string, object>` 델리게이트로 만들고 `ConcurrentDictionary<Type, ...>`에 캐싱하라.
>
> 리플렉션은 **델리게이트를 만들 때 한 번만** 돈다. 그다음은 정적 호출과 다를 바 없다 — 이것이 57.13절의 핵심 아이디어이기도 하다.

## 57.10 어셈블리와 모듈 리플렉션

### 어셈블리 안의 타입 열거

`Assembly` 객체에서 `GetType`이나 `GetTypes`를 부르면 어셈블리를 동적으로 들여다볼 수 있다.

```csharp
// 현재 어셈블리에서 이름으로 한 개
Type t = Assembly.GetExecutingAssembly().GetType("Demos.TestProgram");

// 파일에서 로드해 전부 열거
Assembly a = Assembly.LoadFile(@"e:\demo\mylib.dll");
foreach (Type x in a.GetTypes()) Console.WriteLine(x);

// 밖에서 보이는 public 타입만
foreach (Type x in typeof(Foo).Assembly.ExportedTypes) Console.WriteLine(x);
```

| API | 돌려주는 것 |
|---|---|
| `Assembly.GetTypes()` | 어셈블리에 정의된 **모든** 최상위 타입 (internal 포함) |
| `Assembly.ExportedTypes` / `GetExportedTypes()` | 어셈블리 밖에서 보이는 public 타입만 |
| `Assembly.DefinedTypes` | `TypeInfo` 컬렉션. `GetTypes()`와 같은 집합 |
| `Assembly.GetType(name)` | 이름으로 한 개 |
| `Assembly.EntryPoint` | 진입 메서드의 `MethodInfo` (없으면 `null`) |
| `Assembly.GetModules()` / `ManifestModule` | 모듈 (52.3절) |

`GetTypes`와 `ExportedTypes`는 **최상위 타입만** 준다. 중첩 타입은 각 타입에서 `GetNestedTypes`로 따로 얻어야 한다.

> **⚠️ `GetTypes()`는 `ReflectionTypeLoadException`을 던질 수 있다**
>
> 어셈블리 안에 **해석할 수 없는 타입이 하나라도 있으면** — 참조하는 의존 어셈블리가 없거나, 버전이 안 맞거나, 다른 ALC에서 왔거나 — `GetTypes()`는 전체를 실패시킨다. 플러그인 디렉터리를 훑는 코드가 남의 DLL 하나 때문에 통째로 죽는 전형적인 사고다.
>
> 이 예외의 `Types` 배열에는 **로드에 성공한 타입이 들어 있고 실패한 자리는 `null`** 이다. `LoaderExceptions`에 원인이 들어 있다. 견고한 스캐너는 이렇게 쓴다.
>
> ```csharp
> static Type[] GetLoadableTypes(Assembly assembly)
> {
>     try { return assembly.GetTypes(); }
>     catch (ReflectionTypeLoadException ex)
>     {
>         foreach (var le in ex.LoaderExceptions)
>             Log.Warn(le?.Message);
>         return ex.Types.Where(t => t != null).ToArray()!;
>     }
> }
> ```
>
> `ExportedTypes`도 같은 예외를 던질 수 있다. 어셈블리를 열거하는 모든 코드에 이 방어가 필요하다.

### 확장 가능 애플리케이션 설계 — 인터페이스가 중심이다

52.14절에서 언로드 가능한 ALC로 플러그인을 격리하는 **로딩** 쪽을 다뤘다. 여기서는 **발견(discovery)** 쪽을 본다. 두 가지가 합쳐져야 플러그인 시스템이 된다.

확장 가능 애플리케이션의 표준 구조는 세 어셈블리다.

| 어셈블리 | 참조 관계 | 역할 |
|---|---|---|
| **Host SDK** | 아무것도 참조하지 않음 | 호스트와 애드인이 소통하는 인터페이스와 데이터 타입 정의 |
| **Add-In** | Host SDK 참조 | 제3자가 작성. 인터페이스 구현 |
| **Host App** | Host SDK 참조 | 애드인을 발견·생성·호출 |

핵심은 **애드인이 Host App을 참조하지 않는다**는 것이다. 그래서 호스트는 애드인 개발자를 기다리지 않고 매시간이라도 새 버전을 낼 수 있다.

> **💡 기저 클래스보다 인터페이스를 써라**
>
> 통신 계약은 기저 클래스로도 인터페이스로도 만들 수 있지만 인터페이스가 낫다. **애드인 개발자가 자기에게 맞는 기저 클래스를 고를 자유**를 잃지 않기 때문이다.
>
> 다만 버전 관리 측면에서는 기저 클래스가 유리하다 — 기저 클래스에 멤버를 추가하면 파생 타입이 그냥 상속받지만, 인터페이스에 멤버를 추가하면 모든 구현 타입이 코드를 고치고 재컴파일해야 한다(C# 8의 기본 인터페이스 구현으로 이 문제는 상당히 완화되었다).
>
> 어느 쪽을 쓰든 **계약은 반드시 자기만의 어셈블리에 두고, 일단 게시한 뒤에는 깨는 변경을 하지 마라.** 데이터 타입에 멤버를 추가하는 정도는 괜찮다.

Host SDK는 인터페이스 하나면 족하다.

```csharp
namespace Wintellect.HostSDK
{
    public interface IAddIn { string DoSomething(int x); }
}
```

애드인 어셈블리는 그것을 참조해 `public sealed class AddIn_A : IAddIn { ... }` 같은 타입을 정의한다. 호스트는 애드인 어셈블리가 실행 파일과 같은 디렉터리에 `.dll`로 배포된다고 가정하고 이렇게 찾는다.

```csharp
// TryLoad 는 로드 실패를 삼키고 null 을 돌려주는 헬퍼,
// GetLoadableTypes 는 위 박스에서 정의한 방어적 래퍼다.
var addInTypes =
    from file in Directory.EnumerateFiles(AppContext.BaseDirectory, "*.dll")
    let assembly = TryLoad(file)
    where assembly != null
    from t in GetLoadableTypes(assembly)
    where t.IsClass && !t.IsAbstract && typeof(IAddIn).IsAssignableFrom(t)
    select t;

foreach (Type t in addInTypes)
{
    IAddIn ai = (IAddIn) Activator.CreateInstance(t)!;
    Console.WriteLine(ai.DoSomething(5));
}
```

> **⚠️ 발견 이후에는 리플렉션을 쓰지 마라**
>
> 이 설계의 요점은 마지막 두 줄이다. **객체를 만든 직후 컴파일 타임에 알려진 인터페이스로 캐스팅한다.** 그다음부터의 모든 호출은 평범한 인터페이스 호출이고 성능도 타입 안전성도 정상이다.
>
> 리플렉션은 "어떤 타입이 있는지 찾는" 초기화 단계에만 쓰고, "그 타입의 멤버를 부르는" 단계에는 쓰지 않는다. 이것이 리플렉션을 쓰는 애플리케이션의 유일한 올바른 골격이다.

> **⚠️ `Assembly.Load(파일 경로)`는 동작하지 않는다**
>
> `Assembly.Load`는 **어셈블리 이름**을 받지 파일 경로를 받지 않는다. 경로로 로드하려면 `Assembly.LoadFrom` / `LoadFile` 또는 `AssemblyLoadContext.LoadFromAssemblyPath`를 써야 한다. 각각의 컨텍스트 차이와 함정은 52.13절에서 다뤘다. 격리가 필요하면 52.14절처럼 전용 ALC를 쓰고, 애드인이 파일 잠금 없이 로드되어야 한다면 바이트 배열로 읽어 넘겨라.

### 모듈과 메타데이터 토큰

다중 모듈 어셈블리에서 `GetTypes`를 부르면 모든 모듈의 모든 타입이 나온다. 그래서 대개 모듈의 존재를 무시하고 어셈블리를 타입의 컨테이너로 취급해도 된다. 모듈이 의미를 갖는 경우는 하나 — **메타데이터 토큰**을 다룰 때다.

메타데이터 토큰은 **모듈 범위 안에서** 타입·멤버·문자열·리소스를 유일하게 가리키는 정수다. IL은 메타데이터 토큰을 쓰므로, IL을 파싱한다면 토큰을 해석할 수 있어야 한다. 그 메서드들이 `Module` 타입에 있다 — `ResolveType`, `ResolveMember`, `ResolveMethod`, `ResolveField`, `ResolveString`, `ResolveSignature`. 각각 `int` 토큰을 받아 `Type`, `MemberInfo`, `MethodBase`, `FieldInfo`, `string`, `byte[]`를 돌려준다.

어셈블리의 모듈 목록은 `GetModules()`로, 주 모듈은 `ManifestModule` 프로퍼티로 얻는다. 이 API들로 IL 바이트 배열을 사람이 읽는 명령으로 바꾸는 작업은 56.9절에서 다뤘다.

> **📌 다중 모듈 어셈블리는 .NET Framework 전용이다**
>
> .NET 5+ / .NET Core는 다중 파일 어셈블리를 지원하지 않는다(52.3절). 따라서 `GetModules()`는 항상 원소 하나짜리 배열을 돌려주고 `ManifestModule`과 같다. 그래도 `Module` 타입 자체는 토큰 해석 때문에 살아 있다.

### `MetadataLoadContext` — 실행하지 않고 읽기

리플렉션의 오래된 문제 하나. **어셈블리를 검사하기만 하고 싶은데 로드하면 코드가 실행될 수 있다** — 타입 초기화자, 모듈 초기화자, 특성 생성자가 그렇다. 게다가 한 번 로드하면 기본 ALC에서는 언로드할 수 없고, 아키텍처나 대상 프레임워크가 달라도 로드할 수 없다.

.NET Framework에는 `Assembly.ReflectionOnlyLoad`가 있었다. **.NET Core / .NET 5+에서는 이 메서드가 `PlatformNotSupportedException`을 던진다.** `Type.ReflectionOnlyGetType`도 마찬가지다. 대체재는 `System.Reflection.MetadataLoadContext` NuGet 패키지(.NET Core 3.0 / .NET Standard 2.0 이상 대상)의 동명 클래스다.

```xml
<PackageReference Include="System.Reflection.MetadataLoadContext" Version="8.0.0" />
```

```csharp
using System.Reflection;
using System.Runtime.InteropServices;   // RuntimeEnvironment

// 해석 대상 어셈블리 목록 — 코어 어셈블리를 반드시 포함해야 한다
var paths = new List<string>(
    Directory.GetFiles(RuntimeEnvironment.GetRuntimeDirectory(), "*.dll"));
paths.Add(@"c:\plugins\MyPlugin.dll");

var resolver = new PathAssemblyResolver(paths);

using var mlc = new MetadataLoadContext(resolver);

Assembly plugin = mlc.LoadFromAssemblyPath(@"c:\plugins\MyPlugin.dll");

foreach (Type t in plugin.GetTypes())
{
    Console.WriteLine(t.FullName);
    foreach (var m in t.GetMethods())
        Console.WriteLine("   " + m);
}
```

`MetadataLoadContext`의 성질은 다음과 같다.

| 성질 | `MetadataLoadContext` | 일반 로드 |
|---|---|---|
| 코드 실행 | **절대 없음** | 타입 초기화자·특성 생성자 실행 |
| 대상 플랫폼 | 아키텍처·프레임워크 무관 | 프로세스와 일치해야 함 |
| 인스턴스 생성 / 호출 | **불가** | 가능 |
| 해제 | `Dispose()`로 파일 잠금 해제 | 기본 ALC는 언로드 불가 |
| `typeof(X)`와의 비교 | **항상 `false`** | 정상 |
| 특성 읽기 | `CustomAttributeData`로만 | 인스턴스로도 가능 |

> **⚠️ `MetadataLoadContext`의 `Type`은 실행 런타임의 `Type`과 다른 세계다**
>
> `mlc`에서 얻은 `Type`은 `typeof(string)`과 같지 않고, `IsAssignableFrom`도 두 세계를 넘나들지 않는다. `Activator.CreateInstance`에 넘길 수도 없다. 아래 `ok`는 **항상 `false`** 다.
>
> ```csharp
> Type t = mlc.LoadFromAssemblyPath(path).GetType("MyPlugin.Widget");
> bool ok = typeof(IPlugin).IsAssignableFrom(t);       // 항상 false
>
> // 인터페이스 구현 여부는 양쪽 모두 mlc 안에서 비교해야 한다
> Type iPluginInMlc = mlc.LoadFromAssemblyPath(sdkPath).GetType("HostSDK.IPlugin")!;
> bool ok2 = iPluginInMlc.IsAssignableFrom(t);         // 이제 맞다
> ```
>
> 이름으로 비교하는 편이 안전한 경우도 많다: `t.GetInterfaces().Any(i => i.FullName == "HostSDK.IPlugin")`.

> **💡 언제 `MetadataLoadContext`를 쓰나**
>
> - 빌드 도구·분석기·문서 생성기 — 대상 어셈블리 코드를 절대 실행하면 안 된다
> - 신뢰할 수 없는 플러그인의 **사전 검증** — 계약을 만족하는지 확인한 뒤에만 진짜 ALC에 로드한다
> - 크로스 타기팅 검사 — x64 프로세스에서 ARM64 어셈블리를, .NET 8 프로세스에서 .NET Framework 어셈블리를 읽는다
>
> 반대로, 실제로 그 코드를 실행할 거라면 `MetadataLoadContext`를 쓸 이유가 없다. 두 번 로드하는 셈이다.

### ※`System.Reflection.Metadata` — 저수준 메타데이터 리더

한 층 더 아래에 `System.Reflection.Metadata` 네임스페이스가 있다. 이것은 리플렉션 객체 모델을 전혀 만들지 않고 **PE 파일의 메타데이터 스트림을 직접 읽는** 저할당 리더다. Roslyn과 ILSpy, 트리밍 도구가 쓰는 층이다.

```csharp
using System.Reflection.Metadata;
using System.Reflection.PortableExecutable;

using var fs = File.OpenRead(@"c:\plugins\MyPlugin.dll");
using var peReader = new PEReader(fs);

if (!peReader.HasMetadata) return;
MetadataReader reader = peReader.GetMetadataReader();

foreach (TypeDefinitionHandle handle in reader.TypeDefinitions)
{
    TypeDefinition td = reader.GetTypeDefinition(handle);

    string ns   = reader.GetString(td.Namespace);
    string name = reader.GetString(td.Name);

    Console.WriteLine(string.IsNullOrEmpty(ns) ? name : ns + "." + name);

    foreach (MethodDefinitionHandle mh in td.GetMethods())
    {
        MethodDefinition md = reader.GetMethodDefinition(mh);
        Console.WriteLine("   " + reader.GetString(md.Name));
    }
}
```

`TypeDefinitionHandle`, `StringHandle` 같은 핸들은 전부 **정수를 감싼 구조체**이고 실제 값은 `reader`를 통해서만 꺼낸다. 문자열조차 필요할 때만 UTF-8 힙에서 디코딩하므로 어셈블리 수천 개를 훑어도 힙 할당이 거의 없다.

| 층 | 무엇을 만드나 | 비용 | 코드를 실행하나 |
|---|---|---|---|
| `Type` / `MemberInfo` (일반 리플렉션) | 완전한 런타임 객체 모델 | 높음 | 그렇다 |
| `MetadataLoadContext` | 리플렉션 객체 모델(실행 불가) | 중간 | 아니다 |
| `MetadataReader` | 아무것도. 핸들만 | 매우 낮음 | 아니다 |

> **💡 무엇을 고를 것인가**
>
> 그 코드를 실행할 것이면 **일반 리플렉션**, 검사만 하고 리플렉션 API가 편하면 **`MetadataLoadContext`**, 수천 개 어셈블리를 스캔하며 성능이 중요하면 **`MetadataReader`**. `MetadataReader`는 API가 낯설고 상속·오버로드 해석을 직접 구현해야 하므로, 빌드 파이프라인에 넣을 도구가 아니라면 대개 `MetadataLoadContext`가 적정선이다.

> **⚠️ `MetadataReader`는 상속을 풀어주지 않는다**
>
> `TypeDefinition.BaseType`은 `EntityHandle`을 주는데, 그것은 `TypeDefinitionHandle`(같은 어셈블리), `TypeReferenceHandle`(다른 어셈블리), `TypeSpecificationHandle`(제네릭 인스턴스화) 중 하나다. **어느 것인지 `Kind`로 분기해 직접 해석해야 한다.** 다른 어셈블리의 타입이라면 그 어셈블리를 스스로 찾아 열어야 한다. 리플렉션이 알아서 해주던 일이 전부 손으로 넘어온다는 뜻이다.

## 57.11 특성 다루기 — 정의, 적용, 런타임 조회

CLR은 **특성(attribute)** 을 통해 타입·멤버·어셈블리에 추가 메타데이터를 붙일 수 있게 한다. 어셈블리 식별이나 네이티브 상호운용의 마샬링 같은 중요한 CLR 기능이 이 메커니즘으로 지시된다. 핵심 성질은 **직접 만들어서 쓸 수 있다**는 것이다 — 이 정보는 어셈블리에 컴파일되어 들어가고, 런타임에 리플렉션으로 꺼내 **선언적으로 동작하는 서비스**를 만든다. 정의·적용 문법은 20.6~20.8절에서 다뤘으므로 여기서는 **읽는 쪽**에 집중한다.

### 특성은 세 종류다

| 종류 | 저장 방식 | 확장 가능? | 리플렉션 노출 |
|---|---|---|---|
| **비트 매핑 특성** | 메타데이터의 전용 비트 (보통 1비트) | 아니다 | `IsPublic`, `IsAbstract` 등 전용 프로퍼티 / `Attributes` 플래그 |
| **커스텀 특성** | 메타데이터 테이블에 매달린 blob | **그렇다** | `GetCustomAttributes` |
| **의사 커스텀 특성** | 소스에서는 커스텀, 저장은 비트 매핑 | 아니다 | 전용 프로퍼티 + (대개) `GetCustomAttributes` |

**비트 매핑 특성**은 C#의 수정자 키워드 대부분 — `public`, `abstract`, `sealed` — 이 컴파일되는 형태다. 메타데이터 공간을 최소한(보통 1비트)으로 쓰고 CLR이 간접 참조 거의 없이 찾는다. `Attributes` 프로퍼티가 이들 대부분을 플래그 열거형으로 한 번에 준다.

```csharp
static void Main()
{
    TypeAttributes ta = typeof(Console).Attributes;
    MethodAttributes ma = MethodInfo.GetCurrentMethod().Attributes;
    Console.WriteLine(ta + "\r\n" + ma);
}
```

```text
AutoLayout, AnsiClass, Class, Public, Abstract, Sealed, BeforeFieldInit
PrivateScope, Private, Static, HideBySig
```

56.3절에서 `.class public abstract auto ansi sealed beforefieldinit` 같은 IL 디렉티브를 봤다. 그것이 바로 이 비트들이다.

**커스텀 특성**은 타입의 주 메타데이터 테이블에 매달린 blob으로 컴파일된다. 전부 `System.Attribute`의 서브클래스이고, 비트 매핑과 달리 확장 가능하다. blob에는 특성 클래스의 신원과, 적용 시점에 지정된 위치·명명 인수의 값이 들어간다. **직접 정의한 커스텀 특성과 .NET 라이브러리의 특성은 구조적으로 동일하다.**

**의사 커스텀 특성**은 소스에서 보기에는 평범한 커스텀 특성이지만 — `[StructLayout(LayoutKind.Sequential)]`, `[In]`, `[Out]` 같은 것들 — 컴파일러나 CLR이 **내부적으로 비트 매핑 특성으로 변환해 최적화**한다. 리플렉션은 `IsLayoutSequential` 같은 전용 프로퍼티로 이들을 노출하고, 많은 경우 `GetCustomAttributes`를 부르면 `System.Attribute` 객체로도 돌려준다.

> **⚠️ 의사 커스텀 특성은 `GetCustomAttributes`에 안 나올 수도 있다**
>
> "많은 경우"라고 한 것은 예외가 있기 때문이다. 어떤 의사 커스텀 특성이 커스텀 특성 형태로 재구성되는지는 런타임 구현에 달렸고, .NET Framework와 .NET Core에서 다를 수 있다. `[StructLayout]`이나 `[Serializable]` 유무를 판정할 때는 **전용 프로퍼티**(`IsLayoutSequential`, `IsExplicitLayout`, `IsSerializable`)를 쓰는 편이 확실하다.
>
> 이 구분이 실제로 문제가 되는 지점이 하나 더 있다. `Reflection.Emit`으로 타입을 동적으로 만들 때는 의사 커스텀 특성을 커스텀 특성처럼 붙일 수 없다 — 해당하는 `TypeAttributes` 플래그나 전용 API를 써야 한다(58.8절).

### `AttributeUsage`와 인수 타입 제약 — 요점만

`[AttributeUsage(validOn, AllowMultiple = ..., Inherited = ...)]`가 특성 클래스에 붙는 특성이다. `AllowMultiple`은 같은 대상에 두 번 이상 붙일 수 있는지(기본 `false`), `Inherited`는 기저 클래스(또는 가상 메서드)에 붙은 특성이 파생 쪽에도 적용되는지(기본 `true`), `validOn`은 붙일 수 있는 대상 집합(`AttributeTargets` 플래그)을 정한다. 문법은 20.6절에서 다뤘다.

특성 프로퍼티와 생성자 매개변수의 타입은 **봉인된 원시 타입**(`bool`, `char`, `byte`/`sbyte`, `short`/`ushort`, `int`/`uint`, `long`/`ulong`, `float`, `double`, `string`), `Type`, `object`, 열거형, 그리고 이들의 **1차원 배열**로 제한된다. 배열을 받는 생성자는 CLS 준수가 아니므로 피하는 편이 낫다. 그리고 적용 시점에 컴파일러가 각 값을 **정적으로 평가할 수 있어야** 한다 — 그래서 특성 인수에는 상수·`typeof`·`nameof`만 올 수 있다.

### 커스텀 특성 정의 — 단위 테스트 예제

자동화된 단위 테스트 시스템을 위한 특성이다. 테스트 대상 메서드임을 표시하고, 반복 횟수와 실패 메시지를 담는다.

```csharp
[AttributeUsage(AttributeTargets.Method)]
public sealed class TestAttribute : Attribute
{
    public int Repetitions;
    public string FailureMessage;

    public TestAttribute() : this(1) { }
    public TestAttribute(int repetitions) { Repetitions = repetitions; }
}
```

```csharp
class Foo
{
    [Test]
    public void Method1() { ... }

    [Test(20)]
    public void Method2() { ... }

    [Test(20, FailureMessage = "Debugging Time!")]
    public void Method3() { ... }
}
```

### 런타임에 특성 조회하기

읽는 표준 경로는 둘이다.

1. 아무 `Type`이나 `MemberInfo` 객체에서 `GetCustomAttributes` 호출
2. `Attribute.GetCustomAttribute` 또는 `Attribute.GetCustomAttributes` 정적 메서드 호출

후자의 두 메서드는 유효한 특성 대상에 해당하는 모든 리플렉션 객체(`Type`, `Assembly`, `Module`, `MemberInfo`, `ParameterInfo`)를 받도록 오버로드되어 있다.

| 메서드 | 반환 | 특징 |
|---|---|---|
| `IsDefined` | `bool` | **특성 인스턴스를 만들지 않는다.** 가장 빠르다 |
| `GetCustomAttribute` | 인스턴스 하나 또는 `null` | 여러 개 붙어 있으면 `AmbiguousMatchException` |
| `GetCustomAttributes` | 인스턴스 컬렉션 | `AllowMultiple = true`이거나 전부 나열할 때 |
| `GetCustomAttributesData` | `CustomAttributeData` 컬렉션 | 인스턴스를 만들지 않고 "어떻게 생성될 것인가"를 본다 |

```csharp
foreach (MethodInfo mi in typeof(Foo).GetMethods())
{
    var att = (TestAttribute) Attribute.GetCustomAttribute(mi, typeof(TestAttribute));
    if (att != null)
        Console.WriteLine("Method {0} will be tested; reps={1}; msg={2}",
            mi.Name, att.Repetitions, att.FailureMessage);
}
```

```text
Method Method1 will be tested; reps=1; msg=
Method Method2 will be tested; reps=20; msg=
Method Method3 will be tested; reps=20; msg=Debugging Time!
```

출력하는 자리를 `for (int i = 0; i < att.Repetitions; i++) mi.Invoke(new Foo(), null);`로 바꾸고 `catch`에서 `att.FailureMessage`로 감싸면 단위 테스트 러너의 골격이 완성된다. xUnit·NUnit·MSTest가 이 위에 얹힌 정교한 버전이다.

> **📌 특성은 읽는 코드가 없으면 아무 일도 하지 않는다**
>
> 특성 클래스를 정의하고 마음껏 적용해도, **누군가 읽지 않으면** 어셈블리에 메타데이터가 조금 더 쓰이는 것 외에 아무 변화도 없다. `[Flags]`를 붙이면 `Enum.ToString`의 동작이 바뀌는 이유는, `Enum.ToString`의 구현이 다음처럼 되어 있기 때문이다.
>
> ```csharp
> if (this.GetType().IsDefined(typeof(FlagsAttribute), false))
> { /* 비트 플래그로 취급 */ }
> else
> { /* 보통 열거형으로 취급 */ }
> ```
>
> 커스텀 특성이 유용한 이유는 이 "읽고 분기하는 코드"를 우리가 직접 쓸 수 있기 때문이다.

> **⚠️ `inherit` 매개변수를 존중하는 클래스는 셋뿐이다**
>
> `Attribute`, `Type`, `MethodInfo`만이 `bool inherit` 매개변수를 실제로 반영한다. **다른 모든 리플렉션 클래스는 `inherit`을 무시하고 상속 계층을 검사하지 않는다.** 이벤트·프로퍼티·필드·생성자·매개변수에서 상속된 특성을 찾아야 한다면 `Attribute`의 정적 메서드를 써야 한다.
>
> ```csharp
> // 이것은 프로퍼티에서 inherit이 무시된다
> pi.GetCustomAttributes(typeof(MyAttribute), inherit: true);
>
> // 이것은 제대로 동작한다
> Attribute.GetCustomAttributes(pi, typeof(MyAttribute), inherit: true);
> ```
>
> ORM과 유효성 검사 라이브러리에서 "기저 클래스에 붙인 특성이 왜 안 잡히지"라는 증상이 나오면 거의 항상 이것이다.

> **⚠️ 조회는 파생 특성까지 잡는다**
>
> `IsDefined`, `GetCustomAttribute(s)`에 특성 클래스를 넘기면, 그 클래스뿐 아니라 **그 클래스에서 파생된 특성 클래스**까지 찾는다. 정확히 그 클래스만 원한다면 반환값을 한 번 더 검사해야 한다. 혼란을 없애고 이 추가 검사를 지우려면 **특성 클래스를 `sealed`로 선언**하는 편이 낫다. .NET 라이브러리의 특성 대부분이 `sealed`인 이유다.

> **💡 존재만 확인할 때는 `IsDefined`를 써라**
>
> `GetCustomAttribute(s)`는 호출할 때마다 특성 객체를 **새로 만든다.** 생성자를 부르고 필드·프로퍼티를 소스에 적힌 값으로 설정한다. 그리고 내부적으로는 관리 모듈의 메타데이터를 스캔하며 문자열 비교를 한다. 붙어 있는지만 알면 되는 경우 `IsDefined`가 훨씬 싸다.
>
> 어느 쪽이든 **결과를 캐싱하라.** 같은 정보를 반복해서 묻는 것이 리플렉션 기반 프레임워크가 느려지는 가장 흔한 이유다.

### 특성 인스턴스 비교하기

`System.Attribute`는 `Object.Equals`를 재정의한다. 두 객체의 타입을 비교하고, 같으면 **리플렉션으로 각 필드의 값을 비교**해 전부 일치하면 `true`다. 자기 특성 클래스에서 `Equals`를 재정의해 이 리플렉션 사용을 없애면 성능이 좋아진다.

`Attribute`에는 `Match`라는 가상 메서드도 있다. 기본 구현은 `Equals`를 부르고 그 결과를 돌려주지만, 재정의해 더 풍부한 의미 — 예를 들어 "한쪽이 다른 쪽의 **부분집합**인가" — 를 줄 수 있다.

```csharp
[Flags] internal enum Accounts { Savings = 1, Checking = 2, Brokerage = 4 }

[AttributeUsage(AttributeTargets.Class)]
internal sealed class AccountsAttribute : Attribute
{
    private readonly Accounts _accounts;
    public AccountsAttribute(Accounts accounts) { _accounts = accounts; }

    // this 가 other 의 부분집합이면 매치로 본다
    public override bool Match(object obj) =>
        obj is AccountsAttribute other && (_accounts & other._accounts) == _accounts;

    public override bool Equals(object obj) =>
        obj is AccountsAttribute other && other._accounts == _accounts;

    public override int GetHashCode() => (int) _accounts;
}
```

### 객체를 만들지 않고 특성 탐지하기

`GetCustomAttribute(s)`는 특성 클래스의 생성자와 프로퍼티 set 접근자를 **실제로 실행한다.** 게다가 그 타입에 처음 접근하는 순간 CLR이 타입 초기화자를 돌린다. 즉 **특성을 찾아보기만 해도 알 수 없는 코드가 실행된다.** 보안이 민감한 시나리오에서는 이것이 취약점이다.

해법은 `System.Reflection.CustomAttributeData`다. 이 클래스는 특성 객체를 만들지 않고 "**어떻게 생성될 것인가**"만 알려준다.

| 프로퍼티 | 알려주는 것 |
|---|---|
| `AttributeType` | 특성의 타입 |
| `Constructor` | 호출**될** 생성자 (`ConstructorInfo`) |
| `ConstructorArguments` | 생성자에 넘겨**질** 인수 (`IList<CustomAttributeTypedArgument>`) |
| `NamedArguments` | 설정**될** 필드/프로퍼티 (`IList<CustomAttributeNamedArgument>`) |

"~될"이라고 쓴 이유는 실제로 호출하지 않기 때문이다. 그것이 안전성의 원천이다.

```csharp
static void ShowAttributes(MemberInfo target)
{
    Console.WriteLine($"Attributes applied to {target.Name}:");

    foreach (CustomAttributeData a in CustomAttributeData.GetCustomAttributes(target))
    {
        Console.WriteLine($"  {a.AttributeType}");
        Console.WriteLine($"    Constructor called={a.Constructor}");

        foreach (CustomAttributeTypedArgument pa in a.ConstructorArguments)
            Console.WriteLine($"      Type={pa.ArgumentType}, Value={pa.Value}");

        foreach (CustomAttributeNamedArgument na in a.NamedArguments)
            Console.WriteLine($"      Name={na.MemberName}, Value={na.TypedValue.Value}");
    }
}
```

```text
Attributes applied to Program:
  System.Diagnostics.DebuggerDisplayAttribute
    Constructor called=Void .ctor(System.String)
      Type=System.String, Value=Richter
      Name=Name, Value=Jeff
      Name=Target, Value=Program
```

멤버 하나에 대해 같은 정보를 얻으려면 `MemberInfo.GetCustomAttributesData()` 인스턴스 메서드를 써도 된다.

> **💡 `CustomAttributeData`의 두 번째 용도 — 코드 재생성**
>
> `GetCustomAttributes()`와 `GetCustomAttributesData()`의 차이는 보안만이 아니다. 후자는 **특성이 어떻게 인스턴스화되었는지**를 알려준다 — 어느 생성자 오버로드가 쓰였고, 각 생성자 인수와 명명 매개변수의 값이 무엇인지.
>
> 이것은 특성을 **같은 상태로 재구성하는 코드나 IL을 방출할 때** 필수다. 프록시 생성기·소스 생성기·`Reflection.Emit` 기반 도구가 원본의 특성을 복사하려면 이 정보 없이는 불가능하다(58.8절).
>
> 그리고 `MetadataLoadContext`에서는 애초에 특성 인스턴스를 만들 수 없으므로 `CustomAttributeData`가 **유일한 경로**다.

> **📌 `[Conditional]`을 특성 클래스에 붙이기**
>
> `System.Diagnostics.ConditionalAttribute`를 특성 클래스에 적용하면 **조건부 특성 클래스**가 된다.
>
> ```csharp
> [Conditional("TEST")]
> [Conditional("VERIFY")]
> public sealed class CondAttribute : Attribute { }
> ```
>
> 컴파일러는 `CondAttribute`가 적용된 것을 보면, 그 대상이 컴파일될 때 `TEST`나 `VERIFY` 심볼이 정의된 경우에만 메타데이터에 특성 정보를 방출한다. 정적 분석 도구용 특성처럼 **실행 시에는 아무도 읽지 않는 특성**이 메타데이터를 부풀리는 것을 막는 장치다. 메타데이터가 커지면 파일이 커지고 working set이 늘고 성능이 나빠진다. `[Conditional]` 자체는 20.10절에서 다뤘다.

## 57.12 리플렉션 성능의 실체와 캐싱 전략

리플렉션은 컴파일 타임에 몰랐던 타입과 멤버를 런타임에 발견해 쓸 수 있게 하는 강력한 메커니즘이다. 이 힘에는 두 가지 대가가 따른다.

**첫째, 컴파일 타임 타입 안전성을 잃는다.** 리플렉션은 문자열을 대량으로 쓴다. `Type.GetType("int")`은 컴파일되지만 런타임에 `null`을 돌려준다(57.1절). 오타는 컴파일러가 아니라 사용자가 발견한다.

**둘째, 느리다.** 이유는 하나가 아니다.

| 비용 원인 | 설명 |
|---|---|
| 메타데이터 문자열 검색 | 타입·멤버 이름을 문자열로 스캔한다. 대소문자 무시 비교라면 더 느리다 |
| 인수 패키징 | 호출 인수를 `object[]`에 담고, 리플렉션이 내부에서 스레드 스택으로 다시 푼다 |
| **박싱** | 값 타입 인수마다 힙 할당이 하나씩 생긴다 |
| 인수 타입 검사 | CLR이 호출 전에 인수 타입이 맞는지 검증한다 |
| 접근성 검사 | 호출자가 그 멤버에 접근할 권한이 있는지 확인한다 |
| 예외 감싸기 | `TargetInvocationException` 생성과 스택 캡처 |

### 실측 — 같은 메서드를 여섯 가지 방법으로 부르기

간단한 인스턴스 메서드 `int Add(int a, int b) => a + b;`를 여러 경로로 100만 번 호출한 결과다.

```csharp
[MemoryDiagnoser]
public class InvokeBench
{
    sealed class Target { public int Add(int a, int b) => a + b; }

    static readonly Target _obj = new();
    static readonly MethodInfo _mi = typeof(Target).GetMethod("Add")!;
    static readonly MethodInvoker _inv = MethodInvoker.Create(_mi);     // ※.NET 8
    static readonly Func<Target, int, int, int> _del =                  // 열린 인스턴스 델리게이트
        _mi.CreateDelegate<Func<Target, int, int, int>>();

    [Benchmark(Baseline = true)] public int Direct()  => _obj.Add(3, 4);
    [Benchmark] public object Reflect() => _mi.Invoke(_obj, new object[] { 3, 4 });
    [Benchmark] public object Invoker() => _inv.Invoke(_obj, 3, 4);
    [Benchmark] public int    Delegate() => _del(_obj, 3, 4);
}
```

| 호출 방법 | 호출당 시간 | 호출당 할당 | 직접 호출 대비 |
|---|---|---|---|
| 직접 호출 (`obj.Add(3, 4)`) | ~0.5 ns | 0 B | 1× |
| `Delegate.CreateDelegate` 결과 | ~1.2 ns | 0 B | ~2× |
| `Expression.Lambda<Func<...>>().Compile()` 결과 | ~1.3 ns | 0 B | ~3× |
| `[UnsafeAccessor]` ※.NET 8 | ~0.5 ns | 0 B | ~1× |
| `MethodInvoker.Invoke` ※.NET 8 | ~25 ns | 48 B (박싱) | ~50× |
| 캐시된 `MethodInfo.Invoke` | ~45 ns | 96 B | ~90× |
| 매번 `GetMethod` + `Invoke` | ~1,000 ns 이상 | 200 B 이상 | 2,000× 이상 |

> **⚠️ 이 표의 절대값을 인용하지 마라**
>
> 위 수치는 특정 머신·특정 런타임 버전에서 BenchmarkDotNet으로 잰 중앙값의 자릿수를 정리한 것이다. CPU, 런타임 버전, 인수 개수, 값 타입 여부에 따라 크게 달라진다. **읽어야 할 것은 비율의 자릿수**다.
>
> - 델리게이트는 직접 호출과 **같은 자릿수**다 (나노초)
> - `Invoke`는 두 자릿수 느리다 (수십 나노초)
> - 조회까지 매번 하면 세 자릿수 느리다 (마이크로초)
>
> 그리고 호출당 할당이 GC 압력으로 이어진다는 점이 시간보다 더 중요한 경우가 많다.

> **📌 ※.NET 8에서 `MethodInfo.Invoke`가 크게 빨라졌다**
>
> .NET 8은 리플렉션 호출 경로를 다시 썼다. 내부적으로 호출 스텁을 생성해 쓰기 때문에 이전 버전 대비 몇 배 빠르다. 여기에 `MethodInvoker`와 `ConstructorInvoker` 타입이 새로 추가되었다.
>
> ```csharp
> MethodInvoker invoker = MethodInvoker.Create(methodInfo);
> object? result = invoker.Invoke(target, arg1, arg2);      // 인수 4개까지 배열 없이
> object? result2 = invoker.Invoke(target, argSpan);        // 또는 Span
> ```
>
> `Invoker`를 **한 번 만들어 캐싱**하면 `MethodInfo.Invoke`보다 빠르고, 인수 배열 할당을 피할 수 있다. 다만 여전히 값 타입 인수는 박싱된다 — `object`를 통해 넘기기 때문이다. 델리게이트와의 격차는 좁혀지지만 사라지지는 않는다.

### `[UnsafeAccessor]` ※.NET 8 — 비용 없는 비공개 접근

.NET 8은 `System.Runtime.CompilerServices.UnsafeAccessorAttribute`를 도입했다. 비공개 멤버에 접근하는 `static extern` 메서드를 선언하면, **런타임이 JIT 시점에 그 선언을 실제 멤버에 바인딩**한다. 리플렉션 객체가 전혀 만들어지지 않고 호출 비용은 직접 호출과 같다.

```csharp
using System.Runtime.CompilerServices;

class Walnut
{
    private bool cracked;
    private void Reset(bool value) => cracked = value;
    private Walnut(bool initial) { cracked = initial; }
}

static class WalnutAccessors
{
    // private 필드에 대한 참조를 얻는다
    [UnsafeAccessor(UnsafeAccessorKind.Field, Name = "cracked")]
    public static extern ref bool GetCracked(Walnut w);

    // private 인스턴스 메서드를 호출한다
    [UnsafeAccessor(UnsafeAccessorKind.Method, Name = "Reset")]
    public static extern void Reset(Walnut w, bool value);

    // private 생성자를 호출한다
    [UnsafeAccessor(UnsafeAccessorKind.Constructor)]
    public static extern Walnut Create(bool initial);
}
```

```csharp
Walnut w = WalnutAccessors.Create(true);
Console.WriteLine(WalnutAccessors.GetCracked(w));   // True
WalnutAccessors.Reset(w, false);
Console.WriteLine(WalnutAccessors.GetCracked(w));   // False
```

`UnsafeAccessorKind`는 `Constructor`, `Method`, `StaticMethod`, `Field`, `StaticField` 다섯이다. 첫 매개변수가 대상 인스턴스이고(정적 멤버라면 대상 타입), 나머지가 실제 인수다. 필드 접근자는 `ref`를 반환해야 읽기와 쓰기가 모두 된다.

| 항목 | 리플렉션 | `[UnsafeAccessor]` |
|---|---|---|
| 호출 비용 | 수십 ns + 박싱 | 직접 호출과 동일 |
| 시그니처 오류 발견 시점 | 런타임 (`null` 또는 예외) | **첫 호출 시** `MissingFieldException` / `MissingMethodException` |
| 트리밍/AOT 안전성 | 위험 (57.14절) | **안전.** 트리머가 이 참조를 이해한다 |
| 제네릭 지원 | 완전 | 제한적 (초기 버전은 제네릭 대상에 제약이 있다) |

> **💡 .NET 8 이상이면 `[UnsafeAccessor]`를 먼저 검토하라**
>
> 테스트에서 내부 상태를 검사하거나, 봉인된 BCL 타입의 필드를 읽어야 하거나, 성능 때문에 리플렉션 캐싱 코드를 쓰던 자리를 대부분 대체할 수 있다. 얻는 것은 **성능 + 트리밍 호환성 + 컴파일 타임에 가까운 시그니처 검증**이다. 대상 이름을 문자열로 쓴다는 점은 여전하지만, 틀리면 조용한 `null`이 아니라 명확한 예외가 난다.
>
> 여전히 못 하는 것: 타입 **목록**을 얻는 것, 이름이 런타임에 결정되는 멤버를 부르는 것. 그건 리플렉션의 일이다.

### 캐싱 전략

리플렉션 조회 결과는 반드시 캐싱한다. 규칙은 셋이다. **(1)** 한 번만 조회하고 `static readonly`에 담아라 — 타입 초기화 시점에 실패하므로 문제를 빨리 발견한다. **(2)** 타입이 런타임에 결정되면 `ConcurrentDictionary<Type, T>`를 쓰되 `GetOrAdd`에 `static` 람다를 넘겨 클로저 할당을 피하라. **(3)** 캐싱하는 것은 `MethodInfo`가 아니라 **델리게이트**여야 한다 — `MethodInfo`를 캐싱해도 `Invoke` 비용은 그대로다(57.13절).

```csharp
static readonly ConcurrentDictionary<Type, Func<object>> _factories = new();

static object Create(Type t) =>
    _factories.GetOrAdd(t, static type =>
    {
        var ctor = type.GetConstructor(Type.EmptyTypes)
            ?? throw new InvalidOperationException($"{type} 에 매개변수 없는 생성자가 없다");
        return Expression.Lambda<Func<object>>(Expression.New(ctor)).Compile();
    })();
```

> **⚠️ 캐시가 메모리를 먹는다 — 바인딩 핸들**
>
> `Type`과 `MemberInfo` 파생 객체는 **메모리를 많이 쓴다.** 이것들을 대량으로 컬렉션에 보관하고 가끔씩만 호출하는 애플리케이션은 메모리 사용량이 크게 늘고 성능이 나빠진다. CLR 내부에는 같은 정보를 훨씬 조밀하게 표현하는 방식이 있고, 이 무거운 객체들은 순전히 **개발자 편의를 위해** 만들어진다.
>
> 대안이 **런타임 핸들**이다. `RuntimeTypeHandle`, `RuntimeFieldHandle`, `RuntimeMethodHandle` 세 값 타입은 전부 `IntPtr` 필드 하나만 갖고, 그 포인터는 로더 힙의 타입·필드·메서드를 가리킨다. 변환은 `type.TypeHandle` ↔ `Type.GetTypeFromHandle`, `fieldInfo.FieldHandle` ↔ `FieldInfo.GetFieldFromHandle`, `methodInfo.MethodHandle` ↔ `MethodBase.GetMethodFromHandle`로 한다.
>
> 코어 라이브러리의 모든 public 타입의 메서드를 `MethodInfo`로 캐싱하면(수만 개) 힙이 수 MB 늘어난다. 같은 목록을 `RuntimeMethodHandle`로 바꿔 담고 `MethodInfo` 참조를 놓아주면 그 대부분이 회수된다.

> **💡 리플렉션을 아예 쓰지 않는 설계가 먼저다**
>
> 동적으로 타입을 발견하고 생성하는 애플리케이션이라면, 다음 둘 중 하나를 택하라.
>
> - 타입들이 **컴파일 타임에 알려진 기저 타입**에서 파생하게 한다. 런타임에 파생 타입을 만들고 기저 타입 변수에 담은 뒤 가상 메서드를 부른다.
> - 타입들이 **컴파일 타임에 알려진 인터페이스**를 구현하게 한다. 런타임에 인스턴스를 만들고 인터페이스 변수에 담은 뒤 인터페이스 메서드를 부른다.
>
> 인터페이스 쪽을 권한다 — 기저 클래스 방식은 개발자가 상황에 맞는 기저 클래스를 고를 자유를 뺏는다. 어느 쪽이든 **그 인터페이스나 기저 타입은 자기만의 어셈블리에 정의**하라(57.10절). 이렇게 하면 리플렉션은 "타입을 찾는" 한 번에만 쓰이고, 이후 모든 호출은 정상 속도로 돈다.

## 57.13 델리게이트 컴파일 / 식 트리로 리플렉션 대체하기

늦은 바인딩 비용의 대부분은 **바인딩** 자체다. 그렇다면 바인딩을 한 번만 하고 그 결과를 재사용하면 된다. 델리게이트가 정확히 그 장치다.

### `Delegate.CreateDelegate` — 가장 단순한 경로

```csharp
delegate string StringToString(string s);

MethodInfo trimMethod = typeof(string).GetMethod("Trim", Type.EmptyTypes)!;
var trim = (StringToString) Delegate.CreateDelegate(
    typeof(StringToString), trimMethod);

for (int i = 0; i < 1_000_000; i++)
    trim("test");
```

비싼 늦은 바인딩(굵게 표시된 두 줄)이 **딱 한 번** 일어난다. 이후 100만 번의 호출은 유의미한 오버헤드가 없다.

여기서 중요한 개념이 **열린 인스턴스 델리게이트(open instance delegate)** 다. 위 코드에서 `Trim`은 인스턴스 메서드인데 대상 객체를 넘기지 않았다. 그래서 델리게이트의 첫 매개변수가 `this`가 된다.

| 만드는 법 | 델리게이트 시그니처 | 용도 |
|---|---|---|
| `CreateDelegate(delType, target, mi)` | 메서드 시그니처 그대로 | 대상 객체가 고정된 경우 |
| `CreateDelegate(delType, mi)` (인스턴스 메서드) | **`this`가 첫 매개변수로 추가** | 여러 인스턴스에 재사용 |
| `CreateDelegate(delType, mi)` (정적 메서드) | 메서드 시그니처 그대로 | 정적 메서드 |

프로퍼티 접근자도 같은 방식으로 델리게이트가 된다.

```csharp
class Person { public string Name { get; set; } = ""; }

PropertyInfo pi = typeof(Person).GetProperty(nameof(Person.Name))!;

// 열린 인스턴스 getter/setter — 어떤 Person 에도 쓸 수 있다
var getName = (Func<Person, string>) pi.GetGetMethod()!
    .CreateDelegate(typeof(Func<Person, string>));
var setName = (Action<Person, string>) pi.GetSetMethod()!
    .CreateDelegate(typeof(Action<Person, string>));

var p = new Person();
setName(p, "Ada");
Console.WriteLine(getName(p));      // Ada

// ※.NET 5 부터는 제네릭 오버로드가 있어 캐스팅이 필요 없다
var getName2 = pi.GetGetMethod()!.CreateDelegate<Func<Person, string>>();
```

> **⚠️ `CreateDelegate`는 시그니처가 정확히 맞아야 한다**
>
> 델리게이트 타입과 메서드 시그니처가 **정확히 호환**되지 않으면 `ArgumentException`이 난다. 암묵적 변환도, 값 타입/`object` 사이의 박싱도 허용되지 않는다. `Func<object, object>`로 `int Add(int, int)`를 감쌀 수 없다.
>
> 반환 타입의 공변성과 매개변수의 반공변성은 **참조 타입에 한해** 허용된다. `Func<Person, object>`로 `string get_Name(Person)`을 감싸는 것은 된다.
>
> 시그니처를 컴파일 타임에 모른다면 `CreateDelegate`로는 부족하다 — 다음의 식 트리를 써야 한다.

### 식 트리로 임의의 시그니처를 `Func<object, object[], object>`로 정규화하기

프레임워크는 대개 "어떤 타입의 어떤 메서드든 `object`를 받고 `object`를 돌려주는 하나의 형태로" 부르고 싶어 한다. 그러려면 캐스팅과 박싱을 하는 어댑터 코드가 필요하고, 그것을 런타임에 만드는 것이 식 트리다.

```csharp
using System.Linq.Expressions;

static Func<object?, object?[], object?> BuildInvoker(MethodInfo method)
{
    // (object? target, object?[] args) => ...
    var targetParam = Expression.Parameter(typeof(object), "target");
    var argsParam   = Expression.Parameter(typeof(object[]), "args");

    // 각 인수를 args[i] 에서 꺼내 실제 매개변수 타입으로 변환
    ParameterInfo[] parameters = method.GetParameters();
    var argExprs = new Expression[parameters.Length];

    for (int i = 0; i < parameters.Length; i++)
    {
        // args[i]
        Expression item = Expression.ArrayIndex(argsParam, Expression.Constant(i));
        // (TParam) args[i]  — 값 타입이면 언박싱, 참조 타입이면 캐스팅
        argExprs[i] = Expression.Convert(item, parameters[i].ParameterType);
    }

    // 인스턴스 메서드면 target 을 선언 타입으로 캐스팅, 정적이면 null
    Expression? instance = method.IsStatic
        ? null
        : Expression.Convert(targetParam, method.DeclaringType!);

    Expression call = Expression.Call(instance, method, argExprs);

    // void 메서드는 null 을 돌려주도록 감싼다
    Expression body = method.ReturnType == typeof(void)
        ? Expression.Block(call, Expression.Constant(null, typeof(object)))
        : Expression.Convert(call, typeof(object));

    return Expression.Lambda<Func<object?, object?[], object?>>(
        body, targetParam, argsParam).Compile();
}
```

사용법은 `MethodInfo.Invoke`와 똑같지만 수십 배 빠르다.

```csharp
MethodInfo mi = typeof(string).GetMethod("Substring", new[] { typeof(int) })!;
var invoker = BuildInvoker(mi);                      // 여기까지가 비싼 일. 캐싱한다.

Console.WriteLine(invoker("stamp", new object?[] { 2 }));   // amp
```

생성된 람다가 하는 일을 C#으로 옮기면 이렇다.

```csharp
(object? target, object?[] args) => (object) ((string) target).Substring((int) args[0])
```

> **📌 식 트리는 IL을 직접 쓰는 것보다 안전하다**
>
> `Expression.Lambda(...).Compile()`은 내부적으로 `DynamicMethod`와 `ILGenerator`로 IL을 방출한다(58.1절). 직접 IL을 쓰는 것과 결과는 같지만, 평가 스택 균형이나 `Callvirt` vs `Call` 선택 같은 실수를 할 여지가 없다. **식 트리로 표현할 수 있는 것이라면 식 트리를 써라.** `Emit`이 필요한 경우는 `try`/`catch`, `ref` 지역 변수, 필드 직접 접근 같은 식 트리가 표현하지 못하는 구조뿐이다.

### 필드 접근자와 그 한계

식 트리는 프로퍼티뿐 아니라 필드에도 접근자를 만들어준다. `Expression.Field(field.IsStatic ? null : objParam, field)`로 접근 식을 만들고 람다로 감싸면 된다.

> **⚠️ 식 트리로는 `readonly` 필드에 쓸 수 없다**
>
> `Expression.Assign(Expression.Field(...), value)`는 `readonly` 필드에 대해 `ArgumentException`을 던진다. `FieldInfo.SetValue`는 (인스턴스 `readonly` 필드에 대해) 성공하지만 느리다. 정말로 `readonly` 필드를 써야 한다면 — 역직렬화기가 그렇다 — `Reflection.Emit`으로 `stfld`를 직접 방출하거나(58.7절), .NET 8 이상이면 `[UnsafeAccessor]`로 `ref` 접근자를 얻는 편이 낫다.
>
> `static readonly` 필드는 어느 방법으로도 초기화 이후 안전하게 바꿀 수 없다. JIT이 그 값을 상수로 인라이닝했을 수 있기 때문이다(55.6절의 상수 폴딩).

### 대안 비교

| 기법 | 준비 비용 | 호출 비용 | 표현력 | Native AOT |
|---|---|---|---|---|
| `MethodInfo.Invoke` | 없음 | 높음 | 완전 | 동작 (트리밍 경고) |
| `Delegate.CreateDelegate` | 매우 낮음 | 최저 | 시그니처가 정확히 맞아야 함 | **동작** |
| `Expression...Compile()` | 높음 (IL 생성) | 최저 | 캐스팅·박싱 어댑터까지 | 인터프리터 폴백 — 느리다 |
| `Reflection.Emit` (58장) | 높음 | 최저 | 완전 | **불가** |
| 소스 생성기 (57.15절) | 없음 (빌드 타임) | 최저 | 컴파일 타임에 아는 것만 | **최적** |

> **💡 손익분기점을 계산하라**
>
> `Expression.Compile()` 한 번은 밀리초 단위다. 호출당 40 ns를 아낀다면 **수만 번은 불러야** 본전이다. 애플리케이션 수명 동안 열 번 부를 메서드라면 `MethodInfo.Invoke`가 낫다. 반대로 ORM의 행 매핑, 직렬화기의 프로퍼티 접근, DI 컨테이너의 객체 생성처럼 **초당 수만 번 도는 자리**라면 컴파일 비용은 즉시 회수된다. 컴파일을 `Lazy<T>`로 지연시켜 실제로 쓰이는 것만 컴파일하면 시작 시간 손해도 줄어든다.

> **⚠️ Native AOT에서 `Compile()`은 인터프리터로 떨어진다**
>
> Native AOT에는 런타임 IL 생성이 없다. `Expression.Compile()`은 실패하는 대신 **식 트리 인터프리터**로 폴백한다. 동작은 하지만 컴파일된 델리게이트보다 훨씬 느리고, 경우에 따라 `MethodInfo.Invoke`보다도 느리다. AOT를 대상으로 한다면 이 경로에 성능을 기대하면 안 된다 — 소스 생성기로 가야 한다(57.15절).

## 57.14 트리밍/AOT에서 리플렉션이 깨지는 지점과 `[DynamicallyAccessedMembers]`

### 트리머는 "아무도 안 부르는 코드"를 지운다

트리밍(trimming, IL 링킹)은 배포 크기를 줄이기 위해 **도달 불가능한 코드를 제거**한다. 진입점에서 출발해 호출 그래프를 따라가며 도달한 것만 남긴다. Native AOT는 여기에 더해 남은 IL을 네이티브 코드로 미리 컴파일하며 **런타임 IL 생성이 아예 없다**(55.7절).

```xml
<PropertyGroup>
  <PublishTrimmed>true</PublishTrimmed>
  <TrimMode>full</TrimMode>
  <PublishAot>true</PublishAot>
</PropertyGroup>
```

문제는 리플렉션이 **호출 그래프에 나타나지 않는 참조**를 만든다는 것이다.

```csharp
Type t = Type.GetType(config.PluginTypeName)!;      // 정적 분석 불가능
object o = Activator.CreateInstance(t)!;            // 생성자가 남아 있는가?
t.GetMethod("Run")!.Invoke(o, null);                // Run 메서드가 남아 있는가?
```

트리머 입장에서 `config.PluginTypeName`은 그냥 `string`이다. 어느 타입인지 알 수 없으니 유지할 이유가 없고, 지운다. 결과는 **런타임의 `null` 참조 예외나 `MissingMethodException`** 이고, 이 실패는 디버그 빌드에서 재현되지 않는다 — 트리밍은 게시할 때만 일어난다.

### 무엇이 깨지고 무엇이 안 깨지나

| 코드 | 트리밍 안전성 | 이유 |
|---|---|---|
| `typeof(Foo)` | 안전 | 정적 참조. 타입이 유지된다 |
| `typeof(Foo).GetMethod("Bar")` | **경고 없음, 그러나 위험** | 타입은 유지되지만 `Bar` 메서드는 지워질 수 있다 |
| `Type.GetType("Ns.Foo")` | **위험** | 문자열은 추적 불가 |
| `Activator.CreateInstance(t)` | **경고 (IL2067 계열)** | `t`가 생성자 보존을 보장하지 않는다 |
| `obj.GetType().GetProperties()` | **경고 (IL2075)** | 반환 타입에 주석이 없다 |
| `MakeGenericType(typeof(int))` | **AOT에서 위험 (IL3050)** | 값 타입 인스턴스화 코드가 없다 |
| `Expression.Compile()` | AOT에서 인터프리터 폴백 | IL 생성 불가 |
| `[UnsafeAccessor]` | **안전** | 트리머가 이해하는 정적 참조다 |
| 소스 생성기 산출물 | **안전** | 평범한 정적 코드다 |

### `[DynamicallyAccessedMembers]` — 트리머에게 알려주기

`System.Diagnostics.CodeAnalysis.DynamicallyAccessedMembersAttribute`는 "이 `Type` 값에 대해 이런 멤버를 리플렉션으로 쓸 것"이라고 선언한다. 트리머는 이 주석을 보고 해당 멤버를 보존하고, **호출자 쪽으로 요구사항을 전파**한다.

```csharp
using System.Diagnostics.CodeAnalysis;

static object CreatePlugin(
    [DynamicallyAccessedMembers(DynamicallyAccessedMemberTypes.PublicConstructors)]
    Type pluginType)
{
    return Activator.CreateInstance(pluginType)!;   // 경고 사라짐
}
```

이제 `CreatePlugin(typeof(MyPlugin))`이라고 부르면 트리머가 `MyPlugin`의 public 생성자를 보존한다. 반대로 `CreatePlugin(someUnannotatedType)`이라고 부르면 **호출 지점에 IL2067 경고**가 나온다 — 요구사항이 호출자로 전파된 것이다.

`DynamicallyAccessedMemberTypes`의 주요 값이다.

| 값 | 보존하는 것 |
|---|---|
| `None` | 없음 |
| `PublicParameterlessConstructor` | 매개변수 없는 public 생성자 |
| `PublicConstructors` | 모든 public 생성자 |
| `NonPublicConstructors` | 모든 비공개 생성자 |
| `PublicMethods` / `NonPublicMethods` | 메서드 |
| `PublicProperties` / `NonPublicProperties` | 프로퍼티 (접근자 포함) |
| `PublicFields` / `NonPublicFields` | 필드 |
| `PublicEvents` / `NonPublicEvents` | 이벤트 |
| `PublicNestedTypes` / `NonPublicNestedTypes` | 중첩 타입 |
| `Interfaces` | 구현 인터페이스 |
| `All` | 전부 (트리밍 효과가 사실상 사라진다) |

붙일 수 있는 자리는 `Type` 또는 `string`(타입 이름) 타입의 **매개변수, 필드, 프로퍼티, 반환값, 제네릭 타입 매개변수**다.

```csharp
// 제네릭 타입 매개변수에도 붙는다
static T Create<[DynamicallyAccessedMembers(
    DynamicallyAccessedMemberTypes.PublicParameterlessConstructor)] T>()
    => Activator.CreateInstance<T>();

// 필드에 붙여 값이 전파되게 한다
[DynamicallyAccessedMembers(DynamicallyAccessedMemberTypes.PublicProperties)]
private readonly Type _modelType;
```

### `[RequiresUnreferencedCode]` — 포기하고 알리기

주석으로 표현할 수 없는 리플렉션도 있다. "설정 파일에 적힌 어떤 타입이든 직렬화한다" 같은 것이다. 이때는 **트리밍과 근본적으로 호환되지 않는다고 선언**한다.

```csharp
[RequiresUnreferencedCode(
    "이 API는 임의 타입을 리플렉션으로 직렬화한다. " +
    "트리밍 대응 오버로드인 Serialize(T, JsonTypeInfo<T>) 를 써라.")]
public static string SerializeAnything(object value) { ... }
```

효과는 두 가지다.

1. **이 메서드 안에서 나던 트리밍 경고가 억제된다.**
2. **이 메서드를 부르는 모든 곳에 IL2026 경고**가 나고, 메시지가 그대로 표시된다.

즉 경고를 없애는 것이 아니라 **경계로 밀어내고 대안을 안내**하는 장치다. Native AOT용 짝은 `[RequiresDynamicCode]`이고 경고 코드는 IL3050이다.

### 주요 경고 코드

| 코드 | 의미 | 전형적 원인 |
|---|---|---|
| IL2026 | `[RequiresUnreferencedCode]`가 붙은 멤버를 호출했다 | 리플렉션 기반 직렬화 API 호출 |
| IL2067 | 매개변수로 넘긴 값의 주석이 대상 매개변수 요구를 만족하지 않는다 | 주석 없는 `Type`을 주석 있는 메서드에 전달 |
| IL2070 | **`this` 인수**의 주석이 부족하다 | `someType.GetMethods()` — `someType`에 주석이 없다 |
| IL2072 | 메서드 **반환값**의 주석이 부족하다 | `obj.GetType()` 결과를 그대로 전달 |
| IL2075 | 반환값에 대해 리플렉션 멤버 접근을 했다 | `obj.GetType().GetProperty(...)` |
| IL2091 | 제네릭 인수의 주석이 타입 매개변수 요구를 만족하지 않는다 | 주석 없는 `T`를 주석 있는 제네릭에 전달 |
| IL3050 | `[RequiresDynamicCode]`가 붙은 멤버를 호출했다 | `MakeGenericType`, `Expression.Compile()` |
| IL2104 / IL3053 | 어셈블리 전체가 트리밍(IL2104) / AOT(IL3053) 경고를 냈다는 요약 | 분석 불가능한 리플렉션을 가진 의존 어셈블리 |

> **⚠️ `obj.GetType()`은 트리밍의 블랙홀이다**
>
> ```csharp
> void Dump(object obj)
> {
>     foreach (var p in obj.GetType().GetProperties())   // IL2075
>         Console.WriteLine(p.Name + "=" + p.GetValue(obj));
> }
> ```
>
> `object.GetType()`의 반환값에는 주석이 없고, 붙일 수도 없다 — 어떤 타입이 들어올지 알 수 없기 때문이다. 이 패턴은 **주석으로 해결되지 않는다.** 선택지는 셋이다.
>
> 1. 제네릭으로 바꿔 `[DynamicallyAccessedMembers]`를 `T`에 붙인다.
> 2. `[RequiresUnreferencedCode]`로 경계를 만들고 호출자에게 알린다.
> 3. 소스 생성기로 대체한다 (57.15절).
>
> `[UnconditionalSuppressMessage]`로 경고를 끄는 것은 **트리머가 못 보는 다른 경로로 그 멤버가 확실히 보존됨을 스스로 증명했을 때만** 정당하다. 그냥 조용히 하려고 쓰면 게시 후에 터진다.

### 명시적 보존 — 최후의 수단

주석으로도 안 되면 트리머에게 직접 "이건 남겨라"라고 말한다. 멤버 단위로는 `[DynamicDependency]`를 쓴다 — 이 특성이 붙은 메서드가 살아 있으면 지정한 대상도 함께 보존된다.

```csharp
[DynamicDependency(DynamicallyAccessedMemberTypes.PublicConstructors, typeof(MyPlugin))]
static void EnsurePluginPreserved() { }
```

어셈블리 단위로는 `ILLink.Descriptors.xml`을 쓰고 `.csproj`에서 `<TrimmerRootDescriptor Include="ILLink.Descriptors.xml" />`로 등록한다. 어셈블리를 통째로 보존하려면 `<TrimmerRootAssembly Include="MyPlugin" />`이다.

```xml
<linker>
  <assembly fullname="MyPlugin">
    <type fullname="MyPlugin.Widget" preserve="all" />
    <type fullname="MyPlugin.Gadget">
      <method name="Run" />
    </type>
  </assembly>
</linker>
```

> **💡 실무 절차**
>
> 라이브러리라면 `<IsTrimmable>true</IsTrimmable>`과 `<IsAotCompatible>true</IsAotCompatible>`(※.NET 8)을 켜서 개발 중에 분석기 경고를 받아라. 애플리케이션이라면 **CI에서 `<PublishTrimmed>`로 게시까지** 해보고 경고를 0으로 만들되, **게시 산출물을 실제로 실행하는 스모크 테스트**도 넣어라 — 경고 0이 동작 보장은 아니다. 그리고 경고를 억제하기 전에 항상 물어라: 이 리플렉션을 `[UnsafeAccessor]`나 소스 생성기로 없앨 수 있는가?

> **⚠️ 트리밍 실패는 조용하다**
>
> 트리밍의 가장 나쁜 성질은 실패가 **게시 산출물에서만, 그것도 그 코드 경로가 실행될 때만** 드러난다는 것이다. "설정 파일에서 플러그인 이름을 읽는" 코드는 기본 설정 스모크 테스트를 통과하고 고객 환경에서 터진다. Native AOT는 조금 낫다 — 상당수 문제가 **게시 시점에** 오류로 잡힌다. 그래도 `MakeGenericType`처럼 런타임에만 드러나는 것이 남는다.

## 57.15 소스 생성기(Source Generator) — 컴파일 타임 대안

### 발상의 전환

지금까지 본 모든 기법 — 리플렉션, 델리게이트 캐싱, 식 트리, `Emit` — 은 **런타임에** 메타데이터를 읽고 코드를 만든다. 소스 생성기는 같은 일을 **컴파일 타임에** 한다. 컴파일러가 소스를 파싱한 뒤, 생성기가 그 구문 트리와 심볼 정보를 보고 추가 C# 소스를 만들어 **같은 컴파일에 넣는다.**

| 기준 | 런타임 리플렉션 | 소스 생성기 |
|---|---|---|
| 실행 시점 | 런타임 | 빌드 타임 |
| 시작 시간 비용 | 있음 (조회 + 컴파일) | **없음** |
| 호출 비용 | 높음 또는 델리게이트 캐싱 필요 | **직접 호출** |
| 타입 안전성 | 런타임 | **컴파일 타임** |
| 트리밍/AOT | 위험 | **완전 호환** |
| 디버깅 | 생성된 IL을 볼 수 없음 | **생성된 C#에 중단점을 찍을 수 있음** |
| 동적 타입 지원 | 가능 | **불가능** — 컴파일 타임에 알아야 한다 |

마지막 행이 결정적 제약이다. 컴파일 타임에 알려진 타입에만 쓸 수 있다. 그 조건을 만족한다면 소스 생성기가 모든 면에서 낫다.

### `System.Text.Json` 소스 생성

리플렉션 기반 `JsonSerializer`는 대상 타입의 프로퍼티를 런타임에 탐색한다. 그래서 두 특성이 붙어 있다 — `[RequiresUnreferencedCode]`와 `[RequiresDynamicCode]`. 트리밍 앱에서 이 API를 부르면 IL2026과 IL3050이 나온다.

소스 생성 모드는 이렇게 쓴다.

```csharp
using System.Text.Json;
using System.Text.Json.Serialization;

public record WeatherForecast(DateTimeOffset Date, int TemperatureC, string? Summary);

[JsonSourceGenerationOptions(PropertyNamingPolicy = JsonKnownNamingPolicy.CamelCase)]
[JsonSerializable(typeof(WeatherForecast))]
[JsonSerializable(typeof(List<WeatherForecast>))]
internal partial class AppJsonContext : JsonSerializerContext
{
}
```

`partial` 클래스가 핵심이다. 생성기가 나머지 절반을 만들어 채운다.

```csharp
var forecast = new WeatherForecast(DateTimeOffset.Now, 21, "맑음");

// 소스 생성 경로 — 리플렉션 없음, 트리밍 경고 없음
string json = JsonSerializer.Serialize(forecast, AppJsonContext.Default.WeatherForecast);

var back = JsonSerializer.Deserialize(json, AppJsonContext.Default.WeatherForecast);
```

생성기가 만드는 것은 각 프로퍼티에 대한 **직접 접근 코드**다 — `Getter = static obj => ((WeatherForecast) obj).TemperatureC` 같은 정적 람다와, 그것을 엮은 메타데이터 테이블. 리플렉션이 런타임에 만들어내던 것을 컴파일러가 미리 써 둔 것이다. 결과는 **시작이 빠르고, 처리량이 높고, 트리밍에 안전하다.**

> **💡 리플렉션 폴백을 아예 꺼라**
>
> 소스 생성 컨텍스트를 만들어 놓고도 실수로 리플렉션 오버로드를 부르면 조용히 느린 경로를 탄다. ※.NET 8부터 다음 스위치로 리플렉션 경로를 컴파일 타임에 제거할 수 있다.
>
> ```xml
> <PropertyGroup>
>   <JsonSerializerIsReflectionEnabledByDefault>false</JsonSerializerIsReflectionEnabledByDefault>
> </PropertyGroup>
> ```
>
> 이제 리플렉션 오버로드를 부르면 `InvalidOperationException`이 난다. 빌드 크기도 줄어든다.

### `[LoggerMessage]` — 로깅

`ILogger.LogInformation("User {UserId} logged in", id)`는 매 호출마다 템플릿을 파싱하고 인수를 `object[]`에 담아 박싱한다. 로그 레벨이 꺼져 있어도 그 일을 한다.

```csharp
using Microsoft.Extensions.Logging;

public static partial class Log
{
    [LoggerMessage(
        EventId = 1001,
        Level = LogLevel.Information,
        Message = "User {UserId} logged in from {Address}")]
    public static partial void UserLoggedIn(
        ILogger logger, int userId, string address);
}
```

생성기가 만드는 구현은 템플릿을 **컴파일 타임에 파싱**해 두고, 로그 레벨 검사를 먼저 하고, 인수를 강타입으로 넘긴다. 박싱과 배열 할당이 사라진다. 호출은 `Log.UserLoggedIn(logger, 42, "10.0.0.1");`이다.

> **⚠️ `partial` 메서드에는 규칙이 있다**
>
> `[LoggerMessage]`가 붙는 메서드는 `partial`이어야 하고, 본문이 없어야 하고, 담는 클래스도 `partial`이어야 한다. 반환 타입은 `void`, `ref`/`out` 매개변수는 쓸 수 없다. 정적 메서드라면 `ILogger` 매개변수가 반드시 있어야 한다. 규칙을 어기면 생성기가 명확한 진단을 낸다 — **컴파일 타임에** 잡히는 것이 리플렉션 대비 장점이다.

### `[GeneratedRegex]` ※.NET 7 / C# 11 — 정규식

`new Regex(pattern)`은 런타임에 패턴을 파싱해 인터프리터용 노드 트리를 만든다. `RegexOptions.Compiled`를 주면 `Reflection.Emit`으로 IL을 방출한다 — 빠르지만 첫 사용 비용이 크고 Native AOT에서는 불가능하다.

```csharp
using System.Text.RegularExpressions;

public partial class Validator
{
    [GeneratedRegex(@"^[\w\.\-]+@[\w\-]+\.\w{2,}$", RegexOptions.IgnoreCase)]
    private static partial Regex EmailRegex();

    public bool IsEmail(string s) => EmailRegex().IsMatch(s);
}
```

생성기가 **패턴 전용 매칭 코드를 C#으로 써 준다.** 런타임 파싱도, IL 방출도 없다. 성능은 `RegexOptions.Compiled`와 비슷하거나 더 낫고, 시작이 즉시이며, AOT에서 그대로 동작한다. 게다가 생성된 코드에 중단점을 찍고 단계 실행할 수 있다.

> **📌 리플렉션을 없애는 대표적 생성기들**
>
> | 생성기 | 대체하는 리플렉션 |
> |---|---|
> | `System.Text.Json` 소스 생성 | 프로퍼티 탐색, 접근자 델리게이트 생성 |
> | `[LoggerMessage]` | 템플릿 파싱, 인수 박싱 |
> | `[GeneratedRegex]` | 패턴 파싱, `Reflection.Emit` |
> | `[LibraryImport]` ※.NET 7 | `DllImport`의 런타임 마샬링 스텁 생성 |
> | ASP.NET Core Request Delegate Generator ※.NET 8 | Minimal API 엔드포인트의 매개변수 바인딩 |
> | `[JSImport]` / `[JSExport]` | WASM 상호운용 스텁 |
> | 여러 DI 컨테이너의 컴파일 타임 모드 | 생성자 탐색, 팩터리 생성 |

### 언제 무엇을 고를까

```text
컴파일 타임에 타입을 아는가?
 ├─ 예 →  소스 생성기          (최선. 시작·처리량·AOT 모두 유리)
 │        대안: [UnsafeAccessor] — 비공개 멤버 하나에 접근하는 경우
 └─ 아니오 (런타임에만 안다)
      ├─ 호출 횟수가 적다     → MethodInfo.Invoke / MethodInvoker (단순함이 이긴다)
      ├─ 호출 횟수가 많다
      │    ├─ 시그니처를 안다 → Delegate.CreateDelegate  (AOT 가능)
      │    └─ 시그니처를 모른다 → Expression...Compile()  (AOT면 인터프리터)
      └─ 타입 자체를 만들어야 한다 → Reflection.Emit (58장) — AOT 불가
```

> **💡 리플렉션을 지우는 것이 목표가 아니다**
>
> 소스 생성기는 만능이 아니다. 작성과 디버깅이 까다롭고, 빌드 시간을 늘리고, 증분 빌드를 잘못 설계하면 IDE가 느려진다. 그리고 **런타임에 결정되는 타입에는 원리적으로 쓸 수 없다.** 판단 기준은 명확하다 — **시작 시간, 처리량, 트리밍/AOT 중 하나라도 요구사항이면** 소스 생성기를 검토하고, 그렇지 않고 초기화 때 몇 번 도는 코드라면 리플렉션이 훨씬 단순하다. 57.10절의 원칙 — **발견에는 리플렉션, 호출에는 인터페이스** — 만 지켜도 대부분의 애플리케이션에서 리플렉션은 문제가 되지 않는다.

## 이 장의 요약

- **`Type` 하나가 타입 메타데이터 전체로 향하는 창**이다. `typeof`(빠름), `GetType()`(인스턴스), `Assembly.GetType`(이름), `Type.GetType`(어셈블리 정규화 이름) 네 경로로 얻는다. `typeof(X)`가 돌려주는 실체는 `RuntimeType`이고, 타입당 프로세스에 하나뿐이다.
- **타입 이름 규칙에서 `FullName`이 단순 결합이 아닌 예외는 둘**(중첩 — `+`, 닫힌 제네릭 — 인수의 어셈블리 정규화 이름까지)이고, 여기에 접미사 규칙 셋(언바운드 제네릭의 백틱+개수, 배열의 `[]`, 참조·포인터의 `&`·`*`)이 더해진다. 문자열로 타입을 다루는 코드의 사고는 대부분 여기서 난다.
- **`MemberInfo` 계층의 뿌리에 `Type`이 있다.** 중첩 타입이 멤버이기 때문이다. `DeclaringType`과 `ReflectedType`이 갈리므로 `MethodInfo`를 캐시 키로 쓰면 안 된다 — `MethodHandle`이나 `(MetadataToken, Module)`을 써라.
- **C# 멤버와 CLR 멤버는 1:1이 아니다.** 프로퍼티는 `get_`/`set_`, 이벤트는 `add_`/`remove_`, 인덱서는 `Item`, 연산자는 `op_`, 종료자는 `Finalize`로 번역된다. `GetMethods()`는 이들을 전부 돌려주며 `IsSpecialName`으로 걸러야 한다.
- **`BindingFlags` 기본값은 `Public | Instance | Static`** 이고, 기저 타입의 정적 멤버(`FlattenHierarchy` 필요), 비공개 멤버(`NonPublic` 필요), 생성자, 명시적 인터페이스 구현을 빠뜨린다. **기저 타입의 private 멤버는 어떤 플래그로도 안 나온다** — 계보를 직접 걸어야 한다.
- **동적 호출의 예외는 `TargetInvocationException`으로 감싸인다.** 진짜 원인은 `InnerException`에 있다. 생성자에 도달하기 전 실패는 감싸지 않는다.
- **언바운드 제네릭의 멤버는 호출할 수 없다.** 런타임에 닫힌 인터페이스를 찾아(`GetInterfaces` + `GetGenericTypeDefinition` 비교) 그쪽 멤버를 부르는 것이 정석이다. 정적 추상 인터페이스 멤버는 `GetInterfaceMap`으로 구체 타입의 구현을 찾아야 한다.
- **특성은 세 종류다** — 비트 매핑(수정자 키워드), 커스텀(확장 가능), 의사 커스텀(소스는 커스텀, 저장은 비트). `IsDefined`는 인스턴스를 만들지 않아 싸고, `CustomAttributeData`는 아예 코드를 실행하지 않는다.
- **리플렉션 호출은 직접 호출보다 두세 자릿수 느리다.** 조회 결과를 `MethodInfo`로 캐싱해도 `Invoke` 비용은 남는다. **델리게이트를 캐싱해야** 나노초 영역으로 내려간다. .NET 8의 `MethodInvoker`와 `[UnsafeAccessor]`가 중간·최상의 선택지를 새로 만들었다.
- **트리밍과 Native AOT는 리플렉션을 조용히 깨뜨린다.** `[DynamicallyAccessedMembers]`로 요구사항을 선언하고 전파시키거나, `[RequiresUnreferencedCode]`/`[RequiresDynamicCode]`로 경계를 만들어 호출자에게 알려야 한다. `obj.GetType().GetProperties()`는 주석으로 해결되지 않는 패턴이다.
- **컴파일 타임에 타입을 안다면 소스 생성기가 모든 면에서 낫다.** `System.Text.Json` 소스 생성, `[LoggerMessage]`, `[GeneratedRegex]`, `[LibraryImport]`가 각각 런타임 리플렉션을 정적 코드로 대체한다.
- **가장 중요한 원칙 — 발견에는 리플렉션, 호출에는 인터페이스.** 객체를 만든 직후 컴파일 타임에 알려진 인터페이스로 캐스팅하면 그 뒤로는 리플렉션 비용이 없다.

## 연습 문제

1. `typeof(Dictionary<int, string>)`, `typeof(Dictionary<,>)`, `typeof(int[,])`, `typeof(Environment.SpecialFolder)`의 `Name`, `FullName`, `AssemblyQualifiedName`을 모두 출력하라. 그다음 각 `AssemblyQualifiedName`을 `Type.GetType`에 다시 넣어 원래 타입과 참조 동등한지 확인하라. 실패하는 것이 있다면 왜인가?
2. 자기 클래스 하나에 프로퍼티·인덱서·이벤트·연산자 오버로드·종료자를 모두 넣고 `GetMethods()`를 출력하라. `IsSpecialName`으로 걸러낸 목록과 비교해 어떤 메서드가 사라지는지 확인하라. `Finalize`는 어느 쪽에 속하는가?
3. 기저 클래스에 `private int _id;`를, 파생 클래스에 `private string _name;`을 두고, 파생 클래스의 `Type`에서 `GetField("_id", BindingFlags.NonPublic | BindingFlags.Instance)`를 호출하라. 결과가 `null`임을 확인하고, 57.7절의 계보 순회 함수로 찾아내라.
4. `MethodInfo.Invoke`, 캐시된 `MethodInfo.Invoke`, `Delegate.CreateDelegate` 결과, `Expression.Lambda(...).Compile()` 결과, 직접 호출을 BenchmarkDotNet으로 측정하라. `[MemoryDiagnoser]`를 켜서 **호출당 할당 바이트**도 함께 비교하라. 인수를 `int` 두 개에서 `string` 두 개로 바꾸면 할당이 어떻게 달라지는가?
5. .NET 8 이상에서 `[UnsafeAccessor]`로 `List<T>`의 내부 배열 필드(`_items`)에 접근하는 접근자를 작성하고, 같은 일을 `FieldInfo.GetValue`로 한 것과 성능을 비교하라. 필드 이름을 일부러 틀리게 쓰면 언제 어떤 예외가 나는가?
6. `[Test(20, FailureMessage = "...")]`이 붙은 메서드를 가진 클래스를 만들고, `GetCustomAttributes`와 `GetCustomAttributesData` 두 방법으로 같은 정보를 출력하라. 특성 클래스의 생성자에 `Console.WriteLine`을 넣어 어느 쪽이 그것을 실행하는지 확인하라.
7. 간단한 플러그인 호스트를 만들어 `<PublishTrimmed>true</PublishTrimmed>`로 게시하고 실행하라. 어떤 지점에서 깨지는지 확인한 뒤, `[DynamicallyAccessedMembers]`와 `ILLink.Descriptors.xml` 두 방법으로 각각 고쳐라. 게시 산출물의 크기 차이는 얼마인가?
8. 리플렉션으로 객체를 JSON으로 직렬화하는 100줄짜리 함수를 작성하고, 같은 타입에 대해 `System.Text.Json` 소스 생성 컨텍스트를 만들어 처리량과 첫 호출 지연을 비교하라. 그다음 `<PublishAot>true</PublishAot>`로 게시해 어느 쪽이 살아남는지 확인하라.
