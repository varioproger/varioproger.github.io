# 54장. 타입 시스템의 런타임 표현

> **이 장의 위치** — 52장에서 어셈블리가 타입의 컨테이너이고 메타데이터 테이블이 타입의 "정적" 기술이라는 것을 보았다. 이 장은 그다음 질문에 답한다. 그 메타데이터가 런타임에 **어떤 자료구조로 실체화되고**, 그 타입의 인스턴스가 **메모리에서 실제로 어떻게 생겼는가**. 객체 헤더부터 `MethodTable`, 필드 정렬, 박싱된 값의 바이트 배치까지 끝까지 판다. 이 장을 지나고 나면 "참조 변수에 뭐가 들어 있는가"라는 질문에 바이트 단위로 답할 수 있어야 한다.
>
> **선수 지식** — 15장(`object` 타입과 박싱), 16장(구조체와 값 타입), 52장(어셈블리)
>
> **이 장에서 다루지 않는 것** — IL을 네이티브 코드로 바꾸는 과정과 계층형 컴파일은 55장에서, GC 힙의 물리적 구조(세대·세그먼트·리전)는 62장에서, 할당 경로 자체는 63장에서, 박싱을 실무에서 제거하는 기법은 69장에서 다룬다. 이 장은 "무엇이 어디에 어떻게 놓이는가"만 본다.

---

## 54.1 `MethodTable` 해부 — TypeHandle, 슬롯 테이블, 인터페이스 맵

### 타입이란 무엇인가

ECMA-335는 타입을 "값을 기술하고, 그 타입의 모든 값이 지원해야 할 계약을 명시하는 것"으로 정의한다. 추상적인 정의다. 구현 관점에서는 훨씬 구체적으로 말할 수 있다.

**.NET의 모든 타입은 `MethodTable`이라는 자료구조로 표현된다.** 런타임이 "이 타입이 뭐지"라고 물을 때마다 참조하는 것이 이 구조체다. 실행 엔진과 가비지 컬렉터가 협력하는 기본 building block이며, 이 책의 남은 절반에서 계속 등장한다.

`MethodTable`이 담는 것 중 중요한 것들은 다음과 같다.

| 항목 | 내용 | 누가 쓰는가 |
|---|---|---|
| **GCInfo** | 가비지 컬렉터용 자료구조. 이 타입의 인스턴스 안에서 참조 필드가 어느 오프셋에 있는지 기술한다 | GC (Mark 단계) |
| **Flags** | 타입의 각종 속성(배열인가, 값 타입인가, 인터페이스가 있는가 등) | 런타임 전반 |
| **Basic instance size** (`m_BaseSize`) | 이 타입의 인스턴스가 힙에서 차지하는 기본 크기 | 할당자, GC |
| **EEClass 참조** | "차가운(cold)" 데이터. 타입 로딩·JIT·리플렉션에만 필요한 것들 — 모든 메서드·필드·인터페이스의 기술 | 타입 로더, JIT, 리플렉션 |
| **메서드 기술(슬롯 테이블)** | 상속받은 것을 포함한 **모든 메서드**를 호출하기 위해 필요한 정보 | JIT, 가상 디스패치 |
| **정적 필드 관련 데이터** | 기본형 정적 필드의 위치 정보 (54.5절) | JIT |

런타임은 **`MethodTable`의 주소**를 타입의 신원으로 사용한다. 이 주소에 붙은 이름이 **`TypeHandle`(타입 핸들)** 이다. "타입 핸들"이라는 말이 나오면 그것은 사실상 "그 타입의 `MethodTable`이 있는 주소"라고 읽으면 된다.

> **📌 왜 이름이 하필 "메서드 테이블"인가**
>
> 이름만 보면 메서드 목록처럼 들리지만, 실제로는 타입에 대한 거의 모든 런타임 정보가 여기 모인다. 이름이 이런 이유는 이 구조체의 **끝에 붙어 있는 가변 길이 슬롯 테이블**이 원래의 핵심이었기 때문이다. C++의 vtable에 해당하는 부분이며, 구조체 전체가 그 이름을 물려받았다.

### `MethodTable`의 메모리 배치

`MethodTable`은 **고정 크기 부분 뒤에 가변 길이 영역이 이어지는** 구조다. 고정 부분에는 앞의 표에 정리한 값들(플래그, 기본 인스턴스 크기, 부모 타입, `EEClass` 참조 등)이 놓이고, 그 뒤에 메서드 슬롯 테이블과 인터페이스 관련 데이터가 이어진다.

```text
  TypeHandle ─▶┌──────────────────────────────────────────┐
               │  Flags            타입 속성 플래그          │
               │  기본 인스턴스 크기   힙 인스턴스의 기본 크기   │   고정 크기 부분
               │  부모 타입의 MethodTable                    │
               │  EEClass 참조      "차가운" 데이터로 가는 길   │
               │  GCInfo · 정적 필드 관련 데이터 …            │
               ├──────────────────────────────────────────┤
               │  슬롯 테이블 (C++의 vtable에 해당)           │
               │   [0] System.Object.ToString()            │   가변 길이
               │   [1] System.Object.Equals(Object)        │
               │   [2] System.Object.GetHashCode()         │
               │   [3] System.Object.Finalize()            │
               │   [4] SomeClass.VirtualMethod()           │
               │   ...                                     │
               ├──────────────────────────────────────────┤
               │  인터페이스 맵 등 인터페이스 관련 데이터 …      │
               └──────────────────────────────────────────┘
```

> **⚠️ 필드 이름·순서·오프셋은 문서화된 계약이 아니다**
>
> 위 그림이 말하는 것은 "무엇이 `MethodTable`에 들어 있는가"뿐이다. 각 항목의 실제 필드 이름, 배치 순서, 바이트 오프셋, 고정 부분의 크기는 **CoreCLR의 구현 세부이며 런타임 버전에 따라 달라진다.** 어떤 코드도 이 배치에 의존해서는 안 되고, 이 장의 설명도 특정 오프셋을 전제로 하지 않는다.

여기서 두 가지를 눈여겨보자.

**첫째, 할당자가 `MethodTable`에서 가장 먼저 읽는 값이 인스턴스 기본 크기(`m_BaseSize`)다.** 63장에서 볼 SOH 할당 헬퍼의 첫 명령이 정확히 이것이다.

```text
; rcx에 MethodTable 포인터가 들어온다
mov     edx, [rcx + OFFSET__MethodTable__m_BaseSize]   ; 객체 크기를 읽는다
; m_BaseSize는 항상 8의 배수임이 보장된다
```

객체 하나를 만들 때마다 실행되는 코드가 `MethodTable`에서 이 값을 읽는다. 크기가 "뜨거운" 데이터인 이유다.

**둘째, `EEClass` 참조가 별도로 있다.** 이것이 뜨거운 데이터와 차가운 데이터의 분리다.

### 뜨거운 `MethodTable`, 차가운 `EEClass`

| | `MethodTable` | `EEClass` |
|---|---|---|
| 접근 빈도 | 매우 높음 (할당·가상 호출·형변환·GC마다) | 낮음 (타입 로딩·JIT·리플렉션) |
| 담는 것 | 크기, 플래그, 슬롯 테이블 | 모든 메서드·필드·인터페이스의 기술 |
| 사는 곳 | 도메인의 High Frequency Heap | 도메인의 Low Frequency Heap |

런타임이 이 둘을 나눈 이유는 **접근 빈도**다. 실행 중 계속 읽히는 정보(크기, 슬롯 주소)만 작게 모아 두면 CPU 캐시와 페이지 관리에 유리하다. 그래서 자주 접근되는 타입 정보는 High Frequency Heap에, 타입 로딩·JIT·리플렉션에만 필요한 `EEClass` 같은 데이터는 Low Frequency Heap에 놓인다(54.5절).

> **📌 `!dumpmt`가 보여주는 것**
>
> WinDbg + SOS의 `!dumpmt` 명령은 `MethodTable`이 담고 있는 정보를 보여준다. `EEClass:`, `BaseSize:`, `ComponentSize:`, `Slots in VTable:` 같은 줄이 위에서 본 항목들에 대응한다. 54.10절에서 실제 출력을 본다.

### 슬롯 테이블과 세 가지 호출

`MethodTable`의 슬롯 테이블에는 **타입이 새로 도입한 메서드와 상속받은 가상 메서드가 모두** 들어간다. 인터페이스 메서드도 포함된다. 다음 타입을 보자.

```csharp
internal sealed class SimpleType : IDisposable
{
    public void Dispose() => Console.WriteLine("Dispose");
}
```

`SimpleType`의 슬롯 테이블에는 ① `System.Object`가 정의한 모든 가상 인스턴스 메서드(암시적 기본 클래스), ② 상속한 인터페이스 `IDisposable`이 정의한 모든 인터페이스 메서드 — 여기서는 `Dispose` 하나, ③ `SimpleType`이 새로 도입한 `Dispose` 메서드가 들어간다.

C# 컴파일러는 `SimpleType`이 도입한 `Dispose`가 `IDisposable.Dispose`의 구현이라고 **가정한다.** public이고 시그니처가 같기 때문이다. 그리고 두 슬롯이 **같은 구현을 가리키라는** 메타데이터를 방출한다. 새 `Dispose`에 `virtual`이 붙어 있어도 컴파일러는 여전히 인터페이스 메서드와 일치한다고 본다.

호출 방식에 따라 JIT이 하는 일이 달라진다.

| 호출 종류 | JIT이 하는 일 | 런타임 비용 |
|---|---|---|
| **정적 메서드** | 그 메서드를 **정의한 타입**의 `MethodTable`을 찾고, 해당 슬롯을 찾아 직접 호출 | 간접 참조 0회 |
| **비가상 인스턴스 메서드** | 호출에 쓰인 **변수의 정적 타입**에 해당하는 `MethodTable`에서 슬롯을 찾아 직접 호출. 그 타입이 메서드를 정의하지 않았다면 **부모 타입을 가리키는 필드**를 따라 `Object` 쪽으로 내려가며 찾는다 | 간접 참조 0회 |
| **가상 인스턴스 메서드** | **객체를 따라가서** 그 객체의 `MethodTable` 포인터를 읽고, 거기서 슬롯을 찾아 호출 | 간접 참조 2회 |

세 번째가 다형성의 실체다. `Employee e`가 실제로는 `Manager` 인스턴스를 가리킨다면, 가상 호출은 **변수의 정적 타입이 아니라 객체가 들고 있는 `MethodTable` 포인터**를 따라간다. 그래서 `Manager`의 재정의 구현이 실행된다.

```text
  스택                      관리 힙
┌──────────┐          ┌──────────────────┐        ┌────────────────────┐
│ e ●──────┼─────────▶│ 싱크 블록 인덱스   │        │  Manager MethodTable│
│          │          ├──────────────────┤   ┌───▶│  Flags              │
│ year = 5 │          │ MethodTable 참조 ●┼───┘    │  기본 인스턴스 크기    │
└──────────┘          ├──────────────────┤        │  ...                │
                      │ 인스턴스 필드들    │        │  [슬롯] Manager.    │
                      └──────────────────┘        │    GetProgressReport│
                                                  └────────────────────┘
                       가상 호출: e → MT → 슬롯 → 코드 (간접 참조 2회)
```

> **⚠️ 인터페이스 호출은 슬롯 테이블을 그냥 따라가지 않는다**
>
> 위 표의 세 경로는 모두 슬롯 테이블을 인덱싱한다. 인터페이스 메서드 호출은 다르다. 런타임은 여기에 전통적인 가상 메서드 테이블 대신 **가상 스텁 디스패치(virtual stub dispatch, VSD)** 기법을 쓴다 — 스텁과 캐시 자료구조로 "이 인터페이스 메서드가 이 객체에서는 어느 구현인가"를 풀어낸다(그 자료구조들이 사는 곳이 54.5절에서 볼 Virtual Call Stub 힙이다).
>
> 타입이 구현한 인터페이스 목록 자체는 `MethodTable`이 **인터페이스 맵(interface map)** 으로 들고 있다 — `!dumpmt`가 보여주는 `Number of IFaces in IFaceMap:` 줄이 그 항목 개수다(54.10절). 하지만 그 맵을 실제 호출이 어떻게 소비하는지는 위에서 말한 스텁과 캐시의 몫이다.
>
> 그러니 "인터페이스 호출은 가상 호출과 똑같은 비용"이라고 단정해서는 안 된다. 정확한 비용은 캐시가 더워졌는지에 달린 구현 세부다. 다만 반대 방향의 오해도 조심하라 — JIT의 역가상화(devirtualization)와 가드된 역가상화가 많은 경우 이 비용을 아예 없앤다(55.5절).

### `MethodTable`과 `System.Type` 객체는 다르다

`typeof(Manager)`가 돌려주는 것은 `System.Type`에서 파생된 객체다. 이것을 **타입 객체(type object)** 라고 부른다. 타입 객체 자체도 힙 위의 객체이므로, 타입 객체 역시 자기 헤더와 자기 `MethodTable` 포인터를 가진다.

여기서 재귀가 발생한다. `Manager` 타입 객체의 `MethodTable` 포인터는 무엇을 가리키는가? **`System.Type`의 타입 객체**를 가리킨다. 그러면 `System.Type` 타입 객체의 `MethodTable` 포인터는? **자기 자신**이다. `System.Type` 타입 객체는 자기 자신의 "인스턴스"이기 때문이다. 여기서 재귀가 끝난다.

```text
   Manager 객체            Manager 타입 객체         Type 타입 객체
┌──────────────┐        ┌──────────────┐        ┌──────────────┐
│ 헤더          │        │ 헤더          │        │ 헤더          │
│ MT 참조 ●─────┼───────▶│ MT 참조 ●─────┼───────▶│ MT 참조 ●─┐   │
│ 인스턴스 필드  │        │ 정적 필드     │        │ 정적 필드  │   │
└──────────────┘        │ 슬롯 테이블   │        │ 슬롯 테이블│   │
                        └──────────────┘        └───────────┼──┘
                                                     ▲      │
                                                     └──────┘
                                                    자기 자신을 가리킨다
```

> **⚠️ 위 그림에서 "정적 필드" 칸은 그대로 믿지 마라**
>
> 이 그림은 『CLR via C#』이 그린 .NET Framework 시절의 개념 모델이다. "타입의 정적 필드를 받쳐 주는 바이트는 타입 객체 안에 할당된다"는 것이 당시의 서술이었고, 실제로 .NET Framework에서는 statics blob이 그 타입의 `MethodTable` 옆에 놓였다. **현재 .NET은 다르다** — 정적 필드는 종류에 따라 모듈 단위 statics blob, 공유 핸들 테이블, NonGC 힙으로 나뉘어 저장된다(54.5절). 그림에서 지금도 유효한 것은 **"객체 → 타입 객체 → `System.Type` 타입 객체 → 자기 자신"** 이라는 참조 사슬이다.

`System.Object.GetType()`이 하는 일은 단순하다. **객체의 타입 객체 포인터에 저장된 주소를 그대로 반환한다.** 그래서 이 메서드는 `virtual`이 아니다. 재정의해서 다른 타입인 척하는 것이 불가능해야 타입 안전성이 유지되기 때문이다.

> **📌 "타입 객체 포인터"와 "`MethodTable` 참조"는 같은 것을 다르게 부르는 이름이다**
>
> 『CLR via C#』은 이 필드를 **타입 객체 포인터(type object pointer)** 라고 부르고, 『Pro .NET Memory Management』는 **`MethodTable` 참조**라고 부른다. 전자는 CLR의 개념적 모델("모든 객체는 자기 타입 객체를 가리킨다")에서 온 이름이고, 후자는 CoreCLR 소스 코드의 실제 자료구조 이름이다. 이 책에서는 구현을 다룰 때 `MethodTable`, 개념을 다룰 때 타입 객체라고 쓴다.

> **💡 리플렉션이 느린 이유의 절반이 여기 있다**
>
> `MethodTable`은 실행에 필요한 최소 정보만 뜨겁게 유지한다. 메서드 이름, 매개변수 이름, 특성 같은 것은 `EEClass`와 그 너머의 메타데이터에 있다. `typeof(T).GetMethods()`를 호출하면 런타임은 차가운 쪽 자료구조를 훑고, 없으면 메타데이터 테이블(52.2절)까지 파고들어 `MethodInfo` 객체를 새로 만든다. 리플렉션 결과를 캐싱해야 하는 이유다(57.12절).

## 54.2 객체 헤더(싱크 블록 인덱스)와 메서드 테이블 참조 — 왜 헤더가 "음수 인덱스"인가

### `new`가 실제로 하는 일

CLR은 모든 객체를 `new` 연산자로 만들 것을 요구한다.

```csharp
Employee e = new Employee("ConstructorParam1");
```

`new`가 하는 일은 네 단계다.

1. 타입과 그 **모든 기저 타입**(`System.Object`까지)이 정의한 인스턴스 필드가 요구하는 바이트 수를 계산하고, CLR이 객체를 관리하는 데 쓰는 **부가 멤버 두 개** — 타입 객체 포인터와 싱크 블록 인덱스 — 의 크기를 더한다.
2. 관리 힙에서 그만큼의 바이트를 할당한다. **할당된 바이트는 모두 0으로 채워진다.**
3. 타입 객체 포인터와 싱크 블록 인덱스를 초기화한다.
4. 타입의 인스턴스 생성자를 호출한다. 대부분의 컴파일러는 기저 클래스 생성자를 호출하는 코드를 자동으로 방출하므로 결국 `System.Object`의 생성자까지 호출되며, 이 생성자는 아무것도 하지 않고 그냥 반환한다.

`new`에는 짝이 되는 `delete` 연산자가 없다. 객체 메모리를 명시적으로 해제하는 방법 자체가 없다(62장~64장).

### 힙 객체의 세 부분

.NET 메모리 관리 설계상, 힙 위의 모든 객체는 엄격한 레이아웃을 가진다.

**① 객체 헤더(object header).** CoreCLR 소스의 표현을 빌리면 "임의의 객체에 붙여야 할 수도 있는 부가 정보"를 위한 자리다. **대부분의 경우 그냥 0이다.** 실제로 쓰이는 대표적인 용도는 두 가지다.

- 그 객체에 걸린 **락 정보**
- `GetHashCode()` 호출 결과의 **캐시**

이 필드는 **선착순(first-come, first-served)** 으로 쓰인다. 런타임이 이 자리를 락 관련 정보에 써 버리면 해시 코드는 여기 캐시되지 않고, 반대도 마찬가지다. GC도 내부 동작에서 이 자리를 중요하게 사용한다.

**② 메서드 테이블 참조.** ECMA-335가 말하는 "객체의 타입은 그 표현 안에 명시적으로 저장된다"의 구현이 이것이다. **객체를 가리키는 바깥의 참조들이 실제로 가리키는 지점이 바로 이 필드다.** 즉 참조는 "그 객체의 메서드 테이블 주소가 들어 있는 메모리"를 가리킨다. 그래서 객체 헤더는 **"음수 인덱스"** 에 있다고 말한다.

**③ 최소 한 개의 포인터 크기 필드를 담을 자리.** 현재 GC 설계는 모든 객체가 최소한 포인터 하나를 담을 공간을 가질 것을 요구한다. 이 자리는 여러 용도로 재사용된다 — 보통 객체에서는 **첫 번째 필드**, 배열에서는 **요소 개수**로 쓰인다. GC에게도 중요하다.

### 32비트와 64비트의 레이아웃 대비

다음 클래스를 보자.

```csharp
public class SomeClass
{
    public int Value1;
    public int Value2;
    public int Value3;
    public int Value4;
}
```

```text
── 32비트 런타임 ──────────────────────────────────────

           ┌──────────────────────────┐  ← 참조 - 4
    -4     │ 싱크 블록 인덱스   (4B)    │     (음수 인덱스)
           ├══════════════════════════┤
참조 ─────▶│ MethodTable 참조  (4B)    │  ← 참조 + 0
   +4      ├──────────────────────────┤
           │ Value1           (4B)    │  ← 참조 + 4
   +8      ├──────────────────────────┤
           │ Value2           (4B)    │
  +12      ├──────────────────────────┤
           │ Value3           (4B)    │
  +16      ├──────────────────────────┤
           │ Value4           (4B)    │
           └──────────────────────────┘
             합계 24바이트 (헤더 포함)


── 64비트 런타임 ──────────────────────────────────────

           ┌──────────────────────────┐  ← 참조 - 8
    -8     │ 정렬 패딩         (4B) 0   │     (음수 인덱스)
    -4     │ 싱크 블록 인덱스   (4B)    │
           ├══════════════════════════┤
참조 ─────▶│ MethodTable 참조  (8B)    │  ← 참조 + 0
   +8      ├──────────────────────────┤
           │ Value1           (4B)    │  ← 참조 + 8
  +12      │ Value2           (4B)    │
  +16      │ Value3           (4B)    │
  +20      │ Value4           (4B)    │
           └──────────────────────────┘
             합계 32바이트 (헤더 포함)
```

64비트에서 객체 헤더가 8바이트인데 그중 **4바이트만 실제로 쓰인다.** 나머지 4바이트는 0으로 채워진 정렬 패딩이다. 64비트 아키텍처에서는 8바이트 정렬 레이아웃이 바람직하기 때문이다.

이 레이아웃은 JIT 출력에서 직접 확인된다. `Value1`을 읽고 쓰는 코드는 64비트에서 이렇게 나온다.

```text
mov     [rax+0x8], esi      ; Value1 = data   (rax = 객체 참조)
mov     eax, [rax+0x8]      ; return Value1
```

**`+0x8`.** 참조에서 8바이트 뒤가 첫 필드다. `MethodTable` 참조가 정확히 8바이트를 차지하기 때문이다.

### 왜 참조가 헤더가 아니라 `MethodTable` 포인터를 가리키는가

이 설계는 사소해 보이지만 매우 계산된 것이다. 네 가지 이유가 있다.

**첫째, 필드 접근이 상수 양수 오프셋이 된다.** 위 어셈블리를 보라. `mov [rax+0x8], esi` 하나로 끝난다. 만약 참조가 헤더를 가리켰다면 모든 필드 오프셋에 헤더 크기를 더해야 하고, 그 크기는 32비트(4)와 64비트(8)에서 다르다. 지금 방식에서는 첫 필드가 항상 "포인터 크기만큼 뒤"에 있다.

**둘째, 타입 확인이 오프셋 0이 된다.** 가상 호출, 인터페이스 호출, 형변환 검사, `GetType()` — 이 모든 것이 `MethodTable` 포인터를 읽는다. 실행 중 가장 자주 하는 역참조를 오프셋 0으로 만들면 주소 계산이 사라진다.

**셋째, 헤더는 드물게 쓰인다.** 앞에서 봤듯 객체 헤더는 대부분 0이고, 락을 걸거나 해시 코드를 캐시할 때만 의미를 가진다. **자주 쓰는 것을 앞으로, 드물게 쓰는 것을 뒤(여기서는 음수 쪽)로** 미는 것은 캐시 지역성의 기본 원칙이다.

**넷째, null 검사가 공짜가 된다.** 이 부분은 54.8절에서 `null`을 다루며 자세히 본다.

> **📌 GC는 `MethodTable` 포인터의 남는 비트를 훔쳐 쓴다**
>
> Mark 단계에서 GC가 객체에 "도달했다"는 표시를 남기는 방법은 **`MethodTable` 포인터에 비트 하나를 세우는 것**이다. `MethodTable`의 주소는 워드 정렬되어 있으므로(항상 4 또는 8의 배수) 하위 두 비트가 언제나 0이고, 그 비트를 표시용으로 빌려 쓸 수 있다. 표시를 지우려면 하위 두 비트를 0으로 만들면 된다. 포인터는 파괴되지 않는다.
>
> 이런 트릭이 가능한 이유도 결국 참조가 `MethodTable` 포인터를 정확히 가리키기 때문이다. 자세한 것은 64.2절에서 다룬다.

### 싱크 블록 인덱스의 선착순 규칙

이 한 필드를 락과 해시 코드가 공유한다는 사실은 실무에서 몇 가지 결과를 낳는다.

```csharp
var o = new object();

int h1 = o.GetHashCode();   // 헤더에 해시 코드가 캐시될 수 있다
lock (o)                    // 락 정보가 이 한 자리를 차지하게 된다
{
    int h2 = o.GetHashCode();  // h1 == h2
}
```

**보장되는 것은 `h1 == h2`라는 사실뿐이다.** 헤더 한 자리를 락 정보가 차지해 버리면 해시 코드는 거기 캐시되지 못하고(그 반대도 마찬가지다), 런타임은 값을 잃지 않도록 다른 곳에 보관한다. 어디에 어떻게 보관하는지는 구현 세부이며 버전에 따라 다르다. 우리가 기대어도 되는 계약은 하나다 — **해시 코드는 객체 수명 동안 바뀌지 않는다.**

`System.Object`의 `GetHashCode()` 구현은 파생 타입이나 그 필드에 대해 아무것도 모른다. 그래서 **객체 수명 동안 바뀌지 않을 것이 보장되는 수**를 반환한다.

> **⚠️ 값 타입에는 `lock`을 걸 수 없다 — 그리고 그 이유는 여기 있다**
>
> 박싱되지 않은 값 타입에는 싱크 블록 인덱스가 없다. 따라서 `System.Threading.Monitor`의 메서드(즉 C#의 `lock` 문)로 여러 스레드가 그 인스턴스에 대한 접근을 동기화하는 것이 **불가능하다.** C# 컴파일러가 `lock (someStruct)`를 거부하는 근본 원인이 레이아웃에 있다.
>
> 값 타입을 `object`로 박싱한 다음 그 결과에 `lock`을 거는 것은 문법적으로 가능하지만, 박싱은 **매번 새 객체를 만든다.** 두 스레드가 같은 값을 박싱해서 락을 걸면 서로 다른 객체에 락을 거는 것이고, 상호 배제는 전혀 일어나지 않는다. 조용히 깨지는 전형적인 코드다.

> **⚠️ 해시 코드를 절대 영속화하지 마라**
>
> 해시 코드 값은 언제든 바뀔 수 있다. 미래 버전의 타입이 다른 알고리즘을 쓸 수 있기 때문이다. 실제로 어떤 회사가 계정 생성 시 비밀번호 문자열의 `GetHashCode()` 결과를 DB에 저장하고 로그인 때 다시 계산해 비교했다. 런타임을 새 버전으로 올리자 `String.GetHashCode()`가 다른 값을 반환하기 시작했고 **아무도 로그인할 수 없게 되었다.**
>
> `GetHashCode()`는 프로세스 수명 안에서 해시 테이블 버킷을 정하는 용도다. 파일이나 DB에 쓸 값이 아니다. 영속화가 필요하면 SHA-256 같은 명세가 고정된 해시를 써라.

> **⚠️ `Equals`를 재정의했으면 `GetHashCode`도 재정의하라**
>
> `Dictionary<K,V>`류 해시 기반 컬렉션은 **동등한 두 객체가 반드시 같은 해시 코드를 가진다**는 전제 위에 만들어져 있다. C# 컴파일러는 `Equals`만 재정의하면 CS0659 경고를 낸다. 무시하면 사전에 넣은 항목을 다시 찾지 못하는 버그가 생긴다. 같은 이유로 **컬렉션에 키로 들어가 있는 객체의 상태를 바꾸면 안 된다.** 키를 바꿔야 한다면 제거 → 수정 → 재삽입 순서를 지켜라.

## 54.3 최소 객체 크기가 32비트 12바이트 / 64비트 24바이트인 이유

### 산수

앞 절에서 힙 객체가 세 부분으로 되어 있다고 했다. 세 부분 모두 필수이므로, 힙 객체의 크기는 **적어도 이 세 부분의 합** 이상이어야 한다. CoreCLR 소스에 이 규칙이 그대로 박혀 있다.

```c
// The generational GC requires that every object be at least 12 bytes in size.
#define MIN_OBJECT_SIZE     (2*TARGET_POINTER_SIZE + OBJHEADER_SIZE)

#ifdef TARGET_64BIT
   #define OBJHEADER_SIZE   (sizeof(DWORD) /* m_alignpad */ + \
                             sizeof(DWORD) /* m_SyncBlockValue */)
#else
   #define OBJHEADER_SIZE   sizeof(DWORD) /* m_SyncBlockValue */
#endif
```

`TARGET_POINTER_SIZE`는 32비트에서 4, 64비트에서 8이다. 대입해 보자.

**32비트: 4 + 4 + 4 = 12바이트**

- 4바이트 — 객체 헤더
- 4바이트 — `MethodTable` 참조 (포인터 크기)
- 4바이트 — 내부 데이터 자리 (포인터 크기)

**64비트: 8 + 8 + 8 = 24바이트**

- 8바이트 — 객체 헤더. **그중 4바이트만 실제로 쓰이고** 나머지 4바이트는 0으로 채워진 정렬 패딩이다 (64비트 아키텍처에서 8바이트 정렬 레이아웃이 바람직하므로)
- 8바이트 — `MethodTable` 참조 (포인터 크기)
- 8바이트 — 내부 데이터 자리 (포인터 크기)

### 필드가 하나도 없는 클래스도 24바이트다

```csharp
public class Empty { }             // 64비트에서 힙에 24바이트
public class OneByte { byte B; }   // 64비트에서 힙에 24바이트
public struct OneByteStruct { byte B; }  // 스택에서 1바이트
```

이 대비가 이 절의 요점이다. **바이트 하나를 담은 구조체를 스택에 두면 딱 그 1바이트를 차지한다**(정렬 요구가 오버헤드를 더할 수는 있다 — 54.4절). **바이트 하나를 담은 클래스를 힙에 할당하면 64비트 런타임에서 24바이트를 차지한다.** 24배다.

| 타입 | 필드 | 32비트 힙 크기 | 64비트 힙 크기 |
|---|---|---|---|
| `class Empty {}` | 없음 | 12 B | 24 B |
| `class OneByte { byte b; }` | 1 B | 12 B | 24 B |
| `class OneInt { int i; }` | 4 B | 12 B | 24 B |
| `class TwoInts { int a, b; }` | 8 B | 16 B | 24 B |
| `class ThreeInts { int a, b, c; }` | 12 B | 20 B | 32 B |
| `class FourInts { int a,b,c,d; }` | 16 B | 24 B | 32 B |
| `class OneRef { object o; }` | 4 또는 8 B | 12 B | 24 B |

64비트 열에서 필드 8바이트까지는 전부 24바이트로 같다는 점에 주목하라. 헤더 8 + `MethodTable` 참조 8 = 16바이트가 이미 고정으로 나가고, 그 뒤 필드 영역이 **최소 8바이트**를 요구하기 때문이다. **필드를 하나 늘려도 크기가 안 늘어나는 구간이 있다.** 그 구간을 넘어가면 8바이트 단위로 올림된다 — `ThreeInts`의 필드 12바이트가 16바이트로 올림되어 32바이트가 되는 식이다.

> **📌 이 오버헤드는 "포인터 두 개 크기"라고 기억하면 된다**
>
> 구조체 인스턴스는 자기 데이터만 저장하고 어떤 메타데이터도 저장하지 않는다. 클래스 인스턴스는 여기에 **포인터 두 개 크기**의 부가 정보를 항상 얹는다. 메모리가 싸다지만, 정말 큰 데이터 볼륨을 다룰 때는 이 차이가 결정적이 된다. 백만 개의 2-필드 객체라면 오버헤드만 16MB다.

### GC가 이 규칙을 요구하는 이유

주석이 말하듯 "세대별 GC는 모든 객체가 최소 12바이트일 것을 요구한다". 왜인가?

GC는 힙을 **객체 단위로 걸어다니며** 스캔한다. 현재 객체의 크기를 `MethodTable`에서 읽고, 그 크기만큼 포인터를 전진시켜 다음 객체로 간다. 힙을 거대한 연결 리스트처럼 보는 것이다. 이 방식이 성립하려면 객체 사이에 빈 공간이 없어야 하는데, 힙은 거의 항상 단편화되어 있다. 해법은 **빈 공간에 더미 객체를 채워 넣는 것**이다(54.7절의 "free object").

즉 **"어떤 객체든 헤더 + 타입 + 최소 한 개의 포인터 크기 자리를 갖는다"** 는 불변식이 힙 순회 알고리즘 전체를 떠받친다. 이 자리가 배열에서는 요소 개수를, free object에서는 빈 공간 크기를 담는 데 재사용된다. 세 부분 중 마지막 자리가 왜 "선택적 데이터 자리"라고 불리는지가 여기서 드러난다.

### `BaseSize`와 `ComponentSize`

`MethodTable`은 인스턴스 크기를 두 값으로 표현한다.

- **`BaseSize`** — 인스턴스의 고정 크기 부분. **객체 헤더 몫까지 포함한** 힙 점유 바이트 수이며, 정렬 패딩도 들어 있다. 필드가 없는 클래스의 `BaseSize`가 64비트에서 24인 것이 이 때문이다(앞의 최소 객체 크기 계산 그대로다). 그래서 `!dumpobj`가 보고하는 `Size`와 `!dumpmt`가 보고하는 `BaseSize`는 같은 값이 된다(54.10절).
- **`ComponentSize`** — 가변 길이 타입(배열, 문자열)에서 요소 하나의 크기. 일반 클래스에서는 0이다.

GC가 객체 크기를 계산하는 공식은 이렇다.

```text
일반 객체:   크기 = BaseSize
배열/문자열:  크기 = BaseSize + ComponentSize × 요소 개수
```

`!dumpmt`가 `BaseSize:`와 `ComponentSize:`를 나란히 보여주는 이유가 이것이다.

> **⚠️ `sizeof`, `Marshal.SizeOf`, 힙 크기는 서로 다른 세 값이다**
>
> - `sizeof(T)` — **관리 표현**에서 값 타입 `T`가 차지하는 바이트 수. 참조 타입에는 쓸 수 없다.
> - `Marshal.SizeOf(typeof(T))` — **비관리 마샬링 표현**에서의 크기. `[StructLayout]`과 `[MarshalAs]`의 영향을 받으므로 `sizeof`와 다를 수 있다. `bool`이 대표적이다 — 관리 표현은 1바이트지만 마샬링 기본값은 4바이트 `BOOL`이다.
> - **힙 크기** — 참조 타입 인스턴스가 힙에서 차지하는 실제 바이트. `sizeof`로는 알 수 없고, `!dumpobj`의 `Size:` 줄이나 `!objsize`로 확인한다(54.10절).
>
> 세 값을 혼동해서 "내 객체는 12바이트"라고 계산했는데 힙에서는 24바이트인 상황이 흔하다.

> **💡 24바이트가 문제가 되는 지점을 알아두라**
>
> 객체 하나가 24바이트인 것은 아무 문제도 아니다. 문제가 되는 것은 **작은 객체가 아주 많을 때**다. 참조 둘과 `int` 하나를 가진 노드를 백만 개 만든다면 데이터는 노드당 20바이트인데 실제 점유는 40바이트다. 절반이 메타데이터와 정렬이다. 이럴 때의 답은 보통 "구조체 배열로 바꾸기"다(54.9절, 70.3절). 하지만 먼저 측정하라 — 대부분의 애플리케이션에서 이 오버헤드는 노이즈다.

## 54.4 필드 레이아웃, 정렬, `[StructLayout]`, `[FieldOffset]`

### 정렬이라는 황금률

객체의 총 크기까지는 봤다. 그 안에서 **필드들이 어떤 순서로 어디에 놓이는가**가 이 절의 주제다.

효율적인 메모리 접근을 지배하는 규칙은 하나다 — **데이터 정렬(data alignment)**. 각 기본 데이터 타입에는 선호하는 정렬 값이 있고, 그 값의 배수인 주소에 저장되어야 한다. 대부분의 경우 기본형의 정렬은 **자기 크기와 같다** — 4바이트 `int`는 4바이트 정렬, 8바이트 `double`은 8바이트 정렬, 1바이트 `byte`와 `bool`은 1바이트 정렬(어디에 놓여도 항상 정렬되어 있다).

현대 CPU는 정렬된 데이터에 접근할 때 효율적인 코드를 쓸 수 있다. 정렬되지 않은 데이터에 접근하는 것도 가능하지만 더 많은 명령이 필요하고 일반적으로 느리다.

Microsoft 문서가 정리한 객체 레이아웃 규칙은 셋이다.

1. **타입의 정렬은 가장 큰 요소의 크기(1, 2, 4, 8 …)와 지정된 패킹 크기 중 작은 쪽이다.**
2. **각 필드는 자기 크기와 타입의 정렬 중 작은 쪽에 맞춰 정렬되어야 한다.** 타입의 기본 정렬이 가장 큰 요소의 크기이고 그것이 다른 모든 필드 길이 이상이므로, 보통 이 말은 필드가 자기 크기에 맞춰 정렬된다는 뜻이 된다. 타입에서 가장 큰 필드가 8바이트 정수여도 `byte` 필드는 1바이트 경계에, `Int16`은 2바이트 경계에, `Int32`는 4바이트 경계에 정렬된다.
3. **정렬 요구를 만족시키기 위해 필드 사이에 패딩이 삽입된다.**

복합 타입 자신도 정렬되어야 한다. 그래야 그 타입이 다른 복합 타입의 필드가 되거나 배열의 요소가 되었을 때도 내부 필드가 여전히 정렬되기 때문이다.

### 실제 레이아웃 — `AlignedDouble`

```csharp
public struct AlignedDouble
{
    public byte   B;
    public double D;
    public int    I;
}
```

필드 데이터는 1 + 8 + 4 = 13바이트다. 실제 크기는 **24바이트**다. 왜 그런지 한 줄씩 따라가 보자.

- **오프셋 0** — 첫 필드는 1바이트 정렬인 `byte`. 어느 주소에도 놓일 수 있으므로 0에 놓인다.
- **오프셋 8** — 두 번째 필드는 8바이트 정렬인 `double`. 8의 배수 주소에서 시작해야 한다. 오프셋 1은 안 되므로 8까지 밀린다. **7바이트의 패딩**이 낭비된다.
- **오프셋 16** — 마지막 필드는 4바이트 정렬인 `int`. 16은 4의 배수이므로 그대로 놓인다.

여기까지 20바이트를 쓴다. 그런데 **구조체 전체의 정렬은 가장 큰 요소의 크기**, 즉 8바이트여야 한다. 다시 말해 구조체 크기가 8의 배수여야 한다. 20을 8의 배수로 올림하면 24다. **끝에 4바이트 패딩**이 더 붙는다.

```text
[StructLayout(LayoutKind.Sequential)] — 구조체의 기본값

 오프셋  0        1 ─────────── 7   8 ─────────────── 15  16 ──── 19  20 ── 23
       ┌────────┬──────────────────┬───────────────────┬───────────┬──────────┐
       │ byte B │  패딩 (7바이트)   │   double D (8B)   │ int I (4B)│패딩 (4B) │
       └────────┴──────────────────┴───────────────────┴───────────┴──────────┘
        크기 24바이트 · 패딩 11바이트 (전체의 45%가 빈 공간)
```

전체 24바이트 중 **11바이트가 사용되지 않는다.** 거의 절반이다. 이 구조체를 가끔 쓴다면 문제가 아니다. 하지만 코드가 값 타입에 크게 의존하고 수백만 개를 성능 좋게 처리해야 한다면, 낭비된 공간이 문제가 된다.

전체 정렬이 왜 필요한지는 배열을 그려 보면 명확해진다. 구조체 크기가 24(8의 배수)면 두 번째 요소는 오프셋 24에서 시작하고 그 안의 `double`은 오프셋 32 — 8의 배수다. 만약 끝 패딩이 없어 크기가 20이었다면 두 번째 요소는 오프셋 20에서 시작하고 그 안의 `double`은 **오프셋 28**, 8의 배수가 아니다. **끝 패딩이 없으면 배열의 두 번째 요소부터 `double` 필드가 정렬을 잃는다.** 그래서 구조체 자신의 정렬도 보장되어야 한다.

### 세 가지 레이아웃 종류

필드 레이아웃은 `StructLayout` 특성으로 제어한다. 이름과 달리 **클래스와 구조체 모두에** 적용할 수 있다.

| `LayoutKind` | 동작 | 기본값이 되는 대상 |
|---|---|---|
| `Sequential` | 정렬을 보장하면서 **정의 순서대로** 저장 | **unmanaged 구조체** |
| `Auto` | 정렬은 보장하되 **필드를 재배치**해도 됨 (패딩을 줄여 메모리 절약) | **클래스**, unmanaged가 아닌 구조체 |
| `Explicit` | 각 필드의 오프셋을 **개발자가 직접 지정** | (없음 — 명시적으로만) |

여기서 "unmanaged 타입"은 네이티브라는 뜻이 아니라, **참조 타입이 아니면서 참조 타입 필드도 갖지 않는 타입**을 말한다. 중첩 단계 전부를 검사한다 — 구조체 A가 구조체 B를 담고, B가 C를, C가 참조 타입 필드를 가지면 A 전체가 unmanaged가 아니다.

구조체가 기본적으로 순차 레이아웃인 이유는 역사적이다. .NET 설계 초기에는 구조체가 주로 상호운용 시나리오에서 쓰일 것이라고 예상했고, 그렇다면 필드 정의 순서가 우연이 아니라 의도적인 것이므로 보존해야 했다. 클래스는 반대다. CLR이 그 데이터의 유일한 소유자이므로 CPU 접근 시간과 메모리 사용량 양쪽에서 가장 효율적인 방식으로 자유롭게 재배치한다.

`AlignedDouble`을 자동 레이아웃으로 바꿔 보자.

```csharp
[StructLayout(LayoutKind.Auto)]
public struct AlignedDoubleAuto
{
    public byte   B;
    public double D;
    public int    I;
}
```

```text
[StructLayout(LayoutKind.Auto)]

 오프셋  0 ─────────────── 7   8 ──── 11  12   13 ── 15
       ┌───────────────────┬───────────┬──────┬────────┐
       │  double D (8B)    │ int I (4B)│byte B│패딩(3B)│
       └───────────────────┴───────────┴──────┴────────┘
        크기 16바이트 · 패딩 3바이트
```

24바이트가 16바이트가 되었다. 모든 필드는 여전히 올바르게 정렬되어 있다. 큰 필드를 앞으로 모으고 작은 필드를 뒤로 보내면 패딩이 사라진다.

낭비되는 공간의 양은 대체로 **필드 개수와 크기 다양성에 비례한다.** 다음 구조체를 직접 계산해 보라.

```csharp
public struct ManyDoubles
{
    public byte   B1;
    public double D1;
    public byte   B2;
    public double D2;
    public byte   B3;
    public double D3;
    public byte   B4;
    public double D5;
}
```

`LayoutKind.Sequential`에서는 **64바이트**를 소비하고 그중 28바이트가 패딩이다. `LayoutKind.Auto`에서는 **40바이트**를 쓰고 패딩은 4바이트뿐이다.

> **💡 고성능 코드의 구조체에는 `[StructLayout(LayoutKind.Auto)]`를 고려하라**
>
> 자동 레이아웃의 유일한 단점은 그 구조체를 상호운용에 쓸 수 없다는 것이다. 하지만 값 타입의 메모리 관리 이점(스택 할당, 데이터 지역성, 적은 공간 점유) 때문에 구조체를 쓰기로 했다면, P/Invoke는 애초에 관심사가 아닐 것이다. 그런 코드라면 기본값 대신 자동 레이아웃을 명시적으로 켜는 편이 낫다.

### 조용히 레이아웃을 바꾸는 것들

여기부터가 함정 구역이다.

**참조 타입 필드를 하나만 추가해도 레이아웃이 자동으로 바뀐다.**

```csharp
public struct AlignedDoubleWithReference
{
    public byte   B;
    public double D;
    public int    I;
    public object O;      // ← 이 한 줄이 레이아웃 종류를 바꾼다
}
```

이 구조체는 더 이상 unmanaged 타입이 아니므로 기본 레이아웃이 **자동**이 된다. 필드가 재배치된다. 크기는 24바이트이고 패딩은 3바이트뿐이다.

기본 동작이 바뀌는 이유는 명확하다. **참조 타입 필드를 가진 구조체는 P/Invoke로 넘길 수 없다.** GC가 이동시킬 수 있는 관리 객체에 대한 참조를 담고 있기 때문이다. 비관리 사용이 금지되어 있으므로 자동 레이아웃을 써도 안전하다.

> **📌 자동 레이아웃은 참조를 앞쪽에 배치한다**
>
> 자동 레이아웃은 객체 참조를 **첫 필드들로** 놓는 것을 선호한다. GC의 Mark 단계에서 객체를 순회할 때 캐시 라인 활용이 좋아지기 때문이다. 대부분의 객체 참조가 이미 접근한 `MethodTable` 필드와 **같은 캐시 라인**에 들어온다. 위 예제에서 `object O`가 오프셋 0에 온 것이 이 규칙의 결과다.
>
> 이 최적화가 데이터 지향 설계에 어떤 영향을 주는지는 70.1절에서 다시 본다.

**중첩된 구조체가 자동 레이아웃이면 바깥 구조체도 자동이 된다.** 흔히 쓰는 내장 구조체 대부분(`Decimal`, `Guid`, `Char`, `Boolean`)은 순차 레이아웃이라 문제가 없다. 그런데 **`DateTime`은 자동 레이아웃이다.** 다른 구조체의 필드로 쓰면 그 구조체의 레이아웃 종류를 바꿔 버린다.

```csharp
public struct StructWithFields
{
    public byte   B;
    public double D;
    public int    I;

    // public SomeEnum E;      // 여전히 순차
    // public SomeStruct AD;   // 여전히 순차 (AD가 순차라면)
    // public unsafe void* P;  // 여전히 순차
    // public decimal DE;      // 여전히 순차
    // public Guid G;          // 여전히 순차
    // public char C;          // 여전히 순차
    // public bool BL;         // 여전히 순차
    // public object O;        // 자동으로 전환
    // public DateTime DT;     // 자동으로 전환 — DateTime이 자동 레이아웃이므로
}
```

> **⚠️ P/Invoke 구조체에 `DateTime` 필드를 넣지 마라**
>
> 위 표의 마지막 줄이 실무에서 사고를 낸다. 네이티브 API에 넘길 구조체를 `LayoutKind.Sequential`로 정성껏 만들어 놓고 편의상 `DateTime` 필드를 추가하면 레이아웃 종류가 조용히 자동으로 바뀐다. 네이티브 쪽이 기대하는 바이트 배치와 어긋나고, 컴파일 오류도 런타임 예외도 없이 **쓰레기 값이 넘어간다.** 상호운용 구조체에는 `DateTime` 대신 `long`(틱)을 쓰고 `[StructLayout(LayoutKind.Sequential)]`을 **명시적으로** 붙여라.

> **⚠️ 클래스와 non-unmanaged 구조체는 `Sequential`을 지정해도 무시된다**
>
> 클래스와 참조를 담은 구조체의 자동 레이아웃은 **바꿀 수 없다.** `[StructLayout(LayoutKind.Sequential)]`을 명시적으로 붙여도 그냥 무시된다. 컴파일 오류도, 경고도 없다. "붙였으니 순서가 보장되겠지"라고 믿고 짠 상호운용 코드가 조용히 틀린 데이터를 넘긴다.

> **⚠️ .NET 7 이전에는 중첩 구조체 정렬에 버그가 있었다** ※.NET 7
>
> ```csharp
> [StructLayout(LayoutKind.Auto)] public struct Nested { public bool Value; }
> [StructLayout(LayoutKind.Auto)] public struct TestLayout { public Nested B1, BA; }
> ```
>
> `sizeof(TestLayout)`이 얼마여야 하는가? `bool` 두 개니까 2다. 그런데 **.NET 7 이전의 모든 버전**에서는 64비트에서 **16**, 32비트에서 **8**이 나왔다. 자동 레이아웃이 중첩 구조체를 포인터 크기에 정렬했기 때문이다. 이럴 이유가 전혀 없었고 .NET 7에서 수정되었다 — 이제는 2가 나온다. 구형 런타임 대상 코드에서 작은 구조체를 중첩해 메모리를 아끼려 했다면 실측해서 확인하라.

### 패킹 — 정렬 자체를 포기하기

`StructLayout` 특성의 `Pack` 필드는 타입 필드의 정렬을 제어한다.

```csharp
[StructLayout(LayoutKind.Sequential, Pack = 1)]
public struct AlignedDoublePacked
{
    public byte   B;
    public double D;
    public int    I;
}
```

앞의 첫 번째 규칙을 다시 보자. "타입의 정렬은 가장 큰 요소의 크기와 **지정된 패킹 크기 중 작은 쪽**이다." 여기서는 `double`의 8바이트가 아니라 **1바이트**가 된다. 두 번째 규칙은 "각 필드는 자기 크기와 **타입의 정렬** 중 작은 쪽에 맞춘다"이므로, 각 필드의 정렬도 1바이트다.

결과는 패딩이 전혀 없는 **13바이트의 매우 조밀한 레이아웃**이다. 대신 필드들이 최적 정렬 요구를 만족하지 않는다.

```text
[StructLayout(LayoutKind.Sequential, Pack = 1)]

 0      1 ──────────────── 8   9 ──── 12
┌──────┬────────────────────┬──────────┐
│byte B│   double D (8B)    │int I (4B)│
└──────┴────────────────────┴──────────┘
 크기 13바이트 · 패딩 0바이트 · double이 오프셋 1 (정렬되지 않음)
```

### 명시적 레이아웃과 유니온

세 번째 종류인 명시적 레이아웃은 P/Invoke 시나리오에서 특히 유용하다. 구조체가 메모리에 어떻게 놓이는지를 100% 통제할 수 있어서, 비관리 코드가 기대하는 배치를 그대로 만들어낼 수 있다.

```csharp
[StructLayout(LayoutKind.Explicit)]
public struct UnalignedDouble
{
    [FieldOffset(0)] public byte   B;
    [FieldOffset(1)] public double D;
    [FieldOffset(9)] public int    I;
}
```

크기는 13바이트다. 하지만 `double`이 오프셋 1에 있어 정렬되지 않았다. **명시적 레이아웃에서는 정렬 요구를 맞추는 것이 전적으로 개발자 책임이다.** 정렬되지 않은 필드를 만들기가 아주 쉽다.

컴파일러는 명시적 레이아웃에서 필드가 **겹치지 않을 것을 요구하지 않는다.** 이것을 의도적으로 활용하는 시나리오가 **판별 유니온(discriminated union)** 이다.

```csharp
[StructLayout(LayoutKind.Explicit)]
public struct DiscriminatedUnion
{
    [FieldOffset(0)] public bool Bool;
    [FieldOffset(0)] public byte Byte;
    [FieldOffset(0)] public int  Integer;
}
```

세 필드가 같은 4바이트를 공유한다. C/C++의 `union`을 흉내 낸 것이다. 같은 메모리를 다른 세밀도로 접근하려고 고정 크기 버퍼를 함께 쓸 수도 있다.

```csharp
[StructLayout(LayoutKind.Explicit)]
public unsafe struct DiscriminatedUnionWithBuffer
{
    [FieldOffset(0)] public bool Bool;
    [FieldOffset(0)] public byte Byte;
    [FieldOffset(0)] public int  Integer;
    [FieldOffset(0)] public fixed byte Buffer[8];
}
```

> **⚠️ 참조 타입과 값 타입을 겹치는 것은 불법이다**
>
> 명시적 레이아웃에서 **참조 타입과 값 타입이 겹치는 타입을 정의하는 것은 불법이다.** 겹치면 GC가 그 바이트를 포인터로 해석할지 데이터로 해석할지 결정할 수 없고, 타입 안전성이 무너진다. 런타임이 `TypeLoadException`으로 거부한다.
>
> 여러 **참조 타입**이 같은 시작 오프셋에서 겹치는 타입은 정의할 수 있지만 검증 불가능(unverifiable)하다. 여러 **값 타입**이 겹치는 것은 합법이며, 겹치는 바이트 전부가 public 필드로 접근 가능해야 검증 가능하다.

> **⚠️ 유니온에는 규율이 필요하다**
>
> 판별 유니온은 **쓴 타입으로 읽어야** 한다. `Integer`에 값을 쓰고 `Bool`로 읽으면 최하위 바이트가 0인지 아닌지에 따라 결과가 정해진다. 어떤 필드가 유효한지를 나타내는 태그 필드를 함께 두고 규율 있게 관리하지 않으면, 이 구조체는 정의상 타입 안전하지 않다.
>
> 물론 타입 간 메모리 기반 변환을 의도한 경우라면 이것이 목적 자체다. 그런 목적이라면 `BitConverter`나 `MemoryMarshal.Cast`가 더 읽기 쉽고 안전한 경우가 많다.

### 크기 실측 표

지금까지의 규칙을 한 표로 정리한다. 64비트 런타임 기준이며, 구조체는 힙 오버헤드 없이 그 자체 크기다.

| 정의 | 레이아웃 | 필드 데이터 | 실제 크기 | 패딩 |
|---|---|---|---|---|
| `struct { byte B; double D; int I; }` | Sequential (기본) | 13 B | **24 B** | 11 B (45%) |
| 같은 필드 + `[StructLayout(Auto)]` | Auto | 13 B | **16 B** | 3 B (19%) |
| 같은 필드 + `Pack = 1` | Sequential, Pack=1 | 13 B | **13 B** | 0 B |
| 같은 필드 + `object O` | Auto (강제) | 21 B | **24 B** | 3 B |
| `struct { byte×4, double×4 }` | Sequential (기본) | 36 B | **64 B** | 28 B (44%) |
| 같은 필드 + `[StructLayout(Auto)]` | Auto | 36 B | **40 B** | 4 B (10%) |
| `class { byte B; double D; int I; }` | Auto (강제) | 13 B | **32 B** (힙) | 헤더 16 + 패딩 3 |

### 레이아웃을 직접 확인하는 도구

**ObjectLayoutInspector** — Sergey Teplyakov가 만든 라이브러리로 GitHub과 NuGet 패키지로 제공된다. 객체 메모리 레이아웃 검사만을 위해 만들어졌고, 메서드 하나로 결과를 얻는다.

```csharp
static void Main()
{
    TypeLayout.PrintLayout<AlignedDouble>();
    TypeLayout.PrintLayout<AlignedDoubleWithReference>();
}
```

출력은 ASCII 차트로 깔끔하게 나온다.

```text
Type layout for 'AlignedDouble'
Size: 24 bytes. Paddings: 11 bytes (%45 of empty space)
|===========================|
|     0: Byte B (1 byte)    |
|---------------------------|
|   1-7: padding (7 bytes)  |
|---------------------------|
|  8-15: Double D (8 bytes) |
|---------------------------|
| 16-19: Int32 I (4 bytes)  |
|---------------------------|
| 20-23: padding (4 bytes)  |
|===========================|

Type layout for 'AlignedDoubleWithReference'
Size: 24 bytes. Paddings: 3 bytes (%12 of empty space)
|===========================|
|   0-7: Object O (8 bytes) |
|---------------------------|
|  8-15: Double D (8 bytes) |
|---------------------------|
| 16-19: Int32 I (4 bytes)  |
|---------------------------|
|    20: Byte B (1 byte)    |
|---------------------------|
| 21-23: padding (3 bytes)  |
|===========================|
```

두 번째 출력에서 `object O`가 맨 앞으로 이동한 것을 확인하라. 앞에서 말한 "참조를 앞쪽에"가 눈으로 보인다.

콘솔 출력 대신 `TypeLayout.GetLayout<T>()`로 레이아웃을 프로그램적으로 소비할 수도 있다. 반환된 `TypeLayout`의 `FullSize`, `Paddings` 속성과 `Fields` 컬렉션(원소가 `FieldLayout` 또는 `Padding`)을 순회하면 된다. 이 도구는 런타임에 대상 애플리케이션 안에서 돌리기보다는 **커스텀 빌드 단계나 개발 중 오프라인 확인용**으로 쓰는 것이 자연스럽다.

**SharpLab** — `https://sharplab.io` 웹 페이지도 훌륭한 .NET 코드 분석 기능을 제공한다. `Inspect.Heap`과 `Inspect.Stack` 정적 메서드가 지정한 타입의 레이아웃을 출력한다.

```csharp
public class C
{
    public static void Main()
    {
        var o = new AlignedDouble();
        Inspect.Heap(new AlignedDouble());   // 박싱된(힙) 표현
        Inspect.Stack(in o);                 // 박싱되지 않은 표현
    }
}
```

`Inspect.Heap`은 박싱된(힙 위의) 표현을, `Inspect.Stack`은 박싱되지 않은 표현을 보여준다. 두 결과를 나란히 놓으면 헤더와 `MethodTable` 참조가 붙는 지점이 그대로 드러난다.

> **💡 이 두 도구가 있으면 WinDbg를 꺼낼 일이 거의 없다**
>
> 레이아웃만 확인하는 것이 목적이라면 ObjectLayoutInspector와 SharpLab으로 충분하다. WinDbg는 **살아 있는 프로세스나 덤프에서 실제 객체의 실제 크기**를 봐야 할 때 쓴다 — 예를 들어 어떤 인스턴스가 예상보다 크거나, 유지하고 있는 그래프 전체 크기를 알아야 할 때다. 54.10절이 그 경우를 다룬다.

## 54.5 정적 필드는 어디에 저장되는가 — High Frequency Heap

### 정적 데이터의 수명과 범위

정적 데이터는 프로그램의 전역 변수 같은 것이다. 좋은 설계 관행에서 전역 변수를 환영하지는 않지만, 여전히 유용할 때가 있다. C#에는 정적 데이터의 종류가 **정적 필드 하나뿐**이다. (VB.NET은 함수 안에 정적 변수를 선언할 수 있지만, `Shared` 함수에서 쓰이면 그것은 일반 정적 필드에 대한 문법 설탕일 뿐이다.)

```csharp
public class C
{
    public void Method1() => S.Value = 10;
    public void Method2() => Console.WriteLine(S.Value);
}

public class S
{
    public static int Value;
}
```

문법은 설명이 필요 없다. 메모리 관리 관점에서 덧붙일 것이 몇 가지 있다.

- **정적 데이터는 AppDomain 범위를 갖는다.** 같은 어셈블리가 여러 애플리케이션 도메인에 로드되면 서로 다른 정적 데이터 인스턴스가 여러 개 존재한다.
- **어셈블리에 정의된 타입의 정적 데이터는 그 어셈블리가 로드된 AppDomain이 살아 있는 동안 산다.** 어셈블리가 언로드될 때까지 모든 정적 데이터와 그것이 참조하는 객체는 도달 가능한 상태로 남는다. 즉 **수집되지 않는다.**
- **AppDomain이 없는 .NET(.NET Framework가 아닌)에서는 위의 서술이 `AssemblyLoadContext`에 적용된다**(52.9절).

구현 세부로 들어가면 이렇다.

- **기본형 정적 데이터**(숫자 등)는 해당 애플리케이션 도메인의 **High Frequency Heap**에 저장된다. 이것은 로더 힙(Loader Heap)의 일부다.
- **참조 타입 정적 인스턴스**(객체)는 일반 GC 힙에 산다. 보통 객체와의 차이는 내부 "정적 테이블(statics table)"이 이들을 **추가로 참조한다**는 점이다. 이런 객체는 명백히 오래 살기 때문에 결국 2세대에 안착해 거기 머문다. (다만 큰 객체라면 처음부터 대형 객체 힙에 산다.)
- **참조를 담고 있거나 수집 가능한 어셈블리에서 로드된 사용자 정의 값 타입 정적 인스턴스**(구조체)는 일반 GC 힙에 **박싱된 형태로** 산다. 위의 참조 타입 정적 필드와 정확히 같은 방식으로 처리된다.
- **참조를 담지 않고 수집 가능한 어셈블리에서 온 것도 아닌 사용자 정의 값 타입 정적 인스턴스**는 다르게 취급된다. **NonGC 힙에 박싱된 형태로** 산다 ※.NET 7. 이 특별한 메모리 영역은 영원히 살기 때문에 이 인스턴스들은 결코 수집되지 않는다. 그 대신 JIT이 강력한 최적화를 할 수 있다.

> **📌 로더 힙이라는 것은 실재하지 않는다**
>
> 종종 듣는 것과 달리 **"Loader Heap"이라는 메모리 영역이 따로 만들어지지는 않는다.** High Frequency Heap, Low Frequency Heap, Stub Heap, 각종 Virtual Call Stub Heap 등을 묶어 부르는 **개념적 이름**일 뿐이며, 접근 빈도에 따라 나눈다. 그리고 중요한 성질이 하나 있다. **로더 힙 영역에 한번 로드된 타입은 전체 AppDomain(또는 ALC)이 언로드될 때까지 언로드되지 않는다.**

### 정적 필드 저장의 내부 구조

.NET 애플리케이션의 각 애플리케이션 도메인은 내부 자료구조 집합으로 표현된다. 로드된 어셈블리에 존재하는 **모듈마다** `DomainLocalModule` 자료구조가 유지된다. 정적 데이터 구현 관점에서 여기에 중요한 영역이 둘 있다.

- **참조 타입 필드와 (박싱된) 구조체 필드용** — 해당 모듈의 정적 참조들이 시작되는 `Object[]` 테이블 안쪽을 가리키는 참조(`m_pGCStatics`). 이 `Object[]` 테이블은 애플리케이션 도메인에 로드된 **모든 모듈과 어셈블리가 공유**한다.
- **기본형 필드용** — 메모리 정렬에 필요한 패딩을 포함해 타입별로 묶인 기본형 정적 필드 값들(statics blob).

```text
       ┌────────────────────────────────────────────────────────────┐
       │  AppDomain / AssemblyLoadContext                            │
       │                                                             │
       │  ┌─ Assembly A ──────────┐   ┌─ Assembly B ──────────┐      │
       │  │ DomainLocalModule     │   │ DomainLocalModule     │      │
       │  │  m_pGCStatics ●───────┼─┐ │  m_pGCStatics ●───────┼──┐   │
       │  │  ┌──────────────────┐ │ │ │  ┌──────────────────┐ │  │   │

       │  │  │ ███ int Static1  │ │ │ │  │ ███ long Other   │ │  │   │  ← 회색:

       │  │  │ ███ double Sta2  │ │ │ │  └──────────────────┘ │  │   │
       │  │  └──────────────────┘ │ │ └───────────────────────┘  │   │
       │  │   ↑ High Frequency Heap│ │                            │   │
       │  └───────────────────────┘ │                            │   │
       │                            │  ┌─────────────────────────┘   │
       │                            ▼  ▼                             │
       │   PinnedHeapHandleTable (Pinned Object Heap)                │
       │   ┌───────────────────────────────────────────────┐         │
       │   │  공유 Object[] 배열                            │         │
       │   │  [0] ●──────────────────────────┐             │         │
       │   │  [1] ●───────────────┐          │             │         │
       │   │  [2] null            │          │             │         │
       │   └──────────────────────┼──────────┼─────────────┘         │
       │                          ▼          ▼                       │
       │   관리 힙(SOH/LOH)   ┌─────────┐ ┌─────────┐                 │
       │                     │ ███ R   │ │ ███ 박싱 │                 │
       │                     │  객체    │ │ 된 구조체│                 │
       │                     └─────────┘ └─────────┘                 │
       │                                                             │
       │   NonGC 힙 (frozen)  ┌─────────────────┐                     │
       │                     │ ███ 참조 없는    │  ← 참조를 담지 않고    │
       │                     │  박싱된 구조체    │    수집 불가 어셈블리   │
       │                     └─────────────────┘                     │
       └────────────────────────────────────────────────────────────┘

.NET 8 기준. .NET Framework에서는 statics blob이 해당 타입의 MethodTable 옆에 저장된다.
```

앞서 언급한 공유 `Object[]` 배열은 내부 `PinnedHeapHandleTable` 자료구조가 유지하며(문자열 인터닝에서도 쓰이는 바로 그 구조다 — 54.7절), **고정 객체 힙(POH)** 에 할당된다. 이 배열 자신도 고정되어 있어야 안쪽을 가리키는 주소를 저장하는 것이 안전하다. 이 핸들 테이블은 배열을 버킷 단위로 유지하므로, 현재 쓰는 배열이 가득 차면 새 버킷과 새 배열이 만들어진다 — 예를 들어 정적 필드를 가진 새 제네릭 타입이 구성되어야 할 때 일어난다.

> **⚠️ 제네릭 타입의 정적 필드는 닫힌 타입마다 따로 존재한다**
>
> ```csharp
> public class Cache<T>
> {
>     public static Dictionary<string, T> Items = new();
> }
> ```
>
> `Cache<int>.Items`와 `Cache<string>.Items`는 **서로 다른 필드**다. 각 닫힌 제네릭 타입이 자기 `MethodTable`을 가지고, 따라서 자기 정적 데이터 슬롯을 가진다. 위 다이어그램에서 "정적 필드를 가진 새 제네릭 타입이 구성될 때 새 버킷이 필요할 수 있다"고 한 것이 이 이야기다.
>
> 이 성질은 유용하기도 하고 위험하기도 하다. 유용한 쪽은 타입별 캐시를 공짜로 얻는다는 것이다. 위험한 쪽은 **인스턴스화 개수만큼 캐시가 늘어나고, 그 전부가 절대 수집되지 않는다**는 것이다. 런타임에 타입을 만들어 내는 코드(직렬화기, ORM, DI 컨테이너)와 제네릭 정적 캐시를 결합하면 사실상 무한히 자라는 누수가 된다.

### JIT이 정적 필드를 읽는 세 가지 코드

정적 관련 데이터를 만들 때, 모든 정적 필드의 오프셋이 계산되어 해당 `MethodTable`의 필드 기술에 저장된다. JIT 컴파일러가 정적 필드에 접근하는 코드를 방출할 때 이 데이터를 다음과 같이 소비한다.

- **기본형 정적 필드** — 해당 `DomainLocalModule`의 주소와 statics blob 안에서의 오프셋을 알고 있으므로, 데이터의 **절대 주소를 계산**한다.
- **참조 타입 정적 필드, 그리고 수집 가능 어셈블리에서 왔거나 참조를 담은 구조체 정적 필드**(힙에 박싱되어 할당된 것들) — `PinnedHeapHandleTable`과 그 버킷을 이용해 대응하는 `Object[]` 배열의 주소를 얻고, 인덱스로부터 배열 원소(객체를 가리키는 참조)의 절대 주소를 계산한다.
- **참조를 담지 않고 수집 불가 어셈블리에서 온 구조체 정적 필드라는 특수한 경우** — NonGC 힙의 박싱된 구조체에 대한 **직접 주소**를 JIT이 방출한다. 그곳의 객체는 절대 이동하거나 수집되지 않으므로 가능한 일이다.

세 경우를 다음 타입으로 실제로 확인해 보자.

```csharp
public class ExampleClass
{
    public static int StaticPrimitive;
    public static S   StaticStruct;
    public static R   StaticObject = new R();
}

public class R { public int Value; }
public struct S { public int Value; }
```

**첫째, 기본형 정적 필드.**

```csharp
[MethodImpl(MethodImplOptions.NoInlining)]
public void Method1()
{
    Console.WriteLine(ExampleClass.StaticPrimitive);
}
```

```text
...
mov   ecx,dword ptr [00007ffc`9c65c580] ; High Frequency Heap 안의 주소 (statics blob)
call  00007ff9`3c9c1380                 ; System.Console.WriteLine(Int32)
...
```

**주소 하나에서 값을 읽는 것이 전부다.** 기본형 정적 데이터 접근은 부가 오버헤드가 없는 매우 빠른 연산으로 봐도 된다.

**둘째, 값 타입 정적 필드(NonGC 힙 최적화가 적용되는 경우).** `Method2`가 `ExampleClass.StaticStruct.Value`를 출력한다고 하자.

```text
...
mov  rcx,225779604C0h              ; frozen segment(NonGC 힙) 안의 주소
mov  ecx,dword ptr [rcx]           ; 구조체의 첫 필드 접근
call qword ptr [00007ffc`9c6a4750] ; System.Console.WriteLine(Int32)
...
```

JIT이 NonGC 힙 안의 구조체 인스턴스에 **직접 접근**한다. 매우 효율적이다.

**셋째, 참조 타입 정적 필드.** `Method3`이 `ExampleClass.StaticObject.Value`를 출력한다고 하자.

```text
mov   rcx,19510002940h        ; POH 안의 주소 (핸들 테이블)
mov   rcx,qword ptr [rcx]     ; 핸들 역참조 (rcx가 객체 주소를 담게 된다)
mov   ecx,dword ptr [rcx+8]   ; 객체의 첫 필드 접근
call  00007ff9`3c9c2b60       ; System.Console.WriteLine(Int32)
```

**역참조가 한 번 더 있다.** 핸들 테이블에서 객체 주소를 먼저 읽어야 하기 때문이다. NonGC 힙 최적화가 적용되지 않는 구조체 정적 필드 — 즉 참조를 담고 있거나 수집 가능 어셈블리에서 로드된 모든 구조체 — 에 대해서도 이와 유사한 코드가 방출된다.

> **📌 정적 필드의 타입이 중요하지, 그것을 담은 타입은 상관없다**
>
> 위 예에서 `ExampleClass`가 클래스가 아니라 구조체였어도 (주소만 다를 뿐) **같은 코드가 생성된다.** 정적 필드가 어디에 어떻게 저장될지를 결정하는 것은 **정적 필드 자신의 타입**이지, 그것이 정의된 타입이 아니다.

> **⚠️ .NET 7 이전에는 구조체 정적 필드에 추가 오버헤드가 있었다** ※.NET 7
>
> frozen segment(NonGC 힙)가 도입된 .NET 7 이전에는, 구조체 정적 필드가 관리 힙에 박싱된 형태로 저장되었고 위의 세 번째(참조 타입) 경로와 정확히 같은 방식으로 접근되었다. **구형 프레임워크를 대상으로 한다면 구조체 정적 필드에 이 작은 추가 오버헤드가 있다는 것을 알고 있어야 한다.**
>
> 반대로 최신 런타임에서는, 수집 가능 어셈블리는 흔하지 않고 기본값이 수집 불가이므로, **구조체에 참조 필드만 없으면 이 최적화의 혜택을 받는다.** 특수한 경우처럼 들리지만 실제로는 꽤 흔하다.

> **⚠️ 정적 필드는 GC 루트다 — 그리고 이것이 누수의 1번 원인이다**
>
> 정적 필드에서 도달 가능한 모든 객체는 AppDomain(또는 ALC)이 살아 있는 한 절대 수집되지 않는다. 정적 `Dictionary`에 항목을 넣고 지우지 않으면 그것은 **설계된 메모리 누수**다. 특히 위험한 조합이 정적 이벤트다. `SomeStatic.Changed += instance.Handler;`는 정적 필드에서 `instance`로 가는 강한 참조를 만들고, 구독을 해제하지 않으면 `instance`는 프로세스 종료까지 산다(66.11절).

> **💡 정적 캐시에는 반드시 퇴출 정책을 붙여라**
>
> 정적 컬렉션을 캐시로 쓰기로 했다면 그것은 **크기 상한이나 만료 정책이 있는 캐시여야 한다.** `MemoryCache` 같은 기성 구현을 쓰거나 최소한 LRU 상한을 직접 두라. "일단 딕셔너리에 담아 두고 나중에 생각하자"가 프로덕션 메모리 문제의 가장 흔한 출발점이다. 그리고 `ConcurrentDictionary`를 쓴다고 해결되지 않는다 — 스레드 안전성과 수명 관리는 별개의 문제다.

## 54.6 박싱과 언박싱의 실제 IL과 힙 표현

### 박싱은 타입 시스템이 정의한 연산이다

ECMA-335는 이렇게 말한다.

> 모든 값 타입에 대해, CTS는 **박싱된 타입(boxed type)** 이라 불리는 대응하는 참조 타입을 정의한다. 역은 참이 아니다 — 일반적으로 참조 타입에는 대응하는 값 타입이 없다. 박싱된 타입의 값(박싱된 값)의 표현은 그 값 타입의 값을 저장할 수 있는 위치다. 박싱된 타입은 객체 타입이고 박싱된 값은 객체다. (…)
>
> 모든 값 타입에는 `box`라는 연산이 있다. 값 타입의 값을 박싱하면 그 박싱된 값이 만들어진다. 즉 원본 값의 **비트 단위 복사본**을 담고 있는 대응 박싱 타입의 값이다.

값 타입과 참조 타입의 정의가 스택과 힙을 전혀 언급하지 않듯, 박싱의 정의도 언급하지 않는다. **박싱은 값 타입 인스턴스를 참조 타입 인스턴스로 변환하는 과정이다.**

값 타입 인스턴스가 힙에 할당되어야 하는 시나리오가 있다는 것을 여러 번 봤다. 그리고 관리 힙의 모든 객체는 객체 헤더와 `MethodTable` 참조 같은 부가 메타데이터를 가져야 한다. 따라서 값 타입이 힙에 할당될 때 그 값은 이 부가 데이터로 감싸져야 한다. 박싱은 **두 단계 연산**이다.

1. 대응하는 값 타입을 위한 박싱 타입을 힙에 할당한다 (새 참조 타입 인스턴스).
2. 값 타입 인스턴스의 데이터를 새로 만든 참조 타입 인스턴스로 **복사한다**.

효율적인 연산이 아니라는 직관은 정확하다. 객체가 할당되어야 하고, 데이터 복사가 클록 사이클을 잡아먹는다. 더 나쁜 것은 **이 박싱 타입 인스턴스가 언젠가 가비지 컬렉션되어야 한다**는 점이다. GC에 압력을 준다.

### IL에서 본 박싱

```csharp
int i = 123;
object o = i;  // 암시적 박싱
```

```il
   ldc.i4.s 123
   box       System.Int32
   ret
```

`box` 명령은 값을 받아, 박싱 결과 — 즉 새로 생성된 참조 타입 인스턴스에 대한 참조 — 를 평가 스택에 푸시한다.

이것이 앞서 말한 두 단계 연산으로 그대로 번역된다. 릴리스 x64 모드에서 생성되는 어셈블리를 보자.

```text
push    rbp
sub     rsp,40h
lea     rbp,[rsp+40h]
vxorps  xmm4,xmm4,xmm4
vmovdqu xmmword ptr [rbp-18h],xmm4
xor     eax,eax
mov     qword ptr [rbp-8],rax
mov     dword ptr [rbp-4],7Bh              ; 스택의 int i = 123 (0x7B)
mov     rcx,7FFB7B75F640h                  ; MT: System.Int32
call    coreclr!JIT_TrialAllocSFastMP_InlineGetThread   ; ① 힙 할당
mov     qword ptr [rbp-10h],rax
mov     rax,qword ptr [rbp-10h]
mov     edx,dword ptr [rbp-4]
mov     dword ptr [rax+8],edx              ; ② 값 복사 (오프셋 +8 = 첫 필드)
```

**① 할당 → ② 복사.** 정의 그대로다. 그리고 `mov dword ptr [rax+8],edx`의 `+8`을 다시 확인하라. 54.2절에서 본 그 오프셋이다.

### 박싱된 값의 힙 레이아웃

```text
 박싱 전 (64비트)                       박싱 후 (64비트)

  스택                                   스택            관리 힙
┌───────────────┐                     ┌────────┐     ┌──────────────────────┐
│ int i = 123   │  4바이트             │ i =123 │     │ 정렬 패딩      (4B)   │
│  ▸ 7B 00 00 00│                     ├────────┤     │ 싱크 블록 인덱스(4B)   │
└───────────────┘                     │ o  ●───┼────▶├══════════════════════┤
                                      └────────┘     │ MethodTable 참조 (8B) │ ← o가
   메타데이터 0바이트                                   │  ▸ System.Int32의 MT │   가리키는 곳
   힙 할당 없음                                        ├──────────────────────┤
                                                     │ 값 123        (4B)   │ ← o + 8
                                                     │ 패딩          (4B)   │
                                                     └──────────────────────┘
                                                       힙 점유 24바이트
```

`int` 하나(4바이트)를 박싱하면 힙에서 **24바이트**를 차지한다(54.3절의 최소 객체 크기). 6배다. `Int32`의 값 4바이트에 헤더 8 + `MethodTable` 참조 8 = 16바이트가 붙고, 최소 크기 규칙 때문에 필드 영역이 8바이트로 채워진다.

| 박싱 대상 | 값 크기 | 64비트 힙 점유 | 배수 |
|---|---|---|---|
| `bool` | 1 B | 24 B | 24× |
| `int` | 4 B | 24 B | 6× |
| `long` | 8 B | 24 B | 3× |
| `Guid` | 16 B | 32 B | 2× |
| `DateTime` | 8 B | 24 B | 3× |
| `decimal` | 16 B | 32 B | 2× |

### 언박싱 — `unbox`와 `unbox.any`는 다르다

박싱에는 짝이 되는 연산인 언박싱이 있다. 박싱된 참조 타입 값을 다시 값 타입 인스턴스로 변환하는 것이다. 이 연산은 훨씬 적은 주목을 받는데, 그럴 만한 이유가 있다.

- 애초에 **박싱이 없으면 언박싱도 일어나지 않는다.**
- 언박싱은 **힙 할당을 유발하지 않는다.** 값이 힙에서 스택으로 복사되므로 메모리 복사 오버헤드는 있지만, 스택 관련 비용은 훨씬 덜 두렵다.

여기에 미묘한 함정이 하나 있다. ECMA-335는 이렇게 말한다. "모든 박싱 타입에는 `unbox`라는 연산이 있고, 그 결과는 **값의 비트 표현에 대한 관리 포인터**다." 실제로 CIL의 `unbox` 명령이 정확히 그 일을 한다 — 박싱된 인스턴스 안의 데이터를 가리키는 관리 포인터를 평가 스택에 푸시한다. **순수한 형태의 언박싱은 복사도 할당도 하지 않는다.**

하지만 그 포인터로 실제 값을 얻어야 한다. 그 일을 하는 것이 `ldobj` 명령이다 — "주소 src에 저장된 값을 스택으로 복사한다". C# 컴파일러가 언박싱을 하려 할 때 방출하는 것은 `unbox.any` 명령이며, 이것은 **`unbox` 다음에 `ldobj`가 오는 것과 동등하다.**

```text
   IL 명령          하는 일                                 할당  복사
  ─────────────  ────────────────────────────────────  ────  ────
   box            힙에 박싱 인스턴스 할당 + 값 복사          O     O
   unbox          박싱 인스턴스 안 데이터의 관리 포인터 반환   X     X
   ldobj          그 주소의 값을 평가 스택으로 복사           X     O
   unbox.any      unbox + ldobj  (C# 컴파일러가 방출)       X     O
```

박싱된 값 타입 인스턴스가 언박싱될 때 내부적으로 정확히 다음이 일어난다.

1. 박싱된 값 타입 인스턴스에 대한 참조를 담은 변수가 `null`이면 `NullReferenceException`이 발생한다.
2. 참조가 **원하는 값 타입의 박싱된 인스턴스**인 객체를 가리키지 않으면 `InvalidCastException`이 발생한다.

> **⚠️ 언박싱은 정확한 타입으로만 된다**
>
> 두 번째 항목이 흔한 함정을 만든다.
>
> ```csharp
> int   x = 5;
> object o = x;            // x를 박싱; o는 박싱된 객체를 참조한다
> short y = (short) o;     // InvalidCastException 발생
> ```
>
> 논리적으로는 `o`가 참조하는 박싱된 `int`를 `short`로 캐스팅하는 것이 말이 된다. 그러나 객체를 언박싱할 때 캐스팅은 **정확한 언박싱 값 타입**으로 해야 한다 — 여기서는 `int`다. 올바르게 쓰면 이렇다.
>
> ```csharp
> short y = (short)(int) o;   // 올바른 타입으로 언박싱한 뒤 캐스팅
> ```
>
> 컴파일러가 잡아 주지 않으므로 런타임에 터진다. `Convert.ToInt16(o)`처럼 변환 API를 쓰면 이 문제를 피할 수 있지만, 그 경우 별도의 오버헤드와 예외 종류(값 범위를 벗어나면 `OverflowException`)를 고려해야 한다.

### 박싱은 몇 번 일어나는가

다음 코드에서 박싱이 몇 번 일어나는지 세어 보라.

```csharp
public static void Main()
{
    int    v = 5;
    object o = v;
    v = 123;
    Console.WriteLine(v + ", " + (int) o);   // "123, 5"
}
```

답은 **세 번**이다. IL을 보면 명확하다.

```il
.method public hidebysig static void Main() cil managed
{
  .locals init ([0] int32 v, [1] object o)

  IL_0000: ldc.i4.5
  IL_0001: stloc.0
  IL_0002: ldloc.0
  IL_0003: box        [mscorlib]System.Int32   // ← 박싱 ① : o = v
  IL_0008: stloc.1
  IL_0009: ldc.i4.s   123
  IL_000b: stloc.0
  IL_000c: ldloc.0
  IL_000d: box        [mscorlib]System.Int32   // ← 박싱 ② : Concat의 arg0
  IL_0012: ldstr      ", "
  IL_0017: ldloc.1
  IL_0018: unbox.any  [mscorlib]System.Int32   //   언박싱 : (int) o
  IL_001d: box        [mscorlib]System.Int32   // ← 박싱 ③ : Concat의 arg2
  IL_0022: call       string [mscorlib]System.String::Concat(object, object, object)
  IL_0027: call       void [mscorlib]System.Console::WriteLine(string)
  IL_002c: ret
}
```

`String.Concat(object, object, object)` 오버로드가 선택되었기 때문에 세 인수가 모두 힙 객체 참조여야 한다. `v`는 박싱되고, `", "`는 이미 참조이고, `(int) o`는 **언박싱한 뒤 다시 박싱**된다.

캐스트 하나만 지워 보자.

```csharp
Console.WriteLine(v + ", " + o);   // "123, 5"
```

`o`는 이미 `object`에 대한 참조이므로 주소를 그대로 넘기면 된다. 캐스트를 제거하니 **언박싱 하나와 박싱 하나**가 사라졌다. IL 크기가 10바이트 줄고, 더 중요하게는 **미래에 수집되어야 할 객체 하나가 덜 만들어진다.**

한 걸음 더 갈 수 있다.

```csharp
Console.WriteLine(v.ToString() + ", " + o);   // "123, 5"
```

이제 박싱되지 않은 값 타입 인스턴스 `v`에 대해 `ToString`이 호출되고 `String`이 반환된다. `String` 객체는 이미 참조 타입이므로 박싱 없이 `Concat`에 넘길 수 있다.

> **📌 BCL의 오버로드 폭탄은 박싱을 줄이려는 설계다**
>
> `System.Console`은 `WriteLine`의 오버로드를 여러 개 제공한다.
>
> ```csharp
> public static void WriteLine(bool);     public static void WriteLine(char);
> public static void WriteLine(int);      public static void WriteLine(uint);
> public static void WriteLine(long);     public static void WriteLine(ulong);
> public static void WriteLine(float);    public static void WriteLine(double);
> public static void WriteLine(decimal);  public static void WriteLine(char[]);
> public static void WriteLine(object);   public static void WriteLine(string);
> ```
>
> `Console.Write`, `System.IO.BinaryWriter.Write`, `System.IO.TextWriter.Write`/`WriteLine`, `System.Text.StringBuilder.Append`/`Insert` 등에서 비슷한 오버로드 집합을 볼 수 있다. 이 오버로드 대부분의 유일한 존재 이유가 **흔한 값 타입에 대한 박싱 횟수를 줄이는 것**이다.
>
> 뒤집어 말하면, 당신이 직접 정의한 값 타입에는 이런 오버로드가 존재하지 않는다. 특정 값 타입에 대한 오버로드가 없는 메서드를 호출하면 결국 `object`를 받는 오버로드가 호출되고 박싱이 일어난다. 자기 클래스를 설계한다면 **메서드를 제네릭으로** 정의하는 것이 답이다(필요하면 타입 매개변수를 값 타입으로 제약해서).

> **💡 같은 값을 반복해서 박싱한다면 직접 한 번만 박싱하라**
>
> ```csharp
> int v = 5;
>
> // 나쁨: v가 세 번 박싱된다 — 힙 객체 세 개
> Console.WriteLine("{0}, {1}, {2}", v, v, v);
>
> // 좋음: 수동으로 한 번만 박싱
> object o = v;
> Console.WriteLine("{0}, {1}, {2}", o, o, o);
> ```
>
> 첫 번째 버전은 내용이 전부 `5`로 똑같은 객체 세 개를 힙에서 할당한다. 두 번째는 하나만 할당하고 그 참조를 세 번 넘긴다. 더 빠르고 메모리를 덜 쓴다.
>
> 물론 요즘 C#에서는 보간 문자열 핸들러가 이런 경우를 상당 부분 알아서 처리한다(69.5절). 그래도 원리는 알아 둘 가치가 있다.

### 언제 박싱이 일어나는가 — 그리고 언제 안 일어나는가

박싱은 "값 타입 인스턴스에 대한 참조가 필요할 때" 일어난다. 그런데 값 타입에도 `Equals`, `GetHashCode`, `ToString` 같은 상속된 가상 메서드가 있다. 이들을 호출할 때 매번 박싱이 일어날까? 답은 "경우에 따라 다르다"이며, 규칙은 정확하다.

```csharp
internal struct Point : IComparable
{
    private readonly int m_x, m_y;
    public Point(int x, int y) { m_x = x; m_y = y; }

    // System.ValueType에서 상속한 ToString을 재정의한다.
    // 안쪽에서 ToString()을 명시적으로 호출해 박싱을 막는다.
    public override string ToString()
        => string.Format("({0}, {1})", m_x.ToString(), m_y.ToString());

    public int CompareTo(Point other)               // 타입 안전한 오버로드
        => Math.Sign(Math.Sqrt(m_x * m_x + m_y * m_y)
                   - Math.Sqrt(other.m_x * other.m_x + other.m_y * other.m_y));

    public int CompareTo(object o)                  // IComparable 구현
    {
        if (GetType() != o.GetType()) throw new ArgumentException("o is not a Point");
        return CompareTo((Point) o);
    }
}
```

```csharp
Point p1 = new Point(10, 10);
Point p2 = new Point(20, 20);

Console.WriteLine(p1.ToString());     // 박싱 없음 → "(10, 10)"
Console.WriteLine(p1.GetType());      // 박싱 발생  → "Point"
Console.WriteLine(p1.CompareTo(p2));  // 박싱 없음 → "-1"

IComparable c = p1;                   // 박싱 발생
Console.WriteLine(c.GetType());       // 박싱 없음 (c는 이미 박싱된 Point) → "Point"
Console.WriteLine(p1.CompareTo(c));   // 박싱 없음 → "0"  (c가 가리키는 것이 p1 자신의 박싱본)
Console.WriteLine(c.CompareTo(p2));   // p2가 박싱된다 → "-1"

p2 = (Point) c;                       // 언박싱 + 필드 복사
Console.WriteLine(p2.ToString());     // "(10, 10)"
```

하나씩 이유를 보자.

| 호출 | 박싱? | 이유 |
|---|---|---|
| `p1.ToString()` | **없음** | `Point`가 `ToString`을 재정의했다. JIT은 값 타입이 암시적으로 sealed임을 알고 있으므로 다형성이 개입할 여지가 없다. **비가상으로 직접 호출**하는 코드를 방출한다 |
| `p1.GetType()` | **발생** | `GetType`은 `System.Object`가 정의한 **비가상** 메서드다. 호출하려면 타입 객체 포인터가 필요하고, 그것은 박싱해야만 얻을 수 있다 |
| `p1.CompareTo(p2)` | **없음** | `Point`가 `CompareTo(Point)`를 직접 구현했다. 인수가 `Point`이므로 컴파일러가 그 오버로드를 고른다. `p2`도 값으로 전달되므로 박싱 불필요 |
| `IComparable c = p1;` | **발생** | 인터페이스는 정의상 참조 타입이다. 인터페이스 변수는 항상 힙 객체를 가리켜야 한다 |
| `p1.CompareTo(c)` | **없음** | `c`가 `IComparable`이므로 `CompareTo(object)` 오버로드가 선택된다. `c`는 이미 박싱된 `Point`를 가리키므로 그 주소를 그대로 넘기면 된다 |
| `c.CompareTo(p2)` | **`p2` 박싱** | `c`가 인터페이스 타입이라 `CompareTo(object)`만 호출할 수 있다. `p2`는 박싱되어야 한다 |
| `(Point) c` | 언박싱 | `c`가 가리키는 힙 객체가 언박싱되고 필드가 `p2`로 복사된다 |

> **⚠️ 재정의한 가상 메서드가 `base`를 호출하면 거기서 박싱된다**
>
> `Point.ToString()`이 박싱 없이 호출된다고 했다. 그런데 그 구현 안에서 `base.ToString()`을 호출하면, `System.ValueType.ToString()`을 호출하기 위해 **그 시점에 값 타입 인스턴스가 박싱된다.** 기저 메서드의 `this` 포인터에는 힙 객체에 대한 참조가 넘어가야 하기 때문이다.
>
> 마찬가지로 `GetType`이나 `MemberwiseClone` 같은 **비가상 상속 메서드**를 호출하면 항상 박싱이 필요하다. `System.Object`가 정의한 메서드이므로 `this`가 힙 객체 포인터여야 한다.

### 박싱된 값을 수정하기 — 그리고 왜 하면 안 되는가

이 절의 마지막 예제는 값 타입을 불변으로 만들어야 하는 이유를 가장 선명하게 보여준다.

```csharp
internal interface IChangeBoxedPoint { void Change(int x, int y); }

internal struct Point : IChangeBoxedPoint
{
    private int m_x, m_y;
    public Point(int x, int y) { m_x = x; m_y = y; }
    public void Change(int x, int y) { m_x = x; m_y = y; }
    public override string ToString() => $"({m_x}, {m_y})";
}

public static void Main()
{
    Point p = new Point(1, 1);
    object o = p;                       // p 박싱

    ((Point) o).Change(3, 3);
    Console.WriteLine(o);               // "(1, 1)" ← 많은 개발자가 예상하지 못한다

    ((IChangeBoxedPoint) p).Change(4, 4);
    Console.WriteLine(p);               // "(1, 1)"

    ((IChangeBoxedPoint) o).Change(5, 5);
    Console.WriteLine(o);               // "(5, 5)"
}
```

첫 번째가 문제다. `o`를 `Point`로 캐스팅하면 `o`가 **언박싱되고, 박싱된 `Point`의 필드가 스레드 스택의 임시 `Point`로 복사된다.** 그 임시 `Point`의 필드가 3, 3으로 바뀌지만 **박싱된 `Point`는 영향을 받지 않는다.**

C++/CLI 같은 일부 언어는 박싱된 값 타입의 필드를 바꿀 수 있게 해 주지만 C#은 그렇지 않다. 그런데 **인터페이스를 쓰면 C#을 속일 수 있다** — 위 예제의 나머지 두 호출이 그것이다.

- `((IChangeBoxedPoint) p).Change(4, 4)` — 박싱되지 않은 `p`를 인터페이스로 캐스팅하면 **박싱이 일어난다.** 그 박싱된 값에 `Change`가 호출되어 필드가 4, 4로 바뀌지만, `Change`가 반환되는 순간 그 박싱된 객체는 곧바로 가비지 컬렉션 대상이 된다. 원본 `p`는 그대로다.
- `((IChangeBoxedPoint) o).Change(5, 5)` — `o`는 **이미 박싱된 `Point`** 이므로 박싱이 필요 없다. `Change`가 그 박싱된 `Point`의 필드를 실제로 바꾼다.

> **⚠️ 이것이 값 타입을 불변으로 만들어야 하는 이유다**
>
> 위 예제의 예상 밖 동작은 **전부 값 타입의 인스턴스 필드를 수정하는 메서드를 호출할 때** 일어난다. 값 타입을 생성한 뒤 상태를 바꾸는 메서드를 호출하지 않으면, 박싱과 언박싱/필드 복사가 언제 일어나든 헷갈릴 일이 없다 — 결국 같은 상태를 복사해 옮기는 것뿐이기 때문이다.
>
> 구체적인 권고는 **값 타입의 필드를 `readonly`로 선언하는 것**이다. 실수로 필드를 수정하는 메서드를 작성하면 컴파일러가 오류를 낸다. `readonly struct`(16.5절) ※C# 7.2 를 쓰면 타입 전체에 이 규칙을 걸 수 있다. 그리고 BCL의 핵심 값 타입(`Byte`, `Int32`, `Int64`, `Single`, `Double`, `Decimal`, `BigInteger`, `Complex`, 모든 열거형 등)은 **전부 불변**이니 안심해도 된다.

> **💡 박싱을 찾아내는 도구를 상시 켜 두라**
>
> 암시적 박싱이 일어날 수 있는 자리는 아주 많고 항상 전부 인지하기란 어렵다. Visual Studio용 **Clr Heap Allocation Analyzer** 확장과 ReSharper용 **Roslyn C# Heap Allocation Analyzer** 플러그인이 암시적 박싱을 포함한 숨은 할당을 전부 표시해 준다. 일상 작업에서 켜 두기를 강력히 권한다.
>
> 성능이 걱정되는 알고리즘이라면 `ildasm.exe`나 SharpLab으로 IL을 직접 열어 `box` 명령이 어디에 있는지 보는 것이 가장 확실하다. 박싱 회피의 실무 카탈로그는 63.9절과 69장에서 다룬다.

## 54.7 문자열과 배열의 특수 레이아웃

### 가변 길이 객체라는 예외

지금까지 본 객체는 모두 **크기가 컴파일 타임에 결정되는** 것들이었다. `MethodTable`의 `BaseSize` 하나로 크기가 정해진다. 그런데 배열과 문자열은 다르다. 같은 타입이라도 인스턴스마다 크기가 다르다.

.NET은 이 문제를 54.2절에서 본 "선택적 데이터 자리"를 재활용해 푼다. **보통 객체에서 첫 필드가 놓이는 자리에, 배열과 문자열은 요소 개수를 저장한다.** 그리고 크기 계산 공식이 달라진다.

```text
일반 객체:   크기 = BaseSize
배열/문자열:  크기 = BaseSize + ComponentSize × 요소 개수
```

`ComponentSize`는 `MethodTable`에 저장된 값이며, 요소 하나의 크기다. `int[]`이면 4, `object[]`이면 8(64비트), `string`이면 2다. 일반 클래스에서는 0이다.

### 배열의 레이아웃

```text
── 64비트 런타임: int[4] ──────────────────────────────────

           ┌───────────────────────────┐  ← 참조 - 8
    -8     │ 정렬 패딩          (4B)    │
    -4     │ 싱크 블록 인덱스    (4B)    │
           ├═══════════════════════════┤
참조 ─────▶│ MethodTable 참조   (8B)    │  ← 참조 + 0  (int[]의 MT)
   +8      ├───────────────────────────┤
           │ 요소 개수 = 4      (4B)    │  ← 참조 + 8
   +12     │ 패딩              (4B)    │
   +16     ├───────────────────────────┤
           │ [0]               (4B)    │  ← 참조 + 0x10  ★ 데이터 시작
   +20     │ [1]               (4B)    │
   +24     │ [2]               (4B)    │
   +28     │ [3]               (4B)    │
           └───────────────────────────┘
             합계 40바이트 (헤더 8 + MT 8 + 길이/패딩 8 + 데이터 16)


── 32비트 런타임: int[4] ──────────────────────────────────

 -4: 싱크 블록 인덱스(4B) │ +0: MethodTable 참조(4B) │ +4: 요소 개수 4(4B)
 +8: [0][1][2][3] (16B)   ★ 데이터 시작 — 패딩이 필요 없다
 합계 28바이트
```

64비트에서 **데이터가 오프셋 `0x10`(16)에서 시작한다**는 것이 핵심이다. 요소 개수는 4바이트지만, 그 뒤 데이터가 8바이트 정렬을 유지하려면 4바이트 패딩이 필요하기 때문이다.

이것은 추측이 아니라 JIT 출력에서 직접 읽을 수 있다. 다음 두 헬퍼 메서드를 보자.

```csharp
public int Helper1(SmallStruct[] data, int index) => data[index].Value1;
public int Helper2(SmallClass[]  data, int index) => data[index].Value1;
```

`SmallStruct`는 `int` 두 개(8바이트)이고, `SmallClass`도 `int` 두 개를 가진 클래스다. 생성되는 어셈블리는 이렇다. `rax`가 배열 객체의 주소, `rcx`가 인덱스다.

```text
Helper1(Samples.SmallStruct[], Int32)
...
lea     rax,[rax+rcx*8+10h]      ; 주소 = 배열 + 인덱스×8 + 0x10
mov     eax,dword ptr [rax]      ; 그 주소에서 Value1을 읽는다
...

Helper2(Samples.SmallClass[], Int32)
...
lea     rax,[rax+rcx*8+10h]      ; 주소 = 배열 + 인덱스×8 + 0x10
mov     rax,qword ptr [rax]      ; 그 자리의 "참조"를 읽는다
mov     eax,dword ptr [rax+8]    ; 그 객체의 Value1을 읽는다
...
```

두 경우 모두 `+10h` — 16 — 이 나온다. 배열 데이터의 시작 오프셋이다. `rcx*8`은 요소 크기가 8바이트이기 때문이다(구조체는 `int` 두 개, 참조는 8바이트). 두 헬퍼의 차이는 54.9절의 주제다.

> **📌 GC가 힙을 걸을 때도 이 규칙을 쓴다**
>
> 힙에 빈 공간이 생기면 GC는 그 자리에 **"free object"** 라는 더미를 채운다. 전용 `MethodTable`을 가진 가짜 배열처럼 생겼고, 메서드 테이블 포인터 뒤에 요소 개수가 저장된다 — 정확히 위 레이아웃 그대로다. `ComponentSize`가 1바이트이므로 **요소 개수가 곧 빈 공간의 바이트 수**가 된다. 힙을 훑던 GC(그리고 같은 기법을 쓰는 디버거)는 이 길이만 읽고 빈 공간을 통째로 건너뛴다. 자세한 것은 63.2절에서 다룬다.

### 배열 크기의 한계

.NET 초기부터 객체 하나의 최대 크기는 **2GB**였다. .NET Framework 4.5부터 `gcAllowVeryLargeObjects` 설정이 추가되어 64비트 부호 있는 `long` 값에 맞는 크기(에서 작은 값을 뺀 만큼)의 객체를 만들 수 있게 되었다.

```xml
<!-- .NET Framework의 app.config 스키마. 기본은 꺼져 있다 -->
<configuration>
  <runtime>
    <gcAllowVeryLargeObjects enabled="true" />
  </runtime>
</configuration>
```

2GB보다 큰 배열이 가능해지지만, **다른 한계는 바뀌지 않는다.**

| 항목 | 값 |
|---|---|
| 배열의 최대 요소 개수 | 2,147,483,591 |
| 단일 차원 최대 인덱스 — `byte` 배열과 단일 바이트 구조체 배열 | 2,147,483,591 (0x7FFFFFC7) |
| 단일 차원 최대 인덱스 — 그 외 타입 | 2,146,435,071 (0x7FEFFFFF) |
| 문자열과 그 밖의 비배열 객체의 최대 크기 | 변경 없음 |

이런 거대한 객체는 의심의 여지 없이 대형 객체 힙(LOH) 세그먼트에 만들어진다. 그리고 **할당 자체가 수 초 걸릴 수 있다** — 할당된 메모리를 0으로 채워야 하기 때문이다(62.3절, 63.4절).

### 문자열의 레이아웃

`String`은 문자 시퀀스를 나타내는 참조 타입이다. 오늘날 대부분의 프로그램이 텍스트 처리에 의존하므로, .NET 애플리케이션(특히 웹 기반)의 메모리 덤프를 분석하면 문자열이 언제나 객체 타입 목록의 상위에 있다.

현재 CoreCLR 구현에서 `System.String`은 두 개의 인스턴스 필드를 가진다 — `_stringLength`(`int`)와 `_firstChar`(`char`). 두 번째 필드는 문자 데이터의 **시작점**을 나타내는 표식이며, 실제 데이터는 그 뒤로 이어진다.

```text
── 64비트 런타임: "Hello, World!" (13자) ───────────────────

           ┌────────────────────────────────┐  ← 참조 - 8
    -8     │ 정렬 패딩              (4B)     │
    -4     │ 싱크 블록 인덱스        (4B)     │
           ├════════════════════════════════┤
참조 ─────▶│ MethodTable 참조       (8B)     │  ← String의 MT
    +8     ├────────────────────────────────┤
           │ _stringLength = 13     (4B)    │  ← 문자 개수 (바이트 수가 아니다)
   +12     ├────────────────────────────────┤
           │ 'H' 'e'                (4B)    │  ← _firstChar부터 UTF-16 데이터
   +16     │ 'l' 'l'                (4B)    │
   +20     │ 'o' ','                (4B)    │
           │  ...                           │
   +32     │ 'l' 'd'                (4B)    │
   +36     │ '!'                    (2B)    │  ← 13번째 문자
   +38     │ '\0'                   (2B)    │  ← 널 종결자 (상호운용용)
           └────────────────────────────────┘
             합계 48바이트 (헤더 8 포함, 이미 8의 배수라 패딩 없음)
```

문자 하나는 **2바이트**(UTF-16)다. 그래서 13자짜리 `"Hello, World!"`의 문자 데이터만 26바이트다. 여기에 헤더 8 + `MethodTable` 참조 8 + 길이 4 + 널 종결자 2 = 22바이트가 붙어 48바이트가 되고, 이미 8의 배수이므로 추가 패딩은 없다.

크기 공식은 이렇게 정리된다.

| 런타임 | 공식 | `""` | `"A"` | `"Hello, World!"` (13자) |
|---|---|---|---|---|
| 64비트 | (22 + 2×길이) 를 8의 배수로 올림 | 24 B | 24 B | 48 B |
| 32비트 | (14 + 2×길이) 를 4의 배수로 올림 | 16 B | 16 B | 40 B |

> **⚠️ 문자열의 메모리 비용을 문자 수로 어림하지 마라**
>
> 위 표에서 빈 문자열이 24바이트라는 점을 보라. 짧은 문자열 수백만 개(예: 딕셔너리 키)는 문자 데이터보다 **오버헤드가 더 큰** 경우가 흔하다. 세 글자짜리 문자열 100만 개는 문자 데이터로는 6MB지만 실제 힙 점유는 32MB다. 짧은 문자열이 대량으로 필요하고 대부분 중복이라면 뒤에서 볼 인터닝이나 자체 중복 제거를 검토하라. 아예 문자열을 만들지 않는 방법(`ReadOnlySpan<char>` 슬라이스)이 더 나은 경우도 많다(68.5절).

### 문자열의 불변성

문자열은 **설계상 불변**이라 .NET 환경에서 특별한 대우를 받는다. C나 C++ 같은 비관리 언어와 달리, 한번 만들어진 문자열 값은 바꿀 수 없다. 다음 코드는 `Property or indexer 'string.this[int]' cannot be assigned to -- it is read only` 컴파일 오류로 끝난다.

```csharp
string s = "Hello world!";
s[6] = 'W';   // 컴파일 오류
```

불변성이 주는 이점은 크다.

- **안전성** — 문자열은 다른 자료구조의 중요한 요소로 널리 쓰인다. 딕셔너리류 구조의 키를 생각해 보라. 키 값을 바꿀 수 있다면 그 컬렉션의 내부 표현(대개 균형 트리류)이 무효화된다. 문자열은 자격 증명, 파일 이름과 경로 등을 지정하기 위해 각종 API에 전달되기도 한다. **검사가 끝난 뒤에** 내용을 바꿀 수 있다면 매우 위험하다.
- **동시성** — 데이터가 변하지 않으므로 여러 스레드가 공유해도 위험이 없다. 락도, 거짓 공유의 위험도 필요 없다.

단점도 명확하다. **수정 연산이 문자열 인스턴스를 추가로 만든다.** 큰 텍스트 데이터에서 특히 아프다. 수 메가바이트짜리 텍스트를 담은 문자열에 `Replace('a', 'b')`를 한 번 호출하면, 몇 글자만 바뀐 새 수 메가바이트 문자열이 만들어진다.

> **⚠️ "문자열은 불변이라 절대 못 바꾼다"는 완전히 참은 아니다**
>
> BCL은 문자열 값을 수정할 수 있는 API를 (리플렉션 API를 통해서도) 노출하지 않는다. 그러나 **불변성이 런타임 수준에서 강제되지는 않는다.** 문자열의 내용은 제공된 인코딩의 문자로 해석되는 연속된 바이트 블록일 뿐이다. `unsafe` 모드에서 그 바이트들에 대한 포인터를 얻어 제자리에서 바꾸는 것을 막을 것은 아무것도 없다.
>
> 이것은 엄격히 **지원되지 않는 동작**이다. 이 길로 갔다가 생기는 문제는 전부 스스로 분석해야 한다. 특히 그 문자열이 인터닝된 리터럴이라면 프로그램 전체에서 그 리터럴의 값이 바뀐다.

> **📌 `string`은 왜 구조체가 아닌가**
>
> 값 타입은 불변으로 만들기에 완벽한 후보다. 데이터를 제자리에 저장하고 값에 의한 전달 의미론을 실현하므로 불변으로 만드는 것이 자연스럽다. 그런데 왜 `string`은 구조체가 아닐까?
>
> 잠시 생각해 보면 답이 나온다. **값 타입이 좋은 불변 타입일 수는 있지만, 그 역이 반드시 참일 필요는 없다.** 큰 문자열을 값으로 복사하면 막대한 오버헤드가 생긴다. 참조로 넘기는 편이 훨씬 효율적이다.

### 문자열 인터닝

.NET 런타임에는 **문자열 인터닝(string interning)** 이라는 메커니즘이 있다. 중복된 텍스트에 대한 효과적인 메모리 사용을 위한 최적화 기법으로, 같은 텍스트를 반복 복사하지 않고 메모리에 한 부만 유지한다. 다만 이 메커니즘은 기본적으로 **문자열 리터럴에만** 적용되고, 애플리케이션 실행 중 동적으로 만들어진 문자열에는 적용되지 않는다.

ECMA-335는 이렇게 말한다. "기본적으로, CLI는 같은 문자 시퀀스를 갖는 두 메타데이터 토큰을 참조하는 두 `ldstr` 명령의 결과가 정확히 같은 문자열 객체를 반환하도록 보장한다(문자열 인터닝이라 알려진 과정)."

```csharp
private static string Global = "Hello world!";

static void Main(string[] args)
{
    string s1 = "Hello world!";
    string s2 = "Hello ";
    string s3 = s2 + "world!";

    Console.WriteLine(string.ReferenceEquals(s1, Global));   // True
    Console.WriteLine(string.ReferenceEquals(s1, s3));       // False
}
```

`s1`과 `Global`은 같은 인터닝된 인스턴스를 참조하므로 첫 줄이 `True`다. `s3`는 같은 값을 갖지만 **동적으로 만들어졌으므로 인터닝되지 않았다.** (`"Hello "`와 `"world!"` 리터럴 자체는 인터닝되어 있다.)

왜 동적 생성 문자열은 기본적으로 인터닝하지 않는가? **상당한 오버헤드를 유발할 수 있기 때문이다.** 새 문자열을 만들려 할 때마다 이미 인터닝된 것인지 확인해야 하고, 인터닝된 문자열이 엄청나게 많다면 그 검사 비용이 눈에 띈다. 새 문자열을 만들지 않아 얻는 이득을 이 검사가 압도할 수 있다.

명시적으로 인터닝을 관리할 수는 있다. 정적 메서드 `string.IsInterned`는 주어진 값으로 인터닝된 문자열이 없으면 `null`을, 있으면 그 참조를 반환한다.

```csharp
string s4 = string.IsInterned(s3);
Console.WriteLine(s4);                                   // Hello world!
Console.WriteLine(string.ReferenceEquals(s4, Global));   // True

string message = args[0];
string s5 = string.IsInterned(message);
Console.WriteLine(s5);                                   // null

string s6 = string.Intern(message);
Console.WriteLine(string.ReferenceEquals(s6, message));  // True
```

`string.Intern`은 인터닝된 문자열 참조를 반환한다. 그런 값이 아직 인터닝되어 있지 않다면 주어진 참조를 인터닝하고 그것을 반환한다. 즉 **동적 생성 문자열을 인터닝한다는 것은 내부 자료구조에 그것을 기억해 둔다는 것 이상도 이하도 아니다.**

### 인터닝된 문자열은 어디에 사는가

여기서 흔한 혼란이 하나 있다. 인터닝된 문자열이 저장되는 위치다. 메모리 상의 관련 장소는 여러 개다.

핵심은 런타임이 **AppDomain마다** 네이티브 힙에 만드는 내부 `StringLiteralMap` 객체다. 인터닝할 문자열을 감싸기 위해 `SystemDomain::GlobalStringLiteralMap`에 요청하고, 이것이 문자열을 버킷으로 묶은 해시 테이블로 관리한다. 인터닝된 문자열마다 자기 항목이 있고, 각 항목은 계산된 해시와 **다른 구조의 항목 주소**를 담는다. 그 다른 구조가 `PinnedHeapHandleTable`이며, 실제로는 **고정 객체 힙(POH)** 에 존재한다. 이 핸들 테이블이 담는 것은 문자열 인스턴스에 대한 **참조뿐**이다. 그리고 그 문자열 인스턴스들은 관리 힙에 사는 "보통" 문자열이다.

```text
   네이티브 힙                     고정 객체 힙(POH)          관리 힙 (SOH/LOH)
┌───────────────────┐         ┌────────────────────┐    ┌──────────────────┐
│ StringLiteralMap  │         │PinnedHeapHandleTable│    │ ███ "Hello…"     │
│  (AppDomain별)     │         │  [0] ●──────────────┼───▶│  보통의 string   │
│   ↓ 요청           │         │  [1] ●──────────────┼─┐  └──────────────────┘
│ GlobalStringLiteral│         │  [2] null           │ │  ┌──────────────────┐
│ Map (해시 테이블)   │         └────────────────────┘ └─▶│ ███ "world!"     │
│  버킷: (해시, 핸들●)┼────────────▲                        └──────────────────┘
└───────────────────┘            │
                                 │        NonGC 힙 (.NET 5+)
                                 │      ┌──────────────────────┐
                                 └──────│ ███ 64KB 이하 리터럴    │ ← 핸들이 필요 없다
                                        └──────────────────────┘
```

따라서 **인터닝된 문자열이 어떤 특별한 "String Intern Pool" 자료구조 안에 산다고 말할 수 없다.** 그저 내부 문자열 리터럴 구조와 핸들 테이블 구조에 등록되고 관리될 뿐이다.

중요한 차이는 이 구조들이 **.NET 애플리케이션과 같은 수명을 산다**는 점이다. 따라서 인터닝된 문자열은 언제나 참조된다. GC 용어로 말하면 **항상 도달 가능하고 따라서 절대 수집되지 않는다.** 인터닝된 문자열은 다른 객체와 마찬가지로 관리 힙(85,000바이트 미만이면 SOH, 이상이면 LOH)에 살며, 결국 2세대로 승격되어 거기 영원히 머문다.

### 문자열 리터럴이 로드되는 과정

리터럴의 동작은 본질적으로 같지만 최적화가 하나 더 있다.

```csharp
string s = "Hello world!";
```

소스가 컴파일될 때 모든 문자열 리터럴은 실행 파일의 **`#US` 스트림**(User Strings)에 저장된다. 위 줄은 `#US` 스트림 테이블(`0x70000000`) 오프셋 1에 저장된 `"Hello world!"`에 대응하는 메타데이터 토큰에 적용된 `ldstr` CIL 명령으로 컴파일된다 — 즉 `ldstr 0x70000001`.

.NET 8의 JIT 컴파일러가 이 CIL 명령에 대해 만드는 단계는 다음과 같다.

1. 인덱스 1로 `#US` 스트림에서 문자들을 읽는다. **이것은 아직 관리되는 `System.String`이 아니다.** 읽기 전용 문자 스트림을 저장하는 내부 네이티브 blob 힙의 문자들에 대한 포인터일 뿐이다.
2. String Literal Map에 그 문자들에 대한 항목이 있으면 대응하는 주소를 반환한다.
3. 항목이 없으면 새 문자열을 만든다. .NET 5부터 런타임은 ※.NET 5 이 읽기 전용 리터럴이 **영원히 살 것**임을 알고 있으므로 **NonGC 힙**에 할당하려 시도한다. 크기가 **64KB보다 크면** NonGC 힙에 들어가지 못하고, 85,000바이트 미만이면 SOH에 그 이상이면 LOH에 놓인다. 스트림의 문자들이 그 메모리로 복사된다.
4. SOH나 LOH에 저장되었다면 그 문자열을 가리키는 새 핸들이 `PinnedHeapHandleTable`에 만들어진다(NonGC 힙이면 불필요). 두 경우 모두 String Literal Map에 항목이 만들어지고, NonGC 힙에 있는지를 나타내는 플래그가 함께 들어간다.

> **⚠️ 인터닝은 되돌릴 수 없다**
>
> 인터닝의 이점과 대가를 정확히 재라.
>
> **이점** — ① 중복 제거. ② 동등 비교 성능. 문자열 동등 비교는 양쪽을 바이트 단위로 비교해야 할 수 있어 큰 문자열에서 꽤 느리다. 그러나 `String.Equals`는 `if ((Object)this == value) return true;`로 시작하는 빠른 경로를 가진다.
>
> **대가** — ① **불멸성.** 인터닝된 문자열은 애플리케이션이 끝날 때까지(또는 앱 도메인이 언로드될 때까지) 도달 가능하다. 인터닝하려는 문자열은 십중팔구 곧 도달 불가능해져 수집될 것이었다. 인터닝은 그것을 불멸로 만든다. 메모리 사용을 줄이려다 정반대 결과를 얻을 수 있다. ② **임시 문자열 생성.** 이미 만들어진 문자열만 인터닝할 수 있다. 인터닝된 버전이 있는지 확인하기 위해서만이라도 인터닝되지 않은 문자열이 잠시 존재해야 한다.
>
> 결론은 이렇다. **오랫동안 메모리에 유지되는 중복 문자열이 많은 시나리오에서만** 인터닝의 이득을 본다. 대부분의 애플리케이션은 텍스트 데이터를 잠깐 처리하고 잊어버리므로, 이런 경우는 오히려 드물다. 참고로 XML이나 HTTP 처리 같은 시스템 라이브러리조차 이점이 명확하지 않아 기본적으로 인터닝을 쓰지 않는다.

## 54.8 타입 카테고리와 타입 저장 방식 — 값 타입 / 참조 타입의 실제 배치

### 잘못된 출발점

.NET 메모리에 관한 거의 모든 글이 같은 이야기를 반복한다 — "값 타입은 스택에 할당되고 참조 타입은 힙에 할당된다." **그러나 이것은 값 타입과 참조 타입을 구분하는 가장 적절한 방법이 아니다.** 구현 세부는 어떤 추상화 뒤에 있는 모든 구현이 그렇듯 변경 가능하다. 정말 중요한 것은 그것이 개발자에게 제공하는 **추상화**다. ECMA-335로 돌아가자.

> **값 타입(type, value)**: 그 인스턴스가 자신의 모든 데이터를 직접 담는 타입. (…) 값 타입이 기술하는 값들은 자기 완결적(self-contained)이다.
>
> **참조 타입(type, reference)**: 그 인스턴스가 자기 데이터에 대한 참조를 담는 타입. (…) 참조 타입이 기술하는 값은 다른 값의 **위치**를 나타낸다.

여기에 두 종류의 타입이 제공하는 추상화의 진짜 차이가 있다. **값 타입의 인스턴스(값)는 모든 데이터를 제자리에 담고, 참조 타입의 값은 "어딘가"에 있는 데이터를 가리킬 뿐이다.** 이 데이터 위치 추상화가 세 가지 근본 주제에 매우 중요한 결과를 낳는다.

| 축 | 값 타입 | 참조 타입 |
|---|---|---|
| **수명** | 모든 데이터를 담고 있다 — 하나의 자기 완결적 존재로 볼 수 있다. 데이터는 값 타입 인스턴스 자체가 사는 만큼 산다 | 값은 다른 값이 저장된 **위치**이며, 그 수명은 정의 자체로는 정해지지 않는다 |
| **공유** | 기본적으로 공유되지 않는다. 다른 곳에서 쓰려면 기본적으로 **바이트 단위로 복사**된다(값에 의한 전달). 복사본이 전달되므로 원본 값의 수명은 바뀌지 않는다 | 기본적으로 공유된다. 다른 곳에서 쓰면 참조에 의한 전달이 기본이며, 그 뒤로는 참조 타입 인스턴스 하나가 더 같은 값 위치를 가리킨다. 값의 수명을 알려면 모든 참조를 추적해야 한다 |
| **식별성** | 값 타입 인스턴스에는 **식별성이 없다.** 기본적으로 데이터의 비트열이 같으면 동일하다 | 인스턴스의 **위치가 같을 때만** 동일하다 |

이 정의 어디에도 힙이나 스택에 대한 언급이 **단 한 번도 없다.** 다음에 면접에서 값 타입이 어디에 저장되느냐는 질문을 받으면 이 확장된 정의에서 출발해도 좋다.

> **📌 불변 타입은 세 번째 카테고리다**
>
> 알아 둬야 할 타입 카테고리가 하나 더 있다 — **불변 타입(immutable type)**. 생성 후 값을 바꿀 수 없는 타입이다. 그 이상도 이하도 아니다. **값 의미론이나 참조 의미론에 대해서는 아무것도 말하지 않는다.** 값 타입과 참조 타입 모두 불변일 수 있다.
>
> 객체 지향에서 불변성은 객체의 값을 바꾸는 메서드와 프로퍼티를 노출하지 않는 것만으로 강제할 수 있다. .NET이 제공하는 가장 흔히 쓰이는 불변 타입이 `System.String`이다(54.7절).

### 값 타입은 정말 어디에 저장되는가

"값 타입이 스택에 저장된다"는 이야기의 진짜 답은 **위치별로 따져야** 나온다. 구현상 모든 값 타입을 힙에 저장하는 것을 막는 것은 아무것도 없다. 다만 더 나은 해법이 있을 뿐이다 — 스택이나 CPU 레지스터를 쓰는 것. 무엇을 쓸지 결정하는 것은 **수명과 값 공유**다.

| 값 타입 인스턴스의 위치 | 수명 | 쓸 수 있는 저장소 |
|---|---|---|
| **메서드의 지역 변수** | 메서드 호출(과 모든 하위 호출)의 수명. 매우 엄격하고 잘 정의되어 있다 | 값의 인스턴스가 하나뿐이고 공유되지 않으므로 **스택**이 합리적이다. 메서드가 끝난 뒤나 다른 스레드에서 이 값을 쓸 위험이 없다 |
| **메서드의 인수** | 지역 변수와 동일하게 취급 가능 | **스택** |
| **인스턴스 필드**(참조 타입 또는 값 타입 안) | 담고 있는 타입 인스턴스의 수명에 의존 | **담고 있는 인스턴스와 같은 위치.** 클래스의 필드라면 힙, 스택 위 구조체의 필드라면 스택 |
| **정적 필드**(클래스·인터페이스·모듈 안) | 정의된 타입의 수명 | 활성화 프레임이 훨씬 짧게 살 수 있으므로 **스택을 쓸 수 없다** (54.5절) |
| **로컬 메모리 풀** | 메서드 수명에 엄격히 연결 (ECMA는 "로컬 메모리 풀은 메서드 종료 시 회수된다"고 한다) | **스택.** 그래서 로컬 메모리 풀은 활성화 프레임의 확장으로 구현된다 (`stackalloc` — 63.7절) |
| **평가 스택 위 임시값** | JIT이 엄격히 통제. 왜 필요하고 언제 더는 안 쓰이는지 완벽히 안다 | **힙·스택·레지스터 전부 자유.** 성능상 CPU 레지스터와 스택을 쓰려 한다 |

정확한 문장은 이렇다. **"값 타입은 지역 변수이거나 로컬 메모리 풀 안에 살 때 스택에 저장된다. 힙 위 다른 객체의 일부이거나 정적 필드일 때는 힙에 저장된다. 그리고 평가 스택 처리의 일부로서 언제든 CPU 레지스터에 저장될 수 있다."** 원래 이야기보다 조금 더 복잡하다. 게다가 이것도 전부는 아니다 — 클로저가 지역 변수를 참조 타입 컨텍스트로 캡처하면 그 변수는 힙으로 승격된다(26.10절).

### 세 가지 배치 대비

```text
① 지역 변수 (스택)                ② 클래스의 필드 (힙 안에 인라인)
┌──────────────────┐            ┌──────────────────────────────┐
│  스택 프레임       │            │  관리 힙                       │
│ ┌──────────────┐ │            │ ┌──────────────────────────┐ │
│ │ SomeStruct sd│ │            │ │ 헤더 (8B)                 │ │
│ │  Value1 (4B) │ │            │ │ MethodTable 참조 (8B)     │ │
│ │  Value2 (4B) │ │            │ ├──────────────────────────┤ │
│ │  Value3 (4B) │ │            │ │ SomeStruct 필드           │ │
│ │  Value4 (4B) │ │            │ │  Value1 Value2 (8B)      │ │  ← 헤더도 MT도
│ └──────────────┘ │            │ │  Value3 Value4 (8B)      │ │    없다. 그냥
│   16바이트        │            │ ├──────────────────────────┤ │    16바이트가
│   메타데이터 없음   │            │ │ 다른 필드…                │ │    박혀 있다
└──────────────────┘            │ └──────────────────────────┘ │
                                └──────────────────────────────┘

③ 박싱된 값 (힙 위의 독립 객체)
┌──────────────────────────────┐
│  관리 힙                       │
│ ┌──────────────────────────┐ │
│ │ 정렬 패딩 (4B)             │ │
│ │ 싱크 블록 인덱스 (4B)       │ │  ← ①②에는 없던 것
│ ├══════════════════════════┤ │
│ │ MethodTable 참조 (8B)     │ │  ← SomeStruct의 박싱 타입 MT
│ ├──────────────────────────┤ │
│ │  Value1 Value2 (8B)      │ │  ← 같은 16바이트지만
│ │  Value3 Value4 (8B)      │ │     32바이트를 점유한다
│ └──────────────────────────┘ │
└──────────────────────────────┘
```

같은 `SomeStruct`가 세 곳에 있을 때의 대비다. ①은 16바이트, ②는 담고 있는 객체 안의 16바이트, ③은 헤더 8 + MT 8 + 데이터 16 = 32바이트다. **박싱되는 순간 구조체의 이점이 사라진다.** 구조체의 진짜 힘은 박싱되지 않은 버전에서 나온다.

### 구조체와 클래스의 IL 대비

같은 형태의 코드를 구조체와 클래스로 각각 써 보자.

```csharp
public struct SomeStruct { public int Value1, Value2, Value3, Value4; }
public class  SomeClass  { public int Value1, Value2, Value3, Value4; }

public class ExampleClass
{
    public int MainStruct(int data)
    {
        SomeStruct sd = new SomeStruct();
        sd.Value1 = data;
        return Helper(sd);
    }
    private int Helper(SomeStruct arg) => arg.Value1;
}
```

구조체 버전의 IL은 이렇다.

```il
.method public hidebysig instance int32 MainStruct (int32 data) cil managed
{
      .maxstack 2
      .locals init ([0] valuetype SomeStruct)

      ldloca.s 0                    // 지역 변수 0의 주소를 평가 스택에
      initobj  SomeStruct           // 그 주소를 SomeStruct로 초기화 (모든 필드 0)
      ldloca.s 0                    // 다시 주소를 푸시
      ldarg.1                       // 두 번째 인수(int data)를 푸시
      stfld    int32 SomeStruct::Value1
      ldarg.0                       // this
      ldloc.0                       // 지역 변수의 "값" — 16바이트 전체가 복사된다
      call     instance int32 ExampleClass::Helper(valuetype SomeStruct)
      ret
}
```

클래스 버전은 첫 줄이 다르다. `ldloca.s 0` + `initobj` 대신 **`newobj instance void SomeClass::.ctor()`** 로 시작하고, `ldloc.0`이 16바이트가 아니라 참조(주소) 하나만 평가 스택에 올린다.

**결정적 차이는 `newobj`다.** 구조체 버전에는 힙 할당이 전혀 없다. 지역 변수, 메서드 인수, 평가 스택 세 가지 위치만 쓴다.

여기서 멈춰도 되지만, JIT이 이 추상 스택 머신 코드를 실제 기계어로 어떻게 바꾸는지 보는 것이 훨씬 흥미롭다. RyuJIT x64 릴리스 빌드 결과는 압도적으로 긍정적이다.

```text
Samples.ExampleClass.MainStruct(Int32)
mov eax, edx
ret
```

**두 줄이다.** JIT은 평가 스택 처리 전체를 최적화했고, `mov` 명령 하나면 충분하다는 것을 알아챘다. `edx`(Microsoft x64 호출 규약상 두 번째 인수 `data`가 담긴 레지스터)를 반환값 레지스터 `eax`로 옮기고 반환한다. **`Helper` 호출도 없고(인라이닝되었다), 구조체 데이터 복사도 없고, 사실상 구조체가 아예 없다.**

클래스 버전은 이렇다.

```text
Samples.ExampleClass.MainClass(Int32)
push rsi
sub  rsp, 0x20
mov  esi, edx
mov  rcx, 0x7ffa5192f838                     ; MT: SomeClass
call clr.dll!JIT_TrialAllocSFastMP_InlineGetThread   ; 할당자 호출
mov  [rax+0x8], esi
mov  eax, [rax+0x8]
add  rsp, 0x20
pop  rsi
ret
```

잘 최적화된 코드지만, 구조체 버전의 두 줄에 비하면 훨씬 복잡하다. 성능 차이는 다음과 같다.

| 메서드 | 평균 | Gen 0 | 할당 |
|---|---|---|---|
| `ConsumeStruct` | 0.0327 ns | – | 0 B |
| `ConsumeClass` | 4.3562 ns | 0.0038 | 32 B |

*BenchmarkDotNet, .NET 8 기준.* 객체 할당 때문에 클래스 버전이 **네 배 이상 느리고**, 당연히 메모리를 할당한다. 구조체 버전은 할당이 0이다.

> **⚠️ 이 최적화는 릴리스 빌드에서만 일어난다**
>
> 위의 두 줄짜리 결과는 **릴리스 모드로 컴파일할 때** 나온다. 그때만 모든 최적화가 켜지기 때문이다. 같은 코드를 디버그 모드로 컴파일하면 `MainStruct`는 **32줄의 어셈블리**로 JIT되고 거기에 `SomeStruct`의 스택 복사가 들어간다. `Helper`도 인라이닝되지 않아 **18줄**이 더 붙는다. 릴리스에서 2줄이던 것이 디버그에서 50줄이 된다.
>
> "디버그 빌드로 성능을 측정하지 마라"는 조언의 근거가 이것이다. 측정하는 대상이 아예 다른 코드다.

> **⚠️ 구조체 크기가 임계를 넘으면 최적화가 멈춘다**
>
> **런타임은 구조체의 크기에 따라 다르게 취급하고 최적화한다.** 위의 `SomeStruct`에 `int` 필드를 **하나만 더** 추가하면 JIT은 `MainStruct`를 더 이상 최적화하지 않는다 — 스택 할당과 메모리 복사가 실제로 일어난다. 이 임계값은 크기와 필드 개수 같은 요인에 의존하는 깊은 구현 세부다. **확실히 하고 싶다면 구조체를 참조로 전달하라**(`in`, `ref`). 그리고 "구조체로 바꿨으니 빨라졌겠지"라고 가정하지 말고 측정하라(67장).
>
> 참고로 복사가 일어나더라도 그 복사는 최대한 최적화된다. 데이터는 AVX 명령인 `vmovdqu`로 옮겨진다.

### 참조 타입도 스택에 갈 수 있다 — 이스케이프 분석

참조 타입의 힙 할당에는 예외가 하나 있다. 참조 타입 인스턴스가 지역 값 타입 변수와 **같은 특성**을 가진다면, 값 타입처럼 스택에 할당될 수 있다. 구체적으로는 런타임이 그 참조가 지역 스코프를 **벗어나지 않고 다른 스레드와 공유되지 않음**을 증명할 수 있어야 한다. 이것을 확인하는 기법이 **이스케이프 분석(Escape Analysis)** 이다.

.NET 8 시점에서 런타임은 이스케이프 분석을 **부분적으로만 지원**하며 ※.NET 8(런타임 팀은 이것을 "object stack allocation"이라 부른다) **기본적으로 비활성화되어 있다.** `DOTNET_JitObjectStackAllocation` 환경 변수를 1로 설정하면 동작을 볼 수 있다.

```csharp
public int UseVectors()
{
   var p1 = new Vector(1, 2);      // Vector는 여기서 커스텀 클래스
   var p2 = new Vector(3, 4);
   var result = Add(p1, p2);
   return result.X + result.Y;
}
```

이스케이프 분석이 꺼진 기본 상태에서는 `JIT_TrialAllocSFastMP_InlineGetThread`를 두 번 호출해 `p1`과 `p2`를 할당하고 각각의 필드를 `[rdi+8]`, `[rbx+8]` 식으로 초기화하는 평범한 코드가 나온다. `DOTNET_JitObjectStackAllocation`을 1로 설정하면 훨씬 흥미로운 코드가 나온다.

```text
mov     rax,7FFBF83B2B28h (MT: Vector)
mov     qword ptr [rsp+28h],rax     ; 스택 프레임에 MT 포인터를 직접 쓴다
mov     dword ptr [rsp+30h],1
mov     dword ptr [rsp+34h],2
lea     rdx,[rsp+28h]
mov     qword ptr [rsp+18h],rax
mov     dword ptr [rsp+20h],3
mov     dword ptr [rsp+24h],4
```

두 객체가 메서드의 스택 프레임 안에(`rsp` 레지스터를 기준으로) "만들어진다". 그런데 **메모리 레이아웃은 힙에 할당된 경우와 정확히 같다 — 맨 앞의 메서드 테이블 포인터를 포함해서.** 이 장에서 본 객체 레이아웃 규칙은 저장 위치와 무관하게 유지된다.

현재 구현에는 객체의 스택 할당을 막는 여러 제약이 있다.

- 할당이 배열인 경우
- 할당이 문자열인 경우
- 할당이 박싱된 구조체인 경우
- 클래스 크기가 8KB보다 큰 경우
- ReadyToRun 아래에서, 클래스나 그 기저 클래스 중 하나가 다른 "버저닝 버블"에 있는 경우
- 객체가 루프 안에서 할당되는 경우

또한 JIT에는 프로시저 간(interprocedural) 이스케이프 분석이 없으므로, 객체의 메서드를 호출하거나 인수로 전달하는 것만으로도 대개 스택 할당이 막힌다 — JIT이 그 메서드를 인라이닝하기로 결정하지 않는 한.

> **⚠️ 이스케이프 분석에 기대를 걸지 마라** ※.NET 8
>
> 원저자들의 테스트에서는 메모리를 집약적으로 처리하는 프로그램에서조차 할당 수에 유의미한 차이가 없었다. 제약 조건이 워낙 많기 때문이다. 게다가 이런 "스택 할당"을 측정할 CLR 이벤트나 진단 도구가 현재로서는 없다 — 디버거를 붙여 이스케이프 분석 켜고 끈 JIT 코드를 비교하는 것이 유일한 관찰 방법이다. 물론 자기 애플리케이션에서 시험해 볼 가치는 있다. 이 기능의 진행 상황은 dotnet/runtime 이슈 #11192에서 추적할 수 있고, JIT 최적화 전반은 55.6절에서 다룬다.

### `null`이란 무엇인가

참조에 대해 이야기했으니 `null`도 정리하자. 일반적으로 `null`은 **정상 코드에서 절대 나타나지 않아야 하는 주소**의 표현이며, 유효한 포인터(및 .NET의 참조)와 구별하기 위해 존재한다. 널리 쓰이는 모든 프로그래밍 환경에서 이것은 **주소 0** — 초기화되지 않은 값에 대응한다. OS의 **첫 메모리 페이지는 항상 비어(사용되지 않게) 유지**되어 이 주소를 무효로 만들고 프로그래밍 오류를 잡는 데 도움을 준다.

무효한 페이지에 접근하면 OS가 예외를 일으키고 CLR이 그것을 처리한다. 차이는 이렇다.

- **첫 페이지(보통 첫 4KB)** 에 접근했다면 그 예외는 우리가 잘 아는 `NullReferenceException`으로 바뀐다.
- **그보다 높은 주소**에 접근했다면 `AccessViolationException`이 던져진다.

```csharp
// 첫 페이지 접근 → NullReferenceException
unsafe { int read = *((int*)IntPtr.Zero); }

// 첫 4KB 밖 접근 → AccessViolationException
unsafe { int read = *((int*)0x1_0000); }
```

일반 C# 코드의 `NullReferenceException`도 정확히 같은 방식으로 처리된다. 객체의 필드에 접근한다는 것은 주어진 주소를 작은 필드 오프셋과 함께 역참조하는 것이기 때문이다.

```csharp
public static void Test(SomeClass obj) => Console.WriteLine(obj.Field);
```

```text
C.Test(SomeClass)
  L0000: sub rsp, 0x28
  L0004: mov ecx, [rcx+0x8]      ; obj가 null이면 주소 0x8에 접근하게 된다
  L0007: call System.Console.WriteLine(Int32)
  L000c: nop
  L000d: add rsp, 0x28
  L0011: ret
```

`rcx`로 전달된 참조가 0이면 필드 주소는 `0x8`로 계산된다(`Field`가 첫 필드라고 가정). `0x8`에 접근하는 것도 첫 페이지 안이므로 여전히 `NullReferenceException`이 된다. **54.2절에서 "null 검사가 공짜"라고 한 것이 이 이야기다.** 별도의 비교 명령 없이 하드웨어 페이지 폴트가 null 검사를 대신한다.

> **⚠️ 그러면 객체가 첫 페이지보다 크면 어떻게 되는가**
>
> 객체가 4KB보다 크고 그 끝쪽 필드에 null 참조로 접근하면 헷갈리게도 `AccessViolationException`이 나오지 않을까? **답은 아니오다.** 이런 시나리오는 JIT이 적절한 코드를 생성해 방어한다.
>
> 예를 들어 배열을 전달하면 어차피 경계 검사 코드가 삽입되므로(배열의 크기 필드에 접근한다) 주어진 요소에 접근하기도 전에 `NullReferenceException`이 된다. 필드가 수천 개인 거대한 객체라면, JIT은 특정 필드에 접근하기 전에 **객체 전체에 대한 null 검사를 추가한다.**
>
> ```text
> C.Test(SomeClass)
>   L0000: sub rsp, 0x28
>   L0004: cmp [rcx], ecx            ; ★ 높은 오프셋 필드에 접근할 때만 생성된다
>   L0006: mov rcx, [rcx+0xfa08]
>   L000d: call System.Console.WriteLine(Int64)
>   L0012: nop
>   L0013: add rsp, 0x28
>   L0017: ret
> ```
>
> 두 번째 명령 `cmp [rcx], ecx`가 그것이다. `rcx`가 0이면 이 명령이 `NullReferenceException`을 유발한다. 이 명령은 `SomeClass` 인스턴스의 **높은 오프셋 필드에 접근할 때만** 생성된다.
>
> 참고로 `AccessViolationException`은 `try`/`catch(Exception)`으로 잡히지 않는다(기본 설정에서). 프로세스가 손상되었을 가능성이 있다고 보기 때문이다. 이 예외를 봤다면 십중팔구 상호운용 코드의 버그다(60장).

### 참조로 전달하기

값 타입과 참조 타입에 딸린 값 전달·참조 전달 의미론 위에, **또 한 층의 제어**가 있다. 값 타입 인스턴스든 참조 타입 인스턴스든 상관없이 어떤 값이든 참조로 전달할 수 있다.

```csharp
public int Main(int data)
{
    SomeStruct ss = new SomeStruct();
    ss.Value1 = 10;
    Helper(ss);           // 값으로 전달 → 지역 복사본이 만들어진다. 10을 반환
    HelperRef(ref ss);    // 참조로 전달 → 스택 위 원본을 가리킨다. 11을 반환
    return ss.Value1;
}
private void Helper(SomeStruct data)        => data.Value1 = 11;   // 복사본만 바뀐다
private void HelperRef(ref SomeStruct data) => data.Value1 = 11;   // 원본이 바뀐다
```

구조체를 지역 변수로 쓰면서 참조로 전달하는 것은 훌륭한 최적화 기법이다. **힙 할당이 일어나지 않을 뿐 아니라, 구조체 크기와 무관하게 데이터 복사 오버헤드도 사라진다.**

참조 타입 인스턴스를 참조로 전달할 수도 있다. C/C++에 익숙하다면 포인터에 대한 포인터 같은 것이다.

```csharp
private void Helper(ref SomeClass data)
{
    data = new SomeClass();   // 참조 자체를 다른 인스턴스로 바꾼다 — 호출자에게 보인다
    data.Value1 = 11;
}
```

`Helper` 안에서 평소처럼 접근할 수 있지만(추가 포인터 역참조가 필요하므로 보통 참조보다 약간 느리다), 참조에 대한 참조를 가졌으므로 **그것을 수정해 다른 인스턴스를 가리키게 만들 수 있다.** `ref`가 없었다면 `data` 매개변수는 새 인스턴스의 참조를 담는 지역 변수처럼 동작했을 것이고 그 변경은 메서드 밖에서 보이지 않았을 것이다.

> **💡 참조로 전달해도 JIT은 여전히 최적화한다**
>
> 위의 `ref SomeStruct` 예제를 릴리스로 빌드하면, JIT은 스택에 구조체가 필요 없고 `Value1`에 11(0xb)을 넣으면 된다는 것을 알아챈다. `Main` 메서드는 `mov eax, 0xb`와 `ret`로 JIT된다.
>
> 참조로 전달하기는 .NET과 C# 창작자들의 관심을 계속 끄는 주제다. C# 7.0에서 지역 참조 변수와 참조 반환이 추가되었고 그 뒤로도 많은 기능이 붙었다. Roslyn 컴파일러나 Kestrel 서버처럼 최고 성능을 기대하는 솔루션이 정확히 이 방향으로 최적화된다. `in`/`ref`/`out`과 `ref` 필드의 내부 표현은 68장에서 자세히 다룬다.

## 54.9 타입 데이터 지역성 — 같은 데이터, 다른 성능

### 메타데이터가 없다는 것의 의미

메타데이터 오버헤드가 없으므로 구조체는 매우 조밀하다. 이것이 중요한 이유는 둘이다. **처리할 데이터가 적은 것은 언제나 좋고**, **CPU 캐시를 최대한 활용하는 것도 언제나 좋다.** 객체가 작아서 하나의 캐시 라인에 더 많이 들어가면 상당한 성능 향상을 얻는다(61.4절, 61.5절).

구조체로 만든 자료구조는 참조 타입보다 조밀한 메모리 활용을 제공한다. **더 중요한 것은, 구조체 배열은 데이터 자체로 채워진 연속된 메모리 영역을 이룬다**는 점이다. 참조 타입의 경우 순차적으로 배치되는 것은 **참조들뿐**이고, 그것들이 가리키는 값은 관리 힙 전체에 흩어져 있을 수 있으며 그 배치를 통제할 방법이 없다.

```text
── 구조체 배열: SmallStruct[] (SmallStruct = int Value1, int Value2) ──

  ┌──────┬──────┬──────┬──────┬──────┬──────┬──────┬──────┬──────┐
  │헤더/MT│ 길이  │[0]V1 │[0]V2 │[1]V1 │[1]V2 │[2]V1 │[2]V2 │ ...  │
  └──────┴──────┴──────┴──────┴──────┴──────┴──────┴──────┴──────┘
   └──────────── 하나의 연속된 메모리 영역 ───────────────────────┘
   캐시 라인 64바이트 하나에 요소 8개가 통째로 들어온다


── 클래스 배열: SmallClass[] ──

  ┌──────┬──────┬──────┬──────┬──────┬──────┐
  │헤더/MT│ 길이  │ [0]● │ [1]● │ [2]● │ ...  │   ← 참조만 연속이다
  └──────┴──────┴──┬───┴──┬───┴──┬───┴──────┘
                   │      │      └──────────────┐
        ┌──────────┘      └────────┐            │
        ▼                          ▼            ▼
  관리 힙 어딘가            또 다른 어딘가      또 다른 어딘가
 ┌───────────────┐        ┌───────────────┐  ┌───────────────┐
 │헤더│MT│V1│V2 │        │헤더│MT│V1│V2 │  │헤더│MT│V1│V2 │
 └───────────────┘        └───────────────┘  └───────────────┘
  객체당 24바이트, 위치는 GC가 정한다 — 인접을 보장하지 않는다
```

### 벤치마크

두 접근의 성능 차이를 다음 프로그램으로 확인한다. 배열의 모든 요소에서 첫 필드를 더하는 것이 전부다.

```csharp
public struct SmallStruct { public int Value1; public int Value2; }
public class  SmallClass  { public int Value1; public int Value2; }

// 두 배열 모두 백만 개의 요소로 초기화되어 있다
private SmallClass[]  classes;
private SmallStruct[] structs;

[Benchmark]
public int StructArrayAccess()
{
    int result = 0;
    for (int i = 0; i < items; i++)
        result += Helper1(structs, i);
    return result;
}

[Benchmark]
public int ClassArrayAccess()
{
    int result = 0;
    for (int i = 0; i < items; i++)
        result += Helper2(classes, i);
    return result;
}

public int Helper1(SmallStruct[] data, int index) => data[index].Value1;
public int Helper2(SmallClass[]  data, int index) => data[index].Value1;
```

두 접근의 유일한 차이는 각 헬퍼 메서드에 대해 생성되는 JIT 코드에 있다. 54.7절에서 이미 본 그 코드다.

```text
Helper1(Samples.SmallStruct[], Int32)
lea     rax,[rax+rcx*8+10h]      ; 인덱스 × 구조체 크기로 주소 계산
mov     eax,dword ptr [rax]      ; 그 주소의 값을 결과 레지스터로

Helper2(Samples.SmallClass[], Int32)
lea     rax,[rax+rcx*8+10h]      ; 인덱스 × 참조 크기로 주소 계산
mov     rax,qword ptr [rax]      ; ① 그 인덱스의 객체 참조를 얻는다
mov     eax,dword ptr [rax+8]    ; ② 그 참조가 가리키는 값을 얻는다
```

구조체 배열 접근은 **역참조 한 번**으로 끝난다. 클래스 배열 접근은 **두 번** 해야 한다.

| 메서드 | 평균 | 할당 |
|---|---|---|
| `StructArrayAccess` | 491.2 µs | 0 B |
| `ClassArrayAccess` | 2,247.6 µs | 0 B |

*BenchmarkDotNet, .NET 8.0 기준.* **4.6배 차이다.** 역참조 하나가 추가된 것만으로는 이 차이를 설명할 수 없다. 추가 오버헤드는 **훨씬 나쁜 데이터 지역성**에서 온다. 클래스 인스턴스들이 서로 옆에 놓인다는 보장이 없으므로, 같은 계산을 하는 데 훨씬 많은 캐시 라인을 로드해야 한다.

64바이트 캐시 라인 기준으로 숫자를 보자.

| | 구조체 배열 | 클래스 배열 |
|---|---|---|
| 요소 하나의 크기 | 8 B | 참조 8 B + 객체 24 B |
| 캐시 라인 하나가 담는 요소 | **8개** | 참조 8개 (객체는 별도) |
| 백만 요소 순회 시 캐시 라인 | 약 **125,000개** | 참조용 125,000개 **+ 객체용 최대 1,000,000개** |
| 할당된 힙 | 8 MB + 헤더 | 8 MB(참조) + 24 MB(객체) |

두 배열 모두 벤치마크 실행 자체는 할당이 0이다. 차이는 순전히 **메모리를 읽는 방식**에서 온다.

> **💡 이 차이가 나타나는 조건을 정확히 알아 두라**
>
> 4.6배는 인상적이지만 다음 조건이 모두 맞을 때의 숫자다. **요소 개수가 많고**(캐시에 다 들어가면 차이가 사라진다), **순차 접근이고**(무작위 접근이면 구조체 배열도 캐시 미스를 낸다), **요소가 작고**(요소 하나가 캐시 라인보다 크면 지역성 이득이 줄어든다), **필드 일부만 읽을 때**(전체를 읽는다면 어차피 모든 바이트를 로드한다)다.
>
> 반대로 요소가 크고 값 복사가 자주 일어난다면 구조체 배열이 오히려 느릴 수 있다. AoS(구조체 배열)에서 SoA(배열 구조체)로 가는 다음 단계는 70.3절에서 다룬다.

> **📌 CLR도 같은 최적화를 한다**
>
> 54.4절에서 자동 레이아웃이 객체 참조를 첫 필드들로 놓는다고 했다. 이유가 정확히 이 절의 주제다. GC의 Mark 단계는 객체를 방문할 때 `MethodTable` 포인터를 먼저 읽고, 그다음 참조 필드들을 따라간다. 참조가 앞쪽에 모여 있으면 **대부분의 참조가 이미 로드한 `MethodTable` 필드와 같은 캐시 라인에 들어온다.** 캐시 미스 하나가 줄어든다.
>
> 런타임이 이 정도로 캐시 라인을 신경 쓴다는 사실 자체가, 애플리케이션 코드에서도 같은 사고가 값어치를 한다는 증거다. 이 사고방식을 체계화한 것이 데이터 지향 설계이며 70장의 주제다.

## 54.10 실습: WinDbg로 객체 크기와 레이아웃 직접 확인하기

### 준비

지금까지 그린 레이아웃을 살아 있는 프로세스에서 직접 확인해 보자. 다음 프로그램을 릴리스로 빌드하고 `Console.ReadLine()`에서 멈춰 있는 동안 WinDbg를 붙인다.

```csharp
public class Node { public int Id; public string Name; public Node Next; }
public struct AlignedDouble { public byte B; public double D; public int I; }

public static class Program
{
    public static Node          Head;
    public static AlignedDouble Value;

    public static void Main()
    {
        Head = new Node { Id = 1, Name = "first",
                          Next = new Node { Id = 2, Name = "second" } };
        Value = new AlignedDouble { B = 1, D = 2.5, I = 3 };

        Console.WriteLine("붙일 준비 완료. 엔터를 누르면 종료한다.");
        Console.ReadLine();
        GC.KeepAlive(Head);
    }
}
```

WinDbg는 네이티브 디버거이므로 .NET 구조를 이해하지 못한다. 그 간극을 메우는 확장이 **SOS**(Son of the Strike)다. 최신 WinDbg는 올바른 버전을 자동으로 로드해 준다. 더 새로운 버전을 쓰려면 수동으로 설치한다.

```text
dotnet tool install dotnet-sos -g
dotnet sos install
```

이 명령이 `sos.dll`이 저장될 위치와 WinDbg에서 입력할 명령을 알려준다.

```text
Execute '.load C:\Users\<your user>\.dotnet\sos\sos.dll' to load SOS in your Windows debugger.
```

`.chain` 명령으로 어떤 버전이 로드되어 있는지 확인할 수 있고, 필요하면 `.unload`로 자동 로드된 것을 내린 뒤 위 경로를 `.load` 한다.

> **⚠️ 비트수를 맞춰라**
>
> 32비트 애플리케이션의 덤프에는 x86 확장을, 64비트에는 x64 확장을 로드해야 한다. 어긋나면 `.load`가 다음 오류를 낸다.
>
> ```text
> The call to LoadLibrary(...\x86\netext.dll) failed, Win32 error 0n193
>     "%1 is not a valid Win32 application."
> ```
>
> 구형 SDK/DDK 버전 WinDbg에서는 .NET Framework 덤프에 `.loadby sos clr`, 초기 CoreCLR에는 `.loadby sos coreclr`를 써야 했다. 이 명령들은 `clr.dll`이나 `coreclr.dll`과 같은 폴더에서 `sos.dll`을 찾으라는 뜻이다. **최신 WinDbg에서는 이 암호 같은 명령이 필요 없다.**

### `!dumpheap` — 어떤 객체가 있는가

먼저 힙에 무엇이 있는지 통계로 본다.

```text
> !dumpheap -stat
              MT    Count    TotalSize Class Name
...
00007ffc93a35c98        2           80 Node
00007ffc93a12340       15          642 System.String
Total 1043 objects
```

특정 타입의 인스턴스 주소를 얻으려면 `-type`이나 `-mt`를 쓴다.

```text
> !dumpheap -type Node
         Address               MT     Size
000001751f8a2d18 00007ffc93a35c98       40
000001751f8a2d38 00007ffc93a35c98       40

Statistics:
              MT    Count    TotalSize Class Name
00007ffc93a35c98        2           80 Node
Total 2 objects
```

`Size` 열이 **40**이다. 54.3절의 계산과 맞춰 보자. 헤더 8 + `MethodTable` 참조 8 = 16. 필드는 `string Name`(8) + `Node Next`(8) + `int Id`(4) = 20. 16 + 20 = 36이고 8바이트 정렬로 올림하면 **40**이다. 실제 배치는 다음 명령이 보여준다.

### `!dumpobj` — 객체 하나의 필드 배치

```text
> !DumpObj 000001751f8a2d18
Name:        Node
MethodTable: 00007ffc93a35c98
EEClass:     00007ffc93b41208
Size:        40(0x28) bytes
File:        C:\...\LayoutDemo.dll
Fields:
              MT    Field   Offset                 Type VT     Attr            Value Name
00007ffcfd6a3f80  4000001        8        System.String  0 instance 000001751f8a2d58 Name
00007ffc93a35c98  4000002       10                 Node  0 instance 000001751f8a2d38 Next
00007ffcfd6c66d8  4000003       18         System.Int32  1 instance                1 Id
```

이제 모든 것이 맞는다.

- **`Offset` 열이 우리가 그린 다이어그램 그대로다.** `8`, `10`(=16), `18`(=24) — 16진수다. 첫 필드가 오프셋 8에서 시작한다(64비트에서 `MethodTable` 참조 뒤).
- **`Name`과 `Next`가 `Id`보다 앞에 있다.** 소스 코드 순서는 `Id`, `Name`, `Next`였다. 자동 레이아웃이 **참조 필드를 앞으로 재배치**했다. 54.4절의 그 최적화다.
- **`Size: 40(0x28)`.** 헤더 8 + MT 8 + `Name` 8 + `Next` 8 + `Id` 4 = 36을 8바이트 정렬로 올린 값이다. `Id` 뒤 오프셋 `0x1c`부터 4바이트가 끝 패딩이다. SOS가 보고하는 `Size`에는 **객체 헤더가 포함된다.**
- **`VT` 열**이 1이면 값 타입 필드, 0이면 참조 필드다. `Value` 열은 참조 필드에서는 가리키는 객체의 주소, 값 타입 필드에서는 값 자체다.

`Name` 필드가 가리키는 주소를 그대로 덤프하면 문자열이 나온다.

```text
> !DumpObj 000001751f8a2d58
Name:        System.String
MethodTable: 00007ffcfd6a3f80
EEClass:     00007ffcfd5e4f2c
Size:        32(0x20) bytes
File:        C:\...\System.Private.CoreLib.dll
String:      first
Fields:
              MT    Field   Offset                 Type VT     Attr            Value Name
00007ffcfd6c66d8  4000273        8         System.Int32  1 instance                5 _stringLength
00007ffcfd6b8e28  4000274        c          System.Char  1 instance               66 _firstChar
```

54.7절의 문자열 레이아웃이 그대로 보인다. `_stringLength`가 오프셋 8, `_firstChar`가 오프셋 `0xc`(12). 5글자짜리 `"first"`는 (22 + 2×5) = 32를 8의 배수로 올려 **32바이트**다. 계산이 맞는다.

### `!dumpmt` — `MethodTable` 자체 보기

객체의 `MethodTable` 주소를 알았으니 그것을 덤프한다.

```text
> !dumpmt -md 00007ffc93a35c98
EEClass:         00007FFC93B41208
Module:          00007FFC93A31000
Name:            Node
mdToken:         0000000002000004
File:            C:\...\LayoutDemo.dll
BaseSize:        0x28
ComponentSize:   0x0
Slots in VTable: 5
Number of IFaces in IFaceMap: 0
--------------------------------------
MethodDesc Table
           Entry       MethodDesc    JIT Name
00007FFC93A50010 00007FFC93A3F5A0   NONE System.Object.ToString()
00007FFC93A50018 00007FFC93A3F5B0   NONE System.Object.Equals(System.Object)
00007FFC93A50020 00007FFC93A3F5C0   NONE System.Object.GetHashCode()
00007FFC93A50028 00007FFC93A3F5D0   NONE System.Object.Finalize()
00007FFC93A50030 00007FFC93A35C70    JIT Node..ctor()
```

(주소는 실행할 때마다 달라진다.)

54.1절에서 본 항목들이 그대로 나온다.

- **`EEClass:`** — 차가운 데이터에 대한 참조
- **`BaseSize: 0x28`** — 40. `!dumpobj`가 보여준 `Size`와 같다. 54.3절에서 말한 대로 `BaseSize`에는 객체 헤더 몫이 포함된다
- **`ComponentSize: 0x0`** — 가변 길이 타입이 아니다. 문자열이나 배열의 `MethodTable`을 덤프하면 여기가 2 또는 요소 크기가 나온다
- **`Slots in VTable: 5`** — 슬롯 테이블 항목 개수이며, 아래 `MethodDesc Table`의 행 수와 같다. `Object`에서 물려받은 가상 메서드 네 개에 `Node`의 생성자가 더해진 값이다. `Node`는 아무것도 재정의하지 않았다
- **`Number of IFaces in IFaceMap: 0`** — 인터페이스를 구현하지 않았다
- **`MethodDesc Table`** — 슬롯 테이블의 내용. `JIT` 열이 `JIT`이면 이미 JIT 컴파일되었고, `NONE`이면 아직 안 되었다는 뜻이다(55.1절)

### `!objsize` — 이 객체가 붙잡고 있는 전부

`!dumpobj`의 `Size`는 **그 객체 하나**의 크기다. 실무에서 알고 싶은 것은 대개 "이 객체가 살아 있게 만드는 전체 그래프가 몇 바이트인가"다. 그것이 `!objsize`다.

```text
> !objsize 000001751f8a2d18
sizeof(000001751f8a2d18) = 152 (0x98) bytes (Node)
```

`Node` 하나는 40바이트지만, 그것이 `Next`로 다른 `Node`(40)를, 두 노드가 각각 `"first"`(32)와 `"second"`(40)를 붙잡고 있으므로 그래프 전체는 152바이트다. 메모리 누수를 추적할 때 실제로 보는 숫자는 이쪽이다(66.5절).

### `!dumpvc` — 값 타입 인스턴스 보기

값 타입 인스턴스는 객체가 아니므로 `!dumpobj`로 볼 수 없다. `!dumpvc`는 **`MethodTable` 주소와 데이터 주소**를 함께 받는다.

```text
> !dumpvc 00007ffda2725e18 00007ffda2725e18
Name:        LayoutDemo.AlignedDouble
MethodTable: 00007ffda2725e18
EEClass:     00007ffda2872110
Size:        40(0x28) bytes
File:        (...)\LayoutDemo.dll
Fields:
              MT    Field   Offset                 Type VT     Attr            Value Name
00007ffdfd6a8b60  4000001        0          System.Byte  1 instance                0 B
00007ffdfd6b0858  4000002        8        System.Double  1 instance         0.000000 D
00007ffdfd6c66d8  4000003       10         System.Int32  1 instance        -43316160 I
```

54.4절에서 손으로 계산한 오프셋이 그대로 나온다 — `B`가 0, `D`가 8, `I`가 `0x10`(16). 순차 레이아웃이 만든 7바이트 패딩이 오프셋 1~7에 있다는 것을 오프셋 간격에서 읽을 수 있다.

**여기서 `Size: 40`에 속지 마라.** `sizeof(AlignedDouble)`은 54.4절에서 계산한 대로 24다. 이 줄이 보고하는 것은 그 값 타입의 `MethodTable`이 들고 있는 `BaseSize`, 즉 **이 구조체가 박싱되어 힙에 놓였을 때의 크기**다(24 + 헤더 8 + `MethodTable` 참조 8 = 40). `!dumpvc`에서 믿고 쓸 것은 `Offset` 열이고, 박싱되지 않은 크기를 알고 싶으면 `sizeof`나 ObjectLayoutInspector를 써라.

### 명령 요약

| 명령 | 하는 일 | 언제 쓰나 |
|---|---|---|
| `!dumpheap -stat` | 힙의 타입별 개수·총 크기 통계 | 무엇이 메모리를 먹는지 첫 조망 |
| `!dumpheap -type <이름>` | 그 타입 인스턴스의 주소 목록 | 조사할 인스턴스 고르기 |
| `!dumpheap -mt <MT주소>` | 그 `MethodTable`의 인스턴스 목록 | 같은 이름의 타입이 여럿일 때 |
| `!dumpobj <주소>` / `!do` | 객체 하나의 필드·오프셋·값 | 레이아웃과 필드 값 확인 |
| `!dumpmt -md <MT주소>` | `MethodTable`의 내용과 슬롯 테이블 | `BaseSize`, `ComponentSize`, JIT 여부 |
| `!objsize <주소>` | 그 객체가 유지하는 그래프 전체 크기 | 누수 추적 |
| `!dumpvc <MT주소> <데이터주소>` | 값 타입 인스턴스의 레이아웃 | 구조체 필드 오프셋 확인 |

> **💡 WinDbg는 마지막 수단이다**
>
> 레이아웃만 궁금하다면 54.4절의 ObjectLayoutInspector나 SharpLab이 훨씬 빠르고 편하다. WinDbg + SOS를 꺼내야 하는 상황은 셋이다 — 프로덕션 덤프만 있고 코드를 실행할 수 없을 때, 특정 인스턴스의 **실제 값**을 봐야 할 때, 어떤 객체가 다른 객체를 왜 붙잡고 있는지 추적해야 할 때(`!gcroot`).
>
> 진단 도구 전반과 실전 시나리오는 66장에서 다룬다. 이 절의 목적은 "이 장에서 그린 다이어그램이 상상이 아니라 실측 가능한 것"임을 확인하는 데 있다.

## 이 장의 요약

- **모든 타입의 런타임 실체는 `MethodTable`이다.** 기본 인스턴스 크기, 플래그, 부모 타입, 슬롯 테이블, 인터페이스 맵이 여기 있고, 자주 안 쓰이는 정보는 `EEClass`로 분리된다. 이 `MethodTable`의 주소가 곧 `TypeHandle`이다. 다만 그 안의 **필드 이름·순서·오프셋은 문서화된 계약이 아니라 버전에 따라 바뀌는 구현 세부**다.
- **힙 객체는 세 부분이다** — 객체 헤더(싱크 블록 인덱스), `MethodTable` 참조, 그리고 최소 한 개의 포인터 크기 필드 자리. 참조는 **`MethodTable` 참조를 정확히 가리키고**, 그래서 헤더는 "음수 인덱스"에 있다. 필드 접근이 상수 양수 오프셋이 되고, 타입 확인이 오프셋 0이 되며, GC가 `MethodTable` 포인터의 하위 비트를 마크 비트로 훔쳐 쓸 수 있다.
- **최소 객체 크기는 32비트 12바이트, 64비트 24바이트다.** `2 × 포인터 크기 + 헤더 크기`이며, 64비트 헤더 8바이트 중 실제로 쓰이는 것은 4바이트뿐이다. 바이트 하나짜리 클래스도 64비트에서 24바이트를 차지한다.
- **필드 레이아웃은 정렬 규칙이 지배한다.** 구조체 기본은 순차, 클래스와 참조를 담은 구조체는 자동이다. `[StructLayout(LayoutKind.Auto)]` 한 줄로 24바이트가 16바이트가 되기도 한다. `object` 필드 하나나 `DateTime` 필드 하나가 레이아웃 종류를 조용히 바꾼다.
- **정적 필드는 종류에 따라 세 곳에 산다.** 기본형은 High Frequency Heap의 statics blob, 참조 타입과 참조를 담은 구조체는 POH의 핸들 테이블을 거쳐 관리 힙, 참조 없는 구조체는 NonGC 힙에 직접(.NET 7+). 정적 필드는 언제나 GC 루트이고, 제네릭 타입은 인스턴스화마다 자기 정적 필드를 가진다.
- **박싱은 할당 + 복사, 언박싱은 관리 포인터 획득뿐이다.** `unbox`는 복사하지 않고 `unbox.any`(= `unbox` + `ldobj`)가 복사한다. `int` 하나를 박싱하면 64비트에서 24바이트를 쓴다. 언박싱은 정확한 타입으로만 되며, 박싱된 값의 필드를 수정하려는 시도는 거의 항상 임시 복사본만 바꾼다.
- **문자열과 배열은 `MethodTable` 뒤의 자리에 길이를 저장한다.** 크기는 `BaseSize + ComponentSize × 개수`다. 64비트 배열 데이터는 오프셋 `0x10`에서 시작하고, 문자열 크기는 `(22 + 2×길이)`를 8의 배수로 올린 값이다. 인터닝된 문자열은 절대 수집되지 않는다.
- **"값 타입은 스택"은 절반만 맞다.** 지역 변수와 로컬 메모리 풀에서는 스택, 다른 객체의 필드나 정적 필드일 때는 힙, 평가 스택 처리 중에는 레지스터다. 반대로 이스케이프 분석이 켜지면 참조 타입도 스택에 갈 수 있다(.NET 8에서는 기본 비활성).
- **같은 데이터도 배치에 따라 4배 이상 차이가 난다.** 구조체 배열은 연속된 메모리이고 역참조가 한 번이다. 클래스 배열은 참조만 연속이고 역참조가 두 번이며 캐시 미스가 많다.
- **이 장의 모든 다이어그램은 WinDbg + SOS로 실측 가능하다.** `!dumpobj`의 `Offset` 열, `!dumpmt`의 `BaseSize`/`ComponentSize`, `!dumpvc`의 필드 오프셋이 그대로 확인해 준다.

## 연습 문제

1. 필드가 `byte`, `double`, `int` 순서인 구조체를 만들고 `sizeof`로 크기를 출력하라. 그다음 `[StructLayout(LayoutKind.Auto)]`를 붙이고 다시 출력하라. 두 값이 왜 그렇게 나오는지 오프셋을 손으로 계산해 검증하고, ObjectLayoutInspector의 `TypeLayout.PrintLayout<T>()` 출력과 대조하라.

2. 필드가 없는 클래스, `byte` 하나짜리 클래스, `int` 네 개짜리 클래스를 각각 인스턴스화하고 WinDbg + SOS의 `!dumpobj`로 `Size`를 확인하라. 세 값이 54.3절의 표와 일치하는가? 32비트로 빌드해서 다시 실행하면 어떻게 달라지는가?

3. `int` 두 개짜리 구조체 배열과 같은 필드를 가진 클래스 배열을 각각 백만 개 만들고, 첫 필드의 합을 구하는 벤치마크를 BenchmarkDotNet으로 작성하라. 54.9절의 4.6배 차이가 재현되는가? 요소 개수를 1,000개로 줄이면 어떻게 되는가? 그 이유를 캐시 크기로 설명하라.

4. `int i = 5;`를 `Console.WriteLine("{0}, {1}, {2}", i, i, i)`로 출력하는 코드와, 먼저 `object o = i;`로 박싱한 뒤 `o`를 세 번 넘기는 코드를 각각 작성하라. SharpLab이나 `ildasm`으로 IL을 열어 `box` 명령이 몇 개씩 나오는지 세어라. 그다음 BenchmarkDotNet의 `[MemoryDiagnoser]`로 할당량을 측정해 IL에서 센 숫자와 맞는지 확인하라.

5. `string.ReferenceEquals`를 써서 리터럴 두 개, 동적으로 연결한 문자열, `string.Intern`으로 인터닝한 문자열의 참조 동일성을 확인하는 프로그램을 작성하라. 그다음 `string.IsInterned`가 언제 `null`을 반환하는지 실험으로 확인하라.

6. `DOTNET_JitObjectStackAllocation=1` 환경 변수를 설정한 상태와 안 한 상태에서 같은 프로그램의 JIT 코드를 비교하라(`DOTNET_JitDisasm`으로 특정 메서드의 디스어셈블리를 얻을 수 있다 — 55.8절). 54.8절의 제약 목록 중 하나에 해당하도록 코드를 고치면 스택 할당이 사라지는지 확인하라.

7. 참조 타입 정적 필드, 참조 없는 구조체 정적 필드, 기본형 정적 필드를 각각 읽는 세 메서드를 `[MethodImpl(MethodImplOptions.NoInlining)]`을 붙여 작성하고, 생성된 어셈블리를 비교하라. 54.5절이 예측한 대로 역참조 횟수가 각각 2회, 1회, 1회인가? .NET 6 이하를 대상으로 다시 빌드하면 구조체 쪽이 달라지는가?
