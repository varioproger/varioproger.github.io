# 83장. 런타임 소스 읽기

> **이 장의 위치** — Part XVII「마스터로 가는 마지막 단계」의 첫 장이다. 3권 내내 "런타임 소스의 이 메서드에서 시작하면 된다"고 적어두고 넘어간 자리가 스무 곳쯤 있다. 62장의 쓰기 장벽, 63장의 할당 경로, 64장의 `plan_phase`, 65장의 `gcconfig.h`, 68장의 `Span` 내부. 이 장은 그 포인터들을 실제로 따라가는 **방법**을 가르친다. 82장이 "책이 그렇다고 했다"의 마지막 장이었다면, 이 장은 "소스에서 확인했다"로 넘어가는 다리다.
>
> **선수 지식** — 54장(타입 시스템의 런타임 표현), 55장(JIT 컴파일과 코드 생성), 56장(CIL 읽기), 64장(GC 알고리즘 완전 해부), 66장(메모리 문제 진단), 67장(측정 없이 최적화 없다)
>
> **이 장에서 다루지 않는 것** — 런타임을 처음부터 빌드해 기여하는 절차는 이 책의 범위 밖이다(저장소의 `docs/workflow/`가 항상 최신이고 정확하다). 특정 알고리즘의 내용 자체는 62~65장에서 이미 다뤘고, 여기서는 그 알고리즘의 **코드를 찾아가는 길**만 다룬다. IL을 읽는 법은 56장, JIT 디스어셈블리를 읽는 법은 55.8절에 있다.

---

**시작하기 전에 한 가지 경고.** 이 장이 지목하는 파일 이름, 디렉터리 구조, 메서드 이름, 매크로 이름은 **이 글을 쓰는 시점(.NET 8 ~ .NET 9 계열)의 `dotnet/runtime` `main` 브랜치 기준**이다. 런타임은 매우 활발한 저장소다. 파일이 쪼개지고, 함수가 이름을 바꾸고, 디렉터리가 통째로 옮겨간다. 예를 들어 JIT의 임포터는 오랫동안 `importer.cpp` 한 파일이었지만 어느 시점에 여러 파일로 분할되었고, FCall로 구현되던 메서드들이 계속해서 QCall이나 순수 관리 코드로 옮겨가고 있다.

그래서 이 장은 **"이 파일의 이 줄을 보라"고 가르치지 않는다.** 대신 **"이런 것을 찾고 싶을 때 어떤 순서로 무엇을 검색하는가"** 를 가르친다. 파일 이름은 변하지만 **검색 전략은 변하지 않는다.** 본문의 모든 구체적 이름에는 검색으로 재확인하는 방법을 함께 붙였다. 이름이 안 맞으면 이름을 고치지 말고 **검색 방법을 써라.**

## 83.1 `dotnet/runtime` 저장소 구조 훑기

### 왜 소스를 읽는가 — 그리고 언제 읽지 말아야 하는가

소스를 읽어야 하는 이유는 명확하다.

| 상황 | 문서로 해결되는가 | 소스가 답하는가 |
|---|---|---|
| "이 API가 무엇을 하는가" | **된다.** 공식 문서를 봐라 | 볼 필요 없다 |
| "이 API가 할당을 하는가" | 대개 안 된다 | **된다** |
| "왜 이 경계값이 85,000인가" | 안 된다 | **된다** |
| "이 예외가 정확히 어떤 조건에서 나는가" | 대개 안 된다 | **된다** |
| "이 최적화가 내 코드에 적용되는가" | 안 된다 | 부분적으로. 실험이 함께 필요하다 |
| "이 동작에 의존해도 되는가" | **된다.** 문서가 계약이다 | **답하지 못한다.** 소스는 계약이 아니다 |

마지막 줄이 이 장 전체에서 가장 중요하다. 소스는 **현재 구현**을 알려줄 뿐 **미래의 약속**을 알려주지 않는다. 소스에서 "이렇게 되어 있으니 이렇게 동작한다"를 알아냈다면, 그것은 **오늘의 성능 특성을 이해**하는 데 써야지 **내일도 유지될 정확성 가정**으로 써서는 안 된다.

> **⚠️ 소스에서 읽은 것을 계약으로 착각하는 순간 사고가 난다**
>
> 대표적인 사고 패턴 세 가지다.
>
> 1. `string.Format`이 내부적으로 `StringBuilder`를 캐시한다는 것을 소스에서 확인하고, 그 캐시 크기에 맞춰 애플리케이션 로직을 튜닝한다. 다음 릴리스에서 구현이 `DefaultInterpolatedStringHandler`로 바뀌면 튜닝이 무의미해진다(운이 좋으면).
> 2. `Dictionary<K,V>`의 열거 순서가 삽입 순서와 대체로 일치하는 것을 소스에서 확인하고 그 순서에 의존한다. **문서는 순서를 보장하지 않는다.** 리사이즈 한 번이면 깨진다.
> 3. `internal` 필드를 리플렉션으로 읽어 최적화한다. 다음 버전에서 필드 이름이 바뀌면 `NullReferenceException`이 아니라 잘못된 값으로 조용히 동작한다.
>
> 소스는 **"왜"를 이해하는 도구**다. **"무엇에 의존할 것인가"는 문서로 결정한다.**

읽지 말아야 할 때도 있다. **측정하지 않은 상태에서 소스를 읽는 것은 시간 낭비다.** 67장의 순서 — 측정 → 병목 확인 → 원인 가설 — 이 먼저다. 소스 읽기는 그 가설을 확인하는 마지막 단계에 온다.

### 저장소를 손에 넣는 방법

`https://github.com/dotnet/runtime`은 큰 저장소다. 전체 히스토리를 받으면 수 GB에 달하고, 웬만한 노트북에서 `git clone`이 수십 분 걸린다. 소스를 **읽기만 할 것이라면** 전체 히스토리가 필요 없다.

```bash
# 1) 얕은 클론 — 최신 커밋 하나만. 가장 빠르다. 히스토리 추적은 불가능
git clone --depth 1 https://github.com/dotnet/runtime.git

# 2) 특정 릴리스 브랜치만 얕게 — 자기가 쓰는 런타임과 맞추고 싶을 때
git clone --depth 1 --branch release/8.0 https://github.com/dotnet/runtime.git runtime-8

# 3) blobless 클론 — 트리는 다 받고 파일 내용은 필요할 때 가져온다.
#    히스토리(git log, git blame)를 쓰면서도 초기 다운로드가 작다. 권장
git clone --filter=blob:none https://github.com/dotnet/runtime.git
```

3번이 소스를 읽는 사람에게 가장 좋은 절충이다. `git log`, `git blame`, `git log -S`가 전부 동작하면서 초기 클론이 훨씬 가볍다. 대신 새 파일을 처음 열 때마다 네트워크 왕복이 생기므로 오프라인 작업에는 맞지 않는다.

디렉터리 일부만 필요하다면 sparse checkout을 쓴다.

```bash
git clone --filter=blob:none --sparse https://github.com/dotnet/runtime.git
cd runtime
git sparse-checkout set src/coreclr/gc docs/design
```

> **💡 대부분의 경우 클론조차 필요 없다**
>
> 소스를 **읽기만** 한다면 세 가지 웹 도구가 로컬 클론보다 빠르다.
>
> - **GitHub 코드 검색** — 저장소 페이지에서 `/`를 누르고 검색한다. 정규식과 `path:`, `lang:` 필터를 지원한다. 예: `repo:dotnet/runtime path:src/coreclr/gc plan_phase`
> - **`https://source.dot.net`** — .NET 라이브러리 소스를 Roslyn으로 인덱싱한 브라우저다. 식별자를 클릭하면 정의로 이동하고 **참조 목록**까지 나온다. 관리 코드(C#)를 읽을 때는 이쪽이 압도적으로 편하다. .NET Framework 시절의 대응물은 `https://referencesource.microsoft.com`이다.
> - **GitHub의 `.` 단축키** — 저장소 페이지에서 마침표 키를 누르면 브라우저 안에서 VS Code가 열린다.
>
> 로컬 클론이 필요한 순간은 **`git blame`으로 왜 이렇게 바뀌었는지 추적할 때**, **정규식으로 저장소 전체를 훑을 때**, 그리고 **직접 빌드해서 실험할 때**다.

> **⚠️ `main`을 읽으면서 자기 런타임 이야기를 하고 있다고 착각하지 마라**
>
> `main` 브랜치는 아직 릴리스되지 않은 다음 버전이다. 지금 프로덕션에서 도는 것이 .NET 8이라면 `main`의 코드는 **당신의 런타임이 아니다.** 특히 GC와 JIT은 릴리스마다 실질적으로 바뀐다.
>
> 항상 자기 런타임 버전에 맞는 브랜치나 태그를 보라.
>
> ```bash
> dotnet --info                      # 실제로 도는 런타임 버전 확인
> git checkout release/8.0           # 릴리스 브랜치(패치가 계속 들어간다)
> git checkout v8.0.11               # 정확한 패치 태그(재현 가능)
> ```
>
> 재현 가능한 조사를 하려면 **브랜치가 아니라 태그**를 체크아웃하라. 조사 기록에 커밋 해시를 함께 남기면 몇 달 뒤에도 같은 코드를 다시 볼 수 있다.

### 최상위 디렉터리

저장소 루트에서 실제로 의미 있는 것은 몇 개 안 된다.

| 경로 | 무엇이 있는가 | 언제 여는가 |
|---|---|---|
| `src/` | 모든 제품 소스 | 거의 항상 |
| `docs/` | 설계 문서, BOTR, 워크플로 가이드 | **소스보다 먼저** (83.5절) |
| `eng/` | 빌드 인프라(Arcade), 버전 정의, CI 파이프라인 | 직접 빌드할 때 |
| `.github/` | 이슈 템플릿, 라벨 자동화, 워크플로 | 기여할 때 |
| `global.json` | 이 저장소를 빌드하는 데 필요한 SDK 버전 | 빌드가 안 될 때 첫 확인 대상 |
| `Directory.Build.props`, `Directory.Build.targets` | 저장소 전역 MSBuild 속성 | 빌드 옵션을 추적할 때 |
| `build.sh`, `build.cmd` | 최상위 빌드 진입점 | 83.6절 |
| `NuGet.config` | 내부 피드 정의 | 복원 실패 시 |

`src/` 아래가 본체다.

| 경로 | 무엇이 있는가 |
|---|---|
| `src/coreclr/` | **CoreCLR 런타임** — 실행 엔진, GC, JIT, 디버거, PAL. C++/어셈블리가 대부분 |
| `src/libraries/` | **BCL과 그 위의 모든 라이브러리** — `System.*` 어셈블리들. C#이 대부분 |
| `src/mono/` | **Mono 런타임** — WASM, Android, iOS에서 쓰는 대체 런타임 |
| `src/native/` | 런타임에 종속되지 않는 **네이티브 공용 코드** — 플랫폼 shim, EventPipe, 호스트 |
| `src/installer/` | 설치 패키지 구성 |
| `src/tests/` | 런타임 수준 테스트(주로 CoreCLR용) |
| `src/tasks/` | 빌드에서 쓰는 MSBuild 태스크 |
| `src/workloads/` | 워크로드 매니페스트 |

> **📌 왜 런타임이 두 개인가**
>
> `src/coreclr`과 `src/mono`는 **같은 BCL을 실행하는 서로 다른 런타임**이다. 데스크톱·서버·컨테이너는 CoreCLR, WebAssembly와 모바일은 대체로 Mono가 담당한다. 두 런타임은 `src/libraries`의 라이브러리를 공유하고, 각자의 `System.Private.CoreLib`을 갖는다(83.3절).
>
> 그래서 어떤 동작을 조사할 때 **어느 런타임 이야기인지 먼저 확정**해야 한다. Blazor WebAssembly에서 관찰한 GC 동작을 `src/coreclr/gc/gc.cpp`에서 설명하려 들면 아무것도 맞지 않는다. 그쪽은 Mono의 GC이기 때문이다. 3권 61~65장의 GC 서술은 전부 CoreCLR 기준이다.

> **📌 `DOTNET_` 환경 변수의 정체를 확인하는 법**
>
> 3권에서 `DOTNET_gcServer`, `DOTNET_TieredCompilation`, `DOTNET_JitDisasm` 같은 변수를 여러 번 썼다. 이들의 **정의 위치는 두 군데로 나뉜다.**
>
> - GC 설정 → `src/coreclr/gc/gcconfig.h`
> - 그 외 런타임 설정 → `src/coreclr/inc/clrconfigvalues.h`
> - JIT 전용 설정 → `src/coreclr/jit/jitconfigvalues.h`
>
> 어떤 변수의 정체가 궁금하면 접두사를 떼고 저장소 전체를 검색하면 된다.
>
> ```bash
> grep -rn "TieredCompilation" src/coreclr/inc/clrconfigvalues.h
> grep -rn "JitDisasm" src/coreclr/jit/jitconfigvalues.h
> ```
>
> 정의 줄에 **기본값과 한 줄 설명이 함께** 있다. 문서화되지 않은 변수도 여기에는 있다.

> **⚠️ `COMPlus_`는 죽지 않았다**
>
> 오래된 자료와 옛 코드는 `COMPlus_gcServer`처럼 `COMPlus_` 접두사를 쓴다. .NET 6부터 `DOTNET_` 접두사가 도입되었고 **두 접두사가 모두 인식된다.** 새 코드에는 `DOTNET_`를 쓰되, 검색할 때는 접두사를 빼고 검색해야 양쪽 자료를 다 찾는다.
>
> 그리고 이 변수들은 **대부분 문서화되지 않은 내부 손잡이**다. 진단과 실험에는 자유롭게 쓰되, **프로덕션 구성으로 굳히지 마라.** 릴리스마다 예고 없이 사라질 수 있다. 프로덕션에서 굳혀야 하는 설정은 `runtimeconfig.json`에 정식 이름이 있는 것들뿐이다(65.5절).

### `src/libraries` — 규약이 곧 지도다

`src/libraries` 아래는 **어셈블리마다 같은 모양**이다. 이 규약만 외우면 어떤 라이브러리든 즉시 찾아간다.

```text
src/libraries/System.Text.Json/
├── src/          ← 실제 구현. 여기를 읽는다
│   ├── System/Text/Json/...
│   └── System.Text.Json.csproj
├── ref/          ← 참조 어셈블리. 공개 API 표면만 있다(78장의 public API 개념)
│   └── System.Text.Json.cs
├── tests/        ← 단위 테스트. "이 API가 정확히 무엇을 보장하는가"의 실질적 명세
├── gen/          ← (있다면) 소스 생성기
└── README.md
```

| 하위 폴더 | 여기서 답이 나오는 질문 |
|---|---|
| `ref/` | "공개 API가 정확히 무엇인가" — 한 파일에 시그니처만 있어 훑기 좋다 |
| `src/` | "구현이 무엇을 하는가" |
| `tests/` | "이 동작이 의도된 것인가" — 테스트가 있으면 의도된 것이다 |

> **💡 `ref/`를 먼저 읽는 습관**
>
> "이 타입에 뭐가 있더라"를 확인할 때 `src/`의 여러 파일을 뒤지는 대신 `ref/`의 단일 파일을 열면 5초면 끝난다. 오버로드 전체가 한눈에 들어오고, `internal` 노이즈가 전혀 없다. **공개 API 표면을 파악하는 데는 `ref/`가 문서보다 빠르다.**

`src/libraries/Common/src/`도 알아둘 가치가 있다. 여러 어셈블리가 **소스 링크로 공유**하는 코드가 여기 있다. `System.Text.Json`에서 어떤 헬퍼를 찾는데 그 어셈블리 폴더에 없다면 대개 여기 있다.

### 검색 전략 — 저장소를 다루는 실제 손놀림

디렉터리 구조를 외우는 것보다 **검색을 잘하는 것**이 훨씬 중요하다. 실전에서 쓰는 패턴은 다섯 가지다.

```bash
# 1) 정의 찾기 — 타입/함수가 어디서 선언되는가
grep -rn "class MethodTable" src/coreclr/

# 2) 상수/매크로의 실제 값 찾기 — "이 숫자가 어디서 왔는가"
grep -rn "define MIN_OBJECT_SIZE" src/
grep -rn "loh_size_threshold" src/coreclr/gc/

# 3) 설정 이름 찾기 — 환경 변수/런타임 설정의 정체
grep -rn "GCLOHThreshold" src/coreclr/

# 4) 사용처 찾기 — 이 함수를 누가 부르는가 (C++에는 IDE 없이 이게 최선이다)
grep -rn "decide_on_compacting" src/coreclr/gc/

# 5) 확장자 한정 — 노이즈 제거
grep -rn --include=*.cs "SpanHelpers" src/libraries/
```

`ripgrep`(`rg`)을 쓸 수 있다면 훨씬 빠르다. `.gitignore`를 자동으로 존중하고 바이너리를 건너뛴다.

```bash
rg -n "plan_phase" src/coreclr/gc/
rg -n --type cpp "USE_REGIONS" src/coreclr/gc/ | head -40
rg -n --type cs "\[Intrinsic\]" src/libraries/System.Private.CoreLib/src/System/Runtime/
```

> **⚠️ C++ 쪽에서 "정의로 이동"은 생각보다 안 통한다**
>
> `src/coreclr`의 C++ 코드는 **매크로가 매우 많고 조건부 컴파일이 겹겹이 쌓여 있다.** IDE의 인덱서가 정확한 정의로 안내하지 못하는 경우가 흔하다. 특히 `gc.cpp`는 헤더처럼 `#include`되므로(83.2절) 인덱서가 심볼을 중복으로 보거나 아예 놓친다.
>
> **C++ 쪽에서는 텍스트 검색이 심볼 인덱서보다 신뢰할 만하다.** 반대로 `src/libraries`의 C# 쪽은 정반대로, `source.dot.net`이나 IDE의 참조 찾기가 압도적으로 낫다. 두 세계에서 다른 도구를 쓴다는 것을 몸에 익혀라.

### 히스토리로 "왜"를 찾기

파일 구조가 답하지 못하는 질문 — **"왜 이렇게 되어 있는가"** — 은 히스토리가 답한다.

```bash
# 이 줄을 마지막으로 바꾼 커밋과 사람
git blame -L 100,140 src/coreclr/gc/gcconfig.h

# 이 문자열이 추가되거나 삭제된 모든 커밋 (pickaxe). 상수의 도입 시점 추적에 최고다
git log -S "GCLOHThreshold" --oneline

# 이 함수의 변경 이력만 (함수 단위 추적)
git log -L :decide_on_compacting:src/coreclr/gc/gc.cpp

# 파일이 이름을 바꾸거나 옮겨간 것까지 따라가기
git log --follow --oneline src/coreclr/gc/gcconfig.h
```

커밋 메시지에서 PR 번호를 찾으면 GitHub에서 **그 변경의 토론 전체**를 읽을 수 있다. 성능 관련 PR에는 대개 벤치마크 표가 붙어 있고, 그것이 그 변경의 진짜 근거다(83.5절).

| 68.2절, 68.3절 | `Span<T>` 내부와 `[Intrinsic]` | `Span.cs`, `ByReference`/`ref` 필드 | `source.dot.net`에서 `Span<T>` 검색 |
| 71.5절 | BCL의 벡터화 구현 | `SpanHelpers.*.cs` | `rg -n --type cs "IndexOfValueType" src/libraries/System.Private.CoreLib/` |
| 55.4절 | 인라이닝 정책 | `inline.def`, `InlinePolicy` | `rg -n "InlineObservation" src/coreclr/jit/inline.def` |

| 56.1절 | `ildasm`/`ilasm` 소스 | `src/coreclr/ilasm/`, `src/coreclr/ildasm/` | 저장소에서 디렉터리 확인 |
| 59.4절 | DLR 규칙 캐시 크기 | `CallSite<T>`, `RuleCache<T>` | `source.dot.net`에서 `RuleCache` 검색 |

> **⚠️ 이 표는 지도이지 좌표가 아니다**
>
> 위 표의 심볼 중 상당수는 `internal`이거나 아예 C++ 내부 함수다. **하나도 공개 계약이 아니다.** 그리고 릴리스마다 일부는 이름이 바뀌거나 사라진다. 심볼 이름으로 찾지 못하면 두 단계로 접근하라.
>
> 1. 그 이름의 **일부**로 다시 검색한다(`decide_on_` 같은 접두사).
> 2. 그래도 없으면 `git log -S "<옛 이름>"`으로 **언제 사라졌는지**를 찾고, 그 커밋에서 무엇으로 대체되었는지 읽는다.
>
> 2번이 이 장에서 가장 값진 기술이다. 이름이 사라졌다는 사실 자체가 정보다.

## 83.2 `gc.cpp`를 읽는 법 — 어디서부터 들어갈 것인가

### 이 파일이 얼마나 큰지부터 확인하라

`src/coreclr/gc/gc.cpp`는 이 저장소에서 가장 유명하고 가장 두려운 파일이다. 크기를 먼저 재라.

```bash
wc -l src/coreclr/gc/gc.cpp
# 이 글을 쓰는 시점 기준 4만 줄이 넘는다. 릴리스마다 늘어난다
```

숫자는 시점마다 다르지만 **한 사람이 통독할 수 있는 크기가 아니라는 사실만은 변하지 않는다.** 그래서 이 절의 목표는 "읽기"가 아니라 **"진입하기"** 다.

> **⚠️ 위에서 아래로 읽으려는 시도는 100% 실패한다**
>
> `gc.cpp`를 처음 여는 사람의 절반이 파일 맨 위부터 읽기 시작한다. 파일 앞부분은 매크로 정의, 전방 선언, 플랫폼 분기, 인라인 유틸리티다. **알고리즘은 한 줄도 없다.** 300줄쯤 읽고 나면 "GC가 어렵다"가 아니라 "나는 이걸 못 읽는다"는 잘못된 결론에 도달한다.
>
> 항상 **특정 질문을 들고** 들어가라. "GC를 이해하고 싶다"는 질문이 아니다. "gen0 GC가 압축을 할지 말지 어떻게 정하는가"가 질문이다. 질문이 있어야 검색어가 나오고, 검색어가 있어야 진입점이 나온다.

### 진입점 목록 — 이 여섯 개가 뼈대다

64장에서 본 GC 한 사이클의 단계는 소스에서 함수 하나씩에 거의 그대로 대응한다.

| 함수 | 하는 일 | 3권 대응 |
|---|---|---|
| `gc_heap::garbage_collect` | GC 진입점. 수집할 세대 결정, 동시 GC 여부 판정, EE 중단 조율 | 64.1절 |
| `gc_heap::gc1` | 실제 수집 한 번. **포그라운드와 백그라운드가 같은 함수를 쓴다** | 64.1절, 65.2절 |
| `gc_heap::mark_phase` | 루트에서 도달 가능한 객체 마킹 | 64.2절 |
| `gc_heap::plan_phase` | plug/gap 발견, 새 주소 계산, **압축할지 스윕할지 결정** | 64.6절, 64.8절 |
| `gc_heap::relocate_phase` | 모든 참조를 새 주소로 갱신 | 64.10절 |
| `gc_heap::compact_phase` | 객체를 실제로 이동 | 64.10절 |

여기에 백그라운드 GC의 대응물이 붙는다.

| 함수 | 하는 일 |
|---|---|
| `gc_heap::do_background_gc` | 백그라운드 GC 스레드를 깨운다 |
| `gc_heap::background_mark_phase` | 동시 마킹 |
| `gc_heap::background_sweep` | 동시 스윕 |

호출 관계를 그리면 이렇다.

```text
  GCHeap::GarbageCollect              ← EE가 GC를 요청하는 공개 진입점
          │
          ▼
  gc_heap::garbage_collect            ← 수집 세대 결정, 동시 여부 판정
          │
          ├─────────────► gc_heap::do_background_gc   (settings.concurrent = true)
          │                        │
          ▼                        ▼
  gc_heap::gc1  ◄───────────────────┘   같은 함수. 플래그로 갈린다
          │
          ├──► gc_heap::mark_phase
          │
          ├──► gc_heap::plan_phase   ── should_compact ? ──┐
          │                                                │
          │        아니오(스윕)                             예(압축)
          │           │                                    │
          │           ├─ gc_heap::make_free_lists          ├──► gc_heap::relocate_phase
          │           └─ gc_heap::recover_saved_pinned_info└──► gc_heap::compact_phase
          │
          └──► gc_heap::compute_new_dynamic_data   ← 다음 예산 계산
```

> **📌 이 다이어그램의 핵심은 `plan_phase`의 분기다**
>
> 64.8절에서 "압축할지 스윕할지는 Plan 단계가 끝난 뒤에 결정된다"고 했다. 소스에서 그 결정이 어떻게 생겼는지가 이 다이어그램의 중앙이다. `plan_phase` 안에서 `gc_heap::decide_on_compacting`이 `should_compact`를 계산하고, 그 값에 따라 **완전히 다른 두 경로**로 갈라진다.
>
> 그래서 `plan_phase`는 이름과 달리 "계획만 세우는 함수"가 아니다. **스윕 경로에서는 여기서 수집이 사실상 끝난다.** 이 비대칭이 소스를 처음 읽을 때 가장 헷갈리는 지점이다.

### 진입 절차 — 다섯 단계

```text
① 질문을 한 문장으로 적는다
   "gen2 GC가 압축을 결정하는 기준이 무엇인가"
        ↓
② 3권의 색인(83.1절 표)이나 검색으로 함수 이름을 얻는다
   → gc_heap::decide_on_compacting
        ↓
③ 정의 위치를 찾는다
   $ rg -n "gc_heap::decide_on_compacting" src/coreclr/gc/gc.cpp
        ↓
④ 정의 앞뒤 100줄만 읽는다. 모르는 이름은 넘어간다
        ↓
⑤ 모르는 자료구조 이름을 gcpriv.h에서 찾는다
   $ rg -n "dd_fragmentation\|generation_" src/coreclr/gc/gcpriv.h
```

④가 중요하다. **한 번에 하나의 함수만 읽는다.** 모르는 함수 호출이 나오면 이름에서 짐작하고 넘어가되, **이름을 메모해 둔다.** 같은 이름이 세 번 나오면 그때 찾아본다. 한 번 나온 것을 따라 내려가기 시작하면 스택이 20단이 되어 원래 질문을 잊는다.

### 이 파일은 두 번 컴파일된다

`gc.cpp`를 읽을 때 반드시 알아야 할 구조적 사실이 하나 있다. 65.1절에서 이미 언급한 것이다.

```cpp
// src/coreclr/gc/gcsvr.cpp — 서버 GC 빌드
#define SERVER_GC 1

namespace SVR {
    #include "gcimpl.h"
    #include "gc.cpp"      // ← .cpp 파일을 #include 한다
}
```

```cpp
// src/coreclr/gc/gcwks.cpp — 워크스테이션 GC 빌드
namespace WKS {
    #include "gcimpl.h"
    #include "gc.cpp"      // ← 같은 파일을 다시
}
```

결과적으로 `gc.cpp`의 모든 코드가 **`WKS::`와 `SVR::` 두 네임스페이스에 각각 한 벌씩** 존재한다. 컴파일된 바이너리에는 `WKS::gc_heap::plan_phase`와 `SVR::gc_heap::plan_phase`가 **둘 다** 들어 있다.

이 사실이 실무에서 세 가지로 나타난다.

| 나타나는 곳 | 어떻게 보이는가 |
|---|---|
| WinDbg 콜 스택(64.6절) | `coreclr!WKS::gc_heap::plan_phase+0xa9` — 접두사로 어느 모드인지 즉시 안다 |
| 심볼 검색 | `x coreclr!*plan_phase*`가 두 개를 반환한다 |
| IDE 인덱서 | 같은 함수가 중복 정의된 것처럼 보이거나 아예 인덱싱에 실패한다 |

> **⚠️ `.cpp`를 `#include`하는 구조가 도구를 망가뜨린다**
>
> `gc.cpp`는 **번역 단위가 아니다.** 헤더처럼 포함되는 파일이다. 결과적으로 다음 문제가 생긴다.
>
> - **IDE의 "정의로 이동"이 자주 실패한다.** `gc.cpp`를 단독으로 열면 `SERVER_GC`도 `MULTIPLE_HEAPS`도 정의되어 있지 않으므로, 인덱서가 보는 코드는 실제로 컴파일되는 코드와 다르다.
> - **`compile_commands.json` 기반 도구(clangd 등)에도 `gc.cpp`가 없다.** 컴파일 대상은 `gcsvr.cpp`와 `gcwks.cpp`뿐이다.
> - **에디터의 `#if` 회색 처리를 믿지 마라.** 회색으로 흐려진 블록이 실제로는 컴파일되는 코드일 수 있다.
>
> 그래서 `gc.cpp`는 **텍스트로 읽어야 한다.** 매크로 조건은 눈으로 따라가야 한다.

### 조건부 컴파일 — `#if`를 읽는 법

`gc.cpp`의 밀도가 높은 진짜 이유는 길이가 아니라 **조건부 컴파일**이다. 같은 알고리즘이 세그먼트용/리전용, 단일 힙/다중 힙, 32비트/64비트로 갈린다.

자주 만나는 매크로는 다음과 같다. **이 목록은 시점 기준이며, 실제 목록은 저장소에서 직접 확인해야 한다.**

| 매크로 | 켜지면 무엇이 달라지는가 | 3권 대응 |
|---|---|---|
| `SERVER_GC` | 서버 GC 빌드. `SVR` 네임스페이스 | 65.1절 |
| `MULTIPLE_HEAPS` | 힙이 여럿. `gc_heap` 인스턴스가 코어 수만큼. **`SERVER_GC`가 이것을 함의한다** | 65.1절 |
| `BACKGROUND_GC` | 백그라운드 GC 코드 포함. **SVR/WKS 양쪽에서 항상 정의된다** | 65.2절 |
| `USE_REGIONS` | 힙을 리전으로 관리. 꺼지면 세그먼트 방식 | 62.6절 |
| `FEATURE_EVENT_TRACE` | ETW/EventPipe 이벤트 발행 코드 포함 | 66.6절 |
| `HOST_64BIT` | 64비트 호스트. 상수와 정렬이 달라진다 | 54.3절 |
| `FEATURE_BASICFREEZE` | 고정(frozen) 세그먼트 지원 | 62.5절 |

실제 목록을 확인하려면 이렇게 한다.

```bash
# gc.cpp에서 쓰이는 전처리 조건을 빈도순으로 뽑는다
grep -o "^#if.*" src/coreclr/gc/gc.cpp | sort | uniq -c | sort -rn | head -30
```

읽을 때의 실전 규칙은 세 가지다.

1. **자기가 관심 있는 조합을 먼저 확정한다.** 대부분의 독자에게는 `USE_REGIONS` 켬 + `MULTIPLE_HEAPS` 여부만 정하면 된다. 나머지는 무시한다.
2. **`#else` 블록을 건너뛴다.** 관심 없는 쪽 분기를 읽느라 시간을 버리는 것이 가장 흔한 실수다.
3. **중첩이 3단을 넘으면 에디터의 접기 기능을 쓴다.** `#if`가 200줄 뒤에서 닫히는 경우가 흔해서, `#endif` 옆 주석(`// USE_REGIONS`)이 유일한 단서일 때가 많다.

> **💡 확실하게 알고 싶으면 전처리 결과를 뽑아라**
>
> `#if` 미로를 눈으로 따라가는 것이 지겨우면 **컴파일러에게 물어보면 된다.** 런타임을 한 번 빌드해 두었다면 전처리만 수행한 결과를 파일로 뽑을 수 있다.
>
> ```bash
> # 개념적 형태. 실제 인클루드 경로와 정의는 빌드 로그에서 가져온다
> clang++ -E -DSERVER_GC=1 -DFEATURE_REDHAWK=0 \
>         -I src/coreclr/gc -I src/coreclr/inc \
>         src/coreclr/gc/gcsvr.cpp > /tmp/gcsvr.i
> ```
>
> 정확한 컴파일 인자는 빌드 산출물의 `compile_commands.json`이나 빌드 로그에서 그대로 복사해 오는 것이 확실하다. 결과 파일은 수십만 줄이 되지만, **조건부 컴파일이 전부 해소된 순수한 코드**다. "이 블록이 정말 컴파일되는가"를 두고 논쟁할 일이 없어진다.
>
> 이건 최후의 수단이다. 대부분의 질문은 여기까지 가지 않고 풀린다.

### `gcpriv.h` — 자료구조 사전

`gc.cpp`를 읽다 막히는 이유는 알고리즘이 어려워서가 아니라 **이름을 몰라서**인 경우가 훨씬 많다. `dd_desired_allocation`, `generation_allocation_pointer`, `heap_segment_mem` 같은 것들이다.

이들의 정체는 대부분 `gcpriv.h`에 있다. 이 헤더에서 확인할 주요 타입은 다음과 같다.

| 타입 | 무엇인가 | 3권 대응 |
|---|---|---|
| `gc_heap` | GC 힙 하나. 워크스테이션은 인스턴스 1개, 서버는 코어 수만큼 | 65.1절 |
| `generation` | 세대 하나. 할당 컨텍스트, 프리 리스트 할당자, 시작 세그먼트 | 62.4절 |
| `heap_segment` | 세그먼트 **또는 리전**. 리전 도입 후에도 타입 이름은 그대로다 | 62.6절 |
| `alloc_context` | 할당 컨텍스트(범프 포인터와 한계) | 63.1절 |
| `dynamic_data` | 세대별 동적 상태 — 예산, 생존율, 단편화 | 63.6절 |
| `static_data` | 세대별 정적 튜닝 값 — 최소/최대 크기, 생존율 임계값 | 63.6절 |
| `alloc_list`, `allocator` | 프리 리스트와 버킷 | 63.2절 |

> **⚠️ 접두사 함수는 매크로다**
>
> `dd_desired_allocation(dd)`처럼 생긴 것들은 함수가 아니라 **인라인 접근자 매크로/인라인 함수**다. `dd_`는 `dynamic_data`, `generation_`은 `generation`, `heap_segment_`는 `heap_segment` 필드 접근이다.
>
> ```bash
> rg -n "dd_desired_allocation" src/coreclr/gc/gcpriv.h
> ```
>
> 이 규칙을 모르면 `dd_fragmentation(dd) > dd_max_size(dd)` 같은 줄이 함수 호출로 보여서 정의를 찾아 헤매게 된다. **접두사를 보고 어느 구조체의 필드인지 즉시 알아채는 것**이 `gc.cpp` 독해 속도를 가장 크게 올린다.

`heap_segment` 이야기는 한 번 더 짚을 가치가 있다. 62.6절에서 본 대로 .NET 7부터 세그먼트가 리전으로 바뀌었는데, **타입 이름은 `heap_segment` 그대로**다. 리전 모드에서는 `gen_num` 필드가 그 리전이 속한 세대를, `flags`가 SOH/LOH/POH 구분을 담는다. 이름만 보고 "이건 옛날 세그먼트 코드"라고 판단하면 틀린다.

### `gcconfig.h` — 설정 이름을 찾는 정확한 지점

65.8절에서 `GC.GetConfigurationVariables()`가 반환하는 키가 환경 변수 이름과 다르다는 함정을 봤다. 그 매핑의 원본이 `gcconfig.h`의 `GC_CONFIGURATION_KEYS` 매크로다.

```text
#define GC_CONFIGURATION_KEYS \
BOOL_CONFIG (ServerGC,     "gcServer",     "System.GC.Server",     false, "Whether we should be using Server GC")  \
BOOL_CONFIG (ConcurrentGC, "gcConcurrent", "System.GC.Concurrent", true,  "Whether we should be using Concurrent GC")  \
```

| 열 | 의미 | 실제 사용 예 |
|---|---|---|
| 1 | 내부 키 이름 | `GC.GetConfigurationVariables()`가 반환하는 것 |
| 2 | 환경 변수 이름의 뒷부분 | `DOTNET_gcServer=1` |
| 3 | 런타임 설정 속성 이름 | `runtimeconfig.json`의 `"System.GC.Server": true` |
| 4 | 기본값 | 명시하지 않았을 때의 동작 |
| 5 | 설명 | 이 손잡이가 무엇을 하는지 |

이 파일 하나로 답할 수 있는 질문이 많다.

```bash
# GC 설정 전부 훑어보기 — 문서화되지 않은 것까지 다 나온다
rg -n "CONFIG \(" src/coreclr/gc/gcconfig.h

# 특정 설정의 환경 변수 이름과 기본값 확인
rg -n "GCLOHThreshold\|GCConserveMem\|GCgen0size" src/coreclr/gc/gcconfig.h

# 정수형 설정만
rg -n "INT_CONFIG" src/coreclr/gc/gcconfig.h
```

> **⚠️ `gcconfig.h`에 있다고 해서 써도 되는 것은 아니다**
>
> 이 파일에는 **공개 문서에 없는 설정이 많다.** 개발 중인 기능의 스위치, 진단용 손잡이, 특정 시나리오 실험용 값들이다. 문서에 없다는 것은 대개 **의도적으로 지원 대상이 아니라는 뜻**이다.
>
> - 실험과 진단에는 얼마든지 써라. 이 장 전체가 그것을 권한다.
> - **프로덕션 설정으로 굳히지 마라.** 다음 패치에서 사라져도 아무도 알려주지 않는다.
> - 프로덕션에 넣어야 한다면 **3번 열(런타임 설정 속성)이 있는 것만** 써라. 그것이 지원 대상이라는 신호다.
>
> 65.5절에서 다룬 `System.GC.HeapHardLimit` 같은 것들이 3번 열이 있는 부류다.

### 상수의 출처를 찾는 실전 — LOH 임계값

3권에서 여러 번 나온 "85,000바이트"를 소스에서 확인해 보자. 82장 끝에서 예고한 바로 그 작업이다.

```bash
# ① 숫자로 찾는다. 가장 단순하고 자주 통한다
rg -n "85000" src/coreclr/

# ② 개념 이름으로 찾는다
rg -n "loh_size_threshold\|LARGE_OBJECT_SIZE" src/coreclr/

# ③ 설정으로 바꿀 수 있는지 확인한다
rg -n "GCLOHThreshold" src/coreclr/gc/gcconfig.h
```

여기서 얻는 결론이 세 가지다.

1. **숫자가 코드에 박혀 있는 위치**를 알게 된다.
2. 그 숫자를 담는 **변수 이름**을 알게 되고, 그 변수를 쓰는 모든 곳을 다시 검색할 수 있다.
3. `GCLOHThreshold` 설정이 존재한다는 것 — 즉 **이 값이 상수가 아니라 구성 가능한 값**이라는 것을 알게 된다. 62.3절에서 다룬 내용이다.

3번이 소스 읽기의 전형적인 수확이다. "85,000은 고정값"이라는 통념이 **소스에서는 기본값일 뿐**임이 드러난다. 그리고 83.6절에서 이것을 실험으로 확인한다.

> **📌 `double` 배열 예외도 같은 방법으로 확인된다**
>
> 62.3절에서 "32비트 런타임에서 `double[]`은 1,000개 이상이면 LOH로 간다"고 했다. 이것도 코드에 있다.
>
> ```bash
> rg -n "1000" src/coreclr/vm/gchelpers.cpp
> rg -n "MaxPrimitiveTypeSize\|dbl\|double" src/coreclr/vm/gchelpers.cpp
> ```
>
> 검색어를 여러 개 시도해야 할 수도 있다. **소스 검색은 한 번에 맞히는 게임이 아니다.** 3~5번 검색어를 바꿔가며 좁히는 것이 정상적인 과정이다.

### 디버거로 읽기 — 정적 읽기의 한계를 넘을 때

정적으로 읽어서 답이 안 나오는 질문이 있다. "**지금 이 순간** 어느 분기를 탔는가"가 그렇다. 조건이 런타임 상태에 달려 있으면 코드만 봐서는 알 수 없다.

이때는 66.9절과 74.5절에서 쓴 WinDbg를 그대로 쓴다. GC 심볼이 붙으면 콜 스택에 함수 이름이 그대로 나온다.

```text
0:005> k
 # Child-SP          Call Site
 00 000000a963b7cd30 coreclr!WKS::gc_heap::plan_phase+0xa9
 01 000000a963b7ce40 coreclr!WKS::gc_heap::gc1+0x178
 02 000000a963b7ceb0 coreclr!WKS::gc_heap::garbage_collect+0x5ca
```

이 스택 하나로 세 가지를 동시에 안다. **워크스테이션 GC**(`WKS::`), **Plan 단계 한복판**(`plan_phase`), 그리고 **비동시 경로**(`gc1`이 GC 스레드가 아닌 스레드에 있다면 블로킹 GC다).

> **💡 정적 읽기와 동적 관찰을 번갈아 써라**
>
> 소스를 읽어 함수 이름을 얻고 → 디버거에서 그 이름으로 중단점을 걸고 → 실제로 걸리는지 보고 → 안 걸리면 왜 안 걸리는지 소스로 돌아가 확인한다. 이 왕복이 소스 독해의 실제 모습이다.
>
> ```text
> bp coreclr!WKS::gc_heap::decide_on_compacting
> ```
>
> 중단점이 안 걸린다면 두 가지 중 하나다 — **그 경로를 안 타고 있거나**(서버 GC라 `SVR::`이거나), **인라인되어 독립 심볼이 없거나**. 둘 다 정보다. 실패도 관찰 결과로 기록하라.

> **⚠️ 릴리스 빌드에서는 인라인 때문에 스택이 거짓말한다**
>
> 배포된 `coreclr.dll`은 최적화 빌드다. 작은 함수는 호출자에 인라인되어 **콜 스택에 나타나지 않는다.** `mark_object_simple`이 안 보인다고 마킹을 안 하는 것이 아니다.
>
> 그래서 콜 스택으로 "이 함수가 호출되지 않았다"를 결론 내리면 안 된다. **호출되었다는 것은 증명하지만 호출되지 않았다는 것은 증명하지 못한다.** 확실히 하려면 체크드 빌드를 직접 만들어야 한다(83.6절).

## 83.3 코어 라이브러리(`System.Private.CoreLib`)의 C# 구현 읽기

### CoreLib은 세 조각으로 나뉘어 있다

54장 내내 다룬 대로 `System.Private.CoreLib`은 `object`, `string`, `int`, `Array`, `Span<T>` 같은 **가장 기본적인 타입이 사는 어셈블리**다. 런타임과 뗄 수 없이 얽혀 있어서 다른 라이브러리와 다르게 취급된다.

가장 먼저 알아야 할 것은 **소스가 한 군데 있지 않다**는 사실이다.

| 경로 | 무엇이 있는가 | 우선순위 |
|---|---|---|
| `src/libraries/System.Private.CoreLib/src/` | **공유 파티션.** 모든 런타임이 함께 쓰는 구현 | 기본 |
| `src/coreclr/System.Private.CoreLib/src/` | **CoreCLR 전용.** 같은 타입의 CoreCLR 구현/부분 클래스 | CoreCLR 빌드에서 우선 |
| `src/mono/System.Private.CoreLib/src/` | **Mono 전용** | Mono 빌드에서 우선 |

같은 타입이 두 군데에 나뉘어 있는 경우가 매우 흔하다. 대개 **`partial` 클래스**로 쪼개져 있다 — 알고리즘은 공유 파티션에, 런타임에 물어봐야 하는 부분은 런타임별 파티션에 있다.

```text
src/libraries/System.Private.CoreLib/src/System/String.cs         ← 공유 구현
src/coreclr/System.Private.CoreLib/src/System/String.CoreCLR.cs   ← CoreCLR 전용 조각
```

> **⚠️ 공유 파티션만 읽고 결론 내리면 절반만 본 것이다**
>
> 어떤 메서드의 구현을 찾았는데 본문이 이상하게 얇거나 `throw new NotImplementedException()`처럼 보이거나 `extern`이라면, **다른 파티션에 나머지가 있다.** 파일 이름에 `.CoreCLR.cs`, `.Mono.cs`, `.Unix.cs`, `.Windows.cs`가 붙은 형제 파일을 찾아라.
>
> ```bash
> # 타입 이름으로 모든 파티션의 파일을 찾는다
> find src -name "String*.cs" -path "*System.Private.CoreLib*"
> ```
>
> `source.dot.net`은 이 문제를 잘 처리한다 — 같은 타입의 여러 파일을 한 목록으로 보여준다. C# 쪽에서 그 사이트를 쓰라고 권하는 이유 중 하나다.

**어떤 파일이 실제로 컴파일되는가**를 확인해야 할 때도 있다. CoreLib의 `.csproj`는 파일 목록을 명시적으로 관리한다.

```bash
rg -n "String.cs" src/coreclr/System.Private.CoreLib/System.Private.CoreLib.csproj
```

목록에 없는 파일은 저장소에 있어도 그 런타임 빌드에 들어가지 않는다.

### 특성으로 구현 위치를 판별하는 법

CoreLib의 C# 코드를 읽다 보면 다른 라이브러리에서 볼 수 없는 특성들이 계속 나온다. **이 특성들이 "실제 구현이 어디 있는가"를 알려주는 표지판**이다.

| 특성 / 형태 | 의미 | 진짜 구현이 어디 있는가 |
|---|---|---|
| `[MethodImpl(MethodImplOptions.InternalCall)]` + `extern` | **FCall/ECall** — 런타임 C++ 함수로 직접 연결 | `src/coreclr/vm/`, 등록은 `ecalllist.h` |
| `[LibraryImport(RuntimeHelpers.QCall, ...)]` (과거 `[DllImport(RuntimeHelpers.QCall)]`) | **QCall** — P/Invoke 형태로 런타임 C++ 함수 호출 | `src/coreclr/vm/`, 등록은 QCall 진입점 표 |
| `[Intrinsic]` | **JIT이 이 메서드를 알아본다.** 호출로 두지 않고 직접 코드로 치환할 수 있다 | `src/coreclr/jit/` |
| `[MethodImpl(MethodImplOptions.AggressiveInlining)]` | 인라이닝 강제 힌트. 구현은 이 자리에 있다 | 이 파일 |
| `[DllImport("libSystem.Native", ...)]` / `[LibraryImport("libSystem.Native")]` | 플랫폼 shim 호출 | `src/native/libs/System.Native/` |
| 본문이 `Unsafe.*`, `ref` 조작뿐 | 관리 코드지만 JIT 최적화에 의존 | 이 파일 + JIT |
| `[StackTraceHidden]` | 스택 트레이스에서 숨김. 구현 위치와 무관 | 이 파일 |

> **📌 세 가지 호출 방식의 성격 차이**
>
> | | FCall (`InternalCall`) | QCall | 인트린식 (`[Intrinsic]`) |
> |---|---|---|---|
> | 형태 | 관리→네이티브 직접 호출 | P/Invoke 형태 | 호출이 아예 사라질 수 있다 |
> | GC 모드 | **협조 모드 유지** — GC가 이 스레드를 기다린다 | 선점 모드로 전환 | 해당 없음 |
> | 오버헤드 | 매우 낮음 | P/Invoke 전환 비용 | 없음(호출이 없다) |
> | 적합한 작업 | 아주 짧은 작업 | 오래 걸리거나 블로킹할 수 있는 작업 | 한두 개 명령으로 표현 가능한 것 |
>
> 64.12절에서 본 협조 모드가 여기서 다시 나온다. **FCall 안에서 오래 머무르면 GC가 그 스레드를 기다리느라 EE 중단이 길어진다.** 그래서 런타임 팀은 오래 걸리는 것을 FCall로 두지 않는다. 짧은 FCall 안에도 `FC_GC_POLL` / `FC_GC_POLL_RET` 매크로를 넣어 안전 지점을 만든다(64.12절).
>
> 최근 릴리스들의 흐름은 **FCall을 줄이고 QCall이나 순수 관리 코드로 옮기는 방향**이다. 그래서 옛 자료에서 "이 메서드는 FCall이다"라고 읽었다면 현재 소스에서 다시 확인해야 한다.

### C# 선언에서 C++ 구현으로 건너가는 절차

여기가 이 절의 핵심이다. `[MethodImpl(InternalCall)]`이 붙은 메서드를 만났을 때 실제 구현을 찾는 순서다.

65.8절에서 본 `GC.GetGeneration`을 예로 든다.

**① C# 선언을 확인한다.**

```csharp
public static class GC
{
    [MethodImplAttribute(MethodImplOptions.InternalCall)]
    public static extern int GetGeneration(object obj);
}
```

`extern`이고 본문이 없다. 관리 코드에는 구현이 없다는 뜻이다.

**② 등록표에서 메서드 이름을 검색한다.**

FCall은 `src/coreclr/vm/ecalllist.h`에 **관리 이름 → 네이티브 함수** 매핑으로 등록된다.

```bash
rg -n "GetGeneration" src/coreclr/vm/ecalllist.h
```

찾으면 이런 모양이다.

```cpp
FCFuncStart(gGCInterfaceFuncs)
    FCFuncElement("GetGeneration", GCInterface::GetGeneration)
    // ...
FCFuncEnd()

FCFuncStart(gGCSettingsFuncs)
    FCFuncElement("get_IsServerGC", SystemNative::IsServerGC)
    // ...
FCFuncEnd()
```

읽는 법은 단순하다. `FCFuncStart(...)`가 **타입 하나**에 대한 블록을 열고, 각 `FCFuncElement("관리 메서드 이름", 네이티브함수)`가 한 메서드를 잇는다. 프로퍼티는 `get_`/`set_` 접두사가 붙은 메서드 이름으로 나타난다(56.6절에서 본 IL 수준의 이름 그대로다).

`FCFuncStart` 블록이 **어느 타입에 대응하는지**는 별도의 클래스 목록에서 정해진다. 그 목록도 같은 파일 안에 있다.

```bash
rg -n "gGCInterfaceFuncs" src/coreclr/vm/ecalllist.h
```

**③ 네이티브 함수의 정의를 찾는다.**

```bash
rg -n "GCInterface::GetGeneration" src/coreclr/vm/
```

`comutilnative.cpp`에서 이런 모양으로 나온다.

```cpp
FCIMPL1(int, GCInterface::GetGeneration, Object* objUNSAFE)
{
    FCALL_CONTRACT;

    if (objUNSAFE == NULL)
        FCThrowArgumentNull(W("obj"));

    int result = (INT32)GCHeapUtilities::GetGCHeap()->WhichGeneration(objUNSAFE);
    FC_GC_POLL_RET();
    return result;
}
FCIMPLEND
```

여기서 FCall 관용구를 읽을 줄 알아야 한다.

| 관용구 | 의미 |
|---|---|
| `FCIMPL1` / `FCIMPL2` / ... | FCall 구현 시작. 숫자는 **인자 개수** |
| `FCIMPLEND` | FCall 구현 끝 |
| `FCALL_CONTRACT` | 이 함수의 계약(GC 모드, 예외, 스로우 가능성) 선언 |
| `FCThrow*` | FCall 안에서 예외를 던지는 전용 매크로 |
| `FC_GC_POLL` / `FC_GC_POLL_RET` | **안전 지점 삽입.** GC가 기다리고 있으면 여기서 협조한다(64.12절) |
| `OBJECTREF`, `*UNSAFE` 접미사 | GC가 객체를 옮길 수 있으므로 보호 여부를 이름으로 구분한다 |

**④ 거기서 GC나 다른 서브시스템으로 넘어간다.**

위 코드는 `GCHeapUtilities::GetGCHeap()->WhichGeneration(...)`을 부른다. 이제 83.2절의 세계로 넘어간 것이다.

```bash
rg -n "WhichGeneration" src/coreclr/gc/
```

**⑤ QCall이라면 다른 표를 본다.**

QCall은 P/Invoke 형태이므로 등록 방식이 다르다.

```csharp
internal static partial class Interop
{
    [LibraryImport(RuntimeHelpers.QCall, EntryPoint = "ObjectNative_GetHashCode")]
    private static partial int GetHashCode(/* ... */);
}
```

`EntryPoint` 문자열을 그대로 검색하면 네이티브 쪽 등록과 정의가 나온다.

```bash
rg -n "ObjectNative_GetHashCode" src/coreclr/
```

> **📌 `RuntimeHelpers.QCall`은 실제 DLL 이름이 아니다**
>
> `[LibraryImport(RuntimeHelpers.QCall, ...)]`의 `QCall`은 `"QCall"`이라는 상수 문자열이고, **디스크에 그런 파일은 없다.** 런타임이 이 이름을 특별 취급해서 자기 내부의 등록표에서 진입점을 찾는다.
>
> 그래서 QCall을 `DllImport` 실패로 오해하지 마라. 그리고 이 패턴은 CoreLib 안에서만 유효하다 — 사용자 코드에서 `RuntimeHelpers.QCall`을 흉내 낼 수 없다.

> **⚠️ 등록표에서 못 찾았다고 포기하지 마라**
>
> `ecalllist.h`에서 이름을 못 찾는 경우가 점점 늘고 있다. 이유는 셋이다.
>
> 1. **그 메서드가 QCall로 옮겨갔다.** `EntryPoint` 문자열로 다시 검색한다.
> 2. **관리 코드로 옮겨갔다.** 이제 C#으로 구현되어 있다. `[Intrinsic]`만 남았을 수도 있다.
> 3. **다른 등록 메커니즘을 쓴다.** 시대에 따라 방식이 바뀌었다.
>
> 가장 확실한 우회로는 **메서드 이름 문자열로 저장소 전체를 검색**하는 것이다.
>
> ```bash
> rg -n "GetGeneration" src/coreclr/ | grep -v "\.cs:"
> ```
>
> C# 파일을 제외하고 검색하면 네이티브 쪽 언급만 남는다.

### `[Intrinsic]`을 만났을 때

`[Intrinsic]`은 **"JIT이 이 메서드를 이름으로 알아본다"** 는 표시다. 본문이 있어도 JIT이 그것을 무시하고 자기 코드로 대체할 수 있다.

64.5절에서 본 `GC.KeepAlive`, 68.2절의 `MemoryMarshal.GetReference`, 71장의 하드웨어 내장 함수 전부가 이 부류다.

```csharp
[Intrinsic]
[MethodImpl(MethodImplOptions.AggressiveInlining)]
public static ref T GetReference<T>(Span<T> span) => ref span._reference;
```

JIT 쪽 연결을 찾는 절차는 이렇다.

```bash
# ① JIT이 아는 이름 목록에 있는지 확인
rg -n "GetReference\|KeepAlive" src/coreclr/jit/namedintrinsiclist.h

# ② 이름을 인식하는 지점
rg -n "lookupNamedIntrinsic" src/coreclr/jit/

# ③ 하드웨어 내장 함수라면 아키텍처별 목록
rg -n "Vector128_Create" src/coreclr/jit/hwintrinsiclistxarch.h
```

> **⚠️ `[Intrinsic]`이 붙었다고 항상 인트린식으로 처리되는 것은 아니다**
>
> 이건 3권에서 여러 번 강조한 함정의 소스 버전이다. `[Intrinsic]`은 **JIT이 그렇게 할 수 있다**는 표시일 뿐, 다음 조건에서 그냥 평범한 호출로 남는다.
>
> - **Tier-0 코드에서는** 대체로 인트린식 확장을 하지 않는다(55.2절).
> - **해당 아키텍처에 대응 명령이 없으면** 관리 구현이 그대로 쓰인다(71.4절).
> - **하드웨어 내장 함수가 비활성화되었으면**(`DOTNET_EnableHWIntrinsic=0` 등) 폴백을 탄다.
> - **인터프리터나 다른 런타임에서는** 아예 다른 경로다.
>
> 그래서 "`[Intrinsic]`이 붙어 있으니 공짜다"는 결론은 틀렸다. **소스는 가능성을 말하고, 실제 여부는 디스어셈블리가 말한다.** 83.6절에서 확인 절차를 다룬다.

### 워크스루 — `Span<T>.IndexOf`는 정말 벡터화되어 있는가

82장 끝에서 예고한 질문이다. 71.5절에서 "BCL이 이미 벡터화했다"고 말한 것을 소스로 확인해 보자.

**① 진입점을 찾는다.** `MemoryExtensions.IndexOf`는 `SpanHelpers`로 넘긴다.

```bash
rg -n --type cs "static int IndexOf" \
   src/libraries/System.Private.CoreLib/src/System/
```

**② 구현 파일을 연다.** `SpanHelpers`는 여러 파일로 쪼개져 있다.

```bash
find src/libraries/System.Private.CoreLib/src/System -name "SpanHelpers*.cs"
```

**③ 벡터 경로의 존재를 확인한다.** 확인해야 할 신호는 세 가지다.

| 신호 | 의미 |
|---|---|
| `Vector128.IsHardwareAccelerated` / `Vector256` / `Vector512` 검사 | 폭별 경로가 있다(71.4절) |
| `if (length < Vector128<T>.Count)` 같은 짧은 입력 분기 | **짧은 입력에는 스칼라를 쓴다** |
| 루프 끝의 스칼라 잔여 처리 | 벡터 폭으로 나누어떨어지지 않는 나머지 |

**④ 결론과 그 한계를 함께 적는다.**

- 확인된 것: 벡터 경로가 존재하고, 128/256/512 폭 분기가 있으며, 짧은 입력에는 스칼라 경로를 탄다.
- **확인되지 않은 것: 내 코드에서 실제로 벡터 경로를 타는가.** 입력 길이, 런타임 버전, CPU, 계층 상태에 달려 있다.

④의 구분이 결정적이다. **소스는 "코드가 존재한다"까지만 증명한다.** "내 프로세스에서 그 코드가 실행된다"는 별개의 명제이고, 그것은 83.6절의 실험으로만 확인된다.

> **💡 짧은 입력 분기는 항상 확인하라**
>
> BCL의 벡터화된 메서드는 거의 예외 없이 **입력이 짧으면 스칼라로 빠진다.** 벡터 레지스터 설정 비용이 이득을 넘기 때문이다(71.6절에서 다룬 그 손익분기점이다).
>
> 그래서 "BCL이 벡터화했으니 빠르다"는 기대는 **긴 입력에서만** 맞다. 평균 길이 8짜리 문자열을 백만 번 검색하는 코드에서는 벡터 경로가 한 번도 실행되지 않을 수 있다. 자기 워크로드의 **입력 길이 분포**를 먼저 알아야 소스에서 읽은 것이 의미를 갖는다.

### CoreLib 읽기에서 특히 조심할 것

> **⚠️ CoreLib의 코드 스타일을 자기 코드에 복사하지 마라**
>
> CoreLib에는 일반 애플리케이션 코드에서 금기인 패턴이 가득하다.
>
> - `Unsafe.Add`, `Unsafe.As`, `ref` 산술로 경계 검사를 우회한다
> - `goto`를 적극적으로 쓴다
> - 같은 로직을 여러 번 펼쳐 쓴다(수동 언롤링)
> - 인수 검증을 별도 `[DoesNotReturn]` 헬퍼로 빼서 인라이닝을 돕는다
>
> 이건 **런타임 팀이 매 릴리스마다 벤치마크로 검증하고, 전용 테스트 스위트로 보호하고, 잘못되면 프로세스가 죽는다는 것을 알면서** 쓰는 코드다. 애플리케이션 코드에서 흉내 내면 얻는 것보다 잃는 것이 크다(69장, 79장의 판단 기준을 따르라).
>
> **읽어서 이해하는 것과 따라 쓰는 것은 다르다.**

> **⚠️ `internal`은 계약이 아니다 — 리플렉션으로 뚫지 마라**
>
> 소스에서 유용한 `internal` 멤버를 발견하고 리플렉션으로 접근하고 싶어지는 순간이 온다. 하지 마라.
>
> - 이름이 바뀌면 **컴파일 오류가 아니라 런타임 오류**가 된다.
> - 트리밍·Native AOT에서 제거되어 조용히 실패한다(55.7절).
> - `System.Private.CoreLib`은 특히 위험하다 — 런타임 내부 상태를 건드리면 프로세스가 정의되지 않은 상태가 된다.
>
> 정말 필요하다면 **`dotnet/runtime`에 API를 제안하는 것**이 정공법이다(83.5절). 실제로 그렇게 공개된 API가 많다 — `MemoryMarshal`, `CollectionsMarshal`, `SearchValues` 전부 그 경로로 나왔다.

## 83.4 Roslyn 컴파일러 소스로 문법 동작 확인하기

### 질문의 종류가 다르다

83.2절과 83.3절이 답하는 질문은 "**런타임이 무엇을 하는가**"였다. 이 절이 답하는 질문은 "**컴파일러가 내 문법을 무엇으로 바꾸는가**"다.

3권과 2권에서 이런 문장을 여러 번 썼다.

- "`foreach`는 `GetEnumerator`/`MoveNext`/`Current` 패턴으로 낮춰진다"(56.6절)
- "`(X, Y) = (x, y)`는 튜플을 만들지 않는다"(77.6절)
- "`switch`의 패턴 집합은 결정 DAG가 된다"(77.15절)
- "`using`은 `try`/`finally`로 낮춰진다"(56.6절)

이 문장들의 근거는 **`dotnet/roslyn` 저장소**에 있다. 그리고 런타임과 달리 Roslyn은 **전부 C#으로 되어 있어서** 읽기가 훨씬 쉽다.

### 컴파일 파이프라인 — 어느 단계의 질문인지 먼저 정한다

```text
  *.cs 텍스트
      │
      ▼
  ① 어휘·구문 분석 (Parser)      → SyntaxTree.   "이 문법이 파싱되는가"
      │
      ▼
  ② 의미 분석 (Binder)           → BoundNode.    "이 이름이 무엇으로 해석되는가"
      │                                          "이 오버로드가 왜 선택되는가"
      ▼
  ③ 낮추기 (Lowering)            → 단순화된 BoundNode
      │                                          "이 문법이 무엇으로 바뀌는가"  ← 이 절의 주 관심
      ▼
  ④ 방출 (Emit)                  → IL 바이트
      │                                          "어떤 옵코드가 나오는가"
      ▼
  *.dll
```

| 질문 | 어느 단계 | 어디를 보는가 |
|---|---|---|
| "왜 이 코드가 컴파일 오류인가" | ② Binder | `Binder/`, `ErrorCode.cs` |
| "왜 이 오버로드가 선택되었나" | ② Binder | `Binder/Semantics/OverloadResolution/` |
| "`await`가 무엇으로 바뀌나" | ③ Lowering | `Lowering/AsyncRewriter/` |
| "`foreach`가 무엇으로 바뀌나" | ③ Lowering | `Lowering/LocalRewriter/` |
| "이 최적화를 컴파일러가 하나 JIT이 하나" | ③ vs 런타임 | Roslyn에 없으면 JIT의 일이다 |
| "IL이 정확히 어떻게 나오나" | ④ Emit | 실물 IL을 보는 게 빠르다(56장) |

> **⚠️ "컴파일러 최적화"와 "JIT 최적화"를 섞지 마라**
>
> 3권을 관통하는 구분이다. C# 컴파일러는 **놀랄 만큼 적게 최적화한다.**
>
> | 하는 것 | 안 하는 것 |
> |---|---|
> | 상수 폴딩(컴파일 타임 상수만) | 인라이닝 |
> | 도달 불가능 코드 제거 | 경계 검사 제거 |
> | 문법 낮추기(`foreach`, `using`, `await`, `yield`) | 루프 언롤링 |
> | 일부 관용구 인식(튜플 대입 등) | 역가상화 |
> | 분기 축약(`clt`+`brtrue` → `blt`) | 벡터화 |
>
> 오른쪽 열은 전부 **JIT의 일**이다(55.4~55.6절). "컴파일러가 최적화해 주겠지"라고 생각하고 Roslyn 소스를 뒤지면 아무것도 못 찾는다. **낮추기가 아닌 최적화를 찾고 있다면 저장소를 잘못 고른 것이다.**

### `dotnet/roslyn` 구조

| 경로 | 무엇이 있는가 |
|---|---|
| `src/Compilers/CSharp/Portable/` | **C# 컴파일러 본체** |
| `src/Compilers/CSharp/Portable/Parser/` | 어휘·구문 분석 |
| `src/Compilers/CSharp/Portable/Binder/` | 의미 분석, 오버로드 해석, 변환 규칙 |
| `src/Compilers/CSharp/Portable/Lowering/` | **낮추기 전부** |
| `src/Compilers/CSharp/Portable/Symbols/` | 심볼 모델(타입, 메서드, 매개변수) |
| `src/Compilers/CSharp/Portable/Errors/` | **오류 코드 정의** |
| `src/Compilers/CSharp/Test/` | 컴파일러 테스트 — **사실상의 명세** |
| `src/Compilers/Core/Portable/` | 언어 공용 인프라(메타데이터 읽기, IL 방출) |
| `docs/` | 컴파일러 설계 문서, 기능 구현 노트 |

`Lowering/` 아래가 이 절의 주 무대다.

| 하위 경로 | 무엇을 낮추는가 |
|---|---|
| `LocalRewriter/` | **대부분의 문법 낮추기** — `foreach`, `using`, `lock`, `switch`, 널 병합, 문자열 보간 등 |
| `AsyncRewriter/` | `async`/`await` → 상태 기계(47장) |
| `IteratorRewriter/` | `yield return` → 상태 기계(63.9절) |
| `ClosureConversion/` | 람다·지역 함수 → 클로저 클래스(63.9절) |
| `SpillSequenceSpiller/` | 평가 순서를 지키기 위한 임시 변수 도입 |
| `SyntheticBoundNodeFactory` | 낮추기가 생성하는 노드를 만드는 헬퍼 |

> **📌 `LocalRewriter`의 파일 이름 규약이 지도다**
>
> `Lowering/LocalRewriter/` 안의 파일은 **`LocalRewriter_<문법>.cs`** 형태로 나뉘어 있다. 그래서 찾고 싶은 문법의 이름만 알면 파일을 바로 짚을 수 있다.
>
> ```bash
> ls src/Compilers/CSharp/Portable/Lowering/LocalRewriter/
> # LocalRewriter_ForEachStatement.cs
> # LocalRewriter_UsingStatement.cs
> # LocalRewriter_LockStatement.cs
> # LocalRewriter_NullCoalescingOperator.cs
> # ... (실제 목록은 버전마다 다르다)
> ```
>
> 이 규약 하나 덕분에 Roslyn의 낮추기 소스는 `gc.cpp`보다 훨씬 접근하기 쉽다. **문법 이름 → 파일 이름**이 거의 기계적으로 대응한다.

### 낮추기를 확인하는 3단 절차

소스를 읽기 **전에** 결과를 먼저 보는 것이 항상 빠르다.

```text
① SharpLab에서 결과를 본다        ← 30초. 무엇으로 바뀌는지 즉시 확인
        ↓
② 그 결과가 왜 그런지 궁금하면 Roslyn 소스를 읽는다   ← 규칙과 예외를 확인
        ↓
③ IL로 최종 확인한다              ← ①의 "디컴파일된 C#"은 근사일 뿐이다
```

**① SharpLab.** `https://sharplab.io`에 코드를 붙여넣고 출력 형식을 고른다. 55.8절에서 다룬 그대로다.

| 출력 모드 | 보여주는 것 | 이 절에서의 용도 |
|---|---|---|
| **C#** | **낮추기 후의 코드를 다시 C#으로 디컴파일** | 낮추기 확인의 1순위 |
| IL | 실제 방출된 IL | 최종 확인 |
| Syntax Tree | 파싱 결과 | 파서 질문 |
| JIT Asm | 완전 최적화된 네이티브 코드 | 55장의 질문 |

**② Roslyn 소스.** SharpLab이 보여준 결과의 **조건과 예외**를 알고 싶을 때 소스로 간다. 예를 들어 77.6절의 튜플 대입 최적화가 언제 적용되고 언제 안 되는지는 SharpLab에서 케이스를 하나씩 시도하는 것보다 소스의 조건문을 읽는 편이 확실하다.

```bash
rg -n "DeconstructionAssignment\|IsTupleExpression" \
   src/Compilers/CSharp/Portable/Lowering/LocalRewriter/
```

**③ IL.** ①의 C# 출력은 **디컴파일 결과**이지 컴파일러의 실제 중간 표현이 아니다. 디컴파일러가 표현하지 못하는 것(예: 스택 조작 순서, `nop` 배치)이 있다. 정확성이 걸린 결론이라면 IL을 봐야 한다(56장).

> **⚠️ 낮추기 결과는 언어 명세가 아니다**
>
> 이 절 전체를 관통하는 경고다. **언어 명세가 보장하는 것은 "관찰 가능한 동작"이지 "낮추기 형태"가 아니다.**
>
> - 77.9절에서 본 대로, 패턴 매칭이 프로퍼티를 몇 번 읽는지는 **컴파일러 버전에 따라 바뀔 수 있다.** 현재 Roslyn은 캐시하지만 그것이 명세는 아니다.
> - `foreach`가 만드는 임시 변수의 개수, `using`이 만드는 `try` 블록의 정확한 형태, 문자열 보간이 `string.Format`을 부를지 `DefaultInterpolatedStringHandler`를 쓸지 — 전부 구현 선택이고 실제로 릴리스마다 바뀌어 왔다.
>
> **소스와 SharpLab으로 알아낸 낮추기 형태는 "지금 이 버전에서 할당이 몇 번 일어나는가"를 설명하는 데 쓴다.** 정확성 가정으로 쓰면 안 된다. 정확성은 명세와 문서가 정한다.

### 오류 메시지에서 `ErrorCode`로 역추적하기

"왜 이게 오류지"를 이해하는 가장 빠른 길이다. 컴파일러 오류에는 **항상 코드가 붙는다** — `CS0246`, `CS8352`, `CS0579` 같은 것들이다.

```text
error CS8352: Cannot use variable 'span' in this context because
              it may expose referenced variables outside of their declaration scope
```

이 코드로 소스를 역추적하는 절차다.

**① `ErrorCode` 열거형에서 이름을 찾는다.**

```bash
rg -n "ERR_.*= 8352\|8352" src/Compilers/CSharp/Portable/Errors/ErrorCode.cs
```

숫자 옆에 `ERR_EscapeLocal` 같은 **식별자 이름**이 있다. 이 이름이 다음 단계의 검색어다.

**② 메시지 원문을 확인한다.**

```bash
rg -n "ERR_EscapeLocal" src/Compilers/CSharp/Portable/CSharpResources.resx
```

`.resx`에 영어 원문과 (있다면) 그 오류에 대한 부연이 있다. 번역된 메시지가 애매할 때 원문을 보는 것만으로 해결되는 경우가 많다.

**③ 그 오류를 내는 코드를 찾는다.**

```bash
rg -n "ERR_EscapeLocal" src/Compilers/CSharp/Portable/Binder/
```

**여기가 진짜 답이다.** 그 오류를 보고하는 줄 주변의 조건문이 "정확히 어떤 경우에 이 오류가 나는가"를 말해준다. 68.11절의 `scoped`와 `ref` 안전 컨텍스트처럼 규칙이 복잡한 영역에서 특히 값지다.

**④ 테스트를 찾는다.**

```bash
rg -rn "ERR_EscapeLocal" src/Compilers/CSharp/Test/
```

컴파일러 테스트는 **"이 코드는 오류, 저 코드는 정상"의 사례 모음**이다. 자기 상황과 비슷한 사례를 찾으면 그 자리에서 답이 나온다.

> **💡 테스트가 최고의 명세다**
>
> Roslyn이든 런타임이든, **"이 동작이 의도된 것인가"를 가장 확실하게 알려주는 것은 테스트**다. 테스트가 있다는 것은 누군가 그 동작을 의도적으로 고정했다는 뜻이고, 테스트를 깨는 변경은 리뷰에서 걸린다.
>
> 반대로 **테스트가 없는 동작은 언제든 바뀔 수 있다.** 소스에서 어떤 동작을 발견했는데 그것을 검증하는 테스트가 없다면, 그건 "우연히 그렇게 동작하는 것"일 가능성이 있다.
>
> 이 판단 기준은 라이브러리에도 그대로 적용된다. `src/libraries/<어셈블리>/tests/`에서 자기가 의존하려는 동작을 검증하는 테스트를 찾아라. 있으면 의존해도 상대적으로 안전하고, 없으면 문서를 다시 확인하라.

### 분석기와 소스 생성기를 읽을 때

Roslyn 저장소는 컴파일러만 담고 있지 않다. IDE 기능, 코드 수정(code fix), 리팩터링도 함께 있다.

| 궁금한 것 | 어디를 보는가 |
|---|---|
| 이 IDE 경고가 왜 뜨는가 | `src/Analyzers/` |
| 이 코드 수정이 무엇을 바꾸는가 | `src/Analyzers/`의 대응 `CodeFixProvider` |
| `IDExxxx` 진단의 정체 | `IDEDiagnosticIds` 상수 검색 |

`CAxxxx`(코드 분석 규칙)는 Roslyn이 아니라 **`dotnet/roslyn-analyzers`** 저장소에 있다. 79.13절에서 `.editorconfig`로 켠 규칙 대부분이 그쪽이다.

> **⚠️ 진단 ID 접두사가 저장소를 결정한다**
>
> | 접두사 | 무엇 | 어느 저장소 |
> |---|---|---|
> | `CS` | C# 컴파일러 오류·경고 | `dotnet/roslyn` |
> | `IDE` | IDE 스타일 진단 | `dotnet/roslyn` |
> | `CA` | 코드 분석 규칙 | `dotnet/roslyn-analyzers` |
> | `SYSLIB` | 런타임 라이브러리 진단(사용 중단, 소스 생성기) | `dotnet/runtime` |
> | `IL` | 트리밍·AOT 분석 경고 | `dotnet/runtime` |
> | `RS` | 분석기 작성자용 규칙(78.13절의 공개 API 규칙 포함) | `dotnet/roslyn-analyzers` |
>
> 접두사를 확인하지 않고 엉뚱한 저장소를 검색하는 것이 시간 낭비의 흔한 원인이다.

### `dotnet/csharplang` — 문법이 왜 그렇게 생겼는가

Roslyn이 "어떻게 구현되었는가"라면 `dotnet/csharplang`은 "**왜 그렇게 설계되었는가**"다.

| 경로 | 무엇이 있는가 |
|---|---|
| `proposals/` | 기능 제안서. 채택된 것과 안 된 것 모두 |
| `proposals/csharp-<버전>/` | 그 버전에 들어간 기능의 확정 사양 |
| `meetings/` | **언어 설계 회의(LDM) 노트.** 날짜별로 정리 |
| `spec/` | 언어 명세 |

76장에서 버전별 기능을 훑었다. 그중 어떤 기능의 **경계 조건**이 왜 그렇게 정해졌는지 궁금하면 그 기능의 제안서를 읽는 것이 가장 빠르다. 제안서에는 대개 "Drawbacks", "Alternatives", "Open questions" 절이 있고, 거기에 **설계자들이 무엇을 포기했는지**가 적혀 있다.

`meetings/`의 LDM 노트는 더 날것이다. "이 문법을 이렇게 하면 기존 코드가 깨지므로 다르게 간다" 같은 결정 과정이 그대로 남아 있다.

> **⚠️ 제안서는 구현과 다를 수 있다**
>
> 제안서는 **논의 중인 문서**다. 채택되지 않은 제안, 채택되었지만 구현 중에 바뀐 제안, 여러 버전에 걸쳐 나뉘어 들어간 제안이 모두 같은 폴더에 있다.
>
> 어떤 제안서를 읽고 "이 기능이 있다"고 결론 내리기 전에 **`proposals/csharp-<버전>/` 아래에 있는지** 확인하라. 최상위 `proposals/`에만 있고 버전 폴더에 없다면 아직 들어가지 않았을 가능성이 높다. 76.14절에서 말한 대로, 릴리스별 확정 목록은 항상 저장소의 기능 상태 문서가 이 책을 포함한 어떤 2차 자료보다 정확하다.

## 83.5 런타임 이슈·PR·설계 문서로 최신 동향 따라가기

### 소스보다 먼저 읽어야 할 것 — `docs/design`

83.1절부터 여기까지 소스 이야기를 했지만, **순서는 사실 반대다.** `dotnet/runtime`에는 소스만큼이나 중요한 것이 `docs/` 아래에 있고, 대부분의 질문은 소스에 닿기 전에 여기서 풀린다.

| 경로 | 무엇이 있는가 | 언제 읽는가 |
|---|---|---|
| `docs/design/coreclr/botr/` | **Book of the Runtime (BOTR)** — CLR 서브시스템별 개관 | **소스를 열기 전에** |
| `docs/design/features/` | 개별 기능의 설계 문서 | 새 기능의 배경을 알고 싶을 때 |
| `docs/design/libraries/` | 라이브러리 설계 노트 | BCL 동작의 배경 |
| `docs/design/mono/` | Mono 관련 설계 | WASM·모바일 조사 |
| `docs/design/datacontracts/` | 진단 도구가 의존하는 런타임 내부 계약 | 74장 계열의 도구 개발 |
| `docs/workflow/` | 빌드·테스트·디버깅 절차 | **직접 빌드하기 전에** |
| `docs/project/` | 프로젝트 운영 — API 리뷰, 라벨, 분기 정책 | 83.5절 후반 |

**Book of the Runtime**이 이 목록의 핵심이다. CLR 개발자들이 각 서브시스템을 설명하려고 쓴 문서 모음이고, 원천 도서(Pro .NET Memory Management)도 GC 서술의 여러 곳에서 이 문서를 인용한다.

> **📌 BOTR을 읽는 순서**
>
> 문서 목록은 시점마다 다르므로 **`docs/design/coreclr/botr/README.md`가 항상 최신 목차**다. 다만 대략의 읽는 순서는 이렇다.
>
> 1. **런타임 개관 문서** — CLR이 무엇을 하는 시스템인지. 여기서 나머지 문서의 지도가 나온다
> 2. **타입 시스템 / 타입 로더 / 메서드 디스크립터** — 54장의 배경
> 3. **가상 스텁 디스패치** — 인터페이스 호출이 왜 그 비용인지(55.5절)
> 4. **RyuJIT 개관** — 55장의 배경
> 5. **가비지 컬렉션 / 스택 워킹 / 스레딩** — 64장의 배경. 특히 GC 정보와 안전 지점(64.4절, 64.12절)
> 6. **ReadyToRun** — 55.7절의 배경
> 7. **DAC 노트** — 66장·74장의 SOS와 덤프 분석이 왜 그렇게 동작하는지
>
> 3권을 읽은 독자에게 BOTR은 "이미 아는 것을 다른 각도에서 다시 설명하는 문서"로 읽힌다. 그게 정상이고, 그래서 소화가 빠르다.

> **⚠️ BOTR 문서에는 오래된 것이 섞여 있다**
>
> BOTR의 일부 문서는 .NET Framework 시절에 쓰였고 그 뒤로 크게 갱신되지 않았다. 예를 들어 AppDomain 이야기가 나오는 문서는 .NET(Core)에는 그대로 적용되지 않는다(52.9절).
>
> **판단 기준은 문서 상단의 갱신 이력과 `git log`다.**
>
> ```bash
> git log --oneline -5 -- docs/design/coreclr/botr/garbage-collection.md
> ```
>
> 몇 년간 손대지 않은 문서라면 **개념 설명만 취하고 구체적 수치나 구현 세부는 소스에서 다시 확인**하라. 개념은 거의 안 변하고, 세부는 자주 변한다.

`docs/design/features/`는 성격이 다르다. 여기에는 **비교적 최근에 도입된 기능의 설계 문서**가 쌓인다. 65.7절의 DATAS, 62.6절의 리전, 55.3절의 OSR 같은 것들이 각각 언제 왜 도입되었는지를 여기서 확인할 수 있다.

```bash
ls docs/design/features/
rg -rn "DATAS\|regions" docs/design/ | head -20
```

### 이슈 라벨 — 저장소를 필터링하는 법

`dotnet/runtime`은 이슈가 수만 건이다. 라벨 없이 검색하면 아무것도 못 찾는다.

| 라벨 계열 | 형태 | 용도 |
|---|---|---|
| **영역** | `area-GC-coreclr`, `area-CodeGen-coreclr`, `area-VM-coreclr`, `area-System.Text.Json` 등 | 서브시스템별 필터. **가장 중요하다** |
| **API 리뷰** | `api-suggestion` → `api-ready-for-review` → `api-approved` / `api-needs-work` | 새 API의 진행 단계 |
| **성격** | `tenet-performance`, `tenet-reliability`, `breaking-change` | 이슈의 종류 |
| **분류 상태** | `needs-area-label`, `untriaged` | 아직 담당 영역이 정해지지 않음 |
| **기여** | `help wanted`, `good first issue` | 외부 기여를 기다리는 것 |

검색 예시다.

```text
repo:dotnet/runtime label:area-GC-coreclr is:issue is:open regions
repo:dotnet/runtime label:tenet-performance is:pr is:merged Span
repo:dotnet/runtime label:breaking-change is:issue milestone:9.0.0
repo:dotnet/runtime label:api-approved is:issue Memory
```

> **💡 `area-` 라벨은 저장소 지도의 다른 표현이다**
>
> `docs/area-owners.md`(파일 이름은 시점에 따라 다를 수 있다)에 **라벨 ↔ 담당 영역 ↔ 소스 디렉터리**의 대응이 정리되어 있다. 어떤 동작을 조사하다 "이건 어느 팀 소관이지"가 궁금해지면 여기를 본다.
>
> 반대 방향으로도 쓸 수 있다. 소스 디렉터리를 알면 라벨을 알고, 라벨을 알면 그 영역의 최근 변경과 논의를 전부 훑을 수 있다. **소스에서 답이 안 나올 때 그 영역의 이슈 목록을 훑는 것이 다음 수단이다.**

### 이슈를 읽을 때의 함정

> **⚠️ 이슈의 댓글은 명세가 아니다**
>
> 이슈에서 런타임 팀원이 쓴 설명은 매우 값지지만, **작성 시점의 이야기**다. 3년 전 이슈에서 "현재 GC는 이렇게 동작한다"고 쓴 댓글이 지금도 맞다는 보장은 없다.
>
> 읽을 때 반드시 확인할 세 가지다.
>
> 1. **날짜.** 댓글 옆의 날짜를 먼저 본다.
> 2. **상태.** 닫힌 이슈인가? 닫힌 이유가 "수정됨"인가 "안 하기로 함"인가 "중복"인가?
> 3. **연결된 PR.** 실제로 코드가 바뀌었는가. 코드가 안 바뀌었으면 논의로 끝난 것이다.
>
> 특히 위험한 것이 **"계획 중"으로 끝난 이슈**다. 55.6절에서 언급한 스택 할당(이스케이프 분석) 이슈처럼, 오래 열려 있으면서 부분적으로만 구현된 것들이 있다. 이슈 제목만 보고 "이 기능이 있다"고 결론 내리면 틀린다.

> **⚠️ 옛 저장소에서 마이그레이션된 이슈는 링크가 깨져 있다**
>
> `dotnet/runtime`은 `dotnet/coreclr`, `dotnet/corefx`, `dotnet/core-setup`이 합쳐진 저장소다. 그 이전의 이슈와 PR은 번호가 다시 매겨졌고, 오래된 자료의 링크가 엉뚱한 이슈로 가는 경우가 있다.
>
> 링크가 이상하면 **이슈 제목으로 다시 검색**하는 것이 빠르다. 그리고 옛 저장소(`dotnet/coreclr`)는 아카이브되었지만 여전히 읽을 수 있다 — 오래된 GC·JIT 논의의 원본이 거기 있다.

### PR을 읽는 법 — 변경의 진짜 이유

성능 관련 질문에서는 이슈보다 **PR이 낫다.** 변경을 제안한 사람이 근거를 함께 올리기 때문이다.

PR에서 확인할 것은 네 가지다.

| 확인할 것 | 왜 |
|---|---|
| **본문의 벤치마크 표** | 이 변경이 무엇을 얼마나 개선했는지의 실측치 |
| **연결된 이슈** | 왜 이 변경이 필요했는지 |
| **리뷰 코멘트** | 대안이 왜 기각되었는지. **가장 값진 부분** |
| **변경된 테스트** | 무엇이 보장되게 되었는지 |

특정 코드가 왜 그 모양인지 알아내는 절차는 이렇다.

```bash
# ① 그 줄의 마지막 변경 커밋
git blame -L 250,270 src/coreclr/gc/gc.cpp

# ② 커밋 메시지에서 PR 번호를 얻는다 (대개 "(#12345)" 형태)
git show <해시> --stat

# ③ GitHub에서 그 PR을 연다
#    https://github.com/dotnet/runtime/pull/12345
```

`git blame`이 "포매팅 커밋"이나 "대규모 리팩터링 커밋"을 가리켜 쓸모없을 때가 있다. 그럴 때는 그 커밋을 건너뛰고 그 이전을 본다.

```bash
git blame -L 250,270 <포매팅커밋>^ -- src/coreclr/gc/gc.cpp
```

### API 리뷰 프로세스 — 새 API가 생기는 경로

83.3절 끝에서 "정말 필요하면 API를 제안하는 것이 정공법"이라고 했다. 그 경로는 공개되어 있고 절차가 정해져 있다.

```text
  ① 이슈 등록 (api-suggestion)
        │  제안하는 API의 시그니처를 정해진 형식으로 적는다
        ▼
  ② 영역 담당자 검토
        │  근거가 충분하면 api-ready-for-review
        ▼
  ③ API 리뷰 회의 (공개 녹화·노트)
        │
        ├──► api-approved     — 승인. 이제 누구나 구현 PR을 올릴 수 있다
        ├──► api-needs-work   — 시그니처 수정 필요
        └──► 거절            — 이유가 이슈에 남는다
        ▼
  ④ 구현 PR
        ▼
  ⑤ 릴리스에 포함
```

절차 문서는 `docs/project/` 아래에 있다.

```bash
ls docs/project/
rg -n "api-approved\|api review" docs/project/ | head
```

> **💡 거절된 API 제안이 가장 교육적이다**
>
> `api-suggestion` 라벨이 붙었다가 거절된 이슈를 읽어 보라. 78장에서 다룬 API 설계 원칙 — 최소 표면, 버전 관리 가능성, 오용 가능성 — 이 실제 사례에 어떻게 적용되는지를 **완성된 API를 보는 것보다 훨씬 선명하게** 알 수 있다.
>
> 특히 "이건 확장 메서드로 사용자 코드에 두면 된다", "이 시그니처는 나중에 오버로드를 추가할 수 없다", "이 이름은 기존 규약과 충돌한다" 같은 리뷰 코멘트가 78장의 원칙을 실물로 보여준다.

### 무엇이 깨지는지 추적하기

> **⚠️ 소스를 읽어 성능을 이해하는 것과 호환성을 확인하는 것은 다른 작업이다**
>
> 런타임 버전을 올릴 때 무엇이 깨지는지는 **소스로 확인하는 것이 아니다.** 그런 목적의 전용 문서가 따로 있다.
>
> - **파괴적 변경 문서** — .NET 문서 사이트에 버전별 목록이 정리되어 있다. `dotnet/docs` 저장소에 원본이 있다
> - **`breaking-change` 라벨** — `dotnet/runtime`의 이슈 필터
> - **릴리스 노트** — `dotnet/core` 저장소에 버전별로 정리되어 있다
> - **`SYSLIB`/`IL` 진단** — 사용 중단·트리밍 경고. 컴파일 시점에 알려준다
>
> 소스 diff를 직접 읽어 파괴적 변경을 찾으려는 시도는 비용이 엄청나고 놓치는 것이 생긴다. **정리된 목록이 있는 일은 정리된 목록을 봐라.**

### 동향을 지속적으로 따라가는 현실적인 방법

매일 저장소를 볼 수는 없다. 실무자가 감당 가능한 최소 루틴은 이 정도다.

| 주기 | 무엇 |
|---|---|
| 릴리스마다 (연 1회) | 그 버전의 **릴리스 노트**와 **파괴적 변경 목록**. 이것만은 빠뜨리면 안 된다 |
| 분기마다 | 자기가 의존하는 영역의 `area-*` 라벨 이슈 목록을 훑는다 |
| 필요할 때 | 특정 질문이 생겼을 때 이 장의 절차 |

> **📌 성능 개선 요약이 가장 효율적인 입구다**
>
> 매 릴리스마다 .NET 팀이 공개하는 성능 개선 요약 글이 있다. 매우 길지만, **PR 링크와 벤치마크가 전부 붙어 있어서** "이번 버전에서 내 코드에 영향 가는 변경"을 찾는 데 이보다 효율적인 자료가 없다.
>
> 읽는 법은 통독이 아니다. **자기가 쓰는 타입 이름으로 페이지 내 검색**을 하고, 걸리는 항목의 PR만 따라가면 된다.

## 83.6 직접 만든 실험 코드로 런타임 동작 검증하기

### 소스 읽기는 절반이다

83.1~83.5절이 "소스에서 무엇을 읽을 것인가"였다면 이 절은 **"읽은 것을 어떻게 믿을 것인가"** 다.

소스 읽기만으로 결론을 내리면 반드시 다음 셋 중 하나에 빠진다.

| 오류 | 어떻게 생기는가 |
|---|---|
| **잘못된 분기를 읽었다** | `#if`를 잘못 따라갔거나, 서버 GC 코드를 읽고 워크스테이션 이야기를 했다 |
| **코드가 존재하지만 실행되지 않는다** | Tier-0이라 인트린식이 확장 안 됐다, 입력이 짧아 스칼라 경로를 탔다 |
| **버전이 다르다** | `main`을 읽고 .NET 8 이야기를 했다 |

세 오류 전부 **실험 하나로 잡힌다.** 그래서 소스 읽기와 실험은 짝이다.

### 검증 루프

3권에서 흩어져 쓴 도구들을 하나의 절차로 묶으면 이렇게 된다.

```text
   ┌─────────────────────────────────────────────────────────┐
   │                                                         │
   ▼                                                         │
① 질문을 반증 가능한 명제로 적는다                             │
   "gen0에 할당된 90KB 배열은 LOH로 간다"                      │
   (× "LOH가 어떻게 동작하는지 알고 싶다")                      │
   │                                                         │
   ▼                                                         │
② 소스에서 근거를 찾는다  (83.1~83.4절)                        │
   → 근거가 되는 심볼·상수·조건문을 메모한다                    │
   │                                                         │
   ▼                                                         │
③ 관찰 방법을 고른다  (아래 표)                                │
   → 이 명제를 관찰로 참·거짓 판정할 수 있는가?                  │
   │                                                         │
   ▼                                                         │
④ 최소 실험을 만든다                                          │
   → 명제 하나만 건드리는 가장 작은 코드                        │
   │                                                         │
   ▼                                                         │
⑤ 반증을 시도한다                                             │
   → 참일 조건과 거짓일 조건을 둘 다 만들어 본다                 │
   │                                                         │
   ▼                                                         │
⑥ 기록한다                                                   │
   런타임 버전 · OS · 아키텍처 · GC 모드 · 커밋 해시 · 결과      │
   │                                                         │
   └── 결과가 소스와 어긋나면 ①로 돌아가 명제를 좁힌다 ─────────┘
```

⑤가 이 루프의 심장이다. **"맞았다"를 확인하는 실험은 거의 항상 성공한다.** 원하는 결과가 나올 조건만 무의식적으로 고르기 때문이다. 반대로 "이 조건에서는 틀려야 한다"를 만들어 실제로 틀리는 것을 확인하면, 그때 비로소 명제의 경계를 안 것이다.

### 관찰 방법 선택표

| 알고 싶은 것 | 도구 | 3권 위치 |
|---|---|---|
| 어떤 IL이 나오는가 | SharpLab, `ildasm`, ILSpy | 56.1절, 55.8절 |
| 컴파일러가 무엇으로 낮췄는가 | SharpLab의 C# 출력 | 83.4절 |
| 어떤 네이티브 코드가 나오는가 | `DOTNET_JitDisasm`, SharpLab JIT Asm, BenchmarkDotNet `[DisassemblyDiagnoser]` | 55.8절, 67.3절 |
| 이 메서드가 인라인되었는가 | `DOTNET_JitDisasmSummary`, 디스어셈블리에서 호출 유무 | 55.4절 |
| 할당이 몇 바이트 일어나는가 | `[MemoryDiagnoser]`, `GC.GetAllocatedBytesForCurrentThread()` | 67.5절 |
| 객체가 어느 세대·힙에 있는가 | `GC.GetGeneration()`, `!dumpheap`, `dotnet-gcdump` | 62.3절, 66.8절 |
| GC가 언제 몇 번 일어났는가 | `GC.CollectionCount()`, `GC.GetGCMemoryInfo()`, `dotnet-counters` | 65.8절, 66.8절 |
| GC 내부 어느 함수를 실행 중인가 | WinDbg + 심볼, 콜 스택 | 64.6절, 66.9절 |
| 런타임이 무엇을 하고 있는가(전반) | `dotnet-trace` / PerfView 이벤트 | 66.6절, 66.7절 |
| 이 설정이 실제로 적용되었는가 | `GC.GetConfigurationVariables()`, 런타임 시작 이벤트 | 65.8절 |
| 시간이 얼마나 걸리는가 | BenchmarkDotNet | 67.3절 |

> **⚠️ 도구를 하나만 쓰면 그 도구의 착시를 그대로 믿게 된다**
>
> 3권에서 반복한 경고를 여기서 한 번 더 묶는다.
>
> - **SharpLab의 JIT Asm은 완전 최적화 계층**이다. 실제 실행에서 그 코드가 나온다는 보장이 없다(55.8절).
> - **`Stopwatch` 한 번 재기**는 워밍업·계층 승격·GC 타이밍을 전부 무시한다(67.2절).
> - **`[MemoryDiagnoser]`는 스레드별 할당**을 본다. 백그라운드 스레드의 할당은 안 잡힌다.
> - **WinDbg 콜 스택은 인라인된 함수를 보여주지 않는다**(83.2절).
> - **디버거를 붙이면 JIT이 다르게 컴파일한다.** 최적화가 억제될 수 있다.
>
> **최소 두 가지 독립적인 방법으로 같은 결론이 나와야** 결론으로 삼는다. 하나는 정적(소스·IL·디스어셈블리), 하나는 동적(측정·이벤트·디버거)으로 고르면 가장 좋다.

### 환경 변수로 소스의 분기를 실제로 켜고 끄기

소스에서 "이 조건이면 다른 경로를 탄다"를 읽었을 때, **그 조건을 실제로 바꿔서 결과가 달라지는지 보는 것**이 가장 강력한 검증이다. 런타임은 이런 스위치를 많이 제공한다.

| 무엇을 검증하는가 | 스위치 | 확인 방법 |
|---|---|---|
| GC 모드 분기(65.1절) | `DOTNET_gcServer=1` / `0` | `GCSettings.IsServerGC` |
| 동시 GC 분기(65.2절) | `DOTNET_gcConcurrent=0` | GC 이벤트에서 BGC 유무 |
| 힙 개수(65.5절) | `DOTNET_GCHeapCount` | `!eeheap -gc`, GC 이벤트 |
| LOH 임계값(62.3절) | `DOTNET_GCLOHThreshold` | `GC.GetGeneration()` + 할당 실험 |
| gen0 예산(63.6절) | `DOTNET_GCgen0size` | `GC.CollectionCount(0)` 변화 |
| 계층형 컴파일(55.2절) | `DOTNET_TieredCompilation=0` | 첫 실행부터 최적화 코드 |
| 동적 PGO(55.5절) | `DOTNET_TieredPGO=0` | GDV 유무 |
| 하드웨어 내장 함수(71.4절) | `DOTNET_EnableAVX2=0` 등 | 디스어셈블리, 폴백 경로 |
| R2R 사용(55.7절) | `DOTNET_ReadyToRun=0` | 시작 시간, JIT 통계 |
| JIT 출력 보기(55.8절) | `DOTNET_JitDisasm=<메서드명>` | 표준 출력 |

> **💡 "설정을 껐더니 결과가 그대로다"도 결과다**
>
> `DOTNET_TieredCompilation=0`으로 껐는데 벤치마크 수치가 그대로라면 **계층형 컴파일이 그 시나리오에서 요인이 아니라는 것**을 알게 된 것이다. 이게 반증 실험의 실제 모습이다.
>
> 실험의 성공은 "예상대로 나오는 것"이 아니라 **"두 조건이 구분되는 것"** 이다. 구분되지 않으면 그 요인은 배제된다.

> **⚠️ 이 스위치들로 프로덕션을 튜닝하지 마라**
>
> 83.2절에서 `gcconfig.h` 이야기를 하면서 한 경고와 같다. 위 표의 상당수는 **진단·실험용 손잡이**다. 하나를 끄면 런타임의 다른 부분이 그것을 전제로 한 최적화를 잃을 수 있고, 조합에 따라 지원되지 않는 상태가 된다.
>
> 실험으로 원인을 찾았다면, **그 다음 단계는 지원되는 방법으로 같은 효과를 내는 것**이다. 65.5절의 `runtimeconfig.json` 설정, 코드 수정, 또는 라이브러리 교체다.

### 워크스루 1 — LOH 임계값이 정말 설정 가능한가

83.2절에서 소스로 `GCLOHThreshold`의 존재를 확인했다. 이제 실험으로 확인한다.

**명제**: "LOH 임계값은 85,000바이트 고정이 아니라 `DOTNET_GCLOHThreshold`로 **올릴 수 있다**. 다만 기본값 아래로는 내려가지 않는다."

```csharp
using System;

// 임계값 근처의 크기로 배열을 만들고 세대를 확인한다.
// byte[] n 의 실제 객체 크기는 n + 헤더/길이 오버헤드(64비트에서 24바이트 근처)다.
foreach (int size in new[] { 20_000, 40_000, 80_000, 84_000, 90_000 })
{
    var arr = new byte[size];
    Console.WriteLine($"{size,7} bytes -> gen {GC.GetGeneration(arr)}");
}

// 설정이 실제로 적용되었는지도 함께 확인한다
foreach (var pair in GC.GetConfigurationVariables())
    if (pair.Key.Contains("LOH", StringComparison.Ordinal))
        Console.WriteLine($"{pair.Key} = {pair.Value}");
```

세 번 실행한다.

```bash
# ① 기본값
dotnet run -c Release

# ② 기본값보다 낮게 설정한다 — 62.3절대로라면 무시되어야 한다
#    (GC 설정은 16진수로 해석되는 것이 많다. 소스에서 파싱 방식을 함께 확인하라)
DOTNET_GCLOHThreshold=8000 dotnet run -c Release

# ③ 기본값보다 높게 설정한다
DOTNET_GCLOHThreshold=100000 dotnet run -c Release
```

**판정 기준**: ③에서 90,000바이트 배열이 gen 0에 남으면 "올릴 수 있다"가 참이다. ②의 결과가 ①과 같으면 "내릴 수는 없다"가 확인된다 — 런타임이 설정값과 기본 임계값 중 **큰 쪽**을 택하기 때문이다(62.3절). ③마저 ①과 같다면 설정 자체가 적용되지 않은 것이고, 그때는 값의 형식(10진/16진)과 변수 이름을 소스에서 다시 확인한다.

> **⚠️ `GC.GetGeneration`이 2를 반환한다고 LOH라는 뜻은 아니다**
>
> 62.3절과 62.4절에서 본 대로 **LOH 객체는 gen 2로 보고**되지만, **gen 2 객체가 전부 LOH인 것은 아니다.** 오래 살아남아 승격된 작은 객체도 gen 2다.
>
> 갓 할당한 객체에 대해서는 gen 2 = LOH로 읽어도 되지만, 확실히 하려면 힙별로 나눠 보는 도구를 써야 한다.
>
> ```text
> !dumpheap -stat          (SOS, 66.9절)
> dotnet-gcdump collect    (66.8절)
> ```
>
> **"어떤 관찰이 어떤 명제를 증명하는가"를 정확히 따지는 습관**이 이 절 전체의 요점이다.

> **⚠️ 설정값의 단위와 진법을 확인하라**
>
> 런타임 설정 변수는 **10진으로 읽는 것과 16진으로 읽는 것이 섞여 있다.** 과거 `COMPlus_` 시절의 관례로 16진이 기본인 것들이 많다. `DOTNET_GCgen0size=8000`이 8,000바이트인지 0x8000(32,768)바이트인지에 따라 실험 결과가 전혀 달라진다.
>
> 확인 방법은 두 가지다. `gcconfig.h`의 정의를 보거나, **극단적인 값을 넣어 동작이 확실히 바뀌는지 보는 것**이다. 후자가 더 빠를 때가 많다.

### 워크스루 2 — `[Intrinsic]`이 실제로 인트린식으로 처리되는가

83.3절에서 `[Intrinsic]`이 "가능성"일 뿐이라고 했다. 확인해 보자.

**명제**: "`MemoryMarshal.GetReference`는 호출 명령을 남기지 않는다."

```csharp
using System;
using System.Runtime.CompilerServices;
using System.Runtime.InteropServices;

class Bench
{
    [MethodImpl(MethodImplOptions.NoInlining)]
    static int First(Span<int> s) => MemoryMarshal.GetReference(s);

    static void Main()
    {
        Span<int> data = stackalloc int[8];
        data[0] = 42;
        int sum = 0;
        // Tier-1까지 올리기 위해 충분히 반복한다 (55.2절)
        for (int i = 0; i < 200_000; i++) sum += First(data);
        Console.WriteLine(sum);
    }
}
```

```bash
DOTNET_JitDisasm=First DOTNET_TieredCompilation=1 dotnet run -c Release
```

**판정 기준**: 출력된 `First`의 어셈블리에 `call`이 없고 메모리 로드 명령만 있으면 인트린식으로 처리된 것이다. `call`이 있으면 아니다.

**그리고 반증을 시도한다.**

```bash
# Tier-0 코드를 보면 어떻게 다른가
DOTNET_JitDisasm=First DOTNET_TieredCompilation=0 dotnet run -c Release
```

두 출력을 비교하면 "인트린식은 항상 확장된다"가 아니라 **"어떤 계층에서 확장된다"** 는 더 정확한 명제로 좁혀진다.

> **📌 `DOTNET_JitDisasm`은 메서드 이름 패턴을 받는다**
>
> 정확한 메서드를 못 찾을 때는 패턴을 넓히거나, 어떤 메서드들이 JIT되었는지부터 확인한다.
>
> ```bash
> DOTNET_JitDisasmSummary=1 dotnet run -c Release
> DOTNET_JitStdOutFile=/tmp/jit.txt DOTNET_JitDisasm="Bench:*" dotnet run -c Release
> ```
>
> `DOTNET_JitStdOutFile`로 파일에 뽑으면 애플리케이션 출력과 섞이지 않아 훨씬 읽기 쉽다.

### 워크스루 3 — 경계 검사가 정말 제거되었는가

82장에서 "JIT이 경계 검사를 지웠을 것이다"라고 말하고 넘어간 그 명제다.

**명제**: "`for (int i = 0; i < arr.Length; i++) arr[i]` 형태에서 경계 검사가 제거된다."

```csharp
using System.Runtime.CompilerServices;

class Bounds
{
    [MethodImpl(MethodImplOptions.NoInlining)]
    public static int SumGood(int[] a)
    {
        int s = 0;
        for (int i = 0; i < a.Length; i++) s += a[i];   // 표준 형태
        return s;
    }

    [MethodImpl(MethodImplOptions.NoInlining)]
    public static int SumBad(int[] a, int n)
    {
        int s = 0;
        for (int i = 0; i < n; i++) s += a[i];          // 상한이 Length가 아니다
        return s;
    }

    static void Main()
    {
        var a = new int[1024];
        int s = 0;
        for (int i = 0; i < 100_000; i++) { s += SumGood(a); s += SumBad(a, a.Length); }
        System.Console.WriteLine(s);
    }
}
```

```bash
DOTNET_JitStdOutFile=/tmp/bounds.txt DOTNET_JitDisasm="Bounds:Sum*" \
  dotnet run -c Release
```

**판정 기준**: 55.6절에서 본 대로, 경계 검사는 어셈블리에서 **비교 + 조건부 점프 + `CORINFO_HELP_RNGCHKFAIL` 호출** 형태로 나타난다. `SumGood`의 루프 본문에 그것이 없고 `SumBad`에는 있으면 명제가 확인된다. 두 함수를 **같은 실행에서 나란히 비교**하는 것이 핵심이다 — 런타임 버전이나 CPU 차이가 개입할 여지가 없다.

> **💡 대조군을 항상 함께 만들어라**
>
> 이 워크스루의 진짜 교훈은 `SumBad`의 존재다. `SumGood` 하나만 보면 "이 어셈블리에 경계 검사가 없다"고 말하기 위해 경계 검사가 어떻게 생겼는지 **미리 알고 있어야** 한다. 대조군이 있으면 그럴 필요가 없다 — **차이가 곧 답**이다.
>
> 67.4절에서 벤치마크에 baseline을 두라고 한 것과 같은 원리를 디스어셈블리 읽기에 적용한 것이다.

### 워크스루 4 — GC가 지금 어느 단계인가

64.6절에서 본 WinDbg 절차의 소스 관점 재정리다.

**명제**: "이 애플리케이션의 긴 일시 정지는 Plan/Compact 단계에서 발생한다."

```text
1. 일시 정지 중에 덤프를 뜬다               (74.5절)
2. 모든 스레드의 콜 스택을 본다              ~*k
3. gc_heap::* 프레임이 있는 스레드를 찾는다
4. 함수 이름으로 단계를 판정한다:
      mark_phase      → Mark          (64.2절)
      plan_phase      → Plan/Sweep    (64.6절, 64.9절)
      relocate_phase  → Relocate      (64.10절)
      compact_phase   → Compact       (64.10절)
      background_*    → 백그라운드 GC   (65.2절)
5. WKS:: / SVR:: 접두사로 GC 모드를 확인한다  (83.2절)
```

이 절차가 성립하려면 **심볼이 있어야 한다.** 심볼 서버 구성은 74.6절에 있다.

> **⚠️ 단 한 번의 스택 샘플로 "여기가 병목"이라고 하지 마라**
>
> 덤프 하나는 **한 순간의 스냅샷**이다. Plan 단계에서 잡혔다고 Plan 단계가 오래 걸리는 것이 아니다. 우연히 그 순간이었을 수도 있다.
>
> 시간 배분을 알고 싶으면 **샘플링이나 이벤트 추적**을 써야 한다(66.6절, 67.6절). GC 단계별 시간은 GC 이벤트에서 직접 얻는 편이 훨씬 정확하다.
>
> 덤프 스택은 **"교착이 났다", "이 스레드가 여기서 멈춰 있다"** 같은 정지 상태의 판정에 강하고, **시간 배분 판정에는 약하다.** 도구의 강점에 맞는 질문을 던져라.

### 런타임을 직접 빌드해야 하는 순간

여기까지의 방법으로 안 되는 질문이 있다. **"이 함수가 정확히 몇 번 호출되었는가"**, **"이 조건문의 어느 쪽으로 갔는가"** 같은 것들이다. 배포된 최적화 바이너리에서는 관찰할 수 없다.

이때는 런타임을 직접 빌드한다. 절차의 최신 형태는 항상 저장소가 정확하다.

```bash
# 반드시 이 문서를 먼저 읽는다 — 필요한 도구와 최신 절차가 여기 있다
cat docs/workflow/README.md
cat docs/workflow/building/coreclr/README.md

# 대략의 형태 (인자는 버전마다 다르다)
./build.sh -subset clr+libs -configuration Debug
```

빌드 구성의 성격 차이를 알아야 한다.

| 구성 | 성격 | 언제 |
|---|---|---|
| **Release** | 최적화. 배포되는 것과 같다 | 성능 측정 |
| **Checked** | 최적화 + 어서션·진단 로그 활성화 | **내부 동작 관찰에 가장 유용** |
| **Debug** | 최적화 없음. 매우 느리다 | 런타임 코드에 중단점을 걸 때 |

> **⚠️ Debug 빌드로 성능을 측정하지 마라**
>
> 너무 당연해 보이지만 실제로 자주 일어난다. Debug 런타임은 어서션과 검증이 가득해서 **정상 빌드보다 수 배 느리다.** 여기서 나온 "GC가 오래 걸린다"는 관찰은 의미가 없다.
>
> 반대로 **동작 관찰에는 Checked가 최적**이다. 최적화가 켜져 있어 동작이 실제와 가깝고, 어서션과 진단 출력이 살아 있다. 런타임 팀 자신이 조사할 때 쓰는 구성이 이것이다.

> **💡 빌드까지 가는 경우는 드물다**
>
> 실무에서 이 장의 방법 중 런타임 빌드가 필요한 비율은 아주 낮다. 대부분의 질문은 **소스 읽기 + 환경 변수 + 디스어셈블리 + 이벤트**로 끝난다.
>
> 빌드가 필요하다고 느껴지면 먼저 자문하라. "이 질문에 답해서 내가 바꿀 코드가 있는가?" 없다면 그건 호기심이고, 호기심은 좋지만 업무 시간에 반나절짜리 빌드를 돌릴 이유는 아니다. 반대로 **런타임에 버그를 신고하거나 PR을 올릴 생각이라면** 빌드는 필수이고 그 투자는 정당하다.

## 이 장의 요약

- **소스는 "왜"에 답하고 문서는 "무엇에 의존할 것인가"에 답한다.** 소스에서 읽은 구현 세부를 계약으로 착각하는 순간 사고가 시작된다. 성능을 이해하는 데 쓰고, 정확성 가정으로 쓰지 마라.
- **저장소 구조는 외우는 것이 아니라 검색하는 것이다.** `src/coreclr`(런타임), `src/libraries`(BCL), `src/mono`(대체 런타임), `src/native`(플랫폼 층), `docs`(설계). 파일 이름은 바뀌지만 `rg`로 심볼을 찾는 방법은 바뀌지 않는다.
- **`gc.cpp`는 통독하는 파일이 아니라 진입하는 파일이다.** `garbage_collect` → `gc1` → `mark_phase` → `plan_phase` → `relocate_phase`/`compact_phase`가 뼈대이고, `plan_phase`의 `should_compact` 분기가 전체 구조의 중심이다.
- **`gc.cpp`는 `SVR`과 `WKS` 네임스페이스로 두 번 컴파일된다.** 이 사실이 IDE 인덱서를 망가뜨리고 WinDbg 스택에 접두사를 남긴다. 조건부 컴파일은 자기가 관심 있는 조합만 정해놓고 읽는다.
- **CoreLib은 세 파티션으로 나뉘어 있고, 특성이 구현 위치를 알려준다.** `[MethodImpl(InternalCall)]`은 FCall(등록표는 `ecalllist.h`), `[LibraryImport(RuntimeHelpers.QCall)]`은 QCall, `[Intrinsic]`은 JIT이 대체할 수 있다는 표시일 뿐 항상 대체한다는 보장이 아니다.
- **컴파일러 최적화와 JIT 최적화를 구분하라.** Roslyn은 낮추기를 하고 거의 최적화하지 않는다. 인라이닝·경계 검사 제거·벡터화를 Roslyn 소스에서 찾고 있다면 저장소를 잘못 고른 것이다.
- **오류 코드는 컴파일러 소스로 들어가는 가장 빠른 문이다.** `ErrorCode.cs`에서 이름 → `.resx`에서 원문 → `Binder/`에서 발생 조건 → `Test/`에서 사례. 그리고 **테스트가 없는 동작은 고정된 동작이 아니다.**
- **소스를 열기 전에 `docs/design`을 읽어라.** BOTR은 서브시스템의 개념 지도이고, 개념은 구현보다 훨씬 안정적이다. 다만 오래된 문서가 섞여 있으니 `git log`로 갱신 시점을 확인하라.
- **소스 읽기의 결론은 실험으로 닫는다.** 질문을 반증 가능한 명제로 적고, 최소 실험을 만들고, **반증을 시도하고**, 런타임 버전·모드·아키텍처와 함께 기록한다. 정적 근거 하나와 동적 관찰 하나가 일치해야 결론이다.
- **환경 변수는 소스에서 읽은 분기를 실제로 켜고 끄는 도구지 프로덕션 튜닝 손잡이가 아니다.** 실험으로 원인을 찾았다면 그 다음은 지원되는 방법으로 같은 효과를 내는 것이다.

## 연습 문제

1. `dotnet/runtime`을 `--filter=blob:none`으로 클론하고, 자기 머신에서 도는 런타임 버전에 해당하는 태그를 체크아웃하라(`dotnet --info`로 확인). 그 상태에서 `wc -l src/coreclr/gc/gc.cpp`를 실행해 이 책이 말한 규모와 비교하라. 그다음 `git log --oneline -20 -- src/coreclr/gc/gc.cpp`로 최근 어떤 변경이 있었는지 훑어라.

2. 83.1절의 색인 표에서 항목 다섯 개를 골라, 각 심볼을 `rg`로 실제로 찾아보라. 찾지 못한 것이 있다면 `git log -S "<심볼 이름>" --oneline`으로 **언제 사라졌는지**와 **무엇으로 대체되었는지**를 알아내고, 색인 표를 자기 버전 기준으로 고쳐 적어라.

3. `src/coreclr/gc/gcconfig.h`에서 `CONFIG (`가 들어간 줄을 전부 뽑아, **공식 문서에 있는 설정**과 **없는 설정**으로 분류하라. 3번 열(런타임 설정 속성 이름)이 있는 것과 없는 것의 비율을 세고, 그 차이가 무엇을 의미하는지 한 문단으로 적어라.

4. 83.6절 워크스루 1을 그대로 수행하되, 워크스테이션 GC와 서버 GC(`DOTNET_gcServer=1`) 양쪽에서 실행하라. 결과가 같은가 다른가. 그리고 `double[]`로 같은 실험을 반복해 62.3절에서 말한 예외가 자기 런타임에서 재현되는지 확인하라. 조사 기록 양식(83.6절)에 맞춰 `[한계]` 칸까지 채워라.

5. 자기가 자주 쓰는 BCL 메서드를 하나 고르고(예: `string.Split`, `Enumerable.Where`, `Dictionary<K,V>.TryGetValue`), `source.dot.net`에서 구현을 읽어라. 그 메서드가 (a) 할당을 하는가, (b) 몇 번 하는가, (c) 어떤 조건에서 안 하는가를 소스에서 답한 뒤 `[MemoryDiagnoser]`로 검증하라. 소스에서 예상한 바이트 수와 측정치가 다르면 그 차이의 원인을 찾아라.

6. C# 코드를 하나 골라 SharpLab의 C# 출력에서 낮추기 결과를 확인하고, `dotnet/roslyn`의 `Lowering/LocalRewriter/` 아래에서 대응하는 `LocalRewriter_*.cs` 파일을 찾아라. 그 파일에서 **낮추기가 적용되지 않는 조건**(조기 반환이나 `if`로 갈라지는 분기)을 하나 찾아, 그 조건을 만족하는 C# 코드를 작성해 SharpLab에서 실제로 다르게 낮춰지는지 확인하라.

7. 최근에 겪은 성능 문제나 이해되지 않는 동작을 하나 떠올려, 83.6절의 검증 루프 여섯 단계를 처음부터 끝까지 적용하라. ①의 명제를 반증 가능한 형태로 적는 것에서 시작해 ⑥의 기록까지 완성하라. 도중에 명제를 몇 번 좁혀야 했는지 세어보라 — 한 번도 안 좁혔다면 처음 명제가 너무 느슨했을 가능성이 높다.
