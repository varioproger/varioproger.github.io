## 26.1 델리게이트의 실체 — `MulticastDelegate` 해부

### 델리게이트가 답하는 질문

C 계열 언어에는 오래된 관용구가 있다. **함수 포인터**다. C 런타임의 `qsort`는 비교 함수의 주소를 받고, Windows API는 윈도 프로시저·훅 프로시저·비동기 프로시저 호출의 주소를 받는다. "나중에 이걸 불러 줘"라는 요구를 표현하는 가장 직접적인 수단이다.

문제는 관리되지 않는 C/C++에서 함수의 주소가 **그냥 메모리 주소**라는 데 있다. 그 주소에는 매개변수가 몇 개인지, 타입이 무엇인지, 반환 타입이 무엇인지, 호출 규약이 무엇인지에 대한 정보가 없다. 가볍지만 타입 안전하지 않다. 잘못된 서명의 함수를 넘기면 컴파일러는 통과시키고 런타임에 스택이 깨진다.

.NET은 같은 필요를 **델리게이트(delegate)** 로 채운다. 델리게이트는 "메서드를 호출할 줄 아는 객체"다. 델리게이트 **타입**은 그 객체가 어떤 종류의 메서드를 호출할 수 있는지 — 반환 타입과 매개변수 타입을 — 정의한다.

```csharp
delegate int Transformer (int x);
```

`Transformer`는 `int`를 반환하고 `int` 하나를 받는 모든 메서드와 호환된다.

```csharp
int Square (int x) => x * x;

Transformer t = Square;      // 델리게이트 인스턴스 생성
int answer = t (3);          // 호출 — 9
```

`t(3)`을 호출하면 델리게이트가 `Square`를 호출한다. 호출자는 `Square`라는 이름을 몰라도 되고, `Square`는 누가 자기를 부르는지 몰라도 된다. **이 간접 층이 델리게이트의 존재 이유 전부다.**

> **📌 델리게이트라는 이름**
>
> `delegate`는 "위임하다"라는 뜻이다. 델리게이트 인스턴스는 말 그대로 호출자를 대신하는 **대리인**이다. 호출자는 대리인을 부르고, 대리인이 진짜 메서드를 부른다.

### `delegate` 키워드가 만드는 것 — 클래스다

여기서 이 장의 첫 번째 핵심에 도달한다. **`delegate` 선언은 타입 별칭이 아니라 클래스 선언이다.**

C# 컴파일러가 `delegate int Transformer (int x);`를 만나면, 다음과 **거의 같은** 클래스를 만들어 어셈블리에 넣는다.

```csharp
// 컴파일러가 생성하는 것 (개념적 C# 표현)
internal sealed class Transformer : System.MulticastDelegate
{
    public Transformer (object @object, IntPtr method);

    public virtual int Invoke (int x);

    // 아래 둘은 .NET Framework 시절의 비동기 호출 패턴 잔재다
    public virtual IAsyncResult BeginInvoke (int x, AsyncCallback callback, object @object);
    public virtual int EndInvoke (IAsyncResult result);
}
```

`ildasm`으로 확인하면 실제로 이 네 멤버가 보인다.

```il
// TypDefName: Transformer
// Extends   : System.MulticastDelegate
.class private auto ansi sealed Transformer
       extends [System.Runtime]System.MulticastDelegate
{
  .method public hidebysig specialname rtspecialname
          instance void .ctor(object 'object', native int 'method') runtime managed { }

  .method public hidebysig newslot virtual final
          instance int32 Invoke(int32 x) runtime managed { }
}
```

여기서 놓치면 안 되는 단어가 `runtime managed`다. 보통의 메서드는 `cil managed`이고 IL 본문이 있다. 델리게이트의 생성자와 `Invoke`는 **IL 본문이 없다.** 구현을 런타임이 직접 제공한다. C# 컴파일러도, IL 어셈블러도 이 메서드의 코드를 쓰지 않는다. CLR이 델리게이트 타입을 로드할 때 내부에서 호출 스텁(stub)을 만들어 붙인다.

> **📌 델리게이트는 어디에나 선언할 수 있다**
>
> 델리게이트는 클래스이므로 **클래스를 선언할 수 있는 모든 자리**에 선언할 수 있다. 네임스페이스 수준, 클래스 안(중첩 타입), 구조체 안 모두 가능하다. 접근 제한자도 클래스와 같은 규칙을 따른다 — `internal delegate`로 선언하면 컴파일러가 만드는 클래스도 `internal`이다.
>
> 반대로 델리게이트 안에는 아무것도 선언할 수 없다. 본문 자체가 없기 때문이다.

> **⚠️ `System.Delegate`나 `System.MulticastDelegate`를 직접 상속할 수 없다**
>
> ```csharp
> class MyDelegate : MulticastDelegate { }   // 컴파일 오류 CS0644
> ```
>
> 이 두 클래스는 언어 차원에서 상속이 금지되어 있다. 델리게이트 타입을 만드는 유일한 방법은 `delegate` 키워드다. 반면 **제네릭 제약**으로는 쓸 수 있다 — `where T : Delegate`, `where T : MulticastDelegate`가 ※C# 7.3부터 허용된다(23.6절).

### 두 개의 기반 클래스라는 역사적 사고

모든 델리게이트 타입은 `System.MulticastDelegate`에서 파생되고, `MulticastDelegate`는 `System.Delegate`에서, 그것은 `System.Object`에서 파생된다.

```text
System.Object
   └─ System.Delegate               (추상, ICloneable·ISerializable)
        └─ System.MulticastDelegate (추상)
             └─ Transformer          (sealed, 컴파일러 생성)
             └─ Func<int,int>        (sealed)
             └─ Action               (sealed)
```

왜 둘인가. **역사적 이유이고, 유감스러운 설계다.** 원래 의도는 "단일 대상 델리게이트"와 "다중 대상 델리게이트"를 나누는 것이었지만, 결국 모든 델리게이트가 멀티캐스트가 되면서 구분이 무의미해졌다. 지금은 클래스가 하나만 있어야 했다.

그런데도 둘 다 알아야 한다. **정적 메서드 `Combine`과 `Remove`가 `Delegate` 쪽에 있기 때문이다.** 실무에서 델리게이트를 다루다 보면 `MulticastDelegate`가 아니라 `Delegate`에 정의된 멤버를 쓰게 되는 일이 자주 생긴다.

| 멤버 | 정의 위치 | 종류 | 역할 |
|---|---|---|---|
| `Target` | `Delegate` | 인스턴스 속성 | 인스턴스 메서드 대상이면 그 객체, 정적 메서드 대상이면 `null` |
| `Method` | `Delegate` | 인스턴스 속성 | 대상 메서드의 `MethodInfo` |
| `Combine(Delegate, Delegate)` | `Delegate` | **정적** | 두 델리게이트를 이어 붙인 새 델리게이트 반환 |
| `Remove(Delegate, Delegate)` | `Delegate` | **정적** | 호출 목록에서 마지막 일치 항목을 뺀 새 델리게이트 반환 |
| `RemoveAll(Delegate, Delegate)` | `Delegate` | **정적** | 일치하는 항목을 모두 뺀 새 델리게이트 반환 |
| `DynamicInvoke(object[])` | `Delegate` | 인스턴스 | 컴파일 타임에 시그니처를 모를 때 리플렉션으로 호출 |
| `GetInvocationList()` | `Delegate`(`MulticastDelegate`에서 `sealed override`) | 인스턴스 | 체인의 각 델리게이트를 담은 `Delegate[]` 반환 |
| `operator ==` / `!=` | 양쪽 | 정적 | 대상과 메서드가 같은지 비교 |
| `Invoke(...)` | 각 델리게이트 타입 | 인스턴스 | 컴파일러가 생성. 실제 호출 |

`Target`과 `Method`로 델리게이트가 무엇을 가리키는지 들여다볼 수 있다.

```csharp
public delegate void ProgressReporter (int percentComplete);

class MyReporter
{
    public string Prefix = "";
    public void ReportProgress (int percentComplete)
        => Console.WriteLine (Prefix + percentComplete);
}

var r = new MyReporter { Prefix = "%Complete: " };
ProgressReporter p = r.ReportProgress;

p (99);                             // %Complete: 99
Console.WriteLine (p.Target == r);  // True
Console.WriteLine (p.Method);       // Void ReportProgress(Int32)

r.Prefix = "";
p (99);                             // 99  — 대상 객체의 상태 변화가 그대로 보인다
```

마지막 두 줄이 중요하다. 델리게이트는 **메서드 호출 결과를 복사해 두는 것이 아니라 객체를 참조**한다. 대상 객체의 상태가 바뀌면 다음 호출의 결과가 바뀐다.

### 델리게이트 객체의 필드 — `_target`과 `_methodPtr`

델리게이트 인스턴스가 실제로 무엇을 담고 있는지가 이 절의 핵심이다. `MulticastDelegate`와 그 부모 `Delegate`가 가진 비공개 필드 중 셋이 결정적이다.

| 필드 | 타입 | 담는 것 |
|---|---|---|
| `_target` | `System.Object` | **정적 메서드를 감싸면 `null`.** 인스턴스 메서드를 감싸면 그 메서드의 암시적 `this`로 넘길 객체 |
| `_methodPtr` | `System.IntPtr` | 호출할 메서드를 식별하는 내부 정수(메서드 항목 주소) |
| `_invocationList` | `System.Object` | **보통 `null`.** 체인을 만들면 델리게이트 배열을 가리킨다 |

`_invocationList`와 함께 유효 길이를 담는 `_invocationCount`도 있다. 이 이름들은 런타임 구현 세부사항이고 비공개이므로 코드에서 참조할 수 없다 — 리플렉션으로 억지로 읽는 것도 하지 마라. 여기서는 **동작을 설명하기 위한 모델**로만 쓴다.

이제 두 줄을 보자.

```csharp
Transformer tStatic   = Test.Square;            // 정적 메서드
Transformer tInstance = new Test().Cube;        // 인스턴스 메서드
```

메모리는 이렇게 된다.

```text
                    ┌──────────────────────────────┐
   tStatic ────────▶│ Transformer 인스턴스 (힙)     │
                    ├──────────────────────────────┤
                    │ _target        = null        │◀── 정적이므로 수신자 없음
                    │ _methodPtr     = Test.Square │
                    │ _invocationList= null        │◀── 단일 대상
                    └──────────────────────────────┘

                    ┌──────────────────────────────┐        ┌───────────────┐
   tInstance ──────▶│ Transformer 인스턴스 (힙)     │        │ Test 객체(힙) │
                    ├──────────────────────────────┤        ├───────────────┤
                    │ _target        = ────────────┼───────▶│ (인스턴스 상태)│
                    │ _methodPtr     = Test.Cube   │        └───────────────┘
                    │ _invocationList= null        │              ▲
                    └──────────────────────────────┘              │
                                                        델리게이트가 살아 있는 한
                                                        이 객체도 수집되지 않는다
```

이 그림이 이 장의 절반을 설명한다.

- 델리게이트는 **메서드 하나와 객체 하나를 묶은 쌍**이다.
- 정적 메서드를 가리키면 객체 자리는 비어 있다.
- 인스턴스 메서드를 가리키면 **델리게이트가 그 객체를 붙잡는다.** 델리게이트의 수명이 곧 대상 객체 수명의 하한이 된다. 이벤트 구독이 메모리 누수를 만드는 원리가 정확히 이것이다(27.6절).

### 호출은 `Invoke` 호출이다

`t(3)`은 문법 설탕이다. 컴파일러는 이렇게 바꾼다.

```csharp
t.Invoke (3);
```

두 표현은 완전히 같은 IL을 낳는다. IL을 보면 확실해진다.

```il
IL_0007:  ldarg.2                                    // 델리게이트 변수 로드
IL_0008:  ldloc.0                                    // 인수 로드
IL_0009:  callvirt   instance int32 Transformer::Invoke(int32)
```

> **📌 `sealed` 클래스인데 왜 `callvirt`인가**
>
> `Invoke`는 메타데이터상 `virtual final`로 선언된다. 그래서 `callvirt`가 나온다. `callvirt`는 가상 디스패치의 의미도 있지만 **수신자에 대한 `null` 검사**의 의미도 있다 — C# 컴파일러가 인스턴스 메서드 호출에 `call` 대신 `callvirt`를 즐겨 쓰는 이유가 그것이다.
>
> 실제로 델리게이트가 `null`인 상태에서 호출하면 `NullReferenceException`이 난다. `null` 검사 없이 델리게이트를 부르는 코드는 그래서 위험하다. `?.Invoke(...)` 관용구를 쓰는 이유다(10.10절, 27.5절).

> **⚠️ `Invoke`는 왜 직접 호출할 일이 생기는가**
>
> `t(3)`으로 쓸 수 있다면 `t.Invoke(3)`은 쓸 일이 없어 보인다. 그런데 `null` 조건 연산자와 결합할 때는 **반드시** 명시해야 한다.
>
> ```csharp
> handler?.Invoke (arg);       // 올바르다
> handler?(arg);               // 문법 오류 — 이런 문법은 없다
> ```
>
> `?.` 뒤에는 멤버 접근이 와야 하는데 `(arg)`는 멤버가 아니다. 그래서 실무 코드에서 `Invoke`를 명시적으로 쓰는 자리가 남는다.

### `BeginInvoke` / `EndInvoke` — .NET Framework의 유물

컴파일러가 델리게이트 타입에 `BeginInvoke`/`EndInvoke`를 함께 생성한다는 사실은 위에서 봤다. 이 둘은 .NET Framework의 **비동기 프로그래밍 모델(APM)** 의 일부였다. 델리게이트를 스레드 풀에서 비동기로 실행하고 `IAsyncResult`로 결과를 회수하는 패턴이다.

> **⚠️ .NET(Core 계열)에서 `BeginInvoke`는 컴파일되지만 실행되지 않는다**
>
> 이 메서드들은 여전히 **생성되므로 컴파일 오류가 나지 않는다.** 그러나 .NET Core·.NET 5 이상에서 호출하면 런타임에 실패한다(현재 구현은 플랫폼 미지원 예외를 던진다). 컴파일러가 잡아 주지 않는 종류의 사고라 더 위험하다.
>
> .NET Framework 코드를 .NET으로 이식할 때 이 패턴이 남아 있으면 **테스트가 그 경로를 지나가야만** 드러난다. 대체재는 태스크 기반 비동기 패턴이다(46장·47장).

### 타입 안전성 — 컴파일러가 지키는 계약

델리게이트의 존재 이유 중 하나가 타입 안전성이다.

```csharp
public delegate int BinaryOp (int x, int y);

public class SimpleMath
{
    public static int Add (int x, int y) => x + y;
    public static int SquareNumber (int a) => a * a;
}

BinaryOp b1 = SimpleMath.Add;            // OK
BinaryOp b2 = SimpleMath.SquareNumber;   // 컴파일 오류 CS0123
```

시그니처가 맞지 않으면 컴파일러가 막는다. 관리되지 않는 함수 포인터와 결정적으로 갈리는 지점이다.

> **📌 접근성은 델리게이트를 만드는 쪽 기준으로 검사된다**
>
> `private` 메서드를 가리키는 델리게이트를 만들어 **다른 타입의 코드에 넘겨 호출하게 하는 것은 합법이다.** 접근성 검사는 델리게이트 객체를 **생성하는 시점에** 생성하는 코드의 권한으로 이루어지고, 호출 시점에는 다시 검사하지 않는다.
>
> 이것은 구멍이 아니라 설계다. 콜백을 넘긴다는 것은 "이 동작을 호출할 권한을 준다"는 명시적 행위다. 다만 **넘기는 델리게이트가 무엇을 할 수 있는지는 넘기는 쪽이 책임진다.**

## 26.2 델리게이트로 플러그인 메서드 작성하기

### 실행 시점에 동작을 꽂아 넣기

델리게이트 변수에는 **런타임에** 메서드가 대입된다. 그래서 "알고리즘의 뼈대는 내가 짜고, 한 조각은 호출자가 채운다"는 구조를 만들 수 있다.

```csharp
delegate int Transformer (int x);

void Transform (int[] values, Transformer t)
{
    for (int i = 0; i < values.Length; i++)
        values[i] = t (values[i]);
}

int Square (int x) => x * x;
int Cube   (int x) => x * x * x;

int[] values = { 1, 2, 3 };
Transform (values, Square);     // 1  4  9
Transform (values, Cube);       // 1  64  729
```

`Transform`은 **고차 함수(higher-order function)** 다. 함수를 인수로 받는 함수를 그렇게 부른다. 함수를 반환하는 메서드도 마찬가지다.

이 구조가 주는 것은 하나다. **`Transform`을 고치지 않고 동작을 바꿀 수 있다.** 변환 규칙이 열 개로 늘어도 `Transform`은 그대로다. 이것이 24장에서 본 컬렉션 API가, 그리고 29장·30장에서 볼 LINQ 연산자가 전부 델리게이트를 받는 이유다.

| BCL이 델리게이트로 꽂아 넣게 하는 것 | 대표 API | 델리게이트 타입 |
|---|---|---|
| 조건 판정 | `List<T>.FindAll`, `Array.FindAll` | `Predicate<T>` |
| 순서 결정 | `List<T>.Sort`, `Array.Sort` | `Comparison<T>` |
| 원소 변환 | `Array.ConvertAll` | `Converter<TIn,TOut>` |
| 원소별 동작 | `List<T>.ForEach`, `Array.ForEach` | `Action<T>` |
| 지연 생성 | `Lazy<T>`, `ConcurrentDictionary.GetOrAdd` | `Func<T>`, `Func<TKey,TValue>` |
| 작업 큐잉 | `ThreadPool.QueueUserWorkItem` | `WaitCallback` |
| 타이머 만료 | `System.Threading.Timer` | `TimerCallback` |

### 진행 상황 보고 — 콜백의 전형

오래 걸리는 작업이 호출자에게 진행 상황을 알리는 구조를 보자. 이 예제는 이 장 후반의 멀티캐스트·클로저 논의에서 계속 재사용한다.

```csharp
public delegate void ProgressReporter (int percentComplete);

public class Util
{
    public static void HardWork (ProgressReporter p)
    {
        for (int i = 0; i < 10; i++)
        {
            p (i * 10);                              // 델리게이트 호출
            System.Threading.Thread.Sleep (100);     // 오래 걸리는 일을 흉내
        }
    }
}
```

`Util.HardWork`는 콘솔이 무엇인지, 파일이 무엇인지, UI가 무엇인지 모른다. 그저 `p`를 부른다. 어디에 보고할지는 호출자가 정한다.

```csharp
Util.HardWork (WriteProgressToConsole);

void WriteProgressToConsole (int percentComplete)
    => Console.WriteLine (percentComplete);
```

### 캡슐화 — 델리게이트 필드를 공개하지 마라

실무에서 더 흔한 형태는 델리게이트를 **필드로 보관**하는 것이다. 자동차가 엔진 상태를 외부에 알리는 예를 보자.

```csharp
public class Car
{
    public int CurrentSpeed { get; set; }
    public int MaxSpeed { get; set; } = 100;
    private bool _carIsDead;

    // 1) 델리게이트 타입 정의
    public delegate void CarEngineHandler (string msgForCaller);

    // 2) 그 타입의 필드 — private이다
    private CarEngineHandler _listOfHandlers;

    // 3) 등록 창구
    public void RegisterWithCarEngine (CarEngineHandler methodToCall)
        => _listOfHandlers += methodToCall;

    public void UnRegisterWithCarEngine (CarEngineHandler methodToCall)
        => _listOfHandlers -= methodToCall;

    // 4) 적절한 시점에 호출
    public void Accelerate (int delta)
    {
        if (_carIsDead)
        {
            _listOfHandlers?.Invoke ("Sorry, this car is dead...");
            return;
        }

        CurrentSpeed += delta;

        if (MaxSpeed - CurrentSpeed == 10)
            _listOfHandlers?.Invoke ("Careful buddy! Gonna blow!");

        if (CurrentSpeed >= MaxSpeed)
            _carIsDead = true;
        else
            Console.WriteLine ($"CurrentSpeed = {CurrentSpeed}");
    }
}
```

호출하는 쪽은 이렇다.

```csharp
Car c1 = new Car { CurrentSpeed = 10 };
c1.RegisterWithCarEngine (OnCarEngineEvent);

for (int i = 0; i < 6; i++)
    c1.Accelerate (20);

static void OnCarEngineEvent (string msg)
    => Console.WriteLine ($"*** Message From Car Object ***\n=> {msg}");
```

`_listOfHandlers?.Invoke(...)`의 `?.`가 중요하다. 아무도 등록하지 않으면 필드는 `null`이고, 그대로 호출하면 `NullReferenceException`이 난다.

> **⚠️ 델리게이트 필드를 `public`으로 열면 캡슐화가 무너진다**
>
> `private CarEngineHandler _listOfHandlers`를 `public CarEngineHandler ListOfHandlers`로 바꾸는 순간 호출자는 두 가지를 할 수 있게 된다.
>
> ```csharp
> c1.ListOfHandlers = MyOnlyHandler;   // (1) = 대입으로 남의 구독을 전부 날린다
> c1.ListOfHandlers ("가짜 메시지");    // (2) 발행자가 아닌데 발행한다
> ```
>
> (1)은 `+=`가 아니라 `=`를 썼을 때 조용히 일어난다. 실수 한 글자로 다른 컴포넌트의 구독이 사라지고, 아무 오류도 나지 않는다. (2)는 "이 알림은 `Car`만 낼 수 있다"는 계약을 깬다.
>
> **이 두 구멍을 언어 차원에서 막는 것이 `event` 키워드다.** `event`를 붙이면 외부에서 `+=`/`-=`만 가능해지고, `=` 대입과 직접 호출은 컴파일 오류가 된다. 27.1절에서 컴파일 결과까지 판다.

> **💡 델리게이트 매개변수는 "동작"이라는 이름을 붙여라**
>
> 델리게이트 매개변수 이름을 `func`, `callback`, `action`처럼 타입에서 온 이름으로 짓는 코드가 많다. 읽는 사람에게 아무 정보도 주지 않는다. **무엇을 하는 동작인지**로 이름을 지어라 — `transformer`, `keySelector`, `onProgress`, `shouldRetry`. BCL이 `Func<TSource,TKey> keySelector`, `Func<TSource,bool> predicate`처럼 짓는 이유다.

## 26.3 인스턴스 대상 vs 정적 대상, 메서드 그룹 변환

### `_target`에 무엇이 들어가는가

26.1절의 그림을 코드로 확인하자.

```csharp
class Test
{
    public static int SquareStatic (int x) => x * x;
    public        int SquareInstance (int x) => x * x;
}

Transformer a = Test.SquareStatic;

var test = new Test();
Transformer b = test.SquareInstance;

Console.WriteLine (a.Target == null);   // True  — 정적 대상
Console.WriteLine (b.Target == test);   // True  — 인스턴스 대상
Console.WriteLine (a.Method.Name);      // SquareStatic
Console.WriteLine (b.Method.Name);      // SquareInstance
```

| 대상 종류 | `_target` | `Target` 속성 | 대상 객체 수명 |
|---|---|---|---|
| 정적 메서드 | `null` | `null` | 해당 없음 |
| 인스턴스 메서드 | 수신자 객체 | 그 객체 | **델리게이트 수명만큼 연장된다** |
| 인스턴스 메서드(구조체) | **박싱된 복사본** | 박싱된 객체 | 박스가 연장된다 |
| 캡처 없는 람다 | 컴파일러 생성 싱글턴 | `<>c` 인스턴스 | 프로세스 수명 |
| 캡처 있는 람다 | 디스플레이 클래스 인스턴스 | `<>c__DisplayClass...` | 델리게이트 수명만큼 연장된다 |

세 번째 행이 조용한 함정이다.

> **⚠️ 구조체의 인스턴스 메서드를 델리게이트로 만들면 박싱된다**
>
> ```csharp
> struct Counter
> {
>     public int Value;
>     public void Increment() => Value++;
> }
>
> var c = new Counter();
> Action a = c.Increment;      // 여기서 c가 박싱된다
> a(); a(); a();
> Console.WriteLine (c.Value); // 0 — 원본은 그대로다
> ```
>
> 델리게이트의 `_target`은 `object` 타입이다. 값 타입 수신자를 담으려면 **박싱할 수밖에 없다.** 이후 세 번의 호출은 전부 박스 안의 복사본을 증가시킨다. 원본 `c`는 손대지 않는다.
>
> 값 타입의 복사 의미론(16장)과 박싱(15장)이 결합해 만드는 전형적인 사고다. 구조체의 메서드를 델리게이트로 넘길 일이 있다면 그 순간 "여기서 힙 할당이 하나 생기고 값이 복사된다"를 기억해야 한다.

> **⚠️ 대상 객체 수명 연장은 누수의 씨앗이다**
>
> 인스턴스 메서드를 가리키는 델리게이트는 GC 입장에서 대상 객체에 대한 **강한 참조**다. 수명이 긴 객체(정적 필드에 담긴 이벤트 발행자, 캐시, 싱글턴 서비스)에 짧게 살아야 할 객체의 메서드를 등록하면, 그 짧은 객체는 영원히 수집되지 않는다.
>
> 화면 하나가 서비스의 알림을 구독했는데 화면을 닫을 때 해제하지 않으면 화면 전체가 메모리에 남는다. 이 문제와 해법(약한 이벤트 패턴)은 27.6절·27.7절에서 다룬다.

### 컴파일 결과 — `ldftn`과 `ldvirtftn`

델리게이트 생성이 IL에서 어떻게 보이는지가 두 경우의 차이를 정확히 드러낸다.

**정적 메서드 대상:**

```il
IL_0000:  ldnull                                            // _target = null
IL_0001:  ldftn      int32 Test::SquareStatic(int32)        // _methodPtr
IL_0007:  newobj     instance void Transformer::.ctor(object, native int)
IL_000c:  stloc.0
```

**비가상 인스턴스 메서드 대상:**

```il
IL_0000:  newobj     instance void Test::.ctor()
IL_0005:  stloc.0
IL_0006:  ldloc.0                                           // _target = test
IL_0007:  ldftn      instance int32 Test::SquareInstance(int32)
IL_000d:  newobj     instance void Transformer::.ctor(object, native int)
```

**가상 메서드 대상:**

```il
IL_0006:  ldloc.0
IL_0007:  dup                                               // 스택에 수신자 두 개
IL_0008:  ldvirtftn  instance string Base::Describe()       // 하나를 소비해 실제 구현 주소를 얻는다
IL_000e:  newobj     instance void class [System.Runtime]System.Func`1<string>::.ctor(object,
                                                                                      native int)
```

`ldvirtftn`은 **수신자의 실제 타입에 맞는 구현의 주소**를 스택에서 꺼낸 객체로부터 구한다. `dup`이 필요한 이유가 여기 있다 — `ldvirtftn`이 수신자를 소비해 버리므로, 생성자에 넘길 몫을 미리 복제해 둔다.

이 구분이 실제 동작 차이를 만든다.

```csharp
class Base    { public virtual  string Describe() => "Base"; }
class Derived : Base { public override string Describe() => "Derived"; }

Base obj = new Derived();
Func<string> f = obj.Describe;
Console.WriteLine (f());          // Derived — 가상 디스패치가 델리게이트에도 적용된다
```

델리게이트를 만드는 시점의 정적 타입이 `Base`여도, 바인딩은 `Derived.Describe`로 된다. `ldvirtftn`이 그렇게 하기 때문이다.

### 메서드 그룹 변환

`Transformer t = Square;`에서 `Square`는 괄호도 인수도 없다. 이 표현식을 **메서드 그룹(method group)** 이라 부른다. 이름 하나가 여러 오버로드를 대표할 수 있어 "그룹"이다.

```csharp
Transformer t = Square;
// 다음의 축약형이다
Transformer t = new Transformer (Square);
```

오버로드가 여러 개면 **대상 델리게이트 타입의 시그니처**를 보고 컴파일러가 고른다.

```csharp
int  Parse (string s) => int.Parse (s);
long Parse (string s, int radix) => Convert.ToInt64 (s, radix);

Func<string,int>       f1 = Parse;   // 첫 번째를 고른다
Func<string,int,long>  f2 = Parse;   // 두 번째를 고른다
```

> **⚠️ 메서드 그룹은 그 자체로 타입이 없다**
>
> ```csharp
> var x = Square;             // 컴파일 오류 — 메서드 그룹에는 자연 타입이 없다
> Console.WriteLine (Square); // 컴파일 오류
> ```
>
> 메서드 그룹은 **대상 타입이 정해져야** 델리게이트로 변환된다. `var`에는 대상 타입이 없으므로 실패한다. 반면 람다는 ※C# 10부터 자연 타입을 가진다(26.9절) — 이 비대칭이 헷갈리는 지점이다.
>
> ```csharp
> var y = (int x) => x * x;   // OK — Func<int,int>로 추론된다 ※C# 10
> ```

### 메서드 그룹 변환의 캐싱 ※C# 11

메서드 그룹 변환은 델리게이트 객체를 **하나 할당한다.** 루프 안이나 자주 불리는 메서드 안에서 같은 메서드 그룹을 반복해 변환하면, 매번 힙 할당이 하나씩 생긴다는 뜻이었다.

```csharp
foreach (var item in items)
    Process (item, Handler);       // C# 10까지: 반복마다 델리게이트 객체 생성
```

※C# 11부터 컴파일러는 **메서드 그룹 변환의 결과를 숨은 정적 필드에 캐시**한다. 개념적으로 다음과 같은 코드로 바뀐다.

```csharp
// 컴파일러가 만드는 캐시 필드 (개념적 표현)
private static Handler <>O__cache;

if (<>O__cache is null)
    <>O__cache = new Handler (Handler);
Process (item, <>O__cache);
```

IL로는 람다 캐싱과 같은 형태다.

```il
ldsfld     class Handler Program/'<>O'::'<0>__Handler'
dup
brtrue.s   IL_001a
pop
ldnull
ldftn      void Program::Handler(int32)
newobj     instance void Handler::.ctor(object, native int)
dup
stsfld     class Handler Program/'<>O'::'<0>__Handler'
IL_001a:  // 스택 위에 캐시된 델리게이트가 있다
```

> **⚠️ 캐싱은 수신자가 없을 때만 가능하다**
>
> 이 최적화는 **정적 메서드 그룹**에 적용된다. 인스턴스 메서드 그룹은 캐시할 수 없다. `obj.Handler`의 델리게이트는 `obj`를 붙잡아야 하는데, `obj`가 호출마다 다를 수 있기 때문이다.
>
> ```csharp
> foreach (var x in items)
>     Register (x.OnDone);       // x마다 다른 델리게이트 — 캐시 불가, 매번 할당
> ```
>
> 핫 패스에서 인스턴스 메서드 그룹을 반복 변환한다면 **직접 캐시**해야 한다. 변환 결과를 필드에 한 번 담아 두고 재사용하는 것이다.

> **📌 캐싱은 "허용"이지 "보장"이 아니다**
>
> 이 최적화는 언어 명세가 컴파일러에게 **허용**하는 것이고, 특정 버전의 Roslyn이 실제로 어떤 경우에 캐시할지는 구현 사항이다. 성능이 중요한 코드에서는 컴파일러의 선의에 기대지 말고 `ildasm`이나 벤치마크로 확인하라.
>
> 그리고 캐시에는 대가가 있다. **캐시된 델리게이트 객체는 절대 수집되지 않는다.** 정적 필드가 붙잡고 있기 때문이다. 할당 횟수를 줄이는 대신 상주 메모리가 아주 조금 늘어난다.

### 성능 — 델리게이트 호출은 얼마나 비싼가

델리게이트 호출은 **간접 호출**이다. 대상 주소가 실행 시점에야 정해지므로 다음 비용이 붙는다.

| 항목 | 직접 호출 | 델리게이트 호출 |
|---|---|---|
| 대상 결정 | 컴파일/JIT 시점 | 실행 시점 (`_methodPtr` 로드) |
| 인라인 | 가능 | 일반적으로 불가 |
| 분기 예측 | 정적 | 간접 분기 예측에 의존 |
| 추가 로드 | 없음 | 델리게이트 객체 필드 접근 |
| 멀티캐스트 검사 | 없음 | `_invocationList` 확인 |

> **📌 델리게이트 호출도 인라인될 수 있다 ※.NET 8**
>
> "델리게이트는 절대 인라인되지 않는다"는 말은 이제 정확하지 않다. 동적 PGO(profile-guided optimization)가 기본 활성화된 ※.NET 8부터, JIT은 실행 중 관찰한 호출 대상 분포를 근거로 **추측 인라인(guarded devirtualization)** 을 시도할 수 있다. 대상이 사실상 하나로 고정된 호출 지점이라면 "타입이 예상과 같으면 인라인된 코드로, 아니면 원래 경로로"라는 분기가 만들어진다.
>
> 다만 이건 **최적화의 가능성**이지 보장이 아니다. 호출 대상이 실제로 다양하면 추측이 빗나가 그대로 간접 호출로 돌아간다. 설계 판단을 이 최적화에 걸지 마라.

> **💡 델리게이트 호출 비용이 문제가 되는 지점은 좁다**
>
> 나노초 단위 오버헤드가 문제 되는 곳은 **매우 짧은 작업을 매우 많이 반복**하는 자리뿐이다. 원소당 몇 나노초짜리 작업을 수백만 번 도는 루프에서 델리게이트를 부르면 델리게이트가 작업보다 비쌀 수 있다. 그 밖의 자리에서는 측정 불가능한 차이다.
>
> 진짜 비용은 호출이 아니라 **할당**에 있다. 그건 26.11절과 63.9절의 주제다.

## 26.4 멀티캐스트 델리게이트 — 체이닝, 예외 전파, 반환값

### 모든 델리게이트는 멀티캐스트다

`MulticastDelegate`라는 이름 그대로, **모든 델리게이트 인스턴스는 대상 메서드를 여러 개 가질 수 있다.** 단일 대상만 가리키는 델리게이트 타입 같은 것은 없다. 이건 선택이 아니라 역사적으로 굳어진 사실이고, 뒤에서 볼 여러 함정의 뿌리다.

`+`와 `+=`가 대상을 추가한다.

```csharp
ProgressReporter p = WriteProgressToConsole;
p += WriteProgressToFile;

Util.HardWork (p);      // 두 메서드가 모두 호출된다
```

`-`와 `-=`가 제거한다.

```csharp
p -= WriteProgressToConsole;    // 이제 파일에만 기록된다
```

`null`인 델리게이트에 `+=`를 쓰는 것도 정상 동작한다. `null + x`는 `x`다.

```csharp
ProgressReporter p = null;
p += WriteProgressToConsole;    // p = WriteProgressToConsole 과 같다
```

대칭적으로, 대상이 하나뿐인 델리게이트에서 그 하나를 `-=`로 빼면 결과는 `null`이 된다.

### `+=`는 `Delegate.Combine`이다

여기가 이 절의 핵심이다. C# 컴파일러는 델리게이트에 대한 `+`, `-`, `+=`, `-=`를 **`System.Delegate`의 정적 메서드 호출**로 바꾼다.

```csharp
p += WriteProgressToFile;
```

```il
ldloc.0                                                    // p
ldnull
ldftn      void Program::WriteProgressToFile(int32)
newobj     instance void ProgressReporter::.ctor(object, native int)
call       class [System.Runtime]System.Delegate
             [System.Runtime]System.Delegate::Combine(class System.Delegate,
                                                       class System.Delegate)
castclass  ProgressReporter
stloc.0                                                    // p에 다시 대입
```

직접 써도 완전히 같다.

```csharp
p = (ProgressReporter) Delegate.Combine (p, WriteProgressToFile);
p = (ProgressReporter) Delegate.Remove  (p, WriteProgressToFile);
```

`Combine`과 `Remove`가 `Delegate` 타입을 받고 `Delegate`를 반환하므로 **캐스트가 필요하다.** `+=` 연산자는 이 캐스트까지 대신 넣어 준다.

> **⚠️ 델리게이트는 불변이다 — `+=`는 새 인스턴스를 만든다**
>
> 이 사실이 멀티캐스트 델리게이트를 이해하는 열쇠다. `Combine`은 기존 델리게이트를 **수정하지 않는다.** 새 델리게이트 객체를 만들어 반환하고, `+=`는 그 결과를 변수에 **다시 대입**한다.
>
> ```csharp
> ProgressReporter a = WriteProgressToConsole;
> ProgressReporter b = a;          // 같은 객체를 가리킨다
> a += WriteProgressToFile;        // a는 새 객체를, b는 옛 객체를 가리킨다
>
> Console.WriteLine (ReferenceEquals (a, b));   // False
> ```
>
> `b`는 여전히 콘솔 출력 하나만 가진 옛 델리게이트를 가리킨다. **델리게이트 필드를 다른 변수에 복사해 두었다가 나중에 호출하면, 그 사이의 구독 변경이 반영되지 않는다.** 반대로 이 불변성 덕분에 "발행 직전에 필드를 지역 변수로 복사"하는 스레드 안전 관용구가 성립한다(27.5절).

### 체인의 내부 구조

`Combine`이 실제로 무엇을 만드는지 보자. 델리게이트 세 개를 이어 붙이는 과정이다.

```csharp
Feedback fb1 = FeedbackToConsole;      // 정적
Feedback fb2 = FeedbackToMsgBox;       // 정적
Feedback fb3 = p.FeedbackToFile;       // 인스턴스

Feedback chain = null;
chain = (Feedback) Delegate.Combine (chain, fb1);
chain = (Feedback) Delegate.Combine (chain, fb2);
chain = (Feedback) Delegate.Combine (chain, fb3);
```

첫 번째 `Combine(null, fb1)`은 새 객체를 만들지 않고 **`fb1`을 그대로 반환한다.** 그래서 이 시점에 `chain`과 `fb1`은 같은 객체다.

두 번째 `Combine`부터가 다르다.

```text
1단계: chain = Combine(null, fb1)

  chain ─┐
         ▼
  fb1 ─▶ ┌───────────────────────────┐
         │ _target        = null      │
         │ _methodPtr     = ToConsole │
         │ _invocationList= null      │   ← 단일 대상 델리게이트
         └───────────────────────────┘

2단계: chain = Combine(chain, fb2)   ← 새 델리게이트 객체가 생긴다

  chain ─▶ ┌───────────────────────────┐
           │ _target        = (무의미)  │
           │ _methodPtr     = (무의미)  │
           │ _invocationList= ─────────┼──▶ Delegate[2]
           └───────────────────────────┘      [0] ──▶ fb1
                                               [1] ──▶ fb2

3단계: chain = Combine(chain, fb3)   ← 또 새 객체, 배열도 새로 만든다

  chain ─▶ ┌───────────────────────────┐
           │ _invocationList= ─────────┼──▶ Delegate[3]
           └───────────────────────────┘      [0] ──▶ fb1
                                               [1] ──▶ fb2
    2단계의 델리게이트와 Delegate[2]는            [2] ──▶ fb3
    이제 GC 대상이다
```

정리하면 이렇다.

- 체인 델리게이트의 `_invocationList`는 **개별 델리게이트들의 배열**을 가리킨다.
- 체인 델리게이트 자신의 `_target`/`_methodPtr`은 이 논의에서 의미가 없다.
- 배열의 각 원소는 `_invocationList`가 `null`인 **단일 대상 델리게이트**다. 체인이 중첩되지는 않는다.
- **결합할 때마다 델리게이트 객체 하나와 배열 하나가 새로 할당된다.**

> **⚠️ 핸들러 N개를 붙이면 할당이 O(N²)이다**
>
> `+=`를 N번 하면 길이 2, 3, 4, …, N짜리 배열이 차례로 만들어지고 매번 이전 내용이 복사된다. 총 복사 비용은 N²에 비례한다. 핸들러가 수천 개 붙는 구조 — 예를 들어 컬렉션의 모든 원소가 하나의 발행자를 구독하는 설계 — 는 구독 단계에서만 눈에 띄게 느려질 수 있다.
>
> 이 규모가 되면 델리게이트 체인 대신 **구독자 리스트를 직접 관리**하는 편이 낫다. `List<Action>`에 담고 호출할 때 순회하면 `+=`는 상수 시간(분할 상환)이 된다.

### 호출 — `Invoke`가 하는 일

체인 델리게이트를 호출하면 어떻게 되는가. 컴파일러가 생성한 `Invoke`의 동작은 개념적으로 다음과 같다.

```csharp
// 실제 IL이 아니라 동작을 설명하는 의사 C# 코드다
public void Invoke (int value)
{
    Delegate[] list = _invocationList as Delegate[];
    if (list != null)
    {
        foreach (Feedback d in list)
            d (value);              // 배열 순서대로 하나씩 호출
    }
    else
    {
        // 단일 대상: _target을 this로 삼아 _methodPtr을 호출한다
        // (이 부분은 C#으로 표현할 수 없다)
    }
}
```

여기서 세 가지 성질이 곧바로 따라 나온다.

1. **호출 순서는 추가한 순서다.** 배열에 순서대로 들어가고 순서대로 도니까.
2. **반환값은 마지막 것만 남는다.** 앞선 호출의 결과는 덮어써진다.
3. **예외가 나면 거기서 멈춘다.** `Invoke`는 아무것도 `catch`하지 않는다.

### 반환값 — 마지막 하나만 살아남는다

반환 타입이 `void`가 아닌 델리게이트를 멀티캐스트하면 이렇게 된다.

```csharp
Func<bool> check = CheckWithUser;
check += CheckWithSystem;

bool result = check();     // CheckWithSystem의 결과만 반환된다
                           // CheckWithUser도 호출되지만 그 결과는 버려진다
```

사용자에게 물어보고 시스템에도 물어보는 두 검사를 붙였는데, **사용자가 "중단"이라고 답해도 그 답은 사라진다.** 시스템 쪽 결과만 반환된다.

> **⚠️ 반환값이 있는 델리게이트를 멀티캐스트하지 마라**
>
> 이 동작은 버그가 아니라 명세다. 그러나 이 명세가 유용한 경우는 거의 없다. **반환값이 있는 델리게이트 타입을 여러 대상에 붙이는 코드는 십중팔구 잘못된 코드다.**
>
> 두 가지 중 하나를 골라야 한다.
>
> - 대상이 하나뿐임을 보장한다(예: 필드가 아니라 매개변수로만 받는다).
> - 결과를 모아야 한다면 `GetInvocationList()`로 **직접 순회**한다(아래).
>
> 이벤트처럼 여럿이 듣는 구조는 반환 타입을 `void`로 두는 것이 표준이다(27.2절).

### 예외 — 나머지는 호출되지 않는다

더 위험한 쪽은 예외다.

```csharp
GetStatus getStatus = null;
getStatus += new Light().SwitchPosition;    // 정상 동작
getStatus += new Fan().Speed;               // InvalidOperationException을 던진다
getStatus += new Speaker().Volume;          // 정상 동작

Console.WriteLine (getStatus());            // 예외가 호출자에게 전파된다
```

결과는 이렇다. `Light`의 메서드는 호출된다. `Fan`의 메서드가 예외를 던진다. 그 예외는 `Invoke`의 루프를 뚫고 나가 호출자에게 전파된다. **`Speaker`의 메서드는 아예 호출되지 않는다.**

> **⚠️ 구독자 하나의 예외가 다른 구독자를 침묵시킨다**
>
> 구독자는 서로를 모른다. 그게 이 모델의 장점이다. 그런데 예외 전파 때문에 **서로를 죽일 수는 있다.** 로깅 핸들러 하나가 디스크 가득 참으로 실패하면 그 뒤에 등록된 감사 핸들러·복구 핸들러가 조용히 실행되지 않는다. 순서에 따라 증상이 달라지므로 재현조차 어렵다.
>
> 이 문제는 발행자가 자신을 방어하는 문제가 아니다. **다른 구독자를 방어하는 문제**다. 발행자가 신뢰할 수 없는 구독자를 상대한다면 아래의 순회 호출이 필수다.

### 해법 — `GetInvocationList()`로 직접 순회하기

`MulticastDelegate.GetInvocationList()`는 체인의 각 델리게이트를 담은 `Delegate[]`를 반환한다. `_invocationList`가 `null`인 단일 대상 델리게이트에 대해서도 **원소 하나짜리 배열**을 반환하므로, 분기 없이 항상 같은 코드로 다룰 수 있다.

```csharp
private static string GetComponentStatusReport (GetStatus status)
{
    if (status == null) return null;

    var report = new StringBuilder();

    foreach (GetStatus one in status.GetInvocationList())
    {
        try
        {
            report.AppendLine (one());              // 개별 호출
        }
        catch (InvalidOperationException e)
        {
            object component = one.Target;
            report.AppendLine (
                $"Failed to get status from " +
                $"{(component == null ? "" : component.GetType() + ".")}" +
                $"{one.Method.Name} — {e.Message}");
        }
    }
    return report.ToString();
}
```

출력은 이렇게 된다.

```text
The light is off
Failed to get status from Fan.Speed — The fan broke due to overheating
The volume is loud
```

**세 구독자가 모두 호출되었고, 실패한 하나는 보고서에 기록되었다.** 이것이 멀티캐스트를 신뢰성 있게 쓰는 유일한 방법이다.

반환값 문제도 같은 방법으로 푼다.

```csharp
public void LengthyOperation (Func<bool> shouldContinue)
{
    foreach (var item in container)
    {
        item.DoLengthyWork();

        bool go = true;
        foreach (Func<bool> one in shouldContinue.GetInvocationList())
            go &= one();                 // 모든 결과를 AND로 모은다

        if (!go) return;
    }
}
```

여기서 **"모두 `true`여야 계속한다"는 의미론을 이 코드가 정의했다는 점**이 중요하다. 델리게이트 자체에는 그런 의미가 없다. 결과를 합치는 규칙은 API를 만드는 사람이 정하고 문서화해야 한다.

예외를 모으려면 이렇게 한다.

```csharp
List<Exception> failures = null;

foreach (Action<int> one in handler.GetInvocationList())
{
    try { one (value); }
    catch (Exception ex) { (failures ??= new List<Exception>()).Add (ex); }
}

if (failures != null)
    throw new AggregateException (failures);
```

> **⚠️ `GetInvocationList()`는 호출할 때마다 배열을 새로 만든다**
>
> 반환되는 배열은 내부 배열의 **복사본**이다. 방어적 복사가 필요하기 때문이다(호출 도중 구독이 바뀌어도 순회가 깨지지 않는다). 대신 호출마다 배열 할당이 하나 생긴다.
>
> 초당 수만 번 발행되는 알림에서 매번 `GetInvocationList()`를 부르면 이 할당이 GC 압력이 된다. 그런 자리에서는 예외 격리를 포기하거나, 애초에 델리게이트 체인이 아닌 구조를 쓰거나, 구독 시점에 배열을 만들어 캐시하는 방법을 검토해야 한다(63.9절).

### `Remove`의 미묘한 규칙

`Delegate.Remove`에는 알아 둘 규칙이 몇 개 있다.

| 규칙 | 동작 |
|---|---|
| 검색 방향 | 호출 목록의 **끝에서 앞으로** 스캔한다 |
| 일치 조건 | `_target`과 `_methodPtr`이 모두 같아야 한다 |
| 중복 등록 | **한 번에 하나만 제거된다.** 두 번 등록했으면 두 번 빼야 한다 |
| 없는 대상 제거 | **아무 일도 일어나지 않는다.** 예외도, 경고도 없다 |
| 체인 제거 | 두 번째 인수가 체인이면 그 **연속된 부분열**의 마지막 출현을 제거한다 |
| 전부 제거 | `Delegate.RemoveAll`이 일치하는 모든 항목을 제거한다 |

세 번째와 네 번째가 실무에서 사고를 만든다.

> **⚠️ 같은 핸들러를 두 번 등록하면 두 번 호출된다**
>
> ```csharp
> p += Handler;
> p += Handler;      // 막지 않는다
> p (50);            // Handler가 두 번 호출된다
> p -= Handler;      // 하나만 빠진다 — 여전히 한 번 호출된다
> ```
>
> "초기화 코드가 두 번 실행되어 알림이 두 번 왔다"는 종류의 버그가 여기서 나온다. 델리게이트는 집합이 아니라 **리스트**다. 중복을 막고 싶다면 등록 창구에서 직접 검사해야 한다.

> **⚠️ 람다는 `-=`로 제거할 수 없다 (사실상)**
>
> ```csharp
> p += x => Console.WriteLine (x);
> p -= x => Console.WriteLine (x);     // 제거되지 않는다
> ```
>
> 두 람다는 소스에서 글자가 같아도 **컴파일러가 만드는 서로 다른 메서드**다. `_methodPtr`이 다르므로 일치하지 않고, `Remove`는 조용히 아무것도 하지 않는다. 캡처가 있는 람다라면 `_target`(디스플레이 클래스 인스턴스)까지 달라서 더욱 불가능하다.
>
> 나중에 해제해야 하는 구독은 **델리게이트를 변수에 담아 두고** 그 변수로 빼야 한다.
>
> ```csharp
> ProgressReporter handler = x => Console.WriteLine (x);
> p += handler;
> // ...
> p -= handler;      // 이건 제거된다
> ```

### 델리게이트의 동등성

`==`와 `Equals`는 대상과 메서드를 비교한다.

```csharp
D d1 = Method1;
D d2 = Method1;
Console.WriteLine (d1 == d2);       // True — 같은 정적 메서드
Console.WriteLine (ReferenceEquals (d1, d2));  // 구현에 따라 다르다
```

멀티캐스트 델리게이트는 **같은 메서드들을 같은 순서로** 참조할 때 같다고 판정된다. 순서가 다르면 다르다.

> **📌 델리게이트 타입이 다르면 `==` 자체가 컴파일되지 않는다**
>
> 시그니처가 같아도 델리게이트 타입이 다르면 `==` 비교가 컴파일 오류다. 굳이 비교하려면 양쪽을 `Delegate`로 올려 `Equals`를 부를 수 있지만, 그 결과는 항상 `false`다 — `Delegate.Equals`는 런타임 타입까지 비교하기 때문이다.

## 26.5 제네릭 델리게이트와 `Func` / `Action` / `Predicate`

### 제네릭 델리게이트 타입

델리게이트 타입도 클래스이므로 타입 매개변수를 가질 수 있다.

```csharp
public delegate T Transformer<T> (T arg);

public static void Transform<T> (T[] values, Transformer<T> t)
{
    for (int i = 0; i < values.Length; i++)
        values[i] = t (values[i]);
}
```

이제 `int[]`든 `string[]`든 같은 `Transform`을 쓴다.

```csharp
int[] nums = { 1, 2, 3 };
Transform (nums, x => x * x);           // 1  4  9

string[] names = { "kim", "lee" };
Transform (names, s => s.ToUpper());    // KIM  LEE
```

### `Func`와 `Action` — 델리게이트 타입 폭발의 종결

.NET 초기에는 콜백이 필요한 자리마다 새 델리게이트 타입이 정의되었다. 결과적으로 기반 클래스 라이브러리 하나에만 수십 개의 델리게이트 타입이 생겼다. 그중 몇을 보자.

```csharp
public delegate void WaitCallback (object state);
public delegate void TimerCallback (object state);
public delegate void ContextCallback (object state);
public delegate void SendOrPostCallback (object state);
public delegate void ParameterizedThreadStart (object obj);
```

전부 같은 모양이다. `object` 하나를 받고 `void`를 반환한다. 제네릭이 없던 시절이라 어쩔 수 없었다.

제네릭이 생긴 뒤 .NET은 **일반화된 델리게이트 두 가족**을 `System` 네임스페이스에 넣었다.

```csharp
public delegate void Action();                            // 매개변수 없음
public delegate void Action<in T> (T arg);
public delegate void Action<in T1, in T2> (T1 a1, T2 a2);
// ... T16까지, 총 17개

public delegate TResult Func<out TResult>();
public delegate TResult Func<in T, out TResult> (T arg);
public delegate TResult Func<in T1, in T2, out TResult> (T1 a1, T2 a2);
// ... T16까지, 총 17개
```

`Func`에서 **마지막 타입 인수가 언제나 반환 타입**이다. 이 규칙만 기억하면 읽기 어렵지 않다.

| 델리게이트 | 시그니처 | 정의된 곳 | 변성 |
|---|---|---|---|
| `Action` | `void ()` | `System` | — |
| `Action<T>` | `void (T)` | `System` | `in T` |
| `Action<T1,…,T16>` | `void (T1,…,T16)` | `System` | 전부 `in` |
| `Func<TResult>` | `TResult ()` | `System` | `out TResult` |
| `Func<T,TResult>` | `TResult (T)` | `System` | `in T`, `out TResult` |
| `Func<T1,…,T16,TResult>` | `TResult (T1,…,T16)` | `System` | `in`/`out` |
| `Predicate<T>` | `bool (T)` | `System` | `in T` |
| `Comparison<T>` | `int (T, T)` | `System` | `in T` |
| `Converter<TIn,TOut>` | `TOut (TIn)` | `System` | `in`/`out` |
| `EventHandler` | `void (object, EventArgs)` | `System` | — |
| `EventHandler<TArgs>` | `void (object, TArgs)` | `System` | — |

`Transformer<T>`를 만들 필요 없이 `Func<T,T>`를 쓰면 된다.

```csharp
public static void Transform<T> (T[] values, Func<T,T> transformer)
{
    for (int i = 0; i < values.Length; i++)
        values[i] = transformer (values[i]);
}
```

> **📌 `Func`/`Action`이 없던 시절의 흔적**
>
> BCL의 오래된 API가 `Func`/`Action`이 아니라 전용 델리게이트를 쓰는 것은 순전히 **역사적 이유**다. C#이 처음 나왔을 때는 제네릭 자체가 없었다. `WaitCallback`, `TimerCallback`, `ThreadStart` 같은 이름을 지금 보게 되는 배경이다.
>
> 새 API를 설계한다면 특별한 이유가 없는 한 `Func`/`Action`을 쓰는 것이 권장된다. 타입 수가 줄고, 다른 API와의 조립이 쉬워진다.

### `Func`/`Action`으로 표현할 수 없는 것

전부 대체되지는 않는다. 커스텀 델리게이트가 여전히 필요한 경우는 다음과 같다.

| 필요 | 예 | 이유 |
|---|---|---|
| `ref` / `out` / `in` 매개변수 | `delegate void Filler (ref int slot);` | `Func`/`Action`의 매개변수는 값 전달이다 |
| 포인터 매개변수 | `delegate void Raw (byte* p);` | 제네릭 타입 인수가 될 수 없다 |
| `params` 배열 | `delegate void Log (string fmt, params object[] args);` | `Func`는 `params`를 붙일 수 없다 |
| 매개변수 기본값 | `delegate void Print (string s = "");` | 델리게이트 **타입**의 기본값은 커스텀 타입에만 |
| 타입 매개변수 제약 | `delegate T Make<T>() where T : new();` | `Func<T>`에는 제약을 걸 수 없다 |
| 17개 이상의 매개변수 | — | `T16`까지만 있다 |
| 도메인 이름이 필요할 때 | `ProgressReporter`, `CarEngineHandler` | 가독성과 자기 문서화 |

마지막 항목은 성능이 아니라 설계의 문제다.

> **💡 이름이 계약을 설명한다면 커스텀 델리게이트를 만들어라**
>
> `Func<int,bool>`이라는 타입은 "정수를 받아 bool을 반환한다"만 말한다. `ShouldRetry`라는 델리게이트 타입은 "재시도할지 판단한다"를 말한다. **매개변수 이름과 XML 주석을 델리게이트 선언 한 곳에 모을 수 있다**는 것도 실질적인 이득이다.
>
> 반대로 LINQ 연산자의 `selector`, `predicate`처럼 **의미가 호출 문맥에서 자명한** 자리에는 `Func`/`Action`이 낫다. 커스텀 타입을 만들면 호출자가 그 타입을 알아야 하는 결합이 생긴다.

> **⚠️ `Predicate<T>`와 `Func<T,bool>`은 대입 호환되지 않는다**
>
> ```csharp
> Predicate<int> p = i => i > 0;
> Func<int,bool> f = p;             // 컴파일 오류
> ```
>
> 모양이 같아도 **다른 타입이다.** 26.6절의 규칙이 그대로 적용된다. 이 때문에 `List<T>.FindAll`(`Predicate<T>`를 받는다)에 넘기던 델리게이트 변수를 LINQ의 `Where`(`Func<T,bool>`을 받는다)에 그대로 넘길 수 없다.
>
> 람다를 **직접** 넘기면 두 자리 모두 문제없다. 람다는 타입이 없는 표현식이고 대상 타입에 맞춰 변환되기 때문이다. 문제는 델리게이트를 **변수에 담아 돌려쓸 때** 생긴다.
>
> 굳이 변환하려면 새로 감싸면 된다.
>
> ```csharp
> Func<int,bool> f = new Func<int,bool> (p);   // p를 감싸는 새 델리게이트
> Func<int,bool> g = i => p (i);               // 같은 효과, 람다로
> ```

## 26.6 델리게이트 호환성 규칙

### 타입 호환성 — 구조가 같아도 다르다

델리게이트 타입은 **명목적(nominal)** 이다. 시그니처가 완전히 같아도 서로 다른 타입이면 대입할 수 없다.

```csharp
delegate void D1();
delegate void D2();

D1 d1 = Method1;
D2 d2 = d1;          // 컴파일 오류 CS0029

void Method1() { }
```

이건 제약이 아니라 의도다. `Comparison<T>`와 `Func<T,T,int>`는 모양이 같지만 **의미가 다르다.** 하나는 "순서를 정하는 규칙"이고 다른 하나는 "두 값에서 정수를 뽑는 함수"다. 타입 시스템이 그 차이를 지켜 준다.

명시적으로 감싸는 것은 허용된다.

```csharp
D2 d2 = new D2 (d1);     // OK — d1.Invoke를 대상으로 삼는 새 델리게이트
```

> **⚠️ `new D2(d1)`은 한 겹을 더 쌓는다**
>
> 이렇게 만든 `d2`의 `_target`은 `d1`이고 `_methodPtr`은 `D1.Invoke`다. 호출하면 `d2.Invoke → d1.Invoke → 실제 메서드` 순으로 **간접 호출이 두 번** 일어난다. 델리게이트 객체도 하나 더 생긴다.
>
> 어쩌다 한 번이면 무해하지만, 이 변환을 루프 안에서 반복하거나 여러 겹 중첩하면 비용이 쌓인다. 애초에 API 경계에서 델리게이트 타입을 통일하는 것이 옳다.

### 매개변수 반공변성

일반 메서드 호출에서 매개변수 타입보다 **더 구체적인** 인수를 넘길 수 있다. 델리게이트도 같은 이유로, 델리게이트가 대상 메서드보다 **더 구체적인 매개변수 타입**을 가질 수 있다. 이것을 **반공변성(contravariance)** 이라 한다.

```csharp
delegate void StringAction (string s);

void ActOnObject (object o) => Console.WriteLine (o);

StringAction sa = ActOnObject;     // OK
sa ("hello");                      // hello
```

`StringAction`은 `string`을 받겠다고 약속했다. 대상 메서드는 `object`면 무엇이든 받는다. `string`은 `object`이므로 안전하다. 호출 시점에 인수가 암시적으로 업캐스트된다.

### 반환 타입 공변성

대칭적으로, 대상 메서드가 델리게이트가 약속한 것보다 **더 구체적인 타입**을 반환해도 된다. **공변성(covariance)** 이다.

```csharp
delegate object ObjectRetriever();

string RetrieveString() => "hello";

ObjectRetriever o = RetrieveString;   // OK
object result = o();                  // hello
```

`ObjectRetriever`를 호출한 쪽은 `object`를 기대한다. 실제로 `string`이 오지만 `string`은 `object`이므로 문제없다.

> **⚠️ 변성은 참조 변환에만 적용된다 — 값 타입과 `void`는 안 된다**
>
> ```csharp
> delegate object MyCallback (FileStream s);
>
> string SomeMethod      (Stream s) => "";    // OK — 참조 타입끼리
> int    SomeOtherMethod (Stream s) => 0;     // 컴파일 오류
> ```
>
> `int`는 `object`에서 파생되지만 **값 타입**이다. `int`를 `object`로 만들려면 박싱이라는 표현 변환이 필요하고, 참조 변환이 아니다. 델리게이트 호출은 반환값의 메모리 표현을 그대로 전달하므로 이런 변환을 끼워 넣을 수 없다.
>
> 참조 타입의 참조 변환은 메모리 표현이 포인터로 동일해서 안전하다. **"표현이 같으면 허용, 다르면 금지"** 가 이 규칙 전체를 설명한다. 같은 이유로 `void`도 변성에 참여하지 못한다.

### 제네릭 타입 매개변수의 변성

`Func`와 `Action`의 `in`/`out` 표시는 23.10절에서 본 제네릭 변성이다. 델리게이트에도 인터페이스와 똑같이 적용된다.

```csharp
Func<string> x = () => "hello";
Func<object> y = x;                  // OK — TResult는 out

Action<object> a = o => Console.WriteLine (o);
Action<string> b = a;                // OK — T는 in
```

설계 지침도 그대로다.

- 반환값에만 쓰이는 타입 매개변수는 **공변(`out`)** 으로 표시한다.
- 매개변수에만 쓰이는 타입 매개변수는 **반공변(`in`)** 으로 표시한다.
- 양쪽에 쓰이면 표시할 수 없다(불변).

> **📌 두 변성은 다른 층위의 이야기다**
>
> 헷갈리기 쉬우니 정리하자.
>
> - **델리게이트 호환성의 변성**(이 절 앞부분): *메서드를 델리게이트에 바인딩할 때* 시그니처가 얼마나 어긋나도 되는가. 델리게이트 타입 선언에 아무 표시도 필요 없다.
> - **제네릭 변성**(`in`/`out`): *델리게이트 타입끼리 대입*할 때 타입 인수가 얼마나 어긋나도 되는가. 선언에 표시가 있어야 한다.
>
> 두 규칙 모두 "참조 변환만" 이라는 같은 제약을 받는다.

### 규칙 정리

| 상황 | 허용 | 조건 |
|---|---|---|
| `D2 d = d1;` (`D1`≠`D2`, 시그니처 동일) | 불가 | 명목적 타입 — 언제나 오류 |
| `D2 d = new D2 (d1);` | 가능 | 시그니처 호환. 간접 호출 한 겹 추가 |
| 대상 메서드의 매개변수가 더 일반적 | 가능 | 참조 타입에 한함(반공변) |
| 대상 메서드의 반환 타입이 더 구체적 | 가능 | 참조 타입에 한함(공변) |
| 값 타입 매개변수/반환의 변성 | 불가 | 표현이 다르다 |
| `Func<string>` → `Func<object>` | 가능 | `out TResult` 표시 덕분 |
| `Action<object>` → `Action<string>` | 가능 | `in T` 표시 덕분 |
| `Func<object>` → `Func<string>` | 불가 | 방향이 반대다 |
| `Predicate<T>` → `Func<T,bool>` | 불가 | 다른 타입 |
| `d1 == d2` (다른 델리게이트 타입) | 불가 | 컴파일 오류 |
| `d1 == d2` (같은 타입, 같은 대상·메서드) | 가능 | `true` |

## 26.7 델리게이트 vs 인터페이스 — 언제 무엇을

### 같은 문제를 푸는 두 도구

델리게이트로 푸는 문제는 인터페이스로도 풀 수 있다. 26.2절의 `Transform`을 인터페이스로 다시 써 보자.

```csharp
public interface ITransformer
{
    int Transform (int x);
}

public class Util
{
    public static void TransformAll (int[] values, ITransformer t)
    {
        for (int i = 0; i < values.Length; i++)
            values[i] = t.Transform (values[i]);
    }
}

class Squarer : ITransformer { public int Transform (int x) => x * x; }

int[] values = { 1, 2, 3 };
Util.TransformAll (values, new Squarer());
```

동작은 같다. 그런데 변환 규칙을 하나 더 추가하려면 **클래스를 하나 더** 만들어야 한다.

```csharp
class Cuber : ITransformer { public int Transform (int x) => x * x * x; }
```

한 클래스는 `ITransformer`를 **한 번만** 구현할 수 있으므로, 규칙 열 개에는 클래스 열 개가 필요하다. 델리게이트라면 람다 열 줄이면 된다.

### 선택 기준

다음 중 하나라도 참이면 델리게이트가 낫다.

1. **인터페이스에 메서드가 하나뿐이다.**
2. **멀티캐스트가 필요하다.**
3. **구독자가 같은 계약을 여러 번 구현해야 한다.**

셋 다 거짓이면 인터페이스가 낫다.

| 기준 | 델리게이트 | 인터페이스 |
|---|---|---|
| 메서드 개수 | 하나 | 여럿 가능 |
| 한 타입이 여러 번 제공 | 자연스럽다 | 불가능(명시적 구현으로 우회는 가능하나 지저분하다) |
| 멀티캐스트 | 내장 | 직접 리스트 관리 |
| 구현체의 상태 | 클로저가 대신한다 | 필드로 자연스럽게 표현 |
| 익명 정의 | 람다 한 줄 | 별도 타입 필요 |
| 구현 강제/발견 가능성 | 약하다 | 강하다 — 타입이 계약을 광고한다 |
| 버전 관리 | 시그니처를 바꾸면 모든 호출자가 깨진다 | 기본 구현 멤버로 완화 가능(18.7절) |
| 값 타입 구현체 | 항상 박싱된다(26.3절) | 제네릭 제약으로 박싱 회피 가능 |
| 호출 비용 | 간접 호출 | 인터페이스 디스패치(18.9절) |

> **💡 BCL은 둘 다 제공한다 — 그 이유를 보라**
>
> 정렬 하나에도 두 가지 창구가 있다.
>
> ```csharp
> list.Sort (new LengthComparer());        // IComparer<T>
> list.Sort ((a, b) => a.Length - b.Length); // Comparison<T>
> ```
>
> 왜 둘 다인가. `IComparer<T>`는 **재사용되고 이름이 있고 상태를 갖는** 비교 규칙에 맞다 — 문화권을 담은 문자열 비교자처럼(25장). `Comparison<T>`는 **이 호출 한 번을 위한** 규칙에 맞다. 재사용성과 즉시성 사이의 선택이고, BCL은 사용자에게 그 선택을 남긴다.
>
> 당신의 API도 같은 판단을 하면 된다. 규칙이 재사용될 것 같으면 인터페이스도 함께 받고, 아니면 델리게이트만 받아라.

> **⚠️ 인터페이스를 델리게이트로 바꾸면 발견 가능성이 사라진다**
>
> `ITransformer`를 구현한 타입은 IDE에서 "구현 찾기"로 전부 찾을 수 있다. 람다는 못 찾는다. 계약이 복잡하거나 여러 팀이 확장하는 지점이라면, 타입으로 표현하는 편이 협업에 유리하다.
>
> 반대로 계약이 "정수를 받아 bool을 낸다" 수준이면, 인터페이스를 강요하는 것은 호출자에게 클래스를 하나 쓰게 만드는 비용일 뿐이다. 23.13절에서 본 "제약으로 표현할 수 없는 계약은 델리게이트로"와 같은 판단이다.

## 26.8 익명 메서드와 람다 식 — 문법의 진화

### 세 세대의 문법

같은 일을 하는 코드가 C# 버전에 따라 어떻게 짧아졌는지 보자. `List<int>`에서 짝수를 골라내는 코드다.

**1세대 — 명명된 메서드와 명시적 델리게이트 생성:**

```csharp
Predicate<int> callback = new Predicate<int> (IsEvenNumber);
List<int> evens = list.FindAll (callback);

static bool IsEvenNumber (int i) => i % 2 == 0;
```

**2세대(※C# 2) — 익명 메서드:**

```csharp
List<int> evens = list.FindAll (delegate (int i) { return i % 2 == 0; });
```

**3세대(※C# 3) — 람다 식:**

```csharp
List<int> evens = list.FindAll (i => i % 2 == 0);
```

세 코드는 같은 일을 한다. 마지막이 압도적으로 읽기 쉽다.

| 세대 | 문법 | 특징 |
|---|---|---|
| C# 1 | `new D(Method)` | 메서드를 따로 선언해야 한다 |
| C# 1 | `D d = Method;` | 메서드 그룹 변환(26.3절) |
| C# 2 | `delegate (int i) { … }` | 인라인. 매개변수 타입 명시 필수. 반드시 문 블록 |
| C# 3 | `i => i % 2 == 0` | 타입 추론, 식 본문, 식 트리 변환 가능 |
| C# 9 | `static i => …`, `(_, _) => …` | 캡처 금지 선언, 무시 매개변수 |
| C# 10 | `var f = (int x) => x;` | 자연 타입, 반환 타입 명시, 특성 |
| C# 12 | `(string s = "") => …` | 매개변수 기본값, `params` |

### 익명 메서드가 여전히 할 수 있는 것

익명 메서드는 람다에 거의 완전히 대체되었다. 언어 명세도 새 코드에는 람다를 쓰라고 권고한다. 그런데 **람다가 흉내 낼 수 없는 문법이 딱 하나** 남아 있다.

```csharp
// 델리게이트가 매개변수 두 개를 요구하는데도 매개변수 목록을 통째로 생략할 수 있다
Clicked += delegate { Console.WriteLine ("clicked"); };
```

람다는 매개변수 개수를 맞춰야 한다. 익명 메서드만 **전부 생략**할 수 있다.

```csharp
public event EventHandler Clicked = delegate { };   // 빈 기본 핸들러
```

이 관용구는 이벤트를 항상 비어 있지 않게 만들어 `null` 검사를 없애는 데 쓰였다. 지금은 `?.Invoke`가 더 낫지만(27.5절), 오래된 코드에서 자주 만난다.

| 능력 | 익명 메서드 | 람다 식 |
|---|---|---|
| 암시적 타입 매개변수 | 불가 | 가능 |
| 식 본문 (`=> expr`) | 불가 (문 블록만) | 가능 |
| `Expression<T>`로 변환 | 불가 | 가능 (31장) |
| 매개변수 목록 전체 생략 | **가능** | 불가 |
| 외부 변수 캡처 | 가능 | 가능 |
| `static` 수정자 ※C# 9 | 가능 | 가능 |

> **⚠️ 익명 메서드 블록 뒤에는 세미콜론이 필요하다**
>
> ```csharp
> c1.AboutToBlow += delegate (object s, EventArgs e)
> {
>     Console.WriteLine ("...");
> };                       // ← 이 세미콜론을 빼면 컴파일 오류
> ```
>
> 이건 메서드 선언이 아니라 **식**이기 때문이다. 문의 끝에는 세미콜론이 온다. 람다도 마찬가지다.

### 람다 식의 해부

람다는 다음 형태다.

```text
(매개변수) => 식 또는 문 블록
```

`=>`는 람다 연산자다. 왼쪽은 처리할 인수, 오른쪽은 처리 방법이라고 읽으면 된다.

```csharp
Func<int,int> sqr = x => x * x;                      // 매개변수 1개, 괄호 생략
Func<int,int> sqr2 = (x) => x * x;                   // 괄호를 써도 된다
Func<int,int> sqr3 = x => { return x * x; };         // 문 블록
Func<string,string,int> len = (s1, s2) => s1.Length + s2.Length;   // 2개
Func<string> greet = () => "Hello, world";           // 0개 — 빈 괄호 필수
Func<int,int,int> add = (int a, int b) => a + b;     // 명시적 타입
```

**괄호를 생략할 수 있는 조건은 하나다.** 매개변수가 정확히 하나이고 타입을 추론할 수 있을 때다. 명시적 타입을 쓰면 괄호가 필요하다.

무시할 매개변수는 밑줄로 버릴 수 있다 ※C# 9.

```csharp
Func<string,string,int> constant = (_, _) => 42;
```

> **⚠️ 무시 매개변수는 두 개 이상일 때만 무시가 된다**
>
> `_`는 C# 9 이전에 **합법적인 변수 이름**이었다. 하위 호환을 위해, 매개변수 목록에 `_`가 **하나만** 있으면 그것은 여전히 `_`라는 이름의 평범한 매개변수다. 두 개 이상일 때만 무시(discard)로 해석된다.
>
> ```csharp
> Func<int,int> f = _ => 42;        // _는 평범한 매개변수 이름이다 (참조 가능)
> Func<int,int,int> g = (_, _) => 42;  // 둘 다 무시된다 (참조 불가)
> ```

### 컴파일 결과 — 이름 없는 메서드가 생긴다

컴파일러는 람다를 어떻게 처리하는가. **비공개 메서드를 하나 만들어 본문을 옮긴다.**

```csharp
class AClass
{
    public static void Register()
        => ThreadPool.QueueUserWorkItem (obj => Console.WriteLine (obj), 5);
}
```

컴파일 결과에 다음과 같은 메서드가 생긴다.

```text
<Register>b__0_0(object obj)
```

이름 규칙을 읽는 법은 이렇다.

| 조각 | 의미 |
|---|---|
| `<Register>` | 이 람다가 나타난 **메서드 이름** |
| `b__` | 컴파일러가 붙이는 익명 함수 표시 |
| `0_0` | 메서드 순번 _ 그 안에서의 람다 순번 |

이름이 `<`로 시작하는 이유는 **C# 식별자에 `<`를 쓸 수 없기** 때문이다. 사용자 코드의 이름과 절대 충돌하지 않는다. CLR은 이런 이름을 허용하므로 IL 수준에서는 문제가 없다.

컴파일러는 이 메서드에 `System.Runtime.CompilerServices.CompilerGeneratedAttribute`를 붙인다. 디버거·프로파일러·코드 커버리지 도구가 "사람이 쓴 코드가 아니다"를 판단하는 근거다.

> **⚠️ 생성된 메서드 이름에 의존하지 마라**
>
> 이 이름은 명세가 보장하지 않는다. 컴파일러 버전이 바뀌거나 소스를 조금만 고쳐도 달라질 수 있다. 리플렉션으로 `"<Register>b__0_0"` 같은 문자열을 찾는 코드는 언젠가 반드시 깨진다.
>
> 스택 트레이스에 이 이름이 나오면 "람다 안에서 터졌다"는 신호로만 읽어라. 원하는 것이 안정적인 이름이라면 **명명된 메서드나 지역 함수**를 쓰면 된다(26.12절).

> **📌 생성된 메서드는 언제 정적이고 언제 인스턴스인가**
>
> 컴파일러는 **가능하면 정적 메서드를 만든다.** 인스턴스 메서드는 숨은 `this` 매개변수가 필요해 조금 더 비싸기 때문이다.
>
> - 람다가 인스턴스 멤버를 전혀 건드리지 않으면 → 정적 메서드
> - 인스턴스 필드나 `this`를 건드리면 → 인스턴스 메서드(또는 디스플레이 클래스의 메서드)
>
> 26.11절에서 이 구분이 할당 횟수를 결정하는 것을 본다.

> **📌 람다가 식 트리가 되는 경우**
>
> 컴파일러는 람다를 두 가지 중 하나로 변환한다. 하나는 지금까지 본 **델리게이트 인스턴스**이고, 다른 하나는 `Expression<TDelegate>` 타입의 **식 트리(expression tree)** 다. 어느 쪽이 되는지는 **대상 타입**이 결정한다.
>
> ```csharp
> Func<int,int>             f = x => x * x;   // 델리게이트 — 실행 가능한 코드
> Expression<Func<int,int>> e = x => x * x;   // 식 트리 — 순회 가능한 객체 모델
> ```
>
> 식 트리는 코드를 **데이터로** 표현한다. 그래서 런타임에 해석해 SQL로 번역하는 일이 가능해진다. 이 장의 나머지는 전부 델리게이트 쪽 이야기다. 식 트리는 31장에서 다룬다.

## 26.9 람다 매개변수·반환 타입 명시, 람다 기본값 ※C# 10/12

### 추론이 실패하는 자리

보통은 컴파일러가 문맥에서 매개변수 타입을 알아낸다. 그러지 못하는 경우가 있다.

```csharp
void Foo<T> (T x) { }
void Bar<T> (Action<T> a) { }

Bar (x => Foo (x));      // 컴파일 오류 — x가 무슨 타입인가?
```

`Bar`의 `T`를 정하려면 람다의 타입을 알아야 하고, 람다의 타입을 정하려면 `T`를 알아야 한다. 순환이다. 매개변수 타입을 명시하면 풀린다.

```csharp
Bar ((int x) => Foo (x));    // OK
```

다른 해법도 있다.

```csharp
Bar<int> (x => Foo (x));     // 타입 인수를 직접 지정
Bar<int> (Foo);              // 메서드 그룹으로 넘긴다
```

### 자연 타입 ※C# 10

C# 10부터 람다는 **자연 타입(natural type)** 을 가진다. 대상 타입이 없어도 `Func`/`Action` 중 하나로 추론될 수 있다는 뜻이다.

```csharp
var greeter = () => "Hello, world";     // Func<string>으로 추론된다
var sqr     = (int x) => x * x;         // Func<int,int>
var print   = (string s) => Console.WriteLine (s);   // Action<string>
```

`var sqr = x => x * x;`는 여전히 실패한다. `Func<T,T>`라는 것까지는 알아도 `T`를 정할 수 없기 때문이다. 그래서 매개변수 타입 명시가 짝을 이룬다.

반환 타입도 명시할 수 있다 ※C# 10.

```csharp
var parse = int (string s) => int.Parse (s);
```

문법은 `반환타입 (매개변수) => 본문`이다. 반환 타입을 쓰려면 매개변수 괄호가 필수다.

> **💡 반환 타입 명시는 가독성보다 컴파일 성능을 위한 도구다**
>
> 복잡하게 중첩된 람다에서 컴파일러가 반환 타입을 추론하는 비용은 만만치 않다. 반환 타입을 적어 주면 그 추론이 생략되어 **컴파일이 빨라질 수 있다.** 조건부 식이 여러 갈래인 람다처럼 추론이 무거운 자리에서만 쓰는 것이 좋다.

> **⚠️ 자연 타입은 대상 타입을 대체하지 않는다**
>
> ```csharp
> var f = (int x) => x * x;
> Transformer t = f;         // 컴파일 오류 — Func<int,int>는 Transformer가 아니다
> ```
>
> `var`로 받는 순간 타입은 `Func<int,int>`로 **확정**된다. 그 뒤에는 26.6절의 명목적 타입 규칙이 그대로 적용되어 커스텀 델리게이트에 대입할 수 없다. 커스텀 델리게이트 타입이 목적이라면 `var`를 쓰지 말고 그 타입으로 선언해야 한다.
>
> ```csharp
> Transformer t = (int x) => x * x;    // OK — 대상 타입이 있다
> ```

### 매개변수 기본값과 `params` ※C# 12

C# 12부터 람다 매개변수에도 기본값을 줄 수 있다.

```csharp
var print = (string message = "") => Console.WriteLine (message);
print ("Hello");     // Hello
print ();            // 빈 줄
```

`params`도 쓸 수 있다.

```csharp
var sum = (params int[] nums) => nums.Sum();
Console.WriteLine (sum (1, 2, 3));      // 6
```

이 기능은 최소 API(ASP.NET Core Minimal API)처럼 **핸들러를 람다로 등록하는** 프레임워크를 위해 들어왔다. 명명된 메서드를 만들지 않고도 선택적 매개변수를 표현할 수 있게 된다.

> **⚠️ 기본값이 있는 람다의 자연 타입은 커스텀 델리게이트다**
>
> `Func`/`Action`에는 기본값이 없으므로, 기본값이 있는 람다는 `Func`/`Action`으로 표현할 수 없다. 컴파일러는 이 경우 **익명 델리게이트 타입을 새로 합성**한다. `var`로 받으면 그 합성 타입이 된다.
>
> 그래서 다음이 안 된다.
>
> ```csharp
> var p = (string m = "") => Console.WriteLine (m);
> Action<string> a = p;      // 컴파일 오류 — 타입이 다르다
> ```
>
> 기본값이 있는 람다를 변수에 담아 여기저기 넘길 생각이라면, **직접 델리게이트 타입을 선언**하는 것이 명확하다.
>
> ```csharp
> delegate void Printer (string message = "");
> Printer p = (string m = "") => Console.WriteLine (m);
> ```

> **⚠️ 델리게이트의 기본값과 람다의 기본값이 충돌하면**
>
> 대상 델리게이트 타입에 이미 기본값이 있고 람다에서 다른 기본값을 주면 경고가 난다. **호출 시점에 적용되는 것은 델리게이트 타입 쪽 기본값**이다. 선택적 매개변수는 호출 지점에서 컴파일러가 채워 넣는 것이고, 그 기준은 호출하는 타입의 선언이기 때문이다(10.4절의 버전 관리 함정과 같은 뿌리다).

### 람다에 특성 붙이기 ※C# 10

람다의 메서드·매개변수·반환값에 특성을 붙일 수 있다.

```csharp
Action<int> a =
    [Description ("Method")]
    [return: Description ("Return value")]
    ([Description ("Parameter")] int x) => Console.Write (x);
```

특성은 **컴파일러가 생성한 메서드**에 붙는다. 그래서 조회하려면 델리게이트에서 메서드 정보를 한 번 거쳐야 한다.

```csharp
var methodAtt = a.GetMethodInfo().GetCustomAttributes();
var paramAtt  = a.GetMethodInfo().GetParameters()[0].GetCustomAttributes();
var returnAtt = a.GetMethodInfo().ReturnParameter.GetCustomAttributes();
```

매개변수에 특성을 붙이면 **괄호가 반드시 필요하다.** 문법 모호성 때문이다. 식 트리 람다에는 특성을 붙일 수 없다. 자세한 규칙과 활용은 20.8절에 있다.

### 문법 요소별 버전 정리

| 문법 | 버전 | 예 |
|---|---|---|
| 익명 메서드 | C# 2 | `delegate (int x) { return x; }` |
| 람다 식 | C# 3 | `x => x * x` |
| 무시 매개변수 | ※C# 9 | `(_, _) => 42` |
| `static` 람다 | ※C# 9 | `static x => x * x` |
| 자연 타입 | ※C# 10 | `var f = (int x) => x;` |
| 반환 타입 명시 | ※C# 10 | `var f = int (string s) => …;` |
| 특성 | ※C# 10 | `[Obsolete] () => …` |
| 매개변수 기본값 | ※C# 12 | `(string m = "") => …` |
| 람다의 `params` | ※C# 12 | `(params int[] n) => …` |

## 26.10 외부 변수 캡처와 클로저 — 컴파일러가 만드는 디스플레이 클래스

### 외부 변수

람다는 자신이 정의된 위치에서 접근 가능한 모든 변수를 참조할 수 있다. 지역 변수, 매개변수, 필드 모두 해당한다. 이런 변수를 **외부 변수(outer variable)** 라 하고, 람다가 실제로 참조한 외부 변수를 **캡처된 변수(captured variable)** 라 한다. 변수를 캡처한 람다를 **클로저(closure)** 라 부른다.

```csharp
int factor = 2;
Func<int,int> multiplier = n => n * factor;
Console.WriteLine (multiplier (3));      // 6
```

같은 규칙이 익명 메서드와 지역 함수에도 적용된다.

### 캡처되는 것은 값이 아니라 변수다

이 장에서 가장 중요한 한 문장이다. **람다는 캡처 시점의 값을 복사하지 않는다. 변수 자체를 붙든다.**

```csharp
int factor = 2;
Func<int,int> multiplier = n => n * factor;
factor = 10;                              // 람다를 만든 뒤에 바꾼다
Console.WriteLine (multiplier (3));       // 30 — 2가 아니다
```

캡처된 변수는 **델리게이트를 호출하는 시점에** 평가된다. 람다를 만들 때가 아니다.

람다가 캡처된 변수를 **수정**할 수도 있다.

```csharp
int seed = 0;
Func<int> natural = () => seed++;

Console.WriteLine (natural());   // 0
Console.WriteLine (natural());   // 1
Console.WriteLine (seed);        // 2 — 바깥에서도 바뀐 값이 보인다
```

바깥의 `seed`와 람다 안의 `seed`가 **같은 저장 공간**이라는 뜻이다.

### 수명 연장

지역 변수는 보통 메서드가 끝나면 사라진다. 캡처된 변수는 다르다.

```csharp
static Func<int> Natural()
{
    int seed = 0;
    return () => seed++;      // seed를 캡처한 클로저를 반환한다
}

Func<int> natural = Natural();
Console.WriteLine (natural());   // 0
Console.WriteLine (natural());   // 1
```

`Natural`이 반환된 뒤에도 `seed`는 살아 있다. **캡처된 변수의 수명은 그것을 캡처한 델리게이트의 수명까지 연장된다.**

반대로, 람다 **안에서** 선언된 지역 변수는 호출마다 새로 만들어진다.

```csharp
static Func<int> Natural()
{
    return () => { int seed = 0; return seed++; };
}

Func<int> natural = Natural();
Console.WriteLine (natural());   // 0
Console.WriteLine (natural());   // 0 — 매번 새 seed
```

### 컴파일 결과 — 디스플레이 클래스

이 마술은 어떻게 구현되는가. 컴파일러가 만드는 메서드는 별개의 메서드이므로, 원래 메서드의 지역 변수에 접근할 방법이 없다. 그래서 컴파일러는 **캡처된 변수를 지역 변수에서 필드로 승격(hoisting)** 시킨다. 그 필드를 담을 클래스를 **디스플레이 클래스(display class)** 라 한다.

```csharp
void Demo()
{
    int factor = 2;
    Func<int,int> multiplier = n => n * factor;
    Console.WriteLine (multiplier (3));
}
```

컴파일러는 다음과 **거의 같은** 코드를 만든다.

```csharp
[CompilerGenerated]
private sealed class <>c__DisplayClass0_0
{
    public int factor;                       // 지역 변수가 필드가 되었다

    public int <Demo>b__0 (int n) => n * factor;
}

void Demo()
{
    var cls = new <>c__DisplayClass0_0();     // 힙 할당 (1)
    cls.factor = 2;
    Func<int,int> multiplier = new Func<int,int> (cls.<Demo>b__0);   // 힙 할당 (2)
    Console.WriteLine (multiplier (3));
}
```

IL로 보면 할당이 두 번인 것이 명확히 드러난다.

```il
IL_0000:  newobj     instance void C/'<>c__DisplayClass0_0'::.ctor()   // 할당 1
IL_0005:  stloc.0
IL_0006:  ldloc.0
IL_0007:  ldc.i4.2
IL_0008:  stfld      int32 C/'<>c__DisplayClass0_0'::factor            // 변수 → 필드
IL_000d:  ldloc.0
IL_000e:  ldftn      instance int32 C/'<>c__DisplayClass0_0'::'<Demo>b__0'(int32)
IL_0014:  newobj     instance void Func`2<int32,int32>::.ctor(object, native int)  // 할당 2
```

메모리는 이렇게 된다.

```text
   메서드가 실행 중일 때
   ┌────────────────────┐
   │  Demo()의 스택 프레임 │
   ├────────────────────┤          ┌─────────────────────────────┐
   │ cls  ──────────────┼─────────▶│ <>c__DisplayClass0_0 (힙)    │
   │ multiplier ────────┼───┐      ├─────────────────────────────┤
   └────────────────────┘   │      │ factor = 2                  │◀─┐
                            │      └─────────────────────────────┘  │
                            │                    ▲                  │
                            │      ┌─────────────┴───────────────┐  │
                            └─────▶│ Func<int,int> 인스턴스 (힙)   │  │
                                   ├─────────────────────────────┤  │
                                   │ _target    = ───────────────┼──┘
                                   │ _methodPtr = <Demo>b__0     │
                                   └─────────────────────────────┘

   Demo()가 끝난 뒤에도 multiplier가 살아 있으면
   → 델리게이트가 디스플레이 클래스를, 디스플레이 클래스가 factor를 붙잡는다
   → factor는 수집되지 않는다
```

델리게이트의 `_target`이 **디스플레이 클래스 인스턴스**라는 점을 확인하라. 26.3절의 "인스턴스 메서드 대상" 구조와 정확히 같다. 클로저는 마법이 아니라 **컴파일러가 자동으로 만들어 준 객체 + 인스턴스 메서드**다.

> **📌 스코프 하나당 디스플레이 클래스 하나**
>
> 이름의 `0_0`은 `<메서드 순번>_<스코프 순번>`이다. 중첩된 블록에서 각각 변수를 캡처하면 디스플레이 클래스가 여러 개 생기고, 안쪽 클래스가 바깥쪽 클래스 인스턴스를 필드로 참조한다.
>
> ```csharp
> void Outer()
> {
>     int a = 1;                        // DisplayClass0_0
>     for (int i = 0; i < 3; i++)
>     {
>         int b = i;                    // DisplayClass0_1 (a를 담은 인스턴스를 참조)
>         Register (() => Console.Write (a + b));
>     }
> }
> ```
>
> 이 구조가 26.11절에서 볼 "실수로 오래 붙잡는" 문제의 원인이다.

### 루프 변수 캡처 — `for`의 함정

이제 이 장에서 가장 유명한 함정이다.

```csharp
Action[] actions = new Action[3];

for (int i = 0; i < 3; i++)
    actions[i] = () => Console.Write (i);

foreach (Action a in actions) a();      // 012가 아니라 333
```

왜 `333`인가. **`for` 루프의 반복 변수는 루프 바깥에서 선언된 것처럼 취급된다.** 변수가 하나뿐이므로 세 클로저가 **같은 변수**를 캡처한다. 루프가 끝나면 그 변수의 값은 3이고, 나중에 호출된 세 델리게이트가 모두 3을 본다.

루프를 펼쳐 보면 당연해진다.

```csharp
Action[] actions = new Action[3];
int i = 0;
actions[0] = () => Console.Write (i);
i = 1;
actions[1] = () => Console.Write (i);
i = 2;
actions[2] = () => Console.Write (i);
i = 3;                                   // 루프 종료 조건에서 3이 된다

foreach (Action a in actions) a();       // 333
```

이게 부자연스러워 보이지만, `i`가 반복 사이에 값을 유지하는 변수라는 점을 생각하면 일관된 동작이다. 루프 본문에서 `i`를 직접 바꿀 수도 있다는 사실이 그것을 뒷받침한다.

해법은 **루프 본문 안에 새 변수를 만드는 것**이다.

```csharp
for (int i = 0; i < 3; i++)
{
    int loopScopedI = i;                 // 반복마다 새로 만들어진다
    actions[i] = () => Console.Write (loopScopedI);
}

foreach (Action a in actions) a();       // 012
```

`loopScopedI`는 반복마다 새 변수이므로 **반복마다 새 디스플레이 클래스 인스턴스**가 생기고, 각 클로저가 서로 다른 변수를 캡처한다.

### `foreach`는 C# 5에서 고쳐졌다

`foreach`도 C# 5.0 이전에는 같은 방식으로 동작했다.

```csharp
foreach (var s in new[] { "a", "b", "c" })
    actions.Add (() => Console.Write (s));
```

C# 4까지 이 코드는 `ccc`를 출력했다. `for`와 달리 `foreach`의 반복 변수는 **읽기 전용**이라 본문에서 바꿀 수 없는데도 그랬으니, 혼란이 컸다.

C# 5.0부터 `foreach`의 반복 변수는 **반복마다 새로 선언되는 것으로** 규정이 바뀌었다. 지금 이 코드는 `abc`를 출력한다.

| 반복문 | C# 4 이하 | C# 5 이상 |
|---|---|---|
| `for (int i = …)` | 변수 하나 공유 | **변수 하나 공유(변경 없음)** |
| `foreach (var x in …)` | 변수 하나 공유 | **반복마다 새 변수** |
| 루프 본문 안의 지역 변수 | 반복마다 새 변수 | 반복마다 새 변수 |

> **⚠️ `for` 루프의 함정은 지금도 그대로다**
>
> C# 5의 변경은 `foreach`에만 적용되었다. **`for` 루프의 반복 변수를 캡처하면 여전히 `333`이 나온다.** 언어 명세가 바뀔 여지도 거의 없다 — `for`의 반복 변수는 루프 전체에 걸쳐 하나여야 의미가 통하기 때문이다.
>
> 병렬 처리나 비동기 작업을 `for` 루프에서 시작하는 코드가 이 함정에 자주 빠진다.
>
> ```csharp
> for (int i = 0; i < files.Length; i++)
>     tasks.Add (Task.Run (() => Process (files[i])));   // 위험 — IndexOutOfRange까지 난다
> ```
>
> 루프가 끝난 시점에 `i`는 `files.Length`이고, 그때 태스크가 실행되면 범위를 벗어난다. **인덱스를 지역 변수로 복사하거나 `foreach`로 바꿔라.**

### 캡처할 수 없는 것

모든 변수가 캡처되지는 않는다. 필드로 승격할 수 없는 것들이 있다.

| 대상 | 캡처 가능 | 이유 |
|---|---|---|
| 지역 변수 | 가능 | 필드로 승격 |
| 매개변수(값 전달) | 가능 | 필드로 승격 |
| `this`와 인스턴스 필드 (클래스) | 가능 | `this`를 캡처한다 |
| 정적 필드 | 가능 (캡처 아님) | 어디서든 접근 가능하므로 승격 불필요 |
| `ref` / `out` / `in` 매개변수 | 불가 | 다른 위치의 저장소를 가리키는 별칭이라 힙으로 옮길 수 없다 |
| `ref` 지역 변수 | 불가 | 같은 이유 |
| `ref struct` 타입 변수(`Span<T>` 등) | 불가 | 힙에 올릴 수 없는 타입이다 |
| 구조체의 `this` | 불가 | 값 타입의 `this`는 별칭이다 |
| `stackalloc` 결과 | 불가 | 스택 메모리의 수명이 프레임에 묶인다 |

> **⚠️ `Span<T>`는 람다 안에서 쓸 수 없다**
>
> ```csharp
> Span<int> span = stackalloc int[10];
> Action a = () => span[0] = 1;      // 컴파일 오류
> ```
>
> `Span<T>`는 `ref struct`라 힙에 존재할 수 없다(16장). 디스플레이 클래스의 필드가 되는 순간 힙에 올라가므로 원천적으로 금지된다.
>
> 이 제약은 성능 코드에서 실제로 자주 부딪힌다. 해법은 **람다를 쓰지 않는 것**이다 — 지역 함수는 캡처 방식이 다르므로 상황에 따라 가능하다(26.12절).

> **⚠️ 구조체 안의 람다는 `this`에 접근할 수 없다**
>
> 구조체의 인스턴스 메서드 안에서 람다가 인스턴스 멤버를 참조하면 컴파일 오류다. 구조체의 `this`는 값의 별칭이므로 힙으로 옮길 수 없기 때문이다. 필요하다면 **지역 변수로 복사한 뒤** 그것을 캡처해야 한다.
>
> ```csharp
> struct Point
> {
>     public int X;
>     public Func<int> GetGetter()
>     {
>         int x = X;                  // 복사한다
>         return () => x;             // 복사본을 캡처한다
>     }
> }
> ```
>
> 이 코드는 "복사본을 캡처한다"는 의미가 명시적이라는 점에서도 낫다.

## 26.11 캡처가 만드는 숨은 할당과 `static` 람다 ※C# 9

### 캡처가 없으면 델리게이트도 한 번만 만든다

캡처가 없는 람다는 디스플레이 클래스가 필요 없다. 그뿐 아니라 **델리게이트 인스턴스 자체가 캐시된다.**

```csharp
void Loop()
{
    for (int i = 0; i < 1000; i++)
        Run (() => Console.Write ("."));    // 델리게이트는 딱 한 번만 만들어진다
}
```

컴파일 결과는 개념적으로 이렇다.

```csharp
[CompilerGenerated]
private sealed class <>c
{
    public static readonly <>c <>9 = new <>c();     // 싱글턴
    public static Action <>9__0_0;                  // 캐시된 델리게이트

    internal void <Loop>b__0_0() => Console.Write (".");
}

void Loop()
{
    for (int i = 0; i < 1000; i++)
        Run (<>c.<>9__0_0 ??= new Action (<>c.<>9.<Loop>b__0_0));
}
```

IL의 관용 패턴은 이렇다.

```il
ldsfld     class [System.Runtime]System.Action C/'<>c'::'<>9__0_0'
dup
brtrue.s   IL_001c                                  // 이미 있으면 그대로 쓴다
pop
ldsfld     class C/'<>c' C/'<>c'::'<>9'             // 싱글턴 인스턴스
ldftn      instance void C/'<>c'::'<Loop>b__0_0'()
newobj     instance void [System.Runtime]System.Action::.ctor(object, native int)
dup
stsfld     class [System.Runtime]System.Action C/'<>c'::'<>9__0_0'   // 캐시에 저장
IL_001c:  // 스택 위에 델리게이트
```

`<>c`라는 이름의 클래스, `<>9`라는 싱글턴 필드, `<>9__N_M`이라는 캐시 필드 — 디컴파일러나 할당 프로파일러에서 이 이름들을 보면 "캡처 없는 람다"라는 뜻이다.

**결론: 캡처가 없으면 프로세스 전체에서 델리게이트 객체 하나로 끝난다.** 루프 안에 있든 초당 백만 번 불리든 마찬가지다.

### 캡처가 있으면 매번 할당된다

캡처가 생기는 순간 이야기가 달라진다.

```csharp
void Loop (int factor)
{
    for (int i = 0; i < 1000; i++)
        Run (x => x * factor);      // factor를 캡처한다
}
```

`factor`는 호출마다 다를 수 있으므로 캐시가 불가능하다. `Loop` 호출마다 디스플레이 클래스 하나가 생기고, 델리게이트 변환마다 델리게이트 하나가 생긴다.

정확한 할당 횟수는 캡처 대상에 따라 다르다.

| 람다가 참조하는 것 | 디스플레이 클래스 | 델리게이트 | 캐시 |
|---|---|---|---|
| 아무것도 (상수만) | 없음 | **최초 1회** | `<>c.<>9__N_M` |
| 정적 필드·정적 메서드만 | 없음 | **최초 1회** | 가능 |
| 인스턴스 필드 / `this` | **없음** | 변환마다 1회 | 불가 |
| 지역 변수 / 매개변수 | 스코프 진입마다 1회 | 변환마다 1회 | 불가 |
| 지역 변수 + `this` | 스코프 진입마다 1회 | 변환마다 1회 | 불가 |

세 번째 행이 뜻밖일 수 있다. **인스턴스 멤버만 참조하는 람다는 디스플레이 클래스를 만들지 않는다.** 컴파일러가 람다 본문을 **포함 클래스의 인스턴스 메서드**로 만들고, `_target`에 `this`를 담으면 그만이기 때문이다. 할당은 델리게이트 하나뿐이다.

> **⚠️ 인스턴스 필드를 한 글자 참조하면 객체 전체가 붙잡힌다**
>
> ```csharp
> class Report
> {
>     private int _threshold;
>     private byte[] _hugeBuffer = new byte[10_000_000];
>
>     public Func<int,bool> MakeFilter()
>         => x => x > _threshold;        // _threshold만 쓰는 것처럼 보이지만
> }
> ```
>
> 이 델리게이트의 `_target`은 `_threshold`가 아니라 **`Report` 인스턴스 전체**다. 반환된 델리게이트가 오래 살아 있으면 `_hugeBuffer`도 함께 산다.
>
> 해법은 값을 지역 변수로 복사한 뒤 캡처하는 것이다.
>
> ```csharp
> public Func<int,bool> MakeFilter()
> {
>     int threshold = _threshold;        // 복사
>     return x => x > threshold;         // 디스플레이 클래스에 int 하나만 담긴다
> }
> ```
>
> 캐시·이벤트·정적 컬렉션에 델리게이트를 오래 담아 두는 코드에서 이 패턴은 필수다. 메모리 누수 분석에서 `<>c__DisplayClass`가 루트 경로에 나오면 거의 이 문제다.

> **⚠️ 같은 스코프의 캡처는 한 객체를 공유한다**
>
> 한 스코프에서 캡처된 변수들은 **디스플레이 클래스 하나**에 모인다. 그래서 서로 무관한 두 람다가 같은 객체를 공유하게 된다.
>
> ```csharp
> void Setup()
> {
>     var small = 42;
>     var huge  = new byte[100_000_000];
>
>     _longLived  = () => Console.Write (small);   // small만 쓴다
>     UseOnce (() => Process (huge));              // huge만 쓴다
> }
> ```
>
> 두 람다가 같은 디스플레이 클래스를 공유하므로, `_longLived`가 살아 있는 한 `huge`도 수집되지 않는다. **작은 값만 캡처했다고 안심할 수 없다.**
>
> 스코프를 나누면 해결된다. 캡처가 필요한 부분을 별도 메서드나 별도 블록으로 분리해 디스플레이 클래스를 쪼개라.

### `static` 람다 ※C# 9

캡처를 실수로 만드는 것을 컴파일러가 막게 할 수 있다. 람다·익명 메서드·지역 함수 앞에 `static`을 붙이면 된다.

```csharp
Func<int,int> multiplier = static n => n * 2;      // OK
```

```csharp
int factor = 2;
Func<int,int> bad = static n => n * factor;        // 컴파일 오류
```

`static` 지역 함수도 같다.

```csharp
void Foo()
{
    int factor = 123;
    static int Multiply (int x) => x * 2;          // factor에 접근하면 오류
}
```

`static` 람다는 여전히 **정적 필드와 상수**에는 접근할 수 있다. 이들은 클로저를 필요로 하지 않기 때문이다.

> **📌 `static`은 IL을 바꾸지 않는다 — 검사일 뿐이다**
>
> `static`을 붙이든 안 붙이든, 캡처가 없으면 컴파일러는 어차피 같은 코드를 만든다. 캐싱도 그대로 일어난다. **`static`이 하는 일은 "실수로 캡처하면 컴파일 오류를 내라"는 선언 하나뿐이다.**
>
> 그래서 이 키워드의 가치는 성능이 아니라 **의도의 문서화와 회귀 방지**에 있다. 오늘 캡처가 없는 람다에 `static`을 붙여 두면, 내일 누가 본문에 지역 변수를 하나 끌어다 쓸 때 빌드가 깨진다. 조용히 할당이 늘어나는 대신 즉시 알게 된다.

> **💡 핫 패스의 람다에는 일단 `static`을 붙여 보라**
>
> 성능이 중요한 코드에서 람다를 쓸 때는 `static`을 붙여 보는 것이 좋은 습관이다. 컴파일되면 "이 람다는 할당이 없다"가 증명된 것이고, 컴파일 오류가 나면 **몰랐던 캡처를 발견한 것**이다.
>
> 캡처가 꼭 필요하다면 다른 수단을 검토한다. BCL의 상당수 API가 **상태를 인수로 받는 오버로드**를 제공하는 이유가 이것이다. 캡처 대신 상태를 인수로 넘기면 클로저가 사라진다.
>
> ```csharp
> // 캡처 — 디스플레이 클래스 + 델리게이트
> dict.GetOrAdd (key, _ => Create (arg));
>
> // 상태 전달 — 델리게이트는 캐시되고 디스플레이 클래스는 없다
> dict.GetOrAdd (key, static (_, a) => Create (a), arg);
> ```

> **📌 델리게이트 자체의 할당은 남는다**
>
> 오해하기 쉬운 지점이다. 람다는 결국 **델리게이트 인스턴스로 평가**되고, 델리게이트는 참조 타입이므로 힙 할당이다. `static`을 붙여도 이 사실은 바뀌지 않는다. 다만 캡처가 없으면 그 인스턴스가 **애플리케이션 수명 동안 한 번만** 만들어져 재사용되므로, 실질적인 비용이 없어질 뿐이다.
>
> 할당을 0으로 만들어야 하는 자리라면 델리게이트 자체를 없애야 한다. 제네릭 제약과 구조체를 이용해 호출을 정적으로 결합하는 기법이 그 답이고, 69장에서 다룬다.

### 할당을 실제로 확인하는 방법

이 절의 내용은 **측정으로 확인할 수 있다.** 방법은 세 가지다.

| 방법 | 도구 | 보이는 것 |
|---|---|---|
| IL 확인 | `ildasm`, ILSpy, sharplab.io | `newobj`가 몇 번 나오는가, `<>c__DisplayClass`가 생겼는가 |
| 마이크로벤치마크 | BenchmarkDotNet의 `[MemoryDiagnoser]` | 호출당 할당 바이트 |
| 프로파일링 | dotnet-counters, 할당 프로파일러 | `<>c__DisplayClass...` 타입의 인스턴스 수 |

할당 프로파일러의 타입 목록에서 `<>c__DisplayClass`가 상위에 보이면 클로저가 핫 패스에 있다는 뜻이다. 어느 메서드인지는 이름의 `<메서드명>` 부분이 알려 준다. 숨은 할당의 전체 목록과 대응법은 63.9절에, 제거 기법은 69장에 있다.

## 26.12 람다 vs 지역 함수 — 할당과 성능 차이

### 기능이 겹친다

지역 함수(local function)는 메서드 안에 선언하는 이름 있는 메서드다. 람다와 하는 일이 상당히 겹친다.

```csharp
void Process (int[] data)
{
    // 람다
    Func<int,int> viaLambda = x => x * 2;

    // 지역 함수
    int ViaLocal (int x) => x * 2;

    Console.WriteLine (viaLambda (5) + ViaLocal (5));
}
```

겹치지만 구현이 근본적으로 다르다.

### 지역 함수가 유리한 세 가지

**1. 재귀가 자연스럽다.**

```csharp
// 지역 함수 — 그냥 자기를 부르면 된다
int Fib (int n) => n < 2 ? n : Fib (n - 1) + Fib (n - 2);

// 람다 — 선언과 대입을 분리해야 한다
Func<int,int> fib = null;
fib = n => n < 2 ? n : fib (n - 1) + fib (n - 2);
```

람다 쪽은 `fib`가 대입되기 전에 본문에서 참조되므로 두 단계로 나눠야 하고, 그렇게 만든 클로저는 `fib` 변수를 캡처한다. 나중에 누가 `fib`에 다른 것을 대입하면 재귀가 엉뚱한 곳으로 간다.

**2. 델리게이트 타입을 쓸 필요가 없다.**

지역 함수는 그냥 메서드다. `Func`/`Action`을 고르는 수고도, 매개변수 16개 제한도, `ref`/`out`을 못 쓰는 제약도 없다. `ref struct` 매개변수도 받는다.

**3. 오버헤드가 작다.**

이것이 핵심이다.

| 항목 | 람다 | 지역 함수 |
|---|---|---|
| 델리게이트 객체 | 필요 | **불필요**(직접 호출할 때) |
| 호출 방식 | 간접 호출(`callvirt Invoke`) | **직접 호출**(`call`) |
| 인라인 | 어렵다 | 일반 메서드처럼 가능 |
| 캡처 저장소 | **클래스**(힙) | **구조체**(스택), `ref`로 전달 |
| 캡처 시 할당 | 디스플레이 클래스 할당 | **할당 없음**(델리게이트로 변환하지 않는 한) |
| 재귀 | 우회 필요 | 자연스럽다 |
| 고차 함수에 넘기기 | 그대로 가능 | 델리게이트 변환 필요(이때 할당 발생) |

캡처 저장소의 차이가 결정적이다. 지역 함수를 **델리게이트로 변환하지 않고 직접 호출만 한다면**, 컴파일러는 디스플레이 클래스를 **클래스가 아니라 구조체**로 만들고 `ref`로 넘긴다. 힙 할당이 0이다.

```csharp
void Sum (int[] data)
{
    int total = 0;
    void Add (int x) => total += x;    // total을 캡처하지만 힙 할당은 없다

    foreach (var d in data) Add (d);
    Console.WriteLine (total);
}
```

컴파일 결과는 개념적으로 이렇다.

```csharp
private struct <Sum>g__DisplayClass { public int total; }     // 구조체다

private static void <Sum>g__Add (int x, ref <Sum>g__DisplayClass cls)
    => cls.total += x;
```

구조체는 스택에 있고 `ref`로 전달되므로 할당이 없다. **같은 코드를 람다로 쓰면 힙 할당 두 개가 생긴다.**

> **⚠️ 지역 함수를 델리게이트로 변환하면 이점이 사라진다**
>
> ```csharp
> void Sum (int[] data)
> {
>     int total = 0;
>     void Add (int x) => total += x;
>
>     Array.ForEach (data, Add);     // ← 델리게이트 변환
> }
> ```
>
> `Add`를 `Action<int>`로 변환하는 순간, 캡처 저장소는 **클래스여야 한다.** 델리게이트가 오래 살 수 있어 스택 저장소를 가리킬 수 없기 때문이다. 컴파일러는 이 경우 디스플레이 클래스를 클래스로 만들고, 할당은 람다와 같아진다.
>
> **"지역 함수는 항상 더 빠르다"가 아니라 "직접 호출하는 지역 함수는 할당이 없다"가 정확한 명제다.**

> **💡 판단 기준은 간단하다**
>
> - **고차 함수에 넘길 것이다** → 람다. 어차피 델리게이트가 필요하고, 짧은 람다가 더 읽기 쉽다.
> - **이 메서드 안에서만 부를 것이다** → 지역 함수. 이름이 붙어 의도가 드러나고, 할당이 없고, 스택 트레이스에 사람이 읽을 수 있는 이름이 남는다.
> - **본문이 세 줄을 넘는다** → 람다를 쓰지 마라. 지역 함수나 명명된 메서드로 빼라. 인라인 코드가 길어지면 그 코드가 실제로는 별도 메서드에 있다는 사실이 디버깅을 방해한다.
>
> 지역 함수에도 `static`을 붙일 수 있다는 점을 기억하라(26.11절). 캡처가 필요 없으면 붙여서 못을 박아 두는 편이 낫다.

> **📌 반복자와 비동기 메서드의 인수 검증**
>
> 지역 함수의 대표적인 용도가 하나 더 있다. `yield return`을 쓰는 메서드나 `async` 메서드는 **본문이 즉시 실행되지 않으므로** 인수 검증 예외가 늦게 터진다. 검증부를 일반 메서드에 두고 실제 본문을 지역 함수(반복자/비동기)로 분리하면 이 문제가 해결된다. 28.6절에서 다룬다.

## 26.13 콜백은 델리게이트로 표현하라 — 설계 원칙

### 원칙

작업의 진행 상황을 알리거나, 알고리즘의 한 조각을 호출자에게 맡기거나, 완료를 통지해야 할 때 — 즉 **콜백이 필요할 때 .NET에서의 답은 델리게이트다.**

인터페이스보다 결합이 약하다. 호출자는 타입을 만들지 않고 람다 한 줄을 쓴다. 대상은 실행 시점에 정해지고, 여럿일 수도 있다. .NET 자신이 이 원칙을 따른다 — LINQ 전체, `List<T>`의 검색·정렬·변환 메서드, 스레드 풀 큐잉, 타이머 콜백, UI 프레임워크의 스레드 마샬링이 전부 델리게이트로 표현되어 있다.

```csharp
List<int> numbers = Enumerable.Range (1, 200).ToList();

var odd    = numbers.Find (n => n % 2 == 1);
var allLow = numbers.TrueForAll (n => n < 50);
numbers.RemoveAll (n => n % 2 == 0);
numbers.ForEach (item => Console.WriteLine (item));
```

**단일 메서드가 필요한 자리에서 .NET은 인터페이스가 아니라 델리게이트를 쓴다.** 당신의 API도 같은 관례를 따르는 편이 사용자에게 익숙하다.

### 콜백 API를 설계할 때 결정해야 할 것들

델리게이트 매개변수를 하나 추가하는 것은 문법적으로 간단하다. 그러나 그 순간 **문서화해야 할 계약이 여러 개 생긴다.**

| 결정 사항 | 질문 | 흔한 답 |
|---|---|---|
| 호출 스레드 | 콜백은 어느 스레드에서 실행되는가 | 명시한다. 비동기라면 반드시 |
| 호출 횟수 | 0번? 1번? N번? 보장되는가 | 문서화한다 |
| 호출 시점 | 반환 전인가 후인가, 락을 잡은 채인가 | **락 안에서는 부르지 마라** |
| 예외 | 콜백이 던지면 어떻게 되는가 | 전파할지 격리할지 정한다 |
| 반환값 | 여러 콜백의 결과를 어떻게 합치는가 | 애초에 멀티캐스트를 막는다 |
| `null` 허용 | `null`을 넘길 수 있는가 | 허용하면 `?.Invoke`, 아니면 검증 |
| 재진입 | 콜백 안에서 같은 객체를 다시 부를 수 있는가 | 금지하거나 방어한다 |

> **⚠️ 락을 잡은 채로 콜백을 부르지 마라**
>
> 콜백 안에서 무슨 일이 벌어질지는 API 작성자가 모른다. 다른 락을 잡을 수도, 오래 블록될 수도, 같은 객체의 메서드를 다시 부를 수도 있다. **락을 잡은 상태로 남의 코드를 부르는 것은 교착 상태를 만드는 가장 확실한 방법이다.**
>
> 필요한 데이터를 락 안에서 모아 지역 변수에 담고, 락을 놓은 뒤에 콜백을 불러라.

> **⚠️ 콜백을 저장하면 수명 계약이 생긴다**
>
> 콜백을 필드에 담아 두는 API는 **해제 수단을 반드시 제공해야 한다.** 26.3절에서 봤듯 델리게이트는 대상 객체를 강하게 붙잡는다. 등록만 있고 해제가 없는 API는 사용자에게 메모리 누수를 강제한다.
>
> 등록 메서드가 `IDisposable`을 반환해 `using`으로 해제하게 하는 설계가 요즘 관례다. 이벤트 구독 해제의 짝을 잊기 쉬운 문제를 언어 대신 타입으로 막는다.

> **💡 콜백 매개변수는 마지막에 두어라**
>
> 콜백을 마지막 매개변수로 두면 람다를 여러 줄로 쓸 때 호출문이 자연스럽게 읽힌다. BCL의 `Where(source, predicate)`, `GetOrAdd(key, valueFactory)`, `Sort(comparison)`이 전부 그렇다.
>
> 그리고 **상태를 인수로 받는 오버로드를 함께 제공하는 것**을 검토하라(26.11절). 성능이 중요한 호출자가 클로저 할당을 피할 길이 열린다.

### 요약하면

델리게이트는 "동작을 값으로 다루기"라는 하나의 아이디어를 타입 안전하게 구현한 것이다. 그 위에 이벤트가 얹히고(27장), 반복자가 얹히고(28장), LINQ가 얹힌다(29~31장). 이 장에서 본 세 가지 — **델리게이트는 메서드와 객체의 쌍**, **`+=`는 새 인스턴스를 만든다**, **클로저는 값이 아니라 변수를 캡처한다** — 를 붙들고 있으면 Part V의 나머지는 전부 그 응용이다.

## 이 장의 요약

- **델리게이트는 타입 별칭이 아니라 클래스다.** `delegate` 선언은 `System.MulticastDelegate`에서 파생된 `sealed` 클래스를 만든다. 그 클래스의 생성자와 `Invoke`는 IL 본문이 없는 `runtime managed` 메서드이고, 구현을 CLR이 제공한다.
- **델리게이트 인스턴스는 메서드 하나와 객체 하나의 쌍이다.** `_methodPtr`이 메서드를, `_target`이 수신자를 가리킨다. 정적 메서드면 `_target`은 `null`이고, 인스턴스 메서드면 **그 객체의 수명이 델리게이트의 수명까지 연장된다.** 구조체의 인스턴스 메서드를 가리키면 수신자가 박싱된다.
- **`+=`와 `-=`는 `Delegate.Combine`/`Remove` 호출이다.** 델리게이트는 불변이므로 **매번 새 인스턴스와 새 배열이 만들어진다.** 핸들러 N개를 붙이는 비용은 O(N²)이고, 복사해 둔 변수는 이후의 구독 변경을 보지 못한다.
- **멀티캐스트에는 세 가지 함정이 있다.** 호출 순서는 등록 순서이고, **반환값은 마지막 것만 남으며**, **중간에 예외가 나면 나머지는 호출되지 않는다.** 셋 다 `GetInvocationList()`로 직접 순회하면 통제할 수 있다. 다만 그 메서드는 호출마다 배열을 새로 만든다.
- **`Func`/`Action`/`Predicate`가 커스텀 델리게이트를 대부분 대체한다.** 남는 자리는 `ref`/`out`/포인터/`params`/기본값/제약이 필요할 때와, 도메인 이름이 계약을 설명해 줄 때다. 모양이 같아도 `Predicate<T>`와 `Func<T,bool>`은 **대입 호환되지 않는다.**
- **델리게이트 타입은 명목적이다.** 시그니처가 같아도 다른 타입이면 대입할 수 없다. 대상 메서드는 더 일반적인 매개변수를 받거나(반공변) 더 구체적인 타입을 반환할 수 있지만(공변), **참조 변환에 한한다** — 값 타입과 `void`는 참여하지 못한다.
- **단일 메서드 계약, 멀티캐스트, 한 타입의 다중 구현 중 하나라도 해당하면 델리게이트가 낫다.** 그 밖에는 인터페이스가 발견 가능성과 버전 관리에서 유리하다. BCL이 `IComparer<T>`와 `Comparison<T>`를 나란히 제공하는 이유가 그 균형이다.
- **람다는 컴파일러가 만드는 비공개 메서드다.** 이름은 `<메서드명>b__N_M` 꼴이고 `CompilerGeneratedAttribute`가 붙는다. 대상 타입이 `Expression<T>`면 델리게이트가 아니라 식 트리가 된다(31장).
- **클로저는 값이 아니라 변수를 캡처한다.** 캡처된 지역 변수는 디스플레이 클래스의 **필드로 승격**되고, 그 클래스 인스턴스가 델리게이트의 `_target`이 된다. 그래서 캡처는 값을 복사하지 않고, 호출 시점의 값을 보며, 변수의 수명을 연장한다.
- **`for`의 반복 변수를 캡처하면 모든 클로저가 같은 변수를 본다.** `foreach`는 C# 5부터 반복마다 새 변수가 되어 이 문제가 없지만, **`for`는 지금도 그대로다.** 해법은 루프 본문 안에서 지역 변수로 복사하는 것뿐이다.
- **캡처가 없으면 델리게이트는 `<>c` 싱글턴에 캐시되어 딱 한 번만 할당된다.** 캡처가 생기면 스코프 진입마다 디스플레이 클래스가, 변환마다 델리게이트가 할당된다. **인스턴스 필드 하나만 참조해도 객체 전체가 붙잡히고, 같은 스코프의 캡처는 한 객체를 공유한다.**
- **`static` 람다는 IL을 바꾸지 않는다.** 캡처를 컴파일 오류로 만드는 검사일 뿐이다. 그래서 가치가 있다 — 오늘의 무할당 상태를 내일도 강제한다.
- **직접 호출하는 지역 함수는 캡처 저장소가 구조체라 힙 할당이 없다.** 델리게이트로 변환하는 순간 그 이점은 사라지고 람다와 같아진다. 고차 함수에 넘길 것이면 람다, 이 메서드 안에서만 부를 것이면 지역 함수다.

## 연습 문제

1. `delegate int Transformer (int x);`를 선언한 프로그램을 빌드하고 `ildasm`(또는 ILSpy)으로 열어라. `Transformer`가 `System.MulticastDelegate`에서 파생된 `sealed` 클래스이고, `.ctor`와 `Invoke`가 `runtime managed`로 표시되는 것을 확인하라. `BeginInvoke`/`EndInvoke`도 생성되었는지 보고, .NET에서 `BeginInvoke`를 호출했을 때 무슨 일이 일어나는지 실행해서 확인하라.

2. 정적 메서드와 인스턴스 메서드를 각각 가리키는 델리게이트를 만들어 `Target`과 `Method`를 출력하라. 그다음 구조체의 인스턴스 메서드를 가리키는 델리게이트를 만들어 세 번 호출하고 **원본 구조체의 필드가 변하지 않는 것**을 확인하라. `Target`이 무엇인지도 출력해 박싱을 증명하라.

3. 26.4절의 `Light`/`Fan`/`Speaker` 예제를 그대로 구현하라. 먼저 체인을 그냥 호출해 `Speaker`가 호출되지 않는 것을 확인하고, 그다음 `GetInvocationList()` 순회로 바꿔 세 결과가 모두 보고서에 들어가는 것을 확인하라. 마지막으로 `Fan`을 체인의 **첫 번째**로 옮겨 증상이 어떻게 달라지는지 기록하라.

4. 같은 핸들러를 `+=`로 두 번 등록한 뒤 `-=`로 한 번 빼고 발행하라. 몇 번 호출되는가. 그다음 람다를 `+=`로 등록하고 **글자가 같은 람다**로 `-=`를 시도해 제거되지 않는 것을 확인하라. 델리게이트를 변수에 담아 다시 시도해 성공하는 것도 확인하라.

5. `for` 루프에서 반복 변수를 캡처하는 `Action[]`을 만들어 `333`을 재현하라. 그다음 루프 본문에 지역 변수를 만들어 `012`로 고쳐라. 같은 실험을 `foreach`로 반복해 **고칠 필요가 없다**는 것을 확인하라. 세 경우의 IL을 비교해 `newobj <>c__DisplayClass`가 각각 몇 번 나오는지 세어라.

6. 캡처가 없는 람다, 인스턴스 필드만 캡처하는 람다, 지역 변수를 캡처하는 람다 세 가지를 루프 안에서 1,000번 델리게이트로 변환하는 코드를 작성하고, BenchmarkDotNet의 `[MemoryDiagnoser]`로 호출당 할당 바이트를 측정하라. 26.11절의 표와 결과가 일치하는지 확인하라.

7. 지역 변수를 캡처하는 지역 함수를 만들어 (a) 직접 호출만 하는 경우와 (b) `Array.ForEach`에 넘기는 경우의 IL을 비교하라. 디스플레이 클래스가 `struct`에서 `class`로 바뀌는 것을 확인하고, 각각의 할당 횟수를 측정하라.

**다음 장** — 27장「이벤트」에서는 이 장에서 남겨 둔 빚을 갚는다. 델리게이트 필드를 `public`으로 열었을 때 생기던 두 구멍 — 대입으로 남의 구독을 지우는 것과, 발행자가 아닌 쪽이 발행하는 것 — 을 `event` 키워드가 어떻게 막는지, 컴파일러가 만드는 `add`/`remove` 접근자가 실제로 무슨 코드인지 본다. 그리고 델리게이트가 대상 객체를 붙잡는 성질이 실제 애플리케이션에서 어떤 누수를 만드는지, 약한 이벤트 패턴이 그것을 어떻게 끊는지 다룬다.
