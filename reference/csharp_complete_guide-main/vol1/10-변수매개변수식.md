# 10장. 변수, 매개변수, 식

> **이 장의 위치** — 6장에서 9장까지는 "값이 어떻게 생겼는가"를 다뤘다. `int`, `double`, `string`, 배열. 이 장은 방향을 바꾼다. **값을 담는 그릇 자체**와, 그 그릇을 메서드 경계 너머로 건네는 네 가지 방법, 그리고 값을 계산해 내는 문법 단위인 **식**(expression)의 규칙을 다룬다. 9장에서 `Array.Resize`가 왜 `ref`를 요구했는지, 6장에서 미뤄 둔 연산자 우선순위 표가 어떻게 생겼는지가 여기서 끝난다.
>
> **선수 지식** — 6장(구문과 타입 기초), 특히 6.7절(값 타입 vs 참조 타입), 6.8절(스택과 힙), 6.9절(확정 할당과 기본값). 7장(숫자와 불리언), 8장(문자열과 문자), 9장(배열).
>
> **이 장에서 다루지 않는 것** — `ref` 필드와 `scoped` 한정자, `Span<T>`가 관리 포인터를 어떻게 담는지는 68장(특히 68.11절, 68.12절)의 몫이다. 람다가 지역 변수를 붙잡아 가는 **클로저 캡처**는 26.10절, 지역 함수와 람다의 할당 차이는 26.12절이다. `const`/`readonly` 선택이 API 버전 관리에 미치는 영향의 설계 판단은 79.2절, `var`를 쓸 자리와 쓰지 말 자리의 판단 기준은 79.1절, 선택적 매개변수와 오버로드 폭발의 저울질은 78.4절, `params` 컬렉션의 언어 진화 맥락은 76.12절이다. 문(statement)과 제어 흐름은 11장, 사용자 정의 타입에 연산자를 붙이는 방법은 22장이다. 이 장은 **언어가 이미 제공하는 그릇과 연산자**에서 멈춘다.

## 10.1 지역 변수와 범위(scope) 규칙

### 변수는 다섯 종류뿐이다

C#에서 **변수**(variable)란 "값을 바꿀 수 있는 저장 위치"다. 이 정의에 들어맞는 것은 정확히 다섯 가지다.

| 변수 종류 | 예 | 사는 곳 | 자동 초기화 |
|---|---|---|---|
| 지역 변수 | `int i = 0;` (메서드 안) | 스택 프레임 또는 레지스터 | 안 됨 (확정 할당 필요) |
| 매개변수 | `void F(int p)`의 `p` | 스택 프레임 또는 레지스터 | 호출 시 인수로 채워짐 |
| 인스턴스 필드 | `class C { int f; }`의 `f` | 객체와 같은 곳(주로 힙) | 됨 (비트 0) |
| 정적 필드 | `class C { static int s; }`의 `s` | 타입 객체 (프로세스 수명) | 됨 (비트 0) |
| 배열 요소 | `a[3]` | 배열 객체와 같은 곳(힙) | 됨 (비트 0) |

이 다섯 가지 말고는 없다. 프로퍼티는 변수가 아니다 — 겉보기에 변수처럼 읽고 쓰지만 실제로는 메서드 호출이며(13.8절), 그래서 뒤에 나올 `ref` 지역 변수의 대상이 될 수 없다.

"사는 곳"과 "자동 초기화" 열의 근거는 6.8절과 6.9절에서 이미 다뤘다. 여기서 다시 정리하지 않는다. 이 장에서 중요한 것은 **지역 변수와 매개변수만이 확정 할당(definite assignment) 규칙의 적용을 받는다**는 사실이다. 나머지 셋은 런타임이 알아서 0으로 채운다.

> **📌 "스택 프레임 또는 레지스터"라고 쓴 이유**
>
> C# 사양은 지역 변수가 스택에 놓인다고 말하지 않는다. 스택은 구현 세부사항이다. 실제로 JIT은 짧게 사는 지역 변수를 스택에 아예 올리지 않고 CPU 레지스터에만 두는 경우가 훨씬 많다(레지스터 할당). 스택 프레임에 실제로 슬롯이 잡히는 것은 주소를 얻어야 할 때(`ref`로 넘길 때, 클로저에 캡처될 때) 또는 레지스터가 모자랄 때다.
>
> 그래서 "지역 변수는 스택에 산다"는 문장은 **의미론을 설명하는 모델**로는 맞고, **기계 코드를 설명하는 사실**로는 반쯤 틀리다. 이 책은 앞의 의미로 쓴다.

### 범위는 블록 전체이고, 위아래 양방향이다

지역 변수와 지역 상수의 **범위**(scope)는 자신이 선언된 블록 전체다. 여기서 "전체"라는 말이 함정이다.

```csharp
void Method()
{
    Console.WriteLine(x);   // 오류 CS0841 — 선언 전에 사용할 수 없다
    int x = 5;
}
```

읽는 것은 선언 아래에서만 된다. 그런데 **이름이 점유하는 범위는 블록의 처음부터 끝까지**다. 이 둘은 다른 규칙이다. 다음 코드가 그 차이를 보여준다.

```csharp
class Test
{
    static int x = 100;

    static void Method()
    {
        Console.WriteLine(x);   // 오류 — 여기서 x는 아래의 지역 변수를 가리킨다
        int x = 5;
    }
}
```

필드 `x`가 있는데도 오류가 난다. 블록 안에 지역 변수 `x`가 선언되어 있으면, **그 블록 전체에서 이름 `x`는 지역 변수를 의미한다.** 선언보다 위에 있어도 마찬가지다. 그래서 위쪽의 `Console.WriteLine(x)`는 필드를 읽는 것이 아니라 "아직 확정 할당되지 않은 지역 변수를 읽으려는 시도"가 되어 거부된다.

> **📌 C++와 다른 지점**
>
> C++에서는 선언 지점부터 블록 끝까지가 범위다. 그래서 위 코드가 C++이라면 첫 줄은 전역/멤버 `x`를 읽고, 둘째 줄부터 지역 `x`가 가린다. C#은 그런 "부분 가림"을 허용하지 않는다. 블록 안에서 이름 하나는 처음부터 끝까지 같은 것을 뜻해야 한다는 원칙이며, 사람이 코드를 위아래로 훑을 때 생기는 착시를 막는다.

### 그림자(shadowing)가 금지되는 경우

**그림자**란 바깥 범위의 이름을 안쪽 범위에서 같은 이름으로 다시 선언해 가리는 것이다. C#은 지역 변수끼리의 그림자를 **금지한다.**

```csharp
int x;
{
    int y;
    int x;          // 오류 CS0128 — x는 이미 정의되어 있다
}
{
    int y;          // OK — 위쪽 y는 이 블록의 범위 밖이다
}
Console.Write(y);   // 오류 CS0103 — y는 여기서 범위 밖이다
```

정리하면 이렇다.

| 상황 | 허용? | 이유 |
|---|---|---|
| 바깥 블록의 지역 변수를 안쪽 블록에서 재선언 | 금지 | 같은 이름이 한 블록 안에서 두 가지를 뜻하게 된다 |
| 형제 블록에서 같은 이름 사용 | 허용 | 두 범위가 겹치지 않는다 |
| 필드와 같은 이름의 지역 변수 | 허용 | `this.x`로 필드를 구분해 부를 수 있다 |
| 매개변수와 같은 이름의 지역 변수 | 금지 | 매개변수는 메서드 본문 블록의 범위에 있다 |
| 지역 함수의 매개변수와 바깥 지역 변수 이름 충돌 | 금지 | 지역 함수 본문에서 바깥 변수가 보이기 때문 |
| 람다 매개변수와 바깥 지역 변수 이름 충돌 | 금지 | 위와 같은 이유 |

마지막 두 줄은 실무에서 자주 걸린다.

```csharp
int item = 0;
var q = list.Where(item => item > 3);   // 오류 — 람다 매개변수 이름이 이미 쓰였다
```

바깥 `item`을 람다 본문에서 볼 수 있어야 하는데, 매개변수 `item`이 그것을 가려 버리므로 컴파일러가 거부한다. 해법은 하나 — 이름을 바꿔라.

> **⚠️ `_`는 예약된 그림자 탈출구가 아니다**
>
> 밑줄 하나(`_`)는 C# 7부터 **버림**(discard)으로 특별 취급된다. 하지만 이것은 "진짜 `_`라는 이름의 변수가 범위 안에 없을 때"만 그렇다. 다음 코드에서 `_`는 버림이 아니라 평범한 변수다.
>
> ```csharp
> string _;                                       // 진짜 변수 _
> Split("Stevie Ray Vaughan", out string a, out _);
> Console.WriteLine(_);                           // Vaughan — 값이 들어 있다
> ```
>
> 하위 호환을 위해 이렇게 설계되었다. `_`를 진짜 변수 이름으로 쓰는 코드가 이미 존재했기 때문이다. 그래서 **`_`를 변수 이름으로 쓰지 마라.** 버림 문법이 조용히 무력화된다.

### 범위를 넓히는 선언들 — out 변수와 패턴 변수

C# 7부터 일부 선언은 자신이 등장한 식보다 **넓은 범위**를 갖는다.

```csharp
if (int.TryParse(s, out int n))
    Console.WriteLine(n);       // OK — n은 if 문 밖에서 선언된 셈이다
Console.WriteLine(n);           // OK — 같은 블록이므로 여전히 보인다 (확정 할당은 별개 문제)
```

`out int n`은 `if`의 조건식 안에 쓰여 있지만, 범위는 **`if` 문을 감싸는 블록**이다. 그래서 `if` 뒤에서도 `n`이 보인다. 다만 `TryParse`가 `false`를 반환한 경로에서도 `n`은 확정 할당되어 있으므로(메서드가 반드시 채워야 하니까) 읽는 것 자체는 허용된다.

패턴 변수도 같다.

```csharp
if (obj is string s && s.Length > 3)
    Console.WriteLine(s);
```

이 규칙 때문에 그림자 금지 규칙에 걸리는 새로운 방식이 생겼다.

```csharp
int n = 0;
if (int.TryParse(s, out int n))   // 오류 CS0128 — n이 이미 이 블록에 있다
    ...
```

> **💡 `out` 변수는 필요한 만큼만 좁혀 쓰라**
>
> `out` 변수와 패턴 변수의 범위가 넓은 것은 편의를 위한 설계지만, 메서드가 길면 "이 변수가 어디서 생겼는지" 찾기 어려워진다. 실무 규칙 하나 — `out` 변수를 인라인 선언했다면 그 값을 쓰는 코드를 그 `if` 블록 안에 두어라. 블록을 빠져나온 뒤에도 계속 쓴다면 차라리 위에서 `int n;`으로 명시적으로 선언하는 편이 읽기 좋다.

### 지역 함수와 범위

메서드 안에 메서드를 선언하는 **지역 함수**(local function)도 범위 규칙의 적용을 받는다.

```csharp
void Outer()
{
    int factor = 3;

    Console.WriteLine(Triple(5));   // OK — 선언보다 위에서 호출해도 된다

    int Triple(int x) => x * factor;   // 바깥 지역 변수 factor를 그대로 본다
}
```

지역 변수와 달리 **지역 함수는 선언보다 위에서 호출할 수 있다.** 함수는 "읽는" 것이 아니라 "부르는" 것이고, 확정 할당 규칙의 대상이 아니기 때문이다.

지역 함수가 바깥 지역 변수를 참조하면 그 변수는 캡처된다. 캡처가 무엇을 만들어 내는지 — 컴파일러가 생성하는 구조체 또는 클래스, 그리고 그 할당 비용 — 는 26.10절과 26.12절에서 다룬다. 이 장에서는 범위 규칙만 확인하고 넘어간다.

### 범위(scope)와 수명(lifetime)은 다른 말이다

마지막으로 반드시 구분해야 할 두 단어가 있다.

- **범위**는 "이름이 보이는 소스 코드 영역"이다. 컴파일 타임 개념이다.
- **수명**은 "그 저장 위치가 실제로 존재하는 시간"이다. 런타임 개념이다.

보통은 둘이 일치한다. 블록을 나가면 이름도 안 보이고 스택 슬롯도 사라진다. 그런데 **캡처가 일어나면 어긋난다.**

```csharp
Func<int> MakeCounter()
{
    int count = 0;              // 범위: MakeCounter 본문
    return () => ++count;       // 수명: 반환된 델리게이트가 살아 있는 동안
}
```

`count`는 `MakeCounter`가 반환된 뒤에도 살아 있다. 컴파일러가 `count`를 힙 객체의 필드로 옮겼기 때문이다. 이 변환의 상세는 26.10절이다.

## 10.2 매개변수 전달 — 값 / `ref` / `out` / `in`

이 절이 이 장의 심장이다. C#에서 인수(argument)를 메서드에 건네는 방식은 네 가지고, 그 차이를 정확히 모르면 "왜 값이 안 바뀌지" 또는 "왜 이렇게 느리지"라는 질문에 평생 답하지 못한다.

먼저 용어부터 고정한다.

```csharp
Foo(8);                       // 8은 인수(argument)
static void Foo(int p) { }    // p는 매개변수(parameter)
```

### 네 가지 전달 방식 완전 비교표

| 항목 | (수정자 없음) 값 | `ref` | `out` | `in` |
|---|---|---|---|---|
| 무엇이 넘어가는가 | 값의 복사본 | 변수의 **주소** | 변수의 **주소** | 변수의 **주소** |
| 호출 전 확정 할당 필요 | 필요 | **필요** | 불필요 | **필요** |
| 메서드 종료 전 할당 의무 | 없음 | 없음 | **있다** | 없음 (쓸 수 없다) |
| 메서드 안에서 읽기 | 가능 | 가능 | **할당 전에는 불가** | 가능 |
| 메서드 안에서 쓰기 | 가능(복사본만 바뀜) | 가능(원본이 바뀜) | 가능(원본이 바뀜) | **불가 — CS8331** |
| 호출부 수정자 표기 | — | **필수** | **필수** | 선택(생략 가능) |
| IL 매개변수 타입 | `T` | `T&` | `T&` | `T& modreq(InAttribute)` |
| IL 매개변수 플래그 | — | 없음 | `[out]` | `[in]` |
| 호출부 IL(지역 변수 인수) | `ldloc` | `ldloca` | `ldloca` | `ldloca` |
| 오버로드 구분에 쓸 수 있나 | — | 가능 | 가능 | 가능 |
| `ref`/`out`/`in`끼리 오버로드 | — | `out`과 동시 불가 | `ref`와 동시 불가 | `ref`와 동시 불가 |
| 기본값(선택적 매개변수) 지정 | 가능 | 불가 | 불가 | 가능 |
| 반복자·비동기 메서드에서 사용 | 가능 | 불가 | 불가 | 불가 |
| 표현식이 아닌 값을 넘길 수 있나 | 가능(`Foo(1+2)`) | 불가(변수여야 함) | 불가 | **가능** (임시 변수 생성) |

마지막 줄이 `in`의 특이점이다. `ref`와 `out`은 반드시 "변수"를 요구하지만, `in`은 리터럴이나 계산 결과도 받는다. 이때 컴파일러가 눈에 안 보이는 임시 지역 변수를 만들어 거기에 값을 넣고 그 주소를 넘긴다.

```csharp
static double Hypot(in double a, in double b) => Math.Sqrt(a * a + b * b);

Hypot(3, 4);       // OK — 컴파일러가 임시 슬롯 두 개를 만든다
```

오버로드 규칙도 한 번 더 정리한다. **값 전달과 `in`은 함께 오버로드할 수 있지만**, `ref`·`out`·`in`끼리는 서로 오버로드할 수 없다.

```csharp
void Foo(   SomeBigStruct a) { }
void Foo(in SomeBigStruct a) { }     // OK — 값 전달과 in은 시그니처가 다르다

SomeBigStruct x = default;
Foo(x);            // 값 전달 오버로드를 부른다
Foo(in x);         // in 오버로드를 부른다
```

즉 **호출부에서 `in`을 생략할 수 있다는 규칙은 모호함이 없을 때만 적용된다.** 위처럼 두 오버로드가 공존하면 `in`을 쓰느냐 마느냐가 어느 메서드를 부를지 결정한다. 오버로드가 하나뿐이면 `Foo(x)`와 `Foo(in x)`가 똑같이 그 하나를 부른다.

### 문법 — 값 전달의 두 얼굴

기본값은 **값 전달**이다. 값의 복사본이 만들어진다.

```csharp
int x = 8;
Foo(x);
Console.WriteLine(x);       // 8 — 그대로다

static void Foo(int p)
{
    p = p + 1;              // 복사본을 고쳤을 뿐
    Console.WriteLine(p);   // 9
}
```

여기서 가장 흔한 오해가 시작된다. **참조 타입을 값으로 전달하면 무엇이 복사되는가?**

```csharp
StringBuilder sb = new StringBuilder();
Foo(sb);
Console.WriteLine(sb.ToString());   // test

static void Foo(StringBuilder fooSB)
{
    fooSB.Append("test");           // 힙의 객체를 고친다 → 호출자도 본다
    fooSB = null;                   // 자기 슬롯만 비운다 → 호출자는 모른다
}
```

복사되는 것은 **참조(주소)**다. 객체가 아니다. 그래서 `fooSB`와 `sb`는 **서로 다른 변수인데 같은 객체를 가리킨다.** 객체를 통해 하는 일(`Append`)은 양쪽에 보이고, 변수 자체에 하는 일(`= null`)은 자기 쪽에만 보인다.

> **⚠️ "값 타입은 값으로, 참조 타입은 참조로 전달된다"는 문장은 절반만 맞다**
>
> 매우 널리 퍼진 설명이고, 결과를 대충 예측하는 데는 쓸모가 있지만 정확하지 않다. 정확한 문장은 이것이다.
>
> **"수정자가 없으면 언제나 값 전달이다. 참조 타입의 경우 그 '값'이 참조일 뿐이다."**
>
> 이 차이가 드러나는 곳이 바로 `fooSB = null`이다. 진짜 참조 전달(`ref StringBuilder`)이었다면 호출자의 `sb`도 `null`이 됐을 것이다. 두 문장의 차이를 확인하는 실험은 이 장 연습 문제 1번이다.
>
> 그리고 매개변수의 전달 방식과 매개변수 타입의 종류는 **완전히 독립적인 두 축**이다. 값 타입을 `ref`로 넘길 수도 있고 참조 타입을 값으로 넘길 수도 있다.

```text
      ── 값 전달 (수정자 없음), 값 타입 ──

  호출자 스택 프레임              피호출자 스택 프레임
  ┌────────────────┐            ┌────────────────┐
  │  x : int  = 8  │─── 복사 ──▶│  p : int  = 8  │
  └────────────────┘            └────────────────┘
                                        │ p = p + 1
                                        ▼
  ┌────────────────┐            ┌────────────────┐
  │  x : int  = 8  │  (그대로)   │  p : int  = 9  │
  └────────────────┘            └────────────────┘


      ── ref 전달, 값 타입 ──

  호출자 스택 프레임              피호출자 스택 프레임
  ┌────────────────┐            ┌────────────────┐
  │  x : int  = 8  │◀───────────│  p : int&      │   p는 x의 주소를 담는다
  └────────────────┘            └────────────────┘
          ▲                             │ *p = *p + 1
          └─────────────────────────────┘
  ┌────────────────┐
  │  x : int  = 9  │  원본이 바뀐다
  └────────────────┘


      ── 값 전달 (수정자 없음), 참조 타입 ──

  호출자 프레임            피호출자 프레임              관리 힙
  ┌──────────────┐        ┌──────────────┐        ┌───────────────┐
  │ sb   : 참조  │─ 복사 ─▶│ fooSB : 참조 │───────▶│ StringBuilder │
  │      ────────┼─────────────────────────────────▶│    "test"     │
  └──────────────┘        └──────────────┘        └───────────────┘

  · fooSB.Append("test")  → 힙 객체가 바뀐다      → 호출자도 본다
  · fooSB = null          → 피호출자 슬롯만 비운다 → sb는 그대로
```

### 컴파일 결과 — IL에서 무슨 일이 벌어지는가

값 전달부터 보자. 다음 C# 코드를

```csharp
static int AddOne(int p) => p + 1;

static void Caller()
{
    int x = 8;
    int y = AddOne(x);
}
```

컴파일하면 이런 IL이 나온다.

```il
.method private hidebysig static int32 AddOne(int32 p) cil managed
{
  .maxstack  2
  IL_0000:  ldarg.0
  IL_0001:  ldc.i4.1
  IL_0002:  add
  IL_0003:  ret
}

.method private hidebysig static void Caller() cil managed
{
  .locals init (int32 V_0, int32 V_1)
  IL_0000:  ldc.i4.8
  IL_0001:  stloc.0            // x = 8
  IL_0002:  ldloc.0            // x의 '값'을 평가 스택에 올린다
  IL_0003:  call       int32 Program::AddOne(int32)
  IL_0008:  stloc.1
  IL_0009:  ret
}
```

핵심은 두 곳이다. 시그니처의 매개변수 타입이 `int32`이고, 호출부가 `ldloc.0`(값 로드)을 쓴다. 복사는 바로 이 `ldloc` 한 줄이다.

이제 `ref`로 바꾼다.

```csharp
static void Bump(ref int p) => p = p + 1;

static void Caller()
{
    int x = 8;
    Bump(ref x);
}
```

```il
.method private hidebysig static void Bump(int32& p) cil managed
{
  .maxstack  3
  IL_0000:  ldarg.0            // p (= 주소)
  IL_0001:  ldarg.0
  IL_0002:  ldind.i4           // 주소가 가리키는 int32를 읽는다
  IL_0003:  ldc.i4.1
  IL_0004:  add
  IL_0005:  stind.i4           // 주소가 가리키는 곳에 쓴다
  IL_0006:  ret
}

.method private hidebysig static void Caller() cil managed
{
  .locals init (int32 V_0)
  IL_0000:  ldc.i4.8
  IL_0001:  stloc.0
  IL_0002:  ldloca.s   V_0     // x의 '주소'를 평가 스택에 올린다
  IL_0004:  call       void Program::Bump(int32&)
  IL_0009:  ret
}
```

세 가지가 달라졌다.

1. 시그니처 타입이 `int32`에서 **`int32&`**로 바뀌었다. `&`는 IL에서 **관리 포인터**(managed pointer, byref)를 뜻한다.
2. 호출부가 `ldloc`이 아니라 **`ldloca`**(load local address)를 쓴다.
3. 메서드 본문에서 값을 읽고 쓰려면 **`ldind`/`stind`**라는 간접 접근 명령이 하나씩 더 든다.

3번이 성능 이야기의 출발점이다. `ref`는 공짜가 아니다 — 복사를 없애는 대신 **매번 역참조(dereference)를 한다.**

`out`은 IL에서 `ref`와 거의 같다.

```csharp
static void GetVal(out int v) => v = 10;
```

```il
.method private hidebysig static void GetVal([out] int32& v) cil managed
{
  .maxstack  2
  IL_0000:  ldarg.0
  IL_0001:  ldc.i4.s   10
  IL_0003:  stind.i4
  IL_0004:  ret
}
```

차이는 매개변수에 붙은 `[out]` 플래그 하나뿐이다.

> **📌 CLR은 `out`을 모른다**
>
> CLR 관점에서 `out`과 `ref`는 **완전히 같다.** 생성되는 IL이 같고, 메타데이터도 딱 1비트(`ParamAttributes.Out`)만 다르다. 그 1비트는 CLR의 실행에는 아무 영향을 주지 않는다.
>
> 그러면 왜 두 키워드가 있는가? **C# 컴파일러가 확정 할당 검사를 다르게 하기 위해서**다. `ref`는 "호출자가 미리 채워라", `out`은 "피호출자가 반드시 채워라"라는 계약이며, 이 계약은 전적으로 컴파일 타임에만 존재한다. 오래된 언어가 `out` 표시를 무시하고 이 메서드를 호출해도 CLR은 막지 않는다.
>
> 이 사실이 다음 규칙도 설명한다. **`ref`와 `out`만 다른 두 메서드는 오버로드할 수 없다** — 메타데이터 시그니처가 동일해지기 때문이다. 시도하면 `error CS0663: 'Add' cannot define overloaded methods because it differs only on ref and out.`이 나온다. 반면 값 전달과 `ref`는 시그니처가 달라(`int32` vs `int32&`) 오버로드가 된다.

`in`은 여기에 한 겹을 더 얹는다.

```csharp
static double Length(in Vec3 v) => Math.Sqrt(v.X * v.X + v.Y * v.Y + v.Z * v.Z);
```

```il
.method private hidebysig static float64
        Length([in] valuetype Vec3& modreq([System.Runtime]
                 System.Runtime.InteropServices.InAttribute) v) cil managed
{
  // ...
}
```

`modreq`는 **필수 한정자**(required modifier)다. 이 한정자를 이해하지 못하는 컴파일러는 이 메서드를 호출조차 할 수 없게 만든다. 즉 "이 매개변수는 읽기 전용 참조다"라는 계약을 메타데이터 수준에서 강제하는 장치다. `[in]` 플래그도 함께 붙는다.

> **📌 ※C# 12의 `ref readonly` 매개변수**
>
> C# 12는 `in`과 비슷하지만 호출부가 반드시 `in` 또는 `ref`를 쓰도록 요구하는 `ref readonly` 매개변수를 추가했다. IL 표현은 `in`과 같은 `[in] T& modreq(InAttribute)`이고, 여기에 `System.Runtime.CompilerServices.RequiresLocationAttribute`가 더 붙어 두 기능을 구분한다.
>
> 존재 이유는 API 설계에 있다. `in`은 호출부에서 수정자를 생략할 수 있어서, 원래 값 전달이던 매개변수를 `in`으로 바꿔도 호출 코드가 아무 경고 없이 그대로 컴파일된다. `ref readonly`는 그 조용한 전환을 막는다.

### 런타임 동작 — 무엇이 실제로 복사되는가

가장 중요한 표를 하나 더 만든다. **매개변수 타입 × 전달 방식**의 조합에서 실제로 복사되는 바이트가 무엇인지다.

| 전달 방식 \ 타입 | 값 타입 `struct Vec3`(24바이트) | 참조 타입 `class Node` |
|---|---|---|
| 값 (수정자 없음) | **24바이트 전부 복사** | 참조 4/8바이트 복사 |
| `ref` | 주소 4/8바이트 복사 | 주소 4/8바이트 복사 (**참조를 담은 슬롯의 주소**) |
| `out` | 주소 4/8바이트 복사 | 주소 4/8바이트 복사 |
| `in` | 주소 4/8바이트 복사 (단, 방어적 복사 주의) | 주소 4/8바이트 복사 |

참조 타입에 `ref`를 붙였을 때 무엇이 넘어가는지가 헷갈리는 지점이다. **객체의 주소가 아니라, 객체의 주소를 담고 있는 변수의 주소**가 넘어간다. 한 단계가 더 있다. 그래서 피호출자가 그 변수에 새 객체를 대입하면 호출자 쪽 변수가 새 객체를 가리키게 된다.

```csharp
static void Replace(ref StringBuilder sb) => sb = new StringBuilder("new");

StringBuilder x = new StringBuilder("old");
Replace(ref x);
Console.WriteLine(x);      // new — x 자체가 갈아끼워졌다
```

9장의 `Array.Resize`가 이렇게 동작한다. 새 배열을 만들고 복사한 뒤, `ref` 매개변수를 통해 호출자의 변수를 새 배열로 갈아끼운다. 같은 배열을 가리키던 **다른** 변수는 옛 배열에 그대로 남는다.

> **⚠️ `ref`로 넘기는 변수의 타입은 매개변수 타입과 정확히 일치해야 한다**
>
> 상속 관계여도 안 된다.
>
> ```csharp
> static void Swap(ref object a, ref object b) { ... }
>
> string s1 = "Jeffrey", s2 = "Richter";
> Swap(ref s1, ref s2);       // 컴파일 오류
> ```
>
> 이유는 타입 안전성이다. `ref object`를 받은 메서드는 그 위치에 **아무 참조 타입이나** 쓸 수 있다. `string` 변수의 주소를 `ref object`로 받아 거기에 `FileStream`을 써 버리면, 호출자의 `string` 변수가 `FileStream`을 가리키게 된다. 컴파일러는 이것을 원천 차단한다.
>
> 억지로 하려면 `object o1 = s1;`로 임시 변수를 거친 뒤 다시 캐스트해야 하는데, 제대로 된 해법은 제네릭이다.
>
> ```csharp
> static void Swap<T>(ref T a, ref T b) { T t = b; b = a; a = t; }
> Swap(ref s1, ref s2);       // OK
> ```
>
> `System.Threading.Interlocked` 클래스의 `Exchange`와 `CompareExchange`가 정확히 이 이유로 제네릭 오버로드를 갖는다.

### `in` 매개변수의 방어적 복사 함정

이 항목 하나가 `in`을 "쓰면 무조건 빨라지는 것"에서 "잘못 쓰면 더 느려지는 것"으로 만든다.

`in`의 존재 이유는 **큰 구조체를 복사 없이 넘기는 것**이다. 24바이트짜리 구조체를 값으로 넘기면 매 호출마다 24바이트를 복사하지만, `in`으로 넘기면 8바이트 주소만 복사한다. 그런데 컴파일러는 동시에 "메서드가 원본을 못 고치게" 보장해야 한다. 문제는 이 두 요구가 충돌하는 경우가 있다는 것이다.

```csharp
struct Vec3                 // readonly가 아니다
{
    public double X, Y, Z;
    public double GetLength() => Math.Sqrt(X * X + Y * Y + Z * Z);
}

static double Sum(in Vec3 a, in Vec3 b)
    => a.GetLength() + b.GetLength();
```

`GetLength()`는 인스턴스 메서드다. 인스턴스 메서드를 호출하려면 인스턴스의 주소(`this`)를 넘겨야 하는데, `Vec3`가 `readonly struct`가 아니므로 컴파일러는 **`GetLength()`가 내부에서 `X`를 고치지 않는다고 증명할 수 없다.** 그런데 `a`는 읽기 전용이어야 한다. 컴파일러의 유일한 탈출구는 이것이다.

**구조체 전체를 임시 슬롯에 복사한 뒤, 그 복사본에 대해 메서드를 호출한다.**

```il
  IL_0000:  ldarg.0
  IL_0001:  ldobj      Vec3          // ← 방어적 복사: 24바이트를 통째로 복사
  IL_0006:  stloc.0
  IL_0007:  ldloca.s   V_0
  IL_0009:  call       instance float64 Vec3::GetLength()
```

`ldobj`가 방어적 복사(defensive copy)다. **복사를 없애려고 `in`을 붙였는데 복사가 그대로 일어난다.** 게다가 원래 값 전달이었다면 복사는 호출당 1회였을 텐데, 이제는 **읽기 접근마다** 일어날 수 있다. 루프 안이면 재앙이다.

해법은 딱 하나다.

```csharp
readonly struct Vec3            // ← 이 한 단어
{
    public readonly double X, Y, Z;
    public Vec3(double x, double y, double z) => (X, Y, Z) = (x, y, z);
    public double GetLength() => Math.Sqrt(X * X + Y * Y + Z * Z);
}
```

`readonly struct`이면 모든 인스턴스 메서드가 `this`를 고칠 수 없음이 타입 선언에서 보장되므로, 컴파일러는 방어적 복사 없이 원본 주소를 그대로 넘긴다.

| 상황 | `in` 매개변수에서 멤버 접근 시 |
|---|---|
| `readonly struct` 타입 | 복사 없음. 원본 주소로 직접 호출 |
| 일반 `struct` + `readonly` 표시된 멤버 | 그 멤버에 대해서는 복사 없음 |
| 일반 `struct` + 일반 인스턴스 메서드 호출 | **방어적 복사 발생** |
| 일반 `struct` + 필드 직접 읽기 (`a.X`) | 복사 없음 (필드 읽기는 안전이 자명하다) |
| 일반 `struct` + 프로퍼티 읽기 (`a.X` 자동 프로퍼티) | **방어적 복사 발생** (getter도 인스턴스 메서드다) |

마지막 줄이 특히 잔인하다. 필드를 프로퍼티로 바꾸는 흔한 리팩터링만으로 방어적 복사가 부활한다.

> **⚠️ `in`은 "무조건 붙이면 좋은 것"이 절대 아니다**
>
> 세 가지를 기억하면 된다.
>
> 1. **작은 타입에는 붙이지 마라.** `in int`, `in double`, `in DateTime` 같은 것은 주소(8바이트)를 넘기고 매번 역참조하는 비용이 값(4~8바이트)을 그냥 복사하는 비용보다 크다. 대략적인 경계는 포인터 크기의 2~3배, 즉 16~24바이트 언저리다. 그보다 작으면 값 전달이 낫다.
> 2. **`readonly struct`가 아니면 붙이지 마라.** 방어적 복사 때문에 오히려 느려진다.
> 3. **믿지 말고 재라.** 이 판단의 실제 방법론은 67장에서 다룬다.
>
> `readonly struct`와 `readonly` 멤버가 방어적 복사를 어떻게 제거하는지의 전모는 16.5절이다.

### 성능 영향 — 언제 어느 것이 이기는가

| 시나리오 | 권장 | 근거 |
|---|---|---|
| `int`, `long`, `double` 등 원시 타입 입력 | 값 | 복사가 레지스터 이동 한 번이다 |
| 참조 타입 입력 (객체를 읽기만) | 값 | 어차피 참조 하나만 복사된다 |
| 참조 타입 변수를 갈아끼워야 함 | `ref` | 값 전달로는 불가능하다 |
| 값을 하나 더 반환해야 함 | `out` | 튜플 반환도 대안이다(77.1절) |
| 성공/실패 + 결과 (`TryParse` 패턴) | `out` | 예외를 피하는 표준 관용구다(32.9절) |
| 24바이트 이상 `readonly struct` 입력 | `in` | 복사 제거가 실제로 이득이다 |
| 24바이트 이상 일반 `struct` 입력 | 먼저 `readonly struct`로 | 아니면 `in`이 손해다 |
| `Span<T>` 같은 `ref struct` 입력 | 값 | 이미 16바이트 남짓이고 자체가 참조다(68.2절) |

> **💡 `out`을 세 개 이상 쓰고 있다면 설계를 의심하라**
>
> `out` 매개변수는 "값을 하나 더 돌려주는" 도구다. 셋 이상이 되면 그건 반환할 타입이 하나 필요하다는 신호다. 튜플(77장)이나 작은 `readonly record struct`(19.2절)를 반환하는 편이 호출부에서 훨씬 읽기 좋다. `out`이 여전히 이기는 경우는 딱 하나 — `TryXxx` 패턴처럼 `bool` 반환과 결과가 짝을 이루고, 실패 경로에서 할당을 0으로 유지해야 할 때다.

> **⚠️ 반복자와 비동기 메서드에는 `ref`/`out`/`in`을 쓸 수 없다**
>
> `yield return`을 쓰는 메서드나 `async` 메서드는 컴파일러가 상태 기계 클래스로 바꾸면서 매개변수를 **필드로 옮긴다**(28.4절, 47장). 관리 포인터는 필드에 저장할 수 없으므로(정확히는 `ref struct`의 `ref` 필드로만 가능하며 이는 68.11절의 주제다) 언어 차원에서 금지된다. 람다와 지역 함수도 그 매개변수를 캡처하는 순간 같은 제약에 걸린다.

## 10.3 `ref` 지역 변수와 `ref` 반환

C# 7은 관리 포인터를 매개변수 바깥으로 꺼냈다. 지역 변수도, 메서드의 반환값도 `ref`가 될 수 있다.

### `ref` 지역 변수

```csharp
int[] numbers = { 0, 1, 2, 3, 4 };
ref int numRef = ref numbers[2];    // numbers[2]를 '가리키는' 지역 변수

numRef *= 10;
Console.WriteLine(numRef);          // 20
Console.WriteLine(numbers[2]);      // 20 — 배열 요소가 실제로 바뀌었다
```

`ref int numRef = ref numbers[2];`에서 `ref`가 **두 번** 나온다. 왼쪽 `ref`는 "이 지역 변수는 관리 포인터다", 오른쪽 `ref`는 "값이 아니라 위치를 가져와라"라는 뜻이다. 둘 다 필수다.

**별칭**(alias)이라는 표현이 정확하다. `numRef`는 `numbers[2]`의 다른 이름이다.

```text
       스택                              관리 힙
  ┌───────────────┐              ┌──────────────────────────────┐
  │ numbers : 참조 │────────────▶│ int[5]  [0][1][2][3][4]      │
  ├───────────────┤              │              ▲               │
  │ numRef : int& │──────────────┼──────────────┘               │
  └───────────────┘              └──────────────────────────────┘

  numRef에 쓰면 배열 요소가 바뀐다. 둘은 같은 저장 위치다.
```

`ref` 지역 변수의 대상이 될 수 있는 것은 정해져 있다.

| 대상 | 가능? |
|---|---|
| 배열 요소 (`a[i]`) | 가능 |
| 필드 (`obj.field`, `staticField`) | 가능 |
| 다른 지역 변수 | 가능 |
| `ref`/`out`/`in` 매개변수 | 가능 |
| 프로퍼티 (`obj.Prop`) | **불가** — 프로퍼티는 저장 위치가 아니라 메서드다 |
| 인덱서 (`list[i]`) | **불가** — 같은 이유 (단, `ref` 반환 인덱서는 예외) |
| 상수, 리터럴, 계산식 (`x + 1`) | 불가 |
| `readonly` 필드 (생성자 밖에서) | `ref readonly`로만 가능 |

> **⚠️ `ref` 지역 변수는 "다시 가리키게" 하는 문법이 따로 있다**
>
> 다음 두 줄은 완전히 다른 일을 한다.
>
> ```csharp
> ref int r = ref a[0];
> r = a[1];              // (1) a[0]에 a[1]의 '값'을 쓴다
> r = ref a[1];          // (2) r이 이제 a[1]을 가리킨다  ※C# 7.3
> ```
>
> (1)은 대입이고 (2)는 재바인딩(rebinding)이다. `= ref`가 재바인딩 문법이며 C# 7.3부터 쓸 수 있다. C# 7.0~7.2에서는 `ref` 지역 변수를 한 번 바인딩하면 바꿀 수 없었다.

### `ref` 반환

메서드가 값이 아니라 저장 위치를 반환할 수 있다.

```csharp
class Program
{
    static string x = "Old Value";

    static ref string GetX() => ref x;      // ref 반환

    static void Main()
    {
        ref string xRef = ref GetX();       // ref 지역 변수로 받는다
        xRef = "New Value";
        Console.WriteLine(x);               // New Value
    }
}
```

호출부에서 `ref`를 빼면 평범한 값 반환으로 격하된다.

```csharp
string localX = GetX();     // 합법. localX는 평범한 지역 변수이고 복사본을 받는다
```

IL에서는 반환 타입이 `string&`가 된다.

```il
.method private hidebysig static string& GetX() cil managed
{
  IL_0000:  ldsflda    string Program::x     // 정적 필드의 '주소'
  IL_0005:  ret
}
```

배열 요소를 반환하는 쪽이 더 실전적이다.

```csharp
static ref int Slot(int[] a, int i) => ref a[i];

int[] data = new int[10];
Slot(data, 3) = 42;              // 반환된 위치에 직접 대입한다
Console.WriteLine(data[3]);      // 42
```

```il
.method private hidebysig static int32& Slot(int32[] a, int32 i) cil managed
{
  IL_0000:  ldarg.0
  IL_0001:  ldarg.1
  IL_0002:  ldelema    [System.Runtime]System.Int32
  IL_0007:  ret
}
```

`ldelema`(load element address)가 배열 요소의 주소를 만드는 IL 명령이다.

### `ref` 반환 프로퍼티와 인덱서

프로퍼티와 인덱서도 `ref`를 반환할 수 있다.

```csharp
static ref string Prop => ref x;

Prop = "New Value";                // set 접근자가 없는데도 쓸 수 있다
```

이런 프로퍼티는 **암시적으로 쓰기 가능**하다. `set` 접근자를 명시적으로 정의하는 것은 오히려 불법이다. 쓰기를 막으려면 `ref readonly`를 쓴다.

```csharp
static ref readonly string Prop => ref x;    // 읽기만 가능, 복사는 여전히 없음
```

> **📌 `ref readonly`가 실제로 이득이 되는 조건**
>
> 위 예제의 `x`는 `string`, 즉 참조 타입이다. 문자열이 아무리 길어도 복사되는 것은 참조 4/8바이트뿐이다. **`ref readonly`로 아낄 수 있는 것이 그 4/8바이트가 전부**이므로 사실상 이득이 없다.
>
> 진짜 이득은 큰 값 타입에서 나온다. 그리고 그 값 타입이 `readonly struct`여야 한다 — 아니면 10.2절에서 본 방어적 복사가 그대로 재현된다.

### 안전성 규칙 — 스택을 벗어나는 참조는 막힌다

관리 포인터의 존재는 새로운 위험을 만든다. 이미 사라진 스택 슬롯을 가리키는 포인터를 반환하면 어떻게 되겠는가?

```csharp
static ref int Broken()
{
    int local = 42;
    return ref local;      // 컴파일 오류
}
```

컴파일러가 막는다. 반환할 수 있는 것은 **호출자보다 오래 사는 저장 위치**뿐이다.

| 반환 가능 | 반환 불가 |
|---|---|
| 힙에 있는 것 (배열 요소, 클래스 필드) | 메서드의 지역 변수 |
| 정적 필드 | `stackalloc`으로 잡은 메모리 |
| `ref`/`out`/`in` 매개변수 (호출자 것이므로) | 값으로 받은 매개변수 |
| 위 것들을 반환하는 다른 `ref` 반환 메서드의 결과 | 임시 값 |

이 규칙 체계는 C# 11의 `scoped` 한정자와 `ref` 필드가 들어오면서 훨씬 정교해졌다. 전체 규칙과 `Span<T>`가 이 위에 어떻게 지어졌는지는 68.11절과 68.12절에서 다룬다.

> **💡 `ref` 지역 변수와 `ref` 반환은 미세 최적화 기능이다**
>
> 원서의 표현을 빌리면 "다소 난해한(esoteric) 기능"이다. 일반적인 애플리케이션 코드에서 이걸 써야 할 일은 거의 없다. 존재 이유의 90퍼센트는 `Span<T>`와 `ReadOnlySpan<T>`가 고효율 인덱서를 구현할 수 있게 하는 것이었다(68.2절).
>
> 다만 아는 것 자체는 가치가 있다. **`Span<T>`, `Dictionary<K,V>.CollectionsMarshal.GetValueRefOrNullRef`, `List<T>`의 `CollectionsMarshal.AsSpan` 같은 고성능 API가 왜 그런 모양인지**를 설명해 주기 때문이다.

## 10.4 선택적 매개변수와 명명된 인수 — 버전 관리 함정

### 문법

매개변수 선언에 기본값을 주면 **선택적 매개변수**(optional parameter)가 된다.

```csharp
void Foo(int x = 23) => Console.WriteLine(x);

Foo();      // 23
Foo(5);     // 5
```

**명명된 인수**(named argument)는 위치 대신 이름으로 인수를 지정한다.

```csharp
void Bar(int a = 0, int b = 0, int c = 0, int d = 0) { }

Bar(d: 3);              // a, b, c는 기본값, d만 3
Bar(c: 1, a: 2);        // 순서를 바꿔도 된다
```

둘은 사실상 한 쌍으로 설계되었다. 선택적 매개변수가 여럿일 때 그중 뒤쪽 하나만 지정하려면 명명된 인수가 반드시 필요하다.

### 규칙 정리

| 규칙 | 내용 |
|---|---|
| 기본값의 종류 | 상수 식, 값 타입의 매개변수 없는 생성자(`new Guid()`), `default` 식 |
| 런타임 값 금지 | `DateTime.Now` 같은 것은 불가 — 컴파일 타임에 알 수 없다 |
| 위치 | 필수 매개변수가 선택적 매개변수보다 **앞**에 와야 한다 |
| 예외 | `params` 매개변수는 선택적 매개변수보다도 뒤, 항상 맨 마지막 |
| `ref`/`out` | 기본값을 줄 수 없다 |
| 적용 대상 | 메서드, 생성자, 인덱서, 델리게이트 선언 |
| 명명된 인수 위치 | 위치 인수 뒤에 와야 한다. 단, 올바른 위치에 있으면 섞어도 된다 ※C# 7.2 |
| 인수 평가 순서 | **호출부에 나타난 순서대로**, 이름과 무관 |

마지막 두 줄을 코드로 확인한다.

```csharp
void Foo(int x, int y) => Console.WriteLine($"{x}, {y}");

Foo(x: 1, y: 2);        // OK
Foo(y: 2, x: 1);        // OK — 순서 무관
Foo(1, y: 2);           // OK — 위치 인수 뒤에 명명된 인수
Foo(x: 1, 2);           // OK ※C# 7.2 — 2가 선언된 위치(두 번째)에 있다
Foo(y: 2, 1);           // 오류 — 1이 y 자리에 있는데 x가 되려 한다
```

평가 순서는 인수 표현식에 부수 효과가 있을 때만 눈에 보인다.

```csharp
int a = 0;
Foo(y: ++a, x: --a);    // 출력: 0, 1
```

`++a`가 먼저 평가되어 `a`는 1이 되고 그것이 `y`가 된다. 그다음 `--a`가 평가되어 `a`는 0이 되고 그것이 `x`가 된다. 호출은 `Foo(0, 1)`이다. 컴파일러가 임시 변수 두 개를 만들어 왼쪽부터 채운 뒤 선언 순서로 재배열한다.

> **⚠️ 이런 코드를 실제로 쓰지 마라**
>
> 위 예제는 규칙을 확인하기 위한 것이지 관용구가 아니다. 인수 위치에 부수 효과가 있는 식을 넣는 순간, 코드를 읽는 모든 사람이 평가 순서 규칙을 외우고 있어야 한다. 부수 효과는 별도의 문으로 빼라.

### 컴파일 결과 — 기본값은 호출부에 구워진다

이것이 이 절의 핵심이다.

```csharp
void Foo(int x = 23) => Console.WriteLine(x);
Foo();
```

컴파일 결과의 호출부는 `Foo()`가 아니다.

```il
  IL_0000:  ldarg.0
  IL_0001:  ldc.i4.s   23          // ← 23이 호출부에 직접 박혔다
  IL_0003:  call       instance void Program::Foo(int32)
```

메서드 쪽 메타데이터는 이렇게 생겼다.

```il
.method private hidebysig instance void  Foo([opt] int32 x) cil managed
{
  .param [1] = int32(0x00000017)      // 0x17 = 23
  // ...
}
```

`[opt]`는 "이 매개변수는 생략 가능"이라는 표시이고, `.param [1] = ...`는 메타데이터에 기록된 기본값이다. 컴파일러는 호출부에서 인수가 빠진 것을 보면 **호출 대상 어셈블리의 메타데이터에서 기본값을 읽어 와 호출 코드에 상수로 심는다.**

> **📌 언어 중립적인 표현이 필요했다**
>
> 선택적 매개변수가 C# 전용 기능이면 곤란하다. C#으로 만든 라이브러리를 F#이나 VB에서 호출할 때도 같은 기본값이 적용돼야 한다. 그래서 이 정보는 IL 메타데이터에 남는다.
>
> 명시적으로 같은 효과를 내는 특성도 존재한다. `System.Runtime.InteropServices.OptionalAttribute`와 `DefaultParameterValueAttribute`다. COM 상호운용 계열 API가 이 방식으로 선언되어 있으며, C#의 `= 기본값` 문법은 결국 같은 메타데이터로 귀결된다.

### 버전 관리 함정 — 기본값을 바꿔도 호출자는 모른다

기본값이 호출부에 구워진다는 사실에서 곧바로 사고가 따라 나온다.

```text
   [ 라이브러리 v1 ]                   [ 애플리케이션 ]
   MakePath(string f = "Untitled")     MakePath();
                                          │ 컴파일
                                          ▼
                                       MakePath("Untitled")  ← IL에 박힘

   라이브러리를 v2로 교체 (기본값을 "Report"로 변경)
   애플리케이션은 재컴파일하지 않음
                                          │ 실행
                                          ▼
                                       여전히 "Untitled"가 넘어간다
```

라이브러리 개발자는 기본값을 바꿨다고 생각하지만, 재컴파일하지 않은 호출자는 **옛 기본값을 계속 쓴다.** 조용히 어긋나며 예외도 경고도 없다.

같은 이유로 **public 메서드에 선택적 매개변수를 추가하는 것도 바이너리 호환성을 깬다.** 메서드 시그니처 자체가 바뀌기 때문이다. 필수 매개변수를 추가한 것과 정확히 같은 정도로 위험하다.

> **⚠️ 매개변수 이름을 바꾸는 것도 호환성 파괴다**
>
> 명명된 인수 기능이 생긴 순간, **매개변수 이름은 공개 API의 일부가 되었다.**
>
> ```csharp
> // v1
> void M(int x, DateTime dt) { }
> M(5, dt: DateTime.Now);            // 호출자 코드
>
> // v2 — 매개변수 이름을 dt에서 dateTime으로 "정리"
> void M(int x, DateTime dateTime) { }
> ```
>
> 호출자를 재컴파일하면 `error CS1739: The best overload for 'M' does not have a parameter named 'dt'.`가 난다. 이미 컴파일된 바이너리는 계속 동작하지만(이름은 IL 호출에 남지 않으므로), 소스 호환성이 깨진다.
>
> 리팩터링 도구의 "매개변수 이름 변경"은 라이브러리 코드에서는 위험한 버튼이다.

### 회피 관용구 — 센티널 값

기본값 변경 위험을 없애는 표준 기법이 있다. **기본값 자체를 `null`이나 `0` 같은 센티널(sentinel)로 두고, 진짜 기본값은 메서드 본문에서 결정하는 것**이다.

```csharp
// 이렇게 하지 마라
static string MakePath(string filename = "Untitled")
    => $@"C:\{filename}.txt";

// 이렇게 하라
static string MakePath(string filename = null)
    => $@"C:\{filename ?? "Untitled"}.txt";
```

두 번째 버전에서는 호출부에 `null`이 박힌다. 나중에 "Untitled"를 "Report"로 바꾸고 싶으면 **라이브러리만 다시 빌드하면 된다.** 호출자는 여전히 `null`을 넘기고, 새 본문이 그것을 "Report"로 해석한다.

값 타입 매개변수라면 널 가능 값 타입(`int?`)이 같은 역할을 한다(21장).

> **💡 언제 선택적 매개변수를 쓰고 언제 오버로드를 쓰나**
>
> 짧게 답하면 이렇다.
>
> - **어셈블리 내부에서만 쓰는 메서드** — 선택적 매개변수를 마음껏 쓰라. 항상 함께 컴파일되므로 위험이 없다.
> - **공개 API의 새 메서드** — 선택적 매개변수를 쓰되, 기본값은 센티널로 두라.
> - **이미 배포된 공개 API** — 매개변수를 추가해야 한다면 **오버로드를 추가하라.** 기존 시그니처를 그대로 두는 것이 유일한 안전한 길이다.
>
> 오버로드 폭발과 선택적 매개변수 사이의 저울질은 78.4절에서 설계 관점으로 다시 다룬다. 바이너리 호환성을 깨는 변경의 전체 목록은 78.13절이다.

> **⚠️ 인수를 콤마만 남기고 건너뛸 수는 없다**
>
> ```csharp
> M(1, , DateTime.Now);       // 오류. C#은 이 문법을 지원하지 않는다
> ```
>
> 콤마를 세어서 읽어야 하는 코드를 만들지 않겠다는 설계 결정이다. 중간을 건너뛰려면 명명된 인수를 써라. 참고로 `ref`/`out` 매개변수에도 이름을 붙일 수 있으며, 문법은 `M(x: ref a)`다.

## 10.5 `params` 배열과 `params` 컬렉션 ※C# 13

### 문법

마지막 매개변수에 `params`를 붙이면 개수가 정해지지 않은 인수를 받을 수 있다.

```csharp
static int Sum(params int[] ints)
{
    int sum = 0;
    for (int i = 0; i < ints.Length; i++)
        sum += ints[i];
    return sum;
}

int total = Sum(1, 2, 3, 4);            // 10
int total2 = Sum(new int[] { 1, 2, 3, 4 });   // 같은 결과
int zero = Sum();                       // 0 — 길이 0인 배열이 만들어진다
```

호출부는 두 가지 형태 중 아무것이나 쓸 수 있다. 콤마로 나열해도 되고, 배열을 직접 넘겨도 된다.

규칙은 셋뿐이다.

| 규칙 | 내용 |
|---|---|
| 개수 | 메서드당 `params` 매개변수는 하나뿐 |
| 위치 | 반드시 맨 마지막 |
| 타입 | 1차원 배열이어야 한다 (`params` 컬렉션 이전 기준) |

### 컴파일 결과 — 호출부가 배열을 만든다

`Sum(1, 2, 3, 4)`는 다음과 정확히 같다.

```csharp
Sum(new int[] { 1, 2, 3, 4 });
```

IL로 보면 배열 생성이 **호출자 쪽에** 있다.

```il
  IL_0000:  ldc.i4.4
  IL_0001:  newarr     [System.Runtime]System.Int32   // ← 힙 할당
  IL_0006:  dup
  IL_0007:  ldc.i4.0
  IL_0008:  ldc.i4.1
  IL_0009:  stelem.i4
  IL_000a:  dup
  IL_000b:  ldc.i4.1
  IL_000c:  ldc.i4.2
  IL_000d:  stelem.i4
  // ... 나머지 두 요소
  IL_001b:  call       int32 Program::Sum(int32[])
```

메서드 쪽에는 `System.ParamArrayAttribute`가 붙는다.

```il
.method private hidebysig static int32 Sum(int32[] ints) cil managed
{
  .param [1]
  .custom instance void [System.Runtime]System.ParamArrayAttribute::.ctor() = ( 01 00 00 00 )
  // ...
}
```

이 특성이 컴파일러에게 "이 배열 매개변수는 나열형 호출을 받아도 된다"고 알려 준다.

### 오버로드 해석에서의 순위

컴파일러는 호출을 만나면 **`params`가 없는 후보를 먼저 본다.** 그중 맞는 것이 있으면 그것을 쓰고, 없을 때만 `params` 후보를 찾는다.

```csharp
static void Log(string a) => Console.WriteLine("1개");
static void Log(params string[] all) => Console.WriteLine($"{all.Length}개");

Log("x");           // "1개" — params 없는 쪽이 이긴다
Log("x", "y");      // "2개"
Log();              // "0개"
```

이 규칙이 `String.Concat`의 오버로드 구성을 설명한다.

```csharp
public static string Concat(object arg0);
public static string Concat(object arg0, object arg1);
public static string Concat(object arg0, object arg1, object arg2);
public static string Concat(params object[] args);
public static string Concat(string str0, string str1);
public static string Concat(string str0, string str1, string str2);
public static string Concat(string str0, string str1, string str2, string str3);
public static string Concat(params string[] values);
```

인수 두세 개짜리 호출이 압도적으로 흔하므로, 그 경우만 배열 없이 처리하도록 전용 오버로드를 깔아 둔 것이다. 흔하지 않은 경우만 `params`가 받아 배열을 만든다.

### 성능 영향 — 호출마다 힙 할당

`params` 호출 한 번은 **배열 객체 하나를 힙에 할당한다.** 요소 개수만큼 초기화도 한다. 그 배열은 결국 GC가 회수한다.

| 호출 형태 | 할당 |
|---|---|
| `Sum(1, 2, 3)` | `int[3]` 하나 (힙) |
| `Sum()` | `int[0]` 하나 — 컴파일러에 따라 `Array.Empty<int>()`로 최적화 |
| `Sum(existingArray)` | 없음 — 있는 배열을 그대로 넘긴다 |
| `Sum(null)` | 없음 — `ints`가 `null`이 된다 |

`Sum(null)`이 컴파일되고 실행된다는 사실은 함정이기도 하다. `params` 매개변수는 `null`일 수 있다.

> **⚠️ `params` 매개변수를 `null` 검사 없이 순회하지 마라**
>
> ```csharp
> static int Sum(params int[] ints)
> {
>     int sum = 0;
>     for (int i = 0; i < ints.Length; i++)   // ints가 null이면 NullReferenceException
>         sum += ints[i];
>     return sum;
> }
>
> Sum(null);      // 컴파일된다. 그리고 터진다.
> ```
>
> 방어적으로 쓰려면 `if (ints != null)`을 넣거나, `Sum((int[])null)`처럼 명시적으로 `null` 배열을 넘기는 호출을 API 계약에서 금지하라. 최신 프로젝트에서는 널 가능 참조 타입 주석(21.6절)이 이 실수를 경고로 잡아 준다.

> **💡 핫 패스에 `params`가 있으면 오버로드를 깔아라**
>
> 초당 수백만 번 불리는 로깅 메서드나 포매팅 메서드에 `params`가 있으면, 그 배열 할당이 전부 gen0 쓰레기가 된다. BCL이 `Concat`에서 한 것과 같은 방식 — 인수 1~3개짜리 전용 오버로드를 추가 — 이 가장 단순하고 효과적인 대응이다.
>
> 숨은 할당의 전체 카탈로그는 63.9절에 있고, 할당을 줄이는 기법 전반은 69장이다.

### `params` 컬렉션 ※C# 13

C# 13은 `params`의 대상을 배열 밖으로 넓혔다. 이제 `params`를 붙일 수 있는 타입은 다음과 같다.

```csharp
static void A(params ReadOnlySpan<int> values) { }   // 할당 없이 받을 수 있다
static void B(params List<int> values) { }
static void C(params IEnumerable<int> values) { }
```

가장 중요한 것은 첫 줄이다. `params ReadOnlySpan<T>`이면 컴파일러가 인수를 **스택 또는 재사용 가능한 저장소**에 담아 넘길 수 있어, 호출마다 배열을 힙에 할당하지 않는다. `params`의 가장 큰 약점이 없어진 셈이다.

오버로드가 여럿이면 **가장 "구체적"인 컬렉션 타입**이 선택된다. 대략적인 우선순위는 스팬 계열이 배열보다, 배열이 인터페이스보다 앞이다.

> **📌 이것이 왜 지금에서야 가능해졌나**
>
> `params ReadOnlySpan<T>`는 세 가지 앞선 기능이 모여야 성립한다. `ref struct`로서의 `Span<T>`(C# 7.2), 그것을 안전하게 만드는 `scoped`와 `ref` 필드 규칙(C# 11), 그리고 컬렉션 식(C# 12)이 만든 "임의의 컬렉션 타입을 요소 나열로부터 만든다"는 공통 기반이다. C# 13의 `params` 컬렉션은 그 위에 얹힌 문법 설탕에 가깝다.
>
> 언어 진화의 이 흐름은 76.12절에서, `Span<T>`의 내부 구조는 68.2절에서 다룬다.

## 10.6 `var` — 암시적 지역 변수 타입의 규칙과 오해

### 문법

초기화 식만으로 타입을 알 수 있으면 타입 이름 대신 `var`를 쓸 수 있다.

```csharp
var x = "hello";
var y = new System.Text.StringBuilder();
var z = (float)Math.PI;
```

이것은 다음과 **완전히 동일하다.**

```csharp
string x = "hello";
System.Text.StringBuilder y = new System.Text.StringBuilder();
float z = (float)Math.PI;
```

"완전히 동일하다"는 말은 문자 그대로다. 컴파일 결과 IL이 한 바이트도 다르지 않다. `var`는 **컴파일러가 타입 이름을 대신 적어 주는 것**일 뿐이며, 컴파일이 끝나면 흔적이 남지 않는다.

그래서 `var` 변수는 여전히 정적 타입이다.

```csharp
var x = 5;
x = "hello";      // 오류 — x는 int다
```

### 규칙 — 되는 곳과 안 되는 곳

| 자리 | 가능? | 비고 |
|---|---|---|
| 지역 변수 선언 | 가능 | 초기화 식이 반드시 있어야 한다 |
| `for` 초기화부 | 가능 | `for (var i = 0; ...)` |
| `foreach` 반복 변수 | 가능 | 컬렉션 요소 타입이 추론된다 |
| `using` 선언 | 가능 | |
| 메서드 매개변수 | **불가** | 호출부가 없거나 여럿이라 추론 불가 |
| 메서드 반환 타입 | **불가** | 같은 이유 |
| 필드 (인스턴스·정적) | **불가** | 여러 메서드가 보는 계약은 명시해야 한다 |
| 상수 (`const var`) | **불가** | |
| `var`로의 캐스트 (`(var)x`) | **불가** | `var`는 타입 이름이 아니다 |
| 초기화 없는 선언 (`var x;`) | **불가** | 추론할 근거가 없다 |
| `var x = null;` | **불가** | `null`은 어떤 참조 타입으로도 변환 가능해 하나로 정할 수 없다 |
| `var x = (string)null;` | 가능 | 캐스트가 타입을 확정한다. 다만 실익은 없다 |
| 익명 타입 담기 | **필수** | 이름이 없는 타입이므로 다른 방법이 없다 |

`var x = null;`은 `error CS0815: Cannot assign <null> to an implicitly-typed local variable`을 낸다.

필드에 `var`가 금지된 이유는 두 가지다. 하나는 필드가 여러 메서드에서 읽히는 계약이므로 타입이 명시되어야 한다는 설계 판단이고, 다른 하나는 허용하면 **익명 타입이 메서드 밖으로 새어 나갈 수 있기 때문**이다(익명 타입은 13장 이후, 79.10절에서 다룬다).

### 익명 타입 — `var`가 선택이 아닌 자리

```csharp
var person = new { Name = "Alice", Age = 30 };
Console.WriteLine(person.Name);
```

`new { ... }`가 만드는 타입은 컴파일러가 자동 생성한 것이고 소스 코드에 적을 수 있는 이름이 없다. 따라서 `var` 없이는 담을 방법이 자체가 없다. LINQ의 `select new { ... }` 절이 이 조합을 대량으로 쓴다(29장).

### 성능 — 영향 없음

`var`는 **런타임 성능에 아무 영향이 없다.** 이 문장을 명확히 해 두는 이유는, `var`를 동적 타입으로 오해하는 경우가 흔하기 때문이다.

| 항목 | `var` | `dynamic` |
|---|---|---|
| 결정 시점 | 컴파일 타임 | 런타임 |
| 쓸 수 있는 자리 | 지역 변수만 | 지역 변수, 필드, 매개변수, 반환 타입 |
| 초기화 필수 | 필수 | 불필요 |
| 캐스트 대상 (`(T)x`) | 불가 | 가능 |
| 멤버 접근 검사 | 컴파일 타임 | 런타임 (DLR 호출 사이트) |
| 성능 | 명시 타입과 동일 | 호출 사이트 캐시·바인딩 비용 |
| IL에 흔적 | 없음 | `object` + `[Dynamic]` 특성 + 바인딩 코드 |

`dynamic`은 59장의 주제다.

> **⚠️ `var`와 `dynamic`을 혼동하면 성능 사고가 난다**
>
> `var`는 타이핑을 줄이는 문법 설탕이고 `dynamic`은 런타임 바인딩을 켜는 스위치다. 이름이 비슷해 보인다는 이유로 섞어 쓰면, "왜 이 루프만 100배 느리지"라는 질문에 도달한다.
>
> 구분하는 가장 간단한 방법 — **Visual Studio에서 `var` 위에 마우스를 올리면 컴파일러가 추론한 실제 타입이 툴팁으로 뜬다.** `dynamic`은 그런 것이 없다.

### 가독성 — 이 책의 입장

```csharp
Random r = new Random();
var x = r.Next();
```

`x`의 타입이 무엇인가? `Next()`의 반환 타입을 외우고 있어야 답할 수 있다(`int`다). 이것이 `var`의 대가다.

반대로 이런 경우에는 `var`가 명백히 낫다.

```csharp
Dictionary<string, List<Customer>> map = new Dictionary<string, List<Customer>>();
var map2 = new Dictionary<string, List<Customer>>();     // 오른쪽에 이미 타입이 있다
```

> **💡 `var` 판단 기준 세 줄 요약**
>
> 1. **오른쪽에 타입 이름이 이미 보이면 `var`를 쓰라.** `new`, 캐스트, `as`가 여기 해당한다. 같은 이름을 두 번 적는 것은 소음이다.
> 2. **오른쪽이 메서드 호출이면 타입을 적으라.** 반환 타입이 코드에 안 보이면 독자가 IDE에 의존하게 된다.
> 3. **익명 타입이면 선택의 여지가 없다.**
>
> 팀 컨벤션으로 이 규칙을 강제하는 방법(`.editorconfig`의 `csharp_style_var_*` 옵션)과 더 자세한 판단 기준은 79.1절에서, 도구로 강제하는 방법은 79.13절에서 다룬다.

## 10.7 대상 타입 지정 `new` 식 ※C# 9

### 문법

`var`가 오른쪽 타입 이름으로 왼쪽을 채우는 기능이라면, **대상 타입 지정 `new`**(target-typed new)는 왼쪽 타입 이름으로 오른쪽을 채우는 기능이다.

```csharp
System.Text.StringBuilder sb1 = new();
System.Text.StringBuilder sb2 = new("Test");
```

이것은 다음과 정확히 같다.

```csharp
System.Text.StringBuilder sb1 = new System.Text.StringBuilder();
System.Text.StringBuilder sb2 = new System.Text.StringBuilder("Test");
```

원칙은 하나다. **컴파일러가 타입을 모호하지 않게 추론할 수 있으면 타입 이름을 생략할 수 있다.**

### `var`로는 안 되고 이것으로만 되는 자리

`var`는 지역 변수에서만 쓸 수 있다. 대상 타입 지정 `new`는 **타입이 왼쪽에 이미 적혀 있는 모든 자리**에서 쓸 수 있다. 그래서 `var`가 못 가는 곳까지 간다.

**필드 초기화 / 생성자 안의 대입**

```csharp
class Foo
{
    System.Text.StringBuilder sb;

    public Foo(string initialValue)
    {
        sb = new(initialValue);     // 필드 선언에 타입이 있으므로 추론된다
    }
}
```

**메서드 인수**

```csharp
void MyMethod(System.Text.StringBuilder sb) { }

MyMethod(new("test"));      // 매개변수 타입으로 추론
```

**배열·컬렉션 초기화자**

```csharp
Point[] points = { new(0, 0), new(1, 1), new(2, 4) };
List<Customer> list = new() { new("Alice"), new("Bob") };
```

**반환문**

```csharp
static Dictionary<string, int> Create() => new();
```

세 문법을 나란히 두면 역할이 뚜렷해진다.

| 문법 | 타입 이름이 적히는 쪽 | 쓸 수 있는 자리 |
|---|---|---|
| `Foo f = new Foo();` | 양쪽 | 어디나 |
| `var f = new Foo();` | 오른쪽만 | 지역 변수만 |
| `Foo f = new();` | 왼쪽만 | 타입이 명시된 모든 자리 |

> **📌 대상 타입 추론은 `new`만의 이야기가 아니다**
>
> 같은 원리가 다른 곳에도 적용된다. 조건 연산자(`?:`)의 대상 타입 추론(C# 9), 대상 타입 지정 `switch` 식, 그리고 `default` 리터럴(C# 7.1)이 모두 "왼쪽 타입으로 오른쪽을 결정한다"는 같은 아이디어다.
>
> ```csharp
> decimal d = default;              // default(decimal)과 같다 ※C# 7.1
> Stream s = flag ? new MemoryStream() : new FileStream(path, FileMode.Open);
> ```

### 컴파일 결과와 성능

`var`와 마찬가지로 **IL이 전혀 달라지지 않는다.** `new()`는 컴파일 타임에 완전한 `new T(...)`로 치환되며, 런타임에는 아무 흔적도 남지 않는다.

> **⚠️ 남용하면 읽을 수 없는 코드가 된다**
>
> 이 기능은 반복을 줄이라고 만든 것이지 타입을 숨기라고 만든 것이 아니다. 다음 코드는 합법이지만 나쁘다.
>
> ```csharp
> Process(new(), new(), new());       // 무엇이 세 개 만들어지는가?
> ```
>
> 메서드 시그니처를 찾아가야만 읽을 수 있다. 규칙은 `var`와 대칭이다 — **왼쪽 타입이 같은 화면에 보일 때만 `new()`를 쓰라.** 필드 초기화와 지역 변수 선언은 거의 항상 그 조건을 만족하고, 메서드 인수는 거의 항상 만족하지 않는다.

## 10.8 기본 식(primary expression), void 식, 할당 식

### 식이란 무엇인가

**식**(expression)은 값을 나타내는 문법 단위다. 가장 단순한 식은 상수와 변수다.

```csharp
12                  // 상수 식
x                   // 변수 식
12 * 30             // 연산자로 결합한 식
1 + (12 * 30)       // 피연산자 자리에 다시 식이 올 수 있다
```

연산자는 피연산자(operand)를 하나 이상 받아 새 식을 만든다. 피연산자 개수에 따라 **단항**(unary), **이항**(binary), **삼항**(ternary)으로 나뉜다. 이항 연산자는 언제나 **중위 표기법**(infix)을 쓴다 — 연산자가 두 피연산자 사이에 놓인다.

### 기본 식

**기본 식**(primary expression)은 언어의 기본 배관에 해당하는 연산자로 이루어진 식이다.

```csharp
Math.Log(1)
```

이 한 줄에 기본 식이 둘 들어 있다. `.` 연산자가 멤버를 찾고, `()` 연산자가 메서드를 호출한다. 10.9절 연산자 표의 "기본" 범주에 속하는 것들 — `.`, `?.`, `()`, `[]`, `new`, `typeof`, `nameof`, `default`, `sizeof`, `checked`, 후위 `++`/`--` — 이 전부 기본 식을 만든다.

### void 식

값이 없는 식이 **void 식**이다.

```csharp
Console.WriteLine(1)
```

값이 없으므로 다른 식의 피연산자가 될 수 없다.

```csharp
1 + Console.WriteLine(1)     // 컴파일 오류
```

> **📌 `void`는 타입이 아니라 "타입이 없음"이다**
>
> C#에서 `void`는 값의 부재를 나타내는 표시일 뿐 진짜 타입이 아니다. `void v;` 같은 변수는 선언할 수 없고 제네릭 인자로도 쓸 수 없다. `Action`이 존재하는 이유가 그것이다 — `Func<void>`를 쓸 수 없어서 반환값 없는 델리게이트용 타입을 따로 만들어야 했다(26.5절).
>
> 반면 `System.Void`라는 타입은 리플렉션에서 실제로 존재한다. `typeof(void)`도 컴파일된다. 다만 그 타입의 인스턴스는 만들 수 없다.

### 할당 식

`=`는 연산자이고, 따라서 **할당도 식이다.**

```csharp
x = x * 5
```

할당 식은 void 식이 아니다. **할당된 값을 자신의 값으로 갖는다.** 그래서 다른 식 안에 들어갈 수 있다.

```csharp
y = 5 * (x = 2);        // x에 2를 넣고, y에 10을 넣는다
a = b = c = d = 0;      // 오른쪽부터 왼쪽으로 연쇄
```

연쇄 할당이 되는 이유는 `=`가 **오른쪽 결합**(right-associative)이기 때문이다. `a = (b = (c = (d = 0)))`로 묶인다.

**복합 할당 연산자**는 할당과 다른 연산자를 합친 축약이다.

```csharp
x *= 2      // x = x * 2 와 (거의) 같다
x <<= 1     // x = x << 1 와 (거의) 같다
```

"거의"인 이유는 두 가지다. 하나는 복합 할당이 결과를 원래 타입으로 되돌리는 캐스트를 몰래 포함한다는 것이고(7.3절), 다른 하나는 왼쪽 식을 **한 번만** 평가한다는 것이다. `arr[Next()] += 1`은 `Next()`를 한 번 부르고, `arr[Next()] = arr[Next()] + 1`은 두 번 부른다.

> **⚠️ 이벤트의 `+=`와 `-=`는 복합 할당이 아니다**
>
> 겉모습만 같고 완전히 다른 문법이다. 이벤트에 대한 `+=`는 `x = x + y`로 풀리지 않고 이벤트의 `add` 접근자 호출로, `-=`는 `remove` 접근자 호출로 컴파일된다(27.1절). 그래서 이벤트에는 `*=`나 `|=` 같은 다른 복합 할당을 쓸 수 없다.

### 식문(expression statement)

모든 식이 문이 될 수 있는 것은 아니다. **문이 될 수 있는 식**은 상태를 바꾸거나 바꿀 가능성이 있는 것으로 한정된다.

| 문이 될 수 있는 식 | 예 |
|---|---|
| 할당 식 (증감 포함) | `x = 1 + 2;`, `x++;` |
| 메서드 호출 식 (반환값 유무 무관) | `Console.WriteLine(y);`, `list.Add(1);` |
| 객체 생성 식 | `new StringBuilder();` |
| `await` 식 | `await task;` |

```csharp
x + 1;              // 오류 — 이 식은 문이 될 수 없다
x.Equals(y);        // 합법. 단, 결과를 버리므로 쓸모없다
new StringBuilder();// 합법. 단, 즉시 버려지는 객체를 만든다
```

마지막 두 줄은 컴파일러가 통과시키지만 무의미하다. 정적 분석기가 "이 식의 값이 사용되지 않았다"고 경고하는 경우가 많다.

식과 문의 경계, 그리고 각 문의 문법은 11.1절에서 이어진다.

## 10.9 연산자 우선순위와 결합성 — 전체 연산자 표

### 두 규칙

식 하나에 연산자가 여럿 있으면 **우선순위**(precedence)와 **결합성**(associativity)이 계산 순서를 정한다.

**우선순위** — 높은 것이 먼저 묶인다.

```csharp
1 + 2 * 3       // *가 +보다 높으므로  1 + (2 * 3)  = 7
```

**결합성** — 우선순위가 같으면 어느 쪽부터 묶을지를 정한다.

```csharp
8 / 4 / 2       // /는 왼쪽 결합이므로  (8 / 4) / 2  = 1
8 / (4 / 2)     // 괄호로 바꾸면        = 4
```

C#의 이항 연산자는 **할당·람다·null 병합을 제외하고 전부 왼쪽 결합**이다. 오른쪽 결합인 것은 넷이다.

| 오른쪽 결합 연산자 | 예 | 묶이는 방식 |
|---|---|---|
| 할당 계열 (`=`, `+=`, …) | `x = y = 3` | `x = (y = 3)` |
| 람다 `=>` | `x => y => x + y` | `x => (y => x + y)` |
| null 병합 `??` | `a ?? b ?? c` | `a ?? (b ?? c)` |
| 조건 `?:` | `a ? b : c ? d : e` | `a ? b : (c ? d : e)` |

`x = y = 3`이 컴파일되는 이유가 오른쪽 결합성이다. 먼저 `y`에 3이 들어가고, 그 할당 식의 값(3)이 `x`에 들어간다.

### 전체 연산자 표

같은 범주에 있는 연산자는 우선순위가 같다. 위쪽 범주가 아래쪽보다 우선순위가 높다.

**기본(primary) — 가장 높다**

| 연산자 | 이름 | 예 | 사용자 오버로드 |
|---|---|---|---|
| `.` | 멤버 접근 | `x.y` | 불가 |
| `?.` `?[]` | null 조건부 | `x?.y`, `x?[0]` | 불가 |
| `!` (후위) | null 관용 | `x!.y`, `x![0]` | 불가 |
| `->` (unsafe) | 포인터로 구조체 접근 | `x->y` | 불가 |
| `()` | 함수 호출 | `x()` | 불가 |
| `[]` | 배열·인덱스 | `a[x]` | 인덱서로 간접 가능 |
| `++` (후위) | 후위 증가 | `x++` | 가능 |
| `--` (후위) | 후위 감소 | `x--` | 가능 |
| `new` | 인스턴스 생성 | `new Foo()` | 불가 |
| `stackalloc` | 스택 할당 | `stackalloc int[10]` | 불가 |
| `typeof` | 식별자로 타입 얻기 | `typeof(int)` | 불가 |
| `nameof` | 식별자 이름 얻기 | `nameof(x)` | 불가 |
| `checked` | 정수 오버플로 검사 켜기 | `checked(x)` | 불가 |
| `unchecked` | 정수 오버플로 검사 끄기 | `unchecked(x)` | 불가 |
| `default` | 기본값 | `default(char)` | 불가 |
| `await` | 대기 | `await myTask` | 불가 |
| `sizeof` | 구조체 크기 | `sizeof(int)` | 불가 |

**단항(unary)**

| 연산자 | 이름 | 예 | 사용자 오버로드 |
|---|---|---|---|
| `+` | 양의 값 | `+x` | 가능 |
| `-` | 음의 값 | `-x` | 가능 |
| `!` | 논리 부정 | `!x` | 가능 |
| `~` | 비트 보수 | `~x` | 가능 |
| `++` (전위) | 전위 증가 | `++x` | 가능 |
| `--` (전위) | 전위 감소 | `--x` | 가능 |
| `()` | 캐스트 | `(int)x` | 변환 연산자로 간접 가능 |
| `^` | 끝에서부터의 인덱스 | `array[^1]` | 불가 |
| `*` (unsafe) | 주소가 가리키는 값 | `*x` | 불가 |
| `&` (unsafe) | 값의 주소 | `&x` | 불가 |

**범위 / switch·with / 산술**

| 범주 | 연산자 | 이름 | 예 | 사용자 오버로드 |
|---|---|---|---|---|
| 범위 | `..` | 인덱스 범위 | `x..y` | 불가 |
| switch·with | `switch` | switch 식 | `n switch { 1 => true, _ => false }` | 불가 |
| switch·with | `with` | with 식 | `rec with { X = 123 }` | 불가 |
| 곱셈 계열 | `*` | 곱셈 | `x * y` | 가능 |
| 곱셈 계열 | `/` | 나눗셈 | `x / y` | 가능 |
| 곱셈 계열 | `%` | 나머지 | `x % y` | 가능 |
| 덧셈 계열 | `+` | 덧셈 | `x + y` | 가능 |
| 덧셈 계열 | `-` | 뺄셈 | `x - y` | 가능 |
| 시프트 | `<<` | 왼쪽 시프트 | `x << 1` | 가능 |
| 시프트 | `>>` | 오른쪽 시프트 | `x >> 1` | 가능 |
| 시프트 | `>>>` | 부호 없는 오른쪽 시프트 | `x >>> 1` | 가능 |

**비교 / 비트 / 조건 / 할당**

| 범주 | 연산자 | 이름 | 예 | 사용자 오버로드 |
|---|---|---|---|---|
| 관계 | `<` | 작다 | `x < y` | 가능 |
| 관계 | `>` | 크다 | `x > y` | 가능 |
| 관계 | `<=` | 작거나 같다 | `x <= y` | 가능 |
| 관계 | `>=` | 크거나 같다 | `x >= y` | 가능 |
| 관계 | `is` | 타입 검사·패턴 | `x is y` | 불가 |
| 관계 | `as` | 참조 변환 시도 | `x as y` | 불가 |
| 동등 | `==` | 같다 | `x == y` | 가능 |
| 동등 | `!=` | 다르다 | `x != y` | 가능 |
| 비트 AND | `&` | 논리곱·비트곱 | `x & y` | 가능 |
| 비트 XOR | `^` | 배타적 논리합 | `x ^ y` | 가능 |
| 비트 OR | `\|` | 논리합·비트합 | `x \| y` | 가능 |
| 조건 AND | `&&` | 단축 평가 논리곱 | `x && y` | `&`로 간접 가능 |
| 조건 OR | `\|\|` | 단축 평가 논리합 | `x \|\| y` | `\|`로 간접 가능 |
| null 병합 | `??` | null 병합 | `x ?? y` | 불가 |
| 조건 | `?:` | 조건 연산자 | `c ? a : b` | 불가 |
| 할당·람다 | `=` | 할당 | `x = y` | 불가 |
| 할당·람다 | `*=` `/=` `%=` | 곱·나눗셈·나머지 후 할당 | `x *= 2` | 대응 이항 연산자로 간접 |
| 할당·람다 | `+=` `-=` | 덧셈·뺄셈 후 할당 | `x += 2` | 대응 이항 연산자로 간접 |
| 할당·람다 | `<<=` `>>=` `>>>=` | 시프트 후 할당 | `x <<= 2` | 대응 이항 연산자로 간접 |
| 할당·람다 | `&=` `^=` `\|=` | 비트 연산 후 할당 | `x &= 2` | 대응 이항 연산자로 간접 |
| 할당·람다 | `??=` | null 병합 할당 | `x ??= 0` | 불가 |
| 할당·람다 | `=>` | 람다 | `x => x + 1` | 불가 |

> **📌 "간접 가능"의 뜻**
>
> `&&`와 `||`는 직접 오버로드할 수 없다. 대신 타입에 `&`·`|`와 함께 `true`·`false` 연산자를 정의하면 `&&`·`||`가 그것을 이용해 동작한다. 복합 할당(`+=` 등)도 마찬가지로 대응하는 이항 연산자(`+`)를 오버로드하면 따라온다. 인덱서(`[]`)와 캐스트(`()`)도 각각 인덱서 선언과 변환 연산자 선언으로 "간접" 정의된다.
>
> 상세는 22장의 주제이며, 특히 `true`/`false` 연산자는 22.5절이다.

### 우선순위와 평가 순서는 다른 것이다

이 절에서 반드시 붙잡아야 할 사실이다.

**우선순위는 "무엇이 무엇의 피연산자인가"를 정한다. "누가 먼저 실행되는가"는 정하지 않는다.**

```csharp
int A() { Console.Write("A"); return 1; }
int B() { Console.Write("B"); return 2; }
int C() { Console.Write("C"); return 3; }

int r = A() + B() * C();      // 출력: ABC
```

`*`가 `+`보다 우선순위가 높지만, **출력은 `ABC`다.** C#은 피연산자를 **언제나 왼쪽에서 오른쪽으로** 평가한다. 우선순위가 하는 일은 "곱셈의 결과가 덧셈의 오른쪽 피연산자가 된다"는 구조를 정하는 것뿐이다.

이 규칙은 인수 목록에도, 배열 초기화자에도, 객체 초기화자에도 똑같이 적용된다. 10.4절에서 명명된 인수의 평가 순서가 이름과 무관하게 소스 순서를 따르는 것도 같은 원칙이다.

> **⚠️ C와 C++에서 오는 사람이 가장 많이 틀리는 지점**
>
> C와 C++에서는 피연산자 평가 순서가 대체로 **미정의**(unspecified)다. 그래서 `f() + g()`에서 어느 것이 먼저 불릴지 컴파일러가 정하고, 최적화 수준에 따라 달라질 수도 있다.
>
> **C#은 다르다.** 왼쪽에서 오른쪽 평가가 언어 사양으로 못 박혀 있다. 이식성 걱정 없이 의존해도 된다.
>
> 다만 "의존해도 된다"와 "의존하는 코드를 쓰라"는 다른 이야기다. 부수 효과 두 개의 순서에 의미가 있으면 문 두 개로 나눠 쓰는 편이 언제나 낫다.

> **⚠️ 우선순위를 외우지 말고 괄호를 쓰라**
>
> 이 표를 통째로 외운 사람은 실무에 없다. 실제로 필요한 것은 다음 네 가지 감각이다.
>
> 1. **산술이 비교보다, 비교가 논리보다 높다.** `a + 1 > b && c`는 `((a+1) > b) && c`다.
> 2. **`&`, `^`, `|`가 비교보다 낮다.** 이게 함정이다. `if (flags & Mask == Mask)`는 `flags & (Mask == Mask)`로 묶이며 대개 컴파일 오류가 난다. 괄호가 필수다.
> 3. **`??`는 매우 낮다.** `a ?? b + c`는 `a ?? (b + c)`다.
> 4. **`?:`는 할당 바로 위다.** `x = a ? b : c`는 의도대로 묶인다.
>
> 나머지는 괄호로 해결하라. 괄호는 공짜다 — IL에 아무 흔적도 남기지 않는다.

## 10.10 null 연산자 — `??`, `??=`, `?.`, `?[]`

C#은 null을 다루는 전용 연산자 넷을 제공한다. 넷 다 공통점이 하나 있다 — **왼쪽이 null인지 검사하고, null이면 오른쪽을 건너뛴다.**

### `??` — null 병합 연산자

"왼쪽이 null이 아니면 그것을, null이면 오른쪽을 달라."

```csharp
string s1 = null;
string s2 = s1 ?? "nothing";        // "nothing"
```

**왼쪽이 null이 아니면 오른쪽 식은 아예 평가되지 않는다.** 이 단축 평가가 중요하다.

```csharp
string name = cachedName ?? LoadNameFromDatabase();
```

`cachedName`이 있으면 데이터베이스에 가지 않는다. 만약 `??`가 단축 평가하지 않았다면 이 관용구는 성립하지 않는다.

`??`는 널 가능 값 타입에도 쓸 수 있다.

```csharp
int? maybe = null;
int certain = maybe ?? 0;           // 0 — 결과 타입은 int
```

여기서 **반환 타입 변화**를 눈여겨보라. `int?`에 `?? 0`을 붙이면 결과는 `int`다. null 가능성이 제거되었으므로 타입이 좁아진다.

### `??=` — null 병합 할당 연산자 ※C# 8

"왼쪽이 null이면 오른쪽을 왼쪽에 넣어라."

```csharp
myVariable ??= someDefault;
```

이것은 다음과 같다.

```csharp
if (myVariable == null) myVariable = someDefault;
```

가장 흔한 용도는 **지연 계산 프로퍼티**다.

```csharp
class Report
{
    List<Row> _rows;
    public List<Row> Rows => _rows ??= LoadRows();     // 처음 접근할 때만 계산
}
```

`_rows`가 이미 채워져 있으면 `LoadRows()`는 호출되지 않는다. 여기서도 단축 평가가 핵심이다.

> **⚠️ `??=`는 스레드 안전하지 않다**
>
> 위 코드는 "검사하고 나서 할당"이라는 두 단계이므로, 두 스레드가 동시에 들어오면 `LoadRows()`가 두 번 호출되고 그중 하나의 결과가 버려진다. 결과가 불변이고 두 번 계산해도 무해하다면 넘어갈 수 있지만, 부수 효과가 있거나 인스턴스가 유일해야 한다면 `Lazy<T>`나 명시적 잠금이 필요하다(48장).

### `?.` — null 조건부 연산자

"엘비스 연산자"라는 별명으로도 불린다(`?.`가 엘비스의 앞머리를 닮았다는 농담에서 왔다). 왼쪽이 null이면 `NullReferenceException`을 던지는 대신 **식 전체가 null이 된다.**

```csharp
System.Text.StringBuilder sb = null;
string s = sb?.ToString();          // 예외 없음. s는 null
```

이것은 다음과 같다.

```csharp
string s = (sb == null ? null : sb.ToString());
```

**단축 평가가 나머지 체인 전체에 적용된다**는 점이 중요하다.

```csharp
System.Text.StringBuilder sb = null;
string s = sb?.ToString().ToUpper();     // s는 null. 예외 없음
```

`ToString()` 뒤의 `.ToUpper()`는 평범한 점 연산자인데도 실행되지 않는다. `?.`가 null을 만나는 순간 **그 뒤 전체를 건너뛴다.**

그래서 `?.`를 연달아 쓸 필요는 왼쪽 피연산자가 null일 수 있을 때만 생긴다.

```csharp
x?.y?.z         // x가 null일 수 있고 x.y도 null일 수 있을 때
```

이 식은 다음과 같다(단, `x.y`는 한 번만 평가된다).

```csharp
x == null ? null : (x.y == null ? null : x.y.z)
```

### `?[]` — null 조건부 인덱서

인덱서에도 같은 규칙이 적용된다.

```csharp
string[] words = null;
string word = words?[1];            // null. IndexOutOfRangeException도 아니고 NRE도 아니다
```

### 반환 타입 승격 — 값 타입이 걸릴 때

`?.`의 결과는 null일 수 있어야 한다. 그래서 **최종 식의 타입이 null을 담을 수 없으면 컴파일 오류**가 난다.

```csharp
System.Text.StringBuilder sb = null;
int length = sb?.ToString().Length;      // 오류 — int는 null이 될 수 없다
```

해법은 널 가능 값 타입으로 받는 것이다.

```csharp
int? length = sb?.ToString().Length;     // OK
```

이 **자동 승격**이 `?.`의 숨은 규칙이다. 체인의 최종 타입이 `T`라는 값 타입이면, `?.` 식 전체의 타입은 `T?`가 된다.

| 체인 최종 타입 | `?.` 식의 타입 | 비고 |
|---|---|---|
| `string` (참조 타입) | `string` | 그대로 |
| `int` (값 타입) | `int?` | **승격된다** |
| `DateTime` | `DateTime?` | 승격된다 |
| `int?` (이미 널 가능) | `int?` | 그대로 |
| `void` (메서드 호출) | 없음 | 식이 아니라 문으로만 쓸 수 있다 |

마지막 줄도 유용하다. `?.`로 void 메서드를 호출하면 null일 때 **아무 일도 일어나지 않는다.**

```csharp
someObject?.SomeVoidMethod();       // someObject가 null이면 no-op
```

이 관용구의 가장 중요한 응용이 스레드 안전한 이벤트 발생이다(27.5절).

```csharp
PropertyChanged?.Invoke(this, e);
```

### `??`와 `?.`의 조합

둘은 함께 쓸 때 가장 강력하다.

```csharp
System.Text.StringBuilder sb = null;
string s = sb?.ToString() ?? "nothing";      // "nothing"
```

`sb`가 null이면 `?.`가 null을 만들고, `??`가 그것을 "nothing"으로 바꾼다. 이 두 연산자를 모르던 시절 이 한 줄은 다음과 같았다.

```csharp
string s;
if (sb == null)
    s = "nothing";
else
{
    string t = sb.ToString();
    s = t ?? "nothing";
}
```

### 네 연산자 요약

| 연산자 | 왼쪽이 null이면 | 왼쪽이 null이 아니면 | 오른쪽 평가 |
|---|---|---|---|
| `a ?? b` | `b`를 준다 | `a`를 준다 | 왼쪽이 null일 때만 |
| `a ??= b` | `a = b` 수행 | 아무 일 없음 | 왼쪽이 null일 때만 |
| `a?.M()` | 전체가 null | `a.M()` 결과 | 왼쪽이 null이 아닐 때만 |
| `a?[i]` | 전체가 null | `a[i]` 결과 | 왼쪽이 null이 아닐 때만 |

> **⚠️ `?.`는 예외를 숨기는 도구가 아니다**
>
> `?.`를 습관적으로 붙이면 null이 오류라는 사실 자체가 사라진다.
>
> ```csharp
> var name = order?.Customer?.Name ?? "(unknown)";
> ```
>
> `order`가 null인 것이 정상 상태인가, 아니면 위쪽 어딘가의 버그인가? 이 코드는 두 경우를 구분하지 않고 똑같이 `"(unknown)"`을 만들어 낸다. 버그였다면 **문제가 발생한 지점에서 백만 줄 떨어진 곳에서 이상한 데이터로 드러난다.**
>
> 규칙 — **null이 유효한 값일 때만 `?.`를 쓰라.** null이 계약 위반이면 `ArgumentNullException.ThrowIfNull`로 즉시 터뜨리는 편이 낫다(21.10절, 32.9절).

> **📌 `?.`는 `NullReferenceException`을 없애지 않는다**
>
> 흔한 오해다. `?.`가 막아 주는 것은 **그 점 연산 하나**뿐이다.
>
> ```csharp
> int n = list?.Count ?? 0;          // list가 null이어도 안전
> foreach (var x in list) { }        // 여기서는 여전히 터진다
> ```
>
> 널 안정성을 코드 전체에 걸쳐 보장하려면 컴파일러의 널 가능 참조 타입 분석(21.6절)이 필요하다. `?.`는 그것과 다른 층위의 도구다.

> **💡 `??`의 우선순위가 낮다는 것을 기억하라**
>
> `??`는 조건 연산자 바로 위, 즉 거의 바닥이다.
>
> ```csharp
> int total = a ?? 0 + b ?? 0;       // a ?? (0 + b) ?? 0 로 묶인다
> int total = (a ?? 0) + (b ?? 0);   // 의도한 것은 이것
> ```
>
> `??`가 산술과 섞이면 **언제나 괄호를 쓰라.** 이 실수는 조용히 잘못된 숫자를 만든다.

## 10.11 `const`와 `readonly`의 컴파일 결과 차이

두 키워드는 겉보기에 같은 일을 한다 — "한 번 정하면 못 바꾸는 값". 그런데 컴파일 결과가 완전히 다르고, 그 차이가 실무 사고로 이어진다.

### 문법

**`const`**는 지역 변수에도 필드에도 붙일 수 있다.

```csharp
const double C = 2.99792458E08;     // 지역 상수
C += 10;                            // 컴파일 오류

class Physics
{
    public const int MaxEntries = 50;   // 상수 필드 — 암시적으로 static이다
}
```

`const` 필드에 `static`을 붙이는 것은 **불법**이다. 상수는 언제나 타입에 속하지 인스턴스에 속하지 않기 때문에 `static`이 이미 함축되어 있다.

**`readonly`**는 필드에만 붙는다.

```csharp
class Config
{
    public readonly string Path;                 // 인스턴스 readonly 필드
    public static readonly Random Shared = new();// 정적 readonly 필드

    public Config(string path) => Path = path;   // 생성자에서는 쓸 수 있다
}
```

`readonly` 필드에 값을 쓸 수 있는 곳은 **필드 초기화자와 생성자 본문** 두 군데뿐이다.

### 컴파일 결과 — `const`는 값이 복사되고, `readonly`는 필드가 남는다

라이브러리 어셈블리를 이렇게 만든다.

```csharp
// SomeLibrary.dll
public sealed class SomeLibraryType
{
    public const int MaxEntriesInList = 50;
}
```

이 상수는 메타데이터에 `literal` 필드로 기록된다.

```il
.field public static literal int32 MaxEntriesInList = int32(0x00000032)
```

`literal`은 "저장 공간이 없고 값만 메타데이터에 있다"는 뜻이다. **런타임에 이 필드를 위한 메모리는 단 1바이트도 잡히지 않는다.**

이제 애플리케이션이 이 상수를 쓴다.

```csharp
Console.WriteLine("Max entries supported in list: " + SomeLibraryType.MaxEntriesInList);
```

```il
.method public hidebysig static void Main() cil managed
{
  .entrypoint
  .maxstack  8
  IL_0000:  nop
  IL_0001:  ldstr      "Max entries supported in list: "
  IL_0006:  ldc.i4.s   50                     // ← 50이 여기 박혔다
  IL_0008:  box        [mscorlib]System.Int32
  IL_000d:  call       string [mscorlib]System.String::Concat(object, object)
  IL_0012:  call       void [mscorlib]System.Console::WriteLine(string)
  IL_0017:  nop
  IL_0018:  ret
}
```

`ldc.i4.s 50`. 라이브러리 이름조차 나타나지 않는다. 이 예제에서는 **애플리케이션 메타데이터에 그 DLL에 대한 참조가 아예 추가되지 않으며**, 빌드가 끝난 뒤 DLL을 디스크에서 지워도 실행된다.

이제 `static readonly`로 바꾼다.

```csharp
public sealed class SomeLibraryType
{
    public static readonly int MaxEntriesInList = 50;   // static을 직접 써야 한다
}
```

```il
.field public static initonly int32 MaxEntriesInList
```

`initonly`가 CLR 용어이고 C# 용어가 `readonly`다. 이 필드는 진짜 저장 공간을 갖는다. 사용처의 IL은 이렇게 바뀐다.

```il
  IL_0006:  ldsfld     int32 SomeLibraryType::MaxEntriesInList
```

`ldsfld`(load static field)다. **런타임에 라이브러리를 로드하고, 타입을 초기화하고, 필드를 읽는다.**

### 그래서 무엇이 달라지는가 — 버전 관리

```text
     [ const ]                                [ static readonly ]

  라이브러리 v1: 50                        라이브러리 v1: 50
        │ 컴파일                                 │ 컴파일
        ▼                                        ▼
  앱 IL:  ldc.i4.s 50                      앱 IL:  ldsfld MaxEntriesInList
        │                                        │
  라이브러리를 v2(=1000)로 교체              라이브러리를 v2(=1000)로 교체
  앱은 재컴파일 안 함                        앱은 재컴파일 안 함
        │ 실행                                   │ 실행
        ▼                                        ▼
     여전히 50                                  1000
```

이것이 두 키워드의 결정적 차이다. `const`는 **호출자에게 값을 복사해 심고**, `readonly`는 **정의한 어셈블리에 값을 남긴다.**

> **⚠️ 공개 API의 `const`는 사실상 영구히 바꿀 수 없다**
>
> 값을 바꿔도 재컴파일하지 않은 소비자는 옛 값을 계속 쓴다. 예외도 경고도 없이 두 어셈블리가 서로 다른 숫자를 믿게 된다. 이 종류의 버그는 재현이 어렵고 원인 추적이 지독하다.
>
> 그러므로 `public const`는 **값이 우주가 끝날 때까지 안 변한다고 확신할 때만** 쓴다. `Math.PI`, `int.MaxValue`, `MaxInt16 = 32767` 같은 것이 그 예다. "지금은 50인데 나중에 늘릴 수도 있다"류의 값은 전부 `public static readonly`여야 한다.
>
> 설계 관점의 판단 기준은 79.2절에서 이어진다.

> **⚠️ `const decimal`은 진짜 `literal`이 아니다**
>
> CLI 메타데이터의 상수 테이블은 `decimal`을 표현하지 못한다. 그래서 C# 컴파일러는 `const decimal`을 **`static readonly` 필드로 컴파일하고, `System.Runtime.CompilerServices.DecimalConstantAttribute`를 붙여** "이건 사실 상수다"라고 기록한다. C# 컴파일러는 다른 어셈블리의 `const decimal`을 만나면 이 특성을 읽어 값을 인라인한다.
>
> 실무적 함의는 하나다. **`const decimal`은 `switch`의 `case` 레이블이나 특성 인수처럼 진짜 컴파일 타임 상수를 요구하는 자리에서 다른 `const`와 똑같이 동작하지 않을 수 있다.** 헷갈리면 `static readonly decimal`을 쓰는 편이 낫다.

### 규칙 비교표

| 항목 | `const` | `readonly` |
|---|---|---|
| 붙일 수 있는 곳 | 지역 변수, 필드 | 필드만 |
| 값 결정 시점 | 컴파일 타임 | 런타임 (초기화자 또는 생성자) |
| 허용 타입 | `bool`, `char`, 정수 계열, `float`, `double`, `decimal`, `string`, 열거형, 그리고 값이 `null`인 참조 타입 | **모든 타입** |
| 암시적 `static` | 그렇다 (`static` 표기 불법) | 아니다 (직접 붙여야 한다) |
| IL 필드 플래그 | `literal` | `initonly` |
| 런타임 저장 공간 | 없다 | 있다 |
| 사용처 IL | `ldc.*` / `ldstr` (값 인라인) | `ldsfld` / `ldfld` |
| 어셈블리 간 값 갱신 | **안 된다** (재컴파일 필요) | 된다 |
| 주소를 얻을 수 있나 | 불가 (`ref`로 전달 불가) | 가능 (`ref readonly`로) |
| 인스턴스마다 다른 값 | 불가 | 가능 (인스턴스 `readonly`) |
| 리플렉션으로 변경 | 불가 (필드 자체가 없다) | 가능 |
| 선택적 매개변수 기본값으로 사용 | 가능 | 불가 |
| `switch`의 `case` 레이블로 사용 | 가능 | 불가 |
| 특성(attribute) 인수로 사용 | 가능 | 불가 |

> **📌 `readonly` 필드는 리플렉션으로 고칠 수 있다**
>
> `readonly`는 컴파일러와 검증기가 지키는 규칙이지 메모리 보호가 아니다. `FieldInfo.SetValue`로 `initonly` 필드에 값을 쓰는 것이 가능하다. 직렬화 프레임워크와 의존성 주입 컨테이너가 실제로 이 방법을 쓴다.
>
> 반대로 `const`는 리플렉션으로도 못 고친다. **고칠 필드가 존재하지 않기 때문이다.** `FieldInfo.GetValue`로 값을 읽는 것은 되는데, 그건 메타데이터에서 읽는 것이다.

### `readonly`가 지키는 것과 지키지 않는 것

가장 흔한 오해가 남았다.

```csharp
class Basket
{
    public readonly List<string> Items = new();
}

var b = new Basket();
b.Items.Add("apple");       // 완전히 합법이다
b.Items = new List<string>();  // 이것만 불법
```

`readonly`는 **필드(참조를 담은 슬롯)를 보호하지, 그 참조가 가리키는 객체를 보호하지 않는다.** 참조 타입 필드에 `readonly`를 붙이면 "이 변수는 다른 객체를 가리키지 않는다"만 보장된다.

진짜 불변 컬렉션이 필요하면 `IReadOnlyList<T>`로 노출하거나 불변 컬렉션(24.10절)을 쓴다.

> **📌 CLR에는 C++의 `const` 같은 것이 없다**
>
> C++에서는 메서드나 매개변수에 `const`를 붙여 "이 안에서 객체를 못 고친다"를 표현한다. CLR에는 그런 개념 자체가 없고, 따라서 **어떤 .NET 언어도 그것을 제공할 수 없다.**
>
> 이유는 셋이다. 첫째, C++의 `const`조차 완전한 보장이 아니었다 — `const_cast`로 벗겨 내거나 주소를 얻어 쓰면 그만이었다. 둘째, CLR이 모든 쓰기에서 "지금 이 대상이 상수인가"를 검사하려면 성능 손실이 심각하다. 셋째, 불변성이 타입 시스템에 들어오면 파생 타입도 전부 그것을 존중해야 하고 필드 타입까지 불변이어야 하는 등 복잡도가 폭발한다.
>
> .NET의 답은 다르다 — **불변성은 언어가 강제하는 것이 아니라 타입 설계자가 만들어 내는 것**이다. `string`이 불변인 이유는 CLR이 막아서가 아니라 `String` 클래스가 자신을 바꾸는 메서드를 제공하지 않기 때문이다. 같은 사상이 `readonly struct`(16.5절), `init` 전용 프로퍼티(13.8절), 레코드(19장)로 이어진다. C# 7.2 이후의 `in`과 `ref readonly`는 그 사이 어딘가에서 "복사 없이 읽기만"을 표현하려는 시도이며, 10.2절에서 본 방어적 복사는 그 타협의 대가다.

### 성능 영향

`const`는 JIT에게 최상의 재료다. 값이 IL에 리터럴로 박혀 있으므로 상수 접기(constant folding), 죽은 코드 제거, 루프 언롤링 판단에 곧바로 쓰인다.

```csharp
const bool EnableTrace = false;

if (EnableTrace)
    Log("...");             // JIT이 통째로 지운다
```

`static readonly`로 같은 코드를 쓰면 IL에는 `ldsfld` + 분기가 남는다. 다만 실제 실행에서 예측 가능한 분기 하나의 비용은 대개 측정 한계 아래다.

> **💡 그래서 무엇을 쓰나 — 결론**
>
> - **어셈블리 안에서만 쓰는 `private`/`internal` 상수** — `const`를 쓰라. 버전 문제가 생길 여지가 없고 JIT에게 가장 좋다.
> - **공개 API로 노출하는 값** — 기본적으로 `public static readonly`를 쓰라. `const`는 수학·물리 상수처럼 정의상 불변인 것에만.
> - **참조 타입, 배열, 컬렉션** — `const`가 애초에 불가능하다(`null` 제외). `static readonly`뿐이다. 그리고 컬렉션이면 읽기 전용 래퍼로 감싸라.
> - **조건부 컴파일 스위치** — `const bool`이 정석이다. 다만 `#if`와 `[Conditional]` 중 어느 것이 맞는지는 12.8절에서 비교한다.

## 이 장의 요약

- **변수는 다섯 종류뿐이다** — 지역 변수, 매개변수, 인스턴스 필드, 정적 필드, 배열 요소. 프로퍼티는 변수가 아니라 메서드이며, 그래서 `ref`의 대상이 될 수 없다.

- **지역 변수의 범위는 블록 전체이고 위아래 양방향이다.** 선언보다 위에서도 그 이름은 이미 지역 변수를 뜻한다. 그래서 같은 블록에서 필드와 같은 이름의 지역 변수를 선언하면 선언 위쪽의 코드까지 오류가 된다. 지역 변수끼리의 그림자는 금지되고, 람다·지역 함수의 매개변수 이름 충돌도 같은 규칙에 걸린다.

- **수정자가 없으면 언제나 값 전달이다.** 참조 타입일 때 복사되는 "값"이 참조일 뿐이다. 그래서 메서드 안에서 객체를 고치면 호출자도 보고, 변수에 `null`을 넣으면 호출자는 모른다. 전달 방식과 타입 종류는 독립적인 두 축이다.

- **`ref`·`out`·`in`은 IL에서 전부 `T&`, 즉 관리 포인터다.** 호출부는 `ldloc` 대신 `ldloca`로 주소를 올리고, 본문은 `ldind`/`stind`로 간접 접근한다. CLR 관점에서 `out`과 `ref`는 완전히 같고 1비트만 다르다 — 차이는 오로지 C# 컴파일러의 확정 할당 검사에 있다. 그래서 `ref`와 `out`만 다른 오버로드는 불가능하다.

- **`in`은 `readonly struct`가 아니면 손해를 본다.** 일반 `struct`의 인스턴스 메서드나 프로퍼티를 `in` 매개변수에서 호출하면 컴파일러가 `ldobj`로 구조체 전체를 복사한다. 복사를 없애려고 붙인 수정자가 접근마다 복사를 만드는 것이다. 작은 타입에 `in`을 붙이는 것도 손해다.

- **`ref` 지역 변수와 `ref` 반환은 저장 위치의 별칭을 만든다.** 대상은 배열 요소·필드·지역 변수·`ref` 매개변수뿐이고 프로퍼티는 안 된다. 반환할 수 있는 것은 호출자보다 오래 사는 위치뿐이며, 이 안전성 규칙 체계가 `Span<T>`의 토대다.

- **선택적 매개변수의 기본값은 호출부 IL에 상수로 구워진다.** 라이브러리에서 기본값을 바꿔도 재컴파일하지 않은 호출자는 옛 값을 계속 쓴다. 매개변수 이름도 명명된 인수 때문에 공개 API의 일부가 되었다. 회피 관용구는 기본값을 `null`/`0` 센티널로 두고 진짜 기본값을 본문에서 결정하는 것이다.

- **인수는 언제나 소스에 나타난 순서대로 왼쪽에서 오른쪽으로 평가된다.** 명명된 인수를 써서 순서를 바꿔도 평가 순서는 소스 순서를 따르며, 컴파일러가 임시 변수를 만들어 재배열한다. 우선순위는 "무엇이 무엇의 피연산자인가"만 정하고 실행 순서는 정하지 않는다.

- **`params` 호출은 호출부에서 배열을 힙에 할당한다.** 그래서 BCL의 `String.Concat`은 인수 2~4개짜리 전용 오버로드를 따로 깔아 두었다. `params` 매개변수는 `null`일 수 있어 순회 전 검사가 필요하다. ※C# 13의 `params ReadOnlySpan<T>`가 이 할당을 없앤다.

- **`var`와 대상 타입 지정 `new()`는 IL에 아무 흔적도 남기지 않는다.** 둘 다 타입 이름을 한쪽에서 다른 쪽으로 옮기는 문법이며 런타임 성능에 영향이 없다. `var`는 지역 변수 전용이고, `new()`는 타입이 명시된 모든 자리에서 쓸 수 있다. `var`는 `dynamic`과 아무 관계가 없다.

- **null 연산자 넷은 전부 단축 평가한다.** `??`는 왼쪽이 null일 때만 오른쪽을 평가하고, `?.`는 null을 만나면 뒤의 평범한 점 연산까지 통째로 건너뛴다. `?.` 체인의 최종 타입이 값 타입이면 `T?`로 승격되며, 승격을 받을 준비가 안 된 좌변은 컴파일 오류가 된다. `??`의 우선순위가 매우 낮다는 것을 잊지 마라.

- **`const`는 값이 사용처에 복사되고, `readonly`는 정의 어셈블리에 필드로 남는다.** `const`는 `literal` 필드로 저장 공간이 없고 `ldc`로 인라인되며, `static readonly`는 `initonly` 필드로 `ldsfld`로 읽힌다. 그래서 `public const`의 값 변경은 소비자를 재컴파일해야만 반영되고, 반영되지 않아도 아무 경고가 없다.

- **`readonly`는 슬롯을 지키지 객체를 지키지 않는다.** `readonly List<T>`에 `Add`는 얼마든지 된다. CLR에는 C++의 `const` 같은 개념이 없으며, .NET에서 불변성은 언어가 강제하는 것이 아니라 타입 설계자가 만들어 내는 것이다.

## 연습 문제

1. **값 전달과 `ref` 전달의 차이를 참조 타입에서 확인하라.** `static void A(StringBuilder sb) { sb.Append("X"); sb = null; }`와 `static void B(ref StringBuilder sb) { sb.Append("X"); sb = null; }`를 만들고, 각각에 같은 `StringBuilder`를 넘긴 뒤 호출 후의 변수 상태를 출력하라. 두 결과가 다른 이유를 "무엇이 복사되었는가"라는 말로 설명하라.

2. **네 가지 전달 방식의 IL을 직접 비교하라.** SharpLab(sharplab.io)에 `static void V(int p){} static void R(ref int p){} static void O(out int p){p=0;} static void I(in int p){}`를 넣고 IL 탭을 열어라. 각 메서드의 시그니처에서 `int32`, `int32&`, `[out]`, `modreq`가 어디에 나타나는지 표로 정리하라. 이어서 각각을 호출하는 코드를 추가해 `ldloc`과 `ldloca`가 어디서 갈리는지 확인하라.

3. **`in`의 방어적 복사를 눈으로 확인하라.** 필드 세 개짜리 `struct Vec3`을 만들고 `static double Len(in Vec3 v) => v.GetLength();`를 SharpLab에서 컴파일하라. IL에 `ldobj`가 나타나는 것을 확인한 뒤, `struct` 앞에 `readonly`를 붙이고(필드도 `readonly`로) 다시 컴파일해 `ldobj`가 사라지는 것을 확인하라. 마지막으로 `readonly`를 뗀 상태에서 `GetLength()`에만 `readonly` 한정자를 붙여 세 번째 결과를 비교하라.

4. **선택적 매개변수의 버전 관리 함정을 재현하라.** 클래스 라이브러리 프로젝트에 `public static string Make(string s = "A") => s;`를 만들고, 콘솔 프로젝트에서 `Make()`를 호출해 출력하라. 라이브러리의 기본값을 `"B"`로 바꾸고 **라이브러리만** 다시 빌드해 DLL을 교체한 뒤 콘솔 앱을 다시 실행하라. 무엇이 출력되는가? 이어서 기본값을 `null`로 바꾸고 본문을 `s ?? "B"`로 바꾼 뒤 같은 실험을 반복해 결과가 어떻게 달라지는지 비교하라.

5. **`params`의 할당을 세어 보라.** `static int Sum(params int[] xs)`를 만들고 `Sum(1,2,3)`을 100만 번 호출하는 루프를 `GC.GetAllocatedBytesForCurrentThread()`로 감싸 할당량을 측정하라. 이어서 `static int Sum(int a, int b, int c)` 오버로드를 추가하고 같은 측정을 반복해 차이를 기록하라. 마지막으로 `Sum(null)`을 호출하면 어떻게 되는지 확인하고, 그 결과를 근거로 `Sum`을 방어적으로 고쳐라.

6. **평가 순서가 우선순위와 무관함을 증명하라.** 자기 이름을 출력하고 값을 반환하는 메서드 `A()`, `B()`, `C()`를 만들고 `A() + B() * C()`, `A() * B() + C()`, `A() ?? B()`(참조 타입 버전), `Foo(y: A(), x: B())`를 각각 실행해 출력 순서를 기록하라. 네 결과가 모두 소스 순서를 따르는지 확인하고, `??`의 경우만 다른 이유를 설명하라.

7. **`const`와 `static readonly`의 IL과 버전 동작을 모두 확인하라.** 클래스 라이브러리에 `public const int A = 50;`과 `public static readonly int B = 50;`을 두고, 콘솔 앱에서 둘 다 출력하라. 콘솔 앱의 IL을 `ildasm` 또는 SharpLab으로 열어 `ldc.i4.s`와 `ldsfld`를 찾아라. 그다음 라이브러리에서 두 값을 1000으로 바꾸고 라이브러리만 다시 빌드해 DLL을 교체한 뒤 실행해, 출력이 어떻게 갈리는지 확인하라.
