# 7장. 숫자와 불리언

> **이 장의 위치** — 6장에서 미리 정의된 타입을 표로 훑고, 값 타입이 무엇인지 세웠다. 그 표의 절반은 숫자였고 나머지 한 칸은 `bool`이었다. 이 장은 그 칸들을 하나씩 열어본다. 리터럴이 어떤 타입으로 추론되는지, 어떤 변환이 캐스트 없이 통과하고 어떤 것이 막히는지, 정수 나눗셈이 왜 소수점을 버리는지, `0.1 + 0.2`가 왜 `0.3`이 아닌지를 비트 수준까지 내려가서 본다. 6.10절에서 이름만 던져 두었던 `checked`/`unchecked`도 여기서 끝낸다.
>
> **선수 지식** — 6장(구문과 타입 기초). 특히 6.5절(미리 정의된 타입 분류)과 6.10절(암시적/명시적 변환).
>
> **이 장에서 다루지 않는 것** — `char`는 정수로 변환되는 숫자 같은 타입이지만 본체는 문자이므로 8.1절에서 다룬다. 연산자 우선순위 전체 표는 10.9절, `??`·`?.` 같은 null 연산자는 10.10절, `checked` **문**의 문법적 지위는 11.7절이다. `Math` 클래스의 전체 메서드 목록과 `BigInteger`·`Half`·`Complex`는 39장, 숫자 서식 문자열(`{0:N0}`, `{0:X}`)은 38.3절, 사용자 정의 타입에 `+`를 붙이는 방법은 22장, `bool?`의 3값 논리는 21.5절이다. 비트 연산을 열거형에 쓰는 `[Flags]` 패턴은 20.3절에서 다룬다.

## 7.1 숫자 리터럴, 2진 리터럴, 밑줄 구분자

### 미리 정의된 숫자 타입 다시 보기

6.5절의 표를 숫자 부분만 잘라 다시 놓는다. 이 장 내내 참조할 표다.

| C# 타입 | System 타입 | 접미사 | 크기 | 범위 | CLS 준수 |
|---|---|---|---|---|---|
| `sbyte` | `SByte` | — | 8비트 | −2<sup>7</sup> ~ 2<sup>7</sup>−1 (−128 ~ 127) | 아니오 |
| `short` | `Int16` | — | 16비트 | −2<sup>15</sup> ~ 2<sup>15</sup>−1 (−32,768 ~ 32,767) | 예 |
| `int` | `Int32` | — | 32비트 | −2<sup>31</sup> ~ 2<sup>31</sup>−1 | 예 |
| `long` | `Int64` | `L` | 64비트 | −2<sup>63</sup> ~ 2<sup>63</sup>−1 | 예 |
| `nint` | `IntPtr` | — | 32/64비트 | 프로세스 주소 공간에 맞춤 | 예 |
| `byte` | `Byte` | — | 8비트 | 0 ~ 2<sup>8</sup>−1 (0 ~ 255) | 예 |
| `ushort` | `UInt16` | — | 16비트 | 0 ~ 2<sup>16</sup>−1 (0 ~ 65,535) | 아니오 |
| `uint` | `UInt32` | `U` | 32비트 | 0 ~ 2<sup>32</sup>−1 | 아니오 |
| `ulong` | `UInt64` | `UL` | 64비트 | 0 ~ 2<sup>64</sup>−1 | 아니오 |
| `nuint` | `UIntPtr` | — | 32/64비트 | 프로세스 주소 공간에 맞춤 | 아니오 |
| `float` | `Single` | `F` | 32비트 | ±(~10<sup>−45</sup> ~ ~10<sup>38</sup>) | 예 |
| `double` | `Double` | `D` | 64비트 | ±(~10<sup>−324</sup> ~ ~10<sup>308</sup>) | 예 |
| `decimal` | `Decimal` | `M` | 128비트 | ±(~10<sup>−28</sup> ~ ~10<sup>28</sup>) | 예 |

정수 타입 중에서 `int`와 `long`이 일등 시민이다. C#도 런타임도 이 둘을 우대한다. 나머지 정수 타입은 대개 상호운용(interop)이나 공간 효율이 절대적으로 중요할 때 쓴다. `nint`/`nuint`는 포인터를 다룰 때 유용하므로 7.11절로 미룬다.

실수 타입 중 `float`과 `double`이 **부동소수점 타입**(floating-point type)이고 주로 과학·그래픽 계산에 쓴다. `decimal`은 10진 기준의 정확한 산술과 높은 정밀도가 필요한 금융 계산에 쓴다. 이 갈림길이 7.7절의 주제다.

> **📌 CLS 준수와 부호 없는 타입**
>
> 표의 마지막 열이 "아니오"인 타입 — `sbyte`, `ushort`, `uint`, `ulong` — 은 공용 언어 사양(CLS, Common Language Specification)을 따르지 않는다. 모든 .NET 언어가 이 타입들을 이해하도록 요구되지 않는다는 뜻이다. 라이브러리를 만들어 공개 API로 노출한다면 이 타입들을 시그니처에 쓰지 않는 편이 안전하다. 내부 구현에서 쓰는 것은 아무 문제가 없다.
>
> 그래도 `uint`를 쓸 이유가 "값이 음수가 될 리 없어서"뿐이라면 `int`를 쓰는 편이 낫다. 부호 없는 타입은 뺄셈 한 번으로 조용히 거대한 양수가 되기 때문이다(7.4절).

### 정수 리터럴 — 10진, 16진, 2진

정수 리터럴은 10진법으로 그냥 쓰거나, `0x` 접두사로 16진법, `0b` 접두사로 2진법을 쓴다.

```csharp
int x = 127;
long y = 0x7F;                                // 16진 = 127
var  b = 0b1010_1011_1100_1101_1110_1111;     // 2진
```

`0b` 접두사는 ※C# 7에서 들어왔다. 비트 마스크를 정의할 때 가장 유용하다. 어떤 비트가 켜져 있는지 눈으로 세는 것과 `0x1E8480`을 머릿속에서 풀어보는 것은 난이도가 다르다.

### 밑줄 구분자

숫자 리터럴 **안 어디에나** 밑줄(`_`)을 끼워 넣어 가독성을 올릴 수 있다. ※C# 7.

```csharp
int million = 1_000_000;
```

밑줄은 순전히 사람 눈을 위한 것이다. 컴파일러는 토큰을 읽을 때 밑줄을 지우고 나머지 숫자만 본다. 그래서 그룹 크기를 3자리로 맞출 의무도 없다. 인도식 2/3 그룹핑도 된다.

```csharp
int million = 10_00_000;    // 인도식 2/3 그룹핑도 유효하다
```

※C# 7.2부터는 접두사 **바로 뒤**에도 밑줄을 쓸 수 있다. 16진·2진 리터럴의 자릿수를 바이트 단위로 정렬할 때 쓴다.

```csharp
int hex    = 0x_00_1E_8480;
int sixteen = 0b_0001_0000;
int thirtyTwo = 0b_0010_0000;
int sixtyFour = 0b_0100_0000;
```

세 표기법은 같은 값을 만든다. `2_000_000`, `0b_0001_1110_1000_0100_1000_0000`, `0x_001E_8480`은 모두 200만이다.

### 실수 리터럴

실수 리터럴은 소수점 표기와 지수 표기를 쓸 수 있다.

```csharp
double d       = 1.5;
double million = 1E06;    // 1,000,000
double tiny    = 1.5E-10;
```

지수 기호는 `E` 또는 `e` 둘 다 된다. 지수 표기에는 소수점이 없어도 된다 — `1E06`에는 소수점이 없지만 `double`이다.

### 리터럴의 타입 추론 규칙

리터럴에도 타입이 있다. 컴파일러가 정하는 규칙은 짧다.

1. 리터럴에 **소수점**이나 **지수 기호(`E`)**가 있으면 `double`이다.
2. 그렇지 않으면 `int` → `uint` → `long` → `ulong` 순으로 **값이 들어가는 첫 번째 타입**이 된다.

```csharp
Console.WriteLine ( 1.0.GetType());          // System.Double
Console.WriteLine ( 1E06.GetType());         // System.Double
Console.WriteLine ( 1.GetType());            // System.Int32
Console.WriteLine ( 0xF0000000.GetType());   // System.UInt32
Console.WriteLine (0x100000000.GetType());   // System.Int64
```

`0xF0000000`은 4,026,531,840이다. `int`의 최댓값 2,147,483,647을 넘으므로 `int`가 아니라 `uint`로 추론된다. `0x100000000`은 4,294,967,296이라서 `uint`도 넘고 `long`이 된다.

> **⚠️ `0xF0000000`이 `uint`라서 생기는 사고**
>
> 비트 마스크를 16진으로 쓰다 보면 최상위 비트가 켜진 상수를 자주 만난다. 그런데 그 상수가 `int`가 아니라 `uint`로 추론되면 `int` 변수와 섞이는 순간 규칙이 달라진다.
>
> ```csharp
> int flags = -1;
> // var r = flags & 0xF0000000;   // int와 uint를 섞으면 둘 다 long으로 승격된다
> long r = flags & 0xF0000000;     // 결과는 long, 값은 4026531840
> ```
>
> `int`와 `uint`가 만나면 둘 다 `long`으로 올라간다(7.3절의 승격 표). 32비트 마스크를 기대했는데 64비트 결과가 나온다. `int` 마스크를 원한다면 명시적으로 캐스트하거나 `unchecked((int)0xF0000000)`으로 쓴다.
>
> ```csharp
> const int Mask = unchecked((int)0xF0000000);   // -268435456
> int r2 = flags & Mask;                          // int 그대로
> ```

### 접미사

접미사는 리터럴의 타입을 **명시적으로** 정한다. 대소문자를 가리지 않는다.

| 접미사 | 타입 | 예 |
|---|---|---|
| `F` / `f` | `float` | `float f = 1.0F;` |
| `D` / `d` | `double` | `double d = 1D;` |
| `M` / `m` | `decimal` | `decimal d = 1.0M;` |
| `U` / `u` | `uint` | `uint i = 1U;` |
| `L` / `l` | `long` | `long i = 1L;` |
| `UL` / `ul` | `ulong` | `ulong i = 1UL;` |

여섯 개 중 실제로 중요한 것은 두 개다.

`U`와 `L`은 거의 필요 없다. `uint`, `long`, `ulong`은 `int` 리터럴에서 암시적으로 변환되거나 추론되기 때문이다.

```csharp
long i = 5;   // int 리터럴 5가 long으로 무손실 암시 변환된다
```

`D`도 기술적으로 군더더기다. 소수점이 있는 리터럴은 어차피 `double`로 추론되고, 소수점은 언제든 붙일 수 있다.

```csharp
double x = 4.0;   // D 없이도 double
```

**`F`와 `M`은 반드시 붙여야 한다.** 이 둘이 없으면 컴파일이 안 되는 경우가 대부분이다.

```csharp
float f = 4.5F;       // F가 없으면 4.5는 double로 추론되고, double → float 암시 변환은 없다
decimal d = -1.23M;   // M이 없으면 컴파일 오류
```

`double`은 `float`으로도 `decimal`로도 암시 변환되지 않는다. 두 변환 모두 정보를 잃을 수 있기 때문이다. 이유는 7.2절에서 정리한다.

> **⚠️ `decimal`에 `M`을 빠뜨리면 조용히 정밀도를 잃는 경우가 있다**
>
> 다음 두 줄의 차이를 보라.
>
> ```csharp
> decimal a = 0.1M;              // decimal 리터럴 → 정확히 0.1
> decimal b = (decimal) 0.1;     // double 0.1을 decimal로 캐스트
> ```
>
> `b`가 담는 값은 `double`이 표현할 수 있는 0.1의 **근삿값**을 10진으로 옮긴 것이다. `.NET`의 `double → decimal` 변환은 유효 자릿수를 15자리로 반올림하므로 이 경우 우연히 `0.1M`과 같은 값이 나오지만, 이 우연에 기대면 안 된다. 계산을 몇 번 거친 `double`을 `decimal`로 캐스트하는 순간 오차가 그대로 넘어온다.
>
> 근본 규칙은 하나다. **금액은 처음부터 끝까지 `decimal`이어야 한다.** `double`을 거쳐 온 값을 `decimal`로 캐스트하는 코드가 보이면 그 지점이 이미 버그다.

### 컴파일 결과 — 리터럴은 IL에서 어떻게 되는가

리터럴은 실행 시점에 계산되는 것이 아니라 IL에 상수로 박힌다. `int` 값에 대해서는 크기별로 다른 옵코드가 쓰인다.

```csharp
int a = 5;
int b = 127;
int c = 1_000_000;
```

```il
ldc.i4.5              // 0~8은 전용 1바이트 옵코드
stloc.0
ldc.i4.s   127        // -128~127은 2바이트 (옵코드 + 1바이트 피연산자)
stloc.1
ldc.i4     0xf4240    // 그 밖에는 5바이트 (옵코드 + 4바이트 피연산자)
stloc.2
```

`1_000_000`이 `0xf4240`으로 나온다. **밑줄은 IL에 흔적을 남기지 않는다.** 10진으로 썼든 16진으로 썼든 2진으로 썼든 마찬가지다. `0b_0001_1110_1000_0100_1000_0000`과 `2_000_000`은 IL 수준에서 글자 하나까지 같은 코드를 만든다.

`long` 리터럴은 `ldc.i8`이지만, `int` 범위에 들어가는 값이면 컴파일러가 `ldc.i4` 후 `conv.i8`로 줄여 쓰기도 한다.

```csharp
long y = 0x7F;
```

```il
ldc.i4.s   127
conv.i8
stloc.0
```

`float`/`double` 리터럴은 `ldc.r4`/`ldc.r8`로 IEEE 754 비트 패턴이 그대로 들어간다. `decimal`만 예외다.

```csharp
decimal m = 1.5M;
```

```il
ldc.i4.s   15
ldc.i4.0
ldc.i4.0
ldc.i4.0
ldc.i4.1
newobj     instance void [System.Runtime]System.Decimal::.ctor(int32, int32, int32, bool, uint8)
stloc.0
```

`decimal`은 CLR의 원시 타입이 아니므로(6.5절) IL 상수 옵코드가 없다. 컴파일러는 `1.5M`을 "가수 15, 소수점 자리수 1"로 분해해 생성자 호출로 바꾼다. 이것이 `decimal` 리터럴이 `double` 리터럴보다 비싼 첫 번째 이유다.

> **💡 마법의 숫자는 2진 리터럴로 쓰고 `const`로 뽑아라**
>
> ```csharp
> const int Read    = 0b_0000_0100;
> const int Write   = 0b_0000_0010;
> const int Execute = 0b_0000_0001;
> const int ReadWriteExecute = Read | Write | Execute;   // 0x7보다 의도가 보인다
> ```
>
> `const` 식은 컴파일 시점에 계산되므로 런타임 비용이 0이다. IL에는 `ldc.i4.7` 한 줄만 남는다. 다만 `const`가 소비 어셈블리에 값으로 박히는 버전 관리 문제가 있다 — 10.11절에서 다룬다.

## 7.2 숫자 변환 — 확대와 축소

### 규칙 하나

숫자 변환의 규칙은 문장 하나로 요약된다.

> **대상 타입이 원본 타입의 가능한 모든 값을 표현할 수 있으면 암시적, 아니면 명시적.**

6.10절에서 본 원칙 — "암시적 변환은 항상 성공하고 손실이 없다" — 의 숫자판이다. 이 한 문장에서 아래 모든 규칙이 나온다.

**확대 변환**(widening)은 작은 타입의 값을 큰 타입에 담는 것이다. 정보가 사라질 수 없으므로 캐스트 없이 통과한다. **축소 변환**(narrowing)은 그 반대다. 값이 대상 타입의 범위를 넘을 **가능성**이 있으므로 명시적 캐스트를 요구한다.

```csharp
int x = 12345;
long y = x;             // 확대: 암시적
short z = (short) x;    // 축소: 명시적 캐스트 필요
```

여기서 중요한 것은 **가능성**이다. 실제 값이 범위 안에 있어도 컴파일러는 타입만 본다.

```csharp
byte myByte = 0;
int  myInt  = 200;
// myByte = myInt;      // 컴파일 오류 CS0266
myByte = (byte) myInt;  // OK. 200은 byte 범위 안이지만 캐스트는 여전히 필요하다
```

`200`은 `byte`의 범위(0~255) 안에 있다. 그래도 오류다. C#은 타입 안전성을 위해 설계된 언어이고, 컴파일러는 `myInt`가 실행 시점에 무슨 값일지 모른다.

오류 메시지가 이 규칙을 그대로 말해준다.

```text
error CS0266: Cannot implicitly convert type 'int' to 'byte'.
An explicit conversion exists (are you missing a cast?)
```

"암시적으로는 안 되지만 명시적 변환은 존재한다"는 문구가 핵심이다. 축소 변환은 **금지된 것이 아니라 확인을 요구받는 것**이다.

### 정수 사이의 암시적 변환 표

다음 표가 정수 타입 사이의 암시적 변환 전부다. `→` 표시가 있으면 캐스트 없이 대입할 수 있다.

| 원본 \ 대상 | `sbyte` | `byte` | `short` | `ushort` | `int` | `uint` | `long` | `ulong` |
|---|---|---|---|---|---|---|---|---|
| `sbyte` | — | | → | | → | | → | |
| `byte` | | — | → | → | → | → | → | → |
| `short` | | | — | | → | | → | |
| `ushort` | | | | — | → | → | → | → |
| `int` | | | | | — | | → | |
| `uint` | | | | | | — | → | → |
| `long` | | | | | | | — | |
| `ulong` | | | | | | | | — |
| `char` | | | | → | → | → | → | → |

빈 칸은 전부 캐스트가 필요하다는 뜻이다. 표에서 읽어야 할 것들:

- **`byte`와 `ushort`의 행이 가장 넓다.** 부호 없는 작은 타입은 음수가 없으므로 부호 있는 큰 타입에도, 부호 없는 큰 타입에도 안전하게 들어간다.
- **`sbyte`는 `byte`로 갈 수 없다.** 크기가 같아도 음수를 담을 수 없기 때문이다.
- **`long`과 `ulong`은 서로 갈 수 없다.** `long`의 음수는 `ulong`에 없고, `ulong`의 큰 값은 `long`에 없다.
- **`char`는 정수로 갈 수 있지만, 정수는 `char`로 갈 수 없다.** `char`는 부호 없는 16비트이므로 `ushort`·`int`·`uint`·`long`·`ulong`으로 암시 변환된다. 반대 방향은 전부 캐스트가 필요하다 — `ushort`에서 `char`로도 마찬가지다. 자세히는 8.1절이다.

### 부동소수점 사이, 그리고 정수와의 변환

| 변환 | 암시적? | 이유 |
|---|---|---|
| `float` → `double` | 예 | `double`이 `float`의 모든 값을 표현한다 |
| `double` → `float` | 아니오 (캐스트) | 범위 초과·정밀도 손실 가능 |
| 모든 정수 → `float` / `double` | 예 | 크기(magnitude)는 항상 보존된다 |
| `float` / `double` → 모든 정수 | 아니오 (캐스트) | 소수부가 잘리고 범위를 넘을 수 있다 |
| 모든 정수 → `decimal` | 예 | `decimal`이 모든 C# 정수 값을 표현한다 |
| `decimal` ↔ `float` / `double` | 아니오 (양방향 캐스트) | 범위 초과 또는 정밀도 손실 |
| `float` / `double` → `decimal` | 아니오 (캐스트) | 위와 같음 |

부동소수점에서 정수로 캐스트하면 **소수부가 잘린다. 반올림하지 않는다.** 0 방향으로 절삭한다.

```csharp
Console.WriteLine ((int)  9.9);    // 9
Console.WriteLine ((int) -9.9);    // -9   (-10이 아니다)
```

반올림하면서 변환하고 싶으면 `System.Convert`의 메서드를 쓴다 — `Convert.ToInt32(9.8)`은 `10`이고 `(int)9.8`은 `9`다. 그 반올림 규칙이 무엇인지는 7.8절에서 자세히 판다.

> **⚠️ 정수 → 부동소수점 암시 변환은 크기는 보존하지만 정밀도는 잃을 수 있다**
>
> "암시적 변환은 정보를 잃지 않는다"는 규칙에 하나의 예외가 있다. 정확히는, 규칙이 보장하는 것이 **크기**이지 **정밀도**가 아니다.
>
> ```csharp
> int i1 = 100000001;
> float f = i1;          // 암시적. 크기는 보존, 정밀도는 손실
> int i2 = (int) f;      // 100000000
> ```
>
> `float`은 유효 숫자를 24비트(약 7자리 10진수)밖에 담지 못한다. `100000001`은 9자리다. 마지막 자리가 표현되지 않아 `100000000`이 된다.
>
> `int` → `double`은 이 문제가 없다(`double`의 가수 53비트 > `int`의 32비트). 그러나 2<sup>53</sup>을 넘는 `long` 값은 `double`로 왕복하면 달라진다 — `(long)(double)9007199254740993L`은 `9007199254740992`다. 데이터베이스의 `bigint` ID를 JSON으로 넘길 때 값이 깨지는 유명한 버그가 이것이다.

### 컴파일 결과 — `conv` 계열 옵코드

숫자 변환은 IL에서 `conv.*` 옵코드 한 줄로 나온다.

```csharp
int  a = 300;
byte b = (byte) a;
long c = a;
```

```il
ldc.i4     0x12c
stloc.0
ldloc.0
conv.u1        // int32 → unsigned int8. 상위 24비트를 그냥 버린다
stloc.1
ldloc.0
conv.i8        // int32 → int64. 부호 확장
stloc.2
```

| C# 변환 | IL 옵코드 (unchecked) | IL 옵코드 (checked) |
|---|---|---|
| → `sbyte` | `conv.i1` | `conv.ovf.i1` |
| → `byte` | `conv.u1` | `conv.ovf.u1` |
| → `short` | `conv.i2` | `conv.ovf.i2` |
| → `ushort` | `conv.u2` | `conv.ovf.u2` |
| → `int` | `conv.i4` | `conv.ovf.i4` |
| → `uint` | `conv.u4` | `conv.ovf.u4` |
| → `long` | `conv.i8` | `conv.ovf.i8` |
| → `ulong` | `conv.u8` | `conv.ovf.u8` |
| → `float` | `conv.r4` | (검사 없음) |
| → `double` | `conv.r8` | (검사 없음) |

`conv.u1`은 상위 비트를 **검사 없이 버린다.** 이것이 축소 캐스트가 조용히 값을 망가뜨리는 메커니즘이다. `300`(`0x0000012C`)에서 하위 8비트만 남기면 `0x2C`, 즉 `44`다 — 위 코드에서 `b`에 실제로 들어가는 값이 그것이다.

`checked` 컨텍스트에서는 `conv.ovf.u1`이 되고, 값이 범위를 벗어나면 `OverflowException`이 던져진다. 7.9절의 주제다.

### 런타임 동작 — 확대는 공짜, 축소는 거의 공짜

JIT이 만드는 기계어 관점에서 정수 변환은 거의 비용이 없다.

- `conv.i8`(int → long, 부호 확장)은 x64에서 `movsxd` 한 명령이고, `conv.u1`(int → byte)은 대개 `movzx` 한 명령이거나 아예 사라진다.
- `conv.r8`(int → double)은 `cvtsi2sd` 한 명령이다. 반대로 `conv.i4`(double → int)는 `cvttsd2si`인데 지연 시간(latency)이 길다. 루프 안에서 부동소수점을 정수로 반복 변환하는 코드는 측정할 가치가 있다.

`conv.ovf.*`는 다르다. 범위 검사 분기가 하나 붙는다. 분기 예측이 잘 맞으면 비용이 작지만 0은 아니다. 이것이 C#의 기본이 `unchecked`인 이유다(7.9절).

> **⚠️ 부동소수점 → 정수 캐스트가 범위를 벗어나면 결과는 명세상 정의되지 않는다**
>
> ```csharp
> double huge = 1e20;
> int i = (int) huge;      // unchecked 컨텍스트: 결과는 "지정되지 않음(unspecified)"
> ```
>
> C# 명세는 `unchecked` 컨텍스트에서 부동소수점을 정수로 변환할 때 값이 대상 범위를 벗어나면 결과가 **지정되지 않는다**고 말한다. 예외도 던지지 않는다. 실제로 어떤 값이 나오는지는 런타임과 CPU 아키텍처에 달려 있고, 최신 .NET은 플랫폼 간 일관된 결과를 주도록 정리되었지만 **그 값에 의존하는 코드를 쓰면 안 된다.**
>
> 대안은 두 가지다. `checked`를 써서 `OverflowException`을 받거나, 캐스트 전에 범위를 직접 검사한다.
>
> ```csharp
> if (huge >= int.MinValue && huge <= int.MaxValue)
>     i = (int) huge;
> ```
>
> `double.NaN`을 정수로 캐스트하는 경우도 마찬가지로 위험하다. `checked`에서도 `NaN`은 `OverflowException`을 낸다.

### 성능 영향 — 변환을 없애는 것이 최적화다

변환 자체가 비싼 경우는 드물지만, 변환이 **강제하는 것**은 비쌀 수 있다.

- 루프 안에서 `int`와 `double`을 섞으면 매 반복마다 `cvtsi2sd`가 들어간다. 루프 밖에서 한 번 변환해두면 사라진다.
- `decimal`이 섞이면 모든 연산이 메서드 호출이 된다. 정수 → `decimal` 암시 변환도 `Decimal::op_Implicit` 호출이다.
- 핫 루프에서 타입을 하나로 통일하는 것이 대개 가장 큰 이득이다.

## 7.3 산술 연산자와 증감 연산자

### 다섯 개의 산술 연산자

산술 연산자는 다섯 개다. **8비트·16비트 정수 타입을 제외한** 모든 숫자 타입에 정의되어 있다. 왜 제외인지는 7.5절이다.

| 연산자 | 이름 | 예 | 결과 |
|---|---|---|---|
| `+` | 더하기 | `7 + 3` | `10` |
| `-` | 빼기 | `7 - 3` | `4` |
| `*` | 곱하기 | `7 * 3` | `21` |
| `/` | 나누기 | `7 / 3` | `2` (정수 나눗셈) |
| `%` | 나머지 | `7 % 3` | `1` |

`+`와 `-`는 단항으로도 쓴다. 단항 `+`는 아무 일도 하지 않고, 단항 `-`는 부호를 뒤집는다.

```csharp
int x = 5;
int y = -x;      // -5
int z = +x;      //  5. 사실상 의미 없다
```

### 이항 숫자 승격 — 피연산자 타입이 다를 때

`int + long`처럼 타입이 다른 두 값을 더하면 어떤 타입이 나오는가. 컴파일러는 **이항 숫자 승격**(binary numeric promotion) 규칙을 위에서부터 적용한다.

| 순서 | 조건 | 결과 |
|---|---|---|
| 1 | 한쪽이 `decimal` | 다른 쪽도 `decimal`로 변환. 다른 쪽이 `float`/`double`이면 **컴파일 오류** |
| 2 | 한쪽이 `double` | 다른 쪽도 `double` |
| 3 | 한쪽이 `float` | 다른 쪽도 `float` |
| 4 | 한쪽이 `ulong` | 다른 쪽도 `ulong`. 다른 쪽이 부호 있는 타입이면 **컴파일 오류** |
| 5 | 한쪽이 `long` | 다른 쪽도 `long` |
| 6 | 한쪽이 `uint`, 다른 쪽이 `sbyte`/`short`/`int` | **양쪽 다 `long`** |
| 7 | 한쪽이 `uint` | 다른 쪽도 `uint` |
| 8 | 그 밖에 전부 | **양쪽 다 `int`** |

이 표에서 실무적으로 중요한 행은 세 개다.

**1번 행** — `decimal`과 `double`은 섞이지 않는다. 아예 컴파일이 안 된다.

```csharp
decimal price = 10.5M;
double  rate  = 0.1;
// decimal total = price * rate;   // 컴파일 오류: decimal과 double은 섞을 수 없다
decimal total = price * (decimal) rate;   // 명시적 캐스트 필요
```

이것은 함정이 아니라 **안전장치**다. 컴파일러가 "정확한 타입과 부정확한 타입을 섞으려 한다"고 알려주는 것이다.

**4번 행** — `ulong`은 부호 있는 타입과 섞이지 않는다. `ulong a = 1; long b = 1;`일 때 `a + b`는 컴파일 오류다. `ulong`과 `long`을 다 담을 수 있는 미리 정의된 타입이 없기 때문이며, 어느 쪽으로 캐스트할지는 프로그래머가 결정해야 한다.

**6번 행** — `uint`와 `int`를 섞으면 둘 다 `long`이 된다. 7.1절의 ⚠️에서 본 그 규칙이다. 그리고 **8번 행**이 7.5절의 원인이다 — `byte`, `sbyte`, `short`, `ushort`, `char`끼리 연산하면 전부 `int`가 된다.

### 증감 연산자

`++`와 `--`는 숫자 타입을 1 증가·감소시킨다. 변수 앞에 붙일 수도 뒤에 붙일 수도 있고, **식의 값**이 달라진다.

```csharp
int x = 0, y = 0;
Console.WriteLine (x++);   // 0 출력. 그 후 x는 1
Console.WriteLine (++y);   // 1 출력. y도 1
```

후위(postfix) `x++`는 **증가하기 전 값**을 식의 값으로 내놓고, 전위(prefix) `++y`는 **증가한 후 값**을 내놓는다. 값을 쓰지 않고 문(statement)으로만 쓰면 둘은 완전히 같다.

```csharp
x++;    // 이 둘은
++x;    // 구별할 수 없다
```

### 컴파일 결과 — 전위와 후위의 IL 차이

식의 값을 쓸 때 IL이 어떻게 갈리는지 보면 개념이 선명해진다.

```csharp
int x = 0;
Console.WriteLine (x++);
```

```il
ldloc.0        // x를 스택에 올린다 (값 0)
dup            // 복제 → 스택: [0, 0]
ldc.i4.1
add            // 스택: [0, 1]
stloc.0        // x = 1. 스택: [0]  ← 증가 전 값이 남아 있다
call       void [System.Console]System.Console::WriteLine(int32)
```

전위는 순서가 하나 바뀐다.

```csharp
int y = 0;
Console.WriteLine (++y);
```

```il
ldloc.1
ldc.i4.1
add            // 스택: [1]
dup            // 스택: [1, 1]
stloc.1        // y = 1. 스택: [1]  ← 증가 후 값이 남아 있다
call       void [System.Console]System.Console::WriteLine(int32)
```

`dup`의 위치가 `add` 앞이냐 뒤냐가 전부다. 명령 개수는 같으므로 **전위가 후위보다 빠르다는 말은 C#에서 사실이 아니다.** C++에서 반복자(iterator) 객체에 대해서는 의미가 있었던 조언이지만, C#의 내장 숫자 타입에는 해당하지 않는다.

> **⚠️ 한 식 안에서 같은 변수를 두 번 이상 증감시키지 마라**
>
> `int i = 1; int r = i++ + i++;`의 값은 C#에서 결정적이다 — 평가 순서가 왼쪽에서 오른쪽으로 **정의되어 있으므로** `1 + 2 = 3`이다(C/C++와 달리 미정의 동작이 아니다). 그러나 결정적이라는 것과 읽을 수 있다는 것은 다르다.
>
> **증감 연산자는 문으로만 쓰고, 식 안에서는 쓰지 않는다.** 예외는 `arr[i++] = v` 같은 아주 관용적인 형태 정도다.

### 복합 할당 연산자

`x += 3`은 `x = x + 3`의 축약이지만, 정확히 같지는 않다. 복합 할당은 **결과를 원래 타입으로 되돌리는 캐스트를 자동으로 포함한다.**

```csharp
byte b = 250;
// b = b + 1;    // 컴파일 오류: int를 byte에 대입할 수 없다
b += 1;          // OK. b = (byte)(b + 1)과 같다
```

이 규칙 때문에 복합 할당은 오버플로를 조용히 삼킬 수 있다.

```csharp
byte b = 255;
b += 1;
Console.WriteLine (b);   // 0
```

`b + 1`은 `int` 256이고, `(byte)256`은 0이다. 컴파일러가 끼워 넣은 캐스트가 아무 경고 없이 값을 지웠다.

산술·비트·시프트 계열의 복합 할당 연산자(`+=`, `-=`, `*=`, `/=`, `%=`, `&=`, `|=`, `^=`, `<<=`, `>>=`)가 전부 이 숨은 캐스트를 갖는다.

또 하나의 차이: `x`가 복잡한 식(`arr[Index()]` 같은)이면 복합 할당은 그 식을 **한 번만** 평가한다. `arr[Index()] += 1`은 `Index()`를 한 번 호출하고, `arr[Index()] = arr[Index()] + 1`은 두 번 호출한다.

> **💡 `+=`를 쓰되, 작은 정수 타입에서는 조심하라**
>
> `int`와 `long`에서 복합 할당은 안전하고 읽기도 좋다. 문제는 `byte`, `sbyte`, `short`, `ushort`다. 이 타입들에서 `+=`는 컴파일러가 캐스트를 대신 써주는 것이라, **명시적 캐스트를 쓸 때와 똑같이 위험한데 눈에 보이지 않는다.** 누적은 `int`나 `long`에서 하고, 저장할 때만 좁혀라.

## 7.4 정수 특화 연산 — 나눗셈, 오버플로, 비트 연산

정수 타입은 `int`, `uint`, `long`, `ulong`, `short`, `ushort`, `byte`, `sbyte`(그리고 `nint`/`nuint`)다. 이 타입들에만 적용되는 규칙이 몇 개 있다.

### 정수 나눗셈 — 소수점을 버린다

정수끼리의 `/`는 항상 나머지를 버린다. **0 방향으로 절삭한다**(round toward zero).

```csharp
int a = 2 / 3;      // 0
int b = 7 / 2;      // 3
int c = -7 / 2;     // -3   (-4가 아니다)
```

`-7 / 2`가 `-3`이라는 점이 중요하다. 수학의 바닥 함수(floor)를 기대하면 `-4`가 나와야 하지만, C#은 0 쪽으로 자른다. C, C++, Java와 같은 규칙이다.

### 나머지의 부호 규칙

`%`의 결과 부호는 **왼쪽 피연산자(피제수)의 부호를 따른다.** 오른쪽 피연산자의 부호는 결과 부호에 영향을 주지 않는다.

| 식 | 결과 | 설명 |
|---|---|---|
| `7 % 3` | `1` | 피제수 양수 → 결과 양수 |
| `-7 % 3` | `-1` | 피제수 음수 → 결과 음수 |
| `7 % -3` | `1` | 제수 부호는 무관 |
| `-7 % -3` | `-1` | 피제수 음수 → 결과 음수 |

이 규칙은 `a == (a / b) * b + (a % b)`라는 항등식에서 나온다. `/`가 0 방향 절삭이므로 `%`도 그에 맞춰진 것이다.

> **⚠️ `%`로 짝수/홀수를 판정할 때 음수에서 깨진다**
>
> 가장 흔한 사고 중 하나다.
>
> ```csharp
> bool IsOdd (int n) => n % 2 == 1;    // 버그
>
> Console.WriteLine (IsOdd (3));    // True
> Console.WriteLine (IsOdd (-3));   // False  ← -3 % 2는 -1이다
> ```
>
> 올바른 판정은 `!= 0` 쪽이다.
>
> ```csharp
> bool IsOdd (int n) => n % 2 != 0;    // 음수에서도 맞다
> ```
>
> 원형 버퍼 인덱스에도 같은 함정이 있다. `(i - 1) % length`는 `i`가 0일 때 `-1`을 준다. 항상 음이 아닌 나머지를 원한다면 보정이 필요하다.
>
> ```csharp
> int Mod (int a, int m) => (a % m + m) % m;   // 항상 0 이상
> ```

### 0으로 나누기

변수의 값이 0인 상태로 나누면 런타임에 `DivideByZeroException`이 던져진다.

```csharp
int b = 0;
int c = 5 / b;    // DivideByZeroException
```

리터럴이나 상수 `0`으로 나누면 **컴파일 오류**다. 컴파일러가 상수 폴딩을 하다가 발견한다.

```csharp
// int d = 5 / 0;    // 컴파일 오류
```

부동소수점은 다르다. `5.0 / 0.0`은 예외가 아니라 `Infinity`다(7.6절). `decimal`은 정수처럼 `DivideByZeroException`을 던진다.

> **⚠️ `int.MinValue / -1`은 예외를 던진다**
>
> 정수 나눗셈에서 예외가 나는 경우는 0으로 나눌 때만이 아니다.
>
> ```csharp
> int x = int.MinValue;
> int y = -1;
> int z = x / y;    // OverflowException
> ```
>
> `int.MinValue`는 −2,147,483,648이고 그 부호를 뒤집은 2,147,483,648은 `int`에 담기지 않는다. 이 경우 명세가 `System.OverflowException`을 요구한다. **`unchecked` 컨텍스트에서도 던져진다** — 하드웨어 수준의 오류이지 언어의 오버플로 검사가 아니기 때문이다.
>
> 같은 조합에 대한 `%` 연산(`int.MinValue % -1`)의 동작은 구현에 따라 다르다. 명세가 `OverflowException` 또는 `0` 중 하나를 허용한다. 이 조합에 의존하는 코드를 쓰지 마라.

### 오버플로 — 조용한 순환

정수 연산이 타입의 한계를 넘으면 **기본적으로 아무 일도 일어나지 않는다.** 예외도 없고 경고도 없다. 결과는 "더 큰 정수 타입에서 계산한 뒤 상위 비트를 버린 것"처럼 순환(wraparound)한다.

```csharp
int a = int.MinValue;
a--;
Console.WriteLine (a == int.MaxValue);   // True
```

반대 방향도 마찬가지다.

```csharp
int x = int.MaxValue - 1;
Console.WriteLine (x);   // 2147483646
x++;  Console.WriteLine (x);   // 2147483647
x++;  Console.WriteLine (x);   // -2147483648   ← 조용히 넘어갔다
x++;  Console.WriteLine (x);   // -2147483647
```

이 동작을 바꾸는 방법이 `checked`다. 7.9절 전체가 그 이야기다.

### 왜 순환하는가 — 2의 보수

순환이 마법처럼 보이지만 원리는 단순하다. .NET의 부호 있는 정수는 **2의 보수**(two's complement)로 저장된다. 최상위 비트가 부호를 나타내되, 음수는 "절댓값의 비트를 뒤집고 1을 더한" 형태다.

```text
        10진               2진 (32비트)
 2147483647   0111 1111 1111 1111 1111 1111 1111 1111   ← int.MaxValue
          8   0000 0000 0000 0000 0000 0000 0000 1000
          2   0000 0000 0000 0000 0000 0000 0000 0010
          1   0000 0000 0000 0000 0000 0000 0000 0001
          0   0000 0000 0000 0000 0000 0000 0000 0000
         -1   1111 1111 1111 1111 1111 1111 1111 1111   ← 전부 1
         -2   1111 1111 1111 1111 1111 1111 1111 1110
         -8   1111 1111 1111 1111 1111 1111 1111 1000
-2147483648   1000 0000 0000 0000 0000 0000 0000 0000   ← int.MinValue
```

양수는 전부 최상위 비트가 0, 음수는 전부 1이다. `int.MaxValue`(`0111...1`)에 1을 더하면 `1000...0`이 되는데, 이 비트 패턴이 곧 `int.MinValue`다. CPU 입장에서는 그냥 덧셈이고, 자리올림이 부호 비트로 넘어갔을 뿐이다.

이 표현 덕분에 `long`을 `int`로 자를 때 어떤 값이 나오는지도 예측할 수 있다.

```csharp
long e = long.MaxValue;
Console.WriteLine ((int) e);      // -1   (하위 32비트가 전부 1)

e = 5_000_000_000;
Console.WriteLine ((int) e);      // 705032704   (5,000,000,000 - 4,294,967,296)
```

`long.MaxValue`의 하위 32비트는 전부 1이고, 32비트 2의 보수에서 전부 1은 `-1`이다.

### 비트 연산자

| 연산자 | 의미 | 예 | 결과 |
|---|---|---|---|
| `~` | 보수(complement) | `~0xfU` | `0xfffffff0U` |
| `&` | AND | `0xf0 & 0x33` | `0x30` |
| `\|` | OR | `0xf0 \| 0x33` | `0xf3` |
| `^` | XOR | `0xff00 ^ 0x0ff0` | `0xf0f0` |
| `<<` | 왼쪽 시프트 | `0x20 << 2` | `0x80` |
| `>>` | 오른쪽 시프트 | `0x20 >> 1` | `0x10` |
| `>>>` | 부호 없는 오른쪽 시프트 ※C# 11 | `int.MinValue >>> 1` | `0x40000000` |

`>>`와 `>>>`의 차이가 핵심이다. **`>>`는 부호 있는 정수에서 최상위 비트를 복제한다**(산술 시프트). 즉 음수를 오른쪽으로 밀어도 음수로 남는다. `>>>`는 최상위에 항상 0을 채운다(논리 시프트).

```csharp
int n = -8;                       // 1111 ... 1111 1000
Console.WriteLine (n >> 1);       // -4    부호 유지
Console.WriteLine (n >>> 1);      // 2147483644   부호 비트가 0으로 밀려남
```

`>>>`가 ※C# 11에서 들어오기 전에는 부호 없는 타입으로 캐스트해서 같은 일을 했다.

```csharp
int old = (int)((uint) n >> 1);   // C# 11 이전의 관용구
```

> **⚠️ 시프트 횟수는 마스킹된다**
>
> `x << 32`가 0이 될 것 같지만 아니다.
>
> ```csharp
> int x = 1;
> Console.WriteLine (x << 32);   // 1   (0이 아니다!)
> Console.WriteLine (x << 33);   // 2
> ```
>
> `int`/`uint`에 대한 시프트 횟수는 하위 **5비트**만 쓴다(`count & 0x1F`). 32는 `0b100000`이고 하위 5비트가 전부 0이므로 `x << 0`, 즉 시프트를 하지 않은 것과 같다.
>
> `long`/`ulong`에 대해서는 하위 **6비트**를 쓴다(`count & 0x3F`).
>
> 이 규칙은 x86/x64 CPU의 시프트 명령이 원래 그렇게 동작하기 때문에 생겼다. 언어가 매번 검사를 넣는 대신 하드웨어 동작을 그대로 노출한 것이다. 시프트 횟수가 변수라면 범위를 직접 검사하라.

시프트로 곱셈·나눗셈을 대신하는 옛 최적화는 지금은 대개 불필요하다. JIT이 `x * 8`을 알아서 `shl`로 바꾼다. 다만 **음수 나눗셈에서 `/`와 `>>`는 다르다** — `-7 / 2`는 `-3`(0 방향 절삭)이고 `-7 >> 1`은 `-4`(음의 무한대 방향)다. 그래서 JIT은 `n / 2`를 단순 `shr`로 바꾸지 못하고 보정 명령을 추가한다.

`System.Numerics.BitOperations` 클래스가 비트 세기(`PopCount`), 선행 0 세기(`LeadingZeroCount`), 회전(`RotateLeft`) 같은 연산을 하드웨어 명령으로 제공한다. 자세히는 39.6절이다.

> **📌 비트 연산자와 `bool`**
>
> C/C++과 달리 C#에서 `&`와 `|`를 `bool`에 적용하면 **비트 연산이 아니라 단축 평가하지 않는 논리 연산**이 된다. 숫자에 적용할 때만 비트 연산이다. 7.10절에서 `&&`와 대비해 다룬다.

## 7.5 8비트·16비트 정수 타입의 함정

### 이 타입들에는 산술 연산자가 없다

`byte`, `sbyte`, `short`, `ushort`에는 **자기만의 산술 연산자가 정의되어 있지 않다.** 그래서 C#은 필요할 때마다 이들을 더 큰 타입 — 구체적으로 `int` — 으로 암시 변환한다.

```csharp
short x = 1, y = 1;
// short z = x + y;    // 컴파일 오류 CS0266
```

`x`와 `y`가 `int`로 승격되어 덧셈이 수행되므로 **결과도 `int`**다. 그리고 `int`는 `short`로 암시 변환되지 않는다(데이터 손실 가능). 명시적 캐스트를 붙여야 컴파일된다.

```csharp
short z = (short)(x + y);   // OK
```

승격 규칙을 표로 정리하면 이렇다.

| 식 | 피연산자 승격 후 | 결과 타입 |
|---|---|---|
| `byte + byte` | `int + int` | `int` |
| `short + short` | `int + int` | `int` |
| `ushort * ushort` | `int * int` | `int` |
| `byte + short` | `int + int` | `int` |
| `char + char` | `int + int` | `int` |
| `sbyte - byte` | `int - int` | `int` |
| `short + int` | `int + int` | `int` |
| `short + long` | `long + long` | `long` |
| `byte + 1` (리터럴) | `int + int` | `int` |
| `-someByte` (단항) | `-(int)` | `int` |

마지막 두 행이 특히 자주 사람을 잡는다. `byte`에 리터럴 `1`을 더해도 `int`가 되고, `byte`에 단항 마이너스만 붙여도 `int`가 된다.

### 컴파일 결과 — 승격은 IL에 보이지 않는다

흥미롭게도 이 승격은 IL에서 **별도 명령을 만들지 않는다.**

```csharp
short x = 1, y = 1;
short z = (short)(x + y);
```

```il
ldc.i4.1
stloc.0        // x
ldc.i4.1
stloc.1        // y
ldloc.0
ldloc.1
add            // 승격을 위한 conv 명령이 없다
conv.i2        // 명시적 캐스트만 남는다
stloc.2        // z
```

이유는 CLR의 평가 스택 자체가 32비트 미만의 정수를 담지 못하기 때문이다. `ldloc`으로 `short` 지역 변수를 스택에 올리는 순간 이미 32비트 `int32`로 확장되어 있다. C#의 승격 규칙은 **CLR이 원래 그렇게 동작하는 것을 언어 수준에서 정직하게 반영한 것**이지, 언어가 만들어낸 별도 규칙이 아니다.

### 8/16비트 타입이 감추는 오버플로

이 승격 규칙과 축소 캐스트가 결합하면 값이 조용히 망가진다. 원천 도서의 예제를 그대로 따라가 보자.

```csharp
static int Add (int x, int y) => x + y;

byte b1 = 100;
byte b2 = 250;
byte sum = (byte) Add (b1, b2);
Console.WriteLine (sum);    // 350이 아니라 94
```

`b1`과 `b2`는 각각 `byte` 범위 안에 있다. `Add`는 `int`를 받아 `int` 350을 돌려준다. 그런데 `(byte)350`은 350 − 256 = **94**다. 세 줄짜리 코드에서 값이 완전히 틀렸고 아무 경고도 없다.

`short`도 마찬가지다.

```csharp
short numb1 = 30000, numb2 = 30000;
short answer = (short) Add (numb1, numb2);
Console.WriteLine (answer);    // -5536
```

60,000은 `short`의 최댓값 32,767을 넘는다. `(short)60000`은 60,000 − 65,536 = −5,536이다.

> **⚠️ 캐스트는 "괜찮다는 확인"이지 "안전하게 해달라는 부탁"이 아니다**
>
> 위 두 예제에서 컴파일러는 캐스트를 요구했고, 프로그래머는 캐스트를 붙였고, 값은 망가졌다. 이것은 컴파일러의 잘못이 아니다. 캐스트란 **"이 변환에서 데이터가 손실될 수 있음을 알고 있으며 책임지겠다"**는 선언이기 때문이다.
>
> 캐스트를 붙일 때마다 자문해야 한다. **"이 값이 대상 타입의 범위를 넘을 수 있는가."** 넘을 수 있다면 캐스트가 아니라 범위 검사나 `checked`(7.9절)가 필요하다.
>
> 코드 리뷰에서 `(byte)`, `(short)`, `(int)` 캐스트를 보면 그 값의 출처를 따라 올라가는 습관을 들여라. 외부 입력에서 온 값이면 거의 항상 버그다.

### 그럼 언제 쓰는가

작은 정수 타입을 쓸 정당한 이유는 세 가지다.

| 이유 | 예 | 비고 |
|---|---|---|
| 상호운용 | 네이티브 구조체 필드, 바이너리 프로토콜 헤더 | 크기가 계약의 일부다 |
| 대량 데이터의 메모리 절약 | `byte[]` 이미지 버퍼, `short[]` 오디오 샘플 | 배열에서만 의미가 있다 |
| 도메인상 자연스러운 범위 | 색상 채널 0~255 | 유혹이지만 대개 `int`가 낫다 |

**단일 변수나 필드 하나를 `short`로 선언해서 메모리를 아끼려는 시도는 대개 헛수고다.** 정렬(alignment) 때문에 구조체 크기가 줄지 않는 경우가 많고(54.4절), 지역 변수는 어차피 32비트 슬롯이나 레지스터에 들어간다. 이득은 **배열**에서 나온다. 100만 개짜리 `int[]`는 4MB지만 `short[]`는 2MB다.

> **💡 누산은 `int`로, 저장은 좁은 타입으로**
>
> ```csharp
> // 나쁜 코드: byte로 누적한다
> byte sum = 0;
> foreach (byte b in data) sum += b;   // 조용히 순환한다
>
> // 좋은 코드: 넓은 타입으로 누적하고 마지막에만 좁힌다
> int total = 0;
> foreach (byte b in data) total += b;
> byte avg = (byte)(total / data.Length);   // 이 캐스트는 안전함을 증명할 수 있다
> ```
>
> "좁은 타입은 저장 형식이고, 계산은 넓은 타입에서 한다"는 원칙 하나로 이 절의 함정 대부분이 사라진다.

### 성능 영향

작은 정수 타입이 **더 빠를 것이라는 기대는 틀렸다.** 현대 x64 CPU에서 32비트 연산이 가장 자연스럽고, 8비트·16비트 연산은 부분 레지스터 접근 때문에 오히려 느려질 수 있다. 게다가 C#은 모든 연산을 `int`로 승격하므로 실제 계산은 어차피 32비트로 이뤄지고 좁히는 `conv` 명령만 추가된다.

작은 타입의 이득은 **연산 속도가 아니라 메모리 대역폭**에 있다. 캐시에 두 배 많은 데이터가 들어가면 순회 루프가 빨라진다. 판단 기준은 하나다 — **데이터가 크고 배열로 다루는가.**

## 7.6 `float`/`double`의 특수값 — NaN, ±∞, -0

### IEEE 754 — 부동소수점의 실체

`float`과 `double`은 **IEEE 754** 표준을 따른다. 1985년에 제정된 부동소수점 산술 표준이며 거의 모든 CPU가 하드웨어로 지원한다. 그래서 `double`의 덧셈은 CPU 명령 한 개다.

비트가 어떻게 나뉘는지 보자.

```text
float (32비트, IEEE 754 단정밀도)
┌─┬────────────┬───────────────────────────────────────┐
│S│  지수 (8)  │            가수 (23비트)               │
└─┴────────────┴───────────────────────────────────────┘
 31 30      23 22                                      0
  │      │                        │
  │      │                        └─ 소수부. 앞의 "1."은 생략(암묵적 1)
  │      └─ 편향(bias) 127. 저장값 - 127 = 실제 지수
  └─ 부호. 0이면 양수, 1이면 음수

double (64비트, IEEE 754 배정밀도)
┌─┬──────────────────┬───────────────────────────────────────────┐
│S│    지수 (11)     │              가수 (52비트)                 │
└─┴──────────────────┴───────────────────────────────────────────┘
 63 62            52 51                                          0
                   │                     │
                   │                     └─ 유효 숫자 53비트 상당(암묵적 1 포함)
                   └─ 편향 1023

값 = (-1)^S × 1.가수 × 2^(지수 - 편향)         ← 정규화된 수
```

`double`의 유효 자릿수가 "15~16자리"인 이유가 여기 있다. 가수 52비트 + 암묵적 1비트 = 53비트이고, 2<sup>53</sup> ≈ 9.007 × 10<sup>15</sup>이므로 10진수로 약 15.95자리다.

지수 필드가 전부 0이거나 전부 1인 패턴은 특별한 의미로 예약되어 있다. 그것이 특수값의 정체다.

| 지수 비트 | 가수 비트 | 의미 |
|---|---|---|
| 전부 0 | 0 | ±0 (부호 비트에 따라 +0 또는 −0) |
| 전부 0 | 0이 아님 | 비정규화 수(subnormal). 아주 작은 값 |
| 1 ~ 최대−1 | 임의 | 정규화된 보통의 수 |
| 전부 1 | 0 | ±∞ |
| 전부 1 | 0이 아님 | NaN (Not a Number) |

### 네 가지 특수값

`float`과 `double`에는 정수 타입에 없는 네 가지 값이 있다. **NaN**, **+∞**, **−∞**, **−0**이다.

| 특수값 | `double` 상수 | `float` 상수 |
|---|---|---|
| NaN | `double.NaN` | `float.NaN` |
| +∞ | `double.PositiveInfinity` | `float.PositiveInfinity` |
| −∞ | `double.NegativeInfinity` | `float.NegativeInfinity` |
| −0 | `-0.0` | `-0.0f` |

```csharp
Console.WriteLine (double.NegativeInfinity);   // -Infinity
```

**0이 아닌 수를 0으로 나누면 무한대가 된다.** 예외가 아니다.

```csharp
Console.WriteLine ( 1.0 /  0.0);   // Infinity
Console.WriteLine (-1.0 /  0.0);   // -Infinity
Console.WriteLine ( 1.0 / -0.0);   // -Infinity
Console.WriteLine (-1.0 / -0.0);   // Infinity
```

셋째 줄에 주목하라. `-0.0`은 `0.0`과 `==` 비교에서 같다고 나오지만, 나눗셈에서는 부호가 살아 있다. **−0은 "0에 0 아래에서 접근한 흔적"을 담고 있다.**

**0을 0으로 나누거나, 무한대에서 무한대를 빼면 NaN이 된다.**

```csharp
Console.WriteLine ( 0.0 / 0.0);                    // NaN
Console.WriteLine ((1.0 / 0.0) - (1.0 / 0.0));     // NaN
Console.WriteLine (Math.Sqrt (-1));                // NaN
```

### `NaN != NaN` — 가장 유명한 함정

`==` 연산자로 비교할 때 **NaN은 어떤 값과도 같지 않다. 다른 NaN과도 같지 않다.**

```csharp
Console.WriteLine (0.0 / 0.0 == double.NaN);   // False
double nan = double.NaN;
Console.WriteLine (nan == nan);                 // False
Console.WriteLine (nan != nan);                 // True  ← 자기 자신과 다르다
```

이것은 버그가 아니라 IEEE 754의 설계다. NaN은 "정의되지 않은 결과"를 뜻하므로, 서로 다른 두 계산에서 나온 NaN을 같다고 말할 근거가 없다는 논리다.

NaN인지 확인하려면 전용 메서드를 써야 한다.

```csharp
Console.WriteLine (double.IsNaN (0.0 / 0.0));   // True
```

그런데 `object.Equals`를 쓰면 결과가 뒤집힌다.

```csharp
Console.WriteLine (object.Equals (0.0 / 0.0, double.NaN));   // True
```

`Double.Equals`는 `==` 비교에 "둘 다 NaN이면 같다"는 특례를 얹어 구현되어 있다. 컬렉션과 정렬이 제대로 동작하려면 동등성이 **반사적**(자기 자신과 같음)이어야 하기 때문이다. 만약 `Equals`가 `==`와 똑같이 동작한다면 `List<double>.Contains(double.NaN)`이 항상 `false`가 되고, `Dictionary`에서 NaN 키를 다시 꺼낼 수 없게 된다.

> **⚠️ `==`와 `Equals`가 다르게 동작하는 드문 경우가 여기다**
>
> 대부분의 값 타입에서 `x == y`와 `x.Equals(y)`는 같은 결과를 준다. `double`과 `float`은 예외다.
>
> | 비교 | `NaN` vs `NaN` | `0.0` vs `-0.0` |
> |---|---|---|
> | `==` | `false` | `true` |
> | `Equals` | `true` | `true` |
> | `CompareTo` | `0` (같음) | `0` (같음) |
>
> 이 차이가 실제로 드러나는 자리는 정렬과 딕셔너리다. `Array.Sort`는 `CompareTo`를 쓰므로 NaN이 어딘가에 안정적으로 모인다(`Double.CompareTo`는 NaN을 모든 값보다 작다고 본다). 반면 직접 `<`로 비교하는 정렬 알고리즘에 NaN이 섞이면 비교 결과가 모순되어 순서가 엉망이 되거나 예외가 날 수 있다.
>
> 결론: **NaN이 섞일 수 있는 데이터는 정렬·그룹화 전에 걸러내라.**

### 순서 비교와 NaN

NaN이 관여하면 `<`, `>`, `<=`, `>=`가 **전부 `false`**다. `!=`만 `true`다.

```csharp
double nan = double.NaN;
Console.WriteLine (nan <  1.0);   // False
Console.WriteLine (nan >  1.0);   // False
Console.WriteLine (nan <= 1.0);   // False
Console.WriteLine (nan >= 1.0);   // False
Console.WriteLine (nan != 1.0);   // True
```

`nan < 1.0`과 `nan >= 1.0`이 **둘 다 false**다. 보통의 논리에서는 이 둘이 서로의 부정이어야 한다. IEEE 754는 이것을 **비교 불가능(unordered)** 관계라고 부른다.

> **⚠️ `if (!(x < limit))`와 `if (x >= limit)`는 다르다**
>
> NaN이 들어올 수 있는 코드에서 조건을 뒤집을 때 실수가 나온다.
>
> ```csharp
> double x = double.NaN;
> if (x >= 0) Console.WriteLine ("A");     // 실행 안 됨
> if (!(x < 0)) Console.WriteLine ("B");   // 실행됨
> ```
>
> 드모르간의 법칙이 부동소수점 비교에는 그대로 적용되지 않는다. 유효성 검사 코드에서 이 차이가 보안 취약점이 되기도 한다. 입력을 검증할 때는 NaN을 명시적으로 배제하는 편이 안전하다.
>
> ```csharp
> if (double.IsNaN (x) || x < 0 || x > 100)
>     throw new ArgumentOutOfRangeException (nameof (x));
> ```

### 무한대와 오버플로

정수와 달리 부동소수점은 **오버플로해도 예외를 던지지 않는다.** 무한대가 될 뿐이다.

```csharp
double huge = double.MaxValue;
Console.WriteLine (huge * 2);              // Infinity
Console.WriteLine (huge * 2 - huge);       // Infinity  (∞ - 유한값 = ∞)
Console.WriteLine ((float) huge);          // Infinity  (float 범위를 넘었다)
Console.WriteLine (double.Epsilon / 2);    // 0         (언더플로도 조용하다)
```

이 때문에 `checked` 연산자는 `double`과 `float`에 **아무 효과가 없다**(7.9절).

> **⚠️ `double.Epsilon`은 비교 허용 오차가 아니다**
>
> 이름 때문에 착각하기 쉽다. 다른 언어와 라이브러리에서 "엡실론"은 흔히 "머신 엡실론", 즉 1.0과 그 다음 표현 가능한 수의 차이(`double`의 경우 약 2.22 × 10<sup>−16</sup>)를 뜻한다. **.NET의 `double.Epsilon`은 그것이 아니다.** 표현 가능한 가장 작은 양수, 즉 4.94 × 10<sup>−324</sup>다.
>
> ```csharp
> // 절대 이렇게 쓰지 마라
> if (Math.Abs (a - b) < double.Epsilon) { /* 사실상 a == b와 같다 */ }
> ```
>
> `double.Epsilon`은 너무 작아서 이 검사는 `a == b`와 다를 바가 없다. 올바른 비교 방법은 7.8절에서 다룬다.

### 특수값 검사 API

| 메서드 | 검사 대상 |
|---|---|
| `double.IsNaN(x)` | NaN인가 |
| `double.IsInfinity(x)` | +∞ 또는 −∞인가 |
| `double.IsPositiveInfinity(x)` | +∞인가 |
| `double.IsNegativeInfinity(x)` | −∞인가 |
| `double.IsFinite(x)` | NaN도 무한대도 아닌가 |
| `double.IsNegative(x)` | 부호 비트가 켜져 있는가 (−0도 `true`) |

`IsNegative`가 −0을 잡아내는 유일한 방법이다. `x < 0`으로는 −0을 구별할 수 없다 — `-0.0 == 0.0`은 `true`이고 `-0.0 < 0.0`은 `false`지만, `double.IsNegative(-0.0)`은 `true`이고 `1.0 / -0.0`은 `-Infinity`다.

> **📌 NaN을 "값 없음"으로 쓰는 관행**
>
> NaN을 "측정되지 않음"이나 "자동"의 표시로 쓰는 API가 실제로 있다. WPF(Windows Presentation Foundation)에서 `double.NaN`은 크기가 "Automatic"임을 뜻한다. 같은 목적에는 널 가능 타입 `double?`(21장)나 플래그 필드를 둔 사용자 정의 구조체가 더 낫다 — NaN 관례는 비교 연산이 전부 `false`가 되는 함정을 데이터 전체에 퍼뜨린다.

## 7.7 `double` vs `decimal` — 언제 무엇을 쓰는가

### 표현 방식이 근본적으로 다르다

두 타입의 차이는 정밀도의 크고 작음이 아니라 **밑수**(base)다.

- `double`은 **2진수**로 저장한다. 값 = 가수 × 2<sup>지수</sup>
- `decimal`은 **10진수**로 저장한다. 값 = 가수 × 10<sup>−지수</sup>

`decimal`의 128비트는 이렇게 쓰인다.

```text
decimal (128비트)
┌─┬───────────┬────────────────────────────────────────────────┐
│S│ 스케일(8) │  미사용   │        96비트 정수 가수              │
└─┴───────────┴────────────────────────────────────────────────┘
 │      │                              │
 │      │                              └─ 0 ~ 2^96-1 의 정수
 │      └─ 0 ~ 28. 소수점을 왼쪽으로 몇 칸 옮길지
 └─ 부호

값 = (-1)^S × 가수 / 10^스케일
```

즉 `decimal`은 "큰 정수 하나와 소수점 위치 메모"다. `0.1M`은 가수 1에 스케일 1로 저장된다. `12.75M`은 가수 1275에 스케일 2다. 10진수를 10진수로 저장하므로 **10진 리터럴을 정확히 표현한다.**

`double`은 그럴 수 없다. 0.1을 2진 분수로 쓰면 무한히 반복되기 때문이다. 자세한 원리는 7.8절이다.

### 비교표

| 항목 | `double` | `decimal` |
|---|---|---|
| 내부 표현 | 밑수 2 | 밑수 10 |
| 크기 | 8바이트 | 16바이트 |
| 10진 정밀도 | 유효 숫자 15~16자리 | 유효 숫자 28~29자리 |
| 범위 | ±(~10<sup>−324</sup> ~ ~10<sup>308</sup>) | ±(~10<sup>−28</sup> ~ ~10<sup>28</sup>) |
| 특수값 | +0, −0, +∞, −∞, NaN | 없음 |
| 0으로 나누기 | ±∞ 또는 NaN | `DivideByZeroException` |
| 오버플로 | ∞ (예외 없음) | `OverflowException` (항상) |
| 연산 방식 | CPU 네이티브 명령 | 라이브러리 메서드 호출 |
| 속도 | 빠름 | `double`의 약 1/10 |
| 0.1을 정확히 표현? | 아니오 | 예 |
| 1/3을 정확히 표현? | 아니오 | 아니오 |

마지막 두 행이 중요하다. `decimal`은 **만능이 아니다.** 10진법으로 유한하게 쓸 수 없는 수 — 1/3 같은 순환소수 — 는 `decimal`도 정확히 담지 못한다.

```csharp
decimal m = 1M / 6M;    // 0.1666666666666666666666666667M
double  d = 1.0 / 6.0;  // 0.16666666666666666
```

`decimal`이 보장하는 것은 **10진 소수 리터럴의 정확한 표현**과 **10진 기준의 반올림**이지 수학적 완전성이 아니다.

### 컴파일 결과 — 왜 10배 느린가

`double`의 덧셈은 IL 명령 한 개다.

```csharp
double a = 1.5, b = 2.5;
double c = a + b;
```

```il
ldloc.0
ldloc.1
add            // CPU의 addsd 한 명령으로 JIT된다
stloc.2
```

`decimal`은 다르다. 같은 코드를 `decimal`로 쓰면 이렇게 된다.

```il
ldloc.0
ldloc.1
call       valuetype [System.Runtime]System.Decimal
             [System.Runtime]System.Decimal::op_Addition(
               valuetype [System.Runtime]System.Decimal,
               valuetype [System.Runtime]System.Decimal)
stloc.2
```

6.5절에서 본 대로 `decimal`은 CLR의 원시 타입이 아니다. `+`는 `op_Addition`이라는 **정적 메서드 호출**로 컴파일된다(연산자 오버로딩의 실체 — 22.6절). 그 메서드 안에서는 두 값의 스케일을 맞추고, 96비트 정수 연산을 하고, 결과를 정규화한다. CPU 명령 하나로 끝나는 `double`과 비교가 되지 않는다.

곱셈과 나눗셈은 격차가 더 크다. 스케일 조정과 다중 워드 나눗셈이 필요하기 때문이다.

> **📌 `decimal` 연산이 항상 검사된다는 사실**
>
> `decimal` 연산은 `checked` 컨텍스트와 무관하게 **항상** 오버플로를 검사하고, 넘으면 `OverflowException`을 던진다. `unchecked`로 감싸도 마찬가지다. 이것은 `decimal`이 언어 수준 연산자가 아니라 라이브러리 메서드이기 때문이다 — `unchecked` 키워드는 IL 옵코드 선택에 영향을 주는데, `decimal`에는 선택할 옵코드가 없다.
>
> 금액을 다루는 코드에서 이 성질은 장점이다. 조용히 순환하는 대신 즉시 실패한다.

### 선택 기준표

| 상황 | 선택 | 이유 |
|---|---|---|
| 금액, 통화, 회계 | `decimal` | 10진 정확성이 계약이다. 1원 오차도 감사에서 문제가 된다 |
| 세율, 이자율, 할인율 계산 | `decimal` | 금액과 곱해지므로 같은 세계에 있어야 한다 |
| 사람이 입력하고 사람이 읽는 10진 값 | `decimal` | 왕복(round-trip)이 정확하다 |
| 물리 측정값 (온도, 무게, 거리) | `double` | 측정 자체에 오차가 있다. 정확한 10진은 의미 없다 |
| 좌표, 그래픽, 3D 변환 | `double` 또는 `float` | 속도가 중요하고 정밀도 요구가 낮다 |
| 통계, 과학 계산, 머신러닝 | `double` | 라이브러리 생태계가 `double` 기반이다 |
| GPU/SIMD 대상 대량 연산 | `float` | 대역폭이 절반이고 하드웨어 지원이 넓다 |
| 넓은 범위가 필요한 값 (10<sup>30</sup> 이상) | `double` | `decimal`의 범위는 ±10<sup>28</sup>까지다 |
| 성능이 극단적으로 중요한 루프 | `double`/`float` | `decimal`은 10배 느리다 |

원천 도서의 요약은 이렇다. **`double`은 "실세계를 측정한 값", `decimal`은 "사람이 만들어낸 값"에 쓴다.** 온도계가 읽은 36.5도는 측정값이고, 상품 가격 36,500원은 만들어낸 값이다.

> **⚠️ 금액에 `double`을 쓰면 안 되는 이유 — 구체적으로 무슨 일이 벌어지는가**
>
> "오차가 조금 생긴다"는 말로는 위험이 전달되지 않는다. 실제로 벌어지는 일은 세 가지다.
>
> **1. 합계가 맞지 않는다.**
>
> ```csharp
> double total = 0;
> for (int i = 0; i < 10; i++) total += 0.1;
> Console.WriteLine (total == 1.0);      // False
> Console.WriteLine (total);             // 0.9999999999999999
> ```
>
> 100원짜리 10개를 담았는데 합계가 999.9999...원이다. 이것을 화면에 반올림해 표시하면 1,000원으로 보이지만, `total == 1000` 검사는 실패한다. 장바구니 합계와 결제 금액이 어긋나는 버그가 여기서 나온다.
>
> **2. 반올림이 표시 계층으로 밀려난다.**
>
> 오차를 숨기려고 출력할 때만 `ToString("N2")`로 반올림하기 시작하면, **저장된 값과 보이는 값이 달라진다.** 나중에 그 값들을 다시 더하면 화면의 숫자와 합계가 안 맞는다. 회계 시스템에서 이것은 치명적이다.
>
> **3. 세율 곱셈에서 1원이 어긋난다.** `1234.0 * 0.1`은 `123.4`가 아니라 `123.4000000000000...`이다. 값 하나로는 티가 안 나지만 수백만 건에 누적되면 총계가 몇 만 원까지 벌어지고, 감사에서 이 차이를 설명할 방법이 없다.
>
> 규칙은 절대적이다. **돈은 `decimal`이다.** 데이터베이스 컬럼도 `float`/`real`이 아니라 `decimal`/`numeric`이어야 한다.

> **💡 `decimal`이 느리다는 걱정은 대개 기우다**
>
> `decimal` 덧셈은 나노초 단위이고, 같은 트랜잭션에서 데이터베이스 왕복은 밀리초 단위다. **10만 배 차이나는 비용 옆에 붙은 10배 차이는 보이지 않는다.**
>
> `decimal`의 성능이 실제로 문제가 되는 경우는 하나뿐이다 — **수천만 건 이상을 메모리에서 반복 계산하는 배치**. 그때조차 답은 `double`로 바꾸는 것이 아니라, 금액을 최소 단위 정수(`long`)로 다루는 정수 산술로 바꾸는 것이다.

## 7.8 실수 반올림 오차의 원리

### 왜 0.1을 정확히 저장할 수 없는가

`float`과 `double`은 내부적으로 2진법으로 수를 표현한다. 그래서 **2진법으로 유한하게 쓸 수 있는 수만 정확히 담긴다.**

10진법에서 1/3을 유한 소수로 쓸 수 없듯이(0.333...), 2진법에서 1/10은 유한 소수로 쓸 수 없다. 10 = 2 × 5인데, 2진법은 5로 나눈 몫을 유한하게 표현하지 못하기 때문이다.

먼저 표현할 수 **있는** 수를 보자. 12.75는 2진법으로 정확하다.

```text
   12.75  =  8 + 4 + 0.5 + 0.25

    8     4     2     1     .    1/2   1/4   1/8   1/16
    1     1     0     0     .     1     1     0     0
   ─────────────────────────    ──────────────────────
        1100                 .        1100

   → 1100.1100 (2진)
```

이제 0.1을 시도해보자.

```text
   0.1 (10진)을 2진 소수로

   0.1 × 2 = 0.2  → 0
   0.2 × 2 = 0.4  → 0
   0.4 × 2 = 0.8  → 0
   0.8 × 2 = 1.6  → 1   (0.6 남음)
   0.6 × 2 = 1.2  → 1   (0.2 남음)
   0.2 × 2 = 0.4  → 0   ← 여기서 위의 두 번째 줄로 되돌아온다
   ...

   → 0.0001100110011001100110011... (1100이 무한 반복)
```

무한히 반복된다. `double`은 유효 숫자 53비트에서 끊어야 하므로, 저장되는 것은 0.1이 **아니라** 0.1에 가장 가까운 표현 가능한 수다.

### 비트로 확인하기

`double` 0.1의 실제 비트 패턴은 `0x3FB999999999999A`다. 분해하면 이렇다.

```text
0x3FB999999999999A

부호(1) : 0                          → 양수
지수(11): 0011 1111 1011 = 0x3FB = 1019
          1019 - 1023(편향) = -4     → 2^-4
가수(52): 1001 1001 ... 1001 1010    → 0x999999999999A

값 = 1.6000000000000000888178419700125... × 2^-4
   = 0.1000000000000000055511151231257827021181583404541015625
```

마지막 줄이 `double` 변수에 실제로 들어 있는 값이다. `Console.WriteLine(0.1)`이 `0.1`을 출력하는 것은, .NET의 기본 서식이 **원래 리터럴로 왕복할 수 있는 가장 짧은 표현**을 고르기 때문이지 값이 정확해서가 아니다.

같은 방식으로 0.2와 0.3도 보자.

| 리터럴 | 저장된 비트 (`double`) | 실제 값 |
|---|---|---|
| `0.1` | `3FB999999999999A` | 0.1000000000000000055511151231257827... |
| `0.2` | `3FC999999999999A` | 0.2000000000000000111022302462515654... |
| `0.3` | `3FD3333333333333` | 0.2999999999999999888977697537484346... |
| `0.1 + 0.2` | `3FD3333333333334` | 0.3000000000000000444089209850062616... |

**`0.1 + 0.2`와 `0.3`의 비트는 마지막 한 자리가 다르다** — `...3333`과 `...3334`. 딱 1비트 차이다. 그러나 `==`는 비트를 비교하므로 결과는 `false`다.

```csharp
double a = 0.1;
double b = 0.2;
Console.WriteLine (a + b == 0.3);   // False
Console.WriteLine (a + b);          // 0.30000000000000004
```

왜 이런 방향으로 어긋나는지도 표에서 읽힌다. 저장된 `0.1`과 `0.2`는 둘 다 **참값보다 약간 크고**, 저장된 `0.3`은 참값보다 **약간 작다**. 그래서 합이 `0.3`을 넘어선다.

> **⚠️ `float`으로 바꾸면 "고쳐진 것처럼" 보인다**
>
> ```csharp
> float a = 0.1F;
> float b = 0.2F;
> Console.WriteLine (a + b == 0.3F);   // True (!)
> ```
>
> `float`은 `double`보다 **덜 정확해서** 우연히 두 값이 같은 비트가 되었다. 이 결과를 보고 "`float`을 쓰면 되는구나"라고 결론 내리면 최악의 선택이다. 다른 값 조합에서는 `float`이 훨씬 빨리 틀린다.
>
> ```csharp
> float x = 0.1f;
> Console.WriteLine (x + x + x + x + x + x + x + x + x + x);   // 1.0000001
> ```
>
> `double`로 같은 계산을 하면 `0.9999999999999999`가 나온다. 오차의 방향과 크기가 정밀도에 따라 제각각이라는 것이 진짜 교훈이다. **부동소수점 등호 비교는 우연히 맞을 수도, 우연히 틀릴 수도 있다.**

### 누적 오차

한 번의 오차는 작지만 반복하면 쌓인다.

```csharp
decimal m = 1M / 6M;     // 0.1666666666666666666666666667M
double  d = 1.0 / 6.0;   // 0.16666666666666666

decimal notQuiteWholeM = m + m + m + m + m + m;   // 1.0000000000000000000000000002M
double  notQuiteWholeD = d + d + d + d + d + d;   // 0.99999999999999989

Console.WriteLine (notQuiteWholeM == 1M);    // False
Console.WriteLine (notQuiteWholeD <  1.0);   // True
```

`decimal`도 1/6은 정확히 담지 못하므로 같은 문제를 겪는다. 다만 오차의 크기가 훨씬 작고(28자리 vs 16자리), 오차가 생기는 조건이 예측 가능하다(10진 순환소수일 때만).

주목할 점은 오차의 **방향**이다. `decimal`은 위로 넘쳤고 `double`은 아래로 모자랐다. 반올림 오차의 부호는 값에 따라 달라지므로 "항상 큰 쪽으로 여유를 두면 된다" 같은 대처는 통하지 않는다.

### 그럼 어떻게 비교하는가

부동소수점을 비교하는 방법은 세 가지다.

**1. 비교하지 않는다.** 가장 좋은 답이다. `double`은 크기 비교(`<`, `>`)에만 쓰고 등호 비교는 하지 않는다.

**2. 절대 허용 오차.** 값의 크기 범위를 알고 있을 때만 유효하다.

```csharp
static bool NearlyEqual (double a, double b, double tolerance)
    => Math.Abs (a - b) <= tolerance;

Console.WriteLine (NearlyEqual (0.1 + 0.2, 0.3, 1e-9));   // True
```

`tolerance`는 도메인이 정한다. 화면 좌표라면 `0.5`(반 픽셀)일 수 있고, 물리 시뮬레이션이라면 훨씬 작을 수 있다. **`double.Epsilon`을 쓰지 마라** — 7.6절의 ⚠️를 다시 보라.

**3. 상대 허용 오차.** 값의 크기가 넓게 변할 때 쓴다. 차이를 두 값 중 큰 쪽의 절댓값으로 나눠 비교한다 — `Math.Abs(a - b) <= Math.Max(Math.Abs(a), Math.Abs(b)) * 1e-9`. 두 값 모두 0에 아주 가까울 때는 상대 오차가 무의미해지므로, 실무 구현은 절대 오차와 상대 오차를 함께 쓴다.

> **⚠️ 이 함수는 동등성 계약을 만족하지 않는다**
>
> `NearlyEqual`은 **추이적(transitive)이지 않다.** `a ≈ b`이고 `b ≈ c`여도 `a ≈ c`가 아닐 수 있다. 허용 오차가 0.1일 때 `1.0 ≈ 1.09`, `1.09 ≈ 1.18`이지만 `1.0`과 `1.18`은 아니다.
>
> 따라서 이 함수를 `Equals` 재정의나 `IEqualityComparer<T>` 구현에 넣으면 안 된다. `Dictionary`와 `HashSet`은 동등성이 추이적이라고 가정하고 만들어져 있다(25.4절). 근사 비교는 **테스트 코드와 검증 로직에서만** 쓴다.

### `Math.Round`와 은행가 반올림

C#의 기본 반올림 규칙은 초등학교에서 배운 "5 이상은 올림"이 아니다.

```csharp
Console.WriteLine (Math.Round (9.5));    // 10
Console.WriteLine (Math.Round (10.5));   // 10   ← 11이 아니다
Console.WriteLine (Math.Round (11.5));   // 12
Console.WriteLine (Math.Round (12.5));   // 12   ← 13이 아니다
```

규칙은 이렇다.

- 소수부가 정확히 0.5 **미만**이면 0 방향으로.
- 소수부가 정확히 0.5 **초과**면 0에서 먼 방향으로.
- 소수부가 정확히 0.5**이면 결과가 짝수가 되는 쪽으로.**

이것을 **은행가 반올림**(banker's rounding) 또는 **짝수 반올림**(round half to even)이라고 한다. 항상 올림하면 통계적으로 값이 조금씩 커지는 편향이 생기는데, 짝수 쪽으로 번갈아 반올림하면 그 편향이 상쇄된다. 많은 수를 합산하는 회계·통계에서 표준이다.

`Convert.ToInt32`도 같은 규칙을 쓴다. 원천 도서의 표를 재현하면 이렇다.

| 값 | `Convert.ToInt32` | 값 | `Convert.ToInt32` | 값 | `Convert.ToInt32` |
|---|---|---|---|---|---|
| 9.49 | 9 | 9.5 | 10 | 9.51 | 10 |
| 10.49 | 10 | 10.5 | 10 | 10.51 | 11 |
| 11.49 | 11 | 11.5 | 12 | 11.51 | 12 |
| 12.49 | 12 | 12.5 | 12 | 12.51 | 13 |
| −12.49 | −12 | −12.5 | −12 | −12.51 | −13 |
| −11.49 | −11 | −11.5 | −12 | −11.51 | −12 |
| −10.49 | −10 | −10.5 | −10 | −10.51 | −11 |
| −9.49 | −9 | −9.5 | −10 | −9.51 | −10 |

9.5 → 10, 10.5 → 10, 11.5 → 12, 12.5 → 12. 중간값에서 짝수로 붙는 패턴이 보인다. 음수도 대칭적으로 같다.

> **⚠️ 자바스크립트·파이썬·SQL과 반올림 결과가 다르다**
>
> 자바스크립트의 `Math.round(10.5)`는 `11`이다(양의 무한대 방향). C#의 `Math.Round(10.5)`는 `10`이다. 파이썬 3의 `round(10.5)`는 C#과 같은 `10`이지만 파이썬 2는 `11`이었고, SQL Server의 `ROUND`는 0에서 먼 방향이다.
>
> **프런트엔드와 백엔드가 같은 값을 서로 다르게 반올림하면 화면의 합계와 서버의 합계가 어긋난다.** 청구서 한 줄이 1원 다르고, 그 원인을 찾는 데 며칠이 걸린다.
>
> 대책은 두 가지다. (a) 반올림을 한 곳에서만 하고 나머지 계층은 그 결과를 받아쓴다. (b) 시스템 전체가 쓸 반올림 모드를 명시적으로 정하고, 모든 호출에 `MidpointRounding`을 인자로 넘긴다. 절대로 기본값에 기대지 마라.

### `MidpointRounding`으로 규칙 바꾸기

중간값 처리 방식은 `MidpointRounding` 열거형으로 지정한다.

| 값 | 의미 | `Math.Round(10.5, 0, mode)` | `Math.Round(-10.5, 0, mode)` |
|---|---|---|---|
| `ToEven` (기본) | 짝수 쪽으로 | `10` | `-10` |
| `AwayFromZero` | 0에서 먼 쪽으로 | `11` | `-11` |
| `ToZero` | 0 쪽으로 (절삭) | `10` | `-10` |
| `ToPositiveInfinity` | 위로 (ceiling) | `11` | `-10` |
| `ToNegativeInfinity` | 아래로 (floor) | `10` | `-11` |

`ToZero`, `ToPositiveInfinity`, `ToNegativeInfinity`는 뒤에 추가된 값이다. 이름이 `Up`/`Down`이 아니라 방향을 명시하는 것에 주목하라. 음수가 섞이면 "올림"과 "내림"이라는 말이 모호해지기 때문이다.

```csharp
double[] values = { 9.49, 9.5, 9.51, 10.49, 10.5, 10.51 };

foreach (double n in values)
    Console.WriteLine (
        $"{n} → " + Math.Round (value: n, digits: 0,
                                mode: MidpointRounding.AwayFromZero));

// 9.49 → 9      9.5 → 10      9.51 → 10
// 10.49 → 10    10.5 → 11     10.51 → 11
```

`digits` 인자로 소수 몇째 자리에서 반올림할지 지정한다.

```csharp
Console.WriteLine (Math.Round (3.14159, 2));   // 3.14
Console.WriteLine (Math.Round (2.5m, 0, MidpointRounding.AwayFromZero));   // 3
```

`Math.Round`에는 `double` 오버로드와 `decimal` 오버로드가 모두 있다. **금액을 반올림한다면 반드시 `decimal` 오버로드를 써라.** `double`로 반올림하면 중간값 판정 자체가 부정확해진다 — `2.675`가 실제로는 2.67499999...로 저장되어 있어 "정확히 중간값"으로 인식되지 않는 일이 생긴다.

### 캐스트 · `Convert` · `Math` 세 가지 길

혼동하기 쉬운 세 가지를 한 표로 정리한다.

| 방법 | 소수부 처리 | 범위 초과 시 |
|---|---|---|
| `(int) x` | 0 방향 절삭 | `unchecked`에서 결과 미지정, `checked`에서 `OverflowException` |
| `Convert.ToInt32 (x)` | 은행가 반올림 | `OverflowException` |
| `Math.Round (x)` | 은행가 반올림 (모드 지정 가능) | 결과가 여전히 `double`. 캐스트가 별도로 필요 |
| `Math.Floor (x)` | 음의 무한대 방향 | 결과가 `double` |
| `Math.Ceiling (x)` | 양의 무한대 방향 | 결과가 `double` |
| `Math.Truncate (x)` | 0 방향 절삭 | 결과가 `double` |

핵심 차이 두 개다. **캐스트는 자르고, `Convert`는 반올림한다.** 그리고 **캐스트는 오버플로를 허용하지만 `Convert`는 예외를 던진다.**

```csharp
double g = 9.8;
Console.WriteLine ((int) g);              // 9
Console.WriteLine (Convert.ToInt32 (g));  // 10
```

> **💡 반올림 정책을 코드 한 곳에 못 박아라**
>
> 금액을 다루는 프로젝트라면 반올림 헬퍼를 하나 만들고 그것만 쓰게 하라.
>
> ```csharp
> public static class Money
> {
>     // 이 시스템의 반올림 정책: 원 단위, 0에서 먼 쪽
>     public static decimal Round (decimal amount)
>         => Math.Round (amount, 0, MidpointRounding.AwayFromZero);
>
>     // 정책이 다른 자리는 별도 메서드로 이름을 붙인다
>     public static decimal RoundVat (decimal amount) => Math.Floor (amount);
> }
> ```
>
> `Math.Round`를 코드베이스 여기저기서 직접 호출하는 순간, 어느 호출이 어떤 모드를 쓰는지 아무도 모르게 된다. 검색으로 찾을 수 있는 지점을 하나로 만드는 것이 유일한 방어다.

## 7.9 `checked` / `unchecked`와 오버플로 검사

### 기본값은 왜 `unchecked`인가

7.4절에서 본 대로 정수 오버플로는 기본적으로 조용히 순환한다. 이 선택에는 두 가지 이유가 있다.

**첫째, 성능이다.** 검사를 켜면 모든 산술 연산에 조건 분기가 하나씩 붙는다. C#이 설계될 때 이 비용은 지금보다 훨씬 컸고, 시스템 프로그래밍 언어로서 C/C++와 경쟁하려면 기본이 빠른 쪽이어야 했다.

**둘째, 순환 동작에 의존하는 코드가 있다.** 해시 함수, 난수 생성기, 체크섬, 암호 알고리즘은 의도적으로 오버플로를 이용한다. 예를 들어 문자열 해시를 계산하는 전형적인 루프는 곱셈이 계속 넘치는 것을 전제로 한다.

```csharp
int hash = 17;
foreach (char c in text)
    hash = hash * 31 + c;    // 곧 int 범위를 넘고, 그래도 된다
```

이런 코드에 예외를 던지면 쓸모가 없어진다.

> **📌 오버플로가 기본으로 검사되는 언어들**
>
> 모든 언어가 같은 선택을 하지는 않았다. Swift는 정수 오버플로에서 기본적으로 프로그램을 중단시키고, 순환을 원하면 `&+` 같은 전용 연산자를 써야 한다. Rust는 디버그 빌드에서 패닉을 내고 릴리스 빌드에서는 순환한다(그리고 `wrapping_add` 같은 명시적 메서드를 제공한다).
>
> C#은 두 극단 사이에 있다 — 기본은 조용하지만 `checked`로 켤 수 있고, 프로젝트 전체에도 켤 수 있다. 어느 쪽이 옳은가는 논쟁거리지만, 적어도 **선택지가 있다는 사실을 아는 것**이 중요하다. 이 절이 그 이야기다.

### `checked` 연산자와 `checked` 블록

`checked`는 식 하나를 감싸거나 문 블록을 감쌀 수 있다.

```csharp
int a = 1000000;
int b = 1000000;

int c = checked (a * b);    // 식 하나만 검사

checked
{
    // 이 블록 안의 모든 식이 검사된다
    c = a * b;
}
```

`checked`가 영향을 주는 연산은 정해져 있다.

| 영향받음 | 영향 없음 |
|---|---|
| `++`, `--` | 비트 연산자 `&`, `\|`, `^`, `~` |
| 이항 `+`, `-`, `*`, `/` | 시프트 `<<`, `>>`, `>>>` |
| 단항 `-` | `double`/`float` 연산 (∞로 갈 뿐) |
| 정수 타입 사이의 명시적 변환 | `decimal` 연산 (항상 검사됨) |
| 부동소수점 → 정수 명시적 변환 | 비교 연산자 |

`unchecked`는 반대 방향으로 같은 문법을 쓴다.

```csharp
int x = int.MaxValue;
int y = unchecked (x + 1);
unchecked { int z = x + 1; }
```

### 상수 식은 항상 검사된다

프로젝트 설정과 무관하게, **컴파일 시점에 계산되는 식은 항상 오버플로 검사를 받는다.** `unchecked`를 명시적으로 붙이지 않는 한 그렇다.

```csharp
// int x = int.MaxValue + 1;              // 컴파일 오류 CS0220
int y = unchecked (int.MaxValue + 1);     // OK. -2147483648
```

오류 메시지는 이렇다.

```text
error CS0220: The operation overflows at compile time in checked mode
```

이 규칙이 있는 이유는 명확하다. 상수 식의 오버플로는 **100% 프로그래머의 실수**다. 실행 시점 값에 따라 달라지는 것이 아니라 소스에 그대로 적혀 있는 것이므로, 컴파일러가 잡아주지 않을 이유가 없다.

7.1절에서 본 `unchecked((int)0xF0000000)` 관용구가 여기서 나온다. 최상위 비트가 켜진 32비트 마스크를 `int` 상수로 쓰려면 `unchecked`가 필요하다.

### 컴파일 결과 — `add` vs `add.ovf`

`checked`는 순전히 컴파일 타임 개념이다. 컴파일러가 다른 IL 옵코드를 고를 뿐이다.

```csharp
int a = 1, b = 2;
int c = a + b;
int d = checked (a + b);
```

```il
ldloc.0
ldloc.1
add            // 검사 없음
stloc.2

ldloc.0
ldloc.1
add.ovf        // 오버플로 시 System.OverflowException
stloc.3
```

| 연산 | unchecked IL | checked IL (부호 있음) | checked IL (부호 없음) |
|---|---|---|---|
| 덧셈 | `add` | `add.ovf` | `add.ovf.un` |
| 뺄셈 | `sub` | `sub.ovf` | `sub.ovf.un` |
| 곱셈 | `mul` | `mul.ovf` | `mul.ovf.un` |
| `int`로 변환 | `conv.i4` | `conv.ovf.i4` | `conv.ovf.i4.un` |
| `byte`로 변환 | `conv.u1` | `conv.ovf.u1` | `conv.ovf.u1.un` |

나눗셈에는 `div.ovf`가 없다. 나눗셈의 유일한 오버플로 조합인 `int.MinValue / -1`은 7.4절에서 본 대로 `div` 옵코드 자체가 `OverflowException`을 내도록 정의되어 있기 때문이다.

### 런타임 동작과 성능

`add.ovf`는 JIT에서 `add` 명령 뒤에 오버플로 플래그(`OF`) 검사 분기가 붙은 형태로 나온다.

```asm
; unchecked: int c = a + b;
add     eax, ecx

; checked: int d = checked(a + b);
add     eax, ecx
jo      SHORT G_M000_IG04   ; 오버플로 플래그가 서면 예외를 던지러 간다
G_M000_IG04:
call    CORINFO_HELP_OVERFLOW
```

비용은 두 가지다.

1. **분기 명령 하나.** 오버플로가 실제로 일어나지 않으면 분기 예측이 거의 100% 맞으므로 직접 비용은 아주 작다.
2. **최적화 방해.** 이쪽이 더 크다. `jo` 분기가 있으면 JIT이 루프를 벡터화(SIMD)하거나 명령을 재배치하기 어려워진다. 핫 루프에서 `checked`를 켜면 몇 퍼센트에서 수십 퍼센트까지 느려질 수 있다.

> **⚠️ `checked`는 어휘적(lexical)이지 동적(dynamic)이 아니다**
>
> 가장 자주 오해되는 지점이다.
>
> ```csharp
> static int Add (int x, int y) => x + y;    // 이 메서드는 unchecked로 컴파일된다
>
> checked
> {
>     int r = Add (int.MaxValue, 1);   // 예외가 던져지지 않는다!
>     Console.WriteLine (r);           // -2147483648
> }
> ```
>
> `checked` 블록은 **그 블록 안에 문자로 적힌 연산**에만 영향을 준다. 호출된 메서드 안의 연산은 그 메서드가 컴파일될 때의 컨텍스트를 따른다. `Add`는 별도로 컴파일되었고 그때는 `unchecked`였다.
>
> 이유는 IL을 보면 자명하다. `checked`는 옵코드 선택이고, `Add`의 IL은 이미 `add`로 굳어져 있다. 호출 지점에서 바꿀 방법이 없다.
>
> 그래서 라이브러리 코드에서 오버플로 안전을 보장하려면 **그 라이브러리 자체를 `checked`로 빌드하거나 연산마다 `checked`를 써야 한다.** 소비자가 `checked` 블록으로 감싸는 것으로는 아무것도 달라지지 않는다.

### 프로젝트 전체에 켜기

`checked`를 코드마다 쓰는 것이 번거롭다면 프로젝트 파일에서 한 번에 켠다.

```xml
<PropertyGroup>
  <CheckForOverflowUnderflow>true</CheckForOverflowUnderflow>
</PropertyGroup>
```

Visual Studio에서는 프로젝트 속성 페이지의 Build → General에서 "Check for arithmetic overflow/underflow" 체크박스에 해당한다. 빌드 구성(Debug/Release)별로 따로 설정할 수 있다.

이 설정을 켜면 `unchecked` 키워드가 반대 역할을 한다 — 특정 블록만 검사에서 빼는 도구가 된다.

```csharp
// 프로젝트 전체가 checked인 상태에서
unchecked
{
    int hash = 17;
    foreach (char c in text) hash = hash * 31 + c;   // 순환이 정상 동작인 곳
}
```

> **💡 Debug는 checked, Release는 unchecked — 좋은 절충인가**
>
> 원천 도서가 제안하는 방식이다. 디버그 빌드에서 오버플로를 전부 잡아낸 뒤 릴리스에서 꺼서 성능을 되찾는다는 발상이다. 합리적으로 들리지만 함정이 있다. **디버그 빌드에서 재현되지 않는 입력이 프로덕션에서만 들어온다면, 검사는 꺼져 있는 곳에서만 오버플로가 일어난다.** 정확히 필요할 때 없는 안전장치다.
>
> 저자의 권고는 이렇다.
>
> - **금융·집계·수량 계산 코드는 Release에서도 `checked`로 빌드하라.** 잘못된 숫자를 조용히 저장하는 것보다 예외를 던지고 멈추는 것이 낫다.
> - **핫 루프, 해시, 시리얼라이저 등 성능이 지배적인 코드만 `unchecked` 블록으로 명시적으로 뚫어라.** 그 자리에 왜 순환이 안전한지 주석을 남겨라.
> - 전체를 `unchecked`로 두고 중요한 곳만 `checked`로 감싸는 것보다, 전체를 `checked`로 두고 예외를 뚫는 편이 실수의 방향이 안전하다.

### `checked` 연산자 오버로딩 ※C# 11

C# 11부터 사용자 정의 타입도 `checked` 컨텍스트에서 다르게 동작하는 연산자를 정의할 수 있다.

```csharp
public static Money operator + (Money a, Money b) => /* 순환 */;
public static Money operator checked + (Money a, Money b) => /* 예외 */;
```

`checked` 블록 안에서는 `operator checked +`가, 밖에서는 일반 `operator +`가 호출된다. 문법과 규칙은 22.1절에서 다룬다.

## 7.10 `bool` 변환, 동등·비교 연산자, 조건 연산자

### `bool` 타입

C#의 `bool`은 `System.Boolean`의 별칭이고, `true` 또는 `false` 두 리터럴 중 하나만 담는다.

논리값 하나는 이론상 1비트면 충분하다. 그런데 **런타임은 1바이트를 쓴다.** 런타임과 프로세서가 효율적으로 다룰 수 있는 최소 단위가 바이트이기 때문이다. 배열에서 이 낭비가 커진다 — `bool[1_000_000]`은 1MB다. 정말 비트 단위로 저장해야 한다면 `System.Collections` 네임스페이스의 `BitArray` 클래스가 논리값당 1비트만 쓰도록 설계되어 있다.

`Boolean`에는 `MinValue`/`MaxValue`가 없다. 대신 `bool.TrueString`/`bool.FalseString`이 문자열 `"True"`/`"False"`를 준다.

### `bool` 변환 — 없다

**`bool`과 숫자 타입 사이에는 어떤 변환도 없다.** 암시적이든 명시적이든, 어느 방향이든 마찬가지다.

```csharp
bool b = true;
// int i = (int) b;      // 컴파일 오류
// bool c = (bool) 1;    // 컴파일 오류
// if (1) { }            // 컴파일 오류: int는 bool이 아니다
```

C/C++에서 넘어온 사람이 가장 먼저 부딪히는 벽이다. C에서 `if (n)`은 "`n`이 0이 아니면"이지만 C#에서는 컴파일되지 않는다. 명시적으로 써야 한다.

```csharp
if (n != 0) { }
```

> **📌 이 제약이 막아주는 고전적 버그**
>
> C에서 가장 유명한 오타 버그가 `if (x = 5)`다. 비교(`==`)를 대입(`=`)으로 잘못 쓴 것인데, 대입 식의 값 5가 참으로 평가되어 조건이 항상 성립한다.
>
> C#에서는 `if (x = 5)`가 컴파일되지 않는다. 대입 식의 타입이 `int`이고 `int`는 `bool`로 변환되지 않기 때문이다. 언어 설계 결정 하나가 버그 종류 하나를 통째로 없앤 사례다.
>
> 다만 `bool` 변수에 대해서는 여전히 가능하다. `if (flag = true)`는 컴파일된다. 컴파일러가 경고를 주지만 오류는 아니다.

`bool`을 정수로 바꾸고 싶다면 조건 연산자나 `Convert`를 쓴다.

```csharp
int i = b ? 1 : 0;
int j = Convert.ToInt32 (b);      // true → 1, false → 0
```

### 동등 연산자

`==`와 `!=`는 어떤 타입에도 쓸 수 있고 항상 `bool`을 돌려준다.

값 타입의 동등성은 단순하다. 값이 같으면 같다.

```csharp
int x = 1, y = 2, z = 1;
Console.WriteLine (x == y);   // False
Console.WriteLine (x == z);   // True
```

참조 타입은 기본적으로 **참조 동등성**이다. 내용이 같아도 다른 객체면 다르다.

```csharp
public class Dude
{
    public string Name;
    public Dude (string n) { Name = n; }
}

Dude d1 = new Dude ("John");
Dude d2 = new Dude ("John");
Dude d3 = d1;
Console.WriteLine (d1 == d2);   // False   서로 다른 객체다
Console.WriteLine (d1 == d3);   // True    같은 객체를 가리킨다
```

이 기본 동작을 바꾸는 방법 — `Equals` 재정의, `==` 오버로딩, `IEquatable<T>` 구현, `record` 사용 — 은 22.3절과 25장에서 다룬다. `string`은 참조 타입이면서도 값 동등성을 갖는데, 그 이유는 8장과 25.2절에서 설명한다.

### 비교 연산자

`<`, `>`, `<=`, `>=`는 모든 숫자 타입에 정의되어 있다. 실수에 쓸 때는 7.8절의 경고를 기억하라.

열거형에도 쓸 수 있으며, 이때는 기저 정수 값을 비교한다. 자세히는 20장이다.

사용자 정의 타입에 `<`를 붙이려면 연산자를 오버로딩하거나 `IComparable<T>`를 구현한다. 두 접근의 차이는 25.6절이다.

### 조건 연산자 `&&`와 `||` — 단축 평가

`&&`는 논리곱, `||`는 논리합, `!`은 부정이다.

```csharp
static bool UseUmbrella (bool rainy, bool sunny, bool windy)
{
    return !windy && (rainy || sunny);
}
```

비가 오거나 해가 나면 우산을 쓰되, 바람이 불면 쓰지 않는다는 규칙이다.

`&&`와 `||`는 가능하면 **단축 평가**(short-circuit)한다. `!windy`가 `false`면 `(rainy || sunny)`는 아예 평가되지 않는다.

단축 평가는 편의 기능이 아니라 **필수 기능**이다. 다음 코드가 `NullReferenceException` 없이 동작하는 유일한 이유가 그것이다.

```csharp
if (sb != null && sb.Length > 0) { /* ... */ }
```

`sb`가 `null`이면 `sb != null`이 `false`이고, `sb.Length`는 실행되지 않는다. 순서를 뒤집으면 즉시 터진다.

### `&`와 `|` — 단축 평가하지 않는 논리 연산

`&`와 `|`도 논리곱·논리합을 계산한다. 차이는 **양쪽을 항상 평가한다**는 것이다.

```csharp
return !windy & (rainy | sunny);   // 동작은 같지만 단축 평가가 없다
```

C/C++ 경험자에게 이것은 놀라운 부분이다. **C#에서 `bool`에 적용된 `&`와 `|`는 비트 연산이 아니라 논리 연산이다.** 비트 연산이 되는 것은 숫자에 적용할 때뿐이다.

| 연산자 | `bool` 피연산자 | 숫자 피연산자 |
|---|---|---|
| `&` | 논리곱 (단축 평가 없음) | 비트 AND |
| `\|` | 논리합 (단축 평가 없음) | 비트 OR |
| `^` | 배타적 논리합 (XOR) | 비트 XOR |
| `&&` | 논리곱 (단축 평가) | 사용 불가 |
| `\|\|` | 논리합 (단축 평가) | 사용 불가 |
| `!` | 부정 | 사용 불가 |
| `~` | 사용 불가 | 비트 보수 |

> **⚠️ `&`와 `&&`를 혼동하면 조용히 성능이 죽거나 시끄럽게 터진다**
>
> ```csharp
> // 오타 하나로 NullReferenceException
> if (sb != null & sb.Length > 0) { }    // & 는 오른쪽도 평가한다
>
> // 오타 하나로 성능 저하
> if (cache.TryGetLocal (key) | LoadFromNetwork (key)) { }   // 항상 네트워크를 친다
> ```
>
> 컴파일러는 두 코드 모두 받아들인다. 타입이 맞기 때문이다. **`bool`에 `&`나 `|`를 쓴 코드를 보면 의도인지 오타인지 반드시 확인하라.** 의도라면 주석을 남겨야 한다.

`bool?`(널 가능 `bool`)에 대해서는 `&`와 `|`가 3값 논리로 확장되며, 여기서는 `&`가 `&&`로 대체될 수 없다. 21.5절에서 다룬다.

### 컴파일 결과 — 단축 평가는 분기다

```csharp
static bool And (bool a, bool b) => a && b;
static bool AndNoShort (bool a, bool b) => a & b;
```

```il
// a && b
ldarg.0
brfalse.s  IL_0006     // a가 false면 b를 평가하지 않고 점프
ldarg.1
ret
IL_0006:
ldc.i4.0
ret

// a & b
ldarg.0
ldarg.1
and                    // 분기 없이 한 명령
ret
```

`&&`는 분기를 만들고 `&`는 만들지 않는다. 그래서 **아주 예외적으로 `&`가 빠를 수 있다** — 오른쪽 피연산자가 극히 싸고 분기 예측이 잘 안 맞는 경우다. 이런 최적화는 측정 없이 적용하면 안 되고, 대부분의 코드에서는 `&&`가 옳다.

### 조건 연산자 (삼항 연산자)

피연산자를 세 개 받는 유일한 연산자라 흔히 삼항 연산자라고 부른다. 형태는 `q ? a : b`다.

```csharp
static int Max (int a, int b) => (a > b) ? a : b;
```

`q`가 `true`면 `a`가, 아니면 `b`가 평가된다. 선택되지 않은 쪽은 **평가되지 않는다** — `&&`처럼 단축 평가한다.

```csharp
int len = (s != null) ? s.Length : 0;    // s가 null이면 s.Length는 실행되지 않는다
```

조건 연산자는 **식**이므로 문(statement)이 올 수 없는 자리 — LINQ 쿼리 안, 필드 초기화, 표현식 본문 멤버 — 에 쓸 수 있다.

타입 결정 규칙에 주의할 점이 있다. `a`와 `b`의 타입이 다르면 컴파일러가 공통 타입을 찾는다.

```csharp
var v1 = flag ? 1 : 2.0;         // double (int → double 암시 변환)
// var v2 = flag ? 1 : "text";   // 컴파일 오류: 공통 타입이 없다
```

※C# 9부터는 대상 타입(target-typed) 조건 식이 지원되어, 두 분기의 공통 타입이 없어도 대입 대상 타입으로 변환될 수 있으면 컴파일된다.

```csharp
object o = flag ? 1 : "text";    // ※C# 9부터 OK
```

> **⚠️ 조건 연산자를 중첩하지 마라**
>
> ```csharp
> // 읽을 수 없다
> string grade = s >= 90 ? "A" : s >= 80 ? "B" : s >= 70 ? "C" : "F";
> ```
>
> 이 코드는 동작한다. `:`가 오른쪽 결합이므로 의도대로 해석된다. 그러나 조건이 네 개를 넘어가면 읽는 사람이 결합 방향을 머리로 계산해야 한다.
>
> 대안은 `switch` 식이다(11.3절).
>
> ```csharp
> string grade = s switch
> {
>     >= 90 => "A",
>     >= 80 => "B",
>     >= 70 => "C",
>     _     => "F"
> };
> ```
>
> 조건 연산자는 **분기가 정확히 둘일 때** 쓰는 도구다.

`??`와 `?.`는 이름이 비슷하지만 다른 연산자다. `null` 검사 전용이며 10.10절에서 다룬다.

## 7.11 네이티브 크기 정수 `nint` / `nuint`

### 무엇인가

`nint`와 `nuint`는 ※C# 9에서 도입된 정수 타입이다. 크기가 고정되어 있지 않고 **실행 중인 프로세스의 주소 공간에 맞춰진다** — 실무적으로는 32비트 또는 64비트다.

```csharp
nint x = 123, y = 234;
checked
{
    nint sum = x + y, product = x * y;
    Console.WriteLine (product);   // 28782
}
```

보통의 정수처럼 동작한다. 산술 연산이 전부 되고 오버플로 검사도 지원한다.

### 리터럴과 변환

32비트 정수 상수는 대입할 수 있지만, **64비트 정수 상수는 안 된다.** 32비트 플랫폼에서 실행 시점에 넘칠 수 있기 때문이다.

```csharp
nint a = 1000;              // OK
// nint b = 5_000_000_000;  // 컴파일 오류: 64비트 상수는 대입할 수 없다
```

다른 정수 타입과 주고받으려면 명시적 캐스트를 쓴다.

```csharp
int  i = 42;
nint n = (nint) i;
long l = (long) n;
```

### 언제 쓰는가

**메모리 주소나 오프셋을 포인터 없이 표현할 때** 쓴다. `nuint`는 메모리 블록의 길이를 표현하기에 자연스러운 타입이다. 포인터를 다룰 때는 효율 이득도 있다. C#에서 두 포인터를 빼면 결과가 항상 64비트 `long`인데 32비트 플랫폼에서는 비효율적이다. 포인터를 먼저 `nint`로 캐스트하면 뺄셈 결과도 `nint`가 되어 32비트 플랫폼에서 32비트로 처리된다.

```csharp
unsafe nint AddressDif (char* x, char* y) => (nint) x - (nint) y;
```

포인터와 `unsafe` 문맥은 60.7절에서 다룬다.

> **📌 실제 사용 사례**
>
> `nint`/`nuint`가 포인터와 함께 쓰이는 대표적인 예가 BCL의 `Buffer.MemoryCopy` 구현이다. .NET 소스의 `Buffer.cs`에서 볼 수 있고, ILSpy로 디컴파일해도 확인할 수 있다.

### 런타임 표현 — 대상 프레임워크에 따라 다르다

여기가 이 타입의 미묘한 부분이다.

**.NET 7 이상을 대상으로 하는 프로젝트**에서 `nint`와 `nuint`는 `System.IntPtr`/`System.UIntPtr`의 **동의어**다. `int`가 `System.Int32`의 동의어인 것과 정확히 같은 관계다. .NET 7에서 `IntPtr`/`UIntPtr`이 완전한 산술 능력과 오버플로 검사를 갖도록 강화되었기 때문에 가능해진 일이다.

**.NET 6 이하(또는 .NET Standard)를 대상으로 하는 프로젝트**에서도 기저 런타임 타입은 여전히 `IntPtr`/`UIntPtr`이다. 다만 옛 `IntPtr`/`UIntPtr`에는 대부분의 산술 연산이 없으므로 **컴파일러가 그 빈틈을 메운다.** 그 결과 `nint`/`nuint`는 .NET 7 이상에서와 똑같이 동작한다(`checked` 연산 포함).

원천 도서의 비유가 정확하다 — `nint` 변수는 **특별한 모자를 쓴 `IntPtr`**이라고 생각하면 된다. 컴파일러는 그 모자를 보고 "현대적인 `IntPtr`로 취급해달라"는 뜻으로 읽는다. 그리고 `IntPtr`로 캐스트하는 순간 모자가 벗겨진다.

```csharp
nint x = 123;
Console.WriteLine (x * x);    // OK: 곱셈이 지원된다

IntPtr y = x;
// Console.WriteLine (y * y); // 컴파일 오류: 연산자 *가 지원되지 않는다
```

> **⚠️ .NET 7의 `IntPtr` 강화는 기술적으로 파괴적 변경이다**
>
> `IntPtr`/`UIntPtr`에 검사되는(checked) 산술 능력을 추가한 것은 엄밀히 말해 호환성을 깨는 변경이다. `IntPtr`이 `checked` 블록을 무시한다고 가정한 옛 코드가 있다면 동작이 달라질 수 있다.
>
> 다만 영향은 제한적이다. 그런 코드가 **단지 .NET 7 이상에서 실행되는 것만으로는 깨지지 않는다.** 프로젝트를 .NET 7 이상 대상으로 **다시 컴파일**해야 달라진다. 그래서 라이브러리 작성자는 .NET 7 이상을 명시적으로 겨냥하는 새 버전을 낼 때까지 이 문제를 걱정할 필요가 없다.

### 크기 확인하기

`nint`의 실제 크기는 `IntPtr.Size`(64비트 프로세스면 8)와 `Environment.Is64BitProcess`로 실행 시점에 확인할 수 있다.

> **💡 일반적인 코드에서는 쓰지 마라**
>
> `nint`/`nuint`는 상호운용과 저수준 메모리 조작을 위한 도구다. "플랫폼에 맞춰 자동으로 커지니 좋겠다"는 이유로 일반 비즈니스 로직에 쓰면 안 된다.
>
> 첫째, **크기가 플랫폼마다 다르다는 것은 오버플로 지점도 플랫폼마다 다르다는 뜻이다.** 64비트에서 통과한 테스트가 32비트에서 실패한다. 둘째, 직렬화·데이터베이스 매핑·API 계약에서 크기가 고정되지 않은 타입은 재앙이다.
>
> 일반 코드에는 `int`, 큰 값에는 `long`. 이 두 개면 충분하다.

## 이 장의 요약

- **리터럴에는 타입이 있고, 그 타입은 규칙으로 결정된다.** 소수점이나 `E`가 있으면 `double`, 아니면 `int` → `uint` → `long` → `ulong` 순으로 값이 들어가는 첫 타입이다. `F`와 `M` 접미사는 반드시 붙여야 하고 `D`·`U`·`L`은 대개 군더더기다. 밑줄과 `0b`/`0x` 접두사는 IL에 흔적을 남기지 않는 순수한 가독성 장치다.

- **암시적 변환은 "대상 타입이 원본의 모든 값을 표현할 수 있을 때"만 허용된다.** 실제 값이 범위 안에 있어도 타입이 그것을 보장하지 못하면 캐스트가 필요하다. 예외처럼 보이는 것은 정수 → 부동소수점 변환인데, 여기서 보장되는 것은 크기이지 정밀도가 아니다.

- **정수 나눗셈은 0 방향으로 절삭하고, 나머지의 부호는 피제수를 따른다.** `-7 / 2`는 `-3`이고 `-7 % 2`는 `-1`이다. `n % 2 == 1`로 홀수를 판정하면 음수에서 깨진다. `int.MinValue / -1`은 `unchecked`에서도 `OverflowException`을 던진다.

- **8비트·16비트 정수에는 산술 연산자가 없다.** 모든 연산이 `int`로 승격되므로 `short + short`의 결과는 `int`이고 다시 `short`에 담으려면 캐스트가 필요하다. 이것은 CLR 평가 스택이 32비트 미만을 담지 못하는 사실의 반영이며, 그 캐스트가 값을 조용히 망가뜨리는 자리다.

- **부동소수점은 2진 분수이므로 0.1을 정확히 담을 수 없다.** 저장된 `0.1`과 `0.2`는 참값보다 크고 저장된 `0.3`은 작아서, `0.1 + 0.2`의 비트가 `0.3`의 비트와 마지막 한 자리에서 어긋난다. `float`으로 바꾸면 통과하는 것은 정밀도가 낮아 우연히 같은 비트가 된 것이지 고쳐진 것이 아니다. **NaN은 자기 자신과도 같지 않고 순서 비교가 전부 `false`이며**, `double.Epsilon`은 비교 허용 오차가 아니라 표현 가능한 최소 양수다.

- **`double`은 밑수 2, `decimal`은 밑수 10이다.** `double`은 CPU 명령이고 `decimal`은 메서드 호출이라 약 10배 느리다. 그 대가로 `decimal`은 10진 리터럴을 정확히 표현하고 오버플로를 항상 검사한다. **돈은 `decimal`이다.**

- **C#의 기본 반올림은 은행가 반올림(짝수 반올림)이다.** `Math.Round(10.5)`는 `11`이 아니라 `10`이다. 다른 언어·데이터베이스와 규칙이 다르므로 계층 간 합계가 어긋날 수 있다. `MidpointRounding`으로 명시하고, 정책을 코드 한 곳에 못 박아라.

- **정수 오버플로는 기본적으로 조용히 순환한다.** 성능 때문이고, 해시·체크섬처럼 순환에 의존하는 코드가 있기 때문이다. `checked`로 켜면 `add.ovf` 계열 옵코드가 나오고, `<CheckForOverflowUnderflow>`로 프로젝트 전체에 적용할 수 있다. **`checked`는 어휘적이라 호출된 메서드 안까지 전파되지 않는다.**

- **`bool`은 숫자와 어떤 방향으로도 변환되지 않는다.** `if (n)`은 컴파일되지 않고, 그 덕분에 `if (x = 5)` 같은 고전적 버그가 언어 수준에서 사라졌다. `&&`/`||`는 단축 평가하고 `&`/`|`는 하지 않으며, `bool`에 적용된 `&`는 비트 연산이 아니라 논리 연산이다.

- **`nint`/`nuint`는 상호운용 도구이지 범용 정수 타입이 아니다.** 크기가 플랫폼마다 달라 오버플로 지점도 달라지므로, 일반 코드에는 `int`와 `long`을 쓴다.

## 연습 문제

1. **리터럴 타입 추론 확인하기.** `Console.WriteLine(1.0.GetType()); Console.WriteLine(0xF0000000.GetType()); Console.WriteLine(0x100000000.GetType());`를 실행해 각각 무엇이 나오는지 확인하라. 그다음 `int flags = -1; var r = flags & 0xF0000000;`을 써보고 `r`의 타입이 무엇인지 `r.GetType()`으로 확인하라. 왜 `int`가 아닌지 7.3절의 승격 표에서 근거를 찾아라.

2. **작은 정수의 오버플로 재현하기.** `static int Add(int x, int y) => x + y;`를 정의하고 `byte b1 = 100, b2 = 250; byte sum = (byte)Add(b1, b2);`를 실행해 출력을 확인하라. 값이 94가 나오는 이유를 2진수로 설명하라. 그다음 `checked((byte)Add(b1, b2))`로 바꿔 무엇이 달라지는지 보라.

3. **나머지의 부호 규칙 확인하기.** `7 % 3`, `-7 % 3`, `7 % -3`, `-7 % -3` 네 값을 출력하라. 이어서 `bool IsOdd(int n) => n % 2 == 1;`을 정의하고 `IsOdd(3)`과 `IsOdd(-3)`을 호출해 결과가 갈리는 것을 확인한 뒤, 음수에서도 옳게 동작하도록 고쳐라.

4. **비트로 확인하는 `0.1 + 0.2`.** `BitConverter.DoubleToInt64Bits(0.1 + 0.2).ToString("X16")`과 `BitConverter.DoubleToInt64Bits(0.3).ToString("X16")`을 출력해 두 비트 패턴을 나란히 비교하라. 차이가 몇 비트인지 세어보고, `Console.WriteLine((0.1 + 0.2).ToString("R"))`로 왕복 가능한 표현도 확인하라.

5. **`float`이 "고쳐주는" 착시 관찰하기.** `float a = 0.1F, b = 0.2F;`로 `a + b == 0.3F`를 확인하고, 같은 코드를 `double`로 바꿔 결과가 뒤집히는 것을 보라. 이어서 `float x = 0.1f;`를 열 번 더한 값과 `double d = 0.1;`을 열 번 더한 값을 각각 `"R"` 서식으로 출력해 오차의 방향이 다른 것을 확인하라.

6. **은행가 반올림 표 만들기.** `double[] values = { 9.5, 10.5, 11.5, 12.5, -9.5, -10.5, -11.5, -12.5 };`에 대해 `Convert.ToInt32`, `Math.Round(v)`, `Math.Round(v, 0, MidpointRounding.AwayFromZero)`, `(int)v` 네 가지 결과를 표로 출력하라. 어느 열과 어느 열이 같고 다른지 정리하라.

7. **`checked`가 전파되지 않는 것 확인하기.** `static int Add(int x, int y) => x + y;`를 정의하고 `checked { int r = Add(int.MaxValue, 1); Console.WriteLine(r); }`를 실행하라. 예외가 나지 않는 것을 확인한 뒤, `.csproj`에 `<CheckForOverflowUnderflow>true</CheckForOverflowUnderflow>`를 넣고 다시 실행해 결과가 달라지는지 보라. 이어서 `decimal`과 `double`로 각각 `0.1`을 100만 번 더한 최종값을 `"R"` 서식으로 출력하고, `Stopwatch`로 두 루프의 시간도 재라.
