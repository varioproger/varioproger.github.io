# 13장. 클래스와 캡슐화

> **이 장의 위치** — 6장부터 12장까지는 "이미 있는 타입으로 무엇을 하는가"였다. 이 장부터는 **타입을 직접 만든다.** Part III의 첫 장이며, 다루는 범위는 딱 하나다 — **클래스 하나를 어떻게 설계하고, 어떻게 초기화하는가.** 필드와 프로퍼티 중 무엇을 고를지, 생성자를 몇 개 두고 어떻게 연결할지, 객체가 만들어지는 동안 어떤 순서로 무엇이 실행되는지, 그리고 그 문법들이 IL에서 무엇으로 바뀌는지를 끝까지 판다.
>
> **선수 지식** — 6장(구문과 타입 기초), 특히 6.6절(사용자 정의 타입)과 6.9절(확정 할당과 기본값). 10장(변수, 매개변수, 식), 특히 10.2절(매개변수 전달)과 10.11절(`const`와 `readonly`). 11장(문과 제어 흐름). 12장(네임스페이스와 전처리기).
>
> **이 장에서 다루지 않는 것** — 접근 제한자 전체(`public` / `internal` / `protected` / `private` / `protected internal` / `private protected`)와 중첩 타입은 17장이다. 이 장은 `public`과 `private`만 쓰고 나머지는 17.1절로 넘긴다. 상속·`virtual`·`override`·`base`는 14장이며, 오버로드 해석에 상속이 개입할 때의 규칙은 14.8절, 생성자에서 가상 함수를 부르면 안 되는 이유는 14.10절이다. 구조체 고유의 생성 의미론은 16.3절, 레코드가 자동 생성하는 멤버는 19.3절, 연산자 함수는 22.1절이다. 파이널라이저는 **선언 문법만** 13.16절에서 다루고 실제 동작(F-reachable 큐, 부활, 비용)은 34.2절, 정리 패턴은 33.3절이다. 초기화 순서를 8단계로 쪼개 관용구 관점에서 다시 보는 것은 79.5절이다.

## 13.1 클래스 선언, 필드, 상수

### 클래스 선언의 해부

가장 단순한 클래스 선언은 이렇게 생겼다.

```csharp
class YourClassName
{
}
```

여기에 붙을 수 있는 것들은 위치가 정해져 있다.

```text
┌─ class 키워드 앞 ─────────────────────────────────────────┐
│  특성(attribute)과 클래스 한정자                            │
│  중첩되지 않은 클래스의 한정자:                              │
│    public  internal  abstract  sealed  static  unsafe       │
│    partial  file(※C# 11)                                    │
└──────────────────────────────────────────────────────────┘
                    class YourClassName
┌─ 클래스 이름 뒤 ──────────────────────────────────────────┐
│  제네릭 타입 매개변수와 제약, 기반 클래스, 인터페이스 목록      │
└──────────────────────────────────────────────────────────┘
┌─ 중괄호 안 ───────────────────────────────────────────────┐
│  클래스 멤버: 메서드, 프로퍼티, 인덱서, 이벤트, 필드,          │
│  생성자, 오버로드된 연산자, 중첩 타입, 파이널라이저            │
└──────────────────────────────────────────────────────────┘
```

이 장은 이 중에서 **필드·상수·메서드·생성자·프로퍼티·인덱서·파이널라이저**를 다룬다. 특성은 20.6절, 연산자 함수는 22.1절, 이벤트는 27장, 중첩 타입은 17.5절, 제네릭 타입 매개변수는 23장이다.

CLR 관점에서 멤버의 종류는 여덟 가지다. 이 분류를 알아 두면 리플렉션(57.5절)과 IL을 읽을 때 헤맬 일이 줄어든다.

| CLR 멤버 | C# 문법 | 인스턴스/타입 | 이 책에서 다루는 곳 |
|---|---|---|---|
| 상수(Constant) | `const` | 언제나 타입 | 13.1절 |
| 필드(Field) | 필드 선언 | 둘 다 | 13.1절, 13.11절 |
| 인스턴스 생성자 | `.ctor` | 인스턴스 | 13.3절 |
| 타입 생성자 | `.cctor` (`static` 생성자) | 타입 | 13.12절 |
| 메서드(Method) | 메서드 선언 | 둘 다 | 13.2절 |
| 프로퍼티(Property) | `get`/`set` 블록 | 둘 다 | 13.8절, 13.9절 |
| 이벤트(Event) | `event` | 둘 다 | 27장 |
| 타입(Type) | 중첩 타입 | 타입 | 17.5절 |

> **📌 연산자와 변환 연산자는 CLS의 일부가 아니다**
>
> 위 표에 연산자 오버로드와 변환 연산자가 없는 이유는, 그것들이 CLR 수준에서는 그냥 **특별한 이름을 가진 정적 메서드**(`op_Addition`, `op_Implicit`)이기 때문이다. 모든 .NET 언어가 연산자 오버로딩을 지원하지는 않으므로 CLS(공용 언어 사양, 2.5절)의 필수 항목에서 빠져 있다. 자세히는 22.6절에서 다룬다.

### 필드

**필드**(field)는 클래스나 구조체의 멤버인 변수다.

```csharp
class Octopus
{
    string name;            // private (기본값)
    public int Age = 10;    // 초기화자가 붙은 public 필드
}
```

필드에 붙일 수 있는 한정자는 다음이 전부다.

| 범주 | 한정자 | 의미 |
|---|---|---|
| 정적 한정자 | `static` | 타입의 상태. 인스턴스마다 복사되지 않는다 (13.11절) |
| 접근 한정자 | `public` `internal` `private` `protected` | 17.1절 |
| 상속 한정자 | `new` | 기반 클래스의 같은 이름 필드를 가린다 (14.3절) |
| 비관리 코드 한정자 | `unsafe` | 포인터 타입 필드 (60장) |
| 읽기 전용 한정자 | `readonly` | 생성 이후 대입 불가 |
| 스레딩 한정자 | `volatile` | 특정 최적화를 금지한다 (48장) |

`readonly`는 **선언부 또는 그 타입의 생성자 안에서만** 대입할 수 있다. 그 외의 어떤 메서드에서도 대입하면 컴파일 오류다.

```csharp
class MyMathClass
{
    public readonly double PI;

    public MyMathClass() { PI = 3.14; }     // OK — 생성자 안
    public void ChangePI() { PI = 3.1444; } // 컴파일 오류
}
```

같은 타입의 필드를 쉼표로 묶어 한 번에 선언할 수도 있다. 한정자와 특성을 공유하고 싶을 때 쓴다.

```csharp
static readonly int legs = 8,
                    eyes = 2;
```

초기화는 선택이다. 초기화하지 않은 필드는 **기본값**(`0`, `'\0'`, `null`, `false`)을 갖는다(6.9절). 이것은 C#의 편의가 아니라 CLR의 보장이다 — 참조 타입의 인스턴스를 만들 때 할당된 메모리는 **생성자가 실행되기 전에 0으로 채워진다.** 생성자가 명시적으로 덮어쓰지 않은 필드는 반드시 `0`이나 `null`이다.

필드 초기화자에는 식을 쓸 수 있고 메서드도 부를 수 있다.

```csharp
static readonly string TempFolder = System.IO.Path.GetTempPath();
```

> **⚠️ `readonly` 참조 필드가 지키는 것은 "참조"뿐이다**
>
> 참조 타입 필드에 `readonly`를 붙이면 **그 필드가 가리키는 대상을 바꾸지 못한다**는 뜻이지, 대상 객체의 내용이 불변이라는 뜻이 전혀 아니다.
>
> ```csharp
> public sealed class AType
> {
>     public static readonly char[] InvalidChars = { 'A', 'B', 'C' };
> }
>
> AType.InvalidChars[0] = 'X';                    // 컴파일된다. 내용은 바뀐다
> AType.InvalidChars = new char[] { 'X' };        // 컴파일 오류
> ```
>
> `public static readonly` 배열은 **모든 호출자가 자유롭게 고칠 수 있는 전역 가변 상태**다. BCL이 이 실수를 저지른 자리가 있어서, 지금은 `ReadOnlySpan<T>`나 `ImmutableArray<T>`(24.10절)로 노출하는 것이 표준이다. 리플렉션을 쓰면 `readonly` 필드 자체도 고칠 수 있다는 것도 알아 둘 것(57.7절).

### 상수

**상수**(constant)는 컴파일 시점에 평가되고, 사용된 자리마다 컴파일러가 그 값을 **문자 그대로 치환**한다. C++의 매크로에 가깝다.

```csharp
public class Test
{
    public const string Message = "Hello World";
}
```

상수가 될 수 있는 타입은 `bool`, `char`, `string`, 내장 숫자 타입, `enum` 타입으로 제한된다. 비원시 타입이라도 값이 `null`이면 상수로 선언할 수 있다.

```csharp
public sealed class SomeType
{
    public const SomeType Empty = null;   // 값이 null이면 허용된다
}
```

상수는 **언제나 암시적으로 정적**이다. `static`을 붙이면 오류다. 접근할 때도 인스턴스가 아니라 타입 이름으로 접근한다(`MyMathClass.PI`). 지역 상수도 선언할 수 있다.

```csharp
void Test()
{
    const double twoPI = 2 * System.Math.PI;
    // ...
}
```

비지역 상수에 붙일 수 있는 한정자는 접근 한정자와 `new`뿐이다.

치환의 실제 결과는 IL에 그대로 드러난다.

```csharp
public static double Circumference(double radius)
{
    return 2 * System.Math.PI * radius;
}
```

이 코드는 다음과 동등한 것으로 컴파일된다.

```csharp
public static double Circumference(double radius)
{
    return 6.2831853071795862 * radius;
}
```

`Math.PI`는 그 값이 컴파일 시점에 확정되어 있으므로 상수가 타당하다. 반면 `static readonly` 필드의 값은 실행할 때마다 달라질 수 있다.

```csharp
static readonly DateTime StartupTime = DateTime.Now;
```

> **⚠️ 상수는 어셈블리 경계를 넘는 순간 시한폭탄이 된다**
>
> 어셈블리 X가 `public const decimal ProgramVersion = 2.3;`을 노출하고 어셈블리 Y가 그것을 쓴다고 하자. Y를 컴파일하는 순간 **값 2.3이 Y의 IL에 구워진다.** 나중에 X를 2.4로 고쳐 다시 빌드해 배포해도, Y를 다시 컴파일하기 전까지 Y는 계속 2.3을 쓴다.
>
> 더 심한 것은 참조 관계 자체가 사라진다는 점이다. 상수만 참조한 어셈블리는 컴파일 후 메타데이터에 그 어셈블리 참조가 아예 남지 않는다. 디스크에서 지워도 실행된다.
>
> 판단 기준은 간단하다. **미래에 바뀔 수 있는 값은 정의상 상수가 아니다.** 바뀔 수 있으면 `static readonly`를 쓴다. 컴파일 결과의 세부 비교는 10.11절에서 IL까지 확인했고, 설계 관점의 권고는 79.2절이다.

### 필드로 둘 것인가, 프로퍼티로 둘 것인가

이 장의 첫 설계 판단이다. C#은 `public` 필드를 문법적으로 허용하지만, 실무의 기준선은 **"공개 상태는 프로퍼티, 필드는 `private`"** 이다. 이유는 취향이 아니라 아래의 비대칭성 때문이다.

| 관점 | 필드 | 프로퍼티 |
|---|---|---|
| 값 검증 | 불가능 | `set`에서 예외를 던질 수 있다 |
| 읽기 전용/쓰기 전용 | 불가능(`readonly`는 생성자 이후 전면 금지) | 접근자 하나만 두면 된다 |
| 계산된 값 | 불가능 | 다른 데이터로부터 계산 가능 |
| `ref`/`out` 인수로 전달 | 가능 | **불가능** (CS0206) |
| 메모리 주소 노출 | 노출된다 | 노출되지 않는다 |
| 접근자별 접근 수준 분리 | 불가능 | `public get` + `private set` 가능 |
| 나중에 상대를 바꿀 때 | 프로퍼티로 바꾸면 **호출자 재컴파일 필요** | 구현만 바꾸면 재컴파일 불필요 |
| 인터페이스 멤버로 선언 | 불가능 | 가능 |
| 호출 비용 | 없음 | 접근자 호출 — 단순하면 JIT이 인라인 |

마지막 두 줄이 결정적이다. 필드를 프로퍼티로 바꾸는 것은 **바이너리 호환성을 깨는 변경**이다(78.13절). 처음부터 프로퍼티로 두면 나중에 검증 로직을 넣어도 호출자는 재컴파일이 필요 없다.

> **💡 그래서 필드는 언제 쓰나**
>
> `private`인 백킹 필드, `private readonly` 의존성(생성자로 받은 로거·리포지터리), `private static readonly` 캐시 — 이 셋이 필드의 정당한 자리다. 즉 **타입 바깥에서 보이지 않는 상태**다.
>
> 예외가 하나 있다. 성능이 극단적으로 중요한 내부 자료구조(예: 구조체의 필드에 `ref`로 접근해야 하는 경우, 68장)에서는 `internal` 필드를 쓰기도 한다. 프로퍼티는 `ref`로 넘길 수 없기 때문이다. 이때도 **어셈블리 밖으로는 내보내지 않는다.**
>
> 반대 방향의 함정도 있다. 프로퍼티는 필드처럼 **보이기** 때문에, 호출자는 "싸고, 예외를 안 던지고, 두 번 읽으면 같은 값이 나온다"고 가정한다. 이 가정을 깨는 프로퍼티(네트워크를 타는 `get`, 부수 효과가 있는 `get`, 매번 다른 값을 주는 `get`)는 프로퍼티가 아니라 메서드여야 한다. 이 원칙은 79.9절에서 다시 다룬다.

> **📌 비공개 필드 이름 규칙 두 가지**
>
> 널리 쓰이는 관례는 카멜 표기(`firstName`)와 밑줄 접두사 카멜 표기(`_firstName`) 둘이다. 후자는 **비공개 필드를 매개변수·지역 변수와 한눈에 구분**해 준다는 장점이 있어 최근 코드베이스에서 더 흔하다. `this.` 접두사를 생략해도 오해가 없다는 것도 실질적인 이점이다. 어느 쪽이든 팀 안에서 하나로 통일하고 `.editorconfig`의 `dotnet_naming_rule`로 강제하면 된다(79.13절).

## 13.2 메서드와 오버로드 해석 규칙

### 시그니처가 무엇으로 이루어지는가

메서드는 매개변수로 입력을 받고 반환 타입으로 출력을 돌려준다. `void`면 반환값이 없고, `ref`/`out` 매개변수로도 출력할 수 있다(10.2절).

**메서드의 시그니처는 타입 안에서 유일해야 한다.** 시그니처를 이루는 것은 다음이다.

| 시그니처의 일부인가 | 항목 |
|---|---|
| **그렇다** | 메서드 이름 |
| **그렇다** | 매개변수의 타입과 **순서** |
| **그렇다** | 매개변수의 전달 방식(값 / `ref` / `out` / `in`) |
| **그렇다** | 제네릭 타입 매개변수의 **개수**(arity) |
| 아니다 | 매개변수 이름 |
| 아니다 | **반환 타입** |
| 아니다 | `params` 한정자 |
| 아니다 | 매개변수의 기본값(선택적 매개변수) |

메서드에 붙일 수 있는 한정자는 다음과 같다.

| 범주 | 한정자 |
|---|---|
| 정적 한정자 | `static` |
| 접근 한정자 | `public` `internal` `private` `protected` |
| 상속 한정자 | `new` `virtual` `abstract` `override` `sealed` |
| 부분 메서드 한정자 | `partial` |
| 비관리 코드 한정자 | `unsafe` `extern` |
| 비동기 한정자 | `async` |

### 식 본문 메서드

단일 식으로 이루어진 메서드는 뚱뚱한 화살표(`=>`)로 줄여 쓸 수 있다.

```csharp
int Foo(int x) { return x * 2; }    // 일반 형태
int Foo(int x) => x * 2;            // 식 본문 메서드
```

`void` 반환 메서드도 된다.

```csharp
void Foo(int x) => Console.WriteLine(x);
```

식 본문은 **문법 설탕일 뿐 IL은 동일하다.** 컴파일 결과를 비교해 보면 `ret` 앞에 오는 명령이 똑같다.

### 지역 메서드

메서드 안에 메서드를 선언할 수 있다.

```csharp
void WriteCubes()
{
    Console.WriteLine(Cube(3));
    Console.WriteLine(Cube(4));
    Console.WriteLine(Cube(5));

    int Cube(int value) => value * value * value;
}
```

`Cube`는 `WriteCubes` 안에서만 보인다. 타입의 멤버 목록이 깨끗해지고, "이 함수는 여기 말고 어디에서도 안 쓰인다"는 사실이 코드에 드러난다.

지역 메서드는 **바깥 메서드의 지역 변수와 매개변수에 접근할 수 있다.** 이것이 여러 결과를 낳는데, 캡처가 만드는 할당 이야기는 26.10절과 26.12절에서 다룬다. `static` 한정자를 붙이면(※C# 8) 바깥의 지역 변수와 매개변수를 **볼 수 없게** 되어 결합이 줄고 실수로 캡처하는 일이 막힌다.

지역 메서드는 프로퍼티 접근자, 생성자, 다른 지역 메서드, 문 블록을 쓰는 람다 안에도 놓을 수 있다. 반복자(28장)나 비동기 메서드(47장)로 만드는 것도 된다.

> **⚠️ 최상위 문의 "메서드"는 전부 지역 메서드이고, 지역 메서드는 오버로드할 수 없다**
>
> 최상위 문(3.7절) 안에 선언한 메서드는 모두 컴파일러가 만든 `<Main>$`의 **지역 메서드**로 취급된다. 그래서 (`static`을 붙이지 않는 한) 최상위 문의 변수에 접근할 수 있다.
>
> ```csharp
> int x = 3;
> Foo();
> void Foo() => Console.WriteLine(x);   // 최상위 문의 x가 보인다
> ```
>
> 그 대가가 **오버로드 금지**다. 지역 메서드는 오버로드할 수 없으므로, 최상위 문에 같은 이름의 메서드를 둘 쓰면 컴파일 오류가 난다. 오버로드가 필요하면 별도 클래스로 빼거나 `partial class Program`(13.14절)에 정적 메서드로 두어야 한다.

### 오버로딩과 그 경계

같은 이름의 메서드를 시그니처만 다르게 여러 개 둘 수 있다.

```csharp
void Foo(int x) { }
void Foo(double x) { }
void Foo(int x, float y) { }
void Foo(float x, int y) { }
```

넷 다 공존한다. 반면 다음 쌍은 공존하지 못한다. 반환 타입과 `params` 한정자는 시그니처가 아니기 때문이다.

```csharp
void  Foo(int x) { }
float Foo(int x) { }                // 컴파일 오류

void Goo(int[] x) { }
void Goo(params int[] x) { }        // 컴파일 오류
```

전달 방식은 시그니처의 일부이므로 `Foo(int)`는 `Foo(ref int)`나 `Foo(out int)`와 공존할 수 있다. 다만 `Foo(ref int)`와 `Foo(out int)`는 **서로** 공존할 수 없다 — 메타데이터 시그니처가 둘 다 `int32&`로 같아지기 때문이다(10.2절에서 IL로 확인했다).

```csharp
void Foo(int x) { }
void Foo(ref int x) { }             // 여기까지 OK
void Foo(out int x) { }             // 컴파일 오류
```

### 오버로드 해석이 실제로 일어나는 순서

호출식 하나를 만나면 컴파일러는 다음 순서로 후보를 좁힌다. 이것은 **전적으로 컴파일 시점의 작업**이며, 런타임에는 이미 결정된 메서드 하나가 호출될 뿐이다(`dynamic`이 끼면 이야기가 달라진다 — 59장).

```text
1) 후보 집합 만들기
   이름이 같고, 호출 위치에서 접근 가능한 모든 메서드
        ↓
2) 적용 가능(applicable)한 것만 남기기
   인수 개수가 맞고, 각 인수가 대응 매개변수로
   암시적 변환되는 것만
        ↓  (여기서 "일반 형태"가 먼저다)
   ─ 2a. params를 펼치지 않은 일반 형태로 적용되는가?
   ─ 2b. 아니면 선택적 매개변수를 채워 적용되는가?
   ─ 2c. 아니면 params를 펼친 확장 형태로 적용되는가?
        ↓
3) 남은 것이 둘 이상이면 "더 나은 함수 멤버" 고르기
   모든 인수에 대해 변환이 더 좋거나 같고,
   적어도 하나는 엄격히 더 좋은 쪽이 이긴다
        ↓
4) 그래도 못 고르면 CS0121 (호출이 모호함)
```

3단계의 "변환이 더 좋다"는 판단은 대략 이렇게 움직인다.

| 상황 | 이기는 쪽 | 예 |
|---|---|---|
| 정확히 일치 | 변환이 없는 쪽 | `Foo(int)` vs `Foo(long)`에 `int` 인수 → `Foo(int)` |
| 두 변환이 모두 암시적 | 더 좁은 타입 | `int` 인수에 `long`과 `double` → `long` |
| 제네릭 vs 비제네릭 | **비제네릭** | `Foo(int)` vs `Foo<T>(T)` → `Foo(int)` |
| 일반 형태 vs `params` 확장 형태 | **일반 형태** | 10.5절 |
| 선택적 매개변수를 덜 채우는 쪽 | 덜 채우는 쪽 | `Foo(int)` vs `Foo(int, int = 0)` → 앞쪽 |

> **⚠️ 오버로드를 하나 추가하는 것은 소스 호환성을 깰 수 있다**
>
> 이미 배포된 API에 오버로드를 추가하면, 기존 호출부가 **조용히 다른 메서드를 부르게** 될 수 있다. 다음이 전형적인 사고다.
>
> ```csharp
> // v1
> public void Log(object value) { }
>
> // v2에서 추가
> public void Log(string value) { }
> ```
>
> `Log("hello")`는 v1에서 `Log(object)`를 불렀지만 v2에서는 `Log(string)`을 부른다. 두 구현의 동작이 다르면 호출자는 코드를 한 줄도 안 고쳤는데 동작이 바뀐다. 게다가 재컴파일하기 전까지는 여전히 옛 메서드를 부르므로, **재컴파일 시점에 동작이 바뀐다.** 오버로드 폭발과 선택적 매개변수의 저울질은 78.4절, 호환성을 깨는 변경 목록은 78.13절이다.

> **📌 상속이 끼면 규칙이 하나 더 붙는다**
>
> 파생 클래스에 적용 가능한 후보가 하나라도 있으면, 기반 클래스의 후보는 **더 잘 맞더라도 아예 고려되지 않는다.** 이 규칙 때문에 `Derived.Foo(int)`가 존재하면 `Derived` 인스턴스로는 `Base.Foo(string)`을 부르지 못하는 상황이 생긴다. 상세는 14.8절에서 다룬다.

### 컴파일 결과 — 메서드 하나가 IL에서 어떻게 보이는가

`hidebysig`는 "이름과 시그니처가 모두 같을 때만 기반 클래스의 멤버를 가린다"는 뜻으로, C# 컴파일러는 모든 메서드에 이 플래그를 붙인다.

```il
.method public hidebysig instance int32 Foo(int32 x) cil managed
{
  .maxstack 8
  IL_0000: ldarg.1
  IL_0001: ldc.i4.2
  IL_0002: mul
  IL_0003: ret
}
```

인스턴스 메서드의 `ldarg.0`은 `this`이므로 첫 매개변수는 `ldarg.1`이다. 정적 메서드였다면 첫 매개변수가 `ldarg.0`이 된다. IL을 읽을 때 가장 먼저 확인할 지점이다.

## 13.3 인스턴스 생성자와 생성자 체이닝

### 문법

**생성자**(constructor)는 클래스나 구조체의 인스턴스를 초기화하는 코드를 실행한다. 메서드와 똑같이 정의하되, 이름은 타입 이름이고 반환 타입은 없다.

```csharp
Panda p = new Panda("Petey");       // 생성자 호출

public class Panda
{
    string name;                    // 필드 정의

    public Panda(string n)          // 생성자 정의
    {
        name = n;                   // 초기화 코드
    }
}
```

생성자에 붙일 수 있는 한정자는 접근 한정자와 `unsafe`/`extern`뿐이다. **`virtual`, `override`, `new`, `sealed`, `abstract`는 붙일 수 없다.** 생성자는 상속되지 않기 때문이다 — 클래스는 자기가 직접 선언한 생성자만 갖는다.

문장이 하나뿐인 생성자는 식 본문으로 쓸 수 있다.

```csharp
public Panda(string n) => name = n;
```

매개변수 이름이 필드 이름과 충돌하면 `this`로 구분한다(13.7절).

```csharp
public Panda(string name) => this.name = name;
```

### 암시적 매개변수 없는 생성자

클래스는 **생성자를 하나도 정의하지 않은 경우에만** 컴파일러가 `public` 매개변수 없는 생성자를 자동 생성한다. 하나라도 직접 정의하는 순간 자동 생성은 사라진다.

컴파일러가 만드는 것은 정확히 다음과 같다.

```csharp
public class SomeType { }
// 위 코드는 아래와 같다
public class SomeType
{
    public SomeType() : base() { }
}
```

세부 규칙이 셋 붙는다.

| 클래스 종류 | 자동 생성되는 생성자 |
|---|---|
| 일반 클래스 | `public` 매개변수 없는 생성자 |
| `abstract` 클래스 | `protected` 매개변수 없는 생성자 |
| `static` 클래스 | **아무것도 생성되지 않는다** (13.11절) |
| 기본 생성자가 있는 클래스 ※C# 12 | 기본 생성자가 그 자리를 차지한다 (13.10절) |

구조체는 규칙이 다르다. CLR이 값 타입의 인스턴스 생성을 언제나 허용하므로 C# 컴파일러는 구조체에 매개변수 없는 생성자를 만들어 주지 않는다. ※C# 10부터 구조체가 매개변수 없는 생성자를 **직접** 선언할 수 있게 됐지만, 그것이 항상 실행되는 것도 아니다. 이 함정은 16.3절에서 다룬다.

### 생성자 오버로딩과 `this(...)` 체이닝

생성자도 오버로드할 수 있다. 코드 중복을 없애려면 `this` 키워드로 다른 생성자를 부른다.

```csharp
public class Wine
{
    public decimal Price;
    public int Year;

    public Wine(decimal price) => Price = price;
    public Wine(decimal price, int year) : this(price) => Year = year;
}
```

**호출된 생성자가 먼저 실행된다.** 즉 `new Wine(10m, 2020)`은 `Wine(decimal)`의 본문을 끝내고 나서 `Wine(decimal, int)`의 본문(`Year = year`)을 실행한다.

`this(...)`에는 식을 넘길 수 있다.

```csharp
public Wine(decimal price, DateTime year) : this(price, year.Year) { }
```

이 식은 **클래스의 정적 멤버에는 접근할 수 있지만 인스턴스 멤버에는 접근할 수 없다.** 그 시점에는 객체가 아직 생성자에 의해 초기화되지 않았으므로, 인스턴스 메서드를 부르면 십중팔구 실패할 것이기 때문이다.

> **📌 체이닝은 코드 크기를 줄인다**
>
> 필드 초기화자가 있는 클래스에 생성자가 셋이면, 컴파일러는 **초기화 코드를 생성자마다 한 번씩, 총 세 벌** 만든다(13.4절에서 IL로 확인한다). 초기화할 필드가 많고 생성자도 많으면 이 중복이 실제 코드 크기로 나타난다.
>
> ```csharp
> internal sealed class SomeType
> {
>     private int    m_x;             // 선언부에서 초기화하지 않는다
>     private string m_s;
>     private double m_d;
>
>     public SomeType()               // 공통 초기화는 여기 한 곳
>     {
>         m_x = 5; m_s = "Hi there"; m_d = 3.14159;
>     }
>
>     public SomeType(int x)    : this() { m_x = x; }
>     public SomeType(string s) : this() { m_s = s; }
>     public SomeType(int x, string s) : this() { m_x = x; m_s = s; }
> }
> ```
>
> 초기화 코드는 매개변수 없는 생성자 한 곳에만 있고, 나머지는 그것을 부른 뒤 필요한 것만 덮어쓴다. 중복 초기화 로직을 제거하는 관용구는 79.6절에서 다시 다룬다.

### 비공개 생성자와 팩터리

생성자가 `public`일 필요는 없다. 비공개 생성자를 두는 흔한 이유는 **인스턴스 생성을 정적 메서드로 통제**하기 위해서다. 풀에서 객체를 꺼내 돌려주거나, 인수에 따라 서로 다른 파생 클래스를 돌려줄 수 있다.

```csharp
public class Class1
{
    Class1() { }                        // 비공개 생성자

    public static Class1 Create(/* ... */)
    {
        // 여기서 사용자 정의 로직을 수행해 Class1 인스턴스를 돌려준다
        // ...
    }
}
```

### 런타임에 무슨 일이 일어나는가

참조 타입의 인스턴스를 만들 때 CLR이 하는 일은 순서가 정해져 있다.

1. 인스턴스 데이터 필드가 요구하는 바이트 수를 계산한다. 이때 **모든 기반 타입**(`System.Object`까지)이 정의한 필드와, CLR이 객체를 관리하는 데 쓰는 오버헤드 멤버 둘(타입 객체 포인터, 싱크 블록 인덱스)의 크기가 함께 더해진다 — 54.2절
2. 관리 힙에서 그만큼의 메모리를 할당한다. **할당된 바이트는 전부 0으로 채워진다**
3. 객체의 타입 객체 포인터와 싱크 블록 인덱스를 초기화한다
4. 타입의 인스턴스 생성자를 호출한다

생성자는 메타데이터 상에서 언제나 `.ctor`라는 이름을 갖는다. 검증 가능한(verifiable) 코드가 되려면, 클래스의 생성자는 기반 클래스에서 상속한 필드에 접근하기 **전에** 기반 클래스의 생성자를 호출해야 한다. C# 컴파일러가 이 호출을 자동으로 넣어 주며, 최종적으로 `System.Object`의 매개변수 없는 생성자에 도달한다. `Object`에는 인스턴스 필드가 없으므로 그 생성자는 아무 일도 하지 않고 반환한다.

> **⚠️ 생성자를 거치지 않고 인스턴스가 만들어지는 경로가 있다**
>
> 드물지만 실재한다.
>
> - `Object.MemberwiseClone()`은 메모리를 할당하고 오버헤드 필드를 초기화한 뒤 **원본의 바이트를 그대로 복사**한다. 생성자는 실행되지 않는다(15.6절).
> - `RuntimeHelpers.GetUninitializedObject(Type)`는 생성자를 부르지 않고 0으로 채워진 인스턴스를 만든다. 직렬화 인프라가 이 방식을 쓴다(.NET Framework 시절의 `FormatterServices.GetUninitializedObject`가 이것의 옛 이름이다).
>
> 그래서 **"이 클래스의 인스턴스는 반드시 생성자를 통과했다"는 가정 위에 불변식을 세우면 안 되는 시나리오**가 존재한다. 역직렬화가 걸린 타입에서 특히 그렇다. `required` 멤버(13.13절)도 컴파일러가 강제하는 것이지 CLR이 강제하는 것이 아니다.

> **⚠️ 생성자 안에서 가상 메서드를 부르지 마라**
>
> 그 가상 메서드가 파생 타입에서 재정의되어 있으면 **파생 타입의 구현이 실행되는데, 그 시점에 파생 타입의 필드는 아직 초기화되지 않았다.** 결과는 예측 불가능한 동작이다. 왜 그렇게 되는지는 13.4절의 초기화 순서를 보면 명확해지고, 대응 방법은 14.10절에서 다룬다.

## 13.4 필드 초기화 순서 — 초기화자와 생성자 본문

이 절은 이 장에서 가장 중요하다. **초기화 순서를 모르면 조용히 `null`이 들어간 필드를 찾아 며칠을 헤매게 된다.**

### 규칙 두 줄

1. **필드 초기화자는 생성자 본문보다 먼저, 선언 순서대로 실행된다.**
2. **필드 초기화자는 기반 클래스 생성자보다도 먼저 실행된다.**

첫 번째 규칙부터 보자.

```csharp
class Player
{
    int shields = 50;      // 먼저 초기화된다
    int health = 100;      // 다음에 초기화된다
}
```

두 번째 규칙은 IL을 봐야 납득이 된다.

```csharp
internal sealed class SomeType
{
    private int m_x = 5;
}
```

이 클래스의 `.ctor`는 다음과 같이 컴파일된다.

```il
.method public hidebysig specialname rtspecialname
        instance void .ctor() cil managed
{
  // Code size       14 (0xe)
  .maxstack  8
  IL_0000:  ldarg.0
  IL_0001:  ldc.i4.5
  IL_0002:  stfld      int32 SomeType::m_x
  IL_0007:  ldarg.0
  IL_0008:  call       instance void [mscorlib]System.Object::.ctor()
  IL_000d:  ret
}
```

`stfld`(필드 저장)가 `call ...Object::.ctor` **앞에** 있다. 즉 C#은 필드 초기화자를 생성자 본문이 아니라 **기반 생성자 호출보다도 앞**에 배치한다. 이렇게 하는 이유는 "소스에 적힌 대로 필드는 항상 값을 갖고 있다"는 인상을 유지하기 위해서다. 기반 클래스 생성자가 가상 메서드를 불러 파생 클래스로 제어가 넘어오더라도, 필드 초기화자가 준 값은 이미 들어가 있다.

### 전체 순서 다이어그램

`new Derived(args)`가 실행될 때 벌어지는 일을 그림으로 정리한다.

```text
      new Derived(args)
             │
             ▼
   ┌─────────────────────────────────────────────────────┐
   │ 1. 인수(args) 평가 — 호출부에서, 왼쪽에서 오른쪽으로   │
   └─────────────────────────────────────────────────────┘
             │
             ▼
   ┌─────────────────────────────────────────────────────┐
   │ 2. 힙에 메모리 할당 + 오버헤드 필드 설정               │
   │    모든 인스턴스 필드가 0 / null / false로 채워진다     │
   └─────────────────────────────────────────────────────┘
             │
             ▼
   ┌─────────────────────────────────────────────────────┐
   │ 3. Derived의 인스턴스 필드 초기화자                    │  ← 선언 순서
   │    (이 생성자가 this(...)를 쓰지 않을 때만)            │
   └─────────────────────────────────────────────────────┘
             │
             ▼
   ┌─────────────────────────────────────────────────────┐
   │ 4. base(...) 호출 → 기반 클래스에서 3~5 반복           │
   │      Base의 필드 초기화자                             │
   │      Base의 base(...)  →  ...  →  Object::.ctor      │
   │      Base 생성자 본문                                 │
   └─────────────────────────────────────────────────────┘
             │
             ▼
   ┌─────────────────────────────────────────────────────┐
   │ 5. Derived 생성자 본문                                │
   └─────────────────────────────────────────────────────┘
             │
             ▼
        참조가 호출부로 반환된다
```

**핵심은 3과 4의 순서다.** 필드 초기화자는 아래에서 위로(파생 → 기반) 실행되고, 생성자 본문은 위에서 아래로(기반 → 파생) 실행된다.

`this(...)` 체이닝이 끼면 규칙이 하나 추가된다. **`this(...)` 초기화자를 가진 생성자는 필드 초기화자를 실행하지 않는다.** 필드 초기화자는 체인의 끝, 즉 `base(...)`를 부르는(또는 아무것도 안 부르는) 생성자에서 딱 한 번 실행된다. 그래서 필드 초기화자가 두 번 실행되는 일은 없다.

| 생성자의 초기화자 | 필드 초기화자 실행? | 실행 순서 |
|---|---|---|
| 없음(암시적 `base()`) | **예** | 필드 초기화자 → 기반 생성자 → 본문 |
| `: base(...)` | **예** | 필드 초기화자 → 기반 생성자 → 본문 |
| `: this(...)` | **아니오** | 대상 생성자 전체 → 본문 |

### 왜 이 순서가 사고를 만드는가

```csharp
class Base
{
    public Base() => Init();                    // 기반 생성자가 가상 메서드 호출
    protected virtual void Init() { }
}

class Derived : Base
{
    string _greeting = "안녕";                   // 필드 초기화자
    readonly int _count;                        // 생성자 본문에서만 대입

    public Derived(int count) => _count = count;

    protected override void Init()
        => Console.WriteLine($"{_greeting} / {_count}");
}

new Derived(5);   // 출력: 안녕 / 0
```

`_greeting`은 **필드 초기화자**로 채워지므로 3단계에서 이미 값이 들어간다. `_count`는 **생성자 본문**에서 채워지므로 5단계까지 기다려야 한다. 그런데 `Init()`은 4단계에서 불린다. 그래서 `_greeting`은 보이고 `_count`는 `0`이다. 이 비대칭이 "생성자에서 가상 메서드를 부르지 마라"(14.10절)의 실체다.

> **⚠️ 필드 초기화자에서 다른 필드를 참조하지 마라**
>
> 초기화자는 **선언 순서대로** 실행되므로, 아래에 선언된 필드를 참조하면 그 필드의 기본값을 읽는다. 인스턴스 필드에서는 컴파일 오류(`CS0236`: 초기화자가 비정적 필드를 참조할 수 없음)로 막히지만, **정적 필드에서는 조용히 통과한다**(13.12절에서 다시 본다).
>
> 필드 순서를 바꾸는 것만으로 동작이 바뀌는 코드는 리팩터링 도구가 필드를 재정렬하는 순간 깨진다. 서로 의존하는 초기화는 초기화자가 아니라 **생성자 본문**에 두는 것이 옳다.

> **💡 초기화자와 생성자 할당, 무엇을 언제 쓰나**
>
> - **모든 생성자에서 값이 같으면 초기화자.** 생성자를 추가할 때 초기화를 빠뜨리는 실수가 원천 봉쇄된다.
> - **생성자 인수에 의존하면 생성자 본문.** 다른 선택지가 없다.
> - **초기화 코드가 여러 줄이거나 예외를 던질 수 있으면 생성자 본문.** 초기화자에서 던진 예외는 스택 트레이스가 생성자를 가리켜 원인을 찾기 어렵다.
> - **초기화 순서에 의존하면 생성자 본문.** 위 ⚠️의 이유다.
>
> 이 판단을 8단계로 쪼개 관용구 관점에서 다시 정리한 것이 79.5절이다.

> **📌 구조체는 이야기가 다르다**
>
> 값 타입은 인스턴스 필드에 초기화자를 붙이지 못했다(`error CS0573`). ※C# 10부터 매개변수 없는 생성자와 함께라면 가능해졌지만, **그 생성자가 실행되지 않는 경로**(`default(T)`, 배열 원소, `Array.Resize` 등)에서는 필드가 그냥 0이다. 값 타입의 필드는 언제나 0/null로 시작한다고 보는 편이 안전하다. 상세는 16.3절과 16.4절이다.

## 13.5 분해자(`Deconstruct`)

### 문법

**분해자**(deconstructor, 분해 메서드)는 생성자의 대략적인 반대다. 생성자가 값들을 받아 필드에 넣는다면, 분해자는 필드를 여러 변수로 되돌려 준다.

분해 메서드는 이름이 반드시 `Deconstruct`여야 하고, 하나 이상의 `out` 매개변수를 가져야 한다.

```csharp
class Rectangle
{
    public readonly float Width, Height;

    public Rectangle(float width, float height)
    {
        Width = width;
        Height = height;
    }

    public void Deconstruct(out float width, out float height)
    {
        width = Width;
        height = Height;
    }
}
```

호출은 전용 문법으로 한다.

```csharp
var rect = new Rectangle(3, 4);
(float width, float height) = rect;            // 분해
Console.WriteLine(width + " " + height);       // 3 4
```

두 번째 줄이 분해 호출이다. 지역 변수 둘을 만들고 `Deconstruct`를 부른다. 컴파일 결과는 다음과 완전히 같다.

```csharp
float width, height;
rect.Deconstruct(out width, out height);
```

### 문법 변형들

```csharp
(var width, var height) = rect;      // 암시적 타입 지정
var (width, height) = rect;          // 더 짧게
var (_, height) = rect;              // 관심 없는 값은 무시 항목(_)

float width, height;
(width, height) = rect;              // 이미 선언된 변수 — 분해 할당

double x1 = 0;
(x1, double y2) = rect;              // ※C# 10 — 기존 변수와 새 변수 혼용
```

무시 항목(`_`)은 "쓰지 않을 변수를 굳이 선언"하는 것보다 의도가 분명하다.

분해 할당은 생성자를 짧게 쓰는 데도 쓸 수 있다.

```csharp
public Rectangle(float width, float height) =>
    (Width, Height) = (width, height);
```

### 오버로딩과 확장 메서드

`Deconstruct`를 오버로드하면 호출자에게 여러 분해 방식을 제공할 수 있다.

```csharp
public void Deconstruct(out string name, out DateTimeOffset dob) { /* ... */ }
public void Deconstruct(out string name, out DateTimeOffset dob, out int age) { /* ... */ }
```

어느 것이 불릴지는 **좌변 변수의 개수**로 결정된다. 그래서 `out` 매개변수 개수가 같은 오버로드를 둘 두면 호출이 모호해진다.

`Deconstruct`는 **확장 메서드**여도 된다. 소스를 고칠 수 없는 남의 타입을 분해하고 싶을 때 쓰는 기법이다.

> **⚠️ `Deconstruct`가 인식되는 조건은 생각보다 빡빡하다**
>
> - 이름이 정확히 `Deconstruct`여야 한다. `deconstruct`도, `DeConstruct`도 안 된다.
> - 모든 매개변수가 `out`이어야 한다. 하나라도 값 매개변수면 인식되지 않는다.
> - 반환 타입은 `void`여야 한다.
> - **분해 선언은 변수가 둘 이상이어야 한다.** C#에는 1-튜플 문법이 없기 때문에 `out` 매개변수가 하나뿐인 `Deconstruct`는 분해 문법으로 부를 수 없고, 일반 메서드처럼 직접 부르는 수밖에 없다.
>
> 조건이 안 맞으면 컴파일러는 "분해자가 잘못됐다"고 알려주는 대신 **"이 타입은 분해할 수 없다"**고만 말한다. 메서드 시그니처를 다시 보는 것이 먼저다.

> **📌 레코드는 이것을 공짜로 준다**
>
> 위치 지정 레코드(`record Point(int X, int Y)`)는 컴파일러가 `Deconstruct`를 자동 생성한다. `out` 매개변수 이름은 위치 매개변수의 이름과 같고, 호출부의 변수 이름은 아무거나 써도 **위치로만** 대응된다. 자세히는 19.3절과 19.6절이다.

분해와 튜플·패턴 매칭의 관계(위치 패턴이 내부적으로 `Deconstruct`를 부른다는 사실, `ITuple` 폴백 등)는 77.6절과 77.10절에서 끝까지 다룬다. 이 절은 "클래스에 `Deconstruct`를 어떻게 붙이는가"에서 멈춘다.

## 13.6 객체 초기화자와 컬렉션 초기화자

### 객체 초기화자

객체를 만든 직후에 접근 가능한 필드나 프로퍼티를 중괄호 안에서 설정할 수 있다.

```csharp
public class Bunny
{
    public string Name;
    public bool LikesCarrots, LikesHumans;

    public Bunny() { }
    public Bunny(string n) => Name = n;
}
```

```csharp
// 매개변수 없는 생성자는 빈 괄호를 생략할 수 있다
Bunny b1 = new Bunny { Name = "Bo", LikesCarrots = true, LikesHumans = false };
Bunny b2 = new Bunny("Bo") { LikesCarrots = true, LikesHumans = false };
```

### 컴파일 결과 — 임시 변수와 원자성

이 문법의 핵심은 컴파일 결과에 있다. 위 두 줄은 **정확히** 다음과 같이 컴파일된다.

```csharp
Bunny temp1 = new Bunny();          // temp1은 컴파일러가 만든 이름
temp1.Name = "Bo";
temp1.LikesCarrots = true;
temp1.LikesHumans = false;
Bunny b1 = temp1;                   // 전부 성공한 뒤에야 b1에 대입

Bunny temp2 = new Bunny("Bo");
temp2.LikesCarrots = true;
temp2.LikesHumans = false;
Bunny b2 = temp2;
```

**임시 변수가 존재하는 이유는 원자성이다.** 초기화 도중 예외가 던져지면 `b1`에는 아무것도 대입되지 않는다. 즉 **절반만 초기화된 객체가 변수에 남는 일이 없다.** 프로퍼티 `set` 접근자가 검증을 하고 예외를 던지는 설계(13.8절)와 맞물리면 이 성질이 중요해진다.

부수 효과도 있다. 객체 초기화자는 **문(statement)이 아니라 식(expression)** 이므로 그 자리에서 이어 붙일 수 있다.

```csharp
string s = new Employee { Name = "Jeff", Age = 45 }.ToString().ToUpper();
```

> **⚠️ 초기화자 안의 대입은 순서대로 실행되고, `set` 접근자를 그대로 부른다**
>
> 객체 초기화자는 마법이 아니라 **대입문의 나열**이다. 그래서 다음이 전부 그대로 성립한다.
>
> - 검증 로직이 있는 `set`은 그대로 실행된다 — 잘못된 값을 넣으면 예외가 난다.
> - 프로퍼티 A의 `set`이 프로퍼티 B의 값을 읽는다면, **초기화자에 적은 순서**가 결과를 바꾼다.
> - 대입은 생성자 **이후**에 일어난다. 생성자 안에서 "모든 값이 유효한지" 검사해 봐야 소용없다.
>
> 마지막 항목이 실무에서 가장 자주 물린다. "생성자에서 불변식을 검증했는데 왜 깨진 객체가 있지?"의 답이 대개 객체 초기화자다. 불변식을 강제하고 싶으면 `init` 전용 프로퍼티(13.8절)와 `required`(13.13절)를 조합하거나, 아예 생성자 매개변수로만 받아야 한다.

### 객체 초기화자 vs 선택적 매개변수

같은 일을 생성자의 선택적 매개변수로도 할 수 있다.

```csharp
public Bunny(string name, bool likesCarrots = false, bool likesHumans = false)
{
    Name = name;
    LikesCarrots = likesCarrots;
    LikesHumans = likesHumans;
}

Bunny b1 = new Bunny(name: "Bo", likesCarrots: true);
```

역사적으로 이쪽이 유리한 점이 있었다 — 필드나 프로퍼티를 **읽기 전용**으로 만들 수 있었다. 하지만 ※C# 9의 `init` 한정자가 그 장점을 객체 초기화자 쪽으로 옮겨 왔다.

선택적 매개변수에는 두 가지 단점이 있다.

1. **비파괴적 변경(nondestructive mutation)을 쉽게 지원하지 못한다.** 레코드의 `with` 식(19.4절)이 푸는 문제다.
2. **공개 라이브러리에서 하위 호환을 깬다.** 선택적 매개변수의 기본값은 **호출부에 구워지기** 때문이다. `new Bunny("Bo", true)` 호출은 IL에서 `new Bunny("Bo", true, false)`가 된다. 나중에 매개변수를 하나 더 추가하면, 참조하는 어셈블리를 재컴파일하기 전까지는 **존재하지 않는 3-매개변수 생성자**를 계속 부르다가 런타임에 실패한다. 기본값을 바꿔도 재컴파일 전까지는 옛 값이 쓰인다(10.4절에서 IL로 확인했다).

여기에 상속까지 얹히면 더 나빠진다. 매개변수가 긴 생성자가 여러 개 있으면 서브클래싱이 번거로워진다(14.6절). **생성자는 개수와 복잡도를 최소로 유지하고 나머지는 객체 초기화자로 채우는 것**이 균형점이다.

### 컬렉션 초기화자

프로퍼티나 변수의 타입이 `IEnumerable` 또는 `IEnumerable<T>`를 구현하면, 초기화자는 **대체가 아니라 추가** 동작이 된다.

```csharp
var table = new Dictionary<string, int>
{
    { "Jeffrey", 1 }, { "Kristin", 2 }, { "Aidan", 3 }, { "Grant", 4 }
};
```

컴파일 결과는 다음과 같다.

```csharp
var table = new Dictionary<string, int>();
table.Add("Jeffrey", 1);
table.Add("Kristin", 2);
table.Add("Aidan", 3);
table.Add("Grant", 4);
```

즉 컴파일러는 **`Add`라는 이름의 메서드가 있다고 가정하고 호출 코드를 생성한다.** 인수가 여럿인 `Add`는 중첩 중괄호로 넘긴다.

컬렉션 **프로퍼티**를 초기화하는 형태도 있다. 이때는 `set` 접근자가 아니라 `get`으로 얻은 컬렉션에 `Add`를 부른다.

```csharp
public sealed class Classroom
{
    private List<string> m_students = new List<string>();
    public List<string> Students { get { return m_students; } }   // setter가 없다
}

Classroom classroom = new Classroom
{
    Students = { "Jeff", "Kristin", "Aidan", "Grant" }
};
```

이것은 다음으로 컴파일된다.

```csharp
Classroom classroom = new Classroom();
classroom.Students.Add("Jeff");
classroom.Students.Add("Kristin");
classroom.Students.Add("Aidan");
classroom.Students.Add("Grant");
```

| 문법 | 요구 조건 | 생성되는 코드 |
|---|---|---|
| `new C { P = v }` | `P`에 접근 가능한 `set`/`init` | `temp.P = v;` |
| `new List<T> { a, b }` | `IEnumerable` 구현 + `Add` 메서드 | `temp.Add(a); temp.Add(b);` |
| `new C { P = { a, b } }` | `P`에 접근 가능한 `get`, `P`의 타입에 `Add` | `temp.P.Add(a); temp.P.Add(b);` |
| `new D { { k, v } }` | 인수 2개짜리 `Add` | `temp.Add(k, v);` |

> **⚠️ `IEnumerable`을 구현했는데 `Add`가 없으면 컴파일 오류다**
>
> 컴파일러는 인터페이스 계약이 아니라 **이름으로 `Add`를 찾는다**(덕 타이핑). `IEnumerable<string>` 타입의 프로퍼티에 컬렉션 초기화자를 쓰면 다음과 같은 오류가 난다.
>
> ```text
> error CS1061: 'IEnumerable<string>' does not contain a definition for 'Add'
> and no accessible extension method 'Add' accepting a first argument of type
> 'IEnumerable<string>' could be found
> ```
>
> 아예 `IEnumerable`을 구현하지 않은 타입에 컬렉션 초기화자를 쓰면 오류가 달라진다 — `error CS1922`.
>
> 반대로 `Add`가 **확장 메서드**로만 존재하는 경우, ※C# 6부터는 그것도 인식된다.

> **⚠️ 컬렉션 프로퍼티가 `null`이면 런타임에 터진다**
>
> `new C { P = { a } }` 형태는 `temp.P.Add(a)`로 컴파일되므로, `P`가 `null`을 돌려주면 `NullReferenceException`이다. 컴파일러는 아무 경고도 주지 않는다.
>
> 그래서 컬렉션 프로퍼티는 **선언 시점에 초기화하고 setter를 두지 않는 것**이 표준 관용구다.
>
> ```csharp
> public List<string> Students { get; } = new();
> ```

> **📌 컬렉션 식은 다른 문법이다 ※C# 12**
>
> `int[] a = [1, 2, 3];` 같은 **컬렉션 식**(collection expression)은 컬렉션 초기화자와 문법도 컴파일 결과도 다르다. 대상 타입에 따라 컴파일러가 최적의 생성 코드를 고르며, `List<T>`에는 `Add` 대신 용량을 미리 잡는 경로를 쓰기도 한다. 스프레드 연산자(`..`)까지 포함한 전체 규칙은 24.14절에서 다룬다.

## 13.7 `this` 참조

`this` 참조는 인스턴스 자기 자신을 가리킨다. 다음 예에서 `Marry` 메서드는 상대방의 `Mate` 필드에 자기 자신을 넣는다.

```csharp
public class Panda
{
    public Panda Mate;

    public void Marry(Panda partner)
    {
        Mate = partner;
        partner.Mate = this;
    }
}
```

두 번째 용도는 **이름 가리기 해소**다. 매개변수나 지역 변수가 필드와 이름이 같을 때 필드 쪽을 `this.`로 지목한다.

```csharp
public class Test
{
    string name;
    public Test(string name) => this.name = name;
}
```

`this`는 **클래스나 구조체의 비정적 멤버 안에서만 유효하다.** 정적 메서드에서 `this`를 쓰면 컴파일 오류다 — 정적 멤버는 인스턴스를 전제하지 않기 때문이다.

`this`가 등장하는 자리를 정리하면 다음과 같다.

| 자리 | 의미 | 절 |
|---|---|---|
| 인스턴스 메서드 본문 | 현재 인스턴스 | 13.7절 |
| `: this(...)` 생성자 초기화자 | 같은 타입의 다른 생성자 호출 | 13.3절 |
| `public string this[int i]` | 인덱서 선언 | 13.9절 |
| `static void M(this string s)` | 확장 메서드의 첫 매개변수 | 20.5절 |
| 구조체 생성자의 `this = ...` | 구조체 전체를 덮어쓰기 | 16.3절 |

> **📌 IL에서 `this`는 0번 인수다**
>
> 인스턴스 메서드의 IL을 읽을 때 `ldarg.0`은 언제나 `this`다. C# 소스에 `this`를 쓰지 않아도, 필드에 접근하는 코드는 반드시 `ldarg.0`으로 시작한다(13.4절의 IL을 다시 보라). 정적 메서드에서는 `ldarg.0`이 첫 번째 실제 매개변수다. 디스어셈블 결과를 읽다가 인수 번호가 하나씩 밀려 보인다면 대개 이것을 놓친 것이다.

> **⚠️ 생성자에서 `this`를 밖으로 흘리지 마라**
>
> 생성자 안에서 `this`를 다른 객체에 등록하거나(이벤트 구독, 컬렉션 추가, 스레드 시작) 정적 필드에 저장하면, **아직 초기화가 끝나지 않은 객체의 참조**가 밖으로 나간다.
>
> ```csharp
> class Widget
> {
>     static readonly List<Widget> All = new();
>     readonly string _name;
>
>     public Widget(string name)
>     {
>         All.Add(this);      // 위험 — _name이 아직 대입되지 않았다
>         _name = name;
>     }
> }
> ```
>
> 단일 스레드에서는 대개 무사히 넘어가지만, 다른 스레드가 `All`을 즉시 읽는다면 `_name`이 `null`인 객체를 본다. 파생 클래스가 있다면 파생 클래스의 생성자 본문은 아직 시작조차 하지 않았다(13.4절). **생성자는 자기 상태를 채우는 일만 하고, 등록·구독·시작은 생성자 밖에서** 하는 것이 안전하다.

> **💡 `this.`를 항상 붙일 것인가**
>
> 정답은 없지만 실무의 흐름은 갈렸다. 밑줄 접두사(`_name`) 관례를 쓰는 팀은 필드와 매개변수가 이름 자체로 구분되므로 `this.`를 거의 쓰지 않고, 접두사 없는 관례를 쓰는 팀은 생성자 안에서 `this.`가 필수가 된다.
>
> 어느 쪽이든 **일관성이 가치의 전부**다. `.editorconfig`의 `dotnet_style_qualification_for_field` 규칙으로 강제하면 리뷰에서 논쟁할 일이 없어진다.

## 13.8 프로퍼티 — 자동 구현, 읽기 전용, `init` 전용, `field` 키워드 ※C# 13

### 문법

프로퍼티는 밖에서 보면 필드 같지만 안에는 메서드처럼 로직이 들어 있다. 다음 코드만 보고는 `CurrentPrice`가 필드인지 프로퍼티인지 알 수 없다.

```csharp
Stock msft = new Stock();
msft.CurrentPrice = 30;
msft.CurrentPrice -= 3;
Console.WriteLine(msft.CurrentPrice);
```

프로퍼티는 필드처럼 선언하고 `get`/`set` 블록을 붙여 만든다.

```csharp
public class Stock
{
    decimal currentPrice;                  // 비공개 "백킹" 필드

    public decimal CurrentPrice            // 공개 프로퍼티
    {
        get { return currentPrice; }
        set { currentPrice = value; }
    }
}
```

`get` 접근자는 프로퍼티를 읽을 때 실행되며 프로퍼티 타입의 값을 반환해야 한다. `set` 접근자는 대입할 때 실행되며, 프로퍼티 타입의 **암시적 매개변수 `value`** 를 받는다.

프로퍼티에 붙일 수 있는 한정자는 `static`, 접근 한정자, `new`/`virtual`/`abstract`/`override`/`sealed`, `unsafe`/`extern`이다.

### 읽기 전용과 계산된 프로퍼티

`get`만 있으면 읽기 전용, `set`만 있으면 쓰기 전용이다(쓰기 전용은 거의 쓰이지 않는다). 프로퍼티가 반드시 전용 백킹 필드를 가져야 하는 것도 아니다.

```csharp
decimal currentPrice, sharesOwned;
public decimal Worth
{
    get { return currentPrice * sharesOwned; }
}
```

읽기 전용 프로퍼티는 식 본문으로 줄일 수 있다.

```csharp
public decimal Worth => currentPrice * sharesOwned;
```

`set`도 식 본문으로 쓸 수 있다.

```csharp
public decimal Worth
{
    get => currentPrice * sharesOwned;
    set => sharesOwned = value / currentPrice;
}
```

### 자동 구현 프로퍼티와 백킹 필드의 정체

가장 흔한 구현은 "같은 타입의 비공개 필드를 그대로 읽고 쓰는" 것이다. **자동 구현 프로퍼티**(automatically implemented property)는 그 구현을 컴파일러에게 맡긴다.

```csharp
public class Stock
{
    public decimal CurrentPrice { get; set; }
}
```

컴파일러는 **컴파일러가 만든 이름의 비공개 백킹 필드**를 생성한다. 그 이름은 C# 소스에서 참조할 수 없다. ildasm으로 보면 이렇게 생겼다.

```il
.field private decimal '<CurrentPrice>k__BackingField'
.method public hidebysig specialname instance decimal get_CurrentPrice() cil managed
.method public hidebysig specialname instance void  set_CurrentPrice(decimal 'value') cil managed
.property instance decimal CurrentPrice()
{
  .get instance decimal Stock::get_CurrentPrice()
  .set instance void Stock::set_CurrentPrice(decimal)
}
```

이름의 꺾쇠(`<`, `>`)는 C# 식별자에 쓸 수 없는 문자다. 컴파일러가 일부러 그런 이름을 골라 **소스에서 절대 충돌하지 않게** 만든 것이다(이 기법은 반복자·비동기 상태 기계에서도 똑같이 쓰인다).

프로퍼티 초기화자도 필드와 똑같이 붙일 수 있다.

```csharp
public decimal CurrentPrice { get; set; } = 123;
public int Maximum { get; } = 999;      // 읽기 전용 + 초기화자
```

읽기 전용 자동 프로퍼티는 **생성자 안에서도 대입할 수 있다.** 불변 타입을 만드는 기본 도구다.

`set`에만 더 좁은 접근 수준을 줄 수도 있다. 이때 프로퍼티 자체는 **덜 제한적인 쪽**으로 선언하고, 접근자에 제한을 건다.

```csharp
public class Foo
{
    private decimal x;
    public decimal X
    {
        get         { return x; }
        private set { x = Math.Round(value, 2); }
    }
}
```

> **⚠️ 자동 구현 프로퍼티의 백킹 필드 이름은 컴파일할 때마다 달라질 수 있다**
>
> 이름이 컴파일러 구현 세부이므로, **필드 이름에 의존하는 직렬화기와 함께 쓰면 안 된다.** 필드 이름을 스트림에 기록하는 직렬화 방식(옛 `BinaryFormatter` 계열)에서는 재컴파일만으로 역직렬화가 깨질 수 있다.
>
> 디버깅에도 영향이 있다. 자동 구현 프로퍼티의 `get`/`set`에는 중단점을 걸 수 없다. 값이 언제 바뀌는지 추적해야 한다면 **일시적으로 수동 구현으로 바꾸는 것**이 가장 빠른 길이다.
>
> 그리고 자동 구현 프로퍼티는 **전부 아니면 전무**다. 접근자 하나를 직접 구현하기로 하면 나머지 하나도 직접 구현해야 한다(※C# 13의 `field` 키워드가 이 제약을 푼다 — 아래 참조).

### `init` 전용 setter ※C# 9

`set` 대신 `init`을 쓰면, 객체 초기화자에서는 설정할 수 있지만 그 이후에는 읽기 전용이 된다.

```csharp
public class Note
{
    public int Pitch    { get; init; } = 20;
    public int Duration { get; init; } = 100;
}

var note = new Note { Pitch = 50 };     // OK
note.Pitch = 200;                       // 컴파일 오류
```

`init` 전용 프로퍼티는 **클래스 내부에서도** 마음대로 못 바꾼다. 설정할 수 있는 자리는 프로퍼티 초기화자, 생성자, 그리고 다른 `init` 접근자뿐이다.

대안은 읽기 전용 프로퍼티를 생성자로 채우는 것이다.

```csharp
public class Note
{
    public int Pitch    { get; }
    public int Duration { get; }

    public Note(int pitch = 20, int duration = 100)
    {
        Pitch = pitch; Duration = duration;
    }
}
```

공개 라이브러리라면 이 방식이 버전 관리에서 불리하다. **생성자에 선택적 매개변수를 추가하면 바이너리 호환성이 깨지지만, `init` 전용 프로퍼티를 추가하는 것은 아무것도 깨지 않는다**(13.6절).

`init` 접근자에 구현을 넣을 수도 있다.

```csharp
public class Note
{
    readonly int _pitch;
    public int Pitch { get => _pitch; init => _pitch = value; }
}
```

`_pitch`가 `readonly`인 데 주목할 것. **`init` 접근자는 자기 클래스의 `readonly` 필드를 수정할 수 있다.** 이 허용이 없었다면 `_pitch`를 쓰기 가능하게 만들어야 했고, 타입은 내부적으로 불변이 될 수 없었다.

> **⚠️ `init`과 `set`을 서로 바꾸는 것은 바이너리 호환성을 깬다**
>
> 프로퍼티의 접근자를 `init`에서 `set`으로(또는 그 반대로) 바꾸면 **참조하는 어셈블리를 전부 재컴파일해야 한다.** 완전한 불변 타입을 만들 때는 애초에 `set`이 필요할 일이 없으므로 문제가 되지 않지만, "일단 `set`으로 두고 나중에 `init`으로 조이자"는 계획은 세우지 않는 편이 낫다.

### `init`의 CLR 표현 — `modreq(IsExternalInit)`

CLR 관점에서 `init` 접근자는 **평범한 `set` 접근자**다. 다른 점은 `set` 메서드의 **반환 타입에 특별한 플래그**가 붙는다는 것뿐이다.

이 플래그는 흔한 특성(attribute)이 아니라 **`modreq`(필수 사용자 지정 한정자)** 라는 다소 낯선 메타데이터 장치로 인코딩된다. `modreq`의 규칙은 "이 한정자를 이해하지 못하는 컴파일러는 이 멤버를 아예 무시해야 한다"이다. 그래서 `init`을 모르는 옛 C# 컴파일러는 그 프로퍼티를 **쓰기 가능한 것으로 착각하는 대신 접근자 자체를 못 본 것으로 처리**한다.

이 한정자의 이름이 `IsExternalInit`이다. 리플렉션으로 직접 확인할 수 있다.

```csharp
bool IsInitOnly(PropertyInfo pi) => pi
    .GetSetMethod().ReturnParameter.GetRequiredCustomModifiers()
    .Any(t => t.Name == "IsExternalInit");
```

> **📌 `IsExternalInit`은 .NET 5 이상에만 있다**
>
> `System.Runtime.CompilerServices.IsExternalInit` 타입은 .NET 5부터 BCL에 들어왔다. `netstandard2.0`이나 .NET Framework를 대상으로 하면서 `init`을 쓰려면, 같은 이름의 빈 정적 클래스를 프로젝트에 직접 선언해 주면 컴파일러가 그것을 쓴다. 널리 쓰이는 폴리필 기법이며, `record`도 같은 이유로 같은 처리가 필요하다.

### `field` 키워드 ※C# 13

자동 구현 프로퍼티의 "전부 아니면 전무" 제약을 푸는 기능이다. 접근자 본문에서 문맥 키워드 `field`로 **컴파일러가 만든 백킹 필드를 직접 참조**할 수 있다.

```csharp
// 예전 방식 — 백킹 필드를 손으로 선언해야 했다
private string _name = "";
public string Name
{
    get => _name;
    set => _name = value ?? throw new ArgumentNullException(nameof(value));
}

// field 키워드
public string Name
{
    get;
    set => field = value ?? throw new ArgumentNullException(nameof(value));
}
```

한쪽 접근자만 구현하고 나머지는 자동 구현으로 두는 것이 가능해졌다. 검증 한 줄 때문에 백킹 필드를 선언하고 이름을 짓던 관성이 사라진다.

> **⚠️ `field`라는 이름의 필드가 있으면 의미가 바뀐다**
>
> 이 기능은 **문맥 키워드를 새로 만드는 변경**이다. 프로퍼티 접근자 안에서 `field`는 이제 백킹 필드를 뜻하므로, `field`라는 이름의 필드나 지역 변수를 쓰던 기존 코드는 접근자 안에서 의미가 달라진다. 해결책은 `@field`나 `this.field`로 명시하는 것이다.
>
> 도입 이력도 알아 둘 필요가 있다. **C# 13에서 미리 보기(`<LangVersion>preview</LangVersion>`)로 제공됐고, 정식 기능이 된 것은 그다음 버전이다.** 팀의 `LangVersion` 설정에 따라 컴파일이 될 수도 안 될 수도 있다.

### CLR 구현과 성능

C# 프로퍼티 접근자는 `get_XXX`, `set_XXX`라는 이름의 메서드로 컴파일된다.

```csharp
public decimal get_CurrentPrice() { /* ... */ }
public void    set_CurrentPrice(decimal value) { /* ... */ }
```

여기에 더해 **프로퍼티 정의 항목이 메타데이터에 하나 기록된다.** 이 항목은 플래그와 프로퍼티 타입을 담고 `get`/`set` 접근자 메서드를 가리킨다. "프로퍼티"라는 추상 개념과 실제 접근자 메서드를 이어 주는 것이 목적이며, `System.Reflection.PropertyInfo`로 조회할 수 있다. **CLR은 실행할 때 이 메타데이터를 쓰지 않는다.** 필요한 것은 접근자 메서드뿐이다.

성능은 이렇게 정리된다.

| 상황 | 비용 |
|---|---|
| 단순 비가상 접근자, 릴리스 빌드 | JIT이 인라인 — 필드 접근과 차이 없음 |
| 단순 접근자, 디버그 빌드 | **인라인되지 않는다** — 실제 호출 비용이 든다 |
| 가상 프로퍼티 | 가상 디스패치 비용(14.9절), 역가상화가 되면 인라인 가능 |
| 계산량이 있는 접근자 | 인라인 대상에서 제외될 수 있다(55.4절) |

두 번째 줄이 실무의 함정이다. **프로퍼티 접근이 디버그 빌드에서는 느리고 릴리스 빌드에서는 공짜인 반면, 필드 접근은 양쪽 다 빠르다.** 디버그 빌드에서 잰 수치로 "프로퍼티가 병목"이라고 결론 내리는 것은 거의 항상 틀렸다(67장).

> **⚠️ 프로퍼티는 `ref`/`out` 인수로 넘길 수 없다**
>
> ```csharp
> MethodWithOutParam(out Name);   // error CS0206
> ```
>
> `ref`/`out`은 **저장 위치의 주소**를 요구하는데 프로퍼티에는 주소가 없기 때문이다. `Interlocked` 계열 API나 `TryParse` 패턴에 프로퍼티를 그대로 넘길 수 없는 이유가 이것이다. 지역 변수를 거쳐야 한다.
>
> 같은 이유로 **구조체를 반환하는 프로퍼티**는 매번 복사본을 준다. `obj.Position.X = 5;`가 컴파일 오류인 것도(값을 고쳐 봐야 복사본이 바뀌므로) 여기서 나온다. 16.2절에서 다시 다룬다.

## 13.9 인덱서와 "매개변수 있는 프로퍼티"의 정체

### 문법

**인덱서**(indexer)는 리스트나 딕셔너리를 캡슐화한 타입의 원소에 자연스러운 문법으로 접근하게 해 준다. 프로퍼티와 비슷하지만 **이름 대신 인덱스 인수로** 접근한다. `string` 타입에도 인덱서가 있다.

```csharp
string s = "hello";
Console.WriteLine(s[0]);   // 'h'
Console.WriteLine(s[3]);   // 'l'
```

배열 문법과 같아 보이지만, 인덱스 인수의 타입은 **아무 타입이나** 될 수 있다는 점이 다르다.

인덱서를 구현하려면 `this`라는 이름의 프로퍼티를 정의하고 인수를 대괄호 안에 적는다.

```csharp
class Sentence
{
    string[] words = "The quick brown fox".Split();

    public string this[int wordNum]            // 인덱서
    {
        get { return words[wordNum]; }
        set { words[wordNum] = value; }
    }
}
```

```csharp
Sentence s = new Sentence();
Console.WriteLine(s[3]);        // fox
s[3] = "kangaroo";
Console.WriteLine(s[3]);        // kangaroo
```

한 타입에 인덱서를 여럿 둘 수 있고(매개변수 타입이 다르면 된다), 인덱서가 매개변수를 여럿 받을 수도 있다.

```csharp
public string this[int arg1, string arg2]
{
    get { /* ... */ } set { /* ... */ }
}
```

`set`을 생략하면 읽기 전용이 되고, 식 본문으로 줄일 수 있다.

```csharp
public string this[int wordNum] => words[wordNum];
```

인덱서에 붙는 한정자는 프로퍼티와 같고, **null 조건부 인덱스 연산자**(10.10절)로 부를 수도 있다.

```csharp
string s = null;
Console.WriteLine(s?[0]);      // 아무것도 출력하지 않는다. 오류도 없다
```

`Index`나 `Range`를 매개변수 타입으로 하는 인덱서를 추가하면 `^`와 `..` 문법(9.3절)을 지원할 수 있다.

```csharp
public string   this[Index index] => words[index];
public string[] this[Range range] => words[range];
```

```csharp
Sentence s = new Sentence();
Console.WriteLine(s[^1]);                    // fox
string[] firstTwoWords = s[..2];             // (The, quick)
```

### 정체 — 인덱서는 "매개변수 있는 프로퍼티"다

CLR에는 인덱서라는 개념이 없다. **CLR이 아는 것은 프로퍼티뿐이며, 인덱서는 접근자가 매개변수를 받는 프로퍼티일 뿐이다.** 이 관점에서 프로퍼티는 두 종류로 나뉜다.

| 구분 | `get`의 매개변수 | `set`의 매개변수 | C# 문법 | Visual Basic |
|---|---|---|---|---|
| 매개변수 없는 프로퍼티 | 0개 | 1개(`value`) | `public T P { get; set; }` | 일반 프로퍼티 |
| 매개변수 있는 프로퍼티 | 1개 이상 | 2개 이상 | `public T this[...]` | 기본 프로퍼티 |

컴파일 결과는 프로퍼티와 완전히 같은 구조다.

```csharp
public string get_Item(int wordNum) { /* ... */ }
public void   set_Item(int wordNum, string value) { /* ... */ }
```

이름이 `Item`인 이유는 단순하다. C#의 `this[...]` 문법에는 **이름을 적을 자리가 없어서**, C# 팀이 기본 이름을 하나 정해야 했고 `Item`을 골랐다. 그래서 .NET 문서에서 "`Item`이라는 프로퍼티"를 보면 그것이 그 타입의 인덱서다. `List<T>`의 `Item` 프로퍼티가 바로 그것이다.

### `[IndexerName]`과 `[DefaultMember]`

이 기본 이름은 바꿀 수 있다.

```csharp
using System.Runtime.CompilerServices;

public sealed class BitArray
{
    [IndexerName("Bit")]
    public bool this[int bitPos]
    {
        get { /* ... */ } set { /* ... */ }
    }
}
```

이제 컴파일러는 `get_Bit`, `set_Bit`을 만든다. **`IndexerNameAttribute` 자체는 어셈블리 메타데이터에 남지 않는다** — 컴파일러에게 이름을 알려 주는 역할만 하고 사라진다.

그럼 다른 언어는 어떤 프로퍼티가 "그 타입의 인덱서"인지 어떻게 아는가? 여기서 **`System.Reflection.DefaultMemberAttribute`** 가 등장한다. 인덱서를 정의한 타입에는 컴파일러가 이 특성을 자동으로 붙이며, 그 인수가 인덱서 접근자의 이름이다.

| 소스 | 접근자 이름 | 타입에 붙는 특성 |
|---|---|---|
| `public T this[int i]` | `get_Item` / `set_Item` | `[DefaultMember("Item")]` |
| `[IndexerName("Bit")] public T this[int i]` | `get_Bit` / `set_Bit` | `[DefaultMember("Bit")]` |

`System.String`이 이 이름을 바꾼 대표적인 타입이다. `String`의 인덱서 이름은 `Item`이 아니라 **`Chars`** 다. 대괄호 문법이 없는 언어에서 "문자 하나를 얻는다"는 의미가 더 잘 드러나기 때문이다.

> **⚠️ C#에서는 이름이 다른 인덱서를 둘 만들 수 없다**
>
> C#은 인덱서를 "`[]` 연산자의 오버로드"로 취급하며, 소스 어디에도 인덱서 **이름**을 적지 않는다. 그래서 `[IndexerName]`으로 이름만 다르게 하고 시그니처가 같은 인덱서를 둘 두려 하면 다음 오류가 난다.
>
> ```text
> error CS0111: Type 'SomeType' already defines a member called 'this'
> with the same parameter types
> ```
>
> 반대로 매개변수 타입이 다르면 얼마든지 오버로드할 수 있다.

> **📌 C#에는 정적 인덱서가 없다**
>
> CLR은 정적인 매개변수 있는 프로퍼티를 지원하지만, C#의 `this[...]` 문법은 인스턴스에만 쓸 수 있다. `static`을 붙이면 컴파일 오류다. 정적 조회가 필요하면 정적 메서드(`FromName(...)` 같은)를 두는 것이 유일한 길이다.
>
> 마찬가지로 **인덱서는 제네릭 타입 매개변수를 자기 것으로 도입할 수 없다.** 프로퍼티도 마찬가지다. 프로퍼티는 개념적으로 "객체의 특성"이지 "동작"이 아니므로, 동작이 필요하면 메서드를 쓰라는 것이 언어 설계자의 답이다.

> **💡 인덱서를 만들 자리와 만들지 말 자리**
>
> 인덱서는 **"이 타입이 컬렉션이거나, 컬렉션처럼 조회되는 것이 자연스러운가"** 를 기준으로 판단한다. `dict[key]`, `matrix[row, col]`, `sentence[3]`은 자연스럽다.
>
> 반대로 `person["Name"]`처럼 **문자열 키로 아무 속성이나 꺼내는** 인덱서는 타입 안전성을 통째로 버리는 설계다. 컴파일러 검사도, 리팩터링 지원도, IntelliSense도 전부 사라진다. 이런 형태가 필요하면 딕셔너리를 프로퍼티로 노출하는 편이 정직하다.
>
> 성능 면에서 인덱서는 특별한 것이 없다. 단순한 인덱서는 프로퍼티와 똑같이 JIT이 인라인한다. 다만 **배열을 감싼 인덱서는 경계 검사가 두 번**(인덱서 안의 배열 접근 + 필요하면 자체 검증) 일어날 수 있다는 점은 핫 패스에서 고려할 값어치가 있다(9.5절).

## 13.10 기본 생성자(primary constructor) ※C# 12

### 문법

※C# 12부터 클래스(또는 구조체) 선언 바로 뒤에 매개변수 목록을 붙일 수 있다.

```csharp
class Person(string firstName, string lastName)
{
    public void Print() => Console.WriteLine(firstName + " " + lastName);
}
```

```csharp
Person p = new Person("Alice", "Jones");
p.Print();      // Alice Jones
```

컴파일러가 `firstName`, `lastName`을 받는 **기본 생성자**를 자동으로 만든다. 기본 생성자가 없다면 이렇게 썼어야 한다.

```csharp
class Person
{
    string firstName, lastName;                       // 필드 선언

    public Person(string firstName, string lastName)  // 생성자
    {
        this.firstName = firstName;
        this.lastName = lastName;
    }

    public void Print() => Console.WriteLine(firstName + " " + lastName);
}
```

이 생성자를 "기본(primary)"이라 부르는 이유는, **추가로 작성하는 모든 생성자가 반드시 이것을 호출해야 하기** 때문이다.

```csharp
class Person(string firstName, string lastName)
{
    public Person(string firstName, string lastName, int age)
        : this(firstName, lastName)      // 기본 생성자를 반드시 호출해야 한다
    {
        // ...
    }
}
```

이 규칙이 **기본 생성자 매개변수는 언제나 채워진다**는 것을 보장한다. 기본 생성자는 컴파일러가 만들어 주던 매개변수 없는 생성자를 **밀어낸다** — `new Person()`은 더 이상 컴파일되지 않는다.

### 의미론 — 매개변수가 사라지지 않는다

보통의 생성자에서는 본문 실행이 끝나면 매개변수가 범위를 벗어나 다시 접근할 수 없다. 기본 생성자의 매개변수는 다르다. **범위를 벗어나지 않고, 객체의 수명 내내 클래스 본문 어디에서나 접근할 수 있다.**

접근성은 필드·프로퍼티 초기화자까지 확장된다.

```csharp
class Person(string firstName, string lastName)
{
    public readonly string FirstName = firstName;      // 필드
    public string LastName { get; } = lastName;        // 프로퍼티
}
```

계산도 할 수 있다. **초기화자 안의 코드는 객체가 생성될 때 실행된다** — 필드나 프로퍼티가 접근될 때가 아니다.

```csharp
class Person(string firstName, string lastName)
{
    public readonly string FullName = firstName + " " + lastName;
    public void Print() => Console.WriteLine(FullName);
}

new Person("Alice", "Jones").Print();       // Alice Jones
```

`throw` 식(11.6절)과 조합하면 검증도 된다.

```csharp
class Person(string firstName, string lastName)
{
    readonly string lastName = (lastName == null)
        ? throw new ArgumentNullException("lastName")
        : lastName;
}

new Person("Alice", null);      // ArgumentNullException
```

### 가리기(masking)

필드나 프로퍼티가 기본 생성자 매개변수와 **같은 이름**을 쓸 수 있다.

```csharp
class Person(string firstName, string lastName)
{
    readonly string firstName = firstName;
    readonly string lastName = lastName;

    public void Print() => Console.WriteLine(firstName + " " + lastName);
}
```

이때 필드가 우선하고 매개변수는 가려진다. **예외는 필드·프로퍼티 초기화자의 우변**이며, 거기서는 매개변수가 보인다(위 코드의 `= firstName` 부분). 이 관용구에는 실질적인 이점이 있다 — 기본 생성자 매개변수는 **일반 매개변수처럼 쓰기 가능**하므로, 같은 이름의 `readonly` 필드로 가려 두면 이후 변경을 막을 수 있다.

값을 변형해 저장할 수도 있다.

```csharp
class Person(string firstName, string lastName)
{
    readonly string lastName = lastName.ToUpper();
    public void Print() => Console.WriteLine(firstName + " " + lastName);
}

new Person("Alice", "Jones").Print();       // Alice JONES
```

### 컴파일 결과 — 캡처된 매개변수는 숨은 필드가 된다

기본 생성자 매개변수는 **필드가 아니다.** 특별한 C# 구성물이며, 컴파일러가 필요할 때만 값을 저장할 숨은 필드를 만든다.

여기서 "필요할 때"의 기준이 중요하다.

| 매개변수의 사용처 | 숨은 필드가 생기는가 |
|---|---|
| 필드·프로퍼티 초기화자에서만 사용 | **아니오** — 생성자 안에서 쓰고 버린다 |
| 메서드·프로퍼티 접근자 본문에서 사용 | **예** — 값을 보관해야 하므로 캡처된다 |
| 아예 사용하지 않음 | 아니오 (사용하지 않는 매개변수 경고가 날 수 있다) |

즉 첫 번째 예제(`Print()`에서 `firstName`을 쓰는 형태)는 숨은 필드 둘을 만들지만, `FullName` 예제는 초기화자에서만 쓰므로 숨은 필드를 만들지 않는다. 이 필드의 이름 역시 C#에서 참조할 수 없는 컴파일러 생성 이름이다.

> **⚠️ 값이 두 벌 저장되는 함정**
>
> 기본 생성자 매개변수를 프로퍼티로 노출하면서 메서드에서도 매개변수를 직접 쓰면, **같은 값이 두 곳에 저장된다.**
>
> ```csharp
> class Person(string name)
> {
>     public string Name { get; set; } = name;          // 백킹 필드 1
>     public void Print() => Console.WriteLine(name);   // 캡처 필드 2
> }
>
> var p = new Person("Alice");
> p.Name = "Bob";
> p.Print();          // Alice — Bob이 아니다!
> ```
>
> `Name`을 바꿔도 `Print()`는 초기 매개변수 값을 계속 본다. 두 저장소는 서로 아무 관계가 없기 때문이다. **매개변수를 프로퍼티로 노출하기로 했다면, 그 뒤로는 프로퍼티만 쓴다** — 이 규칙을 지키는 가장 확실한 방법이 같은 이름으로 가리는 것이다.

### 레코드와 무엇이 다른가

레코드도 기본 생성자를 지원하지만, **컴파일러가 한 단계를 더 간다.**

| | 클래스/구조체의 기본 생성자 ※C# 12 | 레코드의 위치 매개변수 |
|---|---|---|
| 매개변수 → 공개 프로퍼티 | **생성되지 않는다** | 기본적으로 `init` 전용 프로퍼티 생성 |
| `Deconstruct` | 없음 | 자동 생성 |
| `Equals`/`GetHashCode`/`ToString` | 없음 | 자동 생성 |
| `with` 식 | 불가 | 가능 |
| 매개변수의 쓰기 가능 여부 | **쓰기 가능** | 프로퍼티는 `init` 전용 |

"매개변수를 그대로 공개 프로퍼티로 만들고 값 동등성까지 원한다"면 클래스가 아니라 **레코드**를 쓰는 것이 맞다(19장).

> **⚠️ 기본 생성자는 프로토타이핑용이라고 보는 편이 안전하다**
>
> 원서가 직접 명시한 한계가 셋이다.
>
> - **기본 생성자에 초기화 코드를 추가할 수 없다.** 본문이 없기 때문이다. 로깅 한 줄, 조건 분기 하나가 필요해지는 순간 일반 생성자로 돌아가야 한다.
> - **읽기 전용이 아닌 프로퍼티에 검증을 넣기 어렵다.** `public string LastName { get; set; } = lastName;`에 검증을 붙이려면 **두 곳**(수동 구현한 `set` 접근자와 프로퍼티 초기화자)에 같은 검증을 써야 한다. `init` 전용이어도 문제는 같다.
> - **매개변수가 쓰기 가능하다.** 메서드 안에서 `firstName = "X";`가 컴파일된다. 놀랄 사람이 많은 동작이다.
>
> 세 번째 상황이 오면 기본 생성자라는 지름길을 버리고 **생성자와 백킹 필드를 명시적으로 쓰는 편이 낫다.** 반대로 의존성 주입을 받는 서비스 클래스(`class OrderService(IRepo repo, ILogger log)`)처럼 "받아서 필드에 넣고 끝"인 경우에는 코드가 극적으로 짧아진다.

> **📌 구조체의 기본 생성자**
>
> 구조체에도 같은 문법을 쓸 수 있지만(`struct Point(int x, int y)`), 구조체는 **언제나 매개변수 없는 기본값 생성 경로가 존재**하므로(`default(Point)`, 배열 원소) 기본 생성자 매개변수가 채워지지 않은 인스턴스가 만들어질 수 있다. 값 타입의 초기화 규칙 전체는 16.3절에서 다룬다.

## 13.11 `static` 키워드 — 정적 필드·메서드·클래스

### 정적 필드

인스턴스 필드는 객체마다 따로 존재하지만, **정적 필드는 타입당 하나만 존재하고 모든 인스턴스가 공유한다.**

```csharp
class SavingsAccount
{
    public double currBalance;                       // 인스턴스마다 따로
    public static double currInterestRate = 0.04;    // 타입당 하나

    public SavingsAccount(double balance) => currBalance = balance;
}
```

```text
   ┌──────────────────────────────────────────────┐
   │  타입 SavingsAccount의 정적 저장소             │
   │      currInterestRate = 0.04                 │
   └──────────────────────────────────────────────┘
            ▲            ▲            ▲
            │            │            │
   ┌────────┴───┐ ┌──────┴─────┐ ┌────┴───────┐
   │ s1         │ │ s2         │ │ s3         │
   │ currBalance│ │ currBalance│ │ currBalance│
   │  = 50      │ │  = 100     │ │  = 10000.75│
   └────────────┘ └────────────┘ └────────────┘
```

객체를 새로 만들어도 정적 필드는 **초기화되지 않는다.** 딱 한 번만 할당되고 그 뒤로는 계속 같은 값이다.

정적 데이터는 타입 객체 안에 자리를 잡으며, 그 메모리는 타입이 로드될 때 확보된다 — 대개 그 타입을 참조하는 메서드가 처음 JIT 컴파일될 때다. 실제 저장 위치(High Frequency Heap)는 54.5절에서 다룬다.

### 정적 메서드

정적 메서드는 인스턴스가 아니라 타입에 속한다.

```csharp
public static void SetInterestRate(double newRate) => currInterestRate = newRate;
public static double GetInterestRate() => currInterestRate;
```

규칙 두 가지가 컴파일러에 의해 강제된다.

- **정적 멤버는 비정적 멤버를 참조할 수 없다.** 어느 인스턴스인지 알 수 없기 때문이다.
- **정적 멤버에서 `this`를 쓸 수 없다.** `this`는 인스턴스를 뜻하기 때문이다.

### 정적 클래스

`static`을 클래스에 붙이면 인스턴스를 만들 수 없고 상속할 수도 없으며, 정적 멤버만 담을 수 있다. `System.Console`과 `System.Math`가 대표적이다.

```csharp
static class TimeUtilClass
{
    public static void PrintTime() => Console.WriteLine(DateTime.Now.ToShortTimeString());
    public static void PrintDate() => Console.WriteLine(DateTime.Today.ToShortDateString());
}
```

컴파일러가 강제하는 제약이 넷이다.

| 제약 | 이유 |
|---|---|
| `System.Object`에서 직접 파생해야 한다 | 인스턴스를 만들 수 없으므로 상속이 의미 없다 |
| 인터페이스를 구현할 수 없다 | 인터페이스 메서드는 인스턴스로만 호출된다 |
| 정적 멤버만 가질 수 있다 | 인스턴스 멤버가 있으면 오류 |
| 필드·매개변수·지역 변수의 **타입**으로 쓸 수 없다 | 그런 변수는 인스턴스를 가리킨다는 뜻이므로 |

**컴파일 결과는 `abstract` + `sealed`다.** 메타데이터에서 정적 클래스는 추상이면서 봉인된 클래스로 표시되고, 인스턴스 생성자(`.ctor`)가 **아예 생성되지 않는다.** `abstract`(인스턴스화 금지)와 `sealed`(파생 금지)를 동시에 붙이는 것은 C#에서 직접 쓸 수 없는 조합인데, `static` 키워드가 정확히 그 조합을 만든다.

```il
.class public abstract auto ansi sealed beforefieldinit TimeUtilClass
       extends [System.Runtime]System.Object
{
  // .ctor 없음
}
```

### 제네릭 타입의 정적 데이터

제네릭 타입에서 정적 데이터는 **닫힌 타입마다 따로** 존재한다.

```csharp
Console.WriteLine(++Bob<int>.Count);       // 1
Console.WriteLine(++Bob<int>.Count);       // 2
Console.WriteLine(++Bob<string>.Count);    // 1
Console.WriteLine(++Bob<object>.Count);    // 1

class Bob<T> { public static int Count; }
```

`Bob<int>`와 `Bob<string>`은 CLR 관점에서 **서로 다른 타입**이므로 정적 필드도 별개다. 이 성질은 타입별 캐시를 만드는 강력한 관용구이면서(`Cache<T>.Instance`), 예상 못 한 메모리 증가의 원인이기도 하다. 23.8절과 23.11절에서 다룬다.

> **⚠️ 가변 정적 상태는 기본적으로 스레드 안전하지 않다**
>
> 정적 필드는 프로세스 전체가 공유한다. 즉 **모든 스레드가 같은 저장소를 두드린다.** `static int _counter; _counter++;`는 원자적이지 않고, `static Dictionary<K,V>`에 여러 스레드가 쓰면 무한 루프에 빠지거나 자료구조가 깨진다(24.12절).
>
> 정적 필드로 둘 수 있는 것은 대체로 셋이다 — **불변 값**(`static readonly`), **스레드 안전하게 설계된 객체**(`ConcurrentDictionary`, `HttpClient`), 그리고 **잠금으로 보호되는 상태**(11.7절, 48장). 그 밖의 가변 정적 상태는 테스트를 어렵게 만들고(80장) 병렬 실행에서 조용히 깨진다.

> **💡 `static`을 쓸 자리 판단표**
>
> | 상황 | 선택 |
> |---|---|
> | 모든 인스턴스가 공유해야 하는 값 | `static` 필드 |
> | 인스턴스 상태를 전혀 안 쓰는 도우미 함수 | `static` 메서드 |
> | 정적 멤버만 있는 유틸리티 타입 | `static` 클래스 |
> | 절대 바뀌지 않고 컴파일 시점에 아는 값 | `const` (13.1절) |
> | 실행 시점에 정해지고 그 뒤 불변인 값 | `static readonly` |
> | 지연 초기화가 필요한 무거운 싱글턴 | `Lazy<T>` (34.7절) 또는 정적 생성자 (13.12절) |
>
> `static`을 붙일 수 있는 것은 지역 함수(※C# 8)와 람다(※C# 9)도 마찬가지이며, 그쪽에서는 "캡처를 금지한다"는 전혀 다른 의미를 갖는다(26.11절). 정적 멤버를 이름 없이 가져다 쓰는 `using static`은 12.4절이다.

## 13.12 정적 생성자(타입 생성자)의 실행 시점과 함정

### 문법

**정적 생성자**(static constructor)는 인스턴스마다가 아니라 **타입마다 한 번** 실행된다. CLR 용어로는 **타입 생성자**(type constructor) 또는 타입 초기화자이며, 메타데이터에서 이름은 `.cctor`다.

```csharp
class Test
{
    static Test() { Console.WriteLine("Type Initialized"); }
}
```

규칙은 짧다.

- 타입당 **하나만** 정의할 수 있다. 오버로드 불가.
- **매개변수가 없어야** 한다.
- **접근 한정자를 붙일 수 없다.** 붙이면 `error CS0515`. 컴파일러가 자동으로 `private`으로 만든다 — 개발자가 직접 부르지 못하게 하기 위해서다. CLR은 언제든 부를 수 있다.
- 붙일 수 있는 한정자는 `unsafe`와 `extern`뿐이다.
- 인스턴스 생성자보다 **먼저** 실행된다.
- 기반 타입의 정적 생성자를 부르지 않는다(정적 필드는 상속되지 않으므로 부를 이유가 없다).

정적 생성자를 쓰는 자리는 명확하다. **정적 필드의 값을 컴파일 시점에 알 수 없을 때** — 파일이나 데이터베이스에서 읽어야 하거나, 계산이 필요할 때다.

```csharp
class SavingsAccount
{
    public static double currInterestRate;

    static SavingsAccount()
    {
        currInterestRate = LoadRateFromConfig();
    }
}
```

### 정적 필드 초기화자와의 관계

정적 필드 초기화자는 **정적 생성자 직전에, 선언 순서대로** 실행된다. 컴파일러는 둘을 하나의 `.cctor`로 합치면서 초기화자 코드를 먼저 배치한다.

```csharp
internal sealed class SomeType
{
    private static int s_x = 5;
}
```

```il
.method private hidebysig specialname rtspecialname static
        void .cctor() cil managed
{
  // Code size       7 (0x7)
  .maxstack  8
  IL_0000:  ldc.i4.5
  IL_0001:  stsfld     int32 SomeType::s_x
  IL_0006:  ret
}
```

명시적 정적 생성자와 초기화자가 둘 다 있으면, `.cctor`는 **초기화자 → 생성자 본문** 순으로 코드를 담는다. 즉 `private static int s_x = 5;`와 `static SomeType() { s_x = 10; }`이 함께 있으면 `s_x`는 5가 됐다가 10이 된다.

선언 순서 의존성은 실제 버그를 만든다.

```csharp
class Foo
{
    public static int X = Y;    // 0
    public static int Y = 3;    // 3
}
```

`X`가 `Y`보다 먼저 초기화되므로 `X`는 `Y`의 기본값 `0`을 읽는다. 두 줄을 바꾸면 둘 다 3이 된다. 인스턴스 필드와 달리 **컴파일 오류가 나지 않고 조용히 통과한다**는 점이 위험하다.

한 단계 더 꼬인 예도 있다.

```csharp
Console.WriteLine(Foo.X);      // 3

class Foo
{
    public static Foo Instance = new Foo();     // 여기서 Foo() 실행
    public static int X = 3;

    Foo() => Console.WriteLine(X);              // 0을 출력한다
}
```

출력은 `0` 다음에 `3`이다. `Instance` 초기화자가 인스턴스를 만들 때 `X`는 아직 3이 되기 전이다. 두 초기화자의 순서를 바꾸면 `3`과 `3`이 출력된다.

### 언제 실행되는가 — `beforefieldinit`이 만드는 차이

런타임은 "타입이 사용되기 직전에" 정적 생성자를 호출한다. 방아쇠는 둘이다.

- 타입을 인스턴스화할 때
- 타입의 정적 멤버에 접근할 때

여기까지가 흔히 알려진 설명이고, 실제 타이밍은 **타입에 명시적 정적 생성자가 있는지**에 따라 달라진다.

| | 명시적 정적 생성자 **없음** (초기화자만) | 명시적 정적 생성자 **있음** |
|---|---|---|
| 타입 메타데이터 플래그 | `beforefieldinit`이 붙는다 | 붙지 않는다 |
| 초기화 시점 | 첫 정적 필드 접근 **이전 아무 때나** — 런타임 재량 | 첫 인스턴스 생성 또는 첫 정적 멤버 접근 **직전에 정확히** |
| 관찰 가능한 부수 효과의 시점 | 예측할 수 없다 | 예측할 수 있다 |
| JIT 최적화 | 초기화 검사를 걷어내기 쉽다 | 검사가 남기 쉽다 |

`.class ... beforefieldinit` 플래그는 앞서 정적 클래스의 IL에서 이미 봤다. "필드 초기화 전 아무 때나 초기화해도 된다"는 뜻으로, 런타임에게 **초기화를 앞당길 자유**를 준다. 그래서 정적 필드 초기화자만 있는 타입에서는 초기화가 예상보다 이르게 일어날 수 있다.

명시적 정적 생성자를 쓰면 그 자유가 사라진다. 정확한 시점이 보장되는 대신, JIT이 정적 멤버 접근마다 "이 타입이 초기화됐는가" 검사를 유지해야 할 수 있다.

> **💡 빈 정적 생성자를 "혹시 몰라서" 쓰지 마라**
>
> `static Foo() { }` 한 줄을 추가하는 것만으로 타입에서 `beforefieldinit`이 사라진다. 즉 **아무 일도 하지 않는 정적 생성자가 성능 특성을 바꾼다.** 반대로, 초기화 시점이 정확해야 하는 코드(예: 초기화 부수 효과의 순서가 중요한 경우)에서는 명시적 정적 생성자를 두는 것이 **의도적인 선택**이 된다.
>
> 판단 기준: 정적 필드를 초기화자로 채울 수 있으면 초기화자로 채우고, 여러 줄의 로직이나 예외 처리, 정확한 시점이 필요하면 정적 생성자를 쓴다.

### 스레드 안전성

CLR은 **정적 생성자가 딱 한 번만 실행되도록** 보장한다. 여러 스레드가 동시에 도달하면 한 스레드만 상호 배타적 잠금을 얻어 본문을 실행하고 나머지는 대기한다. 첫 스레드가 나오면 대기하던 스레드들은 이미 실행됐음을 확인하고 그냥 반환한다.

**그래서 정적 생성자는 싱글턴을 초기화하기에 이상적인 자리다.** 이중 검사 잠금(double-checked locking)을 직접 쓸 이유가 없다.

```csharp
public sealed class Singleton
{
    public static readonly Singleton Instance = new Singleton();
    private Singleton() { }
}
```

> **⚠️ 정적 생성자에서 예외가 나면 그 타입은 영영 못 쓴다**
>
> 정적 생성자가 처리되지 않은 예외를 던지면 CLR은 그 타입을 **사용 불가**로 표시한다. 이후 그 타입의 필드나 메서드에 접근하면 `System.TypeInitializationException`이 던져지고, 원래 예외는 그 `InnerException`에 들어 있다. **애플리케이션(정확히는 그 타입이 로드된 컨텍스트)이 살아 있는 동안 회복되지 않는다.** 재시도해도 같은 예외가 계속 나온다.
>
> 그래서 정적 생성자에서 설정 파일을 읽거나 네트워크를 타는 코드는 위험하다. 예외 하나가 "이 타입은 이 프로세스에서 영구히 사용 불가"로 번역된다. 로그에 `TypeInitializationException`이 보이면 **반드시 `InnerException`을 먼저 보라.** 겉의 메시지에는 진짜 원인이 없다.

> **⚠️ 정적 생성자에서 잠금을 잡거나 스레드를 기다리면 교착이 난다**
>
> 정적 생성자는 이미 런타임의 잠금 안에서 실행되고 있다. 그 안에서
>
> - 다른 스레드를 시작하고 그 스레드의 완료를 기다리는데, 그 스레드가 같은 타입을 건드리거나
> - 비동기 작업을 `.Wait()`나 `.Result`로 동기 대기하거나
> - 서로를 참조하는 두 타입의 정적 생성자가 맞물리면
>
> 교착이 생긴다. 마지막 경우는 CLR도 손을 못 쓴다 — 각 정적 생성자가 한 번만 실행되는 것은 보장하지만, **`ClassA`의 정적 생성자가 끝난 뒤에 `ClassB`의 것이 실행된다는 보장은 없다.** 정적 생성자 사이에 실행 순서를 요구하는 코드는 애초에 쓰지 않는 것이 정답이다.

> **⚠️ 값 타입의 정적 생성자는 실행되지 않을 수 있다**
>
> C#은 구조체에도 정적 생성자를 허용하지만, 실제로 호출되지 않는 경로가 있다.
>
> ```csharp
> internal struct SomeValType
> {
>     static SomeValType() { Console.WriteLine("이 줄은 출력되지 않는다"); }
>     public int m_x;
> }
>
> SomeValType[] a = new SomeValType[10];
> a[0].m_x = 123;
> Console.WriteLine(a[0].m_x);        // 123 — 정적 생성자는 실행되지 않았다
> ```
>
> 배열 원소를 만드는 것은 "타입을 인스턴스화"하는 것으로 간주되지 않기 때문이다. **값 타입에는 정적 생성자를 두지 않는 것**이 안전하다.

> **📌 관련 도구 둘**
>
> - `System.Runtime.CompilerServices.RuntimeHelpers.RunClassConstructor(RuntimeTypeHandle)`로 정적 생성자를 강제 실행할 수 있다. 이미 실행됐으면 다시 부르지 않는다.
> - ※C# 9의 **모듈 초기화자**는 어셈블리가 처음 로드될 때 한 번 실행된다. `static void` 메서드에 `[ModuleInitializer]`를 붙이면 된다.
>
> ```csharp
> [System.Runtime.CompilerServices.ModuleInitializer]
> internal static void InitAssembly() { /* ... */ }
> ```

## 13.13 `required` 멤버 ※C# 11

### 문제

기반 클래스에 매개변수가 많은 생성자가 하나뿐이면, 모든 파생 클래스가 그 생성자를 `base(...)`로 중계하는 코드를 써야 한다(14.6절). 클래스 계층이 커질수록 이 부담이 커진다.

때로는 **생성자를 아예 포기하고 객체 초기화자만으로 상태를 채우는 것**이 최선인데, 그러면 "반드시 채워져야 하는 값"을 강제할 방법이 없었다. ※C# 11의 `required` 한정자가 그 구멍을 메운다.

```csharp
public class Asset
{
    public required string Name;
}
```

```csharp
Asset a1 = new Asset { Name = "House" };    // OK
Asset a2 = new Asset();                     // 컴파일 오류
```

오류 메시지는 이렇게 나온다.

```text
error CS9035: Required member 'Asset.Name' must be set in the object
initializer or attribute constructor.
```

필드와 프로퍼티 양쪽에 붙일 수 있다.

```csharp
public class Book
{
    public required string? Isbn;
    public required string? Title;
    public string? Author;
    public int PageCount;
}
```

> **⚠️ `required`는 널이 아님을 뜻하지 않는다**
>
> 위 예제의 세 문자열이 전부 널 허용(`string?`)인 데 주목할 것. **`required`가 요구하는 것은 "명시적으로 설정했는가"이지 "널이 아닌가"가 아니다.** `new Book { Isbn = null, Title = null }`은 정상적으로 컴파일된다.
>
> 널 안정성은 널 가능 참조 타입(21.6절)의 몫이고, `required`는 초기화 누락의 몫이다. 둘은 직교하는 기능이며, 실무에서는 대개 **함께** 쓴다 — `public required string Name { get; init; }`.

### `[SetsRequiredMembers]`

생성자로 값을 채우는 편의도 함께 제공하고 싶다면, 그 생성자에 `[SetsRequiredMembers]`를 붙여 `required` 제약을 면제받는다.

```csharp
public class Asset
{
    public required string Name;

    public Asset() { }

    [System.Diagnostics.CodeAnalysis.SetsRequiredMembers]
    public Asset(string n) => Name = n;
}
```

```csharp
Asset a1 = new Asset { Name = "House" };    // OK
Asset a2 = new Asset("House");              // OK
Asset a3 = new Asset();                     // 오류 — Name을 안 채웠다
```

컴파일러는 생성자 본문을 검사해 정말로 채웠는지 확인하지 **않는다.** 이 특성은 개발자의 **약속**이다. 그래서 특성만 붙이고 실제로는 대입하지 않으면, 컴파일러는 통과시키고 런타임에 `null`인 상태로 살아남는다.

### 컴파일 결과와 요구 사항

`required`는 컴파일러 기능이지만 메타데이터에 흔적을 남긴다.

| 대상 | 붙는 것 |
|---|---|
| `required` 멤버 | `System.Runtime.CompilerServices.RequiredMemberAttribute` |
| 해당 타입 | `RequiredMemberAttribute` + `CompilerFeatureRequiredAttribute("RequiredMembers")` |
| 해당 타입 | 옛 컴파일러를 막기 위한 `[Obsolete]`(오류 수준) |

마지막 줄이 영리한 부분이다. `required`를 모르는 옛 컴파일러는 `CompilerFeatureRequired`도 모르므로 제약을 무시하고 통과시킬 것이다. 그래서 컴파일러가 **오류로 처리되는 `[Obsolete]`** 를 함께 붙여, 옛 컴파일러가 그 타입을 아예 쓰지 못하게 막는다. 최신 컴파일러는 이 `[Obsolete]`를 알아보고 무시한다.

이 특성들 때문에 `required`는 **.NET 7 이상**이 필요하다(특성 타입이 BCL에 그때 들어왔다). 그 이전 대상 프레임워크에서는 특성을 직접 선언해 폴리필하는 방법이 알려져 있지만, 표준 경로는 아니다.

> **💡 `required` + `init`이 현재의 표준 불변 타입 관용구다**
>
> ```csharp
> public class Order
> {
>     public required string CustomerId { get; init; }
>     public required DateOnly Date     { get; init; }
>     public string? Note               { get; init; }
> }
>
> var o = new Order { CustomerId = "C-1", Date = DateOnly.FromDateTime(DateTime.Today) };
> ```
>
> 이 조합이 주는 것: 생성자 없이도 **누락이 컴파일 오류**, 생성 후 **변경 불가**, 프로퍼티를 추가해도 **바이너리 호환성 유지**(생성자 매개변수 추가와 달리). 레코드(19장)와도 그대로 조합된다.
>
> 다만 대가가 있다. **`required` 멤버를 추가하는 것은 호출자를 깨는 변경**이다 — 기존의 모든 객체 초기화자가 컴파일 오류가 된다. 라이브러리 v2에서 `required` 프로퍼티를 추가할 수는 없다고 보는 것이 맞다.

> **⚠️ 리플렉션·역직렬화는 `required`를 강제하지 않는다**
>
> `required`는 **C# 컴파일러가 호출부에서 검사하는 규칙**이다. CLR은 아무것도 강제하지 않는다. 따라서 `Activator.CreateInstance`, `RuntimeHelpers.GetUninitializedObject`, 역직렬화기를 통해 만들어진 인스턴스는 `required` 멤버가 비어 있을 수 있다(13.3절의 ⚠️와 같은 이유다).
>
> `System.Text.Json`은 `required` 멤버가 JSON에 없으면 예외를 던지도록 동작하지만(※.NET 8), 그것은 그 라이브러리가 메타데이터를 읽고 스스로 검사하기 때문이지 언어가 보장하는 것이 아니다.

## 13.14 부분 타입·부분 메서드와 소스 생성기의 접점

### 부분 타입

**부분 타입**(partial type)은 하나의 타입 정의를 여러 조각으로 나눈다. 대개 파일을 나누는 데 쓴다. 전형적인 시나리오는 **한쪽이 자동 생성 코드이고 다른 쪽이 손으로 쓴 코드**인 경우다.

```csharp
// PaymentFormGen.cs — 자동 생성
partial class PaymentForm { /* ... */ }

// PaymentForm.cs — 직접 작성
partial class PaymentForm { /* ... */ }
```

규칙은 다음과 같다.

| 규칙 | 위반 시 |
|---|---|
| 모든 조각에 `partial` 키워드가 있어야 한다 | `error CS0260` |
| 조각들은 같은 어셈블리·같은 네임스페이스·같은 이름·같은 arity | 별개의 타입이 된다 |
| 충돌하는 멤버를 둘 수 없다 (같은 시그니처의 생성자 등) | 컴파일 오류 |
| 기반 클래스는 한 조각에만 적거나, 적는다면 전부 같아야 한다 | 컴파일 오류 |
| 인터페이스는 조각마다 독립적으로 추가할 수 있다 (합집합) | — |

**부분 타입은 전적으로 컴파일러가 해소한다.** CLR은 부분 타입을 모르며, 언제나 완성된 타입 정의만 본다. 그래서 모든 조각이 컴파일 시점에 존재해야 하고, 같은 어셈블리 안에 있어야 하며, 같은 언어로 작성돼야 한다.

> **⚠️ 조각들 사이의 필드 초기화 순서는 보장되지 않는다**
>
> 한 파일 안에서는 선언 순서대로 초기화되지만(13.4절), **서로 다른 부분 선언 사이의 순서는 컴파일러가 아무것도 보장하지 않는다.** 파일 이름 순서에 의존하는 것처럼 보여도 그것은 구현 세부일 뿐이다.
>
> 초기화 순서에 의존하는 코드를 부분 타입에 나눠 두면, 파일 하나의 이름을 바꾸는 것만으로 깨질 수 있다. 서로 의존하는 초기화는 **생성자 본문** 한 곳에 모아라.

> **📌 최상위 문도 부분 클래스다**
>
> 최상위 문은 컴파일러가 만드는 `partial class Program`의 본문이 된다. 그래서 다른 파일에 `public partial class Program { public static string SayHello() => "Hello"; }`를 두고 최상위 문에서 `SayHello()`를 부를 수 있다. 최상위 문 안의 메서드는 지역 메서드가 되어 오버로드할 수 없으므로(13.2절), 오버로드가 필요할 때 쓰는 우회로이기도 하다.

### 부분 메서드

부분 타입은 **부분 메서드**를 담을 수 있다. 자동 생성 코드가 "여기에 끼어들 수 있다"는 지점을 열어 두는 장치다.

```csharp
partial class PaymentForm            // 자동 생성 파일
{
    partial void ValidatePayment(decimal amount);
}

partial class PaymentForm            // 직접 작성 파일
{
    partial void ValidatePayment(decimal amount)
    {
        if (amount > 100) { /* ... */ }
    }
}
```

부분 메서드는 **정의**와 **구현** 두 부분으로 이루어진다. 구현이 제공되지 않으면 **정의도, 그것을 호출하는 코드도 통째로 컴파일에서 사라진다.** 그래서 코드 생성기는 훅을 마음껏 뿌려 놓아도 코드가 부풀지 않는다.

이 "사라질 수 있음" 때문에 제약이 붙는다 — 부분 메서드는 반환 타입이 `void`여야 하고, 암시적으로 `private`이며, `out` 매개변수를 가질 수 없다.

### 확장 부분 메서드 ※C# 9

**확장 부분 메서드**(extended partial method)는 반대 방향을 위한 것이다. 개발자가 훅을 **정의**하고 코드 생성기가 **구현**하는 시나리오다.

접근 한정자로 시작하면 확장 부분 메서드가 된다.

```csharp
public partial class Test
{
    public  partial void M1();      // 확장 부분 메서드
    private partial void M2();      // 확장 부분 메서드
}
```

접근 한정자의 존재가 접근성만 바꾸는 것이 아니라 **컴파일러의 취급 자체를 바꾼다.** 확장 부분 메서드는 **반드시 구현이 있어야 하고**(사라지지 않는다), 그래서 임의의 반환 타입과 `out` 매개변수를 가질 수 있다.

```csharp
public partial class Test
{
    public   partial bool IsValid(string identifier);
    internal partial bool TryParse(string number, out int result);
}
```

| | 일반 부분 메서드 | 확장 부분 메서드 ※C# 9 |
|---|---|---|
| 접근 한정자 | 불가(암시적 `private`) | **필수** |
| 구현 없을 때 | 호출부까지 사라진다 | **컴파일 오류** |
| 반환 타입 | `void`만 | 아무거나 |
| `out` 매개변수 | 불가 | 가능 |

### 소스 생성기와의 접점

**소스 생성기**(source generator)는 컴파일 과정에 개입해 코드를 만들어 넣는 Roslyn 기능이다. 확장 부분 메서드는 정확히 이 시나리오를 위해 도입됐다. BCL 자체가 이 방식을 쓴다.

```csharp
// 정규식 소스 생성기 ※.NET 7
public partial class Parser
{
    [GeneratedRegex(@"\d{4}-\d{2}-\d{2}")]
    private static partial Regex DateRegex();
}
```

`DateRegex()`의 본문은 개발자가 쓰지 않는다. 소스 생성기가 컴파일 시점에 **완전히 펼쳐진 정규식 엔진 코드**를 담은 구현을 만들어 넣는다. 런타임 해석이 사라지므로 빠르고, 트리밍·AOT에서도 안전하다.

같은 패턴이 여러 곳에 쓰인다.

| 기능 | 형태 | 얻는 것 |
|---|---|---|
| `[GeneratedRegex]` ※.NET 7 | `partial` 메서드 | 런타임 정규식 컴파일 제거 |
| `System.Text.Json` 소스 생성 | `partial class` 컨텍스트 | 리플렉션 없는 직렬화, AOT 호환 |
| `[LibraryImport]` ※.NET 7 | `partial` 메서드 | 마샬링 코드를 컴파일 시점에 생성 |
| 로깅 소스 생성기 | `partial` 메서드 | 박싱·문자열 조합 제거 |

**부분 타입/부분 메서드는 소스 생성기가 코드를 붙일 수 있는 유일한 공식 접합면이다.** 소스 생성기는 기존 코드를 수정할 수 없고 **추가만** 할 수 있으므로, 개발자가 `partial`로 자리를 열어 주어야 한다.

※C# 13부터는 **부분 프로퍼티와 부분 인덱서**도 지원되어 접합면이 넓어졌다. 소스 생성기의 작성 방법과 진단 흐름은 57.15절, 부분 클래스에 훅을 설계하는 관점은 78.11절에서 다룬다.

## 13.15 `nameof` 연산자

`nameof` 연산자는 심볼(타입, 멤버, 변수 등)의 이름을 문자열로 돌려준다.

```csharp
int count = 123;
string name = nameof(count);        // "count"
```

문자열 리터럴을 직접 쓰는 것과 무엇이 다른가? **정적 타입 검사**다. 심볼이 존재하지 않으면 컴파일 오류이고, IDE가 심볼 참조로 인식하므로 **이름을 바꾸면 `nameof` 안의 이름도 함께 바뀐다.**

타입 멤버의 이름을 얻으려면 타입까지 적는다. 정적 멤버와 인스턴스 멤버 모두 된다.

```csharp
string name = nameof(StringBuilder.Length);     // "Length"
```

결과는 `"Length"`이지 `"StringBuilder.Length"`가 아니다. 전체를 원하면 이어 붙인다.

```csharp
nameof(StringBuilder) + "." + nameof(StringBuilder.Length);
```

### 컴파일 결과 — 비용이 정확히 0이다

`nameof`는 컴파일 시점에 **문자열 리터럴로 치환**된다. IL에는 `ldstr` 한 줄만 남는다.

```il
IL_0000:  ldstr      "count"
```

리플렉션도, 문자열 조합도, 런타임 계산도 없다. 문자열 리터럴은 인턴 풀에 있으므로 할당도 발생하지 않는다(8장).

### 쓰는 자리

| 자리 | 예 |
|---|---|
| 인수 검증 | `throw new ArgumentNullException(nameof(name))` |
| 속성 변경 알림 | `PropertyChanged?.Invoke(this, new(nameof(Title)))` |
| 로깅·진단 | `logger.LogError("{Member} 실패", nameof(Process))` |
| 특성 인수 | `[Display(Name = nameof(Resources.Title))]` |
| 데이터 접근 | `builder.Property(nameof(Order.Total))` |

> **⚠️ `nameof`는 네임스페이스도, 선언 타입도 붙여 주지 않는다**
>
> `nameof(System.Collections.Generic.List<int>)`의 결과는 `"List"`다. **마지막 식별자만** 돌아온다. 제네릭 인수도 사라진다.
>
> 완전 정규화된 이름이 필요하면 `typeof(T).FullName`을 써야 하는데, 이쪽은 **런타임 비용이 있고 트리밍에 영향을 받는다**(57.14절). 로그 메시지 안의 타입 이름 하나 때문에 리플렉션을 끌어들이지 않도록 주의할 것.

> **📌 매개변수 이름을 특성에서 쓸 수 있다 ※C# 11**
>
> C# 11부터 `nameof`의 범위가 넓어져, **메서드나 매개변수에 붙인 특성 안에서 그 메서드의 매개변수 이름**을 참조할 수 있다.
>
> ```csharp
> [MemberNotNullWhen(true, nameof(result))]
> public bool TryGet(out string? result) { /* ... */ }
> ```
>
> 그 이전에는 특성 안에서 매개변수가 범위에 없어 문자열 리터럴을 써야 했다. 널 관련 특성(21.9절)과 함께 쓸 때 특히 유용하다.

> **💡 `nameof`보다 나은 것이 있는 경우**
>
> 인수 검증에서는 ※.NET 6의 `ArgumentNullException.ThrowIfNull(name)` 쪽이 더 짧다. 이 메서드는 `[CallerArgumentExpression]`(20.11절)으로 **호출부에 적힌 식 자체**를 문자열로 받아 가므로 `nameof`를 쓸 필요조차 없다. 상세는 21.10절이다.
>
> 반면 **문자열이 실제 데이터로 쓰이는 자리**(설정 키, 직렬화 이름, DB 컬럼명)에 `nameof`를 쓰는 것은 위험하다. 멤버 이름을 리팩터링하는 순간 외부 계약이 조용히 바뀌기 때문이다. `nameof`는 **코드 안에서만 의미를 갖는 이름**에 쓰는 것이 맞다.

## 13.16 파이널라이저 선언 (동작은 34장)

**파이널라이저**(finalizer)는 참조되지 않는 객체의 메모리를 가비지 컬렉터가 회수하기 **전에** 실행되는, 클래스에만 허용되는 메서드다. 문법은 클래스 이름 앞에 `~`를 붙인다.

```csharp
class Class1
{
    ~Class1()
    {
        // ...
    }
}
```

한 문장이면 식 본문으로 쓸 수 있다.

```csharp
~Class1() => Console.WriteLine("Finalizing");
```

### 컴파일 결과

이것은 `Object`의 `Finalize` 메서드를 재정의하는 C# 문법이며, 컴파일러가 다음 형태로 펼친다.

```csharp
protected override void Finalize()
{
    try
    {
        // ~Class1()의 본문
    }
    finally
    {
        base.Finalize();
    }
}
```

`try`/`finally`로 감싸는 이유는 **본문에서 예외가 나더라도 기반 클래스의 파이널라이저가 반드시 실행되게** 하기 위해서다.

문법 규칙은 다음과 같다.

| 규칙 | 비고 |
|---|---|
| 클래스에만 쓸 수 있다 | 구조체에는 파이널라이저가 없다 |
| 클래스당 하나 | 오버로드 불가 |
| 매개변수 없음, 반환 타입 없음 | — |
| 접근 한정자를 붙일 수 없다 | 실제로는 `protected override` |
| 직접 호출할 수 없다 | `Finalize()`를 직접 부르는 것도 금지 |
| 상속되지 않는다 | 각 클래스가 자기 것을 선언한다(체인은 위 `finally`가 만든다) |

> **⚠️ 파이널라이저는 "혹시 몰라서" 다는 것이 아니다**
>
> 파이널라이저가 있는 객체는 **할당될 때 파이널라이제이션 큐에 등록되고, 수집될 때 최소 두 번의 GC를 거쳐야 회수된다.** 세대 승격까지 겹치면 수명이 크게 늘어난다. 실행 시점도, 실행 여부도, 실행 스레드도 보장되지 않는다.
>
> 실무 지침은 명확하다.
>
> - 관리 리소스만 다루는 타입에는 **파이널라이저를 쓰지 않는다.**
> - 비관리 리소스를 직접 잡는 극소수의 타입에만 쓰되, 그마저도 **`SafeHandle`**(33.7절)로 대체하는 것이 현재의 정답이다.
> - 파이널라이저를 두었다면 `Dispose`에서 `GC.SuppressFinalize(this)`를 불러 등록을 취소해야 한다(33.3절).
>
> 파이널라이저의 실제 동작(F-reachable 큐, 실행 순서, 부활, 비용 측정)은 34.2절에서, 결정적 정리 패턴 전체는 33장에서 다룬다. 이 절은 **선언 문법까지만**이다.

## 이 장의 요약

- **클래스 하나를 설계한다는 것은 "무엇을 노출하고 무엇을 감출지"를 정하는 일이다.** 필드는 `private`, 공개 상태는 프로퍼티가 기본선이며, 필드를 프로퍼티로 바꾸는 것은 바이너리 호환성을 깨는 변경이므로 처음부터 프로퍼티로 두는 편이 싸다.
- **`const`는 값이 호출부에 구워지고, `static readonly`는 필드가 남는다.** 미래에 바뀔 수 있는 값을 `const`로 노출하면 어셈블리 경계에서 옛 값이 살아남는다.
- **시그니처는 이름 + 매개변수 타입/순서 + 전달 방식이다.** 반환 타입과 `params`는 시그니처가 아니고, `ref`와 `out`은 메타데이터에서 같은 형태이므로 서로 오버로드할 수 없다.
- **필드 초기화자는 선언 순서대로, 기반 생성자보다도 먼저 실행된다.** 생성자 본문은 그 반대로 기반에서 파생 방향으로 실행된다. 이 비대칭이 "생성자에서 가상 메서드를 부르지 마라"의 근거다. `this(...)`를 쓰는 생성자는 필드 초기화자를 실행하지 않는다.
- **객체 초기화자는 임시 변수를 거쳐 컴파일된다.** 절반만 초기화된 객체가 변수에 남지 않는 대신, 대입은 생성자 이후에 일어나므로 생성자의 검증을 우회한다.
- **프로퍼티와 인덱서는 CLR에서 같은 것이다.** `get_X`/`set_X` 메서드 한 쌍과 메타데이터 항목 하나이며, 인덱서는 그 접근자가 매개변수를 받는 형태다. 기본 이름 `Item`은 `[DefaultMember]`로 기록된다.
- **`init`은 CLR에서 평범한 `set`이고, 차이는 `modreq(IsExternalInit)` 하나다.** 이 장치 덕분에 옛 컴파일러는 그 프로퍼티를 쓰기 가능한 것으로 착각하지 않고 아예 못 본 것으로 처리한다.
- **기본 생성자 매개변수는 필드가 아니다.** 초기화자에서만 쓰면 필드가 생기지 않고, 메서드에서 쓰면 숨은 필드로 캡처된다. 프로퍼티와 매개변수를 동시에 쓰면 값이 두 벌 저장되는 함정이 있다.
- **명시적 정적 생성자의 유무가 `beforefieldinit`을 결정한다.** 없으면 런타임이 초기화 시점을 앞당길 자유를 갖고, 있으면 시점이 정확해지는 대신 최적화가 제한된다. 정적 생성자에서 예외가 나면 그 타입은 프로세스 수명 동안 `TypeInitializationException`만 던진다.
- **`required`는 컴파일러가 호출부에서 검사하는 규칙이지 CLR의 보장이 아니다.** 리플렉션과 역직렬화는 이를 우회하며, `required`가 널 아님을 뜻하지도 않는다.

## 연습 문제

1. **초기화 순서를 눈으로 확인하라.** 기반 클래스와 파생 클래스에 각각 필드 초기화자와 생성자 본문을 두고, 각 지점에서 `Console.WriteLine`을 출력하도록 만들어라. 출력 순서가 13.4절의 다이어그램과 일치하는지 확인하고, 파생 생성자를 `: this(...)`로 바꿨을 때 필드 초기화자가 몇 번 실행되는지 세어 보라.
2. **`beforefieldinit`을 직접 관찰하라.** 정적 필드 초기화자만 있는 클래스와, 여기에 빈 정적 생성자(`static Foo() { }`)를 추가한 클래스를 각각 컴파일해 ildasm(또는 SharpLab, 3.8절)으로 `.class` 줄을 비교하라. `beforefieldinit` 플래그가 사라지는 것을 확인하고, 정적 필드 접근 시점에 무엇이 출력되는지 두 버전에서 비교하라.
3. **`TypeInitializationException`을 만들어 보라.** 정적 생성자에서 예외를 던지는 클래스를 만들고, 그 타입의 정적 멤버를 `try`/`catch`로 감싸 **두 번** 접근하라. 두 번째 접근에서도 예외가 나오는지, `InnerException`에 무엇이 들어 있는지 확인하라.
4. **백킹 필드의 이름을 확인하라.** 자동 구현 프로퍼티가 있는 클래스를 리플렉션으로 조회해(`typeof(T).GetFields(BindingFlags.NonPublic | BindingFlags.Instance)`) 필드 이름을 출력하라. `<Name>k__BackingField` 형태가 나오는지, 그 필드에 `[CompilerGenerated]`가 붙어 있는지 확인하라.
5. **`init`을 리플렉션으로 판별하라.** 13.8절의 `IsInitOnly` 메서드를 그대로 구현하고, `set` 프로퍼티와 `init` 프로퍼티를 각각 넘겨 결과가 다른지 확인하라.
6. **기본 생성자의 이중 저장을 재현하라.** 13.10절의 ⚠️ 예제(프로퍼티와 매개변수를 동시에 쓰는 형태)를 그대로 실행해 `Alice`가 출력되는 것을 확인하라. 그다음 필드를 같은 이름으로 선언해 매개변수를 가리는 방식으로 고쳐, `Bob`이 나오게 만들어라.
7. **객체 초기화자가 생성자 검증을 우회하는 것을 확인하라.** 생성자에서 모든 필드가 유효한지 검사하는 클래스를 만들고, 객체 초기화자로 값을 설정해 검증을 통과한 뒤 상태가 깨지는 시나리오를 만들어라. 그다음 `required` + `init`으로 바꿔 같은 코드가 컴파일 오류가 되는 것을 확인하라.
