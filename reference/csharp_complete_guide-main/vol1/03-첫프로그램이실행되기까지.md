# 3장. 첫 프로그램이 실행되기까지

> **이 장의 위치** — 2장에서 "C#은 IL로 컴파일되고 CLR이 그것을 실행한다"고 말했다. 이 장은 그 한 문장을 파일 단위로 풀어낸다. `dotnet new`가 무엇을 만들고, `dotnet build`가 어느 폴더에 무엇을 남기고, `dotnet run`이 그중 무엇을 어떻게 실행하는지를 전부 추적한다. 그리고 **이 책에서 IL을 처음 보여주는 장**이다. 3.8절에서 SharpLab을 여는 순간부터 이 책의 나머지 81개 장이 쓰는 기본 습관이 시작된다.
>
> **선수 지식** — 1장(가이드북 사용법, 특히 1.5절과 1.6절), 2장(C#이라는 언어, .NET이라는 플랫폼)
>
> **이 장에서 다루지 않는 것** — `.csproj`의 속성 하나하나와 배포 형태는 4장에서, 어셈블리 로딩과 매니페스트의 내부는 52장에서, JIT 최적화의 실제 동작은 55장에서, IL 옵코드 전체는 56장에서 다룬다. 이 장은 **전체 경로를 한 번에 끝까지 걷는 것**이 목적이고, 각 구간의 정밀 지도는 해당 장에 있다.

## 3.1 `dotnet new / build / run`이 실제로 하는 일

### 명령 세 개로 시작한다

C# 프로그램 하나를 만들고 실행하는 데 필요한 명령은 셋뿐이다.

```bash
dotnet new console -o HelloIL
cd HelloIL
dotnet run
```

```text
Hello, World!
```

세 줄이 전부다. 그런데 이 세 줄 뒤에서 **파일 열 몇 개가 만들어지고, 컴파일러가 한 번 돌고, 네이티브 호스트가 런타임을 로드하고, JIT이 메서드를 두어 개 기계어로 바꾼다.** 이 절에서는 그중 "파일"에 해당하는 부분을 전부 추적한다. 나머지는 3.2절부터 3.6절까지 이어진다.

이 책 전체에서 쓰는 세 명령의 역할을 먼저 정리한다.

| 명령 | 하는 일 | 하지 않는 일 |
|---|---|---|
| `dotnet new <템플릿>` | 템플릿에서 파일을 복사·치환해 프로젝트를 만든다 | 컴파일하지 않는다. NuGet도 받지 않는다 |
| `dotnet restore` | 의존성 그래프를 해석하고 NuGet 패키지를 받아 `obj/`에 자산 파일을 쓴다 | 컴파일하지 않는다 |
| `dotnet build` | 복원 후 C# 컴파일러를 돌려 `obj/`에 어셈블리를 만들고 `bin/`으로 옮긴다 | 실행하지 않는다 |
| `dotnet run` | 복원·빌드 후 결과물을 실행한다 | 배포용 산출물을 만들지 않는다(`dotnet publish`의 일) |

`dotnet build`는 `dotnet restore`를 포함하고, `dotnet run`은 `dotnet build`를 포함한다. 그래서 처음부터 `dotnet run`만 쳐도 되는 것이다.

> **📌 명령이 어디서 무엇을 찾는가**
>
> `dotnet build`나 `dotnet run`을 인자 없이 치면 **현재 디렉터리에서 프로젝트 파일(`.csproj`) 또는 솔루션 파일(`.sln`)을 하나 찾는다.** 둘 이상 있으면 어느 것인지 모르겠다는 오류가 난다. 그럴 때는 경로를 명시한다.
>
> ```bash
> dotnet run --project src/HelloIL/HelloIL.csproj
> ```
>
> 솔루션 디렉터리에서 `dotnet build`를 치면 솔루션에 든 모든 프로젝트가 빌드된다. 반면 `dotnet run`은 실행할 프로젝트가 하나로 정해져야 하므로 솔루션에 대고 쓸 수 없다.

### `dotnet new`가 만드는 것 — 파일 두 개

`dotnet new console -o HelloIL`을 치면 디렉터리 `HelloIL`이 생기고 그 안에 파일이 **두 개** 생긴다.

```text
HelloIL/
├── HelloIL.csproj
└── Program.cs
```

`Program.cs`부터 보자.

```csharp
// See https://aka.ms/new-console-template for more information
Console.WriteLine("Hello, World!");
```

주석 한 줄과 코드 한 줄이다. `using System;`도 없고, `class`도 없고, `Main`도 없다. 이 두 가지가 어디로 갔는지가 **3.7절의 주제**다. 지금은 "숨어 있다"고만 알고 넘어간다.

`HelloIL.csproj`는 이렇게 생겼다.

```xml
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net8.0</TargetFramework>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
  </PropertyGroup>

</Project>

```

네 줄의 속성이 각각 무엇을 뜻하는지는 4.1절과 4.6절에서 자세히 다룬다. 이 장에서 필요한 것은 셋이다.

- `OutputType`이 `Exe`이므로 **실행 파일을 만드는 프로젝트**다. 이 값이 `Library`(생략 시 기본값)면 `.dll`만 만든다.
- `TargetFramework`가 `net8.0`이므로 **.NET 8 런타임**을 대상으로 삼는다. 이 값 하나가 참조 어셈블리 집합, 언어 버전, 실행에 필요한 런타임 버전을 전부 결정한다(4.2절, 4.5절).
- `ImplicitUsings`가 `enable`이므로 **컴파일러가 `using` 문 일곱 개를 자동으로 넣어준다.** 3.7절에서 그 파일을 직접 연다.

`.csproj`가 이렇게 짧은 것은 SDK 스타일 프로젝트이기 때문이다. 소스 파일 목록이 없는 것에 주목하라. **디렉터리 아래 모든 `.cs` 파일이 자동으로 포함된다.** 파일을 추가할 때 프로젝트 파일을 고칠 필요가 없다는 뜻이다.

> **⚠️ `dotnet new`는 아직 아무것도 컴파일하지 않았다**
>
> 이 시점에 `bin`도 `obj`도 없다. 그런데 IDE에서 프로젝트를 열면 곧바로 IntelliSense가 동작하고 오류가 표시된다. 그건 IDE가 **백그라운드에서 복원과 부분 컴파일을 돌리기 때문**이지, `dotnet new`가 한 일이 아니다.
>
> 이 구분이 중요한 이유는 CI 파이프라인에서다. 소스만 체크아웃한 상태에서 테스트를 돌리려면 반드시 복원이 선행되어야 한다. `bin`과 `obj`는 소스 관리에 넣지 않는다(넣으면 안 된다).

### `dotnet build`가 만드는 것 — `obj/`

`dotnet build`를 치면 두 개의 폴더가 생긴다. **`obj/`는 컴파일러의 작업장**이고 **`bin/`은 결과물 진열장**이다.

`obj/` 먼저 보자. 프로젝트 루트에 바로 놓이는 파일들은 **복원(restore) 단계의 산출물**이다.

| `obj/` 아래 파일 | 무엇인가 | 만든 단계 |
|---|---|---|
| `project.assets.json` | 해석이 끝난 의존성 그래프 전체. 어떤 패키지의 어떤 파일을 참조할지 확정한 목록 | 복원 |
| `project.nuget.cache` | 복원 결과 캐시. 입력이 안 바뀌었으면 복원을 건너뛰기 위한 표식 | 복원 |
| `HelloIL.csproj.nuget.g.props` | 복원이 생성해 빌드에 주입하는 MSBuild 속성 | 복원 |
| `HelloIL.csproj.nuget.g.targets` | 복원이 생성해 빌드에 주입하는 MSBuild 타깃 | 복원 |
| `HelloIL.csproj.nuget.dgspec.json` | 의존성 그래프 사양(dependency graph spec) 스냅숏 | 복원 |
| `Debug/net8.0/HelloIL.GlobalUsings.g.cs` | 암시적 `using`이 실제로 만들어낸 **C# 소스 파일** (3.7절) | 빌드 |
| `Debug/net8.0/HelloIL.AssemblyInfo.cs` | `AssemblyVersion`, `AssemblyCompany` 등 어셈블리 특성을 담은 생성 소스 | 빌드 |
| `Debug/net8.0/HelloIL.GeneratedMSBuildEditorConfig.editorconfig` | 분석기에 전달할 빌드 속성을 담은 생성 설정 | 빌드 |
| `Debug/net8.0/HelloIL.dll` | **컴파일러가 방금 만든 어셈블리 원본** | 빌드 |
| `Debug/net8.0/HelloIL.pdb` | 디버그 심볼(포터블 PDB) | 빌드 |
| `Debug/net8.0/ref/HelloIL.dll` | 참조 어셈블리 — 공개 API 표면만 담고 메서드 본문이 없다(4.4절) | 빌드 |
| `Debug/net8.0/*.cache`, `*.FileListAbsolute.txt` | 증분 빌드용 입력 해시와 산출 파일 목록 | 빌드 |

여기서 놀랄 만한 사실이 두 가지 있다.

**첫째, 어셈블리 원본은 `bin`이 아니라 `obj`에 만들어진다.** `bin/Debug/net8.0/HelloIL.dll`은 `obj/Debug/net8.0/HelloIL.dll`을 **복사한 것**이다. 이 사실은 "빌드는 성공했는데 `bin`에 반영이 안 된다"는 증상을 만날 때 진단 포인트가 된다.

**둘째, `obj` 안에 C# 소스 파일이 있다.** `HelloIL.GlobalUsings.g.cs`와 `HelloIL.AssemblyInfo.cs`는 사람이 쓰지 않았지만 **컴파일 입력으로 들어가는 진짜 소스**다. 열어보면 이렇게 되어 있다.

```csharp
// <auto-generated/>
global using global::System;
global using global::System.Collections.Generic;
global using global::System.IO;
global using global::System.Linq;
global using global::System.Net.Http;
global using global::System.Threading;
global using global::System.Threading.Tasks;
```

`Program.cs`에 `using System;`이 없는데도 `Console.WriteLine`이 컴파일되는 이유가 여기 있다. 자세한 것은 3.7절에서 판다.

> **📌 `.g.cs`와 `.g.props`의 `g`**
>
> `g`는 generated의 약자다. `.g.cs`, `.g.props`, `.g.targets`처럼 중간에 `g`가 들어간 파일은 **도구가 만든 것이니 손대지 말라**는 관행적 표시다. 고쳐도 다음 빌드에 덮어써진다.
>
> 소스 생성기(source generator)가 만드는 파일도 같은 규칙을 따른다. 다만 소스 생성기 출력은 기본적으로 디스크에 남지 않고 메모리에만 존재한다. 보고 싶으면 `<EmitCompilerGeneratedFiles>true</EmitCompilerGeneratedFiles>`를 켜면 `obj/Debug/net8.0/generated/` 아래에 떨어진다. 소스 생성기 자체는 57.15절에서 다룬다.

### `dotnet build`가 만드는 것 — `bin/`

`bin/Debug/net8.0/`에는 **실행에 필요한 것만** 남는다. 파일 다섯 개다.

```text
bin/Debug/net8.0/
├── HelloIL.dll               ← 어셈블리 (IL + 메타데이터)
├── HelloIL.exe               ← 네이티브 실행 런처 (Windows). Linux/macOS에서는 HelloIL
├── HelloIL.pdb               ← 디버그 심볼
├── HelloIL.deps.json         ← 의존성 목록
└── HelloIL.runtimeconfig.json ← 어느 런타임으로 실행할지
```

| 파일 | 역할 | 없으면 |
|---|---|---|
| `HelloIL.dll` | **어셈블리 본체.** IL 코드와 메타데이터가 전부 여기 있다 | 실행 불가 |
| `HelloIL.exe` | **앱호스트(apphost).** 런타임을 찾아 로드하고 `.dll`을 넘기는 네이티브 실행 파일 | `dotnet HelloIL.dll`로는 여전히 실행 가능 |
| `HelloIL.pdb` | 스택 트레이스의 파일명·줄 번호, 디버거의 지역 변수 매핑 | 실행은 되지만 스택 트레이스에 줄 번호가 안 나온다 |
| `HelloIL.deps.json` | 이 앱이 쓰는 어셈블리와 네이티브 라이브러리의 목록 | 의존성 해석 실패 가능(52.15절) |
| `HelloIL.runtimeconfig.json` | 대상 런타임 이름과 버전, 런타임 설정 | **실행 불가.** 호스트가 어느 런타임을 로드할지 모른다 |

`HelloIL.runtimeconfig.json`을 열면 이렇게 되어 있다.

```json
{
  "runtimeOptions": {
    "tfm": "net8.0",
    "framework": {
      "name": "Microsoft.NETCore.App",
      "version": "8.0.0"
    }
  }
}
```

이 파일이 3.5절에서 아주 중요해진다. **호스트는 이 파일을 읽고 나서야 어느 CLR을 로드할지 안다.**

> **⚠️ `.exe`를 디컴파일러로 열면 아무것도 안 나온다**
>
> .NET(모던 .NET)에서 `HelloIL.exe`는 **어셈블리가 아니다.** 관리 코드가 한 줄도 없는 네이티브 실행 파일이고, 하는 일은 "옆에 있는 같은 이름의 `.dll`을 찾아 런타임에 넘긴다"뿐이다. 이것을 앱호스트라고 부른다.
>
> ILSpy나 `ildasm`으로 열어야 하는 것은 항상 **`.dll` 쪽**이다. 이 함정은 .NET Framework 경험자가 특히 자주 밟는다. .NET Framework에서는 `.exe` 자체가 어셈블리였다(2.3절, 52.1절).
>
> 앱호스트가 필요 없으면 `<UseAppHost>false</UseAppHost>`로 끌 수 있다. 그러면 `bin`에 `.exe`가 안 생기고 `dotnet HelloIL.dll`로만 실행한다.

### `dotnet run`이 하는 일

`dotnet run`은 세 단계다.

1. **복원** — `--no-restore`로 건너뛸 수 있다.
2. **빌드** — `--no-build`로 건너뛸 수 있다(이 경우 복원도 건너뛴다).
3. **실행** — `bin/<구성>/<TFM>/` 아래의 앱호스트를 실행한다.

세 번째 단계는 사실상 다음과 같다.

```bash
# dotnet run이 내부적으로 하는 일과 거의 같다
dotnet build
./bin/Debug/net8.0/HelloIL          # Windows에서는 bin\Debug\net8.0\HelloIL.exe
```

프로그램에 인자를 넘기려면 `--`로 구분한다. 이걸 모르면 `dotnet run`이 자기 옵션으로 오해한다.

```bash
dotnet run -- --verbose input.txt
```

`--` 앞의 것은 `dotnet run`의 옵션, 뒤의 것은 **프로그램의 `args`로 들어가는 것**이다.

> **⚠️ `dotnet run`의 기본 구성은 Debug다**
>
> 아무 옵션도 안 주면 `-c Debug`로 동작한다. Debug 구성에서는 컴파일러 최적화가 꺼지고(3.2절), IL에 `nop`이 잔뜩 들어가고, JIT도 최적화를 줄인다.
>
> 그래서 **성능을 재는 모든 작업은 `-c Release`가 필수다.**
>
> ```bash
> dotnet run -c Release
> ```
>
> 이 규칙을 어긴 측정은 전부 버려야 한다(1.7절, 67.4절). 그리고 IL을 눈으로 확인할 때도 어느 구성인지 항상 의식해야 한다. Debug IL을 보고 "컴파일러가 이상한 걸 만들었다"고 판단하는 실수가 이 책 독자에게 가장 흔한 초기 오류다.

> **💡 빌드가 무엇을 했는지 정확히 보고 싶을 때**
>
> MSBuild는 자기가 실행한 모든 타깃과 그 입출력을 이진 로그로 남길 수 있다.
>
> ```bash
> dotnet build -bl
> ```
>
> 이 명령은 `msbuild.binlog`를 만든다. MSBuild Structured Log Viewer(무료)로 열면 **C# 컴파일러에 실제로 넘어간 명령줄 인자 전체**를 볼 수 있다. 어떤 참조 어셈블리가 들어갔는지, `-optimize+`가 켜졌는지, 어떤 분석기가 실행됐는지가 전부 나온다.
>
> "왜 이 패키지가 참조되지?", "왜 이 경고가 안 꺼지지?" 같은 질문은 추측하지 말고 이 로그를 열어야 한다. 4.7절과 4.8절에서 다시 쓴다.

### 정리 — 여기까지의 그림

`dotnet run` 한 번에 벌어지는 파일 수준의 일은 이렇다.

```text
Program.cs  +  HelloIL.csproj
      │
      │  dotnet restore
      ↓
obj/project.assets.json  (의존성 확정)
      │
      │  dotnet build
      │    ├─ 생성 소스 추가 (GlobalUsings.g.cs, AssemblyInfo.cs)
      │    ├─ C# 컴파일러 실행 → obj/Debug/net8.0/HelloIL.dll
      │    └─ bin/Debug/net8.0/ 로 복사 + 앱호스트·설정 파일 생성
      ↓
bin/Debug/net8.0/HelloIL.dll  +  .exe  +  .runtimeconfig.json  +  .deps.json
      │
      │  dotnet run (실행 단계)
      ↓
   앱호스트 → 런타임 로드 → Main 호출 → JIT → "Hello, World!"
```

이 그림의 가운데 화살표 — "C# 컴파일러 실행" — 안에서 무슨 일이 벌어지는지가 다음 절이다.

## 3.2 소스 → Roslyn 컴파일러 → IL + 메타데이터

### 컴파일러의 이름은 Roslyn이다

C# 컴파일러의 프로젝트 이름은 **Roslyn**이다. C# 6.0(2015년)부터 쓰인 세대의 컴파일러이고, **C#으로 작성된 C# 컴파일러**다. 오픈 소스이고 소스는 공개되어 있다.

Roslyn 이전 컴파일러와 결정적으로 다른 점은 **컴파일 파이프라인 전체를 라이브러리로 노출한다**는 것이다. 구문 트리를 파싱하고, 의미 분석 결과를 조회하고, 코드를 고쳐 쓰는 일을 외부 코드가 할 수 있다. IDE의 리팩터링, 코드 분석기(analyzer), 소스 생성기가 전부 이 API 위에 서 있다. 이 API 자체는 5.8절에서 소개한다.

디스크 위에서 컴파일러의 실체는 SDK 안의 `csc.dll`이다. `dotnet build`는 이것을 직접 부르지 않고 **컴파일러 서버**(`VBCSCompiler`)를 통해 호출한다. 서버 프로세스가 살아 있으면서 참조 어셈블리 메타데이터를 캐시해 두기 때문에 두 번째 빌드부터 눈에 띄게 빨라진다.

> **📌 컴파일러 서버가 남아 있는 것은 정상이다**
>
> 빌드가 끝난 뒤에도 `VBCSCompiler` 프로세스가 몇 분간 살아 있는 것을 보고 놀라는 경우가 있다. 정상이다. 유휴 시간이 지나면 스스로 종료한다.
>
> CI에서 이 프로세스가 문제가 되면(컨테이너가 안 끝난다든가) 끄면 된다.
>
> ```bash
> dotnet build /p:UseSharedCompilation=false
> ```
>
> 대신 빌드는 느려진다. 로컬 개발에서는 끄지 않는 편이 낫다.

### 파이프라인 다섯 단계

소스 텍스트가 어셈블리가 되기까지 Roslyn은 다섯 단계를 거친다.

```text
  Program.cs          GlobalUsings.g.cs      참조 어셈블리
  (사람이 쓴 소스)     (SDK가 만든 소스)      (System.Runtime.dll 등)
        │                    │                      │
        └────────────┬───────┘                      │
                     ↓                              │
        ┌────────────────────────┐                  │
        │  1. 어휘 분석 · 구문 분석 │                  │
        │     (lexing / parsing)  │                  │
        └────────────┬───────────┘                  │
                     ↓                              │
              구문 트리 (Syntax Tree)                 │
                     │                              │
                     ↓                              ↓
        ┌────────────────────────────────────────────┐
        │  2. 선언 수집 · 심볼 테이블 구성              │
        │  3. 바인딩 · 의미 분석 (타입 검사, 오버로드    │
        │     해결, 널 가능성 분석, 흐름 분석)          │
        └────────────┬───────────────────────────────┘
                     ↓
              바인딩된 트리 + 진단(오류·경고)
                     │
                     ↓
        ┌────────────────────────┐
        │  4. 낮추기 (lowering)   │  ← 문법 설탕을 기본 구성 요소로 풀어낸다
        └────────────┬───────────┘
                     ↓
        ┌────────────────────────┐
        │  5. 방출 (emit)         │
        └────────────┬───────────┘
                     ↓
        ┌───────────────────────────────────────┐
        │  HelloIL.dll                          │
        │  ├─ IL 코드          (메서드 본문)      │
        │  ├─ 메타데이터        (타입·멤버 정의)   │
        │  └─ 매니페스트        (어셈블리 신원)    │
        └───────────────────────────────────────┘
                     +
              HelloIL.pdb  (소스 ↔ IL 매핑)
```

각 단계가 무엇을 하는지 표로 정리한다.

| 단계 | 입력 | 출력 | 여기서 나는 오류의 예 |
|---|---|---|---|
| **1. 파싱** | 소스 텍스트 | 구문 트리 | `; 이 필요합니다` — 문법이 안 맞는 경우 |
| **2. 선언** | 구문 트리 | 심볼 테이블(네임스페이스·타입·멤버 목록) | 같은 이름의 멤버가 이미 정의됨 |
| **3. 바인딩** | 심볼 테이블 + 참조 어셈블리 메타데이터 | 타입이 확정된 트리 + 진단 | 형식을 찾을 수 없음, 오버로드 모호, 널 가능성 경고 |
| **4. 낮추기** | 바인딩된 트리 | 단순화된 트리 | (오류가 나지 않는다 — 이미 검증이 끝났다) |
| **5. 방출** | 단순화된 트리 | IL + 메타데이터 + PDB | 파일 쓰기 실패 정도 |

이 중 **4단계 낮추기가 이 책에서 가장 자주 등장하는 개념**이다.

### 낮추기 — 이 책의 절반이 여기 있다

C#의 편리한 문법 상당수는 IL에 대응하는 명령이 없다. IL에는 `foreach`도 없고, `using` 문도 없고, `async`도 없고, 람다도 없고, 프로퍼티도 없다. 그래서 컴파일러는 이것들을 **IL이 표현할 수 있는 형태로 다시 쓴다.** 이 재작성을 낮추기(lowering)라고 부른다.

몇 가지 예를 미리 보여준다. 지금 이해할 필요는 없다. **"C# 문법의 상당수는 컴파일 시점에 다른 코드로 바뀐다"**는 사실 하나만 가져가면 된다.

| 당신이 쓴 것 | 컴파일러가 낮춘 것 | 다루는 절 |
|---|---|---|
| `foreach (var x in list)` | `GetEnumerator()` / `MoveNext()` / `Current` 호출 루프 + `try-finally` | 28.1절 |
| `using (var f = ...)` | `try { ... } finally { f?.Dispose(); }` | 33.10절 |
| `lock (o) { ... }` | `Monitor.Enter` / `Monitor.Exit` + `try-finally` | 48.5절 |
| `x switch { ... }` | 분기 트리 또는 점프 테이블 | 77.15절 |
| `s = $"a={a}"` | 문자열 연결 호출 또는 보간 핸들러 호출 | 35.7절 |
| 람다 / 클로저 | 컴파일러가 만든 클래스 + 델리게이트 생성 | 26.10절 |
| `yield return` | `IEnumerator<T>`를 구현하는 상태 기계 클래스 | 28.4절 |
| `async` / `await` | `IAsyncStateMachine`을 구현하는 상태 기계 + 빌더 | 47.7절 |
| 자동 프로퍼티 | 백업 필드 + `get_X()` / `set_X()` 메서드 | 13.8절 |
| `record` | `Equals`, `GetHashCode`, `ToString`, `Clone` 생성 | 19.3절 |

이 표의 오른쪽 열을 **눈으로 확인하는 방법**이 3.8절의 SharpLab이다. 그리고 이 표의 각 행이 이 책의 한 절씩을 차지한다. **1.3절이 말한 "4단 원칙"의 2단이 바로 이 낮추기 결과를 읽는 일이다.**

> **⚠️ 낮추기 결과는 규격이 아니다**
>
> 컴파일러가 `foreach`를 무엇으로 바꾸는지는 **C# 언어 명세가 정해둔 의미론을 지키는 한** 컴파일러 구현의 자유다. 실제로 Roslyn은 버전이 올라가면서 낮추기 방식을 여러 번 바꿨다.
>
> 그래서 이 책이 보여주는 IL은 **"이 버전의 컴파일러가 이렇게 했다"**는 관찰이지 "항상 이렇게 된다"는 보장이 아니다. 두 가지를 구분해야 한다.
>
> - **지켜지는 것**: 의미론. `using` 블록을 벗어날 때 `Dispose()`가 불린다는 사실은 명세가 보장한다.
> - **안 지켜질 수 있는 것**: 구체적 IL 형태. 생성 클래스의 이름, 필드 개수, 옵코드 선택.
>
> 생성 클래스 이름(`<>c__DisplayClass0_0` 같은 것)에 리플렉션으로 의존하는 코드를 짜면 안 되는 이유가 이것이다.

### 방출 — IL과 메타데이터는 함께 태어난다

마지막 단계에서 컴파일러는 어셈블리 파일 하나를 쓴다. 그 안에 들어가는 것은 크게 셋이다.

- **IL 코드** — 메서드 본문. CPU에 독립적인 명령 열이다.
- **메타데이터** — 이 어셈블리가 정의한 타입·멤버의 목록, 그리고 참조하는 타입·멤버의 목록.
- **매니페스트** — 어셈블리의 신원(이름·버전·참조 목록).

여기서 .NET 플랫폼의 핵심 설계 결정 하나가 나온다. **메타데이터는 IL과 같은 파일 안에 들어간다.** 분리할 수 없다.

이 결정의 결과가 크다.

- C/C++처럼 **헤더 파일이 필요 없다.** 참조하려는 타입의 정보가 그 타입을 구현한 파일 안에 이미 있다. 컴파일러는 `.dll`에서 메타데이터를 직접 읽는다.
- **메타데이터와 IL이 어긋날 수 없다.** 둘을 같은 컴파일러가 같은 순간에 만들어 같은 파일에 넣기 때문이다. COM 시대의 타입 라이브러리(`.tlb`)나 IDL 파일이 실제 DLL과 버전이 안 맞아 생기던 사고가 원천적으로 없다.
- IDE의 IntelliSense가 이 메타데이터를 읽는다. 소스가 없는 NuGet 패키지에서도 자동 완성이 되는 이유다.
- CLR의 타입 안전성 검사, 직렬화, GC의 객체 추적이 전부 이 메타데이터에 의존한다(3.3절).

> **📌 메타데이터가 하는 일 다섯 가지**
>
> 원서(CLR via C#)가 꼽는 메타데이터의 용도는 다음과 같다.
>
> 1. **헤더 파일과 라이브러리 파일을 대체한다.** 참조된 타입·멤버의 정보가 IL과 같은 파일에 있다.
> 2. **IDE가 코드 작성을 돕는다.** IntelliSense가 메타데이터를 파싱해 멤버 목록과 매개변수를 보여준다.
> 3. **CLR의 코드 검증이 이것을 쓴다.** 타입 안전한 연산만 하는지 확인한다.
> 4. **직렬화를 가능하게 한다.** 객체의 필드를 메모리 블록으로 만들어 보내고 다른 쪽에서 복원할 수 있다.
> 5. **GC가 객체 수명을 추적한다.** 어떤 객체든 그 타입을 알아내고, 메타데이터에서 어떤 필드가 다른 객체를 참조하는지 알 수 있다.
>
> 다섯 번째가 특히 중요하다. GC가 "이 객체 안의 어느 8바이트가 포인터인가"를 아는 것은 메타데이터 덕분이다(61장, 64장).

### 최적화 스위치가 IL을 바꾼다

컴파일러에는 IL의 품질을 바꾸는 스위치가 있다. SDK 스타일 프로젝트에서는 구성(configuration)이 이 스위치를 결정한다.

| 구성 | `Optimize` | `DebugType` | 컴파일러가 만드는 IL | JIT이 만드는 네이티브 코드 |
|---|---|---|---|---|
| **Debug** (기본) | `false` | `portable`(전체 PDB) | 최적화 안 함 — `nop`과 무의미한 분기 포함 | 디버깅을 위해 최적화 억제 |
| **Release** | `true` | `portable` | 최적화 — `nop` 제거, 죽은 코드 제거 | 최적화 |

Debug IL에 `nop`(no-operation, 아무것도 안 하는 명령)이 들어가는 데는 이유가 있다.

- 여는 중괄호 `{`와 닫는 중괄호 `}`에도 **중단점을 걸 수 있게** 하기 위해서다. 실행할 명령이 하나도 없는 위치에는 중단점을 걸 수 없다.
- `for`, `while`, `if`, `try` 같은 제어 흐름 위치에서 한 줄씩 실행(single-step)이 자연스럽게 되도록 하기 위해서다.
- 편집 후 계속(edit-and-continue) 기능을 지원하기 위해서다.

Release에서는 이것들이 사라진다. IL이 짧아지고, 대신 디버거로 한 줄씩 따라가면 실행 순서가 소스와 어긋나 보이고 일부 지역 변수를 볼 수 없게 된다.

> **⚠️ Debug IL을 보고 컴파일러를 판단하지 마라**
>
> 이 책 독자가 SharpLab을 처음 열고 가장 많이 하는 실수다.
>
> Debug IL에는 `nop`이 있고, 계산 중간값을 굳이 지역 변수에 저장했다가 다시 읽는 코드가 있고, 마지막 반환값을 지역 변수에 넣었다가 꺼내는 패턴이 있다. 이걸 보고 "컴파일러가 왜 이렇게 비효율적으로 만들지?"라고 생각하면 출발부터 틀린다. **Debug IL은 디버깅 편의를 위해 일부러 비효율적으로 만든 것**이다.
>
> **SharpLab을 열면 제일 먼저 Release로 바꿔라.** 3.8절에서 이 습관을 다시 강조한다.

> **⚠️ IL이 최적화됐다고 최종 코드가 최적화된 것은 아니다**
>
> 컴파일러 최적화(`Optimize`)와 JIT 최적화는 **다른 단계, 다른 주체**다.
>
> C# 컴파일러는 대담한 최적화를 하지 않는다. 인라이닝도, 루프 언롤링도, 경계 검사 제거도 하지 않는다. 그런 것은 전부 **JIT의 몫**이다(55장). C# 컴파일러가 하는 최적화는 `nop` 제거, 도달 불가 코드 제거, 상수 접기 정도로 소박하다.
>
> 그래서 "IL 명령이 3개 줄었으니 3만큼 빨라졌다"는 추론은 거의 항상 틀린다. IL은 최종 실행 코드가 아니라 **JIT에 넘길 중간 표현**이다. 성능 판단은 IL이 아니라 측정으로 한다(67장).

## 3.3 관리 모듈의 해부 — PE32/PE32+ 헤더, CLR 헤더, 메타데이터, IL

### 관리 모듈이라는 말

컴파일러가 만들어낸 파일 하나를 **관리 모듈(managed module)** 이라고 부른다. 형식은 Windows의 표준 실행 파일 형식인 **PE(portable executable)** 다. 32비트 형식이면 PE32, 64비트 형식이면 PE32+라고 한다.

여기서 처음 헷갈리는 지점이 나온다. **PE는 Windows의 파일 형식인데, .NET 어셈블리는 Linux와 macOS에서도 같은 형식이다.** `HelloIL.dll`을 Linux에서 빌드해도 PE 파일이 나온다. 운영체제가 이 파일을 직접 실행하는 게 아니라 **런타임이 읽어서 해석하기 때문에** 형식이 Windows 것이든 상관이 없다. 역사적 이유로 남은 형식이라고 이해하면 된다.

관리 모듈은 네 부분으로 이루어진다.

| 부분 | 담는 것 |
|---|---|
| **PE32 / PE32+ 헤더** | 표준 Windows PE 파일 헤더. 파일 종류(GUI / CUI / DLL), 빌드 타임스탬프, 섹션 목록. IL만 담은 모듈에서는 이 헤더의 대부분이 무시된다. 네이티브 CPU 코드가 들어 있는 모듈에서는 그 코드에 대한 정보를 담는다 |
| **CLR 헤더** | 이 파일을 **관리 모듈로 만들어주는 헤더.** 필요한 CLR 버전, 플래그, 진입점 메서드의 MethodDef 메타데이터 토큰, 메타데이터의 위치와 크기, 리소스, 강력한 이름 서명의 위치 |
| **메타데이터** | 메타데이터 테이블 묶음. 두 종류가 있다 — **이 소스가 정의한** 타입·멤버를 기술하는 테이블, **이 소스가 참조하는** 타입·멤버를 기술하는 테이블 |
| **IL 코드** | 컴파일러가 소스를 컴파일해 만든 코드. 런타임에 CLR이 이것을 네이티브 CPU 명령으로 컴파일한다 |

이 네 부분이 파일 안에서 어떻게 배치되는지 그림으로 본다.

```text
        HelloIL.dll  (PE32 / PE32+ 파일)
┌──────────────────────────────────────────────┐
│ MS-DOS 스텁                                    │  "This program cannot be run in DOS mode."
├──────────────────────────────────────────────┤
│ PE 시그니처 ("PE\0\0")                          │
├──────────────────────────────────────────────┤
│ COFF 파일 헤더                                  │  머신 종류, 섹션 개수, 특성 플래그
├──────────────────────────────────────────────┤
│ 선택적 헤더 (PE32 또는 PE32+)                    │
│   └─ 데이터 디렉터리 (16개)                      │
│        └─ [14] CLI 헤더 → ─────────────┐        │
├────────────────────────────────────────│──────┤
│ 섹션 테이블 (.text, .rsrc, .reloc …)     │        │
├────────────────────────────────────────│──────┤
│ .text 섹션                              │        │
│  ┌─────────────────────────────────────↓────┐ │
│  │ CLR 헤더 (IMAGE_COR20_HEADER, 72바이트)     │ │
│  │   런타임 버전 · 플래그 · 진입점 토큰          │ │
│  │   메타데이터 RVA/크기 · 리소스 · 서명         │ │
│  └──────────────┬───────────────────────────┘ │
│                 ↓                             │
│  ┌──────────────────────────────────────────┐ │
│  │ 메타데이터                                  │ │
│  │  ├ 시그니처 "BSJB" + 버전 문자열             │ │
│  │  ├ #~     메타데이터 테이블 (TypeDef 등)     │ │
│  │  ├ #Strings  이름 문자열 힙                  │ │
│  │  ├ #US       사용자 문자열 힙 (ldstr 대상)   │ │
│  │  ├ #GUID     GUID 힙                        │ │
│  │  └ #Blob     시그니처·상수 블롭 힙            │ │
│  └──────────────────────────────────────────┘ │
│  ┌──────────────────────────────────────────┐ │
│  │ IL 메서드 본문들                             │ │
│  │   각 본문 = 헤더 + 옵코드 열 (+ 예외 절)      │ │
│  └──────────────────────────────────────────┘ │
├──────────────────────────────────────────────┤
│ .rsrc / .reloc 등 나머지 섹션                    │
└──────────────────────────────────────────────┘
```

### PE 헤더 — 거의 무시되는 부분

PE 헤더는 원래 Windows 로더가 네이티브 실행 파일을 메모리에 올리기 위해 읽는 정보다. 그런데 **IL만 담은 관리 모듈에서는 대부분이 의미가 없다.** 파일을 실제로 해석하는 것은 Windows 로더가 아니라 CLR이기 때문이다.

그래도 두 가지는 여전히 유효하다.

- **PE32냐 PE32+냐** — 헤더 형식이 주소 공간 크기를 결정한다. PE32는 32비트/64비트 어느 쪽에서도 실행될 수 있고, PE32+는 64비트를 요구한다.
- **CPU 아키텍처 표시** — x86, x64, ARM64, 또는 아키텍처 무관(agnostic).

이 두 값을 결정하는 것이 `PlatformTarget` 속성이다.

| `PlatformTarget` | 만들어지는 헤더 | 의미 |
|---|---|---|
| `AnyCPU` (기본) | PE32 / 아키텍처 무관 | 어느 아키텍처에서든 실행 가능 |
| `x86` | PE32 / x86 | 32비트 x86 전용 |
| `x64` | PE32+ / x64 | 64비트 x64 전용 |
| `arm64` | PE32+ / ARM64 | ARM64 전용 |

> **📌 대부분의 프로젝트는 이 값을 건드리지 않는다**
>
> 타입 안전한 관리 코드만 쓴다면 아키텍처를 고정할 이유가 없다. **같은 `.dll`이 x64 Linux 서버에서도, ARM64 맥에서도, x86 Windows에서도 그대로 돈다.** IL이 CPU에 독립적이기 때문이다.
>
> 아키텍처를 고정해야 하는 경우는 정해져 있다. 특정 아키텍처용 네이티브 라이브러리와 P/Invoke로 연결할 때(60장), 그리고 포인터를 쓰는 `unsafe` 코드에서 크기 가정을 할 때다. 그런 상황이 아니라면 기본값을 그대로 둔다.
>
> 모던 .NET에서 실행 아키텍처는 사실상 **자체 포함 배포의 RID**(런타임 식별자)가 결정하고, PE 헤더의 아키텍처 표시는 예전만큼 큰 역할을 하지 않는다(4.9절).

### CLR 헤더 — 이 파일이 관리 모듈이라는 증거

PE 선택적 헤더에는 데이터 디렉터리가 16개 있고, 그중 15번째(인덱스 14)가 **CLI 헤더**를 가리킨다. 이 값이 0이 아니면 관리 모듈이고, 0이면 순수 네이티브 파일이다. 다시 말해 **`.dll`이 .NET 어셈블리인지 판별하는 방법은 이 디렉터리 엔트리를 보는 것**이다.

CLR 헤더가 담는 것 중 이 장에서 의미 있는 항목은 다음과 같다.

| 필드 | 내용 |
|---|---|
| **런타임 버전** | 이 모듈을 실행하는 데 필요한 런타임의 주/부 버전 |
| **메타데이터 RVA / 크기** | 메타데이터가 파일 어디서 시작해 몇 바이트인지 |
| **플래그** | `ILONLY`(IL만 들어 있음), `32BITREQUIRED`, `32BITPREFERRED`, `STRONGNAMESIGNED` 등 |
| **진입점 토큰** | **실행을 시작할 메서드의 MethodDef 토큰.** 라이브러리(`.dll`)에서는 0이다 |
| **리소스 RVA / 크기** | 임베드된 관리 리소스의 위치(53.1절) |
| **강력한 이름 서명 RVA / 크기** | 서명된 어셈블리라면 서명 블록의 위치(52.5절) |

여기서 **진입점 토큰**이 3.5절의 열쇠다. "어느 메서드가 `Main`인가"는 실행 시점에 찾는 것이 아니라 **컴파일 시점에 확정되어 파일에 박혀 있다.**

### 메타데이터 — 테이블과 힙

메타데이터는 관계형 데이터베이스처럼 생겼다. **테이블**이 있고, 각 테이블에 **행**이 있고, 행의 필드는 다른 테이블의 행이나 **힙**의 오프셋을 가리킨다.

주요 테이블 몇 개만 본다. 전체 목록과 매니페스트 관련 테이블은 52.2절에 있다.

| 테이블 | 담는 것 | 이 모듈이 정의? 참조? |
|---|---|---|
| `Module` | 이 모듈 자신의 이름과 MVID(모듈 버전 ID) | 정의 |
| `TypeDef` | **이 모듈이 정의한 모든 타입.** 이름, 네임스페이스, 기반 타입, 플래그, 이 타입이 소유한 필드·메서드의 시작 인덱스 | 정의 |
| `MethodDef` | **이 모듈이 정의한 모든 메서드.** 이름, 시그니처, 플래그, IL 본문의 RVA | 정의 |
| `Field` | 이 모듈이 정의한 모든 필드 | 정의 |
| `Property` / `Event` | 프로퍼티·이벤트 정의와 그에 대응하는 접근자 메서드 연결 | 정의 |
| `AssemblyRef` | **참조하는 다른 어셈블리 목록.** 이름, 버전, 공개 키 토큰, 문화권 | 참조 |
| `TypeRef` | **참조하는 다른 타입 목록.** 이름과 그 타입이 사는 어셈블리(AssemblyRef 인덱스) | 참조 |
| `MemberRef` | **참조하는 다른 멤버(메서드·필드) 목록.** 이름, 시그니처, 소유 타입(TypeRef 인덱스) | 참조 |
| `CustomAttribute` | 어디에 어떤 특성이 붙었는지(20장) | 양쪽 |

힙은 네 개다. 테이블의 행이 문자열이나 바이트 배열을 직접 담지 않고 힙의 오프셋만 담는 구조다.

- `#Strings` — 타입 이름, 메서드 이름 등 **식별자 문자열**.
- `#US` — **사용자 문자열**. `ldstr "Hello, World!"`가 가리키는 그 문자열이 여기 있다.
- `#GUID` — GUID들. MVID가 여기 산다.
- `#Blob` — 메서드 시그니처, 특성 인자, 상수 값 같은 **가변 길이 이진 데이터**.

> **📌 메타데이터 토큰 읽는 법**
>
> IL과 CLR 헤더 곳곳에 `0x06000001` 같은 32비트 값이 나온다. 이것을 **메타데이터 토큰**이라고 한다. 구조는 단순하다.
>
> - **상위 1바이트** = 테이블 번호
> - **하위 3바이트** = 그 테이블의 행 번호(1부터 시작)
>
> 자주 보게 되는 테이블 번호는 `0x01`(TypeRef), `0x02`(TypeDef), `0x04`(Field), `0x06`(MethodDef), `0x0A`(MemberRef)이고, `0x70`은 테이블이 아니라 사용자 문자열 힙(`#US`)의 오프셋을 뜻한다.
>
> 그래서 `0x06000001`은 "MethodDef 테이블의 첫 번째 행"이다. CLR 헤더의 진입점 토큰이 `0x06000001`이면 **이 모듈이 정의한 첫 번째 메서드가 진입점**이라는 뜻이다.
>
> `ldstr 0x70000001` 같은 것을 만나면 사용자 문자열 힙의 오프셋 1번을 가리키는 것이다. `ildasm`은 친절하게 실제 문자열로 바꿔 보여준다.

### IL — 실제로 무엇이 들어 있나

메서드 본문 하나를 열어보자. `dotnet build`로 만든 `HelloIL.dll`을 디스어셈블하면 이런 것이 나온다.

```il
.class private auto ansi beforefieldinit Program
    extends [System.Runtime]System.Object
{
  .method private hidebysig static void  '<Main>$'(string[] args) cil managed
  {
    .entrypoint
    // 코드 크기       11 (0xb)
    .maxstack  8
    IL_0000:  ldstr      "Hello, World!"
    IL_0005:  call       void [System.Console]System.Console::WriteLine(string)
    IL_000a:  ret
  } // end of method Program::'<Main>$'
}
```

읽는 법을 한 줄씩 본다.

- `.class private auto ansi beforefieldinit Program` — `Program`이라는 타입 정의. `private`는 CLR 용어로 어셈블리 내부 공개(C#의 `internal`)를 뜻한다.
- `extends [System.Runtime]System.Object` — 기반 타입. `[System.Runtime]`은 **그 타입이 사는 어셈블리**를 대괄호로 표기한 것이다. 이 표기가 나오면 AssemblyRef + TypeRef 조합이 쓰였다는 뜻이다.
- `.method ... static void '<Main>$'(string[] args) cil managed` — 메서드 정의. 이름이 `<Main>$`인 것에 주목하라. C#으로는 쓸 수 없는 이름이다(3.7절).
- **`.entrypoint`** — 이 메서드가 진입점이라는 표시. CLR 헤더의 진입점 토큰이 이 메서드를 가리킨다.
- `.maxstack 8` — 이 메서드 실행 중 평가 스택에 최대 몇 개가 쌓이는지. JIT이 스택 프레임 크기를 잡는 데 쓴다.
- `IL_0000`, `IL_0005`, `IL_000a` — **메서드 본문 안에서의 바이트 오프셋**이다. 줄 번호가 아니다. `ldstr`이 5바이트(옵코드 1 + 토큰 4)라서 다음 명령이 `IL_0005`에서 시작한다.
- `ldstr` / `call` / `ret` — 옵코드. 각각 "문자열을 스택에 올린다", "메서드를 호출한다", "반환한다"는 뜻이다.

IL이 **스택 기반**이라는 점이 여기서 드러난다. `ldstr`이 값을 스택에 밀어 넣고, `call`이 그것을 꺼내 인자로 쓴다. 레지스터를 다루는 명령이 하나도 없다. 이 실행 모델은 56.2절에서, 옵코드 전체는 56.3절에서 다룬다.

> **⚠️ IL은 어셈블리어가 아니다**
>
> "IL을 읽어야 한다"는 말에 겁먹는 독자가 많다. 그런데 IL은 x86 어셈블리와 성격이 완전히 다르다.
>
> - **객체를 안다.** 객체 생성, 가상 메서드 호출, 배열 원소 접근, 예외 던지기·잡기가 전부 **하나의 명령**이다.
> - **타입을 안다.** `call` 명령의 인자가 "주소 0x401000"이 아니라 `void [System.Console]System.Console::WriteLine(string)`이라는 완전한 시그니처다.
> - **레지스터가 없다.** 스택만 있으므로 외울 것이 훨씬 적다.
>
> 이 책이 IL을 계속 보여주는 것은 어셈블리 프로그래밍을 시키려는 게 아니다. **"내가 쓴 C#이 무엇으로 바뀌었는지"를 확인하는 도구**로 쓰는 것이다. 3.8절에서 실제로 해본다.

> **⚠️ IL은 지적 재산을 지켜주지 않는다**
>
> IL은 대부분의 기계어보다 높은 수준이고, 메타데이터에 타입·메서드·매개변수 이름이 전부 들어 있다. 그래서 **디컴파일하면 원본과 상당히 비슷한 C#이 복원된다.** 상용 라이브러리를 배포한다면 이 사실을 전제해야 한다.
>
> 난독화(obfuscation) 도구로 비공개 심볼 이름을 뒤섞을 수는 있다. 그러나 그것도 부분적 보호에 그친다. **CLR이 JIT 컴파일하려면 IL이 어느 시점엔 반드시 읽을 수 있는 상태여야 하기** 때문이다.
>
> 서버에서만 도는 코드라면 애초에 이 걱정이 필요 없다. 어셈블리가 외부로 나가지 않으면 아무도 볼 수 없다.

### 도구로 직접 확인하기

`.dll` 안을 들여다보는 도구는 여러 개가 있다.

```bash
# ILSpy 명령줄 버전 — IL 출력
dotnet tool install --global ilspycmd
ilspycmd -il bin/Debug/net8.0/HelloIL.dll

# IL 없이 디컴파일된 C#만 보고 싶을 때 (옵션 생략이 기본)
ilspycmd bin/Debug/net8.0/HelloIL.dll
```

Windows에서는 .NET Framework SDK와 함께 배포되던 `ildasm`도 여전히 쓸 수 있다. **이 책은 IL을 인용할 때 `ildasm`의 출력 형식을 따른다.** GUI 도구로는 ILSpy와 JetBrains dotPeek이 있다. 도구 비교는 56.8절에 있다.

가장 손쉬운 방법은 아무것도 설치하지 않는 것이다 — **SharpLab을 여는 것**(3.8절).

## 3.4 모듈에서 어셈블리로 — 매니페스트란 무엇인가

### CLR은 모듈이 아니라 어셈블리를 다룬다

3.3절에서 본 것은 **모듈**이다. 그런데 CLR은 모듈 단위로 일하지 않는다. **어셈블리** 단위로 일한다.

어셈블리는 처음에는 잡기 어려운 개념이다. 다음 두 문장이 정의의 전부다.

1. 어셈블리는 **하나 이상의 모듈과 리소스 파일을 논리적으로 묶은 것**이다.
2. 어셈블리는 **재사용·보안·버전 관리의 최소 단위**다.

두 번째 문장이 핵심이다. 버전은 어셈블리에 붙는다. 참조도 어셈블리를 향한다. `internal` 접근 제한의 경계도 어셈블리다. 타입 이름의 해석도 어셈블리 안에서 이루어진다. **모듈은 이 어느 것에도 관여하지 않는다.**

| | 모듈 | 어셈블리 |
|---|---|---|
| 실체 | 물리적 파일 하나 | 논리적 묶음 |
| 버전 번호 | 없다 | **있다** |
| 참조 대상 | 될 수 없다 | **된다** |
| `internal` 경계 | 아니다 | **맞다** |
| 배포 단위 | 아니다 | **맞다** |
| CLR이 로드하는 것 | 아니다 | **맞다** |

### 매니페스트가 모듈을 어셈블리로 만든다

그러면 파일 하나를 놓고 "이건 모듈이냐 어셈블리냐"를 어떻게 구분하는가?

**매니페스트(manifest)가 있으면 어셈블리다.**

매니페스트는 별도의 파일이 아니다. **메타데이터 테이블 몇 개가 추가된 것**이다. 이 테이블들이 다음을 기술한다.

- 이 어셈블리를 구성하는 파일들의 목록
- 이 어셈블리가 외부에 공개하는 타입들
- 이 어셈블리에 연결된 리소스·데이터 파일들
- 어셈블리의 이름·버전·문화권·공개 키

C# 컴파일러는 기본적으로 **매니페스트를 포함한 모듈**을 만든다. 그래서 프로젝트 하나를 빌드하면 나오는 `.dll` 하나가 곧 어셈블리다. 이것을 **단일 파일 어셈블리**라고 한다. 실무의 99% 이상이 이 경우다.

> **📌 매니페스트를 "추가"하는 작업은 없다**
>
> 매니페스트는 만드는 것이 아니라 **컴파일 결과로 생기는 것**이다. `.csproj`에 아무것도 안 써도 컴파일러가 넣는다. `AssemblyVersion`, `AssemblyCompany` 같은 값을 지정하면 매니페스트에 반영될 뿐이다.
>
> 그 값들이 어디서 오는지는 3.1절에서 본 `obj/Debug/net8.0/HelloIL.AssemblyInfo.cs`에 있다. 컴파일러가 소스로 읽는 생성 파일이다. `.csproj`의 속성 → `AssemblyInfo.cs` → 어셈블리 특성 → 매니페스트 테이블, 이 경로로 흘러간다.

매니페스트에 어떤 테이블이 들어가는지는 52.2절에서 전부 다룬다. 이 장에서는 네 개만 이름을 익혀 둔다.

- `Assembly` — 이 어셈블리 자신의 신원. 이름, 버전, 문화권, 공개 키.
- `File` — 어셈블리에 속한 다른 파일 목록. **단일 파일 어셈블리에서는 비어 있다.**
- `ManifestResource` — 임베드된 리소스 목록(53.1절).
- `ExportedType` — 다른 파일에서 구현되었지만 이 어셈블리가 내보내는 타입 목록.

`ildasm`으로 매니페스트를 보면 이런 형태다.

```il
.assembly extern System.Runtime
{
  .publickeytoken = (B0 3F 5F 7F 11 D5 0A 3A )
  .ver 8:0:0:0
}
.assembly extern System.Console
{
  .publickeytoken = (B0 3F 5F 7F 11 D5 0A 3A )
  .ver 8:0:0:0
}
.assembly HelloIL
{
  .custom instance void [System.Runtime]System.Runtime.Versioning.TargetFrameworkAttribute::.ctor(string)
           = ( ... ".NETCoreApp,Version=v8.0" ... )
  .ver 1:0:0:0
}
.module HelloIL.dll
```

읽는 법은 단순하다.

- `.assembly extern XXX` — **참조하는 어셈블리.** 이름, 공개 키 토큰, 버전이 함께 기록된다. 이게 `AssemblyRef` 테이블의 내용이다.
- `.assembly HelloIL` — **이 어셈블리 자신.** `.ver 1:0:0:0`이 `AssemblyVersion`이다.
- `.module HelloIL.dll` — 매니페스트를 담은 모듈의 파일 이름.

### 자기 설명적이라는 것의 의미

`.assembly extern` 항목이 파일 안에 박혀 있다는 사실이 만드는 성질이 있다. **어셈블리는 자기 의존성을 스스로 안다.** 레지스트리도, 별도의 설정 파일도, 시스템 어딘가의 등록 정보도 필요 없다.

이 성질의 실질적 결과가 크다.

- 배포가 파일 복사로 끝난다. COM 컴포넌트를 등록(`regsvr32`)해야 했던 시대와 대비된다.
- 한 머신에 여러 버전의 .NET이 공존할 수 있다.
- Windows 레지스트리가 없는 Linux·macOS에서 그대로 동작한다.

CLR은 실행 중에 타입이 필요해지면 `TypeRef` → `AssemblyRef`를 따라가 "이 타입은 `System.Console`, 버전 8.0.0.0에 있다"를 알아내고, 그 어셈블리를 찾아 로드한다. 어떻게 찾는지(프로빙 순서, `deps.json`의 역할)는 52.15절에서 다룬다.

> **⚠️ 네임스페이스와 어셈블리는 다른 것이다**
>
> 가장 흔한 초기 오해다. `System.Collections.Generic`이라는 네임스페이스에 있는 타입이 `System.Collections.dll`에 있으리라는 보장은 없다.
>
> - **네임스페이스**는 **이름 충돌을 피하기 위한 논리적 그룹**이다. 컴파일 시점의 개념이고, IL 수준에서는 타입 이름 앞에 붙는 문자열일 뿐이다(12.1절).
> - **어셈블리**는 **물리적 배포 단위**다. 런타임의 개념이다.
>
> 하나의 어셈블리가 여러 네임스페이스를 담을 수 있고, 하나의 네임스페이스가 여러 어셈블리에 흩어질 수도 있다. 실제로 `System` 네임스페이스의 타입들은 수십 개의 어셈블리에 흩어져 있다.
>
> 그래서 "`using`을 추가했는데 타입을 못 찾는다"는 상황이 생긴다. `using`은 네임스페이스를 여는 것이고, **타입이 사는 어셈블리를 참조에 추가하는 것은 별개의 일**이다.

> **💡 다중 파일 어셈블리는 잊어도 된다**
>
> 어셈블리가 여러 파일로 이루어질 수 있다는 개념은 .NET Framework 시절의 것이다. 어셈블리 링커(`al.exe`)로 모듈 여러 개를 하나의 어셈블리로 묶는 방식이었고, "거의 안 쓰는 타입은 별도 파일에 넣어 필요할 때만 다운로드한다" 같은 시나리오를 노렸다.
>
> **모던 .NET에는 이 기능이 없다.** C# 컴파일러는 다중 모듈 어셈블리를 만들 수 없고, 만들 도구도 없다. 그러니 이 장에서는 **어셈블리 = 파일 하나**로 이해해도 실무에 문제가 없다.
>
> 다만 개념을 알아 둘 값은 있다. 매니페스트의 `File`·`ExportedType` 테이블이 왜 존재하는지, `.NET Framework` 시절 문서에 나오는 "모듈"이 무슨 뜻인지가 이 개념 없이는 설명되지 않는다. 자세한 것은 52.3절에 있다.

### .NET에서는 파일이 두 개 나온다

한 가지 더 확인하고 넘어간다. 3.1절에서 `bin`에 `.dll`과 `.exe`가 둘 다 있었다.

- **`HelloIL.dll`** — 어셈블리. 매니페스트, 메타데이터, IL이 여기 있다.
- **`HelloIL.exe`** — 앱호스트. 관리 코드가 없는 네이티브 런처.

.NET Framework은 달랐다. **PE 어셈블리 하나가 어셈블리와 실행 런처 역할을 동시에** 했다. 그래서 `.exe` 자체가 디컴파일 대상이었다.

이 차이는 실무에서 자주 헷갈리는 지점이라 52.1절에서 다시 짚는다. 지금 기억할 것은 하나다 — **모던 .NET에서 "어셈블리"라고 하면 항상 `.dll`이다.**

## 3.5 CLR 로딩과 `Main` 진입점 결정

### 실행 파일을 더블클릭하면 무슨 일이 벌어지는가

이제 파일들이 다 준비됐다. `HelloIL.exe`를 실행하면 어떤 순서로 일이 벌어지는지 끝까지 따라간다.

```text
사용자: ./HelloIL  또는  dotnet HelloIL.dll
   │
   ↓
┌──────────────────────────────────────────────────────┐
│ 1. 앱호스트 (HelloIL.exe)                              │
│    - 네이티브 실행 파일. 관리 코드 없음                   │
│    - 자기 옆의 HelloIL.dll 경로를 안다 (빌드 때 박혔다)    │
│    - hostfxr 라이브러리를 찾아 로드한다                   │
└──────────────────┬───────────────────────────────────┘
                   ↓
┌──────────────────────────────────────────────────────┐
│ 2. hostfxr                                            │
│    - HelloIL.runtimeconfig.json 을 읽는다              │
│    - "Microsoft.NETCore.App 8.0.0 이 필요하다"          │
│    - 설치된 공유 프레임워크 중 맞는 것을 고른다             │
│      (롤 포워드 정책 적용)                               │
│    - hostpolicy 를 로드한다                             │
└──────────────────┬───────────────────────────────────┘
                   ↓
┌──────────────────────────────────────────────────────┐
│ 3. hostpolicy                                         │
│    - HelloIL.deps.json 을 읽는다                       │
│    - 앱 어셈블리 + 프레임워크 어셈블리 목록을 만든다        │
│      (TPA: trusted platform assemblies)               │
│    - CoreCLR 을 로드하고 초기화한다                       │
└──────────────────┬───────────────────────────────────┘
                   ↓
┌──────────────────────────────────────────────────────┐
│ 4. CoreCLR (런타임)                                    │
│    - 기본 AssemblyLoadContext 생성 (52.9절)            │
│    - HelloIL.dll 로드                                  │
│    - CLR 헤더의 진입점 토큰을 읽어 Main 을 찾는다          │
│    - 그 메서드를 호출한다                                │
└──────────────────┬───────────────────────────────────┘
                   ↓
┌──────────────────────────────────────────────────────┐
│ 5. Main 실행 시작 → 호출되는 메서드마다 JIT (3.6절)       │
└──────────────────────────────────────────────────────┘
```

각 단계의 역할을 표로 정리한다.

| 단계 | 무엇인가 | 읽는 파일 | 실패하면 |
|---|---|---|---|
| 앱호스트 | 네이티브 런처. `.exe`(Windows) 또는 확장자 없는 실행 파일 | — | 실행 자체가 안 됨 |
| `hostfxr` | **프레임워크를 고른다.** 어느 런타임 버전으로 실행할지 결정 | `runtimeconfig.json` | "지정한 프레임워크를 찾을 수 없습니다" |
| `hostpolicy` | **어셈블리 목록을 만든다.** 앱과 프레임워크의 어셈블리 경로 확정 | `deps.json` | 어셈블리 로드 실패 |
| CoreCLR | **런타임.** GC, JIT, 타입 시스템, 예외 처리 | `HelloIL.dll` | `TypeLoadException` 등 |

> **📌 `dotnet HelloIL.dll`로 실행하면 1단계만 다르다**
>
> `dotnet` 명령 자체가 앱호스트와 같은 일을 하는 프로그램이다(멀티플렉서, muxer라고 부른다). 인자로 받은 `.dll` 경로를 가지고 `hostfxr`부터 똑같은 경로를 탄다.
>
> 그래서 다음 두 명령의 결과는 같다.
>
> ```bash
> ./bin/Debug/net8.0/HelloIL
> dotnet ./bin/Debug/net8.0/HelloIL.dll
> ```
>
> 차이는 앱호스트 유무뿐이다. `<UseAppHost>false</UseAppHost>`로 앱호스트를 끄면 두 번째 방법만 남는다.

> **⚠️ .NET Framework의 로딩 경로는 완전히 다르다 — Framework 전용**
>
> .NET Framework에서는 이 과정이 이렇게 되어 있었다.
>
> 1. Windows 로더가 `.exe`의 PE 헤더를 읽어 32비트/64비트를 판단한다.
> 2. `MSCorEE.dll`(심(shim) 라이브러리)을 프로세스 주소 공간에 로드한다.
> 3. 프로세스의 주 스레드가 `MSCorEE.dll` 안의 메서드를 호출한다. 이 메서드가 CLR을 초기화하고, EXE 어셈블리를 로드하고, 진입점 메서드를 호출한다.
>
> `hostfxr`도 `hostpolicy`도 `runtimeconfig.json`도 없다. 대신 레지스트리와 `%SystemRoot%\Microsoft.NET\Framework` 아래의 설치 정보, 그리고 `app.config`가 그 역할을 나눠 가졌다.
>
> **오래된 블로그에서 `MSCorEE.dll`이나 `mscoree` 이야기가 나오면 그건 .NET Framework 문서다.** 모던 .NET에는 그 파일이 없다.

### 진입점은 어떻게 정해지는가

3.3절에서 봤듯 진입점은 **CLR 헤더의 진입점 토큰**에 박혀 있다. 그러면 컴파일러는 그 토큰을 어떻게 정하는가?

C# 컴파일러는 다음 조건을 **전부** 만족하는 메서드를 찾는다.

1. `static`이다.
2. 이름이 `Main`이다. (대소문자 구분 — `main`은 안 된다)
3. 반환 타입이 `void`, `int`, `Task`, `Task<int>` 중 하나다.
4. 매개변수가 없거나 `string[]` 하나다.
5. 제네릭 메서드가 아니다. 제네릭 타입 안에 있지도 않다.

접근 제한자는 상관없다. `private`, `public`, `internal` 아무거나 된다. 템플릿이 `static void Main`을 `private`으로 두는 것도 이 때문이다 — 외부에서 부를 일이 없다.

유효한 시그니처를 전부 나열하면 여덟 가지다.

| 시그니처 | 종료 코드 | 도입 |
|---|---|---|
| `static void Main()` | 항상 0 | C# 1.0 |
| `static void Main(string[] args)` | 항상 0 | C# 1.0 |
| `static int Main()` | 반환값 | C# 1.0 |
| `static int Main(string[] args)` | 반환값 | C# 1.0 |
| `static async Task Main()` | 항상 0 | ※C# 7.1 |
| `static async Task Main(string[] args)` | 항상 0 | ※C# 7.1 |
| `static async Task<int> Main()` | 반환값 | ※C# 7.1 |
| `static async Task<int> Main(string[] args)` | 반환값 | ※C# 7.1 |

> **⚠️ `async void Main`은 진입점이 될 수 없다**
>
> `async void`는 반환 타입 규칙(3번)을 만족하지 않는다. 컴파일러가 진입점으로 인정하지 않는다.
>
> 설령 인정한다 해도 동작하지 않는다. `async void` 메서드는 **호출자에게 완료를 알릴 방법이 없기 때문**에, 첫 `await`에서 제어를 돌려준 순간 프로세스가 그대로 종료된다. 비동기 작업은 시작만 되고 끝나지 않는다.
>
> `async void` 자체를 왜 피해야 하는지는 47.14절에서 다룬다.

### 진입점이 여럿일 때

`Main`을 만족하는 메서드가 프로젝트에 둘 이상이면 컴파일러는 어느 것인지 모른다.

```csharp
namespace Demo;

class Alpha
{
    static void Main() => Console.WriteLine("Alpha");
}

class Beta
{
    static void Main() => Console.WriteLine("Beta");
}
```

```text
error CS0017: 프로그램에 진입점을 두 개 이상 정의했습니다.
              진입점을 포함하는 형식을 지정하려면 컴파일 시 -main을 사용하십시오.
```

해결은 `.csproj`에서 어느 타입인지 지정하는 것이다.

```xml
<PropertyGroup>
  <StartupObject>Demo.Alpha</StartupObject>
</PropertyGroup>
```

**네임스페이스를 포함한 전체 이름**을 써야 한다. 이 값은 컴파일러의 `-main:` 스위치로 전달된다.

> **💡 진입점이 여러 개 있는 것이 유용할 때**
>
> 실무에서 일부러 이렇게 쓰는 경우가 있다. 하나의 프로젝트에 여러 데모·진단 프로그램을 넣어 두고, 구성에 따라 다른 것을 실행하는 방식이다.
>
> ```xml
> <PropertyGroup Condition="'$(Scenario)' == 'Bench'">
>   <StartupObject>Demo.BenchRunner</StartupObject>
> </PropertyGroup>
> ```
>
> ```bash
> dotnet run -p:Scenario=Bench
> ```
>
> 다만 프로젝트를 나누는 편이 대체로 더 낫다. 진입점이 여럿인 프로젝트는 도구(IDE, 디버거, 게시)마다 다르게 해석될 여지가 있다.

### `async Main`은 실제로 무엇으로 컴파일되는가

여기서 4단 원칙의 2단이 나온다. CLR의 진입점 호출 규약은 아주 오래된 것이고, **`Task`를 반환하는 메서드를 진입점으로 삼는 규약이 없다.** 그러면 `async Task Main`은 어떻게 동작하는가?

**컴파일러가 진짜 진입점을 따로 만든다.**

```csharp
class Program
{
    static async Task Main(string[] args)
    {
        await Task.Delay(100);
        Console.WriteLine("done");
    }
}
```

이 코드에서 컴파일러가 만드는 것은 두 개다.

1. `Main`은 그냥 `async` 메서드로 컴파일된다. 즉 상태 기계 클래스가 생기고 `Main` 본문은 그 상태 기계를 시작하는 코드가 된다(47.7절).
2. 그와 **별도로**, C#으로는 쓸 수 없는 이름의 메서드가 하나 더 생긴다. 개념적으로 이런 모양이다.

```csharp
// 컴파일러가 생성하는 진짜 진입점 — 개념적 형태
private static void <Main>(string[] args)
{
    Main(args).GetAwaiter().GetResult();
}
```

CLR 헤더의 진입점 토큰이 가리키는 것은 **이 생성된 메서드**다. `Task<int>`를 반환하면 생성 메서드도 `int`를 반환하고 `GetResult()`의 결과를 그대로 넘긴다.

즉 `async Main`은 문법 설탕이다. **"진입점에서 결과를 동기로 기다린다"는 코드를 컴파일러가 대신 써주는 것**이다.

> **⚠️ 그런데 이건 sync-over-async 아닌가**
>
> 맞다. 그리고 이 책은 `GetAwaiter().GetResult()`로 비동기를 동기 대기하는 것을 강하게 금지한다(47.14절). 데드락의 대표적 원인이기 때문이다.
>
> **그런데 진입점에서는 안전하다.** 이유가 두 가지다.
>
> 1. **콘솔 애플리케이션에는 동기화 컨텍스트(SynchronizationContext)가 없다.** 데드락은 "완료 콜백을 특정 스레드에서 실행해야 하는데 그 스레드가 대기 중이라 실행할 수 없다"는 상황에서 난다. 돌아갈 특정 스레드가 없으면 이 상황이 성립하지 않는다(47.12절).
> 2. **어차피 여기서 기다리지 않으면 프로세스가 끝난다.** `Main`이 반환하면 프로세스가 종료된다. 진입점에서 동기 대기는 회피할 수 있는 선택이 아니라 필연이다.
>
> 반대로 말하면 이렇다. **UI 애플리케이션의 이벤트 핸들러나 ASP.NET 요청 처리 안에서 같은 코드를 쓰면 데드락이 난다.** "진입점에서 되니까 어디서나 된다"고 일반화하면 사고가 난다.

> **📌 `Main`의 반환값은 프로세스 종료 코드다**
>
> `int`를 반환하면 그 값이 프로세스의 종료 코드가 된다. 셸 스크립트나 CI 파이프라인이 이 값을 보고 성공/실패를 판단한다. 관례상 0이 성공이다.
>
> ```csharp
> static int Main(string[] args)
> {
>     if (args.Length == 0)
>     {
>         Console.Error.WriteLine("사용법: tool <파일>");
>         return 2;              // 0이 아니면 실패
>     }
>     // ...
>     return 0;
> }
> ```
>
> `void` 반환이면 정상 종료 시 0이다. 처리되지 않은 예외로 프로세스가 죽으면 0이 아닌 값이 되는데, 그 구체적 동작은 32.14절에서 다룬다.
>
> 종료 코드는 `Environment.ExitCode`로도 설정할 수 있고, `Environment.Exit(n)`으로 즉시 종료할 수도 있다. 다만 `Environment.Exit`는 `finally` 블록을 건너뛰므로 함부로 쓰면 안 된다.

## 3.6 JIT이 IL을 네이티브 코드로 바꾸는 순간

### 문제 설정

`Main`이 호출됐다. 그런데 `Main` 안에 있는 것은 IL이다. **CPU는 IL을 실행할 수 없다.** x64 CPU는 x64 명령만, ARM64 CPU는 ARM64 명령만 안다.

그래서 어느 시점엔가 IL이 네이티브 명령으로 바뀌어야 한다. 그 일을 하는 것이 **JIT 컴파일러**(just-in-time compiler)다. 이름 그대로 **필요해지는 바로 그 순간에** 컴파일한다.

여기서 중요한 것은 **단위**다. JIT은 어셈블리 전체를 한 번에 컴파일하지 않는다. **메서드 하나씩** 컴파일한다. 그것도 **실제로 호출될 때**만.

### 첫 호출 — 스텁이 JIT을 부른다

`Main`이 실행되기 직전, CLR은 `Main`의 코드가 참조하는 타입들을 확인하고 각 타입마다 내부 자료 구조를 만든다. 이 구조에는 **그 타입이 가진 메서드마다 항목이 하나씩** 있고, 각 항목은 그 메서드의 구현이 있는 **주소**를 담는다.

초기화 시점에 CLR은 이 주소를 전부 **자기 자신 안의 어떤 함수**로 채운다. 원서(CLR via C#)는 이 함수를 `JITCompiler`라고 부른다. 실제 CoreCLR 구현에서는 **프리스텁(prestub)** 이라는 이름으로 불린다.

```text
  [첫 번째 호출]

  Main() {                        Console 타입의 내부 메서드 테이블
    Console.WriteLine("Hello");  ┌────────────────────────────────┐
    Console.WriteLine("Bye");    │ WriteLine()        → 프리스텁    │
  }                              │ WriteLine(string)  → 프리스텁 ●  │
       │                         │ WriteLine(int)     → 프리스텁    │
       │  call                   │ ... (나머지 멤버)                │
       └────────────────────────→└────────────────────────────────┘
                                              │
                                              ↓
                            ┌──────────────────────────────────────┐
                            │ 프리스텁이 하는 여섯 단계               │
                            │                                      │
                            │ 1. 이 메서드(WriteLine)를 정의한       │
                            │    어셈블리의 메타데이터에서 찾는다      │
                            │ 2. 메타데이터에서 그 메서드의 IL을 얻는다 │
                            │ 3. 메모리 블록을 하나 할당한다           │
                            │ 4. IL을 네이티브 명령으로 컴파일해        │
                            │    3에서 잡은 메모리에 쓴다             │
                            │ 5. 타입의 메서드 테이블 항목을            │
                            │    그 메모리 블록 주소로 바꿔 쓴다        │
                            │    ← 이것이 백패칭(backpatching)       │
                            │ 6. 그 네이티브 코드로 점프한다            │
                            └──────────────────────────────────────┘
```

5번이 핵심이다. **JIT은 자기를 부른 그 자리를 자기가 만든 코드의 주소로 덮어쓴다.** 이것을 **백패칭(backpatching)** 이라고 한다.

### 두 번째 호출 — JIT은 등장하지 않는다

두 번째 `Console.WriteLine("Bye")`는 상황이 다르다.

```text
  [두 번째 호출 — 같은 테이블, 항목 하나가 바뀌었다]

  Main() {                        Console 타입의 내부 메서드 테이블
    Console.WriteLine("Hello");  ┌────────────────────────────────┐
    Console.WriteLine("Bye");    │ WriteLine()        → 프리스텁    │
  }                              │ WriteLine(string)  → 네이티브 ●  │  ← 백패칭됨
       │                         │ WriteLine(int)     → 프리스텁    │
       │  call                   └────────────────────────────────┘
       └──────────────────────────────────┘
                                          ↓
                              이미 컴파일된 네이티브 코드로 바로 점프
                              (프리스텁을 거치지 않는다)
```

메서드 테이블의 항목이 이미 네이티브 코드를 가리키고 있으므로 **프리스텁을 건너뛰고 바로 실행된다.**

여기서 나오는 결론이 JIT의 성능 특성 전부를 설명한다.

**성능 손해는 메서드마다 첫 호출 한 번뿐이다.** 그 이후의 모든 호출은 네이티브 코드의 온전한 속도로 실행된다. 대부분의 프로그램은 같은 메서드를 반복해서 부르므로, 전체 실행 시간에서 JIT 비용이 차지하는 비중은 작다.

> **⚠️ 그 "한 번"이 문제가 되는 경우가 있다**
>
> 다음 상황에서는 JIT 비용이 눈에 띈다.
>
> - **시작 시간이 중요한 프로그램.** 짧게 살다 죽는 CLI 도구, 서버리스 함수. 실행 시간 대부분이 첫 호출이라 JIT 비용의 비중이 크다.
> - **서버의 첫 요청.** 요청 처리 경로의 모든 메서드가 첫 호출이라 유난히 느리다. 부하 테스트에서 첫 결과를 버리는 이유다.
> - **벤치마크의 첫 반복.** 워밍업 없이 잰 숫자는 JIT 시간을 포함한다(67.4절).
>
> 대응 수단은 55.7절에서 다루는 ReadyToRun과 Native AOT다. 지금은 "이런 문제가 있고 해법이 있다"까지만 알면 된다.

> **⚠️ 네이티브 코드는 프로세스가 끝나면 사라진다**
>
> JIT이 만든 네이티브 코드는 동적으로 할당한 메모리에 있다. **프로세스가 끝나면 함께 사라진다.**
>
> 결과가 둘이다.
>
> 1. **프로그램을 다시 실행하면 처음부터 다시 JIT한다.** 어제 컴파일한 것을 오늘 재사용하지 않는다.
> 2. **같은 프로그램을 두 프로세스로 동시에 띄우면 각자 JIT한다.** 코드 메모리를 공유하지 못한다.
>
> 두 번째가 특히 중요하다. 네이티브 실행 파일은 읽기 전용 코드 페이지를 여러 프로세스가 공유할 수 있는데, JIT된 코드는 그럴 수 없다. **같은 앱의 인스턴스를 많이 띄우는 환경에서는 이것이 메모리 사용량 차이로 나타난다.**

### 계층형 컴파일 — 요즘의 JIT은 두 번 컴파일한다

지금까지의 설명은 "메서드는 한 번 JIT된다"는 전제였다. **모던 .NET은 그렇지 않다.**

**계층형 컴파일(tiered compilation)** 은 같은 메서드를 두 단계로 컴파일한다.

| 계층 | 언제 | 최적화 | 목적 |
|---|---|---|---|
| **Tier 0** | 첫 호출 시 | 거의 안 함 | **빨리 컴파일해서 빨리 시작하기** |
| **Tier 1** | 호출 횟수가 임계값을 넘으면 | 전면 최적화 | **오래 도는 코드를 빠르게 하기** |

Tier 0 코드에는 호출 횟수를 세는 계측이 들어 있다. 임계값을 넘으면 백그라운드 스레드가 그 메서드를 다시, 이번에는 최적화를 다 켜고 컴파일한다. 컴파일이 끝나면 메서드 테이블 항목이 다시 백패칭되어 이후 호출은 Tier 1 코드로 간다.

**즉 백패칭은 한 번만 일어나는 일이 아니다.** 그리고 계층형 컴파일에 동적 PGO(프로파일 기반 최적화)가 결합하면, Tier 1 컴파일은 Tier 0이 실제로 수집한 실행 프로필을 활용한다. 어느 분기가 자주 타는지, 인터페이스 호출이 실제로 어느 구현으로 가는지 같은 정보다. 2.7절에서 "JIT은 사전 컴파일러보다 많이 알고 컴파일한다"고 말한 것의 실체가 이것이다.

상세한 조건, 루프가 있는 메서드를 실행 도중에 교체하는 OSR(on-stack replacement), 그리고 이 모든 것을 어떻게 관찰하는지는 55.2절과 55.3절에서 다룬다.

> **⚠️ 계층형 컴파일이 벤치마크를 망친다**
>
> 워밍업 없이 잰 숫자는 Tier 0 코드의 성능일 수 있다. Tier 0은 최적화가 거의 안 된 코드라서 **실제 성능보다 몇 배 느리게 나올 수 있다.**
>
> BenchmarkDotNet이 워밍업 반복을 자동으로 돌리는 이유가 이것이다. 직접 `Stopwatch`로 재는 코드에서 "첫 번째 결과가 유난히 느린데?"를 만나면 대개 이 문제다.
>
> 이 함정의 전체 목록은 67.4절에 있다.

### 검증 — IL이 안전한지 확인하는 단계

JIT은 컴파일만 하는 것이 아니라 **검증(verification)** 도 한다. IL을 훑어보며 "이 코드가 하는 일이 타입 안전한가"를 확인한다.

- 모든 메서드가 올바른 개수의 인자로 호출되는가
- 각 인자의 타입이 맞는가
- 반환값이 제대로 쓰이는가
- 스택 깊이가 모든 경로에서 일관되는가

이 검사가 가능한 것은 **메타데이터에 필요한 타입 정보가 전부 들어 있기 때문**이다(3.3절). 검증이 통과하면 그 코드는 잘못된 메모리를 건드릴 수 없다는 것이 보장된다.

`unsafe` 코드는 이 보장 밖에 있다. 포인터로 임의의 주소를 읽고 쓰기 때문에 검증할 수 없다. C# 컴파일러가 `unsafe` 블록마다 키워드를 요구하고 `<AllowUnsafeBlocks>true</AllowUnsafeBlocks>`를 요구하는 것은 **"검증 밖으로 나간다"는 선언을 명시적으로 시키기 위해서**다.

> **⚠️ 코드 접근 보안(CAS)은 모던 .NET에 없다 — Framework 전용**
>
> .NET Framework 시절에는 검증이 **코드 접근 보안**(CAS, code access security)과 묶여 있었다. 어셈블리가 어디서 왔는지(로컬 디스크, 네트워크 공유, 인터넷)에 따라 권한이 달랐고, 권한이 없으면 `unsafe` 코드가 실행 시점에 거부되었다. `PEVerify.exe`라는 도구로 어셈블리에 검증 불가능한 코드가 있는지 미리 확인할 수 있었다.
>
> **모던 .NET에는 이 모델이 없다.** CAS는 제거되었고, 관련 API는 남아 있어도 대부분 동작하지 않거나 예외를 던진다. 신뢰 경계는 이제 프로세스와 컨테이너 수준에서 관리한다.
>
> IL 검증 자체는 여전히 의미가 있고, `ILVerify`라는 오픈 소스 도구가 `PEVerify`의 역할을 이어받았다. 다만 실무에서 이걸 직접 쓸 일은 IL을 손으로 만들거나 생성할 때뿐이다(58장).

### NGen — 이 이름이 나오면 .NET Framework 문서다

검색하다 보면 **NGen.exe**라는 도구를 만나게 된다. 설치 시점에 어셈블리의 IL을 전부 네이티브로 컴파일해 별도 파일로 저장하는 도구다. 목적은 두 가지였다.

- **시작 시간 개선** — 실행 시점에 컴파일할 것이 없다.
- **워킹 세트 감소** — 미리 컴파일된 파일을 여러 프로세스가 메모리 매핑으로 공유할 수 있다.

그런데 문제가 많았다.

- **지적 재산 보호가 안 된다.** 리플렉션과 직렬화에 메타데이터가 필요하므로 IL이 든 원본 어셈블리를 함께 배포해야 했다.
- **동기화가 깨진다.** CLR 버전, CPU 종류, OS 버전, 어셈블리의 MVID, 참조 어셈블리의 버전 중 하나라도 달라지면 미리 컴파일한 파일을 못 쓰고 평소처럼 JIT으로 돌아간다.
- **코드 품질이 떨어진다.** 실행 환경을 알 수 없으므로 JIT만큼 공격적으로 최적화하지 못한다. 정적 필드 접근에 간접 참조가 들어가고, 클래스 생성자 호출 코드가 여기저기 삽입된다. 그래서 **NGen한 쪽이 오히려 느린 경우도 있었다.**

**NGen.exe는 .NET Framework 전용 도구다.** 모던 .NET에는 없다. 같은 문제를 푸는 현재의 수단은 두 가지다.

- **ReadyToRun(R2R)** — 게시 시점에 미리 컴파일하되, IL도 함께 담아 런타임이 필요하면 다시 JIT할 수 있게 한다.
- **Native AOT** — 아예 완전한 네이티브 실행 파일을 만든다. JIT이 없다.

둘의 차이와 선택 기준은 55.7절에, 배포 관점의 정리는 4.9절에 있다.

> **💡 지금 단계에서 JIT에 대해 알아야 할 것은 셋뿐이다**
>
> 1. **JIT은 메서드 단위로, 첫 호출 때 동작한다.** 어셈블리 전체를 미리 컴파일하지 않는다.
> 2. **비용은 첫 호출에만 든다.** 그래서 시작 시간과 정상 상태 처리량은 별개의 문제다.
> 3. **JIT이 무엇을 만들었는지는 볼 수 있다.** SharpLab의 JIT Asm 모드, 또는 `DOTNET_JitDisasm` 환경 변수(55.8절).
>
> 인라이닝, 경계 검사 제거, 역가상화 같은 개별 최적화는 지금 몰라도 된다. 그것들이 필요해지는 시점은 성능 문제를 실제로 만났을 때이고, 그때 55장을 펴면 된다.

## 3.7 최상위 문(top-level statements)과 암시적 `using`의 정체

### 두 줄짜리 `Program.cs`의 정체

3.1절에서 미뤄둔 질문으로 돌아온다.

```csharp
// See https://aka.ms/new-console-template for more information
Console.WriteLine("Hello, World!");
```

이 파일에는 `using System;`이 없다. `class`도 없다. `Main`도 없다. 그런데도 컴파일되고 실행된다. 두 가지 기능이 겹쳐서 만든 결과다.

- **최상위 문**(top-level statements) — 클래스와 `Main`을 컴파일러가 만들어준다. ※C# 9
- **암시적 `using`**(implicit usings) — `using` 문 일곱 개를 SDK가 넣어준다. ※C# 10 / .NET 6

두 기능은 독립적이다. 하나만 켜고 하나만 끌 수 있다. 하나씩 본다.

### 최상위 문 — 컴파일러가 무엇을 만드는가

.NET 5 이전이라면, 혹은 지금도 옵션을 주면, `Program.cs`는 이렇게 생겼다.

```csharp
using System;

namespace HelloIL
{
    class Program
    {
        static void Main(string[] args)
        {
            Console.WriteLine("Hello, World!");
        }
    }
}
```

최상위 문은 이 껍데기를 컴파일러가 대신 써주는 기능이다. 그러면 **정확히 무엇을 써주는가?**

3.3절에서 이미 답을 봤다.

```il
.class private auto ansi beforefieldinit Program
    extends [System.Runtime]System.Object
{
  .method private hidebysig static void  '<Main>$'(string[] args) cil managed
  {
    .entrypoint
    // ...
  }
}
```

디컴파일해서 C#으로 보면 대략 이런 모양이다.

```csharp
// 컴파일러가 생성한 것 — 개념적 형태. 실제 표시는 도구·버전에 따라 조금 다르다
internal class Program
{
    private static void <Main>$(string[] args)
    {
        Console.WriteLine("Hello, World!");
    }
}
```

여기서 읽어낼 사실이 넷이다.

1. **클래스 이름은 `Program`이다.** 사용자가 정한 게 아니라 컴파일러가 정한 이름이다.
2. **메서드 이름은 `<Main>$`다.** 꺾쇠와 달러가 들어간 이 이름은 C#으로는 선언할 수 없다. **사용자가 정의한 어떤 이름과도 충돌하지 않게 하려는 의도적 선택**이다. 컴파일러 생성 멤버가 이런 이름을 갖는 관행은 이 책에서 계속 만나게 된다(`<>c__DisplayClass0_0`, `<GetItems>d__1` 등).
3. **`args` 매개변수가 있다.** 최상위 문에서 `args`를 그냥 쓸 수 있는 이유다.
4. **`namespace`가 없다.** 프로젝트 이름과 상관없이 전역 네임스페이스에 놓인다.

네 번째는 코드로 확인할 수 있다.

```csharp
string? name = typeof(Program).Namespace;
Console.WriteLine(name ?? "(없음)");
```

```text
(없음)
```

`typeof(Program).Namespace`가 `null`이다. 최상위 문이 만드는 `Program` 클래스는 **어떤 네임스페이스에도 속하지 않는다.**

> **💡 숨겨진 코드를 5초 만에 드러내는 방법**
>
> 도구를 안 열고도 확인할 수 있다. 예외를 하나 던지면 스택 트레이스가 진실을 말해준다.
>
> ```csharp
> Console.WriteLine("Hello, World!");
> throw new Exception();
> ```
>
> ```text
> Unhandled exception. System.Exception: Exception of type 'System.Exception' was thrown.
>    at Program.<Main>$(String[] args) in /path/to/Program.cs:line 2
> ```
>
> `Program.<Main>$(String[] args)`가 그대로 찍힌다. 디버거를 붙이면 예외를 가로채므로 **디버깅 없이 실행**해야 이 출력을 볼 수 있다.
>
> 스택 트레이스에 파일명과 줄 번호가 나오는 것은 PDB 덕분이다(3.1절). PDB를 지우고 실행하면 `at Program.<Main>$(String[] args)`까지만 나온다.

### 최상위 문의 규칙

편의 기능인 만큼 제약이 있다.

| 규칙 | 내용 | 어기면 |
|---|---|---|
| **파일 하나만** | 프로젝트 전체에서 최상위 문을 담은 파일은 하나뿐 | 컴파일 오류 |
| **`using`이 맨 위** | 최상위 문보다 앞에 와야 한다 | 컴파일 오류 |
| **타입 선언은 맨 아래** | 클래스·구조체·네임스페이스 선언은 모든 문 뒤에 | 컴파일 오류 |
| **`args` 사용 가능** | `string[] args`가 이미 범위에 있다 | — |
| **`await` 사용 가능** | 컴파일러가 `async` 진입점으로 바꿔준다 | — |
| **`return` 가능** | `return 3;`이 종료 코드 3이 된다 | — |

세 번째 규칙 때문에 최상위 문 파일은 이런 모양이 된다.

```csharp
using System.Text;              // 1. using 먼저

var sb = new StringBuilder();   // 2. 그다음 문
sb.Append("Hello");
Console.WriteLine(Greet(sb.ToString()));
return 0;                        //    종료 코드

string Greet(string s) => $"{s}, World!";   // 지역 함수는 문 사이에 와도 된다

class Helper                     // 3. 타입 선언은 마지막
{
    public int Value { get; set; }
}
```

`Greet`는 **지역 함수**(local function)다. 최상위 문 안에서 선언한 함수는 전부 `<Main>$`의 지역 함수가 된다. 그래서 클래스의 다른 멤버에서는 부를 수 없다.

> **⚠️ 최상위 문과 명시적 `Main`을 같이 두면 `Main`이 무시된다**
>
> 최상위 문이 있는 프로젝트에 `static void Main`을 가진 클래스를 추가하면, **오류가 아니라 경고**가 난다.
>
> ```text
> warning CS7022: 프로그램의 진입점이 전역 코드입니다. 'Program.Main(string[])' 진입점은 무시됩니다.
> ```
>
> 최상위 문이 이긴다. `Main`은 그냥 평범한 정적 메서드가 되어 아무도 부르지 않는다.
>
> 이게 위험한 이유는 **경고라서 빌드가 성공하기 때문**이다. "왜 내 `Main`이 안 도는지 모르겠다"로 시간을 날리기 딱 좋다. 경고를 오류로 승격시켜 두면 이런 사고를 막는다.
>
> ```xml
> <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
> ```

### 최상위 문을 끄는 법

옛 스타일이 필요하면 템플릿 옵션을 준다.

```bash
dotnet new console -o HelloClassic --use-program-main
```

```csharp
namespace HelloClassic;

class Program
{
    static void Main(string[] args)
    {
        Console.WriteLine("Hello, World!");
    }
}
```

두 가지가 달라진다. **`namespace`가 생겼고**(프로젝트 이름과 같다), **`Main`이 진짜 이름을 갖는다.**

Visual Studio에서는 프로젝트 생성 대화 상자의 "최상위 문 사용 안 함"(Do not use top-level statements) 체크 박스가 같은 역할을 한다.

> **⚠️ 통합 테스트에서 `Program`이 안 보이는 문제**
>
> ASP.NET Core 앱을 `WebApplicationFactory<Program>`으로 테스트하려면 테스트 프로젝트에서 `Program` 타입이 보여야 한다. 그런데 최상위 문이 만든 `Program`은 **`internal`이다.** 다른 어셈블리에서 안 보인다.
>
> 해결책 두 가지가 있다.
>
> ```csharp
> // 방법 1 — Program.cs 맨 아래에 부분 클래스를 추가해 public으로 만든다
> public partial class Program { }
> ```
>
> ```xml
> <!-- 방법 2 — 테스트 어셈블리에만 internal을 공개한다 (MSBuild 항목 형태는 ※.NET 8 SDK) -->
> <ItemGroup>
>   <InternalsVisibleTo Include="MyApp.Tests" />
> </ItemGroup>
> ```
>
> 더 오래된 SDK에서는 같은 일을 소스 코드의 어셈블리 특성으로 한다.
>
> ```csharp
> [assembly: System.Runtime.CompilerServices.InternalsVisibleTo("MyApp.Tests")]
> ```
>
> 방법 1이 널리 쓰이는 관용구다. 컴파일러가 만드는 `Program`이 부분 클래스로 병합될 수 있게 설계되어 있어서 동작한다. `InternalsVisibleTo` 자체는 17.2절에서 다룬다.

### 암시적 `using` — 파일은 실제로 존재한다

두 번째 기능이다. `Program.cs`에 `using System;`이 없는데 `Console`을 쓸 수 있는 이유.

3.1절에서 이미 그 파일을 봤다. 다시 열어보자.

```bash
cat obj/Debug/net8.0/HelloIL.GlobalUsings.g.cs
```

```csharp
// <auto-generated/>
global using global::System;
global using global::System.Collections.Generic;
global using global::System.IO;
global using global::System.Linq;
global using global::System.Net.Http;
global using global::System.Threading;
global using global::System.Threading.Tasks;
```

**마법이 아니다.** SDK가 이 C# 파일을 생성해 컴파일 입력에 넣고, 컴파일러는 그냥 평범한 소스 파일 하나로 읽는다.

`global using`은 ※C# 10에 추가된 문법으로, **한 파일에 쓰면 그 프로젝트의 모든 파일에 적용되는 `using`**이다. `global::` 접두사는 "네임스페이스 이름을 전역 네임스페이스 기준으로 해석하라"는 뜻으로, 지역 타입 이름과 겹쳐도 안전하게 하기 위한 것이다. 두 문법 모두 12.3절과 12.5절에서 다룬다.

어떤 네임스페이스가 들어가는지는 **프로젝트의 SDK 종류**가 결정한다.

- **`Microsoft.NET.Sdk`** (콘솔·라이브러리) — 위에서 본 일곱 개. `System`, `System.Collections.Generic`, `System.IO`, `System.Linq`, `System.Net.Http`, `System.Threading`, `System.Threading.Tasks`.
- **`Microsoft.NET.Sdk.Web`** — 위 일곱 개에 더해 `System.Net.Http.Json`, `Microsoft.AspNetCore.Builder`, `Microsoft.AspNetCore.Hosting`, `Microsoft.AspNetCore.Http`, `Microsoft.AspNetCore.Routing`, `Microsoft.Extensions.Configuration`, `Microsoft.Extensions.DependencyInjection`, `Microsoft.Extensions.Hosting`, `Microsoft.Extensions.Logging`.
- **`Microsoft.NET.Sdk.Worker`** — 기본 일곱 개에 더해 `Microsoft.Extensions.Configuration`, `Microsoft.Extensions.DependencyInjection`, `Microsoft.Extensions.Hosting`, `Microsoft.Extensions.Logging`.

목록을 바꾸는 것도 `.csproj`에서 한다.

```xml
<PropertyGroup>
  <!-- 통째로 끄기 -->
  <ImplicitUsings>disable</ImplicitUsings>
</PropertyGroup>

<ItemGroup>
  <!-- 항목 추가 -->
  <Using Include="System.Text" />

  <!-- 항목 제거 -->
  <Using Remove="System.Net.Http" />

  <!-- using static 형태로 추가 -->
  <Using Include="System.Console" Static="true" />

  <!-- 별칭으로 추가 -->
  <Using Include="System.Collections.Generic.Dictionary&lt;string, int&gt;" Alias="Counter" />
</ItemGroup>
```

`Static`은 `using static`(12.4절)에, `Alias`는 타입 별칭(12.5절)에 대응한다. 이 항목들 역시 `GlobalUsings.g.cs`에 반영되므로, 설정이 제대로 먹었는지는 그 파일을 열어 확인하면 된다.

> **📌 암시적 `using`이 논쟁적인 이유**
>
> 편리하지만 반대 의견도 있다.
>
> - **파일만 봐서는 어디서 온 타입인지 모른다.** `List<T>`가 어느 네임스페이스인지 파일 상단에 안 적혀 있다.
> - **이름 충돌이 예상치 못한 곳에서 난다.** 자기 코드에 `Path`라는 클래스를 만들면 `System.IO.Path`와 부딪힌다.
> - **소스만 다른 곳에 복사하면 안 컴파일된다.** 스택오버플로에 코드를 붙일 때 겪게 된다.
>
> 반대로 켜 두는 쪽의 근거는, **파일 상단 일곱 줄이 정보를 주는 일이 실제로는 거의 없다**는 것이다. `System`과 `System.Linq`가 있다는 사실에서 얻는 정보는 0에 가깝다.
>
> 이 책은 템플릿 기본값(켜짐)을 따른다. 다만 라이브러리 프로젝트에서는 끄고 명시적으로 관리하는 팀도 많고, 그것도 합리적인 선택이다.

> **⚠️ 암시적 `using`은 어셈블리 참조를 추가하지 않는다**
>
> 3.4절의 ⚠️ 박스와 같은 이야기다. `global using System.Net.Http;`가 있다고 해서 `HttpClient`가 자동으로 쓸 수 있게 되는 것이 아니다. **그 타입이 사는 어셈블리가 참조 목록에 있어야** 한다.
>
> 기본 SDK에서는 프레임워크 참조(`Microsoft.NETCore.App`)가 그 어셈블리들을 전부 포함하기 때문에 문제가 안 될 뿐이다. NuGet 패키지가 제공하는 네임스페이스를 `<Using Include="...">`에 넣으면서 패키지 참조는 안 했다면, `using`은 통과하고 타입 이름에서 오류가 난다.

## 3.8 첫 코드를 SharpLab에 붙여보기 — 이 책의 기본 습관

### 왜 여기서 시작하는가

1.3절에서 이 책의 4단 원칙을 말했다. **문법 → 컴파일 결과 → 런타임 동작 → 성능 영향.** 그중 2단인 "컴파일 결과"를 확인하는 습관을 여기서 심는다.

지금까지 이 장이 한 이야기 — 낮추기, 메타데이터, IL, `<Main>$`, 암시적 `using` — 는 전부 **눈으로 볼 수 있는 것**이다. 도구를 설치할 필요도 없다. 브라우저만 있으면 된다.

`sharplab.io`를 연다. 왼쪽에 C# 코드를 붙이면 오른쪽에 결과가 나온다.

> **💡 지금 브라우저 탭 하나를 열어라**
>
> 이 절은 읽는 절이 아니라 **하는 절**이다. 아래 실습 여섯 개를 직접 해보는 데 20분이면 충분하고, 그 20분이 남은 81개 장의 독해 속도를 바꾼다.
>
> 이 책은 IL을 지면에 싣지만, **직접 붙여보는 것과는 다르다.** 코드를 한 글자 바꿨을 때 IL이 어떻게 달라지는지를 눈으로 보는 것이 진짜 학습이다.

### 화면 설정 — 시작 전에 두 가지

SharpLab을 열면 상단에 선택지가 있다. 두 개만 신경 쓰면 된다.

- **출력 모드** — `IL`(컴파일 결과 그대로) 또는 `C#`(그것을 다시 C#으로 디컴파일한 것).
- **빌드 구성** — **반드시 `Release`.** Debug IL에는 `nop`과 불필요한 지역 변수가 섞인다(3.2절).

출력 모드는 이 밖에도 `JIT Asm`(JIT이 만든 x64 기계어), `Syntax Tree`(Roslyn 구문 트리), `Run`(실제 실행)이 있다. `JIT Asm`은 55.8절에서, `Syntax Tree`는 57.15절에서 쓴다.

> **⚠️ 구성 확인을 습관으로 만들어라**
>
> 이 책 독자가 SharpLab에서 겪는 문제의 절반은 **Debug로 보고 있었다**는 것이다. 화면 상단을 한 번 보는 데 1초가 걸리고, 잘못된 IL로 잘못된 결론을 내리는 데는 30분이 걸린다.
>
> 반대로 **Debug IL을 일부러 봐야 할 때도 있다.** 디버거가 왜 이 줄에 멈추는지, 편집 후 계속이 왜 안 되는지 같은 질문이 그것이다. 그럴 때는 의식적으로 Debug로 바꿔서 본다. 문제는 "모르고 Debug로 보는 것"이지 Debug 자체가 아니다.

### 실습 1 — `<Main>$`를 눈으로 확인한다

왼쪽에 붙일 코드는 이 장이 계속 이야기한 그 한 줄이다.

```csharp
using System;

Console.WriteLine("Hello, World!");
```

`using System;`을 직접 쓴 것에 주목하라. **SharpLab에는 프로젝트 파일이 없으므로 암시적 `using`도 없다.** 3.7절에서 본 `GlobalUsings.g.cs`를 만들어줄 SDK가 없기 때문이다. 실습 6에서 이 이야기로 돌아온다.

출력 모드를 `IL`로 두면 오른쪽에 이런 것이 나온다.

```il
.class private auto ansi beforefieldinit Program
    extends [System.Private.CoreLib]System.Object
{
    .method private hidebysig static void '<Main>$' (string[] args) cil managed 
    {
        .entrypoint
        .maxstack 8

        IL_0000: ldstr "Hello, World!"
        IL_0005: call void [System.Console]System.Console::WriteLine(string)
        IL_000a: ret
    }
}
```

**확인할 것 네 가지.**

1. **`Program`이라는 클래스가 있다.** 소스에는 없었다.
2. **메서드 이름이 `<Main>$`다.** 3.7절에서 말한 그것이다.
3. **`.entrypoint`가 붙어 있다.** 3.3절의 진입점 토큰이 이 메서드를 가리킨다는 표시다.
4. **`.maxstack 8`, `IL_0000` 오프셋** — 3.3절에서 읽는 법을 본 그대로다.

세 줄짜리 IL이 전부다. `ldstr`로 문자열을 스택에 올리고, `call`로 `WriteLine`을 부르고, `ret`으로 돌아간다.

> **📌 `[System.Private.CoreLib]` vs `[System.Runtime]`**
>
> 3.3절에서는 `extends [System.Runtime]System.Object`라고 썼는데 SharpLab은 `[System.Private.CoreLib]`라고 표시할 수 있다. 둘 다 맞다.
>
> `System.Object`가 실제로 구현된 어셈블리는 `System.Private.CoreLib.dll`이다. 그런데 컴파일할 때 참조하는 것은 **참조 어셈블리**인 `System.Runtime.dll`이고, 그 안의 `System.Object`는 실제 구현으로 타입을 전달(type forwarding)한다. 그래서 컴파일 대상이나 디스어셈블러 설정에 따라 어느 쪽 이름으로 보이는지가 달라진다.
>
> 참조 어셈블리와 구현 어셈블리의 구분은 4.4절에서, 타입 전달은 52.8절에서 다룬다. **지금은 "같은 타입을 다른 이름의 어셈블리로 표시할 수 있다"만 알면 된다.**

### 실습 2 — 컴파일러가 만든 클래스를 C#으로 본다

같은 코드를 두고 출력 모드만 `C#`으로 바꾼다.

```csharp
internal class Program
{
    private static void <Main>$(string[] args)
    {
        Console.WriteLine("Hello, World!");
    }
}
```

**IL을 읽지 않고도 3.7절의 결론이 그대로 확인된다.** 클래스 이름, 메서드 이름, `args` 매개변수, 네임스페이스 없음까지.

이 `C#` 출력 모드가 SharpLab에서 가장 유용한 기능이다. 이 책 후반에서 상태 기계와 클로저를 다룰 때 계속 쓰게 된다.

- `yield return`이 든 메서드를 붙이면 `<GetItems>d__0` 같은 상태 기계 클래스가 통째로 나온다(28.4절).
- 람다를 붙이면 `<>c__DisplayClass0_0` 디스플레이 클래스가 나온다(26.10절).
- `async` 메서드를 붙이면 `MoveNext()` 본문이 전부 나온다(47.7절).

> **⚠️ 디컴파일된 C#은 컴파일되지 않는다**
>
> `<Main>$`라는 이름은 C#으로 선언할 수 없다. 디컴파일러가 보여주는 것은 **IL을 사람이 읽기 좋은 C# 문법으로 옮긴 것**이지, 컴파일 가능한 소스가 아니다.
>
> 그래서 이 출력을 복사해 프로젝트에 붙여넣으면 오류가 난다. **읽으라고 있는 것이지 쓰라고 있는 것이 아니다.** 1.7절에서 말한 "개념 코드"의 대표적 사례다.

### 실습 3 — 최상위 문을 껐을 때와 비교한다

이번에는 옛 스타일을 붙여본다.

```csharp
class Program
{
    static void Main(string[] args)
    {
        System.Console.WriteLine("Hello, World!");
    }
}
```

IL을 보면 달라진 곳은 딱 하나다.

```il
.method private hidebysig static void Main (string[] args) cil managed 
{
    .entrypoint
    // ...
}
```

**`<Main>$`가 `Main`이 되었을 뿐, 나머지는 같다.** `.entrypoint`도 그대로 있다.

이것으로 3.7절의 주장이 확인된다. 최상위 문은 **런타임 개념이 아니라 순수한 문법 설탕**이다. 생성되는 어셈블리의 구조는 사실상 동일하다.

### 실습 4 — IL이 타입에 따라 어떻게 달라지는가

이제 한 글자만 바꿔가며 IL을 비교하는 습관을 연습한다.

```csharp
class C
{
    static int F() => 1;
}
```

```il
IL_0000: ldc.i4.1
IL_0001: ret
```

`ldc.i4.1`은 "32비트 정수 상수 1을 스택에 올린다"는 뜻이다. `int`를 `long`으로 바꿔보자.

```csharp
class C
{
    static long F() => 1;
}
```

```il
IL_0000: ldc.i4.1
IL_0001: conv.i8
IL_0002: ret
```

**`conv.i8`이 생겼다.** IL에는 "64비트 상수 1을 올린다"는 짧은 명령이 없어서, 32비트로 올린 뒤 64비트로 변환하는 두 단계를 쓴 것이다.

한 번 더 해본다. 이번에는 박싱이다.

```csharp
class C
{
    static object F() => 1;
}
```

```il
IL_0000: ldc.i4.1
IL_0001: box [System.Private.CoreLib]System.Int32
IL_0006: ret
```

**`box` 명령이 나타났다.** 소스에는 `new`가 한 글자도 없는데 **힙에 객체가 만들어진다.** 2.7절에서 "숨은 할당"이라고 부른 것의 가장 단순한 형태이고, 이 옵코드 하나를 알아보는 것만으로도 코드 리뷰에서 잡을 수 있는 문제가 여러 개 생긴다. 박싱의 전모는 15장에서 다룬다.

> **💡 이 책을 읽는 법 — 한 글자만 바꿔라**
>
> 실습 4가 이 절에서 가장 중요하다. **두 코드의 IL을 나란히 놓고 차이만 보는 것**이 IL을 읽는 가장 빠른 방법이다.
>
> IL 전체를 이해하려 하지 마라. `.maxstack`이 몇인지, `nop`이 몇 개인지는 대개 중요하지 않다. **"내가 바꾼 한 글자 때문에 늘어난 명령이 무엇인가"**만 보면 된다.
>
> 이 습관이 붙으면 다음 질문들에 스스로 답할 수 있게 된다.
>
> - `List<T>`를 `IEnumerable<T>`로 바꾸면 무엇이 늘어나는가 (1.3절)
> - `struct`를 인터페이스로 받으면 무엇이 늘어나는가 (16장)
> - 람다가 외부 변수를 캡처하면 무엇이 생기는가 (26.10절)
> - `foreach`가 `for`보다 무엇을 더 하는가 (28.1절)

### 실습 5 — Debug와 Release의 IL 차이

3.2절에서 말한 `nop`을 직접 확인한다. 구성을 `Debug`로 바꾸고 다음을 붙인다.

```csharp
class C
{
    void M()
    {
        int x = 1;
        System.Console.WriteLine(x);
    }
}
```

```il
.method private hidebysig instance void M () cil managed 
{
    .maxstack 1
    .locals init (
        [0] int32 x
    )

    IL_0000: nop
    IL_0001: ldc.i4.1
    IL_0002: stloc.0
    IL_0003: ldloc.0
    IL_0004: call void [System.Console]System.Console::WriteLine(int32)
    IL_0009: nop
    IL_000a: ret
}
```

이제 `Release`로 바꾼다.

```il
.method private hidebysig instance void M () cil managed 
{
    .maxstack 8

    IL_0000: ldc.i4.1
    IL_0001: call void [System.Console]System.Console::WriteLine(int32)
    IL_0006: ret
}
```

명령이 7개에서 3개로 줄었다. 없어진 것을 하나씩 보면 이렇다.

- **`nop` 두 개** — `{`와 `}`에 중단점을 걸 수 있게 하려고 있었다.
- **`.locals init ([0] int32 x)`** — 디버거가 `x`의 값을 보여줄 수 있게 하려고 있었다.
- **`stloc.0` / `ldloc.0`** — 값을 지역 변수에 저장했다 다시 꺼내야 `x`를 감시할 수 있으므로 있었다.

**Release는 지역 변수 `x`를 아예 없앴다.** 값 1을 스택에 올려 바로 인자로 넘긴다. 디버거로는 `x`를 볼 수 없게 되지만, 프로그램의 관찰 가능한 동작은 같다.

### 실습 6 — 암시적 `using`이 없는 세계

실습 1에서 `using System;`을 직접 쓴 이유, 그리고 실습 4·5에서 `System.Console.WriteLine`이라고 전체 이름을 쓴 이유를 확인한다.

```csharp
// SharpLab에서는 이것이 오류가 난다
class C
{
    void M() => Console.WriteLine("x");
}
```

```text
error CS0103: 현재 컨텍스트에 'Console' 이름이 없습니다.
```

**SharpLab은 코드 조각을 컴파일할 뿐 프로젝트를 빌드하지 않는다.** `.csproj`가 없으니 `<ImplicitUsings>`도 없고, `GlobalUsings.g.cs`를 만들어줄 SDK도 없다. 그래서 `using`을 직접 써야 한다.

```csharp
using System;

class C
{
    void M() => Console.WriteLine("x");
}
```

이 사소한 차이가 3.7절의 요지를 한 번 더 확인해준다. **암시적 `using`은 언어 기능이 아니라 SDK가 소스 파일을 하나 더 끼워 넣는 빌드 기능이다.** 컴파일러 입장에서는 사람이 쓴 `using`과 SDK가 넣은 `global using`이 구분되지 않는다.


### SharpLab이 보여주지 못하는 것

도구의 한계를 아는 것이 도구를 쓰는 것만큼 중요하다.

| 질문 | SharpLab | 대안 |
|---|---|---|
| 컴파일러가 무엇으로 바꿨나 | **최적** | ILSpy(3.3절) |
| JIT이 어떤 기계어를 만들었나 | JIT Asm 모드로 가능 | `DOTNET_JitDisasm`(55.8절) |
| 이 코드가 힙에 몇 바이트를 할당하나 | **불가** | BenchmarkDotNet의 `[MemoryDiagnoser]`(67.5절) |
| 이 코드가 얼마나 빠른가 | **불가** | BenchmarkDotNet(67.3절) |
| GC가 몇 번 도나 | **불가** | `dotnet-counters`(73.9절) |
| 내 프로젝트의 실제 참조가 무엇인가 | **불가** | `dotnet build -bl`(3.1절) |

> **⚠️ IL이 짧다고 빠른 것이 아니다**
>
> 이 절을 마치며 3.2절의 경고를 다시 한다. **IL 명령 수와 실행 속도의 상관관계는 약하다.**
>
> 이유가 세 가지다.
>
> 1. **IL은 최종 코드가 아니다.** JIT이 인라이닝하고, 재배치하고, 죽은 코드를 없애고, 명령을 합친다. IL에서 `call` 하나가 JIT 후에는 명령 0개가 될 수도 있다.
> 2. **명령마다 비용이 다르다.** `ldc.i4.1`은 거의 공짜지만 `newobj`는 힙 할당을 유발하고, `callvirt`는 간접 분기를 만든다.
> 3. **메모리 접근이 지배한다.** 대부분의 실제 코드에서 성능을 결정하는 것은 명령 수가 아니라 캐시 미스다(61.4절).
>
> IL을 보는 목적은 **"무엇이 일어나는지 아는 것"**이지 "얼마나 빠른지 재는 것"이 아니다. 후자는 67장의 일이다.

> **📌 SharpLab 말고도 있다**
>
> 같은 일을 하는 다른 방법들이다. 팀 정책상 외부 사이트에 코드를 붙일 수 없는 경우에 쓴다.
>
> - **`ilspycmd -il <dll>`** — 로컬에서 빌드한 어셈블리의 IL 출력(3.3절).
> - **ILSpy / dotPeek (GUI)** — 트리로 탐색하며 IL과 디컴파일 C#을 함께 본다(56.8절).
> - **JetBrains Rider의 IL Viewer** — IDE 내장. 에디터 옆에 IL을 띄운다(1.5절).
> - **`ildasm`** — Windows. 이 책의 IL 인용 형식의 기준(56.7절).
>
> 결과물은 같다. SharpLab의 강점은 **저장·빌드 없이 즉시 결과가 나온다**는 것뿐이다. 그리고 그 "즉시"가 습관을 만드는 데 결정적이다.

## 이 장의 요약

- **`dotnet new / build / run` 세 명령이 하는 일은 전부 파일로 추적할 수 있다.** `obj/`는 컴파일러의 작업장이고 `bin/`은 결과물 진열장이다. 어셈블리 원본은 `obj/`에 만들어져 `bin/`으로 복사된다. `bin/`의 다섯 파일 중 `runtimeconfig.json`이 없으면 실행 자체가 안 된다(3.1절).
- **C# 컴파일러의 이름은 Roslyn이고, 파이프라인은 파싱 → 선언 → 바인딩 → 낮추기 → 방출의 다섯 단계다.** 이 중 **낮추기**가 이 책 절반의 주제다. `foreach`, `using`, `lock`, 람다, `yield`, `async`는 전부 IL에 대응 명령이 없어 다른 코드로 다시 쓰인다(3.2절).
- **관리 모듈은 PE32/PE32+ 헤더, CLR 헤더, 메타데이터, IL 네 부분으로 되어 있다.** PE 헤더는 대부분 무시되고, CLR 헤더가 이 파일을 관리 모듈로 만든다. **메타데이터는 IL과 같은 파일에 있어 절대 어긋날 수 없다** — 헤더 파일이 필요 없고 IntelliSense가 동작하고 GC가 객체를 추적할 수 있는 이유다(3.3절).
- **모듈에 매니페스트가 붙으면 어셈블리가 된다.** 어셈블리는 버전·참조·`internal` 경계·배포의 단위이고, 모듈은 그 어느 것도 아니다. **네임스페이스와 어셈블리는 다른 개념이다.** 모던 .NET에서 어셈블리는 항상 `.dll`이고, `.exe`는 관리 코드가 없는 앱호스트다(3.4절).
- **실행은 앱호스트 → `hostfxr` → `hostpolicy` → CoreCLR 순으로 이어진다.** `hostfxr`가 `runtimeconfig.json`으로 런타임을 고르고, `hostpolicy`가 `deps.json`으로 어셈블리 목록을 만든다. .NET Framework의 `MSCorEE.dll` 경로와는 완전히 다르다(3.5절).
- **진입점은 실행 시점에 찾는 것이 아니라 CLR 헤더에 토큰으로 박혀 있다.** `Main`의 유효 시그니처는 여덟 가지이고, `async Main`은 컴파일러가 `GetAwaiter().GetResult()`를 부르는 진짜 진입점을 따로 만들어 처리하는 문법 설탕이다(3.5절).
- **JIT은 어셈블리 전체가 아니라 메서드 하나씩, 첫 호출 때 컴파일한다.** 프리스텁이 IL을 네이티브로 바꾸고 자기 자리를 그 주소로 덮어쓴다(백패칭). 비용은 메서드마다 한 번이고, 계층형 컴파일이 도입되면서 백패칭은 한 번으로 끝나지 않는다(3.6절).
- **최상위 문은 `Program` 클래스와 `<Main>$` 메서드를, 암시적 `using`은 `GlobalUsings.g.cs`라는 실제 소스 파일을 만든다.** 둘 다 런타임 개념이 아니라 컴파일 시점의 편의다. 생성된 `Program`은 네임스페이스가 없고 `internal`이다(3.7절).
- **SharpLab에서 Release로 놓고 한 글자씩 바꿔가며 IL 차이를 읽는 것이 이 책의 기본 습관이다.** IL 전체를 이해하려 하지 말고 **차이만** 본다. 다만 IL은 성능을 재는 도구가 아니다 — 그것은 측정의 영역이다(3.8절).

## 연습 문제

1. **`obj`와 `bin`을 지우고 다시 만들어라.** 콘솔 프로젝트를 하나 만들고 `dotnet build` 후 `obj/`와 `bin/`의 파일 목록을 저장해 둔다. 두 폴더를 통째로 지우고 `dotnet build`를 다시 돌린 뒤 목록을 비교하라. 어떤 파일이 정확히 같고 어떤 파일이 다른가? `HelloIL.dll`의 바이트 크기는 같은가?

2. **`runtimeconfig.json` 없이 실행해 보라.** `bin/Debug/net8.0/`에서 `*.runtimeconfig.json`을 다른 곳으로 옮기고 실행하라. 어떤 오류가 나는가? 그다음 `deps.json`만 옮기고 실행하면 어떻게 되는가? 두 결과가 다른 이유를 3.5절의 호스트 체인으로 설명하라.

3. **진입점 충돌을 만들고 해결하라.** 한 프로젝트에 `static void Main`을 가진 클래스를 두 개 만들어 컴파일 오류를 확인하고, `<StartupObject>`로 해결하라. 그다음 최상위 문이 있는 파일을 추가하면 어떤 진단이 나오는가? 오류인가 경고인가?

4. **`async Main`의 실제 진입점을 찾아라.** `static async Task Main()`을 쓴 코드를 SharpLab의 `C#` 출력 모드에 붙여, 컴파일러가 만든 동기 진입점 메서드를 찾아라. 그 메서드가 `Main`을 어떻게 호출하는가?

5. **암시적 `using`을 끄고 무엇이 깨지는지 보라.** `<ImplicitUsings>disable</ImplicitUsings>`로 바꾸고 빌드하라. `obj/Debug/net8.0/*.GlobalUsings.g.cs`는 어떻게 되는가? 오류를 고치려면 `using`을 몇 개 써야 하는가?

6. **`box` / `unbox.any` 옵코드를 찾아라.** SharpLab을 Release로 놓고 다음 세 메서드의 IL을 비교하라. 어느 것에서 `box`가 나오고, 어느 것에서 `unbox.any`가 나오는가? 셋 다 소스에는 `new`가 없는데 힙 할당이 일어나는 것은 어느 것인가?
   - `static object A() => 1;`
   - `static int B(object o) => (int)o;`
   - `static void C(System.Collections.Generic.List<object> l) => l.Add(1);`

7. **Debug와 Release의 IL 차이를 정량화하라.** 반복문 하나가 들어간 메서드를 하나 써서 두 구성의 IL 명령 개수를 세어라. 차이가 몇 배인가? 그리고 그 차이를 근거로 "Release가 몇 배 빠르다"고 말할 수 있는가? 3.8절의 마지막 ⚠️ 박스를 근거로 답하라.
