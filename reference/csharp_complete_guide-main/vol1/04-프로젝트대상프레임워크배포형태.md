# 4장. 프로젝트, 대상 프레임워크, 배포 형태

> **이 장의 위치** — 3장에서 `dotnet new`가 만든 여섯 줄짜리 `.csproj`를 보고 "이 속성들이 무슨 뜻인지는 4장에서"라고 미뤘다. 그 약속을 여기서 지킨다. 프로젝트 파일 한 장이 **어떤 API를 쓸 수 있는지**, **어떤 C# 문법이 컴파일되는지**, **결과물이 어느 기계에서 도는지**를 전부 결정한다. 이 장을 건너뛰면 앞으로 나올 모든 장의 코드가 "내 환경에서는 왜 안 되지"에 걸린다.
>
> **선수 지식** — 2장(C#이라는 언어, .NET이라는 플랫폼), 3장(첫 프로그램이 실행되기까지)
>
> **이 장에서 다루지 않는 것** — BCL에 어떤 타입이 있는지는 5장에서, 어셈블리 내부 구조와 로딩 규칙은 52장에서, JIT과 Native AOT의 코드 생성 차이는 55.7절에서, 시작 시간 최적화 실전은 72.7절에서, 애플리케이션 유형별 배포 전략은 81.9절에서 다룬다. C# 버전별 기능 목록은 76장이 통째로 담당한다.

## 4.1 SDK 스타일 프로젝트 파일(`.csproj`) 해부

### 여섯 줄에서 시작한다

3.1절에서 본 프로젝트 파일을 다시 꺼낸다.

```xml
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net8.0</TargetFramework>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
  </PropertyGroup>

</Project>
```

XML 태그를 빼고 세면 정보는 **네 조각**뿐이다. 실행 파일을 만들 것, .NET 8을 대상으로 할 것, `using`을 자동으로 넣을 것, 널 가능 참조 타입 분석을 켤 것.

이 파일에 **없는 것**이 더 중요하다.

- 소스 파일 목록이 없다
- 참조하는 어셈블리 목록이 없다
- 출력 폴더 경로가 없다
- 컴파일러를 어떻게 호출할지가 없다
- 빌드 단계 정의가 없다

그런데도 빌드가 된다. 그 이유가 첫 줄의 `Sdk="Microsoft.NET.Sdk"` 하나다.

### 구식 `.csproj`와의 대비

.NET Framework 시절, 정확히는 SDK 스타일이 도입되기 전(2017년 이전)의 프로젝트 파일은 이렇게 생겼다. 아래는 실제 파일의 골격만 남긴 축약본이다.

```xml
<?xml version="1.0" encoding="utf-8"?>
<Project ToolsVersion="15.0"
         xmlns="http://schemas.microsoft.com/developer/msbuild/2003">
  <Import Project="$(MSBuildExtensionsPath)\$(MSBuildToolsVersion)\Microsoft.Common.props"
          Condition="Exists('...')" />
  <PropertyGroup>
    <Configuration Condition=" '$(Configuration)' == '' ">Debug</Configuration>
    <Platform Condition=" '$(Platform)' == '' ">AnyCPU</Platform>
    <ProjectGuid>{8F1A2B3C-4D5E-6F70-8192-A3B4C5D6E7F8}</ProjectGuid>
    <OutputType>Exe</OutputType>
    <RootNamespace>MyApp</RootNamespace>
    <AssemblyName>MyApp</AssemblyName>
    <TargetFrameworkVersion>v4.8</TargetFrameworkVersion>
    <FileAlignment>512</FileAlignment>
  </PropertyGroup>
  <PropertyGroup Condition=" '$(Configuration)|$(Platform)' == 'Debug|AnyCPU' ">
    <DebugSymbols>true</DebugSymbols>
    <DebugType>full</DebugType>
    <Optimize>false</Optimize>
    <OutputPath>bin\Debug\</OutputPath>
    <DefineConstants>DEBUG;TRACE</DefineConstants>
    <ErrorReport>prompt</ErrorReport>
    <WarningLevel>4</WarningLevel>
  </PropertyGroup>
  <PropertyGroup Condition=" '$(Configuration)|$(Platform)' == 'Release|AnyCPU' ">
    <!-- Debug와 거의 같은 내용이 한 벌 더 -->
  </PropertyGroup>
  <ItemGroup>
    <Reference Include="System" />
    <Reference Include="System.Core" />
    <Reference Include="System.Xml.Linq" />
    <Reference Include="System.Data" />
    <Reference Include="System.Xml" />
    <Reference Include="Newtonsoft.Json, Version=13.0.0.0, Culture=neutral,
                        PublicKeyToken=30ad4fe6b2a6aeed, processorArchitecture=MSIL">
      <HintPath>..\packages\Newtonsoft.Json.13.0.3\lib\net45\Newtonsoft.Json.dll</HintPath>
    </Reference>
  </ItemGroup>
  <ItemGroup>
    <Compile Include="Program.cs" />
    <Compile Include="Models\Customer.cs" />
    <Compile Include="Models\Order.cs" />
    <Compile Include="Properties\AssemblyInfo.cs" />
  </ItemGroup>
  <ItemGroup>
    <None Include="App.config" />
    <None Include="packages.config" />
  </ItemGroup>
  <Import Project="$(MSBuildToolsPath)\Microsoft.CSharp.targets" />
</Project>
```

실제 파일은 이보다 길어서, 소스 파일 30개짜리 프로젝트면 100~150행이 예사였다. 무엇이 문제였는지 항목별로 본다.

| 구식 프로젝트의 요소 | 무엇이 문제였나 |
|---|---|
| `<Compile Include="..." />` 파일 목록 | 파일을 하나 추가할 때마다 `.csproj`가 바뀐다. 두 사람이 각자 파일을 추가하면 **머지 충돌**이 난다 |
| `ProjectGuid` | 프로젝트를 복사해 새 프로젝트를 만들면 GUID가 겹쳐 솔루션이 깨진다 |
| Debug/Release `PropertyGroup` 중복 | 거의 같은 내용이 두 벌. 하나만 고치는 실수가 잦다 |
| `<Reference>` + `<HintPath>` | 패키지 버전을 올리면 경로 문자열을 손으로 고쳐야 한다. `packages.config`와 이중 관리 |
| `xmlns` 네임스페이스 선언 | 손으로 편집할 때 태그 하나 잘못 쓰면 조용히 무시된다 |
| 명시적 `<Import>` 두 줄 | 빌드 로직이 어디서 오는지가 파일 안에 드러나지만, 그만큼 손댈 여지가 많다 |

정리하면 구식 `.csproj`는 **"모든 것을 명시한다"** 는 철학이었다. SDK 스타일은 반대다. **"관례를 따르고, 다른 것만 적는다."**

> **📌 SDK 스타일은 파일 형식이 바뀐 게 아니다**
>
> SDK 스타일 프로젝트도 여전히 MSBuild XML이다. 문법이 새로 생긴 게 아니라 **기본값이 통째로 이사한 것**이다. 구식 프로젝트에 적혀 있던 내용은 사라진 게 아니라 SDK가 들고 있는 파일 안으로 들어갔다.
>
> 그래서 SDK 스타일 프로젝트에도 구식 문법을 그대로 쓸 수 있다. `<Compile Include="Program.cs" />`를 직접 쓰는 것도 유효하다 — 단, 자동 포함과 겹치면 "같은 항목이 두 번 들어왔다"는 오류(NETSDK1022)가 난다.

### `Sdk` 특성이 실제로 하는 일

`<Project Sdk="Microsoft.NET.Sdk">`는 문법 설탕이다. MSBuild가 이 특성을 보면 프로젝트 파일의 **맨 위와 맨 아래에 `Import` 두 줄을 몰래 끼워 넣는다.**

```xml
<!-- MSBuild가 실제로 해석하는 형태 (개념적 확장) -->
<Project>
  <Import Project="Sdk.props" Sdk="Microsoft.NET.Sdk" />   <!-- ← 앞에 삽입 -->

  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net8.0</TargetFramework>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
  </PropertyGroup>

  <Import Project="Sdk.targets" Sdk="Microsoft.NET.Sdk" />  <!-- ← 뒤에 삽입 -->
</Project>
```

이 순서가 전부다. 앞뒤가 정해져 있기 때문에 다음 규칙이 생긴다.

```text
┌──────────────────────────────────────────────────────────┐
│  Sdk.props   — SDK가 제공하는 기본 속성                     │
│    OutputPath = bin\$(Configuration)\$(TargetFramework)\  │
│    Optimize   = false   (Debug 기본)                      │
│    ...                                                    │
└──────────────────────────────────────────────────────────┘
                            ↓  나중 값이 이긴다
┌──────────────────────────────────────────────────────────┐
│  내 .csproj  — 내가 덮어쓰는 속성                           │
│    TargetFramework = net8.0                               │
│    Nullable        = enable                               │
└──────────────────────────────────────────────────────────┘
                            ↓  여기서 항목(Item) 확정
┌──────────────────────────────────────────────────────────┐
│  Sdk.targets — 항목 자동 포함 + 빌드 타깃 정의              │
│    Compile Include="**/*.cs"  (bin, obj 제외)             │
│    참조 어셈블리 집합 결정 (TargetFramework 값을 보고)      │
│    Build / Restore / Publish 타깃 정의                     │
└──────────────────────────────────────────────────────────┘
```

**속성은 "마지막에 쓴 값이 이긴다"** — 그래서 SDK 기본값을 내 `.csproj`에서 덮어쓸 수 있다. **항목 자동 포함은 `Sdk.targets`에서, 즉 내 파일을 다 읽은 뒤에 일어난다** — 그래서 `EnableDefaultCompileItems`를 내 `.csproj` 어디에 써도 자동 포함을 끌 수 있다.

> **💡 확장된 프로젝트 파일 전체를 눈으로 보는 법**
>
> "이 속성이 어디서 왔지"를 추측하지 마라. MSBuild가 모든 `Import`를 펼친 최종 XML을 뱉어준다.
>
> ```bash
> dotnet msbuild -preprocess:full.xml
> ```
>
> `full.xml`은 수만 행짜리 파일이 된다. 열어서 궁금한 속성 이름을 검색하면 **어느 SDK 파일 몇 행에서 정의됐는지**가 XML 주석으로 표시되어 있다. 3.1절에서 소개한 `dotnet build -bl`(이진 로그)과 함께, 빌드 문제를 추측 없이 푸는 두 도구다.

### 자동 포함되는 것들

`Microsoft.NET.Sdk`가 관례로 포함하는 항목은 다음과 같다.

| 항목 타입 | 기본 glob | 끄는 속성 |
|---|---|---|
| `Compile` | `**/*.cs` | `EnableDefaultCompileItems` |
| `EmbeddedResource` | `**/*.resx` | `EnableDefaultEmbeddedResourceItems` |
| `None` | 그 외 모든 파일 | `EnableDefaultNoneItems` |
| 위 전부 | — | `EnableDefaultItems` |

세 glob 모두 `bin/`, `obj/`, 그리고 숨김 폴더를 자동으로 제외한다.

```xml
<PropertyGroup>
  <!-- 자동 포함을 끄고 직접 나열하겠다 -->
  <EnableDefaultCompileItems>false</EnableDefaultCompileItems>
</PropertyGroup>

<ItemGroup>
  <Compile Include="Core/**/*.cs" />
  <Compile Include="Generated/Model.cs" />
</ItemGroup>
```

특정 파일만 빼고 싶다면 자동 포함을 끄지 말고 `Remove`를 쓴다. 이쪽이 훨씬 안전하다.

```xml
<ItemGroup>
  <Compile Remove="Experimental/**/*.cs" />
</ItemGroup>
```

> **⚠️ 폴더를 지웠는데 빌드가 깨지는 경우**
>
> 자동 포함은 **빌드 시점의 디스크 상태**를 읽는다. IDE가 프로젝트를 메모리에 캐시해 두었다면, 파일을 탐색기에서 지워도 IDE는 한동안 그 파일이 있다고 믿는다. 반대로 파일을 탐색기에서 추가하면 IDE 새로고침 전까지 안 보인다.
>
> 이 증상이 나면 `dotnet build`를 명령줄에서 한 번 돌려봐라. 명령줄이 성공하고 IDE만 실패하면 IDE 캐시 문제다. 명령줄도 실패하면 진짜 문제다. **진단의 기준선은 항상 명령줄이다.**

### 속성(Property)과 항목(Item)

MSBuild에는 두 종류의 값만 있다. 이 구분을 못 하면 `.csproj`를 읽을 수 없다.

| | 속성(Property) | 항목(Item) |
|---|---|---|
| 담는 것 | 문자열 **하나** | 문자열 **목록** (각각 메타데이터를 가질 수 있다) |
| 선언 위치 | `<PropertyGroup>` | `<ItemGroup>` |
| 참조 문법 | `$(TargetFramework)` | `@(Compile)` |
| 같은 이름을 또 쓰면 | **덮어쓴다** | **추가된다** |
| 예 | `<Nullable>enable</Nullable>` | `<PackageReference Include="..." Version="..." />` |

이 차이가 실전에서 드러나는 순간이 있다.

```xml
<PropertyGroup>
  <DefineConstants>FOO</DefineConstants>
  <DefineConstants>BAR</DefineConstants>   <!-- FOO는 사라진다 -->
</PropertyGroup>
```

속성은 덮어쓰기 때문에 `FOO`가 없어진다. 누적하려면 자기 자신을 참조해야 한다.

```xml
<PropertyGroup>
  <DefineConstants>$(DefineConstants);FOO</DefineConstants>
  <DefineConstants>$(DefineConstants);BAR</DefineConstants>   <!-- FOO;BAR -->
</PropertyGroup>
```

> **⚠️ `DefineConstants`를 통째로 덮어쓰면 `DEBUG`가 사라진다**
>
> SDK는 Debug 구성에서 `DEBUG`와 `TRACE`를 이미 `DefineConstants`에 넣어둔다. `<DefineConstants>MY_FLAG</DefineConstants>`라고 쓰면 그 둘이 날아간다. 그러면 `#if DEBUG` 블록이 전부 컴파일에서 빠지고, `Debug.Assert`가 조용히 사라지고, 그런데도 빌드는 성공한다. 조용히 깨지는 전형이다.
>
> 반드시 `$(DefineConstants);` 접두를 붙여라.

### 조건(Condition)

거의 모든 요소에 `Condition` 특성을 붙일 수 있다.

```xml
<PropertyGroup Condition="'$(Configuration)' == 'Release'">
  <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
</PropertyGroup>

<ItemGroup Condition="'$(TargetFramework)' == 'netstandard2.0'">
  <PackageReference Include="System.Text.Json" Version="8.0.0" />
</ItemGroup>
```

비교 대상을 작은따옴표로 감싸는 것은 관례가 아니라 **필수에 가깝다.** 속성이 비어 있으면 `$(Configuration)`이 빈 문자열로 치환되는데, 따옴표가 없으면 `== 'Release'`의 좌변이 사라져 문법 오류가 되거나 예상 밖으로 참이 된다.

> **📌 자주 쓰는 내장 속성**
>
> | 속성 | 값 예시 |
> |---|---|
> | `$(Configuration)` | `Debug`, `Release` |
> | `$(TargetFramework)` | `net8.0` (멀티 타깃 시 빌드마다 다름) |
> | `$(TargetFrameworkIdentifier)` | `.NETCoreApp`, `.NETStandard`, `.NETFramework` |
> | `$(MSBuildProjectDirectory)` | 프로젝트 파일이 있는 폴더의 절대 경로 |
> | `$(MSBuildThisFileDirectory)` | **이 MSBuild 파일**이 있는 폴더(끝에 구분자 포함) |
> | `$(OutputPath)` | `bin\Debug\net8.0\` |
> | `$(OS)` | `Windows_NT` 또는 `Unix` |

### 컴파일 결과에는 무엇이 남는가

`.csproj`의 속성 중 상당수는 **컴파일러 명령줄 인자로 번역되고 사라진다.** 예를 들어 `<Optimize>true</Optimize>`는 `csc`에 `-optimize+`로 전달될 뿐, 산출 어셈블리에 "최적화 켬"이라는 플래그가 남지 않는다(디버그 특성으로 간접 추론할 수는 있다).

반면 어셈블리에 **흔적을 남기는** 속성도 있다.

| 속성 | 어셈블리에 남는 형태 |
|---|---|
| `TargetFramework` | `[assembly: TargetFramework(".NETCoreApp,Version=v8.0")]` |
| `AssemblyVersion` | 매니페스트의 버전 필드 (52.2절) |
| `Nullable` | 널 가능성 메타데이터와 `[NullableContext]` 특성 |
| `AllowUnsafeBlocks` | IL 자체(`unsafe` 코드가 실제로 있을 때) |
| `Deterministic` | 동일 입력이면 바이트까지 동일한 출력 |

이 구분은 실무에서 중요하다. **어셈블리만 받아서 `.csproj`를 복원할 수는 없다.** 남지 않는 정보가 훨씬 많다.

## 4.2 TFM(대상 프레임워크 모니커)과 멀티 타깃팅

### TFM 하나가 결정하는 것

`<TargetFramework>` 요소는 프로젝트가 **어느 런타임을 대상으로 빌드되는지**를 정하고, 그 값을 **TFM(Target Framework Moniker, 대상 프레임워크 모니커)** 이라고 부른다.

`net8.0`이라는 다섯 글자가 결정하는 것을 나열하면 이렇다.

1. 컴파일 시 참조되는 **참조 어셈블리 집합** (4.4절)
2. 기본 **C# 언어 버전** (4.5절)
3. 자동으로 켜지는 **암시적 `using` 목록** (SDK 종류에 따라 다르다)
4. `runtimeconfig.json`에 기록되는 **런타임 이름과 버전** (3.1절)
5. NuGet 패키지에서 **어느 폴더의 어셈블리를 꺼낼지** (4.7절)
6. `#if`에서 쓸 수 있는 **전처리기 기호**

여섯 가지가 전부 한 줄에 묶여 있다. 그래서 TFM은 프로젝트 파일에서 가장 중요한 한 줄이다.

### TFM 문법

TFM은 세 부분으로 이루어진다. 뒤 두 부분은 선택이다.

```text
net8.0-windows10.0.19041.0
└┬─┘└┬┘ └──┬──┘└────┬─────┘
 │   │     │        └── 플랫폼 버전 (선택)
 │   │     └─────────── 플랫폼 (선택)
 │   └───────────────── 프레임워크 버전
 └───────────────────── 프레임워크 식별자
```

실제로 쓰이는 값들이다.

| TFM | 의미 | 비고 |
|---|---|---|
| `net8.0` | .NET 8 | 크로스 플랫폼. 새 프로젝트의 기본 |
| `net9.0` | .NET 9 ※ | |
| `net7.0` / `net6.0` / `net5.0` | .NET 7 / 6 / 5 | |
| `netcoreapp3.1` | .NET Core 3.1 | 마지막 "Core" 이름 |
| `netstandard2.0` | .NET Standard 2.0 | **런타임이 아니라 사양** (4.3절) |
| `netstandard2.1` | .NET Standard 2.1 | .NET Framework가 지원하지 않는다 |
| `net48` / `net472` / `net461` | .NET Framework 4.8 / 4.7.2 / 4.6.1 | **Windows 전용** |
| `net8.0-windows` | .NET 8 + Windows 전용 API | WPF·Windows Forms |
| `net8.0-windows10.0.19041.0` | 위 + 특정 Windows 빌드의 API | WinUI 등 |
| `net8.0-android` / `net8.0-ios` | .NET 8 + 모바일 플랫폼 API | MAUI |

> **⚠️ `net48`과 `net8.0`은 겉보기와 달리 다른 세계다**
>
> `net48`은 .NET Framework 4.8, `net8.0`은 .NET 8이다. 숫자만 보면 `net48`이 더 최신 같지만 완전히 다른 런타임이다. .NET Framework의 TFM은 점이 없고(`net48`, `net472`), 모던 .NET은 점이 있다(`net8.0`, `net5.0`).
>
> `net5.0`이라는 이름을 정할 때 마이크로소프트가 `net50`을 피하고 점을 넣은 것이 이 혼동 때문이다. 그래도 여전히 혼동은 남았다. **점의 유무를 확인하는 습관을 들여라.**

### 플랫폼 지정 TFM

`net8.0-windows`처럼 플랫폼이 붙으면 그 플랫폼 전용 API가 참조 집합에 추가된다. WPF나 Windows Forms를 쓰려면 여기에 속성을 하나 더 켠다.

```xml
<PropertyGroup>
  <OutputType>WinExe</OutputType>
  <TargetFramework>net8.0-windows</TargetFramework>
  <UseWPF>true</UseWPF>
  <!-- <UseWindowsForms>true</UseWindowsForms> -->
</PropertyGroup>
```

플랫폼이 붙은 TFM으로 빌드한 어셈블리는 **그 플랫폼에서만 돈다.** `net8.0-windows` 라이브러리를 Linux에서 실행하는 .NET 8 앱이 참조하면 빌드 경고 또는 오류가 나고, 참조를 강제해도 런타임에 타입 로드가 실패한다.

> **📌 플랫폼 버전을 붙이는 이유**
>
> `net8.0-windows10.0.19041.0`처럼 뒤에 Windows 빌드 번호를 붙이면 그 빌드 이후에 추가된 Windows 런타임 API까지 참조할 수 있다. 대신 그보다 낮은 Windows에서는 안 돈다.
>
> ns05의 서술대로, UWP가 널리 쓰이지 못한 이유 중 하나가 이것이다. UWP는 OS의 WinRT 타입에 의존했으므로 **Windows 버전 범위를 고르는 일**이 개발자 몫이었다. 낡은 API를 대상으로 하거나, 고객에게 Windows 업데이트를 요구하거나 둘 중 하나였다. Windows App SDK(WinUI 3)는 이 API들을 OS에서 런타임 쪽으로 옮겨 그 부담을 줄이려 한 시도다.

### 상위 호환의 방향

ns05의 표현을 그대로 옮기면 이렇다. **어셈블리는 자기 대상보다 새로운 런타임에서는 돌지만, 오래된 런타임에서는 돌지 않는다.**

```text
   빌드 대상          실행 가능한 런타임
   ─────────          ──────────────────
   net6.0      →      .NET 6, .NET 7, .NET 8, .NET 9 ...    (위로 열려 있다)
   net8.0      →      .NET 8, .NET 9 ...
   net8.0      ×      .NET 6, .NET 7                        (아래로 닫혀 있다)
```

라이브러리를 만든다면 이 방향성이 곧 정책이 된다. **낮은 TFM으로 만들수록 더 많은 소비자가 쓸 수 있고, 대신 내가 쓸 수 있는 API가 줄어든다.** p807의 표를 옮긴다.

| 클래스 라이브러리 대상 | 이 라이브러리를 참조할 수 있는 프로젝트 |
|---|---|
| `netstandard2.0` | .NET Framework 4.6.1+, .NET Core 2+, .NET 5+, Mono 5.4+, Xamarin.Android 8+, Xamarin.iOS 10.14+ |
| `netstandard2.1` | .NET Core 3+, .NET 5+, Mono 6.4+, Xamarin.Android 10+, Xamarin.iOS 12.16+ |
| `net6.0` | .NET 6 이상 |
| `net7.0` | .NET 7 이상 |
| `net8.0` | .NET 8 이상 |

> **⚠️ 새 클래스 라이브러리의 기본 TFM은 SDK 버전에 따라 다르다**
>
> `dotnet new classlib`가 만드는 TFM은 설치된 SDK에 좌우된다.
>
> | SDK | 새 클래스 라이브러리의 기본 TFM |
> |---|---|
> | .NET Core 3.1 | `netstandard2.0` |
> | .NET 6 | `net6.0` |
> | .NET 7 | `net7.0` |
> | .NET 8 | `net8.0` |
>
> 즉 옛 블로그 글을 따라 `dotnet new classlib`를 치면 `netstandard2.0`이 나온다고 적혀 있어도, 지금 실행하면 `net8.0`이 나온다. **템플릿이 준 값을 그대로 받아들이지 말고 항상 확인하고 의식적으로 정하라.** 이것이 p807이 강조하는 지침이다.

### 멀티 타깃팅

TFM을 여러 개 지정하려면 요소 이름을 **복수형**으로 바꾸고 세미콜론으로 나열한다.

```xml
<PropertyGroup>
  <TargetFrameworks>net8.0;netstandard2.0;net48</TargetFrameworks>
</PropertyGroup>
```

이때 **TFM마다 별도의 출력 어셈블리가 생성된다.** 컴파일이 세 번 도는 것이다.

```text
bin/Release/
├── net8.0/
│   └── MyLib.dll          ← net8.0 참조 집합으로 컴파일
├── netstandard2.0/
│   └── MyLib.dll          ← netstandard 참조 집합으로 컴파일
└── net48/
    └── MyLib.dll          ← .NET Framework 4.8 참조 집합으로 컴파일
```

> **⚠️ `TargetFramework`와 `TargetFrameworks` — 글자 하나 차이**
>
> 단수형에 세미콜론으로 여러 값을 넣으면 **오류 메시지가 몹시 불친절하다.** `net8.0;net48`이라는 이름의 TFM을 찾을 수 없다는 식으로 나온다. 반대로 복수형에 값 하나만 넣는 것은 정상 동작한다.
>
> p807의 지적대로, 한 글자 차이라 눈으로 찾기 어렵다. 알 수 없는 TFM 오류가 나면 **가장 먼저 s를 세어라.**

### 조건부 컴파일

멀티 타깃 빌드는 TFM마다 전처리기 기호를 자동으로 정의한다.

```csharp
public static class Hasher
{
#if NET8_0_OR_GREATER
    // .NET 8에는 정적 HashData가 있다 — 배열 할당이 없다
    public static byte[] Sha256(byte[] data)
        => System.Security.Cryptography.SHA256.HashData(data);
#else
    // netstandard2.0에는 없다 — 인스턴스를 만들어야 한다
    public static byte[] Sha256(byte[] data)
    {
        using var sha = System.Security.Cryptography.SHA256.Create();
        return sha.ComputeHash(data);
    }
#endif
}
```

자동 정의되는 기호는 다음과 같다.

| TFM | 정의되는 기호(일부) |
|---|---|
| `net8.0` | `NET`, `NET8_0`, `NET8_0_OR_GREATER`, `NET7_0_OR_GREATER`, ..., `NETCOREAPP` |
| `net8.0-windows` | 위 전부 + `WINDOWS`, `NET8_0_WINDOWS` |
| `netstandard2.0` | `NETSTANDARD`, `NETSTANDARD2_0`, `NETSTANDARD2_0_OR_GREATER`, ..., `NETSTANDARD1_0_OR_GREATER` |
| `net48` | `NETFRAMEWORK`, `NET48`, `NET48_OR_GREATER`, ..., `NET20_OR_GREATER` |

> **💡 `NET8_0`보다 `NET8_0_OR_GREATER`를 써라**
>
> `#if NET8_0`은 정확히 net8.0일 때만 참이다. 나중에 `net9.0`을 TFM 목록에 추가하는 순간 이 블록이 조용히 빠지고 `#else` 쪽이 컴파일된다. 그러면 .NET 9에서 오히려 구식 코드가 돈다.
>
> **"이 버전 이상"이 의도라면 항상 `_OR_GREATER`를 써라.** 예외는 특정 버전에만 있는 버그를 우회할 때뿐이고, 그때는 주석으로 이유를 남겨야 한다.

조건부 컴파일 대신 **패키지 참조 자체를 TFM별로** 나누는 방법도 있다. 오래된 TFM에만 보완 패키지를 붙이는 전형적 패턴이다.

```xml
<ItemGroup Condition="'$(TargetFramework)' == 'netstandard2.0'">
  <PackageReference Include="System.Text.Json" Version="8.0.0" />
  <PackageReference Include="System.Memory" Version="4.5.5" />
</ItemGroup>
```

### 멀티 타깃팅의 비용

- **빌드 시간**이 TFM 수만큼 배수로 늘어난다.
- **테스트**를 각 TFM에서 따로 돌려야 진짜 검증이다. 하나만 돌리면 나머지는 "컴파일되더라" 수준의 보증만 남는다.
- **코드 복잡도**가 오른다. `#if`가 늘수록 읽기 어려워지고, 한쪽만 고치는 버그가 생긴다.
- **API 표면이 어긋날 수 있다.** TFM마다 공개 API가 다르면 소비자가 혼란스럽다.

> **💡 멀티 타깃 대신 라이브러리를 둘로 나누는 선택**
>
> p807은 "`netstandard2.0`용과 `net8.0`용 클래스 라이브러리를 각각 하나씩 만드는 것"을 대안으로 제시한다. `#if`가 다섯 개를 넘어가기 시작하면, 사실은 두 개의 다른 라이브러리를 억지로 한 파일에 넣고 있는 것일 가능성이 높다.
>
> 판단 기준은 간단하다. **`#if`가 구현 세부에만 있으면 멀티 타깃이 맞다. 공개 API 모양이 갈라지기 시작하면 프로젝트를 나눠라.**

## 4.3 .NET Standard — 왜 생겼고 왜 저물었나

### 문제 — 교집합이 없다

2.3절에서 본 것처럼 .NET은 오랫동안 여러 갈래였다. .NET Framework, .NET Core, Mono/Xamarin, UWP, Unity. 이들은 **각자의 CLR과 BCL을 가졌고, 어느 하나가 다른 하나의 부분집합이 아니었다.** 기능이 겹치되 완전히 포개지지 않는 상태였다.

라이브러리 저자에게 이건 골치였다. NuGet에 올린 라이브러리가 .NET Framework에서만 돌면 가치가 절반이다. 그렇다고 런타임마다 별도 빌드를 만들면 유지 비용이 폭발한다.

```text
        .NET Framework          .NET Core            Xamarin/Mono
        ┌─────────────┐      ┌─────────────┐      ┌─────────────┐
        │ A B C D E   │      │ B C D   F G │      │ B C   E F   │
        │       ← 이 셋의 공통분모는 무엇인가? →           │
        └─────────────┘      └─────────────┘      └─────────────┘
                              B, C 만 확실하다
```

### PCL — 실패한 첫 시도

.NET Standard 이전에는 **PCL(Portable Class Library, 이식 가능한 클래스 라이브러리)** 이 있었다. PCL에서는 지원할 플랫폼을 직접 체크박스로 고르고, 라이브러리는 **그 플랫폼들이 지원하는 API의 교집합**만 쓸 수 있었다.

문제는 조합 폭발이었다. 플랫폼 목록을 하나 바꾸면 쓸 수 있는 API 집합이 통째로 달라졌고, 그 조합이 수십 가지였다. p807의 표현대로 마이크로소프트는 **"이 방식이 지속 가능하지 않다"** 고 판단했고, 그래서 .NET Standard를 만들었다.

### .NET Standard — 사양이지 런타임이 아니다

.NET Standard는 **"모든 미래의 .NET 플랫폼이 지원해야 하는 단일 API 집합"** 이다. 플랫폼 조합마다 교집합을 계산하는 대신, **인위적인 부분집합을 미리 정의해 두고** 각 런타임이 그것을 구현하게 했다.

> **⚠️ .NET Standard는 실행되지 않는다**
>
> ns05의 비유가 정확하다. **.NET Standard는 C#의 인터페이스와 같다.** 인터페이스가 스스로 실행되지 않고 구현 타입(런타임)이 실행되듯, `netstandard2.0` 프로젝트도 스스로 실행되지 않는다.
>
> 그래서 `netstandard2.0`은 **라이브러리를 위한 TFM**이지 애플리케이션을 위한 TFM이 아니다. 콘솔 앱의 `TargetFramework`에 `netstandard2.0`을 넣는 것은 의미가 없다. 다른 비유로는 HTML5가 있다 — 크롬과 엣지가 HTML5 표준을 구현하듯, .NET Core·.NET Framework·Xamarin이 .NET Standard를 구현한다.

### 버전별 도달 범위

| .NET Standard | 지원 런타임 | 실무 평가 |
|---|---|---|
| **2.0** | 모던 .NET(5~9, .NET Core 2+), **.NET Framework 4.6.1+**, UWP 10.0.16299+, Mono 5.4+ | **유일하게 실용적인 버전** |
| 2.1 | .NET Core 3+, Mono 6.4+ | .NET Framework 지원 없음 → 존재 이유가 반쯤 사라졌다 |
| 1.x (1.1~1.6) | .NET Core 1.0, .NET Framework 4.5 등 | 2.0에 있는 API 수천 개가 빠져 있다. 사실상 폐기 |

```xml
<PropertyGroup>
  <TargetFramework>netstandard2.0</TargetFramework>
</PropertyGroup>
```

**2.1이 왜 실패했는가**가 핵심이다. p807의 설명대로 .NET Standard 2.1은 약 3,000개의 API를 추가했는데, 그중 일부는 **하위 호환을 깨는 런타임 변경**을 요구했다. .NET Framework는 마이크로소프트의 레거시 플랫폼으로서 "가능한 한 변하지 않아야" 했으므로 그 변경을 받아들일 수 없었다. 그래서 .NET Framework 4.8은 마지막 버전임에도 **.NET Standard 2.0에 머물렀다.**

.NET Standard가 놓으려던 다리는 정확히 여기서 끊겼다. **.NET Framework와 모던 .NET을 잇는 다리는 영원히 2.0이다.**

### 왜 저물었나

.NET 5부터 상황이 달라졌다. p807의 정리를 그대로 옮긴다.

- **.NET 5는 .NET Standard의 필요를 없앴다.** 모든 프로젝트 유형이 하나의 .NET 버전을 대상으로 할 수 있게 됐기 때문이다.
- **.NET 5 이후의 각 버전은 이전 버전과 하위 호환된다.** `net5.0` 클래스 라이브러리는 .NET 5 이상의 모든 프로젝트에서 쓸 수 있다.
- **MAUI가 나오면서 모바일·데스크톱까지 통합됐다.** Mono의 공개 인터페이스가 .NET 6에서 .NET과 병합되어, Mono는 사실상 .NET의 한 구현이 되었다.

한 줄로 요약하면 이렇다. **런타임이 여럿이라서 표준이 필요했는데, 런타임이 하나가 되면서 표준이 필요 없어졌다.**

### 지금도 `netstandard2.0`을 써야 할 자리

그렇다고 0이 된 것은 아니다. 원천이 명시하는 잔여 용도는 셋이다.

- **.NET Framework 소비자가 있는 라이브러리.** .NET Framework 4.8이 참조할 수 있는 최신 TFM이 이것뿐이다.
- **레거시 Xamarin 앱 지원.** 구버전 Xamarin은 모던 .NET TFM을 모른다.
- **소스 생성기(source generator).** p807이 명시한다 — 소스 생성기를 만들려면 `netstandard2.0` 클래스 라이브러리를 써야 한다.

세 번째가 의외로 자주 걸린다. 소스 생성기는 **컴파일러 프로세스 안에서 실행되는** 코드다. 컴파일러가 어느 런타임에서 도는지 알 수 없으므로, 가장 넓은 공통 분모로 만들어야 한다.

> **⚠️ `netstandard2.0`의 기본 C# 버전은 7.3이다**
>
> 이것이 `netstandard2.0`의 진짜 대가다. 아무것도 지정하지 않으면 C# 7.3으로 컴파일된다 — `switch` 식도, 널 가능 참조 타입도, 레코드도, 최상위 문도 못 쓴다.
>
> p807은 이 경우 `<LangVersion>`으로 언어 버전을 올리라고 안내한다.
>
> ```xml
> <PropertyGroup>
>   <TargetFramework>netstandard2.0</TargetFramework>
>   <LangVersion>12</LangVersion>
> </PropertyGroup>
> ```
>
> 다만 **문법이 열린다고 모든 기능이 도는 것은 아니다.** 어느 것이 되고 어느 것이 안 되는지가 다음 절(4.5절)의 주제다.

### .NET Framework 어셈블리를 모던 .NET에서 참조하기

.NET Framework 전용으로만 존재하고 .NET Standard·모던 .NET 버전이 없는 라이브러리를 만나는 일은 흔하다. ns05에 따르면 .NET 5+ 및 .NET Core 프로젝트는 **.NET Framework 어셈블리를 참조하는 것이 허용된다.** 단 두 가지 단서가 붙는다.

- 그 .NET Framework 어셈블리가 **지원되지 않는 API를 호출하면 예외가 던져진다.**
- **사소하지 않은 의존성은 해석에 실패할 수 있고, 실제로 자주 실패한다.**

실무적으로는 비관리 DLL을 감싸는 얇은 래퍼처럼 **단순한 경우에만 통한다.**

> **⚠️ "빌드가 됐으니 되겠지"가 가장 위험하다**
>
> 이 시나리오의 실패는 **컴파일 타임이 아니라 런타임에** 드러난다. 그것도 특정 코드 경로를 밟았을 때만이다. 빌드 성공과 단위 테스트 통과가 안전을 보장하지 않는다.
>
> 이런 참조를 넣었다면 **그 라이브러리를 호출하는 모든 경로에 통합 테스트를 붙여라.** 그리고 이건 임시방편이지 목적지가 아니다. 원본 라이브러리의 모던 .NET 버전을 찾거나, 소스가 있으면 `netstandard2.0`으로 다시 빌드하는 쪽이 정답이다.

## 4.4 참조 어셈블리(reference assembly)와 구현 어셈블리

### 컴파일러가 보는 것과 런타임이 쓰는 것은 다르다

3.2절에서 컴파일러가 IL을 만드는 과정을 봤다. 그때 컴파일러는 `System.Console.WriteLine`이 존재한다는 것을 어떻게 알았는가? 어딘가에 있는 어셈블리의 메타데이터를 읽어서다. 그런데 **그 어셈블리는 실행 시 실제로 쓰이는 어셈블리가 아니다.**

| | 참조 어셈블리 (reference assembly) | 구현 어셈블리 (implementation assembly) |
|---|---|---|
| 언제 쓰이나 | **컴파일 시** | **런타임** |
| 담고 있는 것 | 공개 API 표면(타입·멤버 시그니처)과 메타데이터 | 실제 IL 코드 |
| 메서드 본문 | **없다** | 있다 |
| 위치(.NET 8 기준 Windows) | `C:\Program Files\dotnet\packs\Microsoft.NETCore.App.Ref\8.0.0\ref\net8.0\` | `C:\Program Files\dotnet\shared\Microsoft.NETCore.App\8.0.x\` |
| 배포되나 | 아니다 | 그렇다 |

ns05의 서술을 옮기면 이렇다. `.NET Standard`를 대상으로 하면 프로젝트는 `netstandard.dll`이라는 어셈블리를 암묵적으로 참조한다. 이 어셈블리는 선택한 .NET Standard 버전에서 허용되는 모든 타입과 멤버를 담고 있다. **이것을 참조 어셈블리라고 부르는 이유는, 오직 컴파일러를 위해서만 존재하며 컴파일된 코드를 담지 않기 때문이다.** 런타임에는 어셈블리 리디렉션 특성을 통해 "진짜" 어셈블리가 식별되고, 어떤 어셈블리가 선택되는지는 최종적으로 어느 런타임·플랫폼에서 도는지에 달려 있다.

그리고 흥미롭게도, **`net8.0`을 대상으로 할 때도 같은 일이 벌어진다.** 프로젝트는 선택한 .NET 버전의 런타임 어셈블리를 그대로 반영한 참조 어셈블리 집합을 암묵적으로 참조한다.

```text
      컴파일 타임                              런타임
  ┌────────────────────┐              ┌──────────────────────────┐
  │  Program.cs        │              │  MyApp.dll               │
  └─────────┬──────────┘              └────────────┬─────────────┘
            │ csc                                  │ CLR이 로드
            ↓                                      ↓
  ┌────────────────────┐              ┌──────────────────────────┐
  │ 참조 어셈블리 팩     │   ← 다르다 → │ 공유 프레임워크           │
  │ packs\...App.Ref\  │              │ shared\...NETCore.App\   │
  │ System.Runtime.dll │              │ System.Private.CoreLib   │
  │  (본문 없음)        │              │  (실제 IL과 네이티브 코드) │
  └────────────────────┘              └──────────────────────────┘
```

### 왜 이렇게 나눠 놓았나

세 가지 이유가 있다.

1. **버전 관리** — 참조 어셈블리는 API 표면만 담으므로, 구현이 바뀌어도 표면이 그대로면 재컴파일이 필요 없다. 표면이 바뀌었는지를 기계적으로 판정할 수 있다.
2. **크로스 플랫폼 호환성** — 컴파일 시점에는 "Linux용 구현이냐 Windows용 구현이냐"를 알 필요가 없다. 표면만 같으면 된다.
3. **설치되지 않은 버전을 대상으로 삼기** — ns05가 명시한다. 이 구조 덕분에 **내 기계에 설치된 것과 다른 .NET 버전을 대상으로 빌드할 수 있다.** .NET 8 SDK 하나로 `net6.0` 프로젝트를 빌드할 수 있는 이유가 이것이다. .NET 6 런타임이 없어도 참조 어셈블리 팩만 있으면 컴파일은 된다(실행은 못 한다).

> **⚠️ "컴파일은 되는데 실행이 안 된다"의 진짜 이유**
>
> `dotnet build`는 성공했는데 `dotnet run`이 "framework 'Microsoft.NETCore.App', version '6.0.0' was not found"로 죽는 경우가 있다. 위 3번이 원인이다. **참조 어셈블리는 있었고 런타임은 없었다.**
>
> `dotnet --list-runtimes`로 설치된 런타임을, `dotnet --list-sdks`로 설치된 SDK를 확인하는 습관을 들여라. 이 둘은 별개다.

### `System.Runtime.dll`에는 타입이 0개다

p807이 지적하는 사실이 하나 있다. IDE에서 `string`을 "정의로 이동"하면 `System.Runtime.dll`이라고 표시된다. 그런데 **그 어셈블리에는 타입이 하나도 들어 있지 않다.**

`System.Runtime.dll`이 담고 있는 것은 **타입 전달자(type-forwarder)** 다. 타입 전달자는 어떤 어셈블리에 존재하는 것처럼 보이지만 실제로는 다른 곳에 구현된 특수한 타입이다. `string`의 경우 그 "다른 곳"은 .NET 런타임 깊숙한 곳, 즉 `System.Private.CoreLib.dll`이다.

> **📌 타입 전달자는 왜 필요한가**
>
> 타입을 원래 있던 어셈블리에서 다른 어셈블리로 옮기는 리팩터링을 했다고 하자. 타입 전달자를 정의하지 않으면, 원래 어셈블리를 참조하던 프로젝트는 그 타입을 못 찾고 **런타임 예외**를 만난다.
>
> .NET이 `System.Private.CoreLib`라는 "사적인" 어셈블리에 핵심 타입을 몰아넣고, 공개 어셈블리들은 전달자만 담게 한 것은 이 메커니즘을 대규모로 쓴 결과다. `System`이라는 이름의 어셈블리가 껍데기인 이유도 같다. 자세한 것은 52장에서 다룬다.

### 내 프로젝트도 참조 어셈블리를 만든다

3.1절의 `obj/` 표에 `Debug/net8.0/ref/HelloIL.dll`이 있었다. 이것이 **내 프로젝트의 참조 어셈블리**다. 공개 API 표면만 담고 메서드 본문이 없다.

용도는 **증분 빌드**다. 프로젝트 A를 프로젝트 B가 참조할 때, A의 메서드 *본문*만 바뀌었다면 B는 재컴파일할 필요가 없다. 빌드 시스템은 A의 참조 어셈블리 해시가 그대로인지만 보면 된다.

```text
  A의 메서드 본문 수정  →  A/obj/ref/A.dll 변화 없음  →  B 재컴파일 생략
  A의 public 시그니처 수정 → A/obj/ref/A.dll 변화     →  B 재컴파일 필요
```

`<ProduceReferenceAssembly>`로 끌 수 있지만, 큰 솔루션에서는 켜두는 편이 훨씬 이득이다.

> **💡 참조 어셈블리를 직접 열어봐라**
>
> 참조 어셈블리 팩의 `System.Runtime.dll`을 ILSpy로 열고 아무 메서드나 골라 IL을 보면, 본문이 비어 있거나 `throw null;` 한 줄로 되어 있는 것을 확인할 수 있다.
>
> 이 실험은 5분이면 끝나지만 얻는 게 크다. **"참조하는 것"과 "실행하는 것"이 다른 물건이라는 사실**이 손에 잡히면, 앞으로 어셈블리 로딩 오류를 훨씬 빨리 진단하게 된다. 로딩 규칙 전체는 52.8절과 52.15절에서 다룬다.

## 4.5 런타임 버전과 C# 언어 버전의 관계, `LangVersion`

### 기본 매핑

`.csproj` 어디에도 "C# 12를 쓰겠다"는 말이 없는데 C# 12 문법이 컴파일된다. **런타임 대상이 언어 버전을 자동으로 정하기 때문**이다.

| 대상 프레임워크 | 기본 C# 언어 버전 |
|---|---|
| .NET 9 ※ | C# 13 |
| .NET 8 | C# 12 |
| .NET 7 | C# 11 |
| .NET 6 | C# 10 |
| .NET 5 | C# 9 |
| .NET Core 3.x | C# 8 |
| .NET Core 2.x | C# 7.3 |
| .NET Standard 2.1 | C# 8 |
| .NET Standard 2.0 | C# 7.3 |
| .NET Standard 1.x | C# 7.3 |
| .NET Framework (전 버전) | C# 7.3 |

이 매핑은 임의가 아니다. ns05의 설명 그대로다. **후기 버전의 C#은 후기 런타임에서 도입된 타입에 의존하는 기능을 포함하기 때문이다.**

### 언어 버전을 올리는 법

```xml
<PropertyGroup>
  <TargetFramework>netstandard2.0</TargetFramework>
  <LangVersion>12</LangVersion>
</PropertyGroup>
```

`<LangVersion>`이 받는 값은 다음과 같다.

| 값 | 의미 |
|---|---|
| `7.3`, `8`, `9`, `10`, `11`, `12`, `13` | 그 버전으로 고정 |
| `latestMajor` | 설치된 컴파일러가 지원하는 최신 주 버전 |
| `latest` | 최신 주 버전 + 부 버전 |
| `preview` | 미리 보기 기능 포함 (프로덕션 금지) |
| `default` | 대상 프레임워크가 정하는 기본값 (= 지정 안 한 것과 같다) |

### 무엇이 올라가고 무엇이 안 올라가는가

여기가 핵심이다. ns05의 문장을 정확히 옮긴다. **오래된 런타임(.NET Framework 등)에 최신 언어 버전(C# 12 등)을 조합하면, 새로운 .NET 타입에 의존하는 언어 기능은 동작하지 않는다.** 다만 어떤 경우에는 그 타입을 직접 정의하거나 NuGet 패키지에서 가져올 수 있다.

기능을 세 부류로 나누면 이해가 쉽다.

```text
  ┌─────────────────────────────────────────────────────────┐
  │ 1군. 순수 문법 — 컴파일러만 알면 된다                      │
  │   컴파일 결과가 옛 IL로 떨어진다. 런타임은 차이를 모른다.    │
  │   예: 식 본문 멤버, 보간 문자열, switch 식, 패턴 매칭 대부분,│
  │       파일 범위 네임스페이스, 기본 생성자, 지역 함수         │
  │   → 런타임 상관없이 동작                                   │
  ├─────────────────────────────────────────────────────────┤
  │ 2군. 마커 타입 필요 — 타입만 있으면 된다                    │
  │   컴파일러가 특정 특성/타입을 참조하는 IL을 만든다.          │
  │   그 타입이 없으면 컴파일 오류. 직접 정의하면 해결된다.       │
  │   예: init 접근자·record (IsExternalInit),                │
  │       required 멤버 (RequiredMemberAttribute),           │
  │       범위·인덱스 (System.Index, System.Range)            │
  │   → 타입을 채워 넣으면 동작                                │
  ├─────────────────────────────────────────────────────────┤
  │ 3군. 런타임 지원 필요 — 손쓸 방법이 없다                    │
  │   CLR 자체가 바뀌어야 하는 기능.                           │
  │   예: 기본 인터페이스 멤버, 정적 추상 인터페이스 멤버,        │
  │       ref 필드                                           │
  │   → LangVersion을 올려도 옛 런타임에서는 불가              │
  └─────────────────────────────────────────────────────────┘
```

2군의 대표 사례를 보자. `netstandard2.0` 프로젝트에서 `LangVersion`을 12로 올리고 레코드를 쓰면 이런 오류를 만난다.

```csharp
// netstandard2.0 + LangVersion 12
public record Point(int X, int Y);
```

```text
error CS0518: 미리 정의된 형식 'System.Runtime.CompilerServices.IsExternalInit'이(가)
정의되어 있지 않거나 가져오지 않았습니다.
```

이 타입은 **표식일 뿐 아무 동작도 없다.** 그래서 직접 정의하면 그대로 통한다.

```csharp
// netstandard2.0에서 init/record를 쓰기 위한 마커 타입
namespace System.Runtime.CompilerServices
{
    internal static class IsExternalInit { }
}
```

> **⚠️ 마커 타입을 `public`으로 정의하지 마라**
>
> 위 코드에서 `internal`이 중요하다. `public`으로 정의한 라이브러리를 모던 .NET 프로젝트가 참조하면 **`IsExternalInit`이 두 번 정의되어 모호하다**는 오류(CS0433)가 난다. 내 어셈블리 안에서만 쓸 것이므로 `internal`이 맞다.
>
> 이런 마커 타입을 손으로 관리하는 대신 자동으로 채워주는 NuGet 패키지들이 있다. 다만 어떤 패키지를 쓰든 **그 패키지가 넣는 타입이 `internal`인지 확인하라.**

3군은 우회로가 없다. 기본 인터페이스 멤버는 인터페이스가 구현을 가질 수 있다는 것을 **CLR의 메서드 디스패치가 알아야** 하는 기능이다. 컴파일러 혼자 해결할 수 없다.

> **⚠️ 컴파일러가 항상 친절하게 막아주지는 않는다**
>
> 3군 기능 중 상당수는 컴파일 오류로 걸러진다. 하지만 **2군인데 마커 타입이 우연히 존재해서 컴파일은 되고, 정작 그 타입의 의미를 옛 런타임이 다르게 해석하는** 경계 사례가 있을 수 있다.
>
> 그래서 원칙은 하나다. **`LangVersion`을 대상 프레임워크의 기본값보다 올렸다면, 그 TFM에서 반드시 실제로 실행해서 테스트하라.** 멀티 타깃 프로젝트에서 `net8.0`만 테스트하고 `netstandard2.0`은 "컴파일되니까 되겠지"로 넘기는 것이 가장 흔한 사고 경로다.

### SDK 버전과 런타임 버전은 별개다

여기서 자주 헷갈리는 축이 하나 더 있다. **어떤 SDK로 빌드하는가**와 **어떤 런타임을 대상으로 하는가**는 독립적이다.

| 축 | 정하는 것 | 확인 명령 |
|---|---|---|
| **SDK 버전** | 쓸 수 있는 **컴파일러**와 빌드 도구 | `dotnet --list-sdks` |
| **런타임 대상(TFM)** | 쓸 수 있는 **API**와 실행 환경 | `.csproj`의 `TargetFramework` |
| **설치된 런타임** | 이 기계에서 **실행 가능한** 앱 | `dotnet --list-runtimes` |

p807은 이 독립성을 활용한 전략을 제시한다. **장기 지원(LTS) 런타임을 계속 대상으로 삼으면서, 최신 SDK를 설치해 최신 C# 컴파일러를 쓰는 것이다.**

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net8.0</TargetFramework>   <!-- 런타임은 LTS 유지 -->
    <LangVersion>13</LangVersion>               <!-- 컴파일러는 최신 (.NET 9 SDK 필요) -->
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
  </PropertyGroup>
</Project>
```

이 조합의 이점은 **지원되는 SDK와 지원되는 런타임을 동시에 쓴다**는 것이다. 미리 보기 SDK를 쓰는 것과 근본적으로 다르다. 다만 4.5절 앞부분에서 본 제약은 그대로 적용된다 — **새 라이브러리 기능은 못 쓴다.** 언어 기능만 열린다.

> **📌 .NET SDK 버전 번호 읽는 법**
>
> `8.0.100`을 세 조각으로 읽지 말고 네 조각으로 읽어라. pro02의 설명대로다.
>
> ```text
>    8 . 0 . 1     00
>    └─┬─┘   │      └── 패치 버전
>      │     └───────── 분기별 기능 밴드(feature band)
>      └─────────────── 대상 가능한 런타임의 최고 버전
> ```
>
> 즉 `8.0.100`은 "8.0 런타임까지 대상 가능 / 1분기 기능 밴드 / 패치 0"이다. `8.0.314`라면 3분기 밴드의 14번째 패치다.

### SDK 버전 고정 — `global.json`

기본적으로 `dotnet` 명령은 **설치된 SDK 중 가장 높은 버전**을 쓴다. .NET 9 미리 보기를 깔면 그때부터 모든 프로젝트가 그것으로 빌드된다. 이걸 막으려면 `global.json`을 쓴다.

```bash
dotnet new globaljson --sdk-version 8.0.100
```

```json
{
  "sdk": {
    "version": "8.0.100"
  }
}
```

`dotnet` 명령은 **현재 폴더에서 시작해 상위 폴더로 올라가며** `global.json`을 찾는다. 찾으면 그 버전을 쓴다. 그 버전이 설치돼 있지 않으면 이렇게 죽는다.

```text
Could not execute because the application was not found or a compatible
.NET SDK is not installed.
```

> **💡 팀 저장소에는 `global.json`을 넣어라**
>
> `global.json`이 없으면 팀원 A는 8.0.100으로, 팀원 B는 9.0.100 미리 보기로 빌드한다. 그러면 "내 기계에서는 되는데"가 발생하고, 원인을 찾는 데 몇 시간이 든다.
>
> 저장소 루트에 `global.json`을 두면 모든 하위 프로젝트가 같은 SDK로 빌드된다. CI에서도 같은 파일이 적용되므로 로컬과 CI가 일치한다.
>
> 다만 너무 좁게 고정하면 보안 패치를 못 받는다. `rollForward` 정책을 함께 지정해 "8.0.1xx 기능 밴드 안에서는 최신 패치를 쓴다"처럼 여지를 두는 것이 실무적이다.

### 미리 보기 기능

.NET 6부터 마이크로소프트는 **정식 릴리스(GA)에 미리 보기 기능을 함께 넣는다.** 개발자가 선택적으로 켜서 피드백을 주는 구조다. 이건 "미리 보기 버전의 .NET"과는 다른 이야기다 — 정식 SDK 안에 들어 있는 실험적 기능을 말한다.

```xml
<PropertyGroup>
  <EnablePreviewFeatures>true</EnablePreviewFeatures>
  <LangVersion>preview</LangVersion>
</PropertyGroup>
```

`[RequiresPreviewFeatures]` 특성은 미리 보기 기능을 쓰는 어셈블리·타입·멤버를 표시한다. 코드 분석기가 이 특성을 스캔해서 경고를 낸다. 내 코드가 미리 보기 기능을 쓰지 않으면 경고는 안 나온다.

> **⚠️ 미리 보기 기능은 프로덕션에 쓰지 마라**
>
> p807의 지침을 그대로 옮긴다. 미리 보기 기능은 **정식 릴리스 전에 호환성을 깨는 변경이 일어날 가능성이 높다.** 켜는 것은 자기 책임이다.
>
> 최신 컴파일러 기능이 필요한 것이라면 미리 보기가 아니라 **정식 SDK 상위 버전 + 낮은 TFM** 조합을 써라. 위에서 본 `net8.0 + LangVersion 13`이 그것이다.

런타임 버전과 언어 버전의 조합을 더 촘촘한 표로 보고 싶다면 76.13절에 정리되어 있다. 각 C# 버전이 무슨 기능을 가져왔는지는 76장 전체가 다룬다.

## 4.6 `Nullable`, `ImplicitUsings`, `AllowUnsafeBlocks` 등 주요 속성

### 자주 쓰는 속성 한눈에

| 속성 | 값 | 기본값 | 무엇을 바꾸나 |
|---|---|---|---|
| `OutputType` | `Exe` / `WinExe` / `Library` | `Library` | 실행 파일 / GUI 실행 파일 / 클래스 라이브러리 |
| `TargetFramework(s)` | TFM | 템플릿에 따름 | 4.2절 |
| `LangVersion` | 버전 / `latest` / `preview` | TFM이 결정 | 4.5절 |
| `Nullable` | `enable` / `disable` / `warnings` / `annotations` | 템플릿은 `enable` | 널 가능 참조 타입 분석 |
| `ImplicitUsings` | `enable` / `disable` | 템플릿은 `enable` | 전역 `using` 자동 삽입 |
| `AllowUnsafeBlocks` | `true` / `false` | `false` | `unsafe` 블록 허용 |
| `TreatWarningsAsErrors` | `true` / `false` | `false` | 모든 경고를 오류로 |
| `WarningsAsErrors` | 경고 번호 목록 | 비어 있음 | 지정 경고만 오류로 |
| `NoWarn` | 경고 번호 목록 | 비어 있음 | 지정 경고 무시 |
| `WarningLevel` | 0~9 | TFM에 따름 | 경고 세밀도 |
| `RootNamespace` | 식별자 | 프로젝트 이름 | 새 파일 생성 시 기본 네임스페이스 |
| `AssemblyName` | 파일 이름 | 프로젝트 이름 | 산출 어셈블리 이름 |
| `InvariantGlobalization` | `true` / `false` | 콘솔 템플릿은 `false`(AOT 템플릿은 `true`) | 문화권 무시 모드 |
| `GenerateDocumentationFile` | `true` / `false` | `false` | XML 문서 파일 생성 |
| `DebugType` | `portable` / `embedded` / `none` | `portable` | 디버그 심볼 위치 |
| `Optimize` | `true` / `false` | Release에서 `true` | 컴파일러 최적화 |
| `UseAppHost` | `true` / `false` | `true` | 네이티브 실행 런처 생성 |
| `GenerateAssemblyInfo` | `true` / `false` | `true` | 어셈블리 특성 자동 생성 |
| `ArtifactsPath` | 경로 | 없음 | 빌드 산출물 위치 ※.NET 8 |

### `Nullable` — 네 가지 값

`Nullable`이 켜지고 꺼지는 이분법이라고 아는 사람이 많은데, 실제로는 **두 축의 조합**이다.

| 값 | 주석(annotation) | 경고(warning) | 언제 쓰나 |
|---|---|---|---|
| `enable` | 켬 | 켬 | 새 프로젝트의 기본 |
| `disable` | 끔 | 끔 | 레거시 코드 |
| `warnings` | 끔 | 켬 | **경고만 먼저 보고 싶을 때** |
| `annotations` | 켬 | 끔 | 소비자에게 널 정보는 주되 내 코드는 아직 안 고칠 때 |

- **주석(annotation)** — `string?`처럼 물음표를 붙일 수 있게 하고, 그 정보를 메타데이터에 기록한다.
- **경고(warning)** — 널이 될 수 있는 값을 널이 아닌 자리에 넣으면 경고를 낸다.

> **💡 레거시 프로젝트에 널 가능 참조 타입을 도입하는 순서**
>
> 파일 5,000개짜리 프로젝트에서 `<Nullable>enable</Nullable>`을 켜면 경고가 수만 개 쏟아진다. 그 상태로는 아무도 안 고친다.
>
> 실무적인 순서는 이렇다.
>
> 1. 프로젝트 전체는 `disable`로 두고
> 2. 새로 만드는 파일 맨 위에 `#nullable enable`을 붙인다
> 3. 기존 파일은 손댈 때마다 하나씩 `#nullable enable`을 붙이고 고친다
> 4. 파일 대부분이 전환되면 프로젝트 속성을 `enable`로 바꾸고, 남은 파일에 `#nullable disable`을 붙인다
>
> 부호가 뒤집히는 4단계가 핵심이다. **기본값을 바꾸는 순간부터는 "아직 안 한 것"이 명시적으로 표시된다.**

### `ImplicitUsings` — 켜고 끄고 조절하기

3.7절에서 암시적 `using`이 `obj/`에 진짜 C# 파일(`*.GlobalUsings.g.cs`)을 만들어내는 메커니즘을 봤다. 여기서는 **조절하는 방법**만 본다.

```xml
<PropertyGroup>
  <ImplicitUsings>enable</ImplicitUsings>
</PropertyGroup>

<ItemGroup>
  <!-- 전역 using 추가 -->
  <Using Include="System.Text.Json" />

  <!-- 정적 임포트: 모든 파일에서 Console.WriteLine을 WriteLine으로 -->
  <Using Include="System.Console" Static="true" />

  <!-- 별칭 -->
  <Using Include="System.Collections.Generic.Dictionary&lt;string, object&gt;" Alias="Bag" />

  <!-- SDK가 넣은 것 중 하나를 빼기 -->
  <Using Remove="System.Net.Http" />
</ItemGroup>
```

세 번째 예의 `&lt;` `&gt;`에 주목하라. `.csproj`는 XML이므로 **꺾쇠는 이스케이프해야 한다.**

> **⚠️ 전역 정적 임포트는 신중하게**
>
> `<Using Include="System.Console" Static="true" />`를 넣으면 프로젝트 전체에서 `WriteLine("...")`만 써도 된다. 편해 보이지만 대가가 있다.
>
> - 코드를 다른 프로젝트로 복사하면 컴파일이 깨진다. 왜 깨지는지 `.csproj`를 열기 전에는 알 수 없다
> - `WriteLine`이라는 이름의 지역 메서드를 정의하면 조용히 그쪽이 이긴다
> - 코드만 보고는 `WriteLine`이 어디서 왔는지 알 수 없다
>
> 책의 예제 코드나 짧은 스크립트에는 괜찮지만, **여러 사람이 오래 유지할 코드베이스에서는 권하지 않는다.**

`System` 네임스페이스를 통째로 빼면 어떻게 되는지도 p807이 보여준다.

```xml
<ItemGroup>
  <Using Remove="System" />
</ItemGroup>
```

이 상태에서 `String s = "World";`를 쓰면 다음 오류가 난다.

```text
error CS0246: 'String' 형식 또는 네임스페이스 이름을 찾을 수 없습니다
(using 지시문 또는 어셈블리 참조가 있는지 확인하세요).
```

그런데 `string s = "Hello";`는 **그대로 컴파일된다.** `string`은 키워드이므로 네임스페이스가 필요 없기 때문이다. 여기서 p807의 지침이 나온다. **선택할 수 있다면 실제 타입 이름 대신 C# 키워드를 써라. 키워드는 네임스페이스를 임포트할 필요가 없다.**

### `AllowUnsafeBlocks`

```xml
<PropertyGroup>
  <AllowUnsafeBlocks>true</AllowUnsafeBlocks>
</PropertyGroup>
```

이 속성 없이 `unsafe` 키워드를 쓰면 컴파일 오류(CS0227)가 난다.

이것은 **컴파일러 스위치일 뿐 런타임 보안 장치가 아니다.** 켠다고 해서 실행 시 추가 권한이 필요해지지 않고, 끈다고 해서 다른 어셈블리의 unsafe 코드를 막지도 못한다. 하는 일은 하나다 — **"이 프로젝트는 검증 불가능한 IL을 만들 수 있다"고 선언하는 것.**

> **📌 켜야 하는 진짜 이유는 대개 상호운용이다**
>
> `unsafe`가 필요한 상황은 세 가지로 압축된다.
>
> 1. 네이티브 함수에 포인터를 넘겨야 한다 (P/Invoke)
> 2. `fixed` 버퍼가 있는 구조체로 네이티브 메모리 레이아웃을 맞춰야 한다
> 3. 극단적 핫 패스에서 경계 검사를 우회해야 한다
>
> 3번은 요즘 대부분 `Span<T>`로 해결된다. 즉 **`unsafe`가 정말 필요한 자리는 상호운용 쪽으로 좁아지고 있다.** 상호운용은 60장에서, `unsafe`와 포인터 문법은 60.7절에서 다룬다.

### `TreatWarningsAsErrors`와 그 함정

```xml
<PropertyGroup>
  <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
</PropertyGroup>
```

"경고를 방치하지 말자"는 좋은 규율이다. 그런데 이 속성에는 널리 알려진 함정이 있다.

> **⚠️ `TreatWarningsAsErrors`는 미래의 빌드를 깨뜨린다**
>
> 경고는 **SDK와 분석기 버전에 따라 늘어난다.** 오늘 경고 0개인 코드가, 아무것도 안 고쳤는데 SDK를 8.0.100에서 8.0.400으로 올리는 것만으로 새 경고를 뱉을 수 있다. 새 분석기가 추가됐기 때문이다.
>
> 그러면 **한 줄도 안 바꾼 코드의 CI가 빨간불이 된다.** 그것도 릴리스 직전에.
>
> 두 가지 완화책이 있다.
>
> **(a) 개별 경고만 오류로 승격한다.**
>
> ```xml
> <WarningsAsErrors>CS8600;CS8602;CS8603</WarningsAsErrors>
> ```
>
> **(b) 전체 승격은 켜되 SDK를 `global.json`으로 고정한다.** 그러면 SDK를 올리는 시점이 팀의 통제 아래로 들어온다.
>
> 실무에서는 (a)+(b) 조합을 권한다. "널 관련 경고만은 절대 넘기지 않는다" 같은 구체적 규율이, "모든 경고를 오류로" 같은 총론보다 오래 간다.

`NoWarn`은 반대 방향이다. 특정 경고를 끈다.

```xml
<!-- CS1591: 공개 멤버에 XML 주석이 없음 -->
<NoWarn>$(NoWarn);CS1591</NoWarn>
```

`$(NoWarn);`을 붙인 것에 주목하라. 4.1절에서 본 속성 누적 규칙 그대로다.

### `InvariantGlobalization`

```xml
<PropertyGroup>
  <InvariantGlobalization>true</InvariantGlobalization>
</PropertyGroup>
```

p807에 따르면 이 속성은 **.NET 8의 콘솔 앱 템플릿에서 명시적으로 `true`로 설정되는 것이 새로워진 점**이다. 목적은 콘솔 앱을 특정 문화권에 묶이지 않게 만들어, 세계 어디에 배포해도 같은 동작을 하게 하는 것이다. `false`로 두거나 속성 자체가 없으면 호스트 컴퓨터의 문화권을 따른다.

효과는 문화권 데이터를 아예 로드하지 않는 것이다.

```csharp
using System.Globalization;

Console.WriteLine("Current culture: {0}", CultureInfo.CurrentCulture.DisplayName);
```

`InvariantGlobalization`이 켜져 있으면 출력은 이렇게 나온다.

```text
Current culture: Invariant Language (Invariant Country)
```

> **⚠️ 켜면 문자열 비교 결과가 바뀐다**
>
> 이 속성은 배포 크기와 시작 시간에는 도움이 되지만, **문화권을 인식하는 모든 동작이 달라진다.**
>
> - 문화권 인식 문자열 비교와 정렬 결과가 서수(ordinal) 기준에 가까워진다
> - 날짜·숫자의 지역화된 서식이 사라진다
> - 대소문자 변환이 문화권 규칙을 따르지 않는다
>
> 이게 문제가 되는 지점은 **사용자에게 보이는 정렬 순서**와 **로케일 의존 파싱**이다. 서버 앱에서 "정렬이 이상하다"는 버그의 원인이 이 속성인 경우가 있다. 문자열 비교와 문화권 문제는 35.4절에서 자세히 다룬다.
>
> **AOT 템플릿이 이 속성을 켜는 이유는 크기 때문이다.** 켜는 것이 기본값이라고 오해하지 마라 — 일반 콘솔·웹 앱에서는 켜기 전에 영향을 반드시 검토해야 한다.

### `ArtifactsPath` — 빌드 산출물 위치 바꾸기 ※.NET 8

전통적으로 각 프로젝트가 자기 폴더에 `bin`과 `obj`를 만든다. .NET 8부터는 이걸 한곳에 모을 수 있다.

```bash
dotnet new buildprops --use-artifacts
```

이 명령이 만드는 `Directory.Build.props`는 이렇게 생겼다.

```xml
<Project>
  <PropertyGroup>
    <ArtifactsPath>$(MSBuildThisFileDirectory)artifacts</ArtifactsPath>
  </PropertyGroup>
</Project>
```

그러면 솔루션 폴더 아래 `artifacts/` 하나에 모든 프로젝트의 산출물이 모인다.

> **⚠️ 켠 사실을 잊으면 파일을 못 찾는다**
>
> p807이 경고하는 그대로다. 이 설정을 켜두면 산출물이 **새로운 폴더 구조**에 생긴다. `bin/Debug/net8.0/`을 열러 갔는데 폴더가 없어서 "빌드가 안 됐나" 하고 헤매게 된다. CI 스크립트의 경로도 전부 바뀐다.
>
> 켤 거라면 저장소 전체에 한 번에 켜고, README에 적어라. 절반만 켜는 것이 최악이다.

## 4.7 NuGet 패키지, 의존성 그래프, `deps.json`

### 패키지란 무엇인가

p807의 정의를 옮긴다. **어셈블리는 타입이 파일 시스템에 저장되는 곳**이고, 코드를 배포하는 메커니즘이다. 그리고 **어셈블리는 NuGet 패키지로 배포된다.** NuGet 패키지는 공개 온라인 피드에서 내려받을 수 있는 파일이며, 여러 어셈블리와 기타 리소스를 담을 수 있다.

.NET 자체가 패키지 집합으로 쪼개져 있다. 각 패키지는 대체로 같은 이름의 어셈블리 하나에 대응한다.

| 패키지 | 주요 타입 |
|---|---|
| `System.Runtime` | `Object`, `String`, `Int32`, `Array` |
| `System.Collections` | `List<T>`, `Dictionary<TKey, TValue>` |
| `System.Net.Http` | `HttpClient`, `HttpResponseMessage` |
| `System.IO.FileSystem` | `File`, `Directory` |
| `System.Reflection` | `Assembly`, `TypeInfo`, `MethodInfo` |

패키지로 쪼갠 이득은 다음과 같다.

- 공개 피드로 쉽게 배포된다
- 재사용된다
- **각자의 일정으로 출시된다**
- 다른 패키지와 독립적으로 테스트된다
- 하나의 패키지가 **여러 OS·CPU용 어셈블리 버전을 동시에** 담을 수 있다
- 라이브러리 하나에만 필요한 의존성을 그 라이브러리에만 붙일 수 있다
- **참조되지 않은 패키지는 배포에 포함되지 않으므로 앱이 작아진다**

> **⚠️ 어셈블리와 네임스페이스는 1:1이 아니다**
>
> p807이 명시적으로 짚는다. **한 어셈블리가 여러 네임스페이스를 담을 수 있고, 한 네임스페이스가 여러 어셈블리에 걸쳐 정의될 수 있다.**
>
> | 어셈블리 | 예시 네임스페이스 | 예시 타입 |
> |---|---|---|
> | `System.Runtime.dll` | `System`, `System.Collections`, `System.Collections.Generic` | `Int32`, `String`, `IEnumerable<T>` |
> | `System.Console.dll` | `System` | `Console` |
> | `System.Threading.dll` | `System.Threading` | `Interlocked`, `Monitor`, `Mutex` |
> | `System.Xml.XDocument.dll` | `System.Xml.Linq` | `XDocument`, `XElement`, `XNode` |
>
> 표의 마지막 줄이 이 함정의 전형이다. `XDocument`를 쓰려면 `System.Xml.Linq` **네임스페이스**를 임포트해야 하는데, 그 타입이 사는 **어셈블리**의 이름은 `System.Xml.XDocument.dll`이다. 이름만 보고 추측하면 틀린다.
>
> 그래서 `CS0246: 형식 또는 네임스페이스 이름을 찾을 수 없습니다`라는 오류는 두 가지 서로 다른 원인을 갖는다. **네임스페이스를 안 가져왔거나, 어셈블리 참조가 없거나.** 오류 메시지가 "using 지시문 또는 어셈블리 참조"라고 둘 다 언급하는 이유다.

### `PackageReference`

```xml
<ItemGroup>
  <PackageReference Include="Newtonsoft.Json" Version="13.0.3" />
</ItemGroup>
```

`dotnet add package Newtonsoft.Json`을 치면 이 한 줄이 추가된다. 구식의 `packages.config` + `<Reference><HintPath>` 이중 관리와 비교하면 차이가 뚜렷하다.

| | `packages.config` (구식) | `PackageReference` (현재) |
|---|---|---|
| 선언 위치 | `packages.config` + `.csproj` **두 곳** | `.csproj` 한 곳 |
| 전이 의존성 | **전부 나열됨** | 자동 해석, 나열 안 함 |
| 패키지 파일 위치 | 솔루션 아래 `packages/` 폴더 | 전역 캐시 (`~/.nuget/packages`) |
| 저장소 크기 | 패키지가 저장소에 들어가기도 했다 | 저장소에는 참조만 |

### 의존성 그래프

패키지 A가 B를 참조하고, B가 C를 참조하면, 내 프로젝트는 A만 선언해도 C까지 얻는다. 이것을 **전이 의존성(transitive dependency)** 이라고 한다.

```text
   내 프로젝트
       │
       ├── PackageA 2.0                (직접 참조 — .csproj에 적힌 것)
       │      ├── PackageB 1.5         (전이)
       │      │      └── PackageD 3.0  (전이)
       │      └── PackageC 4.1         (전이)
       │
       └── PackageX 1.0                (직접 참조)
              └── PackageD 3.4         (전이 — D가 두 번 등장한다!)
```

`PackageD`가 3.0과 3.4로 두 번 나타났다. NuGet은 이런 충돌을 규칙에 따라 해소한다.

- **가장 가까운 것이 이긴다.** 내가 `.csproj`에 직접 선언한 버전이 전이로 들어온 버전을 이긴다.
- **같은 깊이면 높은 쪽이 이긴다.** 위 그림처럼 형제 관계로 충돌하면 더 높은 버전(3.4)이 선택된다.
- **다운그레이드는 경고다.** 직접 선언이 전이 요구보다 낮으면 `NU1605` 경고가 난다. 이 경고는 무시하지 마라 — 그 패키지가 요구한 API가 실제로 없을 수 있다.

이 해석의 최종 결과가 `obj/project.assets.json`에 기록된다(3.1절).

> **💡 실제로 무엇이 들어왔는지 보는 법 ※**
>
> ```bash
> dotnet list package --include-transitive
> dotnet list package --outdated
> dotnet list package --vulnerable
> ```
>
> 첫 명령은 전이 의존성까지 전부 보여준다. 직접 참조가 셋인데 실제로는 마흔 개가 들어와 있는 광경을 처음 보면 놀라게 된다.
>
> 세 번째 명령은 알려진 취약점이 있는 패키지를 찾는다. **CI에 이 명령을 넣어두는 것이 실무에서 가장 가성비 높은 보안 조치 중 하나다.**

### 버전 고정

p807은 이 항목에 한 절을 할애한다. **의존성을 고정한다(fixing dependencies)** 는 것은 특정 .NET 버전에 맞춰 함께 출시된 패키지 계열을 쓴다는 뜻이다.

```xml
<ItemGroup>
  <PackageReference Version="8.0.0"
                    Include="Microsoft.EntityFrameworkCore.Sqlite" />
</ItemGroup>
```

고정하려면 **모든 패키지가 추가 한정자 없는 단일 버전**을 가져야 한다. 추가 한정자란 베타(`beta1`), 릴리스 후보(`rc4`), 와일드카드(`*`)를 말한다.

> **⚠️ 와일드카드는 미래의 나를 공격한다**
>
> ```xml
> <!-- 피해야 할 형태 -->
> <PackageReference Include="System.Net.Http" Version="4.1.0-*" />
> <PackageReference Include="Newtonsoft.Json" Version="13.0.2-beta1" />
> ```
>
> 와일드카드는 **항상 최신 릴리스를 자동으로 가져온다.** 편해 보이지만, 호환되지 않는 미래 패키지가 들어와 코드를 깨뜨릴 수 있다. 그것도 **내가 아무것도 안 바꾼 날에.**
>
> p807의 지침은 명확하다. 마이크로소프트는 **특정 .NET 버전과 함께 출시된 버전(예: 8.0.0)으로 의존성을 고정하면 그 패키지들이 함께 잘 동작함을 보장한다.** 거의 언제나 의존성을 고정하라. 특히 프로덕션 배포에서는.
>
> 와일드카드가 정당화되는 경우는 미리 보기를 매달 따라가야 하는 실험 프로젝트 정도다.

### 중앙 패키지 관리 ※

프로젝트가 20개인 솔루션에서 같은 패키지 버전을 20곳에 적는 것은 곧 불일치를 부른다. 솔루션 루트에 `Directory.Packages.props`를 두면 버전을 한곳에서 관리할 수 있다.

```xml
<!-- Directory.Packages.props (솔루션 루트) -->
<Project>
  <PropertyGroup>
    <ManagePackageVersionsCentrally>true</ManagePackageVersionsCentrally>
  </PropertyGroup>
  <ItemGroup>
    <PackageVersion Include="Microsoft.EntityFrameworkCore.Sqlite" Version="8.0.0" />
    <PackageVersion Include="Newtonsoft.Json" Version="13.0.3" />
  </ItemGroup>
</Project>
```

그러면 각 프로젝트는 버전 없이 이름만 쓴다.

```xml
<ItemGroup>
  <PackageReference Include="Newtonsoft.Json" />
</ItemGroup>
```

### `deps.json` — 런타임이 읽는 목록

3.1절에서 `bin`에 생기는 `MyApp.deps.json`을 봤다. 이제 그것이 무엇을 하는지 본다.

pro16의 설명대로, 런타임 호스트는 시작할 때 **프로빙 경로(probing path)** 집합을 준비한다. 다섯 개의 프로빙 속성이 있고 전부 선택적이다.

| 속성 | 담는 것 |
|---|---|
| `TRUSTED_PLATFORM_ASSEMBLIES` | 플랫폼 및 애플리케이션 어셈블리 **파일 경로 목록** |
| `PLATFORM_RESOURCE_ROOTS` | 위성 리소스 어셈블리를 찾을 디렉터리 목록 |
| `NATIVE_DLL_SEARCH_DIRECTORIES` | 비관리(네이티브) 라이브러리를 찾을 디렉터리 목록 |
| `APP_PATHS` | 관리 어셈블리를 찾을 디렉터리 목록 |
| `APP_NI_PATHS` | 관리 어셈블리의 네이티브 이미지를 찾을 디렉터리 목록 |

이 값들은 코드에서 직접 읽을 수 있다.

```csharp
Console.WriteLine("*** 프로빙 경로 확인 ***");

// Windows는 ';', 그 외 플랫폼은 ':'로 구분된다
char sep = OperatingSystem.IsWindows() ? ';' : ':';

string? tpa = AppContext.GetData("TRUSTED_PLATFORM_ASSEMBLIES") as string;
foreach (string path in (tpa ?? string.Empty).Split(sep))
{
    Console.WriteLine(path);
}

Console.WriteLine($"NATIVE_DLL_SEARCH_DIRECTORIES: " +
                  $"{AppContext.GetData("NATIVE_DLL_SEARCH_DIRECTORIES")}");
Console.WriteLine($"APP_PATHS: {AppContext.GetData("APP_PATHS")}");
```

빈 콘솔 앱을 이렇게 만들어 실행하면 값의 대부분이 `TRUSTED_PLATFORM_ASSEMBLIES`에서 온다는 것을 알 수 있다. 목록에는 내 프로젝트의 어셈블리와 함께 **현재 런타임 디렉터리의 기본 클래스 라이브러리들**이 들어 있다.

**이 목록을 채우는 것이 `*.deps.json` 파일들이다.** 내 앱의 `MyApp.deps.json`과, 런타임 설치 폴더의 `Microsoft.NETCore.App.deps.json`이 합쳐져 최종 목록이 된다.

```text
  MyApp.runtimeconfig.json   →  "어느 런타임 버전을 로드할까"
            +
  MyApp.deps.json            →  "그 위에 어떤 어셈블리를 신뢰 목록에 넣을까"
            +
  Microsoft.NETCore.App.deps.json (런타임 설치 폴더)
            ↓
  TRUSTED_PLATFORM_ASSEMBLIES  (파일 경로 수백 개)
            ↓
  CLR이 타입을 찾을 때 이 목록에서 해석한다
```

pro16의 실험이 직관적이다. 빈 콘솔 앱에 `Microsoft.EntityFrameworkCore` 패키지 하나를 추가하고 다시 실행하면, **목록의 파일 수가 눈에 띄게 늘어난다.** 참조는 하나 늘었는데 그 패키지의 의존성들이 전부 딸려 들어왔기 때문이다.

> **⚠️ `deps.json`을 지우면 조용한 실패가 시작된다**
>
> `deps.json`은 사람이 읽으라고 만든 파일이 아니어서, 배포 스크립트를 짜다가 "필요 없어 보인다"고 빼는 실수가 나온다. 그러면 앱이 곧바로 죽지 않고, **특정 기능을 처음 쓰는 순간** 타입 로드나 어셈블리 로드 실패로 죽는다.
>
> 배포 산출물에서 임의로 파일을 빼지 마라. `dotnet publish`가 만든 폴더의 내용은 전부 필요하다고 가정하는 편이 안전하다.

> **📌 GAC는 없다**
>
> .NET Framework는 프레임워크 파일을 **전역 어셈블리 캐시(GAC)** 에 설치했고, 모든 .NET Framework 앱이 그곳을 찾았다. 모던 .NET에는 GAC가 없다.
>
> 이유는 pro16이 설명한다. **GAC는 .NET Core의 나란히 설치(side-by-side) 능력을 방해한다.** 대신 프레임워크 파일들은 `C:\Program Files\dotnet` 아래에 **버전별로 분리되어** 설치된다. 앱의 `runtimeconfig.json`이 지정한 버전의 디렉터리에서 필요한 런타임·프레임워크 파일이 로드된다.
>
> 이 설계가 "한 기계에 .NET 6·7·8을 동시에 두고 각 앱이 자기 버전으로 도는" 일을 가능하게 한다. 어셈블리 로드 컨텍스트(ALC)와 탐색 순서의 상세는 52.9절과 52.15절에서 다룬다.

## 4.8 솔루션 구성과 프로젝트 참조

### 솔루션은 프로젝트의 묶음일 뿐이다

솔루션 파일(`.sln`)은 **여러 프로젝트를 함께 열고 함께 빌드하기 위한 목록**이다. 그 이상도 이하도 아니다. 솔루션 자체는 컴파일되지 않는다.

```bash
dotnet new sln -n MyApp
dotnet new classlib -n MyApp.Core -o src/MyApp.Core
dotnet new console  -n MyApp.Cli  -o src/MyApp.Cli
dotnet sln MyApp.sln add src/MyApp.Core src/MyApp.Cli
dotnet add src/MyApp.Cli reference src/MyApp.Core
```

pro16이 지적하듯, Visual Studio Code로 프로젝트 하나만 다룬다면 솔루션 파일이 꼭 필요하지는 않다. **Visual Studio는 솔루션 중심이고, Visual Studio Code는 코드 중심이다.** 다만 관련 프로젝트를 묶어두는 것은 대부분의 개발자가 유용하다고 여긴다.

> **📌 `dotnet build`가 솔루션과 프로젝트에서 다르게 도는 방식**
>
> 솔루션 파일이 있는 디렉터리에서 `dotnet restore`나 `dotnet build`를 실행하면 **솔루션의 모든 프로젝트**가 대상이 된다. `.csproj`가 있는 디렉터리에서 실행하면 그 프로젝트만 대상이 된다.
>
> `dotnet run`은 다르다. 실행할 프로젝트가 하나로 정해져야 하므로 솔루션에 대고 쓸 수 없다(3.1절).

### 참조의 세 가지 종류

| 종류 | 선언 | 언제 쓰나 | 위험 |
|---|---|---|---|
| **프로젝트 참조** | `<ProjectReference Include="..\Core\Core.csproj" />` | 같은 저장소에서 함께 개발 중인 코드 | 없음 (권장) |
| **직접 참조** | `<Reference Include="Foo"><HintPath>...</HintPath></Reference>` | 소스가 없는 서드파티 DLL | **버전이 어긋나도 모른다** |
| **패키지 참조** | `<PackageReference Include="Foo" Version="1.0.0" />` | 배포된 라이브러리 | 버전 고정 필요 (4.7절) |

pro16이 프로젝트 참조와 직접 참조의 차이를 정확히 설명한다.

**프로젝트 참조를 걸면 솔루션의 빌드 순서가 조정된다.** 의존 대상(위 예의 `MyApp.Core`)이 먼저 빌드되고, 그 산출물이 부모 프로젝트의 출력 디렉터리로 복사된다. 클라이언트를 다시 빌드하면 의존 라이브러리도 함께 다시 빌드되고 새 버전이 다시 복사된다.

**직접 참조를 걸면 컴파일된 라이브러리가 클라이언트의 출력 디렉터리로 복사되긴 하지만, 참조를 건 그 시점의 것이다.** 프로젝트 참조가 없으므로 두 프로젝트는 서로 독립적으로 빌드될 수 있고, **파일이 어긋날 수 있다.**

> **⚠️ 개발 중인 코드에 직접 참조를 걸지 마라**
>
> pro16의 결론이다. 실제 소프트웨어 프로젝트에서 흔히 그렇듯 **의존 라이브러리를 함께 개발하고 있다면, 프로젝트 출력이 아니라 프로젝트를 참조하는 것이 최선이다.**
>
> 직접 참조의 실패 양상이 고약하다. 라이브러리를 고쳤는데 클라이언트에는 반영이 안 된다. 클라이언트를 다시 빌드해도 마찬가지다. 원인을 찾기 전까지 "내 수정이 사라진다"는 유령을 쫓게 된다.

### 순환 참조는 금지다

어떤 어셈블리든 클래스 라이브러리 어셈블리를 하나 이상 의존성으로 참조할 수 있지만, **순환 참조는 할 수 없다.** 어셈블리 A가 이미 B를 참조한다면, B는 A를 참조할 수 없다. 컴파일러가 경고한다.

pro16의 판단을 옮긴다. **순환 참조는 대체로 나쁜 코드 설계의 신호다.** 정말 필요하다고 확신한다면 **인터페이스를 써서 푼다.** 공통 인터페이스를 제3의 프로젝트에 두고 양쪽이 그것을 참조하면 순환이 끊긴다.

```text
   깨진 설계                        고친 설계
   ┌─────┐  →  ┌─────┐          ┌─────┐  →  ┌───────────┐  ←  ┌─────┐
   │  A  │     │  B  │          │  A  │     │ Abstract  │     │  B  │
   │     │  ←  │     │          │     │  ──────────────────→  │     │
   └─────┘     └─────┘          └─────┘     └───────────┘     └─────┘
     순환 — 컴파일 불가            A는 인터페이스만 알고, B가 구현을 제공한다
```

### `InternalsVisibleTo` — 어셈블리 경계에 구멍 내기

`internal` 멤버는 같은 어셈블리 안에서만 보인다. 예외는 하나다. 어셈블리가 `InternalsVisibleTo` 특성으로 다른 어셈블리에 접근을 **명시적으로 허용**하는 경우다.

전통적인 방법은 소스에 특성을 쓰는 것이다.

```csharp
using System.Runtime.CompilerServices;

[assembly: InternalsVisibleTo("MyApp.Tests")]
```

pro16은 프로젝트 파일 쪽을 더 낫다고 본다.

```xml
<ItemGroup>
  <AssemblyAttribute Include="System.Runtime.CompilerServices.InternalsVisibleToAttribute">
    <_Parameter1>MyApp.Tests</_Parameter1>
  </AssemblyAttribute>
</ItemGroup>
```

이유는 **가시성**이다. 다른 개발자가 프로젝트 파일에서 바로 보게 되므로, 소스 어딘가에 숨어 있는 특성을 찾아 헤맬 필요가 없다.

> **⚠️ 접근은 요청하는 것이 아니라 허락받는 것이다**
>
> `InternalsVisibleTo`는 **`internal` 타입을 가진 쪽이 지정한다.** 소비하는 쪽이 "나에게 권한을 달라"고 요청할 방법은 없다.
>
> 그리고 이름이 정확히 일치해야 한다. 어셈블리 이름을 바꾸거나 `AssemblyName` 속성을 건드리면 조용히 끊긴다 — 테스트가 갑자기 컴파일 안 되는 이유가 이것인 경우가 있다.

### `Directory.Build.props`와 `Directory.Build.targets`

프로젝트 20개에 같은 속성을 20번 적는 대신, 상위 폴더에 파일 하나를 두면 된다.

```xml
<!-- 저장소 루트의 Directory.Build.props -->
<Project>
  <PropertyGroup>
    <TargetFramework>net8.0</TargetFramework>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
    <LangVersion>12</LangVersion>
    <TreatWarningsAsErrors>false</TreatWarningsAsErrors>
    <WarningsAsErrors>CS8600;CS8602;CS8603;CS8618</WarningsAsErrors>
    <Company>Contoso</Company>
    <Copyright>© 2026 Contoso</Copyright>
  </PropertyGroup>
</Project>
```

MSBuild는 프로젝트 파일이 있는 폴더에서 시작해 **위로 올라가며** 이 파일을 찾고, **처음 찾은 하나만** 임포트한다.

파일은 두 종류이고, 차이는 **임포트 시점**이다. `Directory.Build.props`는 프로젝트 파일 **앞**에서 임포트되므로 프로젝트가 그 값을 덮어쓸 수 있다 — 기본값을 제공하는 자리다. `Directory.Build.targets`는 프로젝트 파일 **뒤**에서 임포트되므로 프로젝트 설정을 덮어쓴다 — 강제값을 거는 자리다.

이 순서가 곧 용도다. **바꿀 수 있게 하려면 `.props`에, 못 바꾸게 하려면 `.targets`에.**

> **⚠️ 하나만 찾고 멈춘다**
>
> 저장소 루트와 하위 폴더에 각각 `Directory.Build.props`를 두면, **가까운 것 하나만 적용되고 루트 것은 무시된다.** 두 개를 합치는 동작이 아니다.
>
> 하위 폴더에서 루트 설정을 이어받으려면 명시적으로 임포트해야 한다.
>
> ```xml
> <Project>
>   <Import Project="$([MSBuild]::GetPathOfFileAbove('Directory.Build.props', '$(MSBuildThisFileDirectory)../'))" />
>   <PropertyGroup>
>     <!-- 여기부터 이 폴더 전용 설정 -->
>   </PropertyGroup>
> </Project>
> ```
>
> 이걸 모르면 "루트 설정이 왜 안 먹지"로 한참 헤맨다. `dotnet msbuild -preprocess:full.xml`(4.1절)로 확인하는 것이 가장 빠르다.

### `NuGet.Config` — 패키지 출처 지정

NuGet이 어디서 패키지를 찾을지는 `NuGet.Config`가 정한다. Windows에서 주 파일은 `%appdata%\NuGet`에 있고, 대략 이런 내용이다.

```xml
<?xml version="1.0" encoding="utf-8"?>
<configuration>
  <packageSources>
    <add key="nuget.org" value="https://api.nuget.org/v3/index.json" protocolVersion="3" />
  </packageSources>
</configuration>
```

핵심 성질은 **`NuGet.Config` 파일들이 기본적으로 누적된다**는 것이다. 각 파일은 자기가 있는 디렉터리와 모든 하위 디렉터리에 유효하다. 그래서 시스템 전체 목록을 건드리지 않고, 솔루션 폴더에 파일을 하나 더 두어 소스를 추가할 수 있다.

```xml
<?xml version="1.0" encoding="utf-8"?>
<configuration>
  <packageSources>
    <add key="local-packages" value=".\CarLibrary\Publish" />
  </packageSources>
</configuration>
```

누적이 아니라 목록을 **초기화**하고 싶으면 `<clear />`를 넣는다.

```xml
<?xml version="1.0" encoding="utf-8"?>
<configuration>
  <packageSources>
    <clear />
    <add key="local-packages" value=".\CarLibrary\Publish" />
    <add key="NuGet" value="https://api.nuget.org/v3/index.json" />
  </packageSources>
</configuration>
```

> **💡 사내 피드를 쓴다면 `<clear />`를 고려하라**
>
> 사내 피드와 nuget.org가 둘 다 열려 있으면, 사내 패키지와 같은 이름의 패키지를 공개 피드에 올리는 공격(의존성 혼동)이 가능해진다. `<clear />`로 목록을 명시적으로 재구성하고 순서를 통제하는 것이 안전하다.
>
> 그리고 pro16이 짚은 실무 함정 하나 — **Visual Studio를 쓴다면 `NuGet.Config`를 고친 뒤 IDE를 재시작해야 반영된다.**

## 4.9 배포 형태 개요 — 프레임워크 종속 / 자체 포함 / 단일 파일 / AOT

### 배포란 무엇인가

p807의 비유가 좋다. **소설을 썼고 남들이 읽기를 원한다면 출판해야 한다.** 코드도 마찬가지다. 다른 개발자가 자기 프로젝트에서 쓰게 하거나 사용자가 앱으로 실행하게 하려면, 코드를 **패키징된 클래스 라이브러리** 또는 **실행 가능한 애플리케이션**으로 게시해야 한다.

그 명령이 `dotnet publish`다. `dotnet build`와의 차이는 명확하다.

| 명령 | 만드는 것 | 실행 가능한가 |
|---|---|---|
| `dotnet build` | 개발용 산출물 (`bin/<구성>/<TFM>/`) | 이 기계에서는 |
| `dotnet publish` | **배포용 산출물** (`.../publish/`) | 대상 기계에서 |
| `dotnet pack` | NuGet 패키지 (`.nupkg`) | 아니다 — 라이브러리 배포용 |

> **⚠️ `dotnet publish`의 기본 구성이 .NET 8에서 바뀌었다**
>
> p807이 명시한다. **.NET 7 이하에서는 기본이 Debug 구성이었다. .NET 8부터는 Release가 기본이다.**
>
> 오래된 CI 스크립트에 `-c Release`가 빠져 있다면, .NET 7까지는 Debug 산출물을 프로덕션에 올리고 있었다는 뜻이다. 지금도 **명시하는 편이 안전하다.** 기본값에 기대지 마라.

### 네 가지 배포 형태

| | 프레임워크 종속 (FDD/FDE) | 자체 포함 | 단일 파일 | Native AOT |
|---|---|---|---|---|
| **.NET 런타임 설치 필요** | **필요** | 불필요 | 자체 포함이면 불필요 | 불필요 |
| **RID 지정** | 불필요 | **필수** | 필수(자체 포함 시) | **필수** |
| **파일 개수** | 적다 (예: 6개) | 많다 (예: 226개) | 1~2개 | 1~2개 |
| **크기** | 가장 작다 | 가장 크다 | 크다 (압축·트리밍으로 감소) | 작다 |
| **시작 시간** | 보통 (JIT) | 보통 (JIT) | 보통~느림(압축 시) | **가장 빠르다** |
| **JIT 사용** | 사용 | 사용 | 사용 | **사용 안 함** |
| **리플렉션** | 자유 | 자유 | 자유 | **제약 있음** |
| **크로스 플랫폼 게시** | 가능 | 가능 | 가능 | **불가 — 대상 OS에서 게시해야 한다** |
| **주 용도** | 서버, 런타임이 이미 있는 환경 | USB로 건네주는 앱, 런타임 통제 불가 환경 | 배포 단순화 | 컨테이너, 서버리스, CLI 도구 |

### 프레임워크 종속 배포

애플리케이션과 그 패키지 의존성만 배포하고 **.NET 자체는 배포하지 않는 방식**이다. 대상 컴퓨터에 .NET이 이미 있다고 전제한다. p807이 지적하듯 **웹 애플리케이션을 서버에 배포할 때 잘 맞는다.** 서버에는 이미 .NET과 다른 웹 앱들이 올라가 있을 가능성이 높기 때문이다.

이 방식은 다시 둘로 나뉜다.

**FDD(framework-dependent deployment, 프레임워크 종속 배포)** 는 `.dll`을 배포하고 `dotnet MyApp.dll`처럼 명령줄 도구로 실행하게 한다. **FDE(framework-dependent executable, 프레임워크 종속 실행 파일)** 는 `.exe`를 배포하고 명령줄에서 직접 실행하게 한다. 둘 다 **적절한 버전의 .NET 런타임이 시스템에 설치되어 있어야 한다.**

```bash
dotnet publish -c Release
```

RID를 지정하지 않으면 프레임워크 종속이 기본이다. 결과 폴더에는 파일이 얼마 안 들어간다. pro16의 예에서는 여섯 개였다.

```text
bin/Release/net8.0/publish/
├── MyApp.dll                  ← 내 코드
├── CarLibrary.dll             ← 참조한 클래스 라이브러리
├── MyApp.exe                  ← 앱호스트 (FDE)
├── MyApp.pdb                  ← 디버그 심볼
├── MyApp.deps.json            ← 의존성 목록 (4.7절)
└── MyApp.runtimeconfig.json   ← 대상 프레임워크와 버전
```

> **📌 .NET Core 3 이전에는 콘솔 앱이 `.dll`로만 나왔다**
>
> p807이 짚는 역사다. .NET Core 3 이전에는 콘솔 앱이 `.dll` 파일로 컴파일되어 `dotnet run` 명령이나 호스트 실행 파일로만 실행할 수 있었다. 지금은 앱호스트가 함께 생성되므로 `.exe`를 직접 실행할 수 있다.
>
> 앱호스트가 관리 코드를 담지 않는 네이티브 런처라는 사실은 3.1절에서 이미 봤다. `<UseAppHost>false</UseAppHost>`로 끄면 순수 FDD가 된다.

### 자체 포함 배포

p807의 상황 묘사가 정확하다. **누군가에게 USB 스틱에 담아 건네주고, 그 사람 컴퓨터에서 그냥 돌기를 원할 때가 있다.** 그럴 때 자체 포함 배포를 쓴다. 배포 파일의 크기는 커지지만 **동작한다는 것을 알 수 있다.**

RID(Runtime Identifier, 런타임 식별자)를 지정해야 한다.

```xml
<PropertyGroup>
  <OutputType>Exe</OutputType>
  <TargetFramework>net8.0</TargetFramework>
  <RuntimeIdentifiers>
    win10-x64;osx-x64;osx.11.0-arm64;linux-x64;linux-arm64
  </RuntimeIdentifiers>
</PropertyGroup>
```

> **⚠️ `RuntimeIdentifier`와 `RuntimeIdentifiers` — 또 한 글자**
>
> 4.2절의 `TargetFramework(s)`와 똑같은 함정이 여기도 있다. **하나만 지정할 때는 단수형, 여럿을 지정할 때는 복수형이다.** 잘못 쓰면 컴파일러가 오류를 내는데, 한 글자 차이라 원인을 알아보기 어렵다.

p807이 정리한 주요 RID의 의미다.

| RID | 의미 |
|---|---|
| `win10-x64` | Windows 10 또는 Windows Server 2016 64비트 |
| `win10-arm64` | ARM64 Windows (Surface Pro X 등) |
| `osx-x64` | macOS Sierra 10.12 이상 |
| `osx.11.0-x64` / `osx.11.0-arm64` | Big Sur (Intel / Apple Silicon) |
| `linux-x64` | 대부분의 데스크톱 Linux 배포판 (Ubuntu, CentOS, Debian, Fedora) |
| `linux-arm` | Raspbian, Raspberry Pi OS 32비트 |
| `linux-arm64` | Ubuntu 64비트가 도는 Raspberry Pi |

```bash
dotnet publish -c Release -r win10-x64 --self-contained
dotnet publish -c Release -r osx.11.0-arm64 --self-contained
dotnet publish -c Release -r linux-x64 --self-contained
```

> **⚠️ `--self-contained` / `--no-self-contained`를 항상 명시하라**
>
> pro16(.NET 6 기준)은 "RID를 지정하면 게시 과정이 자체 포함을 기본으로 쓴다"고 설명한다. 그런데 이 기본값 규칙은 **SDK 버전에 따라 달라져 왔다.**
>
> 기본값을 외우는 대신 **항상 명시하라.** 한 단어 더 치는 비용으로, SDK를 올렸을 때 배포물의 성격이 조용히 바뀌는 사고를 막을 수 있다.

### 실측 — 크기가 얼마나 차이 나는가

아래 수치는 **p807이 측정한 값**이다. 예제는 `Environment.OSVersion` 정도를 출력하는 최소 콘솔 앱이다.

| 형태 | 대상 | 실행 파일 크기 | 게시 폴더 전체 |
|---|---|---|---|
| 자체 포함 | `win10-x64` | 154 KB | **68.3 MB** |
| 자체 포함 | `osx.11.0-arm64` | 125 KB | **73.9 MB** |
| 자체 포함 + 단일 파일 | `win10-x64` | **62.6 MB** (+ `.pdb` 11 KB) | 62.6 MB |
| Native AOT | `win-x64` | **약 1.2 MB** | 약 1.2 MB |

pro16이 측정한 다른 예제(클래스 라이브러리를 참조하는 콘솔 앱, .NET 6 기준)의 수치도 함께 본다.

- 프레임워크 종속 — **6개 파일**
- 자체 포함 — **226개 파일**
- 자체 포함 + 단일 파일 — 1개 파일, **60 MB**
- 위 + 압축 + 트리밍 + ReadyToRun — 1개 파일, **11 MB**

세 가지가 눈에 띈다.

1. **자체 포함의 실행 파일 자체는 작다(154 KB).** 68 MB는 옆에 딸린 런타임 어셈블리 수백 개의 합이다.
2. **단일 파일은 크기를 줄이지 않는다.** 226개를 하나로 합쳤을 뿐이다. p807의 표현대로 **파일 개수를 줄인 대가를 파일 크기로 치른 것**이다.
3. **크기를 실제로 줄이는 것은 트리밍과 AOT다.** 60 MB → 11 MB는 압축·트리밍·R2R의 합작이고, 1.2 MB는 AOT의 결과다.

### 단일 파일

```bash
# 프레임워크 종속 + 단일 파일
dotnet publish -r win10-x64 -c Release --no-self-contained -p:PublishSingleFile=true

# 자체 포함 + 단일 파일
dotnet publish -r win10-x64 -c Release --self-contained -p:PublishSingleFile=true
```

프레임워크 종속 단일 파일은 **두 개**의 파일을 만든다 — `MyApp.exe`와 `MyApp.pdb`. `.pdb`는 디버깅 정보를 담은 프로그램 디버그 데이터베이스 파일이다.

진짜 파일 하나로 만들려면 심볼을 실행 파일 안에 묻는다.

```xml
<PropertyGroup>
  <DebugType>embedded</DebugType>
</PropertyGroup>
```

> **⚠️ Windows에서는 파일이 더 나올 수 있다**
>
> p807이 명시한다. **.NET이 설치되어 있다고 가정할 수 없는 경우**, Linux는 여전히 두 파일만 만들지만 Windows에서는 다음 파일들이 추가로 나올 수 있다.
>
> `coreclr.dll`, `clrjit.dll`, `clrcompression.dll`, `mscordaccore.dll`
>
> "단일 파일"이 항상 문자 그대로 한 개를 뜻하지는 않는다. **게시 후 폴더를 직접 확인하는 습관을 들여라.**

압축 옵션도 있다.

```bash
dotnet publish -c Release -r win-x64 -p:PublishSingleFile=true \
  -p:DebugType=embedded -p:EnableCompressionInSingleFile=true
```

> **⚠️ 압축은 시작 시간을 희생한다**
>
> pro16이 짚는다. 출력을 압축하면 공간이 절약되지만 **애플리케이션 시작 시간에 영향을 준다.** 첫 실행 때 압축을 풀어야 하기 때문이다.
>
> CLI 도구처럼 자주 짧게 실행되는 프로그램이라면 압축이 손해일 수 있다. **크기와 시작 시간 중 무엇이 중요한지 먼저 정하고 켜라.**

### 트리밍

자체 포함 배포의 문제는 .NET 라이브러리가 자리를 많이 차지한다는 것이다. 트리밍은 **쓰이지 않는 어셈블리·타입·멤버를 제거**한다.

p807이 정리한 역사가 트리밍의 성격을 잘 보여준다.

| 버전 | 무엇이 바뀌었나 |
|---|---|
| .NET Core 3 | 어셈블리 단위 트리밍 도입 (당시 이름 `copyused`) |
| .NET 5 | 타입·멤버 단위까지 제거 (당시 이름 `link`). 기본은 꺼짐 |
| .NET 6 | 마이크로소프트가 라이브러리에 **주석(annotation)** 을 달아 안전하게 트리밍할 수 있게 표시. 타입·멤버 트리밍이 **기본값**이 됨 |
| .NET 7 | 이름 변경 — `link` → `full`, `copyused` → `partial` |

효과의 예로 p807은 Hello World 콘솔 앱에서 `System.Console.dll`이 **61.5 KB에서 31.5 KB로** 줄어든 것을 든다.

.NET 6 이후로는 타입·멤버 단위(전체) 트리밍이 기본이므로, **트림 수준을 따로 지정할 필요 없이 트리밍만 켜면 된다.**

```xml
<PropertyGroup>
  <PublishTrimmed>true</PublishTrimmed>
</PropertyGroup>
```

어셈블리 단위(부분) 트리밍을 원하면 두 속성을 쓴다.

```xml
<PropertyGroup>
  <PublishTrimmed>true</PublishTrimmed>
  <TrimMode>partial</TrimMode>
</PropertyGroup>
```

명령줄로도 같다.

```bash
dotnet publish ... -p:PublishTrimmed=True
dotnet publish ... -p:PublishTrimmed=True -p:TrimMode=partial
```

> **⚠️ 트리밍의 함정은 리플렉션이다**
>
> p807의 표현대로다. **관건은 트리밍이 쓰이지 않는 어셈블리·타입·멤버를 얼마나 잘 식별하느냐**다. 코드가 동적이면, 예컨대 리플렉션을 쓴다면 **제대로 동작하지 않을 수 있다.**
>
> 트리머는 정적 분석으로 "쓰인다"를 판정한다. `Type.GetType("MyApp.Plugin")`처럼 문자열로 타입을 찾는 코드는 정적으로 추적되지 않으므로, 그 타입이 제거되고 런타임에 실패한다.
>
> **가장 위험한 점은 실패가 게시 후에만 드러난다는 것이다.** 개발 중에는 트리밍이 적용되지 않으므로 아무 문제가 없다. 트리밍이나 AOT를 켤 거라면 **반드시 게시 산출물로 테스트하라.**

### Native AOT

Native AOT(ahead-of-time, 사전 컴파일)는 두 성질을 가진 어셈블리를 만든다.

- **자체 포함** — .NET 런타임이 설치되지 않은 시스템에서도 돈다
- **네이티브 코드로 사전 컴파일** — 시작이 빠르고 메모리 사용량이 작을 수 있다

핵심 차이는 시점이다. **Native AOT는 IL을 게시 시점에 네이티브 코드로 컴파일한다.** 런타임에 JIT 컴파일러가 하던 일을 앞당기는 것이다. 대신 **Windows x64나 Linux Arm 같은 특정 런타임 환경을 대상으로 삼아야 한다.**

```xml
<PropertyGroup>
  <TargetFramework>net8.0</TargetFramework>
  <PublishAot>true</PublishAot>
  <InvariantGlobalization>true</InvariantGlobalization>
</PropertyGroup>
```

```bash
dotnet publish -c Release -r win-x64
```

게시 로그에 `Generating native code`라는 줄이 나오면 AOT가 동작한 것이다.

> **⚠️ 개발 중에는 AOT가 적용되지 않는다**
>
> p807이 강조하는 지점이다. **AOT는 게시 시점에 일어나므로, 코드 편집기에서 디버깅하고 작업하는 동안에는 프로젝트에 AOT를 켜놨더라도 여전히 런타임 JIT 컴파일러를 쓴다.**
>
> 결과적으로 이런 일이 생긴다. 개발 중에는 완벽히 동작하던 콘솔 앱이, Native AOT로 게시하고 나면 실패한다. 트리밍되고 JIT되지 않은 **다른 코드**가 되었기 때문이다.
>
> 그래서 지침은 하나다. **프로젝트가 동작하리라 가정하기 전에 게시를 먼저 해봐라.** 게시 시점에 AOT 경고가 하나도 안 나오면 그때 비로소 확신할 수 있다.

### Native AOT의 제약

p807이 나열하는 제약이다.

| 제약 | 내용 |
|---|---|
| 동적 어셈블리 로딩 불가 | 플러그인 구조(52.14절)를 쓸 수 없다 |
| 런타임 코드 생성 불가 | `System.Reflection.Emit` 사용 불가 |
| 트리밍 필수 | 트리밍의 제약을 그대로 물려받는다 |
| 자체 포함 필수 | 호출하는 라이브러리를 전부 임베드해야 하므로 크기가 는다 |
| 크로스 플랫폼 게시 불가 | **Linux에서 Windows용 AOT 게시를 할 수 없고 그 반대도 안 된다** |

> **⚠️ 내 코드가 안 써도 .NET이 쓴다**
>
> 이것이 AOT 도입의 가장 큰 실질 장벽이다. p807의 지적을 옮긴다. **내 어셈블리는 위 기능을 안 쓸지 몰라도 .NET 자체의 주요 부분이 쓴다.**
>
> 예를 들어 ASP.NET Core MVC(컨트롤러를 쓰는 웹 API 포함)와 EF Core는 기능 구현을 위해 **런타임 코드 생성**을 한다. p807 기준으로 .NET 8은 **최소 API(Minimal API)를 쓰는 경우에만 ASP.NET Core를 기본 수준으로 지원하며, EF Core는 지원하지 않는다.**
>
> 즉 "AOT를 켰더니 웹 앱이 죽는다"는 대개 내 잘못이 아니라 아직 그 프레임워크가 준비되지 않은 것이다. **쓰려는 프레임워크가 AOT를 지원하는지부터 확인하라.**

AOT 게시 과정에는 코드 분석기가 포함되어 지원되지 않는 기능을 쓰면 경고한다. 타입이나 멤버가 AOT를 지원하지 않음을 나타내는 가장 흔한 표식은 **`[RequiresDynamicCode]` 특성**이다.

```csharp
using System.Reflection;
using System.Reflection.Emit;

AssemblyBuilder ab = AssemblyBuilder.DefineDynamicAssembly(
    new AssemblyName("MyAssembly"), AssemblyBuilderAccess.Run);
```

이 코드가 있는 프로젝트를 AOT로 게시하면 이런 경고가 나온다.

```text
warning IL3050: Using member 'System.Reflection.Emit.AssemblyBuilder.
DefineDynamicAssembly(AssemblyName, AssemblyBuilderAccess)' which has
'RequiresDynamicCodeAttribute' can break functionality when AOT compiling.
Defining a dynamic assembly requires dynamic code.
```

리플렉션 쪽 대응도 있다. AOT 컴파일 중의 트리밍은 **어떤 타입이 리플렉션으로만 접근되는 멤버를 갖는지 정적으로 판정할 수 없다.** 그 멤버는 제거되고 런타임 예외가 난다. p807의 지침은 이렇다. **개발자는 리플렉션으로만 동적 접근되는 멤버를 `[DynamicallyAccessedMembers]`로 표시해 트리밍에서 제외되게 해야 한다.**

### AOT의 환경 요구사항

Windows에서는 Visual Studio 2022의 **C++를 사용한 데스크톱 개발** 워크로드를 기본 구성 요소 전부와 함께 설치해야 한다. Linux에서는 컴파일러 툴체인과 .NET 런타임이 의존하는 라이브러리의 개발 패키지가 필요하다 — 예컨대 Ubuntu 18.04 이상에서는 다음과 같다.

```bash
sudo apt-get install clang zlib1g-dev
```

이런 도구가 필요한 이유는 AOT가 **네이티브 링커를 호출하기 때문**이다. IL을 네이티브 오브젝트 코드로 바꾼 뒤 실행 파일로 묶는 일은 그 OS의 링커가 한다. 이것이 크로스 플랫폼 게시가 불가능한 이유이기도 하다.

### 어느 것을 고를 것인가

```text
   런타임을 내가 통제하는 서버인가?
   ├─ 예 → 프레임워크 종속 (가장 작고 가장 단순하다)
   │
   └─ 아니오
        │
        시작 시간이 밀리초 단위로 중요한가?
        (컨테이너 · 서버리스 · 자주 실행되는 CLI 도구)
        ├─ 예
        │    │
        │    리플렉션 · 동적 로딩 · EF Core · MVC를 쓰는가?
        │    ├─ 예   → 자체 포함 + 트리밍 + ReadyToRun
        │    └─ 아니오 → Native AOT
        │
        └─ 아니오
             │
             파일 개수를 줄여야 하는가?
             ├─ 예   → 자체 포함 + 단일 파일 (필요하면 압축)
             └─ 아니오 → 자체 포함
```

배포 형태를 프로젝트 파일에 고정하면 명령줄이 짧아진다.

```xml
<PropertyGroup>
  <OutputType>Exe</OutputType>
  <TargetFramework>net8.0</TargetFramework>
  <RuntimeIdentifier>win-x64</RuntimeIdentifier>
  <SelfContained>true</SelfContained>
  <PublishSingleFile>true</PublishSingleFile>
  <PublishTrimmed>true</PublishTrimmed>
  <DebugType>embedded</DebugType>
  <EnableCompressionInSingleFile>true</EnableCompressionInSingleFile>
  <PublishReadyToRun>true</PublishReadyToRun>
</PropertyGroup>
```

```bash
dotnet publish -c Release -o out
```

> **📌 ReadyToRun은 AOT의 절반이다**
>
> `PublishReadyToRun`은 **JIT 컴파일의 일부를 게시 시점에 미리 해두는** 방식이다. AOT와 달리 IL도 함께 담고 JIT도 여전히 존재하므로 리플렉션 제약이 없다. 대신 크기는 늘고, 시작 속도 개선폭은 AOT보다 작다.
>
> "AOT는 못 쓰는데 시작이 느리다"는 상황의 표준 해법이 R2R이다. R2R과 AOT의 코드 생성 차이는 55.7절에서, 시작 시간 최적화 실전은 72.7절에서 다룬다. 애플리케이션 유형별 배포 선택은 81.9절에서 이어진다.

> **💡 배포 스크립트로 자동화하라**
>
> RID가 다섯 개면 명령을 다섯 번 쳐야 한다. p807은 **PowerShell 같은 스크립트 언어로 자동화하고, 크로스 플랫폼인 PowerShell Core로 어느 OS에서든 실행하라**고 권한다.
>
> 다만 Native AOT는 예외다. **크로스 플랫폼 게시가 불가능하므로 대상 OS마다 실제로 그 OS에서 게시해야 한다.** CI에서 OS별 잡을 따로 두는 이유가 이것이다.

## 이 장의 요약

- **SDK 스타일 `.csproj`가 짧은 이유는 정보가 사라져서가 아니라 기본값이 SDK로 이사했기 때문이다.** `Sdk` 특성 하나가 프로젝트 앞뒤로 `Sdk.props`와 `Sdk.targets`를 임포트하고, 소스 파일은 glob으로 자동 포함된다. 구식 프로젝트가 명시하던 파일 목록·GUID·참조 경로가 전부 관례로 대체됐다(4.1절).
- **TFM 한 줄이 여섯 가지를 동시에 결정한다.** 참조 어셈블리 집합, 기본 C# 언어 버전, 암시적 `using`, `runtimeconfig.json`의 런타임 버전, NuGet 자산 선택, 전처리기 기호. 어셈블리는 자기 대상보다 새 런타임에서는 돌지만 오래된 런타임에서는 돌지 않는다(4.2절).
- **.NET Standard는 런타임이 아니라 사양이다.** 여러 런타임이 공존하던 시절 라이브러리의 도달 범위를 넓히려고 만들어졌고, .NET 5의 통합으로 존재 이유가 대부분 사라졌다. 지금 `netstandard2.0`이 필요한 자리는 .NET Framework 소비자, 레거시 Xamarin, 그리고 소스 생성기다(4.3절).
- **컴파일러가 보는 어셈블리와 런타임이 쓰는 어셈블리는 다른 물건이다.** 참조 어셈블리는 API 표면만 담고 메서드 본문이 없다. `System.Runtime.dll`에는 타입이 0개이고 타입 전달자만 있다. 이 구조 덕분에 설치되지 않은 .NET 버전을 대상으로 빌드할 수 있다(4.4절).
- **런타임 대상이 기본 C# 버전을 정하고, `LangVersion`으로 올릴 수 있다.** 다만 올라가는 것은 문법뿐이다. 마커 타입만 필요한 기능은 직접 정의해 살릴 수 있지만, 런타임 지원이 필요한 기능은 방법이 없다. SDK 버전·TFM·설치된 런타임은 서로 독립된 세 축이다(4.5절).
- **`Nullable`은 켜고 끄는 이분법이 아니라 주석과 경고 두 축의 조합이다.** `TreatWarningsAsErrors`는 SDK를 올리는 것만으로 빌드를 깨뜨릴 수 있으므로 `WarningsAsErrors`로 좁히는 편이 오래 간다. `InvariantGlobalization`은 크기를 줄이는 대신 문화권 인식 동작을 통째로 바꾼다(4.6절).
- **패키지 참조 하나가 전이 의존성 수십 개를 끌고 온다.** 그 해석 결과가 `project.assets.json`이고, 실행 시 신뢰 목록을 채우는 것이 `deps.json`이다. 버전에 와일드카드를 쓰면 아무것도 안 바꾼 날 빌드가 깨진다(4.7절).
- **함께 개발 중인 코드는 프로젝트 참조로, 배포된 코드는 패키지 참조로 건다.** 직접 DLL 참조는 파일이 어긋나도 알려주지 않는다. `Directory.Build.props`는 위로 올라가며 **처음 찾은 하나만** 임포트한다(4.8절).
- **배포 형태 넷의 트레이드오프는 크기·시작 시간·동적 기능의 삼각형이다.** 프레임워크 종속이 가장 작고, 자체 포함이 가장 크며, 단일 파일은 개수만 줄일 뿐 크기는 안 줄이고, Native AOT만이 크기와 시작 시간을 동시에 줄이되 리플렉션과 동적 로딩을 포기한다(4.9절).
- **트리밍과 AOT의 실패는 게시 후에만 드러난다.** 개발 중에는 트리밍도 AOT도 적용되지 않으므로, 이 둘을 켤 거라면 반드시 게시 산출물로 테스트해야 한다.

## 연습 문제

1. `dotnet new console -o Probe`로 프로젝트를 만들고 `dotnet msbuild -preprocess:full.xml`을 실행하라. 생성된 `full.xml`에서 `EnableDefaultCompileItems`와 `OutputPath`를 검색해, 각각 **어느 SDK 파일에서 어떤 값으로 정의되는지** 확인하라. 그다음 `.csproj`에서 그 값을 덮어써 보고 다시 확인하라.

2. 클래스 라이브러리를 하나 만들고 `<TargetFrameworks>net8.0;netstandard2.0</TargetFrameworks>`로 멀티 타깃팅하라. `#if NET8_0_OR_GREATER`로 두 구현을 갈라 쓰고, `dotnet build -c Release` 후 `bin/Release/` 아래에 **어셈블리가 몇 개 생겼는지** 확인하라. 이어서 `netstandard2.0` 쪽에서 `record`를 선언해 오류 CS0518을 재현하고, `IsExternalInit`을 직접 정의해 해결하라.

3. `netstandard2.0` 프로젝트에서 `<LangVersion>`을 지정하지 않은 채 `switch` 식(`x switch { ... }`)을 써서 컴파일 오류를 확인하라. 그다음 `<LangVersion>12</LangVersion>`을 추가해 통과하는 것을 보고, **어떤 기능이 이렇게 살아나고 어떤 기능이 안 살아나는지** 최소 세 가지를 직접 실험해 표로 정리하라.

4. 콘솔 앱에서 4.7절의 프로빙 경로 출력 코드를 실행해 `TRUSTED_PLATFORM_ASSEMBLIES`의 항목 수를 세라. 그다음 패키지를 하나(예: `Microsoft.EntityFrameworkCore.Sqlite`) 추가하고 다시 세라. **몇 개가 늘었는가?** `dotnet list package --include-transitive`의 출력과 대조하라.

5. 프로젝트 두 개(`Core` 라이브러리, `App` 콘솔)를 만들고 `App`에서 `Core`를 **프로젝트 참조**로 건 뒤, `Core`의 public 메서드를 고치고 `App`만 빌드해 반영되는 것을 확인하라. 그다음 참조를 지우고 `Core`의 컴파일된 DLL을 **직접 참조**로 바꾼 뒤 같은 실험을 반복해, 수정이 반영되지 않는 상황을 재현하라.

6. 최소 콘솔 앱 하나를 네 가지 형태로 게시하고 **각각의 파일 개수와 총 크기를 직접 측정해 표로 만들어라.** (a) 프레임워크 종속, (b) 자체 포함, (c) 자체 포함 + 단일 파일, (d) 자체 포함 + 단일 파일 + 트리밍. 4.9절의 실측 표와 비교해 자기 환경에서 어떻게 다른지 설명하라.

7. `<PublishAot>true</PublishAot>`를 켠 콘솔 앱에 `AssemblyBuilder.DefineDynamicAssembly` 호출을 넣고 `dotnet publish`를 실행해 **경고 IL3050을 직접 재현하라.** 그다음 그 호출을 지우고 게시해 경고가 사라지는 것과, 생성된 실행 파일의 크기를 확인하라.
