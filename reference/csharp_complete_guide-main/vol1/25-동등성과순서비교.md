## 25.1 값 동등성 vs 참조 동등성

### 동등성은 하나가 아니다

"같다"는 말은 프로그램에서 최소한 네 가지 뜻으로 쓰인다. 이 넷을 구분하지 못하면 나머지 절이 전부 뒤죽박죽이 된다.

| 개념 | 묻는 질문 | 판정 기준 | 대표 API |
|---|---|---|---|
| **참조 동등성**(referential equality) | 두 참조가 **같은 객체**를 가리키는가 | 힙 주소 | `object.ReferenceEquals`, `object`로 캐스팅한 `==` |
| **값 동등성**(value equality) | 두 값이 **같은 것을 나타내는가** | 타입이 정하는 의미 | `Equals`, `IEquatable<T>.Equals` |
| **논리적 동등성**(logical equality) | 도메인 규칙상 **같은 것으로 취급해야 하는가** | 타입이 정의한 특례 | 재정의된 `Equals`, `IEqualityComparer<T>` |
| **구조적 동등성**(structural equality) | **모든 구성 요소가 각각 같은가** | 필드/요소 단위 재귀 비교 | `ValueType.Equals`, `IStructuralEquatable`, 레코드·튜플의 자동 `Equals` |

참조 동등성은 **정체성**(identity)을 묻는다. 값 동등성은 **내용**을 묻는다. 논리적 동등성은 값 동등성의 한 갈래인데, "내용이 전부 같은가"가 아니라 "도메인 관점에서 같은 것인가"를 묻는다는 점이 다르다. 구조적 동등성 역시 값 동등성의 한 갈래이지만, 의미를 따지지 않고 기계적으로 필드를 훑는다.

```csharp
// ① 참조 동등성 — 정체성
var a = new StringBuilder("foo");
var b = new StringBuilder("foo");
Console.WriteLine (object.ReferenceEquals (a, b));   // False

// ② 값 동등성 — 내용
Console.WriteLine (a.Equals (b));                    // True

// ③ 논리적 동등성 — 도메인 규칙 (오프셋이 달라도 같은 시점이면 같다)
var dt1 = new DateTimeOffset (2010, 1, 1, 1, 1, 1, TimeSpan.FromHours (8));
var dt2 = new DateTimeOffset (2010, 1, 1, 2, 1, 1, TimeSpan.FromHours (9));
Console.WriteLine (dt1 == dt2);                      // True

// ④ 구조적 동등성 — 모든 요소가 각각 같은가
var t1 = (1, "x");
var t2 = (1, "x");
Console.WriteLine (t1.Equals (t2));                  // True
```

③이 흥미롭다. `DateTimeOffset`은 UTC `DateTime` 하나와 오프셋 정수 하나를 필드로 갖는 구조체다. 구조적으로 비교하면 두 값의 오프셋 필드가 다르므로 달라야 한다. 그런데 `True`가 나온다. **`DateTimeOffset`이 동등성 의미론을 손봐서, 같은 시점을 가리키면 오프셋이 달라도 같다고 판정하도록 만들었기 때문이다.** 이것이 논리적 동등성이다.

> **📌 네 개념은 계층이 아니라 선택지다**
>
> 타입 작성자는 넷 중 무엇을 자기 타입의 "같음"으로 삼을지 **고른다.** 잘못된 답은 없지만 잘못된 조합은 있다. 예를 들어 `Equals`는 논리적 동등성인데 `GetHashCode`는 구조적 동등성으로 계산하면 계약이 깨진다(25.4절). 무엇을 고르든 **하나의 정의를 모든 창구에 일관되게 적용**하는 것이 전부다.

### 기본 동작 — 재정의하지 않으면 무엇이 되는가

| 타입 종류 | `==` 기본 동작 | `Equals` 기본 동작 | 구현체 |
|---|---|---|---|
| 클래스 | 참조 동등성 | 참조 동등성 | `Object.Equals` |
| 구조체 | **컴파일 오류** (CS0019) | 구조적 동등성 | `ValueType.Equals` |
| 레코드 클래스 | 구조적 동등성 | 구조적 동등성 | 컴파일러 생성(19.3절) |
| 레코드 구조체 | 구조적 동등성 | 구조적 동등성 | 컴파일러 생성(19.3절) |
| 익명 타입 | 참조 동등성 | 구조적 동등성 | 컴파일러 생성 |
| 튜플(`ValueTuple`) | 구조적 동등성 | 구조적 동등성 | 라이브러리 구현(77.3절) |
| 열거형 | 기반 정수 비교 | 기반 정수 비교 | `Enum.Equals` |
| 인터페이스·`object` | 참조 동등성 | 런타임 타입에 따름 | — |

**값 타입은 값 동등성을 쓰고, 참조 타입은 참조 동등성을 쓴다** — 재정의하지 않는 한 이것이 규칙이다. 값 타입은 사실 (박싱되지 않는 한) 값 동등성밖에 쓸 수 없다. 값 타입에는 정체성이 없기 때문이다.

```csharp
int x = 5, y = 5;
Console.WriteLine (x == y);        // True — 값 동등성

class Foo { public int X; }
Foo f1 = new Foo { X = 5 };
Foo f2 = new Foo { X = 5 };
Console.WriteLine (f1 == f2);      // False — 내용이 같아도 다른 객체다

Foo f3 = f1;
Console.WriteLine (f1 == f3);      // True — 같은 객체다
```

메모리 그림으로 보면 자명하다.

```text
   스택                        관리 힙
 ┌────────┐            ┌──────────────────┐
 │  f1 ●──┼───────────▶│ Foo #1   X = 5   │◀──┐
 ├────────┤            └──────────────────┘   │
 │  f2 ●──┼───────┐                           │
 ├────────┤       │    ┌──────────────────┐   │
 │  f3 ●──┼───────┼───▶│ (같은 객체 #1)   │───┘
 └────────┘       │    └──────────────────┘
                  └───▶┌──────────────────┐
                       │ Foo #2   X = 5   │
                       └──────────────────┘

  f1 == f2 → 서로 다른 주소  → False
  f1 == f3 → 같은 주소       → True
```

### 참조 타입에 값 의미론을 얹은 예

`System.Uri`와 `System.String`은 참조 타입인데도 값 동등성을 보인다. 타입 작성자가 그렇게 만들었기 때문이다.

```csharp
Uri uri1 = new Uri ("http://www.linqpad.net");
Uri uri2 = new Uri ("http://www.linqpad.net");
Console.WriteLine (uri1 == uri2);          // True

var s1 = "http://www.linqpad.net";
var s2 = "http://" + "www.linqpad.net";
Console.WriteLine (s1 == s2);              // True
```

두 클래스의 공통점은 **불변**이라는 것이다. 이것은 우연이 아니다. 25.4절과 25.8절에서 보겠지만, 값 의미론을 가진 참조 타입이 가변이면 해시 기반 컬렉션에서 조용히 망가진다.

반대 방향의 예가 `StringBuilder`다. `Equals`는 값 동등성인데 `==`는 참조 동등성이다.

```csharp
var sb1 = new StringBuilder ("foo");
var sb2 = new StringBuilder ("foo");
Console.WriteLine (sb1 == sb2);            // False — 참조 동등성
Console.WriteLine (sb1.Equals (sb2));      // True  — 값 동등성
```

이상해 보이지만 의도된 설계다. `StringBuilder`는 **가변**이므로 값 동등성을 `==`의 기본으로 삼으면 위험하고, 그렇다고 "내용이 같은지" 물을 방법이 아예 없으면 불편하다. 그래서 흔히 쓰이는 `==`는 안전한 쪽(참조)으로 두고, 명시적으로 `Equals`를 부른 사람에게만 값 비교를 준다.

> **⚠️ `==`가 참조 동등성이라고 해서 `Equals`도 그럴 거라고 가정하지 마라**
>
> `sb1 == sb2`가 `False`인 것을 보고 "그러면 이 딕셔너리에 `StringBuilder`를 키로 넣어도 안전하겠군"이라고 판단하면 틀린다. 딕셔너리는 `==`를 쓰지 않는다. **`Equals`와 `GetHashCode`를 쓴다.** `StringBuilder`는 `Equals`가 값 동등성이므로 내용을 바꾸는 순간 키를 잃어버린다(25.8절).
>
> 반대 방향의 오해도 흔하다. `a == b`가 `True`라고 해서 두 참조가 같은 객체를 가리킨다는 뜻은 아니다. 정체성을 묻고 싶으면 `object.ReferenceEquals`를 써야 한다(15.6절).

### 구조체의 기본 동등성 — 구조적 동등성

구조체는 기본적으로 **구조적 동등성**이라 불리는 특수한 값 동등성을 보인다. 모든 멤버가 같으면 두 값이 같다고 본다.

```csharp
struct Point3 { public int X, Y, Z; }

var p = new Point3 { X = 1, Y = 2, Z = 3 };
var q = new Point3 { X = 1, Y = 2, Z = 3 };
Console.WriteLine (p.Equals (q));          // True
// Console.WriteLine (p == q);             // 컴파일 오류 CS0019
```

`==`가 컴파일 오류인 것에 주목하라. **구조체에 `==`는 자동으로 주어지지 않는다.** 값 동등성을 원하면 `Equals`는 공짜지만 `==`는 직접 오버로딩해야 한다(22.2절).

이 기본 구현이 왜 느린지, 어떤 조건에서 비트 비교 빠른 경로로 가고 어떤 조건에서 리플렉션으로 떨어지는지는 16.7절에서 IL 수준까지 다뤘다. **이 장에서 볼 것은 그 기본 구현이 계약을 어떻게 위태롭게 만드는가**다(25.4절, 25.5절).

## 25.2 표준 동등성 프로토콜 — `==`, `Equals`, `IEquatable<T>`, `ReferenceEquals`

### 다섯 개의 창구

"두 값이 같은가"를 묻는 방법이 .NET에는 다섯 개 있다. 이름이 겹치고, 호출 시점이 다르고, 결과도 다를 수 있다. **먼저 표부터 보고 시작한다.**

| # | 창구 | 시그니처 | 바인딩 | 무엇이 결정하는가 | `null` 안전 | 값 타입 박싱 | 재정의 가능 |
|---|---|---|---|---|---|---|---|
| 1 | `==` 연산자 | `static bool op_Equality(T,T)` | **컴파일 타임** | 피연산자의 **정적 타입** | 안전(연산자 본문이 처리) | 없음 | 오버로딩 가능 |
| 2 | `object.Equals(object)` | `virtual bool Equals(object)` | **런타임** | 좌변의 **런타임 타입** | 좌변이 `null`이면 `NullReferenceException` | **인수 박싱** | `override` 가능 |
| 3 | `IEquatable<T>.Equals(T)` | `bool Equals(T)` | 인터페이스/직접 호출 | 정적 타입 + 구현 | 좌변이 `null`이면 예외 | 없음 | 구현으로 제공 |
| 4 | `object.ReferenceEquals(a,b)` | `static bool(object,object)` | 컴파일 타임(비가상) | **항상 정체성** | 안전 | **양쪽 박싱** | **불가** |
| 5 | `object.Equals(a,b)` | `static bool(object,object)` | 컴파일 타임(비가상) | 좌변의 런타임 타입에 위임 | **안전** | **양쪽 박싱** | **불가** |

이 표의 각 행을 하나씩 뜯어본다.

### ① `==` — 정적으로 결정된다

`==`와 `!=`는 **연산자**다. 즉 정적 함수로 구현되며, 컴파일 타임에 어느 타입이 비교를 수행할지 결정된다. 가상 동작은 전혀 개입하지 않는다.

```csharp
int x = 5;
int y = 5;
Console.WriteLine (x == y);        // True — 컴파일러가 int의 ==에 못 박았다
```

그런데 다음은 다르다.

```csharp
object x = 5;
object y = 5;
Console.WriteLine (x == y);        // False
```

`object`는 클래스(따라서 참조 타입)이므로 `object`의 `==`는 참조 동등성을 적용한다. `x`와 `y`는 힙에 각각 박싱된 서로 다른 객체를 가리키므로 결과는 `False`다. **값은 그대로인데 변수의 선언 타입만 바꿨더니 결과가 뒤집혔다.** `==`의 정적 바인딩이 무엇을 뜻하는지 이보다 명확히 보여 주는 예는 없다. IL 수준의 대응은 22.3절에 있다.

### ② `object.Equals(object)` — 런타임에 결정된다

앞 예를 올바르게 비교하려면 가상 `Equals`를 쓴다.

```csharp
object x = 5;
object y = 5;
Console.WriteLine (x.Equals (y));  // True
```

`Equals`는 **객체의 실제 타입에 따라 런타임에 해석된다.** 이 경우 `Int32`의 `Equals`가 호출되어 값 동등성을 적용하고 `True`를 반환한다.

정리하면 이렇다.

- 참조 타입에서 `Equals`의 기본 동작은 참조 동등성이다.
- 구조체에서 `Equals`의 기본 동작은 각 필드에 대해 `Equals`를 호출하는 구조적 비교다.

따라서 `Equals`는 **타입을 모르는 채로 두 객체를 비교**하기에 적합하다.

```csharp
public static bool AreEqual (object obj1, object obj2)
    => obj1.Equals (obj2);
```

그런데 이 코드에는 결함이 하나 있다. **첫 인수가 `null`이면 `NullReferenceException`이 난다.** 고치면 이렇다.

```csharp
public static bool AreEqual (object obj1, object obj2)
{
    if (obj1 == null) return obj2 == null;
    return obj1.Equals (obj2);
}
```

더 짧게는 이렇다.

```csharp
public static bool AreEqual (object obj1, object obj2)
    => obj1 == null ? obj2 == null : obj1.Equals (obj2);
```

> **📌 왜 이렇게 복잡한가 — `==`를 가상으로 만들지 않은 세 가지 이유**
>
> C# 설계자들이 `==`를 가상으로 만들어 `Equals`와 똑같이 동작하게 하지 않은 데는 이유가 셋 있다.
>
> 1. **첫 피연산자가 `null`이면 `Equals`는 `NullReferenceException`으로 실패한다.** 정적 연산자는 그렇지 않다.
> 2. **`==`는 정적으로 해석되므로 극도로 빠르다.** 계산 집약적 코드를 페널티 없이 쓸 수 있고, 그러자고 C++ 같은 다른 언어를 배울 필요가 없다.
> 3. **`==`와 `Equals`가 서로 다른 동등성 정의를 적용하는 것이 유용할 때가 있다.**
>
> 결국 설계의 복잡성은 상황의 복잡성을 반영한다. 동등성이라는 개념 자체가 여러 시나리오를 아우르기 때문이다.

### ⑤ 정적 `object.Equals(a, b)` — `null` 안전한 이유

`object` 클래스는 위 `AreEqual`이 하는 일을 그대로 해 주는 정적 도우미를 제공한다. 이름은 가상 메서드와 똑같은 `Equals`지만 인수가 둘이므로 충돌하지 않는다.

```csharp
public static bool Equals (object objA, object objB);
```

구현은 이렇게 생겼다.

```csharp
public static bool Equals (object left, object right)
{
    // ① 정체성 검사 — 같은 객체면 값도 같다. 둘 다 null인 경우도 여기서 처리된다
    if (object.ReferenceEquals (left, right))
        return true;

    // ② 한쪽만 null이면 다르다 (둘 다 null인 경우는 ①에서 걸렀다)
    if (object.ReferenceEquals (left, null) ||
        object.ReferenceEquals (right, null))
        return false;

    // ③ 좌변의 인스턴스 Equals에 위임한다
    return left.Equals (right);
}
```

**`null` 안전성의 원천은 ①과 ②다.** 인스턴스 메서드를 호출하기 전에 두 번의 `ReferenceEquals`로 `null` 조합을 전부 소진하므로, ③에 도달했을 때 `left`는 절대 `null`이 아니다. 게다가 ①이 `null == null`을 `true`로 만들어 주므로 "둘 다 없음은 같음"이라는 직관도 지켜진다.

```csharp
object x = 3, y = 3;
Console.WriteLine (object.Equals (x, y));    // True
x = null;
Console.WriteLine (object.Equals (x, y));    // False
y = null;
Console.WriteLine (object.Equals (x, y));    // True
```

정적 `Equals`가 위임 대상으로 **좌변**을 고른다는 사실은 중요하다. 좌변 타입의 규칙이 적용된다는 뜻이고, 그래서 `Equals`의 대칭성 계약이 깨져 있으면 **인수 순서에 따라 결과가 달라진다**(25.3절).

이 메서드의 실전 용도는 제네릭 타입이다. 아래 코드에서 `object.Equals`를 `==`나 `!=`로 바꾸면 컴파일되지 않는다.

```csharp
class Test<T>
{
    T _value;

    public void SetValue (T newValue)
    {
        if (!object.Equals (newValue, _value))
        {
            _value = newValue;
            OnValueChanged();
        }
    }

    protected virtual void OnValueChanged() { }
}
```

**연산자는 여기서 금지된다.** 컴파일러가 알려지지 않은 타입의 정적 메서드에 바인딩할 수 없기 때문이다. 이 제약을 정면으로 푸는 것이 ※C# 11의 정적 추상 인터페이스 멤버다(22.7절).

> **💡 제네릭 코드에서는 `EqualityComparer<T>.Default`가 더 낫다**
>
> 같은 비교를 `EqualityComparer<T>` 클래스로 더 정교하게 구현할 수 있다. **박싱을 피한다는 이점**이 있다.
>
> ```csharp
> if (!EqualityComparer<T>.Default.Equals (newValue, _value))
> ```
>
> `object.Equals(a, b)`는 두 인수를 `object`로 받으므로 `T`가 값 타입이면 호출마다 힙 할당이 두 번 일어난다. `EqualityComparer<T>.Default`는 `T`가 `IEquatable<T>`를 구현하면 그쪽으로 직접 디스패치하므로 박싱이 없고, JIT이 값 타입에 대해 이 호출을 가상 해제(devirtualize)할 수도 있다. 비교자 자체의 사용법은 24.13절에 있다.

### ④ `object.ReferenceEquals` — 정체성을 강제한다

가끔 참조 동등성을 강제해야 한다. 정적 `object.ReferenceEquals`가 정확히 그 일을 한다.

```csharp
Widget w1 = new Widget();
Widget w2 = new Widget();
Console.WriteLine (object.ReferenceEquals (w1, w2));   // False

class Widget { /* ... */ }
```

이렇게 해야 하는 이유는, `Widget`이 가상 `Equals`를 재정의해서 `w1.Equals(w2)`가 `true`를 반환하도록 만들었을 수도 있기 때문이다. 게다가 `==`를 오버로딩해서 `w1 == w2`도 `true`가 되게 만들었을 수 있다. 그런 경우 `object.ReferenceEquals`를 호출하면 **정상적인 참조 동등성 의미론이 보장된다.**

참조 동등성을 강제하는 다른 방법은 양쪽 값을 `object`로 캐스팅한 뒤 `==`를 적용하는 것이다.

```csharp
Console.WriteLine ((object) w1 == (object) w2);        // 같은 효과
```

값 타입에 `ReferenceEquals`를 넘기면 언제나 `false`가 나온다. 심지어 자기 자신과 비교해도 그렇다. 매개변수가 `object`라 호출할 때마다 별도로 박싱되기 때문이다(15.6절).

```csharp
int i = 5;
int j = 5;
Console.WriteLine (object.ReferenceEquals (i, j));     // False — 늘 그렇다
Console.WriteLine (object.ReferenceEquals (i, i));     // False — 이것도 그렇다
```

### ③ `IEquatable<T>` — 박싱 없는 동등성

`object.Equals`를 호출하면 값 타입에서 박싱이 강제된다. 박싱은 실제 비교 자체보다 비싸므로 성능이 중요한 상황에서 바람직하지 않다. C# 2.0이 도입한 해법이 `IEquatable<T>`다.

```csharp
public interface IEquatable<T>
{
    bool Equals (T other);
}
```

`IEquatable<T>`는 구현되었을 때 **`object`의 가상 `Equals`와 같은 결과를 더 빨리 내는 것**이 목적이다. 기본 .NET 타입 대부분이 이 인터페이스를 구현한다. 제네릭 타입의 제약으로 쓸 수 있다.

```csharp
class Test<T> where T : IEquatable<T>
{
    public bool IsEqual (T a, T b)
    {
        return a.Equals (b);       // 제네릭 T에 박싱이 없다
    }
}
```

제약을 제거해도 클래스는 여전히 컴파일되지만, `a.Equals(b)`는 더 느린 `object.Equals`에 바인딩된다(`T`가 값 타입이라고 가정할 때 더 느리다).

> **⚠️ `IEquatable<T>`만 구현하고 `Equals`를 재정의하지 않으면 컬렉션이 둘로 갈린다**
>
> `IEquatable<T>.Equals(T)`를 구현하면서 `object.Equals(object)`를 재정의하지 않으면 **두 창구가 다른 답을 낸다.** `Dictionary<T,V>`는 `EqualityComparer<T>.Default`를 통해 `IEquatable<T>` 쪽을 부르고, `Hashtable`이나 `ArrayList.Contains` 같은 비제네릭 경로, 그리고 `object`로 다루는 코드는 `object.Equals` 쪽을 부른다. 같은 데이터를 두 컬렉션에 넣었는데 한쪽에서만 찾아지는 사태가 벌어진다.
>
> **규칙은 단순하다. `IEquatable<T>`를 구현하면 반드시 `object.Equals(object)`도 재정의하고, 그것을 `IEquatable<T>.Equals(T)`로 위임시켜라.** 그리고 `GetHashCode`도 함께 재정의하라.

### `Equals`와 `==`가 다를 때 — NaN과 −0

`==`와 `Equals`가 서로 다른 동등성 정의를 적용하는 것이 유용할 때가 있다고 했다. 가장 유명한 예가 이것이다.

```csharp
double x = double.NaN;
Console.WriteLine (x == x);            // False
Console.WriteLine (x.Equals (x));      // True
```

`double`의 `==` 연산자는 **NaN이 무엇과도 — 심지어 다른 NaN과도 — 같을 수 없다**고 강제한다. 이것이 수학적으로 가장 자연스럽고, 밑바닥 CPU 동작을 그대로 반영한다.

그러나 `Equals` 메서드는 **반사적 동등성**을 적용할 의무가 있다. 즉 `x.Equals(x)`는 언제나 `true`를 반환해야 한다. **컬렉션과 딕셔너리가 이 동작에 의존하기 때문이다.** 그렇지 않으면 앞서 저장한 항목을 찾을 수 없게 된다.

```csharp
var list = new List<double> { double.NaN };
Console.WriteLine (list.Contains (double.NaN));    // True — Equals를 쓴다
Console.WriteLine (list[0] == double.NaN);         // False — ==를 쓴다

var set = new HashSet<double> { double.NaN };
Console.WriteLine (set.Contains (double.NaN));     // True
```

`-0.0`에서는 반대 방향의 불일치가 생긴다.

| 비교 | `NaN` vs `NaN` | `0.0` vs `-0.0` |
|---|---|---|
| `==` | `false` | `true` |
| `Equals` | `true` | `true` |
| `CompareTo` | `0` (같은 순위) | `0` (같은 순위) |
| 비트 패턴 동일 | 아니오(NaN 표현은 여러 개) | **아니오** |

`0.0`과 `-0.0`은 비트 패턴이 다른데도 `==`, `Equals`, `CompareTo` 모두 같다고 답한다. **즉 값 타입의 기본 구조적 동등성(비트 비교)과 부동소수점의 의미론적 동등성이 어긋난다.** 16.7절에서 "`double` 필드가 하나라도 있으면 구조체의 빠른 비트 비교 경로가 막힌다"고 한 이유가 이것이다. 비트로 비교하면 `0.0 != -0.0`이라는 틀린 답이 나온다. 부동소수점 특수값 자체의 전모는 7.6절에 있다.

값 타입에서 `Equals`와 `==`가 갈리는 일은 사실 드물다. **더 흔한 시나리오는 참조 타입**이다. 타입 작성자가 `Equals`는 값 동등성을 수행하도록 손보면서 `==`는 기본 참조 동등성으로 남겨 두는 경우인데, `StringBuilder`가 정확히 그렇다(25.1절).

> **⚠️ `==`의 결과로 반사성을 가정하는 코드를 쓰지 마라**
>
> ```csharp
> // 자기 자신을 제외하려는 의도 — NaN이 섞이면 무너진다
> var others = values.Where (v => !(v == target));
> ```
>
> `target`이 `NaN`이면 `v == target`이 모든 원소에 대해 `false`이므로 **원본 전체가 그대로 나온다.** `NaN` 자기 자신도 포함된다. 의도가 "같은 값을 빼겠다"라면 `Equals`를 써야 한다.
>
> ```csharp
> var others = values.Where (v => !EqualityComparer<double>.Default.Equals (v, target));
> ```

### 다섯 창구의 호출 경로

어느 창구가 어디서 호출되는지가 실무의 핵심이다.

```text
   사용자 코드                       프레임워크 코드
 ┌──────────────┐              ┌────────────────────────────┐
 │  a == b      │              │ Dictionary<K,V>.TryGetValue│
 │  a.Equals(b) │              │ HashSet<T>.Contains        │
 │  Equals(a,b) │              │ List<T>.Contains / IndexOf │
 └──────┬───────┘              │ LINQ Distinct/GroupBy/Join │
        │                      └──────────────┬─────────────┘
        │                                     │
        │                        EqualityComparer<T>.Default
        │                                     │
        │              ┌──────────────────────┴───────────────┐
        │              │ T가 IEquatable<T>?                   │
        │              ├──────────────┬───────────────────────┤
        │              │ 예           │ 아니오                │
        ▼              ▼              ▼                       │
  op_Equality   IEquatable<T>.Equals(T)   object.Equals(object)
   (정적)          (박싱 없음)              (값 타입이면 박싱)
```

**`==`는 프레임워크가 절대 부르지 않는다.** 이것이 이 다이어그램의 결론이다. 컬렉션·LINQ·비교자 전부가 `Equals`와 `GetHashCode`만 쓴다. `==`만 오버로딩하고 `Equals`를 재정의하지 않은 타입은 자기 코드에서만 "잘 동작하는 것처럼" 보이고 컬렉션에 넣는 순간 무너진다. 컴파일러가 CS0660 경고로 이 실수를 알려 준다(22.3절).

## 25.3 `Equals` 재정의 5계명

### 계약이 먼저다

`Equals`를 재정의한다는 것은 **수학적 동치 관계를 구현하겠다는 약속**이다. 이 약속을 어기면 컴파일러도 런타임도 아무 말을 하지 않지만, 컬렉션·정렬·LINQ·직렬화가 예측 불가능하게 동작한다. 계약은 다섯 개다.

| # | 이름 | 형식적 진술 | 깨지면 |
|---|---|---|---|
| 1 | **반사성**(reflexive) | `x.Equals(x)`는 언제나 `true` | 넣은 항목을 자기 자신으로 못 찾는다 |
| 2 | **대칭성**(symmetric) | `x.Equals(y)`와 `y.Equals(x)`는 같은 값 | 인수 순서에 따라 답이 달라진다 |
| 3 | **추이성**(transitive) | `x.Equals(y)`이고 `y.Equals(z)`면 `x.Equals(z)` | 그룹핑·집합 연산이 입력 순서에 좌우된다 |
| 4 | **일관성**(consistent) | 값이 변하지 않는 한 결과가 반복되고 예외를 던지지 않는다 | 조회 결과가 호출마다 달라진다 |
| 5 | **`null` 처리** | `x.Equals(null)`은 `false`(널 허용 타입 제외) | `NullReferenceException`이 예상치 못한 곳에서 난다 |

원천 도서들은 이 다섯을 조금씩 다른 말로 정리하지만 내용은 같다. 하나씩 **깨는 코드와 그 결과**로 확인한다.

### 계명 ① 반사성 — 자기 자신과 같아야 한다

```csharp
// 계약 위반 예제
public sealed class Sloppy
{
    public double Value;
    public override bool Equals (object obj)
        => obj is Sloppy s && Value == s.Value;    // == 를 그대로 썼다
    public override int GetHashCode() => Value.GetHashCode();
}
```

`Value`가 `NaN`인 인스턴스에서 반사성이 깨진다.

```csharp
var a = new Sloppy { Value = double.NaN };
Console.WriteLine (a.Equals (a));                  // False — 반사성 위반

var set = new HashSet<Sloppy> { a };
Console.WriteLine (set.Contains (a));              // False — 방금 넣은 그 객체다
Console.WriteLine (set.Count);                     // 1 — 들어는 있다
set.Add (a);
Console.WriteLine (set.Count);                     // 2 — 같은 객체가 두 번 들어갔다
```

**같은 참조를 두 번 넣었는데 집합의 크기가 2가 됐다.** `HashSet<T>`는 "이미 있는가"를 `Equals`로 판정하는데 그 판정이 `false`를 냈기 때문이다. 이 상태에서 `Remove(a)`도 실패하므로 항목을 지울 수도 없다.

고치는 법은 `double`이 하는 것과 같다. `==` 대신 `Equals`로 위임한다.

```csharp
public override bool Equals (object obj)
    => obj is Sloppy s && Value.Equals (s.Value);   // NaN에 대해 반사적이다
```

> **⚠️ 부동소수점 필드가 있는 타입에서 `==`로 필드를 비교하지 마라**
>
> `double`·`float` 필드를 `==`로 비교하는 `Equals`는 **NaN이 들어오는 순간 반사성을 잃는다.** 좌표, 측정값, 통계량, 파싱 결과 — NaN이 들어올 경로는 생각보다 많다(`0.0/0.0`, `Math.Sqrt(-1)`, `double.Parse("NaN")`, JSON 역직렬화).
>
> 필드 비교는 언제나 `field.Equals(other.field)` 또는 `EqualityComparer<T>.Default.Equals(...)`로 하라. 레코드와 컴파일러 생성 `Equals`는 이미 이렇게 한다(19.3절).

허용 오차(`Math.Abs(a - b) < eps`) 기반 `Equals`는 더 나쁘다. 반사성은 지키지만 **추이성이 깨진다.** 계명 ③에서 다룬다.

### 계명 ② 대칭성 — 순서가 결과를 바꾸면 안 된다

대칭성이 깨지는 대표 경로가 둘 있다. **하나는 `null` 처리이고, 하나는 상속 계층이다.**

먼저 `null`이다. 다음은 계약을 지킨 코드지만 대칭성의 한계를 보여 준다.

```csharp
Foo a = new Foo();
Foo b = null;

Console.WriteLine (a.Equals (b));    // False — 정상
Console.WriteLine (b.Equals (a));    // NullReferenceException
```

`a.Equals(b)`는 `a`가 `null`이 아니고 `b`가 `null`일 때 `false`를 반환한다. 그런데 `b.Equals(a)`는 그 값들에 대해 `NullReferenceException`을 던진다. **인스턴스 메서드로는 이 비대칭을 원리적으로 없앨 수 없다.** 그래서 `null`이 섞일 수 있는 자리에서는 정적 `object.Equals(a, b)`를 쓰는 것이 정답이다(25.2절).

### 상속 계층에서 대칭성이 깨지는 고전적 문제

두 번째 경로가 더 위험하다. 다음은 원천 도서가 제시한 결함 있는 계층이다.

```csharp
public class B : IEquatable<B>
{
    public override bool Equals (object right)
    {
        if (object.ReferenceEquals (right, null)) return false;
        if (object.ReferenceEquals (this, right)) return true;

        // 여기가 문제다
        B rightAsB = right as B;
        if (rightAsB == null) return false;
        return this.Equals (rightAsB);
    }

    public bool Equals (B other) => true;   // B 부분 필드만 비교한다고 가정
}

public class D : B, IEquatable<D>
{
    public override bool Equals (object right)
    {
        if (object.ReferenceEquals (right, null)) return false;
        if (object.ReferenceEquals (this, right)) return true;

        // 여기도 문제다
        D rightAsD = right as D;
        if (rightAsD == null) return false;
        if (base.Equals (rightAsD) == false) return false;
        return this.Equals (rightAsD);
    }

    public bool Equals (D other) => true;   // D 부분 필드까지 비교한다고 가정
}
```

이제 두 방향으로 비교한다.

```csharp
B baseObject    = new B();
D derivedObject = new D();

Console.WriteLine (baseObject.Equals (derivedObject));   // True
Console.WriteLine (derivedObject.Equals (baseObject));   // False
```

**어떤 상황에서든 같은 답이 두 번 나와야 하는데 그렇지 않다.**

- `derivedObject.Equals(baseObject)`는 **절대 `true`가 될 수 없다.** `B` 타입 객체는 `D`로 변환되지 않으므로 `right as D`가 `null`이다.
- `baseObject.Equals(derivedObject)`는 **`true`가 될 수 있다.** `D` 객체는 `B`로 암시적 변환되므로, 우변의 `B` 멤버들이 좌변의 `B` 멤버들과 일치하면 `B.Equals`는 두 객체를 같다고 본다.

두 객체는 타입이 다른데도 메서드가 같다고 판정했다. **대칭성이 깨졌다.** 원인은 상속 계층을 오르내리며 일어나는 자동 변환이다.

원인을 한 줄로 줄이면 이렇다. **`D`는 `B`로 암시적 상향 변환되지만 `B`는 `D`로 하향 변환되지 않는다.** 변환 가능성이 방향에 따라 다르므로, 변환 가능성을 타입 검사로 쓰는 한 비대칭은 필연이다.

**해법은 `as` 대신 `GetType()`을 정확히 비교하는 것이다.**

```csharp
public class Foo : IEquatable<Foo>
{
    public override bool Equals (object right)
    {
        // ① null 검사. C# 메서드 안에서 this는 결코 null이 아니다
        if (object.ReferenceEquals (right, null))
            return false;

        // ② 정체성 검사 — 매우 효율적인 지름길이다
        if (object.ReferenceEquals (this, right))
            return true;

        // ③ 정확한 타입 검사 — 여기가 대칭성을 지킨다
        if (this.GetType() != right.GetType())
            return false;

        // ④ 타입 안전한 비교로 위임
        return this.Equals (right as Foo);
    }

    public bool Equals (Foo other)
    {
        // 실제 필드 비교
        return true;
    }
}
```

③의 형태가 중요하다. **첫째, `this`가 `Foo` 타입이라고 가정하지 않고 `this.GetType()`을 호출한다.** 실제 타입은 `Foo`에서 파생된 클래스일 수 있다. **둘째, 우변을 현재 타입으로 변환할 수 있는지가 아니라 두 객체의 정확한 타입을 검사한다.** 이 두 가지를 지키지 않으면 앞의 미묘한 버그 두 개가 살아난다.

| 타입 검사 방식 | 대칭성 | 상속 계층 | 프록시·동적 타입 |
|---|---|---|---|
| `right is Foo` / `right as Foo` | **깨짐** | 파생 객체가 기반 객체와 같다고 나옴 | 통과함 |
| `this.GetType() != right.GetType()` | 지켜짐 | 파생은 기반과 절대 같지 않음 | **실패함** |
| 레코드의 `EqualityContract` | 지켜짐 | 파생은 기반과 절대 같지 않음 | 실패함(19.7절) |
| `sealed` 클래스 + `is` | 지켜짐(파생이 없음) | 해당 없음 | 해당 없음 |

> **⚠️ `GetType()` 비교는 ORM 프록시를 깨뜨린다**
>
> Entity Framework 같은 ORM은 지연 로딩을 위해 엔터티 클래스를 상속한 **동적 프록시 타입**을 만들어 반환한다. `Customer`를 요청했는데 실제로는 `Customer_A1B2C3` 같은 파생 타입이 온다. 이때 `GetType()` 비교를 쓰면 **같은 행에서 온 두 인스턴스가 서로 다르다고 판정된다.**
>
> 이 상황에서 흔한 처방은 도메인 엔터티의 동등성을 `GetType()`이 아니라 **식별자(ID) 기준**으로 정의하는 것이다. ID가 같으면 같다고 보고, 타입 검사는 `is`로 느슨하게 한다. 이때 대칭성을 지키려면 **`Equals`를 `sealed`로 봉인해** 파생 타입이 정의를 바꾸지 못하게 막아야 한다.
>
> ```csharp
> public abstract class Entity
> {
>     public Guid Id { get; protected set; }
>     public sealed override bool Equals (object obj)
>         => obj is Entity e && Id != Guid.Empty && Id == e.Id;
>     public sealed override int GetHashCode() => Id.GetHashCode();
> }
> ```
>
> `sealed`가 핵심이다. 이것이 없으면 파생 타입이 다른 규칙을 도입해 대칭성을 다시 깨뜨릴 수 있다.

> **💡 가장 확실한 처방은 `sealed` 클래스다**
>
> 상속 계층에서 동등성을 올바르게 유지하는 문제는 근본적으로 어렵다. `GetType()`을 쓰면 리스코프 치환 원칙과 충돌하고, `is`를 쓰면 대칭성이 깨진다. 어느 쪽도 완전한 답이 아니다.
>
> **값 의미론을 갖는 타입은 `sealed`로 만들거나 `record`로 선언하라.** `sealed`면 파생 타입이 없으므로 문제 자체가 사라진다. `record`면 컴파일러가 `EqualityContract`로 정확한 타입 검사를 자동 삽입한다(19.7절). "값처럼 행동하는 타입을 상속하는" 설계가 애초에 드물다는 사실도 참고할 만하다.

### `base.Equals`를 언제 부르는가

파생 타입의 `Equals`에서 기반 타입 `Equals`를 부르는 규칙은 하나다. **기반 버전이 `System.Object`나 `System.ValueType`이 제공하는 것이 아닐 때만 호출하라.**

앞 예에서 클래스 `D`는 기반 클래스 `B`에 정의된 `Equals`를 호출한다. 그러나 클래스 `B`는 `base.Equals`를 부르지 않는다. 그것은 `System.Object`에 정의된 버전이고, 두 인수가 같은 객체를 가리킬 때만 `true`를 반환한다. **애초에 그걸 원했다면 자기 메서드를 쓰지 않았을 것이다.**

```csharp
public class B { public override bool Equals (object o) { /* base.Equals 호출 금지 */ } }
public class D : B { public override bool Equals (object o) { /* base.Equals 호출 필요 */ } }
```

값 타입에서도 같다. 구조체의 `Equals` 재정의 안에서 `base.Equals`를 부르면 리플렉션 기반 `ValueType.Equals`로 되돌아가므로 재정의한 의미가 없어진다(16.7절).

### 계명 ③ 추이성 — 허용 오차 비교의 함정

`a == b`이고 `b == c`면 `a == c`여야 한다. 이 계약을 가장 흔하게 깨는 코드가 **허용 오차 비교**다.

```csharp
public readonly struct Measure : IEquatable<Measure>
{
    public readonly double Value;
    public Measure (double v) => Value = v;

    // 계약 위반: 추이적이지 않다
    public bool Equals (Measure other) => Math.Abs (Value - other.Value) < 0.5;
    public override bool Equals (object o) => o is Measure m && Equals (m);
    public override int GetHashCode() => 0;   // 이것도 곧 문제가 된다
}
```

```csharp
var a = new Measure (1.0);
var b = new Measure (1.4);
var c = new Measure (1.8);

Console.WriteLine (a.Equals (b));    // True  (차이 0.4)
Console.WriteLine (b.Equals (c));    // True  (차이 0.4)
Console.WriteLine (a.Equals (c));    // False (차이 0.8)  ← 추이성 위반
```

이 타입을 `Distinct`에 넣으면 **입력 순서에 따라 결과가 달라진다.**

```csharp
var v1 = new[] { a, b, c }.Distinct().Count();   // a,b는 같음 → a, c  → 2
var v2 = new[] { c, b, a }.Distinct().Count();   // c,b는 같음 → c, a  → 2
var v3 = new[] { a, c, b }.Distinct().Count();   // a,c 다름 → a, c, 그리고 b는 a와 같음 → 2
```

숫자를 조금만 바꾸면 같은 집합에서 2가 나왔다 3이 나왔다 한다. **버그 리포트가 "가끔 결과가 다릅니다"로 들어오고 재현이 안 되는 전형적인 형태다.**

> **⚠️ 허용 오차는 동등성이 아니라 별도 메서드로 표현하라**
>
> 근사 비교가 필요한 것 자체는 정당한 요구다. 그러나 그것은 **동치 관계가 아니므로 `Equals`가 될 수 없다.** 이름을 따로 주고 분리하라.
>
> ```csharp
> public bool IsCloseTo (Measure other, double tolerance)
>     => Math.Abs (Value - other.Value) <= tolerance;
> ```
>
> `Equals`는 정확 비교로 두고, 근사가 필요한 자리에서만 명시적으로 `IsCloseTo`를 부른다. 정말로 근사 기준으로 그룹핑해야 한다면 **값을 양자화**해서(예: `Math.Round(v, 1)`) 그 결과를 키로 쓰는 것이 올바른 접근이다. 양자화는 동치 관계를 만든다.

### 계명 ④ 일관성 — 예외를 던지지 마라

`Equals`는 절대 예외를 던지면 안 된다. **두 참조는 같거나 같지 않을 뿐이고, 다른 실패의 여지가 별로 없다.** `null` 참조나 잘못된 인수 타입 같은 모든 실패 조건에 대해 그냥 `false`를 반환하라.

```csharp
// 계약 위반
public override bool Equals (object obj)
{
    if (obj is not Money m)
        throw new ArgumentException ("Money가 아닙니다");   // 하면 안 된다
    return Amount == m.Amount && Currency == m.Currency;
}
```

무엇이 문제인가. `List<Money>.Contains`는 리스트를 순회하며 각 원소에 `Equals`를 부른다. 다른 타입이 섞인 `ArrayList`나 `List<object>`에서 이 코드를 부르면 **비교 도중 예외로 중단된다.** 딕셔너리 조회 중에 예외가 나면 컬렉션 내부 상태가 불완전한 채로 남을 수도 있다.

```csharp
var list = new List<object> { "hello", new Money (5, "USD") };
Console.WriteLine (list.Contains (new Money (5, "USD")));
// 첫 원소 "hello"와 비교하는 순간 ArgumentException
```

일관성의 나머지 절반은 **값이 변하지 않는 한 결과가 반복되어야 한다**는 것이다. 시간·난수·정적 상태·데이터베이스 조회에 의존하는 `Equals`는 이 계약을 깬다.

```csharp
// 계약 위반: 호출 시점에 따라 답이 달라진다
public override bool Equals (object o)
    => o is Session s && s.ExpiresAt > DateTime.UtcNow == ExpiresAt > DateTime.UtcNow;
```

### 계명 ⑤ `null` 처리 — 객체는 `null`과 같을 수 없다

**객체는 `null`과 같을 수 없다** — 널 허용 타입이 아닌 한. 그리고 `Equals`의 `this`는 C# 메서드 안에서 결코 `null`이 아니다. CLR이 `null` 참조를 통한 인스턴스 메서드 호출 전에 예외를 던지기 때문이다. 따라서 `Equals` 본문에서 `this`의 `null` 검사는 불필요하고, 인수의 `null` 검사만 하면 된다.

```csharp
public override bool Equals (object right)
{
    if (right is null) return false;      // 인수만 검사한다
    // this is null 검사는 불필요하다
    // ...
}
```

널 허용 값 타입은 예외다. `Nullable<T>`는 값이 없는 상태를 표현하므로 `((int?)null).Equals(null)`은 `true`다.

```csharp
int? a = null;
Console.WriteLine (a.Equals (null));                // True
Console.WriteLine (a == null);                      // True
Console.WriteLine (object.Equals (null, null));     // True
```

> **📌 `is null`과 `== null`과 `ReferenceEquals(x, null)`**
>
> `Equals` 구현 안에서 `null`을 검사하는 세 방법의 차이는 실전에서 중요하다.
>
> | 표현 | 사용자 `==` 오버로드를 부르는가 | 안전성 |
> |---|---|---|
> | `x == null` | **부른다** — 무한 재귀 위험 | 위험 |
> | `x is null` | 부르지 않는다(패턴 매칭) | 안전 |
> | `object.ReferenceEquals(x, null)` | 부르지 않는다 | 안전 |
>
> `==` 오버로드 본문 안에서 `if (p1 == null)`이라고 쓰면 **자기 자신을 다시 호출해 `StackOverflowException`으로 죽는다.** 반드시 `is null`이나 `ReferenceEquals`를 쓴다. 이것은 22.3절에서도 강조한 함정이다.

### 표준 구현 템플릿

다섯 계명을 전부 지키는 클래스의 정석은 이렇다.

```csharp
public sealed class Money : IEquatable<Money>
{
    public decimal Amount { get; }
    public string Currency { get; }

    public Money (decimal amount, string currency)
        => (Amount, Currency) = (amount, currency ?? throw new ArgumentNullException (nameof (currency)));

    // ① 타입 안전한 판정 — 진짜 논리는 여기 한 곳에만 있다
    public bool Equals (Money other)
    {
        if (other is null) return false;
        if (ReferenceEquals (this, other)) return true;
        return Amount == other.Amount
            && string.Equals (Currency, other.Currency, StringComparison.Ordinal);
    }

    // ② object 오버로드 — ①로 위임
    public override bool Equals (object obj) => Equals (obj as Money);

    // ③ 해시 — ①이 쓰는 필드와 정확히 같은 필드로 계산
    public override int GetHashCode() => HashCode.Combine (Amount, Currency);

    // ④ 연산자 — null 안전하게 ①로 위임
    public static bool operator == (Money a, Money b) => Equals (a, b);   // 정적 object.Equals
    public static bool operator != (Money a, Money b) => !(a == b);
}
```

`sealed`이므로 `GetType()` 검사 대신 `obj as Money`로 충분하다. **파생 타입이 존재할 수 없으므로 대칭성 문제가 원천 차단된다.** ④에서 정적 `object.Equals(a, b)`를 부르는 것이 요령이다. `null` 처리를 프레임워크가 대신해 준다.

봉인하지 않는다면 ②를 다음으로 바꾼다.

```csharp
public override bool Equals (object obj)
{
    if (obj is null) return false;
    if (ReferenceEquals (this, obj)) return true;
    if (GetType() != obj.GetType()) return false;
    return Equals ((Money) obj);
}
```

### 재정의 절차 요약

클래스나 구조체에서 동등성을 재정의하는 단계는 셋이다. ① `GetHashCode()`와 `Equals()`를 **함께** 재정의한다. ② (선택) `!=`와 `==`를 오버로딩한다. ③ (선택) `IEquatable<T>`를 구현한다. 레코드는 더 간단하다 — 컴파일러가 이미 자기 패턴에 맞춰 재정의해 놓았고, 개입하려면 그 패턴을 따라야 한다(25.5절).

## 25.4 `GetHashCode`의 함정 — 계약, 분포, `HashCode.Combine`

### 왜 `Object`에 있는가

`System.Object`처럼 멤버가 적은 타입이 이렇게 특수하고 좁은 목적의 메서드를 정의하고 있는 것은 이상해 보인다. `GetHashCode`는 사실상 딱 두 타입을 위해 존재한다.

- `System.Collections.Hashtable`
- `System.Collections.Generic.Dictionary<TKey,TValue>`

이들은 **해시테이블**이다. 각 원소가 저장·조회용 키를 갖는 컬렉션이며, 키를 기반으로 원소를 효율적으로 배치하는 아주 구체적인 전략을 쓴다. 이 전략은 각 키가 `Int32` 값, 즉 **해시 코드**를 갖기를 요구한다. 해시 코드가 키마다 유일할 필요는 없지만, 해시테이블 성능을 위해 **가능한 한 다양해야** 한다. 해시테이블이 충분히 중요하다고 판단되었기에 `GetHashCode`가 `System.Object`에 정의되어 모든 타입이 해시 코드를 낼 수 있게 되었다.

> **📌 이 설계는 오늘날까지 논란거리다**
>
> 대부분의 타입은 해시테이블의 키로 쓰이지 않는다. 그럼에도 모든 타입이 `GetHashCode`를 상속하고, `Equals`를 재정의할 때마다 함께 재정의해야 하는 부담을 진다. 원천 도서는 "이 메서드는 인터페이스에 정의되었어야 했다"고 평한다. 오늘날이라면 `IEquatable<T>`가 `GetHashCode`를 함께 요구하는 형태가 되었을 것이다.
>
> 실제로 `IEqualityComparer<T>`는 그렇게 설계되어 있다. `Equals`와 `GetHashCode`를 한 인터페이스에 묶었다(25.7절). 나중에 나온 설계가 더 나은 이유다.

### 세 가지 규칙

`GetHashCode`의 모든 오버로드는 다음 세 규칙을 따라야 한다.

| # | 규칙 | 어기면 |
|---|---|---|
| 1 | `Equals`가 `true`인 두 객체는 **반드시 같은 해시 값**을 낸다 | 컨테이너에서 객체를 찾지 못한다 |
| 2 | 객체 `A`에 대해 `A.GetHashCode()`는 **인스턴스 불변**이다. `A`에 어떤 메서드를 호출하든 언제나 같은 값을 반환해야 한다 | 저장 후 버킷이 어긋나 영구히 유실된다 |
| 3 | 전형적인 입력 집합에 대해 모든 정수에 걸쳐 **고른 분포**를 만들어야 한다 | 딕셔너리가 연결 리스트로 퇴화한다 |

여기에 실무적 규칙 둘이 더 붙는다.

- **예외를 던지면 안 된다.**
- **`Equals`가 쓰지 않는 필드를 해시에 넣으면 규칙 1이 깨진다.** 반대로 `Equals`가 쓰는 필드를 해시에서 빼는 것은 규칙 1을 깨지 않는다(규칙 3만 나빠진다).

**역은 성립하지 않는다는 점이 핵심이다.** "`Equals`가 같으면 해시도 같다"는 요구되지만, "해시가 같으면 `Equals`도 같다"는 요구되지 않는다. 해시 충돌은 정상이고 컬렉션이 처리한다.

```text
   Equals가 true  ───(반드시)──▶  해시 코드 같음
   해시 코드 같음 ───(무관)────▶  Equals가 true일 수도, 아닐 수도
```

### 규칙 1을 깨뜨렸을 때 딕셔너리에서 벌어지는 일 — 단계별 추적

`Dictionary<K,V>`의 내부 구조는 24.7절에서 다뤘다. 여기서는 계약 위반이 그 구조를 어떻게 통과하는지를 따라간다. 다음은 `Equals`만 재정의하고 `GetHashCode`를 잊은 클래스다.

```csharp
public class Sku
{
    public string Code { get; }
    public Sku (string code) => Code = code;

    public override bool Equals (object obj)
        => obj is Sku s && s.Code == Code;

    // GetHashCode를 재정의하지 않았다 → Object.GetHashCode (객체마다 다른 값)
}
```

```csharp
var d = new Dictionary<Sku, int>();
d[new Sku ("A-100")] = 5;
Console.WriteLine (d.ContainsKey (new Sku ("A-100")));   // False
```

무슨 일이 일어났는지 단계별로 본다. 버킷이 8개인 딕셔너리를 가정한다.

```text
[1] d[new Sku("A-100")] = 5;
    ├─ key.GetHashCode()  → Object의 기본 구현 → 예: 58225482
    ├─ 58225482 % 8       → 버킷 2
    └─ 버킷 2의 체인에 엔트리 저장

     buckets                    entries
    ┌───────┐            ┌──────────────────────────────┐
    │ 0  ∅  │            │ hash=58225482                │
    │ 1  ∅  │            │ key = Sku#1 ("A-100")        │
    │ 2  ●──┼───────────▶│ value = 5                    │
    │ 3  ∅  │            │ next = -1                    │
    │ ...   │            └──────────────────────────────┘
    └───────┘

[2] d.ContainsKey(new Sku("A-100"));
    ├─ key.GetHashCode()  → 다른 객체이므로 다른 값 → 예: 22458713
    ├─ 22458713 % 8       → 버킷 1
    ├─ 버킷 1은 비어 있다
    └─ Equals를 단 한 번도 호출하지 않고 False 반환   (1)
```

**핵심은 (1) 지점이다.** `Equals`는 값 동등성을 정확히 판정하도록 잘 작성되어 있다. 그런데 **호출조차 되지 않는다.** 딕셔너리는 해시 코드로 버킷을 고르고, 그 버킷 안에서만 `Equals`로 순차 탐색한다. 버킷을 틀리면 `Equals`가 아무리 정확해도 소용없다.

컴파일러는 이 실수를 경고로 알려 준다.

```text
warning CS0659: 'Sku' overrides Object.Equals(object o) but does not override Object.GetHashCode()
```

> **⚠️ CS0659는 경고이지 오류가 아니다**
>
> 경고이므로 빌드는 성공한다. 그리고 이 버그는 **단위 테스트에서 잡히지 않는 경우가 많다.** `Assert.AreEqual(sku1, sku2)`는 `Equals`를 부르므로 통과하고, 딕셔너리에 넣는 코드 경로만 조용히 실패하기 때문이다.
>
> 처방은 두 가지다. 프로젝트 파일에 `<TreatWarningsAsErrors>true</TreatWarningsAsErrors>`를 넣거나, 최소한 `<WarningsAsErrors>CS0659;CS0660;CS0661</WarningsAsErrors>`로 이 세 개만 오류로 승격하라. 관련 경고 세 개는 다음과 같다.
>
> | 경고 | 의미 |
> |---|---|
> | CS0659 | `Equals`는 재정의했는데 `GetHashCode`를 재정의하지 않음 |
> | CS0660 | `==`/`!=`는 정의했는데 `Equals`를 재정의하지 않음 |
> | CS0661 | `==`/`!=`는 정의했는데 `GetHashCode`를 재정의하지 않음 |

반대 방향의 위반 — **`Equals`가 다르다고 하는 두 객체가 같은 해시를 갖는 것** — 은 계약 위반이 아니다. 성능만 나빠진다.

```csharp
public override int GetHashCode() => 0;   // 합법. 그러나 O(N) 딕셔너리가 된다
```

모든 키가 버킷 하나에 몰리므로 조회가 선형 탐색이 된다. 예외도 경고도 없다. **데이터가 늘수록 조용히 느려질 뿐이다**(24.7절).

### 기본 구현을 세 규칙에 비추어 보면

`Object.GetHashCode`부터 본다. 이 구현은 런타임이 인스턴스마다 부여하는 **내부 객체 토큰**(정체성)에서 값을 만들며, 그 값은 참조 기준 음수 오프셋에 있는 **객체 헤더(싱크 블록 인덱스)** 에 캐시될 수 있다. 참조가 정확히 가리키는 오프셋 0의 **메서드 테이블 포인터**(타입 객체 포인터)와는 별개의 자리다 — 둘을 뭉뚱그리면 안 된다(15.6절, 54.2절).

| 규칙 | `Object.GetHashCode` |
|---|---|
| 1 | **지켜진다** — `Object`의 `Equals`는 정체성을 검사하고, 해시는 정체성 필드에서 나온다 |
| 2 | **지켜진다** — 객체가 만들어진 뒤 해시 코드는 절대 변하지 않는다 |
| 3 | 그런대로 지켜진다 — 파생 타입을 전혀 모르는 상태에서 할 수 있는 최선을 한다 |

**단, 여러분이 직접 `Equals`를 제공했다면 규칙 1이 즉시 깨진다.** 그래서 `GetHashCode`도 함께 제공해야 한다.

이제 `ValueType.GetHashCode`를 같은 잣대로 본다. 이쪽이 훨씬 위험하다.

> **⚠️ `ValueType.GetHashCode`의 구현은 런타임 세부이고 신뢰할 수 없다**
>
> 정확히 어느 필드를 어떻게 섞는지는 **문서화되지 않은 런타임 구현 세부이며 버전에 따라 달라진다**(15.6절). 어떤 코드도 그 동작에 의존해서는 안 된다.
>
> 그럼에도 원천 도서가 지적하는 함정을 알아 둘 가치는 있다. 오랫동안 — 그리고 현재 CoreCLR의 폴백 경로에서도 — 이 구현은 **해시를 낼 수 있는 첫 번째 필드**의 해시 코드를 돌려주는 형태였다. 그 전제 위에서 세 규칙을 점검하면 이렇게 된다.

```csharp
public struct MyStruct
{
    private string msg;
    private int id;
    private DateTime epoch;
}
```

첫 필드 기준 구현이라면 `MyStruct` 객체의 해시 코드는 `msg` 필드가 생성한 해시 코드다. `msg`가 `null`이 아니라고 가정할 때 다음 코드는 언제나 `true`를 반환한다.

```csharp
MyStruct s = new MyStruct();
s.SetMessage ("Hello");
return s.GetHashCode() == s.GetMessage().GetHashCode();
```

| 규칙 | 첫 필드 기준 `ValueType.GetHashCode` |
|---|---|
| 1 | 대체로 지켜진다. `Equals`가 첫 필드를 포함한 모든 필드를 비교하기 때문이다. **첫 필드가 동등성에 참여하지 않는 구조체를 만들면 깨진다** |
| 2 | **첫 필드가 불변일 때만 지켜진다.** 첫 필드가 변하면 해시도 변한다 |
| 3 | 첫 필드의 분포에 전적으로 의존한다 |

규칙 3의 취약함은 필드 순서만 바꿔도 드러난다.

```csharp
public struct MyStruct
{
    private DateTime epoch;   // 순서만 바꿨다
    private string msg;
    private int id;
}
```

`epoch`가 (시각을 뺀) 현재 날짜로 설정된다면 **같은 날 만들어진 모든 `MyStruct` 객체가 같은 해시 코드를 갖는다.** 고른 분포가 불가능해진다. 필드 선언 순서를 바꾼 것만으로 딕셔너리 성능이 O(1)에서 O(N)이 됐다.

정리하면 이렇다.

- `Object.GetHashCode`는 참조 타입에 대해 **올바르게** 동작한다. 다만 효율적인 분포를 보장하지는 않는다. (`Equals`나 `==`를 재정의했다면 깨질 수 있다.)
- `ValueType.GetHashCode`는 **구조체의 첫 필드가 읽기 전용일 때만 올바르다.** 그리고 첫 필드가 의미 있는 값 범위에 걸쳐 분포할 때만 효율적이다.

**결론은 16.7절과 같다. 값 타입을 만들면 `Equals`와 `GetHashCode`를 언제나 직접 재정의하라.**

### `HashCode.Combine` ※.NET Standard 2.1

여러 필드를 하나의 해시로 합치는 표준 방법이 `System.HashCode`다.

```csharp
public override int GetHashCode() => HashCode.Combine (Measure1, Measure2);
```

`HashCode.Combine`은 최대 8개의 값을 받는 정적 제네릭 오버로드 집합이다. 각 인수에 대해 `EqualityComparer<T>.Default.GetHashCode`를 호출한 뒤 그 결과들을 섞는다.

필드가 8개를 넘거나 컬렉션의 요소를 모두 섞어야 하면 인스턴스 API를 쓴다.

```csharp
public override int GetHashCode()
{
    var hc = new HashCode();
    hc.Add (Name);
    hc.Add (Birthday);
    foreach (var tag in Tags) hc.Add (tag);     // 요소 수에 비례하는 비용에 주의
    return hc.ToHashCode();
}
```

비교자를 지정하는 오버로드도 있다.

```csharp
hc.Add (Name, StringComparer.OrdinalIgnoreCase);   // Equals도 같은 규칙을 써야 한다
```

> **⚠️ `HashCode`는 .NET Framework에 없다**
>
> `System.HashCode`는 .NET Core 2.1에서 도입되었고 **.NET Standard 2.1**에 포함된다. **.NET Framework에는 없다.** .NET Standard 2.0이나 .NET Framework를 대상으로 하는 라이브러리에서는 `Microsoft.Bcl.HashCode` NuGet 패키지를 참조하거나 직접 조합해야 한다.
>
> `HashCode`가 없던 시절의 관용적 접근은 **각 값에 소수를 곱한 뒤 더하는 것**이었다.
>
> ```csharp
> public override int GetHashCode()
> {
>     unchecked                       // 오버플로를 허용해야 한다
>     {
>         int hash = 17;
>         hash = hash * 31 + (Name?.GetHashCode() ?? 0);
>         hash = hash * 31 + Age.GetHashCode();
>         return hash;
>     }
> }
> ```
>
> `unchecked`가 필요한 이유는 프로젝트가 `CheckForOverflowUnderflow`를 켰을 때 곱셈 오버플로가 `OverflowException`을 내기 때문이다. `GetHashCode`는 예외를 던지면 안 되므로 반드시 감싸야 한다(7.9절).

원천 도서가 언급하는 더 오래된 관용구는 **모든 필드의 `GetHashCode` 반환값을 XOR하는 것**이다.

```csharp
public override int GetHashCode() => m_x ^ m_y;
```

이 알고리즘은 **타입의 필드 사이에 상관관계가 없을 때만 성공한다.** 상관관계가 있으면 해시 코드가 뭉쳐서, 컨테이너의 버킷 수가 적어지고 각 버킷에 많은 항목이 들어간다. `m_x`와 `m_y`가 항상 같은 좌표라면 `x ^ y`는 언제나 0이다.

### 분포에 대한 감각 — .NET 자체의 두 예

원천 도서가 드는 대비가 명료하다.

| 타입 | `GetHashCode` 동작 | 분포 |
|---|---|---|
| `int` | **자기 자신을 반환한다** | 전혀 무작위가 아니다. 뭉친다 |
| `DateTime` | 64비트 내부 틱 필드의 **상위 32비트와 하위 32비트를 XOR**한다 | 덜 뭉친다 |

이 사실을 조합해 학생 클래스의 해시 함수를 생각해 보자. 이름과 생년월일이 필드다. **`DateTime`의 `GetHashCode` 구현을 그대로 쓰면, 연·월·일에서 직접 해시를 계산하는 것보다 훨씬 나은 결과가 나온다.** 학생의 경우 연도 성분이 가장 흔한 나이 주변으로 뭉칠 것이기 때문이다. **자기 데이터 집합에 대한 지식이 제대로 된 `GetHashCode` 메서드를 만드는 데 결정적이다.**

> **💡 필드가 하나면 그 필드의 해시를 그대로 쓰면 된다**
>
> ```csharp
> public override int GetHashCode() => _semitonesFromA.GetHashCode();
> ```
>
> 단일 필드 타입에서 `HashCode.Combine`으로 한 번 더 섞는 것은 대개 불필요하다. 다만 **그 필드가 `int`이고 값이 좁은 범위에 몰려 있다면** 이야기가 다르다. `int.GetHashCode()`는 자기 자신을 돌려주므로, 0~100 범위의 ID를 키로 쓰면 해시 값도 0~100에 몰린다. 딕셔너리의 모듈로 연산이 이를 어느 정도 흡수하지만, 버킷 수와 값 범위가 나쁘게 맞물리면 충돌이 급증한다. 이럴 때는 `HashCode.Combine(_id)`로 섞는 편이 낫다.

### 해시 코드 랜덤화

문자열 해시에는 한 겹의 복잡성이 더 있다.

**.NET Core / .NET 5 이후 `string.GetHashCode()`는 프로세스마다 다른 무작위 시드를 사용한다.** 같은 문자열이라도 프로그램을 다시 실행하면 다른 해시 코드가 나온다.

```csharp
Console.WriteLine ("hello".GetHashCode());
// 실행할 때마다 다른 값이 나온다
```

목적은 **해시 DoS 공격 방어**다. 공격자가 서로 충돌하는 키(HTTP 헤더 이름, JSON 프로퍼티 이름, 폼 필드 이름)를 대량으로 보내 서버의 딕셔너리를 O(N²)로 만드는 공격이 실재한다. 시드가 프로세스마다 다르면 공격자가 충돌 집합을 미리 계산할 수 없다.

여기에 더해 `Dictionary<string,V>`는 **기본 문자열 비교자에 대해 비무작위 서수 해시라는 빠른 경로**로 시작하고, 한 버킷의 체인이 지나치게 길어지면 무작위화 해시로 전환하며 전체를 재해싱한다(24.7절). 이 둘은 다른 층위의 방어이며 서로 모순되지 않는다.

> **⚠️ 해시 코드를 절대 영속화하지 마라**
>
> 파일·데이터베이스·캐시 키·네트워크 프로토콜 어디에도 `GetHashCode()` 결과를 저장해서는 안 된다. **문자열 해시는 프로세스마다 다르고, `HashCode.Combine`의 결과도 프로세스마다 다르다.** 프로세스를 재시작하는 순간 저장된 값과 새로 계산한 값이 어긋난다.
>
> 게다가 타입의 다음 버전이 다른 알고리즘을 쓸 수도 있다. 15.6절의 사례 — 비밀번호 해시로 `GetHashCode`를 쓰다가 런타임 업그레이드 후 아무도 로그인할 수 없게 된 회사 — 가 정확히 이 함정이다.
>
> 영속적으로 안정된 해시가 필요하면 **자기가 직접 정의한 해시 함수**(예: FNV-1a)를 쓰거나 암호학적 해시(44.3절)를 써라. `GetHashCode`는 **한 프로세스 안에서 버킷을 고르는 용도 전용**이다.

> **📌 `.NET Framework`의 문자열 해시 랜덤화** *(.NET Framework 전용)*
>
> .NET Framework에서는 문자열 해시 랜덤화가 기본으로 켜져 있지 않았고, `app.config`의 `UseRandomizedStringHashAlgorithm` 스위치로 제어했다. 그래서 .NET Framework에서는 같은 문자열이 프로세스를 넘어 같은 해시를 내는 경우가 많았고, **그 동작에 의존한 코드가 .NET Core로 이식되면서 깨지는 사고**가 흔했다. 이식 작업에서 `GetHashCode` 호출부를 전수 점검할 가치가 있는 이유다.

## 25.5 사용자 정의 타입의 동등성 — 클래스 / 구조체 / 레코드

### 언제 재정의하는가

기본 동등성 동작을 다시 정리한다. 값 타입은 값 동등성, 참조 타입은 참조 동등성(익명 타입과 레코드는 예외), 그리고 구조체의 `Equals`는 기본적으로 구조적 값 동등성을 적용한다.

타입을 작성하면서 이 동작을 재정의하는 것이 합당한 경우가 **둘** 있다.

1. **동등성의 의미를 바꾸기 위해**
2. **구조체의 동등성 비교 속도를 높이기 위해**

여기에 원천 도서가 "다소 특이한 경우"라고 부르는 셋째 이유가 붙는다. **해시테이블 성능을 위해 구조체의 해싱 알고리즘을 개선하는 것**이다. 동등성 비교와 해싱이 한 몸이기 때문에 생기는 결과다(25.4절).

| 상황 | `Equals` 재정의 | `GetHashCode` 재정의 | `==`/`!=` 오버로딩 | `IEquatable<T>` |
|---|---|---|---|---|
| 가변 참조 타입(대부분의 클래스) | 하지 않는다 | 하지 않는다 | 하지 않는다 | 하지 않는다 |
| 불변 값 객체 클래스(`Money`, `Uri` 류) | **한다** | **한다** | 한다 | 한다 |
| 참조 타입이지만 `==`는 참조로 남기고 싶다(`StringBuilder` 류) | **한다** | **한다** | 하지 않는다 | 선택 |
| 모든 구조체 | **한다** | **한다** | **한다** | **한다** |
| 레코드 | 컴파일러가 한다 | 컴파일러가 한다 | 컴파일러가 한다 | 컴파일러가 한다 |
| 도메인 엔터티(ID 동등성) | 한다(`sealed`로) | 한다(`sealed`로) | 선택 | 선택 |

### 동등성의 의미를 바꾸는 경우

기본 `==`·`Equals` 동작이 타입에 부자연스럽고 소비자의 기대와 다를 때 의미를 바꾸는 것이 합당하다.

한 예가 `DateTimeOffset`이다. 이 구조체는 비공개 필드 둘 — UTC `DateTime`과 정수 오프셋 — 을 갖는다. 이 타입을 직접 작성한다면 동등성 비교가 **UTC `DateTime` 필드만 고려하고 오프셋 필드는 고려하지 않도록** 만들고 싶을 것이다. 또 다른 예는 `float`·`double`처럼 NaN 값을 지원하는 숫자 타입이다. 그런 타입을 직접 구현한다면 **NaN 비교 논리가 동등성 비교에서 지원되도록** 보장하고 싶을 것이다.

클래스에서는 참조 동등성 대신 **값 동등성을 기본으로 제공하는 것이 더 자연스러운** 경우가 있다. `System.Uri`나 `System.String`처럼 단순한 데이터 한 조각을 담는 작은 클래스가 대개 그렇다.

레코드에서는 컴파일러가 각 필드를 비교하는 구조적 동등성을 자동 구현한다. 그러나 때로는 **비교하고 싶지 않은 필드**가 포함되거나, 컬렉션처럼 **특별한 비교 논리가 필요한 객체**가 포함된다.

### 구조체의 동등성 비교 속도를 높이는 경우

구조체의 기본 구조적 동등성 비교 알고리즘은 상대적으로 느리다. **`Equals`를 재정의해 이 과정을 넘겨받으면 성능이 다섯 배 개선될 수 있다. `==` 연산자를 오버로딩하고 `IEquatable<T>`를 구현하면 박싱 없는 동등성 비교가 가능해져 다시 다섯 배가량 빨라질 수 있다.** (원천 도서가 제시하는 수치다.)

왜 그렇게 느린지 — 리플렉션, 박싱, 필드마다 다시 일어나는 가상 호출 — 는 16.7절에서 IL까지 짚었다. 여기서 강조할 것은 **참조 타입에서는 이 이유가 성립하지 않는다**는 점이다. 참조 동등성의 기본 알고리즘은 32비트나 64비트 참조 둘을 비교할 뿐이라 이미 매우 빠르다. **참조 타입의 동등성 의미론을 재정의해도 성능상 이득은 없다.**

### 예제 — `Area` 구조체

너비와 높이가 서로 바꿔도 되는 넓이를 표현하는 구조체를 생각한다. 즉 5 × 10은 10 × 5와 같다. (직사각형 도형을 배치하는 알고리즘에 어울리는 타입이다.)

```csharp
public struct Area : IEquatable<Area>
{
    public readonly int Measure1;
    public readonly int Measure2;

    public Area (int m1, int m2)
    {
        Measure1 = Math.Min (m1, m2);
        Measure2 = Math.Max (m1, m2);
    }

    public override bool Equals (object other)
        => other is Area a && Equals (a);                       // 아래 메서드를 호출한다

    public bool Equals (Area other)                             // IEquatable<Area> 구현
        => Measure1 == other.Measure1 && Measure2 == other.Measure2;

    public override int GetHashCode()
        => HashCode.Combine (Measure1, Measure2);

    // object 클래스의 정적 Equals 메서드를 호출한다는 점에 주목하라.
    // 자기 (인스턴스) Equals 메서드를 호출하기 전에 null 검사를 해 준다.
    public static bool operator == (Area a1, Area a2) => Equals (a1, a2);
    public static bool operator != (Area a1, Area a2) => !(a1 == a2);
}
```

```csharp
Area a1 = new Area (5, 10);
Area a2 = new Area (10, 5);
Console.WriteLine (a1.Equals (a2));      // True
Console.WriteLine (a1 == a2);            // True
```

이 구현이 지키는 것들을 하나씩 확인하라.

- **생성자에서 정규화한다.** `Min`/`Max`로 필드를 정렬하므로 `(5,10)`과 `(10,5)`가 같은 내부 표현이 된다. 이렇게 하면 `Equals`가 단순 필드 비교로 끝나고, **`GetHashCode`도 자동으로 규칙 1을 만족한다.** 정규화 없이 `Equals`에서만 순서를 무시했다면 `HashCode.Combine(5,10)`과 `HashCode.Combine(10,5)`가 달라져 계약이 깨졌을 것이다.
- **필드가 `readonly`다.** 규칙 2(해시 불변성)가 구조적으로 보장된다.
- **`Equals(object)`는 `Equals(Area)`로 위임한다.** 논리가 한 곳에만 있다.
- **`==`는 정적 `object.Equals`를 부른다.** `null` 처리가 공짜다.
- **`GetHashCode`는 `Equals`가 쓰는 바로 그 두 필드를 쓴다.**

> **💡 ※C# 10 부터는 `record struct` 한 줄로 끝난다**
>
> 위 코드에서 생성자 이후의 모든 코드를 지우고 `record struct`로 선언하면 컴파일러가 같은 일을 해 준다.
>
> ```csharp
> public readonly record struct Area
> {
>     public int Measure1 { get; }
>     public int Measure2 { get; }
>     public Area (int m1, int m2)
>         => (Measure1, Measure2) = (Math.Min (m1, m2), Math.Max (m1, m2));
> }
> ```
>
> 단, **정규화 논리는 여전히 직접 써야 한다.** 컴파일러가 만들어 주는 것은 "모든 필드가 같으면 같다"까지다. "5×10과 10×5는 같다"는 도메인 규칙은 사람이 넣어야 한다.

### 클래스에서 `==`를 어떻게 할 것인가

`Equals`를 재정의하는 것에 더해, 동등·부등 연산자를 오버로딩할 수 있다. **구조체에서는 거의 언제나 오버로딩한다.** 하지 않으면 `==`와 `!=` 연산자가 그 타입에서 아예 동작하지 않기 때문이다.

클래스에서는 두 갈래가 있다.

1. `==`와 `!=`를 건드리지 않고 참조 동등성으로 남긴다.
2. `Equals`에 맞춰 `==`와 `!=`를 오버로딩한다.

**첫째 접근이 사용자 정의 타입 — 특히 가변 타입 — 에 가장 흔하다.** 참조 타입에서 `==`와 `!=`는 참조 동등성을 보여야 한다는 기대를 따르게 되고, 소비자를 혼란스럽게 하지 않는다. `StringBuilder`가 그 예다(25.1절).

**둘째 접근은 소비자가 참조 동등성을 결코 원하지 않을 타입에 합당하다.** 대개 불변 타입이며 — `string`이나 `System.Uri` 클래스처럼 — 때로는 구조체로 만드는 것이 나은 후보이기도 하다.

> **📌 `!=`를 `!(==)`가 아닌 것으로 만들 수도 있다**
>
> 가능하지만 실무에서는 거의 하지 않는다. 예외적인 사례가 SQL Server의 네이티브 열 타입을 표현하는 `System.Data.SqlTypes` 네임스페이스의 타입들이다. 이들은 데이터베이스의 널 비교 논리를 따라, **피연산자 중 하나가 널이면 `=`와 `<>`(C#의 `==`와 `!=`)가 둘 다 널을 반환한다.**
>
> 이 설계는 3값 논리를 표현하기 위한 것이지만, C#의 일반적인 기대(`a != b`는 `!(a == b)`)를 깨므로 도메인이 명확히 요구하지 않는 한 따라 하지 마라.

`IEquatable<T>` 구현은 완결성을 위해서도 좋다. **결과는 언제나 재정의된 `object`의 `Equals` 메서드와 일치해야 한다.** 앞의 `Area`처럼 `Equals` 구현을 구성하면 `IEquatable<T>` 구현에 추가 비용이 전혀 들지 않는다.

### 레코드의 동등성에 개입하기

레코드는 절차가 다르고 더 간단하다. 컴파일러가 이미 자기만의 특별한 패턴에 맞춰 동등성 메서드와 연산자를 재정의해 놓았기 때문이다. 개입하려면 그 패턴을 따라야 하고, **다음과 같은 시그니처의 `Equals` 메서드를 써야 한다.**

```csharp
record Test (int X, int Y)
{
    public virtual bool Equals (Test t) => t != null && t.X == X && t.Y == Y;
}
```

`Equals`가 `override`가 아니라 **`virtual`이고, `object`가 아니라 실제 레코드 타입(여기서는 `Test`)을 받는다**는 점에 주목하라. 컴파일러는 이 메서드가 "올바른" 시그니처를 가졌음을 인식하고 자기가 생성하는 코드에 끼워 넣는다.

`GetHashCode()`도 클래스나 구조체에서와 마찬가지로 재정의해야 한다. 그러나 **`!=`와 `==`를 오버로딩하거나 `IEquatable<T>`를 구현할 필요는 없고, 해서도 안 된다.** 이미 되어 있기 때문이다.

> **⚠️ 레코드의 `Equals`를 `override bool Equals(object)`로 쓰면 계약이 갈라진다**
>
> 레코드에서 `public override bool Equals(object obj)`를 재정의하는 것 자체는 컴파일된다. 그러나 컴파일러가 생성한 `==` 연산자와 `Equals(Test)`는 **여러분의 재정의를 거치지 않는다.** 결과적으로 `a == b`와 `a.Equals((object)b)`가 다른 답을 내는 타입이 만들어진다.
>
> 레코드에서 동등성을 손보려면 반드시 `public virtual bool Equals(<레코드타입> other)` 시그니처를 써라. 레코드 동등성의 전체 규칙 — `EqualityContract`, 상속 계층에서의 동작, `with` 식과의 관계 — 은 19.7절에 있다.

### 실무 결정 순서

1. **이 타입은 "값"인가** — 내용이 곧 정체성인가. 아니라면(엔터티·서비스·가변 상태) 아무것도 재정의하지 않는다. 기본 참조 동등성이 정답이다.
2. **작고 불변인가** — `record struct` 또는 `readonly record struct`.
3. **참조 타입이어야 하는가** — `sealed record` 또는 `sealed class`에 `Equals` + `GetHashCode` + `IEquatable<T>`(필요하면 `==`).
4. **상속이 필요한가** — 설계를 다시 본다. 꼭 필요하면 `GetType()` 정확 비교나 `sealed Equals` 중 하나를 고르고, 그 선택의 대가를 문서에 남긴다.

## 25.6 순서 비교 — `IComparable`, `IComparable<T>`, `<`와 `>`

### 두 개의 프로토콜

동등성의 표준 프로토콜을 정의한 것과 마찬가지로, C#과 .NET은 **한 객체가 다른 객체에 대해 어떤 순서에 오는지**를 결정하는 표준 프로토콜을 둘 정의한다.

- `IComparable` 인터페이스들(`IComparable`과 `IComparable<T>`)
- `>`와 `<` 연산자

`IComparable` 인터페이스들은 **범용 정렬 알고리즘**이 사용한다. 다음 예에서 정적 `Array.Sort` 메서드가 동작하는 것은 `System.String`이 `IComparable` 인터페이스들을 구현하기 때문이다.

```csharp
string[] colors = { "Green", "Red", "Blue" };
Array.Sort (colors);
foreach (string c in colors) Console.Write (c + " ");   // Blue Green Red
```

`<`와 `>` 연산자는 더 특수하며 주로 숫자 타입을 위한 것이다. **정적으로 해석되므로 매우 효율적인 바이트코드로 번역되고**, 계산 집약적 알고리즘에 적합하다.

.NET은 `IComparer` 인터페이스들을 통해 **꽂아 넣을 수 있는 순서 프로토콜**도 제공한다(25.7절, 24.13절).

### `IComparable`

두 인터페이스의 정의는 이렇다.

```csharp
public interface IComparable       { int CompareTo (object other); }
public interface IComparable<in T> { int CompareTo (T other); }
```

**두 인터페이스는 같은 기능을 표현한다.** 값 타입에서는 제네릭 타입 안전 인터페이스가 비제네릭 인터페이스보다 빠르다. 어느 쪽이든 `CompareTo` 메서드는 이렇게 동작한다.

| 관계 | `a.CompareTo(b)` 반환값 |
|---|---|
| `a`가 `b` **뒤에** 온다 | **양수** |
| `a`가 `b`와 **같은 순위**다 | **0** |
| `a`가 `b` **앞에** 온다 | **음수** |

```csharp
Console.WriteLine ("Beck".CompareTo ("Anne"));    //  1
Console.WriteLine ("Beck".CompareTo ("Beck"));    //  0
Console.WriteLine ("Beck".CompareTo ("Chris"));   // -1
```

> **⚠️ 반환값이 정확히 −1, 0, 1이라고 가정하지 마라**
>
> 계약은 **부호**만 정한다. 크기는 아무 의미가 없다. `"a".CompareTo("z")`가 `-25`를 반환하는 구현도 완전히 합법이며, 실제로 `string.CompareOrdinal`은 문자 코드 차이를 그대로 돌려주기도 한다.
>
> ```csharp
> if (a.CompareTo (b) == -1)   // 틀렸다
> if (a.CompareTo (b) <  0)    // 옳다
> ```
>
> 이 실수는 **문화권이나 런타임 버전이 바뀔 때 조용히 드러난다.** 개발 기기에서는 −1이 나오다가 서버에서 −2가 나오면 조건이 통째로 뒤집힌다. 반환값은 언제나 `< 0`, `== 0`, `> 0`으로만 검사하라.

대부분의 기본 타입이 두 `IComparable` 인터페이스를 모두 구현한다.

### `CompareTo`의 계약

`Equals`에 다섯 계명이 있듯 `CompareTo`에도 지켜야 할 것이 있다. **전 순서(total order)**를 이루어야 한다.

| # | 이름 | 형식적 진술 |
|---|---|---|
| 1 | **반사성** | `x.CompareTo(x)`는 `0` |
| 2 | **반대칭성**(antisymmetric) | `x.CompareTo(y)`의 부호와 `y.CompareTo(x)`의 부호는 **반대**다 |
| 3 | **추이성** | `x.CompareTo(y) > 0`이고 `y.CompareTo(z) > 0`이면 `x.CompareTo(z) > 0` |
| 4 | **동치의 추이성** | `x.CompareTo(y) == 0`이면 `x.CompareTo(z)`의 부호와 `y.CompareTo(z)`의 부호가 같다 |
| 5 | **`null` 규약** | `null`은 어떤 객체보다도 작다. `x.CompareTo(null)`은 양수 |
| 6 | **일관성** | 값이 변하지 않는 한 결과가 반복되고 예외를 던지지 않는다 |

5번은 관례이지만 프레임워크 전반이 이에 의존한다. `Array.Sort`로 `null`이 섞인 배열을 정렬하면 `null`들이 앞에 모이는 것이 그래서다.

### `IComparable`과 `Equals`의 관계

`Equals`를 재정의하면서 `IComparable` 인터페이스들도 구현하는 타입을 생각해 보자. `Equals`가 `true`를 반환하면 `CompareTo`는 0을 반환해야 한다고 예상할 것이고, 그것은 옳다. **그런데 함정이 있다.**

> **`Equals`가 `false`를 반환할 때, `CompareTo`는 (내부적으로 일관되기만 하다면) 원하는 무엇이든 반환할 수 있다.**

다시 말해 **동등성은 비교보다 "까다로울" 수 있지만 그 반대는 안 된다.** 이것을 어기면 정렬 알고리즘이 깨진다. `CompareTo`는 "모든 객체는 같다"고 말할 수 있는 반면, `Equals`는 "그래도 어떤 것들은 더 같다!"고 말할 수 있다.

훌륭한 예가 `System.String`이다. **`String`의 `Equals` 메서드와 `==` 연산자는 서수 비교를 사용해 각 문자의 유니코드 포인트 값을 비교한다. 그러나 `CompareTo` 메서드는 문화권 의존 비교를 사용하며, 이 비교는 때로 둘 이상의 문자를 같은 정렬 위치에 놓는다.**

```csharp
string a = "encyclopædia";
string b = "encyclopaedia";

Console.WriteLine (a == b);                     // False — 서수 비교
Console.WriteLine (a.Equals (b));               // False
Console.WriteLine (string.Compare (a, b,
    StringComparison.InvariantCulture));        // 0일 수 있다 — 문화권 비교
```

`æ`와 `ae`가 같은 정렬 위치에 놓이는 문화권에서는 `CompareTo`가 0을 반환하는데 `Equals`는 `false`다. **이것이 허용되는 방향이다.** 문자열 비교 규칙의 전모는 35.4절에 있다.

> **💡 `CompareTo`의 첫 줄에 안전장치를 넣어라**
>
> 사용자 정의 타입에서 `IComparable` 인터페이스들을 구현할 때, 이 규칙을 어기지 않으려면 `CompareTo`의 첫 줄을 이렇게 쓰면 된다.
>
> ```csharp
> if (Equals (other)) return 0;
> ```
>
> 그 뒤로는 일관되기만 하다면 무엇을 반환하든 상관없다. 이 한 줄이 "`Equals`가 `true`인데 `CompareTo`가 0이 아닌" 상황을 원천 차단한다.

25.7절에서 다루는 꽂아 넣을 수 있는 순서 프로토콜 `IComparer`는 `CompareTo`와 `Equals` 사이의 간격을 더 벌릴 수 있다. 예컨대 **대소문자 무시 문자열 비교자는 `"A"`와 `"a"`를 비교할 때 0을 반환한다.** 그래도 역방향 규칙은 여전히 적용된다. **`CompareTo`는 `Equals`보다 까다로울 수 없다.**

### `<`와 `>`

어떤 타입은 `<`와 `>` 연산자를 정의한다.

```csharp
bool after2010 = DateTime.Now > new DateTime (2010, 1, 1);
```

`<`와 `>` 연산자가 구현되어 있다면 **`IComparable` 인터페이스들과 기능적으로 일관되리라고 기대해도 된다.** 이것이 .NET 전반의 표준 관행이다.

`<`와 `>`를 오버로딩할 때마다 `IComparable` 인터페이스들을 구현하는 것도 표준 관행이다. **그러나 역은 참이 아니다.** 실제로 `IComparable`을 구현하는 .NET 타입 대부분은 `<`와 `>`를 오버로딩하지 않는다. 이는 동등성과 다른 점이다. 동등성에서는 `Equals`를 재정의할 때 `==`를 오버로딩하는 것이 정상이다.

전형적으로 `>`와 `<`는 다음 조건에서만 오버로딩한다.

1. 타입이 **"보다 크다"와 "보다 작다"라는 강한 본질적 개념**을 갖는다(`IComparable`의 더 넓은 개념인 "앞에 온다"·"뒤에 온다"와 대비된다).
2. 비교를 수행하는 **방식이나 맥락이 하나뿐**이다.
3. 결과가 **문화권에 걸쳐 불변**이다.

`System.String`은 마지막 조건을 만족하지 못한다. 문자열 비교 결과는 언어에 따라 달라질 수 있다. 따라서 `string`은 `>`와 `<` 연산자를 지원하지 않는다.

```csharp
bool error = "Beck" > "Anne";      // 컴파일 타임 오류
```

| | `IComparable<T>` | `<` / `>` 연산자 |
|---|---|---|
| 바인딩 | 런타임(인터페이스 디스패치) | 컴파일 타임(정적) |
| 프레임워크가 쓰는가 | **쓴다**(`Array.Sort`, `SortedSet`, `OrderBy`) | 쓰지 않는다 |
| 문화권 의존 허용 | 허용(`string`이 그렇게 한다) | 허용하지 않는 것이 관행 |
| 셋 중 어느 것이 먼저인가 | 이쪽을 먼저 구현한다 | 필요할 때만 추가한다 |
| `null` 처리 | `null`은 가장 작다 | 참조 타입이면 직접 처리해야 한다 |

### 구현 예 — `Note` 구조체

음표를 표현하는 다음 구조체는 `IComparable` 인터페이스들을 구현하고 `<`와 `>` 연산자도 오버로딩한다. 완결성을 위해 `Equals`/`GetHashCode`도 재정의하고 `==`와 `!=`도 오버로딩한다.

```csharp
public struct Note : IComparable<Note>, IEquatable<Note>, IComparable
{
    int _semitonesFromA;
    public int SemitonesFromA { get { return _semitonesFromA; } }

    public Note (int semitonesFromA)
    {
        _semitonesFromA = semitonesFromA;
    }

    public int CompareTo (Note other)                    // 제네릭 IComparable<T>
    {
        if (Equals (other)) return 0;                    // 안전장치
        return _semitonesFromA.CompareTo (other._semitonesFromA);
    }

    int IComparable.CompareTo (object other)             // 비제네릭 IComparable
    {
        if (!(other is Note))
            throw new InvalidOperationException ("CompareTo: Not a note");
        return CompareTo ((Note) other);
    }

    public static bool operator < (Note n1, Note n2) => n1.CompareTo (n2) < 0;
    public static bool operator > (Note n1, Note n2) => n1.CompareTo (n2) > 0;

    public bool Equals (Note other)                      // IEquatable<Note>
        => _semitonesFromA == other._semitonesFromA;

    public override bool Equals (object other)
    {
        if (!(other is Note)) return false;
        return Equals ((Note) other);
    }

    public override int GetHashCode() => _semitonesFromA.GetHashCode();

    // null이 제대로 처리되도록 정적 Equals 메서드를 호출한다
    public static bool operator == (Note n1, Note n2) => Equals (n1, n2);
    public static bool operator != (Note n1, Note n2) => !(n1 == n2);
}
```

비제네릭 `CompareTo`가 **명시적 인터페이스 구현**이라는 점에 주목하라. 이렇게 하면 예전 인터페이스를 위해 작성된 코드만 `object` 타입 버전을 부를 수 있다.

`<=`와 `>=`도 같은 형태(`n1.CompareTo (n2) <= 0`)로 함께 정의하는 것이 사용자에게 친절하다. 다만 C#은 `<`와 `>`를 짝으로, `<=`와 `>=`를 짝으로 요구할 뿐 네 개 전부를 요구하지는 않는다(22.2절).

### 비제네릭 `IComparable`의 비용

고전적 `IComparable`에는 싫어할 만한 점이 많다. **인수의 런타임 타입을 검사해야 하고, 잘못된 코드가 아무것이나 인수로 넘겨 이 메서드를 부를 수 있다.** 게다가 올바른 인수라도 실제 비교를 하려면 박싱·언박싱을 거쳐야 한다.

**비용을 계산해 보면 이렇다.** 컬렉션 정렬은 평균적으로 `n log(n)`번 객체를 비교한다. 각 비교마다 박싱·언박싱이 세 번씩 일어난다.

| 원소 수 | 평균 비교 횟수(`n log n`) | 박싱·언박싱 연산 |
|---|---|---|
| 1,000 | 약 7,000 | **20,000회 이상** |
| 10,000 | 약 92,000 | 약 276,000회 |
| 100,000 | 약 1,150,000 | 약 3,450,000회 |

(원천 도서가 제시한 1,000개 기준 수치에서 확장한 예시다.)

그렇다면 비제네릭 `IComparable`을 왜 구현하는가. 이유는 둘이다. **첫째, 단순한 하위 호환성이다.** 여러분의 타입은 제네릭 이전에 만들어진 코드와 상호작용하게 된다. 일부 기본 클래스 라이브러리 클래스(WinForms나 ASP.NET Web Forms를 생각하라)는 1.0 구현과의 하위 호환성을 요구한다. **둘째, 명시적 구현으로 감춰 두면 잘못 쓰일 위험이 없다.**

```csharp
Customer c1;
Employee e1;
if (c1.CompareTo (e1) > 0)          // 컴파일되지 않는다 — 타입이 맞지 않는다
    Console.WriteLine ("Customer one is greater");
```

공개 `Customer.CompareTo(Customer)` 메서드의 인수 타입이 맞지 않아 컴파일이 실패한다. `IComparable.CompareTo(object)` 메서드는 접근할 수 없다. **`IComparable`을 구현할 때는 명시적 인터페이스 구현을 쓰고 강타입 공개 오버로드를 제공하라.** 강타입 오버로드는 성능을 개선하고 `CompareTo`가 오용될 가능성을 낮춘다. 프레임워크의 `Sort` 함수 자체는 여전히 인터페이스 포인터를 통해 `CompareTo()`에 접근하므로 이득을 전부 보지는 못하지만, **비교되는 두 객체의 타입을 아는 코드는 더 나은 성능을 얻는다.**

> **📌 비제네릭 `CompareTo`가 던지는 예외**
>
> 위 `Note` 예제는 `InvalidOperationException`을 던지고, 원천 도서의 `Customer` 예제는 `ArgumentException`을 던진다.
>
> ```csharp
> int IComparable.CompareTo (object obj)
> {
>     if (!(obj is Customer))
>         throw new ArgumentException ("Argument is not a Customer", "obj");
>     return this.CompareTo ((Customer) obj);
> }
> ```
>
> **어느 쪽이든 계약 위반은 아니다.** 인수가 잘못된 타입이라는 것은 프로그래밍 오류이므로 예외가 정당하다. 다만 `ArgumentException` 쪽이 "인수가 잘못됐다"는 의미를 더 정확히 전달하므로 새 코드에서는 이쪽을 권한다. **`Equals`와 대비되는 점에 주의하라. `Equals`는 잘못된 타입에 `false`를 반환해야 하지만, `CompareTo`는 순서를 정의할 수 없으므로 예외를 던지는 것이 맞다.**

### 정렬의 안정성과 비일관 비교자

정렬 알고리즘의 **안정성**(stability)은 "순위가 같은 원소들의 원래 상대 순서가 보존되는가"를 뜻한다.

| API | 알고리즘 | 안정성 |
|---|---|---|
| `Array.Sort` / `List<T>.Sort` | 인트로소트(퀵소트 + 힙소트 + 삽입 정렬) | **불안정** |
| `Enumerable.OrderBy` / `ThenBy` (LINQ) | 키 추출 + 인덱스 타이브레이크 | **안정** |
| `SortedList` / `SortedDictionary` / `SortedSet` | 트리·이진 탐색 | 해당 없음(중복 키 불가) |

```csharp
record Emp (string Name, int Dept);

var emps = new List<Emp>
{
    new ("Alice", 1), new ("Bob", 1), new ("Carol", 1)
};

emps.Sort ((a, b) => a.Dept.CompareTo (b.Dept));
// 부서가 전부 같다 → 순서 보장 없음. 실행 환경·원소 수에 따라 뒤바뀔 수 있다

var stable = emps.OrderBy (e => e.Dept).ToList();
// 원래 순서 보존: Alice, Bob, Carol
```

**다중 키 정렬은 거의 언제나 LINQ의 `OrderBy`/`ThenBy`가 맞다**(30.5절). "부서로 정렬한 다음 이름으로 정렬한다"를 `Sort`를 두 번 호출해 구현하면 불안정성 때문에 틀린 결과가 나온다.

비교자가 계약을 어기면 어떻게 되는가. **`Array.Sort`와 `List<T>.Sort`는 계약 위반을 감지하려 시도한다.**

```csharp
// 계약 위반: 반대칭성이 없다 — 언제나 1을 반환한다
var bad = Comparer<int>.Create ((x, y) => 1);
var arr = Enumerable.Range (0, 100).ToArray();
Array.Sort (arr, bad);
// ArgumentException — "IComparer.Compare() method returns inconsistent results"
```

내부 정렬 루틴은 비교 결과를 신뢰해 인덱스를 움직이는데, 비교자가 모순되면 인덱스가 배열 범위를 벗어난다. 런타임은 이를 감지해 **`ArgumentException`을 던지며, 메시지가 "비교자가 일관되지 않은 결과를 반환한다"고 알려 준다.** 비교자가 스스로 예외를 던진 경우에는 그 예외가 **`InvalidOperationException`으로 감싸져** 나오고 원래 예외는 `InnerException`에 담긴다.

> **⚠️ 예외는 최선 노력일 뿐, 보장이 아니다**
>
> 위 검사는 인덱스가 실제로 범위를 벗어났을 때만 작동한다. **미묘하게 비일관적인 비교자 — 예를 들어 추이성만 깨진 비교자 — 는 예외 없이 그냥 틀린 순서를 낸다.** 원소 수가 적으면 (`Array.Sort`는 작은 구간에서 삽입 정렬로 전환한다) 아예 문제가 드러나지 않다가, 데이터가 커지면 갑자기 예외가 나기 시작하는 형태로 나타난다.
>
> 이 부류의 버그에서 가장 흔한 원인은 **`double` 필드의 뺄셈을 비교 결과로 쓰는 것**이다.
>
> ```csharp
> // 위험한 관용구
> list.Sort ((a, b) => (int)(a.Score - b.Score));   // 0.5 차이가 0으로 잘린다
> list.Sort ((a, b) => a.Score.CompareTo (b.Score)); // 올바르다. 단 NaN 주의
> ```
>
> `int` 필드의 뺄셈도 위험하다. `a.Id - b.Id`는 두 값의 차이가 `int` 범위를 넘으면 오버플로해 부호가 뒤집힌다. **비교는 언제나 `CompareTo`로 하라.**

### `Comparer<T>.Default`와 순서를 지원하지 않는 타입

`Comparer<T>.Default`는 `T`가 제공하는 자연 순서를 쓰는 비교자를 돌려준다. `T`가 `IComparable<T>`를 구현하면 그쪽을, 아니면 `IComparable`을 쓴다. **둘 다 구현하지 않으면 컴파일은 통과하고 런타임에 예외가 난다.**

```csharp
class Widget { }

var list = new List<Widget> { new(), new() };
list.Sort();      // 컴파일 성공. 런타임 예외
```

이것이 순서 비교와 동등성 비교의 큰 차이다. **동등성은 모든 타입이 `object.Equals`를 상속하므로 언제나 "어떤 답"이 나온다. 순서는 그렇지 않다.** 자연 순서가 없는 타입을 정렬하려면 `IComparer<T>`나 `Comparison<T>`를 명시적으로 넘겨야 한다(25.7절).

## 25.7 `IComparer<T>`와 `IEqualityComparer<T>`로 외부에서 정의하기

### 타입 안이 아니라 타입 밖에서

지금까지는 타입 **작성자**가 동등성과 순서를 정의했다. 그러나 두 가지 상황에서 이 방식이 막힌다.

1. **타입의 소스에 손댈 수 없다.** 프레임워크 타입이거나 다른 팀의 라이브러리다.
2. **한 타입에 여러 개의 "같음"이나 "순서"가 필요하다.** 고객을 이름순으로도, 매출순으로도 정렬해야 한다.

이럴 때 쓰는 것이 **꽂아 넣는 프로토콜**이다.

```csharp
public interface IEqualityComparer<T>
{
    bool Equals (T x, T y);
    int  GetHashCode (T obj);
}

public interface IComparer<in T>
{
    int Compare (T x, T y);
}
```

**어느 컬렉션이 어느 인터페이스를 인식하는지, 어떻게 생성자에 넘기는지, `EqualityComparer<T>`·`Comparer<T>` 추상 클래스를 상속하는 방법은 24.13절에서 다뤘다. 이 절은 그 비교자들이 지켜야 할 계약과 의미론만 본다.**

### 비교자의 계약은 타입의 계약과 같다

`IEqualityComparer<T>` 구현은 **25.3절의 다섯 계명과 25.4절의 세 규칙을 그대로 져야 한다.** 다만 주어가 타입이 아니라 비교자로 바뀐다.

| 계약 | 비교자 버전 |
|---|---|
| 반사성 | `c.Equals(x, x)`는 언제나 `true` |
| 대칭성 | `c.Equals(x, y) == c.Equals(y, x)` |
| 추이성 | `c.Equals(x,y) && c.Equals(y,z)`면 `c.Equals(x,z)` |
| 해시 일치 | `c.Equals(x, y)`면 `c.GetHashCode(x) == c.GetHashCode(y)` |
| 해시 불변 | 같은 객체에 대해 `c.GetHashCode(x)`가 반복 호출에서 같다 |

**네 번째 항목이 자주 잊힌다.** 비교자를 만들 때 `Equals`만 신경 쓰고 `GetHashCode`를 `obj.GetHashCode()`로 그냥 넘기는 코드가 흔하다.

```csharp
// 계약 위반: Equals는 대소문자를 무시하는데 GetHashCode는 무시하지 않는다
class BrokenComparer : IEqualityComparer<string>
{
    public bool Equals (string x, string y)
        => string.Equals (x, y, StringComparison.OrdinalIgnoreCase);

    public int GetHashCode (string obj) => obj.GetHashCode();   // 대소문자를 구분한다
}
```

```csharp
var set = new HashSet<string> (new BrokenComparer()) { "Hello" };
Console.WriteLine (set.Contains ("HELLO"));      // False — Equals까지 가지도 못한다
Console.WriteLine (set.Contains ("Hello"));      // True
set.Add ("HELLO");
Console.WriteLine (set.Count);                   // 2 — 같다고 판정될 값이 둘 들어갔다
```

25.4절의 단계별 추적과 정확히 같은 실패다. **`"Hello"`와 `"HELLO"`의 해시가 다르므로 버킷이 갈리고, `Equals`는 호출조차 되지 않는다.** 올바른 구현은 해시도 같은 규칙으로 계산한다.

```csharp
public int GetHashCode (string obj)
    => obj is null ? 0 : StringComparer.OrdinalIgnoreCase.GetHashCode (obj);
```

> **⚠️ 비교자의 `null` 처리 계약**
>
> `IEqualityComparer<T>.GetHashCode(T)`에 `null`이 들어올 수 있다. `Dictionary<K,V>`는 `null` 키를 `ArgumentNullException`으로 거부하지만, `HashSet<T>`·`Distinct`·`GroupBy`·`ToLookup`은 **`null`을 정상적인 값으로 받아들인다.** 비교자가 `null`에서 `NullReferenceException`을 던지면 LINQ 파이프라인 한가운데서 터진다.
>
> ```csharp
> public int GetHashCode (Person p) => p is null ? 0 : p.Id.GetHashCode();
>
> public bool Equals (Person x, Person y)
> {
>     if (ReferenceEquals (x, y)) return true;      // 둘 다 null인 경우 포함
>     if (x is null || y is null) return false;
>     return x.Id == y.Id;
> }
> ```
>
> `IComparer<T>.Compare`도 마찬가지다. `null`은 어떤 값보다 작다는 관례를 지켜라(25.6절).

### `StringComparer` — 하나의 타입, 여러 개의 같음

`StringComparer`는 **`IEqualityComparer`와 `IComparer`(및 제네릭 버전)를 모두 구현**하는 미리 정의된 비교자 집합이다. 사용법 자체는 24.13절에 있고, 여기서는 **왜 문자열에 이렇게 많은 비교 방식이 필요한가**를 본다.

| 비교자 | 동등성 판정 | 정렬 결과 | 언제 쓰는가 |
|---|---|---|---|
| `Ordinal` | 유니코드 코드 포인트 일치 | 코드 포인트 순 | **식별자·키·프로토콜·파일 경로** |
| `OrdinalIgnoreCase` | 대소문자 무시 코드 포인트 | 코드 포인트 순 | HTTP 헤더, 환경 변수, 대소문자 무시 키 |
| `CurrentCulture` | 문화권 규칙 | **사람이 읽는 순서** | 화면에 보여 줄 목록 정렬 |
| `CurrentCultureIgnoreCase` | 문화권 + 대소문자 무시 | 사람이 읽는 순서 | 사용자 입력 검색 |
| `InvariantCulture` | 고정 문화권 규칙 | 문화권 무관 안정 순서 | 저장하거나 비교해야 하는 정렬 순서 |

**핵심 통찰은 25.6절에서 이미 나왔다. `string`의 `Equals`는 서수이고 `CompareTo`는 문화권 의존이다.** 이 비대칭은 실수가 아니라 설계다.

- 동등성은 **정확해야** 한다. `"file.txt"`와 `"FILE.TXT"`가 같은지는 도메인이 정하지 언어가 정하지 않는다. 그래서 기본은 가장 엄격한 서수다.
- 순서는 **사람이 읽기에 자연스러워야** 한다. 스웨덴어에서 `ä`는 `z` 뒤에 오고 독일어에서는 `a` 근처에 온다. 그래서 기본은 문화권 의존이다.

> **⚠️ 문화권 의존 비교로 만든 정렬 결과를 영속화하지 마라**
>
> `CurrentCulture` 비교의 결과는 **운영체제 로케일, .NET 버전, 그리고 사용하는 ICU 버전**에 따라 달라진다. 정렬된 인덱스를 파일이나 데이터베이스에 저장해 두었다가 다른 환경에서 이진 탐색하면 조용히 틀린 결과가 나온다.
>
> 영속 데이터의 정렬 순서에는 **`Ordinal` 또는 `InvariantCulture`** 를 쓰고, 어느 것을 썼는지 데이터와 함께 기록하라.
>
> 참고로 .NET 5부터 Windows에서도 ICU를 쓰도록 기본값이 바뀌었다. **.NET Framework와 .NET 5+ 사이에 문화권 정렬 결과가 달라질 수 있다는 뜻이다.** 이식할 때 정렬 관련 테스트를 반드시 재실행하라.

> **💡 딕셔너리 키의 기본값은 `Ordinal`이다**
>
> `new Dictionary<string, T>()`는 서수 비교를 쓴다. 문화권 비교를 쓰는 딕셔너리는 **만들지 마라.** 키 조회가 로케일에 따라 달라지는 딕셔너리는 재현 불가능한 버그의 온상이고, 서수보다 훨씬 느리다.
>
> 대소문자를 무시하고 싶다면 `StringComparer.OrdinalIgnoreCase`를 넘겨라. `CurrentCultureIgnoreCase`가 아니다.

### `Comparison<T>` 델리게이트와 대체 순서

제네릭이 .NET에 들어온 이후에 개발된 API 대부분은 다른 정렬을 수행할 때 **`Comparison<T>` 델리게이트**를 요구한다. 타입 안에 정적 프로퍼티로 대체 비교 순서를 제공하는 것이 간단하다.

```csharp
public static Comparison<Customer> CompareByRevenue =>
    (left, right) => left.revenue.CompareTo (right.revenue);
```

예전 라이브러리는 같은 기능을 `IComparer` 인터페이스로 요구한다. `IComparer`는 제네릭을 쓰지 않고 타입에 대체 순서를 제공하는 표준 방법이다. 1.x 시절 프레임워크 클래스 라이브러리에서 `IComparable` 타입을 다루는 메서드들은 `IComparer`를 통해 객체를 정렬하는 오버로드를 제공한다.

`Customer` 구조체를 직접 작성했다면 새 클래스(`RevenueComparer`)를 **`Customer` 안의 비공개 중첩 클래스**로 만들고 정적 프로퍼티로 노출할 수 있다.

```csharp
public struct Customer : IComparable<Customer>, IComparable
{
    private readonly string name;
    private double revenue;

    public Customer (string name, double revenue)
    {
        this.name = name;
        this.revenue = revenue;
    }

    public int CompareTo (Customer other) => name.CompareTo (other.name);

    int IComparable.CompareTo (object obj)
    {
        if (!(obj is Customer))
            throw new ArgumentException ("Argument is not a Customer", "obj");
        return this.CompareTo ((Customer) obj);
    }

    public static bool operator <  (Customer l, Customer r) => l.CompareTo (r) <  0;
    public static bool operator >  (Customer l, Customer r) => l.CompareTo (r) >  0;

    private static Lazy<RevenueComparer> revComp =
        new Lazy<RevenueComparer> (() => new RevenueComparer());

    public static IComparer<Customer> RevenueCompare => revComp.Value;

    public static Comparison<Customer> CompareByRevenue =>
        (left, right) => left.revenue.CompareTo (right.revenue);

    // 매출로 고객을 비교하는 클래스.
    // 언제나 인터페이스 포인터를 통해 쓰이므로 인터페이스 구현만 제공한다.
    private class RevenueComparer : IComparer<Customer>
    {
        int IComparer<Customer>.Compare (Customer left, Customer right)
            => left.revenue.CompareTo (right.revenue);
    }
}
```

이 마지막 버전은 고객을 **이름순**(자연 순서)으로 정렬하게 해 주면서, `IComparer`를 구현하는 클래스를 노출해 **매출순**이라는 대체 순서도 제공한다. `Customer` 클래스의 소스에 접근할 수 없다면 그 공개 프로퍼티들을 이용하는 `IComparer`를 바깥에서 제공할 수 있다. **소스에 접근할 수 없을 때만 이 관용구를 쓰라** — 프레임워크 클래스 중 하나에 다른 순서가 필요한 경우 같은 때다.

> **📌 순서 관계와 동등성은 별개의 연산이다**
>
> 원천 도서가 `IComparable` 항목을 마무리하며 강조하는 말이 있다. **순서 관계를 갖기 위해 동등성 비교를 구현할 필요는 없다.** 실제로 참조 타입은 흔히 객체 내용으로 순서를 구현하면서 동등성은 객체 정체성으로 구현한다. `CompareTo()`가 0을 반환하는데 `Equals()`가 `false`를 반환하는 상황이 완벽하게 합법이다.
>
> 다만 25.6절의 방향 규칙은 남는다. **`CompareTo`가 `Equals`보다 까다로우면 안 된다.**

### 비교자를 바꿔 낀 컬렉션끼리 섞을 때

이 함정은 실무에서 자주 나오는데 문서화가 잘 되어 있지 않다.

```csharp
var a = new HashSet<string> (StringComparer.OrdinalIgnoreCase) { "Hello" };
var b = new HashSet<string> (StringComparer.Ordinal)           { "HELLO" };

Console.WriteLine (a.SetEquals (b));      // True  — a의 비교자로 판정
Console.WriteLine (b.SetEquals (a));      // False — b의 비교자로 판정
```

**집합 연산은 "누가 호출되었는가"의 비교자를 쓴다.** 그래서 비교자가 다른 두 집합 사이의 연산은 대칭적이지 않다. `Except`, `Intersect`, `UnionWith`도 마찬가지다.

LINQ 쪽도 같은 종류의 함정이 있다.

```csharp
var d = new Dictionary<string,int> (StringComparer.OrdinalIgnoreCase) { ["a"] = 1 };
var copy = d.ToDictionary (kv => kv.Key, kv => kv.Value);   // 비교자가 사라진다
Console.WriteLine (d.ContainsKey ("A"));       // True
Console.WriteLine (copy.ContainsKey ("A"));    // False
```

`ToDictionary`는 기본 비교자로 새 딕셔너리를 만든다. **원본의 비교자를 유지하려면 명시적으로 넘겨야 한다.**

```csharp
var copy = d.ToDictionary (kv => kv.Key, kv => kv.Value, d.Comparer);
```

> **💡 비교자를 쓰는 컬렉션은 생성 지점을 한곳에 모아라**
>
> `StringComparer.OrdinalIgnoreCase`를 쓰는 딕셔너리가 코드베이스 여기저기서 `new`로 만들어지면, 언젠가 한 군데가 비교자를 빠뜨린다. 팩터리 메서드나 확장 메서드를 하나 만들어 그것만 쓰게 하라.
>
> ```csharp
> static Dictionary<string,T> NewHeaderMap<T>() => new (StringComparer.OrdinalIgnoreCase);
> ```

### 구조적 동등성 — `IStructuralEquatable`과 `IStructuralComparable`

구조체는 기본적으로 구조적 비교를 한다 — 모든 필드가 같으면 두 구조체는 같다(25.1절). **배열처럼 이 방식을 기본으로 삼지 않는 타입에도 구조적 비교를 꽂아 넣고 싶을 때** 쓰는 인터페이스가 둘 있다.

```csharp
public interface IStructuralEquatable
{
    bool Equals (object other, IEqualityComparer comparer);
    int  GetHashCode (IEqualityComparer comparer);
}

public interface IStructuralComparable
{
    int CompareTo (object other, IComparer comparer);
}
```

두 인터페이스 모두 **비제네릭 비교자를 받는다는 점**이 특이하다. 요소 타입이 컴파일 타임에 정해지지 않는 배열·튜플에서 쓰이기 위한 설계다. 넘긴 비교자는 복합 객체의 **개별 요소마다** 적용된다.

```csharp
string[] a1 = "the quick brown fox".Split();
string[] a2 = "THE QUICK BROWN FOX".Split();

Console.WriteLine (a1.Equals (a2));                     // False — 배열의 기본은 참조 동등성
IStructuralEquatable se1 = a1;
Console.WriteLine (se1.Equals (a2,
    StringComparer.InvariantCultureIgnoreCase));        // True
```

**첫 줄이 요점이다.** 배열은 참조 타입이므로 기본 `Equals`가 참조 동등성이다. `IStructuralEquatable`로 캐스팅해야 요소 단위 비교가 열린다.

이 인터페이스들을 구현하는 타입은 `System.Array`와 `Tuple<>` 제네릭 클래스들이다. **이 인터페이스는 그 타입들이 모든 비교에서 값 의미론을 강제하지 않으면서도 값 의미론을 제공할 수 있게 해 준다.** 여러분이 이 인터페이스를 구현하는 타입을 직접 만들 일은 거의 없다. 그런 경량 타입에만 필요하기 때문이다. **`IStructuralEquatable`을 구현한다는 것은 "이 타입은 값 기반 의미론을 갖는 더 큰 객체 안에 구성 요소로 들어갈 수 있다"고 선언하는 것이다.**

`ValueTuple`(C#의 `(int, string)` 문법)의 동등성·구조적 비교는 조금 다르게 작동한다. 자세히는 77.3절에서 다룬다.

> **⚠️ 배열을 딕셔너리 키로 쓰지 마라**
>
> `Dictionary<int[], string>`은 컴파일되고 실행되지만, **키는 참조로 비교된다.** 내용이 같은 새 배열로는 절대 찾을 수 없다.
>
> ```csharp
> var d = new Dictionary<int[], string>();
> d[new[] { 1, 2 }] = "x";
> Console.WriteLine (d.ContainsKey (new[] { 1, 2 }));   // False
> ```
>
> 배열을 키로 쓰려면 요소 비교자를 직접 만들어 넘기거나, 애초에 값 의미론을 가진 타입 — 튜플, 레코드, `ImmutableArray<T>`를 감싼 타입 — 으로 바꿔야 한다. 그리고 **키가 될 배열은 넣은 뒤에 절대 수정하면 안 된다.** 25.8절의 주제다.

## 25.8 가변 객체를 딕셔너리 키로 쓸 때 생기는 일

### 규칙 2를 어기는 유일하고도 가장 흔한 방법

25.4절의 규칙 2는 이랬다. **객체 `A`에 대해 `A.GetHashCode()`는 인스턴스 불변이어야 한다.** 이 규칙을 어기는 방법은 실무에서 사실상 하나다. **해시 계산에 참여하는 필드를 나중에 바꾸는 것.**

원천 도서의 예제로 시작한다.

```csharp
public class Customer
{
    private decimal revenue;

    public Customer (string name) => this.Name = name;

    public string Name { get; set; }        // 가변이다

    public override int GetHashCode() => Name.GetHashCode();
}
```

```csharp
Customer c1 = new Customer ("Acme Products");
myHashMap.Add (c1, orders);

// 이런, 이름이 틀렸다
c1.Name = "Acme Software";
```

**`c1`이 해시 맵 어딘가에서 사라졌다.**

### 코드로 증명하기

실행 가능한 형태로 다시 쓴다.

```csharp
public class Customer
{
    public string Name { get; set; }
    public Customer (string name) => Name = name;

    public override bool Equals (object obj) => obj is Customer c && c.Name == Name;
    public override int GetHashCode() => Name.GetHashCode();
}
```

```csharp
var map = new Dictionary<Customer, string>();
var c1 = new Customer ("Acme Products");
map[c1] = "주문 목록";

Console.WriteLine (map.ContainsKey (c1));       // True

c1.Name = "Acme Software";                      // (1) 키를 바꿨다

Console.WriteLine (map.ContainsKey (c1));       // False ← 같은 객체인데도
Console.WriteLine (map.Count);                  // 1     ← 들어는 있다
Console.WriteLine (map.Remove (c1));            // False ← 지울 수도 없다
Console.WriteLine (map.Keys.Any (k => k.Equals (c1)));  // True ← 선형 열거는 찾는다

map[c1] = "다른 주문 목록";                      // (2) 새 엔트리가 추가된다
Console.WriteLine (map.Count);                  // 2     ← 같은 객체가 키로 두 번
```

**증거가 다 모였다.**

- `ContainsKey(c1)`은 `False`인데 `Keys`를 직접 훑으면(`Any(k => k.Equals(c1))`) `True`다. 전자는 해시 조회고 후자는 선형 열거다. **`map.Keys.Contains(c1)`으로는 재현되지 않는다** — `KeyCollection.Contains`는 안쪽에서 `ContainsKey`를 부르는 해시 조회이기 때문이다.
- `Remove`가 실패하므로 그 엔트리는 **딕셔너리가 폐기될 때까지 남는다.** 사실상 메모리 누수다.
- 같은 참조를 다시 인덱서로 대입하면 새 엔트리가 붙는다. **딕셔너리에 같은 키가 두 개 들어간다.**

### 단계별 추적

```text
[1] map[c1] = "주문 목록";
    c1.Name = "Acme Products"
    GetHashCode() → H("Acme Products") = 0x5A3C…  →  버킷 3

     buckets                 entries
    ┌───────┐         ┌──────────────────────────┐
    │ 0  ∅  │         │ hash  = 0x5A3C…          │
    │ 1  ∅  │         │ key   = ●─── Customer#1  │
    │ 2  ∅  │         │ value = "주문 목록"       │
    │ 3  ●──┼────────▶│ next  = -1               │
    │ ...   │         └──────────────────────────┘
    └───────┘

[2] c1.Name = "Acme Software";
    (1) 딕셔너리는 이 변경을 알 방법이 전혀 없다.
      엔트리의 hash 필드는 0x5A3C… 그대로,
      키 객체의 실제 해시는 H("Acme Software") = 0x91E7… 로 바뀌었다.

     buckets                 entries
    ┌───────┐         ┌──────────────────────────┐
    │ 3  ●──┼────────▶│ hash  = 0x5A3C…  (과거)  │

                      │           Name="Acme Software"
                      └──────────────────────────┘
                                   ▲
                          같은 객체인데 해시가 달라졌다

    GetHashCode() → 0x91E7…  →  버킷 6
    버킷 6은 비어 있다 → Equals 호출 없이 False
```

**딕셔너리는 키가 변했다는 사실을 알 방법이 없다.** 변경 알림을 받지 않기 때문이다. 엔트리는 저장 당시의 해시로 계산된 버킷에 그대로 앉아 있고, 조회는 새 해시로 계산된 다른 버킷을 뒤진다. 다시는 만나지 못한다.

> **⚠️ 이 버그는 예외도 경고도 남기지 않는다**
>
> 코드가 던지는 것은 없다. 로그도 없다. `Count`는 정상이고 열거도 정상이다. **증상은 "가끔 데이터를 못 찾는다"뿐이고, 재현 조건은 "그 사이에 누가 이름을 바꿨을 때"다.**
>
> 진단할 때 결정적인 신호는 이것이다. **`dict.ContainsKey(k)`는 `false`인데 키를 하나씩 훑는 `dict.Keys.Any(x => x.Equals(k))`는 `true`다.** 이 조합이 보이면 100% 해시 불변성 위반이다. (`dict.Keys.Contains(k)`는 내부적으로 다시 해시 조회를 하므로 진단에 쓸 수 없다.)

### 값 타입은 다르게 망가진다

앞의 상황은 `Customer`가 참조 타입일 때만 일어난다. **값 타입은 다르게 잘못 동작하지만, 여전히 문제를 일으킨다.**

`Customer`가 값 타입이라면 해시 맵에 저장되는 것은 `c1`의 **복사본**이다. 이름 값을 바꾸는 마지막 줄은 해시 맵에 저장된 복사본에 아무 영향을 주지 않는다.

```csharp
struct SCustomer
{
    public string Name;
    public SCustomer (string n) => Name = n;
    public override int GetHashCode() => Name.GetHashCode();
    public override bool Equals (object o) => o is SCustomer s && s.Name == Name;
}
```

```csharp
var map = new Dictionary<SCustomer, string>();
var c = new SCustomer ("Acme Products");
map[c] = "주문 목록";

c.Name = "Acme Software";                    // 로컬 변수만 바뀐다

Console.WriteLine (map.ContainsKey (c));                          // False
Console.WriteLine (map.ContainsKey (new SCustomer ("Acme Products"))); // True ← 원본은 찾힌다
```

**박싱과 언박싱도 복사본을 만들기 때문에, 값 타입 객체가 컬렉션에 추가된 뒤에 그 멤버를 바꾸는 것은 애초에 매우 어렵다.** 그래서 값 타입에서는 "딕셔너리 안의 것이 사라지는" 형태가 아니라 "내가 바꾼 것이 반영되지 않는" 형태로 나타난다. 후자가 그나마 덜 위험하지만 여전히 버그다.

### 유일한 해법 — 불변성

**규칙 2를 지키는 유일한 방법은 객체의 불변 프로퍼티에 기반해 해시 코드 함수를 정의하는 것이다.** `System.Object`는 변하지 않는 객체 정체성을 사용해 이 규칙을 지킨다. `System.ValueType`은 타입의 첫 필드가 변하지 않기를 바랄 뿐이다. **타입을 불변으로 만들지 않고서는 그보다 더 잘할 수 없다.**

`Customer` 클래스를 고쳐 이름을 불변으로 만든다.

```csharp
public class Customer
{
    private decimal revenue;

    public Customer (string name) => this.Name = name;

    public string Name { get; }                    // 세터가 없다
    public decimal Revenue { get; set; }           // 해시에 참여하지 않는 필드는 가변이어도 된다

    public override int GetHashCode() => Name.GetHashCode();

    public Customer ChangeName (string newName)
        => new Customer (newName) { Revenue = revenue };
}
```

`ChangeName()`은 생성자와 객체 초기화 문법으로 현재 매출을 설정하면서 **새 `Customer` 객체를 만든다.** 이름을 불변으로 만들면 이름을 수정할 때 고객 객체를 다루는 방식이 달라진다.

```csharp
Customer c1 = new Customer ("Acme Products");
myDictionary.Add (c1, orders);

// 이런, 이름이 틀렸다
Customer c2 = c1.ChangeName ("Acme Software");
Order o = myDictionary[c1];
myDictionary.Remove (c1);
myDictionary.Add (c2, o);
```

**원래 고객을 제거하고, 이름을 바꾸고, 새 `Customer` 객체를 딕셔너리에 추가해야 한다.** 첫 버전보다 번거로워 보이지만 이쪽이 동작한다. 앞 버전은 프로그래머가 잘못된 코드를 쓸 수 있게 허용했다. **해시 값 계산에 쓰이는 프로퍼티의 불변성을 강제함으로써 올바른 동작을 강제하는 것이다.** 개발자에게 더 많은 코드를 쓰게 만들지만, 그것이 올바른 코드를 쓰는 유일한 방법이기 때문이다. **해시 값 계산에 쓰이는 어떤 데이터 멤버든 반드시 불변이어야 한다.**

딕셔너리 안의 키를 "수정"하는 유일하게 올바른 순서는 ① 값을 꺼내고(`var v = dict[oldKey];`) ② 옛 키를 제거하고(`dict.Remove(oldKey);`) ③ 새 키를 만든 뒤 ④ 다시 넣는 것이다(`dict[newKey] = v;`). **②를 ③보다 먼저 해야 한다.** 키 객체를 먼저 바꾸면 ②에서 이미 찾지 못한다.

### 어떤 타입이 안전한 키인가

| 키 타입 | 안전한가 | 이유 |
|---|---|---|
| `string` | **안전** | 불변이다 |
| `int`, `Guid`, `DateTime`, 열거형 | **안전** | 불변 값 타입 |
| `readonly record struct` | **안전** | 불변 + 자동 동등성 |
| `record` (모든 프로퍼티가 `init`) | **안전** | 불변 |
| `record` (가변 프로퍼티 포함) | **위험** | 프로퍼티를 바꾸면 해시가 변한다 |
| 가변 클래스 + `Equals` 재정의 | **위험** | 이 절의 주제 |
| 가변 클래스, 재정의 없음 | 안전 | 해시가 정체성 기반이라 변하지 않는다 |
| `T[]`, `List<T>` | 안전(참조 동등성) | 단, 원하는 동작이 아닐 가능성이 높다(25.7절) |
| `StringBuilder` | **위험** | `Equals`가 값 동등성인데 가변이다 |

> **📌 재정의하지 않은 가변 클래스가 오히려 안전하다는 역설**
>
> 표에서 "가변 클래스, 재정의 없음"이 안전한 것에 주목하라. `Equals`와 `GetHashCode`를 건드리지 않으면 해시가 객체 정체성에 기반하므로 필드를 아무리 바꿔도 변하지 않는다. **동등성을 "개선"하려고 재정의한 순간 위험해진다.**
>
> 이것이 25.5절 표의 첫 행 — "가변 참조 타입은 아무것도 재정의하지 않는다" — 이 그냥 게으름이 아닌 이유다.

> **💡 진단 도구 — 불변성 검사를 테스트로 박아 두기**
>
> 키로 쓰이는 타입에 대해 다음 형태의 테스트를 하나 두면 회귀를 막을 수 있다.
>
> ```csharp
> [Test]
> public void HashCodeIsStableAcrossMutation()
> {
>     var k = CreateSampleKey();
>     int before = k.GetHashCode();
>     MutateEveryPublicSetter (k);            // 리플렉션으로 세터를 전부 호출
>     Assert.AreEqual (before, k.GetHashCode());
> }
> ```
>
> 더 강력한 예방책은 애초에 세터를 만들지 않는 것이다. 키 타입에는 `record`나 `readonly record struct`를 쓰고, 변경이 필요하면 `with` 식으로 새 인스턴스를 만들어라(19.4절). **컴파일러가 강제하는 불변성이 테스트보다 낫다.**

### `HashSet<T>`와 LINQ에서도 같다

이 문제는 `Dictionary`만의 것이 아니다. **해시를 쓰는 모든 것이 같은 방식으로 망가진다.**

```csharp
var set = new HashSet<Customer> { c1 };
c1.Name = "바뀐 이름";
Console.WriteLine (set.Contains (c1));      // False
set.Add (c1);
Console.WriteLine (set.Count);              // 2 — 같은 객체가 두 번

// LINQ도 마찬가지다
var groups = customers.GroupBy (c => c);    // 그룹 키가 바뀌면 결과가 흐트러진다
var joined = a.Join (b, x => x.Key, y => y.Key, (x, y) => (x, y));
```

`Distinct`, `GroupBy`, `Join`, `Except`, `Intersect`, `Union`, `ToLookup`, `ToDictionary`, `ToHashSet`, `FrozenDictionary`, `ConcurrentDictionary` — 전부 내부에 해시테이블을 만든다.

반면 `List<T>.Contains`나 `IndexOf`는 **선형 탐색이므로 해시를 쓰지 않는다.** 그래서 키를 바꿔도 계속 찾힌다. 이 비대칭이 디버깅을 어렵게 만든다. **"`List`에서는 되는데 `Dictionary`에서는 안 된다"가 이 버그의 시그니처다.**

> **⚠️ `ConcurrentDictionary`에서는 더 나쁘다**
>
> `ConcurrentDictionary<K,V>`는 해시 코드로 **잠금 스트라이프**까지 고른다. 키의 해시가 변하면 조회 실패에 더해 **다른 잠금을 잡게 되어**, 원래 스트라이프를 보호하던 동기화가 무의미해진다. 데이터 경합이 조용히 생길 수 있다.
>
> 동시성 컬렉션의 키는 예외 없이 불변이어야 한다(24.12절).

## 이 장의 요약

- **동등성은 네 가지 개념이다.** 참조 동등성(정체성), 값 동등성(내용), 논리적 동등성(도메인 규칙), 구조적 동등성(필드 단위 재귀). 타입 작성자는 이 중 하나를 골라 **모든 창구에 일관되게** 적용해야 한다. 재정의하지 않으면 값 타입은 구조적 동등성, 참조 타입은 참조 동등성이다.
- **동등성 창구는 다섯 개이고 각각 다르게 결정된다.** `==`는 컴파일 타임에 정적 타입으로, `Equals(object)`는 런타임에 실제 타입으로, `IEquatable<T>.Equals(T)`는 박싱 없이, `ReferenceEquals`는 언제나 정체성으로, 정적 `object.Equals(a,b)`는 `null` 검사 후 좌변에 위임한다. **프레임워크는 `==`를 절대 부르지 않는다** — 컬렉션·LINQ·비교자는 `Equals`와 `GetHashCode`만 쓴다.
- **`Equals` 재정의는 다섯 계명을 지는 계약이다.** 반사성·대칭성·추이성·일관성·`null` 처리. 부동소수점 필드를 `==`로 비교하면 반사성이, 상속 계층에서 `as`로 타입을 검사하면 대칭성이, 허용 오차 비교를 쓰면 추이성이 깨진다. 계약 위반은 예외가 아니라 **조용한 오작동**으로 나타난다.
- **상속 계층의 대칭성 문제에는 완전한 해법이 없다.** `GetType()` 정확 비교는 대칭성을 지키지만 ORM 프록시를 깨뜨리고, `is`는 프록시를 통과시키지만 대칭성을 깬다. **`sealed` 클래스나 `record`로 만들어 문제 자체를 없애는 것이 최선이다.**
- **`GetHashCode`의 계약은 세 개다.** `Equals`가 같으면 해시도 같아야 하고, 해시는 인스턴스 불변이어야 하며, 고르게 분포해야 한다. **역은 요구되지 않는다** — 해시가 같아도 `Equals`는 다를 수 있다. 첫 규칙을 깨면 딕셔너리가 `Equals`를 호출조차 하지 않고 실패한다.
- **해시 코드는 절대 영속화하지 마라.** .NET Core 이후 문자열 해시는 프로세스마다 무작위 시드를 쓰고 `HashCode.Combine` 결과도 프로세스마다 다르다. `GetHashCode`는 한 프로세스 안에서 버킷을 고르는 용도 전용이다. `HashCode`는 **.NET Standard 2.1** 이상에서만 쓸 수 있다.
- **가변 객체를 해시 기반 컬렉션의 키로 쓰면 키를 잃는다.** 해시에 참여하는 필드를 바꾸는 순간 엔트리는 옛 버킷에 남고 조회는 새 버킷을 뒤진다. `ContainsKey`는 `false`인데 키를 선형으로 훑으면 찾히는 조합이 이 버그의 결정적 신호다. **해법은 불변성뿐이다.**
- **순서 비교는 `IComparable<T>`가 자연 순서를, `IComparer<T>`가 대체 순서를 정의한다.** `CompareTo`는 부호만 의미가 있으며 −1/0/1을 가정하면 안 된다. **동등성은 비교보다 까다로울 수 있지만 그 반대는 안 된다** — `Equals`가 `true`면 `CompareTo`는 반드시 0이다. `CompareTo`의 첫 줄에 `if (Equals(other)) return 0;`을 넣으면 이 규칙을 자동으로 지킨다.
- **`<`/`>`는 `IComparable`과 다른 물건이다.** 강한 대소 개념이 있고, 비교 맥락이 하나뿐이며, 문화권 불변일 때만 오버로딩한다. `string`이 `<`를 지원하지 않는 이유가 셋째 조건이다.
- **`Array.Sort`와 `List<T>.Sort`는 불안정하고, LINQ의 `OrderBy`는 안정적이다.** 비일관 비교자는 `ArgumentException`으로 잡히기도 하지만 보장은 아니다. 뺄셈을 비교 결과로 쓰는 관용구가 이 부류 버그의 최다 원인이다.

## 연습 문제

1. `Equals`만 재정의하고 `GetHashCode`를 재정의하지 않은 클래스를 만들어 `Dictionary`에 넣고 조회하라. 실패를 확인한 뒤, 조회 실패 시점에 `Equals`가 **한 번도 호출되지 않는다**는 것을 `Equals` 안에 `Console.WriteLine`을 넣어 증명하라. 그다음 `GetHashCode`를 추가해 고쳐라.

2. `double` 필드를 `==`로 비교하는 `Equals`를 가진 구조체를 만들어라. 그 필드에 `double.NaN`을 넣은 인스턴스를 `HashSet<T>`에 두 번 `Add`하고 `Count`를 출력하라. 그다음 `==`를 `Equals`로 바꿔 결과가 어떻게 달라지는지 확인하라.

3. 25.3절의 `B`/`D` 계층을 그대로 실행해 `baseObject.Equals(derivedObject)`와 `derivedObject.Equals(baseObject)`가 다른 값을 내는 것을 확인하라. 그다음 두 클래스의 타입 검사를 `GetType()` 비교로 바꾸고 결과가 대칭이 되는지 확인하라.

4. 이름을 `set` 접근자로 가진 `Customer` 클래스를 `Dictionary`의 키로 쓰고, 이름을 바꾼 뒤 `ContainsKey(c)`와 `Keys.Any(k => k.Equals(c))`를 각각 출력하라. `Keys.Contains(c)`도 함께 출력해 왜 이쪽은 `ContainsKey`와 같은 답을 내는지 설명하라. 두 값이 다른 이유를 24.7절의 버킷 구조로 설명하라. 그다음 `Remove(c)`가 실패하는 것과, 인덱서 대입으로 같은 객체가 키로 두 번 들어가는 것을 확인하라.

5. `Comparer<T>.Create((x, y) => 1)`처럼 반대칭성을 어긴 비교자로 원소 1,000개짜리 배열을 `Array.Sort`하라. 어떤 예외가 나는지 메시지까지 기록하라. 그다음 원소를 10개로 줄여 같은 실험을 반복하고, 예외가 나지 않는다면 왜 그런지 삽입 정렬 전환을 근거로 설명하라.

6. 같은 문자열 목록을 `StringComparer.Ordinal`과 `StringComparer.CurrentCulture`로 각각 `Array.Sort`하고 결과를 비교하라. `"apple"`, `"Apple"`, `"Æon"`, `"aeon"`, `"_x"`, `"1a"`를 포함시켜라. 그다음 `CultureInfo.CurrentCulture`를 `sv-SE`(스웨덴어)로 바꿔 다시 실행하고 순서가 달라지는 것을 확인하라.

7. `"hello".GetHashCode()`를 출력하는 프로그램을 세 번 실행해 값이 매번 다른 것을 확인하라. 그다음 `HashCode.Combine(1, 2)`도 같은지 확인하라. 마지막으로 `"hello".GetHashCode()`를 파일에 저장했다가 다음 실행에서 비교하는 코드를 작성해 실패를 재현하라.
