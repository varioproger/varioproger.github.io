# 14장. 상속과 다형성

> **이 장의 위치** — 13장에서 클래스 **하나**를 설계하는 법을 끝냈다. 이 장은 클래스 **여럿**을 계층으로 묶는다. 상속은 문법이 다섯 줄이면 끝나지만, 그 다섯 줄이 IL의 메서드 플래그를 바꾸고, 메서드 테이블의 슬롯 배치를 바꾸고, JIT이 호출을 어떻게 컴파일할지를 바꾼다. 이 장은 그 연쇄를 끝까지 따라간다.
>
> **선수 지식** — 6장(구문과 타입 기초), 10장(변수·매개변수·식), 13장(클래스와 캡슐화)
>
> **이 장에서 다루지 않는 것** — `System.Object`가 실제로 어떤 멤버를 갖는지와 박싱은 15장에서, 인터페이스와 그 디스패치는 18장에서, 레코드의 상속 규칙은 19장에서 다룬다. `new` 한정자를 실무에서 언제 쓰는가는 79.8절, 기반 클래스 메서드를 오버로딩할 때의 API 설계 지침은 78.8절, 메서드 테이블의 물리적 구조는 54.1절에 있다.

## 14.1 상속의 기본 규칙

### 문법 — 콜론 하나

클래스는 다른 클래스를 **확장(extend)** 할 수 있다. 확장한 클래스는 원래 클래스의 멤버를 모두 물려받고, 자기 멤버를 더한다.

```csharp
public class Asset
{
    public string Name;
}

public class Stock : Asset          // Asset을 상속한다
{
    public long SharesOwned;
}

public class House : Asset          // Asset을 상속한다
{
    public decimal Mortgage;
}
```

`Stock`과 `House`는 `Asset`이 가진 것을 전부 갖고, 각자의 멤버를 추가로 갖는다.

```csharp
Stock msft = new Stock { Name = "MSFT", SharesOwned = 1000 };
Console.WriteLine(msft.Name);           // MSFT   ← Asset에서 물려받은 필드
Console.WriteLine(msft.SharesOwned);    // 1000   ← Stock 자신의 필드

House mansion = new House { Name = "Mansion", Mortgage = 250000 };
Console.WriteLine(mansion.Name);        // Mansion
Console.WriteLine(mansion.Mortgage);    // 250000
```

용어는 여러 벌이 쓰인다. 이 책에서는 다음을 기본으로 쓴다.

| 이 책의 용어 | 같은 뜻으로 쓰이는 말 | 위치 |
|---|---|---|
| **기반 클래스**(base class) | 부모 클래스, 슈퍼클래스(superclass), 상위 클래스 | `Asset` |
| **파생 클래스**(derived class) | 자식 클래스, 서브클래스(subclass), 하위 클래스 | `Stock`, `House` |
| **is-a 관계** | 분류 관계, 일반화/특수화 | "Stock은 Asset이다" |

### 규칙 1 — 단일 상속

C#에서 클래스는 **기반 클래스를 하나만** 가질 수 있다. `class C : A, B`처럼 클래스 둘을 나열하면 컴파일 오류다. 다중 상속이 필요해 보이는 상황은 인터페이스(18장)나 포함·위임(14.12절)으로 푼다.

```csharp
public class A { }
public class B { }
// public class C : A, B { }   // 컴파일 오류: 기반 클래스는 하나뿐이다
```

이 제약은 C#의 취향이 아니라 **CLR의 제약**이다. CLR의 타입 정의는 기반 타입을 가리키는 필드를 하나만 갖는다. 그래서 어떤 .NET 언어도 클래스 다중 상속을 제공할 수 없다.

> **📌 왜 CLR은 다중 상속을 포기했는가**
>
> 클래스 다중 상속을 허용하면 같은 필드가 계층에 두 번 나타나는 다이아몬드 문제를 런타임이 해결해야 한다. C++은 가상 상속과 포인터 조정(thunk adjustment)으로 해결하지만, 그 대가로 객체 레이아웃이 복잡해지고 캐스팅이 주소를 바꾸는 연산이 된다. CLR은 참조 변환이 **주소를 바꾸지 않는다**는 단순한 성질을 지키는 쪽을 택했다(14.7절). 인터페이스 다중 구현은 필드를 갖지 않으므로 이 문제가 없고, 그래서 허용된다.

### 규칙 2 — `object`가 암묵적 기반

기반 클래스를 명시하지 않은 클래스는 자동으로 `System.Object`를 상속한다. 즉 다음 두 선언은 컴파일 결과가 같다.

```csharp
public class Asset { }              // 실제로는 아래와 같다
public class Asset : object { }     // 명시해도 되지만 아무도 이렇게 쓰지 않는다
```

IL을 보면 `extends` 절이 항상 붙어 있는 것을 확인할 수 있다.

```il
.class public auto ansi beforefieldinit Asset
       extends [System.Runtime]System.Object
{
  .field public string Name
  // ...
}

.class public auto ansi beforefieldinit Stock
       extends Asset
{
  .field public int64 SharesOwned
  // ...
}
```

`Asset`은 `extends [System.Runtime]System.Object`, `Stock`은 `extends Asset`이다. C# 소스에는 없던 `extends System.Object`를 컴파일러가 채워 넣었다. 결과적으로 모든 참조 타입은 하나의 트리 안에 있고, 그 뿌리는 `object`다. `object`가 정확히 어떤 멤버를 제공하는지는 15.1절에서 다룬다.

### 규칙 3 — 상속되는 것과 안 되는 것

"모든 멤버를 물려받는다"는 말은 정확하지 않다. 실제로는 다음과 같다.

| 멤버 종류 | 상속되는가 | 파생 클래스에서 접근 가능한가 |
|---|---|---|
| `public` 필드·메서드·프로퍼티·이벤트 | 상속됨 | 가능 |
| `protected` 멤버 | 상속됨 | 가능(외부에서는 불가) |
| `internal` 멤버 | 상속됨 | 같은 어셈블리 안에서만 가능 |
| `private` 멤버 | **객체 안에는 존재하지만** 이름으로 접근 불가 | 불가 |
| 인스턴스 생성자 | **상속되지 않음** | `base(...)`로 호출은 가능(14.6절) |
| 정적 생성자 | 상속되지 않음 | 호출 불가 |
| 파이널라이저 | 상속됨(재정의 형태) | `base.Finalize()`는 직접 호출 불가 |
| 정적 멤버 | 이름 조회 대상에는 포함됨 | 가능 |

`private` 필드에 대한 오해가 특히 흔하다. 파생 클래스 객체의 메모리에는 기반 클래스의 `private` 필드가 **그대로 들어 있다**. 다만 이름으로 접근할 수 없을 뿐이다. 접근 제한자는 메모리 배치가 아니라 **컴파일러의 이름 조회 규칙**이다. 접근 제한자 전체 목록과 조합 규칙은 17.1절에 있다.

> **⚠️ 생성자는 상속되지 않는다**
>
> 이것이 처음 상속을 쓸 때 가장 자주 걸리는 벽이다.
>
> ```csharp
> public class Baseclass
> {
>     public int X;
>     public Baseclass() { }
>     public Baseclass(int x) => X = x;
> }
>
> public class Subclass : Baseclass { }
>
> Subclass s = new Subclass(123);   // 컴파일 오류
> ```
>
> `Baseclass`에 `int`를 받는 생성자가 있어도 `Subclass`는 그것을 물려받지 않는다. `Subclass`가 노출하고 싶은 생성자는 **직접 다시 선언**해야 한다. 자세한 이유와 회피법은 14.6절에서 다룬다.

### 규칙 4 — 상속 관계는 컴파일 시각과 런타임 시각이 다르다

이 장 전체를 관통하는 축이 하나 있다. 변수에는 두 가지 타입이 있다.

- **정적 타입**(static type, 컴파일 타임 타입) — 변수를 선언할 때 쓴 타입. 컴파일러가 아는 전부다.
- **런타임 타입**(runtime type, 동적 타입) — 그 변수가 실제로 가리키는 객체의 타입.

```csharp
Asset a = new House();
// a의 정적 타입   = Asset
// a의 런타임 타입 = House
```

이 두 타입이 갈라지는 순간부터 모든 것이 재미있어진다. 어떤 결정은 정적 타입으로 하고(오버로드 해석, 필드 접근, `new`로 숨긴 메서드), 어떤 결정은 런타임 타입으로 한다(가상 메서드 디스패치, 캐스트 성공 여부, `is` 검사). 어느 쪽이 어느 쪽인지 아는 것이 이 장의 핵심이다.

| 결정 | 무엇을 보고 결정하는가 | 절 |
|---|---|---|
| 어떤 오버로드를 부를까 | 정적 타입 | 14.8 |
| 어떤 필드를 읽을까 | 정적 타입 | 14.3 |
| `new`로 숨긴 메서드 중 무엇을 부를까 | 정적 타입 | 14.3 |
| `virtual` 메서드 중 무엇을 부를까 | **런타임 타입** | 14.2, 14.9 |
| 다운캐스트가 성공할까 | **런타임 타입** | 14.7 |
| `is` / `as`의 결과 | **런타임 타입** | 14.7 |
| `GetType()`의 결과 | **런타임 타입** | 15.4 |

## 14.2 다형성과 가상 함수 멤버

### 참조는 다형적이다

`x` 타입 변수는 `x`를 상속한 어떤 타입의 객체든 가리킬 수 있다. 이것이 **다형성**(polymorphism)의 출발점이다.

```csharp
public static void Display(Asset asset)
{
    Console.WriteLine(asset.Name);
}

Stock msft = new Stock { Name = "MSFT" };
House mansion = new House { Name = "Mansion" };

Display(msft);      // OK — Stock은 Asset이다
Display(mansion);   // OK — House도 Asset이다
```

`Display`는 `Asset`만 받도록 선언됐지만 `Stock`도 `House`도 받는다. 파생 클래스가 기반 클래스의 모든 기능을 갖고 있기 때문이다.

역방향은 성립하지 않는다.

```csharp
public static void Display(House house)
{
    Console.WriteLine(house.Mortgage);
}

Display(new Asset());   // 컴파일 오류 — Asset은 House가 아니다
```

`Asset`에는 `Mortgage`가 없으므로 `Display`가 요구하는 계약을 만족하지 못한다.

### 가상 함수 멤버

여기까지는 "기반 타입 변수에 파생 객체를 담을 수 있다"는 정도다. 진짜 다형성은 **같은 호출이 객체에 따라 다른 코드를 실행하는 것**이다. 그 장치가 `virtual`이다.

```csharp
public class Asset
{
    public string Name;
    public virtual decimal Liability => 0;      // 식 본문 프로퍼티(13.8절)
}

public class Stock : Asset
{
    public long SharesOwned;
    // Liability를 재정의하지 않는다 — 기본값 0을 그대로 쓴다
}

public class House : Asset
{
    public decimal Mortgage;
    public override decimal Liability => Mortgage;
}
```

`Liability => 0`은 `{ get { return 0; } }`의 축약이다(13.8절).

```csharp
House mansion = new House { Name = "McMansion", Mortgage = 250000 };
Asset a = mansion;

Console.WriteLine(mansion.Liability);   // 250000
Console.WriteLine(a.Liability);         // 250000  ← 정적 타입은 Asset인데 House의 코드가 돈다
```

두 번째 줄이 핵심이다. `a`의 정적 타입은 `Asset`이므로 컴파일러는 `Asset.Liability`를 호출하는 코드를 만든다. 그런데 실행되는 것은 `House.Liability`다. 이 "컴파일러가 지목한 것과 실행되는 것이 다르다"가 가상 디스패치이며, 어떻게 그렇게 되는지는 14.9절에서 메서드 테이블 수준으로 판다.

### 가상으로 만들 수 있는 것

메서드만이 아니다.

| 멤버 | `virtual` 가능 | 비고 |
|---|---|---|
| 메서드 | 가능 | 가장 흔한 경우 |
| 프로퍼티 | 가능 | `get`/`set` 접근자 쌍 전체가 함께 가상이 된다 |
| 인덱서 | 가능 | 프로퍼티와 같은 취급(13.9절) |
| 이벤트 | 가능 | `add`/`remove` 접근자가 가상이 된다(27장) |
| 필드 | **불가** | 필드는 코드가 아니라 저장소다 |
| 상수 | **불가** | 컴파일 타임 값이다 |
| 생성자 | **불가** | 생성자는 슬롯을 갖지 않는다 |
| 정적 멤버 | **불가** | 클래스에서는 불가. 인터페이스의 정적 추상 멤버는 18.8절 |

프로퍼티가 가상이 될 수 있는 이유는 프로퍼티가 사실 메서드 쌍이기 때문이다(13.8절). `virtual decimal Liability`는 IL에서 `virtual instance decimal get_Liability()`가 된다.

### 재정의의 계약

`virtual` 멤버를 `override`할 때 지켜야 하는 것이 있다.

| 항목 | 규칙 |
|---|---|
| 이름 | 동일해야 한다 |
| 매개변수 목록 | 타입·순서·전달 방식(`ref`/`out`/`in`)까지 동일해야 한다 |
| 반환 타입 | 동일해야 한다. **단 C# 9부터 더 파생된 타입 허용**(14.11절) |
| 접근성 | 동일해야 한다 |
| `static`/`instance` 구분 | 동일해야 한다 |

접근성 규칙에는 예외가 하나 있다. 기반 멤버가 `protected internal`이고 파생 클래스가 **다른 어셈블리**에 있다면, 재정의 멤버는 `protected`여야 한다. 그 어셈블리에서는 `internal` 부분이 의미를 잃기 때문이다.

> **⚠️ 접근성을 넓히거나 좁힐 수 없다**
>
> `protected virtual void Foo()`를 `public override void Foo()`로 재정의할 수 없다. 접근성을 바꾸고 싶다면 재정의가 아니라 **별도의 공개 래퍼**를 만들어야 한다.
>
> ```csharp
> public class Base
> {
>     protected virtual void Core() { }
> }
>
> public class Derived : Base
> {
>     protected override void Core() { /* 재정의는 protected 그대로 */ }
>     public void Run() => Core();            // 공개는 별도 멤버로
> }
> ```
>
> CLR 자체는 재정의 시 접근성을 넓히는 것을 허용한다(더 접근 가능하게는 되고, 덜 접근 가능하게는 안 된다). 좁히는 것만 막는다. C#이 더 엄격한 규칙을 강제하는 쪽이다.

### 컴파일 결과 — IL 플래그

`virtual`과 `override`가 IL에서 어떤 플래그가 되는지가 이 장의 뼈대다. 먼저 기반 클래스 쪽이다.

```il
.class public auto ansi beforefieldinit Asset
       extends [System.Runtime]System.Object
{
  .method public hidebysig specialname newslot virtual
          instance valuetype [System.Runtime]System.Decimal
          get_Liability() cil managed
  {
    .maxstack  8
    IL_0000:  ldsfld     valuetype [System.Runtime]System.Decimal
                         [System.Runtime]System.Decimal::Zero
    IL_0005:  ret
  }

  .property instance valuetype [System.Runtime]System.Decimal Liability()
  {
    .get instance valuetype [System.Runtime]System.Decimal Asset::get_Liability()
  }
}
```

파생 클래스 쪽이다.

```il
.class public auto ansi beforefieldinit House
       extends Asset
{
  .method public hidebysig specialname virtual
          instance valuetype [System.Runtime]System.Decimal
          get_Liability() cil managed
  {
    .maxstack  8
    IL_0000:  ldarg.0
    IL_0001:  ldfld      valuetype [System.Runtime]System.Decimal House::Mortgage
    IL_0006:  ret
  }
}
```

두 IL의 차이는 **`newslot` 하나**다.

| C# 선언 | IL 메서드 플래그 | 의미 |
|---|---|---|
| `public void Foo()` | `public hidebysig instance` | 비가상 인스턴스 메서드 |
| `public virtual void Foo()` | `public hidebysig newslot virtual instance` | 새 슬롯을 만들고 그 슬롯을 가상으로 |
| `public override void Foo()` | `public hidebysig virtual instance` | 기존 슬롯을 **덮어쓴다**(newslot 없음) |
| `public sealed override void Foo()` | `public hidebysig virtual final instance` | 덮어쓰되 더 이상 못 덮게 |
| `public abstract void Foo();` | `public hidebysig newslot abstract virtual instance` | 새 슬롯을 만들되 구현 없음 |
| `public new void Foo()` | `public hidebysig instance` | 비가상. 기반과 아무 관계 없음 |
| `public new virtual void Foo()` | `public hidebysig newslot virtual instance` | **새 슬롯을 또 만든다**(핵심) |

`newslot`은 "메서드 테이블에 이 메서드용 새 슬롯을 할당하라"는 뜻이고, `newslot`이 없는 `virtual`은 "기반 타입이 이미 만들어 둔 슬롯을 재사용하라"는 뜻이다. 이 한 비트가 `virtual`과 `override`의 차이 전부이고, 뒤에 나올 `new` 한정자의 정체이기도 하다.

> **📌 `hidebysig`는 무슨 뜻인가**
>
> 모든 C# 메서드에 붙는 `hidebysig`(hide by signature)는 "이 메서드는 **시그니처가 같은** 기반 멤버만 숨긴다"는 뜻이다. 반대 개념은 이름만 같으면 전부 숨기는 hide-by-name으로, 옛 Visual Basic 계열이 그렇게 동작했다. C#은 항상 `hidebysig`를 붙이므로 실질적으로 이 플래그를 신경 쓸 일은 없다. 다만 IL을 읽을 때 눈에 걸리므로 알아 두면 좋다.

> **💡 `virtual`은 기본값이 아니어야 한다**
>
> C#에서 메서드는 기본이 비가상이고, 가상으로 만들려면 명시해야 한다. Java와 반대다. 이 기본값은 의도된 것이다. 메서드를 `virtual`로 만드는 순간 그 메서드의 동작에 대한 통제권을 파생 클래스에 넘기는 것이고, 그 계약은 되돌릴 수 없다(78.13절). 성능도 대가를 치른다 — 가상 메서드는 JIT이 인라이닝하기 어렵다(55.4절).
>
> 실무 기준은 이렇다. **"이 메서드를 파생 클래스가 바꿔야 하는 시나리오를 지금 종이에 쓸 수 있는가?"** 쓸 수 있으면 `virtual`, 아니면 비가상이다. "언젠가 필요할지도 모르니까"는 근거가 아니다.

## 14.3 `virtual` / `override` / `new` — 세 가지 다른 의도

### 우연히 이름이 겹칠 때

기반 클래스와 파생 클래스가 이름이 같은 멤버를 정의할 수 있다.

```csharp
public class A { public int Counter = 1; }
public class B : A { public int Counter = 2; }
```

`B`의 `Counter`가 `A`의 `Counter`를 **숨긴다**(hide). 이 상황은 대개 의도된 것이 아니다. 파생 타입에 멤버를 추가한 뒤, 나중에 기반 타입에 같은 이름의 멤버가 추가되면서 생긴다. 그래서 컴파일러는 경고를 낸다.

```text
warning CS0108: 'B.Counter' hides inherited member 'A.Counter'.
Use the new keyword if hiding was intended.
```

경고를 낸 뒤 컴파일러는 다음 규칙으로 모호성을 해소한다.

- 컴파일 시점에 `A` 타입으로 참조하면 → `A.Counter`에 바인딩
- 컴파일 시점에 `B` 타입으로 참조하면 → `B.Counter`에 바인딩

즉 **정적 타입**으로 결정한다.

숨기는 것이 의도라면 `new` 한정자를 붙인다.

```csharp
public class A { public int Counter = 1; }
public class B : A { public new int Counter = 2; }
```

`new` 한정자가 하는 일은 **경고를 끄는 것뿐**이다. 동작은 바뀌지 않는다. 컴파일러와 다른 개발자에게 "이 중복은 실수가 아니다"라고 알리는 신호다.

> **📌 `new`는 두 가지 뜻으로 쓰인다**
>
> `new Foo()`의 `new`(객체 생성 연산자)와 `public new void Foo()`의 `new`(멤버 한정자)는 완전히 다른 기능이다. C#이 키워드를 재사용한 것뿐이다. 이 장에서 그냥 "`new`"라고 쓰면 한정자 쪽을 뜻한다.

### 결정적 비교 — `new`와 `override`

이제 이 장에서 가장 중요한 코드를 본다. 같은 호출이 정적 타입에 따라 다른 메서드를 부른다는 것을 증명하는 예제다.

```csharp
public class BaseClass
{
    public virtual void Foo() { Console.WriteLine("BaseClass.Foo"); }
}

public class Overrider : BaseClass
{
    public override void Foo() { Console.WriteLine("Overrider.Foo"); }
}

public class Hider : BaseClass
{
    public new void Foo() { Console.WriteLine("Hider.Foo"); }
}
```

`Overrider`는 재정의하고, `Hider`는 숨긴다. 이제 각각을 두 가지 정적 타입으로 호출한다.

```csharp
Overrider over = new Overrider();
BaseClass b1 = over;
over.Foo();     // Overrider.Foo
b1.Foo();       // Overrider.Foo   ← 같다

Hider h = new Hider();
BaseClass b2 = h;
h.Foo();        // Hider.Foo
b2.Foo();       // BaseClass.Foo   ← 다르다!
```

마지막 줄이 결정적이다. `b2`와 `h`는 **완전히 같은 객체**를 가리킨다. 그런데 `h.Foo()`와 `b2.Foo()`가 서로 다른 메서드를 실행한다. 객체가 아니라 **변수의 정적 타입**이 결정한 것이다.

### 컴파일 결과가 증명한다

왜 이렇게 되는지는 IL을 보면 한 줄로 끝난다.

```il
// h.Foo();  — h의 정적 타입은 Hider
IL_0010:  ldloc.2
IL_0011:  callvirt   instance void Hider::Foo()

// b2.Foo(); — b2의 정적 타입은 BaseClass
IL_0017:  ldloc.3
IL_0018:  callvirt   instance void BaseClass::Foo()
```

옵코드는 둘 다 `callvirt`로 같다. 다른 것은 **메서드 토큰**이다. 컴파일러가 정적 타입을 보고 `Hider::Foo`와 `BaseClass::Foo`라는 서로 다른 대상을 IL에 박아 넣었다.

여기서 `Hider::Foo`는 `newslot`이 없는 비가상 메서드이므로 `callvirt`가 그냥 그 메서드를 부른다(널 검사만 추가로 한다). `BaseClass::Foo`는 가상 메서드이지만, `Hider`가 이 슬롯을 **덮어쓰지 않았으므로** 슬롯에는 여전히 `BaseClass.Foo`의 코드가 들어 있다. 그래서 `BaseClass.Foo`가 실행된다.

`Overrider`의 경우와 비교하면 차이가 선명하다.

```il
// b1.Foo(); — b1의 정적 타입은 BaseClass
IL_0009:  ldloc.1
IL_000a:  callvirt   instance void BaseClass::Foo()
```

IL은 `b2.Foo()`와 똑같이 `BaseClass::Foo`를 지목한다. 그런데 `Overrider`는 그 슬롯을 자기 코드로 덮어썼으므로, 런타임에 슬롯을 조회하면 `Overrider.Foo`가 나온다. **IL은 같고 메서드 테이블이 다르다.**

### 세 한정자의 의도

| 한정자 | 기반 멤버와의 관계 | 슬롯 | 호출 결정 | 언제 쓰나 |
|---|---|---|---|---|
| `virtual` (기반 쪽) | — | 새 슬롯 생성 | 런타임 타입 | 파생이 바꿀 여지를 열어 둘 때 |
| `override` (파생 쪽) | **있다** — 같은 의미의 특수화 | 기존 슬롯 재사용 | 런타임 타입 | 기반이 연 문으로 들어갈 때 |
| `new` (파생 쪽) | **없다** — 이름만 우연히 같음 | 관여 안 함(비가상) 또는 새 슬롯(`new virtual`) | 정적 타입 | 기반이 문을 열지 않았는데 이름이 겹칠 때 |
| `abstract` (기반 쪽) | — | 새 슬롯 생성(구현 없음) | 런타임 타입 | 파생이 반드시 채워야 할 때 |
| `sealed override` (파생 쪽) | 있다 | 기존 슬롯 재사용 + 잠금 | 런타임 타입 | 여기서 계층을 끊을 때 |

`new`와 `override`는 서로 배타적이다. 같은 멤버에 둘 다 붙일 수 없고, 붙이면 "override로 표시된 멤버는 new나 virtual로 표시할 수 없다"는 컴파일 오류가 난다.

> **⚠️ `new`로 숨긴 멤버는 다형성이 없다**
>
> `Hider.Foo`는 다형적이지 않다. `List<BaseClass>`에 `Hider` 객체를 담고 순회하며 `Foo()`를 부르면 전부 `BaseClass.Foo`가 실행된다. "파생 클래스에서 동작을 바꾸고 싶다"가 목적이라면 `new`는 **틀린 도구**다. 기반 클래스가 `virtual`을 제공하지 않는다면, 상속 대신 포함·위임을 고려하는 편이 낫다(14.12절).

### 숨겨진 멤버에 접근하기

`new`로 숨긴 경우에도 기반 쪽 멤버에 접근할 수 있다. 기반 타입으로 캐스트하면 된다.

```csharp
Hider h = new Hider();
h.Foo();                // Hider.Foo
((BaseClass)h).Foo();   // BaseClass.Foo
```

파생 클래스 **내부**에서라면 `base` 키워드가 더 자연스럽다(14.6절).

```csharp
public class Hider : BaseClass
{
    public new void Foo()
    {
        Console.WriteLine("Hider.Foo");
        base.Foo();                 // BaseClass.Foo
    }
}
```

### 왜 C#은 `override`를 기본값으로 하지 않았는가

C++은 시그니처가 맞으면 자동으로 재정의된다. C#은 명시적으로 `override`를 써야 한다. 이 설계의 이유는 **버전 관리**다.

CompanyA가 `Phone` 클래스를 배포했다고 하자.

```csharp
namespace CompanyA
{
    public class Phone
    {
        public void Dial()
        {
            Console.WriteLine("Phone.Dial");
        }
    }
}
```

CompanyB가 이것을 상속해서 `BetterPhone`을 만든다.

```csharp
namespace CompanyB
{
    public class BetterPhone : CompanyA.Phone
    {
        public new void Dial()
        {
            Console.WriteLine("BetterPhone.Dial");
            EstablishConnection();
            base.Dial();
        }

        protected virtual void EstablishConnection()
        {
            Console.WriteLine("BetterPhone.EstablishConnection");
        }
    }
}
```

여기까지는 잘 돈다. 그런데 CompanyA가 다음 버전에서 **똑같은 이름의 메서드**를 추가한다.

```csharp
namespace CompanyA
{
    public class Phone
    {
        public void Dial()
        {
            Console.WriteLine("Phone.Dial");
            EstablishConnection();
        }

        protected virtual void EstablishConnection()
        {
            Console.WriteLine("Phone.EstablishConnection");
        }
    }
}
```

이제 CompanyB가 재컴파일하면 컴파일러가 경고한다.

```text
warning CS0114: 'CompanyB.BetterPhone.EstablishConnection()' hides inherited member
'CompanyA.Phone.EstablishConnection()'. To make the current member override that
implementation, add the override keyword. Otherwise, add the new keyword.
```

CompanyB의 `EstablishConnection`은 CompanyA의 그것과 **아무 관계가 없다**. 우연히 이름이 같을 뿐이다. C++처럼 자동으로 재정의됐다면 `Phone.Dial`이 `BetterPhone.EstablishConnection`을 호출하게 되어 의미가 조용히 깨졌을 것이다. C#은 개발자에게 명시적 선택을 강요함으로써 이 사고를 막는다. `new`를 붙이면 관계 없음이 메타데이터에 기록되고, 실행 결과는 이렇게 된다.

```text
BetterPhone.Dial
BetterPhone.EstablishConnection
Phone.Dial
Phone.EstablishConnection
```

마지막 줄이 핵심이다. `Phone.Dial`이 호출한 `EstablishConnection`은 `Phone` 자신의 것이다. `BetterPhone`의 것이 `new`로 표시되어 별도 슬롯을 차지했기 때문이다.

반대로 CompanyB가 "CompanyA의 새 설계가 마음에 든다"고 판단하면, 자기 `Dial`을 지우고 `EstablishConnection`을 `override`로 바꾼다.

```csharp
namespace CompanyB
{
    public class BetterPhone : CompanyA.Phone
    {
        protected override void EstablishConnection()
        {
            Console.WriteLine("BetterPhone.EstablishConnection");
        }
    }
}
```

이제 출력은 두 줄이다.

```text
Phone.Dial
BetterPhone.EstablishConnection
```

이 시나리오 전체가 `new` 한정자가 존재하는 유일한 정당한 이유다. 실무 판단 기준은 79.8절에서 다룬다.

> **💡 `new`는 "기반 클래스가 변했을 때의 응급 처치"다**
>
> 새 코드를 쓰면서 `new`를 타이핑하고 있다면 설계를 다시 보라. 이름을 바꾸는 것이 거의 항상 낫다. `new`가 정당한 경우는 딱 하나 — **내가 통제하지 않는 기반 클래스가 나중에 내 멤버와 이름이 겹치는 멤버를 추가했고, 내 멤버의 이름을 바꾸면 내 API 소비자가 깨지는 상황**이다.

## 14.4 추상 클래스와 추상 멤버

### 인스턴스화할 수 없는 클래스

`abstract`로 선언된 클래스는 직접 인스턴스를 만들 수 없다. 구체(concrete) 파생 클래스만 인스턴스화된다.

```csharp
public abstract class Employee
{
    public string Name { get; set; }
    public int Id { get; set; }
}

// Employee e = new Employee();   // 컴파일 오류
Employee m = new Manager();       // OK
```

왜 이런 것이 필요한가. `Employee` 하나만 두고 보면 "직원"이라는 개념은 있지만 실체가 없다. 누군가 "저는 직원입니다"라고 하면 "어떤 직원이요?"라고 되묻게 된다. 이런 타입은 **공통 멤버를 모아 두는 장소**로만 의미가 있고, 직접 만들어지면 곤란하다.

추상 클래스도 생성자를 가질 수 있고, 실제로 흔하다. 직접 호출되지는 않지만 파생 클래스가 생성될 때 `base(...)`를 통해 간접 호출된다(14.6절). 추상 클래스가 메모리에 조립되지 않는 것이 아니라, **단독으로** 조립되지 않을 뿐이다.

```csharp
public abstract class Shape
{
    protected Shape(string name = "NoName")   // protected 생성자 — 파생만 호출 가능
    {
        PetName = name;
    }

    public string PetName { get; set; }
}
```

> **📌 추상 클래스의 생성자는 `protected`가 관용구다**
>
> `public`으로 둬도 컴파일러가 막지는 않는다. 어차피 외부에서 `new`를 못 하기 때문이다. 하지만 `protected`로 두면 "이 생성자는 파생 클래스만 쓴다"는 의도가 시그니처에 드러난다. Roslyn 분석기도 추상 타입의 `public` 생성자를 지적한다.

### 추상 멤버

추상 클래스는 **추상 멤버**를 가질 수 있다. 추상 멤버는 가상 멤버와 같지만 기본 구현이 없다. 파생 클래스가 반드시 구현해야 하며, 하지 않으면 그 파생 클래스도 `abstract`여야 한다.

```csharp
public abstract class Asset
{
    public string Name;
    public abstract decimal NetValue { get; }   // 본문이 없다
}

public class Stock : Asset
{
    public long SharesOwned;
    public decimal CurrentPrice;

    // 가상 메서드와 똑같이 override로 구현한다
    public override decimal NetValue => CurrentPrice * SharesOwned;
}
```

추상 멤버는 이름·반환 타입·매개변수 목록만 정의한다. "나에게는 인자 없이 아무것도 반환하지 않는 `Draw`라는 메서드가 있다. 나를 상속하면 알아서 채워라"라는 순수한 프로토콜이다.

### `virtual`과 `abstract`, 어느 쪽인가

`Shape` 계층으로 차이를 본다. 먼저 `virtual`로 기본 구현을 주는 경우다.

```csharp
public abstract class Shape
{
    protected Shape(string name = "NoName") => PetName = name;
    public string PetName { get; set; }

    public virtual void Draw()
    {
        Console.WriteLine("Inside Shape.Draw()");
    }
}

public class Circle : Shape          // Draw를 재정의하지 않는다
{
    public Circle() { }
    public Circle(string name) : base(name) { }
}

public class Hexagon : Shape         // Draw를 재정의한다
{
    public Hexagon() { }
    public Hexagon(string name) : base(name) { }
    public override void Draw() => Console.WriteLine($"Drawing {PetName} the Hexagon");
}
```

```csharp
Hexagon hex = new Hexagon("Beth");
hex.Draw();                          // Drawing Beth the Hexagon

Circle cir = new Circle("Cindy");
cir.Draw();                          // Inside Shape.Draw()   ← 무의미한 출력
```

`Circle`은 재정의를 깜빡했고, 컴파일러는 아무 말도 하지 않았다. 기본 구현이 있으니 문법적으로 완전하기 때문이다. 이것이 `virtual`의 위험이다 — **재정의를 잊어도 컴파일된다.**

`Draw`를 `abstract`로 바꾸면 컴파일러가 강제한다.

```csharp
public abstract class Shape
{
    protected Shape(string name = "NoName") => PetName = name;
    public string PetName { get; set; }

    public abstract void Draw();     // 구현 없음 — 파생이 반드시 채운다
}

public class Circle : Shape
{
    public Circle() { }
    public Circle(string name) : base(name) { }
    public override void Draw() => Console.WriteLine($"Drawing {PetName} the Circle");
}
```

이제 `Circle`이 `Draw`를 빠뜨리면 컴파일 오류다. 이 강제가 다형성을 신뢰할 수 있게 만든다.

```csharp
Shape[] myShapes =
{
    new Hexagon(), new Circle(), new Hexagon("Mick"),
    new Circle("Beth"), new Hexagon("Linda")
};

foreach (Shape s in myShapes)
{
    s.Draw();       // 각자 자기 방식대로 그린다
}
```

```text
Drawing NoName the Hexagon
Drawing NoName the Circle
Drawing Mick the Hexagon
Drawing Beth the Circle
Drawing Linda the Hexagon
```

`foreach` 안의 코드는 `Shape`가 무엇인지 전혀 모른다. `Triangle`이나 `Square`를 추가해도 이 루프는 한 글자도 바뀌지 않는다. 추상 기반 클래스가 정의한 **다형적 인터페이스**(추상 멤버와 가상 멤버의 집합) 덕분이다.

| 판단 | `virtual` | `abstract` |
|---|---|---|
| 기본 구현 | 있다 | 없다 |
| 파생이 재정의하지 않으면 | 기본 구현이 쓰인다 | **컴파일 오류** |
| 기반 클래스가 인스턴스화 가능한가 | 가능(다른 이유로 `abstract`일 수는 있음) | 반드시 `abstract` |
| 언제 쓰나 | 대다수가 쓸 합리적 기본값이 존재할 때 | 기본값이 존재하지 않거나, 기본값을 쓰면 버그일 때 |
| `base.X()` 호출 | 의미 있음 | **불가**(호출할 구현이 없다) |

> **⚠️ 추상 멤버에는 `base`로 접근할 수 없다**
>
> ```csharp
> public class Circle : Shape
> {
>     public override void Draw()
>     {
>         base.Draw();      // 컴파일 오류: Shape.Draw에는 구현이 없다
>     }
> }
> ```
>
> IDE가 `override`를 자동 생성할 때 `base.X()` 줄을 넣어 주는데, 추상 멤버라면 이 줄을 지워야 한다.

### 컴파일 결과

```il
.class public abstract auto ansi beforefieldinit Shape
       extends [System.Runtime]System.Object
{
  .method public hidebysig newslot abstract virtual
          instance void  Draw() cil managed
  {
  } // end of method Shape::Draw

  .method family hidebysig specialname rtspecialname
          instance void  .ctor(string name) cil managed
  {
    // ...
  }
}
```

세 가지를 확인할 수 있다.

1. 클래스에 `abstract` 플래그가 붙었다. CLR이 `newobj`를 거부하는 근거가 이 플래그다.
2. `Draw`는 `newslot abstract virtual`이고 **본문이 비어 있다**. 명령어가 하나도 없다.
3. `protected` 생성자는 IL에서 `family`다. IL 어셈블리 언어는 `protected`를 `family`라고 부른다.

`abstract` 메서드는 메서드 테이블에서 슬롯을 차지하지만, 그 슬롯에는 코드 주소 대신 "구현되지 않음" 표시가 들어간다. 만약 어떤 경로로든 그 슬롯이 호출되면 CLR은 예외를 던진다. 정상적인 C# 코드로는 도달할 수 없고, 리플렉션 방출(58장)이나 손으로 쓴 IL로만 만들 수 있는 상황이다.

> **📌 `static class`도 IL에서는 `abstract sealed`다**
>
> 13.11절에서 본 정적 클래스는 IL에서 `abstract`와 `sealed`가 **동시에** 붙는다. "인스턴스화할 수 없고 상속할 수도 없다"는 뜻이다. C#에서 이 조합을 직접 쓰는 것은 금지되어 있고, `static` 키워드로만 만들 수 있다.

### 추상 클래스와 인터페이스, 언제 무엇인가

둘 다 "구현을 강제하는 계약"이라는 점에서 겹친다. C# 8부터 인터페이스도 기본 구현을 가질 수 있게 되면서(18.7절) 경계가 더 흐려졌다. 결정 기준은 이렇다.

| 기준 | 추상 클래스 | 인터페이스 |
|---|---|---|
| 상속 개수 | 하나만 | 여럿 가능 |
| 상태(필드) 보유 | **가능** | 불가(정적 필드 제외) |
| 멤버 접근성 | `private`/`protected`/`internal` 자유 | 사실상 공개(또는 인터페이스 수준) |
| 생성자 | 가질 수 있다 | 불가 |
| 구현 강제 | 추상 멤버로 | 모든 멤버(기본 구현 없는 것) |
| 직렬화 | 대체로 문제없음 | 인터페이스 대상 직렬화는 대개 동작하지 않는다 |
| 버전 추가 | 가상 멤버 추가는 안전 | 기본 구현 없는 멤버 추가는 파괴적 변경 |
| 값 타입이 채택 | 불가(구조체는 상속 불가) | 가능(단 박싱 주의, 18.6절) |

`System.IO.Stream`이 좋은 사례다. `Stream`은 추상 클래스이지 인터페이스가 아니다. 위치·길이 같은 **상태**를 다루고, `protected` 헬퍼를 제공하며, 접근성 제어가 필요하기 때문이다. 반대로 `IDisposable`은 상태가 없고 값 타입도 채택할 수 있어야 하므로 인터페이스다.

실무 기준을 한 줄로 줄이면 이렇다. **"구현을 공유하고 싶으면 추상 클래스, 능력을 선언하고 싶으면 인터페이스."** 결정표 전체와 상세 논거는 18.12절에 있다.

## 14.5 `sealed`로 봉인하기 — 클래스와 멤버

### 클래스 봉인

`sealed` 클래스는 상속될 수 없다.

```csharp
public sealed class PtSalesPerson : SalesPerson
{
    public PtSalesPerson(string fullName, int age, int empId,
                         float currPay, string ssn, int numbOfSales)
        : base(fullName, age, empId, currPay, ssn, numbOfSales)
    {
    }
}

// public class Foo : PtSalesPerson { }   // 컴파일 오류
```

계층의 어떤 가지를 "여기서 끝"이라고 못 박는 장치다. BCL에서 가장 유명한 봉인 클래스는 `System.String`이다. 문자열 내부에는 극단적인 최적화가 들어 있어서 상속이 허용되면 그 가정들이 깨진다.

```il
.class public auto ansi sealed beforefieldinit PtSalesPerson
       extends Employees.SalesPerson
{
  // ...
}
```

### 멤버 봉인

클래스 전체가 아니라 특정 재정의만 잠글 수도 있다.

```csharp
public class Singer
{
    public virtual void Sing() => Console.WriteLine("Singing...");
}

public class LadyGaga : Singer
{
    public sealed override void Sing() => Console.WriteLine("Singing with style...");
}

public class GagaClone : LadyGaga
{
    // public override void Sing() { }   // 컴파일 오류: 봉인된 멤버는 재정의 불가
}
```

`Asset`/`House` 예제라면 이렇게 된다.

```csharp
public sealed override decimal Liability { get { return Mortgage; } }
```

> **⚠️ `sealed`는 `override`와만 함께 쓸 수 있다**
>
> ```csharp
> public sealed void Foo() { }              // 컴파일 오류
> public sealed virtual void Foo() { }      // 컴파일 오류
> public sealed override void Foo() { }     // OK
> ```
>
> 애초에 가상이 아닌 메서드는 재정의될 수 없으므로 봉인할 것이 없다. `sealed`는 "이미 열려 있는 것을 다시 닫는" 연산이다.

> **⚠️ 멤버 봉인은 숨기는 것을 막지 못한다**
>
> `sealed override void Sing()`은 파생 클래스가 `override`하는 것만 막는다. `new`로 **숨기는** 것은 여전히 가능하다.
>
> ```csharp
> public class GagaClone : LadyGaga
> {
>     public new void Sing() => Console.WriteLine("Lip syncing...");
> }
>
> GagaClone c = new GagaClone();
> c.Sing();                 // Lip syncing...
> ((Singer)c).Sing();       // Singing with style...   ← 봉인된 구현은 그대로다
> ```
>
> 즉 `sealed`가 지키는 것은 "가상 슬롯의 내용"이지 "이름"이 아니다. 슬롯은 안전하므로 기반 클래스를 통한 호출은 계약을 지킨다. 그것으로 충분하다고 보는 것이 이 설계의 입장이다.

### 성능 — 역가상화

가상 호출이 비가상 호출보다 느린 이유는 런타임에 객체의 타입을 조회해서 어느 구현을 부를지 정해야 하기 때문이다. 그런데 JIT이 "이 타입은 봉인되어 있으니 파생 클래스가 있을 수 없다"는 것을 알면, 가상 호출을 **직접 호출로 바꿔치기**할 수 있다. 이것이 **역가상화**(devirtualization)다.

```csharp
public sealed class Point
{
    private int _x, _y;
    public Point(int x, int y) { _x = x; _y = y; }

    public override string ToString() => $"({_x}, {_y})";
}

Point p = new Point(3, 4);
Console.WriteLine(p.ToString());
```

C# 컴파일러는 여기서도 `callvirt`를 낸다. 하지만 JIT은 `p`의 정적 타입이 `Point`이고 `Point`가 `sealed`라는 것을 알기 때문에, `Point.ToString`을 비가상으로 호출하는 코드를 만든다. 그러면 가상 디스패치 비용이 사라질 뿐 아니라 **인라이닝의 문이 열린다**. 인라이닝이 가능해지면 뒤이은 최적화(상수 전파, 경계 검사 제거)가 연쇄적으로 걸린다.

역가상화는 `sealed`가 없어도 일어날 수 있다. 런타임이 "현재 로드된 타입 중 이 클래스를 상속한 것이 없다"는 사실이나 프로파일 정보를 활용하는 가드된 역가상화(GDV)가 있다. 그 메커니즘 전체는 55.5절에서 다룬다. 다만 `sealed`는 **JIT이 아무 조사 없이 즉시 확정할 수 있는** 가장 값싼 근거다.

> **⚠️ `sealed`가 자동으로 빨라지는 마법은 아니다**
>
> 인터넷에는 "클래스에 `sealed`를 붙이면 성능이 오른다"는 조언이 돌아다닌다. 절반만 맞다. 효과가 나오는 조건은 **호출 지점의 정적 타입이 그 봉인 타입일 때**다.
>
> ```csharp
> Point p = new Point(3, 4);
> p.ToString();          // 역가상화 가능 — 정적 타입이 sealed Point
>
> object o = new Point(3, 4);
> o.ToString();          // 역가상화 불가 — 정적 타입이 object
> ```
>
> 두 번째 호출은 `Point`가 봉인이든 아니든 상관없다. 컴파일러가 아는 것은 `object`뿐이다. 인터페이스 변수를 통한 호출도 마찬가지다.

### 설계 관점 — 봉인이 기본값이어야 하는가

봉인 클래스가 봉인되지 않은 클래스보다 나은 이유는 셋이다.

| 이유 | 내용 |
|---|---|
| **버전 관리** | 봉인 클래스는 나중에 봉인을 풀 수 있다. 그러나 한 번 열린 클래스는 절대 다시 봉인할 수 없다 — 모든 파생 클래스가 깨진다 |
| **성능** | 위에서 본 역가상화 |
| **보안과 예측 가능성** | 클래스가 열려 있으면 파생 클래스가 `protected` 상태를 조작할 수 있고, 가상 메서드를 재정의해 기반 구현을 건너뛸 수 있다. 가상 멤버를 만드는 것은 자기 동작에 대한 통제권을 일부 포기하는 일이다 |

버전 관리 논거가 가장 강하다. **봉인 → 개방은 호환되는 변경, 개방 → 봉인은 파괴적 변경**이라는 비대칭 때문이다. 봉인되지 않은 클래스가 봉인되지 않은 가상 메서드를 갖고 있으면, 다음 버전에서 가상 메서드 호출 순서까지 유지해야 한다. 파생 클래스가 그 순서에 의존하고 있을 수 있기 때문이다(78.14절).

봉인의 대가는 사용자의 불편이다. 기존 타입에 상태나 헬퍼를 붙이고 싶은 사람이 막힌다. 다만 대안이 있다.

- 헬퍼 메서드 → 확장 메서드(23장)
- 객체에 상태 부착 → `ConditionalWeakTable`(34장)

> **💡 저자의 기본값**
>
> 새 클래스를 만들 때 나는 이렇게 한다.
>
> 1. **기본은 `sealed`.** 상속을 통한 특수화가 이 타입의 설계 목적일 때만 봉인을 푼다.
> 2. **기본은 `internal`.** 어셈블리 밖으로 노출할 이유가 생겼을 때만 `public`으로 올린다(C#의 기본값이 이미 `internal`이다).
> 3. **필드는 예외 없이 `private`.** `protected` 필드는 캡슐화를 깨는 가장 쉬운 경로다. `protected` **메서드**는 유용하고 안전하다.
> 4. "상속은 허용하되 특수화는 막고 싶다"면, 물려받은 가상 멤버들을 `sealed override`로 잠그는 방법이 있다.
>
> 반대 방향의 압력도 있다. 라이브러리 사용자가 테스트용 대역(mock)을 만들려면 가상 멤버나 인터페이스가 필요하고, EF Core 같은 ORM은 지연 로딩을 위해 프로퍼티가 `virtual`이기를 요구한다. 무엇을 열지는 **의식적으로** 정할 문제이지 기본값에 맡길 문제가 아니다.

## 14.6 `base` 키워드와 생성자 상속

### `base`의 두 가지 용도

`base`는 `this`와 비슷하지만 기반 클래스 쪽을 가리킨다. 하는 일은 두 가지다.

1. 재정의된(또는 숨겨진) 기반 함수 멤버에 접근한다.
2. 기반 클래스 생성자를 호출한다.

### 용도 1 — 기반 구현 호출

```csharp
public class House : Asset
{
    public decimal Mortgage;
    public override decimal Liability => base.Liability + Mortgage;
}
```

`base.Liability`는 `Asset`의 구현을 **비가상으로** 호출한다. 즉 객체의 런타임 타입이 무엇이든 상관없이 항상 `Asset`의 버전이 실행된다. 이것이 결정적으로 중요하다.

```csharp
public class SalesPerson : Employee
{
    public override void GiveBonus(float amount)
    {
        int salesBonus = SalesNumber switch
        {
            >= 0 and <= 100   => 10,
            >= 101 and <= 200 => 15,
            _                 => 20
        };

        base.GiveBonus(amount * salesBonus);   // 기반의 기본 동작을 재사용
    }
}
```

기반 동작을 완전히 다시 쓰지 않고, 인자를 가공한 뒤 기반에 위임하는 형태다. 재정의의 절반 이상이 이 모양이다.

### 컴파일 결과 — `base`는 `call`이다

```csharp
public class SomeClass
{
    public override string ToString()
    {
        return base.ToString();
    }
}
```

```il
.method public hidebysig virtual instance string
        ToString() cil managed
{
  .maxstack  8
  IL_0000:  ldarg.0
  IL_0001:  call       instance string [System.Runtime]System.Object::ToString()
  IL_0006:  ret
}
```

`callvirt`가 아니라 `call`이다. 만약 `callvirt`였다면 런타임 타입이 `SomeClass`이므로 `SomeClass.ToString`이 다시 호출되고, 스택이 넘칠 때까지 무한 재귀했을 것이다. `base` 호출이 반드시 비가상이어야 하는 이유가 이것이다. `call`과 `callvirt`의 차이는 14.9절에서 자세히 다룬다.

> **📌 `base`는 한 단계만 올라간다**
>
> `base.base.Foo()` 같은 문법은 없다. 조부모 클래스의 구현을 직접 부를 방법은 C#에 없다. 캐스트로도 안 된다 — `((GrandParent)this).Foo()`는 가상 디스패치를 거쳐 다시 자기 자신으로 돌아온다. 이것은 의도된 제약이다. 부모가 자기 부모의 구현을 어떻게 감쌌는지는 부모의 사정이고, 손자가 그 위를 뛰어넘으면 캡슐화가 무너진다.

### 용도 2 — 생성자 호출

생성자는 상속되지 않는다(14.1절). 파생 클래스는 노출하고 싶은 생성자를 직접 선언해야 하고, 그 안에서 `base` 키워드로 기반 생성자를 호출할 수 있다.

```csharp
public class Baseclass
{
    public int X;
    public Baseclass() { }
    public Baseclass(int x) => X = x;
}

public class Subclass : Baseclass
{
    public Subclass(int x) : base(x) { }
}
```

`base(...)`는 `this(...)`(13.3절)와 문법이 같고, 대상만 다르다. `this(...)`는 같은 클래스의 다른 생성자로, `base(...)`는 기반 클래스의 생성자로 간다.

실제 예제를 보자. `Manager`가 `Employee`를 상속한다.

```csharp
public class Employee
{
    public Employee(string name, int age, int id, float pay,
                    string empSsn, EmployeePayTypeEnum payType)
    {
        Name = name;
        Id = id;
        Age = age;
        Pay = pay;
        SocialSecurityNumber = empSsn;
        PayType = payType;
    }
    // 프로퍼티 생략
}

public class Manager : Employee
{
    public Manager(string fullName, int age, int empId,
                   float currPay, string ssn, int numbOfOpts)
        : base(fullName, age, empId, currPay, ssn, EmployeePayTypeEnum.Salaried)
    {
        StockOptions = numbOfOpts;      // 자기 몫만 처리한다
    }

    public int StockOptions { get; set; }
}
```

`base(...)`를 쓰지 않고 파생 생성자 본문에서 상속받은 프로퍼티에 하나씩 대입하는 방법도 문법적으로는 가능하다. 그러나 두 가지가 나쁘다.

1. 읽기 전용 프로퍼티(`SocialSecurityNumber` 같은)에는 대입할 수 없다. 생성자 밖에서는 쓸 수 없기 때문이다.
2. **비효율적이다.** `base(...)`를 생략하면 기반 클래스의 매개변수 없는 생성자가 어차피 호출되고, 그 위에 프로퍼티 대입이 여섯 번 더 얹힌다.

### 매개변수 없는 기반 생성자의 암묵적 호출

파생 생성자에서 `base`를 생략하면 컴파일러가 **기반 타입의 매개변수 없는 생성자**를 자동으로 호출한다.

```csharp
public class Baseclass
{
    public int X;
    public Baseclass() { X = 1; }
}

public class Subclass : Baseclass
{
    public Subclass() { Console.WriteLine(X); }   // 1
}
```

`Subclass`의 생성자에 `: base()`가 없지만 `X`는 1이다. 컴파일러가 넣어 줬기 때문이다.

기반 클래스에 접근 가능한 매개변수 없는 생성자가 **없으면** 파생 클래스는 `base`를 강제로 써야 한다.

```csharp
class Baseclass
{
    public Baseclass(int x, int y, int z, string s, DateTime d) { /* ... */ }
}

public class Subclass : Baseclass
{
    public Subclass(int x, int y, int z, string s, DateTime d)
        : base(x, y, z, s, d) { /* ... */ }
}
```

기반 클래스가 매개변수 여럿짜리 생성자만 갖고 있으면, 모든 파생 클래스가 그 매개변수를 전부 다시 받아 넘기는 짐을 진다. 계층이 깊어지면 이 짐이 누적된다.

> **💡 `required` 멤버가 이 짐을 덜어 준다 ※C# 11**
>
> 큰 계층에서 생성자 매개변수 릴레이가 견디기 힘들어지면, 생성자를 아예 포기하고 객체 초기화자에 의존하는 선택지가 있다. `required`(13.13절)가 그 안전망이다.
>
> ```csharp
> public class Asset
> {
>     public required string Name;
> }
>
> public class House : Asset { }      // 생성자를 하나도 안 만들어도 된다
>
> House h1 = new House { Name = "House" };   // OK
> House h2 = new House();                    // 컴파일 오류: Name이 설정되지 않음
> ```
>
> `Asset`이 매개변수 없는 생성자만 갖고 있으면 `House`는 생성자를 재현할 의무가 없다. 편의 생성자를 함께 두고 싶다면 `[SetsRequiredMembers]`를 붙이면 된다(13.13절).

### 실행 순서 — 가장 중요한 표

객체가 만들어질 때 초기화는 다음 순서로 일어난다.

1. **파생 → 기반 방향으로**
   1. 필드 초기화자가 실행된다.
   2. 기반 생성자 호출의 인자 식이 평가된다.
2. **기반 → 파생 방향으로**
   1. 생성자 본문이 실행된다.

```csharp
public class B
{
    int x = 1;                  // 3번째로 실행

    public B(int x)
    {
        // ...                  // 4번째로 실행
    }
}

public class D : B
{
    int y = 1;                  // 1번째로 실행

    public D(int x) : base(x + 1)   // 2번째로 실행 (인자 평가)
    {
        // ...                  // 5번째로 실행
    }
}
```

그림으로 보면 이렇다.

```text
  new D(10)
     │
     ├─ ①  D의 인스턴스 필드 초기화자        y = 1
     │
     ├─ ②  base(...)의 인자 식 평가          x + 1  →  11
     │        │
     │        └─→ B의 생성자로 진입
     │                │
     │                ├─ ③  B의 인스턴스 필드 초기화자   x = 1
     │                │
     │                └─ ④  B의 생성자 본문 실행
     │
     └─ ⑤  D의 생성자 본문 실행

   ── 필드 초기화자: 파생 → 기반 방향 (아래에서 위로)
   ── 생성자 본문  : 기반 → 파생 방향 (위에서 아래로)
```

이 **비대칭**이 이 장의 뒷부분(14.10절)에서 폭탄이 된다. 파생 클래스의 필드 초기화자는 기반 생성자보다 **먼저** 돌지만, 파생 클래스의 생성자 본문은 **나중에** 돈다.

컴파일 결과를 보면 이 순서가 IL에 그대로 박혀 있다.

```il
.method public hidebysig specialname rtspecialname
        instance void  .ctor(int32 x) cil managed
{
  .maxstack  8
  // ① D의 필드 초기화자
  IL_0000:  ldarg.0
  IL_0001:  ldc.i4.1
  IL_0002:  stfld      int32 D::y
  // ② base 인자 평가 후 ③④ 기반 생성자 호출
  IL_0007:  ldarg.0
  IL_0008:  ldarg.1
  IL_0009:  ldc.i4.1
  IL_000a:  add
  IL_000b:  call       instance void B::.ctor(int32)
  // ⑤ D의 생성자 본문
  IL_0010:  nop
  IL_0011:  ret
}
```

`stfld D::y`가 `call B::.ctor`보다 **앞에** 있다. 컴파일러가 필드 초기화자를 생성자 본문 맨 앞이 아니라 **`base` 호출 앞**에 배치한다.

> **⚠️ `this(...)`를 쓰는 생성자는 필드 초기화자를 실행하지 않는다**
>
> 13.4절에서 본 규칙이 상속과 만나면 더 헷갈린다. 한 객체 생성에서 필드 초기화자는 **정확히 한 번** 실행되어야 하므로, 생성자 체인의 **마지막 생성자**(즉 `base(...)`를 부르는 쪽)만 필드 초기화자를 실행한다.
>
> ```csharp
> public class D : B
> {
>     int y = 1;
>     public D() : this(0) { }        // 필드 초기화자 실행 안 함
>     public D(int x) : base(x) { }   // 여기서 y = 1이 실행됨
> }
> ```

### 기본 생성자와의 조합 ※C# 12

기본 생성자(primary constructor, 13.10절)를 쓰는 클래스도 상속할 수 있다.

```csharp
public class Baseclass(int x) { /* ... */ }
public class Subclass(int x, int y) : Baseclass(x) { /* ... */ }
```

`: Baseclass(x)` 부분이 `base(x)` 역할을 한다. 기반 클래스 이름과 인자가 한 자리에 붙어 있어서 처음 보면 "기반 클래스 지정"과 "기반 생성자 호출"이 섞인 것처럼 보이는데, 실제로 둘 다다. 다음 두 선언은 동등하다.

```csharp
public class Subclass(int x, int y) : Baseclass(x) { /* ... */ }

public class Subclass : Baseclass
{
    public Subclass(int x, int y) : base(x) { /* ... */ }
}
```

> **⚠️ 기본 생성자를 쓰는 클래스를 상속하면 다른 생성자도 기본 생성자를 거쳐야 한다**
>
> 클래스에 기본 생성자가 있으면, 그 클래스의 다른 모든 생성자는 반드시 `: this(...)`로 기본 생성자를 호출해야 한다. `: base(...)`를 직접 부를 수 없다. 기본 생성자가 캡처한 매개변수 필드를 반드시 초기화해야 하기 때문이다.

## 14.7 캐스팅과 참조 변환 규칙

### 참조 변환이란 무엇인가

객체 참조는 두 방향으로 변환될 수 있다.

- 기반 클래스 참조로 **암시적 업캐스트**(upcast)
- 파생 클래스 참조로 **명시적 다운캐스트**(downcast)

핵심은 이것이 **참조 변환**(reference conversion)이라는 점이다. 논리적으로 새 참조가 만들어져 같은 객체를 가리킬 뿐, **객체 자체는 바뀌지 않는다**. 값이 복사되거나 변환되지 않는다. 실행 시점에는 사실상 아무 일도 일어나지 않고, 타입 검사만 일어난다(다운캐스트의 경우).

업캐스트는 항상 성공한다. 다운캐스트는 객체가 실제로 그 타입일 때만 성공한다.

### 업캐스트

```csharp
Stock msft = new Stock();
Asset a = msft;                     // 업캐스트

Console.WriteLine(a == msft);       // True — 같은 객체다
```

업캐스트 후에도 `a`는 `msft`와 같은 `Stock` 객체를 가리킨다. 다만 `a`는 그 객체에 대해 **더 제한적인 시야**를 갖는다.

```csharp
Console.WriteLine(a.Name);          // OK
Console.WriteLine(a.SharesOwned);   // 컴파일 오류
```

마지막 줄이 오류인 이유는 `a`의 정적 타입이 `Asset`이기 때문이다. 객체가 실제로 `Stock`이라는 것은 상관없다 — 컴파일러는 정적 타입만 본다.

### 다운캐스트

```csharp
Stock msft = new Stock();
Asset a = msft;                     // 업캐스트
Stock s = (Stock)a;                 // 다운캐스트 — 명시적 캐스트 필요

Console.WriteLine(s.SharesOwned);   // OK
Console.WriteLine(s == a);          // True
Console.WriteLine(s == msft);       // True
```

다운캐스트가 명시적 캐스트를 요구하는 이유는 **런타임에 실패할 수 있기 때문**이다.

```csharp
House h = new House();
Asset a = h;                        // 업캐스트 — 항상 성공
Stock s = (Stock)a;                 // 다운캐스트 실패: a는 Stock이 아니다
```

이때 `InvalidCastException`이 던져진다. 이것이 **런타임 타입 검사**(runtime type checking)다. 컴파일러가 검증하는 정적 타입 검사와의 관계는 15.3절에서 다룬다.

| 방향 | 문법 | 성공 여부 | 실패 시 |
|---|---|---|---|
| 업캐스트 (파생 → 기반) | 암시적, 캐스트 불필요 | 항상 성공 | — |
| 다운캐스트 (기반 → 파생) | 명시적 캐스트 필요 | 런타임 타입에 따라 | `InvalidCastException` |
| `as`로 다운캐스트 | `x as T` | 런타임 타입에 따라 | `null` 반환 |
| `is`로 검사 | `x is T` | — | `false` 반환 |
| 무관한 타입 간 캐스트 | `(Hexagon)employee` | **컴파일은 통과할 수 있음** | `InvalidCastException` |

> **⚠️ `object`를 거치면 컴파일러가 못 막는다**
>
> ```csharp
> object frank = new Manager();
> Hexagon hex = (Hexagon)frank;      // 컴파일 성공, 런타임에 InvalidCastException
> ```
>
> `Manager`와 `Hexagon`은 아무 관계도 없지만, `frank`의 정적 타입이 `object`이므로 컴파일러는 "언젠가 `Hexagon`이 들어 있을 수도 있다"고 판단한다. `object`나 인터페이스 타입 변수를 거치는 순간 컴파일 타임 안전망이 사라진다.
>
> 반대로 두 클래스가 명백히 무관하고 그것이 정적 타입에서 드러나면 컴파일러가 막아 준다. `Manager m = ...; Hexagon h = (Hexagon)m;`은 컴파일 오류다.

### `as` 연산자

`as`는 실패했을 때 예외 대신 `null`을 낸다.

```csharp
Asset a = new Asset();
Stock s = a as Stock;       // s는 null, 예외는 없다

if (s != null)
    Console.WriteLine(s.SharesOwned);
```

`as`의 제약은 두 가지다.

- 사용자 정의 변환을 수행할 수 없다(22장)
- 숫자 변환을 수행할 수 없다

```csharp
long x = 3 as long;         // 컴파일 오류
```

`as`와 캐스트는 둘 다 업캐스트도 할 수 있지만, 업캐스트는 암시적 변환으로 충분하므로 쓸 일이 없다.

> **💡 실패했을 때 무엇이 터지길 원하는가**
>
> 다음 두 줄은 실패할 때 서로 다른 예외를 던진다.
>
> ```csharp
> long shares = ((Stock)a).SharesOwned;     // 방식 1
> long shares = (a as Stock).SharesOwned;   // 방식 2
> ```
>
> `a`가 `Stock`이 아닐 때 첫 줄은 `InvalidCastException`을 던진다 — **무엇이 잘못됐는지 정확히 말해 주는 예외**다. 두 번째 줄은 `NullReferenceException`을 던진다 — `a`가 `Stock`이 아니었던 건지, `a` 자체가 `null`이었던 건지 알 수 없다.
>
> 판단 기준은 이렇다. **캐스트 연산자는 "나는 이 값의 타입을 확신한다. 틀렸다면 그건 내 코드의 버그이니 예외를 던져라"는 선언이다. `as`는 "확신이 없으니 결과에 따라 분기하겠다"는 선언이다.** 확신하면서 `as`를 쓰면 진단 정보를 버리는 셈이다. 관련 관용구는 79.3절에 있다.

### `is` 연산자

`is`는 변수가 어떤 **패턴**에 맞는지 검사한다. 가장 기본이 타입 패턴이다.

```csharp
if (a is Stock)
    Console.WriteLine(((Stock)a).SharesOwned);
```

이 맥락에서 `is`는 "참조 변환이 성공할 것인가", 즉 객체가 해당 클래스에서 파생됐는가(또는 그 인터페이스를 구현하는가)를 검사한다. 언박싱 변환이 성공할 경우에도 `true`가 된다(15.2절). 사용자 정의 변환과 숫자 변환은 고려하지 않는다.

C# 7부터는 검사와 동시에 변수를 도입할 수 있다.

```csharp
if (a is Stock s)
    Console.WriteLine(s.SharesOwned);
```

이것은 다음과 동등하다.

```csharp
Stock s;
if (a is Stock)
{
    s = (Stock)a;
    Console.WriteLine(s.SharesOwned);
}
```

이중 캐스트가 사라진다. 도입한 변수는 즉시 쓸 수 있고,

```csharp
if (a is Stock s && s.SharesOwned > 100000)
    Console.WriteLine("Wealthy");
```

`is` 식 밖에서도 스코프에 남는다.

```csharp
if (a is Stock s && s.SharesOwned > 100000)
    Console.WriteLine("Wealthy");
else
    s = new Stock();                // s가 스코프 안에 있다

Console.WriteLine(s.SharesOwned);   // 여전히 스코프 안
```

C# 9부터는 `not` 패턴도 쓸 수 있다.

```csharp
if (emp is not Manager and not SalesPerson)
    Console.WriteLine($"{emp.Name}은 승진 대상이 아니다");
```

`is`가 지원하는 패턴 전체(상수 패턴, 관계 패턴, 프로퍼티 패턴, 목록 패턴 등)는 77장에서 다룬다. 이 장에서 쓰는 것은 타입 패턴뿐이다.

### 계층 안에서의 타입 분기

상속 계층을 다루는 실무 코드는 대개 이런 모양이 된다.

```csharp
static void GivePromotion(Employee emp)
{
    Console.WriteLine($"{emp.Name}이(가) 승진했다");

    switch (emp)
    {
        case SalesPerson s when s.SalesNumber > 5:
            Console.WriteLine($"{s.Name}은 {s.SalesNumber}건을 판매했다");
            break;
        case Manager m:
            Console.WriteLine($"{m.Name}은 스톡옵션 {m.StockOptions}주를 갖고 있다");
            break;
        case Employee:
            Console.WriteLine($"{emp.Name}은 일반 직원이다");
            break;
    }
}
```

`case`는 위에서 아래로 검사되고 첫 매치에서 끝나므로 **순서가 결정적으로 중요하다**. `case Employee:`를 맨 위로 올리면 나머지가 영원히 실행되지 않는다. `PtSalesPerson`은 `SalesPerson`을 상속하므로 첫 번째 `case`에 걸린다.

> **⚠️ 타입 분기가 늘어난다면 설계를 의심하라**
>
> `switch`로 파생 타입을 나열하는 코드는 새 파생 타입이 추가될 때마다 손대야 한다. 컴파일러는 빠뜨린 `case`를 알려 주지 않는다. 계층이 닫혀 있고(봉인된 계층) 동작이 계층 밖 관심사라면 타입 분기가 정당하지만, **동작이 타입의 책임이라면 가상 메서드가 옳다**. 가상 메서드로 만들면 파생 타입을 추가할 때 컴파일러가 구현을 강제한다(추상 멤버라면).

## 14.8 오버로딩과 오버로드 해석 — 상속이 개입할 때

### 가장 구체적인 타입이 이긴다

같은 이름의 오버로드가 상속 계층의 여러 타입을 받는다고 하자.

```csharp
static void Foo(Asset a) { Console.WriteLine("Foo(Asset)"); }
static void Foo(House h) { Console.WriteLine("Foo(House)"); }
```

호출되면 **가장 구체적인 타입**이 우선한다.

```csharp
House h = new House();
Foo(h);                     // Foo(House)
```

`House`는 `Asset`이기도 하므로 두 오버로드 모두 적용 가능(applicable)하지만, `House → House` 변환이 `House → Asset` 변환보다 "더 좋은" 변환이므로 `Foo(House)`가 이긴다. 오버로드 해석의 일반 규칙은 13.2절에 있다.

### 결정은 컴파일 타임에 일어난다

이것이 함정이다.

```csharp
Asset a = new House();
Foo(a);                     // Foo(Asset)  ← 런타임 타입이 House인데도!
```

`a`의 런타임 타입은 `House`다. 그런데 `Foo(Asset)`이 호출된다. **오버로드 해석은 정적으로, 즉 컴파일 타임에 결정된다.** 컴파일러가 IL에 `Foo(Asset)`이라는 토큰을 박아 넣었고, 런타임은 그것을 그대로 실행할 뿐이다.

가상 메서드와 정반대다. 이 대비가 핵심이다.

| | 결정 시점 | 근거 |
|---|---|---|
| **오버로드 해석** (어떤 메서드 시그니처인가) | 컴파일 타임 | 인자의 정적 타입 |
| **가상 디스패치** (그 시그니처의 어느 구현인가) | 런타임 | 수신자의 런타임 타입 |

두 단계는 순차적이다. 먼저 컴파일러가 "어느 시그니처"를 정하고, 그다음 런타임이 "그 시그니처의 어느 구현"을 정한다. 가상 디스패치는 절대로 오버로드 선택을 바꾸지 않는다.

> **📌 `dynamic`으로 오버로드 해석을 런타임으로 미루기**
>
> 인자를 `dynamic`으로 캐스트하면 오버로드 해석이 런타임으로 미뤄지고, 객체의 실제 타입을 기준으로 결정된다.
>
> ```csharp
> Asset a = new House();
> Foo((dynamic)a);        // Foo(House)
> ```
>
> 이 기법으로 방문자 패턴을 간단히 흉내 낼 수 있다. 대가는 성능과 컴파일 타임 안전성이다. `dynamic`의 동작 원리와 오버로드 해석은 59장에서 다룬다.

### 메커니즘 — 파생 클래스 후보가 기반 클래스 후보를 지운다

여기서부터가 이 절의 본론이다. 오버로드가 **상속 계층에 흩어져 있을 때** 규칙이 뒤집힌 것처럼 보이는 현상이 있다.

```csharp
public class Base
{
    public void Foo(int x) => Console.WriteLine("Base.Foo(int)");
}

public class Derived : Base
{
    public void Foo(long x) => Console.WriteLine("Derived.Foo(long)");
}

Derived d = new Derived();
d.Foo(5);           // Derived.Foo(long)
```

`5`는 `int` 리터럴이다. `Base.Foo(int)`는 **정확히 일치**하고, `Derived.Foo(long)`은 `int → long` 확대 변환을 요구한다. 상식대로라면 정확한 일치가 이겨야 한다. 그런데 `Derived.Foo(long)`이 호출된다.

이유는 오버로드 해석 알고리즘에 **후보 집합을 좁히는 단계**가 하나 더 있기 때문이다. C# 사양의 메서드 호출 규칙은 이렇게 말한다.

> 후보 메서드 집합은 **가장 파생된 타입의 메서드만** 남도록 축소된다. 집합 안의 각 메서드 `C.F`에 대해(`C`는 `F`가 선언된 타입), `C`의 기반 타입에 선언된 모든 메서드가 집합에서 제거된다.

단계별로 따라가면 이렇다.

```text
1단계 — 이름으로 후보 수집
        { Derived.Foo(long), Base.Foo(int) }

2단계 — 적용 가능한 것만 남김 (인자 5는 둘 다 통과)
        { Derived.Foo(long), Base.Foo(int) }

3단계 — 가장 파생된 타입만 남김   ← 여기서 결판난다
        Derived.Foo(long)이 집합에 있으므로,
        Derived의 기반 타입인 Base에 선언된 것은 전부 제거
        { Derived.Foo(long) }

4단계 — 남은 후보 중 최선 선택
        후보가 하나뿐이므로 Derived.Foo(long)
```

3단계가 끝나는 순간 `Base.Foo(int)`는 경쟁에서 빠진다. "더 정확한 변환"을 따지는 4단계까지 살아남지 못한 것이다. **파생 클래스에 적용 가능한 후보가 하나라도 있으면, 기반 클래스의 후보는 얼마나 잘 맞든 무조건 탈락한다.**

이 규칙이 존재하는 이유는 다시 **버전 관리**다. 기반 클래스에 나중에 오버로드가 추가되더라도, 파생 클래스에서의 호출 의미가 조용히 바뀌지 않게 하려는 것이다. 파생 클래스 작성자의 의도가 기반 클래스 작성자의 의도보다 우선한다는 결정이다.

> **⚠️ 이 규칙은 인터페이스에서는 다르게 동작한다**
>
> 위 규칙은 **클래스 상속**에 대한 것이다. 인터페이스는 다중 상속이 가능해서 "가장 파생된 타입"이 유일하지 않을 수 있고, 규칙이 더 복잡하다. 인터페이스 멤버 조회는 18장에서 다룬다.

### 언제 물리는가

이 규칙에 물리는 전형적인 상황은 셋이다.

| 상황 | 증상 |
|---|---|
| 기반 클래스가 다른 시그니처로 같은 이름 메서드를 갖고 있음 | 파생 오버로드가 부적절한 변환을 하면서 이김 |
| 확장 메서드와 인스턴스 메서드 경쟁 | 인스턴스 메서드가 항상 이긴다(확장 메서드는 후보 수집 단계에서 마지막) |
| 파생 클래스가 `new`로 오버로드를 추가 | 기반 오버로드 전체가 정적 타입 기준으로 숨겨진다 |

세 번째가 특히 조용히 깨진다.

```csharp
public class Base
{
    public void Log(string s) { }
    public void Log(int i) { }
}

public class Derived : Base
{
    public new void Log(string s) { }   // string 오버로드만 숨겼다고 생각하지만
}

Derived d = new Derived();
d.Log(42);      // Base.Log(int)가 호출된다 — Derived에 int를 받는 Log가 없으므로
d.Log("hi");    // Derived.Log(string)
```

여기서는 `Derived`에 `int`를 받는 후보가 없어서 기반 후보가 살아남았다. 그런데 나중에 `Derived`에 `void Log(object o)`를 추가하면 `d.Log(42)`가 **조용히** `Derived.Log(object)`로 옮겨 간다. 박싱이 생기고, 로그 형식이 바뀌고, 아무도 눈치채지 못한다.

> **💡 이 함정의 실무적 결론**
>
> 기반 클래스에 정의된 메서드와 **같은 이름으로 오버로드를 추가하지 마라**. 다른 이름을 쓰거나, 기반 메서드를 `virtual`로 만들어 재정의하라. API 설계 관점에서의 상세한 논거와 대안은 78.8절에 있다.
>
> 그리고 기반 타입 설계자를 위한 짝 규칙이 있다 — **편의 오버로드는 비가상으로, 가장 기능이 풍부한 것만 가상으로** 만드는 것이다.
>
> ```csharp
> public class Set
> {
>     private int _length = 0;
>
>     // 편의 오버로드 — 비가상
>     public int Find(object value) => Find(value, 0, _length);
>
>     // 편의 오버로드 — 비가상
>     public int Find(object value, int startIndex)
>         => Find(value, startIndex, _length - startIndex);
>
>     // 가장 기능이 풍부한 것만 가상
>     public virtual int Find(object value, int startIndex, int endIndex)
>     {
>         // 실제 구현
>         return -1;
>     }
> }
> ```
>
> 파생 클래스는 한 곳만 재정의하면 모든 진입점의 동작이 바뀐다. 재정의 지점이 하나이므로 계약도 하나다. 반대로 오버로드 셋을 모두 가상으로 만들면 파생 클래스가 일부만 재정의해 일관성이 깨지는 사고가 난다.

## 14.9 가상 메서드 디스패치가 실제로 일어나는 방식 (메서드 테이블 예고)

### 두 개의 호출 옵코드

CLR은 메서드를 호출하는 IL 명령을 두 개 제공한다.

**`call`**

- 정적 메서드, 인스턴스 메서드, 가상 메서드 모두 호출할 수 있다
- 인스턴스/가상 메서드를 부를 때는 객체를 가리키는 변수를 지정해야 하며, **그 변수가 `null`이 아니라고 가정한다**
- **변수의 타입**이 어느 타입의 메서드를 부를지 결정한다. 그 타입에 해당 메서드가 없으면 기반 타입들을 검사한다
- 가상 메서드를 **비가상으로** 부를 때 자주 쓰인다

**`callvirt`**

- 인스턴스 메서드와 가상 메서드를 호출할 수 있다(정적 메서드는 불가)
- 비가상 인스턴스 메서드를 부를 때는 **변수의 타입**이 대상을 결정한다
- 가상 인스턴스 메서드를 부를 때는 **CLR이 객체의 실제 타입을 알아내서** 다형적으로 호출한다
- 타입을 알아내려면 변수가 `null`이 아니어야 한다. 그래서 JIT이 널 검사 코드를 생성하고, `null`이면 `NullReferenceException`을 던진다
- **비가상 메서드를 부를 때도 널 검사는 수행된다**

| | `call` | `callvirt` |
|---|---|---|
| 정적 메서드 | 가능 | **불가** |
| 인스턴스 메서드 | 가능 | 가능 |
| 가상 메서드 | 가능(비가상 호출됨) | 가능(다형적 호출) |
| 대상 결정 | 변수의 **정적 타입** | 가상이면 **런타임 타입**, 아니면 정적 타입 |
| 널 검사 | 안 함 | **항상 함** |
| 상대 속도 | 빠름 | 약간 느림 |

### C#이 실제로 내보내는 것

```csharp
using System;

public sealed class Program
{
    public static void Main()
    {
        Console.WriteLine();        // 정적 메서드
        object o = new object();
        o.GetHashCode();            // 가상 인스턴스 메서드
        o.GetType();                // 비가상 인스턴스 메서드
    }
}
```

```il
.method public hidebysig static void  Main() cil managed
{
  .entrypoint
  // Code size 26 (0x1a)
  .maxstack  1
  .locals init (object o)
  IL_0000:  call       void [System.Console]System.Console::WriteLine()
  IL_0005:  newobj     instance void [System.Runtime]System.Object::.ctor()
  IL_000a:  stloc.0
  IL_000b:  ldloc.0
  IL_000c:  callvirt   instance int32 [System.Runtime]System.Object::GetHashCode()
  IL_0011:  pop
  IL_0012:  ldloc.0
  IL_0013:  callvirt   instance class [System.Runtime]System.Type
                       [System.Runtime]System.Object::GetType()
  IL_0018:  pop
  IL_0019:  ret
}
```

세 줄을 하나씩 본다.

- `Console.WriteLine()` → `call`. 정적 메서드이므로 당연하다.
- `o.GetHashCode()` → `callvirt`. 가상 메서드이므로 당연하다.
- `o.GetType()` → **`callvirt`**. `GetType`은 가상이 아닌데도 `callvirt`다.

세 번째가 놀랍다. C# 팀은 **모든 인스턴스 메서드 호출에 `callvirt`를 쓰기로** 결정했다. JIT은 `GetType`이 가상이 아님을 알므로 실제로는 비가상으로 호출하는 코드를 생성한다. 결과적으로 손해는 널 검사 하나뿐이다.

왜 이런 선택을 했는가. **널 참조에 대한 호출을 반드시 예외로 만들기 위해서**다.

```csharp
public sealed class Program
{
    public int GetFive() { return 5; }

    public static void Main()
    {
        Program p = null;
        int x = p.GetFive();        // C#에서는 NullReferenceException
    }
}
```

이론적으로는 이 코드가 정상 동작할 수 있다. `GetFive`는 비가상이므로 CLR은 `p`의 타입(`Program`)만 알면 되고, 메서드 본문이 `this`를 쓰지 않으니 `this`가 `null`이어도 문제없다. 실제로 `call`을 쓰는 다른 언어에서는 잘 돈다. 그러나 C#은 `callvirt`를 내보내므로 예외가 난다.

> **⚠️ 비가상 메서드를 나중에 가상으로 바꾸지 마라**
>
> 어떤 컴파일러는 비가상 메서드를 `call`로 호출한다. 그 상태에서 메서드가 가상으로 바뀌고 호출 측이 재컴파일되지 않으면, 가상 메서드가 **비가상으로** 호출되어 예측할 수 없는 동작이 나온다. 호출 코드가 C#이라면 항상 `callvirt`를 쓰므로 이 문제는 없다. 그러나 다른 .NET 언어에서 호출된다면 실제 위험이다. 이것도 바이너리 호환성을 깨는 변경 목록(78.13절)에 들어간다.

### `call`이 가상 메서드에 쓰이는 경우

```csharp
internal class SomeClass
{
    public override string ToString()
    {
        return base.ToString();     // 여기
    }
}
```

`base.ToString()`은 가상 메서드지만 컴파일러가 `call`을 낸다. `callvirt`였다면 런타임 타입이 `SomeClass`이므로 자기 자신을 무한 재귀 호출해 스택이 넘쳤을 것이다.

또 다른 경우는 값 타입이다. 값 타입은 봉인되어 있어 다형성이 없으므로 컴파일러가 `call`을 쓴다. 인스턴스가 `null`일 수 없으니 널 검사도 불필요하다. 값 타입의 가상 메서드를 굳이 가상으로 부르려면 CLR이 메서드 테이블에 접근하기 위해 **박싱**을 해야 하고, 그러면 힙 압력이 늘어난다(15.2절).

### 메서드 테이블 — 개념

가상 디스패치가 실제로 어떻게 동작하는가. 힙의 모든 객체는 두 개의 오버헤드 멤버를 갖는다 — **타입 객체 포인터**와 **싱크 블록 인덱스**다. 타입 객체 안에는 **메서드 테이블**이 있고, 타입에 정의된 메서드마다 항목이 하나씩 있다.

```text
   스레드 스택                    관리 힙

  ┌──────────────┐        ┌──────────────────────┐
  │ e (Employee) │───────→│  Manager 객체        │
  └──────────────┘        │  ┌────────────────┐  │
                          │  │ 타입 객체 ptr  │──┼──┐
                          │  │ 싱크 블록 인덱스│  │  │
                          │  │ 인스턴스 필드  │  │  │
                          │  └────────────────┘  │  │
                          └──────────────────────┘  │
                                                    ↓
      Employee 타입 객체                Manager 타입 객체
    ┌────────────────────────┐      ┌────────────────────────┐
    │ 타입 객체 ptr          │      │ 타입 객체 ptr          │
    │ 싱크 블록 인덱스       │      │ 싱크 블록 인덱스       │
    │ 정적 필드              │      │ 정적 필드              │
    ├────────────────────────┤      ├────────────────────────┤
    │ 슬롯: GetYearsEmployed │      │ 슬롯: GetYearsEmployed │→ Employee 코드
    │ 슬롯: GetProgressReport│──┐   │ 슬롯: GetProgressReport│──┐
    │ 슬롯: Lookup (static)  │  │   │ 슬롯: Lookup (static)  │  │
    └────────────────────────┘  │   └────────────────────────┘  │
                                ↓                               ↓
                     Employee 구현의 JIT 코드      Manager 구현의 JIT 코드
```

`Manager`가 `GetProgressReport`를 재정의했으므로, `Manager`의 메서드 테이블에서 **같은 위치의 슬롯**이 `Manager`의 코드를 가리킨다. `Manager`가 재정의하지 않은 `GetYearsEmployed`는 `Employee`의 코드를 그대로 가리킨다.

### 세 가지 호출의 실제 동작

| 호출 종류 | JIT이 하는 일 |
|---|---|
| **정적 메서드** | 메서드를 정의한 타입의 타입 객체를 찾고, 메서드 테이블에서 해당 항목을 찾아 그 코드를 호출 |
| **비가상 인스턴스 메서드** | **변수의 타입**에 해당하는 타입 객체를 찾고(그 타입에 없으면 기반 타입 방향으로 내려가며 탐색), 메서드 테이블 항목을 찾아 호출 |
| **가상 인스턴스 메서드** | 호출 지점마다 실행되는 코드를 추가로 생성. 변수를 따라 객체로 가서 **객체의 타입 객체 포인터를 읽고**, 그 타입 객체의 메서드 테이블에서 슬롯을 조회해 호출 |

핵심은 가상 호출에만 **런타임 간접 참조 한 단계**(객체 → 타입 객체 → 슬롯)가 추가된다는 점이다. 정적 호출과 비가상 호출은 JIT 시점에 대상 주소가 확정되지만, 가상 호출은 매번 객체를 따라가야 한다.

여기서 `newslot`의 의미가 완성된다.

- `virtual`(newslot 있음) → 메서드 테이블에 **새 슬롯을 추가**한다
- `override`(newslot 없음) → 기반 타입이 만든 **기존 슬롯의 내용을 자기 코드로 바꾼다**
- `new virtual`(newslot 있음) → 이름은 같지만 **또 다른 슬롯**을 만든다. 기반 슬롯은 그대로 남는다

이제 14.3절의 `Hider` 예제가 완전히 설명된다. `Hider.Foo`는 `BaseClass`의 가상 슬롯을 건드리지 않았다. `b2.Foo()`는 그 슬롯을 조회했고, 거기엔 `BaseClass.Foo`가 그대로 있었다.

> **📌 이 절은 개념까지만이다**
>
> 실제 `MethodTable` 구조는 여기 그림보다 훨씬 복잡하다. `TypeHandle`, 슬롯 테이블, 인터페이스 맵, 부모 체인, `EEClass`로의 포인터 등이 얽혀 있고, 슬롯 조회는 청크(chunk) 단위 간접 참조를 거친다. WinDbg로 실제 메모리를 뜯어 보는 실습을 포함한 상세는 54.1절에 있다. 인터페이스 디스패치는 클래스 가상 디스패치와 메커니즘이 다르다 — 18.9절에서 다룬다.

### 성능 영향

가상 메서드를 정의할 때 치르는 비용은 넷이다.

| 비용 | 내용 |
|---|---|
| **호출 자체** | 간접 참조 한 단계가 추가된다. 절대 비용은 작지만 뜨거운 루프에서는 누적된다 |
| **인라이닝 차단** | JIT은 대상이 확정되지 않은 호출을 인라이닝할 수 없다. 인라이닝이 막히면 뒤따르는 최적화도 함께 막힌다 — 이쪽이 호출 비용보다 크다(55.4절) |
| **버전 취약성** | 가상 메서드는 컴포넌트 버전 관리를 취약하게 만든다(78.14절) |
| **분기 예측** | 호출 대상이 매번 달라지면 간접 분기 예측이 실패한다 |

그래서 지침은 이렇다. **타입을 설계할 때 가상 메서드 개수를 최소화하라.** JIT이 대상을 확정할 수 있으면 역가상화가 걸려 이 비용이 대부분 사라진다(14.5절, 55.5절). `sealed` 클래스, `sealed override` 멤버, 구체 타입 변수를 통한 호출이 그 조건을 만들어 준다.

## 14.10 생성자에서 가상 함수를 호출하면 안 되는 이유

### 규칙

**생성자에서 가상 메서드를 호출하지 마라.** 이것은 취향이 아니라 규칙이다. 파생 클래스 작성자는 자기 재정의 메서드가 **절반만 초기화된 객체** 위에서 실행될 것이라고 예상하지 않는다.

### 실행 순서로 증명하기

14.6절의 초기화 순서를 다시 가져온다.

1. 파생 → 기반 방향: 필드 초기화자 실행, 기반 생성자 인자 평가
2. 기반 → 파생 방향: 생성자 본문 실행

이 비대칭이 폭탄이다. **기반 생성자의 본문은 파생 생성자의 본문보다 먼저 실행된다.** 그런데 객체의 타입은 할당 순간에 이미 확정되어 있으므로, 기반 생성자에서 가상 메서드를 부르면 **파생 클래스의 재정의가 실행된다.**

```csharp
public abstract class Base
{
    protected Base()
    {
        Console.WriteLine("① Base 생성자 진입");
        Initialize();                       // 가상 메서드 호출 — 위험
        Console.WriteLine("③ Base 생성자 종료");
    }

    protected abstract void Initialize();
}

public class Derived : Base
{
    private readonly List<string> _items = new List<string>();   // 필드 초기화자
    private string _prefix;                                       // 생성자 본문에서 설정

    public Derived(string prefix)
    {
        Console.WriteLine("④ Derived 생성자 본문 진입");
        _prefix = prefix;
        Console.WriteLine("⑤ Derived 생성자 본문 종료");
    }

    protected override void Initialize()
    {
        Console.WriteLine("② Derived.Initialize 실행");
        Console.WriteLine($"   _items는 null인가? {_items is null}");
        Console.WriteLine($"   _prefix는 null인가? {_prefix is null}");
        _items.Add(_prefix + "item");       // 여기서 터진다
    }
}
```

```csharp
var d = new Derived("pre-");
```

출력은 이렇다.

```text
① Base 생성자 진입
② Derived.Initialize 실행
   _items는 null인가? False
   _prefix는 null인가? True
③ Base 생성자 종료
④ Derived 생성자 본문 진입
⑤ Derived 생성자 본문 종료
```

②가 ④보다 먼저 나온다는 것이 전부다. 그리고 `_prefix + "item"`은 `"item"`이 되고(널 문자열 연결은 예외를 던지지 않는다), 리스트에 잘못된 값이 들어간다. `_prefix`를 쓰는 대신 `_prefix.Length`를 읽었다면 `NullReferenceException`이 났을 것이다.

### 왜 `_items`는 살아 있고 `_prefix`는 죽었는가

이것이 이 절의 핵심 통찰이다.

| 파생 클래스 멤버 | 기반 생성자 실행 시점의 상태 | 이유 |
|---|---|---|
| **필드 초기화자로 초기화한 필드** | **초기화되어 있다** | 필드 초기화자는 `base(...)` 호출보다 먼저 실행된다 |
| **생성자 본문에서 대입한 필드** | `null` / `0` / `default` | 생성자 본문은 기반 생성자가 끝난 뒤에 실행된다 |
| `readonly` 필드(생성자에서 설정) | `default` | 위와 같다 |
| 기본 생성자(primary constructor) 매개변수 | 초기화되어 있다 | 매개변수 캡처 필드는 `base` 호출 전에 채워진다 ※C# 12 |
| `required` 프로퍼티 | **설정되지 않았다** | 객체 초기화자는 생성자가 **전부 끝난 뒤** 실행된다 |

가장 무서운 조합은 `required` 프로퍼티와 객체 초기화자다. `required`는 컴파일러가 호출부에서 검사하는 규칙일 뿐이고(13.13절), 값이 실제로 들어가는 시점은 생성자 체인이 모두 끝난 후다. 생성자 안에서는 `required` 프로퍼티가 절대 채워져 있지 않다.

```text
시간 →

  new Derived("pre-")
     │
     ├─ 힙에 객체 할당, 타입 객체 포인터 = Derived  ← 여기서 이미 런타임 타입은 Derived
     │
     ├─ ①  Derived의 필드 초기화자 실행       _items = new List<string>()   ✔
     │
     ├─ ②  base() 호출
     │        ├─ Base의 필드 초기화자
     │        └─ Base의 생성자 본문
     │              └─ Initialize()  ──→ 가상 디스패치 ──→ Derived.Initialize
     │                                                        │
     │                                    _items  ✔ (초기화자로 채워짐)
     │                                    _prefix ✘ (아직 null)
     │
     └─ ③  Derived의 생성자 본문 실행         _prefix = "pre-"              ✔
```

### C++과 정반대다

C++ 경험자는 이 동작에 특히 놀란다. C++에서는 기반 클래스 생성자가 실행되는 동안 객체의 가상 함수 테이블 포인터가 **기반 클래스의 것**으로 설정되어 있다. 그래서 기반 생성자에서 가상 함수를 부르면 **기반 클래스의 구현**이 실행된다. 파생 클래스가 재정의했어도 무시된다.

| | C++ | C# / CLR |
|---|---|---|
| 기반 생성자 실행 중 객체의 "타입" | 기반 클래스 | **파생 클래스**(할당 시점에 확정) |
| 기반 생성자에서 가상 함수를 부르면 | 기반 구현 실행 | **파생 구현 실행** |
| 순수 가상 함수를 부르면 | 정의되지 않은 동작 / 런타임 오류 | 파생 구현이 정상 실행됨 |
| 결과적 위험 | "왜 내 재정의가 안 불리지" | **"왜 내 필드가 null이지"** |

CLR 쪽 동작은 일관성 면에서 더 낫다. 객체의 타입은 태어날 때 정해지고 죽을 때까지 안 바뀐다. 대신 초기화되지 않은 상태가 노출되는 위험을 개발자가 져야 한다.

> **⚠️ 널 허용 참조 타입 경고도 이것을 잡아 주지 못한다**
>
> `#nullable enable` 상태에서 `private string _prefix;`를 선언하면 "생성자를 나갈 때 널이 아님을 보장할 수 없다"는 경고가 나온다. 하지만 그것은 **생성자를 나갈 때**의 이야기다. 생성자 **도중에** 가상 메서드를 통해 널이 노출되는 경로는 컴파일러가 추적하지 않는다. `_prefix`를 생성자 본문에서 제대로 대입하면 경고는 사라지고, 버그는 남는다.

### 어떻게 피하는가

| 회피법 | 방법 | 대가 |
|---|---|---|
| **가상 호출을 없앤다** | 생성자에서 자기 클래스의 비가상/`private` 메서드만 호출 | 가장 안전. 파생 클래스의 훅이 사라진다 |
| **클래스를 봉인한다** | `sealed class`로 만들면 재정의가 불가능해 문제가 성립하지 않는다 | 상속 자체를 포기 |
| **멤버를 봉인한다** | 문제되는 가상 멤버만 `sealed override` | 계층 중간에서만 유효 |
| **2단계 초기화** | 생성자는 필드만 채우고, 초기화 로직은 별도 `Initialize()` 공개 메서드로 분리해 호출부가 명시적으로 호출 | 호출을 잊으면 미완성 객체가 돌아다닌다 |
| **팩터리 메서드** | `private` 생성자 + `static Create()`가 생성 후 초기화까지 마치고 반환 | 가장 견고. 상속과 함께 쓰려면 설계가 늘어난다 |

팩터리 방식이 실무에서 가장 깔끔하다.

```csharp
public abstract class Base
{
    protected Base() { }                    // 가상 호출 없음

    protected abstract void Initialize();

    protected static T Create<T>() where T : Base, new()
    {
        var instance = new T();             // 생성자 체인이 완전히 끝난 뒤
        instance.Initialize();              // 여기서 가상 호출 — 안전하다
        return instance;
    }
}

public class Derived : Base
{
    private string _prefix = "";

    public Derived() { _prefix = "pre-"; }

    protected override void Initialize()
    {
        Console.WriteLine(_prefix.Length);  // _prefix는 확실히 채워져 있다
    }

    public static Derived New() => Create<Derived>();
}
```

> **💡 코드 분석기를 켜라**
>
> .NET SDK에 포함된 분석기 규칙 중 **CA2214 — 생성자에서 재정의 가능한 메서드를 호출하지 마시오**가 정확히 이 상황을 잡는다. 기본으로는 경고 수준이 낮게 잡혀 있으므로 `.editorconfig`에서 `dotnet_diagnostic.CA2214.severity = error`로 올리는 것을 권한다. 관용구를 분석기로 강제하는 방법은 79.13절에 있다.
>
> 생성자와 초기화의 관용구 전반(멤버 초기화자와 생성자 대입의 선택 기준 포함)은 79.5절에서 다룬다.

## 14.11 공변 반환 타입 ※C# 9

### 문제

`Clone` 같은 메서드를 가상으로 만들면 반환 타입에서 손해를 본다.

```csharp
public class Asset
{
    public string Name;
    public virtual Asset Clone() => new Asset { Name = Name };
}

public class House : Asset
{
    public decimal Mortgage;
    public override Asset Clone() => new House { Name = Name, Mortgage = Mortgage };
}
```

C# 8까지는 재정의 메서드의 반환 타입이 기반과 **완전히 같아야** 했다. `House.Clone()`이 실제로는 `House`를 만들어 돌려주는데도 선언상으로는 `Asset`이다. 그래서 호출부가 다운캐스트를 해야 한다.

```csharp
House mansion1 = new House { Name = "McMansion", Mortgage = 250000 };
House mansion2 = (House)mansion1.Clone();   // 캐스트가 필요하다
```

이 캐스트는 논리적으로 절대 실패하지 않는데도 런타임 검사를 유발하고, 무엇보다 **API가 자기 자신을 정확히 설명하지 못한다**.

### 해결

C# 9부터 재정의 메서드(또는 프로퍼티의 `get` 접근자)가 **더 파생된 타입**을 반환할 수 있다.

```csharp
public class Asset
{
    public string Name;
    public virtual Asset Clone() => new Asset { Name = Name };
}

public class House : Asset
{
    public decimal Mortgage;
    public override House Clone() => new House { Name = Name, Mortgage = Mortgage };
}
```

```csharp
House mansion1 = new House { Name = "McMansion", Mortgage = 250000 };
House mansion2 = mansion1.Clone();          // 캐스트 없음
```

이것이 허용되는 이유는 계약이 깨지지 않기 때문이다. `Clone`은 `Asset`을 반환해야 하는데, `House`를 반환한다 — `House`는 `Asset`이므로 계약을 지키고, 그 이상을 준다. 이런 성질을 **공변**(covariant)이라고 한다.

정적 타입에 따라 반환 타입이 달라지는 것도 자연스럽게 동작한다.

```csharp
House h = new House();
Asset a = h;

House h2 = h.Clone();       // House 반환 — 정적 타입이 House이므로
Asset a2 = a.Clone();       // Asset 반환 — 정적 타입이 Asset이므로
// 두 경우 모두 런타임에는 House 객체가 만들어진다
```

### 규칙과 제약

| 항목 | 규칙 |
|---|---|
| 어디에 적용되나 | 메서드의 반환 타입, 프로퍼티의 `get` 접근자 타입 |
| 어디에 적용 안 되나 | 매개변수 타입(반공변은 지원되지 않는다), 프로퍼티 `set`, 읽고 쓰는 프로퍼티 |
| 어떤 변환이 허용되나 | **암시적 참조 변환**이 존재해야 한다. 즉 파생 클래스거나 구현한 인터페이스 |
| 값 타입 | 불가. `object`를 `int`로 바꾸는 것은 참조 변환이 아니라 언박싱이다 |
| 인터페이스 구현 | 인터페이스 멤버 구현에서도 사용 가능 |

```csharp
public class Base
{
    public virtual object Get() => null;
    public virtual Base Prop { get; }           // get 전용이면 가능
    public virtual Base RW { get; set; }
}

public class Derived : Base
{
    public override string Get() => "";         // OK — string은 object
    public override Derived Prop { get; }       // OK — get 전용
    // public override Derived RW { get; set; } // 컴파일 오류 — set이 있으면 불가
}
```

`set`이 있으면 안 되는 이유는 명백하다. `set` 쪽은 **반공변**이어야 안전한데(더 넓은 타입을 받아야 한다), 프로퍼티는 타입이 하나뿐이므로 두 방향을 동시에 만족할 수 없다.

### 컴파일 결과 — `[PreserveBaseOverrides]`

공변 반환은 순수한 C# 문법 설탕이 아니다. **런타임 지원이 필요하다.** 이유는 메서드 테이블 슬롯 때문이다.

기반의 `Asset Clone()`과 파생의 `House Clone()`은 **시그니처가 다르다**(반환 타입이 다르다). CLR의 메서드 매칭은 반환 타입도 시그니처의 일부로 본다. 그래서 아무 조치 없이 두면 파생 메서드가 기반 슬롯을 덮어쓰지 못하고 새 슬롯을 차지해 버린다 — `new`와 같은 결과가 된다.

이를 막기 위해 컴파일러는 재정의 메서드에 특별한 특성을 붙인다.

```il
.method public hidebysig virtual instance class House
        Clone() cil managed
{
  .custom instance void [System.Runtime]System.Runtime.CompilerServices.
          PreserveBaseOverridesAttribute::.ctor() = ( 01 00 00 00 )
  // ...
}
```

`[PreserveBaseOverrides]`는 런타임에게 "이 메서드는 시그니처가 정확히 일치하지 않더라도 기반 타입의 대응하는 슬롯을 덮어써야 한다"고 알린다. 런타임은 이 지시에 따라 슬롯 배치를 조정한다.

> **⚠️ 공변 반환은 .NET Framework에서 쓸 수 없다**
>
> 이 기능은 런타임 지원(`CovariantReturnsOfClasses` 기능)이 있는 .NET 5 이상에서만 동작한다. 컴파일러는 대상 런타임이 이 기능을 선언하지 않으면 컴파일 오류를 낸다. C# 9 언어 버전을 `<LangVersion>`으로 강제하더라도 .NET Framework 대상 프로젝트에서는 공변 반환을 쓸 수 없다.
>
> `netstandard2.0`을 대상으로 하는 라이브러리도 마찬가지다. 다중 대상 프로젝트라면 이 기능이 조건부 컴파일 대상이 된다.

> **📌 C# 9 이전 방식도 여전히 유효하다**
>
> 공변 반환을 쓸 수 없는 환경이라면 옛 관용구를 쓴다.
>
> ```csharp
> public class Asset
> {
>     public virtual Asset Clone() => new Asset { Name = Name };
> }
>
> public class House : Asset
> {
>     public override Asset Clone() => new House { Name = Name, Mortgage = Mortgage };
>     public new House CloneTyped() => (House)Clone();     // 타입 지정 편의 메서드
> }
> ```
>
> 재정의는 기반 시그니처를 지키고, 강타입 편의 메서드를 따로 노출하는 패턴이다. BCL에도 이 형태가 여러 곳에 있다.

C# 9의 다른 기능들과 함께 보고 싶다면 76.8절에 시대별 정리가 있다. `ICloneable` 자체를 구현하는 것이 왜 설계상 나쁜 선택인지는 78.7절에서 다룬다.

## 14.12 상속 대신 포함·위임을 택하는 기준

### 두 종류의 코드 재사용

코드 재사용에는 두 가지 방식이 있다.

- **상속** — "is-a" 관계. `SalesPerson`은 `Employee`**이다**
- **포함/위임**(containment/delegation, 집합체 aggregation) — "has-a" 관계. `Employee`는 `BenefitPackage`를 **갖는다**

`Employee`가 `BenefitPackage`(복리후생 패키지)를 상속하는 것은 말이 안 된다. 직원이 복리후생 패키지는 아니다. 하지만 관계는 분명히 있다.

```csharp
class BenefitPackage
{
    public double ComputePayDeduction() => 125.0;
}
```

포함은 그냥 필드로 갖는 것이다.

```csharp
partial class Employee
{
    protected BenefitPackage EmpBenefits = new BenefitPackage();
}
```

**위임**은 포함한 객체의 기능을 바깥에 노출하는 공개 멤버를 추가하는 행위다.

```csharp
partial class Employee
{
    protected BenefitPackage EmpBenefits = new BenefitPackage();

    // 기능 일부를 위임해서 노출
    public double GetBenefitCost() => EmpBenefits.ComputePayDeduction();

    // 객체 자체를 프로퍼티로 노출
    public BenefitPackage Benefits
    {
        get => EmpBenefits;
        set => EmpBenefits = value;
    }
}
```

```csharp
Manager chucky = new Manager("Chucky", 50, 92, 100000, "333-23-2322", 9000);
double cost = chucky.GetBenefitCost();
Console.WriteLine($"복리후생 비용: {cost}");
```

### 상속의 진짜 비용

상속은 문법이 짧아서 싸 보인다. 그러나 실제 비용은 다음과 같다.

| 비용 | 내용 |
|---|---|
| **인터페이스 전체를 물려받는다** | 기반 클래스의 모든 `public` 멤버가 자동으로 내 API가 된다. 원하지 않는 멤버도 포함된다 |
| **기반 클래스 변경에 노출된다** | 기반 클래스가 멤버를 추가하면 내 멤버와 이름이 충돌할 수 있다(14.3절). 기반 클래스가 내부 구현을 바꾸면 내 재정의 메서드의 호출 시점이 바뀔 수 있다 |
| **단 하나뿐인 상속 슬롯을 쓴다** | 나중에 다른 것을 상속해야 하면 방법이 없다 |
| **런타임 결합이 강하다** | 파생 클래스는 기반 클래스가 자기 가상 메서드를 언제·몇 번 부르는지에 의존하게 된다. 이 의존은 문서화되지 않는다 |
| **생성자 릴레이** | 기반 생성자를 파생마다 다시 노출해야 한다(14.6절) |
| **캡슐화 누수** | `protected` 멤버는 사실상 공개 API다. 파생 클래스가 어떤 어셈블리에 있을지 모르므로 마음대로 바꿀 수 없다 |

포함·위임의 비용은 하나다 — **보일러플레이트**. 노출하고 싶은 멤버를 하나씩 손으로 써서 넘겨야 한다. 그 대신 무엇을 노출할지 완전히 통제할 수 있다.

### 결정 기준

| 질문 | "예"라면 | "아니오"라면 |
|---|---|---|
| 리스코프 치환이 성립하는가? 파생 객체를 기반 타입 자리에 넣었을 때 모든 기존 코드가 그대로 옳게 동작하는가 | 상속 후보 | **포함** |
| 기반 클래스의 **모든** `public` 멤버가 파생 타입에서도 의미가 있는가 | 상속 후보 | **포함** |
| 기반 클래스를 내가(또는 우리 팀이) 통제하는가 | 상속 후보 | **포함** — 남의 클래스 상속은 버전 폭탄이다 |
| 다형적으로 다루고 싶은 공통 추상이 실제로 존재하는가 | 상속 후보 | **포함** |
| 기반 클래스가 상속을 **의도해서** 설계됐는가(가상 멤버, `protected` 훅, 문서) | 상속 후보 | **포함** |
| 구현이 아니라 계약만 공유하면 되는가 | **인터페이스**(18장) | — |

이 중 하나라도 "아니오"이면 대개 포함이 맞다.

> **⚠️ "코드를 재사용하려고" 상속하지 마라**
>
> 가장 흔한 오용이다. 기반 클래스에 편리한 메서드가 있어서 상속하는 것. 이때 얻는 것은 메서드 몇 개고, 잃는 것은 API 통제권·상속 슬롯·버전 안정성 전부다.
>
> ```csharp
> // 나쁨 — List가 제공하는 200개의 멤버가 전부 내 API가 된다
> public class OrderCollection : List<Order>
> {
>     public decimal Total => this.Sum(o => o.Amount);
> }
>
> // 좋음 — 노출할 것만 노출한다
> public class OrderCollection : IEnumerable<Order>
> {
>     private readonly List<Order> _orders = new();
>
>     public decimal Total => _orders.Sum(o => o.Amount);
>     public void Add(Order o) => _orders.Add(o);
>     public int Count => _orders.Count;
>
>     public IEnumerator<Order> GetEnumerator() => _orders.GetEnumerator();
>     IEnumerator IEnumerable.GetEnumerator() => GetEnumerator();
> }
> ```
>
> 첫 번째 버전은 `Clear()`, `Insert()`, `RemoveAt()`, `Sort()`, `Capacity` 설정자까지 전부 열어 준다. 그중 어느 하나라도 불변식을 깨면 막을 방법이 없다. `List<T>`는 상속을 위해 설계되지도 않았다 — 가상 멤버가 사실상 없다.

### 상속이 옳은 경우

포함을 기본값으로 두되, 상속이 명백히 옳은 경우도 있다.

| 상황 | 예 |
|---|---|
| 프레임워크가 요구하는 확장 지점 | `Exception` 상속(32.10절), `Stream` 상속, `Attribute` 상속(20.6절) |
| 진짜 분류 체계가 존재 | `Shape` → `Circle`/`Hexagon`, `Employee` → `Manager`/`SalesPerson` |
| 템플릿 메서드 패턴 | 기반 클래스가 알고리즘 골격을 잡고, 파생이 단계별 훅을 채운다 |
| 상당한 상태와 구현을 공유 | 인터페이스로는 필드를 공유할 수 없다 |

`Exception` 상속이 좋은 예다.

```csharp
public class PersonException : Exception
{
    public PersonException() : base() { }
    public PersonException(string message) : base(message) { }
    public PersonException(string message, Exception innerException)
        : base(message, innerException) { }
}
```

여기서 `base(...)`로 세 개의 생성자를 재현하는 이유는 생성자가 상속되지 않기 때문이다(14.1절). 예외 클래스는 이 세 생성자를 갖는 것이 관례이며, 분석기도 이를 검사한다. 예외 클래스 설계는 32.10절에서 다룬다.

### 중첩 타입 — 포함의 변형

포함의 특수한 형태로 중첩 타입이 있다.

```csharp
public partial class Employee
{
    public class BenefitPackage
    {
        public enum BenefitPackageLevel { Standard, Gold, Platinum }

        public double ComputePayDeduction() => 125.0;
    }
}
```

```csharp
Employee.BenefitPackage.BenefitPackageLevel level
    = Employee.BenefitPackage.BenefitPackageLevel.Platinum;
```

중첩 타입의 장점은 접근성 통제와 바깥 타입의 `private` 멤버 접근이다. 단점은 위 예에서 보듯 **이름이 길어지는 것**이고, 그래서 공개 중첩 타입은 설계 지침상 권장되지 않는다. 상세는 17.5절에 있다.

> **💡 실무 순서**
>
> 새 타입을 만들 때 나는 이 순서로 검토한다.
>
> 1. **아무 관계도 만들지 않는다.** 그냥 별개 타입 두 개로 충분한 경우가 생각보다 많다.
> 2. **포함한다.** 필드로 갖고, 필요한 것만 위임한다.
> 3. **인터페이스를 구현한다.** 다형적으로 다뤄야 하는 계약이 있을 때(78.2절).
> 4. **상속한다.** 위 셋으로 안 될 때만.
>
> 그리고 상속을 택했다면 반드시 함께 정한다 — **어떤 멤버를 `virtual`로 열 것인가, 그 멤버들이 언제 호출되는지를 어떻게 문서화할 것인가, 계층은 어디서 `sealed`로 끊을 것인가.** 이 셋을 정하지 않은 상속은 미래의 버그다.

## 이 장의 요약

- **C#은 단일 상속이고, 기반을 지정하지 않은 클래스는 `object`를 상속한다.** 이것은 C#의 취향이 아니라 CLR의 제약이다. 다중 상속이 필요하면 인터페이스(18장)나 포함·위임으로 푼다.
- **변수에는 정적 타입과 런타임 타입이 있고, 어떤 결정이 어느 쪽을 보는지가 이 장 전부다.** 오버로드 해석·필드 접근·`new`로 숨긴 멤버는 정적 타입을 보고, 가상 디스패치·캐스트·`is`는 런타임 타입을 본다.
- **`virtual`은 `newslot virtual`, `override`는 `newslot` 없는 `virtual`이다.** `newslot` 한 비트가 "메서드 테이블에 새 슬롯을 만들 것인가, 기존 슬롯을 덮어쓸 것인가"를 가른다. `sealed override`는 여기에 `final`이 붙는다.
- **`new` 한정자는 경고를 끄는 것 외에 아무 일도 하지 않는다.** 동작은 원래부터 정적 타입 기준이었다. `new`가 정당한 유일한 상황은 내가 통제하지 않는 기반 클래스가 나중에 같은 이름의 멤버를 추가했을 때다.
- **C# 컴파일러는 모든 인스턴스 메서드 호출에 `callvirt`를 낸다.** 비가상 메서드에도 그렇게 한다. 널 참조 호출을 반드시 예외로 만들기 위해서다. 예외는 `base.X()`와 값 타입 메서드로, 이때는 `call`을 쓴다.
- **오버로드 해석에는 "가장 파생된 타입만 남기기" 단계가 있다.** 파생 클래스에 적용 가능한 후보가 하나라도 있으면 기반 클래스 후보는 아무리 정확히 맞아도 탈락한다. 그래서 기반 클래스 메서드를 파생에서 오버로딩하면 안 된다.
- **필드 초기화자는 파생→기반 방향, 생성자 본문은 기반→파생 방향으로 실행된다.** 이 비대칭 때문에 기반 생성자에서 가상 메서드를 부르면, 파생 클래스의 필드 초기화자는 이미 실행됐지만 생성자 본문은 아직 실행되지 않은 반쯤 만들어진 객체 위에서 재정의 코드가 돈다.
- **생성자에서 가상 메서드를 호출하는 것은 C++과 정반대 방식으로 위험하다.** C++은 기반 구현이 불려서 놀라고, C#은 파생 구현이 불려서 필드가 `null`이라 터진다. CA2214를 오류로 올려 두는 것이 가장 싼 예방이다.
- **`sealed`의 가장 큰 가치는 성능이 아니라 버전 관리다.** 봉인을 푸는 것은 호환되는 변경이지만, 이미 열린 클래스를 닫는 것은 모든 파생 클래스를 깨뜨린다. 역가상화 이득은 호출부의 정적 타입이 그 봉인 타입일 때만 나온다.
- **공변 반환(※C# 9)은 순수한 컴파일러 기능이 아니라 런타임 지원이 필요하다.** 컴파일러가 `[PreserveBaseOverrides]`를 붙여 슬롯 덮어쓰기를 지시하며, .NET Framework에서는 쓸 수 없다.
- **기본값은 상속이 아니라 포함이다.** 상속은 기반 클래스의 전체 API·상속 슬롯 하나·버전 안정성을 대가로 지불한다. "코드를 재사용하려고" 상속하는 것이 가장 흔한 오용이다.

## 연습 문제

1. **`new`와 `override`의 차이를 직접 확인하라.** 14.3절의 `BaseClass`/`Overrider`/`Hider` 예제를 그대로 실행해 네 줄의 출력을 확인하라. 그다음 `Hider.Foo`에서 `new`를 지우고 컴파일해 CS0108 경고가 나오는지, 경고를 무시하고 실행했을 때 출력이 그대로인지 확인하라. 마지막으로 `Hider.Foo`를 `public new virtual void Foo()`로 바꾸고 `Hider`를 상속한 클래스에서 `override`했을 때 `BaseClass` 변수로 호출하면 무엇이 나오는지 예측한 뒤 확인하라.
2. **IL 플래그를 눈으로 확인하라.** `virtual`, `override`, `sealed override`, `abstract`, `new`, `new virtual` 여섯 가지 메서드를 갖는 클래스 계층을 만들고 ildasm(또는 SharpLab, 3.8절)으로 열어 `.method` 줄을 비교하라. `newslot`과 `final`이 언제 붙고 언제 안 붙는지 표로 정리하라.
3. **초기화 순서를 추적하라.** 기반과 파생 클래스에 각각 필드 초기화자와 생성자 본문을 두고, 다섯 지점 모두에서 번호를 출력하도록 만들어라. 출력 순서가 14.6절의 다이어그램과 일치하는지 확인하고, 파생 생성자를 `: this(...)`로 바꿨을 때 필드 초기화자가 몇 번 실행되는지 세어 보라.
4. **생성자 가상 호출 버그를 재현하라.** 14.10절의 `Base`/`Derived` 예제를 실행해 `_prefix`가 `null`인 것을 확인하라. 그다음 `_prefix`를 필드 초기화자(`private string _prefix = "pre-";`)로 옮기면 출력이 어떻게 바뀌는지 확인하고, 왜 그런지 설명하라. 마지막으로 `.editorconfig`에 `dotnet_diagnostic.CA2214.severity = error`를 넣고 빌드가 실패하는지 확인하라.
5. **오버로드 해석의 "가장 파생된 타입만 남기기"를 재현하라.** `Base.Foo(int)`와 `Derived.Foo(long)`을 만들고 `new Derived().Foo(5)`가 어느 쪽을 부르는지 확인하라. 그다음 `Derived.Foo(long)`을 지우고 다시 실행해 결과가 바뀌는지 확인하고, `((Base)d).Foo(5)`로 호출하면 어떻게 되는지도 확인하라.
6. **역가상화 조건을 실험하라.** 가상 `ToString()`을 재정의한 클래스를 만들고, 클래스에 `sealed`를 붙인 경우와 안 붙인 경우의 JIT 코드를 `DOTNET_JitDisasm` 환경 변수로 덤프해 비교하라(55.8절). 같은 객체를 `object` 변수에 담아 호출했을 때는 `sealed`가 있어도 코드가 달라지지 않는 것을 확인하라.
7. **상속을 포함으로 리팩터링하라.** `List<T>`를 상속한 컬렉션 클래스를 하나 만들고, 그 타입의 인스턴스에 `Clear()`를 호출해 불변식이 깨지는 시나리오를 재현하라. 그다음 14.12절의 방식대로 `IEnumerable<T>` 구현 + 내부 `List<T>` 포함으로 바꾸고, 같은 시나리오가 컴파일 단계에서 막히는지 확인하라.
