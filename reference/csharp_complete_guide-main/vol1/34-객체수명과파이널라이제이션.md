# 34장. 객체 수명과 파이널라이제이션

> **이 장의 위치** — 33장은 "언제 정리할지 내가 정한다"는 결정적 정리를 다뤘다. 이 장은 그 반대편, **"언제 정리될지 아무도 모르는" 비결정적 세계**를 끝까지 판다. 객체가 살아 있다는 말의 정확한 뜻은 무엇인지, 파이널라이저는 어느 스레드에서 언제 어떤 순서로 실행되는지, 그리고 수명을 붙들거나 놓아 주는 도구들 — 약한 참조, `Lazy<T>`, `GC.KeepAlive`, `ConditionalWeakTable` — 이 각각 어떤 수명 계약을 표현하는지가 주제다.
>
> **선수 지식** — 13장(클래스와 캡슐화), 26장(델리게이트와 람다), 27장(이벤트), 32장(예외 처리), 33장(결정적 정리와 `IDisposable`)
>
> **이 장에서 다루지 않는 것** — `IDisposable`·`SafeHandle`·`using`·표준 Dispose 패턴은 33장에서 이미 끝냈다. 이 장은 그 위에 파이널라이제이션 의미론만 얹는다. GC 알고리즘 자체 — 마크·플랜·스윕·컴팩트 단계, 세대와 예산, 카드 테이블, 쓰기 장벽, GC Info와 스택 루트 스캐닝 — 는 64장이고, 루트의 종류별 스캔 방법은 64.3절, 즉시 루트 수집의 JIT 쪽 메커니즘은 64.4절·64.5절이다. 힙의 물리 구조(세대·LOH·POH·리전)는 62장, 할당 경로는 63장, GC 모드와 `GC` 클래스 API 레퍼런스는 65장이다. 메모리 누수를 도구로 잡아내는 실무 — `!finalizequeue`, `dotnet-gcdump`, PerfView — 는 66장이며, 그중 파이널라이저 큐 적체와 타이머 누수는 66.11절의 대표 시나리오에 들어 있다. 이벤트 구독이 만드는 결합과 약한 이벤트 패턴의 **구현**은 27.6절·27.7절이다. 여기서는 그것들을 **수명의 관점에서만** 다시 본다.

## 34.1 "객체가 살아 있다"의 정의 — 루트

### 죽음의 정의부터

일상 언어로 "이 객체는 이제 안 쓴다"고 말할 때, 우리는 프로그래머의 의도를 말하고 있다. GC는 의도를 읽지 못한다. GC가 아는 것은 하나뿐이다.

> **객체가 살아 있다 = 어떤 루트에서 출발해 참조를 따라가면 그 객체에 도달할 수 있다.**

이 정의는 짧지만 두 가지를 함축한다. 첫째, **살아 있음은 객체 자신의 속성이 아니라 그래프상의 위치**다. 같은 객체가 어떤 시점에는 살아 있고 다음 순간에는 죽는다. 둘째, **"쓸모"와 무관하다.** 두 번 다시 쓰지 않을 객체라도 루트에서 도달 가능하면 영원히 산다. 관리 메모리 누수라는 것의 정의가 정확히 이것이다 — 쓰지 않지만 도달 가능한 객체.

반대 개념도 명확히 해 두자. 서로를 참조하는 객체 무리는 **바깥에서 아무도 그들을 참조하지 않으면 통째로 죽는다.**

```csharp
class Node
{
    public Node? Peer;
}

static void MakeCycle()
{
    var a = new Node();
    var b = new Node();
    a.Peer = b;
    b.Peer = a;   // 순환 참조
}   // 메서드가 끝나면 a, b 모두 회수 대상이다
```

COM의 참조 카운팅에서는 이 코드가 누수였다. `a`의 카운트는 `b` 때문에 0이 되지 못하고, `b`의 카운트는 `a` 때문에 0이 되지 못한다. GUI 라이브러리에서 창이 자식 요소를 참조하고 자식이 부모 창을 참조하는 흔한 구조가 그대로 누수가 됐다. CLR은 참조 카운팅 대신 **참조 추적(reference tracking)** 알고리즘을 쓰기 때문에 이 문제가 없다. 마킹 중에 이미 마크된 객체를 다시 만나면 그 객체의 필드를 다시 조사하지 않는다. 순환이 있어도 무한 루프에 빠지지 않는다.

> **📌 참조 카운팅을 완전히 버린 것은 아니다**
>
> CLR 자체는 참조 카운팅을 쓰지 않지만, COM 상호운용 경계에서는 여전히 참조 카운팅이 살아 있다. 런타임 호출 가능 래퍼(RCW)가 네이티브 쪽 `AddRef`/`Release`를 대신 관리한다. 그리고 `SafeHandle`은 P/Invoke 호출 동안 핸들이 닫히지 않도록 **내부적으로 참조 카운터를 유지**한다(33.7절). 즉 "관리 객체의 수명"에는 참조 카운팅이 없고, "핸들의 유효성"에는 있다.

### 루트의 종류 — 개요

그렇다면 루트란 무엇인가. 네 종류다.

| 루트 종류 | 구체적으로 | 수명 |
|---|---|---|
| 스택 루트 | 실행 중인 메서드와 그 호출 스택 위 모든 메서드의 지역 변수·매개변수 | 메서드가 실행 중인 동안 (정확히는 **마지막 사용 지점까지**) |
| 정적 필드 | `static` 필드가 가리키는 객체 | 타입이 로드된 로드 컨텍스트가 살아 있는 동안 — 실질적으로 프로세스 수명 |
| GC 핸들 | `GCHandle`로 할당한 항목 중 `Normal`·`Pinned` 종류, 인터닝된 문자열 등 | `GCHandle.Free()`를 부를 때까지 |
| 파이널라이제이션 큐 | 파이널라이저가 아직 실행되지 않은 객체 | 파이널라이저 스레드가 처리할 때까지 (34.2절) |

각 루트가 GC의 마크 단계에서 실제로 어떻게 스캔되는지 — 스택 워커, GC Info, 핸들 테이블의 종류별 순회, 카드 테이블을 통한 GC 내부 루트 — 는 64.3절에서 다룬다. 이 장에서 필요한 것은 위 표의 세 번째 열, **각 루트가 객체를 얼마나 오래 붙드는가**다.

> **⚠️ 정적 필드가 가리키는 객체는 사실상 영원히 산다**
>
> 관리 메모리 누수의 가장 흔한 형태가 이것이다. 정적 필드가 컬렉션을 가리키고, 그 컬렉션에 항목을 계속 넣기만 하고 빼지 않는다. 정적 필드는 컬렉션을 살리고, 컬렉션은 모든 항목을 살린다. 항목이 다시 다른 그래프를 살린다.
>
> 정적 캐시, 정적 이벤트, 정적 로그 버퍼, 싱글턴이 붙든 구독자 목록 — 전부 같은 형태다. 정적 필드를 쓸 때는 **"여기 담기는 것이 언제 빠지는가"에 답할 수 있어야 한다.** 답이 없으면 그것은 누수다.

다음은 도달성 판정을 한 장에 그린 것이다.

```text
루트                          관리 힙
────────────                  ────────────────────────────────────
[스택 슬롯]────────────────→ ( A )────→( D )────→( H )
[레지스터] ────────────────→ ( C )         ↑
[정적 필드]────────────────→ ( F )─────────┘
[GC 핸들(Normal)]──────────→ ( K )
[fReachable 큐]────────────→ ( E )····→( G )      ← E는 파이널라이저 대기 중
                                                      G는 E가 살린다

                              ( B )←──→( I )      ← 서로만 참조: 둘 다 죽는다
                              ( J )                ← 아무도 참조 안 함: 죽는다

도달 가능: A C D E F G H K      회수 대상: B I J
```

이 그림에서 눈여겨볼 것은 `E`다. 애플리케이션 코드 어디에서도 `E`를 참조하지 않는데 살아 있다. 파이널라이제이션 큐가 루트이기 때문이다. 그리고 `E`가 살아 있으므로 `E`가 참조하는 `G`도 함께 산다. 34.2절 전체가 이 한 줄의 파장을 다룬다.

### 어휘 범위와 생존 범위는 다르다

여기가 이 절의 핵심이다. C++ 프로그래머의 직관 — "변수가 스코프를 벗어나면 객체가 죽는다" — 은 C#에서 **반쪽만** 맞다. 정확히는 이렇다.

> **지역 변수가 붙드는 객체의 생존 범위는 어휘 범위(lexical scope)가 아니라, 그 변수의 마지막 사용 지점까지다.**

JIT 컴파일러는 각 메서드에 대해 "이 명령 주소에서 어떤 슬롯·레지스터가 살아 있는 객체 참조를 담고 있는가"를 기술한 자료구조(GC Info)를 만든다. 변수를 마지막으로 읽은 뒤부터는 그 슬롯이 루트 목록에서 빠진다. 이것을 **즉시 루트 수집(eager root collection)** 이라 부르고, 메커니즘은 64.5절에 있다.

관찰 가능한 결과를 보자. 이 코드는 원천 도서들이 모두 같은 예제로 설명하는 고전이다.

```csharp
using System;
using System.Threading;

public static class Program
{
    public static void Main()
    {
        // 2초마다 TimerCallback을 부르는 타이머
        Timer t = new Timer(TimerCallback, null, 0, 2000);

        // 사용자가 Enter를 누를 때까지 대기
        Console.ReadLine();
    }

    private static void TimerCallback(object? o)
    {
        Console.WriteLine("In TimerCallback: " + DateTime.Now);

        // 시연을 위해 강제로 GC를 일으킨다
        GC.Collect();
    }
}
```

특별한 컴파일러 스위치 없이(즉 최적화가 켜진 릴리스 빌드로) 컴파일해 실행하면 **`TimerCallback`이 딱 한 번만 호출된다.**

이유는 이제 명확할 것이다. `Main`은 `t`에 대입한 뒤로 `t`를 다시 쓰지 않는다. 첫 콜백이 `GC.Collect()`를 부르는 시점에 `t` 슬롯은 이미 루트가 아니다. `Timer` 객체는 도달 불가능이므로 회수되고, 회수와 함께 타이머가 멈춘다.

### 디버그 빌드에서는 왜 다른가

같은 코드를 `/debug` 스위치로(즉 최적화를 끄고) 컴파일하면 콜백이 계속 호출된다. 컴파일러가 어셈블리에 `System.Diagnostics.DebuggableAttribute`를 `DebuggingModes.DisableOptimizations` 플래그와 함께 심어 넣고, JIT이 그 플래그를 보면 **모든 루트의 수명을 메서드 끝까지 인위적으로 연장**하기 때문이다.

이 동작은 편의 기능이다. 디버거로 한 줄씩 넘어가다가 조사식 창에서 `t`를 들여다봤는데 "이미 수집된 객체"라는 표시가 뜬다면 대부분의 개발자가 버그라고 생각할 것이다. 그래서 JIT이 스스로를 속인다.

| 빌드 | JIT의 판단 | 위 예제의 동작 |
|---|---|---|
| 디버그 (최적화 off) | 모든 지역 변수가 메서드 끝까지 살아 있다 | 콜백이 반복 호출된다 |
| 릴리스 (최적화 on) | 마지막 사용 지점 이후 슬롯은 루트가 아니다 | 콜백이 한 번만 호출된다 |
| 릴리스 + 디버거 연결 | 최적화가 켜져 있으면 그대로 | 한 번만 호출된다 |

> **⚠️ "디버그에서는 되는데 릴리스에서 안 됩니다"의 절반이 여기서 온다**
>
> 그리고 이 부류의 버그는 개발 머신에서 재현되지 않는다. 위 예제는 `GC.Collect()`를 직접 불러 재현성을 확보했지만, 실제로는 **다른 스레드의 할당 때문에** 하필 그 짧은 창에서 GC가 일어난다. 부하가 걸린 프로덕션에서만, 그것도 간헐적으로 나타난다.
>
> 재현 실험을 할 때는 **계층화 컴파일(tiered compilation)도 꺼야 한다.** 계층 0 코드는 빠르게 만드는 것이 목적이라 최적화가 약하고, 그래서 릴리스 빌드인데도 디버그 빌드처럼 동작할 수 있다. 계층 1로 재컴파일된 다음에야 즉시 루트 수집이 관찰된다.

### `null` 대입은 해법이 아니다

직관적인 첫 수정 시도는 이것이다.

```csharp
public static void Main()
{
    Timer t = new Timer(TimerCallback, null, 0, 2000);
    Console.ReadLine();

    t = null;   // ReadLine 이후에 t를 "쓴다"
}
```

**동작하지 않는다.** 지역 변수에 `null`을 넣는 것은 그 변수를 전혀 참조하지 않는 것과 의미상 같다. JIT은 이 대입문을 통째로 제거한다. GC Info는 조금도 바뀌지 않는다.

역으로 이렇게 하면 동작한다.

```csharp
public static void Main()
{
    Timer t = new Timer(TimerCallback, null, 0, 2000);
    Console.ReadLine();

    t.Dispose();   // t가 this 인수로 넘어가야 하므로 여기까지 살아 있어야 한다
}
```

`Dispose`는 인스턴스 메서드다. `t`의 값이 `this` 인수로 전달되어야 하므로 그 지점까지 `t`는 살아 있는 루트다. **폐기 시점을 명시했더니 그 시점까지 객체가 살아남는다** — 아이러니하지만 이것이 정확한 설명이다.

> **💡 `null` 대입이 무의미한 것은 지역 변수일 때뿐이다**
>
> 필드에 `null`을 넣는 것은 전혀 다른 이야기다. 필드는 객체 그래프의 간선이고, 그것을 끊으면 실제로 하위 그래프가 죽는다. 캐시 항목을 비우거나 이벤트 구독을 해지하는 것이 그런 경우다.
>
> 정리하면 이렇다. **지역 변수 `null` 대입은 거의 언제나 불필요하고, 필드 `null` 대입은 종종 필수다.** 33.4절에서 폐기 시 필드를 비울지의 판단 기준을 다뤘다.

### 왜 `Timer`만 이런가

여기까지 읽고 자기 객체가 조기에 수집될까 봐 걱정할 필요는 없다. `Timer`가 예제로 쓰이는 이유는 **힙에 존재한다는 사실 자체가 부수 효과를 만드는 드문 타입**이기 때문이다. 스레드 풀 스레드가 주기적으로 메서드를 부른다. `String` 객체는 메모리에 있다고 해서 아무 일도 일으키지 않는다. 그냥 거기 있을 뿐이다.

수명 자체에 부수 효과가 묶인 타입은 대략 이런 것들이다.

| 부류 | 예 | 조기 수집의 증상 |
|---|---|---|
| 타이머 | `System.Threading.Timer` | 콜백이 멈춘다 (34.10절) |
| 동기화 프리미티브 | `Mutex`, 이름 있는 `EventWaitHandle` | 시스템 전역 잠금이 풀린다 |
| 파이널라이저가 리소스를 닫는 래퍼 | 직접 만든 파일·핸들 래퍼 | 사용 중인 핸들이 닫힌다 (34.8절) |
| 네이티브 콜백 대상 | P/Invoke에 넘긴 델리게이트 | 네이티브가 죽은 함수 포인터를 호출한다 |

이 네 부류를 제외하면 "객체가 필요할 때 살아 있는가"는 애플리케이션이 알아서 보장한다. 쓸 객체는 참조를 갖고 있고, 참조를 갖고 있으면 산다.

> **⚠️ P/Invoke에 넘긴 델리게이트는 GC가 모른다**
>
> 네이티브 코드에 콜백 함수 포인터를 넘기면 마샬러가 델리게이트를 위한 스텁을 만들어 준다. 그러나 **네이티브 쪽이 그 포인터를 저장하고 있다는 사실은 GC의 그래프에 나타나지 않는다.** 관리 쪽에서 델리게이트에 대한 강한 참조를 유지하지 않으면 델리게이트가 수집되고, 나중에 네이티브가 그 포인터를 부르는 순간 프로세스가 죽는다.
>
> 해법은 델리게이트를 정적 필드나 인스턴스 필드에 보관하는 것이다. 자세한 상호운용 규칙은 60장에서 다룬다.

## 34.2 파이널라이저의 동작 순서와 비용 (F-reachable 큐)

### 문법 — `~T()`

파이널라이저는 C++ 소멸자와 같은 모양의 문법으로 선언한다.

```csharp
class FileWrapper
{
    private IntPtr _handle;

    public FileWrapper(string filename)
    {
        _handle = Native.OpenFile(filename);
    }

    // 파이널라이저
    ~FileWrapper()
    {
        if (_handle != IntPtr.Zero)
            Native.CloseHandle(_handle);
    }
}
```

제약은 다음과 같다.

| 규칙 | 이유 |
|---|---|
| 접근 한정자를 붙일 수 없다 | 항상 `protected`로 컴파일된다 |
| `static`일 수 없다 | 인스턴스마다 실행되어야 한다 |
| 매개변수를 가질 수 없다, 오버로드 불가 | 클래스당 정확히 하나 |
| 기반 클래스 버전을 명시적으로 부를 수 없다 | 컴파일러가 자동으로 넣는다 |
| 구조체에 정의할 수 없다 | 값 타입은 관리 힙의 회수 대상이 아니다 |

> **📌 언어마다 다른 문법, 같은 메서드**
>
> C#은 `~T()`만 허용하고 `Finalize`를 직접 재정의하면 컴파일 오류다("Do not override Object.Finalize. Instead, provide a destructor."). F#과 VB.NET에서는 반대로 **`Finalize`를 명시적으로 재정의해야** 파이널라이저가 된다. C++/CLI는 `~T()`를 이미 C++ 소멸자로 쓰고 있어서 파이널라이저를 `!T()`로 쓴다.
>
> "소멸자(destructor)"라는 이름은 C# 언어 명세가 쓰는 용어이지만 불운한 작명이다. 관리 객체를 해체하는 것과는 아무 관계가 없고, 리소스 관리 쪽에 가깝다. 이 책은 **파이널라이저**로 통일한다.

### 컴파일 결과

`~T()`는 `System.Object.Finalize`를 재정의하는 `protected override` 메서드가 된다. 본문은 `try` 블록에 들어가고 `finally` 블록에 `base.Finalize()` 호출이 삽입된다.

```il
.method family hidebysig virtual
    instance void Finalize () cil managed
{
   .override method instance void [System.Runtime]System.Object::Finalize()
   // 본문은 try 블록, base.Finalize() 호출은 finally 블록
}
```

전체 IL과 그 의미 — 내 파이널라이저 본문이 예외를 던져도 기반 클래스 파이널라이저는 실행된다 — 는 33.3절에서 다뤘다. 여기서는 그 결과가 런타임에 무엇을 촉발하는지를 본다.

**`Finalize`를 재정의했다는 사실이 타입과 GC 사이의 계약**이다. 이 계약을 맺은 타입의 인스턴스를 **파이널라이즈 가능(finalizable)** 하다고 부르고, GC는 이들을 특별 취급한다. 재정의하지 않은 타입은 `System.Object`에서 상속받은 빈 `Finalize`를 갖지만 CLR이 그것을 인식하고 무시한다. **비용은 재정의한 타입만 지불한다.**

> **📌 값 타입의 파이널라이저**
>
> ECMA-335는 "값 타입에 파이널라이저를 정의하는 것은 유효하지만, 그 파이널라이저는 박싱된 인스턴스에 대해서만 실행된다"고 규정한다. 현재 .NET 런타임에서는 그렇지 않다 — **박싱 시 값 타입에 정의된 파이널라이저를 그냥 무시한다.** 애초에 C#이 구조체 파이널라이저를 허용하지 않으므로 C#만 쓴다면 마주칠 일이 없다.

### 런타임 동작 — 세 개의 큐를 지나는 여정

파이널라이즈 가능한 객체의 일생은 다음과 같다.

**1단계 — 할당 시 등록.** `new`가 객체를 할당할 때, 타입이 파이널라이즈 가능하면 객체 주소가 **파이널라이제이션 큐(finalization queue)** 에 들어간다. 이 등록은 생성자가 호출되기 **직전**에 일어난다. 그래서 **생성자가 도중에 예외를 던져도 파이널라이저는 호출될 수 있다.**

이 등록 때문에 할당 경로 자체가 달라진다. JIT은 `newobj`를 처리할 때 타입에 파이널라이저가 있는지 검사하고, 있으면 **느린 할당 헬퍼**를 고른다. 범프 포인터를 밀어 올리기만 하면 되는 빠른 경로(63.1절)를 못 쓴다.

**2단계 — 마크 단계 끝의 판정.** GC가 마크 단계를 마치면 파이널라이제이션 큐를 훑는다. 큐에 있는 객체 중 **마크되지 않은(= 도달 불가능한) 것**을 찾으면 그 주소를 파이널라이제이션 큐에서 빼고 **fReachable 큐**로 옮긴다.

**3단계 — 부활.** fReachable 큐는 루트다. 정적 필드가 루트인 것과 정확히 같은 의미에서 루트다. 따라서 fReachable 큐에 들어간 순간 그 객체는 **다시 도달 가능해진다.** 죽었다가 살아났으므로 **부활(resurrection)** 이라 부른다(34.4절). 그리고 그 객체가 필드로 참조하는 객체들도 재귀적으로 마크되어 함께 살아난다.

**4단계 — 파이널라이저 스레드.** GC가 관리 스레드를 재개한 뒤, 전용 **파이널라이저 스레드**가 fReachable 큐에서 항목을 하나씩 빼면서 각 객체의 `Finalize`를 호출한다. 큐가 비어 있으면 이 스레드는 잠들어 있다.

**5단계 — 진짜 회수.** 파이널라이저가 끝나 fReachable 큐에서 참조가 사라지면 객체는 비로소 진짜 도달 불가능이 된다. **그 객체가 속한 세대를 수집하는 다음 GC**가 메모리를 회수한다.

```text
 new            GC #1 (mark 종료)          파이널라이저 스레드      GC #2
  │                    │                          │                  │
  ▼                    ▼                          ▼                  ▼
[할당]──→ 파이널라이제이션 큐 ──→ fReachable 큐 ──→ Finalize() 실행 ──→ 메모리 회수
           (등록: 느린 경로)      (여기가 루트!)      (큐에서 제거)
                                       │
                                       └─→ 객체와 그 하위 그래프가 세대 승격된다
```

> **⚠️ 최소 두 번의 GC, 실제로는 그 이상**
>
> 파이널라이저가 있는 객체의 메모리를 회수하려면 **최소 두 번의 가비지 컬렉션**이 필요하다. 그런데 첫 GC에서 살아남으면서 객체는 다음 세대로 승격된다. 세대 0에서 죽었어야 할 객체가 세대 1이 되고, 다시 승격되면 세대 2가 된다. **세대 2 객체를 회수하려면 세대 2 GC가 필요하고, 서버 애플리케이션에서 세대 2 GC는 몇 시간에 한 번 일어날 수도 있다.**
>
> 더 나쁜 것은 승격이 전염된다는 점이다. 파이널라이즈 가능한 객체가 필드로 참조하는 객체들도 함께 살아남고 함께 승격된다. **파이널라이저가 있는 타입에 참조 타입 필드를 많이 두지 마라.**

### 파이널라이제이션 배열의 실제 레이아웃

파이널라이제이션 큐와 fReachable 큐는 개념상 두 개의 큐지만, 구현은 **하나의 평평한 객체 주소 배열**이다. 논리적으로 세 영역으로 나뉜다.

```text
                       파이널라이제이션 배열 (Object** m_Array)
┌──────────────────────────────────────┬─────────────────────┬──────────────┐
│         파이널라이제이션 부분         │   fReachable 부분    │   자유 부분   │
├──────┬──────┬──────┬───────┬─────────┼──────────┬──────────┼──────────────┤
│ gen0 │ gen1 │ gen2 │  LOH  │   POH   │ Critical │  Normal  │  (미사용)     │
└──────┴──────┴──────┴───────┴─────────┴──────────┴──────────┴──────────────┘
   ▲      ▲      ▲       ▲        ▲         ▲          ▲
   └──────┴──────┴───────┴────────┴─────────┴──────────┘
              경계는 fill pointer 배열이 관리한다 (Object**[] m_FillPointers)
```

이 구조가 설명해 주는 것이 많다.

- **파이널라이제이션 부분이 세대별로 나뉘어 있다.** 세대 1 GC에서는 gen0과 gen1 그룹만 훑으면 된다. 각 객체가 어느 세대에 있는지 주소 범위로 매번 계산하는 대신, 배열 자체를 세대 인식(generation-aware)으로 만든 것이다.
- **그 대가로 객체가 승격·강등될 때마다 주소를 그룹 사이로 옮겨야 한다.** 배열에 구멍을 두지 않으므로 원소를 옮기려면 그 사이의 모든 원소를 시프트해야 한다.
- **새 객체 등록도 시프트를 유발한다.** gen0 그룹은 배열 앞쪽이므로, 그 뒤의 모든 원소를 한 칸씩 밀어야 한다. 여러 스레드가 동시에 할당하므로 **이 배열 접근에는 잠금이 걸린다.**
- 배열이 꽉 차면 20% 더 큰 배열을 만들어 전부 복사한다. 초기 크기는 100개다.
- **fReachable 부분이 Critical과 Normal로 나뉘어 있다.** 임계 파이널라이저의 실행 순서 보장이 여기서 나온다(34.4절).

> **📌 소스에서 확인하려면**
>
> 런타임 소스의 `CFinalize` 클래스가 이 전부를 구현한다. `gc_heap::finalize_queue` 필드가 그 인스턴스를 가리키며, 서버 GC에서는 힙마다 하나씩 있으므로 **파이널라이제이션 배열은 여러 개, 파이널라이저 스레드는 하나**다. `CFinalize::RegisterForFinalization`이 등록, `CFinalize::ScanForFinalization`이 마크 단계 끝의 판정, `CFinalize::UpdatePromotedGenerations`가 세대 그룹 간 이동을 맡는다. 파이널라이저 스레드의 본체는 `FinalizerThread::FinalizerThreadWorker`다. 런타임 소스를 읽는 방법 자체는 83장에서 다룬다.
>
> 참고로 그룹 배치는 .NET 8 이후 자유 부분을 가운데로 옮기는 방향으로 변경이 예정되어 있다.

### 왜 GC가 직접 부르지 않는가

파이널라이저를 GC가 마크 단계에서 바로 호출하면 큐도 스레드도 필요 없을 텐데, 왜 이렇게 복잡한가.

**파이널라이저는 사용자 코드**이기 때문이다. 그 안에 `Thread.Sleep(TimeSpan.FromHours(1))`이 있어도 컴파일러는 막지 않는다. GC가 작업 중에 그것을 실행하면 GC가 한 시간 멈춘다. 데드락이 있으면 GC가 영원히 데드락에 빠진다. **GC 일시 정지 시간이 사용자 코드에 좌우되는 것은 용납할 수 없다.** 그래서 비동기로 뺐다.

전용 스레드를 쓰는 두 번째 이유는 스레드 동기화다. 애플리케이션의 일반 스레드에서 파이널라이저를 실행하면 그 스레드가 이미 잡고 있는 잠금과 파이널라이저가 요구하는 잠금이 충돌해 데드락이 날 수 있다.

### 함정 목록

파이널라이저를 쓰기 전에 이 표를 다 읽어야 한다.

| 함정 | 정확한 내용 |
|---|---|
| 실행 시점 비결정적 | GC가 일어나야 실행된다. 언제 일어날지는 알 수 없다 |
| 실행 순서 미정의 | A가 B를 소유해도 B의 파이널라이저가 먼저 돌 수 있다 |
| 다른 스레드에서 실행 | 스레드 로컬 저장소, 스레드 어피니티, 호출자 컨텍스트를 가정하면 안 된다 |
| 예외 = 프로세스 종료 | 처리되지 않은 예외가 파이널라이저에서 나오면 프로세스가 죽는다. 잡을 방법이 없다 |
| 블로킹 = 전체 정지 | 파이널라이저 스레드는 하나다. 하나가 막히면 그 뒤의 모든 파이널라이저가 실행되지 않는다 |
| 실행 보장 없음 | 프로세스가 급하게 종료되면 실행되지 않는다 |
| 두 번 실행 가능 | 부활 + `ReRegisterForFinalize` 조합(34.4절) |
| 생성자 실패 후에도 실행 | 등록이 생성자 호출 전에 일어나므로, 필드가 초기화됐다고 가정하면 안 된다 |
| 할당이 느려진다 | 느린 할당 헬퍼 + 배열 잠금 + 시프트 |
| 세대 승격을 유발 | 자신과 자신이 참조하는 모든 객체 |

> **⚠️ 프로세스 종료 시 파이널라이저는 실행되지 않는다**
>
> .NET Framework 시절에는 종료 시 파이널라이저 실행을 시도했다(시간 제한이 있어 완주를 보장하지는 않았다). **모던 .NET에서는 애플리케이션이 종료될 때 파이널라이저를 강제로 실행할 방법 자체가 없다.**
>
> 그래서 "프로그램이 끝날 때 파이널라이저가 로그를 남기겠지"라거나 "종료 시 임시 파일이 지워지겠지" 같은 설계는 성립하지 않는다. 프로세스 수명과 묶인 정리는 파이널라이저가 아니라 `AppDomain.CurrentDomain.ProcessExit` 같은 명시적 훅이나, 애초에 그런 정리가 필요 없는 설계로 해결해야 한다.

> **⚠️ 파이널라이저가 예외를 던지면 잡을 수 없다**
>
> `try`/`catch`로 감싸지 않은 파이널라이저 본문에서 예외가 escape하면 프로세스가 종료된다. 파이널라이저 코드는 시스템 전역 동기화 프리미티브 해제 같은 중대한 일을 한다고 간주되므로, 그것을 수행하지 못한 상태는 최고 심각도로 취급된다.
>
> 따라서 **예외를 던질 수 있는 모든 코드를 `try`/`catch`로 감싸라.** 그리고 catch 블록 안의 로깅조차 최대한 단순하고 견고해야 한다 — 정교한 오류 보고 API를 부르면 파이널라이저 스레드에 부담을 주고, 그 API 자체가 예외를 던질 수도 있다.

### `GC.WaitForPendingFinalizers`와 "궁극의 명시적 GC"

파이널라이제이션의 비동기성을 제어하는 유일한 API가 `GC.WaitForPendingFinalizers()`다. 호출 스레드를 막고, fReachable 큐의 모든 객체가 처리될 때까지 기다린다.

여기서 흔히 보이는 세 줄짜리 관용구가 나온다.

```csharp
GC.Collect();                    // 1. 현재의 fReachable 집합을 확정한다
GC.WaitForPendingFinalizers();   // 2. 그들이 파이널라이즈되어 진짜 도달 불가능이 되기를 기다린다
GC.Collect();                    // 3. 그 메모리를 회수한다
```

첫눈에 무의미해 보이지만 각 줄에 이유가 있다. 이 순서가 아니면 파이널라이즈 가능한 객체의 메모리는 첫 번째 `Collect`로 회수되지 않는다.

> **⚠️ 이 관용구도 완전하지 않다**
>
> `WaitForPendingFinalizers`가 도는 동안 다른 스레드가 파이널라이즈 가능한 객체를 계속 할당하면, 두 번째 `GC.Collect` 시점에 또 새로운 fReachable 집합이 생긴다. **모든 메모리를 완전히 회수하는 것은 원리적으로 불가능하다** — 할당하는 모든 스레드를 멈추지 않는 한.
>
> 이 사실은 `GC.GetTotalMemory(forceFullCollection: true)`의 구현에 그대로 드러난다. 이 메서드는 `WaitForPendingFinalizers`와 `Collect`를 **결과가 5% 이내로 안정될 때까지, 최대 20회 반복**한다. 즉 최악의 경우 전체 블로킹 GC를 스무 번 일으킨다. 동적인 메모리 사용 패턴을 가진 큰 애플리케이션에서는 1초 이상 걸릴 수 있다. 진단 목적 외에는 부르지 마라.

### 성능 영향 — 실측

원천 도서(Pro .NET Memory Management)가 BenchmarkDotNet으로 측정한 값이다. 필드 네 개짜리 32바이트 클래스를 파이널라이저 유무만 다르게 해서 N개 할당했다.

| 메서드 | N | 평균 | Gen 0 | Gen 1 | 할당 |
|---|---|---|---|---|---|
| 파이널라이저 없음 | 1 | 2.777 ns | 0.0076 | - | 32 B |
| 파이널라이저 있음 | 1 | 132.138 ns | 0.0074 | 0.0036 | 32 B |
| 파이널라이저 없음 | 10 | 30.667 ns | 0.0762 | - | 320 B |
| 파이널라이저 있음 | 10 | 1,342.092 ns | 0.0744 | 0.0362 | 320 B |
| 파이널라이저 없음 | 100 | 316.633 ns | 0.7625 | - | 3,200 B |
| 파이널라이저 있음 | 100 | 13,607.436 ns | 0.7477 | 0.3662 | 3,200 B |
| 파이널라이저 없음 | 1000 | 3,244.837 ns | 7.6256 | - | 32,000 B |
| 파이널라이저 있음 | 1000 | 131,725.089 ns | 7.5684 | 3.6621 | 32,000 B |

**할당만 놓고 약 40배 느리다.** 할당 크기는 같다. Gen 1 열에 값이 생긴 것이 승격의 증거다. 두 메서드의 JIT 어셈블리 코드는 호출하는 할당자 함수를 빼면 동일하다 — 차이는 전적으로 런타임 쪽에 있다.

> **💡 이 숫자를 읽는 법**
>
> 40배라는 배율에 겁먹을 필요는 없다. 절대값이 130ns다. 파이널라이즈 가능한 객체를 프로그램 수명 동안 수십 개만 만든다면 아무 문제가 없다.
>
> 문제가 되는 것은 **할당률이 높은 경로에 파이널라이저가 있는 타입이 끼어 있을 때**다. 요청마다 하나씩 만드는 래퍼 클래스에 무심코 `~T()`를 넣으면 초당 수만 번 130ns를 지불하고, 그 객체 전부가 세대 1로 승격되어 세대 1 GC 빈도를 끌어올린다. **핫 패스에 파이널라이저를 넣기 전에 두 번 생각하라.**

### 파이널라이제이션이 만드는 메모리 누수

한 가지 시나리오를 더 봐야 한다. fReachable 큐의 파이널라이저들은 **순차적으로** 실행된다. 그러므로 **파이널라이즈 가능한 객체의 할당률이 파이널라이제이션 처리율보다 높으면 fReachable 큐가 무한히 자란다.**

큐에 들어 있는 동안 객체는 살아 있다. 살아 있으니 세대 2로 승격된다. 그렇게 세대 2 힙이 계속 커진다. 증상은 이렇다.

```text
관리 힙 크기가 계속 증가한다
세대 2 힙 크기가 계속 증가한다
그런데 힙 덤프를 떠 보면 "누가 이것들을 붙들고 있는지" 명확하지 않다
```

루트가 fReachable 큐이므로 일반적인 참조 경로 추적으로는 잡히지 않는다. WinDbg의 `!finalizequeue`가 이 상황을 위한 명령이다(66.9절). 진단 실무는 66.11절의 대표 시나리오에 포함되어 있다.

> **⚠️ 파이널라이저 안의 느린 코드는 누수를 만든다**
>
> 파이널라이저 하나가 100ms 걸리면 초당 10개밖에 처리하지 못한다. 초당 100개를 할당하면 큐가 초당 90개씩 자란다. 네트워크 호출, 파일 플러시, 잠금 대기 — 파이널라이저에 넣으면 안 되는 것들의 목록이 전부 여기에 해당한다.
>
> **파이널라이저 코드는 가능한 한 짧고 빨라야 한다.** 이것이 조언이 아니라 요구사항인 이유다.

### `SuppressFinalize`와 `ReRegisterForFinalize`의 비용 비대칭

두 API는 대칭적으로 보이지만 구현 비용이 전혀 다르다.

| API | 구현 | 비용 |
|---|---|---|
| `GC.SuppressFinalize(obj)` | 객체 헤더의 비트 하나를 세팅한다. 배열을 건드리지 않는다 | 매우 저렴 |
| `GC.ReRegisterForFinalize(obj)` | 할당 시의 등록과 **완전히 같은 경로**를 탄다 | 잠금 + 시프트 (등록과 동일) |

`SuppressFinalize`가 이렇게 최적화된 이유는 명확하다. Dispose 패턴의 일부로 **사용자 스레드에서 아주 자주 호출**되기 때문이다. 배열에서 주소를 제거하려면 잠금을 잡고 뒤의 원소를 전부 시프트해야 하는데, 그 대신 헤더 비트를 세우고 파이널라이저 스레드가 그 비트를 확인하도록 했다. 억제된 객체의 주소는 마크 단계 끝에서 fReachable이 아니라 자유 부분으로 옮겨진다.

`SuppressFinalize`가 Dispose 패턴에서 하는 역할과 파생 클래스에서 부르면 안 되는 이유는 33.3절에 있다.

## 34.3 파이널라이저에서 `Dispose` 호출하기

### 관용구

가장 널리 쓰이는 파이널라이저 패턴은 파이널라이저가 `Dispose(false)`를 부르는 것이다.

```csharp
class Test : IDisposable
{
    public void Dispose()              // 가상이 아니다
    {
        Dispose(true);
        GC.SuppressFinalize(this);     // 파이널라이저가 실행되지 않게 한다
    }

    protected virtual void Dispose(bool disposing)
    {
        if (disposing)
        {
            // 이 인스턴스가 소유한 다른 객체의 Dispose()를 부른다
            // 파이널라이즈 가능한 객체를 참조해도 안전하다
        }

        // (이 객체만의) 비관리 리소스를 해제한다
    }

    ~Test() => Dispose(false);
}
```

패턴 전체 — 봉인 타입용 축약형, 상속 가능 타입용 완전형, `Dispose()`를 가상으로 만들면 안 되는 이유, 파생 클래스가 `SuppressFinalize`를 부르면 안 되는 이유 — 는 33.3절에서 다뤘다. 이 절이 답하는 질문은 다른 것이다.

> **`disposing` 인수는 정확히 무엇을 분기하는가? 그리고 왜 그 분기가 필요한가?**

### `disposing == false`는 "최후의 수단 모드"다

`disposing`이 `false`라는 것은 이 호출이 파이널라이저 스레드에서, GC가 이 객체를 죽은 것으로 판정한 뒤에 왔다는 뜻이다. 그 상황에서 무엇을 신뢰할 수 있는지 따져 보자.

이 객체가 필드로 참조하는 객체 `X`가 있다고 하자. 34.2절에서 봤듯이 이 객체가 fReachable 큐에 들어가면 `X`도 재귀적으로 마크되어 함께 살아난다. **즉 `X`의 메모리는 아직 유효하다.** 그런데 `X`도 파이널라이즈 가능한 타입이라면? `X` 역시 같은 GC에서 죽은 것으로 판정되어 fReachable 큐에 들어갔을 수 있고, **파이널라이저 스레드가 `X`를 먼저 처리했을 수 있다.** 순서 보장이 없기 때문이다.

그러면 `X`는 이미 자기 리소스를 놓아 버린 상태다. 메모리는 있지만 논리적으로는 죽었다. `X.Write(...)`를 부르면 `ObjectDisposedException`이 나거나, 더 나쁘게는 아무 예외 없이 잘못된 동작을 한다.

| `disposing == true` (정상 폐기) | `disposing == false` (파이널라이저) |
|---|---|
| 사용자 스레드에서 호출됨 | 파이널라이저 스레드에서 호출됨 |
| 객체 그래프 전체가 정상 상태 | 참조하는 파이널라이즈 가능 객체는 이미 정리됐을 수 있다 |
| 소유한 객체의 `Dispose()`를 불러도 된다 | 부르면 안 된다 |
| 예외를 던져도 호출자가 처리할 수 있다 | 예외가 escape하면 프로세스가 죽는다 |
| 잠금을 잡아도 된다 | 잡으면 안 된다 |
| 시간이 좀 걸려도 된다 | 짧아야 한다 |

### 최후의 수단 모드에서 할 수 있는 일

목록이 짧다. 정말 짧다.

**할 수 있는 것**

1. 이 객체가 **직접** 소유한 OS 리소스의 해제 — P/Invoke로 얻은 원시 핸들을 `CloseHandle`로 닫는 것 같은 일
2. 생성 시 만든 임시 파일 삭제
3. 값 타입 필드 읽기
4. **파이널라이즈 가능하지 않은** 참조 타입 필드 접근
5. 실패 사실을 정적 컬렉션에 기록하기 (뒤에서 다룬다)

**할 수 없는 것**

| 금지 | 이유 |
|---|---|
| 파이널라이즈 가능한 객체의 메서드 호출 | 이미 파이널라이즈됐을 수 있다 |
| 소유한 객체의 `Dispose()` 호출 | 위와 같다. `disposing == true`일 때만 |
| 잠금 획득 (`lock`, `Monitor`, `Mutex`, ...) | 파이널라이저 스레드가 막히면 큐 전체가 막힌다 |
| 블로킹 대기 (`Task.Wait`, `WaitOne`, I/O 동기 호출) | 위와 같다 |
| 스레드 로컬 저장소 접근 | 실행 스레드가 다르다 |
| 예외를 밖으로 내보내기 | 프로세스 종료 |
| 정적 메서드 호출 (조건부) | 그 메서드가 내부적으로 파이널라이즈된 객체를 건드릴 수 있다 |
| 필드가 초기화됐다고 가정 | 생성자가 실패해도 파이널라이저는 호출된다 |

> **⚠️ 정적 메서드 호출도 안전하지 않다**
>
> 마지막 항목이 자주 간과된다. `Logger.Log("...")` 같은 정적 메서드는 언뜻 안전해 보이지만, 그 내부가 정적 필드에 담긴 인스턴스를 쓰고 그 인스턴스가 파이널라이즈 가능하다면 같은 문제가 재현된다. 정적 필드는 루트이므로 그 인스턴스가 살아 있을 가능성이 높지만, **AppDomain 언로드나 프로세스 종료 국면에서는 그 보장도 사라진다.**
>
> 파이널라이저에서 정적 메서드를 부를 때는 그 메서드의 구현이 무엇에 의존하는지까지 확인해야 한다.

### 왜 순서를 정할 수 없었나 — `StreamWriter`의 교훈

"소유 관계를 보고 순서를 정하면 되지 않나"라는 반문이 자연스럽다. Microsoft가 그렇게 하지 않은 이유를 보여 주는 실제 사례가 있다.

```csharp
FileStream fs = new FileStream("DataFile.dat", FileMode.Create);
StreamWriter sw = new StreamWriter(fs);
sw.Write("Hi there");

sw.Dispose();   // 이렇게 해야 한다
                // StreamWriter.Dispose가 FileStream도 닫는다
```

`StreamWriter`는 자기 버퍼에 데이터를 모았다가 가득 차면 `Stream`에 쓴다. `Dispose`를 부르지 않고 두 객체가 함께 가비지가 되면 어떻게 될까.

- `FileStream`이 먼저 파이널라이즈되면: 파일이 닫힌다. 이어서 `StreamWriter`가 파이널라이즈되면서 닫힌 파일에 쓰려 하고 예외가 난다.
- `StreamWriter`가 먼저 파이널라이즈되면: 데이터가 무사히 기록된다.

순서를 GC가 정할 방법이 없다. 객체들은 서로를 참조할 수 있고 순환도 가능하다. **Microsoft의 해법은 순서를 정하는 것이 아니라 문제를 없애는 것이었다 — `StreamWriter` 타입은 파이널라이저를 지원하지 않는다.** 따라서 버퍼의 데이터를 절대 자동으로 플러시하지 않는다.

`StreamWriter`에 `Dispose`를 부르지 않으면 **데이터가 반드시 손실된다.** 반드시 손실되므로 개발자가 알아차리고 고친다. "가끔 손실"보다 "항상 손실"이 나은 설계라는 판단이다.

> **📌 이 결정이 만든 진단 도구**
>
> .NET Framework에는 관리 디버깅 도우미(MDA, Managed Debugging Assistant)라는 기능이 있어서, `StreamWriter` 객체가 명시적 폐기 없이 수집될 때 `StreamWriterBufferedDataLost` MDA가 발동했다. 디버거에서는 예외가 던져진 것처럼 보인다.
>
> 모던 .NET에는 MDA가 없다. 대신 정적 분석기(예: CA2000 "범위를 벗어나기 전에 개체 삭제")가 같은 역할의 일부를 컴파일 타임에 한다.

### 파이널라이저에서 주입된 의존성을 쓰면 안 되는 이유

"비관리 리소스가 없으니 나는 안전하다"고 생각하기 쉬운 코드를 보자.

```csharp
class LoggedObject
{
    private readonly ILogger _logger;

    public LoggedObject(ILogger logger)
    {
        _logger = logger;
        _logger.Log("Object created.");
    }

    ~LoggedObject()
    {
        _logger.Log("Object finalized.");   // 위험하다
    }
}
```

비관리 리소스는 없다. 객체의 생성과 소멸을 로그로 남기고 싶을 뿐이다. 그런데 `_logger`는 **인터페이스**다. 주입된 구현체가 파이널라이즈 가능한 타입이 아니라고 보장할 수 있는가? 파일에 쓰는 로거라면 내부에 `FileStream`이 있을 것이고, 그것이 파이널라이즈 가능하다. `LoggedObject`의 파이널라이저가 도는 시점에 로거가 이미 자기 스트림을 닫았을 수 있다.

완화책은 있다. 코드 리뷰나 정적 분석으로 "`ILogger` 구현체는 파이널라이즈 가능하지 않아야 한다" 또는 "임계 파이널라이저여야 한다"는 규칙을 강제할 수 있다. 하지만 인터페이스로 주입받는 이상 그 보장은 언제든 깨진다.

> **💡 진짜 해법은 파이널라이저를 쓰지 않는 것이다**
>
> 객체의 수명이 로그로 남길 만큼 중요하다면, 그것은 **명시적 정리 지점이 있어야 하는 객체**라는 뜻이다. `IDisposable`을 구현하고 `Dispose`에서 로그를 남겨라. 시점이 명확하고, 로거의 상태가 정상이며, 예외가 나도 프로세스가 죽지 않는다.
>
> 이 원칙을 한 문장으로 줄이면 이렇다. **파이널라이저는 "혹시 개발자가 `Dispose`를 잊었을 때를 위한 안전망"일 때만 정당하다.** 안전망 이외의 일을 시키는 순간 잘못된 도구를 쓰고 있는 것이다.

### 실패를 기록하는 안전한 방법

파이널라이저 안의 작업이 실패했을 때 그 사실을 남기려면 어떻게 해야 하나. 정교한 로깅 API는 부를 수 없다. 답은 **정적 컬렉션에 자기 자신을 넣는 것**이다.

```csharp
public class TempFileRef
{
    static internal readonly ConcurrentQueue<TempFileRef> FailedDeletions
        = new ConcurrentQueue<TempFileRef>();

    public readonly string FilePath;
    public Exception? DeletionError { get; private set; }

    public TempFileRef(string filePath) { FilePath = filePath; }

    ~TempFileRef()
    {
        try { File.Delete(FilePath); }
        catch (Exception ex)
        {
            DeletionError = ex;
            FailedDeletions.Enqueue(this);   // 부활
        }
    }
}
```

애플리케이션의 다른 부분이 나중에 이 큐에서 항목을 꺼내 제대로 된 로깅을 하면 된다. 파이널라이저 스레드는 큐에 넣는 일만 한다 — 빠르고, 단순하고, 예외를 던지지 않는다.

`ConcurrentQueue<T>`를 쓴 것에는 두 가지 이유가 있다. 첫째, CLR은 **여러 스레드에서 파이널라이저를 병렬 실행할 권리를 유보하고 있다.** 현재 구현은 스레드가 하나지만 그것에 의존하는 코드를 쓰면 안 된다. 둘째, 큐에서 항목을 꺼내는 소비자 스레드가 파이널라이저 스레드와 동시에 돌 것이다.

주석의 "부활"이 눈에 띌 것이다. `this`를 정적 컬렉션에 넣는 순간 이 객체는 다시 도달 가능해진다. 그것이 의도다 — 큐에서 꺼내 처리할 때까지 객체가 살아 있어야 하니까. 부활의 의미와 위험은 다음 절의 주제다.

> **⚠️ `SafeHandle`을 쓰면 이 절 전체가 필요 없다**
>
> 33.7절의 결론을 다시 말하면 이렇다. 원시 핸들을 `SafeHandle` 파생 클래스로 감싸는 순간, 감싸는 클래스는 **파이널라이저를 가질 필요가 없어진다.** `SafeHandle` 자신이 검증된 임계 파이널라이저를 갖고 있기 때문이다.
>
> 이 장에서 파이널라이저의 함정을 길게 나열하는 이유는 파이널라이저를 잘 쓰라는 것이 아니라 **왜 쓰지 말아야 하는지**를 납득시키기 위해서다. 그럼에도 직접 써야 하는 상황이 있다면, 그것은 `SafeHandle`로 표현할 수 없는 리소스(예: 핸들이 아닌 형태의 비관리 상태)를 다룰 때뿐이다.

## 34.4 부활(resurrection)과 임계 파이널라이저

### 부활은 이미 일어나고 있다

34.2절에서 봤듯이, 파이널라이즈 가능한 객체는 **모두** 한 번 부활한다. 도달 불가능으로 판정된 뒤 fReachable 큐라는 루트에 등재되면서 다시 도달 가능해지기 때문이다. 이것은 런타임이 하는 부활이고, 개발자가 인지할 필요는 별로 없다.

문제는 **사용자 코드가 하는 부활**이다. 파이널라이저는 인스턴스 메서드다. `this`에 접근할 수 있다. 그러면 `this`를 전역에서 도달 가능한 곳에 저장하는 것을 막을 방법이 없다.

```csharp
class FinalizableObject
{
    ~FinalizableObject()
    {
        Program.GlobalFinalizableObject = this;   // 부활
    }
}
```

수집 직전이었던 객체가 평범한 도달 가능 객체로 돌아왔다. 이제 정적 필드가 유일한 루트이고, 거기서 다시 다른 그래프로 뻗어 나갈 수도 있다.

### 부활한 객체가 다시 죽으면

두 번째로 도달 불가능해졌을 때 파이널라이저가 다시 호출될까. **호출되지 않는다.**

이유는 34.2절의 1단계로 돌아가면 나온다. 파이널라이제이션 등록은 **할당 시점에** 일어난다. 파이널라이저가 실행되면 그 객체 주소는 fReachable 큐에서 제거되고, 부활은 그것을 파이널라이제이션 큐에 되돌려 놓지 않는다. 큐에 없으니 GC가 발견할 수 없다.

다시 파이널라이즈되게 하려면 명시적으로 재등록해야 한다.

```csharp
class FinalizableObject
{
    ~FinalizableObject()
    {
        Program.GlobalFinalizableObject = this;
        GC.ReRegisterForFinalize(this);           // 다음 번에도 파이널라이즈되도록
    }
}
```

이 조합의 결과는 **불멸의 객체**다. 죽을 때마다 되살아나고, 되살아날 때마다 다시 파이널라이즈 대상이 된다. 절대 회수되지 않는다.

> **⚠️ `ReRegisterForFinalize`를 한 파이널라이저에서 두 번 부르지 마라**
>
> 두 번 부르면 객체가 두 번 등록되고, **파이널라이저가 두 번 더 실행된다.** 조건 분기가 복잡한 파이널라이저에서 실수하기 쉬운 지점이다.
>
> 그리고 `ReRegisterForFinalize`는 34.2절에서 봤듯이 할당 시 등록과 같은 비용(잠금 + 배열 시프트)을 치른다. 저렴한 호출이 아니다.

> **📌 루트에 붙이지 않고 재등록만 해도 불멸이 된다**
>
> `Program.GlobalFinalizableObject = this;` 줄을 빼고 `GC.ReRegisterForFinalize(this);`만 남기면 어떻게 될까. 객체는 어떤 루트에서도 도달 불가능하지만, 재등록되어 파이널라이제이션 큐에 들어간다. 큐가 루트이므로 다음 GC에서 fReachable로 옮겨지고, 파이널라이저가 다시 실행되고, 다시 재등록된다.
>
> **파이널라이제이션 큐만이 유일한 참조인 불멸 객체**가 만들어진다. 실제로 이 기법을 쓰는 코드가 BCL 안에 있다(뒤에서 본다). 다만 이것은 **따라 해야 할 설계 패턴이 아니라 그런 가능성이 있다는 사실**로 알아 두는 것이 맞다.

### 실용적인 부활 — 재시도

부활에도 정당한 쓰임이 있다. 34.3절의 임시 파일 예제를 재시도 구조로 확장해 보자.

```csharp
public class TempFileRef
{
    public readonly string FilePath;
    int _deleteAttempt;

    public TempFileRef(string filePath) { FilePath = filePath; }

    ~TempFileRef()
    {
        try { File.Delete(FilePath); }
        catch
        {
            if (_deleteAttempt++ < 3)
                GC.ReRegisterForFinalize(this);   // 다음 GC에서 다시 시도
        }
    }
}
```

세 번 실패하면 조용히 포기한다. 앞의 `FailedDeletions` 큐와 결합하면 "세 번 시도하고, 그래도 안 되면 기록한다"가 된다.

이 예제에서 눈여겨볼 것은 **재시도 간격이 GC 주기라는 점**이다. 다음 시도는 다음 GC에서 일어난다. 그것이 1초 뒤일 수도, 세 시간 뒤일 수도 있다. 파일 삭제처럼 급하지 않은 일에나 성립한다.

### 부활로 객체 풀을 만들면 왜 안 되는가

부활의 유혹적인 응용이 객체 풀이다. 파이널라이저가 자신을 풀에 되돌려 놓으면, 사용자가 반납을 잊어도 풀이 알아서 회수하지 않겠는가.

```csharp
public class EvilPool<T> where T : class
{
    static private List<T> items = new List<T>();

    static public void ReturnToPool(T obj)
    {
        // items에 obj를 추가한다
        GC.ReRegisterForFinalize(obj);
    }

    static public T GetFromPool() { /* ... */ }
}

public class SomeClass
{
    ~SomeClass()
    {
        EvilPool<SomeClass>.ReturnToPool(this);
    }
}
```

이름이 `EvilPool`인 데는 이유가 있다. **리소스가 언제 반납되는지 제어할 수 없다.**

풀링된 인스턴스는 오래 살아남는다. 오래 살아남으니 세대 2로 승격된다. 세대 2 객체의 파이널라이저는 **세대 2 GC가 일어나야** 실행된다. 서버 애플리케이션에서 세대 2 GC는 몇 시간에 한 번 일어날 수 있다. 즉 반납을 잊은 객체는 몇 시간 동안 풀 밖에 떠 있고, 그 사이 풀은 계속 새 인스턴스를 만든다. **풀의 목적이 정확히 무산된다.**

> **💡 객체 풀은 명시적으로 관리하라**
>
> `ArrayPool<T>` 같은 BCL의 풀은 전부 명시적 `Rent`/`Return` 모델이다(69.3절). 풀 관리를 암묵적으로 만들어서 얻는 이득이 없다 — 반납 시점을 모르는 풀은 풀이 아니라 그냥 캐시다.
>
> 그래도 `EvilPool`을 직접 구현해 보는 것은 학습으로서 가치가 있다. 부활, 재등록, 세대 승격, GC 타이밍이 한 코드에 모두 나타난다.

### 실제 BCL 코드 — `Gen2GcCallback`

부활을 정당하게 쓰는 실제 사례가 .NET 코어 라이브러리 안에 있다. `Gen2GcCallback`은 "대략 세대 2 GC마다 콜백을 실행한다"는 목적의 내부 클래스다.

```csharp
internal sealed class Gen2GcCallback : CriticalFinalizerObject
{
    private Gen2GcCallback(Func<object, bool> callback, object targetObj)
    {
        _callback1 = callback;
        _weakTargetObj = GCHandle.Alloc(targetObj, GCHandleType.Weak);
    }

    public static void Register(Func<object, bool> callback, object targetObj)
    {
        // 콜백과 대상 객체를 기억하는, 도달 불가능한 객체를 만든다
        new Gen2GcCallback(callback, targetObj);
    }

    private Func<object, bool>? _callback1;
    private GCHandle _weakTargetObj;

    ~Gen2GcCallback()
    {
        if (_weakTargetObj.IsAllocated)
        {
            object? targetObj = _weakTargetObj.Target;
            if (targetObj == null)
            {
                // 대상이 죽었다. 이 콜백 객체도 더는 필요 없다
                _weakTargetObj.Free();
                return;                       // 재등록하지 않는다 = 여기서 진짜 죽는다
            }

            try
            {
                if (!_callback1!(targetObj))
                {
                    _weakTargetObj.Free();
                    return;                   // 콜백이 false를 반환하면 종료
                }
            }
            catch { /* 예외가 나도 재등록 기회를 잃지 않도록 */ }
        }

        // 재등록으로 자신을 부활시킨다
        GC.ReRegisterForFinalize(this);
    }
}
```

`Register`가 만든 객체는 **어떤 변수에도 대입되지 않는다.** 처음부터 도달 불가능하다. 그런데도 파이널라이제이션 큐가 붙들고 있으므로 매 GC마다 파이널라이저가 실행되고, 실행될 때마다 스스로를 재등록한다.

여기서 결정적인 부분은 대상 객체를 **짧은 약한 참조**로 붙든다는 점이다. 강한 참조였다면 대상 객체가 절대 죽지 않을 것이고, 콜백은 프로세스가 끝날 때까지 계속 돌 것이다. 약한 참조이므로 **대상이 죽으면 콜백도 스스로 멈춘다.** 부활 루프의 종료 조건을 약한 참조가 제공한다.

`Gen2GcCallback`은 `PinnableBufferCache`에서 세대 2 GC마다 프리 리스트를 정리하는 데 쓰인다. 약한 참조 자체는 34.5절의 주제다.

> **⚠️ 이 코드에 기대지 마라**
>
> 이름의 "Gen2"에도 불구하고 세대 2 GC에서만 실행되는 것이 아니다. 클래스 주석 자체가 "세대 0과 세대 1에서도 (한 번씩) 보게 될 것"이라고 인정한다. 승격이 어떻게 일어나는지에 대한 깊은 구현 세부에 의존하고 있고, 대상 객체가 고정되면(또는 확장된 고정 plug의 일부가 되면) 강등되어 임시 세대 GC에서도 다시 호출될 수 있다.
>
> 이것은 **BCL 내부 코드이고 공개 API가 아니다.** 읽고 배우되 흉내 내지 마라.

### 남이 내 파이널라이저를 조작할 수 있다

`GC.SuppressFinalize`와 `GC.ReRegisterForFinalize`는 **아무 객체나 인수로 받는다.** 파이널라이저를 가진 타입의 인스턴스라면 누구든 그 파이널라이제이션 동작을 바꿀 수 있다.

`System.Threading.Timer`를 생각해 보자. 타이머의 파이널라이제이션은 "스레드 풀에게 이 타이머를 취소하라고 알리는" 일을 한다. 만약 `Timer` 자체가 파이널라이즈 가능한 타입이라면, 외부 코드가 `GC.SuppressFinalize(timer)`를 불러서 **타이머가 영영 멈추지 않게 만들 수 있다.**

.NET의 실제 구현은 이 가능성을 차단한다. 두 단계다.

1. 타입을 `sealed`로 만든다 — 파생 클래스가 `Finalize`를 재정의할 수 없다.
2. 파이널라이제이션 책임을 **중첩된 private 헬퍼 객체**로 옮긴다.

```csharp
public sealed class Timer : IDisposable
{
    private TimerHolder timerHolder;

    public Timer()
    {
        timerHolder = new TimerHolder(this);
    }

    private sealed class TimerHolder
    {
        internal Timer m_timer;

        public TimerHolder(Timer timer) => m_timer = timer;

        ~TimerHolder() => m_timer?.Close();

        public void Close()
        {
            m_timer.Close();
            GC.SuppressFinalize(this);
        }
    }

    public void Close() { /* 실제 정리 */ }

    public void Dispose() => timerHolder.Close();
}
```

`Timer` 인스턴스가 도달 불가능해지면 `timerHolder` 필드도 도달 불가능해지고, `TimerHolder`의 파이널라이저가 부모를 정리한다. **`Timer` 자신은 파이널라이즈 가능하지 않다.** 외부에서 `GC.SuppressFinalize(timer)`를 불러도 아무 효과가 없고, `TimerHolder`는 private 중첩 타입이라 참조를 얻을 수 없다.

> **💡 파이널라이제이션을 공개 표면에서 감추는 관용구**
>
> 이 "홀더" 패턴은 재사용할 만하다. 정리 동작이 타입의 계약에서 중요한 부분이라면, 그것을 외부가 조작할 수 없는 곳에 두는 것이 옳다. 비용은 객체 하나가 추가로 할당된다는 것뿐이다.
>
> 물론 첫 번째 선택지는 여전히 `SafeHandle`이다(33.7절). 홀더 패턴은 리소스가 핸들 형태가 아닐 때 쓴다.

### 임계 파이널라이저

파이널라이저의 신뢰성 문제 — 실행 보장이 없고 순서도 없다 — 를 부분적으로 보완하려고 .NET Framework에 도입된 것이 **임계 파이널라이저(critical finalizer)** 다. `System.Runtime.ConstrainedExecution.CriticalFinalizerObject`에서 파생하면 그 타입의 파이널라이저가 임계 파이널라이저가 된다.

```csharp
public abstract class CriticalFinalizerObject
{
    protected CriticalFinalizerObject() { }
    ~CriticalFinalizerObject() { }
}
```

구현이 비어 있다는 데 주목하라. **이것은 코드가 아니라 타입 시스템과 런타임 사이의 계약**이다. `SafeHandle`이 이 클래스에서 파생되며, CLR이 부여하는 세 가지 특별 대우 — 파이널라이저 사전 JIT 컴파일, 일반 파이널라이저보다 나중에 실행, 호스트의 난폭한 AppDomain 중단에도 실행(.NET Framework 전용) — 은 33.7절에서 다뤘다.

여기서는 그 두 번째 보장이 **어떻게 구현되는가**를 34.2절의 배열 그림과 연결해 보자.

```text
fReachable 부분
┌────────────────────┬────────────────────┐
│      Critical      │       Normal       │
└────────────────────┴────────────────────┘
        ▲                      ▲
        │                      └── 일반 파이널라이저: 먼저 실행된다
        └── 임계 파이널라이저: 나중에 실행된다
```

마크 단계 끝에서 죽은 객체를 fReachable로 옮길 때, GC는 그 객체의 파이널라이저가 임계인지 일반인지에 따라 **다른 그룹에** 넣는다. 파이널라이저 스레드는 Normal 그룹을 먼저 비우고 Critical 그룹을 나중에 비운다.

이것을 Microsoft 문서는 **약한 순서(weak ordering)** 라고 부른다. "같은 GC에서 회수되는 객체들에 대해, 모든 비임계 파이널라이저가 어떤 임계 파이널라이저보다 먼저 호출된다." 임계 파이널라이저들 사이의 순서는 여전히 정의되지 않고, 비임계 파이널라이저들 사이의 순서도 마찬가지다.

이 한 겹의 순서로 무엇을 얻는가. `FileStream`은 일반 파이널라이저를 갖고, 그것이 붙든 `SafeFileHandle`은 임계 파이널라이저를 갖는다. 따라서 **`FileStream`의 파이널라이저는 파일이 아직 닫히지 않았다는 확신을 갖고 버퍼를 플러시할 수 있다.**

| 구분 | 일반 파이널라이저 | 임계 파이널라이저 |
|---|---|---|
| 선언 | `~T()` | `CriticalFinalizerObject` 파생 + `~T()` |
| JIT 컴파일 시점 | 최초 실행 시 | **객체 최초 생성 시 (계층 전체)** |
| 실행 순서 | 임계보다 **먼저** | 일반보다 **나중** |
| fReachable 그룹 | Normal | Critical |
| 저메모리 상황 | 컴파일 실패로 실행 못 할 수 있다 | 이미 컴파일되어 있다 |
| 대표 타입 | `FileStream` 등 | `SafeHandle` 계층 전부 |

> **⚠️ CER은 모던 .NET에서 사실상 죽은 개념이다**
>
> Microsoft 문서는 임계 파이널라이저의 보장을 "파이널라이저가 CER(Constrained Execution Region, 제약 실행 영역)의 규칙을 따르는 한"이라는 조건과 함께 서술한다. CER은 `RuntimeHelpers.PrepareConstrainedRegions()`와 `[ReliabilityContract]` 특성으로 표현하는 .NET Framework 시절의 신뢰성 메커니즘이다.
>
> **모던 .NET에는 AppDomain이 없고, CER API는 호출해도 아무 일도 하지 않는다.** `PrepareConstrainedRegions()`는 no-op이고, `[ReliabilityContract]`는 무시된다. 옛 코드에서 이들을 보면 .NET Framework 유물로 이해하면 된다.
>
> 그럼에도 **임계 파이널라이저의 앞 두 보장(사전 JIT 컴파일, 실행 순서)은 모던 .NET에서 여전히 유효하다.** 그리고 `SafeHandle`을 쓰는 실무적 가치는 대부분 그 두 가지와 참조 카운팅에 있다.

> **📌 직접 `CriticalFinalizerObject`에서 파생할 일은 거의 없다**
>
> 실무에서 이 클래스를 직접 상속할 이유는 사실상 없다. 필요한 것은 대개 `SafeHandle` 파생 클래스이고, 그것이 이미 `CriticalFinalizerObject` 파생이다. 직접 파생이 필요한 경우는 "핸들이 아닌 비관리 상태를 반드시 정리해야 하고, 그 정리가 다른 파이널라이저보다 나중에 일어나야 하는" 매우 드문 상황뿐이다.

## 34.5 약한 참조 — 짧은/긴 약한 참조

### 문제 정의

지금까지 본 참조는 전부 **강한 참조(strong reference)** 다. 강한 참조가 하나라도 있으면 객체는 산다. 그런데 가끔 "붙들지는 않지만 살아 있으면 쓰고 싶다"는 관계가 필요하다.

- 객체 A가 객체 B의 메서드를 주기적으로 부르지만, **A가 B를 살려 두어서는 안 되는** 경우
- 어떤 종류의 객체가 몇 개나 살아 있는지 **관찰만** 하고 싶은 경우
- 캐시에 담아 두되, 메모리 압력이 생기면 놓아 주고 싶은 경우

이런 관계를 표현하는 것이 **약한 참조(weak reference)** 다. 약한 참조는 GC의 도달성 판정에서 세지 않는다.

### 아래층 — GC 핸들 테이블

약한 참조의 실체는 GC 핸들이다. CLR은 **GC 핸들 테이블**을 유지하고, `System.Runtime.InteropServices.GCHandle`이 그 테이블의 항목을 조작하는 API다.

```csharp
public struct GCHandle
{
    public static GCHandle Alloc(object value);
    public static GCHandle Alloc(object value, GCHandleType type);

    public void Free();
    public object? Target { get; set; }
    public bool IsAllocated { get; }
    public IntPtr AddrOfPinnedObject();
    // ...
}
```

`GCHandle` 자체는 테이블 인덱스를 담은 `IntPtr` 하나짜리 가벼운 값 타입이다. 종류는 네 가지다.

| `GCHandleType` | 목적 | 객체를 살리는가 | 이동을 막는가 |
|---|---|---|---|
| `Weak` | 수명 **관찰** (짧은 약한 참조) | 아니오 | 아니오 |
| `WeakTrackResurrection` | 수명 **관찰** (긴 약한 참조) | 아니오 | 아니오 |
| `Normal` | 수명 **제어** | **예** | 아니오 |
| `Pinned` | 수명 **제어** + 주소 고정 | **예** | **예** |

`Normal`과 `Pinned`는 상호운용에 쓴다. 관리 객체의 포인터를 네이티브에 넘겼는데 나중에 네이티브가 그것을 되돌려 줄 때(`Normal`), 또는 비동기 I/O 버퍼처럼 네이티브가 그 메모리에 직접 쓰는 동안 GC가 옮기면 안 될 때(`Pinned`) 쓴다. 고정과 그 부작용은 64.7절의 주제다.

이 장의 관심사는 앞의 두 개다.

### 짧은 약한 참조와 긴 약한 참조

두 종류의 차이는 **파이널라이제이션과의 관계**에 있다.

- **짧은 약한 참조(short weak reference)** — `GCHandleType.Weak`. GC가 객체를 죽은 것으로 판정하는 순간 핸들이 0으로 비워진다. **파이널라이저가 실행되기 전이다.** 파이널라이저가 객체를 부활시켜도 이 핸들은 비워진 채로 남는다.
- **긴 약한 참조(long weak reference)** — `GCHandleType.WeakTrackResurrection`. 파이널라이제이션 때문에 객체가 승격되면 핸들은 여전히 유효하다. 파이널라이저가 객체를 부활시키면 핸들도 계속 그 객체를 가리킨다. 그래서 **부활을 추적한다(track resurrection)** 고 말한다.

이 차이는 GC의 한 사이클 안에서 각 단계가 실행되는 순서로 설명된다.

```text
GC 한 사이클에서 핸들 테이블과 파이널라이제이션 큐가 처리되는 순서

1. 도달 가능한 객체를 마크한다
   그다음 핸들 테이블을 훑어 Normal/Pinned 항목이 가리키는 객체를 마크한다
        │
        ▼
2. 핸들 테이블의 Weak 항목을 훑는다
   마크되지 않은 객체를 가리키면 → 항목을 null로 만든다      ← 짧은 약한 참조가 여기서 끊긴다
        │
        ▼
3. 파이널라이제이션 큐를 훑는다
   마크되지 않은 객체를 발견하면 → fReachable 큐로 옮긴다
   이 시점에 그 객체는 다시 마크된다 (부활)
        │
        ▼
4. 핸들 테이블의 WeakTrackResurrection 항목을 훑는다
   여전히 마크되지 않은 객체를 가리키면 → 항목을 null로 만든다   ← 긴 약한 참조가 여기서 끊긴다
        │
        ▼
5. 메모리를 압축한다 (Pinned 객체는 제자리)
```

2단계와 4단계 사이에 3단계가 끼어 있다는 것이 전부다. 3단계에서 부활한 객체는 4단계 시점에 마크되어 있으므로 긴 약한 참조는 살아남고, 짧은 약한 참조는 이미 2단계에서 끊겼다.

확인해 보자. 파이널라이저에서 자신을 재등록하는 클래스를 준비한다.

```csharp
public class LargeClass
{
    private readonly bool _resurrect;

    public LargeClass(bool resurrect) => _resurrect = resurrect;

    ~LargeClass()
    {
        if (_resurrect)
            GC.ReRegisterForFinalize(this);
    }
}
```

짧은 약한 핸들로 관찰하면 이렇다.

```csharp
var obj = new LargeClass(resurrect: true);
GCHandle weakHandle = GCHandle.Alloc(obj, GCHandleType.Weak);
obj = null;

GC.Collect();
GC.WaitForPendingFinalizers();
GC.Collect();

Console.WriteLine(weakHandle.Target ?? "<null>");   // <null>
```

긴 약한 핸들로 바꾸면 결과가 달라진다.

```csharp
var obj = new LargeClass(resurrect: true);
GCHandle weakHandle = GCHandle.Alloc(obj, GCHandleType.WeakTrackResurrection);
obj = null;

GC.Collect();
GC.WaitForPendingFinalizers();
GC.Collect();

Console.WriteLine(weakHandle.Target ?? "<null>");   // LargeClass
```

| 질문 | 짧은 약한 참조 | 긴 약한 참조 |
|---|---|---|
| 언제 끊기는가 | GC가 죽었다고 판정한 순간 | 파이널라이저 실행 후 진짜 회수될 때 |
| `Target`이 non-null일 때 확실한 것 | 객체가 아직 메모리에 있다 | 객체가 메모리에 있고 아직 파이널라이즈 전이거나 부활했다 |
| `Target`이 null일 때 확실한 것 | 애플리케이션에서 도달 불가능하다 (파이널라이저는 실행 전일 수도 있다) | 파이널라이저가 실행됐고 메모리가 회수됐다 |
| 실무 사용 빈도 | 압도적으로 많다 | 극히 드물다 |

> **📌 긴 약한 참조를 실제로 쓰는 사람을 본 적이 없다**
>
> 원천 도서(CLR via C#)의 저자도 "실제 애플리케이션에서 `WeakTrackResurrection`을 쓰는 것을 본 적이 없다"고 적고 있다. 이 플래그가 답하는 질문 — "이 객체의 메모리가 정말로 회수되었는가" — 이 실무에서 거의 나오지 않기 때문이다.
>
> 진단 도구를 만들거나 GC 동작을 실험할 때는 유용하다. 34.9절의 `ConditionalWeakTable` 예제가 그런 용도다.

### 위층 — `WeakReference`와 `WeakReference<T>`

`GCHandle`을 직접 쓰는 것은 번거롭고, `Normal`·`Pinned` 핸들을 만들려면 높은 신뢰 수준이 필요하다. 그래서 약한 참조만 감싼 클래스가 따로 있다.

**비제네릭 `WeakReference`** — 세 멤버가 핵심이다.

| 멤버 | 의미 |
|---|---|
| `IsAlive` | 대상이 아직 살아 있는가 |
| `Target` | 대상 참조 (죽었으면 `null`) |
| `TrackResurrection` | 이 참조가 부활을 추적하는가 (긴 약한 참조인가) |

```csharp
var sb = new StringBuilder("this is a test");
var weak = new WeakReference(sb);
Console.WriteLine(weak.Target);   // this is a test
```

이 API에는 설계 결함이 있다.

```csharp
var obj = new LargeClass(resurrect: false);
WeakReference weakReference = new WeakReference(obj, trackResurrection: false);
obj = null;

if (weakReference.IsAlive)
{
    GC.Collect();                                        // 다른 스레드가 유발했다고 가정
    Console.WriteLine(weakReference.Target ?? "<null>");  // <null>일 수 있다
}
```

**`IsAlive`가 `true`를 반환한 직후에 GC가 일어나면 `Target`은 `null`이다.** 검사와 사용 사이에 창이 있다. 게다가 `Target`이 `object`를 반환하므로 캐스팅이 필요하다.

**제네릭 `WeakReference<T>`** — .NET Framework 4.5에서 도입되어 두 문제를 모두 고쳤다.

```csharp
public sealed class WeakReference<T> where T : class
{
    public WeakReference(T target);
    public WeakReference(T target, bool trackResurrection);

    public void SetTarget(T target);
    public bool TryGetTarget(out T target);
}
```

`TryGetTarget`은 생존 여부 확인과 참조 획득을 **원자적으로** 수행한다. 그리고 `out` 매개변수에 대입되는 순간 그것은 지역 변수, 즉 강한 루트다. 그 변수를 쓰는 동안 객체는 수집되지 않는다.

```csharp
var weakReference = new WeakReference<LargeClass>(obj, trackResurrection: false);

if (weakReference.TryGetTarget(out var target))
{
    // 여기서 target은 강한 참조다. 안심하고 쓸 수 있다
    Console.WriteLine(target);
}
```

> **⚠️ 비제네릭 `WeakReference`를 쓸 때는 `Target`을 먼저 지역 변수에 담아라**
>
> 레거시 코드에서 `WeakReference`를 마주쳤을 때의 안전한 관용구는 이것이다.
>
> ```csharp
> var sb = (StringBuilder?)weak.Target;
> if (sb != null) { /* sb를 쓴다 */ }
> ```
>
> `weak.Target`을 조건문과 본문에서 각각 읽으면 그 사이에 수집될 수 있다. **한 번 읽어 지역 변수에 담고, 그 변수만 쓴다.** 지역 변수가 강한 루트가 되어 사용 구간 동안 객체를 붙든다.
>
> 새 코드에서는 `WeakReference<T>`를 쓰면 이 문제 자체가 없다.

### 비용

약한 참조는 공짜가 아니다.

| 비용 항목 | 내용 |
|---|---|
| 힙 할당 | `WeakReference`/`WeakReference<T>` 인스턴스 자체가 힙 객체다 |
| 핸들 테이블 항목 | 프로세스 전역 테이블에 항목이 하나 늘어난다 |
| GC 시간 | 매 GC마다 핸들 테이블의 약한 항목을 전부 훑어야 한다 |
| 파이널라이제이션 | 래퍼 객체가 파이널라이저를 통해 핸들을 `Free`한다 |

마지막 항목이 중요하다. `WeakReference`는 대상이 죽을 때 핸들 테이블 항목을 반납해야 하고, 그 반납을 파이널라이저로 한다. **약한 참조를 만들 때마다 파이널라이즈 가능한 객체를 하나 만드는 것이다.** 34.2절의 비용이 전부 따라온다.

| 선택지 | 무게 | 언제 |
|---|---|---|
| `GCHandle` (`Weak`) | 가장 가볍다. 값 타입이고 힙 할당이 없다 | 명시적으로 `Free`할 지점이 확실할 때 |
| `WeakReference<T>` | 힙 객체 하나 + 핸들 + 파이널라이저 | 일반적인 경우. 타입 안전하고 API가 안전하다 |
| `WeakReference` | 위와 같지만 API가 위험하다 | 레거시 호환 |

> **⚠️ 약한 참조를 대량으로 만들지 마라**
>
> 항목이 수십만 개인 컬렉션의 모든 원소를 약한 참조로 감싸면, 힙 객체 수십만 개 + 핸들 테이블 항목 수십만 개 + 파이널라이즈 가능 객체 수십만 개가 생긴다. **GC가 매번 그 전부를 훑는다.**
>
> 이것이 27.7절에서 약한 이벤트를 "마지막 수단"으로 분류한 이유이기도 하다. 이벤트 구독은 수가 예측 불가능하게 늘어날 수 있는 대표적인 대상이다.

### 관찰 용도 — 살아 있는 인스턴스 추적

약한 참조의 가장 논란 없는 용도는 **관찰**이다. 다음 클래스는 생성된 모든 `Widget`을 추적하되 그것들을 살려 두지 않는다.

```csharp
class Widget
{
    static List<WeakReference<Widget>> _allWidgets = new();

    public readonly string Name;

    public Widget(string name)
    {
        Name = name;
        _allWidgets.Add(new WeakReference<Widget>(this));
    }

    public static void ListAllWidgets()
    {
        foreach (var weak in _allWidgets)
            if (weak.TryGetTarget(out var w))
                Console.WriteLine(w.Name);
    }
}
```

한 가지 문제가 남는다. **정적 리스트가 계속 자란다.** 대상이 죽어도 `WeakReference<Widget>` 객체 자체는 리스트에 남아 있다. 대상이 `null`인 항목을 주기적으로 걷어 내는 정리 전략이 반드시 필요하다.

> **💡 실험과 진단에는 대단히 유용하다**
>
> "이 객체가 정말로 수집되는가"를 확인하는 가장 간단한 방법이 약한 참조다. 단위 테스트로 누수 회귀를 잡을 수 있다.
>
> ```csharp
> var weak = CreateAndForget();          // 대상을 만들고 참조를 버리는 지역 메서드
> GC.Collect();
> GC.WaitForPendingFinalizers();
> GC.Collect();
> Assert.False(weak.TryGetTarget(out _));   // 수집되었어야 한다
> ```
>
> 단, 대상을 만드는 코드를 **별도 메서드로 분리**해야 한다. 같은 메서드 안에 지역 변수로 두면 즉시 루트 수집이 동작하지 않는 빌드(디버그, 계층 0)에서 테스트가 실패한다. 그리고 이 테스트는 릴리스 빌드에서만 신뢰할 수 있다.

### 강한 참조와 약한 참조 사이를 오가기

약한 참조를 강한 참조로 바꾸는 것은 간단하다 — 대상을 도달 가능한 곳에 대입하면 된다. 반대도 마찬가지로 그 대입을 지우면 된다. BCL 내부의 `StrongToWeakReference<T>`가 이 전환을 캡슐화한 것이다.

```csharp
internal sealed class StrongToWeakReference<T> : WeakReference where T : class
{
    private T? _strongRef;

    public StrongToWeakReference(T obj) : base(obj)
    {
        _strongRef = obj;
    }

    public void MakeWeak() => _strongRef = null;

    public void MakeStrong() => _strongRef = WeakTarget;

    public new T? Target => _strongRef ?? WeakTarget;

    private T? WeakTarget => base.Target as T;
}
```

`_strongRef`가 `null`이 아니면 강한 참조로 동작하고, `null`이면 약한 참조로 동작한다. `MakeStrong()`은 대상이 이미 수집되었으면 조용히 실패한다 — 실무 코드라면 `bool TryMakeStrong()` 형태가 더 낫다.

이 클래스가 34.6절의 캐시 전략의 재료다.

## 34.6 약한 참조와 캐시, 약한 참조와 이벤트

### 순진한 약한 캐시가 실패하는 이유

약한 참조를 배우면 거의 모든 사람이 같은 생각을 한다. "큰 데이터를 약한 참조로 캐시하면, 메모리가 필요할 때 GC가 알아서 버려 주지 않을까?"

```csharp
private WeakReference<BigGraph>? _weakCache;

public BigGraph GetData()
{
    if (_weakCache is not null && _weakCache.TryGetTarget(out var cached))
        return cached;

    var fresh = RebuildExpensiveGraph();
    _weakCache = new WeakReference<BigGraph>(fresh);
    return fresh;
}
```

**동작은 한다. 그런데 캐시 히트율이 처참하다.**

이유는 이 한 문장이다. **GC는 메모리가 부족할 때만 도는 것이 아니다.** GC는 세대 0의 할당 예산이 찼을 때 돈다. 정상적인 메모리 상황에서도 초당 수십 번 돌 수 있다. 캐시 항목이 세대 0에 있으면 **마이크로초 단위**로 수집될 수 있다.

즉 위 코드는 "메모리가 빠듯할 때 캐시를 비우는" 것이 아니라 "아무 때나 캐시를 비우는" 것이다. `RebuildExpensiveGraph()`가 계속 호출되고 성능은 캐시가 없을 때보다 나빠진다 — 약한 참조 관리 비용까지 얹혔으니까.

> **⚠️ "GC가 메모리 압력을 알려 주면 되지 않나"**
>
> CLR은 애플리케이션에게 "메모리가 빠듯해지고 있다"를 알려 주는 범용 메커니즘을 오랫동안 제공하지 않았다. 옛 문헌은 Win32 `GlobalMemoryStatusEx`를 주기적으로 불러 `MEMORYSTATUSEX.dwMemoryLoad`가 80을 넘는지 보라고 권한다.
>
> 모던 .NET에는 `GC.GetGCMemoryInfo()`가 있어서 마지막 GC 시점의 메모리 부하와 힙 하드 리밋 관련 정보를 얻을 수 있다(※.NET Core 3.0, 65.8절). 그러나 이것도 **마지막 GC 시점의 스냅숏**이고, 폴링 기반이라는 성격은 그대로다. 캐시 정책을 이 값에 직접 묶기 전에 65장의 지연 시간 모드와 하드 리밋 논의를 함께 읽는 편이 좋다.

### 2단계 캐시 — 강한 참조를 시간이 지나면 약하게

쓸 만한 약한 캐시를 만들려면 **강한 참조로 시작해서 시간이 지나면 약한 참조로 강등**하는 구조가 필요하다. 34.5절의 `StrongToWeakReference<T>`에 "언제 강해졌는지"를 기록하는 `StrongTime` 필드를 추가했다고 하자.

```csharp
public class WeakEvictionCache<TKey, TValue> where TValue : class
{
    private readonly TimeSpan _weakEvictionThreshold;
    private Dictionary<TKey, StrongToWeakReference<TValue>> _items;

    public WeakEvictionCache(TimeSpan weakEvictionThreshold)
    {
        _weakEvictionThreshold = weakEvictionThreshold;
        _items = new Dictionary<TKey, StrongToWeakReference<TValue>>();
    }

    public void Add(TKey key, TValue value)
    {
        ArgumentNullException.ThrowIfNull(value);
        _items.Add(key, new StrongToWeakReference<TValue>(value));
    }

    public bool TryGet(TKey key, out TValue? result)
    {
        result = null;
        if (_items.TryGetValue(key, out var value))
        {
            result = value.Target;
            if (result != null)
            {
                value.MakeStrong();     // 사용됐으므로 다시 강하게
                return true;
            }
        }
        return false;
    }

    public void DoWeakEviction()
    {
        var toRemove = new List<TKey>();

        foreach (var pair in _items)
        {
            var reference = pair.Value;
            var target = reference.Target;

            if (target != null)
            {
                if (DateTime.Now - reference.StrongTime >= _weakEvictionThreshold)
                    reference.MakeWeak();       // 시간이 지났으므로 약하게 강등
            }
            else
            {
                toRemove.Add(pair.Key);         // 이미 죽었으므로 항목 제거
            }
        }

        foreach (var key in toRemove)
            _items.Remove(key);
    }
}
```

핵심은 **약한 강등이 곧 제거가 아니라는 것**이다. 일반 캐시라면 만료 시각이 지난 항목을 무조건 제거한다. 이 캐시는 만료 후 약한 참조로 바꾸기만 한다. **애플리케이션의 다른 부분이 아직 그 객체를 쓰고 있다면 살아남는다.** 그래서 만료됐지만 여전히 사용 중인 항목을 성급하게 버리지 않는다.

| 캐시 전략 | 항목이 사라지는 조건 | 문제 |
|---|---|---|
| 순수 약한 참조 캐시 | 다음 GC | 히트율이 사실상 0에 가깝다 |
| 시간 기반 강한 캐시 | 만료 시각 도달 | 사용 중인 객체를 버리고 중복 생성한다 |
| 약한 강등 캐시 | 만료 후 + 아무도 안 쓸 때 | 구현이 복잡하고 강등 스위프가 필요하다 |
| `ConditionalWeakTable` | 키가 죽을 때 (34.9절) | 캐시가 아니라 부착 데이터용이다 |

> **⚠️ 위 코드는 뼈대일 뿐이다**
>
> 스레드 안전성이 전혀 없다. `Dictionary<TKey, TValue>`는 동시 접근을 견디지 못하고, `DoWeakEviction`이 도는 동안 `TryGet`이 호출되면 깨진다. `DateTime.Now`를 쓰는 것도 문제다 — 시스템 시간 변경에 취약하다(`Environment.TickCount64`나 `Stopwatch`가 낫다).
>
> 그리고 `DoWeakEviction`을 **누가 언제 부를 것인가**라는 질문이 남는다. 타이머로 부르면 그 타이머가 캐시를 살려 두고, 그 문제는 34.10절의 주제다.
>
> 실무에서는 `Microsoft.Extensions.Caching.Memory`의 `MemoryCache` 같은 검증된 구현을 먼저 검토하라. 크기 제한, 만료 정책, 축출 콜백이 이미 들어 있다.

### 약한 참조와 이벤트 — 수명 관점

이벤트가 메모리 누수를 만드는 메커니즘과 그 해결책의 구현은 27.6절과 27.7절에 있다. 여기서는 **수명 관점의 세 가지 사실**만 정리한다.

**첫째, 델리게이트는 대상 객체의 강한 루트다.** 델리게이트는 `Target`(호출할 인스턴스)과 `Method`(호출할 메서드)의 쌍이다. 인스턴스 메서드를 구독하면 델리게이트가 그 인스턴스를 `_target` 필드에 담는다. 이벤트를 가진 객체(소스)가 그 델리게이트를 붙들고 있으므로, **소스가 구독자(대상)를 살린다.**

**둘째, 누수의 심각도는 소스와 대상의 수명 차이에 비례한다.** 소스가 대상보다 오래 사는 만큼, 그리고 대상이 무거운 만큼 나빠진다. 최악은 정적 이벤트다 — 정적 필드는 프로세스 수명 동안 살아 있으므로 구독자가 **절대** 회수되지 않는다.

**셋째, 약한 이벤트는 "발화 시점에 대상이 죽어 있을 수 있다"는 새 조건을 만든다.** 대상이 도달 불가능해진 순간과 GC가 그것을 확인하는 순간 사이에 시간 차가 있다. 그 사이에 이벤트가 발화하면 **이미 논리적으로 죽은 객체의 핸들러가 실행된다.** 약한 이벤트를 쓰려면 핸들러가 그 상황에서도 안전해야 한다.

> **⚠️ 약한 이벤트에 람다를 등록하면 조용히 사라진다**
>
> ```csharp
> // 이 구독은 다음 GC에서 사라진다
> weakEvent.Subscribe((s, e) => Console.WriteLine("clicked"));
> ```
>
> 람다는 컴파일러가 만든 클로저 객체의 인스턴스 메서드다. 그 클로저 객체를 강하게 참조하는 것이 아무것도 없다면 — 그리고 보통 없다 — 약한 이벤트는 그것을 살려 두지 않는다. **구독이 조용히 없어지고, 아무 예외도 나지 않는다.** 디버깅하기 최악인 부류의 버그다.
>
> 약한 이벤트에는 반드시 **수명이 명확한 객체의 인스턴스 메서드**를 등록해야 한다.

> **📌 왜 .NET 이벤트는 기본적으로 약하지 않은가**
>
> "이벤트가 처음부터 약한 참조였다면 이 모든 문제가 없었을 텐데"라는 생각이 자연스럽다. 그렇게 하지 않은 이유가 몇 가지 있다.
>
> - **직관에 어긋난다.** 핸들러를 등록했으면 그 대상이 살아 있으리라 기대하는 것이 보통이다.
> - **비용.** 약한 이벤트는 약한 핸들을 요구하고, 핸들에는 성능·메모리 오버헤드가 있다. 이벤트의 사용 규모는 무제한이다 — UI 이벤트 수십 개를 상정하고 만들어도 실제로는 수백만 인스턴스가 될 수 있다.
> - **대부분의 경우 해지 시점이 명확하다.** 잘 설계된 코드에는 "여기서 구독을 끊는다"고 말할 수 있는 지점이 있다.
>
> Microsoft 문서가 WPF의 약한 이벤트에 대해 쓴 표현이 정확하다. "이벤트 소스의 수명이 이벤트 수신자와 **독립적일 때** 약한 이벤트 패턴을 쓴다." 그런 독립적 수명은 생각보다 드물다.

## 34.7 `Lazy<T>`, `LazyInitializer`와 지연 초기화

### 왜 수명 장에 지연 초기화가 있는가

지연 초기화는 **객체의 탄생 시점을 뒤로 미루는 도구**다. 수명의 시작점을 옮기는 것이므로 이 장의 주제다. 그리고 미룬다는 결정에는 수명과 관련된 대가가 따른다 — 미루는 동안 **팩터리 델리게이트와 그것이 캡처한 것들이 살아 있어야** 한다.

### 문제 — 안 쓸지도 모르는 비싼 필드

```csharp
class AllTracks
{
    private Song[] _allSongs = new Song[10000];

    public AllTracks()
    {
        // 여기서 배열을 채운다고 하자
        Console.WriteLine("Filling up the songs!");
    }
}

class MediaPlayer
{
    private AllTracks _allSongs = new AllTracks();   // 항상 만들어진다

    public void Play()  { }
    public void Pause() { }
    public void Stop()  { }

    public AllTracks GetAllTracks() => _allSongs;
}
```

`MediaPlayer`를 만들기만 해도 `Song` 객체 1만 개가 생긴다. `GetAllTracks()`를 부르지 않는 사용자에게는 전부 낭비다.

### 문법 — `Lazy<T>`

```csharp
class MediaPlayer
{
    private Lazy<AllTracks> _allSongs = new Lazy<AllTracks>();

    public AllTracks GetAllTracks() => _allSongs.Value;
}
```

`Value` 속성을 처음 읽는 순간 `AllTracks`가 만들어지고, 이후에는 같은 인스턴스가 반환된다. 기본 생성자 대신 다른 생성 로직을 쓰려면 `Func<T>` 팩터리를 넘긴다.

```csharp
private Lazy<AllTracks> _allSongs =
    new Lazy<AllTracks>(() =>
    {
        Console.WriteLine("Creating AllTracks object!");
        return new AllTracks();
    });
```

`IsValueCreated` 속성으로 값이 아직 만들어지지 않았는지 확인할 수 있다.

```csharp
Lazy<string> s = new Lazy<string>(() => DateTime.Now.ToLongTimeString(), true);

Console.WriteLine(s.IsValueCreated);   // False — 아직 Value를 읽지 않았다
Console.WriteLine(s.Value);            // 여기서 델리게이트가 실행된다
Console.WriteLine(s.IsValueCreated);   // True

Thread.Sleep(10000);
Console.WriteLine(s.Value);            // 델리게이트가 다시 실행되지 않는다 — 같은 시각이 나온다
```

### 수명 관점 — 팩터리가 무엇을 붙드는가

여기가 이 절의 핵심이다. `Lazy<T>`는 값이 만들어질 때까지 **팩터리 델리게이트를 붙들고 있어야 한다.** 그리고 팩터리가 람다라면 그것이 캡처한 변수들도 함께 산다.

```csharp
class Report
{
    private readonly Lazy<Summary> _summary;

    public Report(HugeDataSet data)
    {
        // data를 캡처했다
        _summary = new Lazy<Summary>(() => Summary.Build(data));
    }
}
```

`Value`를 한 번도 읽지 않으면 `HugeDataSet`은 **`Report`가 살아 있는 내내 살아 있다.** 지연 초기화로 메모리를 아끼려 했는데, 캡처된 입력이 그보다 더 클 수 있다. "만들지 않아서 절약했다"고 생각한 만큼을 "만들 준비를 하느라" 붙들고 있는 것이다.

> **⚠️ 클로저 캡처가 지연 초기화의 이득을 상쇄할 수 있다**
>
> 판단 기준은 간단하다. **팩터리가 캡처한 것들의 크기와 만들어질 값의 크기를 비교하라.** 캡처가 더 크거나 비슷하면 지연 초기화의 메모리 이득은 없고 복잡도만 늘어난다.
>
> 캡처를 피하려면 팩터리를 정적 메서드로 만들거나, 캡처 대상을 이미 다른 이유로 살아 있는 필드에서 읽도록 바꾼다. 클로저가 무엇을 캡처하는지 판단하는 규칙은 26장에 있다.

> **📌 `Lazy<T>`는 객체를 하나 더 만든다**
>
> `Lazy<T>` 자체가 힙 객체다. 필드 하나를 지연 초기화하려고 래퍼 객체 하나와 델리게이트 객체 하나(그리고 클로저가 있으면 클로저 객체 하나)를 추가한다. 그리고 `Value`를 읽을 때마다 간접 참조가 한 단계 늘어난다.
>
> 값이 크면 이 오버헤드는 무시할 만하다. 값이 작거나, 지연 초기화할 필드가 아주 많거나, 접근이 초당 수백만 번이면 무시할 수 없다. 그럴 때 쓰는 것이 뒤에 나오는 `LazyInitializer`다.

### 스레드 안전성 — `LazyThreadSafetyMode` 세 가지

여러 스레드가 동시에 `Value`를 읽으면 어떻게 되는가. 답은 생성 시 지정한 모드에 달렸다.

```csharp
public enum LazyThreadSafetyMode
{
    None,                       // 스레드 안전성 지원 없음
    PublicationOnly,            // Interlocked.CompareExchange 기법
    ExecutionAndPublication     // 이중 검사 잠금 기법
}
```

| 모드 | 팩터리가 몇 번 실행되나 | 잠금 | 언제 |
|---|---|---|---|
| `None` | 정의되지 않음 (경합 시 깨진다) | 없음 | 단일 스레드 컨텍스트가 확실할 때 (GUI 스레드 등) |
| `PublicationOnly` | 경합한 스레드 수만큼 실행될 수 있다. 게시되는 값은 하나 | 없음 (`Interlocked.CompareExchange`) | 생성이 싸고 부작용이 없을 때 |
| `ExecutionAndPublication` | 정확히 한 번 | 있음 (이중 검사 잠금) | 기본값. 생성이 비싸거나 부작용이 있을 때 |

생성자의 `bool isThreadSafe` 인수는 이 열거형의 축약이다. `true`는 `ExecutionAndPublication`, `false`는 `None`이다.

**`ExecutionAndPublication`이 쓰는 이중 검사 잠금**은 잠금을 잡기 전에 휘발성 읽기(volatile read)를 한 번 더 해서, 이미 초기화되었으면 잠금 획득 비용을 아예 지불하지 않는 기법이다. 정확한 구현과 메모리 모델상의 근거는 48.13절에 있다.

**`PublicationOnly`가 쓰는 기법**은 잠금 대신 원자적 교체다. 싱글턴 패턴으로 쓰면 이런 모양이다.

```csharp
internal sealed class Singleton
{
    private static Singleton? s_value = null;

    private Singleton() { /* 초기화 */ }

    public static Singleton GetSingleton()
    {
        if (s_value != null) return s_value;

        Singleton temp = new Singleton();

        // 다른 스레드가 먼저 넣지 않았다면 내 것을 넣는다
        Interlocked.CompareExchange(ref s_value, temp, null);

        // 경쟁에서 진 쪽의 객체는 나중에 GC가 회수한다
        return s_value;
    }
}
```

여러 스레드가 동시에 진입하면 `Singleton` 객체가 여러 개 만들어질 수 있지만, `s_value` 필드에 게시되는 것은 하나뿐이다. 나머지는 곧바로 가비지가 된다.

장점은 명확하다. **빠르고, 스레드를 절대 막지 않는다.** 스레드 풀 스레드가 `Monitor` 같은 커널 모드 동기화 구조에서 블로킹되면 스레드 풀이 CPU를 놀리지 않으려고 새 스레드를 만든다 — 메모리가 더 할당되고 모든 DLL이 스레드 연결 알림을 받는다. `CompareExchange`에는 그런 일이 없다.

> **⚠️ `PublicationOnly`에서 버려지는 인스턴스는 폐기되지 않는다**
>
> 이 모드의 대가가 여기 있다. 경쟁에서 진 인스턴스는 **아무도 `Dispose`를 부르지 않는다.** 초기화 대상이 `IDisposable`이면 — 파일을 열거나 소켓을 잡는 객체라면 — 리소스가 샌다.
>
> 그 외의 조건도 있다.
> - 코어 수보다 많은 스레드가 경합하면 오히려 느리다.
> - 중복 초기화로 CPU를 낭비한다.
> - **초기화 로직 자체가 스레드 안전해야 한다.** 생성자가 정적 필드에 쓰면 깨진다.
> - 생성자에 부작용이 있으면 그 부작용이 여러 번 일어난다.
>
> **생성자에 부작용이 없고 반환 값이 폐기 대상이 아닐 때만** 이 모드를 쓸 수 있다.

### `LazyInitializer` — 래퍼 객체 없이

메모리가 빠듯하거나 지연 초기화할 필드가 아주 많으면 `Lazy<T>` 인스턴스조차 만들고 싶지 않을 수 있다. `System.Threading.LazyInitializer`의 정적 메서드들은 **당신의 필드를 직접 조작한다.**

```csharp
public static class LazyInitializer
{
    // 내부적으로 Interlocked.CompareExchange를 쓴다
    public static T EnsureInitialized<T>(ref T target) where T : class;
    public static T EnsureInitialized<T>(ref T target, Func<T> valueFactory) where T : class;

    // syncLock을 Monitor.Enter/Exit에 넘긴다
    public static T EnsureInitialized<T>(ref T target, ref bool initialized, ref object syncLock);
    public static T EnsureInitialized<T>(ref T target, ref bool initialized,
                                         ref object syncLock, Func<T> valueFactory);
}
```

사용법은 필드 접근 앞에 한 줄을 넣는 것이다.

```csharp
Expensive _expensive;

public Expensive Expensive
{
    get
    {
        LazyInitializer.EnsureInitialized(ref _expensive, () => new Expensive());
        return _expensive;
    }
}
```

두 번째 호출은 이미 값이 있으므로 델리게이트를 실행하지 않는다.

```csharp
string? name = null;

LazyInitializer.EnsureInitialized(ref name, () => "Jeffrey");
Console.WriteLine(name);   // Jeffrey

LazyInitializer.EnsureInitialized(ref name, () => "Richter");
Console.WriteLine(name);   // 여전히 Jeffrey — 델리게이트가 실행되지 않았다
```

`syncLock`을 명시적으로 넘기는 오버로드에는 별도의 이점이 있다. **여러 초기화 함수와 필드를 같은 잠금으로 보호할 수 있다.**

| 비교 항목 | `Lazy<T>` | `LazyInitializer` |
|---|---|---|
| 추가 힙 객체 | 래퍼 하나 | 없음 |
| 접근 시 간접 참조 | 한 단계 더 | 필드 직접 |
| 스레드 안전 모드 선택 | 세 가지 전부 | 오버로드로 두 가지 (경쟁형 / `Monitor` 기반) |
| `IsValueCreated` 조회 | 있다 | `initialized` 플래그를 직접 관리 |
| 값 타입 지원 | `Lazy<T>`는 값 타입도 가능 | `where T : class` 제약이 붙은 오버로드가 있다 |
| 가독성 | 좋다 | 호출 지점마다 반복된다 |

> **💡 기본은 `Lazy<T>`다**
>
> `LazyInitializer`는 **극단적인 최적화**를 위한 도구다. 마이크로벤치마크로 `Lazy<T>`의 래퍼 할당이 실제로 문제가 된다는 것을 확인한 다음에 쓰는 것이지, 처음부터 고를 것이 아니다.
>
> 그리고 `LazyInitializer`를 쓰면 필드가 `null`인 상태가 코드에 노출되므로 널 가능 참조 형식(21장)의 관점에서 다루기 번거로워진다. 접근자에서 반드시 `EnsureInitialized`를 먼저 부른다는 규약을 사람이 지켜야 한다.

> **⚠️ 지연 초기화는 초기화 순서 문제를 감춘다**
>
> 필드를 생성자에서 채우면 "이 객체가 만들어진 시점에 그 값이 준비되어 있다"가 명확하다. 지연 초기화하면 **값이 만들어지는 시점이 첫 접근 시점**이 되고, 그 시점의 프로그램 상태가 무엇인지는 코드를 읽어서 알기 어렵다.
>
> 팩터리가 다른 지연 필드를 읽고, 그 필드의 팩터리가 다시 첫 번째 필드를 읽으면 무한 재귀나 데드락이 된다. **지연 초기화 팩터리 안에서 다른 지연 필드를 건드리지 마라.**

## 34.8 `GC.KeepAlive`가 필요한 순간

### 문제 재현

34.1절에서 "지역 변수의 생존 범위는 마지막 사용 지점까지"라고 했다. 그 규칙이 `this`에도 적용된다는 것을 보자.

```csharp
public class ProblematicFileWrapper
{
    private IntPtr handle;

    public ProblematicFileWrapper(string filename)
    {
        handle = Native.OpenFile(filename);
    }

    ~ProblematicFileWrapper()
    {
        if (handle != IntPtr.Zero)
            Native.CloseHandle(handle);
    }

    public int UseMe()
    {
        var hnd = this.handle;      // 이 줄 이후로 this는 쓰이지 않는다

        // 인라인되지 않을 만큼 긴 정상 코드
        // ...
        // 여기서 GC가 일어나고 파이널라이저가 실행될 시간이 있었다고 하자

        byte[] buffer = new byte[1];
        if (Native.ReadFile(hnd, buffer, 1, out uint read, IntPtr.Zero))
            return buffer[0];

        return -1;
    }
}
```

`hnd`에 핸들 값을 복사한 순간부터 `this`는 어느 루트에서도 참조되지 않는다. **메서드가 실행되는 도중에 자기 자신이 수집되고 파이널라이즈된다.** 파이널라이저가 핸들을 닫으므로 그다음 `Native.ReadFile` 호출이 실패한다. `UseMe`는 -1을 반환한다.

관리 스트림으로 바꿔도 같다.

```csharp
class ProblematicObject
{
    Stream stream;

    public ProblematicObject() => stream = File.OpenRead(@"C:\Temp.txt");

    ~ProblematicObject()
    {
        stream.Close();
    }

    public int UseMe()
    {
        var localStream = this.stream;
        // ...
        return localStream.ReadByte();   // ObjectDisposedException: Cannot access a closed file
    }
}
```

> **⚠️ 지역 변수로 복사하지 않아도 문제는 남는다**
>
> "마지막 줄을 `return this.stream.ReadByte();`로 바꾸면 `this`가 그 줄까지 살아 있으니 해결된다"고 생각하기 쉽다. 부분적으로만 맞다. **`ReadByte()`가 실행되는 도중에 GC가 일어나면 그 시점에는 이미 `this`가 쓰이지 않는다.** 즉시 루트 수집은 `this` 포인터에도 똑같이 적용된다.
>
> 이 예제가 던지는 진짜 교훈은 다른 데 있다. **파이널라이저에서 관리 객체의 메서드를 부르지 마라**(34.3절). 이 클래스의 근본 문제는 `~ProblematicObject()`가 `stream.Close()`를 부른다는 것이다.

### `GC.KeepAlive` — 아무 일도 하지 않는 메서드

`GC.KeepAlive(object)`는 인수를 받아 아무것도 하지 않는다. 그럼에도 효과가 있다. **JIT이 그 인수를 "이 지점에서 사용됨"으로 취급하기 때문**이다. GC Info가 바뀌고, 그 지점까지 루트가 유지된다.

```csharp
public int UseMe()
{
    var hnd = this.handle;

    byte[] buffer = new byte[1];
    bool ok = Native.ReadFile(hnd, buffer, 1, out uint read, IntPtr.Zero);

    GC.KeepAlive(this);     // 여기까지 this가 살아 있어야 한다

    return ok ? buffer[0] : -1;
}
```

**위치가 전부다.** `GC.KeepAlive`는 "여기까지 살려 둬라"는 표시이므로 **보호하려는 마지막 사용 지점 뒤에** 놓아야 한다. 앞에 놓으면 아무 효과가 없다.

| 오해 | 사실 |
|---|---|
| 객체를 고정(pin)한다 | **아니다.** 수집을 막을 뿐 이동은 막지 않는다. 고정은 `fixed`나 `GCHandleType.Pinned`다 |
| 호출 지점부터 객체를 살린다 | **아니다.** 호출 지점**까지** 살린다 |
| 성능 비용이 있다 | 런타임 비용은 사실상 없다. JIT이 인식하는 특별한 메서드다 |
| 아무 데나 넣어도 무해하다 | 무해하지만 **무의미하다.** 위치가 틀리면 버그는 그대로다 |

> **📌 `GC.KeepAlive`는 인라인되지 않는다**
>
> 메서드 본문이 비어 있으므로 일반적인 규칙대로라면 인라인되어 사라져야 한다. JIT은 이 메서드를 특별 취급해서 인라인하지 않고, 대신 "인수가 이 지점에서 살아 있다"는 정보를 GC Info에 반영한다. 최적화 빌드에서도 효과가 유지된다.
>
> 같은 이유로 `GC.KeepAlive` 대신 `if (x != null) { }` 같은 것을 넣는 편법은 통하지 않는다 — JIT이 그것을 제거해 버린다. 34.1절에서 `t = null`이 사라진 것과 같은 이유다.

### 대안 1 — `HandleRef` (레거시)

`GC.KeepAlive`를 P/Invoke 호출마다 넣는 것은 번거롭고 잊기 쉽다. BCL 초기에 이 문제를 위해 도입된 것이 `HandleRef` 구조체다. **핸들과 그 핸들을 소유한 객체를 함께 담는** 아주 단순한 래퍼이고, 상호운용 마샬러가 이것을 특별 취급해서 **P/Invoke 호출 전체 구간 동안 소유자 객체를 살려 둔다.**

```csharp
public int UseMe()
{
    var hnd = this.handle;

    byte[] buffer = new byte[1];

    // HandleRef가 this를 P/Invoke 동안 살려 둔다
    if (Native.ReadFile(new HandleRef(this, hnd), buffer, 1, out uint read, IntPtr.Zero))
        return buffer[0];

    return -1;
}
```

P/Invoke 시그니처는 `IntPtr` 대신 `HandleRef`를 받도록 선언한다.

> **⚠️ `HandleRef`와 `HandleCollector`는 쓰지 마라**
>
> `HandleRef`는 조기 수집은 막지만 **핸들 재활용 공격(handle-recycling attack)** 을 막지 못한다. 한 스레드가 핸들을 쓰는 동안 다른 스레드가 그것을 닫아 버리고, OS가 같은 핸들 값을 다른 리소스에 재할당하면, 첫 스레드가 엉뚱한 리소스를 조작하게 된다.
>
> `HandleRef`는 사실상 폐기된 접근법이다. 실제 사용의 80% 이상이 Windows Forms와 `System.Drawing` 코드에서 온다. 같은 시기에 도입된 `HandleCollector`(핸들 개수가 임계값을 넘으면 GC를 유발한다)도 마찬가지로 레거시다.
>
> 기존 코드에서 이들을 보더라도 **새 코드에 따라 쓰지 마라.**

### 대안 2 — `SafeHandle` (정답)

`SafeHandle`은 이 문제를 세 방향에서 동시에 해결한다.

1. **조기 수집 방지** — `SafeHandle`을 P/Invoke 인수로 넘기면 CLR이 호출 전후로 내부 참조 카운터를 증감한다. 카운터가 0이 아닌 동안 핸들이 해제되지 않는다.
2. **핸들 재활용 공격 차단** — 같은 참조 카운팅이 다른 스레드의 조기 해제를 막는다.
3. **반환값 경쟁 조건 제거** — P/Invoke가 `IntPtr` 대신 `SafeHandle` 파생 타입을 반환하도록 선언하면, 핸들을 받아 래퍼를 만드는 과정 전체가 네이티브 코드에서 원자적으로 일어난다.

메커니즘의 상세는 33.7절에 있다. 여기서 필요한 것은 선택 기준이다.

| 상황 | 도구 |
|---|---|
| 새 상호운용 코드를 작성한다 | **`SafeHandle` 파생 타입** |
| 관리 객체의 수명에 부수 효과가 묶여 있다 (타이머 등) | 강한 참조를 유지 (필드에 보관) 또는 `Dispose` 호출 |
| 레거시 코드에 최소 변경으로 수정을 넣어야 한다 | `GC.KeepAlive` |
| P/Invoke에 넘긴 델리게이트를 살려야 한다 | 델리게이트를 필드에 보관 |
| 옛 코드에서 마주쳤다 | `HandleRef` — 이해만 하고 따라 쓰지 마라 |

> **💡 `GC.KeepAlive`가 필요하다는 것은 설계 신호다**
>
> `GC.KeepAlive`를 넣어야 하는 상황에 놓였다면, 대개 그것은 **원시 `IntPtr` 핸들을 직접 들고 있다**는 뜻이다. 근본 해결은 그 핸들을 `SafeHandle`로 감싸는 것이다. 감싸고 나면 `GC.KeepAlive`도, 그 클래스의 파이널라이저도 필요 없어진다.
>
> 예외는 타이머처럼 "존재 자체가 부수 효과인" 객체다. 이 경우는 `KeepAlive`보다 **객체를 필드에 보관하는 것**이 정직한 해법이다. 34.10절에서 다룬다.

## 34.9 `ConditionalWeakTable`과 의존 핸들

### 문제 — 남의 객체에 데이터를 붙이고 싶다

내가 만들지 않은 타입의 인스턴스에 추가 정보를 연결해야 할 때가 있다. 상속할 수 없고(봉인되었거나 남의 타입이거나), 필드를 추가할 수도 없다. XAML의 첨부 속성(attached property), 동적 언어의 동적 멤버, 직렬화기의 인스턴스별 상태 같은 것이 그런 요구다.

`Dictionary<object, TValue>`를 쓰면 어떻게 될까. **키가 사전의 강한 참조로 영원히 살아남는다.** 사전이 살아 있는 한 키 객체도 산다. 전형적인 누수다.

`Dictionary<WeakReference<object>, TValue>`는 어떤가. 키는 약해졌지만 새 문제가 생긴다. **값이 키를 참조하면 순환이 아니라 강한 사슬이 된다.** 값은 사전이 강하게 붙들고 있고, 값이 키를 참조하면 키도 산다. 결국 아무것도 죽지 않는다.

```text
Dictionary<WeakReference<K>, V>
   │
   ├── (약함) ──→ [키 객체 K] ←──────┐
   │                                  │ (강함)
   └── (강함) ──→ [값 객체 V] ────────┘

   결과: 사전이 V를 살리고, V가 K를 살린다. 약한 참조가 무의미해진다.
```

### 해법 — 의존 핸들

CLR은 이 관계를 표현하는 특별한 핸들을 갖고 있다. **의존 핸들(dependent handle)** 이다. 의미론은 한 문장이다.

> **키가 살아 있는 동안에만 값을 살린다. 그리고 키 자체는 약하게 붙든다.**

이 한 문장이 앞의 두 문제를 동시에 해결한다. 키를 붙들지 않으므로 키는 자유롭게 죽을 수 있고, 값이 키를 참조해도 그 참조가 키를 살리지 않는다. GC가 "키가 마크되었는가"를 먼저 판정한 뒤에야 값을 마크하기 때문이다.

이것을 공개 API로 감싼 것이 `System.Runtime.CompilerServices.ConditionalWeakTable<TKey, TValue>`다.

```csharp
public sealed class ConditionalWeakTable<TKey, TValue>
    where TKey : class where TValue : class
{
    public ConditionalWeakTable();

    public void   Add(TKey key, TValue value);
    public TValue GetValue(TKey key, CreateValueCallback createValueCallback);
    public bool   TryGetValue(TKey key, out TValue value);
    public TValue GetOrCreateValue(TKey key);
    public bool   Remove(TKey key);

    // 중첩 델리게이트 — 바깥 타입의 TKey/TValue를 그대로 쓴다
    public delegate TValue CreateValueCallback(TKey key);
}
```

| 조합 | 키가 죽으면 | 값이 키를 참조하면 | 용도 |
|---|---|---|---|
| 강한 키 · 강한 값 (`Dictionary`) | 안 죽는다 | 상관없다 | 일반 사전 |
| 약한 키 · 강한 값 | 키는 죽지만 값이 남는다 | 둘 다 산다 (누수) | 쓸 수 없다 |
| 약한 키 · 약한 값 | 둘 다 죽는다 | 상관없다 | 값의 수명을 보장할 수 없다 |
| **의존 핸들** (`ConditionalWeakTable`) | **둘 다 죽는다** | **둘 다 죽는다** | 인스턴스에 데이터 부착 |

> **📌 왜 순환 참조에도 안전한가**
>
> 마크 단계에서 GC는 의존 핸들의 값을 **키가 이미 마크되었을 때만** 마크한다. 값에서 키로 가는 참조는 GC 그래프에서 정상적인 간선이지만, 애초에 값이 마크되지 않았으므로 그 간선을 따라가지 않는다. **값이 키를 살리는 경로가 생기려면 먼저 값이 살아야 하는데, 값이 살려면 키가 먼저 살아야 한다.** 순환이 성립하지 않는다.
>
> 이 의존 관계 때문에 마크 단계가 한 번의 순회로 끝나지 않고 반복이 필요할 수 있다. 그 대가가 `ConditionalWeakTable`이 GC에 주는 부담이다.

### 사용 예 — 객체 수집 알림기

`ConditionalWeakTable`을 쓰면 임의의 객체가 수집될 때 알림을 받는 확장 메서드를 만들 수 있다.

```csharp
internal static class GCWatcher
{
    // 주의: 인터닝되는 문자열과 MarshalByRefObject 프록시는 조심해야 한다
    private readonly static ConditionalWeakTable<object, NotifyWhenGCd<string>> s_cwt =
        new ConditionalWeakTable<object, NotifyWhenGCd<string>>();

    private sealed class NotifyWhenGCd<T>
    {
        private readonly T m_value;

        internal NotifyWhenGCd(T value) { m_value = value; }

        public override string? ToString() => m_value!.ToString();

        ~NotifyWhenGCd() { Console.WriteLine("GC'd: " + m_value); }
    }

    public static T GCWatch<T>(this T @object, string tag) where T : class
    {
        s_cwt.Add(@object, new NotifyWhenGCd<string>(tag));
        return @object;
    }
}
```

동작 원리를 짚어 보자. `s_cwt`는 정적 필드이므로 테이블 자체는 영원히 산다. 그런데 항목의 키를 약하게 붙들므로 감시 대상 객체는 자유롭게 죽는다. 대상이 죽으면 값(`NotifyWhenGCd<string>`)을 살릴 이유가 사라지고, 값도 죽으면서 그 파이널라이저가 콘솔에 출력한다.

```csharp
internal static class ConditionalWeakTableDemo
{
    public static void Main()
    {
        object o = new object().GCWatch("My Object created at " + DateTime.Now);

        GC.Collect();       // 여기서는 알림이 나오지 않는다

        GC.KeepAlive(o);    // o가 가리키는 객체가 여기까지 살아 있게 한다

        o = null;           // 이제 죽어도 된다

        GC.Collect();       // 이 줄 이후 언젠가 알림이 나온다

        Console.ReadLine();
    }
}
```

이 짧은 코드에 이 장의 도구가 세 개나 들어 있다 — 의존 핸들, `GC.KeepAlive`, 파이널라이저. `GC.KeepAlive(o)`가 없으면 첫 `GC.Collect()`에서 이미 객체가 수집되어 알림이 먼저 나올 수 있다.

### 함정

> **⚠️ 키 비교는 참조 동등성이다**
>
> `ConditionalWeakTable`은 키를 **참조 동등성(reference equality)** 으로 비교한다. `Equals`나 `GetHashCode` 재정의를 쓰지 않는다. 수명을 기준으로 하는 자료구조이므로 당연한 선택이다 — 논리적으로 같은 두 객체의 수명은 서로 다르다.
>
> 그래서 **문자열을 키로 쓰면 안 된다.** 리터럴 문자열은 인터닝되어 같은 인스턴스를 공유하고(35.5절), 인터닝 풀이 그것을 영원히 살려 둔다. 값 타입도 키가 될 수 없다 — `TKey : class` 제약이 그것을 막는다.

> **⚠️ 같은 키를 두 번 `Add`하면 예외다**
>
> `Add`는 이미 존재하는 키를 다시 넣으면 `ArgumentException`을 던진다. 값을 바꾸려면 `Remove` 후 다시 `Add`해야 한다. 조회와 생성을 한 번에 하려면 `GetValue`나 `GetOrCreateValue`를 쓴다.

> **⚠️ 스레드 안전하지만 빠르지는 않다**
>
> 이 클래스는 스레드 안전해서 여러 스레드가 동시에 쓸 수 있다. 그 대가로 **성능이 뛰어나지 않다.** 핫 패스에 넣기 전에 반드시 측정하라.
>
> 그리고 의존 핸들은 GC의 마크 단계에 추가 작업을 만든다. 항목 수가 많아지면 GC 일시 정지 시간이 늘어난다. **인스턴스 수만 개 규모의 부착 데이터를 이 방식으로 관리하는 것은 재고하라.**

> **💡 `ConditionalWeakTable`은 캐시가 아니다**
>
> 이름에 "Table"이 있지만 사전의 대체재가 아니다. **키 객체의 수명에 값을 종속시키는** 단 하나의 목적을 위한 도구다.
>
> - 키를 조회 가능한 식별자로 쓰고 싶다 → 사전을 써라
> - 만료 정책이 필요하다 → `MemoryCache`를 써라
> - 특정 인스턴스에 부가 상태를 붙이고 그 인스턴스와 함께 사라지게 하고 싶다 → **`ConditionalWeakTable`**

## 34.10 타이머가 만드는 관리 메모리 누수

### 두 방향의 함정

타이머는 이 장의 모든 주제가 만나는 지점이다. 그리고 **정반대 방향의 두 가지 사고**를 동시에 일으킨다.

| 방향 | 무슨 일이 벌어지나 | 대표 타입 |
|---|---|---|
| **너무 오래 산다** | 런타임이 타이머를 붙들고, 타이머가 핸들러를 통해 내 객체를 붙든다 → 영원히 회수되지 않는다 | `System.Timers.Timer`, Windows Forms 타이머, WPF `DispatcherTimer` |
| **너무 일찍 죽는다** | 런타임이 타이머 객체를 붙들지 않는다 → 지역 변수가 죽으면 즉시 수집·파이널라이즈되어 타이머가 멈춘다 | `System.Threading.Timer` |

같은 "타이머"라는 이름을 달고 정반대의 수명 계약을 갖는다. 어느 쪽인지 모르면 반드시 사고가 난다.

### 방향 1 — 붙들어서 새는 쪽

```csharp
using System.Timers;

class Foo
{
    Timer _timer;

    public Foo()
    {
        _timer = new System.Timers.Timer { Interval = 1000 };
        _timer.Elapsed += tmr_Elapsed;
        _timer.Start();
    }

    void tmr_Elapsed(object? sender, ElapsedEventArgs e) { /* ... */ }
}
```

`Foo` 인스턴스는 **절대 수집되지 않는다.** 사슬은 이렇다.

```text
[런타임 내부]
     │ (활성 타이머를 붙든다 — Elapsed 이벤트를 발생시켜야 하므로)
     ▼
 [_timer]
     │ (Elapsed 이벤트의 델리게이트가 tmr_Elapsed의 대상을 담는다)
     ▼
  [Foo 인스턴스]
     │
     └─→ Foo가 참조하는 모든 것
```

`Foo`를 만드는 코드가 참조를 다 버려도 소용없다. 런타임이 사슬의 맨 위에 있기 때문이다. 그리고 이것은 **정확히 27.6절의 이벤트 누수와 같은 구조**다 — 소스(타이머)가 대상(`Foo`)보다 오래 살면 대상이 새고, 여기서는 소스가 런타임과 같은 수명이다.

해법은 `Timer`가 `IDisposable`이라는 사실에서 나온다. 타이머를 폐기하면 정지하고, 런타임이 더 이상 그것을 참조하지 않는다.

```csharp
class Foo : IDisposable
{
    Timer _timer;
    // ...
    public void Dispose() => _timer.Dispose();
}
```

> **💡 필드가 `IDisposable`이면 내 클래스도 `IDisposable`이어야 한다**
>
> 33.2절의 "소유의 사슬" 규칙이 여기서 그대로 적용된다. `Foo`가 `Timer`를 소유하므로 `Foo`도 `IDisposable`이어야 하고, `Foo`를 만든 쪽이 `Foo`를 폐기해야 한다. 사슬 어느 한 고리가 끊어지면 타이머는 영원히 산다.
>
> Windows Forms의 `System.Windows.Forms.Timer`와 WPF의 `DispatcherTimer`도 수명 면에서 같은 부류로 다뤄야 한다.

### 방향 2 — 놓쳐서 죽는 쪽

`System.Threading.Timer`는 정반대다. **런타임이 활성 스레딩 타이머 객체를 참조하지 않는다.** 콜백 델리게이트를 직접 참조할 뿐이다.

```csharp
static void Main()
{
    var tmr = new System.Threading.Timer(TimerTick, null, 1000, 1000);

    GC.Collect();
    System.Threading.Thread.Sleep(10000);   // 10초 대기
}

static void TimerTick(object? notUsed) => Console.WriteLine("tick");
```

릴리스 빌드(디버깅 비활성, 최적화 활성)로 컴파일해 실행하면 **"tick"이 한 번도 출력되지 않는다.** `tmr` 변수는 생성 직후로 쓰이지 않으므로 `GC.Collect()` 시점에 이미 루트가 아니다. 타이머 객체가 수집되고, 파이널라이제이션이 스레드 풀에 타이머 취소를 알린다. 첫 발화 전에 끝난 것이다.

해법은 34.1절에서 본 것과 같다.

```csharp
using (var tmr = new System.Threading.Timer(TimerTick, null, 1000, 1000))
{
    GC.Collect();
    System.Threading.Thread.Sleep(10000);
}
```

`using` 블록 끝의 암묵적인 `tmr.Dispose()` 호출이 `tmr`을 "블록 끝까지 사용됨"으로 만든다. **폐기하겠다고 선언했더니 그때까지 살아남는 아이러니**가 여기서도 반복된다.

> **⚠️ 이 버그는 디버그 빌드에서 재현되지 않는다**
>
> 디버그 빌드에서는 JIT이 모든 지역 변수를 메서드 끝까지 살려 두므로 타이머가 정상 동작한다. 계층 0 코드도 마찬가지다. **"내 컴퓨터에서는 되는데"의 교과서적 사례**다.
>
> 재현하려면 릴리스 빌드 + 계층화 컴파일 비활성이 필요하다.

### 왜 두 타이머의 설계가 다른가

`System.Timers.Timer`는 이벤트 기반이다. `Elapsed` 이벤트를 발생시키려면 런타임 쪽에서 타이머 객체 자체를 붙들고 있어야 한다. `System.Threading.Timer`는 생성자에서 `TimerCallback` 델리게이트를 받는다. 스레드 풀은 그 델리게이트만 있으면 되고, 타이머 객체는 필요 없다.

그렇다면 스레딩 타이머가 수집될 때 왜 타이머가 정지되는가. **파이널라이제이션 때문**이다. 그리고 34.4절에서 봤듯이, `System.Threading.Timer`는 이 파이널라이제이션을 **중첩 private 홀더 객체**에 위임한다. 단순화하면 이런 구조다.

```csharp
public sealed class Timer : IDisposable
{
    private TimerHolder timerHolder;

    public Timer() => timerHolder = new TimerHolder(this);

    private sealed class TimerHolder
    {
        internal Timer m_timer;

        public TimerHolder(Timer timer) => m_timer = timer;

        ~TimerHolder() => m_timer?.Close();      // 여기서 타이머가 취소된다

        public void Close()
        {
            m_timer.Close();
            GC.SuppressFinalize(this);
        }
    }

    public void Dispose() => timerHolder.Close();
}
```

`Timer` 자신은 파이널라이즈 가능하지 않다. 그래서 외부 코드가 `GC.SuppressFinalize(timer)`를 불러 **타이머를 영영 멈추지 않게 만드는 일이 불가능하다.** 34.4절에서 본 홀더 패턴의 실제 사례다.

### 타이머 수명 요약표

| 타이머 | 런타임이 붙드나 | 방치하면 | 반드시 해야 할 것 |
|---|---|---|---|
| `System.Timers.Timer` | **붙든다** | 구독자가 영원히 산다 (누수) | `Dispose` |
| Windows Forms 타이머 | 붙든다 | 위와 같다 | `Dispose` |
| WPF `DispatcherTimer` | 디스패처가 붙든다 | 위와 같다 | `Stop` 후 핸들러 해지 |
| `System.Threading.Timer` | **붙들지 않는다** | 릴리스 빌드에서 조기 수집 | 강한 참조 유지 + `Dispose` |
| `PeriodicTimer` | 붙들지 않는다 | 대기 중인 태스크가 붙든다 | `Dispose` (49.10절) |

`PeriodicTimer`는 이벤트나 콜백이 아니라 `await`로 소비하는 타이머다(※.NET 6). `WaitForNextTickAsync`를 대기하는 상태 기계가 타이머를 참조하므로 대기 중에는 수집되지 않는다. 세 종류 타이머의 API 차이와 선택 기준은 49.10절에서 다룬다.

> **⚠️ 콜백이 자기 객체를 캡처하면 두 함정이 겹친다**
>
> ```csharp
> class Worker
> {
>     private readonly Timer _timer;
>
>     public Worker()
>     {
>         // 람다가 this를 캡처한다
>         _timer = new System.Threading.Timer(_ => DoWork(), null, 0, 1000);
>     }
>
>     private void DoWork() { /* ... */ }
> }
> ```
>
> 이 코드는 조기 수집 문제는 없다 — `_timer` 필드가 타이머를 붙들고, 스레드 풀이 콜백 델리게이트를 붙들고, 그 델리게이트가 `this`를 붙든다. 대신 **반대 함정에 빠진다.** `Worker`를 아무도 참조하지 않아도 스레드 풀 → 델리게이트 → `Worker` 사슬 때문에 영원히 산다.
>
> **`Worker`는 `IDisposable`이어야 하고 `_timer.Dispose()`를 불러야 한다.** 스레딩 타이머라고 해서 누수가 없는 것이 아니다 — 캡처가 있으면 똑같이 샌다.

### 진단

타이머 누수의 증상은 "관리 힙이 서서히 자라고, 힙 덤프를 뜨면 같은 타입의 인스턴스가 계속 쌓여 있다"이다. WinDbg의 `!gcroot`로 그 인스턴스의 루트 경로를 추적하면 타이머 관련 내부 타입이 나온다. 도구와 워크플로는 66장이며, 타이머 누수는 66.11절의 대표 시나리오 여섯 개 중 하나로 다시 나온다.

> **💡 예방이 진단보다 싸다**
>
> 규칙 세 개면 이 절의 사고 대부분을 막는다.
>
> 1. **타이머는 항상 필드에 보관한다.** 지역 변수에 두지 않는다.
> 2. **타이머를 가진 클래스는 항상 `IDisposable`이다.** 그리고 `Dispose`에서 타이머를 폐기한다.
> 3. **타이머 콜백은 짧게 유지한다.** 콜백이 무거우면 캡처가 커지고, 캡처가 크면 누수의 크기도 커진다.

## 이 장의 요약

- **살아 있다 = 어떤 루트에서 참조를 따라 도달할 수 있다.** 쓸모와는 무관하다. 루트는 스택 루트, 정적 필드, GC 핸들, 파이널라이제이션 큐 네 종류이고, 정적 필드는 사실상 프로세스 수명 동안 대상을 살린다. 루트별 스캔 메커니즘은 64.3절에 있다.

- **지역 변수의 생존 범위는 어휘 범위가 아니라 마지막 사용 지점까지다.** JIT의 즉시 루트 수집이 그렇게 만든다. 디버그 빌드는 이 최적화를 끄므로 "디버그에서는 되는데 릴리스에서 안 되는" 버그가 생긴다. `t = null`은 JIT이 지워 버리므로 해법이 아니고, `t.Dispose()`처럼 실제로 값을 쓰는 코드만 수명을 연장한다.

- **파이널라이즈 가능한 객체는 세 개의 큐를 지난다.** 할당 시 파이널라이제이션 큐 등록 → 마크 단계 끝에서 fReachable 큐로 이동(여기가 루트이므로 부활한다) → 전용 파이널라이저 스레드가 실행 → 다음 GC에서 회수. **최소 두 번의 GC**가 필요하고, 그 사이 객체와 그 하위 그래프가 세대 승격된다.

- **파이널라이저의 함정 목록이 길다.** 순서 미정의, 다른 스레드에서 실행, 예외 시 프로세스 종료, 블로킹 시 큐 전체 정지, 프로세스 종료 시 실행 보장 없음(모던 .NET), 생성자 실패 후에도 호출됨. 할당만 놓고 약 40배 느리다. 이 목록은 "잘 쓰는 법"이 아니라 "쓰지 않을 이유"다.

- **`disposing == false`는 최후의 수단 모드다.** 파이널라이즈 가능한 객체를 건드리면 안 되고, 잠금을 잡거나 블로킹해서도 안 된다. 할 수 있는 것은 직접 소유한 OS 리소스 해제와 정적 컬렉션에 실패를 기록하는 정도다. `StreamWriter`가 파이널라이저를 아예 갖지 않는 것이 이 제약이 만든 설계 결정이다.

- **부활은 파이널라이저에서 `this`를 도달 가능한 곳에 저장하는 것이다.** 두 번째 사망 시에는 파이널라이저가 실행되지 않으므로 `GC.ReRegisterForFinalize`가 필요하고, 그 조합은 불멸의 객체를 만든다. 부활 기반 객체 풀은 세대 2 승격 때문에 실패한다 — 풀은 명시적으로 관리하라.

- **임계 파이널라이저는 fReachable 큐가 Critical/Normal 두 그룹으로 나뉘어 있어서 순서를 보장한다.** 모든 일반 파이널라이저가 임계 파이널라이저보다 먼저 실행된다(약한 순서). CER과 `PrepareConstrainedRegions`는 모던 .NET에서 아무 일도 하지 않는 .NET Framework 유물이다.

- **짧은 약한 참조는 GC가 죽었다고 판정한 순간 끊기고, 긴 약한 참조는 파이널라이저 실행 후에 끊긴다.** 실무에서는 짧은 쪽만 쓴다. `WeakReference`의 `IsAlive` 후 `Target` 읽기에는 경쟁 조건이 있으므로 `WeakReference<T>.TryGetTarget`을 써라. 약한 참조 하나마다 힙 객체 + 핸들 항목 + 파이널라이저가 생긴다.

- **순진한 약한 참조 캐시는 실패한다.** GC는 메모리가 부족할 때만 도는 것이 아니라 세대 0 예산이 찰 때마다 돌기 때문이다. 쓸 만한 캐시는 강한 참조로 시작해 시간이 지나면 약하게 강등하는 2단계 구조여야 한다.

- **`Lazy<T>`는 팩터리 델리게이트와 그 클로저가 캡처한 것들을 값이 만들어질 때까지 붙든다.** `LazyThreadSafetyMode`는 `None`·`PublicationOnly`·`ExecutionAndPublication` 셋이고, `PublicationOnly`는 경쟁에서 진 인스턴스를 폐기하지 않으므로 `IDisposable` 값에 쓰면 안 된다. 래퍼 할당까지 없애려면 `LazyInitializer.EnsureInitialized`를 쓴다.

- **`GC.KeepAlive`는 마지막 사용 지점 뒤에 놓아야 하고, 고정이 아니라 수집 방지만 한다.** 이것이 필요한 상황은 대개 원시 `IntPtr` 핸들을 직접 들고 있다는 신호이며, 근본 해법은 `SafeHandle`이다. `HandleRef`와 `HandleCollector`는 핸들 재활용 공격을 막지 못하는 레거시다.

- **`ConditionalWeakTable`의 의존 핸들은 "키가 살아 있는 동안만 값을 살리되 키는 약하게 붙든다"를 표현한다.** 값이 키를 참조해도 순환이 생기지 않는다. 키 비교는 참조 동등성이므로 문자열을 키로 쓰면 안 되고, 스레드 안전하지만 빠르지 않다.

- **타이머는 정반대의 두 사고를 낸다.** `System.Timers.Timer` 계열은 런타임이 붙들어서 구독자를 영원히 살리고, `System.Threading.Timer`는 붙들지 않아서 릴리스 빌드에서 조기 수집된다. 어느 쪽이든 해답은 같다 — **필드에 보관하고, 소유 클래스를 `IDisposable`로 만들고, 폐기하라.**

## 연습 문제

1. 34.1절의 `Timer` 예제를 그대로 작성하고, (a) 디버그 빌드, (b) 릴리스 빌드, (c) 릴리스 빌드 + `DOTNET_TieredCompilation=0` 세 가지로 실행해 `TimerCallback`이 몇 번 호출되는지 기록하라. 세 결과가 왜 다른지 GC Info와 즉시 루트 수집으로 설명하라. 그다음 `t = null;`을 추가해도 결과가 바뀌지 않음을, `t.Dispose();`를 추가하면 바뀜을 확인하라.

2. 필드 네 개짜리 클래스를 파이널라이저가 있는 버전과 없는 버전으로 만들고, BenchmarkDotNet의 `[MemoryDiagnoser]`를 켜서 N = 1, 10, 100, 1000 각각에 대해 할당 시간과 Gen 0/Gen 1 컬렉션 횟수를 측정하라. 34.2절의 표와 비교하고, Gen 1 열에 값이 나타나는 이유를 설명하라.

3. 파이널라이저에서 `Thread.Sleep(200)`을 부르는 클래스를 만들고, 그 객체를 초당 100개씩 할당하는 루프를 돌려라. `dotnet-counters`로 관리 힙 크기와 Gen 2 크기를 관찰하고, WinDbg의 `!finalizequeue`(또는 `dotnet-dump` + SOS)로 fReachable 큐가 자라는 것을 확인하라(도구 사용법은 66.9절).

4. 34.4절의 `TempFileRef` 재시도 예제를 구현하고, 삭제가 실패하도록 파일을 다른 프로세스에서 열어 둔 채 실행하라. 재시도가 몇 번 일어나는지, 각 재시도 사이에 몇 번의 `GC.Collect()`가 필요한지 확인하라. 그다음 `GC.ReRegisterForFinalize(this)`를 한 파이널라이저에서 두 번 부르도록 바꾸고 파이널라이저가 몇 번 실행되는지 세어 보라.

5. 파이널라이저에서 자신을 재등록하는 `LargeClass`를 만들고, 짧은 약한 핸들(`GCHandleType.Weak`)과 긴 약한 핸들(`GCHandleType.WeakTrackResurrection`)로 각각 관찰하라. `GC.Collect()` → `GC.WaitForPendingFinalizers()` → `GC.Collect()` 이후 두 핸들의 `Target`이 왜 다른지 34.5절의 5단계 순서 그림으로 설명하라.

6. 크기 10MB짜리 배열을 담은 객체를 순수 약한 참조 캐시에 넣고, 1초 간격으로 100번 조회하면서 히트율을 측정하라. 그다음 34.6절의 약한 강등 캐시로 바꿔 같은 측정을 하고 히트율을 비교하라. 강등 임계 시간을 바꿔 가며 히트율과 메모리 사용량의 트레이드오프를 표로 정리하라.

7. `IDisposable`을 구현한 클래스를 `Lazy<T>`의 `PublicationOnly` 모드로 감싸고, 여러 스레드가 동시에 `Value`를 읽게 하라. 생성자와 `Dispose`에 카운터를 넣어 **몇 개가 만들어지고 몇 개가 폐기되는지** 세어라. 그다음 `ExecutionAndPublication`으로 바꿔 같은 측정을 하고 차이를 설명하라.

8. `System.Threading.Timer`를 지역 변수에 담고 콜백에서 카운터를 증가시키는 프로그램을 릴리스 빌드로 작성해, 콜백이 한 번도 실행되지 않는 것을 확인하라. 그다음 (a) `using` 블록, (b) 정적 필드 보관, (c) 콜백 끝의 `GC.KeepAlive` 세 가지 수정을 각각 적용해 어느 것이 동작하고 어느 것이 동작하지 않는지, 그 이유가 무엇인지 정리하라.

9. `ConditionalWeakTable<object, T>`로 34.9절의 `GCWatch` 확장 메서드를 구현하라. 감시 대상으로 (a) `new object()`, (b) 리터럴 문자열, (c) `new string(...)`로 만든 문자열 세 가지를 넣고, 어느 것이 수집 알림을 내고 어느 것이 내지 않는지 확인하라. 리터럴 문자열의 결과를 문자열 인터닝(35.5절)으로 설명하라.
