## 24.1 열거(enumeration)의 기초 — `IEnumerable` / `IEnumerator`

### 자료구조는 다 다른데 순회는 하나여야 한다

컴퓨터과학에는 컬렉션이 많다. 배열, 연결 리스트, 레드/블랙 트리, 해시테이블, 힙, 트라이. 내부 구현도 다르고 외부 특성도 다르다. 그런데 이들 전부에 공통으로 필요한 연산이 하나 있다. **내용을 처음부터 끝까지 훑는 것**이다.

.NET은 이 요구를 인터페이스 한 쌍으로 표준화했다. `IEnumerable`과 `IEnumerator`, 그리고 그 제네릭 대응물이다. 이 한 쌍 덕분에 `foreach`는 배열이든 트리든 데이터베이스 커서든 똑같이 동작하고, LINQ 연산자 전체가 단 하나의 타입(`IEnumerable<T>`) 위에서 작성될 수 있었다.

### `IEnumerator` — 커서 프로토콜

`IEnumerator`는 컬렉션의 요소를 **전방 전용(forward-only)** 으로 훑는 저수준 프로토콜이다.

```csharp
public interface IEnumerator
{
    bool MoveNext();
    object Current { get; }
    void Reset();
}
```

- `MoveNext`는 현재 요소를 가리키는 "커서"를 다음 위치로 옮기고, 더 이상 요소가 없으면 `false`를 반환한다.
- `Current`는 현재 위치의 요소를 반환한다(보통 `object`에서 더 구체적인 타입으로 캐스트해서 쓴다).
- **첫 요소를 꺼내기 전에 `MoveNext`를 먼저 불러야 한다.** 빈 컬렉션을 표현할 수 있어야 하기 때문이다.
- `Reset`은 구현되어 있다면 처음으로 되돌아간다.

커서가 `-1`(첫 요소 **이전**)에서 시작해 `MoveNext`마다 한 칸씩 전진하고, 마지막 요소를 지나면 `false`를 반환한다는 것이 이 프로토콜의 전부다. 그래서 열거자를 손으로 만들 때 인덱스 필드를 `-1`로 초기화하고 `MoveNext`에서 먼저 증가시킨다. 시작 전과 종료 후의 `Current` 값은 정의되지 않는다.

> **📌 `Reset`은 사실상 죽은 멤버다**
>
> `Reset`은 COM(Component Object Model) 상호운용을 위해 존재한다. 직접 호출하는 것은 일반적으로 피한다. 보편적으로 지원되지 않기 때문이고(구현체가 `NotSupportedException`을 던져도 규약 위반이 아니다), 어차피 새 열거자를 하나 만드는 편이 쉽기 때문이다. 반복자(`yield return`)가 생성하는 열거자도 `Reset`을 호출하면 `NotSupportedException`을 던진다(28.4절).

### `IEnumerable` — 열거자 제공자

컬렉션은 보통 자신이 열거자가 되지 않는다. 대신 열거자를 **제공한다**. 그 계약이 `IEnumerable`이다.

```csharp
public interface IEnumerable
{
    IEnumerator GetEnumerator();
}
```

메서드 하나뿐인 이 인터페이스가 두 가지를 얻어 낸다.

1. **반복 로직을 다른 클래스로 떼어 낼 수 있다.** 컬렉션 클래스는 데이터 저장에만 집중하고, 순회 상태(현재 인덱스, 노드 포인터)는 별도 객체가 갖는다.
2. **여러 소비자가 동시에 같은 컬렉션을 열거해도 서로 간섭하지 않는다.** 각자 자기 열거자를 받기 때문이다.

`IEnumerable`을 "`IEnumeratorProvider`"라고 읽으면 정확하다. 이것이 컬렉션 클래스가 구현하는 가장 기본적인 인터페이스다.

저수준으로 직접 써 보면 이렇다.

```csharp
string s = "Hello";

// string이 IEnumerable을 구현하므로 GetEnumerator()를 호출할 수 있다
IEnumerator rator = s.GetEnumerator();
while (rator.MoveNext())
{
    char c = (char) rator.Current;
    Console.Write (c + ".");
}

// 출력: H.e.l.l.o.
```

물론 실제로는 이렇게 쓰지 않는다. C#이 문법 단축을 제공하기 때문이다.

```csharp
string s = "Hello";
foreach (char c in s)
    Console.Write (c + ".");
```

### `foreach`와의 관계

`foreach`가 위 코드로 낮춰지는 과정 — 정확히 어떤 순서로 후보를 검사하고, 배열·문자열에는 어떤 특수 경로가 있고, `Dispose` 호출은 어떤 조건에서 삽입되는지 — 는 **11.5절**에서 이미 IL 수준까지 다뤘다. 여기서는 컬렉션 쪽에서 알아야 할 결론만 다시 확인한다.

- `foreach`는 **인터페이스가 아니라 모양(shape)** 을 본다. `GetEnumerator()`라는 이름의 적절한 메서드가 있으면 `IEnumerable<T>` 구현 여부를 보지 않는다.
- 열거자가 `IDisposable`을 구현하면 `foreach`는 `using`으로 감싼다. 즉 다음 코드가
  ```csharp
  foreach (var element in somethingEnumerable) { /* ... */ }
  ```
  논리적으로 이렇게 된다.
  ```csharp
  using (var rator = somethingEnumerable.GetEnumerator())
      while (rator.MoveNext())
      {
          var element = rator.Current;
          // ...
      }
  ```

`IEnumerator<T>`가 `IDisposable`을 상속하는 이유가 여기 있다. 열거자가 데이터베이스 연결이나 파일 핸들 같은 자원을 붙들고 있을 수 있고, 열거가 끝나거나 **중간에 포기되더라도** 그 자원이 해제되어야 하기 때문이다.

### 제네릭 버전

`IEnumerator`와 `IEnumerable`은 거의 항상 확장된 제네릭 버전과 함께 구현된다.

```csharp
public interface IEnumerator<T> : IEnumerator, IDisposable
{
    T Current { get; }
}

public interface IEnumerable<T> : IEnumerable
{
    IEnumerator<T> GetEnumerator();
}
```

타입이 붙은 `Current`와 `GetEnumerator`를 정의함으로써 세 가지를 얻는다.

| 얻는 것 | 이유 |
|---|---|
| 정적 타입 안전성 | `IEnumerable<int>`를 요구하는 메서드에 `char[]`를 넘기면 **컴파일 오류**가 난다 |
| 박싱 제거 | `IEnumerator<int>.Current`는 `int`를 그대로 돌려준다. `object`로 박싱하지 않는다(15장) |
| 소비자 편의 | 캐스트가 사라진다 |

배열은 요소 타입 `T`에 대해 `IEnumerable<T>`를 자동으로 구현한다(9.7절).

컬렉션 클래스의 표준 관행은 **`IEnumerable<T>`를 공개하고 비제네릭 `IEnumerable`은 명시적 인터페이스 구현으로 숨기는 것**이다(18.3절). 그래야 `GetEnumerator()`를 직접 호출했을 때 타입 안전한 `IEnumerator<T>`를 받는다.

```csharp
public class MyGenCollection : IEnumerable<int>
{
    int[] data = { 1, 2, 3 };

    public IEnumerator<int> GetEnumerator()
    {
        foreach (int i in data)
            yield return i;
    }

    // 명시적 구현으로 숨긴다
    IEnumerator IEnumerable.GetEnumerator() => GetEnumerator();
}
```

`IEnumerable<T>`가 `IEnumerable`을 상속하므로 둘 다 구현해야 한다. 비제네릭 쪽은 제네릭 쪽을 그냥 호출하면 된다. `IEnumerator<T>`가 `IEnumerator`를 상속하므로 반환값이 그대로 맞는다.

> **⚠️ 배열은 이 관행을 깬다**
>
> 하위 호환 때문에 배열은 비제네릭 `IEnumerator`를 돌려준다. 제네릭 열거자를 얻으려면 명시적 인터페이스를 노출시켜야 한다.
>
> ```csharp
> int[] data = { 1, 2, 3 };
> var rator = ((IEnumerable<int>)data).GetEnumerator();   // IEnumerator<int>
> ```
>
> 제네릭이 C# 2.0에서야 등장했기 때문에 생긴 흉터다. `foreach`를 쓰면 마주칠 일이 없지만, 리플렉션이나 제네릭 헬퍼를 쓸 때 튀어나온다.

### 구조체 열거자 — 할당을 0으로 만드는 장치

`List<T>.GetEnumerator()`의 반환 타입은 `IEnumerator<T>`가 아니라 **`List<T>.Enumerator`라는 중첩 구조체**다. `Queue<T>`, `Stack<T>`, `Dictionary<TKey,TValue>`, `HashSet<T>` 모두 마찬가지다. 이유는 하나다. 값 타입이면 **힙 할당이 없기** 때문이다. `foreach`가 덕 타이핑으로 동작하므로(11.5절), 정적 타입이 `List<T>`이면 컴파일러는 구조체 열거자를 그대로 스택에 두고 `call`로 `MoveNext`를 호출한다. 힙 할당 0회, 가상 디스패치 0회다.

그런데 같은 리스트를 `IEnumerable<T>`로 받으면 이야기가 달라진다.

```csharp
List<int> list = new() { 1, 2, 3 };

foreach (int i in list) { }                       // 할당 없음 (구조체 열거자)

IEnumerable<int> seq = list;
foreach (int i in seq) { }                        // 열거자가 박싱되어 힙에 할당된다
```

`IEnumerable<T>.GetEnumerator()`를 통하면 구조체 열거자가 인터페이스로 **박싱**된다(18.6절). 루프 한 번에 객체 하나. 뜨거운 경로에서 초당 수백만 번 돌면 0세대 GC가 눈에 띄게 늘어난다. 이 선택의 실무적 함의는 24.16절에서 정리한다.

> **⚠️ 구조체 열거자를 변수에 담아 직접 조작하지 마라**
>
> ```csharp
> var e = list.GetEnumerator();   // List<int>.Enumerator — 구조체
> var copy = e;                   // 값 복사! 상태가 통째로 복제된다
> e.MoveNext();
> // copy는 여전히 시작 전 상태다
> ```
>
> 구조체이므로 대입·인수 전달·필드 저장이 전부 **복사**다. 열거 상태가 갈라져 조용히 틀린 결과를 낸다. `readonly` 필드에 담으면 매 호출마다 방어적 복사가 일어나 `MoveNext`가 아예 진행되지 않는 경우도 있다(16장).
>
> 구조체 열거자는 `foreach`가 알아서 쓰게 두는 것이 원칙이다. 손으로 돌려야 한다면 `ref` 지역 변수로 받거나, 애초에 인터페이스로 받아서 참조 의미론을 확보하라.

### 열거 인터페이스를 직접 구현하는 세 가지 방법

`IEnumerable`/`IEnumerable<T>`를 구현하고 싶은 이유는 보통 넷 중 하나다. `foreach` 지원, 표준 컬렉션을 기대하는 코드와의 상호운용, 더 상위 컬렉션 인터페이스의 요구사항 충족, 컬렉션 초기화자 지원.

방법은 셋이다.

| 방법 | 언제 | 비고 |
|---|---|---|
| 내부 컬렉션의 열거자를 그대로 반환 | 감싼 컬렉션의 요소가 그대로 필요할 때 | 가장 단순. `=> inner.GetEnumerator();` |
| `yield return` 반복자 | 대부분의 경우 | 컴파일러가 숨은 열거자 클래스를 생성한다(28장) |
| `IEnumerator`를 직접 구현 | 극도의 제어가 필요할 때 | 컴파일러가 하는 일을 손으로 하는 것 |

세 번째 방법을 실제로 써 보면 컴파일러가 대신해 주는 일의 양을 알 수 있다(경계 검사는 간결함을 위해 생략했다).

```csharp
public class MyIntList : IEnumerable<int>
{
    int[] data = { 1, 2, 3 };

    // 제네릭 열거자는 IEnumerable과 IEnumerable<T> 양쪽에 호환된다.
    // 이름 충돌을 피하려고 비제네릭 쪽은 명시적으로 구현한다.
    public IEnumerator<int> GetEnumerator() => new Enumerator (this);
    IEnumerator IEnumerable.GetEnumerator() => new Enumerator (this);

    class Enumerator : IEnumerator<int>
    {
        int currentIndex = -1;
        MyIntList collection;

        public Enumerator (MyIntList items) => collection = items;

        public int Current => collection.data [currentIndex];
        object IEnumerator.Current => Current;

        public bool MoveNext() => ++currentIndex < collection.data.Length;
        public void Reset()    => currentIndex = -1;

        // Dispose가 필요 없으면 명시적으로 구현해 공개 표면에서 숨기는 것이 관행이다
        void IDisposable.Dispose() {}
    }
}
```

`currentIndex`가 `-1`에서 시작하고 `MoveNext`가 **먼저 증가시킨 뒤 비교**한다는 점을 다시 확인하라. 첫 `MoveNext` 호출은 두 번째가 아니라 **첫 번째** 요소로 가야 한다. 비제네릭 버전만 구현하면 `Current`가 `object`라서 `int`를 꺼낼 때마다 박싱된다. 제네릭 버전이 빠른 이유가 이것이다. `Reset` 구현은 선택이며, `NotSupportedException`을 던져도 된다.

> **⚠️ 범위를 벗어난 `Current`의 동작은 구현마다 다르다**
>
> 엄밀한 구현이라면 `Current`가 열거 시작 전과 종료 후에 `InvalidOperationException`을 던진다. 하지만 BCL의 구조체 열거자들은 성능 때문에 이 검사를 최소화하거나 다르게 처리한다. 예컨대 `List<T>.Enumerator.Current`는 범위를 벗어난 상태에서 예외 대신 `default(T)`를 반환할 수 있다.
>
> **열거자를 손으로 돌리면서 `MoveNext`의 반환값을 무시하면 예외 없이 틀린 값을 읽게 된다는 뜻이다.**

### 비제네릭 인터페이스는 언제 쓰는가

`IEnumerable<T>`가 있는데 비제네릭 `IEnumerable`이 필요한 순간이 있는가?

**구현자 입장**에서는 선택의 여지가 없다. `IEnumerable<T>`가 `IEnumerable`을 상속하므로 둘 다 구현해야 한다. **소비자 입장**에서는 거의 항상 제네릭으로 충분하다. 예외는 **모든 요소 타입에 걸친 타입 통일**이 필요할 때다. 다음은 임의의 중첩 컬렉션의 요소 개수를 재귀적으로 세는 메서드다.

```csharp
public static int Count (IEnumerable e)
{
    int count = 0;
    foreach (object element in e)
    {
        var subCollection = element as IEnumerable;
        if (subCollection != null)
            count += Count (subCollection);
        else
            count++;
    }
    return count;
}
```

C#이 제네릭 인터페이스에 공변성을 제공하므로(23.10절) `IEnumerable<object>`로 받아도 될 것 같지만 그렇지 않다. **값 타입 요소에서 실패**하고(`IEnumerable<int>`는 `IEnumerable<object>`가 아니다), `IEnumerable<T>`를 구현하지 않는 레거시 컬렉션에서도 실패한다.

> **⚠️ 위 `Count`에는 버그가 있다**
>
> 순환 참조가 있으면 무한 재귀에 빠져 `StackOverflowException`으로 프로세스가 죽는다. `StackOverflowException`은 잡을 수 없다(78장). 이미 방문한 컬렉션을 `HashSet<object>`에 넣어 두고 걸러 내는 것이 가장 쉬운 해법이다. 이때 참조 동등성으로 비교해야 하므로 `ReferenceEqualityComparer.Instance`를 넘긴다(24.13절).

## 24.2 `ICollection`과 `IList` 인터페이스 계층

### 열거만으로는 부족하다

열거 인터페이스는 전방 전용 순회 프로토콜만 준다. 개수를 알아내거나, 인덱스로 접근하거나, 컬렉션을 수정하는 방법은 없다. 그래서 .NET은 `ICollection`, `IList`, `IDictionary`를 정의한다. 각각 제네릭·비제네릭 버전이 있고, 비제네릭 쪽은 대부분 레거시 지원용이다.

전체 계층은 이렇다.

```text
                    ┌──────────────┐
                    │ IEnumerable  │  비제네릭 루트  ── IList / IDictionary
                    └──────▲───────┘                   (레거시 계열)
          ┌────────────────┴────────────────┐
  ┌───────┴────────┐               ┌────────┴────────┐
  │  ICollection   │               │ IEnumerable<T>  │
  │ Count/CopyTo   │               │ GetEnumerator() │
  │ SyncRoot       │               └────────▲────────┘
  └────────────────┘         ┌──────────────┴──────────────┐
                    ┌────────┴───────┐          ┌──────────┴─────────────┐
                    │ ICollection<T> │          │ IReadOnlyCollection<T> │ out T
                    │ Count/Contains │          │ Count                  │ (공변)
                    │ Add/Remove     │          └──────────┬─────────────┘
                    │ Clear/CopyTo   │          ┌──────────┴─────────────┐
                    │ IsReadOnly     │          │  IReadOnlyList<T>      │ out T
                    └────────┬───────┘          │  this[int] { get; }    │ (공변)
       ┌─────────────────────┼──────────────┐   └────────────────────────┘
┌──────┴─────┐  ┌────────────┴──┐  ┌────────┴────────────┐  ┌──────────────────┐
│  IList<T>  │  │    ISet<T>    │  │  IDictionary<K,V>   │  │ IReadOnlyDiction │
│ this[int]  │  │ Add → bool    │  │ = ICollection<KVP>  │  │  ary<K,V>        │
│ IndexOf    │  │ UnionWith     │  │   + this[K]         │  │ this[K] { get; } │
│ Insert     │  │ ExceptWith    │  │   + Keys / Values   │  │ Keys / Values    │
│ RemoveAt   │  │ IsSubsetOf    │  │   + ContainsKey     │  │ ContainsKey      │
└────────────┘  │ Overlaps      │  │   + TryGetValue     │  │ TryGetValue      │
                └───────┬───────┘  └─────────────────────┘  └──────────────────┘
                ┌───────┴───────────┐
                │ IReadOnlySet<T>   │ ※.NET 5
                └───────────────────┘
```

세 단계로 요약하면 이렇다.

| 인터페이스 | 제공하는 것 |
|---|---|
| `IEnumerable<T>` (및 `IEnumerable`) | 최소 기능 — 열거만 |
| `ICollection<T>` (및 `ICollection`) | 중간 기능 — `Count`, 멤버십, 추가/제거 |
| `IList<T>` / `IDictionary<K,V>` (및 비제네릭 버전) | 최대 기능 — 인덱스/키에 의한 "임의" 접근 |

> **📌 "collection"과 "list"에 일관된 논리는 없다**
>
> `IList<T>`가 `ICollection<T>`의 더 강력한 버전이니까 `List<T>`도 `Collection<T>`보다 강력할 것 같지만, 그렇지 않다(24.9절). .NET 라이브러리 전체에서 "collection"과 "list"라는 단어는 사실상 동의어로 쓰인다. 특정 타입을 지칭할 때만 의미가 갈린다.

### `ICollection<T>`와 `ICollection`

```csharp
public interface ICollection<T> : IEnumerable<T>, IEnumerable
{
    int  Count { get; }
    bool Contains (T item);
    void CopyTo (T[] array, int arrayIndex);
    bool IsReadOnly { get; }

    void Add (T item);
    bool Remove (T item);
    void Clear();
}
```

비제네릭 버전은 상당히 다르다.

```csharp
public interface ICollection : IEnumerable
{
    int Count { get; }
    bool IsSynchronized { get; }
    object SyncRoot { get; }
    void CopyTo (Array array, int index);
}
```

수정 기능도, 멤버십 검사도 없다. 대신 동기화 보조 프로퍼티가 있다. `IsSynchronized`와 `SyncRoot`는 제네릭 버전에서 **의도적으로 빠졌다** — 스레드 안전성이 더 이상 컬렉션의 본질적 속성으로 간주되지 않기 때문이다. 스레드 안전이 필요하면 `System.Collections.Concurrent`를 쓴다(24.12절).

> **⚠️ `SyncRoot`로 락을 걸지 마라**
>
> 레거시 코드에서 `lock (collection.SyncRoot)` 패턴을 볼 수 있다. 이 패턴은 여러 이유로 위험하다. `SyncRoot`가 컬렉션 자신을 반환하는 구현이 흔해서 외부 코드와 락 객체를 공유하게 되고, 그 결과 예측 불가능한 교착이 생긴다. 더 근본적으로는 "한 연산은 원자적이지만 두 연산의 조합은 아니다"라는 문제를 전혀 해결하지 못한다. 락은 컬렉션이 아니라 **불변식(invariant)** 을 보호해야 한다(50장).

읽기 전용 `ICollection<T>`를 구현한다면 `Add`, `Remove`, `Clear`는 `NotSupportedException`을 던져야 한다. 이 인터페이스들은 보통 `IList` 또는 `IDictionary`와 함께 구현된다.

### `IList<T>`와 `IList`

```csharp
public interface IList<T> : ICollection<T>, IEnumerable<T>, IEnumerable
{
    T this [int index] { get; set; }
    int  IndexOf (T item);
    void Insert (int index, T item);
    void RemoveAt (int index);
}
```

`IndexOf`는 **선형 탐색**이다. 찾지 못하면 `-1`을 반환한다.

비제네릭 `IList`는 `ICollection`에서 물려받는 것이 적어서 멤버가 더 많다.

```csharp
public interface IList : ICollection, IEnumerable
{
    object this [int index] { get; set; }
    bool IsFixedSize { get; }
    bool IsReadOnly  { get; }
    int  Add      (object value);
    void Clear();
    bool Contains (object value);
    int  IndexOf  (object value);
    void Insert   (int index, object value);
    void Remove   (object value);
    void RemoveAt (int index);
}
```

`IList.Add`가 **새로 추가된 항목의 인덱스를 `int`로 반환**한다는 점에 주목하라. `ICollection<T>.Add`는 `void`다.

> **📌 왜 `IList<T>`는 `IList`를 상속하지 않는가**
>
> 겉으로 보이는 이유는 역사다. 제네릭이 나중에 왔고, 그 덕에 뒤늦은 깨달음을 반영해 더 나은 멤버 구성을 고를 수 있었다. `ICollection<T>`는 `ICollection`을 상속하지 않고, `IList<T>`는 `IList`를 상속하지 않으며, `IDictionary<TKey,TValue>`는 `IDictionary`를 상속하지 않는다.
>
> 더 미묘한 이유가 하나 더 있다. 만약 `IList<T>`가 `IList`를 상속했다면, `IList<T>`로 캐스트했을 때 `Add(T)`와 `Add(object)`를 **둘 다** 가진 인터페이스가 나온다. 그러면 아무 타입의 객체나 `Add`로 집어넣을 수 있으므로 정적 타입 안전성이 사실상 무너진다.
>
> 물론 구체 클래스는 이득이 되면 두 버전을 다 구현해도 된다. `List<T>`가 그렇게 한다.

`List<T>`는 `IList<T>`와 `IList`의 전형적 구현이다. C# 배열도 제네릭·비제네릭 `IList`를 둘 다 구현하지만, 추가·제거 메서드는 명시적 인터페이스 구현으로 숨겨져 있고 호출하면 `NotSupportedException`을 던진다(9.7절).

> **⚠️ 다차원 배열을 `IList` 인덱서로 접근하면 예외가 난다**
>
> 다음 메서드는 방탄으로 보이지만 아니다.
>
> ```csharp
> public object FirstOrNull (IList list)
> {
>     if (list == null || list.Count == 0) return null;
>     return list[0];
> }
> ```
>
> 다차원 배열을 넘기면 `ArgumentException`이 난다. 다차원 배열은 `IList`를 구현하지만 1차원 인덱서가 의미를 갖지 못하기 때문이다. 런타임에 다차원 배열인지 검사하려면 이렇게 한다(57장).
>
> ```csharp
> list.GetType().IsArray && list.GetType().GetArrayRank() > 1
> ```

### 읽기 전용 인터페이스와 공변성

```csharp
public interface IReadOnlyCollection<out T> : IEnumerable<T>, IEnumerable
{
    int Count { get; }
}

public interface IReadOnlyList<out T> : IReadOnlyCollection<T>, IEnumerable<T>, IEnumerable
{
    T this[int index] { get; }
}
```

타입 매개변수가 **출력 위치에만** 쓰이므로 공변(`out`)으로 표시할 수 있다(23.10절). 그래서 고양이 리스트를 동물의 읽기 전용 리스트로 취급할 수 있다.

```csharp
IReadOnlyList<Cat> cats = new List<Cat>();
IReadOnlyList<Animal> animals = cats;      // OK — 공변
```

`ICollection<T>`와 `IList<T>`는 `T`가 입력 위치(`Add(T)`)와 출력 위치(인덱서 getter) 양쪽에 쓰이므로 공변으로 만들 수 없다.

> **⚠️ 읽기 전용 인터페이스는 "읽기 전용 뷰"일 뿐이다**
>
> 이 인터페이스들은 컬렉션의 **읽기 전용 뷰**를 나타낸다. 밑에 깔린 구현은 여전히 쓰기 가능할 수 있다. 대부분의 가변 컬렉션은 읽기 전용 인터페이스와 읽기/쓰기 인터페이스를 **둘 다** 구현한다. 즉 `IReadOnlyList<string>`을 받은 쪽에서 `(IList<string>)`로 다운캐스트하면 그냥 수정할 수 있다. 이 구멍을 어떻게 막는지는 24.10절에서 다룬다.

`IReadOnlyList<T>`는 Windows 런타임 타입 `IVectorView<T>`에 매핑된다.

### 어떤 타입이 무엇을 구현하는가

| 타입 | `IEnumerable<T>` | `ICollection<T>` | `IList<T>` | `IReadOnlyList<T>` | `ISet<T>` | `IDictionary<K,V>` |
|---|---|---|---|---|---|---|
| `T[]` | O | O(명시적) | O(명시적) | O | X | X |
| `List<T>` | O | O | O | O | X | X |
| `Queue<T>` / `Stack<T>` | O | X (비제네릭 `ICollection`만) | X | X | X | X |
| `LinkedList<T>` | O | O | X | X (`IReadOnlyCollection<T>`만) | X | X |
| `HashSet<T>` | O | O | X | X | O | X |
| `SortedSet<T>` | O | O | X | X | O | X |
| `Dictionary<K,V>` | O(`KeyValuePair`) | O | X | X | X | O |
| `SortedList<K,V>` | O | O | X | X | X | O |
| `ReadOnlyCollection<T>` | O | O(쓰기는 예외) | O(쓰기는 예외) | O | X | X |
| `ImmutableList<T>` | O | O(쓰기는 예외) | O(쓰기는 예외) | O | X | X |

`Queue<T>`와 `Stack<T>`가 `ICollection<T>`를 구현하지 **않는다**는 점이 자주 놀라움을 준다. 임의 위치에 `Add`하거나 `Remove`하는 개념이 이 자료구조에 없기 때문이다. 비제네릭 `ICollection`은 구현하므로 `Count`와 `CopyTo`는 쓸 수 있다.

> **💡 인터페이스를 직접 구현할 일은 거의 없다**
>
> 컬렉션 클래스를 만들어야 할 때 대부분의 답은 "`Collection<T>`를 상속하라"이다(24.9절). LINQ나 반복자 메서드로 끝나는 경우도 많다. `IList<T>`를 밑바닥부터 구현하고 있다면 요구사항을 다시 읽어 보는 편이 낫다.

## 24.3 `Array` 클래스 — 생성, 복사, 검색, 정렬, 변환

### 컬렉션으로서의 배열

9장에서 배열을 언어 기능으로 다뤘다. 여기서는 **컬렉션 계층의 한 구성원**으로서의 배열을 본다.

`Array`는 모든 1차원·다차원 배열의 암시적 기반 클래스이고, 표준 컬렉션 인터페이스를 구현하는 가장 근본적인 타입이다. `Array`가 제공하는 것은 **타입 통일**이다. 선언 방식이나 요소 타입과 무관하게 모든 배열에 공통 메서드 집합이 적용된다.

C# 문법으로 배열을 선언하면 CLR이 `Array`를 암시적으로 서브타이핑해 차원과 요소 타입에 맞는 **의사 타입(pseudotype)** 을 합성한다. 이 의사 타입이 `IList<string>` 같은 타입 붙은 제네릭 컬렉션 인터페이스를 구현한다.

`Array`는 `IList<T>`까지의 컬렉션 인터페이스를 제네릭·비제네릭 양쪽으로 구현한다. 다만 `IList<T>`는 **명시적으로** 구현한다. 고정 길이 컬렉션에서 예외를 던질 수밖에 없는 `Add`나 `Remove`가 공개 표면에 보이지 않게 하기 위해서다.

> **📌 `object[]`가 아니라 `Array`인 이유**
>
> 동적으로 생성된 0기반 배열은 호환되는 C# 배열 타입으로 캐스트할 수 있다(`Apple`이 `Fruit`를 상속하면 `Apple[]`은 `Fruit[]`로 캐스트된다 — 9.6절). 그렇다면 왜 `object[]`를 통일 타입으로 삼지 않았을까?
>
> `object[]`는 **다차원 배열과도, 값 타입 배열과도, 하한이 0이 아닌 배열과도 호환되지 않기** 때문이다. `int[]`는 `object[]`로 캐스트할 수 없다. 완전한 타입 통일에는 `Array` 클래스가 필요하다.

### 정적 메서드가 많다는 함정

> **⚠️ 인스턴스 메서드일 것 같은 것들이 정적 메서드다**
>
> `Array`에서 인스턴스 메서드로 기대할 만한 상당수가 실제로는 정적 메서드다. `Sort`, `Reverse`, `IndexOf`, `Find`, `Copy`, `Clear`, `Resize`, `ConvertAll`, `ForEach`, `BinarySearch`, `Exists`, `TrueForAll`이 전부 정적이다. 인스턴스 메서드는 `GetValue`, `SetValue`, `CopyTo`, `Clone`, `GetLength`, `GetLowerBound` 정도다.
>
> 이상한 설계 결정이고, 실무적 함의는 하나다. **`Array`에서 메서드를 찾을 때는 정적·인스턴스 양쪽을 다 봐야 한다.** IntelliSense에서 `myArray.` 을 쳤을 때 안 보인다고 없는 것이 아니다.

### 검색

`Array`가 제공하는 1차원 배열 검색 메서드는 세 갈래다.

| 갈래 | 메서드 | 전제 | 못 찾았을 때 |
|---|---|---|---|
| 이진 탐색 | `BinarySearch` | **정렬되어 있어야 한다**. 순서 비교 가능해야 한다 | 음수(삽입 위치의 비트 보수) |
| 선형 탐색 | `IndexOf`, `LastIndexOf` | 없음 | `-1` |
| 술어 기반 | `Find`, `FindLast`, `FindIndex`, `FindLastIndex`, `FindAll`, `Exists`, `TrueForAll` | 없음 | 인덱스 반환형은 `-1`, 요소 반환형은 `default(T)` |

**어떤 검색 메서드도 값을 못 찾았다고 예외를 던지지 않는다.** 정수를 반환하면 `-1`(0기반 배열 기준), 제네릭 타입을 반환하면 그 타입의 기본값(`int`면 `0`, `string`이면 `null`)이다.

술어 기반 메서드는 `Predicate<T>` 델리게이트를 받는다.

```csharp
public delegate bool Predicate<T> (T object);
```

```csharp
string[] names = { "Rodney", "Jack", "Jill" };
string match = Array.Find (names, n => n.Contains ("a"));   // "Jack"
```

`FindAll`은 조건을 만족하는 항목의 **배열**을 반환한다. `System.Linq`의 `Enumerable.Where`와 동등하되 반환 타입이 `IEnumerable<T>`가 아니라 배열이다. `Exists`는 `Any`, `TrueForAll`은 `All`에 대응한다(30장).

> **⚠️ `BinarySearch`의 비교자는 정렬에 쓴 비교자와 같아야 한다**
>
> `BinarySearch`는 `IComparer` / `IComparer<T>`를 받을 수 있다. 이 비교자는 **원래 배열을 정렬할 때 쓴 비교자와 일관되어야 한다.** 성(姓) 정렬용 비교자로 정렬해 놓고 기본 비교자로 이진 탐색하면 아무 예외 없이 틀린 답이 나온다. 비교자를 넘기지 않으면 요소 타입의 `IComparable` / `IComparable<T>` 구현에 따른 기본 순서가 적용된다(25.6절).

### 정렬

`Sort`에는 배열 하나를 정렬하는 오버로드(`Sort<T>(T[])`, `Sort(Array)`)와 **배열 쌍**을 정렬하는 오버로드(`Sort<TKey,TValue>(TKey[] keys, TValue[] items)`)가 있다. 각각 `int index`(시작 인덱스), `int length`(정렬할 개수), `IComparer<T>`, `Comparison<T>`를 추가로 받는 오버로드도 있다.

배열 쌍 정렬은 첫 배열의 순서 결정을 두 번째 배열에 그대로 적용한다.

```csharp
int[]    numbers = { 3, 2, 1 };
string[] words   = { "three", "two", "one" };
Array.Sort (numbers, words);
// numbers → { 1, 2, 3 }
// words   → { "one", "two", "three" }
```

`Comparison<T>` 델리게이트는 `IComparer<T>.Compare`와 같은 의미론을 따른다. `x`가 앞이면 음수, 뒤면 양수, 같은 순위면 0.

```csharp
// 홀수를 앞으로
int[] numbers = { 1, 2, 3, 4, 5 };
Array.Sort (numbers, (x, y) => x % 2 == y % 2 ? 0 : x % 2 == 1 ? -1 : 1);
// → { 1, 3, 5, 2, 4 }
```

> **📌 `Array.Sort` 대신 LINQ**
>
> `Array.Sort`는 **원본을 제자리에서 바꾼다.** LINQ의 `OrderBy` / `ThenBy`는 원본을 건드리지 않고 정렬된 결과를 새 `IEnumerable<T>` 시퀀스로 낸다(30.5절). 게다가 LINQ 정렬은 안정 정렬이지만 `Array.Sort`는 아니다(9.7절). 다중 키 정렬이라면 LINQ 쪽이 거의 항상 맞다.

### 변환과 열거

`Array.ConvertAll`은 `Converter` 델리게이트로 요소를 변환한 새 배열을 만든다.

```csharp
public delegate TOutput Converter<TInput,TOutput> (TInput input);
```

```csharp
float[] reals  = { 1.3f, 1.5f, 1.8f };
int[]   wholes = Array.ConvertAll (reals, r => Convert.ToInt32 (r));   // { 1, 2, 2 }
```

`Array.ForEach`는 `Action<T>`를 받아 요소마다 실행한다.

```csharp
Array.ForEach (new[] { 1, 2, 3 }, Console.WriteLine);
```

컬렉션 식을 쓰면 더 짧아진다 ※C# 12 (24.14절).

```csharp
Array.ForEach ([ 1, 2, 3 ], Console.WriteLine);
```

`AsReadOnly`는 요소 재할당을 막는 래퍼를 돌려준다(24.10절). `Array.Empty<T>()`는 길이 0인 **공유** 배열을 돌려주므로 빈 배열을 만들 때 할당이 발생하지 않는다.

`Resize`, `Copy`, `Clone`, `ConstrainedCopy`, `Clear`의 정확한 의미론과 함정은 9.7절에서 다뤘다. 여기서는 컬렉션 관점의 결론만 재확인한다. **`Array.Resize`는 새 배열을 만들어 복사한다.** 비효율적일 뿐 아니라 프로그램의 다른 곳에 남아 있는 참조는 여전히 옛 배열을 가리킨다. 크기가 변하는 컬렉션이 필요하면 `List<T>`가 답이다(24.4절).

### 구조적 동등성

배열은 참조 타입이므로 두 배열의 `==`와 `Equals`는 참조를 비교한다. 요소 단위로 비교하려면 **구조적 동등 비교자**를 써야 한다.

```csharp
object[] a1 = { "string", 123, true };
object[] a2 = { "string", 123, true };

Console.WriteLine (a1 == a2);          // False
Console.WriteLine (a1.Equals (a2));    // False

IStructuralEquatable se1 = a1;
Console.WriteLine (se1.Equals (a2, StructuralComparisons.StructuralEqualityComparer));
// True
```

`Clone`은 **얕은 복제(shallow clone)** 다. 값 타입 요소는 값이 복사되지만 참조 타입 요소는 참조만 복사된다 — 두 배열의 요소가 같은 객체를 가리킨다. 깊은 복사가 필요하면 배열을 돌면서 요소를 하나씩 복제해야 한다. **다른 .NET 컬렉션 타입에도 같은 규칙이 적용된다.**

### 동적 생성과 랭크 무관 코드

`Array.CreateInstance`는 요소 타입과 랭크(차원 수)를 **런타임에** 정하게 해 준다. 이렇게 만든 배열은 `GetValue` / `SetValue`로 접근하며, 다차원이면 인덱서 배열(`params int[] indices`)을 받는다.

```csharp
Array a = Array.CreateInstance (typeof(string), 2);
a.SetValue ("hi", 0);                      // → a[0] = "hi";
string s = (string) a.GetValue (0);        // → s = a[0];
string[] cSharpArray = (string[]) a;       // 캐스트해서 C# 배열로 쓸 수 있다

// 랭크와 무관하게 첫 요소를 출력한다
void WriteFirstValue (Array arr)
{
    // 인덱서 배열은 0으로 초기화되므로 그대로 넘기면 첫 요소를 얻는다
    int[] indexers = new int[arr.Rank];
    Console.WriteLine ($"{arr.Rank}차원, 첫 값 = {arr.GetValue (indexers)}");
}
```

> **💡 타입은 모르지만 랭크는 아는 경우라면 제네릭이 낫다**
>
> ```csharp
> void WriteFirstValue<T> (T[] array) => Console.WriteLine (array[0]);
> ```
>
> `GetValue`는 `object`를 반환하므로 값 타입에서 박싱이 일어나고 런타임 타입 검사도 붙는다. 제네릭 쪽은 둘 다 없다. `SetValue`는 요소 타입과 호환되지 않는 값을 넣으면 예외를 던진다.

> **⚠️ 64비트 인덱서는 실무에서 무의미하다**
>
> `Array`에는 `Int64`를 받는 오버로드(`GetLongLength`, `LongLength` 등)가 있어 이론상 2^64개 요소를 주소 지정할 수 있다. 실제로는 쓸모가 없다. **CLR이 배열을 포함한 어떤 객체도 2GB를 넘지 못하게 하기 때문이다**(32비트든 64비트든). 대용량 데이터는 청크로 쪼개거나 비관리 메모리를 쓴다(68.8절).
>
> 또한 하한이 0이 아닌 배열은 .NET 공용 언어 사양(CLS)과 호환되지 않는다. F#이나 VB에서 소비될 수 있는 라이브러리의 공개 멤버로 노출해서는 안 된다.

## 24.4 `List<T>` 내부 구조 — 배열 증가 전략과 `Capacity`

### 배열 위에 얹은 얇은 층

`List<T>`는 .NET에서 가장 많이 쓰이는 컬렉션이다. 그리고 놀랄 만큼 단순하다. 개념적으로 필드가 셋이면 끝난다.

```csharp
public class List<T> : IList<T>, IList, IReadOnlyList<T>
{
    private T[] _items;      // 실제 저장소 — Capacity 크기
    private int _size;       // 실제 요소 개수 — Count
    private int _version;    // 수정 횟수 — 열거 무결성 검사용
    // ...
}
```

`List<T>`가 하는 일은 "배열 하나를 들고 있다가, 꽉 차면 더 큰 배열로 갈아타면서 내용을 옮긴다"가 전부다. `Add`가 빠르고(보통 끝에 빈칸이 있으니까), `Insert`와 `Remove`가 느리고(삽입점 뒤의 요소를 전부 밀어야 하니까), `Contains`가 느린(하나씩 다 봐야 하니까) 이유가 이 한 문장에서 전부 나온다.

### `Capacity` vs `Count`

이 둘의 구분이 `List<T>`를 이해하는 첫 관문이다.

| | 의미 | 바꾸는 법 |
|---|---|---|
| `Count` | 실제로 들어 있는 요소 개수 (`_size`) | `Add`/`Remove` 등으로 간접적으로 |
| `Capacity` | 내부 배열의 길이 (`_items.Length`) | 직접 설정 가능. 재할당을 유발한다 |

`Capacity >= Count`는 항상 참이다. 그 사이의 빈칸이 "다음 `Add`가 재할당 없이 들어갈 자리"다.

```csharp
var list = new List<int>();
Console.WriteLine ($"{list.Count} / {list.Capacity}");   // 0 / 0
list.Add (1);
Console.WriteLine ($"{list.Count} / {list.Capacity}");   // 1 / 4
for (int i = 0; i < 4; i++) list.Add (i);
Console.WriteLine ($"{list.Count} / {list.Capacity}");   // 5 / 8
```

### 증가 전략 — 2배

내부 배열이 꽉 찬 상태에서 `Add`가 호출되면 `List<T>`는 다음을 한다.

```text
    Add 호출, _size == _items.Length
              │
              ↓
    ┌─────────────────────────────────────────┐
    │ 새 용량 = (현재 용량 == 0) ? 4 : 현재×2  │
    │ (단, Array.MaxLength를 넘지 않게 clamp)  │
    └───────────────────┬─────────────────────┘
                        ↓
    ┌─────────────────────────────────────────┐
    │ 새 배열 할당 → Array.Copy로 전체 복사    │
    │ _items = 새 배열 (옛 배열은 GC 대상)      │
    └───────────────────┬─────────────────────┘
                        ↓
              _items[_size++] = item


  용량 변화:   0 → 4 → 8 → 16 → 32 → 64 → 128 → ...

  ┌───┬───┬───┬───┐
  │ a │ b │ c │ d │              Count=4, Capacity=4  (꽉 참)
  └───┴───┴───┴───┘
          │ Add("e")
          ↓  새 배열 할당 + 복사
  ┌───┬───┬───┬───┬───┬───┬───┬───┐
  │ a │ b │ c │ d │ e │   │   │   │  Count=5, Capacity=8
  └───┴───┴───┴───┴───┴───┴───┴───┘
                    ↑───── 빈칸 3개 (다음 3번의 Add는 복사 없음)
```

2배 전략의 결과가 **분할 상환(amortized) O(1)** 이다. 요소 N개를 추가하는 동안 복사되는 총 요소 수는 4 + 8 + 16 + ... + N/2 + N < 2N이다. 즉 요소 하나당 평균 2회 미만의 복사다. 개별 `Add`는 최악의 경우 O(N)이지만, N번의 `Add` 전체는 O(N)이다.

> **⚠️ 2배 전략은 확장 순간 옛 배열 기준 3배의 메모리를 쓴다**
>
> 용량 100만인 리스트가 확장되는 순간, 힙에는 100만짜리 배열과 200만짜리 배열이 **동시에** 존재한다. 요소가 참조 타입이면 8MB + 16MB = 24MB가 잠깐 함께 살아 있다.
>
> 게다가 크기가 85,000바이트 이상인 배열은 **대형 객체 힙(LOH)** 으로 간다(62장). `List<T>`가 커지면 내부 배열이 LOH에 들어가고, LOH는 기본적으로 압축되지 않으므로 재할당이 반복되면 단편화의 원인이 된다.
>
> 최종 크기를 대략이라도 안다면 반드시 미리 지정하라.

### 미리 잡기 — 생성자, `Capacity`, `EnsureCapacity`

```csharp
var a = new List<string> (10_000);   // 1. 생성자에 초기 용량
var b = new List<string>();
b.Capacity = 10_000;                 // 2. Capacity 직접 설정 (즉시 재할당)
var c = new List<string>();
c.EnsureCapacity (10_000);           // 3. 최소 용량 보장 ※.NET 6
```

`EnsureCapacity`는 실제로 확보된 용량을 반환한다. `Capacity` 설정과 달리 이미 충분하면 재할당하지 않으므로 반복 호출이 안전하다. `Queue<T>`, `Stack<T>`도 ※.NET 6부터 `EnsureCapacity`를 갖는다. `Dictionary<TKey,TValue>`와 `HashSet<T>`는 그보다 먼저(※.NET Core 2.1) 생겼다.

반대 방향은 `TrimExcess()`다. 내부 배열을 `Count`에 맞게 줄인다. 리스트를 다 채운 뒤 오래 보관할 때 유효하다.

> **💡 `AddRange`는 개수를 알면 한 번에 잡는다**
>
> `AddRange(IEnumerable<T>)`는 인자가 `ICollection<T>`를 구현하면 `Count`를 먼저 읽어 필요한 용량을 **한 번에** 확보한 뒤 `CopyTo`로 벌크 복사한다. 구현하지 않으면 열거하면서 하나씩 `Add`하므로 재할당이 여러 번 일어날 수 있다.
>
> 그래서 `list.AddRange(otherList)`는 빠르고 `list.AddRange(query.Where(...))`는 상대적으로 느리다. 후자가 뜨거운 경로라면 `EnsureCapacity`로 힌트를 주거나 `ToArray()`를 먼저 부르는 편이 나을 수 있다.

### 삽입과 제거의 비용

| 연산 | 비용 | 이유 |
|---|---|---|
| `Add` | 분할 상환 O(1) | 끝에 넣는다 |
| `Insert(0, x)` | O(N) | 전체를 한 칸씩 뒤로 민다 |
| `RemoveAt(Count-1)` | O(1) | 밀 것이 없다 |
| `RemoveAt(0)` | O(N) | 전체를 한 칸씩 앞으로 당긴다 |
| `Remove(x)` | O(N) | 선형 탐색 + 이동 |
| `this[i]` | O(1) | 배열 인덱싱 |
| `Contains` / `IndexOf` | O(N) | 선형 탐색 |
| `BinarySearch` | O(log N) | **정렬되어 있어야 한다** |

`RemoveAt`은 용량을 줄이지 않는다. 100만 개를 넣었다가 전부 지워도 내부 배열은 여전히 100만 칸이다. `Clear()`도 마찬가지다 — `Count`만 0이 되고 `Capacity`는 그대로다(참조 타입 요소는 GC를 위해 `null`로 지워진다).

> **⚠️ 리스트 앞쪽에서 반복적으로 제거하지 마라**
>
> ```csharp
> while (list.Count > 0)
> {
>     Process (list[0]);
>     list.RemoveAt (0);      // 매번 O(N) — 전체가 O(N²)가 된다
> }
> ```
>
> 10만 개짜리 리스트에서 이 루프는 약 50억 회의 요소 이동을 일으킨다. 앞에서 빼는 자료구조가 필요하면 `Queue<T>`를 쓰거나(24.5절), 뒤에서부터 처리하라.

### `_version`과 `InvalidOperationException`의 메커니즘

열거 중에 컬렉션을 수정하면 예외가 난다.

```csharp
var list = new List<string> { "a", "b", "c" };

foreach (string s in list)
    if (s == "b")
        list.Remove (s);       // InvalidOperationException
```

메시지는 "Collection was modified; enumeration operation may not execute."다. 이 검사가 어떻게 이루어지는지가 핵심이다.

`List<T>`는 `_version`이라는 정수 필드를 갖는다. **컬렉션의 구조를 바꾸는 모든 연산**(`Add`, `Insert`, `Remove`, `RemoveAt`, `RemoveAll`, `Clear`, `Reverse`, `Sort`, 인덱서 setter 등)이 이 필드를 1 증가시킨다. 열거자는 생성 시점에 그 값을 복사해 두고, `MoveNext`마다 원본과 비교한다.

```csharp
// List<T>.Enumerator의 개념적 구현
public struct Enumerator : IEnumerator<T>
{
    private readonly List<T> _list;
    private int _index;
    private readonly int _version;   // 생성 시점의 스냅샷
    private T _current;

    internal Enumerator (List<T> list)
        => (_list, _index, _version, _current) = (list, 0, list._version, default);

    public bool MoveNext()
    {
        List<T> localList = _list;
        if (_version == localList._version && (uint)_index < (uint)localList._size)
        {
            _current = localList._items[_index++];
            return true;
        }
        return MoveNextRare();       // 버전 불일치면 여기서 예외를 던진다
    }
    // ...
}
```

빠른 경로에서 `_version` 비교는 **정수 비교 한 번**이다. 사실상 공짜다. 불일치하거나 끝에 도달했을 때만 별도 메서드(`MoveNextRare`)로 빠져 예외를 던지거나 종료 처리를 한다. 예외 던지는 코드를 별도 메서드로 분리해 두면 `MoveNext` 본체가 작아져 JIT이 인라이닝하기 좋아진다(55장).

> **⚠️ 마지막 요소를 지우면 예외가 안 날 수도 있다**
>
> `List<T>.Enumerator.MoveNext`의 빠른 경로 조건은 `_version` 일치 **그리고** 인덱스 범위 내다. 마지막에서 두 번째 요소를 처리하는 중에 요소 하나를 지우면, 다음 `MoveNext`에서 인덱스가 이미 범위를 벗어나 있을 수 있다. 그러면 빠른 경로를 벗어나 `MoveNextRare`로 가는데, 여기서는 버전 검사를 하므로 결국 예외가 난다.
>
> 하지만 컬렉션 타입에 따라 결과가 다르다. **버전 검사는 "수정을 감지하면 예외를 던진다"는 최선 노력(best effort)이지 완전한 보장이 아니다.** 어떤 경우에는 예외 없이 조용히 요소를 건너뛰거나 중복 처리한다. 예외가 안 났다고 안전한 것이 아니다.

> **📌 딕셔너리는 규칙이 다르다 ※.NET Core 3.0**
>
> `Dictionary<TKey,TValue>`의 `Remove`는 .NET Core 3.0부터 버전을 증가시키지 않는다. 그래서 딕셔너리는 **열거 중 제거가 허용된다**(추가나 다른 수정은 여전히 안 된다). .NET Framework에서는 이 코드가 예외를 던진다.
>
> 즉 같은 코드가 런타임에 따라 다르게 동작한다. 이식성이 필요하면 이 동작에 기대지 마라.

### 열거 중 수정을 피하는 방법

```csharp
list.RemoveAll (s => s == "b");                  // 1. 술어 기반 일괄 제거 — O(N)

for (int i = list.Count - 1; i >= 0; i--)        // 2. 뒤에서부터 인덱스 루프
    if (list[i] == "b") list.RemoveAt (i);

foreach (string s in list.ToList())              // 3. 스냅샷 위에서 열거
    if (s == "b") list.Remove (s);               //    원본을 고쳐도 대상은 복사본
```

`RemoveAll`은 요소를 한 번만 훑으면서 살아남을 요소를 앞으로 압축하므로 O(N)이다. 반복 `Remove`는 O(N²)다. 2번은 할당이 없고, 3번은 복사본 할당이 하나 생긴다.

> **💡 `CollectionsMarshal.AsSpan`으로 경계 검사를 걷어낼 수 있다 ※.NET 5**
>
> `System.Runtime.InteropServices.CollectionsMarshal.AsSpan(list)`는 `List<T>`의 내부 배열을 `Span<T>`로 그대로 노출한다. 복사가 없고, 스팬 순회는 경계 검사가 제거되기 쉬워 인덱서 접근보다 빠르다(68장).
>
> 대가가 크다. **리스트가 재할당되는 순간 그 스팬은 옛 배열을 가리키는 유령이 된다.** 스팬을 들고 있는 동안 `Add`를 부르면 조용히 다른 데이터를 읽거나 쓴다. 뜨거운 루프 안에서, 리스트 크기가 변하지 않음이 확실할 때만 쓴다.

## 24.5 `Queue`, `Stack`, `LinkedList`, `SortedList`

### `Queue<T>` — 선입선출

`Queue<T>`는 FIFO(first-in, first-out) 자료구조다. `Enqueue`로 꼬리에 넣고 `Dequeue`로 머리에서 꺼낸다. `Peek`은 꺼내지 않고 머리를 본다.

생성자는 셋이다 — 기본, 기존 컬렉션 복사(`IEnumerable<T>`), 초기 용량 지정(`int`). 나머지 멤버는 `Clear`, `Contains`, `CopyTo`, `Count`, `Dequeue`, `Enqueue`, `Peek`, `ToArray`, `TrimExcess`, 그리고 구조체를 반환하는 `GetEnumerator`다.

```csharp
var q = new Queue<int>();
q.Enqueue (10); q.Enqueue (20);
int[] data = q.ToArray();         // 배열로 내보내기
Console.WriteLine (q.Peek());     // 10
Console.WriteLine (q.Dequeue());  // 10
Console.WriteLine (q.Dequeue());  // 20
Console.WriteLine (q.Dequeue());  // InvalidOperationException — 큐가 비었다
```

큐도 열거 가능하지만 `IList<T>` / `IList`는 구현하지 않는다. 인덱스로 직접 접근할 수 없기 때문이다. 임의 접근이 필요하면 `ToArray()`로 내보낸다.

**내부는 배열이다.** `List<T>`처럼 필요할 때 크기가 늘어난다. 다만 머리와 꼬리를 가리키는 인덱스를 별도로 유지하는 **원형 버퍼(circular buffer)** 라서, 머리에서 꺼내도 뒤 요소를 당기지 않는다. `Enqueue`도 `Dequeue`도 O(1)이다(내부 재할당이 일어나는 순간만 예외).

`Dequeue`는 머리 인덱스를 한 칸 전진시킬 뿐 요소를 당기지 않고, `Enqueue`는 꼬리 인덱스 위치에 기록한 뒤 전진시키되 배열 끝에 닿으면 0으로 되감는다. 그래서 `List<T>`의 `RemoveAt(0)`과 달리 O(1)이다.

> **📌 `TryDequeue` / `TryPeek` ※.NET Core 2.0**
>
> 빈 큐에서 `Dequeue`나 `Peek`을 부르면 `InvalidOperationException`이 난다. 예외를 흐름 제어에 쓰지 않으려면 `TryDequeue(out T)` / `TryPeek(out T)`를 쓴다. `Stack<T>`에도 `TryPop`, `TryPeek`이 있다. 예외는 비싸다(78장).

### `Stack<T>` — 후입선출

`Stack<T>`는 LIFO(last-in, first-out)다. `Push`로 꼭대기에 얹고 `Pop`으로 꼭대기에서 꺼낸다. 나머지는 `Queue<T>`와 대칭이다.

```csharp
var s = new Stack<int>();
s.Push (1); s.Push (2); s.Push (3);   // Stack = 1,2,3
Console.WriteLine (s.Peek());         // 3,  Stack = 1,2,3
Console.WriteLine (s.Pop());          // 3,  Stack = 1,2
Console.WriteLine (s.Pop());          // 2,  Stack = 1
Console.WriteLine (s.Pop());          // 1,  Stack = <비어 있음>
Console.WriteLine (s.Pop());          // InvalidOperationException
```

내부 구현은 `Queue<T>`, `List<T>`와 마찬가지로 필요할 때 크기가 늘어나는 배열이다.

> **⚠️ `Stack<T>`의 열거 순서는 꼭대기부터다**
>
> `foreach (var x in stack)`는 마지막에 `Push`한 것부터 나온다. `ToArray()`도 같은 순서다. 즉 배열의 인덱스 0이 스택의 **꼭대기**다. 내부 배열의 물리적 순서와 반대이므로, "삽입 순서대로 돌겠지"라고 가정한 코드가 조용히 뒤집힌 결과를 낸다.

### `PriorityQueue<TElement,TPriority>` ※.NET 6

.NET 6이 우선순위 큐를 추가했다. `Queue<T>`와 같지만 각 항목에 우선순위가 붙고, **우선순위가 낮은 것부터** 꺼내진다(최소 힙).

```csharp
PriorityQueue<string, int> vaccine = new();     // 1 = 최우선, 3 = 후순위
vaccine.Enqueue ("Pamela", 1);   vaccine.Enqueue ("Rebecca", 3);
vaccine.Enqueue ("Juliet", 2);   vaccine.Enqueue ("Ian", 1);

while (vaccine.Count > 0) Console.Write (vaccine.Dequeue() + " ");
// Pamela Ian Juliet Rebecca   (우선순위 1인 둘 사이의 순서는 보장되지 않는다)
```

주요 멤버는 `Enqueue`, `EnqueueRange`, `Dequeue`, `TryDequeue`, `Peek`, `TryPeek`, `Clear`, `Count`, `Comparer`, `EnsureCapacity`, 그리고 `UnorderedItems`다. 우선순위 비교 방식은 생성자에 `IComparer<TPriority>`를 넘겨 바꾼다.

> **⚠️ 같은 우선순위끼리의 순서는 보장되지 않는다**
>
> 우선순위가 같은 항목이 둘 이상이면 어느 쪽이 먼저 나올지 정해져 있지 않다. 위 예에서 우선순위 3인 항목이 둘이었다면 어느 쪽이 먼저 나올지 알 수 없다. 정확한 순서가 필요하면 우선순위 값 자체를 유일하게 만들어야 한다(예: `(priority, sequenceNumber)` 튜플을 우선순위로 쓰고 비교자를 꽂는다).
>
> `UnorderedItems`도 마찬가지다. 이름 그대로 **정렬되지 않은** `(Element, Priority)` 쌍의 시퀀스이며, 내부 힙 배열의 물리적 순서를 그대로 드러낸다. 디버깅·전체 순회 용도이지 우선순위 순서로 읽는 용도가 아니다.

### `LinkedList<T>` — 이중 연결 리스트

`LinkedList<T>`는 이중 연결 리스트다. 각 노드가 앞 노드·뒤 노드·실제 요소를 참조한다.

`First`와 `Last`가 양 끝 노드를 가리키고, 각 노드는 `Previous`·`Next`로 양쪽 이웃을, `Value`로 요소를 참조한다.

장점은 **어디에든 효율적으로 삽입할 수 있다**는 것이다. 노드 하나를 만들고 참조 몇 개를 갱신하면 끝이다. 단점은 **삽입할 위치를 찾는 것이 느리다**는 것이다. 인덱스로 직접 들어갈 수단이 없어 노드를 하나씩 따라가야 하고, 이진 탐색도 불가능하다.

그래서 `IEnumerable<T>`와 `ICollection<T>`는 구현하지만 `IList<T>`는 구현하지 않는다.

```csharp
public sealed class LinkedListNode<T>
{
    public LinkedList<T>     List     { get; }
    public LinkedListNode<T> Next     { get; }
    public LinkedListNode<T> Previous { get; }
    public T                 Value    { get; set; }
}
```

추가 메서드는 위치를 상대 노드나 양 끝으로 지정한다.

```csharp
public void AddFirst (LinkedListNode<T> node);
public LinkedListNode<T> AddFirst (T value);
public void AddLast (LinkedListNode<T> node);
public LinkedListNode<T> AddLast (T value);
public LinkedListNode<T> AddAfter  (LinkedListNode<T> node, T value);
public LinkedListNode<T> AddBefore (LinkedListNode<T> node, T value);
```

제거는 `Clear`, `RemoveFirst`, `RemoveLast`, `Remove(T value)`, `Remove(LinkedListNode<T> node)`다. 검색은 `Contains`, `Find`, `FindLast`이며 **전부 내부 순회를 요구한다**. `Count`, `First`, `Last`는 내부 필드로 관리되므로 빠르다.

```csharp
var tune = new LinkedList<string>();
tune.AddFirst ("do");                        // do
tune.AddLast  ("so");                        // do - so
tune.AddAfter (tune.First, "re");            // do - re - so
tune.AddBefore (tune.Last, "fa");            // do - re - fa - so

LinkedListNode<string> faNode = tune.Find ("fa");
tune.Remove (faNode);                        // do - re - so
tune.AddFirst (faNode);                      // fa - do - re - so
```

> **⚠️ `LinkedList<T>`는 거의 항상 틀린 선택이다**
>
> 교과서의 Big-O만 보면 "중간 삽입 O(1)"이라 매력적이다. 실제 하드웨어에서는 그렇지 않다.
>
> - **요소 하나당 노드 객체 하나가 힙에 할당된다.** 객체 헤더 + 참조 3개 + 값. 64비트에서 `int` 하나를 담는 데 40바이트 안팎이 든다. `List<int>`는 4바이트다.
> - **메모리가 흩어진다.** 순회할 때마다 캐시 미스가 난다. 연속 배열을 훑는 `List<T>`와 비교하면 순회 속도가 수 배에서 수십 배 차이 난다.
> - **삽입 위치를 찾는 데 O(N)이 든다.** "삽입은 O(1)"은 이미 노드를 손에 쥐고 있을 때의 이야기다.
>
> `LinkedList<T>`가 이기는 시나리오는 좁다. 요소가 크고, 이미 확보한 노드 참조를 통해 리스트 중간에서 매우 빈번하게 삽입·제거하며, 순회는 드문 경우다. 그렇지 않다면 `List<T>`가 거의 항상 빠르다. 자세한 상수 비교는 72.6절에 있다.

### `SortedList<TKey,TValue>` — 정렬된 배열 쌍

`SortedList<TKey,TValue>`는 이름과 달리 **딕셔너리**다. 키로 정렬된 상태를 유지한다. 내부 구현은 **키 배열 하나와 값 배열 하나**다.

- 조회는 키 배열에 대한 **이진 탐색**이라 O(log N)이다.
- 삽입·삭제는 배열 요소를 밀어야 하므로 O(N)이다.
- 인덱스로도 접근할 수 있다 — `Keys[i]`, `Values[i]`로 정렬 순서상 n번째 항목에 바로 간다.
- 메모리 오버헤드가 가장 작다.

`SortedDictionary<TKey,TValue>`와의 비교는 24.8절에서 이어 간다. 비제네릭 `SortedList`도 있으며 기능적으로 동일하다.

### `BitArray` — 압축된 불리언

`BitArray`는 `bool` 값을 비트 단위로 압축해 저장한다. `bool`은 값 하나에 1바이트를 쓰지만 `BitArray`는 1비트를 쓴다. `bool[]`이나 `List<bool>`보다 8배 조밀하다.

```csharp
var bits = new BitArray (2);
bits[1] = true;

bits.Xor (bits);                     // 자기 자신과 배타적 논리합
Console.WriteLine (bits[1]);         // False
```

비트 연산 메서드는 `And`, `Or`, `Xor`, `Not` 넷이다. `Not`을 제외하면 다른 `BitArray`를 인자로 받는다. 비제네릭 타입이지만 `bool`만 다루므로 박싱 문제는 없다.

## 24.6 집합 — `HashSet<T>`, `SortedSet<T>`

### 두 집합 타입의 공통점

`HashSet<T>`와 `SortedSet<T>`는 다음 성질을 공유한다.

- `Contains`가 해시 기반(또는 트리 기반) 조회로 **빠르다**.
- **중복을 저장하지 않는다.** 중복 추가 요청은 조용히 무시된다.
- **위치로 요소에 접근할 수 없다.**

차이는 하나다. `SortedSet<T>`는 요소를 정렬 순서로 유지하고 `HashSet<T>`는 그러지 않는다.

공통점은 `ISet<T>` 인터페이스로 포착된다. ※.NET 5부터 두 클래스는 `IReadOnlySet<T>`도 구현하며, 이 인터페이스는 불변 집합 타입들도 구현한다(24.10절).

내부 구현이 성능을 결정한다.

| | 내부 구조 | 조회 | 삽입/삭제 | 순서 |
|---|---|---|---|---|
| `HashSet<T>` | 키만 저장하는 해시테이블 | O(1) | O(1) | 없음 |
| `SortedSet<T>` | 레드/블랙 트리 | O(log N) | O(log N) | 비교자 순 |

즉 `HashSet<T>`는 값이 키와 같은 `Dictionary<T,T>`라고 생각하면 정확하다. 실제로 내부 구조도 딕셔너리와 거의 같다(24.7절).

두 클래스 모두 `ICollection<T>`를 구현하므로 `Contains`, `Add`, `Remove`가 기대대로 있다. 추가로 술어 기반 제거 메서드 `RemoveWhere`가 있다.

```csharp
var letters = new HashSet<char> ("the quick brown fox");

Console.WriteLine (letters.Contains ('t'));    // true
Console.WriteLine (letters.Contains ('j'));    // false

foreach (char c in letters) Console.Write (c); // the quickbrownfx
```

`string`이 `IEnumerable<char>`를 구현하므로 `HashSet<char>`의 생성자에 문자열을 그대로 넘길 수 있다. 출력에서 중복 문자가 사라진 것을 확인하라.

> **⚠️ `HashSet<T>.Add`의 반환값을 버리지 마라**
>
> `ISet<T>.Add`는 `bool`을 반환한다. 실제로 추가됐으면 `true`, 이미 있어서 무시됐으면 `false`다. `ICollection<T>.Add`는 `void`를 반환하므로, **집합을 `ICollection<T>`로 받으면 이 정보가 사라진다.**
>
> ```csharp
> HashSet<string> names = new();
> foreach (string name in new[] { "Adam", "Barry", "Charlie", "Barry" })
>     Console.WriteLine ($"{name} 추가됨: {names.Add (name)}");
> // Adam 추가됨: True / Barry 추가됨: True
> // Charlie 추가됨: True / Barry 추가됨: False
> ```
>
> 이 반환값은 "처음 보는 항목인가"를 O(1)에 판정하는 관용구의 핵심이다. `Contains` 후 `Add`는 조회를 두 번 한다.

### 집합 연산 — 파괴적인 것과 아닌 것

집합 타입의 진짜 가치는 집합 연산에 있다. 네 개는 **원본을 수정한다**.

```csharp
public void UnionWith           (IEnumerable<T> other);   // 더한다
public void IntersectWith       (IEnumerable<T> other);   // 양쪽에 없는 것을 뺀다
public void ExceptWith          (IEnumerable<T> other);   // 지정한 것을 뺀다
public void SymmetricExceptWith (IEnumerable<T> other);   // 한쪽에만 있는 것만 남긴다
```

여섯 개는 **질의만 한다**.

```csharp
public bool IsSubsetOf        (IEnumerable<T> other);
public bool IsProperSubsetOf  (IEnumerable<T> other);
public bool IsSupersetOf      (IEnumerable<T> other);
public bool IsProperSupersetOf(IEnumerable<T> other);
public bool Overlaps          (IEnumerable<T> other);     // 공통 요소가 하나라도 있는가
public bool SetEquals         (IEnumerable<T> other);     // 정확히 같은 요소 집합인가
```

```csharp
// 매번 "the quick brown fox"로 새로 만든 집합에 적용한 결과
letters.IntersectWith ("aeiou");                 // euio         (모음만 남는다)
letters.ExceptWith ("aeiou");                    // th qckbrwnfx (모음을 뺀다)
letters.SymmetricExceptWith ("the lazy brown fox");  // quicklazy (한쪽에만 있는 것만)
```

`HashSet<T>`와 `SortedSet<T>`가 `IEnumerable<T>`를 구현하므로 **인자로 아무 컬렉션이나 넘길 수 있다.** 배열이든 리스트든 문자열이든 다른 집합이든 상관없다.

> **📌 파괴적 연산 vs LINQ 집합 연산자**
>
> LINQ에도 `Union`, `Intersect`, `Except`가 있다(30.7절). 결정적 차이는 두 가지다. LINQ 연산자는 **원본을 건드리지 않고** 새 시퀀스를 내며, **지연 실행**된다. 반면 `UnionWith` 계열은 제자리에서 수정하고 즉시 실행된다.
>
> 이름이 비슷해서 혼동하기 쉽다. `set.Union(other)`(LINQ, 원본 그대로)와 `set.UnionWith(other)`(원본 수정)를 자동 완성으로 잘못 고르면 조용히 다른 프로그램이 된다.

### `SortedSet<T>`의 추가 멤버

`SortedSet<T>`는 `HashSet<T>`의 모든 멤버에 더해 순서에서 나오는 네 가지를 제공한다.

```csharp
public virtual SortedSet<T> GetViewBetween (T lowerValue, T upperValue);
public IEnumerable<T> Reverse();
public T Min { get; }
public T Max { get; }
```

```csharp
var letters = new SortedSet<char> ("the quick brown fox");
foreach (char c in letters) Console.Write (c);       // bcefhiknoqrtuwx

foreach (char c in letters.GetViewBetween ('f', 'i'))
    Console.Write (c);                               // fhi
```

`SortedSet<T>`의 생성자는 동등 비교자가 아니라 **`IComparer<T>`** 를 받는다(24.13절). 해시가 아니라 순서로 동작하기 때문이다. 반대로 `HashSet<T>`는 `IEqualityComparer<T>`를 받는다. 잘못 넘기면 컴파일되지 않는다.

```csharp
class SortPeopleByAge : IComparer<Person>
{
    public int Compare (Person x, Person y)
    {
        if (x?.Age > y?.Age) return 1;
        if (x?.Age < y?.Age) return -1;
        return 0;
    }
}

var setOfPeople = new SortedSet<Person> (new SortPeopleByAge())
{
    new Person { FirstName = "Homer", Age = 47 }, new Person { FirstName = "Marge", Age = 45 },
    new Person { FirstName = "Lisa",  Age =  9 }, new Person { FirstName = "Bart",  Age =  8 }
};
// 나이 순으로 유지된다. 이후에 무엇을 넣거나 빼도 순서가 유지된다
```

> **⚠️ 위 비교자에는 덫이 있다**
>
> `Compare`가 나이만 본다는 것은 **나이가 같은 두 사람이 "같은 요소"로 취급된다**는 뜻이다. `SortedSet<T>`는 중복을 허용하지 않으므로, 나이가 47인 다른 사람을 추가하면 **조용히 무시된다.** 정렬 목적으로 쓴 비교자가 동등성 판정까지 결정한다는 사실을 놓치면 데이터가 사라진다.
>
> 정렬 집합에 넣을 비교자는 "같은 순위 = 같은 요소"를 의도한 것이어야 한다. 그렇지 않다면 최종 결정자(tie-breaker) 키를 비교에 추가하라. 계약 전반은 25.6절에서 다룬다.

> **💡 집합은 중복 제거와 순환 감지의 표준 도구다**
>
> ```csharp
> // 중복 제거 — O(N)
> var unique = new HashSet<string> (rawNames);
>
> // 순환 감지 — 24.1절의 재귀 Count 버그를 고친다
> static int Count (IEnumerable e, HashSet<object> seen)
> {
>     if (!seen.Add (e)) return 0;        // 이미 본 컬렉션이면 즉시 중단
>     // ...
> }
> ```
>
> 두 번째 예에서 `seen`은 참조 동등성으로 비교해야 한다. `new HashSet<object>(ReferenceEqualityComparer.Instance)`로 만든다(24.13절).

## 24.7 `Dictionary<TKey,TValue>` 내부 구조 — 버킷, 해시 충돌, 엔트리 배열

### `IDictionary<TKey,TValue>` — 표준 프로토콜

딕셔너리는 각 요소가 키/값 쌍인 컬렉션이다. `IDictionary<TKey,TValue>`는 `ICollection<KeyValuePair<TKey,TValue>>`를 확장해 임의 타입의 키로 요소에 접근하는 멤버를 더한다.

```csharp
public interface IDictionary<TKey, TValue>
    : ICollection<KeyValuePair<TKey, TValue>>, IEnumerable
{
    bool ContainsKey (TKey key);
    bool TryGetValue (TKey key, out TValue value);
    void Add    (TKey key, TValue value);
    bool Remove (TKey key);

    TValue this [TKey key]        { get; set; }   // 키에 의한 주 인덱서
    ICollection<TKey>   Keys      { get; }
    ICollection<TValue> Values    { get; }
}
```

읽기 전용 부분집합을 정의하는 `IReadOnlyDictionary<TKey,TValue>`도 있다.

항목을 넣는 방법은 둘이다. `Add`를 부르거나 인덱서의 set 접근자를 쓴다. **후자는 키가 없으면 추가하고 있으면 갱신한다.** 모든 딕셔너리 구현에서 중복 키는 금지이므로 같은 키로 `Add`를 두 번 부르면 예외가 난다.

꺼내는 방법도 둘이다. 인덱서와 `TryGetValue`다. **키가 없으면 인덱서는 예외를 던지고 `TryGetValue`는 `false`를 반환한다.** `ContainsKey`로 미리 검사할 수도 있지만, 그렇게 하면 조회를 두 번 하는 비용을 치른다.

```csharp
var d = new Dictionary<string, int>();
d.Add ("One", 1);
d["Two"] = 2;                              // "Two"가 없으므로 추가
d["Two"] = 22;                             // "Two"가 있으므로 갱신

Console.WriteLine (d["Two"]);              // 22
Console.WriteLine (d.ContainsKey ("One")); // true  (빠르다)
Console.WriteLine (d.ContainsValue (3));   // false (느리다 — 전체 순회)
if (!d.TryGetValue ("onE", out int val))
    Console.WriteLine ("No val");          // 대소문자를 구분한다
```

> **⚠️ `ContainsKey` 뒤에 인덱서를 쓰는 것은 조회 두 번이다**
>
> ```csharp
> if (d.ContainsKey (k))      // 조회 1
>     Process (d[k]);         // 조회 2
> ```
>
> 해시 계산과 버킷 탐색을 두 번 한다. 문자열 키라면 해시 계산 자체가 문자열 길이에 비례하므로 무시할 비용이 아니다. 올바른 형태는 하나다.
>
> ```csharp
> if (d.TryGetValue (k, out var v))
>     Process (v);
> ```
>
> 같은 이유로 "없으면 추가" 패턴도 `TryGetValue` → `Add` 조합보다는 `CollectionsMarshal.GetValueRefOrAddDefault`(※.NET 6)가 조회 한 번으로 끝난다. 다만 이 API는 `ref` 반환을 다루므로 뜨거운 경로에서만 쓴다(68.12절).

딕셔너리를 직접 열거하면 `KeyValuePair` 구조체의 시퀀스가 나온다.

```csharp
public readonly struct KeyValuePair<TKey, TValue>
{
    public TKey   Key   { get; }
    public TValue Value { get; }
    public void Deconstruct (out TKey key, out TValue value);
}
```

`Deconstruct`가 있으므로 분해 구문을 쓸 수 있다(77장).

```csharp
foreach (var (key, value) in d)
    Console.WriteLine ($"{key}: {value}");
```

`Keys` / `Values` 프로퍼티로 키만 또는 값만 열거할 수도 있다.

> **📌 비제네릭 `IDictionary`는 두 군데가 다르다**
>
> 레거시 코드(BCL 내부에도 있다)에 등장하는 비제네릭 `IDictionary`는 두 가지가 다르다.
>
> 1. **존재하지 않는 키를 인덱서로 조회하면 예외가 아니라 `null`을 반환한다.**
> 2. 멤버십 검사가 `ContainsKey`가 아니라 `Contains`다.
>
> 그리고 열거하면 `KeyValuePair`가 아니라 `DictionaryEntry` 구조체가 나온다. `DictionaryEntry`의 `Key`와 `Value`는 `object`이고 **setter가 있다**. 제네릭 쪽은 읽기 전용이다.

### 내부 구조 — 버킷 배열 + 엔트리 배열

`Dictionary<TKey,TValue>`는 배열 두 개로 만들어진다.

```csharp
private int[]     _buckets;   // 각 버킷 → 체인의 첫 엔트리 인덱스 + 1 (0 = 비어 있음)
private Entry[]   _entries;   // 실제 데이터, 삽입 순서대로 채워진다
private int       _count;     // _entries에서 사용된 슬롯 수
private int       _freeList;  // 삭제로 생긴 빈 슬롯 체인의 머리
private int       _freeCount; // 빈 슬롯 개수
private IEqualityComparer<TKey> _comparer;

private struct Entry
{
    public uint   hashCode;   // 키의 해시코드 (재계산을 피하려고 저장)
    public int    next;       // 같은 버킷의 다음 엔트리 인덱스 (-1 = 체인 끝)
    public TKey   key;
    public TValue value;
}
```

핵심은 **버킷이 값을 담지 않는다**는 것이다. 버킷은 엔트리 배열의 인덱스를 담을 뿐이고, 같은 버킷에 떨어진 키들은 엔트리 배열 안에서 `next` 인덱스로 엮인 **체인**을 이룬다. 이것이 체이닝(chaining) 방식의 충돌 해결이며, 노드 객체를 따로 할당하지 않고 배열 인덱스로 링크를 표현한다는 점이 .NET 구현의 특징이다.

```text
  d["Two"] = 22;  를 조회하는 과정

  ① 해시 계산                      "Two".GetHashCode()  →  0x8A3F91C2
                                                            │
  ② 버킷 인덱스                     hash % _buckets.Length  →  2
                                                            │
                     ┌──────────────────────────────────────┘
                     ↓
  _buckets (int[7])                       _entries (Entry[7])
  ┌───┬──────────────┐                    ┌───┬──────────┬──────┬───────┬───────┐
  │ 0 │      0       │ (비어 있음)         │idx│ hashCode │ next │ key   │ value │
  ├───┼──────────────┤                    ├───┼──────────┼──────┼───────┼───────┤
  │ 1 │      3       │────────────┐       │ 0 │ 0x51C0.. │  -1  │ "One" │   1   │
  ├───┼──────────────┤            │       ├───┼──────────┼──────┼───────┼───────┤
  │ 2 │      1       │──────┐     │       │ 1 │ 0x8A3F.. │  2   │ "Two" │  22   │◀─┐
  ├───┼──────────────┤      │     │       ├───┼──────────┼──────┼───────┼───────┤  │
  │ 3 │      0       │      │     │       │ 2 │ 0x1D77.. │  -1  │ "Six" │   6   │◀─┼ 충돌!
  ├───┼──────────────┤      │     │       ├───┼──────────┼──────┼───────┼───────┤  │ 같은 버킷 2
  │ 4 │      0       │      │     │       │ 3 │ 0x0BE4.. │  -1  │"Three"│   3   │  │
  ├───┼──────────────┤      │     │       ├───┼──────────┼──────┼───────┼───────┤  │
  │ 5 │      0       │      │     │       │ 4 │  (미사용) │      │       │       │  │
  ├───┼──────────────┤      │     │       └───┴──────────┴──────┴───────┴───────┘  │
  │ 6 │      0       │      │     │                                                │
  └───┴──────────────┘      └─────┼────────────────────────────────────────────────┘
                                  └──▶ 버킷 1 → 엔트리 3 ("Three"), next = -1 → 체인 끝

  ③ 체인 순회:  엔트리 1 → hashCode 일치? → key.Equals("Two")? → 일치! → value 반환
                (불일치면 next(=2)로 이동, next == -1이면 "없음")
```

주의할 점 셋.

- **`_buckets`에는 인덱스 + 1이 저장된다.** `int`의 기본값 0을 "비어 있음"으로 쓰기 위해서다. 실제 코드에서는 `_buckets[i] - 1`로 되돌린다. 위 그림의 화살표는 이미 보정된 값을 가리킨다.
- **`hashCode`를 엔트리에 저장한다.** 체인을 따라가며 비교할 때 먼저 정수 하나만 비교하면 대부분의 후보가 걸러진다. `Equals` 호출은 해시가 일치할 때만 한다. 리사이즈할 때도 해시를 다시 계산하지 않아도 된다.
- **엔트리 배열은 삽입 순서대로 채워진다.** 그래서 삭제가 없는 딕셔너리를 열거하면 삽입 순서로 나오는 것처럼 보인다. 하지만 이것은 **구현 세부이지 보장이 아니다.**

### 삽입·삭제·리사이즈

**삽입.** 해시를 계산해 버킷을 찾고, 체인을 따라가며 같은 키가 있는지 확인한다. 없으면 새 엔트리를 `_entries`의 다음 빈 슬롯(또는 free list의 머리)에 쓰고, 그 엔트리의 `next`를 기존 버킷 값으로 설정한 뒤 버킷이 새 엔트리를 가리키게 한다. 즉 **체인의 맨 앞에 삽입한다** — O(1)이다.

**삭제.** 체인에서 엔트리를 떼어 내고, 그 슬롯을 `_freeList`에 연결한다. 슬롯은 재사용된다. 배열이 줄지는 않는다.

**리사이즈.** `_entries`가 꽉 차면 용량을 대략 2배로 늘리되 **소수(prime number)** 로 맞춘다. 그다음 모든 엔트리를 새 버킷 배열에 재분배한다(rehash). 저장해 둔 `hashCode` 덕분에 키의 `GetHashCode`를 다시 부르지는 않는다.

> **📌 왜 소수인가**
>
> 버킷 인덱스를 `hash % bucketCount`로 구하는데, `bucketCount`가 2의 거듭제곱이면 해시의 하위 비트만 사용된다. 해시 함수가 하위 비트에 편향이 있으면(흔하다) 버킷 분포가 무너진다. 소수를 쓰면 해시의 모든 비트가 결과에 기여한다.
>
> 대가는 나눗셈 연산이다. 정수 나눗셈은 CPU에서 가장 느린 산술 명령 중 하나다. 그래서 ※.NET Core 3.0부터는 소수를 유지하면서도 나눗셈을 곱셈과 시프트로 대체하는 "빠른 모듈로" 기법을 64비트에서 사용한다.

> **⚠️ 딕셔너리의 열거 순서는 정의되지 않는다**
>
> 삽입 순서로 나오는 것처럼 보여도, 삭제가 일어나면 free list 재사용 때문에 순서가 뒤섞인다. 리사이즈가 일어나도 바뀔 수 있다. 런타임 버전이 바뀌면 또 달라질 수 있다.
>
> **딕셔너리의 열거 순서에 의존하는 코드는 언젠가 반드시 깨진다.** 순서가 필요하면 `SortedDictionary`, `SortedList`, 또는 삽입 순서를 유지하는 `OrderedDictionary`를 쓴다(24.8절).

### `GetHashCode` 품질이 만드는 차이

딕셔너리는 어떤 타입이든 키로 쓸 수 있다. 두 가지만 되면 된다. **키끼리 동등한지 판정**할 수 있고, **해시코드를 얻을** 수 있으면 된다. 기본적으로 동등성은 키의 `object.Equals`로, 해시코드는 `GetHashCode`로 판정한다. 이 동작은 재정의하거나 `IEqualityComparer`를 넘겨 바꾼다(24.13절).

좋은 해시 함수는 **유일한 해시코드를 만들려고 애쓰지 않는다**(대개 불가능하다). 대신 **32비트 정수 공간에 고르게 퍼진 해시코드**를 반환하려 애쓴다. 몇 개의 매우 큰(그래서 비효율적인) 버킷이 생기는 상황을 피하기 위해서다.

해시 품질이 나빠지면 무슨 일이 생기는지 극단적으로 보면 이렇다.

```csharp
class BadKey
{
    public int Id;
    public override int GetHashCode() => 0;                 // 최악: 전부 같은 버킷
    public override bool Equals (object o) => o is BadKey b && b.Id == Id;
}
```

| 해시 품질 | 버킷 분포 | `TryGetValue` 비용 |
|---|---|---|
| 이상적 (균등) | 버킷당 평균 1개 미만 | O(1) — 정수 비교 1~2회 |
| 보통 (약간 편향) | 버킷당 평균 2~3개 | O(1)이지만 상수가 2~3배 |
| 나쁨 (충돌 다수) | 몇 개 버킷에 수백 개 | 사실상 O(N) |
| 최악 (`=> 0`) | 버킷 하나에 전부 | **O(N) — 연결 리스트 선형 탐색** |

즉 `GetHashCode`를 잘못 구현하면 딕셔너리가 조용히 연결 리스트로 퇴화한다. 예외도 경고도 없고, 데이터가 늘어날수록 느려질 뿐이다. **프로덕션에서 "왜 갑자기 느려졌지"의 흔한 원인 중 하나다.**

> **⚠️ 문자열 키의 해시 무작위화 전환**
>
> 문자열 키에 대해 .NET은 기본적으로 빠른 비무작위화 해시를 쓴다. 그런데 한 버킷의 체인이 지나치게 길어지면(런타임 내부 임계값 기준) **런타임이 무작위화된 해시 함수로 전환하고 딕셔너리 전체를 재해싱한다.**
>
> 목적은 해시 DoS 공격 방어다. 공격자가 의도적으로 충돌하는 키(예: HTTP 헤더 이름, JSON 프로퍼티 이름)를 대량으로 보내 서버 딕셔너리를 O(N²)로 만드는 공격이 존재한다.
>
> 실무적 함의는 둘이다. 첫째, **외부 입력을 딕셔너리 키로 쓸 때 기본 문자열 비교자를 신뢰해도 된다**. 둘째, `StringComparer.Ordinal`을 명시적으로 넘기면 이 방어가 적용되는 경로가 달라질 수 있으므로, 신뢰할 수 없는 입력에는 성능 최적화 목적의 비교자 교체를 신중히 하라.

### 용량 미리 잡기

`List<T>`와 마찬가지로 예상 크기를 생성자에 넘기면 리사이즈와 재해싱을 줄일 수 있다.

```csharp
var d = new Dictionary<string, int> (capacity: 10_000);
// 또는
d.EnsureCapacity (10_000);       // ※.NET Core 2.1
d.TrimExcess();                  // 다 채운 뒤 축소
```

리사이즈는 배열 두 개를 새로 할당하고 모든 엔트리를 재분배하므로 `List<T>`의 리사이즈보다 비싸다.

> **💡 키 타입을 고를 때**
>
> - **`int` 키가 가장 빠르다.** `int.GetHashCode()`는 자기 자신을 반환하고, 비교는 정수 비교 하나다. 값 타입이므로 제네릭 인스턴스화가 특수화되어 인터페이스 디스패치도 없다(23.11절).
> - **`string` 키는 매우 흔하고 충분히 빠르다.** 해시 계산이 길이에 비례하므로 아주 긴 키는 비싸진다.
> - **구조체 키는 `IEquatable<T>`를 반드시 구현하라.** 그러지 않으면 `EqualityComparer<T>.Default`가 `ValueType.Equals`의 리플렉션 기반 경로로 떨어져 극적으로 느려지고 박싱까지 발생한다(25.5절).
> - **가변 객체를 키로 쓰지 마라.** 딕셔너리에 넣은 뒤 해시에 영향을 주는 필드를 바꾸면 그 항목은 영원히 찾을 수 없게 된다. 이 함정은 25.8절에서 자세히 다룬다.

## 24.8 `SortedDictionary`, `Lookup`, `OrderedDictionary`

### 정렬 딕셔너리 두 개

BCL에는 내용이 항상 키로 정렬되어 있는 딕셔너리 클래스가 둘 있다. 이 절에서는 `<TKey,TValue>`를 `<,>`로 줄여 쓴다.

- `SortedDictionary<,>`는 **레드/블랙 트리**를 쓴다. 어떤 삽입·조회 시나리오에서도 일관되게 잘 동작하도록 설계된 자료구조다.
- `SortedList<,>`는 **정렬된 배열 쌍**으로 구현된다. 이진 탐색으로 빠르게 조회하지만 삽입은 느리다(새 항목 자리를 만들려고 기존 값을 밀어야 한다).

무작위 순서로 요소를 삽입할 때는 `SortedDictionary<,>`가 `SortedList<,>`보다 훨씬 빠르다(특히 큰 컬렉션에서). 대신 `SortedList<,>`에는 능력이 하나 더 있다. **키뿐 아니라 인덱스로도 항목에 접근한다.** 정렬 순서상 n번째 요소로 바로 갈 수 있다(`Keys`/`Values` 프로퍼티의 인덱서를 통해). `SortedDictionary<,>`로 같은 일을 하려면 n개를 직접 열거해야 한다.

셋 중 어느 것도 중복 키를 허용하지 않는다(모든 딕셔너리가 그렇다).

원천 도서에 실린 딕셔너리 클래스 비교표다. 성능 수치는 **1.5GHz PC에서 정수 키/값 딕셔너리에 5만 회 연산을 수행한 밀리초 값**이며, 절대치가 아니라 **비율을 보기 위한 것**이다.

| 타입 | 내부 구조 | 인덱스 조회 | 항목당 메모리(평균 바이트) | 무작위 삽입 |
|---|---|---|---|---|
| `Dictionary<K,V>` | 해시테이블 | X | 22 | 30 |
| `Hashtable` | 해시테이블 | X | 38 | 50 |
| `ListDictionary` | 연결 리스트 | X | 36 | 50,000 |
| `OrderedDictionary` | 해시테이블 + 배열 | O | 59 | 70 |
| `SortedDictionary<K,V>` | 레드/블랙 트리 | X | 20 | 130 |
| `SortedList<K,V>` | 배열 2개 | O | 2 | 3,300 |
| `SortedList` | 배열 2개 | O | 27 | 4,500 |

제네릭과 비제네릭 사이의 차이는 대부분 박싱에서 온다. 값 타입 요소에서만 드러난다.

Big-O로 요약하면 키에 의한 조회 시간은 이렇다.

- `Hashtable`, `Dictionary`, `OrderedDictionary` — **O(1)**
- `SortedDictionary`, `SortedList` — **O(log N)**
- `ListDictionary`(및 `List<T>` 같은 비딕셔너리 타입) — **O(N)**

```csharp
// System.Reflection의 MethodInfo를 이름으로 정렬해 담는다
var sorted = new SortedList<string, MethodInfo>();
foreach (MethodInfo m in typeof (object).GetMethods())
    sorted [m.Name] = m;

foreach (string name in sorted.Keys)
    Console.WriteLine (name);
// Equals / GetHashCode / GetType / ReferenceEquals / ToString
```

> **⚠️ 위 코드가 `Add`였다면 예외가 났다**
>
> `object` 클래스는 `Equals`를 오버로드한다. 즉 이름이 같은 메서드가 둘 있다. `Add`를 썼다면 중복 키로 예외가 났을 것이다. **인덱서를 썼기 때문에** 뒤 항목이 앞 항목을 덮어써서 오류를 피했다.
>
> 같은 키에 여러 값을 담아야 한다면 값 자체를 리스트로 만든다.
>
> ```csharp
> SortedList<string, List<MethodInfo>> multi;
> ```
>
> 또는 다음에 볼 `Lookup<,>`을 쓴다.

`SortedList<,>`만 되는 것이 인덱스 접근이다.

```csharp
Console.WriteLine (sorted.Keys   [sorted.Count - 1]);              // ToString
Console.WriteLine (sorted.Values [sorted.Count - 1].IsVirtual);    // True
```

### `Lookup<TKey,TElement>`와 `ILookup<TKey,TElement>`

`Dictionary`가 "키 하나에 값 하나"라면 `Lookup`은 "키 하나에 값 **여럿**"이다. `System.Linq` 네임스페이스에 있고, 계약은 이렇다.

```csharp
public interface ILookup<TKey, TElement> : IEnumerable<IGrouping<TKey, TElement>>, IEnumerable
{
    int Count { get; }
    bool Contains (TKey key);
    IEnumerable<TElement> this [TKey key] { get; }
}
```

인스턴스는 직접 만들지 않고 LINQ의 `ToLookup` 연산자로 만든다(30.8절).

```csharp
string[] words = { "apple", "avocado", "banana", "blueberry", "cherry" };
ILookup<char, string> byFirstLetter = words.ToLookup (w => w[0]);

foreach (string s in byFirstLetter['b']) Console.WriteLine (s);  // banana, blueberry
Console.WriteLine (byFirstLetter['z'].Count());                  // 0 — 예외가 아니다
```

| | `Dictionary<K,V>` | `Lookup<K,V>` |
|---|---|---|
| 키당 값 | 1개 | 0개 이상 |
| 없는 키 조회 | `KeyNotFoundException` | **빈 시퀀스** |
| 수정 | 가능 | **불가능** (생성 후 읽기 전용) |
| 생성 방법 | `new` 또는 `ToDictionary` | `ToLookup`만 |
| 열거 단위 | `KeyValuePair<K,V>` | `IGrouping<K,V>` |

> **💡 "없는 키에 빈 결과"가 코드를 줄인다**
>
> 그룹핑 결과를 조회하는 코드에서 `Dictionary<K, List<V>>`를 쓰면 매번 `TryGetValue`로 방어해야 한다. `Lookup`은 없는 키에 빈 시퀀스를 돌려주므로 그 방어가 통째로 사라진다. 읽기 전용이라는 제약이 받아들일 만하다면 그룹 조회 테이블의 기본 선택지다.

### `OrderedDictionary`

`OrderedDictionary`는 **추가된 순서를 유지하는** 비제네릭 딕셔너리다(`System.Collections.Specialized`). 인덱스로도 키로도 접근할 수 있다.

**정렬 딕셔너리가 아니다.** 키 순서가 아니라 **삽입 순서**를 유지한다.

내부적으로 `Hashtable`과 `ArrayList`의 조합이다. `Hashtable`의 기능 전부에 `RemoveAt`과 정수 인덱서가 더해진 형태이고, `Keys`/`Values` 프로퍼티도 원래 순서로 요소를 돌려준다.

> **📌 제네릭 `OrderedDictionary<TKey,TValue>` ※.NET 9**
>
> `OrderedDictionary`는 .NET 2.0에 들어왔지만 오랫동안 제네릭 버전이 없었다. .NET 9에서 `System.Collections.Generic.OrderedDictionary<TKey,TValue>`가 추가되어 이 공백이 메워졌다. 그 이전 버전을 대상으로 한다면 `Dictionary<K,V>` + `List<K>` 조합을 직접 만들거나 `KeyedCollection<,>`을 쓴다(24.9절).

### 레거시 특수 딕셔너리

`System.Collections.Specialized`에는 오래된 특수 목적 딕셔너리가 더 있다. 전부 비제네릭이다.

| 타입 | 내부 | 존재 이유 | 현재 권고 |
|---|---|---|---|
| `ListDictionary` | 단일 연결 리스트 | 항목이 10개 미만일 때 메모리 효율 | `Dictionary` 사용 |
| `HybridDictionary` | 작으면 `ListDictionary`, 커지면 `Hashtable` | 두 마리 토끼 | `Dictionary` 사용 |
| `StringDictionary` | 해시테이블 | 문자열 전용 | `Dictionary<string,string>` 사용 |
| `NameValueCollection` | 해시테이블 + 배열 | 키당 다중 값, HTTP 쿼리 문자열 | 여전히 웹 API에서 등장 |

`ListDictionary`는 항목이 많아지면 극도로 느려진다(위 표의 50,000ms를 보라). `HybridDictionary`의 전환 비용을 감안하면, `Dictionary`가 어느 쪽 시나리오에서도 지나치게 무겁거나 느리지 않으므로 처음부터 `Dictionary`를 쓴다고 부당하게 손해 보지 않는다.

## 24.9 사용자 정의 컬렉션과 프록시 — `Collection<T>`, `KeyedCollection<T>`

### 왜 감싸는가

지금까지 본 컬렉션 클래스는 바로 인스턴스화할 수 있어서 편리하지만, **항목이 추가되거나 제거될 때 무슨 일이 일어날지 통제할 수 없다.** 애플리케이션에서 강타입 컬렉션을 쓸 때 이 통제가 필요한 경우가 있다.

- 항목이 추가·제거될 때 이벤트를 발생시키고 싶다
- 추가·제거에 따라 다른 프로퍼티를 갱신하고 싶다
- "불법" 추가·제거를 감지해 예외를 던지고 싶다(비즈니스 규칙 위반 등)

BCL은 이 목적을 위해 `System.Collections.ObjectModel` 네임스페이스에 컬렉션 클래스를 둔다. 본질적으로 **프록시(래퍼)** 다. `IList<T>`나 `IDictionary<,>`를 구현하되 메서드를 내부 컬렉션으로 전달하고, 각 `Add`·`Remove`·`Clear` 연산이 재정의 가능한 **가상 메서드**를 통과하게 만든다.

### `Collection<T>`

`Collection<T>`는 `List<T>`를 감싼 커스터마이즈 가능한 래퍼다. `IList<T>`와 `IList`를 구현하는 데 더해 가상 메서드 넷과 보호 프로퍼티 하나를 정의한다.

```csharp
public class Collection<T> :
    IList<T>, ICollection<T>, IEnumerable<T>, IList, ICollection, IEnumerable
{
    // ...
    protected virtual void ClearItems();
    protected virtual void InsertItem (int index, T item);
    protected virtual void RemoveItem (int index);
    protected virtual void SetItem    (int index, T item);

    protected IList<T> Items { get; }
}
```

가상 메서드가 리스트의 정상 동작에 개입하는 **관문**이다. `Items` 프로퍼티는 "내부 리스트"에 직접 접근하게 해 준다 — 가상 메서드를 발동시키지 않고 내부적으로 변경할 때 쓴다.

가상 메서드를 재정의하지 않으면 `Collection<T>`는 그냥 `List<T>`처럼 동작한다.

```csharp
public class AnimalCollection : Collection<Animal>
{
    // 이대로도 완전히 동작하는 Animal 리스트다. 추가 코드가 필요 없다.
}
```

이제 각 `Animal`이 자신이 속한 `Zoo`를 참조하도록 만들고, 그 프로퍼티를 자동으로 유지하게 하려면 넷을 다 재정의한다.

```csharp
public class AnimalCollection : Collection<Animal>
{
    Zoo zoo;
    public AnimalCollection (Zoo zoo) { this.zoo = zoo; }

    protected override void InsertItem (int index, Animal item)
    {
        base.InsertItem (index, item);
        item.Zoo = zoo;
    }
    protected override void SetItem (int index, Animal item)
    {
        base.SetItem (index, item);
        item.Zoo = zoo;
    }
    protected override void RemoveItem (int index)
    {
        this [index].Zoo = null;
        base.RemoveItem (index);
    }
    protected override void ClearItems()
    {
        foreach (Animal a in this) a.Zoo = null;
        base.ClearItems();
    }
}

public class Zoo
{
    public readonly AnimalCollection Animals;
    public Zoo() { Animals = new AnimalCollection (this); }
}
```

> **⚠️ 관문은 넷이다. 하나라도 빠지면 구멍이 난다**
>
> `Add`만 재정의하면 될 것 같지만 `Add`는 가상이 아니다. `Add`, `Insert`, `AddRange`가 전부 `InsertItem`으로 흘러 들어오고, 인덱서 setter는 `SetItem`으로, `Remove`/`RemoveAt`은 `RemoveItem`으로, `Clear`는 `ClearItems`로 간다. **넷을 다 재정의해야 불변식이 지켜진다.** 셋만 하면 나머지 한 경로로 규칙을 우회하는 코드가 언젠가 나타난다.

> **📌 `Collection<T>`는 기존 리스트를 복사하지 않고 프록시한다**
>
> `Collection<T>`에는 기존 `IList<T>`를 받는 생성자가 있다. 다른 컬렉션 클래스와 달리 **넘긴 리스트는 복사되지 않고 프록시된다.** 즉 원본 리스트의 이후 변경이 래퍼에 그대로 보인다(단, 이 경우 가상 메서드는 발동하지 않는다). 반대로 `Collection<T>`를 통한 변경은 원본 리스트를 바꾼다.

### `KeyedCollection<TKey,TItem>`

`KeyedCollection<TKey,TItem>`은 `Collection<TItem>`을 상속하면서 기능을 더하고 빼는 클래스다.

- **더하는 것**: 딕셔너리처럼 **키로 항목에 접근**하는 능력
- **빼는 것**: 자체 내부 리스트를 프록시하는 능력

`OrderedDictionary`와 닮았지만 `IDictionary`를 구현하지 않고 키/값 쌍이라는 개념도 없다. **키는 항목 자체에서 얻는다** — 추상 메서드 `GetKeyForItem`을 통해서다. 그래서 열거하면 평범한 리스트처럼 항목이 나온다.

**`KeyedCollection<TKey,TItem>` = `Collection<TItem>` + 키에 의한 빠른 조회**로 생각하면 정확하다.

```csharp
public abstract class KeyedCollection<TKey, TItem> : Collection<TItem>
{
    // ...
    protected abstract TKey GetKeyForItem (TItem item);
    protected void ChangeItemKey (TItem item, TKey newKey);

    // 인덱스에 의한 조회에 더해 키에 의한 빠른 조회
    public TItem this[TKey key] { get; }

    protected IDictionary<TKey, TItem> Dictionary { get; }
}
```

`GetKeyForItem`을 재정의해 항목에서 키를 뽑아낸다. **항목의 키 프로퍼티가 바뀌면 `ChangeItemKey`를 호출해야** 내부 딕셔너리가 갱신된다.

```csharp
public class AnimalCollection : KeyedCollection<string, Animal>
{
    Zoo zoo;
    public AnimalCollection (Zoo zoo) { this.zoo = zoo; }

    internal void NotifyNameChange (Animal a, string newName) =>
        this.ChangeItemKey (a, newName);

    protected override string GetKeyForItem (Animal item) => item.Name;

    // InsertItem / SetItem / RemoveItem / ClearItems는 앞 예제와 동일하게 구현
}
```

`Animal.Name`의 setter가 `Zoo.Animals.NotifyNameChange(this, value)`를 부르게 해 두면 이름을 바꿔도 조회가 유지된다.

```csharp
Zoo zoo = new Zoo();
zoo.Animals.Add (new Animal ("Kangaroo", 10));
zoo.Animals.Add (new Animal ("Mr Sea Lion", 20));

Console.WriteLine (zoo.Animals [0].Popularity);              // 10
Console.WriteLine (zoo.Animals ["Mr Sea Lion"].Popularity);  // 20
zoo.Animals ["Kangaroo"].Name = "Mr Roo";
Console.WriteLine (zoo.Animals ["Mr Roo"].Popularity);       // 10
```

> **📌 내부 딕셔너리 생성 임계값**
>
> `Dictionary` 프로퍼티는 조회에 쓰이는 내부 딕셔너리를 반환하며, 첫 항목이 추가될 때 생성된다. 생성자에 **생성 임계값**을 지정하면 항목 수가 그 값에 도달할 때까지 딕셔너리 생성을 미룰 수 있다(그동안 키 조회는 선형 탐색으로 처리된다).
>
> 임계값을 지정하지 않는 편이 나은 이유가 하나 있다. 딕셔너리가 항상 유효하면 그 `Keys` 프로퍼티로 `ICollection<TKey>`를 얻어 공개 프로퍼티로 노출할 수 있다.

### `ObservableCollection<T>`

`System.Collections.ObjectModel`에는 변경 알림을 발생시키는 컬렉션도 있다.

| 타입 | 역할 |
|---|---|
| `ObservableCollection<T>` | 항목 추가·제거·전체 갱신 시 알림을 발생시키는 동적 데이터 컬렉션 |
| `ReadOnlyObservableCollection<T>` | 위의 읽기 전용 버전 |

`ObservableCollection<T>`로 작업하는 방식은 `List<T>`와 거의 같다. 같은 핵심 인터페이스를 구현하기 때문이다. 다른 점은 **`CollectionChanged` 이벤트**다. 새 항목이 삽입되거나, 기존 항목이 제거(또는 이동)되거나, 컬렉션 전체가 바뀔 때 발생한다.

이벤트의 델리게이트는 `NotifyCollectionChangedEventHandler`이고, 두 번째 인자 `NotifyCollectionChangedEventArgs`는 `OldItems`(변경 전 관련 항목)와 `NewItems`(변경에 관련된 새 항목)를 제공한다. 어떤 동작이 이벤트를 유발했는지는 `Action` 프로퍼티로 판별한다.

```csharp
public enum NotifyCollectionChangedAction
{
    Add = 0, Remove = 1, Replace = 2, Move = 3, Reset = 4,
}
```

```csharp
using System.Collections.ObjectModel;
using System.Collections.Specialized;

ObservableCollection<Person> people = new() { new Person ("Peter"), new Person ("Kevin") };

people.CollectionChanged += (sender, e) =>
{
    Console.WriteLine ($"이 이벤트를 유발한 동작: {e.Action}");
    if (e.Action == NotifyCollectionChangedAction.Remove)
        foreach (Person p in e.OldItems) Console.WriteLine (p);
    if (e.Action == NotifyCollectionChangedAction.Add)
        foreach (Person p in e.NewItems) Console.WriteLine (p);
};
```

> **⚠️ `OldItems`와 `NewItems`는 `Action`에 따라 `null`이다**
>
> `Add`일 때 `OldItems`는 `null`이고, `Remove`일 때 `NewItems`가 `null`이다. `Reset`일 때는 **둘 다 `null`** 이며, 무엇이 바뀌었는지 알 방법이 없다 — 컬렉션 전체를 다시 읽어야 한다. `Action`을 확인하지 않고 `e.NewItems`를 순회하면 `NullReferenceException`이 난다.
>
> `Clear()`는 `Remove`가 아니라 `Reset`을 발생시킨다는 점도 자주 걸린다.

### 레거시 기반 클래스

`CollectionBase`는 `Collection<T>`의 비제네릭 버전이다. 템플릿 메서드 대신 `OnInsert`/`OnInsertComplete`, `OnSet`/`OnSetComplete`, `OnRemove`/`OnRemoveComplete`, `OnClear`/`OnClearComplete`라는 "훅" 메서드를 써서 필요한 메서드 수가 두 배가 되고, 비제네릭이므로 서브클래싱할 때 타입이 붙은 인덱서와 `Add`도 직접 구현해야 한다.

`DictionaryBase`는 `KeyedCollection`의 비제네릭 대응으로, `IDictionary`를 구현하고 같은 훅 방식을 쓴다(`OnGet`이 추가된다). `IDictionary`를 구현하는 방식의 유일한 장점은 키를 얻으려고 서브클래싱할 필요가 없다는 것인데, 이 클래스의 존재 목적 자체가 서브클래싱이므로 장점이 아니다. **둘 다 하위 호환용으로만 유용하다.**

## 24.10 읽기 전용·불변 컬렉션

### `ReadOnlyCollection<T>`가 왜 필요한가

클래스가 내부적으로는 갱신하면서 외부에는 읽기 전용 접근만 주고 싶다고 하자. 가장 쉬운 방법은 읽기 전용 인터페이스로 노출하는 것이다.

```csharp
public class Test
{
    List<string> names = new List<string>();
    public IReadOnlyList<string> Names => names;
}
```

문제는 `Names`가 **읽기 전용 인터페이스일 뿐 읽기 전용 객체가 아니라는** 데 있다. 소비자가 런타임에 `List<string>`이나 `IList<string>`으로 다운캐스트해서 `Add`, `Remove`, `Clear`를 호출할 수 있다.

`ReadOnlyCollection<T>`가 더 견고한 해법이다.

```csharp
public class Test
{
    List<string> names = new List<string>();
    public ReadOnlyCollection<string> Names { get; private set; }

    public Test() => Names = new ReadOnlyCollection<string> (names);
    public void AddInternally() => names.Add ("test");
}
```

```csharp
Test t = new Test();
t.AddInternally();
Console.WriteLine (t.Names.Count);          // 1
t.Names.Add ("test");                       // 컴파일 오류
((IList<string>) t.Names).Add ("test");     // NotSupportedException
```

딕셔너리에는 `ReadOnlyDictionary<TKey,TValue>`가 같은 역할을 한다. `List<T>`에는 `AsReadOnly()` 메서드가 있고, 최신 .NET에는 `System.Collections.Generic.CollectionExtensions`에 `IList<T>`와 `IDictionary<K,V>`용 `AsReadOnly()` 확장 메서드도 있다.

### `ReadOnlyCollection<T>`은 불변이 아니다

이것이 이 절에서 가장 중요한 문장이다. **읽기 전용은 불변이 아니다.** 이유가 셋이다.

1. **래퍼는 스냅샷이 아니다.** `ReadOnlyCollection<T>`는 생성자에서 받은 컬렉션을 **영구 참조로 유지한다.** 복사하지 않는다. 따라서 원본 컬렉션이 바뀌면 읽기 전용 래퍼를 통해 그 변화가 **보인다.** "보호된 뷰"이지 고정된 사진이 아니다.
2. **요소 자체는 여전히 가변이다.** `ReadOnlyCollection<Person>`이 담은 `Person` 객체의 프로퍼티는 얼마든지 바꿀 수 있다.
3. **다중 스레드에서 안전하지 않다.** 원본이 다른 스레드에서 수정되는 동안 래퍼를 열거하면 `InvalidOperationException`이 난다.

```csharp
var inner = new List<string> { "a" };
var view  = new ReadOnlyCollection<string> (inner);
inner.Add ("b");
Console.WriteLine (view.Count);      // 2 — 뷰가 원본의 변화를 반영한다
```

> **⚠️ `IsReadOnly`가 `true`라고 안심할 수 없다**
>
> `ICollection<T>.IsReadOnly`는 "이 **참조**를 통해 수정할 수 없다"는 뜻이지 "이 데이터가 변하지 않는다"는 뜻이 아니다. 진짜 불변성이 필요하면 불변 컬렉션을 쓴다.

### 불변 컬렉션

불변 컬렉션은 **초기화 이후 전혀 수정할 수 없는** 컬렉션이다. 항목을 추가해야 하면 새 컬렉션을 만들고, 원래 것은 손대지 않는다.

불변성의 이득은 셋이다. 상태 변화에 얽힌 버그 부류가 통째로 사라지고, 스레드 안전성 문제 대부분이 사라져 병렬화가 단순해지며, 코드를 추론하기 쉬워진다. 대가는 변경할 때마다 새 객체를 만들어야 한다는 것이다.

불변 컬렉션은 `System.Collections.Immutable` 네임스페이스에 있다(.NET Framework에서는 같은 이름의 NuGet 패키지로 제공된다).

| 타입 | 내부 구조 |
|---|---|
| `ImmutableArray<T>` | 배열 |
| `ImmutableList<T>` | AVL 트리 |
| `ImmutableDictionary<K,V>` | AVL 트리 |
| `ImmutableHashSet<T>` | AVL 트리 |
| `ImmutableSortedDictionary<K,V>` | AVL 트리 |
| `ImmutableSortedSet<T>` | AVL 트리 |
| `ImmutableStack<T>` | 연결 리스트 |
| `ImmutableQueue<T>` | 연결 리스트 |

생성은 각 타입의 정적 `Create<T>()` / `CreateRange<T>()` 또는 확장 메서드로 한다.

```csharp
ImmutableArray<int> array = ImmutableArray.Create<int> (1, 2, 3);
var list = new[] { 1, 2, 3 }.ToImmutableList();
```

`Add`는 원본을 바꾸지 않고 **새 컬렉션을 반환한다.** 이것을 **비파괴적 변경(nondestructive mutation)** 이라 부른다.

```csharp
var oldList = ImmutableList.Create<int> (1, 2, 3);
ImmutableList<int> newList = oldList.Add (4);

Console.WriteLine (oldList.Count);    // 3  (그대로)
Console.WriteLine (newList.Count);    // 4
```

이 방식으로 반복해서 추가·제거하면 매번 새 컬렉션이 생겨 비효율적이다. `AddRange` / `RemoveRange`로 한 번에 처리하거나 **빌더**를 쓴다. 빌더는 기능적으로 가변 컬렉션과 동등하고 성능 특성도 비슷하며, `ToImmutable()`로 굳힌다.

```csharp
ImmutableArray<int>.Builder builder = ImmutableArray.CreateBuilder<int>();
builder.Add (1);
builder.Add (2);
builder.RemoveAt (0);
ImmutableArray<int> result = builder.ToImmutable();

// 기존 불변 컬렉션에 여러 변경을 일괄 적용할 때
var builder2 = result.ToBuilder();
builder2.Add (4);                      // 효율적
builder2.Remove (2);                   // 효율적
ImmutableArray<int> result2 = builder2.ToImmutable();
```

### 구조 공유 — AVL 트리를 쓰는 이유

대부분의 불변 컬렉션이 내부적으로 AVL 트리를 쓴다. 덕분에 추가·제거 연산이 **원래 내부 구조의 일부를 재사용**할 수 있다. 전체를 처음부터 다시 만들지 않아도 된다.

루트에서 변경 지점까지의 경로에 있는 노드만 새로 만들고, 그 경로에 걸리지 않은 부분 트리는 **원본 노드를 그대로 가리킨다.** N개짜리 트리에서 경로 하나(약 log N개 노드)만 새로 만들면 나머지는 공유된다. 큰 컬렉션에서 "전체 복사"였을 비용이 "적당한" 비용으로 줄어든다. 대가는 **읽기가 느려진다**는 것이다 — 배열 인덱싱 대신 트리를 내려가야 한다.

결과적으로 대부분의 불변 컬렉션은 읽기와 쓰기 **양쪽에서** 가변 대응물보다 느리다.

| 타입 | 읽기 성능 | 추가 성능 |
|---|---|---|
| `ImmutableList<T>` | 느림 | 느림 |
| `ImmutableArray<T>` | 매우 빠름 | 매우 느림 |

`ImmutableList<T>`는 리스트 크기에 따라 읽기와 추가 모두 `List<T>`보다 **10~200배** 느리다. `ImmutableArray<T>`가 존재하는 이유가 이것이다. 내부에 배열을 쓰므로 읽기 오버헤드가 없다(일반 가변 배열과 비슷한 성능). 반대급부로 추가는 원래 구조를 전혀 재사용할 수 없어 `ImmutableList<T>`보다도 훨씬 느리다.

즉 **`ImmutableArray<T>`는 읽기 성능이 방해받지 않아야 하고 이후 `Add`/`Remove` 호출이 많지 않을 때** 바람직하다(빌더를 쓰지 않는 경우).

> **📌 비용을 균형 있게 보라**
>
> 100만 요소짜리 `ImmutableList`의 `Add` 연산도 일반적인 노트북에서 1마이크로초 미만, 읽기는 100나노초 미만이다. 게다가 세 가지가 비용을 상쇄한다.
>
> - 불변성은 병렬화를 쉽게 만든다(50장). 가변 상태를 병렬화하려면 락이나 동시성 컬렉션이 필요한데 둘 다 성능을 깎는다.
> - 예상 못 한 변경을 막으려는 **방어적 복사**가 필요 없어진다. 이것이 최근 Visual Studio 코드베이스에서 불변 컬렉션을 택한 이유 중 하나였다.
> - 대부분의 프로그램에서 차이가 문제될 만큼 항목이 많은 컬렉션은 몇 개 되지 않는다.
>
> Visual Studio와 Roslyn 툴체인이 불변 컬렉션으로 만들어졌다는 사실이 이 균형의 증거다.

> **⚠️ 불변 컬렉션은 요소의 변경을 막지 않는다**
>
> 불변 컬렉션은 항목의 추가·제거를 막을 뿐, **항목 자체가 변경되는 것은 막지 않는다.** 불변성의 이득을 온전히 얻으려면 불변 컬렉션에 **불변 항목만** 들어가게 해야 한다(19장).

> **⚠️ `ImmutableArray<T>`는 구조체다 — `default`가 폭탄이다**
>
> `ImmutableArray<T>`는 클래스가 아니라 **구조체**다. 내부 배열 참조 하나를 감싼 얇은 래퍼이므로 할당이 없다는 장점이 있지만, 초기화되지 않은 값이 `null`이 아니라 **내부 배열이 `null`인 구조체**가 된다.
>
> ```csharp
> ImmutableArray<int> arr = default;
> Console.WriteLine (arr.IsDefault);       // True
> Console.WriteLine (arr.Length);          // NullReferenceException
> ```
>
> 필드로 선언하고 초기화를 잊거나, `default!`로 널 경고를 눌러 놓으면 이 예외를 만난다. `IsDefault` / `IsDefaultOrEmpty`로 검사하거나 `ImmutableArray<T>.Empty`로 초기화하라.
>
> `ImmutableArray<T>.Remove`는 `List<T>.Remove`보다도 비싸다 — **첫 요소를 지우는 최선의 경우에도** 그렇다. 새 컬렉션 할당이 GC에 추가 부담을 주기 때문이다.

## 24.11 frozen 컬렉션 — `FrozenDictionary`, `FrozenSet` ※.NET 8

### 왜 또 하나의 읽기 전용 컬렉션인가

제네릭 컬렉션에는 설계에서 비롯된 성능 한계가 둘 있다.

**첫째, 제네릭이라서 최적화할 수 없다.** 키 타입이 무엇이든 될 수 있으므로 .NET 팀은 알고리즘을 특정 타입에 맞춰 다듬을 수 없다. 현실에서 가장 많이 쓰이는 것은 `string`과 `int`인데, 그 사실을 컴파일 타임에 알 방법이 없다.

**둘째, 컬렉션이 동적이다.** 언제든 항목이 추가·제거될 수 있으므로, "더 이상 변경이 없다"는 전제 위에서만 가능한 최적화를 할 수 없다.

관찰은 이렇다. **95%의 경우 컬렉션은 채워진 뒤 다시는 바뀌지 않는다.** 그렇다면 생성 시점에 시간을 좀 더 들여 최적화해 두고, 그 이후의 읽기를 크게 빠르게 만들 수 있다.

.NET 8이 `System.Collections.Frozen` 네임스페이스에 두 타입을 도입했다.

- `FrozenDictionary<TKey,TValue>`
- `FrozenSet<T>`

`ImmutableDictionary<K,V>`·`ImmutableHashSet<T>`와 비슷하지만, **비파괴적 변경 메서드(`Add`, `Remove` 등)가 아예 없다.** 그 대가로 읽기 성능을 극도로 최적화한다.

생성은 다른 컬렉션이나 시퀀스에서 확장 메서드로 한다.

```csharp
int[] numbers = { 10, 20, 30 };
FrozenSet<int> frozen = numbers.ToFrozenSet();
Console.WriteLine (frozen.Contains (10));      // True
```

`ToFrozenDictionary` / `ToFrozenSet`은 **생성 비용이 크다.** 키를 분석해 그 집합에 가장 잘 맞는 내부 구현을 고르기 때문이다(예: 항목이 아주 적을 때 전용 구현, 문자열 키의 길이나 특정 위치 문자만으로 구별 가능한지 판단 등). 앞에서 시간과 노력을 더 들이고, 그 뒤 읽기 성능을 크게 개선하는 거래다.

프로그램 시작 시 한 번 초기화하고 애플리케이션 수명 내내 조회에만 쓰는 룩업 테이블에 잘 맞는다.

```csharp
class Disassembler
{
    public readonly static IReadOnlyDictionary<string,string> OpCodeLookup =
        new Dictionary<string, string>()
        {
            { "ADC",  "Add with Carry" },
            { "ADD",  "Add" },
            { "AND",  "Logical AND" },
            { "ANDN", "Logical AND NOT" },
            // ...
        }
        .ToFrozenDictionary();
}
```

frozen 컬렉션은 표준 딕셔너리/집합 인터페이스를 읽기 전용 버전까지 포함해 구현한다. 위 예에서는 `FrozenDictionary<string,string>`을 `IReadOnlyDictionary<string,string>` 타입 필드로 노출했다.

### 세 가지 "변경 불가"의 비교

| | `ReadOnlyCollection<T>` | `Immutable*<T>` | `Frozen*<T>` |
|---|---|---|---|
| 원본 변경이 보이는가 | **보인다** (래퍼일 뿐) | 안 보인다 | 안 보인다 |
| `Add` 메서드 | 있다(호출하면 `NotSupportedException`) | 있다(**새 컬렉션 반환**) | **없다** |
| 생성 비용 | 매우 낮음 (래퍼 하나) | 보통 | **높음** (최적화 수행) |
| 읽기 성능 | 원본과 동일 | 가변보다 느림 | **가변보다 빠름** |
| 스레드 안전 | 원본에 달림 | 안전 | 안전 |
| 주 용도 | 내부 컬렉션의 보호된 뷰 | 함수형 스타일, 공유 상태 | **시작 시 1회 구축하는 룩업 테이블** |

`Add`를 불렀을 때 `List<T>`는 끝에 추가하고, `Dictionary<K,V>`는 내부 구조가 정하는 위치에 추가하며, `ReadOnlyCollection<T>`는 예외를 던지고, `ImmutableList<T>`는 새 컬렉션을 반환하며, `FrozenDictionary<K,V>`에는 **메서드 자체가 없다.**

> **⚠️ 뜨거운 경로에서 frozen 컬렉션을 반복 생성하지 마라**
>
> 생성 비용이 높다는 것이 이 타입의 전체 설계 전제다. 요청마다 `ToFrozenDictionary()`를 부르면 얻는 것보다 잃는 것이 훨씬 크다. **`static readonly` 필드로 한 번 만들어 두는 것**이 의도된 사용법이다.

## 24.12 동시성 컬렉션 — `ConcurrentDictionary`, `ConcurrentBag`, `BlockingCollection`

`System.Collections`와 `System.Collections.Generic`의 컬렉션은 **스레드 안전하지 않다.** 여러 스레드가 동시에 접근하면 예외가 나거나, 더 나쁘게는 조용히 내부 구조가 깨진다. 여러 스레드가 동시에 컬렉션에 접근한다면 `System.Collections.Concurrent`의 타입을 쓴다.

| 타입 | 역할 |
|---|---|
| `ConcurrentDictionary<TKey,TValue>` | 스레드 안전한 키/값 컬렉션 |
| `ConcurrentQueue<T>` | 스레드 안전한 FIFO |
| `ConcurrentStack<T>` | 스레드 안전한 LIFO |
| `ConcurrentBag<T>` | **순서가 없는** 스레드 안전 컬렉션 |
| `BlockingCollection<T>` | 위 컬렉션들에 **블로킹·용량 제한** 기능을 얹는 래퍼 |
| `IProducerConsumerCollection<T>` | 프로듀서/컨슈머 방식 조작의 기반 인터페이스 |
| `Partitioner`, `OrderablePartitioner<T>` | 데이터 소스를 여러 파티션으로 나누는 전략 (50.6절) |

`ConcurrentDictionary`가 가장 자주 쓰인다. 핵심 멤버는 조회·삽입을 원자적으로 묶은 것들이다.

```csharp
var cache = new ConcurrentDictionary<string, byte[]>();
byte[] data = cache.GetOrAdd (key, k => LoadFromDisk (k));   // 없으면 만들어 넣는다
cache.AddOrUpdate (key, k => Create (k), (k, old) => Merge (old));
if (cache.TryRemove (key, out var removed)) { /* ... */ }
```

> **⚠️ `GetOrAdd`의 팩토리는 두 번 이상 실행될 수 있다**
>
> `GetOrAdd(key, valueFactory)`의 팩토리 델리게이트는 **락 바깥에서** 호출된다. 두 스레드가 동시에 없는 키를 요청하면 팩토리가 두 번 실행되고, 그중 하나의 결과만 딕셔너리에 남는다. 반환값은 실제로 저장된 값이므로 "저장된 것과 다른 값을 받는" 일은 없다.
>
> 즉 **팩토리에 부수 효과(파일 생성, 커넥션 열기, 카운터 증가)를 넣으면 조용히 두 번 일어난다.** 값 생성이 비싸거나 부수 효과가 있으면 `Lazy<T>`를 값 타입으로 저장하는 관용구를 쓴다.
>
> ```csharp
> var cache = new ConcurrentDictionary<string, Lazy<byte[]>>();
> byte[] data = cache.GetOrAdd (key, k => new Lazy<byte[]>(() => LoadFromDisk (k))).Value;
> ```

> **⚠️ 개별 연산만 원자적이다**
>
> "스레드 안전"은 **각 메서드 호출이 원자적**이라는 뜻이다. 두 호출의 조합은 원자적이지 않다.
>
> ```csharp
> if (!dict.ContainsKey (k))       // 여기서 다른 스레드가 끼어들 수 있다
>     dict.TryAdd (k, v);
> ```
>
> 이 검사-후-실행 패턴은 동시성 컬렉션에서도 여전히 경합한다. `TryAdd`나 `GetOrAdd` 같은 **복합 원자 연산**을 써야 한다.
>
> `Count` 프로퍼티도 주의 대상이다. `ConcurrentDictionary`의 `Count`는 `Dictionary`처럼 필드 하나를 읽는 O(1) 연산이 아닐 수 있고, 읽는 순간에도 값이 변할 수 있다. 열거는 "특정 시점의 스냅샷"이 아니라 **약한 일관성**을 가진다 — 예외는 나지 않지만 열거 중 추가된 항목이 보일 수도, 안 보일 수도 있다.

`ConcurrentBag<T>`는 순서를 보장하지 않는 대신 **각 스레드가 자기 지역 저장소를 갖는** 구조라서, 한 스레드가 넣고 같은 스레드가 꺼내는 패턴에서 경합이 거의 없다. 반대로 한 스레드가 넣고 다른 스레드가 꺼내는 패턴에서는 훔쳐 오기(work stealing) 비용이 붙는다.

`BlockingCollection<T>`는 `IProducerConsumerCollection<T>`를 구현하는 컬렉션을 감싸 **블로킹과 용량 제한**을 제공한다. 컨슈머가 `Take()`를 부르면 항목이 생길 때까지 대기하고, 프로듀서는 큐가 가득 차면 `Add()`에서 대기한다. 프로듀서/컨슈머 큐의 표준 도구다.

> **💡 언제 동시성 컬렉션을 쓰지 말아야 하는가**
>
> 동시성 컬렉션은 공짜가 아니다. 단일 스레드에서 `ConcurrentDictionary`는 `Dictionary`보다 느리다. 그리고 대부분의 경합 문제는 컬렉션이 아니라 **불변식**의 문제다 — 두 컬렉션을 함께 갱신해야 한다면 동시성 컬렉션 둘로는 해결되지 않고 락이 필요하다.
>
> 스레드 안전성 보장 수준, `IProducerConsumerCollection<T>`의 계약, 프로듀서/컨슈머 큐 구현은 50.10절과 50.11절에서 자세히 다룬다. **확장 메서드와 명시적 인터페이스 구현은 스레드 안전이 보장되지 않는다**는 점도 거기서 다시 짚는다.

## 24.13 동등성·순서 비교자 꽂아넣기 (`IEqualityComparer`, `IComparer`)

### 왜 꽂아 넣는가

`Equals`와 `GetHashCode`가 의미 있는 값을 반환하는 타입은 `Dictionary`나 `Hashtable`의 키로 바로 쓸 수 있다. `IComparable` / `IComparable<T>`를 구현한 타입은 정렬 딕셔너리·리스트의 키로 바로 쓸 수 있다. 타입의 기본 동작이 원하는 것과 다를 때, .NET은 **플러그인 프로토콜**을 제공한다. 이 프로토콜이 두 가지를 해 준다.

1. 대체 동등·비교 동작으로 **바꿔 끼울** 수 있다.
2. 본질적으로 동등 비교나 순서 비교가 불가능한 키 타입도 **쓸 수 있게** 만든다.

| 인터페이스 | 역할 | 인식하는 컬렉션 |
|---|---|---|
| `IEqualityComparer<T>` / `IEqualityComparer` | 동등 비교 + 해싱 | `Dictionary`, `Hashtable`, `HashSet`, `ConcurrentDictionary`, frozen 컬렉션 |
| `IComparer<T>` / `IComparer` | 순서 비교 | `SortedDictionary`, `SortedList`, `SortedSet`, `Array.Sort`, `List<T>.Sort` |

**정렬 딕셔너리에 동등 비교자는 무용지물이고, 해시 딕셔너리에 순서 비교자는 무용지물이다.** 해시테이블 기반 컬렉션은 해시코드가 필요하고, 정렬 기반 컬렉션은 순서가 필요하다.

### `IEqualityComparer<T>`와 `EqualityComparer<T>`

```csharp
public interface IEqualityComparer<T>
{
    bool Equals (T x, T y);
    int  GetHashCode (T obj);
}
```

직접 구현하는 대신 추상 클래스 `EqualityComparer<T>`를 상속하면 비제네릭 버전까지 함께 얻는다.

```csharp
public class Customer                       // Equals를 재정의하지 않았다
{
    public string LastName, FirstName;
    public Customer (string last, string first) { LastName = last; FirstName = first; }
}

public class LastFirstEqComparer : EqualityComparer<Customer>
{
    public override bool Equals (Customer x, Customer y)
        => x.LastName == y.LastName && x.FirstName == y.FirstName;

    public override int GetHashCode (Customer obj)
        => (obj.LastName + ";" + obj.FirstName).GetHashCode();
}
```

`Customer`가 `object.Equals`를 재정의하지 않았으므로 기본 참조 동등성이 적용된다.

```csharp
Customer c1 = new Customer ("Bloggs", "Joe");
Customer c2 = new Customer ("Bloggs", "Joe");

var d1 = new Dictionary<Customer, string>();
d1 [c1] = "Joe";
Console.WriteLine (d1.ContainsKey (c2));      // False

var d2 = new Dictionary<Customer, string> (new LastFirstEqComparer());
d2 [c1] = "Joe";
Console.WriteLine (d2.ContainsKey (c2));      // True
```

`Equals`와 `GetHashCode`의 의미론은 `object.Equals` / `object.GetHashCode`의 규칙을 그대로 따른다. 이 **계약**은 25장에서 다룬다.

> **⚠️ 딕셔너리에 들어 있는 동안 키의 필드를 바꾸지 마라**
>
> 위 예에서 `Customer`가 딕셔너리에 있는 동안 `FirstName`이나 `LastName`을 바꾸면 해시코드가 달라진다. 그 항목은 잘못된 버킷에 남아 **영원히 찾을 수 없게 된다.** 딕셔너리가 조용히 망가진다(25.8절).

`EqualityComparer<T>.Default`는 범용 동등 비교자를 돌려준다. 정적 `object.Equals`의 대안으로 쓸 수 있고, **`T`가 `IEquatable<T>`를 구현하면 그쪽을 먼저 호출해 박싱을 피한다.** 제네릭 메서드에서 특히 유용하다.

```csharp
static bool Foo<T> (T x, T y) => EqualityComparer<T>.Default.Equals (x, y);
```

※.NET 5부터 `ReferenceEqualityComparer.Instance`는 항상 참조 동등성을 적용하는 비교자를 돌려준다. 값 타입에 대해서는 `Equals`가 언제나 `false`를 반환한다.

### `IComparer<T>`와 `Comparer<T>`

```csharp
public interface IComparer<in T> { int Compare (T x, T y); }
```

역시 추상 클래스 `Comparer<T>`를 상속하는 쪽이 편하다.

```csharp
class PriorityComparer : Comparer<Wish>
{
    public override int Compare (Wish x, Wish y)
    {
        if (object.Equals (x, y)) return 0;      // 최적화 겸 Equals와의 모순 방지
        if (x == null) return -1;
        if (y == null) return 1;
        return x.Priority.CompareTo (y.Priority);
    }
}

wishList.Sort (new PriorityComparer());
```

`object.Equals` 검사가 `Equals` 메서드와 모순되지 않도록 보장한다. 정적 `object.Equals`를 부르는 것이 `x.Equals`보다 나은 이유는 **`x`가 `null`이어도 동작하기 때문**이다.

### `StringComparer`

`StringComparer`는 문자열의 동등 비교와 순서 비교를 위해 미리 정의된 플러그인 클래스다. 언어와 대소문자 구분 여부를 지정할 수 있고, `IEqualityComparer`와 `IComparer`(및 제네릭 버전)를 **둘 다** 구현하므로 어떤 종류의 딕셔너리·정렬 컬렉션에도 쓸 수 있다.

추상 클래스이므로 정적 프로퍼티로 인스턴스를 얻는다.

| 멤버 | 의미 |
|---|---|
| `Ordinal` | 서수 비교. **문자열 동등 비교의 기본 동작과 같다** |
| `OrdinalIgnoreCase` | 서수 + 대소문자 무시 |
| `CurrentCulture` | 현재 문화권. **순서 비교의 기본 동작과 같다** |
| `CurrentCultureIgnoreCase` | 현재 문화권 + 대소문자 무시 |
| `InvariantCulture` / `InvariantCultureIgnoreCase` | 불변 문화권 |
| `Create (CultureInfo culture, bool ignoreCase)` | 임의 문화권으로 생성 |

```csharp
// dict["Joe"]와 dict["JOE"]가 같은 항목을 가리킨다
var dict = new Dictionary<string, int> (StringComparer.OrdinalIgnoreCase);

// 오스트레일리아 영어 규칙으로 정렬
string[] names = { "Tom", "HARRY", "sheila" };
Array.Sort<string> (names, StringComparer.Create (new CultureInfo ("en-AU"), false));
```

전화번호부식 성 정렬처럼 정규화가 필요하면 `StringComparer`를 감싼다. 아래 비교자를 `new SortedDictionary<string,string>(new SurnameComparer(...))`에 넘기면 `McDonald`, `MacPhail`, `MacWilliam` 순서로 열거된다.

```csharp
class SurnameComparer : Comparer<string>
{
    StringComparer strCmp;
    public SurnameComparer (CultureInfo ci) => strCmp = StringComparer.Create (ci, false);

    string Normalize (string s)
    {
        s = s.Trim();
        if (s.ToUpper().StartsWith ("MC")) s = "MAC" + s.Substring (2);
        return s;
    }

    public override int Compare (string x, string y)
        => strCmp.Compare (Normalize (x), Normalize (y));
}
```

### 구조적 비교

구조체는 기본적으로 구조적 비교를 한다 — 모든 필드가 같으면 두 구조체는 같다(25.5절). 배열 같은 다른 타입에도 이 방식을 **플러그인 옵션으로** 적용하고 싶을 때 두 인터페이스를 쓴다.

```csharp
public interface IStructuralEquatable
{
    bool Equals (object other, IEqualityComparer comparer);
    int  GetHashCode (IEqualityComparer comparer);
}

public interface IStructuralComparable
{
    int CompareTo (object other, IComparer comparer);
}
```

넘긴 비교자는 복합 객체의 **개별 요소마다** 적용된다.

```csharp
string[] a1 = "the quick brown fox".Split();
string[] a2 = "THE QUICK BROWN FOX".Split();
IStructuralEquatable se1 = a1;
bool isTrue = se1.Equals (a2, StringComparer.InvariantCultureIgnoreCase);   // True
```

> **💡 비교자는 컬렉션 생성 시점에 고정된다**
>
> 딕셔너리에 비교자를 넘기는 것은 생성자에서만 가능하다. 나중에 바꿀 수 없다. 그리고 `BinarySearch`나 `Sort`에 넘기는 비교자는 **컬렉션을 정렬할 때 쓴 것과 일관되어야** 한다. 일관되지 않으면 예외 없이 틀린 결과가 나온다(24.3절).

## 24.14 컬렉션 식과 스프레드 연산자 ※C# 12

### 하나의 문법으로 통일

C# 11까지는 배열·컬렉션·스팬을 초기화하는 문법이 제각각이었다.

```csharp
int[]      numbersArray11 = { 1, 3, 5 };
List<int>  numbersList11  = new() { 1, 3, 5 };
Span<int>  numbersSpan11  = stackalloc int[] { 1, 3, 5 };
```

C# 12부터는 대괄호 하나로 통일된다. 컴파일러가 대상 타입에 맞는 코드를 만들어 낸다.

```csharp
int[]     numbersArray12 = [ 1, 3, 5 ];
List<int> numbersList12  = [ 1, 3, 5 ];
Span<int> numbersSpan12  = [ 1, 3, 5 ];
```

배열 관점의 기본 문법은 9.2절에서 다뤘다. 여기서는 컬렉션 관점의 규칙을 정리한다.

**대상 타입이 될 수 있는 것**은 다음과 같다.

| 대상 타입 | 컴파일러가 만드는 것 |
|---|---|
| `T[]` | 배열 생성 + 요소 대입 |
| `Span<T>` / `ReadOnlySpan<T>` | 상황에 따라 스택 할당 또는 정적 데이터 참조 |
| `List<T>` 등 `IEnumerable`을 구현하고 `Add`를 가진 타입 | `new` + `Add` 반복 (컬렉션 초기화자와 같다) |
| `IEnumerable<T>`, `IReadOnlyCollection<T>`, `IReadOnlyList<T>`, `ICollection<T>`, `IList<T>` | 컴파일러가 적절한 구현을 선택한다 |
| `CollectionBuilderAttribute`가 붙은 타입 (`ImmutableArray<T>` 등) | 지정된 빌더 메서드 호출 |

`ImmutableArray<int> x = [1, 2, 3];`이 동작하는 이유가 마지막 줄이다. 타입에 `[CollectionBuilder(...)]`가 붙어 있으면 컴파일러가 그 팩토리를 호출한다. 사용자 정의 컬렉션도 이 특성을 붙이면 컬렉션 식의 대상이 될 수 있다.

### 스프레드 연산자 `..`

컬렉션 식 안에서 `..`은 다른 시퀀스를 **펼쳐 넣는다**.

```csharp
int[] head = [1, 2], tail = [5, 6];
int[] all  = [..head, 3, 4, ..tail];      // [1, 2, 3, 4, 5, 6]
int[] copy = [..all];                     // 얕은 복사
List<string> merged = [..listA, ..listB];
```

스프레드 요소는 `IEnumerable`이면 무엇이든 될 수 있다. 배열, 리스트, LINQ 쿼리 결과, 스팬 전부 가능하다.

> **⚠️ `..`은 범위 연산자가 아니다**
>
> 같은 토큰이 두 가지 뜻으로 쓰인다. **대괄호 안(컬렉션 식)에서는 스프레드**, **인덱서 안에서는 범위**다(9.3절).
>
> ```csharp
> int[] a = [1, 2, 3, 4, 5];
> int[] b = a[1..3];        // 범위 — { 2, 3 }
> int[] c = [..a];          // 스프레드 — { 1, 2, 3, 4, 5 }의 복사본
> int[] d = [..a[1..3]];    // 둘 다 — { 2, 3 }
> ```
>
> 문맥이 다르므로 컴파일러는 혼동하지 않지만, 사람은 혼동한다.

> **⚠️ 스프레드는 소스를 열거한다 — 비용이 있다**
>
> `[..query]`는 `query`를 **즉시 열거한다.** LINQ 쿼리를 넣으면 그 자리에서 실행된다(29.6절). 열거자를 두 번 돌 수 없는 시퀀스(예: `IAsyncEnumerable`이 아닌 스트림 래퍼)에는 조심해야 한다.
>
> 성능 면에서 컴파일러는 소스가 개수를 알 수 있는 타입(배열, `List<T>`)이면 목적지 크기를 미리 잡지만, 그렇지 않으면 중간 버퍼를 만들며 커진다.

> **⚠️ 컬렉션 식에는 자연 타입이 없다 ※C# 12 기준**
>
> ```csharp
> var x = [1, 2, 3];        // 컴파일 오류 — 대상 타입을 알 수 없다
> int[] y = [1, 2, 3];      // OK
> ```
>
> 컬렉션 식은 **대상 타입이 있어야만** 의미를 갖는다. `var`, 조건 연산자의 두 분기, 오버로드 해결이 모호한 인수 위치에서 오류가 난다. 이 제약은 이후 C# 버전에서 완화될 수 있다.

빈 컬렉션 식 `[]`도 유효하다. 대상이 배열이면 컴파일러가 `Array.Empty<T>()`를 쓸 수 있어 할당이 없다.

```csharp
Array.ForEach ([1, 2, 3], Console.WriteLine);   // 인수 위치에서도 대상 타입이 결정된다
void Process (IReadOnlyList<int> items) { }
Process ([]);                                   // 빈 리스트
```

컬렉션 초기화자(`new List<int> { 1, 2, 3 }`)와의 관계, 그리고 `Add` 메서드 기반 확장 규칙은 28.2절에서 이어 다룬다.

## 24.15 Big-O와 실제 상수 — 컬렉션 선택 가이드

### Big-O 요약표

Big-O 표기법은 입력 크기에 대해 시간이 어떻게 **확장되는지**를 나타낸다. 상수 시간은 O(1), 데이터 크기에 선형으로 비례하면 O(N)이다. 규칙 몇 가지: 단계들은 더한다(O(a+b)), 상수는 버린다(O(2N) → O(N)), 서로 다른 입력의 중첩은 곱한다(O(a*b)), 지배적이지 않은 항은 버린다(O(N + N²) → O(N²)).

| 컬렉션 | 순서 | 연속 저장 | 조회 | 삽입/삭제 | 인덱스 접근 |
|---|---|---|---|---|---|
| `T[]` | 인덱스 | O | 값: O(N) / 인덱스: O(1) | 불가(고정 크기) | O(1) |
| `List<T>` | 삽입 순 | O | 값: O(N) / 인덱스: O(1) | 끝: 분할상환 O(1) / 중간: O(N) | O(1) |
| `LinkedList<T>` | 삽입 순 | X | O(N) | 노드를 알 때 O(1) | 불가 |
| `Queue<T>` | FIFO | O | 앞: O(1) | O(1) | 불가 |
| `Stack<T>` | LIFO | O | 위: O(1) | O(1) | 불가 |
| `Dictionary<K,V>` | 없음 | O | 키: O(1) | O(1) | 불가 |
| `HashSet<T>` | 없음 | O | 키: O(1) | O(1) | 불가 |
| `SortedDictionary<K,V>` | 키 순 | X | 키: O(log N) | O(log N) | 불가 |
| `SortedList<K,V>` | 키 순 | O | 키: O(log N) | O(N) | O(1) |
| `SortedSet<T>` | 값 순 | X | O(log N) | O(log N) | 불가 |
| `ImmutableList<T>` | 인덱스 | X | O(log N) | O(log N) (구조 공유) | O(log N) |
| `ImmutableArray<T>` | 인덱스 | O | 인덱스: O(1) | O(N) (전체 복사) | O(1) |
| `FrozenDictionary<K,V>` | 없음 | O | 키: O(1)이면서 **상수가 작다** | 불가 | 불가 |

`SortedDictionary`는 속도와 순서 사이의 절충이고 이진 탐색 트리를 쓴다. `SortedList`는 트리를 배열로 구현한 형태라서 **미리 정렬된 데이터를 적재할 때는 빠르고 무작위 삽입에는 느리다.**

### Big-O가 말해 주지 않는 것

같은 O(N) 순회라도 실제 소요 시간은 수십 배 차이 날 수 있다. 이유는 **메모리 지역성**이다.

- `List<T>`는 요소가 연속된 배열에 있다. CPU가 캐시 라인 하나를 읽으면 여러 요소가 한꺼번에 온다. 프리페처가 다음 접근을 예측한다.
- `LinkedList<T>`는 노드가 힙 여기저기에 흩어져 있다. 요소마다 캐시 미스가 날 수 있고, 미스 하나가 산술 명령 수백 개에 해당하는 시간을 먹는다.

이것이 "이론상 더 나은 자료구조가 실제로는 느린" 가장 흔한 이유다. 항목당 메모리 오버헤드도 함께 봐야 한다 — 24.8절의 표에서 `SortedList<K,V>`가 항목당 2바이트, `OrderedDictionary`가 59바이트였다는 점을 기억하라. 캐시에 들어가는 양이 곧 속도다.

`List<T>`가 배열보다 약간 느린 이유도 상수에 있다. `List<T>`의 인덱서는 내부 배열 참조를 한 번 더 거치고 `_size` 경계 검사를 한다. 반대로 요소를 채우는 루프에서는 `List<T>.Add`가 배열 인덱싱보다 느리다 — 용량 검사와 버전 증가가 붙기 때문이다. 원천 도서의 벤치마크도 같은 방향을 보인다. **배열은 추가와 인덱스 접근이 빠르고, `List<T>`는 크기 변경의 유연성을 얻는 대신 상수를 지불한다.**

### 선택 가이드

```text
  키로 찾는가?
    ├─ 예 → 순서가 필요한가?
    │        ├─ 아니오 → 시작 후 변경이 없는가?
    │        │             ├─ 예   → FrozenDictionary<K,V>   ※.NET 8
    │        │             └─ 아니오 → Dictionary<K,V>
    │        ├─ 키 정렬 → 삽입이 잦은가?
    │        │             ├─ 예   → SortedDictionary<K,V>
    │        │             └─ 아니오 → SortedList<K,V>  (메모리 최소, 인덱스 접근 가능)
    │        └─ 삽입 순서 → OrderedDictionary
    │
    ├─ 중복 없는 멤버십만 필요한가? → HashSet<T> (정렬 필요 시 SortedSet<T>)
    │
    ├─ 키당 값이 여럿인가? → ILookup<K,V>  (ToLookup)
    │
    └─ 아니오 → 크기가 고정인가?
               ├─ 예   → T[]  (또는 ImmutableArray<T>)
               ├─ 아니오, FIFO → Queue<T>  (우선순위 있으면 PriorityQueue ※.NET 6)
               ├─ 아니오, LIFO → Stack<T>
               ├─ 아니오, 스레드 여럿 → System.Collections.Concurrent
               └─ 그 외 → List<T>
```

> **💡 실전 규칙 셋**
>
> 1. **크기가 변하지 않으면 배열을 써라.** 리스트는 항목을 넣고 빼는 동안에만 쓰고, 조작이 끝나면 배열로 굳히는 것이 좋은 습관이다.
> 2. **`List<T>.Contains`가 뜨거운 경로에 있으면 자료구조가 틀린 것이다.** O(N) 탐색을 반복하고 있다면 `HashSet<T>`나 `Dictionary<K,V>`로 바꿀 신호다.
> 3. **`System.Collections`(비제네릭)는 쓰지 마라.** 미션 크리티컬 코드에서는 특히 그렇다. 박싱과 캐스트가 성능과 타입 안전을 동시에 깎는다.
>
> 실제 측정 없이 이 규칙들을 절대적으로 신뢰하지는 마라. 벤치마크 방법론은 67장, 컬렉션 선택이 만드는 실측 상수의 심화는 72.6절에 있다.

## 24.16 인터페이스로 받을 것인가 구체 클래스로 받을 것인가

### 매개변수 — 유연성의 대가

컬렉션을 처리하는 메서드를 만든다고 하자. 최대한의 유연성을 원한다면 `IEnumerable<T>`를 받고 메서드를 제네릭으로 만들 것이다.

```csharp
void ProcessCollection<T> (IEnumerable<T> collection)
{
    foreach (var item in collection) { /* ... */ }
}
```

배열이든 리스트든 큐든 스택이든, `int`든 `string`이든 `Person`이든 넘길 수 있다. **그런데 이 유연성은 성능 비용을 동반한다.**

첫 번째 비용은 `IEnumerable<T>`의 장점이기도 한 **지연 실행**이다. 이 인터페이스를 구현하는 타입이 반드시 지연 실행을 하는 것은 아니지만 많은 타입이 그렇게 한다(29.6절). 인수가 이미 구체화된 컬렉션인지 매번 실행되는 쿼리인지 호출된 쪽에서는 알 수 없다.

더 심각한 두 번째 비용은 **순회가 힙에 객체를 할당한다**는 것이다. 24.1절에서 본 그대로다. 구체 타입을 쓰면 이 할당을 피할 수 있다.

```csharp
void ProcessCollection<T> (List<T> collection)
{
    foreach (var item in collection) { /* ... */ }
}
```

이쪽은 참조 타입을 반환하는 `IEnumerator<T> GetEnumerator()` 대신 **구조체를 반환하는 `List<T>.Enumerator GetEnumerator()`** 를 쓴다. 원천 도서의 표현을 그대로 옮기면, 이 코드는 **2~3배 빠르고 메모리를 덜 쓴다.**

### 측정을 어떻게 읽을 것인가

성능 관련 벤치마크를 인용할 때는 무엇이 측정됐는지 확인해야 한다. 원천 도서 중 하나는 다음 두 메서드를 벤치마크해 `IList<T>` 쪽이 근소하게 빨랐다고 보고한다.

```csharp
[Benchmark] public void BasicRateInterface() { IList<BasicRate> r = new List<BasicRate>(); }
[Benchmark] public void BasicRateConcrete()  { List<BasicRate>  r = new List<BasicRate>(); }
```

메모리 사용량은 양쪽이 같았다고 보고한다.

> **⚠️ 위 벤치마크가 측정하는 것은 컬렉션 성능이 아니다**
>
> 두 메서드는 **똑같은 객체를 똑같이 할당한다.** 지역 변수의 정적 타입은 IL에서 `newobj` 이후 `stloc`의 타입만 바꿀 뿐 런타임 동작을 바꾸지 않는다. 두 벤치마크가 다르게 나왔다면 그것은 측정 노이즈이거나 코드 배치·정렬 효과이지 인터페이스 선언의 효과가 아니다. 메모리 사용량이 동일하게 나온 것이 그 증거다.
>
> **선언 타입이 성능에 영향을 주는 지점은 인스턴스 생성이 아니라 "그 참조로 무엇을 하는가"다.** 열거하면 열거자 박싱이 생기고, 인덱서를 부르면 인터페이스 디스패치(18.9절)가 생긴다. 즉 실제로 유의미한 비교는 `foreach` 루프를 포함한 벤치마크여야 한다.
>
> 벤치마크는 코드가 아니라 **질문**을 검증한다. 질문이 틀리면 숫자가 맞아도 결론이 틀린다(67장).

### 결정표

| 위치 | 권고 | 이유 |
|---|---|---|
| 공개 API의 매개변수 | `IEnumerable<T>` — 단, 여러 번 열거하지 않을 때 | 호출자가 무엇이든 넘길 수 있다 |
| 개수·인덱스가 필요한 매개변수 | `IReadOnlyList<T>` 또는 `IReadOnlyCollection<T>` | 의도를 표현하면서 유연하다 |
| 수정할 매개변수 | `ICollection<T>` / `IList<T>` | "이 메서드가 컬렉션을 바꾼다"를 시그니처로 알린다 |
| 뜨거운 경로의 내부 메서드 | **구체 타입** (`List<T>`, `T[]`) | 구조체 열거자, 인라이닝, 경계 검사 제거 |
| 공개 API의 반환값 | `IReadOnlyList<T>` 또는 `IEnumerable<T>` | 내부 표현을 바꿀 자유를 남긴다 |
| 내부 컬렉션의 공개 노출 | `ReadOnlyCollection<T>` | 다운캐스트로 뚫리지 않는다(24.10절) |
| 지역 변수·필드 | 구체 타입 | 숨길 이유가 없고 성능만 잃는다 |

> **⚠️ `IEnumerable<T>` 매개변수를 두 번 열거하지 마라**
>
> ```csharp
> void Report<T> (IEnumerable<T> items)
> {
>     Console.WriteLine (items.Count());       // 한 번 열거
>     foreach (var i in items) { /* ... */ }   // 두 번째 열거
> }
> ```
>
> 인수가 지연 실행 쿼리라면 **쿼리가 두 번 실행된다.** 데이터베이스 쿼리라면 왕복도 두 번이다. 소스에 따라서는 두 번째 열거가 아예 다른 결과를 내거나 예외를 던진다.
>
> 여러 번 순회해야 한다면 시그니처를 `IReadOnlyCollection<T>`로 바꿔 계약으로 못 박거나, 메서드 안에서 `ToList()`로 한 번 구체화하라. 전자가 낫다 — 할당이 없고 호출자에게 의도가 보인다.

> **💡 "매개변수는 약하게, 필드는 강하게"**
>
> 라이브러리 경계에서는 추상화가 이긴다. 호출자를 특정 컬렉션 타입에 묶지 않고, 내부 구현을 바꿀 자유를 남긴다. 경계 안쪽 — 클래스의 private 필드, 지역 변수, 뜨거운 루프 — 에서는 구체 타입이 이긴다. 감출 대상이 없는데 인터페이스로 받으면 열거자 할당과 가상 디스패치만 사는 셈이다.
>
> 이 원칙을 한 문장으로 줄이면 이렇다. **인터페이스는 남에게 보이는 곳에, 구체 타입은 나만 보는 곳에.**

## 이 장의 요약

- **컬렉션의 뼈대는 인터페이스 세 단계다.** `IEnumerable<T>`가 열거만, `ICollection<T>`가 개수와 멤버십과 수정을, `IList<T>`/`IDictionary<K,V>`가 인덱스·키에 의한 임의 접근을 제공한다. 제네릭 인터페이스는 비제네릭 대응물을 상속하지 **않는다** — 뒤늦은 깨달음으로 더 나은 멤버 구성을 고를 수 있었기 때문이고, `Add(T)`와 `Add(object)`가 공존하는 타입 안전 구멍을 막기 위해서다.
- **`foreach`는 인터페이스가 아니라 모양을 본다.** 그래서 BCL 컬렉션의 `GetEnumerator()`는 구조체를 반환한다. 정적 타입이 구체 타입이면 열거에 힙 할당이 0회이고, 인터페이스로 받는 순간 열거자가 박싱된다. 이 하나가 24.16절의 결정표 전체를 결정한다.
- **`List<T>`는 배열 하나와 정수 셋이다.** 꽉 차면 용량을 2배로 늘려 새 배열에 복사한다. 그래서 `Add`는 분할 상환 O(1)이고, 앞에서의 `Insert`/`Remove`는 O(N)이며, 확장 순간에는 옛 배열과 새 배열이 함께 살아 있어 메모리가 옛 용량의 3배까지 뛴다. 최종 크기를 알면 생성자나 `EnsureCapacity`(※.NET 6)로 미리 잡아라.
- **열거 중 수정 감지는 `_version` 정수 하나로 이뤄진다.** 수정 연산이 증가시키고 열거자가 생성 시점 값과 매 `MoveNext`마다 비교한다. 비용은 정수 비교 하나지만, **완전한 보장이 아니라 최선 노력**이다. 예외가 안 났다고 안전한 것이 아니다.
- **`Dictionary<K,V>`는 버킷 배열과 엔트리 배열 두 개다.** 버킷은 값이 아니라 엔트리 인덱스를 담고, 충돌한 키들은 엔트리 배열 안에서 `next` 인덱스로 엮인 체인을 이룬다. 해시코드를 엔트리에 저장해 두어 비교와 리사이즈를 가속한다.
- **`GetHashCode`의 품질이 딕셔너리의 복잡도를 결정한다.** 분포가 나쁘면 예외도 경고도 없이 O(1)이 O(N)으로 퇴화한다. 구조체 키에는 반드시 `IEquatable<T>`를 구현하고, 가변 객체는 키로 쓰지 마라.
- **읽기 전용은 불변이 아니다.** `ReadOnlyCollection<T>`는 원본을 복사하지 않고 참조로 붙들어 두는 **보호된 뷰**다. 원본이 바뀌면 그대로 보인다. 진짜 불변이 필요하면 `Immutable*`을, 시작 후 변하지 않는 조회 테이블이면 `Frozen*`(※.NET 8)을 쓴다.
- **불변 컬렉션은 AVL 트리로 구조를 공유한다.** 전체 복사 대신 경로 하나(약 log N개 노드)만 새로 만든다. 대가는 읽기가 느려지는 것이며, 그래서 읽기 전용에 가까운 용도에는 배열 기반 `ImmutableArray<T>`가 따로 있다. 단 이것은 **구조체**이므로 `default` 값이 `NullReferenceException`의 원인이 된다.
- **비교자는 컬렉션 종류에 따라 다르다.** 해시 기반 컬렉션은 `IEqualityComparer<T>`를, 정렬 기반 컬렉션과 `Sort`/`BinarySearch`는 `IComparer<T>`를 인식한다. 서로 바꿔 넘길 수 없고, 생성 후에는 교체할 수 없으며, 정렬에 쓴 비교자와 탐색에 쓴 비교자가 다르면 예외 없이 틀린 답이 나온다.
- **Big-O는 확장성만 말한다.** 같은 O(N)이라도 연속 저장(`List<T>`)과 포인터 추적(`LinkedList<T>`)은 캐시 동작 때문에 수 배에서 수십 배 차이가 난다. 항목당 메모리 오버헤드도 함께 봐야 하고, 마지막 결론은 언제나 측정이 낸다.
- **인터페이스는 남에게 보이는 곳에, 구체 타입은 나만 보는 곳에.** 공개 API 경계에서는 `IEnumerable<T>`/`IReadOnlyList<T>`가 이기고, private 필드와 뜨거운 루프에서는 구체 타입이 이긴다. `IEnumerable<T>` 매개변수를 두 번 열거하는 것은 그 자체로 버그다.

## 연습 문제

1. `List<int>`를 만들고 `Add`를 100회 반복하면서 매 회 `Count`와 `Capacity`를 출력하라. 용량이 바뀌는 지점을 표로 정리해 24.4절의 2배 전략과 일치하는지 확인하라. 그다음 `new List<int>(100)`으로 시작해 같은 실험을 반복하고, `GC.GetAllocatedBytesForCurrentThread()`로 두 방식의 총 할당량을 비교하라.

2. `foreach` 안에서 `List<T>`의 요소를 제거해 `InvalidOperationException`을 재현하라. 그다음 **마지막에서 두 번째** 요소를 처리할 때 제거하도록 바꿔 보고 결과가 달라지는지 확인하라. 같은 실험을 `Dictionary<K,V>`의 `Remove`로 반복해 24.4절의 ※.NET Core 3.0 동작을 확인하라.

3. `GetHashCode()`가 항상 `0`을 반환하는 키 클래스를 만들어 `Dictionary`에 1만 개를 넣고 전체 조회 시간을 측정하라. 그다음 `HashCode.Combine`으로 제대로 구현해 다시 측정하고 배율을 기록하라(25.4절).

4. `List<int>`를 100만 개 채운 뒤 (a) `foreach (int i in list)`, (b) `IEnumerable<int>`로 캐스트한 뒤 `foreach`, (c) `for` 인덱스 루프 세 가지로 합계를 구하고 시간과 0세대 GC 횟수를 비교하라. 24.1절의 구조체 열거자 박싱이 숫자로 드러나는지 확인하라.

5. `Collection<T>`를 상속해 `InsertItem`·`SetItem`·`RemoveItem`·`ClearItems` 중 **셋만** 재정의한 클래스를 만들어라. 재정의하지 않은 경로로 규칙을 우회하는 호출을 찾아 실행하고, 네 번째를 마저 재정의해 막아라.

6. 같은 키/값 데이터로 `Dictionary`, `ImmutableDictionary`, `FrozenDictionary`를 각각 만들어 (a) 생성 시간과 (b) 100만 회 조회 시간을 측정해 표로 만들어라. frozen 쪽의 생성 비용과 조회 이득이 손익분기를 넘는 조회 횟수를 계산하라.

7. `ReadOnlyCollection<string>`으로 감싼 리스트를 공개 프로퍼티로 노출하는 클래스를 만들고, 소비자 쪽에서 (a) `IList<string>`으로 다운캐스트해 `Add`를 호출하고 (b) 내부에서 원본 리스트를 수정해 보라. 각각 무슨 일이 일어나는지 확인하고, `ImmutableList<string>`으로 바꿨을 때 두 결과가 어떻게 달라지는지 기록하라.
