# 11장. 문(statement)과 제어 흐름

> **이 장의 위치** — 10장까지가 "값을 어떻게 만드는가"였다면 이 장은 "그 값을 만드는 일을 어떤 순서로 시킬 것인가"다. 식(expression)은 값을 낳고, 문(statement)은 실행 순서를 만든다. Part II의 마지막 실질 장으로서, 6장에서 12장까지 쌓아 온 문법 조각들이 여기서 하나의 실행 가능한 프로그램 형태로 합쳐진다. 특히 `foreach` 한 줄이 정확히 무엇으로 바뀌는지를 IL로 끝까지 판다 — 이 책이 왜 문법서와 다른지를 가장 짧은 코드로 보여주는 자리다.
>
> **선수 지식** — 6장(구문과 타입 기초), 특히 6.9절(확정 할당). 7장(숫자와 불리언), 특히 7.10절(조건 연산자). 9장(배열). 10장(변수, 매개변수, 식), 특히 10.1절(범위 규칙)과 10.8절(기본 식과 할당 식).
>
> **이 장에서 다루지 않는 것** — 패턴(`case Cat { Legs: 4 }`, `is not null`, 목록 패턴)의 문법과 의미론 전체는 77장이며, `switch` 식의 완전성 검사 상세는 77.14절, 패턴이 컴파일되는 형태와 분기 성능은 77.15절이다. `try`/`catch`/`finally`/`when`의 의미론과 예외 처리 메커니즘은 32장, `using`이 부르는 `Dispose`의 계약은 33장(문법적 낮춤은 33.5절), `lock`이 건드리는 메모리 모델과 경합은 48장(특히 48.5절)이다. `yield return`/`yield break`가 만드는 상태 기계는 28장, `await`와 `await foreach`는 47장이다. `checked`/`unchecked`의 오버플로 의미론은 7.9절에서 이미 끝냈고, `unsafe`와 `fixed`의 실제 사용은 60.7절·60.8절이다. 열거자가 만드는 할당량의 정확한 값은 63.9절이다. **이 장이 다루는 것은 문의 문법과 그것이 컴파일되는 결과, 딱 거기까지다.**

## 11.1 선언문과 식문

### 문이란 무엇인가

C#에서 **문**(statement)은 실행 단위다. 메서드 본문은 문의 나열이고, 문은 **소스에 적힌 텍스트 순서대로** 실행된다. 이 단순한 규칙이 제어 흐름 문(if, switch, 반복문, 점프문)에 의해서만 깨진다.

**문 블록**(statement block)은 중괄호 `{}` 사이에 놓인 문의 나열이다. 블록 자체도 하나의 문이므로, 문 하나가 올 수 있는 자리에는 언제나 블록을 놓을 수 있다.

C#의 문을 전부 분류하면 다음과 같다. 이 장은 이 표의 왼쪽 여섯 줄을 다루고, 나머지는 각각의 장으로 넘긴다.

| 분류 | 문 | 다루는 곳 |
|---|---|---|
| 선언문 | 지역 변수 선언, 지역 상수 선언, 지역 함수 선언 | 11.1절 |
| 식문 | 대입, 증감, 메서드 호출, 객체 생성, `await` | 11.1절 |
| 블록·빈 문 | `{ ... }`, `;` | 11.1절 |
| 선택문 | `if`, `switch` | 11.2절 |
| 반복문 | `while`, `do-while`, `for`, `foreach` | 11.4절, 11.5절 |
| 점프문 | `break`, `continue`, `goto`, `return`, `throw` | 11.6절 |
| 레이블 문 | `label:` | 11.6절 |
| 예외 처리 문 | `try`-`catch`-`finally` | 32장 |
| 반복자 문 | `yield return`, `yield break` | 28장 |
| 리소스 문 | `using` 문, `using` 선언 | 11.7절, 33.5절 |
| 동기화 문 | `lock` | 11.7절, 48.5절 |
| 오버플로 문 | `checked`, `unchecked` | 11.7절, 7.9절 |
| 비관리 문 | `unsafe`, `fixed` | 11.7절, 60.7절·60.8절 |

> **📌 "문"과 "식"은 다른 층위다**
>
> **식**은 값을 만든다. `2 + 3`은 `5`라는 값을 만들고, `Console.ReadLine()`은 `string`을 만든다. **문**은 값을 만들지 않는다. 문은 무언가를 *하고* 끝난다.
>
> 이 구분은 언어마다 다르다. F#이나 Rust 같은 언어에서는 `if`가 값을 만드는 식이다. C#에서 `if`는 문이며 값을 만들지 않는다. 대신 C#은 값이 필요한 자리를 위해 별도의 **식** 문법을 따로 준다 — 조건 연산자 `?:`(11.2절)와 `switch` 식(11.3절)이 그것이다. 그래서 C#에는 같은 일을 하는 문과 식이 짝을 이루어 존재한다. 이 짝을 아는 것이 이 장의 절반이다.

### 지역 변수 선언문

지역 변수 선언은 새 변수를 도입하고, 선택적으로 초기화한다. 같은 타입의 변수 여러 개를 쉼표로 나열할 수 있다.

```csharp
string someWord = "rosebud";
int someNumber = 42;
bool rich = true, famous = false;
```

지역 **상수** 선언은 선언과 동시에 초기화해야 하고, 이후 바꿀 수 없다.

```csharp
const double c = 2.99792458E08;
c += 10;                          // 오류 CS0131 — 대입 왼쪽이 변수가 아니다
```

지역 변수의 범위 규칙(블록 전체를 양방향으로 점유한다, 그림자 금지)은 10.1절에서 이미 끝냈으므로 여기서 반복하지 않는다. `var`의 규칙은 10.6절, `const`와 `readonly`의 컴파일 결과 차이는 10.11절이다.

### 컴파일 결과 — 선언문은 IL에 없다

선언문은 **명령을 하나도 만들지 않는다.** 만드는 것은 초기화뿐이다.

```csharp
static int Demo()
{
    int a;              // 명령 0개
    int b = 7;          // ldc.i4.7 + stloc
    string s;           // 명령 0개
    a = b + 1;          // ldloc + ldc + add + stloc
    return a;
}
```

이것이 IL로는 이렇게 된다.

```il
.method private hidebysig static int32 Demo() cil managed
{
  .maxstack  2
  .locals init (int32 V_0,        // a
                int32 V_1,        // b
                string V_2)       // s  — 쓰이지 않아도 슬롯은 잡힌다
  IL_0000:  ldc.i4.7
  IL_0001:  stloc.1               // b = 7
  IL_0002:  ldloc.1
  IL_0003:  ldc.i4.1
  IL_0004:  add
  IL_0005:  stloc.0               // a = b + 1
  IL_0006:  ldloc.0
  IL_0007:  ret
}
```

선언은 메서드 머리의 `.locals init` 목록으로 **한 번에 모여** 나타난다. 소스에서 선언이 메서드 중간에 흩어져 있어도 마찬가지다. IL 수준에서 지역 변수는 "메서드 진입 시 통째로 잡히는 슬롯 배열"이며, 선언문의 위치는 컴파일러가 이름 해석과 확정 할당 분석에 쓰는 소스 정보일 뿐 실행 시점과는 무관하다.

> **📌 `.locals init`의 `init`**
>
> `init` 플래그는 "메서드 진입 시 이 슬롯들을 전부 0으로 채워라"라는 지시다. 확정 할당 규칙(6.9절) 덕분에 C# 코드는 초기화 전 지역 변수를 읽을 수 없으므로 이 0 채우기는 대체로 낭비다. 그래서 JIT은 실제로 필요 없다고 판단하면 생략한다. 지역 변수가 아주 크거나(`stackalloc` 버퍼 등) 개수가 많으면 이 초기화 비용이 눈에 보일 수 있고, 그럴 때 `[SkipLocalsInit]` 특성으로 플래그를 뗄 수 있다(63.7절과 69장에서 다시 만난다).
>
> 지금 알아 둘 것은 하나다 — **선언문은 실행 비용이 0이 아니다.** 다만 그 비용은 선언한 지점이 아니라 메서드 진입 지점에 한꺼번에 발생한다.

### 식문 — 모든 식이 문이 되지는 않는다

`Console.WriteLine(x);`는 식이면서 문이다. 그런데 `x + y;`는 식이지만 **문이 될 수 없다.**

```csharp
int x = 1, y = 2;
x + y;              // 오류 CS0201
```

오류 메시지는 이렇다.

```text
error CS0201: Only assignment, call, increment, decrement, await, and new
object expressions can be used as a statement
```

이 메시지가 규칙 전체다. 식문이 될 수 있는 식은 정확히 다음뿐이다.

| 식문이 되는 식 | 예 | 이유 |
|---|---|---|
| 대입식 | `x = 1;`, `x += 2;` | 상태를 바꾼다 |
| 전위·후위 증감식 | `x++;`, `--y;` | 상태를 바꾼다 |
| 메서드 호출식 | `Console.WriteLine(y);`, `list.Add(1);` | 상태를 바꿀 수 있다 |
| 객체 생성식 | `new StringBuilder();` | 생성자가 상태를 바꿀 수 있다 |
| `await` 식 | `await task;` | 비동기 진행을 만든다(47장) |
| null 조건부 호출 | `handler?.Invoke(this, e);` | 조건부 메서드 호출식 |

핵심 원리는 이것이다 — **식문은 상태를 바꾸거나, 상태를 바꿀 가능성이 있는 무언가를 호출해야 한다.** `x + y`는 값을 만들 뿐 아무것도 바꾸지 않으므로, 그것만 적어 놓은 줄은 의미가 없다. 컴파일러는 이런 줄을 오타로 간주하고 거부한다.

> **⚠️ `==`를 `=`로 잘못 쓰면 어떻게 되는가**
>
> ```csharp
> bool ok = false;
> ok == true;         // 오류 CS0201 — 다행히 잡힌다
> ok = true;          // OK — 이건 대입이다
> ```
>
> 그런데 반대 방향의 오타는 잡히지 않는다.
>
> ```csharp
> if (ok = true) { }  // 경고는 나지만 컴파일된다
> ```
>
> `ok = true`는 대입식이고, 대입식의 값은 대입된 값이므로 `bool`이다. `if`가 `bool`을 요구하므로 타입이 맞아 버린다. C#이 `if`에 `bool`만 허용하는 덕분에 `if (n = 0)` 같은 정수 버전은 막히지만(11.2절), `bool` 변수에 대해서는 여전히 뚫린다. 컴파일러가 CS0665 경고를 주지만 경고일 뿐이다. **경고를 오류로 승격시켜라**(`<TreatWarningsAsErrors>`).

### 값을 버리는 것은 합법이다 — 그리고 대개 무의미하다

값을 반환하는 메서드나 생성자를 호출하고 결과를 쓰지 않아도 된다. 문법적으로 합법이다. 하지만 그 호출이 상태를 바꾸지 않는다면 그 줄은 완전히 쓸모없다.

```csharp
new StringBuilder();          // 합법. 그러나 무의미하다
new string ('c', 3);          // 합법. 그러나 무의미하다
x.Equals (y);                 // 합법. 그러나 무의미하다
list.Where(i => i > 3);       // 합법. 그리고 위험하다 — 지연 실행이라 아무 일도 안 한다(29.6절)
```

마지막 줄이 실전에서 가장 자주 나오는 사고다. LINQ 연산자는 시퀀스를 반환할 뿐 아무것도 실행하지 않으므로, 결과를 버리면 코드 전체가 죽은 코드가 된다. 컴파일러는 이것을 오류로 잡지 않는다. `Where`가 메서드 호출식이므로 식문 규칙을 통과하기 때문이다.

> **💡 결과를 의도적으로 버릴 때는 버림(discard)을 써라**
>
> ※C# 7의 버림 `_`를 대입 왼쪽에 두면 **어떤 식이든** 문으로 만들 수 있다.
>
> ```csharp
> _ = list.Where(i => i > 3);      // "결과를 안 쓰는 게 의도다"라고 적는 것
> _ = client.SendAsync(request);   // 의도적 fire-and-forget (권장하지는 않는다)
> ```
>
> `_ =`는 대입식이므로 식문 규칙을 통과하고, IL에는 `pop` 한 줄만 남거나 아예 사라진다. 값을 정말로 버릴 생각이라면 그 사실을 코드에 적어라. 나중에 읽는 사람이 "빠뜨린 코드"인지 "일부러 버린 코드"인지 구분할 수 있어야 한다. 분석기 규칙(CA1806 등)도 `_ =`를 붙인 줄은 통과시킨다.

### 빈 문과 블록

세미콜론 하나짜리 **빈 문**(empty statement)은 아무것도 하지 않는다. 문이 하나 필요한데 할 일이 없는 자리에 쓴다.

```csharp
while (Move()) ;              // 본문 없이 Move()만 반복
```

> **⚠️ 실수로 만든 빈 문이 조용히 코드를 죽인다**
>
> ```csharp
> if (x > 0);                   // 여기 세미콜론
>     Console.WriteLine("양수");  // 조건과 무관하게 언제나 실행된다
>
> for (int i = 0; i < 10; i++);  // 여기도
>     Console.WriteLine(i);      // 오류 — i가 범위 밖이다 (운이 좋은 경우)
>
> while (i < 10);                // 여기도
>     i++;                       // 무한 루프. 프로그램이 멈춘다
> ```
>
> 세 번째가 최악이다. `while` 뒤의 빈 문이 본문이 되어 조건이 영원히 참인 무한 루프가 된다. `i++`는 도달조차 하지 않는다. 컴파일러는 첫 줄에 CS0642 경고("가능한 실수로 보이는 빈 문")를 주지만, 이 경고를 켜 놓지 않으면 못 본다.
>
> 예방책은 하나다 — **`if`, `for`, `while`, `foreach` 본문에 언제나 중괄호를 써라.** 이 규칙의 실전 근거는 11.2절에서 다시 나온다.

지역 함수 선언도 문이다. 메서드 본문 안에 함수를 선언하며, 선언 위치와 무관하게 그 블록 어디서든 호출할 수 있다. 지역 함수가 컴파일되는 형태와 람다와의 차이는 26.12절이다.

```csharp
static int Sum(int[] a)
{
    return Run();                       // 아래에 선언되어 있어도 호출된다
    int Run()                           // 지역 함수 선언문
    {
        int t = 0;
        foreach (int x in a) t += x;
        return t;
    }
}
```

## 11.2 선택문 — `if` / `switch` 문

### `if` 문은 `bool`만 받는다

```csharp
if (5 < 2 * 3)
    Console.WriteLine ("true");        // true
```

조건 자리에는 `bool` 식만 올 수 있다. C와 C++에서 통하던 "0이 아니면 참" 규칙이 C#에는 없다.

```csharp
string s = "My textual data";
if (s.Length)                 // 오류 CS0029 — int를 bool로 변환할 수 없다
{ }

if (s.Length > 0)             // OK
{ }
```

이 제약은 불편함이 아니라 방어책이다. C에서 `if (n = 0)`이 오타여도 컴파일되는 이유가 바로 "정수도 조건이 될 수 있다"는 규칙이었다. C#은 그 문을 닫았다.

> **📌 `bool`이 아닌데 조건에 놓을 수 있는 두 가지 예외**
>
> 첫째, `bool`로의 **암시적 변환**을 가진 사용자 정의 타입. 둘째, `true`/`false` 연산자를 오버로딩한 타입(22.5절). 둘 다 드물고, 둘 다 `bool?`은 해당되지 않는다 — `bool?`은 `if`에 직접 놓을 수 없다(21.5절).

### 중괄호를 생략하지 마라 — `#gotofail`

문 하나뿐이면 중괄호를 생략할 수 있다. 문법이 그렇다. 그러나 생략하면 안 된다.

2012년 9월에 출시된 애플 iOS 6에는 SSL/TLS 인증서 검증 코드에 중괄호 없는 `if` 문 때문에 생긴 버그가 있었다. 같은 `goto fail;` 줄이 실수로 두 번 적혔고, 두 번째 줄이 `if`의 본문이 아니라 **언제나 실행되는 문**이 되어 인증서 검증의 마지막 단계를 통째로 건너뛰었다. 이 버그는 18개월 동안 살아 있었고 사파리로 은행 사이트에 접속한 모든 사용자가 영향을 받았다. `#gotofail`이라는 이름으로 알려진 사건이다.

```csharp
// 위험한 형태
if (cond)
    DoA();
    DoB();            // cond와 무관하게 언제나 실행된다

// 안전한 형태
if (cond)
{
    DoA();
    DoB();
}
```

중괄호를 붙인다고 코드가 느려지지 않는다. IL은 한 바이트도 달라지지 않는다. 얻는 것만 있고 잃는 것이 없다.

### `else` 결합 규칙

`else`는 **가장 가까운, 아직 짝이 없는 `if`** 에 붙는다.

```csharp
if (true)
    if (false)
        Console.WriteLine();
    else
        Console.WriteLine ("executes");   // 안쪽 if의 else다
```

들여쓰기는 사람에게만 보이고 컴파일러는 무시한다. 위 코드는 다음과 정확히 같다.

```csharp
if (true)
{
    if (false)
        Console.WriteLine();
    else
        Console.WriteLine ("executes");
}
```

의도가 바깥 `if`의 `else`였다면 중괄호로 명시해야 한다.

```csharp
if (true)
{
    if (false)
        Console.WriteLine();
}
else
    Console.WriteLine ("does not execute");
```

### `else if`는 문법이 아니다

C#에는 `elif` 같은 키워드가 없다. 흔히 쓰는 `else if` 사슬은 **`else` 절 안에 `if` 문이 중첩된 것**이며, 단지 줄바꿈과 들여쓰기를 관례적으로 생략해 놓은 모양일 뿐이다.

```csharp
void TellMeWhatICanDo (int age)
{
    if (age >= 35)
        Console.WriteLine ("You can be president!");
    else if (age >= 21)
        Console.WriteLine ("You can drink!");
    else if (age >= 18)
        Console.WriteLine ("You can vote!");
    else
        Console.WriteLine ("You can wait!");
}
```

의미론적으로는 이렇게 중첩되어 있다.

```csharp
if (age >= 35) { ... }
else { if (age >= 21) { ... }
       else { if (age >= 18) { ... }
              else { ... } } }
```

전처리기의 `#elif`(12.7절)는 진짜 키워드지만, 실행문의 `else if`는 아니다. 이 차이가 중요한 지점이 하나 있다 — **사슬이 길어질수록 실제로는 중첩이 깊어진다.** 조건이 열 개면 열 겹 중첩이고, 마지막 조건에 닿으려면 앞의 아홉 개를 전부 평가해야 한다. `switch`가 이 문제를 해결한다.

### 컴파일 결과 — `if`의 조건은 뒤집힌다

```csharp
static void F(int x)
{
    if (x > 0)
        Console.WriteLine("pos");
    else
        Console.WriteLine("nonpos");
}
```

```il
IL_0000:  ldarg.0
IL_0001:  ldc.i4.0
IL_0002:  ble.s      IL_0010        // "x > 0"이 아니라 "x <= 0이면 else로"
IL_0004:  ldstr      "pos"
IL_0009:  call       void [System.Console]System.Console::WriteLine(string)
IL_000e:  br.s       IL_001a        // then 블록 끝 → 합류 지점으로
IL_0010:  ldstr      "nonpos"
IL_0015:  call       void [System.Console]System.Console::WriteLine(string)
IL_001a:  ret
```

읽을 지점이 두 개 있다.

- **조건이 반전된다.** 소스는 `x > 0`인데 IL은 `ble`(작거나 같으면 분기)다. "참이면 계속 진행하고, 거짓이면 뛰어넘는다"가 기계어의 자연스러운 모양이기 때문이다. `if`의 then 블록은 **분기 없이 그냥 흘러 들어가는** 경로가 되고, else 블록으로 가는 것만 분기가 된다.
- **`else`가 있으면 then 블록 끝에 `br`이 하나 더 붙는다.** else를 건너뛰기 위한 무조건 분기다. `else`가 없으면 이 `br`이 사라진다.

그래서 **분기 예측 관점에서 `if`의 then 쪽이 "예측되는 경로"** 다. 실행 빈도가 훨씬 높은 쪽을 `if` 본문에 두고 예외적인 경우를 `else`에 두는 것이, 최신 CPU에서 아주 미세하게나마 유리한 이유다. 다만 이 차이는 대부분의 코드에서 측정되지 않으며(67장), 가독성을 희생할 가치는 없다.

> **⚠️ `if` 사슬의 비용은 조건의 개수가 아니라 "앞에서 몇 개를 평가하는가"다**
>
> ```csharp
> if (code == 1) A();
> else if (code == 2) B();
> // ... 30개 ...
> else if (code == 31) Z();
> ```
>
> `code`가 31이면 비교를 31번 한다. 순차 비교 사슬은 `O(n)`이다. 같은 코드를 `switch`로 쓰면 컴파일러가 점프 테이블이나 이진 탐색으로 바꿔 `O(1)` 또는 `O(log n)`이 될 수 있다. 조건이 대여섯 개를 넘고 전부 같은 변수를 상수와 비교하는 모양이라면 `switch`가 옳다.

### 조건 연산자 `?:` — 값이 필요한 자리의 `if`

`q ? a : b`의 기본 의미론(단축 평가, 공통 타입 찾기, ※C# 9의 대상 타입 지정 조건식)은 7.10절에서 이미 다뤘다. 여기서는 **문과 식의 경계**에서 생기는 세 가지만 짚는다.

**첫째, 조건 연산자는 문이 될 수 없다.** 11.1절의 식문 규칙에 걸린다.

```csharp
// 오류 CS0201
s.Length > 0
    ? Console.WriteLine ("있다")
    : Console.WriteLine ("없다");
```

`Console.WriteLine`이 `void`를 반환하므로 조건 연산자의 결과 타입 자체가 성립하지 않고, 설령 성립하더라도 조건식은 식문 목록에 없다. 이 자리는 `if`/`else`가 맡아야 한다.

**둘째, 컴파일 결과는 `if`와 같다.** 조건 연산자는 "분기 없는 명령"이 아니다.

```csharp
static int Max(int a, int b) => a > b ? a : b;
```

```il
IL_0000:  ldarg.0
IL_0001:  ldarg.1
IL_0002:  ble.s      IL_0008
IL_0004:  ldarg.0
IL_0005:  br.s       IL_0009
IL_0008:  ldarg.1
IL_0009:  ret
```

`if`/`else`로 쓴 `Max`와 IL이 사실상 동일하다. **조건 연산자를 쓴다고 빨라지지 않는다.** 짧게 쓰는 문법일 뿐이다. (JIT이 이 패턴을 조건부 이동 명령 `cmov`로 바꾸는 경우가 있는데, 그것은 `if`로 써도 마찬가지로 일어난다.)

**셋째, ※C# 7.2부터 `ref` 조건식이 가능하다.** 값이 아니라 **저장 위치**를 고르는 형태다.

```csharp
var small = new int[] { 1, 2, 3, 4, 5 };
var large = new int[] { 10, 20, 30, 40, 50 };
int index = 7;

ref int slot = ref ((index < 5) ? ref small[index] : ref large[index - 5]);
slot = 0;                                       // large가 {10,20,0,40,50}이 된다

index = 2;
((index < 5) ? ref small[index] : ref large[index - 5]) = 100;   // small이 {1,2,100,4,5}
```

두 분기가 모두 `ref`여야 하고 타입이 정확히 같아야 한다. `ref` 지역 변수와 `ref` 반환의 규칙은 10.3절이다.

> **💡 조건 연산자는 분기가 정확히 둘일 때만 쓴다**
>
> 조건이 셋 이상이면 `switch` 식(11.3절)이 옳다. 중첩된 `?:`는 오른쪽 결합이라 의도대로 동작하지만, 읽는 사람이 결합 방향을 머리로 계산해야 하는 코드는 유지보수 비용이 크다. 7.10절에서 같은 권고를 이미 했다.

### `switch` 문 — 하나의 식을 여러 상수와 비교한다

`switch`는 식 하나를 여러 후보와 비교한다. `if` 사슬과의 결정적 차이는 **식이 정확히 한 번만 평가된다**는 것이다.

```csharp
void ShowCard (int cardNumber)
{
    switch (cardNumber)
    {
        case 13:
            Console.WriteLine ("King");
            break;
        case 12:
            Console.WriteLine ("Queen");
            break;
        case 11:
            Console.WriteLine ("Jack");
            break;
        case -1:                       // 조커는 -1
            goto case 12;              // 이 게임에서 조커는 퀸으로 친다
        default:                       // 나머지 전부
            Console.WriteLine (cardNumber);
            break;
    }
}
```

상수 `case`에 쓸 수 있는 타입은 내장 숫자 타입과 `bool`, `char`, `string`, `enum`, 그리고 이들의 널 가능 버전이다. `case null:`도 쓸 수 있다.

### fall-through 금지 — C#이 C와 갈라지는 지점

C와 C++, Java에서는 `case` 본문이 끝나면 다음 `case`로 흘러 들어간다(fall-through). 이것이 버그의 원천이라는 것이 30년에 걸쳐 확인되었고, C#은 이 동작을 **금지**했다.

규칙은 이렇다 — **실행 가능한 문이 있는 `switch` 섹션의 끝점(end point)은 도달 가능해서는 안 된다.** 즉 각 섹션은 반드시 점프문으로 끝나야 한다.

| 섹션을 끝낼 수 있는 것 | 의미 |
|---|---|
| `break;` | `switch` 문 전체를 빠져나간다 |
| `goto case <상수>;` | 다른 `case` 절로 점프한다 |
| `goto default;` | `default` 절로 점프한다 |
| `return;` / `return 식;` | 메서드를 빠져나간다 |
| `throw ...;` | 예외를 던진다 |
| `continue;` | 감싸는 반복문의 다음 회차로 간다 |
| `goto <레이블>;` | 레이블로 점프한다 |
| 무한 루프 | 끝점에 도달할 수 없으므로 허용된다 |

이 규칙을 어기면 컴파일 오류 CS0163("한 case 레이블에서 다른 case 레이블로 제어가 이동할 수 없습니다")이 난다. 실수로 `break`를 빠뜨린 코드는 컴파일되지 않는다.

예외가 하나 있다. **본문이 비어 있는 `case` 레이블은 겹쳐 쌓을 수 있다.**

```csharp
switch (cardNumber)
{
    case 13:
    case 12:
    case 11:
        Console.WriteLine ("Face card");
        break;
    default:
        Console.WriteLine ("Plain card");
        break;
}
```

`case 13:`과 `case 12:` 사이에 문이 하나라도 있으면 오류다. 문이 없으면 세 레이블이 같은 섹션을 가리키는 것이므로 허용된다.

> **📌 `goto case`는 "의도적 fall-through"의 이름이다**
>
> C에서 fall-through는 기본 동작이라 의도인지 실수인지 구분되지 않았다. C#은 기본 동작을 금지하고, 의도적으로 다음 절로 넘어가고 싶으면 `goto case 12;`처럼 **명시적으로 적게** 만들었다. 문법이 실수를 막고 의도는 그대로 표현하게 하는 좋은 설계 사례다.
>
> `goto case`가 갈 수 있는 대상은 **상수 `case` 레이블뿐**이다. 패턴 `case`(`case Cat c:`)로는 점프할 수 없다. 패턴을 쓰는 `switch`에서는 `goto case`를 쓸 수 없다고 기억하면 된다.

### `switch` 섹션의 변수 범위

`switch` 문의 모든 섹션은 **하나의 선언 공간**을 공유한다. 그래서 한 섹션에서 선언한 이름을 다른 섹션에서 다시 선언할 수 없다.

```csharp
switch (n)
{
    case 1:
        int t = 10;         // 선언
        Console.WriteLine(t);
        break;
    case 2:
        int t = 20;         // 오류 CS0128 — 이미 정의된 이름
        break;
}
```

해법은 섹션마다 중괄호로 블록을 만드는 것이다.

```csharp
case 1:
{
    int t = 10;
    Console.WriteLine(t);
    break;
}
case 2:
{
    int t = 20;             // OK — 별도 블록
    break;
}
```

10.1절에서 본 "블록이 범위를 만든다"는 규칙이 여기서도 그대로 적용된다.

### 컴파일 결과 — `switch`는 세 가지 중 하나로 낮춰진다

`switch` 문에는 대응되는 IL 옵코드 `switch`가 존재한다. 그러나 컴파일러가 언제나 그것을 쓰지는 않는다. Roslyn은 `case` 값의 개수와 분포를 보고 세 가지 전략 중 하나를 고른다.

| 전략 | 언제 | 비용 | IL 모양 |
|---|---|---|---|
| 순차 비교 | 값이 적을 때(대략 3개 미만) | `O(n)` | `beq` / `bne.un` 사슬 |
| 점프 테이블 | 값이 조밀할 때 | `O(1)` | `switch` 옵코드 |
| 이진 탐색 | 값이 많고 성긴 때 | `O(log n)` | 비교 + 분기 트리 |

**점프 테이블**은 `switch` 옵코드로 표현된다. 이 옵코드는 정수 하나를 스택에서 꺼내 "N개의 분기 대상 중 그 인덱스의 것으로 점프"한다. 범위를 벗어나면 다음 명령으로 흘러간다.

```csharp
static string Name(int n) 
{
    switch (n)
    {
        case 0: return "zero";
        case 1: return "one";
        case 2: return "two";
        case 3: return "three";
        default: return "?";
    }
}
```

```il
IL_0000:  ldarg.0
IL_0001:  switch     ( IL_0018, IL_001e, IL_0024, IL_002a )   // n = 0,1,2,3
IL_0016:  br.s       IL_0030                                  // 범위 밖 → default
IL_0018:  ldstr      "zero"
IL_001d:  ret
IL_001e:  ldstr      "one"
IL_0023:  ret
IL_0024:  ldstr      "two"
IL_0029:  ret
IL_002a:  ldstr      "three"
IL_002f:  ret
IL_0030:  ldstr      "?"
IL_0035:  ret
```

`case` 값이 0에서 시작하지 않으면 컴파일러가 먼저 뺄셈을 넣어 0 기준으로 정규화한다. 예를 들어 `case 100: case 101: case 102:`는 `n - 100`을 계산한 뒤 `switch` 옵코드에 넣는다.

JIT은 이 옵코드를 실제 **점프 테이블**로 낸다 — 분기 대상 주소가 담긴 배열을 만들고, 인덱스로 한 번 읽어 그 주소로 간접 점프한다. 비교 횟수가 `case` 개수와 무관해진다.

```text
            switch (n)  →  n을 인덱스로 한 번 읽는다

  n ──┐
      ↓
 ┌──────────────────────┐
 │ 점프 테이블 (배열)   │
 │  [0] → IL_0018       │───→ case 0 본문
 │  [1] → IL_001e       │───→ case 1 본문
 │  [2] → IL_0024       │───→ case 2 본문
 │  [3] → IL_002a       │───→ case 3 본문
 └──────────────────────┘
      범위 밖 ──────────────→ default 본문

   비교 1번(범위 검사) + 메모리 읽기 1번 + 간접 점프 1번 = O(1)
```

값이 성기면 테이블이 커진다. `case 1:`과 `case 1000000:` 두 개만 있는데 백만 칸짜리 테이블을 만들 수는 없다. 그래서 컴파일러는 **밀도**를 본다. 대략 "테이블 칸의 절반 이상이 실제 `case`로 채워지는가"를 기준으로 삼고, 미달이면 값들을 구간으로 쪼개 이진 탐색 트리를 만든다. 정확한 임계값은 컴파일러 구현 세부사항이며 버전에 따라 달라질 수 있다.

> **⚠️ "`switch`는 항상 `O(1)`"은 틀린 말이다**
>
> ```csharp
> switch (errorCode)
> {
>     case 1001: ...
>     case 2405: ...
>     case 30119: ...
> }
> ```
>
> 이런 코드는 점프 테이블이 되지 않는다. 값이 너무 성기다. 순차 비교나 이진 탐색이 된다. `switch`가 빠른 것은 **값이 조밀할 때**이며, 그 조건을 만족시키는 가장 흔한 방법이 `enum`을 0부터 연속 부여하는 것이다(20.1절).
>
> 반대로 말하면, `enum` 값을 `[Flags]`처럼 1, 2, 4, 8, 16으로 매기면(20.3절) 점프 테이블이 안 나온다. 성능이 중요한 자리에서 `enum`에 `switch`를 걸 계획이라면 값을 연속으로 두어라.

### 문자열 `switch`는 특별하다

`case "Red":`처럼 문자열을 비교하는 `switch`는 점프 테이블을 쓸 수 없다. 문자열은 정수가 아니기 때문이다. 컴파일러는 두 가지 전략을 쓴다.

**`case` 개수가 적으면** 그냥 `string.op_Equality`(즉 `string.Equals`) 호출을 순차로 늘어놓는다.

```il
IL_0001:  ldarg.0
IL_0002:  ldstr      "Red"
IL_0007:  call       bool [System.Runtime]System.String::op_Equality(string, string)
IL_000c:  brtrue.s   IL_0020
IL_000e:  ldarg.0
IL_000f:  ldstr      "Green"
...
```

**`case` 개수가 대여섯 개를 넘어가면** 전략이 바뀐다. 컴파일러는 `<PrivateImplementationDetails>`라는 숨은 타입에 `ComputeStringHash`라는 정적 메서드를 생성하고, 다음 순서로 낮춘다.

1. 입력 문자열의 해시를 계산한다.
2. 그 **해시 값**을 정수 `switch`(점프 테이블 또는 이진 탐색)로 분기한다.
3. 도착한 자리에서 실제 문자열 비교를 **한 번** 해서 해시 충돌이 아닌지 확인한다.

문자열 비교 횟수가 `n`번에서 1번으로 줄어든다. 대신 해시 계산 비용이 붙는다.

> **📌 `ComputeStringHash`는 컴파일러가 만든 코드다**
>
> 디컴파일러로 어셈블리를 열었을 때 `<PrivateImplementationDetails>.ComputeStringHash`라는 메서드가 보이면, 그것은 아무도 작성하지 않은 코드다. 문자열 `switch`를 위해 Roslyn이 생성한 것이다. 배열 초기화 데이터를 담는 `<PrivateImplementationDetails>` 타입은 9.2절에서 이미 만났다. 컴파일러가 만드는 숨은 멤버를 알아보는 것이 IL 읽기의 기본기이며, 56장에서 이 목록을 전부 정리한다.
>
> 해시 임계값(대여섯 개)은 Roslyn의 휴리스틱이며 버전에 따라 바뀔 수 있다. 코드가 그 값에 의존해서는 안 된다.

### `switch`의 패턴은 77장으로

※C# 7부터 `case`에 상수 대신 **패턴**을 쓸 수 있다.

```csharp
switch (x)
{
    case int i:                     // 타입 패턴
        Console.WriteLine ($"int {i}");
        break;
    case string s when s.Length > 3:   // 타입 패턴 + 가드
        Console.WriteLine ($"긴 문자열 {s}");
        break;
    case null:
        Console.WriteLine ("null");
        break;
    default:
        Console.WriteLine ("모르겠다");
        break;
}
```

패턴 `case`는 상수 `case`와 세 가지가 다르다.

| 항목 | 상수 `case` | 패턴 `case` |
|---|---|---|
| 절의 순서 | 무관 (중복은 컴파일 오류) | **유의미하다** — 위에서부터 순서대로 검사 |
| `default`의 위치 | 무관 | 무관 — 어디에 적어도 **언제나 마지막에** 평가된다 |
| 도달 불가 절 | 중복 값은 오류 | 앞선 절이 모두 삼키면 오류 |
| `goto case` | 가능 | 불가능 |

순서가 유의미하다는 사실이 실수의 원천이다.

```csharp
switch (choice)
{
    case int i:                  // 모든 int를 여기서 삼킨다
        break;
    case int i when i == 0:      // 오류 — 도달할 수 없다
        break;
}
```

패턴의 종류(상수·타입·관계·논리·속성·위치·목록), 가드 절과 패턴 변수의 범위, 평가 순서, 패턴이 컴파일되는 형태는 전부 77장의 몫이다. 이 장에서 알아야 할 것은 "`case`에 패턴이 올 수 있고 그때 순서가 의미를 갖는다"까지다.

## 11.3 `switch` 식과 표현식 지향 코드

### 문법 ※C# 8

`switch` **문**은 값을 만들지 않는다. 그래서 "여러 후보 중 하나를 골라 변수에 넣는다"는 아주 흔한 일을 하려면 문이 장황해진다.

```csharp
static string FromRainbowClassic (string colorBand)
{
    switch (colorBand)
    {
        case "Red":    return "#FF0000";
        case "Orange": return "#FF7F00";
        case "Yellow": return "#FFFF00";
        case "Green":  return "#00FF00";
        case "Blue":   return "#0000FF";
        case "Indigo": return "#4B0082";
        case "Violet": return "#9400D3";
        default:       return "#FFFFFF";
    }
}
```

※C# 8의 `switch` **식**은 같은 일을 이렇게 쓴다.

```csharp
static string FromRainbow (string colorBand) => colorBand switch
{
    "Red"    => "#FF0000",
    "Orange" => "#FF7F00",
    "Yellow" => "#FFFF00",
    "Green"  => "#00FF00",
    "Blue"   => "#0000FF",
    "Indigo" => "#4B0082",
    "Violet" => "#9400D3",
    _        => "#FFFFFF"        // '_'는 default에 해당한다 (버림 패턴)
};
```

문법의 차이가 네 군데다.

| 항목 | `switch` 문 | `switch` 식 |
|---|---|---|
| `switch` 키워드 위치 | 대상 **앞** — `switch (x)` | 대상 **뒤** — `x switch` |
| 각 절의 내용 | 문의 나열 | 식 하나 |
| 절의 구분 | `case`/`:`/`break` | `=>`와 쉼표 |
| 기본 절 | `default:` | `_` (버림 패턴) |
| 값 | 없다 | **있다** — 전체가 하나의 식이다 |
| 쓸 수 있는 자리 | 문이 오는 자리 | 식이 오는 자리 전부 |

마지막 줄이 존재 이유다. `switch` 식은 필드 초기화자, 표현식 본문 멤버, LINQ 쿼리의 `select` 절, 다른 식의 인수 — 문이 올 수 없는 모든 자리에 놓을 수 있다.

```csharp
var results = items.Select (x => x.Kind switch
{
    Kind.A => Handle_A(x),
    Kind.B => Handle_B(x),
    _      => Fallback(x)
});
```

### 각 절은 패턴이다

`switch` 식의 왼쪽은 상수가 아니라 **패턴**이다. 상수를 적으면 상수 패턴이 되는 것이고, 타입·관계·논리·속성·튜플 패턴도 전부 쓸 수 있다.

```csharp
string Describe (object o) => o switch
{
    int n when n < 0        => "음수",
    0                       => "영",          // 상수 패턴
    int                     => "양수",        // 타입 패턴 (변수 이름 생략 ※C# 9)
    string { Length: 0 }    => "빈 문자열",   // 속성 패턴
    string s                => $"문자열({s.Length})",
    null                    => "널",
    _                       => "그 외"
};
```

튜플 패턴을 쓰면 값 여러 개를 한 번에 분기할 수 있다.

```csharp
static string RockPaperScissors (string first, string second) => (first, second) switch
{
    ("rock",     "paper")    => "Paper wins.",
    ("rock",     "scissors") => "Rock wins.",
    ("paper",    "rock")     => "Paper wins.",
    ("paper",    "scissors") => "Scissors wins.",
    ("scissors", "rock")     => "Rock wins.",
    ("scissors", "paper")    => "Scissors wins.",
    (_, _)                   => "Tie."
};
```

패턴 문법 전체는 77장이다. 여기서는 "각 절이 패턴이므로 **순서가 유의미하다**"는 사실만 확정해 두면 된다. 위에서부터 순서대로 검사하고, 처음 맞는 절의 값이 전체의 값이 된다.

### 완전성(exhaustiveness) 검사

`switch` 문에는 "모든 경우를 다뤘는가"라는 질문이 없다. 아무 `case`에도 맞지 않으면 그냥 아무 일도 하지 않고 넘어간다. `switch` 식은 다르다. **반드시 값을 하나 내놓아야 하므로**, 어느 절에도 맞지 않는 입력이 있으면 곤란해진다.

컴파일러는 이것을 검사한다.

```csharp
string F (bool b) => b switch
{
    true => "T"
};
// 경고 CS8509: switch 식이 모든 가능한 입력을 처리하지 않습니다 (예: 'false')
```

경고이지 오류가 아니다. 컴파일은 된다. 그리고 `F(false)`를 호출하면 **런타임에 예외가 난다.**

> **⚠️ 매칭 실패 시 던져지는 예외 타입은 대상 프레임워크에 따라 다르다**
>
> 어느 절에도 맞지 않으면 컴파일러가 삽입한 코드가 예외를 던진다. 던져지는 타입은 이렇다.
>
> - `System.Runtime.CompilerServices.SwitchExpressionException` — 이 타입이 존재하는 대상 프레임워크(.NET Core 3.0 이상, .NET 5 이상)에서.
> - `System.InvalidOperationException` — 그 타입이 없는 대상 프레임워크(.NET Framework, `netstandard2.0`)에서.
>
> 멀티 타깃 라이브러리에서 이 예외를 `catch`로 잡으려 한다면 이 차이 때문에 조건부 컴파일이 필요해진다. 애초에 **잡을 일이 없도록 `_` 절을 두는 것**이 옳다.
>
> 이 검사는 `enum`에도 적용된다. `enum`의 모든 멤버를 다뤘어도 컴파일러는 여전히 경고를 낸다 — `enum` 타입의 변수에는 선언되지 않은 정수 값이 들어갈 수 있기 때문이다(20.4절). "모든 멤버를 다뤘으니 안전하다"는 생각은 `enum`에서는 틀린다.

완전성 검사의 정확한 규칙(어떤 패턴 조합이 "전부를 덮는다"고 인정되는가, 널 가능 참조 타입이 어떻게 계산되는가)은 77.14절에서 다룬다.

### 타입 결정 규칙

`switch` 식 전체의 타입은 각 절의 값들로부터 결정된다. 규칙은 조건 연산자와 같다(7.10절).

1. 모든 절의 값 타입 중 **다른 전부가 암시적으로 변환될 수 있는 하나**가 있으면 그것이 결과 타입이다.
2. 그런 타입이 없으면, ※C# 9부터는 **대상 타입**(대입될 변수, 반환 타입, 매개변수 타입)으로의 변환을 각 절이 각자 만족하는지 본다.
3. 둘 다 실패하면 컴파일 오류다.

```csharp
object o = flag switch { true => 1, false => "x" };   // ※C# 9부터 OK — 대상 타입 object
var  v   = flag switch { true => 1, false => "x" };   // 오류 — var에는 대상 타입이 없다
```

`var`를 쓰면 대상 타입이 없으므로 규칙 1만 적용된다. 이 함정은 대상 타입 지정 `new`(10.7절)에서 본 것과 같은 모양이다.

### 컴파일 결과 — 식이라고 특별한 명령이 있지는 않다

`switch` 식도 결국 분기다. 컴파일러는 결과를 담을 임시 지역 변수를 하나 만들고, 각 절에서 그 변수에 값을 넣은 뒤 합류 지점으로 점프한다.

```csharp
static string Name(int n) => n switch
{
    0 => "zero",
    1 => "one",
    2 => "two",
    _ => "?"
};
```

```il
.locals init (string V_0)
IL_0000:  ldarg.0
IL_0001:  switch     ( IL_0016, IL_0021, IL_002c )   // 상수 패턴이 조밀 → 점프 테이블
IL_0011:  br.s       IL_0037
IL_0016:  ldstr      "zero"
IL_001b:  stloc.0
IL_001c:  br.s       IL_003d                          // 합류 지점으로
IL_0021:  ldstr      "one"
IL_0026:  stloc.0
IL_0027:  br.s       IL_003d
IL_002c:  ldstr      "two"
IL_0031:  stloc.0
IL_0032:  br.s       IL_003d
IL_0037:  ldstr      "?"
IL_003c:  stloc.0
IL_003d:  ldloc.0
IL_003e:  ret
```

앞 절에서 본 `switch` 문 버전과 비교하면 차이가 딱 두 가지다 — 임시 지역 변수 `V_0`가 생겼고, 각 절이 `ret` 대신 `stloc` + `br`로 끝난다. **상수 패턴만 쓰면 점프 테이블도 그대로 나온다.** `switch` 식이 문보다 느리다는 말은 근거가 없고, 반대도 마찬가지다.

패턴을 섞어 쓰면 이야기가 달라진다. 타입 패턴은 `isinst`로, 관계 패턴은 비교 분기로, 속성 패턴은 프로퍼티 호출 후 비교로 낮춰지며, 컴파일러는 이 검사들을 공유할 수 있는 만큼 공유해 **결정 트리(decision DAG)** 를 만든다. 그 구조와 성능은 77.15절이다.

> **💡 `switch` 식을 쓸 자리와 쓰지 말 자리**
>
> **쓸 자리** — 모든 갈래가 값 하나를 만들고, 그 값을 변수에 넣거나 반환하는 경우. 이것이 `switch` 식이 설계된 목적이다. `if` 사슬이나 조건 연산자 중첩보다 언제나 낫다.
>
> **쓰지 말 자리** — 갈래마다 여러 문을 실행해야 하는 경우. 억지로 식으로 만들려고 `=>` 오른쪽에 부작용이 있는 메서드 호출을 넣기 시작하면, 값을 만드는 코드와 일을 하는 코드가 뒤섞여 읽기 어려워진다. 그럴 때는 `switch` 문이 옳다.
>
> 판단 기준은 하나다 — **"이 `switch`의 결과값에 이름을 붙일 수 있는가?"** 붙일 수 있으면 식, 없으면 문이다.

> **📌 `switch` 식은 `break`가 없다**
>
> `break`가 필요 없는 이유는 fall-through 자체가 없기 때문이다. 각 절은 값을 하나 만들고 끝나며, 다음 절로 흘러갈 개념이 존재하지 않는다. `goto case`도 없다. 문에서 골칫거리였던 것들이 식에서는 문제 자체가 사라진다.

## 11.4 반복문 — `for` / `foreach` / `while` / `do-while`

### 네 가지 형태

C#의 반복문은 넷이다. `foreach`는 다른 셋과 성격이 달라 11.5절에서 따로 판다. 여기서는 나머지 셋과 `foreach`의 문법적 위치를 정리한다.

```csharp
// while — 조건을 먼저 본다
int i = 0;
while (i < 3) { Console.Write (i); i++; }              // 012

// do-while — 본문을 먼저 실행한다
int j = 0;
do { Console.Write (j); j++; } while (j < 3);          // 012 — 세미콜론에 주의

// for — 초기화·조건·증가를 한 줄에
for (int k = 0; k < 3; k++)
    Console.Write (k);         // 012

// foreach — 열거 가능한 것을 훑는다
foreach (char c in "beer")
    Console.Write (c);         // beer
```

`while`과 `do-while`의 차이는 **본문이 최소 몇 번 실행되는가** 하나뿐이다. `while`은 0번일 수 있고 `do-while`은 반드시 1번 이상이다. 사용자 입력을 받아 검증하는 코드처럼 "일단 한 번은 해야 하는" 일에 `do-while`이 맞는다.

```csharp
string? password;
do
{
    Console.Write ("비밀번호: ");
    password = Console.ReadLine();
}
while (password != actualPassword);
```

### `for`의 세 절

```text
for (초기화절; 조건절; 증가절)
    문 또는 문 블록
```

| 절 | 언제 실행되는가 | 생략하면 |
|---|---|---|
| 초기화절 | 루프 진입 전 정확히 한 번 | 아무 일도 안 한다 |
| 조건절 | 매 회차 **본문 실행 전** | `true`로 간주된다 |
| 증가절 | 매 회차 **본문 실행 후** | 아무 일도 안 한다 |

세 절 모두 생략할 수 있다. `for (;;)`는 무한 루프이고 `while (true)`와 정확히 같은 IL이 된다.

초기화절에는 같은 타입의 변수를 여러 개 선언할 수 있고, 증가절에는 쉼표로 여러 식을 나열할 수 있다.

```csharp
// 피보나치 수 10개
for (int i = 0, prevFib = 1, curFib = 1; i < 10; i++)
{
    Console.WriteLine (prevFib);
    int newFib = prevFib + curFib;
    prevFib = curFib; curFib = newFib;
}
```

초기화절에서 선언한 변수의 범위는 `for` 문 전체(세 절 + 본문)이며, 루프가 끝나면 사라진다.

```csharp
for (int i = 0; i < 4; i++) { }
Console.WriteLine (i);        // 오류 CS0103 — i는 여기 없다
```

### 컴파일 결과 — 세 형태는 하나로 수렴한다

세 반복문의 IL을 나란히 놓으면 구조가 같다는 것이 드러난다.

**`while` 루프.**

```csharp
int i = 0;
while (i < 3) { Console.Write(i); i++; }
```

```il
IL_0000:  ldc.i4.0
IL_0001:  stloc.0
IL_0002:  br.s       IL_000e        // ① 조건 검사로 먼저 점프
IL_0004:  ldloc.0                   // ② 본문
IL_0005:  call       void [System.Console]System.Console::Write(int32)
IL_000a:  ldloc.0
IL_000b:  ldc.i4.1
IL_000c:  add
IL_000d:  stloc.0
IL_000e:  ldloc.0                   // ③ 조건
IL_000f:  ldc.i4.3
IL_0010:  blt.s      IL_0004        // 참이면 본문으로 되돌아간다
```

**`for` 루프.**

```csharp
for (int i = 0; i < 3; i++) Console.Write(i);
```

```il
IL_0000:  ldc.i4.0
IL_0001:  stloc.0                   // 초기화절
IL_0002:  br.s       IL_000e
IL_0004:  ldloc.0                   // 본문
IL_0005:  call       void [System.Console]System.Console::Write(int32)
IL_000a:  ldloc.0                   // 증가절
IL_000b:  ldc.i4.1
IL_000c:  add
IL_000d:  stloc.0
IL_000e:  ldloc.0                   // 조건절
IL_000f:  ldc.i4.3
IL_0010:  blt.s      IL_0004
```

**IL이 한 바이트도 다르지 않다.** `for`는 `while` 위에 얹힌 순수한 문법 설탕이다.

**`do-while` 루프.**

```csharp
int i = 0;
do { Console.Write(i); i++; } while (i < 3);
```

```il
IL_0000:  ldc.i4.0
IL_0001:  stloc.0
IL_0002:  ldloc.0                   // 본문 — 진입 분기가 없다
IL_0003:  call       void [System.Console]System.Console::Write(int32)
IL_0008:  ldloc.0
IL_0009:  ldc.i4.1
IL_000a:  add
IL_000b:  stloc.0
IL_000c:  ldloc.0                   // 조건
IL_000d:  ldc.i4.3
IL_000e:  blt.s      IL_0002
```

세 IL의 차이는 딱 하나다.

| 형태 | 진입 시 `br` | 회차당 분기 | 본문 최소 실행 횟수 |
|---|---|---|---|
| `while` | 있다 (1회) | 조건 분기 1회 | 0 |
| `for` | 있다 (1회) | 조건 분기 1회 | 0 |
| `do-while` | **없다** | 조건 분기 1회 | 1 |

> **📌 왜 조건이 루프 아래에 있는가 — 루프 회전(loop rotation)**
>
> 소스에서는 조건이 위에 있는데 IL에서는 아래에 있다. 컴파일러가 루프를 **회전**시켰기 때문이다.
>
> 조건을 위에 그대로 두면 회차마다 분기가 두 번 필요하다 — 조건 분기 하나(거짓이면 나간다)와 본문 끝의 무조건 분기 하나(조건으로 되돌아간다). 조건을 아래로 내리면 **회차당 분기가 하나로 줄어든다.** 진입 시 한 번의 `br`만 추가로 지불하면 된다. 회차가 많을수록 이득이다.
>
> 그래서 `do-while`이 이론상 가장 저렴하다 — 진입 `br` 하나가 없다. 실측으로 이 차이가 보이는 경우는 거의 없지만, 세 형태가 왜 같은 모양으로 수렴하는지 이해하는 데는 도움이 된다. **성능 때문에 반복문 형태를 고르는 것은 낭비다. 의미가 맞는 것을 골라라.**

### Debug 빌드는 다르다

위 IL은 전부 Release 빌드(`-c Release`, 최적화 켜짐) 기준이다. Debug 빌드에서는 다음이 추가된다.

- 각 문 사이에 `nop` — 중단점을 걸 자리를 만든다.
- 조건 결과를 담는 임시 지역 변수와 `stloc`/`ldloc` 한 쌍 — 디버거에서 조건식 결과를 볼 수 있게 한다.
- 지역 변수의 레지스터 승격 없음 — 전부 스택 슬롯에 남는다.

> **⚠️ Debug 빌드로 성능을 측정하지 마라**
>
> Debug 빌드의 루프는 Release 빌드보다 몇 배 느릴 수 있다. `nop` 때문이 아니라, 최적화가 꺼져 있어 JIT이 지역 변수를 레지스터에 올리지 않고 인라이닝도 하지 않기 때문이다. 벤치마크는 반드시 Release 빌드로, 그리고 BenchmarkDotNet 같은 도구로 해야 한다(67장).

### 런타임 동작 — 반복문이 JIT에게 주는 정보

반복문은 JIT이 가장 공들여 다루는 구조다. 세 가지가 일어난다.

**분기 예측.** 루프 조건 분기는 "거의 언제나 참"이라는 아주 예측하기 쉬운 패턴이라, CPU의 분기 예측기가 거의 100% 맞춘다. 예측이 빗나가는 것은 루프를 빠져나가는 마지막 한 번뿐이다. 그래서 반복문의 분기 비용은 실질적으로 0에 가깝다.

**경계 검사 제거.** `for (int i = 0; i < a.Length; i++)` 모양은 JIT이 인식하는 관용구이며, 루프 안의 `a[i]` 경계 검사를 통째로 없앤다. 이 규칙과 그것을 망치는 코드 모양은 9.5절에서 이미 표로 정리했다.

**OSR(On-Stack Replacement).** 긴 루프가 Tier-0 코드로 실행되고 있으면 .NET 7 이상의 런타임이 **실행 중인 루프를 최적화된 버전으로 갈아 끼운다**. 그전에는 "메서드가 여러 번 호출되어야만 Tier-1로 승격"되었기 때문에, `Main`에서 한 번 도는 1억 회 루프는 영원히 최적화되지 않았다. 자세히는 55.3절에서 다룬다.

### 어느 반복문을 쓸 것인가

| 상황 | 선택 | 이유 |
|---|---|---|
| 컬렉션의 모든 요소를 순서대로 | `foreach` | 인덱스 실수가 불가능하다 |
| 인덱스가 필요하다 | `for` | 인덱스 변수를 직접 다룬다 |
| 역순·건너뛰기·두 배열 동시 순회 | `for` | `foreach`는 앞으로 한 칸씩만 간다 |
| 반복 횟수를 미리 모른다 | `while` | 조건이 상태에 달려 있다 |
| 최소 한 번은 실행해야 한다 | `do-while` | 검증 후 재시도 패턴 |
| 무한 루프 | `while (true)` | `for (;;)`보다 의도가 분명하다 |

> **⚠️ 반복문 안에서 컬렉션을 수정하지 마라**
>
> ```csharp
> foreach (var x in list)
>     if (x.Expired) list.Remove(x);      // InvalidOperationException
> ```
>
> `List<T>`를 포함한 BCL의 주요 컬렉션은 내부에 버전 번호를 두고, 열거 중에 구조가 바뀌면 다음 `MoveNext()`에서 `InvalidOperationException`을 던진다. 자세한 메커니즘은 11.5절에서 IL과 함께 본다.
>
> `for` 루프로 바꾸면 예외는 나지 않지만 **인덱스가 밀린다.** 앞에서 지우면 뒤의 요소가 한 칸씩 당겨져 하나씩 건너뛰게 된다. 안전한 방법은 두 가지다 — 뒤에서부터 도는 `for (int i = list.Count - 1; i >= 0; i--)`, 또는 `list.RemoveAll(x => x.Expired)`.

> **💡 중괄호 없는 한 줄 반복문의 진짜 위험**
>
> ```csharp
> for (int i = 0; i < 4; i++)
>     Console.WriteLine (i);
>     Console.WriteLine (i + 1);     // 루프 밖. 게다가 i가 범위 밖이라 컴파일 오류
> ```
>
> 이 경우는 운이 좋아 컴파일 오류가 난다. 루프 변수를 쓰지 않는 줄을 추가했다면 오류 없이 조용히 잘못 동작한다. 문제는 "한 줄"이 아니라 **한 줄이 두 줄이 되는 순간**이다. 코드는 자란다. 처음부터 중괄호를 써라.

## 11.5 `foreach`가 실제로 컴파일되는 형태 — 덕 타이핑된 열거자

이 절이 이 장의 핵심이다. `foreach` 한 줄은 C#에서 가장 짧게 쓰이면서 가장 많이 감춰진 문법이며, 같은 한 줄이 **정적 타입에 따라 완전히 다른 코드로 컴파일된다.** 그 차이가 힙 할당과 가상 호출의 유무를 가른다.

### 문법과 반복 변수의 성질

```csharp
foreach (char c in "beer")
    Console.WriteLine (c);
```

`c`는 **읽기 전용**이다. 대입할 수 없다.

```csharp
foreach (char c in "beer")
    c = 'x';                     // 오류 CS1656 — foreach 반복 변수는 대입할 수 없다
```

읽기 전용인 이유는 뒤에서 볼 낮춤 결과를 보면 자명해진다 — `c`는 매 회차 열거자의 `Current`에서 **복사되어 채워지는** 변수라서, 거기에 대입해 봐야 원본 컬렉션에는 아무 영향이 없다. 컴파일러는 그 무의미한 대입을 아예 금지한다.

`var`를 쓸 수 있고, 명시적 타입을 적으면 요소마다 **명시적 캐스트가 삽입된다**(이것이 배열 공변성 사고의 통로 중 하나다 — 9.6절).

### 컴파일러가 `foreach`를 보고 하는 일

`foreach`에게 컴파일러는 다음 순서로 결정한다.

```text
foreach (T v in E)
         │
         ↓
 ┌─────────────────────────────────────────────────────┐
 │ ① E의 정적 타입이 1차원 배열인가?                    │
 │    → 인덱스 for 루프로 낮춘다. 열거자 없음           │
 ├─────────────────────────────────────────────────────┤
 │ ② E의 정적 타입이 string인가?                        │
 │    → Length / this[int] 기반 for 루프로 낮춘다       │
 ├─────────────────────────────────────────────────────┤
 │ ③ E의 타입에 쓸 수 있는 GetEnumerator()가 있는가?    │
 │    (인스턴스 메서드 → 없으면 확장 메서드 ※C# 9)      │
 │    → 그 반환 타입으로 열거자 패턴을 검사한다         │
 ├─────────────────────────────────────────────────────┤
 │ ④ E가 IEnumerable<T>를 구현하는가?                   │
 │    → 인터페이스 경로                                 │
 ├─────────────────────────────────────────────────────┤
 │ ⑤ E가 비제네릭 IEnumerable을 구현하는가?             │
 │    → 인터페이스 경로 + object에서 T로 캐스트         │
 ├─────────────────────────────────────────────────────┤
 │ ⑥ E가 dynamic인가? → 런타임에 ④/⑤를 다시 시도       │
 ├─────────────────────────────────────────────────────┤
 │ 전부 실패 → 컴파일 오류 CS1579                       │
 └─────────────────────────────────────────────────────┘
```

**③이 ④보다 먼저다.** 이것이 결정적이다. 타입에 `GetEnumerator()`라는 이름의 적절한 메서드가 있으면, 그 타입이 `IEnumerable<T>`를 구현하든 말든 컴파일러는 **인터페이스를 쳐다보지도 않고** 그 메서드를 쓴다. 인터페이스 구현 여부는 세 번째 관심사다.

이 규칙을 **덕 타이핑**(duck typing)이라고 부른다 — "오리처럼 걷고 오리처럼 운다면 오리로 취급한다". 컴파일러가 확인하는 것은 계약(인터페이스)이 아니라 **모양(멤버의 존재)** 이다.

### 열거자 패턴의 요구사항

③에서 컴파일러가 확인하는 것을 정확히 적으면 이렇다.

| 요구사항 | 세부 |
|---|---|
| `GetEnumerator()` | 인수 없이 호출 가능하고, 접근 가능해야 한다. 반환 타입은 무엇이든 된다 |
| 반환 타입의 `Current` | 접근 가능한 **getter**를 가진 프로퍼티여야 한다. 타입은 무엇이든 된다 |
| 반환 타입의 `MoveNext()` | 인수 없이 호출 가능하고 `bool`을 반환해야 한다 |
| (선택) `Dispose()` | 정리가 필요하면 — 규칙은 아래 표 참조 |

`IEnumerable<T>`도 `IEnumerator<T>`도 구현할 필요가 없다. 인터페이스는 이 모양을 **형식화한 것**일 뿐이며, 컴파일러가 요구하는 것은 모양 그 자체다.

> **📌 왜 인터페이스가 아니라 모양을 보는가**
>
> 두 가지 이유가 있다.
>
> 첫째, **성능.** `IEnumerator<T>`는 참조 타입 인터페이스이므로 구조체 열거자를 인터페이스로 받으면 박싱된다(18.6절). 모양만 보면 구조체를 구조체 그대로 쓸 수 있고, 그러면 힙 할당이 0이 되며 호출이 `callvirt`가 아니라 `call`이 된다.
>
> 둘째, **인터페이스로 표현할 수 없는 타입.** `Span<T>`의 열거자는 `ref struct`다. `ref struct`는 (※C# 13 이전까지) 인터페이스를 구현할 수 없으므로, 인터페이스만 봤다면 `Span<T>`에는 `foreach`를 아예 쓸 수 없었을 것이다. 덕 타이핑 덕분에 문제가 생기지 않았다.
>
> 이 설계 판단은 C# 1.0 때 내려졌고, 20년 뒤 `Span<T>`를 가능하게 만들었다. 열거의 의미론 전체는 28.1절에서 다시 다룬다.

### 일반 형태의 낮춤

③ 경로에서 컴파일러가 만드는 코드를 C#으로 되돌리면 이렇다.

```csharp
// 원본
foreach (T v in E)
    본문;

// 낮춘 결과 (개념적)
{
    var enumerator = E.GetEnumerator();
    try
    {
        while (enumerator.MoveNext())
        {
            T v = (T)enumerator.Current;      // 필요하면 변환
            본문;
        }
    }
    finally
    {
        // 아래 표의 규칙에 따라 Dispose 호출 (또는 finally 자체가 없음)
    }
}
```

주목할 점 셋.

- **`E`는 한 번만 평가된다.** `foreach (var x in GetList())`는 `GetList()`를 한 번만 부른다.
- **`v`의 선언이 `while` 안에 있다.** 이것이 ※C# 5에서 바뀐 지점이며, 이 절 뒤쪽에서 따로 다룬다.
- **`try`/`finally`가 생긴다.** 다만 언제나 생기지는 않는다.

### `Dispose`가 호출되는 조건 — 네 가지 경우

`finally`가 만들어지는지, 만들어진다면 어떤 코드가 들어가는지는 **열거자 타입**이 무엇이냐로 결정된다.

| 열거자 타입 | `finally` | 그 안의 코드 |
|---|---|---|
| `IDisposable`을 구현한 **구조체** | 생성됨 | `constrained.` 접두사 + `callvirt Dispose()` — 박싱 없음 |
| `IDisposable`을 구현한 **봉인 클래스** | 생성됨 | null 검사 후 `callvirt Dispose()` |
| `IDisposable`을 구현한 **비봉인 클래스** | 생성됨 | null 검사 후 `callvirt Dispose()` |
| `IDisposable`을 구현하지 않은 **구조체** | **생성 안 됨** | — |
| `IDisposable`을 구현하지 않은 **봉인 클래스** | **생성 안 됨** | — |
| `IDisposable`을 구현하지 않은 **비봉인 클래스** | 생성됨 | `isinst IDisposable` **런타임 검사** 후 있으면 호출 |
| `Dispose()` 메서드를 가진 `ref struct` ※C# 8 | 생성됨 | 패턴 기반 `call Dispose()` |

마지막에서 두 번째 줄이 함정이다. **비봉인 클래스 열거자는 `IDisposable`을 구현하지 않아도 회차마다가 아닌 루프 종료 시 한 번, 런타임 타입 검사 비용을 낸다.** 파생 타입이 `IDisposable`을 구현했을 수 있기 때문에 컴파일러가 정적으로 결론을 낼 수 없어서다. 열거자를 클래스로 만들 거라면 `sealed`를 붙여라.

> **💡 열거자를 직접 만들 때의 체크리스트**
>
> 1. **구조체로 만들어라.** 힙 할당이 사라진다.
> 2. **`IEnumerator<T>`를 구현하지 않아도 된다.** `foreach`만 지원할 목적이면 `Current`/`MoveNext()`만 있으면 된다. 인터페이스를 구현하면 LINQ와의 호환성을 얻는 대신, 인터페이스로 받는 순간 박싱된다.
> 3. **정리할 것이 없으면 `IDisposable`을 구현하지 마라.** `finally` 블록이 통째로 사라진다.
> 4. **클래스로 만들어야 한다면 `sealed`를 붙여라.** 런타임 타입 검사가 사라진다.
>
> `List<T>.Enumerator`가 정확히 1번과 그 반대(인터페이스도 구현)를 동시에 만족시키는 방식으로 만들어져 있다 — 구조체이면서 `IEnumerator<T>`를 명시적으로 구현했다. 그래서 `List<T>`로 받으면 할당이 없고 `IEnumerable<T>`로 받으면 박싱이 생긴다(1.3절에서 IL로 비교했다).

### 경로 ① — 배열은 인덱스 루프가 된다

1차원 배열에 대한 `foreach`는 열거자를 **전혀 만들지 않는다.** 컴파일러가 `for` 루프로 직접 낮춘다.

```csharp
static int Sum(int[] a)
{
    int t = 0;
    foreach (int x in a) t += x;
    return t;
}
```

낮춘 결과는 이것과 같다.

```csharp
int t = 0;
int[] tmp = a;
for (int i = 0; i < tmp.Length; i++)
{
    int x = tmp[i];
    t += x;
}
```

IL로 확인하면 열거자도 `try`/`finally`도 없다.

```il

  IL_0001:  stloc.0
  IL_0002:  ldarg.0
  IL_0003:  stloc.1               // tmp = a  (배열 참조를 한 번만 평가)
  IL_0004:  ldc.i4.0
  IL_0005:  stloc.2               // i = 0
  IL_0006:  br.s       IL_0018
  IL_0008:  ldloc.1
  IL_0009:  ldloc.2
  IL_000a:  ldelem.i4             // x = tmp[i]
  IL_000b:  stloc.3
  IL_000c:  ldloc.0
  IL_000d:  ldloc.3
  IL_000e:  add
  IL_000f:  stloc.0               // t += x
  IL_0010:  ldloc.2
  IL_0011:  ldc.i4.1
  IL_0012:  add
  IL_0013:  stloc.2               // i++
  IL_0018:  ldloc.2
  IL_0019:  ldloc.1

```

`newobj`도 `callvirt`도 `.try`도 없다. **손으로 쓴 `for` 루프와 IL이 같다.** 9.5절에서 "`foreach`가 `for`보다 느리지 않다"고 한 근거가 이것이다. `ldlen`을 조건절에 그대로 둔 형태이므로 JIT의 경계 검사 제거 관용구에도 정확히 들어맞는다.

> **⚠️ 배열을 `IEnumerable<T>`에 담는 순간 이 최적화가 통째로 사라진다**
>
> ```csharp
> int[] a = { 1, 2, 3 };
> Sum(a);                        // 배열 경로 — 할당 0
> SumViaInterface(a);            // 인터페이스 경로 — 열거자 객체 할당
>
> static int SumViaInterface(IEnumerable<int> e) { ... }
> ```
>
> 컴파일러가 보는 것은 **정적 타입**이다. 매개변수 타입이 `IEnumerable<int>`면 그 안에서는 배열이라는 사실을 모른다. 런타임에 실제로 배열이 들어와도 인터페이스 경로 그대로다.
>
> "매개변수는 가장 일반적인 타입으로 받아라"라는 조언은 API 설계 원칙으로는 옳지만(24.16절), 핫 패스에서는 이 비용을 안다는 전제 위에서만 옳다. 다차원 배열도 마찬가지로 특수 경로가 아니다 — `GetLowerBound`/`GetUpperBound` 기반의 중첩 루프로 낮춰진다(9.4절).

### 경로 ② — 문자열도 특수 처리된다

`string`은 `IEnumerable<char>`를 구현하지만, `foreach`에서는 그 경로를 타지 않는다. 컴파일러가 인덱서 기반 루프로 낮춘다.

```csharp
foreach (char c in s) { ... }

// 낮춘 결과 (개념적)
for (int i = 0; i < s.Length; i++)
{
    char c = s[i];
    ...
}
```

`get_Length`와 `get_Chars` 호출만 남고 열거자 객체는 생기지 않는다. 이 두 접근자는 JIT이 인라인하는 아주 작은 메서드라, 결과적으로 문자열 순회도 배열 순회와 거의 같은 기계어가 된다. 문자열을 `IEnumerable<char>` 변수에 담으면 이 최적화도 그대로 날아간다.

### 경로 ③ — 구조체 열거자 (패턴 경로)

`List<T>`가 대표적이다. `List<T>.GetEnumerator()`는 `List<T>.Enumerator`라는 **구조체**를 반환하고, 컴파일러는 그 구조체를 지역 슬롯에 그대로 놓는다. 결과 IL은 1.3절에서 이미 줄 단위로 읽었으므로 여기서는 요점만 반복한다.

- 열거자가 `.locals init`에 `valuetype`으로 잡힌다 → **힙 할당 0**.
- `ldloca`로 주소만 실어 `call`한다 → **가상 디스패치 없음**, 구조체 복사 없음.
- `List<T>.Enumerator`가 `IDisposable`을 구현하므로 `finally`가 생기고, 그 안은 `constrained. callvirt`다 → **박싱 없음**.

`Dictionary<K,V>`, `HashSet<T>`, `Queue<T>`, `Stack<T>`, `ImmutableArray<T>` 등 BCL의 주요 컬렉션은 전부 같은 방식으로 구조체 열거자를 제공한다. 이것이 "구체 타입으로 받으면 빠르다"의 실체다.

### 경로 ④ — 인터페이스 경로

`IEnumerable<T>`로 받으면 컴파일러가 고를 수 있는 것이 인터페이스 메서드뿐이다. IL의 차이는 1.3절의 표에 정리되어 있다. 세 가지가 추가된다.

1. **힙 할당** — `GetEnumerator()`가 호출당하는 쪽 안에서 열거자를 힙에 만들거나 박싱한다. 호출하는 쪽 IL에는 `newobj`가 안 보이는데도 할당이 일어나는 이유가 이것이다.
2. **인터페이스 디스패치** — 요소마다 `callvirt`가 두 번(`MoveNext`, `get_Current`).
3. **인라이닝 실패** — 호출 대상이 정적으로 정해지지 않아 JIT이 본문을 펼쳐 넣지 못한다. 가드된 역가상화(55.5절)가 도와주기도 하지만, 이미 할당된 객체는 되돌릴 수 없다.

세 경로를 한 표로 놓으면 이렇다.

| 항목 | 배열/문자열 경로 | 구조체 열거자 경로 | 인터페이스 경로 |
|---|---|---|---|
| 열거자 객체 | 없음 | 스택의 구조체 | **힙 객체 1개** |
| `MoveNext` 호출 | 없음 (인덱스 증가) | `call` | `callvirt` |
| `Current` 접근 | `ldelem` / `get_Chars` | `call` (인라인됨) | `callvirt` |
| `try`/`finally` | 없음 | 있음 (`constrained.`) | 있음 (null 검사 포함) |
| JIT 인라이닝 | 해당 없음 | 매우 잘 됨 | 거의 안 됨 |
| 경계 검사 제거 | 됨 | 열거자 내부에서 됨 | 안 됨 |

정확한 할당 바이트 수와 그것이 GC에 미치는 영향은 63.9절의 「숨은 할당 카탈로그」에서 다룬다.

### `Span<T>`와 `ref struct` 열거자

`Span<T>`와 `ReadOnlySpan<T>`의 `GetEnumerator()`는 `ref struct`인 열거자를 반환한다. 이 열거자의 `Current`는 값이 아니라 **`ref T`** 를 반환한다 — 요소를 복사하지 않고 그 자리를 가리킨다.

```csharp
Span<int> span = stackalloc int[4] { 1, 2, 3, 4 };
foreach (int x in span)         // x는 복사본
    Console.Write(x);

foreach (ref int x in span)     // ※C# 7.3 — x는 원본 슬롯의 별칭
    x *= 2;                     // 컬렉션을 실제로 수정한다
```

`foreach (ref var x in ...)`와 `foreach (ref readonly var x in ...)`는 ※C# 7.3에서 추가되었고, `Current`가 `ref`를 반환하는 열거자에 대해서만 쓸 수 있다. 이때만 반복 변수가 읽기 전용이 아니게 된다 — 정확히는 반복 변수 자체는 여전히 재바인딩할 수 없고, 그것이 가리키는 **저장 위치**에 쓸 수 있는 것이다(10.3절).

`ref struct` 열거자가 `foreach`에서 동작하는 것은 순전히 덕 타이핑 덕분이다. `ref struct`는 인터페이스를 구현할 수 없었으므로(※C# 13에서 완화되었다), 인터페이스 기반 규칙만 있었다면 불가능했을 일이다.

배열과 문자열은 컴파일러가 아는 특수 경로이고, `List<T>`와 `Span<T>`는 **라이브러리가 제공한 구조체 열거자를 패턴 경로로 쓰는 것**이다. 컴파일러의 특별 대우가 아니라 설계의 결과다.

### 확장 메서드 `GetEnumerator` ※C# 9

C# 9부터 `GetEnumerator()`가 **확장 메서드**여도 된다. 남이 만든 타입, 내가 고칠 수 없는 타입에 `foreach`를 붙일 수 있다.

```csharp
public static class Ext
{
    public static IEnumerator<int> GetEnumerator (this Range r)
    {
        for (int i = r.Start.Value; i < r.End.Value; i++) yield return i;
    }
}

foreach (int i in 1..5)          // ※C# 9 — 확장 메서드 덕분에 컴파일된다
    Console.Write(i);
```

인스턴스 메서드가 우선이고, 없을 때만 확장 메서드를 찾는다.

### `foreach` 변수의 캡처 규칙이 바뀐 이유 ※C# 5

C# 5 이전에는 `foreach`의 반복 변수가 루프 **바깥**에 한 번 선언되고 회차마다 값만 갈렸다. 즉 낮춘 결과가 이랬다.

```csharp
// C# 4 이하의 낮춤
T v;                             // 루프 바깥
while (e.MoveNext())
{
    v = e.Current;
    본문;
}
```

이것이 람다와 만나면 재앙이 된다.

```csharp
var actions = new List<Action>();
foreach (int i in new[] { 1, 2, 3 })
    actions.Add (() => Console.Write (i));

foreach (var a in actions) a();
```

- **C# 4 이하의 출력: `333`** — 세 람다가 **같은 변수 하나**를 캡처했다. 루프가 끝난 시점에 그 변수의 값은 3이다.
- **C# 5 이상의 출력: `123`** — 회차마다 별도의 변수가 만들어지고, 세 람다가 각기 다른 변수를 캡처한다.

C# 5는 반복 변수의 선언을 **루프 안**으로 옮겼다. 이것은 명백한 **호환성 깨는 변경**이었고, C# 팀이 그것을 알면서도 감행했다. 이유는 하나다 — 옛 동작을 의도해서 쓰는 코드가 사실상 없었기 때문이다. `333`이 나오는 코드는 거의 언제나 버그였다.

> **⚠️ `for` 루프의 변수는 바뀌지 않았다**
>
> ```csharp
> var actions = new List<Action>();
> for (int i = 0; i < 3; i++)
>     actions.Add (() => Console.Write (i));
> foreach (var a in actions) a();      // 333 — 지금도 그렇다
> ```
>
> `for`의 초기화절에서 선언한 변수는 **루프 전체에 걸쳐 하나**다. 그것이 `for`의 의미론이다 — 증가절이 그 변수를 갱신해야 하므로 회차마다 새 변수를 만들 수가 없다. C# 5의 변경은 `foreach`에만 적용되었다.
>
> `for`에서 회차별 캡처가 필요하면 본문 안에 지역 변수를 하나 만들어 복사하라.
>
> ```csharp
> for (int i = 0; i < 3; i++)
> {
>     int copy = i;                    // 회차마다 새 변수
>     actions.Add (() => Console.Write (copy));   // 012
> }
> ```
>
> 클로저가 무엇을 캡처하는지, 컴파일러가 만드는 디스플레이 클래스가 어떻게 생겼는지는 26.10절에서 다룬다.

> **📌 이 변경은 컴파일러 버전이 아니라 언어 버전에 달려 있다**
>
> 이 동작은 프로젝트의 `<LangVersion>`이 아니라 **컴파일러가 적용하는 언어 규칙**으로 결정된다. 최신 SDK로 빌드하면 C# 5 이후 동작이 나온다. 레거시 코드베이스를 최신 SDK로 옮길 때 `333`을 기대하던 코드가 있었다면 동작이 바뀐다 — 실제로 그런 코드는 거의 없지만, 이 변경이 있었다는 사실 자체는 알아 둘 가치가 있다. C# 버전별 변경 목록은 76.4절이다.

### 열거 중 컬렉션을 수정하면

BCL의 주요 컬렉션은 내부에 `_version` 필드를 두고, 구조를 바꾸는 연산(`Add`, `Remove`, `Clear`, `Insert`)마다 그것을 증가시킨다. 열거자는 생성 시점의 버전을 스냅샷으로 들고 있다가 `MoveNext()`에서 비교한다.

```csharp
// List<T>.Enumerator.MoveNext()의 개념적 구현
public bool MoveNext()
{
    if (_version != _list._version)
        throw new InvalidOperationException("컬렉션이 수정되었습니다");
    ...
}
```

그래서 다음 코드는 예외로 끝난다.

```csharp
foreach (var x in list)
    if (x.Expired) list.Remove(x);      // InvalidOperationException
```

`List<T>`의 요소 **값만** 바꾸는 것(`list[0] = newValue`)은 버전을 올리지 않으므로 예외가 나지 않는다. 다만 `foreach`의 반복 변수는 이미 복사된 값이라 그 변경이 현재 회차에 반영되지는 않는다. 배열은 버전 검사가 아예 없어서 열거 중 수정해도 예외가 나지 않는다 — 대신 무엇이 보일지는 타이밍에 달린다.

## 11.6 점프문 — `break` / `continue` / `goto` / `return` / `throw`

### 다섯 개의 점프문

| 문 | 무엇을 하는가 | 어디서 쓸 수 있는가 |
|---|---|---|
| `break;` | 가장 가까운 반복문 또는 `switch`를 빠져나간다 | 반복문, `switch` 안 |
| `continue;` | 남은 본문을 건너뛰고 다음 회차로 간다 | 반복문 안 |
| `goto <레이블>;` | 같은 메서드 안의 레이블로 점프한다 | 어디서나 (제약 있음) |
| `goto case <상수>;` / `goto default;` | `switch`의 다른 절로 점프한다 | `switch` 안 |
| `return;` / `return 식;` | 메서드를 끝낸다 | `finally` 안을 제외한 어디서나 |
| `throw 식;` | 예외를 던진다 | 어디서나 |

`yield return`과 `yield break`도 점프문의 일종이지만, 그것은 반복자 메서드의 상태 기계를 만드는 완전히 다른 메커니즘이므로 28장의 몫이다.

> **⚠️ 점프문은 `try` 문의 신뢰성 규칙을 따른다**
>
> 두 가지 규칙이 있다.
>
> 1. **`try` 블록 밖으로 나가는 점프는 그 `try`의 `finally` 블록을 반드시 먼저 실행한다.** `break`든 `return`이든 `goto`든 마찬가지다.
> 2. **`finally` 블록 안에서 밖으로 점프할 수 없다.** `return`, `break`, `continue`, `goto` 전부 금지다. 유일한 예외는 `throw`다.
>
> 두 번째 규칙 때문에 `finally` 안에 `return`을 쓸 수 없다. 이것은 "예외를 삼키는 `finally`"라는 고전적 버그를 언어 차원에서 막은 것이다. 자세한 배경은 32.2절이다.

### `break` — 하나만 빠져나간다

```csharp
int x = 0;
while (true)
{
    if (x++ > 5)
        break;               // 이 while만 빠져나간다
}
// break 다음 실행 지점
```

`break`는 **가장 안쪽의** 반복문 또는 `switch` 하나만 빠져나간다. 중첩 루프 두 개를 한 번에 빠져나가는 문법은 C#에 없다(Java의 레이블 `break`가 없다).

`switch` 안의 반복문에서 `break`를 쓰면 반복문을 빠져나가고, 반복문 안의 `switch`에서 `break`를 쓰면 `switch`를 빠져나간다. **가장 가까운 것**이 규칙이다. 이 때문에 `switch` 안에서 감싸는 루프를 빠져나가고 싶으면 `break`로는 안 되고 `goto`나 플래그 변수가 필요하다.

### `continue` — `for`의 증가절은 실행된다

```csharp
for (int i = 0; i < 10; i++)
{
    if ((i % 2) == 0)
        continue;            // 짝수는 건너뛴다
    Console.Write (i + " ");
}
// 출력: 1 3 5 7 9
```

`for`에서 `continue`하면 **증가절이 실행된 뒤** 조건절로 간다. 이것이 `while`로 옮겨 쓸 때의 함정이다.

> **⚠️ `for`를 `while`로 바꾸면서 `continue`를 그대로 두면 무한 루프가 된다**
>
> ```csharp
> int i = 0;
> while (i < 10)
> {
>     if ((i % 2) == 0)
>         continue;            // i++를 건너뛴다 → 영원히 i는 0
>     Console.Write (i);
>     i++;
> }
> ```
>
> `while`에는 증가절이 없으므로 `continue`가 곧장 조건으로 간다. `i++`가 본문 끝에 있으니 실행되지 않는다. 프로그램이 멈춘다.
>
> **`continue`가 있는 루프를 리팩터링할 때는 증가 코드가 어디에 있는지부터 확인하라.** 이것이 `for`가 증가절을 머리에 모아 두는 이유이기도 하다 — 어떤 경로로 회차가 끝나든 증가는 보장된다.

### `goto` — 있지만 거의 쓰지 않는다

```csharp
int i = 1;
startLoop:
if (i <= 5)
{
    Console.Write (i + " ");
    i++;
    goto startLoop;
}
// 출력: 1 2 3 4 5
```

레이블은 콜론을 붙인 식별자이며, 문 앞에 놓인다. `goto`의 제약은 이렇다.

- 같은 메서드 안의 레이블로만 갈 수 있다.
- **블록 안으로 뛰어들 수 없다.** 밖으로 나가는 것만 된다.
- `finally` 블록 밖으로 나갈 수 없다.
- `try` 밖으로 나가면 `finally`가 실행된다.

`goto`가 정당한 경우는 드물지만 존재한다. 세 가지다.

**첫째, 중첩 루프를 한 번에 빠져나갈 때.**

```csharp
for (int i = 0; i < n; i++)
    for (int j = 0; j < m; j++)
        if (grid[i, j] == target)
            goto found;
Console.WriteLine ("없다");
goto done;

found:
Console.WriteLine ("찾았다");
done: ;
```

대안이 셋 있고, 각각 대가가 있다.

| 방법 | 장점 | 대가 |
|---|---|---|
| `goto` | 분기 한 번. 조건 검사 추가 없음 | `goto`에 대한 거부감, 레이블 관리 |
| 플래그 변수 + 이중 `break` | `goto` 없음 | 회차마다 플래그 검사, 조건이 복잡해짐 |
| 메서드로 뽑아내고 `return` | 가장 읽기 좋다 | 메서드 호출 비용(대개 인라인되어 0), 지역 상태 전달 |

**세 번째가 대부분의 경우 정답이다.** 중첩 루프를 통째로 별도 메서드로 만들고 찾으면 `return`하면 된다. `goto`를 쓸 자리는 그 리팩터링이 불가능하거나(캡처해야 할 지역 상태가 너무 많거나) 성능이 극단적으로 중요한 자리다.

**둘째, `switch`의 `goto case`.** 11.2절에서 본 의도적 fall-through다. 이것은 `goto`이면서도 관용구로 인정된다.

**셋째, 손으로 쓴 상태 기계와 파서.** 렉서·파서·프로토콜 디코더처럼 상태 전이가 본질인 코드에서는 `goto`가 상태 전이를 가장 직접적으로 표현한다. .NET 런타임 자체의 성능 임계 코드에도 `goto`가 쓰인다 — `dotnet/runtime` 저장소를 검색해 보면 실제 사례를 확인할 수 있다.

> **💡 `goto` 판단 기준**
>
> "이 `goto`를 없애려면 코드가 더 복잡해지는가?"
>
> 답이 "예"인 경우가 `goto`를 쓸 자리다. 그런 경우는 실무 코드 1만 줄에 한 번쯤 나온다. 답이 "아니오"라면 — 즉 메서드 추출이나 조기 `return`으로 정리되는 코드라면 — `goto`는 그냥 나쁜 코드다.
>
> 그리고 `goto`를 쓸 때는 레이블 이름을 의미 있게 지어라. `label1:`이 아니라 `found:`, `retry:`, `cleanup:`이다.

### `return` — 여러 개여도 된다

```csharp
decimal AsPercentage (decimal d)
{
    decimal p = d * 100m;
    return p;
}
```

`return`은 메서드 어디에서나, 몇 번이든 쓸 수 있다. `finally` 블록 안만 안 된다. `void` 메서드에서는 식 없이 `return;`만 쓴다.

"메서드에는 `return`이 하나여야 한다"는 옛 규칙(single exit point)은 `finally`와 `using`이 없던 언어의 유산이다. C#에서는 조기 `return`으로 중첩을 줄이는 편(가드 절 패턴)이 거의 언제나 읽기 좋다.

```csharp
void Nested (Order? o)                       // 중첩형
{
    if (o != null)
        if (o.IsValid)
            if (o.Items.Count > 0) DoWork(o);
}

void Guarded (Order? o)                      // 가드 절형
{
    if (o == null) return;
    if (!o.IsValid) return;
    if (o.Items.Count == 0) return;
    DoWork(o);
}
```

### `throw` — 문이면서 식이기도 하다

```csharp
if (w == null)
    throw new ArgumentNullException (nameof(w));
```

※C# 7부터 `throw`는 **식**으로도 쓸 수 있다. 조건 연산자의 한쪽, `??`의 오른쪽, 표현식 본문 멤버 자리에 놓을 수 있다.

```csharp
string s = arg ?? throw new ArgumentNullException (nameof(arg));
int v = flag ? 1 : throw new InvalidOperationException();
public string Name => _name ?? throw new InvalidOperationException("초기화 전");
```

인수 검증을 한 줄로 줄여 준다. 다만 최신 BCL에는 더 나은 관용구가 있다 — `ArgumentNullException.ThrowIfNull(arg)`(21.10절). 예외의 의미론 전체, `throw`와 `throw ex`의 차이, 예외 필터는 32장이다.

### 컴파일 결과 — 점프문은 `br`, 보호된 영역 안에서는 `leave`

`break`와 `continue`는 IL에서 그냥 무조건 분기다.

| 소스 | 보통의 IL | `try` 블록 안일 때의 IL |
|---|---|---|
| `break;` | `br` 루프 종료 지점 | `leave` 루프 종료 지점 |
| `continue;` | `br` 증가절/조건절 | `leave` 증가절/조건절 |
| `goto L;` | `br L` | `leave L` |
| `return;` | `ret` | 값을 임시 변수에 넣고 `leave` → 나중에 `ret` |

`leave`는 **보호된 영역(protected region)을 빠져나가는 전용 분기 명령**이다. `br`과 달리 "여기서 나가면서 사이에 있는 모든 `finally` 블록을 실행하라"는 의미를 갖는다. 그래서 다음 코드가 의도대로 동작한다.

```csharp
foreach (var x in list)          // finally에서 Dispose를 부른다
{
    if (x.IsTarget)
        return x;                // 이 return이 열거자를 정리하고 나간다
}
```

`return x`가 `.try` 블록 안에 있으므로, 컴파일러는 이것을 "반환값을 임시 지역 변수에 저장 → `leave` → `finally` 실행 → 임시 변수를 싣고 `ret`" 로 낮춘다. `ret`은 보호된 영역 안에 놓일 수 없기 때문이다.

이 구조가 IL에서 어떻게 표현되는지는 11.7절 마지막에서 마저 본다.

### 점프문과 도달 가능성 분석

컴파일러는 각 문이 도달 가능한지, 각 지역 변수가 확정 할당되었는지를 제어 흐름 그래프로 추적한다(6.9절). 점프문은 이 분석에 직접 개입한다.

```csharp
int x;
if (cond)
    x = 1;
else
    return;                      // 이 경로는 아래로 흐르지 않는다
Console.WriteLine (x);           // OK — 여기 도달했다면 x는 할당되었다
```

```csharp
static int F()
{
    while (true) { }
    return 0;                    // 경고 CS0162 — 도달할 수 없는 코드
}
```

```csharp
static int G(bool b)
{
    if (b) return 1;
    // 오류 CS0161 — 모든 코드 경로가 값을 반환하지는 않습니다
}
```

세 메시지는 전부 같은 분석의 산물이다. `throw`와 `return`은 "이 지점 이후로는 흐름이 없다"를 뜻하고, `while (true)`는 "여기서 나가지 않는다"를 뜻한다. 컴파일러가 이 사실을 알기 때문에 위 첫 예제의 `x`가 확정 할당으로 인정된다.

## 11.7 기타 문 — `using`, `lock`, `checked`, `unsafe`, `fixed`

남은 문 다섯 개는 공통점이 있다. **전부 다른 장에서 본격적으로 다룰 주제의 문법적 껍데기**이며, 대부분 `try`/`finally`로 낮춰진다. 이 절은 문법과 낮춤 결과만 확정하고 의미론은 각 장으로 넘긴다.

| 문 | 무엇으로 낮춰지는가 | 의미론을 다루는 곳 |
|---|---|---|
| `using` 문 / `using` 선언 | `try`/`finally` + `Dispose()` | 33.5절 (`IDisposable` 계약은 33장 전체) |
| `lock` | `try`/`finally` + `Monitor.Enter`/`Exit` | 48.5절 (메모리 모델은 48.2절) |
| `checked` / `unchecked` | 산술 옵코드의 `.ovf` 변형 선택 | 7.9절 |
| `unsafe` | 아무것도 아님 (컴파일러 허가 표시) | 60.7절 |
| `fixed` | 고정(pinning)된 지역 변수 선언 | 60.8절 |

### `using` 문 — `try`/`finally`의 문법 설탕

`IDisposable`을 구현한 객체를 쓰고 나서 반드시 `Dispose()`를 부르게 하는 문법이다.

```csharp
using (var reader = File.OpenText ("file.txt"))
{
    Console.WriteLine (reader.ReadLine());
}
```

낮춘 결과는 이것과 정확히 같다.

```csharp
{
    StreamReader reader = File.OpenText ("file.txt");
    try
    {
        Console.WriteLine (reader.ReadLine());
    }
    finally
    {
        if (reader != null) ((IDisposable)reader).Dispose();
    }
}
```

세 가지를 확인해 두자.

- **`reader`는 `using` 블록 안에서만 보인다.** 낮춤 결과의 바깥 중괄호가 그 범위를 만든다.
- **`reader`는 읽기 전용이다.** `using` 블록 안에서 다른 객체를 대입할 수 없다. 대입할 수 있으면 `finally`가 엉뚱한 객체를 정리하게 된다.
- **`null` 검사가 들어간다.** 리소스 식이 `null`이어도 `NullReferenceException` 없이 조용히 넘어간다. 리소스 타입이 널 불가 값 타입이면 이 검사가 생략되고 `constrained.` 호출이 쓰인다(11.5절의 열거자 규칙과 같은 원리다).

※C# 8의 **`using` 선언**은 중괄호를 없애고 범위를 감싸는 블록 끝까지로 늘린다.

```csharp
static void Read()
{
    using var reader = File.OpenText ("file.txt");     // 괄호도 중괄호도 없다
    Console.WriteLine (reader.ReadLine());
}                                                       // 여기서 Dispose
```

중첩된 `using`이 만드는 계단식 들여쓰기를 없애 준다. 여러 개를 선언하면 **선언의 역순으로** 정리된다 — 나중에 만든 것이 먼저 정리된다. 이 문법과 `IAsyncDisposable`/`await using`은 33.5절과 33.6절이다.

> **⚠️ `using` 지시문과 `using` 문은 완전히 다른 것이다**
>
> ```csharp
> using System.IO;                       // using 지시문 — 네임스페이스 가져오기 (12.2절)
> using (var f = File.OpenText(p)) { }   // using 문 — 리소스 정리
> using var g = File.OpenText(p);        // using 선언 — 리소스 정리 (※C# 8)
> ```
>
> C#은 `using` 키워드에 세 가지 독립적인 의미를 얹었다. 파일 맨 위에 있고 세미콜론으로 끝나며 타입/네임스페이스 이름이 뒤따르면 지시문, 메서드 안에서 괄호나 변수 선언이 뒤따르면 문이다. 키워드 재사용은 C#의 오랜 습관이며(`static`, `new`, `where`도 그렇다), 문맥으로 구분해야 한다.

### `lock` 문

```csharp
lock (locker)
{
    // 임계 구역
}
```

낮춘 결과는 이렇다.

```csharp
bool __lockTaken = false;
object __temp = locker;                     // 대상 식을 한 번만 평가
try
{
    Monitor.Enter (__temp, ref __lockTaken);
    // 임계 구역
}
finally
{
    if (__lockTaken) Monitor.Exit (__temp);
}
```

`__lockTaken` 플래그가 있는 이유는 **`Monitor.Enter` 호출 도중에 스레드 중단이 일어날 수 있기 때문**이다. 잠금을 얻기 전에 예외가 발생했는데 `finally`가 `Monitor.Exit`를 부르면 얻지도 않은 잠금을 해제하려 해 `SynchronizationLockException`이 난다. C# 4 이전의 낮춤에는 이 플래그가 없어서 실제로 그 창(window)이 존재했다.

> **📌 ※C# 13 / .NET 9의 `System.Threading.Lock`**
>
> 잠금 대상 식의 타입이 새로 도입된 `System.Threading.Lock`이면 컴파일러가 **다른 코드로 낮춘다** — `Monitor`가 아니라 `Lock.EnterScope()`가 반환하는 구조체를 `using`처럼 정리하는 형태다. 같은 `lock` 키워드가 대상 타입에 따라 다른 것으로 컴파일되는 것이다.
>
> 기존 코드에서 잠금 객체 필드의 타입만 `object`에서 `Lock`으로 바꾸면 `lock` 문 자체는 그대로 두고 더 빠른 구현으로 갈아탈 수 있다. 다만 그 필드를 `object`로 받는 코드가 어딘가에 남아 있으면 옛 `Monitor` 경로로 조용히 되돌아간다. 이 함정을 포함한 상세는 48.15절이다.

`lock`의 대상 선택, 경합 측정, 데드락, 메모리 모델은 전부 48장이다. 여기서 알아 둘 것은 **`lock`도 `try`/`finally`라는 사실** 하나다.

### `checked` / `unchecked` 문

정수 오버플로 검사를 켜고 끄는 문이다. 블록 형태로 쓰면 그 안의 모든 산술 연산에 적용된다.

```csharp
checked
{
    int x = int.MaxValue;
    x++;                       // OverflowException
}

unchecked
{
    int y = int.MaxValue;
    y++;                       // 조용히 int.MinValue가 된다
}
```

컴파일 결과는 산술 옵코드가 `add`에서 `add.ovf`로 바뀌는 것이며, 여기에 제어 흐름은 개입하지 않는다. 의미론과 성능, 기본값이 `unchecked`인 이유, `<CheckForOverflowUnderflow>` 설정은 7.9절에서 이미 다뤘다. 이 절에서 확정할 것은 **`checked`가 식 형태(`checked(x + y)`)뿐 아니라 문 형태로도 존재한다**는 문법적 사실이다.

### `unsafe`와 `fixed`

```csharp
unsafe
{
    int x = 10;
    int* p = &x;
    Console.WriteLine (*p);
}
```

`unsafe` 블록 안에서는 포인터 타입과 포인터 연산을 쓸 수 있다. 컴파일하려면 프로젝트에 `<AllowUnsafeBlocks>true</AllowUnsafeBlocks>`가 필요하다. `unsafe`는 IL에 아무 흔적을 남기지 않는다 — 컴파일러에게 "이 안에서 포인터를 허용하라"고 말하는 것뿐이다.

`fixed` 문은 관리 힙의 객체를 GC가 옮기지 못하도록 **고정**(pinning)한 채 그 주소를 포인터로 얻는다.

```csharp
unsafe
{
    int[] a = { 1, 2, 3 };
    fixed (int* p = a)              // a를 고정하고 첫 요소의 주소를 얻는다
    {
        Console.WriteLine (p[1]);   // 2
    }                               // 여기서 고정 해제
}
```

`fixed` 블록이 짧아야 하는 이유(고정된 객체가 GC의 압축을 방해한다), 고정 크기 버퍼, `GCHandle`과의 관계는 60.8절과 62장이다. 대부분의 코드에서 `unsafe`/`fixed` 대신 `Span<T>`를 쓰는 것이 옳다(68장).

### 컴파일러가 만드는 제어 흐름 — `finally`는 IL에서 무엇이 되는가

`using`, `lock`, `foreach`, 그리고 직접 쓴 `try`/`finally`가 전부 같은 IL 구조로 수렴한다. 이 구조를 읽을 줄 알아야 컴파일러가 만든 코드를 이해할 수 있다.

```csharp
static void F()
{
    var sw = new StringWriter();
    using (sw)
    {
        sw.Write("x");
    }
    Console.WriteLine("끝");
}
```

```il
.locals init (class [System.Runtime]System.IO.StringWriter V_0)
  IL_0000:  newobj     instance void [System.Runtime]System.IO.StringWriter::.ctor()
  IL_0005:  stloc.0
  .try
  {
    IL_0006:  ldloc.0
    IL_0007:  ldstr      "x"
    IL_000c:  callvirt   instance void [System.Runtime]System.IO.TextWriter::Write(string)
    IL_0011:  leave.s    IL_001d            // ← 보호된 영역 탈출
  }
  finally
  {
    IL_0013:  ldloc.0
    IL_0014:  brfalse.s  IL_001c            // null 검사
    IL_0016:  ldloc.0
    IL_0017:  callvirt   instance void [System.Runtime]System.IDisposable::Dispose()
    IL_001c:  endfinally                    // ← finally 종료
  }
  IL_001d:  ldstr      "끝"
  IL_0022:  call       void [System.Console]System.Console::WriteLine(string)
  IL_0027:  ret
```

세 가지가 새로 나왔다.

**첫째, `.try { } finally { }`는 명령이 아니라 메타데이터다.** `ildasm` 출력에서는 블록처럼 보이지만, 실제 어셈블리에는 메서드 본문의 IL 바이트 스트림 뒤에 **예외 처리 절 테이블**(EH clause table)이 따로 붙는다. 각 항목은 "보호할 구간의 시작 오프셋과 길이, 핸들러의 시작 오프셋과 길이, 그리고 종류(catch/filter/finally/fault)"를 담는다.

```text
   메서드 본문의 IL 바이트 스트림
   ┌────────────────────────────────────────────┐
   │ 0000 newobj ... 0005 stloc.0               │
   │ 0006 ┌──────────────────────────────┐      │
   │      │ 보호된 영역 (try)            │      │
   │      │ ... 0011 leave.s 001d        │      │
   │ 0013 └──────────────────────────────┘      │
   │      ┌──────────────────────────────┐      │
   │      │ 핸들러 (finally)             │      │
   │      │ ... 001c endfinally          │      │
   │ 001d └──────────────────────────────┘      │
   │ 001d ldstr ... 0027 ret                    │
   └────────────────────────────────────────────┘
   예외 처리 절 테이블 (본문과 별도)
   ┌──────────────────────────────────────────────────┐
   │ 종류=finally  try=0x0006..0x0013  handler=0x0013..0x001D │
   └──────────────────────────────────────────────────┘
```

**둘째, `leave`는 그냥 점프가 아니다.** 보호된 영역을 빠져나가는 유일한 합법적 방법이며, "지금부터 목적지까지 사이에 걸쳐 있는 모든 `finally` 핸들러를 순서대로 실행한 뒤 목적지로 가라"를 뜻한다. `leave`는 부작용으로 **평가 스택을 비운다.** 그래서 `try` 안의 `return x`가 값을 임시 지역 변수에 옮겨 담은 뒤 `leave`하는 것이다 — 스택에 얹어 둔 값은 `leave`가 지워 버린다.

**셋째, `endfinally`는 "핸들러가 끝났으니 원래 하려던 일을 계속하라"는 명령이다.** 예외 없이 `leave`로 들어왔으면 `leave`의 목적지로 가고, 예외 처리 중에 들어왔으면 예외 전파를 계속한다. `finally` 핸들러가 **호출되는 서브루틴처럼 동작한다**는 뜻이다.

> **📌 `finally`는 정상 경로에서도 비용을 낸다 — 그리고 JIT이 그것을 줄인다**
>
> 위 IL을 그대로 기계어로 옮기면, 예외가 없는 정상 경로에서도 `finally` 블록으로 "가서" 실행하고 "돌아오는" 구조가 된다. .NET의 실제 구현에서 예외 핸들러는 **펀클릿**(funclet)이라는 별도 코드 조각으로 컴파일되고, 예외 처리 중에는 런타임이 그것을 호출한다(2단계 처리 — 32.6절).
>
> 정상 경로까지 그 비용을 낼 이유는 없다. 그래서 RyuJIT은 **`finally` 클로닝**이라는 최적화를 한다 — `finally` 본문을 정상 종료 경로에 통째로 복제해 넣어, 예외가 없을 때는 펀클릿을 거치지 않고 그대로 흘러가게 만든다. 예외 경로용 펀클릿은 그대로 남는다.
>
> 그래서 `using`이나 `foreach`가 만드는 `try`/`finally`는 **정상 경로에서 사실상 공짜**에 가깝다. "`try`/`finally`는 비싸니 핫 패스에서 피하라"는 조언은 근거가 약하다. 비싼 것은 예외를 **던질 때**이지 보호 구역을 두는 것 자체가 아니다(32.12절).

> **💡 IL에서 `.try`/`finally`를 보면 소스에 무엇이 있었는지 역추적할 수 있다**
>
> | IL에서 보이는 것 | 소스에 있었던 것 |
> |---|---|
> | `.try`/`finally` + `Dispose()` 호출 | `using` 문/선언, 또는 `foreach` |
> | `.try`/`finally` + `Monitor.Exit` | `lock` 문 |
> | `.try`/`finally` + `GetEnumerator`/`MoveNext` | `foreach` |
> | `.try`/`finally` + `bool` 플래그 검사 | `lock` 문 (`__lockTaken`) |
>
> 디컴파일러가 없어도 이 표만으로 상당한 역추적이 된다. 컴파일러 생성 코드를 알아보는 표지의 전체 목록은 56.6절에 있다.

## 이 장의 요약

- **모든 식이 문이 되지는 않는다.** 식문이 될 수 있는 것은 대입, 증감, 메서드 호출, 객체 생성, `await`, null 조건부 호출뿐이다. 규칙의 근거는 "문은 상태를 바꾸거나 바꿀 가능성이 있는 것을 호출해야 한다"이며, 오타를 컴파일 단계에서 잡아 준다. 결과를 의도적으로 버릴 때는 `_ =`를 써서 그 의도를 코드에 남겨라.

- **`if`의 조건은 IL에서 뒤집힌다.** then 블록이 분기 없이 흘러가는 경로가 되고, else로 가는 것만 분기가 된다. 조건 연산자 `?:`도 같은 IL을 만든다 — 짧게 쓰는 문법일 뿐 빨라지지 않는다. `else`는 언제나 가장 가까운 짝 없는 `if`에 붙으며, `else if`는 문법이 아니라 중첩된 `if`다.

- **`switch` 문은 fall-through를 금지한다.** 모든 섹션은 점프문으로 끝나야 하고, 어기면 CS0163이다. 의도적 fall-through는 `goto case`로 명시한다. 상수 `case`는 순서가 무관하지만 패턴 `case`는 순서가 유의미하며, `default`는 어디에 적어도 언제나 마지막에 평가된다.

- **`switch`가 항상 `O(1)`인 것은 아니다.** 값이 조밀하면 점프 테이블(`switch` 옵코드), 성기면 이진 탐색, 아주 적으면 순차 비교다. 문자열은 개수가 늘면 컴파일러가 `<PrivateImplementationDetails>.ComputeStringHash`를 생성해 해시로 먼저 분기한다.

- **`switch` 식은 값을 만들고, 그래서 완전성 검사를 받는다.** 어느 절에도 맞지 않으면 런타임 예외이며, 타입은 대상 프레임워크에 따라 `SwitchExpressionException` 또는 `InvalidOperationException`이다. `enum`을 전부 나열해도 경고는 사라지지 않는다 — 선언되지 않은 값이 들어올 수 있기 때문이다.

- **`while`, `for`, `do-while`은 같은 모양으로 수렴한다.** 컴파일러가 루프를 회전시켜 조건을 아래로 내리므로 회차당 분기가 하나다. `for`와 `while`의 IL은 한 바이트도 다르지 않고, `do-while`만 진입 분기 하나가 없다. 성능 때문에 형태를 고르는 것은 낭비다.

- **`foreach`는 정적 타입에 따라 완전히 다른 코드가 된다.** 배열과 문자열은 인덱스 루프로 낮춰져 열거자도 `try`/`finally`도 없고, 구조체 열거자는 스택에서 `call`로 돌며, 인터페이스 경로는 힙 할당과 `callvirt`를 낸다. 컴파일러는 인터페이스보다 **모양**을 먼저 본다 — 이 덕 타이핑 규칙이 `Span<T>`의 `ref struct` 열거자를 가능하게 했다.

- **`Dispose` 호출은 열거자 타입이 결정한다.** `IDisposable`을 구현하지 않은 구조체나 봉인 클래스면 `finally`가 아예 생기지 않고, 비봉인 클래스면 런타임 타입 검사가 들어간다. 열거자를 직접 만든다면 구조체로, 클래스라면 `sealed`로.

- **`foreach` 반복 변수는 ※C# 5부터 회차마다 새로 만들어진다.** 그전에는 하나를 공유해서 람다 캡처가 전부 마지막 값을 보았다. `for`의 변수는 지금도 하나이며, 회차별 캡처가 필요하면 본문에서 복사해야 한다.

- **점프문은 `try`의 신뢰성 규칙을 따른다.** `try` 밖으로 나가는 점프는 `finally`를 먼저 실행하고, `finally` 밖으로 나가는 점프는 `throw` 말고는 금지된다. IL에서 그 역할을 하는 것이 `leave`이며, `leave`는 평가 스택을 비우므로 `try` 안의 `return`은 값을 임시 변수에 옮겨 담는다.

- **`using`과 `lock`은 `try`/`finally`의 문법 설탕이다.** `using`은 null 검사 후 `Dispose()`, `lock`은 `__lockTaken` 플래그와 `Monitor.Enter`/`Exit`다. `.try`/`finally`는 명령이 아니라 메서드 뒤에 붙는 예외 처리 절 테이블이며, JIT의 `finally` 클로닝 덕분에 정상 경로 비용은 사실상 없다.

## 연습 문제

1. **식문 규칙을 오류 메시지로 확인하라.** `int x = 1, y = 2;` 아래에 `x + y;`, `x == y;`, `x.CompareTo(y);`, `new object();`, `_ = x + y;`를 각각 한 줄씩 넣고 컴파일하라. 어느 줄이 CS0201로 거부되는지 기록하고, 거부되지 않은 줄들이 왜 통과했는지 11.1절의 표로 설명하라.

2. **`switch`의 세 가지 컴파일 전략을 직접 만들어 내라.** SharpLab(sharplab.io)에서 IL 탭을 열고 세 버전을 비교하라 — (a) `case 0..3`, (b) `case 100, 200, 300, 400, 500`, (c) 문자열 `case` 여덟 개. (a)에서 `switch` 옵코드를, (c)에서 `ComputeStringHash` 호출을 찾아라. (b)는 무엇이 나오는가?

3. **`foreach`의 세 경로를 IL로 구분하라.** 같은 `Sum` 로직을 `int[]`, `List<int>`, `IEnumerable<int>` 세 가지 매개변수 타입으로 만들고 IL을 비교하라. 각각에서 다음을 찾아 표로 정리하라 — `.locals init`의 열거자 타입, `.try` 블록의 유무, `call` vs `callvirt`, `ldlen`의 유무.

4. **열거자 설계가 `finally`를 없애는 것을 확인하라.** `Current`와 `MoveNext()`만 가진 구조체 열거자와, 그것을 반환하는 `GetEnumerator()`를 가진 타입을 직접 만들어 `foreach`를 돌려라. IL에 `.try`가 없는 것을 확인한 뒤, 열거자에 `IDisposable`을 구현하고 다시 컴파일해 `.try`/`finally`가 나타나는 것을 확인하라. 마지막으로 열거자를 `class`(비봉인)로 바꿔 `isinst`가 나타나는지 보라.

5. **C# 5의 캡처 변경을 재현하라.** `foreach`로 `Action` 세 개를 만들어 리스트에 담고 전부 호출해 `123`이 나오는 것을 확인하라. 같은 코드를 `for` 루프로 바꿔 `333`이 나오는 것을 확인하고, 본문 안에 지역 변수 하나를 추가해 다시 `012`가 나오게 고쳐라. 세 결과의 차이를 "몇 개의 변수가 캡처되었는가"로 설명하라.

6. **열거 중 수정이 잡히는 지점을 찾아라.** `List<int>`를 `foreach`로 돌면서 `Add`를 부르는 코드, `Remove`를 부르는 코드, `list[0] = 99`처럼 값만 바꾸는 코드를 각각 실행하라. 어느 것이 `InvalidOperationException`을 내고 어느 것이 조용히 넘어가는지 기록하고, 같은 실험을 `int[]`로 반복해 결과가 어떻게 달라지는지 비교하라.

7. **`finally`가 정말 실행되는지 네 가지 탈출 경로로 확인하라.** `try`/`finally`를 감싼 루프를 만들고, `break`, `continue`, `return`, `throw`로 각각 빠져나가면서 `finally`의 출력이 찍히는지 확인하라. 이어서 그 IL을 열어 각 경우에 `br`이 아니라 `leave`가 쓰였는지, `return` 값이 임시 지역 변수에 저장되는지 확인하라.
