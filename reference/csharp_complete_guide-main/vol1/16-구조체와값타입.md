# 16장. 구조체와 값 타입

> **이 장의 위치** — 6.7절에서 "값 타입은 값을 담고 참조 타입은 주소를 담는다"고 첫 설명을 했고, 15장에서는 값 타입이 `object`가 될 때 벌어지는 일(박싱)만 다뤘다. 이 장은 반대편이다. **값 타입을 직접 설계하는 사람의 관점**에서 `struct`의 선언 규칙, 복사 의미론, 생성 의미론, 불변성, 동등성을 끝까지 판다. 13장·14장이 "클래스를 어떻게 만드나"였다면 이 장은 "구조체를 어떻게 만드나"이고, 마지막 절은 그 둘 중 무엇을 고를 것인가에 답한다.
>
> **선수 지식** — 6장(구문과 타입 기초), 10장(변수, 매개변수, 식), 13장(클래스와 캡슐화), 15장(`object` 타입과 박싱)
>
> **이 장에서 다루지 않는 것** — 필드가 메모리에 실제로 어떻게 배치되는지, 정렬·패딩·`[StructLayout]`의 바이트 단위 계산은 54.4절이다. `Span<T>`와 `ref` 필드, `scoped`는 68장이다(이 장은 `ref struct`의 규칙 목록까지만 다룬다). 이미 있는 클래스를 구조체로 바꿀 때의 실측 손익 계산은 69.1절이다. `Equals`/`GetHashCode`의 **계약**(반사성·대칭성·추이성·일관성, 해시 분포)은 25장이며, 이 장은 "값 타입에서 왜 재정의가 필수인가"와 그 코드 형태까지다. 레코드 구조체는 19.2절, 널 가능 값 타입은 21.1절, 열거형은 20장이다.

## 16.1 `struct` 선언 규칙과 제약

### 문법 — 클래스와 거의 같다

구조체 선언은 클래스 선언과 문법이 거의 같다. `class` 자리에 `struct`를 쓰면 된다.

```csharp
public struct Point
{
    public int X;
    public int Y;

    public Point(int x, int y)
    {
        X = x;
        Y = y;
    }

    public double Length => Math.Sqrt(X * X + Y * Y);

    public override string ToString() => $"({X}, {Y})";
}
```

필드, 생성자, 메서드, 프로퍼티, 인덱서, 연산자, 이벤트, 상수, 정적 생성자, 중첩 타입 — 클래스가 가질 수 있는 멤버는 사실상 전부 가질 수 있다. `partial`도 된다. 13장에서 배운 것 대부분이 그대로 적용된다.

차이는 **네 개의 근본 규칙**에서 나오고, 그 넷이 나머지 모든 제약을 파생시킨다.

| # | 규칙 | 파생되는 제약 |
|---|---|---|
| 1 | 구조체는 **값 타입**이고 클래스는 참조 타입이다 | 대입·인수 전달·반환이 전부 복사다(16.2절) |
| 2 | 구조체는 **상속을 지원하지 않는다** — `object`(정확히는 `System.ValueType`)에서 암시적으로 파생될 뿐이다 | 기반 타입 지정 불가, 모든 구조체는 암시적 `sealed` |
| 3 | 구조체는 **파이널라이저를 가질 수 없다** | 결정적이지 않은 정리 코드를 넣을 자리가 없다 |
| 4 | 서브클래싱될 수 없으므로 멤버에 **`virtual`·`abstract`·`protected`를 붙일 수 없다** | 다형성이 원천 차단된다 |

이 넷을 외우면 "구조체가 이건 되나?"라는 질문의 90퍼센트에 스스로 답할 수 있다.

### 컴파일 결과 — IL에서 무엇이 다른가

`Point`를 컴파일하고 ildasm으로 열면 클래스와의 차이가 선언 한 줄에 다 드러난다.

```il
.class public sequential ansi sealed beforefieldinit Point
       extends [System.Runtime]System.ValueType
{
  .field public int32 X
  .field public int32 Y
  // ...
}
```

세 가지를 읽어야 한다.

- **`extends System.ValueType`** — 클래스라면 `extends System.Object`였을 자리다. `System.ValueType`은 추상 클래스이고, 그 자신은 `System.Object`에서 파생된다. 모든 구조체는 예외 없이 여기서 파생된다.
- **`sealed`** — 소스에 `sealed`라고 쓰지 않았는데 붙어 있다. 컴파일러가 자동으로 붙인다. 모든 값 타입은 봉인되어 있고, 그래서 어떤 타입도 값 타입을 기반 타입으로 삼을 수 없다.
- **`sequential`** — 레이아웃 종류다. C# 컴파일러는 **참조 타입에는 `LayoutKind.Auto`를, 값 타입에는 `LayoutKind.Sequential`을** 기본값으로 고른다. 구조체가 비관리 코드와의 상호 운용에 자주 쓰인다고 판단했기 때문이며, 이 경우 필드 순서가 개발자가 쓴 그대로 유지되어야 한다. 상호 운용과 무관한 구조체라면 `[StructLayout(LayoutKind.Auto)]`로 이 기본값을 뒤집어 CLR에게 재배치 권한을 줄 수 있다. 바이트 단위의 결과는 54.4절에서 계산한다.

값 타입의 상속 계층은 이렇게 생겼다.

```text
            System.Object
                  ↑
          System.ValueType          (abstract)
             ↑          ↑
   내가 만든 struct    System.Enum   (abstract)
   int, double, ...        ↑
   Guid, DateTime      모든 enum 타입
   Nullable<T>
   ValueTuple<...>
```

> **📌 `System.ValueType`은 참조 타입이다**
>
> 헷갈리기 쉬운 지점이다. `System.ValueType`은 `class`로 정의된 추상 **참조 타입**이고, 그것을 상속하는 타입들이 값 타입이 된다. 런타임은 "`ValueType`을 직접 상속했는가"라는 메타데이터 사실을 보고 해당 타입을 값 타입으로 취급한다.
>
> `ValueType`이 참조 타입이라는 사실은 실무에서 한 번 드러난다. `ValueType` 타입의 변수에 구조체를 대입하면 박싱된다. `object`에 대입할 때와 정확히 같다(15.2절).
>
> ```csharp
> Point p = new Point(1, 2);
> ValueType v = p;    // 박싱된다. object v = p; 와 다르지 않다
> ```

### 못 하는 것 전수

컴파일 오류로 막히는 것들을 한 표에 모았다.

| 시도 | 결과 | 이유 |
|---|---|---|
| `struct A : B` (`B`가 클래스나 구조체) | 컴파일 오류 | 값 타입은 상속 계층을 만들 수 없다 |
| `struct A { ~A() { } }` | 컴파일 오류 | 값 타입에 파이널라이저를 둘 수 없다 |
| `virtual` / `abstract` 멤버 | 컴파일 오류 | 재정의할 파생 타입이 존재할 수 없다 |
| `protected` / `protected internal` / `private protected` 멤버 | 컴파일 오류 | 서브클래스가 없으므로 의미가 없다 |
| `sealed` / `abstract`를 타입에 명시 | 컴파일 오류 | 이미 암시적으로 `sealed`이며 `abstract`는 불가능하다 |
| `struct Node { Node next; }` | 컴파일 오류 `CS0523` | 구조체 레이아웃에 순환이 생긴다 — 크기가 무한대가 된다 |
| ※C# 10 이전: 인스턴스 필드 초기화자 | 컴파일 오류 `CS0573` | 16.3절에서 다룬다 |
| ※C# 10 이전: 매개변수 없는 생성자 선언 | 컴파일 오류 `CS0568` | 16.3절에서 다룬다 |

반대로, **된다는 사실이 자주 잊히는 것들**도 있다.

| 시도 | 가능 여부 | 비고 |
|---|---|---|
| 인터페이스 구현 | 가능 | 인터페이스 변수로 받으면 박싱된다(18.6절) |
| `object`의 가상 멤버 재정의 (`Equals`, `GetHashCode`, `ToString`) | 가능 | 16.7절. 재정의하면 박싱 없이 호출된다(15.2절) |
| 연산자 오버로딩 | 가능 | 22장. 값 타입에서 오히려 더 자연스럽다 |
| 정적 생성자 | 가능 | 실행 시점 규칙은 13.12절 |
| 중첩 타입, `const`, 이벤트, 인덱서 | 가능 | 클래스와 동일하다 |
| 제네릭 구조체 (`struct Pair<T>`) | 가능 | 값 타입 인수는 코드 특수화 대상이다(23.11절) |
| 기본 생성자 문법 `struct Point(int x, int y)` ※C# 12 | 가능 | 다만 기본값 경로가 이를 우회한다(16.3절) |
| `partial struct` | 가능 | 소스 생성기가 흔히 쓴다(13.14절) |

> **⚠️ "구조체는 상속을 못 한다"의 정확한 의미**
>
> 세 가지가 뒤섞여 오해를 만든다.
>
> 1. **구조체는 다른 타입을 상속할 수 없다.** 맞다.
> 2. **구조체를 상속할 수 없다.** 맞다. 모든 구조체는 `sealed`다.
> 3. **구조체는 아무것도 상속하지 않는다.** **틀렸다.** 구조체는 `System.ValueType`을 상속하고, `ValueType`은 `System.Object`를 상속한다. 그래서 구조체에도 `ToString()`, `Equals()`, `GetHashCode()`, `GetType()`이 있다.
>
> 3번의 오해는 실질적인 손해를 낳는다. "구조체니까 `Equals`는 없겠지"라고 생각하고 재정의를 건너뛰면, 실제로는 `ValueType`이 재정의해 둔 **느린 구현**이 조용히 쓰인다(16.7절).

> **⚠️ 구조체는 `lock`의 대상이 될 수 없다**
>
> ```csharp
> struct Counter { public int Value; }
>
> Counter c = new Counter();
> lock (c) { c.Value++; }      // 컴파일 오류 — 참조 타입이 아니다
> ```
>
> `lock` 문은 대상 객체의 **싱크 블록**을 쓴다(11.7절). 싱크 블록은 힙에 있는 객체 헤더의 일부이고(54.2절), 값 타입에는 그런 헤더가 없다.
>
> 더 위험한 것은 **박싱해서 우회하는 코드**다. `lock ((object)c)`는 컴파일되지만 매번 **새로운 박스**를 만들므로 매번 다른 객체를 잠근다. 즉 아무것도 잠그지 않는다. 컴파일 오류도 경고도 없이 동시성 버그가 만들어진다.
>
> 구조체를 다루는 코드에 상호 배제가 필요하다면 **별도의 참조 타입 잠금 객체**를 두거나, `Interlocked` 계열 연산을 쓰거나, 애초에 그 타입을 클래스로 만들어야 한다.

### 왜 상속을 금지했나 — 슬라이싱

값 타입의 상속 금지는 임의의 제약이 아니다. 값 의미론과 상속은 근본적으로 충돌한다.

C++에서는 모든 매개변수와 반환값이 기본적으로 값으로 전달됐다. 값 전달은 매우 효율적이지만 하나의 문제를 안고 있었다 — **부분 복사(partial copy), 흔히 객체 슬라이싱(slicing)이라고 부르는 현상**이다. 기반 객체가 기대되는 자리에 파생 객체를 쓰면 객체의 **기반 부분만 복사된다.** 파생 객체가 거기 있었다는 사실 자체가 사라진다. 심지어 가상 함수 호출조차 기반 클래스 버전으로 간다.

Java는 반대 방향으로 응답했다. 언어에서 값 타입을 사실상 제거하고 모든 사용자 정의 타입을 참조 타입으로 만들었다. 모든 매개변수와 반환값이 참조로 전달된다. 일관되다는 장점이 있지만 성능에는 부담이다. 어떤 타입은 다형적이지 않고, 다형적일 의도조차 없다. 그런데도 객체 인스턴스마다 힙 할당과 언젠가의 가비지 컬렉션 비용을 낸다. 모든 멤버 접근에 역참조 비용도 낸다.

C#은 제3의 답을 골랐다. **값 타입을 유지하되, 값 타입에서는 상속을 금지한다.** 슬라이싱이 발생할 조건 자체를 언어 차원에서 제거한 것이다. `struct`와 `class` 중 무엇을 쓸지는 타입을 **정의하는 사람**이 정하고, 타입을 **쓰는 사람**은 그 결정을 바꿀 수 없다.

> **📌 C/C++ 개발자가 가장 먼저 걸려 넘어지는 지점**
>
> 비관리 C/C++에서는 타입을 선언한 다음, 그 타입을 **쓰는 코드**가 인스턴스를 스택에 놓을지 힙에 놓을지 결정했다. 관리 코드에서는 **타입을 정의하는 개발자**가 인스턴스가 어디에 할당될지를 지정하고, 타입을 쓰는 개발자에게는 그 통제권이 없다.
>
> 이 차이가 16.8절의 결론을 무겁게 만든다. `struct`냐 `class`냐는 나중에 바꾸기 어려운 결정이다.

### 접근 제한자

구조체 멤버의 기본 접근성은 클래스와 같이 `private`다. 타입 자체의 기본 접근성도 클래스와 같이 `internal`이다. 다만 `protected` 계열 셋(`protected`, `protected internal`, `private protected`)은 쓸 수 없다. 접근 제한자 전체는 17.1절에서 다룬다.

> **💡 필드를 `public`으로 노출하는 구조체는 괜찮은가**
>
> 클래스라면 "필드를 그대로 노출하지 말고 프로퍼티로 감싸라"가 정석이다(13.1절). 구조체에서는 판단이 갈린다.
>
> - **찬성** — 상호 운용용 구조체, 좌표·벡터 같은 순수 데이터 묶음에서는 필드 직접 노출이 관행이다. `System.Numerics`의 `Vector3`도 `X`, `Y`, `Z`를 필드로 노출한다. 프로퍼티 게터는 인스턴스 메서드라서 `in` 매개변수나 `readonly` 문맥에서 방어적 복사를 유발할 수 있다(16.2절). 필드 읽기에는 그런 문제가 없다.
> - **반대** — 필드는 프로퍼티로 바꾸는 순간 이진 호환성이 깨지고, 유효성 검사를 끼워 넣을 자리도 없다.
>
> 실무 기준은 이렇다. **공개 API에서는 프로퍼티, 성능 임계 경로의 내부 구조체에서는 필드.** 그리고 어느 쪽을 고르든 `readonly struct`로 선언하면(16.5절) 이 고민의 절반이 사라진다.

## 16.2 값 타입 복사 의미론과 숨은 복사

### 근본 원리 — 값은 자기 데이터를 직접 담는다

ECMA-335 표준의 정의부터 보자.

- **값 타입(value type)** — 그 인스턴스가 **자기의 모든 데이터를 직접 담는** 타입. 값 타입이 기술하는 값은 자기 완결적(self-contained)이다.
- **참조 타입(reference type)** — 그 인스턴스가 자기 데이터에 대한 **참조를 담는** 타입. 참조 타입이 기술하는 값은 **다른 값의 위치를 가리킨다.**

이 한 줄 차이가 세 가지 결과를 낳는다.

| 성질 | 값 타입 | 참조 타입 |
|---|---|---|
| **수명** | 데이터는 인스턴스 자신과 정확히 같은 기간 산다 | 값은 "다른 값이 저장된 위치"이며, 그 수명은 정의만으로 결정되지 않는다 |
| **공유** | 기본적으로 공유되지 않는다. 다른 곳에서 쓰려면 **바이트 단위로 복사된다**(값 전달 의미론) | 기본적으로 공유된다. 다른 곳에서 쓰면 하나의 값 위치를 가리키는 참조가 하나 더 생긴다 |
| **정체성** | 정체성이 없다. 두 값 타입은 **데이터의 비트 열이 같으면, 그리고 오직 그때만** 동일하다 | 두 참조 타입은 **위치가 같으면, 그리고 오직 그때만** 동일하다 |

여기 어디에도 "스택"이나 "힙"이라는 단어는 없다. 스택과 힙은 구현이고, 위 셋이 추상이다. 값 타입이 실제로 어디에 저장되는지는 6.8절에서 개괄했고 54.8절에서 완결한다. 이 절의 주제는 **공유** 항목, 즉 복사다.

### 복사가 일어나는 지점

`Point`를 예로 들어 복사 지점을 전부 나열한다.

```csharp
struct Point { public int X, Y; }
class Box   { public Point P; }
```

| # | 코드 | 복사되는가 | IL |
|---|---|---|---|
| 1 | `Point b = a;` | 예 — 전체 필드 | `ldloc.0` / `stloc.1` |
| 2 | `Method(a);` (값 매개변수) | 예 | `ldloc.0` / `call` |
| 3 | `return a;` (값 반환) | 예 — 호출자 저장소로 | `ldloc.0` / `ret` |
| 4 | `box.P = a;` (필드 대입) | 예 | `ldloc.0` / `stfld` |
| 5 | `arr[i] = a;` (배열 원소 대입) | 예 | `ldloc.0` / `stelem Point` |
| 6 | `list.Add(a);` | 예 — `List<T>` 내부 배열로 | `call List<Point>::Add` |
| 7 | `Point c = arr[i];` (배열 원소 읽기) | 예 | `ldelem Point` / `stloc` |
| 8 | `object o = a;` (박싱) | 예 — 힙으로(15.2절) | `box Point` |
| 9 | `Method(ref a);` / `Method(in a);` | **아니오** — 주소만 넘긴다 | `ldloca.s` / `call` |
| 10 | `a.X = 5;` (직접 필드 쓰기) | **아니오** | `ldloca.s` / `stfld` 또는 `stfld` |

1번부터 8번까지가 전부 복사다. 값 타입을 쓴다는 것은 **복사를 기본값으로 받아들인다**는 뜻이다.

### 다이어그램 — 대입이 무엇을 하는가

`class SomeRef { public int x; }`와 `struct SomeVal { public int x; }`를 나란히 놓고, 다음 코드를 실행한다.

```csharp
SomeRef r1 = new SomeRef();   // 힙에 할당
SomeVal v1 = new SomeVal();   // 지역 변수 자리에 자리 잡는다
r1.x = 5;
v1.x = 5;

SomeRef r2 = r1;              // 참조(포인터)만 복사한다
SomeVal v2 = v1;              // 멤버를 통째로 복사한다

r1.x = 8;                     // r1.x와 r2.x가 함께 바뀐다
v1.x = 9;                     // v1.x만 바뀐다. v2.x는 그대로다
```

```text
  ── 대입 직후 (r2 = r1; v2 = v1;) ──          ── r1.x=8; v1.x=9; 이후 ──

  스레드 스택        관리 힙                    스레드 스택        관리 힙
 ┌──────────┐     ┌───────────────┐          ┌──────────┐     ┌───────────────┐
 │ r1  ●────┼────→│ 타입 객체 ptr │          │ r1  ●────┼──┐  │ 타입 객체 ptr │
 ├──────────┤     │ 싱크 블록 idx │          ├──────────┤  │  │ 싱크 블록 idx │
 │ v1  x=5  │     │ x = 5         │          │ v1  x=9  │  ├─→│ x = 8         │
 ├──────────┤     └───────────────┘          ├──────────┤  │  └───────────────┘
 │ r2  ●────┼──────────↑                     │ r2  ●────┼──┘
 ├──────────┤                                ├──────────┤
 │ v2  x=5  │                                │ v2  x=5  │   ← 영향 없음
 └──────────┘                                └──────────┘
```

오른쪽 그림이 전부다. `r1`과 `r2`는 **하나의 값**을 공유하고, `v1`과 `v2`는 **두 개의 서로 다른 값**이다. 값 타입 변수는 서로 구별되는 독립 개체이며, 한 값 타입 변수에 대한 연산이 다른 값 타입 변수에 영향을 주는 것은 불가능하다.

> **⚠️ 컬렉션에 넣은 구조체는 "그 구조체"가 아니다**
>
> 가장 자주 나는 사고다.
>
> ```csharp
> var list = new List<Point>();
> list.Add(new Point(1, 1));
>
> Point p = list[0];   // 복사본이 나온다
> p.X = 99;            // 복사본만 바뀐다
> Console.WriteLine(list[0].X);   // 1. 99가 아니다
>
> list[0].X = 99;      // 컴파일 오류 CS1612:
>                      // 반환 값은 변수가 아니므로 수정할 수 없다
> ```
>
> `List<T>`의 인덱서는 **프로퍼티**이고, 프로퍼티 게터는 값을 복사해 반환한다. 컴파일러가 마지막 줄을 오류로 막아 주는 것은 다행이다 — 막지 않았다면 "고쳤는데 안 고쳐지는" 코드가 조용히 통과했을 것이다.
>
> 반면 **배열**은 다르다. `arr[0].X = 99;`는 컴파일된다. 배열 인덱서는 프로퍼티가 아니라 CLR이 직접 지원하는 연산이고, `ldelema`(원소의 **주소**)를 낼 수 있기 때문이다. **같은 문법이 배열에서는 되고 `List<T>`에서는 안 되는 이 비대칭**이 가변 구조체를 위험하게 만드는 핵심이다.

### 숨은 복사 — 소스에 복사가 안 보이는 네 자리

앞 표의 1~8번은 "여기서 복사가 일어나겠구나"가 눈에 보인다. 진짜 문제는 **소스 어디에도 대입이나 인수 전달이 없는데 복사가 일어나는** 경우다. 컴파일러가 값의 불변성을 보장하기 위해 만들어 내는 이 복사를 **방어적 복사(defensive copy)** 라고 부른다.

방어적 복사가 생기는 이유는 하나다. **컴파일러는 인스턴스 메서드가 `this`를 수정하는지 아닌지를 호출 지점에서 증명할 수 없다.** 메서드 안의 조건 분기와 외부 데이터까지 분석해야 하기 때문이다. 그래서 컴파일러는 최악을 가정한다 — "이 메서드는 `this`를 고칠지도 모른다." 그런데 대상은 고쳐지면 안 되는 값이다. 유일한 탈출구는 **통째로 복사한 뒤 복사본에 대해 호출하는 것**이다.

값 타입에서 인스턴스 메서드를 호출하려면 인스턴스의 **주소**가 필요하다는 사실이 배경에 있다. IL에서 값 타입 인스턴스 메서드는 `this`로 관리 포인터(`&T`)를 받는다. 읽기 전용이어야 할 값의 주소를 그냥 넘기면 메서드가 그걸 고칠 수 있으므로, 복사본의 주소를 넘긴다.

#### 자리 ① — `readonly` 필드에 접근할 때

```csharp
struct Counter                      // readonly struct가 아니다
{
    public int Value;
    public void Increment() => Value++;
}

class Holder
{
    private readonly Counter _ro = new Counter();
    private Counter _rw = new Counter();

    public void Run()
    {
        _ro.Increment();            // 아무 일도 일어나지 않는다
        _rw.Increment();            // _rw.Value가 1이 된다
    }
}
```

`_ro.Increment()`가 IL에서 무엇이 되는지가 답이다.

```il
  // _ro.Increment();  ← readonly 필드
  IL_0000:  ldarg.0
  IL_0001:  ldfld      valuetype Counter Holder::_ro    // ← 값을 통째로 로드(복사)
  IL_0006:  stloc.0                                     // ← 임시 슬롯에 저장
  IL_0007:  ldloca.s   V_0                               // ← 임시 슬롯의 주소
  IL_0009:  call       instance void Counter::Increment()

  // _rw.Increment();  ← 일반 필드
  IL_000e:  ldarg.0
  IL_000f:  ldflda     valuetype Counter Holder::_rw    // ← 필드의 주소를 직접
  IL_0014:  call       instance void Counter::Increment()
```

`ldfld` 대 `ldflda`. 한 글자 차이가 전부다. `readonly` 필드에서는 컴파일러가 필드의 **주소**(`ldflda`)를 내줄 수 없다. 주소를 내주면 그 메서드가 `readonly` 필드를 수정해 버릴 수 있기 때문이다. 그래서 값을 복사(`ldfld`)해 임시 지역 변수에 넣고, **그 임시 변수의 주소**를 넘긴다. `Increment()`는 정상적으로 실행되지만 임시 복사본을 증가시키고, 그 복사본은 곧 버려진다.

> **⚠️ `readonly`를 붙였더니 코드가 조용히 아무 일도 하지 않게 됐다**
>
> 위 예제는 극단적으로 들리지만 현실에서 자주 나온다. 흔한 시나리오는 이렇다.
>
> 1. 가변 구조체 필드가 있는 클래스를 작성한다. 잘 동작한다.
> 2. 코드 리뷰에서 "이 필드는 안 바뀌니까 `readonly` 붙이자"는 의견이 나온다.
> 3. `readonly`를 붙인다. **컴파일 오류도, 경고도 나지 않는다.**
> 4. 그 구조체의 상태를 바꾸던 코드가 전부 무효가 된다.
>
> 참조 타입이었다면 `readonly`는 "참조를 갈아끼우지 못한다"만 의미하고 대상 객체의 필드 수정은 그대로 됐을 것이다. **`readonly`가 값 타입에서는 훨씬 강한 의미를 갖는다** — 보호 대상이 참조가 아니라 값 전체이기 때문이다.
>
> 근본 처방은 `readonly`를 떼는 것이 아니라 **구조체를 가변으로 만들지 않는 것**이다(16.5절).

#### 자리 ② — `in` 매개변수

`in` 매개변수는 "참조로 넘기되 수정은 금지"다. `readonly` 필드와 정확히 같은 딜레마를 만든다.

```csharp
static double Sum(in Vec3 a) => a.GetLength();
```

`Vec3`가 `readonly struct`가 아니면 IL은 이렇게 나온다.

```il
  IL_0000:  ldarg.0
  IL_0001:  ldobj      Vec3          // ← 관리 포인터가 가리키는 값을 통째로 복사
  IL_0006:  stloc.0
  IL_0007:  ldloca.s   V_0
  IL_0009:  call       instance float64 Vec3::GetLength()
```

`ldobj`가 방어적 복사다. **복사를 없애려고 `in`을 붙였는데 복사가 그대로 일어나고, 게다가 값 전달이었다면 호출당 1회였을 복사가 이제는 멤버 접근마다 일어날 수 있다.** `in` 매개변수를 언제 붙이고 언제 붙이지 말아야 하는지의 판단표는 10.2절에 있다. 이 절의 관점에서 중요한 것은 **`readonly` 필드와 `in` 매개변수가 정확히 같은 메커니즘의 두 얼굴**이라는 사실이다.

`ref readonly` 반환값도 마찬가지다. 컬렉션이 원소를 복사 없이 노출하려고 `ref readonly`로 돌려줘도, 받은 쪽에서 인스턴스 메서드를 부르는 순간 방어적 복사가 부활한다.

```csharp
public ref readonly Book GetBookByTitle(string title) { /* ... */ }

// 호출 측
ref readonly var book = ref collection.GetBookByTitle("Call of the Wild, The");
book.ModifyAuthor();          // 방어적 복사본에서 실행된다. 원본은 그대로다
```

`ModifyAuthor` 메서드는 **실제로 실행된다.** 다만 곧 버려질 임시 인스턴스에 대해서만 실행되고, 거기 가한 변경은 원본에 반영되지 않고 사라진다.

> **📌 `readonly` 참조가 보호하는 것은 무엇인가**
>
> 한 문장으로 기억하면 헷갈리지 않는다. **보호 대상은 "값"이다.**
>
> - `Book`이 **클래스**라면 값은 참조다. `ref readonly`는 참조를 갈아끼우는 것만 막는다. `book.Author = "..."`는 그대로 된다.
> - `Book`이 **구조체**라면 값은 객체 전체다. `ref readonly`는 `book = new Book()`도 `book.Author = "..."`도 전부 막는다.
>
> 같은 키워드가 값 타입에서 훨씬 강하게 작동한다. 16.5절의 `readonly struct`, 10.2절의 `in`, 10.3절의 `ref readonly`가 모두 이 원리 위에 서 있다.

#### 자리 ③ — 프로퍼티 게터가 구조체를 반환할 때

프로퍼티 게터는 **인스턴스 메서드**다. 그리고 값 타입을 반환하는 메서드는 값을 **복사해서** 반환한다.

```csharp
class Sprite
{
    private Point _position;
    public Point Position => _position;         // 게터: 복사본을 반환한다
    public ref Point PositionRef => ref _position;  // 10.3절의 ref 반환
}

var s = new Sprite();
s.Position.X = 10;         // 컴파일 오류 CS1612 — 반환 값은 변수가 아니다
s.PositionRef.X = 10;      // 컴파일된다. 원본이 바뀐다
```

```il
  // Point p = s.Position;
  IL_0000:  ldloc.0
  IL_0001:  callvirt   instance valuetype Point Sprite::get_Position()
  IL_0006:  stloc.1                       // ← 반환된 복사본을 저장
```

`get_Position()`이 평가 스택에 올려놓는 것은 원본이 아니라 16바이트짜리(또는 그 타입 크기만큼의) 복사본이다. 컴파일러가 `s.Position.X = 10;`을 오류로 막는 이유가 여기 있다 — 대입해 봐야 곧 사라질 임시 값을 고칠 뿐이기 때문이다.

**필드를 프로퍼티로 감싸는 흔한 리팩터링이 이 복사를 만들어 낸다.** `public Point Position;`은 `ldflda`로 접근할 수 있는 변수이지만, `public Point Position { get; }`은 복사본을 내주는 메서드다.

> **⚠️ 자동 프로퍼티는 이 함정을 숨긴다**
>
> ```csharp
> struct Vec3 { public double X, Y, Z; public double Length => /* ... */; }
>
> class Body
> {
>     public Vec3 Velocity { get; set; }     // 자동 프로퍼티
> }
>
> var b = new Body();
> double len = b.Velocity.Length;   // Velocity 게터 호출 → 복사 1회
>                                   // Length 게터 호출 → 그 복사본에 대해 또 복사 가능
> ```
>
> 소스에는 대입이 하나도 없는데 24바이트짜리 구조체가 복사된다. 루프 안에서 `b.Velocity.X`, `b.Velocity.Y`, `b.Velocity.Z`를 각각 읽으면 게터가 세 번 호출되고 복사가 세 번 일어난다.
>
> 처방은 두 가지다. **① 지역 변수에 한 번만 꺼내 쓴다.** `var v = b.Velocity;` 이후 `v.X`, `v.Y`, `v.Z`. **② 구조체를 `readonly struct`로 선언한다**(16.5절) — 그러면 최소한 게터가 반환한 복사본 위에서의 추가 복사는 사라진다.

#### 자리 ④ — `foreach` 반복 변수

```csharp
Point[] points = new Point[3];

foreach (var p in points)
    p.X = 10;          // 컴파일 오류 CS1654:
                       // 'p'는 'foreach 반복 변수'이므로 멤버를 수정할 수 없다

for (int i = 0; i < points.Length; i++)
    points[i].X = 10;  // 컴파일된다. 배열 원소를 직접 고친다
```

`foreach` 반복 변수는 **읽기 전용 지역 변수**이고, 원소의 **복사본**이다. 11.5절에서 본 대로 `foreach`는 열거자 위의 루프로 풀린다. 배열에 대해서는 컴파일러가 인덱스 루프로 최적화하는데, 그 안에서 원소를 반복 변수로 옮기는 명령이 곧 복사다.

```il
  // foreach (var p in points) { ... }
  IL_0004:  ldloc.1                   // 배열 참조
  IL_0005:  ldloc.2                   // 인덱스
  IL_0006:  ldelem     Point          // ← 원소를 평가 스택으로 복사
  IL_000b:  stloc.3                   // ← 반복 변수 p에 저장 (복사 완료)
```

`ldelem`이 `ldelema`가 아니라는 점이 핵심이다. `ldelema`였다면 원소의 주소가 나왔을 것이고, 반복 변수를 통해 배열을 직접 수정할 수 있었을 것이다. 컴파일러는 그렇게 하지 않는다. 그래서 반복 변수를 수정하는 코드를 아예 오류로 막는다 — 막지 않았다면 "루프를 돌며 고쳤는데 아무것도 안 고쳐지는" 코드가 나왔을 것이다.

`List<T>`에 대한 `foreach`는 한 겹 더 있다. `List<T>.Enumerator`는 **구조체**이고 `Current` 프로퍼티는 값을 복사해서 반환한다. 큰 구조체를 담은 `List<T>`를 `foreach`로 도는 것은 원소마다 복사 한 번을 뜻한다.

> **💡 큰 구조체 컬렉션을 순회하는 세 가지 방법**
>
> - `foreach (var p in arr)` — 원소당 복사 1회, 원본 수정 불가. 가장 읽기 쉽다.
> - `for (int i = ...) arr[i].X = ...` — 복사 0회, 원본 수정 가능. 배열에서만 된다.
> - `foreach (ref var p in arr.AsSpan())` — 복사 0회, 원본 수정 가능. `Span<T>`가 필요하다(68장).
>
> 세 번째 형태 — `Span<T>`에 대한 `ref` 반복 변수 — 가 성능과 안전성을 동시에 얻는 현대적 답이다. 다만 `Span<T>`를 배우기 전이라면 두 번째로 충분하다. **어느 쪽이든 판단의 전제는 "구조체가 정말 커서 복사가 문제인가"이고, 그 답은 재 봐야 안다**(67장).

### 숨은 복사 총정리

| 접근 대상 | 필드 직접 읽기 | 필드 직접 쓰기 | 인스턴스 메서드/프로퍼티 호출 |
|---|---|---|---|
| 일반 지역 변수 | 복사 없음 | 가능, 복사 없음 | 복사 없음 (`ldloca`) |
| 일반 인스턴스 필드 | 복사 없음 | 가능, 복사 없음 | 복사 없음 (`ldflda`) |
| `readonly` 필드 | 복사 없음 | **컴파일 오류** | **방어적 복사** |
| `in` 매개변수 | 복사 없음 | **컴파일 오류** | **방어적 복사** |
| `ref readonly` 지역/반환 | 복사 없음 | **컴파일 오류** | **방어적 복사** |
| 프로퍼티 게터 반환값 | 복사 1회 | **컴파일 오류 CS1612** | 복사 1회 후 호출 |
| `foreach` 반복 변수 | 복사 1회 | **컴파일 오류 CS1654** | 복사본 위에서 호출 |
| `static readonly` 필드 | 복사 없음 | **컴파일 오류** | **방어적 복사** |

굵게 표시한 다섯 칸이 이 절의 전부다. 그리고 **다섯 칸 전부가 `readonly struct`로 선언하면 사라진다**(16.5절).

> **⚠️ 방어적 복사는 경고 없이 일어난다**
>
> 컴파일 오류가 나는 칸은 오히려 안전하다. 컴파일러가 막아 주기 때문이다. 위험한 것은 **컴파일도 되고 경고도 없이 복사만 조용히 늘어나는** 칸이다.
>
> 유일한 예외가 하나 있다. `readonly` 멤버 안에서 `readonly`가 아닌 멤버를 호출하면 컴파일러가 "`readonly` 멤버에서 비 `readonly` 멤버를 호출하면 `this`가 암시적으로 복사된다"는 취지의 경고를 낸다(16.5절). 그 한 자리를 빼면 전부 침묵이다.
>
> 그래서 방어적 복사는 **코드를 읽어서 찾는 것이 아니라 규칙으로 예방해야 한다.** 규칙은 두 줄이다 — 구조체는 `readonly struct`로 만든다. 그럴 수 없으면 `in`과 `readonly` 필드를 쓰지 않는다.

## 16.3 구조체 생성 의미론 — 기본 생성자, 필드 초기화 ※C# 10/11

### `new` 없이도 만들어진다

값 타입 인스턴스는 `new` 없이 선언만으로 존재한다. 값 타입 변수는 그 자체가 값을 담는 저장 공간이기 때문이다.

```csharp
SomeVal v1 = new SomeVal();   // 필드가 0으로 채워진다
SomeVal v2;                   // 저장 공간은 이미 있다. 필드는 아직 "확정 할당되지 않음"
```

두 줄이 만들어 내는 **메모리 상태는 같다.** IL도 사실상 같은 일을 한다. 차이는 오직 **C# 컴파일러의 확정 할당(definite assignment) 추적**에 있다.

```csharp
SomeVal a = new SomeVal();
int x = a.x;                  // 컴파일된다. 컴파일러는 a가 초기화됐다고 본다

SomeVal b;
int y = b.x;                  // 컴파일 오류 CS0170:
                              // 할당되지 않았을 수 있는 필드 'x'를 사용했다
```

`new`를 썼든 안 썼든 CLR은 필드를 0으로 채운다. `new`를 쓰면 C# 컴파일러가 "이 인스턴스는 초기화됐다"고 **생각**할 뿐이다. 확정 할당 규칙 자체는 6.9절에서 다뤘다.

두 번째 경우도 필드를 하나씩 전부 채우면 사용할 수 있다.

```csharp
SomeVal b;
b.x = 1;
b.y = 2;
int y = b.x;                  // 이제 컴파일된다
```

### 컴파일 결과 — `initobj`, `call .ctor`, `newobj`

구조체 생성은 IL에서 세 가지 형태 중 하나로 나온다.

```csharp
Point p1 = new Point();       // 매개변수 없는 생성 (① initobj)
Point p2 = new Point(1, 2);   // 매개변수 있는 생성, 지역 변수 대상 (② call .ctor)
Consume(new Point(1, 2));     // 결과를 값으로 바로 써야 함 (③ newobj)
```

```il
  .locals init ([0] valuetype Point p1,
                [1] valuetype Point p2)

  // ① Point p1 = new Point();
  IL_0000:  ldloca.s   p1              // 지역 변수의 주소
  IL_0002:  initobj    Point           // 그 주소의 메모리를 0으로 채운다

  // ② Point p2 = new Point(1, 2);
  IL_0008:  ldloca.s   p2              // 지역 변수의 주소
  IL_000a:  ldc.i4.1
  IL_000b:  ldc.i4.2
  IL_000c:  call       instance void Point::.ctor(int32, int32)

  // ③ Consume(new Point(1, 2));
  IL_0011:  ldc.i4.1
  IL_0012:  ldc.i4.2
  IL_0013:  newobj     instance void Point::.ctor(int32, int32)
  IL_0018:  call       void Program::Consume(valuetype Point)
```

읽어야 할 것은 셋이다.

- **`initobj`** — "지정한 주소에 있는 값 타입의 각 필드를 적절한 원시 타입의 null 참조 또는 0으로 초기화한다." 힙 할당이 아니다. 이미 확보된 메모리를 0으로 미는 명령이다.
- **`call ... .ctor`** — 값 타입 생성자는 이미 존재하는 저장소의 **주소**를 `this`로 받는다. 참조 타입처럼 "객체를 만들어서 참조를 돌려주는" 것이 아니다.
- **`newobj`** — 값 타입에도 `newobj`가 쓰인다. 다만 힙 할당을 뜻하지 않는다. 값 타입에 대한 `newobj`는 임시 저장소를 확보하고 생성자를 호출한 다음, **결과 값을 평가 스택에 남긴다.**

> **📌 `newobj`가 보인다고 힙 할당은 아니다**
>
> IL에서 `newobj`를 보면 반사적으로 "힙 할당"을 떠올리기 쉽지만, 피연산자가 값 타입 생성자이면 힙 할당이 아니다. 힙 할당 여부는 명령이 아니라 **피연산자의 타입 종류**로 판단해야 한다.
>
> 할당 추적 도구가 값 타입 `newobj`를 할당으로 세지 않는 것도 같은 이유다. 실제로 무엇이 힙에 가는지는 63.3절, 63.9절에서 다룬다.

### 암시적 매개변수 없는 생성자는 언제나 존재한다

이것이 구조체 생성 의미론의 뿌리다.

**직접 정의한 생성자와 별개로, 구조체에는 언제나 필드를 비트 단위로 0으로 만드는 암시적 매개변수 없는 생성자가 존재한다.**

```csharp
struct Point { int x, y; }

Point p = new Point();   // p.x와 p.y는 0이다
```

C# 10 이전에는 이 문장이 전부였다. 구조체는 매개변수 없는 생성자를 **정의할 수 없었고**(`CS0568`), 인스턴스 필드에 초기화자를 붙일 수도 **없었다**(`CS0573`). 규칙이 단순해서 헷갈릴 여지가 없었다.

### ※C# 10 — 필드 초기화자와 매개변수 없는 생성자가 허용됐다

C# 10부터 두 금지가 모두 풀렸다. 주된 동기는 **레코드 구조체**(19.2절)를 지원하기 위해서였다.

```csharp
struct Point
{
    int x = 1;                      // ※C# 10: 필드 초기화자 허용
    int y;
    public Point() => y = 1;        // ※C# 10: 매개변수 없는 생성자 허용
}
```

그런데 여기서 문제가 시작된다.

```csharp
Point p1 = new Point();   // p1.x와 p1.y는 둘 다 1이다
Point p2 = default;       // p2.x와 p2.y는 둘 다 0이다
```

`x`는 필드 초기화자로 1이 됐고 `y`는 매개변수 없는 생성자로 1이 됐다. 그런데 `default` 키워드를 쓰면 **두 초기화를 모두 우회한** `Point`를 만들 수 있다. 즉 매개변수 없는 생성자가 사실상 **두 개** 존재하는 셈이다 — 내가 쓴 것과, 언어가 보장하는 0 채우기.

> **⚠️ 우회 경로는 `default` 하나가 아니다**
>
> 사용자가 `default`를 쓰지 않아도 생성자가 건너뛰어지는 경로가 널려 있다.
>
> ```csharp
> var points = new Point[10];   // 배열 원소 10개 전부 (0, 0)
>
> var test = new Test();        // test.p는 (0, 0)
> class Test { Point p; }
> ```
>
> 배열을 만들면 원소마다 생성자가 호출되는 것이 아니라 **배열 전체 메모리가 0으로 채워질 뿐**이다. 클래스의 필드도 마찬가지다 — 클래스 인스턴스가 0으로 초기화되면 그 안의 구조체 필드도 0이 된다.
>
> 이런 경로가 더 있다.
>
> | 경로 | 매개변수 없는 생성자 실행 여부 |
> |---|---|
> | `new Point()` | 실행 |
> | `default` / `default(Point)` | **건너뜀** |
> | `new Point[n]` (배열 원소) | **건너뜀** |
> | 클래스·구조체의 필드로 포함 | **건너뜀** |
> | `Array.Resize`로 늘어난 자리 | **건너뜀** |
> | `List<Point>`의 예약 용량 부분 | **건너뜀** |
> | 제네릭 `default(T)` | **건너뜀** |
> | 대부분의 역직렬화기 | 구현에 따라 다르다 |
>
> **초기화가 반드시 실행된다고 가정하는 설계는 값 타입에서 성립하지 않는다.**

> **💡 구조체에서는 필드 초기화자와 명시적 매개변수 없는 생성자를 쓰지 마라**
>
> 매개변수 없는 생성자가 사실상 두 개가 되는 것은 혼란의 원천이며, **구조체에 필드 초기화자와 명시적 매개변수 없는 생성자를 정의하지 않는 편이 낫다는 충분한 근거**다. 언어가 허용한다는 것과 써야 한다는 것은 다르다.
>
> 이 기능은 레코드 구조체를 위해 열린 문이다. 직접 `struct`를 쓸 때 그 문을 통과할 이유는 거의 없다.
>
> 대신 **기본값 자체를 유효한 상태로 설계한다.** 방법은 16.4절에 있다.

또 하나의 규칙이 있다. ※C# 10에서 구조체에 필드 초기화자를 두려면 **명시적으로 선언한 생성자가 하나 이상 있어야 한다.** 초기화자만 쓰고 생성자를 하나도 선언하지 않으면 "필드 초기화자가 있는 구조체는 명시적으로 선언된 생성자를 포함해야 한다"는 취지의 컴파일 오류가 난다. 초기화자를 실행할 자리가 없기 때문이다.

### ※C# 11 — 확정 할당 규칙의 완화

C# 11 이전에는 구조체 생성자에서 **모든 필드를 명시적으로 대입해야 했다.** 하나라도 빠뜨리면 `CS0171`("호출자에게 제어가 반환되기 전에 필드가 완전히 할당되어야 한다")이 났다.

```csharp
struct Rect
{
    public int W, H;
    public Rect(int w)          // C# 10 이전: 컴파일 오류 CS0171 — H가 대입되지 않았다
    {
        W = w;
    }
}
```

당시의 우회법은 두 가지였다.

```csharp
public Rect(int w) : this()    // ① 암시적 매개변수 없는 생성자를 먼저 부른다
{
    W = w;
}

public Rect(int w)             // ② this 전체를 통째로 덮어쓴다
{
    this = default;
    W = w;
}
```

②는 구조체에서만 가능한 문법이다. 값 타입은 데이터를 자기 안에 직접 담으므로 `this = ...`은 그저 **필드 재초기화**로 처리된다. 참조 타입에서는 불가능하다.

※C# 11부터 이 제약이 완화됐다. 대입되지 않은 필드는 컴파일러가 생성자 진입 시점에 자동으로 기본값으로 초기화한다. 대신 **경고**가 나온다 — "모든 필드가 대입되기 전에 제어가 호출자에게 반환되었고, 그래서 앞선 위치에 암시적 `default` 대입이 삽입되었다"는 취지다.

정리하면 이렇다. C# 10 이전에는 필드를 빠뜨린 구조체 생성자가 컴파일 **오류**(`CS0171`)였고, ※C# 11 이후에는 컴파일러가 자동으로 기본값을 대입하고 **경고**만 낸다.

> **⚠️ 경고를 끄지 마라**
>
> C# 11의 완화는 편의 기능이지 면허가 아니다. 이 경고는 "당신이 잊은 필드가 있다"는 정확한 신호다. 특히 `this`를 읽는 코드가 생성자 앞부분에 있으면 그 시점에 암시적 `default` 대입이 **삽입된 위치**에 따라 의도와 다른 값이 보일 수 있다.
>
> 실무 규칙은 여전히 이렇다. **구조체 생성자는 모든 필드를 명시적으로 대입한다.** 언어가 봐주더라도 사람이 읽을 때 명확해야 한다.

### 기본 생성자(primary constructor)와 구조체 ※C# 12

C# 12의 기본 생성자 문법은 구조체에도 쓸 수 있다(13.10절).

```csharp
public struct Point(int x, int y)
{
    public int X { get; } = x;
    public int Y { get; } = y;
}
```

여기에도 같은 구멍이 있다.

```csharp
Point a = new Point(3, 4);   // X=3, Y=4
Point b = default;           // X=0, Y=0 — 기본 생성자를 우회했다
Point[] c = new Point[5];    // 전부 X=0, Y=0
```

기본 생성자는 매개변수 없는 생성 경로를 **막지 못한다.** 값 타입에서 "생성자를 통과하지 않은 인스턴스는 존재할 수 없다"는 보장은 원리적으로 불가능하다.

> **📌 클래스와 구조체의 생성 규칙 대조**
>
> | 항목 | 클래스 | 구조체 |
> |---|---|---|
> | 생성자를 하나도 안 쓰면 | 컴파일러가 `public` 매개변수 없는 생성자 생성 | 언제나 암시적 0 채우기 생성자 존재 |
> | 매개변수 있는 생성자를 정의하면 | 매개변수 없는 생성자가 **사라진다** | 암시적 매개변수 없는 생성자는 **그대로 남는다** |
> | 매개변수 없는 생성자를 `private`으로 만들 수 있나 | 가능 | **불가능** — 0 채우기 경로는 언어가 보장한다 |
> | 필드 초기화자 | 언제나 가능 | ※C# 10 이후, 생성자가 있을 때만 |
> | 생성자에서 필드를 다 안 채우면 | 나머지는 0 | ※C# 11 이전 오류, 이후 경고 + 자동 0 |
> | `this = ...` 대입 | 불가능 | 가능 |
> | 파이널라이저 | 가능(13.16절) | 불가능 |
>
> 세 번째 줄이 가장 중요하다. **클래스에서는 "생성자를 통해서만 만들 수 있는 타입"을 설계할 수 있지만, 구조체에서는 불가능하다.** 이것이 다음 절의 출발점이다.

## 16.4 0이 유효한 상태여야 하는 이유

### 원칙

.NET의 기본 시스템 초기화는 모든 객체를 전부 0으로 만든다. **다른 개발자가 전부 0으로 초기화된 값 타입 인스턴스를 만드는 것을 막을 방법은 없다.** 그러니 그것을 당신 타입의 기본값으로 삼아라.

앞 절에서 본 것이 근거다. `default`, 배열 원소, 다른 타입의 필드, 제네릭 `default(T)` — 생성자를 우회하는 경로가 너무 많고, 그중 어느 것도 막을 수 없다. 값 타입 설계자에게 남은 선택지는 하나뿐이다. **모든 비트가 0인 상태에 의미를 부여하는 것.**

> **💡 이 규칙 하나가 값 타입 설계의 절반이다**
>
> "0이 유효해야 한다"는 규칙은 사소해 보이지만, 실제로는 값 타입 설계 전체를 규율한다. 이 규칙을 지키려고 노력하다 보면 자연스럽게 다음이 따라온다.
>
> - 필수 필드를 줄이게 된다 (0이 의미 있는 필드만 남기게 되므로)
> - 유효성 검사를 생성자에 몰아넣지 않게 된다 (어차피 우회되므로)
> - 프로퍼티로 감싸게 된다 (0을 다른 값으로 번역할 자리가 필요하므로)
> - 불변으로 만들게 된다 (상태 전이가 없으면 유효성 문제도 줄어든다)
>
> 결국 16.4절과 16.5절은 같은 결론의 두 측면이다.

### 사례 ① — 열거형에 0이 없을 때

특별한 경우가 열거형이다. **0을 유효한 선택지로 포함하지 않는 열거형을 절대 만들지 마라.**

```csharp
public enum Planet
{
    // 값을 명시적으로 지정했다. 기본값은 0부터 시작했을 것이다
    Mercury = 1,
    Venus = 2,
    Earth = 3,
    Mars = 4,
    Jupiter = 5,
    Saturn = 6,
    Uranus = 7,
    Neptune = 8
}

Planet sphere = new Planet();
var anotherSphere = default(Planet);
```

`sphere`와 `anotherSphere`는 둘 다 0이고, **0은 유효한 값이 아니다.** 열거형이 정의된 값 집합으로 제한된다는 (정상적인) 사실에 의존하는 코드는 전부 깨진다.

이 상태는 그 열거형을 담는 다른 값 타입으로 전염된다.

```csharp
public struct ObservationData
{
    private Planet whichPlanet;   // 무엇을 관측하고 있는가
    private double magnitude;     // 관측된 밝기
}

ObservationData d = new ObservationData();
```

새로 만든 `ObservationData`의 밝기 0은 합리적이다. 그런데 행성은 유효하지 않다. 처방은 0을 유효한 상태로 만드는 것이다. 가능하면 **가장 좋은 기본값을 0에 배정하고**, 그럴 만한 값이 없으면 **"초기화되지 않음"을 뜻하는 0 케이스를 만든다.**

```csharp
public enum Planet
{
    None = 0,        // ← 추가
    Mercury = 1,
    Venus = 2,
    Earth = 3,
    Mars = 4,
    Jupiter = 5,
    Saturn = 6,
    Uranus = 7,
    Neptune = 8
}
```

이제 `new Planet()`은 `None`이 된다. 이 변경은 `ObservationData`까지 거슬러 올라가 파급된다 — 새로 만든 `ObservationData`는 밝기 0에 대상 `None`을 갖는다.

명시적 생성자를 추가해 사용자가 필드를 전부 초기화할 수 있게 해 줄 수는 있다.

```csharp
public struct ObservationData
{
    Planet whichPlanet;
    double magnitude;

    ObservationData(Planet target, double mag)
    {
        whichPlanet = target;
        magnitude = mag;
    }
}
```

그러나 **매개변수 없는 생성자는 여전히 보이고 구조체의 일부다.** 사용자는 시스템 초기화된 변형을 만들 수 있고, 그것을 막을 수 없다.

> **⚠️ "아무것도 관측하지 않는 관측 데이터"는 여전히 말이 안 된다**
>
> 위 처방은 완전한 해결이 아니다. `None`을 관측하고 있다는 상태 자체가 의미가 없다면, 그 타입은 애초에 값 타입이 아니어야 한다.
>
> `ObservationData`를 **클래스로 바꾸면** 매개변수 없는 생성자를 접근 불가능하게 만들 수 있으므로 이 문제가 사라진다. 이것도 하나의 답이다 — 16.8절의 판단 기준에 "0이 유효한 상태가 될 수 없는가"를 넣어야 하는 이유다.
>
> 다만 열거형에는 이 탈출구가 없다. 열거형을 만들 때는 다른 개발자에게 규칙을 강제할 방법이 없다. 열거형은 정수 위의 얇은 포장이다. **정수 상수의 집합이 필요한 추상을 제공하지 못한다면 다른 언어 기능을 고려해야 한다.**

### 사례 ② — `[Flags]` 열거형

플래그로 쓰는 열거형에는 특별 규칙이 하나 더 있다. `Flags` 특성을 쓰는 열거형은 **언제나 `None` 값을 0으로 설정해야 한다.**

```csharp
[Flags]
public enum Styles
{
    None = 0,
    Flat = 1,
    Sunken = 2,
    Raised = 4,
}
```

많은 개발자가 플래그 열거형을 비트 AND 연산자와 함께 쓴다. 0 값은 비트 플래그에서 심각한 문제를 일으킨다. `Flat`이 0이라면 다음 검사는 **절대 참이 되지 않는다.**

```csharp
Styles flag = Styles.Sunken;
if ((flag & Styles.Flat) != 0)      // Flat == 0이면 절대 참이 아니다
    DoFlatThings();
```

`Flags`를 쓴다면 **0이 유효하고, 그것이 "모든 플래그의 부재"를 의미하도록** 보장하라. 열거형 전반은 20장, 비트 플래그 패턴은 20.3절에서 다룬다.

### 사례 ③ — 참조를 담은 값 타입

또 하나의 흔한 초기화 문제는 **참조를 포함하는 값 타입**이다. 문자열이 대표적이다.

```csharp
public struct LogMessage
{
    private int ErrLevel;
    private string msg;
}

LogMessage MyMessage = new LogMessage();
```

`MyMessage`의 `msg` 필드에는 **null 참조**가 들어 있다. 다른 초기화를 강제할 방법은 없다. 그러나 **프로퍼티로 문제를 국소화할 수는 있다.**

```csharp
public struct LogMessage
{
    private int ErrLevel;
    private string msg;

    public string Message
    {
        get => msg ?? string.Empty;
        set => msg = value;
    }
}
```

`msg`의 값을 클라이언트에게 노출하는 프로퍼티를 만들고, 게터에 null 대신 빈 문자열을 반환하는 논리를 넣었다. 그리고 **당신의 타입 내부에서도 이 프로퍼티를 쓴다.** 그렇게 하면 null 검사가 한 곳으로 국소화된다. `Message` 접근자는 같은 어셈블리 안에서 호출될 때 거의 확실히 인라인되므로, 효율적인 코드를 얻으면서 오류를 최소화한다.

같은 기법이 "0이 아닌 기본값"을 표현하는 데도 쓰인다.

```csharp
// 이렇게 쓰지 말고
public string Protocol { get; set; } = "https";

// 이렇게 쓴다
struct WebOptions
{
    string protocol;
    public string Protocol
    {
        get => protocol ?? "https";
        set => protocol = value;
    }
}
```

첫 번째 형태는 필드 초기화자다. 앞 절에서 본 대로 `default(WebOptions)`나 배열 원소에서는 실행되지 않으므로 `Protocol`이 `null`이 된다. 두 번째 형태는 **0 상태(= `null`)를 게터에서 원하는 기본값으로 번역한다.** 어떤 경로로 만들어진 인스턴스든 `Protocol`은 항상 `"https"`이거나 사용자가 설정한 값이다.

> **📌 이 관용구를 "게으른 기본값(lazy default)"이라고 부른다**
>
> 핵심은 **저장된 상태와 관측되는 상태를 분리하는 것**이다. 저장된 상태는 언어가 0으로 만든다. 관측되는 상태는 프로퍼티가 정의한다. 그 사이에 번역 계층을 두면 0 초기화 문제가 사라진다.
>
> BCL도 같은 기법을 쓴다. `System.Threading.CancellationToken`의 기본값은 "취소될 수 없는 토큰"으로 동작하고, `default(TimeSpan)`은 0틱이며, `default(Guid)`는 `Guid.Empty`와 같다. 어느 것도 예외를 던지지 않는다.

### BCL 값 타입의 기본값 사전

`default`가 무엇을 주는지는 자주 확인하게 되는 정보다.

| 타입 | `default` 값 | 유효한 상태인가 |
|---|---|---|
| `int`, `long`, `double` 등 숫자 | `0` | 예 |
| `bool` | `false` | 예 |
| `char` | `'\0'` | 예 (다만 문자로 출력하면 보이지 않는다) |
| `decimal` | `0m` | 예 |
| `Guid` | 모든 비트 0 (`Guid.Empty`) | 예 — "지정되지 않은 GUID"로 통용된다 |
| `TimeSpan` | `TimeSpan.Zero` | 예 |
| `DateTime` | `0001-01-01 00:00:00`, `Kind`는 `Unspecified` | **주의** — `DateTime.MinValue`이지 "오늘"이 아니다 |
| `DateTimeOffset` | `0001-01-01 00:00:00 +00:00` | **주의** — 위와 같다 |
| `int?` 등 `Nullable<T>` | `HasValue == false` (즉 `null`) | 예 — 설계상 0이 "값 없음"이다(21.1절) |
| `ValueTuple<...>` | 각 요소의 `default` | 예 |
| 열거형 | 기저 정수 0 | **설계자에게 달렸다** |
| 사용자 정의 `struct` | 모든 필드의 `default` | **설계자에게 달렸다** |

> **⚠️ `default(DateTime)`을 "지정 안 됨"으로 쓰는 코드**
>
> 실무에서 가장 자주 보는 0 관련 사고다.
>
> ```csharp
> public struct Reservation
> {
>     public DateTime CheckIn;     // default면 0001-01-01
>     public DateTime CheckOut;
> }
> ```
>
> `default(Reservation)`은 "서기 1년 1월 1일에 체크인해서 같은 날 체크아웃하는 예약"이다. 이 값이 데이터베이스로 흘러 들어가면 `datetime` 컬럼의 범위를 벗어나 저장 시점에 예외가 나거나, 최소값으로 잘려 저장된다.
>
> 처방은 셋 중 하나다. **① `DateTime?`을 쓴다** — `null`이 "지정 안 됨"이 되고 기본값도 `null`이다. **② 프로퍼티에서 번역한다** — 0 값을 감지해 의미 있는 값으로 바꾼다. **③ 이 타입을 클래스로 만든다.**
>
> 마지막 줄이 왜 답이 될 수 있는지가 16.8절의 주제다.

### 설계 처방 요약

| 상황 | 처방 |
|---|---|
| 열거형에 자연스러운 기본값이 있다 | 그 값을 0에 배정한다 |
| 열거형에 자연스러운 기본값이 없다 | `None = 0` 또는 `Unspecified = 0`을 추가한다 |
| `[Flags]` 열거형 | `None = 0`, "모든 플래그의 부재" |
| 구조체가 참조 필드를 담는다 | 프로퍼티 게터에서 `?? 기본값`으로 번역한다 |
| 구조체에 0이 아닌 기본값이 필요하다 | 필드 초기화자 대신 프로퍼티 게터에서 번역한다 |
| 0 상태에 의미를 부여할 방법이 없다 | **값 타입이 아닌 참조 타입으로 만든다** |

## 16.5 `readonly struct`와 `readonly` 멤버 — 방어적 복사 제거

### 값 타입에 불변성을 선호하라

16.2절에서 방어적 복사를, 16.4절에서 0 초기화 문제를 봤다. 두 문제의 해법이 같은 방향을 가리킨다 — **불변성**이다.

불변 타입은 단순하다. 만들어진 다음에는 상수다. 객체를 만들 때 쓴 매개변수의 유효성을 검사했다면, 그 시점 이후로 객체가 유효한 상태에 있다는 것을 안다. 객체를 유효하지 않게 만들 수 있는 내부 상태 변경이 불가능하다. **객체가 만들어진 다음의 모든 상태 변경을 금지함으로써, 그러지 않았다면 필요했을 많은 오류 검사를 아낀다.**

거기에 셋이 더 붙는다.

- **본질적으로 스레드 안전하다.** 여러 판독자가 같은 내용에 접근할 수 있다. 내부 상태가 바뀔 수 없으면 다른 스레드가 일관성 없는 데이터를 볼 가능성이 없다.
- **안전하게 내보낼 수 있다.** 호출자가 당신 객체의 내부 상태를 수정할 수 없다.
- **해시 기반 컬렉션에서 더 잘 동작한다.** `Object.GetHashCode()`가 반환하는 값은 인스턴스 불변이어야 하는데, 불변 타입에서는 그것이 언제나 참이다(24.7절, 25.8절).

### 가변 구조체가 만드는 문제 — 구체적으로

주소를 표현하는 가변 구조체를 보자.

```csharp
// 가변 Address 구조체
public struct Address
{
    private string state;
    private int zipCode;

    public string Line1 { get; set; }
    public string Line2 { get; set; }
    public string City  { get; set; }

    public string State
    {
        get => state;
        set { ValidateState(value); state = value; }
    }

    public int ZipCode
    {
        get => zipCode;
        set { ValidateZip(value); zipCode = value; }
    }
}
```

사용은 이렇게 된다.

```csharp
Address a1 = new Address();
a1.Line1 = "111 S. Main";
a1.City = "Anytown";
a1.State = "IL";
a1.ZipCode = 61111;

// 이사했다
a1.City = "Ann Arbor";     // 이 시점에서 ZIP과 State가 유효하지 않다
a1.ZipCode = 48103;        // 아직 State가 유효하지 않다
a1.State = "MI";           // 이제 괜찮다
```

내부 상태 변경은 최소한 일시적으로 객체 불변식(invariant)을 위반할 수 있음을 뜻한다. `City` 필드를 바꾼 다음 `a1`은 유효하지 않은 상태다 — 도시가 바뀌었고 더는 주(state)나 우편번호와 맞지 않는다.

코드는 무해해 보인다. 그러나 이것이 다중 스레드 프로그램의 일부라고 하자. **도시가 바뀐 다음, 주가 바뀌기 전에 일어나는 컨텍스트 전환은 다른 스레드가 일관성 없는 데이터를 볼 여지를 남긴다.**

멀티스레드가 아니라도 곤란해질 수 있다. 우편번호가 유효하지 않아서 세터가 예외를 던졌다고 하자. 의도한 변경 중 일부만 적용됐고, 시스템은 유효하지 않은 상태로 남는다.

이 문제를 고치려면 `Address` 구조체에 상당한 내부 유효성 검사 코드를 추가해야 한다. 그 검사 코드는 상당한 크기와 복잡도를 더한다. 예외 안전성을 완전히 구현하려면 필드를 두 개 이상 바꾸는 모든 코드 블록 주위에 방어적 복사를 만들어야 한다. 스레드 안전성을 위해서는 게터와 세터 양쪽 모든 프로퍼티 접근자에 상당한 스레드 동기화 검사를 추가해야 한다. **전부 합치면 상당한 작업이고, 새 기능을 추가할 때마다 계속 늘어날 작업이다.**

### 불변으로 다시 쓰기

```csharp
public struct Address
{
    public string Line1 { get; }
    public string Line2 { get; }
    public string City  { get; }
    public string State { get; }
    public int ZipCode  { get; }

    public Address(string line1, string line2, string city,
                   string state, int zipCode) : this()
    {
        Line1 = line1;
        Line2 = line2;
        City = city;
        ValidateState(state);
        State = state;
        ValidateZip(zipCode);
        ZipCode = zipCode;
    }
}
```

불변 타입을 쓰려면 상태를 바꾸는 호출 순서가 달라진다. 기존 인스턴스를 수정하는 대신 **새 객체를 만든다.**

```csharp
Address a2 = new Address("111 S. Main", "", "Anytown", "IL", 61111);

// 바꾸려면 다시 초기화한다
a2 = new Address(a1.Line1, a1.Line2, "Ann Arbor", "MI", 48103);
```

`a1`의 값은 두 상태 중 하나다 — 원래의 Anytown 위치, 또는 갱신된 Ann Arbor 위치. 앞 예제의 유효하지 않은 임시 상태를 만들기 위해 기존 주소를 수정하지 않는다. 그 중간 상태들은 `Address` 생성자가 실행되는 동안에만 존재하고 생성자 바깥에서는 보이지 않는다. **예외 안전하기도 하다** — `a1`은 원래 값이거나 새 값이다. 새 `Address` 객체를 만드는 도중 예외가 던져지면 `a1`의 원래 값은 바뀌지 않는다.

> **⚠️ 불변 타입에도 구멍이 있다 — 가변 참조 필드**
>
> 불변 타입을 만들려면 클라이언트가 내부 상태를 바꿀 수 있는 구멍이 없는지 확인해야 한다. 값 타입은 파생 타입을 지원하지 않으므로 파생 타입이 필드를 수정하는 것을 방어할 필요는 없다. 그러나 **불변 타입 안에 있는 가변 참조 타입 필드**는 감시해야 한다.
>
> ```csharp
> // 거의 불변이다. 상태 변경을 허용하는 구멍이 있다
> public struct PhoneList
> {
>     private readonly Phone[] phones;
>     public PhoneList(Phone[] ph) { phones = ph; }
>     public IEnumerable<Phone> Phones => phones;
> }
>
> Phone[] phones = new Phone[10];
> PhoneList pl = new PhoneList(phones);
>
> phones[5] = Phone.GeneratePhoneNumber();   // 불변이어야 할 객체의 내부가 바뀐다
> ```
>
> 배열은 참조 타입이다. `PhoneList` 구조체 안에서 참조하는 배열은 객체 바깥에서 할당된 것과 **같은 배열 저장소**를 가리킨다. 개발자는 같은 저장소를 참조하는 다른 변수를 통해 당신의 불변 구조체를 수정할 수 있다.
>
> 처방은 배열의 **방어적 복사본**을 만들거나, `System.Collections.Immutable`의 `ImmutableList<T>`를 쓰는 것이다.
>
> ```csharp
> public struct PhoneList
> {
>     private readonly ImmutableList<Phone> phones;
>     public PhoneList(Phone[] ph) { phones = ph.ToImmutableList(); }
>     public IEnumerable<Phone> Phones => phones;
> }
> ```
>
> `Phone`이 가변 **참조 타입**이라면 문제가 더 커진다. 컬렉션 자체가 수정으로부터 보호되더라도 클라이언트가 컬렉션 안의 값을 수정할 수 있다.

### 불변 타입을 초기화하는 세 가지 전략

타입의 복잡도가 어떤 전략을 쓸지 결정한다.

- **생성자** — 필드 조합이 단순하고 개수가 적을 때. 위 `Address`가 그렇다. 합리적인 생성자 집합을 정의하는 것이 대체로 가장 단순한 접근이다.
- **팩터리 메서드** — 흔히 쓰이는 값을 만들기 쉽게 하고 싶을 때. .NET의 `Color` 타입이 시스템 색을 초기화하는 데 이 전략을 쓴다. 정적 메서드 `Color.FromKnownColor()`와 `Color.FromName()`이 주어진 시스템 색의 현재 값을 나타내는 색 값의 복사본을 반환한다.
- **가변 동반 클래스** — 불변 타입을 완전히 구성하는 데 여러 단계 연산이 필요할 때. .NET의 `string` 클래스가 `System.Text.StringBuilder`와 함께 이 전략을 쓴다. 여러 연산으로 문자열을 만든 다음, `StringBuilder`에서 불변 문자열을 꺼낸다.

**복사 생성자는 필요 없다.** 대입 연산자가 정확히 같은 일을 같은 효율로 하기 때문이다. 그리고 **매개변수 없는 생성자는 여전히 접근 가능하다** — 모든 문자열이 `null`이고 우편번호가 0인 기본 주소가 존재한다. 16.4절의 규칙이 여기서도 그대로 적용된다.

### `readonly struct` — 컴파일러에게 불변성을 알린다

지금까지의 불변성은 **관례**였다. 필드를 `readonly`로 두거나 프로퍼티를 게터 전용으로 두는 것은 설계자의 규율일 뿐이고, 컴파일러는 그것을 타입 수준의 사실로 알지 못한다.

`readonly` 수정자를 구조체에 적용하면 **모든 필드가 `readonly`임을 강제**할 수 있다. 의도를 선언하는 데 도움이 되고, 컴파일러에게 더 많은 최적화 자유를 준다.

```csharp
readonly struct Point
{
    public readonly int X, Y;      // X와 Y는 readonly여야 한다
}
```

C# 컴파일러는 구조체의 모든 필드가 `readonly`로 정의되어 있는지 강제한다. 아니면 컴파일 오류다.

```csharp
public readonly struct ReadonlyBook
{
    public readonly string Title;
    public readonly string Author;

    public ReadonlyBook(string title, string author)
    {
        this.Title = title;
        this.Author = author;
    }

    public void ModifyAuthor()
    {
        // this.Author = "XXX";   // 컴파일 오류:
        //   readonly 필드는 생성자나 변수 초기화자 외에서 대입할 수 없다
        Console.WriteLine(this.Author);
    }
}
```

### 컴파일 결과

`readonly struct`는 IL 메타데이터에 흔적을 남긴다. 타입에 `System.Runtime.CompilerServices.IsReadOnlyAttribute`가 적용된다.

```il
.class public sequential ansi sealed beforefieldinit ReadonlyBook
       extends [System.Runtime]System.ValueType
{
  .custom instance void [System.Runtime]System.Runtime.CompilerServices.IsReadOnlyAttribute::.ctor()
           = ( 01 00 00 00 )
  .field public initonly string Title
  .field public initonly string Author
  // ...
}
```

두 가지를 보면 된다.

- 타입에 `IsReadOnlyAttribute`가 붙었다. 이 어셈블리를 참조하는 **다른** 어셈블리의 컴파일러가 이 사실을 읽고 방어적 복사를 생략한다.
- 필드에 `initonly`가 붙었다. C#의 `readonly` 필드가 IL에서는 `initonly`다(10.11절).

### 런타임 동작 — 방어적 복사가 사라진다

16.2절의 다섯 자리가 전부 정리된다.

```csharp
readonly struct Vec3
{
    public readonly double X, Y, Z;
    public Vec3(double x, double y, double z) => (X, Y, Z) = (x, y, z);
    public double GetLength() => Math.Sqrt(X * X + Y * Y + Z * Z);
}

static double Sum(in Vec3 a, in Vec3 b) => a.GetLength() + b.GetLength();
```

```il
  // a.GetLength()  ← Vec3가 readonly struct일 때
  IL_0000:  ldarg.0                                   // 관리 포인터를 그대로
  IL_0001:  call       instance float64 Vec3::GetLength()
```

`ldobj`도, `stloc`도, `ldloca`도 없다. **복사가 통째로 사라졌다.** 컴파일러가 `GetLength()`가 필드를 고칠 수 없음을 타입 선언에서 알기 때문이다.

같은 일이 `readonly` 필드, `ref readonly` 반환, `static readonly` 필드에서도 일어난다.

| 문맥 | 일반 `struct` | `readonly struct` |
|---|---|---|
| `readonly` 필드에서 메서드 호출 | 방어적 복사 | **복사 없음** |
| `in` 매개변수에서 메서드 호출 | 방어적 복사 | **복사 없음** |
| `ref readonly` 반환값에서 메서드 호출 | 방어적 복사 | **복사 없음** |
| `static readonly` 필드에서 메서드 호출 | 방어적 복사 | **복사 없음** |
| 프로퍼티 게터가 반환한 값 | 복사 1회 (게터 반환 자체) | 복사 1회 (게터 반환 자체) |
| `foreach` 반복 변수 | 복사 1회 | 복사 1회 |

마지막 두 줄은 `readonly struct`로도 사라지지 않는다. 게터가 값을 반환하는 것과 반복 변수에 원소를 담는 것은 **방어적 복사가 아니라 정의상의 값 복사**이기 때문이다. 그것까지 없애려면 `ref` 반환(10.3절)이나 `Span<T>`(68장)가 필요하다.

### `readonly` 멤버 ※C# 8 — 더 세밀한 통제

`readonly`를 더 세밀한 수준에서 적용해야 한다면 C# 8부터 구조체의 **함수**에 `readonly` 수정자를 적용할 수 있다. 이 함수가 필드를 수정하려 시도하면 컴파일 타임 오류가 생성된다.

```csharp
struct Point
{
    public int X, Y;
    public readonly void ResetX() => X = 0;      // 오류!
}
```

정상적인 사용은 이렇다.

```csharp
struct Accumulator
{
    private long _sum;
    private int  _count;

    public void Add(long v) { _sum += v; _count++; }        // 상태를 바꾼다

    public readonly double Average                           // 상태를 안 바꾼다
        => _count == 0 ? 0 : (double)_sum / _count;

    public readonly override string ToString()               // 재정의에도 붙는다
        => $"{_count} items, avg {Average:F2}";
}
```

`Add`는 상태를 바꿔야 하므로 `readonly`를 붙일 수 없다. `Average`와 `ToString`은 붙일 수 있고, 붙이면 `in` 매개변수나 `readonly` 필드에서 그 멤버를 호출할 때 방어적 복사가 사라진다. **타입 전체를 불변으로 만들 수 없는 가변 구조체를 다룰 때의 차선책**이다.

컴파일 결과는 `readonly struct`와 같은 특성이다. 메서드에 `IsReadOnlyAttribute`가 붙는다.

```il
.method public hidebysig instance float64 get_Average() cil managed
{
  .custom instance void [System.Runtime]System.Runtime.CompilerServices.IsReadOnlyAttribute::.ctor()
           = ( 01 00 00 00 )
  // ...
}
```

> **⚠️ `readonly` 함수가 비 `readonly` 함수를 부르면 복사가 되살아난다**
>
> `readonly` 함수가 `readonly`가 아닌 함수를 호출하면, **컴파일러가 경고를 생성하고 변경 가능성을 피하기 위해 구조체를 방어적으로 복사한다.**
>
> ```csharp
> struct Widget
> {
>     private int _n;
>     private int Compute() => _n * 2;                  // readonly가 아니다
>     public readonly int Value => Compute();           // 경고 + this의 암시적 복사
> }
> ```
>
> 경고 메시지는 "`readonly` 멤버에서 비 `readonly` 멤버를 호출하면 `this`의 암시적 복사가 발생한다"는 취지다. **이 경고는 무시하면 안 된다** — 16.2절에서 본 침묵하는 방어적 복사 중 유일하게 컴파일러가 알려 주는 자리다.
>
> 처방은 `Compute()`에도 `readonly`를 붙이는 것이다. 아래에서 위로 `readonly`를 전파해 올라가면, 결국 타입 전체를 `readonly struct`로 만들 수 있는지가 드러난다.

> **📌 자동 프로퍼티 게터는 암시적으로 `readonly`다**
>
> ```csharp
> struct S
> {
>     public int Value { get; set; }   // 게터는 자동으로 readonly로 취급된다
> }
> ```
>
> 자동 구현 프로퍼티의 게터는 백킹 필드를 읽기만 하므로 컴파일러가 알아서 `readonly`로 처리한다. 세터는 당연히 아니다. `get`만 있는 자동 프로퍼티라면 필드 자체가 `initonly`가 되므로 `readonly struct`의 조건도 만족한다.
>
> 반대로 **식 본문 프로퍼티**(`public int Value => _v * 2;`)는 자동 프로퍼티가 아니므로 `readonly`가 자동으로 붙지 않는다. 직접 써야 한다.

### `readonly` 조합 매트릭스

| 선언 | 모든 필드 `readonly` 강제 | 멤버가 상태 변경 가능 | 방어적 복사 제거 |
|---|---|---|---|
| `struct S` | 아니오 | 예 | 없음 |
| `struct S` + 일부 멤버에 `readonly` | 아니오 | 그 멤버만 불가 | 그 멤버에 한해 제거 |
| `readonly struct S` | **예** | 아니오 | **전면 제거** |
| `ref struct S` | 아니오 | 예 | 없음 (16.6절) |
| `readonly ref struct S` | **예** | 아니오 | **전면 제거** |

> **💡 새 구조체를 만들 때의 기본값은 `readonly struct`다**
>
> 실무 규칙 하나로 요약하면 이렇다. **`struct`를 쓸 때는 일단 `readonly struct`로 시작하고, 그럴 수 없는 이유가 생겼을 때만 `readonly`를 뗀다.**
>
> `readonly`를 뗄 수밖에 없는 정당한 경우는 실제로 존재한다 — 열거자(enumerator)가 대표적이다. 열거자는 본질적으로 가변 상태를 갖는다. `List<T>.Enumerator`도 `readonly`가 아니다. 그런 경우에는 개별 멤버에 `readonly`를 붙여 가능한 만큼 회수한다.
>
> 그리고 **불변 값 타입을 만드는 가장 쉬운 방법은 직접 쓰지 않는 것이다.** ※C# 10의 `readonly record struct`는 이 절의 내용 대부분을 한 줄로 해결한다(19.2절).
>
> ```csharp
> public readonly record struct Point(int X, int Y);
> ```

## 16.6 `ref struct` 기초 (심화는 68장)

### 값 타입은 어디에 사는가 — 다시 정리

`ref struct`의 존재 이유를 이해하려면 값 타입의 저장 위치부터 정리해야 한다.

참조 타입의 인스턴스는 언제나 힙에 산다. 값 타입은 **선언된 자리에 그대로** 산다. 값 타입이 매개변수나 지역 변수로 나타나면 스택에 자리 잡는다.

```csharp
void SomeMethod()
{
    Point p;             // p는 스택에 자리 잡는다
}
struct Point { public int X, Y; }
```

그러나 값 타입이 클래스의 필드로 나타나면 **힙에** 산다.

```csharp
class MyClass
{
    Point p;             // MyClass 인스턴스가 힙에 살기 때문에 힙에 산다
}
```

마찬가지로 구조체의 배열은 힙에 살고, 구조체를 박싱하면 힙으로 보내진다.

정리하면 이렇다.

| 값이 있는 곳 | 저장 위치 | 수명 |
|---|---|---|
| 메서드의 지역 변수 | 스택 또는 CPU 레지스터 | 메서드 호출(과 그 하위 호출) 동안 |
| 메서드의 인수 | 스택 또는 CPU 레지스터 | 지역 변수와 같다 |
| 참조 타입의 인스턴스 필드 | 힙 (담고 있는 객체 안에 인라인) | 담고 있는 인스턴스의 수명 |
| 값 타입의 인스턴스 필드 | 담고 있는 인스턴스와 같은 자리 | 담고 있는 인스턴스의 수명 |
| 정적 필드 | 스택이 될 수 없다 | 타입의 수명(54.5절) |
| 지역 메모리 풀 (`stackalloc`) | 스택 (활성화 프레임의 확장) | 메서드 종료 시 회수 |
| 평가 스택의 임시값 | JIT이 자유롭게 결정 — 레지스터·스택·힙 | JIT이 정확히 안다 |

한 문장으로 요약하면 이렇다. **"값 타입은 값이 지역 변수이거나 지역 메모리 풀 안에 있을 때 스택에 저장된다. 힙에 있는 다른 객체의 일부이거나 정적 필드일 때는 힙에 저장된다. 그리고 평가 스택 처리의 일부로 언제나 CPU 레지스터 안에 저장될 수 있다."** 실제 배치의 세부는 54.8절에서 다룬다.

### `ref` 수정자 — 스택에만 살도록 강제한다

구조체 선언에 `ref` 수정자를 추가하면 그 구조체가 **오직 스택에만 존재할 수 있음**이 보장된다. 힙에 존재할 수 있는 방식으로 `ref struct`를 사용하려고 시도하면 컴파일 타임 오류가 생성된다.

```csharp
ref struct Point { public int X, Y; }

var points = new Point[100];      // 오류: 컴파일되지 않는다

class MyClass
{
    Point P;                       // 오류: 컴파일되지 않는다
}
```

`ref struct`는 C# 7.2에서 도입됐으며, 주로 `Span<T>`와 `ReadOnlySpan<T>` 구조체를 위한 특수 기능이었다. `Span<T>`와 `ReadOnlySpan<T>` 인스턴스는 스택에만 존재할 수 있으므로 스택에 할당된 메모리를 안전하게 감쌀 수 있다. 고도로 최적화된 `Utf8JsonReader` 같은 타입도 같은 기법을 쓴다.

### 제약 목록

컴파일러는 `ref struct`가 오직 스택에만 할당되도록 많은 제약을 건다.

| 금지되는 것 | 이유 |
|---|---|
| 클래스나 일반 구조체의 **필드**로 선언 | 박싱되거나 힙에 실릴 수 있다 |
| **정적 필드**로 선언 | 같은 이유 |
| **박싱** — `object`, `dynamic`, 인터페이스 타입으로의 대입/캐스팅 | 정의상 힙으로 간다 |
| **배열 원소**로 사용 | 배열 원소는 힙에 산다 |
| **반복자**(`yield return`)에서 상태 기계에 캡처 | 상태 기계는 숨은 클래스다 |
| **`async` 메서드의 지역 변수** | 비동기 상태 기계에 박싱될 수 있다 |
| **람다식·지역 함수에서 캡처** | 클로저 클래스가 필드로 담는다 |
| **제네릭 타입 인수**로 사용 | 런타임 제약이다 — ※C# 13에서 `allows ref struct`로 완화되기 시작했다 |

한 줄로 묶으면 이렇다. **`ref struct`는 직접적으로든 간접적으로든 힙에 존재할 가능성을 만드는 어떤 C# 기능에도 참여할 수 없다.** 여기에는 람다식, 반복자, 비동기 함수 같은 고급 기능이 포함되는데, 이 셋은 무대 뒤에서 전부 **필드를 가진 숨은 클래스를 만들기** 때문이다.

`ref struct`가 다른 `ref struct`의 필드가 되는 것은 가능하다.

```csharp
public ref struct RefBook
{
    public string Title;
    public string Author;
    public RefPublisher Publisher;    // 다른 ref struct는 필드가 될 수 있다
}

public ref struct RefPublisher
{
    public string Name;
}
```

컴파일 결과에는 `System.Runtime.CompilerServices.IsByRefLikeAttribute`가 타입에 붙는다. 이 특성이 CLR과 다른 컴파일러에게 "이 타입은 byref 같은(byref-like) 타입이다"라고 알린다.

> **📌 왜 "byref-like"라고 부르나**
>
> 관리 포인터(managed pointer)를 CLR 용어로 **byref**라고 부른다. 관리 포인터는 힙에 있을 수 없다 — 힙에 있으면 그것이 가리키던 스택 주소보다 오래 살아남을 수 있고, 그러면 다른 메서드의 데이터를 가리키는 위험한 상태가 된다.
>
> `ref struct`는 **필드로 관리 포인터를 담을 수 있는 타입**이며(※C# 11의 `ref` 필드, 68.11절), 그래서 관리 포인터 자신과 같은 제약을 물려받아야 한다. 그래서 "byref 같은 타입"이다.

### `ref struct`가 주는 두 가지 보장

제약의 대가로 얻는 것이 둘 있다.

- **절대 힙에 할당되지 않는다.** 수명 보장이 매우 강하므로 특별한 방식으로 사용할 수 있다. 관리 포인터를 필드에 저장할 수 있는 것이 대표적이다.
- **절대 여러 스레드에서 접근되지 않는다.** 스택 주소를 스레드 간에 전달하는 것은 불법이므로, 스택에 할당된 `ref struct`는 자기 스레드에서만 접근된다는 것이 보장된다. 동기화 비용 없이 성가신 경쟁 조건을 원천적으로 제거한다.

`readonly ref struct`로 두 기능을 결합하면 **스택에만 존재하는 불변 구조체**를 선언할 수 있다. 컴파일러와 JIT 컴파일러가 방어적 복사 제거 같은 추가 최적화를 할 수 있게 돕는다. `ReadOnlySpan<T>` 자신이 이렇게 선언되어 있다.

> **⚠️ `ref struct`를 "성능 좋은 struct"로 오해하지 마라**
>
> `ref struct`는 성능 최적화 수단이 아니라 **수명 제약을 표현하는 도구**다. 일반 구조체를 `ref struct`로 바꾼다고 빨라지지 않는다. 오히려 쓸 수 있는 자리가 극단적으로 줄어든다.
>
> `ref struct`가 필요한 경우는 사실상 하나다. **타입이 다른 메모리 영역을 가리키는 포인터나 참조를 필드로 담고, 그 메모리보다 오래 살면 안 될 때.** `Span<T>`, `ReadOnlySpan<T>`, 그리고 그것들을 감싸는 파서·리더·열거자 정도다.
>
> 그 밖의 경우에 `ref struct`를 붙이면 컬렉션에 담을 수도, `async` 메서드에서 쓸 수도, 람다에서 캡처할 수도 없는 타입을 만들 뿐이다.

`ref struct`의 진짜 쓰임 — `Span<T>`의 내부 구조, `ref` 필드와 `scoped`, 전방 전용 열거자 패턴, 안전한 `stackalloc` — 는 전부 68장에서 다룬다. 이 장에서 알아야 할 것은 **"이런 종류의 구조체가 존재하고, 이런 제약을 가진다"** 까지다.

## 16.7 기본 `Equals`/`GetHashCode`가 느린 이유와 재정의

### 기본 구현이 무엇을 하는가

15.6절에서 본 것을 요약한다. `System.ValueType`은 `Object`의 `Equals`와 `GetHashCode`를 **재정의한다.**

- `ValueType.Equals` — 두 객체의 필드 값이 일치하면 `true`를 반환한다. 내부적으로 다음 순서다.
  1. `obj` 인수가 `null`이면 `false`.
  2. `this`와 `obj`가 서로 다른 타입이면 `false`.
  3. 타입이 정의한 각 인스턴스 필드에 대해, 그 필드의 `Equals`를 호출해 비교한다. 하나라도 다르면 `false`.
  4. `true`. `Object`의 `Equals`는 호출하지 않는다.
- `ValueType.GetHashCode` — 객체의 인스턴스 필드 값들을 고려하는 알고리즘으로 해시 코드 값을 만든다.

동작 자체는 옳다. `Equals`는 값 동등성을 정확히 구현하고, `GetHashCode`는 같은 값에 같은 해시를 준다. 문제는 **어떻게** 그것을 하는가다.

### 왜 느린가 — 이유 셋

#### ① 리플렉션

`ValueType`은 자기를 상속한 타입이 어떤 필드를 갖는지 컴파일 타임에 알 수 없다. 올바른 동작을 제공하려면 런타임 타입을 모르는 채로 파생 타입의 모든 멤버 필드를 비교해야 한다. C#에서 그것은 **리플렉션을 쓴다**는 뜻이다.

CLR의 리플렉션 메커니즘은 느리다(57장). 그리고 동등성은 프로그램에서 자주 호출되는 근본적인 구성물이다. **자기 값 타입을 정의할 때는 `Equals`를 재정의하고 직접 구현을 제공해서 값 동등성 비교의 성능을 개선해야 한다.**

현대 런타임에는 빠른 경로가 있다 — 구조체에 참조 필드가 없고, 패딩 때문에 쓰레기 바이트가 낄 여지가 없고, `Equals`를 재정의한 필드가 없으면 메모리 블록 비교로 처리한다. 그러나 15.6절에서 본 대로 **`string` 필드 하나, `double` 필드 하나만 있어도 그 조건이 깨지고 조용히 리플렉션 경로로 떨어진다.** 어느 경로를 타는지가 타입 정의의 사소한 변경으로 바뀌므로 신뢰할 수 없다.

#### ② 박싱

`ValueType.Equals`의 시그니처는 `bool Equals(object obj)`다. 값 타입 인수를 `object`로 받으려면 **박싱해야 한다.**

```csharp
struct Point { public int X, Y; }

Point a = new Point(), b = new Point();
bool eq = a.Equals(b);       // b가 박싱된다 — 힙 할당 1회
```

```il
  IL_0000:  ldloca.s   a
  IL_0002:  ldloc.1
  IL_0003:  box        Point         // ← b를 박싱한다
  IL_0008:  constrained. Point
  IL_000e:  callvirt   instance bool [System.Runtime]System.Object::Equals(object)
```

동등성 비교 한 번에 힙 할당 한 번. `Dictionary<Point, T>`에 100만 번 조회하면 박스가 100만 개 생긴다. 15.7절의 박싱 체크리스트에서 값 타입의 `Equals` 재정의가 등장하는 이유다.

#### ③ 필드마다 다시 가상 호출

3단계에서 각 필드의 `Equals`를 호출한다. 필드가 값 타입이면 그 필드도 박싱될 수 있고, 그 필드가 또 `Equals`를 재정의하지 않은 구조체라면 리플렉션이 재귀적으로 다시 시작된다.

### 재정의 — 표준 형태

값 타입에 대한 권고는 단순하다. **값 타입을 만들 때는 언제나 `ValueType.Equals()`의 재정의를 만들어라.** 거의 모든 상황에서 어떤 값 타입에 대해서든 훨씬 빠른 `Equals()` 재정의를 쓸 수 있다.

전체 형태는 이렇다.

```csharp
public readonly struct Point : IEquatable<Point>
{
    public readonly int X;
    public readonly int Y;

    public Point(int x, int y) => (X, Y) = (x, y);

    // ① 타입 안전한 Equals — 박싱도 리플렉션도 없다
    public bool Equals(Point other) => X == other.X && Y == other.Y;

    // ② object 오버로드 — ①로 위임한다
    public override bool Equals(object? obj)
        => obj is Point other && Equals(other);

    // ③ GetHashCode — Equals와 같은 필드를 쓴다
    public override int GetHashCode() => HashCode.Combine(X, Y);

    // ④ 연산자 — ①로 위임한다
    public static bool operator ==(Point a, Point b) => a.Equals(b);
    public static bool operator !=(Point a, Point b) => !a.Equals(b);
}
```

네 부분이 각각 하는 일이 다르다.

| 부분 | 무엇을 해결하나 |
|---|---|
| ① `IEquatable<T>.Equals(T)` | 박싱과 리플렉션을 모두 제거한다. 제네릭 컬렉션이 이것을 찾는다 |
| ② `override Equals(object)` | `object`로 취급될 때의 동작. `ValueType`의 느린 구현을 대체한다 |
| ③ `override GetHashCode()` | 해시 기반 컬렉션. `Equals`를 재정의하면 함께 재정의해야 한다 |
| ④ `==` / `!=` | 문법적 편의. 구조체는 기본적으로 `==`를 지원하지 않는다 |

> **⚠️ `Equals`만 재정의하면 컴파일러가 경고한다**
>
> `GetHashCode`를 함께 재정의하지 않고 `Equals`만 재정의하면 C# 컴파일러가 경고를 낸다 — "`Equals(object)`를 재정의했지만 `GetHashCode()`를 재정의하지 않았다"(`CS0659`).
>
> 이유는 명확하다. `Hashtable`, `Dictionary<TKey,TValue>` 등 여러 컬렉션의 구현이 **같은 두 객체는 반드시 같은 해시 코드 값을 가져야 한다**고 요구하기 때문이다. `Equals`를 재정의한다면, 동등성을 계산하는 알고리즘과 해시 코드를 계산하는 알고리즘이 대응하도록 `GetHashCode`도 재정의해야 한다.
>
> 반대 방향도 위험하다. `GetHashCode`만 재정의하고 `Equals`를 두면 해시는 같은데 `Equals`는 다르다고 하는 상태가 생겨 딕셔너리 조회가 조용히 실패한다. **둘은 언제나 쌍이다.** 계약 전체는 25.3절과 25.4절에 있다.

### `IEquatable<T>`가 중요한 이유

②만 재정의하고 ①을 빠뜨리는 것이 흔한 실수다. 그러면 박싱이 남는다.

제네릭 컬렉션은 원소를 비교할 때 `EqualityComparer<T>.Default`를 쓴다. 이 기본 비교자는 `T`가 `IEquatable<T>`를 구현하는지 **런타임에 확인**하고, 구현했다면 `IEquatable<T>.Equals(T)`를 직접 호출한다. 구현하지 않았다면 `object.Equals(object)` 경로로 떨어지고 거기서 박싱이 발생한다.

```csharp
var set = new HashSet<Point>();
set.Add(new Point(1, 2));
set.Contains(new Point(1, 2));
```

| `Point`의 구현 | 조회 1회당 동작 |
|---|---|
| 아무것도 재정의 안 함 | `ValueType.Equals` → 박싱 + 리플렉션(또는 비트 비교) |
| `Equals(object)`만 재정의 | 박싱 1회 + 사용자 코드 |
| `IEquatable<Point>`까지 구현 | **박싱 없음, 리플렉션 없음** — 직접 호출 |

`Dictionary<TKey,TValue>`의 내부 구조와 비교자 선택 과정은 24.7절, 비교자를 외부에서 꽂는 방법은 24.13절에서 다룬다.

> **📌 `HashCode.Combine`을 쓰라**
>
> 해시 코드를 직접 조합하는 옛날 관용구는 이런 형태였다.
>
> ```csharp
> public override int GetHashCode() => X ^ Y;          // 예전 방식
> ```
>
> 이 방식은 간단하지만 분포가 나쁘다. `(1, 2)`와 `(2, 1)`이 같은 해시를 낸다. 좌표처럼 대칭적인 데이터에서 충돌이 급증한다.
>
> `System.HashCode`(※.NET Core 2.1 이후)는 검증된 알고리즘으로 조합해 준다.
>
> ```csharp
> public override int GetHashCode() => HashCode.Combine(X, Y);
> ```
>
> 필드가 여덟 개를 넘으면 `HashCode` 구조체를 직접 써서 `Add`를 반복하고 `ToHashCode()`로 마무리한다. 해시 분포 이야기는 25.4절에서 계속한다.

> **⚠️ 해시 코드 값을 절대 영속화하지 마라**
>
> 해시 테이블 컬렉션을 직접 구현하거나 `GetHashCode`를 호출하는 코드를 작성한다면, **해시 코드 값을 절대, 절대로 영구 저장하면 안 된다.** 해시 코드 값은 변경될 수 있기 때문이다. 미래 버전의 타입이 다른 알고리즘을 쓸 수 있다.
>
> 실제 사고가 있었다. 어떤 회사의 웹 사이트에서 사용자가 이름과 암호로 계정을 만들면, 사이트가 암호 `String`을 받아 `GetHashCode`를 호출하고 그 해시 코드 값을 데이터베이스에 저장했다. 사용자가 다시 로그인하면 암호를 입력받아 다시 `GetHashCode`를 호출하고 저장된 값과 비교했다. 일치하면 접근을 허용했다.
>
> 불행히도 회사가 새 버전의 CLR로 업그레이드했을 때 `String`의 `GetHashCode` 메서드가 바뀌었고, 다른 해시 코드 값을 반환하기 시작했다. **결과적으로 아무도 웹 사이트에 로그인할 수 없게 됐다.**

### 성능 영향

| 시나리오 | 재정의 없음 | 재정의 있음 |
|---|---|---|
| `a.Equals(b)` 직접 호출 | 박싱 1회 + 리플렉션 또는 비트 비교 | 필드 비교만 |
| `Dictionary<Point,V>` 조회 | 박싱 + 느린 비교 | 할당 0 |
| `List<Point>.Contains` | 박싱 + 느린 비교 | 할당 0 |
| `Array.Sort` / `OrderBy` | (`IComparable<T>` 필요) | — |
| 대량 데이터 비교 루프 | 힙 압박 + GC 유발 | 할당 0 |

숫자를 재려면 67장의 방법론이 필요하다. 다만 방향은 분명하다 — **동등성 비교가 성능에 나타날 정도로 자주 일어나는 값 타입이라면 재정의는 선택이 아니다.**

> **💡 `record struct`가 이 절 전체를 자동화한다** ※C# 10
>
> ```csharp
> public readonly record struct Point(int X, int Y);
> ```
>
> 이 한 줄이 위의 ①②③④를 전부 생성한다. 컴파일러가 만들어 주는 `Equals`는 필드별 직접 비교이고, `GetHashCode`는 `EqualityComparer<T>.Default`를 필드마다 조합한 형태이며, `IEquatable<T>`도 구현되고, `==`/`!=`도 생성된다. `ToString`과 `Deconstruct`는 덤이다.
>
> **새로 값 타입을 만드는데 동등성이 필요하다면 `record struct`가 기본 선택이다.** 직접 `struct`를 쓰고 네 부분을 손으로 쓰는 경우는 (가) 생성된 동등성 규칙이 원하는 것과 다르거나, (나) 필드 일부를 비교에서 제외해야 하거나, (다) 레코드를 쓸 수 없는 프레임워크 제약이 있을 때다. 생성되는 멤버의 전모는 19.3절, 동등성 규칙은 19.7절에 있다.

> **⚠️ 가변 구조체를 딕셔너리 키로 쓰지 마라**
>
> 해시 기반 컬렉션에 키/값 쌍을 추가하면 먼저 키 객체의 해시 코드를 얻는다. 이 해시 코드가 그 쌍이 저장될 "버킷"을 결정한다. 컬렉션이 키를 찾아야 할 때는 지정된 키 객체의 해시 코드를 다시 얻고, 그 코드가 가리키는 버킷을 순차적으로 뒤진다.
>
> 그래서 **컬렉션 안에 있는 키 객체를 바꾸면 컬렉션은 더 이상 그 객체를 찾을 수 없다.** 해시 테이블 안의 키 객체를 바꿔야 한다면, 원래의 키/값 쌍을 제거하고, 키 객체를 수정한 다음, 새 키/값 쌍을 다시 추가해야 한다.
>
> 구조체에서는 이 문제가 한 겹 더 꼬인다. 딕셔너리에 넣은 것은 **복사본**이므로 바깥의 원본을 고쳐도 딕셔너리 안의 키는 그대로다 — 이 경우에는 오히려 안전하다. 그러나 구조체가 가변 참조 타입 필드를 담고 있으면(16.5절) 그 대상을 통해 해시가 바뀔 수 있고, 그 순간 조회가 조용히 실패한다.
>
> 처방은 하나다. **키로 쓸 값 타입은 `readonly struct`로 만들고, 그 안에 가변 참조 타입을 담지 않는다.** 이 문제의 전모는 25.8절에 있다.

### `Equals`와 `==`의 관계

구조체에서 `==`는 기본적으로 **정의되지 않는다.**

```csharp
struct Point { public int X, Y; }

Point a = new Point(), b = new Point();
bool eq1 = a.Equals(b);      // 컴파일된다 — ValueType.Equals
bool eq2 = a == b;           // 컴파일 오류 — == 연산자가 정의되지 않았다
```

`int`나 `double` 같은 내장 값 타입에서 `==`가 되는 것은 CLR이 그 타입들을 특별 취급하기 때문이지 값 타입이라서가 아니다. 사용자 정의 구조체에서 `==`를 쓰려면 직접 정의해야 한다(22.1절). 그리고 정의할 때는 `Equals`와 **의미가 일치해야** 한다 — 두 연산자가 다른 답을 내는 타입은 사용자를 반드시 배신한다(22.3절).

정체성을 확인하고 싶다면 `ReferenceEquals`를 쓰라는 조언이 있지만, **값 타입에는 적용되지 않는다.** 값 타입에는 정체성이 없다.

```csharp
Point p = new Point(1, 2);
Console.WriteLine(object.ReferenceEquals(p, p));   // False
```

`ReferenceEquals`의 두 매개변수는 `object`이므로 `p`가 **두 번 박싱된다.** 서로 다른 두 박스가 만들어지고, 당연히 참조가 다르다. **값 타입에 `ReferenceEquals`를 쓰면 언제나 `false`다.**

## 16.8 `struct`를 쓸 때와 `class`를 쓸 때 — 손익 계산법

### 결정의 무게

값 타입이냐 참조 타입이냐, 구조체냐 클래스냐. 언제 무엇을 써야 하는가.

이것은 C++가 아니다 — C++에서는 모든 타입을 값 타입으로 정의하고 그것에 대한 참조를 만들 수 있다. 이것은 Java도 아니다 — Java에서는 (언어 설계자가 아닌 한) 모든 것이 참조 타입이다. C#에서는 **타입을 만들 때 그 타입의 모든 인스턴스가 어떻게 행동할지를 결정해야 한다.**

**처음에 제대로 하는 것이 중요한 결정이다.** 결정의 결과와 함께 살아야 한다. 나중에 바꾸면 코드가 미묘한 방식으로 상당히 많이 깨질 수 있기 때문이다. 타입을 만들 때 `struct`나 `class` 키워드를 고르는 것은 간단한 문제지만, 나중에 바꾸면 그 타입을 쓰는 모든 클라이언트를 갱신하는 훨씬 큰 작업이 된다.

### 마이크로소프트 지침 — 4조건

마이크로소프트의 권고는 **기본적으로 타입을 클래스로 정의하라**는 것이다. 타입이 다른 객체 안에 임베드되거나 수명이 짧다면 구조체를 고려한다. 구조체를 정의할 때는 다음 특성을 가져야 한다.

| # | 조건 | 취지 |
|---|---|---|
| 1 | 논리적으로 **단일 값**을 표현한다 | 좌표, 금액, 시각처럼 하나의 개념 |
| 2 | 인스턴스 크기가 **16바이트 미만**이다 | 복사 비용이 참조 복사 비용과 비슷한 범위 |
| 3 | **불변**이다 | 16.5절의 이유 전부 |
| 4 | **자주 박싱·언박싱되지 않는다** | 박싱은 구조체의 장점을 전부 되돌린다 |

네 조건을 전부 만족하지 않으면 클래스를 쓰라는 것이 이 지침의 요지다.

### 이 지침의 한계

네 조건은 유용한 출발점이지만 그대로 믿으면 곤란해지는 지점이 있다.

**한계 ① — 16바이트는 근거가 약하다.** 이 숫자의 출처는 "인스턴스가 작으면(대략 16바이트 이하) 값 타입으로 선언하라"는 오래된 권고다. 그런데 같은 권고에는 조건이 하나 더 붙어 있다 — **"인스턴스가 크지만(16바이트 초과) 메서드 매개변수로 전달되거나 메서드에서 반환되지 않는다면"** 역시 값 타입으로 선언하라는 것이다. 즉 16바이트는 절대 기준이 아니라 **복사가 일어나는 빈도와 짝을 이루는 기준**이다.

BCL 자신이 이 선을 자주 넘는다. `System.Numerics.Matrix4x4`는 `float` 16개, 64바이트짜리 구조체다. `System.Numerics.Vector4`는 정확히 16바이트다. `decimal`과 `Guid`도 16바이트다. 큰 구조체들이 여전히 구조체인 이유는 `in`과 `ref`로 복사를 피할 수 있고, 배열에 인라인으로 담겼을 때의 데이터 지역성 이득이 크기 때문이다.

**한계 ② — 크기보다 용도가 중요하다.** .NET 문서는 값 타입과 참조 타입을 가르는 결정 요인으로 타입의 크기를 고려하라고 권한다. 현실에서는 **타입의 용도**가 훨씬 나은 요인이다. 단순한 구조나 데이터 운반자인 타입이 값 타입의 훌륭한 후보다.

**한계 ③ — "16바이트 미만"과 "불변"은 성격이 다르다.** 크기는 재면 알 수 있는 사실이고, 불변성은 설계 결정이다. 그리고 실무에서 사고를 내는 것은 언제나 **불변성 조건 쪽**이다. 크기가 20바이트인 불변 구조체는 대체로 괜찮지만, 크기가 8바이트인 가변 구조체는 16.2절의 함정을 전부 안고 있다.

> **💡 4조건을 실무 우선순위로 다시 배열하면**
>
> | 우선순위 | 조건 | 어기면 |
> |---|---|---|
> | 1 | **불변인가** | 숨은 복사가 조용히 버그를 만든다 |
> | 2 | **0이 유효한 상태인가**(16.4절) | 생성자를 우회한 인스턴스가 유효하지 않다 |
> | 3 | **다형성이 필요 없는가** | 애초에 구조체로 표현할 수 없다 |
> | 4 | **박싱되지 않는가** | 성능 이득이 전부 사라진다 |
> | 5 | **작은가** | 복사 비용이 이득을 넘어선다 |
>
> 마이크로소프트 지침에는 없는 2번을 넣었다. 그리고 크기를 맨 아래로 내렸다. **크기는 재서 고칠 수 있지만, 의미론은 고치려면 타입을 바꿔야 한다.**

### 다른 두 가지 기준표

같은 질문에 대한 다른 정리도 나란히 놓고 보는 편이 낫다.

**기준표 A — 1~3이 전부 참이고, 여기에 4a나 4b 중 하나라도 참이면 값 타입으로 선언하라.**

| # | 조건 | 결합 방식 |
|---|---|---|
| 1 | 타입이 **원시 타입처럼 행동한다.** 즉 인스턴스 필드를 수정하는 멤버가 없는 꽤 단순한 타입이다 | 전부 참이어야 한다 |
| 2 | 타입이 **다른 타입을 상속할 필요가 없다** | 전부 참이어야 한다 |
| 3 | 타입에서 **파생될 다른 타입이 없다** | 전부 참이어야 한다 |
| 4a | 인스턴스가 **작다**(대략 16바이트 이하) | 4a·4b 중 하나면 된다 |
| 4b | 인스턴스가 **크지만**(16바이트 초과) 메서드 매개변수로 전달되거나 메서드에서 반환되지 **않는다** | 4a·4b 중 하나면 된다 |

**기준표 B — 다음 질문에 전부 "예"라고 답하면 값 타입을 만들라.**

| # | 질문 |
|---|---|
| 1 | 이 타입의 주된 책임이 **데이터 저장**인가 |
| 2 | 이 타입을 **불변으로 만들 수 있는가** |
| 3 | 이 타입이 **작을 것으로 기대하는가** |
| 4 | 이 타입의 공개 인터페이스가 전적으로 **데이터 멤버에 접근하는 프로퍼티들로** 정의되는가 |
| 5 | 이 타입에 **서브클래스가 절대 없을 것**이라고 확신하는가 |
| 6 | 이 타입이 **다형적으로 취급될 일이 절대 없을 것**이라고 확신하는가 |

세 표가 같은 곳을 가리킨다. 그리고 그 요지를 한 문장으로 줄이면 이렇다.

> **구조체는 데이터를 저장한다. 클래스는 동작을 정의한다.**

값 타입은 다형적이지 않다. 애플리케이션이 조작하는 **데이터를 저장하는 데** 더 적합하다. 참조 타입은 다형적일 수 있고 애플리케이션의 **동작을 정의하는 데** 써야 한다. 새 타입에 기대되는 책임을 생각하고, 그 책임으로부터 어떤 타입을 만들지 결정하라.

### 값 의미론이 캡슐화를 지킨다

이것이 성능보다 중요한 이유다.

```csharp
private MyData myData;
public MyData Foo() => myData;

// 호출
MyData v = Foo();
TotalSum += v.Value;
```

`MyData`가 **값 타입**이면 반환의 내용이 `v`의 저장소로 복사된다. 그러나 `MyData`가 **참조 타입**이면 내부 변수에 대한 참조를 내보낸 것이다. **캡슐화 원칙을 위반했다.** 호출자가 당신의 API를 우회해 객체를 수정할 수 있게 된다.

물론 참조 타입에서도 복사본을 만들어 반환할 수 있다.

```csharp
public MyData Foo2() => myData.CreateCopy();
```

이제 `v`는 원본의 복사본이다. 참조 타입이므로 힙에 두 개의 객체가 만들어진다. 내부 데이터를 노출하는 문제는 없지만 **힙에 여분의 객체를 만들었다.** 종합하면 비효율적이다.

**공개 메서드와 프로퍼티를 통해 데이터를 내보내는 데 쓰이는 타입은 값 타입이어야 한다.** 다만 공개 멤버에서 반환되는 모든 타입이 값 타입이어야 한다는 말은 아니다. 위 코드에는 `MyData`가 값을 저장한다는 전제가 있었다. 그 책임이 값 저장이었기 때문이다.

반면 이런 코드는 다르다.

```csharp
private MyType myType;
public IMyInterface Foo3() => myType as IMyInterface;

// 호출
IMyInterface iMe = Foo3();
iMe.DoWork();
```

`myType`이 여전히 반환되지만, 이번에는 반환된 값 안의 데이터에 접근하는 대신 정의된 인터페이스를 통해 **메서드를 호출하기 위해** 객체에 접근한다. 이 단순한 코드 조각이 구분을 보여 주기 시작한다 — **값 타입은 값을 저장하고, 참조 타입은 동작을 정의한다.**

### 메모리 관점 — 몇 개의 객체가 만들어지는가

```csharp
public class C
{
    private MyType a = new MyType();
    private MyType b = new MyType();
}

C cThing = new C();
```

객체가 몇 개 만들어지고 크기는 얼마인가. 답은 "경우에 따라 다르다"다.

- `MyType`이 **값 타입**이면 할당은 **한 번**이다. 그 할당의 크기는 `MyType` 크기의 두 배다.
- `MyType`이 **참조 타입**이면 할당은 **세 번**이다. `C` 객체 하나(32비트 포인터를 가정하면 8바이트), 그리고 `C` 객체가 담는 각 `MyType` 객체마다 하나씩 둘.

차이는 **값 타입이 객체 안에 인라인으로 저장되는 반면 참조 타입은 그렇지 않다**는 데서 온다. 참조 타입의 각 변수는 참조를 담고, 저장소는 추가 할당을 요구한다.

배열로 가면 더 극적이다.

```csharp
MyType[] arrayOfTypes = new MyType[100];
```

`MyType`이 값 타입이면 `MyType` 객체 크기의 100배짜리 할당이 **한 번** 일어난다. 참조 타입이면 할당은 지금 막 **한 번** 일어났고, 배열의 모든 원소는 `null`이다. 배열의 각 원소를 초기화하면 **101번의 할당**을 수행하게 된다. 101번의 할당은 1번보다 오래 걸린다. **많은 수의 참조 타입을 할당하면 힙이 단편화되고 느려진다.**

> **📌 그런데 이것은 가장 덜 중요한 이유다**
>
> 위 메모리 논의는 값 타입을 고르는 이유 중 **마지막이자 가장 덜 중요한 것**이다. 앞에서 논의한 타입의 **의미론**이 훨씬 중요한 고려 사항이다.
>
> 순서를 뒤집어 생각하는 팀이 많다. "할당을 줄이려고 구조체로 바꿨다"에서 출발하면 16.2절의 함정을 전부 밟는다. "이 타입은 값이다"에서 출발해야 한다.
>
> 성능만을 이유로 클래스를 구조체로 전환할 때의 실제 손익 계산 — 무엇을 재고, 어떤 임계에서 뒤집히는가 — 는 69.1절에서 다룬다.

### 나중에 바꾸면 무슨 일이 벌어지나

값 타입으로 만들지 참조 타입으로 만들지의 결정은 중요하다. 값 타입을 참조 타입으로 바꾸는 것은 **파급이 큰 변경**이다.

```csharp
public struct Employee
{
    public string Position { get; set; }
    public decimal CurrentPayAmount { get; set; }

    public void Pay(BankAccount b) => b.Balance += CurrentPayAmount;
}
```

이 단순한 타입에는 직원에게 급여를 지급하는 메서드가 하나 있다. 시간이 흐르고 시스템이 잘 돌아간다. 그러다 직원에 여러 종류가 있다고 결정한다 — 영업 사원은 커미션을 받고, 관리자는 보너스를 받는다. `Employee` 타입을 클래스로 바꾸기로 한다.

```csharp
public class Employee
{
    public string Position { get; set; }
    public decimal CurrentPayAmount { get; set; }

    public virtual void Pay(BankAccount b) => b.Balance += CurrentPayAmount;
}
```

이 변경이 당신의 타입을 쓰는 기존 코드의 상당 부분을 깨뜨린다. 값에 의한 반환이 참조에 의한 반환이 된다. 값으로 전달되던 매개변수가 이제 참조로 전달된다. 다음 조각의 동작이 극적으로 바뀐다.

```csharp
Employee e1 = Employees.Find(e => e.Position == "CEO");
BankAccount CEOBankAccount = new BankAccount();
decimal Bonus = 10000;
e1.CurrentPayAmount += Bonus;      // 일회성 보너스를 더한다
e1.Pay(CEOBankAccount);
```

**일회성 급여 인상이던 것이 영구적인 인상이 됐다.** 값에 의한 복사가 쓰이던 자리에 이제 참조가 들어 있다. 컴파일러는 아무 불평 없이 변경을 받아들인다. CEO는 아마 기뻐할 것이다. CFO는 반대로 버그를 보고할 것이다. **값 타입과 참조 타입에 대해서는 나중에 마음을 바꿀 수 없다. 동작이 바뀐다.**

이 문제가 생긴 이유는 `Employee` 타입이 더 이상 값 타입의 지침을 따르지 않기 때문이다. 직원을 정의하는 데이터 요소를 저장하는 것에 더해 **책임을 추가했다** — 이 예에서는 직원에게 급여를 지급하는 것. **책임은 클래스 타입의 영역이다.** 클래스는 공통 책임의 다형적 구현을 쉽게 정의할 수 있지만 구조체는 그럴 수 없고, 값을 저장하는 데 한정되어야 한다.

> **⚠️ 반대 방향 전환도 깨진다**
>
> 클래스를 구조체로 바꾸는 것도 마찬가지로 위험하다.
>
> - `null` 검사 코드가 전부 컴파일 오류가 된다 (구조체는 `null`이 될 수 없다).
> - 참조를 공유하던 코드가 조용히 복사본을 다루게 된다 — **컴파일 오류 없이 동작만 바뀐다.**
> - `==`가 컴파일되지 않게 된다 (연산자를 정의하지 않았다면).
> - `lock (obj)`가 컴파일 오류가 된다 (값 타입은 잠글 수 없다).
> - 컬렉션에 담긴 원소를 인덱서로 수정하던 코드가 `CS1612`가 된다.
>
> 첫 번째와 세 번째, 네 번째, 다섯 번째는 컴파일러가 잡아 준다. **두 번째만 안 잡힌다.** 그리고 실무에서 사고를 내는 것은 언제나 그것이다.

> **💡 확신이 서지 않으면 클래스로 만들어라**
>
> 세 기준표가 공통으로 도달하는 결론이다. **예상되는 사용 방식에 대해 의심스러우면 참조 타입을 써라.**
>
> 이유는 대칭적이지 않다. 클래스를 잘못 골랐을 때의 대가는 약간의 할당과 역참조다. 구조체를 잘못 골랐을 때의 대가는 조용히 사라지는 상태 변경, 되돌리기 어려운 API 변경, 그리고 성능을 위해 골랐는데 오히려 느려지는 결과다.
>
> **저수준 데이터 저장 타입은 값 타입으로 만들라. 애플리케이션의 동작은 참조 타입으로 만들라.** 클래스 객체에서 내보내는 데이터를 복사하는 안전성을 얻고, 스택 기반·인라인 값 저장이 주는 메모리 사용 이점을 얻고, 표준적인 객체 지향 기법으로 애플리케이션의 논리를 만들 수 있다.

## 이 장의 요약

- **구조체는 네 가지 근본 규칙에서 파생된다.** 값 타입이라는 것, 상속을 지원하지 않는다는 것, 파이널라이저를 가질 수 없다는 것, 멤버에 `virtual`·`abstract`·`protected`를 붙일 수 없다는 것. 나머지 모든 제약이 이 넷에서 나온다. 다만 구조체는 **아무것도 상속하지 않는 것이 아니라** `System.ValueType`을 상속한다.

- **값 타입을 쓴다는 것은 복사를 기본값으로 받아들인다는 뜻이다.** 대입, 인수 전달, 반환, 필드 대입, 배열 원소 읽기·쓰기, 컬렉션 저장, 박싱 — 여덟 자리 전부가 복사다. 복사를 피하는 유일한 문법적 수단은 `ref`/`in`/`out`으로 주소를 넘기는 것이다.

- **방어적 복사는 소스에 보이지 않는 다섯 자리에서 일어난다.** `readonly` 필드, `in` 매개변수, `ref readonly` 반환, `static readonly` 필드에서 인스턴스 멤버를 호출할 때, 그리고 프로퍼티 게터가 구조체를 반환할 때다. 원인은 하나 — 컴파일러가 그 메서드가 `this`를 고치지 않는다고 증명할 수 없기 때문이다. `ldfld` 대 `ldflda`, `ldobj`의 유무가 IL에서의 증거다.

- **구조체에는 언제나 필드를 0으로 채우는 매개변수 없는 생성 경로가 존재한다.** ※C# 10이 필드 초기화자와 명시적 매개변수 없는 생성자를 허용했지만, `default`·배열 원소·다른 타입의 필드는 그 초기화를 우회한다. **생성자가 반드시 실행된다고 가정하는 설계는 값 타입에서 성립하지 않는다.**

- **모든 비트가 0인 상태를 유효한 상태로 설계하라.** 열거형에는 `None = 0`을 넣고, `[Flags]` 열거형의 0은 "모든 플래그의 부재"여야 하며, 참조 필드는 프로퍼티 게터에서 `?? 기본값`으로 번역한다. 0에 의미를 부여할 수 없다면 그 타입은 값 타입이 아니어야 한다.

- **`readonly struct`가 방어적 복사 다섯 자리를 전부 없앤다.** 컴파일러가 모든 필드의 불변성을 타입 선언에서 알기 때문이다. 타입 전체를 불변으로 만들 수 없다면 ※C# 8의 `readonly` 멤버로 부분적으로라도 회수하라. 새 구조체는 `readonly struct`로 시작하고, 그럴 수 없는 이유가 생겼을 때만 뗀다.

- **`ref struct`는 성능 도구가 아니라 수명 제약을 표현하는 도구다.** 힙에 실릴 수 있는 모든 경로 — 필드, 배열, 박싱, 반복자, `async`, 람다 캡처 — 가 컴파일 타임에 막힌다. 대가로 절대 힙에 가지 않고 절대 여러 스레드에서 접근되지 않는다는 두 보장을 얻는다. 실제 용도는 68장에서 다룬다.

- **`ValueType.Equals`는 박싱과 리플렉션을 동시에 요구한다.** 값 타입을 만들 때는 `IEquatable<T>.Equals(T)`, `override Equals(object)`, `override GetHashCode()`, `==`/`!=` 넷을 함께 구현한다. ※C# 10의 `readonly record struct`가 이 넷을 전부 자동 생성하므로, 새 값 타입에 동등성이 필요하면 그것이 기본 선택이다.

- **구조체는 데이터를 저장하고 클래스는 동작을 정의한다.** 마이크로소프트의 4조건(단일 값, 16바이트 미만, 불변, 박싱 없음)은 출발점이지만, 실무 우선순위는 불변성 → 0 유효성 → 다형성 불필요 → 박싱 없음 → 크기 순이다. **크기는 재서 고칠 수 있지만 의미론은 타입을 바꿔야 고쳐진다.**

- **값 타입과 참조 타입에 대해서는 나중에 마음을 바꿀 수 없다.** 전환은 컴파일 오류 없이 동작만 바꿔 버린다. 확신이 서지 않으면 참조 타입을 쓰라 — 잘못 골랐을 때의 대가가 훨씬 작다.

## 연습 문제

1. **숨은 복사를 눈으로 확인하라.** 가변 구조체 `Counter { public int Value; public void Increment() => Value++; }`를 만들고, 이를 `readonly` 필드와 일반 필드로 각각 담은 클래스를 작성하라. 두 필드에 대해 `Increment()`를 호출한 뒤 `Value`를 출력해 결과가 다른 것을 확인하라. 그다음 ILSpy나 sharplab.io에서 IL을 열어 `ldfld`와 `ldflda`가 각각 어디에 나오는지 찾아라. 마지막으로 `Counter`를 `readonly struct`로 바꿨을 때 어떤 컴파일 오류가 나는지 확인하고, 그 오류가 왜 "좋은 소식"인지 설명하라.

2. **`in`의 방어적 복사를 재라.** 24바이트짜리 구조체 `Vec3`를 일반 `struct`와 `readonly struct` 두 벌로 만들고, `static double Sum(in Vec3 a)`를 각각에 대해 호출하는 벤치마크를 BenchmarkDotNet으로 작성하라(67.3절). 두 버전의 IL에서 `ldobj`의 유무를 확인하고, 실측 차이가 IL 차이와 일치하는지 검증하라.

3. **생성자 우회 경로를 전부 확인하라.** ※C# 10 이상에서 필드 초기화자와 매개변수 없는 생성자를 모두 가진 구조체를 만들어라. 그다음 `new S()`, `default(S)`, `new S[3]`, 클래스의 필드로 포함, `Array.Resize`로 늘어난 자리 — 다섯 경로 각각에서 필드 값이 무엇인지 출력해 표로 만들어라. 예상과 다른 항목이 있었는가.

4. **0이 유효하지 않은 타입을 고쳐라.** `enum Currency { USD = 1, EUR = 2, KRW = 3 }`와 이를 담는 `struct Money { public decimal Amount; public Currency Currency; }`를 작성하라. `default(Money)`를 문자열로 출력했을 때 무엇이 나오는지 확인하고, 16.4절의 처방 세 가지(열거형에 0 추가 / 프로퍼티에서 번역 / 클래스로 전환) 중 이 경우에 무엇이 적절한지 판단해 적용하라.

5. **`Equals` 재정의의 효과를 재라.** `Point` 구조체를 (가) 아무것도 재정의하지 않은 버전, (나) `Equals(object)`만 재정의한 버전, (다) `IEquatable<Point>`까지 구현한 버전 세 벌로 만들고, 각각을 `HashSet<T>`에 10만 개 넣고 조회하는 벤치마크를 `MemoryDiagnoser`와 함께 실행하라(67.5절). 할당량이 세 버전에서 어떻게 다른지 설명하라. 그다음 `readonly record struct`로 바꿨을 때 어느 버전과 같은 결과가 나오는지 확인하라.

6. **`ref struct`의 제약을 직접 겪어 보라.** `ref struct RefBuffer { public int Length; }`를 선언하고, 다음 여덟 가지를 각각 시도해 어떤 컴파일 오류가 나오는지 기록하라 — 클래스의 필드로 선언, 정적 필드로 선언, `object`로 캐스팅, 배열 만들기, `List<RefBuffer>` 만들기, `async` 메서드의 지역 변수로 사용, 람다에서 캡처, `IDisposable` 구현 후 인터페이스 변수에 대입. 각 오류 메시지가 16.6절의 제약 표 어느 행에 대응하는지 짝지어라.

7. **판단 절차를 실제 코드에 적용하라.** 당신이 유지 보수하는 코드베이스(또는 오픈 소스 프로젝트)에서 `struct`로 선언된 타입을 다섯 개 찾아라. 각각에 대해 16.8절의 판단 흐름도를 위에서부터 적용하고, 어느 관문에서 걸리는지 기록하라. 걸리는 것이 있다면 `class`로 바꿨을 때 무엇이 깨질지(그리고 무엇이 컴파일러에게 잡히지 **않을지**) 예측하라.
