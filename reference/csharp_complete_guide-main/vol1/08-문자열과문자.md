# 8장. 문자열과 문자

> **이 장의 위치** — 7장에서 숫자와 `bool`을 끝냈고, `char`는 "정수처럼 굴지만 본체는 문자"라는 이유로 미뤄 두었다. 이 장이 그 빚을 갚는다. `char` 하나에서 시작해 `string`으로 올라가면서, 참조 타입인 문자열이 왜 값처럼 비교되는지, 왜 한 글자도 바꿀 수 없는지, 그리고 리터럴을 쓰는 네 가지 문법이 각각 어떤 문제를 풀려고 태어났는지를 본다.
>
> **선수 지식** — 6장(구문과 타입 기초), 특히 6.7절(값 타입 vs 참조 타입)과 6.8절(스택과 힙). 7장(숫자와 불리언), 특히 7.2절(숫자 변환)과 7.3절(산술 연산자와 증감 연산자).
>
> **이 장에서 다루지 않는 것** — 이 장은 **문법과 기본 동작**만 다룬다. 문자열 조작 메서드 전수·비교 알고리즘의 상세·문자열 인터닝·`StringBuilder`·`Rune`과 서로게이트 페어의 정확한 처리·텍스트 인코딩은 전부 35장「문자열과 텍스트 처리」의 몫이다. 정규식은 36장, 숫자·날짜 서식 문자열의 전체 목록은 38.3절과 38.5절, 문자열이 힙에 어떻게 배치되는지는 54.7절, 문자열 연결이 만드는 숨은 할당의 카탈로그는 63.9절, `ReadOnlySpan<byte>`로 텍스트를 다루는 방법은 68.5절이다. 이 장에서 그 주제들을 만나면 "여기까지"라고 끊고 절 번호로 넘긴다.

## 8.1 `char`와 문자 변환

### `char`는 무엇인가

C#의 `char`는 `System.Char` 구조체의 별칭(alias)이다. 6.5절의 미리 정의된 타입 표에서 숫자도 `bool`도 아닌 자리에 홀로 서 있던 그 타입이다.

```csharp
char c = 'A';       // 단순 문자
```

세 가지 사실을 먼저 못 박아 둔다.

1. **값 타입이다.** 구조체이므로 변수에 값이 직접 들어간다. 배열이나 필드에 담으면 그 자리에 2바이트가 놓인다.
2. **16비트다.** 정확히는 UTF-16 **코드 단위**(code unit) 하나를 담는다. 부호가 없어서 표현 범위는 `0x0000` ~ `0xFFFF`다.
3. **문자 리터럴은 작은따옴표를 쓴다.** 큰따옴표는 `string`이다. `'A'`와 `"A"`는 타입이 다르다.

`System.Char`는 읽기 전용 상수 필드 두 개를 공개한다. `Char.MinValue`는 `'\0'`으로, `Char.MaxValue`는 `'\uffff'`로 정의되어 있다.

```csharp
Console.WriteLine((int) char.MinValue);   // 0
Console.WriteLine((int) char.MaxValue);   // 65535
```

`char` 리터럴 안에는 문자가 **정확히 하나**만 들어가야 한다. `'ab'`는 컴파일 오류다. 이 규칙이 다음 함정으로 이어진다.

> **⚠️ `char`는 "문자"가 아니라 "코드 단위"다**
>
> .NET에서 문자는 항상 16비트 유니코드 코드 값으로 표현된다. 그런데 **모든 유니코드 문자가 16비트에 들어가지는 않는다.** 16비트를 넘는 문자는 두 개의 16비트 값 — 상위 서로게이트(high surrogate)와 하위 서로게이트(low surrogate) — 로 표현된다. 상위 서로게이트는 U+D800 ~ U+DBFF, 하위 서로게이트는 U+DC00 ~ U+DFFF 범위를 쓴다. 이 방식 덕분에 유니코드는 100만 개가 넘는 문자를 표현할 수 있다.
>
> 그래서 이런 일이 벌어진다.
>
> ```csharp
> string emoji = "\U0001F600";            // GRINNING FACE (U+1F600)
> Console.WriteLine(emoji.Length);        // 2  — 글자는 하나인데 길이가 2
> // char smile = '\U0001F600';           // 컴파일 오류 — char 하나에 안 들어간다
> ```
>
> 게다가 코드 값 **하나**가 곧 사람이 보는 글자 하나인 것도 아니다. 결합 문자(combining character)를 쓰면 두 개 이상의 코드 값이 모여 하나의 **텍스트 요소**(text element)를 이룬다. 예를 들어 U+0625(하즈아가 아래 붙은 아랍 문자 알레프)와 U+0650(아랍 카스라)이 결합하면 사람 눈에는 글자 하나다.
>
> 서로게이트는 미국과 유럽에서는 거의 쓰이지 않지만 동아시아에서는 흔하다. 이 장에서는 "`char` 하나 = 코드 단위 하나"까지만 알면 된다. 서로게이트 페어를 올바르게 다루는 `Rune` 타입과 `StringInfo`, 텍스트 요소 단위 순회는 35.2절에서 정면으로 다룬다. **`s.Length`를 "글자 수"라고 부르는 순간 버그가 시작된다는 것만 기억하라.**

### 이스케이프 시퀀스

작은따옴표 하나, 백슬래시 하나, 줄바꿈 — 이런 문자들은 소스 코드에 그대로 적을 수 없거나 적어도 의미가 어긋난다. 이때 쓰는 것이 **이스케이프 시퀀스**(escape sequence)다. 백슬래시 뒤에 특별한 의미를 가진 문자를 붙인다.

```csharp
char newLine   = '\n';
char backSlash = '\\';
```

| 시퀀스 | 의미 | 코드 값 |
|---|---|---|
| `\'` | 작은따옴표 | `0x0027` |
| `\"` | 큰따옴표 | `0x0022` |
| `\\` | 백슬래시 | `0x005C` |
| `\0` | 널 문자 | `0x0000` |
| `\a` | 경고(벨) | `0x0007` |
| `\b` | 백스페이스 | `0x0008` |
| `\f` | 폼 피드 | `0x000C` |
| `\n` | 줄 바꿈(line feed) | `0x000A` |
| `\r` | 캐리지 리턴 | `0x000D` |
| `\t` | 수평 탭 | `0x0009` |
| `\v` | 수직 탭 | `0x000B` |
| `\e` | 이스케이프(ESC) ※C# 13 | `0x001B` |

마지막 `\e`는 ※C# 13에서 추가됐다. 그전까지는 ANSI 터미널 제어 시퀀스를 쓸 때 `'\u001b'` 또는 `'\x1b'`라고 적어야 했고, 후자는 곧 볼 함정을 안고 있었다.

이스케이프 시퀀스는 `char` 리터럴에서 유효한 것이 문자열 리터럴 안에서도 그대로 통한다.

```csharp
string a = "Here's a tab:\t";
string b = "Model\tColor\tSpeed\tPet Name";      // 탭으로 열 맞추기
Console.WriteLine("Everyone loves \"Hello World\"");
Console.WriteLine("C:\\MyApp\\bin\\Debug");
```

> **📌 `\0`은 8진 이스케이프가 아니다**
>
> C/C++ 출신이라면 `\0`을 "8진수 0"으로 읽고 `\101`이 `'A'`(8진 101 = 65)일 거라고 기대할 수 있다. **C#에는 8진 이스케이프가 없다.** `\0`은 널 문자 하나를 뜻하는 독립된 시퀀스일 뿐이다.
>
> ```csharp
> string s = "\012";
> Console.WriteLine(s.Length);        // 3 — '\0', '1', '2'
> ```
>
> 널 문자 뒤에 숫자를 붙여야 한다면 `"\u0000" + "12"`처럼 명확히 쓰거나, 곧 볼 유니코드 이스케이프를 써라.

> **📌 줄바꿈을 하드코딩하지 마라**
>
> `"Hi\r\nthere."`처럼 캐리지 리턴과 줄 바꿈을 직접 박는 것은 권장되지 않는다. `System.Environment` 타입의 읽기 전용 `NewLine` 프로퍼티가 실행 중인 플랫폼에 맞는 줄바꿈 문자열을 돌려준다. 윈도우에서는 `"\r\n"`, 유닉스 계열에서는 `"\n"`이다.
>
> ```csharp
> string s = "Hi" + Environment.NewLine + "there.";
> Console.WriteLine("All finished.{0}{0}{0}", Environment.NewLine);
> ```
>
> 이 차이는 문자열 비교에서 실제로 사고를 낸다. 윈도우에서 만든 `"First Line\r\nSecond Line"`과 리눅스에서 만든 `"First Line\nSecond Line"`은 다른 문자열이고, `==`는 당연히 `false`를 돌려준다.

### 유니코드 이스케이프 — `\u`, `\U`, `\x`

임의의 유니코드 코드 값을 16진수로 직접 적는 방법이 세 가지 있다. 셋은 **자릿수 규칙이 다르고**, 그 차이가 함정을 만든다.

```csharp
char copyrightSymbol = '\u00A9';    // ©
char omegaSymbol     = '\u03A9';    // Ω
char newLine         = '\u000A';    // 줄 바꿈
```

| 형태 | 16진 자릿수 | 표현 범위 | 비고 |
|---|---|---|---|
| `\u` | **정확히 4자리** | U+0000 ~ U+FFFF | 가장 안전. 자릿수가 모자라면 컴파일 오류 |
| `\U` | **정확히 8자리** | U+00000000 ~ U+0010FFFF | 보조 평면(supplementary plane) 문자용 |
| `\x` | **1~4자리 (가변)** | U+0000 ~ U+FFFF | 자릿수가 고정되지 않아 위험 |

`\u`는 반드시 네 자리를 요구한다. `'\u41'`은 컴파일 오류다. 이 엄격함이 곧 안전장치다.

`\U`는 여덟 자리를 요구하며, 16비트를 넘는 코드 포인트를 적을 수 있다. 다만 `char`는 16비트이므로 U+FFFF를 넘는 값을 `char` 리터럴에 넣을 수는 없다. 문자열 안에서 쓰면 컴파일러가 서로게이트 페어 두 개로 펼쳐 넣는다.

```csharp
string grin = "\U0001F600";         // U+1F600 — 문자열 안에서는 OK
Console.WriteLine(grin.Length);     // 2 — 서로게이트 페어로 저장된다
// char c = '\U0001F600';           // 컴파일 오류 — char에 안 들어간다
```

> **⚠️ `\x`의 함정 — 자릿수가 고정되지 않는다**
>
> `\x`는 뒤따르는 16진수를 **최대 네 자리까지, 먹을 수 있는 만큼 먹는다.** 뒤에 오는 문자가 우연히 16진 숫자(`0`~`9`, `a`~`f`, `A`~`F`)면 그것까지 코드 값의 일부로 빨려 들어간다.
>
> ```csharp
> string a = "\x41";          // "A"        — 의도대로
> string b = "\x41BC";        // "\u41BC"   — 한 글자! "ABC"가 아니다
> string c = "\x41Good";      // "AGood"    — 'G'는 16진 숫자가 아니라 여기서 멈춘다
> ```
>
> `b`는 `'A'` 뒤에 `"BC"`를 붙이려던 코드다. 그런데 `B`와 `C`가 16진 숫자라서 `\x41BC`가 통째로 한 문자가 됐다. **컴파일 오류도 경고도 나지 않는다.** 문자열이 조용히 다른 값이 되고, 그 문자열이 파일 경로나 프로토콜 토큰이면 런타임 한참 뒤에 터진다.
>
> 더 고약한 것은 이 버그가 **주변 문자에 의존한다**는 점이다. `"\x41Good"`은 멀쩡히 동작하다가, 나중에 누가 `Good`을 `Bad`로 바꾸면 `"\x41Bad"`가 `\x41BA` + `'d'`로 해석되어 깨진다. 문자열 상수 하나를 고쳤을 뿐인데 다른 문자가 되는 것이다.
>
> **결론: `\x`를 쓰지 마라. 언제나 `\u`를 써라.** 자릿수가 고정된 `\u`는 이 문제가 원천적으로 없다. `\x`는 C 호환을 위해 남아 있는 유산일 뿐이고, `\x` 뒤에 오는 문자를 통제할 수 있다고 자신하는 순간이 사고 직전이다.

> **💡 눈에 보이지 않는 문자는 반드시 이스케이프로 써라**
>
> `'\u00A9'`가 저작권 기호라는 것을 코드에서 알아볼 사람은 없다. 소스에 그 문자를 직접 적을 수 있으면 직접 적는 편이 낫다(요즘 소스 파일은 대부분 UTF-8이다).
>
> 반대로 **눈에 보이지 않는 문자는 절대 직접 적지 마라.** 제로 폭 공백, 비분리 공백, BOM 같은 것을 소스에 그대로 박아 두면 나중에 아무도 그것이 거기 있는 줄 모른다. `git diff`에도 안 보이고 코드 리뷰에도 안 걸린다.
>
> ```csharp
> const char ZeroWidthSpace   = '\u200B';
> const char NonBreakingSpace = '\u00A0';
> const char ByteOrderMark    = '\uFEFF';
> ```
>
> 이름을 붙여 상수로 만들면 그 문자가 코드에 존재한다는 사실이 검색 가능해진다.

### `char`의 숫자 변환

7.2절에서 변환의 원칙을 세웠다. "대상 타입이 원본의 **모든** 값을 표현할 수 있으면 암시 변환, 아니면 캐스트"다. `char`도 정확히 이 규칙을 따른다.

**`char`에서 숫자로는, `ushort`를 수용할 수 있는 타입이면 암시 변환된다.** 그 외에는 명시적 변환이 필요하다.

| 대상 타입 | `char` → 대상 | 이유 |
|---|---|---|
| `ushort`, `int`, `uint`, `long`, `ulong` | 암시적 | 0 ~ 65,535를 전부 담는다 |
| `float`, `double`, `decimal` | 암시적 | 정수 → 실수 확대 변환 |
| `sbyte`, `byte`, `short` | 명시적(캐스트) | 65,535를 담지 못한다 |
| 모든 숫자 타입 → `char` | 명시적(캐스트) | 어떤 숫자 타입도 `char`로 암시 변환되지 않는다 |

마지막 행이 중요하다. **숫자에서 `char`로 가려면 반드시 캐스트를 써야 한다.** `byte`는 0~255라서 `char` 범위 안에 완전히 들어가지만, 그래도 암시 변환은 없다. 언어 설계자가 "숫자가 슬그머니 문자가 되는 일"을 막아 둔 것이다.

```csharp
char c = 'A';
int  n = c;                  // 암시적 — 65
char d = (char) 66;          // 명시적 — 'B'
```

> **⚠️ 상수 식 예외는 `char`에 적용되지 않는다**
>
> 6.10절에서 본 **상수 식(constant expression)의 암시적 변환** 규칙이 있다. `int` 상수의 값이 컴파일 타임에 확정되고 대상 타입의 범위 안에 있으면 캐스트 없이 통과하는 규칙이다. 그래서 `byte b = 100;`은 컴파일된다.
>
> **그런데 이 규칙이 허용하는 대상 타입 목록에 `char`는 없다.** 명세가 나열하는 것은 `sbyte`, `byte`, `short`, `ushort`, `uint`, `ulong`뿐이다(그리고 `long` 상수 → `ulong`).
>
> ```csharp
> byte b  = 100;             // OK — 상수 식 예외가 적용된다
> // char c1 = 65;           // 컴파일 오류 CS0266 — char에는 예외가 없다
> char c2 = (char) 65;       // OK — 캐스트를 쓴다
> char c3 = 'A';             // OK — 문자 리터럴을 쓴다
> ```
>
> 숫자가 슬그머니 문자가 되는 일을 막겠다는 설계 의도가 여기서도 일관되게 관철된다. **숫자에서 `char`로 가는 길은 언제나 캐스트뿐이다.**

산술 연산은 7.3절의 승격 규칙을 그대로 따른다. `char`끼리 더해도 결과는 `int`다.

```csharp
char a = 'a';
// char next = a + 1;        // 컴파일 오류 — a + 1의 타입은 int
char next = (char)(a + 1);   // 'b'
int  diff = 'z' - 'a';       // 25 — int로 승격되어 계산된다
```

7.5절에서 본 "8비트·16비트 정수 타입에는 산술 연산자가 없다"는 사실의 또 다른 얼굴이다. CLR의 평가 스택은 32비트 미만을 담지 못하므로 `char + int`는 `int + int`가 되고 결과도 `int`다.

> **💡 `char` 산술은 ASCII 범위 안에서만 쓸 만하다**
>
> `c - '0'`으로 숫자 문자를 값으로 바꾸거나 `(char)('a' + i)`로 알파벳을 순회하는 관용구는 널리 쓰인다. ASCII 범위 안에서는 코드 값이 연속이라 안전하다.
>
> 그 밖에서는 위험하다. 유니코드는 알파벳 순서와 코드 값 순서가 일치한다는 보장을 주지 않는다. 한글 음절은 U+AC00부터 연속이지만 자모 조합 규칙이 있고, 악센트가 붙은 라틴 문자는 여기저기 흩어져 있다. **문자를 분류하려면 산술 대신 `char.IsDigit` 계열 메서드를 써라.**

### 세 가지 변환 기법과 그 비용

`char`와 숫자 사이를 오가는 방법은 셋이다. **효율 순서대로** 놓으면 이렇다.

**1. 캐스팅 — 가장 빠르다.** 컴파일러가 변환 IL 명령을 직접 뿜는다. 메서드 호출이 없다. 7.9절에서 본 `checked`/`unchecked`도 적용된다.

```csharp
char c = (char) 65;                        // "A"
int  n = (int) c;                          // 65
c = unchecked((char) (65536 + 65));        // "A" — 하위 16비트만 남는다
```

마지막 줄을 보라. `65536 + 65 = 65601`은 `char` 범위를 넘지만 `unchecked`이므로 상위 비트가 잘려 나가고 65가 남는다. 조용한 데이터 손실이다.

**2. `System.Convert` — 범위 검사를 한다.** `Convert` 타입의 정적 메서드들은 모든 변환을 `checked` 연산으로 수행한다. 변환 결과 데이터 손실이 발생하면 `OverflowException`을 던진다.

```csharp
char c = Convert.ToChar(65);               // "A"
int  n = Convert.ToInt32(c);               // 65

try
{
    c = Convert.ToChar(70000);             // 16비트에 안 들어간다
    Console.WriteLine(c);                  // 실행되지 않는다
}
catch (OverflowException)
{
    Console.WriteLine("70000은 char로 변환할 수 없다.");
}
```

**3. `IConvertible` 인터페이스 — 가장 느리다.** `Char`와 .NET의 모든 숫자 타입은 `IConvertible`을 구현한다. 이 인터페이스는 `ToUInt16`, `ToChar` 같은 메서드를 정의한다. 그런데 이들은 전부 값 타입이므로 인터페이스 메서드를 호출하려면 **박싱**이 일어난다(15.2절). 게다가 `Char`와 숫자 타입들은 `IConvertible`을 명시적 인터페이스 구현(18장)으로 제공하므로, 호출하기 전에 인스턴스를 `IConvertible`로 명시적으로 캐스트해야 한다.

```csharp
char c = ((IConvertible) 65).ToChar(null);      // "A" — 65가 박싱된다
int  n = ((IConvertible) c).ToInt32(null);      // 65 — c가 박싱된다
```

변환할 수 없는 타입 조합(예: `Char`를 `Boolean`으로)이거나 데이터 손실이 발생하면 `InvalidCastException`을 던진다. `IConvertible`의 메서드들은 `GetTypeCode`를 제외하고 모두 `IFormatProvider` 구현 객체의 참조를 받는데, 문화권을 고려할 필요가 없는 대부분의 변환에서는 어차피 무시되므로 `null`을 넘기면 된다.

| 기법 | 속도 | 범위 검사 | 할당 |
|---|---|---|---|
| 캐스트 `(char)`, `(int)` | 가장 빠름(IL 명령) | `checked`일 때만 | 없음 |
| `Convert.ToChar` / `ToInt32` | 중간(메서드 호출) | 항상 → `OverflowException` | 없음 |
| `((IConvertible)x).ToChar` | 가장 느림 | 함 → `InvalidCastException` | **박싱 발생** |

> **💡 실무에서는 캐스트만 쓴다**
>
> `char`↔숫자 변환에 `Convert`나 `IConvertible`을 쓸 일은 거의 없다. 값의 범위를 코드가 이미 알고 있는 경우가 대부분이기 때문이다. 범위가 불확실하다면 `Convert`의 예외에 기대는 것보다 명시적인 검사가 낫다.
>
> ```csharp
> if (code is >= 0 and <= 0xFFFF) { char c = (char) code; /* ... */ }
> ```
>
> `IConvertible` 경로는 리플렉션이나 범용 변환 유틸리티를 직접 만들 때나 등장한다. 일반 코드에 나타나면 대개 잘못 쓴 것이다.

### `System.Char`의 정적 메서드

`Char` 타입은 문자 하나를 담는 것 이상의 기능을 제공한다. 주어진 문자가 숫자인지, 글자인지, 구두점인지를 판정하는 정적 메서드들이다.

```csharp
char myChar = 'a';
Console.WriteLine(char.IsDigit(myChar));                    // False
Console.WriteLine(char.IsLetter(myChar));                   // True
Console.WriteLine(char.IsWhiteSpace("Hello There", 5));     // True  — 인덱스 5는 공백
Console.WriteLine(char.IsWhiteSpace("Hello There", 6));     // False — 인덱스 6은 'T'
Console.WriteLine(char.IsPunctuation('?'));                 // True
```

마지막 두 줄에 주목하라. **`Char`의 판정 메서드 대부분은 호출 규약이 두 가지다.** 문자 하나를 넘기거나, 문자열과 그 안의 인덱스를 넘긴다. 후자는 문자열에서 `s[i]`로 문자를 꺼내는 중간 단계를 생략한다.

| 메서드 | 판정 대상 |
|---|---|
| `IsDigit` | 10진 숫자 |
| `IsNumber` | 숫자(분수·로마 숫자 등 포함) |
| `IsLetter` / `IsLetterOrDigit` | 글자 / 글자 또는 숫자 |
| `IsUpper` / `IsLower` | 대문자 / 소문자 |
| `IsWhiteSpace` | 공백류 |
| `IsPunctuation` / `IsSymbol` / `IsSeparator` | 구두점 / 기호 / 구분자 |
| `IsControl` | 제어 문자 |
| `IsSurrogate` / `IsHighSurrogate` / `IsLowSurrogate` | 서로게이트 코드 값 |

이 메서드들은 대부분 내부적으로 `GetUnicodeCategory`를 호출하고 결과에 따라 `true`/`false`를 돌려준다. `GetUnicodeCategory`는 `System.Globalization.UnicodeCategory` 열거형 값을 반환하는데, 이 값이 해당 문자가 제어 문자인지, 통화 기호인지, 소문자인지, 대문자인지, 구두점인지, 수학 기호인지, 그 밖의 무엇인지를 유니코드 표준에 정의된 대로 알려준다.

`GetNumericValue`는 문자의 숫자 값을 `double`로 돌려준다. 숫자가 아닌 문자에는 `-1`이 나온다.

```csharp
Console.WriteLine(char.GetNumericValue('\u0033'));   // 3    — '3'
Console.WriteLine(char.GetNumericValue('\u00bc'));   // 0.25 — '¼'(4분의 1)
Console.WriteLine(char.GetNumericValue('A'));        // -1   — 숫자가 아니다
```

`'¼'`가 `0.25`를 돌려주는 것이 이 메서드의 존재 이유다. `IsDigit`은 `'¼'`에 `false`를 주지만 `IsNumber`는 `true`를 준다. "숫자"의 정의가 하나가 아니라는 뜻이다.

> **⚠️ `char.IsDigit`은 아라비아 숫자만 뜻하지 않는다**
>
> `IsDigit`은 유니코드의 `DecimalDigitNumber` 범주 전체에 `true`를 준다. 여기에는 `'0'`~`'9'` 말고도 아라비아-인도 숫자, 데바나가리 숫자 등 여러 문자 체계의 10진 숫자가 포함된다.
>
> 입력 검증을 "숫자 문자로만 이루어졌는가"로 하고 나서 `int.Parse`에 넘기면, 검증은 통과했는데 파싱이 실패하는 조합이 나올 수 있다. **파싱 가능성을 확인하고 싶으면 문자를 세지 말고 `int.TryParse`를 써라**(38.1절). ASCII 숫자만 허용하고 싶으면 `c is >= '0' and <= '9'`로 명시적으로 적어라.

### 대소문자 변환과 문화권

`Char`는 인스턴스 메서드도 몇 개 제공한다. `Equals`는 두 `Char`가 같은 16비트 유니코드 코드 포인트를 나타내면 `true`를 돌려준다. `CompareTo`(`IComparable`/`IComparable<Char>`가 요구하는 메서드)는 두 `Char`를 비교하되 **문화권을 고려하지 않는다.** `ToString`은 문자 하나짜리 문자열을 만들고, 반대 방향은 `Parse`/`TryParse`로 문자 하나짜리 문자열에서 UTF-16 코드 포인트를 얻는다.

대소문자 변환은 상황이 다르다. **글자의 대소문자 규칙은 문화권에 의존하는 연산이다.**

```csharp
char.ToUpperInvariant('i');       // 'I' — 항상, 어떤 문화권에서도
char.ToUpper('i');                // 호출 스레드의 CurrentCulture에 따라 달라진다
char.ToUpper('i', someCulture);   // 문화권을 명시
```

`ToLowerInvariant`/`ToUpperInvariant`는 문화권과 무관하게 동작한다. `ToLower`/`ToUpper`는 호출 스레드에 연결된 문화권 정보를 쓴다 — 내부적으로 `System.Globalization.CultureInfo`의 정적 `CurrentCulture` 프로퍼티를 조회한다. 특정 문화권을 쓰고 싶으면 `CultureInfo` 인스턴스를 인자로 넘긴다.

> **⚠️ 터키어 I 문제**
>
> 왜 대소문자 변환에 문화권이 필요한가. 터키어 때문이다.
>
> 터키어는 U+0069(라틴 소문자 I)의 대문자를 **U+0130(위에 점이 있는 라틴 대문자 I)** 으로 본다. 다른 문화권은 U+0049(라틴 대문자 I)로 본다. 즉 **`'i'`를 대문자로 바꾼 결과가 실행 환경의 로캘에 따라 다른 문자다.**
>
> 이것이 실무에서 어떻게 사고를 내는지 보자. 확장자의 첫 글자를 대문자로 정규화해 비교하는 코드가 있다고 하자.
>
> ```csharp
> if (char.ToUpper(ext[0]) == 'I') { /* 이미지 파일 처리 */ }
> ```
>
> 개발자 PC(영어 로캘)에서는 완벽히 동작한다. 터키 사용자의 PC에 배포되는 순간 `char.ToUpper('i')`가 U+0130을 돌려주고 조건이 절대 참이 되지 않는다. 단위 테스트도 통과하고 코드 리뷰도 통과하고, **특정 나라 사용자에게만** 기능이 조용히 사라진다.
>
> **규칙: 프로그램 내부 로직을 위한 정규화에는 반드시 `ToUpperInvariant`를 써라.** 사람에게 보여줄 텍스트를 다듬는 것이 목적일 때만 `ToUpper`를 쓴다. 이 원칙은 문자열에도 그대로 적용된다(8.5절, 상세는 35.4절).

> **📌 `ToUpperInvariant`가 `ToLowerInvariant`보다 낫다**
>
> 문자열을 정규화할 때는 소문자보다 **대문자** 방향을 권장한다. 마이크로소프트가 대문자 비교 경로를 최적화해 두었고, BCL 내부에서도 대소문자 무시 비교를 하기 전에 문자열을 대문자로 정규화하기 때문이다.
>
> `String` 클래스에는 `ToUpperOrdinal`/`ToLowerOrdinal` 같은 메서드가 없다. 그래서 서수(ordinal) 비교 전에 정규화가 필요하면 `ToUpperInvariant`를 쓴다. `ToUpper`/`ToLower`는 문화권에 민감하므로 이 목적에 쓰지 않는다.
>
> 다만 실무에서 더 나은 선택은 **정규화 자체를 하지 않는 것**이다. `StringComparison.OrdinalIgnoreCase`를 넘기면 사본을 만들지 않고 비교할 수 있다(8.5절).

### 서로게이트를 다루는 최소한의 도구

`Char`는 UTF-32 코드 포인트와 UTF-16 사이를 오가는 정적 메서드 두 개를 제공한다.

- `Char.ConvertFromUtf32(int)` — UTF-32 문자 하나를 받아 UTF-16 문자 한 개 또는 두 개로 이루어진 문자열을 만든다.
- `Char.ConvertToUtf32(char high, char low)` — 상위/하위 서로게이트 페어에서 UTF-32 문자를 만든다. 문자열과 인덱스를 받는 오버로드도 있다.

```csharp
string grin = char.ConvertFromUtf32(0x1F600);      // U+1F600 한 글자 — 길이 2
int    cp   = char.ConvertToUtf32(grin, 0);        // 0x1F600
```

여기까지가 이 장의 범위다. 실제로 서로게이트를 정확하게 다뤄야 한다면 ※.NET Core 3.0에서 들어온 `System.Text.Rune` 타입을 쓰는 편이 훨씬 낫다. `Rune`은 유니코드 스칼라 값 하나를 담는 값 타입이라 "코드 단위" 대신 "코드 포인트" 단위로 사고할 수 있게 해 준다. `Rune`, `StringInfo`, 텍스트 요소 열거는 35.2절에서 다룬다.

## 8.2 `string` 타입의 기본 동작과 불변성

### `string`은 무엇인가

C#의 `string`은 `System.String` 클래스의 별칭이다. **불변(immutable)인 유니코드 문자의 시퀀스**를 나타낸다. 문자열 리터럴은 큰따옴표로 감싼다.

```csharp
string a = "Heat";
```

`String`은 `Object`에서 **직접** 파생된 참조 타입이다. 따라서 `String` 객체(그 안의 문자 배열)는 언제나 힙에 산다. 스레드의 스택에는 절대 놓이지 않는다(6.8절). 스택에 놓이는 것은 그 객체를 가리키는 참조뿐이다.

`String`은 여러 인터페이스를 구현한다 — `IComparable`/`IComparable<String>`, `ICloneable`, `IConvertible`, `IEnumerable`/`IEnumerable<Char>`, `IEquatable<String>`. `IEnumerable<Char>`를 구현하므로 `foreach`로 문자를 순회할 수 있다.

```csharp
foreach (char c in "Heat")
    Console.Write(c + " ");        // H e a t
```

| 멤버 | 종류 | 하는 일 |
|---|---|---|
| `Length` | 프로퍼티 | 문자열의 **코드 단위** 개수 |
| `this[int]` | 인덱서 | 지정한 위치의 `char`. **읽기 전용** |
| `Contains()` | 인스턴스 | 부분 문자열 포함 여부 |
| `IndexOf()` / `LastIndexOf()` | 인스턴스 | 부분 문자열/문자의 위치 |
| `Substring()` | 인스턴스 | 일부를 잘라 **새 문자열**로 |
| `Insert()` / `Remove()` / `Replace()` | 인스턴스 | 삽입·제거·치환된 **새 문자열**로 |
| `PadLeft()` / `PadRight()` | 인스턴스 | 지정 길이까지 채운 **새 문자열**로 |
| `Trim()` | 인스턴스 | 앞뒤의 지정 문자들을 제거한 **새 문자열**로 |
| `ToUpper()` / `ToLower()` | 인스턴스 | 대/소문자로 바꾼 **새 문자열**로 |
| `Split()` | 인스턴스 | 구분자로 나눈 `string[]` |
| `ToCharArray()` | 인스턴스 | `char[]` 사본 |
| `Compare()` | 정적 | 두 문자열의 순서 비교 |
| `Equals()` | 인스턴스/정적 | 두 문자열의 동등 비교 |
| `Format()` | 정적 | 서식 문자열과 인자로 문자열 조립 |
| `Concat()` / `Join()` | 정적 | 연결 / 구분자를 끼워 연결 |

표의 "**새 문자열**로"가 반복되는 것이 이 절의 핵심이다. 잠시 뒤에 그 이유를 본다. 이 메서드들의 오버로드 전수와 정확한 동작은 35.3절에서 다룬다.

```csharp
string firstName = "Freddy";
Console.WriteLine(firstName.Length);              // 6
Console.WriteLine(firstName.ToUpper());           // FREDDY
Console.WriteLine(firstName.ToLower());           // freddy
Console.WriteLine(firstName.Contains("y"));       // True
Console.WriteLine(firstName.Replace("dy", ""));   // Fred
Console.WriteLine(firstName);                     // Freddy  ← 변하지 않았다
```

마지막 줄이 함정이다. `Replace`를 부른 뒤에도 `firstName`은 `"Freddy"` 그대로다. 이 메서드들은 문자열을 **바꾸지 않고**, 바뀐 형태의 사본을 **돌려준다.**

### `new`로 문자열 리터럴을 만들 수 없다

많은 프로그래밍 언어(C# 포함)가 `String`을 원시 타입(primitive type)처럼 취급한다. 컴파일러가 소스 코드에 리터럴 문자열을 직접 적을 수 있게 해 준다는 뜻이다. 컴파일러는 이 리터럴들을 **모듈의 메타데이터에 넣고**, 런타임에 그것을 로드해 참조한다.

그래서 리터럴 문자열로 `String` 객체를 만들 때 `new` 연산자를 쓸 수 없다.

```csharp
// string s = new String("Hi there.");   // 컴파일 오류
string s = "Hi there.";                  // 이렇게 써야 한다
```

이 코드를 컴파일해 IL을 보면 무슨 일이 벌어졌는지 알 수 있다.

```il
.method public hidebysig static void Main() cil managed
{
  .entrypoint
  // Code size       13 (0xd)
  .maxstack  1
  .locals init ([0] string s)
  IL_0000:  ldstr      "Hi there."
  IL_0005:  stloc.0
  IL_0006:  ldloc.0
  IL_0007:  call       void [mscorlib]System.Console::WriteLine(string)
  IL_000c:  ret
} // end of method Program::Main
```

객체를 새로 만드는 IL 명령은 `newobj`다. 그런데 위 IL에는 `newobj`가 없다. 대신 **`ldstr`**(load string)이라는 특별한 명령이 있다. 이 명령은 메타데이터에서 가져온 리터럴 문자열로 `String` 객체를 구성한다. CLR이 리터럴 `String` 객체를 만드는 **특별한 경로**를 갖고 있다는 뜻이다.

> **📌 그렇다면 `new String(...)`은 언제 쓰는가**
>
> 안전하지 않은(unsafe) 코드에서는 `Char*`나 `SByte*`로부터 `String`을 만들 수 있다. 이때는 `new` 연산자를 쓰고, `Char*`나 `SByte*` 매개변수를 받는 `String`의 생성자를 호출한다. 이 생성자들은 `Char` 배열이나 부호 있는 바이트 배열로 문자열을 초기화한다.
>
> 포인터 매개변수가 없는 다른 생성자들은 안전한(검증 가능한) 코드에서도 부를 수 있다. 예를 들어 같은 문자를 반복하는 문자열을 만드는 `new string('x', 100)` 오버로드가 있다.
>
> 이 이야기의 핵심은 **리터럴에는 `new`를 쓰지 않는다**는 것이다. `new string("abc")` 같은 코드를 보면 잘못 쓴 것이다.

### 불변성 — 가장 중요한 사실

**`String` 객체에 대해 알아야 할 가장 중요한 사실은 그것이 불변이라는 점이다.** 한번 만들어지면 문자열은 길어질 수도, 짧아질 수도, 문자 하나가 바뀔 수도 없다.

이 사실은 두 가지 방식으로 확인된다.

**첫째, 메서드가 문자열을 바꾸지 않는다.**

```csharp
string s1 = "This is my string.";
string upperString = s1.ToUpper();

Console.WriteLine(s1);            // This is my string.
Console.WriteLine(upperString);   // THIS IS MY STRING.
Console.WriteLine(s1);            // This is my string.   ← 그대로다
```

`ToUpper`는 `s1`을 대문자로 바꾸지 않았다. 대문자로 바뀐 **사본**을 돌려주었을 뿐이다.

**둘째, 인덱서로 문자를 바꿀 수 없다.**

```csharp
string s = "Heat";
char c = s[0];                    // OK — 'H'
// s[0] = 'B';                    // 컴파일 오류 — 인덱서에 setter가 없다
```

`String`의 인덱서는 읽기 전용 프로퍼티다. 배열(9장)과 겉모습이 같지만 결정적으로 다르다.

### 대입도 새 객체를 만든다

C#의 대입 연산자에도 같은 불변 법칙이 적용된다.

```csharp
string s2 = "My other string";
s2 = "New string value";
Console.WriteLine(s2);            // New string value
```

이 코드를 IL로 보면 이렇다.

```il
.method assembly hidebysig static void  StringsAreImmutable2() cil managed
{
  // Code size       32 (0x20)
  .maxstack  1
  .locals init (string V_0)
  IL_0000:  nop
  IL_000c:  ldstr      "My other string"
  IL_0011:  stloc.0
  IL_0012:  ldstr      "New string value"
  IL_0017:  stloc.0
  IL_0018:  ldloc.0
  IL_0019:  ret
} // end of method Program::StringsAreImmutable2
```

`ldstr` 명령이 **두 번** 나온다. 첫 번째 `ldstr`이 `"My other string"`을 담은 객체를 만들고, 두 번째 `ldstr`이 `"New string value"`를 담은 **별개의** 객체를 만든다. `stloc.0`은 지역 변수 `V_0`이 가리키는 대상을 바꿀 뿐이다. 첫 번째 문자열 객체는 아무도 가리키지 않게 되고, 결국 가비지 컬렉터가 회수한다.

그림으로 보면 이렇다.

```text
[1] string s2 = "My other string";

   스택                          관리 힙
  ┌───────────┐                ┌──────────────────────┐
  │  s2  ●────┼───────────────→│ "My other string"    │
  └───────────┘                └──────────────────────┘

[2] s2 = "New string value";

   스택                          관리 힙
  ┌───────────┐                ┌──────────────────────┐
  │  s2  ●─┐  │           ┌───→│ "My other string"    │  ← 도달 불가
  └────────┼──┘           ╳    └──────────────────────┘     (GC 대상)
           │                   ┌──────────────────────┐
           └──────────────────→│ "New string value"   │
                               └──────────────────────┘
```

**변수에 새 값을 대입한 것이지, 문자열을 고친 것이 아니다.** 문자열 객체 자체는 태어나서 죽을 때까지 같은 문자들을 담는다.

> **⚠️ "문자열을 수정했다"는 표현이 이미 틀렸다**
>
> `s = s.Replace("a", "b");` 같은 코드를 "문자열을 수정한다"고 설명하는 자료가 많다. 이 표현이 사고를 부른다. 정확히는 **"새 문자열을 만들어 변수가 그것을 가리키게 한다"** 이다.
>
> 차이가 드러나는 곳은 참조가 둘 이상일 때다.
>
> ```csharp
> string original = "hello";
> string alias    = original;
> original = original.ToUpper();
>
> Console.WriteLine(original);   // HELLO
> Console.WriteLine(alias);      // hello  ← 영향받지 않는다
> ```
>
> `alias`는 여전히 원래 객체를 가리킨다. 그 객체는 바뀌지 않았기 때문이다. **참조 타입인데 별칭(aliasing) 문제가 없다** — 이것이 불변성이 주는 선물이다. 리스트나 배열이었다면 `alias`도 함께 바뀌었을 것이다.

### 불변성이 주는 것

불변 문자열에는 여러 이점이 있다.

**1. 문자열을 실제로 바꾸지 않고도 연산을 이어 붙일 수 있다.**

```csharp
if (s.ToUpperInvariant().Substring(10, 21).EndsWith("EXE"))
{
    // ...
}
```

`ToUpperInvariant`가 새 문자열을 돌려주고, `Substring`이 그 문자열 위에서 동작해 또 새 문자열을 돌려주고, `EndsWith`가 그것을 검사한다. 원본 `s`는 손대지 않았다.

**2. 스레드 동기화 문제가 없다.** 아무도 바꿀 수 없는 데이터는 여러 스레드가 동시에 읽어도 안전하다. 문자열을 여러 스레드에서 공유하면서 락을 걸 필요가 없다. 이것은 대규모 병렬 코드에서 엄청난 단순화다.

**3. CLR이 같은 내용의 문자열을 하나의 객체로 공유할 수 있다.** 같은 문자들을 담은 문자열이 시스템에 여러 개 존재할 필요가 없으므로 메모리를 아낄 수 있다. 이것이 **문자열 인터닝**(string interning)의 근거다. 인터닝의 동작 방식과 메모리 영향, 그리고 그것이 언제 문제가 되는지는 35.5절에서 다룬다.

**4. 안전하게 딕셔너리 키로 쓸 수 있다.** 25.8절에서 볼 "가변 객체를 딕셔너리 키로 쓸 때 생기는 일"이 문자열에는 일어나지 않는다. 해시 코드가 절대 바뀌지 않기 때문이다.

> **📌 `String`이 `sealed`인 이유**
>
> 성능 때문에 `String` 타입은 CLR과 긴밀하게 통합되어 있다. 구체적으로, **CLR은 `String` 타입 안에 정의된 필드의 정확한 레이아웃을 알고 있고 그 필드들에 직접 접근한다.**
>
> 이 성능과 직접 접근에는 작은 개발 비용이 따른다. `String` 클래스는 `sealed`이며, 따라서 자신의 타입의 기반 클래스로 쓸 수 없다. 만약 `String`을 상속할 수 있었다면 필드를 추가할 수 있었을 테고, 그것이 CLR의 가정을 깨뜨렸을 것이다. 또한 `String` 객체가 불변이라는, CLR 팀이 세워 둔 가정도 깨뜨릴 수 있었을 것이다.
>
> 문자열이 힙에 정확히 어떤 모양으로 배치되는지 — 메서드 테이블 포인터, 객체 헤더, 길이 필드, 그리고 문자 데이터가 어디에 놓이는지 — 는 54.7절에서 배열과 함께 다룬다.

### 불변성이 가져가는 것

이점만 있는 것은 아니다. **문자열 조작을 많이 하면 힙에 `String` 객체가 잔뜩 쌓이고, 그 결과 가비지 컬렉션이 더 자주 일어나 애플리케이션 성능이 나빠진다.**

앞의 예를 다시 보자. `ToUpperInvariant`와 `Substring`이 만든 두 개의 임시 문자열은 애플리케이션 코드가 오래 참조하지 않으므로, 다음 컬렉션 때 GC가 메모리를 회수한다. 문자열 하나라면 무시할 만하다. 그 코드가 초당 수만 번 돌면 이야기가 다르다.

정리하면 이렇다. 미국 사회보장번호, 이름, 애플리케이션 안에서 쓰는 짧은 텍스트 조각처럼 **기본적인 문자 데이터**를 나타내는 데는 `string` 클래스가 완벽한 선택이다. 반면 워드프로세서처럼 **자주 바뀌는 대량의 텍스트 데이터**를 다루는 애플리케이션을 `string`으로 표현하는 것은 나쁜 생각이다. 거의 확실히 (그리고 종종 간접적으로) 불필요한 문자열 사본을 계속 만들게 된다.

그럴 때 쓰는 것이 `System.Text.StringBuilder`다. `StringBuilder`의 멤버를 호출하면 사본을 얻는 것이 아니라 객체 내부의 문자 데이터를 **직접 수정한다.** `StringBuilder`의 사용법·용량 증가 전략·언제 이득이고 언제 손해인지는 35.6절에서 다룬다.

> **💡 "문자열이 느리다"는 말의 정확한 의미**
>
> 문자열 자체는 느리지 않다. 인덱싱은 배열 접근만큼 빠르고, 비교는 최적화되어 있다. **느려지는 것은 문자열을 계속 새로 만드는 코드다.**
>
> 판단 기준은 단순하다.
>
> - 문자열을 **읽기만** 하는가 → `string`으로 충분하다. 고민할 것 없다.
> - 문자열을 **정해진 횟수만큼** 조립하는가 → `string` 연결이나 보간으로 충분하다.
> - 문자열을 **루프 안에서, 횟수를 모른 채** 조립하는가 → 여기서부터 문제다(8.5절).
>
> 조기 최적화로 모든 문자열 조립을 `StringBuilder`로 바꾸는 것은 코드만 지저분해지고 이득이 없다. 세 번째 경우에만 손대라.

### `null`과 빈 문자열

`string`은 참조 타입이므로 `null`일 수 있다. 그리고 **`null`인 문자열과 빈 문자열은 완전히 다른 것이다.**

```csharp
string a = null;         // 참조가 아무것도 가리키지 않는다
string b = "";           // 길이 0인 String 객체를 가리킨다
string c = string.Empty; // 길이 0인 String 객체를 가리킨다
```

| 표현 | 참조 | `Length` | `== null` | 메모리 |
|---|---|---|---|---|
| `null` | 없음 | **`NullReferenceException`** | `true` | 참조 슬롯만 |
| `""` | 있음 | `0` | `false` | 빈 문자열 객체 |
| `string.Empty` | 있음 | `0` | `false` | 빈 문자열 객체 |
| `" "` | 있음 | `1` | `false` | 공백 한 개 |

`""`와 `string.Empty`는 같은 것을 나타낸다. `string.Empty`는 `String` 클래스의 정적 읽기 전용 필드이고, `""`는 리터럴이다. 둘을 `==`로 비교하면 `true`다. 취향 문제이므로 팀 안에서 하나로 통일하면 된다.

**`null`은 다르다.** 필드나 배열 요소로 선언된 `string`의 기본값은 `null`이다(6.9절).

```csharp
string[] names = new string[3];
Console.WriteLine(names[0] == null);      // True
// Console.WriteLine(names[0].Length);    // NullReferenceException
```

> **⚠️ `null` 문자열에 메서드를 부르면 던진다 — 단, `==`은 예외다**
>
> ```csharp
> string s = null;
> Console.WriteLine(s == "abc");        // False — 예외 없음
> Console.WriteLine(s.Equals("abc"));   // NullReferenceException
> Console.WriteLine("abc".Equals(s));   // False — 예외 없음
> ```
>
> 세 줄의 차이를 정확히 이해해야 한다.
>
> - `==`는 `String`의 **정적** 연산자다. 피연산자가 `null`인지 먼저 검사하므로 안전하다.
> - `s.Equals(...)`는 **인스턴스** 메서드다. `s`가 `null`이면 호출 대상이 없어 예외가 난다.
> - `"abc".Equals(s)`는 호출 대상이 `null`이 아니므로 안전하고, 인자가 `null`이라 `false`를 준다.
>
> 이 비대칭성 때문에 "상수를 앞에 두는" 관용구(`if ("abc".Equals(s))`)가 존재한다. 다만 요즘 C#에서는 정적 `string.Equals(a, b, StringComparison.Ordinal)`을 쓰거나 널 가능 참조 타입(21.6절)으로 컴파일 타임에 잡는 편이 낫다.
>
> 또 `Console.WriteLine(null)`처럼 `null` 문자열을 출력하면 예외 없이 아무것도 출력되지 않는다. 문자열 보간 안의 `null`도 빈 문자열로 나온다. **`null`이 조용히 빈 문자열처럼 보이는 자리가 있어서** 버그가 늦게 발견된다.

### `IsNullOrEmpty`와 `IsNullOrWhiteSpace`

`null` 검사와 빈 문자열 검사를 매번 두 번 쓰는 것은 번거롭다. `String`은 정적 헬퍼 두 개를 제공한다.

```csharp
public static bool IsNullOrEmpty(string? value);
public static bool IsNullOrWhiteSpace(string? value);
```

차이는 **공백만 있는 문자열을 어떻게 볼 것인가**다.

| 입력 | `IsNullOrEmpty` | `IsNullOrWhiteSpace` |
|---|---|---|
| `null` | `true` | `true` |
| `""` | `true` | `true` |
| `" "` (공백 한 개) | `false` | `true` |
| `"\t\n"` (탭·줄바꿈) | `false` | `true` |
| `"\u00A0"` (비분리 공백) | `false` | `true` |
| `"a"` | `false` | `false` |
| `" a "` | `false` | `false` |

`IsNullOrWhiteSpace`는 내부적으로 각 문자에 `char.IsWhiteSpace`를 적용한다. 그래서 탭·줄바꿈·비분리 공백 같은 "보이지 않지만 존재하는" 문자도 잡아낸다.

```csharp
static void Register(string name)
{
    if (string.IsNullOrWhiteSpace(name))
        throw new ArgumentException("이름이 비어 있다.", nameof(name));
    // ...
}
```

> **💡 사용자 입력에는 `IsNullOrWhiteSpace`, 내부 데이터에는 `IsNullOrEmpty`**
>
> 판단 기준은 "공백만 있는 값이 유효한 값인가"다.
>
> **사용자가 입력한 값**은 거의 항상 `IsNullOrWhiteSpace`다. 사용자가 폼에 스페이스 하나를 입력한 것을 "이름을 입력했다"고 인정하면 안 된다. 웹 폼, CLI 인자, 설정 파일 값이 여기 해당한다.
>
> **프로그램이 만들고 프로그램이 읽는 값**은 `IsNullOrEmpty`다. 여기서는 공백이 의미 있는 데이터일 수 있다. 구분자로 공백을 쓰는 포맷을 파싱하는 중이라면 공백을 "비었다"고 판정하는 순간 데이터가 사라진다.
>
> 그리고 `IsNullOrWhiteSpace`로 검증했다면 저장 전에 `Trim()`도 하라. 검증만 하고 앞뒤 공백을 그대로 저장하면 `"홍길동"`과 `"홍길동 "`이 다른 사용자가 된다.

> **⚠️ `IsNullOrWhiteSpace`가 잡지 못하는 것**
>
> `IsNullOrWhiteSpace`는 `char.IsWhiteSpace`가 `true`를 주는 문자만 공백으로 본다. **제로 폭 공백(U+200B)은 유니코드 분류상 공백이 아니라 서식 문자(Format)다.** 그래서 `"\u200B"`는 `IsNullOrWhiteSpace`에서 `false`가 나온다.
>
> 웹 폼에 붙여넣기로 들어온 텍스트, 워드에서 복사한 문자열에는 이런 문자가 섞이는 일이 드물지 않다. "보기에는 비어 있는데 검증을 통과한 값"이 생기는 전형적인 경로다. 이런 입력을 다뤄야 한다면 정규화 단계를 따로 두고 문제 문자를 명시적으로 제거해야 한다. 유니코드 정규화(normalization)는 35.8절에서 다룬다.

## 8.3 문자열 리터럴 — 축자(`@`), 보간(`$`), 원시 문자열(`"""`) ※C# 11

### 네 가지 리터럴, 그리고 그 조합

C#에는 문자열 리터럴을 쓰는 방법이 네 가지 있다. 각각 다른 시대에, 다른 불만을 해결하려고 추가됐다.

| 형태 | 접두사 | 이스케이프 처리 | 여러 줄 | 도입 |
|---|---|---|---|---|
| 일반 문자열 | 없음 | **한다** | 안 됨 | C# 1 |
| 축자 문자열 | `@` | 안 함 (`""`로 따옴표) | 됨 | C# 1 |
| 보간 문자열 | `$` | 한다 (`{{`로 중괄호) | ※C# 11부터 됨 | C# 6 |
| 원시 문자열 | `"""` | 안 함 | 됨 | ※C# 11 |

이 넷은 서로 조합된다. `$@"..."`, `@$"..."`, `$"""..."""`, `"""..."""u8` 모두 유효하다. 하나씩 본다.

### 일반 문자열 리터럴 — 그리고 백슬래시 지옥

일반 문자열 리터럴은 8.1절에서 본 이스케이프 시퀀스를 전부 해석한다. 편리하지만 대가가 있다. **백슬래시 하나가 필요할 때마다 두 개를 써야 한다.**

```csharp
string a1 = "\\\\server\\fileshare\\helloworld.cs";
```

이것이 `\\server\fileshare\helloworld.cs`를 뜻한다는 것을 한눈에 읽을 사람은 없다. 윈도우 경로, 정규식, 이스케이프가 있는 JSON을 문자열에 담으려면 이 지옥을 지나야 한다.

### 축자 문자열 리터럴 — `@`

이 문제를 피하려고 C#은 **축자 문자열 리터럴**(verbatim string literal)을 제공한다. `@` 접두사를 붙이면 이스케이프 시퀀스를 지원하지 않는다. 백슬래시가 그냥 백슬래시다.

```csharp
string a2 = @"\\server\fileshare\helloworld.cs";      // 위와 같은 문자열
```

컴파일러에게 "백슬래시를 이스케이프 문자가 아니라 백슬래시 문자로 취급하라"고 말하는 것이다. 경로가 소스에서 훨씬 읽기 쉬워진다.

```csharp
string file1 = "C:\\Windows\\System32\\Notepad.exe";
string file2 = @"C:\Windows\System32\Notepad.exe";    // 동일한 문자열
```

두 줄 모두 어셈블리 메타데이터에 **같은** 문자열을 만든다. 차이는 소스 코드의 가독성뿐이다.

축자 문자열은 **여러 줄에 걸칠 수 있고, 공백이 그대로 보존된다.**

```csharp
string escaped  = "First Line\r\nSecond Line";
string verbatim = @"First Line
Second Line";

// 편집기가 CR-LF 줄 구분자를 쓴다면 True
Console.WriteLine(escaped == verbatim);
```

마지막 줄의 조건이 함정의 씨앗이다. 잠시 뒤에 본다.

축자 문자열 안에 큰따옴표를 넣으려면 **두 번 쓴다.**

```csharp
string xml = @"<customer id=""123""></customer>";
Console.WriteLine(@"Cerebus said ""Darrr! Pret-ty sun-sets""");
```

> **⚠️ 축자 문자열의 줄바꿈은 소스 파일이 결정한다**
>
> 축자 문자열이 여러 줄에 걸치면, 그 안에 들어가는 줄바꿈 문자는 **소스 파일에 실제로 저장된 바이트**다. 소스 파일이 CRLF로 저장되어 있으면 `\r\n`이 들어가고, LF로 저장되어 있으면 `\n`이 들어간다.
>
> 이것이 왜 문제인가.
>
> 1. **같은 코드가 개발자마다 다른 문자열을 만든다.** Git의 `core.autocrlf` 설정에 따라 체크아웃된 파일의 줄바꿈이 달라지면, 같은 커밋에서 빌드한 바이너리가 서로 다른 문자열 상수를 갖는다.
> 2. **테스트가 환경 의존적이 된다.** 위 예제의 `escaped == verbatim` 비교가 어떤 머신에서는 `true`, 어떤 머신에서는 `false`다.
> 3. **`.gitattributes`나 `.editorconfig`를 고치면 조용히 깨진다.** 코드 한 줄 바꾸지 않았는데 동작이 달라진다.
>
> 여러 줄 문자열의 줄바꿈이 **의미 있는 데이터**라면(프로토콜 메시지, 파일 포맷) 축자 문자열에 줄바꿈을 맡기지 마라. `string.Join(Environment.NewLine, lines)`나 `"\n"`을 명시적으로 쓰는 편이 안전하다. 이 함정은 곧 볼 원시 문자열에도 그대로 적용된다.

> **⚠️ `@`의 두 얼굴**
>
> 6.2절에서 본 것처럼 `@`는 **식별자 앞**에 붙으면 예약 키워드 이스케이프다(`@class`, `@if`). **문자열 리터럴 앞**에 붙으면 축자 문자열이다. 완전히 다른 기능이 같은 기호를 쓴다.
>
> ```csharp
> var @string = @"C:\temp";     // 앞의 @는 식별자 이스케이프, 뒤의 @는 축자 문자열
> ```
>
> 이런 코드를 쓸 일은 없기를 바라지만, 컴파일러 오류 메시지에서 `@`를 볼 때 어느 쪽인지 구분할 수 있어야 한다.

### 보간 문자열 리터럴 — `$`

`$` 문자를 앞에 붙인 문자열을 **보간 문자열**(interpolated string)이라고 한다. 보간 문자열은 중괄호로 감싼 식을 포함할 수 있다.

```csharp
int x = 4;
Console.Write($"A square has {x} sides");     // A square has 4 sides
```

`{0}`, `{1}` 같은 중괄호 문법은 .NET 1.0부터 있었다. C# 6부터는 변수를 콤마로 구분된 목록으로 뒤에 나열하는 대신 **변수 자체를 문자열 안에 직접 넣을 수 있다.**

```csharp
int age = 4;
string name = "Soren";

// 전통적인 중괄호 문법
string greeting  = string.Format("Hello {0} you are {1} years old.", name, age);

// 보간 문자열
string greeting2 = $"Hello {name} you are {age} years old.";
```

이 문법의 장점은 왼쪽에서 오른쪽으로 선형으로 읽힌다는 것이다. 값을 확인하려고 문자열 끝까지 "점프"할 필요가 없다.

중괄호 안에는 **타입을 가리지 않고 유효한 C# 식이면 무엇이든** 올 수 있다. C#은 그 식의 `ToString` 메서드(또는 그에 준하는 것)를 호출해 문자열로 바꾼다. 중괄호는 유효한 스코프이므로 점 연산자로 멤버를 호출할 수도 있다.

```csharp
string greeting3 = $"Hello {name.ToUpper()} you are {age} years old.";
```

다만 중괄호 안에서 메서드를 호출할 때 세미콜론을 붙이지 않는다. 중괄호 스코프는 여러 줄의 실행 코드를 담는 완전한 메서드 스코프가 아니다. 멤버 하나를 점 연산자로 호출하거나 `{age + 1}` 같은 단순한 일반 식을 정의할 수 있을 뿐이다.

보간 문자열 안에서도 이스케이프 문자를 그대로 쓸 수 있다.

```csharp
string greeting4 = $"\tHello {name.ToUpper()} you are {age} years old.";
```

### 서식 지정자와 정렬

식 뒤에 콜론과 서식 문자열을 붙여 출력 형태를 바꿀 수 있다.

```csharp
string s = $"255 in hex is {byte.MaxValue:X2}";   // X2 = 2자리 16진수
// "255 in hex is FF"
```

콤마를 붙이면 **정렬 폭**을 지정한다. 양수는 오른쪽 정렬, 음수는 왼쪽 정렬이다.

```csharp
Console.WriteLine($"|{"이름",-10}|{"수량",5}|");
Console.WriteLine($"|{"연필",-10}|{12,5}|");
// |이름        |   수량|
// |연필        |   12|
```

전체 문법은 `{식,정렬:서식}` 순서다. 정렬과 서식 둘 다 선택 사항이다.

| 부분 | 의미 | 예 |
|---|---|---|
| `{식}` | 식의 `ToString()` | `{count}` |
| `{식:서식}` | 서식 문자열 적용 | `{price:C}`, `{n:X2}`, `{d:yyyy-MM-dd}` |
| `{식,폭}` | 지정 폭으로 정렬 | `{name,-20}` |
| `{식,폭:서식}` | 정렬 + 서식 | `{price,10:N2}` |

서식 문자열의 전체 목록 — 표준 숫자 서식, 사용자 지정 숫자 서식, 날짜/시간 서식 — 은 38.3절과 38.5절에서 다룬다.

> **⚠️ 삼항 연산자를 보간 문자열에 넣으려면 괄호가 필요하다**
>
> 콜론이 서식 지정자의 구분자이므로, 콜론을 다른 용도로 쓰려면 **식 전체를 괄호로 감싸야 한다.** 대표적인 것이 조건 연산자(7.10절)다.
>
> ```csharp
> bool b = true;
> // Console.WriteLine($"The answer in binary is {b ? 1 : 0}");   // 컴파일 오류
> Console.WriteLine($"The answer in binary is {(b ? 1 : 0)}");    // OK
> ```
>
> 괄호 없이 쓰면 컴파일러가 `b ? 1`을 식으로, `0`을 서식 문자열로 읽으려다 실패한다. 오류 메시지가 원인을 잘 설명해 주지 않아서 처음 만나면 당황하기 쉽다.

### 중괄호 자체를 넣으려면

보간 문자열에 중괄호 문자를 그대로 넣으려면 **그 문자를 반복한다.**

```csharp
Console.WriteLine($"{{{name}}}");     // {Soren}
Console.WriteLine($"CSS: body {{ margin: 0 }}");
```

`{{`가 `{` 하나가 되고 `}}`가 `}` 하나가 된다. 이 규칙은 일반 문자열과 축자 문자열에 모두 적용된다. 원시 문자열에서는 다른 방법을 쓴다(뒤에서 본다).

> **⚠️ `string.Format`에도 같은 규칙이 있다**
>
> `{{`/`}}` 이스케이프는 보간 문자열만의 규칙이 아니다. `string.Format`과 `Console.WriteLine(format, args)`의 서식 문자열에도 동일하게 적용된다.
>
> 그래서 **사용자 입력이나 외부 데이터를 서식 문자열 자리에 넣으면 안 된다.**
>
> ```csharp
> string userInput = "{0}";
> // Console.WriteLine(userInput);              // 안전 — 서식 처리 없음
> // Console.WriteLine(userInput, someValue);   // userInput이 서식 문자열로 해석된다
> // string.Format(userInput);                  // FormatException
> ```
>
> 사용자가 `"{99}"`를 입력하면 `FormatException`이 난다. 로그 메시지를 만들 때 흔히 벌어지는 사고다. 서식 문자열은 항상 코드가 소유해야 하고, 외부 데이터는 인자로만 들어가야 한다.

### 보간 문자열의 확장 — C# 8, 10, 11

**축자 + 보간의 조합(※C# 8부터 순서 무관).** `$`와 `@`를 함께 쓸 수 있다.

```csharp
string interp = "interpolation";
string myLongString = $@"This is a very
   very
         long string with {interp}";
```

※C# 8부터는 `$@`든 `@$`든 순서가 상관없다. 그 이전에는 `$@` 순서만 허용됐다.

**상수 보간 문자열(※C# 10).** 보간되는 값이 전부 상수면 보간 문자열도 상수가 될 수 있다.

```csharp
const string greeting = "Hello";
const string message  = $"{greeting}, world";
```

**여러 줄 보간(※C# 11).** 보간 구멍(interpolation hole) 안의 식이 여러 줄에 걸칠 수 있다. 일반 문자열이든 축자 문자열이든 마찬가지다.

```csharp
string s = $"this interpolation spans {1 +
    1} lines";
```

> **📌 보간 문자열은 무엇으로 컴파일되는가**
>
> C# 9까지는 컴파일러가 보간 문자열을 `String.Format` 호출로 바꿨다. IL을 열어 보면 `string.Format(...)`을 직접 부른 코드와 보간 문자열을 쓴 코드가 **완전히 같은 IL**이었다.
>
> ```il
> IL_0009:  ldstr      "\tHello {0} you are {1} years old."
> IL_000e:  ldloc.1
> IL_000f:  callvirt   instance string [System.Runtime]System.String::ToUpper()
> IL_0014:  ldloc.0
> IL_0015:  box        [System.Runtime]System.Int32
> IL_001a:  call       string [System.Runtime]System.String::Format(string, object, object)
> ```
>
> `box` 명령이 보이는가. 값 타입인 `age`가 `object`로 박싱됐다. 그리고 `Format`은 런타임에 서식 문자열을 다시 파싱해 리터럴·서식 항목·지정자·정렬을 찾아낸다 — **컴파일러가 컴파일 타임에 이미 알고 있던 일을 런타임에 반복하는 것이다.** 인자가 셋을 넘으면 배열도 할당된다.
>
> ※C# 10에서 이것이 바뀌었다. 컴파일 타임에 할 수 있는 일을 `DefaultInterpolatedStringHandler`와 그 메서드들을 써서 IL에 담아 둔다. `AppendLiteral`로 리터럴을, `AppendFormatted`로 변수를 넣고 `ToStringAndClear`로 마무리하는 형태다. 벤치마크에서 유의미한 성능 개선이 확인됐다.
>
> 좋은 소식은 **이 코드를 직접 쓸 필요가 없다는 것**이다. 컴파일러가 알아서 한다. 생성되는 코드의 정확한 형태와 성능 특성, 그리고 `[InterpolatedStringHandler]`로 직접 핸들러를 만드는 방법은 35.7절에서 다룬다.

> **⚠️ 로깅 API에 보간 문자열을 쓰지 마라**
>
> 보간 문자열은 **호출 지점에서 즉시 문자열을 만든다.** 로그 레벨이 꺼져 있어도 만든다.
>
> ```csharp
> logger.LogDebug($"처리 완료: {ComputeExpensiveSummary()}");   // 항상 실행된다
> logger.LogDebug("처리 완료: {Summary}", summary);             // 필요할 때만 서식화
> ```
>
> 두 번째 형태는 구조적 로깅(structured logging)의 표준 형태이기도 하다. 로그 수집기가 `Summary`를 별도 필드로 인덱싱할 수 있다. 첫 번째 형태는 그냥 문자열 한 덩어리다.
>
> 다만 `LoggerMessage.Define`이나 `[LoggerMessage]` 소스 생성기를 쓰는 최신 코드에서는 사정이 다르고, ※C# 10의 보간 문자열 핸들러를 받는 로깅 API도 존재한다. 어느 쪽이든 **"레벨이 꺼져 있으면 문자열을 만들지 않는다"는 보장이 있는지**를 확인하고 써야 한다.

### 원시 문자열 리터럴 — `"""` ※C# 11

축자 문자열도 완벽하지는 않았다. 큰따옴표를 두 번 써야 하는 규칙 때문에 JSON을 담으면 여전히 지저분하다.

**세 개 이상의 큰따옴표로 문자열을 감싸면 원시 문자열 리터럴**(raw string literal)이 된다. ※C# 11에서 들어왔다. 원시 문자열 리터럴은 이스케이프도, 문자 중복도 없이 거의 모든 문자 시퀀스를 담을 수 있다.

```csharp
string raw = """<file path="c:\temp\test.txt"></file>""";
```

백슬래시도 큰따옴표도 그대로다. 이 덕분에 JSON, XML, HTML 리터럴은 물론 정규식과 소스 코드를 문자열로 표현하기가 쉬워진다.

문자열 자체에 큰따옴표를 세 개(또는 그 이상) 넣어야 하면 **네 개(또는 그 이상)로 감싼다.**

```csharp
string raw2 = """"The """ sequence denotes raw string literals."""";
```

규칙은 단순하다. **여는 따옴표의 개수보다 적은 연속 따옴표는 내용으로 취급된다.** 필요한 만큼 늘리면 된다.

### 원시 문자열의 들여쓰기 규칙

여러 줄 원시 문자열 리터럴에는 특별한 규칙이 적용된다. `"Line 1\r\nLine 2"`를 이렇게 쓸 수 있다.

```csharp
string multiLineRaw = """
    Line 1
    Line 2
    """;
```

규칙은 세 가지다.

1. **여는 따옴표와 닫는 따옴표는 문자열 내용과 다른 줄에 있어야 한다.**
2. **여는 `"""` 뒤(같은 줄)의 공백은 무시된다.**
3. **닫는 `"""` 앞(같은 줄)의 공백은 공통 들여쓰기(common indentation)로 취급되어 모든 줄에서 제거된다.**

세 번째가 핵심이다. 이 규칙 덕분에 소스 코드의 가독성을 위해 들여쓰기를 넣어도 그 들여쓰기가 문자열의 일부가 되지 않는다.

그림으로 보면 이렇다. 공백을 눈에 보이게 하려고 `.` 한 개를 공백 한 칸으로 그렸다.

```text
소스 코드                          내가 지정한 공통 들여쓰기
─────────────────────────────      ┌──────┐
    string json = """              │      │  ← 이 폭이 기준이 된다
    ....{                          └──────┘
    ....    "Name" : "Joe"          ↑
    ....}                           닫는 """ 앞의 공백
    ....""";                        (여기서는 4칸)
    ↑↑↑↑
    모든 줄에서 이 4칸이 제거된다

결과 문자열
─────────────────────────────
┌────────────────────────┐
│ {                      │
│     "Name" : "Joe"     │  ← 4칸을 뺀 나머지 들여쓰기는 남는다
│ }                      │
└────────────────────────┘

규칙 위반 (컴파일 오류)
─────────────────────────────
    string bad = """
    ....{
    ..    "Name" : "Joe"     ← 공통 들여쓰기(4칸)보다 얕다
    ....}
    ....""";
```

조건문 안에 넣은 예를 보자.

```csharp
if (true)
    Console.WriteLine("""
        {
            "Name" : "Joe"
        }
        """);
```

출력은 이렇다.

```text
{
    "Name" : "Joe"
}
```

`if` 블록 안이라 소스에서는 여덟 칸 들여써 있지만, 출력된 문자열에는 그 들여쓰기가 없다. `"Name"` 줄이 여전히 네 칸 들여써 있는 것은 **닫는 따옴표 기준으로 상대적인** 들여쓰기이기 때문이다.

> **⚠️ 공통 들여쓰기를 어기면 컴파일 오류다**
>
> 여러 줄 원시 문자열 리터럴의 각 줄이 닫는 따옴표가 지정한 공통 들여쓰기로 시작하지 않으면 **컴파일러가 오류를 낸다.**
>
> ```csharp
> string bad = """
>         Line 1
>     Line 2        ← 공통 들여쓰기보다 덜 들여썼다
>         """;      // 컴파일 오류
> ```
>
> 이것은 좋은 설계다. 조용히 이상한 문자열이 만들어지는 대신 컴파일 타임에 잡힌다. 축자 문자열이었다면 아무 경고 없이 들여쓰기가 문자열에 섞여 들어갔을 것이다.
>
> 함정은 **탭과 스페이스를 섞을 때** 나온다. 공통 들여쓰기는 문자 단위로 비교되므로, 닫는 따옴표 앞이 탭 하나이고 내용 줄이 스페이스 네 개면 시각적으로 같아 보여도 오류가 난다. `.editorconfig`로 파일의 들여쓰기 문자를 통일해 두는 것이 예방책이다.

> **💡 원시 문자열을 언제 쓰는가**
>
> 판단은 간단하다.
>
> - **따옴표나 백슬래시가 많은가** → 원시 문자열. JSON, XML, HTML, 정규식, 윈도우 경로, SQL.
> - **여러 줄이고 들여쓰기가 코드 안에 있는가** → 원시 문자열. 축자 문자열보다 확실히 낫다.
> - **한 줄이고 특수문자가 없는가** → 일반 문자열. `"""abc"""`는 과하다.
>
> 새 코드에서 축자 문자열(`@`)을 쓸 이유는 거의 없어졌다. 다만 C# 11 미만을 대상으로 하는 코드베이스에서는 여전히 축자 문자열이 유일한 선택이다. 언어 버전은 `.csproj`의 `<LangVersion>`이 결정한다(4장).

### 원시 문자열과 보간의 조합

원시 문자열 리터럴도 보간할 수 있다. ※C# 11.

```csharp
string s = $"""The date and time is {DateTime.Now}""";
```

그런데 문제가 있다. JSON은 중괄호를 쓰는 포맷이다. 보간 문자열 안에서 중괄호를 쓰려면 이스케이프해야 하는데, 그러면 "복사해서 붙여넣기만 하면 되는" 원시 문자열의 장점이 사라진다.

C#의 해법은 우아하다. **`$` 접두사를 반복하면 보간 시퀀스가 중괄호 두 개(또는 그 이상)로 바뀐다.**

```csharp
Console.WriteLine($$"""{ "TimeStamp": "{{DateTime.Now}}" }""");
// 출력: { "TimeStamp": "01/01/2024 12:13:25 PM" }
```

`$$`를 썼으므로 보간 구멍은 `{{...}}`가 되고, 중괄호 **하나**는 그냥 중괄호 문자다. JSON 템플릿을 그대로 붙여넣고 값을 넣을 자리만 `{{ }}`로 감싸면 된다.

| 접두사 | 보간 구멍 | 중괄호 하나 |
|---|---|---|
| `$"..."` | `{expr}` | `{{`, `}}`로 이스케이프 |
| `$$"""..."""` | `{{expr}}` | `{`, `}` 그대로 |
| `$$$"""..."""` | `{{{expr}}}` | `{`, `{{` 그대로 |

> **⚠️ 원시 문자열 안에서는 이스케이프가 동작하지 않는다**
>
> 원시 문자열 리터럴은 이스케이프 시퀀스를 **전혀 해석하지 않는다.** 축자 문자열과 같다.
>
> ```csharp
> string s = """C:\temp\new.txt""";
> Console.WriteLine(s);          // C:\temp\new.txt  — \n이 줄바꿈이 되지 않는다
>
> string t = """탭:\t끝""";
> Console.WriteLine(t);          // 탭:\t끝          — 탭이 아니라 백슬래시와 t
> ```
>
> 일반 문자열에서 원시 문자열로 리팩터링할 때 이 차이를 놓치면 조용히 다른 문자열이 된다. `\t`, `\n`, `\\`가 들어 있는 문자열을 원시 문자열로 옮길 때는 각각을 실제 탭·줄바꿈으로 바꿔야 한다.
>
> 반대 방향도 마찬가지다. 원시 문자열에 담긴 정규식을 일반 문자열로 옮기면 백슬래시를 전부 두 배로 늘려야 한다.

## 8.4 UTF-8 문자열 리터럴 (`u8`) ※C# 11

### 문제 — .NET의 문자열은 UTF-16이다

여기까지 본 모든 문자열은 UTF-16이다. `char`가 16비트 코드 단위이고, `string`은 그 코드 단위의 배열이다. 이것은 .NET이 태어난 시대의 선택이었고, 대부분의 상황에서 문제가 없다.

그런데 바깥 세상은 UTF-8이다. HTTP 헤더도, JSON도, 대부분의 텍스트 파일도, 유닉스 계열 시스템의 파일 이름도 UTF-8이다. 그래서 이런 코드가 나온다.

```csharp
// 소켓에서 읽은 UTF-8 바이트가 "application/json"으로 시작하는지 확인
byte[] buffer = ReceiveFromSocket();
string text = Encoding.UTF8.GetString(buffer);        // ① 디코딩 + 할당
if (text.StartsWith("application/json"))              // ② UTF-16끼리 비교
{
    // ...
}
```

①에서 전체 버퍼를 UTF-16 문자열로 **디코딩하고 힙에 할당한다.** 그 문자열은 비교 한 번 하고 버려진다. 초당 수만 건의 요청을 처리하는 서버에서는 이 낭비가 실제로 보인다.

반대 방향으로 접근하면 어떨까. 비교 대상인 `"application/json"`을 미리 UTF-8 바이트로 준비해 두고, 버퍼를 디코딩하지 않고 **바이트끼리** 비교하면 된다.

```csharp
byte[] pattern = Encoding.UTF8.GetBytes("application/json");    // 여전히 매번 할당
```

`Encoding.UTF8.GetBytes`는 호출할 때마다 새 `byte[]`를 만든다. `static readonly` 필드에 담아 캐싱할 수는 있지만, 그러려면 정적 생성자나 필드 초기화 순서를 신경 써야 하고 여전히 힙 객체 하나가 생긴다.

### 해법 — `u8` 접미사

※C# 11부터 `u8` 접미사를 붙이면 UTF-16이 아니라 **UTF-8로 인코딩된 문자열 리터럴**을 만들 수 있다. 이 기능은 성능이 중요한 지점에서 JSON 텍스트를 저수준으로 다루는 것 같은 고급 시나리오를 위한 것이다.

```csharp
ReadOnlySpan<byte> utf8 = "ab\u2192cd"u8;    // 화살표 기호는 3바이트를 차지한다
Console.WriteLine(utf8.Length);              // 7
```

`Length`가 7인 이유를 세어 보자.

| 문자 | UTF-8 바이트 | 개수 |
|---|---|---|
| `a` | `61` | 1 |
| `b` | `62` | 1 |
| `→` (U+2192) | `E2 86 92` | **3** |
| `c` | `63` | 1 |
| `d` | `64` | 1 |
| **합계** | | **7** |

문자는 다섯 개인데 길이는 7이다. **`u8` 리터럴의 `Length`는 문자 수가 아니라 바이트 수다.**

### 타입은 `ReadOnlySpan<byte>`다

이것이 이 기능에서 가장 중요한 사실이다. `u8` 리터럴의 타입은 `string`도 `byte[]`도 아닌 **`ReadOnlySpan<byte>`** 다.

```csharp
var x = "abc"u8;
Console.WriteLine(x.GetType());          // 컴파일 오류 — ref struct는 박싱할 수 없다
```

`ReadOnlySpan<T>`는 `ref struct`이고, `ref struct`에는 강한 제약이 따른다. 클래스의 필드가 될 수 없고, 박싱할 수 없고, 제네릭 타입 인자로 쓸 수 없고, 반복자나 `async` 메서드 안에서 살아남을 수 없다. 이 제약들과 그 근거는 68.1절에서, `Span<T>`의 내부 구조는 68.2절에서 다룬다.

당장 알아야 할 것은 **어디에 담을 수 있는가**다.

```csharp
// 필드로는 안 된다
// static ReadOnlySpan<byte> Json = "application/json"u8;    // 컴파일 오류

// 프로퍼티로는 된다 — 호출될 때마다 스팬을 새로 만들지만 할당은 없다
static ReadOnlySpan<byte> Json => "application/json"u8;

// 배열이 필요하면 ToArray()
static readonly byte[] JsonBytes = "application/json"u8.ToArray();
```

`static` 프로퍼티로 노출하는 것이 관용구다. 프로퍼티 본문이 인라인되면 리터럴을 직접 쓴 것과 같은 코드가 된다.

### 할당이 없다

`u8` 리터럴의 바이트들은 **컴파일 타임에 어셈블리 안에 그대로 박힌다.** 런타임에는 그 데이터를 가리키는 스팬을 만들 뿐이고, 힙 할당이 일어나지 않는다.

```text
  일반 문자열 리터럴                     u8 리터럴
  ─────────────────────                 ─────────────────────
  ldstr "application/json"              어셈블리 데이터 영역
        ↓                                ┌──────────────────┐
  메타데이터의 문자열 힙                 │ 61 70 70 6C ...  │  (UTF-8 바이트)
        ↓                                └──────────────────┘
  관리 힙의 String 객체                          ↑
  (인터닝되어 재사용, 35.5절)            ReadOnlySpan<byte>가 가리킴
                                         (관리 힙 할당 없음)
```

`Encoding.UTF8.GetBytes("application/json")`와 비교하면 차이가 분명하다. 후자는 (1) UTF-16 문자열 객체를 힙에서 가져와 (2) 런타임에 인코딩을 수행하고 (3) 새 `byte[]`를 힙에 할당한다. `u8` 리터럴은 이 셋을 전부 컴파일 타임으로 옮긴다.

> **⚠️ `u8`은 보간 문자열에 쓸 수 없다**
>
> ```csharp
> // var bad = $"id={id}"u8;      // 컴파일 오류
> ```
>
> 보간 문자열은 런타임에 값을 조립한다. `u8` 리터럴은 컴파일 타임에 바이트를 확정하는 기능이므로 둘은 원리적으로 섞이지 않는다.
>
> 런타임에 만든 텍스트를 UTF-8 바이트로 바꾸려면 `Encoding.UTF8.GetBytes`를 쓰거나, 할당 없이 하려면 `Encoding.UTF8.GetBytes(chars, bytes)` 스팬 오버로드에 `stackalloc` 버퍼를 넘긴다(68.9절). ※.NET 8에서는 `IUtf8SpanFormattable`을 통해 숫자·날짜를 UTF-8 바이트로 직접 서식화할 수도 있다(38.8절).

> **⚠️ `ReadOnlySpan<byte>`의 `==`는 내용 비교가 아니다**
>
> `string`과 달리 스팬의 `==` 연산자는 **같은 메모리를 같은 길이로 가리키는지**를 본다. 내용이 같아도 다른 메모리면 `false`다.
>
> 내용을 비교하려면 `SequenceEqual`을 쓴다.
>
> ```csharp
> ReadOnlySpan<byte> received = buffer;
> if (received.StartsWith("application/json"u8))   // 스팬의 StartsWith
> {
>     // ...
> }
> if (received.SequenceEqual("OK"u8))              // 내용 동등 비교
> {
>     // ...
> }
> ```
>
> `MemoryExtensions`가 제공하는 `SequenceEqual`, `StartsWith`, `IndexOf` 같은 확장 메서드들이 스팬 위에서 동작한다(68.4절).

> **⚠️ `u8` 스팬의 `ToString()`은 텍스트를 주지 않는다**
>
> ```csharp
> ReadOnlySpan<byte> s = "hello"u8;
> Console.WriteLine(s.ToString());          // "hello"가 아니다
> ```
>
> `ReadOnlySpan<char>`의 `ToString()`은 문자열을 만들지만, `ReadOnlySpan<byte>`는 그냥 바이트 시퀀스이므로 타입 이름과 길이를 나타내는 문자열이 나온다.
>
> 바이트를 텍스트로 되돌리려면 명시적으로 디코딩한다.
>
> ```csharp
> Console.WriteLine(Encoding.UTF8.GetString(s));   // hello
> ```
>
> 디버깅 중에 `u8` 스팬을 출력해 보고 "값이 깨졌다"고 오해하는 일이 흔하다. 깨진 것이 아니라 원래 그렇다.

> **💡 `u8`을 쓸 자리와 쓰지 말 자리**
>
> `u8` 리터럴은 **핫 패스에서 UTF-8 바이트를 디코딩하지 않고 비교·검색할 때** 값을 한다. 구체적으로는 JSON 프로퍼티 이름 매칭, HTTP 헤더 값 판별, 바이너리 프로토콜의 매직 넘버, 파일 시그니처 검사 같은 곳이다.
>
> 그 밖의 모든 곳에서는 `string`을 써라. 이유는 셋이다.
>
> 1. **`ref struct` 제약이 코드를 오염시킨다.** 필드에 못 담고 `async`를 통과하지 못하므로, `u8`을 쓰기 시작하면 주변 코드 구조가 그 제약에 맞춰 뒤틀린다.
> 2. **읽기가 어렵다.** 바이트 스팬에는 `Substring`도 `Split`도 `Replace`도 없다. 있는 것은 스팬 확장 메서드뿐이다.
> 3. **이득이 측정되지 않으면 이득이 아니다.** 초당 수만 건이 아닌 코드에서 바이트 배열 하나 아끼는 것은 의미가 없다.
>
> 텍스트를 스팬으로 다루는 전반적인 기법은 68.5절, UTF-8과 UTF-16의 인코딩 규칙 자체는 35.8절에서 다룬다.

## 8.5 문자열 연결·비교의 기초 (심화는 35장)

### `+`는 `String.Concat`이다

`+` 연산자가 두 문자열을 연결한다.

```csharp
string s1 = "Programming the ";
string s2 = "PsychoDrill (PTP)";
string s3 = s1 + s2;
Console.WriteLine(s3);       // Programming the PsychoDrill (PTP)
```

C# 컴파일러는 `+` 기호를 처리해 정적 `String.Concat` 메서드 호출을 뿜는다. 그래서 `String.Concat`을 직접 불러도 같은 일을 할 수 있다(타자만 늘어날 뿐 얻는 것은 없다).

```csharp
string s3 = String.Concat(s1, s2);      // 위와 동일
```

IL로 확인하면 이렇다.

```il
  IL_000d:  ldloc.0
  IL_000e:  ldloc.1
  IL_000f:  call       string [System.Runtime]System.String::Concat(string, string)
  IL_0014:  stloc.2
```

`Concat`은 두 문자열의 길이를 더해 그만큼의 새 `String` 객체를 힙에 만들고, 양쪽 내용을 복사해 넣는다. **연결 한 번마다 객체 하나와 전체 복사가 발생한다.**

### 리터럴끼리는 컴파일 타임에 합쳐진다

리터럴만 연결하면 이야기가 다르다.

```csharp
string s = "Hi" + " " + "there.";
```

모든 피연산자가 리터럴이므로 C# 컴파일러가 **컴파일 타임에** 이들을 연결하고, 모듈의 메타데이터에 `"Hi there."` 하나만 넣는다. 런타임에는 `ldstr` 한 번이 전부다. 이것을 상수 폴딩(constant folding)이라고 한다.

리터럴이 아닌 문자열에 `+`를 쓰면 연결이 런타임에 일어난다. 여러 문자열을 런타임에 이어 붙일 때 `+` 연산자를 피해야 하는 이유가 이것이다 — 가비지 컬렉션 힙에 문자열 객체를 여러 개 만들기 때문이다.

> **📌 `a + b + c + d`는 `Concat` 한 번이다**
>
> `+`를 여러 번 이어 쓴다고 임시 문자열이 그만큼 생기지는 않는다. 컴파일러가 연결 사슬을 하나로 평탄화해 인자가 여러 개인 `Concat` 오버로드를 부른다.
>
> ```csharp
> string full = first + " " + middle + " " + last;
> ```
>
> 이 식은 `Concat(string, string, string, string, string)` 한 번으로 컴파일된다. 인자가 더 많으면 배열을 받는 `Concat(string[])` 오버로드가 쓰인다.
>
> 그러니 **한 식(expression) 안의 연결은 걱정할 필요가 없다.** 문제는 언제나 여러 문(statement)에 걸친, 특히 루프 안의 연결이다.

### 문자열이 아닌 피연산자

피연산자 중 하나가 문자열이 아니어도 된다. 그 값의 `ToString`이 호출된다.

```csharp
string s = "a" + 5;          // "a5"
```

값이 상수면 이것도 컴파일 타임에 접힌다. 상수가 아니면 런타임에 `ToString`이 불린다.

```csharp
int count = GetCount();
string s = "개수: " + count;      // count.ToString()이 런타임에 호출된다
```

> **⚠️ 값 타입을 문자열에 더하면 박싱이 일어날 수 있다**
>
> `string + object` 형태의 연결에서는 값 타입이 `object`로 박싱된 뒤 `Concat(object, object)`가 그 위에서 `ToString`을 부르는 경로가 존재한다. 컴파일러 버전에 따라 값 타입의 `ToString`을 먼저 호출해 박싱을 피하는 최적화가 적용되기도 하므로, 생성되는 IL은 컴파일러 버전에 따라 다를 수 있다.
>
> **확실한 것은, 값 타입을 문자열에 이어 붙이는 코드가 루프 안에 있으면 문자열 객체와 박싱이 함께 쌓일 수 있다는 것이다.** 박싱 자체는 15.2절, 그리고 문자열 연결·포매팅이 만드는 숨은 할당의 전체 목록은 63.9절에서 다룬다.
>
> 확신이 필요하면 추측하지 말고 확인하라. 릴리스 빌드로 컴파일한 뒤 ILDasm이나 온라인 디스어셈블러로 실제 IL을 보는 것이 유일하게 확실한 방법이다.

### `null`을 연결하면

`+`로 `null` 문자열을 연결해도 예외가 나지 않는다. `Concat`이 `null`을 빈 문자열로 취급한다.

```csharp
string a = null;
string s = "값: " + a;        // "값: "  — 예외 없음
Console.WriteLine(s.Length);  // 4
```

이것은 편리하지만 위험하기도 하다. **`null`이 조용히 사라진다.** 데이터베이스에서 읽은 값이 `null`인데 로그에는 그냥 `"값: "`으로 찍혀서, 문제를 며칠 뒤에야 발견하는 일이 생긴다. 값이 반드시 있어야 하는 자리라면 연결 전에 검사하라.

### 루프 안의 `+=`가 왜 나쁜가

`+` 연산자를 반복해서 써서 문자열을 쌓아 올리는 것은 비효율적이다. **문자열이 불변이기 때문이다.**

```csharp
string s = "";
for (int i = 0; i < n; i++)
    s += "ab";                // 매 반복마다 새 문자열
```

한 번 도는 동안 무슨 일이 벌어지는지 그려 보자.

```text
반복 1:  ""       + "ab"  →  "ab"          객체 1개,  2자 복사
반복 2:  "ab"     + "ab"  →  "abab"        객체 1개,  4자 복사
반복 3:  "abab"   + "ab"  →  "ababab"      객체 1개,  6자 복사
반복 4:  "ababab" + "ab"  →  "abababab"    객체 1개,  8자 복사
                                              ...
반복 n:                                    객체 1개, 2n자 복사

  ┌─────────────────────────────────────────────────────────┐
  │ 총 객체 수  : n개                                       │
  │ 총 복사량   : 2 + 4 + 6 + ... + 2n = n(n+1)자  →  O(n²) │
  │ 살아남는 것 : 마지막 하나, 나머지 n-1개는 즉시 쓰레기   │
  └─────────────────────────────────────────────────────────┘
```

**핵심은 복사량이 제곱으로 늘어난다는 것이다.** 반복이 10배 늘면 작업량은 100배가 된다. `n`이 100일 때는 아무도 눈치채지 못하지만, `n`이 100,000이면 프로그램이 멈춘 것처럼 보인다.

게다가 만들어진 임시 문자열들이 전부 가비지가 되어 GC를 압박한다. 길이가 충분히 길어지면 대형 객체 힙(LOH)에 할당되기 시작하고, 그때부터는 더 비싼 컬렉션이 유발된다(63.4절).

| 방법 | 객체 수 | 복사 복잡도 | 언제 쓰는가 |
|---|---|---|---|
| 루프 안 `+=` | O(n) | O(n²) | **쓰지 마라** |
| 한 식 안의 `a + b + c` | 1 | O(n) | 조각 수가 고정일 때 |
| 보간 문자열 `$"..."` | 1(+핸들러) | O(n) | 조각 수가 고정일 때 |
| `string.Concat(배열)` | 1 | O(n) | 조각들이 이미 모여 있을 때 |
| `string.Join(구분자, 시퀀스)` | 1 | O(n) | 구분자로 이을 때 |
| `StringBuilder` | 증가에 따라 몇 개 | 상환 O(n) | **횟수를 모르고 반복할 때** |

`string.Join`은 특히 자주 잊히는 도구다.

```csharp
// 나쁜 코드
string csv = "";
foreach (var name in names)
    csv += name + ",";
csv = csv.TrimEnd(',');       // 마지막 콤마 제거까지 해야 한다

// 좋은 코드
string csv2 = string.Join(",", names);
```

`string.Join`은 전체 길이를 먼저 계산해 딱 맞는 크기의 문자열 하나를 만들고 채운다. 구분자 처리도 알아서 한다.

> **💡 `+=` 하나를 봤다고 놀랄 필요는 없다**
>
> 문자열 연결에 대한 조언이 자주 과장된다. "`+`는 느리다"는 말을 듣고 모든 연결을 `StringBuilder`로 바꾸는 사람이 있는데, 대부분의 경우 코드만 길어지고 아무것도 빨라지지 않는다.
>
> 판단 기준은 하나다. **반복 횟수가 컴파일 타임에 정해져 있는가.**
>
> ```csharp
> // 괜찮다 — 조각 수가 고정. Concat 한 번으로 컴파일된다
> string label = prefix + ": " + value + " (" + unit + ")";
>
> // 괜찮다 — 보간도 마찬가지
> string label = $"{prefix}: {value} ({unit})";
>
> // 문제다 — 횟수를 모른다
> foreach (var row in rows) report += Format(row);
> ```
>
> 세 번째 형태만 고치면 된다. `StringBuilder`의 사용법과 용량 전략은 35.6절, 문자열 할당을 줄이는 더 공격적인 기법은 35.11절에서 다룬다.

### 동등 비교 — `==`가 값을 비교하는 이유

`string`은 값 타입이 아니라 참조 타입이다. 그런데 동등 연산자는 **값 타입의 의미론**을 따른다.

```csharp
string a = "test";
string b = "test";
Console.Write(a == b);        // True
```

6.7절에서 배운 규칙대로라면 이상하다. 참조 타입에 `==`를 쓰면 기본적으로 두 참조가 메모리상 같은 객체를 가리킬 때만 `true`가 나와야 한다. **`String` 타입이 `==`와 `!=` 연산자를 재정의해서, 참조가 아니라 문자열의 값을 비교하도록 만들었기 때문이다.**

연산자 재정의(연산자 오버로딩)는 22장의 주제다. 컴파일 결과 관점에서 보면, `a == b`는 `String` 클래스의 정적 메서드 `op_Equality(string, string)` 호출로 컴파일된다(22.6절). 이 메서드가 길이를 먼저 비교하고, 같으면 문자를 하나씩 비교한다.

C#의 동등 연산자는 기본적으로 문자열 객체에 대해 **대소문자를 구분하고, 문화권을 고려하지 않는, 문자 대 문자** 동등성 검사를 수행한다.

```csharp
string s1 = "Hello!";
Console.WriteLine(s1 == "Hello!");      // True
Console.WriteLine(s1 == "HELLO!");      // False — 대소문자를 구분한다
Console.WriteLine(s1 == "hello!");      // False
```

`string`과 `System.String`의 관계를 생각하면, `Equals` 메서드로도 같은 검사를 할 수 있다. 그리고 모든 문자열 리터럴이 유효한 `System.String` 인스턴스이므로 리터럴에서 직접 멤버를 호출할 수도 있다.

```csharp
Console.WriteLine(s1.Equals(s2));
Console.WriteLine("Yo!".Equals(s2));    // 리터럴에서 직접 호출
```

> **⚠️ `object`로 담는 순간 값 비교가 사라진다**
>
> `==`가 값을 비교하는 것은 **정적 타입이 `string`일 때**뿐이다. 컴파일러가 어느 연산자를 부를지는 컴파일 타임의 타입으로 결정된다.
>
> ```csharp
> object a = new string('x', 3);
> object b = new string('x', 3);
> Console.WriteLine(a == b);                    // False! — object의 == (참조 비교)
> Console.WriteLine(a.Equals(b));               // True   — String.Equals가 가상 호출됨
> Console.WriteLine((string)a == (string)b);    // True   — 다시 string의 ==
> ```
>
> 첫 줄이 `false`인 이유는 `object`에는 `String.op_Equality`가 없어서 `object`의 참조 비교가 쓰이기 때문이다. `new string(...)`으로 만들었으므로 두 객체는 서로 다른 인스턴스다(리터럴이었다면 인터닝 때문에 우연히 `true`가 나올 수도 있어서 더 헷갈린다 — 35.5절).
>
> 이 함정은 제네릭 코드에서 특히 잘 나온다. `T`가 `string`이어도 `where T : class` 제약 아래의 `t1 == t2`는 참조 비교다. 제네릭에서 값 동등성이 필요하면 `EqualityComparer<T>.Default.Equals(t1, t2)`를 써라(25.7절).

> **📌 참조가 같은지 정말 알고 싶다면**
>
> 두 참조가 같은 객체를 가리키는지 확인하려면 `object.ReferenceEquals(a, b)`를 쓴다. 이 메서드는 어떤 연산자 재정의에도 영향받지 않는다.
>
> 실무에서 문자열의 참조 동등성을 검사할 이유는 거의 없다. 인터닝 때문에 결과가 직관과 어긋나고(35.5절), 그 결과에 코드가 의존하면 컴파일러나 런타임 버전에 따라 깨진다. `String.Copy` 같은 메서드가 존재하는 이유도 "내용은 같지만 참조는 다른" 문자열이 필요한 아주 특수한 상황 때문이다.

### 순서 비교 — `<`와 `>`는 없다

동등 비교는 `==`나 `Equals`로 하지만, **순서 비교에는 `CompareTo` 메서드를 써야 한다. `<`와 `>` 연산자는 지원되지 않는다.**

```csharp
string a = "apple", b = "banana";
// if (a < b) { }              // 컴파일 오류
if (string.Compare(a, b, StringComparison.Ordinal) < 0) { }
if (a.CompareTo(b) < 0) { }    // 동작하지만 아래 경고를 읽어라
```

`String.Compare`와 `CompareTo`는 음수(앞), 0(같음), 양수(뒤)를 돌려준다. 정확한 절댓값에는 의미가 없으므로 `== -1` 같은 비교를 하면 안 된다.

> **⚠️ `Equals`와 `CompareTo`의 기본 동작이 다르다**
>
> 이것이 문자열 비교에서 가장 위험한 비대칭이다.
>
> - `Equals`와 `==`는 기본적으로 **서수(ordinal)** 비교를 한다.
> - `CompareTo`는 기본적으로 **문화권 인식(culture-sensitive)** 비교를 한다.
>
> 즉 `a.Equals(b)`가 `false`인데 `a.CompareTo(b)`가 `0`일 수 있다. 정렬한 뒤 이진 탐색으로 찾는 코드에서 이 불일치가 조용한 버그를 만든다.
>
> 그래서 권고는 이렇다. **메서드 이름만 보고 어떤 비교가 일어날지 알 수 없는 메서드를 쓰지 마라.** 구체적으로 `CompareTo`(`IComparable`이 요구하는 것), `CompareOrdinal`, 그리고 `==`/`!=` 연산자를 피하고, `StringComparison`을 명시적으로 받는 오버로드를 쓰라는 것이다. 비교 방식을 코드에 적어 두면 읽기도 쉽고 유지보수도 쉽다.
>
> 현실적으로 `==`를 완전히 버리기는 어렵다. 짧은 리터럴 비교에서 `s == "yes"` 대신 `string.Equals(s, "yes", StringComparison.Ordinal)`을 쓰는 것은 과할 수 있다. **다만 그 코드가 서수 비교라는 것을 알고 쓰는 것과 모르고 쓰는 것은 다르다.**

### `StringComparison` — 비교 규칙을 명시한다

동등성을 판정하거나 정렬을 위해 문자열을 비교할 때는 `StringComparison`을 받는 오버로드를 부르는 것이 강력히 권장된다. `String` 클래스가 제공하는 그 오버로드들은 다음과 같다.

```csharp
bool Equals(string value, StringComparison comparisonType);
static bool Equals(string a, string b, StringComparison comparisonType);
static int  Compare(string strA, string strB, StringComparison comparisonType);
static int  Compare(string strA, string strB, bool ignoreCase, CultureInfo culture);
static int  Compare(string strA, string strB, CultureInfo culture, CompareOptions options);
bool StartsWith(string value, StringComparison comparisonType);
bool StartsWith(string value, bool ignoreCase, CultureInfo culture);
bool EndsWith(string value, StringComparison comparisonType);
bool EndsWith(string value, bool ignoreCase, CultureInfo culture);
```

`StringComparison` 열거형은 여섯 개의 값을 갖는다.

| 값 | 하는 일 |
|---|---|
| `CurrentCulture` | 현재 문화권의 문화권 인식 정렬 규칙으로 비교 |
| `CurrentCultureIgnoreCase` | 위와 같되 대소문자 무시 |
| `InvariantCulture` | 불변 문화권의 문화권 인식 정렬 규칙으로 비교 |
| `InvariantCultureIgnoreCase` | 위와 같되 대소문자 무시 |
| `Ordinal` | 서수(2진) 정렬 규칙으로 비교 |
| `OrdinalIgnoreCase` | 서수 정렬 규칙으로 비교하되 대소문자 무시 |

효과를 직접 보자.

```csharp
string s1 = "Hello!";
string s2 = "HELLO!";

Console.WriteLine(s1.Equals(s2));                                          // False
Console.WriteLine(s1.Equals(s2, StringComparison.OrdinalIgnoreCase));      // True
Console.WriteLine(s1.Equals(s2, StringComparison.InvariantCultureIgnoreCase)); // True

Console.WriteLine(s1.IndexOf("E"));                                        // 문화권 인식
Console.WriteLine(s1.IndexOf("E", StringComparison.OrdinalIgnoreCase));    // 1
```

### 어느 것을 언제 쓰는가

많은 프로그램이 경로 이름, 파일 이름, URL, 레지스트리 키와 값, 환경 변수, 리플렉션, XML 태그, XML 특성 같은 **내부 프로그래밍 목적**으로 문자열을 쓴다. 이런 문자열은 사용자에게 보이지 않고 프로그램 안에서만 쓰인다.

**프로그래밍용 문자열을 비교할 때는 언제나 `StringComparison.Ordinal` 또는 `StringComparison.OrdinalIgnoreCase`를 써라.** 문화권 정보를 고려하지 않으므로 언어학적 영향을 전혀 받지 않는, 가장 빠른 비교 방식이다.

반대로 **언어학적으로 올바르게 비교하고 싶을 때는**(보통 최종 사용자에게 보여주기 위해) `StringComparison.CurrentCulture`나 `StringComparison.CurrentCultureIgnoreCase`를 쓴다.

> **⚠️ `InvariantCulture`는 대부분의 경우 쓰지 마라**
>
> `StringComparison.InvariantCulture`와 `InvariantCultureIgnoreCase`는 어중간한 자리에 있다.
>
> 이 값들은 비교를 언어학적으로 올바르게 만들지만, **프로그래밍용 문자열을 비교하는 데 쓰면 서수 비교보다 느리다.** 그리고 불변 문화권은 어떤 문화권도 아니므로, **최종 사용자에게 보여줄 문자열을 다룰 때는 잘못된 선택이다.**
>
> 즉 두 용도 모두에서 더 나은 선택이 따로 있다. 프로그래밍용이면 `Ordinal`, 사용자용이면 `CurrentCulture`다.
>
> 예외는 **문화권과 무관하게 재현 가능한 언어학적 순서**가 필요한 아주 드문 경우다. 서로 다른 로캘의 서버들이 같은 정렬 결과를 내야 하는 상황 정도다. 이때도 대개는 `Ordinal`이 더 나은 답이다.

정리하면 이렇다.

| 상황 | 써야 할 것 |
|---|---|
| 파일 경로, URL, 키, 태그 이름 비교 | `Ordinal` |
| 위와 같되 대소문자 무시 | `OrdinalIgnoreCase` |
| 사용자에게 보여줄 목록 정렬 | `CurrentCulture` |
| 사용자 입력 검색(대소문자 무시) | `CurrentCultureIgnoreCase` |
| 그 밖 | 대개 `Ordinal` |

> **⚠️ 정렬할 때는 반드시 대소문자를 구분하라**
>
> 정렬을 수행할 때는 언제나 대소문자를 구분하는 비교를 써야 한다. 대소문자만 다른 두 문자열을 같다고 보면, **정렬할 때마다 그 둘의 순서가 달라질 수 있다.** 사용자는 같은 목록을 두 번 정렬했는데 결과가 다른 것을 보게 된다.
>
> 대소문자 무시 비교는 "찾기"에는 맞고 "줄 세우기"에는 맞지 않는다.

### `ToUpper()` 비교라는 반패턴

대소문자를 무시하고 비교하고 싶을 때 흔히 쓰는 방법이 있다. 양쪽을 전부 대문자(또는 소문자)로 바꾼 뒤 비교하는 것이다.

```csharp
if (firstString.ToUpper() == secondString.ToUpper())
{
    // ...
}
```

이 코드는 각 문자열의 **사본을 두 개 만든다.** 대부분의 경우 문제가 되지 않겠지만, 문자열이 상당히 크면 성능 저하가 생길 수 있고, 문화권에 따라서는 **아예 틀린 결과를 낼 수도 있다**(8.1절의 터키어 I 문제).

훨씬 나은 방법은 `StringComparison` 값을 받는 오버로드를 써서 비교 방식을 정확히 통제하는 것이다.

```csharp
if (string.Equals(firstString, secondString, StringComparison.OrdinalIgnoreCase))
{
    // ...
}
```

사본이 없고, 문화권 함정이 없고, 의도가 코드에 적혀 있다.

> **⚠️ 메서드마다 기본 비교 방식이 다르다**
>
> `StringComparison`을 넘기지 않았을 때 어떤 비교가 일어나는지는 **메서드마다 다르다.** 이름으로 유추할 수 없다.
>
> | 메서드 | 인자 없는 기본 동작 |
> |---|---|
> | `==`, `!=`, `Equals` | 서수(ordinal) |
> | `Contains(string)` | 서수 |
> | `Replace(string, string)` | 서수 |
> | `IndexOf(string)`, `LastIndexOf(string)` | **문화권 인식** |
> | `StartsWith(string)`, `EndsWith(string)` | **문화권 인식** |
> | `CompareTo(string)` | **문화권 인식** |
> | `IndexOf(char)` | 서수 |
>
> `Contains("abc")`는 서수인데 `IndexOf("abc")`는 문화권 인식이다. 두 줄을 나란히 놓고 봐도 이상하다는 느낌이 들지 않는다는 것이 문제다.
>
> ```csharp
> // 이 두 줄은 같은 뜻이 아니다
> bool found1 = text.Contains("abc");           // 서수
> bool found2 = text.IndexOf("abc") >= 0;       // 문화권 인식
> ```
>
> 코드 분석기(analyzer)가 이 자리에 경고를 낸다. 경고를 끄지 말고 `StringComparison`을 명시하라.

> **⚠️ .NET 5부터 문화권 인식 비교의 결과가 달라졌다**
>
> .NET 5부터는 모든 플랫폼에서 국제화 백엔드로 **ICU**(International Components for Unicode) 라이브러리를 기본으로 쓴다. 그 이전 .NET Framework와 .NET Core는 윈도우에서 운영체제의 NLS를 썼다.
>
> 그래서 **문화권 인식 비교와 검색의 결과가 .NET 5 이전과 달라질 수 있다.** 특히 ICU의 정렬 규칙에서는 일부 문자(제로 폭 문자, 일부 제어 문자 등)가 비교 시 무시되는(ignorable) 것으로 취급된다. 그 결과 문화권 인식 `IndexOf`가 "빈 문자열을 찾은 것 같은" 위치를 돌려주거나, 없을 것 같은 곳에서 일치를 보고하는 일이 생긴다.
>
> 이 변화에 영향을 받지 않는 유일한 방법은 **프로그래밍용 비교에 `Ordinal`을 명시하는 것**이다. 서수 비교는 어떤 백엔드에서도 같은 결과를 낸다. 국제화 백엔드와 그 설정, 그리고 `AppContext` 스위치로 옛 동작을 되살리는 방법은 35.4절에서 다룬다.

### 문화권은 스레드에 붙어 있다

문화권 인식 비교가 무엇을 쓰는지 알아 두면 함정을 이해하기 쉽다.

CLR에서는 **모든 스레드가 두 개의 문화권 프로퍼티를 갖는다.** 각각 `CultureInfo` 객체를 가리킨다.

- **`CurrentUICulture`** — 최종 사용자에게 보여줄 리소스를 가져오는 데 쓴다. 레이블·버튼 같은 UI 요소를 표시할 언어를 결정한다.
- **`CurrentCulture`** — `CurrentUICulture`가 담당하지 않는 모든 것에 쓴다. 숫자와 날짜 서식, 문자열 대소문자 변환, **문자열 비교**가 여기 포함된다.

`CultureInfo`는 RFC 1766이 기술하는 언어/국가 쌍을 나타낸다. `"en-US"`는 미국에서 쓰는 영어, `"en-AU"`는 호주 영어, `"de-DE"`는 독일에서 쓰는 독일어다.

두 프로퍼티는 스레드마다 독립적이고, 새 스레드가 만들어질 때의 기본값은 `CultureInfo`의 정적 `DefaultThreadCurrentCulture`/`DefaultThreadCurrentUICulture` 프로퍼티로 바꿀 수 있다.

> **⚠️ 문화권 의존 코드는 스레드마다 다르게 동작한다**
>
> 문화권이 스레드에 붙어 있다는 사실이 실무에서 어떤 문제를 만드는지 보자.
>
> 1. **스레드 풀 스레드에서 결과가 달라진다.** `Task.Run` 안에서 문화권 인식 비교를 하면 그 스레드의 `CurrentCulture`가 호출자와 다를 수 있다. .NET Framework에서 특히 그렇다(.NET Framework 4.6부터는 `CurrentCulture`가 비동기 흐름을 따라 전파된다).
> 2. **서버 애플리케이션에서 요청마다 문화권이 다르다.** ASP.NET의 요청 지역화 미들웨어는 요청의 `Accept-Language` 헤더에 맞춰 스레드 문화권을 설정한다. 즉 **같은 코드가 사용자마다 다르게 동작한다.**
> 3. **테스트가 개발자 PC 로캘에 의존한다.** 한국어 윈도우에서 통과하는 테스트가 CI의 영어 리눅스 컨테이너에서 실패한다.
>
> 예방책은 하나다. **내부 로직에는 문화권 인식 비교를 쓰지 마라.** `Ordinal`을 명시하면 이 문제 전체가 사라진다. 문화권은 사용자에게 보여주는 마지막 단계에서만 개입해야 한다. 국제화 체크리스트는 38.10절, 불변 문화권을 써야 할 자리는 38.11절에서 다룬다.

### 이 절에서 멈추는 곳

문자열 비교는 여기서 끊는다. 이 장에서 세운 것은 세 가지다.

1. **`==`는 값을 비교한다** — 연산자 재정의 덕분이며, `object`로 담으면 그 성질이 사라진다.
2. **`<`, `>`는 없다** — 순서는 `Compare`/`CompareTo`로 한다.
3. **비교 방식을 명시하라** — 프로그래밍용은 `Ordinal`, 사용자용은 `CurrentCulture`.

비교 알고리즘이 실제로 무엇을 하는지, 정렬 키(sort key)와 대조(collation)가 무엇인지, `CompareOptions`의 플래그들이 각각 어떤 유니코드 규칙을 켜고 끄는지, 그리고 성능 차이가 얼마나 나는지는 35.4절의 몫이다. 동등성 프로토콜 전반 — `Equals`와 `GetHashCode`의 계약, `IEquatable<T>`, `IComparer<T>` — 은 25장에서 다룬다.

## 이 장의 요약

- **`char`는 문자가 아니라 UTF-16 코드 단위 하나다.** 16비트를 넘는 문자는 서로게이트 페어 두 개로 표현되므로 `char`에 담을 수 없고, `string.Length`는 글자 수가 아니라 코드 단위 수다. `Length`를 "글자 수"라고 부르는 순간 버그가 시작된다. 정확한 처리는 `Rune`과 `StringInfo`의 몫이다(35.2절).

- **유니코드 이스케이프 셋 중 `\x`만 자릿수가 가변이다.** `"\x41BC"`는 `'A'` + `"BC"`가 아니라 U+41BC 한 글자다. 컴파일 오류도 경고도 없이 조용히 다른 문자열이 되고, 주변 문자를 고치는 것만으로 동작이 바뀐다. **언제나 `\u`를 써라.**

- **`char`에서 숫자로는 `ushort`를 담을 수 있는 타입이면 암시 변환되고, 반대 방향은 언제나 캐스트가 필요하다.** 변환 기법은 캐스트 → `Convert` → `IConvertible` 순으로 느려지고, 마지막 것은 박싱까지 한다. 실무에서는 캐스트만 쓴다.

- **대소문자 변환은 문화권에 의존한다.** 터키어에서 `'i'`의 대문자는 다른 문자다. 프로그램 내부 정규화에는 반드시 `ToUpperInvariant`를, 사용자에게 보여줄 텍스트에만 `ToUpper`를 쓴다.

- **`string`은 참조 타입이지만 불변이다.** 모든 "수정" 메서드는 새 객체를 돌려주고, 대입도 새 객체를 만든다. IL에 `ldstr`이 두 번 나오는 것이 그 증거다. 불변성 덕분에 별칭 문제도, 스레드 동기화 문제도, 딕셔너리 키로 쓸 때의 문제도 없다. 대가는 힙에 쌓이는 임시 객체다.

- **`null`과 빈 문자열은 다르다.** `null`에 인스턴스 메서드를 부르면 `NullReferenceException`이지만 `==` 비교와 문자열 연결은 안전하다 — 그래서 `null`이 조용히 빈 문자열처럼 보이는 자리가 생긴다. 사용자 입력 검증은 `IsNullOrWhiteSpace`, 내부 데이터는 `IsNullOrEmpty`다.

- **리터럴은 네 종류이고 서로 조합된다.** 일반은 이스케이프를 해석하고, 축자(`@`)는 해석하지 않으며, 보간(`$`)은 식을 담고, 원시(`"""`)는 아무것도 이스케이프하지 않는다. **원시 문자열의 들여쓰기는 닫는 따옴표의 위치가 결정하며**, 그보다 덜 들여쓴 줄이 있으면 컴파일 오류다.

- **보간 문자열은 `{식,정렬:서식}` 문법을 쓰고 `{{`로 중괄호를 이스케이프한다.** 콜론이 서식 구분자이므로 삼항 연산자는 괄호로 감싸야 한다. C# 9까지는 `String.Format` 호출로 컴파일됐고 박싱과 런타임 파싱이 일어났다. ※C# 10부터는 `DefaultInterpolatedStringHandler`로 바뀌었다(35.7절).

- **`u8` 리터럴의 타입은 `string`이 아니라 `ReadOnlySpan<byte>`다.** ※C# 11. 바이트가 어셈블리에 박히므로 할당이 없고, `Length`는 바이트 수이며, `ref struct` 제약을 그대로 물려받는다. 핫 패스의 UTF-8 바이트 비교에만 쓴다.

- **`+`는 `String.Concat`이고, 리터럴끼리는 컴파일 타임에 접힌다.** 한 식 안의 연결은 `Concat` 한 번이므로 걱정할 것이 없다. **문제는 루프 안의 `+=`다** — 객체가 n개 생기고 복사량이 O(n²)로 늘어난다. 횟수를 모르고 반복한다면 `string.Join`이나 `StringBuilder`다(35.6절).

- **`==`가 값을 비교하는 것은 `String`이 연산자를 재정의했기 때문이다.** `object`로 담으면 참조 비교로 되돌아간다. 순서 비교에는 `<`/`>`가 없고, `Equals`는 서수인데 `CompareTo`는 문화권 인식이라는 비대칭이 있다.

- **비교 방식을 명시하라.** 프로그래밍용 문자열은 `Ordinal`/`OrdinalIgnoreCase`, 사용자용은 `CurrentCulture` 계열, `InvariantCulture`는 대부분 잘못된 선택이다. 메서드마다 기본값이 달라서 `Contains`는 서수인데 `IndexOf`는 문화권 인식이다. .NET 5의 ICU 전환으로 문화권 인식 결과가 달라진 것도 `Ordinal`을 명시하면 무관해진다.

## 연습 문제

1. **`\x`의 함정 재현하기.** `Console.WriteLine("\x41BC".Length)`와 `Console.WriteLine("\u0041BC".Length)`를 실행해 길이를 비교하라. 이어서 `"\x41Good"`과 `"\x41Bad"`를 각각 출력하고 첫 글자가 왜 달라지는지 설명하라. 마지막으로 두 문자열의 각 문자를 `((int)c).ToString("X4")`로 출력해 실제 코드 값을 확인하라.

2. **`Length`가 글자 수가 아님을 확인하기.** `"\U0001F600"`, `"a\u0304\u0308bc\u0327"`, `"한글"` 세 문자열에 대해 `Length`를 출력하고, 각각을 `foreach (char c in s)`로 순회하며 `((int)c).ToString("X4")`를 찍어라. 눈에 보이는 글자 수와 `Length`가 일치하는 것은 어느 것인가.

3. **불변성과 별칭 확인하기.** `string a = "hello"; string b = a; a = a.ToUpper();`를 실행한 뒤 `a`와 `b`를 출력하라. 이어서 `var list1 = new List<int>{1,2}; var list2 = list1; list1.Add(3);`로 같은 실험을 하고 결과가 왜 다른지 설명하라.

4. **원시 문자열의 들여쓰기 규칙 실험하기.** 여러 줄 원시 문자열을 만들고 닫는 `"""`의 들여쓰기를 한 칸씩 바꿔 가며 결과 문자열을 `Console.WriteLine(s.Replace(" ", "."))`로 출력하라. 내용 줄보다 닫는 따옴표를 더 깊이 들여쓰면 어떤 컴파일 오류가 나는지 확인하라.

5. **JSON 템플릿을 세 가지 리터럴로 써 보기.** `{"name":"Joe","path":"C:\\tmp"}` 라는 JSON을 (a) 일반 문자열, (b) 축자 문자열, (c) 원시 문자열로 각각 작성하고 세 문자열이 `==`로 같은지 확인하라. 이어서 `name` 부분을 변수로 바꿔 `$$"""..."""` 형태로 다시 써라.

6. **루프 연결의 제곱 비용 측정하기.** `Stopwatch`로 `s += "ab"`를 1,000번 / 10,000번 / 50,000번 반복하는 시간을 각각 재라. 반복 수가 5배 늘 때 시간이 몇 배 느는지 확인하고, 같은 작업을 `StringBuilder`와 `string.Join`으로 바꿔 다시 측정하라.

7. **비교 방식의 차이 관찰하기.** `s1 = "Hello!"`, `s2 = "HELLO!"`에 대해 `s1.Equals(s2)`, `s1.Equals(s2, StringComparison.OrdinalIgnoreCase)`, `s1.IndexOf("E")`, `s1.IndexOf("E", StringComparison.OrdinalIgnoreCase)`를 모두 출력해 표로 정리하라. 이어서 `object o1 = new string('x',3), o2 = new string('x',3);`로 `o1 == o2`와 `o1.Equals(o2)`, `(string)o1 == (string)o2`의 결과가 갈리는 것을 확인하라.
