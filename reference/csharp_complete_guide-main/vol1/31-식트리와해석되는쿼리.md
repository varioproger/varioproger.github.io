## 31.1 델리게이트 vs 식 트리

### 같은 문장, 두 가지 결과

다음 두 줄은 육안으로는 대입 대상만 다르다.

```csharp
using System;
using System.Linq.Expressions;

Func<string, bool> shortName1 = s => s.Length < 5;
Expression<Func<string, bool>> shortName2 = s => s.Length < 5;
```

그런데 결과물은 종류가 다르다.

- `shortName1`은 **실행 가능한 코드**다. 컴파일러가 메서드 하나를 만들고, 그 메서드를 가리키는 델리게이트 인스턴스를 만든다. 호출하면 IL이 실행된다.
- `shortName2`는 **데이터**다. `s`라는 매개변수 노드, `s.Length`라는 멤버 접근 노드, `5`라는 상수 노드, "왼쪽이 오른쪽보다 작다"는 비교 노드로 이루어진 객체 그래프다. 호출할 수 없다. 대신 **읽을 수 있다.**

```csharp
Console.WriteLine (shortName1 ("kangaroo"));    // False
Console.WriteLine (shortName2.Body.NodeType);   // LessThan
Console.WriteLine (((BinaryExpression) shortName2.Body).Right);   // 5
```

`shortName2`를 실행하려면 한 단계가 더 필요하다.

```csharp
Func<string, bool> runnable = shortName2.Compile();
Console.WriteLine (runnable ("kangaroo"));   // False
Console.WriteLine (runnable ("dog"));        // True
```

이 대비가 이 장 전체의 축이다. 표로 정리하면 다음과 같다.

| 관점 | `Func<string,bool>` | `Expression<Func<string,bool>>` |
|---|---|---|
| 정체 | 메서드 포인터 + 대상 객체 | `System.Linq.Expressions` 타입들로 만든 객체 트리 |
| 컴파일 시점 산출물 | 생성 메서드 1개 + 델리게이트 생성 코드 | 트리를 **조립하는 코드** |
| 실행 | `delegate(...)` 직접 호출 | `Compile()` 후 호출, 또는 제3자가 번역해 실행 |
| 내부를 들여다볼 수 있는가 | 불가 (본문 IL은 리플렉션으로도 의미 있게 못 읽는다) | 가능 — 그것이 존재 이유다 |
| 바인딩되는 연산자 클래스 | `Enumerable` | `Queryable` |
| 실행 위치 | 항상 로컬(클라이언트) | 공급자가 정한다 — SQL 서버, 웹 API, 로컬 |
| 역방향 변환 | — | **불가.** 델리게이트를 식 트리로 되돌리는 API는 없다 |

> **📌 "식 트리"라는 이름**
>
> 식 트리(expression tree)는 **미니어처 코드 DOM**이다. XML DOM이 문서를 요소 노드의 트리로 표현하듯, 식 트리는 C# 식 하나를 노드의 트리로 표현한다. 모든 노드 타입이 `System.Linq.Expressions` 네임스페이스에 있고, 최상위 기반 클래스는 (제네릭이 아닌) `Expression`이다.
>
> LINQ 네임스페이스 안에 있지만 LINQ 전용 기술은 아니다. 리플렉션 호출을 대체하는 고속 접근자 생성(57.13절), 규칙 엔진, 시리얼라이저, 매퍼 등이 모두 식 트리를 쓴다.

### 왜 두 세계가 필요한가 — 연산자 시그니처

`Where` 연산자를 `Enumerable`과 `Queryable`에서 각각 꺼내 나란히 놓으면 답이 나온다.

```csharp
// System.Linq.Enumerable
public static IEnumerable<TSource> Where<TSource> (
    this IEnumerable<TSource> source,
    Func<TSource, bool> predicate);

// System.Linq.Queryable
public static IQueryable<TSource> Where<TSource> (
    this IQueryable<TSource> source,
    Expression<Func<TSource, bool>> predicate);
```

`Enumerable.Where`는 술어를 **호출할** 생각이다. 그래서 델리게이트를 받는다. `Queryable.Where`는 술어를 **읽을** 생각이다. 그래서 식 트리를 받는다. `Enumerable.Where`가 받은 델리게이트로 할 수 있는 일은 호출뿐이므로, 이 술어는 반드시 이 프로세스의 CPU에서 실행된다. 데이터가 SQL Server에 있다면 모든 행을 클라이언트로 끌어와야 한다는 뜻이다.

반대로 `Queryable.Where`는 술어의 **내용**을 안다. "`Name` 프로퍼티에 `Contains("a")`를 호출한 결과가 참" — 이 구조를 읽어서 `WHERE CHARINDEX(N'a', [c].[Name]) > 0`이라는 문자열로 옮길 수 있다. 필터가 데이터베이스에서 실행되고, 네트워크를 건너오는 것은 결과 행뿐이다.

> **💡 식 트리는 "코드를 값으로 다루는" C#의 유일한 1급 수단이다**
>
> C#에는 매크로도, `eval`도, 컴파일 타임 리플렉션도 없다. 코드를 데이터로 넘겨 제3자가 해석하게 만드는 방법은 사실상 식 트리 하나뿐이다. `Reflection.Emit`(58장)은 반대 방향 — 데이터에서 코드를 만드는 쪽 — 이고, 소스 생성기(57.15절)는 컴파일 타임에만 작동한다. "런타임에 사용자 의도를 코드로 받아 다른 실행 엔진에 넘긴다"는 요구가 있으면 식 트리를 먼저 떠올려라.

### 쿼리 안에 묻히면 구분이 사라진다

쿼리 표현식 **안에** 직접 쓴 람다는 두 세계에서 겉모습이 완전히 같다.

```csharp
IEnumerable<Product> q1 = localProducts.Where (p => !p.Discontinued);
IQueryable<Product>  q2 = sqlProducts  .Where (p => !p.Discontinued);
```

컴파일러가 `source`의 정적 타입을 보고 어느 오버로드에 바인딩할지 결정하고, 그 결정이 곧 람다의 운명을 정한다. `sqlProducts`가 `IQueryable<Product>`이면 `Queryable.Where`가 더 구체적인 매치이므로 그쪽이 선택되고, 람다는 식 트리로 컴파일된다. 자세한 오버로드 해석 규칙은 31.4절에서 판다.

그러나 람다를 **중간 변수에 담는 순간** 구분은 명시적이 된다.

```csharp
Func<Product, bool> predicate1 = p => !p.Discontinued;
IEnumerable<Product> q1 = localProducts.Where (predicate1);

Expression<Func<Product, bool>> predicate2 = p => !p.Discontinued;
IQueryable<Product> q2 = sqlProducts.Where (predicate2);
```

`predicate1`과 `predicate2`는 **교환 가능하지 않다.** `sqlProducts.Where(predicate1)`은 컴파일은 되지만(`IQueryable<T>`는 `IEnumerable<T>`이므로 `Enumerable.Where`가 적용된다) 조용히 로컬 쿼리로 떨어진다. 이것이 이 장에서 가장 조용하게 사고를 내는 지점이다.

> **⚠️ `var`로 술어를 선언하면 안 되는 이유**
>
> ```csharp
> var predicate = (Product p) => !p.Discontinued;   // ※C# 10 자연 타입
> ```
>
> ※C# 10부터 람다에 자연 타입(natural type)이 생겨 `var`에 대입할 수 있다. 그러나 추론되는 자연 타입은 **항상 델리게이트**(`Func<Product,bool>`)이지 `Expression<>`이 아니다. 이 변수를 EF Core 쿼리에 넘기면 컴파일 오류 없이 전체 테이블 스캔이 된다. 술어를 변수로 뽑을 때는 타입을 명시하라. 이것은 79.1절의 "`var`를 쓰지 말 자리" 목록에 들어가는 대표 사례다.

### 컴파일 결과 — 컴파일러가 실제로 방출하는 것

두 줄이 각각 무엇으로 바뀌는지 보자. 먼저 델리게이트 쪽이다. 캡처가 없는 람다이므로 컴파일러는 `<>c`라는 **캐시 클래스**를 만들고, 델리게이트 인스턴스를 정적 필드에 담아 재사용한다(26.10절).

```il
// Func<string,bool> f = s => s.Length < 5;
IL_0000:  ldsfld     class [System.Runtime]System.Func`2<string,bool> Program/'<>c'::'<>9__0_0'
IL_0005:  dup
IL_0006:  brtrue.s   IL_001f
IL_0008:  pop
IL_0009:  ldsfld     class Program/'<>c' Program/'<>c'::'<>9'
IL_000e:  ldftn      instance bool Program/'<>c'::'<Main>b__0_0'(string)
IL_0014:  newobj     instance void class [System.Runtime]System.Func`2<string,bool>::.ctor(object, native int)
IL_0019:  dup
IL_001a:  stsfld     class [System.Runtime]System.Func`2<string,bool> Program/'<>c'::'<>9__0_0'
IL_001f:  stloc.0
```

핵심은 `brtrue.s`다. **두 번째 실행부터는 아무것도 할당하지 않는다.** 그리고 람다 본문은 `<Main>b__0_0`이라는 실제 메서드로 컴파일되어 JIT의 최적화를 그대로 받는다.

식 트리 쪽은 완전히 다르다. 컴파일러는 본문을 메서드로 만들지 않고, **트리를 조립하는 코드**를 방출한다. 방출되는 IL을 C#으로 되옮기면 대략 이렇다.

```csharp
// Expression<Func<string,bool>> f = s => s.Length < 5;
// 컴파일러가 방출하는 것과 의미상 동등한 코드
ParameterExpression s = Expression.Parameter (typeof (string), "s");
Expression body = Expression.LessThan (
    Expression.Property (s, typeof (string).GetProperty ("Length")),
    Expression.Constant (5, typeof (int)));
Expression<Func<string, bool>> f =
    Expression.Lambda<Func<string, bool>> (body, new[] { s });
```

IL 수준에서는 `Expression`의 정적 팩토리 메서드 호출이 줄줄이 늘어선다(중간 생략).

```il
IL_0000:  ldtoken    [System.Runtime]System.String
IL_0005:  call       class [System.Runtime]System.Type [System.Runtime]System.Type::GetTypeFromHandle(valuetype [System.Runtime]System.RuntimeTypeHandle)
IL_000a:  ldstr      "s"
IL_000f:  call       class [System.Linq.Expressions]System.Linq.Expressions.ParameterExpression [System.Linq.Expressions]System.Linq.Expressions.Expression::Parameter(class [System.Runtime]System.Type, string)
IL_0014:  stloc.0
           // ... Expression::Property, Expression::Constant, Expression::LessThan 호출 ...
IL_00xx:  call       class [System.Linq.Expressions]System.Linq.Expressions.Expression`1<!!0> [System.Linq.Expressions]System.Linq.Expressions.Expression::Lambda<class [System.Runtime]System.Func`2<string,bool>>(class [System.Linq.Expressions]System.Linq.Expressions.Expression, class [System.Linq.Expressions]System.Linq.Expressions.ParameterExpression[])
```

여기서 세 가지가 즉시 따라 나온다.

1. **캐시가 없다.** 델리게이트와 달리 식 트리에는 `<>9__0_0` 같은 캐시 필드가 없다. 그 줄을 실행할 때마다 노드 객체가 새로 할당된다.
2. **리플렉션 조회가 섞인다.** `typeof(string).GetProperty("Length")`에 해당하는 `ldtoken`/`GetTypeFromHandle`/`GetMethodFromHandle` 호출이 들어간다. 메타데이터 토큰에서 시작하므로 문자열 기반 조회보다는 싸지만, 공짜는 아니다.
3. **값 타입 상수는 박싱된다.** `Expression.Constant(5, typeof(int))`의 첫 인자는 `object`이므로 `5`가 박싱된다(15장).

### 런타임 동작 — `Compile()`이 하는 일

`Expression<TDelegate>.Compile()`은 트리를 실행 가능한 델리게이트로 바꾼다. .NET에서 이 작업은 두 갈래다.

| 경로 | 언제 | 특징 |
|---|---|---|
| 동적 메서드 컴파일 | JIT을 쓸 수 있는 일반 런타임 | 트리에서 IL을 방출하고 JIT이 네이티브 코드로 만든다. 호출당 비용은 일반 메서드 수준 |
| 인터프리터 | `Compile(preferInterpretation: true)`, 또는 동적 코드 생성이 불가능한 플랫폼 | 트리를 그대로 걸어가며 해석 실행. 컴파일 비용은 거의 0, 호출 비용은 크다 |

```csharp
Expression<Func<int, int>> square = x => x * x;

Func<int, int> fast = square.Compile();                        // IL 방출 경로
Func<int, int> slow = square.Compile (preferInterpretation: true);  // 인터프리터 경로
```

> **⚠️ `Compile()`은 싸지 않다 — 루프 안에서 부르지 마라**
>
> `Compile()` 한 번은 IL 방출과 JIT을 유발한다. 델리게이트를 직접 호출하는 것과는 자릿수가 다른 비용이다. 식 트리를 반복적으로 쓸 계획이라면 **컴파일한 델리게이트를 캐시하라.** 흔한 사고는 이렇게 생긴다.
>
> ```csharp
> foreach (var row in rows)
>     if (predicateExpression.Compile() (row))   // 행마다 컴파일 — 파국
>         ...
> ```
>
> 올바른 형태는 루프 밖에서 `var predicate = predicateExpression.Compile();` 한 번이다.

> **⚠️ AOT·트리밍 환경에서 `Compile()`은 인터프리터로 떨어진다**
>
> Native AOT처럼 런타임 IL 생성이 금지된 환경에서는 `Compile()`이 동적 메서드를 만들 수 없다. 런타임 구성에 따라 자동으로 인터프리터로 대체되거나, 아예 예외가 난다. 식 트리를 성능 경로의 핵심으로 삼은 라이브러리를 AOT로 게시하면 여기서 성능이 무너진다. 대안(소스 생성기)은 57.15절과 58.11절에서 비교한다.

### 재사용 가능한 술어를 반환하는 패턴

식 트리는 값이므로 메서드가 돌려줄 수 있다. 이 성질이 "같은 규칙을 로컬과 원격 양쪽에서 쓰기"를 가능하게 한다.

```csharp
using System;
using System.Linq.Expressions;

public class Product
{
    public int ID { get; set; }
    public string Description { get; set; } = "";
    public bool Discontinued { get; set; }
    public DateTime LastSale { get; set; }

    // 단종되지 않았고 최근 30일 안에 팔린 제품
    public static Expression<Func<Product, bool>> IsSelling()
        => p => !p.Discontinued && p.LastSale > DateTime.Now.AddDays (-30);
}
```

이 하나의 규칙을 양쪽에 쓴다.

```csharp
void Test()
{
    using var dbContext = new NutshellContext();
    Product[] localProducts = dbContext.Products.ToArray();

    IQueryable<Product> sqlQuery =
        dbContext.Products.Where (Product.IsSelling());          // SQL로 번역

    IEnumerable<Product> localQuery =
        localProducts.Where (Product.IsSelling().Compile());     // 로컬 실행
}
```

`Expression<T>`를 반환하면 양쪽 모두를 만족시킬 수 있지만, `Func<T>`를 반환하면 원격 쪽을 영원히 포기하는 셈이다. **.NET에는 델리게이트를 식 트리로 되돌리는 API가 없기 때문이다.** 이 비대칭 하나가 "규칙을 공유하는 라이브러리는 식 트리로 노출하라"는 설계 지침의 근거다(31.9절).

> **📌 `DateTime.Now`가 트리 안에 있으면 언제 평가되는가**
>
> 위 예제의 `DateTime.Now.AddDays(-30)`은 트리 안에서 `MemberExpression`(정적 프로퍼티 접근) + `MethodCallExpression`으로 남는다. 로컬에서 `Compile()`해서 부르면 **호출할 때마다** 현재 시각으로 다시 계산된다. EF Core로 넘기면 공급자가 이 부분식을 인식해 클라이언트에서 미리 평가한 뒤 SQL 파라미터로 넘기는 것이 보통이다 — 즉 **쿼리를 실행하는 시점**의 값이 된다. 둘 다 "지금"이라 결과가 같아 보이지만, 트리를 만들어 두고 한참 뒤에 실행하는 코드에서는 차이가 드러난다.

### `AsQueryable` — 로컬 시퀀스에 원격의 옷을 입히기

반대 방향도 있다. `AsQueryable`은 평범한 `IEnumerable<T>`를 `IQueryable<T>`로 감싼다.

```csharp
IQueryable<Product> FilterSortProducts (IQueryable<Product> input)
    => from p in input
       where !p.Discontinued
       orderby p.Description
       select p;

void Test()
{
    using var dbContext = new NutshellContext();
    Product[] localProducts = dbContext.Products.ToArray();

    var sqlQuery   = FilterSortProducts (dbContext.Products);
    var localQuery = FilterSortProducts (localProducts.AsQueryable());
}
```

`AsQueryable`이 반환하는 것은 `System.Linq.EnumerableQuery<T>`다. 이 타입은 `IQueryable<T>`와 `IQueryProvider`를 **둘 다** 구현하고, 열거 시점에 누적된 식 트리를 `Enumerable` 연산자 호출로 되바꿔 로컬에서 실행한다. 즉 트리를 만들었다가 다시 컴파일하는 왕복이 생긴다.

> **⚠️ `AsQueryable()`은 공짜 캐스팅이 아니다**
>
> 소스가 이미 `IQueryable<T>`이면 단순 캐스트지만, 로컬 시퀀스라면 래퍼를 만들고 이후 연산자들이 **식 트리를 쌓았다가 암묵적으로 컴파일**한다. 로컬 컬렉션에 `AsQueryable()`을 씌우고 `Where`를 거는 것은 그냥 `Where`를 거는 것보다 항상 느리다. 용도는 성능이 아니라 **다형성**(같은 쿼리 코드를 두 소스에 재사용)과 **테스트**다.

## 31.2 `Expression<TDelegate>`의 구조

### 노드 타입 계층

모든 노드의 기반 클래스는 제네릭이 아닌 `Expression`이다. 그 아래로 식의 **모양**마다 하나씩 파생 타입이 있다.

```text
                        Expression  (추상 기반 — NodeType, Type)
                             │
   ┌──────────┬──────────┬───┴──────┬───────────┬──────────────┬─────────────┐
   │          │          │          │           │              │             │
Binary    Unary     Constant   Parameter    Member       MethodCall     Conditional
Expression Expression Expression Expression  Expression   Expression     Expression
 (a + b)   (-a, cast) (5, "x")     (p)       (p.Name)    (s.Contains(x))  (a ? b : c)
   │
   └── … New / MemberInit / NewArray / Invocation / TypeBinary / Index / Default …
                             │
                    LambdaExpression  (매개변수를 가진 식 = 람다)
                             │
                    Expression<TDelegate>   ← 우리가 선언하는 타입
```

이 계층에서 헷갈리기 쉬운 지점이 하나 있다. **`Expression<TDelegate>`는 "타입 지정된 람다 식"이라는 뜻이지, "임의의 식"이 아니다.** 이름만 보면 `Expression`의 제네릭 버전 같지만 실제로는 `LambdaExpression`의 파생 클래스다.

```csharp
Expression<Func<string, bool>> typed = s => s.Length < 5;
LambdaExpression untyped = typed;    // 항상 성립 — 타입 통일 지점
Expression any = typed;              // 물론 이것도 성립
```

`LambdaExpression`은 타입이 다른 모든 람다 트리를 하나로 받는 자리다. 어떤 `Expression<T>`든 `LambdaExpression`으로 캐스팅할 수 있으므로, 컬렉션에 여러 종류의 람다를 담거나 공용 유틸리티에 넘길 때 이 타입을 쓴다.

> **📌 왜 `LambdaExpression<TDelegate>`이라고 이름 짓지 않았나**
>
> 의미상으로는 그 이름이 정확하다. 하지만 그러면 선언이 이렇게 된다.
>
> ```csharp
> LambdaExpression<Func<Customer,bool>> f = ...;
> ```
>
> 너무 길다. 짧은 이름을 택한 대가로 "`Expression<T>`는 `Expression`의 제네릭 버전이 아니다"라는 혼란이 영구히 남았다.

### 모든 노드가 가진 두 가지 — `NodeType`과 `Type`

`Expression`의 기본 멤버는 실질적으로 둘이다. **`NodeType`**(`ExpressionType` 열거형)은 이 노드가 어떤 종류의 식인지를 말한다 — `Add`, `LessThan`, `Call`, `Constant`, `Parameter`, `MemberAccess`, `Lambda`, `Convert`, `Quote` 등. **`Type`**(`System.Type`)은 이 식을 평가했을 때 나오는 정적 타입이다.

`NodeType`이 중요한 이유는 **CLR 타입과 1:1이 아니기 때문**이다. `BinaryExpression`이라는 CLR 타입 하나가 `Add`, `Subtract`, `LessThan`, `AndAlso`, `Coalesce`, `ArrayIndex` 등 수십 가지 연산을 대표한다. 트리를 순회할 때 `is BinaryExpression`만 봐서는 무슨 연산인지 알 수 없다. **`NodeType`을 봐야 한다.**

```csharp
Expression<Func<int,int,bool>> e = (a, b) => a + b < 10;

Console.WriteLine (e.Body.GetType().Name);   // BinaryExpression 계열(구현 타입 이름)
Console.WriteLine (e.Body.NodeType);         // LessThan
Console.WriteLine (e.Body.Type);             // System.Boolean
```

> **⚠️ `GetType()`으로 노드를 분류하지 마라**
>
> 팩토리 메서드가 돌려주는 것은 최적화된 **내부 파생 클래스**다. 예를 들어 `Expression.LessThan(...)`의 실제 런타임 타입은 `System.Linq.Expressions.LogicalBinaryExpression` 같은 비공개 타입일 수 있다. 공개 계약은 "`BinaryExpression`으로 캐스팅 가능하다"까지이지, 정확한 런타임 타입이 아니다. 분류는 `NodeType`으로, 접근은 `as`/패턴 매칭(`is BinaryExpression b`)으로 하라.

### 주요 노드 타입 레퍼런스

| 노드 타입 | 대표 `NodeType` | 어떤 C# 식에서 나오는가 | 핵심 속성 |
|---|---|---|---|
| `ParameterExpression` | `Parameter` | 람다 매개변수 `p`, 지역 변수 | `Name`, `Type` |
| `ConstantExpression` | `Constant` | 리터럴 `5`, `"a"`, 캡처된 클로저 객체 | `Value` |
| `MemberExpression` | `MemberAccess` | `p.Name`, `p.Length`, 필드 접근 | `Expression`(대상), `Member` |
| `MethodCallExpression` | `Call` | `s.Contains("a")`, `Queryable.Where(...)` | `Object`, `Method`, `Arguments` |
| `BinaryExpression` | `Add`, `LessThan`, `AndAlso`, `Equal`, `Coalesce` … | `a + b`, `a < b`, `a && b`, `a ?? b` | `Left`, `Right`, `Method` |
| `UnaryExpression` | `Not`, `Negate`, `Convert`, `Quote`, `TypeAs` | `!a`, `-a`, `(long)a`, 중첩 람다 | `Operand` |
| `ConditionalExpression` | `Conditional` | `a ? b : c` | `Test`, `IfTrue`, `IfFalse` |
| `NewExpression` | `New` | `new Point(1,2)`, 익명 타입 생성 | `Constructor`, `Arguments`, `Members` |
| `MemberInitExpression` | `MemberInit` | `new Point { X = 1 }` | `NewExpression`, `Bindings` |
| `NewArrayExpression` | `NewArrayInit`, `NewArrayBounds` | `new[] { 1, 2 }` | `Expressions` |
| `InvocationExpression` | `Invoke` | 델리게이트/람다 호출 `f(x)` | `Expression`, `Arguments` |
| `TypeBinaryExpression` | `TypeIs` | `p is Customer` | `Expression`, `TypeOperand` |
| `LambdaExpression` / `Expression<T>` | `Lambda` | 람다 전체 | `Parameters`, `Body`, `ReturnType` |

> **📌 문(statement) 노드도 있다**
>
> `BlockExpression`, `LoopExpression`, `TryExpression`, `SwitchExpression`, `GotoExpression`, `LabelExpression` 같은 타입들은 .NET 4에서 DLR과 함께 추가되었다. 이들로는 **문을 가진 완전한 메서드**를 트리로 표현할 수 있다.
>
> 그러나 **C# 컴파일러는 이런 노드를 만들지 않는다.** C#에서 `Expression<Func<int,int>>`에 대입할 수 있는 것은 **식 본문 람다뿐**이다. 블록 본문(`x => { return x * x; }`)을 대입하면 컴파일 오류(CS0834)가 난다. 블록 노드는 손으로 조립할 때만 쓴다. 이 제약은 EF Core 같은 공급자가 트리를 번역할 때 고려해야 할 경우의 수를 크게 줄여 준다.

### 트리를 손으로 조립하기

컴파일러가 하는 일을 그대로 손으로 해 보면 구조가 몸에 익는다. 원칙은 **바닥에서 위로**다.

목표: `s => s.Length < 5`

```csharp
using System;
using System.Linq.Expressions;

// 1단계 — 바닥. 매개변수 노드
ParameterExpression p = Expression.Parameter (typeof (string), "s");

// 2단계 — 멤버 접근과 상수
MemberExpression stringLength = Expression.Property (p, "Length");
ConstantExpression five = Expression.Constant (5);

// 3단계 — 비교
BinaryExpression comparison = Expression.LessThan (stringLength, five);

// 4단계 — 본문과 매개변수를 묶어 람다로
Expression<Func<string, bool>> lambda =
    Expression.Lambda<Func<string, bool>> (comparison, p);
```

검증은 `Compile()`이 제일 빠르다.

```csharp
Func<string, bool> runnable = lambda.Compile();
Console.WriteLine (runnable ("kangaroo"));   // False
Console.WriteLine (runnable ("dog"));        // True
Console.WriteLine (lambda);                  // s => (s.Length < 5)
```

`ToString()`이 C# 비슷한 문자열을 돌려준다는 점도 기억해 둘 만하다. 디버깅에 유용하다.

> **⚠️ 노드 타입을 `new`로 만들 수 없다**
>
> `new BinaryExpression(...)` 같은 코드는 컴파일되지 않는다. 노드 타입들의 생성자는 공개되어 있지 않다. **반드시 `Expression` 클래스의 정적 팩토리 메서드**(`Expression.Add`, `Expression.Call`, `Expression.Constant`, `Expression.LessThan` …)를 써야 한다. 팩토리는 인자의 타입 호환성을 검사하고, 필요하면 최적화된 내부 구현 타입을 골라 준다.

> **⚠️ 팩토리는 타입을 엄격하게 검사한다**
>
> `Expression.LessThan(stringLength, Expression.Constant("5"))`처럼 `int`와 `string`을 비교하려 들면 `InvalidOperationException`이 난다. 컴파일 타임이 아니라 **트리를 만드는 순간** 터진다. 숫자 타입이 서로 달라도(예: `int`와 `long`) 자동 승격은 없다 — `Expression.Convert`로 명시적으로 맞춰야 한다. 동적 쿼리 빌더를 쓸 때 실무에서 가장 자주 만나는 예외다.

> **💡 어떤 노드 타입을 써야 할지 모르겠다면**
>
> 만들고 싶은 모양의 람다를 C#으로 한 줄 쓰고, `Expression<...>` 변수에 대입한 다음 **디버거로 열어 보라.** 컴파일러가 어떤 노드를 어떻게 중첩했는지가 그대로 보인다. 손으로 조립할 때 이보다 빠른 참조는 없다.

### 트리를 직접 순회해 출력해 보기

이제 반대 방향 — 완성된 트리를 읽는 쪽이다. 공급자가 하는 일의 축소판이다. 다음은 트리를 재귀로 걸어가며 들여쓰기 형태로 찍는 함수다.

```csharp
using System;
using System.Linq.Expressions;

static void Dump (Expression? e, int depth = 0)
{
    if (e is null) return;
    string pad = new string (' ', depth * 2);

    switch (e)
    {
        case LambdaExpression lambda:
            Console.WriteLine ($"{pad}Lambda ({lambda.Type.Name})");
            foreach (var prm in lambda.Parameters) Dump (prm, depth + 1);
            Dump (lambda.Body, depth + 1);
            break;

        case BinaryExpression bin:
            Console.WriteLine ($"{pad}{bin.NodeType} : {bin.Type.Name}");
            Dump (bin.Left,  depth + 1);
            Dump (bin.Right, depth + 1);
            break;

        case UnaryExpression un:
            Console.WriteLine ($"{pad}{un.NodeType} : {un.Type.Name}");
            Dump (un.Operand, depth + 1);
            break;

        case MethodCallExpression call:
            Console.WriteLine ($"{pad}Call {call.Method.DeclaringType!.Name}.{call.Method.Name}");
            Dump (call.Object, depth + 1);                      // 정적 메서드면 null
            foreach (var arg in call.Arguments) Dump (arg, depth + 1);
            break;

        case MemberExpression mem:
            Console.WriteLine ($"{pad}MemberAccess {mem.Member.Name} : {mem.Type.Name}");
            Dump (mem.Expression, depth + 1);
            break;

        case ConstantExpression con:
            Console.WriteLine ($"{pad}Constant {con.Value ?? "null"} : {con.Type.Name}");
            break;

        case ParameterExpression prm:
            Console.WriteLine ($"{pad}Parameter {prm.Name} : {prm.Type.Name}");
            break;

        default:
            Console.WriteLine ($"{pad}{e.NodeType} ({e.GetType().Name}) : {e.Type.Name}");
            break;
    }
}
```

실행해 보자.

```csharp
Expression<Func<Product, bool>> f =
    p => !p.Discontinued && p.Description.Contains ("bike");

Dump (f);
```

출력은 다음과 같다.

```text
Lambda (Func`2)
  Parameter p : Product
  AndAlso : Boolean
    Not : Boolean
      MemberAccess Discontinued : Boolean
        Parameter p : Product
    Call String.Contains
      MemberAccess Description : String
        Parameter p : Product
      Constant bike : String
```

이 출력이 EF Core가 보는 것과 같다. 여기서 `MemberAccess Discontinued` ← `Parameter p`를 만나면 "`p`는 `Product` 테이블의 행이고, `Discontinued`는 그 테이블의 컬럼"이라고 해석해 `[p].[Discontinued]`를 찍는다. `Call String.Contains`를 만나면 데이터베이스별 번역 규칙 표를 찾아 `CHARINDEX(...) > 0` 또는 `instr(...) > 0`으로 바꾼다. 아는 노드가 나오면 번역하고, 모르는 노드가 나오면 실패한다 — 원리는 이것이 전부다.

> **📌 캡처된 지역 변수는 `Constant`가 아니다**
>
> 위 예제에서 `"bike"`를 지역 변수로 바꿔 보라.
>
> ```csharp
> string keyword = "bike";
> Expression<Func<Product, bool>> f = p => p.Description.Contains (keyword);
> ```
>
> 트리에 나타나는 것은 `Constant "bike"`가 아니라 다음 두 노드다.
>
> ```text
> MemberAccess keyword : String
>   Constant Program+<>c__DisplayClass0_0 : <>c__DisplayClass0_0
> ```
>
> 컴파일러는 캡처된 변수를 **디스플레이 클래스의 필드**로 옮기고(26.10절), 트리에는 "이 디스플레이 클래스 인스턴스의 `keyword` 필드"라는 접근 경로를 남긴다. 값이 아니라 **값을 얻는 방법**이 트리에 들어간다는 뜻이다. 이 구조가 EF Core의 쿼리 파라미터화와 쿼리 캐시의 토대다(31.7절).

### `ExpressionVisitor` — 순회의 표준 도구

위의 `Dump`처럼 `switch`를 직접 쓰는 것은 학습에는 좋지만 실무에는 부적합하다. 노드 종류가 40가지가 넘고, 트리를 **변형**하려면 자식이 바뀐 노드를 다시 만들어 붙이는 재구축 로직까지 필요하다. 그 지루한 작업을 `System.Linq.Expressions.ExpressionVisitor`가 대신한다.

`ExpressionVisitor`는 추상 클래스가 아니라 **구현이 들어 있는 클래스**다. 기본 구현은 트리를 순회하면서 각 노드를 그대로 재구축한다 — 자식이 하나도 안 바뀌면 원본 노드를 그대로 돌려주는 최적화까지 되어 있다. 우리는 관심 있는 `Visit*` 메서드만 재정의하면 된다.

| 재정의 대상 | 언제 호출되는가 |
|---|---|
| `VisitParameter(ParameterExpression)` | 매개변수 노드 |
| `VisitConstant(ConstantExpression)` | 상수 노드 |
| `VisitMember(MemberExpression)` | 필드·프로퍼티 접근 |
| `VisitMethodCall(MethodCallExpression)` | 메서드 호출 |
| `VisitBinary(BinaryExpression)` | 이항 연산 |
| `VisitUnary(UnaryExpression)` | 단항 연산·변환·`Quote` |
| `VisitLambda<T>(Expression<T>)` | 람다 |
| `Visit(Expression)` | 모든 노드 (디스패처) |

가장 단순한 활용은 **읽기 전용 수집**이다. 트리 안에서 호출되는 메서드 이름을 전부 모아 보자.

```csharp
using System.Collections.Generic;
using System.Linq.Expressions;

sealed class MethodCollector : ExpressionVisitor
{
    public List<string> Methods { get; } = new();

    protected override Expression VisitMethodCall (MethodCallExpression node)
    {
        Methods.Add ($"{node.Method.DeclaringType!.Name}.{node.Method.Name}");
        return base.VisitMethodCall (node);   // 자식으로 계속 내려간다
    }
}
```

```csharp
var collector = new MethodCollector();
collector.Visit (f);
Console.WriteLine (string.Join (", ", collector.Methods));   // String.Contains
```

`base.VisitMethodCall(node)`를 반드시 호출해야 한다는 점이 함정이다. 빼먹으면 그 노드의 **자식으로 내려가지 않는다.**

변형은 반환값으로 한다. 다음은 트리 안의 모든 `string` 상수를 대문자로 바꾸는 방문자다.

```csharp
sealed class UpperCaseStrings : ExpressionVisitor
{
    protected override Expression VisitConstant (ConstantExpression node)
        => node.Value is string s
            ? Expression.Constant (s.ToUpperInvariant(), typeof (string))
            : node;
}
```

```csharp
Expression<Func<Product, bool>> before = p => p.Description.Contains ("bike");
var after = (Expression<Func<Product, bool>>) new UpperCaseStrings().Visit (before);
Console.WriteLine (after);   // p => p.Description.Contains("BIKE")
```

> **⚠️ 식 트리는 불변이다**
>
> 노드에는 `set` 접근자가 없다. `BinaryExpression.Left = ...` 같은 코드는 존재하지 않는다. 트리를 "고친다"는 것은 언제나 **새 트리를 만든다**는 뜻이다. `ExpressionVisitor`가 하는 일도 정확히 그것 — 바뀐 노드를 만나면 부모 노드를 새로 만들어 위로 올린다. 이 불변성 덕분에 트리를 여러 스레드에서 공유해도 안전하고, 부분 트리를 여러 쿼리에 재사용해도 서로 영향이 없다.

> **💡 `Update` 메서드를 기억하라**
>
> 대부분의 노드 타입에는 `Update(...)` 인스턴스 메서드가 있다. 자식들을 인자로 받아, **하나라도 달라졌으면** 새 노드를, 전부 같으면 `this`를 돌려준다. 방문자를 직접 재구축할 때 이 메서드를 쓰면 불필요한 할당을 피할 수 있다.
>
> ```csharp
> protected override Expression VisitBinary (BinaryExpression node)
>     => node.Update (Visit (node.Left), node.Conversion, Visit (node.Right));
> ```

## 31.3 해석되는 쿼리(interpreted query)의 동작 원리

### 두 개의 평행 아키텍처

LINQ에는 서로 평행한 두 아키텍처가 있다.

| | 로컬 쿼리 (LINQ to Objects) | 해석되는 쿼리 |
|---|---|---|
| 소스 인터페이스 | `IEnumerable<T>` | `IQueryable<T>` |
| 연산자 클래스 | `System.Linq.Enumerable` | `System.Linq.Queryable` |
| 람다의 표현 | 델리게이트 (컴파일된 IL) | 식 트리 (객체 그래프) |
| 연산자 체인의 정체 | 데코레이터 열거자 체인(29.6절) | 중첩된 `MethodCallExpression` 트리 |
| 실행 주체 | `foreach`가 `MoveNext`를 호출 | 공급자가 트리 전체를 번역해 실행 |
| 성격 | **명령적** — 무엇을 어떻게 할지 코드로 박혀 있다 | **서술적** — 무엇을 원하는지 서술만 되어 있다 |

29.6절에서 본 로컬 쿼리의 데코레이터 체인은 실제로 동작하는 기계다. `Where` 반복자가 `Select` 반복자를 감싸고, `MoveNext()` 한 번이 체인을 타고 내려간다. 반면 해석되는 쿼리의 연산자 체인은 **아무 일도 하지 않는 껍데기**다. 각 연산자는 "나는 `Where`라고 불렸고 인자는 이 트리였다"는 사실만 기록한다.

### 예제 하나로 끝까지 따라가기

SQL Server에 다음 테이블이 있다고 하자.

```sql
create table Customer
(
  ID int not null primary key,
  Name varchar(30)
)
insert Customer values (1, 'Tom')
insert Customer values (2, 'Dick')
insert Customer values (3, 'Harry')
insert Customer values (4, 'Mary')
insert Customer values (5, 'Jay')
```

EF Core로 이 테이블에 쿼리를 건다.

```csharp
using System;
using System.Linq;
using Microsoft.EntityFrameworkCore;

using var dbContext = new NutshellContext();

IQueryable<string> query = from c in dbContext.Customers
                           where c.Name.Contains ("a")
                           orderby c.Name.Length
                           select c.Name.ToUpper();

foreach (string name in query) Console.WriteLine (name);

public class Customer
{
    public int ID { get; set; }
    public string Name { get; set; } = "";
}

public class NutshellContext : DbContext
{
    public virtual DbSet<Customer> Customers { get; set; } = null!;

    protected override void OnConfiguring (DbContextOptionsBuilder builder)
        => builder.UseSqlServer ("...connection string...");

    protected override void OnModelCreating (ModelBuilder modelBuilder)
        => modelBuilder.Entity<Customer>().ToTable ("Customer")
                                          .HasKey (c => c.ID);
}
```

EF Core는 이 쿼리를 다음 SQL로 번역한다.

```sql
SELECT UPPER([c].[Name])
FROM [Customer] AS [c]
WHERE CHARINDEX(N'a', [c].[Name]) > 0
ORDER BY CAST(LEN([c].[Name]) AS int)
```

결과는 이렇다.

```text
JAY
MARY
HARRY
```

### 1단계 — 쿼리 구문이 플루언트 구문으로

컴파일러의 첫 작업은 로컬 쿼리와 완전히 동일하다(29.3절). 쿼리 식은 순수한 구문 설탕이므로 확장 메서드 호출로 풀린다.

```csharp
IQueryable<string> query = dbContext.Customers
    .Where   (c => c.Name.Contains ("a"))
    .OrderBy (c => c.Name.Length)
    .Select  (c => c.Name.ToUpper());
```

### 2단계 — 오버로드 해석이 갈림길이다

여기서부터 로컬 쿼리와 갈라진다. `dbContext.Customers`의 정적 타입은 `DbSet<Customer>`이고, `DbSet<T>`는 `IQueryable<T>`를 구현한다. `IQueryable<T>`는 `IEnumerable<T>`의 파생 인터페이스이므로 컴파일러 앞에는 후보가 둘이다.

```csharp
Enumerable.Where<Customer> (IEnumerable<Customer>, Func<Customer,bool>)
Queryable .Where<Customer> (IQueryable<Customer>,  Expression<Func<Customer,bool>>)
```

첫 번째 인자의 타입이 **더 구체적으로 일치하는** 쪽이 이긴다. `IQueryable<Customer>`가 `IEnumerable<Customer>`보다 구체적이므로 `Queryable.Where`가 선택된다.

이 결정이 람다의 운명을 바꾼다. `Queryable.Where`의 두 번째 매개변수가 `Expression<Func<Customer,bool>>`이므로, 컴파일러는 `c => c.Name.Contains("a")`를 **델리게이트가 아니라 식 트리로** 컴파일한다.

`Queryable.Where`의 반환 타입도 `IQueryable<T>`이므로 `OrderBy`, `Select`에도 같은 일이 반복된다. 결과적으로 세 개의 람다가 모두 트리가 된다.

### 3단계 — 트리가 트리를 감싼다

최종적으로 `query` 변수 안에 무엇이 들어 있는지 그림으로 보자.

```text
IQueryable<string> query
  ├─ Provider ──→ EF Core의 IQueryProvider 구현
  └─ Expression ──→ ┌──────────────────────────────────────────┐
                    │ Call Queryable.Select                    │
                    │  ├─ Call Queryable.OrderBy               │
                    │  │   ├─ Call Queryable.Where             │
                    │  │   │   ├─ Constant : DbSet<Customer>   │  ← 쿼리 루트
                    │  │   │   └─ Quote                        │
                    │  │   │       └─ Lambda c => c.Name.Contains("a")
                    │  │   └─ Quote                            │
                    │  │       └─ Lambda c => c.Name.Length    │
                    │  └─ Quote                                │
                    │      └─ Lambda c => c.Name.ToUpper()     │
                    └──────────────────────────────────────────┘
```

주목할 점이 셋이다.

1. **연산자 호출 자체가 노드다.** `Where`, `OrderBy`, `Select`는 실행되지 않았다. 각각 `MethodCallExpression`으로 트리에 남았을 뿐이다.
2. **가장 바깥이 마지막 연산자다.** 데이터 흐름과 트리의 중첩 방향이 반대다. `Select`가 루트고, 소스가 가장 깊은 곳에 있다.
3. **람다가 `Quote` 노드로 한 겹 싸여 있다.** `Queryable` 연산자의 매개변수 타입이 `Expression<...>`이므로, "트리 안에 트리가 들어간다"는 것을 표현하기 위해 `NodeType == Quote`인 `UnaryExpression`이 끼어든다. 트리를 직접 순회할 때 `Quote`를 벗겨야 안쪽 람다에 닿는다.

> **📌 `Quote`를 벗기는 관용구**
>
> ```csharp
> static LambdaExpression Unquote (Expression e)
>     => e is UnaryExpression { NodeType: ExpressionType.Quote } u
>        ? (LambdaExpression) u.Operand
>        : (LambdaExpression) e;
> ```
>
> 공급자를 직접 구현하거나 남의 쿼리 트리를 분석할 때 반드시 필요하다. `Expression.Call`로 `Queryable` 메서드를 조립할 때도 인자를 `Expression.Quote(lambda)`로 감싸 주어야 한다(31.6절).

### `IQueryable<T>`와 `IQueryProvider`의 실물

이 구조를 떠받치는 인터페이스는 놀랍도록 작다.

```csharp
namespace System.Linq
{
    public interface IQueryable : IEnumerable
    {
        Type ElementType { get; }
        Expression Expression { get; }     // 여기까지 누적된 쿼리 트리
        IQueryProvider Provider { get; }   // 이 트리를 해석할 주체
    }

    public interface IQueryable<out T> : IEnumerable<T>, IQueryable { }

    public interface IQueryProvider
    {
        IQueryable CreateQuery (Expression expression);
        IQueryable<TElement> CreateQuery<TElement> (Expression expression);
        object? Execute (Expression expression);
        TResult Execute<TResult> (Expression expression);
    }
}
```

이제 `Queryable.Where`의 구현이 무엇을 하는지 추측할 수 있다. 대략 이렇다.

```csharp
public static IQueryable<TSource> Where<TSource> (
    this IQueryable<TSource> source,
    Expression<Func<TSource, bool>> predicate)
{
    return source.Provider.CreateQuery<TSource> (
        Expression.Call (
            null,                                   // 정적 메서드
            /* 이 Where 메서드의 MethodInfo */ ...,
            source.Expression,                      // 기존 트리
            Expression.Quote (predicate)));         // 새 술어
}
```

**기존 트리를 인자로 삼아 새 `MethodCallExpression`을 만들고, 공급자에게 "이 트리를 담은 새 `IQueryable`을 만들어 달라"고 요청한다.** 이것이 전부다. 데이터베이스 접속도, SQL 생성도 일어나지 않는다.

`Queryable`의 모든 시퀀스→시퀀스 연산자가 이 한 가지 패턴을 따른다. 그래서 `Queryable` 클래스 전체가 사실상 "트리 조립 보일러플레이트"다.

### 실행 — 열거가 방아쇠다

`IQueryable<T>`는 `IEnumerable<T>`이므로 `foreach`가 `GetEnumerator()`를 부른다. 공급자의 `IQueryable` 구현은 이 시점에 다음을 한다.

```text
foreach (string name in query)
        │
        ├─ query.GetEnumerator()
        │        │
        │        └─ Provider.Execute<IEnumerable<string>>(query.Expression)
        │                 │
        │                 ├─ 트리 순회 → 내부 쿼리 모델로 변환
        │                 ├─ SQL 문자열 + 파라미터 생성
        │                 ├─ DbCommand 실행
        │                 └─ DbDataReader → 결과 시퀀스로 실체화
        │
        └─ MoveNext()가 결과 시퀀스를 하나씩 돌려준다
```

29.2절에서 로컬 쿼리를 "컨베이어 벨트가 줄지어 선 생산 라인"에 비유했다. 해석되는 쿼리에서는 **벨트가 하나만 돈다.** 나머지 라인은 이마에 지시서(식 트리)를 붙인 마네킹들의 네트워크일 뿐이다. 가장 바깥 벨트가 돌기 시작하면 생산 관리자(공급자)를 부르고, 관리자는 라인 전체를 훑어 지시서를 한 장의 종이(SQL 문)로 옮겨 적은 뒤 그것을 실행한다. 결과만 소비자에게 흘려보낸다.

> **⚠️ 지연 실행의 규칙은 같지만 대가는 다르다**
>
> 해석되는 쿼리도 지연 실행이다(29.6절). 열거하기 전에는 SQL이 만들어지지도 않는다. 그리고 **같은 쿼리를 두 번 열거하면 데이터베이스에 두 번 간다.** 로컬 쿼리에서 두 번 열거하면 CPU를 두 번 쓰는 데 그치지만, 여기서는 네트워크 왕복과 데이터베이스 부하가 두 배가 된다. 결과를 두 번 이상 쓴다면 `ToList()`로 한 번 실체화하라(29.11절).

> **⚠️ 표준 연산자를 벗어나면 상호운용성이 끝난다**
>
> 로컬 쿼리에서는 `yield return`으로 자기만의 연산자를 쉽게 만들어 표준 집합을 보강할 수 있다(28.8절). 원격 쿼리에서는 그게 어렵고, 대개 바람직하지도 않다. `IQueryable<T>`를 받는 `MyWhere` 확장 메서드를 만들면 생산 라인에 **관리자가 모르는 마네킹**을 세우는 셈이다. 관리자는 그것을 어떻게 해야 할지 모른다.
>
> 설령 공급자 내부에 끼어들어 처리하게 만들더라도, 그 해법은 특정 공급자(EF Core 등)에 하드코딩된다. 다른 `IQueryable` 구현에서는 동작하지 않는다. `Queryable`에 표준 메서드 집합이 있다는 것의 가치는 **어떤 원격 컬렉션에나 통하는 공통 어휘**라는 점이다. 어휘를 확장하는 순간 상호운용성을 잃는다.

> **⚠️ 표준 연산자만 써도 번역이 안 될 수 있다**
>
> `IQueryable` 공급자는 대상 시스템의 능력에 갇혀 있다. EF Core는 데이터베이스 서버가 할 수 있는 일까지만 한다. SQL로 옮길 수 없는 LINQ 쿼리는 존재한다 — 인덱스 오버로드(`Where((x,i) => ...)`), 임의의 .NET 메서드 호출, `Regex`, 사용자 정의 로컬 함수 등. 실패는 컴파일 타임이 아니라 **런타임 예외**로 나타난다(31.4절).

### 최소한의 공급자로 트리 누적을 눈으로 확인하기

공급자를 만드는 것이 목적이 아니라, "정말 아무 일도 안 일어나는가"를 확인하는 것이 목적이다. 다음 공급자는 실행 시점에 누적된 트리를 그대로 찍고 빈 결과를 돌려준다.

```csharp
using System;
using System.Collections;
using System.Collections.Generic;
using System.Linq;
using System.Linq.Expressions;

class DumpQueryable<T> : IQueryable<T>
{
    public DumpQueryable (IQueryProvider provider, Expression expression)
        => (Provider, Expression) = (provider, expression);

    public Type ElementType => typeof (T);
    public Expression Expression { get; }
    public IQueryProvider Provider { get; }

    public IEnumerator<T> GetEnumerator()
        => Provider.Execute<IEnumerable<T>> (Expression).GetEnumerator();
    IEnumerator IEnumerable.GetEnumerator() => GetEnumerator();
}

class DumpProvider : IQueryProvider
{
    public IQueryable CreateQuery (Expression e)
        => throw new NotSupportedException();

    public IQueryable<TElement> CreateQuery<TElement> (Expression e)
        => new DumpQueryable<TElement> (this, e);

    public object Execute (Expression e) => Execute<object> (e)!;

    public TResult Execute<TResult> (Expression e)
    {
        Console.WriteLine ("=== 실행 시점에 도착한 트리 ===");
        Console.WriteLine (e);                     // ToString()이 C# 비슷하게 찍어 준다
        return default!;
    }
}
```

이제 이 공급자 위에 쿼리를 쌓는다.

```csharp
var source = new DumpQueryable<Customer> (new DumpProvider(), Expression.Constant (null, typeof (IQueryable<Customer>)));

var q = source.Where (c => c.Name.Contains ("a"))
              .OrderBy (c => c.Name.Length)
              .Select (c => c.Name.ToUpper());

Console.WriteLine ("여기까지 아무 출력도 없다");

foreach (var x in q) { }   // 이제서야 Execute가 불린다
```

출력은 다음과 같다.

```text
여기까지 아무 출력도 없다
=== 실행 시점에 도착한 트리 ===
null.Where(c => c.Name.Contains("a")).OrderBy(c => c.Name.Length).Select(c => c.Name.ToUpper())
```

세 연산자를 호출했는데도 `foreach`에 닿기 전에는 `Execute`가 한 번도 불리지 않았다. 그리고 도착한 것은 **세 번의 호출이 통째로 합쳐진 트리 하나**다. 공급자는 이 트리를 단위로 처리한다.

> **💡 공급자를 직접 만들 일이 있을까**
>
> 실무에서 완전한 `IQueryProvider`를 구현할 일은 드물다. 트리를 SQL이나 다른 쿼리 언어로 옮기는 작업은 방대하고, 부분 지원은 사용자를 혼란에 빠뜨린다. 그러나 **읽을 줄은 알아야 한다.** EF Core가 왜 이 쿼리를 번역하지 못하는지, `AsEnumerable()`을 어디에 넣어야 하는지, 동적 쿼리 빌더가 만든 트리가 왜 공급자를 화나게 하는지 — 전부 이 구조를 이해해야 답이 나온다.

## 31.4 `IEnumerable` vs `IQueryable` — 어디서 실행되는가

### 인터페이스 관계가 만드는 함정

`IQueryable<T>`는 `IEnumerable<T>`를 **상속한다.** 이 한 줄이 이 절의 모든 문제를 만든다.

```csharp
public interface IQueryable<out T> : IEnumerable<T>, IQueryable { }
```

상속한다는 것은 `IQueryable<T>` 시퀀스에 `Enumerable`의 연산자를 **적법하게 쓸 수 있다**는 뜻이다. 컴파일 오류도, 경고도 없다. 다만 그렇게 하면 쿼리가 클라이언트에서 실행될 뿐이다.

```csharp
IQueryable<Customer> customers = dbContext.Customers;

// (A) Queryable.Where — 서버에서 필터
var a = customers.Where (c => c.Name.StartsWith ("A"));

// (B) Enumerable.Where — 테이블 전체를 끌어와 클라이언트에서 필터
var b = customers.AsEnumerable().Where (c => c.Name.StartsWith ("A"));
```

두 줄은 같은 결과를 낸다. 비용은 자릿수가 다르다.

### 오버로드 해석은 어떻게 결정되는가

컴파일러는 확장 메서드 후보 중 **첫 인자에 대한 변환이 더 나은** 쪽을 고른다. `IQueryable<Customer>` 값을 `IQueryable<Customer>` 매개변수에 넘기는 것은 항등 변환이고, `IEnumerable<Customer>` 매개변수에 넘기는 것은 암시적 참조 변환이다. 항등 변환이 이긴다.

핵심은 **소스 표현식의 정적 타입**이 결정한다는 것이다. 런타임 타입이 아니다.

```csharp
IQueryable<Customer> q = dbContext.Customers;
IEnumerable<Customer> e = dbContext.Customers;   // 같은 객체, 다른 정적 타입

var r1 = q.Where (c => c.ID > 10);   // Queryable.Where  → SQL에 WHERE 절
var r2 = e.Where (c => c.ID > 10);   // Enumerable.Where → 전체 로드 후 로컬 필터
```

`r2`의 런타임 객체는 여전히 `DbSet<Customer>`다. 그러나 컴파일 시점에 `Enumerable.Where`로 바인딩되었으므로 `DbSet`은 그냥 열거될 뿐이다.

> **⚠️ 변수 타입 하나가 성능을 몇 자릿수 바꾼다**
>
> 이것이 이 장에서 가장 흔하고 가장 비싼 사고다. `IEnumerable<T>`로 선언한 필드나 메서드 반환 타입이 어딘가에서 `DbSet`을 받고 있다면, 그 뒤로 붙는 모든 연산자가 클라이언트에서 실행된다. 100만 행 테이블에 `Where`와 `Count()`를 걸었는데 `SELECT COUNT(*)` 대신 100만 행 전송이 일어난다.
>
> 리포지터리 계층에서 `IEnumerable<T>`를 반환하는 것은 "여기서부터 로컬"이라는 **의도적 선언**이어야 한다. 무심코 그렇게 되어서는 안 된다(31.9절).

### 두 인터페이스 비교

| 관점 | `IEnumerable<T>` | `IQueryable<T>` |
|---|---|---|
| 추가 멤버 | 없음 (`GetEnumerator`뿐) | `ElementType`, `Expression`, `Provider` |
| 연산자가 받는 것 | 델리게이트 | 식 트리 |
| 필터·정렬 실행 장소 | 항상 클라이언트 | 공급자가 결정(보통 서버) |
| 지연 실행 | 그렇다 | 그렇다 |
| 사용자 정의 연산자 추가 | 쉽다 (`yield return`) | 사실상 불가 |
| 임의의 .NET 메서드 호출 | 가능 | 공급자가 아는 것만 |
| 실패 시점 | 컴파일 타임에 대부분 잡힘 | **런타임 예외** |
| 원격 소스에서의 왕복 | 실체화 시 1회 (이미 로컬) | 열거할 때마다 1회 이상 |
| 공변성 | `out T` | `out T` |

> **📌 `IQueryable<T>`의 세 멤버를 직접 쓸 일은 거의 없다**
>
> `Expression`과 `Provider`는 `Queryable` 연산자들이 내부적으로 쓰라고 있는 것이다. 애플리케이션 코드가 이들을 직접 만지는 경우는 (1) 공급자를 구현할 때, (2) 트리를 진단 목적으로 들여다볼 때, (3) 동적 쿼리 빌더에서 `Provider.CreateQuery`를 직접 부를 때 정도다. EF Core를 쓰는 보통의 코드는 이 멤버들의 존재를 몰라도 된다.

### 번역 실패는 런타임에 드러난다

`Queryable` 연산자를 썼다고 해서 반드시 번역되는 것은 아니다.

```csharp
using var dbContext = new NutshellContext();

var query = dbContext.Customers
    .Where (c => MyLocalCheck (c.Name));   // 로컬 메서드
```

이 코드는 **컴파일된다.** `c => MyLocalCheck(c.Name)`은 훌륭한 식 트리가 되고, 트리 안에는 `Call MyLocalCheck` 노드가 들어간다. 문제는 EF Core가 `MyLocalCheck`이라는 메서드를 SQL로 옮길 방법을 모른다는 것이다. 열거하는 순간 `InvalidOperationException`이 나며, 메시지는 "The LINQ expression ... could not be translated"로 시작한다.

> **⚠️ EF Core 3.0 이후 클라이언트 평가는 최상위 투영에서만 허용된다**
>
> EF Core 2.x는 번역할 수 없는 부분을 **조용히 클라이언트에서 평가**했다. 편했지만 재앙이었다. `Where` 절 하나가 번역되지 않으면 아무 경고 없이 테이블 전체를 끌어왔고, 개발 데이터베이스에서는 멀쩡하다가 운영에서 터졌다.
>
> EF Core 3.0에서 이 동작이 바뀌었다. **번역할 수 없으면 예외를 던진다.** 예외는 `InvalidOperationException`이다. 유일한 예외 조항이 최종 `Select` 투영 — 거기서는 클라이언트 코드를 호출해도 된다. 결과 행 수가 이미 서버에서 결정되었으므로 안전하기 때문이다.
>
> ```csharp
> // 허용 — 최상위 투영에서의 클라이언트 평가
> var ok = dbContext.Customers
>     .Where (c => c.Name.StartsWith ("A"))     // 서버
>     .Select (c => Format (c.Name));           // 클라이언트
>
> // 예외 — 필터에서의 클라이언트 평가
> var bad = dbContext.Customers
>     .Where (c => Format (c.Name).Length > 3);
> ```

### 어떤 것이 번역되는가 — 감을 잡는 표

정확한 목록은 공급자와 데이터베이스마다 다르다. 다음은 EF Core + 관계형 데이터베이스 기준의 일반적인 경향이다.

| 쓴 것 | 번역 여부 | 비고 |
|---|---|---|
| `==`, `!=`, `<`, `>`, `&&`, `\|\|`, `!` | 대체로 된다 | `null` 의미론이 SQL의 3값 논리와 다를 수 있다 |
| `string.Contains` / `StartsWith` / `EndsWith` | 된다 | `LIKE` 또는 `CHARINDEX`/`instr`로 |
| `string.Length`, `ToUpper`, `ToLower`, `Trim`, `Substring` | 대체로 된다 | 데이터베이스 함수로 매핑 |
| `Math.Abs`, `Math.Round` 등 일부 수학 함수 | 대체로 된다 | 반올림 규칙이 미묘하게 다를 수 있다 |
| `DateTime`의 `Year`/`Month`/`Day` | 대체로 된다 | |
| `Where`, `OrderBy`, `Select`, `Join`, `GroupBy`, `Skip`, `Take` | 된다 | `GroupBy`는 형태에 따라 실패한다(30.6절) |
| 인덱스 오버로드 `Where((x,i) => ...)` | **안 된다** | SQL에 "입력 순서" 개념이 없다 |
| `Regex`, 사용자 정의 메서드, 델리게이트 호출 | **안 된다** | |
| `ToString()` (임의 타입) | 부분적 | 타입과 공급자에 따라 다르다 |
| `Aggregate` | **안 된다** | |
| 로컬 컬렉션에 대한 `Contains` (`ids.Contains(c.ID)`) | 된다 | `IN (...)` 으로 번역 |

> **💡 "된다/안 된다"를 외우려 하지 마라**
>
> 목록은 EF Core 버전마다 늘어난다. 실무에서 훨씬 쓸모 있는 것은 **확인하는 습관**이다. `ToQueryString()`으로 생성 SQL을 찍어 보고(31.7절), 통합 테스트에서 실제 데이터베이스에 한 번 실행해 보라. "컴파일되니까 될 것"이라는 가정이 유일한 진짜 위험이다.

> **⚠️ SQL의 `NULL` 의미론은 C#과 다르다**
>
> C#에서 `null == null`은 `true`지만 SQL에서 `NULL = NULL`은 `UNKNOWN`이다. EF Core는 이 간극을 메우려고 번역된 SQL에 `OR (a IS NULL AND b IS NULL)` 같은 보정 절을 끼워 넣는다. 그래서 생성된 SQL이 예상보다 복잡해 보이고, 인덱스를 못 타기도 한다. 컬럼을 `NOT NULL`로 선언하고 엔티티 프로퍼티를 널 불가로 맞추면 이 보정이 사라진다. 21장의 널 안정성 규율이 여기서 성능으로 돌아온다.

## 31.5 로컬 쿼리와 해석 쿼리 결합하기, `AsEnumerable`

### 전형적 패턴 — 안쪽이 원격, 바깥쪽이 로컬

하나의 쿼리에 해석 연산자와 로컬 연산자를 섞을 수 있다. 실무에서 통하는 배치는 **로컬 연산자를 바깥에, 해석 연산자를 안쪽에** 두는 것이다. 해석되는 쿼리가 로컬 쿼리에 데이터를 공급하는 모양이다.

예를 들어 문자열 시퀀스를 둘씩 짝짓는 로컬 확장 메서드를 하나 만들어 두자.

```csharp
using System.Collections.Generic;

public static IEnumerable<string> Pair (this IEnumerable<string> source)
{
    string? firstHalf = null;
    foreach (string element in source)
        if (firstHalf == null)
            firstHalf = element;
        else
        {
            yield return firstHalf + ", " + element;
            firstHalf = null;
        }
}
```

이 메서드를 EF Core 쿼리 중간에 끼워 넣는다.

```csharp
using var dbContext = new NutshellContext();

IEnumerable<string> q = dbContext.Customers
    .Select (c => c.Name.ToUpper())
    .OrderBy (n => n)
    .Pair()                                           // 여기서부터 로컬
    .Select ((n, i) => "Pair " + i.ToString() + " = " + n);

foreach (string element in q) Console.WriteLine (element);

// Pair 0 = DICK, HARRY
// Pair 1 = JAY, MARY
```

바인딩이 어떻게 흘러갔는지 따라가 보자.

| 위치 | 소스의 정적 타입 | 바인딩된 메서드 | 실행 위치 |
|---|---|---|---|
| `dbContext.Customers` | `DbSet<Customer>` (`IQueryable<Customer>`) | — | — |
| `.Select(c => c.Name.ToUpper())` | `IQueryable<Customer>` | `Queryable.Select` | 서버 |
| `.OrderBy(n => n)` | `IQueryable<string>` | `Queryable.OrderBy` | 서버 |
| `.Pair()` | `IOrderedQueryable<string>` | **`Pair`** (`IEnumerable<string>` 오버로드밖에 없다) | 클라이언트 |
| `.Select((n,i) => ...)` | `IEnumerable<string>` | `Enumerable.Select` | 클라이언트 |

`Pair`에는 `IQueryable<T>`를 받는 오버로드가 없다. 덜 구체적인 `IEnumerable<T>` 매개변수에 바인딩될 수밖에 없고, 그 순간 해석되는 쿼리가 로컬 쿼리의 소스로 **감싸진다.** 반환 타입도 `IEnumerable`이므로 그 뒤의 `Select`도 로컬 연산자가 된다.

EF Core 쪽이 생성하는 SQL은 `Pair` 이전까지다.

```sql
SELECT UPPER([c].[Name]) FROM [Customer] AS [c] ORDER BY UPPER([c].[Name])
```

나머지는 클라이언트에서 처리된다. 결과적으로 **안쪽이 해석 쿼리, 바깥쪽이 로컬 쿼리**인 이중 구조가 된다.

### `AsEnumerable` — 경계를 명시적으로 긋는 도구

경계를 우연이 아니라 **의도적으로** 긋고 싶을 때 쓰는 것이 `AsEnumerable`이다. 전체 정의는 이게 전부다.

```csharp
public static IEnumerable<TSource> AsEnumerable<TSource> (
    this IEnumerable<TSource> source)
{
    return source;
}
```

인자를 그대로 돌려준다. 런타임에 하는 일이 없다. 유일한 효과는 **정적 타입을 `IEnumerable<T>`로 낮춰서, 그 뒤의 연산자들이 `Queryable`이 아니라 `Enumerable`에 바인딩되게 하는 것**이다. 30.8절에서 본 그 메서드가 여기서 진가를 발휘한다.

### 실전 — SQL이 못 하는 일을 클라이언트에 맡기기

SQL Server에 `MedicalArticles` 테이블이 있고, 주제가 "influenza"이면서 초록이 100단어 미만인 논문을 찾고 싶다. 단어 수 세기에는 정규식이 필요하다.

```csharp
using System.Text.RegularExpressions;

Regex wordCounter = new Regex (@"\b(\w|[-'])+\b");

using var dbContext = new NutshellContext();

var query = dbContext.MedicalArticles
    .Where (article => article.Topic == "influenza" &&
                       wordCounter.Matches (article.Abstract).Count < 100);
```

SQL Server는 정규식을 지원하지 않으므로 EF Core는 이 쿼리를 SQL로 옮기지 못한다. 열거하면 예외가 난다.

가장 단순한 해법은 쿼리를 둘로 쪼개는 것이다.

```csharp
IEnumerable<MedicalArticle> efQuery = dbContext.MedicalArticles
    .Where (article => article.Topic == "influenza");

IEnumerable<MedicalArticle> localQuery = efQuery
    .Where (article => wordCounter.Matches (article.Abstract).Count < 100);
```

`efQuery`의 **정적 타입을 `IEnumerable<MedicalArticle>`로 선언했다**는 점이 핵심이다. 그래서 두 번째 `Where`는 로컬 연산자에 바인딩되고, 정규식 필터가 클라이언트에서 돈다.

`AsEnumerable`을 쓰면 같은 일을 한 문장으로 쓸 수 있다.

```csharp
var query = dbContext.MedicalArticles
    .Where (article => article.Topic == "influenza")
    .AsEnumerable()
    .Where (article => wordCounter.Matches (article.Abstract).Count < 100);
```

`.AsEnumerable()`이 있는 자리가 **국경선**이다. 그 위쪽은 SQL로, 아래쪽은 C#으로 실행된다.

### `AsEnumerable` vs `ToList`/`ToArray`

경계를 긋는 다른 방법은 `ToList()`나 `ToArray()`다. 셋의 차이는 분명하다.

| | `AsEnumerable()` | `ToList()` / `ToArray()` |
|---|---|---|
| 즉시 실행 | 하지 않는다 (여전히 지연) | **한다** — 그 자리에서 쿼리가 실행된다 |
| 저장 구조 생성 | 없다 | 리스트/배열 하나를 할당하고 전부 채운다 |
| 메모리 | 스트리밍 — 한 번에 한 행 | 결과 전체가 메모리에 |
| 이후 연산자 바인딩 | `Enumerable` | `Enumerable` |
| 결과 재사용 | 열거할 때마다 다시 쿼리 | 한 번 담아 두고 여러 번 순회 가능 |

경계만 긋는 것이 목적이라면 `AsEnumerable()`이 정답이다. 즉시 실행을 강제하지도, 저장 구조를 만들지도 않기 때문이다. 반대로 결과를 여러 번 순회하거나, `DbContext`를 곧 폐기할 예정이거나, 같은 컨텍스트로 다른 쿼리를 실행해야 한다면 `ToList()`가 맞다.

> **⚠️ `AsEnumerable()`의 위치가 곧 성능이다**
>
> 두 코드의 차이는 점 하나의 위치뿐이다.
>
> ```csharp
> // (A) 필요한 행만 온다
> dbContext.Products.Where (p => p.Price > 100).AsEnumerable().Select (Format);
>
> // (B) 테이블 전체가 온다
> dbContext.Products.AsEnumerable().Where (p => p.Price > 100).Select (Format);
> ```
>
> 결과는 같다. (B)는 1,000만 행 테이블에서 1,000만 행을 네트워크로 끌어와 클라이언트 메모리에 올린 뒤 999만 9천 행을 버린다. 오류도 예외도 없이, 그냥 느릴 뿐이다.
>
> **규칙: 서버가 할 수 있는 일은 전부 경계 위에 놓아라.** 특히 `Where`, `OrderBy`, `Skip`/`Take`, 집계는 경계 위에 있어야 한다.

> **⚠️ 경계 아래의 `Count()`와 `OrderBy`는 조용한 재앙이다**
>
> ```csharp
> int n = dbContext.Orders.AsEnumerable().Count (o => o.Total > 1000);
> ```
>
> 이 한 줄은 `SELECT COUNT(*) FROM Orders WHERE Total > 1000` 대신 **모든 주문 행을 전송한 뒤 클라이언트에서 센다.** 정렬도 마찬가지다. 서버는 인덱스로 정렬하지만 클라이언트는 전체를 메모리에 올려 놓고 정렬한다. 페이징(`Skip`/`Take`)이 경계 아래로 내려가면 최악이다 — 21~40번째 행을 얻으려고 전체를 가져온다.

> **📌 더 나은 해법이 있는 경우도 있다**
>
> 정규식 예제처럼 "데이터베이스가 못 하는 일"이 병목이라면, 처리를 클라이언트로 옮기는 것보다 **데이터베이스에 그 능력을 추가하는 것**이 나을 때가 있다. SQL Server의 CLR 통합으로 정규식 함수를 서버에 노출하면 필터가 서버에 남는다. 복잡도는 올라가지만 전송량이 줄어든다. 전송량이 지배적인 비용이면 검토할 가치가 있다.

> **💡 경계는 눈에 보이게 만들어라**
>
> `AsEnumerable()` 호출은 코드 리뷰에서 반드시 눈에 띄어야 한다. 다음 두 규율을 권한다.
>
> 1. `AsEnumerable()` 바로 위 줄에 **왜 여기서 경계를 긋는지** 주석을 단다("정규식은 SQL로 번역 불가").
> 2. 경계 위에 필터가 하나도 없는 `AsEnumerable()`은 리뷰에서 막는다. 그건 십중팔구 전체 테이블 스캔이다.
>
> 30.15절에서 다룬 LINQ 성능 규칙 중 원격 쿼리에 관한 것은 거의 전부 이 한 줄의 위치 문제로 환원된다.

## 31.6 식 트리를 코드로 만들기 — 동적 쿼리 빌더

### 문제 — 검색 화면

사용자가 이름·가격·단종 여부·최종 판매일 중 **아무거나 골라** 조건을 넣는 검색 화면을 생각하자. 조합은 지수적으로 늘어난다. 조건마다 쿼리를 손으로 쓸 수는 없다.

29.9절에서 본 **점진적 합성**이 첫 번째 답이다. 지연 실행 덕분에 조건부로 연산자를 붙여 나가도 데이터베이스에는 한 번만 간다.

```csharp
IQueryable<Product> Search (NutshellContext db, string? name, decimal? maxPrice, bool? discontinued)
{
    IQueryable<Product> q = db.Products;

    if (!string.IsNullOrWhiteSpace (name))
        q = q.Where (p => p.Description.Contains (name));

    if (maxPrice is decimal max)
        q = q.Where (p => p.Price <= max);

    if (discontinued is bool d)
        q = q.Where (p => p.Discontinued == d);

    return q;
}
```

**대부분의 경우 여기서 끝내는 것이 옳다.** 읽기 쉽고, 컴파일러가 타입을 검사해 주고, 트리 조립 코드가 한 줄도 없다.

한계는 두 가지다.

1. **`AND`만 된다.** 연산자를 이어 붙이면 조건이 항상 `AND`로 결합된다. "이름이 A로 시작 **또는** 가격이 100 미만"을 동적으로 만들 수 없다.
2. **컬럼 이름이 런타임에 정해지면 못 쓴다.** 정렬 기준 컬럼을 사용자가 고르는 경우 `p => p.???`를 컴파일 타임에 쓸 방법이 없다.

이 둘이 트리를 직접 조립해야 하는 이유다.

### 첫 시도 — 그리고 첫 실패

두 술어를 `OR`로 묶어 보자.

```csharp
Expression<Func<Product, bool>> e1 = p => p.Description.StartsWith ("A");
Expression<Func<Product, bool>> e2 = p => p.Price < 100;

var body = Expression.OrElse (e1.Body, e2.Body);                     // 여기까지는 통과
var combined = Expression.Lambda<Func<Product, bool>> (body, e1.Parameters);
```

이 코드는 트리를 만들기까지는 성공한다. 그러나 `Compile()`하거나 EF Core에 넘기는 순간 `InvalidOperationException`이 난다. 메시지의 요지는 "`p`라는 변수가 참조되었지만 정의되어 있지 않다"다.

이유는 **`e1`의 `p`와 `e2`의 `p`가 서로 다른 객체이기 때문**이다.

```csharp
Console.WriteLine (ReferenceEquals (e1.Parameters[0], e2.Parameters[0]));   // False
```

`ParameterExpression`은 이름으로 식별되지 않는다. **참조 동일성으로 식별된다.** 이름이 둘 다 `"p"`라는 것은 표시용 정보일 뿐이다. 우리가 만든 람다는 `e1.Parameters[0]`만 매개변수로 선언했으므로, 본문 오른쪽에 남아 있는 `e2`의 `p`는 어디에서도 정의되지 않은 자유 변수가 된다.

> **⚠️ 이름이 같아도 다른 매개변수다**
>
> 동적 쿼리 빌더를 처음 쓸 때 100% 만나는 예외다. `Expression.Parameter(typeof(Product), "p")`를 두 번 호출하면 **서로 다른 두 매개변수**가 나온다. 팩토리는 캐시하지 않는다. 트리를 합칠 때는 **한쪽의 매개변수로 다른 쪽을 다시 쓰거나(재사용)**, **한쪽의 매개변수를 다른 쪽 것으로 치환해야(치환)** 한다.

### 해법 1 — 매개변수 재사용

가장 단순한 해법은 애초에 매개변수를 하나만 만들어 양쪽이 공유하게 하는 것이다. 트리를 전부 손으로 조립할 때 자연스럽게 이렇게 된다.

```csharp
using System;
using System.Linq.Expressions;
using System.Reflection;

// p => p.Description.Contains(keyword) && p.Price <= maxPrice 를 손으로 만든다
static Expression<Func<Product, bool>> BuildPredicate (string keyword, decimal maxPrice)
{
    // 매개변수는 딱 하나. 모든 하위 식이 이것을 공유한다.
    ParameterExpression p = Expression.Parameter (typeof (Product), "p");

    MethodInfo containsMethod =
        typeof (string).GetMethod (nameof (string.Contains), new[] { typeof (string) })!;

    // p.Description.Contains(keyword)
    Expression left = Expression.Call (
        Expression.Property (p, nameof (Product.Description)),
        containsMethod,
        Expression.Constant (keyword, typeof (string)));

    // p.Price <= maxPrice
    Expression right = Expression.LessThanOrEqual (
        Expression.Property (p, nameof (Product.Price)),
        Expression.Constant (maxPrice, typeof (decimal)));

    return Expression.Lambda<Func<Product, bool>> (
        Expression.AndAlso (left, right), p);
}
```

```csharp
var pred = BuildPredicate ("bike", 500m);
Console.WriteLine (pred);
// p => (p.Description.Contains("bike") AndAlso (p.Price <= 500))

var results = dbContext.Products.Where (pred).ToList();   // SQL로 번역된다
```

`nameof`를 쓴 점을 눈여겨보라. 프로퍼티 이름을 문자열 리터럴로 박으면 리팩터링에서 조용히 깨진다.

> **⚠️ `Expression.Property`는 이름이 틀리면 `ArgumentException`을 던진다**
>
> 존재하지 않는 프로퍼티 이름을 넘기면 트리를 만드는 시점에 `ArgumentException`이 난다. 사용자 입력을 그대로 프로퍼티 이름으로 쓰는 정렬 기능을 만든다면 **반드시 화이트리스트로 검증하라.** 검증 없이 넘기면 (1) 예외가 사용자에게 노출되고, (2) 매핑되지 않은 내부 프로퍼티를 통해 의도치 않은 데이터가 새어 나갈 수 있다.

### 해법 2 — `ExpressionVisitor`로 매개변수 치환

이미 있는 두 람다를 합쳐야 한다면 치환이 답이다. 방문자 하나면 된다.

```csharp
using System.Linq.Expressions;

sealed class ParameterReplacer : ExpressionVisitor
{
    private readonly ParameterExpression _from, _to;

    public ParameterReplacer (ParameterExpression from, ParameterExpression to)
        => (_from, _to) = (from, to);

    protected override Expression VisitParameter (ParameterExpression node)
        => node == _from ? _to : base.VisitParameter (node);

    public static Expression Replace (Expression body, ParameterExpression from, ParameterExpression to)
        => new ParameterReplacer (from, to).Visit (body);
}
```

이제 두 술어를 `AND`/`OR`로 안전하게 결합하는 유틸리티를 만들 수 있다.

```csharp
using System;
using System.Linq.Expressions;

public static class PredicateBuilder
{
    public static Expression<Func<T, bool>> True<T>()  => _ => true;
    public static Expression<Func<T, bool>> False<T>() => _ => false;

    public static Expression<Func<T, bool>> And<T> (
        this Expression<Func<T, bool>> first,
        Expression<Func<T, bool>> second)
        => Combine (first, second, Expression.AndAlso);

    public static Expression<Func<T, bool>> Or<T> (
        this Expression<Func<T, bool>> first,
        Expression<Func<T, bool>> second)
        => Combine (first, second, Expression.OrElse);

    public static Expression<Func<T, bool>> Not<T> (
        this Expression<Func<T, bool>> expression)
        => Expression.Lambda<Func<T, bool>> (
               Expression.Not (expression.Body), expression.Parameters);

    private static Expression<Func<T, bool>> Combine<T> (
        Expression<Func<T, bool>> first,
        Expression<Func<T, bool>> second,
        Func<Expression, Expression, BinaryExpression> merge)
    {
        // 첫 번째 람다의 매개변수를 정본으로 삼는다
        ParameterExpression p = first.Parameters[0];

        // 두 번째 람다의 본문에서 그쪽 매개변수를 p로 치환한다
        Expression secondBody = ParameterReplacer.Replace (
            second.Body, second.Parameters[0], p);

        return Expression.Lambda<Func<T, bool>> (merge (first.Body, secondBody), p);
    }
}
```

사용은 자연스럽다.

```csharp
var predicate = PredicateBuilder.False<Product>();

foreach (string keyword in userKeywords)
{
    string temp = keyword;                                // 클로저 캡처 주의 (29.7절)
    predicate = predicate.Or (p => p.Description.Contains (temp));
}

var matches = dbContext.Products.Where (predicate).ToList();
```

`OR` 누적의 시작값은 `False<T>()`, `AND` 누적의 시작값은 `True<T>()`다. 항등원을 헷갈리면 결과가 전부 비거나 전부 통과한다.

> **⚠️ 루프 변수를 그대로 캡처하지 마라**
>
> `foreach` 변수를 람다 안에서 직접 캡처하는 코드는 C# 5 이전 컴파일러에서 전혀 다른 결과를 냈다. 지금은 `foreach` 변수가 반복마다 새로 만들어지므로 안전하지만, `for` 루프 변수는 여전히 **하나의 변수를 공유**한다. 트리를 누적하는 코드에서 이 실수를 하면 모든 조건이 마지막 값 하나로 수렴한다. 29.7절의 캡처 규칙이 여기에 그대로 적용된다.

> **📌 `Expression.Invoke`를 쓰는 다른 접근**
>
> 매개변수 치환 대신 `Expression.Invoke(second, first.Parameters)`로 두 번째 람다를 **호출**하는 트리를 만드는 방법도 있다. 코드는 더 짧다.
>
> ```csharp
> var body = Expression.AndAlso (
>     first.Body, Expression.Invoke (second, first.Parameters));
> ```
>
> 로컬 실행(`Compile()`)에서는 잘 동작한다. 그러나 `InvocationExpression`을 번역하지 못하는 공급자가 있다 — 람다 호출은 SQL에 대응물이 없기 때문이다. 공급자에 무관하게 통하는 것은 **치환** 쪽이다. 트리에 흔적을 남기지 않기 때문이다.

### 동적 정렬 — 연산자 호출 자체를 조립하기

정렬 기준 컬럼이 런타임 문자열로 온다면 술어 조립만으로는 부족하다. `Queryable.OrderBy` **호출 노드**를 직접 만들어야 한다.

```csharp
using System;
using System.Linq;
using System.Linq.Expressions;
using System.Reflection;

public static class QueryableSortExtensions
{
    private static readonly string[] Allowed = { "Description", "Price", "LastSale" };

    public static IQueryable<T> OrderByProperty<T> (
        this IQueryable<T> source, string propertyName, bool descending = false)
    {
        if (Array.IndexOf (Allowed, propertyName) < 0)
            throw new ArgumentException ($"정렬할 수 없는 컬럼: {propertyName}", nameof (propertyName));

        // x => x.PropertyName  형태의 키 선택자를 만든다
        ParameterExpression x = Expression.Parameter (typeof (T), "x");
        MemberExpression body = Expression.Property (x, propertyName);
        LambdaExpression keySelector = Expression.Lambda (body, x);

        string methodName = descending ? nameof (Queryable.OrderByDescending)
                                       : nameof (Queryable.OrderBy);

        // Queryable.OrderBy<T, TKey>(source, keySelector) 호출 노드
        MethodCallExpression call = Expression.Call (
            typeof (Queryable),
            methodName,
            new[] { typeof (T), body.Type },     // 제네릭 타입 인자 2개
            source.Expression,                   // 지금까지의 쿼리 트리
            Expression.Quote (keySelector));     // 람다는 Quote로 감싼다

        return source.Provider.CreateQuery<T> (call);
    }
}
```

```csharp
var page = dbContext.Products
    .Where (p => !p.Discontinued)
    .OrderByProperty ("Price", descending: true)
    .Skip (20).Take (20)
    .ToList();
```

여기서 배울 점이 세 가지다.

1. **`Expression.Call`의 제네릭 오버로드**가 메서드 이름과 타입 인자로 `MethodInfo`를 찾아 준다. `Queryable`의 오버로드를 리플렉션으로 직접 골라내는 지옥을 피할 수 있다.
2. **람다 인자는 `Expression.Quote`로 감싼다.** `Queryable` 연산자의 매개변수 타입이 `Expression<Func<...>>`이기 때문이다(31.3절).
3. **`source.Provider.CreateQuery<T>`로 새 `IQueryable`을 얻는다.** 이것이 `Queryable`의 모든 연산자가 내부에서 하는 일이다. 우리는 그 패턴을 그대로 따라 했을 뿐이다.

> **⚠️ 이것은 "새 연산자"가 아니라 "표준 연산자 조립기"다**
>
> 31.3절에서 "`IQueryable<T>`용 커스텀 연산자를 만들지 말라"고 했다. `OrderByProperty`는 그 금기를 어기지 않는다. **트리에 남는 것은 표준 `Queryable.OrderBy` 호출뿐**이기 때문이다. 공급자는 우리 확장 메서드의 존재를 알 필요가 없다. 이것이 안전한 동적 쿼리 빌더의 유일한 형태다 — 확장은 **조립 단계**에만 존재하고 **트리에는 흔적을 남기지 않는다.**

### 성능 영향 — 트리 조립과 쿼리 캐시

동적 빌더의 비용은 두 군데에 있다.

**첫째, 조립 자체의 할당.** 노드 하나하나가 힙 객체다. 리플렉션 조회(`GetMethod`, `GetProperty`)도 섞인다. 요청당 수십 개 노드 수준이면 무시할 만하지만, 반복 호출되는 경로라면 `MethodInfo`를 `static readonly` 필드에 캐시하라(57.12절의 리플렉션 캐싱 원칙과 같다).

**둘째, 공급자의 쿼리 캐시.** EF Core는 식 트리의 **모양**을 키로 삼아 번역 결과(SQL과 실체화 코드)를 캐시한다. 모양이 같고 파라미터 값만 다르면 캐시가 적중한다. 그런데 값을 `Expression.Constant`로 트리에 직접 박으면 **값마다 모양이 달라진다.**

```csharp
// 값이 바뀔 때마다 다른 트리 → 캐시 미스 → 매번 재번역
Expression.Constant (maxPrice, typeof (decimal))
```

캡처된 변수에서 온 값은 다르다. 트리에는 "디스플레이 클래스의 필드 접근"만 남고(31.2절), 공급자가 그 부분식을 평가해 **SQL 파라미터**로 만든다. 트리 모양은 값과 무관하게 동일하다.

> **💡 동적으로 만든 상수도 파라미터로 만드는 법**
>
> 값을 `Expression.Constant`로 직접 박는 대신, 값을 담은 작은 홀더 객체를 만들고 그 프로퍼티 접근을 트리에 넣으면 캡처 변수와 같은 모양이 된다.
>
> ```csharp
> sealed class Box<T> { public T Value = default!; }
>
> static Expression ValueOf<T> (T value)
> {
>     var box = new Box<T> { Value = value };
>     return Expression.Field (Expression.Constant (box), nameof (box.Value));
> }
> ```
>
> `Expression.Constant(maxPrice)` 대신 `ValueOf(maxPrice)`를 쓰면 트리 모양이 값에 무관해지고, 공급자는 이를 파라미터로 승격시킨다. ※ 이 기법의 효과는 공급자 구현에 의존하므로, 도입 전에 `ToQueryString()`으로 리터럴이 파라미터로 바뀌는지 확인하라.

> **⚠️ 쿼리 캐시 폭발의 증상**
>
> 값마다 다른 트리를 만들면 캐시 항목이 무한히 늘어난다. 증상은 (1) 메모리 사용량이 계단식으로 증가하고, (2) 같은 쿼리인데 매번 번역 비용이 들며, (3) 데이터베이스 쪽에서도 실행 계획 캐시가 오염된다. 파라미터화된 SQL이 나오는지 로그로 확인하는 것이 유일한 예방법이다.

> **💡 언제 동적 빌더를 쓰지 말아야 하는가**
>
> 조건 조합이 대여섯 개 수준이면 조건부 연산자 체이닝이 낫다. 트리 조립 코드는 타입 검사를 컴파일러가 아니라 런타임이 하고, 디버깅이 어렵고, 읽는 사람이 적다. **`OR` 결합이 필요하거나 컬럼 이름이 런타임에 정해질 때만** 내려가라. 그 외에는 29.9절의 점진적 합성으로 충분하다.

## 31.7 EF Core에서 LINQ가 SQL이 되기까지

### 파이프라인 전경

EF Core는 이 장에서 설명한 구조 위에 세워진 가장 널리 쓰이는 `IQueryable` 공급자다. LINQ 쿼리 하나가 SQL이 되어 돌아오기까지의 흐름은 다음과 같다.

```text
   ┌──────────────────────────────────────────────────────────────────┐
   │ ① 모델 구축 (DbContext 최초 사용 시 1회)                          │
   │    규약 + 특성 + Fluent API  →  IModel (엔티티↔테이블 매핑)       │
   └────────────────────────────┬─────────────────────────────────────┘
                                ↓
   ┌──────────────────────────────────────────────────────────────────┐
   │ ② 쿼리 트리 누적 (Queryable 연산자 호출마다)                      │
   │    MethodCallExpression 중첩 — 아직 아무 일도 안 일어난다         │
   └────────────────────────────┬─────────────────────────────────────┘
                                ↓  열거 / ToList / Count …
   ┌──────────────────────────────────────────────────────────────────┐
   │ ③ 파라미터 추출 · 캐시 키 계산                                    │
   │    캡처 변수 부분식 → 파라미터로 승격, 남은 트리 모양이 캐시 키   │
   └────────────────────────────┬─────────────────────────────────────┘
                                ↓  캐시 적중이면 ⑥으로 직행
   ┌──────────────────────────────────────────────────────────────────┐
   │ ④ 번역 — ExpressionVisitor 파이프라인                             │
   │    탐색 속성 확장 → 쿼리 필터 적용 → 관계 대수 트리 → SQL 트리    │
   └────────────────────────────┬─────────────────────────────────────┘
                                ↓
   ┌──────────────────────────────────────────────────────────────────┐
   │ ⑤ SQL 문자열 생성 + 실체화(materialization) 코드 생성 → 캐시 저장 │
   └────────────────────────────┬─────────────────────────────────────┘
                                ↓
   ┌──────────────────────────────────────────────────────────────────┐
   │ ⑥ 실행 — DbCommand 실행, DbDataReader → 엔티티 인스턴스           │
   │    추적이 켜져 있으면 ChangeTracker에 등록 + ID 해석              │
   └──────────────────────────────────────────────────────────────────┘
```

각 단계를 짚어 보자.

### ① 모델 — 트리를 번역할 사전

EF Core가 트리를 SQL로 옮기려면 "`Product`는 어느 테이블이고 `Cost`는 어느 컬럼인가"를 알아야 한다. 그 지식이 **모델**이고, 모델은 세 가지 재료로 만들어진다.

| 방법 | 어디에 쓰는가 | 특징 |
|---|---|---|
| 규약(convention) | 기본값 | 이름 규칙으로 추론. 코드가 0줄 |
| 특성(data annotation) | 엔티티 클래스에 부착 | 간단하지만 **컴파일 타임 고정**, 표현력 제한 |
| Fluent API | `OnModelCreating` | 가장 강력. 엔티티 클래스를 깨끗하게 유지 |

모델은 `DbContext` 타입마다 한 번 만들어져 캐시된다. 그래서 첫 쿼리가 느리고("첫 실행 페널티") 그 다음부터 빠르다.

### ② 트리 누적과 ③ 파라미터 추출

31.2절에서 본 것이 여기서 결정적으로 쓰인다. 캡처된 지역 변수는 트리에 `Constant(디스플레이 클래스) → MemberAccess(필드)` 형태로 남는다. EF Core는 **매개변수 `p`에 의존하지 않는 부분식**(evaluatable subtree)을 찾아 그 자리에서 평가하고, 결과를 SQL 파라미터로 승격시킨다.

p810의 실측 출력에서 이것을 그대로 볼 수 있다.

```csharp
IQueryable<Category>? categories = db.Categories?
    .Include (c => c.Products.Where (p => p.Stock >= stock));   // stock은 지역 변수
```

```sql
.param set @__stock_0 95

SELECT "c"."CategoryId", "c"."CategoryName", "c"."Description",
       "t"."ProductId", "t"."CategoryId", "t"."UnitPrice",
       "t"."Discontinued", "t"."ProductName", "t"."UnitsInStock"
FROM "Categories" AS "c"
LEFT JOIN (
    SELECT "p"."ProductId", "p"."CategoryId", "p"."UnitPrice",
           "p"."Discontinued", "p"."ProductName", "p"."UnitsInStock"
    FROM "Products" AS "p"
    WHERE "p"."UnitsInStock" >= @__stock_0
) AS "t" ON "c"."CategoryId" = "t"."CategoryId"
ORDER BY "c"."CategoryId"
```

`@__stock_0`이라는 이름이 힌트다. `__` 뒤가 원래 변수 이름, 마지막 숫자가 일련번호다. **변수 이름이 SQL 파라미터 이름에 그대로 나타난다**는 사실만으로도, EF Core가 트리에서 무엇을 읽었는지 알 수 있다.

같은 쿼리를 `stock = 100`으로 다시 실행하면 트리 모양이 같으므로 ④⑤를 건너뛰고 캐시된 SQL에 파라미터만 바꿔 넣는다.

> **📌 SQL Server와 SQLite의 출력 차이**
>
> 같은 LINQ 쿼리라도 공급자가 다르면 SQL이 다르다. SQL Server 공급자는 식별자를 대괄호로 감싸고 파라미터를 `DECLARE`로 선언한다.
>
> ```sql
> DECLARE @__stock_0 smallint = CAST(95 AS smallint);
> SELECT [c].[CategoryId], ... FROM [Categories] AS [c]
> LEFT JOIN ( ... WHERE [p].[UnitsInStock] >= @__stock_0 ) AS [t]
>     ON [c].[CategoryId] = [t].[CategoryId]
> ORDER BY [c].[CategoryId]
> ```
>
> 같은 코드가 데이터베이스마다 다른 SQL을 만든다는 것이 `IQueryable` 추상화의 요점이자, "SQL을 안 봐도 된다"는 착각의 근원이다.

### 생성된 SQL을 눈으로 보는 세 가지 방법

**(1) `ToQueryString()`** — 실행하지 않고 문자열만 얻는다.

```csharp
IQueryable<Product>? products = db.Products?
    .Where (p => p.Cost > price)
    .OrderByDescending (p => p.Cost);

Console.WriteLine (products.ToQueryString());
```

**(2) `LogTo`** — 실제 실행되는 명령을 전부 로그로 흘린다.

```csharp
protected override void OnConfiguring (DbContextOptionsBuilder optionsBuilder)
{
    optionsBuilder.UseSqlite (connectionString);

    optionsBuilder.LogTo (Console.WriteLine)
#if DEBUG
        .EnableSensitiveDataLogging()   // 파라미터 값까지 로그에 포함
        .EnableDetailedErrors()
#endif
        ;
}
```

`LogTo`는 `Action<string>` 델리게이트를 받는다. `Console.WriteLine` 메서드 그룹을 그대로 넘길 수 있다(26.3절의 메서드 그룹 변환).

**(3) `TagWith()`** — 로그에서 어느 코드가 만든 쿼리인지 찾기 위해 SQL 주석을 심는다.

```csharp
IQueryable<Product>? products = db.Products?
    .TagWith ("Products filtered by price and sorted.")
    .Where (p => p.Cost > price)
    .OrderByDescending (p => p.Cost);
```

```sql
-- Products filtered by price and sorted.
SELECT ...
```

> **⚠️ `EnableSensitiveDataLogging`을 운영에 켜 두지 마라**
>
> 이 스위치는 파라미터 값을 로그에 그대로 찍는다. 주민등록번호, 이메일, 비밀번호 해시 같은 값이 평문 로그로 흘러나간다. 개발 구성에서만 켜야 하며, 위 예제처럼 `#if DEBUG`로 감싸는 것이 안전하다.

### ④ 번역 — 방문자들의 행렬

번역 단계는 이 장에서 배운 `ExpressionVisitor`의 대규모 응용이다. EF Core는 트리를 여러 번 훑으면서 단계적으로 변형한다. 개념적 순서는 대략 이렇다.

1. **탐색 속성 확장** — `c.Products`는 조인으로, `Include`는 `LEFT JOIN`이나 별도 쿼리로 바뀐다.
2. **전역 쿼리 필터 주입** — `HasQueryFilter`로 등록한 술어를 모든 접근 지점에 `AND`로 끼워 넣는다.
3. **평가 가능한 부분식 추출** — ③에서 설명한 파라미터화.
4. **관계 대수 형태로 정규화** — `Where`/`Select`/`Join`을 SELECT 절·FROM 절·WHERE 절에 해당하는 내부 표현으로 옮긴다.
5. **번역 시도와 실패 판정** — 옮길 수 없는 노드를 만나면 여기서 예외를 만든다.

여기서 나오는 예외가 `InvalidOperationException`이고, 메시지는 번역하지 못한 **부분식을 그대로 인용**한다. 예외 메시지에서 인용된 식이 진단의 출발점이다.

> **⚠️ 클라이언트 평가는 최상위 투영에서만**
>
> 31.4절에서 다룬 규칙을 다시 강조한다. EF Core 3.0부터 필터·정렬·조인·그룹 키 안의 클라이언트 코드는 **예외**다. 마지막 `Select` 안에서만 허용된다. 이 변화는 "느리지만 동작하는 코드"를 "즉시 실패하는 코드"로 바꾼 의도적 파괴적 변경이며, EF Core 2.x에서 올라오는 마이그레이션에서 가장 많은 코드 수정을 유발한 지점이다.

### 전역 쿼리 필터

모델에 술어를 등록해 두면 해당 엔티티에 대한 **모든** 쿼리에 자동으로 붙는다. 소프트 삭제나 멀티테넌시에 쓴다.

```csharp
protected override void OnModelCreating (ModelBuilder modelBuilder)
{
    // 단종된 제품은 어떤 쿼리에서도 나오지 않는다
    modelBuilder.Entity<Product>()
        .HasQueryFilter (p => !p.Discontinued);
}
```

이제 `Where`를 쓰지 않아도 SQL에 조건이 붙는다.

```sql
SELECT "p"."ProductId", "p"."CategoryId", "p"."UnitPrice",
       "p"."Discontinued", "p"."ProductName", "p"."UnitsInStock"
FROM "Products" AS "p"
WHERE NOT ("p"."Discontinued") AND ("p"."ProductName" LIKE @__Format_1)
```

> **⚠️ 전역 필터는 "왜 데이터가 안 나오지"의 1순위 용의자다**
>
> 필터는 모델에 숨어 있고 쿼리 코드에는 나타나지 않는다. 데이터베이스에는 분명히 행이 있는데 쿼리 결과가 비어 있다면 `OnModelCreating`을 먼저 확인하라. 개별 쿼리에서 필터를 무시하려면 `IgnoreQueryFilters()`를 체인에 넣는다. 관리자 화면처럼 전체를 봐야 하는 경로에서만 쓰고, 그 사실을 주석으로 남겨라.

### 데이터베이스 함수 노출 — `EF.Functions`

SQL에는 있지만 .NET에는 대응물이 없는 함수는 `EF.Functions`를 통해 노출된다. 이 프로퍼티에 붙은 메서드들은 **호출하라고 있는 것이 아니라 트리에 노드를 남기라고 있는 것**이다. 로컬에서 직접 부르면 예외가 난다.

```csharp
// LIKE 패턴 매칭
IQueryable<Product>? products = db.Products?
    .Where (p => EF.Functions.Like (p.ProductName, $"%{input}%"));
```

```sql
SELECT ... FROM "Products" AS "p" WHERE "p"."ProductName" LIKE @__Format_1
```

`EF.Functions.Random()`(※EF Core 6)은 데이터베이스의 난수 함수로 번역된다. 행 수를 곱해 무작위 행 하나를 서버에서 고르는 데 쓸 수 있다. SQLite 공급자는 이를 `abs(random() / 9.2233720368547799E+18)` 형태로 옮긴다.

### `First`와 `Single`의 번역 차이

30.13절에서 "의미를 강제하라"고 했던 두 연산자는 SQL에서 실제로 다르게 번역된다.

```sql
-- db.Products.First (p => p.ProductId == id)
SELECT ... FROM "Products" AS "p" WHERE ... AND "p"."ProductId" = @__id_0 LIMIT 1

-- db.Products.Single (p => p.ProductId == id)
SELECT ... FROM "Products" AS "p" WHERE ... AND "p"."ProductId" = @__id_0 LIMIT 2
```

`First`는 하나만 가져오면 되지만, `Single`은 "둘 이상이면 예외"를 판정해야 하므로 **두 행을 요청해서 두 번째가 있는지 확인해야 한다.** 그래서 `LIMIT 2`다.

> **💡 기본 키로 한 행을 읽을 때의 선택**
>
> 중복이 없음을 보장할 필요가 없다면 `First`가 낫다. 두 행을 읽지 않기 때문이다. 반대로 "여기서 두 행이 나오면 데이터가 손상된 것"이라는 불변식을 코드로 강제하고 싶다면 `Single`이 옳다. 한 행을 더 읽는 비용으로 버그를 조기에 잡는 거래다.

### 컴파일된 쿼리와 분할 쿼리

**컴파일된 쿼리**는 ③~⑤를 애플리케이션 시작 시점에 한 번 해 두고 델리게이트로 들고 다니는 기법이다. 캐시 조회 비용까지 없애므로 초고빈도 쿼리에서 의미가 있다.

```csharp
private static readonly Func<NorthwindDb, int, Product?> GetProductById =
    EF.CompileQuery ((NorthwindDb db, int id) =>
        db.Products.FirstOrDefault (p => p.ProductId == id));

// 사용
Product? p = GetProductById (db, 42);
```

**분할 쿼리**는 `Include`가 만드는 카티전 폭발을 피하는 옵션이다. 컬렉션 탐색 속성을 여러 개 `Include`하면 조인 결과 행 수가 곱해지면서 같은 부모 데이터가 수십 번 반복 전송된다. `AsSplitQuery()`를 붙이면 EF Core가 쿼리를 여러 개로 나눠 보낸다. ※.NET 5 시대의 EF Core 5부터.

```csharp
var categories = db.Categories
    .Include (c => c.Products)
    .AsSplitQuery()
    .ToList();
```

> **⚠️ 분할 쿼리는 원자성을 잃는다**
>
> 쿼리가 여러 개로 나뉘면 그 사이에 다른 트랜잭션이 데이터를 바꿀 수 있다. 단일 쿼리는 한 번의 스냅숏이지만 분할 쿼리는 아니다. 전송량과 일관성 사이의 거래이며, 기본값(단일 쿼리)을 바꾸기 전에 이 사실을 알고 있어야 한다.

> **📌 EF Core는 Native AOT를 아직 지원하지 않는다**
>
> 원천 도서 기준(EF Core 8 시점)으로 EF Core는 Native AOT 게시를 지원하지 않는다. 이 장에서 본 이유가 그대로 원인이다 — 쿼리 번역이 런타임 식 트리 순회와 동적 코드 생성에 의존하기 때문이다. 네이티브 컴파일이 필요하면 ADO.NET을 직접 쓰는 선택지가 남는다. EF Core 공급자들 자체가 ADO.NET(`DbConnection`, `DbCommand`, `DbDataReader`) 위에 얹혀 있으므로, ADO.NET은 언제나 EF Core보다 빠르다. 추상화의 대가를 지불하고 있다는 사실은 잊지 않는 편이 좋다.

## 31.8 EF Core 기초 — 엔티티, `DbContext`, 객체 추적, 변경 추적, 탐색 속성

이 절은 앞의 논의를 실제로 굴리는 데 필요한 최소한의 EF Core를 정리한다. 이 책은 데이터 접근서가 아니므로 마이그레이션·동시성 제어·성능 튜닝의 깊은 부분은 다루지 않는다. 목표는 **식 트리가 어디에서 어떻게 쓰이는지 볼 수 있을 만큼**이다.

### 엔티티 클래스

EF Core는 쿼리하려는 컬럼마다 public 프로퍼티가 있으면 **어떤 클래스든** 엔티티로 쓴다. 기반 클래스도, 인터페이스도, 특성도 필수가 아니다.

```csharp
public class Customer
{
    public int ID { get; set; }
    public string Name { get; set; } = "";
}
```

컬럼 전부를 매핑할 필요도 없다. 다만 매핑하지 않은 컬럼은 읽지도 쓰지도 못하므로, **새 행을 삽입할 때 그 컬럼들이 NULL 허용이거나 데이터베이스 기본값을 가져야** 한다. 아니면 런타임에 실패한다.

### `DbContext`

`DbContext` 파생 클래스 하나가 **데이터베이스와의 작업 세션 하나**를 나타낸다.

```csharp
using Microsoft.EntityFrameworkCore;

public class NorthwindDb : DbContext
{
    // 각 테이블마다 DbSet<T> 프로퍼티 하나
    public DbSet<Category> Categories { get; set; } = null!;
    public DbSet<Product> Products { get; set; } = null!;

    protected override void OnConfiguring (DbContextOptionsBuilder optionsBuilder)
    {
        string path = Path.Combine (Environment.CurrentDirectory, "Northwind.db");
        optionsBuilder.UseSqlite ($"Data Source={path}");
    }

    protected override void OnModelCreating (ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Category>()
            .Property (c => c.CategoryName)
            .IsRequired()          // NOT NULL
            .HasMaxLength (15);
    }
}
```

`DbContext`는 세 가지 일을 한다.

1. 쿼리할 수 있는 `DbSet<T>` 객체의 **팩토리**
2. 엔티티에 가한 변경의 **추적자** — `SaveChanges()`가 이 정보로 SQL을 만든다
3. 연결과 모델을 구성하는 **가상 메서드 제공자** — `OnConfiguring`, `OnModelCreating`, `ConfigureConventions`

`UseSqlite`·`UseSqlServer` 같은 메서드는 공급자 NuGet 패키지가 제공하는 확장 메서드다.

| 데이터 저장소 | NuGet 패키지 |
|---|---|
| SQL Server 2012+ | `Microsoft.EntityFrameworkCore.SqlServer` |
| SQLite 3.7+ | `Microsoft.EntityFrameworkCore.Sqlite` |
| 인메모리(테스트용) | `Microsoft.EntityFrameworkCore.InMemory` |
| Azure Cosmos DB SQL API | `Microsoft.EntityFrameworkCore.Cosmos` |
| MySQL | `MySQL.EntityFrameworkCore` |
| Oracle DB 11.2+ | `Oracle.EntityFrameworkCore` |
| PostgreSQL | `Npgsql.EntityFrameworkCore.PostgreSQL` |

한 프로젝트에서 여러 공급자를 동시에 참조할 수 있다.

> **📌 ASP.NET Core에서는 `OnConfiguring`을 안 쓴다**
>
> 의존성 주입 컨테이너가 옵션을 미리 구성해 주므로, 다음 생성자만 있으면 `OnConfiguring` 재정의가 불필요하다.
>
> ```csharp
> public NorthwindDb (DbContextOptions<NorthwindDb> options) : base (options) { }
> ```
>
> 두 경로를 모두 지원해야 한다면 이미 구성되었는지 확인하면 된다.
>
> ```csharp
> protected override void OnConfiguring (DbContextOptionsBuilder optionsBuilder)
> {
>     if (!optionsBuilder.IsConfigured) { /* ... */ }
> }
> ```

### 모델 구성 — 규약, 특성, Fluent API

기본은 **규약**이다. `DbSet<T>` 프로퍼티 이름이 테이블 이름, 프로퍼티 이름이 컬럼 이름, `Id`/`ID`/`<타입명>Id`가 기본 키가 된다. 키가 정수나 `Guid`면 자동 증가 컬럼으로 간주한다.

규약이 부족하면 **특성**을 붙인다.

```csharp
using System.ComponentModel.DataAnnotations;
using System.ComponentModel.DataAnnotations.Schema;

public class Product
{
    public int ProductId { get; set; }

    [Required]
    [StringLength (40)]
    public string ProductName { get; set; } = null!;

    // 프로퍼티 이름과 컬럼 이름이 다르고, 데이터베이스 타입도 지정
    [Column ("UnitPrice", TypeName = "money")]
    public decimal? Cost { get; set; }

    [Column ("UnitsInStock")]
    public short? Stock { get; set; }

    public bool Discontinued { get; set; }

    public int CategoryId { get; set; }
    public virtual Category Category { get; set; } = null!;
}
```

가장 강력한 것은 **Fluent API**다. `OnModelCreating`에서 `ModelBuilder`에 메서드를 체이닝한다.

```csharp
protected override void OnModelCreating (ModelBuilder modelBuilder) =>
    modelBuilder.Entity<Customer> (entity =>
    {
        entity.ToTable ("Customer");
        entity.Property (e => e.Name)
              .HasColumnName ("Full Name")
              .IsRequired();
    });
```

| 메서드 | 용도 | 예 |
|---|---|---|
| `ToTable` | 엔티티의 테이블 이름 지정 | `builder.Entity<Customer>().ToTable("Customer");` |
| `HasColumnName` | 프로퍼티의 컬럼 이름 지정 | `.Property(c => c.Name).HasColumnName("Full Name");` |
| `HasKey` | 규약을 벗어난 기본 키 지정 | `builder.Entity<Customer>().HasKey(c => c.CustomerNr);` |
| `IsRequired` | NOT NULL | `.Property(c => c.Name).IsRequired();` |
| `HasMaxLength` | 가변 길이 타입의 최대 길이 | `.Property(c => c.Name).HasMaxLength(60);` |
| `HasColumnType` | 컬럼의 데이터베이스 타입 | `.Property(p => p.Description).HasColumnType("varchar(80)");` |
| `Ignore` | 타입 또는 프로퍼티 매핑 제외 | `builder.Ignore<Products>();` / `.Ignore(c => c.ChatName);` |
| `HasIndex` | 인덱스 지정(복합·고유 포함) | `.HasIndex(p => new { p.Date, p.Price });` |
| `HasOne` / `HasMany` | 관계 구성 | `.HasOne(p => p.Customer).WithMany(c => c.Purchases);` |
| `HasData` | 초기 데이터 시딩 | `.HasData(new Product { ProductId = 1, ... });` |
| `HasQueryFilter` | 전역 쿼리 필터(31.7절) | `.HasQueryFilter(p => !p.Discontinued);` |

`HasKey`·`Property`·`HasIndex`·`HasQueryFilter`가 받는 인자를 보라. **전부 람다이고, 전부 식 트리다.** 모델 구성 API조차 식 트리 위에 세워져 있다.

> **⚠️ `DbSet<T>` 이름과 테이블 이름은 다를 수 있다**
>
> `public DbSet<Customer> Customers { get; set; }`라고 쓰면 EF Core는 테이블 이름을 `Customers`(복수)로 추정한다. 실제 테이블이 `Customer`(단수)라면 `ToTable("Customer")`로 잡아 줘야 한다. 기존 데이터베이스에 붙일 때 첫 번째로 만나는 오류다.

> **📌 규약을 통째로 바꾸기 — `ConfigureConventions` ※EF Core 6**
>
> 모델이 커지면 개별 설정이 감당이 안 된다. `ConfigureConventions`를 재정의하면 규약 자체를 미리 바꿀 수 있다. `configurationBuilder.Properties<string>().HaveMaxLength(50)`은 모든 문자열 프로퍼티의 기본 최대 길이를, `configurationBuilder.IgnoreAny<IDoNotMap>()`은 특정 인터페이스를 구현한 타입 전체를 매핑에서 제외한다.

### 기본 사용 — 읽기와 쓰기

읽기는 `DbSet<T>`에 LINQ를 걸면 된다. 쓰기는 컬렉션을 조작하고 `SaveChanges()`를 부른다. 수정은 프로퍼티를 바꾸기만 하면 되고, `Update` 같은 메서드를 호출할 필요가 없다.

```csharp
using var dbContext = new NutshellContext();

Console.WriteLine (dbContext.Customers.Count());        // SELECT COUNT(*) FROM [Customer] AS [c]

Customer cust = new Customer { Name = "Sara Wells" };
dbContext.Customers.Add (cust);                          // 삽입
dbContext.SaveChanges();

Customer found = dbContext.Customers.Single (c => c.Name == "Sara Wells");
found.Name = "Dr. Sara Wells";                           // 수정 — 프로퍼티 대입이 전부다
dbContext.SaveChanges();

dbContext.Customers.Remove (found);                      // 삭제 (여러 개는 RemoveRange)
int affected = dbContext.SaveChanges();
```

### 객체 추적(object tracking)

`DbContext`는 자기가 만든 엔티티를 전부 기억한다. **한 컨텍스트의 수명 동안, 같은 행(기본 키 기준)을 가리키는 엔티티 객체를 둘 이상 내놓지 않는다.** 이것이 객체 추적이다.

```csharp
using var dbContext = new NutshellContext();
Customer a = dbContext.Customers.OrderBy (c => c.Name).First();
Customer b = dbContext.Customers.OrderBy (c => c.ID).First();
```

이름순 첫 고객과 ID순 첫 고객이 같은 행이라면, `a`와 `b`는 **같은 객체를 참조한다.**

두 번째 쿼리에서 EF Core가 하는 일을 보자. 데이터베이스에 질의해 행 하나를 받는다. 그 행의 기본 키를 읽고 컨텍스트의 엔티티 캐시를 조회한다. 일치하는 항목이 있으면 **값을 갱신하지 않고 기존 객체를 그대로 돌려준다.**

이 동작에는 대가가 있다. 그 사이 다른 사용자가 그 고객의 `Name`을 바꿨다면 **새 값은 무시된다.** 이는 버그가 아니라 의도다. 그 `Customer` 객체가 다른 곳에서 쓰이는 중일 수 있고, 이미 프로퍼티를 수정해 놓고 아직 `SaveChanges()`를 안 했을 수도 있다. 자동으로 덮어쓰면 사용자의 편집이 사라진다.

최신 값이 필요하면 새 컨텍스트를 만들거나 명시적으로 다시 읽는다.

```csharp
dbContext.Entry (myCustomer).Reload();
```

> **💡 작업 단위마다 새 `DbContext`**
>
> 가장 좋은 관행은 **작업 단위(unit of work)마다 새 컨텍스트 인스턴스**를 쓰는 것이다. 그러면 `Reload()`를 손으로 부를 일이 거의 없다. ASP.NET Core에서는 HTTP 요청 하나가 작업 단위이고, DI 컨테이너가 요청 시작 시 컨텍스트를 만들고 끝날 때 폐기한다.

### `DbContext`의 폐기 — 미묘한 문제

`DbContext`는 `IDisposable`이지만, 폐기하지 않아도 대체로 문제가 없다. 연결은 쿼리 결과를 다 읽으면 EF Core가 자동으로 닫기 때문이다.

오히려 **너무 일찍 폐기하는 것**이 위험하다.

```csharp
IQueryable<Customer> GetCustomers (string prefix)
{
    using (var dbContext = new NutshellContext())
        return dbContext.Customers.Where (c => c.Name.StartsWith (prefix));
}
// ...
foreach (Customer c in GetCustomers ("a"))     // 실패한다
    Console.WriteLine (c.Name);
```

지연 실행 때문에 쿼리는 `foreach`에서 평가되는데, 그때는 컨텍스트가 이미 폐기된 뒤다.

그래도 폐기해야 할 이유는 있다.

- 연결 객체가 `Close`만으로 모든 비관리 리소스를 놓는다는 보장은 계약상 없다.
- `foreach` 대신 `GetEnumerator()`를 직접 부르고 열거자를 폐기하지 않으면 연결이 열린 채 남는다. 컨텍스트 폐기가 그 백업이 된다.
- `IDisposable` 객체는 폐기한다는 일관된 규율 자체의 가치.

명시적으로 폐기하겠다면 **컨텍스트를 메서드 안에서 만들지 말고 인자로 받아라.** 위 예제의 함정을 피하는 방법이다. DI가 컨텍스트 수명을 관리한다면 그쪽에 맡기면 된다. 33장의 `IDisposable` 규율이 여기서 실제 사례로 등장한다.

### 변경 추적(change tracking)

`DbContext`로 로드한 엔티티의 프로퍼티를 바꾸면 EF Core가 알아챈다. 원리는 **스냅숏 비교**다. 로드 시점의 값을 복사해 두었다가 `SaveChanges()` 때 현재 값과 비교한다.

추적 상태는 직접 열거할 수 있다.

```csharp
foreach (var e in dbContext.ChangeTracker.Entries())
{
    Console.WriteLine ($"{e.Entity.GetType().FullName} is {e.State}");
    foreach (var m in e.Members)
        Console.WriteLine (
            $"  {m.Metadata.Name}: '{m.CurrentValue}' modified: {m.IsModified}");
}
```

`SaveChanges()`는 이 정보로 `INSERT`/`UPDATE`/`DELETE` 문을 만든다. 주변에 `TransactionScope`가 있으면 그것을 존중하고, 없으면 모든 문장을 새 트랜잭션으로 감싼다.

엔티티의 상태 변화를 직접 관찰해 보자.

```csharp
Product p = new() { CategoryId = 6, ProductName = "Bob's Burgers", Cost = 500M, Stock = 72 };

EntityEntry<Product> entity = db.Products.Add (p);
Console.WriteLine ($"State: {entity.State}, ProductId: {p.ProductId}");
// State: Added, ProductId: 0

int affected = db.SaveChanges();
Console.WriteLine ($"State: {entity.State}, ProductId: {p.ProductId}");
// State: Unchanged, ProductId: 78
```

`SaveChanges()` 전에는 상태가 `Added`이고 키가 `0`이다. 이후에는 `Unchanged`가 되고, **데이터베이스가 부여한 키가 객체에 다시 채워진다.**

> **📌 변경 추적 최적화 — `INotifyPropertyChanged`**
>
> 엔티티가 `INotifyPropertyChanged`를 구현하면 EF Core는 스냅숏 비교를 생략할 수 있다. `INotifyPropertyChanging`까지 구현하면 원본 값 저장 자체를 생략할 수 있다. 활성화하려면 모델 구성에서 `HasChangeTrackingStrategy`를 호출한다. 엔티티 수가 수만 개 단위로 올라가는 배치 작업에서 의미 있는 차이가 난다.

### 추적을 끄기 — `AsNoTracking`

읽기 전용 조회에서는 추적이 순수한 낭비다. 스냅숏을 뜨고 캐시에 등록하는 비용과 메모리를 쓰는데 아무도 `SaveChanges()`를 부르지 않는다.

```csharp
// 쿼리 단위로 끄기
var products = db.Products
    .AsNoTracking()
    .Where (p => p.UnitPrice > price)
    .Select (p => new { p.ProductId, p.ProductName, p.UnitPrice });

// 추적은 끄되 ID 해석(동일 행 → 동일 객체)은 유지
var products2 = db.Products
    .AsNoTrackingWithIdentityResolution()
    .Where (p => p.UnitPrice > price);

// 컨텍스트 인스턴스 단위로 끄기
db.ChangeTracker.QueryTrackingBehavior = QueryTrackingBehavior.NoTracking;

// 모든 인스턴스의 기본값 바꾸기
protected override void OnConfiguring (DbContextOptionsBuilder optionsBuilder)
    => optionsBuilder.UseSqlServer (connectionString)
                     .UseQueryTrackingBehavior (QueryTrackingBehavior.NoTracking);
```

세 가지 모드의 성질은 다음과 같다.

| 모드 | 같은 행을 두 번 쿼리하면 | 로컬 변경 추적 | `SaveChanges()` 효과 | 최신 값 반영 |
|---|---|---|---|---|
| 기본(추적 + ID 해석) | 같은 객체 하나 | 한다 | 데이터베이스에 반영 | 안 된다(첫 로드 값 유지) |
| `NoTracking` | 객체가 두 개 생긴다(중복) | 안 한다 | 아무 일도 없다 | 매 쿼리마다 최신 값 |
| `NoTrackingWithIdentityResolution` | 같은 객체 하나 | 안 한다 | 아무 일도 없다 | 쿼리마다 새로 만들되 한 쿼리 안에서는 중복 없음 |

> **⚠️ "`AsNoTracking`을 붙이면 무조건 빨라진다"는 거짓이다**
>
> 인터넷에서 자주 보이는 조언이지만 조건부로만 참이다. 수천 개 엔티티를 반환하는 쿼리를 같은 컨텍스트에서 두 번 실행하면, `NoTracking`에서는 **수천 개의 중복 객체**가 생긴다. 메모리를 낭비하고 GC를 압박하며, 같은 행을 가리키는 서로 다른 객체가 섞여 논리 버그를 만든다.
>
> 규칙은 이렇다. **한 번 읽고 화면에 뿌리고 버리는 조회**에는 `AsNoTracking`. **수정할 엔티티를 로드하거나 같은 데이터를 여러 번 조회하는 코드**에는 기본 추적.

> **📌 키가 없는 엔티티는 추적되지 않는다**
>
> EF Core는 기본 키로 엔티티를 식별하므로, 뷰에서 온 것처럼 키가 없는 엔티티는 **어떤 경우에도 추적되지 않는다.** 읽기 전용이라는 뜻이다.

### 탐색 속성(navigation property)

탐색 속성은 두 가지를 해 준다. 조인을 손으로 쓰지 않고 관련 테이블을 조회하는 것, 그리고 외래 키를 직접 만지지 않고 관련 행을 추가·삭제·수정하는 것.

```csharp
public class Customer
{
    public int ID { get; set; }
    public string Name { get; set; } = "";

    // 자식 쪽 탐색 속성 — ICollection<T> 계열이어야 한다
    public virtual List<Purchase> Purchases { get; set; } = new List<Purchase>();
}

public class Purchase
{
    public int ID { get; set; }
    public DateTime Date { get; set; }
    public string Description { get; set; } = "";
    public decimal Price { get; set; }

    public int? CustomerID { get; set; }              // 외래 키 필드
    public virtual Customer? Customer { get; set; }   // 부모 쪽 탐색 속성
}
```

`CustomerID`라는 이름이 관례를 따르므로 EF Core는 이것이 `Customer` 테이블에 대한 외래 키임을 추론한다. 추론이 안 되면 명시한다.

```csharp
modelBuilder.Entity<Purchase>()
    .HasOne (e => e.Customer)
    .WithMany (e => e.Purchases)
    .HasForeignKey (e => e.CustomerID);
```

이제 조인 없이 관계를 질의할 수 있다.

```csharp
var customersWithPurchases = dbContext.Customers.Where (c => c.Purchases.Any());
```

컬렉션에 추가하면 `SaveChanges()` 때 외래 키가 자동으로 채워진다.

```csharp
Customer cust = dbContext.Customers.Single (c => c.ID == 1);
Purchase p1 = new Purchase { Description = "Bike",  Price = 500 };
Purchase p2 = new Purchase { Description = "Tools", Price = 100 };
cust.Purchases.Add (p1);
cust.Purchases.Add (p2);
dbContext.SaveChanges();
```

EF Core가 각 구매의 `CustomerID`에 `1`을 쓰고, 데이터베이스가 생성한 `ID`를 `Purchase.ID`에 되채운다.

컬렉션에서 **제거**했을 때의 동작은 관계 구성에 달렸다. 위 예제처럼 `CustomerID`가 널 허용이면 외래 키를 `NULL`로 만들고(고객 없는 구매를 표현할 수 있으므로), 널 불가라면 행을 삭제한다.

> **⚠️ 컬렉션 탐색 속성은 반드시 초기화하라**
>
> `= new List<Purchase>()` 또는 `= new HashSet<Product>()`를 빼먹으면 `null`인 상태로 남고, `cust.Purchases.Count`에서 `NullReferenceException`이 난다. 컬렉션이 순서를 필요로 하지 않는다면 `HashSet<T>`가 `List<T>`보다 효율적이다.

### 탐색 속성 로딩 — 세 가지 패턴

EF Core는 기본적으로 탐색 속성을 **채우지 않는다.**

```csharp
using var dbContext = new NutshellContext();
var cust = dbContext.Customers.First();
Console.WriteLine (cust.Purchases.Count);   // 항상 0
```

| 패턴 | 방법 | 왕복 횟수 | 언제 쓰나 |
|---|---|---|---|
| 즉시 로딩(eager) | `Include` | 1회 | 관련 데이터를 반드시 쓸 때 — 기본 선택 |
| 명시적 로딩(explicit) | `Entry(e).Collection(...).Load()` | 필요할 때마다 1회 추가 | 조건에 따라 일부만 필요할 때 |
| 지연 로딩(lazy) | 프록시 활성화 후 그냥 접근 | 접근할 때마다 1회 | 편하지만 위험 |

**즉시 로딩**이 기본 선택이다.

```csharp
var cust = dbContext.Customers
    .Include (c => c.Purchases)
    .Where (c => c.ID == 2)
    .First();
```

`Include` 안에 필터를 넣을 수도 있다(필터링된 `Include`, ※EF Core 5).

```csharp
IQueryable<Category>? categories = db.Categories?
    .Include (c => c.Products.Where (p => p.Stock >= stock));
```

**투영**이 더 나은 경우도 많다. 필요한 컬럼만 가져오므로 전송량이 준다.

```csharp
var custInfo = dbContext.Customers
    .Where (c => c.ID == 2)
    .Select (c => new
    {
        Name = c.Name,
        Purchases = c.Purchases.Select (p => new { p.Description, p.Price })
    })
    .First();
```

**명시적 로딩**은 필요한 시점에 손으로 부른다. 추가 왕복이 발생한다(`CollectionEntry<,>`를 쓰려면 `Microsoft.EntityFrameworkCore.ChangeTracking` 네임스페이스가 필요하다).

```csharp
CollectionEntry<Category, Product> products = db.Entry (c).Collection (c2 => c2.Products);
if (!products.IsLoaded) products.Load();
```

**지연 로딩**은 프록시를 켜야 동작한다. `Microsoft.EntityFrameworkCore.Proxies` 패키지를 참조하고 다음을 호출한다.

```csharp
protected override void OnConfiguring (DbContextOptionsBuilder optionsBuilder)
    => optionsBuilder.UseLazyLoadingProxies().UseSqlite (connectionString);
```

조건은 세 가지다. **탐색 속성이 `virtual`이어야 하고**, 클래스가 상속 가능해야(sealed가 아니어야) 하며, 접근하는 시점에 컨텍스트가 살아 있어야 한다.

지연 로딩을 켜면 `dbContext.Customers.First().GetType()`이 `Castle.Proxies.CustomerProxy`를 돌려준다. 런타임 타입이 엔티티 클래스가 아니라 **파생 프록시**라는 사실은 직렬화나 타입 비교에서 문제가 된다.

> **⚠️ 지연 로딩은 N+1 왕복을 부른다**
>
> 카테고리 8개를 순회하며 각각의 `Products`에 접근하면 SQL이 **9번** 나간다. 카테고리 하나, 제품 여덟 번. 행이 수천 개면 수천 번이다. 코드에는 루프 하나만 보이므로 원인을 찾기 어렵다.
>
> 지연 로딩은 "게으른 데이터베이스 개발자"를 만든다. 기본은 꺼 두고, `Include`나 투영으로 **무엇이 필요한지 명시적으로 선언하는 습관**을 들여라.

### `Select` 서브쿼리의 특별한 지연 실행 의미론

로컬 쿼리에서 `Select` 안에 서브쿼리를 넣으면 **이중 지연**이 된다. 바깥을 열거해도 안쪽을 열거하지 않으면 서브쿼리는 영원히 실행되지 않는다.

EF Core는 다르다. **서브쿼리를 바깥 쿼리와 같은 시점에 실행한다.** 과도한 왕복을 막기 위해서다.

```csharp
using var dbContext = new NutshellContext();

var query = from c in dbContext.Customers
            select
                from p in c.Purchases
                select new { c.Name, p.Price };

foreach (var customerPurchaseResults in query)         // 여기서 단 한 번의 왕복
    foreach (var namePrice in customerPurchaseResults)
        Console.WriteLine ($"{namePrice.Name} spent {namePrice.Price}");
```

명시적으로 투영한 탐색 속성도 한 번에 채워진다.

```csharp
var query = from c in dbContext.Customers
            select new { c.Name, c.Purchases };

foreach (var row in query)
    foreach (Purchase p in row.Purchases)       // 추가 왕복 없음
        Console.WriteLine (row.Name + " spent " + p.Price);
```

반대로 즉시 로딩도 투영도 하지 않고 탐색 속성을 열거하면 원래의 지연 실행 규칙이 적용된다.

```csharp
foreach (Customer c in dbContext.Customers.ToArray())
    foreach (Purchase p in c.Purchases)         // 반복마다 SQL 왕복 (지연 로딩 활성 시)
        Console.WriteLine (c.Name + " spent " + p.Price);
```

이 모델이 유리한 경우도 있다. 클라이언트에서만 판정할 수 있는 조건으로 안쪽 루프를 **선택적으로** 실행할 때다.

```csharp
foreach (Customer c in dbContext.Customers.ToArray())
    if (myWebService.HasBadCreditHistory (c.ID))
        foreach (Purchase p in c.Purchases)
            Console.WriteLine (c.Name + " spent " + p.Price);
```

> **⚠️ `ToArray()`가 왜 거기 있는가 — MARS**
>
> 위 두 예제의 `ToArray()`는 장식이 아니다. SQL Server는 기본적으로 **현재 쿼리의 결과를 다 읽기 전에 새 쿼리를 시작할 수 없다.** `ToArray()`로 고객을 먼저 실체화해야 각 고객의 구매를 조회하는 추가 쿼리를 던질 수 있다.
>
> 연결 문자열에 `;MultipleActiveResultSets=True`를 붙이면 다중 활성 결과 집합(MARS)이 켜져 이 제약이 사라진다. 다만 신중하게 써라. MARS는 **수다스러운 데이터베이스 설계를 가려 준다.** 즉시 로딩이나 투영으로 고쳐야 할 문제를 덮는 것일 수 있다.

### 더 효율적인 수정과 삭제 ※EF Core 7

지금까지 본 수정·삭제 방식은 엔티티를 메모리로 읽고, 변경을 추적하고, `SaveChanges()`로 반영하는 것이었다. 대량 작업에서는 낭비다.

`ExecuteUpdate`/`ExecuteDelete`(및 `Async` 버전)는 **엔티티를 로드하지 않고** LINQ 쿼리가 지정한 행에 직접 작용한다.

```csharp
// 모든 제품 삭제
await db.Products.ExecuteDeleteAsync();
// DELETE FROM Products

// 조건부 삭제
await db.Products
    .Where (p => p.UnitPrice > 50)
    .ExecuteDeleteAsync();
// DELETE FROM Products p WHERE p.UnitPrice > 50

// 조건부 수정
await db.Products
    .Where (p => !p.Discontinued)
    .ExecuteUpdateAsync (s => s.SetProperty (
        p => p.UnitPrice,           // 수정할 프로퍼티 선택
        p => p.UnitPrice * 1.1m));  // 새 값
```

`SetProperty`를 여러 번 체이닝하면 한 명령으로 여러 컬럼을 수정한다. 여기서도 인자는 전부 식 트리다 — 그래서 EF Core가 `SET UnitPrice = UnitPrice * 1.1`이라는 SQL을 만들 수 있다.

> **⚠️ `ExecuteUpdate`/`ExecuteDelete`는 변경 추적기와 동기화되지 않는다**
>
> 이 메서드들은 데이터베이스를 직접 바꾸지만, 컨텍스트가 이미 추적 중인 엔티티는 **옛 값을 그대로 들고 있다.** 전통적 추적 방식과 섞어 쓰면 메모리의 상태와 데이터베이스의 상태가 어긋난다. 같은 작업 단위 안에서 두 방식을 섞지 말고, 섞어야 한다면 이후 엔티티를 다시 로드하라.

> **⚠️ 단일 테이블에만 작용한다**
>
> LINQ 쿼리는 얼마든지 복잡하게 쓸 수 있지만, `ExecuteUpdate`/`ExecuteDelete`가 실제로 수정·삭제하는 대상은 **한 테이블**이다. 조인을 포함한 쿼리로 여러 테이블을 한 번에 바꿀 수는 없다.

> **📌 `DbContext` 풀링**
>
> ASP.NET Core에서는 `AddDbContextPool`로 컨텍스트 인스턴스를 재사용할 수 있다. `DbContext`는 여전히 작업 단위마다 하나씩 쓰되, 인스턴스 생성 비용(특히 내부 서비스 구성)을 아낀다. 코드 관점에서는 평소처럼 만들고 폐기하면 되고, 풀링은 뒤에서 알아서 동작한다.

## 31.9 합성 가능한 시퀀스 API 설계

28.7절에서 로컬 시퀀스를 레고 블록처럼 조립하는 원칙을 세웠다. `IEnumerable<T>`를 받아 `IEnumerable<T>`를 돌려주는 모양이 이긴다는 것이었다. 원격 쿼리가 섞이면 그 원칙에 조건이 하나 붙는다. **반환 타입이 곧 실행 위치의 선언이다.**

### 반환 타입이 계약이다

| 반환 타입 | 호출자에게 하는 약속 | 위험 |
|---|---|---|
| `IQueryable<T>` | "아직 서버에 안 갔다. 더 붙여라" | 호출자가 번역 불가능한 식을 붙일 수 있다. 컨텍스트 수명이 호출자에게 노출된다 |
| `IEnumerable<T>` | "여기서부터는 로컬이다" (또는 "실행 위치를 감췄다") | 호출자가 원격인 줄 알고 필터를 붙이면 전체 전송 |
| `IReadOnlyList<T>` / `T[]` | "이미 실행했다. 여기 결과가 있다" | 유연성 없음. 페이징·필터를 호출자가 못 붙인다 |
| `IAsyncEnumerable<T>` | "비동기로 스트리밍한다" | 소비자가 `await foreach`를 써야 한다(28.9절, 47장) |

이 표에서 읽어야 할 것은 "무엇이 옳다"가 아니라 **"애매하게 두지 마라"**다. 최악은 `IEnumerable<T>`를 반환하면서 실제로는 `DbSet`을 그대로 흘려보내는 메서드다. 호출자는 로컬이라고 믿고 정규식 필터를 붙이고, 실행은 `DbContext`가 살아 있을 때만 성공하며, 성능은 예측 불가능해진다.

> **💡 세 층으로 나눠라**
>
> 1. **합성 층** — `IQueryable<T>`를 받아 `IQueryable<T>`를 돌려준다. 술어와 정렬만 붙인다. 데이터베이스 세션을 소유하지 않는다.
> 2. **경계 층** — 합성이 끝난 지점에서 `ToListAsync()` / `AsEnumerable()`로 경계를 긋고, 여기서만 `DbContext` 수명을 다룬다.
> 3. **소비 층** — 로컬 컬렉션만 본다. 원격이라는 사실을 모른다.
>
> 경계 층이 딱 한 군데면 "쿼리가 언제 실행되는가"라는 질문의 답이 항상 명확하다.

### 확장 메서드는 `Expression`을 받아라

재사용 가능한 필터를 라이브러리로 노출할 때, 델리게이트를 받으면 원격 사용을 영원히 막는다.

```csharp
// 나쁨 — 로컬 전용이 된다
public static IQueryable<T> WhereActive<T> (this IQueryable<T> source, Func<T, bool> extra)
    => source.Where (x => extra (x));   // 트리에 델리게이트 호출이 남는다 — 번역 불가

// 좋음 — 양쪽 모두 통한다
public static IQueryable<Product> OnlySelling (this IQueryable<Product> source)
    => source.Where (Product.IsSelling());

public static IEnumerable<Product> OnlySelling (this IEnumerable<Product> source)
    => source.Where (Product.IsSelling().Compile());
```

31.1절에서 만든 `Product.IsSelling()`처럼 **규칙을 `Expression<Func<T,bool>>`로 노출**해 두면, 같은 규칙을 서버와 클라이언트 양쪽에서 쓸 수 있다. 델리게이트로 노출하면 되돌릴 방법이 없다.

> **⚠️ `IQueryable<T>`에 새 어휘를 추가하지 마라**
>
> 31.3절에서 본 원칙이다. `IQueryable<T>`를 받는 확장 메서드는 만들어도 되지만, 그 안에서 하는 일은 **표준 `Queryable` 연산자를 조립하는 것뿐**이어야 한다. 트리에 표준이 아닌 노드를 남기면 공급자가 이해하지 못한다. 31.6절의 `OrderByProperty`가 지켜야 할 선을 보여 준다 — 확장은 조립 시점에만 존재하고, 결과 트리는 순수한 표준 연산자 체인이다.

### 오류는 이르게, 지연은 명시적으로

지연 실행 API의 고전적 문제는 **오류가 늦게 나온다**는 것이다(78.12절). 인자 검증은 즉시 하고, 시퀀스 생성만 지연하라.

```csharp
public static IQueryable<Product> PricedBetween (
    this IQueryable<Product> source, decimal min, decimal max)
{
    ArgumentNullException.ThrowIfNull (source);
    if (min > max) throw new ArgumentException ("min이 max보다 크다");

    return source.Where (p => p.Price >= min && p.Price <= max);
}
```

`IQueryable<T>`를 돌려주는 메서드는 반복자가 아니므로 인자 검증이 자연스럽게 즉시 실행된다. 반면 `yield return`을 쓰는 로컬 확장 메서드는 검증부와 반복자부를 분리해야 한다(28.6절).

### 테스트 — `AsQueryable`의 진짜 용도

합성 층이 `IQueryable<T>`만 다루면, 테스트에서 데이터베이스 없이 메모리 컬렉션으로 검증할 수 있다.

```csharp
[Fact]
public void PricedBetween_필터링한다()
{
    var data = new[]
    {
        new Product { Price = 50 },
        new Product { Price = 150 },
        new Product { Price = 250 },
    }.AsQueryable();

    var result = data.PricedBetween (100, 200).ToList();

    Assert.Single (result);
}
```

> **⚠️ 인메모리 테스트는 번역 가능성을 검증하지 못한다**
>
> `AsQueryable()`이나 EF Core의 인메모리 공급자 위에서는 **어떤 식이든 다 통과한다.** 로컬 실행이므로 `Regex`도, 사용자 정의 메서드도 잘 돌아간다. 그리고 운영에서 실제 데이터베이스에 붙는 순간 `InvalidOperationException`이 터진다.
>
> 인메모리 테스트는 **로직 검증**에만 쓰고, **번역 가능성은 반드시 실제 데이터베이스 공급자(최소한 SQLite)로 확인하라.** 단위 테스트 100개가 초록불인데 배포하면 죽는 전형적인 패턴이다.

> **💡 설계 체크리스트**
>
> - 이 메서드의 반환 타입은 실행 위치를 정직하게 말하고 있는가
> - 술어를 `Func`로 받고 있지는 않은가 — `Expression`이어야 할 자리가 아닌가
> - `AsEnumerable()` / `ToList()`가 호출 체인의 **가장 늦은** 지점에 있는가
> - 트리에 표준 연산자 외의 노드를 남기지 않는가
> - `DbContext` 수명을 소유하는 계층이 한 곳으로 모여 있는가

## 이 장의 요약

- **같은 람다가 두 가지가 된다.** `Func<T,bool>`이면 컴파일된 IL과 델리게이트 인스턴스가, `Expression<Func<T,bool>>`이면 `System.Linq.Expressions` 노드로 된 객체 트리가 나온다. 전자는 호출만 할 수 있고, 후자는 읽고 분해하고 번역할 수 있다.
- **역방향 변환은 없다.** 식 트리는 `Compile()`로 델리게이트가 되지만 델리게이트를 트리로 되돌리는 API는 없다. 그래서 재사용 규칙은 `Expression<T>`로 노출해야 한다.
- **`NodeType`이 노드의 정체다.** `BinaryExpression` 하나가 수십 가지 연산을 대표하므로 CLR 타입이 아니라 `ExpressionType`을 봐야 한다. 트리는 불변이고, 노드는 `Expression`의 정적 팩토리로만 만든다. 순회와 변형의 표준 도구는 `ExpressionVisitor`다.
- **`Queryable` 연산자는 실행하지 않고 기록한다.** 각 연산자는 기존 트리를 인자로 삼는 `MethodCallExpression`을 만들고 `Provider.CreateQuery`에 넘긴다. 열거하는 순간 공급자가 트리 전체를 단위로 번역해 실행한다.
- **오버로드 해석이 실행 위치를 정한다.** 소스의 정적 타입이 `IQueryable<T>`이면 `Queryable`에, `IEnumerable<T>`이면 `Enumerable`에 바인딩된다. 변수 선언 타입 하나가 서버 실행과 전체 테이블 전송을 가른다.
- **`AsEnumerable()`은 국경선이다.** 아무 원소도 복사하지 않고 즉시 실행도 하지 않지만, 그 아래의 모든 연산자를 클라이언트로 내린다. 위치가 곧 성능이며, 필터가 경계 위에 없으면 전체 스캔이다.
- **동적 쿼리는 트리 조립으로 만든다.** 매개변수는 이름이 아니라 참조로 식별되므로, 두 람다를 합칠 때는 매개변수를 재사용하거나 `ExpressionVisitor`로 치환해야 한다. 조립기가 만드는 트리에는 표준 연산자만 남아야 한다.
- **EF Core는 이 구조 위의 번역기다.** 모델로 사전을 만들고, 캡처 변수를 SQL 파라미터로 승격시키고, 트리 모양을 키로 번역 결과를 캐시한다. 번역할 수 없으면 `InvalidOperationException`을 던진다 — 클라이언트 평가는 최상위 투영에서만 허용된다.
- **추적은 공짜가 아니고 끄는 것도 공짜가 아니다.** 읽고 버리는 조회에는 `AsNoTracking`, 수정하거나 같은 데이터를 여러 번 읽는 코드에는 기본 추적. 무조건 끄면 중복 객체가 생긴다.
- **로딩 패턴을 명시적으로 선언하라.** 기본은 `Include`(즉시 로딩)나 투영이다. 지연 로딩은 편하지만 N+1 왕복을 코드에 보이지 않게 숨긴다.
- **API의 반환 타입이 실행 위치의 계약이다.** 합성 층은 `IQueryable<T>`, 경계 층은 한 곳, 소비 층은 로컬 컬렉션만. 애매한 `IEnumerable<T>` 반환이 가장 비싼 실수다.

## 연습 문제

1. `Expression<Func<int,int,bool>> e = (a, b) => a * 2 + b < 100;`을 선언하고, 31.2절의 `Dump` 함수로 트리를 출력하라. 그 다음 같은 트리를 `Expression.Parameter`/`Expression.Multiply`/`Expression.Add`/`Expression.LessThan`/`Expression.Lambda`만으로 손으로 조립하고, 두 트리의 `ToString()`이 같은지 확인하라.
2. 지역 변수를 캡처하는 람다(`string kw = "bike"; Expression<Func<Product,bool>> f = p => p.Description.Contains(kw);`)를 만들고 트리를 덤프하라. `Constant` 노드의 `Value.GetType()`을 출력해 디스플레이 클래스가 실제로 나타나는지 확인하라. 그 다음 `kw`를 상수 리터럴로 바꿔 트리가 어떻게 달라지는지 비교하라.
3. `ExpressionVisitor`를 상속해, 트리 안의 모든 `>` 비교를 `>=`로 바꾸는 방문자를 작성하라(`ExpressionType.GreaterThan` → `Expression.GreaterThanOrEqual`). `Compile()`해서 동작이 실제로 바뀌는지 검증하라.
4. 31.3절의 `DumpProvider`를 실행해, 연산자를 다섯 개 체이닝해도 `Execute`가 한 번만 불리는지 확인하라. 그 다음 체인 끝에 `Count()`를 붙였을 때 `Execute<TResult>`에 도착하는 트리의 루트 노드가 무엇인지 출력하라.
5. 로컬 배열에 `AsQueryable()`을 씌운 쿼리와 씌우지 않은 쿼리를 각각 100만 회 열거해 시간을 재라. 차이가 어디서 오는지 트리 조립과 암묵적 컴파일 관점에서 설명하라.
6. `PredicateBuilder`를 31.6절대로 구현하고, 키워드 배열로 `Or` 누적 술어를 만들어 `Compile()` 후 로컬 컬렉션에 적용하라. 그 다음 `ParameterReplacer`를 빼고 실행해 어떤 예외가 어느 시점에 나는지 확인하라.
7. SQLite로 Northwind 데이터베이스를 만들고(또는 인메모리 공급자를 쓰고), 같은 쿼리를 `Where(...).AsEnumerable().Count()`와 `Where(...).Count()` 두 형태로 실행하라. `LogTo(Console.WriteLine)`로 생성되는 SQL을 비교하고, 전송되는 행 수의 차이를 설명하라.
8. `Include`를 붙인 쿼리와 붙이지 않은 쿼리를 각각 `ToQueryString()`으로 출력해 비교하라. 그 다음 지연 로딩 프록시를 켜고 같은 코드를 실행해 SQL 명령이 몇 번 나가는지 로그로 세어 보라.
