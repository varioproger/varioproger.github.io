## 18.1 인터페이스 정의와 구현

### 인터페이스란 무엇인가

인터페이스는 클래스와 비슷하지만 **동작만 규정하고 상태(데이터)는 갖지 않는다**. 이 한 문장에서 인터페이스의 모든 규칙이 파생된다.

- 인터페이스는 함수만 정의할 수 있고 **필드는 정의할 수 없다**. (인스턴스 필드 이야기다. 정적 필드는 ※C# 8부터 예외가 있다 — 18.8절)
- 인터페이스 멤버는 **암묵적으로 추상**이다. (여기에도 예외가 있다 — 18.7절, 18.8절)
- 클래스나 구조체는 **여러 인터페이스를 구현**할 수 있다. 반면 클래스는 기반 클래스를 하나만 가질 수 있고, 구조체는 (`System.ValueType`에서 파생되는 것을 빼면) 상속 자체가 불가능하다.

인터페이스가 담을 수 있는 것은 **메서드, 프로퍼티, 이벤트, 인덱서**다. 우연이 아니다. 이 넷은 정확히 클래스에서 `abstract`가 될 수 있는 멤버들이다. CLR 관점에서 프로퍼티·이벤트·인덱서는 결국 메서드로 환원되므로, 인터페이스는 **메서드 시그니처 집합에 이름을 붙인 것**이라고 말해도 틀리지 않는다.

```csharp
// System.Collections에 정의된 IEnumerator의 실제 모습
public interface IEnumerator
{
    bool MoveNext();
    object Current { get; }
    void Reset();
}
```

인터페이스 멤버는 **항상 암묵적으로 `public`**이며, C# 8 이전에는 접근 제한자를 쓰는 것 자체가 금지였다. 따라서 인터페이스를 구현한다는 것은 **모든 멤버에 대해 `public` 구현을 제공한다**는 뜻이다.

```csharp
internal class Countdown : IEnumerator
{
    int count = 11;

    public bool MoveNext() => count-- > 0;
    public object Current => count;
    public void Reset() { throw new NotSupportedException(); }
}
```

구현한 인터페이스로는 **암시적 캐스팅**이 된다. 별도 문법이 필요 없다.

```csharp
IEnumerator e = new Countdown();
while (e.MoveNext())
    Console.Write(e.Current);        // 109876543210
```

> **📌 CLR은 인터페이스를 "축소판 다중 상속"으로 제공한다**
>
> 데이터를 송신하는 `TransmitData`와 수신하는 `ReceiveData`가 있고, 둘 다 하는 `SocketPort`를 만들고 싶다고 하자. C++이라면 두 클래스를 동시에 상속하면 된다. CLR은 클래스 다중 상속을 지원하지 않는 대신 **인터페이스라는 축소판**을 제공한다. "축소판"인 이유는 구현이 딸려오지 않아 구현 메서드를 전부 손으로 써야 하기 때문이다.
>
> 왜 CLR이 클래스 다중 상속을 포기했는지는 14장에서 다뤘다. 요약하면 **참조 변환이 주소를 바꾸지 않는다**는 성질을 지키기 위해서다. 인터페이스는 필드를 갖지 않으므로 이 문제에서 자유롭다.

### 인터페이스는 타입이다

인터페이스 정의는 CLR에게 **타입 정의**와 다르지 않다. CLR은 인터페이스 타입 객체를 위한 내부 자료구조를 만들고, 리플렉션으로 그 특징을 조회할 수 있다. 인터페이스도 파일 스코프에 정의하거나 다른 타입 안에 중첩할 수 있고, 원하는 가시성(`public`, `internal` 등)을 지정할 수 있다. IL에서는 이렇게 보인다.

```il
.class interface public abstract auto ansi IUndoable
{
  .method public hidebysig newslot abstract virtual
          instance void  Undo() cil managed
  {
  }
}
```

| IL 토큰 | 의미 |
|---|---|
| `.class interface` | 이 타입은 인터페이스다 |
| `abstract` (클래스 수준) | 인스턴스화할 수 없다 |
| `abstract virtual` (메서드 수준) | 구현 없는 가상 메서드 — 파생 타입이 채워야 한다 |
| `newslot` | 새 가상 슬롯을 차지한다 (기반의 슬롯을 덮지 않는다) |

`IUndoable p = new IUndoable();`이 컴파일 오류인 이유가 여기 있다. 클래스 수준 `abstract` 때문이다.

> **📌 이름 앞의 `I`는 관례일 뿐 문법이 아니다**
>
> .NET 인터페이스 이름을 대문자 `I`로 시작하는 것은 **강제되지 않는 관례**다. 컴파일러는 아무 검사도 하지 않는다. 그러나 BCL 전체가 이 관례를 지키고 있으므로 커스텀 인터페이스에도 지키는 것이 좋다.

### 인터페이스가 할 수 없는 것

C# 8이 아래 표의 상당 부분을 뒤집었으므로 "이전"과 "이후"를 나눠 본다.

| 요소 | C# 7까지 | C# 8 이후 |
|---|---|---|
| 인스턴스 메서드 시그니처 | 가능 (암묵적 `public abstract`) | 가능 |
| 프로퍼티·인덱서·이벤트 | 가능 | 가능 |
| **인스턴스 필드** | 불가 | **여전히 불가** |
| 인스턴스 생성자 | 불가 | 여전히 불가 |
| 소멸자(파이널라이저) | 불가 | 여전히 불가 |
| 메서드 본문(기본 구현) | 불가 | **가능** (18.7절) |
| 접근 제한자 | 불가 | **가능** (`private`/`protected`/`internal`/`public`) |
| 정적 메서드·정적 필드·정적 생성자 | C#이 금지 | **가능** (18.8절) |
| 정적 추상·정적 가상 멤버 | 불가 | **C# 11부터 가능** (18.8절) |
| 중첩 타입 | 불가 | 가능 |

> **⚠️ CLR이 허용하는 것과 C#이 허용하는 것은 다르다**
>
> CLR 자체는 인터페이스가 정적 메서드·정적 필드·상수·정적 생성자를 정의하는 것을 예전부터 허용했다. 그런데 **CLS(공용 언어 사양)를 준수하는 인터페이스는 이런 정적 멤버를 가지면 안 된다.** 일부 언어가 이를 정의하거나 접근할 수 없기 때문이다. 그래서 C#은 오랫동안 인터페이스의 정적 멤버를 막았다. C# 8에서 이 금지가 풀린 것은 언어의 결정이지 CLR의 변화가 아니다. **다만 기본 구현 멤버는 런타임 지원이 필요하다** — 18.7절에서 다룬다.

**인스턴스 필드가 여전히 금지인 것**이 핵심이다. 이것이 인터페이스와 추상 클래스를 가르는 마지막 선이고, 18.12절 결정표의 첫째 줄이다.

```csharp
public interface IPointy
{
    public int numbOfPoints;               // 오류: 인터페이스는 필드를 가질 수 없다
    public IPointy() { numbOfPoints = 0; } // 오류: 인스턴스 생성자를 가질 수 없다
}
```

### 구현 문법

클래스가 인터페이스를 구현할 때는 콜론 뒤에 쉼표로 나열한다. **직접 기반 클래스는 반드시 첫 번째**여야 한다.

```csharp
public class Pencil : IPointy { }                      // object에서 파생 + 인터페이스 하나
public class SwitchBlade : object, IPointy { }         // object를 명시해도 의미는 같다
public class Fork : Utensil, IPointy, IDisposable { }  // 기반 클래스가 먼저다
public struct PizzaSlice : IPointy { }                 // 구조체는 인터페이스만 나열한다
```

인터페이스는 **부분집합 문제**를 푸는 데 강력하다. 도형 계층에서 `Hexagon`만 "꼭짓점을 갖는" 성질이 있다고 하자. 이것을 기반 클래스 `Shape`에 `abstract byte GetNumberOfPoints()`로 넣으면 `Circle`도 `ThreeDCircle`도 의미 없는 구현을 강제당한다. 인터페이스로 빼면 `Hexagon`에만 꽂아 넣고 나머지는 건드리지 않는다.

```csharp
public interface IPointy
{
    byte Points { get; }   // 암묵적으로 public abstract
}

public class Hexagon : Shape, IPointy
{
    public override void Draw() => Console.WriteLine("Drawing a hexagon");
    public byte Points => 6;
}

// Circle은 IPointy와 무관하다. 한 글자도 바뀌지 않는다
public class Circle : Shape
{
    public override void Draw() => Console.WriteLine("Drawing a circle");
}
```

인터페이스가 특히 유효한 상황은 둘이다.

1. **하나의 계층 안에서 파생 타입의 일부만** 공통 동작을 지원할 때
2. `System.Object` 말고는 공통 부모가 없는 **여러 계층에 걸친** 공통 동작을 모델링할 때

### 인터페이스 참조 얻기

객체가 인터페이스를 구현하는지 확인하고 참조를 얻는 방법은 셋이다.

```csharp
Shape s = GetSomeShape();

IPointy p1 = (IPointy)s;                 // (1) 직접 캐스팅 — 실패하면 InvalidCastException
IPointy? p2 = s as IPointy;              // (2) as 연산자 — 실패하면 null
if (s is IPointy p3) { /* ... */ }       // (3) is 패턴 — 검사와 캐스팅이 한 번에 (권장)
```

세 번째가 가장 좋다. 타입 검사와 캐스팅이 한 연산으로 합쳐지고, 변수 스코프도 자연스럽게 좁아진다. `is`/`as`를 캐스트보다 선호하는 일반 원칙은 79.3절에 있다.

> **⚠️ `internal` 클래스의 인터페이스 구현은 외부에서 호출된다**
>
> `Countdown`이 `internal`이어도, `IEnumerator`를 구현하는 멤버들은 **다른 어셈블리에서 호출될 수 있다**. 같은 어셈블리의 `public` 타입이 인스턴스를 넘겨주기만 하면 된다.
>
> ```csharp
> public static class Util
> {
>     public static object GetCountDown() => new Countdown();
> }
> ```
>
> 다른 어셈블리에서:
>
> ```csharp
> IEnumerator e = (IEnumerator)Util.GetCountDown();
> e.MoveNext();
> ```
>
> 호출자는 `Countdown`이라는 **이름**을 표현할 수 없을 뿐, 그 동작에는 완전히 접근한다. `IEnumerator` 자체가 `internal`이었다면 이것은 불가능하다. 접근성 계산은 17.3절에서 다뤘다. 요점은 **`internal`이 캡슐화를 보장하지 않는다**는 것이다.

### 인터페이스는 매개변수·반환값으로 쓴다

인터페이스가 유용한 이유의 절반은 여기에 있다. 인터페이스 타입 매개변수는 "이 능력을 갖춘 무엇이든 받는다"는 뜻이다.

```csharp
// 인터페이스를 매개변수로 — "3D를 그릴 줄 아는 무엇이든" 받는다
static void DrawIn3D(IDraw3D itf3d) => itf3d.Draw3D();

// 인터페이스를 반환값으로
static IPointy? FindFirstPointyShape(Shape[] shapes)
{
    foreach (Shape s in shapes)
        if (s is IPointy p) return p;
    return null;
}
```

인터페이스 타입 배열도 만들 수 있다. 서로 다른 계층의 타입을 **공통 능력** 하나로 묶는다.

```csharp
// Hexagon은 Shape의 파생, Knife는 Utensil의 파생 — 공통 부모는 object뿐이다
IPointy[] pointyThings = { new Hexagon(), new Knife(), new Triangle(), new Fork() };
foreach (IPointy p in pointyThings)
    Console.WriteLine($"Points: {p.Points}");
```

`Hexagon`과 `Knife`는 상속 계층이 완전히 다르다. 기반 클래스로는 절대 묶을 수 없다. 인터페이스는 **상속 계층을 가로지르는 분류**를 가능하게 한다.

> **💡 인터페이스로 받고, 구체 타입으로 만들어라**
>
> 매개변수 타입은 가능한 한 인터페이스로, 지역 변수와 필드는 필요에 따라 구체 타입으로. 이렇게 하면 호출자가 무엇을 넘기든 받아들이면서, 내부에서는 구체 타입의 최적화된 멤버를 쓸 수 있다. 다만 **반환 타입**은 다르다 — 반환을 인터페이스로 하면 호출자가 성능상 중요한 구체 멤버(예: `List<T>.Capacity`)에 접근하지 못한다. 컬렉션을 인터페이스로 받을 것인가 구체 클래스로 받을 것인가는 24.16절에서 손익을 따진다.

## 18.2 인터페이스 확장(상속)

### 문법과 의미

인터페이스는 다른 인터페이스에서 파생될 수 있다.

```csharp
public interface IUndoable { void Undo(); }
public interface IRedoable : IUndoable { void Redo(); }
```

`IRedoable`은 `IUndoable`의 모든 멤버를 "상속"한다. 다시 말해 `IRedoable`을 구현하는 타입은 `IUndoable`의 멤버도 구현해야 한다.

여기서 "상속"이라는 단어는 느슨하게 쓰인 것이다. 클래스 상속처럼 동작하지 않기 때문이다. **인터페이스 상속은 다른 인터페이스의 계약을 포함(include)하는 것**이라고 생각하는 편이 정확하다. C# 8 이전까지는 물려받을 구현이 아예 없었으므로 더욱 그렇다.

BCL의 `ICollection<T>`가 좋은 예다.

```csharp
public interface IEnumerable<out T> : IEnumerable
{
    new IEnumerator<T> GetEnumerator();
}

public interface ICollection<T> : IEnumerable<T>, IEnumerable
{
    void    Add(T item);
    void    Clear();
    bool    Contains(T item);
    void    CopyTo(T[] array, int arrayIndex);
    bool    Remove(T item);
    int     Count      { get; }
    bool    IsReadOnly { get; }
}
```

`ICollection<T>` 정의는 `IEnumerable<T>`와 `IEnumerable`의 계약을 포함한다. 그 결과 `ICollection<T>`를 상속한 클래스는 **세 인터페이스가 정의한 모든 메서드**를 구현해야 하고, `ICollection<T>` 객체를 기대하는 코드는 그 객체가 나머지 둘의 메서드도 구현하고 있다고 **가정해도 된다**.

### 인터페이스는 다중 상속이 된다

클래스와 달리 인터페이스는 **여러 기반 인터페이스를 확장**할 수 있다. 이것이 인터페이스로 강력한 추상을 설계할 수 있는 이유다.

```csharp
interface IDrawable  { void Draw(); }
interface IPrintable { void Print(); void Draw(); }   // Draw 이름 충돌에 주의

// 인터페이스의 다중 상속 — 문제없다
interface IShape : IDrawable, IPrintable
{
    int GetNumberOfSides();
}
```

```text
        IDrawable          IPrintable
        ┌────────┐         ┌────────────┐
        │ Draw() │         │ Print()    │
        └────┬───┘         │ Draw()     │
             │             └──────┬─────┘
             └───────┬────────────┘
                     ↓
                ┌──────────────────┐
                │ IShape           │
                │ GetNumberOfSides │
                └──────────────────┘
```

`IShape`를 지원하는 클래스는 메서드를 몇 개 구현해야 할까? **경우에 따라 다르다.** `Draw()` 구현을 하나로 공유해도 된다면 셋이면 충분하다. 인터페이스마다 달라야 한다면 **명시적 구현**으로 이름 충돌을 해소한다(18.5절).

```csharp
class Rectangle : IShape                     // Draw를 공유하는 경우 — 멤버 셋
{
    public int GetNumberOfSides() => 4;
    public void Draw()  => Console.WriteLine("Drawing...");
    public void Print() => Console.WriteLine("Printing...");
}

class Square : IShape                        // Draw를 갈라야 하는 경우 — 멤버 넷
{
    void IPrintable.Draw() { /* 프린터로 그린다 */ }
    void IDrawable.Draw()  { /* 화면에 그린다 */ }
    public void Print()    { }
    public int GetNumberOfSides() => 4;
}
```

> **⚠️ 파생 인터페이스는 기반 인터페이스보다 덜 접근 가능할 수 없다**
>
> ```csharp
> internal interface IBase { void M(); }
> public interface IDerived : IBase { }   // 컴파일 오류 CS0061
> ```
>
> `IDerived`가 `public`인데 `IBase`가 `internal`이면, 다른 어셈블리에서 `IDerived`를 구현하려 해도 `IBase.M`을 표현할 수 없다. 접근성 제한(accessibility capping) 규칙은 17.3절에서 다뤘고 인터페이스에도 똑같이 적용된다.

### `new` 한정자로 기반 인터페이스 멤버 가리기

`IEnumerable<T>`의 정의를 다시 보자.

```csharp
public interface IEnumerable<out T> : IEnumerable
{
    new IEnumerator<T> GetEnumerator();   // new 한정자
}
```

`IEnumerable`도 `GetEnumerator()`를 정의하는데, 반환 타입만 다르다(`IEnumerator` vs `IEnumerator<T>`). 반환 타입만으로는 오버로드할 수 없으므로 `new` 한정자로 **가린다**. 결과적으로 `IEnumerable<T>` 타입 변수에서는 제네릭 버전이 보이고, `IEnumerable`로 캐스팅하면 비제네릭 버전이 보인다.

이 구조 때문에 `IEnumerable<T>`를 구현하는 타입은 `GetEnumerator()`를 **두 개** 구현해야 한다. 18.11절에서 표준 관용구를 본다.

> **📌 인터페이스 상속과 클래스 상속의 결정적 차이**
>
> | 항목 | 클래스 상속 | 인터페이스 상속 |
> |---|---|---|
> | 기반 개수 | 정확히 하나 | 제한 없음 |
> | 물려받는 것 | 시그니처 + **구현** + 필드 | 시그니처 (C# 8부터 기본 구현도) |
> | 상태 공유 | 가능 | 불가능 (인스턴스 필드 금지) |
> | 관계 | IS-A | CAN-DO |
> | 멤버 추가의 파급 | 파생 타입이 그냥 물려받는다 | 구현 타입이 전부 깨진다 (C# 8 기본 구현으로 완화) |
>
> 마지막 행이 기본 구현 멤버(18.7절)가 탄생한 이유다.

## 18.3 암시적 구현 vs 명시적 구현 — 무대 뒤에서 벌어지는 일

이 절이 이 장의 심장이다.

### 문법의 차이

```csharp
internal sealed class SimpleType : IDisposable
{
    // 암시적 구현 — 그냥 public 메서드다
    public void Dispose() { Console.WriteLine("public Dispose"); }
}
```

```csharp
internal sealed class SimpleType : IDisposable
{
    // 명시적 구현 — 메서드 이름 앞에 인터페이스 이름을 붙인다
    void IDisposable.Dispose() { Console.WriteLine("IDisposable Dispose"); }
}
```

차이를 표로 먼저 못 박는다.

| 항목 | 암시적 구현 | 명시적 구현 (EIMI) |
|---|---|---|
| 문법 | `public void Dispose()` | `void IDisposable.Dispose()` |
| 접근 제한자 | **`public` 필수** | **쓸 수 없다** (쓰면 컴파일 오류) |
| 메타데이터상 접근성 | `public` | **`private`** |
| 클래스 참조로 호출 | 가능 | **불가능** |
| 인터페이스 참조로 호출 | 가능 | 가능 (유일한 방법) |
| IntelliSense 노출 | 노출됨 | 노출 안 됨 |
| `virtual` 표시 | 가능 | **불가능** |
| 파생 클래스에서 `override` | 가능 (`virtual`일 때) | 불가능 |
| 파생 클래스에서 `base.` 호출 | 가능 | **불가능** |
| 같은 시그니처 충돌 해소 | 불가능 | **가능** |

두 구현을 **동시에** 둘 수도 있다. 그러면 호출 경로에 따라 다른 코드가 실행된다.

```csharp
internal sealed class SimpleType : IDisposable
{
    public void Dispose()             { Console.WriteLine("public Dispose"); }
    void IDisposable.Dispose()        { Console.WriteLine("IDisposable Dispose"); }
}

// 호출부
SimpleType st = new SimpleType();
st.Dispose();                    // public Dispose

IDisposable d = st;
d.Dispose();                     // IDisposable Dispose
```

### 컴파일 결과 — 메서드 테이블에 무슨 일이 벌어지는가

타입이 CLR에 로드되면 그 타입을 위한 **메서드 테이블**이 만들어지고 초기화된다. 이 테이블에는 타입이 새로 도입한 모든 메서드의 항목과, 타입이 물려받은 모든 가상 메서드의 항목이 들어간다. 물려받은 가상 메서드에는 상속 계층의 기반 타입이 정의한 메서드뿐 아니라 **인터페이스 타입이 정의한 메서드**도 포함된다.

`internal sealed class SimpleType : IDisposable`의 메서드 테이블에는 다음이 들어간다.

- 암묵적으로 상속한 기반 클래스 `Object`가 정의한 **모든 가상 인스턴스 메서드**
- 상속한 인터페이스 `IDisposable`이 정의한 **모든 인터페이스 메서드** — 여기서는 `Dispose` 하나
- `SimpleType`이 새로 도입한 메서드 `Dispose`

```text
   SimpleType의 메서드 테이블 (개념도)
   ┌─────────────────────────────────────────────┐
   │ Object 가상 슬롯                            │
   │   [0] ToString      → Object::ToString      │
   │   [1] Equals        → Object::Equals        │
   │   [2] GetHashCode   → Object::GetHashCode   │
   │   [3] Finalize      → Object::Finalize      │
   ├─────────────────────────────────────────────┤
   │ SimpleType 신규 슬롯                        │
   │   [4] Dispose       → SimpleType::Dispose   │
   ├─────────────────────────────────────────────┤
   │ 인터페이스 맵                               │
   │   IDisposable::Dispose ──┐                  │
   │                          └→ 슬롯 [4]        │
   └─────────────────────────────────────────────┘
   물리적 구조와 슬롯 조회의 실제 동작은 54.1절
```

프로그래머의 삶을 편하게 해주기 위해, C# 컴파일러는 **`SimpleType`이 도입한 `Dispose`가 곧 `IDisposable.Dispose`의 구현**이라고 가정한다. 근거는 둘이다.

1. 그 메서드가 `public`이다.
2. 인터페이스 메서드와 새 메서드의 **시그니처가 동일**하다 — 매개변수 타입도 반환 타입도 같다.

이 짝이 맞으면 컴파일러는 **메서드 테이블의 두 항목이 같은 구현을 가리켜야 한다**는 메타데이터를 방출한다. 참고로 새 `Dispose`에 `virtual`을 붙여도 컴파일러는 여전히 인터페이스 메서드와 일치한다고 판단한다.

### IL — `newslot virtual final`이 저절로 붙는다

이제 실물 IL을 본다. C# 소스에는 `virtual`이 한 글자도 없다.

```csharp
internal sealed class SimpleType : IDisposable
{
    public void Dispose() { Console.WriteLine("public Dispose"); }
}
```

컴파일 결과:

```il
.class private auto ansi sealed beforefieldinit SimpleType
       extends [System.Runtime]System.Object
       implements [System.Runtime]System.IDisposable
{
  .method public hidebysig newslot virtual final
          instance void  Dispose() cil managed
  {
    .maxstack  8
    IL_0000:  ldstr      "public Dispose"
    IL_0005:  call       void [System.Console]System.Console::WriteLine(string)
    IL_000a:  ret
  }
}
```

**`newslot virtual final`.** C#에서 `virtual`을 쓰지 않았는데 IL에서는 가상 메서드다. 이유는 명확하다.

> **CLR은 인터페이스 메서드가 `virtual`로 표시될 것을 요구한다.**

인터페이스 호출은 본질적으로 다형적이다. `IDisposable d = something;`에서 `d.Dispose()`를 부를 때 실제로 어떤 코드가 실행되는지는 `something`의 런타임 타입이 정한다. 이런 디스패치는 가상 슬롯 없이는 불가능하다. 따라서 CLR은 인터페이스를 구현하는 메서드가 반드시 가상이기를 요구하고, C# 컴파일러는 소스에 `virtual`이 없으면 **자동으로 붙인다**.

그러면 왜 `final`인가? C#의 의미론을 지키기 위해서다. C#에서 `public void Dispose()`는 가상 메서드가 아니다. 파생 클래스가 `override`할 수 없어야 한다. 그래서 컴파일러는 IL 수준에서 `virtual`로 만들되 **`final`을 붙여 재정의를 막는다**.

| C# 소스 | 방출되는 IL 한정자 | 파생 클래스가 `override` 가능? |
|---|---|---|
| `public void Dispose()` | `public newslot virtual final` | **아니오** |
| `public virtual void Dispose()` | `public newslot virtual` | 예 |
| `public abstract void Dispose();` | `public newslot abstract virtual` | 예 (필수) |
| `void IDisposable.Dispose()` | `private newslot virtual final` + `.override` | 아니오 |

`newslot`은 "기반 타입의 슬롯을 덮지 말고 새 슬롯을 하나 잡아라"는 뜻이다. 인터페이스 구현은 기반 클래스의 무언가를 재정의하는 것이 아니라 새 계약을 채우는 것이므로 새 슬롯이 맞다.

> **📌 C# 컴파일러는 비가상 인스턴스 메서드도 `callvirt`로 호출한다**
>
> 참조 타입의 인스턴스 메서드를 호출할 때 C# 컴파일러는 `call` 대신 `callvirt`를 방출한다. 메서드가 가상이 아니어도 그렇다. `callvirt`가 대상 참조의 **null 검사를 수행**하기 때문이다. `call`은 null 참조로도 그냥 호출해버리고, 메서드 안에서 필드에 접근하는 순간에야 터진다. `callvirt`는 호출 지점에서 `NullReferenceException`을 던진다 — 진단하기 훨씬 쉬운 위치다. 이 습관 때문에 IL만 보고 "가상 메서드구나"라고 단정하면 안 된다. 옵코드가 아니라 **메서드 정의의 한정자**를 봐야 한다.

### 명시적 구현의 IL — `.override` 지시문

이제 명시적 구현이다.

```csharp
internal sealed class SimpleType : IDisposable
{
    void IDisposable.Dispose() { Console.WriteLine("IDisposable Dispose"); }
}
```

```il
.class private auto ansi sealed beforefieldinit SimpleType
       extends [System.Runtime]System.Object
       implements [System.Runtime]System.IDisposable
{
  .method private hidebysig newslot virtual final
          instance void  System.IDisposable.Dispose() cil managed
  {
    .override [System.Runtime]System.IDisposable::Dispose
    .maxstack  8
    IL_0000:  ldstr      "IDisposable Dispose"
    IL_0005:  call       void [System.Console]System.Console::WriteLine(string)
    IL_000a:  ret
  }
}
```

세 가지가 달라졌다.

1. **접근성이 `private`이다.** C#에서 명시적 구현에는 접근 제한자를 쓸 수 없다. 그런데 컴파일러가 메타데이터를 만들 때는 접근성을 `private`으로 설정한다. 그래야 클래스 인스턴스를 가진 코드가 인터페이스 메서드를 그냥 호출하지 못한다.
2. **메서드 이름이 `System.IDisposable.Dispose`다.** 점이 들어간 이 이름은 C# 식별자 규칙으로는 만들 수 없다. 그래서 C# 코드에서 이름으로 부를 방법이 없다.
3. **`.override` 지시문이 붙는다.** 이것이 결정적이다.

`.override`는 메타데이터의 **MethodImpl 테이블**에 항목을 만든다. 이 테이블은 "이 메서드 정의가 저 메서드 선언의 구현이다"라는 **명시적 짝짓기**를 기록한다. 이름이 다르고 접근성이 `private`이어도, MethodImpl 항목 덕분에 CLR은 타입 로드 시 `IDisposable::Dispose` 슬롯을 이 메서드로 채운다.

암시적 구현에는 `.override`가 없다. **이름과 시그니처가 같다는 사실만으로** 런타임이 짝을 찾는다. 이것이 두 방식의 진짜 차이다.

```text
   암시적 구현                        명시적 구현
   ┌──────────────────────┐          ┌─────────────────────────────┐
   │ public Dispose()     │          │ private                     │
   │   newslot            │          │   System.IDisposable.Dispose│
   │   virtual final      │          │   newslot virtual final     │
   └──────────┬───────────┘          │   .override IDisposable::   │
              │                      │             Dispose         │
   이름·시그니처 일치로               └──────────────┬──────────────┘
   런타임이 슬롯 연결                                │
              ↓                        MethodImpl 테이블 항목으로
   IDisposable::Dispose 슬롯          명시적으로 슬롯 연결
                                                     ↓
                                       IDisposable::Dispose 슬롯
```

> **⚠️ 명시적 구현 멤버는 `virtual`로 표시할 수 없고, 그래서 `override`도 못 한다**
>
> ```csharp
> public class TextBox : IUndoable
> {
>     public virtual void IUndoable.Undo() { }   // 컴파일 오류
> }
> ```
>
> IL에서는 `virtual`인데 C#에서는 `virtual`을 못 쓴다는 것이 모순처럼 보이지만, 그렇지 않다. IL의 `final`이 재정의를 막고 있고, C#은 그 사실을 문법으로 반영한 것뿐이다. **명시적 구현 메서드는 타입의 객체 모델에 속하지 않는다.** 동작(메서드) 집합을 타입에 "부착"하되 그 동작을 표면에 드러내지 않는 장치다.

### 언제 명시적 구현을 쓰는가

명시적 구현을 쓸 이유는 넷이다.

**첫째, 시그니처 충돌을 해소할 때.** 이것만이 명시적 구현이 **유일한 해법**인 경우다.

```csharp
interface I1 { void Foo(); }
interface I2 { int  Foo(); }

public class Widget : I1, I2
{
    public void Foo() => Console.WriteLine("I1.Foo");      // 암시적
    int I2.Foo() { Console.WriteLine("I2.Foo"); return 42; } // 명시적 — 반환 타입이 다르다
}

// 호출부
Widget w = new Widget();
w.Foo();          // I1.Foo
((I1)w).Foo();    // I1.Foo
((I2)w).Foo();    // I2.Foo
```

반환 타입만 다른 두 메서드는 C#에서 오버로드할 수 없다. 명시적 구현 외의 길이 없다.

**둘째, 지나치게 특수한 멤버를 타입의 일반적인 사용에서 감출 때.** `ISerializable`을 구현하는 타입은 대개 그 멤버들을 표면에 드러내고 싶어하지 않는다. 명시적으로 구현하면 IntelliSense에서 사라지고, 필요한 사람만 캐스팅해서 쓴다. `IEnumerable<T>`를 구현할 때 비제네릭 `IEnumerable.GetEnumerator()`를 명시적으로 구현하는 관용구(18.11절)도 같은 이유다.

**셋째, 컴파일 타임 타입 안전성을 높이고 박싱을 줄일 때.** 제네릭 버전이 없는 비제네릭 인터페이스를 구현해야 할 때 쓰는 기법이다. 비제네릭 `IComparable`을 보자.

```csharp
public interface IComparable
{
    int CompareTo(object other);
}
```

구조체에 이대로 구현하면 `v.CompareTo(v)`가 인자를 박싱하고, `v.CompareTo(o)`처럼 엉뚱한 타입을 넘겨도 컴파일된다(런타임에 `InvalidCastException`). EIMI로 고친다.

```csharp
internal struct SomeValueType : IComparable
{
    private int m_x;
    public SomeValueType(int x) { m_x = x; }

    // 타입 안전한 공개 버전
    public int CompareTo(SomeValueType other) => m_x - other.m_x;

    // 계약을 채우는 명시적 구현 — 접근 제한자를 쓰지 않는다
    int IComparable.CompareTo(object other) => CompareTo((SomeValueType)other);
}

// 호출부
SomeValueType v = new SomeValueType(0);
object o = new object();

int n = v.CompareTo(v);   // 박싱 없음
n = v.CompareTo(o);       // 컴파일 오류 — 런타임 예외가 컴파일 타임 오류로 앞당겨졌다
```

이 기법은 `IConvertible`, `ICollection`, `IList`, `IDictionary`를 구현할 때 자주 쓰인다. 타입 안전한 버전을 노출하면서 값 타입의 박싱을 줄여준다.

> **⚠️ 그러나 인터페이스 타입 변수를 거치면 이득이 사라진다**
>
> ```csharp
> SomeValueType v = new SomeValueType(0);
> IComparable c = v;          // 박싱! 값 타입을 인터페이스로 캐스팅하는 순간
>
> object o = new object();
> int n = c.CompareTo(v);     // 원치 않는 박싱 (v가 object로)
> n = c.CompareTo(o);         // InvalidCastException
> ```
>
> 위 `Main`에서는 박싱이 **두 번** 일어난다. EIMI는 "인터페이스 변수를 거치지 않는 경로"만 개선한다. 근본 해법은 제네릭 인터페이스(`IComparable<T>`)와 제네릭 제약이다 — 18.6절에서 다룬다.

**넷째, 파생 클래스에서 재구현할 여지를 남길 때.** 18.4절의 주제다.

### 명시적 구현의 대가

C#에 EIMI를 처음 배우면 "멋진데?" 하고 남용하기 쉽다. **하지 마라.** 대가가 셋 있다.

**첫째, 문서와 IntelliSense가 사라진다.** .NET 참조 문서에서 명시적 인터페이스 구현은 목록에 나오지만 타입별 도움말은 없다. `Int32`가 `IConvertible`의 모든 메서드를 구현한다는 것은 문서에 나오는데, 정작 이렇게 쓰면 컴파일되지 않는다.

```csharp
int x = 5;
float s = x.ToSingle(null);                  // 컴파일 오류: 'int'에 'ToSingle' 정의가 없다
float t = ((IConvertible)x).ToSingle(null);  // 이렇게 써야 한다
```

캐스팅이 필요하다는 것은 전혀 자명하지 않고, 많은 개발자가 스스로 알아내지 못한다. **게다가 이 캐스팅은 값 타입을 박싱한다.**

**둘째, 값 타입 인스턴스가 인터페이스로 캐스팅될 때 박싱된다.** 위에서 본 그대로다.

**셋째, 파생 클래스가 EIMI를 호출할 수 없다.** 셋 중 아마 가장 큰 문제다.

```csharp
internal class Base : IComparable
{
    int IComparable.CompareTo(object o) { Console.WriteLine("Base"); return 0; }
}

internal sealed class Derived : Base, IComparable
{
    public int CompareTo(object o)
    {
        base.CompareTo(o);   // 컴파일 오류 — Base에는 호출할 수 있는 CompareTo가 없다
        return 0;
    }
}
```

`Base`는 호출 가능한 `public`이나 `protected` `CompareTo`를 제공하지 않는다. `IComparable` 타입 변수를 통해서만 부를 수 있는 `CompareTo`만 제공한다. 그렇다면 이렇게 하면 될까?

```csharp
public int CompareTo(object o)
{
    IComparable c = this;
    c.CompareTo(o);     // 무한 재귀!
    return 0;
}
```

안 된다. `Derived`의 `public CompareTo`가 곧 `Derived`의 `IComparable.CompareTo` 구현이므로, `c.CompareTo(o)`는 자기 자신을 부른다. **무한 재귀**다.

`Derived` 선언에서 `IComparable`을 빼면 해결되지만, 파생 타입이 인터페이스 메서드를 구현해야 하는 상황이라면 그럴 수 없다.

**올바른 해법은 기반 클래스가 인터페이스 메서드와 함께 가상 메서드를 제공하는 것이다.**

```csharp
internal class Base : IComparable
{
    int IComparable.CompareTo(object o) => CompareTo(o);   // 아래 가상 메서드로 위임

    // 파생 클래스를 위한 가상 메서드 (이름은 아무거나 좋다)
    public virtual int CompareTo(object o) { Console.WriteLine("Base"); return 0; }
}

internal sealed class Derived : Base, IComparable
{
    public override int CompareTo(object o)
    {
        Console.WriteLine("Derived");
        return base.CompareTo(o);     // 이제 Base의 구현을 부를 수 있다
    }
}
```

가상 메서드를 `public`이 아니라 `protected`로 두어도 좋다. 그 경우 다른 사소한 조정이 필요하다.

> **💡 EIMI는 필요할 때만, 그리고 항상 훅과 함께**
>
> 명시적 구현은 강력하지만 타입을 쓰기 어렵게 만든다. 규칙을 셋으로 줄이면 이렇다.
>
> 1. **시그니처 충돌 해소**나 **비제네릭 계약 감추기**가 아니면 암시적 구현을 쓴다.
> 2. 명시적으로 구현했다면, **파생 클래스가 재정의할 수 있는 `protected virtual` 훅**을 반드시 함께 제공한다.
> 3. 상속을 예상하지 않는다면 클래스를 `sealed`로 막아 재구현 자체를 봉쇄한다.
>
> 제네릭 인터페이스가 EIMI의 필요를 크게 줄여줬다. `IComparable<T>`가 있는데 `IComparable`을 위해 EIMI 곡예를 부릴 이유가 없다.

## 18.4 인터페이스 멤버를 가상으로 구현하기, 서브클래스에서 재구현하기

### 암시적 구현은 기본적으로 봉인되어 있다

18.3절에서 IL 한정자를 봤으므로 이 사실은 이제 놀랍지 않다. 암시적으로 구현된 인터페이스 멤버는 기본적으로 `newslot virtual final`이다. **`final`이 붙어 있으므로 파생 클래스가 재정의할 수 없다.** 재정의가 필요하면 기반 클래스에서 명시적으로 `virtual`이나 `abstract`를 붙여야 한다.

```csharp
public interface IUndoable { void Undo(); }

public class TextBox : IUndoable
{
    public virtual void Undo() => Console.WriteLine("TextBox.Undo");
}

public class RichTextBox : TextBox
{
    public override void Undo() => Console.WriteLine("RichTextBox.Undo");
}
```

이때 어느 경로로 불러도 서브클래스의 구현이 실행된다.

```csharp
RichTextBox r = new RichTextBox();
r.Undo();                  // RichTextBox.Undo
((IUndoable)r).Undo();     // RichTextBox.Undo
((TextBox)r).Undo();       // RichTextBox.Undo
```

세 경로가 전부 일치한다. **일관된 의미론**이다. 이것이 우리가 원하는 상태다.

IL을 보면 왜 그런지 알 수 있다.

```il
// TextBox::Undo
.method public hidebysig newslot virtual
        instance void  Undo() cil managed

// RichTextBox::Undo
.method public hidebysig virtual
        instance void  Undo() cil managed
```

`TextBox::Undo`에 `final`이 없다. C#에 `virtual`을 썼기 때문이다. `RichTextBox::Undo`에는 `newslot`이 없다 — 새 슬롯을 잡는 게 아니라 `TextBox`가 잡은 슬롯을 **덮어쓴다**. 인터페이스 맵은 그 슬롯을 가리키고 있으므로, 슬롯 내용이 바뀌면 인터페이스 호출도 자동으로 따라간다.

### 재구현 — 인터페이스를 다시 나열하기

파생 클래스는 기반 클래스가 이미 구현한 인터페이스 멤버를 **재구현(reimplementation)** 할 수 있다. 재구현은 인터페이스를 통해 호출될 때 멤버 구현을 **가로챈다**. 기반 클래스에서 그 멤버가 가상이든 아니든 동작하고, 암시적으로 구현했든 명시적으로 구현했든 동작한다. 다만 **명시적일 때 가장 잘 동작한다.**

명시적 구현부터 보자. `TextBox`가 `IUndoable.Undo`를 명시적으로 구현했으므로 `virtual`을 붙일 수 없다. "재정의"하려면 `RichTextBox`가 `IUndoable`을 다시 나열하고 `Undo`를 새로 구현해야 한다.

```csharp
public class TextBox : IUndoable
{
    void IUndoable.Undo() => Console.WriteLine("TextBox.Undo");
}

public class RichTextBox : TextBox, IUndoable   // 인터페이스를 다시 나열한다
{
    public void Undo() => Console.WriteLine("RichTextBox.Undo");
}

// 호출부
RichTextBox r = new RichTextBox();
r.Undo();                  // RichTextBox.Undo      — Case 1
((IUndoable)r).Undo();     // RichTextBox.Undo      — Case 2
```

두 경로 모두 서브클래스 구현으로 간다. `TextBox.Undo`는 명시적 구현이라 클래스 참조로는 애초에 부를 수 없다. 그래서 **어긋날 경로가 없다.**

### 재구현이 시스템을 깨는 순간

이제 `TextBox`가 `Undo`를 **암시적으로** 구현했다고 하자. `RichTextBox` 정의는 그대로다.

```csharp
public class TextBox : IUndoable
{
    public void Undo() => Console.WriteLine("TextBox.Undo");   // 암시적, virtual 아님
}

public class RichTextBox : TextBox, IUndoable
{
    public void Undo() => Console.WriteLine("RichTextBox.Undo");
}

// 호출부 — Undo를 부를 방법이 하나 더 생겼고, 그것이 시스템을 깬다
RichTextBox r = new RichTextBox();
r.Undo();                  // RichTextBox.Undo      — Case 1
((IUndoable)r).Undo();     // RichTextBox.Undo      — Case 2
((TextBox)r).Undo();       // TextBox.Undo          — Case 3  ← 어긋났다
```

**Case 3이 증거다.** 재구현의 가로채기는 **인터페이스를 통해 호출될 때만** 유효하고, 기반 클래스를 통해 호출될 때는 무력하다. 같은 객체에 대해 같은 이름의 메서드를 불렀는데, 참조 변수의 정적 타입에 따라 다른 코드가 실행된다. **일관성 없는 의미론**이고, 대체로 원하지 않는 결과다.

같은 현상을 CLR 쪽 용어로 다시 확인해보자.

```csharp
internal class Base : IDisposable
{
    // 암묵적으로 sealed다 — 파생 클래스가 재정의할 수 없다
    public void Dispose() { Console.WriteLine("Base's Dispose"); }
}

internal class Derived : Base, IDisposable
{
    // override가 아니다. new는 "IDisposable.Dispose를 재구현한다"는 뜻이다.
    // 기반 구현을 부르고 싶다면 본문에서 base.Dispose();
    new public void Dispose() { Console.WriteLine("Derived's Dispose"); }
}

// Derived 인스턴스를 Base 변수에 담았을 때 — 여기가 문제다
Base b = new Derived();
b.Dispose();                   // Base's Dispose      ← 변수 타입이 결정한다
((IDisposable)b).Dispose();    // Derived's Dispose   ← 객체 타입이 결정한다
```

이 예제에서 **같은 객체**에 대한 두 호출이 다른 메서드를 실행한다. `b.Dispose()`는 `b`의 **변수 타입**(`Base`)으로 결정되고, `((IDisposable)b).Dispose()`는 `b`가 가리키는 **객체의 타입**(`Derived`)으로 결정된다.

> **⚠️ 재구현은 인터페이스 경로만 고치고 기반 클래스 경로는 어긋난 채 남긴다**
>
> 위 코드가 그 증명이다. 이것이 재구현의 본질적 결함이고, 재구현을 **명시적으로 구현된 인터페이스 멤버를 재정의하는 전략으로 한정해야 하는** 이유다. 명시적 구현이면 "기반 클래스 경로" 자체가 존재하지 않으므로 어긋날 수 없다.
>
> 라이브러리를 설계할 때 이 함정은 특히 위험하다. 파생 타입 작성자는 인터페이스 호출만 테스트해보고 "잘 되네" 하고 넘어가기 쉽다. 기반 타입 참조로 호출하는 코드는 실제 배포 후에 발견된다.

### 재구현이 문제인 두 가지 이유

명시적 구현과 함께 쓰더라도 재구현에는 여전히 문제가 있다.

1. **서브클래스가 기반 클래스 메서드를 부를 방법이 없다.** 명시적 구현은 `base.`로 도달할 수 없다(18.3절).
2. **기반 클래스 작성자가 재구현을 예상하지 않았을 수 있다.** 그 결과를 대비하지 않았을 수 있다.

재구현은 서브클래싱이 **예상되지 않았을 때의 최후 수단**으로는 괜찮다. 그러나 더 나은 선택지는 **재구현이 필요 없도록 기반 클래스를 설계하는 것**이다. 방법은 둘이다.

**첫째, 암시적으로 구현할 때는 적절하다면 `virtual`을 붙인다.**

```csharp
public class TextBox : IUndoable
{
    public virtual void Undo() => Console.WriteLine("TextBox.Undo");
}
```

**둘째, 명시적으로 구현할 때 서브클래스가 로직을 재정의할 가능성이 있다면 다음 패턴을 쓴다.**

```csharp
public class TextBox : IUndoable
{
    void IUndoable.Undo() => Undo();                              // 아래 메서드로 위임

    protected virtual void Undo() => Console.WriteLine("TextBox.Undo");
}

public class RichTextBox : TextBox
{
    protected override void Undo() => Console.WriteLine("RichTextBox.Undo");
}
```

`RichTextBox`가 `IUndoable`을 다시 나열하지 않는다는 점에 주목하라. 재구현이 아니라 **정상적인 가상 메서드 재정의**다. 인터페이스로 부르든 기반 클래스로 부르든 항상 `RichTextBox.Undo`가 실행된다. 어긋날 경로가 없다.

서브클래싱을 전혀 예상하지 않는다면 클래스를 **`sealed`로 표시**해 인터페이스 재구현을 원천 봉쇄할 수 있다.

| 전략 | 인터페이스 경로 | 기반 클래스 경로 | 일관성 | 권장도 |
|---|---|---|---|---|
| 암시적 + `virtual` + `override` | 서브클래스 | 서브클래스 | **일관** | 최선 |
| 명시적 + `protected virtual` 훅 | 서브클래스 | 서브클래스 | **일관** | 최선 |
| 명시적 구현 + 재구현 | 서브클래스 | (경로 없음) | 일관 | 차선 |
| **암시적 구현 + 재구현** | 서브클래스 | **기반 클래스** | **어긋남** | 피하라 |
| `sealed` 클래스 | 기반 클래스 | 기반 클래스 | 일관 | 상황에 따라 |

> **💡 재구현은 "고칠 권한이 없을 때"의 도구다**
>
> 남의 라이브러리 클래스를 상속했는데 그 클래스가 인터페이스 멤버를 봉인해뒀고, 동작을 바꿔야만 하는 상황. 그럴 때 재구현이 유일한 탈출구다. 그러나 **내가 기반 클래스를 소유하고 있다면 재구현이 필요한 상황을 만들지 마라.** 위 표의 위 두 행 중 하나를 택하면 된다. API 설계 관점에서의 논의는 78.2절에 있다.

## 18.5 같은 시그니처를 가진 다중 인터페이스 구현

### 문제 상황

여러 인터페이스를 구현하다 보면 같은 이름과 시그니처의 메서드를 만나게 된다.

```csharp
public interface IWindow
{
    object GetMenu();
}

public interface IRestaurant
{
    object GetMenu();
}
```

`IWindow.GetMenu()`는 창의 메뉴 막대를, `IRestaurant.GetMenu()`는 식당의 메뉴판을 뜻한다. 둘 다 구현하는 타입은 **서로 다른 두 `GetMenu` 메서드**를 구현해야 한다. 어느 `GetMenu`가 어느 인터페이스의 구현인지 컴파일러에게 알려줘야 한다.

```csharp
public sealed class MarioPizzeria : IWindow, IRestaurant
{
    // IWindow의 GetMenu 구현
    object IWindow.GetMenu() { /* ... */ return null!; }

    // IRestaurant의 GetMenu 구현
    object IRestaurant.GetMenu() { /* ... */ return null!; }

    // 인터페이스와 무관한 GetMenu (선택 사항)
    public object GetMenu() { /* ... */ return null!; }
}
```

`MarioPizzeria` 객체를 쓰는 코드는 원하는 메서드를 부르기 위해 **특정 인터페이스로 캐스팅**해야 한다.

```csharp
MarioPizzeria mp = new MarioPizzeria();
mp.GetMenu();                     // MarioPizzeria의 public GetMenu
((IWindow)mp).GetMenu();          // MarioPizzeria의 IWindow.GetMenu
((IRestaurant)mp).GetMenu();      // MarioPizzeria의 IRestaurant.GetMenu
```

### 암시적 하나로 공유하는 경우

세 인터페이스 `IDrawToForm`, `IDrawToMemory`, `IDrawToPrinter`가 전부 `void Draw()`를 요구한다고 하자. 셋을 지원하는 `Octagon`을 이렇게 정의하면 컴파일은 깨끗이 된다.

```csharp
class Octagon : IDrawToForm, IDrawToMemory, IDrawToPrinter
{
    public void Draw() => Console.WriteLine("Drawing the Octagon...");   // 공유 로직
}
```

문제는 컴파일이 아니라 **의미**다. `((IDrawToPrinter)oct).Draw()`든 `((IDrawToMemory)oct).Draw()`든 같은 `Draw()`가 불린다. 창에 그리는 코드와 네트워크 프린터로 보내는 코드, 메모리 영역에 렌더링하는 코드는 전혀 다르다. 명시적 구현으로 갈라야 한다.

```csharp
class Octagon : IDrawToForm, IDrawToMemory, IDrawToPrinter
{
    void IDrawToForm.Draw()    => Console.WriteLine("Drawing to form...");
    void IDrawToMemory.Draw()  => Console.WriteLine("Drawing to memory...");
    void IDrawToPrinter.Draw() => Console.WriteLine("Drawing to a printer...");
}
```

명시적 구현의 일반 패턴은 이렇다.

```text
반환타입 인터페이스이름.메서드이름(매개변수) { ... }
```

접근 제한자를 쓰지 않는다. 명시적 구현 멤버는 자동으로 `private`이다.

```csharp
// 컴파일 오류 — 접근 제한자를 쓸 수 없다
public void IDrawToForm.Draw() { }
```

명시적 구현 멤버가 항상 암묵적으로 `private`이므로 **객체 수준에서는 더 이상 보이지 않는다**. `Octagon` 인스턴스에 점 연산자를 찍어도 IntelliSense에 `Draw` 멤버가 나오지 않는다. 원하는 기능에 접근하려면 명시적 캐스팅이 필요하다.

```csharp
Octagon oct = new Octagon();

IDrawToForm itfForm = (IDrawToForm)oct;      // 인터페이스 변수를 나중에 쓸 때
itfForm.Draw();

((IDrawToPrinter)oct).Draw();                // 한 번만 쓸 때의 축약형
if (oct is IDrawToMemory dtm) dtm.Draw();    // is 패턴
```

### 같은 제네릭 인터페이스를 여러 번 구현하기

제네릭 인터페이스의 큰 장점 중 하나가 여기 있다. **타입 인자만 다르면 같은 인터페이스를 여러 번 구현할 수 있다.**

```csharp
// 제네릭 IComparable<T>를 두 번 구현한다
public sealed class Number : IComparable<int>, IComparable<string>
{
    private int m_val = 5;

    public int CompareTo(int n)    => m_val.CompareTo(n);              // IComparable<int>
    public int CompareTo(string s) => m_val.CompareTo(int.Parse(s));   // IComparable<string>
}

// 호출부
Number n = new Number();
int r1 = ((IComparable<int>)n).CompareTo(5);        // int와 비교
int r2 = ((IComparable<string>)n).CompareTo("5");   // string과 비교
```

여기서는 **매개변수 타입이 다르므로** 명시적 구현이 필요 없다. 일반적인 오버로드로 해결된다.

> **⚠️ 타입 매개변수가 통합(unify)될 수 있으면 컴파일 오류다**
>
> ```csharp
> class Multi<T> : IComparable<T>, IComparable<int>   // 컴파일 오류 CS0695
> {
>     public int CompareTo(T other)   => 0;
>     public int CompareTo(int other) => 0;
> }
> ```
>
> `T`가 `int`로 대체되면 `IComparable<T>`와 `IComparable<int>`가 **같은 인터페이스**가 되어버린다. 이런 잠재적 충돌은 컴파일러가 미리 막는다. 오류 메시지는 "일부 타입 매개변수 치환에서 통합될 수 있으므로 둘 다 구현할 수 없다"는 취지다. 제네릭 제약으로 `T`를 `int`가 될 수 없게 만들어도 이 규칙은 완화되지 않는다.

### 명시적 구현 선택 판단표

| 상황 | 해법 |
|---|---|
| 이름·시그니처가 같고 **의미도 같다** | 암시적 구현 하나로 공유 |
| 이름·시그니처가 같고 **의미가 다르다** | 명시적 구현으로 분리 |
| 이름은 같고 **반환 타입만 다르다** | 명시적 구현 필수 (다른 방법 없음) |
| 같은 제네릭 인터페이스, **타입 인자가 다르다** | 일반 오버로드로 해결 |
| 같은 제네릭 인터페이스, **통합 가능성 있음** | 컴파일 불가 — 설계를 바꿔야 한다 |

> **💡 이름 충돌은 대개 설계 신호다**
>
> `IWindow.GetMenu`와 `IRestaurant.GetMenu`가 한 타입에서 만나는 상황은 실무에서 드물다. 명시적 구현이 필요할 정도로 충돌이 잦다면, 한 타입이 너무 많은 책임을 지고 있다는 신호일 수 있다. 두 인터페이스를 각각 구현하는 두 타입으로 분리하고 포함·위임(14.12절)으로 묶는 쪽이 나은 경우가 많다.

## 18.6 인터페이스와 박싱 — 구조체가 인터페이스를 구현할 때

### 문제의 핵심

참조 타입처럼 값 타입도 인터페이스를 0개 이상 구현할 수 있다. 그런데 **값 타입 인스턴스를 인터페이스 타입으로 캐스팅하면 그 인스턴스는 반드시 박싱된다.**

이유는 인터페이스 디스패치의 메커니즘에 있다. 인터페이스 변수는 **힙 위의 객체를 가리키는 참조**여야 한다. CLR이 그 객체의 **타입 객체 포인터**를 검사해 정확한 타입을 알아내야 하기 때문이다. 그다음 박싱된 값 타입에 대해 인터페이스 메서드를 호출할 때, CLR은 객체의 타입 객체 포인터를 따라가 타입 객체의 메서드 테이블을 찾고, 거기서 올바른 메서드를 부른다.

값 타입 인스턴스는 스택이나 다른 객체 안에 값 그대로 놓여 있다. 타입 객체 포인터가 없다. 그러므로 힙에 상자를 만들어 타입 정보를 붙여야 한다. 이것이 박싱이다(15.2절, 54.6절).

```csharp
interface I { void Foo(); }
struct S : I { public void Foo() { } }

// ...
S s = new S();
s.Foo();          // 박싱 없음
I i = s;          // 인터페이스로 캐스팅할 때 박싱이 일어난다
i.Foo();          // 박싱된 복사본에 대해 호출
```

핵심을 다시 못 박는다. **구조체에서 암시적으로 구현된 멤버를 직접 호출하는 것은 박싱하지 않는다.** 박싱은 인터페이스로 캐스팅하는 지점에서 일어난다.

IL을 보면 정확한 위치가 보인다.

```il
// S s = new S(); s.Foo();
IL_0000:  ldloca.s   s
IL_0002:  initobj    S
IL_0008:  ldloca.s   s
IL_000a:  call       instance void S::Foo()      // 직접 호출, 박싱 없음

// I i = s;
IL_000f:  ldloc.0
IL_0010:  box        S                           // ← 여기서 힙 할당
IL_0015:  stloc.1

// i.Foo();
IL_0016:  ldloc.1
IL_0017:  callvirt   instance void I::Foo()      // 인터페이스 디스패치
```

`box` 옵코드 하나가 힙 할당 하나다. 루프 안에서 이런 코드가 돌면 GC 압력이 그대로 늘어난다.

> **⚠️ 박싱된 복사본은 원본과 다른 객체다**
>
> ```csharp
> interface ICounter { void Increment(); int Value { get; } }
> struct Counter : ICounter
> {
>     private int _v;
>     public void Increment() => _v++;
>     public int Value => _v;
> }
>
> Counter c = new Counter();
> ICounter i = c;               // 박싱 — 이 시점의 c 값이 상자에 복사된다
> i.Increment();                // 상자 안의 복사본이 1이 된다
> Console.WriteLine(c.Value);   // 0 — 원본은 그대로다
> Console.WriteLine(i.Value);   // 1
> ```
>
> **가변 구조체가 인터페이스를 구현할 때 가장 흔한 사고**다. 인터페이스를 통한 변경이 원본에 반영되지 않는다. 구조체를 불변으로 설계하면(16.5절, 19.8절) 이 함정 자체가 사라진다.

### 제네릭 제약으로 박싱 피하기

박싱을 피하는 정공법은 **제네릭 타입 매개변수를 인터페이스로 제약하는 것**이다.

```csharp
// T는 IComparable과 IConvertible을 모두 구현하는 타입으로만 제약된다
static int M<T>(T t) where T : IComparable, IConvertible { /* ... */ return 0; }

int x = 5;
Guid g = new Guid();

M(x);   // Int32가 둘 다 구현하므로 컴파일된다
M(g);   // Guid는 IConvertible을 구현하지 않으므로 컴파일 오류
```

제네릭 인터페이스 제약의 이득은 둘이다.

**첫째, 타입 매개변수 하나를 여러 인터페이스로 제약할 수 있다.** 매개변수 타입을 인터페이스로 선언하면 "이 인터페이스를 구현한 아무 타입"만 표현할 수 있다. 제약을 여러 개 걸면 "이 인터페이스들을 **전부** 구현한 타입"을 요구할 수 있다. 클래스 하나와 인터페이스 둘로 제약하면 "지정한 기반 클래스에서 파생되고 두 인터페이스도 구현하는 타입"이 된다. 제약 문법 전체는 23.6절에 있다.

**둘째, 값 타입 인스턴스를 넘길 때 박싱이 줄어든다.** 위 코드에서 `x`(값 타입 `Int32` 인스턴스)를 `M`에 넘길 때 박싱이 일어나지 않는다. `M` 안에서 `t.CompareTo(...)`를 호출해도 그 호출을 위한 박싱은 없다. (`CompareTo`에 넘기는 인자 쪽에서는 여전히 박싱이 있을 수 있다.)

반면 `M`이 `static int M(IComparable t)`처럼 선언되었다면, `x`를 넘기기 위해 **박싱해야 한다**.

> **📌 `constrained.` 접두사 — 컴파일러가 방출하는 특별한 IL**
>
> 인터페이스 제약에 대해 C# 컴파일러는 **값 타입을 박싱하지 않고 인터페이스 메서드를 직접 호출하는** IL 명령을 방출한다. 인터페이스 제약을 쓰는 것 말고는 C# 컴파일러가 이 IL을 방출하게 할 다른 방법이 없다. 그래서 **값 타입에 대한 인터페이스 메서드 호출은 (제약 없이는) 항상 박싱을 일으킨다.**
>
> 그 IL이 `constrained.` 접두사다.
>
> ```il
> .method private hidebysig static void  M<(IFoo) T>(!!T t) cil managed
> {
>   IL_0000:  ldarga.s   t
>   IL_0002:  constrained. !!T
>   IL_0008:  callvirt   instance void IFoo::Foo()
>   IL_000d:  ret
> }
> ```
>
> `constrained.` 접두사가 붙은 `callvirt`는 JIT이 `T`의 실제 타입을 알고 나서 이렇게 처리한다.
>
> - `T`가 **값 타입**이고 그 타입이 메서드를 구현하면 → 박싱 없이 **직접 호출**한다. 인라이닝도 가능하다.
> - `T`가 **참조 타입**이면 → 참조를 역참조해 일반적인 `callvirt`처럼 디스패치한다.
> - `T`가 값 타입인데 메서드를 구현하지 않았다면(예: `Object.ToString`을 재정의하지 않은 구조체) → 박싱 후 호출한다.
>
> 첫 번째 경우가 우리가 원하는 것이다. 제네릭 인프라가 값 타입에 대해 코드를 특수화하는 방식은 23.11절에 있다.

### 박싱이 일어나는 지점 총정리

| 코드 | 박싱? | 이유 |
|---|---|---|
| `s.Foo()` (구조체 변수에 직접) | 없음 | 직접 호출 |
| `I i = s;` | **있음** | 인터페이스 캐스팅 |
| `((I)s).Foo()` | **있음** | 캐스팅 시점 |
| `void M(I i)` 에 `s` 전달 | **있음** | 암시적 캐스팅 |
| `void M<T>(T t) where T : I` 에 `s` 전달 | 없음 | 타입 특수화 |
| `M<T>` 안에서 `t.Foo()` | 없음 | `constrained.` |
| `List<S>`에 담기 | 없음 | `T = S`로 특수화 |
| `List<I>`에 `s` 담기 | **있음** | 요소 타입이 인터페이스 |
| `foreach`가 구조체 열거자를 쓸 때 | 없음 | 덕 타이핑(11.5절) |
| `foreach (var x in (IEnumerable<S>)coll)` | 있음(열거자) | 인터페이스로 얻은 열거자 |
| `using (s)` — `s`가 `IDisposable` 구조체 | 없음 | 컴파일러가 `constrained.` 방출 |

> **📌 `using` 문은 구조체를 박싱하지 않는다**
>
> `using` 문의 리소스가 `IDisposable`을 구현하는 **널 불가능 값 타입**일 때, C# 컴파일러는 인터페이스로 캐스팅하지 않고 `constrained.` 접두사를 붙인 호출을 방출한다. 그래서 구조체 열거자나 `ref struct` 기반 스코프 가드가 `using`과 함께 쓰여도 힙 할당이 없다. `using` 문법 전체는 33.5절이다.

> **⚠️ `ref struct`는 인터페이스로 캐스팅할 수 없다 ※C# 13**
>
> C# 13부터 `ref struct` 타입도 인터페이스를 **구현**할 수 있게 되었다. 그러나 `ref struct`를 **인터페이스 타입으로 변환하는 것은 여전히 금지**다. 그 변환이 곧 박싱이고, `ref struct`는 힙에 올라갈 수 없기 때문이다.
>
> 그러면 구현해봐야 무슨 쓸모인가? **제네릭 제약을 만족시키기 위해서다.** 같은 C# 13에서 도입된 `allows ref struct` 반제약(anti-constraint)을 타입 매개변수에 붙이면, `ref struct`도 그 타입 인자가 될 수 있다. 그러면 위에서 본 `constrained.` 경로를 타고 박싱 없이 인터페이스 메서드를 부를 수 있다.
>
> ```csharp
> // T는 ref struct일 수 있고, IDisposable을 구현해야 한다
> static void Use<T>(T resource) where T : IDisposable, allows ref struct
> {
>     using (resource) { /* ... */ }
> }
> ```
>
> `ref struct`의 기본 규칙은 16.6절, 심화는 68장에 있다. 버전별 도입 시점은 76.12절이다.

### 성능 영향

박싱 하나가 얼마나 비싼가는 상황에 따라 다르다. 확실한 것은 이렇다.

1. **힙 할당이 발생한다.** 0세대 할당이므로 포인터 증가만으로 끝나지만(63장), 0세대가 차면 GC가 돈다.
2. **간접 참조가 하나 늘어난다.** 데이터가 스택이나 배열에 인접해 있었다면 캐시 지역성이 깨진다(70장).
3. **복사가 일어난다.** 큰 구조체일수록 비싸다.
4. **JIT이 인라인하기 어려워진다.** 인터페이스 호출은 역가상화 대상이 되기 어렵다(55.5절).

핫 루프에서 값 타입을 인터페이스로 다룬다면 이 넷이 곱해진다. 실제 수치는 측정해야 안다 — 원칙은 67장이다.

> **💡 구조체가 인터페이스를 구현하는 것이 항상 나쁘지는 않다**
>
> `int`부터 `DateTime`까지 BCL의 거의 모든 구조체가 `IComparable<T>`, `IEquatable<T>`를 구현한다. 이유는 **제네릭 코드에서 제약으로 소비되기 때문**이다. `EqualityComparer<T>.Default`는 `T`가 `IEquatable<T>`를 구현하면 박싱 없는 경로를 택한다(25.2절). 즉 구조체의 인터페이스 구현은 "인터페이스 변수에 담기 위해서"가 아니라 "제네릭 제약을 만족시키기 위해서" 존재한다. 이 구분을 지키면 박싱은 일어나지 않는다.

## 18.7 기본 구현 멤버 ※C# 8

### 무엇을 풀려고 나왔나

인터페이스의 가장 큰 약점은 **버전 관리**다. 인터페이스에 멤버를 하나 추가하면 그 인터페이스를 구현한 **모든 타입이 컴파일 오류**가 난다. 널리 쓰이는 라이브러리라면 수천 개의 구현이 깨질 수 있다. 반면 기반 클래스에 메서드를 추가하면 파생 타입은 그냥 물려받는다. 사용자 소스 코드는 재컴파일할 필요조차 없다.

이 비대칭이 "인터페이스는 한번 배포하면 고칠 수 없는 계약"이라는 통념을 만들었다. C# 8의 **기본 구현 멤버(default interface member)** 가 이 문제를 겨냥한다.

```csharp
interface ILogger
{
    void Log(string text) => Console.WriteLine(text);
}
```

`Log`에 본문이 생겼다. 구현 타입은 `Log`를 구현하지 않아도 된다. **구현이 선택 사항이 된다.**

인기 있는 라이브러리의 인터페이스에 멤버를 추가하면서 (잠재적으로 수천 개의) 구현을 깨뜨리지 않으려 할 때 유용하다.

### 컴파일 결과

IL을 보면 무슨 일이 벌어졌는지 명확하다.

```il
.class interface public abstract auto ansi ILogger
{
  .method public hidebysig newslot virtual
          instance void  Log(string text) cil managed
  {
    .maxstack  8
    IL_0000:  ldarg.1
    IL_0001:  call       void [System.Console]System.Console::WriteLine(string)
    IL_0006:  ret
  }
}
```

`abstract`가 사라졌다. `virtual`이면서 **본문이 있는** 인터페이스 메서드다. CLR 관점에서 인터페이스가 이제 실행 가능한 코드를 담을 수 있게 되었다는 뜻이다.

> **⚠️ 기본 구현 멤버는 런타임 지원이 필요하다 — .NET Framework에서는 쓸 수 없다**
>
> 기본 인터페이스 구현 지원은 기저 플랫폼의 근본적인 변경을 요구한다. 그래서 대상 프레임워크가 **.NET Core 3 이상, .NET 5 이상, 또는 .NET Standard 2.1**일 때만 C#에서 쓸 수 있다. **.NET Framework은 지원하지 않는다.** .NET Framework을 멀티 타깃 대상에 포함하는 라이브러리라면 이 기능을 쓸 수 없다.

### 런타임 동작 — 캐스팅해야만 부를 수 있다

**기본 구현은 항상 명시적이다.** 이 한 문장이 기본 구현 멤버 사용의 절반을 설명한다.

`ILogger`를 구현하는 클래스가 `Log`를 정의하지 않으면, 그것을 부를 유일한 방법은 **인터페이스를 통하는 것**이다.

```csharp
class Logger : ILogger { }

// ...
Logger l = new Logger();
// l.Log("message");                 // 컴파일 오류 — Logger에 Log가 없다
((ILogger)new Logger()).Log("message");   // 이렇게만 부를 수 있다
```

실제 코드에서 이 제약이 얼마나 성가신지 보자.

```csharp
interface IPointy { byte Points { get; } }

interface IRegularPointy : IPointy
{
    int SideLength    { get; set; }
    int NumberOfSides { get; set; }
    int Perimeter => SideLength * NumberOfSides;   // 기본 구현
}

class Square : Shape, IRegularPointy
{
    public Square(string name) : base(name) { }
    public override void Draw() => Console.WriteLine("Drawing a square");

    public byte Points => 4;                       // IPointy에서 온다
    public int SideLength    { get; set; }         // IRegularPointy에서 온다
    public int NumberOfSides { get; set; }
    // Perimeter는 구현하지 않았다
}
```

```csharp
var sq = new Square("Boxy") { NumberOfSides = 4, SideLength = 4 };

// 컴파일되지 않는다 — Square에 Perimeter 멤버가 없다
// Console.WriteLine(sq.Perimeter);

// 구현이 있는 곳으로 캐스팅해야 한다
Console.WriteLine($"둘레: {((IRegularPointy)sq).Perimeter}");
```

한 가지 회피법은 **항상 인터페이스 타입으로 코딩하는 것**이다.

```csharp
IRegularPointy sq = new Square("Boxy") { NumberOfSides = 4, SideLength = 4 };
```

그런데 이러면 `Draw()` 메서드와 `PetName` 프로퍼티가 인터페이스에 없으므로 컴파일 오류가 난다. 이 예제는 사소하지만 **기본 인터페이스 구현의 문제 하나를 정확히 보여준다.** 이 기능을 쓰기 전에 "호출 코드가 구현이 어디 있는지 알아야 한다"는 대가를 계산해야 한다.

> **📌 기본 구현이 항상 명시적인 것은 다중 상속 문제를 막기 위해서다**
>
> 한 클래스가 구현하는 두 인터페이스에 **같은 기본 멤버**가 추가되었다고 하자. 만약 기본 구현이 클래스의 멤버 목록에 암시적으로 합류한다면, "둘 중 어느 것이 불리는가"라는 고전적인 다이아몬드 문제가 발생한다. 기본 구현을 항상 명시적으로 유지하면 **호출자가 어느 인터페이스로 캐스팅했는지가 답을 결정**하므로 모호함이 원천적으로 없다.

### 인터페이스 계층에서의 기본 구현

기본 구현은 **파생 인터페이스로 자동 전파**된다.

```csharp
public interface IDrawable
{
    void Draw();
    int TimeToDraw() => 5;              // 기본 구현
}

public interface IAdvancedDraw : IDrawable
{
    void DrawUpsideDown();
}

public class BitmapImage : IAdvancedDraw
{
    public void Draw() => Console.WriteLine("Drawing...");
    public void DrawUpsideDown() { }
}

// 호출부
BitmapImage myBitmap = new BitmapImage();
if (myBitmap is IAdvancedDraw iAdvDraw)
    Console.WriteLine($"Time to draw: {iAdvDraw.TimeToDraw()}");   // 5
// myBitmap.TimeToDraw();   // 컴파일되지 않는다
```

`IAdvancedDraw`로 캐스팅하면 `TimeToDraw()`에 접근할 수 있다. `BitmapImage` 인스턴스 자체는 그 기본 구현에 접근하지 못하는데도 그렇다.

하위 인터페이스가 자기만의 기본 구현을 제공하려면 상위 구현을 **`new`로 가려야** 한다 — `new int TimeToDraw() => 15;`. 반면 **클래스는 가릴 필요 없이 그냥 구현하면 된다.** `BitmapImage`에 `public int TimeToDraw() => 12;`를 넣으면 어느 경로로 불러도 **인스턴스의 메서드가 실행된다**.

```csharp
Console.WriteLine($"Time to draw: {myBitmap.TimeToDraw()}");                    // 12
Console.WriteLine($"Time to draw: {((IDrawable)myBitmap).TimeToDraw()}");       // 12
Console.WriteLine($"Time to draw: {((IAdvancedDraw)myBitmap).TimeToDraw()}");   // 12
```

**클래스의 구현이 언제나 이긴다.** 기본 구현은 "아무도 구현하지 않았을 때의 대비책"이다.

### 제약 — 상태를 가질 수 없다

기본 구현 멤버가 추상 클래스와 결정적으로 다른 점이다.

**인터페이스는 여전히 인스턴스 필드를 가질 수 없다.** 기본 구현이 참조할 수 있는 것은 인터페이스에 선언된 다른 멤버(추상이든 기본이든)와 정적 멤버뿐이다.

```csharp
interface ICounter
{
    private int _count;                  // 컴파일 오류 — 인스턴스 필드 불가
    void Increment() => _count++;        // 따라서 이런 기본 구현도 불가능
}

interface ICounter                       // 이렇게 써야 한다
{
    int Count { get; set; }              // 저장은 구현 타입의 책임
    void Increment() => Count++;         // 기본 구현은 추상 멤버 위에 서 있다
}
```

상태가 필요하면 **추상 프로퍼티로 선언하고 구현 타입에 저장을 맡겨야 한다.**

이것이 **인터페이스의 원칙 — 상태가 아니라 동작을 정의한다**는 원칙과 일치한다.

| 능력 | 추상 클래스 | 인터페이스 (C# 8 이후) |
|---|---|---|
| 메서드 본문 | 가능 | **가능** |
| 접근 제한자 | 전부 | **전부** (C# 8 이후) |
| 정적 멤버 | 가능 | **가능** |
| 정적 생성자 | 가능 | **가능** |
| **인스턴스 필드** | 가능 | **불가** |
| 인스턴스 생성자 | 가능 | 불가 |
| 파이널라이저 | 가능 | 불가 |
| 다중 채택 | 불가 (단일 상속) | 가능 |
| 구현이 클래스 멤버로 노출 | 예 | **아니오** (캐스팅 필요) |

> **⚠️ 기본 구현은 "인터페이스가 클래스가 된 것"이 아니다**
>
> C# 8의 인터페이스 변경은 기존 언어 기능에 대한 가장 큰 변화 중 하나이고, 인터페이스를 추상 클래스의 기능에 상당히 가깝게 만들었다. 여기에 **여러 인터페이스를 구현할 수 있는 능력**까지 더해진다. 그러나 이 물에서는 조심해서 걸어야 한다. **할 수 있다는 것이 해야 한다는 뜻은 아니다.**
>
> 인스턴스 필드가 없다는 제약, 캐스팅해야 부를 수 있다는 불편, .NET Framework 미지원 — 이 셋만으로도 "이제 추상 클래스 대신 인터페이스를 쓰자"는 결론은 성립하지 않는다.

> **💡 기본 구현을 쓸 자리와 쓰지 말 자리**
>
> **쓸 자리** — 이미 배포된 인터페이스에 멤버를 추가해야 하고, 대부분의 구현 타입이 쓸 만한 합리적인 기본 동작이 존재할 때. 예를 들어 `IEnumerable<T>`에 `TryGetNonEnumeratedCount`류의 멤버를 추가한다면, "무조건 `false`를 반환한다"는 안전한 기본 구현이 있다.
>
> **쓰지 말 자리** — 인터페이스 정의자가 그 멤버가 어떻게 구현되어야 하는지, 심지어 구현될 수 있는지도 모를 때. 그런 기본 구현은 항상 대체되므로 노력 낭비다. `IComparable`의 `CompareTo`가 그런 예다. 실용적으로 의미 있는 기본 구현이 존재하지 않는다. 굳이 짜낸다면 두 객체의 `ToString()` 결과를 비교하는 것 정도인데, 모든 타입이 자기 `CompareTo`를 구현해야 마땅하다. 대부분의 인터페이스가 이 부류에 속한다.
>
> 요약하면 기본 구현은 **버전 관리용 안전장치**이지 코드 재사용 메커니즘이 아니다. 코드 재사용이 목적이라면 추상 클래스나 확장 메서드가 맞다.

## 18.8 정적 인터페이스 멤버와 정적 추상 멤버 ※C# 11

인터페이스는 정적 멤버도 선언할 수 있다. 두 종류가 있다.

- **정적 비가상 인터페이스 멤버** ※C# 8
- **정적 가상/추상 인터페이스 멤버** ※C# 11

> **📌 인스턴스 멤버와 반대다**
>
> 인터페이스의 인스턴스 멤버는 기본이 가상이다. 반면 **정적 멤버는 기본이 비가상**이다. 정적 인터페이스 멤버를 가상으로 만들려면 `static abstract`나 `static virtual`을 명시해야 한다.

### 정적 비가상 인터페이스 멤버 ※C# 8

정적 비가상 멤버는 주로 **기본 구현 멤버를 작성하는 것을 돕기 위해** 존재한다. 클래스나 구조체가 구현하는 것이 아니라 **직접 소비된다**. 메서드·프로퍼티·이벤트·인덱서와 함께 **필드**도 허용된다. 이 필드는 보통 기본 구현 내부 코드에서 접근한다.

```csharp
interface ILogger
{
    void Log(string text) => Console.WriteLine(Prefix + text);

    static string Prefix = "";     // 정적 필드 — 인스턴스 필드가 아니다
}
```

정적 비가상 인터페이스 멤버는 기본이 `public`이므로 바깥에서도 접근할 수 있다.

```csharp
ILogger.Prefix = "File log: ";
```

접근 제한자(`private`, `protected`, `internal`)를 붙여 제한할 수 있다.

**인스턴스 필드는 (여전히) 금지다.** 이것은 동작을 정의하고 상태를 정의하지 않는다는 인터페이스의 원칙과 일치한다.

정적 생성자도 가능하다. 매개변수가 없어야 하고 정적 프로퍼티·메서드에만 접근할 수 있다.

```csharp
interface IRegularPointy : IPointy
{
    int SideLength    { get; set; }
    int NumberOfSides { get; set; }
    int Perimeter => SideLength * NumberOfSides;

    static string ExampleProperty { get; set; }
    static IRegularPointy() => ExampleProperty = "Foo";
}

// 정적 프로퍼티는 인스턴스 변수가 아니라 인터페이스 이름으로 접근한다
Console.WriteLine(IRegularPointy.ExampleProperty);   // Foo
IRegularPointy.ExampleProperty = "Updated";
```

> **⚠️ 인터페이스의 정적 필드는 전역 가변 상태다**
>
> `ILogger.Prefix`는 프로세스 전체에서 하나뿐인 변수다. 여러 스레드가 동시에 쓰면 경합이 생기고, 테스트 간에 상태가 새어 나간다. 정적 필드가 인터페이스에 있다고 해서 특별한 보호를 받지 않는다. 정적 필드가 어디에 저장되는지는 54.5절, 정적 멤버의 올바른 초기화는 79.5절에 있다. **기본 구현에서 쓰는 상수 성격의 값**으로만 제한하는 것이 안전하다.

### 정적 가상/추상 인터페이스 멤버 ※C# 11

C# 11부터 정적 인터페이스 멤버를 `static abstract`나 `static virtual`로 표시할 수 있다. **정적 다형성(static polymorphism)** 을 가능하게 하는 고급 기능이다.

```csharp
interface ITypeDescribable
{
    static abstract string Description { get; }
    static virtual  string Category    => null;
}
```

구현 클래스나 구조체는 `static abstract` 멤버를 **반드시** 구현해야 하고, `static virtual` 멤버는 선택적으로 구현할 수 있다.

```csharp
class CustomerTest : ITypeDescribable
{
    public static string Description => "Customer tests";     // 필수
    public static string Category    => "Unit testing";       // 선택
}
```

메서드·프로퍼티·이벤트뿐 아니라 **연산자와 변환**도 정적 가상 인터페이스 멤버의 합법적인 대상이다(22장). IL에서는 이렇게 보인다.

```il
.class interface public abstract auto ansi ITypeDescribable
{
  .method public hidebysig abstract virtual static
          string get_Description() cil managed
  {
  }
}
```

`abstract virtual static`이 한자리에 모여 있다. .NET 7 이전에는 IL 수준에서도 불가능했던 조합이다.

### 어떻게 호출하는가

정적 가상 인터페이스 멤버는 **제약된 타입 매개변수를 통해** 호출한다. 인터페이스 타입 변수로는 부를 수 없다 — 애초에 인스턴스가 필요 없는 멤버이기 때문이다.

```csharp
static void Describe<T>() where T : ITypeDescribable
{
    Console.WriteLine(T.Description);      // 타입 매개변수 위의 정적 멤버 호출
    Console.WriteLine(T.Category);
}

// 호출
Describe<CustomerTest>();
```

`T.Description`이라는 문법이 핵심이다. `T`는 타입 매개변수이고, JIT이 `T`를 구체 타입으로 대체하면서 그 타입의 정적 멤버로 해석한다.

> **⚠️ 정적 추상 멤버는 인터페이스 타입 자체로는 호출할 수 없다**
>
> ```csharp
> ITypeDescribable.Description;    // 안 된다
> ```
>
> 어떤 구현의 `Description`을 말하는지 알 수 없기 때문이다. 인스턴스 멤버라면 객체가 그 답을 담고 있지만, 정적 멤버에는 객체가 없다. **타입 매개변수만이 "어느 타입인가"라는 정보를 실어 나른다.**

### 왜 만들어졌나 — 제네릭 수학의 기반

정적 추상 멤버가 도입된 실질적 이유는 **제네릭 수학(generic math)** 이다.

C# 11 이전에는 `T`가 숫자 타입이라도 `T a + T b`를 쓸 수 없었다. `+` 연산자는 정적 메서드(`op_Addition`)인데, 정적 메서드는 인터페이스로 계약할 수 없었기 때문이다. 그래서 "제네릭 합계 함수"를 쓰려면 타입마다 오버로드를 쓰거나 델리게이트를 넘기거나 `dynamic`을 써야 했다.

정적 추상 멤버가 이 벽을 허물었다. BCL은 `System.Numerics`에 `IAdditionOperators<TSelf, TOther, TResult>`, `INumber<TSelf>` 같은 인터페이스 계층을 정의하고, 모든 숫자 타입이 이를 구현하게 만들었다.

```csharp
using System.Numerics;

static T Sum<T>(IEnumerable<T> values) where T : INumber<T>
{
    T total = T.Zero;              // 정적 추상 프로퍼티
    foreach (T v in values)
        total += v;                // 정적 추상 연산자
    return total;
}

Console.WriteLine(Sum(new[] { 1, 2, 3 }));          // 6   (int)
Console.WriteLine(Sum(new[] { 1.5, 2.5 }));         // 4   (double)
Console.WriteLine(Sum(new[] { 1.5m, 2.5m }));       // 4.0 (decimal)
```

한 메서드가 `int`, `double`, `decimal`, `BigInteger`, 사용자 정의 숫자 타입까지 전부 처리한다. 게다가 `T`가 값 타입이면 제네릭 특수화 덕분에 **박싱도 가상 호출도 없다**(23.11절).

> **📌 상세는 다른 장에**
>
> 정적 추상 멤버로 연산자를 계약하는 문법과 다형적 연산자의 설계는 22.7절, `INumber<T>` 계열의 인터페이스 계층 전체와 제네릭 수학의 실전 사용법은 22.8절에 있다. 여기서는 "인터페이스가 정적 멤버를 계약할 수 있게 되었다"는 언어 규칙까지만 다룬다.

> **⚠️ 정적 추상 멤버는 .NET 7 이상이 필요하다**
>
> 언어 기능은 C# 11이지만 런타임 지원이 필요하다. .NET 6 이하를 대상으로 하면 컴파일되지 않는다. .NET 6에는 미리보기 기능으로 들어 있었으나 정식 지원은 .NET 7부터다.

| 종류 | 도입 | 구현 타입이 채우는가 | 호출 방법 |
|---|---|---|---|
| 인스턴스 추상 멤버 | C# 1 | 필수 | 인터페이스 변수 |
| 인스턴스 기본 구현 멤버 | C# 8 | 선택 | 인터페이스 변수 (캐스팅 필요) |
| 정적 비가상 멤버 | C# 8 | 아니오 | `IFoo.Member` |
| 정적 추상 멤버 | C# 11 | 필수 | `T.Member` (제약된 타입 매개변수) |
| 정적 가상 멤버 | C# 11 | 선택 | `T.Member` (제약된 타입 매개변수) |

## 18.9 인터페이스 디스패치 비용 — 인터페이스 맵과 스텁

### 왜 인터페이스 호출이 가상 호출보다 비싼가

클래스의 가상 메서드 호출은 개념적으로 단순하다. 객체 헤더에서 메서드 테이블 포인터를 읽고, **고정된 슬롯 번호**로 인덱싱해 함수 주소를 얻고, 호출한다. 슬롯 번호는 컴파일 타임에 정해진다.

인터페이스 호출은 그렇게 단순할 수 없다. 이유는 구조적이다.

```text
   class Dog : IAnimal, IComparable  →  IAnimal.Speak는 몇 번 슬롯?
   class Cat : IPet, IAnimal         →  IAnimal.Speak는 몇 번 슬롯?

   두 클래스는 인터페이스를 다른 순서로, 다른 개수만큼 구현한다.
   IAnimal.Speak가 Dog에서 4번 슬롯이라 해도
   Cat에서 4번 슬롯이라는 보장이 없다.
```

클래스 계층에서는 파생 클래스가 기반 클래스의 슬롯 레이아웃을 그대로 물려받고 뒤에 덧붙이므로, 기반의 슬롯 번호가 파생에서도 유효하다. 인터페이스는 **여러 계층을 가로지르므로** 그런 보장이 없다. 그래서 각 타입의 `MethodTable`은 별도의 **인터페이스 맵(interface map)** 을 갖고, 인터페이스 메서드 호출은 이 맵을 거쳐 실제 슬롯을 찾아야 한다.

### 가상 스텁 디스패치

CoreCLR은 인터페이스 호출을 **가상 스텁 디스패치(virtual stub dispatch, VSD)** 로 처리한다. 개략적인 흐름은 이렇다.

```text
   인터페이스 호출 지점 (call site)
        │
        ↓
   ┌─────────────────────────────────────────────┐
   │ 처음: lookup stub                           │
   │   느린 경로로 인터페이스 맵을 해석한다      │
   └───────────────┬─────────────────────────────┘
                   ↓  해석 결과로 스텁을 교체(백패칭)
   ┌─────────────────────────────────────────────┐
   │ 이후: dispatch stub                         │
   │   "이 호출 지점에서 본 타입이 T였다"를 기억 │
   │   같은 타입이면 → 캐시된 주소로 바로 점프   │
   │   다른 타입이면 → resolve stub으로          │
   └───────────────┬─────────────────────────────┘
                   ↓
   ┌─────────────────────────────────────────────┐
   │ resolve stub                                │
   │   전역 해석 캐시를 조회하고, 필요하면       │
   │   인터페이스 맵을 다시 해석한다             │
   └─────────────────────────────────────────────┘

   물리 구조와 실측 방법은 54.1절
```

핵심 성질은 **단형적(monomorphic) 호출 지점에 최적화되어 있다**는 것이다. 어떤 호출 지점에서 항상 같은 구체 타입만 보인다면, 첫 호출 이후 dispatch stub의 캐시가 적중해 거의 가상 호출 수준으로 빨라진다. 반대로 같은 호출 지점에 여러 타입이 번갈아 들어오면(다형적, polymorphic) 캐시가 계속 빗나가고 resolve stub까지 내려간다.

### JIT의 개입 — 역가상화

JIT은 호출을 **직접 호출로 바꾸려고(devirtualization)** 시도한다. 성공하면 인라이닝까지 열린다.

| 상황 | 역가상화 가능성 |
|---|---|
| `sealed` 클래스의 참조로 호출 | 높다 — 정확한 타입을 안다 |
| `new`로 만든 객체를 바로 호출 | 높다 |
| 인터페이스 변수로 호출 | 낮다 — 구현 타입을 모른다 |
| 제네릭 제약 + 값 타입 인자 | **확정적** — `constrained.`로 직접 호출 |
| 제네릭 제약 + 참조 타입 인자 | 낮다 — 코드를 공유하므로 |
| 계층형 컴파일의 Tier-1 + GDV | 중간 — 프로파일이 단형적이면 가드된 역가상화 |

**가드된 역가상화(guarded devirtualization, GDV)** 는 Tier-0 실행 중 수집한 프로파일에서 "이 호출 지점의 97%가 `List<int>`였다"는 정보를 얻으면, Tier-1 코드에서 `if (타입 == List<int>) { 인라인된 코드 } else { 원래 인터페이스 호출 }` 형태로 재작성하는 최적화다. 상세는 55.5절이다.

### 성능 순서

절대 수치는 하드웨어·런타임 버전·호출 패턴에 따라 크게 달라지므로 여기서는 **순서만** 적는다. 반드시 자기 코드에서 측정해야 한다(67장).

```text
   빠름  ┌────────────────────────────────────────┐
         │ 인라인된 직접 호출                     │
         │ 직접 호출 (call)                       │
         │ 제네릭 제약 + 값 타입 (constrained.)   │
         │ 가상 호출 (callvirt, 슬롯 인덱싱)      │
         │ 인터페이스 호출 — 단형적 (캐시 적중)   │
         │ 인터페이스 호출 — 다형적 (캐시 미스)   │
   느림  └────────────────────────────────────────┘
```

> **⚠️ "인터페이스 호출은 비싸다"를 최적화의 출발점으로 삼지 마라**
>
> 인터페이스 호출 자체의 오버헤드는 대부분의 코드에서 측정 불가능한 수준이다. 진짜 비용은 대개 **인터페이스 호출이 인라이닝을 막아서** 생긴다. 작은 메서드(프로퍼티 접근자 등)를 루프 안에서 인터페이스로 부르면, 호출 오버헤드보다 인라이닝 실패로 잃는 최적화 기회가 훨씬 크다.
>
> 그래서 최적화의 방향은 "인터페이스를 없앤다"가 아니라 "핫 경로에서 타입을 구체화해 JIT이 역가상화할 수 있게 한다"이다. 대표적인 수단이 **제네릭 제약**이다(18.6절).

> **💡 핫 경로에서 인터페이스를 제네릭 제약으로 바꾸는 패턴**
>
> ```csharp
> // 인터페이스 매개변수 — 값 타입이면 박싱, 인터페이스 디스패치, 인라인 불가
> static long SumAll(IEnumerable<int> src)
> {
>     long total = 0;
>     foreach (int v in src) total += v;
>     return total;
> }
>
> // 제네릭 제약 — 값 타입 열거자면 박싱 없음, 직접 호출, 인라인 가능
> static long SumAll<TEnumerable>(TEnumerable src)
>     where TEnumerable : IEnumerable<int>
> {
>     long total = 0;
>     foreach (int v in src) total += v;
>     return total;
> }
> ```
>
> 두 번째 형태는 `List<int>`를 넘기면 `List<int>.Enumerator`(구조체)를 값으로 다루므로 `MoveNext`가 인라인될 수 있다. BCL 내부와 고성능 라이브러리가 흔히 쓰는 기법이다. 다만 **제네릭 인스턴스화가 늘어나 코드 크기가 커진다.** 핫 경로에만 쓰고, 반드시 측정하라.

## 18.10 인터페이스 메서드와 가상 메서드의 차이

두 메커니즘은 겉보기에 비슷하다. 둘 다 "기반 타입이 선언하고 파생 타입이 구현하며, 호출 시점에 실제 타입이 결정한다." 그러나 규칙은 상당히 다르다.

### 전면 비교표

| 항목 | 클래스 가상 메서드 | 인터페이스 메서드 |
|---|---|---|
| 선언 위치 | 클래스(추상 클래스 포함) | 인터페이스 |
| 다중 채택 | 불가 (단일 상속) | **가능** |
| 값 타입이 참여 | 불가 (구조체는 상속 불가) | **가능** (단 박싱 주의) |
| 구현의 기본 상태 | 비가상 (`virtual` 명시 필요) | **자동으로 `virtual final`** |
| 파생 클래스의 재정의 | `override` | 기반이 `virtual`일 때만 `override`, 아니면 **재구현** |
| 접근성 | 자유 (`protected` 등) | 사실상 `public` (명시적이면 `private`) |
| `base.`로 기반 호출 | 가능 | 명시적 구현은 **불가** |
| 상태(필드) 공유 | 가능 | **불가** |
| 새 멤버 추가 시 | 파생 타입 무영향 | **모든 구현이 깨진다** (C# 8 기본 구현으로 완화) |
| 디스패치 방식 | 고정 슬롯 인덱싱 | 인터페이스 맵 + 스텁 (18.9절) |
| 역가상화 난이도 | 낮음 | 높음 |
| 생성자·초기화 로직 | 물려줄 수 있음 | 없음 |
| 관계 | IS-A | CAN-DO |

### 같은 이름이 만드는 세 가지 상황

이 셋을 구별하지 못하면 코드를 잘못 읽는다.

**(1) 재정의(override)** — 기반이 `virtual`, 파생이 `override`. 슬롯을 덮어쓴다. **모든 경로가 파생 구현으로 간다.**

```csharp
class Base { public virtual void M() => Console.WriteLine("Base"); }
class Derived : Base { public override void M() => Console.WriteLine("Derived"); }

Base b = new Derived();
b.M();   // Derived
```

**(2) 숨기기(new)** — 기반과 파생이 무관한 별개 메서드. 새 슬롯을 잡는다. **변수의 정적 타입이 결정한다.**

```csharp
class Base { public void M() => Console.WriteLine("Base"); }
class Derived : Base { public new void M() => Console.WriteLine("Derived"); }

Base b = new Derived();
b.M();               // Base       ← 변수 타입
((Derived)b).M();    // Derived
```

**(3) 재구현(reimplementation)** — 파생이 인터페이스를 다시 나열하고 새 구현을 제공. **인터페이스 맵만 바뀐다.**

```csharp
interface I { void M(); }
class Base : I { public void M() => Console.WriteLine("Base"); }
class Derived : Base, I { public new void M() => Console.WriteLine("Derived"); }

Base b = new Derived();
b.M();               // Base      ← 클래스 경로: 변수 타입이 결정
((I)b).M();          // Derived   ← 인터페이스 경로: 객체 타입이 결정
```

(2)와 (3)은 C# 소스가 거의 같다. 차이는 **파생 클래스가 인터페이스를 다시 나열했는가**뿐이다. 그런데 결과는 인터페이스 경로에서 정반대다. `new` 한정자의 일반 규칙과 언제 쓰는가는 14.3절과 79.8절에 있다.

> **⚠️ `new` 한정자 없이 재구현하면 경고가 뜬다**
>
> ```csharp
> class Derived : Base, I { public void M() { } }   // 경고 CS0108
> ```
>
> "상속된 멤버를 숨긴다. 의도한 것이라면 `new` 키워드를 쓰라"는 취지의 경고다. 컴파일은 되고 동작도 `new`를 붙인 것과 같지만, **경고를 끄지 말고 `new`를 명시하라.** 명시된 `new`는 "나는 이 숨기기를 의도했다"는 문서 역할을 한다. 경고를 방치하면 나중에 기반 클래스에 메서드가 추가되어 우연히 이름이 겹칠 때 알아채지 못한다.

### 인터페이스 멤버 조회 규칙이 다른 이유

14장에서 오버로드 해석을 다룰 때 "가장 파생된 타입의 멤버가 이긴다"는 규칙을 봤다. 이 규칙은 **클래스 상속**에 대한 것이다. 인터페이스에는 그대로 적용되지 않는다.

인터페이스는 다중 상속이 가능하므로 "가장 파생된 타입"이 유일하지 않을 수 있다.

```csharp
interface IA { void M(); }
interface IB { void M(); }
interface IC : IA, IB { }

// IC 타입 변수로 M을 부르면?
IC c = GetSomething();
c.M();      // 컴파일 오류 CS0121 — IA.M과 IB.M 사이에서 모호하다
```

이 경우 `((IA)c).M()`처럼 어느 것을 원하는지 명시해야 한다. C# 8의 기본 구현이 개입하면 규칙이 더 복잡해진다. 컴파일러는 **가장 구체적인 구현(most specific implementation)** 을 찾고, 유일하게 결정되지 않으면 오류를 낸다. 실무에서는 **모호해질 수 있는 인터페이스 계층을 만들지 않는 것**이 최선의 대응이다.

> **💡 언제 인터페이스이고 언제 가상 메서드인가**
>
> 한 줄로 줄이면 이렇다. **구현을 공유하고 싶으면 가상 메서드(추상 클래스), 능력을 선언하고 싶으면 인터페이스.**
>
> 실무에서는 둘을 함께 쓰는 경우가 많다. BCL의 `IComparer<T>`와 `Comparer<T>`가 그 예다. 인터페이스가 계약을 정의하고, 추상 기반 클래스가 그 인터페이스를 구현하면서 공통 로직을 제공한다. 구현자는 편한 쪽을 고른다. 결정표 전체는 18.12절이다.

## 18.11 핵심 인터페이스 구현하기 — `IEnumerable`, `IComparable`, `IEquatable`, `IDisposable`, `ICloneable`(과 그 회피)

BCL은 커스텀 타입이 프레임워크에 매끄럽게 통합되도록 표준 인터페이스를 제공한다. 여기서는 **구현 관용구**만 본다. 각 인터페이스의 의미론과 심화는 해당 장으로 넘긴다.

| 인터페이스 | 메서드 | 얻는 것 | 상세 |
|---|---|---|---|
| `IEnumerable<T>` | `GetEnumerator()` | `foreach`, LINQ | 24.1절, 28.1절 |
| `IComparable<T>` | `CompareTo(other)` | `Array.Sort`, `SortedSet` 등 | 25.6절 |
| `IComparer<T>` | `Compare(a, b)` | 외부에서 정의한 정렬 순서 | 25.7절 |
| `IEquatable<T>` | `Equals(other)` | 박싱 없는 동등 비교, 딕셔너리 키 | 25.2절 |
| `IDisposable` | `Dispose()` | `using`, 결정적 정리 | 33장 |
| `IFormattable` | `ToString(format, provider)` | 문화권 인식 서식화 | 38.2절 |
| `ICloneable` | `Clone()` | (권장하지 않음) | 78.7절 |

### `IEnumerable` / `IEnumerable<T>`

`foreach`는 `GetEnumerator()`라는 이름의 메서드를 가진 **아무 타입이나** 순회할 수 있다(덕 타이핑, 11.5절). 그러나 LINQ와 컬렉션 API에 참여하려면 `IEnumerable<T>`를 구현해야 한다.

가장 간단한 구현은 **내부 컬렉션에 위임하는 것**이다. `System.Array`가 이미 `IEnumerator`를 구현하므로 그대로 넘기면 된다.

```csharp
public class Garage : IEnumerable
{
    private Car[] carArray = new Car[4];
    public IEnumerator GetEnumerator() => carArray.GetEnumerator();
}
```

이제 `foreach (Car c in carLot)`이 컴파일된다. `GetEnumerator()`를 `IEnumerator IEnumerable.GetEnumerator() => ...` 형태로 **명시적으로** 구현하면 일반 사용자는 그 멤버를 찾지 못하지만 `foreach`는 배후에서 인터페이스를 얻어간다 — **18.3절에서 말한 "특수한 멤버 감추기"의 교과서적 사례**다.

제네릭 버전을 구현할 때가 진짜 관용구다. `IEnumerable<T>`가 `IEnumerable`을 상속하므로 **둘 다 구현해야 한다**(18.2절).

```csharp
using System.Collections;
using System.Collections.Generic;

public class Garage : IEnumerable<Car>
{
    private readonly Car[] _cars = new Car[4];

    // 제네릭 버전은 암시적으로 — 호출자가 직접 쓸 수 있게
    public IEnumerator<Car> GetEnumerator()
    {
        foreach (Car c in _cars)
            yield return c;
    }

    // 비제네릭 버전은 명시적으로 — 감추고 제네릭 버전으로 위임
    IEnumerator IEnumerable.GetEnumerator() => GetEnumerator();
}
```

**이 패턴을 외워라.** BCL의 거의 모든 컬렉션이 이 형태다. 제네릭 버전은 표면에 노출하고, 레거시 비제네릭 버전은 명시적 구현으로 감춘 뒤 제네릭 버전으로 위임한다.

`yield return`을 쓰면 컴파일러가 열거자 클래스 전체를 상태 기계로 생성해준다. 문법은 28.3절, 생성되는 상태 기계의 실물 IL은 28.4절에 있다.

> **⚠️ 반복자 메서드의 오류는 첫 `MoveNext()` 때 터진다**
>
> `yield`를 쓴 `GetEnumerator()` 안의 코드는 항목을 처음 순회할 때까지 실행되지 않는다. `yield` 앞에 예외를 던지는 문장이 있어도 메서드 호출 시점이 아니라 **첫 `MoveNext()` 호출 때** 던져진다. 인자 검증이나 연결 확인 같은 **가드 절**은 즉시 실행되어야 하므로, 지역 함수로 반복자 본문을 분리한다.
>
> ```csharp
> public IEnumerator<Car> GetEnumerator()
> {
>     if (_cars is null) throw new InvalidOperationException("초기화되지 않았다");  // 즉시
>     return Impl();
>
>     IEnumerator<Car> Impl()
>     {
>         foreach (Car c in _cars) yield return c;   // 첫 MoveNext 때 실행
>     }
> }
> ```
>
> 이 패턴의 논거와 변형은 28.6절과 78.12절에 있다.

### `IComparable` / `IComparable<T>`

`IComparable`은 어떤 키를 기준으로 객체를 정렬할 수 있게 하는 계약이다.

```csharp
namespace System
{
    public interface IComparable       { int CompareTo(object? obj); }
    public interface IComparable<in T> { int CompareTo(T? other); }
}
```

반환값의 의미는 이렇다.

| `this`가 `other`보다 앞 | 같음 | `this`가 `other`보다 뒤 |
|---|---|---|
| 0보다 작은 값 | 0 | 0보다 큰 값 |

`Array.Sort()`에 커스텀 타입 배열을 넘겼는데 그 타입이 `IComparable`을 구현하지 않으면 런타임 예외가 난다. 정렬 알고리즘이 두 원소를 비교할 수 없기 때문이다.

비교 로직을 손으로 쓰는 대신 **필드 타입의 `CompareTo`에 위임**하는 것이 가장 좋다. `int`가 이미 `IComparable<int>`를 구현하고 있으므로 그 구현을 재사용한다.

```csharp
public class Car : IComparable<Car>
{
    public int CarID { get; set; }
    public string PetName { get; set; } = "";

    public int CompareTo(Car? other)
        => other is null ? 1 : CarID.CompareTo(other.CarID);
}
```

> **📌 제네릭 버전을 쓰는 이유는 둘이다**
>
> **첫째, 컴파일 타임 타입 안전성.**
>
> ```csharp
> int x = 1, y = 2;
>
> IComparable c1 = x;
> c1.CompareTo(y);     // y가 박싱된다
> c1.CompareTo("2");   // 컴파일은 된다. 런타임에 ArgumentException
>
> IComparable<int> c2 = x;
> c2.CompareTo(y);     // 박싱 없음
> c2.CompareTo("2");   // 컴파일 오류
> ```
>
> **둘째, 값 타입에서 박싱이 줄어든다.** 비제네릭 `CompareTo`는 `object` 매개변수를 받으므로 값 타입 인자가 박싱된다. 제네릭 버전은 `T`를 그대로 받는다.
>
> BCL은 `IComparable`, `ICollection`, `IList`, `IDictionary` 등의 비제네릭·제네릭 버전을 모두 정의하고 있다. **커스텀 타입을 정의한다면 보통 제네릭 버전을 구현하라.** 비제네릭 버전은 제네릭 이전 코드와의 하위 호환을 위해 남아 있다.

정렬 기준이 여러 개 필요하면 `IComparable` 대신(또는 함께) **`IComparer<T>`를 구현하는 헬퍼 타입**을 만든다. `IComparer`는 정렬 대상 타입이 아니라 **보조 클래스**에 구현하는 것이 보통이고, 호출자가 헬퍼 이름을 외우지 않아도 되도록 정적 프로퍼티로 노출하는 것이 관용구다.

```csharp
public class PetNameComparer : IComparer<Car>
{
    public int Compare(Car? x, Car? y)
        => string.Compare(x?.PetName, y?.PetName, StringComparison.OrdinalIgnoreCase);
}

public class Car : IComparable<Car>
{
    // ...
    public static IComparer<Car> SortByPetName => new PetNameComparer();
}

Array.Sort(myAutos, Car.SortByPetName);      // Array.Sort(myAutos)는 CarID 순
```

정렬·비교 프로토콜의 세부 규칙(전이성, `null` 처리, `Comparer<T>.Default`의 동작)은 25.6절과 25.7절에 있다.

### `IEquatable<T>`

`IEquatable<T>`는 **박싱 없는 타입 안전 동등 비교**를 제공한다.

```csharp
public struct Point : IEquatable<Point>
{
    public int X { get; init; }
    public int Y { get; init; }

    // IEquatable<T> — 박싱 없음, 타입 안전
    public bool Equals(Point other) => X == other.X && Y == other.Y;

    // object.Equals 재정의 — 반드시 IEquatable 구현으로 위임한다
    public override bool Equals(object? obj) => obj is Point p && Equals(p);

    // GetHashCode도 반드시 함께
    public override int GetHashCode() => HashCode.Combine(X, Y);

    public static bool operator ==(Point a, Point b) =>  a.Equals(b);
    public static bool operator !=(Point a, Point b) => !a.Equals(b);
}
```

**세 가지를 항상 함께 맞춰야 한다.** `IEquatable<T>.Equals`, `object.Equals` 재정의, `GetHashCode` 재정의. 하나라도 어긋나면 `Dictionary`나 `HashSet`에서 조용히 잘못된 결과가 나온다.

`EqualityComparer<T>.Default`는 `T`가 `IEquatable<T>`를 구현하면 그 구현을 직접 쓰고, 아니면 `object.Equals`로 내려간다. 구조체에서는 이 차이가 **박싱 두 번**으로 나타난다. 그래서 구조체가 딕셔너리 키나 `HashSet` 원소로 쓰인다면 `IEquatable<T>` 구현은 선택이 아니라 필수다. 규칙 전체는 25.2절부터 25.4절에 있다.

> **📌 레코드는 이 전부를 컴파일러가 만들어준다**
>
> `record`와 `record struct`는 `IEquatable<T>` 구현, `Equals`/`GetHashCode` 재정의, `==`/`!=` 연산자를 컴파일러가 생성한다(19.3절). 값 의미론이 필요한 데이터 타입이라면 손으로 쓰지 말고 레코드를 쓰는 것이 먼저다.

### `IDisposable`

`IDisposable`은 인터페이스 중 가장 단순하다(`void Dispose()` 하나). 그러나 구현 규칙은 가장 엄격하다.

**`IDisposable`은 암시적으로 구현하라.** 명시적으로 구현하면 호출자가 `Dispose()`를 직접 부를 수 없어 불편해진다. `using` 문은 명시적 구현이어도 동작하지만, 명시적 구현으로 감춰서 얻는 것이 없다.

```csharp
public sealed class FileLogger : IDisposable
{
    private readonly StreamWriter _writer;
    private bool _disposed;

    public FileLogger(string path) => _writer = new StreamWriter(path);

    public void Log(string message)
    {
        ObjectDisposedException.ThrowIf(_disposed, this);   // ※.NET 7
        _writer.WriteLine(message);
    }

    public void Dispose()
    {
        if (_disposed) return;
        _writer.Dispose();
        _disposed = true;
    }
}

using (var logger = new FileLogger("app.log"))
    logger.Log("시작");            // 블록을 벗어날 때 Dispose가 자동 호출된다
```

상속 가능한 타입, 비관리 리소스, 파이널라이저가 얽히면 이야기가 훨씬 복잡해진다. **표준 Dispose 패턴**(`Dispose(bool disposing)`), `SafeHandle`, `IAsyncDisposable`은 33장 전체의 주제다.

### `ICloneable`과 그 회피

`ICloneable`은 자기 자신의 복사본을 반환하는 능력을 선언한다 — 멤버는 `object Clone()` 하나뿐이다.

`System.Object`가 정의한 `protected` 메서드 `MemberwiseClone()`이 얕은 복사(shallow copy)를 제공하므로(15.6절), 값 타입 필드만 가진 타입이라면 구현이 한 줄이다.

```csharp
public class Point : ICloneable
{
    public int X { get; set; }
    public int Y { get; set; }

    public object Clone() => MemberwiseClone();   // 얕은 복사
}
```

문제는 **참조 타입 필드**가 있을 때다.

```csharp
public class PointDescription
{
    public string PetName { get; set; } = "No-name";
    public Guid PointID   { get; set; } = Guid.NewGuid();
}

public class Point : ICloneable
{
    public int X { get; set; }
    public int Y { get; set; }
    public PointDescription Desc = new PointDescription();

    public object Clone() => MemberwiseClone();   // 얕은 복사 — Desc는 공유된다!
}
```

```csharp
Point p3 = new Point { X = 100, Y = 100 };
p3.Desc.PetName = "Jane";

Point p4 = (Point)p3.Clone();
p4.Desc.PetName = "My new Point";
p4.X = 9;

Console.WriteLine(p3.X);              // 100  — 값 타입은 복사되었다
Console.WriteLine(p3.Desc.PetName);   // My new Point  — 참조 타입은 공유된다!
```

**깊은 복사(deep copy)** 를 원하면 참조 타입 필드마다 새 인스턴스를 만들어야 한다.

```csharp
public object Clone()
{
    Point newPoint = (Point)MemberwiseClone();          // 먼저 얕은 복사
    newPoint.Desc = new PointDescription { PetName = Desc.PetName };   // 참조 필드를 메운다
    return newPoint;
}
```

여기까지가 `ICloneable`을 **쓰는 방법**이다. 이제 **왜 쓰지 말아야 하는가**를 본다.

> **⚠️ `ICloneable`을 새 코드에서 구현하지 마라**
>
> 이유는 셋이다.
>
> **첫째, 계약이 얕은 복사인지 깊은 복사인지 규정하지 않는다.** 인터페이스가 `object Clone()` 하나만 선언한다. 호출자는 반환된 객체가 원본과 참조를 공유하는지 알 방법이 없다. **계약이 아무것도 계약하지 않는다.** 위의 두 `Clone` 구현은 시그니처가 같지만 의미가 정반대다.
>
> **둘째, `object`를 반환한다.** 호출자는 매번 캐스팅해야 한다.
>
> ```csharp
> Point p4 = (Point)p3.Clone();     // 캐스팅 강요
> ```
>
> 값 타입이 구현하면 반환 시 **박싱**까지 붙는다.
>
> **셋째, 상속과 결합했을 때 감염된다.** 기반 클래스가 `ICloneable`을 구현하면 모든 파생 클래스가 `Clone`을 올바르게 재정의할 의무를 진다. 새 필드를 추가하고 `Clone` 갱신을 잊으면 조용히 잘못된 복사본이 나온다.
>
> **대안은 셋이다.**
>
> 1. **복사 생성자** — `public Point(Point other) { ... }`. 타입이 명확하고 캐스팅이 없다.
> 2. **레코드의 `with` 식** — `var p4 = p3 with { X = 9 };`. 컴파일러가 복사를 생성한다(19.4절).
> 3. **타입 안전한 자체 메서드** — `public Point DeepClone()`. 이름 자체가 의미를 문서화한다.
>
> `ICloneable`이 설계 선택지를 좁히는 논거 전체는 78.7절에 있다.

> **💡 `ICloneable`을 소비만 하는 것은 괜찮다**
>
> 레거시 API가 `ICloneable`을 요구한다면 구현할 수밖에 없다. 그럴 때는 **타입 안전한 공개 메서드를 만들고 `ICloneable.Clone`은 명시적으로 구현해 그쪽으로 위임**하라. 18.3절에서 본 EIMI 관용구 그대로다.
>
> ```csharp
> public class Point : ICloneable
> {
>     public Point DeepClone() { /* 타입 안전한 진짜 구현 */ return new Point(); }
>     object ICloneable.Clone() => DeepClone();   // 계약만 채운다
> }
> ```

## 18.12 인터페이스 vs 기본 클래스 — 설계 결정표

"기반 타입을 설계할까, 인터페이스를 설계할까?" 이 질문에 항상 명확한 답이 있지는 않다. 판단 기준을 정리한다.

### 판단 기준 다섯

**첫째, IS-A 관계인가 CAN-DO 관계인가.**

타입은 **구현을 하나만** 상속할 수 있다. 파생 타입이 기반 타입과 IS-A 관계를 주장할 수 없다면 기반 타입을 쓰지 말고 인터페이스를 써라. 인터페이스는 CAN-DO 관계를 함의한다. CAN-DO 기능이 여러 객체 타입에 걸쳐 있어 보이면 인터페이스를 써라. 예를 들어 어떤 타입은 자기 인스턴스를 다른 타입으로 변환할 수 있고(`IConvertible`), 어떤 타입은 자기 인스턴스를 정리할 수 있다(`IDisposable`).

**값 타입은 반드시 `System.ValueType`에서 파생되어야 하므로 임의의 기반 클래스에서 파생될 수 없다.** 이 경우 선택지가 없다 — CAN-DO 관계를 쓰고 인터페이스를 정의해야 한다.

**둘째, 사용 편의성.** 개발자 입장에서는 인터페이스의 모든 메서드를 구현하는 것보다 기반 타입에서 파생된 새 타입을 정의하는 것이 일반적으로 더 쉽다. 기반 타입이 많은 기능을 제공하므로 파생 타입은 상대적으로 작은 수정만 하면 된다. 인터페이스를 제공하면 새 타입이 **모든 멤버를 구현해야 한다.**

**셋째, 일관된 구현.** 인터페이스 계약을 아무리 잘 문서화해도 모든 사람이 그 계약을 100% 올바르게 구현할 가능성은 매우 낮다. 실제로 COM이 바로 이 문제로 고생했고, 그 때문에 일부 COM 객체는 특정 애플리케이션에서만 제대로 동작했다. 좋은 기본 구현을 갖춘 기반 타입을 제공하면 **동작하고 잘 테스트된 타입에서 시작해** 필요한 부분만 고치게 된다.

**넷째, 버전 관리.** 기반 타입에 메서드를 추가하면 파생 타입은 새 메서드를 물려받는다. 사용자 소스 코드를 **재컴파일할 필요조차 없다**. 인터페이스에 새 멤버를 추가하면 인터페이스 구현자는 소스 코드를 바꾸고 재컴파일해야 한다. (C# 8의 기본 구현이 이 문제를 완화하지만 없애지는 못한다 — 18.7절.) 바이너리 호환성을 깨는 변경 목록 전체는 78.13절이다.

**다섯째, 상태를 공유해야 하는가.** 인터페이스는 인스턴스 필드를 가질 수 없다. 구현자들이 같은 상태를 공유해야 한다면 기반 클래스밖에 답이 없다. C# 8 이후에도 이 선은 그대로다.

### 결정표

| 기준 | 추상 클래스 | 인터페이스 |
|---|---|---|
| 관계 | **IS-A** | **CAN-DO** |
| 다중 채택 | 불가 (하나만) | 가능 (몇 개든) |
| 값 타입이 채택 | **불가** | 가능 |
| 인스턴스 필드(상태) | 가능 | **불가** |
| 기본 구현 제공 | 자연스럽다 | 제한적 (C# 8, 상태 없음) |
| 구현자의 부담 | 낮다 (물려받는다) | 높다 (전부 구현) |
| 구현의 일관성 | 높다 (검증된 코드 재사용) | 낮다 (각자 구현) |
| 멤버 추가 시 호환성 | **깨지지 않는다** | 깨진다 (기본 구현으로 완화) |
| 생성자·초기화 로직 | 물려줄 수 있다 | 없다 |
| 접근성 제어 | 자유 (`protected` 등) | 사실상 공개 |
| 직렬화 | 대체로 문제없다 | 인터페이스 대상 직렬화는 대개 동작하지 않는다 |
| 테스트 대역(mock) | 봉인되지 않은 가상 멤버 필요 | 자연스럽다 |
| 계층을 가로지르는 분류 | 불가 | **가능** |
| .NET Framework 호환 | 전부 가능 | 기본 구현·정적 추상은 **불가** |

### BCL의 실제 선택

**스트림 — 구현 상속을 택했다.** `System.IO.Stream`이 추상 기반 클래스이고 `Read`, `Write` 등 여러 메서드를 제공한다. `FileStream`, `MemoryStream`, `NetworkStream`이 여기서 파생된다. IS-A 관계를 택한 이유는 **구체 클래스 구현이 쉬워지기 때문**이다. 파생 클래스는 동기 I/O만 구현하면 되고 비동기 I/O 능력은 물려받는다. 솔직히 스트림에 상속을 쓰기로 한 결정이 완전히 자명하지는 않다 — `Stream`이 제공하는 구현은 사실 매우 적다. 그러나 Windows Forms 컨트롤을 보면 명확해진다. `Button`, `CheckBox`, `ListBox`가 전부 `Control`에서 파생되고, `Control`이 구현한 방대한 코드를 그냥 물려받아 동작한다.

**컬렉션 — 인터페이스 기반을 택했다.** `System.Collections.Generic`은 `IEnumerable<out T>`, `ICollection<T>`, `IList<T>`, `IDictionary<TKey, TValue>`를 정의하고, `List<T>`, `Dictionary<TKey, TValue>`, `Queue<T>`, `Stack<T>` 등이 이들의 조합을 구현한다. CAN-DO 관계를 택한 이유는 **이 클래스들의 구현이 서로 근본적으로 다르기 때문**이다. `List<T>`와 `Dictionary<TKey, TValue>`와 `Queue<T>` 사이에 공유할 코드가 별로 없다. 그럼에도 제공하는 연산은 꽤 일관적이라, `IList<T>` 참조만 있으면 **정확히 어떤 컬렉션인지 몰라도** 삽입·제거·검색 코드를 쓸 수 있다.

**둘 다 하는 것도 가능하다.** BCL의 `IComparer<in T>`가 그 예다. 어떤 타입이든 이 인터페이스를 구현할 수 있고, 동시에 BCL은 이 인터페이스를 구현하고 비제네릭 `IComparer.Compare`에 기본 구현을 제공하는 추상 기반 클래스 `Comparer<T>`도 제공한다. 개발자가 선호하는 쪽을 고를 수 있으므로 **큰 유연성**을 준다.

### 클래스로 쓸 것인가, 인터페이스로 쓸 것인가 — 실전 예제

지침을 다시 요약하면 이렇다. **자연스럽게 구현을 공유하는 타입**에는 클래스와 서브클래스를, **독립적인 구현을 갖는 타입**에는 인터페이스를 쓴다. 다음 클래스들을 보자.

```csharp
abstract class Animal {}
abstract class Bird          : Animal {}
abstract class Insect        : Animal {}
abstract class FlyingCreature: Animal {}
abstract class Carnivore     : Animal {}

// 구체 클래스
class Ostrich : Bird {}
class Eagle   : Bird, FlyingCreature, Carnivore {}   // 불법
class Bee     : Insect, FlyingCreature {}            // 불법
class Flea    : Insect, Carnivore {}                 // 불법
```

`Eagle`, `Bee`, `Flea`는 컴파일되지 않는다. 여러 클래스를 상속하는 것이 금지되어 있기 때문이다. 해결하려면 일부 타입을 인터페이스로 바꿔야 한다. **어느 것을?**

일반 규칙을 따르면, 곤충들은 구현을 공유하고 새들도 구현을 공유하므로 이들은 클래스로 남는다. 반면 **나는 생물은 각자 독립적인 비행 메커니즘**을 갖고, **육식 동물은 각자 독립적인 사냥 전략**을 가지므로 `FlyingCreature`와 `Carnivore`를 인터페이스(`IFlyingCreature`, `ICarnivore`)로 바꾼다.

```csharp
class Eagle : Bird,   IFlyingCreature, ICarnivore {}   // 이제 컴파일된다
class Bee   : Insect, IFlyingCreature {}
class Flea  : Insect, ICarnivore {}
```

전형적인 시나리오로 옮기면 `Bird`와 `Insect`는 Windows 컨트롤과 웹 컨트롤에, `FlyingCreature`와 `Carnivore`는 `IPrintable`과 `IUndoable`에 대응한다.

> **💡 결정 절차를 순서대로 밟아라**
>
> 1. **상태를 공유해야 하는가?** → 예: 추상 클래스. (인터페이스는 인스턴스 필드를 가질 수 없다)
> 2. **값 타입도 채택해야 하는가?** → 예: 인터페이스. (구조체는 상속할 수 없다)
> 3. **여러 상속 계층을 가로질러야 하는가?** → 예: 인터페이스.
> 4. **구현자가 많고, 나중에 멤버를 추가할 가능성이 큰가?** → 예: 추상 클래스 쪽이 안전하다. 굳이 인터페이스라면 기본 구현을 전제로 설계한다.
> 5. **구현들이 서로 근본적으로 다른가?** → 예: 인터페이스.
> 6. **위 전부 애매한가?** → **둘 다 제공한다.** 인터페이스로 계약을 정의하고, 추상 기반 클래스로 편의 구현을 제공한다. BCL이 `IComparer<T>`/`Comparer<T>`에서 하는 방식이다.

> **⚠️ "인터페이스가 항상 더 낫다"는 미신**
>
> "상속보다 인터페이스"라는 조언이 널리 퍼져 있고 대체로 옳다(78.2절). 그러나 무조건은 아니다. 모든 클래스에 대해 기계적으로 `IFoo` 인터페이스를 하나씩 만드는 코드베이스를 종종 본다. 구현이 하나뿐인 인터페이스는 **간접 참조 한 겹을 추가할 뿐** 아무것도 추상화하지 않는다. 탐색을 어렵게 만들고, 역가상화를 막고(18.9절), 코드를 늘린다.
>
> 인터페이스는 **실제로 여러 구현이 존재하거나 존재할 것이 확실할 때** 가치가 있다. 테스트 대역을 위해서라면 대안이 있는지 먼저 따져보라 — 봉인하지 않은 클래스의 가상 메서드, 또는 델리게이트(26.7절)로 충분한 경우가 많다.

## 이 장의 요약

- **인터페이스는 동작만 규정하고 상태를 갖지 않는다.** 이 한 문장에서 모든 규칙이 나온다. 인스턴스 필드 금지, 생성자 금지, 멤버는 암묵적 `public`, 다중 채택 가능. C# 8이 여러 제약을 풀었지만 **인스턴스 필드 금지만은 그대로**이고, 그것이 추상 클래스와의 마지막 경계선이다.

- **인터페이스를 구현하면 C#에 `virtual`을 쓰지 않아도 IL에서 `newslot virtual final`이 된다.** CLR이 인터페이스 메서드를 가상으로 요구하기 때문이다. `final`은 C#의 "이 메서드는 가상이 아니다"라는 의미론을 지키기 위해 붙는다. 그래서 암시적 구현은 **기본적으로 봉인**되어 있다.

- **명시적 구현은 메타데이터상 `private`이고 `.override` 지시문(MethodImpl 테이블 항목)으로 인터페이스 슬롯과 짝지어진다.** 암시적 구현은 이름과 시그니처 일치만으로 연결된다. 명시적 구현은 시그니처 충돌 해소, 특수 멤버 감추기, 비제네릭 계약의 타입 안전 래핑에 쓰고, 그 외에는 피한다.

- **재구현은 인터페이스 경로만 고치고 기반 클래스 경로는 어긋난 채 남긴다.** `((IUndoable)r).Undo()`는 파생을 부르는데 `((TextBox)r).Undo()`는 기반을 부른다. 그래서 재구현은 **명시적으로 구현된 멤버**에 대해서만 안전하다. 기반 클래스를 소유하고 있다면 `virtual`을 붙이거나 `protected virtual` 훅을 제공해 재구현이 필요 없게 설계하라.

- **구조체를 인터페이스로 캐스팅하면 박싱된다.** 인터페이스 변수는 타입 객체 포인터를 가진 힙 객체를 가리켜야 하기 때문이다. 박싱된 복사본은 원본과 다른 객체이므로 변경이 반영되지 않는다. **제네릭 제약(`where T : IFoo`)** 을 쓰면 컴파일러가 `constrained.` 접두사를 방출해 박싱 없이 직접 호출한다. C# 컴파일러가 이 IL을 방출하게 하는 다른 방법은 없다.

- **기본 구현 멤버(※C# 8)는 라이브러리 버전 관리를 위한 안전장치이지 코드 재사용 도구가 아니다.** 상태를 가질 수 없고, 항상 명시적이므로 인터페이스로 캐스팅해야 부를 수 있으며, .NET Framework에서는 아예 쓸 수 없다. 클래스가 직접 구현하면 언제나 클래스 구현이 이긴다.

- **정적 추상 멤버(※C# 11)는 정적 다형성을 열었고, 제네릭 수학의 기반이다.** 인스턴스 멤버와 반대로 인터페이스의 정적 멤버는 기본이 비가상이다. 정적 추상 멤버는 인터페이스 타입으로는 부를 수 없고 **제약된 타입 매개변수(`T.Member`)** 로만 호출한다.

- **인터페이스 호출은 인터페이스 맵과 가상 스텁 디스패치를 거치므로 클래스 가상 호출보다 구조적으로 비싸다.** 그러나 진짜 비용은 호출 오버헤드가 아니라 **인라이닝을 막는 것**이다. 최적화 방향은 "인터페이스를 없앤다"가 아니라 "핫 경로에서 타입을 구체화해 JIT이 역가상화하게 한다"이다.

- **`IEnumerable<T>` 구현의 표준 관용구는 제네릭 버전은 암시적으로, 비제네릭 버전은 명시적으로 구현하고 제네릭 버전에 위임하는 것이다.** `IEquatable<T>`는 `object.Equals`·`GetHashCode`와 반드시 함께 맞춘다. `IDisposable`은 항상 암시적으로 구현한다.

- **`ICloneable`은 새 코드에서 구현하지 마라.** 얕은 복사인지 깊은 복사인지 계약이 규정하지 않고, `object`를 반환해 캐스팅과 박싱을 강요하며, 상속과 결합하면 감염된다. 복사 생성자, 레코드의 `with` 식, 타입 안전한 자체 메서드가 대안이다.

- **"구현을 공유하고 싶으면 추상 클래스, 능력을 선언하고 싶으면 인터페이스."** 애매하면 둘 다 제공한다 — 인터페이스로 계약을, 추상 클래스로 편의 구현을. BCL이 `IComparer<T>`/`Comparer<T>`에서 그렇게 한다.

## 연습 문제

1. **`newslot virtual final`을 직접 확인하라.** `public class C : IDisposable { public void Dispose() { } }`를 컴파일하고 `ildasm` 또는 ILSpy의 IL 뷰로 `Dispose` 메서드의 한정자를 확인하라. 그다음 `public virtual void Dispose()`로 바꿔 다시 확인하고, `void IDisposable.Dispose()`로 바꿔 세 번째로 확인하라. **세 경우의 한정자와 `.override` 지시문의 유무**를 표로 정리하라. 18.3절의 표와 일치하는가?

2. **재구현이 깨지는 순간을 재현하라.** 18.4절의 `TextBox`/`RichTextBox` 예제를 두 버전(명시적 구현 버전, 암시적 구현 버전)으로 만들고, Case 1·2·3을 모두 출력하라. 그다음 `TextBox.Undo`에 `virtual`을 붙이고 `RichTextBox`가 `override`하도록 고쳐 세 경로가 일치하는 것을 확인하라. **어느 버전이 어느 Case에서 어긋나는가**를 표로 만들어라.

3. **박싱의 위치를 IL로 짚어라.** `interface I { void Foo(); } struct S : I { public void Foo() { } }`를 정의하고, (a) `s.Foo()`, (b) `((I)s).Foo()`, (c) `M(s)` where `void M(I i)`, (d) `M<S>(s)` where `void M<T>(T t) where T : I` — 네 호출의 IL을 비교하라. `box` 옵코드가 나타나는 곳과 `constrained.` 접두사가 나타나는 곳을 표시하라.

4. **가변 구조체 + 인터페이스의 함정을 겪어보라.** 18.6절의 `Counter` 구조체를 만들고, 인터페이스 변수로 `Increment()`를 100번 호출한 뒤 원본 구조체의 `Value`를 출력하라. 결과가 왜 그런지 IL로 설명하라. 그다음 `Counter`를 `class`로 바꿔 다시 실행하고 차이를 기록하라.

5. **기본 구현 멤버의 접근 경로를 확인하라.** `interface ILogger { void Log(string s); string Format(string s) => $"[{DateTime.Now:HH:mm}] {s}"; }`를 정의하고 `Log`만 구현하는 클래스를 만들어라. 클래스 인스턴스에서 `Format`을 부르려고 시도해 컴파일 오류를 확인한 뒤, 인터페이스로 캐스팅해 호출하라. 그다음 클래스에 `Format`을 직접 구현하고 **세 경로**(클래스 참조, `ILogger` 캐스팅, 파생 인터페이스 캐스팅)에서 어느 구현이 불리는지 확인하라.

6. **정적 추상 멤버로 파서를 만들어라.** `interface IParseable<TSelf> { static abstract TSelf Parse(string s); }`를 정의하고 두 개의 구현 타입(예: `Celsius`, `Fahrenheit`)을 만들어라. 그다음 `static T[] ParseAll<T>(string[] input) where T : IParseable<T>`를 작성해 두 타입 모두에 동작하는지 확인하라. `IParseable<Celsius>.Parse("10")`처럼 인터페이스 타입으로 직접 부르면 어떤 오류가 나는가?

7. **인터페이스 디스패치와 제네릭 제약의 차이를 측정하라.** `IEnumerable<int>`를 매개변수로 받는 합계 함수와, 18.9절의 제네릭 제약 버전 두 개를 만들고 `List<int>` 백만 개 원소에 대해 각각 벤치마크하라. 그다음 `[MethodImpl(MethodImplOptions.NoInlining)]`을 붙였다 뗐다 하면서 차이가 어디서 오는지 확인하라. **수치는 자기 환경에서 직접 재라** — 이 책의 어떤 숫자도 그대로 믿지 마라(67장).
