# 21장. 널 안정성

> **이 장의 위치** — 6.7절에서 값 타입과 참조 타입을 갈랐을 때 "참조 타입만 `null`을 담을 수 있다"고 했고, 6.9절에서 확정 할당을 설명할 때 "참조 타입의 기본값은 `null`"이라고 했다. 그 두 문장은 C#의 가장 큰 구멍 두 개를 동시에 열어 놓는다. **값 타입은 "값 없음"을 표현할 방법이 없고, 참조 타입은 "값 없음"을 거부할 방법이 없다.** 이 장은 그 두 구멍을 각각 메우는 두 기능을 다룬다. 하나는 CLR이 특별 지원까지 붙여 준 진짜 타입(`Nullable<T>`)이고, 다른 하나는 컴파일러가 혼자 지키는 약속(널 가능 참조 타입)이다. 이 둘은 문법이 같아서 같은 기능처럼 보이지만, **실체가 완전히 다르다.** 그 차이를 모르면 반드시 사고가 난다.
>
> **선수 지식** — 6장(구문과 타입 기초 — 특히 6.7절, 6.9절), 10장(변수·매개변수·식 — 특히 10.10절 null 연산자), 15장(`object` 타입과 박싱), 16장(구조체와 값 타입), 20장(열거형과 특성)
>
> **이 장에서 다루지 않는 것** — `??`, `??=`, `?.`, `?[]` 네 연산자의 문법·단축 평가·우선순위는 10.10절에서 이미 끝냈다. 이 장은 그 연산자들을 **쓰기만** 하고 다시 설명하지 않는다. `#nullable` 지시문이 전처리기 지시문 목록 안에서 차지하는 위치는 12.7절에 있다. 널 가능 주석을 공개 API에 추가하는 것이 바이너리 호환성·소스 호환성에 무엇을 하는지는 78.13절이다. `is null` / `is not null` 패턴의 문법과 컴파일 형태는 77.12절, `notnull` 제네릭 제약은 23.6절, `TryXXX` 패턴 설계는 32.9절이다. 이 장은 **타입 시스템 관점**에서만 널을 본다.

## 21.1 널 가능 값 타입 `Nullable<T>` — 구조체의 실체

### 문제 — 값 타입에는 "값 없음"이 없다

참조 타입 변수는 `null` 참조로 "가리키는 대상이 없다"를 표현한다. 값 타입 변수는 그럴 수 없다. 변수 자체가 값이기 때문이다.

```csharp
string s = null;    // OK — 참조 타입
int i = null;       // 컴파일 오류 CS0037 — 값 타입은 null이 될 수 없다
```

오류 메시지는 이렇다.

```text
error CS0037: Cannot convert null to 'int' because it is a non-nullable value type
```

이것은 언어의 결함이 아니라 정의 그 자체다. 6.7절에서 본 대로 `int` 변수는 4바이트 정수를 **담고 있다.** 어떤 비트 조합을 "값 없음"으로 예약해 둘 자리가 없다. 32비트 조합 40억 가지가 전부 유효한 `int` 값이다.

문제는 현실이 이 정의를 존중해 주지 않는다는 것이다. 세 가지 상황이 대표적이다.

| 상황 | 왜 `null`이 필요한가 | 값 타입이라서 생기는 문제 |
|---|---|---|
| 데이터베이스 컬럼 | SQL의 `INT NULL` 컬럼은 값이 없을 수 있다 | `Int32`에는 그것을 표현할 방법이 없다 |
| 다른 플랫폼과의 상호운용 | Java의 `java.util.Date`는 참조 타입이라 `null`이 될 수 있다 | CLR의 `System.DateTime`은 값 타입이라 `null`을 받을 수 없다 |
| "아직 모름" 상태 | 계좌 잔액을 아직 조회하지 못했다 | `0`은 "잔액이 0원"이라는 유효한 값이다 |

세 번째가 가장 위험하다. `decimal Balance = 0`은 "잔액 0원"과 "잔액 미확인"을 구별하지 못한다. 코드는 조용히 잘못된 답을 낸다.

> **📌 이 문제는 .NET 초창기부터 알려져 있었다**
>
> .NET Framework 1.0 시절 ADO.NET은 이 간극을 메우기 위해 `System.Data.SqlTypes` 네임스페이스에 `SqlInt32`, `SqlDecimal`, `SqlString` 같은 별도 타입을 만들었다. 각각이 자체적인 `IsNull` 속성을 갖는다. 이 타입들은 널 가능 값 타입이 나온 뒤에도 사라지지 않았는데, 일대일 대응이 아니기 때문이다. 예를 들어 `SqlDecimal`은 최대 38자리를 담지만 일반 `Decimal`은 29자리까지고, `SqlString`은 `String`에 없는 자체 로캘·비교 옵션을 갖는다. 즉 `SqlDecimal`은 `decimal?`로 대체할 수 없다. 오래된 데이터 액세스 코드에서 이 타입들을 만나면 "구시대 유물"이 아니라 "다른 타입"으로 취급해야 한다.

### 해법 — `System.Nullable<T>` 구조체

C# 2.0과 함께 CLR에 도입된 해법은 놀랄 만큼 단순하다. **값 하나와 "값이 있는가" 플래그 하나를 묶은 구조체를 만든다.** `System.Nullable<T>`가 그것이다. 논리적인 정의는 다음과 같다.

```csharp
[Serializable, StructLayout(LayoutKind.Sequential)]
public struct Nullable<T> where T : struct
{
    // 상태를 나타내는 두 필드가 전부다
    private Boolean hasValue = false;   // null이라고 가정
    internal T value = default(T);      // 모든 비트가 0이라고 가정

    public Nullable(T value)
    {
        this.value = value;
        this.hasValue = true;
    }

    public Boolean HasValue { get { return hasValue; } }

    public T Value
    {
        get
        {
            if (!hasValue)
                throw new InvalidOperationException(
                    "Nullable object must have a value.");
            return value;
        }
    }

    public T GetValueOrDefault() { return value; }

    public T GetValueOrDefault(T defaultValue)
    {
        if (!HasValue) return defaultValue;
        return value;
    }

    public override Boolean Equals(Object other)
    {
        if (!HasValue) return (other == null);
        if (other == null) return false;
        return value.Equals(other);
    }

    public override int GetHashCode() { return HasValue ? value.GetHashCode() : 0; }

    public override string ToString() { return HasValue ? value.ToString() : ""; }

    public static implicit operator Nullable<T>(T value) { return new Nullable<T>(value); }

    public static explicit operator T(Nullable<T> value) { return value.Value; }
}
```

이것이 전부다. 마법은 없다. **필드 두 개짜리 구조체 하나**가 "값 없음"이라는 개념을 값 타입 세계로 들여온다.

여기서 세 가지를 눈여겨보라.

첫째, **`Nullable<T>` 자체가 구조체다.** 그래서 `int?` 변수도 여전히 스택에 놓일 수 있고 힙 할당이 없다. 인스턴스 크기는 원래 값 타입 크기에 `Boolean` 필드 하나를 더한 정도다.

둘째, **타입 매개변수 `T`가 `struct` 제약을 받는다.** 참조 타입 변수는 이미 `null`이 될 수 있으니 감쌀 이유가 없기 때문이다. 이 제약은 "널 가능이 아닌 값 타입"을 뜻하므로 `Nullable<Nullable<int>>`도 금지된다.

셋째, **`Value`는 `HasValue`가 `false`면 예외를 던진다.** 던지는 예외는 `NullReferenceException`이 아니라 `InvalidOperationException`이다. 이 구별은 실무에서 꽤 중요하다.

> **⚠️ `null`인 `int?`를 역참조하면 `NullReferenceException`이 아니다**
>
> ```csharp
> int? x = null;
> int y = x.Value;      // InvalidOperationException
> int z = (int) x;      // InvalidOperationException — 명시적 변환은 Value 호출과 같다
> ```
>
> 메시지는 `"Nullable object must have a value."`다. `NullReferenceException`을 잡는 `catch` 블록은 이것을 잡지 못한다. 반대로 참조 타입을 `null` 상태에서 역참조하면 `NullReferenceException`이 난다. **널 가능 값 타입과 널 가능 참조 타입은 실패할 때 던지는 예외부터 다르다.** 로그를 보고 원인을 좁힐 때 이 차이가 단서가 된다.

### 문법 설탕 — `T?`는 `Nullable<T>`다

`Nullable<Int32>`를 매번 쓰는 것은 번거롭다. C#은 물음표 표기를 제공한다.

```csharp
Nullable<int> a = 5;   // 정식 표기
int? b = 5;            // 문법 설탕 — 완전히 같다
```

**`int?`와 `Nullable<int>`는 같은 타입의 다른 표기다.** 별칭도 아니고 파생도 아니다. C# 컴파일러가 `int?`를 보면 그 자리에 `System.Nullable<System.Int32>`를 넣는다. IL을 보면 물음표는 흔적도 없다.

```il
.method private hidebysig static void  Demo() cil managed
{
  .locals init (valuetype [System.Runtime]System.Nullable`1<int32> V_0,
                valuetype [System.Runtime]System.Nullable`1<int32> V_1)
  // ...
}
```

`` System.Nullable`1<int32> `` — 제네릭 인자 하나짜리 `Nullable` 구조체다. `int?`는 소스 텍스트에만 존재한다.

이 동일성을 코드로도 확인할 수 있다.

```csharp
Console.WriteLine(typeof(int?) == typeof(Nullable<int>));   // True
Console.WriteLine(typeof(int?).FullName);   // System.Nullable`1[[System.Int32, ...]]
```

### 기본값과 초기화

`Nullable<T>`의 기본값은 `null`이다. 이것은 특별 규칙이 아니라 구조체 규칙의 자연스러운 귀결이다. 16.4절에서 본 대로 구조체의 기본값은 모든 필드가 0인 상태이고, `hasValue` 필드가 `false`(0)이면 그것이 곧 `null`이다.

```csharp
int? a = default;             // null
int? b = new int?();          // null — 매개변수 없는 생성자
int? c = new Nullable<int>(); // null — 같은 것
int? d = null;                // null — 위와 완전히 같은 코드로 컴파일된다
int? e = 5;                   // new Nullable<int>(5)
```

`int? d = null;`이라고 쓰면 컴파일러는 `d = new Nullable<int>()`를 생성한다. **`null` 리터럴을 널 가능 값 타입에 대입하는 것은 "널 참조를 대입"하는 것이 아니라 "`hasValue`가 `false`인 구조체를 만드는 것"이다.** 이 사실 하나가 이 절의 나머지 전부를 설명한다.

> **📌 `int?`가 `null`과 비교되는 것이 왜 가능한가**
>
> `x == null`이 컴파일되는 이유는 `Nullable<T>`에 `==` 연산자가 있어서가 아니다. `Nullable<T>`는 `==`를 정의하지 않는다. 컴파일러가 리프팅(lifting) 규칙에 따라 `int`의 `==`를 끌어올려 쓰고(21.4절), `null` 리터럴을 `int?`의 널 상태로 해석한 뒤, 결과적으로 `!x.HasValue` 검사로 바꾼다.
>
> ```csharp
> int? i = null;
> Console.WriteLine(i == null);      // True
> ```
>
> 위 코드는 사실상 다음으로 번역된다.
>
> ```csharp
> Nullable<int> i = new Nullable<int>();
> Console.WriteLine(!i.HasValue);    // True
> ```
>
> **`i == null`이라는 소스에는 참조 비교가 전혀 없다.** 힙도, 참조도, 널 참조도 등장하지 않는다. 컴파일 결과는 `bool` 필드 하나를 읽는 코드다.

### 멤버 전수

| 멤버 | 시그니처 | 동작 | `null`일 때 |
|---|---|---|---|
| `HasValue` | `bool { get; }` | 값이 있는지 | `false` |
| `Value` | `T { get; }` | 값을 꺼낸다 | `InvalidOperationException` |
| `GetValueOrDefault()` | `T` | 값 또는 `default(T)` | `default(T)` |
| `GetValueOrDefault(T)` | `T` | 값 또는 지정한 기본값 | 인자로 준 값 |
| `Equals(object)` | `bool` | 값 동등성 | 상대도 `null`이면 `true` |
| `GetHashCode()` | `int` | 값의 해시 | `0` |
| `ToString()` | `string` | 값의 문자열 | `""` (빈 문자열) |
| 암시적 변환 | `T → T?` | 값을 감싼다 | 해당 없음 |
| 명시적 변환 | `T? → T` | `Value`와 동일 | `InvalidOperationException` |

`ToString()`이 `null`이 아니라 **빈 문자열**을 반환한다는 점을 기억해 두라. 문자열 보간이나 `Console.WriteLine`에 널 가능 값을 넣으면 빈 줄이 나오지 `"null"`이 나오지 않는다.

```csharp
int? y = null;
Console.WriteLine($"[{y}]");        // [] — 빈 문자열
Console.WriteLine(y);               // 빈 줄
```

### `System.Nullable` 정적 클래스 — 이름이 같은 다른 타입

제네릭이 아닌 `System.Nullable` 정적 클래스도 있다. `Nullable<T>` 구조체와 이름만 같고 별개다. 리플렉션에서 자주 쓴다.

```csharp
Type? underlying = Nullable.GetUnderlyingType(typeof(int?));  // System.Int32
bool isNullable = underlying is not null;                     // true
Console.WriteLine(Nullable.GetUnderlyingType(typeof(int)) is null);   // True
```

세 멤버가 있다. `Nullable.GetUnderlyingType(Type)`은 인자가 `Nullable<T>`면 `T`를, 아니면 `null`을 반환한다. 널 가능 여부 판정의 표준 방법이다. `Nullable.Compare<T>(T?, T?)`는 두 널 가능 값의 순서를 비교하며 `null`이 가장 작다. `Nullable.Equals<T>(T?, T?)`는 동등 비교를 한다.

`GetUnderlyingType`은 직렬화기·ORM·모델 바인더가 "이 프로퍼티가 널을 받을 수 있는가"를 판정할 때 쓰는 관용구다. **값 타입에 대해서는** 이것으로 충분하다. 참조 타입은 이 방법으로 판정할 수 없다(21.6절).

### 런타임 동작과 메모리 레이아웃

```text
  int i = 5;                        int? n = 5;                 int? m = null;
┌────────────────┐           ┌─────────┬────────────┐    ┌─────────┬────────────┐
│  value: 5      │           │hasValue │  value: 5  │    │hasValue │  value: 0  │
│  (4바이트)     │           │  true   │  (4바이트) │    │  false  │  (4바이트) │
└────────────────┘           └─────────┴────────────┘    └─────────┴────────────┘
                              1바이트 + 정렬 패딩          m은 "널 참조"가 아니다.
                                                          플래그가 꺼진 구조체다.
```

`int?`는 x64에서 통상 8바이트를 차지한다(`bool` 1바이트 + 정렬 패딩 3바이트 + `int` 4바이트). 정확한 크기는 `T`의 정렬 요구에 따라 달라지므로 이 값은 예시로만 받아들여야 한다. `long?`은 16바이트, `byte?`는 2바이트가 된다.

핵심은 **크기가 커진다는 사실 자체**다. `int[]`와 `int?[]`는 요소당 4바이트와 8바이트로, 배열 100만 개면 4MB와 8MB의 차이다. 캐시 지역성에도 그만큼 영향이 있다.

> **⚠️ 널 가능 값 타입을 대량 데이터에 쓰면 메모리가 두 배가 될 수 있다**
>
> `struct Point { double X, Y; }`는 16바이트지만 `Point?`는 24바이트가 된다(`bool` + 7바이트 패딩 + 16바이트). 50% 증가다. 수백만 개를 다루는 계산 코드라면 `Point?[]`보다 `Point[]` 하나와 `bool[]` 또는 비트마스크 하나를 따로 두는 편이 메모리·캐시 양쪽에서 유리하다. 물론 그 대가로 두 배열의 동기화를 직접 책임져야 한다. 21.11절에서 이 트레이드오프를 다시 본다.

### 성능 — 필드 하나만큼의 비용, 그리고 최적화 방해

널 가능 값 타입의 비용은 세 갈래다.

| 비용 | 크기 | 언제 문제가 되는가 |
|---|---|---|
| 메모리 | `T` + `bool` + 정렬 패딩 | 대량 배열, 큰 구조체 필드 |
| 분기 | 모든 연산마다 `HasValue` 검사 | 타이트 루프 |
| 최적화 방해 | JIT의 벡터화·인라인이 어려워짐 | 수치 계산 커널 |

세 번째가 가장 과소평가된다. `int` 배열을 도는 루프는 JIT이 SIMD로 벡터화할 여지가 있지만, `int?` 배열은 요소마다 조건 분기가 끼어들어 그 여지가 사라진다. **계산 커널 안쪽에서는 널 가능 값 타입을 쓰지 않고, 널 여부는 커널 진입 전에 걸러내는 것이 기본이다.**

## 21.2 암시적·명시적 널 가능 변환

### 변환 방향에 따라 다른 규칙

`T`와 `T?` 사이의 변환은 방향에 따라 규칙이 다르다.

```csharp
int? x = 5;             // 암시적 — int → int?
int y = (int) x;        // 명시적 — int? → int
```

이유는 정보 손실의 방향이다. `int`의 모든 값은 `int?`로 손실 없이 올라가지만, `int?`의 값 중 `null`은 `int`로 내려갈 수 없다. **암시적 변환은 절대 실패하지 않아야 한다**는 원칙(6.10절)이 여기서도 지켜진다.

명시적 변환은 `Value` 프로퍼티 호출과 정확히 같다. 따라서 `HasValue`가 `false`면 `InvalidOperationException`을 던진다.

```csharp
int? n = null;
int m = (int) n;        // InvalidOperationException — (int)n 은 n.Value 와 같다
```

### 변환 표

| 원본 | 대상 | 종류 | 비고 |
|---|---|---|---|
| `T` | `T?` | 암시적 | `new Nullable<T>(value)` |
| `null` 리터럴 | `T?` | 암시적 | `new Nullable<T>()` |
| `T?` | `T` | 명시적 | `Value` — 널이면 예외 |
| `T` | `U?` (`T→U` 암시적일 때) | 암시적 | `int → double?` |
| `T?` | `U?` (`T→U` 암시적일 때) | 암시적 | `int? → double?` — 널이면 널 |
| `T?` | `U?` (`T→U` 명시적일 때) | 명시적 | `long? → int?` — 널이면 널 |
| `T?` | `object` | 암시적(박싱) | 21.3절 — 널이면 `null` 참조 |
| `object` | `T?` | 명시적(언박싱) | 21.3절 — `null`이면 널 |

네 번째와 다섯 번째 줄이 **끌어올려진 변환(lifted conversion)** 이다. 밑바탕 타입 사이에 변환이 있으면 널 가능 형태 사이에도 같은 종류의 변환이 자동으로 생긴다.

```csharp
int? b = null;

double? d = 5;      // int → double? : 암시적 확대 변환이 끌어올려졌다. d는 5.0
double? e = b;      // int? → double? : e는 null
int? f = (int?) 3.7;  // double → int? : 명시적. f는 3 (소수부 절삭)
```

끌어올려진 변환의 규칙은 한 줄이다. **원본이 `null`이면 결과도 `null`, 아니면 밑바탕 변환을 수행한 뒤 감싼다.**

```csharp
// double? e = b; 의 의미
double? e = b.HasValue ? new double?((double) b.GetValueOrDefault()) : new double?();
```

> **⚠️ 끌어올려진 축소 변환도 `checked`의 영향을 받는다**
>
> ```csharp
> long? big = long.MaxValue;
> checked
> {
>     int? small = (int?) big;   // OverflowException
> }
> ```
>
> `null`이면 변환 자체를 하지 않으므로 예외도 없다. 하지만 값이 있으면 밑바탕 축소 변환이 그대로 수행되고, `checked` 문맥이면 오버플로 검사도 그대로 적용된다(7.9절). "널 가능이니까 안전하겠지"라는 직관은 틀렸다. **널 검사와 범위 검사는 별개다.**

### 사용자 정의 변환도 끌어올려진다

`T`와 `U`가 모두 널 가능이 아닌 값 타입이고 `T → U` 사용자 정의 변환이 있으면, `T? → U?` 변환도 자동으로 생긴다(22.4절).

```csharp
public struct Fahrenheit
{
    public double Degrees;
    public Fahrenheit(double d) => Degrees = d;
}

public struct Celsius
{
    public double Degrees;
    public Celsius(double d) => Degrees = d;
    public static implicit operator Fahrenheit(Celsius c)
        => new Fahrenheit(c.Degrees * 9 / 5 + 32);
}

Celsius? c = new Celsius(100);
Fahrenheit? f = c;              // 끌어올려진 사용자 정의 변환. 212
Celsius? c2 = null;
Fahrenheit? f2 = c2;            // null — 변환 연산자는 아예 호출되지 않는다
```

**끌어올려진 사용자 정의 변환은 원본이 `null`이면 변환 연산자를 호출하지 않는다.** 변환 연산자 안에 로깅이나 카운터가 있으면 널 입력에서 실행되지 않는다는 뜻이다.

### 널 가능 값을 안전하게 꺼내는 네 가지 방법

```csharp
int? maybe = GetSomething();

if (maybe.HasValue) Use(maybe.Value);   // 1. HasValue 먼저 검사 — 가장 명시적
int a = maybe.GetValueOrDefault();      // 2. 절대 던지지 않는다. null이면 0
int b = maybe.GetValueOrDefault(-1);    //    null이면 -1
int c = maybe ?? -1;                    // 3. ?? 연산자 (10.10절)
if (maybe is int value) Use(value);     // 4. 패턴 매칭 (77.12절)
```

네 방법이 컴파일 결과까지 완전히 같지는 않다.

| 방법 | 컴파일 결과 | 특징 |
|---|---|---|
| `HasValue` + `Value` | `get_HasValue` 후 `get_Value` | `Value`가 널 검사를 한 번 더 한다 |
| `GetValueOrDefault()` | 필드 직접 읽기 | 검사 없음 — 가장 싸다 |
| `?? d` | `HasValue` 검사 후 분기 | `d`가 널이 아닐 때 평가되지 않는다 |
| `is int v` | `HasValue` 검사 + `GetValueOrDefault` | 변수 선언까지 한 번에 |

> **💡 `HasValue`를 확인한 뒤에는 `Value`보다 `GetValueOrDefault()`가 낫다**
>
> `Value` getter는 매번 `hasValue`를 다시 검사하고 필요하면 예외를 던진다. `HasValue`를 이미 확인한 자리에서는 그 검사가 중복이다. `GetValueOrDefault()`는 검사 없이 필드를 그대로 반환한다. JIT이 대개 중복 검사를 제거해 주지만, 타이트 루프에서는 명시적으로 `GetValueOrDefault()`를 쓰는 편이 확실하다. 실제로 컴파일러가 리프팅된 연산자를 만들 때도 `Value`가 아니라 `GetValueOrDefault()`를 쓴다(21.4절). 컴파일러가 스스로 그렇게 하는 데는 이유가 있다.

> **⚠️ `??`의 오른쪽 식은 널일 때만 평가된다 — `GetValueOrDefault(x)`와 다르다**
>
> ```csharp
> int? cached = 42;
> int v1 = cached ?? ExpensiveDefault();          // ExpensiveDefault()는 호출되지 않는다
> int v2 = cached.GetValueOrDefault(ExpensiveDefault());  // 호출된다!
> ```
>
> `GetValueOrDefault(T)`는 평범한 메서드이므로 **인자가 먼저 평가된다.** 기본값 계산이 비싸거나 부수 효과가 있으면 반드시 `??`를 써라. 이 함정은 코드 리뷰에서 거의 걸러지지 않는다.

## 21.3 널 가능 값의 박싱과 언박싱 — CLR의 특별 지원

### 왜 특별 지원이 필요한가

여기서부터가 이 장의 첫 번째 핵심이다. `Nullable<T>`는 지금까지 본 대로 평범한 구조체다. 평범한 구조체라면 박싱될 때도 평범하게 박싱되어야 한다. 15.2절의 규칙 그대로, 힙에 객체 헤더와 함께 구조체 내용이 복사되고 그 참조가 반환되어야 한다.

그런데 그렇게 하면 이상한 일이 벌어진다.

```csharp
int? n = null;
object o = n;          // 평범한 박싱이라면?
```

평범하게 박싱하면 `o`는 **`hasValue == false`인 `Nullable<int>` 박스를 가리키는 널이 아닌 참조**가 된다. `n`은 논리적으로 `null`인데, `object`로 올리는 순간 `null`이 아니게 되는 것이다.

```csharp
Console.WriteLine(o == null);   // 평범한 박싱이면 False가 나와야 한다
```

이건 받아들일 수 없다. 널 가능 값 타입이 "일급 시민"이 되려면 `null`인 값을 `object`에 넣었을 때 `null`이 나와야 한다. 그래서 **CLR이 직접 개입한다.**

### CLR의 규칙 — `Nullable<T>`는 박싱되지 않는다

CLR은 `Nullable<T>` 인스턴스를 박싱할 때 다음을 한다.

```text
       box  Nullable<T>
             │
             ▼
      hasValue == false ?
        ┌────┴────┐
       예          아니오
        │            │
        ▼            ▼
   아무것도      value 필드를 꺼내서
   박싱하지      T를 박싱한다
   않고 null     (박스의 타입은 T)
   을 반환
```

정리하면 이렇다.

- `HasValue`가 `false`면 **아무것도 박싱하지 않고 `null` 참조를 반환**한다.
- `HasValue`가 `true`면 `value` 필드를 꺼내 **밑바탕 타입 `T`를 박싱**한다.

**힙에 "박싱된 `Nullable<int>`"라는 것은 존재하지 않는다.** 존재하는 것은 박싱된 `Int32`이거나 아무것도 아니거나 둘 중 하나다. 이것을 코드로 확인해 보자.

```csharp
// 널 가능 값 타입을 박싱하면 null이거나 박싱된 T다
int? n = null;
object o = n;                                   // o는 null
Console.WriteLine("o is null={0}", o == null);  // "True"

n = 5;
o = n;                                          // o는 박싱된 Int32를 참조한다
Console.WriteLine("o's type={0}", o.GetType()); // "System.Int32"
```

두 번째 출력이 `System.Nullable\`1[System.Int32]`가 아니라 `System.Int32`다.

IL에는 이 특별함이 드러나지 않는다. 컴파일러는 평범하게 `box`를 낸다.

```il
  IL_0009:  ldloc.0
  IL_000a:  box        valuetype [System.Runtime]System.Nullable`1<int32>
  IL_000f:  stloc.1
```

**특별 취급은 컴파일러가 아니라 런타임이 한다.** `box` 옵코드의 피연산자 타입이 `Nullable<T>`일 때 JIT/런타임이 위 분기를 심는다. 그래서 이것은 "C#의 기능"이 아니라 "CLR의 기능"이고, IL을 직접 쓰는 다른 언어에서도 똑같이 동작한다.

> **📌 왜 컴파일러가 아니라 런타임인가**
>
> 컴파일러가 처리하려면 박싱이 일어나는 모든 자리를 컴파일 타임에 알아야 한다. 그런데 제네릭 코드 안에서는 `T`가 `Nullable<U>`인지 아닌지 컴파일 타임에 알 수 없다. `void Print<T>(T value) { object o = value; }`에서 `T`가 `int?`로 인스턴스화될 수도 있다. CLR이 `box` 옵코드 실행 시점에 판정해야만 모든 경우가 일관되게 처리된다. 15장에서 본 "박싱은 CLR의 동작이지 C#의 동작이 아니다"라는 명제가 여기서 다시 확인된다.

### 언박싱 — 양방향 특별 지원

반대 방향도 특별하다. CLR은 박싱된 `T`를 **`T`로도, `Nullable<T>`로도** 언박싱할 수 있게 허용한다. 그리고 `null` 참조를 `Nullable<T>`로 언박싱하면 `null`인 널 가능 값이 된다.

```csharp
object o = 5;           // 박싱된 Int32
int? a = (int?) o;      // a = 5   — Nullable<Int32>로 언박싱
int  b = (int)  o;      // b = 5   — Int32로 언박싱

o = null;               // null로 초기화된 참조
a = (int?) o;           // a = null            — 널이 그대로 전달된다
b = (int)  o;           // NullReferenceException
```

마지막 두 줄의 대비가 이 절의 요약이다. 같은 `null` 참조인데 대상 타입이 `int?`면 성공하고 `int`면 실패한다.

> **⚠️ `null` 언박싱의 예외 타입은 `NullReferenceException`이다**
>
> `(int) o`에서 `o`가 `null`일 때 나오는 예외는 `InvalidCastException`이 아니라 `NullReferenceException`이다. 언박싱은 "박스 안의 값 필드 주소를 구해서 읽는" 연산이라, 박스가 없으면 널 참조 역참조가 된다. 반면 `o`가 박싱된 `long`인데 `(int) o`를 하면 `InvalidCastException`이다. **같은 캐스트 문법에서 널이면 `NullReferenceException`, 타입이 틀리면 `InvalidCastException`이 나온다.** 예외 타입으로 원인을 좁힐 때 이 구별이 필요하다.

`as` 연산자도 널 가능 값 타입을 대상으로 쓸 수 있다. 실패하면 `null`이 된다.

```csharp
object o = "string";
int? x = o as int?;
Console.WriteLine(x.HasValue);   // False
```

`as`의 대상 타입은 참조 타입이거나 널 가능 값 타입이어야 한다는 규칙(15.3절에서 본 것)이 여기서 성립한다. 실패했을 때 돌려줄 `null`이 필요하기 때문이다. 다만 `o as int?`는 성공해도 `Nullable<int>` 구조체를 만드는 비용이 붙으므로, 값 타입 판정에는 `o is int v` 패턴이 거의 항상 낫다.

### `GetType()`이 `T`를 반환한다

`Nullable<T>`에 대해 `GetType()`을 부르면 CLR은 **거짓말을 한다.** `Nullable<T>`가 아니라 `T`를 반환한다.

```csharp
int? x = 5;
// 아래 줄은 "System.Int32"를 출력한다. "System.Nullable`1[System.Int32]"가 아니다.
Console.WriteLine(x.GetType());
```

엄밀히 말하면 거짓말은 아니고, 21.3절 앞부분의 박싱 규칙에서 자동으로 따라 나오는 결과다. `GetType()`은 `System.Object`의 **비가상 메서드**이고 `Nullable<T>`는 그것을 재정의할 수 없다. 그래서 `x.GetType()`을 호출하려면 `x`를 먼저 박싱해야 한다. 박싱하면 박스의 타입은 `System.Int32`다. 따라서 `GetType()`은 `System.Int32`를 반환한다.

여기서 즉시 따라 나오는 함정이 있다.

> **⚠️ `null`인 널 가능 값에 `GetType()`을 부르면 `NullReferenceException`이 난다**
>
> ```csharp
> int? x = null;
> Console.WriteLine(x.GetType());   // NullReferenceException!
> ```
>
> `x`가 `null`이므로 박싱 결과가 `null` 참조이고, 그 널 참조에 대해 `GetType()`을 호출하니 `NullReferenceException`이다. **`HasValue == false`인 값에 `HasValue`, `Value`, `GetValueOrDefault`, `ToString`, `Equals`, `GetHashCode`를 부르는 것은 전부 안전하지만 `GetType()`만 터진다.** 이유는 앞의 여섯은 `Nullable<T>`가 직접 갖는 멤버라 박싱이 필요 없고, `GetType()`만 박싱이 필요하기 때문이다.
>
> 실행 시점 타입이 필요하면 `Nullable.GetUnderlyingType(typeof(T))`나 정적 타입 정보를 쓰고, 인스턴스에 `GetType()`을 부르지 마라.

이 원리는 다른 멤버에도 적용된다. `Nullable<T>`가 재정의한 `ToString`, `Equals`, `GetHashCode`는 박싱 없이 호출된다(`constrained.` 접두 옵코드로 처리된다. 15.2절 참조). 재정의하지 않은 `GetType`만 박싱을 유발한다.

| 호출 | 박싱 여부 | `null`일 때 |
|---|---|---|
| `x.HasValue` | 없음 | `false` |
| `x.GetValueOrDefault()` | 없음 | `default(T)` |
| `x.Value` | 없음 | `InvalidOperationException` |
| `x.ToString()` | 없음 (재정의됨) | `""` |
| `x.Equals(o)` | 없음 (재정의됨) | `o == null`이면 `true` |
| `x.GetHashCode()` | 없음 (재정의됨) | `0` |
| `x.GetType()` | **있음** | **`NullReferenceException`** |

### 인터페이스 메서드 호출 — 세 번째 특별 지원

`Nullable<T>`는 `T`가 구현하는 인터페이스를 구현하지 않는다. `Nullable<int>`는 `IComparable<int>`도 `IFormattable`도 구현하지 않는다. 그런데도 다음 코드가 컴파일되고 실행된다.

```csharp
int? n = 5;
int result = ((IComparable) n).CompareTo(5);   // 컴파일·실행 모두 OK
Console.WriteLine(result);                     // 0
```

C# 컴파일러가 이 코드를 허용하고, CLR의 검증기도 검증 가능한 코드로 인정한다. 원리는 앞과 같다. 인터페이스로 캐스팅하려면 박싱해야 하고, 박싱하면 박스의 타입이 `Int32`이며, `Int32`는 `IComparable`을 구현한다.

이 특별 지원이 없다면 밑바탕 타입으로 먼저 내린 다음 인터페이스로 올려야 했을 것이다.

```csharp
int result = ((IComparable) (int) n).CompareTo(5);   // 번거롭다
```

물론 여기에도 널 함정이 그대로 있다.

> **⚠️ 인터페이스 캐스팅도 `null`이면 널 참조가 된다**
>
> ```csharp
> int? n = null;
> IComparable c = (IComparable) n;      // c는 null — 예외 없음
> int r = c.CompareTo(5);               // NullReferenceException
> ```
>
> 캐스팅 자체는 성공하고 `null`을 준다. 터지는 것은 그 다음 줄이다. 널 가능 값을 인터페이스로 올리는 코드는 반드시 `HasValue`를 먼저 검사해야 한다. 제네릭 메서드에 `where T : IComparable` 제약을 걸고 `int?`를 넘기는 코드가 실전에서 이 함정에 걸린다.

### 성능 — 박싱은 여전히 박싱이다

CLR의 특별 지원은 **의미론**을 고친 것이지 **비용**을 없앤 것이 아니다. `Nullable<int>` 대신 `Int32`를 박싱하니 박스가 조금 작아지기는 하지만, 힙 할당은 그대로 일어난다. 15.7절의 박싱 최소화 체크리스트가 널 가능 값 타입에도 그대로 적용된다. 특히 다음 세 패턴이 조용히 박싱한다.

```csharp
int? n = 5;
Console.WriteLine("{0}", n);              // 1. object[] 배열에 박싱
IFormattable f = (IFormattable) n;        // 2. 인터페이스 캐스팅에서 박싱
Type t = n.GetType();                     // 3. GetType() 호출에서 박싱
```

첫 번째는 문자열 보간(`$"{n}"`)으로 대부분 피할 수 있다. `ToString()`은 재정의되어 있으므로 `n.ToString()`은 박싱하지 않는다.

## 21.4 연산자 리프팅(operator lifting)

### 문법 — 없는 연산자가 동작한다

`Nullable<T>` 구조체 정의를 다시 보라. `<`, `>`, `==`, `+` 어느 것도 정의되어 있지 않다. 그런데 다음 코드는 컴파일되고 올바르게 동작한다.

```csharp
int? x = 5;
int? y = 10;
bool b = x < y;      // true
int? z = x + y;      // 15
```

컴파일러가 밑바탕 타입 `int`의 연산자를 **빌려 오기(lift)** 때문이다. 이것을 **연산자 리프팅**이라고 한다. `T`에 어떤 연산자가 있으면 `T?`에도 그에 대응하는 연산자가 자동으로 생긴다.

리프팅의 규칙은 연산자 부류마다 다르다. **이 절에서 반드시 기억해야 할 것은 부류가 셋이고, 셋의 널 처리 규칙이 전부 다르다는 것이다.**

### 규칙 1 — 산술·비트·시프트·단항 연산자: 널이 전파된다

대상: `+`, `-`, `*`, `/`, `%`, `&`, `|`, `^`, `<<`, `>>`, 단항 `+`, `-`, `++`, `--`, `!`, `~`

**피연산자 중 하나라도 `null`이면 결과는 `null`이다.** SQL을 써 봤다면 익숙한 규칙이다.

```csharp
int? x = 5, y = null;
int? c = x + y;      // null
```

컴파일러는 이것을 다음으로 번역한다.

```csharp
int? c = (x.HasValue && y.HasValue)
       ? (int?)(x.Value + y.Value)
       : null;
```

단항 연산자도 같다.

```csharp
int? a = 5, b = null;
a++;         // a = 6
b = -b;      // b = null — 부호를 뒤집을 값이 없다
b = ~b;      // b = null
```

### 규칙 2 — 동등 연산자 `==`, `!=`: 참조 타입처럼 동작한다

**둘 다 `null`이면 같고, 하나만 `null`이면 다르고, 둘 다 값이 있으면 값을 비교한다.** 즉 참조 타입의 널 비교와 같은 직관이 성립한다.

```csharp
Console.WriteLine(           null ==            null);   // True
Console.WriteLine((bool?)null == (bool?)null);           // True
```

세부 규칙은 셋이다.

- 정확히 한쪽만 `null`이면 두 피연산자는 같지 않다.
- 양쪽 다 `null`이 아니면 `Value`끼리 비교한다.
- 양쪽 다 `null`이면 같다.

```csharp
int? x = 5, y = null;
Console.WriteLine(x == y);        // False
Console.WriteLine(x == null);     // False
Console.WriteLine(x == 5);        // True
Console.WriteLine(y == null);     // True
Console.WriteLine(y == 5);        // False
Console.WriteLine(y != 5);        // True
```

**동등 연산자의 결과 타입은 `bool`이지 `bool?`가 아니다.** 규칙 1과 여기서 갈린다. `x + y`는 `int?`가 되지만 `x == y`는 `bool`이 된다. 그래서 `if (x == y)`가 그대로 컴파일된다.

### 규칙 3 — 비교 연산자 `<`, `>`, `<=`, `>=`: 널이면 항상 `false`

**`null`을 비교하는 것은 의미가 없다**는 원칙이다. 한쪽이라도 `null`이면 결과는 무조건 `false`다.

```csharp
int? x = 5, y = null;
bool b = x < y;
// 번역:
// bool b = (x.HasValue && y.HasValue) ? (x.Value < y.Value) : false;
// b는 false
```

```csharp
Console.WriteLine(x < 6);    // True
Console.WriteLine(y < 6);    // False
Console.WriteLine(y > 6);    // False
```

`y`가 `null`일 때 `y < 6`도 `false`이고 `y > 6`도 `false`다. **비교 연산자의 결과 타입도 `bool`이다.**

> **⚠️ `!(a < b)`와 `a >= b`는 널 가능 값에서 같지 않다**
>
> 이 장에서 가장 자주 사고를 내는 규칙이다.
>
> ```csharp
> int? a = null;
> int? b = 5;
>
> Console.WriteLine(a < b);       // False
> Console.WriteLine(a >= b);      // False   ← !(a < b)는 True인데!
> Console.WriteLine(!(a < b));    // True
> ```
>
> 널이 아닌 `int`에서는 `!(a < b)`와 `a >= b`가 항상 같지만, `int?`에서는 **셋 중 하나가 널이면 둘 다 `false`가 되어 등식이 깨진다.** 삼분법(trichotomy)이 성립하지 않는 것이다.
>
> 정렬 비교자나 이분 탐색 루프를 널 가능 값으로 쓸 때 이 성질이 무한 루프나 잘못된 정렬을 만든다. 널 가능 값을 정렬해야 한다면 비교 연산자 대신 `Nullable.Compare<T>`를 쓰거나(널이 가장 작다), 널을 먼저 걸러내야 한다.

> **⚠️ 비교 연산자와 동등 연산자의 널 규칙이 다르다는 것을 놓치지 마라**
>
> 둘 다 `bool`을 반환하니 같은 부류처럼 보이지만 규칙이 정반대다.
>
> ```csharp
> int? n = null;
> Console.WriteLine(n == null);   // True   — 동등 연산자는 널끼리 같다고 본다
> Console.WriteLine(n <= null);   // False  — 비교 연산자는 널이 끼면 무조건 false
> ```
>
> `n == null`은 참인데 `n <= null`은 거짓이다. `==`는 "널이라는 상태"를 비교하고, `<`/`>`는 "값의 크기"를 비교하기 때문이다. 값이 없으면 크기도 없다.

### 세 규칙 정리표

| 연산자 부류 | 연산자 | 한쪽이 `null` | 양쪽 다 `null` | 결과 타입 |
|---|---|---|---|---|
| 단항 산술·비트 | `+` `-` `++` `--` `!` `~` | `null` | `null` | `T?` |
| 이항 산술·비트·시프트 | `+` `-` `*` `/` `%` `&` `\|` `^` `<<` `>>` | `null` | `null` | `T?` |
| 동등 | `==` `!=` | 같지 않다 | 같다 | `bool` |
| 비교 | `<` `>` `<=` `>=` | `false` | `false` | `bool` |
| 예외 | `bool?`에 대한 `&` `\|` | 3값 논리 (21.5절) | `null` | `bool?` |

### 컴파일 결과 — 리프팅은 코드를 만든다

리프팅은 무료가 아니다. 컴파일러가 실제 코드를 생성한다. 다음 메서드를 보자.

```csharp
private static int? NullableCodeSize(int? a, int? b)
{
    return a + b;
}
```

컴파일러가 만드는 IL을 C#으로 되돌리면 이런 모양이다.

```csharp
private static Nullable<int> NullableCodeSize(Nullable<int> a, Nullable<int> b)
{
    Nullable<int> nullable1 = a;
    Nullable<int> nullable2 = b;
    if (!(nullable1.HasValue & nullable2.HasValue))
    {
        return new Nullable<int>();
    }
    return new Nullable<int>(nullable1.GetValueOrDefault() + nullable2.GetValueOrDefault());
}
```

한 줄짜리 `a + b`가 지역 변수 둘, 조건 분기 하나, 생성자 호출 둘로 부풀었다. IL로 보면 다음과 비슷한 형태가 된다(정확한 명령 배치는 컴파일러 버전에 따라 달라진다).

### 성능 — 언제 문제가 되는가

| 상황 | 영향 |
|---|---|
| 단발 계산 | 무시해도 좋다. 분기 예측이 거의 항상 맞는다 |
| 수백만 회 루프 | 분기와 구조체 복사가 누적된다. 2~5배 느려질 수 있다 |
| LINQ 집계 (`Sum`, `Average`) | `int?` 오버로드는 요소마다 널 검사를 한다 |
| SIMD·벡터화 대상 코드 | 벡터화가 아예 불가능해진다 |

> **💡 널 검사는 루프 밖으로 빼라**
>
> 널 가능 값의 배열을 반복 계산하는 코드라면, 루프 안에서 리프팅된 연산자를 쓰는 대신 루프 진입 전에 널을 걸러내고 밑바탕 타입 배열로 옮기는 편이 대개 빠르다.
>
> ```csharp
> // 느리다 — 요소마다 HasValue 분기
> int? total = 0;
> foreach (int? v in values) total += v;
>
> // 빠르다 — 널 처리 정책을 한 번만 정하고 int로 계산
> int total2 = 0;
> foreach (int? v in values)
>     if (v.HasValue) total2 += v.GetValueOrDefault();
> ```
>
> 두 코드는 **의미가 다르다.** 첫 번째는 널이 하나라도 있으면 총합이 `null`이 되고, 두 번째는 널을 0으로 취급한다. 어느 쪽이 맞는지는 도메인이 정한다. 중요한 것은 그 정책을 **명시적으로 선택하는 것**이지, 리프팅에 맡겨 우연히 결정되게 두는 것이 아니다.

### 사용자 정의 연산자도 리프팅된다

직접 만든 값 타입에 연산자를 오버로딩하면(22장) 그 연산자도 자동으로 리프팅된다. 조건은 하나다. **피연산자 타입과 결과 타입이 모두 널 가능이 아닌 값 타입이어야 한다.**

```csharp
internal struct Point
{
    private Int32 m_x, m_y;
    public Point(Int32 x, Int32 y) { m_x = x; m_y = y; }

    public static Boolean operator ==(Point p1, Point p2)
        => (p1.m_x == p2.m_x) && (p1.m_y == p2.m_y);

    public static Boolean operator !=(Point p1, Point p2)
        => !(p1 == p2);
}
```

이제 `Point?`에 그 연산자를 쓸 수 있다.

```csharp
Point? p1 = new Point(1, 1);
Point? p2 = new Point(2, 2);
Console.WriteLine("Are points equal? "     + (p1 == p2));   // False
Console.WriteLine("Are points not equal? " + (p1 != p2));   // True
```

두 값이 모두 널이 아니므로 사용자 정의 `==`가 실제로 호출되었다. 한쪽이 널이었다면 연산자는 호출되지 않고 규칙 2가 적용되어 `false`가 나온다.

> **⚠️ 사용자 정의 연산자는 널 피연산자에 대해 호출되지 않는다**
>
> 연산자 안에 로깅·검증·카운팅을 넣어 두었다면, 널 피연산자에서는 그 코드가 실행되지 않는다. 컴파일러가 만든 널 검사가 먼저 걸러 버리기 때문이다.
>
> `T?`에 대한 연산자를 **직접** 정의해서 특수한 널 동작을 줄 수는 있다. 하지만 압도적 다수의 경우 그렇게 하지 마라. 컴파일러가 자동으로 적용하는 체계적인 널 논리를 쓰는 편이, 타입마다 널 규칙이 달라지는 것보다 훨씬 안전하다.

### 널 가능과 널 불가능을 섞어 쓰기

`T`에서 `T?`로 암시적 변환이 있으므로 두 종류를 섞을 수 있다.

```csharp
int? a = null;
int  b = 2;
int? c = a + b;      // c는 null — a + (int?)b 와 같다
```

`b`가 `int?`로 승격된 뒤 규칙 1이 적용된다. 결과 타입도 `int?`다. **널 가능 값이 하나라도 끼면 식 전체가 널 가능이 된다.** 이 전염성 때문에 `int` 변수에 대입하려면 `??`나 명시적 캐스트가 필요해진다.

```csharp
int d = a + b;         // 컴파일 오류 CS0266 — int?를 int에 넣을 수 없다
int e = (a + b) ?? 0;  // OK
```

## 21.5 `bool?`와 `&` / `|` 연산자의 3값 논리

### 예외 조항

21.4절의 규칙 1은 "이항 연산자는 피연산자 중 하나라도 널이면 결과가 널"이었다. 여기에 **예외가 딱 하나** 있다. **`bool?` 피연산자에 대한 `&`와 `|`다.**

이 예외가 존재하는 이유는 논리다. `bool?`의 `null`은 "참인지 거짓인지 모른다"는 뜻으로 읽을 수 있고, 그렇다면 모르는 값이 끼어도 결과가 결정되는 경우가 있다.

```csharp
bool? unknown = null;
Console.WriteLine(unknown | true);    // True — null이 아니다!
```

`unknown`이 무엇이든 `| true`의 결과는 `true`다.

- 모르는 값이 `false`라면 → `false | true` = `true`
- 모르는 값이 `true`라면 → `true | true` = `true`

어느 쪽이든 `true`이므로 결과를 결정할 수 있다. 반대로 `&`는 `false`가 흡수원소다.

```csharp
Console.WriteLine(unknown & false);   // False
```

이것이 SQL의 3값 논리(three-valued logic)와 같은 규칙이며, C#이 데이터베이스 데이터를 자연스럽게 다루게 하려고 채택한 것이다.

### 전체 진리표

```csharp
bool? n = null, f = false, t = true;
Console.WriteLine(n | n);   // (null)
Console.WriteLine(n | f);   // (null)
Console.WriteLine(n | t);   // True
Console.WriteLine(n & n);   // (null)
Console.WriteLine(n & f);   // False
Console.WriteLine(n & t);   // (null)
```

두 연산자를 한 표로 정리하면 다음과 같다.

| 왼쪽 → / 아래 ↓ | `true` | `false` | `null` |
|---|---|---|---|
| **`true`** | `&` = `true`<br>`\|` = `true` | `&` = `false`<br>`\|` = `true` | `&` = `null`<br>`\|` = `true` |
| **`false`** | `&` = `false`<br>`\|` = `true` | `&` = `false`<br>`\|` = `false` | `&` = `false`<br>`\|` = `null` |
| **`null`** | `&` = `null`<br>`\|` = `true` | `&` = `false`<br>`\|` = `null` | `&` = `null`<br>`\|` = `null` |

읽는 법은 간단하다.

- `&`: 어느 한쪽이라도 `false`면 결과는 `false`. 아니면 널이 있으면 `null`.
- `|`: 어느 한쪽이라도 `true`면 결과는 `true`. 아니면 널이 있으면 `null`.

**결과가 결정되면 결정된 값을 주고, 결정되지 않으면 `null`을 준다.** 이 한 문장이 3값 논리의 전부다.

`^`(XOR)에는 이 예외가 적용되지 않는다는 점에 주의하라. `null ^ true`는 `null`이다. XOR은 한쪽 값만으로 결과가 결정되는 경우가 없으니 당연한 결과다.

> **📌 3값 논리는 널을 "모름"으로 해석한 결과다**
>
> `bool?`의 `null`을 "값 없음"으로 읽으면 `null | true`가 `null`이어야 할 것 같다. "값 없음"에 무엇을 OR해도 값이 없어야 하니까. 그런데 "모름"으로 읽으면 답이 달라진다. **C#은 `bool?`에 한해 "모름" 해석을 채택했다.** 이것은 논리적 우아함 때문이 아니라 SQL 호환성 때문이다. SQL의 `WHERE` 절이 정확히 이 규칙으로 동작하므로, 데이터베이스 조건식을 C#으로 옮길 때 같은 결과가 나온다.
>
> 다른 널 가능 값 타입에는 이 해석이 적용되지 않는다. `int? + int?`에서 널은 여전히 "값 없음"이다.

### `&&`와 `||`는 `bool?`에 쓸 수 없다

여기가 실무에서 가장 자주 걸리는 지점이다.

```csharp
bool? a = true, b = null;
bool? c = a && b;    // 컴파일 오류!
```

오류 메시지는 다음과 같다.

```text
error CS0019: Operator '&&' cannot be applied to operands of type 'bool?' and 'bool?'
```

`&&`와 `||`는 조건부 논리 연산자다. 컴파일러는 이 연산자를 처리할 때 왼쪽 피연산자를 평가한 뒤 **"참인가 거짓인가"를 즉시 판정**해서 오른쪽 평가 여부를 결정해야 한다. `bool?`에는 그 판정에 쓸 세 번째 상태가 있으므로 단축 평가를 정의할 수 없다.

정확히는, `&&`와 `||`가 성립하려면 그 타입에 `true` 연산자와 `false` 연산자가 정의되어 있어야 한다(22.5절). `Nullable<bool>`에는 없다.

> **⚠️ `bool?`를 `if`에 그대로 넣을 수 없다**
>
> ```csharp
> bool? flag = GetFlag();
> if (flag) { }        // 컴파일 오류 CS0266
> ```
>
> `if`는 `bool`을 요구한다. `bool?`에서 `bool`로 가는 암시적 변환은 없다. 해결책은 셋이다.
>
> ```csharp
> if (flag == true) { }               // 널이면 false — 가장 흔한 관용구
> if (flag.GetValueOrDefault()) { }   // 널이면 false — 같은 의미
> if (flag ?? false) { }              // 널이면 false — 기본값이 명시적
> ```
>
> 셋 다 "널은 거짓 취급"이다. 널을 참 취급하려면 `flag ?? true`나 `flag != false`를 써야 한다. **`flag != false`와 `flag == true`가 널일 때 정반대라는 것**을 잊지 마라. 널이면 앞은 `true`, 뒤는 `false`다.

### 세 상태를 다루는 실전 패턴

3값 논리를 쓰는 코드는 읽기 어렵다. 널이 어디서 들어와서 어디까지 전파되는지 추적해야 하기 때문이다. 실전에서는 다음 두 패턴 중 하나를 쓴다.

**패턴 1 — 경계에서 널을 없앤다.** 가장 안전하다.

```csharp
bool isActive = record.IsActive ?? false;   // 미지정은 비활성으로 취급
bool isAdmin  = record.IsAdmin  ?? false;
if (isActive && isAdmin) { /* ... */ }      // 여기서는 && 를 쓸 수 있다
```

**패턴 2 — 널을 끝까지 유지하고 마지막에만 결정한다.** 3값 논리가 진짜 필요할 때만.

```csharp
bool? matchesName  = ComputeNameMatch(query);      // 판정 불가면 null
bool? matchesEmail = ComputeEmailMatch(query);

bool? result = matchesName | matchesEmail;         // 한쪽이라도 true면 true
bool include = result ?? false;                     // 최종 결정
```

두 번째 패턴에서 `|`를 쓰는 것이 핵심이다. `||`는 쓸 수 없고, 억지로 `(matchesName ?? false) || (matchesEmail ?? false)`로 바꾸면 **널이 `false`로 조기 붕괴해서** 3값 논리의 이점이 사라진다.

> **💡 `bool?`는 정말 "모름"일 때만 써라**
>
> `bool?`를 쓰는 코드의 대부분은 사실 두 상태만 필요한데 초기화를 미루려고 널을 쓴 것이다. 그런 경우에는 `bool` 두 개(값과 "설정되었는가")나 세 값짜리 `enum`이 훨씬 읽기 쉽다.
>
> ```csharp
> enum ApprovalState { Pending, Approved, Rejected }
> ```
>
> 세 상태에 이름이 붙으면 `null`이 무엇을 뜻하는지 문서를 찾을 필요가 없어진다. **`bool?`는 세 번째 상태의 의미가 진짜로 "모름"이고, 그 모름이 3값 논리를 따라 전파되어야 할 때만 쓴다.** 데이터베이스 컬럼 매핑과 SQL 조건식 변환이 거의 유일한 정당한 용도다.

> **⚠️ `&`와 `|`는 단축 평가하지 않는다**
>
> `bool?`에 3값 논리가 있다고 해서 `&`가 `&&`를 대체하지는 않는다. `&`는 **양쪽 피연산자를 항상 평가한다.**
>
> ```csharp
> bool? a = false;
> bool? b = ExpensiveCheck();       // a가 false여도 반드시 호출된다
> bool? c = a & b;
> ```
>
> 널 검사를 겸한 단축 평가 관용구(`if (x != null && x.Length > 0)`)를 `&`로 바꾸면 널 참조 예외가 난다. 이 관용구는 `bool`끼리의 `&&`이므로 애초에 3값 논리와 무관하다. **`bool?`가 등장하지 않는 곳에서 `&&`를 `&`로 바꾸지 마라.**

## 21.6 널 가능 참조 타입(NRT) ※C# 8 — 컴파일 타임 전용 계약

### 방향이 반대인 기능

지금까지 본 널 가능 값 타입은 **값 타입에 널을 도입**했다. 널 가능 참조 타입(nullable reference types, NRT)은 정확히 반대다. **참조 타입에 (어느 정도의) 널 불가능성을 도입한다.** 목적은 `NullReferenceException`을 줄이는 것이다.

C# 7까지의 상태를 표로 그리면 네 칸 중 세 칸만 차 있었다. C# 8이 나머지 한 칸을 채운다.

| | 널 가능 | 널 불가능 (C# 7) | 널 불가능 (C# 8) |
|---|---|---|---|
| **참조 타입** | CLR 타입 표현은 없고, `?` 접미사가 **주석** 역할 | **지원되지 않음** | NRT를 켜면 **기본값** |
| **값 타입** | `Nullable<T>` 또는 `?` 접미사 | 기본값 | 기본값 |

C# 7에서는 "이 `string` 매개변수는 절대 널이 아니다"를 컴파일러가 이해하는 방식으로 표현할 수 없었다. 주석이나 문서에는 쓸 수 있지만 컴파일러는 읽지 못한다.

이제 첫 행과 둘째 행의 "널 가능" 칸을 비교해 보라. 값 타입 쪽 널 가능은 **"`Nullable<T>`"라는 실재하는 타입**이고, 참조 타입 쪽 널 가능은 **"CLR 타입 표현은 없고 주석뿐"** 이다. **이 비대칭이 이 장 전체에서 가장 중요한 사실이다.**

### 문법 — `?`를 붙이면 널을 허용한다

NRT를 켜면 컴파일러의 기본 가정이 바뀐다. **주석 없는 참조 타입은 널이 아니라고 가정하고, 널을 허용하려면 `?`를 붙여야 한다.**

```csharp
#nullable enable      // 이 지점부터 널 가능 참조 타입 활성화

string s1 = null;     // 경고! s1은 널 불가능으로 선언되었다
string? s2 = null;    // OK — s2는 널 가능 참조 타입
```

첫 줄은 오류가 아니라 **경고**다. 코드는 그대로 컴파일되고 그대로 실행된다.

초기화되지 않은 필드도 경고를 부른다.

```csharp
class Foo { string x; }    // 경고 CS8618 — x가 널로 남는다
```

필드 초기화자를 주거나 생성자에서 대입하면 경고가 사라진다.

```csharp
class Foo1 { string x = ""; }                       // OK
class Foo2 { string x; public Foo2() { x = ""; } }  // OK
```

### 실체 — 런타임에 아무것도 강제하지 않는다

> **⚠️ NRT는 컴파일 타임 구조물이다. 런타임에 `string`과 `string?`은 완전히 같은 타입이다**
>
> 이 문장을 세 번 읽어라. NRT의 오해는 전부 여기서 나온다.
>
> - `string?`이라는 CLR 타입은 **존재하지 않는다.** `typeof(string?)`은 `typeof(string)`과 같은 `Type` 객체다.
> - `?`를 붙이거나 떼도 **생성되는 IL 명령이 하나도 바뀌지 않는다.**
> - 널 불가능으로 선언한 매개변수에 널이 들어와도 **아무 예외도 던져지지 않는다.** 그 값을 역참조하는 순간 평범한 `NullReferenceException`이 날 뿐이다.
> - `Nullable.GetUnderlyingType`으로 판정할 수 없다. 그 메서드는 값 타입 전용이다.
>
> 반면 널 가능 값 타입은 타입 시스템에 **실체를 도입한다.** `Nullable<T>`라는 구조체가 실제로 만들어지고, `typeof(int?) != typeof(int)`이며, 박싱 동작까지 CLR이 특별 취급한다. **같은 `?` 기호를 쓰지만 완전히 다른 두 기능이다.**

C# 컴파일러는 어떻게 이 정보를 어셈블리에 남길까. 20장에서 배운 특성을 쓴다.

### 컴파일 결과 — `NullableAttribute`와 `NullableContextAttribute`

컴파일러는 널 가능 주석을 `System.Runtime.CompilerServices` 네임스페이스의 두 특성으로 인코딩해 메타데이터에 심는다. `NullableAttribute`는 개별 멤버·매개변수·반환값·타입 인자에 붙어 **그 자리의** 널 가능성을 바이트로 담고, `NullableContextAttribute`는 타입·메서드·모듈에 붙어 **그 범위의 기본값**을 담는다. 대다수 자리를 후자 하나로 덮어 메타데이터 크기를 줄이는 구조다.

인코딩 값은 셋이다. `0`은 oblivious(널 가능성을 모른다 — NRT를 켜지 않고 컴파일된 코드), `1`은 not annotated(널 불가능 — `string`), `2`는 annotated(널 가능 — `string?`)를 뜻한다.

제네릭이 섞이면 바이트 배열이 된다. `Dictionary<string, List<string?>>?` 같은 타입은 중첩된 각 위치의 널 가능성을 순서대로 담은 `byte[]`로 인코딩된다.

```csharp
// 소스
public string? Find(string key, List<string?> items) { ... }
```

이 시그니처를 ILSpy 같은 도구로 열면 대략 다음 형태가 보인다.

```csharp
// 디컴파일 결과 (개념적 형태)
[return: Nullable(2)]
public string Find(string key, [Nullable(new byte[] { 1, 2 })] List<string> items) { ... }
```

**IL 시그니처의 타입은 전부 `string`이다.** 널 가능성은 특성 안의 바이트일 뿐이다.

> **📌 이 특성들은 컴파일러가 어셈블리 안에 직접 만들어 넣는다**
>
> `NullableAttribute`와 `NullableContextAttribute`는 BCL에서 오지 않는다. C# 컴파일러가 필요할 때마다 **컴파일 대상 어셈블리 안에 `internal` 클래스로 직접 생성해서 넣는다.** 그래서 오래된 대상 프레임워크(예: .NET Framework 4.6.1을 대상으로 하는 프로젝트)에서도 NRT를 쓸 수 있다. 런타임 지원이 전혀 필요 없기 때문이다.
>
> 부작용도 있다. 어셈블리마다 같은 이름의 `internal` 특성 클래스가 따로 존재하게 되고, 어셈블리를 넘나들며 이 특성을 리플렉션으로 읽으려면 **이름 문자열로 비교**해야 한다. 실제로 널 가능성을 런타임에 읽어야 하는 직렬화기·검증 프레임워크가 이 방식을 쓴다. .NET 6부터는 `System.Reflection.NullabilityInfoContext`가 이 해석을 대신해 준다 ※.NET 6.

> **⚠️ 런타임 널 검사가 필요하면 직접 써야 한다**
>
> "NRT를 켰으니 널 검사 코드를 지워도 된다"는 판단이 가장 흔한 사고 원인이다. 다음 셋 중 하나만 성립해도 널이 들어온다.
>
> - 호출자가 경고를 무시했다.
> - 호출자가 `!` 연산자로 경고를 눌렀다(21.8절).
> - 호출자가 NRT를 켜지 않은 프로젝트이거나, 리플렉션·역직렬화·상호운용을 통해 값을 만들었다.
>
> **공개 API의 인자 검증은 NRT와 무관하게 계속 필요하다.** 방어적 프로그래밍은 여전히 모범 사례다. 21.10절에서 그 관용구를 다룬다.

### 흐름 분석 — 컴파일러가 널 상태를 추적한다

NRT의 경고는 "타입이 `string?`인가"만 보고 내지 않는다. 그렇게 하면 다음 코드가 경고를 낼 것이다.

```csharp
Address? address = customer.Address;
if (address != null)
{
    Console.WriteLine(address.Country);   // 안전한데도 경고가 날까?
}
```

경고가 나지 않는다. 컴파일러가 **각 지점에서 각 식의 널 상태(null state)를 따로 추적**하기 때문이다. 이 분석은 확정 할당 분석(6.9절)과 같은 방식으로 동작한다.

널 상태는 두 가지다.

```text
     선언 / 대입
          │
          ▼
   ┌──────────────┐   x != null 검사 통과      ┌──────────────┐
   │ maybe-null   │ ──────────────────────────▶│  not-null    │
   │ (널일 수     │   x is not null            │ (널이 아님이 │
   │  있음)       │   x!                       │  증명됨)     │
   │              │◀────────────────────────── │              │
   └──────────────┘   널 가능 값 대입          └──────────────┘
          │                                            │
          │ 역참조 → 경고 CS8602                       │ 역참조 → 경고 없음
          ▼                                            ▼
```

`Address?`로 선언했어도 `if (address != null)` 안쪽에서는 상태가 not-null이므로 경고가 없다. 반대로 `string`(널 불가능)으로 선언했어도 널일 수 있는 값을 대입하면 그 이후 상태는 maybe-null이 된다.

지역 변수 없이 프로퍼티를 두 번 접근해도 마찬가지다.

```csharp
if (customer.Address != null)
{
    Console.WriteLine(customer.Address.Country);   // 경고 없음
}
```

컴파일러는 변수뿐 아니라 **프로퍼티 접근 경로**의 상태도 추적한다. 같은 값에 같은 프로퍼티를 두 번 접근하면 두 번 다 같은 결과가 나온다고 가정한다.

> **⚠️ 이 가정은 안전하지 않다 — 그리고 C# 설계팀도 그것을 알고 있다**
>
> 두 접근 사이에 다른 스레드가 `Address`를 `null`로 바꿀 수 있다. `Address` 프로퍼티가 매번 다른 값을 반환하도록 구현되어 있을 수도 있다. 즉 **위 코드는 경고 없이 `NullReferenceException`을 낼 수 있다.**
>
> 이것은 버그가 아니라 의도된 절충이다. 100% 안전하게 만들려면 훨씬 침습적인 언어 변경이 필요했고, 그러면 아무도 이 기능을 켜지 않았을 것이다. **NRT는 "널 참조 예외를 없애는 기능"이 아니라 "널 참조 예외를 크게 줄이는 기능"이다.** 이 한계를 알고 쓰면 문제가 없다.

### 흐름 분석이 추적을 잃는 자리

컴파일러의 분석은 강력하지만 완벽하지 않다. 다음 자리에서 추적이 끊긴다.

| 상황 | 결과 | 예 |
|---|---|---|
| 배열 요소 | 초기화 여부를 모른다. 경고 없이 널을 준다 | `new string[10]` |
| 헬퍼 메서드의 널 검사 | 반환값과 입력의 관계를 모른다 | `if (!IsNullOrEmpty(s)) s.Length` |
| `out` 매개변수 | 특성이 없으면 결과와 무관하게 판단 | `TryGetValue` |
| 람다·지역 함수 캡처 | 호출 시점을 모르므로 보수적으로 판단 | 클로저 안의 필드 접근 |
| 다른 스레드 | 아예 모델링하지 않는다 | 위 ⚠️ 박스 |
| 리플렉션·역직렬화 | 컴파일러 시야 밖이다 | `JsonSerializer.Deserialize` |
| 반복자·비동기 메서드 경계 | 상태 기계 변환으로 일부 정보가 소실 | `yield return` 사이 |

배열 예제가 가장 인상적이다.

```csharp
var strings = new string[10];        // 경고 없음
Console.WriteLine(strings[0].Length); // 경고 없음 — 그리고 NullReferenceException
```

`string[]`은 널 불가능 `string`의 배열이지만, 배열 생성은 모든 요소를 `null`로 초기화한다. 컴파일러는 배열 요소가 채워졌는지 알 방법이 없어서 아무 말도 하지 않는다. 표의 두 번째 항목(헬퍼 메서드)은 특성으로 해결할 수 있다. 21.9절의 주제다.

### 일반적인 널 가능성 경고 코드

| 코드 | 의미 |
|---|---|
| `CS8600` | 널 리터럴 또는 널일 수 있는 값을 널 불가능 타입으로 변환 |
| `CS8601` | 널일 수 있는 참조를 대입 |
| `CS8602` | 널일 수 있는 참조를 역참조 |
| `CS8603` | 널일 수 있는 참조를 반환 |
| `CS8604` | 널일 수 있는 참조를 인수로 전달 |
| `CS8618` | 널 불가능 필드가 생성자 종료 시점에 널이 아님이 보장되지 않음 |
| `CS8619` | 값의 널 가능성이 대상 타입과 맞지 않음 (제네릭 인자) |
| `CS8625` | 널 리터럴을 널 불가능 참조 타입으로 변환할 수 없음 |
| `CS8655` | `switch` 식이 널 입력을 처리하지 않음 (완전하지 않음) |

이 목록은 전부가 아니다. 널 가능성 관련 경고는 50개가 넘는다.

> **💡 세 개만 골라 오류로 승격하는 것이 실용적이다**
>
> 신규 프로젝트라면 처음부터 널 가능 문맥을 완전히 켜는 것이 좋다. 여기에 더해 **널 관련 경고를 오류로 다루면** 전부 해결되기 전까지 컴파일이 되지 않게 만들 수 있다.
>
> ```xml
> <PropertyGroup>
>   <Nullable>enable</Nullable>
>   <WarningsAsErrors>CS8600;CS8602;CS8603</WarningsAsErrors>
> </PropertyGroup>
> ```
>
> 셋을 고른 이유는 이것들이 **실제로 널 참조 예외로 이어지는** 경고이기 때문이다. `CS8618`(필드 초기화) 같은 경고는 소스 생성기나 ORM이 만드는 타입에서 대량으로 나기 쉬워, 초기에 오류로 올리면 작업이 막힌다. 프로젝트 전체를 `<TreatWarningsAsErrors>`로 잠그기 전에 이 세 개부터 시작하라.

## 21.7 널 허용 주석 컨텍스트와 점진적 마이그레이션 전략

### 두 개의 컨텍스트

`#nullable enable`이나 `<Nullable>enable</Nullable>`은 사실 **두 가지 별개의 스위치를 동시에 켠다.**

| 컨텍스트 | 켜면 무엇이 달라지는가 |
|---|---|
| **널 허용 주석 컨텍스트**<br>(nullable annotation context) | 주석 없는 참조 타입 선언을 **널 불가능**으로 해석한다. `?`가 의미를 갖는다 |
| **널 허용 경고 컨텍스트**<br>(nullable warning context) | `NullReferenceException` 위험이 있는 코드에 **경고를 낸다** |

이 둘을 분리해서 켤 수 있다.

```csharp
#nullable enable annotations    // 주석 컨텍스트만 켠다
// 또는
#nullable enable warnings       // 경고 컨텍스트만 켠다
```

`disable`과 `restore`에도 같은 수식어가 붙는다.

```csharp
#nullable disable annotations
#nullable restore warnings
```

프로젝트 파일에서도 같다.

```xml
<Nullable>enable</Nullable>       <!-- 둘 다 -->
<Nullable>disable</Nullable>      <!-- 둘 다 끔 (기본값) -->
<Nullable>annotations</Nullable>  <!-- 주석만 -->
<Nullable>warnings</Nullable>     <!-- 경고만 -->
```

네 값의 조합을 표로 보면 이렇다.

| `<Nullable>` 값 | 주석 | 경고 | 대표 용도 |
|---|---|---|---|
| `disable` | 끔 | 끔 | 기존 코드 그대로. `?`는 무의미해지고 경고 CS8632가 날 수 있다 |
| `annotations` | **켬** | 끔 | **라이브러리 마이그레이션 1단계.** 소비자에게 정보를 주되 내 경고는 안 봄 |
| `warnings` | 끔 | **켬** | 드물게 쓴다. 주석 없이 명백한 널 오용만 잡음 |
| `enable` | **켬** | **켬** | 신규 프로젝트의 기본 |

> **💡 `annotations`만 켜는 것이 레거시 라이브러리의 첫 단계다**
>
> 라이브러리를 만드는 쪽이라면 `annotations`만 먼저 켜는 것이 매우 실용적이다. 공개 멤버에 `?`를 정확히 달아 두면 **그 라이브러리를 쓰는 쪽은 NRT의 이점을 온전히 누린다.** 정작 라이브러리 내부에서는 경고를 하나도 보지 않는다.
>
> 즉 "다른 어셈블리에게 좋은 이웃이 되는" 작업을 내부 정리와 분리할 수 있다. 공개 API 표면은 어차피 가장 신중하게 검토해야 할 부분이고 개수도 적다. 내부 수천 줄의 경고를 해결하는 것은 그 다음에 해도 늦지 않다.

### `#nullable` 지시문의 범위

`#nullable` 지시문은 파일 안에서 나타난 지점부터 다음 지시문이나 파일 끝까지 적용된다. 전처리기 지시문이므로 문법 구조와 무관하게 **줄 단위**로 동작한다(12.7절).

```csharp
#nullable enable
public class NewCode    { public string Name { get; set; } = ""; }  // 검사받는다

#nullable disable
public class LegacyCode { public string Name { get; set; } }        // 경고 없음

#nullable restore
// 여기부터는 프로젝트 설정(<Nullable>)으로 돌아간다
```

`restore`가 중요하다. 파일 일부만 예외 처리하고 나머지는 프로젝트 정책을 따르게 만든다.

> **⚠️ `disable` 문맥의 `?`는 경고를 부른다**
>
> 널 허용 주석 컨텍스트가 꺼진 상태에서 참조 타입에 `?`를 붙이면 다음 경고가 난다.
>
> ```text
> warning CS8632: The annotation for nullable reference types should only be used
>                 in code within a '#nullable' annotations context.
> ```
>
> 이 경고는 흔히 **파일을 복사해 붙이면서** 발생한다. NRT를 켠 프로젝트에서 안 켠 프로젝트로 코드를 옮기면 `string?`이 전부 이 경고를 낸다. 값 타입의 `int?`는 영향받지 않는다는 점에 주의하라. 널 가능 값 타입은 컨텍스트와 무관하게 항상 유효하다.

### 경고를 부분적으로 끄는 방법

| 방법 | 범위 | 문법 |
|---|---|---|
| `<Nullable>` | 프로젝트 전체 | `<Nullable>enable</Nullable>` |
| `<NoWarn>` | 프로젝트 전체, 경고 코드별 | `<NoWarn>CS8600;CS8602</NoWarn>` |
| `#nullable disable` | 파일 일부, 널 관련 전체 | 지시문 |
| `#pragma warning disable` | 문 단위, 경고 코드별 | 지시문 |

가장 좁은 것이 `#pragma`다.

```csharp
#pragma warning disable CS8602
Console.WriteLine(firstName.Length);
Console.WriteLine(lastName.Length);
#pragma warning restore CS8602
```

`restore`를 반드시 짝지어라. 빠뜨리면 파일 끝까지 경고가 꺼진 채로 남는다. 이 기법은 널 관련 경고에만 쓰는 것이 아니라 모든 컴파일러 경고에 쓸 수 있다.

### 마이그레이션 — 두더지 잡기가 정상이다

기존 코드베이스에 NRT를 도입하는 과정은 예측 가능한 패턴을 따른다. 다음은 실제 오픈소스 라이브러리(Noda Time)를 C# 8 프리뷰로 마이그레이션한 기록이다.

첫 통과 후 경고가 약 100개였다. 대부분을 고치고 다시 빌드하니 경고가 약 110개로 **늘었다.** 그것을 다시 고치고 빌드하니 여전히 100개쯤 남았다. 이 반복이 여러 차례 이어졌다. **이것은 무언가 잘못되었다는 신호가 아니다.** 널 가능성을 한 곳에서 바꾸면 그 값을 쓰는 모든 자리에 경고가 번진다. 그것을 고치면 다시 그 다음 자리로 옮겨 간다. 널 가능성에 대한 결정은 코드 전체로 **전파**되며, 전파되는 동안 경고 개수는 오르내린다. 정상이다.

진짜 신호는 따로 있다. **코드의 한쪽은 값이 널이어야 한다고 하고 다른 쪽은 널이면 안 된다고 할 때, 진짜 문제를 발견한 것이다.** 이것은 C# 8이 만든 문제가 아니라 C# 8이 드러낸 문제다. 어떻게 해결할지는 맥락이 정한다.

최종 결과는 이랬다. 전체 작업에 약 5시간이 걸렸고(프리뷰 컴파일러 버그 진단 시간 포함), 실제 버그를 하나 발견했다 — 일부 환경에서 `TimeZoneInfo.Local`이 `null`을 반환하는 경우를 일관되게 처리하지 못하고 있었다. 그 밖에 누락된 주석 몇 개와 내부 멤버의 의도를 명확히 해야 하는 자리를 찾았다.

### 단계별 전략

```text
0단계  현재 상태 파악 — <Nullable>disable</Nullable> 로 두고 경고 개수만 측정
          │
          ▼
1단계  공개 API에 주석 달기 — <Nullable>annotations</Nullable>
       공개 멤버의 ? 만 정확히. 내부 경고는 안 봄
          │
          ▼
2단계  파일 단위로 경고 켜기 — 정리된 파일 맨 위에만 #nullable enable
          │
          ▼
3단계  프로젝트 전체 전환 — <Nullable>enable</Nullable>
       + 아직 못 고친 파일에 #nullable disable
          │
          ▼
4단계  잔여 disable 제거, 경고를 오류로 승격
       <WarningsAsErrors>CS8600;CS8602;CS8603</WarningsAsErrors>
```

2단계와 3단계 중 어느 쪽에서 시작할지는 코드베이스 규모가 정한다. 파일이 수천 개라면 2단계(옵트인)가, 수백 개라면 3단계(옵트아웃)가 빠르다. **마이크로소프트가 자사 패키지를 전환할 때 쓴 방식이 3단계, 즉 프로젝트에서 켜고 아직 안 된 파일에서 끄는 방식이었다.**

> **📌 .NET 생태계의 전환은 오래 걸렸다**
>
> C# 8은 2019년에 나왔지만, 마이크로소프트 자신도 주요 .NET 패키지 전부에 널 가능 주석을 다는 데 .NET 6까지 걸렸다. 로깅·의존성 주입·구성을 담당하는 `Microsoft.Extensions.*` 계열은 .NET 7에 가서야 주석이 붙었다.
>
> 그동안 소비자 쪽에서는 주석이 없는(oblivious) 어셈블리를 참조하게 되는데, 컴파일러는 그런 어셈블리에서 온 값에 대해 **경고를 내지 않는다.** 널 가능성을 "모른다"고 표시된 값은 어느 쪽으로도 판단하지 않기 때문이다. 이것이 마이그레이션 중인 생태계에서 경고 폭발을 막아 준 장치다. 오래된 NuGet 패키지를 쓰는 코드에서 갑자기 경고가 늘었다면, 그 패키지가 최근에 주석을 달았다는 뜻일 수 있다.

### 프로젝트 템플릿의 기본값

| 프로젝트 생성 시점 | `<Nullable>` 기본값 |
|---|---|
| .NET 5 이하 대상 템플릿 | 없음 (= `disable`) |
| .NET 6 이상 대상 템플릿 | `enable` |

**.NET 6 이후 템플릿으로 만든 프로젝트는 NRT가 켜진 상태로 시작한다.** 이것을 모르고 "왜 갑자기 경고가 나느냐"고 당황하는 경우가 많다. 끄고 싶으면 `.csproj`에서 `<Nullable>` 항목을 지우거나 `disable`로 바꾸면 된다. 다만 새 코드에서 끄는 것은 권하지 않는다.

> **⚠️ 널 가능 주석은 소비자에게 보이는 계약이다**
>
> 공개 멤버의 널 가능성을 나중에 바꾸면 그 라이브러리를 쓰는 코드에 새 경고가 쏟아진다. 널 불가능이던 반환 타입을 널 가능으로 바꾸는 것은 특히 파괴적이다. 이것은 바이너리 호환성은 깨지 않지만 소스 호환성은 깬다. 주석을 API 계약의 일부로 다루고 버전 정책에 포함해야 한다는 이야기는 78.13절에서 이어진다.

## 21.8 `!` (null-forgiving) 연산자를 쓸 자리

### 문법 — 컴파일러에게 "내가 안다"고 말한다

식 끝에 느낌표를 붙이면 **그 식의 널 상태를 not-null로 강제로 바꾼다.** 정식 명칭은 널 용인 연산자(null-forgiving operator)지만 커뮤니티에서는 흔히 bang 연산자라고 부른다.

```csharp
void Foo(string? s) => Console.Write(s.Length);    // 경고 CS8602
void Bar(string? s) => Console.Write(s!.Length);   // 경고 없음
```

두 메서드는 **완전히 같은 IL로 컴파일된다.** `!`는 IL을 만들지 않는다. 오직 컴파일러의 흐름 분석 상태만 바꾼다.

> **⚠️ `!`는 널 검사를 하지 않는다. 경고를 지울 뿐이다**
>
> 위 `Bar`에 `null`을 넘기면 `NullReferenceException`이 난다. 그것도 **경고 하나 없이.** `!`는 우리가 피하려던 바로 그 예외를 다시 불러들이는 데 완벽하게 협조한다.
>
> 진짜 해법은 조건 검사다.
>
> ```csharp
> void Baz(string? s)
> {
>     if (s != null) Console.Write(s.Length);
> }
> ```
>
> 여기서는 `!`가 필요 없다. 컴파일러의 흐름 분석이 `if` 안쪽에서 `s`가 널이 아님을 알기 때문이다(21.6절).

### `!`를 써야 하는 두 상황

`!`가 정당한 경우는 서로 정반대인 두 가지다.

**첫째, 컴파일러보다 내가 더 많이 알 때.**

```csharp
static void PrintLength(string? text)
{
    if (!string.IsNullOrEmpty(text))
    {
        Console.WriteLine($"{text}: {text!.Length}");
    }
    else
    {
        Console.WriteLine("Empty or null");
    }
}
```

`string.IsNullOrEmpty`가 `false`를 반환했다면 입력은 널일 수 없다. 하지만 컴파일러는 그 메서드의 **입력과 반환값 사이의 관계**를 모른다. `text!.Length`로 "내가 책임진다"고 말하는 것이다.

**이 특정 예제는 오늘날 필요 없다.** `string.IsNullOrEmpty`에는 `[NotNullWhen(false)]` 특성이 붙어 있어서 컴파일러가 관계를 이해한다(21.9절). 하지만 특성이 없는 자체 헬퍼 메서드에서는 여전히 같은 상황이 벌어진다. 그럴 때 올바른 대응은 `!`가 아니라 **헬퍼 메서드에 특성을 붙이는 것**이다.

**둘째, 일부러 널을 넣어 검증을 시험할 때.** 이쪽이 훨씬 더 정당하다.

```csharp
public class Customer
{
    public string Name { get; }
    public Address? Address { get; }

    public Customer(string name, Address? address)
    {
        Name = name ?? throw new ArgumentNullException(nameof(name));
        Address = address;
    }
}

[Test]
public void Customer_NameValidation()
    => Assert.Throws<ArgumentNullException>(
           () => new Customer(null!, new Address("UK")));   // 일부러 널을 넣는다
```

`name` 매개변수는 널 불가능으로 선언되었지만, 21.6절에서 본 대로 **런타임에는 아무것도 강제되지 않으므로** 인자 검증 코드는 여전히 필요하고 그 검증을 시험하는 테스트도 필요하다. `null` 그대로 쓰면 경고가 나므로 `null!`로 쓴다.

여기서 흥미로운 점 하나. 컴파일러는 `name ?? throw ...`라는 검증 코드 자체에는 아무 불평도 하지 않는다. `name`이 널일 수 없다고 선언되었는데 널 검사를 한다고 해서 "무의미한 검사"라고 경고하지 않는다는 뜻이다. 반면 호출부에서 널을 넘기는 것은 막으려 한다. **이 비대칭이 의도적이다.** 방어적 검증을 계속 쓰라는 신호다.

### `null!` 관용구의 다른 용도

```csharp
private string _connectionString = null!;                 // CS8618을 억제
public IServiceProvider Services { get; set; } = null!;   // 나중에 프레임워크가 채운다
```

프레임워크가 나중에 값을 채워 주는 필드(의존성 주입, ORM 매핑, 테스트 셋업)에서 흔하다. 이 관용구는 **"이 필드는 사용 시점에 널이 아님을 내가 보장한다"**는 선언이다. 보장이 깨지면 조용히 `NullReferenceException`이 난다.

> **💡 `null!` 대신 `required`를 먼저 검토하라 ※C# 11**
>
> 위 첫 번째 용도 중 상당수는 `required` 멤버(13.13절)로 더 안전하게 표현할 수 있다.
>
> ```csharp
> public required string ConnectionString { get; init; }
> ```
>
> `required`는 **객체 초기화자에서 값을 주지 않으면 컴파일 오류**를 낸다. `null!`이 "경고를 끄고 아무 보장도 하지 않는" 것과 정반대다. 객체 초기화자로 만들어지는 설정·모델 타입이라면 `null!`보다 `required`가 거의 항상 낫다.
>
> 의존성 주입 컨테이너가 생성자로 주입하는 경우라면 생성자 매개변수로 받아 `readonly` 필드에 넣으면 `null!` 자체가 필요 없어진다.

### 남용의 신호

| 패턴 | 진단 |
|---|---|
| `x!.Y!.Z!` — 체인 전체에 `!` | 흐름 분석을 통째로 무시하고 있다. 설계를 다시 보라 |
| `!`를 붙였다 뗐다 하며 경고만 없애기 | 널 가능성 결정을 미루고 있다 |
| 라이브러리 반환값마다 `!` | 그 라이브러리가 oblivious이거나 주석이 잘못되었다 |
| 프로덕션 코드에 `!`가 테스트 코드보다 많다 | 거의 확실히 잘못 쓰고 있다 |

> **💡 프로덕션 코드의 `!`에는 반드시 주석을 달아라**
>
> 프로덕션 코드에서 `!`를 써야 한다면 **왜 그런지 주석으로 남겨라.** 그리고 검색 가능한 형식을 쓰면 나중에 전부 찾아낼 수 있다.
>
> ```csharp
> // NULLABLEREF: LoadConfig()는 초기화 후 항상 비-널을 반환하지만
> //              시그니처로 표현할 방법이 없다. 초기화는 Program.Main에서 보장.
> var config = LoadConfig()!;
> ```
>
> `NULLABLEREF` 같은 태그를 쓰면 컴파일러나 도구가 개선된 뒤 전부 찾아 제거할 수 있다. `!`를 쓰는 것 자체가 틀린 것은 아니지만, **그것은 "내가 컴파일러보다 낫다"는 주장**이다. 그 주장을 근거 없이 코드에 남기지 마라.
>
> 테스트 코드에서는 훨씬 관대해도 된다. 테스트에서 `!`를 남발해 가정이 틀렸다면 결과는 `ArgumentNullException`이나 `NullReferenceException`으로 테스트가 실패하는 것이고, 그것으로 충분히 정보를 얻는다. **테스트 코드는 프로덕션 코드보다 덜 방어적이어도 된다.**

> **⚠️ `!`는 값 타입에는 의미가 없다**
>
> ```csharp
> int? n = null;
> int x = n!.Value;    // n!의 타입은 여전히 int? — InvalidOperationException은 그대로
> ```
>
> `!`는 널 가능 참조 타입의 흐름 분석 상태만 바꾼다. `int?`에 붙이면 타입도 바뀌지 않고 지울 경고도 없다. 널 가능 값 타입의 `Value` 접근은 런타임 검사가 실제로 존재하므로 `!`로 없앨 수 없다. **컴파일 타임 전용 기능으로 런타임 검사를 지울 수는 없다.** 이 대비가 두 기능의 차이를 다시 한번 보여 준다.

## 21.9 널 관련 특성 — `NotNullWhen`, `MaybeNull`, `MemberNotNull`

### 특성이 필요한 이유

21.6절에서 흐름 분석이 추적을 잃는 자리를 봤다. 그중 가장 아까운 것이 **헬퍼 메서드**다.

```csharp
string? a = GetInput();
if (!string.IsNullOrEmpty(a))
{
    Console.WriteLine(a.Length);   // 특성이 없다면 경고 CS8602
}
```

이 코드가 안전한 이유는 `string.IsNullOrEmpty`의 **의미** 때문이다. 반환값이 `false`면 입력이 널일 수 없다. 그런데 시그니처 `bool IsNullOrEmpty(string? value)`만 봐서는 그 관계를 알 수 없다.

같은 문제의 다른 사례가 둘 더 있다.

```csharp
if (dict.TryGetValue(key, out var value))
    Console.WriteLine(value.Length);      // 성공했으니 value는 널이 아니다

string? name = GetFileName(path);         // path가 널이 아니면 결과도 널이 아니다
```

이 관계들을 시그니처만으로 표현할 수 없다는 것이 C# 8 초기의 가장 큰 불만이었다. 해법은 **입력과 출력의 관계를 특성으로 기술하는 것**이다. C# 설계팀은 새로운 문법을 만드는 대신 20장에서 배운 특성을 쓰기로 했다. `System.Diagnostics.CodeAnalysis` 네임스페이스에 있다.

### 특성 전수표

| 특성 | 붙는 자리 | 뜻 |
|---|---|---|
| `[AllowNull]` | 입력 (매개변수·프로퍼티 setter) | 타입은 널 불가능이지만 널을 받아도 된다 |
| `[DisallowNull]` | 입력 | 타입은 널 가능이지만 널을 주면 안 된다 |
| `[MaybeNull]` | 출력 (반환값·`out`·프로퍼티 getter) | 타입은 널 불가능이지만 널이 나올 수 있다 |
| `[NotNull]` | 출력 | 타입은 널 가능이지만 널이 나오지 않는다 |
| `[MaybeNullWhen(bool)]` | `out` 매개변수 | 반환값이 지정한 `bool`일 때 널일 수 있다 |
| `[NotNullWhen(bool)]` | 매개변수 | 반환값이 지정한 `bool`일 때 이 인자는 널이 아니다 |
| `[NotNullIfNotNull(string)]` | 반환값·`out` | 지정한 매개변수가 널이 아니면 이것도 널이 아니다 |
| `[DoesNotReturn]` | 메서드 | 절대 정상 반환하지 않는다 |
| `[DoesNotReturnIf(bool)]` | `bool` 매개변수 | 그 인자가 지정한 값이면 반환하지 않는다 |
| `[MemberNotNull(...)]` | 메서드·프로퍼티 | 호출 후 지정한 멤버들이 널이 아니다 |
| `[MemberNotNullWhen(bool, ...)]` | 메서드·프로퍼티 | 반환값이 지정한 `bool`일 때 그 멤버들이 널이 아니다 |

앞의 넷은 **무조건적 사전/사후 조건**이고, 가운데 셋은 **조건부 사후 조건**이며, 뒤의 넷은 **제어 흐름과 멤버 상태**를 다룬다.

### `NotNullWhen` — 가장 많이 쓰는 특성

BCL의 `string.IsNullOrEmpty`는 실제로 이렇게 선언되어 있다.

```csharp
public static bool IsNullOrEmpty([NotNullWhen(false)] string? value);
```

"반환값이 `false`면 `value`는 널이 아니다." 이 한 줄로 앞의 문제가 해결된다.

```csharp
string? a = GetInput();
if (!string.IsNullOrEmpty(a))
    Console.WriteLine(a.Length);   // 경고 없음 — 컴파일러가 관계를 안다
```

직접 만드는 검증 헬퍼에도 똑같이 붙여야 한다.

```csharp
public static class Validation
{
    public static bool IsValid([NotNullWhen(true)] string? line)
        => line is { Length: > 0 } && line[0] != '#';
}

// 호출부
if (Validation.IsValid(input))
    Process(input);        // input이 string?이어도 경고 없음
```

**헬퍼 메서드에 특성을 다는 것이, 호출부마다 `!`를 붙이는 것보다 언제나 낫다.** 한 곳에 쓰면 모든 호출부가 혜택을 본다.

`TryXXX` 패턴에는 `out` 쪽에 `MaybeNullWhen` 또는 `NotNullWhen`을 쓴다.

```csharp
// BCL의 IDictionary<TKey,TValue>
bool TryGetValue(TKey key, [MaybeNullWhen(false)] out TValue value);

// 직접 만들 때
public static bool TryParse(string? text, [NotNullWhen(true)] out ApiVersion? version)
{
    // ...
}
```

두 특성의 차이는 대상 타입이다. `TValue`가 널 불가능으로 선언된 제네릭 매개변수라면 "실패 시에는 널일 수 있다"고 완화해야 하니 `MaybeNullWhen(false)`이고, `ApiVersion?`처럼 이미 널 가능이라면 "성공 시에는 널이 아니다"라고 좁혀야 하니 `NotNullWhen(true)`다. **완화인지 강화인지에 따라 쓰는 특성이 다르다.**

> **⚠️ 특성은 컴파일러에게 하는 약속이지 검증이 아니다**
>
> `[NotNullWhen(true)]`를 붙였는데 실제로는 `true`를 반환하면서 널을 남길 수도 있다. 컴파일러는 메서드 본문이 그 약속을 지키는지 **부분적으로만** 검사한다. 특성으로 거짓말하면 호출부의 흐름 분석이 통째로 오염되고, 경고 하나 없이 `NullReferenceException`이 난다.
>
> 널 관련 특성은 `!` 연산자를 **한 곳에 모아 둔 것**에 가깝다. `!`는 호출부마다 책임을 지지만, 특성은 선언부에서 한 번 책임을 지고 모든 호출부가 그것을 믿는다. 책임의 무게가 더 크다.

### `NotNullIfNotNull` — 입력이 널이 아니면 출력도 널이 아니다

"통과시키는" 종류의 메서드에 쓴다.

```csharp
[return: NotNullIfNotNull(nameof(path))]
public static string? GetFileName(string? path)
{
    if (path is null) return null;
    // ...
}

string? maybe = GetFileName(input);        // input이 string?이면 결과도 string?
string definitely = GetFileName("a/b.txt"); // 리터럴은 널이 아니므로 결과도 널 아님, 경고 없음
```

`nameof`를 쓰는 것이 중요하다(13.15절). 문자열을 직접 쓰면 매개변수 이름을 바꿀 때 조용히 깨진다.

BCL에서는 `Path.GetDirectoryName`, `Convert.ToString` 같은 메서드가 이 특성을 쓴다.

### `MemberNotNull` — 초기화 헬퍼의 약속

`CS8618`(널 불가능 필드가 생성자에서 초기화되지 않음)은 실무에서 매우 자주 만나는 경고다. 초기화 로직을 별도 메서드로 뺐을 때 특히 그렇다.

```csharp
public class Connection
{
    private string _host;      // CS8618 — 생성자가 초기화하지 않는 것처럼 보인다
    private int _port;

    public Connection(string config) => Parse(config);

    [MemberNotNull(nameof(_host))]
    private void Parse(string config)
    {
        var parts = config.Split(':');
        _host = parts[0];
        _port = int.Parse(parts[1]);
    }
}
```

`[MemberNotNull(nameof(_host))]`가 "이 메서드가 정상 반환하면 `_host`는 널이 아니다"라고 선언한다. 생성자가 `Parse`를 호출하므로 컴파일러가 `CS8618`을 거둔다.

`Reset()` 메서드를 여러 생성자가 공유하는 패턴, 지연 초기화 패턴에서 필수적이다. 여러 멤버를 한 번에 지정할 수 있다.

```csharp
[MemberNotNull(nameof(_host), nameof(_scheme), nameof(_query))]
private void Initialize() { /* ... */ }
```

조건부 버전도 있다.

```csharp
public class Cache
{
    private byte[]? _buffer;

    [MemberNotNullWhen(true, nameof(_buffer))]
    public bool IsLoaded => _buffer is not null;

    public int Size()
    {
        if (!IsLoaded) return 0;
        return _buffer.Length;   // 경고 없음 — IsLoaded가 true면 _buffer는 널이 아니다
    }
}
```

`IsLoaded` 프로퍼티가 `true`일 때 `_buffer`가 널이 아니라는 것을 컴파일러가 이해한다. **이 특성 없이는 `_buffer!.Length`를 쓸 수밖에 없다.**

### `DoesNotReturn` — 흐름 분석에게 "여기서 끝"이라고 알린다

절대 정상 반환하지 않는 메서드에 붙인다.

```csharp
[DoesNotReturn]
private static void ThrowInvalid(string message)
    => throw new InvalidOperationException(message);

string? Get(string? key)
{
    if (key is null) ThrowInvalid("key required");
    return key.Trim();      // 경고 없음 — 여기 도달했으면 key는 널이 아니다
}
```

이 특성이 없으면 컴파일러는 `ThrowInvalid`가 반환한다고 가정하고 `key.Trim()`에서 경고를 낸다. `throw` 헬퍼를 쓰는 코드베이스에서는 필수다.

조건부 버전이 `[DoesNotReturnIf(bool)]`이다. BCL의 `Debug.Assert`가 이것을 쓴다.

```csharp
public static void Assert([DoesNotReturnIf(false)] bool condition);
```

```csharp
string? s = GetValue();
Debug.Assert(s is not null);
Console.WriteLine(s.Length);   // 경고 없음
```

> **⚠️ `Debug.Assert`는 Release 빌드에서 사라진다**
>
> `Debug.Assert`는 `[Conditional("DEBUG")]`가 붙어 있어(20.10절) Release 빌드에서는 호출 자체가 제거된다. 그런데 **널 가능성 흐름 분석은 Release 빌드에서도 그대로 적용된다.** 즉 Release에서는 검사가 없는데도 컴파일러는 널이 아니라고 믿는다.
>
> 이것은 설계된 동작이지만 함정이기도 하다. `Debug.Assert`로 널 경고를 끄는 것은 **`!`를 쓰는 것과 실질적으로 같다.** 진짜 검증이 필요하면 `ArgumentNullException.ThrowIfNull`(21.10절)처럼 항상 실행되는 것을 써라.

### `AllowNull` / `DisallowNull` — 읽기와 쓰기의 널 가능성이 다를 때

프로퍼티에서 setter는 널을 받아도 되지만 getter는 절대 널을 반환하지 않는 패턴이 있다.

```csharp
private string _name = "(none)";

[AllowNull]
public string Name
{
    get => _name;                        // 절대 널이 아니다
    set => _name = value ?? "(none)";    // 널을 받아도 된다
}

obj.Name = null;                         // 경고 없음 — AllowNull 덕분
Console.WriteLine(obj.Name.Length);      // 경고 없음 — 타입이 string이므로
```

`[DisallowNull]`은 반대다. 타입은 `string?`(아직 설정 안 됐으면 널)이지만 널을 대입해서는 안 되는 프로퍼티에 쓴다.

> **📌 `netstandard2.0`이나 .NET Framework를 대상으로 해도 쓸 수 있다**
>
> 이 특성들은 .NET Core 3.0부터 BCL에 들어 있다. 그 이전 대상 프레임워크에서는 존재하지 않지만, **컴파일러는 특성을 이름(전체 네임스페이스 포함)으로 인식하므로 직접 선언해도 동작한다.**
>
> ```csharp
> namespace System.Diagnostics.CodeAnalysis
> {
>     [AttributeUsage(AttributeTargets.Parameter, AllowMultiple = false)]
>     internal sealed class NotNullWhenAttribute : Attribute
>     {
>         public NotNullWhenAttribute(bool returnValue) => ReturnValue = returnValue;
>         public bool ReturnValue { get; }
>     }
> }
> ```
>
> `internal`로 선언해도 자신의 어셈블리 안에서는 완전히 동작한다. 다중 대상(multi-targeting) 라이브러리가 흔히 쓰는 기법이다. `NullableAttribute`를 컴파일러가 스스로 만들어 넣는 것(21.6절)과 같은 원리다.

> **💡 특성은 공개 API 표면부터 달아라**
>
> 널 관련 특성을 전부 외워서 모든 메서드에 다는 것은 과하다. 우선순위는 이렇다.
>
> 1. **`bool`을 반환하는 검증·시도 메서드** — `NotNullWhen` / `MaybeNullWhen`. 여기가 투자 대비 효과가 가장 크다
> 2. **`throw` 헬퍼** — `DoesNotReturn`. 안 달면 온 코드베이스에 경고가 번진다
> 3. **초기화 헬퍼** — `MemberNotNull`. `CS8618`을 정직하게 없애는 유일한 방법
> 4. 나머지는 실제로 경고가 났을 때 대응하면 된다
>
> 이 셋만 달아도 `!` 사용량이 극적으로 줄어든다.

## 21.10 널 검사 관용구 — `ArgumentNullException.ThrowIfNull`

### 검사 방법 세 가지와 그 차이

널인지 확인하는 방법은 셋이다.

```csharp
if (x != null)        { }   // 동등 연산자
if (!(x is null))     { }   // is + ! ※C# 7
if (x is not null)    { }   // is not ※C# 9
```

셋은 같아 보이지만 **`!=`만 다르다.** `!=`는 오버로딩할 수 있는 연산자이기 때문이다(22장). 어떤 타입이 `!=`를 이상하게 구현해 두었다면 `x != null`이 예상과 다르게 동작하거나, 사용자 코드가 실행되어 예외를 던질 수도 있다. 반면 `is null`과 `is not null` 패턴은 **오버로딩된 연산자를 절대 호출하지 않고** 언제나 참조 동등성(또는 널 가능 값 타입의 `HasValue`)만 본다. 그래서 **널 검사의 유일하게 보장된 방법은 패턴 매칭이다.**

| 방법 | 사용자 연산자 호출 | 널 가능 값 타입 | 권장 |
|---|---|---|---|
| `x != null` | 있을 수 있음 | `HasValue`로 리프팅 | 조건부 |
| `!(x is null)` | 없음 | `HasValue` | 좋음 |
| `x is not null` | 없음 | `HasValue` | **가장 명확** |

관성적으로 `!=`를 쓰는 개발자가 여전히 많고 대부분의 경우 문제가 없지만, 남이 정의한 타입을 다루는 일반화된 코드(제네릭 유틸리티, 프레임워크 내부)에서는 반드시 패턴을 써라.

### 인자 검증의 진화

인자가 널인지 검사해서 `ArgumentNullException`을 던지는 것은 공개 API의 기본이다. 예전에는 이렇게 썼다.

```csharp
public void Hire(Person manager, Person employee)
{
    if (manager is null)
        throw new ArgumentNullException(paramName: nameof(manager));
    if (employee is null)
        throw new ArgumentNullException(paramName: nameof(employee));
    // ...
}
```

검사만 네 줄이다. `throw` 식(※C# 7)을 쓰면 줄어들지만 여전히 반복이다.

```csharp
_manager = manager ?? throw new ArgumentNullException(nameof(manager));
```

.NET 6이 이 상용구를 없앤 정적 메서드를 추가했다 ※.NET 6.

```csharp
public void Hire(Person manager, Person employee)
{
    ArgumentNullException.ThrowIfNull(manager);
    ArgumentNullException.ThrowIfNull(employee);
    // ...
}
```

**매개변수 이름을 쓰지 않았는데도 예외의 `ParamName`이 정확히 `"manager"`가 된다.** 시그니처를 보면 이유를 알 수 있다.

```csharp
public static void ThrowIfNull(
    [NotNull] object? argument,
    [CallerArgumentExpression(nameof(argument))] string? paramName = null);
```

두 특성이 함께 일한다.

- `[CallerArgumentExpression]`(20.11절)이 **호출부에 쓰인 식의 소스 텍스트**를 컴파일 타임에 문자열로 채워 넣는다.
- `[NotNull]`(21.9절)이 "이 메서드가 정상 반환하면 인자는 널이 아니다"를 흐름 분석에 알린다.

두 번째 덕분에 다음 코드가 경고 없이 컴파일된다.

```csharp
public int Length(string? text)
{
    ArgumentNullException.ThrowIfNull(text);
    return text.Length;      // 경고 없음 — NotNull 덕분
}
```

**널 검사와 흐름 분석 갱신이 한 줄에서 동시에 일어난다.** `!`도, `if`도 필요 없다.

### 같은 계열의 다른 메서드

| 메서드 | 도입 | 검사 대상 | 던지는 예외 |
|---|---|---|---|
| `ArgumentNullException.ThrowIfNull(object?)` | .NET 6 | 널 | `ArgumentNullException` |
| `ArgumentException.ThrowIfNullOrEmpty(string?)` | .NET 7 | 널 또는 빈 문자열 | 널이면 `ArgumentNullException`, 비면 `ArgumentException` |
| `ObjectDisposedException.ThrowIf(bool, object)` | .NET 7 | 조건 | `ObjectDisposedException` |
| `ArgumentException.ThrowIfNullOrWhiteSpace(string?)` | .NET 8 | 널·빈 문자열·공백 | 위와 동일 |
| `ArgumentOutOfRangeException.ThrowIfNegative(T)` 등 | .NET 8 | 범위 | `ArgumentOutOfRangeException` |

> **⚠️ `ThrowIfNullOrEmpty`가 던지는 예외 타입은 상황에 따라 다르다**
>
> `ArgumentException.ThrowIfNullOrEmpty`는 클래스 이름이 `ArgumentException`이지만, **인자가 널이면 `ArgumentNullException`을, 빈 문자열이면 `ArgumentException`을 던진다.** `ArgumentNullException`이 `ArgumentException`에서 파생하므로 `catch (ArgumentException)`은 둘 다 잡지만, 예외 타입으로 원인을 구별하는 테스트를 쓸 때는 이 차이를 알아야 한다.

### 성능 — 던지지 않을 때는 거의 공짜다

```csharp
ArgumentNullException.ThrowIfNull(argument);
```

이 메서드는 널 검사만 하고 즉시 반환하는 작은 메서드이며, 예외 생성 부분은 별도 메서드로 분리되어 있다. **던지지 않는 경로에는 예외 객체 생성이 전혀 없고**, 본체가 작아 JIT이 인라인하기에도 유리하다. 직접 쓴 `if` + `throw`가 인라인을 방해할 수 있는 것과 대조된다. 뜨거운 경로의 공개 메서드에서도 부담 없이 쓸 수 있다.

> **📌 매개변수 널 검사 문법은 제안되었다가 철회되었다**
>
> C# 11 프리뷰에는 매개변수 이름 뒤에 `!!`를 붙이면 컴파일러가 널 검사 코드를 자동 생성하는 기능이 들어 있었다.
>
> ```csharp
> public void Hire(Person manager!!, Person employee!!) { }
> ```
>
> .NET 팀은 이 기능으로 자사 라이브러리에서 1만 줄 이상을 줄였다고 발표했지만, 커뮤니티 반응은 갈렸다. 두 글자 기호보다 특성이 낫다는 의견이 많았다. 결국 **정식 릴리스 전에 제거되었고, 오늘날 널 검사는 손으로 써야 한다.**
>
> 이 일화 자체는 사소하지만 시사점이 있다. **NRT를 도입하고도 런타임 널 검사가 여전히 필요하다는 사실이, 언어 팀이 전용 문법을 검토할 만큼 명백했다는 뜻이다.** "NRT를 켰으니 인자 검증은 필요 없다"는 판단은 언어 설계자들의 판단과 정반대다.

## 21.11 널 가능 타입의 대안 — 결과 타입, 특수 값

### 널 가능 값 타입이 잘 맞는 자리

먼저 정당한 용례부터 확인하자.

**첫째, 데이터베이스 컬럼 매핑.** 가장 흔하고 가장 정당하다. SQL의 대부분의 컬럼 타입이 CLR 구조체로 매핑되므로, 널 허용 컬럼을 표현하려면 널 가능 값 타입이 필요하다.

```csharp
// 데이터베이스의 Customer 테이블에 매핑된다
public class Customer
{
    // ...
    public decimal? AccountBalance;
}
```

문자열 컬럼(`EmailAddress` 등)은 CLR에서 이미 참조 타입이라 문제가 없다. 숫자·날짜·불리언 컬럼이 문제였고, 널 가능 값 타입이 그것을 해결한다.

**둘째, 앰비언트 프로퍼티(ambient property)의 백킹 필드.** 값이 없으면 부모의 값을 쓰는 프로퍼티다.

```csharp
public class Row
{
    // ...
    Grid parent;
    Color? color;

    public Color Color
    {
        get { return color ?? parent.Color; }
        set { color = value == parent.Color ? (Color?)null : value; }
    }
}
```

`color`가 널이면 "직접 지정하지 않음"을 뜻하고 부모 값이 쓰인다. setter는 부모와 같은 값을 넣으면 오히려 널로 되돌려 상속 관계를 유지한다. UI 프레임워크의 스타일 상속이 이 패턴을 쓴다.

### 대안 1 — 특수 값(매직 값)

널 가능 값 타입이 없던 C# 1.0 시절에는 **특정 값 하나를 "널"로 지정**했다. 이 방식은 지금도 BCL에 남아 있다.

```csharp
int i = "Pink".IndexOf('b');
Console.WriteLine(i);        // -1 — "못 찾았음"을 뜻하는 매직 값
```

그런데 `Array.IndexOf`는 미묘하게 다르다. **하한이 0인 배열에서만 `-1`을 반환한다.** 일반 규칙은 "배열의 하한보다 1 작은 값"이다.

```csharp
// 하한이 0이 아니라 1인 배열을 만든다
Array a = Array.CreateInstance(typeof(string), new int[] {2}, new int[] {1});
a.SetValue("a", 1);
a.SetValue("b", 2);
Console.WriteLine(Array.IndexOf(a, "c"));   // 0 — "못 찾았음"인데 0이다!
```

`0`이 "못 찾았음"을 뜻한다. `if (index >= 0)`로 검사하는 관용적 코드가 이 배열에서는 조용히 틀린다.

매직 값의 문제는 넷이다.

- **표현이 타입마다 다르다.** 널 가능 값 타입은 모든 값 타입에 하나의 공통 패턴을 준다.
- **적절한 값이 없을 수 있다.** 잔액에는 `-1`도 `0`도 유효한 값이다.
- **검사를 잊으면 조용히 틀린다.** 반면 `HasValue`를 잊으면 그 자리에서 `InvalidOperationException`이 난다.
- **타입이 의도를 표현하지 못한다.** 널 가능성이 시그니처에 드러나지 않아 컴파일러가 도와줄 수 없다.

네 번째가 핵심이다. **타입은 프로그램의 의도를 전달하고, 컴파일러가 정확성을 검사하게 하며, 일관된 규칙 집합을 강제한다.** 매직 값은 이 셋 중 아무것도 하지 못한다.

> **⚠️ 부동소수점의 `NaN`은 매직 값이지만 성질이 다르다**
>
> `double.NaN`을 "값 없음"으로 쓰는 코드가 있다. 매직 값이지만 특별한 성질이 하나 있다. **`NaN`은 자기 자신과도 같지 않다**(7.6절). 그래서 `if (x == double.NaN)`은 절대 참이 되지 않고, `double.IsNaN(x)`를 써야 한다.
>
> 이 성질은 21.4절에서 본 널 가능 비교 연산자의 성질과 비슷하다. `NaN`이 끼면 `<`, `>`, `==`가 전부 `false`가 되는 것도 같다. 하지만 `NaN`은 널 가능성을 시그니처에 드러내지 못하므로 여전히 열등한 선택이다. 성능이 극도로 중요한 수치 코드에서 `double?` 대신 쓰는 것 외에는 권하기 어렵다.

### 대안 2 — 별도 플래그

값과 "값이 있는가"를 별도 변수로 두는 방식이다. 이것이 `Nullable<T>`가 내부적으로 하는 일과 정확히 같다는 점에 주목하라.

객체 하나에 `decimal _balance`와 `bool _hasBalance`를 따로 두는 것은 `decimal?` 하나보다 나을 것이 없다. **가치가 있는 것은 대량 데이터에서 플래그를 압축할 수 있을 때다.**

```csharp
double?[] values = new double?[1_000_000];   // 16MB (요소당 16바이트)
// 대안: 값 배열 + 비트마스크
double[] data = new double[1_000_000];       // 8MB
ulong[] present = new ulong[1_000_000 / 64]; // 0.125MB — 요소당 1비트
```

16MB가 8.125MB로 줄고, 값 배열은 연속적인 `double` 배열이라 SIMD 연산과 캐시 지역성 모두 유리하다. 대가는 두 배열의 동기화를 직접 책임지는 것이다. 위 수치는 요소당 바이트 수로부터 계산한 예시이며, 실제 이득은 접근 패턴에 따라 달라진다.

**신호 처리, 시계열 분석, 과학 계산처럼 "널이 드물고 데이터가 거대한" 경우에만 이 트레이드오프가 성립한다.** 일반 업무 코드에서는 `T?`가 정답이다.

### 대안 3 — `Try` 패턴

"값이 있을 수도 없을 수도 있다"를 반환값 하나가 아니라 `bool` + `out`으로 표현한다.

```csharp
if (int.TryParse(text, out int value))
    Use(value);
```

널 가능 값 타입으로도 같은 것을 표현할 수 있다.

```csharp
int? TryParseOrNull(string text)
    => int.TryParse(text, out int v) ? v : null;
```

| 기준 | `Try` 패턴 | `T?` 반환 |
|---|---|---|
| 식(expression)에서 쓰기 | 어렵다 — 문이 필요 | 쉽다 — `?? `, `?.`와 조합 |
| 실패 이유 전달 | `out`을 더 붙여 확장 가능 | 불가능 |
| 성능 | 박싱·래핑 없음 | `Nullable<T>` 래핑 |
| 참조 타입에도 적용 | 그대로 됨 | 주석일 뿐 강제 없음 |
| 연쇄(chaining) | 나쁘다 | 좋다 |

BCL은 대부분 `Try` 패턴을 쓴다. 성능과 참조 타입 대응 때문이다. 자세한 설계 지침은 32.9절에 있다.

### 대안 4 — 결과 타입 (`Option` / `Result`)

함수형 언어에서 온 접근이다. "값 또는 없음"을 별도 타입으로 만든다.

```csharp
public readonly struct Option<T>
{
    private readonly T _value;
    public bool HasValue { get; }
    private Option(T value) { _value = value; HasValue = true; }
    public static Option<T> Some(T value) => new(value);
    public static Option<T> None => default;
    public TResult Match<TResult>(Func<T, TResult> some, Func<TResult> none)
        => HasValue ? some(_value) : none();
}
```

`Nullable<T>`와 구조가 같지만 결정적 차이가 셋 있다.

- **`T`에 `struct` 제약이 없다.** 참조 타입에도 쓸 수 있다.
- **`Match`를 통해서만 값을 꺼내게 만들 수 있다.** 널 검사를 잊는 것이 구조적으로 불가능해진다.
- **실패 이유를 담도록 확장할 수 있다.** `Result<T, TError>`가 그것이다.

```csharp
Result<Order, string> result = LoadOrder(id);
string message = result.Match(ok: order => $"주문 {order.Id}", error: err => $"실패: {err}");
```

> **💡 결과 타입은 도입 비용을 반드시 계산하고 써라**
>
> `Option<T>`/`Result<T,E>`는 강력하지만 C#에서는 세 가지 비용이 붙는다.
>
> 1. **생태계 비호환.** BCL·EF Core·ASP.NET Core는 전부 널과 예외를 쓴다. 경계마다 변환 계층이 필요하다.
> 2. **패턴 매칭 지원 부족.** C#에는 `match` 식이 없어 `Match` 메서드로 흉내 내야 하고, 람다 할당이 붙는다.
> 3. **팀 학습 비용.** 익숙하지 않은 팀에서는 `?.`과 `??`보다 읽기 어렵다.
>
> **도메인 로직의 핵심부처럼 실패 경로가 정말 중요한 곳에 국소적으로 도입하고, 공개 API 경계에서는 널과 예외로 되돌리는 것**이 현실적이다. 코드베이스 전체를 결과 타입으로 바꾸는 시도는 대개 절반쯤에서 멈추고, 두 스타일이 섞인 최악의 상태로 남는다.

### 대안 5 — 널 객체 패턴과 빈 값

"값 없음"을 널이 아니라 **무해한 실제 객체**로 표현한다.

```csharp
// 널 대신 빈 컬렉션
public IReadOnlyList<Order> GetOrders(int id)
    => _cache.TryGetValue(id, out var list) ? list : Array.Empty<Order>();

// 널 대신 무동작 구현
public sealed class NullLogger : ILogger
{
    public static readonly NullLogger Instance = new();
    public void Log(string message) { }
}
```

호출부에서 널 검사가 통째로 사라진다. **컬렉션 반환에서는 이것이 거의 항상 정답이다.** 빈 컬렉션과 널을 구별해야 하는 도메인은 드물고, `Array.Empty<T>()`는 할당조차 하지 않는다.

`ILogger`, `IProgress<T>` 같은 선택적 협력자에도 잘 맞는다. BCL의 `NullLogger`, `Stream.Null`, `TextWriter.Null`이 실제 예다.

### 선택 가이드

| 상황 | 권장 |
|---|---|
| DB 널 허용 컬럼 매핑 | `T?` (널 가능 값 타입) |
| "아직 설정 안 됨" 상태의 값 타입 | `T?` |
| 참조 타입 매개변수·반환값 | NRT 주석 + 런타임 검증 |
| 컬렉션 반환 | 빈 컬렉션 (`Array.Empty<T>()`) |
| 선택적 협력자 객체 | 널 객체 패턴 |
| 파싱·조회 실패 | `Try` 패턴 |
| 실패 이유를 전달해야 함 | `Result<T,E>` 또는 예외 |
| 세 가지 이상의 상태 | `enum` |
| 대량 수치 데이터의 결측치 | 값 배열 + 비트마스크 |

> **💡 널을 줄이는 가장 효과적인 방법은 널을 만들지 않는 것이다**
>
> 이 장의 도구를 전부 동원해도, 널이 이미 코드베이스 곳곳에서 만들어지고 있다면 검사 지점만 늘어난다. 근본 대책은 **널이 생성되는 지점을 줄이는 것**이다.
>
> - 생성자에서 모든 필수 필드를 채운다. 부분적으로 초기화된 객체를 만들지 않는다(13.4절).
> - `required` 멤버(13.13절)로 초기화를 강제한다.
> - 불변 타입과 레코드(19장)를 쓴다. 나중에 널이 되는 일이 없어진다.
> - 컬렉션 프로퍼티는 생성 시점에 빈 컬렉션으로 초기화한다.
>
> 이렇게 만든 타입은 NRT 경고가 거의 나지 않는다. **경고가 많이 난다는 것은 그 자체로 설계 신호다.** 경고를 억누르기 전에 그 타입이 왜 부분적으로 초기화된 상태를 허용하는지 먼저 물어라.

## 이 장의 요약

- **`T?`는 두 개의 서로 다른 기능이 공유하는 하나의 기호다.** 값 타입에 붙으면 `Nullable<T>`라는 실재하는 구조체가 되고, 참조 타입에 붙으면 CLR이 전혀 모르는 컴파일러 주석이 된다. 이 비대칭을 모르면 반드시 사고가 난다.
- **`Nullable<T>`는 필드 두 개짜리 구조체다.** `hasValue` 플래그와 `value` 값이 전부다. `x == null`은 참조 비교가 아니라 `!x.HasValue` 검사로 컴파일된다.
- **CLR은 널 가능 값 타입에 세 가지 특별 지원을 한다.** 박싱하면 `Nullable<T>`가 아니라 `T`가 박싱되고 널이면 널 참조가 되며, `GetType()`은 `T`를 반환하고, `T`의 인터페이스로 캐스팅할 수 있다. 그 대가로 `null`인 값에 `GetType()`을 부르면 `NullReferenceException`이 난다.
- **연산자 리프팅에는 세 가지 규칙이 있고 서로 다르다.** 산술·비트 연산자는 널을 전파하고, 동등 연산자는 널끼리 같다고 보며, 비교 연산자는 널이 끼면 무조건 `false`다. 그래서 `!(a < b)`와 `a >= b`가 같지 않다.
- **`bool?`의 `&`와 `|`만 3값 논리를 쓴다.** `null | true`는 `true`이고 `null & false`는 `false`다. 반면 `&&`와 `||`는 `bool?`에 아예 쓸 수 없다.
- **널 가능 참조 타입은 컴파일 타임 전용이다.** 런타임에 `string`과 `string?`은 같은 타입이고, IL도 같으며, 아무것도 강제되지 않는다. 널 가능성은 `NullableAttribute`와 `NullableContextAttribute`가 담은 바이트일 뿐이다.
- **컴파일러는 널 상태를 흐름 분석으로 추적하지만 완전하지 않다.** 배열 요소, 헬퍼 메서드의 반환값, 다른 스레드, 리플렉션에서 추적을 잃는다. 이 한계는 버그가 아니라 의도된 절충이다.
- **`!`는 널 검사가 아니라 경고 억제다.** 정당한 자리는 테스트 코드와, 컴파일러가 이해하지 못하는 관계를 내가 아는 좁은 경우뿐이다. 후자의 올바른 해법은 대개 `!`가 아니라 헬퍼 메서드에 널 관련 특성을 붙이는 것이다.
- **널 관련 특성은 입력과 출력의 관계를 시그니처에 새긴다.** `NotNullWhen`, `MemberNotNull`, `DoesNotReturn` 셋만 제대로 달아도 `!` 사용량이 극적으로 줄어든다.
- **NRT를 켜도 런타임 인자 검증은 계속 필요하다.** `ArgumentNullException.ThrowIfNull`이 `CallerArgumentExpression`과 `NotNull`을 결합해 한 줄로 검사와 흐름 분석 갱신을 동시에 처리한다.
- **널이 최선인 경우는 생각보다 적다.** 컬렉션은 빈 컬렉션으로, 선택적 협력자는 널 객체로, 실패는 `Try` 패턴이나 결과 타입으로 표현하는 편이 낫다. 가장 효과적인 대책은 널이 만들어지는 지점 자체를 줄이는 것이다.

## 연습 문제

1. `int?`, `long?`, `byte?`, `(double, double)?`의 크기를 `Unsafe.SizeOf<T>()`(또는 `sizeof` in unsafe 문맥)로 측정하고, 각각이 밑바탕 타입 크기 + `bool` + 정렬 패딩과 어떻게 대응하는지 표로 정리하라. `Point?`(`double` 두 개)에서 몇 퍼센트가 늘었는가.

2. `int? x = null;`을 만들고 `x.HasValue`, `x.Value`, `x.GetValueOrDefault()`, `x.ToString()`, `x.Equals(null)`, `x.GetHashCode()`, `x.GetType()`을 차례로 호출하는 프로그램을 작성해 각각이 무엇을 반환하거나 어떤 예외를 던지는지 확인하라. 왜 `GetType()`만 다른지 21.3절의 설명으로 자신에게 설명해 보라.

3. `int? a = null; int? b = 5;`로 두고 `a < b`, `a > b`, `a <= b`, `a >= b`, `a == b`, `a != b`, `!(a < b)` 일곱 개를 모두 출력하라. 삼분법이 깨지는 조합을 찾아 표로 정리하라.

4. `bool?` 세 값(`null`, `true`, `false`)의 모든 조합에 대해 `&`, `|`, `^` 결과를 출력하는 이중 루프를 작성하고, 21.5절의 진리표와 대조하라. `^`가 3값 논리 예외에 포함되지 않는 이유를 설명하라.

5. `int? Add(int? a, int? b) => a + b;`를 컴파일한 뒤 `ildasm` 또는 온라인 IL 뷰어로 IL을 확인하라. `get_HasValue`, `GetValueOrDefault`, `initobj`, `newobj`가 각각 어디에 나타나는지 표시하고, 같은 일을 하는 `int Add(int a, int b) => a + b;`의 IL 길이와 비교하라.

6. NRT를 켠 콘솔 프로젝트에서 `var s = new string[3]; Console.WriteLine(s[0].Length);`를 작성하라. 경고가 나는가. 실행하면 어떻게 되는가. 이 결과로부터 흐름 분석의 한계를 한 문장으로 요약하라.

7. `static bool IsUsable(string? s)`를 만들어 널·빈 문자열이 아닐 때 `true`를 반환하게 하고, 호출부에서 `if (IsUsable(x)) Console.WriteLine(x.Length);`를 써 보라. 경고를 `!` 없이 없애려면 무엇을 해야 하는가. 특성을 붙인 전후의 경고를 비교하라.

8. `ArgumentNullException.ThrowIfNull`을 쓰는 메서드에 `null`을 넘겨 예외의 `ParamName`을 확인하고, 인자로 `obj.Property`처럼 복합 식을 넘기면 `ParamName`이 무엇이 되는지도 확인하라.
