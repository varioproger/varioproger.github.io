# 23장. 제네릭

> **이 장의 위치** — Part IV「제네릭과 컬렉션」의 첫 장이다. 15장에서 박싱의 비용을 재고, 18장에서 인터페이스로 계약을 표현하고, 22장에서 `INumber<T>` 제약을 미리 빌려 썼다. 그 모든 자리에서 미룬 질문 — "타입 매개변수는 정확히 무엇이고, CLR은 그것을 어떻게 구현하는가" — 을 여기서 끝낸다. 제네릭은 문법 설탕이 아니다. CLR 2.0이 메타데이터 테이블과 IL 명령과 JIT을 통째로 고쳐서 만든 **런타임 기능**이고, 그 사실이 성능·코드 크기·타입 동일성 전부를 결정한다.
>
> **선수 지식** — 14장(상속과 다형성), 15장(`object` 타입과 박싱), 16장(구조체와 값 타입), 18장(인터페이스)
>
> **이 장에서 다루지 않는 것** — `List<T>`·`Dictionary<TKey,TValue>` 같은 제네릭 컬렉션의 내부 구조는 24장에서, `INumber<T>` 계열의 제네릭 수학은 22.8절에서 이미 다뤘다. 제네릭 타입을 리플렉션으로 조작하는 방법은 57.4절이다. 배열 공변성 자체는 9.6절에 있고, 이 장에서는 제네릭 변성과 **대조**하는 용도로만 언급한다.

## 23.1 제네릭이 존재하는 이유 — `ArrayList`와 박싱의 시대

### 코드 재사용의 두 갈래

C#에는 여러 타입에 걸쳐 재사용 가능한 코드를 쓰는 메커니즘이 두 개 있다. **상속**과 **제네릭**이다.

상속은 재사용성을 **기반 타입**으로 표현한다. "이 알고리즘은 `Shape`에 대해 동작한다"고 쓰면 `Circle`과 `Square`가 그 알고리즘을 공유한다. 제네릭은 재사용성을 **자리표시자(placeholder) 타입을 담은 템플릿**으로 표현한다. "이 알고리즘은 `T`에 대해 동작한다"고 쓰면 `T` 자리에 무엇이 들어와도 동작한다.

둘의 차이는 무엇을 잃느냐에 있다. 상속으로 일반화하면 **타입 정보를 잃는다**. 제네릭으로 일반화하면 잃지 않는다. 이 한 문장이 이 장 전체의 요약이다.

한 가지 표현을 더 얹으면, 상속이 제공하는 것이 **구현 재사용**이라면 제네릭이 제공하는 것은 **알고리즘 재사용**이다. 정렬·검색·교환·비교·변환 — 이런 알고리즘을 만드는 개발자는 자기 알고리즘이 어떤 데이터 타입 위에서 돌아갈지 지정하지 않는다. 그것을 정하는 일은 알고리즘을 쓰는 다른 개발자의 몫이다.

### 제네릭이 없던 시절 — 세 가지 선택지, 세 가지 불행

정수를 담는 스택이 필요한데 제네릭이 없다고 하자. 선택지는 셋이다.

**선택지 1 — 타입마다 클래스를 하나씩 만든다.**

```csharp
public class IntStack    { /* int[]    data; ... */ }
public class StringStack { /* string[] data; ... */ }
public class PersonStack { /* Person[] data; ... */ }
```

타입 안전하고 빠르다. 그리고 유지보수가 지옥이다. 버그 하나를 고치려면 N개의 파일을 고쳐야 한다.

**선택지 2 — `object`로 일반화한다.**

```csharp
public class ObjectStack
{
    int position;
    object[] data = new object[10];
    public void Push (object obj) => data[position++] = obj;
    public object Pop()           => data[--position];
}
```

한 번만 쓰면 되고 모든 타입에 동작한다. 그런데 이렇게 된다.

```csharp
// 정수만 담고 싶은 스택이라고 치자
ObjectStack stack = new ObjectStack();

stack.Push ("s");             // 타입이 틀렸는데 오류가 없다
int i = (int) stack.Pop();    // 다운캐스트 - 런타임 오류
```

컴파일러는 아무 말도 하지 않는다. `InvalidCastException`은 몇 시간 뒤 프로덕션에서 터진다.

**선택지 3 — 강타입 래퍼를 손으로 만든다.**

`ArrayList`를 private 필드로 감싸고 `Person`만 받는 메서드를 노출한다.

```csharp
using System.Collections;

public class PersonCollection : IEnumerable
{
    private ArrayList arPeople = new ArrayList();

    public Person GetPerson(int pos) => (Person) arPeople[pos];   // 호출자 대신 캐스트
    public void AddPerson(Person p)  => arPeople.Add(p);          // Person만 삽입
    public int Count                 => arPeople.Count;

    IEnumerator IEnumerable.GetEnumerator() => arPeople.GetEnumerator();
}
```

이제 타입 안전은 확보했다. 하지만 담고 싶은 타입마다 거의 똑같은 클래스를 또 만들어야 한다. `CarCollection`, `OrderCollection`, `InvoiceCollection`... 선택지 1로 되돌아온 셈이다. 게다가 **박싱 문제는 하나도 해결되지 않았다.** `IntCollection`을 만들어 `int`만 받게 해도, 내부 저장소가 `ArrayList`인 이상 `AddInt`는 박싱하고 `GetInt`는 언박싱한다. 정수를 담을 컨테이너를 무엇으로 고르든 — `System.Array`든 `ArrayList`든 — 비제네릭 컨테이너를 쓰는 한 박싱에서 벗어날 수 없다.

### 박싱이 정확히 얼마나 비싼가

`ArrayList.Add(3)` 한 줄이 실제로 시키는 일은 이렇다 (15.2절에서 IL 수준으로 이미 봤다).

```text
1. 관리 힙에 새 object를 할당한다.
2. 스택에 있던 값을 그 메모리 위치로 옮긴다.
3. (언박싱할 때) 힙 객체에 저장된 값을 다시 스택으로 옮긴다.
4. 이제 아무도 안 쓰는 힙 객체를 GC가 (언젠가) 수거한다.
```

한 번이면 무시할 만하다. 컨테이너에 수만 개가 들어 있고 그것을 주기적으로 훑는다면 얘기가 다르다. 아래는 원천 도서(*CLR via C#*)에 실린 측정 프로그램이다. 각 루프는 1억 회 반복한다.

```csharp
const Int32 count = 100000000;

using (new OperationTimer("List<Int32>")) {
    List<Int32> l = new List<Int32>();
    for (Int32 n = 0; n < count; n++) {
        l.Add(n);                  // 박싱 없음
        Int32 x = l[n];            // 언박싱 없음
    }
    l = null;                      // GC 대상이 되도록
}

using (new OperationTimer("ArrayList of Int32")) {
    ArrayList a = new ArrayList();
    for (Int32 n = 0; n < count; n++) {
        a.Add(n);                  // 박싱
        Int32 x = (Int32) a[n];    // 언박싱
    }
    a = null;
}
```

원천에 기록된 실행 결과다.

```text
00:00:01.6246959 (GCs=  6) List<Int32>
00:00:10.8555008 (GCs=390) ArrayList of Int32
00:00:02.5427847 (GCs=  4) List<String>
00:00:02.7944831 (GCs=  7) ArrayList of String
```

| 시나리오 | 시간 | GC 횟수(0세대) | 해석 |
|---|---|---|---|
| `List<Int32>` | 1.62초 | 6 | 박싱 없음 |
| `ArrayList` (Int32) | 10.86초 | **390** | 1억 번 박싱 |
| `List<String>` | 2.54초 | 4 | 참조 복사 |
| `ArrayList` (String) | 2.79초 | 7 | 참조 복사 + 캐스트 검사 |

> **📌 이 수치는 원천 도서의 저자 환경 측정값이다**
>
> 절대값은 하드웨어와 런타임 버전에 따라 달라진다. 중요한 것은 **비율의 방향**이다. 값 타입에서 약 7배 차이, GC 횟수 65배 차이. 참조 타입에서는 시간 차이가 10% 안쪽이다. 지금 .NET에서 같은 코드를 돌리면 절대 시간은 훨씬 짧게 나오지만, 값 타입과 참조 타입 사이의 이 비대칭은 그대로다. 성능 수치는 언제나 자기 환경에서 다시 재야 한다(67장).

여기서 읽어야 할 것은 두 가지다.

1. **값 타입에서 제네릭의 이득은 압도적이다.** 박싱이 사라지고, 박싱이 사라지니 할당이 사라지고, 할당이 사라지니 GC가 사라진다.
2. **참조 타입에서 제네릭의 성능 이득은 크지 않다.** 어차피 포인터 복사였고, 남는 차이는 캐스트 검사 비용 정도다. 그래도 제네릭을 쓴다. 타입 안전과 코드 명료성 때문이다.

### 왜 제네릭이 CLR 2.0을 요구했나

여기가 이 절의 핵심이다. 제네릭은 컴파일러만 고쳐서 만들 수 있는 기능이 **아니었다**.

만약 C# 컴파일러가 `List<int>`를 `ArrayList`로 바꿔치기하고 캐스트를 자동 삽입하는 식으로 구현했다면 — 이건 실제로 Java가 택한 길이다(23.12절) — 컴파일 타임 타입 안전은 얻었겠지만 박싱은 그대로 남았을 것이다. 위 표의 10.86초가 그대로였을 거란 뜻이다. 제네릭이 약속한 이득의 절반 이상이 날아간다.

박싱을 없애려면 런타임이 "`int`를 담는 리스트"를 **`object`를 담는 리스트와 다른 타입으로** 알고 있어야 한다. 즉 타입 시스템 자체가 바뀌어야 한다. Microsoft가 CLR 2.0에서 실제로 한 일의 목록이다.

| 고친 것 | 무엇을 |
|---|---|
| **IL 명령 집합** | 타입 인자를 인식하는 새 IL 명령을 추가 |
| **메타데이터 테이블** | 제네릭 매개변수를 가진 타입 이름과 메서드를 표현할 수 있도록 기존 테이블 형식을 변경 |
| **언어** | C#, VB.NET 등에 새 문법 추가 |
| **컴파일러** | 새 IL 명령과 새 메타데이터 형식을 내보내도록 수정 |
| **JIT 컴파일러** | 타입 인자를 인식하는 IL을 처리해 올바른 네이티브 코드를 생성하도록 수정 |
| **리플렉션** | 제네릭 매개변수를 조회하는 멤버 추가, 런타임에 제네릭 타입을 만드는 emit 멤버 추가 |
| **디버거** | 제네릭 타입·멤버·필드·지역 변수를 표시하고 조작하도록 수정 |
| **IntelliSense** | 특정 타입 인자로 사용될 때 구체 시그니처를 보여주도록 수정 |

플랫폼 전체를 관통하는 변경이다. "구문 설탕 하나 추가"와는 규모가 다르다. 그리고 이 투자 덕분에 **소스 코드 보호**(알고리즘의 소스 없이 라이브러리만으로 쓸 수 있다), **타입 안전**(컴파일러와 CLR이 함께 보장한다), **더 깨끗한 코드**(캐스트가 줄어든다), **더 나은 성능**(박싱도 캐스트 검사도 없다)이 전부 가능해졌다.

> **💡 "제네릭은 컬렉션용"이라는 오해**
>
> 제네릭이 가장 눈에 띄는 곳이 컬렉션인 것은 맞다. 하지만 제네릭의 용도는 컬렉션보다 훨씬 넓다. `Nullable<T>`(21.1절), `Task<T>`(47장), `Span<T>`(68장), `Func<T,TResult>`(26.5절), `IComparer<T>`(25.7절), `Lazy<T>`, `IOptions<T>`, `ILogger<T>` — 전부 컬렉션이 아니다. 제네릭은 "여러 타입에 걸친 알고리즘"과 "타입을 하나 감싸는 래퍼"를 표현하는 일반 도구다.

> **⚠️ 비제네릭 컬렉션은 지금도 살아 있다**
>
> `System.Collections`의 `ArrayList`, `Hashtable`, `Queue`, `Stack`은 하위 호환을 위해 여전히 BCL에 있다. 삭제되지 않았다는 이유로 새 코드에서 쓰면 안 된다. Microsoft는 명시적으로 비제네릭 컬렉션 사용을 **권장하지 않는다**. 이유는 셋이다. (1) 타입 안전·코드 명료성·성능 이득이 없다. (2) 제네릭 클래스의 객체 모델이 더 낫다 — 가상 메서드가 더 적어서 더 빠르고, 새 기능을 담은 멤버가 추가되어 있다. (3) 최신 분석기가 경고를 낸다. 다만 오래된 API가 `IList`나 `IEnumerable`(비제네릭)을 요구하는 경우는 여전히 있어서, 제네릭 인터페이스가 비제네릭 인터페이스를 **대체한 것이 아니라 병존한다**는 점은 기억해야 한다(`List<T>`가 `IList<T>`만 구현했다면 `List<DateTime>`을 `IList`로 볼 수 없었을 것이다).

## 23.2 제네릭 타입과 제네릭 메서드

### 제네릭 타입 — 열린 타입과 닫힌 타입

제네릭 타입은 **타입 매개변수(type parameter)** 를 선언한다. 소비자가 **타입 인자(type argument)** 로 채워 넣을 자리표시자다.

```csharp
public class Stack<T>
{
    int position;
    T[] data = new T[100];

    public void Push (T obj) => data[position++] = obj;
    public T Pop()           => data[--position];
}
```

`Stack<T>`는 타입 매개변수 `T` 하나를 선언한다. 쓸 때는 이렇다.

```csharp
var stack = new Stack<int>();
stack.Push (5);
stack.Push (10);
int x = stack.Pop();     // x는 10
int y = stack.Pop();     // y는 5
```

`Stack<int>`는 `T` 자리에 `int`를 채워서 타입을 즉석에서 만든다. 이 스택에 문자열을 넣으려 하면 **컴파일 오류**다. 실질적으로 `Stack<int>`는 `T`가 전부 `int`로 치환된 정의 — 필드가 `int[] data`이고 `Push`가 `int`를 받는 클래스 — 를 가진다.

용어를 정리하자. `Stack<T>`는 **열린 타입(open type)**, `Stack<int>`는 **닫힌 타입(closed type)** 이다. **런타임에 존재하는 제네릭 타입 인스턴스는 전부 닫혀 있다.** 자리표시자가 전부 채워져 있다는 뜻이다. 그래서 다음은 불법이다.

```csharp
var stack = new Stack<T>();     // 불법: T가 뭔데?
```

단, `T`를 타입 매개변수로 선언한 클래스나 메서드 **안이라면** 합법이다.

```csharp
public class Stack<T>
{
    public Stack<T> Clone()
    {
        Stack<T> clone = new Stack<T>();   // 합법
        // ...
    }
}
```

이 자리에서 `T`는 미지수가 아니라 "이 인스턴스가 무엇으로 닫혔든 그것"을 가리키는 이름이다.

> **📌 `ObjectStack`은 `Stack<object>`와 기능적으로 동등하다**
>
> 23.1절의 `ObjectStack`이 정확히 `Stack<object>`다. 제네릭이 준 것은 "`object`로도 쓸 수 있고 `int`로도 쓸 수 있게" 하나의 정의를 매개변수화한 것이다. `Stack<T>`는 `ObjectStack`처럼 한 번만 작성되어 모든 타입에 동작하고, 동시에 `IntStack`처럼 특정 타입에 특수화된다.

### 제네릭 메서드

제네릭 메서드는 **메서드 시그니처 안에** 타입 매개변수를 선언한다.

```csharp
static void Swap<T> (ref T a, ref T b)
{
    T temp = a;
    a = b;
    b = temp;
}
```

호출은 이렇다.

```csharp
int x = 5;
int y = 10;
Swap (ref x, ref y);        // 타입 추론
Swap<int> (ref x, ref y);   // 명시
```

`Swap` 하나로 정수·문자열·비트맵·자동차 전부를 교환한다. 그리고 **값 타입은 스택에 남고 참조 타입은 힙에 남는다.** `object` 버전을 만들었다면 값 타입은 힙으로 끌려 올라갔을 것이다.

컴파일 결과를 보자. `ildasm`으로 뜯으면 이렇다.

```il

{
  .maxstack  2
  .locals init ([0] !!T temp)
  IL_0000:  ldarg.0
  IL_0001:  ldobj      !!T
  IL_0006:  stloc.0
  IL_0007:  ldarg.0
  IL_0008:  ldarg.1
  IL_0009:  ldobj      !!T
  IL_000e:  stobj      !!T
  IL_0013:  ldarg.1
  IL_0014:  ldloc.0
  IL_0015:  stobj      !!T
  IL_001a:  ret
}
```

`!!T`가 **메서드의** 타입 매개변수를 가리키는 IL 표기다. 타입의 타입 매개변수는 느낌표 하나 — `!T` — 로 쓴다. `ldobj`/`stobj`는 "타입을 모르는 값을 관리 포인터를 통해 읽고 쓴다"는 명령이고, 이 명령들이 CLR 2.0에서 제네릭을 위해 의미를 확장한 부분이다.

### 무엇이 제네릭 메서드이고 무엇이 아닌가

제네릭 타입 안에 있다고 다 제네릭 메서드가 아니다. **꺾쇠 문법으로 자기 타입 매개변수를 새로 도입해야** 제네릭 메서드다.

```csharp
public class Stack<T>
{
    public T Pop() => data[--position];              // 제네릭 메서드가 아니다
    public Stack<U> FilteredStack<U>() where U : T   // 제네릭 메서드다
    { /* ... */ }
}
```

`Pop`은 이미 있는 `T`를 쓸 뿐이다.

### 타입 매개변수를 도입할 수 있는 구문

**타입과 메서드만이 타입 매개변수를 도입할 수 있다.**

| 구문 | 타입 매개변수 도입 | 이미 선언된 타입 매개변수 사용 |
|---|---|---|
| 클래스, 구조체, 인터페이스, 델리게이트 | 가능 | 가능 |
| 메서드 | 가능 | 가능 |
| 프로퍼티, 인덱서, 이벤트, 필드 | **불가** | 가능 |
| 생성자, 연산자, 종료자 | **불가** | 가능 |
| **열거형** | **불가** | — |

```csharp
public struct Nullable<T>
{
    public T Value { get; }        // 프로퍼티는 T를 쓸 수 있다
}

public class Stack<T>
{
    public T this [int index] => data [index];    // 인덱서도 T를 쓴다
    public Stack<T>() { }                         // 불법: 생성자는 T를 도입 못 한다
}
```

생성자는 이미 있는 타입 매개변수에 참여할 수는 있지만 새로 도입하지는 못한다. 생성자 이름 뒤에 꺾쇠를 붙이는 문법 자체가 없다.

> **📌 왜 프로퍼티·인덱서·연산자는 제네릭이 될 수 없는가**
>
> C# 팀의 판단은 두 갈래였다. 첫째, 이 멤버들을 제네릭으로 만들 필요가 있는 경우가 드물다. 둘째, 적절한 문법을 언어에 집어넣는 비용이 너무 크다. 예를 들어 코드에서 `+` 연산자를 쓸 때, 컴파일러는 연산자 오버로드 메서드를 호출한다. 그런데 `+` 기호와 함께 타입 인자를 지정할 방법이 없다. `a +<int> b` 같은 문법을 만들어야 하는데 아무도 그걸 원하지 않았다.

> **⚠️ 열거형은 제네릭이 될 수 없다**
>
> 클래스·구조체·인터페이스·델리게이트만 제네릭으로 쓸 수 있다. `enum Foo<T> { ... }`는 컴파일되지 않는다. CLR 차원의 제약이다. 반대로 **열거형을 타입 인자로 쓰는 것**은 아무 문제가 없고, ※C# 7.3부터는 `where T : System.Enum` 제약도 걸 수 있다(23.6절).

## 23.3 타입 매개변수 선언과 타입 추론

### 여러 개의 타입 매개변수와 이름 규칙

제네릭 타입과 메서드는 타입 매개변수를 여러 개 가질 수 있다.

```csharp
class Dictionary<TKey, TValue> { /* ... */ }
```

```csharp
Dictionary<int,string> myDict = new Dictionary<int,string>();
var myDict2 = new Dictionary<int,string>();
```

명명 관례는 이렇다.

| 상황 | 관례 | 예 |
|---|---|---|
| 타입 매개변수 1개, 의도가 자명함 | `T` | `List<T>`, `Stack<T>` |
| 여러 개 | `T` 접두사 + 서술적 이름 | `TKey`, `TValue`, `TResult`, `TElement` |
| 위임(delegate) 반환 타입 | `TResult` | `Func<T,TResult>` |

Microsoft 설계 지침은 "제네릭 매개변수 변수는 `T`라고 부르거나, 최소한 대문자 `T`로 시작해야 한다"고 못박는다. 대문자 `T`는 type을 뜻하고, 이는 인터페이스 앞에 붙는 `I`와 같은 관례다.

### 아리티 기반 오버로딩

제네릭 타입 이름과 메서드 이름은 **타입 매개변수의 개수가 다르면** 오버로드할 수 있다.

```csharp
class A          {}
class A<T>       {}
class A<T1,T2>   {}
```

셋은 충돌하지 않는다. 타입 매개변수의 개수를 **아리티(arity)** 라 부른다. 이름 충돌 판정에 쓰이는 것은 오직 아리티다.

> **⚠️ 제약이나 타입 매개변수 이름으로는 오버로드할 수 없다**
>
> CLR은 타입 매개변수 **이름**이나 **제약**에 기반한 오버로딩을 허용하지 않는다. 오버로드 판별은 아리티만으로 한다.
>
> ```csharp
> internal sealed class AType {}                 // OK
> internal sealed class AType<T> {}              // OK
> internal sealed class AType<T1, T2> {}         // OK
> internal sealed class AType<T> where T : IComparable<T> {}   // 오류: AType<T>와 충돌
> internal sealed class AType<T3, T4> {}         // 오류: AType<T1,T2>와 충돌
> ```
>
> 메서드도 같다. `M<T>()`와 `M<T>() where T : IComparable<T>`는 공존할 수 없다.

### 타입 추론의 기본 규칙

제네릭 메서드를 호출할 때는 보통 타입 인자를 줄 필요가 없다. 컴파일러가 **인자의 정적 타입에서** 추론한다.

```csharp
int x = 5, y = 10;
Swap (ref x, ref y);          // Swap<int> 호출로 추론된다
```

추론 규칙의 핵심은 한 문장으로 요약된다.

> 컴파일러는 **변수의 데이터 타입**을 보지, 그 변수가 실제로 가리키는 객체의 런타임 타입을 보지 않는다.

이 문장이 추론 실패의 거의 모든 원인이다.

### 추론이 실패하는 세 가지 경우

**(1) 메서드에 매개변수가 없다.** 추론할 근거가 없다.

```csharp
static void DisplayBaseClass<T>()
{
    Console.WriteLine("Base class of {0} is: {1}.", typeof(T), typeof(T).BaseType);
}

DisplayBaseClass<int>();       // 반드시 명시해야 한다
DisplayBaseClass<string>();
// DisplayBaseClass();         // 컴파일 오류
```

타입 추론은 **제네릭 메서드가 매개변수를 최소 하나 가질 때만** 동작한다. 반환 타입은 추론에 쓰이지 않는다.

**(2) 인자들의 정적 타입이 서로 다르다.**

```csharp
private static void CallingSwapUsingInference() {
    Int32 n1 = 1, n2 = 2;
    Swap(ref n1, ref n2);      // Swap<Int32> 호출

    String s1 = "Aidan";
    Object s2 = "Grant";
    Swap(ref s1, ref s2);      // 오류: 타입을 추론할 수 없다
}
```

`s2`가 실제로 가리키는 것은 `String`이지만 **선언 타입은 `Object`** 다. 컴파일러는 `String`과 `Object` 사이에서 하나를 고르지 못하고 손을 든다.

```text
error CS0411: The type arguments for method 'Program.Swap<T>(ref T, ref T)'
cannot be inferred from the usage. Try specifying the type arguments explicitly.
```

**(3) 후보가 여럿이라 모호하다.** 여러 인자에서 서로 다른 후보가 나오고 그중 하나로 수렴하지 않으면 실패한다.

> **⚠️ `ref`/`out` 매개변수는 추론을 더 빡빡하게 만든다**
>
> `ref`/`out`으로 넘기는 변수는 메서드 매개변수와 **정확히 같은 타입**이어야 한다. 그렇지 않으면 타입 안전성 구멍이 생긴다(10장). 그래서 위 (2)번 예제가 실패하는 것이고, 이 이유로 `Interlocked` 클래스는 제네릭 오버로드를 따로 제공한다.
>
> ```csharp
> public static class Interlocked {
>     public static T Exchange<T>(ref T location1, T value) where T: class;
>     public static T CompareExchange<T>(ref T location1, T value, T comparand)
>         where T: class;
> }
> ```

### 비제네릭 오버로드와의 경쟁

같은 이름으로 구체 타입 버전과 제네릭 버전을 동시에 정의할 수 있다.

```csharp
private static void Display(String s) {
    Console.WriteLine(s);
}

private static void Display<T>(T o) {
    Display(o.ToString());     // Display(String)을 호출한다
}
```

호출 결과는 이렇다.

```csharp
Display("Jeff");            // Display(String) 호출
Display(123);               // Display<T>(T) 호출
Display<String>("Aidan");   // Display<T>(T) 호출
```

세 줄이 각각 다른 이유로 그렇게 된다.

| 호출 | 선택 | 이유 |
|---|---|---|
| `Display("Jeff")` | `Display(String)` | 컴파일러는 **더 명시적인 일치**를 제네릭 일치보다 선호한다 |
| `Display(123)` | `Display<T>(T)` | `Int32`를 받는 비제네릭 버전이 없다 |
| `Display<String>("Aidan")` | `Display<T>(T)` | 타입 인자를 직접 준 것은 "제네릭을 부르겠다"는 선언이다 |

> **📌 컴파일러가 명시적 일치를 선호해서 다행인 경우**
>
> 위 코드에서 만약 컴파일러가 제네릭 버전을 선호했다면, `Display<T>` 안의 `Display(o.ToString())`이 다시 `Display<T>`를 호출하게 되어 **무한 재귀**가 일어난다. 오버로드 해석 규칙이 코드의 정상 동작을 떠받치고 있는 사례다.

이 "제네릭은 언제나 완벽하게 맞는다"는 성질은 강력하면서 동시에 위험하다. 23.15절에서 이것이 어떻게 사고로 이어지는지 본다.

> **💡 추론에 기대되, 애매하면 명시하라**
>
> 원천 도서 중 하나(*Pro C# 10*)는 "제네릭 메서드임을 동료에게 분명히 알리기 위해 항상 타입 인자를 명시하는 습관을 들이라"고 권한다. 다른 원천(*C# 12 in a Nutshell*)은 "보통은 명시할 필요가 없다"는 입장이다. 실무에서 갈리는 지점이라, 필자의 기준은 이렇다. **호출부만 읽어서 `T`가 무엇인지 즉시 보이면 생략하고, 한 번이라도 되짚어야 하면 명시한다.** `Swap(ref x, ref y)`는 생략해도 된다. `Convert(source, target)` 같은 이름에서는 `Convert<Order, OrderDto>(...)`로 쓰는 편이 읽는 사람에게 친절하다.

## 23.4 `typeof`와 언바운드 제네릭 타입

### 열린 타입은 런타임에 존재하지 않는다 — 언바운드 타입은 존재한다

앞 절에서 "런타임의 제네릭 타입 인스턴스는 전부 닫혀 있다"고 했다. 열린 타입은 컴파일 과정에서 닫힌다. 그런데 예외가 하나 있다. **언바운드(unbound) 제네릭 타입**은 런타임에 존재할 수 있다 — 다만 오직 `Type` 객체로서만이다.

C#에서 언바운드 제네릭 타입을 지정하는 유일한 방법은 `typeof` 연산자다.

```csharp
class A<T> {}
class A<T1,T2> {}
// ...
Type a1 = typeof (A<>);     // 언바운드 타입 (타입 인자가 없다)
Type a2 = typeof (A<,>);    // 타입 인자가 여럿이면 쉼표로 표시한다
```

쉼표 개수 = 타입 매개변수 개수 − 1이다. `Dictionary<,>`, `Tuple<,,,>` 처럼 쓴다. 닫힌 타입도 물론 지정할 수 있다.

```csharp
Type a3 = typeof (A<int,int>);        // 닫힌 타입
```

그리고 제네릭 타입 안에서 타입 매개변수 자체에 `typeof`를 쓸 수도 있다(`class B<T> { void X() { Type t = typeof(T); } }`). 이건 컴파일 시점에는 열려 있지만 런타임에는 닫힌다 — `B<int>.X()`가 실행되는 시점의 `t`는 `typeof(int)`다.

### 컴파일 결과

`typeof`는 마법이 아니다. IL 두 줄로 내려간다.

```il
IL_0000:  ldtoken    A`1
IL_0005:  call       class [System.Runtime]System.Type
                     [System.Runtime]System.Type::GetTypeFromHandle(
                       valuetype [System.Runtime]System.RuntimeTypeHandle)
```

`ldtoken`이 메타데이터 토큰을 스택에 올리고, `Type.GetTypeFromHandle`이 그것을 `Type` 객체로 바꾼다. 여기서 눈여겨볼 것은 타입 이름이다.

### 백틱과 아리티 — `` List`1 ``

IL과 리플렉션이 쓰는 제네릭 타입의 진짜 이름은 이렇게 생겼다.

```text
System.Collections.Generic.List`1
System.Collections.Generic.Dictionary`2
DictionaryStringKey`1[System.Guid]
```

백틱(`` ` ``) 뒤의 숫자가 **아리티**, 곧 그 타입이 요구하는 타입 매개변수의 개수다. `Dictionary`는 `TKey`와 `TValue` 두 개가 필요하므로 아리티 2다.

```csharp
Console.WriteLine(typeof(List<>).Name);        // List`1
Console.WriteLine(typeof(List<int>).Name);     // List`1
Console.WriteLine(typeof(List<int>).FullName);
// System.Collections.Generic.List`1[[System.Int32, System.Private.CoreLib, ...]]
```

`Name`은 닫혀 있어도 `` List`1 ``이다. 타입 인자는 `FullName`에서만 대괄호로 붙는다. 이 이름 규칙은 리플렉션으로 타입을 문자열로 찾을 때 직접 부딪히는 부분이고, 자세한 것은 57.1절과 57.4절에서 다룬다.

### 열린 타입의 인스턴스는 만들 수 없다

CLR은 사용 중인 모든 타입에 대해 내부 데이터 구조 — **타입 객체** — 를 만든다. 제네릭 타입 매개변수를 가진 타입도 타입이므로 타입 객체가 만들어진다. 클래스든 구조체든 인터페이스든 델리게이트든 마찬가지다. 그러나 **열린 타입의 인스턴스는 만들 수 없다.** 인터페이스 타입의 인스턴스를 만들 수 없는 것과 같은 이치다.

```csharp
// 부분적으로만 지정된 열린 타입
internal sealed class DictionaryStringKey<TValue> : Dictionary<String, TValue> { }

private static Object CreateInstance(Type t) {
    Object o = null;
    try {
        o = Activator.CreateInstance(t);
        Console.Write("Created instance of {0}", t.ToString());
    }
    catch (ArgumentException e) {
        Console.WriteLine(e.Message);
    }
    return o;
}

// 호출
CreateInstance(typeof(Dictionary<,>));              // 열린 타입 — 실패
CreateInstance(typeof(DictionaryStringKey<>));      // 열린 타입 — 실패
var o = CreateInstance(typeof(DictionaryStringKey<Guid>));   // 닫힌 타입 — 성공
Console.WriteLine("Object type=" + o.GetType());
```

출력이다.

```text
Cannot create an instance of System.Collections.Generic.
Dictionary`2[TKey,TValue] because Type.ContainsGenericParameters is true.
Cannot create an instance of DictionaryStringKey`1[TValue] because
Type.ContainsGenericParameters is true.
Created instance of DictionaryStringKey`1[System.Guid]
Object type=DictionaryStringKey`1[System.Guid]
```

`Activator.CreateInstance`는 열린 타입을 넘기면 `ArgumentException`을 던진다. 예외 메시지가 이유를 정확히 말해 준다 — `Type.ContainsGenericParameters`가 `true`다.

> **⚠️ `DictionaryStringKey<TValue>`도 열린 타입이다**
>
> 타입 인자를 **일부만** 지정한 타입도 열린 타입이다. `Dictionary<String, TValue>`에서 `TKey`는 채워졌지만 `TValue`가 남아 있다. CLR 입장에서는 "아직 채울 게 남은" 타입이고 인스턴스를 만들 수 없다. 판정 기준은 `ContainsGenericParameters` 프로퍼티다.

> **📌 `MakeGenericType`으로 런타임에 닫기**
>
> 언바운드 타입 객체가 존재하는 이유는 이것으로 뭔가를 하기 위해서다. `Type.MakeGenericType`이 언바운드 타입에 타입 인자를 채워 닫힌 타입을 만든다.
>
> ```csharp
> Type openList  = typeof(List<>);
> Type closedInt = openList.MakeGenericType(typeof(int));   // List<int>
> object list    = Activator.CreateInstance(closedInt);
> ```
>
> 이것이 의존성 주입 컨테이너가 `ILogger<>` 등록 하나로 `ILogger<OrderService>`를 만들어 내는 원리다. 전체 이야기는 57.4절에 있다.

## 23.5 `default` 제네릭 값

### 문제 — `T`의 "빈 값"이 무엇인지 모른다

제네릭 코드 안에서 변수를 초기화해야 하는데, `T`가 무엇인지 모른다. `null`을 넣으면 될까?

```csharp
private static void SettingAGenericTypeVariableToNull<T>() {
    T temp = null;
    // CS0403 – Cannot convert null to type parameter 'T' because it could
    // be a non-nullable value type. Consider using 'default(T)' instead
}
```

안 된다. `T`가 제약되지 않았으므로 값 타입일 수 있고, 값 타입 변수에 `null`을 넣을 수는 없다. (만약 `T`가 참조 타입으로 제약되어 있었다면 이 코드는 문제없이 컴파일되고 실행된다.)

그래서 C#은 `default` 키워드에 두 번째 역할을 줬다.

```csharp
private static void SettingAGenericTypeVariableToDefaultValue<T>() {
    T temp = default(T);     // OK
}
```

### 규칙

`default(T)`가 만들어 내는 값이다.

| `T`의 실제 타입 | `default(T)` |
|---|---|
| 참조 타입 (클래스, 인터페이스, 델리게이트, 배열) | `null` |
| 숫자 값 타입 (`int`, `double`, `decimal` 등) | `0` |
| `bool` / `char` | `false` / `'\0'` |
| 열거형 | 기반 값 `0`을 그 열거형으로 캐스트한 것 |
| 구조체 | 모든 필드를 **비트 단위로 0**으로 만든 값 |
| `Nullable<U>` | `HasValue == false`인 상태 |

한 문장으로: **참조 타입은 `null`, 값 타입은 그 타입의 필드를 비트 단위로 0으로 만든 결과**다.

```csharp
static void Zap<T> (T[] array)
{
    for (int i = 0; i < array.Length; i++)
        array[i] = default(T);
}
```

### `default` 리터럴 ※C# 7.1

C# 7.1부터는 컴파일러가 타입을 추론할 수 있는 자리에서 타입 인자를 생략할 수 있다.

```csharp
array[i] = default;
```

이 축약형을 **default 리터럴(default literal)** 이라 부른다. 단순 변수뿐 아니라 복합 타입에도 쓴다.

```csharp
public struct Point<T>
{
    private T _xPos;
    private T _yPos;

    public Point(T xVal, T yVal) { _xPos = xVal; _yPos = yVal; }

    public T X { get => _xPos; set => _xPos = value; }
    public T Y { get => _yPos; set => _yPos = value; }

    // 필드를 타입 매개변수의 기본값으로 리셋한다
    public void ResetPoint()
    {
        _xPos = default;
        _yPos = default;
    }

    public override string ToString() => $"[{_xPos}, {_yPos}]";
}
```

```csharp
Point<string> p4 = default;      // 구조체 전체가 기본값
Point<int>    p5 = default;
```

`Point<T>`를 세 가지 타입으로 만들어 `ResetPoint()`를 호출한 결과다.

```text
p.ToString()=[10, 10]     →  [0, 0]      // Point<int>
p2.ToString()=[5.4, 3.3]  →  [0, 0]      // Point<double>
p3.ToString()=[i, 3i]     →  [, ]        // Point<string> — null이라 빈 문자열
```

`default(T)`가 없었다면 이 메서드는 쓸 수 없다. `_xPos = 0;`이라고 쓰는 순간 `T`가 숫자라는 가정이 들어가기 때문이다.

### 컴파일 결과

`default(T)`는 어떻게 컴파일되는가. IL을 보면 값 타입과 참조 타입을 구분하지 않는다는 것이 드러난다.

```il
.locals init ([0] !!T temp)
IL_0000:  ldloca.s   temp
IL_0002:  initobj    !!T
IL_0008:  ldloc.0
```

`initobj`는 "관리 포인터가 가리키는 위치를 해당 타입의 기본값으로 초기화하라"는 명령이다. 그리고 그 "기본값"을 실제로 무엇으로 만들지는 **JIT이 정한다**. `T`가 참조 타입이면 포인터 크기만큼 0(=`null`)을 쓰고, 값 타입이면 그 타입 크기만큼 0을 쓴다. 하나의 IL이 두 동작을 낳는 것이다. 23.11절에서 볼 "코드 특수화"의 가장 작은 사례다.

> **⚠️ `default(T)`와 `new T()`는 다른 것이다**
>
> 참조 타입에서 이 둘은 완전히 다르다. `default(T)`는 `null`이고, `new T()`는 실제 객체다. 값 타입에서는 결과가 같지만 요구 사항이 다르다 — `new T()`를 쓰려면 `where T : new()` 제약이 필요하고 `default(T)`는 아무 제약도 필요 없다.
>
> ```csharp
> // 제약이 필요 없다
> public static T FirstOrDefault<T>(this IEnumerable<T> sequence, Predicate<T> test)
> {
>     foreach (T value in sequence)
>         if (test(value)) return value;
>     return default(T);
> }
>
> // new() 제약이 필요하다
> public delegate T FactoryFunc<T>();
> public static T Factory<T>(FactoryFunc<T> makeANewT) where T : new()
> {
>     T rVal = makeANewT();
>     if (rVal == null) return new T();
>     else return rVal;
> }
> ```
>
> 제약 하나를 없앨 수 있다면 그것만으로 `default`를 고를 이유가 된다(23.13절).

> **⚠️ `default(T)`가 유효한 상태가 아닐 수 있다**
>
> `default`는 "이 타입의 올바른 초깃값"이 아니라 "비트가 전부 0인 상태"일 뿐이다. `DateTime`의 기본값은 `0001-01-01`이고, `Guid`의 기본값은 전부 0이며, `decimal`의 기본값은 0이다. 도메인상 의미 없는 값일 수 있다. 이 문제는 구조체 설계 원칙 "0이 유효한 상태여야 한다"(16.4절)와 맞닿아 있다.
>
> 또 하나. `default(T)`가 `null`인지 검사해서 "찾지 못했다"를 표현하는 코드는 `T`가 값 타입일 때 조용히 깨진다. `int`에서 `default(T)`는 `0`이고, `0`은 완벽하게 유효한 데이터일 수 있다. LINQ의 `FirstOrDefault`가 `int` 시퀀스에서 헷갈리는 이유가 정확히 이것이고, 그래서 .NET 6부터 `FirstOrDefault(defaultValue)` 오버로드가 추가됐다.

> **📌 `default(T)`로 검사하면 JIT이 코드를 지운다**
>
> 제네릭 타입 변수를 `null`과 비교하는 것은 제약이 없어도 합법이다.
>
> ```csharp
> private static void ComparingAGenericTypeVariableWithNull<T>(T obj) {
>     if (obj == null) { /* 값 타입에서는 절대 실행되지 않는다 */ }
> }
> ```
>
> `T`가 값 타입이면 `obj`는 결코 `null`일 수 없다. 보통이라면 컴파일러가 오류를 낼 만한 코드지만, C# 컴파일러는 이것을 그냥 통과시킨다. 그리고 값 타입 인자로 이 메서드가 호출되면 **JIT 컴파일러가 `if` 검사도, 중괄호 안의 코드도 네이티브 코드로 내보내지 않는다.** `!=`를 썼다면 반대로 검사는 사라지고 본문만 남는다. 제네릭에서 "쓸모없어 보이는 널 검사"가 성능 비용이 아닌 이유다.
>
> 단, `T`가 `struct`로 제약되어 있으면 컴파일러가 오류를 낸다. 결과가 언제나 같은 비교를 굳이 쓸 이유가 없기 때문이다.

## 23.6 제네릭 제약(`where`) 전체 목록 — `class`, `struct`, `notnull`, `unmanaged`, `new()`, 기본 타입, 인터페이스, 허용된 조합

### 제약이 없으면 아무것도 못 한다

제약 없는 제네릭 코드가 할 수 있는 일을 보자.

```csharp
private static Boolean MethodTakingAnyType<T>(T o) {
    T temp = o;
    Console.WriteLine(o.ToString());
    Boolean b = temp.Equals(o);
    return b;
}
```

이건 컴파일된다. 참조 타입이든 값 타입이든 열거형이든 인터페이스든 델리게이트든 — 오늘 존재하는 모든 타입과 **내일 정의될 모든 타입**에 대해 동작한다. 대입과 `System.Object`가 정의한 메서드 호출은 모든 타입이 지원하기 때문이다.

이제 이걸 보자.

```csharp
private static T Min<T>(T o1, T o2) {
    if (o1.CompareTo(o2) < 0) return o1;    // error CS1061: 'T' does not contain
    return o2;                              // a definition for 'CompareTo'
}
```

`CompareTo`를 제공하지 않는 타입이 세상에 널려 있고, 컴파일러는 "이 메서드가 모든 타입에 대해 동작한다"고 보장할 수 없다. C# 컴파일러는 제네릭 코드를 컴파일할 때 **오늘 존재하거나 앞으로 정의될 모든 타입에 대해 이 코드가 동작하는지**를 검사한다.

그래서 제약이 있다.

```csharp
public static T Min<T>(T o1, T o2) where T : IComparable<T> {
    if (o1.CompareTo(o2) < 0) return o1;
    return o2;
}
```

> **📌 제약은 제한이 아니라 해방이다**
>
> 이름이 오해를 부른다. 제약(constraint)의 주된 목적은 **금지가 아니라 허가**다. `T : Foo` 제약은 `T`의 인스턴스를 `Foo`로 다룰 수 있게 해 주고, `T : new()` 제약은 `new T()`를 쓸 수 있게 해 준다. 제약을 걸수록 제네릭 코드 안에서 할 수 있는 일이 늘어난다. 대가는 그 제네릭을 쓸 수 있는 타입이 줄어드는 것이다. 이 저울질이 23.13절의 주제다.

### 제약의 세 부류

CLR과 컴파일러는 제약을 세 부류로 나눈다.

```text
┌──────────────────────────────────────────────────────────────┐
│  where T : [주(primary) 제약] , [부(secondary) 제약...] ,     │
│            [생성자 제약] , [allows ref struct]                │
│              0개 또는 1개      0개 이상       0개 또는 1개      │
└──────────────────────────────────────────────────────────────┘
       │                    │                │            │
       ▼                    ▼                ▼            ▼
  class / struct        인터페이스        new()      ※C# 13
  notnull / unmanaged   타입 매개변수(T2)             반(反)제약
  기반 클래스 이름
```

이 순서는 문법 규칙이다. 어기면 컴파일되지 않는다.

### 제약 전체표

| 제약 | 분류 | 의미 | 도입 |
|---|---|---|---|
| `where T : 기반클래스` | 주 | `T`가 해당 클래스이거나 그 파생 클래스 | C# 2 |
| `where T : 인터페이스` | 부 | `T`가 해당 인터페이스를 구현 | C# 2 |
| `where T : class` | 주 | `T`가 참조 타입 | C# 2 |
| `where T : class?` | 주 | `T`가 참조 타입, 널 허용도 허용 (21.6절) | C# 8 |
| `where T : struct` | 주 | `T`가 널 불가 값 타입 (`Nullable<>` 제외) | C# 2 |
| `where T : notnull` | 주 | 널 불가 값 타입 **또는** 널 불가 참조 타입 | C# 8 |
| `where T : unmanaged` | 주 | 참조를 (재귀적으로) 하나도 포함하지 않는 값 타입 | C# 7.3 |
| `where T : new()` | 생성자 | 공개 매개변수 없는 생성자를 가진 비추상 타입 | C# 2 |
| `where U : T` | 부 | `U`가 `T`이거나 `T`에서 파생 (**나체(naked) 타입 제약**) | C# 2 |
| `where T : System.Enum` | 주 | `T`가 열거형 | C# 7.3 |
| `where T : System.Delegate` | 주 | `T`가 델리게이트 | C# 7.3 |
| `where T : System.MulticastDelegate` | 주 | `T`가 멀티캐스트 델리게이트 | C# 7.3 |
| `where T : default` | — | 재정의·명시적 구현에서 "제약 없음"을 명시 | C# 9 |
| `where T : allows ref struct` | 반제약 | `T`에 `ref struct`를 넣는 것을 허용 | ※C# 13 |

### 주 제약 — 최대 하나

주 제약은 **0개 아니면 1개**다.

**기반 클래스 제약.** 봉인되지 않은 참조 타입 이름을 쓴다.

```csharp
internal sealed class PrimaryConstraintOfStream<T> where T : Stream {
    public void M(T stream) {
        stream.Close();     // OK — T는 Stream이거나 그 파생 타입이다
    }
}
```

`PrimaryConstraintOfStream<FileStream>`은 되고 `PrimaryConstraintOfStream<String>`은 안 된다.

> **⚠️ 특수 타입은 기반 클래스 제약으로 쓸 수 없다**
>
> 다음 타입들은 기반 클래스 제약이 될 수 없다.
>
> `System.Object`, `System.Array`, `System.ValueType`, `System.Void`
>
> `System.Object`를 명시적으로 쓰면 이렇게 나온다.
>
> ```text
> error CS0702: Constraint cannot be special class 'object'
> ```
>
> 주 제약을 아무것도 지정하지 않으면 `System.Object`가 가정되므로 쓸 이유도 없다.
>
> 한편 `System.Enum`, `System.Delegate`, `System.MulticastDelegate`는 **오랫동안 금지되었다가 ※C# 7.3에서 풀렸다.** CLR 2.0 시절에 쓰인 자료(원천 도서 *CLR via C#* 포함)에는 여전히 금지 목록에 들어 있으니 주의해야 한다. C# 7.3 이전에는 정적 생성자에서 `typeof(T).IsEnum`을 검사하고 아니면 `ArgumentException`을 던지는 편법을 썼다. 지금은 `where T : struct, System.Enum`이라고 쓰면 컴파일 타임에 걸린다.

**`class` 제약.** `T`가 참조 타입임을 약속한다. 클래스·인터페이스·델리게이트·배열 타입이 모두 만족한다.

```csharp
internal sealed class PrimaryConstraintOfClass<T> where T : class {
    public void M() {
        T temp = null;     // T가 참조 타입임이 보장되므로 합법
    }
}
```

**`struct` 제약.** `T`가 값 타입임을 약속한다. 열거형을 포함한 모든 값 타입이 만족한다.

```csharp
internal sealed class PrimaryConstraintOfStruct<T> where T : struct {
    public static T Factory() {
        // 모든 값 타입은 암시적으로 공개 매개변수 없는 생성자를 가진다
        return new T();
    }
}
```

> **⚠️ `Nullable<T>`는 `struct` 제약을 만족하지 않는다**
>
> `int?`는 값 타입이지만 `where T : struct` 자리에 넣을 수 없다. 컴파일러와 CLR이 `System.Nullable<T>`를 특별 취급하기 때문이다. 이유는 `Nullable<T>` 자신이 `where T : struct`로 선언되어 있고, CLR이 `Nullable<Nullable<T>>` 같은 재귀 타입을 금지하고 싶어 하기 때문이다(21.1절).
>
> ```csharp
> struct Nullable<T> where T : struct { /* ... */ }
> ```
>
> 그래서 "값 타입이면 다 되는" 제네릭을 쓸 때 `int?`가 갑자기 거부당하는 상황을 만난다.

**`unmanaged` 제약 ※C# 7.3.** `struct` 제약의 강화판이다. `T`는 단순 값 타입이거나, **재귀적으로** 참조 타입을 하나도 포함하지 않는 구조체여야 한다.

```csharp
unsafe static void Clear<T>(T* buffer, int count) where T : unmanaged
{
    for (int i = 0; i < count; i++)
        buffer[i] = default;
}
```

`unmanaged`가 걸리면 `T*` 포인터를 쓸 수 있고, `sizeof(T)`를 쓸 수 있고, `stackalloc T[n]`이 가능해진다. 상호운용(60장)과 고성능 코드(68장, 71장)에서 쓴다.

| 타입 | `struct` 만족 | `unmanaged` 만족 |
|---|---|---|
| `int`, `double`, `char`, `bool`, 열거형 | 예 | 예 |
| `(int, double)` 튜플, `DateTime`, `Guid`, `decimal` | 예 | 예 |
| `string` | 아니오 | 아니오 |
| `int?` | **아니오** | 아니오 |
| `struct S { string Name; }` | 예 | **아니오** |

**`notnull` 제약 ※C# 8.** 널 안정성 문맥(21.6절)에서 도입됐다. `T`가 **널 불가 값 타입이거나 널 불가 참조 타입**이어야 한다는 뜻이다. `class`나 `struct` 중 하나를 강요하지 않으면서 "널은 안 된다"만 말하고 싶을 때 쓴다.

```csharp
public class Cache<TKey, TValue> where TKey : notnull
{
    private readonly Dictionary<TKey, TValue> _map = new();
    // ...
}
```

`Dictionary<TKey,TValue>`의 실제 선언이 `where TKey : notnull`이다. 딕셔너리 키가 `null`이면 안 되지만 값 타입 키도 참조 타입 키도 허용해야 하기 때문이다.

> **⚠️ `notnull` 위반은 오류가 아니라 경고다**
>
> `Dictionary<string?, int>`라고 쓰면 컴파일이 **실패하지 않는다.** 경고(CS8714)가 날 뿐이다. 널 가능 참조 타입 전체가 컴파일 타임 전용 계약이고 런타임에는 아무 강제력이 없기 때문이다(21.6절). `<WarningsAsErrors>`로 승격시켜 두지 않으면 조용히 넘어간다.

**`class?` 제약 ※C# 8.** `where T : class`는 널 허용 문맥에서 "널 **불가** 참조 타입"을 뜻한다. `T`에 `string?`을 넣고 싶다면 `where T : class?`라고 써야 한다.

### 부 제약 — 여러 개 가능

**인터페이스 제약.** 개수 제한이 없다. 나열된 인터페이스를 **전부** 구현해야 한다.

```csharp
class SomeClass {}
interface Interface1 {}

class GenericClass<T,U> where T : SomeClass, Interface1
                        where U : new()
{ /* ... */ }
```

`T`는 `SomeClass`에서 파생되면서 `Interface1`을 구현해야 하고, `U`는 매개변수 없는 생성자를 가져야 한다. 타입 매개변수가 여럿이면 `where` 절도 각각 따로 쓴다.

```csharp
public class MyGenericClass<K, T> where K : SomeBaseClass, new()
                                  where T : struct, IComparable<T>
{ /* ... */ }
```

인터페이스 제약의 실용 예가 `Max`다.

```csharp
public interface IComparable<T> { int CompareTo (T other); }   // 단순화한 버전

static T Max <T> (T a, T b) where T : IComparable<T>
    => a.CompareTo (b) > 0 ? a : b;

int z       = Max (5, 10);         // 10
string last = Max ("ant", "zoo");  // zoo
```

> **📌 인터페이스 제약은 정적 추상 멤버 호출도 열어 준다 ※C# 11**
>
> C# 11부터 인터페이스 제약은 그 인터페이스의 **정적 가상/추상 멤버**를 호출할 수 있게 해 준다. 인터페이스 `IFoo`에 `static abstract void Bar()`가 있다면 `where T : IFoo` 제약 아래에서 `T.Bar()`를 부를 수 있다. 이것이 22.7절의 정적 다형성이고 22.8절의 제네릭 수학이 서 있는 토대다.

**나체 타입 제약(naked type constraint).** 타입 매개변수 사이의 관계를 요구한다.

```csharp
class Stack<T>
{
    Stack<U> FilteredStack<U>() where U : T { /* ... */ }
}
```

`U`는 `T`이거나 `T`에서 파생되어야 한다. 좀 더 실전적인 예다.

```csharp
private static List<TBase> ConvertIList<T, TBase>(IList<T> list)
    where T : TBase {
    List<TBase> baseList = new List<TBase>(list.Count);
    for (Int32 index = 0; index < list.Count; index++) {
        baseList.Add(list[index]);
    }
    return baseList;
}
```

호출해 보자.

```csharp
IList<String> ls = new List<String>();

IList<Object>              lo  = ConvertIList<String, Object>(ls);              // OK
IList<IComparable>         lc  = ConvertIList<String, IComparable>(ls);         // OK
IList<IComparable<String>> lcs = ConvertIList<String, IComparable<String>>(ls); // OK
IList<String>              ls2 = ConvertIList<String, String>(ls);              // OK
IList<Exception>           le  = ConvertIList<String, Exception>(ls);           // 오류
```

앞의 넷은 `String`이 각각 `Object`·`IComparable`·`IComparable<String>`·`String`과 호환되므로 통과한다. 마지막은 이렇게 거부된다.

```text
error CS0311: The type 'string' cannot be used as type parameter 'T' in the
generic type or method 'Program.ConvertIList<T,TBase>(...)'. There is no implicit
reference conversion from 'string' to 'System.Exception'.
```

### 생성자 제약 — 최대 하나, 항상 마지막

```csharp
internal sealed class ConstructorConstraint<T> where T : new() {
    public static T Factory() {
        return new T();
    }
}
```

```csharp
static void Initialize<T> (T[] array) where T : new()
{
    for (int i = 0; i < array.Length; i++)
        array[i] = new T();
}
```

`new()`는 **공개·매개변수 없는 생성자를 가진 비추상 타입**을 요구한다. 값 타입은 전부 암시적으로 이 생성자를 가지므로 자동 통과한다.

> **⚠️ `new()`는 반드시 마지막에 온다**
>
> ```csharp
> // OK
> public class MyGenericClass<T> where T : class, IDrawable, new() { }
>
> // 오류! new() 제약은 마지막이어야 한다
> public class MyGenericClass<T> where T : new(), class, IDrawable { }
> ```

> **⚠️ 매개변수 있는 생성자는 제약할 수 없다**
>
> CLR(따라서 C# 컴파일러)은 **매개변수 없는 생성자만** 제약으로 지원한다. `where T : new(int, string)` 같은 문법은 없다. 이 벽을 넘는 방법은 팩터리 델리게이트를 매개변수로 받는 것이다(23.13절 끝).

### 조합 규칙 — 무엇과 무엇을 같이 못 쓰는가

| 조합 | 가능 | 이유 |
|---|---|---|
| `class` + 인터페이스 + `new()` | 가능 | 표준 조합 |
| 기반 클래스 + 인터페이스 + `new()` | 가능 | 기반 클래스는 `class`를 함의한다 |
| `class` + 기반 클래스 | **불가** | 둘 다 주 제약. 주 제약은 하나뿐 |
| `struct` + `class` | **불가** | 둘 다 주 제약이고 모순이다 |
| `struct` + `new()` | **불가** | 중복이다. 모든 값 타입은 이미 매개변수 없는 생성자를 가진다 (CS0451) |
| `struct` + 인터페이스 | 가능 | `where T : struct, IComparable<T>` |
| `unmanaged` + `struct` | **불가** | `unmanaged`가 `struct`를 함의한다 |
| `unmanaged` + `new()` | **불가** | 같은 이유 |
| `unmanaged` + 인터페이스 | 가능 | |
| `notnull` + `class` / `struct` | **불가** | 셋 다 주 제약 |
| `notnull` + 인터페이스 + `new()` | 가능 | |
| 나체 타입 제약 + 다른 제약 | 가능 | `where U : T, IDisposable` |
| `allows ref struct` | 항상 맨 끝 | 반제약은 다른 모든 제약 뒤에 온다 |

### `allows ref struct` ※C# 13

C# 13이 추가한 것은 제약이 아니라 **반(反)제약(anti-constraint)** 이다. 제약이 "타입 인자가 만족해야 할 조건"을 더한다면, 반제약은 "원래 금지되던 것을 허용"한다.

`ref struct`(16.6절, 68.1절)는 오랫동안 타입 인자가 될 수 없었다. `Span<T>`를 `List<Span<int>>`에 넣을 수 없었다는 뜻이다. 스택에만 살아야 하는 타입이 힙에 올라가는 것을 막기 위한 규칙이었다. C# 13은 "이 타입 매개변수는 `ref struct`도 받겠다"고 선언할 길을 열었다.

```csharp
public static bool AnyMatch<T>(T source, Func<T, bool> predicate)
    where T : allows ref struct
{
    return predicate(source);
}
```

대신 `T`에 대해 할 수 있는 일이 줄어든다. `T`를 `object`로 박싱할 수 없고, 필드에 저장할 수 없고, 배열의 요소로 만들 수 없고, `allows ref struct`를 선언하지 않은 다른 제네릭(`List<T>` 등)의 타입 인자로 넘길 수도 없다. 컴파일러가 `T`를 `ref struct`인 것처럼 취급해 전부 막는다.

> **💡 반제약은 "허용"이 아니라 "포기"로 읽어야 한다**
>
> `allows ref struct`를 붙이는 순간 그 타입 매개변수로 할 수 있는 일이 대폭 줄어든다. 그래서 이것을 무턱대고 붙이는 것은 손해다. `Span<T>`를 받아야 하는 저수준 유틸리티(비교자, 파서, 포매터)에서만 쓴다. 라이브러리 API 하나에 붙였다가 그 API가 내부에서 `T`를 캐시하지 못하게 되어 되돌리는 일이 흔하다.

### 재정의와 제약

가상 제네릭 메서드를 재정의할 때는 규칙이 하나 더 있다.

```csharp
internal class Base {
    public virtual void M<T1, T2>() where T1 : struct where T2 : class { }
}

internal sealed class Derived : Base {
    public override void M<T3, T4>()
        where T3 : EventArgs   // 오류
        where T4 : class       // 오류 — 같은 제약을 다시 써도 오류다
    { }
}
```

```text
error CS0460: Constraints for override and explicit interface implementation
methods are inherited from the base method, so they cannot be specified directly.
```

**재정의 메서드는 제약을 상속하며 다시 쓸 수 없다.** 이름은 바꿔도 된다(`T1`→`T3`). 인터페이스 메서드를 구현할 때도 같다. 유일한 예외가 ※C# 9의 `where T : default`로, 널 허용 문맥에서 "이 타입 매개변수는 `class`도 `struct`도 아닌 무제약"임을 밝히기 위해서만 쓴다.

### 제약의 IL 표현

제약은 메타데이터에 그대로 남는다. `ildasm`으로 보면 이렇다.

```il
// where T : IComparable<T>
.method public hidebysig static !!T  Max<([System.Runtime]System.IComparable`1<!!T>) T>
        (!!T a, !!T b) cil managed

// where T : class          →  .method ... void M<class T>()
// where T : new()          →  .method ... void M<.ctor T>()
// where T : struct         →  .method ... void
//                              M<valuetype .ctor ([System.Runtime]System.ValueType) T>()
```

`class` 제약은 `class` 플래그, `new()` 제약은 `.ctor` 플래그, `struct` 제약은 `valuetype .ctor (System.ValueType)`의 조합으로 인코딩된다. 인터페이스·기반 클래스 제약은 괄호 안에 타입 이름으로 들어간다. **제약이 메타데이터에 있다는 사실이 중요하다.** 덕분에 다른 어셈블리를 참조하는 컴파일러도, 리플렉션도, JIT도 제약을 볼 수 있다. C++ 템플릿과 갈라지는 지점이다(23.12절).

## 23.7 제네릭 타입의 서브클래싱과 자기 참조 제네릭 선언

### 세 가지 파생 방식

제네릭 클래스는 비제네릭 클래스와 똑같이 상속할 수 있다. 파생 클래스가 기반 타입의 타입 매개변수를 어떻게 처리하느냐에 따라 세 가지다.

**(1) 열어 둔 채로 넘긴다.**

```csharp
class Stack<T>        { /* ... */ }
class SpecialStack<T> : Stack<T> { /* ... */ }
```

**(2) 구체 타입으로 닫는다.**

```csharp
class IntStack : Stack<int> { /* ... */ }
```

**(3) 새 타입 인자를 추가한다.**

```csharp
class List<T>            { /* ... */ }
class KeyedList<T,TKey> : List<T> { /* ... */ }
```

> **📌 엄밀히 말하면 파생 타입의 타입 인자는 전부 새것이다**
>
> 파생 타입이 기반 타입의 타입 인자를 "닫았다가 다시 연다"고 보는 편이 정확하다. 그래서 파생 클래스는 다시 여는 타입 인자에 **새 이름**을 붙일 수 있다.
>
> ```csharp
> class List<T> { /* ... */ }
> class KeyedList<TElement,TKey> : List<TElement> { /* ... */ }
> ```

### 상속 계층은 타입 인자와 무관하다

여기서 가장 자주 나오는 오해를 짚어야 한다. **타입 인자를 지정하는 것은 상속 계층과 아무 관계가 없다.**

제네릭 타입에 타입 인자를 주면 CLR에 새 타입 객체가 정의되고, **그 새 타입 객체는 제네릭 타입이 원래 파생된 타입에서 파생된다.**

- `List<T>`가 `Object`에서 파생되므로 `List<String>`과 `List<Guid>`도 `Object`에서 파생된다.
- `DictionaryStringKey<TValue>`가 `Dictionary<String, TValue>`에서 파생되므로 `DictionaryStringKey<Guid>`는 `Dictionary<String, Guid>`에서 파생된다.

`List<String>`이 `List<Object>`에서 파생되는 것은 **아니다.** `String`이 `Object`에서 파생된다는 사실은 이 관계에 아무 영향을 주지 않는다. 이 규칙을 이해하면 어떤 캐스트가 되고 안 되는지가 저절로 정리된다. (예외적으로 변성 표시가 붙은 인터페이스와 델리게이트만 다른 규칙을 따르고, 그게 23.10절이다.)

### 연결 리스트로 보는 설계 선택

```csharp
internal sealed class Node<T> {
    public T m_data;
    public Node<T> m_next;

    public Node(T data) : this(data, null) { }
    public Node(T data, Node<T> next) { m_data = data; m_next = next; }

    public override String ToString() {
        return m_data.ToString() +
            ((m_next != null) ? m_next.ToString() : String.Empty);
    }
}
```

```csharp
Node<Char> head = new Node<Char>('C');
head = new Node<Char>('B', head);
head = new Node<Char>('A', head);
Console.WriteLine(head.ToString());   // "ABC"
```

`m_next` 필드가 `Node<T>`이므로 **모든 노드의 데이터 타입이 같아야 한다.** 한 노드는 `Char`, 다른 노드는 `DateTime`인 리스트는 만들 수 없다. `Node<Object>`로 통일하면 되지만 그러면 컴파일 타임 타입 안전을 잃고 값 타입은 박싱된다.

해법은 **비제네릭 기반 클래스 + 제네릭 파생 클래스**다.

```csharp
internal class Node {
    protected Node m_next;
    public Node(Node next) { m_next = next; }
}

internal sealed class TypedNode<T> : Node {
    public T m_data;

    public TypedNode(T data) : this(data, null) { }
    public TypedNode(T data, Node next) : base(next) { m_data = data; }

    public override String ToString() {
        return m_data.ToString() +
            ((m_next != null) ? m_next.ToString() : String.Empty);
    }
}
```

```csharp
Node head = new TypedNode<Char>('.');
head = new TypedNode<DateTime>(DateTime.Now, head);
head = new TypedNode<String>("Today is ", head);
Console.WriteLine(head.ToString());
```

노드마다 타입이 다르면서, 각 노드는 자기 타입에 대해 안전하고, 값 타입은 박싱되지 않는다. "연결 구조는 비제네릭 층에서, 데이터는 제네릭 층에서"라는 이 분리는 실무에서 반복되는 패턴이다.

### 자기 참조 제네릭 선언

타입이 자기 자신을 타입 인자로 지정하는 것은 완전히 합법이다.

```csharp
public interface IEquatable<T> { bool Equals (T obj); }

public class Balloon : IEquatable<Balloon>
{
    public string Color { get; set; }
    public int CC { get; set; }

    public bool Equals (Balloon b)
    {
        if (b == null) return false;
        return b.Color == Color && b.CC == CC;
    }
}
```

`IEquatable<Balloon>`을 구현하는 `Balloon` — 이게 **자기 참조 제네릭(self-referencing generic)** 이다. 이 패턴 덕분에 `Equals`의 매개변수가 `object`가 아니라 `Balloon`이 되고, 캐스트와 (구조체라면) 박싱이 사라진다. `IEquatable<T>`, `IComparable<T>`가 전부 이 패턴을 전제로 설계됐다(25.2절, 25.6절).

제약 자리에 자기 참조를 쓰는 형태가 더 흥미롭다.

```csharp
class Foo<T> where T : IComparable<T> { /* ... */ }
class Bar<T> where T : Bar<T>         { /* ... */ }
```

첫 줄은 "`T`는 자기 자신과 비교 가능해야 한다"는 뜻이다. 둘째 줄은 흔히 **CRTP(curiously recurring template pattern)** 라 불리는 것으로, "`T`는 `Bar<T>`에서 파생된 타입이어야 한다"고 요구한다.

```csharp
public abstract class Entity<T> where T : Entity<T>
{
    public int Id { get; init; }

    // 반환 타입이 T다 — 파생 타입에서 캐스트 없이 체이닝된다
    public T Self() => (T)this;
}

public sealed class Order : Entity<Order> { /* ... */ }
```

> **⚠️ CRTP는 계약을 완전히 강제하지 못한다**
>
> `where T : Bar<T>`는 "`T`가 `Bar<T>`에서 파생"만 요구할 뿐, "`T`가 **바로 그** 파생 타입"임을 요구하지 못한다. 다음이 그대로 컴파일된다.
>
> ```csharp
> public sealed class Invoice : Entity<Order> { }   // 컴파일된다
> ```
>
> `Invoice`가 `Entity<Order>`를 상속했으니 `Invoice` 인스턴스의 `Self()`는 `Order`를 반환한다고 선언되고, 실제로 호출하면 `(Order)this` 캐스트가 실패해 `InvalidCastException`이 난다. 의도와 정반대인데 컴파일러는 막지 않는다. CRTP는 **관용구이지 보증이 아니다.** 정말 강제하고 싶다면 생성자를 `protected`로 막고 봉인하는 등의 추가 장치가 필요하며, 대개는 그만한 값어치가 없다. C# 11의 정적 추상 인터페이스 멤버(22.7절)가 이 패턴이 하려던 일의 상당 부분을 더 깔끔하게 처리한다.

## 23.8 제네릭 타입의 정적 데이터 — 인스턴스별 분리

### 코드로 증명하기

CLR은 타입의 정적 필드를 **타입 객체 안에** 할당한다(54.5절). 그리고 닫힌 제네릭 타입 각각이 자기만의 타입 객체를 가진다. 결론은 하나다. **닫힌 타입마다 정적 필드가 따로 존재한다.**

```csharp
Console.WriteLine (++Bob<int>.Count);      // 1
Console.WriteLine (++Bob<int>.Count);      // 2
Console.WriteLine (++Bob<string>.Count);   // 1
Console.WriteLine (++Bob<object>.Count);   // 1

class Bob<T> { public static int Count; }
```

`Bob<int>.Count`와 `Bob<string>.Count`와 `Bob<object>.Count`는 **서로 다른 세 개의 정수**다. `List<T>`가 정적 필드를 정의했다면 그 필드는 `List<DateTime>`과 `List<String>` 사이에 공유되지 않는다.

메모리 그림으로 보면 이렇다.

```text
                    ┌───────────────────────────────┐
                    │  Bob`1  (열린 타입 — 정의)      │
                    │  인스턴스 생성 불가             │
                    └───────────────────────────────┘
                              │  닫는다
        ┌─────────────────────┼─────────────────────┐
        ▼                     ▼                     ▼
┌───────────────┐    ┌───────────────┐    ┌───────────────┐
│ Bob`1<int>    │    │ Bob`1<string> │    │ Bob`1<object> │
│ 타입 객체       │    │ 타입 객체       │    │ 타입 객체       │
│ ┌───────────┐ │    │ ┌───────────┐ │    │ ┌───────────┐ │
│ │ Count = 2 │ │    │ │ Count = 1 │ │    │ │ Count = 1 │ │
│ └───────────┘ │    │ └───────────┘ │    │ └───────────┘ │
└───────────────┘    └───────────────┘    └───────────────┘
```

### 정적 생성자도 닫힌 타입마다 실행된다

같은 규칙이 정적 생성자에도 적용된다. 제네릭 타입이 정적 생성자를 정의하면, 그 생성자는 **닫힌 타입 하나당 한 번씩** 실행된다.

```csharp
class Registry<T>
{
    public static readonly string Name;

    static Registry()
    {
        Name = typeof(T).Name;
        Console.WriteLine($"정적 생성자 실행: {Name}");
    }
}

// 실행
_ = Registry<int>.Name;      // "정적 생성자 실행: Int32"
_ = Registry<int>.Name;      // (아무것도 출력되지 않는다)
_ = Registry<string>.Name;   // "정적 생성자 실행: String"
```

이 성질이 유용한 관용구를 만들어 낸다.

> **💡 타입별 캐시를 정적 제네릭 필드로 만들기**
>
> "타입마다 한 번만 계산하고 그 뒤로는 필드 읽기"라는 패턴을 딕셔너리 없이 구현할 수 있다.
>
> ```csharp
> internal static class SerializerCache<T>
> {
>     // T마다 정확히 한 번 실행된다. 락도, 딕셔너리 조회도 없다
>     public static readonly PropertyInfo[] Properties =
>         typeof(T).GetProperties(BindingFlags.Public | BindingFlags.Instance);
> }
>
> // 사용
> foreach (var p in SerializerCache<Order>.Properties) { /* ... */ }
> ```
>
> `Dictionary<Type, PropertyInfo[]>` 캐시와 비교하면 해시 계산도, 버킷 탐색도, 동시성 제어도 없다. 정적 필드 하나를 읽는 것이 전부이고, JIT이 인라인하면 상수 로드로까지 줄어든다. 리플렉션 캐싱의 표준 기법이고 57.12절에서 다시 다룬다.

> **⚠️ 정적 제네릭 필드는 조용히 메모리를 먹는다**
>
> 좋은 성질에는 대가가 있다. `Cache<T>`에 큰 객체를 담아 두면 **`T`의 종류만큼** 그 객체가 생긴다. 게다가 정적 필드는 그 타입이 로드된 어셈블리 로드 컨텍스트가 언로드되기 전에는 수거되지 않는다(52장). 제네릭 정적 필드에 컬렉션을 두고 계속 채우는 코드는 사실상 누수다.
>
> 더 미묘한 문제도 있다. `Cache<T>`의 정적 생성자가 예외를 던지면 `TypeInitializationException`이 나고, **그 닫힌 타입은 그 뒤로 영원히 못 쓴다.** CLR이 초기화 실패 상태를 기억해서 이후 모든 접근에 같은 예외를 다시 던진다. `Cache<int>`가 죽어도 `Cache<string>`은 멀쩡하다는 점이 디버깅을 더 헷갈리게 만든다.

> **⚠️ 스레드 안전은 공짜가 아니다**
>
> 정적 생성자의 실행 자체는 CLR이 스레드 안전하게 보장한다. 하지만 그 뒤에 정적 필드를 **쓰는** 코드는 보장 대상이 아니다. `Counter<T>.Count++`를 여러 스레드에서 부르면 그냥 경합이다. 타입 매개변수로 분리되어 있다는 사실이 동기화를 대신해 주지 않는다(48장).

## 23.9 타입 매개변수와 변환

### 왜 `(StringBuilder) arg`가 컴파일되지 않는가

C#의 캐스트 연산자는 여러 종류의 변환을 수행한다.

- 숫자 변환
- 참조 변환
- 박싱/언박싱 변환
- 사용자 정의 변환 (연산자 오버로딩, 22.4절)

**어떤 종류의 변환을 할지는 컴파일 타임에 피연산자의 알려진 타입을 보고 결정된다.** 그런데 제네릭 타입 매개변수는 컴파일 타임에 정확한 타입을 모른다. 모호하면 컴파일러는 오류를 낸다.

가장 흔한 경우가 참조 변환이다.

```csharp
StringBuilder Foo<T> (T arg)
{
    if (arg is StringBuilder)
        return (StringBuilder) arg;      // 컴파일되지 않는다
    // ...
}
```

`T`의 실제 타입을 모르는 상태에서 컴파일러는 "혹시 사용자 정의 변환을 의도한 건 아닐까" 하고 걱정한다. 그래서 거부한다.

### 해법 1 — `as` 연산자

```csharp
StringBuilder Foo<T> (T arg)
{
    StringBuilder sb = arg as StringBuilder;
    if (sb != null) return sb;
    // ...
}
```

`as`는 **사용자 정의 변환을 절대 수행하지 않으므로** 모호하지 않다. 참조 변환(또는 널 가능 언박싱)만 한다.

### 해법 2 — `object`를 경유하기

더 일반적인 해법은 먼저 `object`로 캐스트하는 것이다.

```csharp
return (StringBuilder) (object) arg;
```

`object`로/에서의 변환은 **사용자 정의 변환이 아니라고 가정된다.** 참조 변환이거나 박싱/언박싱 변환이다. `StringBuilder`가 참조 타입이므로 여기서는 참조 변환이 된다.

언박싱도 같은 문제를 낳는다.

```csharp
int Foo<T> (T x) => (int) x;             // 컴파일 오류
```

이건 언박싱일 수도, 숫자 변환일 수도, 사용자 정의 변환일 수도 있다. 해법은 같다.

```csharp
int Foo<T> (T x) => (int) (object) x;    // 명백한 언박싱
```

정리하면 이렇다.

```csharp
static void Cast1<T>(T obj) {
    Int32 x = (Int32) obj;               // 오류
    String s = (String) obj;             // 오류
}
static void Cast2<T>(T obj) {
    Int32 x = (Int32) (Object) obj;      // 컴파일된다
    String s = (String) (Object) obj;    // 컴파일된다
}
static void Cast3<T>(T obj) {
    String s = obj as String;            // 컴파일된다
}
```

> **⚠️ 컴파일이 된다고 안전해진 것이 아니다**
>
> `(Int32)(Object) obj`는 컴파일러의 모호성 불평을 잠재울 뿐이다. 런타임에 `T`가 `Int32`가 아니면 여전히 `InvalidCastException`이 난다. `object` 경유 캐스트는 **"내가 무슨 변환인지 알고 있으니 그대로 해라"** 는 지시이지 검사가 아니다. 안전이 필요하면 `is`로 먼저 확인하거나 `as` + 널 검사를 쓴다.

> **⚠️ `x as T`는 `T`에 참조 타입 제약이 필요하다**
>
> 방향에 주의해야 한다. **`T` 타입 값을 참조 타입으로** 변환하는 `obj as String`은 제약 없이 된다. 반대로 **어떤 값을 `T`로** 변환하는 `something as T`는 `T`가 참조 타입이라는 보장이 없으면 거부된다.
>
> ```csharp
> static T Convert<T>(object o) => o as T;   // 오류 CS0413
> static T Convert2<T>(object o) where T : class => o as T;   // OK
> ```
>
> `as`는 실패하면 `null`을 반환해야 하는데, `T`가 값 타입이면 `null`을 반환할 수가 없기 때문이다.

### 패턴 매칭 우회 ※C# 7.1

C# 7.1부터는 제네릭에 대한 패턴 매칭이 정리되어, 캐스트 대신 패턴을 쓰는 쪽이 더 읽기 좋다.

```csharp
static void PatternMatching<T>(Point<T> p)
{
    switch (p)
    {
        case Point<string> pString:
            Console.WriteLine("Point is based on strings");
            return;
        case Point<int> pInt:
            Console.WriteLine("Point is based on ints");
            return;
    }
}
```

`is` 패턴은 캐스트 종류를 결정할 필요가 없다 — **런타임 타입 검사**이기 때문이다. 그래서 모호성 오류가 나지 않는다. 이 방식이 23.14절의 "런타임 타입 검사로 특수화하기"의 문법적 토대다.

### 값 타입에 대한 `is`는 박싱하지 않는다

```csharp
static bool IsPositive<T>(T value)
{
    if (value is int i) return i > 0;      // 박싱이 일어나지 않는다
    return false;
}
```

JIT이 `T`마다 코드를 특수화하므로(23.11절), `T`가 `int`인 인스턴스화에서 이 검사는 상수 `true`로 접히고 `value`는 그대로 레지스터에 남는다. `T`가 `string`인 인스턴스화에서는 검사 전체가 `false`로 접혀 사라진다. `object`를 받아 `is int`로 검사하는 코드와는 전혀 다른 기계어가 나온다.

### 제네릭 타입 변수끼리의 비교

```csharp
private static void ComparingTwoGenericTypeVariables<T>(T o1, T o2) {
    if (o1 == o2) { }     // 오류
}
```

`T`가 무제약이면 컴파일되지 않는다. 참조 타입 변수 둘을 비교하는 것은 합법이지만, 값 타입 변수 둘은 그 타입이 `==`를 오버로드하지 않는 한 비교할 수 없기 때문이다.

| `T`의 제약 | `o1 == o2` |
|---|---|
| 무제약 | 컴파일 오류 |
| `where T : class` | 참조 동등성 비교 (같은 객체인지) |
| `where T : class`이고 그 클래스가 `==`를 오버로드 | 오버로드된 `==` 호출 |
| `where T : struct` | 컴파일 오류 |
| `where T : IEquatable<T>` | `==`는 여전히 오류. `o1.Equals(o2)`를 쓴다 |

> **⚠️ 제네릭 코드에서는 `==` 대신 `EqualityComparer<T>.Default`를 쓴다**
>
> 제네릭 안에서 두 값이 같은지 확인하는 표준 방법은 이것이다.
>
> ```csharp
> static bool AreSame<T>(T a, T b) => EqualityComparer<T>.Default.Equals(a, b);
> ```
>
> `EqualityComparer<T>.Default`는 `T`가 `IEquatable<T>`를 구현하면 그것을 쓰고, 아니면 `Object.Equals`로 내려간다. 값 타입에서 박싱을 피하고, `null` 처리도 알아서 한다. 순서 비교라면 `Comparer<T>.Default`가 같은 역할을 한다(25.7절).

### 연산자는 여전히 못 쓴다 — 그리고 그 예외

제네릭 타입 변수에 산술 연산자를 쓸 수 없다는 것이 오랫동안 CLR 제네릭의 대표적 한계였다. `struct` 제약을 걸고 `default(T)`로 초기화해도 세 개의 오류가 난다.

```csharp
private static T Sum<T>(T num) where T : struct {
    T sum = default(T);
    for (T n = default(T); n < num; n++)
        sum += n;                            // 아래 오류 세 개
    return sum;
}
```


```text
error CS0019: Operator '<'  cannot be applied to operands of type 'T' and 'T'
error CS0023: Operator '++' cannot be applied to operand of type 'T'
error CS0019: Operator '+=' cannot be applied to operands of type 'T' and 'T'
```

컴파일러가 컴파일 타임에 타입을 모르므로 어떤 `op_Addition`을 부를지 정할 수 없다. 과학·금융·수학 분야 개발자들이 오래 아쉬워한 지점이고, 리플렉션·`dynamic`·연산자 오버로딩을 동원한 우회책이 여럿 나왔지만 전부 심각한 성능 손해나 가독성 손해를 낳았다.

이 벽은 ※C# 11의 정적 추상 인터페이스 멤버로 무너졌다. `where T : INumber<T>` 제약 아래에서는 `a + b`가 그대로 컴파일된다. 자세한 것은 22.7절과 22.8절에 있다.

## 23.10 공변성(`out`)과 반공변성(`in`)

### 정의

`A`가 `B`로 변환 가능하다고 하자.

- `X<A>`가 `X<B>`로 변환 가능하면 `X`는 `T`에 대해 **공변(covariant)** 이다.
- `X<B>`가 `X<A>`로 변환 가능하면 `X`는 `T`에 대해 **반공변(contravariant)** 이다.
- 어느 쪽도 아니면 **불변(invariant)** 이다.

여기서 "변환 가능"은 **암시적 참조 변환**만을 뜻한다. `A`가 `B`를 상속하거나 `A`가 `B`를 구현하는 경우다. 숫자 변환, 박싱 변환, 사용자 정의 변환은 포함되지 않는다.

### 변성은 자동이 아니다

23.2절의 `Stack<T>`를 그대로 쓰되 계층을 하나 얹자.

```csharp
class Animal {}
class Bear : Animal {}
class Camel : Animal {}
```

```csharp
Stack<Bear> bears = new Stack<Bear>();
Stack<Animal> animals = bears;      // 컴파일 오류
```

정적 타입 안전을 지키기 위해 타입 매개변수는 기본적으로 불변이다. 이 제한이 없었다면 다음이 통과했을 것이다.

```csharp
animals.Push (new Camel());         // 곰 스택에 낙타를 넣는다
```

하지만 변성이 없으면 재사용성이 죽는다. `Stack<Animal>`을 받는 `Wash` 메서드에 `Stack<Bear>`를 넘길 수 없다. 우회책 하나는 제약을 쓰는 것이다 — `static void Wash<T>(Stack<T> animals) where T : Animal`. 더 나은 해법은 변성 표시가 붙은 인터페이스다.

### 공변성 `out`

인터페이스와 델리게이트의 타입 매개변수에 `out` 수정자를 붙이면 공변이 된다.

```csharp
public interface IPoppable<out T> { T Pop(); }
```

`out`은 "`T`가 **출력 위치에서만** 쓰인다"는 선언이다. 출력 위치란 메서드 반환 타입, 프로퍼티 get 접근자, 그리고 일부 델리게이트 위치다.

```csharp
var bears = new Stack<Bear>();
bears.Push (new Bear());

// Stack<Bear>가 IPoppable<Bear>를 구현한다. IPoppable<Animal>로 변환할 수 있다
IPoppable<Animal> animals = bears;      // 합법
Animal a = animals.Pop();
```

이 변환이 안전한 이유는 단순하다. 컴파일러가 막으려던 사고 — 곰 스택에 낙타를 밀어 넣는 것 — 이 **일어날 수 없다.** `T`가 출력 위치에만 나타나는 인터페이스로는 낙타를 집어넣을 통로 자체가 없다.

이제 `Wash`는 `IPoppable<Animal>`을 받도록 쓰면 되고, 곰 스택이든 낙타 스택이든 그대로 넘어간다.

공변 타입 매개변수를 입력 위치(메서드 매개변수, 쓰기 가능 프로퍼티)에 쓰면 컴파일러가 오류를 낸다.

### 반공변성 `in`

반대 방향이다. 타입 매개변수가 **입력 위치에만** 나타나면 `in`을 붙일 수 있다.

```csharp
public interface IPushable<in T> { void Push (T obj); }
```

```csharp
IPushable<Animal> animals = new Stack<Animal>();
IPushable<Bear> bears = animals;        // 합법
bears.Push (new Bear());
```

`IPushable`에는 `T`를 내보내는 멤버가 없으므로, `animals`를 `bears`로 취급해도 사고가 나지 않는다. `Pop`할 방법이 없기 때문이다.

BCL의 실제 예다.

```csharp
public interface IComparer<in T> { int Compare (T a, T b); }

var objectComparer = Comparer<object>.Default;    // IComparer<object>를 구현한다
IComparer<string> stringComparer = objectComparer;
int result = stringComparer.Compare ("Brett", "Jemaine");
```

`object` 두 개를 비교할 줄 아는 비교자는 당연히 `string` 두 개도 비교할 수 있다.

### 어떤 위치에 무엇을 쓸 수 있는가

| 위치 | `out T` (공변) | `in T` (반공변) |
|---|---|---|
| 메서드 반환 타입, 인덱서 반환 타입 | 가능 | 불가 |
| 메서드 매개변수, 인덱서 매개변수 | 불가 | 가능 |
| `ref` / `out` 매개변수 | **불가** | **불가** |
| 읽기 전용 프로퍼티 (get) | 가능 | 불가 |
| 쓰기 전용 프로퍼티 (set) | 불가 | 가능 |
| 읽기·쓰기 프로퍼티 | 불가 | 불가 |
| 이벤트, 제네릭 제약 위치 | 불가 | 가능 |

`ref`/`out` 매개변수가 양쪽 다 불가인 이유는 명백하다 — 값이 양방향으로 흐른다.

```csharp
delegate void SomeDelegate<in T>(ref T t);
// error: Invalid variance: The type parameter 'T' must be invariantly valid on
// 'SomeDelegate<T>.Invoke(ref T)'. 'T' is contravariant.
```

> **⚠️ 메서드의 `out` 매개변수는 공변성 대상이 아니다**
>
> 이름이 같아서 헷갈리는데, 메서드 매개변수에 붙는 `out` 수정자와 타입 매개변수에 붙는 `out` 수정자는 완전히 다른 것이다. 그리고 `out`으로 표시된 메서드 매개변수는 **CLR의 제약 때문에** 공변성 대상이 되지 않는다. 값이 흘러나가는 위치이므로 논리적으로는 출력 위치인데도 그렇다.

### 클래스는 변성을 가질 수 없다

`out`/`in`은 **인터페이스와 델리게이트에만** 쓸 수 있다. 클래스에는 못 쓴다. 이유는 `Stack<T>` 하나로 설명된다. `Stack<T>`는 `IPushable<T>`와 `IPoppable<T>`를 **동시에** 구현할 수 있다. 두 인터페이스에서 `T`의 변성 표시가 정반대인데도 그렇다.

```csharp
public class Stack<T> : IPushable<T>, IPoppable<T> { /* ... */ }
```

가능한 이유는 **변성은 클래스가 아니라 인터페이스를 통해서만 행사되기 때문**이다. 변성 변환을 하려면 먼저 `IPoppable`이라는 렌즈를 쓸지 `IPushable`이라는 렌즈를 쓸지 결정해야 하고, 그 렌즈가 허용하는 연산으로 제한된다. 구체 구현은 보통 데이터가 양방향으로 흐르므로 변성을 가질 수 없다.

### 배열 공변성과 무엇이 다른가

배열은 역사적 이유로 공변성을 지원한다(9.6절). `B[]`는 `B`가 `A`를 상속하고 둘 다 참조 타입이면 `A[]`로 캐스트된다.

```csharp
Bear[] bears = new Bear[3];
Animal[] animals = bears;         // OK
animals[0] = new Camel();         // 런타임 오류
```

차이는 결정적이다.

| | 배열 공변성 | 제네릭 변성 |
|---|---|---|
| 선언 필요 | 없음 (자동) | `out`/`in` 명시 필요 |
| 안전성 | **안전하지 않다** — 런타임 검사로 막는다 | **완전히 타입 안전하다** |
| 실패 시점 | 런타임 `ArrayTypeMismatchException` | 컴파일 오류 |
| 쓰기 방향 | 허용해 놓고 런타임에 막는다 | 애초에 표현할 수 없다 |
| 런타임 비용 | 참조 타입 배열 저장마다 검사 | 없음 |
| 값 타입 | 불가 | 불가 |

배열은 "일단 허용하고 사고가 나면 예외를 던진다"이고, 제네릭 변성은 "사고가 날 수 있는 코드는 애초에 쓸 수 없다"이다. `out`을 붙였다면 쓰기 멤버가 인터페이스에 존재할 수 없으므로, 런타임 검사가 필요 없고 따라서 런타임 비용도 없다.

### 값 타입에는 왜 안 되는가

```csharp
IEnumerable<string> strings = new List<string>();
IEnumerable<object> objects = strings;      // OK

IEnumerable<int> ints = new List<int>();
IEnumerable<object> boxed = ints;           // 컴파일 오류
```

`int`는 `object`에서 파생되는데도 안 된다. 이유는 **변성이 참조 변환에만 적용되기 때문**이다. `int`에서 `object`로 가는 변환은 참조 변환이 아니라 **박싱 변환**이다.

왜 그 구분이 중요한가. 참조 변환은 **비트를 하나도 바꾸지 않는다.** `string` 참조와 `object` 참조는 같은 32/64비트 포인터이고, 변환은 컴파일러의 관점 변경일 뿐 런타임에는 아무 일도 일어나지 않는다. 그래서 `IEnumerable<string>`을 담고 있는 메모리를 `IEnumerable<object>`라고 부르기만 하면 된다.

박싱은 다르다. `int` 4바이트를 힙에 새로 할당된 객체로 **복사**해야 한다. `List<int>`가 내부에 갖고 있는 `int[]` 배열을 `object[]` 배열로 만들려면 요소 하나하나를 박싱해서 새 배열을 만들어야 한다. 이건 관점 변경이 아니라 데이터 변환이고, 참조 하나 대입하는 것으로는 절대 표현할 수 없다.

```text
참조 변환 (변성 가능)                박싱 변환 (변성 불가)
──────────────────────              ──────────────────────
strings ──┐                         ints  ──→ [4, 8, 15]   (int[] 그대로)
          ├──→ [힙의 List 객체]      boxed ──→ ??? 요소마다 새 힙 객체가
objects ──┘                                   필요하다 — 대입만으로 불가능
같은 포인터, 다른 컴파일 타임 타입
```

> **⚠️ 변성이 값 타입에 안 되면 API 설계가 갈린다**
>
> 원천 도서(*CLR via C#*)의 저자는 이 제한 때문에 "변성 기능이 그다지 유용하지 않다"고까지 말한다. 예를 보자.
>
> ```csharp
> void ProcessCollection(IEnumerable<Object> collection) { /* ... */ }
> ```
>
> 이 메서드에 `List<DateTime>`을 넘길 수 없다. 해법은 제네릭 메서드로 바꾸는 것이다.
>
> ```csharp
> void ProcessCollection<T>(IEnumerable<T> collection) { /* ... */ }
> ```
>
> 대신 JIT 코드가 늘어난다. `IEnumerable<Object>` 버전은 JIT 코드가 하나뿐이다. 제네릭 버전은 모든 참조 타입 `T`가 코드 하나를 공유하지만, 값 타입 `T`마다 새 코드가 생긴다. 대신 값 타입 컬렉션을 넘길 수 있게 된다. 트레이드오프를 알고 고르는 것이지, 한쪽이 늘 옳은 게 아니다.

> **📌 `in`/`out`을 붙일 수 있으면 붙여라**
>
> 인터페이스나 델리게이트를 설계할 때 `in`/`out`을 명시하는 데는 아무 부작용이 없고, 그 타입을 쓸 수 있는 시나리오만 늘어난다. BCL은 `IEnumerable<out T>`, `IEnumerator<out T>`, `IComparer<in T>`, `Func<in T, out TResult>`, `Action<in T>` 전부에 변성을 붙여 놓았다.
>
> `IEquatable<T>`가 불변인 것은 실수가 아니다. 정의상 `Planet`은 `Moon`과 같을 수 없다. 타입이 다르면 동등할 수 없으므로 변성이 의미를 갖지 않는다. `IList<T>`가 불변인 것도 같은 이유다 — 인덱서가 읽기·쓰기 양쪽이다.

> **💡 왜 컴파일러가 알아서 추론해 주지 않는가**
>
> 컴파일러가 인터페이스 선언을 분석해 변성을 자동 판정할 수는 있다. 그런데 C# 팀은 일부러 명시를 요구했다. 변성은 **계약**이기 때문이다. 자동 추론이라면, 나중에 인터페이스에 멤버 하나를 추가해 `T`가 출력 위치에 나타나는 순간 그 타입 매개변수는 조용히 불변이 되고, 반공변성에 의존하던 **호출부 전부가 갑자기 깨진다.** 명시를 강제하면 그 순간 인터페이스 선언 자체에서 오류가 나므로 계약을 깨고 있다는 사실을 즉시 알 수 있다.

## 23.11 CLR의 제네릭 인프라 — 값 타입은 코드 특수화, 참조 타입은 코드 공유

### JIT이 하는 일

제네릭 타입 매개변수를 쓰는 메서드가 JIT 컴파일될 때, CLR은 그 메서드의 IL을 가져와 **지정된 타입 인자를 치환하고**, 그 데이터 타입에 특화된 네이티브 코드를 만든다. `Stack<int>.Push`의 기계어에는 `int`를 다루는 명령이 직접 박혀 있다. 박싱도, 캐스트도, 간접 호출도 없다.

이것이 제네릭의 핵심 기능이자 성능 이득의 출처다. 그런데 문제가 하나 따라온다.

### 코드 폭발(code explosion)

CLR은 **메서드/타입 조합마다** 네이티브 코드를 계속 만든다. 이것을 코드 폭발이라 부른다. 애플리케이션의 워킹 셋(working set)이 크게 늘어나고, 그것이 다시 성능을 갉아먹는다. 코드가 많아지면 명령 캐시 적중률이 떨어지고, JIT 시간이 늘고, 시작이 느려진다.

CLR에는 이를 줄이는 최적화가 둘 있다.

**최적화 1 — 같은 조합은 한 번만 컴파일한다.** 한 어셈블리가 `List<DateTime>`을 쓰고 완전히 다른 어셈블리(같은 AppDomain에 로드된)가 또 `List<DateTime>`을 써도 코드는 한 벌이다.

**최적화 2 — 모든 참조 타입 인자를 동일하게 취급한다.** `List<String>`의 메서드로 컴파일된 코드가 `List<Stream>`의 메서드에 그대로 쓰인다.

이 최적화가 가능한 이유는 명확하다. **모든 참조 타입 인자와 변수는 결국 힙 객체를 가리키는 포인터**다. 32비트에서 32비트, 64비트에서 64비트. 그리고 객체 포인터는 전부 똑같은 방식으로 조작된다.

값 타입은 다르다. 타입 인자가 값 타입이면 CLR은 **그 값 타입 전용 네이티브 코드를 반드시 따로 만들어야** 한다. 이유는 둘이다.

1. 값 타입은 크기가 제각각이다. `byte`는 1바이트, `Guid`는 16바이트, 큰 구조체는 수십 바이트다.
2. **크기가 같아도** 코드를 공유할 수 없다. `Int32`와 `UInt32`는 둘 다 32비트지만, 이 값들을 다루는 네이티브 CPU 명령이 다를 수 있다.

### 그림으로 보기

```text
        IL 하나                          네이티브 코드
   ┌──────────────────┐
   │ List`1<T>::Add   │
   └────────┬─────────┘
            │ JIT
   ┌────────┴──────────────────────────────────────────┐
   │                                                   │
   ▼                                                   ▼
[참조 타입 인스턴스화]                          [값 타입 인스턴스화]
List<string>  ─┐                              List<int>    → 코드 #2
List<Stream>  ─┼─→ 정규(canonical) 코드 #1     List<double> → 코드 #3
List<Order>   ─┤    (전부 공유)                List<Guid>   → 코드 #4
List<object>  ─┘                              List<MyStruct> → 코드 #5
```

.NET 런타임(CoreCLR)은 이 "정규 인스턴스화"를 표현하려고 `System.__Canon`이라는 내부 타입을 쓴다. 디버거나 프로파일러에서 `List<__Canon>` 같은 이름이 보이는 이유가 이것이다. 모든 참조 타입 인스턴스화가 이 한 벌의 코드를 공유한다.

### 이것이 왜 성능과 코드 크기에 **동시에** 영향을 주는가

여기가 이 절의 요점이다.

| | 값 타입 인스턴스화 | 참조 타입 인스턴스화 |
|---|---|---|
| 네이티브 코드 | 타입마다 별도 생성 | 전부 공유 (`__Canon`) |
| 박싱 | 없음 | 해당 없음 |
| 필드/배열 저장 | 인라인 저장 | 포인터 저장 |
| 메서드 호출 | 정적 바인딩·인라인 가능 | 정규 코드라 인라인 기회가 적다 |
| 코드 크기 | **N개 타입 → N벌** | 1벌 |
| 워킹 셋 | 늘어난다 | 늘지 않는다 |
| 타입 정보가 필요한 곳 | 코드에 상수로 박힌다 | **런타임 조회가 필요하다** |

두 축이 서로 반대 방향으로 움직인다.

- **값 타입 특수화의 이득** — `Dictionary<int, int>`의 조회 루프에서 `int` 비교가 CPU 명령 한 개로 내려간다. `EqualityComparer<int>.Default.Equals`가 인라인되어 사라진다. 박싱도, 가상 호출도 없다. 손으로 쓴 전용 코드와 같은 기계어가 나온다.
- **값 타입 특수화의 비용** — `Dictionary<TKey,TValue>`를 값 타입 조합 20가지로 쓰는 프로그램은 딕셔너리 코드 20벌을 갖게 된다. 시작 시간과 메모리가 늘고, Native AOT 빌드에서는 바이너리 크기가 늘어난다.
- **참조 타입 공유의 이득** — 코드가 한 벌이다.
- **참조 타입 공유의 비용** — 공유 코드는 자기가 지금 `T`가 무엇인지 모른다. `new T[]`, `typeof(T)`, 정적 필드 접근처럼 실제 타입이 필요한 자리에서는 런타임에 **제네릭 딕셔너리 조회**를 해야 한다. 값 타입 경로에서는 상수인 것이 참조 타입 경로에서는 간접 참조 한 번이 된다.

> **💡 성능이 중요한 제네릭에서 값 타입 인자를 쓰는 이유**
>
> `List<int>`가 `List<object>`보다 빠른 것은 박싱이 없어서만이 아니다. **인라이닝이 가능해서**이기도 하다. `T`가 `int`로 확정된 코드에서는 JIT이 비교자를 통째로 인라인하고 경계 검사를 지우고 루프를 벡터화할 수 있다. `__Canon` 공유 코드에서는 그럴 수 없다. 이것이 22.8절에서 "제네릭 수학의 값 타입 경로에는 추상화 비용이 없다"고 말한 문장의 정확한 근거다.

> **⚠️ 값 타입 인스턴스화를 남발하면 시작이 느려진다**
>
> 값 타입 타입 인자를 조합해서 만들어지는 인스턴스화 개수는 곱셈으로 늘어난다. `Dictionary<TKey,TValue>`에 값 타입 키 5개와 값 타입 값 5개를 쓰면 25벌이다. 여기에 `List<KeyValuePair<TKey,TValue>>`, `IEnumerable<...>` 같은 파생 인스턴스화가 딸려 온다. Native AOT나 시작 시간이 중요한 서비스에서는 이 곱셈이 실제 문제가 된다. 진단은 측정으로만 가능하다(67장, 55.7절).

> **⚠️ 이 최적화는 제네릭 코드를 "무료"로 만들지 않는다**
>
> 원천 도서의 경고를 그대로 옮긴다. **CLR은 특정 데이터 타입으로 메서드가 처음 호출될 때마다 네이티브 코드를 생성한다.** 이것이 워킹 셋 크기를 늘리고 성능을 해친다. 제네릭이 언제나 이득이라는 서술은 정확하지 않다 — 값 타입에서 얻는 것이 크고, 참조 타입에서는 코드 크기 손해 없이 타입 안전만 얻는다.

### 제네릭 타입 동일성

이 인프라가 낳는 실무적 함정이 하나 있다. 꺾쇠가 많아 읽기 힘들다는 이유로 이런 클래스를 만드는 사람이 있다.

```csharp
internal sealed class DateTimeList : List<DateTime> {
    // 아무 코드도 넣을 필요가 없다
}
```

```csharp
DateTimeList dtl = new DateTimeList();     // 꺾쇠 없이 깔끔하다
```

> **⚠️ 가독성을 위해 파생 클래스를 만들지 마라**
>
> **타입 동일성(type identity)과 동등성(equivalence)을 잃는다.**
>
> ```csharp
> Boolean sameType = (typeof(List<DateTime>) == typeof(DateTimeList));   // false
> ```
>
> 서로 다른 두 타입 객체를 비교하고 있으므로 `false`다. 그리고 `DateTimeList`를 받는 메서드에 `List<DateTime>`을 넘길 수 없다. 반대 방향 — `List<DateTime>`을 받는 메서드에 `DateTimeList`를 넘기는 것 — 은 파생 관계라 가능하다. 이 비대칭이 사람을 헷갈리게 한다.
>
> 올바른 해법은 **using 별칭 지시문**이다.
>
> ```csharp
> using DateTimeList = System.Collections.Generic.List<System.DateTime>;
> ```
>
> 이건 `DateTimeList`라는 **심볼**을 정의할 뿐이다. 컴파일러가 모든 `DateTimeList`를 `System.Collections.Generic.List<System.DateTime>`으로 치환한다. 타입 동일성이 그대로 유지되므로 위 비교가 `true`가 된다. 지역 변수라면 `var`를 쓰면 된다.

## 23.12 C# 제네릭 vs C++ 템플릿

### 합성(synthesis)이 언제 일어나는가

C# 제네릭과 C++ 템플릿은 **용도가 비슷하고 동작 방식이 완전히 다르다.** 두 경우 모두 생산자의 자리표시자 타입을 소비자가 채우는 합성이 일어나야 한다. 차이는 **그 합성 시점**이다.

- **C# 제네릭** — 닫힌 타입을 만드는 합성이 **런타임**에 일어난다. 그래서 생산자 타입(`List<T>` 같은 열린 타입)을 라이브러리(`.dll`)로 컴파일해 배포할 수 있다.
- **C++ 템플릿** — 합성이 **컴파일 타임**에 일어난다. 그래서 템플릿 라이브러리를 `.dll`로 배포하지 못한다. 소스 코드로만 존재한다. 그리고 매개변수화된 타입을 런타임에 동적으로 조사하거나 만들어 내는 일이 어렵다.

### `Max`로 보는 결정적 차이

C#의 `Max`는 이렇게 써야 한다.

```csharp
static T Max <T> (T a, T b) where T : IComparable<T>
    => a.CompareTo (b) > 0 ? a : b;
```

이렇게는 못 쓴다.

```csharp
static T Max <T> (T a, T b) => (a > b ? a : b);     // 컴파일 오류
```

**`Max`는 단 한 번 컴파일되어 `T`의 모든 가능한 값에 대해 동작해야 하기 때문**이다. `>`는 모든 `T`에 대해 단일한 의미를 갖지 않는다. 아예 `>` 연산자가 없는 `T`도 있다. 컴파일이 성공할 수 없다.

C++ 템플릿은 정반대다.

```cpp
template <class T> T Max (T a, T b)
{
    return a > b ? a : b;
}
```

이 코드는 **`T`의 값마다 따로 컴파일된다.** 특정 `T`에서 `>`가 갖는 의미가 무엇이든 그것을 취하고, 그 `T`가 `>`를 지원하지 않으면 그때 컴파일에 실패한다.

이 차이가 낳는 결과가 하나 더 있다. C#에서는 **인스턴스화 시점의 타입이 더 좋은 메서드를 갖고 있어도 쓰이지 않는다.** 제네릭이 컴파일될 때 제약으로 명시된 것만 컴파일러가 볼 수 있기 때문이다. `T`가 `IEquatable<T>`를 구현하더라도, 제약에 그렇게 쓰여 있지 않으면 `left.Equals(right)`는 `System.Object.Equals`를 부른다.

### Java의 소거(erasure)와의 3자 비교

Java도 제네릭을 지원하지만 세 번째 길을 갔다. **타입 소거(type erasure)** — 컴파일러가 타입 검사를 끝낸 뒤 타입 인자를 지우고, 필요한 자리에 캐스트를 삽입한다. 런타임에는 제네릭 정보가 남지 않는다. `List<String>`과 `List<Integer>`는 런타임에 **같은 클래스**다. ※저자 보강

| | C# 제네릭 | C++ 템플릿 | Java 제네릭 |
|---|---|---|---|
| 합성 시점 | 런타임 (JIT) | 컴파일 타임 | 컴파일 타임 (소거) |
| 런타임 타입 정보 | **보존** — `typeof(T)` 가능 | 해당 없음 (별개 타입으로 존재) | **소실** — `T.class` 불가 |
| 라이브러리 배포 | 컴파일된 `.dll` 가능 | 소스 필요 (헤더) | 컴파일된 `.class` 가능 |
| 값 타입 (프리미티브) | **박싱 없음** | 박싱 개념 없음 | **박싱 필수** (`List<int>` 불가) |
| 코드 크기 | 값 타입마다 특수화, 참조 타입은 공유 | 인스턴스화마다 완전 복제 | 언제나 한 벌 |
| 제약 표현 | `where` 절 — 메타데이터에 기록 | 없었음 (C++20 concepts로 도입) | `extends` 바운드 |
| 오류 발생 시점 | 제네릭 **정의**를 컴파일할 때 | 제네릭을 **사용**할 때 | 제네릭 정의를 컴파일할 때 |
| 연산자 사용 | 불가 (C# 11의 정적 추상 멤버로 우회) | 가능 (덕 타이핑) | 불가 |
| 런타임 리플렉션 | 가능 (57.4절) | 불가 | 제한적 |
| 배열 생성 `new T[n]` | 가능 | 가능 | **불가** |

### 세 갈래가 각각 잃은 것

**C++ 템플릿이 잃은 것** — 배포 형태와 오류 메시지다. 템플릿 인스턴스화 오류는 사용 지점에서 터지고 메시지가 난해하기로 악명 높으며, 인스턴스화마다 완전한 코드 복제가 일어나 바이너리가 커진다. 얻은 것은 표현력이다. 제약 없이 `>`든 `.Foo()`든 쓸 수 있고 컴파일 타임 계산까지 가능하다.

**Java 소거가 잃은 것** — 런타임 타입 정보와 값 타입 성능이다. `List<int>`를 쓸 수 없고 `List<Integer>`를 써야 하므로, C#이 제네릭으로 해결한 박싱 문제를 Java는 아직 안고 있다. `new T[10]`도, `T`로 오버로드도, 타입 인자 리플렉션도 안 된다. 얻은 것은 **하위 호환**이다 — 제네릭 이전 바이트코드와 JVM을 그대로 쓸 수 있었다. C#은 정확히 반대의 선택, 곧 CLR 자체를 고치는 길을 갔고 그것이 23.1절 마지막 표의 내용이다.

**C# 제네릭이 잃은 것** — 표현력이다. 제약으로 표현할 수 있는 것만 쓸 수 있어 C++보다 할 수 있는 일이 좁다. 매개변수 있는 생성자를 제약할 수 없고, 오랫동안 연산자도 제약할 수 없었다. 얻은 것은 런타임 타입 정보, 라이브러리 배포 가능성, 박싱 없는 값 타입, 그리고 **정의 지점에서 나는 명료한 오류 메시지**다.

> **📌 소스 코드 보호는 부수 효과가 아니다**
>
> "제네릭 알고리즘을 쓰는 개발자가 그 알고리즘의 소스 코드를 가질 필요가 없다"는 것은 상용 라이브러리 벤더에게 실질적인 요구 사항이었다. C++ 템플릿 라이브러리는 헤더로 소스를 공개해야 한다. .NET에서 `List<T>`가 `System.Private.CoreLib.dll` 안에 IL로만 존재하면서 모든 타입 인자에 대해 동작하는 것은 이 설계 덕분이다.

> **⚠️ "C# 제네릭은 C++ 템플릿과 같다"는 문장이 만드는 사고**
>
> C++ 배경 개발자가 가장 자주 부딪히는 벽이 세 개다. (1) `T`에 연산자를 쓸 수 없다. (2) `T`의 메서드를 덕 타이핑으로 부를 수 없다 — 제약에 없으면 존재하지 않는 것이다. (3) 부분 특수화(partial specialization)가 없다. `class Stack<bool>`만 다르게 구현하는 문법이 C#에는 없고, 하려면 런타임 타입 검사(23.14절)로 흉내 내야 한다.

## 23.13 제약은 최소이면서 충분하게 — 설계 원칙

### 저울의 양쪽

타입 매개변수에 선언하는 제약은 "이 클래스가 일을 해내려면 타입 인자가 반드시 갖춰야 하는 것"의 목록이다. 제약을 만족하지 못하는 타입은 아예 쓸 수 없다. 그 반대편에는, **제약 하나하나가 이 타입을 쓰려는 개발자에게 추가 작업을 의미한다**는 사실이 있다.

| 제약이 너무 적으면 | 제약이 너무 많으면 |
|---|---|
| 런타임 검사와 캐스트가 늘어난다 | 쓸 수 있는 타입이 줄어든다 |
| 리플렉션을 쓰게 된다 | 사용자가 인터페이스를 억지로 구현해야 한다 |
| 오용을 컴파일 타임에 못 막는다 | 시간이 지날수록 제거하기 어려워진다 |

양쪽 극단이 다 틀렸다. 목표는 **필요한 것은 말하되 원하는 것 전부를 말하지 않는** 중간이다.

### 제약 없는 코드가 어떻게 생기는가

```csharp
public static bool AreEqual<T>(T left, T right)
{
    if (left == null)
        return right == null;

    if (left is IComparable<T>)
    {
        IComparable<T> lval = left as IComparable<T>;
        if (right is IComparable<T>)
            return lval.CompareTo(right) == 0;
        else
            throw new ArgumentException(
                "Type does not implement IComparable<T>", nameof(right));
    }
    else
    {
        throw new ArgumentException(
            "Type does not implement IComparable<T>", nameof(left));
    }
}
```

제약을 하나 걸면 이렇게 된다.

```csharp
public static bool AreEqual2<T>(T left, T right)
    where T : IComparable<T> =>
    left.CompareTo(right) == 0;
```

**런타임 오류를 컴파일 타임 오류와 맞바꾼 것이다.** 코드가 줄고, 첫 버전에서 방어해야 했던 런타임 오류를 컴파일러가 대신 막아 준다. 제약이 없으면 명백한 프로그래머 오류를 보고할 좋은 방법도 없다. 클라이언트 개발자가 이 클래스를 어떻게 써야 하는지 알아낼 유일한 방법이 문서를 읽는 것뿐이라면, 그들은 자주 틀린 추측을 한다.

### 제약을 줄이는 세 가지 기술

**(1) 없어도 되는 기능을 요구하지 않는다.**

`IEquatable<T>`는 좋은 인터페이스다. 값 타입에서 박싱을 피하고, 가상 호출 비용도 줄인다. 그런데 그것이 **제약으로 강제할 만한 수준인가?** 잘 동작하는 `System.Object.Equals`가 이미 있는데, 이 클래스를 쓰는 모든 사람이 `IEquatable<T>`를 구현해야 하는가.

권고는 이렇다. **가능하면 선호되는 메서드(`IEquatable<T>`)를 쓰되, 없으면 조용히 덜 선호되는 API(`Equals()`)로 내려가라.** 지원 여부에 따라 오버로드되는 내부 메서드를 만들면 된다. 손이 더 가지만 클라이언트에게 추가 작업을 요구하지 않는다. `EqualityComparer<T>.Default`와 `Comparer<T>.Default`가 정확히 이 설계다.

**(2) `new()`를 `default()`로 바꿔 본다.**

`new()`, `struct`, `class` 이 세 제약은 특히 조심해야 한다. 셋 다 객체가 어떻게 생성되는지, 기본값이 0인지 널 참조인지, 제네릭 클래스 안에서 인스턴스를 만들 수 있는지에 대한 가정을 만든다. **가능하면 이 셋을 피하라.** 23.5절에서 본 `FirstOrDefault`(제약 0개)와 `Factory`(`new()` 제약)의 대비가 그 예다. "당연히 `new T()`를 부를 수 있지"라고 머릿속에서만 만들어 낸 가정인 경우가 많다.

**(3) 제네릭·비제네릭 인터페이스 양쪽을 본다.**

`IEnumerable`과 `IEnumerable<T>`처럼 신구 인터페이스가 공존하는 자리에서도 같은 기법이 통한다. 좋은 쪽이 있으면 쓰고, 없으면 내려간다.

> **⚠️ 제약은 나중에 뺄 수 없다 — 사실상**
>
> 제약을 **추가**하는 것은 그 라이브러리를 쓰는 코드를 깨뜨리는 파괴적 변경이다. 그래서 처음 설계할 때 최소로 잡아야 한다. 반대로 제약을 **제거**하는 것은 소스 호환이지만, 그 제약이 있다는 전제로 짜인 내부 구현을 전부 고쳐야 한다. 어느 쪽이든 값이 비싸다.

> **⚠️ `IDisposable`을 구현하는 타입 인자를 잊지 마라**
>
> 제약은 "타입 인자가 무엇을 **할 수 없는지**"를 지정하지 못한다. 대부분의 경우 상관없지만 `IDisposable`은 예외다.
>
> ```csharp
> public class EngineDriverOne<T> where T : IEngine, new()
> {
>     public void GetThingsDone()
>     {
>         T driver = new T();
>         driver.DoWork();
>     }                     // T가 IDisposable이면 여기서 리소스가 샌다
> }
> ```
>
> 제네릭 클래스 안에서 타입 매개변수의 인스턴스를 만든다면, 그 타입이 `IDisposable`일 가능성을 방어해야 한다. 지역 변수라면 `using`에 캐스트를 태우는 관용구를 쓴다.
>
> ```csharp
> public void GetThingsDone()
> {
>     T driver = new T();
>     using (driver as IDisposable)
>     {
>         driver.DoWork();
>     }
> }
> ```
>
> 컴파일러가 `IDisposable`로 캐스트한 참조를 담을 숨은 지역 변수를 만든다. `T`가 `IDisposable`이 아니면 그 값은 `null`이고, `using`은 `null` 검사 후 `Dispose()`를 부르지 않는다. `T`가 `IDisposable`이면 블록을 벗어날 때 `Dispose()`가 호출된다.
>
> 인스턴스를 **필드로** 들고 있다면 문제가 더 커진다. 그 제네릭 클래스 자신이 `IDisposable`을 구현해야 하고, 파생 클래스를 위해 전체 Dispose 패턴을 구현하거나 클래스를 `sealed`로 막아야 한다(33장). 가능하면 **생성 책임을 클래스 밖으로 옮겨** 이 문제 자체를 피하는 편이 낫다.
>
> ```csharp
> public sealed class EngineDriver<T> where T : IEngine
> {
>     private T driver;
>     public EngineDriver(T driver) { this.driver = driver; }
>     public void GetThingsDone() => driver.DoWork();
> }
> ```
>
> `new()` 제약이 사라지고 소유권 문제도 사라졌다.

> **💡 제약으로 표현할 수 없는 계약은 델리게이트로 표현하라**
>
> C#의 제약 메커니즘은 기반 클래스 하나, 인터페이스 몇 개, `class`/`struct`, 매개변수 없는 생성자밖에 못 지정한다. 정적 메서드(연산자 포함)도, 매개변수 있는 생성자도 지정할 수 없다.
>
> `IAdd<T>` 같은 인터페이스를 만들어 강제하는 것은 가능하지만 최악의 선택이다. 이 제네릭을 쓰려는 모든 개발자가 `IAdd<T>`를 구현하는 클래스를 새로 만들어야 한다. 메서드 하나를 부르자고 API 시그니처를 맞추기 위한 클래스를 만들게 하는 것이다.
>
> 대신 필요한 메서드의 **시그니처를 델리게이트로 표현하고 매개변수로 받는다.**
>
> ```csharp
> public static class Example
> {
>     public static T Add<T>(T left, T right, Func<T, T, T> AddFunc) =>
>         AddFunc(left, right);
> }
> ```
>
> ```csharp
> int sum = Example.Add(6, 7, (x, y) => x + y);
> ```
>
> 호출자는 람다 한 줄을 쓰면 끝이다. 컴파일러가 타입과 반환값을 추론하고, 비공개 정적 메서드를 만들고, `Func<T,T,T>` 델리게이트 객체를 만들어 넘긴다. 이 기법은 **매개변수 있는 생성자 제약**의 부재도 메워 준다 — 팩터리 델리게이트를 생성자 매개변수로 받아 필드에 보관하면 된다.
>
> ```csharp
> public delegate T CreateFromStream<T>(TextReader reader);
>
> public class InputCollection<T>
> {
>     private readonly List<T> thingsRead = new();
>     private readonly CreateFromStream<T> readFunc;
>
>     public InputCollection(CreateFromStream<T> readFunc) => this.readFunc = readFunc;
>     public void ReadFromStream(TextReader reader) => thingsRead.Add(readFunc(reader));
> }
>
> var readValues = new InputCollection<Point>(input => new Point(input));
> ```
>
> 다만 `IComparable<T>`, `IEquatable<T>`, `IEnumerable<T>`처럼 **널리 쓰이고 의미가 명확한** 인터페이스는 그대로 제약으로 쓰는 것이 옳다. 델리게이트는 "이 제네릭 하나만을 위한 커스텀 계약"에 쓰는 도구다.

## 23.14 런타임 타입 검사로 제네릭 알고리즘 특수화하기

### 일반적일수록 느려지는 순간

제네릭은 타입 매개변수만 바꿔서 재사용된다. 그런데 **더 일반적이라는 것이 더 나은 알고리즘을 포기한다는 뜻일 때**가 있다. 게다가 제네릭 인스턴스화는 **컴파일 타임 타입**을 기준으로 결정되므로, 런타임 타입이 더 많은 기능을 제공해도 그냥 지나친다.

역순 열거자를 예로 보자.

```csharp
public sealed class ReverseEnumerable<T> : IEnumerable<T>
{
    IEnumerable<T> sourceSequence;
    IList<T> originalSequence;

    public ReverseEnumerable(IEnumerable<T> sequence) => sourceSequence = sequence;

    public IEnumerator<T> GetEnumerator()
    {
        if (originalSequence == null)       // 뒤집을 수 있도록 원본을 복사한다
        {
            originalSequence = new List<T>();
            foreach (T item in sourceSequence) originalSequence.Add(item);
        }
        return new ReverseEnumerator(originalSequence);
    }
    // ...
}
```

이 구현은 입력에 대해 **최소한만 가정한다.** `IEnumerable<T>`는 임의 접근을 제공하지 않으므로, 뒤집으려면 전체를 훑어 복사하는 수밖에 없다. 그런데 실제로 넘어오는 컬렉션 상당수는 임의 접근을 지원한다. 그 경우 이 복사는 완전히 낭비다.

### 생성자에서 런타임 검사 한 줄

```csharp
public ReverseEnumerable(IEnumerable<T> sequence)
{
    sourceSequence = sequence;
    // sequence가 IList<T>를 구현하지 않으면 originalSequence가 null이 되므로 문제없다
    originalSequence = sequence as IList<T>;
}
```

한 줄이다. 그런데 왜 `IList<T>`를 받는 생성자 오버로드를 하나 더 만들지 않는가? 만들어야 한다 — **둘 다** 만들어야 한다.

```csharp
public ReverseEnumerable(IList<T> sequence)
{
    sourceSequence = sequence;
    originalSequence = sequence;
}
```

오버로드만으로는 **매개변수의 컴파일 타임 타입이 `IEnumerable<T>`인데 런타임 타입이 `IList<T>`를 구현하는 경우**를 못 잡는다. 런타임 검사만으로는 컴파일 타임에 확정할 수 있는 것을 런타임으로 미룬다. 두 개를 다 제공해야 모든 경우를 잡는다.

### 능력의 사다리를 내려가며

`IList<T>`는 아니지만 `ICollection<T>`인 컬렉션도 있다. 그 경우 `Count`를 알 수 있으므로 리스트 용량을 미리 잡을 수 있다.

```csharp
public IEnumerator<T> GetEnumerator()
{
    // string은 특수 케이스다
    if (sourceSequence is string)
    {
        // T가 컴파일 타임에 char가 아닐 수 있어 캐스트가 필요하다
        return new ReverseStringEnumerator(sourceSequence as string)
            as IEnumerator<T>;
    }

    if (originalSequence == null)
    {
        if (sourceSequence is ICollection<T>)
        {
            ICollection<T> source = sourceSequence as ICollection<T>;
            originalSequence = new List<T>(source.Count);   // 재할당을 피한다
        }
        else
            originalSequence = new List<T>();

        foreach (T item in sourceSequence)
            originalSequence.Add(item);
    }
    return new ReverseEnumerator(originalSequence);
}
```

`string`이 왜 별도 분기인가. `string`은 문자에 임의 접근하는 메서드를 제공하지만 **`IList<char>`를 구현하지 않는다.** 이런 타입을 활용하려면 제네릭 클래스 안에 그 타입 전용 코드를 따로 써야 한다. 위 코드의 `as IEnumerator<T>` 캐스트는 컴파일 타임에 `T`가 `char`라는 보장이 없기 때문에 필요하다. 이 경로에 도달하는 유일한 조건이 "시퀀스가 `string`"이므로 안전하고, 클래스 안에 감춰져 있어 공개 인터페이스를 더럽히지 않는다.

이것이 `List<T>`의 `List<T>(IEnumerable<T>)` 생성자가 실제로 하는 일과 같은 종류의 코드다.

> **💡 원칙 — 최소한만 요구하고, 더 주면 더 잘한다**
>
> 이 기법의 핵심은 **클라이언트에게 더 많은 기능을 강제하지 않으면서, 그들이 이미 제공하는 기능이 있으면 활용한다**는 것이다. 제약을 올리는 대신 런타임 검사를 넣는다. 최대 재사용성과 특정 알고리즘의 최선 구현 사이의 가장 좋은 타협이다.

> **⚠️ 런타임 검사에는 값이 붙는다**
>
> 위의 모든 검사는 런타임 매개변수에 대한 런타임 검사다. 추가 기능을 조회하는 비용을 매번 낸다는 뜻이다. 이 예에서는 요소 복사 비용이 검사 비용보다 훨씬 크므로 명백히 이득이다. 그러나 언제나 그런 것은 아니다. **특수화된 경로가 확실히 훨씬 나을 때만** 쓰고, 넣은 뒤에는 측정하라(67장).
>
> 검사 위치도 중요하다. 위 코드는 검사를 **생성자와 `GetEnumerator` 진입부**에 두었다. 요소마다 검사하는 코드였다면 이야기가 완전히 달라진다.

## 23.15 기반 클래스·인터페이스에 대한 제네릭 특수화를 피하라

### 출력을 맞춰 보라

```csharp
using static System.Console;

public class MyBase { }
public interface IMessageWriter { void WriteMessage(); }

public class MyDerived : MyBase, IMessageWriter
{
    void IMessageWriter.WriteMessage() => WriteLine("Inside MyDerived.WriteMessage");
}

public class AnotherType : IMessageWriter
{
    public void WriteMessage() => WriteLine("Inside AnotherType.WriteMessage");
}

class Program
{
    static void WriteMessage(MyBase b)  => WriteLine("Inside WriteMessage(MyBase)");
    static void WriteMessage<T>(T obj)
    {
        Write("Inside WriteMessage<T>(T):  ");
        WriteLine(obj.ToString());
    }
    static void WriteMessage(IMessageWriter obj)
    {
        Write("Inside WriteMessage(IMessageWriter):  ");
        obj.WriteMessage();
    }

    static void Main()
    {
        MyDerived d = new MyDerived();
        WriteMessage(d);                        // ①
        WriteMessage((IMessageWriter)d);        // ②
        WriteMessage((MyBase)d);                // ③

        AnotherType anObject = new AnotherType();
        WriteMessage(anObject);                 // ④
        WriteMessage((IMessageWriter)anObject); // ⑤
    }
}
```

출력이다.

```text
① Inside WriteMessage<T>(T):  Item14.MyDerived
② Inside WriteMessage(IMessageWriter):  Inside MyDerived.WriteMessage
③ Inside WriteMessage(MyBase)
④ Inside WriteMessage<T>(T):  Item14.AnotherType
⑤ Inside WriteMessage(IMessageWriter):  Inside AnotherType.WriteMessage
```

### 왜 제네릭이 이겼는가

첫 호출 `WriteMessage(d)`가 핵심이다. `MyDerived`는 `MyBase`를 상속하고 `IMessageWriter`를 구현하는데, 선택된 것은 **제네릭 버전**이다.

이유는 오버로드 해석 규칙이다. `WriteMessage<T>(T obj)`는 `T`에 `MyDerived`를 대입하면 **정확히 일치**한다. `WriteMessage(MyBase b)`는 **암시적 변환**이 필요하다. 정확한 일치가 이긴다.

> **⚠️ 제네릭 메서드는 언제나 완벽한 일치다 — 그래서 기반 클래스 메서드를 이긴다**
>
> 이 한 문장이 이 절 전체다. 기반 클래스나 인터페이스를 받는 오버로드 옆에 제네릭 오버로드를 두면, **파생 타입으로 호출할 때마다 제네릭 쪽이 선택된다.** 호출자가 명시적으로 캐스트하지 않는 한 그렇다. 위 출력에서 두 번째와 세 번째 호출이 의도한 메서드를 부른 유일한 이유는 호출부에 캐스트가 있었기 때문이다.
>
> 이 성질은 `Queryable`과 `Enumerable`의 확장 메서드(30장)에서 특히 중요해진다.

### 규칙

- **기반 클래스에 대한 제네릭 특수화를 만들지 마라** — 그 클래스와 모든 후손을 지원할 의도라면.
- **인터페이스에 대한 제네릭 특수화도 마찬가지로 위험하다.**
- **숫자 타입은 예외다.** 정수 타입과 부동소수점 타입 사이에는 상속 관계가 없으므로 이 함정이 없다. 실제로 .NET은 `Enumerable.Max<T>`, `Enumerable.Min<T>` 등에 모든 숫자 타입 특수화를 제공한다.

정말 특수화가 필요하다면 런타임 타입 검사가 아니라 **컴파일러**에게 시켜야 한다. 런타임 검사를 넣는 것은 제네릭을 쓰는 이유 자체를 갉아먹는다.

```csharp
// 최선의 해법이 아니다 — 런타임 타입 검사를 쓴다
static void WriteMessage<T>(T obj)
{
    if (obj is MyBase)                WriteMessage(obj as MyBase);
    else if (obj is IMessageWriter)   WriteMessage((IMessageWriter)obj);
    else                              WriteLine($"Inside WriteMessage<T>(T): {obj}");
}
```

검사할 조건이 두어 개뿐이라면 괜찮다. 추한 동작을 클라이언트로부터 감춰 주기는 한다. 하지만 런타임 오버헤드가 들어가고, 조건이 늘어나면 감당이 안 된다.

> **💡 규칙을 한 문장으로**
>
> 특정 타입에 대해 제네릭 메서드의 특수 버전을 만들려면 **그 타입과 모든 후손에 대해** 만들어야 한다. 인터페이스에 대한 특수화를 만들려면 **그 인터페이스를 구현하는 모든 타입에 대해** 만들어야 한다. 그럴 수 없다면 만들지 마라. 23.14절의 기법과 헷갈리지 마라. 23.14절은 **생성자에서 능력을 조회해 내부 구현을 고르는 것**이고, 오버로드 해석에 의존하지 않는다.

### 제네릭 메서드와 제네릭 클래스 사이의 선택

두 절의 논의는 자연스럽게 마지막 질문으로 이어진다. **제네릭 클래스를 만들 것인가, 비제네릭 클래스에 제네릭 메서드를 담을 것인가.**

C# 컴파일러는 제네릭 클래스 전체에 대해 **하나의 제약 집합**으로 유효한 IL을 만들어야 한다. 제네릭 메서드를 담은 유틸리티 클래스는 메서드마다 다른 제약을 지정할 수 있다.

```csharp
// 제네릭 클래스 — 호출부가 매번 타입 인자를 써야 한다
public static class Utils<T>
{
    public static T Max(T left, T right) =>
        Comparer<T>.Default.Compare(left, right) < 0 ? right : left;
    public static T Min(T left, T right) =>
        Comparer<T>.Default.Compare(left, right) < 0 ? left : right;
}
```

```csharp
double max = Utils<double>.Max(d1, d2);      // 타입 인자를 생략할 수 없다
```

문제는 문법만이 아니다. 많은 내장 타입이 이미 `Math.Max`, `Math.Min`을 갖고 있는데 이 제네릭 클래스는 언제나 자기 `Comparer<T>` 버전을 쓴다. 동작은 하지만 `IComparer<T>` 구현 여부를 런타임에 확인하고 올바른 메서드를 호출하는 비용을 매번 낸다.

비제네릭 클래스 + 제네릭 메서드로 바꾸면 이렇게 된다.

```csharp
public static class Utils
{
    public static T Max<T>(T left, T right) =>
        Comparer<T>.Default.Compare(left, right) < 0 ? right : left;
    public static double Max(double left, double right) => Math.Max(left, right);
    // 다른 숫자 타입 버전 생략

    public static T Min<T>(T left, T right) =>
        Comparer<T>.Default.Compare(left, right) < 0 ? left : right;
    public static double Min(double left, double right) => Math.Min(left, right);
}
```

```csharp
double max = Utils.Max(d1, d2);       // double 전용 버전이 선택된다
string sMax = Utils.Max(foo, bar);    // 제네릭 버전이 선택된다
double? m = Utils.Max(d3, d4).Value;  // 제네릭 버전
```

**타입 인자를 쓰지 않아도 되고, 구체 버전이 있으면 컴파일러가 그것을 고른다.** 나중에 특수 버전을 더 추가하면 호출부는 재컴파일만으로 자동으로 그것을 쓴다. 호출자에게 타입 인자를 강제하는 API는 나중에 더 나은 구현을 제공해도 계속 제네릭 버전을 쓰게 된다.

> **💡 판단 기준 — 딱 두 가지**
>
> 제네릭 **클래스**가 필요한 경우는 두 가지뿐이다.
>
> 1. **타입 매개변수의 값을 내부 상태로 저장할 때.** 컬렉션이 명백한 예다.
> 2. **제네릭 인터페이스를 구현할 때.** `IEnumerable<T>`를 구현하려면 클래스가 `T`를 가져야 한다.
>
> 그 외에는 비제네릭 클래스에 제네릭 메서드를 담는다. 앞으로 알고리즘을 고칠 때 훨씬 세밀하게 손댈 수 있다. 클래스 수준에 제약을 걸어 두면, 클래스가 커질수록 그 제약이 목을 조른다. **두 번쯤 릴리스하고 나면 메서드 수준으로 잡을 걸 그랬다고 후회하게 된다.**
>
> 정적 유틸리티 클래스만의 얘기가 아니다.
>
> ```csharp
> public class CommaSeparatedListBuilder
> {
>     private readonly StringBuilder storage = new();
>
>     public void Add<T>(IEnumerable<T> items)      // 타입 매개변수가 메서드에 있다
>     {
>         foreach (T item in items)
>         {
>             if (storage.Length > 0) storage.Append(", ");
>             storage.Append('"').Append(item.ToString()).Append('"');
>         }
>     }
>
>     public override string ToString() => storage.ToString();
> }
> ```
>
> 타입 매개변수를 클래스에 붙였다면 이 빌더는 **한 종류의 타입만** 담을 수 있었을 것이다. 메서드에 붙였기 때문에 서로 다른 타입을 얼마든지 섞을 수 있다. 둘 다 유효한 설계이고, 의미가 완전히 다르다.

## 이 장의 요약

- **제네릭은 문법 설탕이 아니라 CLR 2.0이 통째로 만들어 낸 런타임 기능이다.** IL 명령, 메타데이터 테이블, JIT, 리플렉션, 디버거를 전부 고쳐야 했다. 그렇게 하지 않았다면 컴파일 타임 타입 안전은 얻어도 값 타입의 박싱은 남았을 것이다.
- **박싱 제거가 값 타입에서 압도적 이득을 낸다.** 원천 도서의 측정에서 `List<Int32>`가 `ArrayList`보다 약 7배 빠르고 0세대 GC는 6회 대 390회였다. 참조 타입에서는 차이가 10% 안쪽이며, 그래도 타입 안전과 명료성 때문에 제네릭을 쓴다.
- **열린 타입은 런타임에 인스턴스화되지 않는다.** 런타임의 제네릭 인스턴스는 전부 닫혀 있고, 언바운드 타입은 `typeof(A<>)`가 만든 `Type` 객체로만 존재한다. 메타데이터 이름은 `` List`1 ``처럼 백틱과 아리티를 쓴다.
- **제약의 목적은 금지가 아니라 허가다.** 주 제약 0~1개, 부 제약(인터페이스·나체 타입) 0개 이상, 생성자 제약 0~1개, 그리고 ※C# 13의 `allows ref struct` 순서로 쓴다. `new()`는 항상 마지막이고, `struct`와 `new()`는 함께 쓸 수 없다.
- **닫힌 타입마다 정적 필드가 분리된다.** `Bob<int>.Count`와 `Bob<string>.Count`는 다른 정수다. 정적 생성자도 닫힌 타입당 한 번 실행되며, 이 성질이 리플렉션 캐시 관용구를 만들고 동시에 조용한 메모리 증가의 원인이 된다.
- **타입 매개변수 캐스트는 `object`를 경유하거나 `as`를 쓴다.** 컴파일러가 사용자 정의 변환일 가능성을 배제하지 못해 직접 캐스트를 거부하기 때문이다. 컴파일된다고 안전해진 것은 아니다.
- **변성은 참조 변환에만 적용된다.** 그래서 `IEnumerable<string>`은 `IEnumerable<object>`가 되지만 `IEnumerable<int>`는 되지 않는다. 참조 변환은 비트를 바꾸지 않고 박싱은 데이터를 복사하기 때문이다. `out`은 출력 위치, `in`은 입력 위치에만 쓸 수 있고, 클래스에는 변성을 붙일 수 없다.
- **배열 공변성은 안전하지 않고 제네릭 변성은 안전하다.** 배열은 허용해 놓고 런타임 검사로 막지만, 제네릭 변성은 위험한 코드를 애초에 표현할 수 없게 만들어 런타임 비용도 0이다.
- **값 타입은 인스턴스화마다 네이티브 코드가 특수화되고 참조 타입은 하나를 공유한다.** 특수화가 인라이닝과 박싱 제거를 낳는 동시에 코드 크기와 워킹 셋을 늘린다. 성능과 코드 크기에 동시에 영향을 주는 이유가 이 비대칭이다.
- **C# 제네릭은 런타임에, C++ 템플릿은 컴파일 타임에 합성한다.** 그래서 C#은 열린 타입을 `.dll`로 배포하고 리플렉션할 수 있는 대신 연산자와 덕 타이핑을 포기했다. Java는 소거를 택해 하위 호환을 얻고 런타임 타입 정보와 값 타입 성능을 잃었다.
- **제약은 최소이면서 충분하게.** `new()`·`struct`·`class`는 특히 조심하고, `default(T)`로 대체할 수 있으면 대체한다. 표현할 수 없는 계약은 인터페이스를 강요하지 말고 델리게이트 매개변수로 받는다.
- **제네릭 메서드는 언제나 완벽한 일치라서 기반 클래스 오버로드를 이긴다.** 기반 클래스나 인터페이스에 대한 제네릭 특수화를 만들지 마라. 타입 매개변수를 인스턴스 필드로 저장하거나 제네릭 인터페이스를 구현할 때가 아니면, 제네릭 클래스보다 비제네릭 클래스 + 제네릭 메서드가 낫다.

## 연습 문제

1. `Stack<T>`를 직접 작성하고 `Stack<int>`와 `Stack<string>`으로 각각 100만 회 `Push`/`Pop`을 돌려라. 같은 작업을 `ArrayList`로도 하고, `Stopwatch`와 `GC.CollectionCount(0)`을 함께 기록해 표로 정리하라. 23.1절의 비율 방향이 자기 환경에서도 재현되는지 확인하라.

2. `class Bob<T> { public static int Count; }`를 만들고 `Bob<int>`, `Bob<string>`, `Bob<object>`, `Bob<List<int>>`의 `Count`를 각각 증가시켜 값이 분리되는지 확인하라. 그다음 정적 생성자에 `Console.WriteLine`을 넣어 닫힌 타입마다 정확히 한 번 실행되는지 확인하라. 마지막으로 정적 생성자가 `T`가 `int`일 때만 예외를 던지게 하고, `Bob<int>`에 두 번 접근했을 때 어떤 예외가 나는지 확인하라.

3. `typeof(List<>)`, `typeof(List<int>)`, `typeof(Dictionary<,>)`의 `Name`, `FullName`, `IsGenericTypeDefinition`, `ContainsGenericParameters`를 출력하라. 그다음 `Activator.CreateInstance(typeof(List<>))`를 시도해 예외 타입과 메시지를 확인하고, `MakeGenericType`으로 닫은 뒤 다시 시도하라.

4. `where T : struct`, `where T : unmanaged`, `where T : notnull`, `where T : new()`를 각각 요구하는 메서드 네 개를 만들어라. `int`, `int?`, `string`, `DateTime`, `Guid`, `struct S { string Name; }`, `decimal` 일곱 가지를 각 메서드에 넣어 보고 어떤 조합이 컴파일되는지 7×4 표로 채워라. 실패한 칸마다 오류 번호를 적어라.

5. `IPoppable<out T>`와 `IPushable<in T>`를 정의하고 하나의 `Stack<T>`가 둘 다 구현하게 하라. `Stack<Bear>`를 `IPoppable<Animal>`로, `Stack<Animal>`을 `IPushable<Bear>`로 변환해 보고, 각 인터페이스에 반대 방향 멤버(예: `IPoppable<out T>`에 `void Push(T)`)를 추가하면 어떤 오류가 나는지 확인하라. 그다음 `Stack<int>`를 `IPoppable<object>`로 변환해 보고 오류 메시지를 읽어라.

6. `class Bob<T> { public static int Count; }`를 값 타입 인자 10개와 참조 타입 인자 10개로 인스턴스화하는 프로그램을 두 벌 만들어라. `dotnet publish -p:PublishAot=true`로 각각 빌드해 바이너리 크기를 비교하고, 23.11절의 "값 타입은 특수화, 참조 타입은 공유"가 크기 차이로 드러나는지 확인하라.

7. `WriteMessage(MyBase)`, `WriteMessage(IMessageWriter)`, `WriteMessage<T>(T)` 세 오버로드를 만들고 23.15절의 다섯 가지 호출을 실행해 출력을 확인하라. 그다음 제네릭 오버로드를 지우고 다시 실행해 어떤 호출이 바뀌는지 비교하라. 마지막으로 `Utils<T>` 형태와 `Utils` + 제네릭 메서드 형태를 둘 다 작성해 호출부 코드가 어떻게 달라지는지 나란히 적어라.
