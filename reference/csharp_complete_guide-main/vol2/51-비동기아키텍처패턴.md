## 51.1 프로듀서/컨슈머와 `System.Threading.Channels`

### 왜 또 하나의 큐인가

50.11절에서 `BlockingCollection<T>`으로 프로듀서/컨슈머 큐를 만들었고, 마지막에 그 한계를 짚었다. 이름이 곧 한계다 — **블로킹한다**. `Take()`는 스레드를 세우고, `TakeAsync()`는 없다. 서버 애플리케이션에서 컨슈머 하나가 스레드 풀 스레드 하나를 영구히 붙들면 그것은 스레드 풀 기아(thread pool starvation)의 직행 티켓이다.

.NET Core 3에서 도입된 `System.Threading.Channels` 네임스페이스는 정확히 이 구멍을 메운다. 채널(channel)은 **비동기 프로듀서/컨슈머 큐**다. 큐가 비었을 때 컨슈머는 스레드를 블로킹하는 대신 `await` 한다. 큐가 찼을 때 프로듀서도 `await` 한다.

```csharp
using System.Threading.Channels;

// 무제한 채널 — 용량 제한 없음
Channel<string> unbounded = Channel.CreateUnbounded<string>();

// 경계 채널 — 최대 100개
Channel<string> bounded = Channel.CreateBounded<string>(100);
```

`Channel<T>`는 실제로는 `Channel<TWrite, TRead>`를 상속한 축약형이다. 읽는 타입과 쓰는 타입이 같은 일반적인 경우를 위한 것이고, 둘이 다른 채널(예: 변환하며 통과시키는 채널)을 만들 수 있게 기반 타입이 두 개의 타입 매개변수를 갖는다. 실무에서 `Channel<TWrite, TRead>`를 직접 쓸 일은 거의 없다.

### 문법 — 읽는 쪽과 쓰는 쪽이 분리되어 있다

채널의 첫인상에서 가장 눈에 띄는 것은 `Channel<T>` 자체에 `Add`나 `Take` 같은 메서드가 **없다**는 점이다. 대신 속성 두 개가 있다.

```csharp
public abstract class Channel<TWrite, TRead>
{
    public ChannelReader<TRead>  Reader { get; protected set; }
    public ChannelWriter<TWrite> Writer { get; protected set; }
}

public abstract class Channel<T> : Channel<T, T> { }
```

이 분리는 편의를 위한 것이 아니라 **설계 장치**다.

`ChannelWriter<T>`와 `ChannelReader<T>`는 각각 독립된 추상 클래스이므로, 프로듀서 컴포넌트에는 `ChannelWriter<T>`만, 컨슈머 컴포넌트에는 `ChannelReader<T>`만 주입할 수 있다.

```csharp
// 프로듀서는 쓰는 능력만 받는다 — 큐를 읽거나 비울 수 없다
public sealed class OrderIngestService
{
    private readonly ChannelWriter<Order> _writer;
    public OrderIngestService(ChannelWriter<Order> writer) => _writer = writer;

    public ValueTask EnqueueAsync(Order order, CancellationToken ct)
        => _writer.WriteAsync(order, ct);
}

// 컨슈머는 읽는 능력만 받는다 — 큐에 항목을 밀어 넣을 수 없다
public sealed class OrderProcessor
{
    private readonly ChannelReader<Order> _reader;
    public OrderProcessor(ChannelReader<Order> reader) => _reader = reader;

    public async Task RunAsync(CancellationToken ct)
    {
        await foreach (Order order in _reader.ReadAllAsync(ct))
            await HandleAsync(order, ct);
    }
}
```

`BlockingCollection<T>`을 그대로 주입하면 컨슈머 코드가 실수로 `Add`를 부를 수 있고, 프로듀서가 `CompleteAdding`을 부를 수 있으며, 아무나 `Count`를 보고 분기할 수 있다. 채널의 분리형 타입은 **컴파일 시점에** 그 실수를 막는다. 타입으로 방향을 표현하는 것 — 이것이 78.3절이 말하는 "명확하고 최소한인 메서드 그룹"의 전형이다.

> **📌 `Channel<T>`은 DI 컨테이너에 그대로 등록하기 좋다**
>
> ASP.NET Core에서는 다음 세 줄이 관용구다.
>
> ```csharp
> builder.Services.AddSingleton(_ => Channel.CreateBounded<Order>(
>     new BoundedChannelOptions(1000) { FullMode = BoundedChannelFullMode.Wait }));
> builder.Services.AddSingleton(sp => sp.GetRequiredService<Channel<Order>>().Reader);
> builder.Services.AddSingleton(sp => sp.GetRequiredService<Channel<Order>>().Writer);
> ```
> 채널 자체는 싱글턴이지만 **불변 상태가 아니라 스레드 안전한 상태**이므로 48.14절이 금지한 "싱글턴의 가변 상태"에 해당하지 않는다. 채널은 동시 접근을 계약으로 보장한다.

### `ChannelWriter<T>`의 다섯 가지 메서드

| 메서드 | 반환 | 언제 쓰는가 |
|---|---|---|
| `TryWrite` | `bool` | 즉시 쓸 수 있으면 쓰고 아니면 실패. **절대 블로킹하지 않는다** |
| `WaitToWriteAsync` | `ValueTask<bool>` | "쓸 자리가 생길 때까지" 대기. 채널이 닫혔으면 `false` |
| `WriteAsync` | `ValueTask` | 자리가 생길 때까지 기다렸다가 쓴다 |
| `Complete` | `void` | 더 이상 쓰지 않음을 선언. 두 번 부르면 `InvalidOperationException` |
| `TryComplete` | `bool` | 같은 일을 하되 이미 완료됐으면 `false` |

`TryWrite`와 `WaitToWriteAsync`를 조합한 루프는 `WriteAsync` 하나보다 빠를 수 있다. 자리가 있는 동안 `TryWrite`의 동기 경로만 타기 때문이다.

```csharp
// 고빈도 프로듀서의 관용구 (HasMore 는 bool, Produce() 는 T 를 반환한다)
while (HasMore && await writer.WaitToWriteAsync(ct))
    while (HasMore && writer.TryWrite(Produce()))
    { }
```

> **⚠️ `TryWrite`가 `false`를 반환하는 이유는 두 가지다**
>
> 하나는 **채널이 가득 찼기 때문**(`FullMode.Wait`인 경계 채널)이고, 다른 하나는 **채널이 이미 완료됐기 때문**이다. 반환값만으로는 구분되지 않는다. 두 경우의 대응은 정반대다 — 전자는 기다렸다 다시 시도해야 하고, 후자는 영원히 재시도해도 성공하지 않는다.
>
> 구분이 필요하면 `WaitToWriteAsync`를 쓴다. 이 메서드는 **자리가 생기면 `true`**, **채널이 닫혔으면 `false`** 를 반환하므로 두 상황이 갈린다. 위의 관용구가 바깥 루프에 `WaitToWriteAsync`를 두는 이유가 이것이다.

### `ChannelReader<T>`와 표준 소비 루프

```csharp
public abstract class ChannelReader<T>
{
    public abstract bool TryRead(out T item);
    public abstract ValueTask<bool> WaitToReadAsync(CancellationToken ct = default);
    public virtual  ValueTask<T> ReadAsync(CancellationToken ct = default);
    public virtual  IAsyncEnumerable<T> ReadAllAsync(CancellationToken ct = default);
    public virtual  Task Completion { get; }
    public virtual  int  Count      { get; }   // ※.NET 6
    public virtual  bool CanCount   { get; }   // ※.NET 6
    public virtual  bool CanPeek    { get; }   // ※.NET 7
    public virtual  bool TryPeek(out T item);  // ※.NET 7
}
```

**이 장에서 외워야 할 코드가 하나 있다면 이것이다.**

```csharp
// 표준 소비 루프 — 이 형태에서 벗어나는 이유가 없으면 벗어나지 마라
await foreach (T item in reader.ReadAllAsync(ct))
{
    await ProcessAsync(item, ct);
}
```

`ReadAllAsync`는 `IAsyncEnumerable<T>`를 돌려주며, 다음 세 가지를 한꺼번에 처리한다.

1. 항목이 있으면 즉시 내놓는다(동기 완료 경로).
2. 없으면 스레드를 놓고 `await` 한다.
3. `Complete()`가 호출되고 남은 항목이 모두 소비되면 **루프가 정상 종료된다.**

세 번째가 핵심이다. `BlockingCollection<T>`의 `GetConsumingEnumerable`이 하던 일을 스레드 블로킹 없이 한다. 명시적으로 풀어 쓰면 아래와 같고, 결과는 같다.

```csharp
// ReadAllAsync가 내부에서 하는 일과 사실상 동등한 코드
while (await reader.WaitToReadAsync(ct))
    while (reader.TryRead(out T item))
        await ProcessAsync(item, ct);
```

이 이중 루프 형태를 직접 쓰는 이유는 하나뿐이다 — **배치 처리**. 안쪽 `TryRead` 루프에서 항목을 모았다가 한 번에 처리하고 싶을 때다.

```csharp
// 최대 100개씩 모아서 한 번에 DB에 밀어 넣는다
var batch = new List<Order>(100);
while (await reader.WaitToReadAsync(ct))
{
    while (batch.Count < 100 && reader.TryRead(out Order order))
        batch.Add(order);

    if (batch.Count > 0)
    {
        await _repository.BulkInsertAsync(batch, ct);
        batch.Clear();
    }
}
```

항목 하나당 왕복 한 번인 구조를 100개당 한 번으로 바꾸면 처리량이 자릿수 단위로 달라진다. 그리고 채널이 "지금 바로 꺼낼 수 있는 것"을 `TryRead`로 알려주므로 **부하가 낮을 때는 배치가 저절로 작아지고 높을 때 저절로 커진다** — 타이머 없이 적응형 배칭이 된다.

### 완료 전파 — `Complete`와 `Completion`

채널의 수명은 명시적으로 끝난다.

```csharp
// 프로듀서 쪽
try
{
    foreach (var line in File.ReadLines(path))
        await writer.WriteAsync(line, ct);
    writer.Complete();                 // 정상 종료
}
catch (Exception ex)
{
    writer.Complete(ex);               // 오류 종료 — 예외를 컨슈머에게 전달
}
```

`Complete()` 이후의 동작은 다음 표와 같다.

| 작업 | `Complete()` 이후 동작 |
|---|---|
| `Writer.TryWrite` / `WaitToWriteAsync` | `false` 반환 |
| `Writer.WriteAsync` | `ChannelClosedException` 발생 |
| `Writer.Complete` (두 번째) | `InvalidOperationException` 발생 |
| `Reader.TryRead` | 남은 항목이 있으면 `true`, 다 비면 `false` (`ReadAsync`는 다 읽은 뒤 `ChannelClosedException`) |
| `Reader.ReadAllAsync` | 남은 항목을 다 내놓고 **루프가 종료된다** |
| `Reader.Completion` | 남은 항목이 다 소비되면 완료(또는 전달된 예외로 실패) |

`ChannelClosedException`은 `System.Threading.Channels` 네임스페이스의 실제 타입이며 `InvalidOperationException`을 상속한다. `Complete(ex)`로 예외를 전달했다면 `ChannelClosedException.InnerException`에 그 예외가 담긴다.

`Reader.Completion`은 `Task`다. "이 채널의 생산이 끝났고 남은 것도 다 소비됐다"를 기다리는 데 쓴다.

```csharp
// 파이프라인 조립: 프로듀서 태스크와 컨슈머 태스크를 함께 기다린다
Task producer = ProduceAsync(channel.Writer, ct);
Task consumer = ConsumeAsync(channel.Reader, ct);
await Task.WhenAll(producer, consumer);
```

> **⚠️ `Complete()`를 잊으면 컨슈머가 영원히 끝나지 않는다**
>
> 채널을 쓰는 코드에서 가장 흔한 버그다. 프로듀서가 정상 종료했는데 `Complete()`를 부르지 않으면, `await foreach (var x in reader.ReadAllAsync(ct))` 루프는 **다음 항목을 영원히 기다린다.** 예외가 나지도 않고 CPU를 쓰지도 않는다. 그냥 프로세스가 종료되지 않는다.
>
> 방어책은 `try/finally`다.
>
> ```csharp
> try { /* 생산 */ }
> finally { writer.Complete(); }   // 예외로 빠져나가도 반드시 완료 선언
> ```
>
> 다만 `finally`에서 인자 없이 `Complete()`를 부르면 **프로듀서의 예외가 컨슈머에게 전달되지 않는다.** 예외를 잡아 `Complete(ex)`로 넘기는 쪽이 낫다.

> **⚠️ 프로듀서의 예외가 조용히 사라지는 경로**
>
> ```csharp
> _ = Task.Run(() => ProduceAsync(channel.Writer));   // 위험
> await foreach (var item in channel.Reader.ReadAllAsync()) { ... }
> ```
>
> 프로듀서 태스크를 `_ =`로 버리면 그 안에서 난 예외는 아무도 관찰하지 않는다(46.11절). 컨슈머 루프는 채널이 완료되지 않았으니 영원히 대기한다. 결과는 "아무 로그도 없이 멈춘 서비스"다.
>
> 프로듀서 태스크 참조를 반드시 붙들고 `Task.WhenAll`로 함께 기다리거나, 프로듀서 내부를 `try/catch`로 감싸 `Complete(ex)`를 부르게 하라.

### 완료가 여러 컨슈머에게 퍼지는 방식

컨슈머를 여러 개 붙이는 팬아웃(fan-out)은 채널의 대표 용법이다.

```csharp
var channel = Channel.CreateBounded<WorkItem>(
    new BoundedChannelOptions(500) { SingleWriter = true });   // SingleReader는 false

Task[] consumers = Enumerable.Range(0, 4)
    .Select(_ => Task.Run(async () =>
    {
        await foreach (WorkItem item in channel.Reader.ReadAllAsync(ct))
            await HandleAsync(item, ct);
    }))
    .ToArray();

await ProduceAsync(channel.Writer, ct);
channel.Writer.Complete();
await Task.WhenAll(consumers);      // 네 개 모두 정상 종료된다
```

`Complete()` 한 번이 **모든** 컨슈머 루프를 끝낸다. 각 항목은 정확히 한 컨슈머에게만 간다(채널은 브로드캐스트가 아니다). 이 두 성질 덕분에 위 코드가 정확히 의도대로 동작한다.

```text
  팬아웃 파이프라인 (컨슈머 4, 경계 500)

                        ┌──────────────────────────────┐
                        │  Channel<WorkItem>  cap=500  │
   Producer ──WriteAsync│ ▓▓▓▓▓▓▓░░░░░░░░░░░░░░░░░░░░░ │
     (1)                └──────────────┬───────────────┘
                                       │ ReadAllAsync
                    ┌──────────┬───────┴──┬──────────┐
                    ↓          ↓          ↓          ↓
                Consumer0  Consumer1  Consumer2  Consumer3
                    │          │          │          │
                    └──────────┴─────┬────┴──────────┘
                                     ↓
                          Complete() 한 번 → 넷 다 종료
```

### 파이프라인 — 채널을 여러 단으로 잇기

각 단계가 채널 하나로 연결되면 단계마다 병렬도를 따로 정할 수 있다.

```csharp
// 1단계: URL 목록 → 2단계: 다운로드 → 3단계: 파싱 → 4단계: 저장
var urls    = Channel.CreateBounded<string>(1000);
var pages   = Channel.CreateBounded<Page>(200);    // 페이지는 크므로 작게
var records = Channel.CreateBounded<Record>(5000); // 레코드는 작으므로 크게

Task stage2 = RunStageAsync(urls.Reader, pages.Writer,    DownloadAsync, dop: 16, ct);
Task stage3 = RunStageAsync(pages.Reader, records.Writer, ParseAsync,    dop: 4,  ct);

static async Task RunStageAsync<TIn, TOut>(
    ChannelReader<TIn> input, ChannelWriter<TOut> output,
    Func<TIn, CancellationToken, Task<TOut>> transform, int dop, CancellationToken ct)
{
    try
    {
        await Parallel.ForEachAsync(
            input.ReadAllAsync(ct),
            new ParallelOptions { MaxDegreeOfParallelism = dop, CancellationToken = ct },
            async (item, token) => await output.WriteAsync(await transform(item, token), token));
        output.Complete();          // 다음 단계로 완료가 전파된다
    }
    catch (Exception ex) { output.Complete(ex); }
}
```

`Parallel.ForEachAsync`(50.7절)가 `IAsyncEnumerable<T>` 오버로드를 갖고 있으므로 채널과 자연스럽게 결합한다. 단계별 병렬도는 그 단계의 성격에 맞춘다 — I/O 바운드인 다운로드는 16, CPU 바운드인 파싱은 코어 수 근처로.

> **💡 각 단계의 채널 용량은 "항목 하나의 크기"에 반비례하게 잡아라**
>
> 위 예제에서 `pages` 채널만 200으로 작게 잡은 이유가 있다. HTML 페이지 하나가 평균 100 KB라면 용량 200은 최대 20 MB의 대기 메모리를 뜻한다. 같은 200을 레코드(수백 바이트)에 적용하면 아무 의미가 없고, 5000으로 잡아도 몇 MB에 불과하다.
>
> **큐 용량은 개수가 아니라 바이트로 환산해서 검토하라.** 이 계산은 51.2절에서 리틀의 법칙과 함께 다시 다룬다.

### `ChannelOptions` — 켜면 구현이 바뀌는 스위치

```csharp
public class ChannelOptions
{
    public bool SingleWriter { get; set; }                  // 기본 false
    public bool SingleReader { get; set; }                  // 기본 false
    public bool AllowSynchronousContinuations { get; set; } // 기본 false
}

public sealed class UnboundedChannelOptions : ChannelOptions { }

public sealed class BoundedChannelOptions : ChannelOptions
{
    public int Capacity { get; set; }
    public BoundedChannelFullMode FullMode { get; set; }    // 기본 Wait
}
```

`SingleReader`와 `SingleWriter`는 **최적화 힌트가 아니라 계약**이다. `true`로 설정하면 채널 팩터리가 **다른 내부 구현 클래스를 선택한다**. 동시 소비자가 하나뿐임을 알면 항목 대기열과 대기자 목록을 보호하는 잠금 대부분을 제거할 수 있고, 대기자를 여러 명 관리하는 자료구조도 필요 없어진다.

기본값(`false`)에서는 대기 중인 컨슈머 여러 명을 큐로 관리하고 항목 인출 경로에 잠금이 필요하다. `SingleReader = true`면 대기자가 최대 한 명이므로 필드 하나로 충분해지고 인출 경로의 잠금이 줄어든다. `SingleWriter = true`도 마찬가지로 삽입 경로와 경계 채널의 대기 생산자 관리를 단순화한다.

차이는 항목당 나노초 단위이고, 채널이 초당 수백만 항목을 나르는 핫 패스에서만 의미가 있다. 다만 **틀리면 정합성이 깨진다.**

> **⚠️ `SingleReader = true`인데 컨슈머가 둘이면 무슨 일이 일어나는가**
>
> 예외가 나지 않는다. 그게 문제다. 조용히 항목이 유실되거나 중복되거나 내부 상태가 깨진 채로 계속 돈다. 채널은 이 계약을 **검증하지 않는다** — 검증하는 순간 최적화의 이유가 사라지기 때문이다.
>
> 특히 조심할 것은 "지금은 컨슈머가 하나"인 코드다. 6개월 뒤 누군가 처리량을 늘리려고 `Task.Run` 하나를 더 붙이는 순간, 채널 생성 코드는 다른 파일에 있으므로 아무도 `SingleReader = true`를 보지 못한다.
>
> **`SingleReader`/`SingleWriter`를 켜려면 채널 생성 지점 바로 위에 왜 그것이 참인지 주석으로 남겨라.** 그리고 측정으로 이득을 확인하기 전에는 켜지 마라.

`await foreach`가 여러 개 도는 것만 다중 컨슈머가 아니다. `Parallel.ForEachAsync(reader.ReadAllAsync(ct), ...)`는 병렬도만큼의 동시 소비자를 만든다. 이때 `SingleReader = true`는 틀린 선언이다.

### `AllowSynchronousContinuations` — 켜면 안 되는 스위치

기본값 `false`가 뜻하는 것은 이렇다. 컨슈머가 `ReadAsync`에서 대기 중일 때 프로듀서가 `TryWrite`로 항목을 넣으면, 채널은 컨슈머의 연속(continuation)을 **스레드 풀에 큐잉**한다. `TryWrite`는 곧바로 반환하고, 컨슈머 코드는 다른 스레드에서 실행된다.

`true`로 켜면 채널은 **`TryWrite`를 호출한 그 스레드 위에서 컨슈머의 연속을 곧바로 실행한다.** 스레드 풀 큐잉 한 번과 컨텍스트 전환 한 번이 사라진다. 대신 세 가지가 딸려 온다.

1. **프로듀서가 컨슈머의 작업 시간만큼 멈춘다.** `TryWrite` 한 줄이 컨슈머의 처리 로직 전체를 실행하고 돌아온다. 프로듀서 입장에서 이 호출은 더 이상 상수 시간이 아니다.
2. **잠금 안에서 `TryWrite`를 부르면 컨슈머 코드가 그 잠금을 잡은 채로 실행된다.** 컨슈머가 같은 잠금을 다시 얻으려 하면 즉시 데드락이다. 48.8절이 말한 "잠금을 쥔 채 남의 코드를 호출하지 마라"가 여기서 함정으로 나타난다 — `TryWrite`는 남의 코드처럼 보이지 않는다.
3. **스택이 깊어진다.** 프로듀서 → 컨슈머 → (컨슈머가 다시 다른 채널에 `TryWrite`) → 다음 컨슈머 … 로 인라인 실행이 연쇄되면 스택 오버플로가 가능하다.

> **⚠️ `AllowSynchronousContinuations = true`는 "성능 옵션"이 아니다**
>
> 이름이 중립적이라 무해해 보이지만, 이 스위치는 **채널의 스레딩 계약을 바꾼다.** 켜기 전에 확인해야 할 것.
>
> - 프로듀서 스레드가 UI 스레드인가? → 절대 켜지 마라. 컨슈머 작업이 UI를 멈춘다.
> - `TryWrite`/`WriteAsync`를 잠금 안에서 부르는 곳이 하나라도 있는가? → 켜지 마라.
> - 컨슈머가 예외를 던지면 그 예외가 어디로 가는지 확인했는가?
>
> 세 질문에 자신 있게 답할 수 있고 프로파일러가 스레드 풀 큐잉을 병목으로 지목했을 때만 켠다. 그런 경우는 드물다.

### `BlockingCollection<T>` 대비

50.11절에서 개요 표를 봤다. 여기서는 **왜** 그런 차이가 나는지까지 채운다.

| 축 | `BlockingCollection<T>` | `Channel<T>` |
|---|---|---|
| 대기 방식 | `Monitor`/`SemaphoreSlim` 기반 **스레드 블로킹** | `ValueTask` 기반 **`await`** |
| 대기 중 스레드 점유 | 컨슈머 1명 = 스레드 1개 상주 | **0개** — 항목이 올 때만 스레드를 빌린다 |
| 비어 있을 때 컨슈머 비용 | 커널 대기 객체 진입(마이크로초 단위) | 연속 등록만(할당 없는 경로 존재) |
| 가득 찼을 때 프로듀서 | 스레드 블로킹 | `await` 또는 즉시 드롭(정책 선택) |
| 가득 찼을 때 정책 | **대기만** 가능 | `Wait`/`DropOldest`/`DropNewest`/`DropWrite` |
| 항목당 할당 | 대기 시 커널 객체·`SemaphoreSlim` 대기 노드 | 동기 완료 시 **0**, 비동기 대기 시 대기 노드 1 |
| 취소 | `Take(ct)` — 블로킹 상태에서 취소 | `ReadAsync(ct)` — `await` 상태에서 취소 |
| 소비 열거 | `GetConsumingEnumerable()` (`IEnumerable<T>`) | `ReadAllAsync()` (`IAsyncEnumerable<T>`) |
| 완료 신호 | `CompleteAdding()` | `Writer.Complete(Exception?)` — **예외 전달 가능** |
| 하위 컬렉션 교체 | `IProducerConsumerCollection<T>` 아무거나 | 불가(FIFO 전용 구현) |
| 단일 리더/라이터 최적화 | 없음 | `SingleReader`/`SingleWriter` |
| .NET Framework | 4.0부터 내장 | NuGet 패키지 필요 |

핵심은 세 번째 행이다. 컨슈머 8명짜리 `BlockingCollection<T>` 파이프라인은 **아무 일이 없어도 스레드 8개를 점유하고**, 같은 구성의 채널은 큐가 비어 있는 동안 스레드를 0개 쓴다. 스레드 하나의 기본 스택 예약이 1 MB(45.4절)임을 떠올리면 서버에서 이 차이가 무엇을 뜻하는지 분명하다.

> **📌 `Channel<T>`의 할당 경로**
>
> `ReadAsync`와 `WriteAsync`가 `Task` 대신 `ValueTask`를 반환하는 것은 장식이 아니다(47.13절). 항목이 이미 큐에 있으면 `ReadAsync`는 **동기적으로 완료된 `ValueTask<T>`** 를 돌려주고 힙 할당이 전혀 일어나지 않는다. 채널 구현은 대기해야 하는 경우에도 `IValueTaskSource<T>`를 구현한 재사용 가능한 객체로 대기를 표현하므로, 대기 노드조차 매번 새로 할당하지 않는다.
>
> 그래서 채널은 "초당 수백만 항목"급 처리량에서도 GC 압력을 거의 만들지 않는다. 같은 부하에서 `BlockingCollection<T>`은 대기가 발생할 때마다 커널 전이 비용을 문다.

> **📌 우선순위 채널 ※.NET 9**
>
> .NET 9에서 `Channel.CreateUnboundedPrioritized<T>()`가 추가됐다. `UnboundedPrioritizedChannelOptions<T>.Comparer`가 정한 순서대로 항목을 꺼내는 무제한 채널이다. FIFO가 아니므로 **기아(starvation)** 가 생길 수 있다 — 우선순위가 낮은 항목이 영원히 안 나올 수 있다. 채널을 둘(고우선/저우선) 두고 고우선을 먼저 확인하는 구성이면 "저우선을 N회마다 한 번은 강제로 소비"하는 기아 방지 정책을 직접 넣을 수 있다.

> **💡 채널을 언제 쓰지 말아야 하는가**
>
> - **단순 팬아웃 병렬 처리** — 입력 컬렉션이 이미 메모리에 다 있고 그냥 병렬로 돌리면 되는 경우라면 `Parallel.ForEachAsync`(50.7절) 하나면 된다. 채널을 끼우면 코드만 늘어난다.
> - **요청/응답** — 채널은 단방향이다. 응답이 필요하면 항목에 `TaskCompletionSource`를 담아 보내는 방식(46.5절)이 되는데, 이 구조가 두 개 이상 등장하면 설계를 다시 보는 게 낫다.
> - **브로드캐스트** — 한 항목을 여러 컨슈머 모두에게 보내야 한다면 채널이 아니다. `System.Reactive`의 `IObservable<T>`이나 구독자별 채널이 맞다.
> - **프로세스 경계를 넘는 큐** — 채널은 인메모리다. 프로세스가 죽으면 큐도 죽는다. 내구성이 필요하면 메시지 브로커다.

## 51.2 백프레셔와 큐 크기 설계

### 무제한 큐는 버그다

`Channel.CreateUnbounded<T>()`는 타이핑이 짧고 아무것도 결정하지 않아도 되므로 기본 선택처럼 보인다. 실제로는 **결정을 안 한 것이 아니라 최악의 결정을 한 것**이다.

무제한 큐의 계약은 이렇다. "생산 속도가 소비 속도를 넘으면 그 차이만큼 메모리에 쌓는다. 언제까지? 프로세스가 죽을 때까지."

```text
  생산율 λ_in = 초당 1000, 소비율 λ_out = 초당 800  (20% 초과)

  t=1초    큐 200개
  t=10초   큐 2,000개
  t=60초   큐 12,000개
  t=1시간  큐 720,000개
  t=?      OutOfMemoryException 또는 OOM Killer
```

여기서 두 가지 문제가 동시에 자란다.

**첫째, 메모리다.** 항목 하나가 1 KB면 한 시간 뒤 720 MB다. 이것은 GC가 회수할 수 없는 메모리다 — 큐가 참조를 붙들고 있으니 살아 있는 객체다. 66장에서 다루는 "메모리 누수"의 진단 화면에서 이 상황은 정확히 누수처럼 보인다. 큐가 2세대로 승격된 항목을 가득 채우면 2세대 GC 비용도 함께 오른다(64장).

**둘째, 지연이다.** 이쪽이 더 자주 간과된다.

### 리틀의 법칙 — 큐 길이가 곧 지연 시간이다

대기행렬 이론의 리틀의 법칙(Little's law)은 정상 상태(steady state)의 시스템에 대해 다음을 말한다.

```text
  L = λ × W

  L = 시스템 안에 있는 평균 항목 수  (큐 길이)
  λ = 평균 처리율 (초당 항목 수)
  W = 항목 하나가 시스템 안에 머무는 평균 시간 (지연)
```

여기서 우리가 필요한 형태는 `W = L / λ`다.

**큐에 항목이 12,000개 쌓여 있고 컨슈머가 초당 800개를 처리한다면, 지금 막 들어온 항목이 처리되기까지 15초가 걸린다.** 이 15초는 큐가 흡수해 준 것이 아니라 큐가 만들어 낸 것이다.

| 큐 깊이 L | 처리율 λ | 예상 지연 W = L/λ |
|---|---|---|
| 100 | 1,000/s | 100 ms |
| 1,000 | 1,000/s | 1 초 |
| 10,000 | 1,000/s | 10 초 |
| 100,000 | 1,000/s | 100 초 |

> **⚠️ 무제한 큐는 장애를 감추다가 한꺼번에 터뜨린다**
>
> 경계 큐라면 다운스트림이 느려지는 순간 프로듀서가 즉시 그것을 느낀다. 무제한 큐는 아무 신호도 주지 않는다. 대시보드의 처리량 그래프는 정상이고, 오류율도 0이고, 그러다 어느 시점에 프로세스가 OOM으로 죽거나 응답 지연이 타임아웃 한계를 넘어 **전부 실패**한다.
>
> 더 나쁜 것은 재시작 이후다. 큐에 있던 항목은 인메모리였으므로 전부 사라진다. 사용자에게는 "접수했다"고 응답해 놓고 실제로는 처리되지 않은 요청이 12,000건 생긴다.
>
> **"이 큐가 무한히 길어질 수 있는가"를 답할 수 없다면 무제한 채널을 쓰면 안 된다.**

무제한 큐가 정당한 경우는 존재한다. **생산량의 상한이 구조적으로 정해져 있을 때**다. 예를 들어 프로그램 시작 시 파일 목록 1만 개를 채널에 밀어 넣고 끝내는 경우, 큐 길이의 상한은 1만이며 그 이상 자랄 수 없다. 이때는 무제한이 오히려 단순하다.

### `BoundedChannelFullMode` — 가득 찼을 때 무엇을 할 것인가

경계 채널을 만드는 순간 "가득 찼을 때" 정책을 정해야 한다. 이것이 이 절 전체에서 가장 중요한 설계 결정이다.

```csharp
public enum BoundedChannelFullMode
{
    Wait,        // 자리가 생길 때까지 대기 (기본값)
    DropNewest,  // 큐에서 가장 최근 항목을 버리고 새 항목을 넣는다
    DropOldest,  // 큐에서 가장 오래된 항목을 버리고 새 항목을 넣는다
    DropWrite    // 지금 쓰려는 항목을 버린다
}
```

| 모드 | `WriteAsync` 동작 | `TryWrite` 반환 | 버려지는 것 | 전형적 용도 |
|---|---|---|---|---|
| `Wait` | 자리가 날 때까지 **대기** | 가득 차면 `false` | 없음 | **작업 큐** — 모든 항목이 처리돼야 함 |
| `DropOldest` | 즉시 완료 | 항상 `true` | 큐의 맨 앞 항목 | **최신 상태 스트림** — 센서값, 시세, 진행률 |
| `DropNewest` | 즉시 완료 | 항상 `true` | 큐의 맨 뒤 항목 | 드묾. 앞쪽 순서를 지키면서 상한만 두고 싶을 때 |
| `DropWrite` | 즉시 완료 | 항상 `true` | **방금 쓰려던 항목** | **부하 차단** — 텔레메트리, 감사 로그의 샘플링 |

세 개의 Drop 모드에서 `WriteAsync`는 **절대 대기하지 않고**, `TryWrite`는 **절대 `false`를 반환하지 않는다**. 즉 이 모드들에서는 백프레셔가 발생하지 않는다. 대신 데이터가 조용히 사라진다.

> **⚠️ Drop 모드에서 `TryWrite`의 반환값은 "성공"을 뜻하지 않는다**
>
> ```csharp
> var ch = Channel.CreateBounded<Metric>(
>     new BoundedChannelOptions(100) { FullMode = BoundedChannelFullMode.DropWrite });
>
> if (ch.Writer.TryWrite(metric))
>     _sentCount++;              // 틀렸다 — 항목이 버려졌어도 true다
> ```
>
> `DropWrite` 모드에서 큐가 가득 차면 `TryWrite`는 **항목을 버리고 `true`를 반환한다.** "쓰기 연산은 성공했다"는 의미이지 "항목이 큐에 들어갔다"는 의미가 아니다. 유일하게 `false`가 나오는 경우는 채널이 이미 `Complete()` 된 경우다.
>
> 버려진 항목을 세고 싶으면 아래의 `itemDropped` 콜백을 써야 한다.

### 버려진 항목 관측하기 ※.NET 7

.NET 7에서 드롭 콜백을 받는 오버로드가 추가됐다.

```csharp
private long _dropped;

var ch = Channel.CreateBounded<LogRecord>(
    new BoundedChannelOptions(10_000)
    {
        FullMode = BoundedChannelFullMode.DropWrite,
        SingleReader = true
    },
    itemDropped: _ => Interlocked.Increment(ref _dropped));   // ※.NET 7
```

콜백은 **항목을 버린 스레드 위에서 동기적으로** 호출된다. 그러니 여기서 무거운 일을 하면 안 된다. 카운터 증가나 이미 준비된 메트릭 기록 정도가 적당하다. 로그를 남기려는 유혹이 특히 위험하다 — 로그 채널이 가득 차서 항목을 버리는 상황인데 그 사실을 로그로 남기면 무한 재귀에 가까운 부하가 된다.

> **💡 드롭은 반드시 세라**
>
> 부하 차단은 정당한 설계이지만 **관측되지 않는 부하 차단은 데이터 손실**이다. `DropWrite`·`DropOldest`를 쓰기로 했다면 드롭 카운터를 메트릭으로 내보내는 것까지가 한 세트다. 이 숫자가 0에서 벗어나는 순간이 곧 "용량이 부족하다"는 신호이며, 이것이 무제한 큐가 절대 줄 수 없는 정보다.

### 백프레셔는 어떻게 전파되는가

`FullMode.Wait`가 만드는 연쇄를 따라가 보자.

```text
  ┌─────────┐   WriteAsync   ┌───────────┐   ReadAllAsync   ┌──────────┐
  │ Producer│ ─────────────→ │ Channel   │ ───────────────→ │ Consumer │
  └─────────┘                │  cap=100  │                  └────┬─────┘
       ↑                     └───────────┘                       │
       │                          ▓▓▓▓▓ 가득                     ↓
       │                                                   느린 다운스트림
       │                                                   (DB / 외부 API)
       │
       └──── ① 컨슈머가 느려진다
             ② 큐가 찬다
             ③ WriteAsync 가 대기한다        ← 백프레셔
             ④ 프로듀서 루프가 느려진다
             ⑤ 프로듀서의 입력원(HTTP 핸들러 등)도 느려진다
             ⑥ 결국 클라이언트가 느려지거나 429를 받는다
```

핵심은 **③에서 ⑥까지가 자동으로 이어져야 한다**는 점이다. 중간 어디선가 끊기면 백프레셔는 그 지점에서 증발하고, 끊긴 지점 앞에 무제한 큐가 하나 생긴 것과 같아진다.

가장 흔한 끊김은 이것이다.

```csharp
// ⚠️ 백프레셔가 여기서 죽는다
[HttpPost("/orders")]
public IActionResult Submit(Order order)
{
    _ = _writer.WriteAsync(order);   // 반환된 ValueTask를 버렸다
    return Accepted();
}
```

`WriteAsync`가 반환한 `ValueTask`를 버리면 "쓸 자리가 생길 때까지 기다린다"는 의미가 사라진다. 요청은 즉시 202를 받고, 큐에는 대기 중인 쓰기 작업이 무한히 쌓인다. 채널에 경계를 준 의미가 완전히 없어졌을 뿐 아니라, `ValueTask`를 버리는 것 자체가 잘못된 사용이다(47.13절 — `ValueTask`는 한 번만 소비해야 한다).

```csharp
// 백프레셔를 요청 처리까지 전파하는 형태
[HttpPost("/orders")]
public async Task<IActionResult> Submit(Order order, CancellationToken ct)
{
    await _writer.WriteAsync(order, ct);   // 큐가 차 있으면 여기서 기다린다
    return Accepted();
}
```

이제 큐가 가득 차면 **요청 스레드가 아니라 요청이** 기다린다(`await`이므로 스레드는 반납된다). 클라이언트의 응답 시간이 늘어나고, 그것이 클라이언트 쪽 타임아웃과 재시도 정책을 자극하며, 결국 부하가 상류로 되밀린다.

### 부하 차단인가, 대기인가

둘은 다른 실패 모드를 고른 것이다.

| | **대기** (`FullMode.Wait`) | **부하 차단** (`Drop*` 또는 즉시 거절) |
|---|---|---|
| 데이터 | 전부 보존 | 일부 유실 |
| 지연 | 큐가 찰수록 증가 | **상한이 유지된다** |
| 실패 모드 | 느려짐 → 타임아웃 연쇄 | 명시적 거절(429 등) |
| 클라이언트가 아는가 | 늦게 안다 | **즉시 안다** |
| 적합한 데이터 | 주문, 결제, 명령 | 메트릭, 로그, 실시간 시세 |

실무에서 가장 좋은 형태는 대개 **혼합**이다. 짧게 기다려 보고, 그래도 안 되면 거절한다.

```csharp
public async Task<bool> TryEnqueueAsync(Order order, CancellationToken ct)
{
    using var timeout = CancellationTokenSource.CreateLinkedTokenSource(ct);
    timeout.CancelAfter(TimeSpan.FromMilliseconds(200));   // 여기까지만 견딘다
    try
    {
        await _writer.WriteAsync(order, timeout.Token);
        return true;
    }
    catch (OperationCanceledException) when (!ct.IsCancellationRequested)
    {
        return false;      // 큐 포화 — 호출자가 503/429로 응답한다
    }
}
```

`when (!ct.IsCancellationRequested)` 필터가 "내가 건 타임아웃"과 "호출자의 취소"를 구분한다. 이 판별법은 51.4절에서 자세히 다룬다.

> **📌 ASP.NET Core에는 요청 단위 부하 차단 미들웨어가 있다 ※.NET 7**
>
> `System.Threading.RateLimiting`과 `app.UseRateLimiter()`로 동시 요청 수·초당 요청 수에 상한을 두고 초과분을 503으로 거절할 수 있다. 채널 레벨의 백프레셔가 마지막 방어선이라면, 이쪽은 **입구에서 미리 막는** 층이다. 둘은 대체 관계가 아니라 계층 관계다.

### 큐 크기를 정하는 법

용량을 "적당히 1000" 같은 식으로 정하지 않으려면 계산의 출발점이 필요하다. 리틀의 법칙을 뒤집으면 된다.

```text
  용량 = 허용 지연(초) × 소비 처리율(초당 항목)
```

예를 들어 컨슈머가 초당 500건을 처리하고, 큐에서의 대기 시간을 2초 이내로 유지하고 싶다면 용량은 1,000이다. 큐가 그 이상 자라는 것은 이미 SLA 위반이므로, 자라게 두는 대신 백프레셔나 거절로 바꾸는 편이 낫다.

여기에 두 가지 보정을 더한다.

1. **버스트 흡수분** — 트래픽이 순간적으로 몰리는 폭을 흡수하려면 그만큼 여유가 필요하다. 평균 대비 3배 버스트가 500 ms 지속된다면 `500/s × 3 × 0.5s = 750`의 여유가 추가로 필요하다.
2. **메모리 상한** — 계산 결과가 메모리 예산을 넘으면 용량이 아니라 **처리율을 올려야 한다**. 항목 하나가 100 KB인데 용량 1,000이면 100 MB다.

| 큐 유형 | 항목 크기 | 처리율 | 허용 지연 | 권장 용량(예시) |
|---|---|---|---|---|
| 주문 처리 | 1 KB | 500/s | 2 s | 1,000 (약 1 MB) |
| 이미지 리사이즈 | 5 MB | 20/s | 5 s | **10~20** (약 100 MB) |
| 로그 배출 | 500 B | 50,000/s | 100 ms | 5,000 (약 2.5 MB) |
| UI 진행률 | 100 B | 60/s | 16 ms | **1** (`DropOldest`) |

이 표의 값은 계산 방법을 보이기 위한 **예시**이며 실측치가 아니다. 마지막 행이 중요하다 — UI 진행률처럼 "최신값만 의미 있는" 스트림의 정답은 용량 1 + `DropOldest`다. 그러면 채널은 큐가 아니라 **최신 값 하나를 담는 슬롯**이 되고, UI는 항상 가장 최근 상태만 그린다.

> **💡 용량 1 채널은 큐가 아니라 랑데부에 가깝다**
>
> `Channel.CreateBounded<T>(1)` + `FullMode.Wait`는 프로듀서와 컨슈머를 거의 보조를 맞춰 움직이게 만든다. 프로듀서는 컨슈머가 이전 항목을 꺼내야 다음을 넣을 수 있다. 파이프라인 단계 사이에서 **버퍼링을 원치 않을 때**(예: 각 단계가 큰 객체를 다뤄서 메모리를 최소화해야 할 때) 쓸모 있는 구성이다.
>
> 반대로 용량 1 + `DropOldest`는 "최신값 슬롯"이다. 같은 숫자 1인데 두 정책의 의미가 완전히 다르다.

### 다단 큐의 지연은 더해진다

파이프라인이 세 단계이고 각 단계 큐가 2초씩 지연을 흡수하도록 잡혔다면, 최악의 종단 간 지연은 6초다. 여기에 각 단계의 처리 시간이 더 붙는다.

```text
  Stage1 큐(2s) → 처리(0.1s) → Stage2 큐(2s) → 처리(0.5s) → Stage3 큐(2s) → 처리(0.2s)
  ────────────────────────────────────────────────────────────────────────────────────
  종단 간 최악 지연 = 2 + 0.1 + 2 + 0.5 + 2 + 0.2 = 6.8초
```

> **⚠️ "단계별로는 다 정상"인데 종단 간 SLA를 못 맞추는 전형**
>
> 각 단계의 큐 깊이를 따로 모니터링하면 어느 것도 경보를 울리지 않는다. 모두 설계 범위 안이기 때문이다. 그런데 사용자가 보는 지연은 그 합이다.
>
> **종단 간 지연을 직접 측정하라.** 항목이 파이프라인에 들어간 시각을 항목 자체에 담아 두고, 마지막 단계에서 그 차이를 히스토그램으로 기록하는 것이 가장 확실하다.
>
> ```csharp
> public readonly record struct Envelope<T>(T Payload, long EnqueuedTicks);
>
> // 마지막 단계
> var latency = TimeSpan.FromTicks(Stopwatch.GetTimestamp() - env.EnqueuedTicks);
> _latencyHistogram.Record(latency.TotalMilliseconds);
> ```
>
> `Stopwatch.GetTimestamp()`를 쓰는 이유는 `DateTime.UtcNow`보다 해상도가 높고 시스템 시계 변경에 영향받지 않기 때문이다(73.8절).

### 무엇을 모니터링할 것인가

큐를 도입했다면 다음 네 가지는 반드시 내보내야 한다.

| 지표 | 얻는 법 | 무엇을 말해 주는가 |
|---|---|---|
| **큐 깊이** | `reader.Count` (`CanCount`가 `true`일 때) | 지금 얼마나 밀려 있는가 |
| **대기 시간** | 항목에 타임스탬프를 심고 소비 시 차이 계산 | 실제 사용자 체감 지연 |
| **드롭 수** | `itemDropped` 콜백의 카운터 | 용량이 부족한가 |
| **프로듀서 대기 시간** | `WriteAsync` 앞뒤 시간 측정 | 백프레셔가 실제로 걸리고 있는가 |

```csharp
// 큐 깊이 게이지 — ObservableGauge는 System.Diagnostics.Metrics (75.3절)
private readonly Meter _meter = new("MyApp.Pipeline");

public PipelineMetrics(ChannelReader<Order> reader)
    => _meter.CreateObservableGauge("orders.queue.depth",
           () => reader.CanCount ? reader.Count : -1);
```

> **⚠️ `ChannelReader<T>.Count`는 모든 채널에서 지원되지 않는다**
>
> `CanCount`가 `false`인 구현이 있다. 특히 `SingleReader = true`로 만든 무제한 채널의 일부 구현이 그렇다. `Count`를 그냥 읽으면 `NotSupportedException`이 발생한다. **반드시 `CanCount`를 먼저 확인하라.**
>
> `CanCount`가 `false`인 경우에는 프로듀서 쪽과 컨슈머 쪽에서 각각 `Interlocked.Increment`/`Decrement`로 직접 세는 수밖에 없다. 카운터 하나 정도의 비용은 채널 자체의 비용에 비하면 무시할 만하다.

> **💡 큐 깊이 경보의 임계값은 절대값이 아니라 지속 시간으로 잡아라**
>
> "큐 깊이 > 500이면 경보"는 버스트마다 울린다. 쓸모 있는 규칙은 "큐 깊이 > 용량의 50%가 60초 이상 지속"이다. 전자는 순간 부하를, 후자는 **처리율 부족**을 잡는다. 큐는 원래 버스트를 흡수하라고 있는 것이므로 잠깐 차는 것은 정상 동작이다.
>
> 반대로 큐 깊이가 **항상 0**인 것도 정보다. 큐가 필요 없거나 프로듀서가 병목이라는 뜻이다.

## 51.3 비동기 잠금 — `SemaphoreSlim`을 async lock으로

### `lock` 안에서 `await`는 컴파일되지 않는다

```csharp
lock (_locker)
{
    await Task.Delay(1000);   // 컴파일 오류 CS1996
}
```

오류 메시지는 "Cannot await in the body of a lock statement"다. 컴파일러가 막는다.

이것은 임의의 제약이 아니라 **`Monitor`의 근본 구조에서 따라 나오는 결과**다. 47.10절에서 본 대로 `lock` 문은 다음으로 확장된다.

```csharp
// C# 12 이전, object 잠금 대상일 때
bool __lockTaken = false;
try
{
    Monitor.Enter(_locker, ref __lockTaken);
    // 본문
}
finally
{
    if (__lockTaken) Monitor.Exit(_locker);
}
```

`Monitor`는 **스레드 친화적(thread-affine)** 이다. 잠금을 획득한 스레드의 ID가 잠금 객체의 헤더에 기록되고(48.5절), `Monitor.Exit`는 **그 스레드에서만** 호출할 수 있다. 다른 스레드가 `Exit`를 부르면 `SynchronizationLockException`이 발생한다.

이제 `await`가 무엇을 하는지 겹쳐 보자(47.4절). `await`는 메서드를 중단하고 반환한다. 재개는 **다른 스레드**에서 일어날 수 있다. 즉 `Monitor.Enter`를 한 스레드와 `Monitor.Exit`를 하려는 스레드가 달라진다. 정확히 `SynchronizationLockException`의 조건이다.

문제는 그것만이 아니다. `await` 지점에서 스레드가 반환되는 동안에도 **잠금은 계속 잡혀 있다.** 상태 기계는 지역 변수를 필드로 옮겼을 뿐 `Monitor`의 소유권까지 옮길 방법이 없다. 그 결과 "아무 스레드도 실행하고 있지 않은데 잠금은 잡혀 있는" 상태가 만들어지고, 다른 스레드가 그 잠금을 기다리면서 블로킹한다. 비동기로 얻으려던 것을 전부 잃는다.

| | `lock` / `Monitor` | `SemaphoreSlim(1,1)` |
|---|---|---|
| 소유권 | **스레드가 소유** | 소유자 없음 — 카운트만 있다 |
| 해제 가능 주체 | 획득한 스레드만 | **아무 스레드나** |
| 재진입 | **가능**(같은 스레드는 다시 들어감) | **불가능** — 자기 자신과 데드락 |
| 대기 방식 | 블로킹(스핀 후 커널 대기) | `Wait()` 블로킹 / `WaitAsync()` 비동기 |
| `await` 가능 | 불가(CS1996) | **가능** |
| 취소 | 불가 | `WaitAsync(ct)` |
| 비용(무경합) | 20 ns 미만 수준 | `Semaphore`의 1/10 수준(원천 실측) |
| 잘못된 해제 | `SynchronizationLockException` | `SemaphoreFullException`(상한 초과 시) |

### 정석 — `SemaphoreSlim(1, 1)` + `try/finally`

```csharp
private readonly SemaphoreSlim _gate = new(1, 1);   // 초기 1, 최대 1

public async Task<Config> LoadAsync(CancellationToken ct)
{
    await _gate.WaitAsync(ct);
    try
    {
        if (_cached is not null) return _cached;
        _cached = await FetchFromNetworkAsync(ct);
        return _cached;
    }
    finally
    {
        _gate.Release();
    }
}
```

생성자의 두 번째 인자 `maxCount: 1`을 빠뜨리지 마라. `new SemaphoreSlim(1)`도 초기 카운트 1로 동작하지만 상한이 없어서, `Release`를 실수로 두 번 부르면 카운트가 2가 되고 **두 스레드가 동시에 임계 구역에 들어간다.** `new SemaphoreSlim(1, 1)`이면 두 번째 `Release`가 `SemaphoreFullException`을 던져 버그가 즉시 드러난다.

> **⚠️ `WaitAsync`를 `try` 안에 넣으면 안 된다**
>
> ```csharp
> // 틀렸다
> try
> {
>     await _gate.WaitAsync(ct);   // 여기서 취소되면 잠금을 얻지 못했는데
>     DoWork();
> }
> finally
> {
>     _gate.Release();             // 얻지도 않은 것을 반환한다
> }
> ```
>
> `WaitAsync(ct)`가 취소되면 `OperationCanceledException`을 던지며 **잠금을 획득하지 않은 채로** 빠져나간다. 그런데 `finally`는 실행되므로 `Release()`가 호출되고, 세마포어 카운트가 1 늘어난다. `maxCount = 1`이면 `SemaphoreFullException`이 나서 그나마 드러나지만, `maxCount`를 지정하지 않았다면 **카운트가 조용히 늘어나 상호 배제가 깨진다.**
>
> 규칙은 하나다. **`WaitAsync`는 `try` 바로 앞에 둔다.** 이것은 `lock`의 확장 형태(`Monitor.Enter`가 `try` 밖)와 정확히 같은 구조다.

### `IDisposable` 스코프로 감싸기

`try/finally`를 매번 쓰는 것은 잊기 쉽다. `using`으로 강제하는 관용구가 있다.

```csharp
public static class SemaphoreSlimExtensions
{
    public static async ValueTask<IDisposable> EnterAsync(
        this SemaphoreSlim semaphore, CancellationToken ct = default)
    {
        await semaphore.WaitAsync(ct).ConfigureAwait(false);
        return new Releaser(semaphore);
    }

    private sealed class Releaser(SemaphoreSlim semaphore) : IDisposable
    {
        private SemaphoreSlim? _semaphore = semaphore;

        // Interlocked.Exchange로 이중 Dispose를 막는다
        public void Dispose() => Interlocked.Exchange(ref _semaphore, null)?.Release();
    }
}
```

사용하는 쪽은 이렇게 된다.

```csharp
public async Task<Config> LoadAsync(CancellationToken ct)
{
    using (await _gate.EnterAsync(ct))
    {
        if (_cached is not null) return _cached;
        _cached = await FetchFromNetworkAsync(ct);
        return _cached;
    }
}
```

세 가지가 중요하다.

- **`await`가 `using` 안이 아니라 `using`의 괄호 안에 있다.** `using (await ...)`이므로 획득에 실패하면 `Releaser`가 만들어지지 않고 `Dispose`도 호출되지 않는다. 위 함정이 구조적으로 막힌다.
- **`Releaser`가 `class`인 이유.** `struct`로 만들면 `IDisposable`로 박싱되거나, 값 복사로 인해 `Dispose`가 여러 번 호출될 위험이 생긴다. `Interlocked.Exchange`로 한 번만 해제되게 하는 방어까지 넣었다.
- **`ConfigureAwait(false)`** — 라이브러리성 코드이므로 컨텍스트를 되찾을 이유가 없다(47.12절).

> **📌 왜 BCL에 `AsyncLock`이 없는가**
>
> `SemaphoreSlim(1,1)`이 이미 그 일을 하고, "비동기 잠금"이라는 이름을 가진 타입이 생기면 사람들이 `lock`처럼 쓸 것이기 때문이다 — 즉 재진입을 기대할 것이다. 재진입 가능한 비동기 잠금은 "같은 논리 흐름"을 정의해야 하는데, 그 정의는 `AsyncLocal<T>`(49.9절)에 의존하고 흐름이 갈라질 때 의미가 모호해진다.
>
> 결과적으로 .NET은 이름 없는 관용구를 남겨 두는 쪽을 택했다. `System.Threading.Lock`(48.15절 ※C# 13)도 **동기 전용**이며 `await`를 지원하지 않는다.

### 재진입이 안 된다 — 가장 잘 잡히지 않는 데드락

`lock`은 재진입 가능하다. 같은 스레드가 이미 가진 잠금에 다시 들어가면 카운트만 올라간다(48.7절). 이 성질에 익숙해진 채로 async lock을 쓰면 다음과 같은 코드를 쓰게 된다.

```csharp
private readonly SemaphoreSlim _gate = new(1, 1);

public async Task OuterAsync()
{
    await _gate.WaitAsync();
    try
    {
        await InnerAsync();      // (X) 여기서 영원히 멈춘다
    }
    finally { _gate.Release(); }
}

private async Task InnerAsync()
{
    await _gate.WaitAsync();     // 카운트가 0이므로 대기 — 해제할 주체는 나 자신
    try { /* ... */ }
    finally { _gate.Release(); }
}
```

`SemaphoreSlim`에는 소유자 개념이 없으므로 "이미 내가 가진 잠금"이라는 판단을 할 수가 없다. 카운트는 0이고 대기한다. 그 대기를 풀어 줄 `Release`는 `OuterAsync`의 `finally`에 있는데, `OuterAsync`는 `InnerAsync`를 기다리고 있다. **완전한 자기 데드락**이다.

> **⚠️ 이 데드락은 프로덕션에서만 터진다**
>
> - **CPU를 쓰지 않는다.** CPU 그래프는 평온하다.
> - **예외가 없다.** 로그에 아무것도 안 남는다.
> - **호출 경로가 길면 코드 리뷰로 안 보인다.** `OuterAsync → ServiceA → ServiceB → InnerAsync`처럼 세 단계를 거치면 같은 세마포어를 두 번 잡는다는 사실이 어느 파일에서도 드러나지 않는다.
> - **가상 메서드나 이벤트를 거치면 정적 분석도 못 잡는다.**
>
> 진단은 사실상 덤프 분석뿐이다. `dotnet-dump`로 덤프를 뜨고 비동기 스택(74.4절)에서 `SemaphoreSlim.WaitAsync`의 연속에 걸린 상태 기계를 찾는 식이다.
>
> 예방책은 규칙이다. **세마포어를 잡은 상태에서 다른 컴포넌트의 메서드를 호출하지 마라.** 48.8절에서 "잠금을 쥔 채 남의 코드를 호출하지 마라"고 한 것과 같은 규칙인데, 재진입이 불가능하므로 async lock에서는 훨씬 더 엄격하게 지켜야 한다.

### 임계 구역을 좁히기

위 규칙을 지키는 실무적 방법은 **잠금 안에서는 순수한 상태 갱신만** 하는 것이다.

```csharp
// 나쁨 — 네트워크 호출이 잠금 안에 있다
using (await _gate.EnterAsync(ct))
{
    var data = await _http.GetFromJsonAsync<Data>(url, ct);   // 수백 ms
    _state = Transform(data);
}

// 나음 — 잠금 밖에서 준비하고 잠금 안에서는 교체만
Data data = await _http.GetFromJsonAsync<Data>(url, ct);
Snapshot next = Transform(data);
using (await _gate.EnterAsync(ct))
{
    _state = next;              // 수십 나노초
}
```

두 번째 형태에는 "여러 요청이 동시에 네트워크를 때린다"는 다른 문제가 있으므로, 캐시 스탬피드를 막아야 한다면 51.4절의 동시성 제한이나 `Lazy<Task<T>>` 관용구를 함께 써야 한다. 요점은 **잠금의 길이와 그 안에서 하는 일의 종류를 의식적으로 고르라**는 것이다.

### 애초에 잠금이 필요 없게 만드는 세 가지 대안

async lock은 최후의 수단이어야 한다. 셋 중 하나가 적용되면 그쪽이 거의 항상 낫다.

**대안 1 — 채널로 직렬화한다(액터 모델).**

상태를 만지는 코드가 한 곳뿐이면 잠금이 필요 없다. 모든 변경 요청을 채널에 넣고, 단일 소비 루프가 순차 처리한다.

```csharp
public sealed class AccountActor : IAsyncDisposable
{
    private readonly Channel<Func<AccountState, AccountState>> _mailbox
        = Channel.CreateUnbounded<Func<AccountState, AccountState>>(
            new UnboundedChannelOptions { SingleReader = true });

    private AccountState _state = AccountState.Empty;   // 이 필드는 루프만 만진다
    private readonly Task _loop;

    public AccountActor() => _loop = RunAsync();

    // 소비자가 하나뿐이므로 _state 접근은 자동으로 직렬화된다
    private async Task RunAsync()
    {
        await foreach (var mutate in _mailbox.Reader.ReadAllAsync())
            _state = mutate(_state);
    }

    public ValueTask DepositAsync(decimal amount)
        => _mailbox.Writer.WriteAsync(s => s with { Balance = s.Balance + amount });

    public async ValueTask DisposeAsync()
    {
        _mailbox.Writer.Complete();
        await _loop;
    }
}
```

잠금이 하나도 없다. 상호 배제는 "소비 루프가 하나"라는 구조가 보장한다. 재진입 데드락도 원리적으로 불가능하다 — 루프는 자기 자신을 기다릴 수 없다.

**대안 2 — 불변 스냅숏 교체 + `Interlocked.Exchange`.**

읽기가 압도적으로 많고 쓰기가 드물면, 상태를 불변 객체로 만들고 참조만 원자적으로 바꾼다.

```csharp
private ImmutableDictionary<string, Rate> _rates = ImmutableDictionary<string, Rate>.Empty;

// 읽기 — 잠금 없음, 대기 없음
public Rate? Lookup(string symbol)
    => Volatile.Read(ref _rates).TryGetValue(symbol, out var r) ? r : null;

// 쓰기 — CAS 루프
public void Upsert(string symbol, Rate rate)
{
    ImmutableDictionary<string, Rate> snapshot, updated;
    do
    {
        snapshot = Volatile.Read(ref _rates);
        updated  = snapshot.SetItem(symbol, rate);
    }
    while (!ReferenceEquals(
        Interlocked.CompareExchange(ref _rates, updated, snapshot), snapshot));
}
```

읽는 쪽은 완전히 잠금이 없고 `await`도 필요 없다. 참조 대입은 원자적이므로(48.2절) 읽는 스레드는 항상 **일관된 스냅숏 하나**를 본다 — 반쯤 갱신된 상태를 볼 수 없다. 48.4절의 `Interlocked.CompareExchange` 패턴 그대로다.

이 방식의 비용은 명확하다. 쓸 때마다 새 컬렉션을 만든다(구조 공유가 있으므로 전체 복사는 아니다). 쓰기가 잦으면 CAS 루프의 재시도도 늘어난다. **읽기 : 쓰기 비율이 100:1 이상**일 때 유효한 선택이다.

**대안 3 — 값을 한 번만 만들고 공유한다(`Lazy<Task<T>>`).**

"비싼 초기화를 정확히 한 번만"이 목적이라면 잠금이 아니라 지연 초기화의 문제다.

```csharp
private readonly Lazy<Task<Config>> _config;

public ConfigProvider(HttpClient http)
    => _config = new Lazy<Task<Config>>(
        () => http.GetFromJsonAsync<Config>("/config")!,
        LazyThreadSafetyMode.ExecutionAndPublication);

public Task<Config> GetAsync() => _config.Value;   // 여러 호출자가 같은 Task를 await
```

`Lazy<T>`가 팩터리를 한 번만 호출하도록 보장하고, 반환된 `Task<Config>` 하나를 모든 호출자가 `await` 한다. 잠금 안에서 `await` 하는 문제 자체가 생기지 않는다.

> **⚠️ `Lazy<Task<T>>`는 실패를 영구히 캐시한다**
>
> 팩터리가 만든 `Task`가 실패하면 그 실패한 `Task`가 `_config.Value`에 영원히 남는다. 이후 모든 호출자가 같은 예외를 받는다. 재시도가 필요하면 실패 시 `Lazy` 인스턴스 자체를 교체하는 로직(`Interlocked.CompareExchange`)을 추가해야 한다.
>
> `LazyThreadSafetyMode.PublicationOnly`로 만들면 팩터리가 여러 번 호출될 수 있지만 실패가 캐시되지 않는다. 어느 쪽이 맞는지는 팩터리의 비용과 부작용에 달렸다.

### 동시성 제한 — 카운트가 1이 아닌 세마포어

`SemaphoreSlim`의 원래 용도는 상호 배제가 아니라 **동시 실행 수 제한**이다(48.11절). 다운스트림을 보호하는 데 이 쪽이 훨씬 자주 쓰인다.

```csharp
// 외부 API에 동시 요청 10개까지만
private readonly SemaphoreSlim _limiter = new(10, 10);

public async Task<byte[]> DownloadAsync(string uri, CancellationToken ct)
{
    await _limiter.WaitAsync(ct);
    try
    {
        return await _http.GetByteArrayAsync(uri, ct);
    }
    finally { _limiter.Release(); }
}
```

이 코드는 원천의 `DownloadWithSemaphoreAsync` 예제와 같은 구조다. 다만 실무에서는 대안 두 가지를 먼저 검토할 만하다.

| 방법 | 적합한 상황 | 한계 |
|---|---|---|
| `SemaphoreSlim(n, n)` | 임의의 호출 지점에서 상한을 걸 때 | 대기열 길이 제어 불가 — 대기자가 무한히 쌓일 수 있다 |
| `Parallel.ForEachAsync` (50.7절) | 처리할 컬렉션이 이미 있을 때 | 컬렉션 형태여야 함 |
| `System.Threading.RateLimiting` ※.NET 7 | 대기열 상한·거절 정책까지 필요할 때 | 별도 개념 학습 필요 |

> **⚠️ `SemaphoreSlim`으로 동시성을 제한하면 대기열은 여전히 무제한이다**
>
> `WaitAsync`를 기다리는 호출자 수에는 상한이 없다. 동시 실행은 10개로 묶었지만 대기자가 10,000명이면 메모리도 지연도 그만큼 늘어난다. 51.2절이 큐에 대해 말한 것이 여기서도 그대로 적용된다 — **제한한 것은 처리량이지 큐가 아니다.**
>
> 대기열에도 상한이 필요하면 `WaitAsync(timeout)` 오버로드로 짧게 기다렸다 실패시키거나, `RateLimiting`의 `ConcurrencyLimiter`처럼 대기열 길이 옵션이 있는 도구를 쓴다.

> **💡 `SemaphoreSlim`은 언제 `Dispose` 해야 하는가**
>
> `SemaphoreSlim`은 `IDisposable`이지만, `AvailableWaitHandle` 속성을 한 번도 읽지 않았다면 내부에 커널 핸들을 만들지 않는다. 그래도 필드로 보유한다면 소유 타입의 `Dispose`에서 함께 정리하는 것이 규칙이다(33장).
>
> 단, **대기 중인 호출자가 있는 상태에서 `Dispose`하면 그 대기자들은 `ObjectDisposedException`을 받지 못하고 영원히 대기할 수 있다.** 정리 순서를 확실히 하려면 먼저 취소 토큰으로 모든 대기자를 깨우고, 그다음에 `Dispose` 한다.

## 51.4 타임아웃 · 재시도 · 취소의 결합

### 세 가지는 서로 다른 것을 말한다

셋을 한 절에 묶는 이유는 실무에서 늘 함께 등장하고, 함께 잘못 조합되기 때문이다. 먼저 구분부터.

| | 누가 시작하는가 | 무엇을 뜻하는가 | 결과 |
|---|---|---|---|
| **취소** | 사용자·상위 호출자 | "더 이상 결과가 필요 없다" | `OperationCanceledException` |
| **타임아웃** | 나 자신(정책) | "이 시간 안에 안 끝나면 포기한다" | 보통 `TimeoutException` 또는 `OperationCanceledException` |
| **재시도** | 나 자신(정책) | "실패했지만 다시 하면 될 수도 있다" | 성공 또는 마지막 예외 |

취소와 타임아웃은 **같은 메커니즘**(`CancellationToken`)으로 구현되지만 **다른 의미**를 갖는다. 이 구분을 잃어버리면 "사용자가 취소했는데 재시도하는" 코드가 나온다.

### 링크된 토큰 — 타임아웃과 사용자 취소를 합치기

`CancellationTokenSource.CreateLinkedTokenSource`는 여러 토큰 중 **하나라도** 취소되면 함께 취소되는 새 소스를 만든다(46.8절).

```csharp
public async Task<Report> GenerateAsync(CancellationToken userToken)
{
    using var cts = CancellationTokenSource.CreateLinkedTokenSource(userToken);
    cts.CancelAfter(TimeSpan.FromSeconds(30));      // 30초 타임아웃

    // cts.Token 은 "사용자가 취소" 또는 "30초 경과" 중 먼저 오는 쪽에서 취소된다
    var data = await _repo.QueryAsync(cts.Token);
    return await RenderAsync(data, cts.Token);
}
```

토큰 하나만 있으면 되는 경우에는 생성자로 더 짧게 쓸 수 있다.

```csharp
using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(30));
```

> **⚠️ 링크된 `CancellationTokenSource`는 반드시 `Dispose` 해야 한다**
>
> `CreateLinkedTokenSource`는 부모 토큰들에 **콜백을 등록한다.** `Dispose`하지 않으면 그 등록이 부모 토큰의 콜백 목록에 남는다. 부모가 요청 단위 토큰(`HttpContext.RequestAborted`)이라면 요청이 끝날 때 함께 정리되므로 피해가 작지만, 부모가 **애플리케이션 수명 토큰**(`IHostApplicationLifetime.ApplicationStopping`)이라면 이야기가 다르다.
>
> 그 토큰은 프로세스가 살아 있는 내내 존재하고, 링크할 때마다 콜백이 하나씩 붙는다. 초당 100 요청이면 하루에 860만 개가 쌓인다. **전형적인 메모리 누수이고, 66.11절이 나열한 대표 시나리오 중 하나다.**
>
> `CancelAfter`가 내부 타이머를 예약한다는 점도 같은 이유로 `Dispose`를 필요하게 만든다. `using`을 빠뜨리지 마라.

### `Task.WaitAsync` ※.NET 6

.NET 6부터 `Task`/`Task<T>`에 다음 오버로드가 생겼다.

```csharp
public Task WaitAsync(TimeSpan timeout);
public Task WaitAsync(CancellationToken cancellationToken);
public Task WaitAsync(TimeSpan timeout, CancellationToken cancellationToken);
```

이전에는 `Task.WhenAny(task, Task.Delay(timeout))` 패턴을 직접 짜야 했다(46.9절). `WaitAsync`는 그것을 대체하고, 타임아웃 시 **`TimeoutException`** 을 던진다.

```csharp
try
{
    Result r = await LongOperationAsync().WaitAsync(TimeSpan.FromSeconds(5), ct);
}
catch (TimeoutException)
{
    // 5초 안에 안 끝났다
}
catch (OperationCanceledException)
{
    // ct 가 취소됐다
}
```

`TimeoutException`과 `OperationCanceledException`이 갈리므로 예외 타입만으로 원인을 구분할 수 있다. `CancelAfter` 방식은 둘 다 `OperationCanceledException`이 되어 구분이 더 번거롭다.

> **⚠️ `WaitAsync`는 대상 작업을 멈추지 않는다**
>
> 이것이 이 절 전체에서 가장 중요한 문장이다. `WaitAsync(5초)`가 `TimeoutException`을 던진 뒤에도 **원래 `Task`는 계속 실행된다.** 데이터베이스 쿼리는 계속 돌고, HTTP 요청은 계속 나가 있고, 파일은 계속 쓰이고 있다.
>
> 46.9절에서 `Task.WhenAny`의 함정으로 본 것과 정확히 같은 문제다. 관찰을 그만두는 것과 실행을 멈추는 것은 다르다.
>
> 결과는 세 가지다.
>
> 1. **자원이 계속 점유된다.** DB 커넥션, 소켓, 파일 핸들.
> 2. **버려진 작업의 예외가 관찰되지 않는다**(46.11절).
> 3. **부작용이 나중에 일어난다.** "타임아웃돼서 재시도했는데 원래 요청도 결국 성공해서 주문이 두 번 들어갔다."
>
> **진짜로 멈추려면 취소 토큰이 대상까지 전달돼야 한다.** `LongOperationAsync()`가 토큰을 받지 않는다면 `WaitAsync`로는 아무것도 취소할 수 없다.

```csharp
// 나쁨 — 타임아웃은 걸리지만 작업은 계속 돈다
await _http.GetAsync(url).WaitAsync(TimeSpan.FromSeconds(5));

// 좋음 — 토큰이 HttpClient 내부까지 전달되어 요청이 실제로 중단된다
using var cts = CancellationTokenSource.CreateLinkedTokenSource(ct);
cts.CancelAfter(TimeSpan.FromSeconds(5));
await _http.GetAsync(url, cts.Token);
```

`WaitAsync`가 유용한 곳은 **토큰을 받지 않는 작업**을 감쌀 때다. 하지만 그때조차 해결하는 것은 "내가 기다리는 시간"뿐이고, 뒤에 남는 작업은 그대로 남는다는 사실을 인지하고 써야 한다.

> **📌 `HttpClient.Timeout`과 취소 토큰의 관계**
>
> `HttpClient`는 자체 `Timeout` 속성(기본 100초)을 갖는다. 이 타임아웃이 걸리면 .NET 5 이후로는 `TaskCanceledException`이 발생하되 `InnerException`이 `TimeoutException`이다. 취소 토큰으로 취소된 경우와 예외 타입이 같으므로, 구분하려면 `InnerException`을 보거나 토큰의 `IsCancellationRequested`를 확인해야 한다. 43.4절에서 다룬 내용이다.

### `OperationCanceledException`의 출처 판별

"타임아웃인가 사용자 취소인가"는 로그와 재시도 판단에 필요하다. `OperationCanceledException`은 `CancellationToken` 속성을 갖고 있으므로 그것으로 구분할 수 있다 — 이론상으로는.

**`ex.CancellationToken`이 아니라 원본 토큰의 `IsCancellationRequested`를 보는 것**이 실무에서 더 믿을 만하다. 이유는 두 가지다.

1. `ex.CancellationToken`은 링크된 토큰일 뿐 원인이 무엇이었는지 알려주지 않는다. 링크 소스는 부모 중 누가 취소했는지 기록하지 않는다.
2. 라이브러리가 `OperationCanceledException`을 던질 때 토큰을 채우지 않는 경우가 있다(`new OperationCanceledException()`).

정석 형태는 **예외 필터**를 쓰는 것이다.

```csharp
catch (OperationCanceledException) when (userToken.IsCancellationRequested)
{
    throw;                              // 사용자 취소는 그대로 위로 올린다
}
catch (OperationCanceledException)      // 타임아웃
{
    return Result.Timeout();
}
```

예외 필터는 스택을 풀기 전에 평가되므로(32.7절) 진단 정보가 보존된다는 부수 이점도 있다.

> **⚠️ `catch (Exception)`이 취소를 삼킨다**
>
> ```csharp
> try { await DoWorkAsync(ct); }
> catch (Exception ex) { _log.LogError(ex, "실패"); return null; }
> ```
>
> 사용자가 취소했을 때도 "실패" 로그가 남고 `null`이 반환된다. 취소는 오류가 아니라 정상적인 흐름 종료다. 취소를 오류로 세면 오류율 대시보드가 사용자의 페이지 이탈에 반응한다.
>
> **취소는 항상 별도로 잡아 다시 던져라.**
>
> ```csharp
> catch (OperationCanceledException) { throw; }
> catch (Exception ex) { _log.LogError(ex, "실패"); return null; }
> ```
>
> `catch` 절의 순서가 중요하다. `OperationCanceledException`이 먼저 와야 한다.

### 재시도 — 무엇을 다시 시도해도 되는가

재시도는 "실패가 일시적(transient)이다"라는 가정 위에서만 정당하다. 이 가정이 틀리면 재시도는 응답 시간만 몇 배로 늘린다.

| 실패 유형 | 예 | 재시도? | 이유 |
|---|---|---|---|
| 네트워크 일시 장애 | `SocketException`, `HttpRequestException` | **예** | 다음 시도에 다른 경로/서버로 갈 수 있다 |
| 서버 과부하 | HTTP 503, 429 | **예** (백오프 필수) | 시간이 지나면 회복된다 |
| 게이트웨이 오류·타임아웃 | HTTP 502, 504, 408 | **예**(408은 멱등일 때만) | 상류 일시 장애 |
| 서버 내부 오류 | HTTP 500 | **조건부** | 원인 불명 — 무한 반복 위험 |
| 인증 실패 | HTTP 401, 403 | **아니오** | 토큰 갱신 후라면 1회 |
| 잘못된 요청 | HTTP 400, 422 | **아니오** | 같은 요청은 항상 같은 결과 |
| 없음 | HTTP 404 | **아니오** | 상태가 바뀌길 기대하는 재시도는 폴링이지 재시도가 아니다 |
| 취소 | `OperationCanceledException` | **절대 아니오** | 결과를 원하지 않는다는 뜻 |
| 프로그래밍 오류 | `NullReferenceException`, `ArgumentException` | **절대 아니오** | 결정적으로 재현된다 |

> **⚠️ 멱등성(idempotency)을 확인하지 않은 재시도는 데이터 손상이다**
>
> "타임아웃 → 재시도"의 위험은 **첫 요청이 실제로는 성공했을 수 있다**는 것이다. 응답이 오는 길에 유실됐을 뿐일 수 있다. 결제 요청을 재시도해서 두 번 결제되는 사고는 이 경로로 일어난다.
>
> - `GET`, `PUT`, `DELETE`는 정의상 멱등이다.
> - **`POST`는 멱등이 아니다.** 재시도하려면 멱등성 키(idempotency key)를 요청에 실어 서버가 중복을 걸러 주어야 한다.
> - 내부 메시지 처리도 마찬가지다. "이미 처리한 메시지 ID"를 기록하지 않으면 재시도는 중복 처리다.
>
> 재시도 정책을 붙이기 전에 **"이 연산을 두 번 실행해도 되는가"** 를 먼저 답하라. 답이 "아니오"면 재시도가 아니라 멱등성 설계가 먼저다.

### 지수 백오프와 지터

고정 간격 재시도는 부하가 몰릴 때 최악이다. 실패한 클라이언트들이 같은 간격으로 동시에 재시도하면 서버는 같은 순간에 같은 파도를 다시 맞는다.

```csharp
// 지수 백오프 + 완전 지터(full jitter)
static TimeSpan Backoff(int attempt, TimeSpan baseDelay, TimeSpan maxDelay)
{
    // 2^attempt 배로 늘리되 상한을 둔다
    double exp = Math.Min(baseDelay.TotalMilliseconds * Math.Pow(2, attempt),
                          maxDelay.TotalMilliseconds);
    // [0, exp) 범위로 무작위화 — 재시도 시각을 흩뜨린다
    return TimeSpan.FromMilliseconds(Random.Shared.NextDouble() * exp);
}
```

| 시도 | 지수 지연(base 200 ms) | 완전 지터 후 실제 대기 범위 |
|---|---|---|
| 1 | 200 ms | 0 ~ 200 ms |
| 2 | 400 ms | 0 ~ 400 ms |
| 3 | 800 ms | 0 ~ 800 ms |
| 4 | 1,600 ms | 0 ~ 1,600 ms |
| 5 | 3,200 ms | 0 ~ 3,200 ms (상한 적용) |

`Random.Shared`(※.NET 6)는 스레드 안전하다. 예전처럼 `[ThreadStatic] Random`을 직접 관리할 필요가 없다.

> **📌 왜 지터가 필요한가 — 재시도 폭풍(retry storm)**
>
> 서버가 5초간 죽었다가 살아났다고 하자. 그 사이 실패한 클라이언트 10,000개가 모두 "1초 뒤 재시도"를 예약했다면, 서버는 부활하자마자 10,000개의 요청을 **같은 순간에** 맞는다. 다시 죽는다. 그리고 이번엔 "2초 뒤 재시도"가 동기화된다.
>
> 지터는 이 동기화를 깨뜨린다. 재시도 시각이 구간에 고르게 퍼지면 서버가 회복할 틈이 생긴다. **백오프만으로는 부족하고 지터가 있어야 한다.**

### 재시도 예산과 계층 곱셈

> **⚠️ 계층마다 재시도를 걸면 시도 횟수가 곱해진다**
>
> ```text
>   API Gateway   재시도 3회
>        ↓
>   Service A     재시도 3회      →  3 × 3 = 9
>        ↓
>   Service B     재시도 3회      →  3 × 3 × 3 = 27
>        ↓
>   Database                        원 요청 1건 → 최대 27번의 DB 호출
> ```
>
> 각 계층은 자기 관점에서 "합리적인 3회"를 설정했다. 전체로는 27배의 부하 증폭이다. 장애 상황에서 이 증폭이 서버를 회복 불가능하게 만든다.
>
> 규칙: **재시도는 한 계층에서만 한다.** 보통은 가장 바깥(사용자에 가까운 쪽)이나 가장 안쪽(실제 I/O를 하는 쪽) 중 하나를 고르고, 나머지 계층은 실패를 그대로 전파한다. 그리고 계층 전체에 **타임아웃 예산**을 두어 하위 계층 타임아웃 합이 상위 타임아웃보다 작게 만든다.
>
> ```text
>   상위 타임아웃 10초
>     └ 하위 호출 타임아웃 3초 × 최대 3회 시도 = 최대 9초  → 예산 안
> ```

### 서킷 브레이커 — 실패를 빨리 인정하기

다운스트림이 완전히 죽었을 때 재시도는 해롭기만 하다. 서킷 브레이커(circuit breaker)는 실패가 일정 비율을 넘으면 **아예 호출을 시도하지 않고 즉시 실패시킨다.**

```text
                 실패율이 임계값을 넘음
       ┌────────┐ ──────────────────────→ ┌────────┐
       │ Closed │                          │  Open  │
       │ (정상) │ ←────────────────────── │(차단중)│
       └────────┘      성공                └────┬───┘
            ↑                                   │ 대기 시간 경과
            │                                   ↓
            │  시험 호출 성공            ┌────────────┐
            └───────────────────────────│ Half-Open  │
                                        │ (시험 중)  │
                                        └────────────┘
                                             │ 시험 호출 실패
                                             └────→ Open 으로 복귀
```

| 상태 | 호출 시 동작 | 전이 조건 |
|---|---|---|
| **Closed** | 정상 통과, 실패를 센다 | 실패율/실패 수가 임계값 초과 → Open |
| **Open** | **호출하지 않고 즉시 예외** | 지정한 시간 경과 → Half-Open |
| **Half-Open** | 소수의 시험 호출만 통과 | 성공 → Closed / 실패 → Open |

Open 상태의 이점은 두 방향이다. 죽은 다운스트림에 부하를 더하지 않고, 호출하는 쪽도 타임아웃까지 기다리지 않고 즉시 실패해 자원을 반환한다. **장애가 전파되지 않게 막는 장치**다.

### 벌크헤드 — 격벽으로 나누기

배의 격벽(bulkhead)에서 온 이름이다. 하나의 다운스트림이 느려졌을 때 그 대기가 **애플리케이션 전체의 자원을 잠식하지 않도록** 자원을 구획별로 나눈다.

```csharp
// 다운스트림별로 독립된 동시성 예산
private readonly SemaphoreSlim _paymentGate  = new(20, 20);
private readonly SemaphoreSlim _catalogGate  = new(50, 50);
private readonly SemaphoreSlim _analyticsGate = new(5, 5);
```

결제 API가 느려져도 최대 20개의 진행 중 호출만 그쪽에 묶인다. 카탈로그 조회는 자기 예산 50개를 그대로 쓴다. 격벽이 없다면 결제 지연이 스레드 풀과 커넥션 풀을 모두 먹어치우고 카탈로그까지 죽는다.

> **💡 벌크헤드의 크기는 "이것이 완전히 멈춰도 견딜 수 있는 양"으로 잡는다**
>
> `_analyticsGate`가 5인 이유는 분석 전송이 완전히 막혀도 5개의 대기만 발생하기 때문이다. 중요도가 낮은 종속성일수록 예산을 작게 잡는 것이 원칙이다. 반대로 핵심 경로는 크게 잡되, 그만큼 그쪽 장애가 치명적이라는 뜻이므로 서킷 브레이커를 더 민감하게 설정한다.

### 이 조합을 직접 짜지 마라

지금까지 나온 요소를 모두 조합하면 다음이 필요하다.

- 지수 백오프 + 지터 계산
- 재시도 가능 예외 분류
- 시도 횟수 상한과 전체 타임아웃 예산
- 서킷 브레이커 상태 기계(스레드 안전하게)
- 벌크헤드 세마포어
- 각 단계의 메트릭과 로그
- 취소 토큰을 이 모든 것에 정확히 전파

직접 구현하면 400줄쯤 되고, 그중 절반은 경계 조건이다. **표준 라이브러리를 써라.** .NET 생태계에서는 Polly가 사실상 표준이고, `Microsoft.Extensions.Http.Resilience`가 그것을 `HttpClient`에 통합한다.

```csharp
// Polly v8 스타일 — ResiliencePipeline 구성
var pipeline = new ResiliencePipelineBuilder<HttpResponseMessage>()
    .AddRetry(new RetryStrategyOptions<HttpResponseMessage>
    {
        MaxRetryAttempts = 3,
        BackoffType = DelayBackoffType.Exponential,
        UseJitter = true,
        Delay = TimeSpan.FromMilliseconds(200)
    })
    .AddTimeout(TimeSpan.FromSeconds(10))
    .Build();

// IHttpClientFactory(43.7절)와 결합하면 더 간단해진다
builder.Services.AddHttpClient<PaymentClient>()
    .AddStandardResilienceHandler();   // 재시도 + 서킷 브레이커 + 타임아웃 + 동시성 제한
```

> **📌 API 이름은 라이브러리 버전에 따라 다르다**
>
> Polly는 v7(`Policy.Handle<T>().WaitAndRetryAsync(...)`)과 v8(`ResiliencePipelineBuilder`)의 API 형태가 크게 다르다. 위 코드는 v8 계열의 구성 형태를 보인 것이며, 실제 사용 시에는 프로젝트가 참조하는 버전의 문서를 확인해야 한다. **이 책이 보증하는 것은 필요한 개념 목록이지 특정 라이브러리의 시그니처가 아니다.**

> **⚠️ 정책의 순서가 의미를 바꾼다**
>
> "재시도 바깥에 타임아웃"과 "타임아웃 바깥에 재시도"는 완전히 다른 동작이다.
>
> - `Retry(Timeout(op))` — **시도마다** 타임아웃. 3회 × 10초 = 최대 30초.
> - `Timeout(Retry(op))` — **전체**에 타임아웃. 재시도를 몇 번 하든 10초 안에 끝난다.
>
> 대개 둘 다 필요하다. 안쪽에 "시도당 타임아웃", 바깥에 "전체 예산 타임아웃"을 두는 이중 구성이 실무의 기본형이다. 정책을 조합할 때는 **어느 쪽이 안쪽인지 반드시 확인하라.**

## 51.5 UI 스레드 모델과 크로스 스레드 호출 (WinForms / WPF / MAUI)

### 단일 UI 스레드 원칙

윈도우 기반 UI 프레임워크는 예외 없이 같은 규칙 위에 서 있다. **컨트롤은 그것을 만든 스레드에서만 만질 수 있다.**

이 규칙의 뿌리는 .NET이 아니라 Win32와 COM에 있다. Windows 컨트롤은 단일 스레드 아파트(single-threaded apartment, STA) 모델을 따르는 아파트 스레드 방식 컴포넌트이고, 많은 동작이 **메시지 펌프(message pump)** 를 통해 이루어진다. 창 하나는 메시지 큐 하나에 묶여 있고, 그 큐를 처리하는 스레드는 하나다.

```text
  ┌──────────────────────── UI 스레드 (STA) ────────────────────────┐
  │                                                                  │
  │   ┌──────────────┐                                               │
  │   │ 메시지 큐     │  ← OS: 마우스, 키보드, 페인트, 타이머         │
  │   │ WM_PAINT     │  ← 다른 스레드: Invoke/BeginInvoke 로 넣은 항목 │
  │   │ WM_MOUSEMOVE │                                               │
  │   │ (invoke 요청) │                                               │
  │   └──────┬───────┘                                               │
  │          ↓                                                        │
  │   while (GetMessage(&msg)) {          ← 메시지 루프(펌프)         │
  │       TranslateMessage(&msg);                                     │
  │       DispatchMessage(&msg);          → WndProc → 이벤트 핸들러   │
  │   }                                                               │
  │                                                                   │
  │   이 루프가 멈추면 = UI가 얼어붙는다                              │
  └───────────────────────────────────────────────────────────────────┘
```

이 그림에서 두 가지 결론이 나온다.

1. **다른 스레드가 컨트롤을 만지면 안 된다.** 큐를 처리하는 스레드가 아닌 곳에서 상태를 바꾸면 경합이 생긴다.
2. **UI 스레드에서 오래 걸리는 일을 하면 루프가 멈춘다.** 루프가 멈추면 `WM_PAINT`가 처리되지 않아 창이 하얗게 되고, Windows가 "응답 없음"으로 표시한다.

45.8절에서 이 모델의 기초와 동기화 컨텍스트를 다뤘다. 여기서는 프레임워크별 API와 실무 설계를 채운다.

### WinForms — `InvokeRequired` / `Invoke` / `BeginInvoke`

```csharp
private void UpdateStatus(string text)
{
    if (statusLabel.InvokeRequired)
        statusLabel.Invoke(() => statusLabel.Text = text);
    else
        statusLabel.Text = text;
}
```

| 멤버 | 시그니처 | 동작 |
|---|---|---|
| `Control.InvokeRequired` | `bool` | 현재 스레드가 컨트롤의 스레드가 아니면 `true` |
| `Control.Invoke` | `object Invoke(Delegate)` | 메시지를 포스트하고 **완료될 때까지 블로킹** |
| `Control.BeginInvoke` | `IAsyncResult BeginInvoke(Delegate)` | 메시지를 포스트하고 **즉시 반환** |
| `Control.EndInvoke` | `object EndInvoke(IAsyncResult)` | `BeginInvoke`의 결과 회수 |
| `Control.IsHandleCreated` | `bool` | 네이티브 창 핸들이 만들어졌는가 |

**런타임 동작 — `Invoke`가 실제로 하는 일.** 호출 스레드가 컨트롤의 스레드와 같으면 지름길로 델리게이트를 그냥 호출한다. 다르면 델리게이트·인자·호출 스택 참조를 담은 내부 구조체를 만들어 큐에 넣고 대상 컨트롤에 메시지를 포스트한다. **인자는 복사된다** — 멀티스레드 환경이므로 델리게이트가 호출되기 전에 값이 바뀌는 것을 막기 위해서다. 그다음 `Invoke`는 UI 스레드가 그 메시지를 처리할 때까지 **스핀 대기와 슬립을 섞어 가며** 기다린다. 델리게이트가 던진 예외는 스레드 경계를 넘을 수 없으므로 컨트롤이 `try`/`catch`로 잡아 구조체에 담고, 처리가 끝나면 `Invoke`가 그것을 **백그라운드 스레드에서 다시 던진다.**

> **⚠️ `WndProc`은 대기 중인 invoke 델리게이트를 전부 한 번에 처리한다**
>
> 대상 컨트롤이 invoke 메시지를 처리할 때는 **큐에 있는 모든** invoke 델리게이트를 처리한다. `Invoke`만 쓰면 이 사실이 드러나지 않지만, `Invoke`와 `BeginInvoke`를 섞으면 관찰 가능한 차이가 생긴다.
>
> ```csharp
> private void OnTick(object sender, EventArgs e)
> {
>     statusLabel.BeginInvoke(() => statusLabel.Text = DateTime.Now.ToLongTimeString());
>     statusLabel.Text += " 그리고 추가 텍스트";   // 거의 항상 사라진다
> }
> ```
>
> `BeginInvoke`는 메시지를 큐에 넣기만 하고 반환한다. 다음 줄이 먼저 실행되고, 그 뒤에 큐에 넣은 델리게이트가 텍스트를 통째로 덮어쓴다.
>
> `BeginInvoke`로 예약한 델리게이트는 **넣은 순서대로** 처리되지만 "언제"는 통제할 수 없다. 그리고 나중에 `Invoke`를 부르면 그 전에 `BeginInvoke`로 넣어 둔 것들이 **먼저 전부** 실행된다. 그러니 델리게이트 안에서 프로그램 상태를 다시 확인하도록 방어적으로 작성해야지, `Invoke`를 부르던 시점의 상태를 그대로 신뢰하면 안 된다.

> **⚠️ `InvokeRequired`는 핸들이 없으면 거짓말을 한다**
>
> `InvokeRequired`는 보통 스레드 ID 두 개를 비교하는 값싼 연산이다. 문제는 **컨트롤의 창 핸들이 아직 만들어지지 않았을 때**다. 비교할 대상이 없으므로 프레임워크는 부모 컨트롤 트리를 거슬러 올라가며 이미 생성된 창을 찾고, 그것도 없으면 파킹 윈도(parking window)라는 특수 창까지 뒤진다. 그마저 없으면 **무조건 `false`를 반환한다** — "마셜링이 필요 없다"는 뜻인데 이것이 옳다는 보장이 없다. 프레임워크가 "확실한 즉시 실패" 대신 "가능한 나중의 실패"를 택한 것이다.
>
> 정리하면, 컨트롤이 생성된 뒤의 `InvokeRequired`는 빠르고 안전하다. 생성 전에는 느리고, 아무 창도 없으면 답이 틀릴 수 있다. 그래서 `IsHandleCreated`를 먼저 확인하는 방어 코드가 관용구로 쓰인다.

크로스 스레드 접근을 실제로 어겼을 때 나오는 예외는 `InvalidOperationException`이며, 메시지는 "Cross-thread operation not valid"로 시작한다. **다만 이 검사는 핸들이 생성된 뒤에만 동작하고, `Control.CheckForIllegalCrossThreadCalls`가 `true`일 때만 활성화된다.** 디버거가 붙어 있으면 기본적으로 `true`이지만, 릴리스 실행에서는 검사가 꺼져 예외 없이 조용히 깨질 수 있다.

### WPF — `Dispatcher`

WPF에는 `InvokeRequired`가 없다. 대신 `DispatcherObject`(대부분의 WPF 요소의 기반 클래스)가 `Dispatcher` 속성을 갖고, 접근 확인은 `CheckAccess`/`VerifyAccess`로 한다.

```csharp
private void UpdateStatus(string text)
{
    if (statusText.CheckAccess())
        statusText.Text = text;                                  // 이미 UI 스레드
    else
        statusText.Dispatcher.Invoke(() => statusText.Text = text);
}
```

| 멤버 | 동작 |
|---|---|
| `DispatcherObject.CheckAccess()` | 현재 스레드가 이 객체의 스레드면 `true` |
| `DispatcherObject.VerifyAccess()` | 아니면 `InvalidOperationException`을 던진다 |
| `Dispatcher.Invoke(Action)` | 동기 — 완료까지 블로킹 |
| `Dispatcher.BeginInvoke(...)` | 비동기 — `DispatcherOperation` 반환 |
| `Dispatcher.InvokeAsync(...)` | 비동기 — `await` 가능한 `DispatcherOperation` 반환 |
| `Dispatcher.CurrentDispatcher` | 현재 스레드의 디스패처(없으면 생성) |
| `Application.Current.Dispatcher` | 애플리케이션의 UI 디스패처 |

WPF만의 추가 개념이 **우선순위**다.

```csharp
await statusText.Dispatcher.InvokeAsync(
    () => statusText.Text = text,
    DispatcherPriority.Background);   // 렌더링보다 낮은 우선순위
```

| `DispatcherPriority` | 상대 위치 | 쓰임 |
|---|---|---|
| `Send` | 가장 높음 | 즉시 — 사실상 동기 |
| `Normal` | 기본값 | 일반 UI 갱신 |
| `DataBind` | Normal 아래 | 데이터 바인딩 처리 |
| `Render` | DataBind 아래 | 렌더링 |
| `Loaded` / `Input` | Render 아래 | 레이아웃 완료 후 / 사용자 입력 처리 |
| `Background` | Input 아래 | 급하지 않은 작업 |
| `ContextIdle` / `ApplicationIdle` / `SystemIdle` | 가장 낮음 | 유휴 시간에만 |

우선순위가 존재하는 이유는 WPF가 **UI 스레드와 렌더링 스레드를 분리**하기 때문이다. 렌더링 파이프라인은 계속 돌면서 애니메이션을 그린다. 급하지 않은 갱신을 `Background` 우선순위로 넣으면 입력 처리와 렌더링이 먼저 진행되어 체감 반응성이 좋아진다.

`Dispatcher`는 스레드마다 하나씩 존재한다. 어떤 컨트롤의 디스패처를 처음 요청하면 라이브러리가 그 스레드에 디스패처가 이미 있는지 보고, 있으면 그것을, 없으면 새로 만들어 연결한다.

크로스 스레드 위반 시 예외는 `InvalidOperationException`이며 메시지는 "The calling thread cannot access this object because a different thread owns it."이다.

### MAUI — `MainThread`

```csharp
using Microsoft.Maui.ApplicationModel;

if (MainThread.IsMainThread)
    statusLabel.Text = text;
else
    MainThread.BeginInvokeOnMainThread(() => statusLabel.Text = text);

// 결과를 기다려야 하면
await MainThread.InvokeOnMainThreadAsync(() => statusLabel.Text = text);
```

요소의 `Dispatcher` 속성(`IDispatcher`)으로도 같은 일을 할 수 있다 — `Dispatch(Action)`과 `DispatchAsync(...)`다.

### 세 프레임워크 비교

| | WinForms | WPF | MAUI |
|---|---|---|---|
| 스레드 확인 | `Control.InvokeRequired` | `DispatcherObject.CheckAccess()` | `MainThread.IsMainThread` |
| 강제 검증 | 없음(예외로 드러남) | `VerifyAccess()` | 없음 |
| 동기 마셜링 | `Control.Invoke` | `Dispatcher.Invoke` | `Dispatcher.Dispatch`(반환 없음) |
| 비동기 마셜링 | `Control.BeginInvoke` | `Dispatcher.BeginInvoke` | `MainThread.BeginInvokeOnMainThread` |
| `await` 가능 | 없음 | `Dispatcher.InvokeAsync` | `MainThread.InvokeOnMainThreadAsync` |
| 우선순위 | 없음 | `DispatcherPriority` | 없음 |
| 위반 시 예외 | `InvalidOperationException` (조건부 검사) | `InvalidOperationException` | 플랫폼별 |

### 그리고 `SynchronizationContext`가 이 셋을 지운다

위 표를 외울 필요가 거의 없는 이유가 있다. `async`/`await`가 이 모든 것을 **자동으로** 처리하기 때문이다.

각 UI 프레임워크는 자기 방식의 마셜링을 구현한 `SynchronizationContext` 파생 클래스를 UI 스레드에 설치한다 — WinForms는 `WindowsFormsSynchronizationContext`, WPF는 `DispatcherSynchronizationContext`. `await`는 재개할 때 캡처해 둔 컨텍스트의 `Post`를 호출하고, 그 `Post`가 각각 `Control.BeginInvoke`와 `Dispatcher.BeginInvoke`로 이어진다(47.12절).

```csharp
private async void OnLoadClicked(object sender, EventArgs e)
{
    loadButton.Enabled = false;              // UI 스레드
    try
    {
        var data = await _service.FetchAsync();   // 여기서 스레드가 바뀌었다가
        resultsGrid.DataSource = data;            // 돌아온다 — Invoke 없이 안전
    }
    finally { loadButton.Enabled = true; }
}
```

`Invoke`도 `InvokeRequired`도 없다. **직접 마셜링 코드를 쓰는 것은 `async`/`await`로 표현할 수 없는 경우뿐이다** — 예컨대 이벤트 기반 콜백이 임의의 스레드에서 오거나, 네이티브 라이브러리의 콜백이거나, `Timer`(멀티스레드 타이머, 49.10절)의 틱 안에서 UI를 갱신할 때다.

> **⚠️ 잠금을 쥔 채 `Invoke`를 부르면 데드락이다**
>
> 백그라운드 스레드가 잠금 L을 잡고 `Dispatcher.Invoke`(또는 `Control.Invoke`)를 호출한다. 그런데 UI 스레드가 마침 같은 잠금 L을 기다리고 있다. 백그라운드는 UI가 메시지를 처리하기를 기다리고, UI는 잠금이 풀리기를 기다린다. **완전한 데드락**이다.
>
> 해법은 셋 중 하나다.
>
> 1. `Invoke` 대신 `BeginInvoke`를 쓴다(또는 동기화 컨텍스트가 있는 상태에서 `await`를 쓴다 — 이쪽이 암묵적으로 같은 일을 한다).
> 2. `Invoke`를 부르기 전에 잠금을 푼다. 다만 호출자가 잠금을 잡았다면 이 방법은 통하지 않는다.
> 3. 애초에 UI 스레드가 잡을 수 있는 잠금을 백그라운드에서 잡지 않는다.
>
> 셋째가 근본 해결이다. UI 스레드는 **어떤 잠금도 기다리면 안 된다.** UI 스레드에서 `lock`을 쓰는 코드를 발견하면 그 자체를 의심하라.

### `async void`가 허용되는 유일한 자리

47.14절이 `async void`를 금지했다. 예외가 딱 하나 있다 — **이벤트 핸들러**다.

이벤트 핸들러 프로토콜(`void` 반환)은 `async`/`await`가 언어에 들어오기 전에 정해졌다. 게다가 이벤트를 발생시키는 쪽은 대개 사용자 코드가 아니라 프레임워크이고, `Task`를 돌려받아도 무엇을 해야 할지 모른다. 그래서 C#은 `async void` 메서드를 허용한다 — 이것 없이는 비동기 이벤트 핸들러를 만들 수 없다.

그러나 `async void`의 대가는 그대로 남는다. **`async void`에서 던져진 예외는 그 메서드가 시작될 때 활성이었던 `SynchronizationContext` 위에서 직접 던져진다.** UI 애플리케이션에서 이것은 처리되지 않은 예외 핸들러로 직행하고, 대개 프로세스 종료다. `try`/`catch`로 잡을 방법이 호출자 쪽에 없다.

```csharp
// UI 이벤트 핸들러의 정석
private async void OnCommand(object sender, RoutedEventArgs e)
{
    try
    {
        await _viewModel.UpdateAsync();
    }
    catch (OperationCanceledException) { /* 취소는 정상 종료 */ }
    catch (Exception ex)
    {
        _viewModel.Messages.Add(ex.ToString());   // 로그 후 계속 실행
    }
}
```

**모든 `async void` 이벤트 핸들러는 본문 전체를 `try`/`catch`로 감싼다.** 예외가 하나라도 빠져나가면 애플리케이션이 죽는다.

복구 불가능한 오류라서 즉시 종료시키는 편이 나은 경우도 있다. 그때는 예외 필터로 로깅만 하고 예외를 그대로 통과시킨다(32.8절).

```csharp
private async void OnCommand(object sender, RoutedEventArgs e)
{
    try { await _viewModel.UpdateAsync(); }
    catch (Exception ex) when (LogAndFallThrough(_viewModel, ex)) { }
}

// 항상 false를 반환하므로 catch 블록은 실행되지 않고 예외가 계속 전파된다
private static bool LogAndFallThrough(SampleViewModel vm, Exception ex)
{
    vm.Messages.Add(ex.ToString());
    return false;
}
```

> **⚠️ `async void`는 재진입을 막지 않는다**
>
> 사용자가 버튼을 세 번 빠르게 누르면 `async void` 핸들러가 **세 번 동시에** 시작된다. 첫 호출이 `await`에서 대기 중이면 두 번째 호출이 그대로 진입한다. `lock`으로는 막을 수 없다(`await`가 있으므로).
>
> 방어책은 세 가지다.
>
> 1. **버튼을 비활성화한다** — `finally`에서 다시 켠다. 가장 단순하고 사용자에게도 명확하다.
> 2. **진행 중 플래그** — `Interlocked.CompareExchange(ref _busy, 1, 0) != 0`이면 즉시 반환.
> 3. **취소하고 재시작** — 이전 작업의 `CancellationTokenSource`를 취소하고 새로 시작한다. 검색어 입력 같은 경우에 맞는 형태다.

### UI 스레드를 막지 않는 설계

원칙은 하나다. **UI 스레드는 UI만 한다.**

| 작업 종류 | 올바른 처리 |
|---|---|
| I/O (파일, 네트워크, DB) | `await` — `Task.Run` 불필요 |
| CPU 바운드 계산 | `await Task.Run(...)` — 결과만 UI 스레드로 |
| 진행 상황 보고 / 결과 표시 | `IProgress<T>`(46.12절) / `await` 이후 그대로 |

```csharp
private async void OnAnalyzeClicked(object sender, EventArgs e)
{
    analyzeButton.Enabled = false;
    progressBar.Value = 0;
    _cts = new CancellationTokenSource();
    try
    {
        // Progress<T>는 생성된 시점의 동기화 컨텍스트로 콜백을 마셜링한다
        var progress = new Progress<int>(p => progressBar.Value = p);

        // CPU 바운드 작업만 Task.Run 으로 밀어낸다
        Report report = await Task.Run(
            () => Analyzer.Run(_input, progress, _cts.Token), _cts.Token);

        reportView.Document = report;   // UI 스레드로 돌아와 있다
    }
    catch (OperationCanceledException) { statusLabel.Text = "취소됨"; }
    finally { analyzeButton.Enabled = true; }
}
```

`Progress<T>`가 동기화 컨텍스트를 캡처하므로 `ProgressChanged` 콜백은 UI 스레드에서 실행된다. **이 객체를 UI 스레드에서 생성해야** 그 성질이 성립한다는 점이 중요하다(46.12절).

> **⚠️ `IProgress<T>.Report`는 UI를 초당 수천 번 갱신할 수 있다**
>
> `Progress<T>`는 호출을 그대로 전달한다. 계산 루프에서 반복마다 `Report`를 부르면 UI 메시지 큐에 초당 수만 개의 항목이 쌓인다. UI 스레드는 그것을 처리하느라 마우스 이동조차 못 그린다. **진행률 표시가 애플리케이션을 얼린다.**
>
> 사람 눈은 초당 60프레임 이상을 구분하지 못하고, 진행률 텍스트는 초당 10회면 충분하다. 갱신 빈도를 반드시 제한하라.

### UI 갱신 스로틀링

**방법 1 — 값이 의미 있게 바뀔 때만, 또는 시간 간격을 두고 보고한다.**

```csharp
int  lastPercent  = -1;
long lastTicks    = 0;
long minInterval  = Stopwatch.Frequency / 20;    // 초당 최대 20회

for (int i = 0; i < total; i++)
{
    DoWork(i);
    int percent = i * 100 / total;
    long now = Stopwatch.GetTimestamp();
    if (percent != lastPercent && now - lastTicks >= minInterval)
    {
        lastPercent = percent;
        lastTicks = now;
        progress.Report(percent);
    }
}
```

**방법 2 — 용량 1 + `DropOldest` 채널로 "최신값 슬롯"을 만든다.**

51.2절에서 예고한 구성이다. 계산 쪽은 아무 제약 없이 마음껏 쓰고, UI 쪽이 자기 속도로 읽는다.

```csharp
// 생산자는 전혀 대기하지 않고, 큐에는 항상 최신 값 하나만 남는다
private readonly Channel<int> _progressSlot = Channel.CreateBounded<int>(
    new BoundedChannelOptions(1)
    {
        FullMode = BoundedChannelFullMode.DropOldest,
        SingleReader = true,
        SingleWriter = true
    });

// 계산 스레드: 반복마다 불러도 비용이 거의 없다
_progressSlot.Writer.TryWrite(percent);

// UI 스레드: 자기 속도로 읽는다 (PeriodicTimer는 49.10절)
private async Task PumpProgressAsync(CancellationToken ct)
{
    using var timer = new PeriodicTimer(TimeSpan.FromMilliseconds(50));
    while (await timer.WaitForNextTickAsync(ct))
        if (_progressSlot.Reader.TryRead(out int percent))
            progressBar.Value = percent;
}
```

이 구조의 장점은 **생산자와 소비자의 속도가 완전히 분리된다**는 것이다. 계산이 아무리 빨라도 UI는 초당 20회만 갱신되고, 계산이 느려도 UI는 마지막 값을 유지한다. 진행률·센서값·실시간 시세처럼 "최신값만 의미 있는" 모든 스트림에 같은 패턴이 적용된다.

> **💡 UI 갱신 스로틀링은 성능 최적화가 아니라 정확성 문제다**
>
> 갱신을 초당 20회로 줄이면 사용자가 보는 것은 **더 매끄러운** 진행률이다. 초당 수천 번 갱신하면 메시지 큐가 밀려서 진행률이 계단식으로 튀거나 아예 멈춘 것처럼 보인다. 덜 그리는 쪽이 더 잘 보인다.

## 51.6 서버 애플리케이션의 비동기 설계 원칙

### ASP.NET Core에는 `SynchronizationContext`가 없다

.NET Framework 시절의 ASP.NET에는 `AspNetSynchronizationContext`가 있었다. 요청 처리 중 `await`가 있으면 연속이 그 컨텍스트로 돌아왔고, 그 컨텍스트는 요청당 하나의 스레드만 허용했다. 그래서 `.Result`나 `.Wait()` 한 번이 곧바로 데드락이었다(47.14절).

**ASP.NET Core에는 동기화 컨텍스트가 없다.** `SynchronizationContext.Current`는 `null`이고, `await` 이후의 연속은 그냥 스레드 풀에서 실행된다. 이 하나의 변화가 세 가지를 바꾼다.

| | .NET Framework ASP.NET | ASP.NET Core |
|---|---|---|
| `SynchronizationContext` | `AspNetSynchronizationContext` | **없음** (`null`) |
| sync-over-async | **데드락** | 데드락은 없음 — 대신 **스레드 기아** |
| `ConfigureAwait(false)` | 앱 코드에서도 필요 | 앱 코드에서는 불필요 |
| `HttpContext` 접근 | 컨텍스트가 복원해 줌 | `AsyncLocal` 기반(`IHttpContextAccessor`) |
| 요청당 스레드 | 사실상 고정 | 자유롭게 바뀜 |

> **⚠️ "ASP.NET Core에서는 `.Result`를 써도 데드락이 안 난다"는 위험한 절반의 진실이다**
>
> 데드락은 안 난다. 대신 더 나쁜 것이 생긴다 — **스레드 풀 기아**. 데드락은 요청 하나가 멈추는 것이고 개발 중에 즉시 드러난다. 기아는 부하가 어느 선을 넘는 순간 서비스 전체가 무너지는 것이고, 개발 환경에서는 절대 재현되지 않는다.
>
> 데드락이 사라진 것은 안전해졌다는 뜻이 아니라 **경고 신호가 사라졌다는 뜻**이다.

### 끝까지 async — 하나의 sync-over-async가 만드는 붕괴

기아가 어떻게 일어나는지 단계별로 따라가 보자.

```csharp
// 컨트롤러 어딘가, 세 계층 아래의 오래된 라이브러리 메서드
public Order GetOrder(int id) => _repo.GetOrderAsync(id).Result;   // (X)
```

```text
  1. 요청이 들어온다. 스레드 풀 스레드 T1이 요청 처리를 시작한다.
  2. GetOrder() 가 GetOrderAsync() 를 호출한다.
     내부에서 DB I/O 가 시작되고 미완료 Task 가 반환된다.
  3. .Result 가 T1 을 블로킹한다.
     → T1 은 살아 있지만 아무 일도 하지 않는다. 스레드 풀에 반환되지 않는다.
  4. DB 응답이 도착하면 그 연속을 실행할 스레드가 필요하다.
     → 스레드 풀에 요청된다.
  5. 부하가 높으면 사용 가능한 스레드가 없다.
     → 스레드 풀은 새 스레드를 만들어야 한다.
  6. 그런데 스레드 주입 속도는 최소 스레드 수를 넘으면
     초당 1~2개 수준으로 제한된다 (46.2절, hill-climbing).
  7. 그 사이 새 요청은 계속 들어오고, 각각 또 하나의 스레드를 블로킹한다.
  8. 블로킹 속도 > 주입 속도  →  큐가 폭발한다.
  9. 응답 시간이 초 단위 → 십 초 단위 → 타임아웃.
     CPU 사용률은 5% 다. 아무도 일을 하고 있지 않다.
```

기아의 특징적 증상은 **낮은 CPU 사용률과 높은 응답 시간의 조합**이다. CPU가 놀고 있는데 요청이 밀린다면 거의 항상 스레드가 블로킹되어 있다.

| 금지 패턴 | 대체 |
|---|---|
| `task.Result` | `await task` |
| `task.Wait()` | `await task` |
| `task.GetAwaiter().GetResult()` | `await task` |
| 동기 `Stream.Read` | `await stream.ReadAsync(...)` |
| `Thread.Sleep` | `await Task.Delay(...)` |
| `SemaphoreSlim.Wait()` | `await sem.WaitAsync(...)` |
| `BlockingCollection.Take()` | `await channel.Reader.ReadAsync(...)` (51.1절) |
| `lock` 안의 긴 작업 | 임계 구역 축소 또는 `SemaphoreSlim` (51.3절) |

> **💡 sync-over-async를 찾는 법**
>
> 1. **분석기를 켜라.** `Microsoft.VisualStudio.Threading.Analyzers` 같은 Roslyn 분석기가 `.Result`·`.Wait()`를 경고로 잡는다.
> 2. **덤프를 떠라.** 부하 테스트 중 `dotnet-dump`로 덤프를 뜨고 스레드 스택을 보면, 같은 프레임에 수십 개 스레드가 몰려 있는 곳이 정확히 그 지점이다(74.5절).
> 3. **카운터를 보라.** `ThreadPool Thread Count`가 계속 증가하는데 `ThreadPool Queue Length`도 함께 커지면 기아다(51.7절).
>
> 예외는 하나 있다. **`Main` 메서드**다. `Main`이 반환하면 프로그램이 끝나므로 어딘가에서는 동기적으로 기다려야 한다. 다만 C# 7.1 이후 `async Task Main`이 지원되므로 컴파일러가 그 대기를 대신 만들어 준다.

### 요청 취소 토큰을 끝까지 흘리기

클라이언트가 연결을 끊었는데 서버가 15초짜리 쿼리를 끝까지 수행하는 것은 순수한 낭비다. ASP.NET Core는 `HttpContext.RequestAborted`로 그 신호를 준다.

```csharp
[HttpGet("/reports/{id}")]
public async Task<IActionResult> Get(int id, CancellationToken ct)   // 자동 바인딩
{
    var report = await _service.BuildAsync(id, ct);
    return Ok(report);
}
```

액션 메서드의 `CancellationToken` 매개변수는 **모델 바인더가 `HttpContext.RequestAborted`로 채워 준다.** 별도 설정이 필요 없다. 그다음은 이 토큰을 아래로 계속 전달하는 것이 전부다 — 서비스 계층, 리포지토리, `HttpClient`, `DbCommand`까지.

> **⚠️ 토큰을 받아 놓고 넘기지 않는 코드가 가장 흔한 실수다**
>
> ```csharp
> public async Task<Report> BuildAsync(int id, CancellationToken ct)
> {
>     var rows = await _db.QueryAsync(sql);           // ct 를 안 넘겼다
>     var extra = await _http.GetAsync(url);          // 여기도
>     ct.ThrowIfCancellationRequested();              // 여기서만 확인 — 너무 늦다
>     return Render(rows, extra);
> }
> ```
>
> `ThrowIfCancellationRequested`는 **이미 끝난 작업 뒤에서** 확인할 뿐이다. 두 번의 I/O는 이미 다 수행됐다. 취소의 목적인 자원 절약이 전혀 달성되지 않는다.
>
> 규칙: **`CancellationToken`을 받는 오버로드가 있으면 반드시 그것을 쓴다.** 컴파일러 경고가 없으므로 코드 리뷰나 분석기로 잡아야 한다.

> **⚠️ 쓰기 연산에 `RequestAborted`를 그대로 쓰면 데이터가 반쯤 쓰인다**
>
> 읽기 요청은 클라이언트가 끊으면 취소해도 된다. 그런데 주문 생성 도중 클라이언트가 끊었다고 트랜잭션 중간에 취소하면? 결제는 됐고 주문은 없는 상태가 될 수 있다.
>
> **부작용이 있는 연산은 요청 취소 토큰을 끝까지 흘리면 안 된다.** 대신 "여기부터는 끝까지 간다"는 경계를 명시적으로 두고, 그 안쪽은 `CancellationToken.None`이나 별도의 셧다운 토큰만 쓴다.
>
> ```csharp
> // 검증·조회 단계는 요청 취소를 존중한다
> var cart = await _carts.LoadAsync(cartId, ct);
>
> // 커밋 단계는 끝까지 간다
> await using var tx = await _db.BeginTransactionAsync(CancellationToken.None);
> await _orders.InsertAsync(order, CancellationToken.None);
> await tx.CommitAsync(CancellationToken.None);
> ```

### 동시성 제한으로 다운스트림 보호하기

ASP.NET Core는 들어오는 요청 수를 스스로 제한하지 않는다. 그래서 요청 1,000개가 동시에 들어오면 다운스트림에도 1,000개가 그대로 간다. 데이터베이스 커넥션 풀 크기가 100이라면 900개는 커넥션을 기다리다 타임아웃한다.

```csharp
// 이 레거시 API 는 동시 8개까지만 견딘다 (검증된 값)
private static readonly SemaphoreSlim Gate = new(8, 8);

public async Task<Quote> GetQuoteAsync(string symbol, CancellationToken ct)
{
    // 대기가 길어지면 차라리 실패시킨다 (51.2절의 혼합 전략)
    if (!await Gate.WaitAsync(TimeSpan.FromMilliseconds(500), ct))
        throw new ServiceBusyException("견적 서비스 포화");
    try
    {
        return await _http.GetFromJsonAsync<Quote>($"/quote/{symbol}", ct)
               ?? throw new InvalidOperationException("빈 응답");
    }
    finally { Gate.Release(); }
}
```

`WaitAsync(TimeSpan, CancellationToken)` 오버로드는 시간 안에 얻으면 `true`, 못 얻으면 `false`를 반환한다. **`false`일 때는 `Release`를 부르면 안 되므로** `try`가 그 뒤에 있어야 한다는 점을 다시 확인하라(51.3절).

### 싱글턴 서비스의 가변 상태

DI 컨테이너에 `AddSingleton`으로 등록된 서비스는 **모든 요청이 동시에 같은 인스턴스를 사용한다.** 48.14절이 다룬 애플리케이션 서버의 스레드 안전성 문제가 여기서 그대로 나타난다.

```csharp
// (X) 싱글턴(AddSingleton)에 요청별 상태를 두었다
public sealed class ReportBuilder
{
    private int _currentUserId;            // 요청마다 다른 값 — 경합

    public async Task<Report> BuildAsync(int userId, CancellationToken ct)
    {
        _currentUserId = userId;           // 다른 요청이 덮어쓴다
        var data = await _repo.LoadAsync(ct);
        return Render(data, _currentUserId);   // 남의 사용자 ID 일 수 있다
    }
}
```

이 버그는 부하가 낮으면 절대 나타나지 않고, 나타나면 **한 사용자에게 다른 사용자의 데이터를 보여 준다.** 보안 사고다.

| 수명 | 인스턴스 | 가변 상태 |
|---|---|---|
| `AddSingleton` | 애플리케이션당 1개 | **금지** (스레드 안전한 자료구조만) |
| `AddScoped` / `AddTransient` | 요청당 1개 / 주입할 때마다 | 허용 — 단 요청 안에서 병렬 실행하면 다시 문제 |

> **⚠️ `AddScoped`도 병렬 실행 앞에서는 안전하지 않다**
>
> `DbContext`는 대표적인 스코프 서비스이고 **스레드 안전하지 않다.** 다음은 흔한 사고다.
>
> ```csharp
> // (X) 같은 DbContext 를 동시에 사용한다
> await Task.WhenAll(ids.Select(id => _db.Orders.FindAsync(id).AsTask()));
> ```
>
> `InvalidOperationException`("A second operation was started on this context instance...")이 나거나, 더 나쁘게는 조용히 잘못된 결과가 나온다. 병렬로 조회하려면 `IDbContextFactory<T>`로 컨텍스트를 여러 개 만들어야 한다.
>
> **"스코프"는 요청 경계이지 스레드 경계가 아니다.**

싱글턴에서 상태가 필요하면 스레드 안전한 구조만 쓴다.

```csharp
private readonly ConcurrentDictionary<string, Quote> _cache = new();  // 50.10절
private long _hits;                                                    // Interlocked 로만 조작

public bool TryGet(string symbol, out Quote quote)
{
    if (!_cache.TryGetValue(symbol, out quote!)) return false;
    Interlocked.Increment(ref _hits);
    return true;
}
```

### `BackgroundService`와 우아한 종료

호스트가 관리하는 백그라운드 작업은 `IHostedService`, 실무에서는 그 추상 구현인 `BackgroundService`를 쓴다.

```csharp
public sealed class OrderWorker(ChannelReader<Order> reader,
                                IServiceScopeFactory scopes,
                                ILogger<OrderWorker> log) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await foreach (Order order in reader.ReadAllAsync(stoppingToken))
        {
            // 싱글턴 워커에서 스코프 서비스를 쓰려면 스코프를 직접 만든다
            using IServiceScope scope = scopes.CreateScope();
            var handler = scope.ServiceProvider.GetRequiredService<IOrderHandler>();
            try
            {
                await handler.HandleAsync(order, stoppingToken);
            }
            catch (OperationCanceledException) when (stoppingToken.IsCancellationRequested)
            {
                throw;                       // 종료 중 — 루프를 끝낸다
            }
            catch (Exception ex)             // 한 건의 실패가 워커를 죽이지 않게 한다
            {
                log.LogError(ex, "주문 {Id} 처리 실패", order.Id);
            }
        }
    }
}
```

여기 담긴 결정이 넷이다.

1. **`stoppingToken`을 `ReadAllAsync`에 넘긴다** — 종료 시 루프가 즉시 빠져나온다.
2. **`IServiceScopeFactory`로 스코프를 만든다** — `BackgroundService`는 싱글턴이므로 `DbContext` 같은 스코프 서비스를 생성자 주입으로 받으면 안 된다. 받으면 프로세스 수명 내내 같은 인스턴스를 쓰게 되어 위의 스코프 문제가 그대로 재현된다.
3. **항목별 예외를 잡는다** — 주문 하나가 실패했다고 워커가 죽으면 나머지가 처리되지 않는다.
4. **종료 중 취소는 다시 던진다** — 종료 신호를 오류로 취급하지 않는다.

> **⚠️ `BackgroundService`에서 예외가 빠져나가면 호스트가 멈춘다 ※.NET 6**
>
> .NET 6부터 `BackgroundServiceExceptionBehavior`의 기본값이 `StopHost`다. `ExecuteAsync`에서 처리되지 않은 예외가 나오면 **애플리케이션 전체가 종료된다.**
>
> .NET 5 이전에는 기본값이 사실상 무시(`Ignore`)여서, 워커가 조용히 죽고 아무도 모르는 상태가 됐다. 새 기본값이 훨씬 낫지만, **업그레이드 후 갑자기 프로세스가 종료되기 시작한 원인**이 이것인 경우가 있다.
>
> ```csharp
> builder.Services.Configure<HostOptions>(o =>
>     o.BackgroundServiceExceptionBehavior = BackgroundServiceExceptionBehavior.Ignore);
> ```
>
> 이 설정으로 옛 동작으로 되돌릴 수 있지만, 되돌리기 전에 **왜 예외가 빠져나오는지**를 먼저 고쳐야 한다.

**우아한 종료(graceful shutdown)의 순서**는 다음과 같다.

```text
  SIGTERM / Ctrl+C / 오케스트레이터의 종료 신호
   ↓ ① IHostApplicationLifetime.ApplicationStopping 이 신호를 받는다
   ↓ ② 새 요청 수락 중단 (서버가 리스너를 닫는다)
   ↓ ③ 모든 IHostedService 의 StopAsync 호출
   │    → BackgroundService 는 stoppingToken 을 취소하고 ExecuteAsync 완료를 기다린다
   ↓ ④ 진행 중인 요청이 끝나기를 기다린다
   ↓ ⑤ HostOptions.ShutdownTimeout 안에 안 끝나면 강제 종료
   ↓ ⑥ ApplicationStopped, 프로세스 종료
```

`HostOptions.ShutdownTimeout`의 기본값은 현재 30초다(과거 버전에서는 5초였으므로 대상 런타임에서 확인하라). 큐에 쌓인 작업을 비우고 나가려면 이 시간 안에 끝나야 한다.

```csharp
builder.Services.Configure<HostOptions>(o =>
    o.ShutdownTimeout = TimeSpan.FromSeconds(60));
```

> **💡 종료 시 큐를 비우려면 토큰을 두 개 써야 한다**
>
> `stoppingToken`을 `ReadAllAsync`에 넘기면 종료 신호가 오는 즉시 루프가 끝나고 **큐에 남은 항목이 버려진다.** 남은 것을 처리하고 나가려면 신호를 나눠야 한다.
>
> ```csharp
> protected override async Task ExecuteAsync(CancellationToken stoppingToken)
> {
>     // stoppingToken 은 "새 항목 받기를 멈춰라"로만 쓴다
>     stoppingToken.Register(() => _writer.Complete());
>
>     // 읽기 루프는 취소하지 않는다 — Complete() 로 자연 종료된다
>     await foreach (Order order in _reader.ReadAllAsync(CancellationToken.None))
>         await HandleAsync(order, CancellationToken.None);
> }
> ```
>
> 이러면 종료 신호가 프로듀서를 막고, 컨슈머는 남은 항목을 다 처리한 뒤 끝난다. 단 **이 배출 시간이 `ShutdownTimeout` 안에 들어가야** 한다. 그러지 못하면 어차피 강제 종료되므로, 큐 용량과 종료 타임아웃은 함께 설계해야 한다(51.2절).

### 요청당 스레드 모델 vs async 모델

두 모델의 차이를 자원 관점에서 정리하면 이렇다.

| | 요청당 스레드(동기) | async |
|---|---|---|
| I/O 대기 중 | 스레드가 블로킹된 채 유지 | 스레드가 풀로 반환됨 |
| 동시 요청 1,000건 | 스레드 약 1,000개 필요 | 스레드 수십 개로 충분 |
| 스레드당 스택 예약 | 기본 1 MB (45.4절) | — |
| 1,000 동시성의 스택 비용 | 약 1 GB 예약 | 무시할 수준 |
| 컨텍스트 전환 | 스레드 수에 비례해 증가 | 훨씬 적음 |
| CPU 바운드 작업 | 차이 없음 | **차이 없음** |

마지막 행이 중요하다. **async는 I/O 대기를 스레드 없이 표현하는 기법이지 CPU를 빠르게 만드는 기법이 아니다.** 작업이 순수하게 CPU 바운드라면 async로 바꿔도 처리량은 그대로다 — 오히려 상태 기계 오버헤드만 늘어난다.

> **⚠️ 서버에서 CPU 바운드 작업을 `Task.Run`으로 감싸는 것은 손해다**
>
> ```csharp
> public async Task<IActionResult> Compose()
> {
>     var model = await Task.Run(() => LongRunningCpuWork());   // 이득이 없다
>     return View(model);
> }
> ```
>
> 무슨 일이 일어나는지 따라가 보자. 요청을 처리하던 스레드 풀 스레드 T1이 작업을 T2에게 넘긴다. T1은 해방되어 다른 일을 받는다. **그런데 T2도 같은 스레드 풀에서 왔다.** 해방된 스레드 하나를 얻으려고 스레드 하나를 소모했다. 순 이득은 0이고, 컨텍스트 전환 두 번이 추가됐다.
>
> UI 애플리케이션에서는 이 거래가 남는다 — UI 스레드는 **희소 자원**이고 풀 스레드는 아니기 때문이다. 서버에서는 모든 스레드가 동등하므로 남는 것이 없다.
>
> 서버에서 CPU 바운드 작업이 정말 문제라면 해법은 **다른 프로세스나 다른 머신으로 넘기는 것**이다. 별도의 워커 서비스를 두고 큐(51.1절)로 연결하는 구성이 그것이다.

### 캐시, 커넥션 풀, `HttpClient` 수명

서버 성능의 상당 부분은 "매 요청마다 다시 만들지 않는 것"에서 온다.

**`HttpClient`** — 요청마다 `new HttpClient()`를 만들면 소켓 고갈(socket exhaustion)이 발생한다. `Dispose`해도 TCP 연결은 `TIME_WAIT` 상태로 수십 초 남기 때문이다. 반대로 싱글턴 하나를 영원히 쓰면 DNS 변경을 반영하지 못한다. 정답은 `IHttpClientFactory`이며, 43.7절과 43.9절에서 상세히 다뤘다.

**메모리 캐시** — `IMemoryCache`(`Microsoft.Extensions.Caching.Memory`)를 `builder.Services.AddMemoryCache()`로 등록하고 DI로 주입받아 쓴다.

```csharp
var options = new MemoryCacheEntryOptions()
    .SetSlidingExpiration(TimeSpan.FromSeconds(20));   // 마지막 접근 기준
_memoryCache.Set(key, value, options);
```

슬라이딩 만료(sliding expiration)는 마지막 접근으로부터의 시간을 재고, 절대 만료(`SetAbsoluteExpiration`)는 생성 시점부터의 시간을 잰다. 자주 접근되는 항목이 영원히 살아 있으면 안 되는 경우에는 둘을 함께 건다.

> **⚠️ 캐시는 그 자체로 메모리 누수 후보다**
>
> `IMemoryCache`는 **크기 제한이 기본으로 없다.** 키가 무한히 늘어날 수 있는 형태(사용자 ID, 요청 파라미터 조합)로 캐싱하면 프로세스 메모리가 무한히 자란다. 66.11절이 나열한 대표 누수 시나리오의 "정적 캐시"가 정확히 이것이다.
>
> `MemoryCacheOptions.SizeLimit`을 설정하고 각 항목에 `SetSize`를 지정하면 상한이 생긴다. **`SizeLimit`을 설정했는데 `SetSize`를 빠뜨린 항목이 있으면 `InvalidOperationException`이 발생한다** — 전부 지정하거나 전부 지정하지 않거나 둘 중 하나다.

## 51.7 비동기 코드에서 스레드 할당과 컨텍스트 전환을 줄이기

### 먼저 무엇을 줄이려는지 정하기

이 절의 기법들은 모두 같은 두 가지를 겨냥한다.

- **할당** — `Task` 객체, 상태 기계 박스, 델리게이트, 클로저(47.7절·47.8절)
- **컨텍스트 전환** — 스레드 풀 큐잉, 동기화 컨텍스트 `Post`, OS 스레드 전환

그리고 두 가지 모두 **핫 패스가 아니면 무의미하다.** 초당 10번 호출되는 메서드에서 `Task` 할당 하나를 아끼는 것은 측정 불가능한 개선이다. 이 절의 마지막 문단에서 이 이야기로 다시 돌아온다.

### 동기 완료 경로를 살리기 — `ValueTask`

비동기 메서드의 상당수는 **대부분의 호출에서 실제로는 동기적으로 완료된다.** 캐시 적중, 버퍼에 이미 데이터가 있는 스트림 읽기, 채널에 항목이 이미 있는 `ReadAsync` 같은 경우다.

`Task<T>`를 반환하면 이런 호출에서도 힙 객체가 하나 생긴다(캐시된 완료 태스크로 회피되는 특수 경우 — `Task.CompletedTask`, `bool`/작은 `int` 결과 — 를 제외하면). `ValueTask<T>`는 결과를 구조체 안에 그대로 담아 그 할당을 없앤다(47.13절).

원천이 보여 준 관용구는 이렇다. **바깥 메서드에 `async`를 붙이지 않고**, 비동기 경로만 지역 함수로 분리한다.

```csharp
public ValueTask<IReadOnlyList<WeatherData>> GetHistoryAsync(CancellationToken ct)
{
    if (DateTime.UtcNow - _lastReading <= TimeSpan.FromMinutes(5))
        return new ValueTask<IReadOnlyList<WeatherData>>(_cached);   // 할당 0, 상태 기계 0

    return new ValueTask<IReadOnlyList<WeatherData>>(LoadAsync());

    async Task<IReadOnlyList<WeatherData>> LoadAsync()
    {
        var list = new List<WeatherData>();
        for (var d = _start; d < _end; d = d.AddDays(1))
            list.Add(await FetchAsync(d, ct));
        (_cached, _lastReading) = (list, DateTime.UtcNow);
        return list;
    }
}
```

핵심은 **바깥 메서드에 `async` 수식자가 없다**는 것이다. `async`를 붙이는 순간 컴파일러가 상태 기계를 만들고, 캐시 적중 경로에서도 그 비용을 문다. `async` 없이 `ValueTask`를 직접 만들어 반환하면 캐시 적중 시 상태 기계 자체가 존재하지 않는다.

> **⚠️ `ValueTask`의 사용 규칙은 `Task`보다 훨씬 엄격하다**
>
> - **한 번만 `await` 한다.** 두 번 `await` 하면 동작이 정의되지 않는다.
> - **두 곳에서 동시에 `await` 하지 않는다.**
> - **완료되기 전에 `.Result`를 읽지 않는다.**
> - **저장해 두었다가 나중에 쓰지 않는다.** 보관이 필요하면 `.AsTask()`로 변환한다.
> - **`Task.WhenAll`에 넘기려면 `.AsTask()`** — `ValueTask`를 여러 개 모으는 것 자체가 위험 신호다.
>
> 이 제약이 있는 이유는 `IValueTaskSource` 기반 구현이 완료 후 객체를 **재사용**하기 때문이다. 51.1절에서 본 채널의 대기 노드 재사용이 그 예다. 이미 재사용된 객체를 다시 `await` 하면 남의 결과를 받는다.
>
> **공개 API의 반환 타입은 기본적으로 `Task`/`Task<T>`로 두어라.** 측정으로 할당이 병목임을 확인한 뒤에만 `ValueTask`로 바꾼다. 47.13절이 그 판단 기준을 다뤘다.

### 불필요한 `Task.Run` 제거

51.6절에서 서버 쪽 사례를 봤다. 여기서는 더 나쁜 형태를 본다 — **동기 메서드를 `Task.Run`으로 감싸 비동기인 척하는 API**다.

```csharp
// (X) 가짜 비동기 API
public Task<double> ComputeValueAsync() => Task.Run(() => ComputeValue());
```

호출자는 `Async` 접미사를 보고 "이건 I/O를 기다리는구나, 스레드를 아끼는구나"라고 생각한다. 실제로는 스레드 풀 스레드 하나를 태워 CPU 작업을 돌린다. **API가 거짓말을 한다.**

동기 버전만 제공하면 호출자가 선택할 수 있다. 이미 백그라운드에 있으면 그냥 부르고, UI 스레드에 있으면 자기가 `Task.Run`으로 감싼다. 비동기 래퍼를 제공하는 순간 그 선택권을 빼앗는다.

| `Task.Run`이 옳은 자리 | `Task.Run`이 틀린 자리 |
|---|---|
| UI 이벤트 핸들러에서 CPU 작업 밀어내기 | 라이브러리 내부 |
| 콘솔 앱에서 여러 CPU 작업 병렬화 | 서버 요청 핸들러 |
| 동기 API만 있는 레거시를 호출부에서 감쌀 때 | 동기 메서드에 `Async` 이름 붙이기 |
| — | 이미 비동기인 메서드를 다시 감싸기 |

### `async` 래퍼의 비용과 `return task`의 트레이드오프

메서드가 하는 일이 "다른 비동기 메서드를 호출해서 그 결과를 그대로 돌려주는 것"뿐이라면, 두 가지 형태가 가능하다.

```csharp
// A: async 래퍼 — 상태 기계가 한 겹 생긴다
public async Task<Data> GetAsync(int id, CancellationToken ct)
    => await _inner.GetAsync(id, ct);

// B: 태스크 직접 반환 — 상태 기계가 없다
public Task<Data> GetAsync(int id, CancellationToken ct)
    => _inner.GetAsync(id, ct);
```

B가 더 싸다. A는 상태 기계 구조체를 만들고, 첫 `await`에서 미완료면 힙으로 박싱하고, `AsyncTaskMethodBuilder`가 새 `Task`를 만들어 내부 태스크의 완료를 그 태스크로 전달한다. B는 내부 태스크 참조를 그대로 넘긴다. **호출 계층이 다섯 겹이면 A는 상태 기계 다섯 개, B는 0개다.**

그런데 B는 세 가지가 달라진다.

**① 예외가 던져지는 시점이 다르다.**

```csharp
// A (async): 검증 예외도 faulted Task 에 담긴다 — 호출자가 await 해야 관찰된다
public async Task<Data> GetAsync(int id, CancellationToken ct)
{
    if (id <= 0) throw new ArgumentOutOfRangeException(nameof(id));
    return await _inner.GetAsync(id, ct);
}

// B (return task): 검증 예외가 호출 즉시 동기적으로 던져진다
public Task<Data> GetAsync(int id, CancellationToken ct)
{
    if (id <= 0) throw new ArgumentOutOfRangeException(nameof(id));
    return _inner.GetAsync(id, ct);
}
```

`var t = GetAsync(-1, ct);` 한 줄만 실행하면, A는 아무 일도 일어나지 않고(태스크가 실패 상태로 반환됨) B는 즉시 예외가 터진다. 78.12절이 다루는 "즉시 오류 보고" 문제이며, 인자 검증에 한해서는 **B의 동작이 더 바람직하다**. 그래서 원천이 제시한 관용구가 나온다 — **바깥은 `async` 없이 검증만 하고, 비동기 본체는 지역 함수로 분리한다.**

```csharp
public Task<Data> GetAsync(int id, CancellationToken ct)
{
    if (id <= 0) throw new ArgumentOutOfRangeException(nameof(id));   // 즉시 던진다
    return Impl();

    async Task<Data> Impl()
    {
        var raw = await _inner.GetAsync(id, ct);
        return Transform(raw);
    }
}
```

지역 함수는 바깥 메서드의 매개변수와 지역 변수에 그대로 접근할 수 있고, 외부에서 호출할 수 없으므로 검증을 우회할 방법이 없다. 람다 대신 지역 함수를 쓰는 이유는 컴파일러가 델리게이트 인스턴스 생성 없이 private 메서드로 낮출 수 있기 때문이다.

**② `using` 스코프가 달라진다. 이쪽이 훨씬 위험하다.**

```csharp
// (X) 치명적 버그
public Task<string> ReadAsync(string path)
{
    using var reader = new StreamReader(path);
    return reader.ReadToEndAsync();      // 반환하는 순간 using 이 reader 를 Dispose 한다
}
```

`return`이 실행되는 즉시 `using`의 `Dispose`가 호출되고, 그다음 반환된 태스크는 **이미 닫힌 스트림 위에서** 계속 읽으려 한다. 결과는 `ObjectDisposedException`이거나, 더 나쁘게는 타이밍에 따라 달라지는 간헐적 실패다.

```csharp
// 올바른 형태 — await 가 있으므로 using 이 완료 후에 끝난다
public async Task<string> ReadAsync(string path)
{
    using var reader = new StreamReader(path);
    return await reader.ReadToEndAsync();
}
```

**`using`(또는 `try`/`finally`, `lock`) 안에서 태스크를 반환할 때는 반드시 `await` 해야 한다.** 이 경우 `async` 래퍼의 비용은 정확성의 대가이지 낭비가 아니다.

**③ 스택 트레이스와 진단 정보가 달라진다.**

B에서는 내부 메서드의 예외 스택에 래퍼 메서드가 나타나지 않는다. 호출 계층을 얇게 만든 만큼 디버깅 정보도 얇아진다.

| | A: `async` 래퍼 | B: `return task` |
|---|---|---|
| 상태 기계 | 한 겹 생성 | 없음 |
| 할당(비동기 경로) | 박스 + `Task` | 없음(내부 태스크 재사용) |
| 인자 검증 예외 | faulted `Task` | **동기적으로 던짐** |
| `using`/`try-finally` 안전 | **안전** | **위험** |
| 스택 트레이스 | 래퍼 프레임 포함 | 래퍼 프레임 없음 |
| `ConfigureAwait` 제어 | 가능 | 불가(내부 설정 그대로) |

> **💡 실무 규칙**
>
> - 메서드 본문이 **호출 하나뿐이고** `using`·`try`·`lock`이 없으면 → `return task` (B).
> - 인자 검증이 있으면 → **검증은 바깥, 본체는 지역 함수**.
> - `using`이나 `try/finally`가 있으면 → 무조건 `async`/`await` (A).
> - `await` 뒤에 무슨 작업이든 있으면 → 당연히 A.
>
> 그리고 이 최적화의 이득은 **호출 빈도가 아주 높을 때만** 의미 있다. 계층이 다섯 겹이고 초당 백만 번 호출되는 경로라면 재 볼 가치가 있고, 그 외에는 가독성을 택하라.

### `ConfigureAwait(false)`의 실제 이득

`ConfigureAwait(false)`는 "연속을 캡처된 컨텍스트에서 실행하지 마라"는 지시다(47.12절). 이득은 실행 환경에 따라 다르다.

| 환경 | `ConfigureAwait(false)`의 효과 |
|---|---|
| ASP.NET Core | **거의 없음** — 컨텍스트가 애초에 `null`이다 |
| WinForms / WPF / MAUI | **크다** — UI 스레드로 되돌아가는 마셜링을 생략 |
| 콘솔 / 워커 서비스 | 없음 — 기본 컨텍스트다 |
| 라이브러리 코드 | **반드시 쓴다** — 어떤 환경에서 호출될지 모른다 |

라이브러리에서 필수인 이유는 명확하다. UI 애플리케이션이 그 라이브러리를 호출하면, `ConfigureAwait`가 없는 모든 `await`가 UI 스레드로 되돌아온다. 라이브러리 내부의 순수 계산이 UI 스레드에서 실행되고, UI가 그만큼 느려진다. 게다가 47.14절이 다룬 sync-over-async 데드락의 조건이 바로 이것이다.

> **⚠️ 첫 `await`만 `ConfigureAwait(false)`를 붙이면 충분하다는 오해**
>
> "첫 번째 `await` 이후에는 이미 기본 컨텍스트에 있으니 나머지는 필요 없다"고 생각하기 쉽다. **틀렸다.**
>
> 첫 번째 태스크가 **동기적으로 완료되면** `await`는 컨텍스트를 바꾸지 않고 그대로 진행한다(47.9절 — 완료 경로 최적화). 그러면 두 번째 `await`에 도달했을 때도 여전히 원래 컨텍스트 위에 있고, 거기서 `ConfigureAwait`가 없으면 그 컨텍스트로 되돌아온다.
>
> 캐시 적중이 잦은 코드에서는 첫 태스크가 거의 항상 동기 완료된다. 즉 "가끔만 UI 스레드에 갇히는" 코드가 되어 재현이 어려운 성능 문제가 된다.
>
> **라이브러리 코드에서는 모든 `await`에 `ConfigureAwait(false)`를 붙인다.** 예외 없이.

> **📌 컨텍스트 캡처 자체의 비용은 크지 않다**
>
> 캡처는 `SynchronizationContext.Current`(스레드 정적 필드)를 읽고 `null`인지 확인하는 정도다. ASP.NET Core에서 `ConfigureAwait(false)`를 다 붙여도 측정 가능한 처리량 개선은 나오지 않는다. 그럼에도 애플리케이션 코드에서 붙이지 않는 것을 권하는 이유는 노이즈이기 때문이고, 라이브러리 코드에서 붙이는 이유는 **성능이 아니라 정확성** 때문이다.
>
> 프로젝트 전체에 `ConfigureAwait`를 붙이는 정책이 필요하다면 `ConfigureAwaitOptions`(※.NET 8)나 빌드 프로퍼티를 검토할 수 있지만, 대개는 "라이브러리 프로젝트에만 분석기를 켠다"가 가장 실용적이다.

### `Task.Yield`가 필요한 순간

`await Task.Yield()`는 "지금 즉시 반환하고 나머지는 연속으로 스케줄하라"는 뜻이다. 항상 비동기적으로 완료되므로 반드시 한 번의 스케줄링이 일어난다. 필요한 경우는 셋이다.

**① 긴 동기 루프 중간에 UI에 숨 쉴 틈을 준다.**

```csharp
private async Task RenderAllAsync(IReadOnlyList<Item> items)
{
    for (int i = 0; i < items.Count; i++)
    {
        canvas.Draw(items[i]);          // UI 스레드에서만 가능한 작업
        if ((i & 0x3F) == 0)            // 64개마다
            await Task.Yield();          // 메시지 펌프에 제어를 돌려준다
    }
}
```

UI 컨텍스트에서 `Task.Yield`의 연속은 디스패처 큐에 들어가므로, 대기 중인 입력·페인트 메시지가 먼저 처리된다. `Task.Delay(1)`로 같은 효과를 흉내 내는 코드를 볼 수 있는데, 그쪽은 타이머를 걸므로 더 비싸고 실제 대기 시간도 시스템 타이머 해상도에 좌우된다.

**② 동기 완료의 연쇄로 스택이 깊어지는 것을 막는다.**

```csharp
async Task ProcessAllAsync(ChannelReader<Item> reader, CancellationToken ct)
{
    while (await reader.WaitToReadAsync(ct))
    {
        while (reader.TryRead(out Item item))
        {
            await HandleAsync(item, ct);   // 캐시 적중 시 항상 동기 완료
            await Task.Yield();            // 스택 성장을 끊는다
        }
    }
}
```

모든 `await`가 동기 완료되면 연속이 인라인으로 실행되어 스택이 계속 깊어질 수 있다. 실제로 이 문제가 나타나는 코드는 드물지만, 재귀적 비동기 구조에서는 `StackOverflowException`으로 이어질 수 있다. 51.1절에서 `AllowSynchronousContinuations = true`가 위험한 이유와 같은 뿌리다.

**③ `async` 메서드의 앞부분을 즉시 반환시킨다.** 호출자를 바로 돌려보내고 싶을 때 첫 줄에 `await Task.Yield()`를 둔다. 다만 이 용법은 대개 설계 냄새다 — 정말 필요한 것이 무엇인지 다시 보는 편이 낫다.

> **⚠️ `Task.Yield`를 루프마다 부르면 그 자체가 병목이다**
>
> 매 반복마다 스케줄링을 한 번씩 강제하는 것이므로 루프 본문이 짧으면 스케줄링 비용이 본문을 압도한다. 위 예제에서 `(i & 0x3F) == 0`처럼 **간격을 두는 것이 핵심이다.** 간격은 "한 덩어리가 대략 몇 밀리초인가"로 정한다 — UI라면 16 ms(한 프레임) 이내가 목표다.

### 스레드 풀 카운터로 문제를 확인하는 법

이 장에서 다룬 문제들은 대부분 몇 개의 숫자로 드러난다.

```bash
# 실행 중인 프로세스의 런타임 카운터를 실시간으로 본다
dotnet-counters monitor --process-id 1234 --counters System.Runtime
```

| 카운터 | 정상 | 문제 신호 |
|---|---|---|
| `ThreadPool Thread Count` | 안정적, 코어 수의 몇 배 이내 | **계속 증가** → 블로킹(sync-over-async) |
| `ThreadPool Queue Length` | 0에 가깝게 유지 | **지속적으로 큼** → 기아 또는 처리량 부족 |
| `% Time in GC` / `Allocation Rate` | 낮고 안정적 | 급증 → `Task`·클로저 할당 과다(69장) |
| `CPU Usage` | 부하에 비례 | **낮은데 지연이 크다** → 블로킹 |

코드에서 직접 읽을 수도 있다.

```csharp
// System.Threading.ThreadPool 의 진단 속성 (75.3절의 Meter 로 내보낸다)
_meter.CreateObservableGauge("threadpool.thread.count", () => ThreadPool.ThreadCount);
_meter.CreateObservableGauge("threadpool.queue.length", () => ThreadPool.PendingWorkItemCount);
```

> **💡 가장 진단력이 높은 조합은 "CPU 낮음 + 지연 높음 + 스레드 수 증가"다**
>
> 이 셋이 동시에 나타나면 원인은 거의 항상 스레드 블로킹이다. 그다음 순서는 정해져 있다.
>
> 1. 부하 상태에서 `dotnet-dump collect`로 덤프를 뜬다.
> 2. 스레드 스택을 모두 나열해 **같은 프레임에 몰려 있는 스레드 무리**를 찾는다.
> 3. 그 프레임이 `.Result`·`.Wait()`·`Monitor.Wait`·`SemaphoreSlim.Wait`(비동기 아닌 버전) 중 하나일 것이다.
>
> 상세한 절차는 74.5절과 74.8절에 있다.

### 마무리 — 측정 없이 이 최적화를 하지 마라

이 절에 나온 기법은 전부 **조건부**다.

- `ValueTask`는 동기 완료가 잦고 호출 빈도가 극단적으로 높을 때만 이득이 있고, 오용 시 진단 불가능한 버그를 만든다.
- `return task`는 상태 기계 한 겹을 아끼지만 `using` 안에서 쓰면 데이터가 깨진다.
- `ConfigureAwait(false)`는 UI 애플리케이션에서 크게 유효하고 서버에서는 거의 무의미하다.
- `Task.Yield`는 응답성을 살리지만 간격을 잘못 잡으면 그 자체가 병목이다.

이 조건들을 코드만 보고 판단할 방법은 없다. **어느 메서드가 초당 몇 번 호출되는지, 그중 몇 퍼센트가 동기 완료되는지, 할당이 실제로 GC 시간에 반영되고 있는지** 는 측정해야만 안다. 67장 전체가 이 이야기를 한다.

그리고 순서가 중요하다. 이 절의 미시적 최적화는 **51.1절부터 51.6절까지의 구조적 결정을 모두 올바르게 내린 뒤에** 의미가 생긴다. 스레드를 블로킹하는 코드 한 줄이 남아 있다면 `ValueTask` 백 개를 도입해도 아무것도 나아지지 않는다. 무제한 큐가 하나 있다면 상태 기계를 아무리 줄여도 결국 메모리가 터진다.

**순서는 이렇다.**

1. **끝까지 async** — 블로킹을 0으로 만든다(51.6절).
2. **경계와 백프레셔** — 모든 큐에 상한과 정책을 준다(51.2절).
3. **타임아웃·취소·격리** — 장애가 번지지 않게 한다(51.4절).
4. **측정** — 병목이 어디인지 숫자로 확인한다(67장).
5. **그다음에** 이 절의 기법을 적용한다.

### 2권을 닫으며

2권은 35장의 문자열 처리에서 시작해 여기까지 왔다. 앞의 열 장(35~44장)은 BCL이 이미 준비해 둔 도구 — 텍스트, 날짜, 스트림, 직렬화, 네트워킹, 암호화 — 를 다뤘다. 뒤의 일곱 장(45~51장)은 그 도구들을 **동시에** 쓸 때 무엇이 달라지는지를 다뤘다.

Part IX을 관통하는 명제 하나를 다시 적어 둔다. **동시성은 도구의 문제가 아니라 자원의 문제다.**

- 45장은 스레드가 왜 비싼 자원인지 보였다 — 커널 객체, 1 MB 스택 예약, 컨텍스트 전환.
- 46장은 그래서 풀이 필요하고, 풀에는 주입 속도라는 한계가 있음을 보였다.
- 47장은 `async`/`await`가 "기다리는 동안 스레드를 놓아주는" 언어 차원의 장치임을 상태 기계 수준까지 분해했다.
- 48장과 49장은 공유 상태를 다루는 비용 — 잠금, 경합, 메모리 모델 — 을 보였다.
- 50장은 CPU 코어라는 자원을 어떻게 나눠 쓰는지, 그리고 암달의 법칙이 정한 상한을 보였다.
- 51장은 그 모든 것을 **큐 하나의 크기를 정하는 결정**, **타임아웃 하나를 어디에 두는 결정**으로 환원했다.

이 장의 모든 실패 모드는 결국 같은 문장으로 요약된다. **무언가가 무한하다고 가정했다.** 큐가 무한히 길어질 수 있다고, 스레드가 무한히 생길 수 있다고, 재시도를 무한히 해도 된다고, 다운스트림이 무한히 빠르다고. 유한한 자원 위에서 유한한 상한을 명시하는 것 — 그것이 이 장이 말하는 아키텍처의 전부다.

3권은 여기서 한 층 더 내려간다. 지금까지 "런타임이 무엇을 해 준다"고 말하고 넘어간 것들 — 어셈블리를 어떻게 찾고, 타입을 메모리에 어떻게 배치하고, IL을 어떻게 기계어로 바꾸고, 객체를 언제 회수하는지 — 을 직접 열어 본다.

## 이 장의 요약

- **`Channel<T>`은 비동기 프로듀서/컨슈머 큐이고, `BlockingCollection<T>`의 자리를 대체한다.** 결정적 차이는 대기 중 스레드 점유가 0이라는 것이다. `ChannelReader<T>`/`ChannelWriter<T>`가 분리되어 있어 방향을 타입으로 강제할 수 있고, `await foreach (var x in reader.ReadAllAsync(ct))`가 표준 소비 루프다. `Complete()`를 부르지 않으면 그 루프는 영원히 끝나지 않으므로 `try/finally`로 완료를 보장하고, 프로듀서의 예외는 `Complete(ex)`로 전달하라.
- **`SingleReader`/`SingleWriter`는 힌트가 아니라 계약이다.** 켜면 내부 구현이 바뀌고, 틀리면 예외 없이 조용히 깨진다. `AllowSynchronousContinuations`는 컨슈머 코드를 프로듀서 스레드에서 인라인 실행시키므로 잠금 안에서 쓰거나 UI 스레드에서 쓰면 즉시 사고다.
- **무제한 큐는 메모리 누수이자 지연 폭발이다.** 리틀의 법칙(`W = L / λ`)이 말하듯 큐 길이가 곧 지연이다. 용량은 `허용 지연 × 처리율`에서 출발해 버스트와 메모리 예산으로 보정하고, 개수가 아니라 **바이트로 환산해** 검토하라.
- **`BoundedChannelFullMode`의 네 값은 서로 다른 실패를 고르는 것이다.** `Wait`는 백프레셔(데이터 보존, 지연 증가), `Drop*`은 부하 차단(지연 상한 유지, 데이터 손실)이다. Drop 모드에서 `TryWrite`는 항목을 버리고도 `true`를 반환하므로 드롭 수는 `itemDropped` 콜백(※.NET 7)으로 반드시 세라. 그리고 **백프레셔는 전파되지 않으면 없는 것이다** — `WriteAsync`가 반환한 `ValueTask`를 버리는 한 줄이 경계 채널의 의미를 통째로 없앤다. 큐 깊이·대기 시간·드롭 수·프로듀서 대기 시간 네 지표를 내보내지 않으면 큐는 관측 불가능한 블랙박스다. 다단 파이프라인이면 각 단계의 지연이 더해지므로 **종단 간 지연을 직접 측정**해야 한다.
- **`lock` 안에서 `await`는 컴파일되지 않는다.** `Monitor`가 스레드 친화적이기 때문이다. async lock의 정석은 `SemaphoreSlim(1, 1)` + `WaitAsync` + `try/finally Release`이며, **`WaitAsync`는 반드시 `try` 바깥에** 있어야 한다. `using (await sem.EnterAsync())` 관용구가 이 실수를 구조적으로 막는다.
- **async lock은 재진입할 수 없다.** 같은 논리 흐름이 다시 들어오면 CPU도 예외도 로그도 없는 자기 데드락이다. 세마포어를 쥔 채 다른 컴포넌트를 호출하지 마라. 애초에 잠금이 필요 없게 만드는 세 대안 — 채널로 직렬화(액터), 불변 스냅숏 + `Interlocked.CompareExchange`, `Lazy<Task<T>>` — 이 거의 항상 낫다.
- **타임아웃은 작업을 멈추지 않는다.** `WaitAsync`가 `TimeoutException`을 던진 뒤에도 원래 작업은 계속 돈다. 실제로 멈추려면 취소 토큰이 대상까지 전달돼야 한다. 링크된 `CancellationTokenSource`는 반드시 `Dispose` 하라 — 장수명 토큰에 링크하면 그 자체가 누수다.
- **재시도는 멱등성을 확인한 뒤에만 정당하다.** 지수 백오프에 **지터가 반드시** 붙어야 재시도 폭풍을 막고, 계층마다 재시도를 걸면 시도 횟수가 곱해진다. 서킷 브레이커와 벌크헤드까지 필요해지면 직접 짜지 말고 Polly 같은 라이브러리를 쓰되, 정책의 안팎 순서가 의미를 바꾼다는 것만은 직접 확인하라.
- **UI는 단일 스레드 메시지 펌프 위에 있다.** WinForms의 `Invoke`/`InvokeRequired`, WPF의 `Dispatcher`/`CheckAccess`/`DispatcherPriority`, MAUI의 `MainThread` — 이 셋을 `SynchronizationContext`가 추상화하므로 `async`/`await`를 쓰면 마셜링 코드가 거의 필요 없다. 잠금을 쥔 채 `Invoke`를 부르면 데드락이고, UI 갱신 빈도는 반드시 스로틀링해야 한다.
- **`async void`는 UI 이벤트 핸들러에서만 허용되고, 그때도 본문 전체를 `try/catch`로 감싸야 한다.** 빠져나간 예외는 동기화 컨텍스트 위에서 직접 던져져 애플리케이션을 종료시킨다. 그리고 `async void`는 재진입을 막지 않으므로 버튼 비활성화나 진행 중 플래그가 별도로 필요하다.
- **ASP.NET Core에는 `SynchronizationContext`가 없다.** 그래서 sync-over-async가 데드락 대신 **스레드 풀 기아**를 만든다 — 경고 신호가 사라진 것이지 안전해진 것이 아니다. 증상은 "CPU는 낮은데 지연이 크고 스레드 수가 계속 증가"다.
- **서버에서 CPU 바운드 작업을 `Task.Run`으로 감싸는 것은 손해다.** 같은 풀에서 스레드 하나를 얻으려고 하나를 소모하고 컨텍스트 전환 두 번만 추가된다. UI에서는 이득이지만(UI 스레드가 희소 자원이므로) 서버에서는 다른 프로세스로 넘기는 것이 유일한 해법이다. 그리고 **`BackgroundService`는 항목별 예외를 잡고, 스코프 서비스는 `IServiceScopeFactory`로 만들어야 한다.** ※.NET 6부터 `ExecuteAsync`에서 빠져나간 예외는 호스트 전체를 종료시킨다. 종료 시 큐를 배출하려면 `stoppingToken`으로 프로듀서만 막고 컨슈머는 자연 종료시키되, 그 시간이 `ShutdownTimeout`(기본 30초) 안에 들어가야 한다.
- **`ValueTask`·`return task`·`ConfigureAwait(false)`·`Task.Yield`는 전부 조건부 최적화다.** `using` 안에서 태스크를 반환하면 스트림이 먼저 닫히고, 라이브러리에서 `ConfigureAwait(false)`를 첫 `await`에만 붙이면 동기 완료 경로에서 컨텍스트에 갇힌다. **구조적 결정을 먼저 끝내고, 측정으로 병목을 확인한 뒤에** 이 기법들을 꺼내라.

## 연습 문제

1. **채널 완료 전파 관찰.** `Channel.CreateUnbounded<int>()`로 프로듀서 1 / 컨슈머 3 구성을 만들어라. (a) `Complete()`를 부르는 버전, (b) 부르지 않는 버전, (c) `Complete(new InvalidOperationException("실패"))`를 부르는 버전 세 가지를 실행하고, 각각에서 세 컨슈머 태스크의 최종 상태(`Task.Status`)와 `Reader.Completion`의 상태를 출력하라. (b)에서 프로세스가 종료되지 않는 것을 확인한 뒤, 컨슈머 루프에 `CancellationToken`을 넣어 탈출시키는 버전을 추가하라.

2. **백프레셔 실측.** 용량 10인 경계 채널에 초당 1,000건을 쓰는 프로듀서와 초당 100건을 처리하는 컨슈머를 붙여라. `FullMode`를 `Wait`·`DropOldest`·`DropWrite` 세 가지로 바꿔 가며 30초간 실행하고, 각각에 대해 (i) 실제 쓰기 성공 건수, (ii) 처리 완료 건수, (iii) `itemDropped` 콜백 호출 수, (iv) 항목이 큐에서 대기한 시간의 p50/p99를 표로 기록하라. 리틀의 법칙이 예측한 값과 비교하라.

3. **async lock 데드락 재현과 진단.** 51.3절의 `OuterAsync`/`InnerAsync` 자기 데드락을 그대로 재현하라. 프로세스가 멈춘 상태에서 `dotnet-dump collect`로 덤프를 뜨고, 비동기 스택에서 `SemaphoreSlim`에 걸린 상태 기계를 찾아 두 호출 지점을 식별하라. 그다음 액터 방식(채널 직렬화)으로 같은 로직을 다시 구현해 데드락이 원리적으로 불가능해지는지 확인하라.

4. **타임아웃이 작업을 멈추지 않음을 증명.** 10초 걸리는 작업을 `WaitAsync(TimeSpan.FromSeconds(1))`로 감싸고, `TimeoutException`을 잡은 뒤에도 원래 작업이 계속 실행되어 10초 뒤에 부작용(파일 쓰기나 콘솔 출력)을 남기는 것을 확인하라. 그다음 `CancellationTokenSource.CancelAfter`로 바꾸고 토큰을 작업 안쪽까지 전달해, 부작용이 실제로 발생하지 않는 것을 확인하라. 두 버전에서 잡히는 예외 타입이 어떻게 다른지도 기록하라.

5. **재시도 지터의 효과.** 실패 확률 50%인 가짜 서비스와 클라이언트 1,000개를 시뮬레이션하라. (a) 고정 간격 1초, (b) 지수 백오프(지터 없음), (c) 지수 백오프 + 완전 지터 세 정책에 대해 시간축 100 ms 버킷별 요청 수 히스토그램을 출력하고, (a)·(b)에서 나타나는 파도 모양이 (c)에서 사라지는 것을 확인하라. 서비스가 초당 200건만 견딘다고 할 때 각 정책의 전체 성공률도 비교하라.

6. **UI 갱신 스로틀링 비교.** WinForms나 WPF 앱에서 1,000만 회 루프를 `Task.Run`으로 돌리며 진행률을 보고하라. (a) 반복마다 `IProgress<int>.Report` 호출, (b) 퍼센트가 바뀔 때만 호출, (c) 용량 1 + `DropOldest` 채널 + `PeriodicTimer`(50 ms) 세 버전을 만들고, 각각에서 전체 소요 시간과 UI 반응성(작업 중 창을 드래그해 보라)을 비교하라. (a)에서 진행률 바가 오히려 끊기는 것을 확인하라.

7. **스레드 풀 기아 재현.** ASP.NET Core 최소 API에 `await Task.Delay(500)`을 하는 엔드포인트와 `Task.Delay(500).Wait()`를 하는 엔드포인트를 각각 만들어라. 동시 200 요청 부하를 걸고 `dotnet-counters monitor --counters System.Runtime`으로 `ThreadPool Thread Count`·`ThreadPool Queue Length`·`CPU Usage`를 관찰하라. 두 엔드포인트의 p99 응답 시간과 처리량을 비교하고, `ThreadPool.SetMinThreads`를 올렸을 때 증상이 어떻게 달라지는지(그리고 왜 근본 해결이 아닌지) 설명하라.
