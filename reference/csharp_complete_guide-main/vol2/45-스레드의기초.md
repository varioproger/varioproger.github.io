## 45.1 왜 OS는 스레드를 지원하는가

### 실행 흐름이 하나뿐이던 시절

컴퓨터 초창기의 운영체제에는 스레드라는 개념이 없었다. 시스템 전체를 관통하는 **실행 흐름이 하나**뿐이었고, 그 하나가 OS 코드와 애플리케이션 코드를 모두 실행했다.

문제는 명백하다. 오래 걸리는 작업 하나가 다른 모든 작업을 막는다. 16비트 Windows 시절에는 문서를 인쇄하는 애플리케이션이 머신 전체를 멈추게 하는 일이 흔했다. OS도, 다른 애플리케이션도 전부 응답을 멈췄다. 애플리케이션에 버그가 있어 무한 루프에 빠지면 역시 머신 전체가 멈췄다.

이때 사용자에게 남은 선택은 리셋 버튼이나 전원 스위치뿐이다. 실행 중이던 모든 애플리케이션이 종료되고, 더 중요하게는 그 애플리케이션들이 처리 중이던 **데이터가 메모리에서 통째로 사라진다**.

### 프로세스가 푼 문제와 풀지 못한 문제

Microsoft가 새 OS 커널(Windows NT에 처음 실린 그 커널)을 설계할 때 내린 결정이 **프로세스**다. 프로세스는 애플리케이션 인스턴스 하나가 쓰는 리소스의 묶음이다. 각 프로세스는 자기만의 **가상 주소 공간**을 받는다.

이것이 해결한 것은 다음과 같다.

| 문제 | 프로세스가 주는 해답 |
|---|---|
| 한 앱이 다른 앱의 데이터를 망가뜨린다 | 주소 공간이 분리되어 접근 자체가 불가능하다 |
| 앱이 OS 코드·데이터를 망가뜨린다 | 커널 코드와 데이터는 프로세스에서 접근할 수 없다 |
| 앱이 다른 앱의 비밀을 읽는다 | 사용자 이름·비밀번호·카드 번호가 프로세스 경계 밖으로 새지 않는다 |
| 앱이 무한 루프에 빠진다 | **해결되지 않는다** |

마지막 줄이 핵심이다. 머신에 CPU가 하나뿐이라면, 그 CPU는 무한 루프를 계속 실행할 뿐 다른 아무것도 실행하지 못한다. 데이터는 안전해졌지만 시스템은 여전히 사용자에게 응답하지 않는다.

### 스레드는 CPU의 가상화다

이 문제의 답이 **스레드**다. 스레드의 임무를 한 문장으로 줄이면 이렇다.

> **스레드는 CPU를 가상화한다.**

Windows는 각 프로세스에 자기만의 스레드(CPU처럼 동작하는 것)를 하나씩 준다. 애플리케이션 코드가 무한 루프에 빠지면 그 코드와 연결된 프로세스가 얼어붙을 뿐, 자기 스레드를 가진 다른 프로세스들은 계속 돌아간다.

이 구도를 완성하는 것이 **선점형 멀티태스킹(preemptive multitasking)** 이다. Windows는 시점마다 하나의 스레드를 CPU에 배정하고, 그 스레드가 **타임슬라이스(time-slice, 퀀텀quantum이라고도 한다)** 동안 실행되게 한다. 타임슬라이스가 끝나면 다른 스레드로 **컨텍스트 스위치(context switch)** 한다.

```text
     시간 →
CPU  ┌────────┬────────┬────────┬────────┬────────┐
코어0│ 스레드A│ 스레드B│ 스레드A│ 스레드C│ 스레드B│
     └────────┴────────┴────────┴────────┴────────┘
              ↑        ↑        ↑        ↑
           컨텍스트  컨텍스트  컨텍스트  컨텍스트
            스위치    스위치    스위치    스위치

각 스위치마다: 레지스터 저장 → 다음 스레드 선택 → 레지스터 복원
(스레드가 다른 프로세스 소유라면 주소 공간까지 전환)
```

"선점형"이란 스레드가 **아무 때나 멈춰질 수 있다**는 뜻이다. 스레드가 자발적으로 CPU를 내놓기를 기다리지 않는다. 이 덕분에 무한 루프에 빠진 스레드가 있어도 작업 관리자의 스레드가 CPU를 얻어 그 프로세스를 죽일 수 있다. 프로세스는 죽고 그 데이터는 사라지지만, 다른 프로세스들은 데이터를 잃지 않고 계속 돌아간다. 사용자는 리셋 버튼을 누르지 않아도 된다.

> **⚠️ 선점은 "언제든지"라는 뜻이다**
>
> 스레드가 다른 스레드의 코드 실행과 뒤섞이는 지점에서 그 스레드는 **선점되었다(preempted)** 고 말한다. 이 단어는 대개 "뭔가 잘못됐는데 왜 그런지" 설명할 때 등장한다.
>
> 선점은 문장 사이가 아니라 **기계어 명령 사이**에서 일어난다. `x++` 한 줄도 읽기·증가·쓰기 세 동작으로 나뉘고, 그 사이에서 선점될 수 있다. 이것이 45.5절에서 볼 공유 상태 문제의 뿌리다.

### 스레드를 쓰는 두 가지 이유

스레드를 쓸 이유는 사실 두 가지뿐이다.

| 이유 | 설명 | 코어가 하나라면 |
|---|---|---|
| **응답성(responsiveness)** | 시간이 오래 걸리는 작업을 별도 스레드로 밀어내 UI 스레드가 사용자 입력에 계속 반응하게 한다 | 여전히 유효하다. 전체 처리 시간은 오히려 늘지만 사용자 경험이 낫다 |
| **성능·확장성(performance, scalability)** | 여러 연산을 여러 코어에서 동시에 실행해 같은 일을 더 짧은 시간에 끝낸다 | **효과가 없다.** 코어가 여러 개일 때만 얻는 이득이다 |

응답성을 위해 스레드를 쓸 때는 머신의 코어 수보다 많은 스레드를 만들게 되고, 그만큼 시스템 리소스를 낭비하며 성능을 깎는다. 그럼에도 사용자는 반응하는 UI를 얻으므로 전체적으로는 더 나은 경험이다. 이 거래를 의식적으로 하고 있는지가 중요하다.

> **📌 흔한 동시성 시나리오**
>
> - **응답성 있는 UI** — WPF·모바일·Windows Forms에서 시간이 걸리는 작업을 UI 코드와 동시에 실행한다.
> - **요청 동시 처리** — 서버에서 클라이언트 요청이 동시에 도착하므로 병렬로 처리해야 확장된다. ASP.NET Core나 Web API를 쓰면 런타임이 알아서 해주지만, 공유 상태(예: 캐시용 정적 변수)는 여전히 직접 신경 써야 한다.
> - **병렬 프로그래밍** — 계산 집약적 코드를 코어 수만큼 쪼개 실행한다(50장).
> - **투기적 실행(speculative execution)** — 필요할지도 모르는 것을 미리 계산하거나, 같은 문제를 푸는 여러 알고리즘을 동시에 돌려 먼저 끝나는 쪽을 채택한다.

### I/O를 기다리는 동안 CPU는 놀지 않는다

컨텍스트 스위치는 타임슬라이스 만료로만 일어나지 않는다. 스레드는 **자발적으로 타임슬라이스를 조기 종료**할 수 있고, 실제로 이 일이 훨씬 자주 벌어진다.

메모장을 생각해 보자. 메모장의 스레드는 대개 할 일 없이 앉아 입력을 기다린다. 사용자가 `J` 키를 누르면 Windows가 메모장 스레드를 깨워 키 입력을 처리하게 한다. 처리에 5ms가 걸렸다고 하자. 그러면 메모장 스레드는 "다음 입력 이벤트를 처리할 준비가 됐다"고 Windows에 알리는 함수를 호출한다. 대기 중인 입력 이벤트가 더 없으면 Windows는 그 스레드를 **대기 상태**에 넣는다. 다음 입력이 올 때까지 이 스레드는 어떤 CPU에도 스케줄되지 않는다.

이것이 시스템 전체 성능을 끌어올린다. I/O 완료를 기다리는 스레드는 CPU 시간을 낭비하지 않고, 그 자리에 실행할 일이 있는 다른 스레드가 들어간다. "I/O 대기 중 CPU를 다른 일에 쓴다"는 것이 스레드가 주는 두 번째 선물이다.

### CPU 트렌드가 바꾼 그림

한때는 CPU 속도가 시간에 따라 올라갔다. 어떤 머신에서 느리게 돌던 애플리케이션이 새 머신에서는 그냥 빨라졌다. 그러나 CPU를 고속으로 돌리면 열이 나고, 그 열을 빼야 한다. 제조사는 클럭을 계속 올리는 대신 트랜지스터를 더 작게 만들어 한 칩에 더 많이 넣는 쪽으로 방향을 틀었다.

결과는 이렇다. **소프트웨어가 여러 코어를 쓰도록 작성되어야만 빨라진다.**

| 기술 | 구조 | OS가 보는 모습 |
|---|---|---|
| **다중 CPU** | 메인보드에 소켓이 여러 개, 소켓마다 CPU | 진짜로 동시에 실행되는 여러 CPU |
| **하이퍼스레딩** | 한 칩이 아키텍처 상태(레지스터 등) 집합을 두 벌 갖되 실행 자원은 한 벌 | CPU 두 개로 보인다. 실제로는 한 번에 하나만 실행하고, 캐시 미스·분기 예측 실패·데이터 의존으로 한쪽이 멈추면 다른 쪽으로 전환한다 |
| **멀티코어** | 한 칩 안에 CPU 코어 여러 개 | 코어 수만큼의 CPU. 오늘날의 기본형 |

Windows는 하이퍼스레딩을 인지하므로, 하이퍼스레딩 CPU가 여러 개 있으면 먼저 각 CPU에 스레드를 하나씩 배치해 진짜로 동시 실행되게 하고, 그다음에 이미 바쁜 CPU에 추가 스레드를 배치한다.

> **⚠️ Windows는 실시간 운영체제가 아니다**
>
> "네트워크에서 데이터가 도착한 뒤 1ms 안에 특정 스레드가 실행되도록 보장할 수 있는가"라는 질문의 답은 **없다**이다.
>
> 실시간 OS는 자신이 도는 하드웨어를 속속들이 알아야 한다 — 디스크 컨트롤러의 지연, 키보드의 지연 같은 것들. Windows의 목표는 온갖 다양한 하드웨어에서 도는 것이므로 실시간 OS로 설계되지 않았다. 여기에 CLR이 얹히면 실시간성은 더 멀어진다. DLL의 JIT 로딩, 코드의 JIT 컴파일, 예측할 수 없는 시점에 끼어드는 가비지 컬렉터가 전부 변수다.
>
> 실시간 보장이 필요한 문제를 스레드 우선순위 조정으로 풀려는 시도는 45.7절에서 다시 다룬다. 결론은 같다 — 그 방향은 틀렸다.

### 대가

스레드가 공짜였다면 이 장의 나머지는 필요 없다. 대가는 크게 셋이다.

1. **공간** — 스레드 하나가 커널 객체, TEB, 사용자 모드 스택, 커널 모드 스택을 소비한다(45.4절).
2. **시간** — 생성·소멸에 시간이 들고, 컨텍스트 스위치는 순수한 오버헤드다. 컨텍스트 스위치에서 얻는 메모리·성능 이득은 **없다**. 견고하고 응답성 있는 OS를 위해 성능을 지불하는 것이다.
3. **복잡도** — 공유 상태가 생기고, 실행 순서가 비결정적이 되며, 버그는 간헐적으로만 재현된다.

> **💡 스레드는 답이 아니라 도구다**
>
> 이 장의 나머지 전체를 관통하는 긴장이 하나 있다. **가능한 한 적은 수의 스레드를 만들면서, 코드를 응답성 있게 유지하고, 코어가 여러 개인 머신에서 확장되게 하라.** 46장 이후의 모든 메커니즘 — 스레드 풀, `Task`, `async`/`await` — 은 이 긴장을 다루기 위해 존재한다.

## 45.2 스레드 생성, `Join`, `Sleep`, 블로킹

### 문법 — 가장 단순한 형태

클라이언트 프로그램(콘솔, WPF, Windows Forms)은 OS가 자동으로 만들어 준 스레드 하나로 시작한다. 이것이 "주 스레드(main thread)"다. 직접 또는 간접적으로 스레드를 더 만들지 않는 한 프로그램은 단일 스레드로 살아간다.

`Thread` 객체를 만들고 `Start`를 호출하면 새 스레드가 시작된다. 가장 단순한 생성자는 매개변수 없는 메서드를 가리키는 `ThreadStart` 델리게이트를 받는다.

```csharp
using System;
using System.Threading;

Thread t = new Thread(WriteY);   // 새 스레드에서 WriteY()를 실행한다
t.Start();

// 동시에 주 스레드는 자기 일을 한다
for (int i = 0; i < 1000; i++) Console.Write("x");

void WriteY()
{
    for (int i = 0; i < 1000; i++) Console.Write("y");
}
```

출력은 실행할 때마다 다르다. 전형적으로는 `x`와 `y`가 불규칙한 덩어리로 번갈아 나온다.

```text
xxxxxxxxxxxxxxxxyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyy
xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxyyyyyyyyyyyyy
yyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyxxxxxxxxxxxxxxxxxxxxxx
```

코어가 하나인 컴퓨터라면 OS가 각 스레드에 시간 조각을 나눠 주며 동시성을 흉내 내므로 덩어리가 생긴다. 코어가 여러 개면 두 스레드가 진짜로 병렬 실행될 수 있지만, 이 예제에서는 `Console`이 동시 요청을 처리하는 방식 때문에 여전히 덩어리로 보인다.

### 스레드를 만드는 다섯 단계

`System.Threading`으로 스레드를 만드는 절차는 예측 가능한 다섯 단계다.

1. 새 스레드의 진입점이 될 메서드를 만든다.
2. `ThreadStart` 또는 `ParameterizedThreadStart` 델리게이트를 만들어 그 메서드를 가리킨다.
3. `Thread` 객체를 만들면서 델리게이트를 생성자 인자로 넘긴다.
4. 초기 특성(이름, 우선순위, 백그라운드 여부 등)을 설정한다.
5. `Thread.Start()`를 호출한다.

```csharp
public class Printer
{
    public void PrintNumbers()
    {
        Console.WriteLine("-> {0} is executing PrintNumbers()",
            Thread.CurrentThread.Name);

        Console.Write("Your numbers: ");
        for (int i = 0; i < 10; i++)
        {
            Console.Write("{0}, ", i);
            Thread.Sleep(2000);
        }
        Console.WriteLine();
    }
}
```

```csharp
Printer p = new Printer();

Thread backgroundThread = new Thread(new ThreadStart(p.PrintNumbers));
backgroundThread.Name = "Secondary";
backgroundThread.Start();

Console.WriteLine("This is on the main thread, and we are finished.");
Console.ReadLine();
```

단일 스레드로 `PrintNumbers()`를 직접 호출하면 마지막 메시지는 숫자가 전부 출력된 뒤에야 나온다. 각 숫자마다 2초씩 쉬므로 20초가 걸린다. 스레드를 쓰면 메시지가 즉시 나온다. 이것이 45.1절에서 말한 "응답성"의 가장 작은 시연이다.

### 컴파일 결과 — 생성자는 아무것도 만들지 않는다

`new Thread(p.PrintNumbers)`가 컴파일되면 메서드 그룹 변환으로 델리게이트 객체가 하나 만들어지고, 그것을 인자로 `Thread`의 생성자가 호출된다.

여기서 중요한 사실은 **`Thread` 객체를 만드는 것 자체는 상대적으로 가벼운 연산**이라는 점이다. 물리적인 운영체제 스레드는 그 시점에 만들어지지 않는다. 실제 OS 스레드를 만들고 콜백 메서드를 실행시키는 것은 **`Start`** 다. 45.4절에서 볼 모든 비용은 `Start` 호출에서 발생한다.

### 런타임 동작 — 스레드의 수명

시작된 뒤 스레드의 `IsAlive` 속성은 `true`를 반환하고, 스레드가 끝나는 시점에 `false`가 된다. 스레드는 생성자에 넘긴 델리게이트의 실행이 끝나면 종료된다. **한 번 끝난 스레드는 다시 시작할 수 없다.**

`Name` 속성은 디버깅용 이름이다. Visual Studio의 Threads 창과 Debug Location 툴바에 표시되므로 붙여 두면 진단이 훨씬 쉬워진다. 단, **이름은 한 번만 설정할 수 있고** 나중에 바꾸려 하면 예외가 난다.

```csharp
Thread primaryThread = Thread.CurrentThread;
primaryThread.Name = "ThePrimaryThread";

Console.WriteLine("ID of current thread: {0}", primaryThread.ManagedThreadId);
Console.WriteLine("Thread Name: {0}", primaryThread.Name);
Console.WriteLine("Has thread started?: {0}", primaryThread.IsAlive);
Console.WriteLine("Priority Level: {0}", primaryThread.Priority);
Console.WriteLine("Thread State: {0}", primaryThread.ThreadState);
```

```text
ID of current thread: 1
Thread Name: ThePrimaryThread
Has thread started?: True
Priority Level: Normal
Thread State: Running
```

### `Thread`의 주요 멤버

| 정적 멤버 | 역할 |
|---|---|
| `Thread.CurrentThread` | 현재 실행 중인 스레드를 나타내는 `Thread` 참조 |
| `Thread.Sleep(int)` / `Sleep(TimeSpan)` | 현재 스레드를 지정한 시간 동안 정지시킨다 |
| `Thread.Yield()` | 현재 프로세서에서 실행 준비된 다른 스레드에 타임슬라이스를 양보한다 |
| `Thread.SpinWait(int)` | 지정한 횟수만큼 스핀한다(블로킹하지 않는다). 48.12절 |
| `Thread.GetDomain()` | 현재 스레드를 호스팅하는 `AppDomain` |

| 인스턴스 멤버 | 역할 |
|---|---|
| `IsAlive` | 시작되었고 아직 끝나지 않았으면 `true` |
| `IsBackground` | 백그라운드 스레드 여부. 45.7절 |
| `IsThreadPoolThread` | 스레드 풀 스레드에서 실행 중인지. 46.1절 |
| `Name` | 진단용 이름. 한 번만 설정 가능 |
| `ManagedThreadId` | CLR이 부여한 스레드 식별자. 45.3절 |
| `Priority` | `ThreadPriority` 값. 45.7절 |
| `ThreadState` | `ThreadState` 플래그 열거형 |
| `Start()` / `Start(object)` | 스레드를 시작한다 |
| `Join()` / `Join(int)` / `Join(TimeSpan)` | 이 스레드가 끝날 때까지 호출 스레드를 블로킹한다 |
| `Interrupt()` | 대기 상태의 스레드를 깨워 `ThreadInterruptedException`을 던지게 한다 |

> **⚠️ `Abort`·`Suspend`·`Resume`은 쓰지 마라**
>
> `Thread.Abort`는 대상 스레드가 어떤 상태에 있든 강제로 끝내려 든다. 정적 생성자 실행 중이거나 잠금을 쥔 상태에서 중단되면 남는 것은 복구 불가능한 손상이다. 이 API는 오랫동안 애플리케이션 크래시의 주요 원인이었다.
>
> .NET 5 이상을 대상으로 하는 프로젝트에서 `Thread.Abort` 계열 API를 호출하면 **`SYSLIB0006` 컴파일 경고**가 뜬다. 이 API는 폐기되었고, Microsoft의 권고는 `CancellationToken`을 이용한 **협력적 취소**다(46.8절).
>
> `Suspend`/`Resume` 역시 같은 이유로 폐기 대상이다. 다른 스레드를 임의 지점에서 멈추는 API는 그 스레드가 무엇을 쥐고 있는지 알 수 없기 때문에 근본적으로 안전할 수 없다. "활성 스레드를 중단하거나 일시 중지하는 것은 일반적으로 나쁜 생각"이라는 것이 원천의 표현이다.

### `Join` — 다른 스레드를 기다리기

`Join`은 호출한 스레드를, 대상 스레드가 종료될 때까지 블로킹한다.

```csharp
Thread t = new Thread(Go);
t.Start();
t.Join();
Console.WriteLine("Thread t has ended!");

void Go() { for (int i = 0; i < 1000; i++) Console.Write("y"); }
```

`y`가 1,000번 출력된 직후에 `Thread t has ended!`가 나온다.

`Join`에는 타임아웃 오버로드가 있다.

| 오버로드 | 반환값 | 의미 |
|---|---|---|
| `Join()` | `void` | 스레드가 끝날 때까지 무한정 기다린다 |
| `Join(int millisecondsTimeout)` | `bool` | 시간 안에 끝났으면 `true`, 타임아웃이면 `false` |
| `Join(TimeSpan timeout)` | `bool` | 위와 같되 `TimeSpan`으로 지정 |

타임아웃 오버로드가 `bool`을 반환한다는 점이 중요하다. 이 반환값을 무시하면 "기다렸는데 안 끝났다"와 "기다렸더니 끝났다"를 구분하지 못한다.

```csharp
if (!worker.Join(TimeSpan.FromSeconds(5)))
{
    // 5초 안에 끝나지 않았다. 로그를 남기고 포기하거나 다른 조치를 취한다.
    // 여기서 Abort를 부르고 싶은 유혹이 생기지만 그러면 안 된다.
    logger.LogWarning("worker 스레드가 제시간에 종료되지 않았다");
}
```

### `Sleep`, `Sleep(0)`, `Yield`

`Thread.Sleep`은 현재 스레드를 지정한 시간 동안 정지시킨다.

```csharp
Thread.Sleep(TimeSpan.FromHours(1));   // 1시간
Thread.Sleep(500);                     // 500밀리초
```

인자가 `0`일 때가 특별하다. **`Thread.Sleep(0)`은 현재 타임슬라이스를 즉시 반납하고, 자발적으로 CPU를 다른 스레드에 넘긴다.** `Thread.Yield()`도 같은 일을 하되, **같은 프로세서에서 돌고 있는 스레드에게만** 양보한다.

| 호출 | 스레드가 대기 상태로 들어가는가 | 양보 대상 | 특징 |
|---|---|---|---|
| `Thread.Sleep(0)` | 아니다 — 실행 준비 상태로 남는다 | 스케줄러가 고를 수 있는 다른 스레드 | 양보할 대상이 없으면 즉시 돌아온다 |
| `Thread.Yield()` | 아니다 — 실행 준비 상태로 남는다 | **같은 프로세서**에서 실행 준비된 스레드 | 양보에 성공하면 `true` 반환 |
| `Thread.Sleep(1)` | 그렇다 — 타이머 만료까지 대기 상태 | 제약 없음 | 실제 정지 시간은 시스템 타이머 해상도에 좌우되므로 1ms보다 길어질 수 있다 |
| `Thread.Sleep(n)` (n>1) | 그렇다 | 제약 없음 | 명시적 블로킹 |

`Sleep(0)`과 `Yield()`는 스레드를 대기 상태로 보내지 않고 즉시 다시 스케줄 대상이 된다. 반면 `Sleep(1)` 이상은 스레드를 진짜로 **블로킹**시켜 타이머가 만료될 때까지 CPU 배정 후보에서 빠진다. 스핀 루프 안에서 `Sleep(0)`만 반복하면 양보 대상이 없을 때 사실상 바쁜 대기가 되어 버리지만, `Sleep(1)`은 어떤 경우에도 다른 스레드에 실행 기회를 준다. 다만 정확한 스케줄링 규칙은 OS와 버전에 따라 달라지므로, 이 차이를 **정확한 동작 보장으로 삼는 코드는 쓰지 마라**.

> **📌 `Yield`는 훌륭한 진단 도구다**
>
> `Sleep(0)`이나 `Yield`는 고급 성능 튜닝에 가끔 쓰이지만, 그보다 훨씬 자주 쓸모 있는 용도가 진단이다.
>
> **코드 어딘가에 `Thread.Yield()`를 끼워 넣었을 때 프로그램이 깨진다면, 거의 확실하게 스레드 안전성 버그가 있는 것이다.** 원래 드물게 일어나던 인터리빙을 강제로 자주 일어나게 만드는 것이므로, 잠복한 경쟁 조건을 표면으로 끌어올린다.

### 블로킹의 정의

이 장에서 가장 정확히 정의해 둬야 할 단어가 **블로킹(blocking)** 이다.

> **스레드가 어떤 이유로 실행이 멈춘 상태를 블로킹되었다고 한다. 블로킹된 스레드는 즉시 자기 프로세서 타임슬라이스를 반납하고, 그 이후 블로킹 조건이 만족될 때까지 프로세서 시간을 전혀 소비하지 않는다.**

`Sleep(n)`, `Join()`, 잠금 대기, `WaitOne()`, `Console.ReadLine()`이 모두 블로킹이다. 핵심은 "멈춰 있다"가 아니라 **"CPU를 쓰지 않는다"** 이다. 이것이 스핀 대기와의 결정적 차이다.

스레드가 블로킹되었는지는 `ThreadState`로 검사할 수 있다.

```csharp
bool blocked = (someThread.ThreadState & ThreadState.WaitSleepJoin) != 0;
```

`ThreadState`는 세 "계층"의 정보를 비트로 합쳐 놓은 플래그 열거형이다. 대부분의 값은 중복이거나 사용되지 않거나 폐기되었다. 실제로 쓸모 있는 값은 네 개뿐이며, 다음 확장 메서드로 걸러낼 수 있다.

```csharp
public static ThreadState Simplify(this ThreadState ts)
{
    return ts & (ThreadState.Unstarted |
                 ThreadState.WaitSleepJoin |
                 ThreadState.Stopped);
}
```

이렇게 하면 `Unstarted`, `Running`, `WaitSleepJoin`, `Stopped` 네 가지만 남는다.

### 스레드의 생명주기

네 가지 상태를 흐름으로 그리면 이렇다.

```text
      new Thread(...)
            │
            ▼
      ┌───────────┐
      │ Unstarted │
      └─────┬─────┘
            │ Start()
            ▼
      ┌───────────┐   Sleep(n) / Join() / WaitOne() / lock 대기
      │  Running  │────────────────────────────┐
      └─────┬─────┘                            ▼
            │                          ┌────────────────┐
            │◀─────────────────────────│ WaitSleepJoin  │
            │  시간 만료 / 신호 /       └────────────────┘
            │  Interrupt()                     │
            │                                  │ Interrupt()
            │ 델리게이트 반환                   │ → ThreadInterruptedException
            ▼                                  │
      ┌───────────┐                            │
      │  Stopped  │◀───────────────────────────┘
      └───────────┘
       (재시작 불가)
```

`ThreadState`가 실제로 노출하는 값 중 알아 둘 만한 것들이다.

| 값 | 의미 | 비고 |
|---|---|---|
| `Unstarted` | `Thread` 객체는 있으나 `Start`가 호출되지 않았다 | OS 스레드가 아직 없다 |
| `Running` | 실행 중이거나 실행 준비 상태다 | 플래그가 하나도 없을 때의 상태 |
| `WaitSleepJoin` | `Sleep`·`Join`·잠금·대기 핸들로 블로킹되어 있다 | 이 장이 말하는 "블로킹" |
| `Background` | 백그라운드 스레드다 | 다른 값과 함께 켜진다. 45.7절 |
| `Stopped` | 종료되었다 | 다시 시작할 수 없다 |

나머지 값들(`SuspendRequested`, `Suspended`, `AbortRequested`, `Aborted`, `StopRequested`)은 폐기된 API와 짝을 이루므로 현대 .NET 코드에서는 볼 일이 없다.

> **⚠️ `ThreadState`는 진단용이지 동기화용이 아니다**
>
> `ThreadState`를 읽고 그 값에 근거해 행동하는 코드는 틀렸다. 값을 읽은 시점과 행동하는 시점 사이에 스레드 상태가 바뀔 수 있기 때문이다. 로그에 찍는 용도로만 써라. 동기화가 필요하면 48장과 49장의 구성 요소를 써야 한다.

### 블로킹 vs 스피닝

I/O 바운드 연산은 두 가지 방식 중 하나로 동작한다. 현재 스레드에서 완료될 때까지 **동기적으로 기다리거나**(`Console.ReadLine`, `Thread.Sleep`, `Thread.Join`), 완료 시 콜백을 부르는 **비동기 방식**으로 동작한다(47장).

동기적으로 기다리는 쪽은 대부분의 시간을 스레드를 블로킹하며 보낸다. 그런데 블로킹 대신 루프를 도는 방식도 있다.

```csharp
// 주기적으로 깨어나며 도는 방식 — 절반은 블로킹
while (DateTime.Now < nextStartTime)
    Thread.Sleep(100);
```

```csharp
// 계속 도는 방식 — 순수한 스핀
while (DateTime.Now < nextStartTime) ;
```

두 번째 방식은 프로세서 시간에 대해 대단히 낭비적이다. CLR과 OS 입장에서 이 스레드는 중요한 계산을 하고 있는 것이고, 그에 맞게 리소스를 배정받는다. **I/O 바운드여야 할 연산을 컴퓨트 바운드로 바꿔 버린 것이다.**

| 구분 | 블로킹 | 스핀 대기 |
|---|---|---|
| CPU 소비 | 0 | 100%(한 코어) |
| 컨텍스트 스위치 | 블록·언블록 시 각 1회 | 없음 |
| 지연 시간 | 컨텍스트 스위치 왕복만큼 | 최소 |
| 적합한 상황 | 대기가 길거나 길이를 모를 때 | 조건이 수 마이크로초 안에 만족될 것이 확실할 때 |

아주 짧게 스핀하는 것은 조건이 곧(수 마이크로초 안에) 만족될 것으로 기대될 때 효과적이다. 컨텍스트 스위치의 오버헤드와 지연을 피하기 때문이다. .NET은 이를 돕는 전용 타입을 제공하며, 상세는 48.12절에서 다룬다.

반대 방향의 진실도 있다. **블로킹도 비용이 0은 아니다.** 스레드는 살아 있는 동안 대략 1MB의 메모리를 붙들고 있고, CLR과 OS에 지속적인 관리 오버헤드를 지운다. 그래서 수백~수천 개의 동시 연산을 처리해야 하는 I/O 집약 프로그램에서 블로킹은 골칫거리가 된다. 그런 프로그램은 기다리는 동안 스레드를 아예 반납하는 콜백 기반 접근이 필요하고, 그것이 47장에서 다룰 비동기 패턴의 존재 이유다.

> **⚠️ 블록·언블록에도 컨텍스트 스위치가 든다**
>
> 스레드가 블로킹되거나 블로킹에서 풀릴 때 OS는 컨텍스트 스위치를 수행한다. 이 오버헤드는 작지만 0이 아니며, 원천은 **일반적으로 1~2마이크로초**로 기술한다.
>
> 1~2마이크로초는 대기 시간이 밀리초 단위라면 무시할 만하지만, 마이크로초 단위 작업을 백만 번 반복하는 루프 안에서는 지배적인 비용이 된다. "블로킹은 공짜"라는 직관이 깨지는 지점이 여기다.

### `Interrupt` — 대기 중인 스레드 깨우기

`Interrupt`는 `WaitSleepJoin` 상태(대기·수면·조인)에 있는 스레드를 깨우고, 그 스레드에서 `ThreadInterruptedException`을 던지게 한다.

```csharp
Thread worker = new Thread(() =>
{
    try
    {
        Thread.Sleep(Timeout.Infinite);
    }
    catch (ThreadInterruptedException)
    {
        Console.WriteLine("깨워졌다");
    }
});
worker.Start();
Thread.Sleep(100);
worker.Interrupt();
```

블로킹 상태가 아닌 스레드에 `Interrupt`를 호출하면 예외가 즉시 발생하지는 않는다. 그 스레드가 다음번에 블로킹될 때 던져진다. 이 "나중에 터진다" 성질 때문에 `Interrupt`는 실무에서 쓰기 까다롭고, 협력적 취소(46.8절)로 대체하는 것이 옳다.

## 45.3 CLR 스레드와 OS 스레드의 관계

### 논리 스레드와 물리 스레드

CLR은 오늘날 Windows의 스레딩 기능을 그대로 쓴다. 즉 "관리 코드로 노출된 스레드"는 실제로는 OS 스레드다. 그러나 이것이 **명세로 보장된 사실은 아니다**.

.NET Framework 초기에 CLR 팀은 언젠가 CLR이 **논리 스레드(logical thread)** 를 제공하고, 그것이 OS 스레드에 반드시 1:1로 대응하지 않게 만들려는 구상을 가지고 있었다. 2005년 무렵 이를 시도했으나 성공하지 못했고, 팀은 아이디어를 포기했다. 그래서 **오늘날 CLR 스레드는 OS 스레드와 동일하다.**

이 시도의 흔적이 API에 남아 있다.

| 흔적 | 위치 | 무엇을 나타내는가 |
|---|---|---|
| `Environment.CurrentManagedThreadId` | `System.Environment` | CLR이 스레드에 부여한 ID(논리 스레드 쪽) |
| `Thread.ManagedThreadId` | `System.Threading.Thread` | 위와 같은 값 |
| `ProcessThread.Id` | `System.Diagnostics` | 같은 스레드에 대한 **Windows의** ID(물리 스레드 쪽) |
| `Thread.BeginThreadAffinity` / `EndThreadAffinity` | `System.Threading.Thread` | "이 구간에서는 논리 스레드가 물리 스레드에 고정되어야 한다"고 호스트에 알린다 |

`BeginThreadAffinity`/`EndThreadAffinity`가 존재한다는 사실 자체가 **논리 스레드와 물리 스레드가 개념적으로 분리되어 있다**는 증거다. 실제 구현이 1:1이라 해도, 그 1:1은 CLR이 약속한 것이 아니라 현재 구현의 사실일 뿐이다.

```text
┌───────────────────────────────────────────────────────────┐
│  관리 세계                                                │
│    System.Threading.Thread 객체                           │
│    ManagedThreadId = 3                                    │
│    Name = "Worker"                                        │
│    [ThreadStatic] 필드들, CurrentCulture, ExecutionContext │
└──────────────────────────┬────────────────────────────────┘
                           │ 현재 구현에서는 1:1
                           │ (CLR이 보장하지는 않는다)
┌──────────────────────────┴────────────────────────────────┐
│  OS 세계                                                  │
│    커널 스레드 객체 (컨텍스트 = CPU 레지스터 사본)        │
│    OS 스레드 ID = 21748  ← ProcessThread.Id               │
│    TEB, 사용자 모드 스택, 커널 모드 스택                  │
└──────────────────────────┬────────────────────────────────┘
                           │ 스케줄러가 배정
┌──────────────────────────┴────────────────────────────────┐
│  하드웨어                                                 │
│    CPU 코어 (타임슬라이스마다 하나의 스레드)              │
└───────────────────────────────────────────────────────────┘
```

> **⚠️ 관리 스레드 ID는 OS 스레드 ID가 아니다**
>
> WinDbg, `dotnet-dump`, ETW 트레이스, 네이티브 프로파일러는 OS 스레드 ID로 말한다. `Thread.ManagedThreadId`는 그와 완전히 다른 번호 체계다. 로그에 `ManagedThreadId`만 남겨 두고 네이티브 도구의 출력과 맞춰 보려 하면 아무것도 맞지 않는다.
>
> 두 세계를 오가는 진단을 할 계획이라면 **양쪽 ID를 모두 로그에 남겨라.** WinDbg의 SOS 확장에서 `!threads`를 실행하면 두 ID를 나란히 보여준다.

> **⚠️ 관리 스레드 ID를 영구 키로 쓰지 마라**
>
> `ManagedThreadId`는 **현재 살아 있는 스레드들 사이에서** 고유하다. 스레드가 종료된 뒤 같은 값이 다시 나타나지 않는다는 보장은 없다.
>
> 스레드별 통계를 `Dictionary<int, Stats>`에 `ManagedThreadId`로 모으는 코드는, 스레드가 계속 생겼다 죽는 환경에서 서로 다른 스레드의 통계를 한 항목에 섞어 버릴 수 있다. 스레드에 붙는 상태가 필요하면 그 목적에 맞는 도구인 `[ThreadStatic]`이나 `ThreadLocal<T>`를 써라(45.5절, 49.8절).

### 두 세계의 뷰 — `Thread` vs `ProcessThread`

`System.Diagnostics` 네임스페이스에는 `Process`와 `ProcessThread` 클래스가 있다. 이들은 프로세스와 스레드에 대한 **Windows의 관점**을 제공한다. 진단·유틸리티 작성용으로 만들어졌기 때문에 `System.Diagnostics`에 있는 것이고, 사용하려면 특별한 보안 권한이 필요할 수 있다.

반면 `AppDomain`과 `Thread` 클래스는 **CLR의 관점**을 제공한다. 대부분의 경우 특별한 권한 없이 쓸 수 있다.

```csharp
using System.Diagnostics;
using System.Threading;

// CLR의 관점
Console.WriteLine($"Managed thread id : {Environment.CurrentManagedThreadId}");
Console.WriteLine($"Thread name       : {Thread.CurrentThread.Name}");
Console.WriteLine($"IsBackground      : {Thread.CurrentThread.IsBackground}");
Console.WriteLine($"IsThreadPoolThread: {Thread.CurrentThread.IsThreadPoolThread}");

// OS의 관점 (권한과 플랫폼 지원이 필요하다)
using Process me = Process.GetCurrentProcess();
Console.WriteLine($"OS thread count   : {me.Threads.Count}");
foreach (ProcessThread pt in me.Threads)
    Console.WriteLine($"  OS thread {pt.Id}");
```

> **📌 `me.Threads.Count`가 예상보다 훨씬 큰 이유**
>
> 위 코드를 아무것도 하지 않는 콘솔 앱에서 돌려 보면 스레드가 여러 개 나온다. 주 스레드 외에 CLR 자신이 만든 스레드들이 있기 때문이다 — 파이널라이저 스레드(34.2절), 백그라운드 GC 스레드(65장), 디버거 도우미, 타이머 스레드 등.
>
> 즉 프로세스 안의 스레드 수는 애플리케이션 코드가 만든 스레드 수보다 항상 많다. "내 앱은 스레드를 하나도 안 만든다"는 말은 프로세스에 스레드가 하나뿐이라는 뜻이 아니다.

### 스레드 어피니티 — 스레드에 묶이는 상태

CLR 스레드와 OS 스레드가 개념적으로 분리되어 있다는 사실이 실무에서 중요해지는 지점이 **스레드 어피니티(thread affinity)** 다. 어떤 상태는 특정 스레드에 붙어 있어서 다른 스레드에서 건드리면 깨진다.

| 어피니티를 가진 것 | 왜 | 어디서 다루는가 |
|---|---|---|
| UI 컨트롤 | 만든 스레드에서만 접근 가능하다 | 45.8절 |
| `[ThreadStatic]` 필드, `ThreadLocal<T>` | 값이 스레드마다 별개로 저장된다 | 45.5절, 49.8절 |
| COM STA 객체 | 아파트먼트 모델이 호출 스레드를 강제한다 | 45.9절, 60.12절 |
| `Mutex`, `Monitor` 소유권 | 획득한 스레드만 해제할 수 있다 | 48.5절, 48.10절 |
| `Thread.CurrentCulture` | 스레드별 설정이다 | 38장 |

스레드에 붙는 또 하나의 것이 **실행 컨텍스트(`ExecutionContext`)** 다. 보안·호출·동기화·지역화·트랜잭션 컨텍스트 같은, "논리적 실행 흐름"에 관련된 정보를 담는다. 스레드는 언제든 실행 컨텍스트 안으로 옮겨질 수 있고, 런타임이 그 이동을 관장한다.

```csharp
ExecutionContext ctx = Thread.CurrentThread.ExecutionContext;
```

.NET 개발자는 대개 주어진 스레드가 어느 컨텍스트에 있는지 모른 채로 지내도 된다. 그러나 스레드 풀과 비동기 함수가 이 컨텍스트를 **캡처해서 흐르게 한다**는 사실은 알아 둘 필요가 있다. 그 흐름의 규칙은 46.7절에서 다룬다.

`async`/`await`가 도입되면서 이 문제는 새로운 형태를 얻는다. `await` 앞뒤의 코드가 서로 다른 스레드에서 실행될 수 있기 때문이다. 그 사정은 47.12절에서, 비동기 흐름을 따라가는 상태인 `AsyncLocal<T>`는 49.9절에서 다룬다.

## 45.4 스레드 생성 비용 — 커널 객체, 스택 예약, 컨텍스트 스위치

스레드가 왜 비싼지 구성 요소별로 분해한다. 이 절의 수치는 원천이 제시한 값이며, 하드웨어와 OS 버전에 따라 달라진다.

### 스레드 하나가 소비하는 것

모든 스레드는 다음 각각을 **하나씩** 갖는다.

#### 1. 스레드 커널 객체(thread kernel object)

OS는 시스템에서 만들어지는 스레드마다 이 자료 구조를 하나씩 할당하고 초기화한다. 여기에는 스레드를 서술하는 여러 속성이 들어가고, 무엇보다 **스레드의 컨텍스트(context)** 가 들어간다. 컨텍스트는 CPU 레지스터 한 벌을 담는 메모리 블록이다.

| CPU 아키텍처 | 컨텍스트 크기(대략) |
|---|---|
| x86 | 약 700바이트 |
| x64 | 약 1,240바이트 |
| ARM | 약 350바이트 |

#### 2. 스레드 환경 블록(TEB, thread environment block)

TEB는 **사용자 모드**에 할당·초기화되는 메모리 블록이다. 애플리케이션 코드가 빠르게 접근할 수 있는 주소 공간에 있다. TEB는 메모리 **1 페이지**를 소비한다(x86·x64·ARM에서 4KB).

TEB가 담는 것은 다음과 같다.

- 스레드의 **예외 처리 체인의 머리**. 스레드가 `try` 블록에 들어갈 때마다 이 체인의 머리에 노드가 삽입되고, `try` 블록을 벗어나면 제거된다.
- 스레드의 **스레드 로컬 저장소(TLS)** 데이터.
- GDI와 OpenGL 그래픽스가 쓰는 자료 구조.

#### 3. 사용자 모드 스택(user-mode stack)

지역 변수와 메서드에 전달되는 인자가 여기에 놓인다. 현재 메서드가 반환할 때 스레드가 다음에 무엇을 실행해야 하는지 나타내는 **반환 주소**도 여기 들어간다.

핵심은 예약과 커밋의 구분이다. Windows는 기본적으로 각 스레드의 사용자 모드 스택에 1MB의 메모리를 할당한다. 더 정확히 말하면 **1MB의 주소 공간을 예약(reserve)하고, 스레드가 스택을 키워 나가며 실제로 필요로 할 때 물리 저장소를 성기게 커밋(commit)한다.**

이 구분이 실무에서 중요하다. 스레드 1,000개를 만든다고 곧바로 1GB의 물리 메모리를 쓰는 것이 아니다. 그러나 **주소 공간은 즉시 소진된다**.

| 관점 | 스레드 100개가 소비하는 것 |
|---|---|
| 예약된 주소 공간 | 약 100MB (32비트 프로세스에서는 심각하다) |
| 커밋된 물리 메모리 | 각 스레드가 실제로 밟은 페이지 분량만 |

#### 4. 커널 모드 스택(kernel-mode stack)

애플리케이션 코드가 커널 모드 함수에 인자를 넘길 때 쓴다. 보안상의 이유로 Windows는 사용자 모드에서 커널로 넘어가는 인자를 스레드의 사용자 모드 스택에서 **커널 모드 스택으로 복사**한다. 복사한 뒤에야 커널이 인자 값을 검증할 수 있고, 애플리케이션 코드는 커널 모드 스택에 접근할 수 없으므로 검증 후에 값을 바꿔치기할 수 없다.

| Windows | 커널 모드 스택 크기 |
|---|---|
| 32비트 | 12KB |
| 64비트 | 24KB |

#### 5. DLL 스레드 연결·해제 통지

Windows에는 정책이 하나 있다. **프로세스 안에서 스레드가 만들어질 때마다, 그 프로세스에 로드된 모든 비관리 DLL의 `DllMain` 메서드가 `DLL_THREAD_ATTACH` 플래그와 함께 호출된다.** 스레드가 죽을 때는 `DLL_THREAD_DETACH` 플래그로 다시 호출된다.

일부 DLL은 이 통지를 필요로 한다. 예를 들어 C 런타임 라이브러리 DLL은 스레드가 그 라이브러리의 함수를 쓸 경우에 대비해 스레드 로컬 저장소 상태를 할당한다.

Windows 초창기에는 프로세스에 로드된 DLL이 대여섯 개였다. 오늘날은 수백 개가 로드되는 프로세스도 흔하다. 원천의 저자는 자기 머신의 Visual Studio 프로세스 주소 공간에 **약 470개의 DLL**이 로드되어 있다고 기록한다. 즉 Visual Studio에서 새 스레드가 만들어질 때마다 그 스레드가 자기 일을 시작하기 전에 **470개의 DLL 함수가 호출되어야 한다**. 스레드가 죽을 때 다시 470번. 이것은 프로세스 안에서 스레드를 만들고 없애는 성능에 심각하게 영향을 준다.

> **📌 관리 DLL은 이 비용을 내지 않는다**
>
> C#을 비롯한 대부분의 관리 언어가 만드는 DLL에는 `DllMain`이 아예 없다. 따라서 **관리 DLL은 `DLL_THREAD_ATTACH`·`DLL_THREAD_DETACH` 통지를 받지 않고**, 그만큼 성능이 낫다.
>
> 비관리 DLL도 Win32의 `DisableThreadLibraryCalls` 함수를 호출해 이 통지를 거부할 수 있다. 다만 많은 비관리 개발자가 이 함수의 존재를 모른다.
>
> 이 통지는 **Windows 고유의 메커니즘**이다. Linux·macOS에는 해당하지 않는다.

#### 6. CLR 쪽 비용

여기까지가 OS 비용이다. CLR은 그 위에 자기 몫을 얹는다.

- **관리 `Thread` 객체** — 관리 힙에 할당된다.
- **GC 루트 등록** — 스레드의 스택과 레지스터는 GC 루트의 원천이다(64.3절). 스레드가 하나 늘면 GC가 마킹 단계에서 스캔해야 할 스택이 하나 늘어난다.
- **스레드 로컬 저장소 구조** — CLR은 스레드별로 자기 내부 정보를 담는 구조를 유지하고, 스레드 정적 필드를 위한 별도의 자료 구조를 관리한다(49.8절).

### 비용 요약표

| 항목 | 크기 / 성격 | 어디에 |
|---|---|---|
| 스레드 커널 객체 + 컨텍스트 | x86 약 700B, x64 약 1,240B, ARM 약 350B | 커널 |
| TEB | 1 페이지(4KB) | 사용자 모드 |
| 사용자 모드 스택 | 기본 1MB **예약**, 점진 커밋 | 사용자 모드 |
| 커널 모드 스택 | 32비트 12KB, 64비트 24KB | 커널 |
| DLL 통지 | 로드된 비관리 DLL 수에 비례한 함수 호출 | 프로세스(Windows 전용) |
| 관리 `Thread` 객체 | 관리 힙 할당 | 관리 힙 |
| GC 루트 등록 | 마킹 시 스캔 대상 스택 하나 추가 | CLR |

└────────────────┘         │  │ 커밋된 부분   │ ← 실제로 │

### 기본 스택 크기 — 숫자가 갈리는 이유

스택의 예약 크기는 어디서 오는가. **실행 파일 헤더**에서 온다. Windows에서 초기 스레드 스택 크기(예약 크기와 초기 커밋 크기 모두)는 EXE 파일 헤더에서 읽어 오고, 수동으로 만든 스레드는 스레드 생성 시 별도로 지정할 수 있다.

원천마다 보고하는 기본값이 조금씩 다르다.

| 원천이 말하는 기본값 | 값 |
|---|---|
| Windows가 스레드에 할당하는 사용자 모드 스택 | 1MB 예약, 점진 커밋 |
| .NET 런타임이 계산하는 기본값(전형적 32비트 컴파일 / 64비트 컴파일) | 1MB / 4MB |
| Windows(ARM64·x86·x64) 기본 스택 크기 | 1MB |
| 전형적인 최신 Linux 기반 OS | 8MB (`ulimit -a`로 확인 가능) |

.NET 런타임이 기본 스택 크기를 계산하는 방식은 꽤 복잡하다. 요점은 **이 값이 고정 상수가 아니라 빌드 산출물과 OS에 따라 달라진다**는 것이고, 정확한 값이 필요하면 대상 환경에서 직접 확인해야 한다는 것이다.

스택 데이터는 대체로 작고 호출 스택도 대개 얕다(중첩 호출 수백 단계는 흔치 않다). 그래서 1MB나 4MB가 괜찮은 기본값이다. `StackOverflowException`을 만났다면 이 장벽에 부딪힌 것이고, 십중팔구 무한 재귀 같은 프로그래밍 오류다.

### 스택 크기를 바꾸는 방법과 바꾸지 말아야 할 이유

`Thread` 클래스에는 최대 스택 크기를 받는 생성자 오버로드가 있다.

```csharp
// 스택을 크게 잡아야 하는 특수한 경우 — 깊은 재귀를 도는 파서 등
Thread deepThread = new Thread(ParseDeeply, maxStackSize: 16 * 1024 * 1024);
deepThread.Start();
```

프로세스 전체의 기본 스택 크기는 Visual Studio와 함께 배포되는 `editbin.exe`로 실행 파일 헤더를 편집해 바꿀 수 있다.

```bash
editbin DotNet.HelloWorld.exe /stack:8000000
```

이 방법은 .NET 실행 파일에 대해 동작하지만 **지원되지 않는 접근**으로 봐야 한다. 앞으로도 .NET이 스레드를 만들 때 이 값을 반영하리라는 보장이 없다.

> **⚠️ 스택을 키우는 것은 `StackOverflowException`의 해법이 아니다**
>
> `StackOverflowException`은 .NET에서 **잡을 수 없고**, 발생 즉시 프로세스가 종료된다. 이 예외가 났다면 원인은 거의 항상 무한 재귀이거나, 재귀 깊이가 입력 데이터에 좌우되는 설계다.
>
> 스택 크기를 늘리면 증상이 나타나는 입력 크기가 커질 뿐 문제는 그대로 있다. 게다가 늘어난 예약 크기는 **모든 스레드에** 적용되므로 주소 공간 소비가 비례해서 커진다. 올바른 대응은 재귀를 반복으로 바꾸거나 깊이 상한을 두는 것이다. 스택 자체의 구조는 61.1절, 스택 할당은 63.7절에서 다룬다.

### 스레드 개수의 물리적 한계

주소 공간이 유한하므로 스레드 개수에도 한계가 있다. 32비트 프로세스는 최대 2GB의 사용 가능한 주소 공간을 갖는다. 여러 Win32 DLL이 로드되고, CLR DLL이 로드되고, 네이티브 힙과 관리 힙이 할당되고 나면 약 1.5GB가 남는다. 스레드 하나가 사용자 모드 스택과 TEB로 1MB보다 조금 더 쓰므로, **32비트 프로세스에서 얻을 수 있는 스레드 수는 대략 1,360개**다. 그보다 많이 만들려 하면 `OutOfMemoryException`이 던져진다.

64비트 프로세스는 훨씬 넓은 주소 공간을 가지므로 이론상 수십만 개의 스레드를 만들 수 있다. 그러나 그 근처의 숫자를 할당하는 것은 리소스 낭비일 뿐이다. 특히 **이상적인 스레드 수는 머신의 CPU 수와 같다**는 점을 생각하면 더 그렇다.

### 컨텍스트 스위치의 비용

CPU가 하나뿐인 컴퓨터는 한 번에 한 가지만 할 수 있다. 그래서 Windows는 실제 CPU 하드웨어를 시스템 안의 모든 스레드(논리 CPU들) 사이에서 공유해야 한다.

컨텍스트 스위치마다 Windows는 다음을 수행한다.

1. CPU 레지스터의 값들을 현재 실행 중인 스레드의 커널 객체 안 컨텍스트 구조에 **저장**한다.
2. 기존 스레드 집합에서 다음에 스케줄할 스레드 **하나를 선택**한다. 그 스레드가 다른 프로세스 소유라면, 코드를 실행하거나 데이터를 건드리기 전에 **CPU가 보는 가상 주소 공간까지 전환**해야 한다.
3. 선택된 스레드의 컨텍스트 구조에 있는 값들을 CPU 레지스터에 **로드**한다.

Windows는 대략 30ms마다 컨텍스트 스위치를 수행한다(다른 원천은 Windows의 전형적인 타임슬라이스를 20ms로 기술한다. 정확한 값은 OS 버전과 설정에 따라 달라진다).

**컨텍스트 스위치는 순수한 오버헤드다.** 컨텍스트 스위치에서 나오는 메모리 이득도 성능 이득도 없다. Windows가 이 일을 하는 이유는 오직 사용자에게 견고하고 응답성 있는 OS를 제공하기 위해서다.

그런데 성능 타격은 생각보다 훨씬 나쁘다. 컨텍스트 스위치 자체의 시간도 시간이지만, 진짜 비용은 그다음이다. 직전까지 실행되던 스레드의 코드와 데이터는 **CPU 캐시에 올라와 있었다**. 그래서 CPU가 지연이 큰 RAM에 자주 접근할 필요가 없었다. Windows가 새 스레드로 컨텍스트 스위치하면, 이 새 스레드는 십중팔구 다른 코드를 실행하고 캐시에 없는 다른 데이터에 접근한다. CPU는 캐시를 다시 채우기 위해 RAM에 접근해야 하고, 좋은 실행 속도를 회복하기까지 시간이 걸린다. 그런데 30ms쯤 뒤에 또 컨텍스트 스위치가 일어난다.

| 컨텍스트 스위치가 발생시키는 비용 | 성격 |
|---|---|
| 레지스터 저장·복원 | 직접 비용. 아키텍처와 속도에 따라 다르다 |
| 스케줄러 큐 조작과 스레드 선택 | 직접 비용 |
| 주소 공간 전환(프로세스가 다를 때) | TLB 무효화를 동반한다 |
| CPU 캐시 오염 | **간접 비용이지만 대개 가장 크다.** 캐시를 다시 채우는 동안 실행 속도가 떨어진다 |

컨텍스트 스위치에 걸리는 시간은 CPU 아키텍처와 속도에 따라 다르고, 캐시를 다시 채우는 시간은 실행 중인 애플리케이션·캐시 크기 등 여러 요인에 좌우된다. 그래서 절대적인 수치를 제시하는 것은 불가능하다. 원천의 결론은 이렇다 — **고성능 애플리케이션과 컴포넌트를 만들고 싶다면 컨텍스트 스위치를 가능한 한 피하라.**

> **📌 같은 스레드를 다시 고르면 스위치는 일어나지 않는다**
>
> 타임슬라이스가 끝날 때 Windows가 (다른 스레드로 전환하는 대신) 같은 스레드를 다시 스케줄하기로 결정하면, **컨텍스트 스위치를 수행하지 않는다.** 스레드는 그냥 계속 실행된다. 이것이 성능을 크게 개선하며, 코드를 설계할 때 가능한 한 자주 달성하고 싶은 상태다.
>
> 스레드 수가 코어 수에 가까울수록 이 상황이 자주 일어난다. 스레드 수가 코어 수를 크게 넘어서면 매 타임슬라이스마다 진짜 스위치가 일어난다. 46.1절에서 볼 스레드 풀이 존재하는 이유 중 하나가 이것이다.

### 스레드가 많으면 GC와 디버깅도 느려진다

가비지 컬렉션을 수행할 때 CLR은 **모든 스레드를 일시 중단**해야 한다. 그다음 각 스레드의 스택을 순회해 힙 객체를 마킹할 루트를 찾고, (압축이 일어났다면) 이동한 객체를 가리키도록 루트를 갱신하기 위해 스택을 한 번 더 순회한 뒤, 모든 스레드를 재개한다. 즉 **스레드를 줄이면 가비지 컬렉터의 성능도 크게 개선된다.** 실행 엔진 일시 중단과 안전 지점(safe point)의 상세는 64.12절에서 다룬다.

디버거를 쓸 때도 마찬가지다. 중단점에 걸릴 때마다 Windows는 디버깅 대상 애플리케이션의 **모든 스레드를 일시 중단**하고, 한 단계 실행하거나 계속 실행할 때 모든 스레드를 재개한다. **스레드가 많을수록 디버깅 경험이 느려진다.**

> **📌 "Stop the Madness" — 실제 시스템의 스레드 수**
>
> 원천의 저자가 자기 머신의 작업 관리자를 관찰한 기록이 있다. 프로세스 55개가 실행 중인데 스레드는 **864개**였다. 프로세스당 평균 약 15.7개다. 듀얼 코어 머신이므로 이상적으로는 프로세스당 2개면 충분한데도 그렇다.
>
> 더 나쁜 것은 CPU 사용률이 5%였다는 점이다. 즉 **95%의 시간 동안 이 864개의 스레드는 문자 그대로 아무 일도 하지 않으면서 메모리만 붙들고 있었다.**
>
> 저자가 덧붙인 실험도 인상적이다. 메모장을 열고 작업 관리자로 스레드 수를 보면 1개다. 그다음 파일 열기 대화 상자를 띄우면 스레드가 **31개** 늘어난다. 게다가 대화 상자를 닫아도 상당수가 사라지지 않는다.
>
> 프로세스 생성은 몇 초가 걸리고 메모리를 많이 쓰므로 비싸다. 그에 비해 스레드 생성은 싸다. 그래서 개발자들은 프로세스 대신 스레드를 만들기 시작했다. 그러나 **스레드가 프로세스보다 싸다는 것이 다른 시스템 리소스보다 싸다는 뜻은 아니다.** 리소스를 애플리케이션 안에서 할당하는 것과, 할당해 놓고 쓰지 않는 것은 전혀 다른 문제다.

### 성능 영향 정리

지금까지의 비용을 "언제 아프기 시작하는가"로 바꿔 정리하면 이렇다.

| 상황 | 지배적 비용 | 증상 |
|---|---|---|
| 스레드를 자주 만들고 없앤다 | 커널 객체 초기화 + (Windows) DLL 통지 | 처리량이 작업량이 아니라 **작업 개수**에 비례해 나빠진다 |
| 스레드를 많이 살려 둔다 | 스택 예약(주소 공간) + 커널 객체 | 32비트에서 `OutOfMemoryException`, 64비트에서 RSS 증가와 GC 지연 |
| 활성 스레드가 코어보다 많다 | 컨텍스트 스위치 + 캐시 오염 | CPU 사용률은 높은데 처리량이 오히려 떨어진다 |
| 스레드가 대부분 블로킹되어 있다 | 스택 메모리와 관리 오버헤드 | 메모리는 크게 쓰는데 CPU는 놀고 있다 |
| GC가 자주 돈다 | EE 일시 중단 + 스택 순회 | 스레드 수에 비례해 일시 중단 시간이 늘어난다 |

여기서 도출되는 세 가지 실무 규칙이 이 장의 나머지를 지배한다.

1. **스레드를 만들지 말고 빌려 써라.** 생성·소멸 비용은 재사용으로만 사라진다(46장).
2. **활성 스레드 수를 코어 수 근처로 유지하라.** 그래야 타임슬라이스가 끝나도 같은 스레드가 다시 스케줄되어 컨텍스트 스위치가 생략된다.
3. **기다리는 일에 스레드를 쓰지 마라.** 기다림은 콜백으로 표현할 수 있고, 그러면 기다리는 동안 스레드를 반납할 수 있다(47장).

> **💡 "스레드를 몇 개 만들어야 하나요"에 대한 정답**
>
> 순수 성능만 따지면 어떤 머신에서든 최적의 스레드 수는 **그 머신의 CPU 수와 같다.** 이유는 명백하다 — CPU보다 스레드가 많으면 컨텍스트 스위치가 도입되고 성능이 나빠진다. CPU마다 스레드가 하나씩이면 컨텍스트 스위치가 없고 스레드는 전속력으로 돈다.
>
> 그러나 Microsoft는 원시 속도와 성능보다 **신뢰성과 응답성**을 선호하도록 Windows를 설계했다. 그래서 각 프로세스에 자기 스레드를 준다. 이 결정이 없었다면 애플리케이션 하나가 여전히 OS와 다른 애플리케이션을 멈춰 세울 수 있었을 것이다.
>
> 즉 "코어 수만큼"은 이론적 최적이지 실무의 답이 아니다. 실무의 답은 **그 숫자를 우리가 정하지 않는 것** — 스레드 풀에 맡기는 것이다(46.2절).

## 45.5 지역 상태 vs 공유 상태

### 지역 변수는 공짜로 안전하다

CLR은 각 스레드에 자기만의 메모리 스택을 배정한다. 그 결과 **지역 변수는 자동으로 분리된다.**

```csharp
new Thread(Go).Start();   // 새 스레드에서 Go() 호출
Go();                     // 주 스레드에서 Go() 호출

void Go()
{
    // 지역 변수 cycles를 선언하고 사용한다
    for (int cycles = 0; cycles < 5; cycles++) Console.Write('?');
}
```

`cycles` 변수의 **사본이 각 스레드의 메모리 스택에 따로 만들어진다**. 그래서 출력은 예측 가능하게 물음표 열 개다.

이것은 동시성 프로그래밍에서 가장 중요한 하나의 사실일지도 모른다. **상태를 지역 변수에만 두면 동기화가 필요 없다.** 45.5절의 나머지 전부와 48장 전체는 이 조건을 만족하지 못할 때 벌어지는 일에 대한 이야기다.

### 공유되는 세 가지 경로

스레드는 같은 객체나 변수에 대한 공통 참조를 가질 때 데이터를 공유한다. 경로는 크게 셋이다.

#### 경로 1 — 인스턴스 필드

```csharp
var tt = new ThreadTest();
new Thread(tt.Go).Start();
tt.Go();

class ThreadTest
{
    bool _done;

    public void Go()
    {
        if (!_done) { _done = true; Console.WriteLine("Done"); }
    }
}
```

두 스레드가 **같은 `ThreadTest` 인스턴스**에서 `Go()`를 호출하므로 같은 `_done` 필드를 공유한다.

#### 경로 2 — 정적 필드

```csharp
class ThreadTest
{
    static bool _done;   // 정적 필드는 같은 프로세스의 모든 스레드가 공유한다

    static void Main()
    {
        new Thread(Go).Start();
        Go();
    }

    static void Go()
    {
        if (!_done) { _done = true; Console.WriteLine("Done"); }
    }
}
```

#### 경로 3 — 람다가 캡처한 지역 변수

```csharp
bool done = false;
ThreadStart action = () =>
{
    if (!done) { done = true; Console.WriteLine("Done"); }
};
new Thread(action).Start();
action();
```

이 세 번째 경로가 가장 조용하게 사고를 낸다. `done`은 문법적으로는 지역 변수다. 그런데 두 스레드가 그 값을 공유한다.

### 컴파일 결과 — 캡처된 지역 변수는 힙 객체의 필드다

이유는 26.10절에서 이미 본 컴파일러의 변환에 있다. 람다가 지역 변수를 캡처하면 컴파일러는 **디스플레이 클래스(display class)** 를 하나 만들고, 캡처된 변수를 그 클래스의 필드로 옮긴다.

```csharp
// 컴파일러가 만드는 것 (개념적 형태)
sealed class <>c__DisplayClass0_0
{
    public bool done;                     // 지역 변수였던 것이 필드가 되었다
    internal void <Main>b__0()
    {
        if (!done) { done = true; Console.WriteLine("Done"); }
    }
}
```

그러니까 이 코드에서 `done`은 **스택이 아니라 힙에 있는 객체의 필드**다. 그리고 그 객체 하나를 두 스레드가 참조한다. 문법적으로 지역 변수라는 사실은 아무런 보호를 제공하지 못한다.

| 상태의 종류 | 어디에 사는가 | 스레드 간 공유 | 동기화 필요 |
|---|---|---|---|
| 캡처되지 않은 지역 변수 | 각 스레드의 스택 | 아니다 | 아니다 |
| 값 타입 매개변수 | 각 스레드의 스택 | 아니다 | 아니다 |
| 인스턴스 필드 | 힙의 객체 안 | 같은 인스턴스를 공유하면 그렇다 | 그렇다 |
| 정적 필드 | 정적 저장 영역 | **항상** 그렇다 | 그렇다 |
| **캡처된** 지역 변수 | 힙(디스플레이 클래스의 필드) | 델리게이트를 공유하면 그렇다 | 그렇다 |
| `[ThreadStatic]` 필드 | 스레드별 저장소 | 아니다 | 아니다 |
| `ThreadLocal<T>.Value` | 스레드별 저장소 | 아니다 | 아니다 |

> **⚠️ "지역 변수니까 안전하다"는 문장의 조건**
>
> 정확한 문장은 이렇다. **"캡처되지 않은 지역 변수는 안전하다."** 람다나 지역 함수가 그 변수를 캡처하는 순간 힙 객체의 필드가 되며, 그 델리게이트가 여러 스레드에서 실행되면 공유 상태가 된다.
>
> 델리게이트를 다른 스레드에 넘기는 코드를 볼 때마다 **"이 람다가 무엇을 캡처하는가"** 를 물어라. 캡처가 만드는 숨은 할당과 `static` 람다는 26.11절에서 다뤘다.

### 런타임 동작 — 왜 결과가 비결정적인가

위 네 예제는 모두 **스레드 안전성이 없다**는 같은 사실을 보여준다. 출력은 실제로 비결정적이다. 가능성은 낮지만 "Done"이 두 번 출력될 수 있다. 문장 순서를 바꾸면 두 번 출력될 확률이 극적으로 올라간다.

```csharp
static void Go()
{
    if (!_done) { Console.WriteLine("Done"); _done = true; }
}
```

문제는 한 스레드가 `if` 문을 평가하는 바로 그 순간에 다른 스레드가 `WriteLine`을 실행하고 있을 수 있다는 것이다 — `_done`을 `true`로 설정하기 **전에**.

더 심한 사실도 있다. **변수를 자동 증가시키는 것조차 스레드 안전하지 않다.** `x++`는 하부 프로세서에서 읽기·증가·쓰기라는 별개의 연산으로 실행된다. 두 스레드가 잠금 없이 동시에 `x++`를 실행하면 변수가 두 번이 아니라 한 번만 증가할 수 있다. 더 나쁘게는 특정 조건에서 `x`가 **찢어져서(torn)** 옛 내용과 새 내용이 비트 단위로 뒤섞인 값이 될 수 있다.

이 문제의 해법은 잠금이다.

```csharp
class ThreadSafe
{
    static bool _done;
    static readonly object _locker = new object();

    static void Go()
    {
        lock (_locker)
        {
            if (!_done) { Console.WriteLine("Done"); _done = true; }
        }
    }
}
```

두 스레드가 동시에 잠금을 다투면 한쪽이 잠금이 풀릴 때까지 기다린다(블로킹된다). 이런 식으로 보호된 코드를 **스레드 안전(thread safe)** 하다고 한다.

이 장에서 잠금 이야기는 여기까지다. **잠금 자체의 의미론, 원자성·가시성·재배치, `Interlocked`, 데드락, 잠금 성능은 전부 48장에서 다룬다.** 여기서 기억할 것은 하나다 — 잠금은 만병통치약이 아니다. 필드 접근에 잠금 거는 것을 잊기 쉽고, 잠금 자체가 데드락 같은 새로운 문제를 만든다. **가능하면 공유 상태를 아예 만들지 않는 쪽이 낫다.**

> **💡 잠그는 것보다 나누는 것이 낫다**
>
> 실무에서 동시성 버그의 대부분은 "잠금을 잘못 걸어서"가 아니라 "공유하지 않아도 될 것을 공유해서" 생긴다.
>
> 설계할 때 순서는 이렇다. (1) 상태를 스레드마다 나눌 수 있는가 → 나눠라. (2) 상태를 불변으로 만들 수 있는가 → 불변으로 만들어라(19장). (3) 그래도 공유해야 하는가 → 그때 잠근다.
>
> 45.5절의 나머지에서 볼 스레드 로컬 저장소가 (1)의 도구이고, 50.10절의 동시성 컬렉션이 (3)을 대신 해주는 도구다.

### 스레드 로컬 저장소 — `[ThreadStatic]`과 `ThreadLocal<T>`

일반 정적 변수는 전역 변수처럼 동작한다. 애플리케이션의 모든 스레드가 접근하므로 스레드 안전하게 다루려면 대체로 동기화 기법이 필요하다.

그런데 **전역이면서 스레드마다 고유한** 종류의 데이터가 있다. 이를 **스레드 로컬 저장소(TLS, thread local storage)** 라고 한다. 전역 변수처럼 모든 스레드가 같은 이름·식별자로 접근하지만, 데이터는 스레드마다 따로 저장된다. 값에는 연결된 스레드만 접근할 수 있으므로 동기화 문제가 사라진다.

.NET에서 TLS를 쓰는 방법은 세 가지다.

| 방법 | 형태 | 상태 |
|---|---|---|
| **스레드 정적 필드** | 정적 필드에 `[ThreadStatic]` 특성 | 가장 빠르다 |
| **`ThreadLocal<T>`** | 스레드 정적 필드를 감싼 클래스 도우미 | 편리하다 |
| **스레드 데이터 슬롯** | `Thread.SetData` / `Thread.GetData` | **폐기된 것으로 봐야 한다** |

#### `[ThreadStatic]`의 사용법과 함정

일반 정적 필드에 `[ThreadStatic]` 특성만 붙이면 된다. 값 타입과 참조 타입 모두 쓸 수 있다.

```csharp
class SomeClass
{
    [ThreadStatic]
    private static int threadStaticValueData;

    [ThreadStatic]
    private static SomeData threadStaticReferenceData;

    public void Run(object param)
    {
        int arg = int.Parse(param.ToString());
        threadStaticValueData = arg;
        threadStaticReferenceData = new SomeData { Field = arg };
        while (true)
        {
            Thread.Sleep(1000);
            Console.WriteLine($"Worker {threadStaticValueData}:{threadStaticReferenceData.Field}.");
        }
    }
}
```

두 스레드가 같은 필드를 읽지만 각자 다른 값을 본다. 한 스레드는 `Worker 1:1`을, 다른 스레드는 `Worker 2:2`를 출력한다. 두 필드가 일반 정적 필드였다면 쓰기에서 경쟁 조건이 일어나 1과 2가 뒤섞인 결과가 나왔을 것이다.

> **⚠️ `[ThreadStatic]` 필드의 이니셜라이저는 한 스레드에서만 돈다**
>
> 순수 스레드 정적 필드에는 함정이 하나 있다. **필드에 이니셜라이저가 있으면 그 이니셜라이저는 정적 생성자를 실행한 스레드에서 딱 한 번만 호출된다.** 다시 말해 그 타입을 처음 사용한 스레드만 필드가 제대로 초기화되고, 나머지 스레드는 그 필드가 **기본값으로 초기화된 것**을 본다.
>
> ```csharp
> class SomeOtherClass
> {
>     [ThreadStatic]
>     private static int threadStaticValueData = 44;
>
>     public void Run()
>     {
>         while (true)
>         {
>             Thread.Sleep(1000);
>             Console.WriteLine($"Worker {threadStaticValueData}");  // "Worker 44" 또는 "Worker 0"
>         }
>     }
> }
> ```
>
> 두 스레드가 `Run`을 실행하면 하나는 `Worker 44`를, 다른 하나는 `Worker 0`을 출력한다. 상당히 놀라운 결과다. **`[ThreadStatic]` 필드에는 이니셜라이저를 쓰지 마라.**

이니셜라이저를 못 쓴다면 초기화는 어떻게 하는가. 스레드 정적 필드를 지연 초기화하는 속성으로 감싸면 된다.

```csharp
[ThreadStatic]
private static int? threadStaticData;

public static int ThreadStaticData
{
    get
    {
        if (threadStaticData == null)
            threadStaticData = 44;
        return threadStaticData.Value;
    }
}
```

#### `ThreadLocal<T>`

이 문제들을 해결하기 위해 .NET Framework 4.0부터 `ThreadLocal<T>` 클래스가 제공된다. **더 낫고 더 결정적인 초기화 동작**을 제공한다. 생성자에 값 팩터리를 넘기면 `Value` 속성에 처음 접근할 때 지연 초기화된다.

```csharp
private static ThreadLocal<int> threadValueLocal =
    new ThreadLocal<int>(() => 44, trackAllValues: true);

public void Run()
{
    while (true)
    {
        Thread.Sleep(1000);
        Console.WriteLine($"Worker {threadValueLocal.Value}.");
        Console.WriteLine(threadValueLocal.Values.Count);
        threadValueLocal.Value = threadValueLocal.Value + 1;
    }
}
```

`ThreadLocal<T>`는 **정적이 아닌 필드에도 저장할 수 있다**. 그러면 클래스의 인스턴스마다 서로 다른 스레드별 값을 추적한다. 또 생성자의 `trackAllValues` 인자에 `true`를 넘기면 초기화된 모든 값을 추적하고, 나중에 `Values` 속성으로 전부 순회할 수 있다.

#### 둘의 차이 정리

| 항목 | `[ThreadStatic]` | `ThreadLocal<T>` |
|---|---|---|
| 선언 위치 | **정적 필드에만** | 정적·인스턴스 필드 모두 |
| 초기화 시점 | 정적 생성자를 실행한 스레드에서 **한 번만** | 각 스레드가 `Value`에 처음 접근할 때 지연 초기화 |
| 다른 스레드가 보는 초기값 | **타입의 기본값**(`0`, `null`) | 값 팩터리가 만든 값 |
| 모든 값 순회 | 불가능 | `trackAllValues: true`이면 `Values`로 가능 |
| 폐기 필요성 | 없다 | **있다.** `Dispose`하지 않으면 누수 위험 |
| 강한 타입 | 그렇다 | 그렇다 |
| 접근 비용(원천 벤치마크) | 값 타입 약 0.23ns, 참조 타입 약 0.20ns | 값 타입 약 5.37ns, 참조 타입 약 8.01ns |

접근 비용의 차이가 20~40배쯤 난다. `ThreadLocal<T>`가 스레드 정적 필드를 감싼 꽤 복잡한 래퍼이기 때문이다. 내부 구조를 추가로 다루느라 성능 손해가 생긴다. 게다가 `ThreadLocal<T>`는 **파이널라이저를 갖고 있고, 생성과 파이널라이제이션 때 전역 잠금을 획득한다.** 인스턴스를 대량으로 만드는 애플리케이션에서는 이것이 심각한 경합 원인이 될 수 있다.

그럼에도 성능이 주된 관심사가 아니라면 `ThreadLocal<T>`가 순수 스레드 정적 필드보다 편리한 경우가 많다.

> **⚠️ `ThreadLocal<T>`가 만드는 메모리 누수**
>
> `ThreadLocal<T>`에 무엇을 저장하는지 주의해야 한다. 미묘한 누수의 원인이 될 수 있다.
>
> ```csharp
> internal class Repository
> {
>     private ThreadLocal<List<Item>> _storage = new(valueFactory: () => new List<Item>());
>
>     public void Add(int value) => _storage.Value.Add(new Item(value, this));
>
>     internal class Item(int value, Repository parent)
>     {
>         public int Value { get; } = value;
>         public Repository Parent { get; } = parent;
>     }
> }
> ```
>
> `Repository`를 아무도 참조하지 않게 만들고 `GC.Collect()`를 여러 번 불러도 이 객체는 살아 있다. 이유는 이렇다. 스레드 정적 필드에 담긴 값은 **연결된 스레드가 죽을 때까지 살아 있다.** 정적 필드처럼 쓰는 "고전적" 스레드 정적 필드에서는 문제가 안 되지만, `ThreadLocal<T>`가 인스턴스 필드에 저장되면 수명이 더 짧아지므로 인스턴스가 필요 없어질 때 스레드 정적 값들을 정리해야 한다. 그 정리를 하는 것이 `Dispose`이고 파이널라이저가 백업이다.
>
> 그런데 위 코드에서는 리스트 안의 `Item`이 `Repository`를 역참조하고, `Repository`가 `ThreadLocal<T>`를 붙들고 있어 서로가 서로를 루팅한다. 그래서 파이널라이저도 발동하지 않는다. **`ThreadLocal<T>`는 반드시 제대로 `Dispose`하라.**

> **📌 스레드 데이터 슬롯은 폐기된 것으로 보라**
>
> `Thread.GetNamedDataSlot`/`Thread.AllocateDataSlot`과 `Thread.SetData`/`Thread.GetData`로 접근하는 데이터 슬롯 API가 있다. .NET Framework 초기에는 런타임에 TLS 데이터를 동적으로 할당하기 위한 편의 장치였다(클래스에 스레드 정적 필드를 런타임에 추가할 수는 없으므로).
>
> 문제는 **강한 타입이 사라진다**는 것이다. `SetData`와 `GetData`는 `System.Object`를 주고받는다. 이름 있는 슬롯은 문자열 식별자를 쓰므로 컴파일 시점에 잡기 어려운 문제를 부른다. .NET 문서는 스레드 정적 필드가 데이터 슬롯보다 성능이 훨씬 좋으므로 가능하면 그쪽을 쓰라고 명확히 말한다. 실제로 .NET Core에서 데이터 슬롯은 `ThreadLocal<T>` 위의 래퍼일 뿐이다.

### 성능 영향 — 나누는 것이 잠그는 것보다 빠르다

45.5절의 앞에서 "잠그는 것보다 나누는 것이 낫다"고 했다. 이 주장을 수치로 확인할 수 있는 실험이 원천에 있다. 32개의 스레드가 하나의 카운터를 정해진 횟수만큼 증가시키는 작업을 세 가지 방식으로 구현하고 비교한 것이다.

- **`Interlocked.Increment`** — 공유 카운터 하나를 원자적 연산으로 증가시킨다(48.4절).
- **`lock`** — 공유 카운터를 배타적 잠금으로 보호한다(48.5절).
- **`ThreadLocal<long>`** — 스레드마다 자기 부분 카운터를 증가시키고, 마지막에 `Values`를 순회해 합친다.

```csharp
[Benchmark]
public long ThreadLocal()
{
    static void increment(ThreadLocal<long> counter) => counter.Value++;

    static long getResult(ThreadLocal<long> counter)
    {
        long result = 0;
        foreach (var value in counter.Values)
            result += value;
        return result;
    }

    return Run(increment, getResult, new ThreadLocal<long>(trackAllValues: true));
}
```

.NET 8에서 측정한 결과다.

| 방식 | 반복 10,000 | 반복 100,000 | 반복 1,000,000 |
|---|---|---|---|
| `InterlockedIncrement` | 1.900 ms | 92.672 ms | 715.166 ms |
| `Lock` | 13.274 ms | 139.899 ms | 1,323.899 ms |
| `ThreadLocal` | **1.944 ms** | **3.614 ms** | **23.600 ms** |

반복 횟수가 늘수록 격차가 벌어진다. 백만 회에서 `ThreadLocal` 방식은 `Interlocked`보다 30배, `lock`보다 56배 빠르다. 할당은 오히려 `ThreadLocal` 쪽이 많다(수십 KB 대 수 KB). **동기화 비용을 없앤 대가로 메모리를 조금 더 쓴 것**이다.

> **⚠️ 이 수치를 그대로 믿지 마라**
>
> 이것은 극단적인 예다. 스레드들이 카운터를 증가시키는 것 외에 아무 일도 하지 않으므로 **경합이 최대화**되어 있다. 실제 시나리오에서는 결과가 훨씬 덜 극적이다. 어느 쪽을 고르든 반드시 직접 측정하라(67.3절).
>
> 그럼에도 이 표가 가르치는 방향은 확실하다. **경합은 비용의 원인이고, 경합을 없애는 가장 확실한 방법은 상태를 공유하지 않는 것이다.** 잠금을 더 잘 거는 것이 아니라.

스레드 로컬 저장소의 내부 구조와 `AsyncLocal<T>`는 49.8절과 49.9절에서 자세히 다룬다.

## 45.6 스레드에 데이터 전달하기와 예외 처리

### `ParameterizedThreadStart`

스레드의 시작 메서드에 인자를 넘기고 싶을 때가 있다. `Thread`의 생성자는 두 델리게이트 중 하나를 받도록 오버로드되어 있다.

```csharp
public delegate void ThreadStart();
public delegate void ParameterizedThreadStart(object obj);
```

`ThreadStart`는 인자를 받지 않고 `void`를 반환하는 메서드만 가리킬 수 있다. 인자를 넘기려면 `ParameterizedThreadStart`를 쓰고, `Start` 메서드에 인자를 넘긴다.

```csharp
Thread t = new Thread(Print);
t.Start("Hello from t!");

void Print(object messageObj)
{
    string message = (string)messageObj;   // 캐스팅이 필요하다
    Console.WriteLine(message);
}
```

`ParameterizedThreadStart`는 `System.Object` 하나만 받는다. 무엇이든 `System.Object`로 표현할 수 있으므로 커스텀 클래스나 구조체를 통해 원하는 만큼의 인자를 넘길 수 있다.

```csharp
class AddParams
{
    public int a, b;
    public AddParams(int numb1, int numb2) { a = numb1; b = numb2; }
}

void Add(object data)
{
    if (data is AddParams ap)
    {
        Console.WriteLine("ID of thread in Add(): {0}", Environment.CurrentManagedThreadId);
        Console.WriteLine("{0} + {1} is {2}", ap.a, ap.b, ap.a + ap.b);
    }
}

AddParams ap = new AddParams(10, 10);
Thread t = new Thread(new ParameterizedThreadStart(Add));
t.Start(ap);
```

> **📌 어느 델리게이트를 쓸 것인가**
>
> 원천의 한 저자는 인자 없는 `ThreadStart`보다 `ParameterizedThreadStart` 쪽을 권한다. 이유는 이렇다 — 스레드 메서드가 `Object`를 받고 `void`를 반환하면 그 메서드를 **전용 스레드로도, 스레드 풀로도 호출할 수 있다**. 인자 없는 형태는 그만큼 제약이 크다.
>
> 다만 오늘날 실무의 기본 선택은 셋 중 어느 쪽도 아니다. 람다로 캡처하는 방식이 가장 편하고, 그보다도 `Task`가 낫다(46.3절).

### 람다로 데이터 넘기기

가장 쉬운 방법은 원하는 인자로 메서드를 호출하는 람다다.

```csharp
Thread t = new Thread(() => Print("Hello from t!"));
t.Start();

void Print(string message) => Console.WriteLine(message);
```

이 방식이면 인자 개수에 제약이 없고 캐스팅도 필요 없다. 구현 전체를 여러 문장의 람다에 넣을 수도 있다.

```csharp
new Thread(() =>
{
    Console.WriteLine("I'm running on another thread!");
    Console.WriteLine("This is so easy!");
}).Start();
```

### 함정 — 루프 변수 캡처

편리한 만큼 위험도 따라온다. **스레드를 시작한 뒤에 캡처된 변수를 실수로 수정하는 것**을 조심해야 한다.

```csharp
for (int i = 0; i < 10; i++)
    new Thread(() => Console.Write(i)).Start();
```

출력이 비결정적이다. 전형적인 결과는 이렇다.

```text
0223557799
```

문제는 `i`가 루프의 수명 내내 **같은 메모리 위치를 가리킨다**는 것이다. 따라서 각 스레드는 자기가 실행되는 동안에도 값이 바뀔 수 있는 변수에 대해 `Console.Write`를 호출한다.

해결은 임시 변수다.

```csharp
for (int i = 0; i < 10; i++)
{
    int temp = i;
    new Thread(() => Console.Write(temp)).Start();
}
```

`temp`는 이제 루프 반복마다 지역 변수다. 각 스레드가 서로 다른 메모리 위치를 캡처하므로 0부터 9까지가 정확히 한 번씩 출력된다(순서는 여전히 정해지지 않는다. 스레드가 언제 시작될지 알 수 없기 때문이다).

같은 문제를 더 단순하게 보여주는 예다.

```csharp
string text = "t1";
Thread t1 = new Thread(() => Console.WriteLine(text));

text = "t2";
Thread t2 = new Thread(() => Console.WriteLine(text));

t1.Start(); t2.Start();
```

두 람다가 **같은 `text` 변수**를 캡처하므로 `t2`가 두 번 출력된다.

> **⚠️ `for`와 `foreach`가 다르다**
>
> 이 문제는 멀티스레딩만의 문제가 아니라, C#의 `for` 루프에서 변수를 캡처하는 규칙의 문제다(26.10절).
>
> `foreach`의 반복 변수는 C# 5.0부터 **반복마다 새로 선언되는 것으로** 규정이 바뀌었다. 그래서 `foreach`에서는 이 함정이 없다. 그러나 **`for` 루프의 반복 변수를 캡처하면 여전히 같은 위치를 공유한다.** 언어 명세가 바뀔 여지도 거의 없다 — `for`의 반복 변수는 루프 전체에 걸쳐 하나여야 의미가 통하기 때문이다.
>
> 즉 `for`로 스레드나 태스크를 뿌리는 코드를 보면 반사적으로 인덱스 캡처를 의심해야 한다.

### 결과를 돌려받기

스레드에 데이터를 넣는 것은 쉽지만, **`Join`한 스레드에서 "반환값"을 얻어 내는 쉬운 방법은 없다.** 어떤 공유 필드를 마련해야 한다.

```csharp
int result = 0;
Thread thread = new Thread(() => { result = Add(1, 2); });
thread.Start();
thread.Join();               // 여기서 기다려야 result를 읽을 수 있다
Console.WriteLine($"The addition of 1 plus 2 is {result}.");

static int Add(int a, int b) => a + b;
```

`Join` 없이 `result`를 읽으면 아직 쓰이지 않은 값을 볼 수 있고, `Join`을 넣으면 결국 호출 스레드를 블로킹한다. 신호 구성 요소(`AutoResetEvent`, `ManualResetEvent`)를 쓰면 조금 더 유연해지지만 여전히 수작업이다.

```csharp
AutoResetEvent _waitHandle = new AutoResetEvent(false);

AddParams ap = new AddParams(10, 10);
Thread t = new Thread(new ParameterizedThreadStart(Add));
t.Start(ap);

_waitHandle.WaitOne();       // 신호가 올 때까지 여기서 기다린다
Console.WriteLine("Other thread is done!");

void Add(object data)
{
    if (data is AddParams ap)
    {
        Console.WriteLine("{0} + {1} is {2}", ap.a, ap.b, ap.a + ap.b);
        _waitHandle.Set();   // 다른 스레드에 끝났다고 알린다
    }
}
```

스레드에서 결과를 돌려받는 방법을 정리하면 이렇다.

| 방법 | 호출자를 블로킹하는가 | 여러 결과 | 예외 전달 | 비고 |
|---|---|---|---|---|
| 공유 필드 + `Join()` | **그렇다** | 필드를 더 만든다 | 직접 필드에 담아야 한다 | 가장 단순하고 가장 제약이 크다 |
| 공유 필드 + `Join(timeout)` | 그렇다(제한적) | 위와 같다 | 위와 같다 | 타임아웃 반환값을 반드시 검사하라 |
| 신호 구성 요소(`AutoResetEvent` 등) | 그렇다 | 신호를 더 만든다 | 위와 같다 | 폐기(`Dispose`)가 필요하다. 49.2절 |
| 콜백 델리게이트 | 아니다 | 가능하다 | 콜백 안에서 잡아야 한다 | 콜백이 어느 스레드에서 도는지 주의 |
| `SynchronizationContext.Post` | 아니다 | 가능하다 | 삼켜질 수 있다 | UI 갱신용. 45.8절 |
| **`Task<TResult>`** | 선택할 수 있다 | 합성 가능하다 | **자동 전파** | 46장의 답 |

마지막 줄이 이 표를 쓴 이유다. 위 다섯 줄은 전부 수작업이고, 마지막 줄은 그 수작업을 라이브러리가 대신한다.

신호 구성 요소의 전체 카탈로그는 49장에서 다룬다. 여기서 볼 것은 **"결과를 돌려받는 일이 이렇게 번거롭다"** 는 사실 자체다. 이것이 45.9절에서 `Task`를 써야 하는 이유 중 하나로 다시 등장한다.

### 예외는 스레드 경계를 넘지 않는다

이 절에서 가장 중요한 사실이다.

> **스레드가 만들어지는 시점에 유효했던 `try`/`catch`/`finally` 블록은, 그 스레드가 실행을 시작할 때 아무런 관련이 없다.**

```csharp
try
{
    new Thread(Go).Start();
}
catch (Exception ex)
{
    // 여기에는 절대 오지 않는다!
    Console.WriteLine("Exception!");
}

void Go() { throw null; }   // NullReferenceException을 던진다
```

이 `try`/`catch` 문은 무효하다. 새로 만들어진 스레드는 처리되지 않은 `NullReferenceException`을 짊어지게 된다. 각 스레드가 **독립적인 실행 경로**를 가진다는 것을 생각하면 당연한 동작이다.

그리고 32.14절에서 본 대로 **프로세스의 어느 스레드에서든 처리되지 않은 예외가 발생하면 CLR은 프로세스를 종료한다.** 워커 스레드에서 던진 예외 하나가 애플리케이션 전체를 죽인다.

해결은 예외 처리기를 스레드 진입 메서드 안으로 옮기는 것이다.

```csharp
new Thread(Go).Start();

void Go()
{
    try
    {
        // ...
        throw null;   // 아래에서 잡힌다
        // ...
    }
    catch (Exception ex)
    {
        // 보통은 예외를 로그에 남기고 / 또는 다른 스레드에
        // 문제가 생겼음을 알린다
    }
}
```

프로덕션 애플리케이션에서는 **모든 스레드 진입 메서드에 예외 처리기가 필요하다.** 주 스레드에 (보통 호출 스택의 더 높은 곳에) 두는 것과 똑같은 이유다.

> **💡 스레드 진입 메서드의 템플릿**
>
> ```csharp
> void ThreadEntryPoint()
> {
>     try
>     {
>         DoWork();
>     }
>     catch (Exception ex)
>     {
>         _logger.LogError(ex, "worker 스레드가 실패했다");
>         // 필요하면 여기서 다른 스레드에 실패를 신호로 알린다
>     }
> }
> ```
>
> 이런 블록을 쓸 때 오류를 그냥 무시하는 일은 거의 없어야 한다. 보통은 예외의 상세를 로그에 남긴다. 클라이언트 애플리케이션이라면 사용자에게 대화 상자를 띄워 상세를 서버로 자동 제출하게 할 수도 있다. 그다음에는 애플리케이션을 재시작하는 것을 고려하라 — 예상치 못한 예외는 프로그램을 유효하지 않은 상태로 남겨 놓았을 수 있다.
>
> 다시 던져야 할 때는 `throw;`를 쓴다. `throw ex;`는 스택 트레이스를 날린다(32.5절).

### 중앙 예외 처리로는 부족하다

WPF와 Windows Forms 애플리케이션은 "전역" 예외 처리 이벤트를 제공한다.

| 프레임워크 | 이벤트 | 발동 범위 |
|---|---|---|
| WPF | `Application.DispatcherUnhandledException` | 메시지 루프를 통해 호출된 코드 |
| Windows Forms | `Application.ThreadException` | 메시지 루프를 통해 호출된 코드 |
| 공통 | `AppDomain.CurrentDomain.UnhandledException` | 처리되지 않은 예외 통지(32.14절) |

앞의 두 이벤트는 **애플리케이션이 활성 상태인 동안 주 스레드에서 실행되는 모든 코드**에 대해 발동한다. 버그를 기록하고 보고하기 위한 최후의 방어선으로 유용하다. 이 이벤트를 처리하면 프로그램이 종료되는 것을 막을 수도 있다(다만 처리되지 않은 예외로 이어졌거나 그로부터 파생된 상태 손상을 피하려면 애플리케이션을 재시작하는 편이 나을 수 있다).

> **⚠️ 전역 처리기는 워커 스레드를 구해 주지 않는다**
>
> `DispatcherUnhandledException`과 `Application.ThreadException`은 **직접 만든 워커 스레드에서 발생한 처리되지 않은 예외에 대해서는 발동하지 않는다.**
>
> "전역 처리기를 달아 놨으니 안전하다"는 생각이 이 지점에서 무너진다. 스레드마다 자기 `try`/`catch`가 있어야 한다는 규칙에 예외는 없다.

### `Thread`와 `Task`의 예외 처리 대비

| 항목 | `Thread` | `Task` (46장) |
|---|---|---|
| 진입 메서드에서 던진 예외 | 처리되지 않음 → **프로세스 종료** | 태스크에 저장되고 태스크가 "실패(faulted)" 상태가 된다 |
| 호출자에게 전파되는가 | 아니다 | `Wait()`나 `Result` 접근 시 `AggregateException`으로 다시 던져진다 |
| 결과 반환 | 공유 필드 + `Join` 수작업 | `Task<TResult>.Result` |
| 관찰하지 않은 예외 | 개념 자체가 없다 | `TaskScheduler.UnobservedTaskException`으로 통지받을 수 있다(46.11절) |

이 표가 45.9절의 논지를 미리 요약한다. 스레드를 직접 다룰 때 수작업으로 해야 하는 일 중 상당 부분이 **예외를 안전하게 다루는 일**이다.

## 45.7 포그라운드 vs 백그라운드 스레드, 스레드 우선순위

### 정의

CLR은 모든 스레드를 **포그라운드 스레드** 아니면 **백그라운드 스레드**로 취급한다.

> **프로세스 안의 모든 포그라운드 스레드가 실행을 멈추면, CLR은 아직 실행 중인 백그라운드 스레드를 강제로 끝낸다. 이 백그라운드 스레드들은 즉시 종료되며, 예외는 던져지지 않는다.**

바꿔 말하면 이렇다. **포그라운드 스레드가 하나라도 살아 있으면 프로세스는 죽지 않는다.**

```csharp
public static class Program
{
    public static void Main()
    {
        Thread t = new Thread(Worker);   // 기본은 포그라운드
        t.IsBackground = true;           // 백그라운드로 만든다

        t.Start();

        // t가 포그라운드면 애플리케이션은 약 10초 동안 죽지 않는다
        // t가 백그라운드면 애플리케이션은 즉시 죽는다
        Console.WriteLine("Returning from Main");
    }

    private static void Worker()
    {
        Thread.Sleep(10000);
        // 아래 줄은 이 코드가 포그라운드 스레드에서 실행될 때만 표시된다
        Console.WriteLine("Returning from Worker");
    }
}
```

### 무엇이 기본으로 무엇인가

| 스레드 | 기본 상태 |
|---|---|
| 애플리케이션의 주 스레드 | **포그라운드** |
| `new Thread(...)`로 명시적으로 만든 스레드 | **포그라운드** |
| 스레드 풀 스레드 (`Task.Run` 포함) | **백그라운드** |
| 네이티브 코드에서 관리 실행 환경으로 진입한 스레드 | **백그라운드** |

수명 중 언제든 포그라운드↔백그라운드를 바꿀 수 있다. 다만 스레드가 시작된 뒤에 바꾸는 코드는 읽기 어려우므로 `Start` 전에 정하는 것이 낫다.

용도의 구분은 이렇다. **정말로 완료되기를 원하는 작업**(메모리 버퍼의 데이터를 디스크로 플러시하는 것 같은)은 포그라운드 스레드로 실행한다. **미션 크리티컬하지 않은 작업**(스프레드시트 셀 재계산, 레코드 인덱싱 같은)은 백그라운드 스레드로 실행한다. 이런 일은 애플리케이션이 재시작될 때 다시 할 수 있고, 사용자가 종료하려는데 애플리케이션을 붙잡아 둘 이유가 없다.

> **⚠️ 백그라운드 스레드는 `finally`도 돌지 않는다**
>
> 프로세스가 이런 식으로 종료되면 **백그라운드 스레드의 실행 스택에 있는 모든 `finally` 블록이 건너뛰어진다.** `using` 블록도 마찬가지다(`using`은 `try`/`finally`이므로).
>
> 프로그램이 임시 파일 삭제 같은 정리 작업을 `finally`나 `using`에 의존하고 있다면, 그 정리는 **일어나지 않는다**. 대응은 애플리케이션 종료 시 그런 백그라운드 스레드를 명시적으로 기다리는 것이다 — `Join`하거나 신호 구성 요소를 쓴다(49장).
>
> 어느 쪽이든 **타임아웃을 지정하라.** 끝나기를 거부하는 스레드는 포기할 수 있어야 한다. 그러지 않으면 애플리케이션은 사용자가 작업 관리자(Unix라면 `kill`)를 동원해야만 닫히게 된다.

> **⚠️ 애플리케이션이 종료되지 않는 가장 흔한 원인**
>
> 활성 포그라운드 스레드의 존재다. 원천의 저자는 애플리케이션이 도무지 종료되지 않는다는 문제로 컨설팅에 불려 갔다가, 몇 시간을 조사한 끝에 **UI 컴포넌트 하나가 포그라운드 스레드(기본값)를 명시적으로 만들고 있었던 것**을 찾아냈다고 기록한다. 그 컴포넌트가 스레드 풀을 쓰도록 고쳐 문제를 해결했고, 덤으로 효율도 좋아졌다.
>
> 포그라운드 스레드는 이런 대접이 필요 없지만, **끝나지 않게 만드는 버그를 조심해야 한다**는 점은 같다.

> **📌 포그라운드/백그라운드는 왜 CLR의 개념인가**
>
> CLR이 이 개념을 제공해야 했던 이유는 AppDomain을 더 잘 지원하기 위해서였다. 각 AppDomain이 별개의 애플리케이션을 실행할 수 있고, 각 애플리케이션이 자기 포그라운드 스레드를 갖는다. 한 애플리케이션이 종료되어 그 포그라운드 스레드가 끝나도, CLR은 다른 애플리케이션이 계속 돌 수 있도록 살아 있어야 한다. 모든 애플리케이션이 종료되고 모든 포그라운드 스레드가 끝나야 프로세스 전체가 파괴될 수 있다.
>
> .NET(.NET Core 계열)에는 AppDomain이 하나뿐이므로 이 사정은 역사적 배경으로만 남았지만, 포그라운드/백그라운드 구분 자체는 그대로다.

### 스레드 우선순위 — Windows 쪽 그림

선점형 운영체제는 어떤 스레드를 언제 얼마나 스케줄할지 결정하는 알고리즘이 필요하다.

모든 스레드에는 **0(가장 낮음)부터 31(가장 높음)까지의 우선순위 레벨**이 부여된다. 시스템은 어떤 스레드를 CPU에 배정할지 결정할 때 우선순위 31인 스레드부터 살펴보고, 라운드 로빈으로 스케줄한다. 우선순위 31 스레드가 스케줄 가능하기만 하면, 시스템은 우선순위 0~30인 스레드를 **절대로 CPU에 배정하지 않는다.** 이 상태를 **기아(starvation)** 라고 한다.

높은 우선순위 스레드는 낮은 우선순위 스레드를 **항상 선점한다.** 낮은 쪽이 무엇을 실행 중이든 상관없다. 우선순위 5 스레드가 실행 중인데 시스템이 더 높은 우선순위 스레드가 실행 준비되었다고 판단하면, 시스템은 즉시 낮은 쪽을 (타임슬라이스 중간이라도) 중단시키고 높은 쪽에 CPU를 배정한다. 높은 쪽은 완전한 타임슬라이스를 받는다.

> **📌 제로 페이지 스레드**
>
> 시스템이 부팅될 때 **제로 페이지 스레드(zero page thread)** 라는 특별한 스레드를 만든다. 우선순위 0이 배정되며, 시스템 전체에서 우선순위 0으로 도는 유일한 스레드다. 다른 스레드가 할 일이 없을 때 시스템의 빈 RAM 페이지를 0으로 채우는 것이 이 스레드의 일이다.

### 프로세스 우선순위 클래스와 상대적 스레드 우선순위

0~31의 레벨을 개발자가 직접 다루게 하는 것은 너무 어렵다고 판단해, Windows는 그 위에 추상 계층을 얹었다.

애플리케이션을 설계할 때 먼저 **이 애플리케이션이 머신의 다른 애플리케이션보다 더 응답성이 좋아야 하는가 덜해야 하는가**를 결정하고, 그에 맞는 **프로세스 우선순위 클래스**를 고른다. Windows는 여섯 개를 지원한다 — Idle, Below Normal, Normal, Above Normal, High, Realtime. 물론 Normal이 기본이자 압도적으로 흔하다.

그다음에는 다른 애플리케이션과의 관계는 잊고 **자기 애플리케이션 안의 스레드들**만 생각한다. Windows는 일곱 개의 상대적 스레드 우선순위를 지원한다 — Idle, Lowest, Below Normal, Normal, Above Normal, Highest, Time-Critical. 이 값들은 프로세스의 우선순위 클래스에 **상대적**이다.

시스템은 프로세스의 우선순위 클래스와 스레드의 상대적 우선순위를 조합해 실제 우선순위 레벨로 매핑한다.

| 상대적 스레드 우선순위 | Idle | Below Normal | Normal | Above Normal | High | Realtime |
|---|---|---|---|---|---|---|
| Time-Critical | 15 | 15 | 15 | 15 | 15 | 31 |
| Highest | 6 | 8 | 10 | 12 | 15 | 26 |
| Above Normal | 5 | 7 | 9 | 11 | 14 | 25 |
| Normal | 4 | 6 | 8 | 10 | 13 | 24 |
| Below Normal | 3 | 5 | 7 | 9 | 12 | 23 |
| Lowest | 2 | 4 | 6 | 8 | 11 | 22 |
| Idle | 1 | 1 | 1 | 1 | 1 | 16 |

읽는 법. Normal 프로세스의 Normal 스레드는 레벨 8을 받는다. 대부분의 프로세스가 Normal 클래스이고 대부분의 스레드가 Normal 우선순위이므로, **시스템의 대부분 스레드는 레벨 8**이다.

High 우선순위 프로세스의 Normal 스레드는 레벨 13이다. 프로세스의 우선순위 클래스를 Idle로 바꾸면 그 스레드의 레벨은 4가 된다. 스레드의 **상대적** 우선순위는 그대로지만 실제 번호가 달라진다.

표에서 레벨 0을 얻는 방법이 없다는 점에 주목하라. 0은 제로 페이지 스레드 전용이다. 또 17·18·19·20·21·27·28·29·30은 사용자 모드 애플리케이션이 얻을 수 없다(커널 모드 디바이스 드라이버는 얻을 수 있다). Realtime 클래스의 스레드는 레벨 16 미만이 될 수 없고, Realtime이 아닌 클래스의 스레드는 15를 넘을 수 없다.

> **📌 Windows는 프로세스를 스케줄하지 않는다**
>
> 프로세스 우선순위 클래스 개념은 사람들을 헷갈리게 한다. Windows가 프로세스를 스케줄한다고 오해하는 것이다. **Windows는 프로세스를 절대 스케줄하지 않는다. 스레드만 스케줄한다.**
>
> 프로세스 우선순위 클래스는 자기 애플리케이션이 다른 실행 중인 애플리케이션과 어떻게 비교되는지 개발자가 머릿속에서 정리하도록 Microsoft가 만든 추상 개념이다. 그 외의 목적은 없다.

### .NET에서 우선순위 다루기

관리 코드에서는 `Thread`의 `Priority` 속성에 `ThreadPriority` 열거형 값을 넣는다.

```csharp
public enum ThreadPriority
{
    Lowest,
    BelowNormal,
    Normal,       // 기본값
    AboveNormal,
    Highest
}
```

일곱 개가 아니라 다섯 개다. Windows가 레벨 0과 실시간 범위를 자기 몫으로 예약했듯, **CLR은 Idle과 Time-Critical 우선순위 레벨을 자기 몫으로 예약했다.** CLR의 파이널라이저 스레드가 Time-Critical 레벨에서 돈다(34.2절).

프로세스 우선순위는 `System.Diagnostics`의 `Process` 클래스로 바꾼다.

```csharp
using Process p = Process.GetCurrentProcess();
p.PriorityClass = ProcessPriorityClass.High;
```

이것은 다른 프로세스의 스레드보다 높은 우선순위가 필요할 때 필요하다. 스레드 우선순위만 올려 봐야 같은 프로세스 안에서의 상대 순위만 바뀌기 때문이다. 최소한의 일만 하면서 낮은 지연 시간이 필요한 비 UI 프로세스에는 잘 맞는다. 반면 계산량이 많은 애플리케이션(특히 UI가 있는 것)에서 프로세스 우선순위를 올리면 다른 프로세스를 굶기고 컴퓨터 전체를 느리게 만든다.

> **⚠️ 관리 애플리케이션은 프로세스 우선순위 클래스를 건드리면 안 된다**
>
> 관리 애플리케이션은 자기가 프로세스를 소유한 것처럼 행동해서는 안 된다. AppDomain 안에서 실행되는 것처럼 행동해야 한다. 그래서 **프로세스의 우선순위 클래스를 바꾸면 안 된다** — 그 프로세스에서 실행되는 모든 코드에 영향을 주기 때문이다.
>
> 여러 ASP.NET 애플리케이션이 하나의 프로세스에서 각자의 AppDomain으로 돌던 구조를 생각하면 이유가 분명하다. 관리 저장 프로시저가 SQL Server 프로세스 안에서 도는 경우도 마찬가지다.

> **⚠️ Realtime 클래스는 사실상 금지다**
>
> Realtime 우선순위는 극단적으로 높아서 운영체제 작업을 방해할 수 있다. 필요한 디스크 I/O와 네트워크 트래픽이 일어나지 못하게 막을 수 있고, 키보드와 마우스 입력이 제때 처리되지 못해 **사용자에게 시스템이 완전히 얼어붙은 것처럼 보이게** 만들 수 있다.
>
> Realtime을 쓰려면 아주 좋은 이유가 있어야 한다 — 짧은 지연으로 하드웨어 이벤트에 응답해야 하거나, 아주 짧게 끝나는 작업을 수행해야 하는 경우 같은. 참고로 시스템 전체를 원활하게 유지하기 위해, 사용자가 "스케줄링 우선순위 증가" 권한을 갖지 않으면 프로세스는 Realtime 클래스로 실행될 수 없다.

> **💡 올리지 말고 내려라**
>
> **다른 스레드의 우선순위를 올리는 것보다 이 스레드의 우선순위를 내리는 편이 낫다.**
>
> 우선순위를 내려야 할 스레드는 코드 컴파일, 맞춤법 검사, 스프레드시트 재계산 같은 **오래 걸리는 컴퓨트 바운드 작업**을 실행하는 스레드다. 우선순위를 올려야 할 스레드는 **아주 빠르게 무언가에 반응한 뒤 아주 짧게 실행되고 다시 대기 상태로 돌아가는** 스레드다. 높은 우선순위 스레드는 생애의 대부분을 무언가를 기다리며 보내야 시스템 전체의 응답성을 해치지 않는다.
>
> 사용자가 키보드의 Windows 키를 눌렀을 때 반응하는 탐색기 스레드가 좋은 예다. 키를 누르면 탐색기가 즉시 다른 낮은 우선순위 스레드들을 선점하고 메뉴를 표시한다. 사용자가 메뉴를 탐색하는 동안 각 키 입력에 빠르게 반응하고 메뉴를 갱신한 뒤, 사용자가 계속 탐색할 때까지 실행을 멈춘다.

> **⚠️ 우선순위로 동기화 문제를 해결하려 들지 마라**
>
> "스레드 A가 스레드 B보다 먼저 실행되어야 한다"를 우선순위로 표현하려는 시도는 항상 틀린다. 이유는 셋이다.
>
> 1. **우선순위는 힌트일 뿐 보장이 아니다.** `ThreadPriority.Highest`를 준 스레드가 반드시 먼저 실행된다는 보장은 없다. 스케줄러가 다른 일(객체 동기화, 스레드 전환, 스레드 이동)로 바쁘면 우선순위 레벨은 그에 맞춰 조정된다.
> 2. **Windows는 오래 실행되지 못한 스레드의 동적 우선순위를 올린다.** 낮은 우선순위 때문에 한동안 실행되지 못한 스레드도 결국은 실행된다. 즉 "낮은 우선순위 = 절대 안 돎"이 아니다.
> 3. **코어 수가 바뀌면 결과가 바뀐다.** 싱글 코어 머신에서 "동작하던" 우선순위 기반 순서 제어는 멀티 코어에서 무너진다.
>
> 순서가 필요하면 순서를 표현하는 도구를 써라 — `Join`, 신호 구성 요소(49장), 연속(46.4절).

우선순위와 잠금이 만나면 **우선순위 역전(priority inversion)** 이라는 고전적 문제가 생긴다. 낮은 우선순위 스레드가 잠금을 쥔 채 선점되고, 높은 우선순위 스레드가 그 잠금을 기다리는데, 중간 우선순위 스레드가 CPU를 계속 차지해 낮은 쪽이 잠금을 놓지 못하는 상황이다. 진단과 대응은 48.8절에서 다룬다.

> **📌 스레드 풀 스레드의 우선순위**
>
> 스레드 풀 스레드의 우선순위는 자유롭게 바꿀 수 있고, 풀로 반환될 때 정상 우선순위로 복원된다. 다만 **우선순위 변경이 스레드 풀 연산 사이에 유지되지 않는다**는 뜻이므로, 우선순위가 중요한 작업이라면 애초에 풀을 쓸 대상이 아니다(45.9절).

## 45.8 리치 클라이언트 애플리케이션의 스레딩과 동기화 컨텍스트

### UI 스레드가 특별한 이유

WPF, UWP, Windows Forms 애플리케이션에서 주 스레드는 단순한 실행 흐름이 아니다. 이 스레드는 **메시지 루프(message loop)** 를 돌린다. 메시지 루프는 렌더링을 수행하고 키보드·마우스 이벤트를 처리한다.

그래서 주 스레드에서 오래 걸리는 작업을 실행하면 애플리케이션이 응답하지 않게 된다. 메시지 루프가 돌지 않으니 화면이 갱신되지 않고 입력이 처리되지 않는다.

해결의 방향은 명확하다. 시간이 걸리는 작업을 "워커" 스레드로 밀어내고, 끝나면 UI를 갱신한다. 그런데 여기서 벽에 부딪힌다.

> **모든 리치 클라이언트 애플리케이션은 UI 요소와 컨트롤을 그것을 만든 스레드(대개 주 UI 스레드)에서만 접근할 수 있다는 스레딩 모델을 갖는다. 이를 위반하면 예측할 수 없는 동작이 일어나거나 예외가 던져진다.**

이유는 역사에 있다. Windows 컨트롤은 COM의 **단일 스레드 아파트먼트(STA, single-threaded apartment) 모델**을 쓴다. 하부 컨트롤이 아파트먼트 스레드 방식이기 때문이다. 게다가 많은 컨트롤이 여러 동작에 메시지 펌프를 쓴다. 이 모델은 각 컨트롤에 대한 모든 함수 호출이 **그 컨트롤을 만든 스레드에서** 일어나야 한다고 말한다. .NET 코드 아래에는 여전히 Win32 API와 윈도 메시지가 도사리고 있고, WPF에서도 이 레거시 동작은 계속된다.

이것이 WPF 애플리케이션의 진입점에 `[STAThread]` 특성이 붙는 이유다.

```csharp
[STAThread]
static void Main()
{
    // ...
}
```

### 마샬링 — 요청을 UI 스레드로 넘기기

워커 스레드에서 UI를 갱신하려면 요청을 UI 스레드로 **전달(마샬marshal)** 해야 한다. 저수준 방법은 다음과 같다.

| 프레임워크 | 비동기(큐에 넣고 반환) | 동기(처리될 때까지 블로킹) |
|---|---|---|
| WPF | `Dispatcher.BeginInvoke` | `Dispatcher.Invoke` |
| UWP | `Dispatcher.RunAsync` | `Dispatcher.Invoke` |
| Windows Forms | `Control.BeginInvoke` | `Control.Invoke` |
| 공통 추상화 | `SynchronizationContext.Post` | `SynchronizationContext.Send` |

이 메서드들은 모두 실행하려는 메서드를 참조하는 델리게이트를 받는다. `BeginInvoke`/`RunAsync`는 델리게이트를 **UI 스레드의 메시지 큐**(키보드·마우스·타이머 이벤트를 처리하는 바로 그 큐)에 넣는 방식으로 동작한다. `Invoke`는 같은 일을 하되 메시지가 UI 스레드에 의해 읽히고 처리될 때까지 블로킹한다. 그래서 `Invoke`는 메서드에서 반환값을 받을 수 있다.

반환값이 필요 없다면 **`BeginInvoke`/`RunAsync`가 낫다.** 호출자를 블로킹하지 않고 데드락 가능성을 만들지 않기 때문이다.

> **📌 `Application.Run`은 개념적으로 이런 루프다**
>
> ```text
> while (!thisApplication.Ended)
> {
>     메시지 큐에 뭔가 나타날 때까지 기다린다
>     뭔가 왔다: 어떤 종류의 메시지인가?
>       키보드/마우스 메시지     -> 이벤트 핸들러를 발동한다
>       사용자 BeginInvoke 메시지 -> 델리게이트를 실행한다
>       사용자 Invoke 메시지      -> 델리게이트를 실행하고 결과를 게시한다
> }
> ```
>
> 워커 스레드가 델리게이트를 UI 스레드로 마샬링할 수 있게 해주는 것이 바로 이 루프다.

### 예제 — WPF

시간이 걸리는 작업 후 텍스트 박스를 갱신하는 코드다.

```csharp
partial class MyWindow : Window
{
    public MyWindow()
    {
        InitializeComponent();
        new Thread(Work).Start();
    }

    void Work()
    {
        Thread.Sleep(5000);          // 시간이 걸리는 작업을 흉내 낸다
        UpdateMessage("The answer");
    }

    void UpdateMessage(string message)
    {
        Action action = () => txtMessage.Text = message;
        Dispatcher.BeginInvoke(action);
    }
}
```

실행하면 창이 즉시 나타나고 응답한다. 5초 뒤에 텍스트 박스가 갱신된다.

Windows Forms에서는 (Form의) `BeginInvoke`를 부른다는 점만 다르다.

```csharp
void UpdateMessage(string message)
{
    Action action = () => txtMessage.Text = message;
    this.BeginInvoke(action);
}
```

### `Invoke`가 실제로 하는 일

`Control.Invoke`의 내부 동작을 알아 두면 왜 이 호출이 비싼지, 왜 데드락을 만들 수 있는지가 분명해진다. 원천의 설명을 요약하면 이렇다.

1. 먼저 특수 경우 처리 — **이미 컨트롤과 같은 스레드에서 실행 중이라면** 프레임워크가 그냥 델리게이트를 호출한다(단락 경로).
2. 그렇지 않으면, 델리게이트를 호출하는 데 필요한 모든 것을 담는 비공개 구조체를 만든다. 여기에는 **모든 인자, 호출 스택 참조, 델리게이트 대상**이 들어간다. 인자는 **복사된다** — 멀티스레드 세계이므로 대상 델리게이트가 호출되기 전에 인자 값이 바뀌는 것을 막기 위해서다.
3. 이 구조체를 큐에 추가하고, 대상 컨트롤에 메시지를 게시한다.
4. UI 스레드가 메시지를 처리하고 델리게이트를 호출하기를 기다리며 **스핀 대기와 슬립을 조합**한다.
5. 델리게이트가 던진 예외는 UI 스레드에서 `try`/`catch`로 잡혀 구조체에 복사되고, UI 스레드의 처리가 끝난 뒤 **워커 스레드에서 다시 던져진다**.

메서드 하나를 호출하는 데 이만큼의 처리가 든다. `BeginInvoke`는 4단계와 5단계를 생략하고 메시지를 게시한 즉시 반환한다.

> **⚠️ `Invoke` 메시지 하나가 큐 전체를 비운다**
>
> 대상 컨트롤이 `Invoke` 메시지를 처리할 때, 델리게이트 하나만 처리하는 것이 아니다. **큐에 있는 모든 `Invoke` 델리게이트를 처리한다.** 항상 동기 `Invoke`만 쓰면 이 사실이 드러나지 않지만, `Invoke`와 `BeginInvoke`를 섞으면 동작이 달라진다.
>
> `BeginInvoke`로 델리게이트를 큐에 넣은 뒤 나중에 `Invoke`를 호출하면, 그 `Invoke`가 앞서 `BeginInvoke`로 넣어 둔 것들까지 전부 처리한다. 즉 대기 중이던 델리게이트가 `Invoke` 델리게이트보다 먼저 실행되며 프로그램 상태를 바꿀 수 있다.
>
> 따라서 **`Invoke` 델리게이트 안에서 프로그램 상태를 다시 확인하라.** `Invoke`를 호출하던 과거 시점에 넘긴 상태를 믿으면 안 된다.

> **⚠️ `BeginInvoke` 뒤의 코드가 먼저 실행된다**
>
> ```csharp
> private void OnTick(object sender, EventArgs e)
> {
>     this.BeginInvoke(new Action(() =>
>         toolStripStatusLabel1.Text = DateTime.Now.ToLongTimeString()));
>     toolStripStatusLabel1.Text += " And set more stuff";
> }
> ```
>
> 이 코드는 " And set more stuff"를 거의 보여주지 않는다. 첫 번째 변경은 메시지를 큐에 넣어 예약할 뿐이고, 실제 변경은 다음 메시지들이 처리될 때 일어난다. 그 시점은 다음 문장이 레이블에 텍스트를 덧붙인 **뒤**다.
>
> "나중에 처리한다"는 것은 **그 나중이 언제인지 통제할 수 없다**는 뜻이다.

### `InvokeRequired`의 비용

Windows Forms에서 흔히 보는 관용구는 이렇다.

```csharp
private void OnTick(object sender, EventArgs e)
{
    Action action = () => toolStripStatusLabel1.Text = DateTime.Now.ToLongTimeString();
    if (this.InvokeRequired)
        this.Invoke(action);
    else
        action();
}
```

`InvokeRequired`는 현재 코드가 컨트롤을 만든 스레드에서 실행 중인지, 아니면 다른 스레드라서 마샬링이 필요한지 판단한다. 대부분의 경우 구현은 단순하다 — 현재 스레드 ID와 해당 컨트롤의 스레드 ID를 비교한다. 비교 자체는 시간이 별로 안 든다.

그런데 흥미로운 경계 사례들이 있다.

| 상황 | `InvokeRequired`의 동작 | 비용 |
|---|---|---|
| 컨트롤이 생성됨 | 현재 스레드 ID와 컨트롤 스레드 ID를 비교 | 저렴하고 항상 안전 |
| 컨트롤이 아직 생성되지 않음 | 부모 컨트롤 트리를 거슬러 올라가 생성된 창을 찾는다 | 훨씬 오래 걸린다 |
| 어느 부모도 생성되지 않음 | **파킹 윈도(parking window)** 를 찾는다 | 더 오래 걸린다 |
| 파킹 윈도조차 없음 | 항상 `false`를 반환한다 | 오래 걸리고 **답이 틀릴 수 있다** |

마지막 경우가 위험하다. 프레임워크는 확실한 즉시 실패 대신 가능한 나중의 실패를 택한 것이다. 실무에서는 드문 상황이며, WPF의 `Dispatcher`에는 이 상황을 막는 추가 코드가 들어 있다.

정리하면, **컨트롤이 일단 생성되고 나면 `InvokeRequired`는 충분히 빠르고 항상 안전하다.** 그리고 `Control.InvokeRequired`가 다소 비싸더라도, 필요 없는데 `Control.Invoke`를 부르는 것보다는 훨씬 싸다.

WPF에는 `InvokeRequired`가 없다. 대신 현재 스레드와 컨트롤 상호작용이 일어나야 할 스레드를 직접 비교한다.

```csharp
private void UpdateTime()
{
    Action action = () => textBlock1.Text = DateTime.Now.ToString();
    if (Thread.CurrentThread != textBlock1.Dispatcher.Thread)
        textBlock1.Dispatcher.Invoke(DispatcherPriority.Normal, action);
    else
        action();
}
```

`DispatcherObject`는 많은 WPF 컨트롤의 기반 클래스이며 스레드 간 디스패치 연산을 처리한다. 각 스레드는 디스패처를 갖는다. 컨트롤에 디스패처를 처음 요청하면 라이브러리가 그 스레드에 이미 디스패처가 있는지 보고, 있으면 그것을 반환하고 없으면 새로 만들어 컨트롤과 그 스레드에 연결한다.

> **📌 WPF에서 우선순위를 지정할 수 있는 이유**
>
> WPF에서는 이벤트 핸들러 액션의 우선순위(`DispatcherPriority`)를 지정할 수 있다. WPF 애플리케이션이 **두 개의 UI 스레드**를 쓰기 때문이다. 한 스레드가 UI 렌더링 파이프라인을 처리해 애니메이션 같은 동작이 계속 렌더링될 수 있게 한다. 우선순위를 지정하면 렌더링과 특정 배경 이벤트 처리 중 무엇이 사용자에게 더 중요한지 통제할 수 있다.

### `SynchronizationContext` — 마샬링의 일반화

앞에서 본 마샬링 API들은 프레임워크마다 이름이 다르다. 이것들을 한 겹 위에서 일반화한 것이 `SynchronizationContext` 클래스다.

모바일과 데스크톱용 리치 클라이언트 API(UWP, WPF, Windows Forms)는 각자 `SynchronizationContext`의 하위 클래스를 정의하고 인스턴스화한다. UI 스레드에서 실행 중일 때 정적 속성 `SynchronizationContext.Current`로 그것을 얻을 수 있다. 이 속성을 캡처해 두면 나중에 워커 스레드에서 UI 컨트롤로 "게시(post)"할 수 있다.

```csharp
partial class MyWindow : Window
{
    SynchronizationContext _uiSyncContext;

    public MyWindow()
    {
        InitializeComponent();
        // 현재 UI 스레드의 동기화 컨텍스트를 캡처한다
        _uiSyncContext = SynchronizationContext.Current;
        new Thread(Work).Start();
    }

    void Work()
    {
        Thread.Sleep(5000);
        UpdateMessage("The answer");
    }

    void UpdateMessage(string message)
    {
        // 델리게이트를 UI 스레드로 마샬링한다
        _uiSyncContext.Post(_ => txtMessage.Text = message, null);
    }
}
```

이 방식이 유용한 이유는 **같은 기법이 모든 리치 클라이언트 UI API에서 동작한다**는 것이다. `Post`를 호출하는 것은 `Dispatcher`나 `Control`에서 `BeginInvoke`를 호출하는 것과 같고, `Invoke`에 해당하는 `Send` 메서드도 있다.

| `SynchronizationContext` 메서드 | 대응 | 블로킹 |
|---|---|---|
| `Post(SendOrPostCallback, object)` | `BeginInvoke` / `RunAsync` | 하지 않는다 |
| `Send(SendOrPostCallback, object)` | `Invoke` | **한다** |

> **⚠️ `SynchronizationContext.Current`는 `null`일 수 있다**
>
> 콘솔 애플리케이션, 서비스, 스레드 풀 스레드에는 동기화 컨텍스트가 설치되어 있지 않다. 그래서 `SynchronizationContext.Current`는 `null`을 반환할 수 있다.
>
> 또 하나. **이 속성은 반드시 UI 스레드에서 읽어야 한다.** 워커 스레드에서 읽어 봐야 UI의 컨텍스트가 아니다. 생성자나 `Loaded` 핸들러에서 캡처해 필드에 담아 두는 것이 관용구인 이유다.

> **⚠️ `Send`/`Invoke`는 데드락을 만들 수 있다**
>
> `Invoke`와 `Send`는 UI 스레드가 델리게이트를 처리할 때까지 호출 스레드를 블로킹한다. 그런데 UI 스레드가 그 워커 스레드를 기다리고 있다면(예를 들어 `Task.Wait()`나 `Join()`으로) 양쪽이 서로를 기다리는 **데드락**이 된다.
>
> 이 패턴은 `async`/`await`와 만나면 훨씬 흔해진다. UI 스레드에서 `.Result`나 `.Wait()`를 부르는 이른바 sync-over-async 데드락이 그것이다. 정확한 해부는 47.14절에서 다룬다.

### 여러 개의 UI 스레드

각각 다른 창을 소유한다면 **UI 스레드를 여러 개** 두는 것도 가능하다. 주된 시나리오는 Microsoft Word처럼 최상위 창이 여러 개인 애플리케이션(SDI, Single Document Interface)이다. 각 SDI 창은 대개 작업 표시줄에 별개의 "애플리케이션"으로 나타나고, 기능적으로 다른 SDI 창과 대체로 격리되어 있다. 각 창에 자기 UI 스레드를 주면 서로에 대해 더 응답성이 좋아진다.

> **💡 오늘날 이 절의 코드는 대부분 `async`/`await`로 대체된다**
>
> 이 절에서 본 `Dispatcher.BeginInvoke`, `Control.Invoke`, `SynchronizationContext.Post`는 전부 **저수준 마샬링 도구**다.
>
> `async`/`await`를 쓰면 컴파일러가 만드는 상태 기계가 동기화 컨텍스트를 자동으로 캡처하고 `await` 이후의 코드를 원래 컨텍스트로 되돌려 준다. UI 코드에서 `await`가 마법처럼 보이는 이유가 바로 이것이다 — 마법이 아니라 이 절의 메커니즘을 컴파일러가 대신 호출해 주는 것이다.
>
> 그래도 이 절을 이해해야 하는 이유는 둘이다. (1) `ConfigureAwait(false)`가 무엇을 끄는 것인지 알려면 무엇이 켜져 있는지 알아야 한다(47.12절). (2) 데드락이 났을 때 콜 스택에서 `Send`와 `Invoke`를 알아볼 수 있어야 한다.
>
> UI 스레드 모델의 실무 패턴은 51.5절에서 다시 다룬다.

## 45.9 스레드를 직접 만들면 안 되는 이유

### 다섯 가지 이유

이 장 전체가 이 절을 위한 준비였다. `new Thread(...)`를 쓰지 말아야 하는 이유를 정리한다.

#### 1. 생성 비용이 크다

45.4절에서 본 대로 스레드 하나에는 커널 객체, TEB, 사용자 모드 스택 1MB 예약, 커널 모드 스택, (Windows에서는) 로드된 모든 비관리 DLL에 대한 통지가 따라붙는다. 원천의 한 저자는 스레드를 시작할 때마다 **새 지역 변수 스택 등을 준비하는 데 수백 마이크로초**가 쓰인다고 기술한다.

#### 2. 개수가 늘면 컨텍스트 스위치 스래싱이 온다

**오버서브스크립션(oversubscription)** — CPU 코어보다 활성 스레드가 많아 OS가 스레드를 타임슬라이싱해야 하는 상태 — 은 성능을 해친다. 타임슬라이싱에는 비싼 컨텍스트 스위치가 필요하고, 현대 프로세서의 성능을 떠받치는 **CPU 캐시를 무효화**하기 때문이다.

원천의 실측이 이 지점을 잘 보여준다. 계산 알고리즘을 단일 스레드, 수동 생성 스레드, 스레드 풀, `Task` 기반으로 각각 실행해 비교한 결과다.

| 접근 | 관찰된 특성 |
|---|---|
| 수동 생성 스레드 | 스레드 풀·`Task`보다 오버헤드가 훨씬 크다. **10개를 넘으면 스레딩 오버헤드가 주된 성능 병목**이 된다 |
| 스레드 풀 (`QueueUserWorkItem`) | **40개가 넘는 작업을 큐에 넣어야** 오버헤드가 작업 시간을 지배하기 시작한다(듀얼 코어 노트북 기준) |
| `Task` 기반 | 고정된 상수 오버헤드가 있어 작업 수가 적을 때는 느리지만, 요청 태스크 수가 늘어날수록 스레드 수를 가장 잘 관리한다 |

수치 자체보다 **기울기**가 중요하다. 수동 스레드는 개수가 늘수록 급격히 나빠지고, 풀 기반은 훨씬 완만하다.

#### 3. 스택 메모리를 붙든다

수백~수천 개의 동시 I/O 바운드 연산을 실행해야 한다면, 스레드 기반 접근은 **순전히 스레드 오버헤드로만 수백~수천 메가바이트의 메모리를 소비한다.** 그 메모리는 사용자의 문서 같은 더 중요한 데이터에 쓰일 수 있었던 것이다.

#### 4. 취소·예외·결과 반환이 전부 수작업이다

스레드는 동시성을 만드는 저수준 도구이고, 그만큼 제약이 많다.

- 스레드에 데이터를 넣기는 쉽지만, **`Join`한 스레드에서 "반환값"을 얻어 낼 쉬운 방법이 없다.** 어떤 공유 필드를 마련해야 한다.
- 연산이 예외를 던지면 그것을 **잡아서 전파하는 일도 똑같이 고통스럽다**(45.6절).
- 스레드가 끝났을 때 다른 일을 시작하라고 지시할 수 없다. 대신 `Join`해야 하고, 그 과정에서 자기 스레드를 블로킹한다.
- 취소를 하려면 협력적 취소 프로토콜을 직접 구현해야 한다(46.8절). `Abort`는 답이 아니다.

이 제약들은 **세밀한 단위의 동시성(fine-grained concurrency)을 억누른다.** 작은 동시 연산들을 합성해 큰 동시 연산을 만드는 것이 어려워지고, 그 결과 수동 동기화(잠금, 신호)에 더 많이 의존하게 되며, 그와 함께 오는 문제들도 따라온다.

#### 5. 최적 스레드 수를 알 수 없다

애플리케이션에 몇 개의 스레드가 최적인지는 알 수 없다. 오늘 여러 코어를 가진 머신에서 돌더라도, 지금 가정한 코어 수는 6개월 뒤에 거의 확실히 틀린다. 게다가 CLR이 자기 작업(가비지 컬렉터 같은)을 위해 만드는 스레드 수는 통제할 수 없다. ASP.NET이나 REST 서비스 같은 서버 애플리케이션에서는 새 요청마다 다른 스레드가 처리한다.

반면 **.NET 스레드 풀은 대상 시스템에서 활성 스레드 수를 최적화하는 데 필요한 지식을 전부 갖고 있다.**

### 스레드 풀과 `Task`가 이 모두를 해결한다

| 문제 | 스레드 풀·`Task`의 해결 |
|---|---|
| 생성·소멸 비용 | 미리 만들어 재사용 가능한 스레드 풀. 작업이 끝나면 스레드는 파괴되지 않고 준비 상태로 돌아간다 |
| 오버서브스크립션 | CLR이 하드웨어 코어 수만큼 동시 태스크로 시작한 뒤 hill-climbing 알고리즘으로 동시성 수준을 조율한다(46.2절) |
| 스택 메모리 | 스레드 수 자체가 억제되므로 총 스택 소비가 제한된다 |
| 결과 반환 | `Task<TResult>.Result` |
| 예외 전파 | 태스크가 예외를 담고, `Wait()`/`Result`에서 다시 던진다(46.4절) |
| 완료 후 작업 연결 | 연속(continuation)으로 합성한다(46.4절) |
| 취소 | `CancellationToken` 프로토콜(46.8절) |
| I/O 대기 중 스레드 점유 | `TaskCompletionSource`와 비동기 함수가 콜백 기반으로 스레드를 반납한다(47장) |

가장 짧은 비교는 이것이다.

```csharp
// 스레드를 직접 만드는 방법
new Thread(() => Console.WriteLine("Foo")).Start();

// 스레드 풀을 쓰는 방법
Task.Run(() => Console.WriteLine("Foo"));
```

거의 같아 보이지만, 두 번째 코드는 위 표의 모든 항목을 무료로 가져온다.

> **⚠️ 스레드를 늘리면 처리량이 는다는 착각**
>
> 개발자들이 스레드 풀의 최대 스레드 수를 인위적으로 제한하거나 반대로 크게 늘리려는 유혹에 자주 빠진다. 원천의 저자는 이것을 강하게 만류한다.
>
> "애플리케이션이 쓸 수 있는 메모리 양을 제한하겠다거나 네트워크 대역폭을 제한하겠다고 시스템에 알리며 애플리케이션을 시작한 적이 있는가? 그런데 왜 스레드 풀의 스레드 수는 제한하려 드는가?"
>
> 애플리케이션이 수백~수천 개의 스레드를 필요로 한다고 생각된다면, **애플리케이션의 아키텍처와 스레드 사용 방식에 심각하게 잘못된 것이 있다.**
>
> 스레드 풀 파라미터를 만지기 전에 반드시 측정하라. 스레드 사용량과 컨텍스트 스위치를 성능 카운터로 관찰하는 것이 먼저다(67장, 73장).

### 그렇다면 언제 직접 만드는가

전용 스레드를 명시적으로 만들어야 하는 경우가 아주 드물게 있다. 대체로 **스레드 풀 스레드에게는 정상이 아닌 특정 상태**를 요구하는 코드를 실행할 때다.

| 상황 | 이유 | 관련 절 |
|---|---|---|
| **정상이 아닌 우선순위**가 필요하다 | 모든 스레드 풀 스레드는 Normal 우선순위로 돈다. 바꿀 수는 있지만 권장되지 않으며, 변경이 스레드 풀 연산 사이에 유지되지 않는다 | 45.7절 |
| **포그라운드 스레드**로 동작해야 한다 | 작업이 끝날 때까지 애플리케이션이 죽지 않게 해야 한다. 스레드 풀 스레드는 항상 백그라운드이고, CLR이 프로세스를 끝내려 하면 작업을 완료하지 못할 수 있다 | 45.7절 |
| **극단적으로 오래 걸리는** 컴퓨트 바운드 작업 | 스레드를 추가로 만들지 결정하려는 스레드 풀의 로직에 부담을 주지 않는다 | 46.2절 |
| **특정 스택 크기**가 필요하다 | 깊은 재귀를 도는 파서 등. `Thread(ThreadStart, int maxStackSize)` 생성자 | 45.4절 |
| **특정 아파트먼트 모델**이 필요하다 | STA를 요구하는 COM 컴포넌트를 호출해야 한다 | 60.12절 |
| **장수명 전용 스레드** | 애플리케이션 수명 내내 하나의 루프를 도는 디스패처·펌프 같은 것 | — |

> **⚠️ `TaskCreationOptions.LongRunning`도 만능이 아니다**
>
> 오래 걸리거나 블로킹하는 작업이라면 스레드 풀 스레드를 쓰지 않도록 다음처럼 요청할 수 있다.
>
> ```csharp
> Task task = Task.Factory.StartNew(() => { /* ... */ },
>                                   TaskCreationOptions.LongRunning);
> ```
>
> 장수명 태스크 **하나**를 이렇게 돌리는 것은 문제를 일으키지 않는다. 문제는 여러 개의 장수명 태스크를 (특히 블로킹하는 것들을) 병렬로 돌릴 때다. 그리고 그런 경우에는 대개 더 나은 해결책이 있다.
>
> - 태스크가 **I/O 바운드**라면 `TaskCompletionSource`와 비동기 함수로 스레드 대신 콜백(연속)을 써서 동시성을 구현한다(46.5절, 47장).
> - 태스크가 **컴퓨트 바운드**라면 프로듀서/컨슈머 큐로 그 태스크들의 동시성을 조절해 다른 스레드와 프로세스의 기아를 피한다(51.1절).

### 결정 순서도

```text
              동시에 실행할 일이 있다
                       │
        ┌──────────────┴──────────────┐
        │                             │
   I/O를 기다리는가?            계산을 하는가?
        │                             │
        ▼                             ▼
  async/await                  Task.Run / Parallel
  (47장)                       (46장 / 50장)
        │                             │
        └──────────────┬──────────────┘
                       │
            그래도 안 되는 이유가 있는가?
                       │
        ┌──────────────┴──────────────┐
        │ 아니오                       │ 예
        ▼                             ▼
   여기서 끝. 스레드를        우선순위 / 포그라운드 /
   만들지 마라.               스택 크기 / STA /
                              장수명 전용 루프인가?
                                      │
                          ┌───────────┴───────────┐
                          │ 예                     │ 아니오
                          ▼                        ▼
                   new Thread(...)          설계를 다시 보라
```

> **💡 스레드를 만들기 전에 대답해야 할 질문**
>
> 1. 이 작업은 I/O를 기다리는가? — 그렇다면 스레드가 필요 없다. 47장을 보라.
> 2. 이 작업은 밀리초 단위로 끝나는가? — 그렇다면 `Task.Run`이 맞다.
> 3. 스레드 풀 스레드에게는 없는 어떤 속성이 필요한가? — 그 속성의 이름을 말할 수 없다면 만들지 마라.
> 4. 이 스레드는 몇 개나 만들어지는가? — 개수가 입력 데이터에 비례한다면 설계가 틀렸다.
> 5. 이 스레드는 언제, 어떻게 끝나는가? — 답할 수 없다면 만들지 마라.

이 장의 결론을 원천의 문장으로 옮기면 이렇다. **스레드는 아껴서 사용해야 하는 아주 비싼 리소스다. 그 목표를 달성하는 최선의 방법은 스레드 풀을 쓰는 것이다.** 스레드 풀은 스레드 생성과 소멸을 자동으로 관리하며, 여러 작업에 재사용되는 스레드 집합을 만들어 애플리케이션이 아주 적은 수의 스레드로 모든 일을 해낼 수 있게 한다.

그것이 46장의 주제다.

## 이 장의 요약

- **스레드는 CPU를 가상화한다.** 프로세스가 주소 공간을 격리해 데이터 손상과 보안 문제를 풀었다면, 스레드는 CPU를 분할해 응답성 문제를 풀었다. 선점형 멀티태스킹 덕분에 무한 루프에 빠진 코드가 있어도 시스템 전체가 멈추지 않는다. 대가는 컨텍스트 스위치라는 **순수한 오버헤드**다.
- **스레드를 쓸 이유는 응답성과 확장성 둘뿐이다.** 응답성은 코어가 하나여도 얻지만 전체 처리 시간은 오히려 늘어난다. 확장성은 코어가 여러 개일 때만 얻는다. 그 외의 이유로 스레드를 만들고 있다면 이유를 다시 생각해야 한다.
- **`Thread` 객체 생성은 가볍고 `Start`가 비싸다.** 물리적 OS 스레드는 `Start`에서 만들어지며, 그때 커널 객체(x64에서 컨텍스트만 약 1,240바이트), TEB 4KB, 사용자 모드 스택 1MB 예약, 커널 모드 스택 24KB(64비트), 그리고 Windows에서는 로드된 모든 비관리 DLL에 대한 `DLL_THREAD_ATTACH` 통지가 발생한다.
- **블로킹은 "멈춰 있다"가 아니라 "CPU를 쓰지 않는다"이다.** 블로킹된 스레드는 즉시 타임슬라이스를 반납하고 조건이 만족될 때까지 프로세서 시간을 소비하지 않는다. `Sleep(0)`과 `Yield()`는 대기 상태로 들어가지 않고 타임슬라이스만 양보하며, `Sleep(1)` 이상은 진짜로 블로킹한다. 스핀 대기는 I/O 바운드 연산을 컴퓨트 바운드로 바꿔 버린다.
- **CLR 스레드는 현재 구현에서 OS 스레드와 1:1이지만 그것이 명세는 아니다.** 논리 스레드와 물리 스레드가 개념적으로 분리되어 있다는 흔적이 `CurrentManagedThreadId`와 `ProcessThread.Id`, `BeginThreadAffinity`/`EndThreadAffinity`에 남아 있다. 두 ID를 혼동하면 네이티브 진단 도구의 출력과 아무것도 맞지 않는다.
- **캡처되지 않은 지역 변수만 공짜로 안전하다.** 각 스레드가 자기 스택을 가지므로 지역 변수는 자동으로 분리되지만, 람다가 캡처하는 순간 디스플레이 클래스의 필드가 되어 힙으로 옮겨 가고 공유 상태가 된다. 필드와 정적 필드는 말할 것도 없다.
- **`[ThreadStatic]`의 이니셜라이저는 한 스레드에서만 돈다.** 정적 생성자를 실행한 스레드만 초기값을 보고 나머지는 기본값을 본다. `ThreadLocal<T>`는 값 팩터리로 이 문제를 해결하고 인스턴스 필드에도 쓸 수 있지만, 접근 비용이 20~40배 비싸고 `Dispose`하지 않으면 누수한다.
- **`for` 루프의 인덱스를 캡처해 스레드에 넘기면 결과가 비결정적이다.** `foreach`는 C# 5부터 반복마다 새 변수를 선언하도록 바뀌었지만 `for`는 그대로다. 임시 변수로 복사하는 것이 유일한 해법이다.
- **스레드에서 던진 예외는 호출한 쪽으로 전파되지 않는다.** 스레드를 만든 시점의 `try`/`catch`는 아무 관련이 없고, 처리되지 않은 예외는 프로세스를 종료시킨다. 전역 처리기(`DispatcherUnhandledException` 등)도 워커 스레드는 구해 주지 않는다. **모든 스레드 진입 메서드에 `try`/`catch`가 있어야 한다.**
- **포그라운드 스레드가 하나라도 살아 있으면 프로세스는 죽지 않는다.** 반대로 백그라운드 스레드는 프로세스 종료 시 즉시 죽고, 실행 스택의 `finally`와 `using` 블록이 **건너뛰어진다**. 명시적으로 만든 스레드는 기본이 포그라운드, 스레드 풀 스레드는 항상 백그라운드다.
- **우선순위로 동기화 문제를 풀려 들지 마라.** 우선순위는 힌트일 뿐 보장이 아니고, Windows는 오래 실행되지 못한 스레드의 동적 우선순위를 올리며, 코어 수가 바뀌면 결과도 바뀐다. 올리는 것보다 내리는 편이 낫고, Realtime 클래스는 사실상 금지다. 관리 애플리케이션은 프로세스 우선순위 클래스를 건드리면 안 된다.
- **UI 컨트롤은 만든 스레드에서만 만질 수 있다.** COM STA 모델의 유산이며 WPF에도 그대로 남아 있다. 마샬링은 WPF `Dispatcher.BeginInvoke`/`Invoke`, WinForms `Control.BeginInvoke`/`Invoke`로 하고, `SynchronizationContext`가 그것을 일반화한 추상이다. `Post`는 블로킹하지 않고 `Send`는 블로킹하며 데드락을 만들 수 있다.
- **스레드를 직접 만들면 안 되는 이유는 다섯이다** — 생성 비용, 오버서브스크립션과 컨텍스트 스위치 스래싱, 스택 메모리, 취소·예외·결과 반환의 수작업, 최적 스레드 수를 알 수 없다는 것. 수동 스레드는 10개를 넘으면 스레딩 오버헤드가 병목이 되지만 스레드 풀은 40개까지 견딘다.
- **직접 만들어도 되는 경우는 좁고 명확하다.** 정상이 아닌 우선순위, 포그라운드 동작, 특정 스택 크기, 특정 아파트먼트 모델, 애플리케이션 수명 내내 도는 장수명 전용 스레드. 이 중 어느 것도 이름 댈 수 없다면 `Task.Run`이 답이다.

## 연습 문제

1. 스레드를 1개, 4개, 16개, 64개, 256개 만들어 각각 같은 계산 작업을 나눠 실행하는 프로그램을 작성하고 총 실행 시간을 측정하라. 같은 실험을 `Task.Run`으로 반복해 두 곡선을 겹쳐 그려라. 수동 스레드 쪽에서 성능이 꺾이기 시작하는 개수가 당신의 머신에서 몇 개인지 확인하고, 그 값을 `Environment.ProcessorCount`와 비교하라.

2. `Thread.Sleep(0)`, `Thread.Yield()`, `Thread.Sleep(1)`을 각각 백만 번 호출하는 루프 세 개를 만들어 실행 시간을 측정하라. 그다음 작업 관리자나 `dotnet-counters`로 각 루프 실행 중의 CPU 사용률을 관찰하고, "블로킹된 스레드는 CPU를 소비하지 않는다"는 45.2절의 정의가 세 경우 중 어디에 해당하는지 판단하라.

3. 백그라운드 스레드 안에서 `try` / `finally`를 쓰고 `finally`에서 파일을 삭제하는 프로그램을 작성하라. 주 스레드가 즉시 끝나게 만들고 파일이 남아 있는지 확인하라. 그다음 `IsBackground = false`로 바꿔 같은 실험을 반복하고, 마지막으로 `Join(TimeSpan.FromSeconds(2))`를 넣어 세 경우의 차이를 표로 정리하라.

4. `for (int i = 0; i < 10; i++) new Thread(() => Console.Write(i)).Start();`를 열 번 실행해 출력을 모두 기록하라. 같은 코드를 `foreach (int i in Enumerable.Range(0, 10))`으로 바꿔 다시 열 번 실행하고 결과가 어떻게 달라지는지 확인하라. 두 결과의 차이를 26.10절의 디스플레이 클래스 설명으로 해석하라.

5. `[ThreadStatic]` 필드에 이니셜라이저 `= 42`를 붙이고 세 개의 스레드에서 그 값을 출력하라. 몇 개가 42를 보고 몇 개가 0을 보는지 기록한 뒤, 같은 시나리오를 `ThreadLocal<int>(() => 42)`로 바꿔 반복하라. 이어서 두 방식의 읽기 성능을 BenchmarkDotNet으로 측정해(67.3절) 원천이 보고한 20~40배 차이가 재현되는지 확인하라.

6. 워커 스레드 진입 메서드에서 `throw new InvalidOperationException()`을 던지는 콘솔 프로그램을 작성하고, 그 스레드를 만든 곳을 `try`/`catch`로 감싸도 예외가 잡히지 않으며 프로세스가 종료된다는 것을 확인하라. 그다음 `AppDomain.CurrentDomain.UnhandledException`에 핸들러를 붙여 무엇이 통지되는지, 그리고 프로세스 종료를 막을 수 있는지 관찰하라.

7. WPF 또는 Windows Forms 애플리케이션을 만들어 워커 스레드에서 컨트롤의 속성을 직접 대입해 보라. 어떤 예외가 어떤 메시지와 함께 발생하는지 정확히 기록하고, 같은 갱신을 `Dispatcher.BeginInvoke`(또는 `Control.BeginInvoke`)와 `SynchronizationContext.Post`로 각각 바꿔 세 코드의 콜 스택을 디버거로 비교하라.
