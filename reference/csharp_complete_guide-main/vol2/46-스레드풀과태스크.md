## 46.1 CLR 스레드 풀의 구조 — 전역 큐, 로컬 큐, 워크 스틸링

### 풀이 존재하는 이유

45.4절에서 본 대로 스레드를 만들고 파괴하는 일은 시간 면에서 비싸다. 게다가 스레드가 많으면 메모리를 낭비하고, 실행 가능한 스레드들 사이를 OS가 스케줄링하고 컨텍스트 스위치하느라 성능까지 깎인다. 이 상황을 개선하려고 CLR은 **자기 스레드 풀을 관리하는 코드**를 내장하고 있다.

스레드 풀은 애플리케이션이 쓸 수 있게 준비된 스레드의 집합이라고 생각하면 된다. **CLR 하나당 스레드 풀 하나**가 있다. .NET Framework에서는 그 CLR이 제어하는 모든 AppDomain이 이 풀 하나를 공유했고, 한 프로세스에 여러 CLR이 로드되면 각 CLR이 자기 풀을 따로 가졌다.

CLR이 초기화될 때 풀에는 스레드가 **하나도 없다**. 풀은 내부적으로 연산 요청의 큐를 유지한다. 애플리케이션이 비동기 연산을 수행하려고 하면, 큐에 항목 하나를 덧붙이는 메서드를 호출한다. 풀의 코드가 이 큐에서 항목을 꺼내 풀 스레드에 디스패치한다. 풀에 스레드가 없으면 새로 만든다.

여기까지는 직접 스레드를 만드는 것과 다를 게 없어 보인다. 차이는 그다음이다. **풀 스레드가 작업을 끝내면 그 스레드는 파괴되지 않는다.** 대신 풀로 돌아가 다음 요청을 기다리며 유휴 상태로 앉아 있는다. 스레드가 자살하지 않으므로 파괴 비용이 추가로 들지 않는다.

애플리케이션이 풀에 요청을 많이 던지면, 풀은 **일단 그 하나의 스레드로 전부 처리하려고 시도한다.** 스레드 하나가 감당할 수 있는 속도보다 빠르게 요청이 쌓이면 그때 스레드를 추가한다. 결국 애플리케이션은 적은 수의 스레드로 모든 요청을 처리할 수 있는 지점에 도달하고, 풀은 스레드를 많이 만들 필요가 없어진다.

반대로 애플리케이션이 요청을 멈추면 풀에는 아무 일도 하지 않는 스레드가 잔뜩 남는다. 이건 메모리 자원 낭비다. 그래서 풀 스레드가 일정 시간(CLR 버전마다 다르다) 할 일 없이 유휴 상태였다면, 그 스레드는 스스로 깨어나 **자기를 죽여** 자원을 반납한다. 죽는 순간 성능 손실이 있지만, 애초에 죽는 이유가 유휴 상태였기 때문이라 애플리케이션이 일을 많이 하고 있지 않다는 뜻이므로 문제되지 않는다.

> **📌 스레드 풀의 미덕은 "긴장 관리"다**
>
> 스레드가 적으면 자원을 아끼지만 멀티프로세서·하이퍼스레딩·멀티코어를 활용하지 못한다. 스레드가 많으면 그 반대다. 풀은 이 긴장을 **휴리스틱**으로 관리한다. 작업이 많고 CPU가 남으면 스레드를 늘리고, 작업량이 줄면 스레드가 스스로 죽는다. 이 판단을 애플리케이션 코드가 손으로 하는 것보다 잘하기는 어렵다.

### 가장 낮은 층 — `ThreadPool.QueueUserWorkItem`

컴퓨트 바운드 비동기 연산을 풀에 큐잉하는 가장 원시적인 방법은 `ThreadPool` 클래스의 다음 메서드다.

```csharp
static bool QueueUserWorkItem(WaitCallback callBack);
static bool QueueUserWorkItem(WaitCallback callBack, object state);
```

두 메서드 모두 "작업 항목(work item)"과 선택적 상태 데이터를 풀의 큐에 넣고 **즉시 반환한다**. 작업 항목은 그저 `callBack` 매개변수가 가리키는 메서드이고, 이 메서드는 풀 스레드가 호출한다. 상태 데이터를 받지 않는 오버로드는 콜백에 `null`을 넘긴다. 콜백 메서드는 `System.Threading.WaitCallback` 델리게이트 타입과 시그니처가 맞아야 한다.

```csharp
delegate void WaitCallback(object state);
```

실제로 써 보자.

```csharp
using System;
using System.Threading;

public static class Program
{
    public static void Main()
    {
        Console.WriteLine("주 스레드: 비동기 연산을 큐잉한다");
        ThreadPool.QueueUserWorkItem(ComputeBoundOp, 5);
        Console.WriteLine("주 스레드: 여기서 다른 일을 한다...");
        Thread.Sleep(10000);            // 다른 작업 시뮬레이션 (10초)
        Console.WriteLine("<Enter>를 누르면 종료한다...");
        Console.ReadLine();
    }

    // 이 메서드의 시그니처는 WaitCallback 델리게이트와 일치해야 한다
    private static void ComputeBoundOp(object state)
    {
        // 이 메서드는 스레드 풀 스레드가 실행한다
        Console.WriteLine($"ComputeBoundOp 안: state={state}");
        Thread.Sleep(1000);             // 다른 작업 시뮬레이션 (1초)
        // 이 메서드가 반환하면 스레드는 풀로 돌아가
        // 다음 작업을 기다린다
    }
}
```

출력은 이렇게 나올 수도 있고,

```text
주 스레드: 비동기 연산을 큐잉한다
주 스레드: 여기서 다른 일을 한다...
ComputeBoundOp 안: state=5
```

이렇게 나올 수도 있다.

```text
주 스레드: 비동기 연산을 큐잉한다
ComputeBoundOp 안: state=5
주 스레드: 여기서 다른 일을 한다...
```

두 메서드가 서로 비동기적으로 실행되기 때문이다. 어느 쪽을 먼저 스케줄할지는 Windows 스케줄러가 정하고, 멀티 CPU 머신이라면 둘을 동시에 스케줄할 수도 있다.

> **⚠️ 풀 스레드에서 새어 나간 예외는 프로세스를 죽인다**
>
> 콜백 메서드가 던진 예외를 아무도 처리하지 않으면 CLR은 **프로세스를 종료한다**(호스트가 자체 정책을 강제하지 않는 한). 32.14절에서 본 규칙이 그대로 적용된다. `Task`는 이 동작이 다르다 — 태스크의 예외는 삼켜져 저장되며, 그 차이가 46.11절에서 다룰 "관찰되지 않은 예외" 문제를 낳는다.

> **📌 `WaitCallback`, `TimerCallback`, `ParameterizedThreadStart`는 시그니처가 같다**
>
> 세 델리게이트 모두 `void M(object state)` 형태다. 이 시그니처에 맞는 메서드 하나를 정의하면 `ThreadPool.QueueUserWorkItem`으로도, `System.Threading.Timer`로도, `Thread` 객체로도 호출할 수 있다. 델리게이트 타입은 다르지만 호환되는 메서드 그룹 변환이 성립하기 때문이다(26장).

### 전역 큐와 스레드별 로컬 큐

여기서부터가 이 절의 핵심이다. 풀에는 큐가 하나가 아니다.

```text
                    ┌─────────────────────── CLR 스레드 풀 ───────────────────────┐
                    │                                                             │
  비워커 스레드      │   ┌──────────────────────────────┐                          │
  (Main / UI /   ───┼──▶│  전역 큐 (Global Queue)       │  FIFO · 락 필요           │
   Timer 스레드)     │   │  [ W ][ W ][ W ][ W ]        │◀───────────┐             │
                    │   └──────────────────────────────┘            │             │
                    │                                     (3) 훔칠 것도 없으면      │
                    │   ┌───────────────┐   ┌───────────────┐       │             │
                    │   │  로컬 큐 1     │   │  로컬 큐 n     │──────┘             │
                    │   │  [T][T][T]    │   │  [T]          │                     │
                    │   └───────────────┘   └───────────────┘                     │
                    │   head↑        tail↓  head↑        tail↓                    │
                    │   LIFO·락 없음  훔치기  LIFO·락 없음  훔치기                   │
                    │        │            ▲       │                               │
                    │        │            └───────┼──── (2) 남의 큐 꼬리에서 훔친다  │
                    │        ▼   (1) 내 큐 머리부터 ▼                               │
                    │   ┌───────────────┐   ┌───────────────┐                     │
                    │   │  워커 스레드 1 │   │  워커 스레드 n │                     │
                    │   └───────────────┘   └───────────────┘                     │
                    └─────────────────────────────────────────────────────────────┘
```

**전역 큐**부터 보자. `ThreadPool.QueueUserWorkItem` 메서드와 `Timer` 클래스는 **항상** 작업 항목을 전역 큐에 넣는다. 워커 스레드들은 이 큐에서 **선입선출(FIFO)** 알고리즘으로 항목을 꺼내 처리한다. 여러 워커가 동시에 전역 큐에서 항목을 꺼낼 수 있으므로, 두 스레드가 같은 항목을 가져가지 않도록 모든 워커가 **스레드 동기화 락을 두고 경합한다**. 이 락은 어떤 애플리케이션에서는 병목이 되어 확장성과 성능을 어느 정도 제한한다.

이제 기본 `TaskScheduler`(`TaskScheduler.Default`)로 스케줄되는 `Task` 객체를 보자. 규칙은 **누가 스케줄했느냐**에 달려 있다.

- **비워커 스레드**가 `Task`를 스케줄하면 그 태스크는 **전역 큐**에 들어간다.
- **워커 스레드**가 `Task`를 스케줄하면 그 태스크는 **호출 스레드의 로컬 큐**에 들어간다.

워커 스레드가 항목을 처리할 준비가 되면 **항상 자기 로컬 큐부터 확인한다.** 태스크가 있으면 로컬 큐에서 꺼내 처리한다. 이때 워커는 로컬 큐에서 **후입선출(LIFO)** 알고리즘으로 태스크를 꺼낸다. 자기 로컬 큐의 머리(head)에 접근할 수 있는 스레드는 자기 자신뿐이므로 **스레드 동기화 락이 필요 없고**, 큐에 넣고 빼는 일이 매우 빠르다.

이 동작의 부작용은 명확하다. **태스크가 큐잉된 순서의 역순으로 실행된다.**

> **⚠️ 실행 순서를 가정하는 코드는 언젠가 반드시 깨진다**
>
> 스레드 풀은 큐잉된 항목이 처리되는 순서를 **한 번도 보장한 적이 없다.** 여러 스레드가 항목을 동시에 처리할 수 있다는 것만으로도 이미 그렇다. 그런데 로컬 큐의 LIFO 동작은 이 문제를 한층 더 노골적으로 만든다. 작업 항목이나 `Task`가 실행되는 순서에 대해 애플리케이션이 **어떤 기대도 갖지 않도록** 만들어야 한다. 순서가 필요하면 순서를 코드로 강제하라 — 연속(46.4절), `await`의 순차 실행(47장), 또는 `Channel`·`BlockingCollection`(50.11절) 같은 명시적 파이프라인을 써야 한다.

> **💡 왜 로컬 큐는 하필 LIFO인가**
>
> 두 가지 이유가 겹친다.
>
> 첫째, **캐시 지역성**이다. 방금 큐에 넣은 작업이 만지는 데이터는 방금 그 스레드가 만졌던 데이터일 가능성이 높고, 그 데이터는 아직 이 코어의 L1/L2 캐시에 살아 있을 확률이 높다. 가장 최근 것부터 꺼내면 캐시 미스가 줄어든다.
>
> 둘째, **작업 트리의 깊이 우선 순회**가 된다. 분할 정복 알고리즘이 하위 작업을 계속 큐잉할 때, LIFO는 방금 만든 하위 작업을 바로 처리하므로 트리를 깊이 우선으로 내려간다. FIFO였다면 너비 우선이 되어 대기 중인 작업 항목이 폭발적으로 늘어난다. 이건 메모리 사용량의 문제다.

### 워크 스틸링

워커 스레드가 자기 로컬 큐가 비어 있는 것을 발견하면, **다른 워커 스레드의 로컬 큐에서 태스크를 훔치려고 시도한다.** 이것이 **워크 스틸링(work stealing)** 이다.

태스크는 로컬 큐의 **꼬리(tail)** 에서 훔쳐 오며, 이때는 스레드 동기화 락을 잡아야 하므로 성능이 조금 나빠진다. 물론 훔치는 일이 드물게 일어나기를 기대하는 것이고, 그래서 이 락도 드물게 잡히길 기대한다.

모든 로컬 큐가 비어 있으면 워커 스레드는 **전역 큐**에서 (락을 잡고) FIFO 알고리즘으로 항목을 꺼낸다. 전역 큐마저 비어 있으면 워커 스레드는 무언가 나타나기를 기다리며 잠든다. 오래 자면 스스로 깨어나 자기를 파괴하고, 그 스레드가 쓰던 자원(커널 객체, 스택, TEB)을 시스템이 회수한다.

정리하면 워커 스레드가 일감을 찾는 순서는 이렇다.

| 순서 | 어디서 | 알고리즘 | 락 | 비고 |
|---|---|---|---|---|
| 1 | 자기 로컬 큐의 머리 | LIFO | 없음 | 가장 빠른 경로. 캐시 지역성이 가장 좋다 |
| 2 | 다른 워커의 로컬 큐 꼬리 | 꼬리에서 훔치기 | 필요 | 드물게 일어나기를 기대한다 |
| 3 | 전역 큐 | FIFO | 필요 | 경합 시 병목이 될 수 있다 |
| 4 | 없음 | — | — | 잠들었다가 오래 유휴하면 스스로 파괴한다 |

> **💡 왜 꼬리에서 훔치는가**
>
> 소유 스레드는 머리에서 꺼내고 도둑은 꼬리에서 꺼낸다. 큐가 비어 있지 않은 한 두 접근은 **서로 다른 메모리 위치**를 건드리므로 경합이 최소화된다. 게다가 꼬리에 있는 항목은 가장 오래전에 큐잉된 것이라 소유 스레드의 캐시에 남아 있을 확률이 이미 낮다. 잃어봤자 손해가 적은 것부터 가져간다는 설계다.

### 큐 배치를 제어할 수 있는가

.NET Core 3.0부터 제네릭 오버로드가 추가되어 큐 배치를 힌트로 지정할 수 있다.

```csharp
// ※.NET Core 3.0 — preferLocal 이 true 면 호출 스레드의 로컬 큐를 선호한다
ThreadPool.QueueUserWorkItem<int>(
    static n => Console.WriteLine(n),
    42,
    preferLocal: true);
```

`preferLocal`은 **힌트**다. 호출 스레드가 워커 스레드가 아니면 로컬 큐 자체가 없으므로 전역 큐로 간다. 이 오버로드의 진짜 가치는 큐 배치보다도 **박싱과 클로저 할당을 피하는 것**에 있다 — 상태를 `object`가 아니라 `TState`로 받으므로 값 타입 상태를 박싱하지 않고, `static` 람다를 쓰면 디스플레이 클래스 할당도 없다(26장, 69장).

### 워커 스레드와 I/O 스레드

풀은 사실 두 종류의 스레드를 관리한다. **워커 스레드(worker thread)** 는 지금까지 설명한, 큐에서 작업 항목을 꺼내 실행하는 스레드다. **I/O 스레드(completion port thread)** 는 완료된 비동기 I/O 요청의 결과를 처리하는 스레드다. `ThreadPool`의 설정 API가 인자를 항상 두 개씩 받는 이유가 이것이다.

```csharp
const int WorkerThreads = 12;
const int CompletionPortThreads = 12;
ThreadPool.SetMinThreads(WorkerThreads, CompletionPortThreads);
```

`WorkerThreads`는 스레드 풀이 필요에 따라 만드는 워커 스레드의 최소 개수, `CompletionPortThreads`는 비동기 I/O 스레드의 개수다. I/O 완료 포트는 Windows 커널 기능이고, 다른 플랫폼에서는 런타임이 등가의 메커니즘으로 대체한다. 비동기 I/O가 실제로 어떻게 동작하는지는 47장에서 다룬다.

### 풀 상태를 관찰하는 API

풀을 블랙박스로 취급하되, 진단할 때는 안을 들여다볼 수 있어야 한다.

| API | 반환 | 의미 |
|---|---|---|
| `ThreadPool.ThreadCount` | `int` | 현재 풀에 존재하는 스레드 수 ※.NET Core 3.0 |
| `ThreadPool.PendingWorkItemCount` | `long` | 처리 대기 중인 작업 항목 수 ※.NET Core 3.0 |
| `ThreadPool.CompletedWorkItemCount` | `long` | 지금까지 처리를 완료한 작업 항목 수 ※.NET Core 3.0 |
| `ThreadPool.GetMinThreads(out w, out io)` | `void` | 지연 주입 없이 즉시 만들 수 있는 스레드 수 |
| `ThreadPool.GetMaxThreads(out w, out io)` | `void` | 풀이 만들 수 있는 스레드 수의 상한 |
| `ThreadPool.GetAvailableThreads(out w, out io)` | `void` | 최대치에서 현재 사용 중인 수를 뺀 값 |
| `Thread.CurrentThread.IsThreadPoolThread` | `bool` | 지금 실행 중인 스레드가 풀 스레드인가 |

`PendingWorkItemCount`가 계속 증가하고 `CompletedWorkItemCount`가 거의 늘지 않는다면 풀이 막힌 것이다. 원인은 대개 46.2절에서 다룰 **스레드 풀 기아**다.

> **📌 풀 스레드는 항상 백그라운드 스레드다**
>
> 45.7절에서 본 포그라운드/백그라운드 구분이 여기서 의미를 갖는다. 풀 스레드는 예외 없이 백그라운드다. 즉 **풀 스레드만 살아 있으면 프로세스는 종료된다.** 콘솔 애플리케이션에서 `Task.Run(...)`만 던져 놓고 `Main`이 반환하면 그 작업은 끝나지 않은 채 프로세스가 죽는다. 위 예제가 `Console.ReadLine()`으로 주 스레드를 붙잡아 두는 이유가 이것이다.
>
> 덤으로, 풀 스레드는 **이름을 설정할 수 없어** 디버깅이 조금 불편하다(Visual Studio의 Threads 창에서 설명을 붙일 수는 있다). 풀 스레드의 우선순위는 바꿀 수 있지만 풀로 반환될 때 정상(Normal)으로 복원된다.

## 46.2 스레드 주입(injection)과 hill-climbing 알고리즘

### 풀은 스레드를 몇 개 만드는가

풀의 스레드 개수 정책에는 두 개의 국면이 있다.

**첫 번째 국면 — 즉시 생성 구간.** 풀은 워커 스레드 수가 `ThreadPool.SetMinThreads`에 전달된 값과 같아질 때까지 **빠르게** 워커 스레드를 만든다. 이 메서드를 한 번도 호출하지 않았다면(그리고 호출하지 않는 편이 권장된다) 기본값은 **프로세스가 사용할 수 있는 CPU 수** — 프로세스의 affinity mask가 결정한다 — 와 같다. 보통 프로세스는 머신의 모든 CPU를 쓸 수 있으므로, 풀은 머신의 CPU 수만큼 워커 스레드를 순식간에 만든다.

**두 번째 국면 — 지연 주입 구간.** 이만큼 스레드를 만든 다음부터 풀은 **작업 항목의 완료율을 모니터링한다.** 항목이 완료되는 데 오래 걸리면(그 "오래"의 정확한 의미는 문서화되어 있지 않다) 워커 스레드를 더 만든다. 항목이 빨리 완료되기 시작하면 워커 스레드를 파괴한다.

> **⚠️ 지연 주입의 속도를 정확한 숫자로 외우지 마라**
>
> "초당 1개", "초당 2개" 같은 수치가 인터넷에 떠돌지만, 이건 **문서화된 계약이 아니라 구현 세부다.** CLR 버전마다, 플랫폼마다, 심지어 클라이언트 OS냐 서버 OS냐에 따라 달랐고 앞으로도 바뀐다. 확실한 것은 두 가지뿐이다. (1) `MinThreads` 이하는 즉시 만들어진다. (2) 그 위로는 **스로틀링된 속도**로만 주입되며, 특히 애플리케이션 수명 초기에 더 인색하다. 설계는 이 두 사실 위에 세워야 하고, 정확한 숫자 위에 세우면 안 된다.

### hill-climbing — 처리량을 측정해서 방향을 정한다

두 번째 국면에서 풀이 실제로 하는 일이 **hill-climbing 알고리즘**이다.

CLR은 스레드 풀에서 **오버서브스크립션(oversubscription)** 을 막는 것을 목표로 한다. 오버서브스크립션은 CPU 코어보다 활성 스레드가 많아 OS가 스레드를 시분할해야 하는 상태다. 시분할은 비싼 컨텍스트 스위치를 요구하고, 현대 프로세서의 성능에 필수적인 CPU 캐시를 무효화하므로 성능을 해친다.

CLR은 태스크를 큐잉하고 그 시작을 스로틀링해서 오버서브스크립션을 막는다. 시작은 **하드웨어 코어 수만큼의 동시 태스크**로 하고, 그다음부터는 **hill-climbing 알고리즘으로 동시성 수준을 조율한다** — 작업 부하를 한 방향으로 계속 조정해 보고, **처리량이 개선되면 같은 방향으로 계속 가고, 아니면 방향을 뒤집는다.** 이렇게 하면 머신에서 다른 프로세스가 경쟁하고 있어도 항상 최적 성능 곡선을 추적하게 된다.

```text
   처리량
     ▲
     │            ● ← 여기가 최적점. 여기를 넘어서면 처리량이 떨어진다
     │         ●     ●
     │      ●           ●
     │   ●                 ●
     │ ●                      ●
     └────────────────────────────────▶ 워커 스레드 수
       코어 수

   풀의 전략: 스레드를 늘려 본다 → 처리량을 잰다 → 좋아졌으면 계속 늘린다
                                            → 나빠졌으면 줄이는 쪽으로 뒤집는다
```

이 전략은 두 조건이 만족될 때 가장 잘 작동한다.

1. **작업 항목이 대체로 짧다** — 250ms 미만, 이상적으로는 100ms 미만. 그래야 CLR이 측정하고 조정할 기회를 충분히 얻는다.
2. **대부분의 시간을 블로킹으로 보내는 작업이 풀을 지배하지 않는다.**

### 블로킹이 hill-climbing을 속인다

두 번째 조건이 이 장 전체에서 가장 중요한 함정이다.

블로킹이 문제인 이유는 CLR에게 **"내가 CPU를 꽉 채워 쓰고 있다"는 잘못된 인상**을 주기 때문이다. 실제로는 블로킹된 스레드가 CPU를 전혀 쓰지 않는데, 풀 입장에서는 "스레드 8개가 전부 작업 중이고 완료된 항목이 없다"로만 보인다. CLR은 이 상황을 감지하고 보상한다 — 풀에 스레드를 더 주입한다. 하지만 이 보상에는 두 가지 대가가 따른다.

- 주입된 스레드 때문에 풀이 이후의 **오버서브스크립션에 취약**해진다. 블로킹이 풀린 순간 갑자기 실행 가능한 스레드가 잔뜩 생긴다.
- CLR이 새 스레드를 주입하는 **속도를 스로틀링**하므로 **지연(latency)** 이 생긴다. 특히 애플리케이션 수명 초기에, 그리고 자원 소비를 낮게 유지하려는 클라이언트 운영체제에서 더 그렇다.

### 스레드 풀 기아 — 메커니즘

이 두 가지가 결합하면 **스레드 풀 기아(thread pool starvation)** 가 된다. 메커니즘은 이렇다.

```text
t = 0ms    요청 100개가 동시에 도착. 풀 워커 = 코어 수(예: 8)
           워커 8개가 각각 핸들러를 실행 → 전부 someTask.Result 에서 블로킹
           ↓
t = 0ms    블로킹된 8개는 CPU를 쓰지 않지만 풀 스레드는 점유한다
           블로킹을 푸는 데 필요한 연속(continuation)은 전역 큐에 대기 중
           큐에는 그 연속 + 나머지 요청 92개가 쌓여 있다
           ↓
           ┌──────────────────────────────────────────┐
           │  교착의 핵심:                              │
           │  블로킹을 풀 작업이 큐에 있는데             │
           │  그 큐를 처리할 스레드가 전부 블로킹돼 있다  │
           └──────────────────────────────────────────┘
           ↓
t = ?      풀: "완료율이 0이다" → 스레드 주입 시작 (스로틀됨)
           ↓
t = +1s    워커 9개. 9번째도 새 요청을 집어 .Result 에서 블로킹
           ↓
t = +2s    워커 10개. 10번째도 블로킹
           ...
t = +90s   요청이 드디어 처리되기 시작. 그 사이 타임아웃과 재시도가 폭주
```

핵심은 **주입 지연과 블로킹이 맞물린다**는 것이다. 블로킹된 스레드가 풀리려면 그 스레드가 기다리는 태스크의 연속이 실행되어야 하는데, 연속은 큐에서 대기하고 있고, 큐를 처리할 스레드는 전부 블로킹돼 있다. 새 스레드가 주입되어야 큐가 소진되기 시작하는데, 주입은 스로틀링되어 있고, 새로 주입된 스레드마저 대기 중인 새 요청을 집어 또 블로킹된다.

**이것이 서버 애플리케이션에서 `.Result`와 `.Wait()`를 금지하는 진짜 이유다.** 데드락이 나서가 아니라(그것도 나지만, 그건 47.14절의 `SynchronizationContext` 이야기다), 부하가 올라갈 때 시스템 전체가 조용히 멎기 때문이다.

> **⚠️ 기아는 CPU 사용률이 0에 가까운 상태로 나타난다**
>
> 진단할 때 가장 헷갈리는 지점이다. 애플리케이션이 완전히 멎었는데 CPU 사용률은 5%다. "부하가 없는데 왜 응답이 없지?"라는 질문이 나온다. 블로킹된 스레드는 CPU를 소비하지 않기 때문이다(45.2절). 확인해야 할 지표는 CPU가 아니라 **`ThreadPool.ThreadCount`가 계속 증가하는가**와 **`ThreadPool.PendingWorkItemCount`가 줄지 않는가**다. 스레드 수가 코어 수를 한참 넘어 천천히 증가하고 있다면 기아가 진행 중이다.

### `SetMinThreads` — 언제 정당하고 언제 남용인가

CLR은 풀이 만들 스레드의 최대 개수를 개발자가 설정할 수 있게 해 준다. 하지만 스레드 풀은 **애초에 스레드 수에 상한을 두면 안 된다.** 기아나 데드락이 발생할 수 있기 때문이다. 1,001번째 항목이 신호하는 이벤트에서 블로킹하는 작업 항목 1,000개를 큐잉했다고 상상해 보라. 최대치를 1,000으로 설정했다면 1,001번째 항목은 실행되지 못하고, 1,000개 스레드는 영원히 블로킹되며, 최종 사용자는 애플리케이션을 강제 종료하고 작업 내용을 전부 잃는다.

고객들이 기아와 데드락 문제를 겪었기 때문에 CLR 팀은 기본 최대 스레드 수를 꾸준히 늘려 왔다. 원천이 쓰인 시점의 기본 최대치는 **약 1,000개**였는데, 32비트 프로세스는 사용 가능한 주소 공간이 최대 2GB뿐이므로 이건 사실상 무제한이다. Win32 DLL들과 CLR DLL이 로드되고 네이티브 힙과 관리 힙이 할당되고 나면 약 1.5GB가 남는데, 스레드 하나가 사용자 모드 스택과 TEB에 1MB 이상을 요구하므로 32비트 프로세스가 가질 수 있는 스레드는 **약 1,360개**가 한계다. 이보다 많이 만들려고 하면 `OutOfMemoryException`이 발생한다. 물론 64비트 프로세스는 주소 공간이 8테라바이트이므로 이론적으로 수십만 개를 만들 수 있지만, 이 정도 스레드를 할당하는 것은 그냥 자원 낭비다. 이상적인 스레드 수는 머신의 CPU 수와 같다.

`ThreadPool` 클래스는 스레드 수를 조작하는 정적 메서드 몇 개를 제공한다 — `GetMaxThreads`, `SetMaxThreads`, `GetMinThreads`, `SetMinThreads`, `GetAvailableThreads`. 원천의 권고는 단호하다. **이 메서드들을 호출하지 마라.** 스레드 풀 한계를 만지작거리면 대개 애플리케이션이 더 빨라지는 게 아니라 더 느려진다. 애플리케이션에 수백~수천 개의 스레드가 필요하다고 생각한다면, 애플리케이션의 아키텍처와 스레드 사용 방식에 심각한 문제가 있는 것이다.

반면 성능 튜닝 관점의 원천은 다른 이야기를 한다. 스레드 풀은 처음 사용될 때 아무 이력(history)이 없고, 시간이 지나면서 스스로를 튜닝해 성능을 개선한다. 스레드를 많이 쓰고 CPU에 큰 부하를 거는 애플리케이션은 **높은 시작 비용**을 만날 수 있다. 스레드가 만들어져 풀에 제공될 때까지 풀이 기다려야 하기 때문이다. 시작 시점의 성능 조정 방법 하나가 최소 스레드 수를 설정하는 것이다.

두 원천이 충돌하는 것처럼 보이지만 실제로는 서로 다른 질문에 답하고 있다.

| 상황 | `SetMinThreads` 판단 | 이유 |
|---|---|---|
| 시작 직후 폭발적 부하가 예상되는 서버 | 정당함 | 즉시 생성 구간을 넓혀 지연 주입 스로틀링을 우회한다 |
| 레거시 동기 API를 감싸 블로킹이 섞인 코드 | 정당하지만 임시방편 | 블로킹을 없애는 것이 진짜 해법이다 |
| 정상 상태(steady state)의 처리량이 부족하다 | 부당함 | hill-climbing이 이미 최적점을 찾고 있다. 개입하면 방해만 된다 |
| "스레드가 많으면 빠르겠지" | 부당함 | 오버서브스크립션 → 컨텍스트 스위치 스래싱 → 더 느려진다 |
| CPU 바운드 작업의 병렬도를 조절하고 싶다 | 부당함 | `Parallel`의 `MaxDegreeOfParallelism`이나 PLINQ의 `WithDegreeOfParallelism`을 써라(50.5절) |

> **⚠️ `SetMinThreads`는 문제를 감추지 해결하지 않는다**
>
> 최소 스레드 수를 올리면 기아의 **증상**이 완화된다. 블로킹된 스레드가 8개까지는 즉시 보충되니까. 하지만 부하가 그 선을 넘으면 똑같은 절벽이 다시 나타나고, 이번에는 스레드가 훨씬 많은 상태에서 나타나므로 상황이 더 나쁘다. 그리고 정상 상태에서는 필요 없는 스레드를 상시 유지하게 되어 메모리와 컨텍스트 스위치 비용을 낸다.
>
> 설정을 올바르게 잡지 못하면 스레드를 너무 많이 만들고 태스크를 과도하게 스케줄하게 된다. 그러면 컨텍스트 스위치가 늘어나 CPU에 부하가 더 걸리고 성능이 **떨어진다.** 값을 설정하기 전에 성능 모니터링으로 애플리케이션의 스레드 사용량과 컨텍스트 스위치를 관찰하는 것이 좋다. `GetMaxThreads`와 `GetMinThreads`도 최적값 분석에 쓸 수 있다.

> **💡 순서를 지켜라**
>
> 1. 먼저 **블로킹을 제거한다.** `.Result`/`.Wait()`를 `await`로 바꾸고, 동기 I/O를 비동기 I/O로 바꾼다. 대부분의 기아는 여기서 끝난다.
> 2. 제거할 수 없는 블로킹(제3자 동기 라이브러리 등)은 **격리한다.** 전용 스레드나 `TaskCreationOptions.LongRunning`(46.10절), 또는 동시성을 제한한 커스텀 스케줄러로 풀 바깥에 둔다.
> 3. 그래도 시작 시점의 지연이 문제라면 **그때** `SetMinThreads`를 고려한다. 그리고 그 값을 정할 때는 반드시 측정한다(67장).

> **📌 풀을 블랙박스로 믿어라**
>
> 원천은 풀의 내부 구현을 자세히 설명하기를 꺼린다. CLR 버전마다 크게 바뀌어 왔고 앞으로도 바뀔 것이기 때문이다. 풀은 블랙박스로 생각하는 편이 낫다. 이 블랙박스는 어느 한 애플리케이션에 완벽하지 않다 — 아주 다양한 애플리케이션과 함께 동작하도록 설계된 범용 스레드 스케줄링 기술이므로 어떤 애플리케이션에는 더 잘 맞고 어떤 애플리케이션에는 덜 맞는다. 그래도 오늘날 아주 잘 동작하며, 여러분이 CLR에 들어 있는 것보다 나은 스레드 풀을 만들기는 매우 어렵다. 시간이 지나면 풀 내부가 개선되면서 대부분의 애플리케이션이 저절로 좋아진다.

## 46.3 `Task` 시작하기와 값 반환

### `QueueUserWorkItem`의 한계

`ThreadPool.QueueUserWorkItem`을 호출해 비동기 컴퓨트 바운드 연산을 시작하는 것은 매우 간단하다. 하지만 이 기법에는 한계가 많다. **가장 큰 문제는 연산이 언제 완료되었는지 알 방법이 내장되어 있지 않고, 완료 시 반환값을 돌려받을 방법도 없다는 것이다.** 이런 한계들을 해결하려고 Microsoft는 태스크(task) 개념을 도입했고, `System.Threading.Tasks` 네임스페이스의 타입들로 쓴다.

스레드가 저수준 동시성 도구라는 관점에서 보면 한계는 더 구체적이다.

- 시작하는 스레드에 데이터를 넘기는 것은 쉽지만, `Join`한 스레드에서 "반환값"을 받아 오는 쉬운 방법이 없다. 공유 필드 같은 걸 만들어야 한다. 연산이 예외를 던지면 그것을 잡아 전파하는 일도 똑같이 고통스럽다.
- 스레드에게 "끝나면 다른 걸 시작해라"고 말할 수 없다. 대신 `Join`해야 하고, 그 과정에서 자기 스레드가 블로킹된다.

이 한계들이 **세밀한(fine-grained) 동시성**을 막는다. 작은 동시 연산들을 조합해 큰 동시 연산을 만들기 어렵게 하고, 그래서 수동 동기화(잠금, 신호)에 더 의존하게 만든다.

`Task`는 이 모든 문제를 해결한다. 스레드에 비해 `Task`는 **더 높은 층위의 추상**이다 — 스레드가 뒷받침할 수도 있고 아닐 수도 있는 동시 연산을 나타낸다. 태스크는 **조합 가능**하다(연속으로 이어 붙일 수 있다). 시작 지연을 줄이려고 스레드 풀을 쓸 수 있고, `TaskCompletionSource`(46.5절)를 쓰면 I/O 바운드 연산을 기다리는 동안 스레드를 아예 쓰지 않는 콜백 방식을 채택할 수도 있다.

### 세 가지 시작 방법

```csharp
ThreadPool.QueueUserWorkItem(ComputeBoundOp, 5);   // QueueUserWorkItem 호출
new Task(ComputeBoundOp, 5).Start();               // 위와 동등한 Task 방식
Task.Run(() => ComputeBoundOp(5));                 // 또 하나의 동등한 방식
```

두 번째 줄은 `Task` 객체를 만든 다음 즉시 `Start`를 호출해 태스크를 실행 스케줄에 올린다. 물론 `Task` 객체를 만들어 두고 나중에 `Start`를 호출해도 된다. `Task` 객체를 만들어 다른 메서드에 넘기고, 그 메서드가 언제 `Start`를 호출할지 결정하는 코드를 상상할 수 있다. `Task` 객체를 만들고 곧바로 `Start`를 호출하는 일이 흔하므로, 편의를 위한 정적 메서드 `Task.Run`이 마지막 줄이다.

`Task.Run`이 만드는 태스크를 **"핫(hot)" 태스크**라고 부른다 — 이미 실행 중이거나 실행 스케줄에 올라 있다. `Task` 생성자로 만들고 `Start`를 부르지 않은 태스크는 **"콜드(cold)" 태스크**다. 실무에서 콜드 태스크를 쓰는 일은 드물다.

`Task`를 만들 때는 생성자에 수행할 연산을 나타내는 `Action` 또는 `Action<object>` 델리게이트를 넘긴다. `object`를 받는 메서드를 넘긴다면 그 연산에 최종적으로 전달할 인자도 생성자에 함께 넘겨야 한다. `Run`을 호출할 때는 `Action` 또는 `Func<TResult>` 델리게이트를 넘길 수 있다. 생성자를 호출할 때든 `Run`을 호출할 때든 `CancellationToken`을 선택적으로 넘길 수 있으며, 이러면 태스크가 스케줄되기 전에 취소될 수 있다(46.8절).

> **📌 `Task.Run`은 `Task.Factory.StartNew`의 지름길이다**
>
> `Task.Run`은 사실 `Task.Factory.StartNew`를 부르는 지름길이며, `StartNew`는 오버로드가 더 많아 유연성이 크다. 그런데 그 "유연성"이 곧 함정이기도 하다. 다음 항목을 보라.

### `Task.Factory.StartNew`의 기본 옵션이 위험한 이유

`StartNew`는 상태 객체를 지정할 수 있다. 대상 메서드의 시그니처는 그러면 `object` 타입 매개변수 하나여야 한다.

```csharp
var task = Task.Factory.StartNew(Greet, "Hello");
task.Wait();                                       // 태스크 완료를 기다린다

void Greet(object state) { Console.Write(state); }  // Hello
```

이렇게 하면 `Greet`를 호출하는 람다 실행에 필요한 클로저 비용을 피할 수 있다. 이건 미시 최적화라 실무에서 필요한 경우가 드물기 때문에, 상태 객체는 오히려 **태스크에 의미 있는 이름을 붙이는 데** 쓰는 편이 낫다. 그러면 `AsyncState` 속성으로 이름을 조회할 수 있다.

```csharp
var task = Task.Factory.StartNew(state => Greet("Hello"), "인사");
Console.WriteLine(task.AsyncState);                // 인사
task.Wait();

void Greet(string message) { Console.Write(message); }
```

Visual Studio는 Parallel Tasks 창에 각 태스크의 `AsyncState`를 표시하므로, 의미 있는 이름을 붙여 두면 디버깅이 훨씬 쉬워진다(50.13절).

문제는 `StartNew`의 **기본 동작**이다.

> **⚠️ `Task.Factory.StartNew`의 기본값 세 가지가 함정이다**
>
> **1. 스케줄러가 `TaskScheduler.Current`다.** `Task.Run`은 항상 `TaskScheduler.Default`(스레드 풀 스케줄러)를 쓴다. 반면 `StartNew`는 **호출 시점의 현재 스케줄러**를 쓴다. 커스텀 스케줄러 위에서 실행 중인 코드 안에서 `StartNew`를 호출하면 새 태스크도 그 스케줄러로 간다. 동시성을 1로 제한한 스케줄러였다면 그 안에서 만든 태스크가 자기 자신을 기다리며 데드락에 빠질 수 있다.
>
> **2. 자식 태스크가 붙을 수 있다.** `Task.Run`은 `TaskCreationOptions.DenyChildAttach`를 적용한다. `StartNew`는 적용하지 않는다. 그래서 델리게이트 안에서 누군가 `AttachedToParent`로 태스크를 만들면, 바깥 태스크는 그 자식이 끝날 때까지 완료되지 않는다. 라이브러리 안쪽 구현에 따라 완료 시점이 달라진다는 뜻이다.
>
> **3. `async` 델리게이트를 넘기면 `Task<Task>`가 나온다.** 이게 가장 자주 사고를 낸다.
>
> ```csharp
> // 위험: task 의 타입은 Task<Task> 다.
> // 바깥 태스크는 "안쪽 async 람다가 첫 await 에 도달한 순간" 완료된다.
> Task<Task> task = Task.Factory.StartNew(async () =>
> {
>     await Task.Delay(5000);
>     Console.WriteLine("5초 뒤");
> });
> task.Wait();                 // 5초를 기다리지 않고 즉시 반환한다!
>
> // 해결 1: Unwrap()
> Task real = Task.Factory.StartNew(async () => { await Task.Delay(5000); }).Unwrap();
>
> // 해결 2: 애초에 Task.Run 을 쓴다 (Func<Task> 오버로드가 자동으로 언랩한다)
> Task ok = Task.Run(async () => { await Task.Delay(5000); });
> ```
>
> 결론은 하나다. **특별한 이유가 없으면 `Task.Run`을 써라.** `StartNew`는 `TaskCreationOptions`나 커스텀 스케줄러가 정말 필요할 때만 쓰고, 그때도 `async` 델리게이트를 넘기지 마라.

### 완료를 기다리고 결과를 얻기

계산량이 많은 `Sum` 메서드가 있다고 하자.

```csharp
private static int Sum(int n)
{
    int sum = 0;
    for (; n > 0; n--)
        checked { sum += n; }   // n이 크면 System.OverflowException 이 발생한다
    return sum;
}
```

이제 `Task`에서 파생된 `Task<TResult>` 객체를 만들 수 있다. 제네릭 인자 `TResult`에는 컴퓨트 바운드 연산의 반환 타입을 넘긴다. 태스크를 시작한 뒤 완료를 기다리고 결과를 얻는 코드는 이렇다.

```csharp
// Task 를 만든다 (아직 실행되지 않는다)
Task<int> t = new Task<int>(n => Sum((int)n), 1000000000);

// 나중에 시작할 수 있다
t.Start();

// 선택적으로, 완료를 명시적으로 기다릴 수 있다
t.Wait();   // 참고: 타임아웃과 CancellationToken 을 받는 오버로드가 있다

// 결과를 얻는다 (Result 속성은 내부적으로 Wait 를 호출한다)
Console.WriteLine("합계: " + t.Result);
```

> **⚠️ `Wait`가 블로킹하지 않고 태스크를 그 자리에서 실행할 수 있다**
>
> 스레드가 `Wait` 메서드를 호출하면, 시스템은 기다리는 대상 `Task`가 실행을 시작했는지 확인한다. 시작했다면 `Wait`를 호출한 스레드는 `Task`가 완료될 때까지 블로킹된다. 그런데 `Task`가 아직 실행을 시작하지 않았다면, 시스템은 (`TaskScheduler`에 따라) **`Wait`를 호출한 그 스레드로 `Task`를 실행할 수 있다.** 이러면 `Wait`를 호출한 스레드는 블로킹되지 않고 `Task`를 실행한 뒤 즉시 반환한다.
>
> 이건 좋은 일이다. 스레드가 블로킹되지 않으므로 블로킹된 스레드를 대체할 스레드를 만들지 않아도 되어 자원 사용이 줄고, 스레드 생성 시간과 컨텍스트 스위치가 없어 성능도 좋아진다.
>
> 하지만 나쁜 일일 수도 있다. 예를 들어 **스레드가 동기화 락을 잡은 상태에서 `Wait`를 호출했고, 그 `Task`가 같은 락을 잡으려 한다면 그 스레드는 데드락에 빠진다.** 이 "인라인 실행" 동작은 46.5절의 `TaskCompletionSource` 함정과 원인이 같다.

### `TaskStatus` — 태스크의 생애 주기

`Task` 객체가 존재하는 동안 `Status` 속성을 조회하면 생애 주기의 어디쯤인지 알 수 있다. 이 속성은 `TaskStatus` 값을 반환한다.

```csharp
public enum TaskStatus
{
    // 태스크가 살아 있는 동안의 상태
    Created,                        // 명시적으로 생성됨. 수동으로 Start() 할 수 있다
    WaitingForActivation,           // 암묵적으로 생성됨. 자동으로 시작된다
    WaitingToRun,                   // 스케줄되었으나 아직 실행 전
    Running,                        // 실제로 실행 중
    WaitingForChildrenToComplete,   // 자식 완료를 기다리는 중

    // 최종 상태는 이 셋 중 하나다
    RanToCompletion,
    Canceled,
    Faulted
}
```

`Task` 객체를 처음 생성하면 상태는 `Created`다. 태스크가 시작되면 `WaitingToRun`으로 바뀐다. 실제로 어떤 스레드에서 실행되고 있으면 `Running`이다. 실행을 멈추고 자식 태스크를 기다리는 중이면 `WaitingForChildrenToComplete`가 된다. 완전히 끝나면 `RanToCompletion`, `Canceled`, `Faulted` 중 하나로 들어간다.

`WaitingForActivation` 상태는 특별하다. `ContinueWith`, `ContinueWhenAll`, `ContinueWhenAny`, `FromAsync` 중 하나로 만들어진 `Task`, 그리고 `TaskCompletionSource<TResult>` 객체를 생성해서 만들어진 `Task`가 이 상태로 태어난다. 이 상태는 **태스크의 스케줄링을 태스크 인프라가 제어한다**는 뜻이다. 예를 들어 `ContinueWith`로 만든 `Task`는 명시적으로 시작할 수 없다. 선행(antecedent) 태스크가 실행을 마치면 자동으로 시작된다.

편의를 위해 `Task`는 읽기 전용 불리언 속성 몇 개를 제공한다.

| 속성 | `true`가 되는 조건 |
|---|---|
| `IsCompleted` | `RanToCompletion`, `Canceled`, `Faulted` **셋 다** |
| `IsCanceled` | `Canceled` |
| `IsFaulted` | `Faulted` |
| `IsCompletedSuccessfully` | `RanToCompletion` ※.NET Core 2.0 |

> **⚠️ `IsCompleted == true`는 "성공"이 아니다**
>
> 가장 흔한 오해다. `IsCompleted`는 태스크가 **끝났다**는 뜻이지 **잘 끝났다**는 뜻이 아니다. 예외로 실패했거나 취소되었어도 `true`다. 성공 여부를 판정하려면 이렇게 써야 한다.
>
> ```csharp
> if (task.Status == TaskStatus.RanToCompletion) { /* 성공 */ }
> // 또는
> if (task.IsCompletedSuccessfully) { /* 성공 — ※.NET Core 2.0 이상 */ }
> ```

### `Task` 안에는 무엇이 있는가 — 비용의 근거

`Task` 객체마다 태스크의 상태를 구성하는 필드 집합이 있다. `int` ID(읽기 전용 `Id` 속성), `Task`의 실행 상태를 나타내는 `int`, 부모 태스크에 대한 참조, 태스크가 생성될 때 지정된 `TaskScheduler`에 대한 참조, 콜백 메서드에 대한 참조, 콜백 메서드에 전달할 객체에 대한 참조(읽기 전용 `AsyncState` 속성으로 조회), `ExecutionContext`에 대한 참조, `ManualResetEventSlim` 객체에 대한 참조가 들어 있다. 여기에 더해 각 `Task` 객체는 요청 시에 생성되는 보조 상태에 대한 참조를 갖는다. 보조 상태에는 `CancellationToken`, `ContinueWithTask` 객체의 컬렉션, 처리되지 않은 예외를 던진 자식 태스크의 `Task` 객체 컬렉션 등이 들어 있다.

요점은 이렇다. **태스크는 많은 기능을 제공하지만 이 모든 상태를 위해 메모리를 할당해야 하므로 비용이 있다.** 태스크가 제공하는 추가 기능이 필요 없다면 `ThreadPool.QueueUserWorkItem`을 쓰는 편이 자원을 더 효율적으로 쓴다.

> **💡 `Dispose`를 부르지 마라**
>
> `Task`와 `Task<TResult>`는 `IDisposable`을 구현하므로 `Dispose`를 호출할 수 있다. 그런데 오늘날 `Dispose` 메서드가 하는 일은 `ManualResetEventSlim` 객체를 닫는 것뿐이다. 원천의 권고는 명확하다 — **`Task` 객체에 명시적으로 `Dispose`를 호출하지 말고, 더 이상 사용되지 않는다고 GC가 판단할 때 자원을 정리하게 두라.** 33장의 "`IDisposable`이면 반드시 `Dispose`" 규칙에 대한 드문 예외다. `Task` 파생 클래스가 자체 자원을 할당한다면 그 클래스의 `Dispose` 재정의에서 해제되겠지만, 실무에서 그런 타입을 만날 일은 거의 없다.

### 태스크 ID

각 `Task` 객체는 고유 ID를 나타내는 `int` 필드를 담고 있다. `Task` 객체를 만들면 이 필드는 0으로 초기화된다. 그다음 읽기 전용 `Id` 속성을 **처음 조회할 때** 속성이 고유한 `int` 값을 이 필드에 할당하고 반환한다. 태스크 ID는 1부터 시작해 하나씩 증가한다. Visual Studio 디버거에서 `Task` 객체를 들여다보기만 해도 디버거가 태스크의 ID를 표시하려고 ID 할당을 유발한다.

태스크 코드를 실행하는 중에는 `Task.CurrentId` 정적 속성을 조회할 수 있다. 이 속성은 nullable `int`(`int?`)를 반환한다. 태스크가 실행 중이 아닐 때 조회하면 `null`을 반환한다.

### 이미 완료된 태스크를 만드는 방법

동기적으로 결과가 나오는 경로에서 굳이 스레드 풀을 거칠 이유가 없다. .NET은 이미 완료된 태스크를 만드는 팩터리를 제공한다.

```csharp
Task<string> a = Task.FromResult("캐시 적중");         // 이미 RanToCompletion
Task<int>    b = Task.FromException<int>(new InvalidOperationException());
Task<int>    c = Task.FromCanceled<int>(cancellationToken);
Task         d = Task.CompletedTask;                   // 논제네릭 완료 태스크
```

이 메서드들은 **비동기 코드를 테스트할 때**, 그리고 **캐시 적중 경로에서 할당을 줄일 때** 특히 유용하다. `Task.CompletedTask`는 싱글턴이라 할당이 아예 없다.

## 46.4 태스크의 예외와 연속(continuation)

### 예외는 삼켜졌다가 다시 던져진다

컴퓨트 바운드 태스크가 처리되지 않은 예외를 던지면 **예외는 삼켜져 컬렉션에 저장되고**, 스레드 풀 스레드는 풀로 돌아갈 수 있게 된다. 나중에 `Wait` 메서드나 `Result` 속성이 호출되면, 이 멤버들이 `System.AggregateException` 객체를 던진다.

`AggregateException` 타입은 예외 객체의 컬렉션을 캡슐화하는 데 쓴다(부모 태스크가 예외를 던지는 자식 태스크를 여럿 만들면 이런 일이 생긴다). `AggregateException`은 `ReadOnlyCollection<Exception>` 객체를 반환하는 `InnerExceptions` 속성을 갖는다. 이 `InnerExceptions` 속성을 `System.Exception` 기반 클래스에서 상속한 `InnerException` **단수형** 속성과 혼동하면 안 된다. 위 `Sum` 예제라면 `AggregateException.InnerExceptions`의 0번 원소가 컴퓨트 바운드 메서드가 실제로 던진 `System.OverflowException` 객체를 가리킨다.

CLR이 예외를 `AggregateException`으로 감싸는 이유는 **병렬 프로그래밍 시나리오와 잘 맞물리게 하기 위해서**다. 여러 스레드를 쓰는 라이브러리에서는 둘 이상의 예외가 동시에 던져질 수 있고, 모든 예외를 보고하려면 컨테이너가 필요하다.

`AggregateException`의 `Flatten`, `Handle`, `GetBaseException`은 32.13절에서 이미 다뤘으므로 여기서는 태스크 맥락에서 쓰는 방법만 본다.

### `await`는 첫 예외를 벗겨서 던진다

여기가 이 절에서 가장 자주 사고를 내는 지점이다.

`Task`에 `await`를 쓰면 `AggregateException` 대신 **첫 번째 내부 예외**가 던져진다. 이건 개발자가 기대하는 프로그래밍 경험을 주기 위한 설계다. 이렇게 하지 않으면 코드 전반에서 `AggregateException`을 잡고, 내부 예외를 확인하고, 처리하거나 다시 던지는 일을 반복해야 한다. 매우 번거롭다. 실제로 첫 내부 예외를 던지는 것은 `TaskAwaiter`의 `GetResult` 메서드다.

같은 이유로, 연속에서 `awaiter.GetResult()`를 호출하면 선행 태스크가 실패했을 때 예외가 `AggregateException`에 감싸이지 않고 **직접** 던져진다. `Result` 속성에 접근하는 대신 `GetResult`를 부르는 이점이 이것이다. 논제네릭 태스크에 대해 `GetResult()`는 반환값이 `void`이므로, 그 유일한 기능이 **예외를 다시 던지는 것**이다.

| 접근 방식 | 실패한 태스크에서 던져지는 예외 | 비고 |
|---|---|---|
| `task.Wait()` | `AggregateException` | 감싼 채 |
| `task.Result` | `AggregateException` | 내부적으로 `Wait` 호출 |
| `Task.WaitAll(...)` | `AggregateException` | 모든 실패를 취합한다 |
| `await task` | **첫 내부 예외** | 스택 트레이스가 보존된다 |
| `task.GetAwaiter().GetResult()` | **첫 내부 예외** | 동기 코드에서 언랩이 필요할 때 |
| `task.Exception` 조회 | 던지지 않음 | 항상 `AggregateException` 또는 `null` |

> **⚠️ `.GetAwaiter().GetResult()`는 언랩만 해결하지 블로킹은 해결하지 않는다**
>
> `.Result` 대신 `.GetAwaiter().GetResult()`를 쓰면 예외가 예쁘게 나온다. 그러나 **여전히 스레드를 블로킹한다.** 46.2절의 스레드 풀 기아와 47.14절의 동기화 컨텍스트 데드락은 그대로 발생한다. 이 관용구는 "이미 완료된 것이 확실한 태스크에서 결과를 꺼낼 때" 또는 "`Main` 진입점처럼 블로킹이 불가피한 최상위 경계에서" 쓰는 것이지, `await`의 대체재가 아니다.

### 태스크 예외를 다루는 실제 코드

```csharp
Task<int> t = Task.Run(() => Sum(1_000_000_000));   // OverflowException 발생

// 방식 1 — 동기 대기. AggregateException 을 잡아야 한다
try
{
    Console.WriteLine(t.Result);
}
catch (AggregateException ae)
{
    foreach (Exception inner in ae.Flatten().InnerExceptions)
        Console.WriteLine($"  {inner.GetType().Name}: {inner.Message}");
}

// 방식 2 — await. 첫 내부 예외가 그대로 온다
try
{
    Console.WriteLine(await t);
}
catch (OverflowException oe)                         // AggregateException 이 아니다
{
    Console.WriteLine(oe.Message);
}
```

`Handle` 메서드는 태스크가 취소되었을 때 특히 유용하다. 취소를 "처리된 것"으로 간주하고 나머지만 다시 던지는 관용구다.

```csharp
try
{
    Console.WriteLine("합계: " + t.Result);
}
catch (AggregateException x)
{
    // OperationCanceledException 객체는 처리된 것으로 간주한다.
    // 다른 예외가 있으면 처리되지 않은 것만 담은 새 AggregateException 이 던져진다
    x.Handle(e => e is OperationCanceledException);

    // 모든 예외가 처리되었다면 여기가 실행된다
    Console.WriteLine("합계 계산이 취소되었다");
}
```

### 연속 — 태스크가 끝나면 다른 태스크를 시작한다

확장 가능한 소프트웨어를 작성하려면 **스레드를 블로킹하면 안 된다.** 태스크가 아직 끝나지 않았는데 `Wait`를 호출하거나 `Result` 속성을 조회하면 스레드 풀이 새 스레드를 만들 가능성이 매우 높고, 이건 자원 사용을 늘리고 성능을 해친다.

다행히 태스크가 언제 완료되었는지 알아내는 더 나은 방법이 있다. **태스크가 완료되면 다른 태스크를 시작하게 하는 것**이다.

```csharp
// 태스크를 만들어 시작하고, 다른 태스크를 이어 붙인다
Task<int> t = Task.Run(() => Sum(CancellationToken.None, 10000));

// ContinueWith 는 Task 를 반환하지만 보통은 신경 쓰지 않는다
Task cwt = t.ContinueWith(task => Console.WriteLine("합계: " + task.Result));
```

이제 `Sum`을 실행하는 태스크가 완료되면, 이 태스크가 (역시 어떤 스레드 풀 스레드에서) 결과를 표시하는 다른 태스크를 시작한다. 위 코드를 실행하는 스레드는 두 태스크 중 어느 것도 기다리며 블로킹하지 않는다. 다른 코드를 실행하러 가거나, 자기가 스레드 풀 스레드라면 풀로 돌아가 다른 연산을 수행한다.

`Sum`을 실행하는 태스크가 `ContinueWith`가 호출되기 **전에** 완료될 수도 있다. 이건 문제가 되지 않는다. `ContinueWith` 메서드는 `Sum` 태스크가 이미 완료된 것을 보고 결과를 표시하는 태스크를 즉시 시작한다.

`Task` 객체는 내부적으로 `ContinueWith` 태스크의 컬렉션을 담는다. 그래서 하나의 `Task` 객체에 `ContinueWith`를 여러 번 호출할 수 있다. 태스크가 완료되면 모든 `ContinueWith` 태스크가 스레드 풀에 큐잉된다.

```csharp
var t = Task.Factory.StartNew(() => Thread.Sleep(1000));
t.ContinueWith(ant => Console.Write("X"));
t.ContinueWith(ant => Console.Write("Y"));
// 1초를 기다린 뒤 XY 또는 YX 를 출력한다
```

`ContinueWith` 자체가 `Task`를 반환하므로 연속을 계속 이어 붙일 수 있다.

```csharp
Task.Factory.StartNew<int>(() => 8)
    .ContinueWith(ant => ant.Result * 2)
    .ContinueWith(ant => Math.Sqrt(ant.Result))
    .ContinueWith(ant => Console.WriteLine(ant.Result));   // 4
```

### `TaskContinuationOptions`

`ContinueWith`를 호출할 때 `TaskContinuationOptions` 플래그를 비트 OR로 조합해 지정할 수 있다. 앞의 여섯 플래그(`None`, `PreferFairness`, `LongRunning`, `AttachedToParent`, `DenyChildAttach`, `HideScheduler`)는 `TaskCreationOptions`가 제공하는 플래그와 동일하다(46.10절).

| 플래그 | 값 | 의미 |
|---|---|---|
| `None` | 0x0000 | 기본값 |
| `PreferFairness` | 0x0001 | 스케줄러에게 이 태스크를 늦기보다 이르게 실행하라고 힌트를 준다 |
| `LongRunning` | 0x0002 | 스케줄러에게 풀 스레드를 더 적극적으로 만들라고 힌트를 준다 |
| `AttachedToParent` | 0x0004 | 태스크를 부모 태스크와 연결한다. 항상 존중된다 |
| `DenyChildAttach` | 0x0008 | 자식이 붙으려 하면 `InvalidOperationException`이 던져진다 |
| `HideScheduler` | 0x0010 | 자식 태스크가 부모 스케줄러 대신 기본 스케줄러를 쓰게 강제한다 |
| `LazyCancellation` | 0x0020 | 선행 태스크가 완료될 때까지 연속의 완료를 막는다 |
| `ExecuteSynchronously` | 0x80000 | 첫 태스크를 실행한 스레드가 연속도 실행하게 한다 |
| `NotOnRanToCompletion` | 0x10000 | 선행이 성공 완료하면 실행하지 않는다 |
| `NotOnFaulted` | 0x20000 | 선행이 예외로 실패하면 실행하지 않는다 |
| `NotOnCanceled` | 0x40000 | 선행이 취소되면 실행하지 않는다 |
| `OnlyOnCanceled` | — | `NotOnRanToCompletion \| NotOnFaulted` |
| `OnlyOnFaulted` | — | `NotOnRanToCompletion \| NotOnCanceled` |
| `OnlyOnRanToCompletion` | — | `NotOnFaulted \| NotOnCanceled` |

`Not*` 플래그는 **감산적(subtractive)** 이다. 더 많이 적용할수록 연속이 실행될 가능성이 낮아진다. 세 개를 전부 조합하는 것은 무의미하다 — 연속이 항상 취소되기 때문이다.

세 가지 결과를 각각 다른 연속으로 처리하는 관용구는 이렇다.

```csharp
Task<int> t = Task.Run(() => Sum(10000));

t.ContinueWith(task => Console.WriteLine("합계: " + task.Result),
    TaskContinuationOptions.OnlyOnRanToCompletion);

t.ContinueWith(task => Console.WriteLine("Sum 예외: " + task.Exception.InnerException),
    TaskContinuationOptions.OnlyOnFaulted);

t.ContinueWith(task => Console.WriteLine("Sum 취소됨"),
    TaskContinuationOptions.OnlyOnCanceled);
```

여기서 `"RanToCompletion"`은 선행 태스크가 취소도 처리되지 않은 예외도 없이 성공했다는 뜻이다. `"Faulted"`는 선행 태스크에서 처리되지 않은 예외가 던져졌다는 뜻이다. `"Canceled"`는 두 가지 중 하나를 뜻한다.

- 선행 태스크가 자기 취소 토큰으로 취소되었다. 다시 말해 선행 태스크에서 `OperationCanceledException`이 던져졌고, 그 예외의 `CancellationToken` 속성이 태스크 시작 시 전달된 토큰과 일치했다.
- 선행 태스크가 **조건부 연속 술어를 만족하지 못해 암묵적으로 취소되었다.**

### 조건부 연속이 만드는 조용한 함정

> **⚠️ 실행되지 않은 연속은 잊히는 게 아니라 "취소"된다**
>
> 위의 플래그들 때문에 연속이 실행되지 않으면, 그 연속은 **버려지는 게 아니라 취소된다.** 즉 그 연속에 다시 붙인 연속들은 `NotOnCanceled`로 술어를 걸지 않는 한 **실행된다.**
>
> ```csharp
> Task t1 = Task.Factory.StartNew(...);
> Task fault = t1.ContinueWith(ant => Console.WriteLine("실패"),
>                              TaskContinuationOptions.OnlyOnFaulted);
> Task t3 = fault.ContinueWith(ant => Console.WriteLine("t3"));
> ```
>
> 이 코드에서 `t3`는 **항상** 스케줄된다. `t1`이 예외를 던지지 않아도 그렇다. `t1`이 성공하면 `fault` 태스크가 취소되고, `t3`에는 아무 제약이 없으므로 무조건 실행되기 때문이다.
>
> `fault`가 실제로 실행됐을 때만 `t3`가 실행되게 하려면 이렇게 써야 한다.
>
> ```csharp
> Task t3 = fault.ContinueWith(ant => Console.WriteLine("t3"),
>                              TaskContinuationOptions.NotOnCanceled);
> ```
>
> 대안으로 `OnlyOnRanToCompletion`을 지정할 수도 있다. 차이는 `fault` 안에서 예외가 던져졌을 때 `t3`가 실행되지 않는다는 점이다.

### `ExecuteSynchronously`의 의미와 위험

기본적으로 선행 태스크와 연속 태스크는 서로 다른 스레드에서 실행될 수 있다. `TaskContinuationOptions.ExecuteSynchronously`를 지정하면 **같은 스레드에서** 실행하도록 강제할 수 있다. 아주 세밀한 연속에서는 간접 비용이 줄어 성능이 개선된다. 선행 태스크가 이미 완료된 상태라면 `ContinueWith`를 호출하는 그 스레드가 연속을 실행한다.

한 선행 태스크에 여러 연속이 붙어 있을 때, 선행이 끝나면 모든 연속이 **함께** 시작된다. 다만 `ExecuteSynchronously`를 지정하면 연속들이 **순차적으로** 실행된다.

> **⚠️ `ExecuteSynchronously`는 남의 스레드를 훔쳐 쓴다**
>
> 이 플래그를 지정한 연속은 **선행 태스크를 완료시킨 스레드** 위에서 실행된다. 그 스레드가 UI 스레드일 수도 있고, I/O 완료를 처리하던 스레드일 수도 있고, 잠금을 잡고 있는 스레드일 수도 있다.
>
> - 연속이 오래 걸리면 그 스레드를 그만큼 붙잡아 둔다. I/O 완료 처리가 지연된다.
> - 연속이 잠금을 잡으려 하는데 그 스레드가 이미 다른 잠금을 잡고 있으면 데드락 가능성이 생긴다.
> - 연속 안에서 다시 동기적으로 대기하면 스택이 깊어진다. 재귀적으로 이어지면 `StackOverflowException`까지 갈 수 있다.
>
> 그래서 이 플래그는 **아주 짧고, 잠금을 잡지 않고, 예외를 던지지 않는 연속**에만 써야 한다. 46.5절에서 `TaskCompletionSource`의 인라인 실행 문제로 다시 만나게 된다.

### 부모 태스크와 자식 태스크

태스크는 부모/자식 관계를 지원한다.

```csharp
Task<int[]> parent = new Task<int[]>(() =>
{
    var results = new int[3];   // 결과 배열

    // 이 태스크가 자식 태스크 3개를 만들고 시작한다
    new Task(() => results[0] = Sum(10000), TaskCreationOptions.AttachedToParent).Start();
    new Task(() => results[1] = Sum(20000), TaskCreationOptions.AttachedToParent).Start();
    new Task(() => results[2] = Sum(30000), TaskCreationOptions.AttachedToParent).Start();

    // 원소가 아직 초기화되지 않았을 수 있지만 배열 참조를 반환한다
    return results;
});

// 부모와 자식이 모두 완료되면 결과를 표시한다
var cwt = parent.ContinueWith(
    parentTask => Array.ForEach(parentTask.Result, Console.WriteLine));

// 부모 Task 를 시작해 자식들을 시작하게 한다
parent.Start();
```

기본적으로 다른 태스크가 만든 `Task` 객체는 자신을 만든 태스크와 아무 관계가 없는 **최상위 태스크**다. 하지만 `TaskCreationOptions.AttachedToParent` 플래그는 `Task`를 그것을 만든 `Task`와 연결해서, **모든 자식(그리고 손자)이 실행을 마칠 때까지 부모 태스크가 완료된 것으로 간주되지 않게** 한다.

연속의 강력한 기능 하나가 **모든 자식 태스크가 완료된 뒤에야 시작된다**는 것이다. 그 시점에 자식들이 던진 예외는 연속으로 마샬링된다.

```csharp
TaskCreationOptions atp = TaskCreationOptions.AttachedToParent;
Task.Factory.StartNew(() =>
{
    Task.Factory.StartNew(() => { throw null; }, atp);
    Task.Factory.StartNew(() => { throw null; }, atp);
    Task.Factory.StartNew(() => { throw null; }, atp);
})
.ContinueWith(p => Console.WriteLine(p.Exception),
              TaskContinuationOptions.OnlyOnFaulted);
```

자식이 손자를 만들면 예외는 **중첩된 `AggregateException`** 안에 겹겹이 싸인다. 그래서 `Flatten()`을 먼저 부르는 것이 관용구다(32.13절).

### 그런데 왜 대개 `await`가 낫나

`ContinueWith`는 병렬 프로그래밍 시나리오에서 여전히 유용하다(50.8절). 하지만 일반적인 비동기 코드에서는 `await`가 낫다. 이유는 셋이다.

1. **예외 처리.** `ContinueWith`를 쓰면 태스크가 실패했을 때 `AggregateException`을 직접 다뤄야 한다. `await`는 첫 내부 예외를 벗겨서 던지므로 `catch` 블록이 단순하고 깨끗하다.
2. **컨텍스트 마샬링.** UI 애플리케이션에서 `ContinueWith`로 UI를 갱신하려면 `TaskScheduler.FromCurrentSynchronizationContext()`를 넘기는 코드를 추가로 써야 한다(46.10절). `await`는 동기화 컨텍스트를 자동으로 캡처하고 복원한다.
3. **제어 흐름의 표현력.** `for`, `foreach`, `try`/`finally` 같은 명령형 제어 구조는 연속과 잘 섞이지 않는다. 루프의 현재 지역 상태("이 루프가 몇 번 더 돌지?")에 의존하기 때문이다. 연속으로 순차 실행을 만들려면 루프를 없애고 재귀 호출로 바꿔야 하고, 그 메서드 자체를 비동기로 만들려면 `TaskCompletionSource`로 상태 기계를 손으로 짜야 한다.

그 손으로 짠 상태 기계를 컴파일러가 대신 만들어 주는 것이 `async`/`await`다. 어떻게 만드는지는 47.7절에서 판다.

> **💡 `ContinueWith`가 여전히 옳은 자리**
>
> 태스크의 **결과에 접근하지 않고**, UI 스레드로 되돌아갈 필요도 없으며, 완료 자체에만 반응하면 되는 자리다. 46.9절의 커스텀 합성기 구현이 대표적이다. 그런 코드에서는 `ContinueWith(..., TaskContinuationOptions.ExecuteSynchronously, TaskScheduler.Default)`가 `GetAwaiter().OnCompleted`보다 편리하다.

## 46.5 `TaskCompletionSource` — 무엇이든 태스크로 감싸기

### 델리게이트 없이 태스크를 만든다

`Task.Run`은 델리게이트를 (풀 또는 비풀) 스레드에서 실행하는 태스크를 만든다. 태스크를 만드는 또 다른 방법이 `TaskCompletionSource`다.

`TaskCompletionSource`는 **미래에 완료되는 아무 연산이나** 태스크로 만들 수 있게 해 준다. 여러분이 손으로 조종하는 "종속(slave)" 태스크를 하나 주고, 연산이 끝났는지 실패했는지를 여러분이 직접 알려 주는 방식으로 동작한다. 이건 **I/O 바운드 작업에 이상적**이다 — 연산이 진행되는 동안 스레드를 블로킹하지 않으면서도 태스크의 모든 이점(반환값 전파, 예외 전파, 연속)을 얻는다.

쓰는 법은 간단하다. 클래스를 인스턴스화하기만 하면 된다. `Task` 속성이 태스크를 반환하는데, 이 태스크는 다른 태스크와 똑같이 기다리고 연속을 붙일 수 있다. 다만 이 태스크는 전적으로 `TaskCompletionSource` 객체가 다음 메서드들로 제어한다.

```csharp
public class TaskCompletionSource<TResult>
{
    public void SetResult(TResult result);
    public void SetException(Exception exception);
    public void SetCanceled();

    public bool TrySetResult(TResult result);
    public bool TrySetException(Exception exception);
    public bool TrySetCanceled();
    public bool TrySetCanceled(CancellationToken cancellationToken);
    // ...
}
```

이 메서드 중 하나를 호출하면 태스크에 신호가 가서 완료·실패·취소 상태 중 하나로 들어간다. **이 메서드들은 정확히 한 번만 호출해야 한다.** 다시 호출하면 `SetResult`, `SetException`, `SetCanceled`는 예외를 던지고, `Try*` 메서드는 `false`를 반환한다.

가장 단순한 예제는 이렇다. 5초를 기다린 뒤 42를 출력한다.

```csharp
var tcs = new TaskCompletionSource<int>();
new Thread(() => { Thread.Sleep(5000); tcs.SetResult(42); })
    { IsBackground = true }
    .Start();

Task<int> task = tcs.Task;      // 우리의 "종속" 태스크
Console.WriteLine(task.Result); // 42
```

> **💡 왜 `Set*`이 아니라 `TrySet*`을 쓰는가**
>
> `Set*` 계열은 이미 완료된 태스크에 다시 호출하면 `InvalidOperationException`을 던진다. 콜백이 여러 경로에서 들어올 수 있는 어댑터 코드(취소 등록 + 완료 이벤트가 경쟁하는 상황)에서는 **경합이 정상**이다. 이런 자리에서는 `TrySet*`을 쓰고 반환값으로 "내가 이겼는가"를 판단하는 편이 낫다. 46.9절의 `WithCancellation` 구현이 바로 그 예다.

### 진짜 힘은 스레드를 쓰지 않는 데 있다

`TaskCompletionSource`로 우리만의 `Run` 메서드를 만들 수 있다.

```csharp
Task<TResult> Run<TResult>(Func<TResult> function)
{
    var tcs = new TaskCompletionSource<TResult>();
    new Thread(() =>
    {
        try { tcs.SetResult(function()); }
        catch (Exception ex) { tcs.SetException(ex); }
    }).Start();
    return tcs.Task;
}
```

이건 `Task.Factory.StartNew`에 `TaskCreationOptions.LongRunning`을 지정해 비풀 스레드를 요청하는 것과 동등하다. 하지만 이건 `TaskCompletionSource`의 본래 용도가 아니다.

**`TaskCompletionSource`의 진짜 힘은 스레드를 붙잡지 않는 태스크를 만드는 데 있다.** 5초를 기다린 뒤 42를 반환하는 태스크를 생각해 보자. 스레드 없이 `Timer` 클래스로 쓸 수 있다.

```csharp
Task<int> GetAnswerToLife()
{
    var tcs = new TaskCompletionSource<int>();

    // 5000ms 뒤에 한 번 발화하는 타이머를 만든다
    var timer = new System.Timers.Timer(5000) { AutoReset = false };
    timer.Elapsed += delegate { timer.Dispose(); tcs.SetResult(42); };
    timer.Start();

    return tcs.Task;
}
```

이 메서드는 5초 뒤에 42라는 결과로 완료되는 태스크를 반환한다. 여기에 연속을 붙이면 **어떤 스레드도 블로킹하지 않고** 결과를 쓸 수 있다.

```csharp
var awaiter = GetAnswerToLife().GetAwaiter();
awaiter.OnCompleted(() => Console.WriteLine(awaiter.GetResult()));
```

이 방식이 스레드를 쓰지 않는다는 것은 **10,000개를 동시에 시작해 보면** 확인된다. 오류도, 과도한 자원 소비도 없다.

```csharp
for (int i = 0; i < 10000; i++)
    Delay(5000).GetAwaiter().OnCompleted(() => Console.WriteLine(42));
```

> **📌 그래도 스레드는 마지막에 필요하다**
>
> 타이머는 콜백을 풀 스레드에서 발화시킨다. 그래서 5초 뒤 스레드 풀은 `TaskCompletionSource`에 `SetResult(null)`을 호출해 달라는 요청 10,000건을 받는다. 요청이 처리 속도보다 빨리 도착하면 풀은 큐잉했다가 CPU에 최적인 병렬도로 처리한다. 스레드에 묶인 작업이 짧은 경우에 이상적인데, 여기가 정확히 그렇다 — 스레드에 묶인 일이라곤 `SetResult` 호출과, (UI 애플리케이션이라면) 연속을 동기화 컨텍스트에 게시하는 동작 또는 (그 외에는) 연속 자체(`Console.WriteLine(42)`)뿐이다.

### 논제네릭 `TaskCompletionSource`

이 `Delay` 메서드를 일반화하려면 반환 타입이 `Task<int>`가 아니라 `Task`여야 한다. 그런데 `TaskCompletionSource`에는 오랫동안 논제네릭 버전이 없었다. 해결책은 간단했다. `Task<TResult>`가 `Task`에서 파생되므로, `TaskCompletionSource<아무거나>`를 만들고 그것이 주는 `Task<아무거나>`를 `Task`로 암묵 변환하면 된다.

```csharp
var tcs = new TaskCompletionSource<object>();
Task task = tcs.Task;
```

```csharp
Task Delay(int milliseconds)
{
    var tcs = new TaskCompletionSource<object>();
    var timer = new System.Timers.Timer(milliseconds) { AutoReset = false };
    timer.Elapsed += delegate { timer.Dispose(); tcs.SetResult(null); };
    timer.Start();
    return tcs.Task;
}
```

.NET 5부터는 **논제네릭 `TaskCompletionSource`** 가 도입되었으므로, .NET 5 이상을 대상으로 한다면 `TaskCompletionSource<object>` 대신 `TaskCompletionSource`를 쓰면 된다.

```csharp
// ※.NET 5
var tcs = new TaskCompletionSource();
Task task = tcs.Task;
tcs.SetResult();                 // 결과값이 없다
```

### 어댑터 패턴 — 이벤트, 콜백, 레거시 APM

`TaskCompletionSource`의 가장 흔한 실무 용도는 **태스크를 모르는 API를 태스크로 감싸는 것**이다.

**이벤트 기반 API(EAP) 감싸기.** `WebClient`처럼 완료를 이벤트로 알리는 클래스를 감싸는 코드는 이렇게 생겼다.

```csharp
private static async Task<string> AwaitWebClient(Uri uri)
{
    // System.Net.WebClient 는 이벤트 기반 비동기 패턴을 지원한다
    var wc = new System.Net.WebClient();

    // TaskCompletionSource 와 그 밑의 Task 객체를 만든다
    var tcs = new TaskCompletionSource<string>();

    // 문자열 다운로드가 끝나면 WebClient 가 DownloadStringCompleted 이벤트를
    // 발생시키고, 그것이 TaskCompletionSource 를 완료시킨다
    wc.DownloadStringCompleted += (s, e) =>
    {
        if (e.Cancelled) tcs.SetCanceled();
        else if (e.Error != null) tcs.SetException(e.Error);
        else tcs.SetResult(e.Result);
    };

    // 비동기 연산을 시작한다
    wc.DownloadStringAsync(uri);

    // 이제 TaskCompletionSource 의 Task 를 평소처럼 await 하고 결과를 처리한다
    string result = await tcs.Task;
    return result;
}
```

이 코드의 구조가 어댑터 패턴의 정석이다. **세 갈래(취소·실패·성공)를 빠짐없이 처리한다**는 점에 주목하라. 하나라도 빠지면 그 경로에서 태스크가 영원히 완료되지 않고, 그것을 기다리는 코드는 영원히 멈춘다.

**콜백 기반 API 감싸기.** 콜백에 `Exception`과 결과가 함께 오는 API도 같은 모양이다.

```csharp
Task<Config> LoadConfigAsync(string path)
{
    var tcs = new TaskCompletionSource<Config>();
    LegacyLoader.Load(path, (config, error) =>
    {
        if (error != null) tcs.TrySetException(error);
        else tcs.TrySetResult(config);
    });
    return tcs.Task;
}
```

**레거시 APM(`Begin`/`End`) 감싸기.** 가장 오래된 비동기 패턴은 **APM(Asynchronous Programming Model)** 으로, `Begin`으로 시작하고 `End`로 끝나는 메서드 쌍과 `IAsyncResult` 인터페이스를 쓴다. `Stream.Read`를 예로 보면 동기 버전, 태스크 버전, APM 버전이 이렇게 대응된다.

```csharp
public int Read(byte[] buffer, int offset, int size);                    // 동기
public Task<int> ReadAsync(byte[] buffer, int offset, int size);         // 태스크

public IAsyncResult BeginRead(byte[] buffer, int offset, int size,       // APM
                              AsyncCallback callback, object state);
public int EndRead(IAsyncResult asyncResult);
```

APM은 쓰기 어색할 뿐 아니라 올바르게 **구현하기**가 놀랍도록 어렵다. APM 메서드를 다루는 가장 쉬운 방법은 `Task.Factory.FromAsync` 어댑터 메서드를 호출해 APM 메서드 쌍을 `Task`로 변환하는 것이다. **내부적으로 이 메서드는 `TaskCompletionSource`를 써서, APM 연산이 완료되거나 실패할 때 신호를 받는 태스크를 만들어 준다.**

```csharp
Task<int> readChunk = Task<int>.Factory.FromAsync(
    stream.BeginRead, stream.EndRead, buffer, 0, 1000, null);
```

APM과 EAP의 상세는 47.16절에서 다룬다.

### `RunContinuationsAsynchronously` — 반드시 알아야 할 함정

여기가 이 절에서 가장 중요한 부분이다.

> **⚠️ `SetResult`는 연속을 그 자리에서(동기적으로) 실행할 수 있다**
>
> `TaskCompletionSource<TResult>`에서 알아 둬야 할 한 가지는, **결과를 설정하면 연결된 태스크에 붙어 있던 연속이 같은 스레드에서 동기적으로 실행될 수 있다**는 것이다. 연속이 정확히 어떻게 실행되는지는 관련된 스레드와 동기화 컨텍스트의 여러 측면에 달려 있다.
>
> 이게 왜 위험한가. `tcs.SetResult(x)`를 호출하는 스레드는 대개 **여러분의 스레드가 아니다.** 드라이버의 I/O 완료 콜백 스레드, 타이머 스레드, 락을 잡고 있는 라이브러리 내부 스레드일 수 있다. 그런데 `SetResult`가 반환되기 전에 그 스레드 위에서 `await` 뒤의 코드 전부가 실행된다.
>
> 결과는 셋이다.
>
> **1. 데드락.** `SetResult`를 잠금 안에서 호출했는데, 연속 코드가 같은 잠금을 잡으려 하면 데드락이다. 프로듀서/컨슈머 큐를 직접 구현할 때 전형적으로 밟는 지뢰다.
>
> ```csharp
> // 위험한 코드
> lock (_gate)
> {
>     _items.Enqueue(item);
>     _waiter?.SetResult(item);   // 여기서 컨슈머의 연속이 이 스레드에서 실행된다
>                                 // 그 연속이 lock (_gate) 를 잡으려 하면? 재진입 또는 데드락
> }
> ```
>
> **2. 스택 오버플로.** 완료와 연속이 서로를 부르는 구조라면 스택이 재귀적으로 쌓인다. 파이프라인의 각 단계가 `TaskCompletionSource`로 만들어져 있고 전부 동기적으로 완료되면, 단계 수만큼 스택 프레임이 쌓여 `StackOverflowException`으로 끝난다.
>
> **3. 지연 폭탄.** I/O 완료 스레드나 타이머 스레드 위에서 사용자 코드가 실행되면, 그 스레드가 처리해야 할 다른 완료들이 전부 밀린다. 처리량 그래프에서 설명되지 않는 지연 스파이크로 나타난다.
>
> **해법은 하나다.** 생성자에 `TaskCreationOptions.RunContinuationsAsynchronously`를 넘겨라.
>
> ```csharp
> var tcs = new TaskCompletionSource<int>(
>     TaskCreationOptions.RunContinuationsAsynchronously);
> ```
>
> 이러면 `SetResult`는 연속을 **스레드 풀에 큐잉만 하고 즉시 반환한다.** 완료시키는 스레드는 자기 일로 돌아가고, 연속은 별개의 풀 스레드에서 실행된다. 대가는 컨텍스트 스위치 하나다. 그 정도는 데드락과 바꿀 만하다.
>
> **여러분이 `TaskCompletionSource`를 직접 만드는 거의 모든 경우에 이 플래그를 켜는 것이 옳다.** 켜지 않는 것이 옳은 경우는 완료 스레드가 여러분의 통제 아래 있고, 연속이 매우 짧으며, 어떤 잠금도 잡지 않는다는 것을 확신할 때뿐이다.

이 플래그는 `TaskCreationOptions`에 속하지만 `TaskCompletionSource` 생성자에 전달할 수 있는 **유일하게 의미 있는 플래그**에 가깝다. 논제네릭 `TaskCompletionSource`(※.NET 5)도 같은 생성자 오버로드를 갖는다.

> **💡 라이브러리를 쓰는 쪽의 방어책**
>
> 남이 만든 `TaskCompletionSource`가 이 플래그를 켰는지 알 수 없다면, 여러분 쪽에서 방어할 수 있다. 완료 통지를 받은 뒤 무거운 작업이나 잠금이 필요하다면 `await` 다음 줄이 아니라 `await Task.Yield()` 뒤에 두거나, `Task.Run`으로 명시적으로 풀에 던져라. 다만 이건 대증 요법이고, 근본 해법은 생산자 쪽에서 플래그를 켜는 것이다.

### 예외를 태스크 밖으로 내보내지 않는 설계

배경 작업의 예외 처리에 대한 다른 관점도 있다. **예외가 애초에 백그라운드 작업 밖으로 새어 나가지 않게 하는 것이 거의 모든 경우에 더 낫다.** `TaskCompletionSource<>` 클래스를 쓴다면, 그것은 `TrySetException()`을 절대 호출하지 않고 모든 태스크가 어떤 식으로든 `TrySetResult()`를 호출해 완료를 알리게 한다는 뜻이다.

물론 모든 예외를 잡으라는 뜻은 아니다. **복구할 수 있는 예외만** 잡아야 한다. 예를 들어 원격 호스트가 응답하지 않는다는 `WebException`은 합리적으로 복구할 수 있다. 다른 예외 타입은 더 심각한 문제를 뜻하므로 계속 예외를 만들고 처리를 멈춰야 한다.

```csharp
private static Task<byte[]> StartDownload(string url)
{
    var tcs = new TaskCompletionSource<byte[]>(url);
    var wc = new WebClient();
    wc.DownloadDataCompleted += (sender, e) =>
    {
        if (e.UserState == tcs)
        {
            if (e.Cancelled)
                tcs.TrySetCanceled();
            else if (e.Error != null)
            {
                if (e.Error is WebException)
                    tcs.TrySetResult(new byte[0]);   // 0바이트 읽음으로 복구
                else
                    tcs.TrySetException(e.Error);    // 나머지는 정상 경로로 던진다
            }
            else
                tcs.TrySetResult(e.Result);
        }
    };
    wc.DownloadDataAsync(new Uri(url), tcs);
    return tcs.Task;
}
```

`WebException`은 0바이트를 읽었다는 반환으로 처리하고, 나머지 예외는 정상 채널로 던진다. 이렇게 해도 `AggregateException`이 던져질 때를 다뤄야 하는 건 여전하지만, 그것을 치명적 오류로 취급하고 나머지는 배경 태스크가 처리하게 만들 수 있다.

### 태스크를 완료 순서대로 재배열하기

`TaskCompletionSource`의 응용 하나를 보자. 태스크 여러 개를 시작한 뒤 **완료된 순서대로** 처리하고 싶다고 하자. 시작한 순서대로 `await`하면 오래 걸리는 태스크 뒤에 이미 끝난 태스크들이 줄줄이 밀린다. `Task.WhenAny`를 반복 호출하는 방법도 있지만, 호출할 때마다 새 태스크가 만들어지므로 태스크 수가 늘어날수록 할당이 늘어나 비효율적이다.

`TaskCompletionSource`를 쓰면 할당을 한 번으로 끝낼 수 있다.

```csharp
public static Task<T>[] OrderByCompletion<T>(this IEnumerable<Task<T>> tasks)
{
    // 여러 번 열거되므로 List 로 복사한다
    var sourceTasks = tasks.ToList();

    // 소스를 할당하고 출력 태스크를 할당한다.
    // 각 출력 태스크는 대응하는 완료 소스의 태스크다
    var completionSources = new TaskCompletionSource<T>[sourceTasks.Count];
    var outputTasks = new Task<T>[completionSources.Length];
    for (int i = 0; i < completionSources.Length; i++)
    {
        completionSources[i] = new TaskCompletionSource<T>();
        outputTasks[i] = completionSources[i].Task;
    }

    // 각 태스크의 연속이 자기 결과를 완료 소스 배열의 다음 빈 자리에 넣는다
    int nextTaskIndex = -1;
    Action<Task<T>> continuation = completed =>
    {
        var bucket = completionSources[Interlocked.Increment(ref nextTaskIndex)];
        if (completed.IsCompleted)
            bucket.TrySetResult(completed.Result);
        else if (completed.IsFaulted)
            bucket.TrySetException(completed.Exception);
    };

    // 각 입력 태스크에 위 연속을 붙인다
    foreach (var inputTask in sourceTasks)
    {
        inputTask.ContinueWith(continuation, CancellationToken.None,
            TaskContinuationOptions.ExecuteSynchronously,
            TaskScheduler.Default);
    }

    return outputTasks;
}
```

> **⚠️ 이 코드의 `IsCompleted` 검사는 원천 자료 그대로이지만 순서가 위태롭다**
>
> `IsCompleted`는 실패·취소를 포함해 "끝났다"는 뜻이므로(46.3절), 실패한 태스크도 첫 분기에 걸려 `completed.Result`에서 예외가 다시 던져진다. 실제로 쓴다면 `IsFaulted`·`IsCanceled`를 먼저 검사하거나 `IsCompletedSuccessfully`(※.NET Core 2.0)를 쓰는 편이 안전하다.

빈 자리를 고르는 데 `Interlocked.Increment`를 쓰는 것이 핵심이다(48.4절). 태스크 10개를 시작해 3, 7, 2, 0, 4, 9, 1, 6, 5, 8 순서로 끝났다면, 태스크 3의 연속이 결과를 0번 슬롯에, 태스크 7이 1번 슬롯에, 태스크 2가 2번 슬롯에 넣는 식으로 진행되어 마지막에 태스크 8이 9번 슬롯을 채운다.

.NET 9부터는 이 패턴을 표준 API가 대신해 준다 — `Task.WhenEach`다(46.9절).

## 46.6 `Task.Delay`, `PeriodicTimer`, 주기적 작업

### `Task.Delay` — 스레드를 잡지 않는 기다림

`Task.Delay`는 지정한 시간이 지나면 완료되는 태스크를 돌려준다.

```csharp
public static Task Delay(int millisecondsDelay);
public static Task Delay(TimeSpan delay);
public static Task Delay(TimeSpan delay, CancellationToken cancellationToken);       // int 오버로드도 있다
public static Task Delay(TimeSpan delay, TimeProvider timeProvider);                 // ※.NET 8
```

문법만 보면 `Thread.Sleep`의 비동기 판이다. 실제로 45.2절에서 본 `Thread.Sleep`과 하는 일이 겉으로는 같아 보인다. 그러나 **런타임 동작이 근본적으로 다르다.**

`Thread.Sleep(2000)`은 호출한 스레드를 커널의 대기 상태로 밀어 넣는다. 그 2초 동안 그 스레드는 아무 일도 못 하지만 여전히 존재하며 1MB 남짓의 사용자 모드 스택과 커널 객체를 붙들고 있다. 그 스레드가 풀 스레드였다면 풀의 워커 하나가 2초간 증발한 셈이고, 46.2절에서 본 hill-climbing이 이것을 "일이 많아 처리량이 안 나온다"로 오해해 스레드를 더 주입한다.

`Task.Delay(2000)`은 스레드를 전혀 쓰지 않는다. 내부적으로 타이머 큐에 항목 하나를 등록하고, 그 항목이 만기되면 내부 완료 소스를 완료시키는 것이 전부다. 만기를 기다리는 동안 **어떤 스레드도 블로킹되지 않는다.** 만기 시점에만 풀 스레드 하나가 잠깐 깨어나 연속을 실행한다.

| 항목 | `Thread.Sleep(n)` | `Task.Delay(n)` |
|---|---|---|
| 반환 타입 | `void` | `Task` |
| 대기 동안 스레드 점유 | 점유한다 (커널 대기) | 점유하지 않는다 |
| 취소 | 불가 | `CancellationToken` 오버로드로 가능 |
| UI 스레드에서 호출 | UI가 얼어붙는다 | `await`하면 UI가 계속 돈다 |
| 풀 스레드에서 호출 | 풀 스레드 하나 소모, 주입 유발 | 소모 없음 |
| 소요 자원 | 스레드 1개 | 타이머 큐 항목 1개 |
| 만기 후 실행 스레드 | 잠들었던 그 스레드 | 연속을 실행할 임의의 스레드 |

> **⚠️ `Task.Delay(n).Wait()`는 두 세계의 나쁜 점만 모은 것이다**
>
> `Task.Delay(2000).Wait()`나 `Task.Delay(2000).GetAwaiter().GetResult()`는 `Thread.Sleep(2000)`보다 **나쁘다.** 호출 스레드는 어차피 2초간 블로킹되고, 게다가 타이머 항목 등록·태스크 할당·연속 스케줄링 비용까지 추가로 낸다. 동기적으로 쉬어야 한다면 `Thread.Sleep`을 써라. 그럴 일이 없어야 정상이지만.
>
> 이 sync-over-async 관용구가 데드락으로 이어지는 정확한 메커니즘은 47.14절에서 다룬다.

### 취소 토큰 오버로드

취소 토큰을 넘기면 대기 중에 취소가 요청되었을 때 태스크가 즉시 **Canceled 상태로** 끝난다.

```csharp
var cts = new CancellationTokenSource();
try
{
    await Task.Delay(TimeSpan.FromMinutes(5), cts.Token);
    Console.WriteLine("5분이 지났다");
}
catch (OperationCanceledException) { Console.WriteLine("기다리는 도중 취소되었다"); }
```

이것이 중요한 이유는 **취소가 대기 시간을 단축한다**는 데 있다. 취소 토큰 없이 `await Task.Delay(60_000)`을 걸어 두면 취소를 요청해도 그 1분이 다 지나야 루프가 다음 검사 지점에 도달한다. 토큰을 넘기면 그 자리에서 깨어난다.

> **📌 `TaskCanceledException`은 `OperationCanceledException`의 파생 타입이다**
>
> `Task.Delay`가 취소로 끝날 때 `await`가 실제로 던지는 것은 `System.Threading.Tasks.TaskCanceledException`이다. 이 타입은 `System.OperationCanceledException`을 상속하므로 `catch (OperationCanceledException)`으로 잡힌다. **취소를 잡는 코드는 언제나 기반 타입인 `OperationCanceledException`으로 잡아라.** `TaskCanceledException`으로만 잡으면 `CancellationToken.ThrowIfCancellationRequested()`가 던지는 순수 `OperationCanceledException`을 놓친다.

### 해상도의 한계

`Task.Delay(1)`이 정확히 1밀리초 뒤에 완료된다고 기대하면 안 된다. 이 지연은 OS 타이머 인프라 위에 얹혀 있고, 그 해상도는 플랫폼에 달려 있다. 원천 자료는 멀티스레드 타이머의 정밀도를 **일반적으로 10~20밀리초 수준**으로 서술한다. `Task.Delay`도 같은 인프라를 쓰므로 같은 제약을 받는다.

게다가 만기와 실제 실행 사이에 단계가 하나 더 있다. 타이머가 만기되면 연속이 스레드 풀에 큐잉되고, 풀이 포화 상태면 거기서 또 밀린다. 즉 실제 지연은 **요청한 시간 이상**이다. `Task.Delay`는 "최소 n밀리초 뒤"를 보장할 뿐 "정확히 n밀리초 뒤"를 보장하지 않는다.

> **⚠️ `Task.Delay`를 벤치마크나 정밀 스케줄링의 시계로 쓰지 마라**
>
> 1밀리초 단위 스케줄링이 필요한 오디오·계측 코드에서 `Task.Delay(1)`을 1000번 돌리면 1초가 아니라 10초를 넘게 걸릴 수 있다. 정밀한 시간 측정은 `Stopwatch`로 하고, 고해상도 주기 작업은 애초에 관리 코드의 타이머로 만들 것이 아니다. 또 하나, `Task.Delay(0)`은 특별 취급되어 이미 완료된 태스크를 돌려주므로 아무것도 양보하지 않는다 — 스레드 양보가 목적이라면 `Task.Yield()`를 써라.
### `System.Threading.Timer`와 재진입 문제

주기 작업의 고전적 수단은 `System.Threading.Timer`다.

```csharp
public sealed class Timer : MarshalByRefObject, IDisposable
{
    // dueTime/period 는 int, uint, long, TimeSpan 오버로드가 있다
    public Timer(TimerCallback callback, object state, TimeSpan dueTime, TimeSpan period);
    public bool Change(int dueTime, int period);
    public void Dispose();                          // IDisposable 구현
    public bool Dispose(WaitHandle notifyObject);   // 대기 중인 콜백이 끝나면 신호
}

delegate void TimerCallback(object state);
```

`dueTime`은 첫 호출까지 기다릴 밀리초, `period`는 이후 호출 간격이다. `period`에 `Timeout.Infinite`(-1)를 주면 콜백은 딱 한 번만 호출된다.

런타임 동작은 이렇다. **스레드 풀은 모든 `Timer` 객체를 위해 스레드를 딱 하나만 쓴다.** 이 스레드는 다음 타이머의 만기 시각을 알고 있다가, 만기가 되면 깨어나서 내부적으로 `ThreadPool.QueueUserWorkItem`을 호출해 항목을 풀의 전역 큐에 넣는다(46.1절). 콜백을 실행하는 것은 그 항목을 꺼낸 워커 스레드다.

여기서 함정이 나온다.

> **⚠️ 콜백이 아직 도는 중에 다음 틱이 겹친다**
>
> 타이머 스레드는 콜백이 끝났는지 신경 쓰지 않는다. `period`가 2초인데 콜백이 3초 걸리면, 첫 콜백이 아직 돌고 있는 2초 시점에 두 번째 항목이 큐에 들어가고 **다른 풀 스레드가 콜백을 동시에 실행한다.** 부하가 계속되면 콜백 인스턴스가 계속 쌓인다.
>
> 결과는 셋이다. 첫째, 콜백이 공유 상태를 만진다면 그 상태가 깨진다 — 콜백은 스레드 안전해야 한다. 둘째, 콜백이 잠금을 잡는다면 겹친 인스턴스들이 그 잠금 앞에 줄을 서서 풀 스레드를 통째로 소모한다. 셋째, 최악의 경우 46.2절에서 본 스레드 풀 기아로 번진다.
>
> 이 겹침은 `System.Timers.Timer`도 똑같이 갖는다. 원천 자료의 표현대로 "`Elapsed` 이벤트는 이전 `Elapsed`가 끝났는지와 무관하게 (거의) 정확한 시각에 항상 발생한다." 따라서 **콜백과 `Elapsed` 핸들러는 반드시 스레드 안전하게 작성해야 한다.**

회피법은 원천 자료가 권하는 관용구다. **주기를 아예 쓰지 않고 매번 다시 예약한다.**

```csharp
internal static class TimerDemo
{
    private static Timer s_timer;

    public static void Main()
    {
        // 절대 발화하지 않는 타이머를 먼저 만든다. Status 가 풀 스레드에서 호출되기
        // 전에 s_timer 가 타이머를 참조하도록 보장하기 위해서다
        s_timer = new Timer(Status, null, Timeout.Infinite, Timeout.Infinite);
        s_timer.Change(0, Timeout.Infinite);    // 이제 발화시켜도 안전하다
        Console.ReadLine();                     // 프로세스가 끝나지 않게 붙잡는다
    }

    private static void Status(object state)
    {
        Console.WriteLine("Status 진입 {0}", DateTime.Now);
        Thread.Sleep(1000);                     // 다른 작업 시뮬레이션 (1초)
        s_timer.Change(2000, Timeout.Infinite); // 반환 직전에 다음 발화를 예약한다
    }
}
```

`period`를 `Timeout.Infinite`로 두었으므로 타이머는 매번 한 번씩만 발화한다. 콜백이 **끝나기 직전에** 다음 발화를 예약하므로 두 인스턴스가 겹칠 수 없다. 대가는 주기가 "2초 간격"이 아니라 "작업 종료 후 2초"가 된다는 것 — 드리프트가 누적된다. 이 문제는 곧 다시 다룬다.

> **⚠️ `Timer` 객체를 살아 있게 붙들어야 한다**
>
> `Timer` 객체가 가비지 컬렉션되면 그 파이널라이저가 스레드 풀에 타이머 취소를 알린다. 즉 **콜백이 조용히 멈춘다.** 지역 변수에만 담아 둔 타이머는 메서드가 반환된 뒤 어느 시점에 수거될 수 있고, 최적화된 릴리스 빌드에서는 메서드가 아직 실행 중이어도 그 변수가 더는 읽히지 않는다면 수거 대상이 된다.
>
> 그래서 위 예제가 `s_timer`를 정적 필드에 담는다. "타이머가 왜 몇 분 뒤에 멈추는가"는 디버그 빌드에서는 재현되지 않고 릴리스에서만 터지는 대표적 사고다. 객체가 언제 수거 대상이 되는지는 34장에서 다룬다.

> **📌 `System.Timers.Timer`는 `System.Threading.Timer`의 래퍼다**
>
> 같은 엔진 위에 편의 기능을 씌운 것이다. `Change` 대신 `Interval` 속성, 콜백 델리게이트 대신 `Elapsed` 이벤트, `Enabled` 속성과 `Start`/`Stop`, 반복 여부를 결정하는 `AutoReset` 플래그(기본 `true`), WPF 요소나 WinForms 컨트롤로 안전하게 되돌리는 `SynchronizingObject` 속성을 갖고, `IComponent`를 구현하므로 디자이너의 컴포넌트 트레이에 올릴 수 있다. 원천 자료 저자의 평가는 냉정하다 — 디자인 표면에 타이머를 얹어야 하는 것이 아니라면 `System.Threading.Timer`를 쓰라는 것이다. 타이머 다섯 종류의 전면 비교는 49.10절에 있다.

### `PeriodicTimer` — 겹침이 구조적으로 불가능한 타이머 ※.NET 6

`PeriodicTimer`는 이름과 달리 **엄밀히는 타이머가 아니다.** 비동기 반복문을 돕는 클래스다.

```csharp
public sealed class PeriodicTimer : IDisposable
{
    public PeriodicTimer(TimeSpan period);
    public PeriodicTimer(TimeSpan period, TimeProvider timeProvider);   // ※.NET 8

    public ValueTask<bool> WaitForNextTickAsync(
        CancellationToken cancellationToken = default);

    public void Dispose();
}
```

쓰는 모양은 이렇다.

```csharp
var timer = new PeriodicTimer(TimeSpan.FromSeconds(1));
StartPeriodicOperation();

// 반복을 멈추고 싶을 때 타이머를 Dispose 한다

async void StartPeriodicOperation()
{
    while (await timer.WaitForNextTickAsync())
    {
        Console.WriteLine("Tick");
        // 여기서 할 일
    }
}
```

**왜 겹침이 구조적으로 불가능한가.** `Timer`와 `PeriodicTimer`의 차이는 제어의 방향이다.

```text
  System.Threading.Timer  —  푸시(push) 모델
  ┌──────────────┐  만기   ┌────────────┐  큐잉   ┌──────────────┐
  │ 타이머 스레드 │ ──────→ │ 전역 큐    │ ──────→│ 워커 스레드 A │→ 콜백 실행
  └──────────────┘         └────────────┘         └──────────────┘
         │ 2초 뒤 또 만기 (앞 콜백이 끝났는지 모른다)
         └────────────────────────────────────────→ 워커 스레드 B → 콜백 동시 실행

  PeriodicTimer  —  풀(pull) 모델
  ┌──────────────────────────────────────────────────────────┐
  │ while (await timer.WaitForNextTickAsync())                │
  │ {                                                         │
  │     본문;   ← 본문이 끝나야 다음 WaitForNextTickAsync 호출 │
  │ }                                                         │
  └──────────────────────────────────────────────────────────┘
    소비자가 하나뿐이고, 다음 틱을 "요청"해야 받는다 → 동시 실행 불가
```

`Timer`는 콜백을 **밀어 넣으므로** 앞 콜백의 상태를 모르고 겹침을 막을 수 없다. `PeriodicTimer`는 틱을 **꺼내 간다.** 반복문의 본문이 끝나야 다음 `WaitForNextTickAsync` 호출에 도달하므로, 본문 두 개가 동시에 도는 상태가 **문법적으로 만들어질 수 없다.** 이것이 이 타입의 존재 이유다.

| 항목 | `System.Threading.Timer` | `PeriodicTimer` ※.NET 6 |
|---|---|---|
| 제어 방향 | 푸시(콜백 호출) | 풀(`await`로 꺼냄) |
| 콜백 겹침 | 발생한다 | 구조적으로 불가능 |
| 콜백 스레드 | 매번 다른 풀 스레드 | `await` 규칙을 따름(컨텍스트 캡처) |
| 정지 방법 | `Dispose()` / `Change(Infinite, Infinite)` | `Dispose()` → 대기가 `false` 반환 |
| 취소 토큰 | 없음 | `WaitForNextTickAsync(ct)` |
| 반환 타입 | `void` 콜백 | `ValueTask<bool>` |
| 예외 처리 | 콜백에서 새면 프로세스 종료 위험 | 반복문 밖 `try`로 잡힌다 |
| GC 수거 시 | 조용히 멈춘다 | 반복문이 참조를 붙들고 있다 |

**정지와 취소의 차이가 중요하다.** `timer.Dispose()`를 호출하면 대기 중이던 `WaitForNextTickAsync`가 **`false`를 반환하고** `while` 조건이 거짓이 되어 반복문이 정상적으로 빠져나간다 — 예외가 아니다. 반면 `WaitForNextTickAsync(ct)`에 넘긴 토큰이 취소되면 **`OperationCanceledException`이 던져져** 반복문이 예외로 빠져나간다. "이제 그만 돌자"는 `Dispose`, "지금 하던 작업을 포함해 전부 중단하라"는 취소 토큰이다.

> **💡 `PeriodicTimer`는 `using`과 함께, `await using`이 아니라**
>
> `PeriodicTimer`는 `IDisposable`만 구현한다(`IAsyncDisposable`이 아니다). 소유 범위가 명확하면 `using`으로 감싸는 것이 정석이다.
>
> ```csharp
> public async Task RunAsync(CancellationToken ct)
> {
>     using var timer = new PeriodicTimer(TimeSpan.FromSeconds(30));
>     while (await timer.WaitForNextTickAsync(ct))
>     {
>         try { await PollAsync(ct); }
>         catch (OperationCanceledException) when (ct.IsCancellationRequested) { throw; }
>         catch (Exception ex) { _logger.LogError(ex, "폴링 실패"); }   // 한 번 실패해도 계속 돈다
>     }
> }
> ```
>
> 본문의 `try`가 핵심이다. 이것이 없으면 폴링 한 번의 실패가 반복문 전체를 끝내 버린다. 취소 예외는 다시 던져 반복을 끝내고, 나머지는 로깅하고 다음 틱으로 넘어가는 것이 주기 작업의 표준 골격이다.

### 드리프트와 실행 시간이 주기를 넘을 때

주기 작업의 진짜 설계 문제는 타이머 API 선택이 아니라 **"작업이 주기보다 오래 걸리면 어떻게 할 것인가"** 다.

먼저 드리프트부터 보자. `await DoWorkAsync(ct)` 뒤에 `await Task.Delay(1000, ct)`를 거는 흔한 반복문은, 작업이 300밀리초 걸린다면 한 바퀴가 1.3초다. 하루가 지나면 예정보다 약 6,600번 적게 실행된다. "매일 자정에"나 "매분 0초에" 같은 요구라면 이 방식은 오답이다. 이것을 **드리프트(drift)** 라고 한다.

드리프트를 없애려면 **다음 실행 시각을 절대 시간으로 계산**해야 한다.

```csharp
// 드리프트를 보정하는 고정 주기 반복
public static async Task RunAtFixedRateAsync(
    Func<CancellationToken, Task> work, TimeSpan period, CancellationToken ct)
{
    var sw = Stopwatch.StartNew();
    long tick = 0;
    while (!ct.IsCancellationRequested)
    {
        TimeSpan next = TimeSpan.FromTicks(period.Ticks * (++tick));   // 절대 시각
        TimeSpan wait = next - sw.Elapsed;
        if (wait > TimeSpan.Zero) await Task.Delay(wait, ct);          // 남은 만큼만
        // wait <= 0 이면 이미 늦은 것이다. 아래 표의 정책에 따라 처리한다
        await work(ct);
    }
}
```

작업 시간이 주기를 넘어설 때의 정책은 셋 중 하나다.

| 정책 | 동작 | 장점 | 대가 | 적합한 경우 |
|---|---|---|---|---|
| 고정 지연(fixed delay) | 작업이 끝난 뒤 항상 주기만큼 쉰다 | 겹침 없음, 시스템 부하 자동 완화 | 드리프트 누적, 실행 횟수 예측 불가 | 폴링, 헬스 체크, 캐시 갱신 |
| 밀린 틱 몰아치기(catch-up) | 늦은 만큼 지연 없이 연속 실행해 따라잡는다 | 총 실행 횟수 보존 | 부하 급증, 밀림이 계속되면 영원히 못 따라잡는다 | 회계 마감처럼 횟수 자체가 의미인 작업 |
| 밀린 틱 버리기(skip) | 늦었으면 그 틱들을 버리고 다음 정각으로 | 드리프트 없음, 부하 폭증 없음 | 실행이 누락된다 | 모니터링 샘플링, 대시보드 갱신 |

> **💡 기본값은 "밀린 틱 버리기"로 두고, 필요할 때만 바꿔라**
>
> 실무에서 가장 자주 옳은 정책은 **버리기**다. 30초마다 지표를 수집하는 작업이 어쩌다 40초 걸렸다면, 밀린 것을 따라잡겠다고 즉시 한 번 더 도는 것은 이미 과부하인 시스템을 더 밀어붙이는 짓이다. 그 틱은 없던 것으로 하고 다음 정각을 기다리는 편이 낫다.
>
> "몰아치기"를 골라야 하는 경우는 **틱 하나하나가 처리해야 할 일감을 대표할 때**뿐이다. 그마저도 밀림이 구조적이라면 몰아치기는 문제를 감출 뿐 풀지 못한다. 이때 필요한 것은 타이머가 아니라 백프레셔가 있는 큐다(51.2절).
정리하면 이렇다. 비동기 작업을 겹침 없이 주기 실행해야 하면 `PeriodicTimer`, 동기 콜백이고 겹침을 감당할 수 있으면 `System.Threading.Timer`, .NET 6 미만에서 겹침을 막아야 하면 `Timer` + `period = Timeout.Infinite` + `Change` 재예약, UI 갱신이면 `DispatcherTimer`/WinForms `Timer`(49.10절)다.

## 46.7 실행 컨텍스트(`ExecutionContext`)의 흐름과 캡처

### 무엇이 흐르는가

모든 스레드에는 **실행 컨텍스트(execution context)** 라는 자료구조가 딸려 있다. 여기에는 보안 설정(압축 스택, 스레드의 `Principal` 속성, 윈도우 ID), 호스트 설정, 논리적 호출 컨텍스트 데이터가 들어 있다. 스레드가 코드를 실행할 때 일부 연산은 이 설정값의 영향을 받는다 — 보안 설정이 대표적이다.

이상적으로는, 어떤 스레드가 다른(도우미) 스레드에게 일을 시킬 때 **발주한 스레드의 실행 컨텍스트가 도우미 스레드로 흘러가야(복사되어야) 한다.** 그래야 도우미가 하는 일이 같은 보안 설정·호스트 설정으로 실행된다. **CLR은 기본적으로 이 흐름을 자동으로 만들어 준다.** 현대 .NET에서 실행 컨텍스트를 통해 흐르는 것 중 애플리케이션 코드가 실제로 마주치는 것은 사실상 `AsyncLocal<T>`다.

```csharp
static readonly AsyncLocal<string> _correlationId = new AsyncLocal<string>();

async Task HandleRequestAsync(string id)
{
    _correlationId.Value = id;          // 여기서 설정하면
    await Task.Delay(100);
    await DoWorkAsync();                // 여기서도 보인다 — 스레드가 바뀌었어도
}

async Task DoWorkAsync()
{
    _logger.LogInformation("처리 중 (상관 ID: {Id})", _correlationId.Value);   // id 가 보인다
}
```

`[ThreadStatic]`이나 `ThreadLocal<T>`는 **스레드**에 값을 묶으므로, `await` 뒤에 다른 스레드로 돌아올 수 있는 비동기 코드에서는 무용지물이다(49.8절). `AsyncLocal<T>`는 스레드가 아니라 **논리적 호출 흐름**에 값을 묶으며, 그것을 실어 나르는 운반체가 `ExecutionContext`다. 상세는 49.9절에서 다룬다.

### 어디서 캡처되고 어디서 복원되는가

핵심 규칙은 하나다. **비동기 작업을 "예약하는 시점"에 현재 스레드의 실행 컨텍스트가 캡처되고, 그 작업이 "실행되는 시점"에 복원된다.**

| 예약 지점 | 캡처 시점 | 복원되는 곳 |
|---|---|---|
| `ThreadPool.QueueUserWorkItem(cb)` | `QueueUserWorkItem` 호출 시 | 콜백을 실행하는 워커 스레드 |
| `ThreadPool.UnsafeQueueUserWorkItem(cb)` | **캡처하지 않는다** | 워커 스레드의 기존 컨텍스트 |
| `Task.Run(f)` / `new Task(...).Start()` | 태스크를 스케줄링할 때 | 태스크 본문 실행 스레드 |
| `task.ContinueWith(c)` | `ContinueWith` 호출 시 | 연속 실행 스레드 |
| `await task` | `await`가 일시 중단될 때 | `await` 뒷부분을 실행하는 스레드 |
| `new Timer(cb, ...)` | 타이머 생성 시 | 콜백 실행 스레드 |
| `token.Register(cb)` | `Register` 호출 시 | `Cancel()`을 호출한 스레드 |
| `token.UnsafeRegister(cb, s)` | **캡처하지 않는다** | `Cancel()`을 호출한 스레드 |
| `new Thread(...).Start()` | `Start()` 호출 시 | 새 스레드 |

캡처되는 시점은 **콜백을 등록할 때**지 실행될 때가 아니다. 그래서 다음 코드는 직관과 다르게 동작한다.

```csharp
static readonly AsyncLocal<string> _tag = new AsyncLocal<string>();

_tag.Value = "A";
Action cb = () => Console.WriteLine(_tag.Value);

ThreadPool.QueueUserWorkItem(_ => cb());   // 여기서 "A" 가 캡처된다
_tag.Value = "B";                          // 이 변경은 이미 큐잉된 항목에 반영되지 않는다

// 출력: A
```

### 자식이 바꾼 값은 부모로 돌아오지 않는다

`AsyncLocal<T>`의 흐름에는 방향이 있다. **부모 → 자식은 흐르지만, 자식 → 부모는 흐르지 않는다.** 새 스레드나 새 태스크는 값의 **복사본**을 받기 때문이다.

```csharp
static readonly AsyncLocal<string> _test = new AsyncLocal<string>();

void Main()
{
    _test.Value = "test";
    var t = new Thread(AnotherMethod);
    t.Start();
    t.Join();
    Console.WriteLine(_test.Value);     // test   (ha-ha! 가 아니다)
}

void AnotherMethod() => _test.Value = "ha-ha!";
```

새 스레드는 시작 시점에 `"test"`를 **상속**하지만, 그 스레드가 값을 바꿔도 원래 흐름에는 아무 영향이 없다. `await` 경계에서도 같다 — `async` 메서드 안에서 `AsyncLocal<T>.Value`에 대입하면 그 값은 **그 메서드 아래로만** 흐르고 호출자에게는 보이지 않는다.

> **⚠️ 새 스레드가 받는 것은 얕은 복사다**
>
> 상속되는 것은 **값 자체의 복사본**이지 값이 가리키는 객체의 복사본이 아니다. `AsyncLocal<StringBuilder>`나 `AsyncLocal<List<string>>`을 쓰면, 자식 흐름이 그 `StringBuilder`를 지우거나 리스트에 항목을 추가하는 순간 **원래 흐름도 그 변화를 본다.**
>
> 그래서 `AsyncLocal<T>`에는 문자열이나 불변 타입 같은 **불변 값**만 담는 것이 안전하다. 가변 객체를 담아야 한다면, 값을 바꾸는 대신 새 객체를 만들어 `Value`에 다시 대입하는 방식(교체 전용)으로 써라.
### 캡처와 복원의 비용

컨텍스트를 흘리는 것은 공짜가 아니다. 원천 자료의 표현은 이렇다. **실행 컨텍스트에는 정보가 많고, 그 정보를 전부 모아 도우미 스레드용으로 복사하는 데 상당한 시간이 든다.** 도우미 스레드가 또 다른 도우미를 쓰면 그만큼 더 만들어진다. .NET Framework 시절에는 논리적 호출 컨텍스트(`CallContext.LogicalSetData`)의 항목들을 캡처할 때마다 **직렬화·역직렬화했기 때문에** 성능이 극적으로 나빠질 수 있었다. 현대 .NET의 `ExecutionContext`는 훨씬 얇은 불변(immutable) 객체라, `AsyncLocal<T>`를 하나도 쓰지 않았다면 캡처는 참조 하나를 복사하는 정도로 끝난다.
### 흐름을 억제하기 — `SuppressFlow`

`System.Threading` 네임스페이스의 `ExecutionContext` 클래스가 흐름 제어 수단을 제공한다.

```csharp
public sealed class ExecutionContext : IDisposable, ISerializable
{
    public static AsyncFlowControl SuppressFlow();
    public static void RestoreFlow();
    public static bool IsFlowSuppressed();
    // 덜 쓰이는 멤버는 생략
}
```

동작을 보여 주는 원천 자료의 예제는 .NET Framework의 논리적 호출 컨텍스트를 쓰지만, `AsyncLocal<T>`로 옮겨도 결과는 같다.

```csharp
static readonly AsyncLocal<string> _name = new AsyncLocal<string>();

public static void Main()
{
    // 주 스레드의 흐름에 데이터를 넣는다
    _name.Value = "Jeffrey";

    // 풀 스레드가 할 일을 시작한다 — 이 스레드는 데이터를 볼 수 있다
    ThreadPool.QueueUserWorkItem(state => Console.WriteLine($"Name={_name.Value}"));

    // 이제 주 스레드의 실행 컨텍스트 흐름을 억제한다
    ExecutionContext.SuppressFlow();

    // 풀 스레드가 할 일을 시작한다 — 이 스레드는 데이터를 볼 수 **없다**
    ThreadPool.QueueUserWorkItem(state => Console.WriteLine($"Name={_name.Value}"));

    // 앞으로 또 풀 스레드를 쓸 것에 대비해 흐름을 복원한다
    ExecutionContext.RestoreFlow();

    Console.ReadLine();
}

// 출력:
// Name=Jeffrey
// Name=
```

`SuppressFlow`가 돌려주는 `AsyncFlowControl`은 `IDisposable`이므로 `using (ExecutionContext.SuppressFlow()) { ... }`로 범위를 한정하는 편이 안전하다 — `Dispose`가 `RestoreFlow`를 호출한다.

> **⚠️ `SuppressFlow`는 성능 최적화지 보안 장치가 아니다**
>
> 흐름을 억제하면 도우미 스레드는 **자기가 마지막으로 갖고 있던 실행 컨텍스트를 그대로 쓴다.** 원천 자료의 경고 그대로다. 즉 앞선 작업이 남긴 컨텍스트가 그 스레드에 붙어 있을 수 있다. 따라서 흐름을 억제한 도우미 스레드는 **실행 컨텍스트 상태(사용자의 윈도우 ID 같은 것)에 의존하는 코드를 실행하면 안 된다.** "컨텍스트를 깨끗이 지운다"가 아니라 "가져가지 않는다"임을 정확히 이해해야 한다.
>
> 억제로 얻는 성능 이득은 서버 애플리케이션에서는 꽤 클 수 있지만 클라이언트 애플리케이션에서는 크지 않다.

`ThreadPool.UnsafeQueueUserWorkItem`은 같은 일을 호출 단위로 한다.

```csharp
public static bool QueueUserWorkItem(WaitCallback callBack, object state);
public static bool UnsafeQueueUserWorkItem(WaitCallback callBack, object state);
public static void UnsafeQueueUserWorkItem(IThreadPoolWorkItem callBack, bool preferLocal);  // ※.NET Core 3.0
```

`Unsafe` 접두사가 붙은 쪽은 실행 컨텍스트를 캡처하지 않는다. "Unsafe"라는 이름은 메모리 안전성이 아니라 **보안 컨텍스트가 따라가지 않는다는 뜻**이다. 취소 콜백의 `CancellationToken.UnsafeRegister`도 정확히 같은 관계다.
### `ExecutionContext` vs `SynchronizationContext`

이 둘은 이름이 비슷해 늘 혼동된다. 하는 일이 완전히 다르다.

| 항목 | `ExecutionContext` | `SynchronizationContext` |
|---|---|---|
| 답하는 질문 | 연속이 **무엇을 보며** 실행되는가 | 연속이 **어느 스레드에서** 실행되는가 |
| 담는 것 | `AsyncLocal<T>` 값, 보안·호스트 설정 | 델리게이트를 올바른 스레드에 올리는 방법 |
| 대표 구현 | 단일 클래스(밀봉) | WPF `Dispatcher`, WinForms, ASP.NET Core(=없음) |
| 핵심 멤버 | `Capture()`, `Run()`, `SuppressFlow()` | `Post()`(비동기), `Send()`(동기) |
| `await`에서 | 항상 흐른다 | 캡처된 것이 있으면 그리로 되돌린다 |
| 끄는 방법 | `ExecutionContext.SuppressFlow()` | `ConfigureAwait(false)` |
| 끄면 생기는 일 | 앰비언트 상태가 사라진다 | 연속이 풀 스레드에서 실행된다 |
| 콘솔 앱에서 | 존재하며 흐른다 | 기본적으로 `null`(캡처할 것이 없다) |

원천 자료가 요약한 대로다. **동기화 컨텍스트는 `ConfigureAwait`로 명시적으로 옵트아웃할 수 있다. 실행 컨텍스트는 그렇지 않다 — 비동기 메서드가 재개될 때는 스레드가 달라지더라도 거의 언제나 같은 실행 컨텍스트를 원하기 때문이다.** 그래서 `ConfigureAwait(false)`는 `AsyncLocal<T>` 값을 잃게 만들지 **않는다.** 이건 반드시 기억해야 한다.

> **📌 `AwaitOnCompleted`와 `AwaitUnsafeOnCompleted`가 둘인 이유**
>
> awaiter가 `INotifyCompletion`만 구현하는지 `ICriticalNotifyCompletion`까지 구현하는지에 따라, 컴파일러는 각 `await` 지점에서 빌더의 `AwaitOnCompleted` 또는 `AwaitUnsafeOnCompleted`를 호출하도록 코드를 만든다. `ICriticalNotifyCompletion.UnsafeOnCompleted`는 `[SecurityCritical]`이 붙어 있어 프레임워크의 `AsyncTaskMethodBuilder` 같은 신뢰된 코드만 호출할 수 있다.
>
> 직접 awaiter를 만들면서 부분 신뢰 환경까지 신경 쓴다면, `INotifyCompletion.OnCompleted` 구현이 `ExecutionContext.Capture`와 `ExecutionContext.Run`으로 실행 컨텍스트를 흘려야 한다. 반대로 `ICriticalNotifyCompletion`을 구현하는 경우에는 흘리지 않아도 된다 — 비동기 인프라가 이미 흘려 놨다고 믿는 것이다. 컨텍스트를 두 번 캡처·복원하지 않기 위한 최적화다. 상태 기계와 빌더의 전모는 47.7절과 47.8절에서 다룬다.

## 46.8 협력적 취소 — `CancellationToken` 프로토콜 구현

### 취소는 요청이지 명령이 아니다

.NET은 연산을 취소하는 표준 패턴을 제공한다. 이 패턴은 **협력적(cooperative)** 이다. 즉 취소하고 싶은 연산이 **취소당하는 것을 명시적으로 지원해야** 한다. 취소를 시도하는 코드와 취소당할 연산을 수행하는 코드가 **둘 다** 이 절의 타입들을 써야 한다.

이 문장이 이 절 전체의 요약이다. `CancellationToken`은 스레드를 강제로 멈추는 수단이 아니다. 실행 중인 코드를 임의 지점에서 끊으면 상태 일관성을 아무도 보장할 수 없기 때문이다. 협력적 취소는 "여기까지만 하고 나오라"는 **요청**이고, 언제 나올지는 요청받은 쪽이 정한다.

### `CancellationTokenSource`와 `CancellationToken`

취소를 요청하려면 먼저 `System.Threading.CancellationTokenSource` 객체를 만든다.

```csharp
public sealed class CancellationTokenSource : IDisposable   // 참조 타입
{
    public CancellationTokenSource();
    public CancellationTokenSource(TimeSpan delay);       // int, TimeProvider 오버로드도 있다
    public bool IsCancellationRequested { get; }
    public CancellationToken Token { get; }
    public void Cancel();                                 // 내부적으로 Cancel(false) 호출
    public void Cancel(bool throwOnFirstException);
    public Task CancelAsync();                            // ※.NET 8
    public void CancelAfter(TimeSpan delay);
    public bool TryReset();                               // ※.NET 6
    public void Dispose();
    public static CancellationTokenSource CreateLinkedTokenSource(
        params CancellationToken[] tokens);
}
```

이 객체가 취소 관리와 관련된 모든 상태를 갖는다. 소스(참조 타입)를 만든 뒤 `Token` 속성으로 `CancellationToken`(**값 타입**)을 하나 이상 얻어 취소를 허용할 연산들에 넘긴다.

```csharp
public struct CancellationToken            // 값 타입
{
    public static CancellationToken None { get; }
    public bool IsCancellationRequested { get; }   // 태스크가 아닌 연산이 폴링할 때
    public void ThrowIfCancellationRequested();    // 태스크로 시작된 연산이 호출할 때
    public WaitHandle WaitHandle { get; }          // 취소되면 신호를 받는 대기 핸들
    public bool CanBeCanceled { get; }             // 드물게 쓴다
    public CancellationTokenRegistration Register(Action callback);
    public CancellationTokenRegistration Register(Action<object> callback, object state,
                                                  bool useSynchronizationContext);
    public CancellationTokenRegistration UnsafeRegister(Action<object> callback, object state);
}
```

`CancellationToken`은 **가벼운 값 타입**이다. 필드가 하나뿐이다 — 자기 `CancellationTokenSource` 객체에 대한 참조. 그래서 매개변수로 마음껏 넘겨도 부담이 없다.

**소스와 토큰을 분리한 이유**는 권한 분리다. `CancellationToken`만 받은 메서드는 취소를 **검사할 수는 있지만 개시할 수는 없다.** 취소를 개시할 권한은 소스를 쥔 쪽에만 있다.

### 폴링 vs 던지기

컴퓨트 바운드 연산의 반복문은 두 가지 방식으로 취소를 확인한다.

```csharp
// 방식 1 — 폴링: 조용히 빠져나온다
private static void Count(CancellationToken token, int countTo)
{
    for (int count = 0; count < countTo; count++)
    {
        if (token.IsCancellationRequested)
        {
            Console.WriteLine("카운트가 취소되었다");
            break;                      // 반복을 빠져나가 연산을 끝낸다
        }
        Console.WriteLine(count);
        Thread.Sleep(200);
    }
    Console.WriteLine("카운트 완료");
}

// 방식 2 — 던지기: 예외로 알린다
private static int Sum(CancellationToken ct, int n)
{
    int sum = 0;
    for (; n > 0; n--)
    {
        // CancellationTokenSource 에 Cancel 이 호출되었다면
        // 다음 줄이 OperationCanceledException 을 던진다
        ct.ThrowIfCancellationRequested();
        checked { sum += n; }           // n 이 크면 OverflowException
    }
    return sum;
}
```

**왜 두 개인가.** `ThreadPool.QueueUserWorkItem`으로 시작한 작업 항목과 달리 **태스크는 "완료되었다"는 개념을 갖고 값까지 반환할 수 있다.** 그러므로 완료된 태스크와 취소된 태스크를 구별할 방법이 필요하고, 예외를 던지는 것이 그 방법이다.

선택 기준은 단순하다. `Task`/`Task<T>`로 감싼 연산은 태스크 상태를 Canceled로 만들어야 하므로 `ThrowIfCancellationRequested()`를 쓴다. `QueueUserWorkItem`으로 던진 작업은 결과를 보고할 상대가 없으므로 폴링한다. **부분 결과라도 돌려줘야 하는 연산도 폴링**이다 — 예외로 끝나면 결과를 돌려줄 길이 없다.

> **📌 `CancellationToken.None`과 `CanBeCanceled`**
>
> 연산을 실행하되 취소를 막고 싶다면, `CancellationToken`의 정적 `None` 속성이 돌려주는 토큰을 넘겨라. 이 특별한 토큰은 **어떤 `CancellationTokenSource`와도 연결되어 있지 않다**(내부 필드가 `null`이다). 소스가 없으니 아무도 `Cancel`을 부를 수 없고, `IsCancellationRequested`는 언제나 `false`를 돌려준다. 이 토큰의 `CanBeCanceled`는 `false`이며, 소스의 `Token` 속성에서 얻은 다른 모든 토큰은 `true`다.
>
> `CanBeCanceled`가 쓸모 있는 곳은 라이브러리 내부다. 토큰이 애초에 취소될 수 없다면, 등록·연결 같은 준비 작업 자체를 건너뛰는 최적화를 할 수 있다.
### `Cancel`, `CancelAsync`, `Register`

`Cancel()`을 호출하면 그 소스에서 나온 모든 토큰이 취소 상태가 되고 **등록된 콜백들이 실행된다.**

```csharp
var cts = new CancellationTokenSource();
cts.Token.Register(() => Console.WriteLine("Canceled 1"));
cts.Token.Register(() => Console.WriteLine("Canceled 2"));

cts.Cancel();

// 출력:
// Canceled 2
// Canceled 1
```

출력 순서를 보라. **등록의 역순으로 실행된다.**

> **⚠️ `Register` 콜백은 `Cancel`을 호출한 스레드에서 동기적으로 실행된다**
>
> 이것이 이 절에서 가장 자주 사고를 내는 사실이다. `useSynchronizationContext`에 `false`를 넘기면(기본값), **`Cancel`을 호출한 스레드가 등록된 메서드들을 순차적으로 호출한다.** `true`를 넘기면 캡처된 `SynchronizationContext`로 콜백이 **`Send`(동기 전송)** 되어, 그 컨텍스트가 정하는 스레드가 콜백을 실행한다.
>
> 결과는 46.5절의 `SetResult` 함정과 같은 모양이다.
>
> - 콜백이 오래 걸리면 **`Cancel()` 호출이 그만큼 오래 블로킹된다.** UI 스레드에서 `Cancel()`을 부르는 흔한 코드가 UI를 얼린다.
> - 콜백이 잠금을 잡는데 `Cancel()`이 그 잠금 안에서 호출되었다면 **데드락**이다.
> - 콜백이 예외를 던지면 그 예외가 `Cancel()` 호출부로 전파된다(아래 참조).
>
> 그래서 취소 콜백은 **짧고, 예외를 던지지 않고, 잠금을 잡지 않아야** 한다. 무거운 정리는 콜백에서 플래그를 세우거나 신호를 보내고, 실제 작업은 다른 곳에서 하라.
>
> ※.NET 8부터는 `CancelAsync()`가 있다. 이 메서드는 `Task`를 돌려주고, 콜백 실행이 호출자를 블로킹하지 않게 한다. UI 스레드나 요청 처리 경로에서 취소를 개시한다면 `CancelAsync()`를 쓰는 편이 낫다.

콜백이 예외를 던졌을 때의 규칙은 `Cancel`의 오버로드가 결정한다.

| 호출 | 콜백이 예외를 던지면 |
|---|---|
| `Cancel()` = `Cancel(false)` | 등록된 콜백을 **전부** 실행하고, 발생한 예외들을 모아 `AggregateException`으로 던진다. 예외가 없으면 그냥 반환한다 |
| `Cancel(true)` | **첫 번째** 미처리 예외에서 나머지 콜백 실행을 중단하고, 그 예외를 `Cancel`에서 그대로 던진다 |

여기에 원천 자료가 명시한 제약이 붙는다. **`AggregateException`의 내부 예외를 특정 연산과 대응시킬 방법은 없다.** `InnerExceptions`를 뒤져도 어떤 예외가 어느 등록에서 나왔는지 알려 주는 정보가 없으므로, 실패 지점을 찾으려면 `StackTrace`를 보고 소스 코드를 손으로 훑어야 한다. `AggregateException`의 `Flatten`·`Handle`은 32.13절에서 다룬다.

### 등록 해제 — `CancellationTokenRegistration`

`Register`가 돌려주는 값을 버리면 안 되는 경우가 있다.

```csharp
public struct CancellationTokenRegistration
    : IEquatable<CancellationTokenRegistration>, IDisposable, IAsyncDisposable
{
    public void Dispose();
    public ValueTask DisposeAsync();
}
```

`Dispose`를 호출하면 등록된 콜백이 소스에서 제거되어, 이후 `Cancel`이 호출되어도 실행되지 않는다.

> **⚠️ 등록을 해제하지 않으면 오래 사는 토큰이 짧게 사는 객체를 붙든다**
>
> 취소 관련 메모리 누수의 표준 형태다. 프로세스 수명 내내 사는 `appShutdownToken`에 `appShutdownToken.Register(() => Cleanup())`처럼 등록만 하고 반환값을 버리면, 그 소스의 콜백 목록에 `this`를 캡처한 람다가 들어가 **그 객체는 절대 수거되지 않는다.** 세션을 초당 수백 개 만드는 서버라면 몇 분 만에 힙이 부푼다. 고치려면 등록을 보관하고 정리 시점에 `Dispose`하라.
>
> ```csharp
> class Session : IDisposable
> {
>     private readonly CancellationTokenRegistration _reg;
>     public Session(CancellationToken appShutdownToken)
>         => _reg = appShutdownToken.Register(static s => ((Session)s).Cleanup(), this);
>     public void Dispose() => _reg.Dispose();
> }
> ```
>
> `static` 람다와 `state` 인자를 쓰면 클로저 할당도 없앨 수 있다(26.11절).

여기에 덧붙일 사실이 하나 더 있다. `CancellationTokenSource`가 **이미 취소된 뒤에** 콜백을 등록하면, `Register`를 호출한 스레드가 콜백을 즉시 호출한다. 즉 `Register`는 "나중에 부르겠다"가 아니라 "취소 시점에, 이미 지났으면 지금"이라는 계약이다. 생성자 안의 `Register` 호출이 아직 초기화되지 않은 필드를 건드리는 사고가 여기서 나온다.

### 연결된 토큰 소스

여러 취소 소스 중 **아무거나 하나**가 취소되면 함께 취소되는 소스를 만들 수 있다.

```csharp
var cts1 = new CancellationTokenSource();
cts1.Token.Register(() => Console.WriteLine("cts1 canceled"));
var cts2 = new CancellationTokenSource();
cts2.Token.Register(() => Console.WriteLine("cts2 canceled"));

// cts1 이나 cts2 가 취소되면 함께 취소되는 새 소스를 만든다
var linkedCts = CancellationTokenSource.CreateLinkedTokenSource(cts1.Token, cts2.Token);
linkedCts.Token.Register(() => Console.WriteLine("linkedCts canceled"));

cts2.Cancel();      // 둘 중 하나만 취소한다

Console.WriteLine("cts1={0}, cts2={1}, linked={2}", cts1.IsCancellationRequested,
    cts2.IsCancellationRequested, linkedCts.IsCancellationRequested);

// 출력:
// linkedCts canceled
// cts2 canceled
// cts1=False, cts2=True, linked=True
```

연결은 한 방향이다 — `linkedCts`가 취소되어도 `cts1`·`cts2`는 취소되지 않는다.

> **⚠️ 연결된 소스는 반드시 `Dispose`해야 한다**
>
> `CreateLinkedTokenSource`는 내부적으로 **원본 토큰들에 콜백을 등록한다.** 원본 토큰의 수명이 길고 연결된 소스를 버리기만 하면, 바로 위에서 본 것과 같은 누수가 생긴다 — 원본 소스의 콜백 목록에 죽은 연결 소스가 계속 쌓인다.
>
> 요청마다 연결 소스를 만드는 서버 코드가 특히 위험하다. **`using`으로 감싸는 것이 사실상 필수다.**
>
> ```csharp
> public async Task<Result> HandleAsync(CancellationToken requestAborted)
> {
>     using var timeoutCts = new CancellationTokenSource(TimeSpan.FromSeconds(10));
>     using var linked = CancellationTokenSource.CreateLinkedTokenSource(
>         requestAborted, timeoutCts.Token);
>
>     return await _client.QueryAsync(linked.Token);
> }
> ```
>
> 이 두 줄이 "요청이 중단되거나 10초가 지나면 취소"를 표현하는 표준 관용구다.

### 타임아웃 토큰

시간이 지나면 스스로 취소되게 하는 방법이 둘 있다. `new CancellationTokenSource(TimeSpan.FromSeconds(5))`처럼 생성자에 지연을 주거나, 만들어 둔 소스에 `cts.CancelAfter(5000)`을 호출하는 것이다.

원천 자료가 든 사례가 이 기능의 존재 이유를 설명한다. 클라이언트 요청을 받아 계산을 시작한 서버가 **무슨 일이 있어도 2초 안에는 응답해야 한다면**, 완전한 결과를 오래 기다리기보다 짧은 시간 안에 오류나 부분 결과를 돌려주는 편이 낫다.

> **⚠️ `CancellationTokenSource`는 `IDisposable`이며 타이머 자원을 쓴다**
>
> `CancelAfter`나 지연 생성자를 쓰면 소스는 내부에 **타이머를 하나 갖는다.** 이 타이머는 소스를 `Dispose`할 때 해제된다. `Dispose`하지 않은 소스를 대량으로 만들면 타이머 큐에 항목이 쌓이고, 소스가 GC되기 전까지 그 항목이 남는다.
>
> `Dispose`는 또한 `WaitHandle` 속성이 지연 생성한 커널 객체를 닫는다. `CancellationToken.WaitHandle`을 한 번이라도 읽었다면 이건 진짜 커널 핸들이다.
>
> **규칙: 여러분이 `new CancellationTokenSource(...)`로 만든 소스는 여러분이 `Dispose`한다.** 남에게서 받은 `CancellationToken`은 `Dispose`할 수 없고(값 타입이며 `IDisposable`이 아니다) 해서도 안 된다.
### 태스크가 Canceled가 되는 조건

이 부분이 가장 미묘하다. **`OperationCanceledException`이 던져졌다고 해서 태스크가 자동으로 Canceled가 되는 것은 아니다.**

```csharp
var cts = new CancellationTokenSource();

Task<int> t = Task.Run(() => Sum(cts.Token, 1_000_000_000), cts.Token);
//                                 ↑ 본문이 쓰는 토큰      ↑ 태스크에 연결된 토큰
//                                    이 둘이 같아야 한다

cts.Cancel();   // 비동기 요청이다. 태스크는 이미 끝났을 수도 있다

try
{
    Console.WriteLine("합계: " + t.Result);
}
catch (AggregateException x)
{
    // OperationCanceledException 은 처리된 것으로 간주한다.
    // 다른 예외가 있으면 그것들만 담은 새 AggregateException 이 던져진다
    x.Handle(e => e is OperationCanceledException);
    Console.WriteLine("합계 계산이 취소되었다");
}
```

규칙은 이렇다.

| 태스크의 출처 | Canceled가 되는 조건 |
|---|---|
| `Task.Run(action, token)` | 본문이 던진 `OperationCanceledException`의 `CancellationToken`이 `token`과 **같고**, 그 토큰이 취소된 상태일 때 |
| `Task.Run(action)` (토큰 없음) | 어떤 `OperationCanceledException`이든 **Faulted**가 된다 |
| `async` 메서드가 반환한 태스크 | 미처리 `OperationCanceledException`이면 **언제나 Canceled** (`IsCanceled`=true, `IsFaulted`=false) |
| `TaskCompletionSource` | `SetCanceled()`/`TrySetCanceled()`를 호출했을 때 |
| 스케줄 전에 토큰이 취소됨 | 태스크는 아예 실행되지 않고 Canceled |

**즉 `Task.Run`에서 토큰을 두 군데 다 넘겨야 하는 이유가 여기 있다.** 람다 안에서만 쓰고 두 번째 인자로 넘기지 않으면 취소가 Faulted로 기록된다. `await`하는 쪽은 어차피 `OperationCanceledException`을 받으므로 차이가 없어 보이지만, 조건부 연속(`TaskContinuationOptions.OnlyOnCanceled`, 46.4절)을 쓰면 동작이 완전히 달라진다.

> **📌 `Task` 객체에 연결된 토큰은 다시 꺼낼 수 없다**
>
> `Task`가 `CancellationToken`을 갖고 있어도 그것을 읽는 공개 API는 없다. 그래서 태스크 본문이 같은 토큰을 보게 만들려면 **직접 전달해야** 한다. 가장 쉬운 방법이 람다 식으로 감싸 클로저 변수로 "전달"하는 것이다. 위 예제의 `() => Sum(cts.Token, ...)`이 정확히 그 패턴이다.
### 취소를 지원하는 API를 설계하는 지침

여러분이 취소 가능한 비동기 API를 새로 쓴다면 다음을 지켜라.

1. **취소를 지원할 수 있을 때만 토큰 매개변수를 노출하라.** 근본 메커니즘이 취소를 지원하지 않는데 오버로드만 두면, 호출자가 효과도 없는 프로토콜을 구현하느라 헛수고한다.
2. **매개변수 이름은 `cancellationToken`, 위치는 마지막, 기본값은 `= default`.** TAP 규약이다(47.15절).
3. **취소 확인 지점을 문서화하라.** 호출자는 요청 후 얼마나 기다려야 하는지 알아야 한다.
4. **아래로 계속 전달하라.** 토큰은 호출 스택을 따라 아래로 흐르고, 취소 요청은 예외의 형태로 위로 올라간다.
5. **취소 후의 상태 일관성은 여러분 책임이다.** 이게 가장 중요하다.

> **⚠️ 취소된 연산이 남긴 상태를 아무도 대신 치워 주지 않는다**
>
> 취소는 중간에 던져진 예외다. 파일을 절반 쓴 상태, 트랜잭션이 열린 상태, 캐시에 미완성 항목을 넣은 상태에서 취소되면 그 상태는 그대로 남는다. 취소를 지원한다는 것은 **모든 취소 확인 지점에서 그 시점의 상태가 관측 가능하게 일관적임을 보장한다**는 뜻이다.
>
> 실무 규칙 셋.
>
> - 취소 확인은 **부수 효과 사이**에 두고 부수 효과 중간에 두지 마라.
> - 되돌릴 수 없는 지점(결제 승인, 메일 발송)을 지난 뒤에는 취소를 확인하지 마라. 원천 자료의 급여 처리 예제가 그렇다 — 급여 이체가 시작된 후에는 그 연산이 더 이상 취소 가능하지 않다.
> - 정리가 필요하다면 `try`/`finally`나 `using`으로 묶어라. 취소는 예외이므로 33.10절의 정리 관용구가 그대로 적용된다.

> **💡 `async void`에는 취소를 붙이지 마라**
>
> 취소된 태스크는 예외로 끝나는데, `async void` 메서드는 예외를 돌려줄 태스크가 없으므로 취소 예외가 **미처리 예외 핸들러로 직행해 프로세스를 죽인다.** 취소를 지원하려면 반환 타입이 `Task`여야 한다. `async void`가 왜 그 자체로 금지 대상인지는 47.14절에서 다룬다.

## 46.9 태스크 합성기 — `WhenAll`, `WhenAny`, `WhenEach` ※.NET 9

비동기 함수들이 일관되게 태스크를 반환한다는 규약 덕분에, **태스크를 유용하게 조합하는 함수** 를 쓰고 만들 수 있다. 그 태스크들이 구체적으로 무슨 일을 하는지는 몰라도 된다. 이런 함수를 **합성기(combinator)** 라고 한다.

### `Task.WhenAll` — 전부 끝날 때까지

```csharp
public static Task WhenAll(params Task[] tasks);                 // IEnumerable 오버로드도 있다
public static Task<TResult[]> WhenAll<TResult>(IEnumerable<Task<TResult>> tasks);
```

`WhenAll`은 넘긴 태스크가 **전부** 완료될 때 완료되는 태스크를 돌려준다. 아래는 3초 뒤에 완료된다(fork/join 패턴).

```csharp
async Task<int> Delay1() { await Task.Delay(1000); return 1; }
async Task<int> Delay2() { await Task.Delay(2000); return 2; }
async Task<int> Delay3() { await Task.Delay(3000); return 3; }

await Task.WhenAll(Delay1(), Delay2(), Delay3());

// 아래처럼 세 번 await 하는 것과 비슷해 보인다
Task task1 = Delay1(), task2 = Delay2(), task3 = Delay3();
await task1; await task2; await task3;
```

**결정적인 차이가 있다.** `task1`이 실패하면 `task2`·`task3`에는 영영 도달하지 못하고, 그 둘의 예외는 **미관측(unobserved)** 으로 남는다(46.11절). 반면 `WhenAll`은 **실패가 있어도 전부 완료될 때까지 기다린다.**

`Task<TResult>`를 넘기면 `Task<TResult[]>`가 나오고, `await`하면 배열이 된다.

```csharp
Task<int> task1 = Task.Run(() => 1);
Task<int> task2 = Task.Run(() => 2);
int[] results = await Task.WhenAll(task1, task2);      // { 1, 2 }
```

결과 배열의 순서는 **완료 순서가 아니라 입력 순서**다. 이건 중요한 보장이다.

> **⚠️ `await Task.WhenAll(...)`은 첫 예외만 던진다**
>
> 여러 태스크가 실패하면 그 예외들은 합쳐진 태스크의 `AggregateException`에 전부 모인다. 그런데 **`await`는 그중 첫 번째만 벗겨서 던진다.** 전부 보려면 반환된 태스크의 `Exception` 속성을 봐야 한다.
>
> ```csharp
> Task task1 = Task.Run(() => { throw null; });
> Task task2 = Task.Run(() => { throw null; });
> Task all = Task.WhenAll(task1, task2);
>
> try { await all; }
> catch
> {
>     Console.WriteLine(all.Exception.InnerExceptions.Count);   // 2
> }
> ```
>
> `catch (Exception ex)`로 받은 `ex`에는 **하나**만 들어 있다. 나머지 하나를 로그에 남기지 않으면 사고 원인의 절반이 사라진다. 다중 실패를 전부 기록해야 하는 코드라면 `all` 변수를 반드시 따로 붙들어라. `AggregateException`이 실제로 유용해지는 몇 안 되는 자리다.

취소가 섞이면 규칙이 하나 더 붙는다. 넘긴 태스크가 전부 RanToCompletion이면 합쳐진 태스크도 RanToCompletion이고, 하나라도 Faulted면 Faulted(모든 실패가 `Exception`에 모인다), Faulted 없이 Canceled만 있으면 Canceled, 빈 시퀀스면 즉시 RanToCompletion이다. 즉 **실패가 취소보다 우선한다.** `await`가 던지는 예외도 그에 따라 갈린다 — Faulted면 첫 실패 예외, Canceled면 `OperationCanceledException`이다.

> **💡 `WhenAll`에 넘길 태스크는 미리 만들어라**
>
> ```csharp
> // 나쁨: 각 항목마다 순차적으로 await 된다 — 병렬성이 없다
> foreach (var uri in uris) results.Add(await DownloadAsync(uri));
>
> // 좋음: 전부 시작해 놓고 한꺼번에 기다린다
> var tasks = uris.Select(uri => DownloadAsync(uri)).ToList();   // ToList 가 핵심
> var results = await Task.WhenAll(tasks);
> ```
>
> `ToList()`(또는 `ToArray()`)를 빼면 안 된다. `Select`는 지연 평가되므로 시퀀스를 두 번 열거하는 코드에서는 태스크가 두 벌 만들어져 요청이 두 배로 나간다. 비동기 람다(`uris.Select(async uri => (await DownloadDataAsync(uri)).Length)`)를 쓰면 중간 결과를 붙들지 않고 바로 줄일 수도 있다.

> **⚠️ `WhenAll`은 동시성 제한 장치가 아니다**
>
> URI 10,000개로 `WhenAll`을 부르면 요청 10,000개가 동시에 나간다. 소켓이 고갈되거나 상대 서버가 거부하거나 스레드 풀이 무너진다. 동시 실행 개수를 제한하려면 `SemaphoreSlim`(48.11절)이나 `Parallel.ForEachAsync`(50.7절)를 써라. `WhenAll`이 하는 일은 "기다리기"뿐이지 "조절하기"가 아니다.

### `Task.WhenAny` — 하나라도 끝나면

```csharp
public static Task<Task> WhenAny(params Task[] tasks);
public static Task<Task<TResult>> WhenAny<TResult>(params Task<TResult>[] tasks);
```

`WhenAny`는 여러 태스크 중 **아무거나 하나**가 완료되면 완료되는 태스크를 돌려준다. 반환 타입이 `Task<Task>`라는 점에 주목하라 — 결과가 "먼저 끝난 태스크"다.

```csharp
Task<int> winningTask = await Task.WhenAny(Delay1(), Delay2(), Delay3());
Console.WriteLine("Done");
Console.WriteLine(winningTask.Result);      // 1
```

1초 만에 완료된다. `winningTask`는 이미 끝났으므로 `Result`를 읽어도 블로킹되지 않지만, **`await`하는 편이 낫다** — 예외가 `AggregateException`으로 감싸이지 않고 원래 타입 그대로 다시 던져지기 때문이다. 두 `await`를 한 줄로 합칠 수도 있다: `int answer = await await Task.WhenAny(...)`.

> **⚠️ 진 태스크의 예외는 미관측으로 남는다**
>
> 원천 자료의 문장 그대로다. **이기지 못한 태스크가 나중에 실패하면, 그 태스크를 별도로 `await`하거나 `Exception` 속성을 조회하지 않는 한 예외는 미관측으로 남는다.**
>
> `WhenAny`는 완료되는 순간 나머지 태스크에 손을 대지 않는다. 취소하지도, 관찰하지도 않는다. 그 태스크들은 계속 실행되다가 실패하고, 아무도 그 예외를 보지 않으면 46.11절의 미관측 예외가 된다.
>
> **대책은 셋 중 하나다.** 진 태스크에 예외를 삼키는 연속을 붙여 관측하거나(`loser.ContinueWith(t => _ = t.Exception, TaskContinuationOptions.OnlyOnFaulted)`), `TaskScheduler.UnobservedTaskException`을 로깅에 연결하거나(46.11절), 애초에 취소 토큰을 넘겨 진 태스크를 실제로 중단시킨다.

### 타임아웃 관용구와 그 함정

`WhenAny`의 대표적 용도가 **취소를 지원하지 않는 연산에 타임아웃을 씌우는 것**이다. 타입이 다른 태스크를 섞게 되므로 `winner`는 `Task<string>`이 아니라 그냥 `Task`로 보고된다. 라이브러리 메서드로 만들면 이렇다.

```csharp
async static Task<TResult> WithTimeout<TResult>(this Task<TResult> task, TimeSpan timeout)
{
    var cancelSource = new CancellationTokenSource();
    var delay = Task.Delay(timeout, cancelSource.Token);

    Task winner = await Task.WhenAny(task, delay).ConfigureAwait(false);

    if (winner == task)
        cancelSource.Cancel();          // 제때 끝났으니 타이머를 치운다
    else
        throw new TimeoutException();

    return await task.ConfigureAwait(false);   // 결과를 벗기거나 예외를 다시 던진다
}
```

`ConfigureAwait(false)`를 붙인 이유는 이것이 외부 공유 상태를 건드리지 않는 전형적인 "라이브러리 메서드"라서 UI 동기화 컨텍스트로 튀는 것을 피해야 하기 때문이다(47.12절). `cancelSource.Cancel()`은 제때 끝났을 때 타이머 항목이 5초간 남아 있는 작은 오버헤드를 없앤다.

> **⚠️ 타임아웃은 태스크를 멈추지 않는다 — 기다리기를 멈출 뿐이다**
>
> 이 관용구의 가장 큰 오해다. `WithTimeout`이 `TimeoutException`을 던진 뒤에도 **원래 태스크는 계속 돌고 있다.** 데이터베이스 쿼리는 계속 실행되고, HTTP 요청은 계속 살아 있고, 파일 쓰기는 계속 진행된다. 커넥션도, 스레드도, 버퍼도 그대로 잡혀 있다.
>
> 결과는 조용한 자원 고갈이다. 타임아웃 5초에 실제 응답이 60초 걸리는 백엔드를 초당 100번 호출하면, 아무도 기다리지 않는 요청 6,000개가 항상 떠 있게 된다. 게다가 그 태스크가 나중에 실패하면 그것이 바로 위에서 본 **미관측 예외**다.
>
> **진짜 해법은 타임아웃 토큰을 대상 연산에 넘기는 것이다.**
>
> ```csharp
> using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(5));
> var result = await _client.QueryAsync(cts.Token);   // 연산 자체가 5초 뒤 중단된다
> ```
>
> `WhenAny` 타임아웃은 **대상이 취소를 아예 지원하지 않을 때의 차선책**일 뿐이다. 그 경우에도 진 태스크를 관측하는 코드를 반드시 붙여라.

### `WaitAsync` — 타임아웃 관용구의 표준화 ※.NET 6

.NET 6부터는 위 패턴을 직접 쓸 필요가 거의 없다.

```csharp
public Task WaitAsync(TimeSpan timeout);
public Task WaitAsync(CancellationToken cancellationToken);
public Task WaitAsync(TimeSpan timeout, CancellationToken cancellationToken);
public Task WaitAsync(TimeSpan timeout, TimeProvider timeProvider);   // ※.NET 8
```

```csharp
try
{
    string result = await SomeAsyncFunc().WaitAsync(TimeSpan.FromSeconds(5));
}
catch (TimeoutException)
{
    // 5초 안에 끝나지 않았다
}
```

`WaitAsync`는 타임아웃 시 `TimeoutException`, 토큰 취소 시 `OperationCanceledException`을 던진다. 이름이 `Wait`로 시작하지만 **블로킹 메서드가 아니다.**

> **⚠️ `WaitAsync`도 원래 태스크를 취소하지 않는다**
>
> 구현이 표준화되었을 뿐 의미론은 `WhenAny` 관용구와 같다. 여전히 원래 태스크는 계속 돈다. `WaitAsync(ct)`의 토큰은 **기다리기를 중단**시키는 토큰이지 대상 연산을 중단시키는 토큰이 아니다. 대상을 진짜로 멈추고 싶으면 대상이 받는 토큰에 넘겨야 한다.

### 블로킹 버전 — `Task.WaitAll`과 `Task.WaitAny`

`Task` 클래스에는 스레드를 블로킹하는 정적 메서드도 있다.

```csharp
public static bool Task.WaitAll(Task[] tasks, int millisecondsTimeout);   // 타임아웃 없는 void 버전도 있다
public static int  Task.WaitAny(Task[] tasks, int millisecondsTimeout);   // 타임아웃 없는 버전도 있다
```

`WaitAny`는 배열 안의 태스크 중 **아무거나 하나**가 완료될 때까지 호출 스레드를 블로킹하고 완료된 태스크의 인덱스를 돌려준다. 타임아웃이면 `-1`이고, `CancellationToken`을 통해 `WaitAny` 자체가 취소되면 `OperationCanceledException`을 던진다. `WaitAll`은 모든 태스크가 완료될 때까지 블로킹하며 전부 완료되면 `true`, 타임아웃이면 `false`를 돌려준다.

| 항목 | `Task.WhenAll` / `WhenAny` | `Task.WaitAll` / `WaitAny` |
|---|---|---|
| 반환 | `Task` / `Task<Task>` | `void`·`bool` / `int` 인덱스 |
| 호출 스레드 | 블로킹하지 않는다 | **블로킹한다** |
| 예외 전달 | `await`가 첫 예외를 던진다 | `AggregateException`을 던진다 |
| 취소 표현 | 태스크가 Canceled | `OperationCanceledException` |
| 타임아웃 표현 | 없음(`WaitAsync` 사용) | `false` / `-1` |
| UI 스레드에서 | 안전 | UI를 얼리고 데드락 위험 |
| 풀 스레드에서 | 안전 | 풀 스레드 소모, 기아 유발 |

> **⚠️ `WaitAll`/`WaitAny`는 사실상 레거시다**
>
> 이 둘을 써야 하는 정당한 자리는 극히 좁다 — 동기 API만 노출해야 하는 경계, 콘솔 앱의 최상단 정도다. 그 외의 모든 곳에서는 `WhenAll`/`WhenAny`를 `await`하라. 블로킹 버전은 46.2절에서 본 스레드 풀 기아의 주된 원인이며, 동기화 컨텍스트가 있는 환경에서는 47.14절의 데드락을 만든다.
>
> 하나 더. `Task.Wait`나 `Result`처럼 이들도 예외를 **`AggregateException`으로 감싸서** 던진다. `catch (HttpRequestException)`이 잡히지 않아 당황하게 되는 지점이다.

### `Task.WhenEach` — 완료되는 순서대로 ※.NET 9

46.5절 끝에서 `TaskCompletionSource`로 직접 구현했던 "완료 순서대로 재배열하기"를 .NET 9가 표준 API로 대체한다.

```csharp
public static IAsyncEnumerable<Task> WhenEach(params Task[] tasks);   // IEnumerable 오버로드도 있다
public static IAsyncEnumerable<Task<TResult>> WhenEach<TResult>(IEnumerable<Task<TResult>> tasks);
```

`IAsyncEnumerable<T>`를 돌려주므로 `await foreach`로 소비한다.

```csharp
var tasks = symbols.Select(s => ReadSymbolAsync(s)).ToList();

await foreach (Task<StockResult> completed in Task.WhenEach(tasks))
{
    try
    {
        StockResult r = await completed;      // 이미 완료된 태스크 — 결과를 벗긴다
        Render(r);                            // 도착하는 대로 화면에 그린다
    }
    catch (Exception ex)
    {
        _logger.LogWarning(ex, "심볼 조회 실패");
    }
}
```

이전에는 이 동작을 셋 중 하나로 흉내 냈고 셋 다 문제가 있었다. 시작 순서대로 `await`하면 늦게 끝나는 태스크 뒤에 이미 끝난 것들이 줄줄이 밀린다. `WhenAny`를 반복 호출하며 리스트에서 제거하면 호출마다 새 태스크를 할당해 비용이 가파르게 는다. 46.5절의 `TaskCompletionSource` 재배열은 할당은 한 번이지만 코드가 길고 실패 처리를 직접 써야 한다.

`WhenEach`는 할당이 적고, 순서 보장이 명확하며, 각 태스크의 예외를 **그 태스크를 `await`할 때** 자연스럽게 관측하게 만든다 — 미관측 예외가 생길 여지가 구조적으로 줄어든다.

> **📌 `WhenEach`가 넘겨주는 것은 결과가 아니라 태스크다**
>
> `await foreach`가 돌려주는 항목은 `TResult`가 아니라 **완료된 `Task<TResult>`** 다. 그래서 안쪽에서 한 번 더 `await`(또는 `.Result`)해야 값이 나온다. 번거로워 보이지만 의도된 설계다. 실패한 태스크와 취소된 태스크를 **개별적으로** 처리할 수 있어야 하기 때문이다. 항목이 결과값이었다면 첫 실패에서 열거 전체가 끝나 버렸을 것이다.

> **💡 합성기 선택 요약**
>
> | 하고 싶은 일 | 쓸 것 |
> |---|---|
> | 전부 끝날 때까지 기다린다 | `Task.WhenAll` |
> | 가장 빠른 하나만 쓴다 | `Task.WhenAny` + 진 태스크 관측/취소 |
> | 끝나는 대로 처리한다 | `Task.WhenEach` ※.NET 9 |
> | 타임아웃을 건다 | `WaitAsync` ※.NET 6, 가능하면 취소 토큰 |
> | 하나라도 실패하면 즉시 중단 | 연결 토큰 + `WhenAll`, 또는 직접 만든 합성기 |
> | 동시 실행 개수를 제한한다 | `SemaphoreSlim`(48.11절) / `Parallel.ForEachAsync`(50.7절) |
> | 블로킹으로 기다린다 | 원칙적으로 하지 마라 |

합성기를 직접 만드는 일은 복잡할 수 있고 때로는 49장의 신호 구조가 필요하다. 원천 자료의 지적대로 **이건 오히려 좋은 일이다.** 동시성의 복잡함이 비즈니스 로직 밖으로 밀려나 따로 테스트할 수 있는 재사용 가능한 메서드 안에 갇히기 때문이다.

## 46.10 `TaskScheduler`, `TaskFactory`, `TaskCreationOptions`

### 스케줄러가 하는 일

태스크 인프라가 유연한 이유의 상당 부분이 `TaskScheduler`에 있다. `TaskScheduler` 객체는 **예약된 태스크를 실제로 실행하는 책임**을 지고, 디버거에 태스크 정보를 노출하는 역할도 한다.

프레임워크는 두 종류의 파생 타입을 기본 제공한다. **스레드 풀 태스크 스케줄러**가 기본값으로, 46.1절에서 본 워커 스레드들에게 태스크를 예약한다. **동기화 컨텍스트 태스크 스케줄러**는 GUI 애플리케이션용으로, 모든 태스크를 애플리케이션의 GUI 스레드에 예약하므로 태스크 코드가 UI 요소를 안전하게 갱신할 수 있다 — **스레드 풀을 전혀 쓰지 않는다.**

정적 멤버는 넷이다. `TaskScheduler.Default`(스레드 풀 스케줄러, 기본값), `TaskScheduler.Current`(현재 실행 중인 태스크의 스케줄러 — 태스크 밖이면 `Default`), `TaskScheduler.FromCurrentSynchronizationContext()`(현재 `SynchronizationContext`에 태스크를 올리는 스케줄러), 그리고 `TaskScheduler.UnobservedTaskException`(미관측 예외 이벤트, 46.11절)이다.

### UI 스레드로 연속을 되돌리기

원천 자료의 WinForms 예제가 이 스케줄러의 용도를 정확히 보여 준다.

```csharp
internal sealed class MyForm : Form
{
    private readonly TaskScheduler m_syncContextTaskScheduler;
    private CancellationTokenSource m_cts;

    public MyForm()
        // 동기화 컨텍스트 태스크 스케줄러 참조를 얻는다 (GUI 스레드에서 생성해야 한다)
        => m_syncContextTaskScheduler = TaskScheduler.FromCurrentSynchronizationContext();

    protected override void OnMouseClick(MouseEventArgs e)
    {
        if (m_cts != null) { m_cts.Cancel(); m_cts = null; base.OnMouseClick(e); return; }

        Text = "연산 실행 중";
        m_cts = new CancellationTokenSource();

        // 이 태스크는 기본 스케줄러를 쓰므로 풀 스레드에서 실행된다
        Task<int> t = Task.Run(() => Sum(m_cts.Token, 20000), m_cts.Token);

        // 이 연속들은 동기화 컨텍스트 스케줄러를 쓰므로 GUI 스레드에서 실행된다
        t.ContinueWith(task => Text = "결과: " + task.Result,
            CancellationToken.None, TaskContinuationOptions.OnlyOnRanToCompletion,
            m_syncContextTaskScheduler);
        t.ContinueWith(task => Text = "연산이 취소되었다",
            CancellationToken.None, TaskContinuationOptions.OnlyOnCanceled,
            m_syncContextTaskScheduler);
        t.ContinueWith(task => Text = "연산이 실패했다",
            CancellationToken.None, TaskContinuationOptions.OnlyOnFaulted,
            m_syncContextTaskScheduler);
        base.OnMouseClick(e);
    }
}
```

컴퓨트 바운드 작업(`Sum`)이 풀 스레드에서 돌기 때문에 GUI 스레드가 막히지 않고 사용자는 클릭으로 취소할 수 있다. 그러나 **풀 스레드가 실행하는 코드는 UI 요소를 갱신하려 해서는 안 된다** — 하면 `InvalidOperationException`이 던져진다. 그래서 세 연속을 전부 동기화 컨텍스트 스케줄러에 붙였다.

> **📌 `FromCurrentSynchronizationContext()`는 반드시 UI 스레드에서 호출해야 한다**
>
> 이 메서드는 **호출 시점의** `SynchronizationContext.Current`를 잡는다. 풀 스레드에서 호출하면 잡을 컨텍스트가 없다. .NET Framework에서는 이 경우 `InvalidOperationException`이 던져진다. 그래서 위 예제가 폼 생성자에서 미리 얻어 필드에 보관한다.
>
> 현대 코드에서 이 스케줄러를 직접 쓸 일은 거의 없다. `await`가 같은 일을 자동으로 해 주기 때문이다(47.12절). `ContinueWith`로 짠 레거시 코드를 읽고 고칠 때 필요한 지식이다.

### 커스텀 스케줄러 — 계약

특별한 스케줄링 요구가 있다면 `TaskScheduler`에서 파생한 클래스를 직접 정의할 수 있다. 구현해야 하는 계약은 다음과 같다.

```csharp
public abstract class TaskScheduler
{
    // 태스크를 이 스케줄러의 큐에 넣는다. 언젠가 TryExecuteTask 를 불러야 한다
    protected internal abstract void QueueTask(Task task);
    // 현재 스레드에서 인라인 실행할지 결정한다. 실행했으면 true, 거부했으면 false
    protected abstract bool TryExecuteTaskInline(Task task, bool taskWasPreviouslyQueued);
    protected abstract IEnumerable<Task> GetScheduledTasks();   // 디버거용
    protected internal virtual bool TryDequeue(Task task);      // 선택
    public virtual int MaximumConcurrencyLevel { get; }         // 기본 int.MaxValue
    protected bool TryExecuteTask(Task task);   // 실제로 태스크를 실행하는 유일한 통로
}
```

계약에서 지켜야 할 것이 둘 있다. 첫째, **`QueueTask`는 태스크를 실행하는 것이 아니라 "언젠가 실행되도록" 보장한다.** 실제 실행은 `TryExecuteTask(task)`를 통해서만 한다 — 태스크의 델리게이트를 직접 호출하면 예외 포착·상태 전이·부모-자식 관계가 전부 깨진다. 둘째, **`TryExecuteTaskInline`은 거부할 수 있어야 한다.** 이 메서드는 누군가 `task.Wait()`를 호출했을 때 런타임이 "이 스레드에서 그냥 실행해 버릴까?"를 묻는 통로이고, 스케줄러의 불변식("동시에 하나만" 같은 것)을 깨뜨리는 요청이면 `false`를 돌려줘야 한다.

동시성을 제한하는 스케줄러의 뼈대는 이렇다.

```csharp
// 동시에 n 개까지만 실행하는 스케줄러 (핵심 부분)
public sealed class LimitedConcurrencyTaskScheduler : TaskScheduler
{
    [ThreadStatic] private static bool t_processing;
    private readonly LinkedList<Task> _tasks = new LinkedList<Task>();
    private readonly int _max;
    private int _running;

    protected override void QueueTask(Task task)
    {
        lock (_tasks) { _tasks.AddLast(task); if (_running < _max) { _running++; Pump(); } }
    }

    private void Pump() => ThreadPool.UnsafeQueueUserWorkItem(_ =>
    {
        t_processing = true;
        try
        {
            while (true)
            {
                Task item;
                lock (_tasks)
                {
                    if (_tasks.Count == 0) { _running--; break; }
                    item = _tasks.First.Value; _tasks.RemoveFirst();
                }
                TryExecuteTask(item);          // 반드시 이 메서드로 실행한다
            }
        }
        finally { t_processing = false; }
    }, null);

    protected override bool TryExecuteTaskInline(Task task, bool wasQueued)
    {
        if (!t_processing) return false;       // 내 스레드가 아니면 인라인을 거부한다
        if (wasQueued && !TryDequeue(task)) return false;
        return TryExecuteTask(task);
    }

    protected override bool TryDequeue(Task t) { lock (_tasks) return _tasks.Remove(t); }
    protected override IEnumerable<Task> GetScheduledTasks() { lock (_tasks) return _tasks.ToArray(); }
    public override int MaximumConcurrencyLevel => _max;
}
```

생성자의 `_max`에 1을 넘기면 **단일 스레드 순차 실행 스케줄러**가 된다. 태스크들이 서로 다른 풀 스레드에서 실행되더라도 절대 겹치지 않으므로, 잠금 없이 공유 상태를 다룰 수 있다.

> **⚠️ 커스텀 스케줄러를 만들기 전에 다시 생각하라**
>
> 원천 자료가 제한된 동시성·순차 실행 같은 예제 스케줄러를 소개하지만, 오늘날 이 요구들에는 더 나은 답이 있다. **동시 실행 제한**은 `SemaphoreSlim`(48.11절)이나 `Parallel.ForEachAsync`(50.7절)로, **순차 실행**은 채널이나 액터 형태의 큐(51.1절)로 푸는 편이 낫다.
>
> 커스텀 스케줄러는 태스크 인프라의 가장 깊은 층을 건드린다. `TryExecuteTaskInline`을 잘못 구현하면 데드락이 나고, 예외 처리를 빠뜨리면 미관측 예외가 쌓이며, `await`가 만드는 연속은 기본적으로 `TaskScheduler.Current`를 상속하므로 스케줄러가 예상 못 한 곳까지 전파된다. 정말 필요한 경우는 특수한 스레드(전용 COM 아파트, 특정 프레임워크의 렌더 스레드)에 태스크를 올려야 할 때 정도다.

> **📌 `TaskScheduler.Current`는 전염된다**
>
> 태스크 안에서 새 태스크를 만들면, 기본적으로 그 태스크는 `TaskScheduler.Current`(= 부모의 스케줄러)에 예약된다. 단일 스레드 스케줄러 위에서 도는 코드가 `Task.Factory.StartNew(...)`로 하위 작업을 만들면 그것도 같은 단일 스레드에 줄을 서게 되고, 그 하위 작업을 `Wait`하면 데드락이다. `TaskCreationOptions.HideScheduler`가 이 전염을 끊는 플래그이고, `Task.Run`은 애초에 항상 `TaskScheduler.Default`를 쓰므로 이 문제가 없다.

### `TaskFactory`

같은 설정을 공유하는 태스크를 여러 개 만들어야 할 때, 매번 같은 인자를 생성자에 넘기는 대신 **공통 설정을 캡슐화한 태스크 팩토리**를 만들 수 있다. `void`를 반환하는 태스크들에는 `TaskFactory`를, 특정 타입을 반환하는 태스크들에는 `TaskFactory<TResult>`를 쓴다(둘 다 `System.Object`에서 직접 파생한 동격의 타입이다). 생성자에 `CancellationToken`, `TaskScheduler`, `TaskCreationOptions`, `TaskContinuationOptions`를 넘겨 기본값으로 삼는다.

```csharp
var cts = new CancellationTokenSource();
var tf = new TaskFactory<int>(cts.Token, TaskCreationOptions.AttachedToParent,
                              TaskContinuationOptions.ExecuteSynchronously,
                              TaskScheduler.Default);

// 이 팩토리가 만드는 태스크는 전부 위 설정을 공유한다
var childTasks = new[]
{
    tf.StartNew(() => Sum(cts.Token, 10000)),
    tf.StartNew(() => Sum(cts.Token, 20000)),
    tf.StartNew(() => Sum(cts.Token, int.MaxValue))    // 너무 커서 OverflowException
};

// 자식 하나가 실패하면 나머지를 취소한다
foreach (var child in childTasks)
    child.ContinueWith(t => cts.Cancel(), TaskContinuationOptions.OnlyOnFaulted);

// 자식이 전부 끝나면 성공한 것들 중 최댓값을 구한다
tf.ContinueWhenAll(childTasks,
        done => done.Where(t => t.Status == TaskStatus.RanToCompletion).Max(t => t.Result),
        CancellationToken.None)             // 팩토리의 토큰을 덮어써 취소 불가로 만든다
    .ContinueWith(t => Console.WriteLine("최댓값: " + t.Result),
        TaskContinuationOptions.ExecuteSynchronously);
```

마지막 `ContinueWhenAll`에 `CancellationToken.None`을 명시적으로 넘긴 것에 주목하라. 다른 자식들이 취소되더라도 **결과를 집계하는 이 태스크만은 실행되어야** 하므로, 팩토리의 기본 토큰을 덮어쓴 것이다. 참고로 `ContinueWhenAll`/`ContinueWhenAny`에는 `OnlyOnFaulted` 같은 조건부 플래그를 쓸 수 없다 — 선행 태스크들이 어떻게 끝났든 연속이 실행된다. 둘 다 `Task.WhenAll`/`WhenAny` 이전의 API이므로 새 코드에서는 쓰지 마라.

`Task.Factory`는 기본 설정을 가진 `TaskFactory` 인스턴스를 노출하는 정적 속성이고, 그래서 `Task.Factory.StartNew(...)`라는 관용구가 성립한다.

> **⚠️ `Task.Factory.StartNew`의 기본값이 위험한 이유(재확인)**
>
> 46.3절에서 이미 다뤘지만 이 절의 맥락에서 다시 정리할 값어치가 있다. `Task.Factory.StartNew`의 기본값은 `TaskScheduler.Current`이고 `DenyChildAttach`가 **꺼져 있다.** 반면 `Task.Run`은 `TaskScheduler.Default` + `DenyChildAttach`다.
>
> | 항목 | `Task.Run(f)` | `Task.Factory.StartNew(f)` |
> |---|---|---|
> | 스케줄러 | 항상 `TaskScheduler.Default` | `TaskScheduler.Current` |
> | 자식 부착 | `DenyChildAttach`(차단) | 허용 |
> | `async` 람다 | 자동 언랩(`Task` 반환) | `Task<Task>` 반환 — `Unwrap()` 필요 |
> | 옵션 지정 | 불가 | 가능 |
>
> **`LongRunning` 같은 옵션이 정말 필요한 경우가 아니면 언제나 `Task.Run`을 써라.** `StartNew`에 `async` 람다를 넘겨 놓고 왜 즉시 완료되는지 몰라 헤매는 것이 가장 흔한 사고다.

### `TaskCreationOptions` 전수

```csharp
[Flags, Serializable]
public enum TaskCreationOptions
{
    None                            = 0x0000,
    PreferFairness                  = 0x0001,
    LongRunning                     = 0x0002,
    AttachedToParent                = 0x0004,
    DenyChildAttach                 = 0x0008,
    HideScheduler                   = 0x0010,
    RunContinuationsAsynchronously  = 0x0040,
}
```

| 플래그 | 의미 | 항상 존중되는가 |
|---|---|---|
| `None` | 기본값 | — |
| `PreferFairness` | 이 태스크를 나중보다 먼저 실행해 달라고 스케줄러에 **힌트**를 준다. 실제로는 로컬 큐(LIFO) 대신 전역 큐(FIFO)로 보낸다 | 힌트 |
| `LongRunning` | 오래 걸리는 태스크라고 스케줄러에 힌트를 준다. 기본 스케줄러는 **풀에 넣지 않고 전용 스레드를 새로 만든다** | 힌트 |
| `AttachedToParent` | 자신을 만든 태스크의 자식이 된다. 부모는 모든 자식(과 손자)이 끝나야 완료된 것으로 간주된다 | **항상** |
| `DenyChildAttach` | 자식이 붙으려 해도 붙지 못하게 한다. 붙으려던 태스크는 평범한 최상위 태스크가 된다 | **항상** |
| `HideScheduler` | 자식 태스크가 부모의 스케줄러 대신 기본 스케줄러를 쓰게 강제한다 | **항상** |
| `RunContinuationsAsynchronously` | 완료 시 연속을 동기 실행하지 않고 스케줄러에 큐잉한다(46.5절) | **항상** |

`PreferFairness`와 `LongRunning`은 `TaskScheduler`가 존중할 수도 무시할 수도 있는 **힌트**이고, 나머지는 스케줄러와 무관한 태스크 인프라 자체의 동작이므로 **항상 존중된다.**

> **⚠️ `LongRunning`은 전용 스레드를 만든다 — 그래서 남용하면 안 된다**
>
> 기본 스케줄러에서 `LongRunning`은 사실상 "이 태스크를 위해 스레드를 하나 새로 만들어라"로 동작한다. 이건 45.4절에서 본 스레드 생성 비용을 그대로 낸다는 뜻이다. 정당한 경우는 **몇 초 이상 CPU를 붙들거나 블로킹하는 작업 하나**를 풀에서 격리할 때다.
>
> 남용의 전형은 이렇다. 요청마다 `TaskCreationOptions.LongRunning`으로 태스크를 만드는 서버 코드는, 요청마다 스레드를 새로 만드는 코드와 정확히 같다. 46.1절 전체가 부정하는 그 방식이다.
>
> 반대로 **비동기 코드에는 `LongRunning`이 의미가 없다.** `async` 메서드는 첫 `await`에서 스레드를 반납하므로, 전용 스레드를 만들어 봐야 즉시 놀게 된다.

부모-자식 관계는 46.4절에서 다뤘으므로 여기서는 옵션 관점만 짚는다. 태스크 안에서 만든 태스크는 **기본적으로 아무 관계 없는 최상위 태스크**다. `AttachedToParent`를 줘야만 부모의 완료 조건에 포함된다. 반대로 라이브러리를 만든다면 **호출자가 넘긴 델리게이트가 몰래 자식을 붙이는 것을 막기 위해** `DenyChildAttach`를 켜는 것이 방어적이다. `Task.Run`이 이 플래그를 기본으로 켜는 이유가 그것이다.

실무에서 실제로 쓰게 되는 플래그는 둘뿐이다 — `RunContinuationsAsynchronously`(`TaskCompletionSource`를 만들 때, 46.5절)와 `LongRunning`(전용 스레드가 정말 필요할 때). 나머지는 대부분 `Task.Run`의 기본값이 알아서 처리하거나 애초에 쓸 일이 없다. 플래그를 조합해야 할 것 같다는 생각이 들면 설계를 먼저 의심하라.

## 46.11 관찰되지 않은 예외(`UnobservedTaskException`)

### 아무도 보지 않은 예외는 어디로 가는가

46.4절에서 본 대로, 태스크 본문이 던진 미처리 예외는 그 자리에서 프로세스를 죽이지 않는다. 예외는 **삼켜져 컬렉션에 저장되고** 풀 스레드는 풀로 돌아간다. `Wait`를 호출하거나 `Result`를 조회하면 그때 `AggregateException`으로 다시 던져진다.

문제는 아무도 그러지 않을 때다.

> **⚠️ `Wait`도 `Result`도 `Exception`도 건드리지 않으면 코드는 그 예외가 일어났다는 사실 자체를 모른다**
>
> 원천 자료의 경고 그대로다. 이건 바람직하지 않다. 프로그램이 예상치 못한 문제를 겪었는데 여러분은 그것을 모르는 상태이기 때문이다.
>
> 예외를 무시해도 되는 경우가 아예 없지는 않다. 예외가 **"더 이상 관심 없는 결과를 얻지 못했다"** 는 사실만을 뜻할 때다. 사용자가 웹 페이지 다운로드를 취소했다면 그 페이지가 존재하지 않았다는 사실은 아무래도 좋다.
>
> 그러나 예외가 **프로그램의 버그**를 뜻할 때 이것을 무시하면 두 가지 이유로 문제가 된다. 첫째, 그 버그가 프로그램을 유효하지 않은 상태로 남겼을 수 있다. 둘째, 그 버그의 결과로 나중에 더 많은 예외가 발생할 텐데, 최초 오류를 기록하지 않았으므로 진단이 어려워진다.

### `TaskScheduler.UnobservedTaskException`

미관측 예외를 탐지하려면 `TaskScheduler`의 정적 `UnobservedTaskException` 이벤트에 콜백을 등록한다.

```csharp
public static event EventHandler<UnobservedTaskExceptionEventArgs> UnobservedTaskException;

public class UnobservedTaskExceptionEventArgs : EventArgs
{
    public AggregateException Exception { get; }
    public bool Observed { get; }
    public void SetObserved();
}
```


이 이벤트는 **미관측 예외를 가진 `Task`가 가비지 컬렉션될 때 CLR의 파이널라이저 스레드가 발생시킨다.** 핸들러는 미관측 `AggregateException`을 담은 `UnobservedTaskExceptionEventArgs` 객체를 받는다.

```csharp
TaskScheduler.UnobservedTaskException += (sender, e) =>
{
    _logger.LogError(e.Exception, "관측되지 않은 태스크 예외");   // sender 는 대개 그 Task
    e.SetObserved();     // "봤다"고 표시한다
};
```

`SetObserved()`는 이 예외를 관측된 것으로 표시한다. .NET Framework 4.0에서는 이 호출 여부가 프로세스의 생사를 갈랐다.

> **⚠️ 미관측 예외가 프로세스를 죽이던 시절과 지금**
>
> .NET Framework 4.0에서는 미관측 예외를 가진 태스크가 파이널라이즈될 때 그 예외가 **파이널라이저 스레드에서 다시 던져져 프로세스를 종료시켰다.** `UnobservedTaskException` 핸들러에서 `SetObserved()`를 부르는 것이 이를 막는 유일한 방법이었다.
>
> **.NET Framework 4.5부터 기본 동작이 바뀌었다.** 미관측 예외는 이벤트를 발생시킨 뒤 무시되고, 프로세스는 계속 실행된다. 예전 동작으로 되돌리려면 .NET Framework 애플리케이션 구성 파일에 다음을 넣는다.
>
> ```xml
> <configuration>
>   <runtime>
>     <ThrowUnobservedTaskExceptions enabled="true"/>
>   </runtime>
> </configuration>
> ```
>
> **이 설정은 .NET Framework 전용이다.** .NET Core 계열(.NET 5 이후 포함)에는 이에 해당하는 설정이 없으며, 미관측 예외는 이벤트만 발생시키고 프로세스를 죽이지 않는다. 이 차이를 모르고 .NET Framework 코드를 .NET 8로 이식하면, 예전에는 즉시 크래시로 드러나던 버그가 조용히 묻히게 된다.

### 왜 늦게 발견되는가

가장 실무적으로 중요한 성질이 여기 있다.

`UnobservedTaskException`은 **오류가 발생한 시점이 아니라 그 태스크가 수거되는 시점에** 발생한다. 서버가 한가해 GC가 좀처럼 일어나지 않으면 몇 분 뒤에 뜨고, 프로세스가 그전에 종료되면 아예 뜨지 않는다. 로그의 타임스탬프가 사건 시각과 무관하다는 뜻이다.

또 하나. 이 이벤트는 **파이널라이저 스레드**에서 발생하므로, 핸들러가 오래 걸리거나 예외를 던지면 파이널라이저 큐 전체가 막힌다(34장).

무엇이 미관측인가. **태스크를 만들고 아무도 `await`하지 않은 경우, `WhenAny`에서 진 태스크가 나중에 실패한 경우, 타임아웃을 걸고 기다린 태스크가 타임아웃 이후에 실패한 경우**가 전부 여기 해당한다. 반대로 `await task`, `task.Wait()`, `task.Result` 조회는 물론이고 **`task.Exception` 속성을 조회하는 행위 자체가 그 예외를 "관측됨"으로 만든다.**

두 번째 사실이 실무적으로 유용하다. 예외를 처리하지 않더라도 조회만 하면 미관측 상태를 해제할 수 있다.

```csharp
// 진 태스크를 관측만 해 두는 관용구
static void Observe(Task t) =>
    t.ContinueWith(static x => _ = x.Exception,     // 읽기만 한다
                   CancellationToken.None,
                   TaskContinuationOptions.OnlyOnFaulted | TaskContinuationOptions.ExecuteSynchronously,
                   TaskScheduler.Default);
```

> **💡 이 이벤트는 반드시 로깅에 연결하라 — 그러나 이것을 대책으로 삼지는 마라**
>
> 애플리케이션 시작 지점에서 `TaskScheduler.UnobservedTaskException`을 로깅에 연결하는 것은 **비용이 거의 없고 언젠가 반드시 도움이 되는 조치다.** 프로덕션에서 원인 불명의 이상 동작을 추적할 때, 이 로그 한 줄이 유일한 단서인 경우가 드물지 않다.
>
> ```csharp
> // 애플리케이션 시작 시 한 번
> TaskScheduler.UnobservedTaskException += (s, e) =>
> {
>     foreach (var inner in e.Exception.Flatten().InnerExceptions)
>         Log.Error(inner, "미관측 태스크 예외 (사건 시각 아님)");
>     e.SetObserved();
> };
> ```
>
> 다만 이것은 **탐지 장치이지 처리 장치가 아니다.** 로그에 이 메시지가 뜬다는 것은 어딘가에 "만들어 놓고 잊어버린" 태스크가 있다는 뜻이고, 진짜 할 일은 그 코드를 찾아 예외를 제대로 처리하게 고치는 것이다.

## 46.12 진행 상황 보고 — `IProgress<T>`

### 델리게이트를 직접 넘기면 안 되는 이유

비동기 연산이 진행 상황을 알려 줘야 할 때가 있다. 가장 단순한 해법은 `Action` 델리게이트를 넘기고 진행이 바뀔 때마다 호출하는 것이다.

```csharp
Task Foo(Action<int> onProgressPercentChanged) => Task.Run(() =>
{
    for (int i = 0; i < 1000; i++)
    {
        if (i % 10 == 0) onProgressPercentChanged(i / 10);
        // 컴퓨트 바운드 작업...
    }
});

Action<int> progress = i => Console.WriteLine(i + " %");
await Foo(progress);
```

콘솔 애플리케이션에서는 잘 동작한다. 그러나 리치 클라이언트에서는 이상적이지 않다. **워커 스레드에서 진행 상황을 보고하므로 소비자 쪽에 스레드 안전성 문제가 생길 수 있기 때문이다.** 사실상 동시성의 부작용을 바깥세상으로 "새어 나가게" 만든 셈이다.

### `IProgress<T>`와 `Progress<T>`

프레임워크는 이 문제를 풀기 위해 인터페이스 하나와 그 구현 클래스 하나를 제공한다.

```csharp
public interface IProgress<in T> { void Report(T value); }
```

메서드가 하나뿐이므로 쓰는 쪽의 코드는 거의 바뀌지 않는다.

```csharp
Task Foo(IProgress<int> onProgressPercentChanged) => Task.Run(() =>
{
    for (int i = 0; i < 1000; i++)
    {
        if (i % 10 == 0) onProgressPercentChanged.Report(i / 10);
        // 컴퓨트 바운드 작업...
    }
});
```

`Progress<T>` 클래스는 `Action<T>` 델리게이트를 받는 생성자로 그것을 감싼다 — `var progress = new Progress<int>(i => Console.WriteLine(i + " %"));` 그리고 생성자에 델리게이트를 넘기는 대신(또는 그와 함께) 구독할 수 있는 `ProgressChanged` 이벤트도 노출한다.

### 핵심 동작 — 생성 시점의 동기화 컨텍스트로 되돌린다

**`Progress<int>` 인스턴스를 만들 때 그 클래스는 (있다면) 현재 동기화 컨텍스트를 캡처한다. 이후 `Foo`가 `Report`를 호출하면 델리게이트가 그 컨텍스트를 통해 호출된다.**

이 한 문장이 `Progress<T>`의 존재 이유 전부다.

```text
  UI 스레드                                 워커 스레드
  ────────────────────────────────         ────────────────────────
  var p = new Progress<int>(Update);
        │  ← 여기서 SynchronizationContext.Current 를 캡처
  await Foo(p); ────────────────────────→  Foo 본문 → p.Report(30)
        ┌─────────────────────────────────────────┘  캡처한 컨텍스트로 Post
        ▼
  Update(30) 실행  ← UI 스레드다. 컨트롤을 직접 갱신해도 안전하다
```

> **⚠️ `Progress<T>`를 어디서 만드는가가 전부를 결정한다**
>
> 캡처는 **`Report` 시점이 아니라 생성자 시점**에 일어난다. 따라서
>
> ```csharp
> // 옳다: UI 스레드에서 만들었으므로 콜백이 UI 스레드로 돌아온다
> private async void OnClick(object s, EventArgs e)
> {
>     var progress = new Progress<int>(p => _progressBar.Value = p);
>     await _service.RunAsync(progress);
> }
>
> // 틀렸다: 워커 스레드에서 만들면 콜백도 워커 스레드에서 실행된다
> await Task.Run(async () =>
> {
>     var progress = new Progress<int>(p => _progressBar.Value = p);   // 여기가 문제
>     await _service.RunAsync(progress);
> });
> ```
>
> 아래 코드의 콜백은 UI 스레드가 아닌 곳에서 컨트롤을 만지므로 `InvalidOperationException`이 난다. **`Progress<T>`는 UI 코드에서, `await` 앞에서 만들어라.**

동기화 컨텍스트가 없으면 — 콘솔 앱, ASP.NET Core, `Task.Run` 안, 라이브러리 내부가 전부 여기 해당한다 — **스레드 풀을 대상으로 하는 기본 컨텍스트가 쓰인다.** 즉 콜백은 임의의 풀 스레드에서 실행되고, 그 안에서 공유 상태를 만진다면 잠금이 필요하다. 커스텀 `SynchronizationContext` 아래에서 만들었다면 그 컨텍스트가 정하는 스레드에서 실행된다.

### `Report`는 비동기다 — 순서도 최종값도 보장되지 않는다

여기가 가장 조용히 물리는 지점이다. `Progress<T>`는 캡처한 컨텍스트에 콜백을 **`Post`(비동기 전송)** 한다. `Send`(동기)가 아니다. 원천 자료의 표현대로, **진행 상황 갱신을 비동기적으로 발생시켜 비동기 연산이 지연되지 않게 하기 위해서**다.

그래서 다음이 전부 사실이다.

- `Report(50)`이 반환되었다고 해서 콜백이 실행된 것은 아니다. 큐에 들어갔을 뿐이다.
- `Report(10)`, `Report(20)`, `Report(30)`을 빠르게 연달아 호출했을 때 **그 순서대로 처리된다는 보장이 문서화되어 있지 않다.** 특히 컨텍스트가 없어 풀 스레드로 갈 때는 순서가 뒤집힐 수 있다.
- 가장 중요한 것: **연산이 끝난 뒤에 마지막 진행 콜백이 도착할 수 있다.**

```csharp
var progress = new Progress<int>(p => _label.Text = $"{p}%");
await _service.RunAsync(progress);
_label.Text = "완료";              // 여기서 "완료" 를 쓴 뒤에
                                   // 큐에 남아 있던 Report(100) 콜백이 실행되어
                                   // 라벨이 다시 "100%" 로 덮일 수 있다
```

> **⚠️ 진행률 100%를 "완료"의 신호로 쓰지 마라**
>
> 완료의 신호는 **태스크의 완료**다. `await`가 반환되는 것이 완료다. `Report(100)`이 도착하는 것이 아니다. 진행 콜백에서 "작업이 끝났으니 다음 화면으로 넘어간다" 같은 상태 전이를 하는 코드는 경합을 안고 있다.
>
> 마찬가지로 진행 콜백에서 누적 계산을 하면 안 된다. `_total += p;` 같은 코드는 순서와 중복에 취약하다. `Report`가 넘겨주는 값은 **그 자체로 완결된 스냅샷**이어야 한다.

> **📌 값 타입을 넘길 때 캡처 시점의 값이 아니라 복사본이 간다**
>
> `IProgress<T>`의 `T`가 가변 참조 타입이면 위험하다. 워커가 같은 객체를 재사용하며 값만 바꿔 `Report`를 반복 호출하면, 콜백이 비동기로 실행될 즈음에는 그 객체가 이미 다음 값으로 덮여 있다. **`T`는 값 타입이거나 불변 타입이어야 한다.** 여러 값을 보고해야 한다면 튜플이나 `record`가 알맞다.
>
> ```csharp
> // 좋다
> IProgress<(int Percent, string Message)> progress
> // 위험하다
> IProgress<MutableProgressInfo> progress   // 재사용되는 인스턴스를 넘기면 깨진다
> ```

### 고빈도 보고의 스로틀링

`Report`는 값싸지 않다. 컨텍스트에 `Post`한다는 것은 UI 스레드의 메시지 큐에 항목을 하나 넣는다는 뜻이고, 그 메시지들은 UI 스레드가 처리해야 한다.

> **⚠️ 초당 수천 번의 `Report`는 UI를 얼린다**
>
> 파일 100만 개를 처리하며 매 파일마다 `Report`를 부르면, UI 스레드는 진행률 갱신 메시지를 처리하느라 사용자 입력을 처리할 틈이 없어진다. 아이러니하게도 **"진행 상황을 보여 주려던" 코드가 애플리케이션을 응답 없음 상태로 만든다.**
>
> 화면 갱신이 사람 눈에 의미 있으려면 초당 10~30회면 충분하다. 두 가지 스로틀링 전략이 있다.
>
> **1. 생산자 쪽에서 줄인다** — 가장 간단하고 효과적이다.
>
> ```csharp
> var sw = Stopwatch.StartNew();
> var last = TimeSpan.Zero;
> for (int i = 0; i < files.Length; i++)
> {
>     Process(files[i]);
>     // 100ms 마다, 그리고 마지막에 한 번
>     if (sw.Elapsed - last > TimeSpan.FromMilliseconds(100) || i == files.Length - 1)
>     {
>         last = sw.Elapsed;
>         progress?.Report((i + 1) * 100 / files.Length);
>     }
> }
> ```
>
> **2. 소비자 쪽에서 병합한다** — `IProgress<T>`를 직접 구현해 최신 값만 남기고 타이머로 UI를 갱신한다. 생산자를 고칠 수 없을 때의 방법이다.
>
> 두 방법 모두 **마지막 값이 반드시 반영되도록** 보장해야 한다. 스로틀링 때문에 "99%에서 멈춘 진행률 바"가 남는 것이 이 최적화의 전형적 버그다.

### 취소와 함께 쓰는 표준 시그니처

TAP 규약(47.15절)은 취소와 진행 보고를 **선택적**으로 정의한다. 취소를 지원할 수 있을 때만 `CancellationToken` 오버로드를 두고, 진행을 정확히 보고할 수 있을 때만 `IProgress<T>` 오버로드를 둔다. 원천 자료의 급여 처리 예제가 오버로드 집합의 정석을 보여 준다.

```csharp
public Task RunPayroll(DateTime payrollPeriod)
    => RunPayroll(payrollPeriod, CancellationToken.None, null);

public Task RunPayroll(DateTime payrollPeriod, CancellationToken cancellationToken)
    => RunPayroll(payrollPeriod, cancellationToken, null);

public Task RunPayroll(DateTime payrollPeriod, IProgress<(int, string)> progress)
    => RunPayroll(payrollPeriod, CancellationToken.None, progress);

// 실제 구현은 하나뿐이다
public async Task RunPayroll(DateTime payrollPeriod, CancellationToken cancellationToken,
                             IProgress<(int, string)> progress)
{
    progress?.Report((0, "급여 처리 시작"));

    var payrollData = await RetrieveEmployeePayrollDataFor(payrollPeriod);   // 1단계
    cancellationToken.ThrowIfCancellationRequested();
    progress?.Report((20, "직원과 근무 시간 조회 완료"));

    var taxReporting = new Dictionary<EmployeePayrollData, TaxWithholding>(); // 2단계
    foreach (var employee in payrollData)
        taxReporting.Add(employee, await RetrieveTaxData(employee));
    cancellationToken.ThrowIfCancellationRequested();
    progress?.Report((40, "원천징수 계산 완료"));

    await Task.WhenAll(taxReporting                                          // 3단계
        .Select(i => GenerateAndEmailPaystub(i.Key, i.Value)));
    cancellationToken.ThrowIfCancellationRequested();
    progress?.Report((60, "명세서 발송 완료"));

    // 4단계: 급여 이체 — 이 지점을 지나면 더 이상 취소할 수 없다
    await Task.WhenAll(taxReporting.Select(i => MakeDeposit(i.Key, i.Value)));
    progress?.Report((80, "이체 완료"));

    await ClosePayrollPeriod(payrollPeriod);                                 // 5단계
    progress?.Report((100, "완료"));
}
```

이 코드에서 배울 점 넷. **공통 코드는 하나의 메서드에 모으고** 오버로드들은 기본값을 채워 넘기기만 한다. **`progress?.Report(...)`** 의 물음표가 핵심이다 — `IProgress<T>` 매개변수는 `null`을 허용해야 하며 `null`이면 보고를 생략한다. **취소를 지원하지 않는 오버로드도 토큰을 만들어 넘긴다** — 절대 취소되지 않는 토큰이므로 `ThrowIfCancellationRequested()`가 아무 일도 하지 않고, 분기가 늘지 않는다. 마지막으로 **4단계 이후에는 취소 확인이 없다.** 돈이 이체된 뒤에는 되돌릴 수 없으므로 취소를 받아 주지 않는 것이 옳다 — 46.8절의 "상태 일관성 보장 책임"이 코드로 나타난 모습이다.

| 규약 | 내용 |
|---|---|
| 매개변수 이름 | `cancellationToken`, `progress` |
| 매개변수 순서 | 동기 버전의 매개변수 → `cancellationToken` → `progress` |
| `null` 허용 | `progress`는 `null` 허용. 토큰은 `CancellationToken.None` |
| 보고 시점 | `Report`는 **동기적으로** 호출한다 — 비동기 처리는 `Progress<T>`가 한다 |
| 지원 표시 | 지원할 수 없으면 그 오버로드를 아예 만들지 않는다 |

## 이 장의 요약

- **스레드 풀은 스레드를 재사용하는 인프라이며 CLR 하나당 하나다.** 전역 큐 하나와 워커 스레드마다의 로컬 큐로 이루어지고, 로컬 큐는 LIFO·잠금 없음, 전역 큐는 FIFO·잠금 필요다. 로컬 큐가 비면 다른 스레드의 큐 꼬리에서 작업을 훔친다.
- **풀의 스레드 수는 hill-climbing으로 조율된다.** 처리량을 측정하며 스레드 수를 밀어 보고 결과가 좋으면 같은 방향으로 더 간다. 블로킹은 이 알고리즘을 속여 스레드 주입을 유발하고, 심하면 스레드 풀 기아가 된다.
- **`Task`는 `QueueUserWorkItem`이 못 하는 네 가지를 한다** — 완료 통지, 결과 반환, 예외 전파, 연속. 대가는 태스크 하나당 여러 필드의 상태 객체다.
- **태스크의 예외는 삼켜졌다가 관측 시점에 다시 던져진다.** `Wait`/`Result`는 `AggregateException`으로 감싸서, `await`는 첫 예외를 벗겨서 던진다. 아무도 관측하지 않으면 `TaskScheduler.UnobservedTaskException`이 GC 시점에야 알려 준다.
- **`TaskCompletionSource`는 델리게이트 없이 태스크를 만든다.** 이벤트·콜백·레거시 APM을 태스크로 감싸는 어댑터의 핵심이며, 만들 때 거의 언제나 `RunContinuationsAsynchronously`를 켜야 한다.
- **`Task.Delay`는 스레드를 잡지 않고, `PeriodicTimer`는 콜백 겹침이 구조적으로 불가능하다.** 반면 `System.Threading.Timer`와 `System.Timers.Timer`는 앞 콜백이 끝났는지 모르므로 겹친다. 주기 작업 설계의 실제 쟁점은 드리프트 보정과 "작업이 주기를 넘을 때의 정책"이다.
- **실행 컨텍스트는 `AsyncLocal<T>` 같은 앰비언트 상태를 비동기 흐름을 따라 흘린다.** 예약 시점에 캡처되고 실행 시점에 복원되며, 부모에서 자식으로만 흐른다. `ConfigureAwait(false)`는 동기화 컨텍스트만 끄지 실행 컨텍스트는 끄지 않는다.
- **취소는 협력적이다.** `CancellationToken`은 강제 중단 수단이 아니라 요청이고, 취소 후의 상태 일관성은 연산을 구현한 쪽 책임이다. `Register` 콜백은 `Cancel`을 호출한 스레드에서 동기 실행되며, 등록과 연결 소스는 `Dispose`해야 누수를 막는다.
- **합성기는 예외 관측의 관점에서 이해해야 한다.** `WhenAll`은 전부 기다리며 예외를 모으지만 `await`는 첫 예외만 던진다. `WhenAny`는 진 태스크의 예외를 방치하고, 타임아웃 관용구는 대상 연산을 실제로는 멈추지 않는다. `WhenEach`(※.NET 9)가 "완료 순서대로"를 표준화했다.
- **`Progress<T>`는 생성 시점의 동기화 컨텍스트로 콜백을 되돌린다.** 그래서 UI 스레드에서 만들어야 한다. `Report`는 비동기이므로 순서와 최종값이 보장되지 않으며, 고빈도 보고는 반드시 스로틀링해야 한다.

## 연습 문제

1. `Thread.Sleep(2000)`을 호출하는 작업 100개를 `ThreadPool.QueueUserWorkItem`으로 큐잉하고, 1초마다 `ThreadPool.ThreadCount`를 출력하는 프로그램을 작성하라. 그다음 `Thread.Sleep`을 `await Task.Delay`로 바꾸고 같은 측정을 하라. 스레드 수 곡선이 어떻게 달라지는지 설명하라(46.2절, 46.6절).

2. `System.Threading.Timer`를 `period = 500ms`로 만들고 콜백 안에서 `Thread.Sleep(2000)`을 하도록 하라. 콜백 진입 시 `Interlocked.Increment`로 동시 실행 수를 세어 출력하라. 겹침을 실제로 관측한 뒤, 같은 작업을 `PeriodicTimer`로 다시 작성해 최대 동시 실행 수가 1임을 확인하라.

3. `AsyncLocal<string>`을 하나 두고, ① `await` 앞뒤, ② `Task.Run` 안, ③ `new Thread` 안, ④ `ExecutionContext.SuppressFlow()` 범위 안의 `Task.Run`에서 각각 값을 출력하라. 네 경우의 결과를 표로 정리하고, 자식이 값을 바꿨을 때 부모가 그것을 보는지도 확인하라.

4. `CancellationToken.Register`에 `Thread.Sleep(3000)`을 하는 콜백을 등록한 뒤 `cts.Cancel()`을 호출하고, `Cancel()` 전후로 `Stopwatch`를 찍어라. `Cancel()`이 3초간 블로킹되는 것을 확인한 다음 `CancelAsync()`(※.NET 8)로 바꿔 차이를 측정하라.

5. 5초 걸리는 태스크와 1초 뒤 실패하는 태스크를 `Task.WhenAny`로 조합하라. 이긴 쪽만 `await`하고 프로그램을 계속 돌리면서 `GC.Collect()`와 `GC.WaitForPendingFinalizers()`를 호출하라. `TaskScheduler.UnobservedTaskException`이 언제 발생하는지 관측하고, 진 태스크에 관측용 연속을 붙이면 발생하지 않음을 확인하라.

6. `Task.WhenAll`에 실패하는 태스크 3개를 넘기고 `await`하라. `catch`로 받은 예외에 몇 개가 들어 있는지, 합쳐진 태스크의 `Exception.InnerExceptions.Count`가 몇인지 각각 출력해 차이를 확인하라. 그다음 같은 태스크들을 `Task.WhenEach`(※.NET 9)로 소비하며 실패를 개별 처리하도록 고쳐 보라.

7. 파일 10,000개의 크기를 합산하며 `IProgress<int>`로 진행률을 보고하는 메서드를 작성하라. 먼저 매 파일마다 `Report`를 호출해 UI(또는 콘솔 출력)가 얼마나 느려지는지 측정하고, 100밀리초 스로틀링을 넣어 다시 측정하라. 스로틀링 후에도 마지막 100%가 반드시 보고되도록 만들어라.
