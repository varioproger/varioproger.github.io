# 44장. 암호화

> **이 장의 위치** — Part VIII「BCL II — 데이터와 I/O」의 마지막 장이다. 40장에서 `CryptoStream`이라는 이름만 던지고 넘어간 것, 43장에서 "TLS·인증서의 상세는 44장"이라고 미뤄 둔 것을 여기서 끝낸다. 암호화는 API 목록을 외운다고 되는 분야가 아니다. **무엇을 지키려는지 정의하지 못하면 어떤 API를 써도 안전하지 않다.** 이 장은 .NET이 제공하는 도구의 지도를 그리고, 그 도구를 잘못 조립하는 방법이 왜 그렇게 많은지를 함께 다룬다.
>
> **선수 지식** — 33장(결정적 정리와 IDisposable), 39장(숫자와 유틸리티 타입), 40장(스트림과 파일 I/O)
>
> **이 장에서 다루지 않는 것** — 스트림 아키텍처와 데코레이터 패턴 자체는 40장, TLS 핸드셰이크·HTTPS·`SslStream`의 사용법은 43장, 난수 생성기의 일반적인 비교(`Random` vs `RandomNumberGenerator`)는 39.5절이다. 역직렬화 공격은 41.8절, 어셈블리 강력한 이름과 Authenticode 서명은 52.5절·52.7절에서 다룬다. ASP.NET Core의 인증·인가 파이프라인은 81.3절의 지도에 맡긴다.

## 44.1 .NET 암호화 API 개요와 선택 기준

### 이 장에서 쓰는 네임스페이스

```csharp
using System.Security.Cryptography;                 // 대부분의 타입이 여기 있다
using System.Security.Cryptography.X509Certificates; // 인증서
using System.Security.Cryptography.Xml;              // XML 서명 (특수 목적)
using System.Security.Cryptography.Pkcs;             // CMS/PKCS#7 (NuGet 패키지)
using System.Text;                                   // Encoding
```

`System.Security.Cryptography`가 사실상 전부다. `System.Security.Cryptography.Xml`은 XML 기반 서명의 생성·검증을 위한 특수 목적 지원이고, `X509Certificates`는 디지털 인증서를 다루는 타입을 담는다.

### 먼저 정할 것 — 무엇을 지키려는가

암호화 API를 고르기 전에 답해야 하는 질문은 "어떤 알고리즘을 쓸까"가 아니다. **"공격자가 무엇을 할 수 있고, 나는 무엇을 막고 싶은가"** 다. 보안 목표는 네 가지로 나뉜다.

| 목표 | 정의 | 공격자가 못 하게 되는 것 |
|---|---|---|
| **기밀성**(confidentiality) | 내용을 못 읽게 한다 | 데이터를 훔쳐 읽기 |
| **무결성**(integrity) | 변조를 탐지한다 | 데이터를 몰래 바꾸기 |
| **인증**(authentication) | 보낸 쪽이 누구인지 확인한다 | 다른 사람인 척하기 |
| **부인 방지**(non-repudiation) | 보낸 사실을 나중에 부인하지 못하게 한다 | "나는 그거 안 보냈다"고 우기기 |

이 네 가지는 **하나를 달성한다고 나머지가 따라오지 않는다.** 특히 초심자가 가장 많이 하는 착각이 "암호화했으니 변조도 못 하겠지"다. 틀렸다. 44.5절에서 왜 틀렸는지 구체적으로 본다.

목표가 정해지면 도구는 거의 자동으로 결정된다.

| 지키려는 것 | 도구 | .NET 타입 | 절 |
|---|---|---|---|
| 기밀성만 (대량 데이터) | 대칭 암호 | `Aes` | 44.5절 |
| 기밀성 + 무결성 + (암묵적) 인증 | 인증 암호(AEAD) | `AesGcm`, `ChaCha20Poly1305` | 44.5절 |
| 무결성만 (비적대적 환경) | 해시 | `SHA256`, `SHA512` | 44.3절 |
| 무결성 + 인증 (공유 비밀 있음) | MAC | `HMACSHA256` | 44.3절 |
| 무결성 + 인증 + 부인 방지 | 디지털 서명 | `RSA`, `ECDsa` | 44.7절 |
| 비밀번호 저장 | 비밀번호 해시 | `Rfc2898DeriveBytes`, Argon2 | 44.4절 |
| 사전 공유 비밀 없이 키 합의 | 키 교환 | `ECDiffieHellman` | 44.7절 |
| 로컬 머신에서 설정값 보호 | OS 위임 | `ProtectedData`(Windows) | 44.2절 |
| 예측 불가능한 값 생성 | CSPRNG | `RandomNumberGenerator` | 44.8절 |

> **⚠️ "암호화"라는 단어가 가리는 것**
>
> 실무 요구사항이 "이 데이터를 암호화해 주세요"로 들어오면 그대로 받아들이면 안 된다. 실제로 필요한 것이 무엇인지 되물어야 한다.
>
> - "비밀번호를 암호화해 저장"은 **거의 항상 틀린 요구사항**이다. 비밀번호는 암호화가 아니라 해싱 대상이다(44.4절). 암호화하면 복호화가 가능하다는 뜻이고, 그건 서버가 평문 비밀번호를 알 수 있다는 뜻이다.
> - "설정 파일을 암호화"는 보통 **키를 어디 둘 것인가** 문제로 되돌아온다. 키가 같은 파일 시스템에 있으면 암호화하지 않은 것과 큰 차이가 없다(44.6절).
> - "전송 구간 암호화"는 대부분 **TLS를 켜는 일**이지 직접 암호화하는 일이 아니다(43장).

### .NET이 제공하는 옵션의 전체 그림

원천이 정리한 옵션 비교는 다음과 같다.

| 옵션 | 관리할 키 개수 | 속도 | 강도 | 비고 |
|---|---|---|---|---|
| `File.Encrypt` | 0 | 빠름 | 사용자 암호에 의존 | 파일 시스템에서 투명하게 보호. 키는 로그인 사용자 자격 증명에서 암묵적으로 파생. Windows 전용 |
| Windows 데이터 보호(DPAPI) | 0 | 빠름 | 사용자 암호에 의존 | 바이트 배열을 암묵적 키로 암호화·복호화. Windows 전용 |
| 해싱 | 0 | 빠름 | 높음 | 단방향(비가역) 변환. 비밀번호 저장, 손상 검출용 체크섬 계산에 사용 |
| 대칭 암호화 | 1 | 빠름 | 높음 | 범용 암호화. 암호화·복호화에 같은 키를 쓴다. 메시지 서명에도 쓸 수 있다 |
| 공개키 암호화 | 2 | 느림 | 높음 | 암호화와 복호화에 다른 키를 쓴다. 대칭 키의 교환과 디지털 서명에 사용 |

여기에 .NET은 XML 기반 서명을 만들고 검증하는 `System.Security.Cryptography.Xml`, 디지털 인증서를 다루는 `System.Security.Cryptography.X509Certificates`를 더 제공한다.

### 런타임 동작 — .NET은 암호를 직접 구현하지 않는다

`SHA256.Create()`나 `Aes.Create()`가 반환하는 객체는 관리 코드로 작성된 암호 구현이 아니다. .NET(Core) 이후의 구현은 **OS가 제공하는 검증된 암호 라이브러리에 위임**한다.

| 플랫폼 | 실제로 호출되는 것 |
|---|---|
| Windows | CNG(Cryptography Next Generation), 일부 레거시 경로는 CAPI |
| Linux | OpenSSL |
| macOS | Apple이 제공하는 시스템 암호 라이브러리 |

이 설계가 중요한 이유는 세 가지다.

1. **하드웨어 가속을 공짜로 얻는다.** AES-NI 명령어, SHA 확장 명령어는 OS 라이브러리가 이미 쓰고 있다. 관리 코드로 다시 짜면 그 이득이 사라진다.
2. **부채널 방어를 물려받는다.** 상수 시간 구현, 캐시 타이밍 대응 같은 것은 전문가가 수년에 걸쳐 다듬은 결과물이다.
3. **OS의 정책을 따른다.** FIPS 모드, 알고리즘 사용 금지 정책 같은 시스템 설정이 그대로 적용된다.

> **⚠️ FIPS 모드에서 조용히 실패하는 알고리즘**
>
> Windows나 RHEL 계열 Linux에서 FIPS 140 준수 모드가 켜져 있으면, 승인되지 않은 알고리즘 호출이 `CryptographicException`으로 실패한다. MD5는 대표적으로 금지되고, 관리 코드 구현 클래스(이름이 `Managed`로 끝나던 옛 타입들)도 금지 대상이 될 수 있다.
>
> 개발 머신에서는 잘 돌던 코드가 고객사 서버에서만 예외를 던진다면 이 경우를 의심해야 한다. 로그를 남길 때 쓰려고 넣어 둔 MD5 한 줄 때문에 전체 기능이 죽는 일이 실제로 생긴다.

> **📌 `Create()` 팩터리를 써야 하는 이유**
>
> `new SHA256Managed()`, `new AesManaged()` 같은 파생 타입 직접 생성은 폐기됐다(`SYSLIB0021`). 이유는 위와 같다 — 파생 타입을 직접 지정하면 플랫폼이 고른 최적 구현 대신 특정 구현을 강제하게 되고, FIPS 정책과도 충돌한다.
>
> 항상 기반 타입의 정적 `Create()`를 쓴다. `Aes.Create()`, `SHA256.Create()`, `RSA.Create()`. .NET 5 이후에는 아예 인스턴스가 필요 없는 정적 메서드(`SHA256.HashData`)가 더 나은 선택인 경우가 많다(44.3절).

### 성능 감각

암호 연산의 비용은 자릿수 단위로 갈린다. 아래는 상대적 비용의 감각을 잡기 위한 순위이며, 절대 수치는 하드웨어·OS·키 크기에 따라 크게 달라진다.

| 연산 | 상대 비용 | 비고 |
|---|---|---|
| 해시(SHA-256, 1KB) | 기준 | AES-NI/SHA 확장이 있으면 GB/s 단위 처리량 |
| HMAC-SHA256(1KB) | 해시의 약 2배 | 내부적으로 해시를 두 번 돈다 |
| AES-GCM 암호화(1KB) | 해시와 비슷한 자릿수 | 하드웨어 가속 시 |
| PBKDF2(수십만 회 반복) | **의도적으로 느림** | 44.4절. 느린 것이 기능이다 |
| RSA-2048 서명 생성 | 해시보다 수천 배 | 개인 키 연산이 공개 키 연산보다 훨씬 비싸다 |
| RSA-2048 서명 검증 | 서명 생성보다 훨씬 빠름 | 공개 지수가 작아서 |
| RSA-2048 키 쌍 생성 | 가장 비쌈 | 소수 탐색이 확률적이라 편차도 크다 |

> **💡 결정 순서 — 이 장을 다 읽고 나서도 이 순서를 따르라**
>
> 1. **직접 만들지 않아도 되는 길이 있는가?** TLS로 충분한가(43장), 플랫폼이 제공하는 보호로 충분한가(44.2절), 프레임워크의 기능(ASP.NET Core Identity, Data Protection)으로 충분한가.
> 2. **없다면 표준 조합을 그대로 쓴다.** 기밀성이 필요하면 AES-GCM, 비밀번호면 Argon2id 또는 충분한 반복 횟수의 PBKDF2, 서명이면 ECDSA P-256 또는 RSA-PSS.
> 3. **파라미터를 조립하지 않는다.** 모드·패딩·IV 처리 방식을 직접 고르기 시작했다면 이미 프로토콜을 설계하고 있는 것이고, 그건 이 책이 말리는 일이다.
> 4. **그래도 조립해야 한다면 리뷰를 받는다.** 암호 코드는 테스트가 통과해도 안전하지 않을 수 있다. 정상 동작과 안전성은 다른 문제다.

## 44.2 Windows 데이터 보호(DPAPI)

### 파일 단위 투명 암호화 — `File.Encrypt`

40.10절에서 파일·디렉터리 조작을 다루며 `File.Encrypt`를 짧게 봤다. OS에게 파일을 투명하게 암호화해 달라고 요청하는 메서드다.

```csharp
File.WriteAllText ("myfile.txt", "");
File.Encrypt ("myfile.txt");
File.AppendAllText ("myfile.txt", "sensitive data");
```

이 경우의 암호화는 **로그인한 사용자의 암호에서 파생된 키**를 쓴다. 애플리케이션 코드는 키를 만들지도, 저장하지도, 전달하지도 않는다. 파일을 여는 프로세스가 그 사용자로 실행 중이면 평문이 보이고, 아니면 안 보인다.

### 같은 키를 바이트 배열에 쓰기 — `ProtectedData`

이 암묵적으로 파생된 키를 바이트 배열 암호화에 그대로 쓸 수 있게 열어 준 것이 **Windows 데이터 보호 API(DPAPI)** 다. .NET에서는 `ProtectedData` 클래스가 노출한다. 정적 메서드 두 개가 전부인 단순한 타입이다.

```csharp
public static byte[] Protect
  (byte[] userData, byte[] optionalEntropy, DataProtectionScope scope);

public static byte[] Unprotect
  (byte[] encryptedData, byte[] optionalEntropy, DataProtectionScope scope);
```

사용은 이보다 더 단순할 수 없다.

```csharp
byte[] original = {1, 2, 3, 4, 5};
DataProtectionScope scope = DataProtectionScope.CurrentUser;

byte[] encrypted = ProtectedData.Protect   (original,  null, scope);
byte[] decrypted = ProtectedData.Unprotect (encrypted, null, scope);
// decrypted는 이제 {1, 2, 3, 4, 5}
```

**관리할 키가 0개다.** 이것이 DPAPI의 전부이자 존재 이유다. 키 생성·저장·백업·순환이라는 문제 전체가 사라진다. 대신 그 문제를 OS와 사용자 계정 체계에 떠넘긴 것이므로, 그 체계가 제공하는 만큼만 안전하다.

### `optionalEntropy` — 추가 비밀

`optionalEntropy`에 넣는 값은 키에 더해져 보안을 높인다. 같은 사용자로 실행되는 **다른 프로그램이 내 데이터를 복호화하지 못하게** 하는 용도로 쓴다.

```csharp
// 애플리케이션 고유의 고정 바이트열. 비밀이라기보다 "용도 구분자"에 가깝다.
static readonly byte[] AppEntropy =
    Encoding.UTF8.GetBytes ("Contoso.Invoicing.ConnectionString.v1");

byte[] blob = ProtectedData.Protect (secretBytes, AppEntropy,
                                     DataProtectionScope.CurrentUser);
```

> **⚠️ `optionalEntropy`는 비밀번호가 아니다**
>
> 엔트로피 값은 복호화할 때 똑같이 필요하므로 애플리케이션 어딘가에 있어야 한다. 어셈블리에 상수로 박아 두면 디컴파일러로 바로 읽힌다(44.6절). 그러니 **"공격자가 모를 것"에 기대면 안 된다.**
>
> 이 인자의 현실적인 가치는 보안 강화보다 **용도 분리**다. 같은 사용자 계정으로 도는 여러 모듈이 서로의 blob을 실수로 복호화하는 일을 막고, 버전이 바뀌었을 때 옛 blob을 명시적으로 실패시킨다.

### `DataProtectionScope` — 사용자 범위와 머신 범위

| 값 | 키의 출처 | 누가 복호화할 수 있나 | 전형적 용도 |
|---|---|---|---|
| `CurrentUser` | 로그인한 사용자의 자격 증명에서 파생 | **그 사용자만** | 데스크톱 앱의 사용자별 설정, 저장된 토큰 |
| `LocalMachine` | 머신 전역 키 | 그 머신의 **모든 사용자** | Windows 서비스, 여러 계정으로 도는 프로그램 |

`CurrentUser`로 암호화한 데이터는 **다른 사용자가 복호화할 수 없다.** 반대로 `LocalMachine` 키는 보호 수준이 낮지만, Windows 서비스처럼 여러 계정 아래에서 동작해야 하는 프로그램에서 쓸 수 있다.

> **⚠️ `LocalMachine`의 실제 의미**
>
> `LocalMachine` 범위는 "이 머신에 로그인할 수 있는 아무나 복호화할 수 있다"는 뜻이다. 게스트 계정, 다른 서비스 계정, 침해된 저권한 계정 전부 포함이다. **머신에 대한 물리적·전자적 접근이 제한된 환경에서만 의미가 있다.**
>
> 웹 서버에서 `LocalMachine`으로 DB 연결 문자열을 보호하는 구성을 자주 보는데, 서버에서 임의 코드를 실행할 수 있는 취약점이 하나만 있어도 그 보호는 무의미해진다. 그 경우 실제로 얻는 것은 "설정 파일을 눈으로 읽어서는 바로 알 수 없다" 정도다. 그것이 목표라면 괜찮지만, 그 이상을 기대하면 안 된다.

Windows 데이터 보호는 컴퓨터에 완전히 접근 가능한 공격자에 대해 **사용자 암호의 강도에 비례하는 중간 정도의 보안**을 제공한다. `LocalMachine` 범위에서는 물리적·전자적 접근이 제한된 상대에게만 효과가 있다.

### Windows 전용이라는 제약

> **⚠️ 다른 OS에서는 `PlatformNotSupportedException`**
>
> Windows 데이터 보호는 **Windows에서만 동작하며, 다른 운영체제에서는 `PlatformNotSupportedException`을 던진다.**
>
> 게다가 .NET(Core) 이후에는 `ProtectedData`가 기본 프레임워크에 없다. **`System.Security.Cryptography.ProtectedData` NuGet 패키지**를 참조해야 컴파일된다. 이 패키지는 모든 플랫폼에서 설치는 되지만, 호출은 Windows에서만 성공한다.
>
> 즉 크로스 플랫폼 코드에서는 반드시 분기해야 한다.
>
> ```csharp
> if (OperatingSystem.IsWindows())
>     blob = ProtectedData.Protect (data, entropy, DataProtectionScope.CurrentUser);
> else
>     blob = _dataProtector.Protect (data);   // 아래의 대안
> ```
>
> `OperatingSystem.IsWindows()`(※.NET 5)로 감싸면 플랫폼 호환성 분석기(CA1416) 경고도 함께 사라진다.

### 크로스 플랫폼 대안 — ASP.NET Core Data Protection

DPAPI의 자리를 크로스 플랫폼에서 메우는 것이 **ASP.NET Core Data Protection** 스택이다. 이름에 ASP.NET Core가 붙었지만 **콘솔 앱을 포함한 어떤 .NET 애플리케이션에서도 쓸 수 있다.**

```csharp
using Microsoft.AspNetCore.DataProtection;

// 키 링(key ring)을 디스크에 보관하는 독립 실행형 구성
var provider = DataProtectionProvider.Create (
                   new DirectoryInfo (@"/var/lib/myapp/keys"));

// "용도"별로 프로텍터를 만든다. 용도가 다르면 서로의 데이터를 못 푼다.
IDataProtector protector = provider.CreateProtector ("Contoso.Invoicing.v1");

string blob      = protector.Protect ("secret payload");
string roundTrip = protector.Unprotect (blob);
```

DPAPI와의 핵심 차이는 세 가지다.

| 항목 | `ProtectedData` (DPAPI) | ASP.NET Core Data Protection |
|---|---|---|
| 플랫폼 | Windows 전용 | 크로스 플랫폼 |
| 키 저장 | OS가 관리(보이지 않음) | **키 링을 직접 어딘가에 보관해야 한다** |
| 키 순환 | OS가 처리 | 자동 생성·순환(기본 수명 90일), 옛 키로 푼 것은 계속 풀린다 |
| 용도 분리 | `optionalEntropy` | `CreateProtector(purpose)` 문자열 |
| 여러 머신 공유 | 불가 | 키 링을 공유하면 가능 |

> **⚠️ 키 링을 어디에 두느냐가 전부다**
>
> Data Protection은 키 링을 자동으로 만들어 주지만, **그 키 링을 어디에 어떻게 보관할지는 여전히 개발자 책임**이다. 기본 동작은 환경에 따라 다르다 — Windows에서는 사용자 프로필 아래에 DPAPI로 감싸 저장하고, 컨테이너처럼 영속 저장소가 없는 환경에서는 **키가 프로세스 재시작마다 사라질 수 있다.**
>
> 컨테이너에서 이 구성을 방치하면 배포할 때마다 이전에 보호한 데이터가 전부 복호화 불가가 된다. 인증 쿠키가 무효화되어 전원 로그아웃되는 사고의 단골 원인이다. 반드시 `PersistKeysToFileSystem`(공유 볼륨)이나 Blob 저장소 확장으로 위치를 고정하고, 키 링 자체를 인증서나 KMS로 감싸라.

> **💡 무엇을 언제 쓸 것인가**
>
> - **단일 Windows 데스크톱 앱**이 사용자 자기 자신의 자격 증명을 저장한다 — `ProtectedData` + `CurrentUser`. 가장 단순하고 목적에 정확히 맞는다.
> - **크로스 플랫폼 앱**이거나 웹 애플리케이션이다 — ASP.NET Core Data Protection.
> - **여러 인스턴스·여러 머신**이 같은 데이터를 풀어야 한다 — 클라우드 KMS(Azure Key Vault, AWS KMS)로 올라간다(44.6절). Data Protection의 키 링을 공유하는 것도 방법이지만, 그 키 링을 다시 무엇으로 보호할지가 남는다.
> - **사용자 비밀번호에서 키를 만들어야 한다** — DPAPI가 아니라 PBKDF2다(44.4절).

> **📌 사용자가 비밀번호를 바꾸면?**
>
> DPAPI의 `CurrentUser` 키는 사용자 자격 증명에서 파생되지만, 사용자가 **정상적인 절차로** 비밀번호를 변경하면 Windows가 키 자료를 새 비밀번호로 다시 감싸므로 기존 데이터는 계속 풀린다.
>
> 문제가 되는 것은 **관리자가 비밀번호를 재설정**하는 경우다. 이때는 옛 비밀번호를 모르는 상태에서 강제로 바꾸는 것이라 파생 키 체인이 끊어질 수 있다. 40장에서 본 NTFS 투명 암호화가 "관리자가 암호를 재설정하면 데이터를 복구할 수 없다"고 경고하는 것과 같은 원리다. **DPAPI로 보호한 데이터는 백업 대상이 아니라 "언제든 다시 만들 수 있는 캐시"로 설계하는 편이 안전하다.**

## 44.3 해싱 — .NET의 해시 알고리즘

### 해시가 하는 일

해싱 알고리즘은 임의 크기의 바이트열을 **작고 고정된 길이의 해시코드로 압축**한다. 설계 목표는 원본 데이터의 **단 한 비트만 바뀌어도 해시코드가 크게 달라지는 것**이다. 이 성질 덕분에 파일을 비교하거나, 파일·데이터 스트림의 우발적(또는 악의적) 손상을 검출하는 데 쓸 수 있다.

해싱은 **단방향 암호화**로도 작동한다. 해시코드를 원본 데이터로 되돌리는 것은 어렵거나 불가능하기 때문이다. 이 성질이 비밀번호를 데이터베이스에 저장할 때 이상적인 이유다 — DB가 침해되더라도 공격자가 평문 비밀번호를 얻지 못하게 하려는 것이다. 인증할 때는 사용자가 입력한 값을 해싱해서 저장된 해시와 비교하면 된다.

다만 **일반 해시를 그대로 비밀번호에 쓰는 것은 오늘 기준으로 부족하다.** 왜 부족하고 무엇으로 대체해야 하는지는 44.4절 전체가 그 이야기다.

### 해시 ≠ 암호화 ≠ 인코딩

이 셋을 섞어 쓰는 것이 실무에서 가장 흔한 개념 오류다.

| | 인코딩 | 해싱 | 암호화 |
|---|---|---|---|
| 목적 | 표현 형식 변환 | 요약·지문 생성 | 기밀성 보호 |
| 키 | 없음 | 없음(MAC은 있음) | **있음** |
| 되돌리기 | **누구나 가능** | 불가능(설계상) | 키가 있으면 가능 |
| 예 | Base64, URL 인코딩, UTF-8 | SHA-256 | AES |
| 보안 가치 | **0** | 무결성 | 기밀성 |

> **⚠️ Base64는 암호화가 아니다**
>
> "인코딩해서 보냈으니 안전하다"는 코드 리뷰 코멘트를 실제로 본다. Base64는 바이너리를 텍스트로 옮기는 **표현 변환**일 뿐이고, 디코딩에는 아무 비밀도 필요 없다. 로그에 Base64로 찍힌 토큰은 평문으로 찍힌 토큰과 정확히 같은 수준으로 유출된 것이다.
>
> 반대 방향의 오해도 있다. **해시는 되돌릴 수 없으므로 "해시로 암호화했다"는 표현도 틀렸다.** 되돌릴 필요가 있는 데이터에는 해시를 쓸 수 없다.

### 해싱하는 법 — 인스턴스 방식

전통적인 방법은 `HashAlgorithm` 파생 클래스의 `ComputeHash`를 호출하는 것이다.

```csharp
byte[] hash;
using (Stream fs = File.OpenRead ("checkme.doc"))
    hash = SHA1.Create().ComputeHash (fs);

// SHA1 해시는 20바이트다
```

`ComputeHash`는 바이트 배열도 받는다.

```csharp
byte[] data = System.Text.Encoding.UTF8.GetBytes ("stRhong%pword");
byte[] hash = SHA256.Create().ComputeHash (data);
```

> **📌 해시 바이트를 문자열로 만들 때**
>
> `Encoding` 객체의 `GetBytes`는 문자열을 바이트 배열로, `GetString`은 그 반대로 바꾼다. 그러나 **`Encoding` 객체는 암호화되거나 해싱된 바이트 배열을 문자열로 바꿀 수 없다.** 뒤섞인 데이터는 대개 텍스트 인코딩 규칙을 위반하기 때문이다.
>
> 대신 `Convert.ToBase64String`과 `Convert.FromBase64String`을 쓴다. 임의의 바이트 배열과 XML·JSON에서 안전한 문자열 사이를 오간다.
>
> ```csharp
> string b64 = Convert.ToBase64String (hash);      // "n4bQgYhMfWWaL+q..."
> string hex = Convert.ToHexString (hash);         // "9F86D081884C7D65..."  ※.NET 5
> byte[] back = Convert.FromBase64String (b64);
> ```
>
> 16진수 표현이 필요하면 `Convert.ToHexString`/`FromHexString`(※.NET 5)이 있다. 직접 `BitConverter.ToString(hash).Replace("-","")`를 짜던 관용구는 이제 필요 없다. 인코딩 전반은 35.8절, `Convert` 클래스의 전모는 38.9절에 있다.

### 정적 `HashData` — 인스턴스 없이 해싱하기 ※.NET 5

.NET 5부터는 인스턴스를 만들 필요조차 없다.

```csharp
byte[] data = Encoding.UTF8.GetBytes ("hello");

byte[] hash = SHA256.HashData (data);                       // byte[] / ReadOnlySpan<byte>

// 미리 확보한 버퍼에 쓰기 — 할당 0
Span<byte> dest = stackalloc byte[32];
int written = SHA256.HashData (data, dest);

// 스트림 버전
await using FileStream fs = File.OpenRead ("big.iso");
byte[] fileHash = await SHA256.HashDataAsync (fs);
```

정적 메서드가 나은 이유는 문법적 간결함이 아니다.

1. **할당이 사라진다.** `SHA256.Create()`는 OS 핸들을 감싼 관리 객체를 만든다. 반복 호출 경로에서 이 할당과 `Dispose` 누락이 실제 비용이 된다(69장).
2. **`Dispose` 실수가 원천 차단된다.** 위 `SHA1.Create().ComputeHash(fs)` 코드는 원천의 예제지만 반환된 `SHA1` 객체를 폐기하지 않는다. 파이널라이저가 결국 정리하겠지만 그때까지 OS 리소스를 붙잡는다(34.2절).
3. **스레드 안전하다.** `HashAlgorithm` 인스턴스는 내부 상태를 갖기 때문에 여러 스레드가 공유하면 깨진다. 정적 메서드에는 그 문제가 없다.

> **💡 새 코드의 기본값은 정적 메서드다**
>
> 한 번에 다 넣을 수 있는 데이터라면 `SHA256.HashData`, 스트림이면 `SHA256.HashDataAsync`. 인스턴스를 만들어야 하는 경우는 **조각조각 들어오는 데이터를 누적**할 때뿐이고, 그때는 `HashAlgorithm`이 아니라 `IncrementalHash`가 더 낫다(아래).

### 조각을 누적해서 해싱하기 — `IncrementalHash`

데이터가 여러 번에 걸쳐 도착하는데 스트림으로 감싸기 어렵다면 `IncrementalHash`를 쓴다.

```csharp
using IncrementalHash hasher =
    IncrementalHash.CreateHash (HashAlgorithmName.SHA256);

foreach (ReadOnlyMemory<byte> chunk in chunks)
    hasher.AppendData (chunk.Span);

byte[] hash = hasher.GetHashAndReset();   // 상태를 비우고 다시 쓸 수 있다
```

`HashAlgorithm`의 `TransformBlock`/`TransformFinalBlock` 쌍이 하던 일을 훨씬 알아보기 쉽게 대체한다. `GetCurrentHash`는 상태를 유지한 채 현재까지의 해시를 뽑는다.

### .NET의 해시 알고리즘

`SHA1`과 `SHA256`은 .NET이 제공하는 `HashAlgorithm` 파생 타입 중 둘이다. 주요 알고리즘을 보안 강도 오름차순으로 정리하면 다음과 같다.

| 클래스 | 알고리즘 | 해시 길이(바이트) | 강도 |
|---|---|---|---|
| `MD5` | MD5 | 16 | 매우 나쁨 |
| `SHA1` | SHA-1 | 20 | 나쁨 |
| `SHA256` | SHA-2 | 32 | 좋음 |
| `SHA384` | SHA-2 | 48 | 좋음 |
| `SHA512` | SHA-2 | 64 | 좋음 |

다섯 알고리즘의 현재 구현은 대체로 비슷한 속도로 실행되지만, **`SHA256`은 예외적으로 2~3배 빠르다**(하드웨어와 OS에 따라 달라진다). 감을 잡기 위한 수치로, 2024년 무렵의 데스크톱·서버라면 어떤 알고리즘이든 최소 초당 500MB는 기대할 수 있다. 해시가 길수록 **충돌**(서로 다른 두 입력이 같은 해시를 내는 것) 가능성이 줄어든다.

> **⚠️ 비밀번호나 보안 민감 데이터에는 최소 SHA-256을 써라**
>
> MD5와 SHA-1은 이 목적으로는 안전하지 않다고 간주되며, **우발적 손상을 막는 용도로만** 적합하다. 의도적인 변조를 막는 데는 쓸 수 없다.

> **📌 SHA-3 ※.NET 8**
>
> .NET 8 이상은 최신 SHA-3 해싱을 `SHA3_256`, `SHA3_384`, `SHA3_512` 클래스로 지원한다. SHA-3 알고리즘은 앞의 알고리즘들보다 더 안전한 것으로 간주되며(그리고 더 느리다), **Windows Build 25324 이상 또는 OpenSSL 1.1.1 이상의 Linux**를 요구한다. OS 지원 여부는 이 클래스들의 정적 `IsSupported` 속성으로 확인한다.
>
> ```csharp
> if (SHA3_256.IsSupported)
>     hash = SHA3_256.HashData (data);
> else
>     hash = SHA256.HashData (data);
> ```
>
> 참고로 **SHA-3이 SHA-2보다 급하게 필요한 상황은 실무에 거의 없다.** SHA-2는 깨지지 않았고, SHA-3은 SHA-2가 깨질 경우를 대비한 구조적으로 다른 대안으로 표준화됐다. 지원 여부를 분기해야 하는 부담을 감수할 이유가 명확할 때만 쓴다.

### MD5와 SHA-1은 정확히 무엇이 깨졌나

"깨졌다"는 말이 뭉뚱그려져서 오해가 많다. 해시 함수에는 세 가지 저항성이 있고, 깨진 것은 그중 하나다.

| 저항성 | 공격자가 하려는 일 | MD5 | SHA-1 | SHA-256 |
|---|---|---|---|---|
| **원상 저항성**(preimage) | 해시값 h를 보고 h를 내는 입력 찾기 | 실용적 공격 없음 | 실용적 공격 없음 | 안전 |
| **제2원상 저항성**(second preimage) | 주어진 입력 m과 같은 해시를 내는 다른 m′ 찾기 | 실용적 공격 없음 | 실용적 공격 없음 | 안전 |
| **충돌 저항성**(collision) | 같은 해시를 내는 **아무** 두 입력 찾기 | **완전히 붕괴** | **붕괴** | 안전 |

즉 "MD5 해시를 보고 원본 비밀번호를 역산한다"는 것은 (사전 공격을 빼면) 아직도 어렵다. 붕괴한 것은 **공격자가 두 입력을 모두 자기가 만들 수 있는 상황**이다.

이 구분이 실무에서 중요한 이유는, 충돌 저항성이 필요한 자리와 필요 없는 자리가 다르기 때문이다.

- **서명·인증서**: 충돌 저항성이 필수다. 공격자가 "무해한 문서 A"와 "악성 문서 B"가 같은 해시를 내도록 만들 수 있으면, A에 받은 서명을 B에 옮겨 붙일 수 있다. 2012년 Flame 악성코드가 MD5 충돌로 위조 Microsoft 코드 서명 인증서를 만든 사건이 정확히 이 시나리오다. SHA-1도 2017년 실제 충돌 PDF 두 개(SHAttered)로 무너졌고, 2020년에는 접두사를 공격자가 고르는 더 강한 형태의 충돌까지 나왔다.
- **HMAC**: 충돌 저항성에 훨씬 덜 의존하는 구조다. 그래서 HMAC-SHA1은 HMAC 용도로는 여전히 즉각적인 위험으로 분류되지 않는다. 그렇다고 새로 쓸 이유는 없다.
- **비적대적 체크섬**: 디스크 오류나 전송 오류를 잡는 용도라면 MD5로도 목적은 달성된다. 공격자가 없기 때문이다.

> **⚠️ "아직 남아 있다"와 "써도 된다"는 다르다**
>
> MD5·SHA-1이 여전히 보이는 자리는 많다. Git의 객체 ID(SHA-1 기반이며, 2017년 이후 충돌 탐지 로직이 추가됐고 SHA-256으로의 이행이 진행 중이다), 오래된 파일 배포 사이트의 체크섬, 레거시 시스템과의 상호운용, 캐시 키 계산 같은 것들이다.
>
> 이 중 **캐시 키·파티셔닝처럼 보안과 무관한 용도**라면 MD5를 계속 써도 기능적 문제는 없다. 그러나 코드에 `MD5`라는 글자가 있으면 보안 스캐너가 잡고, FIPS 모드에서 예외가 나며, 인수인계받은 사람이 보안 용도로 오해한다. 비보안 용도라면 애초에 암호학적 해시가 아니라 `System.IO.Hashing` 패키지의 `XxHash64`/`Crc32` 같은 비암호학적 해시가 더 빠르고 의도도 분명하다.

> **⚠️ 해시 길이는 보안 강도의 두 배다**
>
> 생일 문제(birthday problem) 때문에, n비트 해시의 **충돌 저항 강도는 n비트가 아니라 n/2비트**다. SHA-256의 충돌 저항은 128비트 수준이고, SHA-1의 160비트 해시는 이론상 80비트 — 이것이 SHA-1이 현실적인 계산 자원으로 무너진 이유다.
>
> "해시가 256비트니까 256비트 보안"이라는 계산은 원상 저항성에만 해당한다.

### 키가 있는 해시 — HMAC

일반 해시는 **무결성만** 준다. 데이터와 해시를 함께 전송하는 상황을 생각해 보자. 공격자가 데이터를 바꾸면 해시도 같이 다시 계산해서 붙이면 그만이다. 해시 계산에 비밀이 없으니 아무나 할 수 있다.

**메시지 인증 코드(MAC)** 는 여기에 키를 넣어 "이 해시를 계산할 수 있는 사람은 키를 가진 쪽뿐"이라는 성질을 추가한다. 표준 구성이 HMAC이고, .NET은 `HMACSHA256`, `HMACSHA384`, `HMACSHA512`, `HMACSHA1`, `HMACMD5`를 제공한다.

```csharp
byte[] key     = RandomNumberGenerator.GetBytes (32);     // 44.8절
byte[] message = Encoding.UTF8.GetBytes ("transfer 100 to alice");

byte[] tag = HMACSHA256.HashData (key, message);          // ※.NET 6 정적 메서드

// 검증하는 쪽
byte[] expected = HMACSHA256.HashData (key, message);
bool ok = CryptographicOperations.FixedTimeEquals (tag, expected);
```

| | 해시 | HMAC | 디지털 서명 |
|---|---|---|---|
| 키 | 없음 | 대칭(공유 비밀) | 비대칭(개인/공개) |
| 무결성 | 제공 | 제공 | 제공 |
| 인증 | **없음** | 제공(키를 아는 쪽) | 제공(개인 키 소유자) |
| 부인 방지 | 없음 | **없음** — 양쪽이 같은 키를 가지므로 | **제공** |
| 속도 | 가장 빠름 | 빠름 | 느림 |
| 크기 | 해시 길이 | 해시 길이 | 키 크기에 비례(RSA-2048이면 256바이트) |

> **⚠️ HMAC은 부인 방지를 주지 않는다**
>
> HMAC 태그를 만들 수 있는 사람과 검증할 수 있는 사람이 **동일한 키를 가진다.** 따라서 "A가 보낸 게 맞다"고 제3자에게 증명할 수 없다 — B도 똑같은 태그를 만들 수 있기 때문이다. 감사 로그나 계약처럼 "나중에 부인하지 못하게" 해야 하는 자리에는 서명(44.7절)이 필요하다.

> **📌 왜 `key + message`를 그냥 해싱하면 안 되나**
>
> `SHA256.HashData(key.Concat(message))` 같은 구성을 직접 만드는 코드를 종종 본다. SHA-2 계열은 머클-담고르(Merkle–Damgård) 구조라서 **길이 확장 공격(length extension attack)** 에 취약하다. 공격자는 키를 모르는 채로 `H(key || message)`만 보고 `H(key || message || padding || 임의데이터)`를 계산해 낼 수 있다.
>
> HMAC은 해시를 두 번 중첩하는 구조로 정확히 이 문제를 막는다. **키가 들어가는 해시는 반드시 HMAC 클래스를 쓴다.** 이것이 이 장이 반복하는 원칙 — 조립하지 말고 이름 붙은 표준 구성을 쓴다 — 의 가장 작은 사례다.

> **💡 `GetHashCode`와 혼동하지 마라**
>
> `object.GetHashCode`(25.4절)는 해시 테이블 버킷 분산이 목적인 32비트 값이고, 암호학적 성질이 전혀 없다. 같은 프로세스 안에서만 의미가 있으며, .NET에서 문자열 해시는 실행마다 무작위화될 수도 있다.
>
> `GetHashCode` 결과를 DB에 저장하거나 무결성 검증에 쓰는 코드는 두 겹으로 틀렸다. 지속되는 지문이 필요하면 `SHA256.HashData`다.

## 44.4 비밀번호 해싱 — `Rfc2898DeriveBytes`, 솔트, 반복 횟수

### 일반 해시가 비밀번호에 부족한 이유

44.3절에서 본 것처럼, 긴 SHA 알고리즘은 **강력한 비밀번호 정책으로 사전 공격(dictionary attack)을 완화한다면** 비밀번호 해싱의 기초로 쓸 수 있다. 사전 공격은 공격자가 사전의 모든 단어를 해싱해서 비밀번호 조회 테이블을 만드는 전략이다.

문제는 그 "완화"가 오늘의 계산 자원 앞에서 잘 작동하지 않는다는 데 있다.

암호학적 해시의 설계 목표는 **빠른 것**이다. 초당 수 GB를 처리하는 것이 미덕이다. 그런데 비밀번호 검증에서는 그 미덕이 그대로 약점이 된다. 정직한 서버는 로그인 한 번에 해시를 한 번 계산하지만, DB를 훔친 공격자는 후보 비밀번호를 **병렬로 무한히** 시도한다.

SHA-256은 GPU에서 대량 병렬화가 매우 잘 되는 연산이다. 정확한 처리량은 하드웨어 세대마다 다르지만, 자릿수 감각을 위한 예시로 말하면 **고성능 GPU 한 장이 초당 수십억 회 규모의 SHA-256 해시를 계산**한다는 것이 널리 알려진 수준이다. 전용 하드웨어를 여러 장 묶으면 그보다 훨씬 올라간다.

이 숫자 앞에서 "8자 이상, 대소문자·숫자·특수문자"라는 정책은 방어선이 되지 못한다. 사람이 만드는 비밀번호는 실제 엔트로피가 낮고, 규칙을 강제할수록 오히려 `Password1!` 같은 예측 가능한 패턴으로 수렴한다.

> **⚠️ 비밀번호 해싱의 목표는 "느리게 만드는 것"이다**
>
> 일반 해싱과 비밀번호 해싱은 목표가 정반대다. 전자는 빠를수록 좋고, **후자는 (사용자가 견딜 수 있는 한도 안에서) 느릴수록 좋다.**
>
> 그래서 `SHA256.HashData(password)`는 비밀번호 해싱이 아니다. 문법적으로는 해시를 만들지만, 방어라는 목적을 달성하지 못한다.

### 솔트 — 사용자별로 다른 재료

비밀번호를 해싱할 때의 표준 기법은 **솔트(salt)** 를 넣는 것이다. 솔트는 처음에 난수 생성기로 얻은 긴 바이트열이고, 해싱 전에 각 비밀번호와 결합한다. 이것이 공격자를 두 가지 방식으로 좌절시킨다.

- 공격자는 **솔트 바이트도 알아야 한다.**
- **레인보우 테이블**(비밀번호와 그 해시코드를 미리 계산해 공개해 둔 데이터베이스)을 쓸 수 없다. 다만 충분한 계산력이 있으면 사전 공격은 여전히 가능하다.

솔트에 관해 실무에서 가장 자주 나오는 질문에 먼저 답하자.

| 질문 | 답 |
|---|---|
| 솔트를 비밀로 유지해야 하나? | **아니다.** 해시와 나란히 저장한다 |
| 사용자마다 달라야 하나? | **그렇다.** 이것이 핵심이다 |
| 애플리케이션 전역 솔트 하나면 안 되나? | 안 된다. 레인보우 테이블은 막지만, **같은 비밀번호를 쓴 사용자가 같은 해시를 갖는다**는 사실이 노출된다 |
| 길이는? | 16바이트(128비트) 이상이면 충분하다 |
| 무엇으로 생성하나? | `RandomNumberGenerator`(44.8절). `Random`은 절대 안 된다 |
| 비밀번호를 바꾸면? | 새 솔트를 뽑는다 |

> **📌 솔트를 비밀로 하려는 시도가 만드는 문제**
>
> "솔트를 별도 서버에 숨기면 더 안전하지 않나"라는 아이디어는 자연스럽지만, 솔트는 그 목적으로 설계되지 않았다. 솔트의 역할은 **미리 계산된 테이블을 무력화하고 사용자마다 공격을 개별화**하는 것이지 비밀 유지가 아니다.
>
> 비밀을 추가하고 싶다면 그건 솔트가 아니라 **페퍼(pepper)** 라고 부르는 별개의 개념이다. 페퍼는 DB가 아니라 애플리케이션 설정·KMS에 두는 전역 비밀값으로, 해시 계산에 HMAC 형태로 섞는다. DB만 유출됐을 때 방어선을 하나 더 두는 효과가 있다. 다만 페퍼가 유출되거나 순환이 필요해지면 전체 재해싱이 필요하므로, **먼저 솔트와 반복 횟수를 제대로 하고 나서 고려할 선택지**다.

### 스트레칭 — 반복 횟수

보안을 더 강화하려면 비밀번호 해시를 **스트레칭(stretching)** 한다 — 계산량이 더 많은 바이트열을 얻기 위해 반복해서 다시 해싱하는 것이다. 100번 다시 해싱하면, 원래 한 달이 걸릴 사전 공격이 8년으로 늘어난다.

`KeyDerivation`, `Rfc2898DeriveBytes`, `PasswordDeriveBytes` 클래스가 정확히 이런 종류의 스트레칭을 수행하면서 편리한 솔팅도 함께 제공한다. 이 중 `KeyDerivation.Pbkdf2`가 최선의 해싱을 제공한다.

```csharp
byte[] encrypted = KeyDerivation.Pbkdf2 (
    password: "stRhong%pword",
    salt: Encoding.UTF8.GetBytes ("j78Y#p)/saREN!y3@"),
    prf: KeyDerivationPrf.HMACSHA512,
    iterationCount: 100,
    numBytesRequested: 64);
```

> **📌 `KeyDerivation.Pbkdf2`는 NuGet 패키지가 필요하다**
>
> `Microsoft.AspNetCore.Cryptography.KeyDerivation` 패키지를 참조해야 한다. 네임스페이스에 ASP.NET Core가 들어 있지만 **어떤 .NET 애플리케이션에서도 쓸 수 있다.**

> **⚠️ 위 예제의 두 값은 오늘 기준으로 그대로 쓰면 안 된다**
>
> 원천의 예제 코드에는 설명용으로 단순화된 부분이 두 군데 있다. 실제 코드로 옮기기 전에 반드시 고쳐야 한다.
>
> 1. **`iterationCount: 100`은 턱없이 낮다.** 스트레칭의 효과는 반복 횟수에 비례하는데, 100회는 현대 하드웨어에서 사실상 무의미하다. OWASP는 PBKDF2-HMAC-SHA256에 대해 수십만 회 수준(2023년 권고치는 600,000회)을 제시한다. 반복 횟수는 **시간이 지날수록 올려야 하는 값**이고, 오늘의 적정값은 "우리 서버에서 로그인 한 건당 허용 가능한 지연(보통 50~250ms) 안에 들어오는 최대치"를 직접 측정해서 정한다.
> 2. **솔트가 고정 문자열이다.** 예제이므로 리터럴을 썼지만, 실제로는 **사용자마다 난수로 생성**해야 한다.

### `Rfc2898DeriveBytes` — PBKDF2 표준 구현

`Rfc2898DeriveBytes`는 RFC 2898이 정의한 PBKDF2(Password-Based Key Derivation Function 2)의 .NET 구현이다. 추가 패키지 없이 BCL에 들어 있다. .NET 6부터는 정적 메서드가 생겨서 인스턴스를 만들 필요가 없다.

```csharp
using System.Security.Cryptography;

const int SaltSize      = 16;      // 128비트
const int HashSize      = 32;      // 256비트
const int Iterations    = 600_000; // 측정해서 정한 값. 시간이 지나면 올린다
static readonly HashAlgorithmName Prf = HashAlgorithmName.SHA256;

static string HashPassword (string password)
{
    byte[] salt = RandomNumberGenerator.GetBytes (SaltSize);

    byte[] hash = Rfc2898DeriveBytes.Pbkdf2 (      // ※.NET 6
        password:        password,
        salt:            salt,
        iterations:      Iterations,
        hashAlgorithm:   Prf,
        outputLength:    HashSize);

    // 알고리즘·파라미터·솔트를 해시와 함께 저장한다 (아래 설명)
    return $"pbkdf2-sha256${Iterations}${Convert.ToBase64String (salt)}$" +
           Convert.ToBase64String (hash);
}
```

파라미터 하나하나가 하는 일은 다음과 같다.

| 파라미터 | 역할 | 정하는 기준 |
|---|---|---|
| `password` | 입력 비밀번호 | 사용자 입력 |
| `salt` | 사용자별 고유 재료 | 16바이트 이상, `RandomNumberGenerator`로 매번 새로 |
| `iterations` | 반복 횟수 = 비용 | 허용 지연 안에서 최대. 매년 재검토 |
| `hashAlgorithm` | 내부 PRF | SHA-256 또는 SHA-512 |
| `outputLength` | 출력 바이트 수 | 해시 출력 길이(SHA-256이면 32)면 충분 |

> **⚠️ `outputLength`를 무작정 늘리지 마라**
>
> PBKDF2는 요청한 길이가 내부 해시 출력보다 길면 **블록을 여러 번 반복 계산**해서 이어 붙인다. SHA-256(32바이트) PRF로 64바이트를 요청하면 전체 반복을 두 번 도는 셈이라 정직한 서버의 비용만 두 배가 된다.
>
> 그런데 공격자는 첫 32바이트만 맞춰 보면 되므로 **공격 비용은 늘어나지 않는다.** 방어자만 두 배 손해다. 출력 길이는 PRF의 해시 길이와 맞추는 것이 원칙이다.

> **⚠️ `Rfc2898DeriveBytes` 생성자의 함정**
>
> `new Rfc2898DeriveBytes(password, salt, iterations)`처럼 **해시 알고리즘을 지정하지 않는 생성자는 폐기됐다**(`SYSLIB0041`). 이 생성자의 기본 PRF가 **SHA-1**이기 때문이다. 동작은 하지만 오늘 기준으로 권장되는 구성이 아니다.
>
> 인스턴스가 꼭 필요하다면 `HashAlgorithmName`을 받는 생성자를 쓰고, 인스턴스는 `IDisposable`이므로 `using`으로 감싼다.
>
> ```csharp
> using var kdf = new Rfc2898DeriveBytes (
>     password, salt, Iterations, HashAlgorithmName.SHA256);
> byte[] hash = kdf.GetBytes (HashSize);
> ```
>
> 그리고 `PasswordDeriveBytes`는 PBKDF2가 아니라 그 이전 세대인 PBKDF1 기반이다. **새 코드에서 쓸 이유가 없다.**

### 저장 형식 — 파라미터를 해시와 함께 남겨라

비밀번호 해시를 저장할 때 해시 바이트만 저장하면 나중에 반드시 곤란해진다. 반복 횟수를 올리거나 알고리즘을 바꾸는 순간, 기존 레코드를 어떤 파라미터로 만들었는지 알 수 없기 때문이다.

그래서 실무의 표준은 **자기 기술적(self-describing) 형식**이다.

```text
pbkdf2-sha256$600000$RiWZbnKfE3aXbVoV2v0Q1A==$Kx5g...(base64)...

  └─ 알고리즘   └─ 반복  └─ 솔트(base64)      └─ 해시(base64)
```

이 형식이면 검증 코드가 레코드를 읽어 그 안에 적힌 파라미터로 재계산하면 되고, 알고리즘 이행도 레코드 단위로 점진적으로 할 수 있다.

```text
┌──────────────────────────────────────────────────────────────────┐
│  비밀번호 등록                                                   │
│                                                                  │
│   비밀번호 ──┐                                                   │
│              ├──▶ PBKDF2(반복 N회) ──▶ 해시 ──┐                  │
│   솔트(난수)─┘                                 │                 │
│              └─────────────────────────────────┼──▶ DB에 저장    │
│   알고리즘·반복 횟수 ───────────────────────────┘  (한 줄로)     │
├──────────────────────────────────────────────────────────────────┤
│  로그인 검증                                                     │
│                                                                  │
│   DB 레코드 파싱 ──▶ 알고리즘·반복·솔트 획득                     │
│                          │                                       │
│   입력 비밀번호 ─────────┴──▶ PBKDF2 ──▶ 후보 해시               │
│                                              │                   │
│                          FixedTimeEquals(후보, 저장된 해시)      │
│                                              │                   │
│                          일치 ──▶ 파라미터가 낡았으면 재해싱     │
└──────────────────────────────────────────────────────────────────┘
```

### 검증 — 타이밍 공격을 피하는 비교

검증 코드에서 가장 자주 나오는 실수가 해시 비교다.

```csharp
static bool Verify (string password, string stored)
{
    string[] parts = stored.Split ('$');
    int    iterations = int.Parse (parts[1]);
    byte[] salt       = Convert.FromBase64String (parts[2]);
    byte[] expected   = Convert.FromBase64String (parts[3]);

    byte[] actual = Rfc2898DeriveBytes.Pbkdf2 (
        password, salt, iterations, HashAlgorithmName.SHA256, expected.Length);

    // 반드시 상수 시간 비교
    return CryptographicOperations.FixedTimeEquals (actual, expected);
}
```

`CryptographicOperations.FixedTimeEquals`는 두 스팬의 **모든 바이트를 항상 끝까지** 비교하고 결과를 누적한다. 첫 번째 다른 바이트에서 빠져나오지 않는다.

> **⚠️ `SequenceEqual`과 `==`가 왜 위험한가**
>
> `byte[]`에 `==`를 쓰면 **참조 비교**가 되어 항상 `false`다. 이건 기능 버그라 테스트에서 잡힌다.
>
> 진짜 위험한 것은 `actual.SequenceEqual(expected)`다. 기능적으로는 맞지만, **첫 번째 불일치 바이트에서 즉시 반환**한다. 공격자가 후보 값을 조금씩 바꿔 가며 응답 시간을 측정하면, 앞에서 몇 바이트가 맞았는지를 통계적으로 알아낼 수 있다. 바이트를 하나씩 확정해 가면 전수 탐색이 지수에서 선형으로 떨어진다.
>
> 네트워크 지터 때문에 원격에서는 어렵다는 반론이 있지만, 충분한 반복 측정으로 실증된 공격이 존재한다. **비밀과 비교하는 모든 자리에서 `FixedTimeEquals`를 쓴다.** 비밀번호 해시, API 키, HMAC 태그, 서명 전부 해당한다.
>
> 참고로 `FixedTimeEquals`는 **길이가 다르면 즉시 `false`** 를 반환한다. 길이는 비밀이 아니라는 전제이며, 해시는 어차피 고정 길이라 문제가 되지 않는다.

### 반복 횟수를 올려야 할 때 — 점진적 재해싱

반복 횟수는 하드웨어가 빨라질수록 올려야 한다. 그런데 저장된 것은 해시뿐이라 **일괄 재계산이 불가능하다** — 평문 비밀번호가 없기 때문이다.

유일한 방법은 **사용자가 로그인에 성공하는 순간** 그 평문으로 새 파라미터의 해시를 만들어 덮어쓰는 것이다.

```csharp
if (Verify (password, stored))
{
    if (NeedsUpgrade (stored))                 // 저장된 반복 횟수 < 현재 정책
        SavePasswordHash (userId, HashPassword (password));

    return LoginResult.Success;
}
```

> **💡 이행 계획을 처음부터 형식에 넣어라**
>
> 위의 자기 기술적 형식을 처음부터 쓰면, 나중에 PBKDF2에서 Argon2id로 옮길 때도 코드 한 군데만 바꾸면 된다. 접두사가 `pbkdf2-sha256`이면 옛 검증 경로로, `argon2id`면 새 경로로 보내고, 로그인 성공 시 새 형식으로 승격한다.
>
> 반대로 해시 바이트만 저장해 둔 시스템은 이행 시점에 **전원 비밀번호 재설정** 외에 선택지가 없다. 그 이메일을 보내는 날의 고객 문의량을 생각하면, 지금 형식 한 줄을 설계하는 편이 싸다.

### PBKDF2보다 나은 것 — 메모리 하드 함수

PBKDF2는 **연산량만** 늘린다. 그런데 GPU와 ASIC은 정확히 연산량을 병렬화하는 데 특화된 하드웨어다. 즉 방어자는 CPU 한 코어로 600,000회를 돌지만 공격자는 수천 개 연산 유닛으로 동시에 돈다. 비용 비대칭이 방어자에게 불리하다.

**메모리 하드(memory-hard)** 함수는 이 비대칭을 뒤집는다. 계산 과정에서 큰 메모리 영역을 무작위로 접근하도록 설계되어, 병렬화하려면 코어 수만큼 메모리도 필요하게 만든다. 메모리는 실리콘 면적을 많이 잡아먹으므로 대량 병렬화 비용이 급격히 올라간다.

| 알고리즘 | 특성 | .NET 내장 | 비고 |
|---|---|---|---|
| PBKDF2 | 연산량만 | **있음** (`Rfc2898DeriveBytes`) | FIPS 승인. 규제 환경에서 자주 강제된다 |
| bcrypt | 약한 메모리 하드 | 없음 | 1999년 설계. 오래 검증됐다 |
| scrypt | 메모리 하드 | 없음 | 메모리·시간 파라미터 조절 |
| **Argon2id** | 메모리 하드 | 없음 | 2015년 비밀번호 해싱 경연 우승. 현재의 권장 기본값 |

.NET BCL에는 Argon2·bcrypt·scrypt 구현이 없다. 접근 방법은 세 가지다.

1. **NuGet 라이브러리를 쓴다.** Argon2는 `Konscious.Security.Cryptography.Argon2`나 libsodium 바인딩인 `NSec.Cryptography`, bcrypt는 `BCrypt.Net-Next`가 널리 쓰인다.
2. **ASP.NET Core Identity를 쓴다.** `PasswordHasher<TUser>`가 솔트 생성·형식·검증·반복 횟수 이행을 전부 처리한다. 내부 구현은 PBKDF2 기반이고, .NET 버전이 올라가면서 기본 반복 횟수도 상향돼 왔다.
3. **PBKDF2에 충분한 반복 횟수를 쓴다.** FIPS 승인 알고리즘만 허용되는 환경이라면 이것이 유일한 선택지다.

> **💡 대부분의 애플리케이션에는 2번이 정답이다**
>
> 비밀번호 저장은 이미 여러 번 잘 풀린 문제다. ASP.NET Core를 쓰고 있다면 `PasswordHasher<TUser>`를 쓰고 직접 구현하지 마라. 형식 설계·이행 경로·상수 시간 비교가 전부 들어 있다.
>
> 직접 구현이 필요한 상황(다른 스택과 형식을 맞춰야 한다든지)이라면 Argon2id를 쓰되, **파라미터는 반드시 배포 대상 하드웨어에서 측정해서 정한다.** 메모리 파라미터를 크게 잡으면 로그인이 몰릴 때 서버 메모리가 먼저 터진다. 이건 실제로 일어나는 사고다.

> **⚠️ bcrypt의 72바이트 절단**
>
> bcrypt는 입력의 **앞 72바이트만** 사용한다. 그보다 긴 비밀번호는 조용히 잘린다. 긴 패스프레이즈를 장려하는 정책과 정면으로 충돌하고, "72자 이후는 아무 값이나 넣어도 로그인된다"는 황당한 동작이 된다.
>
> 회피책으로 비밀번호를 먼저 SHA-256으로 해싱한 뒤 bcrypt에 넣는 구성이 돌아다니는데, 이때 해시 결과를 Base64가 아니라 **원시 바이트로 넘기면 널 바이트 때문에 또 잘리는** 별개의 함정이 있다. 이런 조합을 직접 만들어야 하는 상황 자체가 신호다 — Argon2id로 가는 편이 낫다.

## 44.5 대칭 암호화 — 메모리 내 암호화, 스트림 체이닝

### 대칭 암호와 .NET의 알고리즘

대칭 암호화는 **암호화와 복호화에 같은 키**를 쓴다. .NET BCL은 네 가지 대칭 알고리즘을 제공하는데, 그중 Rijndael이 최상급이고 나머지는 주로 옛 애플리케이션과의 호환을 위한 것이다. Rijndael은 빠르고 안전하며 두 가지 구현이 있다.

- `Rijndael` 클래스
- `Aes` 클래스

둘은 거의 동일하되, `Aes`는 **블록 크기를 바꿔 암호를 약화시킬 수 없다**는 점이 다르다. CLR 보안 팀은 `Aes`를 권장한다.

| 클래스 | 알고리즘 | 상태 |
|---|---|---|
| `Aes` | AES(Rijndael, 블록 128비트 고정) | **권장** |
| `Rijndael` | Rijndael(블록 크기 변경 가능) | 폐기(`SYSLIB0022`) |
| `TripleDES` | 3DES | 레거시 호환 전용 |
| `DES` | DES | 안전하지 않음. 56비트 키 |
| `RC2` | RC2 | 안전하지 않음 |

> **⚠️ `Rijndael`은 폐기됐다**
>
> `Rijndael`과 `RijndaelManaged`는 `SYSLIB0022`로 폐기됐다. 이유는 위와 같다 — 128비트가 아닌 블록 크기를 고를 수 있어서 AES 표준과 어긋나는 구성을 만들 수 있기 때문이다. 그렇게 만든 데이터는 다른 언어·플랫폼의 AES 구현으로 풀 수 없다.
>
> 레거시 코드에서 `RijndaelManaged`를 발견했다면, **블록 크기가 128인지 먼저 확인**하라. 128이면 `Aes`로 바꿔도 데이터 호환성이 유지된다. 아니라면 데이터 이행 계획이 필요하다.

### 키와 IV

Rijndael과 Aes는 **16, 24, 32바이트 길이의 대칭 키**를 허용하며 전부 현재 안전하다고 간주된다. 다음은 16바이트 키로 바이트열을 파일에 쓰면서 암호화하는 방법이다.

```csharp
// 키는 코드에 박지 않는다 — 44.6절. 여기서는 키 저장소에서 가져왔다고 가정한다.
byte[] key = keyStore.GetDataKey();          // 16 / 24 / 32 바이트
byte[] iv  = RandomNumberGenerator.GetBytes (16);   // 메시지마다 새로 생성
byte[] data = { 1, 2, 3, 4, 5 };             // 암호화할 대상

using (SymmetricAlgorithm algorithm = Aes.Create())
using (ICryptoTransform encryptor = algorithm.CreateEncryptor (key, iv))
using (Stream f = File.Create ("encrypted.bin"))
{
    f.Write (iv, 0, iv.Length);              // IV를 평문으로 먼저 기록한다

    using Stream c = new CryptoStream (f, encryptor, CryptoStreamMode.Write);
    c.Write (data, 0, data.Length);
}
```

복호화는 이렇게 한다.

```csharp
byte[] key = keyStore.GetDataKey();
byte[] iv  = new byte[16];

using (Stream f = File.OpenRead ("encrypted.bin"))
{
    f.ReadExactly (iv);                      // ※.NET 7. 앞의 16바이트가 IV
    using SymmetricAlgorithm algorithm = Aes.Create();
    using ICryptoTransform decryptor = algorithm.CreateDecryptor (key, iv);
    using Stream c = new CryptoStream (f, decryptor, CryptoStreamMode.Read);

    for (int b; (b = c.ReadByte()) > -1;)
        Console.Write (b + " ");             // 1 2 3 4 5
}
```

키가 틀리면 `CryptoStream`이 `CryptographicException`을 던진다. **키가 맞는지 확인하는 유일한 방법은 이 예외를 잡는 것이다.** 이 사실 자체가 대칭 암호화만으로는 부족하다는 첫 번째 신호다(뒤에서 이어진다).

키 외에 **IV(Initialization Vector, 초기화 벡터)** 도 만들었다. 이 16바이트 시퀀스는 키처럼 암호의 일부를 이루지만 **비밀로 취급되지 않는다.** 암호화된 메시지를 전송한다면 IV를 평문으로(예컨대 메시지 헤더에) 보내고 **메시지마다 바꾼다.** 그러면 평문이 서로 비슷하거나 동일하더라도 각 암호문이 이전 것과 전혀 달라 보이게 된다.

| | 키 | IV / nonce |
|---|---|---|
| 비밀인가 | **그렇다** | 아니다 |
| 저장·전송 | 안전한 곳에만 | 암호문과 나란히 평문으로 |
| 재사용 | 여러 메시지에 재사용 가능 | **메시지마다 새로 만든다** |
| 길이(AES) | 16 / 24 / 32바이트 | 16바이트(CBC), 12바이트(GCM 권장) |
| 생성 방법 | 키 관리 체계(44.6절) | `RandomNumberGenerator` |

> **⚠️ IV를 고정하거나 키와 같게 두지 마라**
>
> 원천에는 "IV의 보호가 필요 없거나 원하지 않으면 키와 IV에 같은 16바이트 값을 써서 무력화할 수 있다"는 서술이 있고, 이어서 **여러 메시지를 같은 IV로 보내면 암호가 약해지고 해독이 가능해질 수도 있다**고 경고한다. 오늘의 실무 기준으로 말하면, 그 "무력화"는 선택지가 아니다.
>
> CBC 모드에서 같은 키·같은 IV로 두 메시지를 암호화하면, **평문의 공통 접두사만큼 암호문도 동일하게 나온다.** 공격자는 두 메시지가 같은 값으로 시작한다는 사실을 알게 된다. 로그인 상태·계좌 종류·문서 템플릿처럼 값의 종류가 몇 개 안 되는 필드라면 이것만으로 내용이 사실상 드러난다.
>
> **IV 생성 비용은 16바이트 난수 한 번이다.** 아낄 이유가 없다.

> **📌 키와 IV를 지정하지 않으면**
>
> `Aes.Create()`로 만든 객체에 키와 IV를 지정하지 않으면 **암호학적으로 강한 난수 값이 자동으로 생성된다.** `Key`와 `IV` 속성으로 그 값을 읽을 수 있다.
>
> 즉 "IV를 어떻게 만들지"를 고민할 필요조차 없는 경로가 있다. 객체를 만들고 `algorithm.IV`를 읽어 암호문 앞에 붙이면 된다.

### 역할 분담 — 수학자와 배관공

암호 작업은 여러 클래스로 나뉘어 있다. **`Aes`는 수학자다** — 암호 알고리즘을 적용하고 암호화·복호화 변환기(transform)를 만든다. **`CryptoStream`은 배관공이다** — 스트림 배관을 처리한다. `Aes`를 다른 대칭 알고리즘으로 바꿔도 `CryptoStream`은 그대로 쓸 수 있다.

`CryptoStream`은 **양방향**이다. `CryptoStreamMode.Read`를 고르는지 `Write`를 고르는지에 따라 스트림에서 읽거나 쓴다. 암호화기와 복호화기 둘 다 읽기·쓰기를 알기 때문에 조합이 네 가지가 되고, 이 선택 때문에 한동안 빈 화면을 들여다보게 될 수 있다. **읽기를 "당기기(pull)", 쓰기를 "밀기(push)"로 모델링하면 도움이 된다.** 헷갈리면 암호화에는 `Write`, 복호화에는 `Read`로 시작하라. 대개 이쪽이 가장 자연스럽다.

| 조합 | 데이터 흐름 | 전형적 용도 |
|---|---|---|
| 암호화기 + `Write` | 평문을 밀어 넣으면 암호문이 하위 스트림으로 | 파일에 암호화해 저장 |
| 복호화기 + `Read` | 하위 스트림의 암호문을 당기면 평문이 나온다 | 암호화된 파일 읽기 |
| 암호화기 + `Read` | 하위 스트림의 평문을 당기면 암호문이 나온다 | 암호화하면서 전송(소스가 스트림일 때) |
| 복호화기 + `Write` | 암호문을 밀어 넣으면 평문이 하위 스트림으로 | 받으면서 복호화해 저장 |

### 메모리 안에서 암호화하기

.NET 6부터는 `EncryptCbc`와 `DecryptCbc` 메서드로 바이트 배열 암호화·복호화 과정을 단축할 수 있다.

```csharp
public static byte[] Encrypt (byte[] data, byte[] key, byte[] iv)
{
    using Aes algorithm = Aes.Create();
    algorithm.Key = key;
    return algorithm.EncryptCbc (data, iv);
}

public static byte[] Decrypt (byte[] data, byte[] key, byte[] iv)
{
    using Aes algorithm = Aes.Create();
    algorithm.Key = key;
    return algorithm.DecryptCbc (data, iv);
}
```

모든 .NET 버전에서 동작하는 등가 코드는 다음과 같다.

```csharp
public static byte[] Encrypt (byte[] data, byte[] key, byte[] iv)
{
    using (Aes algorithm = Aes.Create())
    using (ICryptoTransform encryptor = algorithm.CreateEncryptor (key, iv))
        return Crypt (data, encryptor);
}

public static byte[] Decrypt (byte[] data, byte[] key, byte[] iv)
{
    using (Aes algorithm = Aes.Create())
    using (ICryptoTransform decryptor = algorithm.CreateDecryptor (key, iv))
        return Crypt (data, decryptor);
}

static byte[] Crypt (byte[] data, ICryptoTransform cryptor)
{
    MemoryStream m = new MemoryStream();
    using (Stream c = new CryptoStream (m, cryptor, CryptoStreamMode.Write))
        c.Write (data, 0, data.Length);
    return m.ToArray();
}
```

여기서는 암호화와 복호화 양쪽 모두 `CryptoStreamMode.Write`가 가장 잘 맞는다. 두 경우 다 **새 메모리 스트림으로 밀어 넣는** 것이기 때문이다.

문자열을 받고 돌려주는 오버로드도 만들 수 있다.

```csharp
public static string Encrypt (string data, byte[] key, byte[] iv)
{
    return Convert.ToBase64String (
        Encrypt (Encoding.UTF8.GetBytes (data), key, iv));
}

public static string Decrypt (string data, byte[] key, byte[] iv)
{
    return Encoding.UTF8.GetString (
        Decrypt (Convert.FromBase64String (data), key, iv));
}
```

> **📌 `.NET 6`의 모드별 단축 메서드**
>
> `SymmetricAlgorithm`에는 `EncryptCbc`/`DecryptCbc` 외에 `EncryptEcb`/`DecryptEcb`, `EncryptCfb`/`DecryptCfb`도 있다. 이름에 모드가 박혀 있는 것이 장점이다 — 코드 리뷰에서 `EncryptEcb`라는 글자가 보이면 즉시 걸린다(44.9절). `CipherMode` 속성을 설정하는 옛 방식은 어떤 모드가 쓰였는지 호출부에서 보이지 않는다.

### 스트림 체이닝

`CryptoStream`은 **데코레이터**다(40.1절). 다른 스트림과 사슬처럼 엮을 수 있다는 뜻이다. 다음 예제는 압축된 암호문을 파일에 쓰고 다시 읽는다.

```csharp
byte[] key = keyStore.GetDataKey();
byte[] iv  = RandomNumberGenerator.GetBytes (16);

using (Aes algorithm = Aes.Create())
{
    using (ICryptoTransform encryptor = algorithm.CreateEncryptor (key, iv))
    using (Stream f = File.Create ("serious.bin"))
    using (Stream c = new CryptoStream (f, encryptor, CryptoStreamMode.Write))
    using (Stream d = new DeflateStream (c, CompressionMode.Compress))
    using (StreamWriter w = new StreamWriter (d))
        await w.WriteLineAsync ("Small and secure!");

    using (ICryptoTransform decryptor = algorithm.CreateDecryptor (key, iv))
    using (Stream f = File.OpenRead ("serious.bin"))
    using (Stream c = new CryptoStream (f, decryptor, CryptoStreamMode.Read))
    using (Stream d = new DeflateStream (c, CompressionMode.Decompress))
    using (StreamReader r = new StreamReader (d))
        Console.WriteLine (await r.ReadLineAsync());     // Small and secure!
}
```

한 글자 변수들이 전부 사슬의 일부다. 수학자들(`algorithm`, `encryptor`, `decryptor`)은 `CryptoStream`의 암호 작업을 돕기 위해 존재한다. 이런 식으로 스트림을 엮으면 **최종 스트림 크기와 무관하게 메모리를 거의 쓰지 않는다.**

```text
  쓰기 방향 (안쪽에서 바깥쪽으로 흐른다)

   StreamWriter w        "Small and secure!"  → UTF-8 바이트
        │
        ▼
   DeflateStream d       압축
        │
        ▼
   CryptoStream c ◀── encryptor ◀── Aes algorithm (키 + IV)
        │                              (수학자)
        ▼               암호화
   FileStream f          serious.bin


  읽기 방향은 정확히 반대로 당긴다:
   FileStream → CryptoStream(복호화) → DeflateStream(해제) → StreamReader
```

> **⚠️ 순서는 압축 → 암호화다. 반대로 하면 안 된다**
>
> 40.7절에서 이미 본 내용이다. 암호화된 데이터는 통계적 규칙성이 없으므로 거의 압축되지 않는다. 위 사슬에서 `DeflateStream`이 `CryptoStream`보다 **안쪽**(어댑터 쪽)에 있는 이유가 그것이다.
>
> 다만 압축과 암호화를 결합할 때는 **압축률 자체가 비밀을 누출**하는 부류의 공격(CRIME/BREACH 계열)이 알려져 있다. 공격자가 평문의 일부를 통제할 수 있고 결과 길이를 관찰할 수 있는 상황 — 대표적으로 HTTP 응답 — 이라면, 압축을 끄는 것이 정답인 경우가 있다. 파일을 저장하는 용도라면 대개 문제되지 않는다.

### 모드와 패딩

블록 암호는 **고정 크기 블록**(AES는 16바이트) 단위로 동작한다. 그보다 긴 데이터를 처리하려면 블록을 어떻게 이어 붙일지 정해야 하고, 그것이 **운용 모드(mode)** 다. 그리고 데이터 길이가 블록 크기의 배수가 아니면 마지막 블록을 채워야 하고, 그것이 **패딩(padding)** 이다.

| `CipherMode` | 동작 | 평가 |
|---|---|---|
| `ECB` | 블록마다 독립적으로 암호화 | **절대 쓰지 마라**(44.9절) |
| `CBC` | 이전 암호문 블록과 XOR한 뒤 암호화. 첫 블록은 IV와 XOR | 널리 쓰이지만 인증이 없다 |
| `CFB` | 블록 암호를 스트림 암호처럼 사용 | 플랫폼별 지원 편차 |
| `OFB` | 위와 유사한 다른 구성 | 플랫폼별 지원 편차 |
| `CTS` | 암호문 훔치기(패딩 없이 길이 유지) | AES에서 지원되지 않는 플랫폼이 많다 |

| `PaddingMode` | 동작 | 비고 |
|---|---|---|
| `PKCS7` | 채운 바이트 수를 값으로 채운다 | **기본값이자 표준** |
| `Zeros` | 0으로 채운다 | 원본이 0으로 끝나면 복원 불가 |
| `ANSIX923` | 마지막 바이트만 개수, 나머지는 0 | 레거시 |
| `ISO10126` | 마지막 바이트만 개수, 나머지는 난수 | 표준에서 철회됨 |
| `None` | 패딩 없음 | 입력 길이가 블록의 배수여야 한다 |

> **⚠️ ECB와 CBC 외의 모드는 플랫폼 지원이 갈린다**
>
> .NET(Core)의 `Aes`는 OS 라이브러리에 위임하므로(44.1절), 지원되는 모드가 OS와 구현에 따라 다르다. `CFB`는 피드백 크기(`FeedbackSize`)에 따라 지원 여부가 갈리고, `CTS`는 AES에서 지원하지 않는 플랫폼이 흔하다. 지원되지 않는 조합을 설정하면 `CryptographicException`이나 `PlatformNotSupportedException`이 나온다.
>
> **크로스 플랫폼 코드에서 안전하게 기댈 수 있는 조합은 CBC + PKCS7**이고, 그 위에 인증을 얹거나(아래) 아예 AES-GCM으로 가는 것이 답이다.

### 암호화만으로는 변조를 막지 못한다

이 절에서 가장 중요한 문단이다.

AES-CBC로 암호화한 데이터는 **읽을 수는 없지만 바꿀 수는 있다.** 공격자가 키를 몰라도 암호문의 비트를 뒤집으면 복호화 결과가 예측 가능한 방식으로 바뀐다.

CBC의 복호화는 "블록을 복호화한 뒤 이전 암호문 블록과 XOR"이다. 그래서 **IV의 어떤 바이트를 뒤집으면, 복호화된 첫 블록의 같은 위치 바이트가 정확히 같은 패턴으로 뒤집힌다.** 키는 전혀 필요 없다. 첫 블록이 `{"role":"user"...` 같은 구조라면 공격자는 그 바이트들을 원하는 값으로 바꿀 수 있다. 중간 블록도 마찬가지로, 한 블록을 희생하면 다음 블록을 임의로 조작할 수 있다.

여기에 더해 **패딩 오라클(padding oracle)** 문제가 있다. 복호화 후 PKCS7 패딩이 올바른지 검사하는데, 이 검사의 실패와 다른 실패를 공격자가 구분할 수 있으면 — 예외 메시지, HTTP 상태 코드, 응답 시간 무엇이든 — **키 없이 평문 전체를 한 바이트씩 복원**할 수 있다. 2010년대에 다수의 웹 프레임워크가 이 공격으로 무너졌다.

> **⚠️ 이 두 문제는 "잘 짜면 피할 수 있는 버그"가 아니다**
>
> CBC + PKCS7 구성 자체의 성질이다. 코드를 조심스럽게 짠다고 사라지지 않는다. 해결책은 **암호문에 인증을 붙여서, 변조된 암호문은 복호화를 시작조차 하지 않게 하는 것**이다.
>
> 복호화 순서가 결정적이다. `태그 검증 → (통과하면) 복호화` 순서여야 한다. 반대로 하면 패딩 오라클이 그대로 열려 있다.

### 인증 암호(AEAD) — `AesGcm`

**AEAD(Authenticated Encryption with Associated Data)** 는 기밀성과 무결성·인증을 한 번에 제공하는 구성이다. 암호화 결과로 암호문과 함께 **인증 태그(tag)** 가 나오고, 복호화는 태그를 먼저 검증한다.

.NET은 `AesGcm`, `AesCcm`, `ChaCha20Poly1305`를 제공한다. 기본 선택은 `AesGcm`이다.

```csharp
using System.Security.Cryptography;

const int NonceSize = 12;   // AesGcm.NonceByteSizes가 권장하는 크기
const int TagSize   = 16;   // AesGcm.TagByteSizes의 최대값

static byte[] Seal (byte[] key, byte[] plaintext, byte[] associatedData)
{
    byte[] nonce      = RandomNumberGenerator.GetBytes (NonceSize);
    byte[] ciphertext = new byte[plaintext.Length];
    byte[] tag        = new byte[TagSize];

    using (var gcm = new AesGcm (key, TagSize))          // ※.NET 8부터 태그 크기 필수
        gcm.Encrypt (nonce, plaintext, ciphertext, tag, associatedData);

    // nonce ‖ tag ‖ ciphertext 로 이어 붙여 저장·전송한다
    byte[] output = new byte[NonceSize + TagSize + ciphertext.Length];
    nonce     .CopyTo (output, 0);
    tag       .CopyTo (output, NonceSize);
    ciphertext.CopyTo (output, NonceSize + TagSize);
    return output;
}

static byte[] Open (byte[] key, byte[] sealed_, byte[] associatedData)
{
    ReadOnlySpan<byte> s = sealed_;
    ReadOnlySpan<byte> nonce      = s.Slice (0, NonceSize);
    ReadOnlySpan<byte> tag        = s.Slice (NonceSize, TagSize);
    ReadOnlySpan<byte> ciphertext = s.Slice (NonceSize + TagSize);

    byte[] plaintext = new byte[ciphertext.Length];
    using (var gcm = new AesGcm (key, TagSize))
        gcm.Decrypt (nonce, ciphertext, tag, plaintext, associatedData);
                                        // 태그 불일치면 예외를 던진다
    return plaintext;
}
```

호출부는 예외를 반드시 처리해야 한다.

```csharp
try
{
    byte[] plaintext = Open (key, blob, associatedData);
    // ...
}
catch (CryptographicException)
{
    // 변조됐거나, 키가 다르거나, 연관 데이터가 맞지 않는다.
    // 어느 쪽인지 호출자에게 알려 주지 않는다 — 44.9절.
    return Result.Invalid;
}
```

> **📌 태그 불일치 예외 타입**
>
> .NET 8부터는 태그가 맞지 않을 때 `AuthenticationTagMismatchException`이 던져진다. 이 타입은 `CryptographicException`을 상속하므로, **`CryptographicException`을 잡으면 모든 버전에서 동작한다.** .NET 8 미만에서는 `CryptographicException` 자체가 던져진다.

AEAD의 세 가지 입력을 구분하자.

| 입력 | 비밀인가 | 암호화되나 | 인증되나 |
|---|---|---|---|
| 평문(plaintext) | 그렇다 | **그렇다** | 그렇다 |
| 연관 데이터(associated data) | 아니다 | 아니다 | **그렇다** |
| nonce | 아니다 | 아니다 | 그렇다(암묵적) |

**연관 데이터**는 암호화하고 싶지는 않지만 변조는 막고 싶은 값을 넣는 자리다. 레코드 ID, 사용자 ID, 버전 번호, 파일 경로 같은 것들이다. 이걸 쓰면 공격자가 A 사용자의 암호화된 blob을 B 사용자 레코드에 옮겨 붙이는 공격(confused deputy)을 막을 수 있다.

> **⚠️ GCM에서 nonce 재사용은 치명적이다 — 절대 규칙**
>
> CBC에서 IV를 재사용하면 "정보가 조금 샌다". **GCM에서 같은 키로 nonce를 재사용하면 훨씬 나쁜 일이 일어난다.**
>
> 1. 두 평문의 XOR이 그대로 드러난다(스트림 암호의 키스트림 재사용과 같은 문제).
> 2. 그보다 심각하게, **인증 키가 복원된다.** 그러면 공격자는 그 키로 임의의 메시지에 유효한 태그를 붙일 수 있다. 즉 무결성 보장이 그 키에 대해 영구히 무너진다.
>
> 규칙은 단순하다. **하나의 키로 같은 nonce를 두 번 쓰지 않는다.** 어기면 복구할 방법이 없다.
>
> 위험한 패턴 두 가지를 알아 두라. **(가) nonce를 설정 파일이나 상수로 두는 것** — 재시작할 때마다 같은 값이다. **(나) 카운터를 메모리에만 두는 것** — 프로세스가 죽거나 인스턴스가 여러 개면 겹친다.

> **💡 nonce는 난수인가 카운터인가**
>
> 둘 다 맞다. 규칙은 "재사용 금지"이지 "난수"가 아니다.
>
> - **12바이트 난수**: 가장 단순하고, 분산 시스템에서 조율이 필요 없다. 다만 생일 문제 때문에 무한하지는 않다 — 하나의 키로 대략 2^32건 규모를 넘어서면 충돌 확률이 무시할 수 없어진다. NIST가 무작위 nonce에 대해 그 수준의 상한을 제시한다.
> - **카운터**: 충돌이 원천적으로 없지만, **모든 인스턴스·모든 재시작에 걸쳐 단조 증가**를 보장해야 한다. 단일 프로세스 안에서는 쉽고, 여러 인스턴스에서는 어렵다.
>
> 실무의 기본값은 **난수 nonce + 주기적 키 순환**이다(44.6절). 키를 바꾸면 nonce 예산이 초기화된다.

### 대안 — Encrypt-then-MAC

AEAD를 쓸 수 없는 상황(레거시 형식 호환, FIPS 정책 등)이라면 CBC 암호화에 HMAC을 붙이는 구성을 쓴다. 순서가 전부다.

| 구성 | 순서 | 평가 |
|---|---|---|
| **Encrypt-then-MAC** | 암호화한 뒤 **암호문에** MAC | **유일하게 안전한 순서** |
| MAC-then-Encrypt | 평문에 MAC을 붙이고 전체를 암호화 | 복호화를 먼저 해야 하므로 패딩 오라클이 열린다 |
| Encrypt-and-MAC | 평문에 MAC, 암호문과 나란히 전송 | MAC이 평문 정보를 누출한다 |

Encrypt-then-MAC를 직접 조립할 때 지켜야 할 규칙은 다음과 같다.

- **암호화 키와 MAC 키를 분리한다.** 같은 키를 두 용도로 쓰지 않는다. 하나의 마스터 키에서 KDF로 두 개를 파생시키는 것이 정석이다.
- **MAC의 입력에 IV를 포함시킨다.** IV를 빼면 IV 변조로 첫 블록을 조작할 수 있다.
- **버전·알고리즘 식별자도 MAC 입력에 포함시킨다.** 그러지 않으면 공격자가 "이건 옛 버전이다"라고 우기는 다운그레이드 공격이 가능하다.
- **검증은 `FixedTimeEquals`로 하고, 실패하면 복호화 자체를 하지 않는다.**

> **⚠️ 이 목록이 네 줄이라는 사실 자체가 경고다**
>
> 위 규칙 중 하나만 빠져도 구성 전체가 무너지고, **테스트는 전부 통과한다.** 정상 경로에서는 암호화도 되고 복호화도 되기 때문이다.
>
> `AesGcm`을 쓰면 이 네 가지가 전부 알고리즘 안에 들어 있다. 이 장이 반복하는 원칙 — **직접 조립하지 마라** — 의 가장 구체적인 사례가 여기다. Encrypt-then-MAC를 손으로 짜야 한다면, 그 결정에는 "AEAD를 쓸 수 없는 명시적 제약"이라는 근거가 문서로 남아 있어야 한다.

### 알고리즘 선택 요약

| 상황 | 선택 |
|---|---|
| 일반적인 데이터 암호화 | **AES-GCM** (`AesGcm`) |
| AES 하드웨어 가속이 없는 환경(일부 모바일·임베디드) | **ChaCha20-Poly1305** |
| 스트림으로 처리해야 하는 대용량 파일 | AES-CBC + `CryptoStream` + HMAC, 또는 청크 단위 AES-GCM |
| 레거시 형식과의 호환 | 형식이 요구하는 것. 새 데이터는 새 형식으로 |
| 길이를 보존해야 하는 필드(FPE) | .NET 기본 제공 없음. 전문 검토 필요 |

> **⚠️ `AesGcm`은 스트림 API가 아니다**
>
> `AesGcm.Encrypt`는 평문 전체를 한 번에 받는다. 수 GB짜리 파일을 통째로 메모리에 올릴 수는 없으므로, 대용량 데이터에는 **청크로 쪼개서 각 청크를 개별 AEAD 메시지로 처리**하는 설계가 필요하다.
>
> 그런데 이때 청크 순서 바꾸기·청크 삭제·잘라내기 공격이 새로 생긴다. 각 청크의 연관 데이터에 **청크 인덱스와 전체 개수, 마지막 청크 표시**를 넣어야 막을 수 있다. 이 지점에서 다시 "프로토콜을 설계하고 있다"는 신호가 켜진다 — 가능하면 age, Tink, libsodium의 secretstream처럼 이미 검증된 스트리밍 AEAD 구성을 쓰는 편이 낫다.

### 성능

| 요인 | 영향 |
|---|---|
| AES-NI 하드웨어 명령어 | 있으면 소프트웨어 구현 대비 자릿수 단위로 빠르다. x64·ARM64 현대 CPU에는 대부분 있다 |
| 키 크기 128 vs 256 | 256비트가 라운드 수가 많아 약 40% 정도 느리다. 그래도 대개 무시할 만하다 |
| GCM vs CBC | GCM의 인증 계산(GHASH)도 하드웨어 가속을 받는다. 보통 GCM이 CBC+HMAC보다 빠르다 |
| 메시지 크기 | 작은 메시지는 객체 생성·키 확장 오버헤드가 지배한다 |
| `Aes.Create()` 호출 빈도 | 반복 경로에서는 인스턴스 재사용이나 `EncryptCbc` 정적 경로가 낫다 |

작은 메시지를 대량으로 처리한다면 `AesGcm` 인스턴스를 **키마다 하나씩 만들어 재사용**하는 것이 유리하다. 키 확장(key schedule) 계산이 생성 시점에 한 번만 일어나기 때문이다. 다만 `AesGcm` 인스턴스는 스레드 안전이 보장되지 않으므로, 공유하려면 스레드별 인스턴스나 풀이 필요하다.

## 44.6 암호화 객체의 해제와 키 관리

### `CryptoStream`을 폐기해야 하는 이유

`CryptoStream`을 폐기하면 **내부 데이터 캐시가 하위 스트림으로 플러시된다.** 암호화 알고리즘은 데이터를 한 바이트씩이 아니라 **블록 단위로** 처리하므로 내부 캐싱이 필수다.

`CryptoStream`은 특이하게도 **`Flush` 메서드가 아무 일도 하지 않는다.** 폐기하지 않고 스트림을 플러시하려면 `FlushFinalBlock`을 호출해야 한다. `Flush`와 달리 `FlushFinalBlock`은 **한 번만** 호출할 수 있고, 그 뒤로는 더 이상 데이터를 쓸 수 없다.

> **⚠️ 폐기를 잊으면 마지막 블록이 사라진다**
>
> `using` 없이 `CryptoStream`에 쓰기만 하고 프로세스가 끝나면, 마지막 블록과 패딩이 하위 스트림에 도달하지 않는다. 결과는 **"암호화는 성공했는데 복호화할 때만 예외가 나는" 파일**이다.
>
> 더 나쁜 변형은 `CryptoStream`은 폐기했는데 그 안쪽의 `StreamWriter`를 폐기하지 않은 경우다. 사슬은 **가장 안쪽부터 바깥쪽 순서로** 정리돼야 한다. `using` 선언을 겹쳐 쓰면(33.5절) 역순 폐기가 자동으로 보장되므로, 사슬을 손으로 닫는 코드는 쓰지 마라.
>
> 하위 스트림을 살려 두고 싶다면 `CryptoStream(stream, transform, mode, leaveOpen: true)` 생성자를 쓴다.

### 수학자도 폐기해야 한다

위 예제들에서는 수학자 — `Aes` 알고리즘 객체와 `ICryptoTransform`(암호화기·복호화기) — 도 폐기했다. **Rijndael 변환기가 폐기될 때 대칭 키와 관련 데이터를 메모리에서 지운다.** 컴퓨터에서 동작하는 다른 소프트웨어(즉, 악성코드)가 나중에 그것을 발견하지 못하게 하기 위해서다. 이 일을 **가비지 컬렉터에 맡길 수는 없다.** GC는 메모리 영역을 "사용 가능"으로 표시할 뿐, 모든 바이트에 0을 덮어쓰지는 않는다.

`using` 문 바깥에서 `Aes` 객체를 폐기하는 가장 쉬운 방법은 **`Clear`를 호출하는 것**이다. `Clear`는 `Dispose`와 같은 일을 하며, 관리되지 않는 리소스를 해제하는 대신 **메모리를 지운다는 비정상적인 폐기 의미론**을 이름으로 드러낸다. (.NET Framework에서는 `SymmetricAlgorithm.Dispose`가 명시적 인터페이스 구현으로 숨겨져 있어 `Clear`가 사실상 유일한 통로였다. 모던 .NET에서는 `Dispose`도 공개 메서드이므로 둘 중 무엇을 불러도 된다.)

```csharp
Aes algorithm = Aes.Create();
try
{
    // ... 사용 ...
}
finally
{
    algorithm.Clear();     // = Dispose. 키 자료를 0으로 덮어쓴다
}
```

33.4절에서 본 "고가치 비밀은 폐기 시 지워라"라는 예외 규칙의 표준 사례가 바로 이것이다 — `SymmetricAlgorithm`은 키를 담은 바이트 배열에 `Array.Clear`를 호출한다.

### 비밀을 메모리에서 지우기

애플리케이션이 해제된 메모리를 통해 비밀을 흘릴 가능성을 더 줄이려면 다음을 하면 된다.

- **보안 정보에 문자열을 쓰지 않는다.** 불변이므로 한 번 만들어진 `string`의 값은 결코 지울 수 없다.
- **버퍼를 더 이상 쓰지 않게 되는 즉시 덮어쓴다.** 예컨대 바이트 배열에 `Array.Clear`를 호출한다.

.NET에는 이 목적의 전용 메서드가 있다.

```csharp
byte[] key = DeriveKey (password, salt);
try
{
    Encrypt (data, key);
}
finally
{
    CryptographicOperations.ZeroMemory (key);   // Span<byte>를 0으로 채운다
}
```

> **📌 `Array.Clear`가 아니라 `ZeroMemory`인 이유**
>
> `Array.Clear`도 0을 채우지만, JIT이 "이 배열은 이후 읽히지 않는다"고 판단해 **최적화로 제거해 버릴 여지**가 이론적으로 존재한다. C/C++ 세계에서 `memset`이 제거되어 비밀이 남는 것은 잘 알려진 문제이고, 그래서 `SecureZeroMemory` 같은 전용 함수가 있다.
>
> `CryptographicOperations.ZeroMemory`는 이 목적을 위해 제거되지 않도록 만들어진 메서드다. **비밀을 지우는 의도라면 이쪽을 쓴다.** 이름만으로도 의도가 드러난다는 장점은 덤이다.

> **⚠️ 메모리에서 완전히 지우는 것은 불가능하다**
>
> 위 기법들은 **최선의 노력**이지 보장이 아니다. GC는 객체를 힙 안에서 이동시키며(63장·64장), 이동 전 위치의 바이트를 지워 주지 않는다. 즉 `ZeroMemory`로 지우는 시점 이전에 이미 여러 개의 사본이 힙 여기저기에 남아 있을 수 있다. 페이지가 스왑되었거나 하이버네이션 파일에 기록되었을 수도 있고, 크래시 덤프에 통째로 들어갈 수도 있다.
>
> 그러니 "메모리에서 지웠으니 안전하다"고 결론 내리면 안 된다. 이 노력의 목적은 **비밀이 메모리에 머무는 시간 창을 줄이는 것**이지 위험을 없애는 것이 아니다.

> **⚠️ `SecureString`은 답이 아니다**
>
> 이름 때문에 오해받는 타입이다. `SecureString`은 .NET Framework 시절 Windows의 `CryptProtectMemory`에 기대어 만들어졌고, **.NET(Core)의 Windows 외 플랫폼에서는 내용이 암호화되지 않는다.** 공식 지침도 새 코드에서 쓰지 말 것을 권한다.
>
> 게다가 실제로 쓰려면 결국 평문 바이트로 마샬링해야 하므로 그 순간 보호가 사라진다. 비밀을 다뤄야 한다면 **`byte[]`나 `char[]`를 쓰고 즉시 `ZeroMemory`로 지우는 편**이 정직하고 실질적이다.

### 키 관리 — 이 장의 진짜 어려운 부분

키 관리는 보안의 결정적 요소다. **키가 노출되면 데이터도 노출된다.** 누가 키에 접근할 수 있어야 하는지, 하드웨어 장애에 대비해 어떻게 백업할지, 그러면서 무단 접근은 어떻게 막을지를 고려해야 한다.

**암호화 키를 하드코딩하는 것은 권장되지 않는다.** 어셈블리를 디컴파일하는 대중적인 도구가 존재하고, 그걸 쓰는 데 전문성이 거의 필요 없기 때문이다. 더 나은 선택지는 (Windows에서) **설치마다 랜덤 키를 생성해서 Windows 데이터 보호로 안전하게 저장하는 것**이다.

클라우드에 배포하는 애플리케이션이라면 Microsoft Azure와 Amazon Web Services(AWS)가 **감사 추적(audit trail)** 같은 기업 환경에 유용한 추가 기능을 갖춘 키 관리 시스템을 제공한다. 메시지 스트림을 암호화하는 경우라면 공개키 암호화가 여전히 최선의 선택지다.

### 키를 어디에 둘 것인가

| 저장 위치 | 보호 수준 | 문제점 |
|---|---|---|
| 소스 코드 상수 | **없음** | 디컴파일, Git 이력에 영구 잔존, 순환 불가 |
| `appsettings.json` | **거의 없음** | 배포 아티팩트·백업·로그에 그대로 |
| 환경 변수 | 낮음 | 프로세스 덤프·자식 프로세스·오류 페이지에 노출. 순환하려면 재시작 |
| `dotnet user-secrets` | **개발 전용** | **암호화되지 않는다.** 사용자 프로필의 평문 JSON일 뿐 |
| DPAPI / Data Protection | 중간 | 머신·사용자에 묶인다. 다중 인스턴스에서 키 링 공유 문제(44.2절) |
| OS 키 저장소(자격 증명 관리자, 키체인) | 중간~높음 | 데스크톱 앱에 적합. 서버에서는 다루기 번거롭다 |
| **KMS / Key Vault** | 높음 | 네트워크 의존, 지연, 비용. 감사 추적과 순환이 내장 |
| **HSM** | 가장 높음 | 비싸다. 키가 하드웨어 밖으로 나오지 않는다 |

> **⚠️ `dotnet user-secrets`는 암호화하지 않는다**
>
> 이름이 오해를 부른다. User Secrets는 비밀을 **암호화해서 보관하는 기능이 아니라**, 비밀을 소스 트리 바깥(사용자 프로필 디렉터리)의 평문 JSON 파일로 옮겨 **실수로 커밋되는 것만 막는** 개발 편의 기능이다.
>
> 그러니 프로덕션에서 쓰면 안 된다. 문서에도 개발 전용이라고 명시돼 있다.

> **⚠️ 환경 변수는 생각만큼 안전하지 않다**
>
> 12-factor 관행 때문에 "비밀은 환경 변수로"가 널리 퍼졌지만, 환경 변수에는 세 가지 누출 경로가 있다.
>
> 1. **자식 프로세스가 상속한다.** 애플리케이션이 외부 도구를 실행하면 그 도구도 비밀을 본다.
> 2. **프로세스 덤프와 진단 도구에 그대로 나온다.** Linux의 `/proc/<pid>/environ`, 크래시 덤프, APM 에이전트의 환경 수집 기능 전부 해당한다.
> 3. **오류 페이지·로그 수집기가 환경을 통째로 찍는 일이 잦다.**
>
> 컨테이너 환경에서 현실적인 타협은 "환경 변수에는 **KMS에 접근할 자격 증명이나 마운트 경로만** 두고, 실제 데이터 키는 KMS에서 받아 온다"는 구조다.

### 키 계층과 봉투 암호화

키를 KMS에 두면 새 문제가 생긴다. 데이터 1억 건을 암호화할 때마다 KMS를 호출할 수는 없다. 표준 해법이 **봉투 암호화(envelope encryption)** 다.

```text
   ┌─────────────────────────────────────────────────────────────┐
   │  KMS / HSM                                                  │
   │    마스터 키(KEK)  — 절대 밖으로 나오지 않는다               │
   └───────────────┬─────────────────────────────────────────────┘
                   │ ① 데이터 키 생성 요청
                   ▼
        평문 데이터 키(DEK)  +  암호화된 데이터 키
                   │                      │
       ② 메모리에서만 사용             ③ 암호문 옆에 함께 저장
                   │                      │
                   ▼                      ▼
        ┌──────────────────────────────────────────┐
        │  레코드                                  │
        │   암호화된 DEK ‖ nonce ‖ tag ‖ 암호문    │
        └──────────────────────────────────────────┘
                   │
       ④ 사용 후 DEK는 ZeroMemory로 즉시 폐기
```

- **KEK(Key Encryption Key)** 는 KMS 안에 머물고 밖으로 나오지 않는다.
- **DEK(Data Encryption Key)** 는 실제 데이터를 암호화하는 AES 키다. 암호화된 형태로 데이터 옆에 저장한다.
- 복호화할 때는 KMS에 "이 암호화된 DEK를 풀어 달라"고 한 번만 요청하고, 그 뒤 대량의 데이터는 로컬에서 처리한다.

이 구조의 장점은 **KEK 하나만 순환하면 되고**, KMS 호출 횟수가 데이터 양이 아니라 배치 수에 비례한다는 것이다.

### 키 순환

키는 언젠가 바꿔야 한다. 유출 의심, 규정 요구, 담당자 퇴사, 알고리즘 이행 등 이유는 여러 가지다. 순환 가능한 시스템의 조건은 하나다 — **암호문이 자기가 어떤 키로 암호화됐는지 알고 있어야 한다.**

```text
  키 ID를 포함한 레코드 형식(예시)

  ┌────────┬─────────┬────────┬──────┬───────────────────────┐
  │ 버전 1 │ 키 ID 4 │nonce 12│tag 16│ 암호문 (가변)         │
  └────────┴─────────┴────────┴──────┴───────────────────────┘
     바이트    바이트   바이트  바이트
```

이 형식이면 순환 절차가 다음과 같이 단순해진다.

1. 새 키를 만들고 **쓰기는 새 키로**, 읽기는 키 ID를 보고 옛 키·새 키 중 선택.
2. 배경 작업으로 옛 키 레코드를 점진적으로 재암호화.
3. 옛 키로 된 레코드가 0이 되면 옛 키 폐기.

> **💡 최소한 이것만은**
>
> 완벽한 키 관리 체계를 처음부터 갖추기는 어렵다. 우선순위를 매기면 다음과 같다.
>
> 1. **키가 소스 저장소에 없다.** Git 이력에 한 번 들어간 비밀은 커밋을 지워도 사라지지 않는다고 가정하고, 발견 즉시 **순환**해야 한다(삭제가 아니라).
> 2. **암호문 형식에 키 ID와 버전 필드가 있다.** 이게 없으면 나중에 어떤 방법으로도 순환할 수 없다.
> 3. **키에 접근한 기록이 남는다.** 유출 사고에서 "언제부터 새는지"를 답할 수 있느냐가 대응 비용을 결정한다.
> 4. **개발·스테이징·프로덕션의 키가 다르다.** 같으면 개발 DB 유출이 곧 프로덕션 유출이다.
>
> 1번과 2번은 첫날에 할 수 있고, 하지 않으면 나중에 비싸진다.

## 44.7 공개키 암호화와 서명 — `RSA` 클래스, 디지털 서명

### 비대칭이라는 것

공개키 암호는 **비대칭**이다. 암호화와 복호화에 서로 다른 키를 쓴다는 뜻이다.

대칭 암호화에서는 적절한 길이의 **아무 바이트열이나** 키로 쓸 수 있었지만, 비대칭 암호는 **특별히 만들어진 키 쌍**을 요구한다. 키 쌍은 공개 키와 개인 키 성분을 담고 다음과 같이 함께 작동한다.

- **공개 키는 메시지를 암호화한다.**
- **개인 키는 메시지를 복호화한다.**

키 쌍을 만든 쪽은 개인 키를 비밀로 유지하면서 공개 키를 자유롭게 배포한다. 이 방식의 특별한 점은 **공개 키로부터 개인 키를 계산할 수 없다**는 것이다. 그래서 개인 키를 잃어버리면 암호화된 데이터를 복구할 수 없고, 반대로 개인 키가 새면 암호 체계 전체가 쓸모없어진다.

공개키 핸드셰이크는 사전 접촉도, 기존의 공유 비밀도 없이 두 컴퓨터가 공용 네트워크에서 안전하게 통신할 수 있게 한다. Origin이 Target에게 기밀 메시지를 보내려는 상황을 보자.

1. Target이 공개/개인 키 쌍을 만들고 **공개 키를 Origin에게 보낸다.**
2. Origin이 **Target의 공개 키로** 기밀 메시지를 암호화해 Target에게 보낸다.
3. Target이 **자기 개인 키로** 기밀 메시지를 복호화한다.

도청자가 보게 되는 것은 Target의 공개 키와, 그 공개 키로 암호화된 비밀 메시지뿐이다. Target의 개인 키가 없으면 메시지를 복호화할 수 없다.

> **⚠️ 이것으로 중간자 공격을 막지는 못한다**
>
> 다시 말해, Origin은 **Target이 악의적인 상대가 아니라는 것을 알 수 없다.** 수신자를 인증하려면 발신자가 수신자의 공개 키를 이미 알고 있거나, 디지털 사이트 인증서를 통해 그 키를 검증할 수 있어야 한다.
>
> 이 한 문장이 인증서·PKI·TLS가 존재하는 이유의 전부다. 공개 키 자체는 "누구의 것인지"를 말해 주지 않는다.

### 크기 제한과 하이브리드 암호화

공개키 암호화는 상대적으로 느리고 메시지 크기에 제한이 있기 때문에, Origin이 Target에게 보내는 비밀 메시지는 보통 **이후 대칭 암호화에 쓸 새 키**를 담는다. 그러면 세션의 나머지 구간에서는 공개키 암호화를 버리고, 더 큰 메시지를 처리할 수 있는 대칭 알고리즘으로 넘어갈 수 있다. 세션마다 새 공개/개인 키 쌍을 생성한다면 어느 쪽에도 키를 저장할 필요가 없어 특히 안전하다.

**공개키 암호화 알고리즘은 메시지가 키보다 작을 것을 전제로 한다.** 그래서 이후의 대칭 암호화용 키처럼 아주 작은 데이터를 암호화하는 데만 적합하다. **키 크기의 절반보다 훨씬 큰 메시지를 암호화하려 하면 공급자가 예외를 던진다.**

정확한 상한은 패딩 방식이 정한다.

| 키 크기 | 패딩 | 최대 평문 바이트 | 계산 |
|---|---|---|---|
| RSA-2048 | OAEP-SHA256 | 190 | 256 − 2×32 − 2 |
| RSA-2048 | OAEP-SHA1 | 214 | 256 − 2×20 − 2 |
| RSA-2048 | PKCS#1 v1.5 | 245 | 256 − 11 |
| RSA-4096 | OAEP-SHA256 | 446 | 512 − 2×32 − 2 |

```text
   하이브리드 암호화 — 실제 시스템이 하는 일

   ① 대칭 데이터 키를 새로 만든다
        DEK = RandomNumberGenerator.GetBytes(32)

   ② 큰 데이터는 대칭으로 (빠르다)
        암호문, tag = AES-GCM(DEK, nonce, 평문, 연관데이터)

   ③ 작은 DEK만 상대의 공개 키로 (느리지만 32바이트뿐)
        감싼DEK = RSA-OAEP-SHA256(수신자 공개키, DEK)

   ④ 함께 전송
        ┌──────────┬───────┬─────┬─────────────────┐
        │ 감싼 DEK │ nonce │ tag │ 암호문          │
        └──────────┴───────┴─────┴─────────────────┘

   ⑤ 수신자는 개인 키로 DEK를 풀고, DEK로 본문을 푼다
   ⑥ DEK는 사용 후 ZeroMemory (44.6절)
```

44.6절의 봉투 암호화와 같은 구조다. 다른 점은 KEK가 KMS 안의 대칭 키가 아니라 **수신자의 공개 키**라는 것뿐이다.

> **💡 하이브리드 구성을 직접 짜기 전에 표준 봉투를 찾아보라**
>
> 위 구조는 개념적으로 단순하지만, 실제로는 메타데이터 인증·수신자 여러 명·알고리즘 협상·형식 버전 같은 것이 줄줄이 붙는다. 이미 표준화된 봉투 형식이 있다.
>
> - **CMS / PKCS#7** — `System.Security.Cryptography.Pkcs` 패키지의 `EnvelopedCms`와 `SignedCms`. 인증서 기반 생태계와 잘 맞는다.
> - **JWE / JWS** — JSON 기반. 웹 API 사이에서 널리 쓰인다.
> - **age, Tink, libsodium sealed box** — 파라미터 선택의 여지를 없앤 현대적 설계.
>
> 이 중 하나가 요구사항에 맞는다면 직접 조립할 이유가 없다.

### `RSA` 클래스

.NET은 여러 비대칭 알고리즘을 제공하는데 그중 RSA가 가장 널리 쓰인다. 원천이 보여주는 기본 사용법은 다음과 같다.

```csharp
byte[] data = { 1, 2, 3, 4, 5 };     // 암호화할 대상

using (var rsa = new RSACryptoServiceProvider())
{
    byte[] encrypted = rsa.Encrypt (data, true);
    byte[] decrypted = rsa.Decrypt (encrypted, true);
}
```

공개 키나 개인 키를 지정하지 않았기 때문에 암호 공급자가 기본 길이인 **1,024비트**로 키 쌍을 자동 생성한다. 생성자를 통해 8바이트 단위로 더 긴 키를 요청할 수 있다. **보안이 중요한 애플리케이션이라면 2,048비트를 요청하는 것이 신중한 선택이다.**

```csharp
var rsa = new RSACryptoServiceProvider (2048);
```

**키 쌍 생성은 계산 집약적이어서 10ms 정도 걸릴 수 있다.** 그래서 RSA 구현은 `Encrypt` 호출처럼 키가 실제로 필요해질 때까지 생성을 미룬다. 덕분에 기존 키(또는 키 쌍)가 있다면 그것을 먼저 적재할 기회가 생긴다.

> **⚠️ 새 코드에서는 `RSACryptoServiceProvider` 대신 `RSA.Create()`**
>
> `RSACryptoServiceProvider`는 Windows CAPI에 묶인 레거시 구현이다. .NET(Core)의 크로스 플랫폼 환경에서는 일부 멤버가 기대대로 동작하지 않거나 `PlatformNotSupportedException`을 던질 수 있다.
>
> `RSA.Create()`는 플랫폼에 맞는 구현을 반환하고, **기본 키 크기가 2,048비트**다. `RSA.Create(3072)`처럼 크기를 지정할 수도 있다.
>
> ```csharp
> using RSA rsa = RSA.Create (3072);
> ```
>
> 마찬가지로 `ImportCspBlob`/`ExportCspBlob`, `FromXmlString`/`ToXmlString` 같은 CAPI·XML 기반 키 입출력은 .NET Framework 시절의 관행이다. 새 코드는 아래의 표준 형식 메서드를 쓴다.

> **⚠️ `Encrypt(data, true)`의 `true`가 무슨 뜻인지 알고 쓰라**
>
> `RSACryptoServiceProvider.Encrypt`의 `bool` 인자는 **OAEP 패딩을 쓸지**를 지정한다. `true`면 OAEP(SHA-1 기반), `false`면 **PKCS#1 v1.5**다.
>
> `false`는 절대 쓰지 마라. PKCS#1 v1.5 암호화 패딩은 **Bleichenbacher 공격**에 취약하다 — 복호화 실패의 원인을 구분할 수 있는 오라클이 있으면 키 없이 평문을 복원할 수 있다. 44.5절의 패딩 오라클과 같은 부류의 문제이고, 20년 넘게 변형이 계속 발견되고 있다.
>
> `true`도 최선은 아니다. SHA-1을 쓰기 때문이다. **현대적 API에서는 패딩을 명시적으로 지정한다.**
>
> ```csharp
> byte[] ct = rsa.Encrypt (data, RSAEncryptionPadding.OaepSHA256);
> byte[] pt = rsa.Decrypt (ct,   RSAEncryptionPadding.OaepSHA256);
> ```
>
> `RSAEncryptionPadding.Pkcs1`은 **옛 시스템과의 호환이 강제될 때만** 쓰고, 그때도 복호화 실패를 호출자에게 구분해서 알려 주지 않도록 특히 조심해야 한다.

### 키를 저장하고 불러오기

`ImportCspBlob`과 `ExportCspBlob` 메서드는 키를 바이트 배열 형식으로 적재·저장한다. `FromXmlString`과 `ToXmlString`은 같은 일을 문자열 형식으로 하는데, 이 문자열은 XML 조각을 담는다. `bool` 플래그로 저장 시 개인 키를 포함할지 지정한다. 다음은 키 쌍을 만들어 디스크에 저장하는 코드다.

```csharp
using (var rsa = new RSACryptoServiceProvider())
{
    File.WriteAllText ("PublicKeyOnly.xml",  rsa.ToXmlString (false));
    File.WriteAllText ("PublicPrivate.xml",  rsa.ToXmlString (true));
}
```

기존 키를 제공하지 않았으므로 `ToXmlString`이 (첫 호출에서) 새 키 쌍 생성을 강제한다. 다음 예제는 이 키들을 다시 읽어 메시지를 암호화·복호화한다.

```csharp
byte[] data = Encoding.UTF8.GetBytes ("Message to encrypt");

string publicKeyOnly = File.ReadAllText ("PublicKeyOnly.xml");
string publicPrivate = File.ReadAllText ("PublicPrivate.xml");
byte[] encrypted, decrypted;

using (var rsaPublicOnly = new RSACryptoServiceProvider())
{
    rsaPublicOnly.FromXmlString (publicKeyOnly);
    encrypted = rsaPublicOnly.Encrypt (data, true);

    // 다음 줄은 예외를 던진다 — 복호화하려면 개인 키가 필요하다:
    // decrypted = rsaPublicOnly.Decrypt (encrypted, true);
}

using (var rsaPublicPrivate = new RSACryptoServiceProvider())
{
    // 개인 키가 있으면 복호화에 성공한다:
    rsaPublicPrivate.FromXmlString (publicPrivate);
    decrypted = rsaPublicPrivate.Decrypt (encrypted, true);
}
```

새 코드에서 권장되는 형식은 XML이 아니라 **표준 인코딩**이다.

| 메서드 | 형식 | 개인 키 포함 |
|---|---|---|
| `ExportSubjectPublicKeyInfo` | SPKI(DER) | 아니오 |
| `ExportRSAPublicKey` | PKCS#1 RSAPublicKey | 아니오 |
| `ExportPkcs8PrivateKey` | PKCS#8 | **예 (평문!)** |
| `ExportEncryptedPkcs8PrivateKey` | PKCS#8 (암호 기반 암호화) | **예 (암호로 보호)** |
| `ImportFromPem` ※.NET 5 | PEM 텍스트 자동 판별 | 형식에 따름 |
| `ExportSubjectPublicKeyInfoPem` ※.NET 7 | PEM 텍스트 | 아니오 |

```csharp
using RSA rsa = RSA.Create (3072);

// 공개 키는 그냥 배포해도 된다
string publicPem = rsa.ExportSubjectPublicKeyInfoPem();     // ※.NET 7

// 개인 키는 반드시 암호로 감싸서 내보낸다
byte[] encryptedPkcs8 = rsa.ExportEncryptedPkcs8PrivateKey (
    passwordBytes,
    new PbeParameters (PbeEncryptionAlgorithm.Aes256Cbc,
                       HashAlgorithmName.SHA256,
                       iterationCount: 600_000));
```

> **⚠️ `ExportPkcs8PrivateKey`는 평문이다**
>
> 이름에 "Encrypted"가 없는 개인 키 내보내기 메서드는 **암호화하지 않은 개인 키 바이트**를 그대로 준다. 그 배열을 파일에 쓰는 순간 개인 키가 디스크에 평문으로 놓인다.
>
> 개인 키를 파일로 다뤄야 한다면 `ExportEncryptedPkcs8PrivateKey`를 쓰고, 그 암호를 다시 어디에 둘지가 결국 44.6절의 문제로 돌아온다는 점을 인식해야 한다. **가장 좋은 것은 개인 키가 애플리케이션 메모리에 들어오지 않는 것** — 즉 HSM이나 KMS 안에서 서명·복호화 연산을 수행하는 구조다.

### 디지털 서명

공개키 알고리즘은 메시지나 문서에 **디지털 서명**을 하는 데도 쓸 수 있다. 서명은 해시와 비슷하지만, **생성에 개인 키가 필요하므로 위조할 수 없다.** 서명 검증에는 공개 키를 쓴다. 원천의 예제는 다음과 같다.

```csharp
byte[] data = Encoding.UTF8.GetBytes ("Message to sign");
byte[] publicKey;
byte[] signature;
object hasher = SHA1.Create();          // 선택한 해싱 알고리즘

// 새 키 쌍을 만들고 그것으로 데이터에 서명한다:
using (var publicPrivate = new RSACryptoServiceProvider())
{
    signature = publicPrivate.SignData (data, hasher);
    publicKey = publicPrivate.ExportCspBlob (false);      // 공개 키만 얻는다
}

// 공개 키만으로 새 RSA를 만들어 서명을 검증한다.
using (var publicOnly = new RSACryptoServiceProvider())
{
    publicOnly.ImportCspBlob (publicKey);
    Console.Write (publicOnly.VerifyData (data, hasher, signature));   // True

    // 이제 데이터를 변조하고 서명을 다시 확인해 보자:
    data[0] = 0;
    Console.Write (publicOnly.VerifyData (data, hasher, signature));   // False

    // 다음 줄은 개인 키가 없으므로 예외를 던진다:
    signature = publicOnly.SignData (data, hasher);
}
```

서명은 **먼저 데이터를 해싱한 다음, 그 결과 해시에 비대칭 알고리즘을 적용**하는 방식으로 동작한다. 해시는 크기가 작고 고정되어 있으므로 큰 문서도 비교적 빠르게 서명할 수 있다(공개키 암호화는 해싱보다 CPU를 훨씬 많이 쓴다). 원한다면 해싱을 직접 수행하고 `SignData` 대신 `SignHash`를 호출할 수도 있다.

```csharp
using (var rsa = new RSACryptoServiceProvider())
{
    byte[] hash = SHA1.Create().ComputeHash (data);
    signature = rsa.SignHash (hash, CryptoConfig.MapNameToOID ("SHA1"));
    // ...
}
```

`SignHash`도 어떤 해시 알고리즘을 썼는지 알아야 한다. `CryptoConfig.MapNameToOID`가 "SHA1" 같은 친숙한 이름으로부터 그 정보를 올바른 형식으로 제공한다.

`RSACryptoServiceProvider`는 키 크기와 같은 크기의 서명을 만든다 — RSA-2048이면 256바이트다. 원천은 여기에 "주류 알고리즘 중 128바이트보다 의미 있게 작은 안전한 서명을 내는 것은 없다"고 덧붙이는데, 이는 RSA를 전제로 한 서술이다. **타원곡선 서명은 훨씬 짧다** — ECDSA P-256은 64바이트, Ed25519도 64바이트다(뒤의 타원곡선 절). 서명 크기가 제약이라면 RSA가 아니라 ECC를 봐야 한다.

> **⚠️ 서명이 효력을 가지려면 공개 키를 신뢰할 수 있어야 한다**
>
> 수신자가 발신자의 공개 키를 **알고, 또 신뢰해야** 한다. 이는 사전 통신, 사전 구성, 또는 사이트 인증서를 통해 이루어진다. 사이트 인증서는 발신자의 공개 키와 이름을 담은 전자 기록이며, 그 자체가 **독립적인 신뢰 기관에 의해 서명**되어 있다. `System.Security.Cryptography.X509Certificates` 네임스페이스가 인증서를 다루는 타입을 정의한다.
>
> 이 점을 놓치면 서명 검증은 의식(儀式)에 불과해진다. "서명이 유효하다"가 아니라 **"내가 신뢰하는 그 사람의 키로 서명됐다"** 를 확인해야 한다.

새 코드의 서명은 해시 알고리즘과 패딩을 명시한다.

```csharp
using RSA rsa = RSA.Create (3072);

byte[] signature = rsa.SignData (
    data, HashAlgorithmName.SHA256, RSASignaturePadding.Pss);

bool ok = rsa.VerifyData (
    data, signature, HashAlgorithmName.SHA256, RSASignaturePadding.Pss);
```

| 서명 패딩 | 특성 | 언제 |
|---|---|---|
| `RSASignaturePadding.Pss` | 확률적. 현대적 권장 | 새 시스템 |
| `RSASignaturePadding.Pkcs1` | 결정적. 널리 호환됨 | 기존 형식·상대 시스템이 요구할 때 |

> **📌 서명 패딩의 PKCS#1 v1.5는 암호화의 그것과 다르다**
>
> 혼동하기 쉬운 지점이다. **암호화**에서의 PKCS#1 v1.5는 Bleichenbacher 공격 때문에 실질적으로 폐기 대상이다. 반면 **서명**에서의 PKCS#1 v1.5는 구현 오류(길이 검사를 게을리한 검증기)로 인한 위조 사례가 있었을 뿐, 방식 자체가 붕괴한 것은 아니며 TLS·인증서 생태계에서 여전히 광범위하게 쓰인다.
>
> 그래도 새로 설계한다면 PSS가 낫고, **선택의 여지가 없으면 PKCS#1 v1.5 서명도 받아들일 수 있다**는 정도로 이해하면 된다.

### 서명 vs MAC vs 해시 — 다시 정리

| | 해시 | HMAC | 디지털 서명 |
|---|---|---|---|
| 필요한 것 | 없음 | 공유 비밀 | 키 쌍 |
| 검증자가 위조 가능? | **가능** | **가능**(같은 키) | 불가능 |
| 제3자에게 증명 | 불가 | 불가 | **가능** |
| 비용 | 매우 낮음 | 낮음 | 높음 |
| 결과 크기 | 32바이트(SHA-256) | 32바이트 | 키 크기(RSA-3072이면 384바이트) |
| 쓰는 곳 | 체크섬, 중복 제거 | API 요청 서명, 세션 토큰 | 코드 서명, 인증서, 계약, 감사 로그 |

**부인 방지가 필요한지**가 핵심 질문이다. 내부 서비스끼리 요청 무결성만 확인하면 되는데 RSA 서명을 쓰는 것은 낭비다 — HMAC이 수천 배 싸다. 반대로 "이 사용자가 이 문서에 동의했다"를 나중에 제3자에게 증명해야 하면 HMAC으로는 불가능하다.

### 타원곡선 — 같은 강도, 짧은 키

RSA의 안전성은 큰 수 인수분해의 어려움에, ECC(타원곡선 암호)는 타원곡선 이산로그의 어려움에 기댄다. 현재까지 알려진 최선의 공격 알고리즘 기준으로 **ECC가 훨씬 짧은 키로 같은 강도**를 낸다. NIST가 정리한 등가 관계는 다음과 같다.

| 보안 강도(비트) | 대칭 | RSA 키 크기 | ECC 키 크기 |
|---|---|---|---|
| 112 | 3DES | 2048 | 224~255 |
| **128** | AES-128 | **3072** | **256** |
| 192 | AES-192 | 7680 | 384 |
| 256 | AES-256 | 15360 | 512 이상 |

RSA-2048은 112비트 강도에 해당한다. 128비트 강도를 맞추려면 RSA는 3072비트가 필요한데, ECC는 256비트면 된다. 키가 짧으면 저장·전송·연산 비용이 전부 줄어든다.

```csharp
using System.Security.Cryptography;

// 서명 — ECDSA
using ECDsa ecdsa = ECDsa.Create (ECCurve.NamedCurves.nistP256);

byte[] signature = ecdsa.SignData (data, HashAlgorithmName.SHA256);
bool   ok        = ecdsa.VerifyData (data, signature, HashAlgorithmName.SHA256);

// 공개 키 배포
byte[] spki = ecdsa.ExportSubjectPublicKeyInfo();
```

키 합의는 `ECDiffieHellman`이 담당한다.

```csharp
using ECDiffieHellman alice = ECDiffieHellman.Create (ECCurve.NamedCurves.nistP256);
using ECDiffieHellman bob   = ECDiffieHellman.Create (ECCurve.NamedCurves.nistP256);

// 각자 상대의 공개 키로 같은 비밀을 유도한다
byte[] aliceSecret = alice.DeriveKeyMaterial (bob.PublicKey);
byte[] bobSecret   = bob  .DeriveKeyMaterial (alice.PublicKey);
// 두 배열은 같다
```

| 알고리즘 | 할 수 있는 일 | 할 수 없는 일 |
|---|---|---|
| `RSA` | 암호화, 서명 | 키 합의 |
| `ECDsa` | 서명 | **암호화**, 키 합의 |
| `ECDiffieHellman` | 키 합의 | 암호화, 서명 |
| `DSA` | 서명(레거시) | 나머지 전부 |

> **⚠️ ECDSA로는 "암호화"할 수 없다**
>
> `ECDsa`에는 `Encrypt` 메서드가 없다. 이는 API 누락이 아니라 설계다. 타원곡선으로 기밀성을 얻으려면 **ECDH로 공유 비밀을 만들고 → KDF로 대칭 키를 유도하고 → AEAD로 암호화**하는 세 단계(ECIES 계열)를 밟는다.
>
> .NET은 이 조합을 하나로 묶은 고수준 API를 제공하지 않는다. 즉 손으로 조립해야 한다는 뜻이고, 그건 이 장이 말리는 일이다. 상대의 공개 키로 데이터를 바로 암호화해야 한다면 **RSA-OAEP 하이브리드**가 표준 API만으로 도달할 수 있는 경로다.

> **📌 ECDSA 서명 형식의 두 가지**
>
> ECDSA 서명은 두 정수 (r, s)의 쌍이고, 이를 바이트로 표현하는 방법이 두 가지다. **DER 시퀀스**(X.509·인증서 세계의 관례)와 **고정 길이 연접**(IEEE P1363, JWS·WebAuthn의 관례)이다.
>
> .NET의 `ECDsa.SignData`/`SignHash` **기본값은 고정 길이 연접(IEEE P1363)** 이다. DER 시퀀스가 필요하면 `DSASignatureFormat`을 받는 오버로드에 `DSASignatureFormat.Rfc3279DerSequence`를 지정한다 ※.NET Core 3.0. 다른 언어나 도구(OpenSSL 계열은 대개 DER)로 만든 서명이 .NET에서 검증되지 않는다면 **거의 항상 이 형식 불일치**다. 알고리즘 문제가 아니다.

### 인증서 — `X509Certificate2`

인증서는 "이 공개 키는 이 이름의 주체 것"이라는 주장에 **신뢰 기관이 서명한 문서**다. 앞서 말한 "공개 키를 신뢰할 수 있어야 한다"는 문제를 위임으로 푸는 장치다.

```csharp
using System.Security.Cryptography.X509Certificates;

// 저장소에서 지문으로 찾기 (Windows·Linux 모두 동작)
using var store = new X509Store (StoreName.My, StoreLocation.CurrentUser);
store.Open (OpenFlags.ReadOnly);

X509Certificate2Collection found = store.Certificates.Find (
    X509FindType.FindByThumbprint, thumbprint, validOnly: true);

using X509Certificate2 cert = found[0];

// 인증서에서 키를 꺼낸다
using RSA?   rsa   = cert.GetRSAPrivateKey();     // 개인 키가 있을 때만 null이 아니다
using ECDsa? ecdsa = cert.GetECDsaPublicKey();
```

체인 검증은 `X509Chain`이 담당한다.

```csharp
using var chain = new X509Chain();
chain.ChainPolicy.RevocationMode = X509RevocationMode.Online;
chain.ChainPolicy.VerificationTime = DateTime.UtcNow;

bool valid = chain.Build (cert);
if (!valid)
    foreach (X509ChainStatus s in chain.ChainStatus)
        Console.WriteLine (s.StatusInformation);   // 왜 실패했는지
```

> **⚠️ 검증을 끄는 코드를 프로덕션에 남기지 마라**
>
> 개발 중에 자체 서명 인증서를 쓰다가 검증 콜백을 항상 `true`로 반환하게 만들어 두고 그대로 배포하는 사고가 정말 흔하다. 그렇게 하면 TLS가 제공하던 **인증**이 사라지고 기밀성만 남는데, 인증 없는 기밀성은 중간자에게 무력하다(43장).
>
> 검증을 완화해야 한다면 **"이 특정 지문의 인증서만 추가로 허용"** 처럼 범위를 좁혀서 해야 하고, 그 코드는 개발 환경에서만 컴파일되도록 조건부로 격리하는 것이 안전하다.

> **📌 인증서 로딩 API가 바뀌었다 ※.NET 9**
>
> .NET 9는 `X509CertificateLoader` 정적 클래스를 도입하고, 파일·바이트 배열에서 인증서를 만드는 **`X509Certificate2` 생성자들을 폐기**했다. 옛 생성자는 내용의 형식을 자동 추측했는데 그 추측이 보안 문제와 이식성 문제의 원인이었기 때문이다.
>
> ```csharp
> // ※.NET 9 이후 권장
> X509Certificate2 cert = X509CertificateLoader.LoadCertificateFromFile (path);
> X509Certificate2 pfx  = X509CertificateLoader.LoadPkcs12FromFile (path, password);
> ```
>
> 형식을 명시하게 만들어서 "PFX인 줄 알았는데 DER이었다" 같은 모호함을 없앤 것이다.

> **⚠️ PFX(PKCS#12) 파일은 개인 키를 담는다**
>
> `.pfx`/`.p12` 파일은 인증서 **와 개인 키**를 함께 담는다. 이걸 소스 저장소에 넣거나, 컨테이너 이미지에 굽거나, 로그에 경로를 남기는 것은 개인 키를 그렇게 하는 것과 같다.
>
> 또 하나. Windows에서 PFX를 로드하면 개인 키가 **디스크의 키 저장소에 임시 파일로 남을 수 있다.** 서버에서 반복 로드하면 파일이 계속 쌓여 디스크를 채우는 문제가 알려져 있다. 인증서 객체를 반드시 `Dispose`하고, 가능하면 저장소에 한 번 설치해 두고 지문으로 참조하는 편이 낫다.

> **💡 자체 서명 인증서가 필요할 때**
>
> 테스트나 내부 통신용 인증서는 외부 도구 없이 만들 수 있다.
>
> ```csharp
> using RSA key = RSA.Create (3072);
> var request = new CertificateRequest (
>     "CN=internal.example.test", key,
>     HashAlgorithmName.SHA256, RSASignaturePadding.Pss);
>
> using X509Certificate2 cert = request.CreateSelfSigned (
>     DateTimeOffset.UtcNow.AddDays (-1),
>     DateTimeOffset.UtcNow.AddYears (1));
> ```
>
> `CertificateRequest`는 CA에 보낼 CSR을 만드는 데도 쓴다. 어셈블리 서명(52.5절·52.7절)과는 별개의 체계라는 점만 헷갈리지 마라.

## 44.8 난수와 암호학적 안전성

`Random`과 `RandomNumberGenerator`의 일반적인 비교 — 시드, 스레드 안전성, `Random.Shared`, 범위 편향, 성능 — 은 39.5절에서 이미 다뤘다. 여기서는 **암호학의 관점에서만** 본다.

### 암호에서 난수가 필요한 자리

랜덤 키나 IV를 생성하려면 `System.Security.Cryptography`의 `RandomNumberGenerator`를 쓴다. 이것이 만들어 내는 수는 진정으로 예측 불가능하며, 즉 **암호학적으로 강하다**(`System.Random` 클래스는 같은 보장을 제공하지 않는다).

```csharp
byte[] key = new byte [16];
byte[] iv  = new byte [16];

RandomNumberGenerator rand = RandomNumberGenerator.Create();
rand.GetBytes (key);
rand.GetBytes (iv);
```

.NET 6부터는 더 짧게 쓸 수 있다.

```csharp
byte[] key = RandomNumberGenerator.GetBytes (16);
byte[] iv  = RandomNumberGenerator.GetBytes (16);
```

이 장에서 난수가 필요한 자리를 모으면 다음과 같다.

| 용도 | 권장 크기 | 재사용 | 저장 |
|---|---|---|---|
| AES 키 | 16 / 24 / 32바이트 | 여러 메시지에 재사용 | 키 저장소(44.6절) |
| CBC IV | 16바이트 | **금지** | 암호문과 함께 평문으로 |
| GCM nonce | 12바이트 | **절대 금지** | 암호문과 함께 평문으로 |
| 비밀번호 솔트 | 16바이트 이상 | 사용자마다 새로 | 해시와 함께 평문으로 |
| 세션 토큰·API 키 | 32바이트 | 금지 | 해시해서 저장 |
| HMAC 키 | 32바이트 | 재사용 | 키 저장소 |

### "예측 불가능"이 정확히 무엇인가

`Random`과 `RandomNumberGenerator`의 차이는 **분포의 품질이 아니라 상태 복구 가능성**이다.

`System.Random`은 결정적 알고리즘이다. 내부 상태를 알면 이후 출력이 전부 정해지고, **출력을 충분히 관찰하면 내부 상태를 역산할 수 있다.** 통계적으로는 훌륭한 난수처럼 보이지만, 그건 통계 검정을 통과한다는 뜻이지 공격자를 막는다는 뜻이 아니다.

암호학적 CSPRNG는 반대의 성질을 요구한다.

| 성질 | 의미 |
|---|---|
| 다음 비트 예측 불가 | 지금까지의 출력을 전부 봐도 다음 출력을 예측할 수 없다 |
| 상태 복구 불가 | 출력으로부터 내부 상태를 되돌릴 수 없다 |
| 순방향 비밀성 | 상태가 노출돼도 **과거** 출력을 복원할 수 없다 |

`RandomNumberGenerator`는 이 요구를 직접 구현하지 않고 **OS의 난수 서비스에 위임**한다. Windows에서는 CNG의 난수 생성기, Linux에서는 커널의 `getrandom` 계열이다. 커널은 하드웨어 인터럽트 타이밍, CPU의 RDRAND 같은 여러 엔트로피 원천을 모아 시드를 만들고 지속적으로 재시드한다.

> **📌 대칭 알고리즘 객체는 이미 CSPRNG를 쓴다**
>
> 44.5절에서 본 것처럼, `Aes.Create()`로 만든 객체에 키와 IV를 지정하지 않으면 **암호학적으로 강한 난수 값이 자동 생성**된다. 즉 `algorithm.IV`를 그대로 쓰는 것과 `RandomNumberGenerator.GetBytes(16)`을 쓰는 것은 안전성 면에서 동등하다.
>
> 마찬가지로 `RSA.Create()`의 키 쌍 생성, `Rfc2898DeriveBytes`의 내부 연산도 전부 검증된 경로를 탄다. **직접 시드를 공급하려는 시도가 오히려 위험을 만든다.**

> **⚠️ `RNGCryptoServiceProvider`는 폐기됐다**
>
> 옛 코드에서 흔히 보이는 `new RNGCryptoServiceProvider()`는 `SYSLIB0023`으로 폐기됐다. 대체는 `RandomNumberGenerator.Create()`이고, 대부분의 경우 정적 메서드(`GetBytes`, `Fill`)로 인스턴스 자체가 필요 없다.

> **⚠️ 보안 값에 `Guid.NewGuid()`를 쓰지 마라**
>
> 버전 4 GUID는 128비트 중 6비트가 버전·변형 표시로 고정되어 실제 난수는 122비트다. 그 자체로는 나쁘지 않은 값이지만, **`Guid.NewGuid()`가 CSPRNG를 쓴다는 보장이 명세로 주어진 적은 없다.** 구현이 그렇게 되어 있는 것과 계약으로 보장되는 것은 다르다.
>
> 세션 토큰·비밀번호 재설정 링크·초대 코드처럼 **맞히면 누군가 이득을 보는 값**은 `RandomNumberGenerator.GetBytes(32)`를 Base64Url로 인코딩해서 만든다. 의도도 코드에 드러난다. GUID의 버전별 특성은 39.7절에 있다.

> **⚠️ 시간·프로세스 ID·카운터를 섞어 "더 무작위하게" 만들지 마라**
>
> `DateTime.Now.Ticks ^ Process.GetCurrentProcess().Id` 같은 시드 조합을 실제 코드에서 본다. 이런 값들은 **공격자가 상당 부분 추측할 수 있는 저엔트로피 소스**다. 여러 개를 XOR한다고 엔트로피가 더해지지 않으며, 결과적으로 몇 만 가지 후보로 좁혀지는 경우가 흔하다.
>
> 엔트로피가 필요하면 커널에서 받아 오면 된다. 그것이 `RandomNumberGenerator`가 하는 일 전부다.

### 성능 관점

CSPRNG는 `Random`보다 느리다(39.5절에 상대 비용 표가 있다). 그러나 이 장의 용도에서는 **거의 항상 무의미한 차이**다. AES 키 하나, IV 하나를 뽑는 비용은 그 뒤에 이어지는 암호 연산에 묻힌다.

예외는 nonce를 대량으로 생성하는 고빈도 경로다. 이때는 39.5절의 조언대로 **한 번에 크게 받아 잘라 쓰는 것**이 유리하다.

```csharp
// 1,000개 메시지에 쓸 12바이트 nonce를 한 번에 받는다
byte[] pool = RandomNumberGenerator.GetBytes (12 * 1000);
```

다만 이 버퍼는 **비밀이 아니지만**(nonce는 공개돼도 된다) 여전히 재사용 방지 관리가 필요하다. 잘라 쓴 구간을 추적하는 코드가 틀리면 44.5절의 최악 시나리오가 된다.

## 44.9 흔한 실수 카탈로그 — 직접 구현, ECB 모드, 하드코딩된 키

암호 코드의 특이한 점은 **틀려도 동작한다**는 것이다. 잘못된 구성으로 암호화한 데이터도 문제없이 복호화되고, 단위 테스트는 전부 초록색이고, 코드 리뷰에서도 눈에 띄지 않는다. 이 절은 그 사각지대를 목록으로 만든다.

이 절의 항목들에 대해 **잘못된 완성 코드는 싣지 않는다.** 복사해 갈 수 있는 형태로 두는 것 자체가 위험하기 때문이다. 대신 "무엇이 왜 잘못됐는지"를 서술한다.

### 한눈에 보는 목록

| # | 실수 | 무엇이 무너지나 | 대신 |
|---|---|---|---|
| 1 | 알고리즘·프로토콜 직접 구현 | 전부 | 표준 API |
| 2 | ECB 모드 | 기밀성(패턴 노출) | AES-GCM |
| 3 | 고정 IV / nonce 재사용 | 기밀성, GCM에서는 무결성까지 | 메시지마다 새 값 |
| 4 | 하드코딩된 키 | 기밀성 전부 | 키 저장소·KMS |
| 5 | 비밀번호를 키로 직접 사용 | 키 강도 | PBKDF2/Argon2로 유도 |
| 6 | 비밀번호를 일반 해시로 저장 | 비밀번호 | 44.4절 |
| 7 | `==`/`SequenceEqual`로 비밀 비교 | 인증 | `FixedTimeEquals` |
| 8 | 예외 메시지로 실패 원인 노출 | 기밀성(오라클) | 단일한 실패 응답 |
| 9 | 인증 없는 암호화 | 무결성 | AEAD |
| 10 | 자체 프로토콜 롤링 | 예측 불가 | 표준 봉투·TLS |
| 11 | MD5 / SHA-1을 보안 용도로 | 무결성 | SHA-256 이상 |
| 12 | 암호화한 뒤 압축 | 압축 효과 상실 | 압축 → 암호화(40.7절) |
| 13 | 비밀을 로그·예외·URL에 | 기밀성 | 마스킹, 헤더·본문 사용 |
| 14 | 검증 실패를 무시하거나 삼킴 | 인증 | 실패는 실패로 처리 |

### 1. 직접 구현

가장 근본적인 실수다. 대상은 세 층위로 나뉜다.

- **알고리즘 자체를 구현한다** — AES나 SHA-256을 논문 보고 짜는 것. 정답이 나와도 부채널(타이밍·캐시)에 완전히 열려 있다. 교육 목적 외에는 이유가 없다.
- **모드·패딩을 조립한다** — CTR 모드가 필요해서 AES-ECB로 카운터 블록을 암호화해 만드는 식. 44.5절에서 본 Encrypt-then-MAC의 네 가지 규칙처럼, 빠뜨리면 조용히 무너지는 세부가 많다.
- **프로토콜을 만든다** — 클라이언트와 서버가 주고받는 순서·필드·재전송·키 협상을 설계하는 것. 아래 10번 항목이다.

> **⚠️ "약간의 난독화"도 직접 구현이다**
>
> XOR로 문자열을 뒤집거나, Base64를 두 번 하거나, 문자를 시프트하는 코드에 `Encrypt`라는 이름을 붙이는 일이 여전히 많다. 이건 암호가 아니라 **난독화**이고, 난독화는 시간을 조금 벌 뿐이다.
>
> 문제는 이름이다. `EncryptPassword`라는 메서드를 보면 다음 사람은 그것이 암호화라고 믿는다. 난독화라면 `Obfuscate`라고 쓰고, 주석에 **보안 가치가 없다**고 명시해야 한다.

### 2. ECB 모드

ECB(Electronic Codebook)는 각 블록을 **독립적으로, 같은 키로** 암호화한다. 결과적으로 **같은 평문 블록은 항상 같은 암호문 블록**이 된다.

무엇이 문제인지는 비트맵 이미지를 ECB로 암호화한 유명한 예시("ECB 펭귄")가 잘 보여준다. 픽셀 값이 암호화됐는데도 **원본 그림의 윤곽이 그대로 남는다.** 같은 색이 같은 암호문이 되니 이미지의 구조가 보존되기 때문이다.

텍스트 데이터에서도 똑같은 일이 일어난다.

- 16바이트 정렬된 레코드에서 같은 값을 가진 필드는 같은 암호문으로 나타난다. 성별·등급·상태 코드처럼 값이 몇 가지 안 되면 빈도 분석으로 매핑을 복원할 수 있다.
- 블록 단위로 **잘라 붙이기**가 가능하다. A 레코드의 "잔액" 블록을 B 레코드에 옮겨 붙여도 복호화가 성공한다.

.NET에서 ECB가 나타나는 경로는 두 가지다. `CipherMode.ECB`를 명시적으로 설정하는 코드와, .NET 6의 `EncryptEcb`/`DecryptEcb` 메서드다. 후자는 이름에 모드가 드러나므로 리뷰에서 잡기 쉽다.

> **⚠️ ECB가 정당한 경우는 사실상 하나뿐이다**
>
> 정확히 한 블록 크기(16바이트)이고 **완전히 무작위한** 데이터, 예컨대 다른 키를 감싸는 경우다. 이때는 반복 패턴이 존재할 수 없어 ECB의 약점이 발현되지 않는다. 그마저도 전용 키 래핑 알고리즘(AES-KW)이 있으므로 굳이 쓸 이유가 없다.
>
> 즉 실무 규칙은 단순하다. **`ECB`라는 글자가 코드에 있으면 잘못된 것이다.**

### 3. 고정 IV와 nonce 재사용

44.5절에서 자세히 봤다. 요약하면 이렇다.

| 모드 | IV/nonce 재사용의 결과 |
|---|---|
| CBC | 같은 평문 접두사가 같은 암호문 접두사로 노출된다 |
| CTR / GCM | **두 평문의 XOR이 드러난다.** 한쪽 평문을 알면 다른 쪽이 통째로 복원된다 |
| GCM | 추가로 **인증 키가 복원**되어 임의 메시지 위조가 가능해진다 |

이 실수가 나타나는 전형적인 형태는 다음과 같다.

- IV를 상수 배열이나 설정 파일 값으로 두고 재사용한다.
- IV를 **키에서 유도**한다. 키가 안 바뀌면 IV도 안 바뀐다.
- IV 대신 사용자 ID나 레코드 ID처럼 **재사용되는 식별자**를 쓴다.
- 카운터를 인스턴스 필드에만 두어 프로세스 재시작·수평 확장 시 겹친다.
- 테스트 편의로 IV를 0으로 고정해 두고 그대로 배포한다.

> **💡 IV·nonce는 코드에서 절대 상수가 될 수 없는 값이다**
>
> 리뷰 기준으로 삼기 좋은 규칙 하나. **암호 코드에 등장하는 `byte[]` 상수는 전부 의심 대상**이다. 정당한 경우는 도메인 분리 문자열(HKDF의 info, 연관 데이터의 태그) 정도이고, 키·IV·nonce·솔트가 상수라면 그 자리에 버그가 있다.

### 4. 하드코딩된 키

44.6절에서 본 대로, 어셈블리를 디컴파일하는 도구는 대중적이고 전문성도 거의 필요 없다. `byte[] key = { 145, 12, 32, ... }` 같은 배열은 IL 메타데이터의 필드 초기화 데이터로 그대로 들어가 있어 문자열보다도 찾기 쉽다.

같은 부류의 변형들이 있다.

- 설정 파일의 평문 키. 배포 아티팩트와 백업에 그대로 들어간다.
- 컨테이너 이미지에 구운 키. 이미지 레이어에 영구히 남고, 레지스트리에 접근할 수 있는 사람 전부가 본다.
- Git 이력에 한 번 들어갔던 키. **커밋을 되돌려도 사라지지 않는다.**

> **⚠️ 유출된 키는 지우는 것이 아니라 순환하는 것이다**
>
> 저장소에서 비밀을 발견했을 때 커밋을 재작성하거나 파일을 지우는 것으로 대응하는 팀이 많다. 그건 대응이 아니다. **포크·클론·CI 캐시·미러에 이미 복제됐다고 가정**해야 하고, 유일하게 유효한 대응은 그 키를 무효화하고 새 키로 바꾸는 것이다.
>
> 그리고 이 대응이 가능하려면 44.6절의 키 ID 필드가 처음부터 있어야 한다. 순환할 수 없는 설계는 유출에 대응할 수 없는 설계다.

### 5. 비밀번호를 대칭 키로 직접 쓰기

사용자 비밀번호를 UTF-8 바이트로 바꿔 앞 16바이트나 32바이트를 AES 키로 쓰는 코드를 종종 본다. 세 가지가 동시에 잘못됐다.

1. **엔트로피가 턱없이 부족하다.** 32바이트 AES 키는 256비트 엔트로피를 전제하는데, 사람이 만든 비밀번호의 실제 엔트로피는 그 근처에도 가지 않는다. 키 공간이 사실상 비밀번호 사전 크기로 줄어든다.
2. **길이가 안 맞으면 잘리거나 패딩된다.** 짧은 비밀번호는 0으로 채워지고, 긴 비밀번호는 뒷부분이 무시된다. "비밀번호 뒷부분을 아무렇게나 바꿔도 복호화된다"는 동작이 나온다.
3. **바이트 분포가 편향된다.** ASCII 문자열은 각 바이트가 좁은 범위에 몰려 있어 실질 키 공간이 더 줄어든다.

올바른 방법은 **키 유도 함수를 거치는 것**이다. 비밀번호에서 키를 만들어야 한다면 44.4절과 같은 PBKDF2/Argon2를 쓰되, **비밀번호 검증용 해시와 암호화 키를 같은 출력에서 뽑지 않도록** 주의한다(도메인을 분리하거나 별도로 유도한다).

> **📌 KDF는 엔트로피를 만들어 내지 않는다**
>
> PBKDF2를 거쳤다고 약한 비밀번호가 강해지는 것이 아니다. KDF가 하는 일은 **시도 한 번의 비용을 올리는 것**이지 비밀번호의 엔트로피를 늘리는 것이 아니다.
>
> 그래서 비밀번호 기반 암호화의 안전성 상한은 언제나 **비밀번호 자체의 품질**이다. 이것이 실제 시스템이 비밀번호로 데이터를 직접 암호화하지 않고, 랜덤 데이터 키를 만들어 그 키를 비밀번호 유도 키로 감싸는 이유다.

### 6. 비밀번호를 일반 해시로 저장

44.4절 전체가 이 항목이다. `SHA256.HashData(password)`는 문법적으로는 해시지만 방어로서 기능하지 않는다. 솔트가 없으면 레인보우 테이블에, 스트레칭이 없으면 GPU 대량 시도에 그대로 노출된다.

### 7. `==`와 `SequenceEqual`로 비밀 비교

44.4절에서 본 타이밍 공격이다. `byte[]`에 `==`를 쓰면 참조 비교라 항상 실패하고(기능 버그), `SequenceEqual`은 **첫 불일치에서 빠져나온다**(보안 버그).

적용 범위를 놓치기 쉬운데, **비밀과 비교하는 모든 자리**가 해당한다.

- 비밀번호 해시 비교
- HMAC 태그 검증
- API 키·웹훅 서명 검증
- 이메일 인증 토큰, 비밀번호 재설정 토큰 비교
- CSRF 토큰 비교

`string.Equals`로 토큰을 비교하는 코드도 같은 문제를 갖는다. 토큰을 바이트로 바꿔 `CryptographicOperations.FixedTimeEquals`를 쓰는 것이 정석이다.

### 8. 예외 메시지로 실패 원인 노출 — 오라클

44.5절의 패딩 오라클이 대표적이다. 핵심은 **공격자가 실패의 종류를 구분할 수 있으면 안 된다**는 것이다.

`CryptographicException`의 메시지를 그대로 응답에 담거나 로그 레벨을 달리하거나, 실패 경로마다 응답 시간이 달라지면 그것이 오라클이 된다.

| 노출 경로 | 예 |
|---|---|
| 예외 메시지 | "Padding is invalid and cannot be removed"를 HTTP 응답에 포함 |
| 상태 코드 | 패딩 오류는 500, MAC 오류는 400 |
| 응답 시간 | 태그 검증 실패는 즉시, 복호화 후 실패는 늦게 |
| 로그 | 공격자가 로그를 볼 수 있는 멀티테넌트 환경 |

> **⚠️ 실패는 하나의 모양이어야 한다**
>
> 복호화·검증 실패는 원인이 무엇이든 **호출자에게 동일한 결과**를 돌려줘야 한다. 키가 틀린 것인지, 태그가 안 맞는 것인지, 형식이 깨진 것인지 구분해서 알려 줄 이유가 없다.
>
> 내부 로그에는 상세히 남기되, 그 로그가 공격자에게 도달하지 않는지 확인해야 한다. 인증 실패 응답에서 "아이디가 없음"과 "비밀번호가 틀림"을 구분하지 않는 관행과 같은 원리다.

### 9. 인증 없는 암호화

44.5절에서 다뤘다. AES-CBC만 쓰고 태그나 MAC이 없으면 **암호문을 변조당해도 알 수 없고**, 복호화 과정이 오라클이 된다.

코드에서 이 실수를 찾는 방법은 간단하다. 암호화 경로에 **`tag`나 `hmac`이라는 이름의 변수가 하나도 없으면** 인증이 없는 것이다.

### 10. 자체 프로토콜 롤링

가장 알아채기 어려운 실수다. 개별 API는 전부 올바르게 썼는데 조합이 틀린 경우다.

프로토콜을 설계하고 있다는 신호는 다음과 같다.

- 클라이언트와 서버가 **여러 번 주고받는** 메시지 순서를 정의하고 있다.
- 재전송·재시도 시 nonce나 카운터를 어떻게 할지 결정해야 한다.
- 알고리즘이나 버전을 **협상**하는 필드를 넣고 있다.
- "이 필드는 인증만, 저 필드는 암호화까지"를 필드별로 정하고 있다.
- 세션 키를 만들고 갱신하는 규칙을 쓰고 있다.

이 중 하나라도 해당하면, 그 설계에는 이 장에 나오지 않는 공격 표면이 있다. **재생 공격(replay)** — 유효한 메시지를 그대로 다시 보내기 —, **다운그레이드 공격** — 약한 알고리즘을 쓰자고 우기기 —, **반사 공격**, **메시지 순서 바꾸기** 같은 것들이다.

> **💡 프로토콜이 필요하면 이미 있는 것을 쓰라**
>
> - 두 시스템 사이의 안전한 채널이 필요하다 → **TLS**(43장). 상호 인증이 필요하면 클라이언트 인증서.
> - 메시지 단위로 암호화·서명해서 저장하거나 전달해야 한다 → **JWE/JWS**, **CMS**, **age**.
> - 서비스 간 요청 인증 → **HMAC 서명 헤더**(AWS SigV4 같은 기존 방식을 참고) 또는 **OAuth 2.0 / mTLS**.
> - 종단 간 암호화 메신저 → **Signal 프로토콜** 계열 라이브러리.
>
> 여기 없는 요구사항이라면, 그것이 정말 새로운 요구인지 다시 확인하는 편이 좋다.

### 11~14. 나머지

**11. MD5/SHA-1을 보안 용도로 쓰기.** 44.3절에서 다뤘다. 비적대적 체크섬이라면 `System.IO.Hashing`의 비암호학적 해시가 더 낫다.

**12. 암호화한 뒤 압축하기.** 40.7절과 44.5절에서 다뤘다. 압축이 거의 되지 않는다. 순서는 압축 → 암호화다.

**13. 비밀을 로그·예외·URL에 남기기.** 키·토큰·비밀번호가 로그에 찍히는 사고는 암호 구현의 결함보다 훨씬 자주 실제 유출을 만든다. 특히 URL 쿼리 문자열에 토큰을 넣으면 **서버 액세스 로그, 프록시 로그, `Referer` 헤더**를 통해 여러 곳에 복제된다. 토큰은 헤더나 본문으로 보낸다.

**14. 검증 실패를 삼키기.** `catch (CryptographicException) { }`으로 비우거나, 검증 결과 `bool`을 무시하는 코드는 보안 기능 전체를 무력화한다. 32장의 예외 처리 원칙이 여기서도 그대로 적용된다 — **처리할 수 없는 예외는 삼키지 않는다.**

### 코드 리뷰 체크리스트

암호 코드를 리뷰할 때 순서대로 확인할 항목이다.

```text
□ 이 코드가 지키려는 것이 무엇인지 한 문장으로 적을 수 있는가
□ 표준 API를 조합했는가, 아니면 프로토콜을 설계했는가
□ 키가 소스·설정·이미지·Git 이력 어디에도 없는가
□ 암호문 형식에 버전과 키 ID가 있는가 (순환 가능한가)
□ IV/nonce가 메시지마다 새로 만들어지는가
□ 인증(AEAD 태그 또는 MAC)이 있는가
□ 검증 실패 시 원인을 구분해서 노출하지 않는가
□ 비밀 비교에 FixedTimeEquals를 쓰는가
□ 비밀번호에 KDF를 거치고, 파라미터를 함께 저장하는가
□ 키 자료를 사용 후 ZeroMemory로 지우는가
□ 예외를 삼키는 catch 블록이 없는가
□ MD5·SHA1·ECB·PKCS#1 v1.5 암호화가 코드에 없는가
```

> **💡 마지막 질문**
>
> 위 목록을 다 통과해도 남는 질문이 하나 있다. **"이걸 직접 해야 하는 이유가 무엇인가?"**
>
> 이 장에서 본 모든 함정은 직접 조립하기 때문에 생긴다. TLS를 켜는 것으로 끝나는 문제, 프레임워크의 인증 기능으로 끝나는 문제, 클라우드 KMS의 봉투 암호화로 끝나는 문제를 직접 푸는 코드가 아닌지 먼저 확인하라. 이 장의 목적은 독자가 암호 프로토콜을 설계할 수 있게 만드는 것이 아니라, **설계해야 할 상황을 알아보고 피할 수 있게** 만드는 것이다.

## 이 장의 요약

- **API를 고르기 전에 목표를 정한다.** 기밀성·무결성·인증·부인 방지는 서로 다른 목표이고, 하나를 달성한다고 나머지가 따라오지 않는다. "암호화해 주세요"라는 요구사항은 거의 항상 다시 물어야 한다.
- **.NET은 암호를 직접 구현하지 않는다.** `Aes.Create()`나 `SHA256.HashData`는 OS의 검증된 암호 라이브러리(Windows CNG, Linux OpenSSL 등)를 호출한다. 하드웨어 가속과 부채널 방어를 공짜로 물려받으므로, 파생 타입을 직접 생성하지 말고 팩터리와 정적 메서드를 쓴다.
- **DPAPI는 관리할 키가 0개인 대신 Windows 전용이다.** `ProtectedData`는 다른 OS에서 `PlatformNotSupportedException`을 던지고 .NET에서는 별도 NuGet 패키지가 필요하다. 크로스 플랫폼 대안은 ASP.NET Core Data Protection이며, 이쪽은 **키 링을 어디에 둘지가 새 숙제**로 남는다.
- **해시·인코딩·암호화는 다른 것이다.** Base64는 보안 가치가 0이고, 해시는 되돌릴 수 없으며, 암호화만이 키로 복원 가능하다. MD5와 SHA-1에서 무너진 것은 **충돌 저항성**이므로, 서명·인증서에는 치명적이고 비적대적 체크섬에는 여전히 기능한다.
- **비밀번호 해싱의 목표는 느리게 만드는 것이다.** 일반 해시는 빠른 것이 미덕이지만 그 미덕이 그대로 공격자의 무기가 된다. 사용자별 솔트 + 충분한 반복 횟수의 PBKDF2가 최소선이고, 메모리 하드한 Argon2id가 더 낫다. 알고리즘·반복·솔트를 해시와 **함께 저장**해야 나중에 이행할 수 있다.
- **암호화만으로는 변조를 막지 못한다.** AES-CBC 암호문은 키 없이도 예측 가능한 방식으로 조작할 수 있고, 패딩 검사 결과가 새면 평문 전체가 복원된다. 기본값은 **AES-GCM**이며, 인증 없는 암호화를 쓸 이유는 사실상 없다.
- **GCM에서 nonce 재사용은 복구 불가능한 사고다.** 두 평문의 XOR이 드러나는 데서 그치지 않고 인증 키가 복원되어 위조가 가능해진다. 키·IV·nonce·솔트가 코드에 상수로 있다면 그 자리에 버그가 있다.
- **`CryptoStream`은 폐기해야 마지막 블록이 나간다.** `Flush`는 아무 일도 하지 않으며 `FlushFinalBlock`은 한 번만 부를 수 있다. 대칭 알고리즘 객체의 `Clear`는 키 자료를 0으로 덮어쓰는 폐기이고, GC는 그 일을 대신해 주지 않는다.
- **키 관리가 이 장의 진짜 어려운 부분이다.** 하드코딩·설정 파일·환경 변수·User Secrets는 전부 보호 수준이 낮다. 봉투 암호화로 KMS 호출을 줄이고, 암호문 형식에 **버전과 키 ID**를 넣어야 순환이 가능해진다. 유출된 키는 지우는 것이 아니라 순환하는 것이다.
- **공개키는 느리고 작다.** RSA는 키 크기보다 작은 데이터만 암호화할 수 있으므로 실제 시스템은 하이브리드 구조를 쓴다. 패딩은 `OaepSHA256`이고 PKCS#1 v1.5 암호화는 피한다. 같은 강도를 ECC가 훨씬 짧은 키로 내며(128비트 강도 = RSA-3072 = ECC-256), `ECDsa`는 서명만·`ECDiffieHellman`은 키 합의만 한다.
- **서명과 MAC의 차이는 부인 방지다.** 양쪽이 같은 키를 가지는 HMAC으로는 제3자에게 증명할 수 없다. 반대로 내부 무결성 확인에 RSA 서명을 쓰는 것은 수천 배 비싼 낭비다.
- **비밀과의 비교는 항상 `CryptographicOperations.FixedTimeEquals`다.** `==`는 참조 비교라 기능 버그이고, `SequenceEqual`은 첫 불일치에서 빠져나와 타이밍 공격을 허용한다.
- **암호 코드는 틀려도 동작한다.** 테스트가 통과하는 것과 안전한 것은 다른 문제다. 그래서 44.9절의 체크리스트가 필요하고, 그 마지막 항목은 언제나 "이걸 직접 해야 하는 이유가 무엇인가"다.

## 연습 문제

1. 같은 파일을 `MD5.HashData`, `SHA1.HashData`, `SHA256.HashData`, `SHA512.HashData`로 각각 해싱하고 `Stopwatch`로 처리량(MB/s)을 측정하라. 원천이 말하는 "SHA256이 2~3배 빠르다"가 당신의 하드웨어에서도 성립하는지 확인하고, `SHA3_256.IsSupported`를 출력해 OS 지원 여부도 함께 기록하라.

2. 같은 평문 두 개를 **같은 키·같은 IV**로 AES-CBC 암호화한 뒤 두 암호문을 16바이트 블록 단위로 나란히 출력하라. 평문의 앞부분을 같게 하고 뒷부분만 다르게 만들었을 때 암호문의 어디까지가 동일한지 확인하고, IV를 매번 새로 뽑았을 때 그 현상이 사라지는지 다시 측정하라.

3. AES-CBC로 암호화한 blob의 **IV 첫 바이트를 1 뒤집고** 복호화해 보라. 예외가 나는지, 아니면 복호화가 성공하면서 평문의 첫 바이트만 달라지는지 관찰하라. 같은 실험을 `AesGcm`으로 반복해 어떤 예외가 어느 시점에 나오는지 비교하고, 두 결과의 차이를 "인증"이라는 단어로 설명하라.

4. `Rfc2898DeriveBytes.Pbkdf2`의 반복 횟수를 1,000 / 10,000 / 100,000 / 600,000으로 바꿔 가며 한 번의 해싱에 걸리는 시간을 측정하라. 당신의 서버에서 로그인 한 건당 100ms를 예산으로 잡았을 때 쓸 수 있는 최대 반복 횟수를 구하고, 그 값을 `outputLength`를 32에서 64로 늘렸을 때와 비교하라.

5. 32바이트 배열 두 개를 만들어 첫 바이트만 다른 경우와 마지막 바이트만 다른 경우에 대해 `SequenceEqual`과 `CryptographicOperations.FixedTimeEquals`의 실행 시간을 각각 수백만 번 반복 측정하라. 두 메서드의 시간 분포가 어떻게 다른지 그래프로 그리고, 그 차이가 원격 공격자에게 무엇을 알려 주는지 한 문단으로 적어라.

6. `RSA.Create(2048)`로 `RSAEncryptionPadding.OaepSHA256`을 써서 190바이트와 191바이트를 각각 암호화해 보라. 어느 쪽에서 예외가 나는지 확인하고, 키를 3072비트로 바꿨을 때 경계값이 어떻게 이동하는지 계산식과 대조하라. 이어서 32바이트 AES 키만 RSA로 감싸고 본문은 `AesGcm`으로 암호화하는 하이브리드 경로를 만들어, 10MB 데이터에 대해 RSA 직접 암호화 시도와 소요 시간을 비교하라.

7. `Aes.Create()`로 만든 객체의 `Key`를 지역 변수에 복사한 뒤 `algorithm.Clear()`를 호출하고, 복사본과 원본 배열의 내용을 각각 출력하라. 무엇이 0으로 덮이고 무엇이 남는지 확인한 다음, `CryptographicOperations.ZeroMemory`를 `finally` 블록에 넣어 다시 실험하고 44.6절의 "최선의 노력이지 보장이 아니다"라는 서술을 자기 말로 설명하라.
