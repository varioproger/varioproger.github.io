# 43장. 네트워킹

> **이 장의 위치** — 40장에서 스트림이라는 바이트의 통로를 팠고, 41장·42장에서 그 통로에 흘려보낼 데이터의 표현을 다뤘다. 이 장은 그 통로의 반대편 끝이 **다른 기계**일 때 무슨 일이 벌어지는지를 다룬다. .NET의 네트워킹 API는 소켓부터 `HttpClient`까지 층층이 쌓여 있고, 어느 층에서 프로그래밍할지 고르는 판단이 이 장의 절반이다. 나머지 절반은 그 층에서 조용히 깨지는 지점들 — 메시지 경계, 소켓 고갈, 타임아웃 — 을 아는 일이다.
>
> **선수 지식** — 40장(스트림과 파일 I/O), 33장(결정적 정리와 `IDisposable`), 32장(예외 처리), 41장(직렬화와 JSON)
>
> **이 장에서 다루지 않는 것** — `async`/`await`가 만드는 상태 기계와 취소 프로토콜의 내부는 47장·46.8절에서, 스트림 아키텍처 자체는 40장에서, JSON 직렬화의 세부는 41장에서, TLS·인증서·암호 스위트의 상세는 44장에서 다룬다. ASP.NET Core로 서버를 만드는 방법 전반은 81장의 지도에 맡긴다. 이 장은 그 요소들이 **네트워크 위에서 어떻게 맞물리는지**만 본다.

## 43.1 네트워크 아키텍처와 .NET의 계층

### 계층 모델부터 시작하는 이유

네트워크 코드를 쓸 때 가장 먼저 해야 하는 판단은 "어떤 API를 쓸까"가 아니라 **"어느 층에서 일할까"** 다. 층을 잘못 고르면 이미 남이 해결한 문제를 손으로 다시 푸는 처지가 되거나, 반대로 필요 없는 추상화 비용을 계속 내게 된다.

개념 모델은 두 가지가 통용된다. 교과서에 나오는 OSI 7계층 참조 모델과, 실제 인터넷이 돌아가는 방식에 가까운 TCP/IP 4계층 모델이다.

| OSI 계층 | TCP/IP 계층 | 하는 일 | 대표 프로토콜 |
|---|---|---|---|
| 7. 응용(Application) | 응용 | 사용자·응용이 데이터를 주고받는 형식을 정한다 | HTTP, HTTPS, FTP, SMTP, POP3, IMAP4, DNS |
| 6. 표현(Presentation) | 응용 | 암호화·형식 변환·압축 | TLS(관례상 여기에 놓는다), MIME |
| 5. 세션(Session) | 응용 | 세션 개시·종료, 포트 할당 | — |
| 4. 전송(Transport) | 전송 | 바이트 스트림을 세그먼트로 쪼개고 전달을 보장(하거나 안 하거나) | TCP, UDP |
| 3. 네트워크(Network) | 인터넷 | 논리 주소 지정과 라우팅 | IPv4, IPv6, ICMP |
| 2. 데이터 링크(Data Link) | 네트워크 인터페이스 | 물리 매체에 맞는 프레임으로 변환 | Ethernet II, PPP, SLIP |
| 1. 물리(Physical) | 네트워크 인터페이스 | 전기·광 신호로 비트를 나른다 | 이더넷 케이블, 광섬유, 무선 |

OSI 모델은 "이 세상에 실재하지 않는" 개념 모델이다. 실제로 구현되어 돌아가는 것은 4계층 TCP/IP 모델이다. 그럼에도 OSI를 아는 값어치는 있다 — 실무에서 "L4 로드밸런서", "L7 라우팅" 같은 말이 OSI 층 번호로 오가기 때문이다.

> **📌 자주 만나는 약어들**
>
> 네트워킹은 약어의 늪이다. 이 장에서 반복해서 나오는 것만 정리한다.
>
> | 약어 | 원어 | 뜻 |
> |---|---|---|
> | DNS | Domain Name Service | 도메인 이름(`ebay.com`)과 IP 주소를 상호 변환한다 |
> | HTTP | Hypertext Transfer Protocol | 웹 페이지 조회와 웹 서비스 호출 |
> | IP | Internet Protocol | TCP·UDP 아래의 네트워크 계층 프로토콜 |
> | POP | Post Office Protocol | 메일 수신 |
> | REST | REpresentational State Transfer | 기본 HTTP 위에서 동작하는 웹 서비스 아키텍처 |
> | SMTP | Simple Mail Transfer Protocol | 메일 발송 |
> | TCP | Transmission Control Protocol | 연결 지향 전송 계층 프로토콜 |
> | UDP | User Datagram Protocol | 비연결 저비용 전송 계층 프로토콜 |
> | UNC | Universal Naming Convention | `\\computer\sharename\filename` |
> | URI | Uniform Resource Identifier | 자원 이름 지정 체계 |
> | URL | Uniform Resource Locator | 기술적으로는 URI의 부분집합, 통념상 URI의 동의어 |

### TCP와 UDP — 무엇이 다른가

전송 계층에서 실무자가 고르는 것은 사실상 둘뿐이다.

| 항목 | TCP | UDP |
|---|---|---|
| 연결 | 연결 지향. 핸드셰이크로 세션을 연다 | 비연결. 그냥 던진다 |
| 신뢰성 | 순서 보장, 손실 시 재전송 | 보장 없음. 유실되어도 알려주지 않는다 |
| 오류 검사 | 수행하고 실패하면 재전송을 요청한다 | 체크섬만 있고 복구는 없다 |
| 오버헤드 | 크다 | 작다 |
| 브로드캐스트 | 불가 | 가능 |
| 대표 사용처 | HTTP/1.1·HTTP/2, FTP, SMTP | DNS, VoIP, BitTorrent, HTTP/3(QUIC) |
| .NET 타입 | `TcpClient`, `TcpListener` | `UdpClient` |

RFC 768이 UDP를, RFC 793이 TCP를 정의한다. 판단 기준은 단순하다. **데이터가 반드시 도착해야 하면 TCP**(금융 거래), **늦게 도착한 데이터가 무가치하면 UDP**(실시간 영상). 영상 스트리밍이 가끔 뭉개져 보이는 것은 이 선택의 결과다.

### .NET 타입의 계층 지도

.NET의 네트워킹 타입은 위의 계층 위에 그대로 얹혀 있다.

```text
┌──────────────────────────────────────────────────────────────────────┐
│  응용 프레임워크 계층 (별도 패키지 / ASP.NET Core)                    │
│  ASP.NET Core (Kestrel) · SignalR · gRPC(43.14절) · Refit 등          │
└───────────────────────────────┬──────────────────────────────────────┘
                                │ 대부분 아래 계층을 감싼다
┌───────────────────────────────▼──────────────────────────────────────┐
│  응용 프로토콜 계층 — System.Net.Http / System.Net / System.Net.Mail  │
│  HttpClient(43.4절)   HttpListener(43.10절)   SmtpClient(43.13절)     │
│  Dns(43.11절)         ClientWebSocket(43.10절)                        │
└───────────────────────────────┬──────────────────────────────────────┘
                                │ HttpMessageHandler → SocketsHttpHandler
┌───────────────────────────────▼──────────────────────────────────────┐
│  전송 계층 파사드 — System.Net.Sockets                                │
│  TcpClient / TcpListener / UdpClient   →  NetworkStream (40장)        │
│  (선택적 데코레이터) SslStream — System.Net.Security (44장)           │
└───────────────────────────────┬──────────────────────────────────────┘
                                │ Client 프로퍼티로 노출된다
┌───────────────────────────────▼──────────────────────────────────────┐
│  소켓 계층 — System.Net.Sockets.Socket / SocketAsyncEventArgs         │
│  IP 계층 직접 접근, 원시 소켓, 비인터넷 프로토콜 패밀리                 │
└───────────────────────────────┬──────────────────────────────────────┘
                                │ P/Invoke
┌───────────────────────────────▼──────────────────────────────────────┐
│  OS 소켓 API (Winsock / BSD sockets) → 커널 TCP/IP 스택               │
└──────────────────────────────────────────────────────────────────────┘
```

위로 갈수록 편하고 아래로 갈수록 자유롭다. 위 계층은 인증·암호화·재전송·헤더 파싱을 대신 해 주지만, 아래 계층은 그 전부를 직접 해야 한다.

### 어느 계층을 언제 쓰는가

| 상황 | 쓸 것 | 이유 |
|---|---|---|
| REST API 호출, 파일 다운로드 | `HttpClient` | 사실상 유일한 정답. 인증·리다이렉트·압축·풀링이 전부 들어 있다 |
| 사내 서비스 간 고빈도 호출 | gRPC(43.14절) | 이진 프레이밍 + HTTP/2 멀티플렉싱 |
| 브라우저와 양방향 실시간 | `ClientWebSocket` / SignalR | HTTP 위에서 업그레이드된 지속 연결 |
| .NET이 지원하지 않는 응용 프로토콜(POP3 등) | `TcpClient` | 프로토콜을 손으로 구현해야 한다(43.13절) |
| 직접 만든 사설 프로토콜, P2P | `TcpClient` 또는 `Socket` | 프레이밍을 스스로 정의한다(43.12절) |
| 초당 수만 연결, 무할당 수신 경로 | `Socket` + `SocketAsyncEventArgs` / `System.IO.Pipelines` | 파사드가 만드는 할당을 없앤다 |
| 브로드캐스트, 손실 허용 스트림 | `UdpClient` | 전달 보장 비용을 내지 않는다 |
| 실서비스 HTTP 서버 | ASP.NET Core(Kestrel) | `HttpListener`는 학습·도구용이다(43.10절) |

응용 프로토콜 중에서 HTTP는 특별한 자리를 차지한다. "이 URL의 페이지를 달라"는 기본 동작이 "이 엔드포인트를 이 인자로 호출한 결과를 달라"로 자연스럽게 확장되기 때문이다. 게다가 HTTP는 인증·암호화·청크 전송·확장 가능한 헤더·쿠키를 이미 갖췄고, 여러 서버 응용이 하나의 IP·포트를 공유할 수 있다. 기업 방화벽이 80·443만 열어 두는 현실까지 겹쳐, 결국 대부분의 원격 호출이 HTTP를 타게 됐다.

### 네임스페이스 지도

```csharp
using System;                    // Uri, UriBuilder
using System.Net;                // IPAddress, IPEndPoint, Dns, WebProxy, CookieContainer
using System.Net.Http;           // HttpClient, HttpRequestMessage, HttpContent
using System.Net.Http.Headers;   // AuthenticationHeaderValue, MediaTypeHeaderValue
using System.Net.Http.Json;      // GetFromJsonAsync, PostAsJsonAsync (41장)
using System.Net.Sockets;        // Socket, TcpClient, TcpListener, UdpClient, NetworkStream
using System.Net.Security;       // SslStream (44장)
using System.Net.Mail;           // SmtpClient, MailMessage (43.13절)
using System.Net.WebSockets;     // ClientWebSocket
using System.Net.NetworkInformation;  // Ping, NetworkInterface
```

`Uri`가 `System.Net`이 아니라 `System`에 있다는 점이 매번 헷갈리는 지점이다. 프레임워크 초기부터 `Uri`를 아주 기본적인 타입으로 취급했기 때문이다.

> **⚠️ 이미 폐기된 API를 새로 쓰지 마라**
>
> 오래된 예제와 블로그가 아직도 살아 있어 함정이 된다.
>
> | 폐기된 것 | 상태 | 대체 |
> |---|---|---|
> | `WebClient` | 폐기(obsolete) 표시 | `HttpClient` |
> | `WebRequest` / `HttpWebRequest` / `WebResponse` | 폐기 표시 | `HttpClient` |
> | `FtpWebRequest` | .NET 6부터 폐기 표시 | NuGet의 FluentFTP 등 |
> | `ServicePointManager` | .NET(Core) 계열에서는 `HttpClient`에 영향을 주지 않는다 | `SocketsHttpHandler` 옵션(43.7절) |
> | `SmtpClient` | 새 개발에 권장하지 않음 | MailKit 등(43.13절) |
>
> 특히 `ServicePointManager.DefaultConnectionLimit` 를 설정해 두고 "동시 연결 수를 늘렸다"고 믿는 코드가 흔하다. **.NET Framework에서만 유효한 설정**이다. 모던 .NET에서는 `SocketsHttpHandler.MaxConnectionsPerServer`가 그 역할을 한다.

## 43.2 주소와 포트, `IPAddress`, `IPEndPoint`

### 두 개의 주소 체계

통신이 성립하려면 기계에 주소가 있어야 한다. 인터넷은 두 체계를 함께 쓴다.

- **IPv4** — 32비트. 문자열로 쓸 때는 점으로 구분된 십진수 넷이다(`101.102.103.104`). 여전히 지배적이다.
- **IPv6** — 128비트. 콜론으로 구분된 16진수다(`3EA0:FFFF:198A:E4A3:4FF2:54FA:41BC:8D31`). .NET에서 URI 안에 쓸 때는 **대괄호로 감싸야 한다**.

`System.Net.IPAddress`가 두 체계를 모두 표현한다. 바이트 배열을 받는 생성자와 문자열을 받는 정적 `Parse` 메서드가 있다.

```csharp
IPAddress a1 = new IPAddress (new byte[] { 101, 102, 103, 104 });
IPAddress a2 = IPAddress.Parse ("101.102.103.104");

Console.WriteLine (a1.Equals (a2));        // True
Console.WriteLine (a1.AddressFamily);      // InterNetwork

IPAddress a3 = IPAddress.Parse
  ("[3EA0:FFFF:198A:E4A3:4FF2:54fA:41BC:8D31]");
Console.WriteLine (a3.AddressFamily);      // InterNetworkV6
```

`AddressFamily`가 `InterNetwork`면 IPv4, `InterNetworkV6`면 IPv6다. 이름이 직관적이지 않은 이유는 BSD 소켓 API의 `AF_INET` / `AF_INET6` 상수를 그대로 옮겼기 때문이다.

`IPAddress`는 값 의미론을 흉내 낸다. 참조 타입이지만 `Equals`와 `GetHashCode`가 주소 내용 기준으로 동작하므로 딕셔너리 키로 쓸 수 있다. 다만 **불변이 아니다** — `ScopeId`는 쓸 수 있는 프로퍼티다.

> **⚠️ 파싱은 항상 `TryParse`로**
>
> `IPAddress.Parse`는 형식이 어긋나면 `FormatException`을 던진다. 사용자 입력이나 설정 파일에서 온 문자열을 파싱할 때는 예외 대신 `TryParse`를 쓴다.
>
> ```csharp
> if (!IPAddress.TryParse (configValue, out IPAddress? addr))
>     throw new InvalidOperationException ($"주소 형식이 올바르지 않다: {configValue}");
> ```
>
> 더 중요한 것은 **파싱 관용도가 런타임에 따라 다르다**는 사실이다. `1.2.3` 처럼 옥텟이 모자란 표기나 앞자리 0이 붙은 표기(`010.1.1.1`)를 .NET Framework 시절의 파서는 관대하게 받아들였다. 모던 .NET은 훨씬 엄격하다. 이런 표기를 받아들이는 데 의존하는 코드는 이식하는 순간 조용히 깨진다. 반대로 **관대한 파싱에 의존한 보안 검사**(예: 사용자가 준 주소가 사설망인지 검사)는 그 자체가 취약점이다. 검사할 때는 정규화된 바이트 배열(`GetAddressBytes()`)을 기준으로 판단하라.

### 특수 주소 상수

`IPAddress`에는 자주 쓰는 주소가 정적 필드로 준비돼 있다. 값을 외우지 말고 상수를 쓰는 편이 안전하다.

| 상수 | 값 | 의미 |
|---|---|---|
| `IPAddress.Any` | `0.0.0.0` | 서버가 **모든** 로컬 인터페이스에서 수신한다 |
| `IPAddress.Loopback` | `127.0.0.1` | 자기 자신 |
| `IPAddress.Broadcast` | `255.255.255.255` | 로컬 브로드캐스트(UDP) |
| `IPAddress.None` | `255.255.255.255` | "주소 없음"을 뜻하는 센티넬 |
| `IPAddress.IPv6Any` | `::` | IPv6판 `Any` |
| `IPAddress.IPv6Loopback` | `::1` | IPv6판 루프백 |
| `IPAddress.IPv6None` | `::` | IPv6판 `None` |

> **⚠️ `None`과 `Broadcast`는 같은 값이다**
>
> IPv4에서 `IPAddress.None`과 `IPAddress.Broadcast`는 **둘 다 `255.255.255.255`** 다. 따라서 `addr.Equals(IPAddress.None)`으로 "주소가 없다"를 판별하는 코드는 브로드캐스트 주소를 "없음"으로 오판한다. "없음"은 `IPAddress?`의 `null`로 표현하는 편이 정확하다.
>
> IPv6 쪽은 더하다. `IPv6Any`와 `IPv6None`은 **같은 `::`** 다. 이런 센티넬 겸용은 소켓 API의 유산이므로 새 코드에서 의미를 얹지 마라.

### IPv4와 IPv6의 다리

두 체계가 공존하는 동안 변환이 필요하다.

```csharp
IPAddress v4 = IPAddress.Parse ("192.168.0.1");
IPAddress mapped = v4.MapToIPv6();             // ::ffff:192.168.0.1
Console.WriteLine (mapped.IsIPv4MappedToIPv6); // True
Console.WriteLine (mapped.MapToIPv4());        // 192.168.0.1
```

`::ffff:x.x.x.x` 형태를 **IPv4 매핑 IPv6 주소**라고 부른다. 듀얼 스택 소켓이 IPv4 클라이언트의 주소를 이 형태로 보고한다.

> **⚠️ 듀얼 모드 소켓과 원격 주소 비교**
>
> `Socket`을 `AddressFamily.InterNetworkV6`로 만들고 `DualMode = true`로 두면 IPv4·IPv6 클라이언트를 한 소켓으로 받는다. 이때 IPv4 클라이언트의 `RemoteEndPoint`는 `192.168.0.5`가 아니라 `::ffff:192.168.0.5`로 나온다. 화이트리스트를 IPv4 문자열로 관리하고 있었다면 전부 불일치가 난다.
>
> 비교 전에 정규화하라.
>
> ```csharp
> static IPAddress Normalize (IPAddress a) =>
>     a.IsIPv4MappedToIPv6 ? a.MapToIPv4() : a;
> ```

### 포트

TCP와 UDP는 각 IP 주소를 **65,535개의 포트**로 쪼갠다. 그래서 주소 하나를 가진 기계가 여러 응용을 각자의 포트에 올릴 수 있다. HTTP는 80, HTTPS는 443, SMTP는 25 같은 관례적 기본값이 있다.

| 범위 | 이름 | 성격 |
|---|---|---|
| 0 ~ 1023 | 잘 알려진 포트(well-known) | 표준 서비스용. 유닉스 계열에서는 바인딩에 권한이 필요하다 |
| 1024 ~ 49151 | 등록된 포트(registered) | IANA에 등록된 응용용 |
| 49152 ~ 65535 | 동적/사설 포트(dynamic) | 공식 미할당. 테스트와 소규모 배포에 적합 |

클라이언트가 연결을 열 때 OS가 자동으로 배정하는 출발지 포트를 **임시 포트(ephemeral port)** 라고 한다. 임시 포트 풀의 기본 범위는 Windows가 49152~65535, 리눅스가 보통 32768~60999다. 43.9절에서 볼 소켓 고갈 문제는 정확히 이 풀이 바닥나는 사건이다.

### `IPEndPoint`

주소와 포트를 묶은 것이 **엔드포인트**다.

```csharp
IPAddress a = IPAddress.Parse ("101.102.103.104");
IPEndPoint ep = new IPEndPoint (a, 222);        // 포트 222
Console.WriteLine (ep.ToString());              // 101.102.103.104:222
```

`IPEndPoint`는 `EndPoint` 추상 클래스를 상속한다. 소켓 API가 유닉스 도메인 소켓(`UnixDomainSocketEndPoint`)이나 DNS 이름(`DnsEndPoint`) 같은 다른 종류의 엔드포인트도 받아들이기 때문에 추상화가 하나 더 있는 것이다.

문자열에서 되돌리는 `IPEndPoint.Parse` / `TryParse`도 있다 ※.NET Core 3.0.

```csharp
if (IPEndPoint.TryParse ("[::1]:8080", out IPEndPoint? parsed))
    Console.WriteLine ($"{parsed.Address} / {parsed.Port}");   // ::1 / 8080
```

IPv6 엔드포인트를 문자열로 쓸 때 대괄호가 필수인 이유가 여기서 드러난다. 대괄호가 없으면 주소 안의 콜론과 포트 구분자 콜론을 구별할 수 없다.

> **📌 방화벽은 포트를 막는다**
>
> 많은 기업 환경에서 열려 있는 포트는 80(평문 HTTP)과 443(HTTPS) 정도다. 사설 프로토콜을 위해 새 포트를 열어 달라고 요청하는 일은 기술 문제라기보다 정치 문제가 되기 쉽다. 이 현실이 "무엇이든 HTTP 위에 얹는" 관행의 기원이다. gRPC가 HTTP/2 위에 올라간 것도(43.14절), WebSocket이 HTTP 업그레이드로 시작하는 것도 같은 이유다.

### 성능 관점

`IPAddress`는 참조 타입이므로 생성할 때마다 힙 할당이 일어난다. IPv4는 내부적으로 32비트 정수 하나로 저장되지만 IPv6는 추가 배열을 동반한다. 초당 수십만 번 주소를 파싱하는 경로(예: 로그 파서)라면 다음을 고려한다.

- 반복되는 주소는 `Dictionary<string, IPAddress>`로 캐시한다.
- `IPAddress.TryParse(ReadOnlySpan<char>, out …)` 오버로드를 써서 부분 문자열 할당을 없앤다(68장).
- 주소를 비교만 할 목적이면 `GetAddressBytes()`(호출마다 새 배열을 만든다) 대신 `TryWriteBytes(Span<byte>, out int)`로 `stackalloc` 버퍼에 쓴다.

## 43.3 URI 다루기 — `Uri`, `UriBuilder`

### URI는 문자열이지만 문자열로 다루면 안 된다

URI(Uniform Resource Identifier)는 인터넷이나 LAN 위의 자원을 가리키는 특정 형식의 문자열이다. `http://www.ietf.org`, `ftp://myisp/doc.txt`, `mailto:joe@bloggs.com` 이 모두 URI다. 정확한 형식은 IETF가 정의한다.

`System.Uri` 클래스는 이 문자열을 구성 요소로 쪼개고, 정규화하고, 유효성을 검사한다.

```text
  https://user:pw@www.example.com:8443/shop/items?id=42&hl=ko#reviews
  └─┬─┘   └──┬──┘ └──────┬───────┘└┬─┘└────┬────┘└─────┬────┘└──┬──┘
  Scheme  UserInfo      Host      Port  AbsolutePath  Query   Fragment
          └──────────────── Authority ─────────────┘
```

| 프로퍼티 | 위 예제에서의 값 | 비고 |
|---|---|---|
| `Scheme` | `https` | 항상 소문자로 정규화된다 |
| `UserInfo` | `user:pw` | 없으면 빈 문자열 |
| `Host` | `www.example.com` | 소문자로 정규화된다 |
| `IdnHost` | `www.example.com` | 국제화 도메인을 퓨니코드로 |
| `Port` | `8443` | 생략되면 스킴의 기본 포트가 들어온다 |
| `Authority` | `www.example.com:8443` | 호스트와 비기본 포트 |
| `AbsolutePath` | `/shop/items` | 이스케이프된 형태 |
| `Segments` | `["/", "shop/", "items"]` | 경로를 조각으로 |
| `Query` | `?id=42&hl=ko` | **물음표를 포함한다** |
| `Fragment` | `#reviews` | **샵을 포함한다**. 서버로 전송되지 않는다 |
| `PathAndQuery` | `/shop/items?id=42&hl=ko` | 요청 라인에 실제로 실리는 부분 |
| `AbsoluteUri` | 전체 문자열(정규화됨) | |
| `OriginalString` | 생성자에 넘긴 원본 | 정규화 전 |

`Query`와 `Fragment`가 구분자를 **포함한** 채로 나온다는 점이 흔한 실수 지점이다. `uri.Query.Substring(1)`처럼 잘라 쓰거나, 애초에 파서를 쓴다.

> **📌 URI를 그냥 문자열로 둬도 되는 경우**
>
> `Uri`가 유용한 것은 형식을 검증하거나 조각으로 쪼갤 때다. 그렇지 않다면 문자열 그대로 둬도 된다 — 네트워킹 메서드는 대부분 `Uri`와 `string` 오버로드를 모두 제공한다. `HttpClient.GetStringAsync("https://...")` 가 동작하는 이유다. 내부적으로는 어차피 `Uri`가 만들어진다.

### 생성과 상대 URI

`Uri` 생성자에 넘길 수 있는 것은 세 가지다.

1. URI 문자열 — `http://www.ebay.com`, `file://janespc/sharedpics/dolphin.jpg`
2. 로컬 절대 경로 — `c:\myfiles\data.xlsx`, 유닉스라면 `/tmp/myfiles/data.xlsx`
3. UNC 경로 — `\\janespc\sharedpics\dolphin.jpg`

파일 경로와 UNC 경로는 자동으로 URI로 바뀐다. `file:` 스킴이 붙고 역슬래시가 슬래시로 바뀐다. 생성자는 그 밖에도 기본적인 정리를 한다 — 스킴과 호스트 이름을 소문자로 낮추고, 기본 포트나 빈 포트 번호를 제거한다.

스킴이 없는 문자열(`www.test.com`)을 넘기면 `UriFormatException`이 난다.

```csharp
if (Uri.TryCreate (input, UriKind.Absolute, out Uri? uri)   // 던지지 않는 방식
    && (uri.Scheme == Uri.UriSchemeHttp || uri.Scheme == Uri.UriSchemeHttps))
{ /* 안전하게 쓸 수 있다 */ }
```

상대 URI는 명시적으로 만들어야 한다.

```csharp
Uri u = new Uri ("page.html", UriKind.Relative);
```

> **⚠️ 상대 `Uri`의 프로퍼티는 대부분 예외를 던진다**
>
> 상대 `Uri` 인스턴스에서 `IsAbsoluteUri`와 `ToString()` 외의 거의 모든 프로퍼티·메서드를 호출하면 `InvalidOperationException`이 난다. `Host`, `Scheme`, `AbsolutePath` 전부 해당한다. 외부에서 받은 `Uri`를 다룰 때는 `IsAbsoluteUri`를 먼저 검사하는 습관이 필요하다.

`Uri`는 경로를 비교하고 빼는 메서드도 제공한다.

```csharp
Uri info = new Uri ("http://www.domain.com:80/info/");
Uri page = new Uri ("http://www.domain.com/info/page.html");

Console.WriteLine (info.Host);              // www.domain.com
Console.WriteLine (info.Port);              // 80
Console.WriteLine (page.Port);              // 80  ← 기본 포트를 알고 있다

Console.WriteLine (info.IsBaseOf (page));   // True
Uri relative = info.MakeRelativeUri (page);
Console.WriteLine (relative.IsAbsoluteUri); // False
Console.WriteLine (relative.ToString());    // page.html
```

`IsLoopback`은 URI가 로컬 호스트(127.0.0.1)를 가리키는지, `IsFile`은 로컬 또는 UNC 경로인지(`IsUnc`), `LocalPath`는 OS에 맞는 슬래시로 바꾼 경로를 준다. 리눅스 파일시스템에 마운트된 Samba 공유에 대해서는 `IsUnc`가 `false`를 보고한다.

### 상대 URI 결합 — 후행 슬래시라는 지뢰

기준 URI와 상대 URI를 합치는 것은 `Uri(Uri, string)` 생성자다. 여기서 규칙이 직관을 배신한다.

```csharp
var b1 = new Uri ("https://api.example.com/v1/");
var b2 = new Uri ("https://api.example.com/v1");

Console.WriteLine (new Uri (b1, "users"));   // https://api.example.com/v1/users
Console.WriteLine (new Uri (b2, "users"));   // https://api.example.com/users   ← v1이 사라졌다
Console.WriteLine (new Uri (b1, "/users"));  // https://api.example.com/users   ← v1이 사라졌다
```

RFC 3986의 참조 해석 규칙이다. 기준 URI의 **마지막 세그먼트는 파일 이름 취급**이라 상대 경로로 대체된다. 그리고 슬래시로 시작하는 상대 경로는 **루트 기준 절대 경로**라서 기준 경로를 통째로 버린다.

> **⚠️ `HttpClient.BaseAddress`에서 가장 많이 나는 사고**
>
> 위 규칙이 그대로 `HttpClient`에 적용된다.
>
> ```csharp
> client.BaseAddress = new Uri ("https://api.example.com/v1");   // 후행 슬래시 없음
> await client.GetAsync ("users");   // → https://api.example.com/users  (404)
> ```
>
> 규칙은 두 줄로 요약된다.
>
> 1. **`BaseAddress`는 항상 슬래시로 끝낸다.**
> 2. **상대 경로는 절대 슬래시로 시작하지 않는다.**
>
> 이 두 가지를 팀 규약으로 못 박아 두면 이 부류의 404는 사라진다. `IHttpClientFactory`로 클라이언트를 구성할 때(43.7절) 한곳에서 검증하기도 쉽다.

후행 슬래시는 서버 쪽에서도 의미가 있다. `http://www.albahari.com/nutshell/`은 웹 서버가 `nutshell` 하위 디렉터리의 기본 문서(보통 `index.html`)를 찾게 만든다. 슬래시가 없으면 서버는 사이트 루트에서 확장자 없는 `nutshell` 파일을 찾고, 없으면 대개 **301 Permanent Redirect**로 "슬래시를 붙여 다시 요청하라"고 답한다. .NET HTTP 클라이언트는 기본적으로 브라우저처럼 301을 따라가므로 요청은 결국 성공한다 — 대신 **왕복이 한 번 더 늘어난다**. 초당 수천 요청을 보내는 서비스에서 이 한 번은 공짜가 아니다.

### 이스케이프 — `EscapeDataString`과 `EscapeUriString`

URI에는 쓸 수 있는 문자와 없는 문자가 있다. 공백, 한글, `&`, `=`, `?` 같은 문자는 그대로 넣을 수 없거나 넣으면 구조를 망가뜨린다. 그래서 퍼센트 인코딩이 필요하다.

`Uri`에는 겉보기에 비슷한 두 정적 메서드가 있었다.

| 메서드 | 인코딩 대상 | 상태 |
|---|---|---|
| `Uri.EscapeDataString(s)` | 예약 문자를 포함한 **거의 모든** 비안전 문자. `&`, `=`, `?`, `/`, `#`, 공백을 모두 인코딩 | 현역 |
| `Uri.EscapeUriString(s)` | ASCII 127 초과 문자 등 "URI를 깨는" 문자만. `&`, `=`, `?`, `/`는 **남겨 둔다** | **폐기됨**(SYSLIB0013, .NET 6) |

`EscapeUriString`은 "이미 완성된 URI 문자열을 살짝 다듬는" 용도로 만들어졌다. 문제는 사람들이 그것을 **값 인코딩**에 썼다는 것이다.

```csharp
// 잘못된 코드 — 절대 이렇게 쓰지 마라
string q = Uri.EscapeUriString ("a=1&b=2");
string url = "https://example.com/search?q=" + q;
// → https://example.com/search?q=a=1&b=2
//   b=2 가 별개의 쿼리 매개변수가 되어 버렸다
```

`&`와 `=`가 살아남기 때문에 사용자가 넣은 값이 **쿼리 문자열 구조 자체를 바꿔 버린다**. 검색어가 파라미터를 주입하는 통로가 되는 것이다. 값을 인코딩할 때는 언제나 `EscapeDataString`을 쓴다.

```csharp
string search   = Uri.EscapeDataString ("(HttpClient or HttpRequestMessage)");
string language = Uri.EscapeDataString ("fr");
string requestUri = $"http://www.google.com/search?q={search}&hl={language}";
// q 값의 공백은 %20으로, 괄호는 %28·%29로 인코딩되어 들어간다.
// 결과 URI는 http://www.google.com/search?q=...&hl=fr 형태가 된다.
```

> **⚠️ `EscapeUriString`이 폐기된 이유는 "구식"이어서가 아니다**
>
> .NET 6에서 `Uri.EscapeUriString`에 폐기 표시(SYSLIB0013)가 붙은 것은 이 메서드가 **본질적으로 오용을 유도하기 때문**이다. 이름이 "URI 문자열을 이스케이프한다"로 읽혀서, 대부분의 개발자가 "URI에 넣을 값을 이스케이프한다"로 이해한다. 그 오해가 곧 주입 취약점이다. 새 코드에서는 쓰지 말고, 기존 코드에서 보이면 그 자리가 버그일 가능성부터 의심하라.

인코딩 계열 API가 하나 더 있다. `System.Net.WebUtility`다.

| API | 인코딩 규칙 | 용도 |
|---|---|---|
| `Uri.EscapeDataString` | 공백 → `%20`. RFC 3986 기준 | URI의 **경로 세그먼트**와 쿼리 값 전반 |
| `WebUtility.UrlEncode` | 공백 → `+`. HTML 폼 규칙(application/x-www-form-urlencoded) | HTML 폼 본문 |
| `WebUtility.HtmlEncode` | `<`, `>`, `&` → 엔티티 | HTML 출력(URI와 무관) |

> **⚠️ 공백은 `%20`인가 `+`인가**
>
> 둘은 같지 않다. `+`는 `application/x-www-form-urlencoded` 본문에서만 공백을 뜻한다. **경로 세그먼트에서 `+`는 문자 그대로의 플러스 기호**다. 파일 이름에 공백이 있는 경로를 `WebUtility.UrlEncode`로 만들면 서버가 `+`가 든 파일을 찾다가 404를 낸다.
>
> - 경로에 넣을 값 → `Uri.EscapeDataString`
> - 폼 본문에 넣을 값 → `FormUrlEncodedContent`가 알아서 처리한다(43.6절)

### `UriBuilder` — 수정 가능한 URI

`Uri` 인스턴스의 프로퍼티는 전부 읽기 전용이다. 기존 URI를 고치려면 `UriBuilder`를 쓴다. 쓰기 가능한 프로퍼티를 갖고 있고 `Uri` 프로퍼티로 다시 `Uri`를 얻는다.

```csharp
var ub = new UriBuilder ("https://api.example.com/v1/items?page=1");
ub.Port  = 8443;
ub.Path  = "/v2/items";
ub.Query = "page=2&size=50";         // 물음표는 붙이지 않아도 된다
Console.WriteLine (ub.Uri);          // https://api.example.com:8443/v2/items?page=2&size=50
```

`UriBuilder.Query`는 대입할 때 물음표를 알아서 붙여 주지만, **읽을 때는 물음표가 포함된 값**이 나온다. 그래서 "기존 쿼리에 파라미터를 하나 더 붙이기"를 순진하게 짜면 물음표가 문자열 중간에 끼거나(런타임 버전에 따라) 중복된 URI가 만들어진다.

```csharp
// 위험한 패턴 — 읽은 값에 물음표가 이미 들어 있다
ub.Query = ub.Query + "&extra=1";        // 빈 쿼리일 때는 "?&extra=1"이 된다
```

쿼리 조립은 손으로 하지 말고 도우미를 쓴다.

```csharp
static string BuildQuery (IEnumerable<KeyValuePair<string,string>> pairs) =>
    string.Join ("&", pairs.Select (p =>
        $"{Uri.EscapeDataString (p.Key)}={Uri.EscapeDataString (p.Value)}"));

var ub = new UriBuilder ("https://api.example.com/v2/items")
       { Query = BuildQuery (parameters) };
```

ASP.NET Core를 참조하는 프로젝트라면 `Microsoft.AspNetCore.WebUtilities.QueryHelpers.AddQueryString`을 쓰는 편이 낫다.

> **📌 `CheckHostName`과 `CheckSchemeName`**
>
> `Uri.CheckHostName(string)`은 문자열이 호스트 이름으로서 문법적으로 유효한지 `UriHostNameType` 열거형으로 알려 준다(`Dns`, `IPv4`, `IPv6`, `Basic`, `Unknown`). `Uri.CheckSchemeName(string)`은 스킴 이름의 문법 검사다. 둘 다 **존재 여부는 확인하지 않는다** — 문법 검사일 뿐이다.

### 성능 관점

`Uri` 생성은 생각보다 비싸다. 문자열 파싱, 정규화, 구성 요소 인덱스 계산이 일어나고 여러 개의 문자열이 새로 할당될 수 있다. 요청마다 같은 기준 URI로 `new Uri(...)`를 반복하는 코드는 흔한 낭비다.

```csharp
// 나쁜 예 — 요청마다 기준 URI를 다시 파싱한다
foreach (var id in ids)
    await client.GetAsync (new Uri ("https://api.example.com/v1/items/" + id));

// 나은 예 — 기준은 한 번만 만든다
static readonly Uri Base = new ("https://api.example.com/v1/");
foreach (var id in ids)
    await client.GetAsync (new Uri (Base, $"items/{id}"));
```

가장 나은 방법은 `BaseAddress`를 클라이언트에 한 번 설정하고 상대 문자열만 넘기는 것이다(후행 슬래시 규칙을 지킨다는 전제에서).

## 43.4 `HttpClient` — `GetAsync`와 응답 메시지

### `HttpClient`가 무엇을 대체했는가

`System.Net.Http.HttpClient`는 HTTP 클라이언트 작업을 위한 현대적 API다. 예전의 `WebClient`와 `WebRequest`/`WebResponse`를 대체했고, 그 셋은 이제 폐기 표시가 붙어 있다.

`HttpClient`는 "웹 페이지 하나 가져오기"보다 복잡한 프로토콜을 다루기 위해, HTTP 기반 웹 API와 REST 서비스의 성장에 대응해 설계됐다. 구체적으로는 다음이 다르다.

- **인스턴스 하나가 동시 요청을 처리**하며, 커스텀 헤더·쿠키·인증 스킴과 잘 맞물린다.
- **커스텀 메시지 핸들러를 끼워 넣을 수 있다.** 단위 테스트의 목(mock)과 로깅·압축·암호화 파이프라인이 여기서 나온다(43.7절).
- **헤더와 콘텐츠를 위한 풍부하고 확장 가능한 타입 체계**를 갖췄다.

가장 단순한 사용은 인스턴스를 만들고 `Get*` 계열 메서드에 URI를 넘기는 것이다.

```csharp
string html = await new HttpClient().GetStringAsync ("http://linqpad.net");
```

`HttpClient`의 I/O 바운드 메서드는 **전부 비동기**다. 동기 버전은 `Send`(※.NET 5) 하나뿐이고, 이것도 특수 상황용이다. 비동기 메서드의 동작 원리 자체는 47장에서 다룬다.

> **⚠️ 이 코드를 그대로 실무에 옮기지 마라**
>
> `new HttpClient()`를 매번 만드는 위 한 줄은 문서와 예제에서 셀 수 없이 반복됐고, 그만큼 많은 장애를 만들었다. 최선의 성능을 얻으려면 **같은 인스턴스를 재사용해야 한다** — 그러지 않으면 DNS 해석이 불필요하게 반복되고 소켓이 필요 이상으로 오래 열려 있게 된다. 전체 이야기는 43.9절에서 다룬다. 이 절의 예제들은 설명을 위해 인스턴스를 인라인으로 만들지만, 실제 코드에서는 재사용되는 인스턴스를 가정하고 읽어라.

### 네 가지 `Get` 메서드

| 메서드 | 반환 | 언제 쓰나 | 주의 |
|---|---|---|---|
| `GetStringAsync(uri)` | `Task<string>` | 작은 텍스트 응답 | 본문 전체를 문자열로 메모리에 올린다 |
| `GetByteArrayAsync(uri)` | `Task<byte[]>` | 작은 이진 응답 | 본문 전체를 배열로 올린다 |
| `GetStreamAsync(uri)` | `Task<Stream>` | 대용량 다운로드 | 응답 메시지에 접근할 수 없다 |
| `GetAsync(uri)` | `Task<HttpResponseMessage>` | **기본 선택** | 상태 코드·헤더·본문 모두 접근 가능 |

앞의 셋은 `GetAsync`의 편의 단축이다. 응답 메시지가 필요하면 `GetAsync`를 쓴다.

```csharp
var client = new HttpClient();
// GetAsync는 CancellationToken 오버로드도 받는다.
HttpResponseMessage response = await client.GetAsync ("http://...");
response.EnsureSuccessStatusCode();
string html = await response.Content.ReadAsStringAsync();
```

`HttpClient`는 동시 작업을 허용하므로 다음처럼 두 페이지를 한꺼번에 내려받는 코드가 정당하다.

```csharp
var client = new HttpClient();
var task1 = client.GetStringAsync ("http://www.linqpad.net");
var task2 = client.GetStringAsync ("http://www.albahari.com");
Console.WriteLine (await task1);
Console.WriteLine (await task2);
```

### `HttpResponseMessage`

응답 메시지는 상태 코드, 헤더, 본문을 담는다.

| 멤버 | 타입 | 설명 |
|---|---|---|
| `StatusCode` | `HttpStatusCode` | `OK`, `NotFound`, `InternalServerError` 등 |
| `IsSuccessStatusCode` | `bool` | 상태 코드가 200~299면 참 |
| `EnsureSuccessStatusCode()` | `HttpResponseMessage` | 실패면 `HttpRequestException`을 던진다 |
| `ReasonPhrase` | `string?` | `"Not Found"` 같은 텍스트. 신뢰하지 마라 |
| `Headers` | `HttpResponseHeaders` | 응답 헤더(콘텐츠 헤더 제외) |
| `Content` | `HttpContent` | 본문. 헤더는 `Content.Headers`에 있다 |
| `Version` | `Version` | 실제로 사용된 HTTP 버전 |
| `RequestMessage` | `HttpRequestMessage?` | 리다이렉트 후 최종 요청 |

> **⚠️ 404는 예외를 던지지 않는다**
>
> `HttpClient`는 **HTTP 오류 상태 코드를 예외로 바꾸지 않는다**. 404도, 500도 정상 반환이다. `EnsureSuccessStatusCode()`를 명시적으로 호출해야 예외가 된다.
>
> 반면 **통신 오류와 DNS 오류는 예외를 던진다**. 연결 거부, 이름 해석 실패, TLS 핸드셰이크 실패는 `HttpRequestException`이 된다.
>
> 이 구분은 의도된 설계다. HTTP 상태 코드는 "프로토콜이 정상 동작한 결과"이고, 예외는 "프로토콜이 동작하지 못한 사건"이다. 그러나 이 구분을 모르는 코드는 `GetStringAsync`(내부에서 `EnsureSuccessStatusCode`를 호출한다)와 `GetAsync`가 오류를 다르게 다룬다는 사실에 걸려 넘어진다.

.NET 5부터 `HttpRequestException.StatusCode`가 생겨서, 예외만 잡고도 어떤 상태 코드였는지 알 수 있다. .NET 8은 `HttpRequestError` 열거형(`HttpRequestException.HttpRequestError`)을 추가해 "연결 실패인지, 이름 해석 실패인지, 응답이 잘렸는지"를 구조적으로 구분할 수 있게 했다 ※.NET 8.

```csharp
try
{
    using var res = await client.GetAsync (url);
    res.EnsureSuccessStatusCode();
}
catch (HttpRequestException ex) when (ex.StatusCode == HttpStatusCode.NotFound)
{
    // 자원이 없는 정상 시나리오
}
catch (HttpRequestException ex)   // 통신 오류 또는 그 밖의 실패 상태 코드
{
    logger.LogWarning (ex, "요청 실패: {Url}", url);
}
```

### 본문 읽기 — `HttpContent`

`HttpContent`는 본문을 여러 형태로 읽어 준다.

| 메서드 | 반환 | 비고 |
|---|---|---|
| `ReadAsStringAsync()` | `Task<string>` | 인코딩을 `Content-Type`의 charset에서 추론 |
| `ReadAsByteArrayAsync()` | `Task<byte[]>` | 전체를 배열로 |
| `ReadAsStreamAsync()` | `Task<Stream>` | 스트리밍 읽기 |
| `ReadAsStream()` | `Stream` | 동기 ※.NET 5 |
| `CopyToAsync(stream)` | `Task` | 다른 스트림으로 바로 복사 |

파일로 저장하거나 JSON 응답을 객체로 바로 받는 전형적인 코드는 이렇다. 후자의 확장 메서드는 `System.Net.Http.Json`에 있고, 직렬화 옵션과 소스 생성기 연동은 41.2절·41.6절에서 다룬다.

```csharp
using (var fileStream = File.Create ("linqpad.html"))
    await response.Content.CopyToAsync (fileStream);

Product[]? items = await client.GetFromJsonAsync<Product[]> ("api/products");
```

### 대용량 응답을 스트리밍하기 — `HttpCompletionOption`

기본적으로 `GetAsync`가 반환하는 태스크는 **응답 본문 전체를 버퍼링한 뒤에** 완료된다. 500MB짜리 파일을 받으면 그 500MB가 메모리에 올라간 뒤에야 코드가 이어진다.

`HttpCompletionOption.ResponseHeadersRead`를 넘기면 **헤더만 도착한 시점에** 태스크가 완료된다.

```csharp
using HttpResponseMessage res = await client.GetAsync (
    url, HttpCompletionOption.ResponseHeadersRead, cancellationToken);

res.EnsureSuccessStatusCode();

// 이제 Content-Length를 보고 진행률을 계산할 수 있다
long? total = res.Content.Headers.ContentLength;

await using Stream net = await res.Content.ReadAsStreamAsync (cancellationToken);
await using FileStream file = File.Create (path);
await net.CopyToAsync (file, cancellationToken);
```

| 옵션 | 태스크 완료 시점 | 메모리 사용 | 용도 |
|---|---|---|---|
| `ResponseContentRead`(기본) | 본문까지 전부 수신 | 본문 크기만큼 | 작은 JSON·HTML 응답 |
| `ResponseHeadersRead` | 헤더만 수신 | 복사 버퍼만큼 | 대용량 다운로드, 진행률 표시, 서버 전송 이벤트 |

> **⚠️ `ResponseHeadersRead`를 쓰면 `Dispose`가 필수가 된다**
>
> 기본 모드에서는 본문이 이미 다 읽혔으므로 `HttpResponseMessage`를 해제하지 않아도 연결이 풀로 돌아간다. 그러나 `ResponseHeadersRead` 모드에서는 **응답 스트림이 아직 살아 있는 연결을 붙들고 있다**. `using`으로 감싸지 않으면 그 연결이 풀로 반환되지 않고, 요청이 반복되면 커넥션 풀이 말라붙어 이후 요청이 큐에서 대기한다.
>
> 증상은 "처음 몇십 번은 빠르다가 갑자기 전부 느려진다"로 나타난다. 원인 추적이 매우 어려운 부류의 버그다. `ResponseHeadersRead`를 쓰는 곳에서는 응답과 스트림을 모두 `using`으로 묶어라.

> **📌 `HttpClient`는 진행률 보고를 지원하지 않는다**
>
> `IProgress<T>` 같은 진행률 매개변수는 `HttpClient` API에 없다. 진행률이 필요하면 위처럼 `ResponseHeadersRead`로 스트림을 얻고, `Content-Length`와 지금까지 복사한 바이트 수를 직접 세면서 `CopyToAsync` 대신 손으로 루프를 돌린다. `IProgress<T>` 패턴 자체는 46.12절에서 다룬다.

### 타임아웃 — `Timeout`과 `CancellationToken`

`HttpClient.Timeout`의 기본값은 **100초**다. 그리고 중요한 성질이 하나 있다.

> **⚠️ `Timeout`은 요청 하나 전체에 적용된다**
>
> `HttpClient.Timeout`은 "연결 타임아웃"도 "읽기 타임아웃"도 아니다. **요청 시작부터 응답 완료까지의 총 시간**이다. 그래서 기본 모드(`ResponseContentRead`)에서 1GB짜리 파일을 받는 요청은 아무리 꾸준히 데이터가 흐르고 있어도 100초에 잘린다.
>
> 대용량 전송이 있는 클라이언트에서는 두 가지 중 하나를 택한다.
>
> 1. `Timeout`을 `Timeout.InfiniteTimeSpan`으로 두고, 호출마다 `CancellationTokenSource(TimeSpan)`으로 개별 시한을 건다.
> 2. `ResponseHeadersRead`를 쓴다. 이 모드에서는 헤더 수신까지만 `Timeout`이 적용되고, 이후 스트림 읽기는 별도의 취소 토큰으로 관리한다.

`Timeout`이 만료되면 어떤 예외가 나오는가는 런타임 버전에 따라 다르다. 오랫동안 `TaskCanceledException`이었고 — 취소가 아닌데 취소 예외가 나온다는 점 때문에 악명 높았다 — .NET 5부터는 그 `TaskCanceledException`의 `InnerException`에 `TimeoutException`이 들어간다. 그래서 "진짜 취소"와 "타임아웃"을 구분할 수 있다.

```csharp
using var cts = new CancellationTokenSource (TimeSpan.FromSeconds (5));
try { var res = await client.GetAsync (url, cts.Token); }
catch (OperationCanceledException) when (cts.IsCancellationRequested)
{ /* 내가 건 5초 시한에 걸렸다 */ }
catch (OperationCanceledException ex) when (ex.InnerException is TimeoutException)
{ /* HttpClient.Timeout에 걸렸다 — ※.NET 5 이상에서 구분 가능 */ }
```

`TaskCanceledException`은 `OperationCanceledException`을 상속하므로 위처럼 상위 타입으로 잡고 조건 필터로 갈라내는 편이 안전하다. 취소 프로토콜 자체는 46.8절에서, 타임아웃·재시도·취소를 결합하는 설계는 51.4절에서 다룬다.

### 나머지 인스턴스 프로퍼티

`HttpClient` 자체는 얇은 껍데기다. 대부분의 설정은 뒤에서 볼 `HttpMessageHandler` 쪽에 있고, 클라이언트에 직접 있는 것은 다음 정도다.

| 프로퍼티 | 설명 |
|---|---|
| `BaseAddress` | 모든 요청 앞에 붙는 기준 URI. 후행 슬래시 규칙 주의(43.3절) |
| `Timeout` | 요청 전체 시한. 기본 100초 |
| `DefaultRequestHeaders` | 모든 요청에 붙는 헤더 |
| `DefaultRequestVersion` | 기본 HTTP 버전 ※.NET 5 |
| `DefaultVersionPolicy` | 버전 협상 정책 ※.NET 5 |
| `MaxResponseContentBufferSize` | 버퍼링 모드에서의 본문 크기 상한 |

> **⚠️ `DefaultRequestHeaders`는 첫 요청 이후에 건드리면 안 된다**
>
> `HttpClient`는 동시 요청에 대해 안전하지만, 그것은 **요청을 보내는 동작**에 대한 이야기다. `DefaultRequestHeaders`·`BaseAddress`·`Timeout`은 요청이 진행 중일 때 변경하면 동작이 정의되지 않는다. 요청마다 다른 헤더가 필요하면 `DefaultRequestHeaders`를 고치지 말고 `HttpRequestMessage.Headers`를 쓴다(43.5절).
>
> 이 함정은 "요청마다 Bearer 토큰을 갈아 끼우는" 코드에서 특히 자주 터진다. 멀티스레드 환경에서 A 요청의 토큰이 B 요청에 실려 나가는, 재현하기 어려운 권한 사고가 된다.

### 성능 관점

- `GetStringAsync`는 본문 전체를 `string`으로 만든다. 문자열은 UTF-16이므로 UTF-8 본문 대비 **메모리가 대략 두 배**가 되고, 85KB를 넘으면 대형 객체 힙(LOH)에 들어간다(62장). JSON을 받아 곧바로 역직렬화할 것이라면 `GetFromJsonAsync`나 `ReadAsStreamAsync`로 문자열 단계를 건너뛰어라(41.9절).
- `EnsureSuccessStatusCode()`는 실패 시 예외를 만들면서 응답 본문 일부를 메시지에 담는다. 오류가 흔한 경로(예: 폴링)에서 예외를 제어 흐름으로 쓰면 비싸다. `IsSuccessStatusCode`로 분기하라.
- 응답 메시지 `Dispose`는 기본 모드에서 생략해도 대체로 무해하지만, `ResponseHeadersRead`로 바꾸는 순간 필수가 되므로 습관으로 `using`을 쓰는 편이 낫다.

## 43.5 `SendAsync`와 요청 메시지 직접 구성

### 모든 길은 `SendAsync`로 통한다

`GetAsync`, `PostAsync`, `PutAsync`, `DeleteAsync`, `PatchAsync`는 전부 `SendAsync`의 단축이다. `SendAsync`는 모든 것이 모여드는 단 하나의 저수준 메서드다.

```csharp
var client = new HttpClient();
var request = new HttpRequestMessage (HttpMethod.Get, "http://...");
HttpResponseMessage response = await client.SendAsync (request);
response.EnsureSuccessStatusCode();
```

`HttpRequestMessage`를 직접 만드는 이유는 요청의 세부 — 헤더, 콘텐츠, HTTP 버전, 단축 메서드가 없는 HTTP 메서드 — 를 제어하기 위해서다.

```text
    client.GetAsync(uri)         client.PostAsync(uri, content)
            │                              │
            └──────────────┬───────────────┘
                           ▼
              new HttpRequestMessage(method, uri) { Content = ... }
                           │
                           ▼
                  client.SendAsync(request, completionOption, ct)
                           │
                           ▼
              ┌────────────────────────────┐
              │  DelegatingHandler 체인     │  ← 43.7절
              │  (로깅 · 재시도 · 인증)      │
              └────────────┬───────────────┘
                           ▼
              ┌────────────────────────────┐
              │  SocketsHttpHandler        │  커넥션 풀 · TLS · 압축
              └────────────┬───────────────┘
                           ▼
                        Socket
```

### `HttpMethod`

```csharp
var req = new HttpRequestMessage (HttpMethod.Patch, "api/items/42");
```

| 정적 프로퍼티 | 메서드 | 단축 메서드 |
|---|---|---|
| `HttpMethod.Get` | GET | `GetAsync` |
| `HttpMethod.Post` | POST | `PostAsync` |
| `HttpMethod.Put` | PUT | `PutAsync` |
| `HttpMethod.Delete` | DELETE | `DeleteAsync` |
| `HttpMethod.Patch` | PATCH | `PatchAsync` |
| `HttpMethod.Head` | HEAD | 없음 |
| `HttpMethod.Options` | OPTIONS | 없음 |
| `HttpMethod.Trace` | TRACE | 없음 |

표준에 없는 메서드는 `new HttpMethod("PURGE")` 처럼 만든다.

### HTTP 버전과 버전 정책

.NET 5부터 요청 단위로 HTTP 버전과 협상 실패 시의 동작을 지정할 수 있다.

```csharp
var req = new HttpRequestMessage (HttpMethod.Get, url)
{
    Version = HttpVersion.Version20,
    VersionPolicy = HttpVersionPolicy.RequestVersionOrLower
};
```

| `HttpVersionPolicy` | 동작 |
|---|---|
| `RequestVersionOrLower`(기본) | 요청 버전으로 시도하고, 안 되면 더 낮은 버전으로 내려간다 |
| `RequestVersionOrHigher` | 요청 버전 이상으로 협상한다. 서버가 더 높은 버전을 지원하면 올라간다 |
| `RequestVersionExact` | 정확히 그 버전이어야 한다. 아니면 요청이 실패한다 |

`HttpVersion.Version11`, `Version20`, `Version30`(※.NET 6) 상수를 쓴다. HTTP/3를 강제하려면 `Version30` + `RequestVersionExact` 조합이다. 버전별 성능 차이는 43.15절에서 다룬다.

클라이언트 전체의 기본값은 `client.DefaultRequestVersion`, `client.DefaultVersionPolicy`로 설정한다.

> **⚠️ `Version`을 올린다고 HTTP/2가 되지는 않는다**
>
> HTTP/2는 TLS 위에서 ALPN으로 협상된다. `https://`가 아닌 평문 URL에 `Version20`을 지정하면 대부분 HTTP/1.1로 떨어진다(사전 지식 없는 h2c 업그레이드는 지원되지 않는다). 실제로 어떤 버전이 쓰였는지는 **응답의 `Version` 프로퍼티**로 확인하라. 요청의 `Version`은 희망 사항일 뿐이다.
>
> ```csharp
> Console.WriteLine (response.Version);   // 실제 사용된 버전
> ```

### 요청 메시지는 한 번만 보낼 수 있다

```csharp
var req = new HttpRequestMessage (HttpMethod.Get, url);
await client.SendAsync (req);
await client.SendAsync (req);   // InvalidOperationException
```

> **⚠️ `HttpRequestMessage`는 재사용 불가다**
>
> 이미 전송된 `HttpRequestMessage`를 다시 보내면 `InvalidOperationException`이 난다("The request message was already sent"). 재시도 로직을 짤 때 가장 먼저 만나는 벽이다.
>
> 해결은 **요청을 값이 아니라 팩터리로 다루는 것**이다.
>
> ```csharp
> async Task<HttpResponseMessage> SendWithRetryAsync (
>     HttpClient client, Func<HttpRequestMessage> factory, int attempts)
> {
>     for (int i = 1; ; i++)
>     {
>         using var req = factory();          // 매 시도마다 새 메시지
>         var res = await client.SendAsync (req);
>         if (res.IsSuccessStatusCode || i == attempts) return res;
>         res.Dispose();
>         await Task.Delay (TimeSpan.FromMilliseconds (200 * (1 << i)));
>     }
> }
> ```
>
> 콘텐츠도 마찬가지다. `StreamContent`는 스트림을 이미 소비했기 때문에 재전송 시 빈 본문이 나간다(43.6절). 재시도가 필요한 경로에서는 콘텐츠도 매번 새로 만든다.

### 요청 헤더 vs 콘텐츠 헤더

`HttpRequestMessage`에는 `Headers`가 있고, `HttpContent`에도 `Headers`가 있다. **다른 컬렉션이다.**

```csharp
var req = new HttpRequestMessage (HttpMethod.Post, url);
req.Headers.Add ("X-Request-Id", Guid.NewGuid().ToString());     // 요청 헤더
req.Content = new StringContent ("{}");
req.Content.Headers.ContentType =
    new MediaTypeHeaderValue ("application/json") { CharSet = "utf-8" };  // 콘텐츠 헤더
```

> **⚠️ `Content-Type`을 요청 헤더에 넣으면 예외가 난다**
>
> ```csharp
> req.Headers.Add ("Content-Type", "application/json");
> // InvalidOperationException: Misused header name.
> // 'Content-Type' is a content header.
> ```
>
> HTTP 사양이 헤더를 "메시지에 대한 것"과 "본문(엔터티)에 대한 것"으로 나눈다. .NET은 이 구분을 타입 체계로 강제한다. 어느 쪽에 넣어야 하는지 모를 때는 다음 표를 본다.
>
> | 헤더 | 소속 | .NET 접근 경로 |
> |---|---|---|
> | `Accept`, `Accept-Encoding`, `Accept-Language` | 요청 | `req.Headers.Accept` |
> | `Authorization` | 요청 | `req.Headers.Authorization` |
> | `User-Agent` | 요청 | `req.Headers.UserAgent` |
> | `If-None-Match`, `If-Modified-Since` | 요청 | `req.Headers.IfNoneMatch` |
> | `Content-Type` | 콘텐츠 | `req.Content.Headers.ContentType` |
> | `Content-Length` | 콘텐츠 | `req.Content.Headers.ContentLength` |
> | `Content-Encoding` | 콘텐츠 | `req.Content.Headers.ContentEncoding` |
> | `Content-Disposition` | 콘텐츠 | `req.Content.Headers.ContentDisposition` |
> | `ETag`, `Location` | 응답 | `res.Headers.ETag` |
> | `Last-Modified`, `Expires` | 응답 콘텐츠 | `res.Content.Headers.LastModified` |
>
> 커스텀 헤더(`X-`로 시작하는 것들)는 대개 요청 헤더다.

`TryAddWithoutValidation`은 검증을 건너뛰고 헤더를 추가한다. 사양에 어긋나는 헤더를 서버가 요구할 때의 탈출구다.

```csharp
req.Headers.TryAddWithoutValidation ("X-Weird-Header", "value with \"quotes\"");
```

### `HttpRequestOptions` — 파이프라인에 데이터 전달하기

핸들러 체인(43.7절)에 요청별 메타데이터를 전달해야 할 때가 있다. "이 요청은 재시도하지 마라", "이 요청의 상관 ID는 이것이다" 같은 정보다.

.NET 5부터 `HttpRequestMessage.Options`가 그 통로다. 형식 안전한 키를 쓴다.

```csharp
static readonly HttpRequestOptionsKey<bool> NoRetryKey = new ("NoRetry");

var req = new HttpRequestMessage (HttpMethod.Post, url);   // 호출 측
req.Options.Set (NoRetryKey, true);

if (request.Options.TryGetValue (NoRetryKey, out bool noRetry) && noRetry)  // 핸들러 측
    return await base.SendAsync (request, ct);
```

이전의 `HttpRequestMessage.Properties`(`IDictionary<string, object?>`)는 폐기됐다. 문자열 키와 `object` 값이라 오타와 캐스팅 오류를 잡을 수 없었기 때문이다.

### 성능 관점

- `HttpRequestMessage`와 `HttpResponseMessage`는 둘 다 `IDisposable`이다. 요청 메시지의 `Dispose`는 콘텐츠를 해제한다. 짧은 수명의 요청에서 생략해도 치명적이지 않지만, `StreamContent`를 쓴다면 원본 스트림이 함께 닫히므로 수명을 의식해야 한다.
- 헤더 컬렉션은 지연 생성된다. `req.Headers`를 건드리는 순간 딕셔너리가 만들어지므로, 헤더를 붙이지 않는 요청은 그 비용이 없다.
- `DefaultRequestHeaders`에 넣은 헤더는 요청마다 다시 만들지 않고 캐시된 표현을 쓴다. 모든 요청에 공통으로 붙는 헤더(예: `User-Agent`, API 키)는 요청 메시지가 아니라 클라이언트 기본 헤더에 두는 편이 빠르다.

## 43.6 데이터 업로드와 `HttpContent` 종류

### `HttpContent` 계층

`HttpRequestMessage.Content`에 대입하는 값의 타입은 추상 클래스 `HttpContent`다. .NET은 여러 구체 서브클래스를 제공하며, 직접 만들 수도 있다.

| 타입 | 담는 것 | 기본 `Content-Type` | 네임스페이스 |
|---|---|---|---|
| `StringContent` | 문자열 | `text/plain; charset=utf-8` | `System.Net.Http` |
| `ByteArrayContent` | `byte[]` | 없음(직접 설정) | `System.Net.Http` |
| `ReadOnlyMemoryContent` | `ReadOnlyMemory<byte>` | 없음 | `System.Net.Http` |
| `StreamContent` | `Stream` | 없음 | `System.Net.Http` |
| `FormUrlEncodedContent` | 키/값 쌍 | `application/x-www-form-urlencoded` | `System.Net.Http` |
| `MultipartFormDataContent` | 여러 파트 + 파트별 이름 | `multipart/form-data; boundary=...` | `System.Net.Http` |
| `MultipartContent` | 여러 파트 | `multipart/mixed; boundary=...` | `System.Net.Http` |
| `JsonContent` | 객체(직렬화됨) | `application/json; charset=utf-8` | `System.Net.Http.Json` |

가장 단순한 예는 문자열을 그대로 보내는 것이다.

```csharp
var client = new HttpClient (new HttpClientHandler { UseProxy = false });
var request = new HttpRequestMessage (
    HttpMethod.Post, "http://www.albahari.com/EchoPost.aspx");
request.Content = new StringContent ("This is a test");

HttpResponseMessage response = await client.SendAsync (request);
response.EnsureSuccessStatusCode();
Console.WriteLine (await response.Content.ReadAsStringAsync());
```

### Content-Type을 제대로 붙이기

`StringContent`의 기본 미디어 타입은 `text/plain`이다. JSON을 보내면서 이걸 그대로 두면 서버가 415 Unsupported Media Type을 돌려준다.

```csharp
var c1 = new StringContent (json, Encoding.UTF8, "application/json");  // 생성자에서

var c2 = new StringContent (json);                                     // 나중에
c2.Headers.ContentType = new MediaTypeHeaderValue ("application/json") { CharSet = "utf-8" };
```

`JsonContent`를 쓰면 직렬화와 헤더가 한 번에 처리된다.

```csharp
using System.Net.Http.Json;

var res  = await client.PostAsync ("api/orders",
               JsonContent.Create (new Order { Id = 7, Total = 12.5m }));
var res2 = await client.PostAsJsonAsync ("api/orders", new Order { Id = 7 });  // 더 짧게
```

직렬화 옵션·소스 생성기와의 조합은 41.2절·41.6절에서 다룬다.

> **⚠️ `charset=utf-8`이 붙어서 문제가 되는 서버가 있다**
>
> `new StringContent(json, Encoding.UTF8, "application/json")`은 헤더를 `application/json; charset=utf-8`로 만든다. 사양상 정당하지만, 일부 오래된 서버와 서명 검증 로직(특히 정확한 Content-Type 문자열로 서명을 계산하는 결제 API)이 이 파라미터 때문에 요청을 거부한다.
>
> 파라미터 없이 보내야 한다면 헤더를 직접 만든다.
>
> ```csharp
> var c = new StringContent (json);
> c.Headers.ContentType = new MediaTypeHeaderValue ("application/json");  // charset 없음
> ```
>
> 다만 이 경우 서버는 본문 인코딩을 추측해야 한다. 사양상 `application/json`의 기본 인코딩은 UTF-8이므로 대개 문제가 없다.

### 폼 데이터

HTML 폼과 같은 형식으로 보내려면 `FormUrlEncodedContent`를 만들어 `PostAsync`에 넘기거나 요청의 `Content`에 대입한다.

```csharp
string uri = "http://www.albahari.com/EchoPost.aspx";
var client = new HttpClient();
var dict = new Dictionary<string,string>
{
    { "Name", "Joe Albahari" },
    { "Company", "O'Reilly" }
};
var values = new FormUrlEncodedContent (dict);
var response = await client.PostAsync (uri, values);
response.EnsureSuccessStatusCode();
Console.WriteLine (await response.Content.ReadAsStringAsync());
```

`FormUrlEncodedContent`는 키와 값을 `application/x-www-form-urlencoded` 규칙으로 인코딩한다 — 공백은 `+`, 나머지 비안전 문자는 퍼센트 인코딩이다. 직접 인코딩하지 마라. 이중 인코딩이 되어 서버가 `%2520` 같은 값을 받게 된다.

> **⚠️ `FormUrlEncodedContent`는 큰 본문에서 실패한다**
>
> 이 타입은 내부적으로 인코딩된 문자열을 만들면서 길이 제한에 부딪힐 수 있다. 폼 필드에 수 MB짜리 텍스트를 담아야 한다면 `FormUrlEncodedContent` 대신 직접 인코딩한 문자열로 `StringContent`를 만들고 미디어 타입을 `application/x-www-form-urlencoded`로 지정하는 편이 안전하다. 애초에 그 크기의 데이터를 폼 인코딩으로 보내는 설계 자체를 의심해야 한다 — `multipart/form-data`나 JSON이 맞다.

### 파일 업로드 — `MultipartFormDataContent`

파일과 필드를 함께 보내는 표준 방식이다.

```csharp
using var form = new MultipartFormDataContent();
form.Add (new StringContent ("2026-09-07"), "uploadedOn");     // 일반 필드

await using var fs = File.OpenRead (@"C:\reports\q3.pdf");     // 파일 파트
var fileContent = new StreamContent (fs);
fileContent.Headers.ContentType = new MediaTypeHeaderValue ("application/pdf");
form.Add (fileContent, name: "file", fileName: "q3.pdf");

using var res = await client.PostAsync ("api/upload", form);
res.EnsureSuccessStatusCode();
```

`Add(content, name, fileName)` 오버로드가 `Content-Disposition: form-data; name="file"; filename="q3.pdf"` 헤더를 만들어 준다.

> **⚠️ `MultipartFormDataContent`를 `Dispose`하면 파트도 함께 죽는다**
>
> `MultipartFormDataContent.Dispose()`는 추가된 모든 파트를 해제하고, `StreamContent`의 해제는 **감싼 스트림을 닫는다**. 그래서 위 코드에서 `fs`를 별도로 `using`했더라도 이중 해제가 아니라 순서 문제로 이어질 수 있다. 파트에 넣은 스트림을 업로드 후에도 계속 쓸 계획이라면 `MemoryStream`으로 복사해서 넣거나, `StreamContent`가 스트림을 소유하도록 설계를 정리하라.

> **⚠️ `StreamContent`는 한 번만 읽힌다**
>
> 재시도·리다이렉트·인증 재협상이 일어나면 `HttpClient`는 요청 본문을 **다시 보내야 한다**. `ByteArrayContent`나 `StringContent`는 메모리에 데이터가 있으니 문제가 없지만, `StreamContent`가 감싼 스트림은 이미 끝까지 읽혀 있다. 되감을 수 없는 스트림(네트워크 스트림, 압축 스트림)이라면 두 번째 전송에서 **빈 본문이 나가거나 예외가 난다**.
>
> 증상이 특히 고약한 경우는 401 → 인증 헤더 추가 → 재전송 흐름이다. 첫 요청은 본문을 다 소비하고 401을 받고, 재전송은 빈 본문으로 200을 받는다. 서버에는 빈 파일이 저장된다.
>
> 재시도 가능성이 있는 경로에서는 (1) 본문을 `byte[]`로 미리 읽어 `ByteArrayContent`를 쓰거나, (2) 43.5절처럼 콘텐츠를 매번 새로 만드는 팩터리를 쓴다.

### 콘텐츠 길이와 청크 전송

`Content-Length`를 미리 알 수 있으면 그대로 보내고, 알 수 없으면 HTTP/1.1의 청크 전송 인코딩을 쓴다.

```csharp
// 길이를 모르는 스트림 → 청크 전송
req.Headers.TransferEncodingChunked = true;
req.Content = new StreamContent (nonSeekableStream);
```

`StreamContent`는 스트림이 `CanSeek`이면 `Length`에서 `Content-Length`를 계산한다. 그렇지 않으면 청크 전송이 필요하다. 일부 서버와 프록시는 청크 요청 본문을 거부하므로, 상대가 받아 주는지 확인해야 한다.

### 커스텀 `HttpContent`

`HttpContent`를 직접 상속하면 "필요할 때 데이터를 만들어 내보내는" 콘텐츠를 만들 수 있다. 큰 데이터를 메모리에 올리지 않고 곧바로 직렬화해서 소켓으로 흘려보내는 용도다.

```csharp
sealed class CsvContent<T> : HttpContent
{
    readonly IEnumerable<T> _rows;
    readonly Func<T,string> _fmt;

    public CsvContent (IEnumerable<T> rows, Func<T,string> fmt)
    { _rows = rows; _fmt = fmt; Headers.ContentType = new ("text/csv"); }

    protected override async Task SerializeToStreamAsync (
        Stream stream, TransportContext? context)
    {
        await using var w = new StreamWriter (stream, leaveOpen: true);
        foreach (T row in _rows) await w.WriteLineAsync (_fmt (row));
    }

    // 길이를 미리 알 수 없다 → 청크 전송으로 나간다
    protected override bool TryComputeLength (out long length) { length = 0; return false; }
}
```

`TryComputeLength`가 `false`를 반환하면 런타임이 청크 전송을 선택한다. `SerializeToStreamAsync`는 재전송 시 **다시 호출된다** — 그래서 `_rows`가 한 번만 열거 가능한 시퀀스라면 위 코드도 `StreamContent`와 같은 함정에 빠진다. 재열거 가능한 컬렉션을 요구하도록 설계하라.

### 성능 관점

| 상황 | 나쁜 선택 | 나은 선택 |
|---|---|---|
| 이미 UTF-8 바이트로 가진 JSON | `new StringContent(Encoding.UTF8.GetString(bytes))` | `new ByteArrayContent(bytes)` + 미디어 타입 지정 |
| 객체를 JSON으로 보내기 | `JsonSerializer.Serialize` → `StringContent` | `JsonContent.Create` / `PostAsJsonAsync` |
| 대용량 파일 업로드 | `File.ReadAllBytes` → `ByteArrayContent` | `StreamContent(File.OpenRead(...))` |
| 짧은 바이트 조각 | `ByteArrayContent(array.ToArray())` | `ReadOnlyMemoryContent(memory)` |

`StringContent`는 문자열을 UTF-8로 다시 인코딩하는 과정에서 바이트 배열을 새로 만든다. 이미 바이트를 갖고 있다면 문자열을 거치는 왕복이 순수한 낭비다. 41.9절에서 본 "문자열을 거치지 않는다"는 규칙이 네트워크 경계에서도 똑같이 적용된다.

## 43.7 `HttpMessageHandler`와 파이프라인, `IHttpClientFactory`

### 핸들러라는 확장점

앞에서 요청을 커스터마이즈하는 프로퍼티 대부분이 `HttpClient`가 아니라 `HttpClientHandler`에 있다고 했다. `HttpClientHandler`는 추상 클래스 `HttpMessageHandler`의 서브클래스이며, 그 정의는 놀랄 만큼 단순하다.

```csharp
public abstract class HttpMessageHandler : IDisposable
{
    protected internal abstract Task<HttpResponseMessage> SendAsync
      (HttpRequestMessage request, CancellationToken cancellationToken);

    public void Dispose();
    protected virtual void Dispose (bool disposing);
}
```

`HttpClient.SendAsync`가 이 메서드를 호출한다. 메서드 하나짜리 추상 클래스이므로 상속이 쉽고, 이것이 `HttpClient`의 확장점이 된다.

핸들러를 클라이언트에 붙이는 방법은 생성자다.

```csharp
var handler = new HttpClientHandler { UseProxy = false };
var client = new HttpClient (handler);
```

위 예에서는 프록시 지원을 껐다. 자동 프록시 탐지 비용이 사라져 성능이 나아지는 경우가 있다.

### 단위 테스트와 모킹

`HttpMessageHandler`를 상속해서 목 핸들러를 만들면 네트워크 없이 `HttpClient`를 쓰는 코드를 테스트할 수 있다.

```csharp
class MockHandler : HttpMessageHandler
{
    Func<HttpRequestMessage, HttpResponseMessage> _responseGenerator;

    public MockHandler
      (Func<HttpRequestMessage, HttpResponseMessage> responseGenerator)
    {
        _responseGenerator = responseGenerator;
    }

    protected override Task<HttpResponseMessage> SendAsync
      (HttpRequestMessage request, CancellationToken cancellationToken)
    {
        cancellationToken.ThrowIfCancellationRequested();
        var response = _responseGenerator (request);
        response.RequestMessage = request;
        return Task.FromResult (response);
    }
}
```

생성자가 "요청에서 응답을 만드는 함수"를 받는 구조라, 같은 핸들러로 여러 요청을 테스트할 수 있다. 응답 생성 함수는 짧게 끝날 것이므로 `Task.FromResult`로 동기 완료시켜도 무방하다.

```csharp
var mocker = new MockHandler (request =>
    new HttpResponseMessage (HttpStatusCode.OK)
    {
        Content = new StringContent ("You asked for " + request.RequestUri)
    });

var client = new HttpClient (mocker);
var response = await client.GetAsync ("http://www.linqpad.net");
string result = await response.Content.ReadAsStringAsync();
Assert.AreEqual ("You asked for http://www.linqpad.net/", result);
```

(`Assert.AreEqual`은 NUnit 같은 단위 테스트 프레임워크의 메서드다. 테스트 설계 전반은 80장에서 다룬다.)

### `DelegatingHandler`로 체인 만들기

다른 핸들러를 호출하는 핸들러가 `DelegatingHandler`다. 이것을 상속하면 요청·응답 파이프라인을 만들 수 있다. 커스텀 인증, 압축, 암호화 프로토콜이 전형적인 용도다.

```csharp
class LoggingHandler : DelegatingHandler
{
    public LoggingHandler (HttpMessageHandler nextHandler)
    {
        InnerHandler = nextHandler;
    }

    protected async override Task<HttpResponseMessage> SendAsync
      (HttpRequestMessage request, CancellationToken cancellationToken)
    {
        Console.WriteLine ("Requesting: " + request.RequestUri);
        var response = await base.SendAsync (request, cancellationToken);
        Console.WriteLine ("Got response: " + response.StatusCode);
        return response;
    }
}
```

`SendAsync`를 재정의하면서 `async`를 붙이는 것은 정당하며, 이 경우 바람직하다. `base.SendAsync`가 반환한 태스크를 그대로 돌려주지 않고 결과를 관찰해야 하기 때문이다.

실무에서는 `Console.WriteLine` 대신 로깅 객체를 주입받거나, 요청·응답을 어떻게 기록할지 알려 주는 `Action<T>` 델리게이트 두 개를 받는 편이 낫다.

```text
   HttpClient.SendAsync
        │
        ▼
   ┌─────────────────────┐
   │ CorrelationHandler  │  X-Correlation-Id 부여
   ├─────────────────────┤
   │ AuthHandler         │  토큰 주입, 401 시 갱신 후 1회 재시도
   ├─────────────────────┤
   │ RetryHandler        │  5xx·타임아웃 시 지수 백오프
   ├─────────────────────┤
   │ LoggingHandler      │  실제 전송 직전/직후를 기록
   ├─────────────────────┤
   │ SocketsHttpHandler  │  ← 체인의 끝(primary handler) → Socket
   └─────────────────────┘
```

체인의 **순서가 의미를 결정한다**. 위 배치에서 로깅 핸들러는 재시도 안쪽에 있으므로 재시도 횟수만큼 로그가 남는다. 밖으로 빼면 논리적 요청 하나당 한 줄만 남는다. 인증 핸들러가 재시도 바깥에 있으면 토큰 갱신이 재시도마다 반복되지 않는다.

인증 핸들러의 전형적인 형태는 이렇다.

```csharp
sealed class BearerTokenHandler : DelegatingHandler
{
    readonly ITokenProvider _tokens;
    public BearerTokenHandler (ITokenProvider tokens) => _tokens = tokens;

    protected override async Task<HttpResponseMessage> SendAsync (
        HttpRequestMessage request, CancellationToken ct)
    {
        request.Headers.Authorization =
            new AuthenticationHeaderValue ("Bearer", await _tokens.GetAsync (ct));

        var response = await base.SendAsync (request, ct);

        if (response.StatusCode != HttpStatusCode.Unauthorized)
            return response;

        // 토큰 만료로 보고 한 번만 갱신 후 재시도
        response.Dispose();
        await _tokens.InvalidateAsync (ct);

        // ⚠️ 같은 request 객체는 재사용할 수 없다 — 복제가 필요하다
        using var retry = CloneRequest (request);
        retry.Headers.Authorization =
            new AuthenticationHeaderValue ("Bearer", await _tokens.GetAsync (ct));
        return await base.SendAsync (retry, ct);
    }

    static HttpRequestMessage CloneRequest (HttpRequestMessage req)
    {
        var clone = new HttpRequestMessage (req.Method, req.RequestUri)
                    { Version = req.Version, Content = req.Content };
        foreach (var h in req.Headers)
            clone.Headers.TryAddWithoutValidation (h.Key, h.Value);
        return clone;
    }
}
```

> **⚠️ 핸들러 안에서 요청을 재전송할 때의 두 가지 함정**
>
> 1. **요청 메시지 재사용 불가** — 위 코드가 `CloneRequest`를 쓰는 이유다(43.5절).
> 2. **콘텐츠 재소비 불가** — 복제본이 원본과 같은 `HttpContent` 인스턴스를 가리키면, 그 콘텐츠가 `StreamContent`인 경우 두 번째 전송에서 빈 본문이 나간다(43.6절). 재시도 핸들러를 쓰는 파이프라인에서는 "본문 있는 요청은 메모리 기반 콘텐츠만 허용한다"를 규약으로 두는 편이 안전하다.

### `SocketsHttpHandler` — 실제 일을 하는 핸들러

.NET Core 2.1부터 HTTP 스택은 완전히 관리 코드로 다시 쓰였고, 그 구현이 `SocketsHttpHandler`다. `HttpClientHandler`는 이제 플랫폼 중립 파사드로, 내부적으로 `SocketsHttpHandler`에 위임한다. 세밀한 제어가 필요하면 `SocketsHttpHandler`를 직접 쓴다.

```csharp
var handler = new SocketsHttpHandler
{
    PooledConnectionLifetime    = TimeSpan.FromMinutes (2),
    PooledConnectionIdleTimeout = TimeSpan.FromSeconds (30),
    MaxConnectionsPerServer     = 20,
    AutomaticDecompression      = DecompressionMethods.All,   // ※.NET 5
    AllowAutoRedirect           = true,
    ConnectTimeout              = TimeSpan.FromSeconds (5),
};
var client = new HttpClient (handler);
```

| 옵션 | 역할 | 기본값 |
|---|---|---|
| `PooledConnectionLifetime` | 풀의 연결이 살아 있을 최대 시간. DNS 변경 추적의 핵심(43.9절) | 무한 |
| `PooledConnectionIdleTimeout` | 유휴 연결을 닫기까지의 시간 | 1분(문서 기준) |
| `MaxConnectionsPerServer` | 서버당 동시 연결 상한 | `int.MaxValue` |
| `AutomaticDecompression` | gzip·deflate·brotli 자동 해제 | `None` |
| `AllowAutoRedirect` | 3xx 자동 추적 | `true` |
| `MaxAutomaticRedirections` | 리다이렉트 추적 횟수 상한 | 50 |
| `UseCookies` / `CookieContainer` | 쿠키 처리 | `true` / 새 컨테이너 |
| `UseProxy` / `Proxy` | 프록시 사용 여부와 지정 | `true` / 시스템 기본 |
| `Credentials` / `PreAuthenticate` | 인증(43.8절) | `null` / `false` |
| `ConnectTimeout` | TCP 연결 수립까지의 시한 | 무한 |
| `Expect100ContinueTimeout` | 100-continue 대기 시간 | 1초 |
| `SslOptions` | TLS 세부 설정(44장) | 기본값 |
| `ConnectCallback` | 연결 수립을 직접 구현 ※.NET 5 | `null` |
| `EnableMultipleHttp2Connections` | HTTP/2 스트림 상한 초과 시 연결 추가 | `false` |

> **📌 `ConnectCallback`으로 할 수 있는 일**
>
> ※.NET 5에서 추가된 `SocketsHttpHandler.ConnectCallback`은 "이 호스트·포트로의 연결을 어떻게 만들지"를 직접 구현하게 해 준다. 이것으로 유닉스 도메인 소켓 위의 HTTP, 사설 DNS 해석, 특정 로컬 인터페이스 바인딩, 연결 단계 계측 같은 것이 가능해진다.
>
> ```csharp
> handler.ConnectCallback = async (ctx, ct) =>
> {
>     var socket = new Socket (SocketType.Stream, ProtocolType.Tcp)
>                  { NoDelay = true };
>     await socket.ConnectAsync (ctx.DnsEndPoint, ct);
>     return new NetworkStream (socket, ownsSocket: true);
> };
> ```

> **⚠️ `AutomaticDecompression`은 기본이 꺼져 있다**
>
> 브라우저와 달리 `HttpClient`는 기본적으로 `Accept-Encoding`을 보내지 않고 압축도 풀지 않는다. 응답이 gzip으로 오면 그대로 바이트가 넘어온다. 큰 JSON을 반복해서 받는 클라이언트라면 `AutomaticDecompression`을 켜는 것만으로 대역폭이 수 배 줄어드는 경우가 흔하다. 대신 CPU가 든다 — 이미 압축된 데이터(이미지, 동영상)를 받는 경로에서는 이득이 없다.

### `IHttpClientFactory`

핸들러 수명 관리, 파이프라인 구성, 이름별 설정을 한곳에서 처리하기 위해 ASP.NET Core 2.1에서 도입된 것이 `IHttpClientFactory`다(패키지: `Microsoft.Extensions.Http`). Microsoft가 개발자들의 `HttpClient` 오용을 인지하고 모범 사례를 강제하기 위해 만든 장치다.

**명명 클라이언트(named client)** 는 이름으로 설정을 구분한다.

```csharp
builder.Services.AddHttpClient (name: "Northwind.WebApi",
  configureClient: options =>
  {
      options.BaseAddress = new Uri ("https://localhost:5151/");
      options.DefaultRequestHeaders.Accept.Add (
        new MediaTypeWithQualityHeaderValue (
          mediaType: "application/json", quality: 1.0));
  });
```

주입받는 쪽은 `IHttpClientFactory`에서 이름으로 꺼낸다.

```csharp
public async Task<IActionResult> Customers (string country)   // MVC 컨트롤러 안
{
    string uri = string.IsNullOrEmpty (country)
        ? "api/customers"
        : $"api/customers/?country={Uri.EscapeDataString (country)}";

    HttpClient client = _clientFactory.CreateClient (name: "Northwind.WebApi");
    HttpRequestMessage request = new (method: HttpMethod.Get, requestUri: uri);
    HttpResponseMessage response = await client.SendAsync (request);

    IEnumerable<Customer>? model = await response.Content
        .ReadFromJsonAsync<IEnumerable<Customer>>();
    return View (model);
}
```

**형식화 클라이언트(typed client)** 는 한 걸음 더 나아가, 클라이언트를 감싼 전용 서비스 타입을 등록한다.

```csharp
public class NorthwindApi
{
    readonly HttpClient _http;
    public NorthwindApi (HttpClient http) => _http = http;

    public Task<Customer[]?> GetCustomersAsync (string? country = null) =>
        _http.GetFromJsonAsync<Customer[]> (
            country is null ? "api/customers" : $"api/customers?country={country}");
}

builder.Services.AddHttpClient<NorthwindApi> (c =>          // 등록
{
    c.BaseAddress = new Uri ("https://api.example.com/v1/");   // 후행 슬래시!
    c.Timeout = TimeSpan.FromSeconds (10);
});
```

호출부는 `HttpClient`를 전혀 보지 않고 `NorthwindApi`만 주입받는다. HTTP 세부가 한 클래스에 갇히므로 테스트와 교체가 쉬워진다.

파이프라인 구성도 팩터리에서 선언한다. `AddHttpMessageHandler`로 등록한 순서가 곧 체인 순서이며, 먼저 등록한 것이 바깥에 온다.

```csharp
builder.Services.AddTransient<LoggingHandler>();
builder.Services.AddHttpClient<NorthwindApi> (/* ... */)
    .AddHttpMessageHandler<LoggingHandler>()              // DelegatingHandler 추가
    .ConfigurePrimaryHttpMessageHandler (() =>            // 기본 핸들러 교체
        new SocketsHttpHandler { AutomaticDecompression = DecompressionMethods.All })
    .SetHandlerLifetime (TimeSpan.FromMinutes (5));       // 핸들러 풀 수명
```

> **📌 로깅은 기본으로 켜져 있다**
>
> `IHttpClientFactory`로 만든 클라이언트는 각 요청과 응답을 자동으로 로그에 남긴다. 카테고리 이름에 클라이언트 이름이 들어간다.
>
> ```text
> info: System.Net.Http.HttpClient.Northwind.WebApi.ClientHandler[100]
>       Sending HTTP request GET https://localhost:5151/api/customers/?country=UK
> info: System.Net.Http.HttpClient.Northwind.WebApi.ClientHandler[101]
>       Received HTTP response headers after 931.864ms - 200
> ```
>
> 소요 시간까지 나오므로 느린 엔드포인트를 찾는 1차 도구로 충분하다. 시끄러우면 `System.Net.Http.HttpClient` 카테고리의 로그 레벨을 낮춘다.

### 회복 탄력성 — Polly 연동

재시도·회로 차단기·타임아웃 같은 정책은 직접 짜기보다 검증된 라이브러리를 붙이는 편이 낫다. Polly가 사실상 표준이다.

```csharp
// Microsoft.Extensions.Http.Polly
builder.Services.AddHttpClient<NorthwindApi>()
    .AddTransientHttpErrorPolicy (p =>
        p.WaitAndRetryAsync (3, i => TimeSpan.FromMilliseconds (200 * Math.Pow (2, i))))
    .AddTransientHttpErrorPolicy (p =>
        p.CircuitBreakerAsync (5, TimeSpan.FromSeconds (30)));
```

.NET 8부터는 `Microsoft.Extensions.Http.Resilience`가 재시도·회로 차단기·타임아웃·헤지를 묶은 표준 파이프라인을 한 줄로 제공한다 ※.NET 8.

```csharp
builder.Services.AddHttpClient<NorthwindApi>()
       .AddStandardResilienceHandler();
```

> **⚠️ 재시도와 멱등성**
>
> 자동 재시도를 켜기 전에 반드시 확인할 것: **그 요청이 두 번 실행되어도 안전한가.** GET·PUT·DELETE는 대체로 멱등이지만 POST는 아니다. 결제 요청을 타임아웃 때문에 재시도해서 이중 청구가 나는 사고는 실재한다.
>
> 안전한 설계는 두 가지다. (1) 재시도 정책을 GET에만 적용하거나, (2) 서버가 멱등성 키(`Idempotency-Key` 헤더)를 지원하게 만들고 재시도 시 같은 키를 보낸다. 43.5절의 `HttpRequestOptions`로 "이 요청은 재시도 금지"를 표시하는 것도 방법이다.

> **⚠️ 형식화 클라이언트의 수명은 transient다 — 캡티브 의존성 주의**
>
> `AddHttpClient<T>()`로 등록한 형식화 클라이언트는 기본적으로 transient로 등록된다. 이 클라이언트를 **싱글턴 서비스가 생성자에서 주입받으면** 그 클라이언트(와 그 안의 핸들러)가 싱글턴 수명 동안 고정된다. 팩터리가 핸들러를 주기적으로 교체하는 이점(43.9절)이 사라지고, DNS 변경을 다시 못 따라가게 된다.
>
> 싱글턴에서 HTTP를 써야 한다면 `HttpClient`가 아니라 **`IHttpClientFactory`를 주입받아** 호출 시점마다 `CreateClient()`를 부른다. `CreateClient()`는 싸다 — 실제 비용이 드는 핸들러는 풀에서 재사용된다.

## 43.8 프록시, 인증, 헤더, 쿼리 문자열, 폼 데이터, 쿠키

### 프록시

프록시 서버는 HTTP 요청이 거쳐 가는 중개자다. 조직에서 직원의 인터넷 접근 통로를 프록시 하나로 묶어 두는 경우가 흔하다 — 주로 보안 관리가 단순해지기 때문이다. 프록시는 자체 주소를 갖고 인증을 요구할 수 있어서, LAN의 선택된 사용자만 인터넷에 나가게 만들 수 있다.

`HttpClient`에서 프록시를 쓰려면 핸들러의 `Proxy`를 설정한 뒤 그 핸들러를 클라이언트 생성자에 넘긴다.

```csharp
WebProxy p = new WebProxy ("192.178.10.49", 808);
p.Credentials = new NetworkCredential ("username", "password", "domain");
var handler = new HttpClientHandler { Proxy = p };
var client = new HttpClient (handler);
```

`UseProxy = false`로 두면 `Proxy`를 `null`로 만드는 것과 별개로 자동 탐지 자체를 무력화한다.

`NetworkCredential`을 만들 때 도메인을 함께 주면 Windows 기반 인증 프로토콜이 쓰인다. 현재 인증된 Windows 사용자로 프록시를 통과하려면 정적 `CredentialCache.DefaultNetworkCredentials`를 `Credentials`에 대입한다.

프로세스 전역 기본 프록시는 정적 프로퍼티로 설정한다 — `HttpClient.DefaultProxy = new WebProxy("http://proxy.corp:8080");` ※.NET Core 3.0.

> **📌 환경 변수로 프록시를 지정하는 방법**
>
> .NET(Core) 계열은 유닉스 관례를 따라 `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY` 환경 변수를 읽어 기본 프록시를 구성한다. 컨테이너 환경에서 코드를 고치지 않고 프록시를 주입하는 표준 방법이다. Windows에서는 여기에 더해 시스템(인터넷 옵션) 설정도 참조한다.

### 인증

사용자 이름과 암호를 핸들러에 주면 된다.

```csharp
string username = "myuser";
string password = "mypassword";
var handler = new HttpClientHandler();
handler.Credentials = new NetworkCredential (username, password);
var client = new HttpClient (handler);
```

이 방식은 Basic·Digest 같은 대화형 인증 프로토콜과 동작하며, Windows NTLM·Kerberos도 지원한다(`NetworkCredential`에 도메인 이름을 함께 준 경우). 현재 인증된 Windows 사용자를 쓰려면 `Credentials`를 `null`로 두고 `UseDefaultCredentials`를 `true`로 설정한다.

자격 증명을 주면 `HttpClient`가 호환되는 프로토콜을 자동으로 협상한다. 선택지가 여럿일 수 있다. 예를 들어 Microsoft Exchange 웹 메일 페이지의 최초 응답은 이런 헤더를 담을 수 있다.

```text
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Negotiate
WWW-Authenticate: NTLM
WWW-Authenticate: Basic realm="exchange.somedomain.com"
```

401은 인증이 필요하다는 신호이고, `WWW-Authenticate` 헤더들이 이해 가능한 프로토콜 목록을 알려 준다. 핸들러에 올바른 자격 증명이 설정돼 있으면 이 왕복은 코드에서 보이지 않는다 — 런타임이 호환 프로토콜을 골라 헤더를 추가한 뒤 원래 요청을 재제출한다.

```text
Authorization: Negotiate TlRMTVNTUAAABAAAt5II2gjACDArAAACAwACACgAAAAQ...
```

> **⚠️ 투명한 인증에는 왕복 한 번의 대가가 있다**
>
> 위 흐름은 편리하지만 **요청마다 401 왕복이 한 번 더 생긴다**. 같은 URI로 반복 요청한다면 핸들러의 `PreAuthenticate`를 `true`로 설정해 두 번째 요청부터는 처음부터 인증 헤더를 보내게 할 수 있다.
>
> 다만 `PreAuthenticate`는 모든 프로토콜에서 의미가 있는 것은 아니다. Basic·Digest에서는 효과가 분명하지만, 연결 단위로 인증되는 NTLM·Negotiate에서는 동작 방식이 다르다. 성능이 중요하면 애초에 토큰 기반 인증(아래)으로 옮기는 편이 낫다.

#### `CredentialCache`로 프로토콜 강제하기

`CredentialCache`는 프로토콜과 URI 접두사별로 자격 증명을 담는다. 특정 프로토콜을 **배제**하는 데 쓸 수 있다. 예를 들어 Exchange 서버에 로그인할 때 암호를 평문으로 보내는 Basic을 피하고 싶다면 이렇게 한다.

```csharp
CredentialCache cache = new CredentialCache();
Uri prefix = new Uri ("http://exchange.somedomain.com");
cache.Add (prefix, "Digest",    new NetworkCredential ("joe", "passwd"));
cache.Add (prefix, "Negotiate", new NetworkCredential ("joe", "passwd"));

var handler = new HttpClientHandler();
handler.Credentials = cache;
```

프로토콜은 문자열로 지정한다. 유효한 값은 `Basic`, `Digest`, `NTLM`, `Kerberos`, `Negotiate`다. 위 상황에서는 서버가 Digest를 지원한다고 알리지 않았으므로 Negotiate가 선택된다. Negotiate는 서버의 능력에 따라 Kerberos나 NTLM으로 귀결되는 Windows 프로토콜이며, 미래에 새 표준이 배치되어도 코드가 계속 동작하도록 보장한다.

암호 없이 현재 Windows 사용자를 캐시에 추가할 수도 있다.

```csharp
cache.Add (prefix, "Negotiate", CredentialCache.DefaultNetworkCredentials);
```

#### 헤더로 직접 인증하기

오늘날 대부분의 웹 API는 위의 대화형 프로토콜이 아니라 **헤더 하나**로 인증한다.

```csharp
var client = new HttpClient();
client.DefaultRequestHeaders.Authorization =
  new AuthenticationHeaderValue ("Basic",
    Convert.ToBase64String (Encoding.UTF8.GetBytes ("username:password")));
```

OAuth 같은 커스텀 인증 체계도 같은 방식이다.

```csharp
request.Headers.Authorization = new AuthenticationHeaderValue ("Bearer", accessToken);
```

| 방식 | 헤더 형태 | 특징 |
|---|---|---|
| Basic | `Authorization: Basic base64(user:pass)` | 암호가 사실상 평문. **HTTPS 필수** |
| Bearer | `Authorization: Bearer <token>` | OAuth 2.0·JWT의 표준. 만료·갱신 필요 |
| API 키 | `X-Api-Key: <key>` 등 | 표준 아님. 서비스마다 헤더 이름이 다르다 |
| Negotiate/NTLM | 런타임이 자동 처리 | Windows 통합 인증. 연결 단위로 상태를 갖는다 |

> **⚠️ Bearer 토큰을 `DefaultRequestHeaders`에 박아 두지 마라**
>
> 토큰은 만료된다. `DefaultRequestHeaders.Authorization`에 대입해 두면 갱신 시점에 그 프로퍼티를 갈아 끼워야 하는데, 43.4절에서 본 대로 요청이 진행 중일 때 기본 헤더를 변경하는 것은 안전하지 않다.
>
> 올바른 자리는 **`DelegatingHandler`** 다(43.7절). 요청마다 최신 토큰을 조회해 헤더를 붙이면 경합이 없고, 401 처리도 한곳에 모인다.

### 헤더 조작

`HttpClient`는 요청에 커스텀 헤더를 붙이고 응답 헤더를 열거하게 해 준다. 헤더는 결국 메타데이터를 담은 키/값 쌍이다 — 메시지의 콘텐츠 타입이나 서버 소프트웨어 같은 것이다.

`HttpClient`는 표준 HTTP 헤더에 대해 강타입 컬렉션을 노출한다. `DefaultRequestHeaders`는 모든 요청에 적용되는 헤더용이다.

```csharp
var client = new HttpClient (handler);
client.DefaultRequestHeaders.UserAgent.Add (
  new ProductInfoHeaderValue ("VisualStudio", "2022"));
client.DefaultRequestHeaders.Add ("CustomHeader", "VisualStudio/2022");
```

특정 요청에만 적용할 헤더는 `HttpRequestMessage.Headers`에 넣는다. 요청 헤더와 콘텐츠 헤더가 별개의 컬렉션이라는 함정은 43.5절에서 자세히 다뤘다.

응답 헤더를 읽는 것도 강타입이다.

```csharp
if (res.Headers.TryGetValues ("X-RateLimit-Remaining", out var values))
    Console.WriteLine (values.First());
DateTimeOffset? modified = res.Content.Headers.LastModified;
EntityTagHeaderValue? etag = res.Headers.ETag;
```

> **⚠️ 헤더 값은 `string`이 아니라 `IEnumerable<string>`이다**
>
> HTTP는 같은 이름의 헤더가 여러 번 나타나는 것을 허용한다(위의 `WWW-Authenticate` 예처럼). 그래서 `TryGetValues`는 문자열 하나가 아니라 시퀀스를 준다. `values.First()`로 첫 값만 보는 코드는 대부분의 경우 옳지만, `Set-Cookie`처럼 여러 값이 정상인 헤더에서는 데이터를 잃는다.

### 쿼리 문자열

쿼리 문자열은 URI에 물음표를 붙여 이어 쓴 문자열로, 서버에 간단한 데이터를 보낸다. 여러 키/값 쌍을 다음 문법으로 담는다.

```text
?key1=value1&key2=value2&key3=value3...
```

```csharp
string requestURI = "http://www.google.com/search?q=HttpClient&hl=fr";
```

값에 기호나 공백이 들어갈 수 있으면 `Uri.EscapeDataString`으로 이스케이프해야 한다(43.3절에서 그 이유와 `EscapeUriString`을 쓰면 안 되는 이유를 다뤘다).

```csharp
string search   = Uri.EscapeDataString ("(HttpClient or HttpRequestMessage)");
string language = Uri.EscapeDataString ("fr");
string requestURI = "http://www.google.com/search?q=" + search + "&hl=" + language;
```

파라미터가 많고 일부가 선택적이라면 문자열 연결은 금방 지저분해진다. 43.3절의 `BuildQuery` 같은 도우미를 두거나, 값이 `null`인 항목을 걸러 내는 작은 확장 메서드를 만든다.

```csharp
static string WithQuery (this string path, params (string Key, string? Value)[] ps)
{
    string q = string.Join ("&", ps.Where (p => p.Value is not null)
        .Select (p => $"{Uri.EscapeDataString (p.Key)}={Uri.EscapeDataString (p.Value!)}"));
    return q.Length == 0 ? path : $"{path}?{q}";
}

string uri = "api/customers".WithQuery (("country", country), ("page", "2"));
```

### 쿠키

쿠키는 HTTP 서버가 응답 헤더로 클라이언트에 보내는 이름/값 문자열 쌍이다. 웹 브라우저는 보통 쿠키를 기억했다가 만료될 때까지 같은 주소로 가는 모든 후속 요청에 다시 실어 보낸다. 이 덕분에 서버는 URI에 지저분한 쿼리 문자열을 넣지 않고도 "1분 전에, 혹은 어제 이야기하던 그 클라이언트"임을 알 수 있다.

**기본적으로 `HttpClient`는 서버가 보낸 쿠키를 무시한다.** 쿠키를 받으려면 `CookieContainer`를 만들어 핸들러에 대입한다.

```csharp
var cc = new CookieContainer();
var handler = new HttpClientHandler();
handler.CookieContainer = cc;
var client = new HttpClient (handler);
```

받은 쿠키를 이후 요청에 다시 실으려면 같은 `CookieContainer` 객체를 계속 쓰면 된다. 빈 컨테이너에서 시작해 쿠키를 직접 추가할 수도 있다.

```csharp
Cookie c = new Cookie ("PREF",
                       "ID=6b10df1da493a9c4:TM=1179...",
                       "/",
                       ".google.com");
freshCookieContainer.Add (c);
```

세 번째와 네 번째 인자는 발신자의 경로와 도메인이다. 하나의 `CookieContainer`가 여러 출처의 쿠키를 담을 수 있고, `HttpClient`는 그중 서버의 경로·도메인과 일치하는 쿠키만 보낸다.

> **⚠️ 쿠키 컨테이너는 공유 가변 상태다**
>
> `IHttpClientFactory`가 관리하는 핸들러는 여러 논리 클라이언트가 공유한다(43.9절). 그 핸들러에 `CookieContainer`가 붙어 있으면 **사용자 A의 세션 쿠키가 사용자 B의 요청에 실릴 수 있다.** 서버 애플리케이션에서 이것은 심각한 권한 사고다.
>
> 그래서 팩터리로 만든 클라이언트에서는 기본적으로 `UseCookies = false`로 두고, 쿠키가 필요하면 요청마다 `Cookie` 헤더를 명시적으로 붙이는 편이 안전하다.
>
> ```csharp
> builder.Services.AddHttpClient<MyApi>()
>     .ConfigurePrimaryHttpMessageHandler (() =>
>         new SocketsHttpHandler { UseCookies = false });
> ```

## 43.9 `HttpClient` 수명 관리 — 소켓 고갈 문제

### 두 개의 잘못된 극단

`HttpClient`는 `IDisposable`을 구현한다. 그래서 대부분의 개발자가 배운 규칙 — "`IDisposable`이면 `using`으로 감싼다"(33장) — 를 그대로 적용한다.

```csharp
// 잘못된 코드
public async Task<string> GetAsync (string url)
{
    using var client = new HttpClient();     // ← 매 호출마다 새로 만든다
    return await client.GetStringAsync (url);
}
```

이것이 .NET에서 가장 널리 퍼진 오용이다. Microsoft 자신의 문서조차 한때 이렇게 보여 줬다.

문제는 **밑에 깔린 네트워크 소켓이 어떻게 관리되는가**에 있다. `HttpClient`를 해제하면 그 핸들러가 해제되고, 핸들러가 들고 있던 커넥션 풀이 통째로 버려진다. 그 안의 TCP 연결들은 즉시 사라지지 않는다 — **`TIME_WAIT` 상태로 넘어가 수 분간 남는다.**

```text
연결을 닫은 쪽의 소켓 상태 전이

  ESTABLISHED
       │  close()
       ▼
  FIN_WAIT_1 ──▶ FIN_WAIT_2 ──▶ TIME_WAIT ──────────▶ CLOSED
                                    ▲                    ▲
                                    │                    │
                          이 구간에서 임시 포트가       비로소 포트가
                          점유된 채로 남는다            반환된다
                          (리눅스 60초, Windows는
                           설정에 따라 보통 1~4분)

  임시 포트 풀:  Windows 49152~65535 (약 16,000개)
                리눅스   32768~60999 (약 28,000개)

  초당 300 요청 × 60초 = 18,000개  →  풀이 마른다
```

포트가 마르면 새 연결을 열 수 없다. 증상은 `SocketException` — 흔히 `AddressAlreadyInUse` 또는 "일시적으로 사용 가능한 포트 없음" — 이고, 트래픽이 정점을 찍은 순간 서비스 전체가 마비된다. `netstat -an | find /c "TIME_WAIT"`(Windows)이나 `ss -s`(리눅스)로 확인할 수 있다.

그래서 **반대 극단**이 처방으로 유행했다. 정적 싱글턴이다.

```csharp
// 절반만 맞는 코드
static readonly HttpClient Shared = new HttpClient();
```

소켓 고갈은 사라진다. 그런데 새로운 문제가 생긴다.

> **⚠️ 싱글턴 `HttpClient`는 DNS 변경을 따라가지 못한다**
>
> `SocketsHttpHandler`는 연결을 풀에 넣고 재사용한다. 연결이 살아 있는 한 **DNS를 다시 조회하지 않는다.** 그런데 클라우드 환경에서는 서비스의 IP가 바뀐다 — 블루/그린 배포, 오토스케일링, 장애 조치(failover), CDN 엔드포인트 갱신이 전부 DNS 레코드를 바꾼다.
>
> 프로세스가 며칠씩 살아 있는 서버 애플리케이션에서 싱글턴 `HttpClient`는 **없어진 IP로 계속 연결을 시도하거나, 옛 인스턴스에 트래픽을 계속 보낸다.** 다른 모든 클라이언트는 새 주소로 옮겨 갔는데 우리 서비스만 그대로인 상황이 되고, 재시작하기 전에는 낫지 않는다.
>
> .NET Framework 시절에는 `ServicePointManager.DnsRefreshTimeout`이 이 문제를 다뤘다. 모던 .NET에서는 그 설정이 `HttpClient`에 아무 영향도 주지 않는다.

### 균형점 — `PooledConnectionLifetime`

두 문제는 서로 반대 방향을 가리킨다.

| | 매번 새로 만들기 | 영구 싱글턴 |
|---|---|---|
| 소켓 사용 | 요청마다 새 연결 → 고갈 | 풀 재사용 → 효율적 |
| DNS 변경 | 항상 최신 | 따라가지 못함 |
| TLS 핸드셰이크 | 요청마다 반복(비쌈) | 재사용 |
| 지연 시간 | 연결 수립 + 핸드셰이크가 매번 | 두 번째 요청부터 매우 빠름 |

해답은 "연결을 재사용하되, **영원히**는 아니게" 하는 것이다. `SocketsHttpHandler.PooledConnectionLifetime`이 정확히 이 역할을 한다. 지정한 시간이 지난 연결은 **사용 중이 아닐 때** 풀에서 제거되고, 다음 요청은 새 연결을 만들면서 DNS를 다시 조회한다.

```csharp
static readonly HttpClient Shared = new HttpClient (new SocketsHttpHandler
{
    PooledConnectionLifetime = TimeSpan.FromMinutes (2),
});
```

이 값의 선택은 트레이드오프다.

| `PooledConnectionLifetime` | DNS 반영 지연 | 연결 재수립 비용 |
|---|---|---|
| 무한(기본) | 영원히 반영 안 됨 | 없음 |
| 15분 | 최대 15분 | 아주 낮음 |
| 2분 | 최대 2분 | 낮음 — 일반적인 권장 출발점 |
| 10초 | 거의 즉시 | 높음. TLS 핸드셰이크가 잦아진다 |

> **📌 `PooledConnectionLifetime`은 진행 중인 요청을 끊지 않는다**
>
> 수명이 만료된 연결은 즉시 파괴되지 않는다. 현재 요청이 끝난 뒤 풀에 반환될 때 폐기된다. 그래서 이 값을 짧게 잡아도 전송 중인 응답이 잘리는 일은 없다. 이 점이 `PooledConnectionIdleTimeout`(유휴 연결 정리)과 다르다 — 후자는 "얼마나 놀고 있으면 닫을까"이고, 전자는 "얼마나 오래 살았으면 은퇴시킬까"다.

### `IHttpClientFactory`가 하는 일

`IHttpClientFactory`(43.7절)는 이 문제를 다른 각도에서 푼다. **`HttpClient` 인스턴스는 싸게 만들고 버리되, 그 뒤의 핸들러를 풀링한다.**

```text
  CreateClient("api")  →  새 HttpClient 객체 (싸다, 버려도 된다)
                                │
                                └─▶ 핸들러 체인 (풀에서 빌려옴)
                                        │
                                        └─▶ SocketsHttpHandler
                                                │
                                                └─▶ 커넥션 풀 (공유)

  핸들러 수명(기본 2분)이 지나면:
     · 그 핸들러는 "만료" 표시되고 새 요청에 배정되지 않는다
     · 사용 중인 요청이 모두 끝나면 해제된다
     · 새 요청은 새 핸들러(→ 새 연결 → 새 DNS 조회)를 받는다
```

핸들러 수명의 기본값은 **2분**이며 `SetHandlerLifetime`으로 바꾼다. 즉 팩터리는 `PooledConnectionLifetime`과 같은 목표를 핸들러 교체로 달성한다.

```csharp
builder.Services.AddHttpClient<NorthwindApi>()
       .SetHandlerLifetime (TimeSpan.FromMinutes (5));
```

> **📌 팩터리와 `PooledConnectionLifetime`을 함께 쓸 수 있나**
>
> 쓸 수 있고, 그 조합이 오히려 권장되는 경우가 있다. 핸들러 교체는 그 시점에 새로 만들어지는 클라이언트에만 영향을 주고, 이미 진행 중인 오래된 핸들러의 연결은 그대로 남는다. `PooledConnectionLifetime`을 함께 설정하면 연결 단위로도 은퇴가 보장된다.
>
> 반대로 **`PooledConnectionLifetime`만으로 충분한 시나리오**도 많다. 콘솔 앱이나 데스크톱 앱처럼 DI 컨테이너가 없는 곳에서는 정적 `HttpClient` + `PooledConnectionLifetime` 조합이 가장 단순하고 정확한 답이다.

### 정리 — 세 가지 전략

| 전략 | 적합한 곳 | 소켓 고갈 | DNS 추적 | 비고 |
|---|---|---|---|---|
| 요청마다 `new HttpClient()` | **없음** | 발생 | 됨 | 쓰지 마라 |
| 정적 싱글턴 + `PooledConnectionLifetime` | 콘솔·데스크톱·간단한 서비스 | 없음 | 됨 | 가장 단순한 정답 |
| `IHttpClientFactory` | ASP.NET Core, DI를 쓰는 앱 | 없음 | 됨 | 이름별 설정·파이프라인·로깅이 덤 |

핵심 규칙은 한 문장이다. **소비하는 HTTP 엔드포인트마다 인스턴스를 하나씩 두고, 애플리케이션 수명 동안 재사용한다.** 그러면 엔드포인트별로 적절한 기본값(기준 주소, 타임아웃, 헤더)을 설정하면서도 밑의 소켓은 효율적으로 관리된다.

> **⚠️ 그렇다면 `HttpClient`를 절대 `Dispose`하지 않아도 되나**
>
> 애플리케이션 수명 동안 사는 인스턴스라면 프로세스 종료가 곧 정리이므로 실질적으로 문제가 없다. 그러나 "해제하지 않는다"가 규칙이 되면 안 된다. 짧게 살고 사라지는 클라이언트(예: 일회성 마이그레이션 도구)는 정상적으로 해제하는 편이 옳다.
>
> 핸들러를 외부에서 주입받아 여러 클라이언트가 공유하는 구조라면, 클라이언트가 핸들러를 죽이지 않도록 명시해야 한다.
>
> ```csharp
> var shared = new SocketsHttpHandler { PooledConnectionLifetime = TimeSpan.FromMinutes (2) };
> var a = new HttpClient (shared, disposeHandler: false);
> var b = new HttpClient (shared, disposeHandler: false);
> // a.Dispose()가 shared를 죽이지 않는다
> ```
>
> `disposeHandler`를 지정하지 않는 생성자는 **`true`가 기본**이다. 이 기본값이 "핸들러를 공유하려 했는데 하나를 해제했더니 나머지가 전부 `ObjectDisposedException`을 내는" 사고의 원인이다.

### 진단

소켓 고갈이 의심될 때 확인할 것들.

```bash
netstat -an | find /c "TIME_WAIT"   # Windows — TIME_WAIT 소켓 개수
ss -s                                # 리눅스 — 상태별 요약
dotnet-counters monitor --process-id <pid> --counters System.Net.Http,System.Net.Sockets
```

`System.Net.Http` 카운터의 `current-requests`가 계속 증가하고 `requests-started`와 완료 수의 격차가 벌어진다면 커넥션 풀에서 요청이 대기 중이라는 뜻이다. `MaxConnectionsPerServer`가 너무 낮거나, `ResponseHeadersRead` 응답을 해제하지 않고 있거나(43.4절), 소켓이 고갈되고 있다. 계측 도구 전반은 73장·75장에서 다룬다.

## 43.10 HTTP 서버 직접 작성하기

### `HttpListener`

.NET에는 `HttpListener` 클래스로 자체 HTTP 서버를 작성하는 길이 열려 있다. 다음은 51111 포트에서 대기하다가 클라이언트 요청 하나를 받고 한 줄짜리 응답을 돌려주는 간단한 서버다.

```csharp
using var server = new SimpleHttpServer();

Console.WriteLine (await new HttpClient().GetStringAsync      // 클라이언트 요청
  ("http://localhost:51111/MyApp/Request.txt"));

class SimpleHttpServer : IDisposable
{
    readonly HttpListener listener = new HttpListener();
    public SimpleHttpServer() => ListenAsync();

    async void ListenAsync()
    {
        listener.Prefixes.Add ("http://localhost:51111/MyApp/");   // 51111 포트에서
        listener.Start();                                          // 수신

        HttpListenerContext context = await listener.GetContextAsync();

        string msg = "You asked for: " + context.Request.RawUrl;
        context.Response.ContentLength64 = Encoding.UTF8.GetByteCount (msg);
        context.Response.StatusCode = (int) HttpStatusCode.OK;

        using (Stream s = context.Response.OutputStream)
        using (StreamWriter writer = new StreamWriter (s))
            await writer.WriteAsync (msg);
    }

    public void Dispose() => listener.Close();
}
// 출력: You asked for: /MyApp/Request.txt
```

`GetContext`(또는 `GetContextAsync`)는 다음 클라이언트 요청을 기다렸다가 `Request`와 `Response` 프로퍼티를 가진 객체를 준다. 각각 클라이언트 쪽의 요청·응답에 대응하지만 **서버의 관점**이다. 클라이언트에서 하듯 헤더와 쿠키를 읽고 쓸 수 있다.

HTTP 프로토콜의 어느 기능까지 지원할지는 예상 클라이언트에 따라 선택하면 된다. 최소한 **각 요청마다 콘텐츠 길이와 상태 코드는 설정해야 한다.**

### 왜 여러 앱이 같은 포트를 공유할 수 있는가

> **📌 Windows에서 `HttpListener`는 소켓을 직접 쓰지 않는다**
>
> Windows에서 `HttpListener`는 내부적으로 .NET `Socket` 객체를 쓰지 않는다. Windows HTTP Server API(커널 모드 `http.sys`)를 호출한다. 그래서 **한 기계의 여러 응용이 같은 IP와 포트에서 수신할 수 있다** — 각자 다른 주소 접두사를 등록하기만 하면 된다.
>
> 위 예제는 `http://localhost:51111/MyApp/`을 등록했으므로, 다른 응용이 같은 IP·포트의 `http://localhost:51111/anotherapp/`에서 자유롭게 수신할 수 있다. 기업 방화벽에서 새 포트를 여는 일이 정치적으로 지난한 현실을 생각하면 이것은 실질적인 가치가 있다.
>
> 비 Windows 플랫폼에서는 `HttpListener`가 관리 소켓 위의 구현으로 대체된다. 따라서 위의 포트 공유 특성은 성립하지 않고, 일부 기능(예: 통합 Windows 인증, 일부 WebSocket 경로)이 지원되지 않거나 `PlatformNotSupportedException`을 낼 수 있다.

> **⚠️ URL ACL — Windows에서 나는 "액세스 거부" 오류**
>
> Windows에서 `localhost` 이외의 접두사(`http://+:51111/`, `http://*:51111/`)를 등록하려면 **관리자 권한이 필요하거나 URL ACL이 미리 등록돼 있어야 한다.** 그렇지 않으면 `listener.Start()`에서 `HttpListenerException`(액세스 거부)이 난다.
>
> 관리자 명령 프롬프트에서 한 번 등록해 두면 일반 권한으로 실행할 수 있다.
>
> ```bash
> netsh http add urlacl url=http://+:51111/MyApp/ user=DOMAIN\username
> ```
>
> 이것은 **Windows 전용** 절차다. 리눅스·macOS에서는 1024 미만 포트에 바인딩할 때만 권한 문제가 생긴다.

### 확장 가능한 파일 서버

다음은 비동기로 작성한 아주 단순한 웹 페이지 서버다.

```csharp
class WebServer
{
    readonly HttpListener _listener = new();
    readonly string _baseFolder;

    public WebServer (string uriPrefix, string baseFolder)
    { _listener.Prefixes.Add (uriPrefix); _baseFolder = baseFolder; }

    public async void Start()
    {
        _listener.Start();
        while (true)
            try
            {
                var context = await _listener.GetContextAsync();
                Task.Run (() => ProcessRequestAsync (context));
            }
            catch (HttpListenerException)     { break; }   // 리스너가 멈췄다
            catch (InvalidOperationException) { break; }   // 리스너가 멈췄다
    }

    public void Stop() => _listener.Stop();

    async void ProcessRequestAsync (HttpListenerContext context)
    {
        try
        {
            string path = Path.Combine (_baseFolder,
                            Path.GetFileName (context.Request.RawUrl)!);
            byte[] msg;

            if (!File.Exists (path))
            {
                context.Response.StatusCode = (int) HttpStatusCode.NotFound;
                msg = Encoding.UTF8.GetBytes ("Sorry, that page does not exist");
            }
            else
            {
                context.Response.StatusCode = (int) HttpStatusCode.OK;
                msg = File.ReadAllBytes (path);
            }

            context.Response.ContentLength64 = msg.Length;
            using (Stream s = context.Response.OutputStream)
                await s.WriteAsync (msg, 0, msg.Length);
        }
        catch (Exception ex) { Console.WriteLine ("Request error: " + ex); }
    }
}

// 기동: 51111 포트에서 d:\webroot의 파일을 서비스한다
var server = new WebServer ("http://localhost:51111/", @"d:\webroot");
server.Start();
Console.WriteLine ("Server running... press Enter to stop");
Console.ReadLine();
server.Stop();
```

비동기 함수를 쓴 덕분에 이 서버는 확장 가능하고 효율적이다. 다만 **UI 스레드에서 시작하면 확장성이 훼손된다** — 각 `await` 이후 실행이 UI 스레드로 되돌아가기 때문이다. 공유 상태가 없는 이 코드에서 그 왕복은 순수한 낭비다. UI 시나리오라면 `Task.Run(Start)`로 UI 스레드를 벗어나거나 `GetContextAsync()` 뒤에 `ConfigureAwait(false)`를 붙인다(47.12절).

`ProcessRequestAsync`가 이미 비동기인데도 `Task.Run`으로 감싼 이유가 있다. 그래야 호출자가 메서드의 동기 구간(첫 `await`까지)을 기다리지 않고 **즉시 다음 요청을 받으러 갈 수 있다.**

> **⚠️ 이 코드를 인터넷에 노출하지 마라**
>
> 위 서버는 교육용이다. 실서비스에 필요한 것이 거의 다 빠져 있다.
>
> - `Path.GetFileName`이 경로 순회를 부분적으로 막지만, 경로 검증은 이 정도로 끝나지 않는다(40.12절)
> - `File.ReadAllBytes`가 동기이며 파일 전체를 메모리에 올린다
> - `Content-Type`을 설정하지 않는다
> - 요청 크기 제한, 속도 제한, 타임아웃이 없다
> - HTTPS·인증·로깅이 없다
>
> 실서비스 HTTP 서버는 ASP.NET Core의 Kestrel을 쓴다. .NET 6부터는 최소 API(minimal API)로 몇 줄이면 시작한다.
>
> ```csharp
> var app = WebApplication.CreateBuilder().Build();
> app.MapGet ("/", () => "Hello, world!");
> app.Run();
> ```
>
> Microsoft 문서도 `HttpListener`를 새 개발에 권장하지 않는다. `HttpListener`의 자리는 **테스트 스텁, 개발 도구, 로컬 OAuth 콜백 수신기** 정도다.

> **⚠️ 포트를 다른 소프트웨어가 쓰고 있으면 시작되지 않는다**
>
> `HttpListener`는 같은 포트를 놓고 경쟁하는 다른 소프트웨어가 있으면 시작하지 못한다(그 소프트웨어도 Windows HTTP Server API를 쓰는 경우는 예외다). 기본 포트 80에서 수신할 수 있는 응용의 예로는 웹 서버나 Skype 같은 P2P 프로그램이 있다.

### WebSocket

HTTP 요청/응답 모델로는 서버가 먼저 말을 걸 수 없다. WebSocket은 HTTP 핸드셰이크로 시작해 **지속적인 양방향 연결로 업그레이드**하는 프로토콜이다.

클라이언트 쪽은 `System.Net.WebSockets.ClientWebSocket`이다.

```csharp
using var ws = new ClientWebSocket();
await ws.ConnectAsync (new Uri ("wss://echo.example.com/socket"), ct);

await ws.SendAsync (Encoding.UTF8.GetBytes ("hello"),
                    WebSocketMessageType.Text, endOfMessage: true, ct);

var buffer = new byte[4096];
WebSocketReceiveResult result = await ws.ReceiveAsync (buffer, ct);
Console.WriteLine (Encoding.UTF8.GetString (buffer, 0, result.Count));

await ws.CloseAsync (WebSocketCloseStatus.NormalClosure, "bye", ct);
```

서버 쪽은 `HttpListenerContext.AcceptWebSocketAsync`로 업그레이드하거나(플랫폼 제약이 있다), ASP.NET Core의 WebSocket 미들웨어를 쓴다.

> **⚠️ `ReceiveAsync` 한 번이 메시지 하나가 아니다**
>
> WebSocket은 TCP와 달리 메시지 경계를 갖지만, 한 메시지가 여러 **프레임**으로 쪼개져 올 수 있다. `WebSocketReceiveResult.EndOfMessage`가 `false`면 아직 뒤가 남았다는 뜻이다. 버퍼 하나를 읽고 메시지 하나를 받았다고 가정하는 코드는 큰 메시지에서 조용히 잘린다.
>
> ```csharp
> using var ms = new MemoryStream();
> WebSocketReceiveResult r;
> do
> {
>     r = await ws.ReceiveAsync (buffer, ct);
>     ms.Write (buffer, 0, r.Count);
> } while (!r.EndOfMessage);
> ```
>
> 실시간 기능이 애플리케이션의 중심이라면 재연결·하트비트·그룹 브로드캐스트를 이미 갖춘 SignalR을 쓰는 편이 현실적이다.

## 43.11 DNS 조회

### `Dns` 클래스

정적 `Dns` 클래스가 도메인 이름 시스템을 캡슐화한다. `66.135.192.87` 같은 원시 IP 주소와 `ebay.com` 같은 사람이 읽는 도메인 이름 사이를 오간다.

`GetHostAddresses`는 도메인 이름을 IP 주소(들)로 바꾸고, `GetHostEntry`는 반대 방향 — 주소에서 도메인 이름으로 — 이다. `GetHostEntry`는 `IPAddress` 객체도 받으므로 바이트 배열로 주소를 지정할 수 있다.

```csharp
foreach (IPAddress a in Dns.GetHostAddresses ("albahari.com"))
    Console.WriteLine (a.ToString());        // 205.210.42.167

IPHostEntry entry = Dns.GetHostEntry ("205.210.42.167");
Console.WriteLine (entry.HostName);          // albahari.com

IPAddress address = new IPAddress (new byte[] { 205, 210, 42, 167 });
Console.WriteLine (Dns.GetHostEntry (address).HostName);   // albahari.com
```

비동기 버전이 있고, 네트워크 I/O이므로 그쪽을 써야 한다.

```csharp
foreach (IPAddress a in await Dns.GetHostAddressesAsync ("albahari.com"))
    Console.WriteLine (a.ToString());
```

| 메서드 | 하는 일 | 반환 |
|---|---|---|
| `Dns.GetHostAddressesAsync(host)` | 정방향 조회(이름 → 주소) | `Task<IPAddress[]>` |
| `Dns.GetHostEntryAsync(hostOrAddress)` | 정방향 + **역방향** 조회 | `Task<IPHostEntry>` |
| `Dns.GetHostName()` | 로컬 기계의 호스트 이름 | `string` |

`IPHostEntry`는 `HostName`, `AddressList`, `Aliases` 세 조각을 담는다.

> **⚠️ `GetHostEntry`는 `GetHostAddresses`보다 훨씬 느릴 수 있다**
>
> 이름을 주소로 바꾸는 것이 목적이라면 `GetHostAddressesAsync`를 써라. `GetHostEntryAsync`는 정방향 조회 뒤에 **역방향 조회(PTR 레코드)** 를 추가로 수행해 정식 이름을 채운다. 역방향 레코드가 설정돼 있지 않은 호스트에서는 타임아웃이 날 때까지 기다리게 되고, 그 대기가 수 초에 이를 수 있다.
>
> "이름을 IP로 바꾸기"에 `GetHostEntry`를 쓰는 코드는 대단히 흔하고, 대단히 느리다.

### DNS와 성능

`WebRequest`나 `TcpClient` 같은 클래스를 쓰면 도메인 이름은 자동으로 IP 주소로 해석된다. 그러나 애플리케이션 수명 동안 같은 주소로 많은 요청을 보낼 계획이라면, 먼저 `Dns`로 도메인 이름을 IP 주소로 명시적으로 변환한 뒤 그 주소로 직접 통신하는 편이 나을 때가 있다. 같은 도메인 이름을 반복해서 해석하는 왕복이 사라지기 때문이다. 이 이득은 특히 전송 계층에서 작업할 때(`TcpClient`, `UdpClient`, `Socket`) 의미가 있다.

> **⚠️ 그렇다고 `HttpClient`에 IP 주소를 직접 넣지 마라**
>
> HTTP에서는 이야기가 다르다. URL의 호스트가 `Host` 헤더와 TLS의 SNI(Server Name Indication)에 그대로 쓰이기 때문이다. IP 주소를 URL에 넣으면 가상 호스팅 서버가 어느 사이트인지 알 수 없고, TLS 인증서 이름 검증도 실패한다.
>
> `HttpClient`에서 DNS 왕복이 걱정된다면 커넥션 풀이 이미 그 문제를 해결하고 있다 — 풀에 있는 연결을 재사용하는 동안 DNS 조회는 일어나지 않는다. 43.9절의 논의가 정확히 이 지점이다.

### 캐시라는 세 겹의 층

"DNS가 반영되지 않는다"는 문제를 볼 때, 캐시는 여러 층에 있다.

| 층 | 수명 결정 | 무효화 방법 |
|---|---|---|
| 커넥션 풀(연결 재사용) | `PooledConnectionLifetime` | 해당 값 설정(43.9절) |
| OS 리졸버 캐시 | 레코드의 TTL(운영체제 정책) | Windows `ipconfig /flushdns`, 리눅스는 서비스별 |
| 상위 DNS 서버 캐시 | 권한 서버가 지정한 TTL | 기다리는 수밖에 없다 |

.NET 자체는 별도의 DNS 캐시를 두지 않는다. `Dns.GetHostAddressesAsync`를 부르면 OS 리졸버에 묻고, OS가 캐시를 관리한다. .NET Framework의 `ServicePointManager.DnsRefreshTimeout`은 모던 .NET에는 대응물이 없다 — 그 자리를 `PooledConnectionLifetime`이 대신한다.

### 네트워크 상태 조회

`System.Net.NetworkInformation`에는 진단용 타입들이 있다.

```csharp
using System.Net.NetworkInformation;

using var ping = new Ping();                                   // ICMP 에코 요청
PingReply reply = await ping.SendPingAsync ("example.com", timeout: 2000);
Console.WriteLine ($"{reply.Status} {reply.RoundtripTime}ms");

foreach (NetworkInterface ni in NetworkInterface.GetAllNetworkInterfaces())
    Console.WriteLine ($"{ni.Name}: {ni.OperationalStatus} / {ni.NetworkInterfaceType}");

NetworkChange.NetworkAvailabilityChanged += (s, e) =>          // 가용성 변화 감시
    Console.WriteLine (e.IsAvailable ? "온라인" : "오프라인");
```

> **⚠️ `Ping`으로 "서비스가 살아 있다"를 판단하지 마라**
>
> ICMP는 대부분의 클라우드 방화벽에서 차단된다. 핑이 실패해도 HTTP는 멀쩡한 경우가 흔하고, 반대로 핑이 성공해도 애플리케이션은 죽어 있을 수 있다. 서비스 상태는 **그 서비스의 상태 확인 엔드포인트를 HTTP로 호출해서** 판단한다.
>
> `NetworkInterface.GetIsNetworkAvailable()`도 마찬가지다. "인터페이스가 올라와 있다"와 "인터넷에 나갈 수 있다"는 전혀 다른 명제다. 가상 어댑터나 사설 네트워크만 붙어 있어도 참을 반환한다.

## 43.12 TCP 직접 사용하기와 TCP 동시성

### 전송 계층으로 내려가는 이유

TCP와 UDP는 대부분의 인터넷·LAN 서비스가 그 위에 지어진 전송 계층 프로토콜이다. HTTP(버전 2 이하), FTP, SMTP는 TCP를 쓰고, DNS와 HTTP 버전 3은 UDP를 쓴다. TCP는 연결 지향이며 신뢰성 메커니즘을 포함한다. UDP는 비연결이고 오버헤드가 낮으며 브로드캐스트를 지원한다. BitTorrent와 VoIP가 UDP를 쓴다.

전송 계층은 상위 계층보다 유연하고 성능을 더 끌어낼 여지가 있지만, **인증과 암호화 같은 일을 직접 해야 한다.**

.NET에서 TCP를 쓰는 선택지는 둘이다. 쓰기 쉬운 파사드 `TcpClient`·`TcpListener`, 또는 기능이 풍부한 `Socket`. 사실 섞어 쓸 수도 있다 — `TcpClient`가 `Client` 프로퍼티로 밑의 `Socket`을 노출하기 때문이다. `Socket` 클래스는 더 많은 설정 옵션을 노출하고, 네트워크 계층(IP)과 Novell의 SPX/IPX 같은 비인터넷 프로토콜에 직접 접근하게 해 준다.

### 기본 구조

다른 프로토콜과 마찬가지로 TCP는 클라이언트와 서버를 구분한다. 클라이언트가 요청을 개시하고 서버가 기다린다.

```csharp
using (TcpClient client = new TcpClient())
{
    client.Connect ("address", port);
    using (NetworkStream n = client.GetStream())
    { /* 네트워크 스트림에 읽고 쓴다... */ }
}
```

`Connect`는 연결이 수립될 때까지 블록한다(`ConnectAsync`가 비동기 버전이다). `NetworkStream`이 양방향 통신 수단을 제공한다.

서버는 이렇게 생겼다.

```csharp
TcpListener listener = new TcpListener (<ip address>, port);
listener.Start();
while (keepProcessingRequests)
    using (TcpClient c = listener.AcceptTcpClient())
    using (NetworkStream n = c.GetStream())
    {
        // 네트워크 스트림에 읽고 쓴다...
    }
listener.Stop();
```

`TcpListener`는 수신할 로컬 IP 주소를 요구한다(네트워크 카드가 둘인 기계는 주소가 둘이다). `IPAddress.Any`를 주면 모든(또는 유일한) 로컬 IP에서 수신한다. `AcceptTcpClient`는 클라이언트 요청이 올 때까지 블록하고, 요청이 오면 클라이언트 쪽과 마찬가지로 `GetStream`을 호출한다.

### 누가 언제 말할 것인가

전송 계층에서 일할 때는 **누가 언제 얼마나 말할지에 대한 규약**을 정해야 한다. 무전기와 비슷하다. 양쪽이 동시에 말하거나 동시에 듣기만 하면 통신은 무너진다.

클라이언트가 먼저 "Hello"라고 말하면 서버가 "Hello right back!"이라고 답하는 프로토콜을 만들어 보자.

```csharp
new Thread (Server).Start();       // 서버 메서드를 동시에 실행
Thread.Sleep (500);                // 서버가 시작할 시간을 준다
Client();

void Client()
{
    using (TcpClient client = new TcpClient ("localhost", 51111))
    using (NetworkStream n = client.GetStream())
    {
        BinaryWriter w = new BinaryWriter (n);
        w.Write ("Hello");
        w.Flush();
        Console.WriteLine (new BinaryReader (n).ReadString());
    }
}

void Server()     // 클라이언트 요청 하나를 처리하고 종료한다
{
    TcpListener listener = new TcpListener (IPAddress.Any, 51111);
    listener.Start();
    using (TcpClient c = listener.AcceptTcpClient())
    using (NetworkStream n = c.GetStream())
    {
        string msg = new BinaryReader (n).ReadString();
        BinaryWriter w = new BinaryWriter (n);
        w.Write (msg + " right back!");
        w.Flush();          // 라이터를 해제하지 않으므로 Flush가 필요하다
    }
    listener.Stop();
}
// 출력: Hello right back!
```

루프백을 써서 클라이언트와 서버를 같은 기계에서 돌렸고, 미할당 범위(49152 이상)의 포트를 임의로 골랐고, 텍스트 메시지를 인코딩하는 데 `BinaryWriter`·`BinaryReader`를 썼다. 리더와 라이터를 닫거나 해제하지 않은 것은 대화가 끝날 때까지 밑의 `NetworkStream`을 열어 두기 위해서다.

### 메시지 경계 — TCP가 주지 않는 것

`BinaryReader`와 `BinaryWriter`가 문자열을 다루는 데 이상한 선택으로 보일 수 있다. 그러나 `StreamReader`·`StreamWriter`에 없는 결정적 장점이 있다. **문자열 앞에 길이를 나타내는 정수를 붙인다.** 그래서 `BinaryReader`는 몇 바이트를 읽어야 하는지 정확히 안다.

이것이 전송 계층에서 가장 중요한 개념으로 이어진다.

> **⚠️ TCP에는 메시지 경계가 없다**
>
> TCP는 **바이트 스트림**이지 메시지 큐가 아니다. 송신 측이 `Write`를 세 번 호출해도 수신 측이 `Read`를 세 번 해서 같은 세 조각을 받는다는 보장이 전혀 없다. 다음이 모두 가능하다.
>
> - 세 번의 쓰기가 하나의 읽기로 뭉쳐서 온다(Nagle 알고리즘, 커널 버퍼링)
> - 한 번의 쓰기가 여러 번의 읽기로 쪼개져 온다(MTU, 혼잡 제어, 경로 분할)
>
> 로컬 루프백에서 테스트하면 거의 항상 "보낸 대로" 도착하기 때문에 이 버그는 **개발 환경에서 절대 재현되지 않고 운영에서만 터진다.** 그것도 부하가 높을 때만.
>
> 해결책은 프로토콜에 **프레이밍**을 넣는 것뿐이다.
>
> | 프레이밍 방식 | 방법 | 장단점 |
> |---|---|---|
> | 길이 접두사 | 본문 앞에 4바이트 길이를 쓴다 | 이진 데이터에 안전. 가장 흔한 선택 |
> | 구분자 | 개행 등으로 메시지를 나눈다 | 텍스트 프로토콜에 적합. 본문에 구분자가 나오면 이스케이프 필요 |
> | 고정 길이 | 모든 메시지가 같은 크기 | 단순하지만 낭비가 크다 |
> | 연결 종료 | 한 메시지 보내고 닫는다 | HTTP/1.0 스타일. 연결 비용이 크다 |

길이 접두사 프레이밍의 최소 구현은 이렇다.

```csharp
static async Task WriteFrameAsync (Stream s, byte[] payload, CancellationToken ct)
{
    await s.WriteAsync (BitConverter.GetBytes (payload.Length), ct);   // 4바이트 헤더
    await s.WriteAsync (payload, ct);
    await s.FlushAsync (ct);
}

static async Task<byte[]> ReadFrameAsync (Stream s, CancellationToken ct)
{
    byte[] header = new byte[4];
    await s.ReadExactlyAsync (header, ct);          // ※.NET 7

    int length = BitConverter.ToInt32 (header);
    if (length < 0 || length > 16 * 1024 * 1024)    // 상한 검사는 필수다
        throw new InvalidDataException ($"프레임 길이가 비정상이다: {length}");

    byte[] payload = new byte[length];
    await s.ReadExactlyAsync (payload, ct);
    return payload;
}
```

`ReadExactlyAsync`가 하는 일이 핵심이다. `Stream.ReadAsync`는 **요청한 만큼 읽었다고 보장하지 않으므로** 루프가 필요하다 — 40.2절에서 본 스트림의 일반 계약과 같은 이야기이고, 네트워크 스트림에서 특히 자주 위반된다. ※.NET 7부터 `ReadExactly`/`ReadExactlyAsync`가 BCL에 들어와 직접 구현할 필요가 없어졌다.

> **⚠️ 길이 접두사에는 반드시 상한을 둔다**
>
> 위 코드에서 `length > 16MB`를 검사하는 부분을 생략하면, 악의적인 클라이언트가 길이 필드에 `int.MaxValue`를 보내는 것만으로 서버가 2GB를 할당하려다 죽는다. 인증 이전 단계에서 동작하는 원격 서비스 거부 공격이다. 프레이밍을 직접 구현할 때 가장 흔히 빠뜨리는 방어다.

> **⚠️ `NetworkStream`에 `StreamReader`를 쓰지 마라**
>
> `StreamReader`는 `NetworkStream`과 **원천적으로 맞지 않는다.** `ReadLine`만 부를 계획이어도 그렇다. `StreamReader`에는 미리 읽기 버퍼가 있어서 현재 사용 가능한 것보다 많은 바이트를 읽으려 하고, 그 결과 무기한(또는 소켓 타임아웃까지) 블록될 수 있다.
>
> 같은 이유로 `StreamReader.ReadToEnd`는 절대 쓰면 안 된다. **`NetworkStream`에는 끝이 없기 때문이다.** 연결이 열려 있는 한, 네트워크 스트림은 클라이언트가 더 보내지 않을 것이라고 확신할 수 없다.
>
> `FileStream` 같은 다른 스트림은 이 비호환이 없다. 명확한 끝이 있고, 그 지점에서 `Read`가 0을 반환하며 즉시 돌아오기 때문이다.

### TCP 동시성

`TcpClient`와 `TcpListener`는 확장 가능한 동시성을 위해 태스크 기반 비동기 메서드를 제공한다. 블로킹 호출을 `*Async` 버전으로 바꾸고 반환된 태스크를 `await`하면 된다.

다음은 5,000바이트 길이의 요청을 받아 바이트를 뒤집어 되돌려 주는 비동기 TCP 서버다.

```csharp
async void RunServerAsync()
{
    var listener = new TcpListener (IPAddress.Any, 51111);
    listener.Start();
    try     { while (true) Accept (await listener.AcceptTcpClientAsync()); }
    finally { listener.Stop(); }
}

async Task Accept (TcpClient client)
{
    await Task.Yield();
    try
    {
        using (client)
        using (NetworkStream n = client.GetStream())
        {
            byte[] data = new byte [5000];
            int bytesRead = 0; int chunkSize = 1;
            while (bytesRead < data.Length && chunkSize > 0)
                bytesRead += chunkSize =
                    await n.ReadAsync (data, bytesRead, data.Length - bytesRead);

            Array.Reverse (data);                     // 바이트 순서를 뒤집는다
            await n.WriteAsync (data, 0, data.Length);
        }
    }
    catch (Exception ex) { Console.WriteLine (ex.Message); }
}
```

이 프로그램이 확장 가능한 이유는 요청이 진행되는 동안 스레드를 붙들지 않기 때문이다. 느린 네트워크에서 1,000개의 클라이언트가 한꺼번에 접속해 각 요청이 수 초씩 걸린다 해도, 이 프로그램은 그 시간 동안 1,000개의 스레드를 필요로 하지 않는다(동기 방식이라면 필요하다). `await` 앞뒤의 코드를 실행하는 짧은 순간에만 스레드를 빌린다.

`while` 루프가 읽기를 반복하는 것도 앞에서 본 이유 그대로다 — `ReadAsync` 한 번이 5,000바이트를 다 준다는 보장이 없다.

> **📌 `Accept`를 `await`하지 않는 이유**
>
> `RunServerAsync`의 루프는 `Accept(...)`가 반환한 태스크를 기다리지 않는다. 기다리면 한 번에 클라이언트 하나만 처리하는 서버가 된다. 대신 `Accept` 첫 줄의 `await Task.Yield()`가 이 메서드의 나머지를 즉시 다른 곳으로 넘겨서, 수락 루프가 곧바로 다음 연결을 받으러 가게 만든다.
>
> 다만 이 패턴은 **예외를 관찰하지 않는다.** `Accept` 안의 `try/catch`가 그것을 보완한다. 태스크를 버리는 코드에서 예외 처리를 빠뜨리면 실패가 조용히 사라진다(46.11절).

※.NET 6부터 `AcceptTcpClientAsync(CancellationToken)` 오버로드가 생겨 수신 루프를 깔끔하게 종료할 수 있다.

```csharp
try
{
    while (!ct.IsCancellationRequested)
        _ = HandleAsync (await listener.AcceptTcpClientAsync (ct), ct);
}
catch (OperationCanceledException) { /* 정상 종료 */ }
```

### Nagle 알고리즘과 `NoDelay`

TCP 스택은 작은 쓰기를 모아서 한 번에 보내려 한다. 이것이 **Nagle 알고리즘**이다. 대역폭 효율은 좋아지지만 지연이 생긴다 — 보통 수십 밀리초, 상대의 지연 ACK와 겹치면 최악의 경우 수백 밀리초다.

```csharp
var client = new TcpClient();
client.NoDelay = true;          // Nagle 끄기
// 또는 소켓에서 직접
client.Client.NoDelay = true;
```

| 트래픽 성격 | 권장 | 이유 |
|---|---|---|
| 작은 메시지를 자주, 지연이 중요 (RPC, 게임, 채팅) | `NoDelay = true` | Nagle 지연이 그대로 응답 시간이 된다 |
| 큰 데이터 전송 (파일, 백업) | 기본값 유지 | 패킷 효율이 이득 |
| 작은 쓰기를 여러 번 하는 프로토콜 | `NoDelay = false` + 애플리케이션 레벨 버퍼링 | 스스로 모아서 한 번에 쓰는 편이 더 낫다 |

`NoDelay = true`가 만능은 아니다. 헤더에 이어 본문을 따로 쓰는 코드에서 Nagle을 끄면 작은 패킷이 두 배로 늘어난다. **가장 좋은 답은 애플리케이션이 한 번에 쓰는 것**이다 — `BufferedStream`으로 감싸거나(40.3절), 헤더와 본문을 한 버퍼에 담아 한 번 `WriteAsync`한다.

### `Socket`과 `SocketAsyncEventArgs`

`TcpClient`·`TcpListener`는 편의 파사드다. 더 아래로 내려가면 `Socket`이 있다.

```csharp
using var listenSocket = new Socket (SocketType.Stream, ProtocolType.Tcp);
listenSocket.Bind (new IPEndPoint (IPAddress.Loopback, 7000));
listenSocket.Listen (backlog: 120);

while (true)
    _ = ProcessAsync (await listenSocket.AcceptAsync());
```

`Listen`의 인자는 **백로그** — 아직 `Accept`되지 않은 완료된 연결을 커널이 쌓아 두는 큐의 크기다. 이 값이 작으면 순간적인 접속 폭주에서 연결이 거부된다.

`Socket`이 노출하는 주요 옵션은 다음과 같다.

| 멤버 | 의미 |
|---|---|
| `NoDelay` | Nagle 알고리즘 비활성화 |
| `ReceiveBufferSize` / `SendBufferSize` | 커널 소켓 버퍼 크기 |
| `ReceiveTimeout` / `SendTimeout` | 동기 호출의 시한(비동기에는 적용되지 않는다) |
| `LingerState` | `Close` 시 미전송 데이터를 어떻게 처리할지 |
| `DualMode` | IPv6 소켓으로 IPv4도 받을지 |
| `SetSocketOption(...KeepAlive, true)` | TCP 킵얼라이브 프로브 |

극단적인 성능이 필요한 경로에서는 `SocketAsyncEventArgs`를 쓴다. 이것은 비동기 소켓 작업마다 발생하는 할당(태스크 객체, 콜백 클로저)을 없애기 위해 **작업 컨텍스트 객체를 미리 만들어 재사용**하는 API다.

```csharp
var args = new SocketAsyncEventArgs();
args.SetBuffer (buffer, 0, buffer.Length);
args.Completed += (s, e) => OnReceiveCompleted (e);

if (!socket.ReceiveAsync (args))   // true면 비동기 진행 중, false면 이미 동기 완료
    OnReceiveCompleted (args);
```

`ReceiveAsync`가 `false`를 반환하면 작업이 **동기적으로 완료된 것**이므로 `Completed` 이벤트가 발생하지 않는다. 이 이중 완료 경로를 다루는 것이 `SocketAsyncEventArgs`를 직접 쓰기 어려운 이유다.

> **💡 `SocketAsyncEventArgs`는 마지막 수단이다**
>
> 모던 .NET에서는 `Socket`의 `ValueTask` 기반 오버로드가 이미 대부분의 할당을 제거했다.
>
> ```csharp
> int n = await socket.ReceiveAsync (memory, SocketFlags.None, ct);   // ValueTask<int>
> ```
>
> 이 오버로드는 내부적으로 재사용 가능한 `IValueTaskSource`를 쓰기 때문에, 순차적으로 대기하는 한 태스크 객체를 할당하지 않는다(47.13절). 초당 수십만 연산이 아니라면 `SocketAsyncEventArgs`의 복잡도를 감당할 가치가 없다. 측정하고 나서 결정하라(67장).

### `System.IO.Pipelines`

소켓 데이터를 올바르게 파싱하는 일의 복잡도를 줄이기 위해 만들어진 고성능 I/O 라이브러리가 `System.IO.Pipelines`다. .NET Core 2.1과 함께 처음 배포됐으며, Kestrel 팀의 성능 작업에서 태어났다.

파이프라인은 앞에서 본 프레이밍 문제 — "버퍼 경계를 넘어가는 메시지를 어떻게 다룰 것인가" — 를 라이브러리 수준에서 해결한다.

```csharp
static async Task ProcessLinesAsync (Socket socket)
{
    PipeReader reader = PipeReader.Create (new NetworkStream (socket));

    while (true)
    {
        ReadResult result = await reader.ReadAsync();
        ReadOnlySequence<byte> buffer = result.Buffer;

        while (TryReadLine (ref buffer, out ReadOnlySequence<byte> line))
            ProcessLine (line);

        reader.AdvanceTo (buffer.Start, buffer.End);
        if (result.IsCompleted) break;
    }
    await reader.CompleteAsync();
}

static bool TryReadLine (ref ReadOnlySequence<byte> buffer,
                         out ReadOnlySequence<byte> line)
{
    SequencePosition? position = buffer.PositionOf ((byte)'\n');
    if (position == null) { line = default; return false; }

    line = buffer.Slice (0, position.Value);
    buffer = buffer.Slice (buffer.GetPosition (1, position.Value));
    return true;
}

static void ProcessLine (in ReadOnlySequence<byte> buffer)
{
    foreach (ReadOnlyMemory<byte> segment in buffer)
        Console.Write (Encoding.UTF8.GetString (segment.Span));
    Console.WriteLine();
}
```

`AdvanceTo(consumed, examined)`의 두 인자가 핵심이다. 첫 번째는 "여기까지 소비했다", 두 번째는 "여기까지 봤지만 아직 메시지를 완성하지 못했다"이다. 이 정보를 받은 파이프는 소비되지 않은 데이터를 유지한 채 다음 `ReadAsync`에서 이어 붙여 준다. 프레이밍 코드를 직접 짤 때 가장 성가신 부분이 사라진다.

클라이언트 쪽은 놀랄 만큼 짧다 — 표준 입력을 그대로 네트워크 스트림에 복사하면 끝이다.

```csharp
Socket clientSocket = new Socket (SocketType.Stream, ProtocolType.Tcp);
clientSocket.Connect (new IPEndPoint (IPAddress.Loopback, 7000));
await Console.OpenStandardInput().CopyToAsync (new NetworkStream (clientSocket));
```

`ReadOnlySequence<byte>`와 `Memory<byte>`의 의미론은 68장에서 다룬다.

> **📌 UDP는 반대 문제를 갖는다**
>
> `UdpClient`는 `SendAsync`/`ReceiveAsync`가 **데이터그램 단위**로 동작한다. 즉 메시지 경계가 **보존된다** — TCP와 정반대다. 대신 순서와 도착이 보장되지 않고, 데이터그램이 통째로 사라질 수 있으며, 경로 MTU를 넘는 크기는 단편화되어 신뢰성이 급격히 떨어진다. 실무 기준으로 안전한 페이로드 크기는 IPv4에서 대략 508바이트, 이더넷 환경이라면 1,400바이트 안쪽이다.

### TLS는 어디에

전송 계층에서 직접 통신하면서 암호화가 필요하면 `NetworkStream`을 `System.Net.Security.SslStream`으로 감싼다. `SslStream`은 40장에서 본 데코레이터 스트림의 전형이다.

```csharp
using var tcp = new TcpClient ("example.com", 443);
using var ssl = new SslStream (tcp.GetStream(), leaveInnerStreamOpen: false);
await ssl.AuthenticateAsClientAsync ("example.com");   // 이후 ssl 읽기·쓰기는 암호화된다
```

인증서 검증, 프로토콜 버전 고정, 상호 TLS 같은 세부는 44장에서 다룬다.

## 43.13 메일 전송과 수신 (`SmtpClient`, POP3 over TCP)

### `SmtpClient`

`System.Net.Mail`의 `SmtpClient`는 SMTP로 메일을 보낸다. 단순 텍스트 메시지라면 `Host`를 설정하고 `Send`를 부르면 끝이다.

```csharp
SmtpClient client = new SmtpClient();
client.Host = "mail.myserver.com";
client.Send ("from@adomain.com", "to@adomain.com", "subject", "body");
```

`MailMessage` 객체를 만들면 첨부 파일을 포함한 더 많은 옵션이 열린다.

```csharp
SmtpClient client = new SmtpClient();
client.Host = "mail.myisp.net";

MailMessage mm = new MailMessage();
mm.Sender = new MailAddress ("kay@domain.com", "Kay");
mm.From   = new MailAddress ("kay@domain.com", "Kay");
mm.To.Add (new MailAddress ("bob@domain.com", "Bob"));
mm.CC.Add (new MailAddress ("dan@domain.com", "Dan"));
mm.Subject = "Hello!";
mm.Body = "Hi there. Here's the photo!";
mm.IsBodyHtml = false;
mm.Priority = MailPriority.High;

Attachment a = new Attachment ("photo.jpg",
                               System.Net.Mime.MediaTypeNames.Image.Jpeg);
mm.Attachments.Add (a);
client.Send (mm);
```

스팸을 막기 위해 인터넷의 대부분의 SMTP 서버는 인증된 연결만 받고 SSL 통신을 요구한다.

```csharp
var client = new SmtpClient ("smtp.myisp.com", 587)
{
    Credentials = new NetworkCredential ("me@myisp.com", "MySecurePass"),
    EnableSsl = true
};
client.Send ("me@myisp.com", "someone@somewhere.com", "Subject", "Body");
Console.WriteLine ("Sent");
```

`DeliveryMethod`를 바꾸면 IIS를 통해 보내거나, 지정한 디렉터리에 `.eml` 파일로 각 메시지를 쓰게 할 수 있다. 개발 중에 유용하다.

```csharp
SmtpClient client = new SmtpClient
{
    DeliveryMethod = SmtpDeliveryMethod.SpecifiedPickupDirectory,
    PickupDirectoryLocation = @"c:\mail"
};
```

> **⚠️ `SmtpClient`는 새 개발에 권장되지 않는다**
>
> Microsoft 문서는 `SmtpClient`를 **호환용(compat-only)** 으로 표시하고 새 개발에 쓰지 말 것을 권고한다. 이유는 나이가 아니라 기능이다.
>
> - `EnableSsl`이 켜져도 실제 동작은 **STARTTLS**(평문으로 시작해 업그레이드)이고, 처음부터 암호화된 연결(implicit TLS, 465 포트)을 지원하지 않는다
> - OAuth 2.0(XOAUTH2) 인증을 지원하지 않는다 — 오늘날 Gmail·Microsoft 365가 요구하는 방식이다
> - MIME 구성이 제한적이고 국제화 주소(SMTPUTF8) 처리가 약하다
> - 비동기 API가 태스크 기반이 아닌 옛 이벤트 모델의 흔적을 갖는다
>
> 대안은 **MailKit**(과 그 MIME 계층인 MimeKit)이 사실상 표준이다. STARTTLS·implicit TLS·OAuth2·IMAP·POP3를 모두 지원한다. 다만 `SmtpClient`가 컴파일 오류를 내지는 않으므로, 사내 릴레이 서버로 평문 메일을 보내는 정도의 용도라면 계속 써도 된다. 인터넷 메일 제공자에 붙어야 한다면 처음부터 MailKit으로 가라.

| 요구 | `SmtpClient` | MailKit |
|---|---|---|
| 사내 릴레이(인증 없음) | 충분 | 가능 |
| STARTTLS(587) | 지원 | 지원 |
| implicit TLS(465) | 미지원 | 지원 |
| OAuth 2.0 | 미지원 | 지원 |
| 메일 수신(POP3/IMAP) | 없음 | 지원 |

### POP3를 TCP로 직접 구현하기

.NET은 POP3에 대해 **응용 계층 지원을 전혀 제공하지 않는다.** 그래서 POP3 서버에서 메일을 받으려면 TCP 계층에서 직접 써야 한다. 다행히 단순한 프로토콜이다. 대화는 이렇게 흐른다.

| 클라이언트 | 메일 서버 | 비고 |
|---|---|---|
| (연결) | `+OK Hello there.` | 환영 메시지 |
| `USER joe` | `+OK Password required.` | |
| `PASS password` | `+OK Logged in.` | |
| `LIST` | `+OK` / `1 1876` / `2 5412` / `3 845` / `.` | 각 메시지의 ID와 크기 |
| `RETR 1` | `+OK 1876 octets` / 본문... / `.` | 지정 ID의 메시지 조회 |
| `DELE 1` | `+OK Deleted.` | 서버에서 메시지 삭제 |
| `QUIT` | `+OK Bye-bye.` | |

각 명령과 응답은 개행(CR+LF)으로 끝난다. 예외는 여러 줄로 응답하는 `LIST`와 `RETR`로, 이들은 **점 하나만 있는 줄**로 끝난다.

`NetworkStream`에 `StreamReader`를 쓸 수 없으므로(43.12절), 버퍼링 없이 한 줄을 읽는 도우미부터 만든다.

```csharp
string ReadLine (Stream s)
{
    List<byte> lineBuffer = new List<byte>();
    while (true)
    {
        int b = s.ReadByte();
        if (b == 10 || b < 0) break;          // LF 또는 스트림 끝
        if (b != 13) lineBuffer.Add ((byte)b); // CR은 버린다
    }
    return Encoding.UTF8.GetString (lineBuffer.ToArray());
}
```

명령을 보내는 도우미도 필요하다. 응답이 항상 `+OK`로 시작해야 하므로 읽기와 검증을 한 번에 한다.

```csharp
void SendCommand (Stream stream, string line)
{
    byte[] data = Encoding.UTF8.GetBytes (line + "\r\n");
    stream.Write (data, 0, data.Length);
    string response = ReadLine (stream);
    if (!response.StartsWith ("+OK"))
        throw new Exception ("POP Error: " + response);
}
```

이 둘이 있으면 메일 조회는 간단하다. 110 포트(POP3 기본)로 TCP 연결을 맺고 대화를 시작한다. 아래 예제는 각 메시지를 무작위 이름의 `.eml` 파일에 쓰고 서버에서 삭제한다.

```csharp
using (TcpClient client = new TcpClient ("mail.isp.com", 110))
using (NetworkStream n = client.GetStream())
{
    ReadLine (n);                        // 환영 메시지를 읽는다
    SendCommand (n, "USER username");
    SendCommand (n, "PASS password");
    SendCommand (n, "LIST");             // 메시지 ID를 받는다

    List<int> messageIDs = new List<int>();
    while (true)
    {
        string line = ReadLine (n);      // 예: "1 1876"
        if (line == ".") break;
        messageIDs.Add (int.Parse (line.Split (' ')[0]));   // 메시지 ID
    }

    foreach (int id in messageIDs)       // 각 메시지를 조회한다
    {
        SendCommand (n, "RETR " + id);
        string randomFile = Guid.NewGuid().ToString() + ".eml";
        using (StreamWriter writer = File.CreateText (randomFile))
            while (true)
            {
                string line = ReadLine (n);   // 메시지의 다음 줄
                if (line == ".") break;       // 점 하나 = 메시지 끝
                if (line == "..") line = ".";  // 이중 점 이스케이프 해제
                writer.WriteLine (line);
            }
        SendCommand (n, "DELE " + id);   // 서버에서 삭제
    }
    SendCommand (n, "QUIT");
}
```

`if (line == "..") line = ".";` 한 줄이 프로토콜의 미묘함을 보여 준다. 본문의 어떤 줄이 점 하나로 시작하면 서버가 점을 하나 더 붙여 보내기 때문에(점 채우기, dot-stuffing), 클라이언트가 되돌려야 한다. 프로토콜을 직접 구현할 때 이런 세부를 빠뜨리면 특정 메일에서만 본문이 잘리는 버그가 된다.

> **⚠️ 이 코드는 평문이다**
>
> 위 예제는 110 포트에 평문으로 붙어 **암호를 그대로 전송한다.** 실사용에는 995 포트의 POP3S(implicit TLS)나 STARTTLS가 필요하다. `NetworkStream`을 `SslStream`으로 감싸면 되지만(43.12절), 그러고 나면 MIME 파싱·인증·오류 처리가 줄줄이 따라온다.
>
> NuGet의 오픈소스 POP3 라이브러리들이 TLS/SSL 연결 인증, MIME 파싱 등 프로토콜의 세부를 지원한다. 위 코드는 **프로토콜을 TCP 위에 직접 구현하는 방법을 배우기 위한 예제**로 읽어야 한다.

## 43.14 gRPC와 이진 프로토콜

### gRPC란

gRPC는 오픈소스 RPC(원격 프로시저 호출) 프레임워크다. 전송 계층으로 **HTTP/2**를, 메시지 직렬화로 **프로토콜 버퍼(Protobuf)** 를 쓴다. Protobuf는 언어 중립 계약 언어이기도 하다.

gRPC는 현대적인 고성능·크로스 플랫폼 응용을 염두에 두고 설계됐고, 사실상 모든 주요 언어에 구현이 있다. 서로 다른 운영체제와 언어로 만든 응용이 대화할 수 있다.

gRPC는 **의견이 뚜렷한 계약 우선(contract-first) 프레임워크**다. 계약은 `.proto` 파일에 정의한다. 이 파일이 API 정의와 주고받을 메시지를 담는다. 그다음 코드 생성이 각 언어·플랫폼에 맞는 강타입 클라이언트와 메시지를 만들어 낸다. gRPC의 언어는 이진이며 컴퓨터를 위해 설계됐다. 그래서 텍스트 기반 HTTP API보다 성능이 좋다. 원격 호출의 복잡도는 프레임워크가 감춘다 — 손으로 해야 했을 많은 일을 코드 생성 도구가 대신하고, 남는 일은 클라이언트의 메서드를 부르고 결과를 기다리는 것뿐이다.

### `.proto` 파일

```protobuf
syntax = "proto3";
option csharp_namespace = "CH09_GrpcService";
package greet;

service Greeter {                                          // 인사 서비스 정의
  rpc SayHello (HelloRequest) returns (HelloReply);        // 단항
  rpc SayHelloStream (HelloRequest) returns (stream HelloReply);  // 서버 스트리밍
}

message HelloRequest { string name = 1; }                  // 요청 메시지
message HelloReply   { string message = 1; }               // 응답 메시지
```

proto 언어는 단순하다. 문법 버전, 어셈블리 네임스페이스, 패키지 이름을 선언하고, RPC 요청·응답을 정의하는 서비스 정의를 제공하고, 요청·응답 메시지를 정의한다.

필드 뒤의 숫자(`= 1`)는 **필드 번호**이며, 이것이 스키마의 진짜 계약이다. 이름이 아니라 번호가 바이트에 실린다. 그래서 필드 이름은 자유롭게 바꿔도 호환이 유지되지만 번호를 바꾸면 즉시 깨진다. JSON에서는 이름이 계약이라는 41.1절의 대비가 여기서 정확히 반전된다.

> **📌 생성된 코드는 어디에 있나**
>
> 후드 아래에서 상당한 양의 코드 생성이 일어난다. 파일을 찾는다면 프로젝트의 `obj\Debug\net8.0\Protos` 폴더 안에 숨어 있다. `.csproj`의 `<Protobuf Include="..." GrpcServices="Client" />` 항목이 그 생성을 지시한다.

### 서버와 클라이언트

서버는 생성된 기반 클래스를 상속해 메서드를 재정의한다.

```csharp
public class GreeterService : Greeter.GreeterBase
{
    public override Task<HelloReply> SayHello (
        HelloRequest request, ServerCallContext context)
        => Task.FromResult (new HelloReply { Message = "Hello " + request.Name });

    public override async Task SayHelloStream (
        HelloRequest request,
        IServerStreamWriter<HelloReply> responseStream,
        ServerCallContext context)
    {
        for (int i = 0; i < 10; i++)
        {
            await responseStream.WriteAsync (new HelloReply
            {
                Message = $"Response Stream Message: {i}"
            });
            await Task.Delay (TimeSpan.FromSeconds (1));
        }
    }
}
```

클라이언트는 채널을 만들고 생성된 클라이언트 타입을 통해 호출한다.

```csharp
GrpcChannel channel = GrpcChannel.ForAddress ("https://localhost:5001");
var greeter = new Greeter.GreeterClient (channel);

HelloReply reply = await greeter.SayHelloAsync (         // 단항 호출
    new HelloRequest { Name = "gRPC Demonstration!" });
Console.WriteLine ($"Message From gRPC Server: {reply.Message}");

AsyncServerStreamingCall<HelloReply> stream =            // 서버 스트리밍 호출
    greeter.SayHelloStream (new HelloRequest { Name = "Streaming!" });

await foreach (HelloReply item in stream.ResponseStream.ReadAllAsync())
    Console.WriteLine (item.Message);
```

`await foreach`가 비동기 스트림이다(28장·47.11절).

### 네 가지 호출 유형

| 유형 | `.proto` 표기 | 클라이언트가 보내는 것 | 서버가 보내는 것 | 전형적 용도 |
|---|---|---|---|---|
| 단항(unary) | `rpc M(Req) returns (Resp)` | 메시지 1개 | 메시지 1개 | 일반 RPC. REST의 대체 |
| 서버 스트리밍 | `returns (stream Resp)` | 메시지 1개 | 메시지 N개 | 구독, 진행 상황 알림 |
| 클라이언트 스트리밍 | `rpc M(stream Req) returns (Resp)` | 메시지 N개 | 메시지 1개 | 대량 업로드, 텔레메트리 수집 |
| 양방향 스트리밍 | `rpc M(stream Req) returns (stream Resp)` | 메시지 N개 | 메시지 N개 | 채팅, 실시간 협업 |

네 유형 모두 하나의 HTTP/2 연결 위에서 멀티플렉싱된다. 이것이 gRPC가 연결 하나로 수천 개의 동시 호출을 처리할 수 있는 이유다(43.15절).

### REST와의 비교

HTTP API는 **콘텐츠 우선**이다. URL의 모양, HTTP 메서드, JSON·XML 같은 것을 고민한다. REST API는 코드 우선이어서 보통 코드를 먼저 쓰고 나중에 Swagger나 RAML 계약을 생성한다. 텍스트 기반이라 사람이 읽을 수 있고 도구만 있으면 디버깅이 쉽지만 gRPC보다 느리고, 저수준 HTTP를 다루므로 요청·응답·라우팅을 더 많이 생각해야 한다. 대신 제어 수준이 높고 가장 넓은 개발자층에 호소한다.

| 항목 | REST/JSON | gRPC |
|---|---|---|
| 계약 | 코드 우선(사후 OpenAPI) | 계약 우선(`.proto`) |
| 페이로드 | 텍스트(JSON) | 이진(Protobuf) |
| 전송 | HTTP/1.1 이상 | HTTP/2 필수 |
| 스트리밍 | 제한적(SSE, 청크) | 4가지 유형 모두 |
| 사람이 읽기 | 쉽다 | 도구 필요 |
| 브라우저 직접 호출 | 가능 | 불가(gRPC-Web 필요) |
| 스키마 진화 | 이름 기준, 느슨함 | 필드 번호 기준, 엄격함 |

크기 차이는 실제로 크다. Blazor 기본 템플릿의 데이터 조회 페이지가 쓰는 JSON 데이터는 627바이트인데, 같은 데이터를 gRPC로 바꾸면 309바이트가 된다. 전송·수신할 데이터가 적으니 더 빠르고, 스로틀링에 걸리기 전에 더 많은 요청을 보낼 수 있다.

> **📌 gRPC-Web**
>
> 브라우저는 HTTP/2 프레임을 직접 제어할 수 없어 gRPC를 그대로 호출하지 못한다. 그래서 웹 프로젝트를 위해 **gRPC-Web**이라는 래퍼가 만들어졌다. 이것으로 HTTP/1.1과 HTTP/2 양쪽과 호환되는 종단 간 파이프라인을 만들 수 있다. Blazor WebAssembly 클라이언트에서는 채널을 만들 때 핸들러를 끼운다.
>
> ```csharp
> using var channel = GrpcChannel.ForAddress ("https://localhost:7272/",
>     new GrpcChannelOptions
>     {
>         HttpHandler = new GrpcWebHandler (new HttpClientHandler())
>     });
> ```
>
> 서버 쪽은 `app.UseGrpcWeb(new GrpcWebOptions { DefaultEnabled = true })`를 파이프라인에 넣고, 브라우저에서 호출한다면 CORS에서 `Grpc-Status`, `Grpc-Message`, `Grpc-Encoding`, `Grpc-Accept-Encoding` 헤더를 노출해야 한다. gRPC-Web은 IPC에서 TCP 외에 명명 파이프와 유닉스 도메인 소켓도 쓸 수 있게 해 준다.

> **⚠️ gRPC를 공용 API로 내보내기 전에 확인할 것**
>
> - **중간 장비** — 일부 기업 프록시·L7 방화벽은 HTTP/2를 종단시키거나 알 수 없는 콘텐츠 타입을 차단한다
> - **로드밸런서** — HTTP/2는 연결 하나에 스트림을 몰아넣으므로, L4 로드밸런서 뒤에서는 트래픽이 특정 인스턴스에 쏠린다. L7(gRPC 인지) 로드밸런싱이 필요하다
> - **메시지 크기 제한** — 서버는 기본 수신 크기 제한을 갖는다. 큰 페이로드는 `MaxReceiveMessageSize`/`MaxSendMessageSize`를 조정하거나 스트리밍으로 쪼갠다
> - **디버깅** — `curl`로 확인할 수 없다. `grpcurl` 같은 전용 도구가 필요하다
>
> 조직 내부의 서비스 간 통신이라면 gRPC의 이득이 크다. 불특정 다수의 외부 개발자가 호출할 API라면 REST가 여전히 현실적인 선택이다.

## 43.15 네트워크 성능 — 커넥션 풀링, HTTP/2·3, 압축

### 비용의 구조

HTTP 요청 하나의 시간은 대략 이렇게 쪼개진다.

```text
  DNS 조회 ──▶ TCP 핸드셰이크 ──▶ TLS 핸드셰이크 ──▶ 요청 전송 ──▶ 서버 처리 ──▶ 응답 수신
   0~수십ms      1 RTT             1~2 RTT           대역폭       애플리케이션    대역폭

  ├──────────── 연결 수립 (재사용하면 0이 된다) ────────────┤
```

지연 시간이 큰 경로(모바일, 대륙 간)에서 앞의 세 단계가 전체의 절반을 넘는 경우가 흔하다. **네트워크 성능 최적화의 첫 번째 규칙은 연결을 재사용하는 것**이고, 두 번째는 왕복 횟수를 줄이는 것이다.

### 커넥션 풀링

`SocketsHttpHandler`는 서버(스킴+호스트+포트)별로 연결 풀을 유지한다. 요청이 끝나면 연결이 풀로 돌아가고 다음 요청이 그것을 재사용한다. 43.9절에서 본 수명 관리가 이 풀의 정책이다.

| 옵션 | 조정 지침 |
|---|---|
| `MaxConnectionsPerServer` | 기본은 무제한. 상대 서버를 보호하거나 자원을 제한하려면 낮춘다. 너무 낮으면 요청이 큐에서 대기한다 |
| `PooledConnectionLifetime` | 2~15분. DNS 반영 지연과 재수립 비용의 균형(43.9절) |
| `PooledConnectionIdleTimeout` | 유휴 연결 정리. 트래픽이 산발적이면 늘려서 재수립을 줄인다 |

> **⚠️ `MaxConnectionsPerServer`가 만드는 조용한 병목**
>
> 이 값을 10으로 설정하고 동시에 100개의 요청을 보내면, 90개는 **큐에서 조용히 기다린다.** 타임아웃(`HttpClient.Timeout`)은 큐 대기 시간까지 포함해서 재므로, 실제 서버는 빠른데 클라이언트에서 타임아웃이 나는 상황이 생긴다.
>
> 증상은 "서버 로그에는 100ms인데 클라이언트는 30초 타임아웃"이다. `dotnet-counters`의 `System.Net.Http` 카운터에서 요청 큐 대기 시간을 보면 바로 드러난다.

### HTTP/1.1의 한계와 HTTP/2

HTTP/1.1은 연결 하나에서 요청을 **순서대로** 처리한다. 파이프라이닝은 사실상 쓰이지 않는다. 그래서 동시 요청 수만큼 연결이 필요하고, 앞선 요청이 느리면 뒤가 막힌다(헤드 오브 라인 블로킹).

HTTP/2는 하나의 TCP 연결 위에서 **스트림을 멀티플렉싱**한다.

| | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 전송 | TCP | TCP | **QUIC**(UDP 위) |
| 동시 요청 | 연결 수만큼 | 연결 하나에 다수 스트림 | 연결 하나에 다수 스트림 |
| 헤더 | 매번 텍스트로 반복 | HPACK 압축 | QPACK 압축 |
| 헤드 오브 라인 블로킹 | 애플리케이션 계층에서 발생 | TCP 계층에서 여전히 발생 | 없음(스트림별 독립) |
| 연결 수립 | TCP + TLS(2~3 RTT) | TCP + TLS | QUIC이 TLS 통합(1 RTT, 재개 시 0-RTT) |
| .NET 지원 | 항상 | .NET Core 3.0 이상, HTTPS에서 자동 협상 | ※.NET 7에서 정식 |

HTTP/2는 TLS의 ALPN으로 협상되므로, `https://` 주소로 HTTP/2를 지원하는 서버에 요청하면 자동으로 쓰인다. 특별히 할 일이 없다.

> **⚠️ HTTP/2 연결 하나가 병목이 될 수 있다**
>
> HTTP/2는 연결 하나에 모든 스트림을 실으므로 연결 수는 줄지만, 서버가 정한 **최대 동시 스트림 수**(`SETTINGS_MAX_CONCURRENT_STREAMS`, 흔히 100)에 도달하면 나머지가 대기한다. 또 TCP 패킷 하나가 유실되면 그 연결의 **모든 스트림이 함께 멈춘다** — TCP 계층의 헤드 오브 라인 블로킹은 HTTP/2도 해결하지 못했다.
>
> 고부하 클라이언트에서는 연결을 추가로 열게 허용하는 편이 낫다.
>
> ```csharp
> new SocketsHttpHandler { EnableMultipleHttp2Connections = true }
> ```
>
> 기본값은 `false`다.

HTTP/3는 전송을 TCP에서 QUIC(UDP 위에 구현된 프로토콜)으로 바꿔 그 문제를 없앤다. 패킷 손실이 한 스트림에만 영향을 주고, TLS가 전송에 통합되어 핸드셰이크 왕복이 줄어든다. 무선 네트워크에서 IP가 바뀌어도 연결이 유지된다.

```csharp
var req = new HttpRequestMessage (HttpMethod.Get, url)
{
    Version = HttpVersion.Version30,
    VersionPolicy = HttpVersionPolicy.RequestVersionOrLower
};
```

> **⚠️ HTTP/3에는 플랫폼 요구 사항이 있다**
>
> .NET의 QUIC 구현은 `msquic` 라이브러리에 의존한다. 리눅스에서는 배포판 패키지(`libmsquic`)를 설치해야 하고, Windows에서는 Windows 11 또는 Windows Server 2022 이상이 필요하다. 요건이 충족되지 않으면 요청은 조용히 하위 버전으로 내려간다(`RequestVersionOrLower`인 경우) 또는 실패한다(`RequestVersionExact`인 경우).
>
> 그래서 HTTP/3를 켠 뒤에는 반드시 **응답의 `Version`을 확인해서 실제로 쓰이고 있는지 검증**해야 한다. "켰다고 생각했는데 계속 HTTP/2였다"가 가장 흔한 결말이다.

### 압축

전송량 자체를 줄이는 가장 값싼 수단이다. 텍스트를 인터넷으로 보낼 때 문자가 많을수록 파일이 커지고, 페이지가 커질수록 로드 시간이 늘어난다. deflate 또는 gzip 압축을 켜면 요청과 응답의 크기가 줄어들며, 웹 서버 대부분이 웹 압축을 제공한다. 클라이언트 쪽에서는 한 줄이다.

```csharp
new SocketsHttpHandler { AutomaticDecompression = DecompressionMethods.All }  // ※.NET 5
```

이것이 `Accept-Encoding` 헤더를 보내고 응답을 자동으로 해제한다(개별 지정은 `GZip | Deflate | Brotli`). Brotli는 gzip보다 압축률이 높지만 CPU를 더 쓴다.

| 데이터 | 압축 효과 |
|---|---|
| JSON, HTML, CSS, JS | 매우 큼(흔히 70~90% 감소) |
| 이미 압축된 것(JPEG, PNG, 동영상, ZIP) | 없음. CPU만 낭비 |
| 작은 응답(< 1KB) | 헤더 오버헤드로 오히려 커질 수 있다 |

압축 스트림 API 자체는 40.7절에서 다룬다. 웹 자원 최적화의 나머지 — 이미지 포맷 선택과 압축, HTML/CSS/JS 미니피케이션, 서버 측 필터링과 페이징 — 는 전송량을 줄이는 같은 원리의 다른 적용이다.

### Keep-Alive와 타임아웃 설계

HTTP/1.1은 기본적으로 연결을 유지한다(`Connection: keep-alive`). TCP 수준의 킵얼라이브와는 다른 개념이다. HTTP/2에서는 `SocketsHttpHandler.KeepAlivePingDelay`/`KeepAlivePingTimeout`으로 PING 프레임을 보내 죽은 연결을 빨리 감지할 수 있다.

타임아웃은 **한 겹으로 설계하면 안 된다.** 계층별로 다른 실패를 잡는다.

| 설정 | 무엇을 자르나 | 권장 |
|---|---|---|
| `SocketsHttpHandler.ConnectTimeout` | TCP 연결 수립 | 3~5초. 죽은 노드를 빨리 포기한다 |
| `HttpClient.Timeout` | 요청 전체(큐 대기 포함) | 상대 서비스의 SLA + 여유 |
| 호출별 `CancellationToken` | 논리적 작업 전체 | 상위 요청의 남은 예산 |
| `PooledConnectionLifetime` | 연결의 은퇴 시점 | 2~15분(43.9절) |
| `Expect100ContinueTimeout` | 100-continue 대기 | 큰 본문 업로드가 있으면 조정 |

> **⚠️ `HttpClient.Timeout`과 `CancellationToken`의 관계**
>
> 둘은 **경쟁**한다. 먼저 만료되는 쪽이 이긴다. 내부적으로 `HttpClient`는 `Timeout` 기반의 토큰과 전달받은 토큰을 연결(linked)해서 쓴다. 그래서 다음 규칙이 나온다.
>
> - 호출별 토큰의 시한이 `Timeout`보다 길면, **`Timeout`이 먼저 자른다.** 호출별 시한을 늘리려면 `Timeout`도 함께 늘려야 한다
> - `Timeout`을 `InfiniteTimeSpan`으로 두고 호출별 토큰만 쓰는 설계가 가장 예측 가능하다
> - `ResponseHeadersRead`로 얻은 스트림을 읽는 동안에는 `Timeout`이 적용되지 않는다. 그 구간은 반드시 토큰으로 보호한다
>
> ```csharp
> var client = new HttpClient (handler) { Timeout = Timeout.InfiniteTimeSpan };
> using var cts = CancellationTokenSource.CreateLinkedTokenSource (callerToken);
> cts.CancelAfter (TimeSpan.FromSeconds (10));
> var res = await client.GetAsync (url, HttpCompletionOption.ResponseHeadersRead, cts.Token);
> ```
>
> 타임아웃·재시도·취소를 하나의 예산으로 묶는 설계는 51.4절에서 다룬다.

### 캐싱

가장 빠른 요청은 보내지 않은 요청이다. 자원을 요청한 컴퓨터에 캐시해 두면 네트워크 트래픽과 로드 시간이 줄어든다. 자원이 필요할 때 캐시에 있는지 먼저 확인하고, 있으면 만료 시각을 검사한 뒤 사용한다. 만료됐거나 없으면 내려받아 캐시에 저장한다. .NET 쪽 도구는 `Microsoft.Extensions.Caching.Memory`의 `IMemoryCache`이며, `SetSlidingExpiration`(마지막 접근 기준)과 `SetAbsoluteExpiration`(절대 시각)으로 만료 정책을 정한다.

```csharp
builder.Services.AddMemoryCache();

var options = new MemoryCacheEntryOptions().SetSlidingExpiration (TimeSpan.FromSeconds (20));
_memoryCache.Set (key, value, options);
if (_memoryCache.TryGetValue (key, out DateTime whenCached)) { /* ... */ }
```

HTTP 수준에서는 조건부 요청이 있다. 서버가 준 `ETag`나 `Last-Modified`를 보관했다가 다음 요청에 `If-None-Match`/`If-Modified-Since`로 되돌려 보내면, 바뀐 것이 없을 때 서버가 본문 없이 **304 Not Modified**만 보낸다.

```csharp
var req = new HttpRequestMessage (HttpMethod.Get, url);
if (cachedETag is not null)
    req.Headers.IfNoneMatch.Add (new EntityTagHeaderValue (cachedETag));
using var res = await client.SendAsync (req);
if (res.StatusCode == HttpStatusCode.NotModified) return cachedBody;  // 본문이 없다
```

> **⚠️ `HttpClient`는 HTTP 캐시를 구현하지 않는다**
>
> 브라우저와 달리 `HttpClient`에는 `Cache-Control`을 해석하는 캐시 계층이 **없다.** 서버가 `max-age=3600`을 보내도 다음 요청은 그냥 다시 나간다. 캐싱이 필요하면 위처럼 직접 구현하거나 캐싱 `DelegatingHandler`를 만든다(43.7절).

`System.Net.Http` 카운터에서 `requests-started`, `current-requests`, 연결 수 지표를 볼 수 있다. ※.NET 8부터는 `System.Diagnostics.Metrics` 기반의 표준 계측(`http.client.request.duration` 등)이 추가되어 OpenTelemetry로 곧바로 흘려보낼 수 있다. 관측 가능성 전반은 75장에서 다룬다. 웹 앱이라면 브라우저 개발자 도구의 네트워크 탭(요청별 상태·크기·시간과 워터폴)과 성능 탭(로딩·스크립팅·렌더링·시스템·유휴 시간 분해)이 1차 진단에 충분하다.

> **💡 최적화 순서**
>
> 네트워크 성능 작업은 이 순서로 하면 대개 어긋나지 않는다.
>
> 1. **연결을 재사용한다** — `IHttpClientFactory` 또는 정적 클라이언트 + `PooledConnectionLifetime`
> 2. **왕복을 줄인다** — 배치 API, 조건부 요청, 캐싱, 후행 슬래시 지키기(43.3절)
> 3. **전송량을 줄인다** — 압축, 필요한 필드만 요청, 페이징
> 4. **프로토콜을 올린다** — HTTP/2, 필요하면 HTTP/3, 내부 통신은 gRPC
> 5. **그다음에야 저수준으로 간다** — `Socket`, 파이프라인, 무할당 경로
>
> 1번을 건너뛰고 5번부터 시작하는 코드를 자주 본다. 측정 없이 시작하지 마라(67장).

## 이 장의 요약

- **먼저 정할 것은 API가 아니라 계층이다.** 소켓 → `TcpClient`/`UdpClient` → `HttpClient` → 상위 프레임워크로 갈수록 편해지고 자유는 줄어든다. .NET이 지원하지 않는 프로토콜이거나 사설 프로토콜일 때만 전송 계층으로 내려간다.
- **`Uri`의 후행 슬래시는 장식이 아니다.** `BaseAddress`는 슬래시로 끝내고 상대 경로는 슬래시로 시작하지 않는다. 이 두 줄이 `HttpClient` 404의 큰 부분을 없앤다.
- **값을 인코딩할 때는 `Uri.EscapeDataString`뿐이다.** `EscapeUriString`은 `&`와 `=`를 남기기 때문에 사용자 입력이 쿼리 구조를 바꿔 버린다. 그래서 .NET 6에서 폐기됐다.
- **`HttpClient`는 HTTP 오류를 예외로 만들지 않는다.** 404도 500도 정상 반환이고, `EnsureSuccessStatusCode()`를 불러야 예외가 된다. 반면 DNS·연결·TLS 실패는 예외다.
- **요청 헤더와 콘텐츠 헤더는 다른 컬렉션이다.** `Content-Type`을 `request.Headers`에 넣으면 "Misused header name" 예외가 난다.
- **`HttpRequestMessage`와 스트림 콘텐츠는 재사용할 수 없다.** 재시도 로직은 요청을 값이 아니라 팩터리로 다뤄야 하고, 본문은 메모리 기반이어야 한다.
- **`HttpClient` 수명은 두 극단 사이의 균형 문제다.** 매번 만들면 `TIME_WAIT` 소켓이 임시 포트를 고갈시키고, 영구 싱글턴은 DNS 변경을 따라가지 못한다. `PooledConnectionLifetime`이나 `IHttpClientFactory`의 핸들러 교체가 그 균형을 잡는다.
- **`HttpClient.Timeout`은 요청 전체에 적용된다.** 연결 타임아웃도 읽기 타임아웃도 아니다. 대용량 전송이 있으면 `Timeout`은 무한으로 두고 호출별 `CancellationToken`으로 시한을 건다.
- **TCP에는 메시지 경계가 없다.** 길이 접두사나 구분자로 프레이밍을 직접 정의해야 하고, 길이 접두사에는 반드시 상한을 둔다. `NetworkStream`에 `StreamReader`를 붙이면 미리 읽기 버퍼 때문에 무기한 블록될 수 있다.
- **`HttpListener`와 `SmtpClient`는 새 개발의 기본값이 아니다.** 전자는 도구·스텁용이고 실서비스는 Kestrel이며, 후자는 OAuth2와 implicit TLS를 지원하지 않으므로 인터넷 메일에는 MailKit 계열이 필요하다.
- **gRPC의 계약은 이름이 아니라 필드 번호다.** JSON과 정확히 반대다. 이진 프레이밍과 HTTP/2 멀티플렉싱 덕에 내부 서비스 간 통신에서 유리하지만, 브라우저·중간 장비·L4 로드밸런서라는 제약이 따라온다.
- **네트워크 최적화의 순서는 연결 재사용 → 왕복 감소 → 전송량 감소 → 프로토콜 상향 → 저수준화다.** 1번을 건너뛰고 5번부터 손대는 코드가 흔하다.

## 연습 문제

1. `IPAddress.None`과 `IPAddress.Broadcast`, `IPAddress.IPv6Any`와 `IPAddress.IPv6None`을 각각 `Equals`로 비교해 결과를 확인하라. 그다음 "주소가 지정되지 않았다"를 표현하는 코드를 이 상수들로 짤 때 어떤 오판이 가능한지 예를 만들어 보라.

2. `BaseAddress`를 `https://httpbin.org/anything` 과 `https://httpbin.org/anything/` 두 가지로 두고, 상대 경로를 `sub`와 `/sub`로 조합한 네 가지 요청을 보내라. 실제로 도달한 URL(응답 본문의 `url` 필드)을 기록하고, 네 결과가 왜 그렇게 나오는지 RFC의 참조 해석 규칙으로 설명하라.

3. 검색어에 `a&b=c`를 넣어 쿼리 문자열을 만들되 (a) 그대로 연결, (b) `WebUtility.UrlEncode`, (c) `Uri.EscapeDataString` 세 가지로 각각 만들어 에코 서비스에 보내라. 서버가 파싱한 파라미터 목록이 어떻게 달라지는지 비교하고, (a)가 주입 취약점이 되는 시나리오를 한 문장으로 적어라.

4. 100MB 이상의 파일을 내려받는 코드를 (a) `GetByteArrayAsync`, (b) `GetAsync` 기본 옵션, (c) `GetAsync` + `ResponseHeadersRead` + `CopyToAsync` 세 가지로 작성하고, `MemoryDiagnoser`나 작업 관리자로 최대 메모리 사용량을 비교하라. (c)에서 `using`을 일부러 빼고 요청을 100번 반복했을 때 처리량이 어떻게 변하는지도 측정하라.

5. `DelegatingHandler`를 상속해 요청·응답을 기록하는 핸들러와 5xx에서 3회 재시도하는 핸들러를 만들어라. 두 핸들러의 등록 순서를 바꿔 가며 로그 줄 수가 어떻게 달라지는지 확인하고, `StreamContent`를 본문으로 쓴 POST를 재시도시켰을 때 무슨 일이 일어나는지 서버에 도달한 바이트 수로 확인하라.

6. `TcpListener`로 에코 서버를, `TcpClient`로 클라이언트를 만들되 프레이밍 없이 문자열을 그대로 쓰고 읽어라. 로컬에서 잘 동작하는 것을 확인한 뒤, 클라이언트가 짧은 메시지를 1,000번 연속으로 보내게 하고 서버가 받은 "메시지" 개수를 세라. 개수가 1,000이 아닌 이유를 설명하고, 길이 접두사 프레이밍을 넣어 다시 측정하라.

7. 같은 엔드포인트를 향해 (a) 요청마다 `new HttpClient()`, (b) 정적 싱글턴, (c) 정적 싱글턴 + `PooledConnectionLifetime = 30초` 세 가지 클라이언트로 초당 수백 건의 요청을 수 분간 보내라. `netstat`(또는 `ss -s`)로 `TIME_WAIT` 소켓 수를, `dotnet-counters`로 요청 지표를 함께 기록하고 세 곡선을 비교하라.
