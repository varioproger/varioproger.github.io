## 40.1 스트림 아키텍처 — 백킹 스토어 / 데코레이터 / 어댑터

.NET의 스트림 아키텍처는 세 개념을 축으로 돌아간다. **백킹 스토어(backing store)**, **데코레이터(decorator)**, **어댑터(adapter)**다. 이 셋의 역할 분담을 이해하면 `System.IO`의 타입 수십 개가 한 장의 그림으로 정리된다.

### 백킹 스토어 — 데이터가 실제로 있는 곳

백킹 스토어는 입출력을 유의미하게 만드는 **종착점**이다. 정확히 말하면 바이트를 순차적으로 **읽어낼 수 있는 소스**, 바이트를 순차적으로 **써넣을 수 있는 목적지** 둘 중 하나이거나 둘 다인 것을 말한다. 파일, 네트워크 연결, 메모리 블록, OS 파이프가 전부 백킹 스토어다.

그런데 백킹 스토어는 프로그래머에게 노출되지 않으면 쓸모가 없다. 그 노출을 담당하는 표준 클래스가 `Stream`이며, 읽기·쓰기·위치 지정을 위한 표준 메서드 집합을 드러낸다. 배열과 결정적으로 다른 점이 하나 있다. 배열은 뒷받침하는 데이터 전체가 한꺼번에 메모리에 존재한다. 스트림은 데이터를 **직렬로** — 한 번에 한 바이트씩, 또는 감당 가능한 크기의 블록 단위로 — 다룬다. 그래서 백킹 스토어의 크기가 얼마든 스트림은 **작고 고정된 양의 메모리**만 쓴다. 100GB 파일을 4KB 버퍼로 훑을 수 있는 이유가 이것이다.

### 데코레이터 — 흐르는 데이터를 변형한다

데코레이터 스트림은 **다른 스트림을 먹고 산다**. 자기 백킹 스토어가 없고, 생성자로 받은 스트림에서 데이터를 끌어와 어떤 식으로든 변형한다. `DeflateStream`(압축), `CryptoStream`(암호화, 44.5절), `BufferedStream`(버퍼링)이 대표적이다.

데코레이터 구조가 주는 이점은 네 가지다.

1. 백킹 스토어 스트림이 압축·암호화 같은 기능을 **직접 구현할 필요가 없다**.
2. 데코레이션되어도 **인터페이스가 바뀌지 않는다**. `Stream`을 받는 코드는 그것이 무엇으로 감싸였는지 몰라도 된다.
3. 데코레이터는 **런타임에** 연결한다. 컴파일 타임에 조합이 고정되지 않는다.
4. 데코레이터끼리 **체인**으로 엮을 수 있다. 압축한 뒤 암호화하는 식이다.

### 어댑터 — 바이트를 사람이 쓰는 타입으로 바꾼다

백킹 스토어 스트림도 데코레이터 스트림도 **오로지 바이트만** 다룬다. 유연하고 효율적이지만 애플리케이션은 대개 텍스트나 XML 같은 더 높은 수준에서 일한다. 어댑터가 이 간극을 메운다 — 스트림을 감싸서 특정 형식에 특화된 타입 지정 메서드를 가진 클래스로 바꾼다. 텍스트 리더는 `ReadLine`을, XML 라이터는 `WriteAttributes`를 노출한다.

> **📌 어댑터는 데코레이터와 무엇이 다른가**
>
> 어댑터도 데코레이터처럼 스트림을 감싼다. 결정적 차이는 **어댑터는 그 자체가 `Stream`이 아니라는 것**이다. `StreamReader`는 `Stream`을 상속하지 않고 `TextReader`를 상속한다. 어댑터는 바이트 지향 메서드를 대개 완전히 숨긴다. 반면 `GZipStream`은 `Stream`이므로 다시 다른 데코레이터로 감쌀 수 있다.
>
> 이 구분이 실무에서 중요한 이유: 체인의 **중간에는 데코레이터만** 올 수 있고, **어댑터는 항상 체인의 맨 끝**에 온다.

### 세 계층 그림

```text
┌─────────────────────────────────────────────────────────────┐
│  어댑터 (Stream이 아님 — 체인의 끝)                          │
│   StreamReader  StreamWriter  StringReader  BinaryWriter    │
│   XmlReader     XmlWriter                                   │
└──────────────────────────┬──────────────────────────────────┘
                           │ char / int / string / XML 노드
                           ↓
┌─────────────────────────────────────────────────────────────┐
│  데코레이터 스트림 (Stream — 몇 겹이든 쌓을 수 있음)         │
│   DeflateStream  GZipStream  BrotliStream                   │
│   CryptoStream(44.5절)  BufferedStream  SslStream(43장)     │
└──────────────────────────┬──────────────────────────────────┘
                           │ byte[]  /  Span<byte>
                           ↓
┌─────────────────────────────────────────────────────────────┐
│  백킹 스토어 스트림 (Stream — 체인의 바닥)                   │
│  ┌────────────┐ ┌──────────────┐ ┌────────────┐ ┌────────┐  │
│  │ FileStream │ │ MemoryStream │ │ PipeStream │ │Network │  │
│  └─────┬──────┘ └──────┬───────┘ └─────┬──────┘ └───┬────┘  │
└────────┼───────────────┼───────────────┼────────────┼───────┘
         ↓               ↓               ↓            ↓
      디스크          RAM 배열       OS 파이프      소켓
```

체인을 조립하는 방법은 단순하다. **한 객체를 다른 객체의 생성자에 넘기면 된다.**

```csharp
using var file   = File.Create("data.gz");                       // 백킹 스토어
using var gzip   = new GZipStream(file, CompressionMode.Compress); // 데코레이터
using var writer = new StreamWriter(gzip);                        // 어댑터

writer.WriteLine("압축되어 파일에 기록된다");
```

이 세 줄이 이 장 전체의 요약이다. `StreamWriter`는 문자열을 UTF-8 바이트로 바꿔 아래로 넘기고, `GZipStream`은 그 바이트를 압축해 아래로 넘기고, `FileStream`은 그것을 디스크에 쓴다. **각 계층은 자기 일만 하고, 아래 계층이 무엇인지 모른다.**

> **💡 "이건 어느 계층인가"를 먼저 물어라**
>
> 새로운 I/O 타입을 만났을 때 던질 첫 질문은 "이게 `Stream`을 상속하는가"이고, 두 번째는 "생성자가 다른 `Stream`을 받는가"다. 두 답이 모두 예이면 데코레이터, 첫 답만 예이면 백킹 스토어, 첫 답이 아니오면 어댑터다. 이 세 갈래만 알면 처음 보는 타입도 어디에 끼워야 할지 안다.

> **📌 `System.IO.Pipelines`는 다른 물건이다**
>
> `System.IO.Pipelines`의 `Pipe`/`PipeReader`/`PipeWriter`는 이름이 비슷하지만 40.3절의 `PipeStream`과 아무 관계가 없다. 고성능 네트워크 서버에서 버퍼 관리·역압(backpressure)·부분 메시지 파싱을 라이브러리가 대신 처리해 주는 별개의 API다. Kestrel과 gRPC가 내부에서 쓴다. 이 책에서는 다루지 않는다.

## 40.2 스트림 사용법 — 읽기·쓰기, 탐색(seek), 닫기·플러시, 타임아웃, 스레드 안전성

추상 클래스 `Stream`은 모든 스트림의 기반이다. 세 가지 기본 동작 — **읽기, 쓰기, 탐색** — 과 **닫기·플러시·타임아웃 설정** 같은 관리 작업을 위한 멤버를 정의한다.

### `Stream`의 멤버 전수

| 범주 | 멤버 |
|---|---|
| 읽기 | `public abstract bool CanRead { get; }` · `public abstract int Read (byte[] buffer, int offset, int count)` · `public virtual int ReadByte()` |
| 쓰기 | `public abstract bool CanWrite { get; }` · `public abstract void Write (byte[] buffer, int offset, int count)` · `public virtual void WriteByte (byte value)` |
| 탐색 | `public abstract bool CanSeek { get; }` · `public abstract long Position { get; set; }` · `public abstract long Length { get; }` · `public abstract void SetLength (long value)` · `public abstract long Seek (long offset, SeekOrigin origin)` |
| 닫기·플러시 | `public virtual void Close()` · `public void Dispose()` · `public abstract void Flush()` |
| 타임아웃 | `public virtual bool CanTimeout { get; }` · `public virtual int ReadTimeout { get; set; }` · `public virtual int WriteTimeout { get; set; }` |
| 기타 | `public static readonly Stream Null` · `public static Stream Synchronized (Stream stream)` |

`Read`/`Write`에는 `Task`를 반환하고 취소 토큰을 선택적으로 받는 **비동기 버전**이 있고, `Span<T>`/`Memory<T>`를 받는 오버로드도 있다(68장).

기본 동작을 파일 스트림으로 확인해 보자.

```csharp
using System;
using System.IO;

// 현재 디렉터리에 test.txt를 만든다
using (Stream s = new FileStream("test.txt", FileMode.Create))
{
    Console.WriteLine(s.CanRead);    // True
    Console.WriteLine(s.CanWrite);   // True
    Console.WriteLine(s.CanSeek);    // True

    s.WriteByte(101);
    s.WriteByte(102);
    byte[] block = { 1, 2, 3, 4, 5 };
    s.Write(block, 0, block.Length);  // 5바이트 블록을 쓴다

    Console.WriteLine(s.Length);      // 7
    Console.WriteLine(s.Position);    // 7

    s.Position = 0;                   // 처음으로 되돌아간다

    Console.WriteLine(s.ReadByte());  // 101
    Console.WriteLine(s.ReadByte());  // 102

    // 스트림에서 다시 block 배열로 읽는다
    Console.WriteLine(s.Read(block, 0, block.Length));  // 5

    // 방금 Read가 5를 반환했다면 파일 끝에 도달했으므로
    // 다음 Read는 0을 반환한다
    Console.WriteLine(s.Read(block, 0, block.Length));  // 0
}
```

비동기로 바꾸는 것은 `ReadAsync`/`WriteAsync`를 호출하고 `await`하는 것이 전부다(호출 메서드에 `async`를 붙여야 한다).

```csharp
static async Task AsyncDemoAsync()
{
    using Stream s = new FileStream("test.txt", FileMode.Create);

    byte[] block = { 1, 2, 3, 4, 5 };
    await s.WriteAsync(block, 0, block.Length);   // 비동기로 쓴다

    s.Position = 0;

    Console.WriteLine(await s.ReadAsync(block, 0, block.Length));  // 5
}
```

비동기 메서드는 느릴 수 있는 스트림(특히 네트워크 스트림)을 다루면서도 스레드를 붙잡아 두지 않는, 반응성 좋고 확장 가능한 애플리케이션을 쉽게 만들어 준다. 다만 **파일 스트림에서 이것이 진짜 비동기인지는 전혀 다른 문제**이고, 40.15절 전체를 여기에 쓴다.

### `Read`는 요청한 만큼 읽어 주지 않는다

이 장에서 딱 하나만 기억해야 한다면 이것이다.

`Read`는 스트림에서 데이터 블록을 배열로 받아 온다. 반환값은 **실제로 받은 바이트 수**이며 항상 `count` 인자 **이하**다. `count`보다 작다면 스트림의 끝에 도달했거나, 스트림이 데이터를 더 작은 덩어리로 주고 있는 것이다(네트워크 스트림에서 흔하다). 어느 쪽이든 배열의 나머지 부분은 **건드려지지 않고 이전 값이 그대로 남는다**.

> **⚠️ `Read` 한 번으로 다 읽었다고 가정하지 마라**
>
> `Read`로 스트림의 끝을 확신할 수 있는 유일한 경우는 **반환값이 0일 때**다. 1,000바이트짜리 스트림이 있어도 다음 코드는 전부 읽는 데 실패할 수 있다.
>
> ```csharp
> // s가 스트림이라고 하자
> byte[] data = new byte[1000];
> s.Read(data, 0, data.Length);   // 1~1000 사이 아무 값이나 읽을 수 있다
> ```
>
> `Read`는 1바이트만 읽고 돌아올 수도 있으며, 나머지는 읽히지 않은 채 남는다. 로컬 파일에서는 거의 항상 다 채워져서 이 버그가 **개발 환경에서는 재현되지 않는다**. 그리고 네트워크나 압축 스트림을 끼우는 순간 운영에서 터진다. 이 책이 아는 한 .NET 초보자가 만드는 가장 흔한 조용한 버그다.

올바른 방법은 루프다.

```csharp
byte[] data = new byte[1000];

// 스트림 자체가 더 짧지 않은 한 bytesRead는 결국 1000이 된다
int bytesRead = 0;
int chunkSize = 1;
while (bytesRead < data.Length && chunkSize > 0)
    bytesRead += chunkSize =
        s.Read(data, bytesRead, data.Length - bytesRead);
```

.NET 7부터는 이 루프를 대신 써 주는 헬퍼가 `Stream`에 들어왔다. `ReadExactly`와 `ReadAtLeast`(그리고 각각의 비동기 버전)다. ※.NET 7

```csharp
byte[] data = new byte[1000];
s.ReadExactly(data);                            // 정확히 1000바이트를 읽는다
// 위 줄은 다음과 같다
s.ReadExactly(data, offset: 0, count: 1000);
```

`ReadExactly`는 요청한 바이트 수를 다 채우기 전에 스트림이 끝나면 **예외를 던진다**. "부족하면 부족한 대로"가 필요하면 `ReadAtLeast`를 쓴다.

| 방법 | 동작 | 스트림이 짧을 때 | 가용 버전 |
|---|---|---|---|
| `Read` 1회 | 1바이트 이상 임의 개수 | 그냥 적게 반환 | 전 버전 |
| `Read` 루프 | 요청 개수까지 반복 | 루프가 자연 종료 | 전 버전 |
| `ReadExactly` | 요청 개수를 채운다 | **예외** | .NET 7+ |
| `ReadAtLeast(buf, min)` | 최소 개수를 채운다 | `throwOnEndOfStream: false`면 적게 반환 | .NET 7+ |
| `new BinaryReader(s).ReadBytes(n)` | n바이트까지 읽는다 | 실제 크기만큼의 배열 반환 | 전 버전 |
| `CopyTo`/`CopyToAsync` | 끝까지 다른 스트림으로 | 정상 종료 | 전 버전 |

`BinaryReader`를 쓰는 방법도 실용적이다.

```csharp
byte[] data = new BinaryReader(s).ReadBytes(1000);
```

스트림이 1,000바이트보다 짧으면 반환된 배열은 **실제 스트림 크기**를 반영한다. 스트림이 탐색 가능하면 `1000` 자리에 `(int)s.Length`를 넣어 전체를 읽을 수 있다.

`ReadByte`는 훨씬 단순하다. 딱 1바이트를 읽고, 스트림 끝이면 −1을 반환한다. `byte`로는 −1을 표현할 수 없으므로 반환 타입이 `int`다.

`Write`와 `WriteByte`는 데이터를 스트림으로 보낸다. 지정한 바이트를 보낼 수 없으면 **예외를 던진다** — `Read`처럼 "일부만 쓰고 개수를 반환"하지 않는다.

> **⚠️ `offset`은 스트림의 위치가 아니다**
>
> `Read`와 `Write`의 `offset` 인자는 **버퍼 배열 안에서 읽기/쓰기를 시작할 인덱스**다. 스트림 안의 위치가 아니다. 스트림 위치를 바꾸려면 `Position`이나 `Seek`를 써야 한다. 이름이 짧아서 매년 누군가는 헷갈린다.

### 탐색 (seek)

`CanSeek`가 `true`면 탐색 가능한 스트림이다. 파일 스트림 같은 탐색 가능한 스트림에서는 `Length`를 조회하거나 `SetLength`로 바꿀 수 있고 언제든 읽기/쓰기 `Position`을 바꿀 수 있다. `Position`은 **스트림의 처음을 기준**으로 하는 절대 위치이고, `Seek` 메서드는 현재 위치나 끝을 기준으로 상대 이동을 허용한다.

```csharp
s.Seek(0, SeekOrigin.End);      // 끝으로 이동 (append 위치)
s.Seek(-10, SeekOrigin.Current); // 현재에서 10바이트 뒤로
s.Position = 0;                  // 처음으로
```

탐색 불가능한 스트림(암호화 스트림, 압축 스트림, 네트워크 스트림)에서 길이를 알아내는 유일한 방법은 **끝까지 다 읽는 것**이다. 게다가 앞부분을 다시 읽어야 한다면 스트림을 닫고 새로 열어야 한다.

> **📌 `Position` 변경도 공짜가 아니다**
>
> `FileStream`의 `Position`을 바꾸는 데는 보통 수 마이크로초가 든다. 이걸 루프 안에서 수백만 번 하면 그 자체가 병목이 된다. 그런 접근 패턴이라면 `FileStream`보다 `MemoryMappedFile`이 나은 선택이다(40.14절).

### 닫기와 플러시

스트림은 파일 핸들·소켓 핸들 같은 하부 리소스를 놓아 주기 위해 **반드시 해제**해야 한다. 가장 간단한 보장 방법은 `using` 블록/선언 안에서 인스턴스화하는 것이다(33.5절). 스트림은 표준 해제 의미론(33.2절)을 따른다.

- `Dispose`와 `Close`는 기능적으로 동일하다.
- 스트림을 반복해서 해제하거나 닫아도 오류가 나지 않는다.
- **데코레이터 스트림을 닫으면 데코레이터와 그 하부 백킹 스토어 스트림이 함께 닫힌다.** 데코레이터 체인에서는 가장 바깥(체인의 머리)을 닫으면 전체가 닫힌다.

일부 스트림은 백킹 스토어로 오가는 왕복을 줄여 성능을 높이려고 내부에서 데이터를 버퍼링한다(파일 스트림이 대표적이다). 이 말은 **스트림에 쓴 데이터가 버퍼가 찰 때까지 백킹 스토어에 도달하지 않을 수 있다**는 뜻이다. `Flush`는 내부 버퍼에 있는 데이터를 즉시 쓰도록 강제한다. 스트림이 닫힐 때 `Flush`가 자동 호출되므로 다음은 쓸 필요가 없다.

```csharp
s.Flush(); s.Close();   // Flush는 군더더기다
```

> **⚠️ 프로세스가 죽으면 버퍼는 사라진다**
>
> `Flush`를 부르지 않은 채 프로세스가 강제 종료되거나 정전이 나면, 버퍼에 있던 데이터는 **그냥 없어진다**. `Write`가 성공적으로 반환했다는 것은 "버퍼에 넣었다"는 뜻이지 "디스크에 기록됐다"는 뜻이 아니다. 로그 파일이나 트랜잭션 기록처럼 유실이 치명적인 경우는 `Flush`를 명시적으로 호출하거나 `FileOptions.WriteThrough`를 고려해야 한다(40.4절).
>
> 그리고 `Stream.Flush()`가 OS 파일 캐시까지 비워 주지는 않는다. `FileStream.Flush(true)` 오버로드가 OS 버퍼까지 내려보내도록 요청한다.

### 타임아웃

`CanTimeout`이 `true`면 스트림이 읽기·쓰기 타임아웃을 지원한다. **네트워크 스트림은 타임아웃을 지원하고, 파일 스트림과 메모리 스트림은 지원하지 않는다.** 지원하는 스트림에서는 `ReadTimeout`/`WriteTimeout` 속성이 밀리초 단위 타임아웃을 정하며, 0은 타임아웃 없음을 뜻한다. `Read`/`Write`는 타임아웃이 발생하면 예외를 던져서 알린다.

> **⚠️ 비동기 메서드는 타임아웃 속성을 무시한다**
>
> `ReadAsync`/`WriteAsync`는 `ReadTimeout`/`WriteTimeout`을 **지원하지 않는다**. 비동기 경로에서 시간 제한이 필요하면 **취소 토큰**을 넘겨야 한다.
>
> ```csharp
> using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(5));
> int n = await s.ReadAsync(buffer, cts.Token);
> ```
>
> 동기 코드에 익숙한 사람이 `ReadTimeout = 5000`만 설정해 놓고 `ReadAsync`를 쓰면 아무 일도 일어나지 않는다. 조용히 무한 대기한다.

### 스레드 안전성

원칙적으로 **스트림은 스레드 안전하지 않다**. 두 스레드가 같은 스트림을 동시에 읽거나 쓰면 오류가 날 수 있다. 이유는 구조적이다. 스트림에는 **`Position`이라는 공유 가변 상태**가 있고, 읽기/쓰기가 그 값을 옮긴다.

`Stream`은 정적 `Synchronized` 메서드로 간단한 우회로를 제공한다. 아무 타입의 스트림이든 받아서 스레드 안전한 래퍼를 반환한다. 이 래퍼는 각 읽기·쓰기·탐색 주위에 배타 잠금을 걸어, 한 번에 한 스레드만 그런 연산을 수행하도록 한다.

```csharp
Stream safe = Stream.Synchronized(fs);
```

> **⚠️ `Synchronized`는 "덧붙이기"까지만 안전하다**
>
> `Stream.Synchronized`가 보장하는 것은 **개별 연산의 원자성**이지 논리적 작업의 원자성이 아니다. 실무적으로 이것이 허용하는 것은 여러 스레드가 **같은 스트림에 동시에 덧붙이는(append)** 정도다. 동시 읽기처럼 각 스레드가 스트림의 특정 구간에 접근해야 하는 작업은 **추가 잠금이 필요하다**. "위치를 옮기고 → 읽는다"는 두 연산 사이에 다른 스레드가 끼어들면 엉뚱한 데이터를 읽는다.

> **💡 진짜 스레드 안전한 파일 I/O가 필요하면 `RandomAccess`**
>
> .NET 6부터 `System.IO.RandomAccess` 정적 클래스가 있다. `SafeFileHandle`과 **명시적 파일 오프셋**을 받아 읽고 쓰기 때문에 공유 `Position`이 아예 없다. 여러 스레드가 같은 파일의 서로 다른 구간을 동시에 다뤄야 하면 `Stream.Synchronized`보다 이쪽이 정답이다. 여러 버퍼를 한 번에 넘겨 성능을 올리는 오버로드도 있다. ※.NET 6
>
> ```csharp
> using SafeFileHandle handle = File.OpenHandle("big.bin");
> byte[] buf = new byte[4096];
> int n = RandomAccess.Read(handle, buf, fileOffset: 1_000_000);
> long len = RandomAccess.GetLength(handle);
> ```

### `Stream.Null`과 `CopyTo`

`Stream.Null`은 쓰면 버리고 읽으면 즉시 끝나는 "널 스트림"이다. 단위 테스트나, 출력이 필요 없는데 API가 스트림을 요구할 때 쓴다.

`CopyTo`/`CopyToAsync`는 한 스트림의 남은 내용을 다른 스트림으로 통째로 옮긴다. 내부적으로 위에서 본 `Read` 루프를 제대로 구현해 두었으므로, 직접 루프를 쓰는 것보다 안전하고 대개 빠르다.

```csharp
using var src = File.OpenRead("in.bin");
using var dst = File.Create("out.bin");
await src.CopyToAsync(dst);
```

## 40.3 백킹 스토어 스트림 — `FileStream`, `MemoryStream`, `PipeStream`, `BufferedStream`

이 절은 .NET이 제공하는 주요 백킹 스토어 스트림을 훑는다. `BufferedStream`은 엄밀히는 데코레이터지만, 백킹 스토어 스트림과 짝지어 쓰는 일이 압도적으로 많으므로 여기서 함께 다룬다.

### `FileStream` 만들기

가장 간단한 방법은 `File` 클래스의 정적 파사드(façade) 메서드다.

```csharp
FileStream fs1 = File.OpenRead("readme.bin");    // 읽기 전용
FileStream fs2 = File.OpenWrite("writeme.tmp");  // 쓰기 전용
FileStream fs3 = File.Create("readwrite.tmp");   // 읽기/쓰기
```

> **⚠️ `OpenWrite`와 `Create`는 기존 파일에서 다르게 동작한다**
>
> 파일이 이미 있을 때 `Create`는 기존 내용을 **잘라낸다(truncate)**. `OpenWrite`는 기존 내용을 **그대로 두고** 스트림 위치만 0으로 놓는다. 이전에 있던 것보다 적은 바이트를 쓰면 `OpenWrite`는 **새 내용과 옛 내용이 뒤섞인 파일**을 남긴다. "왜 파일 뒤에 이상한 쓰레기가 붙어 있지"의 90%가 이것이다.

`FileStream`을 직접 인스턴스화할 수도 있다. 생성자는 파일명 또는 저수준 파일 핸들, 파일 생성·접근 모드, 공유·버퍼링 옵션 등 모든 기능에 접근할 수 있게 해 준다.

```csharp
using var fs = new FileStream("readwrite.tmp", FileMode.Open);
```

### `File` 클래스의 단축 메서드

전체 파일을 한 번에 메모리로 읽어 들이는 정적 메서드가 있다.

| 메서드 | 반환 | 비동기 버전 |
|---|---|---|
| `File.ReadAllText` | `string` | `ReadAllTextAsync` |
| `File.ReadAllLines` | `string[]` | `ReadAllLinesAsync` |
| `File.ReadAllBytes` | `byte[]` | `ReadAllBytesAsync` |
| `File.ReadLines` | `IEnumerable<string>` (지연 평가) | `ReadLinesAsync` ※.NET 7 |

전체 파일을 한 번에 쓰는 메서드도 대칭적으로 있다. `File.WriteAllText`, `File.WriteAllLines`, `File.WriteAllBytes`, 그리고 로그 덧붙이기에 좋은 `File.AppendAllText`다(모두 `...Async` 짝이 있다).

`File.ReadLines`는 `ReadAllLines`와 달리 **지연 평가되는** `IEnumerable<string>`을 반환한다. 파일 전체를 한꺼번에 메모리에 올리지 않으므로 훨씬 효율적이다. LINQ와 궁합이 좋다.

```csharp
int longLines = File.ReadLines("filePath")
                    .Count(l => l.Length > 80);
```

> **💡 파일 크기가 예측 불가면 `ReadAllText`를 쓰지 마라**
>
> `ReadAllText`는 파일 크기만큼 문자열을 힙에 올린다. 100MB 텍스트 파일이면 UTF-16 문자열로 최대 200MB가 대형 객체 힙(62장)에 잡힌다. 사용자가 고르는 파일이나 외부 시스템이 만드는 파일에는 `ReadLines`나 `StreamReader` 루프를 쓴다. 5.10절의 역인덱스에서도 같은 조언을 했다.

### 파일명 지정하기

파일명은 절대 경로(`c:\temp\test.txt`, Unix에서는 `/tmp/test.txt`)이거나 현재 디렉터리에 대한 상대 경로(`test.txt`, `temp\test.txt`)일 수 있다. 현재 디렉터리는 정적 `Environment.CurrentDirectory` 속성으로 읽고 바꾼다.

> **⚠️ 현재 디렉터리는 실행 파일이 있는 폴더가 아니다**
>
> 프로그램이 시작될 때 현재 디렉터리는 프로그램 실행 파일의 디렉터리와 **일치할 수도 있고 아닐 수도 있다**. 그래서 실행 파일과 함께 배포한 런타임 파일을 찾을 때 현재 디렉터리에 의존하면 안 된다. 서비스로 등록하거나, 바로 가기로 실행하거나, 다른 프로세스가 띄우면 곧바로 깨진다.
>
> 애플리케이션 기준 디렉터리는 `AppDomain.CurrentDomain.BaseDirectory` (또는 `AppContext.BaseDirectory`)로 얻는다.
>
> ```csharp
> string baseFolder = AppContext.BaseDirectory;
> string logoPath = Path.Combine(baseFolder, "logo.jpg");
> Console.WriteLine(File.Exists(logoPath));
> ```

Windows 네트워크 상의 파일은 UNC 경로(`\\JoesPC\PicShare\pic.jpg`, `\\10.1.1.2\PicShare\pic.jpg`)로 읽고 쓸 수 있다. macOS나 Unix에서 Windows 파일 공유에 접근하려면 OS별 절차로 파일 시스템에 마운트한 뒤 평범한 경로로 연다.

### `MemoryStream`

`MemoryStream`은 **배열을 백킹 스토어로 쓴다**. 백킹 스토어 전체가 한꺼번에 메모리에 있어야 하므로 스트림을 쓰는 목적을 어느 정도 무색하게 만들지만, **탐색 불가능한 스트림에 임의 접근이 필요할 때** 유용하다. 원본 스트림 크기가 감당 가능하다면 이렇게 복사한다.

```csharp
var ms = new MemoryStream();
sourceStream.CopyTo(ms);
```

`MemoryStream`을 바이트 배열로 바꾸려면 `ToArray`를 호출한다. `GetBuffer`는 같은 일을 더 효율적으로 한다 — **내부 저장 배열에 대한 직접 참조를 반환**하기 때문이다. 문제는 이 배열이 대개 스트림의 실제 길이보다 **길다**는 것이다.

| | `ToArray()` | `GetBuffer()` |
|---|---|---|
| 반환 | 새 배열(복사본) | 내부 배열 직접 참조 |
| 길이 | 정확히 `Length` | `Capacity` (보통 더 크다) |
| 할당 | 있다 | 없다 |
| 닫힌 스트림에서 | 허용된다 | 노출 불가 스트림이면 예외 |
| 안전성 | 안전 | 수정하면 스트림이 오염된다 |

```csharp
var ms = new MemoryStream();
ms.Write(new byte[] { 1, 2, 3 }, 0, 3);

byte[] exact  = ms.ToArray();     // Length 3
byte[] buffer = ms.GetBuffer();   // Length는 256 같은 용량 값일 수 있다
// 실제 데이터는 buffer[0..(int)ms.Length]
```

> **⚠️ `GetBuffer`는 아무 `MemoryStream`에서나 되지 않는다**
>
> `MemoryStream`에는 **버퍼 노출 가능 여부**라는 개념이 있다. 기본 생성자(`new MemoryStream()`)나 용량만 받는 생성자로 만든 스트림은 노출 가능하다. 반면 **기존 `byte[]`를 감싸는 생성자**로 만들면 기본적으로 노출 불가가 되어 `GetBuffer`가 `UnauthorizedAccessException`을 던진다. 노출을 허용하려면 `publiclyVisible: true`를 받는 오버로드를 써야 한다.
>
> ```csharp
> var ms1 = new MemoryStream(existingArray);                    // GetBuffer → 예외
> var ms2 = new MemoryStream(existingArray, 0, existingArray.Length,
>                            writable: true, publiclyVisible: true); // OK
> ```
>
> .NET Core 이후로는 `TryGetBuffer(out ArraySegment<byte> segment)`가 더 나은 선택이다. 예외 없이 성공 여부를 알려 주고, **오프셋과 길이가 붙은 `ArraySegment`** 를 주므로 "용량이 더 길다" 문제도 함께 해결한다.

> **📌 `MemoryStream`은 닫지 않아도 된다**
>
> `MemoryStream`을 닫거나 플러시하는 것은 선택 사항이다. 닫으면 더 이상 읽거나 쓸 수 없지만, `ToArray`를 호출해 하부 데이터를 얻는 것은 여전히 허용된다. 메모리 스트림에서 `Flush`는 **아무 일도 하지 않는다**. 그래도 `using`을 쓰는 습관은 유지하는 편이 낫다 — 나중에 타입이 `FileStream`으로 바뀌었을 때 자동으로 옳아진다.

> **💡 `MemoryStream`을 반복 생성하면 LOH를 오염시킨다**
>
> 큰 `MemoryStream`을 초당 수백 개 만들면, 내부 배열이 자라면서 85,000바이트를 넘는 순간 대형 객체 힙에 떨어지고 단편화를 만든다(62장). 서버 코드에서 이 패턴이 나오면 `RecyclableMemoryStream` 같은 풀링 구현을 고려한다(69.4절).

### `PipeStream` — 프로세스 간 통신

`PipeStream`은 OS의 파이프 프로토콜로 프로세스 간에 통신하는 간단한 수단을 제공한다. 파이프는 두 종류다.

| | 익명 파이프 | 명명된 파이프 |
|---|---|---|
| 속도 | 더 빠르다 | 상대적으로 느리다 |
| 방향 | 단방향 | 양방향(기본) |
| 범위 | 같은 컴퓨터의 부모-자식 프로세스 | 같은 컴퓨터 또는 네트워크 너머 임의 프로세스 |
| 식별 | 비공개 핸들 | 시스템 전역 이름 |
| 서버 타입 | `AnonymousPipeServerStream` | `NamedPipeServerStream` |
| 클라이언트 타입 | `AnonymousPipeClientStream` | `NamedPipeClientStream` |

파이프는 **단일 컴퓨터에서의 프로세스 간 통신(IPC)** 에 좋다. 네트워크 전송에 의존하지 않으므로 네트워크 프로토콜 오버헤드가 없고, 방화벽 문제도 없다.

명명된 파이프가 더 쓰기 쉽다. 양쪽이 같은 이름의 파이프를 통해 통신하며, 프로토콜은 클라이언트와 서버라는 두 역할을 정의한다.

1. 서버가 `NamedPipeServerStream`을 인스턴스화하고 `WaitForConnection`을 호출한다.
2. 클라이언트가 `NamedPipeClientStream`을 인스턴스화하고 `Connect`를 호출한다(타임아웃 선택 가능).
3. 양쪽이 스트림을 읽고 쓰며 통신한다.

```csharp
// 서버
using var s = new NamedPipeServerStream("pipedream");
s.WaitForConnection();
s.WriteByte(100);                  // 값 100을 보낸다
Console.WriteLine(s.ReadByte());
```

```csharp
// 클라이언트
using var s = new NamedPipeClientStream("pipedream");
s.Connect();
Console.WriteLine(s.ReadByte());
s.WriteByte(200);                  // 값 200을 돌려보낸다
```

명명된 파이프 스트림은 기본적으로 양방향이므로 어느 쪽이든 읽고 쓸 수 있다. 그래서 양쪽이 동시에 보내거나 동시에 받는 상황을 피하려면 **클라이언트와 서버가 어떤 프로토콜에 합의해야 한다.** 전송 길이에 대한 합의도 필요하다. 1바이트씩만 주고받은 위 예제는 이 점에서 사소하다. 1바이트보다 긴 메시지를 돕기 위해 파이프는 **메시지 전송 모드**를 제공한다(Windows 전용). 활성화하면 `Read`를 호출한 쪽이 `IsMessageComplete` 속성을 확인해 메시지가 끝났는지 알 수 있다.

```csharp
static byte[] ReadMessage(PipeStream s)
{
    MemoryStream ms = new MemoryStream();
    byte[] buffer = new byte[0x1000];   // 4KB 블록으로 읽는다

    do { ms.Write(buffer, 0, s.Read(buffer, 0, buffer.Length)); }
    while (!s.IsMessageComplete);

    return ms.ToArray();
}
```

> **⚠️ 파이프에서 `Read`가 0을 반환하기를 기다리면 안 된다**
>
> `Read`가 0을 반환하는 것으로 메시지 수신 완료를 판단할 수 없다. 대부분의 다른 스트림 타입과 달리 **파이프 스트림과 네트워크 스트림에는 확정적인 끝이 없기 때문**이다. 이들은 메시지 전송 사이에 일시적으로 "마를" 뿐이다.

서버 쪽에서 메시지 모드를 켜려면 생성 시 `PipeTransmissionMode.Message`를 지정한다.

```csharp
// 서버
using var s = new NamedPipeServerStream("pipedream", PipeDirection.InOut,
                                        1, PipeTransmissionMode.Message);
s.WaitForConnection();
s.Write(Encoding.UTF8.GetBytes("Hello"));
Console.WriteLine(Encoding.UTF8.GetString(ReadMessage(s)));
```

클라이언트 쪽에서는 `Connect` 이후 `ReadMode`를 설정한다.

```csharp
using var s = new NamedPipeClientStream("pipedream");
s.Connect();
s.ReadMode = PipeTransmissionMode.Message;      // 여기가 핵심이다
Console.WriteLine(Encoding.UTF8.GetString(ReadMessage(s)));
s.Write(Encoding.UTF8.GetBytes("Hello right back!"));
```

> **⚠️ 메시지 모드는 Windows 전용이다**
>
> `PipeTransmissionMode.Message`는 Windows에서만 지원된다. 다른 플랫폼에서는 `PlatformNotSupportedException`을 던진다. 크로스 플랫폼 IPC를 만든다면 처음부터 **길이 접두사 프로토콜을 직접 구현**하는 편이 낫다.

익명 파이프는 부모와 자식 프로세스 사이의 단방향 통신 스트림을 제공한다. 시스템 전역 이름 대신 **비공개 핸들**로 접속한다.

1. 서버가 `AnonymousPipeServerStream`을 인스턴스화하면서 `PipeDirection`을 `In` 또는 `Out`으로 확정한다.
2. 서버가 `GetClientHandleAsString`으로 파이프 식별자를 얻어 클라이언트에 전달한다(보통 자식 프로세스 시작 인자로).
3. 자식 프로세스가 반대 방향의 `AnonymousPipeClientStream`을 인스턴스화한다.
4. 서버가 `DisposeLocalCopyOfClientHandle`를 호출해 2단계에서 만든 로컬 핸들을 놓아 준다.
5. 부모와 자식이 스트림을 읽고 쓰며 통신한다.

익명 파이프는 단방향이므로 양방향 통신에는 파이프 **두 개**를 만들어야 한다.

```csharp
static void AnonymousPipeServer()
{
    using var tx = new AnonymousPipeServerStream(
        PipeDirection.Out, HandleInheritability.Inheritable);
    using var rx = new AnonymousPipeServerStream(
        PipeDirection.In,  HandleInheritability.Inheritable);

    // 자식 프로세스를 만들고 시작한다. 같은 실행 파일에 핸들 ID만 인자로 준다
    string thisExe = Path.ChangeExtension(Assembly.GetEntryAssembly().Location, ".exe");
    var startInfo = new ProcessStartInfo(
        thisExe, $"{tx.GetClientHandleAsString()} {rx.GetClientHandleAsString()}");
    startInfo.UseShellExecute = false;      // 자식 프로세스에 필수
    Process p = Process.Start(startInfo);

    tx.DisposeLocalCopyOfClientHandle();    // 비관리 핸들 리소스를 놓아 준다
    rx.DisposeLocalCopyOfClientHandle();

    tx.WriteByte(100);
    Console.WriteLine("Server received: " + rx.ReadByte());
    p.WaitForExit();
}

static void AnonymousPipeClient(string rxID, string txID)
{
    using var rx = new AnonymousPipeClientStream(PipeDirection.In,  rxID);
    using var tx = new AnonymousPipeClientStream(PipeDirection.Out, txID);

    Console.WriteLine("Client received: " + rx.ReadByte());
    tx.WriteByte(200);
}
```

> **⚠️ 익명 파이프는 메시지 모드를 지원하지 않는다**
>
> 명명된 파이프와 마찬가지로 클라이언트와 서버는 송수신 순서와 각 전송의 길이에 합의해야 하는데, 익명 파이프에는 메시지 모드가 아예 없다. 직접 프로토콜을 만들어야 한다. 흔한 해법은 **각 전송의 첫 4바이트에 뒤따를 메시지 길이를 정수로 넣는 것**이다. `BitConverter` 클래스가 정수와 4바이트 배열 사이의 변환 메서드를 제공한다.

### `BufferedStream`

`BufferedStream`은 다른 스트림을 버퍼링 기능으로 감싸는 데코레이터다. 버퍼링은 백킹 스토어로의 왕복을 줄여 성능을 개선한다.

```csharp
// 100K를 파일에 쓴다
File.WriteAllBytes("myFile.bin", new byte[100000]);

using FileStream fs = File.OpenRead("myFile.bin");
using BufferedStream bs = new BufferedStream(fs, 20000);   // 20K 버퍼

bs.ReadByte();
Console.WriteLine(fs.Position);   // 20000
```

1바이트만 읽었는데 하부 스트림은 20,000바이트를 전진했다. 미리 읽기(read-ahead) 버퍼링 덕이다. `ReadByte`를 19,999번 더 호출해도 `FileStream`을 다시 건드리지 않는다.

> **⚠️ `FileStream`을 `BufferedStream`으로 감싸는 것은 대개 무의미하다**
>
> `FileStream`에는 이미 버퍼링이 내장돼 있다(40.4절). 위 예제처럼 둘을 결합하는 것은 가치가 제한적이다. 유일한 용도는 **이미 만들어진 `FileStream`의 버퍼를 키우는 것** 정도다. 실제로 `BufferedStream`이 필요한 곳은 버퍼링이 없는 스트림 — 예를 들어 `NetworkStream`이나, `Read`가 자주 작은 조각으로 되돌아오는 데코레이터 위 — 이다.
>
> `BufferedStream`을 닫으면 하부 백킹 스토어 스트림도 자동으로 닫힌다.

## 40.4 `FileStream` 옵션과 버퍼링 전략

`FileStream`의 생성자는 이 장에서 가장 많은 선택지를 요구하는 지점이다. 조합을 정확히 이해하지 못하면 "왜 다른 프로세스가 이 파일을 못 여는가", "왜 비동기가 비동기가 아닌가" 같은 문제로 하루를 날린다.

### `FileMode` — 파일을 어떻게 열 것인가

파일명을 받는 `FileStream` 생성자는 모두 `FileMode` 열거형 인자를 요구한다.

```csharp
public enum FileMode
{
    CreateNew, Create, Open, OpenOrCreate, Truncate, Append
}
```

| 멤버 | 파일이 없을 때 | 파일이 있을 때 | 대응하는 `File` 메서드 |
|---|---|---|---|
| `CreateNew` | 만든다 | **`IOException`** | — |
| `Create` | 만든다 | 덮어쓴다(잘라낸다) | `File.Create` |
| `Open` | **`FileNotFoundException`** | 연다 | `File.OpenRead` |
| `OpenOrCreate` | 만든다 | 연다(내용 유지, 위치 0) | `File.OpenWrite` |
| `Truncate` | **예외** | 열고 0바이트로 자른다 | — |
| `Append` | 만든다 | 열고 끝으로 이동 | `File.AppendText` |

> **⚠️ `FileMode.Append`는 쓰기 전용 스트림을 준다**
>
> `Append`는 유일하게 튀는 모드다. 이 모드로 얻은 스트림은 **읽을 수 없다**. 읽기·쓰기를 모두 하면서 끝에 덧붙이려면 `FileMode.Open`이나 `OpenOrCreate`로 열고 직접 끝으로 탐색해야 한다.
>
> ```csharp
> using var fs = new FileStream("myFile.bin", FileMode.Open);
> fs.Seek(0, SeekOrigin.End);
> ```
>
> `FileMode.Append`에 `FileAccess.Read`를 함께 넘기면 `ArgumentException`이 난다.

> **⚠️ 숨김 파일에 `Create`를 쓰면 실패한다 (Windows)**
>
> `File.Create`와 `FileMode.Create`는 **숨김(hidden) 속성이 붙은 파일**에 사용하면 예외를 던진다. 숨김 파일을 덮어쓰려면 지우고 다시 만들어야 한다.
>
> ```csharp
> File.Delete("hidden.txt");
> using var file = File.Create("hidden.txt");
> ```

파일명과 `FileMode`만 주면 (딱 한 가지 예외를 빼고) 읽고 쓸 수 있는 스트림이 나온다. `FileAccess` 인자를 함께 주면 권한을 낮출 수 있다.

```csharp
[Flags]
public enum FileAccess { Read = 1, Write = 2, ReadWrite = 3 }
```

```csharp
using var fs = new FileStream("x.bin", FileMode.Open, FileAccess.Read);
```

### `FileShare` — 다른 프로세스에게 무엇을 허용할 것인가

세 번째 인자 `FileShare`는 내가 파일을 다 쓰기 전에 **같은 파일을 건드리려는 다른 프로세스에게 얼마나 허용할지**를 정한다.

```csharp
public enum FileShare
{
    None, Read, Write, ReadWrite, Delete, Inheritable
}
```

| 값 | 다른 프로세스가 할 수 있는 것 |
|---|---|
| `None` | 아무것도 못 한다. 열기 시도가 실패한다 |
| `Read` | 읽기 위해 열 수 있다 (**`FileStream` 기본값**) |
| `Write` | 쓰기 위해 열 수 있다 |
| `ReadWrite` | 읽기·쓰기 모두 열 수 있다 |
| `Delete` | 삭제할 수 있다 |
| `Inheritable` | 핸들을 자식 프로세스가 상속할 수 있다 (플래그 조합용) |

### `FileMode` × `FileAccess` × `FileShare` 조합표

실무에서 반복적으로 등장하는 조합만 추리면 다음과 같다.

| 목적 | `FileMode` | `FileAccess` | `FileShare` |
|---|---|---|---|
| 설정 파일 읽기 (다른 앱이 계속 쓸 수 있게) | `Open` | `Read` | `ReadWrite` |
| 로그 파일에 덧붙이면서 tail 허용 | `Append` | `Write` | `Read` |
| 배타적 편집 (락 획득 목적) | `Open` | `ReadWrite` | `None` |
| 새 출력 파일 생성 (덮어쓰기) | `Create` | `Write` | `None` |
| 이미 있으면 실패시켜 경쟁 방지 | `CreateNew` | `Write` | `None` |
| 여러 리더가 동시에 읽는 정적 자산 | `Open` | `Read` | `Read` |
| 메모리 매핑 공유 (40.14절) | `Open` | `ReadWrite` | `ReadWrite` |

> **⚠️ 남의 로그 파일을 `FileShare` 기본값으로 열면 그 앱이 죽는다**
>
> `File.OpenRead(path)`의 기본 공유 모드는 `FileShare.Read`다. 즉 **다른 프로세스의 쓰기를 막는다**. 다른 애플리케이션이 계속 쓰고 있는 로그 파일을 이렇게 열면, 상대 프로세스의 다음 쓰기가 `IOException`으로 실패한다. 모니터링 도구를 만들 때 반드시 `FileShare.ReadWrite`로 열어야 한다.
>
> ```csharp
> using var fs = new FileStream(logPath, FileMode.Open,
>                               FileAccess.Read, FileShare.ReadWrite);
> using var sr = new StreamReader(fs);
> ```

`FileShare.ReadWrite`로 열면 여러 프로세스나 사용자가 같은 파일을 동시에 읽고 쓸 수 있다. 혼란을 막으려면 읽기·쓰기 전에 파일의 특정 구간을 잠그기로 모두가 합의하면 된다.

```csharp
// FileStream 클래스에 정의돼 있다
public virtual void Lock   (long position, long length);
public virtual void Unlock (long position, long length);
```

`Lock`은 요청한 파일 구간의 일부 또는 전체가 이미 잠겨 있으면 예외를 던진다.

> **📌 `FileStream.Lock`은 Windows에서만 실질적 의미가 있다**
>
> Unix 계열의 파일 잠금은 대체로 **권고적(advisory)** 이다. 참여하는 모든 프로세스가 같은 잠금 규약을 따를 때만 의미가 있다. 플랫폼 간 이식성이 필요한 조율에는 파일 잠금보다 명명된 뮤텍스나 별도의 잠금 파일(원자적 `CreateNew`) 같은 명시적 프로토콜이 안전하다.

### `FileOptions` — OS에 주는 힌트와 지시

`FileStream` 생성자의 고급 오버로드는 `FileOptions` 플래그 열거형을 받는다.

| 플래그 | 의미 |
|---|---|
| `None` | 아무 옵션도 없다 |
| `WriteThrough` | OS의 지연 쓰기(write-behind) 캐시를 끄도록 요청한다. 트랜잭션 파일·로그용 |
| `Asynchronous` | OS 수준 비동기 I/O를 사용하겠다고 선언한다 (40.15절) |
| `RandomAccess` | 임의 접근 패턴이라는 최적화 힌트 |
| `SequentialScan` | 처음부터 끝까지 순차적으로 읽는다는 최적화 힌트 |
| `DeleteOnClose` | 스트림을 닫을 때 파일을 자동 삭제한다. 임시 파일용 |
| `Encrypted` | OS 수준 파일 암호화를 요청한다 (Windows/NTFS) |

> **⚠️ 지원되지 않는 플래그는 조용히 무시된다**
>
> 하부 OS가 지원하지 않는 `FileOptions` 플래그는 **예외 없이 그냥 무시된다**. Linux에서 `FileOptions.Encrypted`를 넘겨도 아무 일도 일어나지 않고, 파일은 평문으로 저장된다. "옵션을 줬으니 됐겠지"라고 가정하면 안 된다. 보안이 걸린 요구사항은 코드로 검증해야 한다.

`SequentialScan`과 `RandomAccess`는 서로 반대되는 힌트다. OS의 미리 읽기 정책과 캐시 유지 정책을 바꾼다.

- **`SequentialScan`** — "앞에서 뒤로 한 번 훑는다". OS는 더 공격적으로 미리 읽고, 이미 지나간 페이지를 빨리 버린다. 대용량 파일 스캔·복사·해싱에 유리하다.
- **`RandomAccess`** — "여기저기 뛴다". 미리 읽기를 줄인다. 인덱스 파일이나 데이터베이스 파일처럼 위치가 튀는 접근에 유리하다.

> **💡 힌트는 측정 없이 믿지 마라**
>
> `SequentialScan`/`RandomAccess`의 효과는 파일 크기·저장 매체(HDD/SSD/NVMe)·OS 캐시 상태에 따라 크게 달라진다. SSD에서는 차이가 거의 사라지는 경우도 많다. 67장의 원칙 그대로다 — **측정 없이 최적화 없다.** 힌트를 넣고 뺀 두 버전을 실제 데이터로 벤치마크하는 데 5분이면 충분하다.

### 버퍼 크기

`FileStream`의 내부 버퍼 크기는 생성자에서 바이트 단위로 지정한다. **현재 기본값은 4KB(4096바이트)** 다.

4,096이라는 숫자에는 이유가 있다. 2의 거듭제곱이면서 **메모리 페이지 크기**이기 때문이다. 페이지는 페이지 테이블의 한 항목으로 기술되는 고정 길이 연속 가상 메모리 블록이다. 시스템이 페이지를 디스크로 스왑하기로 결정할 때 추가 오버헤드 없이 한 번에 처리할 수 있다.

버퍼 크기 선택의 대략적인 지침은 다음과 같다.

| 상황 | 권장 버퍼 크기 | 근거 |
|---|---|---|
| 일반적인 텍스트/설정 파일 | 기본값(4KB) | 페이지 크기와 정렬됨 |
| 대용량 순차 복사 | 64KB ~ 1MB | 시스템 콜 횟수를 줄인다 |
| 아주 작은 파일 다수 | 기본값 또는 더 작게 | 큰 버퍼는 낭비 |
| 이미 `BufferedStream`으로 감쌈 | `bufferSize: 1` (버퍼링 끔) | 이중 버퍼링 방지 |
| `MemoryMappedFile` 대상 | 해당 없음 | 40.14절 |

> **⚠️ 버퍼를 무작정 키우면 오히려 느려진다**
>
> 버퍼 크기를 늘리면 시스템 콜 횟수는 줄지만, 그만큼 큰 배열을 힙에 잡는다. 85,000바이트를 넘으면 대형 객체 힙으로 가고(62장), 이 스트림을 초당 수천 개 만드는 서버라면 GC 압력이 성능 이득을 지워 버린다. 그리고 파일이 버퍼보다 작으면 남는 공간은 그냥 낭비다.
>
> 대용량 복사에는 스트림 버퍼를 키우는 대신 `CopyToAsync(dest, bufferSize)`에 큰 값을 주거나, `ArrayPool<byte>`에서 빌린 버퍼로 직접 루프를 돌리는 편이 낫다(69.3절).

`bufferSize: 1`을 넘기면 `FileStream`은 **버퍼링을 비활성화**한다. 자체 버퍼 관리를 하는 상위 계층이 있을 때 이중 버퍼링을 피하는 관용구다.

### `FileStreamOptions` ※.NET 6

여러 인자를 순서대로 나열하는 생성자는 실수하기 쉽다. .NET 6부터는 옵션 객체를 받는 생성자가 있다.

```csharp
using var fs = new FileStream("data.bin", new FileStreamOptions
{
    Mode       = FileMode.Create,
    Access     = FileAccess.Write,
    Share      = FileShare.None,
    Options    = FileOptions.Asynchronous | FileOptions.SequentialScan,
    BufferSize = 64 * 1024,
    PreallocationSize = 1024 * 1024 * 100     // 100MB 미리 확보
});
```

`PreallocationSize`는 파일 크기를 미리 확보해 조각화를 줄이도록 파일 시스템에 요청한다. Unix 계열에서도 `UnixCreateMode`로 생성 시 권한 비트를 지정할 수 있다(40.13절).

> **📌 .NET 6의 `FileStream` 재작성**
>
> .NET 6에서 `FileStream`은 내부 구현이 크게 다시 쓰였다. 특히 비동기 경로에서 불필요한 할당과 스레드 전환이 줄었다. .NET Framework이나 초기 .NET Core에서 측정한 파일 I/O 수치를 모던 .NET에 그대로 적용하면 안 된다. 40.15절에서 다시 다룬다.

## 40.5 텍스트 어댑터 — `StreamReader` / `StreamWriter`와 인코딩

`Stream`은 오직 바이트만 다룬다. 문자열·정수·XML 요소 같은 데이터 타입을 읽고 쓰려면 어댑터를 꽂아야 한다. .NET이 제공하는 어댑터는 다음과 같다.

| 종류 | 추상 기반 | 구현 |
|---|---|---|
| 텍스트 어댑터 | `TextReader`, `TextWriter` | `StreamReader`/`StreamWriter`, `StringReader`/`StringWriter` |
| 바이너리 어댑터 | (없음, `object` 직접 상속) | `BinaryReader`, `BinaryWriter` |
| XML 어댑터 | `XmlReader`, `XmlWriter` | 42장 |

`TextReader`와 `TextWriter`는 **문자와 문자열만** 다루는 어댑터의 추상 기반 클래스다. 각각 .NET에 범용 구현이 둘씩 있다.

- **`StreamReader`/`StreamWriter`** — 원시 데이터 저장소로 `Stream`을 쓰며, 스트림의 바이트를 문자·문자열로 번역한다.
- **`StringReader`/`StringWriter`** — 메모리 내 문자열을 써서 `TextReader`/`TextWriter`를 구현한다.

### `TextReader`의 멤버

| 범주 | 멤버 |
|---|---|
| 한 문자 읽기 | `public virtual int Peek();` · `public virtual int Read();` |
| 여러 문자 읽기 | `public virtual int Read (char[] buffer, int index, int count);` · `public virtual int ReadBlock (char[] buffer, int index, int count);` · `public virtual string ReadLine();` · `public virtual string ReadToEnd();` |
| 닫기 | `public virtual void Close();` · `public void Dispose();` |
| 기타 | `public static readonly TextReader Null;` · `public static TextReader Synchronized (TextReader reader);` |

`Peek`는 위치를 전진시키지 않고 다음 문자를 반환한다. `Peek`와 인자 없는 `Read`는 스트림 끝이면 −1을 반환하고, 그렇지 않으면 `char`로 바로 캐스팅할 수 있는 정수를 반환한다. `char[]` 버퍼를 받는 `Read` 오버로드는 `ReadBlock` 메서드와 기능이 같다. `ReadLine`은 CR(문자 13) 또는 LF(문자 10), 또는 연속된 CR+LF 쌍을 만날 때까지 읽고, CR/LF 문자를 버린 문자열을 반환한다.

### `TextWriter`의 멤버

| 범주 | 멤버 |
|---|---|
| 한 문자 쓰기 | `public virtual void Write (char value);` |
| 여러 문자 쓰기 | `public virtual void Write (string value);` · `public virtual void Write (char[] buffer, int index, int count);` · `public virtual void Write (string format, params object[] arg);` · `public virtual void WriteLine (string value);` |
| 닫기·플러시 | `public virtual void Close();` · `public void Dispose();` · `public virtual void Flush();` |
| 포매팅·인코딩 | `public virtual IFormatProvider FormatProvider { get; }` · `public virtual string NewLine { get; set; }` · `public abstract Encoding Encoding { get; }` |
| 기타 | `public static readonly TextWriter Null;` · `public static TextWriter Synchronized (TextWriter writer);` |

`Write`와 `WriteLine`은 모든 기본 타입과 `object`를 받도록 추가로 오버로드돼 있으며, 넘겨받은 것에 대해 단순히 `ToString`을 호출한다(메서드 호출 시점이나 `TextWriter` 생성 시점에 지정한 `IFormatProvider`를 통할 수도 있다 — 38장).

> **📌 `Environment.NewLine`**
>
> `Environment.NewLine`은 현재 OS의 줄바꿈 시퀀스를 반환한다. Windows에서는 `"\r\n"`이고, 기계식 타자기를 본떠 CR(문자 13) 다음에 LF(문자 10)가 온다. 순서를 뒤집으면 줄이 두 번 바뀌거나 아예 안 바뀐다. Unix와 macOS에서는 그냥 `"\n"`이다.
>
> `WriteLine`은 주어진 텍스트 뒤에 `Environment.NewLine`을 붙인다. `NewLine` 속성으로 이를 바꿀 수 있다. Windows에서 Unix 형식 파일을 만들어야 할 때 유용하다.
>
> ```csharp
> using var w = new StreamWriter("unix.txt");
> w.NewLine = "\n";
> ```

### 기본 사용

```csharp
using (FileStream fs = File.Create("test.txt"))
using (TextWriter writer = new StreamWriter(fs))
{
    writer.WriteLine("Line1");
    writer.WriteLine("Line2");
}

using (FileStream fs = File.OpenRead("test.txt"))
using (TextReader reader = new StreamReader(fs))
{
    Console.WriteLine(reader.ReadLine());   // Line1
    Console.WriteLine(reader.ReadLine());   // Line2
}
```

텍스트 어댑터는 파일과 짝지어 쓰는 일이 워낙 많아서 `File` 클래스가 단축 메서드를 제공한다.

```csharp
using (TextWriter writer = File.CreateText("test.txt"))
{
    writer.WriteLine("Line1");
    writer.WriteLine("Line2");
}

using (TextWriter writer = File.AppendText("test.txt"))
    writer.WriteLine("Line3");

using (TextReader reader = File.OpenText("test.txt"))
    while (reader.Peek() > -1)
        Console.WriteLine(reader.ReadLine());
```

파일 끝을 판정하는 방법이 두 가지 나왔다. `reader.Peek()`가 −1인지 보거나, `reader.ReadLine()`이 `null`을 반환할 때까지 읽는 것이다. 후자가 더 흔한 관용구다.

```csharp
string line;
while ((line = reader.ReadLine()) != null)
    Console.WriteLine(line);
```

비동기 버전도 대칭적으로 있다. `ReadLineAsync`, `ReadToEndAsync`, `WriteLineAsync`, `ReadBlockAsync`다. .NET 7부터 `ReadLineAsync`는 취소 토큰을 받는 오버로드가 추가됐다. ※.NET 7

```csharp
using var reader = File.OpenText("big.log");
while (await reader.ReadLineAsync() is { } line)
    Process(line);
```

> **⚠️ 텍스트 어댑터로 숫자를 저장하면 다시 파싱해야 한다**
>
> `TextWriter`는 넘겨받은 값에 `ToString`을 호출하므로, 읽을 때는 반드시 문자열을 파싱해야 한다.
>
> ```csharp
> using (TextWriter w = File.CreateText("data.txt"))
> {
>     w.WriteLine(123);    // "123"이 기록된다
>     w.WriteLine(true);   // "true"라는 단어가 기록된다
> }
> using (TextReader r = File.OpenText("data.txt"))
> {
>     int myInt = int.Parse(r.ReadLine());     // 123
>     bool yes  = bool.Parse(r.ReadLine());    // true
> }
> ```
>
> 그리고 `ToString`/`Parse`는 **현재 문화권의 영향을 받는다**. 독일어 로캘에서 `1.5.ToString()`은 `"1,5"`다. 파일 형식은 반드시 `CultureInfo.InvariantCulture`로 쓰고 읽어야 한다(38장). 이것을 놓쳐서 생기는 사고가 매년 반복된다.

### 문자 인코딩

`TextReader`와 `TextWriter` 자체는 스트림이나 백킹 스토어와 아무 연결이 없는 추상 클래스다. 반면 `StreamReader`와 `StreamWriter`는 바이트 지향 스트림에 연결되므로 **문자와 바이트 사이를 변환**해야 한다. 이 변환은 `System.Text`의 `Encoding` 클래스를 통해 이루어지며, `StreamReader`/`StreamWriter`를 생성할 때 선택한다. 아무것도 고르지 않으면 **기본값 UTF-8**이 쓰인다.

인코딩 자체의 상세는 35.8절·35.9절에서 다뤘다. 여기서는 스트림 어댑터와 얽히는 부분만 본다.

가장 단순한 인코딩은 ASCII다. 각 문자가 1바이트로 표현되며, 유니코드 집합의 첫 127자를 1바이트에 매핑한다. 특수 기호와 비영어 문자를 포함한 대부분의 다른 문자는 표현할 수 없어 `□` 문자로 변환된다.

기본 UTF-8 인코딩은 할당된 모든 유니코드 문자를 매핑할 수 있지만 더 복잡하다. 첫 127자는 ASCII 호환성을 위해 1바이트로 인코딩되고, 나머지는 가변 개수(대개 2~3바이트)로 인코딩된다.

```csharp
using (TextWriter w = File.CreateText("but.txt"))   // 기본 UTF-8
    w.WriteLine("but—");

using (Stream s = File.OpenRead("but.txt"))
    for (int b; (b = s.ReadByte()) > -1;)
        Console.WriteLine(b);
```

"but" 뒤에 온 것은 평범한 하이픈이 아니라 더 긴 엠 대시(—) 문자 U+2014다. 출력은 다음과 같다.

```text
98      // b
117     // u
116     // t
226     // 엠 대시 바이트 1
128     // 엠 대시 바이트 2
148     // 엠 대시 바이트 3
13      // <CR>
10      // <LF>
```

멀티바이트 시퀀스의 각 조각은 값이 128 이상이다. 엠 대시는 유니코드 집합의 첫 127자 바깥에 있으므로 UTF-8에서 1바이트를 넘게(이 경우 3바이트) 쓴다.

UTF-8은 서구 알파벳에 효율적이다. 흔히 쓰는 문자 대부분이 1바이트만 소비하고, 128 이상의 바이트를 무시하면 ASCII로 쉽게 낮출 수도 있다. 단점은 문자의 위치가 스트림 안의 바이트 위치와 대응하지 않아 **스트림 안에서 탐색하기가 까다롭다**는 것이다. 대안은 UTF-16(`Encoding` 클래스에서는 그냥 "Unicode"로 표기)이다.

```csharp
using (Stream s = File.Create("but.txt"))
using (TextWriter w = new StreamWriter(s, Encoding.Unicode))
    w.WriteLine("but—");

foreach (byte b in File.ReadAllBytes("but.txt"))
    Console.WriteLine(b);
```

```text
255     // 바이트 순서 표시 1
254     // 바이트 순서 표시 2
98  0   // 'b'
117 0   // 'u'
116 0   // 't'
20  32  // 엠 대시
13  0   // <CR>
10  0   // <LF>
```

기술적으로 UTF-16은 문자당 2바이트 또는 4바이트를 쓴다(할당되거나 예약된 유니코드 문자가 거의 100만 개에 이르므로 2바이트로는 늘 충분하지 않다). 그러나 C#의 `char` 타입 자체가 16비트이므로, UTF-16 인코딩은 **.NET `char` 하나당 정확히 2바이트**를 쓴다. 덕분에 스트림 안에서 특정 문자 인덱스로 뛰기가 쉽다.

UTF-16은 바이트 쌍이 리틀 엔디언(최하위 바이트 먼저)인지 빅 엔디언인지 식별하기 위해 2바이트 접두사를 쓴다. 기본 리틀 엔디언 순서가 Windows 기반 시스템의 표준이다.

### BOM 함정

> **⚠️ 인코딩을 명시하면 `StreamWriter`가 BOM을 붙인다**
>
> 인코딩을 명시적으로 지정하면 `StreamWriter`는 기본적으로 **인코딩을 식별하는 접두사(BOM, byte-order mark)를 스트림 맨 앞에 쓴다**. 대개 원치 않는 동작이다. UTF-8 BOM(`EF BB BF`)이 붙은 CSV를 다른 시스템이 읽으면 첫 컬럼 이름 앞에 정체불명의 문자가 붙는다. JSON 파서 중에는 BOM에서 그냥 실패하는 것도 있다.
>
> 인코딩 객체를 이렇게 만들면 막을 수 있다.
>
> ```csharp
> var encoding = new UTF8Encoding(
>     encoderShouldEmitUTF8Identifier: false,
>     throwOnInvalidBytes: true);
> ```
>
> 두 번째 인자는 해당 인코딩에서 유효한 문자열 번역이 없는 바이트를 만나면 예외를 던지라고 `StreamWriter`(또는 `StreamReader`)에 지시한다. 이는 인코딩을 지정하지 않았을 때의 기본 동작과 일치한다.
>
> 그리고 `Encoding.UTF8` 정적 속성은 **BOM을 방출하는 인스턴스**다. 헷갈리기 쉬운 지점이다.

### 인코딩 자동 감지

`StreamReader` 생성자에는 `detectEncodingFromByteOrderMarks` 인자가 있다. `true`(여러 오버로드의 기본값)면 리더가 스트림 앞부분의 BOM을 살펴 인코딩을 스스로 판단한다.

| 스트림 앞 바이트 | 감지되는 인코딩 |
|---|---|
| `EF BB BF` | UTF-8 |
| `FF FE` (뒤에 00 00이 아님) | UTF-16 리틀 엔디언 |
| `FE FF` | UTF-16 빅 엔디언 |
| `FF FE 00 00` | UTF-32 리틀 엔디언 |
| `00 00 FE FF` | UTF-32 빅 엔디언 |
| 그 외 | 생성자에 지정한 인코딩 (없으면 UTF-8) |

> **⚠️ BOM이 없으면 감지는 실패하고 기본값으로 떨어진다**
>
> `detectEncodingFromByteOrderMarks`는 이름 그대로 **BOM만 본다**. 내용을 통계적으로 분석하지 않는다. BOM 없는 CP949(한국어 완성형)나 EUC-KR 파일은 UTF-8로 해석되어 깨진 글자가 나온다. 레거시 인코딩 파일을 다뤄야 한다면 인코딩을 **명시적으로 지정**해야 하고, .NET Core 이후에는 `System.Text.Encoding.CodePages` NuGet 패키지를 참조한 뒤 `Encoding.RegisterProvider(CodePagesEncodingProvider.Instance)`를 호출해야 코드 페이지 인코딩을 쓸 수 있다.

### 어댑터의 닫기와 해제

어댑터를 정리하는 방법은 네 가지다.

1. 어댑터만 닫는다
2. 어댑터를 닫고 스트림을 닫는다
3. (라이터의 경우) 어댑터를 플러시하고 스트림을 닫는다
4. (리더의 경우) 스트림만 닫는다

어댑터에서도 `Close`와 `Dispose`는 동의어다.

1번과 2번은 의미상 동일하다. 어댑터를 닫으면 하부 스트림이 자동으로 닫히기 때문이다. `using` 문을 중첩하면 암묵적으로 2번을 취한다.

```csharp
using (FileStream fs = File.Create("test.txt"))
using (TextWriter writer = new StreamWriter(fs))
    writer.WriteLine("Line");
```

중첩은 안쪽에서 바깥쪽으로 해제되므로 어댑터가 먼저 닫히고 그다음 스트림이 닫힌다. 게다가 어댑터의 생성자에서 예외가 던져지더라도 스트림은 여전히 닫힌다. **중첩 `using` 문으로는 틀리기 어렵다.**

> **⚠️ 라이터를 닫거나 플러시하기 전에 스트림을 닫지 마라**
>
> 어댑터 버퍼에 있던 데이터가 **잘려 나간다**. 다음은 파일이 비어 있거나 내용이 잘리는 전형적인 실수다.
>
> ```csharp
> var fs = File.Create("bad.txt");
> var writer = new StreamWriter(fs);
> writer.WriteLine("이 줄은 사라질 수 있다");
> fs.Dispose();      // 라이터 버퍼를 비우지 않고 스트림부터 닫았다
> ```

3번과 4번이 가능한 이유는 어댑터가 **선택적으로 해제 가능한 객체**라는 특이한 범주에 속하기 때문이다. 어댑터는 다 썼지만 하부 스트림은 나중에 계속 쓰고 싶을 때 유용하다.

```csharp
using (FileStream fs = new FileStream("test.txt", FileMode.Create))
{
    StreamWriter writer = new StreamWriter(fs);
    writer.WriteLine("Hello");
    writer.Flush();          // 필수

    fs.Position = 0;
    Console.WriteLine(fs.ReadByte());
}
```

`StreamWriter`를 해제했다면 하부 `FileStream`도 닫혀 이어지는 읽기가 실패했을 것이다. 단서는 `Flush`를 호출해 `StreamWriter`의 버퍼가 하부 스트림에 기록되도록 하는 것이다.

> **📌 어댑터는 파이널라이저로 자신을 구제하지 않는다**
>
> 스트림 어댑터는 — 선택적 해제 의미론 때문에 — 파이널라이저가 `Dispose`를 호출하는 확장 해제 패턴(33.3절)을 구현하지 않는다. 버려진 어댑터는 GC가 따라잡아도 자동 해제를 피해 간다. 즉 **`Dispose`도 `Flush`도 호출하지 않은 `StreamWriter`의 내용은 영원히 유실된다.** 파이널라이저가 구해 주리라 기대하면 안 된다.

### `leaveOpen`

`StreamReader`/`StreamWriter`에는 해제 후에도 스트림을 열어 두라고 지시하는 생성자가 있다. 이 인자를 쓰면 앞의 예제를 이렇게 다시 쓸 수 있다.

```csharp
using (var fs = new FileStream("test.txt", FileMode.Create))
{
    using (var writer = new StreamWriter(fs, new UTF8Encoding(false, true),
                                         0x400, leaveOpen: true))
        writer.WriteLine("Hello");

    fs.Position = 0;
    Console.WriteLine(fs.ReadByte());
    Console.WriteLine(fs.Length);
}
```

> **💡 `leaveOpen`은 라이브러리 API 설계의 필수 옵션이다**
>
> `Stream`을 인자로 받는 메서드를 만들 때, 그 안에서 `StreamWriter`로 감싸고 `using`으로 해제하면 **호출자의 스트림이 닫힌다**. 호출자는 이를 예상하지 못한다. 스트림을 받는 라이브러리 코드는 항상 `leaveOpen: true`를 쓰거나, 소유권 이전 여부를 매개변수로 노출해야 한다. `GZipStream`을 비롯한 압축 스트림도 같은 이유로 `leaveOpen` 생성자를 갖고 있다(40.7절).

### `AutoFlush`

`StreamWriter`에는 `AutoFlush` 속성이 있다. `true`로 설정하면 쓰기 연산을 할 때마다 모든 데이터를 플러시한다. 기본값은 `false`다.

| `AutoFlush` | 성능 | 데이터 안전성 | 용도 |
|---|---|---|---|
| `false` (기본) | 빠르다 | 닫기 전 크래시 시 유실 | 일반 파일 출력 |
| `true` | 쓰기마다 시스템 콜 | 각 쓰기가 즉시 반영 | 로그, 파이프, 대화형 프로토콜 |

> **⚠️ `AutoFlush = true`는 대량 쓰기에서 치명적으로 느리다**
>
> 100만 줄을 쓰면서 `AutoFlush`가 켜져 있으면 시스템 콜이 100만 번 일어난다. 반대로 파이프나 소켓으로 요청-응답을 주고받는데 `AutoFlush`가 꺼져 있으면, 상대는 버퍼가 찰 때까지 아무것도 못 받고 **양쪽이 서로를 기다리는 교착**에 빠진다. 어느 쪽이 맞는지는 용도에 달렸으니 기본값이라고 방치하지 마라.

### `StringReader`와 `StringWriter`

`StringReader`와 `StringWriter` 어댑터는 스트림을 전혀 감싸지 않고 `string` 또는 `StringBuilder`를 하부 데이터 소스로 쓴다. 바이트 변환이 필요 없다 — 사실 문자열이나 `StringBuilder`에 인덱스 변수를 붙이면 쉽게 할 수 있는 일 이상은 하지 않는다. 그럼에도 **`StreamReader`/`StreamWriter`와 기반 클래스를 공유한다**는 장점이 있다. 예를 들어 XML을 담은 문자열이 있고 `XmlReader`로 파싱하고 싶다고 하자. `XmlReader.Create`는 URI, `Stream`, `TextReader` 중 하나를 받는다. `StringReader`가 `TextReader`의 서브클래스이므로 다음이 가능하다.

```csharp
XmlReader r = XmlReader.Create(new StringReader(myString));
```

`StringWriter`는 `GetStringBuilder()`로 내부 `StringBuilder`를 꺼낼 수 있다.

```csharp
using var strWriter = new StringWriter();
strWriter.WriteLine("Don't forget Mother's Day this year...");
Console.WriteLine(strWriter);            // ToString()이 내용을 준다
strWriter.GetStringBuilder().Insert(0, "Hey!! ");
```

## 40.6 바이너리 어댑터 — `BinaryReader` / `BinaryWriter`

`BinaryReader`와 `BinaryWriter`는 네이티브 데이터 타입 — `bool`, `byte`, `char`, `decimal`, `float`, `double`, `short`, `int`, `long`, `sbyte`, `ushort`, `uint`, `ulong`, 그리고 문자열과 기본 타입 배열 — 을 읽고 쓴다. `StreamReader`/`StreamWriter`와 달리 바이너리 어댑터는 기본 데이터 타입을 **메모리에 표현된 그대로** 효율적으로 저장한다. `int`는 4바이트, `double`은 8바이트를 쓴다. 문자열은 (`StreamReader`/`StreamWriter`처럼) 텍스트 인코딩을 통해 쓰이지만, **길이 접두사가 붙는다** — 덕분에 특별한 구분자 없이도 일련의 문자열을 다시 읽어 낼 수 있다.

### 기본 사용

```csharp
public class Person
{
    public string Name;
    public int    Age;
    public double Height;

    public void SaveData(Stream s)
    {
        var w = new BinaryWriter(s);
        w.Write(Name);
        w.Write(Age);
        w.Write(Height);
        w.Flush();   // BinaryWriter 버퍼를 비운다. Dispose/Close는 하지 않는다 —
    }                // 스트림에 더 쓸 수 있도록

    public void LoadData(Stream s)
    {
        var r = new BinaryReader(s);
        Name   = r.ReadString();
        Age    = r.ReadInt32();
        Height = r.ReadDouble();
    }
}
```

`BinaryWriter`의 핵심 멤버는 다음과 같다.

| 멤버 | `BinaryWriter` | `BinaryReader` |
|---|---|---|
| `BaseStream` | 하부 스트림에 대한 읽기 전용 접근 | 같다 |
| `Close()` | 바이너리 스트림을 닫는다 | 바이너리 리더를 닫는다 |
| `Flush()` | 바이너리 스트림을 플러시한다 | — |
| `Seek()` | 현재 스트림의 위치를 설정한다 | — |
| `Write()` | 값을 현재 스트림에 쓴다 (다중 오버로드) | — |
| `PeekChar()` | — | 위치를 전진시키지 않고 다음 문자를 반환한다 |
| `Read()` | — | 주어진 바이트/문자 집합을 읽어 배열에 저장한다 |
| `ReadXXX()` | — | `ReadBoolean()`, `ReadByte()`, `ReadInt32()` 등 타입별 읽기 |

`BinaryReader`는 바이트 배열로도 읽을 수 있다. 다음은 탐색 가능한 스트림의 전체 내용을 읽는다.

```csharp
byte[] data = new BinaryReader(s).ReadBytes((int)s.Length);
```

스트림에서 직접 읽는 것보다 편리하다. 모든 데이터를 다 읽었는지 확인하는 루프가 필요 없기 때문이다.

`BinaryWriter`의 생성자는 `Stream` 파생 타입이면 무엇이든 받는다. `FileStream`이든 `MemoryStream`이든 `BufferedStream`이든 상관없다. 즉 바이너리 데이터를 파일 대신 메모리에 쓰는 것은 유효한 `MemoryStream` 객체를 넘기는 것만큼 간단하다.

### 7비트 인코딩 길이 접두사

`BinaryWriter.Write(string)`이 붙이는 길이 접두사는 고정 4바이트 정수가 **아니다**. **7비트 인코딩된 가변 길이 정수**다. 형식은 이렇다.

- 정수를 7비트씩 잘라 하위부터 1바이트씩 내보낸다
- 각 바이트의 최상위 비트(0x80)는 "**뒤에 바이트가 더 있다**"는 표시다
- 최상위 비트가 0인 바이트가 마지막이다

| 문자열 바이트 길이 | 접두사 바이트 수 | 접두사 바이트 |
|---|---|---|
| 0 ~ 127 | 1 | `0x00` ~ `0x7F` |
| 128 ~ 16,383 | 2 | 예: 300 → `AC 02` |
| 16,384 ~ 2,097,151 | 3 | |
| 2,097,152 ~ 268,435,455 | 4 | |
| 그 이상 | 5 | |

짧은 문자열이 압도적으로 많은 현실을 노린 설계다. 127바이트 이하 문자열은 접두사가 1바이트뿐이다. 이 인코딩은 `BinaryWriter.Write7BitEncodedInt` / `BinaryReader.Read7BitEncodedInt` 메서드로도 직접 쓸 수 있으며, IL 메타데이터를 비롯한 .NET 내부 형식 곳곳에서 같은 방식을 쓴다(56장).

> **⚠️ 길이 접두사는 문자 수가 아니라 바이트 수다**
>
> 접두사에 들어가는 값은 인코딩된 **바이트 수**이지 `char` 개수가 아니다. UTF-8에서 한글 한 글자는 3바이트이므로, 10글자 한국어 문자열의 접두사는 30이다. 다른 언어로 이 형식을 파싱하는 코드를 짤 때 가장 흔히 틀리는 지점이다.

> **⚠️ `BinaryWriter` 형식은 상호 운용 형식이 아니다**
>
> `BinaryWriter`가 만드는 바이트 열은 **.NET이 정의한 비공식 형식**이다. 다음 세 가지 이유로 시스템 간 교환 형식으로 쓰면 안 된다.
>
> 1. **엔디언을 고를 수 없다.** `BinaryWriter`/`BinaryReader`에는 바이트 순서를 선택하는 옵션이 전혀 없다. 네트워크 바이트 순서(빅 엔디언)가 필요한 프로토콜에는 쓸 수 없다.
> 2. **7비트 길이 접두사**는 다른 플랫폼의 표준이 아니다.
> 3. **스키마가 없다.** 필드 순서만으로 의미가 정해지므로, 쓰는 쪽과 읽는 쪽의 코드가 한 글자라도 어긋나면 조용히 쓰레기를 읽는다.
>
> 바이트 순서를 명시적으로 통제해야 하면 `System.Buffers.Binary.BinaryPrimitives`를 쓴다. `WriteInt32BigEndian`, `ReadUInt16LittleEndian` 같은 메서드가 `Span<byte>` 위에서 동작한다.
>
> ```csharp
> Span<byte> buf = stackalloc byte[4];
> BinaryPrimitives.WriteInt32BigEndian(buf, 0x01020304);
> ```

> **💡 그래서 `BinaryWriter`는 언제 쓰나**
>
> 같은 애플리케이션이 쓰고 같은 애플리케이션이 읽는 **로컬 캐시·인덱스·중간 산출물**에 적합하다. 크기가 작고 파싱이 빠르며 의존성이 없다. 반대로 버전이 바뀌거나 다른 언어가 읽어야 하는 데이터는 JSON(41장)이나 명시적 스키마가 있는 이진 형식을 쓴다. `BinaryFormatter`는 완전히 다른 물건이며 보안 위험 때문에 사용이 금지되었다 — 41.7절에서 다룬다.

## 40.7 압축 스트림 — `GZipStream`, `DeflateStream`, `BrotliStream`

`System.IO.Compression` 네임스페이스에는 범용 압축 스트림이 있다. 오래된 셋에 .NET 6의 `ZLibStream`이 더해졌다.

| 타입 | 알고리즘 | 특징 |
|---|---|---|
| `DeflateStream` | Deflate (RFC 1951) | 헤더 없는 순수 압축 스트림 |
| `GZipStream` | Deflate + gzip 컨테이너 (RFC 1952) | 시작·끝에 추가 프로토콜, **CRC로 오류 검출**, 다른 소프트웨어가 인식하는 표준 |
| `BrotliStream` | Brotli (RFC 7932) | 압축률이 더 좋다. 압축은 훨씬 느리고, 압축 해제는 매우 빠르다 |
| `ZLibStream` ※.NET 6 | Deflate + zlib 컨테이너 (RFC 1950) | zlib 헤더/Adler-32 체크섬 |

`DeflateStream`과 `GZipStream`은 ZIP 형식과 유사한 압축 알고리즘을 쓴다. 차이는 `GZipStream`이 시작과 끝에 추가 프로토콜(오류 검출용 CRC 포함)을 쓴다는 점이다. `BrotliStream`은 나머지 둘보다 **10배 넘게 느리지만** 더 나은 압축률을 달성한다 — 성능 손해는 **압축에만** 적용되고 압축 해제는 매우 잘 수행된다.

세 스트림 모두 읽기와 쓰기를 허용하되 다음 단서가 붙는다.

- **압축할 때는 항상 스트림에 쓴다.**
- **압축을 풀 때는 항상 스트림에서 읽는다.**

셋 다 데코레이터다. 생성 시 넘겨받은 다른 스트림의 데이터를 압축하거나 압축 해제한다.

```csharp
using (Stream s  = File.Create("compressed.bin"))
using (Stream ds = new DeflateStream(s, CompressionMode.Compress))
    for (byte i = 0; i < 100; i++)
        ds.WriteByte(i);

using (Stream s  = File.OpenRead("compressed.bin"))
using (Stream ds = new DeflateStream(s, CompressionMode.Decompress))
    for (byte i = 0; i < 100; i++)
        Console.WriteLine(ds.ReadByte());     // 0부터 99까지 출력
```

`DeflateStream`으로 압축한 이 파일은 **102바이트**다. 원본(100바이트)보다 오히려 약간 크다(`BrotliStream`이면 73바이트로 압축된다). 압축은 "조밀한" 비반복적 이진 데이터에서 잘 작동하지 않으며, 설계상 규칙성이 없는 암호화된 데이터에서 최악이다.

텍스트에서는 잘 작동한다. 다음 예제는 짧은 문장에서 무작위로 고른 1,000개 단어로 이루어진 텍스트 스트림을 Brotli 알고리즘으로 압축하고 해제한다. 40.1절 그림의 백킹 스토어 스트림 → 데코레이터 스트림 → 어댑터 체인과 비동기 메서드 사용을 함께 보여 준다.

```csharp
string[] words = "The quick brown fox jumps over the lazy dog".Split();
Random rand = new Random(0);       // 일관성을 위해 시드를 준다

using (Stream s  = File.Create("compressed.bin"))
using (Stream ds = new BrotliStream(s, CompressionMode.Compress))
using (TextWriter w = new StreamWriter(ds))
    for (int i = 0; i < 1000; i++)
        await w.WriteAsync(words[rand.Next(words.Length)] + " ");

Console.WriteLine(new FileInfo("compressed.bin").Length);   // 808

using (Stream s  = File.OpenRead("compressed.bin"))
using (Stream ds = new BrotliStream(s, CompressionMode.Decompress))
using (TextReader r = new StreamReader(ds))
    Console.Write(await r.ReadToEndAsync());
```

`BrotliStream`은 808바이트로 효율적으로 압축한다 — 단어당 1바이트도 안 된다. 비교하자면 `DeflateStream`은 같은 데이터를 885바이트로 압축한다.

### `CompressionMode`와 `CompressionLevel`

압축 스트림의 생성자는 두 갈래다.

```csharp
new GZipStream(stream, CompressionMode.Compress)        // 모드로 만든다
new GZipStream(stream, CompressionLevel.SmallestSize)   // 레벨로 만든다 (= 압축)
```

`CompressionMode`는 압축인지 해제인지를 정한다.

| `CompressionMode` | 의미 |
|---|---|
| `Compress` | 스트림에 쓰면 압축된다 |
| `Decompress` | 스트림에서 읽으면 압축이 풀린다 |

`CompressionLevel`은 압축 강도를 정한다. 레벨을 받는 생성자는 항상 압축 모드다.

| `CompressionLevel` | 의미 |
|---|---|
| `Optimal` | 크기와 속도의 균형 (기본값) |
| `Fastest` | 속도 우선, 결과물이 커진다 |
| `NoCompression` | 압축하지 않고 컨테이너만 씌운다 ※.NET Core 2.1 |
| `SmallestSize` | 크기 우선, 시간이 훨씬 오래 걸린다 ※.NET 6 |

> **⚠️ `Dispose`하지 않으면 마지막 블록이 파일에 남지 않는다**
>
> 압축 알고리즘은 데이터를 블록 단위로 모아 처리한다. 마지막 블록은 **스트림이 해제될 때** 비로소 마무리되고 기록된다. `Dispose`(또는 `using` 종료) 없이 프로세스를 끝내면 압축 파일의 **끝부분이 잘려** 압축 해제 시 `InvalidDataException`이 난다.
>
> 더 나쁜 것은 `Flush()`로는 부족하다는 점이다. 압축 스트림에서 `Flush`는 하부 스트림으로 내려보내기는 하지만 **압축 블록을 종료하지 않는다**. 완결된 압축 스트림을 만드는 유일한 방법은 해제다.
>
> ```csharp
> var gz = new GZipStream(output, CompressionMode.Compress);
> gz.Write(data);
> gz.Flush();          // 부족하다 — 파일이 손상된 채로 남는다
> // 반드시 gz.Dispose() 또는 using
> ```

### 메모리에서 압축하기

전부 메모리에서 압축해야 할 때가 있다. `MemoryStream`을 쓴다.

```csharp
byte[] data = new byte[1000];   // 빈 배열이니 압축률이 좋을 것이다

var ms = new MemoryStream();
using (Stream ds = new DeflateStream(ms, CompressionMode.Compress))
    ds.Write(data, 0, data.Length);

byte[] compressed = ms.ToArray();
Console.WriteLine(compressed.Length);   // 11

// 다시 data 배열로 압축 해제
ms = new MemoryStream(compressed);
using (Stream ds = new DeflateStream(ms, CompressionMode.Decompress))
    for (int i = 0; i < 1000; i += ds.Read(data, i, 1000 - i)) ;
```

`DeflateStream`을 감싼 `using` 문은 교과서적으로 스트림을 닫으면서 기록되지 않은 버퍼를 플러시한다. 이는 감싸고 있던 `MemoryStream`도 닫는다는 뜻이므로, 데이터를 꺼내려면 그다음에 `ToArray`를 호출해야 한다.

`MemoryStream`을 닫지 않는 대안은 세 번째 생성자 인자(`leaveOpen`)를 쓰는 것이다.

```csharp
byte[] data = new byte[1000];

MemoryStream ms = new MemoryStream();
using (Stream ds = new DeflateStream(ms, CompressionMode.Compress, leaveOpen: true))
    await ds.WriteAsync(data, 0, data.Length);

Console.WriteLine(ms.Length);      // 113
ms.Position = 0;

using (Stream ds = new DeflateStream(ms, CompressionMode.Decompress))
    for (int i = 0; i < 1000; i += await ds.ReadAsync(data, i, 1000 - i)) ;
```

추가 플래그는 `DeflateStream`에게 해제 시 하부 스트림을 데려가지 않도록 지시한다. 즉 `MemoryStream`이 열린 채로 남아 위치를 0으로 되돌려 다시 읽을 수 있다.

> **📌 왜 11바이트가 113바이트가 되었나**
>
> 두 예제 모두 1,000바이트 0 배열을 압축했는데 결과가 11바이트와 113바이트로 다르다. 원천 도서는 두 수치를 나란히 싣기만 하고 이유를 설명하지 않으며, **왜 다른지는 확인이 필요하다** — 쓰기 경로(동기/비동기)와 내부 플러시 단위가 다르면 Deflate 블록이 다르게 잘릴 수 있다는 것이 유력한 설명이다.
>
> 실용적으로 기억할 것은 하나다. **압축 결과 크기는 알고리즘 구현·런타임 버전·플러시 시점에 따라 달라질 수 있는 값이므로, 특정 바이트 수를 단정하는 테스트를 쓰면 안 된다.**

### gzip 파일 만들기

`GZipStream`의 압축 알고리즘은 Unix 시스템에서 파일 압축 형식으로 널리 쓰인다. 각 원본 파일이 `.gz` 확장자를 가진 별도의 대상 파일로 압축된다.

다음 메서드는 Unix 명령줄 유틸리티 `gzip`, `gunzip`이 하는 일을 한다.

```csharp
async Task GZipAsync(string sourcefile, bool deleteSource = true)
{
    var gzip = $"{sourcefile}.gz";
    if (File.Exists(gzip)) throw new Exception("Gzip file already exists");

    using (FileStream inStream  = File.Open(sourcefile, FileMode.Open))
    using (FileStream outStream = new FileStream(gzip, FileMode.CreateNew))
    using (GZipStream gzipStream =
               new GZipStream(outStream, CompressionMode.Compress))
        await inStream.CopyToAsync(gzipStream);

    if (deleteSource) File.Delete(sourcefile);
}

async Task GUnzipAsync(string gzipfile, bool deleteGzip = true)
{
    if (Path.GetExtension(gzipfile) != ".gz") throw new Exception("Not a gzip file");
    var uncompressedFile = gzipfile.Substring(0, gzipfile.Length - 3);
    if (File.Exists(uncompressedFile)) throw new Exception("Destination exists");

    using (FileStream outStream = File.Open(uncompressedFile, FileMode.Create))
    using (FileStream inStream  = File.Open(gzipfile, FileMode.Open))
    using (var unzip = new GZipStream(inStream, CompressionMode.Decompress))
        await unzip.CopyToAsync(outStream);

    if (deleteGzip) File.Delete(gzipfile);
}
```

> **💡 압축 순서: 압축 → 암호화, 절대 반대로 하지 마라**
>
> 데코레이터를 체인으로 엮을 때 순서가 중요하다. 암호화된 데이터는 규칙성이 없어 거의 압축되지 않는다. 반드시 **압축을 먼저 하고 그 결과를 암호화**한다.
>
> ```csharp
> using var file  = File.Create("out.bin");
> using var crypt = new CryptoStream(file, encryptor, CryptoStreamMode.Write);
> using var gzip  = new GZipStream(crypt, CompressionMode.Compress);
> using var w     = new StreamWriter(gzip);
> ```
>
> 안쪽(어댑터 쪽)에서 바깥(백킹 스토어 쪽)으로 데이터가 흐르므로, 위 체인은 텍스트 → 압축 → 암호화 → 파일 순이다. 다만 압축과 암호화를 결합할 때는 압축률이 비밀을 누출하는 부류의 공격(CRIME/BREACH 계열)이 알려져 있으니, 공격자가 평문 일부를 통제할 수 있는 상황에서는 주의해야 한다(44장).

## 40.8 ZIP 파일 다루기

`System.IO.Compression`의 `ZipArchive`와 `ZipFile` 클래스가 ZIP 압축 형식을 지원한다. `DeflateStream`·`GZipStream`에 대한 ZIP 형식의 장점은 **여러 파일을 담는 컨테이너 역할도 한다**는 것과, Windows 탐색기가 만든 ZIP 파일과 호환된다는 것이다.

`ZipArchive`는 스트림을 다루고 `ZipFile`은 파일을 다루는 더 흔한 시나리오를 담당한다(`ZipFile`은 `ZipArchive`를 위한 정적 헬퍼 클래스다).

### 디렉터리 통째로 압축·해제

```csharp
ZipFile.CreateFromDirectory(@"d:\MyFolder", @"d:\archive.zip");
ZipFile.ExtractToDirectory(@"d:\archive.zip", @"d:\MyFolder");
```

.NET 8부터는 ZIP 파일 경로 대신 `Stream`을 지정할 수도 있다. ※.NET 8

압축할 때는 파일 크기와 속도 중 무엇에 최적화할지, 그리고 아카이브에 원본 디렉터리 이름을 포함할지를 지정할 수 있다. 후자를 켜면 예제에서 아카이브 안에 `MyFolder`라는 하위 디렉터리가 만들어지고 압축된 파일들이 그 안에 들어간다.

```csharp
ZipFile.CreateFromDirectory(@"d:\MyFolder", @"d:\archive.zip",
                            CompressionLevel.SmallestSize,
                            includeBaseDirectory: true);
```

### 개별 엔트리 다루기

`ZipFile.Open`은 개별 엔트리를 읽고 쓰기 위한 메서드다. `ZipArchive` 객체를 반환한다(`Stream` 객체로 `ZipArchive`를 직접 인스턴스화해도 같은 것을 얻는다). `Open`을 호출할 때는 파일명과 함께 아카이브를 어떻게 다룰지를 지정해야 한다.

| `ZipArchiveMode` | 의미 | 요구되는 스트림 능력 |
|---|---|---|
| `Read` | 읽기 전용. 엔트리 열거와 추출 | 읽기 |
| `Create` | 새 아카이브 생성. 엔트리 추가만 가능 | 쓰기 (탐색 불필요) |
| `Update` | 기존 아카이브 수정. 추가·삭제·변경 | 읽기 + 쓰기 + **탐색** |

```csharp
using (ZipArchive zip = ZipFile.Open(@"d:\zz.zip", ZipArchiveMode.Read))
    foreach (ZipArchiveEntry entry in zip.Entries)
        Console.WriteLine(entry.FullName + " " + entry.Length);
```

`ZipArchiveEntry`에는 `Delete` 메서드, `ExtractToFile` 메서드(사실 `ZipFileExtensions` 클래스의 확장 메서드다), 그리고 읽고 쓸 수 있는 `Stream`을 반환하는 `Open` 메서드가 있다. 새 엔트리는 `ZipArchive`에서 `CreateEntry`(또는 확장 메서드 `CreateEntryFromFile`)를 호출해 만든다.

```csharp
byte[] data = File.ReadAllBytes(@"d:\foo.dll");
using (ZipArchive zip = ZipFile.Open(@"d:\zz.zip", ZipArchiveMode.Update))
    zip.CreateEntry(@"bin\X64\foo.dll").Open().Write(data, 0, data.Length);
```

`MemoryStream`으로 `ZipArchive`를 만들면 이 모든 일을 메모리에서만 할 수도 있다.

> **⚠️ `ZipArchiveMode.Update`는 아카이브 전체를 메모리에 올린다**
>
> `Update` 모드는 엔트리를 자유롭게 추가·삭제·수정할 수 있게 하려고 아카이브 내용을 메모리에 적재한다. 수 GB짜리 아카이브에 파일 하나를 추가하려고 `Update`를 쓰면 메모리를 그만큼 먹는다. 대안은 `Create` 모드로 **새 아카이브를 만들면서 기존 엔트리를 스트림으로 복사**하는 것이다.

> **📌 엔트리 스트림은 탐색할 수 없을 수 있다**
>
> `ZipArchiveEntry.Open()`이 반환하는 스트림의 `CanSeek`는 아카이브를 연 방식에 따라 달라진다. 특히 탐색 불가능한 스트림 위에 `ZipArchive`를 올렸다면 엔트리 스트림도 탐색할 수 없다. 40.2절의 원칙이 그대로 적용된다 — **`Read`를 루프로 감싸고, 길이를 미리 안다고 가정하지 마라.**

### Zip Slip — 경로 탈출 취약점

여기서부터가 이 절에서 가장 중요한 부분이다.

ZIP 엔트리의 이름은 **아카이브를 만든 사람이 완전히 통제하는 문자열**이다. 어떤 언어에서든 엔트리 이름에는 `../../../../etc/cron.d/evil`이나 `C:\Windows\System32\payload.dll` 같은 값이 들어갈 수 있다. 이를 검증 없이 대상 디렉터리와 결합해 파일을 쓰면 **아카이브가 시스템의 임의 위치에 파일을 쓸 수 있다.** 이 취약점을 Zip Slip이라고 부르며, 전형적인 취약 코드는 이렇게 생겼다.

```csharp
// 절대 이렇게 쓰지 마라
using ZipArchive zip = ZipFile.OpenRead(uploadedPath);
foreach (ZipArchiveEntry entry in zip.Entries)
{
    string dest = Path.Combine(targetDir, entry.FullName);  // 위험
    entry.ExtractToFile(dest, overwrite: true);
}
```

`Path.Combine`은 `..`을 해석하지 않는다. 그리고 `entry.FullName`이 절대 경로면 **`targetDir`을 통째로 버린다**(40.10절). 두 함정이 겹쳐 있다.

> **⚠️ 안전한 추출의 규칙**
>
> 엔트리 하나를 추출하기 전에 **결합한 경로를 정규화하고, 그것이 대상 디렉터리 안에 있는지 확인**해야 한다.
>
> ```csharp
> static void SafeExtract(string archivePath, string targetDir)
> {
>     // 대상 디렉터리를 정규화하고 구분자로 끝나게 만든다
>     string root = Path.GetFullPath(targetDir);
>     if (!root.EndsWith(Path.DirectorySeparatorChar))
>         root += Path.DirectorySeparatorChar;
>
>     using ZipArchive zip = ZipFile.OpenRead(archivePath);
>     foreach (ZipArchiveEntry entry in zip.Entries)
>     {
>         // 디렉터리 엔트리는 이름이 구분자로 끝나고 Length가 0이다
>         if (string.IsNullOrEmpty(entry.Name)) continue;
>
>         string dest = Path.GetFullPath(Path.Combine(root, entry.FullName));
>
>         if (!dest.StartsWith(root, StringComparison.Ordinal))
>             throw new IOException($"Zip Slip 시도 감지: {entry.FullName}");
>
>         Directory.CreateDirectory(Path.GetDirectoryName(dest)!);
>         entry.ExtractToFile(dest, overwrite: false);
>     }
> }
> ```
>
> 핵심은 세 가지다. **`Path.GetFullPath`로 `..`을 해소한 뒤**, **접두사 비교로 탈출 여부를 검사하고**, **`overwrite: false`로 기존 파일 덮어쓰기를 막는 것**이다.
>
> `ZipFile.ExtractToDirectory` 자체는 모던 .NET에서 경로 탈출을 검사한다. 하지만 **엔트리를 직접 순회하며 `ExtractToFile`을 부르는 코드는 스스로 검사해야 한다.**

> **⚠️ Zip Bomb도 함께 막아라**
>
> 경로 탈출만이 위협이 아니다. 수 KB짜리 아카이브가 압축을 풀면 수십 GB가 되도록 만들 수 있다(zip bomb). 신뢰할 수 없는 아카이브를 다룬다면 다음도 함께 검사한다.
>
> - `entry.Length`(압축 해제 후 크기)의 **총합** 상한
> - `entry.Length / entry.CompressedLength` **압축률** 상한
> - **엔트리 개수** 상한
> - 심볼릭 링크나 예약 이름(40.12절) 필터링
>
> `entry.Length`는 아카이브 헤더에 기록된 값이므로 그것 자체를 신뢰할 수 없다. 실제 추출 시 쓴 바이트 수도 함께 세는 것이 확실하다.

## 40.9 Tar 파일 다루기 ※.NET 7

`System.Formats.Tar` 네임스페이스의 타입들이 `.tar` 아카이브 형식을 지원한다. Unix에서 여러 파일을 묶는 데 널리 쓰이는 형식이며 .NET 7부터 BCL에 들어왔다.

```csharp
TarFile.CreateFromDirectory("/tmp/testfolder", "/tmp/test.tar", false);
```

세 번째 인자는 아카이브 엔트리에 기준 디렉터리 이름을 포함할지를 나타낸다. 추출은 대칭적이며, 세 번째 인자는 기존 파일을 덮어쓸지를 나타낸다.

```csharp
TarFile.ExtractToDirectory("/tmp/test.tar", "/tmp/testfolder", true);
```

두 메서드 모두 `.tar` 파일 경로 대신 `Stream`을 지정할 수 있다. 다음 예제는 tarball을 메모리 스트림에 쓴 다음, `GZipStream`으로 그 스트림을 압축해 `.tar.gz` 파일을 만든다.

```csharp
var ms = new MemoryStream();
TarFile.CreateFromDirectory("/tmp/testfolder", ms, false);
ms.Position = 0;                 // 스트림을 읽기용으로 재사용하기 위해

using (var fs = File.Create("/tmp/test.tar.gz"))
using (var gz = new GZipStream(fs, CompressionMode.Compress))
    ms.CopyTo(gz);
```

`.tar`를 `.tar.gz`로 압축하는 것이 유용한 이유는 **`.tar` 형식 자체는 압축을 포함하지 않기 때문**이다(`.zip` 형식과 다른 점이다). `.tar.gz` 파일은 이렇게 푼다.

```csharp
using (var fs = File.OpenRead("/tmp/test.tar.gz"))
using (var gz = new GZipStream(fs, CompressionMode.Decompress))
    TarFile.ExtractToDirectory(gz, "/tmp/testfolder", true);
```

### ZIP과 TAR의 구조적 차이

| | ZIP | TAR |
|---|---|---|
| 압축 | 형식에 내장. 엔트리별 압축 | 없음. 외부 압축(gzip 등)과 조합 |
| 중앙 디렉터리 | 파일 끝에 있다 | 없다 |
| 임의 엔트리 접근 | 가능 (탐색해서 바로) | 불가능 (앞에서부터 순차 스캔) |
| 스트리밍 생성 | 제약이 있다 | 자연스럽다 |
| Unix 권한·소유자 | 표준 지원 아님 | 표준 지원 |

TAR에 중앙 디렉터리가 없다는 사실이 실무적 차이를 만든다. `.tar.gz`에서 파일 하나만 꺼내려 해도 그 앞의 모든 데이터를 압축 해제하며 지나가야 하는 반면, TAR은 끝을 모른 채로도 스트림에 계속 흘려보낼 수 있어 파이프라인에 자연스럽다.

### `TarReader`와 `TarWriter`

더 세밀한 수준에서 API에 접근하려면 `TarReader`와 `TarWriter` 클래스를 쓴다.

```csharp
using (FileStream archiveStream = File.OpenRead("/tmp/test.tar"))
using (TarReader reader = new(archiveStream))
    while (true)
    {
        TarEntry entry = reader.GetNextEntry();
        if (entry == null) break;      // 더 이상 엔트리가 없다

        Console.WriteLine(
            $"Entry {entry.Name} is {entry.DataStream.Length} bytes long");

        entry.ExtractToFile(
            Path.Combine("/tmp/testfolder", entry.Name), true);
    }
```

> **⚠️ TAR에도 Zip Slip이 있다**
>
> 40.8절의 경로 탈출 검사는 TAR에도 **그대로** 필요하다. 오히려 TAR 쪽이 더 위험하다. TAR 엔트리는 심볼릭 링크와 하드 링크(`TarEntryType.SymbolicLink`, `TarEntryType.HardLink`)를 표현할 수 있어서, 링크를 먼저 만들고 그 링크를 통해 바깥에 쓰는 2단계 공격이 가능하다. 신뢰할 수 없는 tarball을 풀 때는 링크 엔트리를 **거부**하는 것이 가장 안전하다.
>
> ```csharp
> if (entry.EntryType is TarEntryType.SymbolicLink or TarEntryType.HardLink)
>     throw new IOException($"링크 엔트리 거부: {entry.Name}");
> ```

> **📌 `entry.DataStream`은 다음 엔트리로 넘어가면 무효가 된다**
>
> `TarReader`는 순차 리더다. `GetNextEntry()`를 다시 호출하면 이전 엔트리의 `DataStream`은 더 이상 유효하지 않다. 엔트리 데이터를 나중에 쓰려면 **그 자리에서** 복사해 두어야 한다.

## 40.10 파일·디렉터리 조작 — `File`, `Directory`, `FileInfo`, `DirectoryInfo`, `Path`

`System.IO`는 복사·이동, 디렉터리 생성, 파일 속성·권한 설정 같은 "유틸리티" 성격의 작업을 위한 타입 집합을 제공한다. 대부분의 기능에 대해 **정적 메서드 클래스**와 **인스턴스 메서드 클래스** 중 하나를 고를 수 있다.

| | 정적 클래스 | 인스턴스 클래스 | 기반 클래스 |
|---|---|---|---|
| 파일 | `File` | `FileInfo` | `FileSystemInfo` |
| 디렉터리 | `Directory` | `DirectoryInfo` | `FileSystemInfo` |

`File`과 `Directory`는 `System.Object`를 직접 상속하고, `FileInfo`와 `DirectoryInfo`는 추상 `FileSystemInfo` 타입에서 파생된다. 추가로 정적 클래스 `Path`가 있다. `Path`는 파일이나 디렉터리에 아무 일도 하지 않는다 — 파일명과 디렉터리 경로에 대한 **문자열 조작 메서드**를 제공할 뿐이다.

### 정적 vs 인스턴스 — 무엇을 언제 쓰나

`File`과 `Directory`의 정적 메서드는 **단일 파일·디렉터리 작업 한 번**을 실행할 때 편리하다. 연달아 여러 메서드를 호출해야 하면 `FileInfo`와 `DirectoryInfo`가 제공하는 객체 모델이 일을 쉽게 만든다.

이유는 성능에 있다. 파일 시스템 메타데이터 조회는 시스템 콜이라, `File.Exists(p)`, `File.GetLastWriteTime(p)`, `new FileInfo(p).Length`를 차례로 부르면 **경로 파싱과 시스템 콜이 매번 반복된다**. `FileInfo`는 첫 조회 시 메타데이터를 가져와 **캐싱**한다.

| 판단 기준 | 선택 |
|---|---|
| 한 경로에 대해 한 가지만 확인/수행 | `File` / `Directory` (정적) |
| 한 경로의 여러 속성을 연달아 읽음 | `FileInfo` / `DirectoryInfo` |
| 많은 파일을 열거하며 속성을 읽음 | `DirectoryInfo.EnumerateFiles` (열거 중 메타데이터가 함께 채워진다) |
| 문자열 경로만 있으면 충분 | `Directory.EnumerateFiles` |
| 강타입 객체를 계속 넘겨야 함 | `FileInfo` / `DirectoryInfo` |

> **⚠️ `FileInfo`는 캐시한다 — `Refresh()`를 잊지 마라**
>
> `FileInfo`/`DirectoryInfo`가 메타데이터를 캐싱한다는 것은 **파일이 그동안 바뀌어도 옛 값을 계속 준다**는 뜻이다.
>
> ```csharp
> FileInfo fi = new FileInfo(Path.Combine(dir, "FileInfo.txt"));
> Console.WriteLine(fi.Exists);         // false
>
> using (TextWriter w = fi.CreateText())
>     w.Write("Some text");
>
> Console.WriteLine(fi.Exists);         // 여전히 false (캐시된 값)
> fi.Refresh();
> Console.WriteLine(fi.Exists);         // true
> ```
>
> 이 캐싱은 성능상 이점이자 함정이다. 장수하는 `FileInfo` 인스턴스를 필드에 들고 있으면서 최신 상태를 기대하면 안 된다.

### `FileSystemInfo`의 공통 속성

| 속성 | 의미 |
|---|---|
| `Attributes` | `FileAttributes` 열거형으로 표현되는 속성 (읽기 전용·암호화·숨김·압축 여부 등) |
| `CreationTime` | 생성 시각 (UTC 버전도 있다) |
| `Exists` | 존재 여부 |
| `Extension` | 파일 확장자 |
| `FullName` | 전체 경로 |
| `LastAccessTime` | 마지막 접근 시각 |
| `LastWriteTime` | 마지막 기록 시각 |
| `Name` | 이름 |

`FileSystemInfo`는 `Delete()` 메서드도 정의한다. 파생 타입이 구현하며, 주어진 파일이나 디렉터리를 디스크에서 지운다. `Refresh()`는 앞서 본 대로 캐시를 무효화한다.

### `File` 클래스

`File`의 메서드는 전부 public static이며 파일명을 받는다.

```csharp
bool Exists (string path);
void Delete (string path);
void Copy   (string sourceFileName, string destFileName);
void Move   (string sourceFileName, string destFileName);
void Replace(string sourceFileName, string destinationFileName,
             string destinationBackupFileName);

FileAttributes GetAttributes (string path);
void SetAttributes (string path, FileAttributes fileAttributes);

// 시각 조회·설정 (UTC 버전도 제공된다)
DateTime GetCreationTime (string path);   // GetLastAccessTime, GetLastWriteTime도 있다
void SetCreationTime (string path, DateTime creationTime);   // Set... 3종
```

`Move`는 대상 파일이 이미 있으면 예외를 던지고 `Replace`는 그렇지 않다. 두 메서드 모두 이동과 동시에 이름을 바꿀 수 있다.

> **⚠️ `File.Delete`가 던지는 예외는 상황에 따라 다르다**
>
> `Delete`는 파일이 읽기 전용으로 표시돼 있으면 `UnauthorizedAccessException`을 던진다. `GetAttributes`를 미리 호출해 이를 알 수 있다. OS가 프로세스에 삭제 권한을 거부해도 같은 예외가 난다. 반면 **파일이 아예 없으면 예외를 던지지 않고 조용히 성공**한다. 디렉터리가 없으면 `DirectoryNotFoundException`이다. 세 경우의 동작이 다르므로 "삭제했으니 없어졌다"고 단정하지 말고 필요하면 검증해야 한다.

`GetAttributes`가 반환하는 `FileAttributes` 열거형의 멤버는 다음과 같다.

```text
Archive, Compressed, Device, Directory, Encrypted,
Hidden, IntegritySystem, Normal, NoScrubData, NotContentIndexed,
Offline, ReadOnly, ReparsePoint, SparseFile, System, Temporary
```

이 열거형의 멤버는 조합 가능하다. 나머지를 건드리지 않고 단일 속성만 토글하는 방법은 이렇다.

```csharp
string filePath = "test.txt";

FileAttributes fa = File.GetAttributes(filePath);
if ((fa & FileAttributes.ReadOnly) != 0)
{
    // 배타적 논리합(^)으로 ReadOnly 플래그를 뒤집는다
    fa ^= FileAttributes.ReadOnly;
    File.SetAttributes(filePath, fa);
}

File.Delete(filePath);
```

`FileInfo`는 읽기 전용 플래그를 바꾸는 더 쉬운 방법을 제공한다.

```csharp
new FileInfo("test.txt").IsReadOnly = false;
```

> **⚠️ `SetAttributes`로 압축·암호화 속성은 바꿀 수 없다 (Windows)**
>
> `Compressed`와 `Encrypted` 파일 속성은 Windows 탐색기의 속성 대화 상자에 있는 압축·암호화 체크박스에 대응한다. 그런데 `SetAttributes`로 이 둘을 바꾸려 하면 **예외도 없이 조용히 실패한다.** 암호화는 `File.Encrypt()`/`File.Decrypt()`를 쓰면 되고, 압축은 WMI(`System.Management` NuGet 패키지) 같은 우회로가 필요하다.
>
> 투명 암호화·압축은 특별한 파일 시스템 지원이 필요하다. NTFS는 지원하지만 CDFS(CD-ROM)나 FAT(이동식 미디어 카드)는 지원하지 않는다. 또한 투명 암호화의 키는 로그인 사용자의 암호에서 파생되므로, **관리자가 암호를 재설정하면 암호화된 파일의 데이터를 복구할 수 없다.** 이 기능들은 전부 Windows 전용이다.

### `Directory` 클래스

정적 `Directory` 클래스는 `File`과 유사한 메서드 집합을 제공한다 — 존재 확인(`Exists`), 이동(`Move`), 삭제(`Delete`), 생성·접근 시각 조회·설정, 보안 권한 조회·설정이다. 추가로 다음 정적 메서드를 노출한다.

```csharp
string GetCurrentDirectory ();
void   SetCurrentDirectory (string path);

DirectoryInfo CreateDirectory (string path);
DirectoryInfo GetParent       (string path);
string        GetDirectoryRoot(string path);

string[] GetLogicalDrives();     // Unix에서는 마운트 지점을 가져온다

// 다음 메서드는 모두 전체 경로를 반환한다
string[] GetFiles (string path);   // GetDirectories, GetFileSystemEntries도 있다
IEnumerable<string> EnumerateFiles (string path);   // Enumerate... 3종
```

`Enumerate*`와 `Get*`는 `searchPattern`(문자열)과 `searchOption`(열거형) 매개변수를 받도록 오버로드돼 있다. `SearchOption.AllDirectories`를 지정하면 재귀적 하위 디렉터리 검색이 수행되고, `*FileSystemEntries` 메서드는 `*Files`와 `*Directories`의 결과를 합친다.

### `EnumerateFiles` vs `GetFiles`

`Enumerate*` 계열이 `Get*` 계열보다 잠재적으로 효율적이다. **지연 평가**되어 시퀀스를 열거하는 동안 파일 시스템에서 데이터를 가져오기 때문이며, LINQ 쿼리에 특히 잘 맞는다.

| | `GetFiles` | `EnumerateFiles` |
|---|---|---|
| 반환 | `string[]` | `IEnumerable<string>` |
| 평가 | 즉시 (전체 수집 후 반환) | 지연 (한 개씩) |
| 첫 결과까지 | 전체 스캔이 끝나야 한다 | 즉시 |
| 메모리 | 전체 목록만큼 | 상수 |
| 중간에 멈출 수 있나 | 아니오 | 예 (`First`, `Take`) |
| 도중에 예외가 나면 | 아무것도 못 받는다 | 그때까지 받은 것은 유효 |

> **💡 파일이 수십만 개인 디렉터리에서는 선택이 아니라 필수다**
>
> `Directory.GetFiles(@"C:\Windows\System32")`는 배열을 다 만들 때까지 반환하지 않는다. 네트워크 드라이브라면 수십 초가 걸릴 수 있다. `EnumerateFiles`는 첫 항목을 즉시 준다. UI 스레드에서 파일 목록을 보여 주는 코드라면 이 차이가 "응답 없음" 여부를 가른다.
>
> 반대로 **파일 크기 같은 메타데이터를 함께 읽어야 한다면** `DirectoryInfo.EnumerateFiles`가 반환하는 `FileInfo`를 쓰는 편이 낫다. `Directory.EnumerateFiles`가 준 문자열로 `new FileInfo(path).Length`를 다시 부르면 파일마다 추가 시스템 콜이 발생한다. 디렉터리 크기를 합산하는 코드에서 이 차이는 실측으로 확인되는 수준이다.
>
> ```csharp
> // 느린 방식: 경로 문자열 → FileInfo를 다시 만든다
> long size1 = Directory.GetFiles(dir).Sum(p => new FileInfo(p).Length);
>
> // 빠른 방식: 열거 과정에서 이미 채워진 메타데이터를 쓴다
> long size2 = new DirectoryInfo(dir).EnumerateFiles().Sum(f => f.Length);
> ```

디렉터리가 없으면 만드는 관용구는 이렇다.

```csharp
if (!Directory.Exists(@"d:\test"))
    Directory.CreateDirectory(@"d:\test");
```

사실 `Directory.CreateDirectory`는 **이미 존재하면 아무 일도 하지 않는다**. `Exists` 검사는 없어도 된다 — 그리고 40.16절에서 볼 TOCTOU 관점에서는 없는 편이 낫다.

### `FileInfo`와 `DirectoryInfo`

`FileInfo`는 `File`의 정적 메서드 대부분을 인스턴스 형태로 제공하며, `Extension`, `Length`, `IsReadOnly`, `Directory`(`DirectoryInfo` 객체 반환) 같은 속성이 추가된다.

```csharp
static string TestDirectory =>
    RuntimeInformation.IsOSPlatform(OSPlatform.Windows) ? @"C:\Temp" : "/tmp";

Directory.CreateDirectory(TestDirectory);

FileInfo fi = new FileInfo(Path.Combine(TestDirectory, "FileInfo.txt"));

using (TextWriter w = fi.CreateText())
    w.Write("Some text");

fi.Refresh();

Console.WriteLine(fi.Name);            // FileInfo.txt
Console.WriteLine(fi.FullName);        // C:\temp\FileInfo.txt / /tmp/FileInfo.txt
Console.WriteLine(fi.DirectoryName);   // C:\temp / /tmp
Console.WriteLine(fi.Extension);       // .txt
Console.WriteLine(fi.Length);          // 9

fi.Attributes ^= FileAttributes.Hidden;   // 숨김 플래그를 토글한다
fi.IsReadOnly = true;
fi.MoveTo(Path.Combine(TestDirectory, "FileInfoX.txt"));

DirectoryInfo di = fi.Directory;
Console.WriteLine(di.FullName);          // C:\temp 또는 /tmp
Console.WriteLine(di.Parent.FullName);   // C:\ 또는 /
di.CreateSubdirectory("SubFolder");
```

`DirectoryInfo`로 파일과 하위 디렉터리를 열거하는 방법은 이렇다.

```csharp
DirectoryInfo di = new DirectoryInfo(@"e:\photos");

foreach (FileInfo fi in di.GetFiles("*.jpg"))
    Console.WriteLine(fi.Name);

foreach (DirectoryInfo subDir in di.GetDirectories())
    Console.WriteLine(subDir.FullName);
```

`DirectoryInfo.CreateSubdirectory()`는 단일 하위 디렉터리는 물론 **중첩된 여러 하위 디렉터리를 한 번의 호출로** 만들 수 있다. 반환값을 받지 않아도 되지만, 성공하면 새로 만든 항목을 나타내는 `DirectoryInfo` 객체가 돌아온다.

```csharp
DirectoryInfo dir = new DirectoryInfo(".");
dir.CreateSubdirectory("MyFolder");

DirectoryInfo myDataFolder = dir.CreateSubdirectory(
    $"MyFolder2{Path.DirectorySeparatorChar}Data");
```

`Directory.Delete`의 두 번째 인자는 하위 디렉터리까지 지울지를 정한다.

```csharp
Directory.Delete("MyFolder");
Directory.Delete("MyFolder2", recursive: true);
```

> **⚠️ `Directory.Delete(path, true)`는 되돌릴 수 없다**
>
> 재귀 삭제는 휴지통을 거치지 않는다. 경로 계산에 버그가 있으면 사용자의 문서 폴더가 통째로 사라진다. 사용자 입력이나 설정 파일에서 온 경로에 재귀 삭제를 적용하기 전에는 **`Path.GetFullPath`로 정규화하고, 허용된 루트 아래인지 검사**해야 한다(40.8절의 Zip Slip 검사와 같은 패턴이다).

### `Path` 클래스

정적 `Path` 클래스는 경로와 파일명을 다루는 메서드와 필드를 정의한다. 다음 설정을 가정하자.

```csharp
string dir  = @"c:\mydir";                 // 또는 /mydir
string file = "myfile.txt";
string path = @"c:\mydir\myfile.txt";      // 또는 /mydir/myfile.txt
Directory.SetCurrentDirectory(@"k:\demo"); // 또는 /demo
```

| 식 | 결과 (Windows / Unix) |
|---|---|
| `Directory.GetCurrentDirectory()` | `k:\demo\` / `/demo` |
| `Path.IsPathRooted(file)` | False |
| `Path.IsPathRooted(path)` | True |
| `Path.GetPathRoot(path)` | `c:\` / `/` |
| `Path.GetDirectoryName(path)` | `c:\mydir` / `/mydir` |
| `Path.GetFileName(path)` | `myfile.txt` |
| `Path.GetFullPath(file)` | `k:\demo\myfile.txt` / `/demo/myfile.txt` |
| `Path.Combine(dir, file)` | `c:\mydir\myfile.txt` / `/mydir/myfile.txt` |
| `Path.HasExtension(file)` | True |
| `Path.GetExtension(file)` | `.txt` |
| `Path.GetFileNameWithoutExtension(file)` | `myfile` |
| `Path.ChangeExtension(file, ".log")` | `myfile.log` |
| `Path.DirectorySeparatorChar` | `\` / `/` |
| `Path.AltDirectorySeparatorChar` | `/` |
| `Path.PathSeparator` | `;` / `:` |
| `Path.VolumeSeparatorChar` | `:` / `/` |
| `Path.GetInvalidPathChars()` | 문자 0~31과 `"<>` 및 세로줄 / 문자 0 |
| `Path.GetInvalidFileNameChars()` | 문자 0~31과 `"<>:*?\/` 및 세로줄 / 문자 0과 `/` |
| `Path.GetTempPath()` | `<로컬 사용자 폴더>\Temp` / `/tmp/` |
| `Path.GetRandomFileName()` | `d2dwuzjf.dnp` |
| `Path.GetTempFileName()` | `<로컬 사용자 폴더>\Temp\tmp14B.tmp` / `/tmp/tmpubSUYO.tmp` |

`Combine`이 특히 유용하다. 후행 경로 구분자가 있는지 먼저 확인할 필요 없이 디렉터리와 파일명 — 또는 두 디렉터리 — 을 결합할 수 있고, OS에 맞는 경로 구분자를 자동으로 쓴다. 디렉터리와 파일명을 최대 네 개까지 받는 오버로드가 있다. `GetFullPath`는 현재 디렉터리 기준의 상대 경로를 절대 경로로 변환하며, `..\..\file.txt` 같은 값도 받는다.

### `Combine` vs `Join` vs `GetFullPath`

세 메서드는 비슷해 보이지만 결정적으로 다르다.

| | `Path.Combine` | `Path.Join` ※.NET Core 2.1 | `Path.GetFullPath` |
|---|---|---|---|
| 뒤 조각이 절대 경로면 | **앞을 전부 버린다** | 그냥 이어 붙인다 | 해당 없음 |
| 구분자 중복 정리 | 한다 | 한다 | 한다 |
| `..`, `.` 해소 | **안 한다** | 안 한다 | **한다** |
| 잘못된 문자 검사 | 하지 않는다(모던 .NET) | 하지 않는다 | 예외를 던질 수 있다 |
| 파일 시스템 접근 | 없다 | 없다 | 없다(문자열 연산) |
| 결과 | 조합된 경로 | 조합된 경로 | 절대 경로 |

> **⚠️ `Path.Combine`은 절대 경로를 만나면 앞의 것을 버린다**
>
> 이것이 이 절에서 가장 위험한 함정이다.
>
> ```csharp
> Path.Combine(@"C:\safe\uploads", "report.txt")     // C:\safe\uploads\report.txt
> Path.Combine(@"C:\safe\uploads", @"C:\Windows\System32\evil.dll")
> //  → C:\Windows\System32\evil.dll   (앞의 C:\safe\uploads가 사라졌다)
>
> Path.Combine("/var/app/data", "/etc/passwd")       // /etc/passwd
> ```
>
> 사용자·아카이브·네트워크에서 온 문자열을 신뢰된 기준 디렉터리와 `Combine`하는 코드는 **경로 탈출 취약점 그 자체**다. 두 가지 방어가 있다.
>
> 1. `Path.Join`을 쓴다. 절대 경로여도 앞을 버리지 않고 그냥 이어 붙인다.
> 2. 결합 후 `Path.GetFullPath`로 정규화하고, 기준 디렉터리로 시작하는지 검사한다.
>
> 두 번째가 근본적인 방어다. `Join`만으로는 `..`을 막지 못하기 때문이다.
>
> ```csharp
> string root = Path.GetFullPath(baseDir) + Path.DirectorySeparatorChar;
> string full = Path.GetFullPath(Path.Join(root, untrusted));
> if (!full.StartsWith(root, StringComparison.Ordinal))
>     throw new UnauthorizedAccessException();
> ```

> **📌 `Path.GetRelativePath`와 `Path.EndsInDirectorySeparator`**
>
> .NET Core 2.1 이후 `Path`에 유용한 메서드가 몇 개 추가됐다. `Path.GetRelativePath(relativeTo, path)`는 한 경로를 다른 경로 기준의 상대 경로로 바꾼다. `Path.EndsInDirectorySeparator`와 `Path.TrimEndingDirectorySeparator`는 위와 같은 접두사 비교 검사를 쓸 때 후행 구분자를 정리하는 데 쓴다. `Span<char>`를 받는 오버로드도 있어 할당 없이 경로를 조작할 수 있다(68.5절).

### 임시 파일

`GetRandomFileName`은 실제로 파일을 만들지 않고 **8.3 형식의 진짜 고유한 파일명**을 반환한다. `GetTempFileName`은 자동 증가 카운터로 임시 파일명을 만드는데(이 카운터는 **65,000개마다 반복된다**), 그런 다음 로컬 임시 디렉터리에 이 이름으로 0바이트 파일을 만든다.

> **⚠️ `Path.GetTempFileName`은 결국 예외를 던진다**
>
> `GetTempFileName`이 만든 파일은 다 쓰고 나면 **반드시 삭제해야 한다.** 그러지 않으면 65,000번째 호출 이후 예외가 난다. 서버 프로세스에서 요청마다 임시 파일을 만들면서 정리하지 않으면 언젠가 서비스 전체가 멈춘다.
>
> 문제가 되면 `GetTempPath`와 `GetRandomFileName`을 `Combine`해서 쓴다. 다만 사용자의 하드 드라이브를 가득 채우지 않도록 주의해야 한다.
>
> ```csharp
> string temp = Path.Combine(Path.GetTempPath(), Path.GetRandomFileName());
> ```
>
> 더 나은 방법은 `FileOptions.DeleteOnClose`를 함께 쓰는 것이다. 스트림이 닫히면 파일이 사라지므로, 프로세스가 정상 종료하는 한 잔해가 남지 않는다.
>
> ```csharp
> using var fs = new FileStream(temp, FileMode.CreateNew, FileAccess.ReadWrite,
>                               FileShare.None, 4096, FileOptions.DeleteOnClose);
> ```
>
> `GetTempFileName`이 **파일을 실제로 만든다**는 사실도 함정이다. `File.Move`로 다른 파일을 그 이름으로 옮기려 하면 "이미 존재한다"로 실패한다. 반면 `GetRandomFileName`은 이름만 주므로 이 문제가 없다.

## 40.11 특수 폴더, 볼륨 정보, 파일 시스템 이벤트 감시

### 특수 폴더

`Path`와 `Directory`에 빠진 것이 하나 있다. 내 문서, Program Files, Application Data 같은 폴더를 찾아내는 수단으로, `System.Environment` 클래스의 `GetFolderPath` 메서드가 제공한다.

```csharp
string myDocPath = Environment.GetFolderPath(
    Environment.SpecialFolder.MyDocuments);
```

`Environment.SpecialFolder`는 `AdminTools`, `ApplicationData`, `Fonts`, `History`, `SendTo`, `StartMenu` 등 Windows의 모든 특수 디렉터리를 값으로 갖는 열거형이다. .NET 런타임 디렉터리만 빠져 있는데, 그것은 이렇게 얻는다.

```csharp
System.Runtime.InteropServices.RuntimeEnvironment.GetRuntimeDirectory()
```

Windows 시스템에서 특히 가치 있는 것은 다음과 같다.

| `SpecialFolder` | 의미 | 대상 |
|---|---|---|
| `ApplicationData` | 네트워크를 따라 사용자와 함께 이동하는 설정 (도메인에서 로밍 프로필이 켜져 있을 때) | 현재 사용자, 로밍 |
| `LocalApplicationData` | 비로밍 데이터 | 현재 사용자, 로컬 |
| `CommonApplicationData` | 컴퓨터의 모든 사용자가 공유 | 전체 사용자 |
| `MyDocuments` | 사용자 문서의 권장 위치 | 현재 사용자 |

이 폴더에 애플리케이션 데이터를 쓰는 것이 Windows 레지스트리를 쓰는 것보다 낫다고 여겨진다. 이 폴더에 데이터를 저장하는 표준 규약은 **애플리케이션 이름으로 하위 디렉터리를 만드는 것**이다.

```csharp
string appDataPath = Path.Combine(
    Environment.GetFolderPath(Environment.SpecialFolder.ApplicationData),
    "MyCoolApplication");          // 로밍이 필요 없으면 LocalApplicationData

if (!Directory.Exists(appDataPath))
    Directory.CreateDirectory(appDataPath);
```

> **⚠️ `CommonApplicationData`에는 지독한 함정이 있다**
>
> 사용자가 관리자 권한 상승 상태로 프로그램을 시작하고, 프로그램이 `CommonApplicationData`에 폴더와 파일을 만든다고 하자. 나중에 **제한된 Windows 로그인으로 실행할 때 그 사용자는 자기가 만든 파일을 교체할 권한이 없을 수 있다.** (제한 권한 계정끼리 전환할 때도 비슷한 문제가 생긴다.)
>
> 해법은 설치 과정에서 원하는 폴더를 **모두에게 권한을 부여한 상태로** 미리 만들어 두는 것이다.

> **⚠️ 애플리케이션 기준 디렉터리에 쓰지 마라**
>
> 설정·로그 파일을 `AppContext.BaseDirectory`에 쓰는 것은 권장되지 않는다. 최초 설치 이후 OS가 (관리자 권한 상승 없이) 이 폴더에 쓰기 권한을 거부할 가능성이 높기 때문이다. `Program Files` 아래에 설치된 앱이라면 거의 확실히 실패한다.

> **📌 Unix에서는 대부분의 특수 폴더가 비어 있다**
>
> Unix 시스템에서는 대부분의 특수 폴더에 경로가 할당되지 않아 `GetFolderPath`가 빈 문자열을 반환한다. 원천 도서가 확인한 Ubuntu Linux 18.04 데스크톱에서 경로가 있는 것은 `ApplicationData`, `CommonApplicationData`, `Desktop`, `DesktopDirectory`, `LocalApplicationData`, `MyDocuments`, `MyMusic`, `MyPictures`, `MyVideos`, `Templates`, `UserProfile`이었다. 크로스 플랫폼 앱이라면 **빈 문자열이 돌아올 가능성을 반드시 처리**해야 한다.

### 볼륨 정보 조회

`DriveInfo` 클래스로 컴퓨터의 드라이브를 조회한다.

```csharp
DriveInfo c = new DriveInfo("C");        // C: 드라이브 조회. Unix에서는 /

long totalSize  = c.TotalSize;           // 바이트 단위 크기
long freeBytes  = c.TotalFreeSpace;      // 디스크 할당량을 무시한다
long freeToMe   = c.AvailableFreeSpace;  // 할당량을 반영한다

foreach (DriveInfo d in DriveInfo.GetDrives())   // Unix에서는 마운트 지점
{
    Console.WriteLine($"{d.Name} {d.DriveType} {d.RootDirectory}");  // C:\ Fixed C:\

    // 드라이브가 준비되지 않았다면 다음 두 속성은 예외를 던진다
    if (d.IsReady)
        Console.WriteLine($"{d.VolumeLabel} {d.DriveFormat}");       // OS NTFS
}
```

정적 `GetDrives` 메서드는 CD-ROM, 미디어 카드, 네트워크 연결을 포함해 매핑된 모든 드라이브를 반환한다. `DriveType`은 다음 값을 갖는 열거형이다.

```text
Unknown, NoRootDirectory, Removable, Fixed, Network, CDRom, Ram
```

> **⚠️ `IsReady`를 확인하지 않으면 예외가 난다**
>
> 빈 CD 드라이브, 연결이 끊긴 네트워크 드라이브, 꺼진 이동식 미디어에 `VolumeLabel`이나 `DriveFormat`을 물으면 예외가 난다. `DriveInfo.GetDrives()`를 순회하는 코드에는 `IsReady` 검사가 사실상 필수다. 그리고 **`IsReady`가 true를 반환한 직후에 미디어가 빠질 수도 있다** — 40.16절의 TOCTOU 문제와 같은 성격이므로, 검사와 예외 처리를 함께 둔다.

`TotalFreeSpace`와 `AvailableFreeSpace`의 차이도 기억할 만하다. 디스크 할당량(quota)이 걸린 환경에서 "디스크에 남은 공간"과 "내가 쓸 수 있는 공간"은 다르다. 저장 가능 여부를 판단할 때는 `AvailableFreeSpace`를 봐야 한다.

### 파일 시스템 이벤트 감시

`FileSystemWatcher` 클래스는 디렉터리(그리고 선택적으로 하위 디렉터리)의 활동을 감시한다. 파일이나 하위 디렉터리가 생성·수정·이름 변경·삭제될 때, 그리고 속성이 바뀔 때 이벤트를 발생시키며, 이 이벤트는 **변경을 수행한 사용자나 프로세스와 무관하게** 발생한다. 감시 대상은 `NotifyFilters` 열거형으로 지정한다.

```csharp
public enum NotifyFilters
{
    Attributes, CreationTime, DirectoryName, FileName,
    LastAccess, LastWrite, Security, Size
}
```

```csharp
void Watch(string path, string filter, bool includeSubDirs)
{
    using var watcher = new FileSystemWatcher(path, filter);

    watcher.Created += FileCreatedChangedDeleted;
    watcher.Changed += FileCreatedChangedDeleted;
    watcher.Deleted += FileCreatedChangedDeleted;
    watcher.Renamed += FileRenamed;
    watcher.Error   += FileError;

    watcher.IncludeSubdirectories = includeSubDirs;
    watcher.EnableRaisingEvents   = true;

    Console.WriteLine("Listening for events - press <enter> to end");
    Console.ReadLine();
    // FileSystemWatcher를 해제하면 이후 이벤트가 멈춘다
}

void FileCreatedChangedDeleted(object o, FileSystemEventArgs e)
    => Console.WriteLine("File {0} has been {1}", e.FullPath, e.ChangeType);
void FileRenamed(object o, RenamedEventArgs e)
    => Console.WriteLine("Renamed: {0}->{1}", e.OldFullPath, e.FullPath);
void FileError(object o, ErrorEventArgs e)
    => Console.WriteLine("Error: " + e.GetException().Message);
```

> **⚠️ 이벤트 핸들러에서 예외가 새면 프로세스가 죽는다**
>
> `FileSystemWatcher`는 **별도 스레드에서 이벤트를 발생시킨다.** 핸들러 안에서 처리되지 않은 예외가 나면 오류가 애플리케이션 전체를 끌어내린다(32.14절). 이벤트 처리 코드는 반드시 예외 처리로 감싸야 한다.

> **⚠️ `Error` 이벤트는 파일 시스템 오류가 아니다**
>
> `Error` 이벤트는 파일 시스템 오류를 알려 주지 않는다. **`FileSystemWatcher`의 이벤트 버퍼가 오버플로했음**을 알린다 — `Changed`, `Created`, `Deleted`, `Renamed` 이벤트가 감당할 수 없이 몰렸다는 뜻이다. 버퍼 크기는 `InternalBufferSize` 속성으로 바꿀 수 있다.
>
> 그리고 **버퍼가 넘치면 그 사이의 이벤트는 영구히 유실된다.** 다시 받을 방법이 없다. 이것이 `FileSystemWatcher`를 신뢰할 수 없는 근본 이유다.

> **⚠️ 중복 이벤트와 "아직 다 안 쓴 파일"**
>
> `FileSystemWatcher`에는 잘 알려진 두 가지 병리가 더 있다.
>
> 1. **중복 이벤트.** 파일 하나를 저장했을 뿐인데 `Changed`가 두 번, 세 번 온다. 편집기가 내부적으로 여러 번 쓰거나 메타데이터를 갱신하기 때문이다. `NotifyFilter`를 좁혀도 완전히 사라지지 않는다. 짧은 시간 창 안의 중복을 제거하는 디바운싱이 필요하다.
> 2. **완성되지 않은 파일.** 파일이 완전히 기록되기 전에 `Created` 이벤트가 온다. 그 자리에서 열면 내용이 비어 있거나 잘려 있고, 심지어 쓰는 쪽이 아직 잡고 있으면 `IOException`이 난다. 파일을 만드는 다른 소프트웨어와 함께 동작한다면, **감시하지 않는 확장자로 만든 뒤 다 쓰고 이름을 바꾸는 전략**을 상대에게 요구하거나, 열기를 재시도하는 정책을 두어야 한다(40.16절).

> **⚠️ `IncludeSubdirectories`는 재귀적이다**
>
> `IncludeSubdirectories`는 재귀적으로 적용된다. `C:\`에 `IncludeSubdirectories = true`로 `FileSystemWatcher`를 만들면 **하드 드라이브 어디에서 파일이나 디렉터리가 바뀌든 이벤트가 발생한다.** 버퍼 오버플로로 가는 가장 빠른 길이다.

> **💡 `FileSystemWatcher`는 힌트로만 쓰고, 폴링을 병행하라**
>
> 정리하면 `FileSystemWatcher`는 **유실될 수 있고, 중복될 수 있고, 이른 시점에 올 수 있다.** 네트워크 드라이브에서는 더 나쁘다. 데이터 정확성이 걸린 시스템에서 이것만 믿으면 안 된다.
>
> 실무에서 검증된 구조는 이렇다.
>
> - `FileSystemWatcher`는 "**지금 확인해 볼 만하다**"는 힌트로만 쓴다
> - 실제 판단은 **디렉터리를 다시 스캔**해서 한다 (마지막 처리 시각·해시·크기 비교)
> - 이벤트가 없어도 **N초마다 한 번은 무조건 스캔**한다 (유실 대비)
> - 이벤트는 **디바운싱**해서 스캔 폭주를 막는다
>
> 감시자가 있어서 반응이 빨라지고, 폴링이 있어서 절대 놓치지 않는다.

## 40.12 크로스 플랫폼 경로 함정과 긴 경로

.NET은 Windows API와의 상호작용을 감춰 주는 관리 코드를 제공한다. `System.IO` 네임스페이스는 경로 정보를 OS API에 넘기고, OS가 작업을 수행한 뒤 제어를 .NET에 돌려준다. 즉 **경로 문자열의 규칙은 결국 OS가 정한다.** 크로스 플랫폼 코드에서 사고가 나는 지점이 여기다.

### 경로 형식

.NET의 파일 경로는 절대 경로, 상대 경로, UNC 경로, DOS 장치 경로 중 하나다.

| 형식 | 예 | 비고 |
|---|---|---|
| 절대 경로 (Windows) | `C:\temp\file.txt` | 드라이브 문자로 시작 |
| 드라이브 상대 | `C:file.txt` | **드라이브의 현재 디렉터리** 기준. 거의 항상 버그다 |
| 루트 상대 | `\temp\file.txt` | 현재 드라이브의 루트 기준 |
| 상대 경로 | `sub\file.txt` | 현재 디렉터리 기준 |
| UNC 경로 | `\\server\share\file.txt` | 네트워크 공유 |
| DOS 장치 경로 | `\\?\C:\temp\file.txt` | 경로 정규화를 건너뛴다 |
| 절대 경로 (Unix) | `/tmp/file.txt` | `/`가 유일한 루트 |

> **⚠️ `C:file.txt`는 `C:\file.txt`가 아니다**
>
> Windows는 드라이브마다 현재 디렉터리를 따로 기억한다. `C:file.txt`는 "C 드라이브의 현재 디렉터리에 있는 file.txt"를 뜻한다. 문자열을 조립하다 백슬래시 하나를 빠뜨리면 완전히 다른 파일을 가리키게 된다. 그리고 이 형식은 Unix에서 아무 의미가 없다 — 그냥 `C:file.txt`라는 이름의 파일이 된다.

### 구분자

`Path.DirectorySeparatorChar`는 Windows에서 `\`, Unix에서 `/`다. `Path.AltDirectorySeparatorChar`는 양쪽 모두 `/`다.

> **📌 Windows는 `/`도 받아 준다**
>
> Windows API는 대부분의 경우 `/`를 디렉터리 구분자로 받아들인다. 그래서 `"data/config.json"`은 양쪽 플랫폼에서 모두 동작한다. 반대는 성립하지 않는다 — Unix에서 `"data\config.json"`은 `data\config.json`이라는 **이름 하나짜리 파일**이다. 백슬래시는 Unix에서 완전히 유효한 파일명 문자다.
>
> 그러므로 하드코딩해야 한다면 `/`를 쓰는 편이 덜 위험하다. 물론 `Path.Combine`/`Path.Join`을 쓰는 것이 정답이다.

`Path.PathSeparator`는 다른 물건이다. **여러 경로를 나열할 때** 쓰는 구분자로 Windows에서 `;`, Unix에서 `:`다(`PATH` 환경 변수를 생각하면 된다). 이름이 비슷해 `DirectorySeparatorChar`와 혼동하기 쉽다.

### 대소문자 구분

**Windows의 파일과 디렉터리는 대소문자를 구분하지 않는다. Unix 계열은 구분한다.**

이 한 줄이 만드는 사고는 다음과 같다.

- Windows에서 개발한 코드가 `Config.json`을 `config.json`으로 열어도 잘 된다. Linux 컨테이너에 배포하는 순간 `FileNotFoundException`이 난다.
- 같은 디렉터리에 `README.md`와 `readme.md`가 **동시에 존재할 수 있다** (Unix). 이 디렉터리를 Windows로 복사하면 하나가 사라지거나 충돌한다.
- 경로 문자열 비교에 `StringComparison.Ordinal`을 쓰면 Windows에서 같은 파일을 다르다고 판정한다. `OrdinalIgnoreCase`를 쓰면 Unix에서 다른 파일을 같다고 판정한다.

> **⚠️ 경로 비교에 정답인 `StringComparison`은 없다**
>
> 40.8절의 Zip Slip 방어에서 `StringComparison.Ordinal`을 썼다. 보안 검사에서는 이것이 옳다 — **더 엄격한 쪽으로 틀리기** 때문이다. 대소문자만 다른 경로를 "탈출 시도"로 오판해 거부하는 것은 안전하지만, 반대는 취약점이다.
>
> 반면 "이 파일을 이미 처리했나"를 판정하는 캐시 키 같은 용도라면 플랫폼에 맞춰야 한다. 확실한 방법은 두 경로 모두 `Path.GetFullPath`로 정규화한 뒤, Windows에서만 `OrdinalIgnoreCase`를 쓰는 것이다. 파일이 실제로 존재한다면 `FileInfo`의 `FullName`을 비교하는 편이 더 정확하다.
>
> macOS의 기본 파일 시스템(APFS)은 기본 설정에서 대소문자를 구분하지 않지만, 구분하도록 포맷할 수도 있다. **"macOS는 이렇다"라고 단정할 수 없다.**

### 예약 이름과 금지 문자 (Windows)

Windows에는 DOS 시대에서 물려받은 예약 장치 이름이 있다.

```text
CON, PRN, AUX, NUL, COM1~COM9, LPT1~LPT9
```

확장자를 붙여도 예약이 유지된다. `CON.txt`라는 파일을 만들 수 없다. Unix에는 이런 제약이 없으므로, 사용자 입력으로 파일명을 만드는 코드는 Linux에서는 통과하고 Windows에서는 실패한다.

금지 문자도 다르다. Windows는 `< > : " | ? *` 와 제어 문자(0~31)를 파일명에 쓸 수 없고, Unix는 `/`와 NUL만 금지한다. 또 Windows는 **파일명이 공백이나 마침표로 끝나는 것**을 허용하지 않는다(조용히 잘라 낸다).

> **💡 사용자 입력으로 파일명을 만들 때의 규칙**
>
> 크로스 플랫폼을 목표로 한다면 **가장 엄격한 규칙(Windows)에 맞춘다.**
>
> ```csharp
> static string SanitizeFileName(string name)
> {
>     foreach (char c in Path.GetInvalidFileNameChars())
>         name = name.Replace(c, '_');
>
>     name = name.TrimEnd(' ', '.');
>
>     string stem = Path.GetFileNameWithoutExtension(name);
>     string[] reserved = { "CON","PRN","AUX","NUL",
>                           "COM1","COM2","COM3","COM4","COM5",
>                           "COM6","COM7","COM8","COM9",
>                           "LPT1","LPT2","LPT3","LPT4","LPT5",
>                           "LPT6","LPT7","LPT8","LPT9" };
>     if (reserved.Contains(stem, StringComparer.OrdinalIgnoreCase))
>         name = "_" + name;
>
>     return string.IsNullOrEmpty(name) ? "_" : name;
> }
> ```
>
> `Path.GetInvalidFileNameChars()`는 **현재 실행 중인 플랫폼의** 목록을 반환한다는 점에 주의한다. Linux에서 실행하면 `/`와 NUL만 걸러진다. Windows 클라이언트에 배포될 파일명을 Linux 서버에서 만든다면 위처럼 명시적 목록이 필요하다.

### `MAX_PATH`와 긴 경로 지원

기본적으로 Windows는 길이 260자까지의 경로만 받아들인다(이 상수를 `MAX_PATH`라고 부른다). 파일을 백업하거나 옮길 때 나오는 "대상 경로가 너무 김" 경고가 이것이다. NPM으로 노드 모듈을 쓰는 웹 프로젝트가 대표적인 사례로, 패키지 경로가 깊게 중첩되면서 260자를 쉽게 넘긴다. 성능 관점에서도 이 문제는 시간을 낭비시킨다. 수십 GB를 복사하는 작업이 **28분 뒤에 경로 길이 때문에 실패**하면 그 시간이 통째로 날아간다. 파일 관리 애플리케이션이라면 복사 전에 예상 경로 길이를 검사해 사용자에게 미리 경고하고, 파일 구조를 재정리할 기회를 주거나 레지스트리 설정을 대신 갱신해 주는 편이 낫다.

제한을 없애는 방법은 두 가지다.

| 방법 | 절차 |
|---|---|
| 레지스트리 | `regedit` → `HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Control\FileSystem` → `LongPathsEnabled`를 `1`로 설정(없으면 32비트 DWORD로 추가) |
| 그룹 정책 | `gpedit.msc` → 컴퓨터 구성 → 관리 템플릿 → 시스템 → 파일 시스템 → **Win32 긴 경로 사용**을 **사용**으로 |

둘 다 반드시 필요하지는 않지만 변경 사항 반영을 위해 재시작하는 것이 좋다. `gpedit.msc`는 일부 Windows 에디션에서 제공되지 않거나 기업 그룹 정책 때문에 사용할 수 없을 수 있다.

> **⚠️ 레지스트리 편집은 신중하게**
>
> 레지스트리를 변경할 때는 항상 주의해야 한다. 권한 문제가 생기면 레지스트리 편집기를 관리자로 실행하고, 그래도 안 되면 시스템 관리자에게 문의한다.

> **📌 긴 경로 지원은 앱도 선언해야 한다**
>
> `LongPathsEnabled`를 켜는 것만으로는 부족한 경우가 있다. 애플리케이션 매니페스트에 `longPathAware` 설정이 있어야 프로세스가 긴 경로를 쓸 수 있다. 모던 .NET 런타임은 이를 기본으로 켜지만, 호스팅 방식에 따라 달라질 수 있다.
>
> 프로그램 차원의 우회로는 **DOS 장치 경로 접두사**를 쓰는 것이다. 경로 앞에 `\\?\`를 붙이면 Windows는 정규화를 건너뛰고 약 32,767자까지 허용한다. UNC 경로에는 `\\?\UNC\server\share\...` 형태를 쓴다.
>
> ```csharp
> string longPath = @"\\?\C:\very\deep\...\file.txt";
> ```
>
> 단, `\\?\` 경로는 **정규화되지 않는다**. `..`, `.`, 상대 경로, `/` 구분자가 해석되지 않으므로 완전히 정규화된 절대 경로를 직접 만들어 넘겨야 한다. 이 접두사는 **Windows 전용**이라 크로스 플랫폼 코드에서는 조건부로만 써야 한다.

> **💡 백업이 조용히 실패하는 이유**
>
> 경로 길이 제한 때문에 클라이언트와 서버의 중요한 백업이 실패한 사례가 실제로 있다. 서드파티 라이브러리와 작업할 때 개발 프로젝트가 깨지기도 한다. 파일을 다루는 도구를 만든다면 이 제한을 **알고 있는 것만으로는 부족하고, 실패를 사용자에게 보이게 만들어야 한다.** 예외를 삼키고 "완료"라고 표시하는 백업 도구가 최악이다.

## 40.13 OS 보안 — 표준 사용자 계정, 관리자 권한 상승, 가상화

모든 애플리케이션은 사용자의 로그인 권한에 근거한 OS 제약을 받는다. 이 제약은 파일 I/O뿐 아니라 Windows 레지스트리 접근 같은 다른 기능에도 영향을 준다. Windows와 Unix 모두 계정은 두 종류다.

- 로컬 컴퓨터 접근에 제약이 없는 **관리자/슈퍼유저 계정**
- 관리 기능과 다른 사용자 데이터의 가시성을 제한하는 **제한 권한 계정**

Windows에는 **사용자 계정 컨트롤(UAC)** 이라는 기능이 있어, 관리자는 로그인할 때 두 개의 토큰(또는 "모자")을 받는다. 관리자 모자와 일반 사용자 모자다. 기본적으로 프로그램은 **일반 사용자 모자를 쓰고** — 제한된 권한으로 — 실행되며, 프로그램이 관리자 권한 상승을 요청하면 사용자가 표시된 대화 상자에서 요청을 승인해야 한다. Unix에서는 사용자가 대개 제한된 계정으로 로그인한다. 관리자도 시스템을 실수로 망가뜨릴 확률을 낮추기 위해 그렇게 한다. 상승된 권한이 필요한 명령을 실행할 때는 명령 앞에 `sudo`(super-user do)를 붙인다.

기본적으로 애플리케이션은 제한된 사용자 권한으로 실행된다. 즉 다음 둘 중 하나를 선택해야 한다.

- 관리자 권한 없이 실행되도록 애플리케이션을 작성한다.
- 애플리케이션 매니페스트에서 관리자 권한 상승을 요구하거나(Windows 전용), 필요한 권한이 없음을 감지해 관리자/슈퍼유저로 재시작하라고 사용자에게 알린다.

**첫 번째가 더 안전하고 사용자에게 편리하다.** 대부분의 경우 관리자 권한 없이 동작하도록 설계하는 것은 쉽다.

관리자 계정으로 실행 중인지 다음과 같이 알아낼 수 있다.

```csharp
[DllImport("libc")]
public static extern uint getuid();

static bool IsRunningAsAdmin()
{
    if (RuntimeInformation.IsOSPlatform(OSPlatform.Windows))
    {
        using var identity = WindowsIdentity.GetCurrent();
        var principal = new WindowsPrincipal(identity);
        return principal.IsInRole(WindowsBuiltInRole.Administrator);
    }
    return getuid() == 0;
}
```

Windows에서 UAC가 켜져 있으면 이 메서드는 **현재 프로세스가 관리자 권한으로 상승된 경우에만** true를 반환한다. Linux에서는 현재 프로세스가 슈퍼유저로 실행 중일 때(예: `sudo myapp`)만 true를 반환한다.

### 표준 사용자 계정에서 할 수 없는 것

| 금지되는 것 | 대상 |
|---|---|
| OS 폴더(`\Windows` 또는 `/bin`, `/sbin` 등)와 하위 디렉터리에 쓰기 | 양쪽 |
| 프로그램 파일 폴더(`\Program Files` 또는 `/usr/bin`, `/opt`)와 하위 디렉터리에 쓰기 | 양쪽 |
| OS 드라이브 루트(`C:\` 또는 `/`)에 쓰기 | 양쪽 |
| 레지스트리의 `HKEY_LOCAL_MACHINE` 분기에 쓰기 | Windows |
| 성능 모니터링(WMI) 데이터 읽기 | Windows |

또한 일반 Windows 사용자(심지어 관리자)라도 **다른 사용자에게 속한 파일이나 리소스**에는 접근이 거부될 수 있다. Windows는 접근 제어 목록(ACL)으로 이런 리소스를 보호하며, `System.Security.AccessControl`의 타입들로 ACL을 조회하고 자신의 권한을 주장할 수 있다.

> **⚠️ 권한 거부는 `UnauthorizedAccessException`으로 온다**
>
> OS 보안 때문에 무언가에 대한 접근이 거부되면 CLR이 실패를 감지해 **`UnauthorizedAccessException`을 던진다.** 조용히 실패하지 않는다. 이 예외가 나면 "코드가 틀렸다"가 아니라 "권한이 없다"로 해석해야 하며, 사용자에게 알려 주고 관리자 권한으로 재시작하도록 안내하는 것이 올바른 대응이다.

대부분의 경우 표준 사용자 제약은 다음으로 해결된다.

- 파일은 **권장 위치**에 쓴다(40.11절).
- 파일에 저장할 수 있는 정보는 레지스트리를 쓰지 않는다(Windows에서 읽기/쓰기 권한이 있는 `HKEY_CURRENT_USER` 하이브는 예외다).
- ActiveX나 COM 구성 요소는 **설치 과정에서** 등록한다(Windows 전용).

### 관리자 권한 상승과 가상화

애플리케이션 매니페스트로 프로그램을 실행할 때마다 Windows가 사용자에게 관리자 권한 상승을 요청하도록 만들 수 있다(Linux는 이 요청을 무시한다).

```xml
<?xml version="1.0" encoding="utf-8"?>
<assembly manifestVersion="1.0" xmlns="urn:schemas-microsoft-com:asm.v1">
  <trustInfo xmlns="urn:schemas-microsoft-com:asm.v2">
    <security>
      <requestedPrivileges>
        <requestedExecutionLevel level="requireAdministrator" />
      </requestedPrivileges>
    </security>
  </trustInfo>
</assembly>
```

애플리케이션 매니페스트의 상세는 52장에서 다룬다.

`requireAdministrator`를 `asInvoker`로 바꾸면 관리자 권한 상승이 필요 없다고 Windows에 알린다. 애플리케이션 매니페스트가 아예 없는 것과 효과가 거의 같은데, **딱 하나 다른 점은 가상화가 비활성화된다는 것**이다.

**가상화(virtualization)** 는 오래된 애플리케이션이 관리자 권한 없이 올바르게 동작하도록 돕기 위해 Windows Vista에서 도입된 임시 조치다. `requestedExecutionLevel` 요소가 있는 애플리케이션 매니페스트가 없으면 이 하위 호환 기능이 활성화된다. 가상화는 애플리케이션이 Program Files나 Windows 디렉터리, 또는 레지스트리의 `HKEY_LOCAL_MACHINE` 영역에 쓸 때 작동해, **예외를 던지는 대신 변경 사항을 하드 디스크의 별도 위치로 리디렉션**한다. 이는 애플리케이션이 OS나 다른 잘 동작하는 애플리케이션을 방해하는 것을 막는다.

> **⚠️ 가상화는 "성공한 것처럼 보이는 실패"다**
>
> 가상화의 리디렉션 대상은 `C:\Users\%USERNAME%\AppData\Local\VirtualStore`다. 사용자마다 별도의 가상 스토어가 있다.
>
> 여기서 실무의 악몽이 시작된다. 여러 사람이 한 사무실 컴퓨터에 로그인하는데 **각자 자기만의 데이터 사본을 갖게 되는** 현상이 그것이다. 애플리케이션은 "저장했다"고 보고하고, 사용자는 다른 사람의 변경 사항을 전혀 보지 못한다.
>
> 소프트웨어 설치 시 "**이 컴퓨터를 사용하는 모든 사람**"과 "**나만**" 중 후자를 고르면 이 상황이 자주 발생한다. 전자를 고르면 애플리케이션 데이터가 보통 `C:\ProgramData\제품이름`에 저장된다.
>
> 이런 상황이 이미 벌어졌다면 소프트웨어를 제거하고 **모든 사용자용으로 다시 설치**한 다음, 각 사용자의 가상 스토어에 흩어진 데이터를 병합해 중앙 위치에 넣어야 한다. 병합이 끝날 때까지 사용자들에게 소프트웨어 사용을 중단하도록 요청해야 한다.
>
> 가상 스토어의 위치를 아는 것만으로 기술 지원 시간이 크게 줄어든다.

### 로컬 저장소 위치 선택

| 위치 | 용도 | 백업 |
|---|---|---|
| `AppData\Local` | 재생성하거나 다시 받기 어려운 데이터, 설정, 파일 | 사용자 폴더 백업에 포함 |
| 로컬 캐시 | 세션 간 유지되는 캐시 데이터 | 대개 제외 |
| `AppData\Roaming` | 네트워크 사용자의 로밍 프로필. 서버에 저장된다 | 관리자가 정기 백업 |
| `AppData\Temp` | 임시 데이터 | 제외 |
| `C:\ProgramData` | 애플리케이션 데이터의 모범 위치 | **항상 백업되지는 않는다** |

`Temp` 폴더의 데이터는 다 쓰고 나면 정리하는 것이 좋다. **애플리케이션 초기화와 종료 시점**이 시스템 정리를 수행하기 좋은 지점이다.

> **💡 설치 위치를 가정하지 마라**
>
> 학교나 기업처럼 보안이 강하게 굳어진 시스템에서는 애플리케이션이 `C:\` 드라이브에 설치된다고 가정할 수 없고, `C:\ProgramData` 폴더에 접근할 수 있다고 가정할 수도 없다. 경로는 항상 `Environment.GetFolderPath`로 얻고, 쓰기 실패는 **예상되는 시나리오**로 처리해야 한다.

### Unix 파일 권한

.NET 7부터 `File` 클래스에 Unix 시스템의 파일 권한을 읽고 쓰는 `GetUnixFileMode`, `SetUnixFileMode` 메서드가 들어왔다. `Directory.CreateDirectory` 메서드도 Unix 파일 모드를 받도록 오버로드됐고, 파일 생성 시에도 모드를 지정할 수 있다. ※.NET 7

```csharp
var fs = new FileStream("test.txt",
    new FileStreamOptions
    {
        Mode = FileMode.Create,
        UnixCreateMode = UnixFileMode.UserRead | UnixFileMode.UserWrite
    });
```

`UnixFileMode`는 플래그 열거형으로, `UserRead`/`UserWrite`/`UserExecute`, `GroupRead`/`GroupWrite`/`GroupExecute`, `OtherRead`/`OtherWrite`/`OtherExecute`, 그리고 `SetUser`/`SetGroup`/`StickyBit`를 갖는다. 익숙한 8진수 표기 `0644`는 `UserRead | UserWrite | GroupRead | OtherRead`에 해당한다.

> **⚠️ Unix 권한 API를 Windows에서 호출하면 예외가 난다**
>
> `File.GetUnixFileMode`/`SetUnixFileMode`는 Windows에서 `PlatformNotSupportedException`을 던진다. `FileStreamOptions.UnixCreateMode` 역시 Windows에서는 무시되는 것이 아니라 예외의 원인이 될 수 있다. 크로스 플랫폼 코드에서는 `RuntimeInformation.IsOSPlatform(OSPlatform.Windows)`로 분기해야 한다.
>
> 그리고 실제로 적용되는 권한은 프로세스의 **umask**에 의해 더 좁혀진다. `UserRead | UserWrite | GroupRead`를 요청해도 umask가 `0077`이면 그룹 비트가 떨어진다. 비밀 키 파일처럼 권한이 중요한 경우에는 **생성 후 읽어서 검증**해야 한다.

## 40.14 메모리 매핑 파일 — 임의 접근 I/O, 공유 메모리, 뷰 접근자

메모리 매핑 파일은 두 가지 핵심 기능을 제공한다.

- **파일 데이터에 대한 효율적인 임의 접근**
- **같은 컴퓨터의 서로 다른 프로세스 간 메모리 공유**

관련 타입은 `System.IO.MemoryMappedFiles` 네임스페이스에 있다. 내부적으로는 OS의 메모리 매핑 파일 API를 감싼다.

### 임의 파일 I/O

일반 `FileStream`도 `Position` 속성을 설정해 임의 파일 I/O를 할 수 있지만 **순차 I/O에 최적화**돼 있다. 대략적인 경험칙은 이렇다.

- 순차 I/O에서는 `FileStream`이 메모리 매핑 파일보다 대략 **10배 빠르다**.
- 임의 I/O에서는 메모리 매핑 파일이 `FileStream`보다 대략 **10배 빠르다**.

`FileStream`의 `Position`을 바꾸는 데는 수 마이크로초가 들 수 있고 루프 안에서 반복하면 누적된다. 또한 `FileStream`은 읽거나 쓸 때 위치가 바뀌므로 **다중 스레드 접근에 적합하지 않다**. 메모리 매핑 파일을 만드는 절차는 세 단계다.

1. 평소처럼 `FileStream`을 얻는다.
2. `MemoryMappedFile`을 인스턴스화하면서 파일 스트림을 넘긴다.
3. 메모리 매핑 파일 객체에서 `CreateViewAccessor`를 호출한다.

마지막 단계가 `MemoryMappedViewAccessor` 객체를 준다. 단순 타입, 구조체, 배열을 임의로 읽고 쓰는 메서드를 제공한다.

```csharp
File.WriteAllBytes("long.bin", new byte[1000000]);

using MemoryMappedFile mmf = MemoryMappedFile.CreateFromFile("long.bin");
using MemoryMappedViewAccessor accessor = mmf.CreateViewAccessor();

accessor.Write(500000, (byte)77);
Console.WriteLine(accessor.ReadByte(500000));   // 77
```

`CreateFromFile`을 호출할 때 맵 이름과 용량도 지정할 수 있다. **null이 아닌 맵 이름을 지정하면 메모리 블록을 다른 프로세스와 공유**할 수 있고, 용량을 지정하면 파일이 그 값까지 자동으로 확장된다.

```csharp
File.WriteAllBytes("short.bin", new byte[1]);
using (var mmf = MemoryMappedFile.CreateFromFile(
           "short.bin", FileMode.Create, null, 1000))
{
    // 파일이 1,000바이트로 늘어난다
}
```

### `CreateViewAccessor` vs `CreateViewStream`

`MemoryMappedFile`에서 뷰를 얻는 방법은 두 가지다.

| | `CreateViewAccessor` | `CreateViewStream` |
|---|---|---|
| 반환 타입 | `MemoryMappedViewAccessor` | `MemoryMappedViewStream` (`Stream` 파생) |
| 접근 방식 | 오프셋을 명시한 임의 접근 | 순차 접근 (`Position` 기반) |
| 타입 지원 | `Read*`/`Write*` 로 값 타입·구조체·배열 | 바이트 |
| 기존 스트림 API와의 호환 | 없다 | 있다 (`StreamReader` 등을 꽂을 수 있다) |
| 스레드 안전 | 오프셋을 명시하므로 상대적으로 유리 | 위치 공유 문제 그대로 |

`CreateViewStream`은 메모리 매핑 영역을 평범한 `Stream`으로 보여 준다. 기존 스트림 코드를 재사용해야 할 때 편리하다. 반면 임의 접근이 목적이라면 뷰 접근자가 맞다.

두 메서드 모두 오프셋과 크기를 받아 **파일의 일부만 매핑**할 수 있다. 파일이 프로세스의 주소 공간보다 클 때 필수적인 기능이다.

> **⚠️ 32비트 프로세스에서 대용량 파일 전체를 매핑할 수 없다**
>
> 뷰는 프로세스의 가상 주소 공간을 소비한다. 32비트 프로세스는 사용자 모드 주소 공간이 보통 2GB 남짓이므로, 4GB 파일 전체를 매핑하려 하면 실패한다. 해법은 **필요한 구간만 창(window)으로 매핑하고 이동**하는 것이다.
>
> ```csharp
> using var view = mmf.CreateViewAccessor(offset: 1_000_000_000, size: 64 * 1024);
> ```
>
> 64비트 프로세스에서도 뷰는 주소 공간을 소비하며, 뷰를 해제하지 않고 계속 만들면 주소 공간이 고갈된다(33장의 표에서 `MemoryMappedFile`의 실패 양상으로 이미 언급했다). `MemoryMappedViewAccessor`와 `MemoryMappedViewStream`은 **반드시 해제해야 한다.**

> **⚠️ 뷰의 오프셋은 시스템 할당 단위에 정렬된다**
>
> OS는 뷰의 시작 오프셋을 시스템 할당 단위(Windows에서 보통 64KB)의 배수로 요구한다. 임의의 오프셋을 넘기면 예외가 나거나, 실제 매핑이 요청 위치보다 앞에서 시작한다. 창을 옮기며 스캔하는 코드는 이 정렬을 직접 계산해야 한다.

### 공유 메모리 IPC

Windows에서는 메모리 매핑 파일을 같은 컴퓨터의 프로세스 간 메모리 공유 수단으로 쓸 수 있다. 한 프로세스가 `MemoryMappedFile.CreateNew`를 호출해 공유 메모리 블록을 만들고, 다른 프로세스가 같은 이름으로 `MemoryMappedFile.OpenExisting`을 호출해 그 메모리 블록에 참여한다. 여전히 메모리 매핑 "파일"이라고 부르지만 **전적으로 메모리에 존재하며 디스크에 흔적이 없다.**

```csharp
// 프로세스 A: 500바이트 공유 메모리를 만들고 위치 0에 정수 12345를 쓴다
using (MemoryMappedFile mmFile = MemoryMappedFile.CreateNew("Demo", 500))
using (MemoryMappedViewAccessor accessor = mmFile.CreateViewAccessor())
{
    accessor.Write(0, 12345);
    Console.ReadLine();   // 사용자가 Enter를 누를 때까지 공유 메모리를 유지한다
}
```

```csharp
// 프로세스 B: 별도 실행 파일에서 실행될 수 있다
using (MemoryMappedFile mmFile = MemoryMappedFile.OpenExisting("Demo"))
using (MemoryMappedViewAccessor accessor = mmFile.CreateViewAccessor())
    Console.WriteLine(accessor.ReadInt32(0));   // 12345
```

> **⚠️ `CreateNew`/`OpenExisting`의 이름 기반 공유는 Windows 전용이다**
>
> 이름만으로 공유 메모리를 여는 방식은 Unix에서 지원되지 않는다. 크로스 플랫폼으로 프로세스 간 공유 메모리가 필요하면 **실제 파일을 양쪽이 매핑**해야 한다. 이때 파일 공유 설정에 각별히 주의해야 한다.

```csharp
// 양쪽 프로세스가 똑같이 호출하는 헬퍼
static (FileStream, MemoryMappedFile, MemoryMappedViewAccessor) OpenShared(string file)
{
    var fs = new FileStream(file, FileMode.Open, FileAccess.ReadWrite,
                            FileShare.ReadWrite);          // 공유 설정이 핵심이다
    var mmf = MemoryMappedFile.CreateFromFile(
        fs, null, fs.Length, MemoryMappedFileAccess.ReadWrite,
        HandleInheritability.None, leaveOpen: true);
    return (fs, mmf, mmf.CreateViewAccessor());
}

static void Writer(string file)
{
    File.WriteAllBytes(file, new byte[100]);
    var (fs, mmf, accessor) = OpenShared(file);
    using (fs) using (mmf) using (accessor)
    {
        accessor.Write(0, 12345);
        Console.ReadLine();          // 다른 프로세스가 읽을 때까지 유지한다
    }
    File.Delete(file);
}

static void Reader(string file)     // 별도 실행 파일에서 실행될 수 있다
{
    var (fs, mmf, accessor) = OpenShared(file);
    using (fs) using (mmf) using (accessor)
        Console.WriteLine(accessor.ReadInt32(0));   // 12345
}
```

`FileShare.ReadWrite`가 핵심이다. 기본값인 `FileShare.Read`로 열면 두 번째 프로세스가 파일을 열지 못한다.

> **⚠️ 공유 메모리에는 동기화가 따라와야 한다**
>
> 메모리 매핑 파일은 **데이터를 공유해 줄 뿐 동기화는 해 주지 않는다.** 한 프로세스가 `int`를 쓰는 동안 다른 프로세스가 읽으면 찢어진 값을 볼 수 있고, 여러 필드로 이루어진 구조체는 더 심하다. 프로세스 간 동기화에는 명명된 뮤텍스나 세마포어처럼 **크로스 프로세스 대기 핸들**이 필요하다. `Mutex`는 48.10절에서 다룬다.

### 뷰 접근자로 작업하기

`Read*`/`Write*` 메서드는 숫자 타입, `bool`, `char`, 그리고 값 타입 요소나 필드만 담은 배열과 구조체를 받는다. **참조 타입은 — 참조 타입을 담은 배열이나 구조체도 — 비관리 메모리에 매핑할 수 없어 금지된다.** 그래서 문자열을 쓰려면 바이트 배열로 인코딩해야 한다.

```csharp
byte[] data = Encoding.UTF8.GetBytes("This is a test");
accessor.Write(0, data.Length);
accessor.WriteArray(4, data, 0, data.Length);
```

길이를 먼저 썼다는 점에 주목한다. 나중에 몇 바이트를 읽어야 할지 알 수 있다.

```csharp
byte[] data = new byte[accessor.ReadInt32(0)];
accessor.ReadArray(4, data, 0, data.Length);
Console.WriteLine(Encoding.UTF8.GetString(data));   // This is a test
```

구조체를 읽고 쓰는 예는 이렇다.

```csharp
struct Data { public int X, Y; }
// ...
var data = new Data { X = 123, Y = 456 };
accessor.Write(0, ref data);
accessor.Read(0, out data);
Console.WriteLine(data.X + " " + data.Y);   // 123 456
```

> **⚠️ `Read`/`Write` 메서드는 놀랄 만큼 느리다**
>
> 뷰 접근자의 `Read`/`Write` 메서드는 관리 메모리와 비관리 메모리 사이를 복사하며, 호출당 오버헤드가 상당하다. 하부 비관리 메모리에 **포인터로 직접 접근**하면 훨씬 나은 성능을 얻는다.
>
> ```csharp
> unsafe
> {
>     byte* pointer = null;
>     try
>     {
>         accessor.SafeMemoryMappedViewHandle.AcquirePointer(ref pointer);
>         int* intPointer = (int*)pointer;
>         Console.WriteLine(*intPointer);   // 123
>     }
>     finally
>     {
>         if (pointer != null)
>             accessor.SafeMemoryMappedViewHandle.ReleasePointer();
>     }
> }
> ```
>
> 프로젝트에서 `unsafe` 코드를 허용해야 한다.
>
> ```xml
> <PropertyGroup>
>   <AllowUnsafeBlocks>true</AllowUnsafeBlocks>
> </PropertyGroup>
> ```
>
> `AcquirePointer`와 `ReleasePointer`는 반드시 `try`/`finally`로 짝을 맞춰야 한다. 해제하지 않으면 뷰가 영원히 고정된다. 포인터의 성능 이점은 **큰 구조체**에서 더 두드러진다. `Read`/`Write`로 관리 메모리와 비관리 메모리 사이를 복사하는 대신 원시 데이터를 직접 다룰 수 있기 때문이다. 60장에서 더 파고든다.

> **💡 언제 메모리 매핑 파일을 선택하나**
>
> - 수 GB 파일의 여기저기를 무작위로 읽는다 → **예**
> - 파일을 처음부터 끝까지 한 번 훑는다 → 아니오. `FileStream` + `SequentialScan`
> - 여러 스레드가 한 파일의 서로 다른 구간을 동시에 읽는다 → **예** (또는 `RandomAccess`)
> - 프로세스 간에 큰 데이터를 자주 주고받는다 → **예** (파이프보다 빠르다)
> - 작은 설정 파일을 읽는다 → 아니오. `File.ReadAllText`로 충분하다
> - 네트워크 드라이브의 파일이다 → 아니오. 동작이 보장되지 않거나 매우 느리다

## 40.15 비동기 I/O가 진짜 비동기인 조건 — OS 수준 겹침 I/O

이 절은 이 장에서 가장 오해가 많은 주제를 다룬다.

### 왜 비동기 파일 접근인가

- 파일 작업이 몇 초 이상 걸려도 **UI 스레드가 사용자 상호작용을 막지 않는다.**
- 수동으로 스레드를 관리할 필요가 줄어 애플리케이션의 **확장성**이 좋아진다. ASP.NET과 서버 측 애플리케이션이 특히 이득을 본다.
- **파일 접근 지연**은 하드 디스크 종류, 네트워크 업로드·다운로드 속도, 보안 소프트웨어의 실시간 검사, 파일 크기 등 여러 요인에 좌우된다.
- 스레드 대비 비동기 태스크의 오버헤드는 작다.
- 비동기 태스크는 병렬로 실행할 수 있다.

### 진짜 비동기의 조건

`FileStream` 클래스는 파일 접근 연산에 대해 가장 많은 제어권을 준다. **OS 수준에서 I/O 연산을 수행하도록 구성**하면 스레드 풀 스레드를 블로킹하지 않게 되는데, 그러려면 생성자 호출에서 다음 중 하나를 지정해야 한다.

- `useAsync: true`
- `options: FileOptions.Asynchronous`

> **⚠️ 이 플래그가 없으면 `ReadAsync`는 진짜 비동기가 아니다**
>
> 이것이 이 장의 마지막 큰 함정이다.
>
> ```csharp
> using var fs = new FileStream("data.bin", FileMode.Open);   // 플래그 없음
> await fs.ReadAsync(buffer, 0, buffer.Length);               // 진짜 비동기가 아니다
> ```
>
> 이 코드는 컴파일되고, 동작하고, `Task`를 반환한다. 하지만 내부적으로는 **동기 읽기를 스레드 풀 스레드에서 수행**한다. 즉 그 시간 동안 스레드 풀 스레드 하나가 **블로킹**된다.
>
> 결과는 이렇다. 데스크톱 앱에서는 UI 스레드가 자유로워지므로 눈에 띄는 문제가 없다. **서버에서는 다르다.** 동시 요청 1,000개가 각각 파일을 "비동기로" 읽으면 스레드 풀 스레드 1,000개가 블로킹되고, 스레드 풀은 hill-climbing 알고리즘에 따라 천천히 스레드를 주입하며(46.2절), 처리량이 붕괴한다. **비동기를 쓰는 목적이 정확히 반대로 작동한다.**
>
> 올바른 코드는 이렇다.
>
> ```csharp
> using var fs = new FileStream("data.bin", FileMode.Open, FileAccess.Read,
>                               FileShare.Read, bufferSize: 4096, useAsync: true);
> await fs.ReadAsync(buffer, 0, buffer.Length);   // 진짜 비동기
> ```

이 옵션은 `StreamReader`와 `StreamWriter` 클래스와도 함께 쓸 수 있는데, **그들에게 제공된 스트림이 `FileStream`으로 열린 것일 때에만** 그렇다. 즉 `new StreamReader(path)`처럼 경로만 넘기면 비동기 플래그를 지정할 방법이 없다. 스트림을 먼저 만들어 넘겨야 한다.

### 그 아래에서 벌어지는 일

`FileOptions.Asynchronous`가 켜지면 런타임은 OS의 비동기 I/O 메커니즘을 쓴다.

| 플랫폼 | 메커니즘 | 성격 |
|---|---|---|
| Windows | 겹침(overlapped) I/O + I/O 완료 포트(IOCP) | 커널이 완료를 통지한다. 대기 중 스레드 없음 |
| Linux | 커널·런타임 버전에 따라 `epoll`, 스레드 풀 위임, `io_uring` 계열 | 파일 I/O의 진짜 비동기 지원은 역사적으로 제한적 |
| macOS | 유사 | 유사 |

Windows의 겹침 I/O가 가장 깔끔하다. 읽기를 요청하면 커널이 즉시 반환하고, DMA가 디스크에서 데이터를 옮긴 뒤 완료 포트에 알린다. 그 사이 **어떤 스레드도 대기하지 않는다.**

> **📌 Unix 계열의 파일 I/O는 사정이 다르다**
>
> 전통적으로 Unix의 파일 디스크립터는 정규 파일에 대해 "항상 준비됨"으로 보고하기 때문에, `epoll` 같은 준비 상태 기반 메커니즘으로는 파일 I/O를 진짜 비동기로 만들 수 없었다. 그래서 런타임은 내부 스레드 풀에 위임하는 방식을 오래 써 왔다. 최근 커널의 `io_uring` 같은 완료 기반 인터페이스가 이 그림을 바꾸고 있지만, **런타임 버전과 커널 버전에 따라 실제 동작이 달라진다.**
>
> 실무적 결론은 이렇다. **`FileOptions.Asynchronous`를 켜는 것은 언제나 옳다.** 플랫폼이 진짜 비동기를 지원하면 이득을 보고, 지원하지 않으면 지금과 같다. 하지만 "Linux에서도 스레드가 절대 블로킹되지 않는다"고 단정해서는 안 된다.

### 소규모 읽기에서는 동기가 더 빠를 수 있다

비동기는 공짜가 아니다. 상태 기계 할당(47.7절), 컨텍스트 캡처(47.12절), 완료 콜백 디스패치 비용이 붙는다. 4KB 설정 파일 하나를 읽는 데 이 비용은 실제 I/O 시간보다 클 수 있고, OS 파일 캐시에 이미 올라와 있다면 더욱 그렇다.

| 상황 | 권장 |
|---|---|
| 서버에서 큰 파일 스트리밍 | `useAsync: true` + `ReadAsync` |
| 서버에서 동시 요청이 많음 | `useAsync: true` (스레드 풀 보호) |
| 네트워크 드라이브·느린 매체 | 비동기 |
| UI 스레드에서 파일 접근 | 비동기 (크기 무관) |
| 시작 시 작은 설정 파일 1회 로드 | 동기가 단순하고 빠를 수 있다 |
| 콘솔 도구의 단발성 처리 | 동기로 충분 |

> **💡 `ReadAsync`가 완료된 `Task`를 반환하는 경우**
>
> `FileStream`의 버퍼에 이미 데이터가 있으면 `ReadAsync`는 동기적으로 완료된 `ValueTask`를 반환한다. 이 경우 `await`는 상태 기계를 진행시키지 않고 그대로 이어 간다(47.9절의 완료 경로 최적화). 즉 **비동기 API를 써도 실제 비용은 상황에 따라 크게 달라진다.** 마이크로벤치마크에서 "비동기가 더 빠르다/느리다"라는 결론이 잘 뒤집히는 이유다.

### 비동기 읽기·쓰기 예제

원천 도서의 예제를 그대로 옮기면 이렇다. OS 수준에서 동작하도록 구성한 버전이다.

```csharp
public async Task<string> ReadTextFromFileAsync(string path)
{
    StringBuilder sb = new StringBuilder();
    byte[] buffer = new byte[0x1000];
    int n;

    using var fileStream = new FileStream(
        path, FileMode.Open, FileAccess.Read, FileShare.Read,
        bufferSize: 4096, useAsync: true);

    while ((n = await fileStream.ReadAsync(buffer, 0, buffer.Length)) != 0)
        sb.Append(Encoding.Unicode.GetString(buffer, 0, n));

    return sb.ToString();
}
```

버퍼 크기 4,096을 고른 이유는 40.4절에서 설명했다 — 2의 거듭제곱이면서 메모리 페이지 크기다.

> **⚠️ 이 읽기 루프에는 인코딩 버그가 숨어 있다**
>
> 위 코드는 원천 도서의 구조를 따랐지만, 블록 경계에서 멀티바이트 문자가 잘리면 깨진다. UTF-16에서는 4,096바이트가 짝수이므로 대부분 괜찮지만 **서로게이트 페어**가 경계에 걸리면 문제가 되고, UTF-8이라면 훨씬 자주 깨진다.
>
> 정답은 **바이트를 직접 디코딩하지 않는 것**이다. 텍스트를 읽을 때는 `StreamReader`에 맡긴다. `StreamReader`는 `Decoder`의 상태를 유지해 블록 경계를 올바르게 처리한다(35.9절).
>
> ```csharp
> using var fs = new FileStream(path, FileMode.Open, FileAccess.Read,
>                               FileShare.Read, 4096, useAsync: true);
> using var reader = new StreamReader(fs, Encoding.Unicode);
> string text = await reader.ReadToEndAsync();
> ```
>
> 바이트를 직접 디코딩해야 한다면 `Encoding.GetDecoder()`로 상태를 유지하는 `Decoder`를 얻어 써야 한다.

> **💡 하드웨어가 나쁘면 소프트웨어로 못 이긴다**
>
> I/O 성능을 소프트웨어로 최적화하기 전에, 수행할 I/O 유형에 하드웨어가 적합한지부터 확인해야 한다. 네트워크 카드 속도, SSD 사용 여부, CPU 개수, 사용 중인 RAM 양이 먼저다. 대상 컴퓨터에서 어떤 다른 프로세스가 실행되는지도 고려해야 한다 — **실시간 검사를 수행하는 보안 소프트웨어**는 애플리케이션 느려짐의 원인으로 자주 간과된다. 이 경우 애플리케이션을 백신 예외에 추가하면 실시간 검사가 더는 소프트웨어를 늦추지 않는다. 운영 중요 시간대에 네트워크 백업이 도는 것도 마찬가지다.
>
> 아무리 효율적인 프로그램이라도 백업 서버 위에서 돌면 성능이 심각하게 영향받는다. 백업 일정을 비핵심 시간대로 옮기거나, 성능이 더 나은 서버로 옮기거나, 네트워크 병목을 찾아 해소해야 한다. 67장의 원칙이 여기서도 그대로다 — **측정하고 나서 고쳐라.**

## 40.16 I/O 예외 처리와 재시도 정책

I/O 연산은 실패한다. 네트워크가 끊기고, 디스크가 차고, 다른 프로세스가 파일을 잡고 있고, 사용자가 USB를 뽑는다. **I/O 코드에서 예외는 예외적인 사건이 아니라 정상적인 실행 경로의 일부다.**

### I/O 예외 계층

I/O 예외의 기반은 `IOException`이며, 서로 다른 I/O 예외를 구분해 기록하면 문제 해결이 빨라진다.

| 예외 | 언제 던져지는가 | 기반 |
|---|---|---|
| `IOException` | 일반 I/O 오류. 파일 잠김, 디스크 가득 참 등 | `SystemException` |
| `FileNotFoundException` | 파일을 찾을 수 없다 | `IOException` |
| `DirectoryNotFoundException` | 경로의 일부 디렉터리가 없다 | `IOException` |
| `EndOfStreamException` | 스트림 끝을 넘어 읽으려 했다 | `IOException` |
| `PathTooLongException` | 경로가 시스템 최대 길이를 넘는다 (40.12절) | `IOException` |
| `DriveNotFoundException` | 사용할 수 없는 드라이브에 접근했다 | `IOException` |
| `FileLoadException` | 관리 어셈블리를 찾았으나 로드할 수 없다 | `IOException` |
| `UnauthorizedAccessException` | OS가 접근을 거부했다 (40.13절) | `SystemException` |
| `ArgumentException` | 경로 문자열 자체가 잘못됐다 | `SystemException` |
| `NotSupportedException` | 스트림이 그 연산을 지원하지 않는다 | `SystemException` |
| `ObjectDisposedException` | 이미 해제된 스트림을 썼다 | `InvalidOperationException` |

> **⚠️ `UnauthorizedAccessException`은 `IOException`이 아니다**
>
> 계층 표에서 가장 중요한 줄이다. `catch (IOException)`만 쓴 코드는 **권한 거부를 잡지 못한다.** 파일 작업을 감싸는 `catch`는 `IOException`과 `UnauthorizedAccessException`을 **둘 다** 다뤄야 한다.
>
> ```csharp
> try
> {
>     File.Delete(path);
> }
> catch (Exception ex) when (ex is IOException or UnauthorizedAccessException)
> {
>     logger.LogWarning(ex, "삭제 실패: {Path}", path);
> }
> ```
>
> `NotSupportedException`과 `ObjectDisposedException`도 `IOException`이 아니다. 전자는 프로그래밍 오류이므로 잡지 않는 것이 맞고, 후자는 대개 수명 관리 버그다.

### 예외 처리 원칙

애플리케이션이 인지해야 할 예외는 두 범주다.

- **예상되는 예외** — 프로그램이 복구할 수 있는 예외
- **예상치 못한 예외** — 프로그램이 복구할 수 없는 예외

예상되는 예외는 조용히 처리해야 한다. 무엇이 왜 실패할 수 있는지 알고 있으므로, 애초에 그런 예외가 발생하지 않도록 방어 코드를 둘 수 있다. 예외가 계층을 타고 올라가게 두면 애플리케이션 성능이 떨어지고, 성능 저하는 사용자 경험을 해친다. 그래서 **예외는 발생한 지점에서 처리하는 것이 좋은 관행**이다. `try`/`catch`로 오류를 잡을 때는 `catch` 블록을 여러 개 두되, `catch` 블록을 구성할 예외는 현재 메서드가 던질 수 있는 것들뿐이어야 한다. **가장 구체적인 예외가 맨 위**에 오고 가장 덜 구체적인 것이 맨 아래에 오도록 순서를 잡으면 코드가 읽기 좋고 디버깅도 쉬워진다.

특정 조건이 있을 때만 예외를 처리하려면 **예외 필터**를 쓴다(32.7절). 필터가 `true`를 반환하면 예외가 처리되고, `false`를 반환하면 예외 처리기 탐색이 계속된다. **잡았다가 다시 던지는 것보다 필터가 낫다** — 필터는 스택을 훼손하지 않으므로, 나중에 스택을 덤프하면 마지막으로 다시 던진 위치가 아니라 예외가 원래 발생한 지점을 볼 수 있다.

예상치 못한 예외는 프로그램의 예측 가능성에 심각한 악영향을 줄 수 있으므로 던져져야 한다. 이 경우 **예외를 기록하고 종료해 데이터 무결성을 보호**한다. `System.Exception`을 잡는 것이 나쁜 생각인 이유가 이것이다 — 모든 예외를 삼켜 버린다. 메서드는 자신이 발생할 것으로 예상하는 예외만 잡고, 예상치 못한 모든 예외는 애플리케이션 최상위에서 기록하고 종료하는 방식으로 처리한다. 최상위 처리기까지 전파된 예외에서는 `Exception.GetBaseException()`으로 이후 예외들을 연쇄적으로 일으킨 근본 예외를 꺼낼 수 있다.

### TOCTOU — `File.Exists`는 답이 아니다

가장 흔한 오해부터 정리한다.

```csharp
// 잘못된 코드
if (File.Exists(path))
{
    using var fs = File.OpenRead(path);   // 여기서 여전히 예외가 날 수 있다
    // ...
}
```

`File.Exists`가 `true`를 반환한 순간과 `OpenRead`가 실행되는 순간 사이에 다른 프로세스가 파일을 지우거나, 이름을 바꾸거나, 배타적으로 잠글 수 있다. 이 경쟁을 **TOCTOU(Time-of-check to time-of-use)** 라고 부른다.

> **⚠️ 검사-후-사용은 파일 시스템에서 원리적으로 불가능하다**
>
> 파일 시스템은 공유 자원이고, 검사와 사용을 원자적으로 묶는 API가 없다. 그러므로 `File.Exists`로 예외를 **예방**할 수 없다. `File.Exists`가 유용한 경우는 딱 둘이다.
>
> 1. 사용자에게 **미리 안내**하기 위해 (덮어쓰기 확인 대화 상자 같은 것)
> 2. 비용이 큰 작업을 시작하기 전 **빠른 조기 탈출**
>
> 두 경우 모두 **그다음에 오는 예외 처리를 대체하지 않는다.** 정답은 검사를 생략하거나 남겨 두되, **예외 처리를 반드시 함께 두는 것**이다.
>
> ```csharp
> try
> {
>     using var fs = File.OpenRead(path);
>     // ...
> }
> catch (FileNotFoundException)      { /* 없어졌다 */ }
> catch (DirectoryNotFoundException) { /* 디렉터리째 사라졌다 */ }
> catch (IOException)                { /* 잠겨 있다 */ }
> catch (UnauthorizedAccessException){ /* 권한이 없다 */ }
> ```
>
> 원자성이 정말 필요한 곳에는 **OS가 원자적으로 보장하는 연산**을 쓴다. `FileMode.CreateNew`는 "없으면 만들고 있으면 실패"를 원자적으로 수행하므로 잠금 파일 관용구에 쓸 수 있다. `File.Replace`도 원자적 교체에 가깝다.

### 파일 잠금 경합과 재시도

바이러스 검사, 백업 소프트웨어, 인덱서, 사용자가 열어 둔 편집기가 파일을 잠깐씩 잡는다. 이런 실패는 **일시적(transient)** 이며 잠시 후 재시도하면 성공한다. 권한 부족이나 경로 오류는 반대로 재시도해 봐야 소용없다.

| 예외 | 재시도 가치 | 이유 |
|---|---|---|
| `IOException` (파일 사용 중) | **높다** | 검사기·백업이 곧 놓아 준다 |
| `IOException` (디스크 가득 참) | 낮다 | 사람이 개입해야 한다 |
| `FileNotFoundException` | 낮다 | 파일이 나타날 이유가 없다 |
| `DirectoryNotFoundException` | 낮다 | 위와 같다 |
| `UnauthorizedAccessException` | **없다** | 권한은 저절로 생기지 않는다 |
| `PathTooLongException` | **없다** | 결정론적 실패 |
| `DriveNotFoundException` | 상황에 따라 | 네트워크 드라이브면 재연결될 수 있다 |

지수 백오프(exponential backoff)를 적용한 재시도 헬퍼는 이렇게 생겼다.

```csharp
static async Task<T> RetryIoAsync<T>(
    Func<Task<T>> action,
    int maxAttempts = 5,
    int baseDelayMs = 50,
    CancellationToken ct = default)
{
    var rng = Random.Shared;

    for (int attempt = 1; ; attempt++)
    {
        try
        {
            return await action();
        }
        catch (IOException) when (attempt < maxAttempts)
        {
            // 50ms, 100ms, 200ms, 400ms ... 에 지터를 더한다
            int delay = baseDelayMs * (1 << (attempt - 1));
            delay += rng.Next(delay / 2);
            await Task.Delay(delay, ct);
        }
    }
}
```

핵심 설계 결정 네 가지를 짚는다.

1. **`when (attempt < maxAttempts)` 필터를 쓴다.** 마지막 시도의 예외는 잡히지 않고 그대로 호출자에게 전파된다. 잡았다가 다시 던지지 않으므로 스택 트레이스가 온전하다(32.5절, 32.7절).
2. **`IOException`만 재시도한다.** `UnauthorizedAccessException`은 재시도 대상이 아니므로 필터에 넣지 않는다.
3. **지수 백오프.** 간격을 두 배씩 늘려 경합 상대에게 시간을 준다.
4. **지터(jitter).** 무작위 편차를 더해 여러 워커가 동시에 재시도하는 "천둥 무리(thundering herd)"를 막는다.

> **⚠️ 재시도가 상황을 악화시키는 경우**
>
> 재시도는 만능이 아니다. 세 가지를 조심한다.
>
> - **멱등하지 않은 연산.** "파일에 한 줄 추가"를 재시도하면 두 번 추가될 수 있다. 부분적으로 성공한 뒤 실패했는지 알 수 없다면 재시도 전에 상태를 확인해야 한다.
> - **디스크 가득 참.** 재시도해 봐야 계속 실패하며, 그동안 다른 작업의 자원을 잡아먹는다.
> - **무한 재시도.** 반드시 상한을 둔다. 상한 없는 재시도는 장애를 감추기만 하고 결국 더 크게 터진다.

### 로깅

예외를 기록할 수 있는 위치는 크게 셋이다. **애플리케이션 로그 파일**(텍스트·JSON·XML), **이벤트 뷰어**(예상되는 예외는 애플리케이션이 지정한 이벤트 로그에, 응답 없음 같은 예상치 못한 예외는 시스템이 Windows 애플리케이션 로그나 시스템 로그에 기록한다), **데이터베이스 테이블**이다. 어떤 메커니즘을 고르든 로그가 **잘 정리돼 있고 제공되는 데이터가 의미 있어야** 한다. 읽기 어렵고 잡음이 많은 로그는 없느니만 못하다.

I/O 예외 로그에 반드시 포함해야 할 항목은 다음과 같다.

| 항목 | 이유 |
|---|---|
| 전체 경로 | 상대 경로만 남기면 나중에 재현이 불가능하다 |
| 예외 타입과 HResult | `IOException`은 원인이 너무 다양하다 |
| 시도 횟수와 경과 시간 | 일시적 실패인지 영구 실패인지 구분한다 |
| 실행 계정 | 권한 문제 진단의 출발점이다 |
| 파일 크기·가용 공간 | 디스크 가득 참을 즉시 판정한다 |

> **💡 리소스 누수는 장애를 진단 불가능하게 만든다**
>
> 관리·비관리 리소스는 올바르게 해제해야 한다. **특히 애플리케이션이 크래시할 때** 그렇다. 애플리케이션이 크래시하면서 리소스를 잠근 채로 남기거나 메모리에 살려 둔 사례는 기술 지원 현장에서 흔하다. 나쁜 사용자 경험으로 이어지고, 파일·디렉터리·기타 리소스에 접근할 수 없게 되며, 심지어 애플리케이션 자체가 시작되지 않게 만든다. 이럴 때 남는 선택지는 작업 관리자로 애플리케이션을 죽이거나 컴퓨터를 재시작하는 것뿐이다.
>
> 33장의 규칙 그대로다. `using`을 쓰고, 파이널라이저에 의존하지 말고, `SafeHandle`로 감싼다(33.7절).

## 이 장의 요약

- **스트림 아키텍처는 세 계층이다.** 백킹 스토어(`FileStream`, `MemoryStream`, `PipeStream`, `NetworkStream`)가 실제 데이터를 대고, 데코레이터(`GZipStream`, `CryptoStream`, `BufferedStream`)가 흐르는 바이트를 변형하고, 어댑터(`StreamReader`, `BinaryWriter`, `XmlReader`)가 바이트를 사람이 쓰는 타입으로 바꾼다. 데코레이터는 몇 겹이든 쌓이고, 어댑터는 항상 체인의 끝이다.
- **`Read`는 요청한 만큼 읽어 주지 않는다.** 끝을 확신할 수 있는 것은 반환값 0뿐이다. 루프를 쓰거나 .NET 7의 `ReadExactly`/`ReadAtLeast`를 쓴다. 로컬 파일에서는 재현되지 않고 네트워크와 압축 스트림에서 터지는 종류의 버그다.
- **`FileStream`의 세 열거형 조합이 동작을 결정한다.** `FileMode`는 파일이 있고 없을 때의 행동을, `FileAccess`는 내 권한을, `FileShare`는 남에게 허용할 것을 정한다. 남이 쓰고 있는 로그를 기본 공유 모드로 열면 그 프로세스가 죽는다.
- **압축 스트림은 반드시 해제해야 한다.** `Flush`로는 부족하다. 마지막 압축 블록은 `Dispose` 시점에 마무리되며, 빠뜨리면 파일이 손상된 채 남는다.
- **아카이브 엔트리 이름은 공격자가 통제하는 문자열이다.** ZIP과 TAR 모두 경로 탈출(Zip Slip)이 가능하다. `Path.GetFullPath`로 정규화한 뒤 기준 디렉터리 접두사를 검사하고, TAR에서는 링크 엔트리를 거부한다.
- **`Path.Combine`은 절대 경로를 만나면 앞을 버린다.** 신뢰할 수 없는 조각을 결합할 때는 `Path.Join`을 쓰고, 그다음 반드시 정규화와 접두사 검사를 한다.
- **`FileSystemWatcher`는 유실되고, 중복되고, 이르다.** 버퍼가 넘치면 이벤트가 영구히 사라진다. 힌트로만 쓰고 주기적 스캔을 병행한다.
- **`FileOptions.Asynchronous`(또는 `useAsync: true`) 없이는 `ReadAsync`가 진짜 비동기가 아니다.** 스레드 풀 스레드를 블로킹할 뿐이며, 서버에서는 비동기를 쓰는 목적이 정확히 반대로 작동한다.
- **메모리 매핑 파일은 임의 접근에서 `FileStream`보다 대략 10배 빠르고, 순차 접근에서는 대략 10배 느리다.** 접근 패턴이 선택을 결정한다.
- **`File.Exists`로는 예외를 예방할 수 없다(TOCTOU).** 검사와 사용 사이의 경합은 원리적으로 막을 수 없으므로, 예외 처리가 정답이다. 일시적 `IOException`에는 지터를 곁들인 지수 백오프 재시도를, `UnauthorizedAccessException`에는 재시도 대신 사용자 안내를 적용한다.

## 연습 문제

1. 1MB짜리 파일을 만들고, `Read`를 딱 한 번만 호출하는 코드와 루프로 읽는 코드를 각각 작성하라. 그다음 두 코드를 `GZipStream`으로 감싼 스트림에 적용해 실행하고, **어느 쪽에서 처음으로 결과가 달라지는지** 확인하라. 이어서 `ReadExactly`로 바꿔 예외 메시지를 확인하라.

2. `FileMode` 6개 값과 `FileAccess` 3개 값의 조합 18가지에 대해, 파일이 있을 때와 없을 때 각각 무슨 일이 일어나는지 실행해서 표를 완성하라. 예외가 나는 조합에는 예외 타입을 적어라. 40.4절의 표와 대조해 빠진 것이 있는지 확인하라.

3. 한 프로세스에서 `FileShare.Read`로 파일을 열어 둔 채, 다른 프로세스에서 같은 파일을 `FileAccess.Write`로 열어 보라. 어떤 예외가 나는가. 첫 번째 프로세스의 `FileShare`를 `ReadWrite`로 바꾸면 어떻게 되는가.

4. `GZipStream`으로 파일을 압축하되 `Dispose`를 호출하지 않고 프로세스를 종료시켜라. 그 파일을 압축 해제할 때 나오는 예외를 기록하라. 그다음 `Flush()`만 호출한 버전으로 같은 실험을 반복해, **`Flush`로는 해결되지 않는다**는 것을 직접 확인하라.

5. 엔트리 이름이 `../../pwned.txt`인 ZIP 파일을 `ZipArchive`로 직접 만들어라. 그것을 (a) `ZipFile.ExtractToDirectory`로, (b) `entry.ExtractToFile`을 직접 부르는 루프로 각각 풀어 보고 결과를 비교하라. 그다음 40.8절의 `SafeExtract`를 적용해 차단되는지 확인하라.

6. `Path.Combine`과 `Path.Join`에 `("C:\\base", "C:\\Windows")`와 `("/base", "/etc")`를 넘겨 결과를 출력하라. 이어서 `Path.GetFullPath(Path.Combine(root, "../../etc/passwd"))`의 결과를 출력하고, 접두사 검사가 왜 필요한지 설명할 수 있을 만큼 결과를 모아라.

7. 같은 파일을 `useAsync: true`와 `useAsync` 없이 각각 열어 `ReadAsync`로 100회씩 읽는 벤치마크를 작성하라. 파일 크기를 4KB, 1MB, 100MB로 바꿔 가며 측정하고, **어느 크기에서 차이가 유의미해지는지** 찾아라. 그다음 동시 요청 수를 늘려 가며 같은 실험을 반복해 스레드 풀 고갈이 관측되는지 확인하라.

8. `File.Exists` 검사 뒤에 `File.OpenRead`를 부르는 코드를 두 스레드로 동시에 실행하면서, 한쪽에서는 계속 파일을 지우고 다시 만들어라. `FileNotFoundException`이 얼마나 자주 발생하는지 세어 TOCTOU가 이론이 아님을 확인하라. 그다음 40.16절의 재시도 헬퍼를 적용해 실패율이 얼마나 떨어지는지 측정하라.
