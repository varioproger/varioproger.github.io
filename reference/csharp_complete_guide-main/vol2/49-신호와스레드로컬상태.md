## 49.1 이벤트 대기 핸들로 신호 보내기

### 잠금과 신호는 목적이 다르다

48장의 도구들은 전부 **배제(exclusion)** 를 위한 것이었다. `lock`은 임계 구역에 한 스레드만 들여보내고, 세마포어는 정원을 제한하고, 읽기/쓰기 잠금은 읽기끼리만 겹치게 한다. 공통점은 이렇다 — **막는 것이 목적이고, 통과는 부수 효과다.**

신호(signaling)는 방향이 반대다. **스레드 A가 스레드 B에게 "그 일이 끝났다", "데이터가 준비됐다", "이제 진행해도 된다"를 알리는 것**이 목적이다. 막는 것은 부수 효과다 — 알림이 오기 전까지 기다려야 하니까 막힐 뿐이다.

| 축 | 잠금(locking) | 신호(signaling) |
|---|---|---|
| 목적 | 공유 상태를 보호한다 | 사건의 발생을 알린다 |
| 질문 | "지금 들어가도 되나" | "그 일이 일어났나" |
| 짝 | 획득한 스레드가 해제한다 | **아무 스레드나** 신호할 수 있다 |
| 성공의 모습 | 통과했고 곧 나올 것이다 | 통과했고 다시 오지 않을 수도 있다 |
| 대표 타입 | `lock`, `Mutex`, `SemaphoreSlim` | `AutoResetEvent`, `ManualResetEvent(Slim)`, `CountdownEvent`, `Barrier` |

이 구분이 실무에서 중요한 이유는 **같은 타입을 두 목적 모두에 쓸 수 있기 때문**이다. `AutoResetEvent`를 초기 상태 `true`로 만들면 그것은 사실상 배타적 잠금이 된다(48.11절의 "최대 카운트 1인 세마포어" 논의와 같은 이야기다). 반대로 `SemaphoreSlim(0)`을 만들어 두고 `Release`로 신호를 보내는 관용구도 있다. 도구가 겹치는 것은 사실이지만, **코드를 읽는 사람에게 의도를 전달하는 이름은 하나뿐**이다. 신호가 목적이면 신호 타입을 써라.

> **📌 여기서 말하는 "이벤트"는 C#의 `event`가 아니다**
>
> `EventWaitHandle`·`AutoResetEvent`·`ManualResetEvent`의 "이벤트"는 **Windows 커널이 관리하는 불리언 변수**를 가리키는 운영체제 용어다. 27장에서 다룬 C#의 `event` 키워드(델리게이트 기반 알림)와는 아무 관계가 없다. 이름이 같아 혼동이 잦으니, 이 장에서 "이벤트"라고 쓰면 언제나 커널의 신호 객체를 뜻한다고 읽어라.

### 대기 핸들 계층

`System.Threading` 네임스페이스는 커널 객체 핸들을 감싸는 추상 기반 클래스 `WaitHandle`을 제공한다. 계층은 이렇다.

```text
                       ┌───────────────────────────────┐
                       │  WaitHandle  (abstract)       │
                       │  - SafeWaitHandle 필드        │
                       │  - WaitOne / WaitAll /        │
                       │    WaitAny / SignalAndWait    │
                       └───────────────┬───────────────┘
             ┌─────────────────────────┼─────────────────────────┐
             ▼                         ▼                         ▼
   ┌──────────────────┐        ┌──────────────┐        ┌──────────────┐
   │ EventWaitHandle  │        │  Semaphore   │        │    Mutex     │
   │  Set() / Reset() │        │  Release(n)  │        │ReleaseMutex()│
   └────────┬─────────┘        └──────────────┘        └──────────────┘
            │                    (48.11절)                (48.10절)
   ┌────────┴────────┐
   ▼                 ▼
┌───────────────┐ ┌───────────────────┐
│AutoResetEvent │ │ ManualResetEvent  │
│  (sealed)     │ │     (sealed)      │
│  턴스타일      │ │       문          │
└───────────────┘ └───────────────────┘

   ※ WaitHandle을 상속하지 않는 것들 (관리 코드 구현, 하이브리드)
      ManualResetEventSlim  →  WaitHandle 속성으로 노출
      CountdownEvent        →  WaitHandle 속성으로 노출
      SemaphoreSlim         →  AvailableWaitHandle 속성으로 노출
      Barrier               →  노출하지 않는다
```

`WaitHandle` 내부에는 Win32 커널 객체 핸들을 담는 `SafeWaitHandle` 필드가 있다. 이 필드는 구체 파생 클래스가 생성될 때 초기화된다. `AutoResetEvent`와 `ManualResetEvent`의 생성자는 Win32 `CreateEvent`를, `Semaphore`는 `CreateSemaphore`를, `Mutex`는 `CreateMutex`를 각각 호출하고 그 핸들을 여기에 저장한다.

`WaitHandle`이 노출하는 핵심 멤버는 이렇다.

```csharp
public abstract class WaitHandle : MarshalByRefObject, IDisposable
{
    // 내부적으로 Win32 WaitForSingleObjectEx 를 호출한다
    public virtual bool WaitOne();
    public virtual bool WaitOne(int millisecondsTimeout);
    public virtual bool WaitOne(TimeSpan timeout);
    public virtual bool WaitOne(int millisecondsTimeout, bool exitContext);
    public virtual bool WaitOne(TimeSpan timeout, bool exitContext);

    // 내부적으로 Win32 WaitForMultipleObjectsEx (bWaitAll = TRUE) 를 호출한다
    public static bool WaitAll(WaitHandle[] waitHandles);
    public static bool WaitAll(WaitHandle[] waitHandles, int millisecondsTimeout);
    public static bool WaitAll(WaitHandle[] waitHandles, TimeSpan timeout);

    // 내부적으로 Win32 WaitForMultipleObjectsEx (bWaitAll = FALSE) 를 호출한다
    public static int WaitAny(WaitHandle[] waitHandles);
    public static int WaitAny(WaitHandle[] waitHandles, int millisecondsTimeout);
    public static int WaitAny(WaitHandle[] waitHandles, TimeSpan timeout);

    public static bool SignalAndWait(WaitHandle toSignal, WaitHandle toWaitOn);

    public const int WaitTimeout = 258;   // 타임아웃 시 WaitAny 가 돌려주는 값

    public void Dispose();                // 내부적으로 Win32 CloseHandle
    public virtual void Close();
}
```

**커널 객체에 대한 모든 메서드 호출은 전체 메모리 펜스(full memory fence)다.** 48.2절과 48.3절에서 본 재배치·가시성 논의가 여기서 그대로 적용된다. 즉 신호 구조를 써서 "한 번에 한 스레드만 변수를 읽고 쓴다"를 보장했다면, 그 변수에 별도의 `lock`이나 `volatile`이 필요 없다.

```csharp
var signal = new ManualResetEvent(false);
int x = 0;

new Thread(() => { x++; signal.Set(); }).Start();

signal.WaitOne();
Console.WriteLine(x);      // 1 — 언제나. x 를 잠글 필요가 없다
```

`Set`과 `WaitOne`이 각각 펜스를 세우므로 `x++` 의 결과는 반드시 보인다.

### 커널 객체는 마이크로초 단위로 비싸다

`WaitHandle` 파생 타입은 전부 **커널 모드 구조(kernel-mode construct)** 다. 메서드를 하나 부를 때마다 스레드는 관리 코드 → 네이티브 사용자 모드 코드 → 네이티브 커널 모드 코드를 거쳐 다시 돌아온다. 이 전이가 비싸다.

원천 자료에 실린 측정이 그 규모를 보여 준다. `x++`를 1,000만 번 실행하는 데 걸린 시간을 네 가지 방식으로 잰 것이다.

| 방식 | 소요 시간 | 배수 |
|---|---|---|
| `x++` 만 | 8 ms | 기준 |
| 앞뒤로 빈 메서드 호출 추가 | 69 ms | 약 9배 |
| `SpinLock` (사용자 모드 구조) 획득·해제 | 164 ms | 약 21배 |
| `AutoResetEvent` 기반 잠금 획득·해제 | 8,854 ms | **약 1,107배** |

원천 저자의 결론은 단호하다. **동기화를 피할 수 있으면 피하고, 필요하면 사용자 모드 구조를 쓰고, 커널 모드 구조는 언제나 피하려고 노력하라.**

다른 원천의 표현으로는 이렇다. `AutoResetEvent`나 `ManualResetEvent`에 신호를 보내거나 대기하는 데 **약 1마이크로초**가 든다(막히지 않는 경우 기준). 반면 `ManualResetEventSlim`과 `CountdownEvent`는 짧은 대기 시나리오에서 **최대 50배까지 빠를 수 있다** — OS에 의존하지 않고 스핀 구조를 적절히 쓰기 때문이다.

> **⚠️ "1,107배 느리다"를 "쓰면 안 된다"로 읽지 마라**
>
> 위 측정은 **1,000만 번 반복**한 결과다. 신호를 초당 몇 번 보내는 코드라면 마이크로초 단위 비용은 아무 의미가 없다. 원천 자료도 "대부분의 시나리오에서 신호 클래스 자체의 오버헤드는 병목이 되지 않으므로 고려 대상이 아닌 경우가 많다"고 덧붙인다.
>
> 문제가 되는 것은 **신호를 잠금 대신 쓰는 경우**다. 뜨거운 루프 안에서 `AutoResetEvent.WaitOne`/`Set` 쌍으로 상호 배제를 구현했다면 그 코드는 `lock`보다 세 자릿수 느리다. 목적이 배제라면 배제 도구를 써라.

그러면 커널 모드 구조를 쓰는 이유는 무엇인가. 원천 자료가 정리한 장점은 다섯 가지다.

| 장점 | 설명 |
|---|---|
| 진짜로 막는다 | 경합을 감지하면 Windows가 스레드를 블로킹한다. CPU를 스핀으로 낭비하지 않는다 |
| 네이티브 ↔ 관리 동기화 | 네이티브 스레드와 관리 스레드를 서로 동기화할 수 있다 |
| 프로세스 경계를 넘는다 | 같은 머신의 서로 다른 프로세스에서 도는 스레드를 동기화할 수 있다(49.4절) |
| 보안 적용 가능 | 커널 객체에 보안을 걸어 권한 없는 계정의 접근을 막을 수 있다 |
| 집합 대기 | 여러 구조가 **전부** 신호될 때까지, 또는 **하나라도** 신호될 때까지 막을 수 있다(49.5절) |

여기에 타임아웃 지정이 더해진다. 원하는 시간 안에 자원을 얻지 못하면 스레드가 깨어나 다른 일을 할 수 있다.

### `WaitOne`의 반환값·타임아웃·`exitContext`

`WaitOne`은 **불리언을 반환한다.** `true`면 대기 핸들이 신호되어 통과한 것이고, `false`면 타임아웃으로 끝난 것이다.

```csharp
var wh = new AutoResetEvent(false);

if (wh.WaitOne(TimeSpan.FromSeconds(5)))
    Console.WriteLine("신호를 받았다");
else
    Console.WriteLine("5초 안에 신호가 오지 않았다");
```

타임아웃 인자가 없는 오버로드는 사실상 `Timeout.Infinite`(-1)를 넘긴 것과 같으므로 **언제나 `true`만 반환한다.** 원천 저자는 이 오버로드가 애초에 `void`를 반환하도록 설계됐어야 한다고 말한다. 반환값을 검사할 필요가 없다.

타임아웃 `0`을 넘기면 **막히지 않고 상태만 확인**할 수 있다.

```csharp
bool isOpen = wh.WaitOne(0);       // 즉시 반환. 열려 있으면 true
```

> **⚠️ `WaitOne(0)`은 `AutoResetEvent`를 소비한다**
>
> `AutoResetEvent`가 열려 있는 상태에서 `WaitOne(0)`을 부르면 `true`를 돌려받는 **동시에 그 이벤트가 닫힌다.** "상태만 살짝 보려던" 코드가 신호를 먹어 버리는 것이다. 다른 스레드가 그 신호를 기다리고 있었다면 그 스레드는 영원히 깨어나지 않는다.
>
> `ManualResetEvent`에는 이 문제가 없다(통과해도 열린 채로 남는다). `AutoResetEvent`의 상태를 부작용 없이 알아낼 방법은 없다고 보는 편이 안전하다. 상태를 검사해야 한다는 발상 자체가 대개 설계 오류다.

`exitContext` 매개변수를 가진 오버로드도 있다.

```csharp
public virtual bool WaitOne(int millisecondsTimeout, bool exitContext);
public virtual bool WaitOne(TimeSpan timeout, bool exitContext);
```

`true`를 넘기면 **대기하기 전에 현재 동기화 도메인(synchronization domain)을 빠져나갔다가 대기가 끝난 뒤 다시 들어간다.** 여기서 말하는 동기화 도메인은 `ContextBoundObject`와 `[Synchronization]` 특성으로 만드는 .NET Framework의 리모팅 컨텍스트 기능이다. 이 기능을 쓰지 않는 코드에서 `exitContext`는 아무 의미가 없다.

> **⚠️ `exitContext`는 .NET Framework의 유물이다**
>
> `ContextBoundObject` 기반 동기화 도메인은 **.NET Framework 전용 기능**이며 .NET Core 이후의 런타임에는 존재하지 않는다. 현대 .NET에서 `exitContext: true`를 넘겨도 아무 일도 일어나지 않는다.
>
> 이름 때문에 "동기화 컨텍스트(`SynchronizationContext`)를 빠져나간다"거나 "실행 컨텍스트(`ExecutionContext`)를 리셋한다"로 오해하는 코드를 자주 본다. 둘 다 아니다. `SynchronizationContext`와 `ExecutionContext`는 46.7절과 47.12절의 주제이고 `exitContext`와는 무관하다. **새 코드에서는 이 매개변수를 가진 오버로드를 쓰지 마라.**

### 대기 핸들의 폐기

`WaitHandle`은 `IDisposable`이다. `Dispose`(또는 `Close`)는 내부적으로 Win32 `CloseHandle`을 호출해 커널 객체 핸들을 닫는다.

그런데 여기에는 다른 `IDisposable`과 다른 판단이 필요하다. **다른 스레드가 그 핸들을 아직 쓰고 있는지 확실히 알아야만 안전하게 폐기할 수 있기 때문**이다. 잘못 폐기하면 대기 중인 스레드가 `ObjectDisposedException`을 맞는다.

원천 저자 두 사람의 조언은 미묘하게 다르다. Richter는 **직접 `Dispose`하지 말라**고 한다 — GC가 "이제 아무 스레드도 이 객체를 쓰지 않는다"를 알아서 판단해 주므로, 어떤 의미에서 GC가 스레드 동기화를 대신 해 주는 셈이다. Albahari는 `Close`로 OS 자원을 즉시 놓아도 되고 참조를 전부 버려 GC에 맡겨도 된다고 하면서, **파이널라이저에 기대는 것이 (논쟁의 여지는 있지만) 허용되는 몇 안 되는 시나리오** 중 하나라고 덧붙인다 — 대기 핸들의 OS 부담이 가볍기 때문이다.

두 조언의 실질적 결론은 같다. **대기 핸들은 파이널라이저가 정리하게 두어도 되는 드문 예외다.** 프로세스가 종료되면 대기 핸들은 자동으로 해제된다. 다만 대기 핸들을 **수천 개 단위로 만들고 버리는** 코드라면 이야기가 다르다 — 그때는 핸들 고갈이 실제 문제가 되므로 명시적으로 폐기해야 하고, 애초에 그런 설계를 하지 말아야 한다.

> **💡 `using` 하나로 끝나는 범위가 아니면 폐기 계획을 세우지 마라**
>
> 실무 규칙은 간단하다. 대기 핸들의 수명이 명확히 한 메서드 안에 갇혀 있고 다른 스레드가 그 이후 접근할 일이 없으면 `using`을 쓴다. 그렇지 않으면(필드에 담아 여러 스레드가 오래 공유하면) **폐기하지 않고 GC에 맡긴다.** 중간은 없다. "적당한 시점에 `Dispose`" 는 경합의 다른 이름이다.

### 이 장에서 다룰 신호 구조 지도

| 구조 | 성격 | 통과시키는 대상 | 프로세스 간 | 취소 토큰 | 절 |
|---|---|---|---|---|---|
| `AutoResetEvent` | 커널 | 대기자 **한 명** | 이름 있으면 가능(Windows) | 없음 | 49.2 |
| `ManualResetEvent` | 커널 | `Reset`까지 **전부** | 이름 있으면 가능(Windows) | 없음 | 49.2 |
| `ManualResetEventSlim` | 하이브리드 | `Reset`까지 전부 | **불가** | **있음** | 49.2 |
| `CountdownEvent` | 하이브리드 | 카운트 0이 되면 전부 | **불가** | **있음** | 49.3 |
| `Barrier` | 하이브리드 | 참가자 전원이 모이면 전부 | **불가** | **있음** | 49.6 |
| `Monitor.Wait`/`Pulse` | 하이브리드 | 조건이 참인 대기자 | **불가** | 없음 | 49.7 |

"하이브리드"는 48.12절에서 본 그 의미다 — 경합이 없으면 사용자 모드에서 스핀으로 끝내고, 경합이 생겼을 때만 커널 객체를 만들어 진짜로 블로킹한다. 경합이 한 번도 없으면 커널 객체를 아예 만들지 않으므로 그 생성 비용과 메모리도 들지 않는다.

## 49.2 `AutoResetEvent`와 `ManualResetEvent`(`Slim`)

### 두 클래스의 본질 — 턴스타일과 문

커널이 관리하는 **이벤트는 단순한 불리언 변수**다. 이벤트를 기다리는 스레드는 값이 `false`이면 막히고 `true`가 되면 풀린다. 종류는 둘이다.

- **자동 리셋 이벤트**가 `true`가 되면 커널이 막힌 스레드 **하나**만 깨우고 **즉시 다시 `false`로 되돌린다.**
- **수동 리셋 이벤트**가 `true`가 되면 기다리던 스레드 **전부**가 풀린다. 커널이 자동으로 되돌리지 않으므로 코드가 직접 `Reset`해야 한다.

이것을 비유로 옮기면 이렇다.

```text
  AutoResetEvent — 지하철 턴스타일(개찰구)
  ┌───────────────────────────────────────────────────┐
  │ [T4] [T3] [T2] ──▶ ╱│ 턴스타일 │╲ ──▶ 한 명만 통과 │
  │                    Set() 이 티켓 한 장,             │
  │                    한 명 지나가면 자동으로 닫힘      │
  └───────────────────────────────────────────────────┘
     아무도 없을 때 Set() 을 세 번 불러도 한 명분만 남는다 (나머지는 버려진다)

  ManualResetEvent — 문
  ┌───────────────────────────────────────────────────┐
  │ [T4] [T3] [T2] ──▶ ▕  열린 문  ▏──▶ 전부 통과      │
  │                    Set() 이 문을 열고,              │
  │                    Reset() 을 부를 때까지 열려 있음  │
  └───────────────────────────────────────────────────┘
     문이 열려 있는 동안 도착한 스레드는 막히지 않고 그냥 지나간다
```

클래스 정의는 이렇다.

```csharp
public class EventWaitHandle : WaitHandle
{
    public bool Set();      // 불리언을 true 로. 언제나 true 를 반환한다
    public bool Reset();    // 불리언을 false 로. 언제나 true 를 반환한다
}

public sealed class AutoResetEvent : EventWaitHandle
{
    public AutoResetEvent(bool initialState);
}

public sealed class ManualResetEvent : EventWaitHandle
{
    public ManualResetEvent(bool initialState);
}
```

`Set`과 `Reset`이 `bool`을 반환하지만 **언제나 `true`다.** 반환값을 검사할 이유가 없다.

### `AutoResetEvent` — 기본 사용

만드는 방법이 둘이다. 생성자를 쓰거나, 기반 클래스에 모드를 넘기거나.

```csharp
var auto = new AutoResetEvent(false);
var auto2 = new EventWaitHandle(false, EventResetMode.AutoReset);   // 동등하다
```

생성자에 `true`를 넘기는 것은 만들자마자 `Set`을 부르는 것과 같다.

스레드 하나가 다른 스레드의 신호를 기다리는 가장 단순한 형태는 이렇다.

```csharp
class BasicWaitHandle
{
    static EventWaitHandle _waitHandle = new AutoResetEvent(false);

    static void Main()
    {
        new Thread(Waiter).Start();
        Thread.Sleep(1000);                 // 1초 쉰다
        _waitHandle.Set();                  // Waiter 를 깨운다
    }

    static void Waiter()
    {
        Console.WriteLine("대기 중...");
        _waitHandle.WaitOne();              // 신호를 기다린다
        Console.WriteLine("통보받음");
    }
}

// 출력:
// 대기 중...   (1초 정지)   통보받음
```

**티켓은 아무 스레드나 넣을 수 있다.** 대기 핸들 객체에 접근할 수 있고 막혀 있지 않은 스레드라면 누구든 `Set`을 불러 막힌 스레드 하나를 풀어 줄 수 있다. 잠금과 결정적으로 다른 지점이다 — 잠금은 획득한 스레드만 해제할 수 있다.

`Reset`을 부르면 (열려 있었다면) 턴스타일이 닫힌다. 대기하거나 막히지는 않는다.

### 신호가 이미 있으면 대기 없이 통과한다

`Set`이 호출됐는데 아무도 기다리지 않으면 어떻게 되는가. **핸들은 열린 채로 남고, 다음에 `WaitOne`을 부르는 스레드가 즉시 통과한다.**

이 동작에는 이유가 있다. 이것이 없으면 **"티켓을 1마이크로초 일찍 넣었더니 상대가 영원히 기다리게 됐다"** 는 경합이 생긴다. 신호를 보내는 스레드와 받는 스레드의 도착 순서에 의존하지 않게 만드는 장치다.

```csharp
var wh = new AutoResetEvent(false);

wh.Set();               // 아무도 기다리지 않는다 — 핸들이 열린 채 남는다
Console.WriteLine("신호를 먼저 보냈다");

wh.WaitOne();           // 즉시 통과한다. 막히지 않는다
Console.WriteLine("그래도 통과했다");
```

> **⚠️ 그런데 신호는 누적되지 않는다 — 이 장에서 가장 많은 사고를 내는 사실**
>
> 아무도 없는 턴스타일에 `Set`을 세 번 연속 불러도 나중에 세 명이 통과하지는 **않는다.** 딱 한 명만 통과하고 **나머지 티켓 두 장은 버려진다.**
>
> ```csharp
> var wh = new AutoResetEvent(false);
>
> wh.Set(); wh.Set(); wh.Set();       // 세 번 신호
>
> Console.WriteLine(wh.WaitOne(0));   // True  — 첫 번째 통과
> Console.WriteLine(wh.WaitOne(0));   // False — 두 번째는 없다
> Console.WriteLine(wh.WaitOne(0));   // False
> ```
>
> `AutoResetEvent`는 카운트를 세지 않는 **불리언**이기 때문이다. `false → true` 로 바뀌는 것은 세 번 다 같은 일이고, 통과 한 번이 다시 `false`로 만든다.
>
> **"작업 항목이 N개 준비됐다"를 N번의 `Set`으로 알리려는 코드는 조용히 항목을 잃는다.** 이 문제의 정답은 세 가지다. (1) 카운트를 세는 구조를 쓴다 — `SemaphoreSlim`(48.11절)이나 `CountdownEvent`(49.3절). (2) 별도의 카운터를 잠금으로 보호하고 이벤트는 "확인하라"는 신호로만 쓴다. (3) 애초에 큐를 쓴다 — `BlockingCollection<T>`(50.11절)이나 `Channel`(51.1절).
>
> 세마포어와의 차이를 정확히 말하면 이렇다. 자동 리셋 이벤트에 `Set`을 연속으로 여러 번 불러도 여전히 스레드 하나만 풀리지만, 세마포어에 `Release`를 연속으로 부르면 내부 카운트가 계속 올라가 **여러 스레드를 풀 수 있다.**

### 양방향 신호 — 신호 유실을 막는 관용구

주 스레드가 작업 스레드에게 세 번 연속 신호를 보내야 한다고 하자. 위 함정 그대로다 — 주 스레드가 `Set`을 빠르게 세 번 부르면 두 번째나 세 번째 신호가 사라진다. 작업 스레드가 각 신호를 처리하는 데 시간이 걸리기 때문이다.

해법은 **주 스레드가 작업자가 준비될 때까지 기다린 뒤에 신호를 보내는 것**이다. 그러려면 `AutoResetEvent`가 하나 더 필요하다.

```csharp
class TwoWaySignaling
{
    static EventWaitHandle _ready = new AutoResetEvent(false);
    static EventWaitHandle _go = new AutoResetEvent(false);
    static readonly object _locker = new object();
    static string _message;

    static void Main()
    {
        new Thread(Work).Start();

        _ready.WaitOne();                            // 작업자가 준비될 때까지 기다린다
        lock (_locker) _message = "ooo";
        _go.Set();                                   // 작업자에게 진행하라고 알린다

        _ready.WaitOne();                            // 다시 준비될 때까지
        lock (_locker) _message = "ahhh";            // 메시지를 하나 더 준다
        _go.Set();

        _ready.WaitOne();
        lock (_locker) _message = null;              // 종료하라는 신호
        _go.Set();
    }

    static void Work()
    {
        while (true)
        {
            _ready.Set();                            // 준비됐음을 알린다
            _go.WaitOne();                           // 출발 신호를 기다린다
            lock (_locker)
            {
                if (_message == null) return;        // 정상 종료
                Console.WriteLine(_message);
            }
        }
    }
}

// 출력:
// ooo
// ahhh
```

핵심은 두 가지다. 첫째, **`_ready`와 `_go`가 번갈아 신호되므로 어느 쪽도 신호를 잃지 않는다.** 둘째, `null` 메시지를 종료 신호로 쓴다 — **무한히 도는 스레드에는 반드시 탈출 전략이 있어야 한다.**

> **💡 이 관용구를 새로 쓰지 마라**
>
> 위 코드는 신호 구조의 동작을 이해하는 데는 훌륭한 예제지만, 2020년대에 이런 코드를 새로 작성할 이유는 거의 없다. 하는 일은 **용량 1인 프로듀서/컨슈머 큐**이고, 그건 `Channel<string>`(51.1절)의 세 줄짜리 코드다. `BlockingCollection<string>`(50.11절)도 마찬가지다. 그리고 이 코드는 작업자 스레드를 하나 전용으로 붙들고 있다 — 45.9절이 하지 말라고 한 바로 그것이다.

### `ManualResetEvent` — 문

`ManualResetEvent`는 단순한 문처럼 동작한다. `Set`이 문을 열어 `WaitOne`을 부른 **아무 수의 스레드**를 통과시킨다. `Reset`이 문을 닫는다. 닫힌 문에서 `WaitOne`을 부른 스레드들은 막히고, 다음에 문이 열리면 **한꺼번에** 풀린다. 그 외에는 `AutoResetEvent`와 동일하게 동작한다.

```csharp
var manual1 = new ManualResetEvent(false);
var manual2 = new EventWaitHandle(false, EventResetMode.ManualReset);   // 동등하다
```

대표적인 쓰임은 **한 스레드가 여러 스레드를 한꺼번에 출발시키는 것**이다.

```csharp
static ManualResetEvent _start = new ManualResetEvent(false);

static void Main()
{
    for (int i = 1; i <= 5; i++)
    {
        int id = i;
        new Thread(() =>
        {
            _start.WaitOne();                       // 문 앞에서 대기
            Console.WriteLine($"{id} 출발");
        }).Start();
    }

    Thread.Sleep(500);                              // 다섯 스레드가 모두 문 앞에 모이도록
    Console.WriteLine("출발!");
    _start.Set();                                   // 다섯 전부 동시에 풀린다
}
```

`ManualResetEvent`가 한 스레드로 여러 스레드를 푸는 도구라면, **그 반대 — 여러 스레드의 완료를 한 스레드가 기다리는 것 — 이 `CountdownEvent`**다(49.3절).

`ManualResetEvent`는 "한 번 켜지면 영원히 켜져 있는 상태"를 표현하는 데도 좋다. 초기화 완료 플래그가 대표적이다.

```csharp
static readonly ManualResetEventSlim _initialized = new ManualResetEventSlim(false);

// 초기화 담당 스레드: LoadConfiguration() 뒤에 _initialized.Set() — 이후 Reset 하지 않는다
// 사용하는 쪽:     _initialized.Wait();  // 초기화 전에는 막히고, 이후에는 즉시 통과한다
```

### `ManualResetEventSlim` — 스핀 우선, 프로세스 내 전용

`ManualResetEvent`에는 짧은 대기에 최적화된 판본이 있다.

```csharp
public class ManualResetEventSlim : IDisposable
{
    public ManualResetEventSlim(bool initialState);
    public ManualResetEventSlim(bool initialState, int spinCount);

    public void Set();
    public void Reset();
    public void Wait();
    public bool Wait(int millisecondsTimeout);
    public void Wait(CancellationToken cancellationToken);
    public bool Wait(int millisecondsTimeout, CancellationToken cancellationToken);

    public bool IsSet      { get; }
    public int  SpinCount  { get; }
    public WaitHandle WaitHandle { get; }

    public void Dispose();
}
```

동작은 커널 판본과 **정확히 같지만** 구현이 다르다. 48.12절에서 본 하이브리드 전략을 쓴다.

1. `Wait`가 호출되면 먼저 **사용자 모드에서 정해진 횟수만큼 스핀**한다(`spinCount`).
2. 스핀 중에 `Set`이 오면 커널을 한 번도 건드리지 않고 끝난다.
3. 스핀이 소진되면 그때 비로소 **커널 이벤트 객체를 만들어** 진짜로 블로킹한다.

즉 **경합이 없거나 대기가 아주 짧으면 커널 객체를 아예 만들지 않는다.** 생성 비용도, 메모리도, 전이 비용도 들지 않는다.

| 항목 | `ManualResetEvent` | `ManualResetEventSlim` |
|---|---|---|
| 구현 | 순수 커널 객체 | 하이브리드(스핀 후 필요 시 커널) |
| `WaitHandle` 상속 | **한다** | 하지 않는다 (`WaitHandle` 속성으로 노출) |
| 대기 메서드 이름 | `WaitOne` | `Wait` |
| `CancellationToken` | 없음 | **있다** |
| 프로세스 간 사용 | 이름을 주면 가능(Windows 전용) | **불가** |
| 스핀 횟수 조절 | 불가 | `spinCount` 생성자 인자 |
| 상태 조회 | 전용 속성 없음(`WaitOne(0)`으로 대신한다) | **`IsSet` 속성** |
| 짧은 대기 성능 | 약 1마이크로초 | 최대 50배 빠를 수 있다 |
| 긴 대기 성능 | 같다 | **스핀이 낭비된다** |

> **⚠️ 대기가 길면 `Slim`이 더 느리다**
>
> `Slim`이 이기는 것은 **신호가 곧 올 때**뿐이다. 신호가 수 밀리초 이상 뒤에 온다면 스핀 구간은 그냥 CPU를 태우는 시간이고, 결국 커널 객체를 만들어 블로킹하므로 커널 판본이 하던 일을 **추가 비용을 내고** 하는 셈이 된다. 코어가 적은 머신이나 컨테이너의 CPU 할당량이 낮은 환경에서는 그 스핀이 다른 스레드의 실행 시간을 빼앗아 상황을 더 악화시킨다.
>
> 판단 기준은 이렇다. **대기 시간이 컨텍스트 스위치 비용(수 마이크로초)과 비슷하거나 그보다 짧을 것으로 기대되면 `Slim`, 밀리초 이상이면 커널 판본이거나 애초에 비동기 설계**다.

`WaitHandle` 속성은 **필요할 때만** 만져라.

```csharp
var mres = new ManualResetEventSlim(false);
WaitHandle wh = mres.WaitHandle;      // 이 순간 진짜 커널 객체가 만들어진다
WaitHandle.WaitAny(new[] { wh, otherHandle });
```

이 속성에 접근하는 순간 하이브리드 구조의 이점이 사라진다. 반환되는 것은 **전통적 대기 핸들의 성능 특성**을 가진 객체다. `WaitAny`/`WaitAll`에 참여시켜야 할 때(49.5절)만 쓴다.

> **📌 `AutoResetEventSlim`은 없다**
>
> BCL에는 `ManualResetEventSlim`만 있고 자동 리셋 판본은 없다. 원천 저자의 조언은 이렇다 — **최대 카운트를 1로 준 `SemaphoreSlim`으로 많은 상황에서 대체할 수 있다.** 다만 의미론이 완전히 같지는 않다. `AutoResetEvent`는 `Set`을 여러 번 불러도 티켓이 하나뿐이지만 `SemaphoreSlim`은 카운트가 쌓인다. **최대 카운트를 명시적으로 1로 주면**(`new SemaphoreSlim(0, 1)`) 초과 `Release` 시 `SemaphoreFullException`이 나므로 그 차이가 조용히 넘어가지 않고 드러난다.

### 세 이벤트 구조 상태표

같은 조작을 세 구조에 가했을 때 무슨 일이 벌어지는지 한 표로 정리한다.

| 상황 | `AutoResetEvent` | `ManualResetEvent(Slim)` | `SemaphoreSlim(0, n)` |
|---|---|---|---|
| 초기 상태 `false`, `WaitOne` | 막힌다 | 막힌다 | 막힌다 |
| 대기자 3명, `Set`/`Release()` 1회 | **1명** 통과 | **3명 전부** 통과 | **1명** 통과 |
| 대기자 3명, `Set` 3회 연속 | 1명씩 3번, 즉 3명 통과 | 3명 전부(첫 `Set`에서) | 3명 통과 |
| 대기자 0명, `Set` 3회 → 이후 `WaitOne` 3회 | **1번만** 통과 | 3번 전부 통과 | **3번 전부** 통과 |
| 통과 후 다음 `WaitOne` | 막힌다(자동으로 닫힘) | 통과한다(`Reset` 전까지) | 카운트가 남아 있으면 통과 |
| `Reset()` | 열려 있으면 닫는다 | 문을 닫는다 | 그런 메서드가 없다 |
| 신호가 누적되는가 | **아니다** | 해당 없음(열림/닫힘) | **그렇다**(카운트) |

이 표의 4행이 핵심이다. **`AutoResetEvent`는 유일하게 신호를 잃는 구조다.**

> **💡 어느 것을 고를 것인가 — 세 문장 규칙**
>
> 1. **"이 일이 끝났다"를 한 번 알리고 끝나면** `ManualResetEventSlim`. 래치처럼 쓰고 `Reset`하지 않는다. 늦게 도착한 스레드도 통과한다.
> 2. **"작업 항목이 하나 생겼다"를 반복해서 알리면** 신호 구조가 아니라 **큐**다. `Channel<T>`(51.1절).
> 3. **그 외에 정말로 턴스타일 의미론이 필요하면** `AutoResetEvent`. 다만 신호가 누적되지 않는다는 사실을 코드 주석에 적어 둬라.

## 49.3 `CountdownEvent`

### 카운트가 0이 될 때까지 기다린다

`ManualResetEvent`가 **한 스레드로 여러 스레드를 풀어 주는** 도구였다면, `CountdownEvent`는 그 반대다 — **여러 스레드의 완료를 한 스레드가 기다린다.**

내부적으로 `ManualResetEventSlim`을 쓰는 완전 관리 코드 구현이며, 세마포어와 정반대의 조건에서 막는다. 세마포어는 카운트가 **0일 때** 막지만, `CountdownEvent`는 카운트가 **0이 아닐 때** 막는다.

```csharp
public class CountdownEvent : IDisposable
{
    public CountdownEvent(int initialCount);

    public bool Signal();                                   // CurrentCount 를 1 감소
    public bool Signal(int signalCount);                    // signalCount 만큼 감소
    public void AddCount();                                 // 1 증가
    public void AddCount(int signalCount);                  // signalCount 만큼 증가
    public bool TryAddCount();                              // 증가 시도. 0이면 false
    public bool TryAddCount(int signalCount);

    public void Wait();
    public bool Wait(int millisecondsTimeout);
    public void Wait(CancellationToken cancellationToken);
    public bool Wait(int millisecondsTimeout, CancellationToken cancellationToken);

    public void Reset();                                    // InitialCount 로 되돌린다
    public void Reset(int count);                           // 지정한 값으로 되돌린다

    public int  CurrentCount { get; }
    public int  InitialCount { get; }
    public bool IsSet        { get; }                       // CurrentCount 가 0이면 true
    public WaitHandle WaitHandle { get; }

    public void Dispose();
}
```

기다릴 스레드 수(카운트)로 초기화하고, 각 스레드가 끝날 때 `Signal`을 부르고, 기다리는 쪽은 `Wait`를 부른다.

```csharp
var countdown = new CountdownEvent(3);      // 카운트 3으로 초기화

new Thread(SaySomething).Start("나는 스레드 1");
new Thread(SaySomething).Start("나는 스레드 2");
new Thread(SaySomething).Start("나는 스레드 3");

countdown.Wait();                           // Signal 이 3번 불릴 때까지 막힌다
Console.WriteLine("모든 스레드가 말을 마쳤다!");

void SaySomething(object thing)
{
    Thread.Sleep(1000);
    Console.WriteLine(thing);
    countdown.Signal();
}
```

`Signal`은 **카운트를 0으로 만들었으면 `true`를 반환**한다. 마지막 참가자가 자기가 마지막이었음을 알 수 있다.

```csharp
if (countdown.Signal())
    Console.WriteLine("내가 마지막이었다 — 후처리를 내가 한다");
```

### 카운트를 다시 올리기 — 그리고 그 함정

작업 중에 할 일이 늘어나는 경우가 있다. 디렉터리를 재귀 순회하면서 하위 디렉터리를 발견할 때마다 작업을 하나 더 만드는 식이다. `AddCount`가 그 용도다.

```csharp
var cd = new CountdownEvent(1);             // 루트 작업 1개로 시작

void ProcessDirectory(string path)
{
    foreach (var sub in Directory.GetDirectories(path))
    {
        cd.AddCount();                      // 하위 작업이 하나 늘었다
        ThreadPool.QueueUserWorkItem(_ =>
        {
            try { ProcessDirectory(sub); }
            finally { cd.Signal(); }        // 반드시 finally 에서
        });
    }
    // 이 디렉터리 자체 처리...
}

ThreadPool.QueueUserWorkItem(_ => { try { ProcessDirectory(root); } finally { cd.Signal(); } });
cd.Wait();
```

> **⚠️ 카운트가 0이 된 뒤의 `AddCount`는 예외다**
>
> `CurrentCount`가 이미 0에 도달한 `CountdownEvent`에 `AddCount`를 부르면 **`InvalidOperationException`이 발생한다.** 원천 자료의 표현대로, **`AddCount`로 카운트다운을 "언신호(unsignal)"할 수는 없다.** 한 번 0이 되면 그 상태는 바뀌지 않는다.
>
> 위 디렉터리 예제가 카운트 **1로 시작해서** 루트 작업 자체도 `Signal`하는 이유가 여기 있다. 0에서 시작해 `AddCount`로 늘리려 했다면, 첫 `AddCount` 전에 이미 카운트가 0이라 예외가 난다. **"작업이 남아 있다"는 사실을 나타내는 초기 카운트 1을 항상 잡아 두고 마지막에 그것을 `Signal`하는 것이 이 관용구의 정석이다.**
>
> 예외를 피하고 싶으면 `TryAddCount`를 쓴다. 카운트가 0이면 예외 대신 **`false`를 반환**한다.
>
> ```csharp
> if (!cd.TryAddCount())
>     return;      // 이미 다 끝났다. 새 작업을 만들 이유가 없다
> ```

카운트가 0인 상태에서 `Signal`을 더 부르는 것도 **`InvalidOperationException`** 이다. `Signal`과 `AddCount`의 짝을 정확히 맞춰야 하며, `Signal`은 **반드시 `finally`에서** 불러야 한다. 작업이 예외로 죽으면 `Signal`이 불리지 않고, 기다리는 스레드는 영원히 깨어나지 않는다.

`Reset`은 **언신호와 카운트 되돌리기를 한꺼번에** 한다. 인자 없는 `Reset()`은 `InitialCount`로, `Reset(n)`은 지정한 값으로 되돌린다. 다만 **대기자가 있는 상태에서 `Reset`을 부르면 동작이 정의되지 않으므로**, 모든 대기가 끝난 것이 확실한 시점에만 써라. 라운드마다 재사용하는 설계라면 매 라운드 새 인스턴스를 만드는 편이 훨씬 안전하다.

### `Task.WhenAll`과의 비교

"여러 작업이 끝나기를 기다린다"는 요구는 46.9절의 `Task.WhenAll`이 훨씬 자연스럽게 푼다.

```csharp
// CountdownEvent 방식 — 스레드를 하나 막는다
var cd = new CountdownEvent(urls.Length);
foreach (var url in urls)
    ThreadPool.QueueUserWorkItem(_ => { try { Download(url); } finally { cd.Signal(); } });
cd.Wait();                                  // 여기서 스레드 하나가 통째로 잠긴다

// Task.WhenAll 방식 — 아무 스레드도 막지 않는다
await Task.WhenAll(urls.Select(u => DownloadAsync(u)));
```

| 항목 | `CountdownEvent` | `Task.WhenAll`(46.9절) |
|---|---|---|
| 대기 방식 | 스레드를 블로킹한다 | `await` — 스레드를 놓는다 |
| 결과 수집 | 직접 배열·컬렉션에 담아야 한다 | `Task<T[]>` 로 자동 수집 |
| 예외 전파 | **없다.** 작업의 예외를 직접 모아야 한다 | `AggregateException` 으로 자동 수집 |
| 취소 | `Wait(CancellationToken)` | 각 태스크의 토큰 |
| 작업 수 동적 증가 | `AddCount` 로 가능 | 불가(태스크 목록이 고정) |
| 참가자가 태스크가 아닐 때 | **가능** — 스레드, 네이티브 콜백, 이벤트 어느 것이든 | 불가(`TaskCompletionSource` 로 감싸야 한다, 46.5절) |

원천 자료의 조언도 같은 방향이다. **`CountdownEvent`로 푸는 문제 중 상당수는 구조화된 병렬성 구조(PLINQ, `Parallel` 클래스 — 50장)로 더 쉽게 풀린다.**

> **💡 `CountdownEvent`가 여전히 옳은 두 가지 경우**
>
> 첫째, **참가자가 태스크가 아닐 때.** 네이티브 라이브러리의 완료 콜백, 이벤트 핸들러, 전용 스레드 같은 것들이 완료를 알려 오는 구조라면 `CountdownEvent`가 가장 직접적이다(각각을 `TaskCompletionSource`로 감싸는 방법도 있다 — 46.5절).
>
> 둘째, **작업 수가 실행 중에 늘어날 때.** `Task.WhenAll`은 호출 시점에 태스크 목록이 확정되어야 하지만 `AddCount`는 그렇지 않다. 다만 이 경우에도 `Channel`(51.1절)이나 재귀적 `Task.WhenAll`이 더 읽기 쉬운 경우가 많다.
>
> 그 외에는 **`Task.WhenAll`이다.** 특히 예외 처리 — `CountdownEvent`는 작업이 던진 예외를 전혀 전달해 주지 않는다는 사실을 반드시 기억해라.

`CountdownEvent`도 `ManualResetEventSlim`처럼 `WaitHandle` 속성을 노출한다. `WaitHandle` 기반 객체를 요구하는 API(49.5절의 `WaitAny`/`WaitAll`)에 참여시켜야 할 때 쓴다.

## 49.4 크로스 프로세스 `EventWaitHandle` 만들기

### 이름이 커널 객체를 공유하게 만든다

`EventWaitHandle`의 생성자는 **이름(name)** 을 받는 오버로드를 갖는다. 이름을 주면 그 이벤트는 **머신 전체에서 유일한 커널 객체**가 되고, 서로 다른 프로세스가 같은 이름으로 접근하면 **같은 객체를 공유한다.**

```csharp
public class EventWaitHandle : WaitHandle
{
    public EventWaitHandle(bool initialState, EventResetMode mode);
    public EventWaitHandle(bool initialState, EventResetMode mode, string name);
    public EventWaitHandle(bool initialState, EventResetMode mode, string name,
                           out bool createdNew);

    public static EventWaitHandle OpenExisting(string name);
    public static bool TryOpenExisting(string name, out EventWaitHandle result);
}
```

이름은 그냥 문자열이며, 다른 사람의 것과 의도치 않게 충돌하지만 않으면 아무 값이나 된다.

```csharp
EventWaitHandle wh = new EventWaitHandle(
    false, EventResetMode.AutoReset, @"Global\MyCompany.MyApp.SomeName");
```

두 애플리케이션이 각각 이 코드를 실행하면 **서로에게 신호를 보낼 수 있다.** 이 대기 핸들은 두 프로세스의 모든 스레드에 걸쳐 작동한다.

동작 원리는 커널이 보장하는 이름 공간에 있다. 같은 이름으로 커널 객체를 만들려는 스레드가 여럿이면, **Windows 커널은 그중 하나만 실제로 객체를 만들게 한다.** 나머지는 이미 존재하는 객체의 핸들을 받는다. `createdNew` 출력 매개변수가 "내가 만든 쪽인가"를 알려 준다.

```csharp
bool createdNew;
using var wh = new EventWaitHandle(
    false, EventResetMode.ManualReset, @"Global\MyCompany.MyApp.Ready", out createdNew);

if (createdNew)
    Console.WriteLine("이 프로세스가 이벤트를 만들었다");
else
    Console.WriteLine("이미 존재하는 이벤트를 열었다 — 다른 인스턴스가 돌고 있다");
```

이미 존재하는 것만 열고 싶으면 `OpenExisting`을 쓴다. 그 이름의 커널 객체가 없으면 **`WaitHandleCannotBeOpenedException`** 이 발생한다. 예외 없이 시도만 하려면 `TryOpenExisting`이다.

> **⚠️ 이름 있는 이벤트 대기 핸들은 Windows 전용이다**
>
> 원천 자료의 서술 그대로다 — **이름 있는 이벤트 대기 핸들은 Windows에서만 사용할 수 있다.** Linux·macOS의 .NET에서 이름을 주어 `EventWaitHandle`을 만들면 **`PlatformNotSupportedException`** 이 발생한다.
>
> 같은 제약이 이름 있는 `Semaphore`에도 적용된다. 반면 **이름 있는 `Mutex`는 Unix 플랫폼에서도 동작한다**(48.10절). 크로스 플랫폼으로 프로세스 간 조정을 해야 한다면 선택지는 사실상 이름 있는 `Mutex`뿐이고, 그마저도 신호가 아니라 잠금이다.
>
> 컨테이너로 배포되는 서비스, Linux 호스트에서 도는 ASP.NET Core 애플리케이션에서 이 코드를 쓰면 **개발 머신(Windows)에서는 되고 운영(Linux)에서 터진다.** 이 장에서 가장 조용히 깨지는 지점이다.

### `Global\`과 `Local\` 접두사

Windows의 커널 객체 이름 공간은 **터미널 서비스 세션**별로 분리되어 있다. 접두사가 그 범위를 결정한다.

| 접두사 | 가시 범위 | 비고 |
|---|---|---|
| `Local\` (또는 접두사 없음) | 같은 세션 안의 프로세스 | 사용자별 격리에 적합 |
| `Global\` | **모든 세션** | 원격 데스크톱 세션, 서비스 ↔ 데스크톱 앱 간 통신에 필요 |

원천 자료가 `Mutex`에 대해 남긴 경고가 여기에도 그대로 적용된다. **터미널 서비스나 별도의 Unix 콘솔에서 실행하면 머신 전역 객체가 보통 같은 세션의 애플리케이션에만 보인다.** 모든 터미널 서버 세션에서 보이게 하려면 이름 앞에 `Global\`을 붙여야 한다.

> **⚠️ `Global\` 이름 공간은 권한이 필요하다**
>
> 표준 사용자 권한으로 실행되는 프로세스가 `Global\` 접두사로 커널 객체를 **만들려고** 하면 권한 문제로 실패할 수 있다. 서비스(높은 권한)가 만들고 데스크톱 앱(표준 권한)이 여는 조합은 대체로 동작하지만, 반대는 아니다. 그리고 두 프로세스가 서로 다른 사용자 계정으로 돌면 기본 보안 서술자 때문에 접근이 거부될 수 있다. .NET Framework에서는 `EventWaitHandleSecurity`로 ACL을 지정할 수 있었지만, 현대 .NET에서 이 API는 `System.Threading.AccessControl` 패키지로 분리되어 있고 **Windows 전용**이다.

### 단일 인스턴스 애플리케이션

이름 있는 커널 객체의 가장 흔한 쓰임은 **애플리케이션의 인스턴스를 하나로 제한하는 것**이다. Outlook·미디어 플레이어 류의 프로그램이 이렇게 만들어져 있다.

원천 자료는 `Semaphore`로 이것을 구현한다.

```csharp
using System;
using System.Threading;

public static class Program
{
    public static void Main()
    {
        bool createdNew;

        // 지정한 이름으로 커널 객체를 만들어 본다
        using (new Semaphore(0, 1, "SomeUniqueStringIdentifyingMyApp", out createdNew))
        {
            if (createdNew)
            {
                // 이 스레드가 커널 객체를 만들었다 — 다른 인스턴스가 없다.
                // 나머지 애플리케이션 코드를 여기서 실행한다...
            }
            else
            {
                // 기존 커널 객체를 열었다 — 다른 인스턴스가 돌고 있다.
                // Main 에서 반환해 이 두 번째 인스턴스를 종료한다.
            }
        }
    }
}
```

여기서 `Semaphore`를 쓴 것은 **동기화 동작이 필요해서가 아니다.** 원천 저자의 설명 그대로, 어떤 종류의 커널 객체를 만들든 커널이 제공하는 "같은 이름의 객체는 하나만 만들어진다"는 동작을 이용했을 뿐이다. `EventWaitHandle`이나 `Mutex`를 썼어도 똑같이 동작한다.

두 인스턴스가 정확히 동시에 시작해도 안전하다. 커널이 이름 등록을 직렬화하므로 **`createdNew`가 `true`인 프로세스는 정확히 하나**다.

크로스 플랫폼이 필요하면 이름 있는 `Mutex`로 같은 일을 한다. 이름 있는 `Mutex`를 `true`(초기 소유 요청)로 만들고 짧은 타임아웃으로 `WaitOne`을 시도해, 실패하면 다른 인스턴스가 돌고 있다고 판단하는 형태다. 전체 코드는 48.10절에 있다.

> **📌 `createdNew` 방식과 `WaitOne` 방식의 차이**
>
> 세마포어의 `createdNew`를 검사하는 방식은 **커널 객체의 존재 여부**로 판단한다. `Mutex`의 `WaitOne`으로 판단하는 방식은 **소유권 획득 성공 여부**로 판단한다.
>
> 실질적 차이는 **먼저 뜬 인스턴스가 종료 중일 때** 나타난다. `createdNew` 방식은 커널 객체가 아직 살아 있으면 무조건 "다른 인스턴스가 있다"로 판정하지만, `Mutex` + 타임아웃 방식은 몇 초 기다려 상대가 완전히 끝나면 진입할 수 있다. 사용자가 앱을 껐다가 바로 다시 켜는 흔한 시나리오에서 후자가 덜 짜증스럽다.

### 프로세스 간 신호 관용구

이름 있는 이벤트로 할 수 있는 대표적 IPC 패턴은 이렇다.

| 패턴 | 구성 | 설명 |
|---|---|---|
| 준비 완료 통보 | 서비스가 `ManualResetEvent`를 `Set`, 클라이언트가 `WaitOne` | "서버가 초기화를 마쳤다"를 알린다 |
| 종료 요청 | 관리자 도구가 `Set`, 서비스 루프가 `WaitOne(0)`으로 폴링 | 우아한 종료 신호 |
| 작업 깨우기 | 프로듀서가 `AutoResetEvent`를 `Set`, 컨슈머 프로세스가 대기 | 실제 데이터는 파일·공유 메모리·파이프로 |
| 단일 인스턴스 | 위의 `createdNew` 관용구 | 신호를 실제로 쓰지는 않는다 |

**신호는 "무언가 일어났다"만 전달할 뿐 데이터를 나르지 않는다.** 실제 데이터는 별도의 채널이 필요하다 — 메모리 매핑 파일(`MemoryMappedFile`), 명명된 파이프(`NamedPipeServerStream`), 파일 시스템, 소켓 중 하나다.

> **💡 프로세스 간 신호가 정답인 경우는 생각보다 드물다**
>
> 이름 있는 커널 객체는 Windows 전용 제약, 세션 격리, 권한 문제, 컨테이너 격리(각 컨테이너가 별도의 커널 이름 공간을 갖는다)를 전부 안고 간다. 그리고 상대 프로세스가 죽었는지 알 방법이 없다 — `Mutex`와 달리 이벤트에는 유기(abandoned) 개념이 없으므로, 신호를 보내기로 한 프로세스가 죽으면 기다리는 쪽은 **영원히 기다린다.**
>
> 반드시 타임아웃을 걸고, 상대의 생존을 별도로 확인해라. 그리고 새로 설계한다면 **명명된 파이프나 로컬 소켓**을 먼저 검토하는 편이 낫다 — 연결이 끊기면 그 사실이 즉시 드러나기 때문이다.

## 49.5 대기 핸들과 연속, `WaitAny` / `WaitAll` / `SignalAndWait`

### 여러 핸들을 한꺼번에 다루기

`Set`·`WaitOne`·`Reset` 외에 `WaitHandle`에는 **여러 핸들을 동시에 다루는 정적 메서드**가 셋 있다.

| 메서드 | 하는 일 | 반환값 |
|---|---|---|
| `WaitHandle.WaitAny(handles)` | 배열 중 **하나라도** 신호될 때까지 막는다 | 신호된 핸들의 **인덱스**, 타임아웃이면 `WaitHandle.WaitTimeout`(258) |
| `WaitHandle.WaitAll(handles)` | 배열 **전부**가 신호될 때까지 **원자적으로** 막는다 | 전부 신호되면 `true`, 타임아웃이면 `false` |
| `WaitHandle.SignalAndWait(a, b)` | `a`에 `Set`을 부르고 곧바로 `b`에 `WaitOne` | `b`를 얻었으면 `true` |

핸들의 타입은 섞여도 된다. `Mutex`와 `Semaphore`도 `WaitHandle`을 상속하므로 함께 넣을 수 있다. `ManualResetEventSlim`과 `CountdownEvent`는 `WaitHandle` 속성을 통해 참여시킬 수 있다.

```csharp
var done1 = new ManualResetEvent(false);
var done2 = new AutoResetEvent(false);
var slim  = new ManualResetEventSlim(false);

int index = WaitHandle.WaitAny(new WaitHandle[] { done1, done2, slim.WaitHandle },
                               TimeSpan.FromSeconds(10));

if (index == WaitHandle.WaitTimeout)
    Console.WriteLine("10초 안에 아무것도 신호되지 않았다");
else
    Console.WriteLine($"{index}번 핸들이 신호됐다");
```

내부적으로 `WaitAny`와 `WaitAll`은 둘 다 Win32 `WaitForMultipleObjectsEx`를 호출한다. 차이는 `bWaitAll` 인자뿐이다 — `WaitAll`은 `TRUE`, `WaitAny`는 `FALSE`.

### `WaitAll`의 원자성이 뜻하는 것

**`WaitAll`은 원자적이다.** 이것이 단순히 "루프로 하나씩 `WaitOne`하는 것"과 결정적으로 다른 점이다.

두 개의 `AutoResetEvent`를 기다린다고 하자.

- `WaitAny`는 **두 이벤트를 동시에 "래치(latch)"하는 일이 절대 없다.** 하나만 소비한다.
- `WaitAll`은 **하나만 래치하는 일이 절대 없다.** 둘 다 신호된 순간에 둘 다 소비하거나, 아무것도 소비하지 않는다.

루프로 흉내 내면 이 보장이 깨진다.

```csharp
// 이것은 WaitAll 이 아니다 — 원자적이지 않다
foreach (var h in handles) h.WaitOne();
```

`handles[0]`을 소비한 직후 `handles[1]`에서 영영 막힐 수 있고, 그동안 다른 스레드는 `handles[0]`이 이미 소비된 것을 보고 다른 판단을 내린다. `AutoResetEvent`처럼 소비되는 핸들을 여러 스레드가 공유할 때 이 차이가 데드락과 신호 유실로 이어진다.

> **⚠️ 배열 원소는 64개를 넘을 수 없다**
>
> `WaitAny`와 `WaitAll`에 넘기는 배열은 원소가 **64개 이하**여야 한다. 초과하면 **`System.NotSupportedException`** 이 발생한다. Win32 `WaitForMultipleObjectsEx`의 `MAXIMUM_WAIT_OBJECTS` 제약이 그대로 드러난 것이다.
>
> 게다가 배열에 **중복된 핸들**이 들어 있으면 `WaitAll`은 실패한다(같은 객체를 두 번 기다릴 수 없다). 동적으로 배열을 만드는 코드라면 중복 제거를 잊지 마라.
>
> "핸들이 64개를 넘을 수도 있다"는 시점에서 이미 설계를 다시 봐야 한다. 그 규모의 완료 대기는 `CountdownEvent`(49.3절)나 `Task.WhenAll`(46.9절)의 영역이다.

### STA 스레드에서는 `WaitAll`과 `SignalAndWait`이 안 된다

이 제약은 레거시 COM 아키텍처에서 온다. **`WaitAll`과 `SignalAndWait`은 호출 스레드가 다중 스레드 아파트먼트(MTA)에 있을 것을 요구한다.**

문제는 **WPF와 Windows Forms 애플리케이션의 주 스레드가 단일 스레드 아파트먼트(STA)** 라는 데 있다. UI 주 스레드에서 `WaitHandle.WaitAll`을 부르면 **`NotSupportedException`** 이 발생한다. 그리고 스레드를 MTA로 바꾸면(주 메서드의 `[STAThread]`를 제거하면) 클립보드 같은 COM 상호 운용 기능이 동작하지 않는다 — 원천 자료의 표현대로 MTA는 상호 운용에 가장 부적합한 모델이다.

> **📌 STA 스레드는 대기 중에도 메시지를 펌프한다**
>
> COM STA 스레드가 막히면, 내부적으로 깨어나 메시지를 펌프하는 경우가 있다. 다른 스레드가 보낸 Windows 메시지를 처리하려고 깨어나는 것이다. COM 상호 운용을 지원하기 위한 동작이며 대부분의 애플리케이션에서는 오히려 좋은 일이다.
>
> 그런데 **그 메시지를 처리하는 도중에 코드가 또 다른 동기화 잠금을 잡으면 데드락이 발생할 수 있다.** 하이브리드 잠금(48.12절)도 내부적으로 이 메서드들을 호출하므로 같은 위험을 공유한다. UI 스레드에서 블로킹 대기를 하지 말아야 할 이유가 하나 더 있는 셈이다(47.14절, 51.5절).

**대안은 무엇인가.** `SignalAndWait`의 큐 새치기 의미론이 정말로 필요한 경우는 드물다 — 뒤에 나올 랑데부 예제라면 첫 번째 핸들에 `Set`을 부르고 두 번째 핸들에 `WaitOne`을 부르는 것으로 충분하다. `WaitAny`/`WaitAll`은 **원자성이 필요 없다면** 대기 핸들을 태스크로 바꿔 `Task.WhenAny`/`Task.WhenAll`을 쓰면 된다(46.9절). 원자성이 반드시 필요하다면 남는 선택지는 가장 낮은 수준으로 내려가는 것 — `Monitor`의 `Wait`/`Pulse`로 논리를 직접 쓰는 것이다(49.7절).

### `SignalAndWait`과 랑데부

`SignalAndWait`은 **한 대기 핸들에 `Set`을 부르고 곧바로 다른 대기 핸들에 `WaitOne`을 부른다.** 첫 핸들을 신호한 뒤 두 번째 핸들의 대기 큐 **맨 앞으로 끼어든다.** 이것이 성공 확률을 높여 주지만, 원천 자료가 분명히 밝히듯 **연산 전체가 진짜로 원자적이지는 않다.**

한 신호를 다른 신호와 "맞바꾸는" 연산으로 생각하면 된다. 두 스레드를 같은 시점에 **랑데부(rendezvous)** 시키는 데 쓸 수 있다.

```csharp
// 스레드 1
WaitHandle.SignalAndWait(wh1, wh2);

// 스레드 2
WaitHandle.SignalAndWait(wh2, wh1);
```

`AutoResetEvent`든 `ManualResetEvent`든 상관없이 동작한다.

> **⚠️ 랑데부에 `SignalAndWait`을 쓰는 것은 위험한 관용구다**
>
> 세 가지 이유로 그렇다.
>
> 첫째, **STA에서 동작하지 않는다.** UI 스레드가 참여하는 순간 `NotSupportedException`이다.
>
> 둘째, **참가자가 셋 이상이면 확장되지 않는다.** 두 스레드의 짝짓기 전용이다. 셋 이상이면 `Barrier`(49.6절)를 써야 한다.
>
> 셋째, **한쪽이 예외로 죽으면 다른 쪽이 영원히 기다린다.** `SignalAndWait`에는 타임아웃 오버로드가 있지만, 타임아웃이 발생하면 **이미 첫 번째 핸들에 신호는 보낸 상태**다. 상대는 통과했는데 나는 못 통과한 비대칭 상태가 되고, 그것을 되돌릴 방법이 없다.
>
> 두 스레드 랑데부가 정말 필요하면 **`Barrier(2)`** 를 써라. 훨씬 안전하고 의도가 명확하다.

### 대기 핸들을 태스크로 바꾸기

대기 핸들 위에서 스레드를 막는 대신, **연속(continuation)을 붙일 수 있다.** `ThreadPool.RegisterWaitForSingleObject`가 그 수단이다.

```csharp
public static RegisteredWaitHandle RegisterWaitForSingleObject(
    WaitHandle waitObject,
    WaitOrTimerCallback callBack,
    object state,
    int millisecondsTimeOutInterval,     // -1 이면 타임아웃 없음
    bool executeOnlyOnce);               // true 면 1회성, false 면 반복

public delegate void WaitOrTimerCallback(object state, bool timedOut);
```

대기 핸들이 신호되면(또는 타임아웃이 지나면) 델리게이트가 **풀 스레드에서** 실행된다.

```csharp
var starter = new ManualResetEvent(false);

RegisteredWaitHandle reg = ThreadPool.RegisterWaitForSingleObject(
    starter, Go, "어떤 데이터", -1, true);

Thread.Sleep(5000);
Console.WriteLine("작업자에게 신호를 보낸다...");
starter.Set();

Console.ReadLine();
reg.Unregister(starter);          // 끝났으면 정리한다

void Go(object data, bool timedOut)
{
    Console.WriteLine("시작 - " + data);
    // 작업 수행...
}

// 출력:
// (5초 지연)
// 작업자에게 신호를 보낸다...
// 시작 - 어떤 데이터
```

콜백을 등록한 뒤에는 **`Unregister`를 호출해 관리되지 않는 핸들을 해제해야 한다.**

> **⚠️ 한 대기 핸들에 `RegisterWaitForSingleObject`는 한 번만**
>
> 원천 자료의 경고 그대로다. **하나의 대기 핸들에 대해 이 메서드를 신뢰성 있게 호출할 수 있는 것은 한 번뿐이다.** 같은 대기 핸들에 다시 호출하면 간헐적 실패가 발생한다 — 신호되지 않은 대기 핸들이 마치 신호된 것처럼 콜백을 발화시킨다.
>
> 이 제약 때문에 **(`Slim`이 아닌) 대기 핸들은 비동기 프로그래밍에 부적합하다.** 새 코드에서 신호가 필요하면 대기 핸들 대신 `TaskCompletionSource`(46.5절)나 `Channel`(51.1절)로 설계해라.

이 메서드와 `TaskCompletionSource`를 조합하면 **어떤 대기 핸들이든 `Task`로 바꿀 수 있다.**

```csharp
public static Task<bool> ToTask(this WaitHandle handle, int timeoutMs = -1)
{
    var tcs = new TaskCompletionSource<bool>(
        TaskCreationOptions.RunContinuationsAsynchronously);

    RegisteredWaitHandle registration = null;
    registration = ThreadPool.RegisterWaitForSingleObject(
        handle,
        (state, timedOut) =>                     // timedOut 이 true 면 타임아웃
        {
            tcs.TrySetResult(!timedOut);
            registration?.Unregister(null);      // 관리되지 않는 핸들 정리
        },
        null, timeoutMs, executeOnlyOnce: true);

    return tcs.Task;
}
```

이제 대기 핸들이 `await` 가능해진다.

```csharp
var wh = new ManualResetEvent(false);

if (await wh.ToTask(5000))
    Console.WriteLine("신호를 받았다");
else
    Console.WriteLine("타임아웃");
```

그리고 여러 핸들을 태스크로 바꾸면 `Task.WhenAny`/`Task.WhenAll`을 쓸 수 있다 — **원자성은 잃지만 STA 제약도 64개 제약도 사라진다.**

```csharp
Task<bool>[] tasks = handles.Select(h => h.ToTask()).ToArray();
await Task.WhenAll(tasks);      // WaitAll 의 비동기 대체 (원자성은 없다)
```

> **💡 `RunContinuationsAsynchronously`를 빠뜨리지 마라**
>
> 위 코드에서 `TaskCompletionSource`에 `TaskCreationOptions.RunContinuationsAsynchronously`를 넘긴 것은 실수 방지 장치다. 이것이 없으면 `TrySetResult` 호출 시점에 `await` 뒷부분의 연속이 **그 자리에서 동기적으로** 실행된다. 그 자리가 어디인가 하면 **스레드 풀의 대기 전용 스레드**다. 연속이 오래 걸리면 그 스레드가 다른 대기 핸들의 감시를 못 하게 된다.
>
> 46.5절에서 다룬 그 문제이고, `TaskCompletionSource`를 쓰는 모든 어댑터에 똑같이 적용된다.

### 블로킹 대기에서 비동기로

이 절 전체를 한 줄로 요약하면 이렇다. **`WaitAny`·`WaitAll`·`SignalAndWait`은 관리 코드로 비동기를 쓸 수 없던 시절의 API다.**

| 하고 싶은 일 | 옛 방식 | 현대적 방식 |
|---|---|---|
| 하나라도 끝날 때까지 | `WaitHandle.WaitAny` | `Task.WhenAny`(46.9절) |
| 전부 끝날 때까지 | `WaitHandle.WaitAll` | `Task.WhenAll`(46.9절) |
| 끝나는 대로 하나씩 | 루프 + `WaitAny` + 배열 재구성 | `Task.WhenEach` ※.NET 9 (46.9절) |
| 두 스레드 만나기 | `WaitHandle.SignalAndWait` | `Barrier(2)`(49.6절) |
| 대기 핸들에 콜백 | `RegisterWaitForSingleObject` | 위의 `ToTask` 어댑터 + `await` |
| N개 완료 대기 | `CountdownEvent.Wait` | `Task.WhenAll` |
| 타임아웃 | 각 메서드의 타임아웃 인자 | `CancellationTokenSource(TimeSpan)` (51.4절) |

**`WaitHandle`의 정적 메서드를 새로 쓸 이유는 거의 없다.** 여전히 필요한 경우는 딱 하나 — 네이티브 코드나 레거시 API가 대기 핸들을 돌려주고, 그것을 관리 코드 세계로 끌어와야 할 때다. 그때도 목적지는 `ToTask` 어댑터이지 블로킹 `WaitOne`이 아니다.

## 49.6 `Barrier` 클래스 — 단계적 병렬 작업

### 여러 스레드를 같은 지점에 모으는 장벽

`Barrier`는 **스레드 실행 장벽(thread execution barrier)** 을 구현한다. 여러 스레드가 시간상 한 지점에서 랑데부하게 만드는 것이다.

> **📌 `Thread.MemoryBarrier`와 혼동하지 마라**
>
> 이름이 같은 "배리어"지만 완전히 다른 것이다. `Thread.MemoryBarrier`(48.3절)는 **명령어 재배치를 막는 메모리 펜스**이고, `System.Threading.Barrier`는 **스레드들을 만나게 하는 동기화 구조**다. 하나는 CPU에게 말하고 하나는 스레드에게 말한다.

`Barrier`는 매우 빠르고 효율적이며, 내부적으로 `Wait`/`Pulse`(49.7절)와 스핀락 위에 구현되어 있다. 대기는 `ManualResetEventSlim`으로 처리한다.

```csharp
public class Barrier : IDisposable
{
    public Barrier(int participantCount);
    public Barrier(int participantCount, Action<Barrier> postPhaseAction);

    public long AddParticipant();                        // 참가자 1명 추가
    public long AddParticipants(int participantCount);
    public void RemoveParticipant();
    public void RemoveParticipants(int participantCount);

    public void SignalAndWait();
    public bool SignalAndWait(int millisecondsTimeout);
    public void SignalAndWait(CancellationToken cancellationToken);
    public bool SignalAndWait(int millisecondsTimeout, CancellationToken cancellationToken);

    public long CurrentPhaseNumber      { get; }         // 진행 중인 단계(0부터)
    public int  ParticipantCount        { get; }         // 참가자 수
    public int  ParticipantsRemaining   { get; }         // SignalAndWait 을 아직 안 부른 수

    public void Dispose();
}
```

사용법은 두 단계다.

1. **랑데부에 참여할 스레드 수를 지정해 생성한다.** 나중에 `AddParticipants`/`RemoveParticipants`로 바꿀 수 있다.
2. **각 스레드가 랑데부하고 싶은 지점에서 `SignalAndWait`을 부른다.**

`Barrier(3)`으로 만들면 `SignalAndWait`은 그 메서드가 세 번 호출될 때까지 막는다. 그런 다음 **처음부터 다시 시작한다** — `SignalAndWait`을 다시 부르면 또 세 번 호출될 때까지 막힌다. 이렇게 각 스레드가 다른 스레드들과 **보조를 맞춘다.**

```csharp
var barrier = new Barrier(3);

new Thread(Speak).Start();
new Thread(Speak).Start();
new Thread(Speak).Start();

void Speak()
{
    for (int i = 0; i < 5; i++)
    {
        Console.Write(i + " ");
        barrier.SignalAndWait();
    }
}

// 출력:
// 0 0 0 1 1 1 2 2 2 3 3 3 4 4 4
```

세 스레드가 각자 0~4를 쓰는데, `0 0 1 1 1 0 ...` 같은 뒤섞임이 절대 일어나지 않는다. 모든 스레드가 같은 `i`를 쓴 뒤에야 다음 값으로 넘어가기 때문이다.

### 단계 후 액션(post-phase action)

정말 유용한 기능은 생성자에 **단계 후 액션**을 지정할 수 있다는 것이다. `SignalAndWait`이 n번 호출된 뒤, **그러나 스레드들이 풀려나기 전에** 실행되는 델리게이트다.

```csharp
static Barrier _barrier = new Barrier(3, barrier => Console.WriteLine());
```

이렇게 만들면 앞 예제의 출력이 이렇게 바뀐다.

```text
0 0 0
1 1 1
2 2 2
3 3 3
4 4 4
```

```text
   단계 0                     단계 후 액션            단계 1
 ┌──────────┐               ┌────────────┐        ┌──────────┐
 │ T1 작업   │──SignalAndWait─┐             │        │ T1 작업   │
 ├──────────┤               │             │        ├──────────┤
 │ T2 작업   │──SignalAndWait─┼──▶ 마지막   ─┼──모두──▶│ T2 작업   │
 ├──────────┤               │   스레드가   │  해제   ├──────────┤
 │ T3 작업   │──SignalAndWait─┘   액션 실행  │        │ T3 작업   │
 └──────────┘               └────────────┘        └──────────┘
                     ▲ 이 구간에는 아무 참가자도 실행 중이 아니다
```

단계 후 액션은 **각 작업 스레드의 데이터를 합치는 데** 유용하다. 그동안 모든 작업자가 막혀 있으므로 **선점을 걱정할 필요가 없다** — 락 없이 공유 데이터를 안전하게 읽고 쓸 수 있다.

액션을 실행하는 것은 **마지막으로 `SignalAndWait`을 호출한 스레드**다. 별도의 스레드가 만들어지지 않으며, 액션에 전달되는 `Barrier` 인자로 `CurrentPhaseNumber`를 읽어 지금이 몇 단계인지 알 수 있다.

### 단계적 시뮬레이션 예제

`Barrier`가 실제로 필요한 문제는 **격자를 반복적으로 갱신하는 시뮬레이션**이다. 열 확산, 세포 자동자, 물리 시뮬레이션이 전형적이다. 모든 셀이 **이전 단계의 값**을 보고 새 값을 계산해야 하므로, 어떤 스레드도 남들보다 앞서 나가면 안 된다.

```csharp
class HeatDiffusion
{
    const int Size = 1000, Steps = 100;
    static readonly double[,] _current = new double[Size, Size];
    static readonly double[,] _next    = new double[Size, Size];
    static Barrier _barrier;

    static void Run(int workerCount)
    {
        // 아무도 실행 중이 아닐 때 버퍼를 교환한다 — 잠금이 필요 없다
        _barrier = new Barrier(workerCount, _ => Array.Copy(_next, _current, _next.Length));

        int rows = Size / workerCount;
        var threads = new Thread[workerCount];

        for (int w = 0; w < workerCount; w++)
        {
            int start = w * rows;
            int end = (w == workerCount - 1) ? Size : start + rows;

            threads[w] = new Thread(() =>
            {
                for (int step = 0; step < Steps; step++)
                {
                    for (int r = Math.Max(start, 1); r < Math.Min(end, Size - 1); r++)
                        for (int c = 1; c < Size - 1; c++)
                            _next[r, c] = (_current[r - 1, c] + _current[r + 1, c] +
                                           _current[r, c - 1] + _current[r, c + 1]) / 4;

                    _barrier.SignalAndWait();     // 모두가 이 단계를 끝낼 때까지
                }
            });
            threads[w].Start();
        }

        foreach (var t in threads) t.Join();
    }
}
```

이 코드에서 `Barrier`가 없으면 어떤 작업자가 다음 단계로 먼저 넘어가 **아직 갱신 중인 이웃 행**을 읽어 버린다. 결과가 조용히 틀려진다.

CLR의 서버 GC가 정확히 이런 구조로 동작한다. 원천 자료의 설명 그대로다 — 코어당 하나씩 GC 스레드를 만들고, 각 스레드가 서로 다른 애플리케이션 스레드의 스택을 걸어 올라가며 힙의 객체를 동시에 마킹한다. 자기 몫을 끝낸 스레드는 다른 스레드가 끝날 때까지 기다려야 한다. 모두가 마킹을 끝내면 그다음 힙의 서로 다른 구역을 동시에 압축하고, 압축을 끝낸 스레드는 또 기다린다. 모두가 압축을 끝내면 스택을 다시 걸어 올라가며 루트를 새 위치로 고친다. 이 모든 단계가 끝나야 GC가 완료된 것으로 간주된다.

### 참가자 수를 동적으로 바꾸기

`AddParticipant`/`AddParticipants`는 참가자를 늘리고, `RemoveParticipant`/`RemoveParticipants`는 줄인다. `AddParticipant`는 **추가된 참가자가 참여할 단계 번호**를 반환한다.

```csharp
long phase = _barrier.AddParticipant();
Console.WriteLine($"새 작업자는 단계 {phase}부터 참여한다");
```

원천 자료는 이 기능이 **실무에서 거의 쓰이지 않는다**고 명시한다. 그럴 만한 이유가 있다 — 참가자 수 변경과 `SignalAndWait` 호출 사이의 경합을 관리하기가 매우 어렵기 때문이다.

> **⚠️ 참가자 수를 잘못 세면 영원히 멈춘다**
>
> `Barrier`가 만들어 내는 사고는 거의 전부 **참가자 수 불일치**다.
>
> - 참가자를 3으로 만들었는데 스레드를 2개만 시작하면 → **모두 영원히 대기**한다.
> - 스레드 하나가 루프를 일찍 빠져나가 `SignalAndWait`을 부르지 않으면 → **나머지가 영원히 대기**한다.
> - 스레드 하나가 **예외로 죽으면** → 마찬가지다. 죽은 스레드는 `SignalAndWait`을 부르지 않는다.
>
> 마지막 항목이 가장 위험하다. 작업자 스레드 안에서 던져진 예외는 45.6절에서 본 대로 그 스레드에서 처리되지 않으면 프로세스를 종료시키지만, `try`/`catch`로 조용히 삼키는 코드가 흔하다. 그러면 프로세스는 살아 있고 나머지 참가자들만 영원히 막힌다.
>
> **방어책은 `finally`에서 `RemoveParticipant`를 부르는 것**이다.
>
> ```csharp
> try
> {
>     for (int step = 0; step < Steps; step++)
>     {
>         DoWork(step);
>         _barrier.SignalAndWait(ct);
>     }
> }
> catch (Exception ex)
> {
>     _errors.Add(ex);                       // 예외를 모아 둔다
>     throw;
> }
> finally
> {
>     _barrier.RemoveParticipant();          // 남은 참가자들이 진행할 수 있게 한다
> }
> ```
>
> 그리고 **타임아웃 오버로드를 쓰는 습관**을 들여라. `SignalAndWait(TimeSpan.FromSeconds(30))`이 `false`를 반환하면 무언가 잘못된 것이고, 영원히 멈춘 프로세스보다 진단 가능한 실패가 훨씬 낫다.

### `BarrierPostPhaseException`

단계 후 액션이 예외를 던지면 어떻게 되는가. 그 예외는 그대로 새어 나가지 않는다. 대신 **`BarrierPostPhaseException`으로 감싸여** 그 단계에 참여한 **모든 참가자에게** 던져진다. 원래 예외는 `InnerException`에 담긴다.

```csharp
var barrier = new Barrier(2, _ => throw new InvalidOperationException("합치기 실패"));

void Worker()
{
    try
    {
        barrier.SignalAndWait();
    }
    catch (BarrierPostPhaseException ex)
    {
        // ex.InnerException 이 InvalidOperationException
        Console.WriteLine($"단계 후 액션이 실패했다: {ex.InnerException?.Message}");
    }
}
```

> **⚠️ 단계 후 액션의 예외는 배리어 전체를 오염시킨다**
>
> 참가자 하나가 던진 예외가 아니라 **단계 후 액션이 던진 예외**가 이 경로를 탄다. 그리고 그 예외를 **모든 참가자가 받는다.** 참가자 코드가 `BarrierPostPhaseException`을 처리하지 않으면 여러 스레드가 동시에 처리되지 않은 예외로 죽는다.
>
> 그래서 **단계 후 액션은 절대 예외를 던지지 않도록 작성해야 한다.** 액션 안에서 실패할 수 있는 일(파일 쓰기, 네트워크 호출)을 하지 마라. 액션의 역할은 메모리 안의 데이터를 합치고 다음 단계를 준비하는 것으로 한정해라.

### `Barrier` vs 다른 선택지

| 요구 | `Barrier` | 대안 |
|---|---|---|
| N단계 반복, 매 단계 동기화 | **적합** | — |
| 1회성 완료 대기 | 과하다 | `CountdownEvent`(49.3절), `Task.WhenAll`(46.9절) |
| 두 스레드 랑데부 1회 | 적합 (`Barrier(2)`) | `SignalAndWait`(권장하지 않음) |
| 단계마다 태스크를 새로 만들어도 되는 경우 | 필요 없다 | 단계별 `await Task.WhenAll` |
| 참가자 수가 계속 변한다 | 어렵다 | `Channel`(51.1절) 기반 파이프라인 |

원천 자료의 평가는 냉정하다. **`Barrier`는 매우 드문 문제를 풀기 위해 설계되었고, 쓸 일이 있을 가능성은 낮다.** 그리고 이 클래스가 푸는 문제 상당수는 46장의 `Task`로 훨씬 낫게 풀린다 — 여러 `Task`를 만들어 한 단계를 처리하게 하고, 전부 완료되면 다음 단계의 `Task`들로 이어 가면 된다.

```csharp
for (int step = 0; step < Steps; step++)           // Barrier 없는 단계적 병렬 처리
{
    await Task.WhenAll(partitions.Select(p => Task.Run(() => Process(p, step))));
    Merge(step);                                   // 단계 후 액션에 해당한다
}
```

> **💡 `Barrier`가 이기는 유일한 조건**
>
> 위의 `Task.WhenAll` 방식은 **매 단계마다 태스크를 새로 만들고 스케줄링한다.** 단계가 수만 번 반복되고 각 단계의 작업이 마이크로초 단위라면, 그 스케줄링 오버헤드가 계산 시간을 압도한다.
>
> `Barrier`는 스레드를 **그대로 유지한 채** 동기화만 한다. 스레드 생성·스케줄링 비용이 단계마다 들지 않는다. 그래서 **"고정된 수의 전용 스레드가 아주 많은 단계를 반복하는 계산 집약적 시뮬레이션"** 이 `Barrier`의 자리다. 그 외에는 `Task`가 낫다.

## 49.7 조건 변수 패턴

### 문제 — "복잡한 조건이 참이 될 때까지"

지금까지 본 신호 구조는 전부 **미리 정해진 형태의 신호**만 전달한다. `AutoResetEvent`는 "한 명 통과", `CountdownEvent`는 "N번 완료", `Barrier`는 "전원 도착"이다.

그런데 실제 요구는 훨씬 자유로운 형태다. **"큐에 항목이 있고, 동시에 처리 중인 항목이 3개 미만이고, 셧다운 플래그가 꺼져 있을 때까지 기다린다."** 이런 복합 조건을 이벤트 하나로 표현할 방법은 없다.

한 가지 방법은 **스핀**이다 — 잠금을 잡고 조건을 검사하고 놓고를 반복한다. 그런데 이것은 CPU 시간을 낭비하고, 잠금을 잡았다 놨다 하는 사이에 조건을 구성하는 여러 변수를 **원자적으로 검사할 수 없다**는 문제도 있다.

정답은 **조건 변수 패턴(condition variable pattern)** 이다. `Monitor` 클래스의 세 메서드가 이 패턴을 제공한다(48.5절에서 API만 소개했다).

```csharp
public static class Monitor
{
    public static bool Wait(object obj);
    public static bool Wait(object obj, int millisecondsTimeout);
    public static bool Wait(object obj, TimeSpan timeout);
    public static void Pulse(object obj);
    public static void PulseAll(object obj);
}
```

### `Wait`의 정확한 의미론

`Monitor.Wait(obj)`가 하는 일은 세 단계이며, **그 순서와 원자성이 이 패턴의 전부**다.

```text
   호출 전: 이 스레드가 obj 의 잠금을 쥐고 있다 (반드시!)

   ┌────────────────────────────────────────────────────────────┐
   │ 1. 잠금을 놓는다        ← 다른 스레드가 들어와 조건을 바꿀 수 │
   │                           있게 된다                          │
   │ 2. 이 스레드를 obj 의 "대기 큐"에 넣고 블로킹한다             │
   │    ── 여기서 Pulse / PulseAll 또는 타임아웃을 기다린다 ──      │
   │ 3. 깨어나면 잠금을 다시 획득한다   ← 여기서 또 막힐 수 있다!  │
   └────────────────────────────────────────────────────────────┘

   반환 후: 이 스레드가 다시 obj 의 잠금을 쥐고 있다
```

1번과 2번이 **원자적으로** 일어나는 것이 핵심이다. "잠금을 놓았는데 아직 대기 큐에 들어가기 전"이라는 틈이 있다면, 바로 그 순간 다른 스레드가 조건을 바꾸고 `Pulse`를 불러 신호가 사라진다. 커널이 이 두 동작을 하나로 묶어 준다.

3번도 중요하다. **`Wait`에서 돌아왔다는 것은 잠금을 다시 쥐었다는 뜻이다.** 그러므로 `Wait` 호출 전후로 잠금 상태가 같고, `lock` 블록 안에서 `Wait`을 불러도 `Monitor.Exit`의 짝이 어긋나지 않는다.

`Wait`은 **`bool`을 반환한다** — 타임아웃 오버로드에서 신호를 받았으면 `true`, 타임아웃이면 `false`다.

> **⚠️ 잠금을 쥐지 않고 `Wait`/`Pulse`를 부르면 예외다**
>
> `Monitor.Wait`·`Pulse`·`PulseAll`은 전부 **그 객체의 잠금을 쥐고 있는 스레드만** 부를 수 있다. 그렇지 않으면 **`SynchronizationLockException`** 이 발생한다.
>
> 그리고 48.5절에서 본 대로, 어떤 객체에 `Wait`/`Pulse`를 쓰는 순간 그 객체의 잠금은 **반드시 팻 락(동기화 블록)으로 팽창한다.** 객체 헤더의 씬 락으로는 대기 큐를 표현할 수 없기 때문이다.

### 정석 패턴 — 반드시 `while` 루프

원천 자료가 제시하는 표준 형태는 이렇다.

```csharp
internal sealed class ConditionVariablePattern
{
    private readonly object m_lock = new object();
    private bool m_condition = false;

    public void Thread1()
    {
        Monitor.Enter(m_lock);                  // 배타적 잠금 획득

        // 잠금을 쥔 채로 복잡한 조건을 "원자적으로" 검사한다
        while (!m_condition)
        {
            // 조건이 성립하지 않으면 다른 스레드가 바꿔 주기를 기다린다
            Monitor.Wait(m_lock);               // 잠금을 일시적으로 놓는다
        }

        // 조건이 성립했다 — 데이터를 처리한다...

        Monitor.Exit(m_lock);                   // 잠금을 완전히 놓는다
    }

    public void Thread2()
    {
        Monitor.Enter(m_lock);                  // 배타적 잠금 획득

        // 데이터를 처리하고 조건의 상태를 바꾼다...
        m_condition = true;

        // Monitor.Pulse(m_lock);               // 대기자 하나를 깨운다 (잠금이 풀린 뒤)
        Monitor.PulseAll(m_lock);               // 대기자 전부를 깨운다 (잠금이 풀린 뒤)

        Monitor.Exit(m_lock);                   // 잠금 해제
    }
}
```

**`if`가 아니라 `while`이어야 하는 이유가 이 패턴에서 가장 자주 틀리는 지점**이다. 이유가 셋 있다.

**첫째, 깨어난 것과 잠금을 얻은 것 사이에 시간이 있다.** `Pulse`가 대기자를 깨워도 그 스레드는 즉시 실행되지 않는다. 신호를 보낸 스레드가 `Monitor.Exit`으로 잠금을 놓아야 비로소 잠금을 얻고, 그사이에 **제3의 스레드**가 잠금을 얻어 조건을 다시 거짓으로 만들 수 있다.

**둘째, `PulseAll`은 대기자를 전부 깨우지만 잠금은 하나뿐이다.** 세 스레드가 깨어나도 잠금을 얻는 것은 한 번에 하나다. 첫 번째 스레드가 조건이 표현하는 자원(예: 큐의 항목 하나)을 소비하고 나면, 두 번째와 세 번째가 잠금을 얻었을 때는 조건이 이미 거짓이다.

**셋째, 가짜 깨어남(spurious wakeup)이 있을 수 있다.** 하부 운영체제의 조건 변수 구현은 `Pulse` 없이도 대기자가 깨어나는 것을 허용한다 — POSIX 조건 변수의 명시적 계약이며, 관리 코드에서도 이 가능성에 기대지 않는 편이 안전하다.

> **⚠️ `if (!조건) Monitor.Wait(...)` 는 언젠가 반드시 깨진다**
>
> `while`을 `if`로 바꾼 코드는 대부분의 테스트를 통과한다. 대기자가 하나뿐이고 프로듀서가 하나뿐이면 잘 돌아가기 때문이다. **대기자가 둘이 되는 순간** 조건이 거짓인데도 진행하는 스레드가 생기고, 빈 큐에서 `Dequeue`를 불러 `InvalidOperationException`이 나거나 더 나쁘게는 조용히 잘못된 데이터를 처리한다.
>
> 규칙에는 예외가 없다. **`Monitor.Wait`은 언제나 조건을 재검사하는 `while` 루프 안에 있어야 한다.**

### `Pulse` vs `PulseAll`

| | `Pulse` | `PulseAll` |
|---|---|---|
| 깨우는 대상 | 가장 오래 기다린 대기자 **하나** | 대기 중인 **전부** |
| 비용 | 낮다 | 대기자 수에 비례 (컨텍스트 스위치 폭풍) |
| 안전성 | **조건이 까다롭다** | 언제나 안전하다 |
| 언제 옳은가 | 모든 대기자가 **같은 조건**을 기다리고, 신호 하나가 정확히 대기자 하나를 진행시킬 때 | 그 외 전부 |

`Pulse`가 위험한 이유는 **잘못된 대기자를 깨울 수 있기 때문**이다. 큐가 가득 차기를 기다리는 프로듀서와 비기를 기다리는 컨슈머가 같은 잠금 객체에서 대기하고 있다고 하자. `Pulse`가 프로듀서를 깨웠는데 실제로 바뀐 조건은 컨슈머의 것이었다면, 프로듀서는 조건이 거짓이라 다시 `Wait`으로 돌아가고 **컨슈머는 영영 깨어나지 않는다.** 신호 하나가 소실된 것이다.

> **💡 확신이 없으면 `PulseAll`**
>
> `Pulse`는 성능 최적화이고 `PulseAll`은 정확성의 기본값이다. 원천 자료도 `PulseAll` 쪽을 활성 코드로 두고 `Pulse`를 주석 처리해 두었다. 깨어난 스레드들이 조건을 재검사하고 대부분 다시 잠드는 것은 **CPU 시간의 낭비이지 논리적 오류가 아니다.** 반대로 `Pulse`의 실수는 무한 대기다. 대기자가 수십 명 이상이고 그것이 실측으로 병목일 때만 `Pulse`를 검토해라.

### 스레드 안전한 큐 만들기

원천 자료의 예제는 여러 스레드가 항목을 넣고 빼는 큐다. 항목이 없으면 꺼내려는 스레드가 막힌다.

```csharp
internal sealed class SynchronizedQueue<T>
{
    private readonly object m_lock = new object();
    private readonly Queue<T> m_queue = new Queue<T>();

    public void Enqueue(T item)
    {
        Monitor.Enter(m_lock);

        // 항목을 넣은 뒤 대기자를 깨운다
        m_queue.Enqueue(item);
        Monitor.PulseAll(m_lock);

        Monitor.Exit(m_lock);
    }

    public T Dequeue()
    {
        Monitor.Enter(m_lock);

        // 큐가 비어 있는 동안(=조건) 계속 기다린다
        while (m_queue.Count == 0)
            Monitor.Wait(m_lock);

        // 항목을 꺼내 반환한다
        T item = m_queue.Dequeue();
        Monitor.Exit(m_lock);
        return item;
    }
}
```

**이 코드에는 실전에서 반드시 필요한 것이 빠져 있다.** 예외 안전성(`try`/`finally`), 종료 신호, 용량 제한, 취소가 전부 없다. 그것들을 넣으면 코드는 이렇게 자란다.

```csharp
public sealed class BoundedQueue<T>
{
    private readonly object _lock = new object();
    private readonly Queue<T> _queue = new Queue<T>();
    private readonly int _capacity;
    private bool _completed;

    public BoundedQueue(int capacity) => _capacity = capacity;

    public bool TryEnqueue(T item)
    {
        lock (_lock)
        {
            while (_queue.Count >= _capacity && !_completed)   // 가득 찼으면 기다린다
                Monitor.Wait(_lock);

            if (_completed) return false;

            _queue.Enqueue(item);
            Monitor.PulseAll(_lock);      // 컨슈머와 프로듀서 모두 깨운다
            return true;
        }
    }

    public bool TryDequeue(out T item)
    {
        lock (_lock)
        {
            while (_queue.Count == 0 && !_completed)           // 비었으면 기다린다
                Monitor.Wait(_lock);

            if (_queue.Count == 0) { item = default!; return false; }   // 완료 + 빈 큐

            item = _queue.Dequeue();
            Monitor.PulseAll(_lock);
            return true;
        }
    }

    public void CompleteAdding()
    {
        lock (_lock)
        {
            _completed = true;
            Monitor.PulseAll(_lock);      // 대기 중인 모두를 깨워 종료를 알린다
        }
    }
}
```

여기서 배울 점이 몇 가지 있다.

- **`lock` 문을 쓰면 `try`/`finally`가 공짜다.** `Monitor.Enter`/`Exit`를 직접 쓰는 원천 예제는 본문에서 예외가 나면 잠금이 새어 나간다(48.5절).
- **종료 조건이 대기 조건에 포함되어야 한다.** `while (_queue.Count == 0)` 만으로는 `CompleteAdding` 이후에도 컨슈머가 영원히 잠들어 있다.
- **`PulseAll`을 두 방향 모두에서 부른다.** 이 큐에는 두 종류의 대기자(가득 차서 기다리는 프로듀서, 비어서 기다리는 컨슈머)가 같은 잠금에서 대기한다. 그러므로 `Pulse`는 위험하고 `PulseAll`이어야 한다.

### 그래서 이 패턴을 직접 쓰지 마라

`BoundedQueue<T>`를 완성했다면 축하할 일이지만, **그것을 프로덕션 코드에 넣을 이유는 없다.** BCL에 이미 있다.

| 필요 | BCL 타입 | 절 |
|---|---|---|
| 블로킹 프로듀서/컨슈머 큐 | `BlockingCollection<T>` | 50.11 |
| 비동기 프로듀서/컨슈머 큐 | `System.Threading.Channels.Channel<T>` | 51.1 |
| 백프레셔가 있는 큐 | `Channel.CreateBounded<T>` | 51.2 |
| 잠금 없는 동시 컬렉션 | `ConcurrentQueue<T>`, `ConcurrentBag<T>` | 50.10 |
| 비동기 상호 배제 | `SemaphoreSlim.WaitAsync` | 48.11, 51.3 |

조건 변수 패턴이 어려운 이유를 정리하면 이렇다.

| 함정 | 증상 |
|---|---|
| `while` 대신 `if` | 대기자가 둘 이상일 때 조건이 거짓인데 진행한다 |
| `Pulse` 오용 | 신호 유실 → 무한 대기 |
| 종료 조건 누락 | 셧다운 시 컨슈머가 깨어나지 않아 프로세스가 안 끝난다 |
| `Wait` 앞뒤로 잠금을 안 쥠 | `SynchronizationLockException` |
| 잠금 안에서 외부 코드 호출 | 데드락(48.6절) |
| 스레드를 통째로 막는다 | 스레드 풀 기아(46.2절), 확장성 붕괴 |

마지막 항목이 가장 근본적이다. **`Monitor.Wait`은 스레드를 블로킹한다.** 서버 애플리케이션에서 요청마다 스레드가 이 큐에서 대기하면, 요청이 늘수록 스레드 풀이 스레드를 계속 주입하고 결국 컨텍스트 스위치만 하다가 끝난다. **비동기 대응 API가 없다는 것이 이 패턴의 결정적 한계**다 — `await Monitor.WaitAsync` 같은 것은 존재하지 않는다.

> **💡 그럼에도 이 패턴을 배워야 하는 이유**
>
> 세 가지다. 첫째, **`BlockingCollection<T>`·`Channel<T>`·`Barrier`가 전부 이 위에 지어져 있다.** 그것들의 동작을 이해하려면 이 계층을 알아야 한다. 둘째, **BCL이 제공하지 않는 복합 조건**을 만나는 날이 온다 — "큐에 항목이 있고, 워커가 여유가 있고, 레이트 리밋 예산이 남았을 때"는 표준 컬렉션으로 표현되지 않는다. 셋째, **덤프 분석**에서 `!syncblk`이 보여 주는 대기 큐를 읽으려면 이 의미론을 알아야 한다(48.8절).
>
> 다만 그 셋 중 어느 것도 "그러니 직접 쓰라"는 뜻이 아니다. **이해는 하되 쓰지는 마라.**

## 49.8 스레드 로컬 저장소 — `[ThreadStatic]`, `ThreadLocal<T>`, `GetData`/`SetData`

### 반대 방향의 해법

이 장의 앞 일곱 절과 48장 전체가 **공유 상태를 어떻게 안전하게 나눠 쓸 것인가**를 다뤘다. 이 절은 정반대 질문을 던진다. **애초에 나눠 쓰지 않으면 안 되나?**

48.1절의 두 조건을 다시 보자 — 동기화가 필요하려면 (1) 둘 이상의 실행 흐름이 같은 상태에 접근하고 (2) 그중 최소 하나가 쓴다. **스레드 로컬 저장소(TLS, thread local storage)** 는 1번 조건을 깨는 도구다. 전역 변수처럼 이름 하나로 접근하지만 **데이터는 스레드마다 따로 저장된다.** 값에 접근할 수 있는 것은 연결된 스레드뿐이므로 동기화 문제가 사라진다.

지역 변수도 같은 일을 하지만 **수명이 짧다.** TLS의 주된 용도는 원천 자료의 표현으로 **"대역 외(out-of-band) 데이터"** — 실행 경로의 인프라를 떠받치는 데이터다. 메시징·트랜잭션·보안 토큰 같은 것들. 이런 데이터를 매개변수로 넘기면 지저분하고 남의 메서드에는 전달할 수도 없다. 그렇다고 일반 정적 필드에 두면 모든 스레드가 공유한다.

두 번째 용도는 **병렬 코드 최적화**다. 각 스레드가 스레드 안전하지 않은 객체의 자기 판본을 잠금 없이 배타적으로 쓸 수 있고, 메서드 호출 사이에 그 객체를 다시 만들 필요도 없다.

.NET에서 TLS를 쓰는 방법은 네 가지다.

| 방법 | 형태 | 평가 |
|---|---|---|
| `[ThreadStatic]` | 정적 필드에 특성 | 가장 빠르다. 정적 필드에만 |
| `ThreadLocal<T>` | 스레드 정적 필드를 감싼 클래스 | 편리하다. 인스턴스 필드에도 |
| `Thread.GetData`/`SetData` | `LocalDataStoreSlot` 기반 | **구형.** 새 코드에서 쓰지 마라 |
| `AsyncLocal<T>` | 논리적 호출 흐름 기반 | TLS가 아니다 — 49.9절 |

앞의 셋은 **스레드에 값을 묶고**, 마지막 하나는 **논리적 호출 흐름에 값을 묶는다.** 이 차이가 `async` 코드에서 결정적이다.

### `[ThreadStatic]`과 `ThreadLocal<T>` — 기본은 45.5절

두 구조의 문법·초기화 함정·성능 비교·메모리 누수 시나리오는 45.5절에서 이미 상세히 다뤘다. 여기서는 그 결론만 표로 옮기고 넘어간다.

| 항목 | `[ThreadStatic]` | `ThreadLocal<T>` |
|---|---|---|
| 선언 위치 | **정적 필드에만** (인스턴스 필드에 붙이면 아무 일도 안 한다) | 정적·인스턴스 필드 모두 |
| 필드 이니셜라이저 | **정적 생성자를 실행한 스레드에서만 한 번** 실행된다 | 해당 없음(팩터리 사용) |
| 다른 스레드의 초기값 | 타입의 기본값(`0`, `null`) | 값 팩터리가 만든 값 |
| 지연 초기화 | 직접 구현해야 한다 | `Value` 첫 접근 시 자동 |
| 모든 값 순회 | 불가 | `trackAllValues: true` + `Values` |
| 값이 만들어졌는지 확인 | 불가(기본값과 구분 안 됨) | **`IsValueCreated`** |
| 폐기 | 불필요 | **`IDisposable` — 반드시 폐기** |
| 접근 비용(원천 벤치마크) | 약 0.2ns | 약 5~8ns |

> **⚠️ `[ThreadStatic]` 필드에 이니셜라이저를 쓰면 조용히 틀린다**
>
> 45.5절에서 본 그 함정이다. `[ThreadStatic] static int _x = 44;` 라고 쓰면 **타입을 처음 사용한 스레드만 44를 보고 나머지 스레드는 전부 0을 본다.** 컴파일 경고도 없고 예외도 없다. 다시 강조할 만한 가치가 있는 함정이다.
>
> 지연 초기화 속성으로 감싸는 것이 정석이다.
>
> ```csharp
> [ThreadStatic] private static int? _threadStaticData;
>
> public static int ThreadStaticData
> {
>     get
>     {
>         if (_threadStaticData == null) _threadStaticData = 44;
>         return _threadStaticData.Value;
>     }
> }
> ```

`ThreadLocal<T>`에서 45.5절이 다루지 않은 멤버 두 개를 짚어 둔다.

```csharp
var cache = new ThreadLocal<ExpensiveThing>(() => new ExpensiveThing());

if (cache.IsValueCreated)            // 이 스레드에서 팩터리가 이미 돌았는가
    Console.WriteLine("캐시 적중");

foreach (var v in cache.Values)      // trackAllValues: true 인 경우만
    v.Flush();

cache.Dispose();                     // 모든 스레드의 값을 놓아 준다
```

`IsValueCreated`는 **호출한 스레드 기준**이다. 다른 스레드에서 값이 만들어졌는지는 알려 주지 않는다.

> **⚠️ `Values`는 스레드 격리를 스스로 깨뜨리는 문**
>
> `trackAllValues: true`로 만들고 `Values`를 순회하면 **다른 스레드가 자기 것이라고 믿고 잠금 없이 쓰고 있는 객체의 참조를 얻는다.** 그 참조를 스레드 간에 돌려쓰기 시작하면 TLS를 쓴 의미가 사라지고, 원천 자료의 표현대로 "문제로 가는 지름길"이 된다.
>
> `Values`가 안전한 경우는 **모든 작업 스레드가 확실히 끝난 뒤 결과를 집계할 때**뿐이다. 45.5절의 `ThreadLocal<long>` 카운터 벤치마크가 정확히 그 형태다 — `Join`으로 전부 기다린 다음에야 `Values`를 읽는다.

### `Thread.GetData` / `SetData`와 `LocalDataStoreSlot`

세 번째 방법은 `Thread` 클래스의 두 정적 메서드다. **스레드별 "슬롯"** 에 데이터를 저장한다.

```csharp
public sealed class Thread
{
    public static LocalDataStoreSlot GetNamedDataSlot(string name);
    public static LocalDataStoreSlot AllocateDataSlot();
    public static void FreeNamedDataSlot(string name);

    public static object GetData(LocalDataStoreSlot slot);
    public static void SetData(LocalDataStoreSlot slot, object data);
}
```

`Thread.GetData`는 스레드의 격리된 데이터 저장소에서 읽고, `Thread.SetData`는 거기에 쓴다. 두 메서드 모두 슬롯을 식별하는 `LocalDataStoreSlot` 객체를 요구한다. **같은 슬롯 객체를 모든 스레드에서 써도 각 스레드는 서로 다른 값을 본다.**

```csharp
class Test
{
    // 같은 LocalDataStoreSlot 객체를 모든 스레드에서 쓸 수 있다
    LocalDataStoreSlot _secSlot = Thread.GetNamedDataSlot("securityLevel");

    // 이 속성은 스레드마다 다른 값을 갖는다
    int SecurityLevel
    {
        get
        {
            object data = Thread.GetData(_secSlot);
            return data == null ? 0 : (int)data;        // null == 초기화되지 않음
        }
        set { Thread.SetData(_secSlot, value); }
    }
}
```

슬롯에는 두 종류가 있다.

| 종류 | 얻는 법 | 범위 |
|---|---|---|
| **이름 있는 슬롯** | `Thread.GetNamedDataSlot("이름")` | 문자열 이름으로 애플리케이션 전체에서 공유 |
| **이름 없는 슬롯** | `Thread.AllocateDataSlot()` | 반환된 객체를 가진 코드만 |

`Thread.FreeNamedDataSlot`은 이름 있는 슬롯을 **모든 스레드에서** 해제한다. 다만 실제 해제는 그 `LocalDataStoreSlot`에 대한 참조가 전부 범위를 벗어나고 가비지 컬렉션된 뒤에야 일어난다. 슬롯이 필요한 동안 참조를 유지하는 스레드의 발밑에서 데이터가 사라지지 않도록 보장하는 설계다.

> **⚠️ 데이터 슬롯은 폐기된 것으로 보라**
>
> 이유가 셋이다.
>
> 첫째, **강한 타입이 사라진다.** `SetData`와 `GetData`는 `System.Object`를 주고받는다. 값 타입을 넣으면 박싱이 일어나고(15장), 꺼낼 때는 캐스팅이 필요하다.
>
> 둘째, **이름 있는 슬롯은 문자열 식별자를 쓴다.** 오타는 컴파일 시점에 잡히지 않고, 다른 라이브러리와 이름이 충돌해도 알 수 없다.
>
> 셋째, **더 느리다.** .NET 문서는 스레드 정적 필드가 데이터 슬롯보다 성능이 훨씬 좋으므로 가능하면 그쪽을 쓰라고 명확히 말한다.
>
> .NET Framework 초기에는 런타임에 TLS 데이터를 동적으로 할당할 유일한 수단이었다(클래스에 스레드 정적 필드를 실행 중에 추가할 수는 없으니까). .NET Framework 4.0에서 `ThreadLocal<T>`가 그 자리를 대체했고, **.NET Core에서 데이터 슬롯은 `ThreadLocal<T>` 위의 얇은 래퍼일 뿐이다.**

### 런타임 동작 — TLS는 마법의 빠른 메모리가 아니다

"스레드 로컬 저장소"라는 이름은 스레드 전용의 아주 빠른 특수 메모리를 연상시킨다. 스레드 친화성이라고 하면 스택이 떠오르고, 스택은 빠르니까. **사실은 훨씬 복잡하고, 그 복잡함이 성능 특성을 결정한다.**

운영체제가 각 스레드에 할당하는 전용 메모리 영역은 실제로 존재한다. Windows에서는 **TLS**, Linux에서는 **스레드별 데이터(thread-specific data)** 라고 부른다. 그런데 그 영역은 **매우 작다.**

| 플랫폼 | 슬롯 개수 |
|---|---|
| Windows | 정해져 있지 않지만 프로세스당 **최소 64개, 최대 1,088개** 보장 |
| Linux (glibc) | 보통 1,024개 |
| Linux (musl) | 128개 |

Windows의 보장치인 64개 슬롯은 64비트 프로세스에서 **고작 512바이트**다. 그러므로 이 슬롯에 데이터 자체를 담을 수는 없다 — **정상적으로 할당된 메모리를 가리키는 포인터**를 담는다. .NET뿐 아니라 C·C++ 컴파일러도 마찬가지다.

CoreCLR은 이 슬롯을 **딱 하나** 소비한다. `ThreadLocalInfo` 타입의 전역 스레드 정적 변수 주소를 담기 위해서다.

```text
 ┌───────────────────────────────────────────────────────────┐
 │ 스레드의 OS TLS 영역 (포인터 크기 슬롯 수십~수백 개)          │
 │  [슬롯0] ... [슬롯k: &gCurrentThreadInfo] ... [슬롯n]      │
 └──────────────────────────┬────────────────────────────────┘
                            ▼
   ThreadLocalInfo (CLR 내부) — 관리 Thread 주소 / AppDomain(레거시) /
                               스레드 역할 플래그(레거시)
                            ▼
   ThreadLocalBlock (AppDomain 당 하나) └ ThreadStaticHandleTable
                            ▼            (강한 핸들로 아래 배열을 붙든다)
        ┌───────────────────┴───────────────────┐
        ▼                                       ▼
 ThreadLocalModule (모듈당 하나)          관리 Object[] 배열
  └ 비관리 정적 블롭                       (참조 타입 필드용, GC 힙)
    (기본·값 타입 필드용)
```

즉 **TLS에 들어 있는 것은 `ThreadLocalInfo` 구조체를 가리키는 포인터 하나뿐**이고, 스레드 정적 데이터는 전부 CLR의 사설 힙과 GC 힙에 산다 — 일반 정적 필드와 비슷하게.

저장 위치는 필드 타입에 따라 갈린다.

| 필드 타입 | 저장 위치 | 결과 |
|---|---|---|
| 참조 타입 | 인스턴스는 GC 힙에 일반 할당. 참조는 전용 `Object[]` 배열에 담기며 `ThreadStaticHandleTable`의 강한 핸들이 그 배열을 붙든다 | 관리 스레드마다 별도 인스턴스·별도 배열 |
| 비관리 타입(기본형, 참조를 포함하지 않는 값 타입) | `ThreadLocalModule`의 정적 블롭(비관리 메모리) | 스레드·AppDomain·모듈 조합마다 별도 블롭 |
| 구조체(참조 포함) | GC 힙에 **박싱된 형태**로 | 참조 타입과 동일하게 취급 |

한 모듈의 타입·정적 필드 개수는 컴파일 시점에 정해지므로, `Object[]` 배열과 정적 블롭의 크기도 **미리 계산된 상수**다.

> **📌 스레드를 만드는 것은 생각보다 많은 할당을 유발한다**
>
> 위 구조를 보면 알 수 있다. .NET에서 스레드 하나를 만들면 각 모듈용 `ThreadLocalModule`과 각 AppDomain·모듈 조합의 `Object[]` 배열이 필요해진다. **다행히 이 구조체와 배열 대부분은 지연 할당된다** — 실제로 그 모듈의 스레드 정적 필드를 만질 때 만들어진다.
>
> 45.4절에서 본 "스레드 생성 비용"에 이 항목이 하나 더 붙는 셈이다. 스레드를 직접 만들지 말아야 할 이유가 또 하나 늘었다(45.9절).

### 컴파일 결과와 접근 비용

스레드 정적 필드의 오프셋은 **JIT 시점에 계산된다** — 비관리 타입이면 정적 블롭 안의 오프셋, 참조 타입이면 참조 배열 안의 오프셋이다. 이 오프셋은 `MethodTable` 관련 영역에 저장되어 JIT 컴파일러가 주소 계산에 쓴다.

문제는 **오프셋을 알아도 기준 주소를 얻으려면 현재 스레드의 `ThreadLocalModule`을 찾아와야 한다**는 것이다. 원천 자료가 보여 주는 생성 코드는 이렇다(계층 0의 단순화된 형태).

```asm
; 비관리 타입 스레드 정적 필드에 대입 (esi 에 저장할 값이 들어 있다고 가정)
mov     ecx, 2                                            ; 정적 블록 인덱스를 넘긴다
call    coreclr!JIT_GetSharedNonGCThreadStaticBaseOptimized ; TLS 포인터를 거쳐
                                                           ; ThreadLocalModule 주소를 rax 로
mov     rdi, rax
mov     dword ptr [rdi+1Ch], esi                          ; 1Ch 는 미리 계산된 오프셋
```

```asm
; 참조 타입 스레드 정적 필드에 대입 (rbx 에 저장할 참조가 들어 있다고 가정)
mov     edx, 2
call    coreclr!JIT_GetSharedGCThreadStaticBaseOptimized  ; 해당 타입의 참조가 시작되는
                                                          ; 배열 원소의 주소를 rax 로
mov     rcx, rax
mov     rdx, rbx
call    JitHelp: CORINFO_HELP_ASSIGN_REF                  ; 쓰기 배리어를 거쳐 저장
```

**정적 필드 접근이 일반 필드 접근보다 훨씬 느린 이유가 여기 있다.** 일반 인스턴스 필드는 `mov` 한두 개면 끝나지만, 스레드 정적 필드는 헬퍼 호출이 하나 끼어든다.

> **📌 이 코드는 계층 0 기준이며 최적화 여지가 있다**
>
> 위 어셈블리는 설명을 위해 단순화된 계층 0 버전이다. 계층 1 JIT은 헬퍼 호출을 인라인하고 TLS 접근을 더 짧은 시퀀스로 줄이는 최적화를 적용한다(55장). 그래도 **일반 필드보다 비싸다**는 방향은 변하지 않는다.
>
> 그래서 TLS 접근이 뜨거운 루프 안에 있으면 **루프 밖에서 한 번 읽어 지역 변수에 담는 것**이 효과적인 최적화다.
>
> ```csharp
> // 나쁨: 반복마다 헬퍼 호출
> for (int i = 0; i < n; i++) _threadLocalBuffer.Value[i] = Compute(i);
>
> // 좋음: 한 번만
> var buffer = _threadLocalBuffer.Value;
> for (int i = 0; i < n; i++) buffer[i] = Compute(i);
> ```

TLS가 주는 실질적 이점은 두 가지로 정리된다. **(1) 슬롯이 담긴 메모리 페이지는 정기적으로 접근하면 물리 메모리에 상주할 확률이 높다. (2) 그 페이지에 대한 접근은 한 스레드만 보므로 동기화가 필요 없다.** 원천 자료의 결론은 명확하다 — **TLS 자체가 무언가를 빠르게 만들어 주지는 않는다.** 여기서 TLS는 대응하는 자료구조의 스레드 친화성을 구현하는 수단일 뿐이다.

> **⚠️ 스레드 정적 데이터도 거짓 공유를 일으킬 수 있다**
>
> "스레드 전용 정적"이라는 이름 때문에 서로 멀리 떨어져 있을 것 같지만, 실제로는 **GC 힙 위에 나란히 놓인 평범한 객체들**이다. 서로 다른 스레드의 값이 **같은 캐시 라인에 들어갈 수 있고**, 그러면 거짓 공유(false sharing)로 성능이 무너진다. 정적 블롭 안의 값들은 정렬을 위해 패딩되지만 그것이 캐시 라인 격리를 보장하지는 않는다.
>
> 거짓 공유와 캐시 라인의 상세는 50.12절과 61.4절에 있다.

### 스레드 풀 스레드에 상태를 두면 다른 작업으로 샌다

TLS의 가장 위험한 함정은 성능이 아니라 **의미론**이다.

스레드 로컬 상태는 **스레드가 죽을 때까지 살아 있다.** 이것은 전용 스레드에서는 자연스러운 계약이다 — 스레드가 하나의 논리적 작업에 대응하니까. 그런데 **스레드 풀 스레드는 그렇지 않다.** 풀 스레드는 작업을 하나 끝내면 다음 작업을 받으러 돌아가고, 그 다음 작업은 완전히 무관한 요청일 수 있다.

```csharp
// 이 코드는 사고다
static class RequestContext
{
    [ThreadStatic] private static string _userId;

    public static string UserId
    {
        get => _userId;
        set => _userId = value;
    }
}

// 요청 처리
void HandleRequest(HttpContext ctx)
{
    RequestContext.UserId = ctx.User.Identity.Name;    // 설정하고
    DoWork();                                          // 쓰고
    // 지우는 것을 잊었다!
}
```

이 요청이 끝나면 그 풀 스레드는 다음 요청을 처리하러 간다. 그 요청이 `UserId`를 설정하지 않고 읽으면 **앞 요청의 사용자 ID를 본다.** 인증 정보가 사용자 간에 새는 보안 사고다.

> **⚠️ 스레드 풀 스레드에 스레드 로컬 상태를 남기지 마라**
>
> 세 가지 사고가 동시에 일어난다.
>
> 1. **데이터 누출** — 앞 작업의 값을 뒤 작업이 본다. 요청별 사용자 정보라면 보안 사고다.
> 2. **메모리 누수** — 값이 참조 타입이면 그 객체 그래프 전체가 **풀 스레드가 살아 있는 한** 살아 있다. 풀 스레드는 프로세스 수명 내내 산다. 45.5절의 `ThreadLocal<T>` 누수 사례와 같은 구조다.
> 3. **비결정성** — 어떤 풀 스레드가 걸리느냐에 따라 값이 있기도 하고 없기도 하다. 테스트에서는 재현되지 않고 부하가 걸리면 나타난다.
>
> 반드시 써야 한다면 **`try`/`finally`로 반드시 지운다.**
>
> ```csharp
> RequestContext.UserId = ctx.User.Identity.Name;
> try { DoWork(); }
> finally { RequestContext.UserId = null; }        // 스레드를 원래 상태로 돌려놓는다
> ```
>
> 그런데 이 코드는 `await`가 하나만 끼어들어도 깨진다. **요청 범위 상태에는 `AsyncLocal<T>`를 써라**(49.9절). 그것이 이 문제를 풀기 위해 존재하는 타입이다.

같은 이유로 **`async` 메서드에서는 `[ThreadStatic]`과 `ThreadLocal<T>`를 쓸 수 없다.** 원천 자료의 표현 그대로다 — `async` 메서드의 연속은 같은 스레드에서 실행된다는 보장이 없으므로, `await` 뒤에 재개되면 스레드 로컬 데이터를 잃는다. 예외는 있다. 데스크톱 애플리케이션의 UI 스레드처럼 연속이 반드시 같은 스레드로 돌아오는 것이 보장되는 경우다(47.12절).

### TLS가 여전히 옳은 경우

| 시나리오 | 예 |
|---|---|
| **스레드 친화 자원 관리** | 어떤 비관리 자원은 획득한 스레드가 반드시 해제해야 한다 |
| **진단·로깅** | 스레드별 로컬 데이터를 동기화 없이 다룬다. `EventSource`의 `[ThreadStatic]` 예외 재귀 카운터 필드가 실제 사례다 |
| **캐싱** | 스레드별 캐시. 관리 스레드 수만큼 중복이 생긴다는 대가를 안다면 유효하다 |
| **병렬 집계** | 스레드마다 부분 결과를 모으고 마지막에 합친다(45.5절 벤치마크) |

BCL 자신이 쓰는 대표적 예가 둘 있다. **`StringBuilderCache`** 는 스레드마다 작은 `StringBuilder` 인스턴스를 하나 캐시해 전역 풀에서 동기화 없이 가져다 쓰게 한다. **`System.Buffers`의 `SharedArrayPool<T>`** 도 계층적 캐싱 구조에 TLS를 쓴다.

공통점을 보라. **전부 값이 전용 스레드 수명 동안 유효해도 되는, 순수한 캐시·집계 목적이다.** 요청별 컨텍스트나 사용자 정보처럼 "논리적 작업"에 속한 데이터는 하나도 없다. 그것이 다음 절의 주제다.

## 49.9 `AsyncLocal<T>` — 비동기 흐름을 따라가는 상태

### 스레드가 아니라 흐름에 묶는다

49.8절의 결론은 이랬다. **`[ThreadStatic]`·`ThreadLocal<T>`·데이터 슬롯은 전부 비동기 함수와 호환되지 않는다.** `await` 이후에는 다른 스레드에서 실행이 재개될 수 있기 때문이다.

`AsyncLocal<T>`가 이 문제를 푼다. **`await`를 건너서도 값이 보존된다.**

```csharp
static AsyncLocal<string> _asyncLocalTest = new AsyncLocal<string>();

async void Main()
{
    _asyncLocalTest.Value = "test";
    await Task.Delay(1000);
    // 다른 스레드로 돌아와도 아래가 동작한다
    Console.WriteLine(_asyncLocalTest.Value);      // test
}
```

그러면서도 **서로 다른 스레드에서 시작된 작업들은 여전히 격리된다.** `Thread.Start`로 시작했든 `Task.Run`으로 시작했든 마찬가지다. 다음 코드는 "one one"과 "two two"를 출력한다.

```csharp
static AsyncLocal<string> _asyncLocalTest = new AsyncLocal<string>();

void Main()
{
    // 두 개의 동시 스레드에서 Test 를 부른다
    new Thread(() => Test("one")).Start();
    new Thread(() => Test("two")).Start();
}

async void Test(string value)
{
    _asyncLocalTest.Value = value;
    await Task.Delay(1000);
    Console.WriteLine(value + " " + _asyncLocalTest.Value);
}
```

`"one two"`나 `"two one"`은 절대 나오지 않는다. 값이 **스레드가 아니라 논리적 호출 흐름(logical call flow)** 에 묶여 있기 때문이다.

### 무엇이 이것을 실어 나르는가

`AsyncLocal<T>`의 값은 **`ExecutionContext`에 실려 흐른다.** 실행 컨텍스트가 캡처되는 시점과 복원되는 시점, 그리고 그 비용의 전모는 46.7절에서 다뤘다. 여기서 필요한 것은 한 문장이다 — **비동기 작업을 "예약하는 시점"에 현재 실행 컨텍스트가 캡처되고, 그 작업이 "실행되는 시점"에 복원된다.**

`AsyncLocal<T>`의 값 자체는 실행 컨텍스트 안의 딕셔너리에 담긴다. 메모리 관리 관점에서 `AsyncLocal<T>`는 특별할 것 없는 평범한 클래스이고, 그 인스턴스와 저장된 값은 실행 컨텍스트가 붙들고 있다.

```text
   [흐름 A]  _ctx.Value = "req-1"
       │
       │  ExecutionContext { AsyncLocal 딕셔너리: { _ctx → "req-1" } }
       │
       ├──▶ await Foo()      ── 캡처 → 복원 ──▶ 여전히 "req-1"
       │
       ├──▶ Task.Run(...)    ── 캡처 → 복원 ──▶ 자식도 "req-1"
       │                                          자식이 바꿔도 A 는 안 바뀐다
       │
       └──▶ ExecutionContext.SuppressFlow() 이후 예약 ──▶ 자식은 값을 못 본다
```

> **⚠️ `ConfigureAwait(false)`는 `AsyncLocal<T>` 값을 잃게 만들지 않는다**
>
> 46.7절에서 확인한 사실이다. `ConfigureAwait(false)`가 끄는 것은 **동기화 컨텍스트**이지 실행 컨텍스트가 아니다. `AsyncLocal<T>` 값은 그대로 흐른다. 실행 컨텍스트를 끄려면 `ExecutionContext.SuppressFlow()`가 필요하다(46.7절).
>
> 실무에서 자주 나오는 오해라 다시 적어 둔다. **`ConfigureAwait(false)`를 붙였더니 `Activity.Current`가 사라졌다면 원인은 다른 데 있다.**

### 복사-온-쓰기 의미론 — 자식이 바꾼 값은 부모로 돌아오지 않는다

`AsyncLocal<T>`에는 특이하고 고유한 뉘앙스가 있다. **`AsyncLocal<T>` 객체가 이미 값을 갖고 있을 때 스레드가 시작되면, 새 스레드는 그 값을 "상속"한다.**

```csharp
static AsyncLocal<string> _asyncLocalTest = new AsyncLocal<string>();

void Main()
{
    _asyncLocalTest.Value = "test";
    new Thread(AnotherMethod).Start();
}

void AnotherMethod() => Console.WriteLine(_asyncLocalTest.Value);      // test
```

그런데 **새 스레드가 받는 것은 값의 복사본이므로, 그것이 값을 바꿔도 원본에는 영향이 없다.**

```csharp
static AsyncLocal<string> _asyncLocalTest = new AsyncLocal<string>();

void Main()
{
    _asyncLocalTest.Value = "test";
    var t = new Thread(AnotherMethod);
    t.Start(); t.Join();
    Console.WriteLine(_asyncLocalTest.Value);      // test  ("ha-ha!" 가 아니다)
}

void AnotherMethod() => _asyncLocalTest.Value = "ha-ha!";
```

**흐름의 방향은 부모 → 자식 한 방향뿐이다.** 46.7절에서 본 그 규칙이며, `await` 경계에서도 같다 — `async` 메서드 안에서 `Value`에 대입하면 그 값은 **그 메서드 아래로만** 흐르고 호출자에게는 보이지 않는다.

이 의미론에는 이름이 있다. **복사-온-쓰기(copy-on-write)** 다. 값을 읽기만 하는 동안은 부모와 자식이 같은 것을 보지만, 자식이 쓰는 순간 자식용 사본이 만들어진다. 실행 컨텍스트가 **불변 객체**로 구현되어 있기 때문에 가능한 동작이다.

> **⚠️ 상속되는 것은 얕은 복사다**
>
> 46.7절에서 강조한 함정이다. 복사되는 것은 **값 자체**이지 값이 가리키는 객체가 아니다. `AsyncLocal<StringBuilder>`나 `AsyncLocal<List<string>>`을 쓰면 자식 흐름이 그 `StringBuilder`를 지우거나 리스트에 항목을 추가하는 순간 **원래 흐름도 그 변화를 본다.**
>
> 그래서 `AsyncLocal<T>`에는 **불변 값만** 담아라. 가변 객체가 필요하면 값을 바꾸는 대신 새 객체를 만들어 `Value`에 다시 대입해라(교체 전용).

### `valueChangedHandler`

두 번째 생성자 오버로드는 **값이 바뀔 때마다 불리는 콜백**을 받는다.

```csharp
public sealed class AsyncLocal<T>
{
    public AsyncLocal();
    public AsyncLocal(Action<AsyncLocalValueChangedArgs<T>> valueChangedHandler);

    public T Value { get; set; }
}

public readonly struct AsyncLocalValueChangedArgs<T>
{
    public T PreviousValue      { get; }
    public T CurrentValue       { get; }
    public bool ThreadContextChanged { get; }
}
```

콜백은 두 가지 경우에 불린다.

| 경우 | `ThreadContextChanged` | 의미 |
|---|---|---|
| 코드가 `Value`에 대입했다 | `false` | 명시적 변경 |
| 실행 컨텍스트가 복원되어 값이 달라졌다 | **`true`** | 스레드가 다른 흐름의 컨텍스트를 넘겨받았다 |

두 번째 경우가 이 기능의 존재 이유다. **`AsyncLocal<T>`의 값을 스레드 로컬 캐시와 동기화해야 할 때** 쓴다.

```csharp
[ThreadStatic] private static string _cachedForFastAccess;

// 컨텍스트가 이 스레드로 복원될 때마다 스레드 로컬 캐시를 갱신한다
static readonly AsyncLocal<string> _correlationId =
    new AsyncLocal<string>(args => _cachedForFastAccess = args.CurrentValue);
```

`Activity.Current`가 정확히 이 기법을 쓴다. 값 변경 알림을 받아 진단 인프라의 내부 상태를 맞춘다.

> **⚠️ `valueChangedHandler`는 아주 자주 불린다**
>
> `ThreadContextChanged: true` 알림은 **실행 컨텍스트가 복원될 때마다** 발생한다. 즉 `await`가 재개될 때마다, 태스크 연속이 실행될 때마다, 풀 스레드가 작업 항목을 집을 때마다다. 초당 수만 번이 될 수 있다.
>
> 그러므로 핸들러는 **극도로 가벼워야 한다.** 할당하지 말고, 잠금을 잡지 말고, 로깅하지 마라. 무거운 핸들러는 애플리케이션 전체의 비동기 경로를 느리게 만든다.

### 대표 용도

| 용도 | 담는 값 | 비고 |
|---|---|---|
| **상관 ID(correlation ID)** | 요청을 식별하는 문자열/`Guid` | 로그 항목을 요청 단위로 묶는다 |
| **진단 스코프** | 로거의 스코프 스택(불변) | `ILogger.BeginScope`의 구현이 이 방식이다 |
| **분산 추적** | `System.Diagnostics.Activity` | `Activity.Current`가 `AsyncLocal`로 구현되어 있다(75장) |
| **암묵적 트랜잭션** | 트랜잭션 스코프 | `TransactionScope`의 `Transaction.Current` |
| **테스트용 시간 제어** | 가짜 시계 | 테스트가 시간을 조작할 때(80장) |

상관 ID의 표준 골격은 이렇다.

```csharp
public static class RequestContext
{
    private static readonly AsyncLocal<string?> _correlationId = new();

    public static string? CorrelationId => _correlationId.Value;

    public static IDisposable Begin(string id)
    {
        string? previous = _correlationId.Value;
        _correlationId.Value = id;
        return new Restore(previous);       // 스코프를 나갈 때 되돌린다
    }

    private sealed class Restore(string? previous) : IDisposable
    {
        public void Dispose() => _correlationId.Value = previous;
    }
}

using (RequestContext.Begin(Guid.NewGuid().ToString("N")))
    await HandleRequestAsync();             // 이 아래 전부에서 CorrelationId 가 보인다
```

> **💡 왜 `Dispose`에서 되돌리는가**
>
> 복사-온-쓰기 의미론 때문에 **호출자의 흐름에서는 어차피 값이 바뀌지 않는다.** 그러면 `Restore`는 왜 필요한가.
>
> 같은 **동기적** 흐름 안에서 여러 스코프를 중첩할 때 필요하다. `Begin`을 부른 그 흐름 자체는 `Value`를 실제로 바꾸므로, 스코프를 나갈 때 되돌리지 않으면 형제 스코프가 앞 스코프의 값을 본다. 흐름이 갈라지는 지점(`Task.Run`, `await`)을 지나면 자동으로 격리되지만, 갈라지기 전까지는 직접 관리해야 한다.

### 흐름이 끊기는 지점

`AsyncLocal<T>`가 "언제나 따라온다"고 믿으면 사고가 난다. **끊기는 지점이 분명히 있다.**

**첫째, 설정 시점이 예약 시점보다 늦으면 안 된다.**

```csharp
static readonly AsyncLocal<string> _tag = new AsyncLocal<string>();

// 옳다 — Task.Run 이전에 설정
_tag.Value = "A";
await Task.Run(() => Console.WriteLine(_tag.Value));      // A

// 틀렸다 — Task.Run 이후에 설정
var t = Task.Run(() => { Thread.Sleep(100); Console.WriteLine(_tag.Value); });
_tag.Value = "B";
await t;                                                   // (빈 값)
```

컨텍스트는 **작업을 큐에 넣는 순간** 캡처된다. 그 뒤의 변경은 이미 예약된 작업에 반영되지 않는다(46.7절의 표).

**둘째, `ExecutionContext.SuppressFlow()` 구간에서 예약된 작업은 값을 받지 못한다.** 그리고 `ThreadPool.UnsafeQueueUserWorkItem`·`CancellationToken.UnsafeRegister` 같은 `Unsafe` 계열 API도 컨텍스트를 캡처하지 않는다. 상세는 46.7절이다.

**셋째, 흐름 밖에서 시작된 콜백은 아무것도 상속하지 않는다.** 네이티브 콜백, 이벤트 핸들러, 타이머 콜백 중 컨텍스트를 캡처하지 않는 경로로 들어온 것들이 여기 해당한다.

**넷째, 프로세스 경계는 절대 넘지 않는다.** HTTP 요청이나 메시지 큐를 통해 다른 서비스로 넘어가면 값이 사라진다. 분산 추적에서 상관 ID를 **헤더로 명시적으로 전파**하는 이유다(75장).

### 남용의 위험

`AsyncLocal<T>`는 **암묵적 매개변수**를 만드는 도구다. 그것이 장점이자 위험이다.

> **⚠️ `AsyncLocal<T>`는 전역 변수의 비동기 판본이다**
>
> 세 가지 대가를 정확히 알고 써라.
>
> **암묵적 결합.** 메서드 시그니처만 보면 그 메서드가 무엇에 의존하는지 알 수 없다. 호출자가 값을 설정하지 않으면 조용히 `null`이 되고, 그것이 프로덕션에서 처음 드러난다. 테스트도 어렵다 — 값을 설정하지 않은 테스트는 통과하는데 프로덕션에서는 다른 값이 흐른다.
>
> **디버깅 곤란.** 값이 어디서 설정됐는지 스택을 거슬러 올라가며 추적해야 한다. 흐름이 여러 번 갈라졌다면 "지금 이 값이 어느 흐름의 것인지" 판단하기가 매우 어렵다.
>
> **성능.** `AsyncLocal<T>`를 하나라도 쓰면 실행 컨텍스트가 더 이상 "빈 불변 객체"가 아니게 되고, 캡처·복원이 진짜 작업이 된다. 46.7절의 표현대로 아무것도 쓰지 않았다면 캡처는 참조 하나 복사로 끝나지만, 값이 있으면 그렇지 않다.
>
> **판단 기준은 이것이다. 그 값이 비즈니스 로직에 쓰이면 매개변수로 넘겨라. 인프라(로깅·추적·진단)에만 쓰이면 `AsyncLocal<T>`가 적절하다.** 사용자 ID로 권한을 판단한다면 매개변수여야 하고, 로그 항목에 붙이기만 한다면 `AsyncLocal<T>`여도 된다.

### 스레드 로컬과의 비교표

| 항목 | `[ThreadStatic]` / `ThreadLocal<T>` | `AsyncLocal<T>` |
|---|---|---|
| 값이 묶이는 대상 | **스레드** | **논리적 호출 흐름** |
| `await` 이후 | **값을 잃는다** (다른 스레드일 수 있으므로) | 보존된다 |
| 새 스레드/태스크 | 값이 없다(기본값) | **부모 값을 상속한다** |
| 자식의 변경이 부모에 보이는가 | 해당 없음(애초에 격리) | **보이지 않는다** (복사-온-쓰기) |
| 참조 대상의 변경이 부모에 보이는가 | 해당 없음 | **보인다** (얕은 복사) |
| 운반체 | OS TLS + CLR 자료구조 | `ExecutionContext` |
| 풀 스레드에서 값이 새는가 | **샌다** (직접 지워야 한다) | 새지 않는다(작업마다 컨텍스트가 복원된다) |
| 억제 방법 | 없다 | `ExecutionContext.SuppressFlow()` |
| 접근 비용 | 0.2ns ~ 8ns | 더 비싸다(딕셔너리 조회) |
| 값 변경 알림 | 없다 | `valueChangedHandler` |
| 대표 용도 | 캐시, 병렬 집계, 스레드 친화 자원 | 상관 ID, 진단 스코프, `Activity` |

> **💡 셋 중 하나를 고르는 규칙**
>
> 1. 값이 **"이 스레드의 것"** 이면 `ThreadLocal<T>`. 스레드별 `Random`, 스레드별 버퍼 캐시, 병렬 집계의 부분 합.
> 2. 값이 **"이 요청/이 작업의 것"** 이면 `AsyncLocal<T>`. 상관 ID, 진단 스코프.
> 3. 값이 **"이 호출의 것"** 이면 **그냥 매개변수로 넘겨라.** 대부분의 경우가 여기 해당하며, 앞의 둘을 쓰고 싶어질 때 먼저 이것을 검토해라.

## 49.10 타이머 세 종류 — `PeriodicTimer`, 멀티스레드 타이머, 단일 스레드 타이머

### 왜 타이머인가

어떤 메서드를 일정 간격으로 반복 실행해야 한다면 가장 쉬운 방법은 타이머다. 타이머는 "전용 스레드를 만들어 `DoSomeAction()` 후 `Thread.Sleep(TimeSpan.FromHours(24))`를 반복한다" 같은 기법에 비해 메모리와 자원 사용이 편리하고 효율적이다. 그 스레드 방식은 **스레드 자원을 영구히 붙들고 있을 뿐 아니라**, 추가 코딩 없이는 `DoSomeAction`이 매일 조금씩 늦은 시각에 실행된다(작업 시간이 누적되기 때문이다). 타이머가 이 문제들을 푼다.

.NET이 제공하는 타이머는 다섯 종류다.

| 분류 | 타입 | 콜백이 도는 곳 |
|---|---|---|
| 범용 멀티스레드 | `System.Threading.Timer` | 스레드 풀 |
| 범용 멀티스레드 | `System.Timers.Timer` | 스레드 풀(또는 `SynchronizingObject`) |
| 단일 스레드 | `System.Windows.Forms.Timer` | Windows Forms 메시지 루프 |
| 단일 스레드 | `System.Windows.Threading.DispatcherTimer` | WPF 디스패처 |
| 비동기 루프 | `PeriodicTimer` ※.NET 6 | `await` 규칙에 따른다 |

**멀티스레드 타이머가 더 강력하고, 정확하고, 유연하다. 단일 스레드 타이머는 더 안전하고, Windows Forms 컨트롤이나 WPF 요소를 갱신하는 단순한 작업에 더 편리하다.**

### `System.Threading.Timer`

가장 단순한 멀티스레드 타이머다. 생성자 하나와 메서드 둘이 전부다.

```csharp
public sealed class Timer : MarshalByRefObject, IDisposable, IAsyncDisposable
{
    public Timer(TimerCallback callback, object? state, int dueTime, int period);
    public Timer(TimerCallback callback, object? state, TimeSpan dueTime, TimeSpan period);
    // uint, long 오버로드도 있다

    public bool Change(int dueTime, int period);
    public bool Change(TimeSpan dueTime, TimeSpan period);

    public void Dispose();
    public bool Dispose(WaitHandle notifyObject);
    public ValueTask DisposeAsync();                     // ※.NET Core 3.0
}

public delegate void TimerCallback(object? state);
```

```csharp
using System;
using System.Threading;

// 첫 간격 5000ms, 이후 간격 1000ms
Timer tmr = new Timer(Tick, "tick...", 5000, 1000);
Console.ReadLine();
tmr.Dispose();          // 타이머를 멈추고 정리한다

void Tick(object data)
{
    // 이 코드는 풀 스레드에서 돈다
    Console.WriteLine(data);        // "tick..." 출력
}
```

간격은 나중에 `Change`로 바꿀 수 있다. **한 번만 발화시키려면 생성자의 마지막 인자에 `Timeout.Infinite`(-1)** 를 준다.

`System.Threading.Timer`의 런타임 동작과 **콜백 재진입 문제**, 그리고 `period`를 `Timeout.Infinite`로 두고 콜백 끝에서 `Change`로 재예약하는 회피 관용구는 46.6절에서 상세히 다뤘다. 여기서는 46.6절이 다루지 않은 것 하나를 짚는다.

### `Dispose(WaitHandle)` — 실행 중인 콜백을 기다리기

`Timer.Dispose()`는 **이미 시작된 콜백이 끝나기를 기다려 주지 않는다.** 즉 `Dispose`가 반환된 뒤에도 풀 스레드에서 콜백이 돌고 있을 수 있다. 콜백이 만지는 자원을 그 직후에 정리하면 `ObjectDisposedException`이 난다.

`Dispose(WaitHandle)` 오버로드가 이 문제를 푼다. **대기 중이거나 실행 중인 모든 콜백이 완료되면 지정한 대기 핸들에 신호를 보낸다.**

```csharp
var timer = new Timer(Callback, null, 0, 1000);

// ... 한참 뒤 정리할 때 ...
using var done = new ManualResetEvent(false);
if (timer.Dispose(done))                    // false 면 이미 폐기된 것이다
    done.WaitOne();                         // 실행 중인 콜백이 끝날 때까지 기다린다

_connection.Dispose();                      // 이제 콜백이 만지던 자원을 안전하게 정리
```

이 절 전체가 다룬 신호 구조가 여기서 쓰인다는 점에 주목해라. `Dispose(WaitHandle)`가 요구하는 것이 바로 `WaitHandle`이다.

현대 코드에서는 `DisposeAsync`가 같은 일을 더 깔끔하게 한다.

```csharp
await timer.DisposeAsync();                 // 콜백 완료까지 기다린다. 스레드는 막지 않는다
_connection.Dispose();
```

> **⚠️ `Dispose(WaitHandle)`를 콜백 안에서 부르면 데드락이다**
>
> 콜백 스스로 자기 타이머를 `Dispose(WaitHandle)`로 폐기하고 그 핸들을 기다리면, **자기가 끝나기를 자기가 기다리는** 구조가 되어 영원히 멈춘다.
>
> 콜백 안에서 타이머를 멈춰야 하면 `Change(Timeout.Infinite, Timeout.Infinite)`를 쓰거나, 인자 없는 `Dispose()`를 쓴다.

`System.Threading.Timer`의 **수명 함정** — 참조를 놓치면 GC가 수거해 타이머가 조용히 멈추는 문제 — 는 34.10절에서 완전히 다뤘다. 그 절의 요약을 한 줄로 옮기면 이렇다. **타이머는 항상 필드에 보관하고, 타이머를 가진 클래스는 항상 `IDisposable`이어야 한다.**

### `System.Timers.Timer`

`System.Timers` 네임스페이스에 **같은 이름의 타이머**가 하나 더 있다. 이것은 `System.Threading.Timer`를 **감싼 래퍼**이며, 동일한 엔진을 쓰면서 편의 기능을 더한다.

추가된 기능은 이렇다.

| 기능 | 설명 |
|---|---|
| `IComponent` 구현 | Visual Studio 디자이너의 컴포넌트 트레이에 올릴 수 있다 |
| `Interval` 속성 | `Change` 메서드 대신 `double` 밀리초 속성 |
| `Elapsed` 이벤트 | 콜백 델리게이트 대신 이벤트 |
| `Enabled` 속성 | 타이머를 켜고 끈다(**기본값 `false`**) |
| `Start`/`Stop` 메서드 | `Enabled`가 헷갈리는 사람을 위해 |
| `AutoReset` 플래그 | 반복 여부(기본값 `true`) |
| `SynchronizingObject` 속성 | `Invoke`/`BeginInvoke`로 WPF 요소·WinForms 컨트롤의 메서드를 안전하게 호출 |

```csharp
using System;
using System.Timers;                      // Threading 이 아니라 Timers 네임스페이스

var tmr = new Timer();                    // 인자가 필요 없다
tmr.Interval = 500;
tmr.Elapsed += tmr_Elapsed;               // 델리게이트 대신 이벤트
tmr.Start();                              // 타이머 시작
Console.ReadLine();
tmr.Stop();                               // 타이머 정지
Console.ReadLine();
tmr.Start();                              // 재시작
Console.ReadLine();
tmr.Dispose();                            // 영구히 정지

void tmr_Elapsed(object sender, EventArgs e) => Console.WriteLine("Tick");
```

`SynchronizingObject`에 폼이나 컨트롤을 지정하면 `Elapsed` 이벤트가 **그 컨트롤의 스레드에서** 발생한다. UI 갱신을 하면서도 멀티스레드 타이머의 정확도를 유지하려는 절충안이다. 다만 그 순간부터 UI 스레드가 밀리면 이벤트도 밀린다.

> **⚠️ `System.Timers.Timer`의 기본 `Enabled`는 `false`다**
>
> `new System.Timers.Timer(1000)`을 만들고 `Elapsed`를 구독한 뒤 **`Start()`(또는 `Enabled = true`)를 부르지 않으면 아무 일도 일어나지 않는다.** `System.Threading.Timer`가 생성자에서 곧바로 시작하는 것과 정반대다. 두 타이머를 오가며 코드를 쓰면 반드시 한 번은 걸리는 함정이다.
>
> 그리고 **수명 계약도 정반대**다. `System.Timers.Timer`는 런타임이 붙들고 있어서 폐기하지 않으면 구독자가 영원히 산다. `System.Threading.Timer`는 붙들지 않아서 참조를 놓치면 조용히 멈춘다. 34.10절의 핵심이다.

### 멀티스레드 타이머의 공통 성질

두 멀티스레드 타이머 모두 **스레드 풀을 써서 적은 수의 스레드로 많은 타이머를 서비스한다.** 결과적으로 이런 성질을 갖는다.

- **콜백/`Elapsed` 이벤트는 매번 다른 스레드에서 발화할 수 있다.**
- **`Elapsed` 이벤트는 이전 이벤트의 실행이 끝났는지와 무관하게 (거의) 정확한 시각에 발화한다.**
- 따라서 **콜백과 이벤트 핸들러는 반드시 스레드 안전해야 한다.**

두 번째 항목이 46.6절에서 다룬 **재진입** 문제다. `System.Timers.Timer`에서는 `AutoReset = false`로 두고 핸들러 끝에서 `Start()`를 다시 부르는 것이 회피 관용구다.

**정밀도는 운영체제에 달려 있으며 일반적으로 10~20밀리초 수준이다.** 더 높은 정밀도가 필요하면 네이티브 상호 운용으로 Windows 멀티미디어 타이머를 호출하는 방법이 있다. 이것은 1밀리초까지의 정밀도를 갖고 `winmm.dll`에 정의되어 있다. 먼저 `timeBeginPeriod`로 OS에 높은 타이밍 정밀도가 필요함을 알리고, `timeSetEvent`로 멀티미디어 타이머를 시작한다. 다 쓰면 `timeKillEvent`로 타이머를 멈추고 `timeEndPeriod`로 높은 정밀도가 더 이상 필요 없음을 알린다. P/Invoke로 외부 메서드를 호출하는 방법은 60장에서 다룬다.

### 단일 스레드 타이머

.NET은 WPF와 Windows Forms 애플리케이션의 스레드 안전성 문제를 없애기 위한 타이머도 제공한다.

- `System.Windows.Threading.DispatcherTimer` (WPF)
- `System.Windows.Forms.Timer` (Windows Forms)

둘 다 `System.Timers.Timer`와 비슷한 멤버(`Interval`, `Start`, `Stop`, 그리고 `Elapsed`에 해당하는 `Tick`)를 노출하고 비슷하게 쓴다. **그러나 내부 동작이 다르다.** 풀 스레드에서 타이머 이벤트를 발화시키는 대신 **WPF나 Windows Forms의 메시지 루프에 이벤트를 게시(post)한다.**

즉 `Tick` 이벤트는 언제나 **타이머를 만든 그 스레드에서** 발생한다. 일반적인 애플리케이션에서 그 스레드는 모든 UI 요소와 컨트롤을 관리하는 그 스레드다. 여기서 세 가지 이점이 나온다.

1. **스레드 안전성을 잊어도 된다.**
2. **이전 `Tick`의 처리가 끝나기 전에는 새 `Tick`이 발화하지 않는다.**
3. **`Control.BeginInvoke`나 `Dispatcher.BeginInvoke` 없이 `Tick` 핸들러에서 UI 요소를 직접 갱신할 수 있다.**

```csharp
// WPF
var timer = new DispatcherTimer(DispatcherPriority.Normal)
{
    Interval = TimeSpan.FromSeconds(1)
};
timer.Tick += (s, e) => _clockText.Text = DateTime.Now.ToLongTimeString();   // 직접 갱신 OK
timer.Start();
```

이런 타이머를 쓰는 프로그램은 사실 **멀티스레드가 아니다.** 47장에서 UI 스레드의 비동기 함수를 다루며 본 것과 같은 종류의 **의사 동시성(pseudo-concurrency)** 이 된다. 한 스레드가 모든 타이머와 UI 이벤트 처리를 함께 담당하므로, **`Tick` 이벤트 핸들러는 빨리 끝나야 한다.** 그러지 않으면 UI가 응답하지 않는다.

정밀도 면에서 단일 스레드 타이머는 멀티스레드 타이머와 비슷한 수준(수십 밀리초)이지만, **다른 UI 요청이나 다른 타이머 이벤트를 처리하느라 지연될 수 있어 일반적으로 덜 정확하다.**

> **⚠️ 단일 스레드 타이머는 자기 환경 밖에서 동작하지 않는다**
>
> 원천 자료의 명시적 경고다. **단일 스레드 타이머는 각자의 환경 밖에서 동작하도록 설계되지 않았다.** 예를 들어 Windows 서비스 애플리케이션에서 Windows Forms 타이머를 쓰면 **`Timer` 이벤트가 아예 발화하지 않는다.** 메시지 루프가 없기 때문이다.
>
> 예외도 오류도 없이 그냥 조용히 아무 일도 일어나지 않는다. 콘솔 앱이나 백그라운드 서비스에 UI 타이머를 끌어다 쓰지 마라.

### `PeriodicTimer` ※.NET 6

`PeriodicTimer`는 엄밀히 말하면 타이머가 아니라 **비동기 반복을 돕는 클래스**다. API와 겹침 불가 구조, 정지와 취소의 차이, 드리프트 정책은 **46.6절**에서 전부 다뤘다. 여기서는 다른 네 타이머와의 비교 축에서만 다시 본다.

핵심은 **제어의 방향**이다. 다른 네 타이머는 콜백을 **밀어 넣지만(push)**, `PeriodicTimer`는 소비자가 틱을 **꺼내 간다(pull)**. 그래서 본문 두 개가 동시에 도는 상태를 문법적으로 만들 수 없다.

| 환경 제약 | 없다 | 없다 | **WinForms 전용** | **WPF 전용** | 없다 |

```text
        │           │           │    └─ 아니오 ─▶ System.Threading.Timer
        │           │           │                  + period = Timeout.Infinite
        │           │           │                  + 콜백 끝에서 Change  (46.6절)
        │           │           │
        │           │           └─ 디자이너에 올려야 하는가?
        │           │                └─ 예 ─▶ System.Timers.Timer
        │           │
        │           └─ 정밀도가 1ms 단위로 필요한가?
        │                └─ 예 ─▶ 관리 코드 타이머로는 불가.
        │                          winmm.dll 멀티미디어 타이머 (60장)
        │

```

> **💡 새 코드의 기본값은 `PeriodicTimer`다**
>
> 백그라운드 서비스, 폴링 루프, 헬스 체크, 캐시 갱신 — 서버 애플리케이션의 주기 작업은 거의 전부 비동기다. 그렇다면 **선택지는 `PeriodicTimer` 하나**다. 겹침이 불가능하고, 취소 토큰을 받고, 예외를 반복문 안의 `try`로 잡을 수 있고, `IHostedService`의 `ExecuteAsync`와 자연스럽게 맞물린다.
>
> `System.Threading.Timer`는 **동기 콜백이고 겹침을 감당할 수 있을 때**만 쓴다. `System.Timers.Timer`는 **디자이너 지원이 필요할 때**만 쓴다. 그 외의 경우 두 타입은 34.10절의 수명 함정만 추가로 안겨 준다.

## 이 장의 요약

- **잠금은 배제가 목적이고 신호는 통보가 목적이다.** 도구가 겹치는 것은 사실이지만 코드를 읽는 사람에게 의도를 전하는 이름은 하나뿐이다. 뜨거운 루프에서 `AutoResetEvent`로 상호 배제를 흉내 내면 `lock`보다 세 자릿수 느리다.
- **`WaitHandle` 파생 타입은 전부 커널 객체다.** 메서드 호출마다 관리 → 사용자 모드 → 커널 모드 전이가 일어나고, 무경합 획득·해제에 약 1마이크로초가 든다. 모든 호출이 전체 메모리 펜스이므로 신호로 순서를 보장했다면 별도의 `lock`이나 `volatile`이 필요 없다.
- **`AutoResetEvent`는 신호를 누적하지 않는다.** 아무도 없는 턴스타일에 `Set`을 세 번 불러도 통과하는 것은 한 명뿐이고 나머지 티켓은 버려진다. "항목이 N개 준비됐다"를 N번의 `Set`으로 알리는 코드는 조용히 항목을 잃는다. 카운트가 필요하면 세마포어나 큐다.
- **`Slim` 판본은 짧은 대기에서만 이긴다.** 스핀 후 필요할 때만 커널 객체를 만드는 하이브리드 전략이라 대기가 밀리초 단위로 길어지면 스핀은 낭비다. `WaitHandle` 속성에 접근하는 순간 하이브리드의 이점도 사라진다.
- **`CountdownEvent`는 카운트가 0이 된 뒤 되돌릴 수 없다.** `AddCount`는 `InvalidOperationException`이고 `TryAddCount`가 `false`를 돌려준다. 초기 카운트 1을 잡아 두고 마지막에 `Signal`하는 것이 동적 작업 추가의 정석이며, `Signal`은 반드시 `finally`에 있어야 한다.
- **이름 있는 `EventWaitHandle`은 Windows 전용이다.** Linux에서는 `PlatformNotSupportedException`이다. 이름 있는 `Semaphore`도 마찬가지이고 이름 있는 `Mutex`만 Unix에서 동작한다. 개발 머신에서는 되고 운영 컨테이너에서 터지는 대표적 사고다.
- **`WaitAll`과 `SignalAndWait`은 STA 스레드에서 동작하지 않는다.** 배열 원소는 64개를 넘을 수 없다. 원자성이 필요 없다면 `RegisterWaitForSingleObject` + `TaskCompletionSource`로 태스크로 바꿔 `Task.WhenAll`/`WhenAny`를 쓰는 편이 모든 면에서 낫다.
- **`Barrier`의 사고는 거의 전부 참가자 수 불일치다.** 하나가 예외로 죽으면 나머지가 영원히 기다린다. `finally`에서 `RemoveParticipant`를 부르고 타임아웃 오버로드를 써라. 단계 후 액션이 던진 예외는 `BarrierPostPhaseException`으로 감싸여 모든 참가자에게 전달된다.
- **`Monitor.Wait`은 반드시 `while` 루프 안에 있어야 한다.** 깨어남과 잠금 획득 사이에 조건이 다시 거짓이 될 수 있고, `PulseAll`은 여럿을 깨우지만 자원은 하나일 수 있고, 가짜 깨어남도 가능하다. 확신이 없으면 `Pulse`가 아니라 `PulseAll`이다.
- **조건 변수 패턴은 이해하되 쓰지 마라.** `BlockingCollection<T>`(50.11절)과 `Channel<T>`(51.1절)이 이 위에 지어져 있고, 이 패턴에는 비동기 대응 API가 없어 서버에서 스레드 풀 기아를 부른다.
- **TLS는 마법의 빠른 메모리가 아니다.** OS TLS 슬롯에는 CLR 내부 구조체를 가리키는 포인터 하나만 들어가고, 실제 데이터는 GC 힙과 CLR 사설 힙에 있다. 접근에는 JIT 헬퍼 호출이 끼어들므로 뜨거운 루프에서는 지역 변수로 끌어내야 한다.
- **스레드 풀 스레드에 스레드 로컬 상태를 남기면 다음 작업으로 샌다.** 요청별 사용자 정보라면 보안 사고이고, 참조 타입이면 풀 스레드 수명 내내 살아 있는 누수다. 요청 범위 상태에는 `AsyncLocal<T>`를 써라.
- **`AsyncLocal<T>`는 부모 → 자식 한 방향으로만 흐른다.** 자식이 `Value`를 바꿔도 부모는 보지 못하지만(복사-온-쓰기), 값이 가리키는 가변 객체를 바꾸면 부모도 본다(얕은 복사). 그래서 불변 값만 담아야 한다.
- **`ConfigureAwait(false)`는 `AsyncLocal<T>` 값을 잃게 만들지 않는다.** 그것이 끄는 것은 동기화 컨텍스트이고, `AsyncLocal<T>`를 실어 나르는 것은 실행 컨텍스트다(46.7절).
- **타이머 선택의 첫 질문은 "UI를 갱신하는가"이고 두 번째는 "비동기인가"다.** UI면 `DispatcherTimer`/WinForms `Timer`, 비동기면 `PeriodicTimer`, 동기이고 겹침을 감당할 수 있으면 `System.Threading.Timer`다. 그리고 어느 것을 고르든 34.10절의 수명 계약을 반드시 확인해라.

## 연습 문제

1. **신호 유실 재현.** `AutoResetEvent` 하나를 만들고 아무도 대기하지 않는 상태에서 `Set()`을 다섯 번 부른 뒤 `WaitOne(0)`을 다섯 번 호출해 반환값을 출력하라. 같은 실험을 `SemaphoreSlim(0)`과 `Release()`로 반복하고 결과 차이를 표로 정리하라. 그다음 `ManualResetEventSlim`으로도 해 보고 왜 결과가 또 다른지 설명하라.

2. **`Slim`이 지는 지점 찾기.** `ManualResetEvent`와 `ManualResetEventSlim`으로 각각 "한 스레드가 `Set`하고 다른 스레드가 대기"를 100,000회 반복하는 벤치마크를 작성하라. `Set`까지의 지연을 0μs, 10μs, 1ms, 10ms로 바꿔 가며 측정하고, 두 곡선이 교차하는 지점을 찾아라.

3. **`CountdownEvent` 예외 함정.** 작업 스레드 세 개 중 하나가 예외를 던지도록 만들고 `Signal`을 `finally`가 아닌 본문 끝에 두어 프로그램이 멈추는 것을 확인하라. 그다음 `finally`로 옮겨 고치고, `Wait(TimeSpan)`으로 바꿔 타임아웃 진단이 어떻게 달라지는지 비교하라.

4. **플랫폼 제약 확인.** 이름 있는 `EventWaitHandle`을 만드는 콘솔 앱을 작성하고 Windows와 Linux 컨테이너에서 각각 실행해 어떤 예외가 나는지 기록하라(`docker run --rm -v ... mcr.microsoft.com/dotnet/sdk` 로 충분하다). 같은 프로그램을 이름 있는 `Mutex`로 바꿔 다시 실행하고 결과를 비교하라.

5. **대기 핸들을 태스크로.** 49.5절의 `ToTask` 확장 메서드를 구현하고, `ManualResetEvent` 세 개를 만들어 `await Task.WhenAny(...)`로 가장 먼저 신호된 것을 찾는 프로그램을 작성하라. `RunContinuationsAsynchronously`를 뺐을 때 연속이 어느 스레드에서 실행되는지 `Thread.CurrentThread.ManagedThreadId`로 확인하라.

6. **`Barrier` 데드락 만들고 고치기.** 참가자 3으로 `Barrier`를 만들고 작업자 하나가 두 번째 단계에서 예외를 던지게 하라. 나머지 두 스레드가 멈추는 것을 확인한 뒤 `dotnet-dump`로 덤프를 떠 어느 지점에서 막혀 있는지 확인하고, `finally`의 `RemoveParticipant`로 고쳐라.

7. **스레드 로컬이 새는 것 관찰.** `[ThreadStatic]` 필드에 요청 ID를 넣고 `ThreadPool.QueueUserWorkItem`으로 작업 100개를 큐잉하되 절반만 값을 설정하도록 하라. 값을 설정하지 않은 작업이 앞 작업의 값을 보는 것을 출력으로 확인하고, `AsyncLocal<T>`로 바꾸면 그 현상이 사라지는지 검증하라.

8. **`AsyncLocal<T>` 흐름 실험.** `Task.Run` **이전**과 **이후**에 `Value`를 설정하는 두 버전을 만들어 자식이 무엇을 보는지 확인하라. 그다음 `AsyncLocal<List<int>>`로 바꿔 자식이 리스트에 항목을 추가했을 때 부모가 그것을 보는지 확인하고, 왜 그런지 46.7절의 얕은 복사 설명과 연결해 설명하라.

9. **타이머 재진입과 정리.** `System.Threading.Timer`의 콜백이 3초 걸리고 `period`가 1초인 프로그램을 만들어 콜백이 겹치는 것을 `ManagedThreadId` 출력으로 확인하라. 그다음 `Dispose(WaitHandle)`로 폐기하면서 실행 중인 콜백이 끝날 때까지 기다리는 코드를 넣고, 인자 없는 `Dispose()`와 동작이 어떻게 다른지 기록하라.
