## 38.1 `ToString`과 `Parse` / `TryParse` / `IParsable<T>`

### 두 방향의 변환

**포매팅(formatting)** 은 값을 문자열로 바꾸는 것이고, **파싱(parsing)** 은 문자열에서 값을 꺼내는 것이다. 이 두 작업은 프로그래밍에서 끊임없이 반복되고, 그래서 .NET은 네 가지 서로 다른 메커니즘을 제공한다.

| 메커니즘 | 대상 | 문화권 인식 | 이 장에서 |
|---|---|---|---|
| `ToString` / `Parse` | 단순 값 타입 전반 | 기본값이 현재 문화권 | 38.1절 |
| 형식 공급자(format provider) | 숫자 타입, `DateTime`/`DateTimeOffset` | 완전히 제어 가능 | 38.2 ~ 38.7절 |
| `XmlConvert` | 숫자, `bool`, `DateTime`, `DateTimeOffset`, `TimeSpan`, `Guid` | **항상 문화권 독립** | 38.9절 |
| 타입 변환기(`TypeConverter`) | 100종 이상의 BCL 타입 | 디자이너·XAML 대상 | 38.9절 |

이 장은 두 번째 메커니즘 — 형식 공급자 — 에 대부분의 지면을 쓴다. 나머지 셋은 형식 공급자로 해결되지 않는 자리를 메우는 도구다.

### `ToString`

가장 단순한 포매팅 메커니즘은 `ToString`이다. 모든 단순 값 타입 — `bool`, `DateTime`, `DateTimeOffset`, `TimeSpan`, `Guid`, 그리고 모든 숫자 타입 — 에서 의미 있는 출력을 낸다.

```csharp
string s = true.ToString();          // "True"
string n = 42.ToString();            // "42"
string g = Guid.Empty.ToString();    // "00000000-0000-0000-0000-000000000000"
```

`ToString`은 `object`에 정의된 가상 메서드이므로 모든 타입이 갖는다. 다만 재정의하지 않은 타입은 타입의 전체 이름을 돌려줄 뿐이다.

```csharp
class Point { public int X, Y; }
Console.WriteLine (new Point().ToString());   // "Point" (네임스페이스가 있으면 그 전체 이름)
```

### `Parse`와 `FormatException`

역방향은 각 타입이 정의하는 정적 `Parse` 메서드다.

```csharp
string s = true.ToString();     // s = "True"
bool b = bool.Parse (s);        // b = true
```

파싱이 실패하면 **`FormatException`** 이 던져진다. 다만 실패의 종류에 따라 예외 타입이 달라진다는 점이 중요하다.

| 입력 | `int.Parse` 결과 | 이유 |
|---|---|---|
| `"123"` | `123` | 정상 |
| `"qwerty"` | `FormatException` | 형식이 숫자가 아니다 |
| `""` | `FormatException` | 빈 문자열도 형식 오류다 |
| `null` | `ArgumentNullException` | 인자 자체가 없다 |
| `"99999999999"` | `OverflowException` | 형식은 맞지만 `int` 범위를 벗어난다 |

> **⚠️ `catch (FormatException)`만으로는 파싱 실패를 다 못 잡는다**
>
> 파싱 오류를 예외로 처리하는 코드에서 가장 흔한 버그가 이것이다. `int.Parse(userInput)`을 `catch (FormatException)`으로만 감싸면, 사용자가 `"99999999999"`를 입력한 순간 `OverflowException`이 빠져나가 프로세스를 죽인다. `null`이 들어오면 `ArgumentNullException`이 빠져나간다.
>
> 세 개를 다 잡으려면 `catch (Exception)`을 써야 하는데, 그건 32.9절에서 본 대로 `TryXXX` 패턴이 존재하는 이유를 정면으로 부정하는 코드다. 결론은 하나다 — **`Parse`를 `try`로 감싸지 말고 `TryParse`를 써라.**

부동소수점 타입의 오버플로 동작은 런타임에 따라 다르므로 별도로 짚는다.

> **⚠️ `double.Parse`의 오버플로 동작은 런타임마다 다르다**
>
> `.NET Framework`에서 `double.Parse("1e400")`은 `OverflowException`을 던진다. `.NET Core 3.0` 이후에는 예외 없이 `double.PositiveInfinity`를 돌려준다. IEEE 754 규격을 엄격히 따르도록 변경된 결과다.
>
> 같은 이유로 `double.TryParse("1e400", out var d)`는 최신 런타임에서 **`true`를 반환하고 `d`에 무한대를 담는다.** `TryParse`가 `true`를 냈으니 값이 유한하다고 가정한 코드는 여기서 조용히 깨진다. 유한성이 필요하면 `double.IsFinite(d)`로 따로 검사해라.
>
> `decimal.Parse`는 이 변화의 대상이 아니다. 범위를 벗어나면 여전히 `OverflowException`을 던진다.

### `TryParse`와 discard

많은 타입이 `TryParse`도 정의한다. 변환이 실패하면 예외 대신 `false`를 돌려준다.

```csharp
bool failure = int.TryParse ("qwerty", out int i1);   // false, i1 = 0
bool success = int.TryParse ("123",    out int i2);   // true,  i2 = 123
```

결과값이 필요 없고 "파싱이 될 문자열인가"만 알고 싶다면 **discard**(`_`)를 쓴다.

```csharp
bool isNumeric = int.TryParse (s, out int _);
bool isNumeric2 = int.TryParse (s, out _);     // 타입도 생략 가능
```

오류가 예상되는 상황이라면 `Parse`를 예외 처리 블록으로 감싸는 것보다 `TryParse`를 부르는 쪽이 **빠르고 우아하다.** 여기서 "빠르다"는 것은 막연한 표현이 아니다.

**성능 영향** — 예외를 하나 던지고 잡는 비용은 스택 워크와 예외 객체 할당을 포함해 마이크로초 단위다. 파싱 자체는 수십 나노초다. 즉 실패가 흔한 경로에서 `Parse` + `catch`는 정상 경로보다 **수백 배 느리다.** 사용자 입력을 검증하는 반복문에서 이 차이는 즉시 드러난다.

```csharp
// 나쁜 코드 — 실패가 흔하면 재앙
foreach (string line in lines)
{
    try { total += int.Parse (line); }
    catch (FormatException) { skipped++; }
}

// 좋은 코드
foreach (string line in lines)
{
    if (int.TryParse (line, out int v)) total += v;
    else skipped++;
}
```

> **💡 `Parse`를 쓸 자리와 `TryParse`를 쓸 자리**
>
> 판단 기준은 "실패가 정상 흐름의 일부인가"다.
>
> - **실패가 버그를 의미한다면 `Parse`** — 설정 파일의 상수, 코드에 하드코딩된 리터럴, 이미 검증을 통과한 값. 여기서 실패했다면 프로그램이 계속 돌면 안 된다.
> - **실패가 데이터의 성질이라면 `TryParse`** — 사용자 입력, 외부 API 응답, CSV의 한 칸.
>
> 32.9절의 "실패가 예상되는 연산에는 `TryXXX`" 원칙이 파싱에서 가장 자주 위반된다. 예외를 던지고 잡는 실제 비용은 32.12절에서 측정한다.

### `Parse`는 현재 문화권을 본다

`DateTime`/`DateTimeOffset`과 숫자 타입의 `Parse`·`TryParse`는 **로컬 문화권 설정을 존중한다.** 이것이 이 장 전체를 관통하는 함정의 근원이다.

```csharp
Console.WriteLine (double.Parse ("1.234"));      // 독일에서 1234
```

독일에서는 마침표가 소수점이 아니라 **천 단위 구분자**다. 그래서 `"1.234"`는 "일점이삼사"가 아니라 "천이백삼십사"로 읽힌다. 예외도 없고 경고도 없다. 값이 1,000배 틀린 채로 조용히 흘러간다.

`CultureInfo`를 명시하면 고쳐진다.

```csharp
double x = double.Parse ("1.234", CultureInfo.InvariantCulture);   // 1.234
```

`ToString()`에도 같은 이야기가 적용된다.

```csharp
string x = 1.234.ToString (CultureInfo.InvariantCulture);          // "1.234"
```

> **⚠️ 이 버그는 개발자의 PC에서 절대 재현되지 않는다**
>
> 위 코드가 만드는 사고의 성질을 정확히 이해해야 한다.
>
> 1. 한국이나 미국 개발 PC에서는 `double.Parse("1.234")`가 정확히 1.234를 낸다. 테스트가 전부 통과한다.
> 2. 코드는 독일·프랑스·브라질 사용자의 PC에서, 또는 `de-DE` 로캘로 설정된 리눅스 컨테이너에서 처음 틀린다.
> 3. 값이 1000배가 되었을 뿐 예외가 없으므로 로그에도 남지 않는다.
>
> "문화권을 명시하지 않은 `Parse`/`ToString`"은 이 책이 지적하는 함정 중 **가장 넓게 퍼져 있고 가장 늦게 발견되는 것**이다. 38.11절에 어느 자리에 무엇을 써야 하는지 표로 정리해 두었다.

### `IParsable<T>`와 `ISpanParsable<T>` ※.NET 7

.NET 6까지 `Parse`/`TryParse`는 **관례**였다. 모든 숫자 타입이 같은 이름의 정적 메서드를 갖고 있지만, 그 사실을 타입 시스템이 알지 못했다. 그래서 "문자열을 `T`로 파싱하는 제네릭 메서드"를 쓸 수 없었다.

C# 11의 **정적 추상 멤버**(22.7절)가 이 구멍을 막았다. .NET 7은 파싱을 인터페이스로 승격했다.

```csharp
namespace System
{
    public interface IParsable<TSelf> where TSelf : IParsable<TSelf>?
    {
        static abstract TSelf Parse (string s, IFormatProvider? provider);

        static abstract bool TryParse (string? s, IFormatProvider? provider,
                                       out TSelf result);
    }

    public interface ISpanParsable<TSelf> : IParsable<TSelf>
        where TSelf : ISpanParsable<TSelf>?
    {
        static abstract TSelf Parse (ReadOnlySpan<char> s, IFormatProvider? provider);

        static abstract bool TryParse (ReadOnlySpan<char> s, IFormatProvider? provider,
                                       out TSelf result);
    }
}
```

이제 제네릭 파서를 쓸 수 있다.

```csharp
static T[] ParseAll<T> (IEnumerable<string> lines, IFormatProvider? provider = null)
    where T : IParsable<T>
{
    var list = new List<T>();
    foreach (string line in lines)
        if (T.TryParse (line, provider, out T? value))
            list.Add (value);
    return list.ToArray();
}

int[] ints = ParseAll<int> (new[] { "1", "2", "x", "3" });          // [1, 2, 3]
DateTime[] dates = ParseAll<DateTime> (isoStrings,
                                       CultureInfo.InvariantCulture);
```

`T.TryParse(...)`라는 호출 형태에 주목해라. **타입 매개변수 위에서 직접 정적 메서드를 부른다.** 이것이 정적 추상 멤버가 열어 준 문법이다.

**컴파일 결과** — 제약이 `where T : IParsable<T>`이므로 컴파일러는 `constrained.` 접두사를 붙인 `call`을 방출한다.

```il
ldarg.0
ldarg.1
ldloca.s value
constrained. !!T
call       bool class [System.Runtime]System.IParsable`1<!!T>::TryParse(
               string, class [System.Runtime]System.IFormatProvider, !0&)
```

**런타임 동작** — `T`가 값 타입이면 CLR은 23.11절에서 본 대로 타입마다 코드를 특수화한다. 즉 `ParseAll<int>`는 `int.TryParse`를 **직접 호출**하도록 JIT된다. 인터페이스 디스패치도 박싱도 없다. `T`가 참조 타입이면 공유 코드가 사용되고 런타임 타입 핸들을 통해 정적 메서드를 찾는다.

> **📌 `IParsable<T>`를 구현하는 BCL 타입**
>
> .NET 7 이후 `IParsable<T>` 또는 `ISpanParsable<T>`를 구현하는 타입은 매우 넓다 — 모든 정수·부동소수점 타입, `decimal`, `BigInteger`, `Complex`, `Half`, `Int128`/`UInt128`, `DateTime`, `DateTimeOffset`, `DateOnly`, `TimeOnly`, `TimeSpan`, `Guid`, `Version`, `IPAddress`, `Uri`, `char`, `bool`, `Rune`, `Enum`(제네릭 오버로드) 등이다.
>
> `INumber<T>`(39.9절, 22.8절)는 `ISpanParsable<T>`를 상속하므로, 제네릭 수학 제약을 건 코드는 파싱까지 공짜로 얻는다.

.NET 8은 여기에 UTF-8 버전을 더했다.

```csharp
public interface IUtf8SpanParsable<TSelf> where TSelf : IUtf8SpanParsable<TSelf>?
{
    static abstract TSelf Parse (ReadOnlySpan<byte> utf8Text, IFormatProvider? provider);
    static abstract bool TryParse (ReadOnlySpan<byte> utf8Text, IFormatProvider? provider,
                                   out TSelf result);
}
```

UTF-8 바이트에서 **UTF-16 문자열을 거치지 않고** 곧바로 숫자를 뽑는다. 자세한 이야기는 38.8절이다.

> **⚠️ 커스텀 타입에 `IParsable<T>`를 구현할 때 잊기 쉬운 것**
>
> `IParsable<T>.TryParse`의 시그니처는 `out TSelf result`이지 `out TSelf? result`가 아니다. 실패 경로에서 `result = default!`를 넣어야 컴파일러의 널 허용성 분석을 통과한다. 그리고 인터페이스가 요구하는 `Parse(string, IFormatProvider?)` 오버로드를 **반드시** 만들어야 한다 — 기존에 `Parse(string)`만 있던 타입은 인터페이스를 만족시키지 못한다.
>
> ```csharp
> public readonly struct Sku : IParsable<Sku>, ISpanParsable<Sku>
> {
>     public string Code { get; }
>     private Sku (string code) => Code = code;
>
>     public static Sku Parse (string s, IFormatProvider? p)
>         => TryParse (s, p, out var r) ? r : throw new FormatException ($"잘못된 SKU: {s}");
>
>     public static bool TryParse (string? s, IFormatProvider? p, out Sku result)
>         => TryParse (s.AsSpan(), p, out result);
>
>     public static Sku Parse (ReadOnlySpan<char> s, IFormatProvider? p)
>         => TryParse (s, p, out var r) ? r : throw new FormatException ("잘못된 SKU");
>
>     public static bool TryParse (ReadOnlySpan<char> s, IFormatProvider? p, out Sku result)
>     {
>         // 규칙: 영문 대문자 3자 + 숫자 5자
>         if (s.Length == 8
>             && char.IsAsciiLetterUpper (s[0]) && char.IsAsciiLetterUpper (s[1])
>             && char.IsAsciiLetterUpper (s[2])
>             && int.TryParse (s[3..], NumberStyles.None,
>                              CultureInfo.InvariantCulture, out _))
>         {
>             result = new Sku (s.ToString());
>             return true;
>         }
>         result = default;
>         return false;
>     }
> }
> ```
>
> `s.AsSpan()`은 `s`가 `null`이어도 안전하다 — 빈 스팬이 된다. 그래서 별도의 널 검사가 필요 없다.

### UTF-8 직접 포매팅·파싱 ※.NET 8

.NET 8부터 숫자·날짜/시간 타입을 비롯한 단순 타입은 `byte[]`나 `Span<byte>` 위에서 동작하는 `TryFormat`과 `Parse`/`TryParse`를 갖는다. 고성능 시나리오에서 일반적인 UTF-16 문자열을 만들고 별도로 UTF-8 인코딩/디코딩을 수행하는 것보다 효율적이다. 상세는 38.8절이고, `Span<byte>` 자체의 규칙은 68장이다.

## 38.2 형식 공급자(`IFormatProvider`), `CultureInfo`, `NumberFormatInfo`

### 왜 별도의 메커니즘이 필요한가

`ToString()`은 인자를 받지 않으니 "이렇게 찍어라"라고 지시할 방법이 없다. `DateTime` 하나만 해도 표현 방법이 수십 가지다. **형식 공급자**는 이 통제권을 호출자에게 넘긴다.

형식 공급자의 관문은 `IFormattable`이다. 모든 숫자 타입과 `DateTime`/`DateTimeOffset`이 구현한다.

```csharp
public interface IFormattable
{
    string ToString (string format, IFormatProvider formatProvider);
}
```

인자가 둘이고, 역할이 명확히 나뉜다.

- **형식 문자열(format string)** — *무엇을* 할지 지시한다. `"C"`, `"F4"`, `"yyyy-MM-dd"`.
- **형식 공급자(format provider)** — 그 지시를 *어떻게* 번역할지 결정한다. 통화 기호가 `$`인지 `€`인지, 소수점이 `.`인지 `,`인지.

```csharp
NumberFormatInfo f = new NumberFormatInfo();
f.CurrencySymbol = "$$";
Console.WriteLine (3.ToString ("C", f));      // $$ 3.00
```

`"C"`는 "통화로 찍어라"라는 지시이고, `NumberFormatInfo` 인스턴스가 통화가 어떻게 생겼는지를 정의한다. 이 분리가 세계화(globalization)를 가능하게 하는 구조다.

### 세 종류의 공급자

.NET은 `IFormatProvider`를 구현하는 클래스를 정확히 셋 정의한다.

| 클래스 | 네임스페이스 | 담당 |
|---|---|---|
| `NumberFormatInfo` | `System.Globalization` | 숫자 서식 — 소수점, 구분자, 통화·백분율 기호, 부호, NaN/무한대 표기 |
| `DateTimeFormatInfo` | `System.Globalization` | 날짜/시간 서식 — 패턴, 요일·월 이름, AM/PM, 달력 |
| `CultureInfo` | `System.Globalization` | 위 둘로 가는 **간접 계층** |

`CultureInfo`는 스스로 서식을 만들지 않는다. 문화권의 지역 설정에 맞는 `NumberFormatInfo` 또는 `DateTimeFormatInfo`를 골라 돌려주는 **디스패처**다.

```csharp
public interface IFormatProvider
{
    object GetFormat (Type formatType);
}
```

이 메서드 하나가 간접 계층의 전부다. 숫자 타입이 서식을 만들 때 `provider.GetFormat(typeof(NumberFormatInfo))`를 부르고, `CultureInfo`는 자기 `NumberFormat` 속성을 돌려준다.

```text
              3.ToString("C", provider)
                          │
                          ▼
   ┌──────────────────────────────────────────────┐
   │ Int32.ToString(string, IFormatProvider)      │
   └──────────────────────┬───────────────────────┘
                          │ NumberFormatInfo.GetInstance(provider)
                          ▼
   ┌──────────────────────────────────────────────┐
   │ provider.GetFormat(typeof(NumberFormatInfo)) │
   └──────────────────────┬───────────────────────┘
                          │
          ┌───────────────┴────────────────┐
          │                                │
   provider가 CultureInfo          provider가 NumberFormatInfo
          │                                │
          ▼                                ▼
   culture.NumberFormat 반환          자기 자신 반환
          │                                │
          └───────────────┬────────────────┘
                          ▼
   ┌──────────────────────────────────────────────┐
   │ CurrencySymbol / CurrencyDecimalDigits /     │
   │ CurrencyGroupSeparator / CurrencyNegativePattern │
   └──────────────────────┬───────────────────────┘
                          ▼
                       "$3.00"
```

**형식 문자열은 무엇을, 형식 공급자는 어떻게 — 해석 경로**

> **📌 열거형은 이 구조 밖에 있다**
>
> 모든 `enum` 타입도 서식화할 수 있지만 전용 `IFormatProvider` 클래스는 없다. 열거형의 서식 문자열은 문화권과 무관하기 때문이다(38.7절).

### 기본 공급자는 `CultureInfo.CurrentCulture`

형식 문자열이나 공급자에 `null`을 넘기면 기본값이 적용된다. **기본 형식 공급자는 `CultureInfo.CurrentCulture`** 이고, 이 값은 별도로 지정하지 않는 한 실행 중인 컴퓨터의 지역 설정을 반영한다.

```csharp
Console.WriteLine (10.3.ToString ("C", null));     // en-US에서 $10.30
```

편의를 위해 대부분의 타입은 공급자를 생략할 수 있는 오버로드를 제공한다.

```csharp
Console.WriteLine (10.3.ToString ("C"));      // $10.30
Console.WriteLine (10.3.ToString ("F4"));     // 10.3000 — 소수점 이하 4자리 고정
```

인자 없이 `ToString()`을 부르는 것은 **기본 형식 공급자 + 빈 형식 문자열**을 쓰는 것과 같다.

> **⚠️ "기본값"이라는 말이 감추는 것**
>
> 위 세 줄은 전부 같은 문장으로 요약된다 — **호출한 스레드의 `CurrentCulture`에 의존한다.** 그리고 `CurrentCulture`는 다음 요인 전부에 의해 바뀐다.
>
> - 사용자의 OS 지역 설정 (Windows 제어판, 리눅스의 `LANG`/`LC_ALL`)
> - 컨테이너 이미지의 로캘 설정 (많은 기본 이미지가 `C`/`POSIX`다)
> - `CultureInfo.CurrentCulture`에 대한 다른 코드의 대입
> - ASP.NET Core의 요청 지역화 미들웨어
> - 스레드 풀 스레드인지 아닌지
>
> 즉 `value.ToString()`의 결과는 **환경 변수와 다름없다.** 화면에 보여 줄 문자열이라면 그게 정확히 원하는 동작이고, 파일에 쓰거나 HTTP로 보낼 문자열이라면 그게 정확히 버그다.

### `CultureInfo` 다루기

특정 문화권을 요청하는 방법은 둘이다.

```csharp
CultureInfo uk1 = CultureInfo.GetCultureInfo ("en-GB");   // 캐시된 읽기 전용 인스턴스
CultureInfo uk2 = new CultureInfo ("en-GB");              // 새 인스턴스, 쓰기 가능
Console.WriteLine (3.ToString ("C", uk1));                // £3.00
```

| 생성 방법 | 반환 | 쓰기 가능 | 비용 |
|---|---|---|---|
| `CultureInfo.GetCultureInfo(name)` | 프로세스 전역 캐시의 공유 인스턴스 | **아니오**(읽기 전용) | 두 번째 호출부터 사실상 공짜 |
| `new CultureInfo(name)` | 매번 새 인스턴스 | 예 | 매번 ICU 데이터 조회 + 할당 |

> **💡 반복 호출 경로에서는 `GetCultureInfo`를 써라**
>
> 루프 안에서 `new CultureInfo("en-GB")`를 부르면 매번 문화권 데이터를 새로 채운다. 읽기만 할 거라면 `GetCultureInfo`가 캐시를 쓴다. 고정된 문화권을 여러 번 쓴다면 `static readonly` 필드에 한 번 담아 두는 편이 가장 낫다.
>
> ```csharp
> static readonly CultureInfo Uk = CultureInfo.GetCultureInfo ("en-GB");
> ```

**불변 문화권**은 항상 같다. 컴퓨터 설정과 무관하다.

```csharp
DateTime dt = new DateTime (2000, 1, 2);
CultureInfo iv = CultureInfo.InvariantCulture;
Console.WriteLine (dt.ToString (iv));         // 01/02/2000 00:00:00
Console.WriteLine (dt.ToString ("d", iv));    // 01/02/2000
```

불변 문화권은 미국 문화권을 기반으로 하되 다음이 다르다.

| 항목 | 불변 문화권 | `en-US` |
|---|---|---|
| 통화 기호 | `¤` (U+00A4, 일반 통화 기호) | `$` |
| 날짜 자릿수 | 앞자리 0을 채운다 (`01/02/2000`) | 채우지 않는다 (`1/2/2000`) |
| 시각 표기 | 24시간제 | AM/PM |
| 월/일 순서 | 월이 먼저 (미국식 그대로) | 월이 먼저 |
| `Name` 속성 | `""` (빈 문자열) | `"en-US"` |

> **📌 불변 문화권의 통화 기호는 `¤`다**
>
> `CultureInfo.InvariantCulture.NumberFormat.CurrencySymbol`은 U+00A4 CURRENCY SIGN(`¤`)이다. 특정 문화권에 묶이지 않은 "통화 자리"를 뜻하는 유니코드 문자이며, 그래서 불변 문화권으로 통화를 찍으면 사람이 읽기에는 쓸모없는 문자열이 나온다.
>
> 레거시 코드 페이지로 동작하는 Windows 콘솔에서는 이 문자가 물음표나 엉뚱한 기호로 보일 수 있다. 폰트·코드 페이지 문제이지 값이 다른 것이 아니다. `Console.OutputEncoding = System.Text.Encoding.UTF8;`를 설정하면 제대로 나온다(35.9절).
>
> 여기서 얻을 실무적 교훈은 이것이다 — **통화 표시는 불변 문화권으로 하는 것이 아니다.** 금액을 저장할 때는 `decimal` 값과 통화 코드(`"KRW"`)를 따로 저장하고, 표시할 때 사용자 문화권으로 서식화해라.

### `NumberFormatInfo` 직접 만들기

```csharp
NumberFormatInfo f = new NumberFormatInfo();
f.NumberGroupSeparator = " ";
Console.WriteLine (12345.6789.ToString ("N3", f));    // 12 345.679
```

새로 만든 `NumberFormatInfo`나 `DateTimeFormatInfo`의 초기 설정은 **불변 문화권 기준**이다. 다른 출발점이 필요하면 기존 공급자를 `Clone`한다.

```csharp
NumberFormatInfo f = (NumberFormatInfo)
    CultureInfo.CurrentCulture.NumberFormat.Clone();
f.CurrencyDecimalDigits = 0;
```

**복제된 형식 공급자는 언제나 쓰기 가능하다** — 원본이 읽기 전용이었더라도 그렇다.

> **⚠️ `CultureInfo.CurrentCulture.NumberFormat`을 직접 수정하려 들지 마라**
>
> `CultureInfo.CurrentCulture`가 `GetCultureInfo`로 얻어진 인스턴스라면 `NumberFormat`은 읽기 전용이고, 속성에 대입하면 `InvalidOperationException`이 난다.
>
> 설령 쓰기 가능한 인스턴스였다 해도 수정하면 안 된다. 그 인스턴스는 스레드 전체가 공유하는 상태이고, 라이브러리 코드가 예상하지 못한 방식으로 서식이 바뀐다. 항상 `Clone()`해서 **자기 사본**을 고쳐라.

### `NumberFormatInfo`의 주요 속성

| 속성 | 영향 받는 형식 | `en-US` 기본값 |
|---|---|---|
| `NumberDecimalSeparator` | `F` `N` `G` `E` 사용자 지정 `.` | `.` |
| `NumberGroupSeparator` | `N` 사용자 지정 `,` | `,` |
| `NumberGroupSizes` | 위와 같음 | `[3]` |
| `NumberDecimalDigits` | `F` `N`의 기본 정밀도 | `2` |
| `NumberNegativePattern` | 음수 배치 (`-n`, `- n`, `n-` 등) | `1` |
| `CurrencySymbol` | `C` | `$` |
| `CurrencyDecimalSeparator` / `CurrencyGroupSeparator` | `C` | `.` / `,` |
| `CurrencyDecimalDigits` | `C`의 기본 정밀도 | `2` |
| `CurrencyPositivePattern` / `CurrencyNegativePattern` | `C`의 기호 위치와 음수 표기 | `0` / `0` |
| `PercentSymbol` / `PerMilleSymbol` | `P`, 사용자 지정 `%` `‰` | `%` / `‰` |
| `PercentDecimalDigits` | `P`의 기본 정밀도 | `2` |
| `PositiveSign` / `NegativeSign` | 모든 부호 | `+` / `-` |
| `NaNSymbol` | `double.NaN` 출력 | `NaN` |
| `PositiveInfinitySymbol` / `NegativeInfinitySymbol` | 무한대 출력 | `∞` / `-∞` |
| `NativeDigits` / `DigitSubstitution` | 아라비아-인도 숫자 등 대체 숫자 | 서양 숫자 |

> **⚠️ 인도식 자릿수 구분(`NumberGroupSizes`)**
>
> `NumberGroupSizes`가 항상 `[3]`인 것은 아니다. `hi-IN`(힌디어-인도)에서는 `[3, 2]`다. 즉 `12345678`이 `1,23,45,678`로 찍힌다(라크·크로르 표기). 자릿수 구분자가 3자리마다 온다고 가정한 파서나 정규식은 인도 사용자에게서 깨진다.
>
> `CurrencyNegativePattern`도 마찬가지다. 값에 따라 `($1.00)`, `-$1.00`, `$-1.00`, `$1.00-` 등이 나온다. **괄호가 음수를 뜻하는 문화권이 있다**는 사실은 파싱 쪽에서 특히 중요하다(38.4절).

```csharp
foreach (string p in CultureInfo.GetCultureInfo ("ko-KR")
                                .DateTimeFormat.GetAllDateTimePatterns ('d'))
    Console.WriteLine (p);
```

### 복합 서식(composite formatting)

복합 형식 문자열은 변수 치환과 형식 문자열을 결합한다. 정적 `string.Format`이 이를 받는다(35.7절에서 보간 문자열과 대비해 다룬 그 문법이다).

```csharp
string composite = "Credit={0:C}";
Console.WriteLine (string.Format (composite, 500));       // Credit=$500.00
```

`Console`의 `Write`/`WriteLine`도 복합 형식 문자열 오버로드를 갖는다.

```csharp
Console.WriteLine ("Credit={0:C}", 500);                  // Credit=$500.00
```

`StringBuilder.AppendFormat`과 `TextWriter`(40.5절)도 마찬가지다.

복합 형식 항목의 완전한 문법은 다음과 같다.

```text
{ index [,alignment] [:formatString] }
```

| 부분 | 의미 | 예 |
|---|---|---|
| `index` | 0부터 시작하는 인자 번호 | `{0}` |
| `alignment` | 최소 폭. 양수면 오른쪽 정렬, 음수면 왼쪽 정렬 | `{0,10}` `{0,-10}` |
| `formatString` | 그 인자에 적용할 형식 문자열 | `{0:N2}` |

```csharp
const int width = 40;
Console.WriteLine ($"{ulong.MaxValue,width:N0}");
// "          18,446,744,073,709,551,615"  (폭 40, 오른쪽 정렬, 천 단위 구분)
```

`{{`와 `}}`는 중괄호 리터럴이다.

`string.Format`은 형식 공급자를 받는 오버로드도 있다. 임의의 객체에 대해 공급자를 지정한 `ToString`을 부르는 용도로 쓸 수 있다.

```csharp
string s = string.Format (CultureInfo.InvariantCulture, "{0}", someObject);
```

이는 다음과 동등하다.

```csharp
string s;
if (someObject is IFormattable)
    s = ((IFormattable)someObject).ToString (null, CultureInfo.InvariantCulture);
else if (someObject == null)
    s = "";
else
    s = someObject.ToString();
```

> **⚠️ 보간 문자열은 복합 서식이지만 문화권이 다르다**
>
> `$"Credit={amount:C}"`는 컴파일러가 `DefaultInterpolatedStringHandler`로 낮추며(35.7절), 기본적으로 **`CurrentCulture`** 를 쓴다. `string.Format(provider, ...)`처럼 공급자를 앞에 붙일 자리가 문법에 없다.
>
> 불변 문화권으로 보간하려면 `string.Create`를 쓴다.
>
> ```csharp
> string s = string.Create (CultureInfo.InvariantCulture, $"Credit={amount:C}");
> ```
>
> `FormattableString.Invariant($"...")`도 같은 목적을 달성하지만, 이 쪽은 `FormattableString` 객체를 힙에 만들고 인자를 `object[]`에 박싱한다. 성능이 중요하면 `string.Create` 쪽이다.

### `CompositeFormat`으로 파싱 비용 없애기 ※.NET 8

`string.Format`은 호출할 때마다 형식 문자열을 **다시 파싱한다.** 형식 문자열이 상수라면 이는 순수한 낭비다. .NET 8의 `System.Text.CompositeFormat`은 파싱 결과를 미리 만들어 재사용한다.

```csharp
using System.Text;

static readonly CompositeFormat Fmt =
    CompositeFormat.Parse ("사용자 {0}이(가) {1:yyyy-MM-dd}에 로그인했다.");

string Render (string user, DateTime when)
    => string.Format (CultureInfo.InvariantCulture, Fmt, user, when);
```

**성능 영향** — 형식 문자열이 길고 항목이 많을수록, 그리고 호출 빈도가 높을수록 이득이 커진다. 로컬라이즈된 리소스 문자열(53장)처럼 런타임에 결정되어 보간 문자열로 쓸 수 없는 형식 문자열에서 특히 값어치가 있다.

> **📌 `[StringSyntax]`로 편집기 지원 받기 ※.NET 7**
>
> BCL의 형식 문자열 매개변수는 `[StringSyntax]` 특성으로 표시되어 있다. 편집기가 이 특성을 보고 문자열 리터럴 안에서 IntelliSense와 구문 강조를 제공한다.
>
> ```csharp
> using System.Diagnostics.CodeAnalysis;
>
> [StringSyntax (StringSyntaxAttribute.DateTimeFormat)]
> private const string FullDateTime = "dddd, d MMMM yyyy";
> ```
>
> 인식되는 값에는 `CompositeFormat`, `DateOnlyFormat`, `DateTimeFormat`, `EnumFormat`, `GuidFormat`, `Json`, `NumericFormat`, `Regex`, `TimeOnlyFormat`, `TimeSpanFormat`, `Uri`, `Xml`이 있다. .NET BCL의 350개 이상의 매개변수·속성·필드가 이 특성으로 표시되어 있다. 자기 API의 형식 문자열 매개변수에도 붙여 두면 호출자가 편해진다.

### 형식 공급자로 파싱하기

포매팅에는 `IFormattable`이라는 표준 인터페이스가 있지만, **파싱에는 그런 인터페이스가 없다**(.NET 7의 `IParsable<T>`가 그 자리를 뒤늦게 메웠다). 대신 각 타입이 정적 `Parse`/`TryParse`를 오버로드해 형식 공급자와, 선택적으로 `NumberStyles` 또는 `DateTimeStyles` 열거형을 받는다.

```csharp
int error = int.Parse ("(2)");                       // FormatException

int minusTwo = int.Parse ("(2)", NumberStyles.Integer |
                                 NumberStyles.AllowParentheses);   // -2

decimal fivePointTwo = decimal.Parse ("£5.20", NumberStyles.Currency,
                                      CultureInfo.GetCultureInfo ("en-GB"));
```

`NumberStyles`와 `DateTimeStyles`는 파싱 동작을 제어한다 — 괄호나 통화 기호가 입력에 나타날 수 있는지 같은 것을 지정한다. **기본적으로 둘 다 허용되지 않는다.** 전체 목록은 38.4절과 38.6절이다.

### 사용자 정의 형식 공급자 — `ICustomFormatter`

`IFormatProvider`와 `ICustomFormatter`를 함께 구현하면 기존 타입과 연동되는 자기만의 형식 공급자를 만들 수 있다.

```csharp
public interface ICustomFormatter
{
    string Format (string format, object arg, IFormatProvider formatProvider);
}
```

다음 공급자는 숫자를 단어로 쓴다.

```csharp
public class WordyFormatProvider : IFormatProvider, ICustomFormatter
{
    static readonly string[] _numberWords =
        "zero one two three four five six seven eight nine minus point".Split();

    IFormatProvider _parent;   // 공급자를 체이닝할 수 있게 한다

    public WordyFormatProvider () : this (CultureInfo.CurrentCulture) { }
    public WordyFormatProvider (IFormatProvider parent) => _parent = parent;

    public object GetFormat (Type formatType)
    {
        if (formatType == typeof (ICustomFormatter)) return this;
        return null;
    }

    public string Format (string format, object arg, IFormatProvider prov)
    {
        // 우리 형식 문자열이 아니면 부모 공급자에게 넘긴다
        if (arg == null || format != "W")
            return string.Format (_parent, "{0:" + format + "}", arg);

        StringBuilder result = new StringBuilder();
        string digitList = string.Format (CultureInfo.InvariantCulture, "{0}", arg);
        foreach (char digit in digitList)
        {
            int i = "0123456789-.".IndexOf (digit, StringComparison.InvariantCulture);
            if (i == -1) continue;
            if (result.Length > 0) result.Append (' ');
            result.Append (_numberWords[i]);
        }
        return result.ToString();
    }
}
```

`Format` 메서드 안에서 입력 숫자를 문자열로 만들 때 `arg.ToString()`이 아니라 `string.Format`에 **불변 문화권**을 넘긴 이유가 있다. 몇 줄 아래에서 드러난다.

```csharp
int i = "0123456789-.".IndexOf (digit, StringComparison.InvariantCulture);
```

여기서 숫자 문자열이 반드시 `0123456789-.` 문자로만 이루어져야 한다. 국제화된 숫자 문자가 섞이면 인덱스를 찾지 못한다.

```csharp
double n = -123.45;
IFormatProvider fp = new WordyFormatProvider();
Console.WriteLine (string.Format (fp, "{0:C} in words is {0:W}", n));
// -$123.45 in words is minus one two three point four five
```

> **⚠️ 사용자 정의 형식 공급자는 복합 형식 문자열에서만 동작한다**
>
> `n.ToString("W", fp)`는 동작하지 않는다. `double.ToString`은 `ICustomFormatter`를 조회하지 않고 곧바로 `NumberFormatInfo`를 찾기 때문이다. `ICustomFormatter`를 조회하는 것은 **복합 서식 엔진**(`string.Format`, `StringBuilder.AppendFormat`, `Console.Write`)뿐이다.
>
> 이 제약은 `ICustomFormatter`의 실용성을 크게 떨어뜨린다. 실무에서는 대체로 확장 메서드나 전용 헬퍼를 만드는 편이 낫다.

## 38.3 표준·사용자 지정 숫자 형식 문자열

### 두 종류

형식 문자열은 숫자 타입 또는 `DateTime`/`DateTimeOffset`이 문자열로 변환되는 방식을 제어한다. 두 종류가 있다.

- **표준 형식 문자열** — 큰 방향만 지시한다. **글자 하나** 뒤에 선택적으로 **숫자**(정밀도 지정자)가 붙는다. `"C"`, `"F2"`, `"N0"`.
- **사용자 지정 형식 문자열** — 템플릿으로 모든 문자를 세밀하게 지시한다. `"#.000E+00"`, `"0,000.##"`.

> **📌 "사용자 지정 형식 문자열"과 "사용자 정의 형식 공급자"는 무관하다**
>
> 이름이 비슷해서 헷갈리지만 층이 다르다. 사용자 지정 **형식 문자열**은 *무엇을* 찍을지를 템플릿으로 쓰는 것이고, 사용자 정의 형식 **공급자**(38.2절의 `ICustomFormatter`)는 그 지시를 *어떻게* 번역할지 갈아 끼우는 것이다.

### 표준 숫자 형식 문자열 전수표

| 글자 | 의미 | 예 입력 | 결과 | 비고 |
|---|---|---|---|---|
| `G` / `g` | 일반(General) | `1.2345, "G"` | `1.2345` | 작거나 큰 수는 지수 표기로 전환 |
| | | `0.00001, "G"` | `1E-05` | 대문자 `G`는 `E`, 소문자 `g`는 `e` |
| | | `0.00001, "g"` | `1e-05` | |
| | | `1.2345, "G3"` | `1.23` | `G3`은 **유효 자릿수** 3자리로 제한 |
| | | `12345, "G3"` | `1.23E+04` | 유효 자릿수를 못 담으면 지수 표기 |
| `F` | 고정 소수점(Fixed point) | `2345.678, "F2"` | `2345.68` | `F2`는 소수점 이하 **2자리**로 반올림 |
| | | `2345.6, "F2"` | `2345.60` | 부족하면 0을 채운다 |
| `N` | 구분자 있는 고정 소수점(Numeric) | `2345.678, "N2"` | `2,345.68` | `F`와 같되 자릿수 구분자(`1,000`)를 넣는다 |
| | | `2345.6, "N2"` | `2,345.60` | 구분자는 형식 공급자에서 온다 |
| `D` | 앞자리 0 채우기(Decimal) | `123, "D5"` | `00123` | **정수 타입 전용** |
| | | `123, "D1"` | `123` | 자릿수가 넘쳐도 자르지 않는다 |
| `E` / `e` | 지수 표기 강제 | `56789, "E"` | `5.678900E+004` | 기본 정밀도 6자리 |
| | | `56789, "e"` | `5.678900e+004` | 소문자 `e`는 지수 기호도 소문자 |
| | | `56789, "E2"` | `5.68E+004` | |
| `C` | 통화(Currency) | `1.2, "C"` | `$1.20` | 정밀도를 생략하면 공급자의 소수 자릿수 |
| | | `1.2, "C4"` | `$1.2000` | 기호·구분자 모두 공급자에서 온다 |
| `P` | 백분율(Percent) | `.503, "P"` | `50.30%` | 100을 곱하고 기호를 붙인다 |
| | | `.503, "P0"` | `50%` | 정밀도로 소수 자릿수를 덮어쓴다 |
| `X` / `x` | 16진수(Hexadecimal) | `47, "X"` | `2F` | **정수 타입 전용** |
| | | `47, "x"` | `2f` | 소문자면 자릿수도 소문자 |
| | | `47, "X4"` | `002F` | 정밀도는 최소 자릿수(앞자리 0 채우기) |
| `B` / `b` ※.NET 8 | 2진수(Binary) | `10, "B8"` | `00001010` | **정수 타입 전용** |
| `R` (또는 `G17`/`G9`) | 왕복(Round-trip) | `1f / 3f, "R"` | `0.33333334` (.NET Framework에서는 `0.333333343`) | `BigInteger`, `double`, `float`에서 사용. .NET Core 3.0 이후 `R`은 **가장 짧은 왕복 문자열**을 낸다 |

정밀도 지정자의 **의미는 글자마다 다르다**. 이것이 표준 형식 문자열에서 가장 자주 틀리는 지점이다.

| 글자 | 정밀도 지정자의 의미 |
|---|---|
| `G` | 유효 자릿수 총합 |
| `F` `N` `C` `P` `E` | 소수점 **이하** 자릿수 |
| `D` `X` `B` | 결과의 **최소** 자릿수 (모자라면 앞을 0으로 채운다) |
| `R` | 정밀도 지정자를 받지 않는다 |

> **⚠️ `D`·`X`·`B`는 정수 타입에만 쓸 수 있다**
>
> `3.5.ToString("D2")`는 `FormatException`을 던진다. `double`에는 `D` 지정자가 정의되어 있지 않기 때문이다. `X`도 마찬가지다. `decimal`도 정수 타입이 아니므로 `X`를 못 쓴다.
>
> 반대로 `int`에 `"C"`나 `"P"`를 쓰는 것은 정상이다 — `42.ToString("C")`는 `$42.00`이다.

### `G`(생략 시 기본값)의 동작

숫자 형식 문자열을 주지 않거나, `null` 또는 빈 문자열을 주면 **정밀도 없는 `"G"`** 를 쓴 것과 같다. `G`의 동작은 다음 두 규칙으로 요약된다.

1. 10⁻⁴보다 작거나 그 타입의 정밀도보다 큰 수는 **지수(과학) 표기**로 나온다.
2. `float`나 `double`의 정밀도 한계에 있는 마지막 두 자리는 **반올림해서 지운다.** 이진 표현을 십진수로 옮길 때 생기는 오차를 감추기 위해서다.

이 자동 반올림은 대체로 이롭고 눈에 띄지 않는다. 하지만 숫자를 **왕복**시켜야 할 때 — 문자열로 바꿨다가 다시 값으로 읽으면서 값의 동등성을 유지해야 할 때 — 문제가 된다. `R`, `G17`, `G9` 형식 문자열이 이 암묵적 반올림을 우회하기 위해 존재한다.

> **📌 .NET Core 3.0 이후 기본 `ToString()`은 이미 왕복 가능하다** ※.NET Core 3.0
>
> .NET Core 3.0부터 `double.ToString()`과 `float.ToString()`은 **원래 값으로 정확히 되돌아가는 가장 짧은 문자열**을 만들도록 바뀌었다. 즉 최신 런타임에서는 `R`을 붙이지 않아도 왕복이 보장된다.
>
> 이 변화 이전(.NET Framework, .NET Core 2.x)에는 `R`이 필수였고, 심지어 `R` 자체에도 특정 값에서 왕복이 깨지는 알려진 결함이 있어 `G17`을 권장하던 시기가 있었다. **.NET Framework을 대상으로 하는 코드라면 `G17`을(`float`은 `G9`) 쓰는 편이 여전히 안전하다.**
>
> 이 차이 때문에 같은 `double` 값이 .NET Framework와 .NET 8에서 다른 문자열로 찍힐 수 있다. 두 런타임이 공유하는 파일 형식이 있다면 반드시 확인해라.

### 사용자 지정 숫자 형식 문자열 전수표

| 지정자 | 의미 | 예 입력 | 결과 | 비고 |
|---|---|---|---|---|
| `#` | 자릿수 자리 표시자 | `12.345, ".##"` | `12.35` | 마지막 `#` 위치에서 반올림 |
| | | `12.345, ".####"` | `12.345` | 값이 없으면 아무것도 안 찍는다 |
| `0` | 0 자리 표시자 | `12.345, ".00"` | `12.35` | `#`과 같되 |
| | | `12.345, ".0000"` | `12.3450` | 뒤쪽 0을 채우고 |
| | | `99, "000.00"` | `099.00` | 앞쪽 0도 채운다 |
| `.` | 소수점 | 위 예 참조 | | 실제 찍히는 문자는 `NumberFormatInfo`에서 온다 |

### 섹션 구분자의 규칙

`;`로 나뉜 섹션의 **개수**에 따라 의미가 달라진다.

| 섹션 수 | 첫째 | 둘째 | 셋째 |
|---|---|---|---|
| 1 | 모든 값 | — | — |
| 2 | 양수와 **0** | 음수 | — |
| 3 | 양수 | 음수 | 0 |

> **⚠️ 섹션이 2개 이상이면 음수 부호가 사라진다**
>
> 섹션을 두 개 이상 쓰면 음수 섹션에는 **부호가 자동으로 붙지 않는다.** 음수 값의 절댓값이 그 섹션의 템플릿으로 서식화될 뿐이다.
>
> ```csharp
> Console.WriteLine ((-5).ToString ("#;#"));      // "5"   ← 부호가 없다
> Console.WriteLine ((-5).ToString ("#;-#"));     // "-5"  ← 직접 넣어야 한다
> Console.WriteLine ((-5).ToString ("#;(#)"));    // "(5)"
> ```
>
> 회계 표기(`(1,234)`)를 만들 때 이 성질이 유용하지만, 모르고 쓰면 음수가 양수처럼 보이는 치명적인 버그가 된다.

> **⚠️ `#`만으로 이루어진 형식은 0을 빈 문자열로 만든다**
>
> ```csharp
> Console.WriteLine (0.ToString ("#"));       // ""    ← 빈 문자열
> Console.WriteLine (0.ToString ("#.##"));    // ""
> Console.WriteLine (0.ToString ("0.##"));    // "0"
> ```
>
> `#`은 "값이 있으면 찍고 없으면 생략"이라는 뜻이므로, 값이 0이면 찍을 자릿수가 없다. 0이 사라지면 안 되는 자리에는 정수부에 반드시 `0`을 하나 이상 넣어라.

> **⚠️ 사용자 지정 형식 문자열의 반올림은 `MidpointRounding.AwayFromZero`다**
>
> `12.345.ToString(".##")`이 `12.35`(`12.34`가 아니라)인 것에서 보이듯, 서식화 단계의 반올림은 0에서 먼 쪽으로 간다. `Math.Round`의 기본값(은행가 반올림)과 **다르다**(39.1절).
>
> 그래서 `Math.Round(12.345, 2)`는 `12.34`, `12.345.ToString("F2")`는 `12.35`가 나올 수 있다. 금액을 계산하고 표시하는 코드에서 이 불일치가 1센트짜리 회계 오차를 만든다. 계산 단계에서 반올림 정책을 정하고, 표시 단계에서는 이미 반올림된 값을 그대로 찍어라.

### 형식 문자열이 한 글자일 때의 모호성

한 글자짜리 문자열은 **표준 형식 문자열로 먼저 해석된다.** 사용자 지정 지정자 하나만 쓰고 싶다면 앞에 `%`를 붙이거나 다른 문자를 함께 써야 한다.

```csharp
Console.WriteLine (5.ToString ("D"));      // "5"   ← 표준 D (앞자리 0 채우기)
Console.WriteLine (5.ToString ("#"));      // "5"   ← # 은 표준 지정자가 아니므로 사용자 지정
```

날짜/시간 쪽에서는 이 모호성이 훨씬 자주 사고를 낸다(38.5절).

### 4단으로 보는 숫자 서식화

**문법** — 위 두 표가 전부다.

**컴파일 결과** — 형식 문자열은 런타임 문자열일 뿐, 컴파일러는 아무 해석도 하지 않는다. `42.ToString("N2")`는 그냥 `Int32.ToString(string, IFormatProvider)` 호출로 컴파일된다. 예외는 보간 문자열로, C# 10 이후 컴파일러가 형식 문자열 조각을 상수로 잘라 `AppendFormatted(value, format)` 호출로 낮춘다(35.7절).

```il
ldc.i4.s   42
stloc.0
ldloca.s   V_0
ldstr      "N2"
call       instance string [System.Runtime]System.Int32::ToString(string)
```

값 타입에 `ToString`을 부를 때 `ldloca` + `call`이 나오는 것에 주목해라. 박싱이 없다. `Int32`가 `ToString`을 **재정의**했기 때문에 `constrained.` 없이 직접 호출된다(15.2절, 15.5절 참고).

**런타임 동작** — 표준 형식 문자열은 런타임 내부에서 `(char fmt, int precision)` 쌍으로 파싱된 뒤 전용 경로로 분기한다. 사용자 지정 형식 문자열은 문자를 하나씩 훑는 상태 기계를 돈다. 즉 **사용자 지정 쪽이 구조적으로 더 느리다.**

**성능 영향** — 서식화 한 번의 비용은 대체로 문자열 할당이 지배한다. 최적화 순서는 다음과 같다.

| 순위 | 기법 | 할당 |
|---|---|---|
| 1 | `TryFormat`으로 스택 버퍼에 직접 쓰기(38.8절) | 없음 |
| 2 | 보간 문자열(핸들러 경로, 35.7절) | 결과 문자열 하나 |
| 3 | `CompositeFormat` + `string.Format` | 결과 문자열 하나 (형식 파싱 없음) |
| 4 | `string.Format(string, params object[])` | 배열 + 박싱 + 결과 문자열 |
| 5 | `a.ToString() + " " + b.ToString()` | 중간 문자열마다 하나씩 |

## 38.4 `NumberStyles` 파싱 플래그

### 무엇을 통제하는가

모든 숫자 타입은 `NumberStyles` 인자를 받는 정적 `Parse`/`TryParse`를 정의한다. `NumberStyles`는 **플래그 열거형**(20.3절)이고, 문자열이 숫자로 읽힐 때 **무엇을 허용할지**를 결정한다.

```csharp
namespace System.Globalization;

[Flags]
public enum NumberStyles { … }
```

핵심은 이것이다 — **허용하지 않은 문자가 하나라도 있으면 `FormatException`이다.** 서식화는 관대하지만 파싱은 엄격하다.

### 개별 플래그 전수표

| 플래그 | 값 | 허용하는 것 | 관련 `NumberFormatInfo` 속성 |
|---|---|---|---|
| `None` | 0 | 아무것도 — 숫자 자릿수만 | — |
| `AllowLeadingWhite` | 1 | 앞쪽 공백 | — |
| `AllowTrailingWhite` | 2 | 뒤쪽 공백 | — |
| `AllowLeadingSign` | 4 | 앞쪽 부호 | `PositiveSign`, `NegativeSign` |
| `AllowTrailingSign` | 8 | 뒤쪽 부호 | 위와 같음 |
| `AllowParentheses` | 16 | 음수를 뜻하는 괄호 | — |
| `AllowDecimalPoint` | 32 | 소수점 | `NumberDecimalSeparator`, `CurrencyDecimalSeparator` |
| `AllowThousands` | 64 | 자릿수 구분자 | `NumberGroupSeparator`, `NumberGroupSizes` |
| `AllowExponent` | 128 | 지수 표기(`1e6`) | `PositiveSign`, `NegativeSign` |
| `AllowCurrencySymbol` | 256 | 통화 기호 | `CurrencySymbol` |
| `AllowHexSpecifier` | 512 | 16진수 자릿수(`A`~`F`) | — |
| `AllowBinarySpecifier` ※.NET 8 | 1024 | 2진수 자릿수(`0`, `1`) | — |

### 조합 상수 전수표

`None`을 제외한 모든 조합 값은 `AllowLeadingWhite`와 `AllowTrailingWhite`를 **항상** 포함한다.

| 조합 상수 | 포함하는 플래그 |
|---|---|
| `None` | (없음) |
| `Integer` | `AllowLeadingWhite`, `AllowTrailingWhite`, `AllowLeadingSign` |
| `Number` | `Integer` + `AllowTrailingSign`, `AllowDecimalPoint`, `AllowThousands` |
| `Float` | `Integer` + `AllowDecimalPoint`, `AllowExponent` |
| `Currency` | `Number` + `AllowParentheses`, `AllowCurrencySymbol` |
| `Any` | `Currency` + `AllowExponent` (= `AllowHexSpecifier`·`AllowBinarySpecifier`를 뺀 전부) |
| `HexNumber` | `AllowLeadingWhite`, `AllowTrailingWhite`, `AllowHexSpecifier` |
| `BinaryNumber` ※.NET 8 | `AllowLeadingWhite`, `AllowTrailingWhite`, `AllowBinarySpecifier` |

```text
                 AllowLeadingWhite + AllowTrailingWhite  (None을 제외한 전부에 포함)
                                   │
  ┌────────────────────────────────┼──────────────────────────────┐
  │                                │                              │
Integer                        HexNumber                    BinaryNumber
  + AllowLeadingSign             + AllowHexSpecifier          + AllowBinarySpecifier
  │
  ├─────────────────────┐
  │                     │
Number                 Float
  + AllowTrailingSign     + AllowDecimalPoint
  + AllowDecimalPoint     + AllowExponent
  + AllowThousands
  │
  ▼
Currency
  + AllowParentheses
  + AllowCurrencySymbol
  │
  ▼
Any
  + AllowExponent
```

**조합 `NumberStyles`의 구성** — 실무에서 자주 쓰는 셋은 `Integer`, `Float`, `Currency`다.

### 타입별 기본 파싱 플래그

플래그를 지정하지 않고 `Parse`를 부르면 타입마다 다른 기본값이 적용된다.

| 타입 | 기본 `NumberStyles` | 결과적으로 허용되는 것 |
|---|---|---|
| `int`, `long`, `short`, `byte`, `sbyte`, `uint`, `ulong`, `ushort`, `nint`, `nuint`, `Int128`, `UInt128`, `BigInteger` | `Integer` | 공백, 앞쪽 부호 |
| `float`, `double`, `Half` | `Float \| AllowThousands` | 공백, 앞쪽 부호, 소수점, 지수, 자릿수 구분자 |
| `decimal` | `Number` | 공백, 앞뒤 부호, 소수점, 자릿수 구분자 (**지수는 불가**) |

> **⚠️ `decimal.Parse("3e6")`은 기본값으로 실패한다**
>
> `decimal`의 기본 스타일은 `Number`이고 `Number`에는 `AllowExponent`가 없다. 반면 `double.Parse("3e6")`은 성공한다. 같은 문자열이 타입에 따라 성공하기도 실패하기도 한다.
>
> ```csharp
> double d = double.Parse ("3e6");                            // 3000000
> decimal m = decimal.Parse ("3e6");                          // FormatException
> decimal ok = decimal.Parse ("3e6", NumberStyles.Any);       // 3000000
> ```
>
> 반대로 `int.Parse("1,000")`도 실패한다 — `Integer`에 `AllowThousands`가 없기 때문이다. `double.Parse("1,000")`은 성공해서 1000이 된다(단, 문화권에 따라 다르다).

### 사용 예

```csharp
int thousand   = int.Parse ("3E8", NumberStyles.HexNumber);
int minusTwo   = int.Parse ("(2)", NumberStyles.Integer |
                                   NumberStyles.AllowParentheses);
double aMillion = double.Parse ("1,000,000", NumberStyles.Any);
decimal threeMillion = decimal.Parse ("3e6", NumberStyles.Any);
decimal fivePointTwo = decimal.Parse ("$5.20", NumberStyles.Currency);
```

위 예에는 형식 공급자를 넘기지 않았으므로 **로컬 통화 기호·구분자·소수점**이 적용된다. 다음은 유로 기호와 공백 구분자로 고정한 예다.

```csharp
NumberFormatInfo ni = new NumberFormatInfo();
ni.CurrencySymbol = "€";
ni.CurrencyGroupSeparator = " ";
double million = double.Parse ("€1 000 000", NumberStyles.Currency, ni);
```

> **⚠️ `AllowHexSpecifier`에 `0x` 접두사를 붙이면 실패한다**
>
> `AllowHexSpecifier`는 16진 **자릿수**를 허용할 뿐, C# 소스의 `0x` 접두사를 알지 못한다.
>
> ```csharp
> int.Parse ("0x1E", NumberStyles.HexNumber);   // FormatException
> int.Parse ("1E",   NumberStyles.HexNumber);   // 30
> ```
>
> 접두사가 붙어 올 수 있다면 직접 벗겨야 한다.
>
> ```csharp
> ReadOnlySpan<char> s = input;
> if (s.StartsWith ("0x", StringComparison.OrdinalIgnoreCase)) s = s[2..];
> int v = int.Parse (s, NumberStyles.HexNumber, CultureInfo.InvariantCulture);
> ```
>
> 또한 `AllowHexSpecifier`는 `AllowLeadingSign`과 **함께 쓸 수 없다.** `"-1E"`를 16진으로 파싱하려 하면 `ArgumentException`이 난다. 16진 문자열의 음수는 최상위 비트로 표현되기 때문이다 — `int.Parse("FFFFFFFF", NumberStyles.HexNumber)`는 `-1`이다.

> **⚠️ `AllowThousands`는 구분자의 *위치*를 검사하지 않는다**
>
> `double.Parse("1,0,0,0", NumberStyles.Any)`는 예외 없이 1000을 낸다. 파서는 구분자를 만나면 그냥 건너뛴다. 즉 **`NumberStyles`는 검증 도구가 아니다.** 입력 형식을 엄격히 강제해야 한다면 정규식(36장)으로 먼저 검사하거나, 필요한 플래그만 최소로 켜라.

> **💡 `NumberStyles`는 최소로 켜는 것이 원칙이다**
>
> `NumberStyles.Any`는 편해 보이지만 통화 기호·괄호·자릿수 구분자를 전부 허용하므로, 잘못된 입력이 조용히 통과한다. `Any`를 쓰는 코드는 사실상 "입력을 검증하지 않겠다"고 선언하는 것이다.
>
> 기계가 만든 데이터를 읽을 때 저자의 기본값은 이것이다.
>
> ```csharp
> // 정수 필드: 부호도 공백도 허용하지 않는다
> bool ok = int.TryParse (field, NumberStyles.None,
>                         CultureInfo.InvariantCulture, out int v);
>
> // 실수 필드: 부호와 소수점만
> bool ok2 = double.TryParse (field,
>                             NumberStyles.AllowLeadingSign | NumberStyles.AllowDecimalPoint,
>                             CultureInfo.InvariantCulture, out double d);
> ```
>
> 공급자를 반드시 함께 넘긴다. 플래그만 지정하고 공급자를 생략하면 여전히 `CurrentCulture`가 적용되어 소수점 문자가 뒤바뀐다.

### 파싱은 서식화의 정확한 역함수가 아니다

**런타임 동작** — 서식화와 파싱은 대칭이 아니다. 서식화는 `NumberFormatInfo`의 패턴 속성(`CurrencyNegativePattern` 등)을 따라 정확히 한 가지 결과를 만들지만, 파싱은 여러 표현을 **관대하게** 받아들인다. 예컨대 `Currency` 스타일은 통화 기호가 앞에 있든 뒤에 있든 받아들인다.

이 비대칭 때문에 "`ToString`한 결과가 `Parse`로 되돌아온다"는 보장이 없다.

| 값 | `ToString("C")` (en-US) | `Parse(…, NumberStyles.Currency)` | 왕복? |
|---|---|---|---|
| `1234.5m` | `$1,234.50` | 성공 | 예 |
| `-1234.5m` | `($1,234.50)` | 성공 (`AllowParentheses` 포함) | 예 |
| `1234.5m` | `$1,234.50` | `NumberStyles.Number`로 파싱 | **실패** — 통화 기호 |
| `double.NaN` | `NaN` | `double.Parse("NaN")` | 예 (`NaNSymbol` 일치 시) |
| `double.PositiveInfinity` | `∞` | `double.Parse("∞")` | 문화권이 같아야 성공 |

> **⚠️ `NaN`과 `∞`의 문자열은 문화권마다 다르다**
>
> `NumberFormatInfo.NaNSymbol`, `PositiveInfinitySymbol`, `NegativeInfinitySymbol`은 문화권 데이터에서 온다. 한 문화권에서 찍은 `∞`를 다른 문화권에서 파싱하면 실패할 수 있다. 특수값이 나올 수 있는 데이터를 직렬화한다면 문화권을 고정하거나(38.11절), 아예 특수값을 별도 표기로 치환해라.

## 38.5 표준·사용자 지정 날짜/시간 형식 문자열

### 두 그룹

`DateTime`/`DateTimeOffset`의 형식 문자열은 **문화권과 형식 공급자 설정을 존중하는가**를 기준으로 두 그룹으로 갈린다. 이 구분이 날짜 서식에서 가장 중요한 사실이다.

이후 표의 예시 출력은 다음 값을 서식화한 결과다(문화권 인식 형식은 불변 문화권 기준).

```csharp
new DateTime (2000, 1, 2, 17, 18, 19);
```

### 문화권 인식 표준 형식 문자열

| 형식 문자열 | 의미 | 예 출력(불변 문화권) | 대응 `DateTimeFormatInfo` 속성 |
|---|---|---|---|
| `d` | 짧은 날짜 | `01/02/2000` | `ShortDatePattern` |
| `D` | 긴 날짜 | `Sunday, 02 January 2000` | `LongDatePattern` |
| `t` | 짧은 시각 | `17:18` | `ShortTimePattern` |
| `T` | 긴 시각 | `17:18:19` | `LongTimePattern` |
| `f` | 긴 날짜 + 짧은 시각 | `Sunday, 02 January 2000 17:18` | `LongDatePattern` + `ShortTimePattern` |
| `F` | 긴 날짜 + 긴 시각 | `Sunday, 02 January 2000 17:18:19` | `FullDateTimePattern` |
| `g` | 짧은 날짜 + 짧은 시각 | `01/02/2000 17:18` | `ShortDatePattern` + `ShortTimePattern` |
| `G` (기본값) | 짧은 날짜 + 긴 시각 | `01/02/2000 17:18:19` | `ShortDatePattern` + `LongTimePattern` |
| `m`, `M` | 월과 일 | `02 January` | `MonthDayPattern` |
| `y`, `Y` | 연과 월 | `January 2000` | `YearMonthPattern` |

### 문화권 비인식 표준 형식 문자열

| 형식 문자열 | 의미 | 예 출력 | 비고 |
|---|---|---|---|
| `o`, `O` | 왕복(round-trippable) | `2000-01-02T17:18:19.0000000` | `DateTimeKind`가 `Unspecified`가 아니면 시간대 정보를 덧붙인다 |
| `r`, `R` | RFC 1123 표준 | `Sun, 02 Jan 2000 17:18:19 GMT` | UTC로 **직접** 변환해야 한다(`DateTime.ToUniversalTime`) |
| `s` | 정렬 가능, ISO 8601 | `2000-01-02T17:18:19` | 텍스트 정렬과 호환된다 |
| `u` | "범용" 정렬 가능 | `2000-01-02 17:18:19Z` | 위와 비슷하되 UTC로 직접 변환해야 한다 |
| `U` | UTC | `Sunday, 02 January 2000 17:18:19` | 긴 날짜 + 긴 시각을 UTC로 변환해서 출력 |

> **⚠️ `r`·`R`·`u`는 UTC라고 써 놓고 변환은 안 해 준다**
>
> 이 셋은 UTC를 암시하는 접미사(`GMT`, `Z`)를 출력하지만, **로컬 `DateTime`을 UTC로 자동 변환하지 않는다.** 즉 서울 시각 17:18을 `"R"`로 찍으면 `Sun, 02 Jan 2000 17:18:19 GMT`가 나온다. 실제 UTC는 08:18인데도 그렇다. **9시간 틀린 문자열**이 만들어진다.
>
> 반대로 `"U"`는 UTC로 **자동 변환하지만 시간대 접미사를 쓰지 않는다.** 정확한 시점을 담지만 그 사실이 문자열에 드러나지 않는다.
>
> 이 그룹에서 개입 없이 명확한 `DateTime`을 쓸 수 있는 지정자는 **`"o"` 하나뿐이다.**
>
> ```csharp
> var local = new DateTime (2000, 1, 2, 17, 18, 19, DateTimeKind.Local);
> Console.WriteLine (local.ToString ("R"));                       // 17:18:19 GMT — 틀렸다
> Console.WriteLine (local.ToUniversalTime().ToString ("R"));     // 08:18:19 GMT — 맞다
> Console.WriteLine (local.ToString ("o"));                       // 2000-01-02T17:18:19.0000000+09:00
> ```

`"o"`가 `DateTimeKind`(37.4절)를 어떻게 인코딩하는지 정리하면 다음과 같다.

| `Kind` | `"o"` 출력 접미사 | 되읽을 때 |
|---|---|---|
| `Utc` | `Z` | `RoundtripKind`로 파싱하면 `Utc` 복원 |
| `Local` | 실제 오프셋 (`+09:00`) | `RoundtripKind`로 파싱하면 `Local` 복원 |
| `Unspecified` | 없음 | `Unspecified` 그대로 |

`DateTimeOffset`은 `Kind` 개념이 없으므로 `"o"`가 언제나 오프셋을 붙인다.

> **📌 `"s"`와 `"u"`는 텍스트 정렬이 곧 시간 정렬이다**
>
> `yyyy-MM-dd` 순서는 자릿수가 고정되어 있고 큰 단위가 앞에 오므로, **문자열을 서수 비교로 정렬하면 시간순 정렬이 된다.** 파일 이름이나 로그 키에 시각을 넣을 때 이 성질이 유용하다. `"o"`도 같은 성질을 갖는다.
>
> 반대로 `"d"`(`01/02/2000`)나 `"R"`(`Sun, 02 Jan 2000`)은 정렬하면 뒤죽박죽이 된다.

### 사용자 지정 날짜/시간 형식 문자열 전수표

`DateTimeFormatInfo`는 사용자 지정 형식 문자열도 지원한다. 숫자 쪽과 구조가 같다.

**날짜 구성 요소**

| 지정자 | 의미 | 예 출력(2000-01-02, `en-US`) |
|---|---|---|
| `d` | 일 (1~31, 앞자리 0 없음) | `2` |
| `dd` | 일 (01~31, 앞자리 0 채움) | `02` |
| `ddd` | 요일 약칭 | `Sun` |
| `dddd` | 요일 전체 이름 | `Sunday` |
| `M` | 월 (1~12) | `1` |
| `MM` | 월 (01~12) | `01` |
| `MMM` | 월 약칭 | `Jan` |
| `MMMM` | 월 전체 이름 | `January` |
| `y` | 연도 마지막 두 자리, 앞자리 0 없음 | `0` |
| `yy` | 연도 마지막 두 자리 | `00` |
| `yyy` | 최소 세 자리 연도 | `2000` |
| `yyyy` | 네 자리 연도 | `2000` |
| `yyyyy` | 다섯 자리 연도 | `02000` |
| `g`, `gg` | 연호(era) | `A.D.` |

**시각 구성 요소**

| 지정자 | 의미 | 예 출력(17:18:19.1234567) |
|---|---|---|
| `h` | 12시간제 시 (1~12) | `5` |
| `hh` | 12시간제 시 (01~12) | `05` |
| `H` | 24시간제 시 (0~23) | `17` |
| `HH` | 24시간제 시 (00~23) | `17` |
| `m` | 분 (0~59) | `18` |
| `mm` | 분 (00~59) | `18` |
| `s` | 초 (0~59) | `19` |
| `ss` | 초 (00~59) | `19` |
| `f` ~ `fffffff` | 소수 초, **0을 포함해 항상 출력** | `f`→`1`, `fff`→`123`, `fffffff`→`1234567` |
| `F` ~ `FFFFFFF` | 소수 초, **뒤쪽 0은 생략** | 값이 `.1200000`이면 `FFF`→`12` |
| `t` | AM/PM 지정자의 첫 글자 | `P` |
| `tt` | AM/PM 지정자 전체 | `PM` |

**시간대 구성 요소**

| 지정자 | 의미 | `DateTime`에서 | `DateTimeOffset`에서 |
|---|---|---|---|
| `z` | UTC 오프셋 시 (부호 포함, 앞자리 0 없음) | 로컬 시간대 오프셋 | 값의 오프셋 |
| `zz` | UTC 오프셋 시 (두 자리) | `+09` | `+09` |
| `zzz` | UTC 오프셋 시:분 | `+09:00` | `+09:00` |
| `K` | `Kind`에 따른 시간대 표기 | `Utc`→`Z`, `Local`→`+09:00`, `Unspecified`→빈 문자열 | 항상 오프셋 |

**구분자와 리터럴**

| 지정자 | 의미 |
|---|---|
| `:` | 시간 구분자 — 실제 문자는 `DateTimeFormatInfo.TimeSeparator` |
| `/` | 날짜 구분자 — 실제 문자는 `DateTimeFormatInfo.DateSeparator` |
| `'문자열'` `"문자열"` | 리터럴 문자열 (그대로 출력) |
| `\문자` | 다음 한 문자를 리터럴로 |
| `%지정자` | 한 글자짜리 사용자 지정 지정자임을 명시 |
| 그 외 | 리터럴로 출력 |

> **⚠️ `z`는 `DateTime`에서 거짓말을 한다**
>
> `DateTime`은 오프셋을 저장하지 않는다(37.2절). 그런데 `z`/`zz`/`zzz`는 값을 요구받으면 **실행 중인 컴퓨터의 로컬 시간대 오프셋**을 찍는다. `Kind`가 `Unspecified`든 `Utc`든 상관없이 그렇다.
>
> ```csharp
> var utc = new DateTime (2000, 1, 2, 17, 18, 19, DateTimeKind.Utc);
> Console.WriteLine (utc.ToString ("HH:mm zzz"));    // 서울 PC에서 "17:18 +09:00" — 틀렸다
> Console.WriteLine (utc.ToString ("HH:mm K"));      // "17:18 Z" — 맞다
> ```
>
> `DateTime`에는 `z` 대신 **`K`** 를 써라. 오프셋이 진짜로 필요하다면 애초에 `DateTimeOffset`을 써야 한다.

> **⚠️ 한 글자짜리 사용자 지정 형식 문자열은 표준 형식으로 해석된다**
>
> ```csharp
> dt.ToString ("d");     // 표준 "짧은 날짜" — "01/02/2000"
> dt.ToString ("%d");    // 사용자 지정 "일" — "2"
> dt.ToString ("dd");    // 사용자 지정 "일 두 자리" — "02"
> ```
>
> 사용자 지정 지정자 하나만 쓰고 싶으면 `%`를 앞에 붙이거나 다른 문자를 함께 써야 한다. 이 규칙을 모르면 `"M"`이 월을 낼 거라 기대했다가 `"02 January"`(`MonthDayPattern`)를 받는다.

> **⚠️ `MM`과 `mm`을 바꿔 쓰는 것이 이 장에서 가장 흔한 오타다**
>
> 대문자 `M`은 **월**, 소문자 `m`은 **분**이다. `"yyyy-mm-dd"`는 컴파일도 되고 실행도 되지만 월 자리에 분이 들어간다. 마찬가지로 `H`는 24시간제, `h`는 12시간제다. `"hh:mm"`으로 로그를 찍으면 오후 5시가 `05:18`이 되어 오전과 구별되지 않는다.
>
> | 잘못 쓴 형식 | 나오는 것 | 의도 |
> |---|---|---|
> | `yyyy-mm-dd` | `2000-18-02` | `yyyy-MM-dd` |
> | `hh:mm:ss` (AM/PM 없이) | `05:18:19` | `HH:mm:ss` |
> | `YYYY-MM-DD` | `FormatException` 또는 리터럴 | `yyyy-MM-dd` |
>
> `Y`와 `D`는 사용자 지정 지정자가 아니다. 형식 문자열에 다른 지정자가 함께 있으면 리터럴 문자로 출력되고, 혼자 있으면 표준 형식 문자열로 해석된다.

### 실무에서 쓰는 사용자 지정 패턴

```csharp
"yyyy-MM-dd"                 // 2000-01-02
"yyyy-MM-dd HH:mm:ss"        // 2000-01-02 17:18:19
"yyyy-MM-ddTHH:mm:ssK"       // "o"와 같되 밀리초 없음
"yyyy'년' M'월' d'일'"        // 2000년 1월 2일 (한글 리터럴은 따옴표로 감싼다)
"HH:mm:ss.fff"               // 17:18:19.123
```

원천 문헌이 명시하듯 `"o"` 형식 문자열은 출력에 소수 초를 포함한다. 소수 초 없이 같은 결과를 원하면 위의 `yyyy-MM-ddTHH:mm:ssK`를 쓴다.

> **📌 한글 리터럴을 따옴표로 감싸야 하는 이유**
>
> `"yyyy년 M월 d일"`은 대체로 잘 동작하지만, 형식 문자열 파서는 지정자가 아닌 문자를 만나면 리터럴로 취급하되 일부 문자(`:`, `/`, `%`, `\`, `'`, `"`)를 특별 취급한다. 한글은 특별 문자가 아니므로 실제로는 따옴표 없이도 나온다. 그래도 감싸는 습관을 들이면 나중에 형식 문자열 안에 `/`나 `:`가 섞였을 때 사고를 피한다.

### 파싱과 오파싱

월이나 일을 앞에 두는 문자열은 **모호하고 오파싱되기 쉽다.** 특히 전 세계 고객을 상대한다면 그렇다.

`01/02/2000`이라는 문자열은 미국에서 1월 2일이고 영국에서 2월 1일이다. UI 컨트롤 안에서는 서식화할 때와 파싱할 때 같은 설정이 적용되므로 문제가 되지 않는다. 하지만 **파일에 쓸 때**는 날짜/월 오파싱이 실제 문제가 된다.

해법은 둘이다.

1. 서식화할 때와 파싱할 때 **항상 같은 명시적 문화권**을 지정한다(예: 불변 문화권).
2. 애초에 **문화권과 무관한 방식**으로 `DateTime`과 `DateTimeOffset`을 서식화한다.

두 번째가 더 견고하다. 특히 **네 자리 연도를 앞에 두는 형식**을 고르면 그렇다. 그런 문자열은 다른 시스템이 오파싱하기가 훨씬 어렵다. 게다가 `"o"` 같은 표준 준수 연도 우선 형식으로 만든 문자열은 로컬 형식 문자열과 **나란히 두고도 올바르게 파싱된다** — 일종의 "만능 공혈자" 같은 성질이다. `"s"`나 `"u"`로 만든 날짜는 정렬 가능하다는 이점까지 갖는다.

문화권 비인식 문자열을 만들었다고 하자.

```csharp
string s = DateTime.Now.ToString ("o");
```

되읽는 방법은 둘이다. `ParseExact`는 지정한 형식 문자열을 **엄격하게** 요구한다.

```csharp
DateTime dt1 = DateTime.ParseExact (s, "o", null);
```

`Parse`는 `"o"` 형식과 `CurrentCulture` 형식을 **둘 다** 암묵적으로 받아들인다.

```csharp
DateTime dt2 = DateTime.Parse (s);
```

둘 다 `DateTime`과 `DateTimeOffset`에서 동작한다. `XmlConvert`의 `ToString`/`ToDateTime`으로도 비슷한 결과를 얻을 수 있다(38.9절).

> **💡 파싱할 문자열의 형식을 안다면 `ParseExact`가 낫다**
>
> 형식이 틀렸을 때 예외가 던져진다는 뜻이고, 이는 날짜가 잘못 해석될 위험을 감수하는 것보다 대체로 낫다. 조용히 틀린 날짜가 데이터베이스에 들어가는 것보다 요란하게 실패하는 편이 싸다.
>
> `TryParseExact`는 형식 문자열 **배열**을 받는 오버로드가 있다. 여러 형식을 순서대로 시도한다.
>
> ```csharp
> string[] formats = { "yyyy-MM-dd", "yyyy/MM/dd", "yyyyMMdd" };
> bool ok = DateTime.TryParseExact (input, formats,
>                                   CultureInfo.InvariantCulture,
>                                   DateTimeStyles.None, out DateTime result);
> ```

### `TimeSpan`, `DateOnly`, `TimeOnly`의 형식 문자열

`TimeSpan`은 별도의 형식 문자열 체계를 갖는다.

| 형식 문자열 | 의미 | 예 (`1.02:03:04.5000000`) |
|---|---|---|
| `c` (또는 `null`, `""`) | 불변(constant) — 문화권 비인식 | `1.02:03:04.5000000` |
| `g` | 일반 짧은 형식 — 문화권 인식 | `1:2:03:04.5` |
| `G` | 일반 긴 형식 — 문화권 인식 | `1:02:03:04.5000000` |

`TimeSpan`의 사용자 지정 지정자는 `d`, `h`, `m`, `s`, `f` 계열이며, 리터럴은 반드시 따옴표나 `\`로 이스케이프해야 한다. `TimeSpan`에는 표준/사용자 지정 구분의 모호성이 없는 대신, **한 글자 사용자 지정 형식 문자열이 금지**되어 있어 `"%h"`처럼 써야 한다.

`DateOnly`와 `TimeOnly`(37.3절)는 `DateTime`의 형식 문자열 체계를 그대로 쓰되, 자기가 담지 않는 구성 요소를 요구하면 `FormatException`이 난다. `DateOnly.ToString("HH:mm")`은 실패한다.

## 38.6 `DateTimeStyles` 파싱 플래그

### 무엇을 통제하는가

`DateTimeStyles`는 `DateTime`/`DateTimeOffset`의 `Parse`·`TryParse`·`ParseExact`·`TryParseExact`에 추가 지시를 주는 플래그 열거형이다. `NumberStyles`가 "어떤 문자를 허용할까"를 다룬다면, `DateTimeStyles`는 거기에 더해 **결과값의 시간대 해석**까지 다룬다. 이 두 번째 역할이 훨씬 중요하다.

```csharp
namespace System.Globalization;

[Flags]
public enum DateTimeStyles { … }
```

### 전수표

| 플래그 | 분류 | 동작 |
|---|---|---|
| `None` | 기본값 | 아무 특별 처리도 하지 않는다 |
| `AllowLeadingWhite` | 공백 | 앞쪽 공백을 무시한다 |
| `AllowTrailingWhite` | 공백 | 뒤쪽 공백을 무시한다 |
| `AllowInnerWhite` | 공백 | 구성 요소 사이의 공백을 무시한다 |
| `AllowWhiteSpaces` | 공백(조합) | 위 세 개를 모두 켠다 |
| `AssumeLocal` | 시간대 | 문자열에 시간대 정보가 **없으면** 로컬 시각으로 간주 |
| `AssumeUniversal` | 시간대 | 문자열에 시간대 정보가 **없으면** UTC로 간주 |
| `AdjustToUniversal` | 시간대 | 시간대 접미사를 존중하되, 결과를 UTC로 **변환**한다 |
| `RoundtripKind` | 시간대 | 문자열에 표기된 그대로 `DateTimeKind`를 복원한다 |
| `NoCurrentDateDefault` | 날짜 보완 | 날짜 없는 문자열에 오늘 날짜 대신 **0001년 1월 1일**을 채운다 |

조합 상수는 하나뿐이다.

```csharp
AllowWhiteSpaces = AllowLeadingWhite | AllowTrailingWhite | AllowInnerWhite
```

기본값은 `None`이다. **여분의 공백은 원래 금지된다** — 표준 `DateTime` 패턴의 일부인 공백은 예외다.

### 시간대 플래그의 실제 동작

`AssumeLocal`과 `AssumeUniversal`은 문자열에 `Z`나 `+9:00` 같은 시간대 접미사가 **없을 때** 적용된다. `AdjustToUniversal`은 시간대 접미사를 여전히 존중하되, 그 다음 현재 지역 설정을 써서 UTC로 변환한다.

여기서 한 가지를 먼저 못 박아 두어야 한다. **`AssumeUniversal`은 "UTC로 간주"까지만 하고, 결과를 UTC로 남겨 두지는 않는다.** `AdjustToUniversal`을 함께 켜지 않으면 파서는 "UTC로 해석한 값"을 다시 로컬 시각으로 변환해 `Kind`가 `Local`인 값을 돌려준다. UTC 값을 그대로 받고 싶다면 `AssumeUniversal | AdjustToUniversal`을 함께 지정해야 한다. 반면 `AssumeLocal`은 값을 그대로 두고 `Kind`만 `Local`로 표시한다 — 두 플래그의 대칭성이 깨져 있는 지점이다.

시나리오별로 정리하면 이렇다. 로컬 시간대가 `UTC+09:00`이라고 가정한다.

| 입력 문자열 | `DateTimeStyles` | 결과 시각 | 결과 `Kind` |
|---|---|---|---|
| `"2000-01-02T17:18:19"` | `None` | 17:18:19 | `Unspecified` |
| `"2000-01-02T17:18:19"` | `AssumeLocal` | 17:18:19 | `Local` |
| `"2000-01-02T17:18:19"` | `AssumeUniversal` | 02:18:19 (다음 날, 로컬로 변환) | `Local` |
| `"2000-01-02T17:18:19"` | `AssumeUniversal \| AdjustToUniversal` | 17:18:19 | `Utc` |
| `"2000-01-02T17:18:19"` | `AssumeLocal \| AdjustToUniversal` | 08:18:19 | `Utc` |
| `"2000-01-02T17:18:19Z"` | `None` | 02:18:19 (로컬로 변환) | `Local` |
| `"2000-01-02T17:18:19Z"` | `RoundtripKind` | 17:18:19 | `Utc` |
| `"2000-01-02T17:18:19Z"` | `AdjustToUniversal` | 17:18:19 | `Utc` |
| `"2000-01-02T17:18:19+09:00"` | `RoundtripKind` | 17:18:19 | `Local` |
| `"2000-01-02T17:18:19+09:00"` | `AdjustToUniversal` | 08:18:19 | `Utc` |

> **⚠️ `DateTime.Parse`의 기본 동작이 `Z`를 로컬로 바꾼다**
>
> 위 표의 여섯 번째 행이 실무에서 가장 많은 사고를 낸다. `Z` 접미사가 붙은 UTC 문자열을 `DateTime.Parse`로 아무 플래그 없이 읽으면, 값이 **로컬 시각으로 변환되고 `Kind`가 `Local`이 된다.** 시점 자체는 같으므로 "틀렸다"고 말하기 애매하지만, UTC를 기대한 코드에서는 예상과 다르다(37.4절에서 미리 짚었다).
>
> - UTC로 받고 싶다면 → `DateTimeStyles.AdjustToUniversal`
> - 문자열에 적힌 그대로의 `Kind`를 원한다면 → `DateTimeStyles.RoundtripKind`
>
> 이 사고를 근본적으로 피하는 방법은 `DateTime` 대신 `DateTimeOffset`을 쓰는 것이다(37.5절). `DateTimeOffset.Parse`는 오프셋을 값의 일부로 보존하므로 이 함정이 없다.

> **⚠️ `AssumeLocal`과 `AssumeUniversal`은 함께 쓸 수 없다**
>
> 두 플래그를 동시에 켜면 `ArgumentException`이 난다. 서로 모순되는 지시이기 때문이다.
>
> `RoundtripKind`는 "문자열에 적힌 대로"를 뜻하므로 `AssumeLocal`/`AssumeUniversal`/`AdjustToUniversal`과 의미가 충돌한다. 예외가 나지 않더라도 결과가 어느 쪽 규칙을 따르는지 읽는 사람이 알 수 없으니, **시간대 플래그는 하나만 켜라.**

### `NoCurrentDateDefault`

시각만 있고 날짜가 없는 문자열을 파싱하면 기본적으로 **오늘 날짜**가 채워진다. `NoCurrentDateDefault` 플래그를 주면 대신 0001년 1월 1일이 쓰인다.

```csharp
DateTime a = DateTime.Parse ("17:18");
// 2026-09-07 17:18:00 (오늘이 2026-09-07이라면)

DateTime b = DateTime.Parse ("17:18", CultureInfo.InvariantCulture,
                             DateTimeStyles.NoCurrentDateDefault);
// 0001-01-01 17:18:00
```

> **⚠️ 시각만 파싱하는 코드는 자정에 깨진다**
>
> `DateTime.Parse("23:50")`으로 근무 종료 시각을 읽고 `DateTime.Parse("00:10")`으로 다음 근무 시작 시각을 읽으면, 둘 다 **오늘 날짜**를 받는다. 자정을 넘긴 근무를 계산하면 결과가 음수가 된다.
>
> 게다가 `DateTime.Parse("23:50")`을 23:59:59에 부르는 것과 00:00:01에 부르는 것은 **다른 날짜**를 만든다. 테스트가 자정 근처에서만 깨지는 유명한 유형의 버그다.
>
> .NET 6 이후라면 시각만 다루는 값에는 `TimeOnly`를 써라(37.3절). `TimeOnly.Parse("23:50")`에는 날짜가 아예 없다.

### `ParseExact`와 스타일의 상호작용

`ParseExact`는 형식 문자열과 정확히 맞아떨어질 것을 요구하지만, `DateTimeStyles`는 여기서도 유효하다. 특히 공백 플래그가 중요하다.

```csharp
// 입력에 앞뒤 공백이 있을 수 있는 CSV
bool ok = DateTime.TryParseExact (field.Trim(), "yyyy-MM-dd",
                                  CultureInfo.InvariantCulture,
                                  DateTimeStyles.None, out DateTime d);

// 또는 Trim 없이 플래그로
bool ok2 = DateTime.TryParseExact (field, "yyyy-MM-dd",
                                   CultureInfo.InvariantCulture,
                                   DateTimeStyles.AllowWhiteSpaces, out DateTime d2);
```

> **💡 저장·전송용 날짜 파싱의 표준 조합**
>
> 기계가 만든 ISO 8601 문자열을 읽을 때 저자의 기본값은 다음 셋 중 하나다.
>
> ```csharp
> // 1) DateTimeOffset을 쓸 수 있다면 — 가장 안전
> var dto = DateTimeOffset.Parse (s, CultureInfo.InvariantCulture);
>
> // 2) DateTime으로 받되 UTC로 정규화
> var utc = DateTime.Parse (s, CultureInfo.InvariantCulture,
>                           DateTimeStyles.AdjustToUniversal | DateTimeStyles.AssumeUniversal);
>
> // 3) 형식이 고정이고 Kind를 그대로 복원해야 할 때
> var rt = DateTime.ParseExact (s, "o", CultureInfo.InvariantCulture,
>                               DateTimeStyles.RoundtripKind);
> ```
>
> 세 경우 모두 **문화권을 명시했다.** `DateTimeStyles`만 넘기고 공급자를 `null`로 두면 여전히 `CurrentCulture`가 적용되어, 태국 로캘에서는 불교력으로 해석될 수 있다(38.10절).

## 38.7 열거형 형식 문자열

### 네 개가 전부다

20장에서 열거형 값의 서식화와 파싱을 다뤘다. 형식 문자열은 정확히 네 종류다. 아래 표의 출력은 다음 식의 결과다.

```csharp
Console.WriteLine (System.ConsoleColor.Red.ToString (formatString));
```

| 형식 문자열 | 의미 | 예 출력 | 비고 |
|---|---|---|---|
| `G` / `g` | 일반(General) | `Red` | 기본값 |
| `F` / `f` | `Flags` 특성이 있는 것처럼 취급 | `Red` | `Flags` 특성이 **없어도** 조합된 멤버에서 동작한다 |
| `D` / `d` | 십진 값 | `12` | 기저 정수 값을 가져온다 |
| `X` / `x` | 16진 값 | `0000000C` | 기저 정수 값을 가져온다 |

`X` 형식의 자릿수는 **기저 타입의 크기**로 결정된다. `int` 기저면 8자리, `byte` 기저면 2자리다.

```csharp
enum Small : byte { A = 1, B = 2 }
Console.WriteLine (Small.B.ToString ("X"));   // "02"
```

### `G`와 `F`의 차이

`G`는 값과 정확히 일치하는 멤버가 있으면 그 이름을, 없으면 다음을 한다.

- 열거형에 `[Flags]`가 있으면 → 비트를 분해해 `A, B` 형태로 쓴다
- `[Flags]`가 없으면 → 숫자를 그대로 쓴다

`F`는 `[Flags]` 여부와 무관하게 **항상 비트를 분해하려 시도한다.**

```csharp
enum Plain { A = 1, B = 2, C = 4 }        // Flags 없음

Plain v = Plain.A | Plain.B;              // 값 3

Console.WriteLine (v.ToString ("G"));     // "3"
Console.WriteLine (v.ToString ("F"));     // "A, B"
```

> **⚠️ 열거형의 `ToString()`은 리플렉션을 쓴다**
>
> `enum.ToString()`은 값에 대응하는 **이름**을 찾아야 하고, 그 이름은 메타데이터에 있다. 런타임은 열거형 타입별로 이름/값 배열을 만들어 캐시하지만, 첫 호출은 리플렉션 비용을 낸다.
>
> **성능 영향** — 로그 한 줄마다 열거형을 문자열로 찍는 코드는 생각보다 비싸다. 정수 값만 필요하면 `((int)v).ToString()`이, 이름이 필요하고 값이 몇 개뿐이면 `switch` 식으로 상수 문자열을 돌려주는 편이 훨씬 빠르다.
>
> ```csharp
> static string Name (LogLevel l) => l switch
> {
>     LogLevel.Trace => "TRACE",
>     LogLevel.Debug => "DEBUG",
>     LogLevel.Info  => "INFO",
>     _              => l.ToString()      // 드문 경우만 느린 경로로
> };
> ```

### `Enum.Parse`와 `Enum.TryParse`

```csharp
// 대소문자 구분 (기본)
ConsoleColor c1 = (ConsoleColor) Enum.Parse (typeof (ConsoleColor), "Red");

// 대소문자 무시
ConsoleColor c2 = (ConsoleColor) Enum.Parse (typeof (ConsoleColor), "red", true);

// 제네릭 버전 (권장)
bool ok = Enum.TryParse<ConsoleColor> ("red", ignoreCase: true, out var c3);
```

| 메서드 | 시그니처 | 실패 시 |
|---|---|---|
| `Enum.Parse(Type, string)` | 대소문자 구분 | `ArgumentException` |
| `Enum.Parse(Type, string, bool)` | 세 번째 인자가 `ignoreCase` | `ArgumentException` |
| `Enum.Parse<TEnum>(string)` | 제네릭, 박싱 없음 | `ArgumentException` |
| `Enum.Parse<TEnum>(string, bool)` | 제네릭 + `ignoreCase` | `ArgumentException` |
| `Enum.TryParse<TEnum>(string, out TEnum)` | 제네릭 | `false` |
| `Enum.TryParse<TEnum>(string, bool, out TEnum)` | 제네릭 + `ignoreCase` | `false` |

`ReadOnlySpan<char>`를 받는 오버로드도 있다 ※.NET 8. 파싱 실패 시 `Enum.Parse`가 던지는 것은 `FormatException`이 아니라 **`ArgumentException`** 이라는 점에 주의해라 — 다른 `Parse` 메서드와 예외 타입이 다르다.

> **⚠️ `Enum.Parse`는 정의되지 않은 값도 만들어 낸다**
>
> 이것이 열거형 파싱의 가장 큰 함정이며, 20.4절에서 지적한 열거형의 타입 안전성 문제가 파싱에서 다시 나타나는 것이다.
>
> ```csharp
> enum Status { Active = 1, Inactive = 2 }
>
> var a = Enum.Parse<Status> ("Active");     // Status.Active
> var b = Enum.Parse<Status> ("99");         // (Status)99 — 예외 없음!
> bool ok = Enum.TryParse<Status> ("99", out var c);   // true, c = (Status)99
> ```
>
> **숫자 문자열은 언제나 파싱에 성공한다.** 정의된 멤버가 아니어도 그렇다. 외부에서 온 문자열을 열거형으로 받는다면 파싱 성공만으로는 부족하고 `Enum.IsDefined`를 함께 검사해야 한다.
>
> ```csharp
> bool valid = Enum.TryParse<Status> (input, ignoreCase: true, out var s)
>              && Enum.IsDefined (s);         // .NET 5 이후 제네릭 오버로드
> ```
>
> 단, `[Flags]` 열거형에서는 `IsDefined`가 조합 값(`A | B`)에 대해 `false`를 돌려주므로 이 검사를 그대로 쓸 수 없다. 조합의 유효성은 마스크로 직접 검사해라.
>
> ```csharp
> const Perm All = Perm.Read | Perm.Write | Perm.Exec;
> bool valid2 = (parsed & ~All) == 0;
> ```

> **📌 열거형과 JSON**
>
> `System.Text.Json`은 기본적으로 열거형을 **숫자**로 직렬화한다. 이름으로 쓰고 싶으면 `JsonStringEnumConverter`를 등록한다(41.5절). 어느 쪽을 택하든, 저장된 표현이 코드의 멤버 이름이나 값과 함께 진화한다는 사실을 잊지 마라 — 멤버 이름을 리팩터링하면 이미 저장된 데이터가 깨진다.

## 38.8 `ISpanFormattable` / `IUtf8SpanFormattable`로 무할당 포매팅

### 문제 정의

`ToString`은 **반드시 문자열을 할당한다.** 값 하나를 찍을 때는 무시할 만하지만, 초당 수십만 건의 로그 줄이나 CSV 행을 만드는 코드에서는 이 할당이 GC 압력의 주범이 된다.

```csharp
// 한 줄마다 최소 4개의 문자열이 힙에 생긴다
string line = id.ToString() + "," + name + "," + amount.ToString ("F2");
```

해법은 **결과를 담을 버퍼를 호출자가 제공하는 것**이다. .NET 6은 이를 인터페이스로 규격화했다.

### `ISpanFormattable` ※.NET 6

```csharp
namespace System;

public interface ISpanFormattable : IFormattable
{
    bool TryFormat (Span<char> destination, out int charsWritten,
                    ReadOnlySpan<char> format, IFormatProvider? provider);
}
```

BCL의 숫자 타입, `DateTime`, `DateTimeOffset`, `TimeSpan`, `Guid`, `DateOnly`, `TimeOnly`, `Version`, `IPAddress` 등이 전부 구현한다.

각 타입은 인터페이스 구현 외에 **선택적 인자를 가진 public 오버로드**도 제공하므로 실제로는 이렇게 쓴다.

```csharp
Span<char> buffer = stackalloc char[32];

if (42.TryFormat (buffer, out int written, "D5"))
    Console.Out.Write (buffer[..written]);      // "00042" — 문자열 할당 0
```

`TryFormat`이 `false`를 돌려주는 유일한 이유는 **버퍼가 모자란 것**이다. 이때 `charsWritten`은 0이고 버퍼 내용은 정의되지 않은 것으로 취급해야 한다.

> **⚠️ `TryFormat`이 실패했을 때 버퍼 내용을 믿지 마라**
>
> `false`가 반환되면 `destination`에 부분적으로 쓰인 내용이 남아 있을 수 있다. 그 상태의 버퍼를 읽으면 잘린 값이나 쓰레기가 나온다. **반드시 `false`를 검사하고 더 큰 버퍼로 재시도해라.**
>
> ```csharp
> static string FormatWithGrowth<T> (T value, string format) where T : ISpanFormattable
> {
>     Span<char> buf = stackalloc char[64];
>     if (value.TryFormat (buf, out int n, format, CultureInfo.InvariantCulture))
>         return new string (buf[..n]);
>
>     // 드문 경우: 힙 버퍼로 승격
>     char[] rented = ArrayPool<char>.Shared.Rent (512);
>     try
>     {
>         value.TryFormat (rented, out n, format, CultureInfo.InvariantCulture);
>         return new string (rented, 0, n);
>     }
>     finally { ArrayPool<char>.Shared.Return (rented); }
> }
> ```
>
> `ArrayPool<T>`의 상세는 69.3절, `stackalloc`과 `Span`의 결합은 68.9절이다.

### 얼마나 큰 버퍼가 필요한가

| 타입 | 안전한 `stackalloc` 크기 | 근거 |
|---|---|---|
| `int` | 12 | `-2147483648`이 11자 |
| `long` | 24 | `-9223372036854775808`이 20자 |
| `double` (`"R"`/기본) | 32 | 지수 표기 포함 최악의 경우 |
| `decimal` | 32 | 부호 + 29자릿수 + 소수점 |
| `Guid` (`"D"`) | 36 | 하이픈 포함 고정 길이 |
| `Guid` (`"B"`/`"P"`) | 38 | 괄호 포함 |
| `DateTime` (`"o"`) | 33 | 오프셋 포함 최대 길이 |

> **💡 `stackalloc` 크기는 넉넉하게, 단 상수로**
>
> 스택 버퍼는 공짜에 가깝다. 32자면 될 것을 64자로 잡아도 비용 차이가 거의 없다. 대신 **크기를 런타임 값으로 계산하지 마라** — `stackalloc new char[n]`에서 `n`이 커지면 스택 오버플로가 나고, 이 예외는 `catch`할 수 없어 프로세스가 즉사한다(68.8절). 상수를 쓰고, 모자라면 `ArrayPool`로 넘어가는 2단 전략이 정석이다.

### 보간 문자열과의 연결

35.7절에서 본 `DefaultInterpolatedStringHandler`의 `AppendFormatted<T>`는 `T`가 `ISpanFormattable`이면 `TryFormat`으로 **핸들러 버퍼에 직접 쓴다.** 중간 문자열조차 만들지 않는다. 즉 다음 두 줄의 할당량이 다르다.

```csharp
string a = "id=" + id.ToString();     // id.ToString()의 문자열 + 결과 문자열
string b = $"id={id}";                // 결과 문자열 하나 (핸들러 경로)
```

이것이 보간 문자열이 단순한 문법 설탕이 아닌 이유다.

### `IUtf8SpanFormattable` ※.NET 8

네트워크와 파일은 대부분 UTF-8을 쓴다. UTF-16 문자열을 만든 뒤 UTF-8로 인코딩하면 **버퍼를 두 번 거친다.** .NET 8은 이 중간 단계를 없앴다.

```csharp
namespace System;

public interface IUtf8SpanFormattable
{
    bool TryFormat (Span<byte> utf8Destination, out int bytesWritten,
                    ReadOnlySpan<char> format, IFormatProvider? provider);
}
```

```csharp
Span<byte> utf8 = stackalloc byte[32];
if (12345.TryFormat (utf8, out int bytes, "N0", CultureInfo.InvariantCulture))
    stream.Write (utf8[..bytes]);     // UTF-16 문자열도, 인코딩 변환도 없다
```

역방향은 `IUtf8SpanParsable<TSelf>`다(38.1절).

```csharp
ReadOnlySpan<byte> field = utf8Line.Slice (start, length);
if (int.TryParse (field, CultureInfo.InvariantCulture, out int value)) { … }
```

### `Utf8.TryWrite` — UTF-8 보간 ※.NET 8

`System.Text.Unicode.Utf8` 정적 클래스는 보간 문자열을 UTF-8 버퍼에 곧바로 쓰는 메서드를 제공한다.

```csharp
using System.Text.Unicode;

Span<byte> dest = stackalloc byte[128];

if (Utf8.TryWrite (dest, CultureInfo.InvariantCulture,
                   $"{{\"id\":{id},\"amount\":{amount:F2}}}", out int written))
{
    stream.Write (dest[..written]);
}
```

`TryWrite`의 두 번째 인자는 보간 문자열 핸들러(`Utf8.TryWriteInterpolatedStringHandler`)이며, 컴파일러가 `[InterpolatedStringHandlerArgument]`를 통해 대상 버퍼를 핸들러에 전달한다. 즉 **각 값이 UTF-8 바이트로 직접 서식화된다.**

**성능 영향** — UTF-16 경로와 비교했을 때 없어지는 것은 다음과 같다.

| 단계 | UTF-16 경로 | UTF-8 직접 경로 |
|---|---|---|
| 값 → 문자 | `ToString()` 문자열 할당 | 버퍼에 직접 쓰기 |
| 조립 | `StringBuilder` 또는 결과 문자열 | 같은 버퍼 |
| 인코딩 | `Encoding.UTF8.GetBytes` — 새 배열 | 없음 |
| 힙 할당 | 최소 2~3개 | **0** |

> **📌 `Utf8Formatter`/`Utf8Parser`는 그 이전 세대다**
>
> `System.Buffers.Text` 네임스페이스에는 `Utf8Formatter.TryFormat`과 `Utf8Parser.TryParse`가 .NET Core 2.1부터 있었다. 이들은 형식을 `StandardFormat` 구조체로 받고 **불변 문화권으로만** 동작한다.
>
> .NET 8 이후에는 타입에 직접 정의된 `TryFormat(Span<byte>, …)`/`TryParse(ReadOnlySpan<byte>, …)` 쪽을 써라. 문화권을 지정할 수 있고, 대상 타입이 훨씬 넓고, 성능도 대체로 낫다.

> **⚠️ 무할당 포매팅은 `Span`을 잘못 다루면 즉시 위험해진다**
>
> `Span<char>`는 `ref struct`이므로 필드에 저장할 수 없고 `async` 메서드의 `await` 경계를 넘을 수 없다(68.1절). `stackalloc` 버퍼를 반환하는 것은 **댕글링 참조**를 만드는 일이며 컴파일러가 대부분 막지만, `ArrayPool`에서 빌린 배열을 `Return`한 뒤에도 스팬을 들고 있으면 컴파일러가 막지 못한다.
>
> ```csharp
> char[] rented = ArrayPool<char>.Shared.Rent (128);
> Span<char> span = rented;
> ArrayPool<char>.Shared.Return (rented);
> span[0] = 'x';                 // 이미 반납한 배열에 쓴다 — 다른 코드의 데이터를 오염시킨다
> ```
>
> 이런 종류의 버그는 재현이 어렵고 증상이 엉뚱한 곳에서 나타난다. `Span`의 수명 규칙은 68장에서, 풀링 규율은 69.3절에서 다룬다.

> **💡 언제 무할당 포매팅으로 갈아탈 것인가**
>
> 결론부터 말하면 **대부분의 코드에서는 필요 없다.** 판단 기준은 다음과 같다.
>
> | 상황 | 권고 |
> |---|---|
> | UI 표시, 설정 읽기, 초당 수백 회 이하 | `ToString`/보간 문자열로 충분 |
> | 로그 프레임워크의 내부, 직렬화기, 프로토콜 인코더 | `TryFormat` 검토 |
> | 초당 수만 건 이상의 레코드 처리 | `TryFormat` + UTF-8 직접 경로 |
> | 할당이 병목임을 **측정으로 확인**했을 때 | 갈아타라 |
>
> 마지막 줄이 핵심이다. 67장의 원칙 — 측정 없이 최적화 없다 — 이 여기에도 그대로 적용된다. 무할당 코드는 읽기 어렵고 수명 버그를 부른다. 값을 지불할 이유가 확인된 자리에만 써라.

## 38.9 기타 변환 메커니즘 — `Convert`, `XmlConvert`, `TypeConverter`, `BitConverter`

형식 공급자는 .NET의 주력 포매팅·파싱 메커니즘이지만 전부는 아니다. 나머지 중요한 변환 도구가 여러 타입과 네임스페이스에 흩어져 있다.

### `Convert` — 기본 타입 사이의 변환

.NET은 다음을 **기본 타입(base type)** 이라 부른다.

- `bool`, `char`, `string`, `System.DateTime`, `System.DateTimeOffset`
- 모든 C# 숫자 타입

정적 `Convert` 클래스는 모든 기본 타입을 다른 모든 기본 타입으로 변환하는 메서드를 정의한다. 다만 그중 대부분은 쓸모가 없다 — 예외를 던지거나, 암시적 캐스트로 이미 되는 것을 중복 제공한다. 실제로 값어치가 있는 것은 넷이다.

#### 1. 실수 → 정수 변환에서 반올림하기

7.2절에서 본 대로 캐스트는 효율을 위해 최적화되어 있고, 따라서 **들어가지 않는 데이터를 잘라 버린다.** 실수를 정수로 바꿀 때는 자르기보다 반올림을 원하는 경우가 많다. `Convert`의 숫자 변환 메서드는 **언제나 반올림한다.**

```csharp
double d = 3.9;
int i = Convert.ToInt32 (d);       // i == 4
int j = (int) d;                   // j == 3  (잘라 버린다)
```

`Convert`는 **은행가 반올림(banker's rounding)** 을 쓴다. 중간값을 짝수 정수로 맞춰 양·음의 편향을 없애는 방식이다.

```csharp
Convert.ToInt32 (2.5);    // 2  ← 3이 아니다
Convert.ToInt32 (3.5);    // 4
Convert.ToInt32 (4.5);    // 4  ← 5가 아니다
```

은행가 반올림이 곤란하다면 먼저 `Math.Round`를 부른다. `Math.Round`는 중간값 처리 방식을 지정하는 인자를 받는다(39.1절).

```csharp
int k = (int) Math.Round (2.5, MidpointRounding.AwayFromZero);   // 3
```

> **⚠️ 세 가지 반올림 규칙이 한 코드베이스에 공존한다**
>
> | 연산 | 중간값 처리 |
> |---|---|
> | `(int) d` 캐스트 | 버림(0 방향으로 절단) |
> | `Convert.ToInt32(d)` | 은행가 반올림(짝수로) |
> | `Math.Round(d)` (인자 없음) | 은행가 반올림 |
> | `Math.Round(d, MidpointRounding.AwayFromZero)` | 0에서 먼 쪽으로 |
> | `d.ToString("F0")` | 0에서 먼 쪽으로 |
>
> 마지막 두 행이 앞의 세 행과 다르다는 사실을 놓치면, **계산 결과와 화면 표시가 1씩 어긋난다.** 금액을 다루는 코드는 반올림 정책을 한 곳에 정의하고 그 함수만 쓰도록 강제해라.

#### 2. 2·8·16진수 파싱

`To(정수 타입)` 메서드 중에는 다른 진법으로 파싱하는 오버로드가 숨어 있다.

```csharp
int thirty = Convert.ToInt32 ("1E", 16);    // 16진수로 파싱 → 30
uint five  = Convert.ToUInt32 ("101", 2);   // 2진수로 파싱 → 5
int eight  = Convert.ToInt32 ("10", 8);     // 8진수로 파싱 → 8
```

두 번째 인자가 진법이다. 원하는 아무 진법이나 쓸 수 있다 — **2, 8, 10, 16이기만 하면.** 다른 값을 주면 `ArgumentException`이 난다.

역방향은 `ToString(int value, int toBase)`다.

```csharp
string hex = Convert.ToString (255, 16);    // "ff"
string bin = Convert.ToString (10, 2);      // "1010"
```

> **📌 .NET 8부터는 표준 형식 문자열로도 된다**
>
> `10.ToString("B8")`이 `"00001010"`을 내고, `int.Parse("1010", NumberStyles.BinaryNumber)`가 10을 낸다(38.3절, 38.4절). `Convert.ToString(v, 2)`와 달리 앞자리 0 채우기를 지정할 수 있고 부호 처리도 명확하다. 새 코드에서는 이쪽을 권한다.

#### 3. 동적 변환 — `ChangeType`

런타임까지 타입을 모르는 상황을 위한 메서드다.

```csharp
public static object ChangeType (object value, Type conversionType);
```

원본과 대상 타입 모두 기본 타입 중 하나여야 한다. `IFormatProvider`를 받는 오버로드도 있다.

```csharp
Type targetType = typeof (int);
object source = "42";
object result = Convert.ChangeType (source, targetType);
Console.WriteLine (result);              // 42
Console.WriteLine (result.GetType());    // System.Int32
```

여러 타입을 다루는 역직렬화기를 만들 때 쓸 만하다. 열거형을 그 기저 정수 타입으로 변환하는 데에도 쓸 수 있다(20.2절).

`ChangeType`의 한계는 **형식 문자열이나 파싱 플래그를 지정할 수 없다는 것**이다. 그리고 반환 타입이 `object`이므로 값 타입이면 박싱이 일어난다.

> **⚠️ `Convert.ChangeType`도 `CurrentCulture`를 기본으로 쓴다**
>
> 공급자 없는 오버로드는 `CultureInfo.CurrentCulture`를 쓴다. 설정 파일이나 쿼리 문자열을 `ChangeType`으로 변환하는 코드는 38.1절에서 본 독일 소수점 문제를 그대로 물려받는다. 데이터 바인딩 계층에서 이 함수를 쓸 때는 반드시 공급자를 넘겨라.
>
> ```csharp
> object v = Convert.ChangeType (raw, targetType, CultureInfo.InvariantCulture);
> ```

#### 4. Base64 변환

비트맵 같은 이진 데이터를 XML 파일이나 이메일 같은 텍스트 문서에 넣어야 할 때가 있다. Base64는 ASCII 문자 64개로 이진 데이터를 인코딩하는 보편적인 방법이다.

```csharp
string s = Convert.ToBase64String (bytes);
byte[] back = Convert.FromBase64String (s);
```

관련 메서드를 정리하면 다음과 같다.

| 메서드 | 방향 | 비고 |
|---|---|---|
| `Convert.ToBase64String(byte[])` | 이진 → 텍스트 | 길이가 약 4/3배로 늘어난다 |
| `Convert.ToBase64String(byte[], Base64FormattingOptions)` | 이진 → 텍스트 | `InsertLineBreaks`로 76자마다 줄바꿈 |
| `Convert.FromBase64String(string)` | 텍스트 → 이진 | 잘못된 입력은 `FormatException` |
| `Convert.TryFromBase64String(string, Span<byte>, out int)` | 텍스트 → 이진 | 예외 없음 |
| `Convert.ToHexString(byte[])` ※.NET 5 | 이진 → 16진 문자열 | 대문자 |
| `Convert.FromHexString(string)` ※.NET 5 | 16진 문자열 → 이진 | |

> **⚠️ Base64는 암호화가 아니다**
>
> 굳이 쓰지만, 실무에서 반복해서 보는 오해다. Base64는 인코딩이지 암호화가 아니다. 누구나 즉시 되돌릴 수 있다. 비밀번호나 토큰을 Base64로 "숨기는" 코드는 아무것도 보호하지 않는다(44장).
>
> 또한 표준 Base64는 `+`와 `/`를 쓰므로 **URL에 그대로 넣으면 깨진다.** URL 안전 변형이 필요하면 `-`와 `_`로 치환하고 패딩(`=`)을 제거해야 한다.

### `XmlConvert`

XML 파일에서 왔거나 XML 파일로 갈 데이터를 다룬다면 `System.Xml.XmlConvert`가 가장 적합한 포매팅·파싱 수단이다. `XmlConvert`의 메서드는 **특별한 형식 문자열 없이** XML 서식의 미묘한 규칙을 처리한다. 예를 들어 XML에서 참은 `"True"`가 아니라 `"true"`다. .NET BCL 내부도 `XmlConvert`를 광범위하게 쓴다.

`XmlConvert`는 **범용 문화권 독립 직렬화**에도 좋다.

```csharp
string s = XmlConvert.ToString (true);      // s = "true"
bool isTrue = XmlConvert.ToBoolean (s);
```

서식화 메서드는 전부 오버로드된 `ToString`이고, 파싱 메서드는 `ToBoolean`, `ToDateTime` 같은 이름을 갖는다. 지원 타입은 숫자 타입 전부, `bool`, `DateTime`, `DateTimeOffset`, `TimeSpan`, `Guid`다.

`DateTime`을 오가는 메서드는 `XmlDateTimeSerializationMode` 인자를 받는다.

| 값 | 서식화할 때 | 결과 예 |
|---|---|---|
| `Unspecified` | `DateTimeKind` 정보를 **제거**한 뒤 서식화 | `2010-02-22T14:08:30.9375` |
| `Local` | 로컬 시간대로 변환하고 오프셋을 붙인다 | `2010-02-22T14:07:30.9375+09:00` |
| `Utc` | UTC로 변환하고 `Z`를 붙인다 | `2010-02-22T05:08:30.9375Z` |
| `RoundtripKind` | `DateTimeKind`를 존중해 그대로 표기 | 원래 `Kind`에 따라 위 셋 중 하나 |

**`RoundtripKind`만이 왕복을 보장한다.** 다시 파싱했을 때 결과 `DateTime` 구조체가 원래와 정확히 같아진다(37.10절에서 미리 짚었다).

> **📌 `XmlConvert.EncodeName` / `DecodeName`**
>
> XML 요소 이름에는 공백이나 `#` 같은 문자를 쓸 수 없다. `XmlConvert.EncodeName`은 이런 문자를 `_x0020_` 형태로 이스케이프하고, `DecodeName`이 되돌린다. 사전의 키를 XML 요소 이름으로 쓰는 코드에서 필요하다(42장).

> **💡 `XmlConvert` vs `InvariantCulture` + `"o"`**
>
> 둘 다 문화권 독립 왕복을 제공한다. 선택 기준은 이렇다.
>
> | 상황 | 선택 |
> |---|---|
> | XML/XSD 스키마와 상호운용해야 한다 | `XmlConvert` |
> | `bool`을 XML 규약(`"true"`)으로 써야 한다 | `XmlConvert` |
> | JSON이나 자체 텍스트 형식 | `InvariantCulture` + `"o"` |
> | `Span`/UTF-8 무할당 경로 | `TryFormat` (38.8절) — `XmlConvert`에는 없다 |
>
> `XmlConvert`는 편리하지만 `string`만 다룬다. 고성능 경로에는 맞지 않는다.

### 타입 변환기(`TypeConverter`)

타입 변환기는 **디자인 타임 환경**에서 서식화·파싱하기 위해 설계되었다. XAML 문서의 값도 이들이 파싱한다(WPF에서 쓰인다).

.NET에는 색, 이미지, URI 등을 다루는 타입 변환기가 100종이 넘는다. 반면 형식 공급자는 소수의 단순 값 타입에만 구현되어 있다.

타입 변환기는 대체로 **힌트 없이도 여러 방식의 문자열을 파싱한다.** Visual Studio의 WPF 애플리케이션에서 속성 창에 `"Beige"`를 입력하면 `Color`의 타입 변환기가 그것이 색 이름이지 RGB 문자열이나 시스템 색이 아님을 알아낸다. 이 유연성 덕분에 디자이너나 XAML 밖에서도 쓸모가 있을 때가 있다.

모든 타입 변환기는 `System.ComponentModel`의 `TypeConverter`를 상속한다. 얻으려면 `TypeDescriptor.GetConverter`를 부른다.

```csharp
TypeConverter cc = TypeDescriptor.GetConverter (typeof (Color));

Color beige  = (Color) cc.ConvertFromString ("Beige");
Color purple = (Color) cc.ConvertFromString ("#800080");
Color window = (Color) cc.ConvertFromString ("Window");
```

관례상 타입 변환기의 이름은 `Converter`로 끝나고, 변환 대상 타입과 같은 네임스페이스에 놓인다. 타입은 `TypeConverterAttribute`로 자기 변환기를 가리키며, 이를 통해 디자이너가 변환기를 자동으로 찾는다.

타입 변환기는 디자인 타임 서비스도 제공한다 — 디자이너의 드롭다운을 채울 표준 값 목록을 만들거나, 코드 직렬화를 돕는 일이다.

> **⚠️ `TypeDescriptor`는 트리밍·AOT와 상극이다**
>
> `TypeDescriptor.GetConverter`는 리플렉션으로 특성을 읽고 변환기 타입을 동적으로 만든다. 트리머(trimmer)는 이 참조를 정적으로 추적하지 못하므로, 자체 포함 트리밍 배포나 Native AOT에서 **변환기 클래스가 잘려 나가 런타임에 실패**할 수 있다.
>
> 새 코드에서 문자열 파싱이 목적이라면 `IParsable<T>`(38.1절)나 타입 자체의 `TryParse`를 써라. `TypeConverter`는 디자이너·XAML 호환이 필요할 때만 쓴다.

### `BitConverter`

대부분의 기본 타입은 `BitConverter.GetBytes`로 바이트 배열로 바꿀 수 있다.

```csharp
foreach (byte b in BitConverter.GetBytes (3.5))
    Console.Write (b + " ");        // 0 0 0 0 0 0 12 64
```

역방향은 `ToDouble` 같은 메서드다.

| 대상 | 지원 | 대안 |
|---|---|---|
| 정수 타입, `float`, `double`, `char`, `bool` | `GetBytes` / `ToXxx` | — |
| `decimal` | **미지원** | `decimal.GetBits` → `int[]`, 되돌릴 때는 `int[]`를 받는 생성자 |
| `DateTime`/`DateTimeOffset` | **미지원** | `DateTime.ToBinary`로 `long`을 얻은 뒤 `BitConverter` 적용, `DateTime.FromBinary`로 복원 |

> **⚠️ `BitConverter`는 실행 중인 머신의 엔디언을 따른다**
>
> `BitConverter.GetBytes(3.5)`가 `0 0 0 0 0 0 12 64`를 내는 것은 x86/x64/ARM이 **리틀 엔디언**이기 때문이다. 빅 엔디언 머신에서는 순서가 뒤집힌다. `BitConverter.IsLittleEndian`이 현재 머신의 엔디언을 알려준다.
>
> 파일이나 네트워크로 나가는 바이트에 `BitConverter`를 쓰면 **플랫폼 사이에서 조용히 깨지는 형식**을 만드는 것이다. 실제로 .NET이 이제 리눅스·macOS·ARM에서 돌아가므로, 이 문제는 이론이 아니다.
>
> 엔디언을 명시하려면 `System.Buffers.Binary.BinaryPrimitives`를 써라.
>
> ```csharp
> using System.Buffers.Binary;
>
> Span<byte> buf = stackalloc byte[4];
> BinaryPrimitives.WriteInt32BigEndian (buf, value);       // 네트워크 바이트 순서
> int back = BinaryPrimitives.ReadInt32BigEndian (buf);
>
> BinaryPrimitives.WriteInt32LittleEndian (buf, value);    // 명시적 리틀 엔디언
> ```
>
> `BinaryPrimitives`는 `Span` 기반이라 할당도 없다. **새 코드에서 `BitConverter.GetBytes`를 쓸 이유는 거의 없다.**

> **📌 비트 패턴을 그대로 옮기기**
>
> `BitConverter`에는 배열을 거치지 않고 비트 패턴만 재해석하는 메서드도 있다.
>
> ```csharp
> long bits = BitConverter.DoubleToInt64Bits (3.5);
> double d  = BitConverter.Int64BitsToDouble (bits);
> int  fbits = BitConverter.SingleToInt32Bits (3.5f);
> ```
>
> 부동소수점의 정확한 비트 비교, 해시 계산, 특수값 검사에 쓴다. `double.NaN == double.NaN`이 `false`인 것과 달리(7.6절) 비트 비교는 NaN도 구별한다.

### 변환 메커니즘 선택표

| 목적 | 도구 |
|---|---|
| 10진 숫자 파싱 | `Parse` / `TryParse` |
| 2·8·16진 파싱 | `Convert.ToInt32(s, base)` 또는 `NumberStyles.HexNumber`/`BinaryNumber` |
| 16진 서식화 | `ToString("X")` |
| 무손실 숫자 변환 | 암시적 캐스트 |
| 잘라내는 숫자 변환 | 명시적 캐스트 |
| 반올림하는 실수 → 정수 변환 | `Convert.ToInt32` |
| 런타임에 결정되는 타입 변환 | `Convert.ChangeType` |
| 이진 ↔ 텍스트 | `Convert.ToBase64String` / `ToHexString` |
| XML 상호운용 | `XmlConvert` |
| 디자이너·XAML | `TypeConverter` |
| 명시적 엔디언 이진 직렬화 | `BinaryPrimitives` |

## 38.10 국제화 체크리스트와 테스트 전략

### 세계화와 지역화

애플리케이션을 국제화하는 데에는 두 측면이 있다.

**세계화(globalization)** 는 중요도 순으로 세 가지 작업을 다룬다.

1. 다른 문화권에서 실행해도 **프로그램이 깨지지 않게** 하는 것
2. 지역 문화권의 서식 규칙을 존중하는 것 — 예컨대 날짜를 표시할 때
3. 나중에 작성·배포할 **위성 어셈블리**에서 문화권별 데이터와 문자열을 가져오도록 프로그램을 설계하는 것

**지역화(localization)** 는 그 마지막 작업을 마무리하는 것, 즉 특정 문화권을 위한 위성 어셈블리를 작성하는 일이다. 프로그램을 다 쓴 뒤에 할 수 있으며, 상세는 53장이다.

.NET은 기본적으로 문화권별 규칙을 적용해 두 번째 작업을 도와준다. `DateTime`이나 숫자에 `ToString`을 부르면 로컬 서식 규칙이 존중되는 것을 이미 봤다. 그런데 **바로 그 점 때문에 첫 번째 작업에 실패하기 쉽다** — 날짜나 숫자가 어떤 문화권으로 서식화될 것이라 가정한 코드가 깨진다.

해법은 두 가지다. 서식화·파싱할 때 문화권(예: 불변 문화권)을 지정하거나, `XmlConvert` 같은 문화권 독립 메서드를 쓰는 것이다.

### 세계화 체크리스트

원천 문헌이 정리한 필수 작업에, 실무에서 반복해서 보이는 항목을 더해 정리한다.

| # | 항목 | 확인 방법 |
|---|---|---|
| 1 | 유니코드와 텍스트 인코딩을 이해한다 | 35.8절 |
| 2 | `char`/`string`의 `ToUpper`/`ToLower`가 **문화권 인식**임을 안다 | 문화권 민감성이 필요 없으면 `ToUpperInvariant`/`ToLowerInvariant`를 쓴다 (35.4절) |
| 3 | `DateTime`/`DateTimeOffset`에 문화권 독립 서식·파싱을 선호한다 | `ToString("o")`, `XmlConvert` |
| 4 | 그 외의 경우 숫자·날짜/시간을 서식화·파싱할 때 **문화권을 명시한다** | 로컬 문화권 동작을 원하는 게 아니라면 |
| 5 | 하드코딩된 사용자 대면 문자열을 제거한다 | 리소스 파일(`.resx`)로 옮긴다 (53.2절) |
| 6 | 문자열 비교에 `StringComparison`을 명시한다 | 35.4절 |
| 7 | 정렬을 목적에 맞게 선택한다 | 화면 표시는 `CurrentCulture`, 키·식별자는 `Ordinal` |
| 8 | 통화와 숫자 서식이 문화권을 따르는지 확인한다 | 자릿수 구분 크기, 음수 표기, 통화 기호 위치 |
| 9 | 달력 가정을 제거한다 | 그레고리력이 아닌 문화권이 있다 |
| 10 | 양방향(BiDi) 텍스트를 고려한다 | 아랍어·히브리어 |
| 11 | UI 레이아웃이 문자열 길이 변화를 견디는지 확인한다 | 독일어는 영어보다 대체로 30~50% 길다 |
| 12 | `CurrentCulture`와 `CurrentUICulture`를 구분한다 | 아래 참조 |

### `CurrentCulture` vs `CurrentUICulture`

`Thread`와 `CultureInfo`는 `CurrentCulture` 외에 `CurrentUICulture` 속성도 지원한다. 후자는 지역화 쪽 관심사이며 53장에서 다룬다. 둘의 역할은 완전히 다르다.

| | `CurrentCulture` | `CurrentUICulture` |
|---|---|---|
| 결정하는 것 | **서식** — 숫자, 날짜, 통화, 정렬 | **리소스 조회** — 어느 위성 어셈블리를 볼지 |
| 영향을 받는 API | `ToString`, `Parse`, `string.Compare` | `ResourceManager.GetString` |
| OS에서 오는 값 | 지역/형식 설정 | 표시 언어 설정 |
| 전형적인 값 | 사용자가 사는 곳 | 사용자가 읽는 언어 |

이 둘이 다를 수 있다는 것이 핵심이다. 독일에 사는 영어 사용자는 `CurrentCulture = de-DE`(날짜는 `dd.MM.yyyy`, 소수점은 쉼표), `CurrentUICulture = en-US`(UI는 영어)를 원한다.

```csharp
CultureInfo.CurrentCulture   = CultureInfo.GetCultureInfo ("de-DE");
CultureInfo.CurrentUICulture = CultureInfo.GetCultureInfo ("en-US");
```

> **⚠️ 두 속성을 한꺼번에 설정하는 코드는 사용자의 의도를 지운다**
>
> "언어를 한국어로 바꾼다"는 UI 설정 때문에 `CurrentCulture`까지 `ko-KR`로 바꿔 버리면, 독일에 사는 사용자의 날짜 표기가 갑자기 `yyyy. M. d.`가 된다. **언어 선택은 `CurrentUICulture`만 바꾸는 것이 원칙**이며, 서식 문화권은 별도 설정으로 두거나 OS 값을 그대로 존중해라.

> **📌 스레드와 문화권**
>
> `CultureInfo.CurrentCulture`에 대입하면 그 값은 실행 컨텍스트를 따라 흐른다 — `await` 이후에도 유지된다. 하지만 **설정한 적이 없는 스레드**(새로 만든 스레드, 스레드 풀에서 처음 꺼내온 스레드)는 프로세스 기본값을 쓴다.
>
> 프로세스 전체의 기본값을 바꾸려면 다음을 쓴다.
>
> ```csharp
> CultureInfo.DefaultThreadCurrentCulture   = CultureInfo.InvariantCulture;
> CultureInfo.DefaultThreadCurrentUICulture = CultureInfo.GetCultureInfo ("en-US");
> ```
>
> 애플리케이션 진입점에서 한 번 설정한다. 라이브러리 코드에서는 절대 설정하지 마라 — 호스트 애플리케이션의 정책을 훔치는 짓이다.

### 달력

`CultureInfo.DateTimeFormat.Calendar`는 그 문화권의 기본 달력이다. 그레고리력이 아닌 문화권이 실제로 존재한다.

| 문화권 | 기본 달력 | 2000년 1월 2일의 `"d"` 출력 |
|---|---|---|
| `en-US` | `GregorianCalendar` | `1/2/2000` |
| `th-TH` | `ThaiBuddhistCalendar` | `2/1/2543` (불기) |
| `ar-SA` | `UmAlQuraCalendar` | 히즈라력 날짜 |
| `ja-JP` | `GregorianCalendar` (기본) | `2000/01/02` |

> **⚠️ 태국 로캘에서 연도가 543 커진다**
>
> `th-TH` 문화권에서 `DateTime.Now.ToString("d")`를 부르면 불기 연도가 나온다. 2000년이 2543년이 된다. 이 문자열을 그대로 파일에 쓰고 나중에 `InvariantCulture`로 되읽으면 **543년 미래의 날짜**가 된다.
>
> 반대 방향도 성립한다 — `th-TH`로 `"2543"`을 파싱하면 2000년이 되고, 데이터베이스에는 2000년이 들어간다. 서로 다른 로캘의 클라이언트가 같은 데이터베이스를 쓰면 날짜가 뒤죽박죽이 된다.
>
> `"o"`, `"s"`, `"u"`, `"r"`/`"R"` 같은 문화권 비인식 형식은 **언제나 그레고리력**을 쓴다. 저장·전송용 날짜에 이들을 쓰면 이 함정을 통째로 피한다.

일본의 원호(`JapaneseCalendar`)는 다른 종류의 위험을 갖는다 — **연호가 바뀌면 데이터가 바뀐다.** 2019년 레이와 개원 때 실제로 대응 작업이 필요했다. 저장 형식으로 문화권 달력을 쓰면 안 되는 결정적인 이유다.

### 양방향 텍스트

아랍어와 히브리어는 오른쪽에서 왼쪽으로 쓴다. 숫자와 라틴 문자가 섞이면 유니코드 양방향 알고리즘이 표시 순서를 결정한다. 실무에서 부딪히는 지점은 다음과 같다.

- **문자열 연결의 시각적 순서가 논리적 순서와 다르다.** `"주문 " + id + " 완료"`가 화면에서 뒤엉켜 보일 수 있다.
- 방향 제어 문자 LRM(U+200E)과 RLM(U+200F)을 경계에 삽입하면 해결되는 경우가 많다. C#에서는 `"\u200E"`처럼 이스케이프로 쓴다.
- 로그나 식별자에 사용자 입력을 그대로 넣으면, RTL 오버라이드 문자(U+202E)로 **표시를 조작**할 수 있다. 파일 이름 위장 공격에 쓰인 기법이다. 신뢰할 수 없는 문자열을 표시하기 전에 제어 문자를 걸러라.

### 테스트 전략

문화권을 바꿔 가며 테스트하려면 `Thread`의 `CurrentCulture` 속성(`System.Threading`)을 재할당한다. 다음은 현재 문화권을 터키로 바꾼다.

```csharp
Thread.CurrentThread.CurrentCulture = CultureInfo.GetCultureInfo ("tr-TR");
```

**터키는 특히 좋은 테스트 케이스다.** 이유는 셋이다.

- `"i".ToUpper() != "I"` 이고 `"I".ToLower() != "i"` 다
- 날짜가 `일.월.년` 형식으로 서식화된다(마침표 구분자에 주의)
- 소수점 표시자가 마침표가 아니라 쉼표다

Windows 제어판에서 숫자·날짜 서식 설정을 바꿔 실험할 수도 있다. 이 설정이 기본 문화권(`CultureInfo.CurrentCulture`)에 반영된다. `CultureInfo.GetCultures()`는 사용 가능한 모든 문화권의 배열을 돌려준다.

> **💡 테스트에 넣어야 할 문화권 셋**
>
> 저자가 CI에서 최소로 돌리는 조합은 다음과 같다.
>
> | 문화권 | 잡아내는 문제 |
> |---|---|
> | `de-DE` | 소수점이 쉼표, 자릿수 구분자가 마침표 — 숫자 파싱 사고의 대부분 |
> | `tr-TR` | 터키어 대소문자 문제 — 문자열 비교 사고 |
> | `th-TH` | 불교력 — 날짜 저장 사고 |
> | `ar-SA` | RTL + 히즈라력 — 표시 레이아웃 문제 |
> | `InvariantCulture` | 기준선 |
>
> xUnit이라면 테스트 클래스에 문화권을 설정하는 픽스처를 두고, 같은 테스트를 여러 문화권으로 반복 실행하는 것이 가장 실용적이다.
>
> ```csharp
> [Theory]
> [InlineData ("en-US")]
> [InlineData ("de-DE")]
> [InlineData ("tr-TR")]
> [InlineData ("th-TH")]
> public void 저장_형식은_문화권과_무관하다 (string culture)
> {
>     var prev = CultureInfo.CurrentCulture;
>     try
>     {
>         CultureInfo.CurrentCulture = CultureInfo.GetCultureInfo (culture);
>         string s = Serialize (new Order (Id: 7, Amount: 1234.5m,
>                                          When: new DateTime (2000, 1, 2)));
>         Assert.Equal ("7|1234.5|2000-01-02T00:00:00.0000000", s);
>     }
>     finally { CultureInfo.CurrentCulture = prev; }
> }
> ```

### 의사 로케일(pseudo-locale) 테스트

번역이 도착하기 전에 지역화 준비 상태를 검증하는 기법이 **의사 로케일**이다. 실제 번역 대신 원문을 기계적으로 변형한 문자열을 넣는다.

- 문자열 길이를 30~50% 늘려 **UI 잘림**을 드러낸다
- 악센트 문자로 치환해 **인코딩 문제**를 드러낸다
- 앞뒤에 대괄호를 붙여 **하드코딩된(리소스로 옮기지 않은) 문자열**을 즉시 눈에 띄게 한다

Windows는 `qps-ploc` 계열의 의사 로캘을 제공한다. 자체 빌드 단계에서 `.resx`의 모든 값을 변형해 가짜 위성 어셈블리를 만드는 방식도 널리 쓰인다(53장).

```text
원문 :  Save changes
의사 :  [!!! Şåvé çĥåņĝéš ‼‼‼ ]
        ↑                    ↑
        └─ 대괄호가 안 보이면 → 하드코딩된 문자열
           문자열이 잘리면    → UI 폭 부족
           ??? 로 보이면      → 인코딩/폰트 문제
```

### ICU와 `InvariantGlobalization`

.NET 5부터 모든 플랫폼에서 문화권 데이터의 출처는 **ICU**(International Components for Unicode) 라이브러리다. 그 이전의 Windows 전용 .NET Framework은 **NLS**(National Language Support)를 썼다.

> **⚠️ ICU 전환으로 정렬 결과와 문화권 데이터가 바뀌었다**
>
> .NET Framework(NLS)과 .NET 5+(ICU)는 같은 문자열을 다르게 정렬할 수 있고, 일부 문화권의 서식 패턴도 다르다. .NET Framework에서 .NET 8로 마이그레이션할 때 **정렬 순서에 의존하는 테스트가 깨지는** 전형적인 원인이다.
>
> Windows에서 옛 동작이 필요하다면 런타임 구성으로 NLS를 되살릴 수 있다.
>
> ```xml
> <ItemGroup>
>   <RuntimeHostConfigurationOption Include="System.Globalization.UseNls"
>                                   Value="true" />
> </ItemGroup>
> ```
>
> 하지만 이는 임시방편이다. 근본 해결은 **정렬이 필요한 자리마다 `StringComparer`를 명시하는 것**이다(35.4절).

`InvariantGlobalization`은 정반대 방향의 스위치다. ICU 데이터 자체를 싣지 않는다.

```xml
<PropertyGroup>
  <InvariantGlobalization>true</InvariantGlobalization>
</PropertyGroup>
```

| 항목 | 효과 |
|---|---|
| 배포 크기 | ICU 데이터(수 MB)가 빠져 컨테이너 이미지가 작아진다 |
| 시작 시간 | ICU 로드가 없어 조금 빨라진다 |
| 모든 문화권 | **불변 문화권처럼 동작한다** |
| 문자열 비교 | 문화권 인식 비교가 사실상 서수 비교가 된다 |
| `new CultureInfo("fr-FR")` | `PredefinedCulturesOnly`가 `true`(기본)면 `CultureNotFoundException` |
| 대소문자 변환 | 불변 문화권 규칙만 적용된다 — 터키어 `i` 같은 문화권 특수 규칙이 사라진다 |

> **⚠️ `InvariantGlobalization`은 서버에는 좋고 UI에는 나쁘다**
>
> 컨테이너에서 도는 백엔드 API — 모든 입출력이 불변 문화권 기준이고 사용자에게 직접 텍스트를 보여 주지 않는 서비스 — 라면 켜는 것이 합리적이다. 이미지가 작아지고, 로캘 설정에 따라 동작이 달라지는 사고 자체가 사라진다.
>
> 반대로 사용자에게 날짜·통화를 표시하거나 문화권 정렬이 필요한 애플리케이션에서 켜면 **조용히 잘못된 결과**가 나온다. 예외가 아니라 "모두가 미국인처럼" 보이는 결과다.
>
> 더 위험한 것은 **전이적 영향**이다. 라이브러리는 자기가 어떤 앱에 실려 갈지 모른다. `InvariantGlobalization=true`인 앱에 실린 라이브러리가 `CultureInfo.GetCultureInfo("ja-JP")`를 부르면 예외가 난다. 라이브러리 코드는 특정 문화권의 존재를 가정하지 말아야 한다.

## 38.11 불변 문화권(`InvariantCulture`)을 써야 할 자리

### 하나의 질문

이 장 전체가 결국 하나의 질문으로 압축된다.

> **이 문자열을 읽을 대상이 사람인가, 기계인가?**

- **사람이 읽는다** → `CultureInfo.CurrentCulture`. 사용자가 자기 방식으로 숫자와 날짜를 보게 하는 것이 옳다.
- **기계가 읽는다** → `CultureInfo.InvariantCulture`. 문자열을 만든 환경과 읽는 환경이 다를 수 있고, 서식이 달라지면 데이터가 깨진다.

"기계"는 다른 프로세스일 수도, 6개월 뒤의 같은 프로그램일 수도, 지구 반대편의 파트너 시스템일 수도 있다.

### 자리별 결정표

| 자리 | 문화권 | 이유 |
|---|---|---|
| 화면에 표시할 숫자·날짜·통화 | `CurrentCulture` | 사용자의 기대에 맞춘다 |
| 사용자가 입력한 숫자·날짜 파싱 | `CurrentCulture` | 사용자가 자기 방식으로 입력한다 |
| 사용자에게 보여 줄 목록 정렬 | `CurrentCulture` | 사용자의 알파벳 순서로 |
| **파일에 저장** | `InvariantCulture` | 다른 로캘에서 다시 읽는다 |
| **네트워크 전송(JSON/XML/CSV)** | `InvariantCulture` | 수신자의 로캘을 모른다 |
| **데이터베이스 리터럴** | `InvariantCulture` | 서버·클라이언트 로캘이 다르다 |
| **로그** | `InvariantCulture` | 로그는 기계가 파싱한다. 시간대는 UTC로 |
| **설정 파일**(`.ini`, `.yaml`, `.env`) | `InvariantCulture` | 개발자 PC와 서버의 로캘이 다르다 |
| **URL·쿼리 문자열** | `InvariantCulture` | 프로토콜의 일부다 |
| **HTTP 헤더** | `InvariantCulture` 또는 RFC 형식(`"R"`) | 규격이 정한다 |
| **캐시 키·해시 입력** | `InvariantCulture` (비교는 `Ordinal`) | 같은 값이 같은 키를 내야 한다 |
| **파일 이름에 넣는 타임스탬프** | `InvariantCulture` + `"yyyyMMdd_HHmmss"` | 정렬 가능하고 파일 시스템 안전 |
| **`switch` 문의 문자열 비교** | 비교는 `StringComparison.Ordinal` | 서식 문제가 아니라 비교 문제다(35.4절) |
| **테스트의 기대값** | `InvariantCulture` | CI 머신의 로캘이 무엇이든 통과해야 한다 |
| **예외 메시지** | 상황에 따라 | 사용자에게 보이면 `CurrentUICulture`, 로그로만 가면 `Invariant` |

> **💡 규칙 하나로 줄이면**
>
> **문자열이 프로세스 밖으로 나가서 다시 들어올 수 있다면 `InvariantCulture`다.** 화면 픽셀에서 끝나는 문자열만 `CurrentCulture`다.

### 실수를 막는 코드 습관

문화권을 매번 손으로 넘기는 것은 잊기 쉽다. 세 가지 장치가 도움이 된다.

**1) 분석기를 켠다.**

.NET SDK에는 문화권 미지정을 잡는 분석 규칙이 내장되어 있다.

| 규칙 | 잡는 것 |
|---|---|
| CA1305 | `IFormatProvider`를 받는 오버로드가 있는데 생략했다 |
| CA1304 | `CultureInfo`를 받는 오버로드가 있는데 생략했다 |
| CA1307 / CA1310 | 문자열 비교에 `StringComparison`을 생략했다 |
| CA1311 | `ToUpper`/`ToLower`에 문화권을 지정하지 않았다 |

```xml
<PropertyGroup>
  <AnalysisMode>Recommended</AnalysisMode>
  <EnforceCodeStyleInBuild>true</EnforceCodeStyleInBuild>
</PropertyGroup>
```

`.editorconfig`에서 심각도를 오류로 올리면 빌드가 막힌다.

```text
dotnet_diagnostic.CA1305.severity = error
dotnet_diagnostic.CA1310.severity = error
```

> **⚠️ CA1305는 "지정했는가"만 본다**
>
> `CultureInfo.CurrentCulture`를 명시적으로 넘기면 CA1305는 통과한다. 분석기는 **의도가 옳은지**까지는 알 수 없다. 저장용 코드에 `CurrentCulture`를 명시해도 경고는 나지 않는다. 분석기는 잊는 실수를 막을 뿐, 잘못 고르는 실수는 코드 리뷰의 몫이다.

**2) 직렬화 경로를 함수 하나로 좁힌다.**

문화권 결정을 코드 곳곳에 흩어 놓지 말고 한 곳에 모은다.

```csharp
static class Wire
{
    static readonly CultureInfo Iv = CultureInfo.InvariantCulture;

    public static string Num (decimal v)     => v.ToString ("0.##########", Iv);
    public static string Date (DateTime v)   => v.ToString ("o", Iv);
    public static string Date (DateTimeOffset v) => v.ToString ("o", Iv);

    public static bool TryNum (string? s, out decimal v)
        => decimal.TryParse (s, NumberStyles.AllowLeadingSign |
                                NumberStyles.AllowDecimalPoint, Iv, out v);

    public static bool TryDate (string? s, out DateTimeOffset v)
        => DateTimeOffset.TryParse (s, Iv, DateTimeStyles.RoundtripKind, out v);
}
```

이렇게 하면 리뷰에서 확인할 지점이 **한 파일**로 줄어든다. 그리고 요구사항이 바뀌었을 때(예: 소수 자릿수 정책 변경) 고칠 곳도 한 곳이다.

**3) 직렬화기의 기본값을 확인한다.**

라이브러리마다 정책이 다르다.

| 도구 | 숫자·날짜 서식 기본값 |
|---|---|
| `System.Text.Json` | **불변 문화권 고정**. 숫자는 JSON 규격, 날짜는 ISO 8601 확장 형식 |
| `XmlConvert`·`XmlSerializer` | XSD 규격 — 문화권 독립 |
| `string.Format` / 보간 문자열 | **`CurrentCulture`** |
| `ToString()` | **`CurrentCulture`** |
| `StringBuilder.AppendFormat` | **`CurrentCulture`** (공급자 오버로드 있음) |
| ADO.NET 매개변수 | 문자열 변환 자체가 일어나지 않는다 — 값이 그대로 전달된다 |

> **💡 SQL을 문자열로 조립하지 마라**
>
> `$"WHERE Amount > {value}"`는 SQL 인젝션 문제이기 이전에 **문화권 문제**다. 독일 로캘에서 `value`가 `1.5m`이면 `WHERE Amount > 1,5`가 만들어지고, 쉼표가 인자 구분자로 해석되어 문법 오류나 엉뚱한 쿼리가 된다.
>
> 매개변수를 쓰면 이 문제가 통째로 사라진다. 값이 문자열을 거치지 않기 때문이다.

### 마지막 함정 — 불변 문화권도 문화권이다

> **⚠️ `InvariantCulture`는 "문화권 없음"이 아니다**
>
> 35.4절에서 이미 지적했듯 `StringComparison.InvariantCulture`는 **대부분 잘못된 선택**이다. 문자열 *비교*에는 `Ordinal`이 맞다. 불변 문화권 비교는 여전히 대조 테이블(collation table)을 통과하므로 느리고, `Ordinal`처럼 단순한 바이트 순서를 보장하지도 않는다.
>
> 이 장이 권하는 것은 **서식화·파싱에서의 `InvariantCulture`**다. 두 용도를 혼동하지 마라.
>
> | 용도 | 옳은 선택 |
> |---|---|
> | 저장할 숫자·날짜의 **서식화/파싱** | `CultureInfo.InvariantCulture` |
> | 식별자·키의 **비교** | `StringComparison.Ordinal` |
> | 사용자 목록의 **정렬** | `StringComparer.CurrentCulture` |
>
> 또한 불변 문화권도 고유한 규칙을 갖는다는 사실을 잊지 마라 — 통화 기호는 `¤`이고, 짧은 날짜는 **미국식으로 월이 먼저**다(`MM/dd/yyyy`). "중립적"이라는 말이 "규칙이 없다"는 뜻은 아니다. 그래서 저장 형식을 정할 때는 불변 문화권의 `"d"`에 기대지 말고 **`"o"`나 `"yyyy-MM-dd"`처럼 명시적인 패턴**을 써라.

## 이 장의 요약

- **포매팅과 파싱은 대칭이 아니다.** 서식화는 형식 공급자의 패턴대로 정확히 하나의 결과를 만들지만, 파싱은 `NumberStyles`/`DateTimeStyles`가 허용하는 범위 안에서 여러 표현을 받아들인다. `ToString`한 결과가 `Parse`로 되돌아온다는 보장은 어디에도 없다.
- **`Parse`는 실패를 예외로 알리고 `TryParse`는 `false`로 알린다.** 그리고 `Parse`가 던지는 예외는 `FormatException` 하나가 아니다 — 널이면 `ArgumentNullException`, 범위를 넘으면 `OverflowException`이다(`.NET Core 3.0` 이후의 `double`은 무한대를 돌려준다). 실패가 정상 흐름의 일부라면 언제나 `TryParse`다.
- **`IParsable<T>`·`ISpanParsable<T>`가 파싱을 타입 시스템 안으로 들여왔다** ※.NET 7. C# 11의 정적 추상 멤버 덕분에 `T.TryParse(...)`를 제네릭 코드에서 부를 수 있고, 값 타입에서는 코드 특수화로 직접 호출까지 낮아진다.
- **형식 문자열은 "무엇을", 형식 공급자는 "어떻게"를 결정한다.** `CultureInfo`는 스스로 서식하지 않고 `NumberFormatInfo`/`DateTimeFormatInfo`로 위임하는 간접 계층이다. 공급자를 생략하면 기본값은 언제나 `CultureInfo.CurrentCulture`이고, 이것이 이 장에서 다룬 거의 모든 사고의 근원이다.
- **표준 형식 문자열은 글자 하나 + 선택적 정밀도**이며, 정밀도의 의미는 글자마다 다르다. `G`는 유효 자릿수, `F`·`N`·`C`·`P`·`E`는 소수점 이하 자릿수, `D`·`X`·`B`는 최소 자릿수다. `D`·`X`·`B`는 정수 타입 전용이다.
- **사용자 지정 형식 문자열의 `;`는 섹션 구분자이고, 섹션이 둘 이상이면 음수 부호가 자동으로 붙지 않는다.** `#`만으로 이루어진 형식은 0을 빈 문자열로 만든다. 서식화 단계의 반올림은 `Math.Round`의 기본값(은행가 반올림)과 다르다.
- **날짜 형식 문자열에서 `M`은 월, `m`은 분이고, 한 글자짜리 사용자 지정 지정자는 표준 형식으로 해석된다.** `r`/`R`/`u`는 UTC 접미사를 쓰면서 변환은 해 주지 않고, `U`는 변환하면서 접미사를 안 쓴다. 개입 없이 명확한 지정자는 `"o"` 하나뿐이다.
- **`DateTimeStyles`의 진짜 역할은 공백 처리가 아니라 결과 `Kind`의 결정이다.** `Z`가 붙은 문자열을 기본값으로 파싱하면 로컬 시각으로 바뀐다. `AdjustToUniversal`, `RoundtripKind` 중 하나를 의식적으로 고르거나, 애초에 `DateTimeOffset`을 써라.
- **`Enum.Parse`는 정의되지 않은 값도 만들어 낸다.** 숫자 문자열은 언제나 성공하므로 `Enum.IsDefined`를 함께 검사해야 하며, `[Flags]` 열거형은 마스크로 직접 검증해야 한다. 실패 시 던지는 예외는 `FormatException`이 아니라 `ArgumentException`이다.
- **`ISpanFormattable`/`IUtf8SpanFormattable`의 `TryFormat`은 힙 할당 없이 서식화한다.** 스택 버퍼로 시작해 모자라면 `ArrayPool`로 승격하는 2단 전략이 정석이다. 다만 이 기법은 측정으로 필요가 확인된 자리에만 쓴다 — 읽기 어렵고 수명 버그를 부른다.
- **`Convert`·`XmlConvert`·`TypeConverter`·`BitConverter`는 각자 다른 구멍을 메운다.** `Convert`는 반올림·진법·Base64, `XmlConvert`는 XML 규약 왕복, `TypeConverter`는 디자이너, `BitConverter`는 이진 변환이다. 다만 `BitConverter`는 머신 엔디언을 따르므로 프로세스 밖으로 나가는 데이터에는 `BinaryPrimitives`를 써라.
- **`CurrentCulture`는 서식을, `CurrentUICulture`는 리소스 조회를 결정한다.** 언어 설정을 바꿀 때 둘을 함께 바꾸면 사용자의 지역 설정을 지운다. 저장·전송·로그·설정·비교에는 `InvariantCulture`, 화면 표시에만 `CurrentCulture`다.

## 연습 문제

1. **독일 로캘 사고를 재현하라.** `CultureInfo.CurrentCulture`를 `de-DE`로 바꾼 뒤 `double.Parse("1.234")`, `double.Parse("1,234")`, `(1.234).ToString()`을 출력하라. 그다음 같은 코드에 `CultureInfo.InvariantCulture`를 넘겨 결과가 어떻게 바뀌는지 표로 정리하라.

2. **`Parse`의 예외 세 가지를 각각 재현하라.** `int.Parse`에 `null`, `""`, `"12x"`, `"99999999999"`를 넘겨 실제로 어떤 예외 타입이 나오는지 확인하라. 그다음 같은 입력을 `int.TryParse`에 넘겨 반환값과 `out` 값을 기록하라.

3. **표준 숫자 형식 문자열 전수 출력기를 만들어라.** `1234.5678`, `0`, `-0.000012`, `int.MaxValue` 네 값에 대해 `G`, `G3`, `F2`, `N2`, `E2`, `C`, `P`, `D5`, `X` 를 모두 적용해 표로 출력하라. 어떤 조합이 `FormatException`을 내는지, 그 이유가 무엇인지 설명하라.

4. **섹션 구분자로 회계 표기를 만들어라.** 양수는 검은 숫자, 음수는 괄호, 0은 `-`로 나오는 사용자 지정 형식 문자열을 작성하고 `1234.5m`, `-1234.5m`, `0m`으로 검증하라. 음수 부호가 자동으로 붙지 않는다는 사실을 이용해야 한다.

5. **`"o"`·`"R"`·`"u"`·`"U"`의 차이를 실측하라.** `DateTimeKind`가 `Utc`/`Local`/`Unspecified`인 `DateTime` 세 개를 만들어 네 형식으로 각각 출력하고, 그 문자열을 다시 `DateTime.Parse`로 읽어 값과 `Kind`가 보존되는지 3×4 표로 정리하라. 어느 조합만 완전히 왕복하는가?

6. **`DateTimeStyles` 조합표를 직접 채워라.** 38.6절의 시나리오 표를 코드로 재현하되, 자기 머신의 시간대에서 실행하라. `AdjustToUniversal`과 `RoundtripKind`가 각각 언제 다른 결과를 내는지 설명하라.

7. **열거형 파싱의 구멍을 막아라.** `[Flags]`가 붙은 열거형과 붙지 않은 열거형 각각에 대해, `Enum.TryParse`가 정의되지 않은 값을 통과시키는 것을 재현하라. 그다음 `Enum.IsDefined`와 마스크 검사를 각각 적용해 두 경우의 올바른 검증 코드를 작성하라.

8. **무할당 포매팅의 이득을 측정하라.** 정수 백만 개를 `,`로 이어 붙이는 코드를 (a) `string.Join`, (b) `StringBuilder` + 보간, (c) `TryFormat` + `stackalloc` + `ArrayPool` 세 방식으로 작성하고 BenchmarkDotNet의 `MemoryDiagnoser`로 할당량과 시간을 비교하라(67.3절, 67.5절). 세 번째가 항상 이기는가?

9. **CI에서 문화권을 강제하라.** 38.10절의 `[Theory]` 예시를 참고해 `de-DE`, `tr-TR`, `th-TH`에서 각각 실행되는 직렬화 왕복 테스트를 작성하라. 일부러 `ToString()`(문화권 미지정)을 쓴 버전을 만들어 테스트가 실패하는 것을 확인한 뒤 고쳐라.

10. **`InvariantGlobalization`을 켜 보라.** 콘솔 프로젝트에 `<InvariantGlobalization>true</InvariantGlobalization>`을 추가하고 `new CultureInfo("fr-FR")`, `"i".ToUpper()`, `DateTime.Now.ToString("D")`가 어떻게 달라지는지 확인하라. 배포 크기 차이도 `dotnet publish` 결과로 비교하라.

11. **CA1305를 오류로 올려라.** 기존 프로젝트에 `dotnet_diagnostic.CA1305.severity = error`를 넣고 빌드하라. 몇 개의 지점이 걸리는가? 각 지점이 "사람이 읽을 문자열"인지 "기계가 읽을 문자열"인지 분류한 뒤 고쳐라.
