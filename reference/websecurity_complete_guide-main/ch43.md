# 43장. 코드 구조: 불변성, 계약, 검증

> **이 장에서 다루는 것**
>
> - 가변성(mutability)이 어떻게 무결성 문제와 가용성 문제를 동시에 만들어내는지
> - 계약(contract)과 사전 조건 검사가 "누가 무엇을 책임지는가"를 코드에 적는 방식
> - 검증의 다섯 단계 — 출처, 크기, 어휘적 내용, 구문, 의미 — 와 **그 순서가 왜 그 순서인지**
> - WAHH의 경계 검증과 SBD의 검증 순서가 충돌하지 않고 보완하는 지점
> - 방어적 코드 구조가 왜 방어가 되지 못하고 오히려 공격 표면이 되는지

42장은 이해의 층위를 다뤘다. 도메인을 어떻게 이해하고, 그 이해를 어떤 개념으로 나누고, 개념 사이의 경계를 어디에 그을 것인가. 그 장이 남긴 것은 어휘였다. 엔티티, 값 객체, 애그리게이트, 바운디드 컨텍스트. 그러나 어휘는 아직 코드가 아니다.

이 장은 그 어휘를 코드의 문법으로 옮긴다. 42.5절이 "값 객체는 불변이어야 한다"고 선언했을 때, 실제 언어에서 그것을 강제하지 않으면 무슨 일이 벌어지는가. 42.5절이 "값 객체는 자신의 불변식을 강제한다"고 했을 때, 그 강제는 코드의 어느 위치에서 어떻게 일어나며 실패하면 무엇을 던져야 하는가. 42.2절이 "모델은 엄격하다"고 했을 때, 그 엄격함은 입력 검증이라는 실무 작업과 어떻게 만나는가.

이 세 질문에 대응하는 것이 이 장의 세 축이다. **불변성**은 데이터 무결성과 가용성 문제를 다루고, **계약**은 잘못된 인자와 잘못된 상태를 다루고, **검증**은 신뢰할 수 없는 입력을 다룬다. 세 축은 서로 독립적인 기법처럼 보이지만 한 문장으로 수렴한다. **어떤 값이 존재한다는 사실 자체가 그 값이 이미 검사되었다는 사실이 되게 하라.** 이 문장을 코드로 실현하는 것이 44장의 도메인 프리미티브이고, 이 장은 그 문장이 왜 필요한지와 그것을 뒷받침하는 코드 구조를 다룬다.

이 장의 43.4절과 43.5절은 앞의 여러 장이 미뤄 둔 청구서를 받는 자리다. 26.8절이 "출처 검증은 검증 순서의 첫 단계"라고 말하며 이 장으로 넘긴 것, 27.5절과 32.8절이 "필터는 어휘 단계의 도구일 뿐"이라며 미뤄 둔 것, 28.6절이 "크기 검사가 파싱보다 먼저 와야 한다"고만 말하고 근거를 남기지 않은 것, 29.1절이 "로직 결함은 스캐너가 못 찾는다"고 했을 때 그 이유가 무엇인지 — 모두 이 두 절에서 하나의 틀로 정리된다.

이 장의 코드 예제는 자바로 쓴다. 도메인은 계속해서 **온라인 서점**이다.

## 43.1 불변성 — 평범한 웹숍에서 무엇이 잘못되는가

객체를 설계할 때 첫 번째로 결정해야 하는 것은 그 객체의 상태가 생성 이후에 바뀔 수 있는가다. **가변성(mutability)** 은 상태 변경을 허용하고, **불변성(immutability)** 은 그것을 금지한다. 사소한 선택처럼 보이지만 보안 관점에서는 큰 차이를 만든다.

불변 객체는 스레드 사이에서 락 없이 공유해도 안전하다. 락이 없으면 블로킹이 없고, 블로킹이 없으면 스레드 경합(thread contention)이 없다. 이것이 곧 높은 데이터 가용성이다. 반대로 가변 객체는 변경되기 위해 설계된 것이므로 **정당하지 않은 갱신**의 여지를 구조적으로 갖는다.

가변성은 대개 의도적으로 선택되지 않는다. 프레임워크가 무인자 생성자와 세터를 요구해서, 혹은 그냥 그렇게 쓰는 것이 익숙해서 선택된다. 그 대가가 얼마나 클 수 있는지를 구체적인 사고 하나로 보자.

### 43.1.1 온라인 서점에서 벌어진 일

온라인 서점을 생각하자. 고객이 로그인하고 장바구니에 책을 담는다. 각 고객에게는 구매 이력과 멤버십 포인트로 계산되는 **신용 점수(credit score)** 가 붙어 있다. 점수가 높으면 세금계산서 후불 결제를 쓸 수 있고, 낮으면 신용카드 결제만 가능하다. 신용 점수 계산은 비용이 큰 연산이라 시스템 부하를 고르게 하려고 지속적으로 백그라운드에서 돌린다.

시스템은 잘 돌아갔다. 최근까지는.

마지막 마케팅 캠페인이 시작되자 트래픽이 몰렸다. 시스템은 부하를 감당하지 못했고 고객들의 불만이 쌓였다. 주문이 결제 단계에서 타임아웃된다, 응답이 느리다, 그리고 **결제 수단이 일관되지 않게 보인다**. 세 번째 불만은 사소해 보였다. 그러나 재무 부서가 "신용 점수가 낮은 고객 다수에게 미수 세금계산서가 나가 있다"고 보고하면서 상황이 달라졌다. 전면 보안 조사가 시작됐다. 시스템이 침해당한 것이 분명해 보였다.

당연히 첫 번째 용의자는 신용 점수 계산 로직이었다. 그러나 근본 원인은 훨씬 넓은 곳에 있었다. **`Customer` 객체의 설계** 였다.

> **리스팅 43-1. 가변 `Customer` 클래스**
>
> ```java
> public class Customer {
>     private static final int MIN_INVOICE_SCORE = 500;
>
>     private Id id;                    // 고객을 유일하게 식별하는 값
>     private Name name;                // 이름
>     private Order order;              // 장바구니에 담긴 항목 전체
>     private CreditScore creditScore;  // 현재 신용 점수를 계산하는 서비스
>
>     public synchronized Id getId() {
>         return id;
>     }
>
>     public synchronized void setId(final Id id) {
>         this.id = id;
>     }
>
>     public synchronized Name getName() {
>         return name;
>     }
>
>     public synchronized void setName(Name name) {
>         this.name = name;
>     }
>
>     public synchronized Order getOrder() {
>         this.order = OrderService.fetchLatestOrder(id);
>         return order;
>     }
>
>     public synchronized void setOrder(Order order) {
>         this.order = order;
>     }
>
>     public synchronized CreditScore getCreditScore() {
>         return creditScore;
>     }
>
>     public synchronized void setCreditScore(CreditScore creditScore) {
>         this.creditScore = creditScore;
>     }
>
>     public synchronized boolean isAcceptedForInvoicePayment() {
>         return creditScore.compute() > MIN_INVOICE_SCORE;
>     }
>     ...
> }
> ```

이 클래스에서 눈여겨볼 것은 두 가지다.

**첫째, 모든 필드가 세터로 초기화된다.** 이것은 내부 상태가 객체 생성 이후에 바뀔 수 있다는 뜻이다. 그리고 더 근본적으로는 **이 객체가 언제 제대로 초기화되었는지를 아무도 알 수 없다**는 뜻이다. 생성자를 통과한 객체는 반쯤 빈 상태이고, 완전해지는 시점은 호출자들의 협조에 달려 있다.

**둘째, 모든 메서드에 `synchronized`가 붙어 있다.** 동시적 필드 수정을 막으려는 의도다. 그 의도는 옳지만 대가가 있다.

### 43.1.2 문제를 무결성과 가용성으로 분류하기

세 가지 불만이 코드의 어느 성질에서 나오는지를 보려면 먼저 그것들을 분류해야 한다. **데이터 무결성(data integrity)** 은 데이터가 생애 주기 전체에 걸쳐 일관되게 유지되는 성질이고, **데이터 가용성(data availability)** 은 데이터를 기대한 성능 수준에서 얻을 수 있는 성질이다.

이 두 범주로 나누면 원인이 있는 자리가 좁혀진다. **데이터를 가져오지 못하는 문제는 가용성 문제이고, 그 원인은 대개 병렬·동시 접근을 막는 코드에 있다. 데이터가 이상해지는 문제는 무결성 문제이고, 그 원인은 대개 수정을 허용하는 코드에 있다.**

**표 43-1. 온라인 서점에서 관찰된 문제의 분류**

| 관찰된 문제 | 범주 | 유력한 원인 |
|---|---|---|
| 응답이 느리고 대기가 길다 | 가용성 | 고객 데이터에 안정적으로 접근하지 못하고 타임아웃된다 |
| 결제 단계에서 주문이 타임아웃된다 | 가용성 | 주문 처리에 필요한 데이터를 제때 가져오지 못한다 |
| 결제 수단이 일관되지 않다 | 무결성 | 신용 점수가 정당하지 않은 방식으로 바뀐다 |

이 분류 자체가 진단 도구다. 뒤에서 볼 것처럼 **같은 하나의 설계 결정(가변성)이 두 범주 모두를 만들어냈다.**

### 43.1.3 암묵적 블로킹이 가용성을 깎는다

동시·병렬 접근을 허용할지 말지는 대개 성능과 일관성 사이의 저울질이다. 상태가 항상 일관돼야 하고 읽기와 갱신이 뒤섞인다면 락 메커니즘이 타당하다. 그러나 접근이 대부분 읽기라면 락은 불필요한 경합을 만든다.

여기서 자주 간과되는 것이 있다. **동시 접근으로 인한 경합은 코드에서 비교적 쉽게 읽히지만, 병렬 접근으로 인한 경합은 그렇지 않다.** 자바에서 메서드에 `synchronized`를 붙이면 그 메서드가 속한 객체의 고유 락(intrinsic lock)을 획득해야 한다. 그런데 **한 객체의 모든 `synchronized` 메서드는 같은 락을 쓴다.** 리스팅 43-1에서 어떤 스레드가 `getOrder()`를 호출해 데이터베이스 왕복을 하는 동안, 전혀 무관한 다른 스레드의 `getName()` 호출이 **암묵적으로 막힌다.**

리스팅 43-1의 `getOrder()`는 특히 나쁘다. 게터를 표방하지만 실제로는 원격 서비스를 호출해 최신 주문을 가져온다. 즉 **락을 쥔 채로 네트워크를 기다린다.** 캠페인 트래픽이 몰렸을 때 무슨 일이 벌어졌을지는 명백하다. 주문 조회가 느려지자 그 객체의 모든 메서드가 줄을 섰고, 그 대기가 결제 단계의 타임아웃으로 나타났다.

온라인 서점의 읽기·쓰기 비율을 실제로 재 보면 읽기가 압도적이다. 데이터를 바꾸는 것은 주로 신용 점수 계산 배치이고, 읽는 것은 수많은 클라이언트 요청과 재무 부서의 리포팅 시스템이다. 그렇다면 락을 그냥 없애면 되지 않는가.

안 된다. 읽기가 대부분이라고 해서 쓰기가 없는 것은 아니고, 가변 객체를 동기화 없이 공유하는 것은 재앙이다. 대안으로 읽기·쓰기를 구분하는 정교한 락을 쓸 수도 있다. 그러나 락 메커니즘은 복잡도와 인지 부하를 늘린다. 그리고 이 책이 42.2절부터 반복해 온 주장이 있다. **복잡도는 그 자체로 공격 표면이다.**

> **불변 값은 락 없이 스레드 사이에서 공유해도 안전하다. 락이 없으면 블로킹도 없다.**

더 단순하고 더 나은 전략은 병렬·동시 접근에 친화적인 설계, 즉 불변성이다.

> **리스팅 43-2. 불변 `Customer` 클래스**
>
> ```java
> public final class Customer {
>     private final Id id;
>     private final Name name;
>     private final CreditScore creditScore;
>
>     public Customer(final Id id,
>                     final Name name,
>                     final CreditScore creditScore) {
>         this.id = notNull(id);
>         this.name = notNull(name);
>         this.creditScore = notNull(creditScore);
>     }
>
>     public Id id() {
>         return id;
>     }
>
>     public Name name() {
>         return name;
>     }
>
>     public Order order() {
>         return OrderService.fetchLatestOrder(id);
>     }
>
>     public boolean isAcceptedForInvoicePayment() {
>         return creditScore.isAcceptedForInvoicePayment();
>     }
> }
> ```

`synchronized`가 전부 사라졌다. 상태가 바뀌지 않으므로 락이 필요 없다. `order()`는 여전히 원격 호출이지만 이제 그 호출이 다른 메서드를 막지 않는다. 클래스는 `final`이고 필드도 전부 `final`이다.

그렇다면 고객 데이터를 어떻게 바꾸는가. **바꿀 수 있는 자료 구조가 있어야 변경을 지원할 수 있는 것은 아니다.** 필요한 것은 읽기와 쓰기를 분리하고, 갱신을 읽기와 다른 경로로 수행하는 것이다. 읽기와 쓰기의 비율이 크게 비대칭인 시스템에서는 이 분리가 값을 한다. 그 구체적 패턴 — 엔티티 스냅샷 — 은 44.10절이 다룬다.

### 43.1.4 신용 점수가 바뀌는 세 가지 경로 — 무결성 문제

가용성은 해결됐다. 무결성은 어떤가. 신용 점수가 낮은 고객이 후불 결제를 쓸 수 있게 된 사건을 다시 보자.

**리스팅 43-3. 가변 `Customer`의 신용 점수 관련 부분**

```java
public class Customer {
    private static final int MIN_INVOICE_SCORE = 500;
    private CreditScore creditScore;
    ...
    public synchronized void setCreditScore(CreditScore creditScore) {
        this.creditScore = creditScore;      // (1) 언제든 새 점수 주입 가능
    }                                        // (3) 외부의 공유 참조를 그대로 대입

    public synchronized CreditScore getCreditScore() {
        return creditScore;                  // (2) 내부 참조가 그대로 새어 나간다
    }

    public synchronized boolean isAcceptedForInvoicePayment() {
        return creditScore.compute() > MIN_INVOICE_SCORE;
    }
    ...
}
```

세 가지 경로가 있다.

**첫째, 초기화를 통한 명시적 변경.** `creditScore` 필드는 `setCreditScore`로 초기화된다. 설계상 의도된 것이지만, 이 방식은 **"최대 한 번만 호출된다"는 보장을 전혀 제공하지 않는다.** 따라서 고객의 신용 점수는 언제든 다시 설정될 수 있다. "클라이언트는 읽기만 할 텐데"라는 가정은 가변 API 앞에서 지켜지지 않는다. 가변 설계는 **누군가가 실수로 가변 API를 쓰는 것을 막을 방법이 없다.** 그 결과 `Customer` 객체의 무결성은 보장될 수 없다.

**둘째, 객체 바깥에서의 변경.** `getCreditScore()`가 내부 `creditScore` 참조를 그대로 반환한다. 참조가 새어 나간(escaped) 것이다. 이제 호출자는 `Customer`의 락을 획득하지 않은 채로 신용 점수를 수정할 수 있다. 공유 가변 객체를 동기화 없이 갱신하는 것은 언젠가 터질 사고다.

여기에 `CreditScore` 자체의 가변성이 겹친다.

**리스팅 43-4. 가변 `CreditScore` 클래스**

```java
public class CreditScore {
    private Id id;

    public synchronized void setCustomerId(Id id) {
        this.id = id;                        // 이 점수가 누구 것인지를 바꿀 수 있다
    }

    public synchronized int compute() {
        List<Record> history =
            BillingService.fetchBillingHistory(id);
        Membership membership =
            MembershipService.fetchMembership(id);
        return CreditScoreEngine.compute(id, history, membership);
    }
    ...
}
```

`setCustomerId`가 공개되어 있으므로 **`Customer`의 ID와 `CreditScore`의 ID가 달라질 수 있다.** 그 순간 `compute()`는 A 고객의 결제 이력으로 B 고객의 점수를 계산한다. 결제 수단이 일관되지 않게 보이는 현상의 완벽한 설명이다.

**셋째, 공유된 참조를 통한 변경.** 가장 덜 눈에 띄는 경로다. `setCreditScore`는 외부에서 받은 가변 참조를 **복사하지 않고** 그대로 내부 필드에 대입한다. 그 참조가 다른 `Customer` 객체에도 대입된다면, 두 고객이 같은 `CreditScore` 인스턴스를 공유하게 된다. 한 고객의 점수를 갱신하면 다른 고객의 점수도 같이 바뀐다. 캠페인 기간에 대량으로 객체를 생성하는 코드 어딘가에서 참조 하나를 재사용했다면, 그것만으로 수많은 저신용 고객이 고신용 고객의 점수를 물려받았을 수 있다.

**리스팅 43-5. 불변 `CreditScore` 클래스**

```java
public class CreditScore {
    private static final int MIN_INVOICE_SCORE = 500;
    private final int score;

    public CreditScore(final int computedCreditScore) {
        isTrue(computedCreditScore > -1, "신용 점수는 -1보다 커야 한다");
        this.score = computedCreditScore;    // 대입 이후 절대 바뀌지 않는다
    }

    public boolean isAcceptedForInvoicePayment() {
        return score > MIN_INVOICE_SCORE;
    }
    ...
}
```

두 가지가 사라졌다. `synchronized`와 **고객 ID에 대한 의존성**이다. 점수는 생성자에서 확정되고 이후 바뀌지 않으므로 락이 필요 없다. 그리고 점수가 확정된 값이라면 그것을 누구 것으로 계산했는지에 대한 의존은 이 객체 안에 있을 이유가 없다. 계산은 객체 바깥으로 나가고, 이 객체는 계산 결과만 담는다. 이것이 42.5절이 말한 **값 객체(value object)** 다. 정체성이 없고 값으로 정의되며, 불변이고, 자신의 불변식(`score > -1`)을 스스로 강제한다.

### 43.1.5 근본 원인을 특정하지 않는 것이 요점이다

세 가지 경로 중 실제로 사고를 일으킨 것은 무엇인가. 재무 부서가 물으면 답해야 하겠지만, **설계 관점에서는 중요하지 않다.**

요점은 이것이다. `Customer`와 `CreditScore`를 가변으로 만들기로 한 하나의 결정이 코드를 **여러 방식으로 동시에** 취약하게 만들었다. 그중 하나를 고쳐도 나머지 둘은 남는다. 반면 불변성을 택하면 세 경로가 **한꺼번에** 닫힌다. 락도 필요 없어지고 우발적 변경에 대한 방어도 필요 없어진다.

이것이 이 책이 "설계에 의한 보안"이라고 부르는 것의 전형적인 모양이다. **보안 검사를 추가해서 안전해지는 것이 아니라, 위험한 상태를 표현할 수 없게 만들어서 안전해진다.** 42.2절이 "모델이 허용하지 않는 상태는 코드에서 표현될 수 없어야 한다"고 정식화한 것의 코드 수준 실현이다.

다만 불변성에도 한계가 있다. 엔티티는 정의상 상태가 변한다. 주문은 담기고, 결제되고, 배송된다. 완전히 불변인 엔티티는 대부분의 도메인에서 성립하지 않는다. 이 간극 — **바뀌어야 하는 것의 무결성을 어떻게 지키는가** — 은 44.9절과 44.10절의 주제다. 이 장은 값 수준의 불변성까지만 다룬다.

> **이 절이 뒷받침하는 것**
>
> - 가변 객체의 내부 참조가 게터로 새어 나가는 것이 무결성 결함의 전형적 경로다 → **44.9** (엔티티에서 게터·세터와 가변 객체 공유를 어떻게 다룰 것인가)
> - 읽기와 쓰기를 분리하면 불변 설계로도 변경을 지원할 수 있다 → **44.10** (엔티티 스냅샷, 엔티티 릴레이)
> - 락 경합이 곧 가용성 저하이고, 가용성은 보안 속성이다 → **45.3**, **45.7** (가용성을 위한 설계, 여유 추정)
> - "모델이 허용하지 않는 상태는 표현될 수 없어야 한다"는 명제의 코드 수준 실현 → **42.2**가 세운 원칙

## 43.2 계약으로 빠르게 실패하기 — 메서드 인자의 사전 조건 검사

1장부터 이 책이 반복해 온 원칙이 있다. **심층 방어(defense in depth)** 다. 경계에 놓인 방어 하나가 뚫려도 그 다음 단계에서 침해의 확산을 막는 장치가 있어야 한다. 물리 보안에서 방문자가 출입 카드로 건물에 들어왔더라도 사진이 붙은 배지를 항상 착용하게 하는 것과 같다.

소프트웨어 설계에서 이 원칙을 실행하는 가장 값싼 도구가 **사전 조건(precondition)** 과 **계약에 의한 설계(Design by Contract)** 다.

사전 조건에 대한 논의는 1960년대 후반 C. A. R. 호어(C. A. R. Hoare)의 이론적 작업에서 나왔다. "계약에 의한 설계"라는 용어는 1980년대 후반 버트런드 마이어(Bertrand Meyer)가 객체 지향의 기초로 삼으면서 만들어졌다. 이론적 흥미와 별개로, 이 개념에는 보안에 직접 닿는 실용적 이득이 있다.

**계약과 사전 조건의 관점에서 설계를 생각하면 어느 부분이 무엇을 책임지는지가 명확해진다.** 그리고 이것이 핵심이다. **보안 문제의 상당수는 시스템의 한 부분이 다른 부분이 어떤 책임을 진다고 가정하는데, 실제로 그 부분은 정반대를 가정할 때 생긴다.** 29장에서 본 로직 결함의 여러 사례, 26.7절에서 본 클라이언트 데이터 처리의 실패, 그리고 이 장 뒤의 43.7절이 다룰 방어적 코드 구조가 모두 이 하나의 패턴이다.

### 43.2.1 계약이란 무엇인가

소프트웨어 밖의 예로 시작하자. 욕실 세면대가 고장 나 배관공을 부른다. 배관공은 두 가지를 요구한다. 문이 열려 있을 것, 그리고 수도 차단 밸브가 잠겨 있을 것. 이것이 **사전 조건**이다. 충족되지 않으면 일이 제대로 되지 않는다. 반대로 배관공은 작업이 끝나면 세면대가 정상 작동할 것을 약속한다. 이것이 계약의 **사후 조건(postcondition)** 이다.

객체의 계약도 같은 구조다. 계약은 메서드가 의도대로 동작하기 위해 필요한 사전 조건을 명시하고, 메서드가 끝난 뒤 객체가 어떻게 변해 있을지를 사후 조건으로 명시한다.

온라인 서점의 예로 보자. 서점의 편집팀은 다음 주 추천 도서 목록을 미리 대기열에 넣어 둔다. 이 대기열을 다루는 클래스가 `RecommendationQueue`다. 편집자가 추천할 책을 떠올리면 `queueIsbn`으로 줄을 세우고, 다음에 소개할 책이 필요하면 `nextIsbn`으로 확인하고, 실제로 소개했으면 `dequeueIsbn`으로 지운다. `size`는 대기 중인 책이 몇 권인지 알려 준다.

**리스팅 43-6. 추천 도서 대기열 (계약이 코드에 없는 상태)**

```java
public class RecommendationQueue {
    private final List<String> isbns = new ArrayList<String>();

    public void queueIsbn(String isbn) {         // 올바른 ISBN만 넣어야 한다
        isbns.add(isbn);
    }

    public String nextIsbn() {                   // 다음 항목이 있을 때만 불러야 한다
        return isbns.get(0);
    }

    public void dequeueIsbn() {                  // 이미 소개한 책을 빼낸다
        isbns.remove(0);
    }

    public int size() {                          // 대기 중인 책의 수
        return isbns.size();
    }
}
```

주석에 적힌 "~해야 한다"가 바로 계약이다. 그런데 그 계약은 **코드 어디에도 없다.** 주석은 강제되지 않는다.

이 클래스의 계약을 정리하면 다음과 같다.

**표 43-2. 추천 도서 대기열의 계약**

| 메서드 | 사전 조건이 요구하는 것 | 사후 조건이 보장하는 것 |
|---|---|---|
| `nextIsbn` | 대기열이 비어 있지 않을 것 | 호출 후 `size`가 그대로다<br>반환값은 ISBN-10 형식을 만족한다 |
| `dequeueIsbn` | 대기열이 비어 있지 않을 것 | 호출 후 `size`가 1 줄어든다 |
| `queueIsbn` | `isbn`이 `null`이 아닐 것<br>`isbn`이 ISBN-10 형식일 것<br>`isbn`이 이미 대기열에 없을 것 | 호출 후 `size`가 1 늘어난다 |

`queueIsbn`의 사전 조건 세 개를 보자. `null`이 안 되는 것은 당연하다. 형식이 맞아야 하는 것도 당연하다. 세 번째 — 이미 대기열에 없어야 한다 — 는 설계상의 결정이다. 편집팀은 같은 책이 두 번 추천 목록에 오르는 것을 원하지 않는다.

계약은 **다르게 쓸 수도 있었다.** 중복 방지의 부담을 대기열 쪽이 지도록 하는 것이다.

**표 43-3. 중복 방지 책임을 대기열이 지는 대안 계약**

| 메서드 | 사전 조건이 요구하는 것 | 사후 조건이 보장하는 것 |
|---|---|---|
| `nextIsbn` | 대기열이 비어 있지 않을 것 | 호출 후 `size`가 그대로다<br>반환값은 ISBN-10 형식을 만족한다 |
| `dequeueIsbn` | 대기열이 비어 있지 않을 것 | 호출 후 `size`가 1 줄어든다 |
| `queueIsbn` | `isbn`이 `null`이 아닐 것<br>`isbn`이 ISBN-10 형식일 것 | 호출 후 `size`가 1 늘거나, 이미 있는 값이면 그대로다 |

여기서 두 가지를 읽어야 한다.

**첫째, 계약은 메서드 하나가 아니라 클래스 전체에 관한 것이다.** 표 43-2는 `queueIsbn`에 들어가는 값이 ISBN-10 형식일 것을 **요구**하고, 동시에 `nextIsbn`이 돌려주는 값이 ISBN-10 형식임을 **약속**한다. 이 두 문장은 짝이다. 입구에서 요구한 것이 출구에서의 보장이 된다.

**둘째, 중복 방지라는 과제는 `RecommendationQueue`나 호출자 중 한쪽이 반드시 져야 한다.** 계약을 명시하는 행위 자체가 그 책임이 누구에게 있는지를 결정한다. 명시하지 않으면 어느 쪽도 지지 않게 되고, 그 틈이 결함이 된다.

### 43.2.2 사전 조건이 충족되지 않으면 무엇을 할 것인가

배관공으로 돌아가자. 문이 잠겨 있으면 배관공은 들어올 수 없다. 수도가 잠겨 있지 않으면 작업을 시작해서는 안 된다. 밸브가 열린 채로 배관을 뜯으면 상황은 훨씬 나빠진다.

더 나은 선택은 **빠르게 실패하는 것(fail fast)** 이다. 사전 조건이 충족되지 않았음이 드러나는 즉시 작업을 중단한다. 여기서 진짜 보안 이득이 나온다.

> **잘못된 데이터나 비정상 상황은 빠르게 멈추는 편이, 그냥 흘려보냈다가 나중에 보안 문제로 터지게 두는 것보다 훨씬 낫다.**

이 원칙이 왜 보안 원칙인지는 이 책이 이미 여러 번 보여 줬다. 27.5절의 2차 SQL 인젝션은 검증되지 않은 값이 저장 시점을 통과해 **나중에 다른 맥락에서** 실행된 사례다. 30.8절이 다룬 "검증 전에 복구하지 말라"는 원칙은 잘못된 데이터를 고쳐서 통과시키는 관행이 만들어 낸 필터 우회를 겨냥한 것이다. 두 경우 모두 **잘못된 값이 시스템 안으로 들어와 정상 값처럼 돌아다니게 된 것**이 문제였다.

계약을 강제하려면 규칙이 코드에 있어야 한다. 마이어가 설계한 에펠(Eiffel)은 사전 조건·사후 조건·불변식을 언어 차원에서 지원하고 런타임이 검사해 준다. 대부분의 언어는 그렇지 않으므로 직접 써야 한다. 어렵지 않다. `if` 하나와 예외 하나면 된다.

**리스팅 43-7. 사전 조건을 빠른 실패로 강제하기**

```java
public void queueIsbn(String isbn) {
    if (isbn == null)
        throw new NullPointerException();
    if (!isbn.matches("[0-9]{9}[0-9X]"))
        throw new IllegalArgumentException("ISBN-10 형식이 아니다");
    if (isbns.contains(isbn))
        throw new IllegalArgumentException("이미 대기열에 있다");
    isbns.add(isbn);
}
```

장황하지만 제 역할을 한다. `null`도, 형식이 틀린 값도, 중복도 들어오지 못한다.

**던지는 예외의 종류에는 의미가 있다.** 자바에서 있어서는 안 될 자리에 `null`이 왔다면 `NullPointerException`을 던진다. 이 예외의 문서상 정의가 "객체가 필요한 자리에 애플리케이션이 `null`을 쓰려 했을 때" 던지는 것이기 때문이다. 값은 있으나 그 값이 받아들여질 수 없다면 `IllegalArgumentException`을 던진다. 이 구분은 호출한 쪽이 무엇을 잘못했는지를 말해 준다.

> **표기 약속 — `notNull`, `isTrue`, `inclusiveBetween`**
>
> 이런 검사를 매번 `if`와 `throw`로 쓰면 코드가 금방 지저분해진다. 이 책은 이후의 예제에서 `notNull(x)`, `isTrue(조건, "메시지")`, `matchesPattern(x, "정규식", "메시지")`, `inclusiveBetween(하한, 상한, 값)`, `validState(조건)` 같은 **한 줄짜리 표기**를 쓴다. 각각은 "조건을 검사하고 어긋나면 적절한 예외를 던진다"는, 위와 정확히 같은 일을 하는 헬퍼다. 원서 SBD는 아파치 커먼즈 랭(Apache Commons Lang)의 `Validate` 유틸리티를 쓰지만, 이 책에서 중요한 것은 **어떤 라이브러리를 쓰는가가 아니라 검사가 메서드의 첫 줄에 있고 어긋나면 즉시 던진다는 구조** 다. 특정 검증 라이브러리의 비교는 이 책의 범위 밖이다.

**리스팅 43-8. 헬퍼 표기로 쓴 같은 코드**

```java
public void queueIsbn(String isbn) {
    notNull(isbn);
    matchesPattern(isbn, "[0-9]{9}[0-9X]", "ISBN-10 형식이 아니다");
    isTrue(!isbns.contains(isbn), "이미 대기열에 있다");
    isbns.add(isbn);
}
```

> **예외 메시지에 잘못된 값을 되돌려 담지 말라**
>
> 리스팅 43-7과 43-8의 예외 메시지 어디에도 **문제가 된 입력값 자체가 들어 있지 않다.** 의도적이다. 예외 메시지는 로그로 가고, 종종 응답으로도 나간다. 잘못된 입력을 그대로 반향(echo)하면 그 자체가 취약점이 된다. 30.7절이 "입력을 절대 그대로 반향하지 말라"는 원칙으로, 30.5절이 "예외 페이로드에 무엇을 담지 말 것인가"로 다룬 문제다. 45.6절이 같은 원칙을 실패 처리 설계의 관점에서 다시 다룬다.

### 43.2.3 어디까지 검사할 것인가

사전 조건을 검사하는 것 자체는 쉽다. 계약을 생각해 내는 것이 일이다. 그 노력이 어디에서 값을 하는가.

**표 43-4. 사전 조건 검사의 적용 범위**

| 메서드의 가시성 | 사전 조건 검사 | 근거 |
|---|---|---|
| `public` | **반드시 한다.** 최소한 인자가 `null`이 아님은 검사한다 | 호출자를 통제할 수 없다. 이 지점이 신뢰 경계다 |
| 패키지 내부 | 판단에 맡긴다 | 패키지가 크고 그 클래스가 널리 쓰이면 하는 편이 낫다. 몇 군데서만 쓰는 헬퍼라면 생략한다 |
| `private` | **하지 않는다** | 호출자가 같은 클래스 안에 있다. 내부 계약이 필요할 정도라면 그 클래스가 너무 큰 것이고, 검사가 아니라 분할이 답이다 |

마지막 행이 중요하다. **`private` 메서드에까지 사전 조건 검사를 흩뿌리고 싶어진다면, 그것은 클래스를 쪼개라는 신호다.** 이 진단을 무시하고 검사를 계속 추가하면 43.7절이 다루는 "자기 자신을 신뢰하지 않는 코드"가 된다.

> **모든 `public` 메서드의 사전 조건을 검사하라. 최소한 인자가 `null`이 아님은 검사하라.**

## 43.3 생성자에서 불변식 유지하기 / 잘못된 상태에 대해 실패하기

메서드 인자의 사전 조건을 봤으니 이제 생성자 인자로 넘어간다. 그리고 마이어가 사전 조건·사후 조건과 함께 말한 세 번째 개념, **불변식(invariant)** 을 다룬다. 불변식은 객체에 대해 **항상 참이어야 하는 것**이며, 객체 생성 시점에 생성자가 최초로 그것을 성립시켜야 한다.

### 43.3.1 생성자의 특별함

생성자 인자는 메서드 인자보다 한 겹 더 까다롭다. 메서드 인자는 주로 처리되거나 객체의 상태를 바꾸는 데 쓰인다. 생성자 인자는 **객체의 최초 상태를 만든다.**

이 차이가 보안에서 중요한 이유는 시간과 거리 때문이다. 객체는 애플리케이션의 한 부분에서 만들어져 완전히 다른 부분에서 사용될 수 있다. 잘못된 상태로 만들어진 객체는 **생성 지점에서 아무 증상도 보이지 않다가**, 한참 뒤 전혀 다른 코드에서 추적하기 어려운 버그로 나타난다. 그리고 추적하기 어려운 버그는 취약점의 온상이다. 그렇게 두느니 빠르게 실패하는 편이 낫다.

생성자의 계약을 강제하는 것은 대개 단순하다. "이 필드는 필수다"라고 말하고 값이 `null`이 아님을 검사하면 된다. 여기서 **필수(mandatory)** 라는 말은 곧 "이 객체의 계약에는 이 필드가 항상 객체를 가리키며 결코 `null`이 아니라는 불변식이 있다"는 뜻이다. `null` 검사를 넣는 것이 그 불변식을 강제하는 행위다.

온라인 서점의 `Book` 클래스로 보자. 계약이 말하는 불변식은 두 개다. 제목이 지정되지 않은 책은 없고, ISBN이 없는 책도 없다.

**리스팅 43-9. 생성자에서 계약을 강제하기**

```java
public class Book {

    private final String title;
    private final String isbn;

    public Book(String title, String isbn) {
        notNull(title);                              // 필수 불변식: 제목
        notNull(isbn);                               // 필수 불변식: ISBN
        matchesPattern(isbn, "[0-9]{9}[0-9X]",
                       "ISBN-10 형식이어야 한다");   // 형식 불변식
        this.title = title;
        this.isbn = isbn;
    }
    ...
}
```

대부분의 검증 헬퍼는 검사한 값을 그대로 돌려주도록 만들 수 있다. 그러면 생성자를 더 압축할 수 있다.

**리스팅 43-10. 압축한 생성자**

```java
public Book(String title, String isbn) {
    this.title = notNull(title);                     // notNull은 검증된 값을 반환한다
    this.isbn  = notNull(isbn);
    matchesPattern(isbn, "[0-9]{9}[0-9X]",
                   "ISBN-10 형식이어야 한다");       // 패턴 검사는 값을 반환하지 않는다
}
```

패턴 검사처럼 값을 돌려주지 않는 검사는 자기 줄에 남는다. 동작은 같다. `null`이면 `NullPointerException`, 형식이 틀리면 `IllegalArgumentException`이다.

여기서 눈에 걸리는 것이 있다. **ISBN 형식 검사가 코드의 두 군데에 있다.** 리스팅 43-8의 `queueIsbn`에도 있고 리스팅 43-9의 `Book` 생성자에도 있다. **DRY(Don't Repeat Yourself)** 원칙의 노골적인 위반이다. 같은 아이디어는 시스템 안에서 단 하나의 권위 있는 표현을 가져야 한다.

이 문제의 해법은 이미 42.9절이 예고했고 44.1절이 완성한다. **ISBN이라는 개념을 타입으로 만드는 것** 이다. `String isbn` 대신 `ISBN isbn`을 받으면 형식 검사가 `ISBN` 클래스 안 한 곳으로 모인다. 이 장에서는 문제가 여기 있다는 것만 표시해 두고 넘어간다.

### 43.3.2 잘못된 상태에 대해 실패하기

세 번째 종류의 계약 검사가 남았다. **연산이 유효하려면 객체가 특정 상태에 있어야 한다**는 사전 조건이다.

추천 도서 대기열이 비어 있다면 "다음 책"을 묻는 것은 말이 되지 않는다. 그것은 `RecommendationQueue`의 현재 상태에 맞지 않는 연산이다. 표 43-2의 계약에서 `nextIsbn`과 `dequeueIsbn`은 대기열이 비어 있지 않을 것을 요구했다.

`isTrue`로 검사할 수도 있다. 그러나 그것은 `IllegalArgumentException`을 던지고, 인자가 아예 없는 `nextIsbn()`을 호출한 사람에게 "인자가 잘못됐다"는 예외는 혼란스럽다. 이 경우에 맞는 것은 상태를 검사하고 `IllegalStateException`을 던지는 표기다.

**리스팅 43-11. 상태 사전 조건 강제**

```java
public String nextIsbn() {
    validState(!isbns.isEmpty());     // 대기열이 비어 있지 않을 때만 의미가 있다
    return isbns.get(0);
}
```

이 구분은 사소해 보이지만 사소하지 않다. **예외의 종류가 "누가 무엇을 잘못했는가"를 말해 준다.** `NullPointerException`은 필수 값이 빠졌다는 뜻이고, `IllegalArgumentException`은 값이 받아들여질 수 없다는 뜻이고, `IllegalStateException`은 값이 아니라 **호출 시점**이 잘못됐다는 뜻이다. 세 번째가 특히 중요한데, 이것이 곧 29장의 로직 결함이 코드에 나타나는 방식이기 때문이다. 이미 배송된 주문에 항목을 추가하려는 시도는 값이 잘못된 것이 아니라 **순서가 잘못된 것**이다.

**표 43-5. 세 가지 계약 검사**

| 검사하는 것 | 어디서 | 어긋났을 때 | 무엇을 뜻하는가 |
|---|---|---|---|
| 인자의 사전 조건 | `public` 메서드의 첫 줄 | `NullPointerException` / `IllegalArgumentException` | 호출자가 계약을 어겼다 |
| 생성 시 불변식 | 생성자 | 같음 | 객체를 유효하지 않은 상태로 만들려 한다 |
| 상태 사전 조건 | 메서드의 첫 줄 | `IllegalStateException` | 지금 이 객체에게 할 수 있는 연산이 아니다 |

세 검사를 모두 넣은 최종 형태는 다음과 같다.

**리스팅 43-12. 계약이 빠른 실패로 강제된 `RecommendationQueue`**

```java
public class RecommendationQueue {
    private final List<String> isbns = new ArrayList<String>();

    public void queueIsbn(String isbn) {
        notNull(isbn);                                    // null 금지
        matchesPattern(isbn, "[0-9]{9}[0-9X]",
                       "ISBN-10 형식이어야 한다");        // 형식 강제
        isTrue(!isbns.contains(isbn), "이미 대기열에 있다");  // 중복 금지
        isbns.add(isbn);
    }

    public String nextIsbn() {
        validState(!isbns.isEmpty());                     // 비어 있으면 호출 불가
        return isbns.get(0);
    }

    public void dequeueIsbn() {
        validState(!isbns.isEmpty());                     // 비어 있으면 호출 불가
        isbns.remove(0);
    }

    public int size() {                                   // 언제든 호출 가능
        return isbns.size();
    }
}
```

코드가 다섯 줄 늘었다. 그리고 훨씬 안전해졌다. 잘못된 인자는 초기에 멈추고, 객체는 유효하지 않은 상태에 들어갈 수 없다. 노력의 대부분은 코드를 쓰는 데가 아니라 **설계를 끝까지 생각하고 그것을 계약으로 표현하는 데** 들어간다. 그 일은 어차피 해야 하는 일이다.

> **이 절이 뒷받침하는 것**
>
> - 계약을 명시하는 행위가 곧 책임의 소재를 결정한다 → **43.7**이 책임이 불분명해진 코드의 모습을 보여 준다
> - 생성자의 형식 검사 중복은 개념을 타입으로 만들라는 신호다 → **44.1** (도메인 프리미티브와 불변식)
> - `IllegalStateException`은 로직 결함이 코드에 나타나는 자리다 → **29.1** (로직 결함의 본질), **43.4.5** (의미 검사)
> - 예외 메시지에 입력을 담지 않는다 → **30.5**, **30.7**, **45.6**
> - `private` 메서드까지 검사가 번지면 클래스를 쪼개라 → **44.6** (과밀한 엔티티 메서드 정리)

## 43.4 검증의 순서 — 데이터의 출처 → 크기 → 어휘적 내용 → 구문 → 의미

시스템을 안전하게 유지하려면 데이터를 검증해야 한다. "입력을 검증하라"는 조언은 웹 보안 문헌의 첫 페이지에 항상 있다. 명백하고 온당한 조언처럼 들린다.

그러나 이 조언은 그대로는 쓸모가 없다. 두 가지 문제가 있다. 첫째, **입력이 모든 곳에서 검증되도록 코드를 어떻게 구조화할 것인가**. 둘째, **애초에 유효한 데이터란 무엇인가**.

두 번째부터 보자. 어떤 값이 유효한지를 그 값만 보고 묻는 것은 무의미하다. `42`는 유효한 입력인가. `-1`은? `<script>install(keylogger)</script>`는? 답은 전부 "상황에 따라 다르다"다. 책을 주문할 때 수량 `42`는 유효하고 `-1`은 아니다. 기온을 보고할 때 `-1`은 완벽히 정상이다. 스크립트 문자열은 대부분의 자리에서 원하지 않는 값이지만, 보안 버그를 제보하는 게시판에서는 정당한 본문이다.

"검증"이라는 단어 자체도 여러 가지를 뜻한다. 어떤 사람은 `AV56734T`가 유효한 주문번호라고 말한다. 시스템이 쓰는 주문번호 **형식**을 따르기 때문이다. 다른 사람은 유효하지 않다고 말한다. 그 번호의 주문이 시스템에 **존재하지 않기** 때문이다. 또 다른 사람은 주문이 존재해도 유효하지 않다고 말한다. 배송을 위해 해당 주문을 처리하려 했는데 그 시점에 **그 상태에서는 불가능**했기 때문이다. 셋 다 "검증"이라는 같은 단어를 썼지만 전혀 다른 것을 검사했다.

이런 혼란 속에서 "입력을 검증하라"는 조언은 "운전할 때 사고를 내지 마라"만큼의 정보량을 갖는다. 선의는 분명하지만 도움이 되지 않는다.

혼란을 정리하는 틀이 있다. 검증의 종류를 다섯으로 나누고, **그것을 수행할 순서**를 정하는 것이다.

### 43.4.1 다섯 단계와 그 순서

**표 43-6. 검증의 다섯 단계**

| # | 단계 | 묻는 질문 | 비용 | 실패 시 |
|---|---|---|---|---|
| 1 | **출처(origin)** | 이 데이터가 정당한 발신자로부터 왔는가 | 매우 낮음 (설정 조회 또는 서명 검증) | 즉시 폐기 |
| 2 | **크기(size)** | 크기가 합리적인가 | 매우 낮음 (길이 비교) | 즉시 폐기 |
| 3 | **어휘적 내용(lexical content)** | 기대한 문자와 인코딩만 들어 있는가 | 낮음 (한 번 훑기) | 즉시 폐기 |
| 4 | **구문(syntax)** | 형식이 맞는가 | 중간 (파싱, CPU와 메모리) | 즉시 폐기 |
| 5 | **의미(semantics)** | 이 값이 이 맥락에서 말이 되는가 | 높음 (데이터베이스 왕복) | 도메인 예외 |

이 목록의 순서는 임의가 아니다. **비용이 낮은 검사가 앞에 오고, 비용이 높은 검사가 뒤에 온다. 그 결과 앞의 검사가 뒤의 검사를 보호한다.**

각 단계의 비용을 구체적으로 보자. 출처를 확인하는 것은 IP 대역 비교나 서명 검증이며 값싸다. 크기를 확인하는 것은 정수 비교 하나다. 어휘적 내용을 확인하려면 데이터를 한 번 훑어야 하므로 시간과 자원이 조금 더 든다. 구문을 확인하려면 파싱이 필요할 수 있고, 파싱은 CPU를 소모하며 스레드를 상당 시간 점유한다. 의미를 확인하려면 대개 데이터베이스까지 다녀와야 한다.

**이 순서가 만드는 것이 방패의 층이다.** 1단계를 통과하지 못한 데이터는 2단계를 소모시키지 않는다. 2단계를 통과하지 못한 데이터는 파서를 건드리지 못한다. 4단계를 통과하지 못한 데이터는 데이터베이스에 도달하지 못한다. 공격자가 시스템의 가장 비싼 부품을 때리려면 그 앞의 모든 값싼 관문을 통과해야 한다.

그리고 **각 단계는 앞 단계를 전제한다.** 이것이 순서의 두 번째 근거다.

- 크기를 검사하는 것은 데이터를 받아들이기로 결정한 뒤에나 의미가 있다. 출처가 불명이면 크기가 얼마든 상관없다.
- 문자를 훑어보려면 훑을 데이터의 양이 유한하다는 것이 먼저 보장되어야 한다.
- 구문을 파싱하려면 그 안에 파서를 폭발시킬 토큰이 없다는 것이 먼저 보장되어야 한다.
- 의미를 묻는 것은 값이 어떤 형식인지 알아야 가능하다. `AV56734T`가 주문번호 형식인지도 모르면서 "이 주문이 존재하는가"를 묻는 것은 데이터베이스에 쓰레기를 던지는 일이다.

### 43.4.2 1단계 — 데이터의 출처 확인

데이터를 처리하는 데 노력을 들이기 전에 그것이 어디서 왔는지를 확인하는 것은 합당하다. 이유는 **공격의 비대칭성** 이다.

비대칭이란 공격자가 악성 데이터를 보내는 데 드는 노력이, 시스템이 그 데이터를 처리하는 데 드는 노력보다 훨씬 적다는 뜻이다. 이것이 서비스 거부(DoS) 공격의 기본 논리다. 시스템에 쓰레기 데이터를 대량으로 보내면 시스템은 그것을 처리하느라 바빠지고, 본래 해야 할 일을 할 자원이 남지 않는다. 지리적으로 분산된 다수의 클라이언트가 동시에 보내는 형태가 분산 서비스 거부(DDoS)이며, 그 클라이언트는 대개 원격 조종 기능이 심어진 봇넷이다.

출처 검증이 모든 경우에 도움이 되지는 않는다. 그러나 **비대칭을 우리 쪽으로 조금 되돌리는 가장 값싼 첫 단계** 다. 출처가 정당하면 계속 진행하고, 아니면 버린다. 대략 두 가지 수단이 있다.

**IP 주소 확인.** 가장 명백한 방법이다. 연결이 점점 개방적으로 변하면서 적용 범위가 좁아지고 있지만 여전히 쓸모가 있다. 마이크로서비스 구조라면 일부 서비스는 가장자리에서 외부 트래픽을 받지만 나머지는 내부에 앉아 다른 서비스로부터의 호출만 기대한다. 내부 서비스는 특정 IP 대역만 받도록 제한할 수 있다. 가장자리 서비스는 대개 불가능하다. 어떤 클라이언트에서든 접근 가능해야 하기 때문이다.

실무에서 이 검사는 **애플리케이션 코드 안에서 하는 일이 아니다.** 네트워크 설정으로 제한한다. 물리 장비라면 라우터에서, 클라우드라면 보안 그룹에서 한다. 사내 시스템, 예를 들어 매장 POS 시스템처럼 접근 주체가 사내 단말과 사무실 데스크톱으로 한정되는 경우에는 IP 대역 기반 출처 확인이 잘 맞는다. 다만 그런 상황은 점점 드물어지고 있다.

그리고 **IP 필터도 MAC 주소 필터도 보장이 아니다.** MAC 주소는 운영체제에서 바꿀 수 있고, IP 주소는 스푸핑되거나 실제 장비가 탈취될 수 있다. 최소한의 1차 방어선일 뿐이다. 이 한계는 20.2절이 클라이언트 식별의 관점에서, 26.8절이 클라이언트가 보낸 데이터의 관점에서 이미 다뤘다.

**접근 키(access key) 요구.** 시스템이 어디서든 오는 요청을 받아야 한다면 IP로 걸러낼 수 없다. 고객을 상대하는 공개 서비스는 거의 다 이 경우다. 이때 남는 수단이 접근 키다. 키는 정당한 클라이언트 전부에게 나눠 준다. 클라이언트가 다른 시스템이면 배포 시점에 주고, 애플리케이션이면 애플리케이션에 넣고, API 이용자면 이용 약관에 서명할 때 발급한다. 요점은 **키를 가졌다는 사실 자체가 데이터를 보낼 자격이 있다는 증명**이 된다는 것이다.

AWS의 REST API가 전형적인 예다. S3 같은 자원을 관리하는 이 API에 요청을 보낼 때는 접근 키를 `Authorization` 헤더에 담아야 한다.

```http
GET /photos/puppy.jpg HTTP/1.1
Host: johnsmith.s3.amazonaws.com
Date: Mon, 26 Mar 2007 19:37:58 +0000
Authorization: AWS AKIAIOSFODNN7EXAMPLE:frJIUN8DYpKDtOLCwo//yllqDzg=
```

*리스팅 43-13. 접근 키와 서명을 사용하는 AWS REST API 호출 (SBD 4장 리스팅 4.13 기준)*

헤더가 없으면 요청은 거부된다. 그런데 **키를 보내는 것만으로는 부족하다.** 키가 유출되면 공격자가 그것으로 사칭할 수 있다. 그래서 `Authorization` 헤더에는 접근 키와 함께 **서명**이 들어간다. 메시지 내용을 비밀 키로 서명한 값이며, 그 비밀 키는 발신자와 AWS만 안다. AWS는 접근 키를 보고 어떤 비밀 키로 서명을 검사할지 정한다.

이 방식에는 서버 측 계산 비용이 든다. 서명이 맞는지 확인해야 하기 때문이다. 비싼 연산은 아니지만, 누군가 대량의 데이터를 보내 그 검증에 자원을 쓰게 만드는 공격에 약간의 여지를 준다. 대신 얻는 것은 **공격자가 진짜 접근 키를 가져야 한다는 조건**이고, 악용이 확인되면 그 키를 한동안 차단할 수 있다는 것이다.

접근 키를 쓰는 것은 추가 작업이다. 다만 대개 한 번 하면 되고, API 게이트웨이류의 제품을 쓴다면 제공되기도 한다. 직접 만든다면 **접근 키 자체에 대해서도 적절한 검증(길이, 문자 집합, 형식)을 해야 한다.** 그렇지 않으면 접근 키가 새로운 공격 경로가 된다. 이 자기 참조는 우연이 아니다. 1단계의 도구도 결국 입력이고, 그 입력도 2·3·4단계를 거쳐야 한다.

> **접근 토큰**
>
> 접근 키는 접근 토큰의 특수한 경우다. 인증 서버가 토큰을 발급하고, 그 토큰이 다른 자원에 접근할 권한의 증거가 되는 프로토콜들이 있다. 공통점은 **이전에 인증이 있었고, 토큰·키가 발신자가 주장하는 그 주체임을 증명한다**는 것이다. 이 책은 21장과 22장에서 HTTP 수준의 인증을 다뤘고, 24장에서 인가를 다뤘다. 여기서는 그 결과물이 검증 순서의 1단계 도구가 된다는 점만 짚는다.

**26.8절이 이 단계였다.** 그 절은 클라이언트가 보낸 데이터의 출처를 어떻게 검증할 것인가를 설계 관점에서 정리했다. 숨은 폼 필드, 쿠키에 담긴 가격, `Referer` 헤더 — 모두 "정당한 발신자로부터 온 값인가"라는 하나의 질문에 답하지 못하는 것들이었다. 그 절이 내린 처방(전달하지 않기, 서명하거나 암호화하기, 서버에서 재검증하기)은 이 단계의 구체적 실행이다.

### 43.4.3 2단계 — 크기 확인

1GB짜리 주문번호를 받아들이는 것이 말이 되는가. 그렇지 않다. 출처가 정당함을 확인했다면 다음 질문은 **크기가 합리적인가** 이며, 이 검사는 **가능한 한 이른 시점에** 해야 한다.

합리적인 크기는 전적으로 맥락에 달렸다. 동영상 사이트의 업로드라면 100MB에서 수 GB도 이상하지 않다. 단순한 JSON이나 XML 메시지를 주고받는 업무 애플리케이션이라면 수 KB를 넘을 이유가 없다. **당신의 데이터에 합리적인 크기는 얼마인가.** 이 질문에 답이 없다면 크기 검사도 없는 것이다.

HTTP로 데이터가 온다면 `Content-Length` 헤더와 실제 본문 크기를 확인할 수 있다. 배치 처리라면 파일 크기를 확인한다. 웹 서버와 컨테이너는 대개 POST 본문 크기와 헤더 크기의 상한을 설정할 수 있게 해 준다. 12장이 다룬 웹 서버 오설정의 상당수가 이 상한을 그대로 두거나 지나치게 크게 잡은 것이었다.

**전체 크기만으로는 부족하다.** 데이터를 처리하면서 **각 부분의 크기도 확인해야 한다.** 공격자는 정상 크기의 요청 안에 1GB짜리 주문번호를 숨겨 넣을 수 있다. 전체 요청 크기 검사를 잊었을 수도 있고, 전체 크기는 상한 안에 있는데 특정 필드 하나만 비정상일 수도 있다. 주문번호의 크기도 따로 검사한다면, **주문번호를 만드는 모든 자리에 방어가 생긴다.**

이 습관이 만드는 것이 무엇인지가 중요하다. 주문번호, 전화번호, 도로명, 우편번호에 대해 이 검사를 일관되게 하면, **공격자가 큰 데이터를 밀어 넣을 자리를 찾기가 매우 어려워진다.** 어떤 부분도 이상한 크기를 가질 수 없다는 방어가 생긴 것이다.

온라인 서점의 예로 보자. 주문에 관한 배치 파일이나 HTTP 요청을 받는다. 그 안의 책은 대개 ISBN으로 식별된다. ISBN-10은 아홉 자리 숫자에 검사 숫자 하나가 붙은 형태다. 파일이나 요청 전체의 크기를 확인하는 것도 좋지만, 그 안에서 ISBN이어야 할 부분을 골라냈다면 그 부분도 따로 확인해야 한다.

**리스팅 43-14. 길이 검사를 포함한 `ISBN` 클래스**

```java
public class ISBN {
    private final String isbn;

    public ISBN(final String isbn) {
        notNull(isbn);                          // null이 아님을 보장
        inclusiveBetween(10, 10, isbn.length()); // 정확히 10자.
                                                 // 긴 문자열은 여기서 멈춘다
        this.isbn = isbn;
    }
    // 이후 절에서 검사가 더 붙는다
}
```

길이 검사가 불필요해 보일 수 있다. 다음 단계에서 어차피 정규식으로 내용과 구조를 검사할 것이기 때문이다. 정규식이 `[0-9]{20}`이라면 25자짜리 문자열은 어차피 매칭에 실패한다. 왜 두 번 검사하는가.

**길이 검사의 목적은 값을 거르는 것이 아니라 정규식 엔진을 보호하는 것이다.** 문자열이 25자가 아니라 10억 자라면 어떻게 되는가. 정규식 엔진은 그 거대한 문자열을 메모리에 올리고 처리하기 시작한다. 너무 크다는 사실을 알아채지 못한 채로. **이른 길이 검사가 뒤 단계를 지킨다.**

이 관계는 이 책이 여러 번 본 것이다. 28.6절의 Billion Laughs 공격에서 1KB도 안 되는 XML이 10억 개의 문자열로 팽창해 파서를 죽였다. 40.6절의 GraphQL DoS에서 짧은 질의 하나가 중첩 관계를 타고 지수적으로 팽창했다. 두 경우 모두 **입력의 크기와 처리의 비용이 비례하지 않는다**는 것이 공격의 본질이었고, 방어의 첫 줄은 항상 "처리하기 전에 크기를 본다"였다. 45.7절이 이 문제를 가용성 테스트의 관점에서 다시 다룬다.

### 43.4.4 3단계 — 어휘적 내용 확인

데이터가 신뢰할 만한 출처에서 왔고 크기도 합리적임을 알았다면 이제 내용을 들여다볼 수 있다. 대개는 결국 파싱해서 원하는 부분을 뽑아내야 할 것이다. JSON이든 XML이든. 그러나 **파싱은 CPU와 메모리 양쪽에서 비싸다.** 파싱을 시작하기 전에 검사를 한 겹 더 넣는다.

**어휘적 내용(lexical content)을 검사한다는 것은 내용을 보되 구조는 보지 않는 것이다.** 데이터를 훑으면서 기대한 문자와 기대한 인코딩만 들어 있는지 확인한다. 수상한 것이 나오면, 서버를 무릎 꿇릴 수도 있는 파싱을 시작하는 대신 데이터를 버린다.

예를 들어 숫자만 들어 있어야 하는 데이터라면 스트림을 훑어서 그 밖의 것이 있는지 본다. 있다면 결론은 둘 중 하나다. 실수로 깨졌거나, 시스템을 속이려고 의도적으로 조작됐거나. 어느 쪽이든 안전한 선택은 버리는 것이다. HTML 인코딩된 평문을 기대한다면, 모든 `<`는 `&lt;`로 인코딩되어 있어야 하므로 꺾쇠괄호는 하나도 나오지 않아야 한다. 꺾쇠괄호를 만나면 경계한다. 누군가 자바스크립트 조각을 밀어 넣으려는 것일 수 있다. 안전한 쪽을 택해 버린다.

**어휘적 내용은 데이터를 가까이서 볼 때의 모습이다.** 세부에 집중하고 큰 구조는 보지 않는다. 단순한 상황에서는 단순한 정규식이 훌륭한 도구다. ISBN-10은 숫자와 문자 `X`만 담을 수 있다. (가독성을 위해 하이픈과 공백이 들어가기도 하지만 여기서는 무시한다.)

**리스팅 43-15. 어휘적 내용을 검사하는 정규식이 붙은 `ISBN` 클래스**

```java
public class ISBN {
    private final String isbn;

    public ISBN(final String isbn) {
        notNull(isbn);
        inclusiveBetween(10, 10, isbn.length());  // 길이는 10자
        isTrue(isbn.matches("[0-9X]*"));          // ISBN에 나올 수 있는
                                                  // 문자만 들어 있는가
        this.isbn = isbn;
    }
}
```

입력이 더 복잡하다면 — XML 같은 것이라면 — 더 강력한 **렉서(lexer, 토크나이저)** 가 필요하다. 렉서는 문자열을 **렉심(lexeme)** 또는 **토큰(token)** 이라 불리는 부분으로 쪼갠다. 토큰은 의미를 갖는 가장 작은 단위, 또는 구문 단위를 이루는 문자열이다. 영어 문장에서는 단어가 토큰이다. XML에서는 태그와 그 안의 내용이 토큰이다.

```xml
<book>
   <title>Secure by Design</title>
   <authors>
       <author>Dan Bergh Johnsson</author>
       <author>Daniel Deogun</author>
       <author>Daniel Sawano</author>
   </authors>
</book>
```


*리스팅 43-18. 10억 개의 lol로 팽창하는 XML (SBD 4장 리스팅 4.18 기준)*

이것을 통과시킬 수는 없다. 방어 중 하나가 **XML 엔티티 정의 자체를 허용하지 않는 것** 이다. 즉 렉서가 데이터를 훑으면서 `<!ENTITY`를 정당한 렉심으로 인정하지 않게 한다. **이것이 어휘 단계의 방어다.** 구조를 이해할 필요가 없다. 이 토큰이 나와서는 안 된다는 것만 알면 된다.

여기서 28.6절이 남긴 질문에 답할 수 있다. 그 절은 파서 설정으로 외부 엔티티와 DTD를 끄는 처방을 제시했다. 그것은 옳지만 **파서에 도달한 뒤의 방어** 다. 어휘 검사는 **파서에 도달하기 전의 방어** 다. 두 방어는 층이 다르며, 이 책이 말하는 심층 방어는 정확히 이런 형태를 뜻한다.

실무에서는 문제가 하나 있다. XML 문서를 다룰 때 결국 파싱해서 필요한 부분을 뽑아야 한다. 검사용 파싱과 구조용 파싱을 두 번 하고 싶지는 않다. 해법은 **어휘 검사를 파싱 안에 끼워 넣는 것** 이다. 스트림 처리의 일부로 어휘 검사를 수행하면 한 번의 통과로 둘 다 된다.

**7.6절과 7.7절이 이 단계를 위한 준비였다.** 그 두 절은 URL 인코딩, HTML 엔티티, base64, 유니코드, 16진 인코딩을 정리하고, 정규화(canonicalization)와 다중 인코딩의 함정 — 오버롱 UTF-8, 이중 디코딩 — 을 다뤘다. 어휘 검사가 무의미해지는 가장 흔한 경로가 바로 이것이다. **어떤 인코딩으로 볼 것인가를 정하지 않고 문자를 검사하면, 같은 바이트열이 검사하는 쪽과 사용하는 쪽에서 다른 문자로 읽힌다.** 27.5절이 다룬 필터 우회의 상당수, 32.8절이 다룬 XSS 필터 우회의 상당수가 이 불일치를 이용한 것이었다.

그래서 어휘 검사의 정확한 정의는 "기대한 문자가 들어 있는가"가 아니라 **"기대한 인코딩으로 해석했을 때 기대한 문자만 들어 있는가"** 다. 인코딩을 명시하지 않은 어휘 검사는 검사가 아니다.

### 43.4.5 4단계 — 구문 확인

어휘 단계에서 가까이 봤다면, 구문 단계에서는 **뒤로 물러나 전체 그림을 본다.** XML이라면 여는 태그마다 닫는 태그가 있는가. 속성은 태그 안에서 제대로 형성되어 있는가.

때로는 구문 검사도 정규식 하나로 끝난다. 다만 솔직히 말해 정규식이 항상 단순하지는 않다. 복잡하고 때로는 이해 불가능한 정규식을 만들어 내는 경우를 흔히 본다. **정규식은 단순한 것을 단순하게 쓸 때만 쓴다.** 정규식을 보는 순간 머리가 아프다면 그 로직은 코드로 쓰는 편이 낫다.

ISBN은 구문 검사가 단순한 예다. ISBN-10은 아홉 자리 숫자에 검사 숫자 하나다. 검사 숫자는 10일 수 있고 그때는 문자 `X`로 표기한다. 따라서 `[0-9]{9}[0-9X]`에 매칭되는지 보면 된다. 매칭되면 형식이 맞고, 아니면 버린다.

XML처럼 복잡한 구조는 파서가 필요하다. 그리고 **크고 복잡한 자료 구조를 파싱하는 것은 상당한 계산 자원을 요구한다. 그래서 파서는 DoS를 노리는 공격자에게 매력적인 표적이다.** 앞의 세 단계 — 출처, 크기, 어휘적 내용 — 는 상당 부분 **파서를 방패로 감싸기 위해** 존재한다.

구문 검사에는 형식 검사 외에 하나가 더 있다. **체크섬(checksum)** 이다. ISBN의 열 번째이자 마지막 자리는 검사 숫자다. 계산 방식의 세부는 넘어가되, 이 검사도 구문 검사의 일부다.

**리스팅 43-19. 어휘와 구문을 모두 검사하는 `ISBN` 클래스**

```java
public class ISBN {
    private final String isbn;

    public ISBN(final String isbn) {
        notNull(isbn);
        inclusiveBetween(10, 10, isbn.length());
        isTrue(isbn.matches("[0-9X]*"));         // 어휘: 기대한 문자만
        isTrue(isbn.matches("[0-9]{9}[0-9X]"));  // 구문: 형식이 맞는가
        isTrue(checksumValid(isbn));             // 구문: 검사 숫자가 맞는가
        this.isbn = isbn;
    }

    private boolean checksumValid(String isbn) { /* ... */ }
}
```

구조가 충분히 단순하면 어휘 정규식 하나를 쓰고 곧바로 비슷한 구문 정규식을 하나 더 쓰는 것이 우스꽝스러워 보인다. 이런 경우에는 두 단계를 하나로 합치는 것이 보통이다.

**리스팅 43-20. 어휘와 구문 검사를 한 단계로 합친 형태**

```java
public ISBN(final String isbn) {
    notNull(isbn);
    inclusiveBetween(10, 10, isbn.length());
    isTrue(isbn.matches("[0-9]{9}[0-9X]"));  // 어휘 + 구문 검사가 합쳐졌다
    isTrue(checksumValid(isbn));
    this.isbn = isbn;
}
```

이것이 검증 순서를 어기는 것처럼 보일 수 있다. 그렇지 않다. **어휘 분석과 구문 분석이 너무 비슷해서 같은 메커니즘이 둘 다 수행하는 것** 이다. 두 단계가 서로 얽혔거나 붕괴했다고 보면 된다. 순서의 본질적 아이디어는 그대로 남아 있다. **합쳐도 되는 것은 비용이 같은 인접한 두 단계이고, 비용이 다른 단계를 합치거나 뒤집는 것은 다른 문제다.**

특히 **길이 검사는 이 축약에서 살아남아야 한다.** 리스팅 43-20에서 `inclusiveBetween`이 남아 있는 이유가 그것이다. 어휘와 구문은 같은 정규식 엔진이 하지만, **그 엔진에 무엇이 들어가는지를 결정하는 것은 길이 검사** 이기 때문이다.

### 43.4.6 5단계 — 의미 확인

출처, 크기, 내용, 구조를 확인하고 나면 입력 데이터에 대해 상당한 확신이 쌓인다. 이제 그것에 따라 행동할 준비가 됐다. 여기까지 오는 동안 CPU를 많이 쓰거나 메모리를 많이 쓰는 검사를 했을 수 있다. 주문에 여러 항목을 추가하라는 큰 XML 메시지를 처리했을 수도 있다. 그러나 **지금까지 한 것은 전부 데이터 자체에 대한 작업이었고, 데이터와 시스템 나머지의 관계에 대한 작업이 아니었다.** 아마 데이터베이스는 한 번도 건드리지 않았을 것이다.

주문을 확장하는 큰 XML 메시지의 예에서, 추가할 주문 항목을 많이 찾아냈을 수는 있다. 그러나 **지정된 상품 번호가 실제로 존재하는지 확인하지 않았고, 재고 상태는 더더욱 확인하지 않았다.** 지정된 주문 자체가 존재하지 않을 수도 있고, 이미 배송돼서 확장이 불가능한 상태일 수도 있다. 구문만 확인했을 뿐이다.

이제 **의미 검사** 의 차례다. 이 데이터는 **시스템 나머지가 갖고 있는 세계관과 일관되는가.** 이 상품 번호가 상품 카탈로그에 있는가. 이 주문번호가 가리키는 주문에 항목을 더 붙일 수 있는가.

**이런 제약이 놓일 가장 자연스러운 자리는 도메인 모델이다.** 상품 카탈로그 도메인 서비스에 "이 상품 번호가 존재하는가"를 묻고, 없으면 예외를 던져 흐름을 끊는다. 마찬가지로 이미 닫힌(결제되고 배송된) 주문에 항목을 추가하려 하면 `Order` 클래스에서 `IllegalStateException`이 나온다. 43.3.2절이 다룬 상태 사전 조건이 바로 이것이다.

실은 이 검사들이 도메인 모델에 워낙 자연스럽게 속하기 때문에, 그것을 "검증"이라고 부르는 것조차 어색하다. **그것은 도메인 모델 그 자체다.**

그럼에도 의미 검증이 이 목록에 들어가는 것은 옳다. 왜냐하면 **"검증한다"는 동사는 혼자서는 의미가 없기 때문이다.** 항상 무엇에 비추어 검증하는지가 있어야 한다. 데이터가 어떤 규칙과 제약을 지키는지 검증하는 것이고, 그 규칙과 제약을 이루는 것이 도메인 모델이다. 도메인 모델은 **당신이 세계를 어떻게 보기로 했는지에 대한 진술** 이다. 주문번호가 특정 형식을 갖는다고 모델링했고, 주문이 배송되면 수정 불가로 닫힌다고 모델링했다. 이 모든 단계를 통과하고 나면 데이터가 그 모델에 비추어 온당하다는 것을 알게 된다. 검증된 것이다.

**29장 전체가 이 단계의 실패에 관한 장이었다.** 로직 결함이 스캐너에 잡히지 않는 이유(→ 29.1)가 여기서 설명된다. 스캐너는 1~4단계를 검사할 수 있다. 이상한 문자, 이상한 길이, 이상한 형식은 기계적으로 탐지 가능하다. 그러나 **5단계에서 공격자가 보내는 입력은 정상 사용자가 보내는 입력과 문자 단위로 동일하다.** 다른 것은 그 입력이 놓인 맥락뿐이다. 다른 사람의 계좌번호는 완벽히 정상적인 계좌번호다. 이미 사용한 쿠폰 코드는 완벽히 정상적인 쿠폰 코드다. 배송된 주문에 항목을 추가하는 요청은 문법적으로 완전무결하다.

**그래서 5단계의 방어는 필터가 아니라 모델이어야 한다.** 29.3절의 미수금 원장 결함, 29.4절의 자작 할인 쿠폰, 29.5절의 무료 보험 증서 — 세 사건 모두 1~4단계를 완벽하게 통과한 입력이 일으킨 것이었다.

### 43.4.7 순서를 바꾸면 무슨 일이 생기는가

다섯 단계의 순서가 왜 그 순서인지를 정리하는 가장 좋은 방법은 **뒤집었을 때 무슨 일이 생기는지를 보는 것** 이다.

**표 43-7. 순서를 어겼을 때 생기는 일**

| 어긴 순서 | 결과 | 이 책의 사례 |
|---|---|---|
| 출처 확인 없이 처리 시작 | 아무나 보낸 데이터가 나머지 모든 단계의 비용을 소모시킨다. 비대칭이 공격자 쪽으로 완전히 기운다 | **26.8** (출처를 묻지 않은 클라이언트 데이터) |
| 크기 확인 전에 파싱 | 작은 입력이 파서 안에서 거대하게 팽창해 메모리와 CPU를 고갈시킨다 | **28.6** (Billion Laughs), **40.6** (GraphQL 중첩 질의 폭발) |
| 크기 확인 전에 정규식 적용 | 정규식 엔진이 거대한 문자열을 통째로 올려 처리한다. 형식이 틀렸다는 결론은 자원을 다 쓴 뒤에야 나온다 | 이 절 43.4.3 |
| 어휘 확인 전에 파싱 | 파서를 폭발시키도록 만들어진 토큰이 파서에 도달한다. 파서 설정에만 의존하게 된다 | **28.6** (외부 엔티티) |
| 인코딩을 정하지 않고 어휘 확인 | 검사하는 쪽과 사용하는 쪽이 같은 바이트열을 다른 문자로 읽는다. 필터가 통째로 무력해진다 | **7.7** (다중 인코딩), **27.5**, **32.8** (필터 우회) |
| 구문 확인 전에 의미 확인 | 형식조차 모르는 값으로 데이터베이스를 조회한다. 가장 비싼 자원이 가장 검증이 덜 된 값에 노출된다 | **27장** (인젝션이 도달하는 자리) |
| 의미 확인을 아예 하지 않음 | 문법적으로 완벽한 요청이 업무 규칙을 위반한다. 스캐너도 WAF도 잡지 못한다 | **29장 전체**, **24장** (접근 제어) |

표의 마지막 두 행이 중요한 대칭을 이룬다. **앞 단계를 건너뛰면 가용성이 무너지고, 뒤 단계를 건너뛰면 무결성이 무너진다.** 43.1절이 온라인 서점 사건에서 본 두 범주가 여기서 다시 나타난다.

그리고 이 표에는 이 장의 논지가 하나 더 숨어 있다. **각 단계는 다음 단계를 지키기 위해 존재한다.** 출처 검사는 크기 검사를 지키고, 크기 검사는 어휘 검사를 지키고, 어휘 검사는 파서를 지키고, 파서는 데이터베이스를 지킨다. 단계를 하나 빼면 그 뒤의 모든 단계가 벌거벗는다. 이것이 심층 방어의 정확한 정의다. **여러 개의 방어를 늘어놓는 것이 아니라, 각 방어가 다음 방어의 전제를 보장하도록 배열하는 것이다.**

### 43.4.8 검증되었다는 사실을 코드에 남기기

이 절의 마지막 요점이 다음 장으로 가는 다리다.

설계를 안전하게 만들려면 **데이터가 검증되었는지, 그리고 어느 정도까지 검증되었는지를 코드가 반영하게 하는 것** 이 강력하다. 앞에서 본 `ISBN` 클래스가 그 예다. 작고 도메인에 밀착한 구성 요소이며, **그 안에 든 값이 유효한 ISBN 형식임을 우리가 안다.** 그 번호를 다시 검증할 이유가 없다.

이것이 왜 중요한지는 반대 상황을 생각하면 명확하다. `String isbn`이 함수 사이를 돌아다닐 때, 그 문자열이 검증을 거쳤는지 아닌지를 아는 방법은 **호출 경로를 전부 추적하는 것** 뿐이다. 시스템이 조금만 커져도 불가능하다. 그래서 각 함수는 스스로 다시 검사하거나, 아니면 누군가 했겠거니 하고 넘어간다. 첫 번째가 43.7절의 방어적 코드 구조이고, 두 번째가 이 책이 지금까지 다룬 취약점의 절반이다.

`ISBN` 타입은 이 딜레마를 해소한다. **타입이 곧 검증 이력의 증거** 다. 그런 구성 요소를 만드는 방법 — 이 책이 **도메인 프리미티브(domain primitive)** 라고 부르는 것 — 이 44장의 주제다.

> **이 책의 범위를 넘어서**
>
> 이 절은 검증을 **어떤 순서로 무엇을 검사할 것인가**의 문제로 다뤘고, 도구는 정규식과 직접 작성한 검사로 한정했다. 실무에서는 선언적 검증 라이브러리, 스키마 언어(JSON Schema, XML Schema 등), 데이터 흐름을 추적하는 정적 분석 도구, 그리고 검증된 값과 그렇지 않은 값을 타입 수준에서 구분하는 정교한 타입 시스템 기능이 이 작업의 상당 부분을 자동화한다. 이들은 각각 그 자체로 큰 주제이고, 언어와 생태계에 따라 선택지가 크게 다르며, 이 책이 근거로 삼는 다섯 권의 범위 밖이다. 다만 어떤 도구를 쓰든 이 절의 판단 기준은 그대로 적용된다. **그 도구가 다섯 단계 중 어느 것을 하고 있는가, 그리고 그것을 어떤 순서로 하는가.** 스키마 검증기가 파싱 이후에만 동작한다면 그것은 3단계와 4단계를 수행하는 것이지 2단계를 대신하는 것이 아니다.

> **이 절이 뒷받침하는 것**
>
> - 출처 검증은 검증 순서의 1단계이며, 클라이언트 데이터 처리 원칙이 그 구체적 실행이다 → **26.8**이 이 단계를 다뤘다
> - 크기 검사가 파싱보다 먼저 와야 하는 이유 → **28.6** (Billion Laughs), **40.6** (GraphQL DoS 방어), **45.7** (가용성 테스트)
> - 어휘 검사는 인코딩을 명시해야만 검사다 → **7.6**, **7.7** (인코딩과 정규화), **27.5**, **32.8** (필터 우회)
> - 의미 단계의 실패가 곧 로직 결함이고, 그래서 스캐너가 찾지 못한다 → **29.1**, **29.3**~**29.5**
> - 검증되었다는 사실을 타입으로 남기기 → **44.1** (도메인 프리미티브와 불변식)

## 43.5 경계 검증(boundary validation)과의 대응

43.4절은 **무엇을 어떤 순서로** 검증할지를 정리했다. 그러나 이 절의 서두에서 던진 두 질문 중 첫 번째가 아직 남아 있다. **입력이 모든 곳에서 검증되도록 코드를 어떻게 구조화할 것인가.** 다시 말해 **어디서** 검증할 것인가.

이 질문에 대한 가장 정교한 답을 내놓은 것이 WAHH 2장의 **경계 검증(boundary validation)** 이다. 이 절은 두 틀을 나란히 놓는다.

### 43.5.1 순진한 그림과 그것이 틀린 이유

신뢰 경계를 넘는 데이터를 검증한다는 발상 자체는 익숙하다. 웹 애플리케이션의 핵심 보안 문제는 사용자로부터 받은 데이터를 신뢰할 수 없다는 것이다(→ 6.7). 클라이언트 측에서 수행하는 입력 검증은 성능과 사용자 경험을 개선할 수는 있어도 **실제로 서버에 도달하는 데이터에 대해서는 아무것도 보장하지 않는다**(→ 26장 전체). 사용자 데이터가 서버 측 애플리케이션에 처음 도달하는 지점, 그것이 거대한 신뢰 경계다.

여기서 자연스럽게 떠오르는 그림이 있다. 인터넷은 "나쁘고" 신뢰할 수 없으며, 서버 측 애플리케이션은 "좋고" 신뢰할 수 있다. 그 사이에 국경이 있다. 입력 검증의 역할은 도착한 데이터를 깨끗하게 씻어서 신뢰할 수 있는 애플리케이션에 넘기는 것이다. **그 지점을 지나면 데이터는 신뢰할 수 있고, 더 이상의 검사나 공격 걱정 없이 처리해도 된다.**

```
        신뢰할 수 없음        │        신뢰할 수 있음
                              │
   인터넷 ──── 요청 ────▶  [ 입력 검증 ]  ────▶  애플리케이션 전체
                              │
                          "국경 하나"
```

*그림 43-1. 입력 검증에 대한 순진한 그림 (WAHH 2장 기준)*

이 그림은 **부적절하다.** WAHH가 드는 이유는 셋이다.

**첫째, 방어해야 할 공격의 종류가 너무 많다.** 애플리케이션이 구현하는 기능의 범위와 사용하는 기술이 다양하기 때문에, 전형적인 애플리케이션은 수많은 종류의 입력 기반 공격에 대비해야 하고, 각 공격은 서로 다른 방식으로 조작된 데이터를 쓴다. **이 모든 공격을 외부 경계 한 곳의 단일 메커니즘으로 막는 것은 매우 어렵다.**

**둘째, 데이터가 처리를 거치며 변형된다.** 많은 애플리케이션 기능은 여러 종류의 처리를 사슬처럼 이어 붙인다. 사용자가 보낸 입력 하나가 여러 컴포넌트에서 여러 연산을 거치고, 각 연산의 출력이 다음 연산의 입력이 된다. 데이터가 변형되면서 **원래 입력과 아무 닮은 데도 없는 것이 될 수 있다.** 숙련된 공격자는 처리 과정의 특정 단계에서 악성 입력이 **생성되도록** 애플리케이션을 조작해, 그 데이터를 받는 컴포넌트를 공격할 수 있다. 외부 경계에서 각 입력의 모든 가능한 처리 결과를 예견하는 검증 메커니즘을 만드는 것은 극도로 어렵다.

**셋째, 방어끼리 서로 충돌한다.** 서로 다른 범주의 입력 기반 공격을 막으려면 **양립할 수 없는 검증**이 필요할 수 있다. XSS를 막으려면 `>`를 `&gt;`로 HTML 인코딩해야 하고, 명령 인젝션을 막으려면 `&` 같은 문자가 든 입력을 차단해야 한다. 모든 범주의 공격을 애플리케이션의 외부 경계 한 곳에서 동시에 막으려는 시도는 때때로 불가능하다.

세 번째 이유는 특히 중요하다. 이 책의 32.8절이 XSS 방어를 다룰 때 반복해 강조한 것이 **인코딩은 목적지가 정해져야 결정된다**는 것이었다. HTML 본문에 들어갈 값과 자바스크립트 문자열 리터럴에 들어갈 값과 URL 파라미터에 들어갈 값은 같은 원본에 대해 서로 다른 인코딩을 요구한다. **목적지를 모르는 자리에서 인코딩을 결정하는 것은 원리적으로 불가능하다.** 외부 경계는 목적지를 모르는 자리다.

### 43.5.2 경계 검증

더 효과적인 모델이 **경계 검증** 이다. 여기서는 서버 측 애플리케이션의 **개별 컴포넌트 또는 기능 단위 각각이 자신의 입력을 잠재적으로 악의적인 출처에서 온 것으로 취급한다.** 데이터 검증은 클라이언트와 서버 사이의 외부 국경뿐 아니라 **이 모든 신뢰 경계에서** 수행된다.

이 모델은 앞의 세 문제를 모두 해결한다. **각 컴포넌트는 자신이 취약한 특정 종류의 조작된 입력에 대해 스스로를 방어할 수 있다.** 데이터가 여러 컴포넌트를 통과하는 동안, 검증은 **앞선 변형의 결과로 데이터가 갖게 된 실제 값**에 대해 수행된다. 그리고 각 검증이 처리의 서로 다른 단계에서 이뤄지므로 **서로 충돌할 일이 없다.**

온라인 서점의 로그인 기능으로 보자. 사용자가 보낸 입력 하나가 여러 단계의 처리를 거치고, 각 단계마다 적절한 검증이 붙는다.

```
                   ┌──────────────────────────────────────────────────┐
   사용자 ──▶ (1) │ 폼 핸들러                                        │
                   │  허용된 문자만, 길이 상한, 알려진 공격 시그니처  │
                   └────────────────────┬─────────────────────────────┘
                                        │
                   ┌────────────────────▼─────────────────────────────┐
              (2)  │ 인증 — 자격 증명 확인 SQL 질의                   │
                   │  DB 공격에 쓰일 수 있는 문자를 이스케이프        │
                   └────────────────────┬─────────────────────────────┘
                                        │
                   ┌────────────────────▼─────────────────────────────┐
              (3)  │ 프로필 조회 — 계정 정보 서비스 호출              │
                   │  XML 메타문자를 적절히 인코딩                    │
                   └────────────────────┬─────────────────────────────┘
                                        │
                   ┌────────────────────▼─────────────────────────────┐
              (4)  │ 응답 생성 — 계정 정보를 브라우저에 표시          │
                   │  페이지에 삽입되는 사용자 데이터를 HTML 인코딩   │
                   └──────────────────────────────────────────────────┘
```

*그림 43-2. 여러 처리 단계에서 경계 검증을 수행하는 로그인 기능 (WAHH 그림 2-5 기준)*

네 단계 각각의 검증은 **서로 다른 것을 검사한다.** (1)은 문자 집합과 길이를, (2)는 SQL 문법에서 위험한 문자를, (3)은 XML 메타문자를, (4)는 HTML 메타문자를 본다. 이 넷을 (1)에 몰아넣으려 하면 서로 충돌한다. 각자의 자리에 두면 충돌하지 않는다.

여기서 이 책의 다른 장들과의 연결이 명확해진다. 27.9절이 다룬 파라미터화 질의는 (2)에 놓이는 방어이고, 32.8절이 다룬 출력 인코딩은 (4)에 놓이는 방어이며, 28장이 다룬 백엔드 컴포넌트 방어는 (3)에 놓이는 방어다. **이 책이 각 공격 장의 끝에 배치한 강화 절들은, 전부 경계 검증 모델의 서로 다른 위치를 채우고 있었다.**

### 43.5.3 두 틀은 무엇을 답하는가

이제 두 틀을 나란히 놓는다.

**표 43-8. 경계 검증과 검증 순서**

| 축 | WAHH — 경계 검증 | SBD — 검증 순서 |
|---|---|---|
| 답하는 질문 | **어디서** 검증하는가 | **무엇을 어떤 순서로** 검증하는가 |
| 기본 단위 | 컴포넌트, 기능 단위 | 검증 단계 |
| 핵심 통찰 | 신뢰 경계는 하나가 아니라 여러 개다 | 값싼 검사가 비싼 검사를 지킨다 |
| 실패의 모습 | 방어를 외부 국경 한 곳에 몰아 넣음 → 충돌하거나 변형된 데이터를 놓침 | 순서를 어김 → 파서·정규식 엔진·DB가 벌거벗음 |
| 데이터의 상태 표현 | 각 경계에서 "이 컴포넌트에 대해 안전한가"를 그때그때 판단 | 통과한 값을 **타입** 으로 만들어 이후 재검증 불필요 |
| 주로 겨냥하는 것 | 무결성 (인젝션, XSS, 우회) | 무결성 + **가용성** (DoS, 자원 고갈) |
| 이 책의 대응 | 27.9, 28장, 32.8의 강화 절들 | 43.4, 44장 |

**두 틀은 충돌하지 않는다.** 서로 다른 질문에 답하기 때문이다. 실제로 둘은 정확히 맞물린다.

경계 검증은 **검증이 일어나야 할 위치들의 목록**을 준다. 그러나 각 위치에서 무엇을 어떻게 검사할지는 말해 주지 않는다. 검증 순서는 **각 위치에서 수행할 절차**를 준다. 그러나 그 절차를 어디에 배치할지는 말해 주지 않는다.

```
                   ┌─── 신뢰 경계 ────┐    ┌─── 신뢰 경계 ────┐
                   │                  │    │                  │
   요청 ─────────▶ │  출처            │ ─▶ │  출처            │ ─▶ ...
                   │  크기            │    │  크기            │
                   │  어휘            │    │  어휘            │
                   │  구문            │    │  구문            │
                   │  의미            │    │  의미            │
                   │      ↓           │    │      ↓           │
                   │  타입이 된 값    │    │  타입이 된 값    │
                   └──────────────────┘    └──────────────────┘
                    WAHH가 위치를 정하고,  SBD가 그 안의 절차를 정한다
```

*그림 43-3. 두 틀의 결합*

**그리고 두 틀이 결합할 때 각자의 약점이 서로 보완된다.**

경계 검증의 약점은 **반복** 이다. 각 컴포넌트가 자기 입력을 다시 검사한다는 원칙을 문자 그대로 적용하면, 같은 값이 시스템을 통과하는 동안 같은 검사가 수십 번 반복된다. 그것이 43.7절이 다룰 "자기 자신을 신뢰하지 않는 코드"다. 검증 순서의 마지막 산물 — **통과한 값을 타입으로 만드는 것** — 이 이 반복을 끊는다. `ISBN` 타입을 받는 컴포넌트는 형식을 다시 검사할 필요가 없다. **타입 자체가 그 검사가 이미 끝났다는 증거이기 때문이다.**

검증 순서의 약점은 **배치** 다. 다섯 단계를 어디에서 수행할지에 대해 그 목록 자체는 말하지 않는다. 애플리케이션의 입구 한 곳에서만 하면 그림 43-1의 순진한 그림으로 되돌아간다. 경계 검증이 이 공백을 채운다. **경계마다 다섯 단계를 수행한다.**

### 43.5.4 검증됨은 값과 컨텍스트의 쌍이 갖는 속성이다

한 가지 오해를 미리 막아야 한다. "타입으로 만들면 다시 검사할 필요가 없다"는 말은 **모든 검사가 끝났다**는 뜻이 아니다.

42.6절이 바운디드 컨텍스트를 다루며 도달한 결론을 다시 꺼내자. **같은 이름이 컨텍스트마다 다른 것을 뜻한다.** 배송 컨텍스트의 "주문"과 재무 컨텍스트의 "주문"은 다른 개념이고, 다른 불변식을 갖는다. 그렇다면 "이 값은 검증되었다"는 진술도 **어느 컨텍스트에 대해** 검증되었는지를 함께 말해야 성립한다.

그래서 정확한 정식화는 이렇다. **검증됨은 값 하나가 갖는 속성이 아니라, 값과 컨텍스트의 쌍이 갖는 속성이다.**

`ISBN` 타입이 보장하는 것은 "이 문자열이 ISBN-10 형식이고 검사 숫자가 맞는다"는 것뿐이다. 그것은 형식에 관한 진술이고, 어느 컨텍스트에서나 참이다. 그러나 **"이 ISBN에 해당하는 책이 우리 카탈로그에 있다"** 는 것은 다른 진술이며, `ISBN` 타입이 보장하지 않는다. 그것은 5단계, 의미 검사의 영역이고, 카탈로그 컨텍스트 안에서만 의미가 있다.

경계 검증이 여러 경계를 요구하는 이유가 여기 있다. **경계를 넘을 때마다 컨텍스트가 바뀌고, 컨텍스트가 바뀌면 1~4단계의 결과는 대체로 유지되지만 5단계의 결과는 다시 확인해야 한다.** 42.6절이 "의미론 경계를 넘는 데이터는 보안 관점에서 특별한 관심 대상"이라고 한 것의 정확한 의미가 이것이다. 24.7절이 "인가는 경계 검증의 한 형태다"라고 한 것도 같은 구조다. 인가란 **이 주체가 이 자원에 대해 이 연산을 할 수 있는가**를 묻는 5단계 검사이고, 서비스 경계를 넘을 때마다 다시 물어야 한다.

### 43.5.5 이 책의 결론

두 틀을 합쳐 이 책이 채택하는 원칙은 한 문장이다.

> **경계에서, 정해진 순서로 검증하고, 통과한 값을 타입으로 만든다.**

세 부분 각각이 하나씩의 문제를 해결한다.

**표 43-9. 세 부분이 각각 막는 것**

| 원칙의 부분 | 없으면 생기는 문제 | 이 책의 사례 |
|---|---|---|

## 43.6 입력 처리 방식의 비교 — 거부, 정제, 안전한 처리, 의미론적 검사

43.4절과 43.5절이 **언제, 어디서, 어떤 순서로** 검증할지를 정리했다면, 이 절은 남은 질문에 답한다. **각 자리에서 실제로 무엇을 할 것인가.** 통과시키는가, 거부하는가, 고쳐서 통과시키는가, 아니면 애초에 위험하지 않게 처리하는가.

사용자 입력을 다루는 접근법은 대체로 다섯 가지로 분류된다. 상황과 입력의 종류에 따라 적합한 것이 다르고, 조합해서 쓰는 것이 바람직한 경우도 많다.

### 43.6.1 다섯 가지 접근법

**알려진 나쁜 것 거부(reject known bad).** 공격에 쓰이는 것으로 알려진 문자열이나 패턴의 목록 — 블랙리스트 — 을 두고, 목록에 걸리는 데이터를 차단하고 나머지는 허용한다.

**일반적으로 가장 효과가 낮은 접근법으로 평가된다.** 이유는 둘이다. 첫째, 전형적인 웹 취약점 하나는 매우 다양한 입력으로 익스플로잇할 수 있고, 그 입력은 여러 방식으로 인코딩되거나 표현될 수 있다. 가장 단순한 경우를 제외하면 블랙리스트는 공격에 쓸 수 있는 입력 패턴 일부를 반드시 빠뜨린다. 둘째, 익스플로잇 기법은 계속 진화한다. 기존 취약점 범주에 대한 새로운 익스플로잇 방법이 현재의 블랙리스트에 걸릴 이유가 없다.

블랙리스트 기반 필터는 사소한 변형만으로 우회되는 경우가 흔하다.

```
select 가 차단되면          →  seLeCt
or 1=1 -- 이 차단되면       →  or 2=2--
alert('xss') 가 차단되면    →  prompt('xss')
```

토크나이징을 교란하는 비표준 문자를 끼워 넣는 방법도 있다.

```sql
SELECT/*foo*/username,password/*foo*/FROM/*foo*/users
```

```html
<img%09onerror=alert(1) src=a>
```

그리고 블랙리스트 기반 필터, 특히 웹 애플리케이션 방화벽에 구현된 것들은 **NULL 바이트 공격**에 취약한 경우가 많았다. 관리 실행 환경과 비관리 실행 환경에서 문자열을 다루는 방식이 다르기 때문에, 차단 대상 표현식 앞 어딘가에 NULL 바이트를 넣으면 일부 필터가 입력 처리를 그 지점에서 멈춰 표현식을 식별하지 못한다.

```
%00<script>alert(1)</script>
```

**27.5절과 32.8절이 이 우회 기법들을 상세히 다뤘다.** 12.11절은 같은 문제를 WAF의 구조적 한계라는 관점에서 다뤘다. 요점은 **블랙리스트가 무용하다는 것이 아니라, 블랙리스트가 방어의 마지막 층이 되어서는 안 된다**는 것이다.

**알려진 좋은 것 허용(accept known good).** 온당한 입력에만 매칭되는 것으로 알려진 문자열, 패턴, 또는 기준의 집합 — 화이트리스트 — 을 두고, 매칭되는 데이터만 허용하고 나머지를 차단한다. 예를 들어 요청된 상품 코드를 데이터베이스에서 조회하기 전에, 그것이 영숫자만 포함하고 정확히 여섯 자인지 검증한다. 상품 코드에 뒤이어 수행될 처리를 아는 개발자는 **이 검사를 통과한 입력이 어떤 문제도 일으킬 수 없다는 것을 안다.**

이 접근이 가능한 경우에는 잠재적 악성 입력을 다루는 **가장 효과적인 방법**으로 평가된다. 화이트리스트를 신중하게 구성했다면 공격자는 조작된 입력으로 애플리케이션의 동작에 개입할 수 없다.

그러나 만능은 아니다. **어떤 합리적인 "좋음"의 기준도 만족하지 못하는 데이터를 받아들여야 하는 경우가 무수히 많다.** 어떤 사람의 이름에는 아포스트로피나 하이픈이 들어간다. 이 문자들은 데이터베이스 공격에 쓰일 수 있지만, 애플리케이션이 누구든 자신의 실명으로 가입할 수 있게 해야 한다는 것이 요구사항일 수 있다. 화이트리스트는 대단히 효과적이지만 사용자 입력 처리 문제의 범용 해법은 아니다.

**정제(sanitization).** 안전하다고 보장할 수 없는 데이터를 받아들여야 할 때가 있다는 것을 인정하는 접근이다. 그런 입력을 거부하는 대신, 부작용을 일으키지 못하도록 여러 방식으로 정제한다. 잠재적으로 위험한 문자를 제거해 안전한 것만 남기거나, 이후 처리 전에 적절히 인코딩하거나 이스케이프한다.

정제 기반 접근은 매우 효과적인 경우가 많고, 여러 상황에서 악성 입력 문제의 일반 해법으로 신뢰할 수 있다. XSS에 대한 통상적 방어 — 위험한 문자를 HTML 인코딩한 뒤 페이지에 삽입하는 것(→ 32.8) — 이 대표적이다. 그러나 **여러 종류의 잠재적 악성 데이터를 하나의 입력 항목 안에서 동시에 수용해야 한다면 효과적인 정제가 어려워진다.** 이 상황이 바로 43.5절이 다룬 경계 검증이 필요한 이유다.

**안전한 데이터 처리(safe data handling).** 많은 웹 취약점은 사용자가 제공한 데이터가 **안전하지 않은 방식으로 처리되기 때문에** 생긴다. 입력 자체를 검증하는 것이 아니라 **그 입력에 수행되는 처리가 본질적으로 안전하도록 보장함으로써** 취약점을 피할 수 있는 경우가 많다.

가장 명확한 예가 SQL 인젝션이다. 데이터베이스 접근에 파라미터화 질의를 올바르게 사용하면 SQL 인젝션은 성립하지 않는다(→ 27.9). 사용자 입력을 운영체제 명령 해석기에 넘기는 것 같은 본질적으로 위험한 관행을 아예 피하도록 기능을 설계하는 것도 같은 접근이다(→ 28장).

이 접근은 웹 애플리케이션이 수행해야 하는 모든 종류의 작업에 적용할 수는 없다. 그러나 **적용 가능한 자리에서는 잠재적 악성 입력에 대한 효과적인 일반 해법** 이다.

**의미론적 검사(semantic checks).** 앞의 네 가지는 모두 **애플리케이션의 처리에 개입하도록 조작된 잘못된 형식의 데이터**로부터 방어하는 것을 겨냥한다. 그러나 어떤 취약점에서는 **공격자가 보내는 입력이 평범한 비악의적 사용자가 보내는 입력과 완전히 동일하다.** 그것을 악의적으로 만드는 것은 제출된 상황이 다르다는 사실뿐이다.

공격자가 숨은 폼 필드에 실려 전송되는 계좌번호를 바꿔 다른 사용자의 계좌에 접근하려 한다고 하자. **어떤 구문 검증도 정상 사용자의 데이터와 공격자의 데이터를 구별하지 못한다.** 무단 접근을 막으려면 애플리케이션이 **제출된 계좌번호가 그것을 제출한 사용자의 것인지**를 검증해야 한다.

43.4.6절이 다룬 5단계가 이것이다. 그리고 29장 전체와 24장 전체가 이 검사의 실패를 다뤘다.

### 43.6.2 다섯 접근법과 다섯 단계의 대응

이 다섯 접근법을 43.4절의 다섯 단계 위에 올려놓으면 각자의 자리가 드러난다.

**표 43-10. 입력 처리 방식 비교**

| 접근법 | 원리 | 주로 작동하는 단계 | 실패하는 방식 | 이 책의 사례 |
|---|---|---|---|---|
| **알려진 나쁜 것 거부** | 블랙리스트에 걸리면 차단 | 3 (어휘) | 인코딩 변형, 대소문자 변형, 주석 삽입, NULL 바이트로 우회. 새로운 기법은 원리상 못 막음 | **27.5**, **32.8**, **12.11** |
| **알려진 좋은 것 허용** | 화이트리스트에 맞으면 허용 | 2·3·4 (크기·어휘·구문) | 정당한 입력이 "좋음"의 기준에 안 맞는 경우(이름의 아포스트로피 등) | **43.4.3**~**43.4.5**의 `ISBN` |
| **정제** | 위험한 문자를 제거·인코딩 | 3 (어휘), 그리고 **출력 시점** | 목적지가 여럿이면 인코딩이 충돌. 목적지를 모르는 자리에서는 결정 불가 | **32.8** (문맥별 인코딩), **30.8** (검증 전 복구 금지) |
| **안전한 데이터 처리** | 처리 자체를 안전하게 설계 | 단계 밖 — **처리 방식의 문제** | 적용 가능한 작업의 범위가 제한적 | **27.9** (파라미터화 질의), **28장** |
| **의미론적 검사** | 값이 이 맥락에서 말이 되는가 | 5 (의미) | 하지 않으면 아무것도 대신해 주지 않음 | **24장**, **29장** |

이 표에서 읽어야 할 것이 셋이다.

**첫째, 앞의 세 접근법(거부·허용·정제)은 전부 3단계 근처에 몰려 있다.** 문자와 패턴을 다루는 도구들이다. 이것이 "입력 검증"이라는 말을 들었을 때 대부분의 개발자가 떠올리는 것이고, 동시에 **검증의 전부라고 오해되는 것** 이다.

**둘째, 안전한 데이터 처리는 검증이 아니다.** 표에서 유일하게 "단계 밖"이라고 표시한 이유다. 파라미터화 질의는 입력을 검사하지 않는다. 입력이 무엇이든 그것이 코드로 해석될 수 없는 구조를 만든다. **검증을 잘하는 것과 검증이 필요 없게 만드는 것은 다른 일이며, 후자가 언제나 낫다.** 27.9절이 파라미터화 질의를 SQL 인젝션 방어의 1순위로 놓은 이유, 32.8절이 "위험한 삽입 지점 자체를 제거하라"를 방어 목록에 넣은 이유가 같다.

**셋째, 의미론적 검사에는 대체재가 없다.** 다른 네 가지는 서로를 어느 정도 보완한다. 화이트리스트가 강하면 블랙리스트가 덜 필요하고, 안전한 처리가 가능하면 정제가 덜 필요하다. 그러나 5단계를 대신할 수 있는 것은 아무것도 없다. **공격자의 입력이 정상 입력과 문자 단위로 같을 때, 문자를 보는 어떤 도구도 그것을 구별하지 못한다.**

### 43.6.3 그래서 무엇을 쓸 것인가

일반화하면 이렇게 정리된다.

- **가능하면 안전한 데이터 처리를 쓴다.** 검증을 불필요하게 만드는 설계가 검증을 잘하는 설계보다 낫다.
- **그것이 불가능한 자리에서는 알려진 좋은 것 허용을 쓴다.** 도메인이 값의 형태를 알고 있다면 화이트리스트는 정확하고 강력하다. `ISBN` 클래스의 검사 전부가 화이트리스트다.
- **화이트리스트가 불가능한 자리에서는 목적지에 맞춰 정제한다.** 목적지가 정해지는 자리 — 즉 출력 지점 — 에서 한다. 입구에서 하지 않는다.
- **블랙리스트는 층 하나로만 쓴다.** 알려진 공격 시그니처를 로깅하고 탐지하는 용도로는 값이 있다. 그것이 유일한 방어인 상태를 만들지 않는다.
- **의미론적 검사는 도메인 모델에 둔다.** 그것은 필터가 아니라 규칙이며, 규칙은 모델에 산다.

마지막 항목이 이 장의 세 축을 다시 묶는다. **의미론적 검사를 도메인 모델에 두려면, 도메인 모델의 객체들이 잘못된 상태를 표현할 수 없어야 한다.** 그것이 43.1절의 불변성과 43.2~43.3절의 계약이 하는 일이다.

## 43.7 방어적 코드 구조가 실패하는 이유 — 자기 자신을 신뢰하지 않는 코드

시스템을 안정적이고 견고하게 만드는 것은 훌륭한 목표다. 잘 설계된 시스템은 `NullPointerException`으로 죽지 않아야 한다.

그런데 실무에서 흔히 보는 것은 `!= null` 검사로 뒤덮인 코드다. `null` 값이 나올 이유가 전혀 없는 깊숙한 자리에서도 그렇다. **`null`에 대한, 형식에 대한, 경계 조건에 대한 반복된 검사는 그 자체로 좋은 설계가 아니다.** 그것은 오히려 **코드의 한 조각이 나머지 코드의 설계를 감히 신뢰하지 못한다**는 표현이다. 그래서 혹시 몰라 다시 검사한다. 각 부분이 서로에게 무엇을 기대할 수 있는지에 대한 명확한 계약 대신, 목적이 불분명한 방어적 코드 구조가 코드를 채운다.

문제는 두 겹이다.

**첫째, 코드가 복잡해지고 읽기 어려워지고 불필요한 반복으로 부풀어 오른다.** 리팩터링도 어려워진다. 이것만으로도 나쁘지만, 여기서 두 번째 문제가 나온다.

**둘째, 이런 코드가 오랜 시간 유지보수되면 검사들이 서로 어긋나기 시작한다.** 그리고 **일관되지 않은 검사가 흩어져 있는 코드는 공격자에게 창의적으로 악용할 기회다.**

두 번째 문제가 이 절의 핵심이다. 구체적인 코드로 보자.

### 43.7.1 자기 자신을 신뢰하지 않는 코드

온라인 서점의 코드다. `ShoppingService`가 공개 메서드 `addToOrder`로 `Order`에 책을 추가한다. 이 공개 메서드는 `putInCartAsNew`, `isAlreadyInCart` 같은 여러 비공개 헬퍼 메서드를 갖고 있다.

**리스팅 43-21. `null`과 형식 검사가 반복되는 코드**

```java
class ShoppingService {

    public void addToOrder(String orderId, String isbn, int qty) {
        Order order = orderservice.find(orderId);
        if (isbn.matches("[0-9]{9}[0-9X]")) {     // 공개 메서드를 부르기 전에
            order.addBook(isbn, qty);             // 형식을 검사한다
        }
    }
}

class Order {
    private Set<OrderLine> items;

    public void addBook(String isbn, int qty) {
        if (isbn != null && !isbn.isEmpty()       // 공개 메서드 입구에서
              && !isAlreadyInCart(isbn)) {        // isbn을 검사한다
            putInCartAsNew(isbn, qty);
        } else {
            addToLine(isbn, qty);
        }
    }

    private void putInCartAsNew(String isbn, int quantity) {
        if (isbn != null && isbn.matches("[0-9]{9}[0-9X]")) {
            items.add(new OrderLine(isbn, quantity));
        }
    }

    private void addToLine(String isbn, int quantity) { ... }

    private boolean isAlreadyInCart(String isbn) {
        boolean result = false;
        for (OrderLine item : items) {
            String itemISBN = item.isbn();
            if (itemISBN != null                  // OrderItem에서 나온 값이
                                                  // 어떻게 null일 수 있는가?
                  && isbn != null
                  && isbn.matches("[0-9]{9}[0-9X]")) {  // 루프 깊은 곳에서
                if (itemISBN.equals(isbn)) {            // 또 형식을 검사한다
                    result = true;
                }
            }
        }
        return result;
    }
    // 다른 메서드들
}
```

`null`과 형식 검사가 도처에 있다. 비공개 메서드 깊숙한 곳에도 있다. 특히 `isAlreadyInCart` 안의 검사들을 보라. 그리고 이 코드의 아이러니를 보라. **`ShoppingService`는 `isbn`의 형식을 검사한 뒤에 `order.addBook(isbn, qty)`로 넘긴다. 형식 검사를 했음에도, `Order` 안의 코드는 그 검사를 신뢰하지 않는다.**

정규식을 적용하기 전에 `isbn`이 `null`이 아님을 확인하는 것은 언뜻 현명해 보인다. `NullPointerException`이 아무 데서나 튀어나오길 원하지는 않으니까. 문제는 이런 검사들이 **코드를 크게 안전하게도 견고하게도 만들지 못하면서, 이해하기는 훨씬 어렵게 만든다**는 것이다.

**이 코드는 자기 자신을 불신한다. 어떤 규칙이 유효한지를 모른다.** `null`인 `isbn`을 보내도 되는가. 된다면 어떻게 처리해야 하는가. 안 된다면 누가 그것을 먼저 막았는가.

공개 메서드 `addBook`이 입력을 철저히 검사하는 것은 타당하다. 그 메서드는 `null`도 빈 문자열도 들어오지 못하게 확실히 막는다. 그런데 **형식은 검사하지 않는다.**

```java
isbn.matches("[0-9]{9}[0-9X]")
```

이 검사는 다른 곳에서 이뤄진다. 그리고 다음 두 메서드는 `addBook`의 `null` 검사를 명백히 신뢰하지 않고, 루프 깊은 곳에서까지 그것을 반복한다.

```java
private void putInCartAsNew(String isbn, int quantity)
private boolean isAlreadyInCart(String isbn)
```

그런데 같은 두 메서드가 `!isbn.isEmpty()` 검사는 반복하지 **않는다.** **각 부분이 다른 부분으로부터 어떤 약속을 기대할 수 있는지가 근본적으로 불분명하다.**

축약된 예제이지만 드문 일이 아니다. 수백 줄짜리 메서드 한가운데에서 `if (value != null)`을 만나는 일은 흔하다. 그 여분의 `null` 검사를 넣은 프로그래머를 변호하자면, 그의 의도는 프로그램이 죽지 않게 하는 것이었을 것이다. 많은 경우 그 검사는 **실제로 그 지점에서 프로그램이 `NullPointerException`으로 죽은 적이 있어서** 들어갔다. 그러나 그때 한 일은 **`null`이 나타나지 않도록 설계를 명확히 하는 것**이 아니라 **그 자리에 `if` 하나를 반창고처럼 붙인 것**이었다.

### 43.7.2 대처 전략의 부재

이 코드에는 또 하나의 문제가 있다. **대처 전략(coping strategy)** 이다.

`isAlreadyInCart`가 형식에 맞지 않는 `item.isbn()`을 만나면 어떻게 반응하는가. **아무것도 하지 않는다.** 실행을 멈추지도, 예외를 던지지도, 로그로 보고하지도 않는다. 그냥 그 항목을 건너뛴다.

결과가 무엇인지는 명백하다. **장기적으로 아무것도 고쳐지지 않고, 데이터에는 잘못된 값이 계속 쌓인다.** 그리고 그 잘못된 값을 만난 코드는 매번 조용히 무시한다. 문제가 있다는 신호가 시스템 어디에도 남지 않는다.

이것을 43.2절의 빠른 실패 원칙과 대조하라. 빠른 실패는 **잘못된 상황을 즉시 드러낸다.** 조용한 무시는 **잘못된 상황을 영원히 감춘다.** 그리고 감춰진 상태는 언젠가 다른 코드가 그것을 다르게 해석하는 날 취약점이 된다. 27.5절의 2차 SQL 인젝션이 정확히 그 구조였다.

여기에 더해, 이렇게 흩뿌려진 검사들은 코드를 부풀릴 뿐 아니라 **코드가 자기 기능을 더 간결하게 표현하도록 만드는 리팩터링을 가로막는다.**

### 43.7.3 현대적 변종 — `Optional`의 과도한 사용

같은 설계 결함에는 현대적 변종이 있다. 자바의 `Optional<T>` 같은 선택적 자료형을 쓸 때 나타난다.

`null` 값이 코드에 굴러다니게 두는 대신, 그 값들을 `Optional.EMPTY`로 바꾼다. 주소가 가끔 없다면 주문의 주소 필드를 `Optional<Address>`로 쓴다. **결국에는 주문에 반드시 주소가 있어야 하는데도** 그렇게 한다. 그리고 데이터를 쓸 때가 되면 `Optional.map`을 거치는 우회로에서 결함이 드러난다.

**리스팅 43-22. `Optional.EMPTY`를 고려하느라 뒤틀린 코드**

```java
Address anAddr;
Optional<Address> perhapsAddr;

Zip anZip = anAddr.zip();
Optional<Zip> perhapsZip = perhapsAddr.map(Address::zip);
```

`anAddr`와 `perhapsAddr`를 다루는 코드를 비교하라. `perhapsAddr` 쪽이 훨씬 뒤틀려 있다. `zip` 메서드로 우편번호를 그냥 묻는 대신 `map`이라는 우회로를 탄다. 주소 하나에서 우편번호 하나를 꺼내면서, 주소가 없을 수 있다는 가능성을 고려하느라 거치는 번거로운 우회다.

**주소가 필수인데 `Optional<Address>`가 쓰이고 있다면 경계해야 한다.** 그 `Optional`은 도메인에 대한 통찰을 담고 있지 않다. **코드가 나머지 설계를 신뢰하지 못한다는 사실을 덮는 포장** 일 뿐이다.

구식이든(반복된 `null`·형식 검사) 신식이든(`Optional`의 남용), 방어적 코드 구조는 **무언가 잘못되어 있다는 명확한 신호** 다.

### 43.7.4 방어를 흩어 두면 어디서도 확실하지 않다

이 절의 진단을 이 책 전체의 관점에서 다시 말할 수 있다.

**표 43-11. 방어적 코드 구조의 흔적과 그것이 감추는 것**

| 코드에서 보이는 것 | 감추고 있는 것 |
|---|---|
| 비공개 메서드 안의 `null` 검사 | 공개 메서드가 어디까지 보장하는지가 정해져 있지 않다 |
| 같은 형식 검사가 여러 곳에 | 그 형식이 개념으로 존재하지 않는다. 타입이 없다 |
| 어떤 곳은 검사하고 어떤 곳은 안 함 | 아무도 계약을 쓰지 않았다 |
| 검사에 걸렸을 때 아무 일도 하지 않음 | 대처 전략이 없다. 실패가 신호로 남지 않는다 |
| 필수 필드에 붙은 `Optional` | 도메인 규칙이 코드에 반영되지 않았다 |

그리고 이 표의 각 행이 **이 책이 앞에서 본 실패 패턴의 코드 수준 형태** 다.

12.11절이 WAF의 한계를 다루며 도달한 결론을 다시 보자. WAF는 애플리케이션 앞에 놓인 하나의 방어층이다. 그러나 WAF가 보는 바이트열과 애플리케이션이 최종적으로 해석하는 값은 같지 않다. 인코딩, 정규화, 프레임워크의 파라미터 파싱을 거치며 값은 변형된다. **방어가 그 변형을 알지 못하는 자리에 놓여 있으면, 그 방어는 자기가 무엇을 막고 있는지 모른다.**

26.7절이 클라이언트 데이터 처리를 다루며 도달한 결론도 같은 형태다. 클라이언트에서 온 값을 어디서 검증할 것인가. 여러 곳에서 조금씩 검증하면 각 지점은 자기가 무엇을 보장하는지 모르고, 다음 지점은 앞 지점이 무엇을 했는지 모른다.

**공통 구조는 이것이다. 방어를 여러 곳에 흩어 두면 어디서도 확실하지 않다.**

여기서 43.5절이 남긴 긴장이 다시 나타난다. 경계 검증은 **여러 경계에서** 검증하라고 말한다. 그렇다면 경계 검증은 방어를 흩어 두는 것 아닌가.

아니다. 차이는 **각 검증이 무엇을 보장하는지가 명시되어 있는가**에 있다.

**표 43-12. 흩어진 방어와 경계 검증**

| | 흩어진 방어적 검사 | 경계 검증 |
|---|---|---|
| 검사의 위치 | 아무 데나. 사고가 났던 자리 | 신뢰 경계. 컴포넌트의 입구 |
| 무엇을 검사하는지 | 불명확. 그때그때 다름 | 그 컴포넌트가 취약한 것 |
| 통과 후 보장 | 없음. 다음 코드가 다시 검사 | 명시됨. 다음 코드가 신뢰 |
| 검사 사이의 관계 | 없음. 서로 모름 | 각 경계가 자기 층을 책임짐 |
| 실패 시 | 대개 조용히 무시 | 빠른 실패 |

**경계 검증은 검증을 흩는 것이 아니라 검증에 좌표를 부여하는 것이다.** 좌표가 없는 검증이 방어적 코드 구조이고, 좌표가 있는 검증이 경계 검증이다. 그리고 좌표를 코드에 적는 방법이 다음 절의 주제다.

## 43.8 계약과 도메인 프리미티브가 구원하는 지점

`null` 데이터로부터 코드를 보호하기 위해 `null` 검사를 온 사방에 덧바르는 대신, **데이터가 `null`이 아님을 보장해야 한다.** 마찬가지로 형식 검사가 반복되는 것을 피하려면, **그 검사가 이미 수행되었다는 사실을 캡슐화해야 한다.** 이를 위한 두 도구가 **계약**(43.2~43.3절)과 **도메인 프리미티브**(44장)다.

리스팅 43-21의 코드로 돌아가자. 그 코드에는 두 개의 도메인 프리미티브 타입 — `ISBN`과 `Quantity` — 이 `Order`의 인터페이스가 되어야 한다. 변환의 전모는 44장의 몫이고, 여기서는 차이만 스케치한다.

`ShoppingService`가 `Order`를 호출할 때, 먼저 대응하는 도메인 프리미티브 객체를 만들어 넘긴다.

**리스팅 43-23. `Order` 객체를 호출하는 쪽**

```java
public void addToOrder(String orderId, String isbn, int qty) {
    Order order = orderservice.find(orderId);
    order.addBook(new ISBN(isbn), new Quantity(qty));
}
```

**`Order`를 호출하는 코드가 도메인 프리미티브 객체를 생성함으로써 검증의 부담을 진다.** 이 한 문장이 43.7절이 진단한 문제의 해답이다. 책임이 명시적으로 배분됐다.

`Order.addBook`이 `ISBN`과 `Quantity`를 받으면, 그 값들은 잘 포장되어 있고 **이미 제대로 검사되었다는 사실에 의존할 수 있다.** 같은 검사를 다시 할 이유가 없다. `Order`는 자신에게 `null`이 전달되지 않는다는 것만 보장하면 된다.

**리스팅 43-24. `Order`는 인자에 대해 `notNull` 계약만 지킨다**

```java
public void addBook(ISBN isbn, Quantity qty) {
    notNull(isbn);
    notNull(qty);
    if (!isAlreadyInCart(isbn)) {
        putInCartAsNew(isbn, qty);
    } else {
        addToLine(isbn, qty);
    }
}
```

검증된 도메인 프리미티브 객체가 인자로 들어오므로 `Order`가 ISBN의 형식을 다시 검증할 필요가 사라졌다. 그리고 공개 메서드 `addBook`에서 `notNull`을 검사했으므로 `putInCartAsNew`나 `isAlreadyInCart` 같은 비공개 메서드에서 `null` 검사를 반복할 필요도 사라졌다. 정리된 `isAlreadyInCart`를 보자.

**리스팅 43-25. 정리된 `isAlreadyInCart`**

```java
private boolean isAlreadyInCart(ISBN isbn) {
    boolean result = false;
    for (OrderLine item : items) {
        if (item.isbn().equals(isbn)) {
            result = true;
        }
    }
    return result;
}
```

**이 메서드는 형식 검사가 설계에 의해 보장된다는 것을 신뢰한다.**

혼란스러운 재검사가 전부 사라지자 코드가 무엇을 하는지가 훨씬 분명해졌다. 그리고 더 단순하게 만들 여지도 보인다. 이 루프가 하는 일은 항목들을 훑어서 찾는 ISBN과 일치하는 것이 있는지 보는 것이다.

**리스팅 43-26. ISBN 검색**

```java
private boolean isAlreadyInCart(final ISBN isbn) {
    return items.stream().anyMatch(item -> item.isbn().equals(isbn));
}
```

**주목할 점은 이 마지막 단순화가 검증 제거의 부산물이라는 것이다.** 리스팅 43-21의 원래 코드에서는 이런 리팩터링이 불가능했다. 루프 안에 형식 검사와 `null` 검사가 섞여 있었기 때문에 그 루프는 "찾기"라는 하나의 아이디어를 표현하고 있지 않았다. **방어적 코드는 코드가 자기 의도를 드러내는 것을 막는다.** 그리고 의도를 드러내지 않는 코드는 리뷰로도 검사로도 결함을 찾기 어렵다.

**표 43-13. 변환 전후**

| | 리스팅 43-21 (전) | 리스팅 43-23~43-26 (후) |
|---|---|---|
| 검증의 위치 | `ShoppingService`, `addBook`, `putInCartAsNew`, `isAlreadyInCart` 네 곳 | `ISBN`·`Quantity` 생성자 한 곳 |
| 검증의 내용 | 곳마다 다름 (`null`, 빈 문자열, 형식이 제각각) | 한 곳에서 43.4절의 다섯 단계를 수행 |
| 계약 | 없음 | `addBook`은 `notNull`만 요구, 나머지는 타입이 보장 |
| 검사 실패 시 | 대개 조용히 무시 | 생성자에서 빠르게 실패 |
| 값이 검증되었는지 아는 법 | 호출 경로 전체를 추적 | 타입을 본다 |
| 리팩터링 가능성 | 낮음 | 높음 |

마지막에서 두 번째 행이 이 장의 결론이다.

**`String isbn`은 검증에 대해 아무 말도 하지 않는다. `ISBN isbn`은 검증이 끝났다고 말한다.**

이것이 43.4.8절에서 예고한 "검증되었다는 사실을 코드에 남기기"의 완성된 모습이다. 그리고 이 문장이 성립하려면 하나의 조건이 필요하다. **`ISBN` 타입의 유효하지 않은 인스턴스가 존재할 수 없어야 한다.** 검증을 통과하지 못한 값으로 `ISBN` 객체를 만들 수 있다면 타입은 아무것도 증명하지 않는다.

그 조건을 어떻게 강제하는가. 답은 이 장이 이미 다 준비했다.

- **생성자에서 불변식을 강제한다**(43.3절). 검증은 생성자에 있고, 실패하면 객체가 만들어지지 않는다.
- **불변으로 만든다**(43.1절). 생성 이후 값이 바뀔 수 있다면 생성자의 검증은 무의미해진다.
- **검증은 정해진 순서로 한다**(43.4절). 그래야 생성자가 DoS 벡터가 되지 않는다.

**불변성, 계약, 검증 순서 — 이 장의 세 축이 하나의 타입을 만들기 위해 모인다.** 그 타입이 도메인 프리미티브이고, 44장의 첫 절이 그 정의에서 시작한다.

찾아야 할 설계 결함은 명확하다. **`null`, 형식, 범위에 대한 깊숙한 검사** 다. 그것이 감추는 것은 **코드가 자기 자신을 신뢰할 수 있도록 설계되지 않았다**는 사실이다. 그리고 그 지저분한 코드는 코드가 자기 기능을 더 간결하게 말하도록 만드는 리팩터링을 방해한다. 적절한 계약과 도메인 프리미티브를 도입하는 것이 더 나은 상태로 가는 길이다. 이 진단을 레거시 코드베이스 전체에 적용하는 절차 — 어디서부터 시작할 것인가, 어떻게 점진적으로 바꿀 것인가 — 는 47.1절과 47.2절이 다룬다.

> **이 절이 뒷받침하는 것**
>
> - 도메인 프리미티브 객체를 만드는 쪽이 검증의 부담을 진다 → **44.1**~**44.3** (도메인 프리미티브, 라이브러리, API 강화)
> - 방어적 코드는 리팩터링을 막고, 리팩터링이 막히면 결함이 보이지 않는다 → **44.6**, **44.10** (복잡도 축소)
> - 레거시 코드에서 이 진단을 적용하는 절차 → **47.1**, **47.2**, **47.5**
> - 유효하지 않은 인스턴스가 존재할 수 없다는 조건 → **44.8** (생성 시 일관성)

## 이 장의 요약

- **가변성은 무결성 문제와 가용성 문제를 동시에 만든다.** 온라인 서점 사건에서 `Customer`를 가변으로 만든 하나의 결정이 신용 점수 변조의 세 가지 경로와 스레드 경합에 의한 타임아웃을 함께 만들어냈다. 불변성은 세 경로를 한꺼번에 닫는다.
- **계약을 명시하는 행위가 책임의 소재를 결정한다.** 보안 문제의 상당수는 한 부분이 다른 부분이 책임진다고 가정하는데 그 부분은 정반대를 가정할 때 생긴다. 사전 조건, 불변식, 상태 사전 조건의 세 가지 검사를 `public` 메서드와 생성자에 두는 것이 이 문제를 코드에서 다루는 방법이다.
- **빠르게 실패하는 것이 흘려보내는 것보다 낫다.** 잘못된 값이 시스템 안으로 들어와 정상 값처럼 돌아다니게 되는 것이 2차 인젝션과 로직 결함의 공통 전제다. 던지는 예외의 종류가 무엇이 잘못됐는지를 말해 준다.
- **검증에는 다섯 단계가 있고 순서가 있다.** 출처 → 크기 → 어휘적 내용 → 구문 → 의미. 값싼 검사가 앞에 오고 비싼 검사가 뒤에 온다. 그 결과 **각 단계가 다음 단계를 지킨다.** 크기 검사가 파서와 정규식 엔진을 지키고, 어휘 검사가 파서를 지키고, 구문 검사가 데이터베이스를 지킨다.
- **순서를 어기면 앞쪽에서는 가용성이, 뒤쪽에서는 무결성이 무너진다.** 크기 검사 없이 파싱하면 Billion Laughs가 성립하고, 의미 검사를 생략하면 문법적으로 완벽한 요청이 업무 규칙을 위반한다.
- **경계 검증과 검증 순서는 다른 질문에 답한다.** WAHH는 "어디서"에 답하고 SBD는 "무엇을 어떤 순서로"에 답한다. 두 틀은 충돌하지 않고 서로의 약점을 보완한다. 이 책의 원칙은 **경계에서, 정해진 순서로 검증하고, 통과한 값을 타입으로 만든다** 이다.
- **검증됨은 값 하나가 아니라 값과 컨텍스트의 쌍이 갖는 속성이다.** 형식에 대한 보장은 컨텍스트를 넘어 유지되지만 의미에 대한 보장은 그렇지 않다. 경계마다 5단계를 다시 물어야 하는 이유가 이것이다.
- **다섯 가지 입력 처리 방식 중 안전한 데이터 처리는 검증이 아니라 검증을 불필요하게 만드는 설계이며, 의미론적 검사에는 대체재가 없다.** 앞의 세 가지(거부·허용·정제)는 전부 어휘 단계 근처에 몰려 있고, 그것이 "입력 검증"이 검증의 전부라고 오해되는 이유다.
- **흩어진 방어적 검사는 방어가 아니다.** 어디서도 무엇을 보장하는지 알 수 없고, 검사들이 시간이 지나며 서로 어긋나고, 실패해도 조용히 무시된다. 경계 검증과의 차이는 위치가 아니라 **각 검증이 무엇을 보장하는지가 명시되어 있는가**에 있다.
- **불변성, 계약, 검증 순서는 하나의 타입을 만들기 위해 모인다.** `String isbn`은 검증에 대해 아무 말도 하지 않고 `ISBN isbn`은 검증이 끝났다고 말한다. 이 문장이 성립하려면 유효하지 않은 인스턴스가 존재할 수 없어야 하며, 그 조건을 만드는 것이 이 장의 세 축이다.

## 이어지는 장

이 장은 코드의 문법을 다뤘다. 상태를 바꿀 수 없게 만드는 법, 계약을 검사로 적는 법, 검증을 순서대로 배치하는 법. 세 가지 모두 개별 기법으로도 값을 하지만, 이 장이 반복해서 가리킨 곳은 하나다. **그 세 가지가 모여 만드는 타입.**

44장이 그 타입을 다룬다. 44.1절은 **도메인 프리미티브**를 정의하면서 시작한다. 42.5절의 값 객체에서 출발하되 조건 하나를 더한다. **유효하지 않은 인스턴스가 존재할 수 없다.** 이 장의 43.3절이 생성자에서 불변식을 강제하는 방법을 보였고 43.1절이 불변성이 왜 필요한지를 보였다면, 44.1절은 그 둘을 합쳐 "존재 자체가 유효성의 증거인 값"을 만든다.

44.2절은 이 장의 43.5.4절이 남긴 문제를 이어받는다. 검증됨이 값과 컨텍스트의 쌍이 갖는 속성이라면, 도메인 프리미티브의 유효성도 컨텍스트 안에서만 정의된다. 44.3절은 그렇게 만든 타입들을 라이브러리로 조직하고 API의 경계에 배치하는 방법을 다루며, 이는 43.5절이 말한 "경계에서 검증한다"의 구체적 실행이다.

44.9절과 44.10절은 이 장의 43.1절이 남긴 미완의 문제를 받는다. 값은 불변으로 만들 수 있지만 엔티티는 정의상 변한다. 주문은 담기고 결제되고 배송된다. **바뀌어야 하는 것의 무결성을 어떻게 지키는가.** 43.1.3절에서 "읽기와 쓰기를 분리하면 불변 설계로도 변경을 지원할 수 있다"고만 말하고 넘긴 엔티티 스냅샷 패턴이 44.10절에서 완성된다.

그리고 45장이 이 장의 다른 축을 받는다. 이 장은 "빠르게 실패하라"고 말했지만, **실패한 다음에 무엇을 할 것인가**는 다루지 않았다. 예외를 어떻게 설계하고, 실패를 어떻게 정상 흐름의 일부로 다루고, 실패가 연쇄되지 않도록 어떻게 격리할 것인가. 45.6절은 이 장의 43.2.2절이 남긴 원칙 — 검증 전에 복구하지 말라, 입력을 반향하지 말라 — 을 실패 처리 설계의 관점에서 다시 다루고, 45.7절과 45.8절은 이 장 43.4.3절의 크기 검사를 가용성 설계 전체로 확장한다.

한 문장으로 말하면 이렇다. **43장은 값이 유효하다는 것을 어떻게 보장하는지를 다뤘고, 44장은 그 보장을 타입에 담는 법을 다루며, 45장은 보장이 깨졌을 때 무슨 일이 일어나야 하는지를 다룬다.**

> 43.6절: WAHH 2장 "Approaches to Input Handling" 전체. 다섯 접근법의 정의와 평가, 블랙리스트 우회 예(`seLeCt`, `or 2=2--`, `prompt('xss')`, `/*foo*/` 주석 삽입, `<img%09onerror=...>`, `%00` NULL 바이트), NULL 바이트가 관리·비관리 실행 환경의 문자열 처리 차이에서 비롯한다는 설명, 여섯 자 영숫자 상품 코드 화이트리스트 예, 아포스트로피가 든 이름이라는 화이트리스트의 한계, HTML 인코딩을 통한 XSS 방어, 파라미터화 질의를 통한 SQL 인젝션 방어, 숨은 폼 필드의 계좌번호 변조와 "어떤 구문 검증도 구별하지 못한다"는 논증은 모두 원서 서술. 표 43-10(다섯 접근법을 다섯 단계 위에 대응시킨 것)과 43.6.2~43.6.3절의 세 가지 독법 및 우선순위 목록은 이 책의 구성이며, 원서에 없는 종합이다.

> 43.7절: SBD 12.4, 12.4.1, 12.4.3. 반복된 `!= null` 검사가 "코드가 자기 자신을 신뢰하지 못한다는 표현"이라는 진단, 문제가 두 겹(가독성 저하 + 시간이 지나며 검사가 어긋남)이라는 분석, 온라인 서점의 `ShoppingService`/`Order` 코드(리스팅 43-21은 원서 리스팅 12.8 그대로이며 원서에서도 온라인 서점 도메인이다), `ShoppingService`가 형식을 검사하고도 `Order`가 그것을 신뢰하지 않는다는 아이러니, `addBook`이 `isEmpty`는 검사하는데 다른 메서드는 그것을 반복하지 않는다는 불일치, 수백 줄 메서드 한가운데의 `null` 검사가 실제 사고 이후 반창고처럼 붙는다는 관찰, 잘못된 값을 만나고도 아무것도 하지 않는 대처 전략의 문제, 방어적 검사가 리팩터링을 방해한다는 지적, `Optional`의 과도한 사용(리스팅 43-22는 원서 리스팅 12.13 기준)은 모두 원서 서술. 표 43-11(흔적과 감추는 것), 43.7.4절 전체(12.11절 WAF·26.7절과의 연결, "방어를 여러 곳에 흩어 두면 어디서도 확실하지 않다"), 표 43-12(흩어진 방어와 경계 검증의 대비)는 이 책의 구성이다. 특히 "경계 검증은 검증을 흩는 것이 아니라 검증에 좌표를 부여하는 것"이라는 정식화는 43.5절과 43.7절을 잇기 위해 이 책이 추가한 것이다.

> 43.8절: SBD 12.4.2. 리스팅 43-23~43-26은 원서 리스팅 12.9~12.12 기준. "`Order` 객체를 호출하는 코드가 도메인 프리미티브 객체를 생성함으로써 검증의 부담을 진다"는 문장, 재검사가 사라지자 `Stream` API로 단순화할 수 있게 된다는 관찰, "찾아야 할 설계 결함은 `null`·형식·범위에 대한 깊숙한 검사"라는 결론은 모두 원서 서술. 표 43-13(변환 전후)과 "`String isbn`은 검증에 대해 아무 말도 하지 않고 `ISBN isbn`은 검증이 끝났다고 말한다"는 정식화, 그리고 그 문장이 성립하려면 이 장의 세 축이 모두 필요하다는 마지막 논증은 이 책의 구성이다.

> 이 장의 코드 예제는 모두 자바이며 원서 SBD의 표기를 따랐다. `notNull`, `isTrue`, `matchesPattern`, `inclusiveBetween`, `validState`는 원서가 사용하는 아파치 커먼즈 랭 `Validate` 유틸리티의 메서드이나, 이 책에서는 라이브러리가 아니라 "조건을 검사하고 어긋나면 적절한 예외를 던진다"는 구조의 표기로 다뤘다.
