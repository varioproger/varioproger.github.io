# 38장. GraphQL 입문과 공격 표면

> **이 장에서 다루는 것**
>
> - GraphQL이 하나의 엔드포인트에 POST로 통신한다는 사실이 HTTP 층위의 통제 — URL 기반 접근 제어, WAF 룰, 캐시 키, 접근 로그 — 를 어떻게 무력화하는가
> - GraphQL이 실제로 해결한 문제(오버페칭·언더페칭)와, 그 대가로 클라이언트에게 넘긴 것(질의 구조의 통제권)
> - 질의·뮤테이션·서브스크립션·프래그먼트·디렉티브·앨리어스·변수라는 언어 요소가 각각 어떤 공격 벡터가 되는가
> - 스키마·타입 시스템·인트로스펙션·검증·실행이라는 서버 측 구조
> - GraphQL의 흔한 약점이 이 책 Part V~VII의 어느 장과 일대일로 대응하는가, 그리고 무엇이 같고 무엇이 다른가

Part VIII이 여기서 시작한다. 이 부 전체가 답하려는 질문은 하나다. **같은 실패 유형이 새 프로토콜에서 어떻게 되풀이되는가.** 앞의 일곱 부는 HTTP를 계층별로 훑으며 그 위에서 깨지는 신뢰 경계를 하나씩 짚었다. GraphQL은 그 위에 올라앉은 또 하나의 애플리케이션 계층이며, 앞에서 본 취약점의 압도적 다수를 그대로 물려받는다. 인가 우회, 인젝션, 정보 노출, 요청 위조 — 이 부의 어느 것도 GraphQL이 발명한 것이 아니다.

이 부의 논지를 미리 못 박아 둔다. **GraphQL은 새로운 종류의 취약점을 거의 만들지 않았다.** 27장의 SQL 인젝션은 리졸버를 진입점으로 삼아 그대로 재현되고(→ 27.14), 30장의 정보 노출은 더 친절한 얼굴로 반복되며(→ 30.10), 33장의 CSRF는 단일 엔드포인트와 쿠키 인증이라는 조건 위에서 다시 성립한다(→ 33.6). 이 장 마지막 절(38.10)의 대응표가 그 대응을 낱낱이 보인다.

그런데 **한 가지는 정말 새롭다.** GraphQL에서는 **클라이언트가 질의의 구조를 정한다.** 응답에 어떤 필드가 담길지, 관계를 얼마나 깊이 따라 내려갈지, 같은 필드를 몇 번 반복할지를 서버가 아니라 클라이언트가 결정한다. 이 설계가 서버의 자원 소모를 클라이언트가 제어할 수 있게 만들었다. 이것이 40장에서 다룰 서비스 거부(DoS)의 뿌리이며, 이 부가 "같은 것의 반복"이라는 논지에 붙이는 유일한 예외다. 이 장에서 언어를 설명할 때 앨리어스와 디렉티브를 특히 정확히 다루는 이유가 여기에 있다 — 그것들이 40장의 전제이기 때문이다.

이 장은 두 부분으로 나뉜다. 앞부분(38.1~38.4)은 GraphQL이 무엇이고 어떻게 통신하며 어떻게 실습하는가를 세운다. 뒷부분(38.5~38.10)은 그 위에서 공격 표면을 그린다. 38.1이 이 장의 고유한 기여를 담고, 38.10이 이 장의 절정이다.

## 38.1 GraphQL의 기초 / 통신은 어떻게 이뤄지는가 — HTTP 위의 단일 엔드포인트

GraphQL은 API를 위한 오픈 소스 데이터 질의·조작 언어다. 페이스북이 2012년 사내에서 쓰기 시작해 2015년 명세와 참조 구현(JavaScript로 작성된 GraphQL.js)을 함께 공개했고, 지금은 GraphQL 재단이 관리한다. 클라이언트(대개 브라우저, 때로는 다른 서버)가 애플리케이션 서버의 GraphQL API를 통해 데이터를 읽거나 바꾼다는 점은 여느 API와 같다. 다른 것은 **누가 응답의 형태를 정하는가**다. REST가 고정된 데이터 구조를 돌려주고 클라이언트가 필요 없는 것을 걸러 내게 하는 반면, GraphQL은 클라이언트가 요청한 데이터만 돌려준다.

### 38.1.1 핵심 구성 요소

GraphQL 서버가 요청을 처리하는 경로에는 몇 개의 부품이 있다. 보안을 다루려면 이 부품들을 알아야 한다.

- **질의 파서(query parser).** 들어온 질의 문자열을 읽어 추상 구문 트리(abstract syntax tree, AST)로 바꾼다. AST는 필드·인자 등을 담은 계층 구조 객체다.
- **스키마(schema).** 클라이언트가 질의할 수 있는 데이터의 타입을 정의한다. 파서는 이 스키마에 질의를 대조해 유효성을 검사한다.
- **리졸버 함수(resolver functions).** 검증을 통과한 질의의 각 필드에 대해 실제 데이터를 채워 응답을 만든다. 리졸버는 관계형 데이터베이스, 캐시, 파일시스템, 다른 서버의 REST API를 호출한다. 모든 필드에는 그에 대응하는 리졸버가 있다.

리졸버가 데이터를 실제로 가져오는 곳이므로, **취약점이 사는 곳도 바로 여기다.** 리졸버가 백엔드 SQL을 문자열로 이어 붙이면 SQL 인젝션이 생기고(→ 27.14), 리졸버가 사용자가 준 URL을 그대로 가져오면 SSRF가 생긴다(→ 28.10). GraphQL은 클라이언트와 애플리케이션 로직 사이에 놓인 질의 계층일 뿐이며, 그 뒤의 위험은 앞의 여러 장에서 본 것 그대로다.

### 38.1.2 단일 엔드포인트에 POST — 이 장의 고유한 기여

여기서부터가 이 장이 이 책 전체에 더하는 고유한 관찰이다. 클라이언트가 GraphQL 서버와 통신하려 할 때, 그 통신은 거의 언제나 **하나의 URL 경로에 HTTP POST 메서드로** 이뤄진다. 엔드포인트는 관례상 `/graphql`이며(버전을 붙여 `/v1/graphql`을 쓰기도 한다), **자원이 무엇이든, 동작이 무엇이든 이 경로는 바뀌지 않는다.** 클라이언트의 의도 — 읽기인지 쓰기인지, 어떤 자원인지 — 는 URL이 아니라 요청 본문(payload)에 담긴 질의 안에 들어 있다.

REST와 대조하면 이 결정의 무게가 드러난다. REST는 자원마다 별도의 엔드포인트를 노출한다. `/users`는 사용자 목록, `/history/<id>`는 로그인 이력이며, 각 엔드포인트는 자기만의 통제와 지원 메서드를 가질 수 있다. `/history`는 `GET`만 허용하고, `/users`는 `GET`과 `POST`를 함께 허용하는 식이다. REST에서 HTTP 메서드는 클라이언트의 의도를 나타낸다 — `GET`은 읽기, `POST`는 생성·수정. 그런데 **GraphQL은 이 관례를 따르지 않는다.** 데이터를 쓰든 지우든 단순히 읽든, 통신은 대개 `POST`로 이뤄진다.

이 두 성질 — 단일 URL, 그리고 본문에 감춰진 의도 — 이 결합하면, HTTP 층위에 세워진 통제 장치 여럿이 한꺼번에 무력해진다. 이것을 하나씩 짚는다.

**URL 기반 접근 제어가 무의미해진다.** 24.1절에서 접근 제어의 흔한 결함으로 "식별자 기반 기능"과 "URL·경로에 건 통제"를 다뤘다. 웹 서버나 리버스 프록시 앞단에서 `/admin/*` 경로를 특정 역할에만 열어 주는 식의 통제는 REST에서는 자연스럽다. 그러나 GraphQL에서는 관리자 전용 뮤테이션도, 일반 사용자의 조회도 **모두 같은 `/graphql`로 간다.** 경로로는 둘을 구분할 수 없다. 그래서 GraphQL의 인가는 경로가 아니라 **필드 단위로, 리졸버 안에서** 강제되어야 한다. 24장이 "인가는 중앙 컴포넌트에서, 요청마다"라고 요구한 이유가 GraphQL에서 문자 그대로 강제된다. 경로에 통제를 걸어 두고 안심하던 습관은 GraphQL 앞에서 곧장 결함이 된다.

**WAF 룰이 헛돈다.** 12.11절에서 웹 애플리케이션 방화벽(WAF)이 대개 URL·메서드·헤더·본문의 패턴에 룰을 걸어 판단한다고 했다. 전통적 WAF와 취약점 스캐너는 RFC 2616 HTTP 표준을 전제로 만들어졌고, 애플리케이션이 그 상태 코드 관례를 지킨다고 가정한다. GraphQL은 이 가정을 깬다 — 인가 오류든 자원 없음이든, 응답은 거의 항상 `200 OK`다(38.2에서 자세히 본다). 무차별 대입을 탐지하려고 `401`·`403`의 빈도를 세는 룰은 GraphQL 트래픽 앞에서 아무 신호도 얻지 못한다. `200 OK`만 돌아오기 때문이다. 나아가 WAF가 특정 URL이나 메서드에 룰을 매어 두었다면, 모든 트래픽이 `POST /graphql` 하나로 수렴하는 GraphQL에서는 그 룰이 자원을 구별하지 못한다. 실제로 2022년 AWS AppSync 사례에서 WAF가 인트로스펙션의 `__schema` 키워드만 차단하고 `__type`은 놓쳐 우회된 일이 있다(→ 30.10.3, 39.5). WAF가 GraphQL 본문의 의미를 이해하도록 특별히 만들어지지 않는 한, 단일 엔드포인트는 WAF의 시야를 가린다.

**공유 캐시가 헛돈다.** 14.8절에서 공유 캐시의 판단이 두 가지 — "이 응답을 저장해도 되는가"와 "이 요청에 저장본을 돌려줘도 되는가" — 로 나뉘고, 후자는 **캐시 키**로 결정된다고 했다. 표준 HTTP 캐시의 기본 키는 메서드와 URL이다. 그런데 GraphQL은 거의 모든 요청이 `POST /graphql`이다. `POST`는 기본적으로 캐시되지 않고, 설령 캐시하더라도 URL이 전부 같으니 서로 다른 질의가 같은 키로 뭉개진다. 요청의 실제 내용은 본문 안에 있는데, 표준 캐시는 본문을 키로 보지 않는다. 그래서 GraphQL 앞에서 HTTP 캐시는 대개 무력하며, 캐싱하려면 애플리케이션이 질의 내용을 키에 반영하는 별도의 장치를 만들어야 한다. 이 사정이 GET 기반 질의라는 우회를 부르고, 그것이 다시 캐시·로그 누출이라는 별개의 문제를 낳는다(→ 39.8).

**접근 로그가 무의미해진다.** 16.1절에서 무엇을 로깅할 것인가를 다루며, 접근 로그의 핵심 필드가 요청 라인 — 메서드와 URL — 임을 보았다. GraphQL 애플리케이션의 접근 로그는 이렇게 남는다.

```
172.17.0.1 - - [04:31:01] "POST /graphql HTTP/1.1" 200 -
172.17.0.1 - - [04:31:05] "POST /graphql HTTP/1.1" 200 -
172.17.0.1 - - [04:31:37] "POST /graphql HTTP/1.1" 200 -
```

세 줄이 완전히 똑같다. 하나는 무해한 조회이고 하나는 전체 사용자 삭제였을 수 있지만, **로그만 보아서는 구별되지 않는다.** 메서드도 URL도 상태 코드도 모두 같기 때문이다. 클라이언트가 붙이는 오퍼레이션 이름(operation name)마저 임의로 지을 수 있어서, `getPastes`라는 이름의 요청이 실제로는 전체를 삭제할 수도 있다(→ 38.6). REST 로그를 분석하던 방식 — 상태 코드의 이상 패턴, 민감 경로의 접근 빈도 — 은 여기서 통하지 않는다. GraphQL을 의미 있게 로깅하려면 요청 본문의 질의를 파싱해 오퍼레이션 종류와 필드를 기록하는 전용 로깅이 필요하다. 표준 접근 로그는 GraphQL 앞에서 세 줄의 `POST /graphql`로 붕괴한다.

정리하면 이렇다. **HTTP 층위의 통제 장치들은 대부분 "메서드와 URL이 자원과 의도를 나타낸다"는 전제 위에 서 있다.** GraphQL은 그 전제를 깬다. 자원과 의도가 URL이 아니라 본문 안으로 들어갔기 때문이다. 이것이 GraphQL이 새로 만든 유일한 구조적 변화이자, 이 장이 이 책에 더하는 고유한 관찰이다. GraphQL은 새 취약점을 거의 만들지 않았지만, 앞의 여러 장이 의지하던 방어선 몇 개를 무력화한다. 그 방어를 잃은 자리에서 익숙한 취약점들이 재현되는 것이 이 부의 이야기다.

## 38.2 GraphQL이 해결하는 문제 / REST API와의 비교

GraphQL이 왜 생겼는지는 두 단어로 압축된다 — **오버페칭(over-fetching)** 과 **언더페칭(under-fetching)**. 둘 다 고정된 응답 구조를 돌려주는 REST의 성질에서 온다.

관리자 페이지가 사용자 목록을 보여 주는 예를 든다. 데이터베이스 테이블에는 사용자 ID·이름·이메일·성·이름·상태가 담겨 있다.

**표 38-1. 사용자 데이터베이스 테이블 (BHGQL 표 1-1 기준)**

| User ID | Username | Email | First name | Last name | State |
|---|---|---|---|---|---|
| 1 | dsmith | david@example.com | David | Smith | Disabled |
| 2 | clarry | chris@example.com | Chris | Larry | Enabled |

REST API가 이 데이터를 두 엔드포인트로 노출한다고 하자. `GET /rest/v1/users`는 모든 사용자를, `GET /rest/v1/history/<user_id>`는 특정 사용자의 로그인 이력을 돌려준다.

**오버페칭.** 관리자가 사용자들의 이메일 주소만 필요하다고 하자. `GET /rest/v1/users`는 이메일뿐 아니라 이름·상태·ID를 전부 담아 돌려준다. 클라이언트는 응답 전체를 받아 이메일만 뽑아내야 한다. **필요 없는 데이터가 함께 왔다.** 이것이 오버페칭이며, 대역폭을 낭비할 뿐 아니라 개인식별정보(PII) 같은 민감 데이터를 의도치 않게 노출할 여지를 늘린다. 필요 이상으로 돌려주는 응답은 곧 정보 노출의 표면이다.

**언더페칭.** 이번엔 스크립트로 밤마다 침입 시도를 점검한다고 하자. 각 사용자의 마지막 로그인 시각을 보려면 `GET /rest/v1/history/1`을 호출해야 하는데, 이 엔드포인트는 사용자 ID를 요구한다. 스크립트는 ID를 모르니 먼저 `GET /rest/v1/users`로 전체 사용자를 받아 ID를 얻고, 그다음 각 ID마다 이력을 따로 요청해야 한다. 사용자가 1,000명이면 요청이 1,001번이다. **한 번에 필요한 것을 다 못 받아 추가 왕복이 강제된다.** 이것이 언더페칭이다. 요청 하나하나가 지연을 더하므로, 수백만 클라이언트를 상대하는 규모에서는 치명적이다.

GraphQL은 클라이언트가 질의 구조를 스스로 정하게 해 두 문제를 함께 없앤다. 사용자와 이력 노드 사이에 스키마 상의 간선(edge)이 정의돼 있으면, 클라이언트는 한 번의 질의로 원하는 필드만, 관계를 따라 내려가며 가져올 수 있다.

```graphql
query {
  users {
    email
    history {
      last_login_timestamp
    }
  }
}
```

이 질의는 정확히 이메일과 마지막 로그인 시각만, 한 번의 왕복으로 돌려준다. 오버페칭도 언더페칭도 없다. 응답은 요청한 필드만 담는다.

```json
{
  "data": {
    "users": [
      { "email": "david@example.com", "history": { "last_login_timestamp": ["02:03:37"] } },
      { "email": "chris@example.com", "history": { "last_login_timestamp": ["02:03:37", "03:05:55"] } }
    ]
  }
}
```

보안 관점에서 이 설계는 양날이다. 요청하지 않은 데이터를 돌려주지 않으니 우발적 정보 노출의 기회는 줄어든다. 그러나 **클라이언트가 질의 구조를 정한다는 바로 그 힘이** — 응답의 형태와 깊이와 반복 횟수를 클라이언트가 결정한다는 힘이 — 서버 자원 소모의 통제권을 클라이언트에게 넘긴다. 이것이 이 부의 유일한 새 취약점, DoS의 뿌리다(→ 40장).

### 38.2.1 그 밖의 차이 — 메서드, 엔드포인트, 상태 코드

REST를 테스트해 본 사람에게 낯설 만한 GraphQL의 관례가 몇 가지 더 있다. 이 차이들이 곧 38.1에서 본 통제 무력화의 실무적 근거다.

- **HTTP 메서드.** GraphQL은 읽기·쓰기·삭제를 가리지 않고 대개 `POST`를 쓴다. 다만 명세는 `GET`으로 질의를 받는 것도 허용하므로, 대상 서버가 `GET`을 지원하는지 반드시 시험해야 한다 — CSRF의 문을 열 수 있기 때문이다(→ 33.6).
- **엔드포인트 경로.** 자원마다 경로가 다른 REST와 달리, GraphQL은 모든 요청이 `/graphql` 하나로 간다. 클라이언트의 의도는 질의 페이로드 안의 오퍼레이션으로 표현된다.
- **HTTP 상태 코드.** REST에서 상태 코드는 결과를 알리는 핵심 신호다. GraphQL에서는 인가 오류든 자원 없음이든 응답이 거의 항상 `200 OK`이며, 오류는 응답 본문의 `errors` 필드로 전달된다.

```json
{
  "errors": [
    {
      "message": "Cannot query field \"usernam\" on type \"User\". Did you mean \"username\"?",
      "locations": [ { "line": 3, "column": 5 } ]
    }
  ]
}
```

데이터베이스 다운 같은 치명적 서버 오류에서만 `500`이 돌아온다. 이 `200 OK` 일변도가 왜 중요한지는 38.1에서 이미 보았다 — 상태 코드에 의존하는 로그 분석과 WAF 룰과 스캐너가 모두 헛돈다. 그리고 `errors` 필드의 메시지 자체가 정보를 흘리는 통로가 된다. 위 예의 "Did you mean ...?"이 스키마의 실제 필드 이름을 알려 주는데, 이것이 필드 제안(field suggestion)이며 GraphQL 특유의 정보 노출이다(→ 30.10, 39.5).

> **이 책의 범위를 넘어서**
>
> GraphQL을 게이트웨이로 확장하는 기법 — 여러 하위 GraphQL 서비스의 스키마를 하나로 합치는 스키마 스티칭(schema stitching)과 스키마 페더레이션(schema federation), 그리고 이를 제품화한 Apollo 같은 구현체의 세부, persisted query의 현대적 구현 — 은 이 책의 범위를 넘는다. 공통 원리만 짚어 둔다. 복잡도가 올라갈수록 취약점의 여지도 커진다는 것, 그리고 여러 스키마를 하나로 합치는 통합 지점은 인가 문맥이 유실되기 쉬운 자리라는 것(→ 24.8)이다. 이 책은 단일 스키마 단일 서버를 전제로 GraphQL의 공격 표면을 다룬다.

## 38.3 첫 질의 작성하기

GraphQL을 손으로 만져 보는 가장 쉬운 길은 대부분의 구현체가 함께 제공하는 그래픽 IDE다. **GraphiQL Explorer**(발음은 "그래피컬", 소문자 i에 주의)와 **GraphQL Playground**가 대표적이다. 둘 다 자동 완성, 자동 생성된 스키마 문서, 오류 강조, 질의 이력, 변수 입력을 지원해 처음 쓰는 사람도 쉽게 질의를 짤 수 있다. 해커에게도 이 인터페이스는 유용하며, 이런 인터페이스를 찾아내고 남용하는 법은 39장이 다룬다.

스키마가 다음처럼 정의돼 있다고 하자. `User`와 `Location` 두 객체 타입이 있고, `Query` 타입이 `users`를 진입점으로 노출한다.

```graphql
type User {
  username: String
  email: String
  location: Location
}

type Location {
  latitude: Int
  longitude: Int
}

type Query {
  users: [User]
}

schema {
  query: Query
}
```

`[User]`의 대괄호는 이 질의가 `User` 객체의 **배열**을 돌려준다는 뜻이다. 이제 클라이언트가 보낼 질의는 이렇다.

```graphql
query {
  users {
    username
    email
  }
}
```

읽기 쉽다. `query` 루트 오퍼레이션으로 시작하고, `users`를 최상위 필드로 요청하며, 그 안에서 `username`과 `email`만 고른다. 데이터를 읽기만 하고 바꾸지 않으므로 뮤테이션이 아니라 질의다. 필드 이름(`users`)은 소문자로, 객체 이름(`User`)은 대문자로 시작하는 것이 가장 흔한 관례다. 이름은 대소문자를 구분하므로 정확히 따라야 한다.

명령줄에서 같은 일을 하려면 `cURL`로 `POST` 요청을 보내면 된다. GraphiQL 같은 IDE는 편리하지만 침투 테스트 중에 늘 있는 것은 아니므로, 명령줄에서 질의를 짜고 보내는 데 익숙해져야 한다. 서버가 스키마를 자기 자신에게 질의하도록 열어 두었다면(인트로스펙션, → 38.8), IDE의 자동 완성은 그 인트로스펙션 질의로 스키마를 읽어 채운 것이다. 즉 편의 기능의 원천 자체가 공격자에게도 지도를 그려 준다.

## 38.4 보안 랩 구축 — Kali, 웹 클라이언트, 취약 GraphQL 서버, 해킹 도구 설치

이 책은 0.4절에서 패킷 캡처 도구, 인터셉팅 프록시, 취약 서버를 포함한 통합 실습 환경을 세웠다. 여기서는 그 위에 얹는 **GraphQL 특화 부분만** 다룬다. 가상화·스냅샷·격리 원칙 등 일반적인 랩 구축 지침은 0.4절로 갈음한다.

- **기반 OS와 격리.** 침투 테스트용 배포판인 Kali Linux를 하이퍼바이저(VirtualBox 등) 위 가상 머신으로 올린다. 취약한 코드나 구식 소프트웨어를 다루므로 랩을 공개 인터넷에 직접 붙이지 않고, 신뢰하는 로컬 네트워크에서만 작업하며, 상태를 저장할 수 있도록 스냅샷을 자주 남긴다.
- **웹 클라이언트.** 명령줄 HTTP 클라이언트 `cURL`과 그래픽 GraphQL 클라이언트 **Altair**를 함께 쓴다. Altair는 원격 GraphQL 서버에 붙어 질의를 보내고, 자동 완성·스키마 문서·질의 이력·커스텀 HTTP 헤더 설정을 제공한다. 인증이 걸린 원격 서버에는 Altair의 헤더 설정으로 토큰을 실어야 질의가 통한다.
- **취약 GraphQL 서버.** 학습 표적으로 **DVGA(Damn Vulnerable GraphQL Application)** 를 Docker 컨테이너로 띄운다. DVGA는 DoS·정보 노출·코드 실행·인증 우회·SQL 인젝션·깨진 인가 등을 의도적으로 심어 둔 애플리케이션이며, Pastebin처럼 텍스트 조각(paste)을 올리고 공유하는 형태다. 이후 39·40장의 실습이 모두 이 표적을 향한다. 서버가 살아 있는지는 다음 질의로 확인한다.

```graphql
query {
  systemHealth
}
```

- **GraphQL 해킹 도구.** REST와 다른 GraphQL의 성질(38.1~38.2) 때문에 전용 도구가 필요하다. 이 부에서 이름이 나올 도구를 미리 표로 둔다. 실제 사용은 39·40장이다.

**표 38-2. 이 부에서 쓰는 GraphQL 도구 (BHGQL 2장 기준)**

| 도구 | 역할 | 주로 쓰는 장 |
|---|---|---|
| Burp Suite | 인터셉팅 프록시 — 질의를 가로채 수정·재전송 | 전 장 |
| InQL | 인트로스펙션 기반 스키마 자동 추출 | 39장 |
| Clairvoyance | 인트로스펙션이 꺼졌을 때 필드 제안으로 스키마 재구성 | 39장 |
| graphw00f | 응답 차이로 GraphQL 구현체 핑거프린팅 | 39장 |
| GraphQL Cop | 정보 노출·DoS 취약점 감사 | 40장 |
| BatchQL | 배칭 관련 DoS·CSRF·정보 노출 점검 | 40장 |
| CrackQL | GraphQL 언어 기능을 이용한 무차별 대입 최적화 | 40장 |
| graphql-path-enum | 특정 데이터에 이르는 질의 경로 열거(인가 결함 탐지) | 40장 |
| Commix | 명령 인젝션 자동 탐지·익스플로잇 | 40장 |

이 표의 도구 대부분은 GraphQL이 `200 OK` 일변도이고 단일 엔드포인트라는 성질(38.1) 때문에 기존 도구가 오탐을 내는 문제를 메우려 만들어졌다. 도구의 존재 자체가 이 장의 관찰 — GraphQL이 HTTP 층위의 전제를 깬다는 것 — 을 방증한다.

## 38.5 공격 표면이란 무엇인가

공격 표면(attack surface)이란 공격자가 시스템의 기밀성·무결성·가용성을 무너뜨리는 데 쓸 수 있는 모든 공격 벡터의 총합이다. 앞문·옆문·창문이 여럿인 건물을 떠올리면 된다. 공격자에게 각 문과 창은 무단 진입의 기회다. 문과 창이 많을수록 그중 하나가 잠기지 않았을 확률이 높다.

이 비유가 담는 두 가지가 이 부 전체에 걸린다. 첫째, **표면이 클수록 위험이 크다.** 애플리케이션·데이터베이스·서버·엔드포인트가 많을수록 뚫릴 지점이 늘어난다. 둘째, **표면은 시간에 따라 변한다.** 특히 클라우드 환경에서 서버는 잠깐 살다 사라지고 IP는 하루에도 여러 번 바뀐다. 25장에서 애플리케이션 매핑을 다루며 "공격 표면 지도"를 그린 것이 이 정의의 실무판이었다(→ 25.7).

GraphQL의 공격 표면을 그리는 것이 38.6부터의 일이다. 그 표면을 두 시점으로 나눠 본다. **언어(language)** 는 클라이언트가 서버에 요청을 보내는 데 쓰는 것이므로 클라이언트의 관점에서 보고(38.6), **타입 시스템(type system)** 은 서버가 데이터를 정의하는 것이므로 서버의 관점에서 본다(38.7). 그다음 인트로스펙션(38.8)과 검증·실행(38.9)이라는 서버 측 메커니즘을 짚고, 마지막으로 이 표면 위에서 실제로 나타나는 약점들을 이 책의 앞 장들과 대응시킨다(38.10). 목표는 GraphQL 명세를 전부 옮기는 것이 아니라, 다음 장들에서 공격 벡터를 시험하기에 충분한 만큼만 정확히 아는 것이다.

## 38.6 언어 — 질의, 뮤테이션, 서브스크립션, 프래그먼트, 디렉티브, 앨리어스, 변수

GraphQL 질의는 독특한 구조를 갖는다. 그 부품을 하나의 예로 먼저 본다.

```graphql
query Anatomy {
  pastes(filter: "some title", public: true) {
    title
    content
    ipAddr @show_network(style: "cidr")
  }
  users {
    username(capitalize: true)
  }
}
```

**표 38-3. GraphQL 질의의 구성 요소 (BHGQL 표 3-1 기준)**

| 요소 | 예 | 설명 |
|---|---|---|
| 오퍼레이션 타입 | `query` | 서버와의 상호작용 방식(query·mutation·subscription) |
| 오퍼레이션 이름 | `Anatomy` | 클라이언트가 붙이는 임의의 레이블 |
| 최상위 필드 | `pastes`, `users` | 오퍼레이션 안에서 요청하는 정보·객체 단위 |
| 인자 | `filter`, `public`, `capitalize` | 필드의 동작·결과를 조정하는 파라미터 |
| 값 | `"some title"`, `true` | 인자에 실리는 데이터 |
| 필드 | `title`, `content` | 선택 집합 안의 정보 단위(중첩 가능) |
| 디렉티브 | `@show_network` | 필드의 검증·실행 동작을 바꾸는 장치 |

이 요소들이 각각 어떻게 공격 벡터가 되는지가 이 절의 핵심이다.

### 38.6.1 질의, 뮤테이션, 서브스크립션

모든 GraphQL 오퍼레이션은 세 루트 타입 중 하나로 시작한다.

- **질의(query).** 읽기 전용. 데이터를 바꾸지 않는다.
- **뮤테이션(mutation).** 데이터 조작 — 쓰기·추가·삭제. 바꾸면서 동시에 읽을 수 있다.
- **서브스크립션(subscription).** 클라이언트와 서버 사이의 실시간 통신. 이벤트가 일어나면 서버가 클라이언트에 데이터를 민다.

뮤테이션 예를 든다. `editPaste`가 `id`와 `content`를 인자로 받아 1번 paste의 내용을 바꾸고, 바뀐 paste를 되돌려 준다.

```graphql
mutation {
  editPaste(id: 1, content: "My first mutation!") {
    paste { id title content }
  }
}
```

여기서 보안상 중요한 한 가지. REST에서 `GET`이 관례상 읽기이면서도 규약을 어기면 데이터를 바꿀 수 있듯, **GraphQL 구현체도 명세를 무시하고 질의(query) 오퍼레이션으로 데이터를 쓰게 만들 수 있다.** 파괴적 동작을 뮤테이션이 아니라 질의로 구현하면, 그것은 `GET`으로도 실행 가능해져 CSRF의 문을 연다(→ 33.6). 질의로 데이터를 쓰는 것이 왜 나쁜지는 33·40장이 다룬다.

**서브스크립션**은 양방향이며 대개 WebSocket 위에서 실행된다. 클라이언트와 서버가 HTTP 커넥션을 WebSocket으로 업그레이드하는 핸드셰이크를 거친다.

```
GET /subscriptions HTTP/1.1
Host: 0.0.0.0:5013
Connection: Upgrade
Upgrade: websocket
Origin: http://localhost:5013
Sec-WebSocket-Version: 13
Sec-WebSocket-Key: MV5U83GH1UG8AlEb18lHiA==
```

서버가 `101 Switching Protocols`로 답하면 커넥션이 WebSocket으로 전환된다. 이후 클라이언트는 이 채널로 `subscription { paste { id title content } }` 같은 구독을 걸고, 새 paste가 생길 때마다 서버가 알린다. WebSocket을 쓴다는 사실이 서브스크립션을 **크로스 사이트 WebSocket 하이재킹(CSWSH)** 에 노출시킨다 — 서버가 핸드셰이크에서 `Origin`을 검증하지 않을 때다(→ 33.7, 37.7). 서브스크립션이 이 책의 실시간 채널 논의와 GraphQL을 잇는 다리다.

### 38.6.2 오퍼레이션 이름 — 로그를 속이는 벡터

오퍼레이션 이름은 클라이언트가 오퍼레이션에 붙이는 레이블이다. 문서 하나에 오퍼레이션이 여럿이고 같은 타입이 둘 이상이면 이름이 필수다. 문제는 **이 이름을 클라이언트가 마음대로 정한다**는 데 있다. `getPastes`라는 이름을 달고 실제로는 모든 paste를 삭제할 수 있다. 로그를 검토하는 분석가를 속이기에 좋은 수단이다(→ 38.1의 로그 붕괴). 나아가 일부 구현체는 오퍼레이션 이름에 특수문자를 허용하고 애플리케이션이 이 이름을 감사 로그나 제3자 시스템에 저장하므로, 이름 자체가 인젝션의 진입점이 될 수 있다(→ 16.6 로그 인젝션).

### 38.6.3 필드와 인자

**필드(field)** 는 선택 집합(중괄호로 감싼 목록) 안의 정보 단위다. 필드는 자기만의 선택 집합을 가질 수 있어, 복잡한 데이터 관계를 표현한다.

```graphql
{
  id
  title
  content
  owner { name }
}
```

선택 집합이 필드로 이뤄지고 필드가 다시 선택 집합을 갖는 이 **재귀 구조**가 곧 순환 질의(circular query)의 씨앗이다 — 두 객체가 서로를 참조하면 질의가 무한히 깊어질 수 있고, 그것이 DoS가 된다(→ 40.2). 또한 필드를 오타 내면 서버가 정정을 제안하는 **필드 제안** 기능이 스키마를 흘린다(→ 30.10, 39.5).

**인자(argument)** 는 필드의 동작을 조정한다. `users(id: 1)`처럼 필드에, `@show_network(style: "cidr")`처럼 디렉티브에 붙는다.

```graphql
query {
  users(id: 1) {
    username(capitalize: true)
  }
}
```

인자는 순서가 없다 — 순서를 바꿔도 의미가 같다. 이것은 명세의 규칙이다("인자는 어떤 구문 순서로든 제공될 수 있으며 동일한 의미를 유지한다"). 그런데 인자의 값은 클라이언트가 정하므로, **인자는 인젝션의 주요 진입점**이다(→ 27.14, 28.10). GraphQL은 강타입이므로 문자열 자리에 정수를 넣으면 검증 오류가 난다. 그러나 문자열을 넣으면 GraphQL 검증은 통과하고, 그 값이 이메일인지 IP인지는 애플리케이션이 따로 확인해야 한다. 이 틈이 인젝션과 우회를 부른다.

### 38.6.4 앨리어스 — 40장의 전제 (1)

**앨리어스(alias)** 는 필드의 응답 키를 원래 이름과 다른 것으로 바꾼다.

```graphql
query {
  pastes {
    myalias: title
  }
}
```

응답의 키가 `title`이 아니라 `myalias`가 된다. 앨리어스가 유용한 진짜 이유는 **같은 필드를 인자만 바꿔 여러 번 부를 때** 키 충돌을 피하기 때문이다. 다음처럼 `pastes`를 인자만 달리해 두 번 부르면 충돌 오류가 난다.

```graphql
query {
  pastes(public: false) { title }
  pastes(public: true)  { title }
}
```

서버는 "Fields \"pastes\" conflict because they have differing arguments. Use different aliases..."라고 답한다. 앨리어스로 각각 이름을 주면 해결된다.

```graphql
query {
  queryOne: pastes(public: false) { title }
  queryTwo: pastes(public: true)  { title }
}
```

응답은 `queryOne`과 `queryTwo` 두 키를 담는다. 각 키를 별개의 질의에 대한 별개의 응답으로 보면 된다. **바로 이 성질이 무기가 된다.** 앨리어스에는 개수 제한이 없으므로, 클라이언트는 같은 비싼 필드를 앨리어스만 바꿔 한 요청 안에서 수백·수천 번 부를 수 있다. 이것이 40장의 앨리어스 기반 DoS(앨리어스 과부하)와, 인증 통제를 무력화하는 배치 공격의 토대다(→ 40.3, 40.8). 로그인 뮤테이션을 앨리어스로 한 번에 수천 번 시도하면, 요청 하나로 무차별 대입이 된다 — 요청 빈도를 세는 레이트 리밋이 헛돈다. 여기서 앨리어스를 정확히 짚어 두는 이유가 이것이다.

### 38.6.5 프래그먼트

**프래그먼트(fragment)** 는 같은 필드 집합을 재사용하는 장치다. `fragment` 키워드로 정의하고 `on`으로 대상 객체 타입을 지정한 뒤, 스프레드 연산자(`...`)로 참조한다.

```graphql
query {
  pastes {
    ...CommonFields
  }
}

fragment CommonFields on PasteObject {
  title
  content
}
```

프래그먼트는 참조 횟수에 제한이 없다. 그리고 **프래그먼트끼리 서로를 참조하게 만들면 순환 프래그먼트(circular fragment)가 되어** DoS를 일으킨다(→ 40.2). 필드의 재귀 구조와 함께, 프래그먼트의 상호 참조가 순환 질의 DoS의 두 번째 통로다.

### 38.6.6 변수

**변수(variable)** 는 오퍼레이션에 인자 값을 넘기는 장치다. 오퍼레이션 이름 뒤에 `$이름: 타입`으로 선언하고, 타입 뒤의 `!`는 필수를 뜻한다.

```graphql
query publicPastes($status: Boolean!) {
  pastes(public: $status) {
    id
    title
    content
  }
}
```

값은 기본값을 주거나 JSON 객체로 따로 넘긴다(`{"status": false}`). 변수는 런타임의 값비싼 문자열 조립을 피하게 해 주며, 값을 여러 곳에 재사용하기 쉽게 한다. 인자와 마찬가지로 변수의 값도 클라이언트가 정하므로 인젝션 페이로드가 실릴 수 있다.

### 38.6.7 디렉티브 — 40장의 전제 (2)

**디렉티브(directive)** 는 필드를 "장식"해 그 동작 — 검증·처리·실행 방식 — 을 바꾼다. `@`로 시작하고 인자를 가질 수 있으며, 질의 수준과 스키마 수준 두 종류가 있다. 인자가 필드의 값을 조정한다면, 디렉티브는 조건에 따라 필드를 넣거나 빼는 더 높은 수준의 통제를 한다. 클라이언트는 서버가 정의한 디렉티브만 쓸 수 있다.

**표 38-4. 명세가 요구하는 기본 디렉티브 (BHGQL 표 3-2 기준)**

| 이름 | 설명 | 위치 |
|---|---|---|
| `@skip` | 조건이 참이면 필드를 응답에서 뺀다 | 질의 |
| `@include` | 조건이 참일 때만 필드를 포함한다 | 질의 |
| `@deprecated` | 스키마 구성 요소의 지원 중단을 표시 | 스키마 |
| `@specifiedBy` | 커스텀 스칼라의 명세 URL을 지정 | 스키마 |

`@skip`은 인자 `if`가 참이면 필드와 그 하위 필드를 통째로 응답에서 뺀다.

```graphql
query pasteDetails($pasteOnly: Boolean!) {
  pastes {
    id
    title
    content
    owner @skip(if: $pasteOnly) { name }
  }
}
```

`@include`는 그 반대다. `@deprecated`는 클라이언트가 질의에 쓰는 것이 아니라 스키마 정의에서 필드가 더는 지원되지 않음을 표시하며, 이 정보가 인트로스펙션 응답과 IDE 문서에 그대로 드러난다.

디렉티브의 힘이 곧 약점이다. **명세는 디렉티브의 일반 문법 외에는 거의 규정하지 않아, 구현체마다 자기 디렉티브를 자유롭게 설계한다.** 커스텀 디렉티브 — 예컨대 두 필드를 합치는 `@computed`나, 인가를 거는 스키마 수준 디렉티브 — 를 잘못 구현하면 새로운 공격 벡터가 열린다. 특히 인가를 디렉티브로 거는 구현에서, 수천 줄짜리 SDL 어딘가의 민감 필드에 인가 디렉티브를 빠뜨리면 그 필드가 그대로 노출된다(→ 24장, 38.7 인터페이스). 그리고 디렉티브도 개수 제한이 없어, 한 필드에 디렉티브를 대량으로 붙이는 디렉티브 과부하가 DoS가 된다(→ 40.3). 앨리어스와 함께, 디렉티브가 40장 DoS의 두 축이다.

> **이 절이 뒷받침하는 것**
>
> - 앨리어스의 무제한 반복 → **40.3** (앨리어스 과부하 DoS), **40.8** (배치로 인증 통제 무력화)
> - 필드의 재귀 구조·순환 프래그먼트 → **40.2** (순환 질의 DoS)
> - 디렉티브 과부하와 커스텀 디렉티브 결함 → **40.3** (디렉티브 과부하), **24장** (인가 디렉티브 누락)
> - 인자·변수의 클라이언트 통제 → **27.14**, **28.10** (인젝션 진입점)
> - 오퍼레이션 이름의 임의성 → **16.6** (로그 인젝션), **38.1** (로그 붕괴)

## 38.7 데이터 타입과 스키마

언어가 클라이언트의 어휘라면, 타입 시스템은 서버가 데이터를 정의하는 어휘다. GraphQL에는 여섯 종류의 타입이 있다 — 객체·스칼라·enum·union·인터페이스·input.

**객체(object).** 하나 이상의 필드를 묶어 도메인 객체를 정의한다. DVGA의 `PasteObject`를 보자.

```graphql
type PasteObject {
  id: ID!
  title: String
  content: String
  public: Boolean
  userAgent: String
  ipAddr: String
  ownerId: Int
  burn: Boolean
  owner: OwnerObject
}
```

`id` 뒤의 `!`는 이 필드가 널이 될 수 없음을 뜻한다(non-null wrapping type). `owner` 필드는 스칼라가 아니라 커스텀 객체 타입 `OwnerObject`를 가리킨다 — 즉 `Paste`에서 `Owner`로 가는 일방향 간선이다. 이 객체 간 간선이 38.6.3에서 본 재귀·순환의 구조적 토대다.

**스칼라(scalar).** `ID`·`Int`·`Float`·`String`·`Boolean` 같은 내장 값 타입. 구현체는 커스텀 스칼라(`DateTime`·`UUID` 등)를 정의할 수 있고, `@specifiedBy`로 그 명세 URL을 붙일 수 있다. 커스텀 스칼라가 값 검증(이메일·IP 형식 등)을 맡기도 하는데, **그 검증에 결함이 있으면 우회가 생긴다.** 실제로 파이썬 `ipaddress` 라이브러리의 취약점(CVE-2021-29921)이 IP 기반 접근 통제 우회로 이어진 사례가 있다.

**enum.** 정해진 값 목록에서 하나를 고르는 타입.

```graphql
enum UserSortEnum { ID EMAIL USERNAME DATE_JOINED }
```

`ID`로 사용자를 정렬하게 열어 두면, 공격자가 **시스템에서 가장 먼저 생성된 사용자** — 대개 슈퍼관리자나 내장 계정 — 를 짚어낼 수 있다. 정렬 옵션 하나가 고가치 표적을 알려 주는 것이다.

**union.** 여러 객체 타입 중 하나를 돌려준다. DVGA의 검색이 한 요청으로 사용자와 paste를 함께 찾는 데 쓴다.

```graphql
union SearchResults = UserObject | PasteObject
```

**인터페이스(interface).** 여러 객체가 공통으로 가져야 할 필드 목록을 규정한다. union이 서로 다른 필드를 허용하는 반면, 인터페이스는 같은 필드가 모든 구현 객체에 있기를 요구한다. 인터페이스는 인가가 허술한 곳에서 문제가 된다 — 인터페이스가 여러 객체에 필드를 강제하므로, 인가 디렉티브로 제대로 장식되지 않은 민감 필드가 의도치 않게 노출될 수 있다(→ 24장, 38.6.7).

**input.** 크고 복잡한 입력을 인자로 넘길 때 쓰는 타입. 객체 타입과 비슷하나 입력 전용이다. `createUser` 뮤테이션에 `UserInput!`을 통째로 넘기는 식이다. input 타입은 타입 검증을 우회하는 통로가 될 수 있는데, 커스텀 스칼라의 검증 결함과 겹치면 등록·로그인 폼 우회나 인젝션으로 이어진다.

스키마 전체는 이 타입들의 조합이며, 스키마가 곧 서버가 클라이언트에게 노출하는 공격 표면의 명세다. 그리고 그 스키마를 클라이언트가 통째로 읽어낼 수 있게 하는 기능이 다음 절의 인트로스펙션이다.

## 38.8 인트로스펙션

인트로스펙션(introspection)은 GraphQL의 가장 강력한 기능이자, 해커에게 금광이다. **클라이언트가 서버의 스키마 자체를 질의로 물어볼 수 있게 하는 내장 기능**이다. 질의·뮤테이션·서브스크립션·디렉티브·타입·필드 — 서버가 무엇을 지원하는지를 클라이언트가 직접 캐낼 수 있다. REST에 비유하면 Swagger(OpenAPI) 정의 파일을 통째로 건네받는 것과 같다.

인트로스펙션 시스템에는 일곱 개의 메타타입이 있다.

**표 38-5. 인트로스펙션 시스템 타입 (BHGQL 표 3-3 기준)**

| 타입 | 용도 |
|---|---|
| `__Schema` | 스키마 전체 정보 |
| `__Type` | 특정 타입의 정보 |
| `__TypeKind` | 타입의 종류(스칼라·객체·인터페이스·union·enum 등) |
| `__Field` | 객체·인터페이스 타입의 각 필드 정보 |
| `__InputValue` | 필드·디렉티브 인자 정보 |
| `__EnumValue` | enum의 가능한 값 |
| `__Directive` | 커스텀·내장 디렉티브 정보 |

`__schema` 메타필드로 모든 타입의 이름을 뽑는다.

```graphql
query {
  __schema {
    types { name }
  }
}
```

응답에는 `ID`·`String` 같은 내장 스칼라와 함께 `PasteObject`·`OwnerObject`·`UserObject` 같은 개발자 정의 타입이 섞여 나온다. 후자가 눈길을 끄는 것들이다. 관심 가는 타입은 `__type`으로 더 파고들어 그 안의 필드와 각 필드의 타입·종류를 캐낸다.

```graphql
query {
  __type(name: "PasteObject") {
    name
    kind
    fields {
      name
      type { name kind }
    }
  }
}
```

이 한 번의 질의로 `PasteObject`가 가진 필드 전부와 그 타입이 드러난다. 직원·내부용으로 의도된 민감 필드도 스키마에 포함되고 인트로스펙션이 켜져 있으면 그대로 공개된다. 인트로스펙션은 단순한 필드 발견을 넘어, 지원되는 오퍼레이션과 그 인자와 실행 방법까지 알려 준다 — 즉 악의적 오퍼레이션을 정확히 짜는 데 필요한 모든 정보를 준다.

**이 절은 인트로스펙션의 메커니즘까지만 다룬다.** 이 기능을 정찰에 실제로 활용하는 것 — InQL로 스키마를 자동 추출하고(→ 39.2, 39.4), 인트로스펙션이 꺼졌을 때 필드 제안과 필드 스터핑으로 스키마를 재구성하며(→ 39.5), Clairvoyance로 그 재구성을 자동화하는 것(→ 39.6) — 은 39장이 도구와 절차 수준까지 파고든다. 여기서 알아둘 것은 하나다. 인트로스펙션은 대부분의 구현체에서 **기본으로 켜져 있고**, 켜져 있으면 스키마 전체가 클라이언트에게 열린다는 것. 이것이 GraphQL 정보 노출의 첫 번째 통로다(→ 30.10).

## 38.9 검증과 실행

모든 GraphQL 요청은 실행되기 전에 스키마와 타입 시스템에 대조해 유효성을 검사받는다. 클라이언트가 어떤 필드를 요청하면, 검증 단계는 그 필드가 해당 타입에 실제로 존재하는지 스키마에서 확인한다. 존재하지 않거나 그 타입과 무관한 필드면 질의는 무효로 표시되고 실행되지 않는다.

명세는 여러 검증 유형을 규정한다 — 문서·오퍼레이션·필드·인자·프래그먼트·값·디렉티브·변수 검증. 위 예는 필드 검증이고, 디렉티브 검증은 클라이언트가 보낸 디렉티브가 스키마에 정의되고 구현체가 지원하는지를 본다. 검증을 통과한 요청만 실행 단계로 넘어가, 리졸버 함수(→ 38.1.1)가 각 필드의 응답을 채운다.

여기서 보안상 결정적인 사실이 있다. **구현체마다 명세를 해석하고 준수하는 정도가 크게 다르며, 특히 무효 요청에 응답하는 방식이 다르다.** 명세 자체가 이 여지를 허용한다 — "적합성 요구사항은 인지되는 결과가 동등한 한 어떤 방식으로든 충족될 수 있다"고 명시하기 때문이다. 예컨대 참조 구현 GraphQL.js를 기반으로 한 PHP 구현 graphql-php는 앨리어스에 `$` 같은 특수문자를 허용하는데, 이는 다른 많은 구현체와 다르다.

이 미세한 차이가 두 가지를 낳는다. 첫째, 무효 요청에 대한 응답 차이로 **구현체를 핑거프린팅**할 수 있다 — graphw00f가 하는 일이며, 39장이 다룬다. 둘째, 특정 구현체에서만 통하는 페이로드를 짤 수 있고, 한 구현체에서 발견된 취약점이 다른 구현체에는 없을 수 있다. 검증 단계의 철저함이 곧 그 서버의 보안 성숙도를 드러내므로, 구현체별 검증 차이를 분석하는 것이 정찰의 한 축이다. 이 비교를 정리한 것이 GraphQL Threat Matrix라는 프레임워크다.

## 38.10 GraphQL의 흔한 약점 지도 — Part V~VII 대응표

이 절이 이 장의 절정이다. 지금까지 GraphQL의 언어·타입·인트로스펙션·검증을 훑으며, 각 자리에서 이 책의 앞 장들을 계속 가리켰다. 이제 그 대응을 한자리에 모은다. **이 표가 이 부 전체의 논지를 한 화면에 담는다** — GraphQL의 약점은 거의 모두 이 책이 이미 다룬 실패 유형의 재현이며, 단 하나(DoS)만이 새롭다.

원서 BHGQL 3장은 GraphQL의 흔한 약점을 명세·구현 약점, DoS, 정보 노출, 인증·인가 결함, 인젝션으로 분류한다. 이 책은 그 분류를 앞 부들의 장 번호에 일대일로 붙인다.

**표 38-6. GraphQL 약점과 이 책 Part V~VII의 대응**

| 약점 부류 | GraphQL에서의 형태 | 대응 장 | 무엇이 같고 무엇이 다른가 |
|---|---|---|---|
| **인증** | 명세가 인증 지침을 주지 않아 제각각 구현. 앨리어스·배치로 로그인을 한 요청에 수천 번 시도 | **22장** | 같음: 약한 비밀번호·무차별 대입·로직 결함은 그대로. 다름: 앨리어스 배치가 요청 빈도 기반 레이트 리밋을 무력화(→ 40.8) |
| **세션** | 서브스크립션이 WebSocket 위에서 도는 장수명 세션. 토큰을 헤더로 나름 처리 | **23장** | 같음: 토큰 생성·처리·종료의 약점 동일. 다름: 서브스크립션 커넥션의 수명이 판정 시점을 압축(→ 37.7) |
| **인가 우회** | 단일 엔드포인트라 경로 기반 통제 불가. 인가는 필드·리졸버 단위로. 인터페이스·디렉티브에서 필드 인가 누락 | **24장** | 같음: 식별자 기반 기능·수직/수평 권한 상승 동일. 다름: 통제 지점이 URL에서 필드로 이동, 누락 지점이 스키마 전체로 확산 |
| **인젝션** | 리졸버가 백엔드 질의를 조립할 때 인자·변수가 SQL·OS 명령·요청에 흘러듦 | **27장, 28장** | 같음: SQL·NoSQL·OS 명령·SSRF의 성질 완전 동일. 다름: 진입점이 REST 파라미터에서 GraphQL 인자로 바뀔 뿐(→ 27.14, 28.10) |
| **정보 노출** | 오류 메시지가 백엔드를 흘림. 필드 제안·인트로스펙션이 스키마를 노출 | **30장** | 같음: 오류·스택 트레이스 노출 동일. 다름: GraphQL이 개발자 편의로 더 친절히 흘림, 필드 제안은 GraphQL 고유(→ 30.10) |
| **XSS** | GraphQL 응답의 데이터가 클라이언트에서 인코딩 없이 DOM에 삽입 | **32장** | 같음: 반사·저장·DOM XSS 성질 동일. 다름: 데이터 전달 경로가 GraphQL 응답일 뿐, XSS 자체는 그대로(→ 32.11) |
| **CSRF** | 단일 엔드포인트·쿠키 인증. 비 JSON 본문을 JSON으로 역해석, GET 질의 허용 | **33장** | 같음: 자동 첨부 쿠키 문제 동일. 다름: 콘텐츠 타입 우회와 GET 질의가 GraphQL 특유의 조건(→ 33.6) |
| **DoS** | 클라이언트가 질의 구조를 정함 — 순환 질의, 앨리어스·디렉티브 과부하, 배치 | **40장** (이 부에서 새로 다룸) | **이것만 새롭다.** 클라이언트가 서버 자원 소모를 제어. 앞의 여덟 부에 대응 장이 없다 |

이 표에서 읽어야 할 것은 두 가지다.

첫째, **DoS를 뺀 모든 행이 "같음"으로 시작한다.** 인증·세션·인가·인젝션·정보 노출·XSS·CSRF — 이 일곱 부류의 성질은 GraphQL에서 조금도 바뀌지 않았다. 바뀐 것은 진입점(인젝션), 통제 지점(인가), 전달 경로(XSS), 우회 조건(CSRF)이다. 병은 같고, GraphQL은 그 병이 드나드는 문의 모양만 바꿨다. 그래서 방어도 앞 장들의 것이 그대로 듣는다 — 파라미터화 질의, 출력 인코딩, 안티 CSRF 토큰, 필드 단위 인가, 오류 메시지 일반화. 같은 병에는 같은 처방이 듣는다.

둘째, **마지막 행만이 예외다.** DoS는 앞의 여덟 부에 대응할 장이 없다. 클라이언트가 질의의 형태와 깊이와 반복을 정한다는 GraphQL의 고유한 설계가, 서버 자원 소모의 통제권을 클라이언트에게 넘겼기 때문이다. 이것이 이 부가 새로 여는 유일한 장이며, 40장의 주제다. 38.6에서 앨리어스와 디렉티브를 특히 정확히 짚어 둔 것이 이 한 행을 위한 준비였다.

이 표를 손에 쥐고 나면, 39장과 40장은 이 지도의 각 구역을 실제로 걷는 일이 된다. 39장은 정찰과 정보 노출(표의 정보 노출 행)을 도구와 절차로 파고들고, 40장은 DoS(새 행)와 인증·인가(앞의 두 행)를 실습으로 다룬 뒤 공개된 취약점 사례로 이 부를 닫는다.

> **이 절이 뒷받침하는 것**
>
> - 인증·세션·인가 → **22·23·24장**의 결함이 GraphQL에서 재현
> - 인젝션 → **27.14**(SQL), **28.10**(OS 명령·SSRF)
> - 정보 노출·XSS·CSRF → **30.10**, **32.11**, **33.6**
> - DoS → **40장** (이 부의 유일한 새 주제)

## 이 장의 요약

- **GraphQL은 새로운 종류의 취약점을 거의 만들지 않았다.** 인증·세션·인가·인젝션·정보 노출·XSS·CSRF는 모두 이 책 Part V~VII이 다룬 실패 유형의 재현이다. 바뀐 것은 진입점·통제 지점·전달 경로일 뿐, 병의 성질과 처방은 그대로다.

- **단 하나가 정말 새롭다 — DoS.** 클라이언트가 질의의 구조·깊이·반복을 정한다는 GraphQL의 고유한 설계가 서버 자원 소모의 통제권을 클라이언트에게 넘겼다. 이것이 앞의 여덟 부에 대응 장이 없는 유일한 약점이며 40장의 주제다.

- **단일 엔드포인트에 POST가 HTTP 층위의 통제를 무력화한다.** 자원과 의도가 URL이 아니라 본문에 들어가면서, URL 기반 접근 제어(→ 24.1), WAF 룰(→ 12.11), 캐시 키(→ 14.8), 접근 로그(→ 16.1)가 모두 전제를 잃는다. 이것이 GraphQL이 만든 유일한 구조적 변화이자 이 장의 고유한 기여다.

- **응답이 거의 항상 `200 OK`다.** 인가 오류든 자원 없음이든 상태 코드가 성공을 가리키고, 오류는 본문의 `errors` 필드로 온다. 상태 코드에 의존하는 로그 분석·WAF·스캐너가 헛도는 이유이며, 그 `errors` 메시지 자체가 정보를 흘리는 통로다.

- **앨리어스와 디렉티브는 40장의 전제다.** 앨리어스는 개수 제한 없이 같은 필드를 반복시켜 배치 공격·앨리어스 과부하의 토대가 되고, 디렉티브도 과부하와 커스텀 결함의 자리가 된다. 필드의 재귀 구조와 순환 프래그먼트는 순환 질의 DoS를 낳는다.

- **인트로스펙션은 스키마 전체를 클라이언트에게 여는 기본 켜짐 기능이다.** REST의 OpenAPI 정의를 통째로 건네는 것과 같다. 메커니즘은 이 장에서, 정찰 활용은 39장에서 다룬다.

- **구현체마다 명세 준수가 다르다.** 무효 요청에 대한 응답 차이가 핑거프린팅의 근거이자 구현체별 페이로드의 근거다. 검증의 철저함이 그 서버의 보안 성숙도를 드러낸다.

## 이어지는 장

이 장은 GraphQL의 지형을 세우고 그 위에 공격 표면의 지도(표 38-6)를 그렸다. 남은 두 장은 그 지도의 구역들을 실제로 걷는다.

39장은 **정찰과 정보 노출**을 파고든다. 이 장이 메커니즘만 짚은 인트로스펙션을 InQL로 자동 추출하고, 그것이 꺼졌을 때 필드 제안·필드 스터핑으로 스키마를 재구성하며, graphw00f로 구현체를 핑거프린팅하고, 오류 메시지와 GET 질의로 데이터를 캐낸다. 표 38-6의 "정보 노출" 행 전체가 39장의 대상이다.

40장은 이 부가 새로 여는 **DoS**를 실습으로 다룬다. 이 장에서 준비해 둔 앨리어스·디렉티브·순환 질의·배치가 어떻게 서버를 무너뜨리는지, 그리고 깊이·복잡도 제한, 비용 분석, 질의 허용목록으로 어떻게 막는지를 본다. 이어 **인증·인가**를 실습하고, 공개된 취약점 사례로 이 부를 닫는다. 이 장이 남긴 질문 — 클라이언트가 응답의 형태를 정하는 API에서 서버는 무엇을 신뢰 경계로 삼는가 — 에 40장이 방어의 언어로 답한다.

그리고 이 부 전체가 던진 논지는 마지막 부(Part IX)로 이어진다. 같은 실패가 새 프로토콜에서 되풀이된다면, 문제는 프로토콜이 아니라 그 아래의 설계다. 왜 같은 것이 계속 깨지는가 — 그 물음이 41장에서 시작된다.

GraphQL의 정의·기원·핵심 구성 요소(질의 파서·스키마·리졸버), 스키마 정의 언어와 노드·간선, 질의·뮤테이션·서브스크립션 루트 타입, REST와의 오버페칭·언더페칭 비교(표 38-1은 BHGQL 표 1-1), HTTP 메서드·엔드포인트·상태 코드의 차이, `errors` 응답 형식, 접근 로그 패턴이 모두 원서에서 인용되었다. 38.1.2의 단일 엔드포인트가 HTTP 층위 통제(URL 접근 제어·WAF·캐시 키·접근 로그)를 무력화한다는 분석은, 원서가 흩어 서술한 관찰(WAF 회피, 로그 분석의 곤란)을 이 책의 12.11·14.8·16.1·24.1절과 결합해 재구성한 이 책의 편집이다. AWS AppSync `__type` 우회 사례는 BHGQL의 관련 서술을 30.10.3과 일관되게 인용했다.
>
> 38.4절: BHGQL 2장(Setting Up a Security Lab) 기준. Kali·VirtualBox·스냅샷의 보안 예방 지침, cURL·Altair 웹 클라이언트, Docker와 DVGA 배포, `systemHealth` 확인 질의, 그리고 표 38-2의 도구 목록(Burp Suite·InQL·Clairvoyance·graphw00f·GraphQL Cop·BatchQL·CrackQL·graphql-path-enum·Commix)이 원서에서 인용되었다. 일반적 랩 구축(가상화·격리·인터셉팅 프록시)은 0.4절과 중복되지 않도록 GraphQL 특화 부분만 남기고 역참조했다. 도구별 사용 장의 배정은 이 책의 목차에 맞춘 편집이다.
>
> 38.5~38.9절: BHGQL 3장(The GraphQL Attack Surface) 전체 기준. 공격 표면의 정의(건물 비유), 질의 해부(표 38-3은 BHGQL 표 3-1), 질의·뮤테이션·서브스크립션(WebSocket 핸드셰이크 포함), 오퍼레이션 이름·필드·인자·앨리어스·프래그먼트·변수·디렉티브(표 38-4는 BHGQL 표 3-2), 여섯 타입 시스템(객체·스칼라·enum·union·인터페이스·input)과 각 타입의 위험(enum 정렬로 슈퍼관리자 노출, 인터페이스의 인가 누락, CVE-2021-29921 IP 우회), 인트로스펙션 일곱 메타타입(표 38-5는 BHGQL 표 3-3)과 `__schema`·`__type` 질의, 검증·실행의 구현체별 차이와 graphql-php 앨리어스 특수문자, GraphQL Threat Matrix가 모두 원서에서 인용되었다. 예제는 DVGA를 그대로 쓰되 서점 맥락이 필요한 곳은 온라인 서점으로 옮겼다. 앨리어스·디렉티브를 40장 DoS의 전제로, 인자·변수를 27.14·28.10 인젝션의 진입점으로 명시적으로 연결한 것은 이 책의 편집이다. 인트로스펙션의 정찰 활용은 39장으로 넘겨 메커니즘만 남겼다.
>
> 38.10절: BHGQL 3장 "Common Weaknesses"의 분류(명세·구현 약점, DoS, 정보 노출, 인증·인가, 인젝션)를 근거로, 이 책 Part V~VII의 장 번호에 일대일 대응시킨 표 38-6은 이 책이 구성한 것이다. 각 행의 "같음/다름" 판정은 27.14·28.10·30.10·32.11·33.6절의 GraphQL 대응 서술과 일관되게 작성했다. "DoS만이 새롭다"는 논지는 원서가 반복해 강조한 "클라이언트가 질의 구조를 통제한다"는 관찰(BHGQL 1·3·5장)을 이 책의 부 구조에 맞춰 정식화한 것이다.
