# 44장. 도메인 프리미티브와 상태 무결성

> **이 장에서 다루는 것**
>
> - 유효하지 않은 인스턴스가 존재할 수 없는 타입 — 도메인 프리미티브가 인젝션·XSS·로직 결함을 동시에 막는 이유
> - 같은 문자열이 컨텍스트마다 다른 타입이어야 하는 이유, 그리고 외부에서 정의된 용어를 다시 정의하면 안 되는 이유
> - 비밀번호·카드 번호가 로그·직렬화·예외 메시지로 새는 네 갈래 경로를 하나의 패턴으로 닫는 법
> - 무인자 생성자에서 빌더 패턴까지 — 엔티티가 생성 시점부터 업무 규칙을 지키게 만드는 네 가지 구성 방식
> - 상태가 열다섯 개인 엔티티를 상태가 다섯 개인 엔티티 셋으로 쪼개는 설계, 그리고 그것이 왜 보안 조치인지

43장은 값이 유효하다는 것을 어떻게 보장하는지를 다뤘다. 불변성으로 값이 바뀌지 않게 하고, 계약으로 책임의 소재를 코드에 적고, 다섯 단계 검증으로 신뢰할 수 없는 입력을 걸러냈다. 그 장은 하나의 문장으로 닫혔다. **경계에서, 정해진 순서로 검증하고, 통과한 값을 타입으로 만든다.**

이 장은 그 문장의 마지막 절을 담당한다. **통과한 값을 타입으로 만든다** — 그 타입의 이름이 도메인 프리미티브(domain primitive)다. 42.5절이 값 객체(value object)를 소개했을 때, 그것은 도메인 모델링의 어휘였다. 43.3절이 생성자에서 불변식을 강제하는 법을 보였을 때, 그것은 코드의 문법이었다. 44.1절은 그 둘을 합친다. 값 객체이되, 생성 시점에 불변식이 강제되어 **유효하지 않은 인스턴스가 아예 존재할 수 없는** 값. 그런 타입이 존재한다는 사실 자체가 검증이 끝났다는 증거가 된다.

이 장이 받아야 할 청구서는 43장 하나가 아니다. 27.10절은 "인젝션을 막는 가장 깊은 방법은 위험한 문자를 걸러내는 것이 아니라 위험한 값이 존재할 수 없는 타입 구조를 만드는 것"이라고 선언하고 상세를 이 장으로 넘겼다. 32.10절은 출력 컨텍스트별 인코딩의 근본 문제 — 문자열이 컨텍스트를 잃는다는 것 — 를 진단하고 답을 이 장에 맡겼다. 16.6절과 22.9절은 로그 인젝션과 비밀 취급의 처방으로 읽기 1회 객체를 인용했고, 31.9절은 Part VI 전체를 "복잡도가 곧 공격 표면"이라는 명제로 닫으며 네 가지 설계 패턴을 이 장의 마지막 절에 예약했다. 42장은 엔티티·값 객체·바운디드 컨텍스트라는 어휘를 남기며, 그 어휘가 코드가 되는 자리로 이 장을 지목했다.

그래서 이 장은 두 부분으로 나뉜다. **앞의 절반(44.1~44.7)은 값의 문제**다. 가장 작은 구성 요소를 어떻게 만들고, 그것을 어떻게 라이브러리로 조직하고, API의 경계에 어떻게 배치하고, 민감한 값은 어떻게 다르게 다루는가. **뒤의 절반(44.8~44.10)은 상태의 문제**다. 값은 불변으로 만들 수 있지만 엔티티는 정의상 변한다. 주문은 담기고, 결제되고, 배송된다. 바뀌어야 하는 것의 무결성을 어떻게 지키는가.

코드 예제는 자바로 쓴다. 도메인은 계속해서 **온라인 서점**이다.

## 44.1 도메인 프리미티브와 불변식 — 가장 작은 구성 요소

### 44.1.1 값 객체에 조건 하나를 더하면

42.5절에서 값 객체의 성질 두 가지를 확인했다. **불변이고, 개념적 전체(conceptual whole)를 이룬다.** 금액은 숫자와 통화가 함께 있어야 의미가 있고, 한 번 만들어진 "1만 2천 원"은 다른 금액으로 변하지 않는다.

도메인 프리미티브는 이 개념을 보안 관점으로 조인 것이다. 조인 지점은 두 곳이다.

**첫째, 불변식(invariant)의 존재를 요구한다.** 값 객체는 불변식을 가질 수도 있고 안 가질 수도 있다. 도메인 프리미티브는 **반드시 가져야 한다.** 그 개념이 무엇인지만이 아니라 **무엇이 아닌지**까지 정의하는 데 노력을 들이면, 그 개념에 대해 훨씬 깊은 통찰을 얻게 된다. 그 통찰을 불변식으로 옮긴다.

**둘째, 그 불변식을 생성 시점에 강제한다.** 나중에 검사하는 것이 아니다. 어딘가의 서비스가 검사해 주는 것도 아니다. 생성자가 검사하고, 통과하지 못하면 객체가 만들어지지 않는다.

이 두 조건을 합치면 결론이 하나 나온다.

> **NOTE** 정의가 너무나 정확해서, 존재한다는 사실만으로 자신의 유효성을 증명하는 값 객체가 **도메인 프리미티브**다.

이 문장을 뒤집으면 더 유용해진다. **유효하지 않으면 존재할 수 없다.** `ISBN` 타입의 참조를 손에 들고 있다면, 그 값이 열 자리인지, 허용된 문자만 쓰는지, 체크섬이 맞는지 다시 물을 필요가 없다. 물었어야 한다면 그 객체는 애초에 만들어지지 않았을 것이기 때문이다.

여기에 금지 조항 하나가 따라붙는다.

> **NOTE** 도메인 모델의 어떤 개념도 언어 원시 타입(language primitive)이나 범용 타입(generic type)으로 표현하지 않는다. `null`도 마찬가지다. 각 개념은 도메인 프리미티브로 모델링되어야 한다. 그래야 그 값이 코드를 돌아다닐 때 **의미를 함께 지니고**, 자신의 불변식을 스스로 지킬 수 있다.

"프리미티브"라는 이름 때문에 오해하기 쉬운데, 도메인 프리미티브가 단순해야 한다는 뜻은 아니다. 다른 도메인 프리미티브를 품을 수 있고, 사소하지 않은 로직을 담을 수 있다. 프리미티브라는 말은 **크기가 작다**는 뜻이 아니라 **더 쪼갤 필요가 없는 도메인의 최소 단위**라는 뜻이다.

### 44.1.2 수량은 정수가 아니다

온라인 서점에 **수량(quantity)** 이라는 개념이 있다. 고객이 어떤 책을 몇 권 사려는지를 나타낸다. 수량은 숫자다. 그래서 `int`로 쓰고 싶어진다.

여기서 멈추고, 도메인 전문가와 이야기를 한다. 이 도메인에서 **유효한 수량이란 무엇인가.**

- 0은 유효하지 않다. 고객이 0권을 사려 한다면, 그 주문 항목은 존재해서는 안 된다.
- 음수는 유효하지 않다. 산 것을 되사지 않는(un-buy) 것이고, 반품은 별도 절차로 처리된다.
- 상한이 있다. 이 서점의 온라인 채널은 한 항목당 200권까지만 처리한다. 그보다 큰 주문은 극히 드물고, 발생하면 창고·물류의 별도 확인이 필요하므로 영업 담당자와의 직접 접촉으로 처리한다.

이 대화의 결과가 **1 이상 200 이하의 정수**다. 여기서 중요한 것은 200이라는 숫자 자체가 아니라, **그 숫자가 코드가 아니라 대화에서 나왔다는 사실**이다(→ 42.9). 42장이 말한 대로, `Quantity` 클래스를 만드는 일은 쉽다. 어려운 것은 상한이 얼마인지 알아내는 일이다.

```java
import static org.apache.commons.lang3.Validate.inclusiveBetween;
import static org.apache.commons.lang3.Validate.notNull;

public final class Quantity {

    private final int value;                       // 정수 값

    public Quantity(final int value) {
        inclusiveBetween(1, 200, value);           // 생성 시점에 불변식을 강제
        this.value = value;
    }

    public int value() {
        return value;
    }

    public Quantity add(final Quantity addend) {   // 도메인 연산을 캡슐화
        notNull(addend);
        return new Quantity(value + addend.value);
    }

    public boolean greaterOrEqualTo(final Quantity other) {
        notNull(other);
        return value >= other.value;
    }

    // equals() hashCode() toString() ...
}
```

*리스팅 44-1. `Quantity` 도메인 프리미티브 (SBD 리스팅 5.1 기준, 서점 맥락으로 확장)*

이 코드에서 읽어야 할 것이 세 가지다.

**첫째, `final` 클래스이고 `final` 필드다.** 서브클래싱으로 불변식을 우회할 수 없고, 생성 후 값이 바뀌지 않는다. 43.1절이 불변성으로 닫은 세 가지 변조 경로가 여기서 닫힌다.

**둘째, 생성자가 유일한 진입점이다.** `inclusiveBetween`이 실패하면 예외가 던져지고 객체는 만들어지지 않는다. 절반쯤 만들어진 `Quantity`는 존재하지 않는다. 43.3절이 "생성자는 특별하다"고 한 이유가 이것이다 — 객체는 한 곳에서 만들어져 여러 곳에서 쓰이므로, 생성 시점의 검사 한 번이 사용 시점의 검사 수백 번을 대신한다.

**셋째, 도메인 연산이 타입 안에 있다.** `add`가 왜 `Quantity` 안에 있어야 하는가. 두 수량을 더하는 연산은 수량의 도메인 규칙을 알아야 한다 — 이제 다루는 것은 평범한 정수가 아니다. 만약 `add`를 `Functions`라는 유틸리티 클래스에 두면, `Quantity`의 규칙이 바뀔 때 그 유틸리티도 함께 고쳐야 한다는 것을 기억해야 한다. **기억하지 못할 것이고, 그렇게 찾기 어려운 버그가 들어온다.** 개념에서 멀어질수록 그 개념에 대한 상세한 지식을 기대할 수 없다. 그러니 도메인 연산은 도메인 프리미티브 안에 둔다.

29.3절에서 본 "안티북" 사건 — 고객이 음수 수량을 보내 스스로에게 할인 쿠폰을 발행한 사건 — 은 이 클래스 하나로 성립하지 않는다. 주목할 것은 **명시적 대응책이 없다는 점**이다. 음수 수량 필터도, 입력 검증 미들웨어도, WAF 규칙도 없다. 그저 수량이라는 개념을 정확하게 모델링했을 뿐인데 취약점 하나가 사라졌다.

### 44.1.3 존재가 증거가 된다 — 왜 세 종류의 취약점이 동시에 닫히는가

도메인 프리미티브가 특정 공격 하나를 겨냥한 기법이 아니라는 점이 중요하다. 그것은 **코드가 값에 대해 무엇을 아는가**를 바꾸는 것이고, 그래서 서로 다른 계보의 취약점이 함께 닫힌다.

**인젝션(→ 27장).** SQL 인젝션이 성립하는 전제는 "질의를 만드는 코드가 자기가 받은 문자열이 무엇인지 모른다"는 것이다. `findByISBN(String isbn)`은 인자가 ISBN인지 `' OR '1'='1`인지 알 수 없다. `findByISBN(ISBN isbn)`은 안다. `ISBN`의 생성자가 `[0-9]{9}[0-9X]` 패턴을 강제했으므로, 인용부호도 공백도 주석 기호도 그 타입 안에 존재할 수 없다. 27.10절이 "위험한 값이 존재할 수 없는 타입 구조"라고 부른 것이 이것이다. 파라미터화 질의(→ 27.9)가 **질의를 만드는 순간**을 방어한다면, 도메인 프리미티브는 **값이 만들어지는 순간**을 방어한다. 둘은 경쟁하지 않고 겹친다.

**XSS(→ 32장).** 32.10절이 진단한 문제는 "문자열이 컨텍스트를 잃는다"는 것이었다. 출력 계층이 `String`을 받으면 그것이 이미 인코딩된 것인지, 신뢰할 수 있는 것인지, HTML 컨텍스트용인지 JavaScript 컨텍스트용인지 알 수 없다. 그래서 전부 인코딩하거나(때로 이중 인코딩) 아무것도 하지 않는다(취약). `CustomerName` 타입을 받으면 그 타입이 허용 문자 집합을 이미 강제했고, 출력 계층은 타입이 지시하는 대로 정확히 처리할 수 있다. **컨텍스트가 개발자의 기억에서 타입 시스템으로 옮겨 간다.**

**로직 결함(→ 29장).** 로직 결함은 문법적으로 완벽한 요청이 업무 규칙을 위반할 때 생긴다. 스캐너가 찾지 못하는 이유가 이것이다(→ 29.1) — 페이로드가 이상하지 않기 때문이다. `-1`은 완벽하게 유효한 정수다. 도메인 프리미티브는 **업무 규칙을 타입의 존재 조건으로 승격**시킨다. 규칙 위반은 요청 처리 중의 판단 실패가 아니라 객체 생성 실패가 되고, 실패는 훨씬 이른 시점에, 훨씬 시끄럽게 일어난다.

**표 44-1. 도메인 프리미티브가 세 계보의 취약점을 동시에 닫는 구조**

| 취약점 계보 | 성립 전제 | 도메인 프리미티브가 없애는 전제 | 이 책의 관련 절 |
|---|---|---|---|
| 인젝션 | 해석기가 받는 문자열의 정체를 코드가 모른다 | 타입이 허용 문자 집합을 이미 강제했다 | 27.10, 27.9 |
| XSS·인코딩 결함 | 출력 계층이 값의 컨텍스트를 모른다 | 타입이 컨텍스트를 기억한다 | 32.10, 31.2 |
| 로직 결함 | 문법적으로 유효한 값이 업무 규칙을 위반한다 | 업무 규칙이 타입의 존재 조건이 되었다 | 29.1, 29.3 |
| 로그 인젝션·데이터 누출 | 검증되지 않은 문자열이 로그 구조를 바꾼다 | 타입 없이는 로그에 넣을 수 없다 | 16.6, 47.3 |

이 표의 오른쪽에서 왼쪽을 보면, 네 줄이 하나의 문장으로 수렴한다. **값이 존재한다는 사실 자체가 그 값이 무엇인지를 말해 주도록 만드는 것.** 43장이 세 축(불변성·계약·검증)을 세운 이유가 이 문장 하나를 성립시키기 위해서였다.

42.2절이 "모델은 단순화이며, 동시에 엄격하다"고 했을 때, 그 엄격함이 무엇을 뜻하는지도 여기서 분명해진다. **모델이 허용하지 않는 상태는 코드에서 표현될 수 없어야 한다.** 수량이 1에서 200 사이라는 것이 모델의 규칙이라면, `-1`을 담은 수량 객체는 만들어질 수 없어야 한다. 그 엄격함이 문서나 주석이 아니라 생성자에 있을 때에만, 모델의 단순화가 보안의 자산이 된다. 그렇지 않으면 모델은 코드가 실제로 하는 일과 무관한 그림이 되고, 그 간극이 곧 로직 결함이 서식하는 자리다.

### 44.1.4 43.5절의 결론을 이어받으며

43.5.5절은 이 책의 원칙을 이렇게 정식화했다. **경계에서, 정해진 순서로 검증하고, 통과한 값을 타입으로 만든다.** 세 부분이 각각 다른 것을 막는다는 것도 그곳에서 확인했다.

이제 세 번째 부분의 정체를 말할 수 있다. **타입은 검증의 결과를 코드에 기록하는 수단이다.**

43.4.8절에서 이 문제를 이렇게 제기했다. 다섯 단계 검증을 다 통과한 문자열이 있다. 그 사실을 어떻게 코드에 남기는가. 변수 이름을 `validatedIsbn`으로 짓는 것은 기록이 아니라 주석이고, 주석은 강제되지 않는다. `boolean isValidated` 플래그를 함께 들고 다니는 것은 두 값이 어긋날 여지를 만든다. 검증 여부를 문서에 적는 것은 코드가 읽지 않는다.

**타입은 컴파일러가 읽는다.** `ISBN`을 받는 메서드에 `String`을 넘기면 컴파일되지 않는다. 검증을 잊었다는 사실이 런타임 취약점이 아니라 컴파일 오류로 나타난다. 43.7절이 진단한 "흩어진 방어적 검사"의 근본 문제 — 어디서도 무엇을 보장하는지 알 수 없다는 것 — 가 여기서 구조적으로 해결된다. 보장의 목록이 곧 타입의 목록이 되기 때문이다.

> **이 책의 범위를 넘어서**
>
> 도메인 프리미티브를 언어 차원에서 더 싸게 만들려는 시도가 여럿 있다. 값 하나를 감싸는 클래스에 런타임 할당 비용을 물리지 않는 인라인 값 타입, 기존 타입에 새 이름과 제약만 붙이는 뉴타입(newtype) 관용구, 술어를 타입 수준으로 끌어올리는 정제 타입(refinement type), 그리고 불변 데이터와 전면 함수(total function)를 기본값으로 삼는 함수형 스타일이 그것이다. 이 책은 특정 언어의 최신 타입 시스템 기능이나 함수형 패러다임 논쟁을 다루지 않는다. 여기서 다루는 것은 어떤 주류 객체지향 언어에서도 오늘 당장 쓸 수 있는 최소 형태 — 불변 필드, 생성자에서의 불변식 검사, `final` 클래스 — 이고, 이 최소 형태만으로도 이 장이 주장하는 보안 효과는 전부 얻어진다. 언어가 더 나은 도구를 제공한다면 같은 설계를 더 싸게 표현할 수 있을 뿐이다.

> **이 절이 뒷받침하는 것**
>
> - 통과한 값을 타입으로 만든다 → **43.5** (경계 검증과 검증 순서의 종합)이 요구한 세 번째 부분
> - 값 객체에 불변식과 생성 시점 강제를 더한 것 → **42.5** (모델의 구성 요소), **43.3** (생성자에서 불변식 유지하기)
> - 위험한 값이 존재할 수 없는 타입 구조 → **27.10** (인젝션의 구조적 차단)이 예고한 상세
> - 타입이 컨텍스트를 기억한다 → **32.10** (출력 컨텍스트별 인코딩), **44.2**

## 44.2 컨텍스트 경계가 의미를 정의한다

### 44.2.1 유효한 이메일 주소란 무엇인가

도메인 프리미티브는 값 객체와 마찬가지로 **정체성이 아니라 값으로 정의된다.** 같은 타입에 같은 값을 가진 두 도메인 프리미티브는 서로 교환 가능하다. 엔티티나 애그리게이트의 범주에 들어가지 않는 온갖 도메인 개념을 표현하는 데 적합한 이유가 이것이다.

그런데 어떤 개념을 도메인 프리미티브로 모델링할 때 반드시 붙잡아야 할 것이 있다. **그 개념이 지금 이 도메인에서 무엇을 뜻하는지로, 정확히 그것으로 정의해야 한다는 것이다.**

온라인 서점이 회원에게 서점 도메인의 이메일 주소를 발급한다고 하자. 회원이 `@` 왼쪽 부분(local part)을 고르면 `jane.doe@example-books.com` 같은 주소가 만들어지고, 그 주소로 메시지를 주고받는다. 모델링을 하다 보면 이메일 주소가 도메인 프리미티브의 전형적인 예임을 알게 된다. 값으로 정의되고, 유효성을 판정할 제약을 세울 수 있다.

여기서 첫 번째 충동은 **이메일 주소의 공식 정의를 찾아보는 것**이다. RFC를 열고, 허용되는 문자와 인용 문자열과 주석 문법을 확인한다. 그렇게 만든 검증은 기술적으로 옳다. RFC의 요구를 정확히 충족한다.

**그러나 그것이 이 도메인에서 유효한 이메일 주소인지는 별개의 문제다.**

엔지니어에게는 이 말이 낯설 수 있다. 그러나 우리가 지금 붙잡으려는 것은 **특정 도메인 안에서 개념이 갖는 의미**이지, 다른 어떤 맥락 — 예컨대 국제 표준이라는 맥락 — 에서 그것이 무엇을 뜻하는지가 아니다. 서점의 도메인은 이메일 주소를 대소문자 구분 없는 것으로 정의할 수 있다. 사용자가 무엇을 입력하든 소문자로 변환한다. 더 나아가 허용 문자를 ASCII 알파벳과 숫자와 점 — `[a-z0-9.]` — 으로만 제한할 수도 있다. 기술 명세에서 벗어난 것이지만, **이 도메인의 맥락에서는 타당한 선택이다.**

```
        RFC가 정의한 것            당신이 정의한 것
        ┌──────────────┐          ┌──────────────┐
        │              │          │              │
        │    Email     │          │    Email     │
        │              │          │              │
        └──────────────┘          └──────────────┘

          외부 컨텍스트              당신의 컨텍스트
```

*그림 44-1. 용어의 의미는 주어진 컨텍스트의 경계 안에서 정의된다 (SBD 그림 5.1 기준)*

이것이 42.6절의 **바운디드 컨텍스트**가 코드에 나타나는 방식이다. 42장에서 바운디드 컨텍스트는 모델과 언어가 통용되는 범위였다. 여기서 그것은 **불변식이 통용되는 범위**가 된다. 같은 이름의 개념이 컨텍스트 밖에도 존재하지만, 안에서의 정의가 밖에서의 정의와 같을 의무는 없다.

### 44.2.2 ISBN은 다시 정의하지 않는다

반대 방향의 사례가 필요하다. 모든 외부 정의를 무시해도 좋다는 뜻이 아니기 때문이다.

**ISBN은 ISO가 정의한다.** 이것을 서점의 도메인이 임의로 재정의하면 혼란과 오해와 버그가 생긴다. 이런 종류의 미묘한 의미 차이는 보안 문제의 흔한 원인이며, 특히 **다른 시스템이나 다른 도메인 컨텍스트와 상호작용할 때** 그렇다. 서점의 `ISBN`이 유통사의 `ISBN`과 다른 것을 뜻한다면, 두 시스템이 주고받는 모든 메시지에 해석의 틈이 생긴다.

```
                 같은 의미
        ┌──────────────┐          ┌──────────────┐
        │              │          │              │
        │     ISBN     │ ═══════  │     ISBN     │
        │              │          │              │
        └──────────────┘          └──────────────┘

          외부 컨텍스트              당신의 컨텍스트
```

*그림 44-2. 외부에서 정의된 용어를 의미를 바꾸지 않고 사용하기 (SBD 그림 5.2 기준)*

문제는 이렇게 시작된다. 서점 시스템이 한동안 잘 돌아간 뒤, **아직 ISBN을 받지 못한 책**을 식별하고 다룰 방법이 필요해진다. 자비 출판 예정 도서, 사전 계약된 미출간 원고, 서점이 자체 제작한 굿즈 같은 것들이다.

한 가지 접근은 **ISBN이라는 용어를 재정의하는 것**이다. 실제 ISBN만이 아니라 내부적으로 부여한 식별자도 포함하도록 넓히고, 매직 접두사 같은 것으로 둘을 구분한다. 이것이 위험하다. ISO 표준을 재정의하는 순간, `ISBN`이라는 타입은 더 이상 자신의 정확한 불변식을 지킬 수 없고 — 체크섬 검증이 접두사 있는 값에는 적용되지 않는다 — 외부 시스템과의 모든 접점에서 "이 ISBN이 진짜 ISBN인가"를 다시 물어야 한다. **정확했던 타입이 부정확해졌고, 부정확한 타입은 검증의 증거가 되지 못한다.**

올바른 접근은 **새 용어를 도입하는 것**이다.

```
                                  ┌─────────────────────────┐
        ┌──────────────┐          │        BookId           │
        │              │          │   ┌──────┐  ┌────────┐  │
        │     ISBN     │ ═══════  │   │ ISBN │  │Unpub-  │  │
        │              │          │   │      │  │lished  │  │
        └──────────────┘          │   └──────┘  │BookNo  │  │
                                  │             └────────┘  │
          외부 컨텍스트            └─────────────────────────┘
                                        당신의 컨텍스트
```

*그림 44-3. 기존 용어를 재정의하는 대신 새 용어를 도입하기 (SBD 그림 5.3 기준)*

`BookId`가 책을 식별하고, 그것은 `ISBN`이거나 `UnpublishedBookNumber`다. `ISBN`은 ISO 정의 그대로의 정확한 불변식 — 열 자리, 마지막 자리는 숫자 또는 X, 체크섬 일치 — 을 유지한 채 도메인 프리미티브로 남는다. `UnpublishedBookNumber`는 서점 내부에서만 의미를 갖는 별개의 개념으로, 자기만의 불변식을 갖는다.

일반 규칙은 이렇다. **잘 알려진 용어를 재정의하고 싶어지는 상황은, 대개 그 용어가 지금 컨텍스트에서 두 가지 이상을 가리키고 있다는 신호다.** 그럴 때는 용어를 둘로 쪼개거나 완전히 새로운 용어를 만든다. 새 용어는 이 컨텍스트에 고유하므로 오해의 여지가 없고, 왜 표준과 다른 불변식이 적용되는지가 이름 자체로 설명된다. 원래 용어는 선명한 정의를 지킨 채 도메인 프리미티브로 남는다. **모델의 정확성을 잃지 않으면서 도메인의 필요를 충족한 것이다.**

### 44.2.3 같은 문자열, 다른 타입

이 절의 논지를 가장 실용적인 형태로 옮기면 이렇다. **문자열이 같아 보인다는 것은 타입이 같아야 한다는 뜻이 아니다.**

43.5.4절이 이 문제를 다른 방향에서 세웠다. **검증됨은 값 하나가 아니라 값과 컨텍스트의 쌍이 갖는 속성이다.** 형식에 대한 보장은 컨텍스트를 넘어도 유지되지만 — 열 자리 숫자는 어디서나 열 자리 숫자다 — 의미에 대한 보장은 그렇지 않다. 어떤 컨텍스트에서 안전한 값이 다른 컨텍스트에서 위험할 수 있다.

도메인 프리미티브는 이 사실에 대한 답이다. **컨텍스트가 다르면 타입이 다르다.**

서점에서 문자열로 표현될 법한 값들을 나열해 보자.

**표 44-2. 온라인 서점에서 "그냥 문자열"로 보이는 값들과 그 컨텍스트**

| 개념 | 순진한 표현 | 도메인 프리미티브 | 불변식 | 이 타입이 없으면 |
|---|---|---|---|---|
| 도서 식별자 | `String isbn` | `ISBN` | 10자리, `[0-9]{9}[0-9X]`, 체크섬 | SQL 인젝션(→ 27.2), 잘못된 책 조회 |
| 검색어 | `String query` | `SearchTerm` | 길이 상한, 제어문자 금지 | 저장형 XSS(→ 32.6), 로그 인젝션(→ 16.6) |
| 도서 제목(표시용) | `String title` | `BookTitle` | 길이 상한, 정규화된 유니코드 | 인코딩 결함(→ 31.2), 이중 인코딩 |
| 회원 식별자 | `String memberId` | `MemberId` | 정해진 형식, 존재하는 회원 | 접근 통제 우회(→ 24장) |
| 수량 | `int qty` | `Quantity` | 1~200 | 로직 결함(→ 29.3) |
| 금액 | `BigDecimal amount` | `Money` | 통화 + 금액, 음수 금지 | 통화 혼동(→ 47.6), 가격 조작 |
| 내부 서버 주소 | `InetAddress addr` | `InternalAddress` | 내부 대역만 | 감사 로그 외부 유출(→ 44.3) |
| 비밀번호 | `String password` | `Password`(읽기 1회) | 길이·문자 규칙, 1회 소비 | 로그·직렬화 누출(→ 44.5) |

이 표의 왼쪽 열만 보면 여덟 개 중 다섯 개가 `String`이다. **타입 시스템의 관점에서 그 다섯은 완전히 동일하고, 서로 교환 가능하며, 어느 것을 어디에 넘겨도 컴파일된다.** 검색어를 ISBN 조회에, 도서 제목을 회원 식별자 자리에 넘겨도 컴파일러는 침묵한다. 오른쪽 열로 옮기면 그 교환 가능성이 사라진다. 이것이 타입으로 컨텍스트를 표현한다는 말의 구체적 의미다.

한 가지 더. 같은 개념이라도 **컨텍스트를 넘으면 다시 타입을 통과해야 한다.** 서점의 판매 컨텍스트에서 만들어진 `MemberId`가 물류 컨텍스트로 넘어갈 때, 물류 컨텍스트는 그 값을 자기 컨텍스트의 `RecipientId`로 다시 만든다. 두 컨텍스트가 우연히 같은 형식을 쓴다 해도, 그것은 두 컨텍스트가 같은 규칙을 영원히 공유하겠다는 약속이 아니다. 42.7절의 컨텍스트 맵이 이 경계를 그리는 도구였다면, 경계에서의 타입 변환이 그 그림을 코드로 옮긴 것이다.

> **이 절이 뒷받침하는 것**
>
> - 불변식이 통용되는 범위로서의 컨텍스트 → **42.6** (바운디드 컨텍스트), **42.7** (컨텍스트 맵)
> - 검증됨은 값과 컨텍스트의 쌍이 갖는 속성 → **43.5.4**가 제기한 문제의 코드 수준 답
> - 타입이 컨텍스트를 기억한다 → **32.10** (출력 컨텍스트별 인코딩과 도메인 타입)
> - 외부 정의를 재정의하지 않기 → **47.8** (각 서비스는 하나의 바운디드 컨텍스트다)

## 44.3 도메인 프리미티브 라이브러리 구축과 API 강화

### 44.3.1 라이브러리는 유틸리티 모음이 아니다

도메인 프리미티브를 도구 상자에 넣었으니, 이제 **가능한 한 많이 쓰는 것**이 다음 단계다. 이것들은 가장 작은 구성 요소이고 도메인 모델의 기반이므로, 모델의 거의 모든 개념이 하나 이상의 도메인 프리미티브 위에 서게 된다. 모델링이 끝나면 도메인 프리미티브의 모음이 손에 남는다. 그것을 **도메인 프리미티브 라이브러리**로 볼 수 있다.

여기서 한 가지를 분명히 해야 한다. **이 라이브러리는 범용 유틸리티 클래스와 메서드의 모음이 아니다.** `StringUtils`나 `ValidationHelper` 같은 것이 아니다. 그것은 **잘 정의된, 유비쿼터스한 도메인 개념의 집합**이다.

이 구분이 실무에서 갖는 무게를 42.4절이 미리 짚었다. **같은 이름으로 불리는 것만 라이브러리에 모을 수 있다.** 어떤 팀은 "수량"이라 부르고 다른 팀은 "개수"라 부르고 코드에서는 `cnt`라고 쓴다면, 그 개념을 담을 타입은 세 개가 되거나 하나도 없게 된다. 유비쿼터스 언어가 도메인 프리미티브 라이브러리의 전제인 이유다. 이름이 흩어지면 규칙을 붙일 자리가 흩어진다.

도메인 프리미티브는 **개발자의 인지 부하를 낮춘다.** 쓰기 위해 내부 동작을 이해할 필요가 없기 때문이다. 그것들이 항상 유효한 값과 잘 정의된 개념을 표현한다는 확신을 갖고 안심하고 쓸 수 있다. 유효하지 않으면 존재하지 않는다. 이것은 또한 **안전하게 쓸 수 있는지 확인하려고 데이터를 계속 재검증할 필요를 없앤다.** 도메인 안에 정의된 것이라면 신뢰하고 자유롭게 쓴다.

43.7절이 진단한 병 — 자기 자신을 신뢰하지 않는 코드, 같은 값을 열두 번 검사하는 코드 — 의 처방이 여기 있다. **재검증이 사라지는 이유는 검사를 줄이기로 결심해서가 아니라, 검사가 이미 끝났다는 것을 타입이 말해 주기 때문이다.**

### 44.3.2 API 강화 — 서명이 검증이다

프로그래밍 API에서는 항상 도메인 프리미티브를 쓰려 노력해야 한다. 모든 인자와 반환값이 정의상 유효하다면, **추가 노력 없이 코드베이스의 모든 메서드가 입력 검증과 출력 검증을 갖게 된다.** 도메인 설계를 이렇게 쓰면 극도로 탄력적이고 견고한 코드를 만들 수 있다. 그 부수 효과로 유효하지 않은 입력 데이터로 인한 보안 취약점의 수가 급격히 줄어든다.

구체적인 예로 보자. 서점 시스템의 감사 로그를 중앙 감사 로그 저장소로 보내는 작업을 맡았다고 하자. 감사 로그는 민감한 데이터를 담고 있고, 지정된 장소로 보내져 제대로 저장·보호되는 것이 중요하다. 엉뚱한 곳으로 보내면 업무에 심각한 악영향이 생긴다.

현재 로그를 받아 주어진 서버 주소의 로그 저장소로 보내는 메서드를 만들면 이렇게 될 것이다.

```java
void sendAuditLogsToServerAt(java.net.InetAddress serverAddress);
```

**이 서명의 문제는 어떤 IP 주소든 로그의 목적지가 될 수 있다는 것이다.** 로그를 보내기 전에 주소를 제대로 검증하지 못하면, 안전하지 않은 위치로 로그를 보내 민감한 데이터를 노출할 수 있다.

대신 `InternalAddress`라는 도메인 프리미티브를 정의해 내부 IP 주소가 무엇인지를 엄격하게 규정하고, 그것을 메서드의 입력 파라미터 타입으로 쓴다.

```java
import static org.apache.commons.lang3.Validate.notNull;

void sendAuditLogsToServerAt(InternalAddress serverAddress) {
    notNull(serverAddress);          // 남은 검증은 널 검사뿐이다

    // 로그를 조회해 서버로 전송
}
```

*리스팅 44-2. 도메인 프리미티브로 API 강화하기 (SBD 리스팅 5.2 기준)*

**이제 이 메서드에 유효하지 않은 입력을 넘기는 것이 불가능하도록 설계되었다.** IP 주소가 내부 주소인지를 확인한다는 관점에서 남은 검증은 널이 아님을 확인하는 것뿐이다.

여기서 무슨 일이 일어났는지 정확히 보자. 검증이 사라진 것이 아니다. **검증의 위치가 옮겨졌다.** `InternalAddress`를 만드는 쪽이 검증의 부담을 진다. 그리고 그 쪽은 설정에서 내부 대역을 읽어오는 곳, 즉 그 판단을 내리기에 가장 적합한 위치다. 호출되는 메서드가 "이 주소가 내부인가"를 묻는 것보다, 주소를 만드는 곳이 "이것은 내부 주소다"라고 선언하는 편이 낫다. 43.8절이 "도메인 프리미티브 객체를 만드는 쪽이 검증의 부담을 진다"고 예고한 것이 이 이동이다.

### 44.3.3 라이브러리를 경계에 배치한다

43.5절은 두 개의 틀을 종합했다. WAHH의 경계 검증은 **어디서** 검증할 것인가에 답하고, SBD의 검증 순서는 **무엇을 어떤 순서로** 검증할 것인가에 답한다. 도메인 프리미티브 라이브러리는 그 종합이 코드에서 취하는 형태다.

**경계마다 그 경계에 맞는 도메인 프리미티브 생성이 놓인다.**

```
   HTTP 요청                                              데이터베이스
      │                                                        ▲
      ▼                                                        │
 ┌─────────┐   ┌──────────────┐   ┌──────────┐   ┌────────────────────┐
 │  DTO    │──▶│ 도메인 프리   │──▶│ 엔티티   │──▶│ 영속 모델           │
 │ (프로토 │   │ 미티브 생성   │   │ (의미    │   │ (다시 타입을        │
 │  콜 제약)│   │ (출처·크기·  │   │  검증)   │   │  통과시켜 로드)      │
 └─────────┘   │ 어휘·구문)   │   └──────────┘   └────────────────────┘
               └──────────────┘
                     ▲
              여기가 43.4절의
              1~4단계가 실행되는 자리
```

*그림 44-4. 도메인 프리미티브 생성이 경계에 놓이는 방식 (이 책의 구성)*

이 그림에서 읽을 것이 셋이다.

**첫째, 다섯 단계 중 앞의 네 단계가 도메인 프리미티브 생성자 안에서 일어난다.** 출처 확인은 요청 수신 계층이 담당하지만(→ 43.4.2), 크기·어휘·구문 검사는 생성자로 들어간다. 남는 것은 다섯 번째 단계 — 의미 검증 — 이고, 그것은 엔티티의 몫이다. 데이터의 상태와 이력을 아는 것이 엔티티이기 때문이다(→ 44.6).

**둘째, 경계를 넘을 때마다 타입이 다시 만들어진다.** 데이터베이스에서 로드할 때도 마찬가지다. 데이터베이스를 별개의 시스템으로 볼 것인지, 자기 통제 영역 안으로 볼 것인지가 판단의 갈림길이고, 이 문제는 44.8절에서 다시 다룬다.

**셋째, DTO의 제약과 도메인의 불변식은 다른 것이다.** 이것이 다음 절의 주제다.

> **이 절이 뒷받침하는 것**
>
> - 유비쿼터스 언어가 라이브러리의 전제 → **42.4** (모델이 유비쿼터스 언어를 형성한다)
> - 재검증이 사라지는 이유 → **43.7** (자기 자신을 신뢰하지 않는 코드), **43.8** (계약과 도메인 프리미티브가 구원하는 지점)
> - 경계에서의 검증이 취하는 코드 형태 → **43.5** (경계 검증과의 대응)
> - 레거시 코드에서 이 라이브러리를 키우는 법 → **47.1** (적용 지점 찾기), **47.2** (모호한 파라미터 목록)

## 44.4 도메인을 공개적으로 노출하지 않기

### 44.4.1 도메인 모델이 공개 API가 되는 순간

API를 강화할 때 반드시 기억해야 할 것이 하나 있다. **다른 도메인과의 인터페이스 역할을 하는 API라면, 그 API에 자기 도메인 모델의 객체를 노출하지 말아야 한다.** 노출하는 순간 도메인 모델이 **즉시 공개 API의 일부가 되기** 때문이다.

다른 도메인을 향한 공개 API의 전형적인 예가 인터넷에 노출되어 클라이언트 소프트웨어가 소비하는 REST API다. 그 API에 내부 도메인을 노출하면, **소프트웨어 클라이언트를 함께 진화시키지 않고서는 도메인을 진화시킬 수 없다.** 사업이 그 클라이언트들에 의존한다면 그들을 무시할 수 없고, 소비자들이 클라이언트를 적응시킬 수 있는 속도에 맞춰서만 진화하는 것 외에 선택지가 없다.

더 나빠지는 지점이 있다. **소비자가 여럿이면, 자신을 각 소비자에게 묶는 것에 그치지 않고 소비자들끼리도 서로 묶는다.** 서점의 도메인 모델이 파트너사 A와 B와 C의 클라이언트에 동시에 노출되어 있다면, A를 위한 변경이 B와 C를 깨뜨린다. 도메인 주도 설계는 이렇게 공유된 도메인을 **공유 커널(shared kernel)** 이라 부르며, 그것이 필요한 경우가 없지는 않지만 **의도하지 않은 공유 커널은 재앙**이다.

이것이 왜 보안 문제인가. 세 갈래다.

**첫째, 진화하지 못하는 모델은 안전해지지 못한다.** 42장과 43장의 논지 전체가 "모델을 더 깊게 만들면 취약점이 사라진다"였다. 그런데 모델을 바꿀 수 없다면 — 바꾸는 순간 외부 클라이언트가 깨진다면 — 그 개선은 영원히 미뤄진다. 결함이 발견되어도 고치는 대신 우회하게 되고, 우회가 쌓이면 복잡도가 되고, 복잡도가 곧 공격 표면이다(→ 31.9).

**둘째, 내부 개념이 그대로 새어 나간다.** 서점의 `Order` 도메인 객체에는 원가, 공급사 계약 조건, 재고 배분 정책, 내부 고객 등급 같은 것이 붙어 있을 수 있다. 그것을 직렬화해 그대로 응답에 담으면, 클라이언트가 요청하지 않은 정보가 함께 나간다. 42.9절이 "원가는 주문의 내부 정보이며 판매 컨텍스트에서만 의미가 있다"는 모델의 이해를 언급했을 때, 그 이해가 코드로 옮겨지는 자리가 여기다. **노출 여부가 매 응답마다 판단되는 것이 아니라 타입에 붙는다.**

**셋째, 도메인 객체의 필드가 곧 입력 표면이 된다.** 도메인 객체를 그대로 역직렬화해 받으면, 그 객체의 모든 필드가 외부에서 채워질 수 있는 필드가 된다. 요청 본문에 예상치 못한 필드를 추가해 도메인 객체의 내부 상태를 설정하는 공격 — 26장이 클라이언트 측 데이터 조작으로 다룬 것의 서버 측 대응물 — 이 여기서 성립한다.

GraphQL은 이 문제의 가장 선명한 사례다. 38.8절과 39.2절에서 본 인트로스펙션은 **스키마 전체를 질의 가능하게 공개한다.** 스키마가 도메인 모델을 그대로 반영하고 있다면, 인트로스펙션은 도메인 모델의 완전한 명세를 공격자에게 제공하는 것이 된다. 인트로스펙션을 끄는 것은 완화책이지 해법이 아니다(→ 39.5에서 필드 제안과 스터핑으로 상당 부분 복원된다). **해법은 스키마와 도메인 모델을 애초에 같은 것으로 두지 않는 것이다.**

### 44.4.2 번역 계층 — DTO는 도메인이 아니다

해야 할 일은 각 도메인 객체에 대해 **다른 표현**을 쓰는 것이다. 이것은 다른 도메인과 통신하기 위한 일종의 **데이터 전송 객체(DTO, data transfer object)** 로 볼 수 있다.

DTO에도 불변식을 둘 수 있다. **그러나 그 제약은 도메인에 존재하는 제약과 같은 것이 아니다.** DTO의 제약은 예컨대 **API가 정의하는 통신 프로토콜과 관련된 제약**이다. 문자열 길이 상한, 필수 필드의 존재, 인코딩 형식 같은 것이다.

그리고 이런 API 메서드에서 **가장 먼저 하는 일이 DTO를 대응하는 도메인 프리미티브로 변환하는 것**이다. 그 변환이 데이터의 유효성을 보장한다.

```java
// 공개 API 계층 — 프로토콜의 언어를 쓴다
public final class AddItemRequest {
    public String isbn;        // 프로토콜 제약: 널 아님, 길이 상한
    public int quantity;       // 프로토콜 제약: 정수
}

@POST("/orders/{orderId}/items")
public Response addItem(final OrderIdParam orderIdParam,
                        final AddItemRequest request) {

    // 경계에서 가장 먼저 하는 일: DTO → 도메인 프리미티브
    final OrderId orderId = new OrderId(orderIdParam.value());
    final ISBN isbn       = new ISBN(request.isbn);
    final Quantity qty    = new Quantity(request.quantity);

    // 이 아래로는 도메인의 언어만 존재한다
    orderService.addItem(orderId, isbn, qty);

    return Response.accepted();
}
```

*리스팅 44-3. 공개 API 경계에서의 번역 (이 책의 구성)*

이 번역 계층을 API의 개념과 도메인 사이에 두면 **둘을 결합에서 풀어낼 수 있다.** API와 도메인을 독립적으로 진화시킬 수 있게 되는 것이다.

번역 계층이 방어하는 것을 정리하면 이렇다.

**표 44-3. 번역 계층이 각각 무엇을 막는가**

| 방향 | 번역 계층이 하는 일 | 없으면 생기는 문제 |
|---|---|---|
| 안으로(요청) | DTO의 필드를 명시적으로 골라 도메인 프리미티브로 변환 | 예상치 못한 필드가 도메인 객체 내부 상태를 설정 |
| 안으로(요청) | 프로토콜 제약(크기·인코딩)을 도메인 불변식보다 먼저 적용 | 큰 페이로드가 도메인 로직에 도달(→ 43.4.3, 45.8) |
| 밖으로(응답) | 응답에 담을 필드를 명시적으로 나열 | 원가·내부 등급 등 내부 개념 유출(→ 30장, 39.7) |
| 양방향 | 도메인 모델 변경이 API 계약에 자동 전파되지 않음 | 모델을 못 고쳐 결함이 우회로 쌓임 |

마지막 줄이 가장 중요하다. **번역 계층의 진짜 값은 필드 하나를 감추는 것이 아니라, 모델을 계속 고칠 수 있게 유지하는 것이다.** 이 장의 나머지가 제안하는 모든 개선 — 새 도메인 프리미티브를 도입하고, 엔티티를 쪼개고, 상태 그래프를 재설계하는 것 — 은 모델을 고칠 수 있다는 전제 위에 있다.

47.8절이 이 논의를 마이크로서비스로 확장한다. 각 서비스가 하나의 바운디드 컨텍스트라면, 서비스 간 API는 전부 이 절이 말하는 "다른 도메인을 향한 공개 API"다. 내부 서비스라고 해서 예외가 아니다.

> **이 절이 뒷받침하는 것**
>
> - 컨텍스트 간 모델 공유의 위험 → **42.7** (컨텍스트 간 상호작용, 공유 커널)
> - 스키마가 도메인 모델을 그대로 반영할 때 → **38.8** (인트로스펙션), **39.2**, **39.5**
> - 응답에 내부 개념이 새는 문제 → **30장** (정보 노출), **39.7** (오류 메시지 남용)
> - 서비스 경계에서의 API 설계 → **47.8** (각 서비스는 하나의 바운디드 컨텍스트다)

## 44.5 읽기 1회 객체(read-once object) — 비밀의 의도치 않은 사용 탐지, 코드 진화로 인한 누출 방지

### 44.5.1 민감한 값은 다르게 다뤄야 한다

소프트웨어에서 보안 문제의 흔한 원천 하나가 **민감한 데이터의 누출**이다. 이 누출은 개발자가 의도치 않게 일으킬 수도 있고, 누군가가 의도적으로 촉발할 수도 있다. 누출의 이유가 무엇이든, 설계 기법 몇 가지로 이 문제를 다룰 수 있다.

**읽기 1회 객체(read-once object)** 는 그중 하나다. 핵심 성질은 여섯 가지다.

- **주목적은 비의도적 사용의 탐지를 돕는 것이다.**
- 민감한 값이나 개념을 표현한다.
- 대개 도메인 프리미티브다.
- 값을 **한 번만, 딱 한 번만** 읽을 수 있다.
- 민감 데이터의 **직렬화를 막는다.**
- **서브클래싱과 확장을 막는다.**

첫 번째 항목이 이 패턴의 성격을 규정한다. **읽기 1회 객체는 누출을 막는 것이 아니라 누출을 탐지 가능하게 만드는 것이다.** 이 구분이 이 절 전체에서 중요하다.

기본 발상은 이렇다. 객체가 생성된 뒤 캡슐화한 데이터를 한 번만 꺼낼 수 있고, 두 번 이상 꺼내려 하면 오류가 난다. 그리고 직렬화를 통해 민감 데이터가 빠져나가는 것을 막기 위해 합리적인 노력을 기울인다.

22.9절이 이 패턴을 비밀 취급의 맥락에서 소개하며 `Password` 구현을 보였다. 이 절은 그 패턴의 일반형과, 그것이 실제로 무엇을 잡아내는지를 다룬다.

### 44.5.2 일반형 — `SensitiveValue`

```java
import java.io.Externalizable;
import java.io.ObjectInput;
import java.io.ObjectOutput;
import java.util.concurrent.atomic.AtomicReference;

import static org.apache.commons.lang3.Validate.notNull;
import static org.apache.commons.lang3.Validate.notBlank;

public final class SensitiveValue                  // 서브클래싱 방지
        implements Externalizable {                // 직렬화 경로를 장악

    private transient final                        // 필드 접근 직렬화 방지
            AtomicReference<String> value;

    public SensitiveValue(final String value) {
        validate(value);                           // 생성 시점에 도메인 규칙 검사
        this.value = new AtomicReference<>(value);
    }

    public String value() {
        return notNull(value.getAndSet(null),      // 읽으면서 동시에 비운다
            "Sensitive value has already been consumed");
    }

    @Override
    public String toString() {
        return "SensitiveValue{value=*****}";      // toString이 값을 노출하지 않는다
    }

    @Override
    public void writeExternal(final ObjectOutput out) { deny(); }

    @Override
    public void readExternal(final ObjectInput in) { deny(); }

    private static String validate(final String value) {
        // 도메인 고유 불변식 검사
        return notBlank(value).trim();
    }

    private static void deny() {
        throw new UnsupportedOperationException(
            "Not allowed on sensitive value");
    }
}
```

*리스팅 44-4. 민감 데이터를 담는 읽기 1회 객체 (SBD 리스팅 5.3 기준)*

구현의 각 조각이 무엇을 막는지 하나씩 짚는다.

`final` 클래스이므로 **서브클래싱으로 `toString`을 되살리거나 접근자를 우회할 수 없다.** 값은 `AtomicReference`로 감싼다. 접근자 `value()`가 호출되면 `getAndSet(null)`이 **이전 값을 반환하면서 동시에 내부를 `null`로 만든다.** 원자적 연산이므로 두 스레드가 동시에 호출해도 값을 얻는 쪽은 하나뿐이다. 이미 호출된 뒤라면 이전 값이 `null`이므로 `notNull`이 예외를 던진다.

`Externalizable`을 구현하고 두 메서드가 모두 예외를 던지므로 **자바 직렬화가 원천 차단된다.** 그런데 어떤 라이브러리는 자바 직렬화를 쓰지 않고 리플렉션으로 필드를 직접 읽어 직렬화한다. 그런 라이브러리도 대개 `transient` 키워드는 존중하므로, 필드를 `transient`로 선언해 두 번째 방어선을 친다.

`toString`은 별표만 반환한다. 이것이 왜 필요한지는 **누출 경로의 목록**을 보면 분명해진다.

**표 44-4. 민감 값이 코드에서 새는 네 갈래 경로와 각각의 차단 지점**

| 경로 | 어떻게 일어나는가 | 무엇이 막는가 | 관련 절 |
|---|---|---|---|
| 로깅 | `log.info("login: " + user)` 또는 구조화 로거의 객체 덤프 | `toString`이 값을 반환하지 않음 | 16.6, 46.4 |
| 문자열 병합·템플릿 | 오류 화면, 디버그 출력, 문자열 포맷 | 같음 (`toString` 경유) | 30.5 |
| 직렬화 | 세션 지속화, 캐시 저장, 메시지 큐 전송 | `writeExternal`/`readExternal`이 거부, `transient` | 44.5.4 |
| 예외 메시지 | 예외 페이로드에 도메인 객체를 담아 던짐 | `toString` 경유 + 두 번째 읽기 시 예외 | 30.5, 45.1 |

이 네 경로가 겹치는 지점이 `toString`이다. **자바에서 객체가 의도치 않게 문자열이 되는 거의 모든 경로가 `toString`을 지난다.** 그래서 그 하나를 막는 것이 비용 대비 효과가 가장 크다. 나머지 셋은 각각의 차단 장치를 따로 둔다.

한 가지 세부. 22.9절에서 본 `Password`는 `String` 대신 `char[]`를 쓰고, 소비 후 배열을 `Arrays.fill`로 지우고, 입출력 배열을 모두 복제한다. `SensitiveValue`와 다른 이유는 **JVM의 메모리 관리 방식** 때문이다. `String`은 불변이므로 사용 후 지울 수 없고, 문자열 풀과 GC의 사정에 따라 힙에 얼마나 오래 남을지 통제할 수 없다. 배열은 지울 수 있다. 목표는 **JVM 메모리에 민감 값이 노출되는 시간을 줄이는 것**이고, 이 정도의 노력은 비교적 낮은 비용으로 합리적인 값을 하므로 자바에서는 좋은 관행으로 삼을 만하다. 더 밀고 나갈 수도 있지만, 이 책은 여기까지를 실용적 균형으로 본다.

### 44.5.3 비의도적 사용을 탐지한다

이 설계 패턴의 이점을 이해하려면 실제 흐름을 따라가야 한다.

서점의 로그인 기능을 만든다고 하자. 사용자명과 비밀번호가 입력되고, 그것으로 인증을 수행한다. 인증은 자격증명 검증을 담당하는 별도 시스템 — 인증 시스템 — 을 호출해 이루어진다. **비밀번호가 시스템에 들어온 뒤로는 인증 외의 어떤 목적으로도 쓰여서는 안 된다.** 즉 비밀번호를 꺼내야 하는 지점은 그것을 인증 시스템에 넘기는 순간 하나뿐이다. 그러고 나면 비밀번호를 더 들고 있을 이유가 없다.

```
   비밀번호
     ****
       │
       ▼
  ┌──────────┐
  │  웹 모듈  │            비밀번호는 시스템을
  └────┬─────┘            통과하지만 딱 한 번만
       │                  사용된다
       ▼
  ┌──────────┐      ┌──────────────┐        비밀번호
  │ 도메인    │─────▶│ 인프라 모듈   │───────▶  ****
  │ 로직      │      │              │           │
  └──────────┘      └──────────────┘           ▼
                                          ┌──────────┐
      서점 시스템                          │ 인증 시스템│
                                          └──────────┘
```

*그림 44-5. 읽기 1회 객체의 생애 주기 (SBD 그림 5.4 기준)*

비밀번호는 민감 데이터의 전형이다. 사용자의 비밀번호가 디스크의 어느 로그 파일에 평문으로 남아 아무나 읽을 수 있게 되는 것, 사용자 브라우저의 오류 메시지에 찍히는 것, 운영팀의 모니터링 대시보드에 표시되는 것 — 모두 절대 원하지 않는 일이다.

비밀번호를 도메인 프리미티브로 모델링하고 읽기 1회 객체로 구현하면, **비밀번호가 어딘가로 새기 시작할 때 그것을 쉽게 탐지할 수 있는 안전망**을 만든 것이 된다.

이 구현에서 비밀번호를 의도치 않게 사용하면, 인증 시스템으로 자격증명을 검증하려는 시점에 **"Password value has already been consumed"** 라는 오류 메시지가 나온다. 그 비의도적 사용은 예컨대 로그 메시지일 수도 있고, 비밀번호를 담은 예외를 던진 결과일 수도 있다.

**이 실수는 대개 아주 이른 시점에 잡힌다.** 지속적 전달 파이프라인의 테스트가 깨지기 때문이다(→ 46.8, 46.9). 파이프라인에서 잡지 못하더라도, 로그인이 되지 않는다는 사실이 프로덕션에서 금방 발견될 것이고, 오류 메시지가 무슨 일인지를 상당히 쉽게 설명해 준다.

여기서 정직해야 할 지점이 있다. **접근자를 통해 값을 꺼내는 경우, 읽기 1회 객체는 데이터가 새는 것을 막지 못한다. 새는 순간을 탐지하기 쉽게 만들 뿐이다.** 좋은 개발 관행과 충실한 테스트 스위트를 갖추고 있다면, 그 누출이 프로덕션 환경에 도달하기 전에 막을 가능성이 높다. 그것이 이 패턴이 약속하는 전부이고, 실무에서는 그것으로 충분한 경우가 많다.

### 44.5.4 코드 진화가 부르는 누출

의도치 않은 데이터 누출이 쉽게 생기는 또 하나의 상황은 **코드를 재설계하거나 다시 모델링할 때**다. 이것은 SBD의 저자들이 직접 겪은 종류의 일이고, 읽기 1회 객체 덕분에 누출을 찾아 프로덕션 도달을 막을 수 있었던 사례다.

시나리오는 이렇다. 웹 애플리케이션을 만들고 있고, 코드가 현재 로그인한 사용자의 데이터에 자주 접근해야 한다. 필요한 정보는 `User` 도메인 객체에 있다. 어느 시점에 개발자들이 접근을 쉽게 하고 캐시 역할을 하게 하려고 **`User` 객체를 웹 세션에 넣기로** 한다. 이 해법은 의도대로 동작하고 원하던 이점을 준다.

나중에 새로운 업무 요구사항의 결과로 `User` 도메인 객체가 다시 모델링되면서 **주민등록번호에 해당하는 민감 식별자가 추가**된다. 그 식별자 객체는 한 번만 쓰이도록 의도된 것이므로 읽기 1회 객체로 구현된다.

```
      User                      다시 모델링          User
   ┌─────────┐                                   ┌─────────┐
   │ 이름     │                                   │ 이름     │
   │ 별명     │        ──────────────▶            │ 별명     │
   │ 나이     │                                   │ 나이     │
   └─────────┘                                   │ 주민번호 │  ← 민감
                                                 └─────────┘

  User에 민감 데이터가                        이제 User가 민감
       없다                                    데이터를 담는다
```

*그림 44-6. `User` 객체의 재모델링이 민감 데이터 누출을 만드는 경로 (SBD 그림 5.5 기준)*

새 도메인 모델은 새 기능을 잘 수행하고, 테스트 스위트가 전부 통과한다. **그런데 스테이징 환경의 인수 테스트 도중, 애플리케이션을 종료할 때마다 스택 트레이스가 찍히는 것을 우연히 발견한다.** 오류 메시지는 "Not allowed on sensitive value"다.

스택 트레이스를 따라가면 예외의 원인이 그 민감 식별자를 직렬화하려는 시도임이 드러난다. 무엇이 민감 데이터를 직렬화하려 하는지 의아해하며 추적을 시작한다. 파고들어 가면 직렬화를 촉발한 것이 쓰고 있는 톰캣 웹 서버임을 발견한다. **톰캣은 기본 설정에서 종료하거나 재시작할 때마다 활성 세션을 디스크에 지속시킨다.** 이 기능을 끄지 않은 채 세션에 민감 데이터를 넣으면, 그 데이터가 디스크에 남아 **디스크 접근 권한을 가진 누구나 읽을 수 있게 된다** — 적절한 인가 없이 민감 데이터를 노출하는 완벽한 사례다.

이 절이 이 시나리오를 길게 다루는 이유는, 여기에 세 가지 교훈이 겹쳐 있기 때문이다.

**첫째, 누구도 잘못하지 않았다.** 세션에 `User`를 넣은 개발자는 그때 `User`에 민감 데이터가 없었으므로 옳은 판단을 했다. 민감 식별자를 추가한 개발자는 그것을 읽기 1회 객체로 구현하는 옳은 판단을 했다. 톰캣은 문서화된 기본 동작을 했다. **결함은 세 판단의 조합에서만 나타난다.** 이런 종류의 데이터 누출은 소프트웨어 시스템에서 흔하고 거의 항상 의도치 않은 것이다. 개발자들이 함의를 생각하지 못했거나, 알지 못했기 때문이다 — 대개 그들이 작업하던 코드가 **민감 데이터가 만들어진 곳에서 멀리 떨어져 있었기 때문이다.**

**둘째, 읽기 1회 객체가 아니었다면 아무 일도 일어나지 않았다.** 평범한 `String` 필드였다면 톰캣은 조용히 직렬화에 성공했을 것이고, 민감 데이터는 조용히 디스크에 떨어졌을 것이며, 스택 트레이스도 오류 메시지도 없었을 것이다. **탐지 가능하게 만든다는 것이 이런 것이다.** 이 패턴이 만든 것은 방벽이 아니라 **경보**다.

**셋째, 프레임워크의 편의가 불변식을 깬다.** 톰캣의 세션 지속화는 재시작 시 사용자 경험을 지키기 위한 편의 기능이다. 이 구조 — 프레임워크가 제공하는 편의가 도메인의 규칙을 우회하는 경로가 되는 것 — 는 이 장에서 다시 나온다. 44.8절의 ORM 프레임워크와 무인자 생성자가 정확히 같은 구조다.

읽기 1회 객체로 설계하면 **개발자가 당면한 작업에 더 집중할 수 있고 보안을 걱정하지 않아도 된다.** 걱정을 대신하는 것은 타입이다.

### 44.5.5 서점에서 무엇을 읽기 1회로 만들 것인가

패턴을 적용할 후보를 고르는 기준은 하나다. **정당한 소비 지점이 하나뿐인 값인가.**

**표 44-5. 온라인 서점의 읽기 1회 후보**

| 값 | 정당한 소비 지점 | 두 번째 읽기가 뜻하는 것 |
|---|---|---|
| 로그인 비밀번호 | 인증 시스템 호출 | 로그·예외·디버그 출력으로의 유출 |
| 결제 카드 번호 | 결제 게이트웨이 호출 | 주문 이력·영수증·로그에 잔류 |
| 비밀번호 재설정 토큰 | 재설정 링크 생성 1회 | 재사용 가능한 토큰이 저장됨(→ 22.4) |
| 수령인 연락처 | 배송사 API 전달 | 마케팅·분석 경로로의 확산(→ 47.9) |
| API 자격증명 | 외부 시스템 인증 헤더 구성 | 설정 덤프·오류 응답 유출(→ 46.2) |

오른쪽 열이 이 표의 요점이다. **두 번째 읽기가 언제나 나쁜 것은 아니다.** 어떤 값은 정당하게 여러 번 읽힌다. 그러나 위의 다섯은 두 번째 읽기가 거의 언제나 설계자가 의도하지 않은 경로다. 그런 값에 읽기 1회를 적용하면, 그 경로가 생기는 순간이 예외로 드러난다.

적용의 한계도 분명히 해 둔다. **재시도가 필요한 값에는 이 패턴을 그대로 쓸 수 없다.** 결제 게이트웨이 호출이 네트워크 오류로 실패해 재시도해야 한다면, 카드 번호를 이미 소비한 뒤다. 이 경우의 설계는 두 가지다. 재시도를 소비 지점 **안쪽**으로 옮겨 한 번의 소비 안에서 반복하게 하거나, 값의 생애를 재시도 경계에 맞춰 다시 만들게 하는 것이다. 어느 쪽이든 **"어디까지가 한 번의 소비인가"를 명시적으로 결정하게 만든다는 점**에서 설계상의 이득이 있다. 45.4절의 타임아웃·재시도 설계와 함께 봐야 하는 지점이다.

## 44.6 도메인 프리미티브 위에 서기 — 과밀한 엔티티 메서드 정리

### 44.6.1 엔티티는 왜 비대해지는가

도메인 프리미티브가 없으면, 나머지 코드가 검증과 형식 변환과 비교와 그 밖의 온갖 세부를 떠맡아야 한다.

**엔티티**는 구별되는 정체성을 가진 오래 사는 객체다. 뉴스 피드의 기사, 호텔의 객실, 온라인 판매의 장바구니 같은 것이다. 시스템의 기능은 대개 이 객체들의 상태를 바꾸는 일을 중심으로 돈다. 객실이 예약되고, 장바구니의 내용이 결제된다. 조만간 제어 흐름은 이 객체들을 표현하는 코드로 인도된다.

**그리고 모든 데이터가 `int`나 `String` 같은 범용 타입으로 전달된다면, 검증하고 비교하고 형식을 맞추는 책임이 엔티티 코드로 떨어진다.** 엔티티 코드는 자신이 모델링하는 중심 업무 흐름 — 상태 변화 — 에 집중하는 대신 온갖 작업의 부담을 지게 된다.

시간이 지나면서 엔티티 클래스는 코드가 쓰이고, 확장되고, 여러 번 바뀐다. **엔티티가 기능의 자석이 되어, 메서드가 수백 줄에 걸치고 중첩된 `for`와 `if` 블록으로 뒤덮인 코드 덩어리가 되기 쉽다.** 그런 메서드 깊숙한 곳의 `if` 문에 `else` 절을 추가한다고 상상해 보라. 어떤 조건을 확인하는 것을 잊어버릴 확률이 얼마나 되겠는가. 코드가 복잡해지면 중요한 세부가 간과되는데, **특히 검증은 잊히는 경향이 있고 그 결과는 보안에 파괴적이다.**

### 44.6.2 열 줄짜리 메서드에 숨은 두 개의 실수

온라인 서점의 `Order` 클래스를 보자. 책이 주문에 추가되고, 나중에 결제되고, 배송될 때 애플리케이션의 상태가 바뀐다. `Order` 클래스가 이 변화를 추적할 책임을 진다.

`addItem` 메서드는 책이 주문에 추가되는 시점을 추적한다. 열 줄이지만 많은 업무 규칙을 지킨다. 그리고 미묘한 실수가 있다. 찾아보라. **쉽지 않다.**

```java
import org.apache.commons.lang3.Validate;

class Order {
    private BookRepository bookCatalog;
    private ArrayList<Object> items;
    private boolean paid = false;
    Inventory inventory;

    public void addItem(String isbn, int qty) {
        if (this.paid == false) {                          // 주문이 닫히지 않았는지 확인
            notNull(isbn);
            isTrue(isbn.length() == 10);                   // ISBN 형식 검증
            isTrue(isbn.matches("[0-9X]*"));
            isTrue(isbn.matches("[0-9]{9}[0-9X]"));
            Book book = bookCatalog.findByISBN(isbn);      // 검증된 ISBN으로 책 조회
            if (inventory.availableBooks(isbn) >= qty) {   // 재고가 충분한지 확인
                items.add(new OrderLine(book, qty));       // 수량만큼 주문에 추가
            }
        }
    }
    ...
}

class ShoppingFlow {

    void handleOrderAdd() {                                // 엔티티를 호출해 갱신
        ...
        String isbnText = ...
        int qty = Integer.parseInt(qtyText);
        ...
        order.addItem(isbn, qty);                          // 검증했던가? 했어야 했나?
        ...
    }
}
```

*리스팅 44-5. `addItem`이 너무 많은 일을 하는 `Order` 엔티티 (SBD 리스팅 5.5 기준)*

열 줄 안에서 `addItem`은 인자를 검증하고, 주문의 상태를 확인하고, 책의 재고를 확인하고, 주문 항목 목록을 관리한다. 견고해 보인다. 그리고 이 서점에서 ISBN을 검증하는 저 코드 조각들은 코드베이스 전체에 반복되어, 거의 관용구가 되어 있다.

실수는 무엇인가. **두 개다.**

**첫째, 코드가 ISBN의 체크섬을 검증하지 않는다.** 사소한 결함이고 아마 무해하다.

**둘째, 코드가 음수 수량을 확인하지 않는다.** 29.3절의 안티북 사건에서 막대한 금전 손실로 이어진 바로 그 결함이다. 알아챘다면 훌륭한 발견이다. 못 알아챘다면 너무 자책할 필요 없다. **이런 식으로 보여 주는 코드베이스에서 이런 종류의 실수를 발견하는 것은 어렵다.** (게다가 그 사건에서는 창고와 물류의 제약 때문에 수량이 최대 240권이어야 한다는 제한도 있었다. 그 검사 역시 이 코드에 없다.)

### 44.6.3 왜 사람은 이런 실수를 놓치는가

실수를 찾는 일은 더 현실적인 코드베이스에서 훨씬 까다로워진다. 현실적인 코드베이스는 훨씬 더 많은 것을 고려해야 한다.

오류 처리를 해야 한다 — 이 예제는 그것을 생략했다. 현실적인 `addItem`이라면 적절한 시점에 `ItemCannotBeAddedException`과 `InvalidISBNException`을 던질 것이다. 같은 ISBN에 대해 여러 개의 `OrderLine`이 생기지 않도록 이미 주문에 그 ISBN이 있는지 찾는 `for` 루프도 있을 것이다. 더 엉망으로 만들자면, 코드는 철 지난 기능들로 뒤덮여 있을 것이다. 작년 판촉 행사 — 인테리어 관련 도서 세 권을 사면 요리책 한 권을 무료로 주던 — 를 위해 추가된 코드는 더 이상 쓰이지 않지만 제거되지도 않았다. 크리스마스 캠페인 코드도 마찬가지다. VIP 고객의 특급 배송 할인 사례가 있고, 특정 조건에서의 무료 배송이 그 난장판 어딘가에 끼워져 있다. 목록은 계속된다. **그런 크고 지저분한 메서드에서 빠진 범위 검사를 못 알아챘다 해도 이상한 일이 아니다.**

단순한 예제에서조차 세부를 놓치기 쉬운 이유는 **근본적인 심리학**에 있다.

**인간은 유사성을 인식하는 데 능하고, 무의식적으로 뒷받침하는 증거를 찾는다.** 사람들이 신분증 확인을 훈련받아야 하는 이유가 이것이다. 훈련 없이는 앞의 사람을 보고, 증명서를 보고, "그래, 눈 두 개, 가운데 코, 아래 턱 — 맞는 것 같군" 하고 생각하거나, 그것보다 약간 더 정교한 판단을 한다. 경찰 훈련에는 이것을 피하기 위한 별도 수업이 있다. 심리학자들은 이 인간 특성을 **확증 편향(confirmation bias)** 이라 부르며, 1960년대부터 체계적으로 연구해 왔다.

코드를 볼 때 이것이 어떻게 작용하는가. **코드를 읽을 때, 보이는 코드의 대부분은 옳다.** 게으른 뇌는 "여기까지 본 코드는 괜찮았다"고 생각하고, 무의식적으로 "나머지도 아마 괜찮을 것"이라는 가설을 세운다. 그 뒤로는 확증 편향 때문에 뭔가 괜찮아 보일 때마다 고개를 끄덕이게 되고, 코드가 불완전하거나 잘못된 지점을 찾는 것이 거의 불가능해진다.

반대 방향으로도 겪어 봤을 것이다. **첫 번째 버그를 발견하면 주문이 깨지고, 갑자기 사방에서 버그가 보인다.** 숲에서 버섯을 찾거나 새를 관찰하는 것과 비슷하다 — 처음에는 하나도 안 보이다가, 첫 번째를 발견하면 갑자기 도처에 보인다.

**요약하면 이렇다.** 인간은 많은 코드를 볼 때 검증 같은 미묘한 세부를 놓치는 경향이 있고, 동시에 빠진 검증은 심각한 보안 문제를 일으킬 수 있다. **엔티티를 정리할 필요가 분명하다.**

### 44.6.4 정리하기

도메인 프리미티브는 본질적으로 많은 관련 검증을 담고 있다. 엔티티 코드가 그 검증들의 부담에서 벗어나면, **자신이 가장 잘할 수 있는 종류의 검증에 집중할 수 있다.**

43.4절에서 본 검증의 다섯 단계를 다시 놓고 보자.

- **출처** — 데이터가 정당한 발신자에게서 왔는가?
- **크기** — 합리적인 크기인가?
- **어휘적 내용** — 올바른 문자와 인코딩을 담고 있는가?
- **구문** — 형식이 맞는가?
- **의미** — 데이터가 말이 되는가?

**마지막 단계인 의미 검증이 엔티티가 해야 할 검증이다.** 엔티티는 데이터의 상태와 이력을 알고 있으므로, 들어오는 데이터가 **지금 여기서** 말이 되는지를 판단하기에 적합하다. 그러나 앞선 단계들은 데이터를 엔티티로 가져오기 **전에** 끝나야 할 검사다.

앞에서 만든 `Quantity`가 `addItem`의 `int` 파라미터를 대체한다. 이제 ISBN 문자열을 대체할 도메인 프리미티브가 필요하다.

```java
import org.apache.commons.lang3.Validate.*;

    private final String isbn;

    public ISBN(final String isbn) {        // 생성자가 ISBN 객체는 항상
        notNull(isbn);                      // 유효한 ISBN을 담도록 보장한다
        isTrue(isbn.length() == 10);
        isTrue(isbn.matches("[0-9X]*"));
        isTrue(isbn.matches("[0-9]{9}[0-9X]"));
        isTrue(checksumValid(isbn));        // 여기서는 체크섬 검증을 잊지 않았다 —
        this.isbn = isbn;                   // 한 곳에서만 기억하면 된다
    }

    private static boolean checksumValid(final String isbn) {
        // ISO 2108의 가중합 검사
        ...
    }
    ...
}
```

*리스팅 44-6. 검증 로직을 포함한 `ISBN` 도메인 프리미티브 (SBD 리스팅 5.6 기준)*

**이 클래스는 한 번 쓰인다.** 그러므로 어떤 때는 체크섬 검증을 기억하고 어떤 때는 잊어버릴 위험이 없다. 이 클래스가 크기·어휘적 내용·구문에 대한 검증을 모두 담고 있으므로, 엔티티에서 `ISBN`을 쓸 때 엔티티 코드를 그 검증들로 어지럽힐 필요가 없다.

이제 `Order` 엔티티를 `ISBN`과 `Quantity`를 쓰도록 고칠 수 있다.

```java

        if (this.paid == false) {                           // 주문이 닫히지 않았는지 확인 —

            }                                               //  코드가 실제로 말한다

*리스팅 44-7. `ISBN`과 `Quantity`를 쓰는 `Order` (SBD 리스팅 5.7 기준)*

새 버전에서 개선을 볼 수 있다. 우선 코드가 줄었지만, 그것은 대부분 코드가 다른 곳으로 옮겨 갔기 때문이다. **더 중요한 것은 코드가 요점에 집중한다는 것이다.** 주문에 새 항목을 추가할 때 무엇을 해야 하는지에 대한 코드가 되었다.

`addItem`은 이전 단계의 검증 부담을 지지 않는다. 마지막 부분 — **의미** 라 부른 단계, "이 데이터가 지금 말이 되는가"를 묻는 단계 — 만 진다. 메서드 안의 코드가 줄었으므로 나중에 이 메서드를 고쳐야 할 때 실수할 위험도 줄었다. 또한 검증이 도메인 프리미티브에 의해 일관되게 처리되므로, **ISBN 체크섬 검증을 잊거나 수량이 음수가 아닌지 확인하는 것을 잊을 위험이 없다.**

그리고 `ShoppingFlow`의 클라이언트 코드는 더 이상 ISBN에 벌거벗은 `String`을, 수량에 `int`를 보낼 수 없다. **그렇게 하려 하면 컴파일 오류가 난다.** `Order.addItem`을 호출하려면 클라이언트 코드가 `ISBN` 객체와 `Quantity` 객체를 만들어야 하고, `ISBN`과 `Quantity`의 생성자가 검증을 담고 있으므로 **엔티티에 검증되지 않은 데이터를 보낼 위험이 더 이상 없다. 검증이 호출자 쪽으로 밀려난 것이다.**

호출하는 클라이언트가 `ISBN`이나 `Quantity`를 만들려 할 때 검증 문제가 생길 수 있다. 그런 경우 클라이언트 코드는 호출한 GUI로 되돌아가 그 문제를 해결해야 한다 — 예컨대 사용자에게 데이터를 고쳐 달라고 요청함으로써. **관심사의 분리에 주목하라. 클라이언트 코드는 검증이 수행되도록 보장하지만, 그것이 어떻게 수행되는지는 도메인 프리미티브 `ISBN`과 `Quantity`의 책임이다.**

지금까지는 메서드 인자를 논했다. 같은 논의가 생성자의 인자에도 적용된다. 그리고 **반환값과 엔티티가 보유하는 데이터 필드**에도 같은 발상을 적용하는 것이 값을 한다.

> **TIP** 엔티티의 메서드 인자, 생성자 인자, 반환값, 데이터 필드에 도메인 프리미티브를 쓴다.

엔티티 코드에서 도메인 프리미티브를 쓰는 주된 이점은 다음과 같다.

- **입력이 항상 검증된다.** 타입 시스템이 도메인 프리미티브를 쓰도록 강제한다.
- **검증이 일관된다.** 항상 도메인 프리미티브의 생성자가 수행한다.
- **엔티티 코드가 덜 어지럽고 요점에 집중한다.** 경계 검사나 형식 제어 따위를 할 필요가 없다.
- **엔티티 코드가 더 읽기 쉽다.** 도메인의 언어로 말한다.

이 이점을 얻는 방법이 도메인 프리미티브뿐인 것은 아니다. 다만 **특히 메서드의 인자로 도메인 프리미티브를 쓰는 것이, 엔티티가 잘 검증된 입력을 받도록 보장하는 가장 좋은 방법**임을 저자들은 경험으로 확인했다.

### 44.6.5 언제 쓰지 않는가, 그리고 성능 이야기

도메인 프리미티브로 엔티티의 검증 부담을 덜어내는 것은 강력한 기법이다. 사실 너무 강력해서, **쓰지 말아야 할 상황의 예를 찾기가 어렵다.** 입력을 검증할 필요가 (거의) 없는 상황, 모든 데이터가 허용되는 상황이어야 한다. 온도의 시계열 정도면 충분히 단순할까? 그것조차 절대영도(0K, 섭씨 -273도) 아래의 온도는 받고 싶지 않을 것이다. 무언가가 그저 `int`이거나 완전히 제한 없는 `String`인 상황을 찾기는 어렵다.

**추가 래퍼 객체(`String`을 감싼 `ISBN` 같은)가 런타임에 성능 손해를 준다**는 주장을 종종 듣는다. 원리적으로는 사실이지만 실무적 관심사인 경우는 드물다. 어차피 ISBN 검증은 실행해야 한다는 것을 기억하라. 그것을 `ISBN` 생성자 안에서 하든 다른 방식으로 하든 성능 부담은 같다. **추가되는 것은 객체 하나의 할당과 관리뿐이다.**

현대적인 가비지 컬렉션을 쓰면 이런 종류의 단명 객체에는 사실상 손해가 없다. **메모리 할당은 기계어 명령 열 개 정도이고, 해제는 대개 비용이 0이다.** 그리고 데이터베이스를 건드리거나 네트워크 호출을 하는 순간 이 모든 우려는 왜소해진다.

**여기서 언급한 성능 제약은 나노초에서 마이크로초 범위이고, 데이터베이스 왕복은 밀리초 단위로 측정된다.** 1.6절에서 RTT를 모든 것의 단위로 삼았던 이유가 여기서 다시 나타난다. 서울과 프랑크푸르트 사이의 왕복 한 번이 250밀리초라면, 그 사이에 할당할 수 있는 단명 객체는 수백만 개다. 객체 할당을 신경 써야 하는 상황은 극단적이어야 한다 — 아마 빅데이터 분석 정도일 것이고, 메모리에서 막대한 양의 수치를 처리하거나 제약된 장치를 위해 프로그래밍하는 상황이라면 애초에 엔티티를 쓰지 않을 가능성이 높다.

한 가지 더. **엔티티 안에서 도메인 프리미티브를 쓰는 패턴은 새로 만드는 코드에만 적용되는 것이 아니다.** 유지보수나 추가 개발로 엔티티를 건드릴 때, 서명을 도메인 프리미티브를 쓰도록 바꾸는 기회로 삼는다. 적합한 도메인 프리미티브가 없다면, 새것을 도입할 적기를 찾은 것이다. 이렇게 코드를 만질 때마다 한 걸음씩 나아가는 방식으로 코드베이스를 서서히 돌려세울 수 있다. 시간이 지나면 도메인 프리미티브 라이브러리가 풍부해지고 엔티티는 더 집중된다. **레거시 코드에 대한 이 전략은 47.1절과 47.2절이 다룬다.**

> **이 절이 뒷받침하는 것**

## 44.7 테인트 분석

### 44.7.1 오염 비트라는 발상

보안 연구 분야에서 **테인트 분석(taint analysis)** 은 입력을 오염된 것으로 표시함으로써 악성 공격 데이터의 사용을 막는 방법을 연구한다. 공격 데이터는 키로거를 설치하는 자바스크립트가 박힌 웹 콘텐츠일 수도 있고, 데이터베이스를 파괴하거나 내용을 드러내려는 SQL 명령이 박힌 것일 수도 있다.

기본 원리는 이렇다. **모든 입력은 의심을 벗기 전까지 의심스러운 것으로 간주된다.** 의심을 벗는 것은 데이터가 어떤 메커니즘을 통해 검사되었을 때다. 정리되지 않은(여전히 오염된) 데이터가 민감한 방식으로 사용되면 — 예컨대 사용자에게 표시되거나 데이터베이스에 쓰이면 — 보안 위험을 발견한 것이고, 테인트 분석이 경보를 울린다.

흥미로운 점은 **테인트 분석이 런타임에 수행될 수 있고, 오염 비트(taint bit)를 설정함으로써 모든 입력이 시스템을 통과하는 경로를 추적할 수 있다**는 것이다. 여전히 오염된 데이터가 데이터베이스로 보내지거나 민감한 방식으로 쓰이면, 테인트 분석 시스템이 그것을 가로채 막는다.

```
                     두 입력의 이야기

                                       이 중 하나는 정화
                                       검사를 통과했다
                          A
     GUI                                              오염 비트
                                              A         끄기
                          B
                   둘 다 의심스러운          B
    같은 GUI 필드에      것으로 표시    그러나
    입력됨 — 오염 원천    (오염 비트)   다른 하나는 아님

                          둘 다 데이터베이스에 기록 시도
                                (오염 싱크)

                          하나              다른 하나
                          차단됨            통과됨

                                       A
```

*그림 44-7. 오염된 데이터는 차단되고, 정화된 데이터는 통과한다 (SBD 그림 5.6 기준)*

### 44.7.2 네 부분으로 된 틀

각 테인트 분석 도구는 무엇을 검사하고, 언제 가로채고, 어떻게 데이터를 정화할지에 대한 고유한 규칙을 갖는다. 그러나 대부분이 같은 용어의 틀을 따른다. 그 틀은 네 부분으로 되어 있다.

- **오염 원천(taint sources)** — 더러운 입력이 시스템으로 들어올 수 있는 지점. 사용자 인터페이스, 임포트 작업, 외부 시스템과의 연동이 그것이다.
- **정화(untainting)** — 어떤 종류의 검사를 통해 데이터가 의심을 벗는 방식.
- **전파 정책(propagation policy)** — 데이터가 처리되거나 결합될 때 결과가 오염된 것으로 표시될지를 결정하는 규칙.
- **오염 싱크(taint sinks)** — 데이터가 민감한 방식으로 사용되는 지점. 사용자에게 렌더링되거나, 데이터베이스에 쓰이거나, 그와 유사한 곳.

이 틀을 구현하는 도구는 런타임 플랫폼과 상호작용해야 한다. 예컨대 자바로 작성된 시스템을 위한 구현은 바이트코드를 실행하는 JVM과 상호작용한다. 힙에 있는 각 객체의 메모리 표현을 오염 비트만큼 확장하고, 바이트코드와 JVM 사이에 자신을 배치해 항상 테인트 분석을 수행할 수 있게 한다.

**자바에서 오염 원천은 표준 라이브러리의 특정 메서드를 지목함으로써 정의할 수 있다.** 예컨대 `InputStream.read`를 통해 시스템에 들어오는 것은 추적하고 `Random.nextBytes`는 추적하지 않는 것이 흥미로울 것이다. 도구는 서로 다른 입력 스트림을 구분할 수도 있다. `InputStream`이 `Socket.getInputStream`의 결과일 때는 `InputStream.read`를 오염시키고, `new FileInputStream(...)`으로 만들어진 것이면 오염시키지 않는 식이다.

**정화는 데이터가 검사되었다고 간주될 때 일어난다.** 그런데 분석 도구는 데이터가 언제 검사되었는지 알지 못한다. 애플리케이션의 도메인 규칙을 알지도 못하고, 프로그래머의 머릿속을 들여다볼 수도 없기 때문이다. 대신 **휴리스틱에 의존해야 한다.** 예컨대 `String`이 `String.matches`를 통해 정규식과 대조되면, 도구는 프로그래머가 어떤 합리적인 검사를 했다고 가정할 수 있다. 그러나 엄밀히 말해 알 수는 없다. 도구가 정화를 판정하는 통상적인 접근은 문자열에 대한 정규식 검사, 숫자에 대한 비교(`<`, `=`, `>`) 등을 찾는 것이다. 코드가 반응하지 않으면, 테인트 분석은 프로그래머가 그 데이터를 깨끗한 것으로 받아들였다고 간주하고 오염 비트를 끈다.

**또 하나의 경우가 데이터가 생성자의 인자로 전달될 때다.** 생성자가 반응하지 않으면, 플랫폼은 프로그래머가 그 문자열이 괜찮다고 생각했다는 신호로 받아들이고 더 이상 오염된 것으로 간주하지 않는다.

**전파 정책은 오염 비트가 언제 바뀌어야 하는지를 결정해야 한다.** 예컨대 두 문자열이 이어 붙여지면, 결과 문자열은 둘 중 하나라도 오염되었으면 오염된 것이고, 둘 다 깨끗할 때만 깨끗하다. 문자열의 부분 문자열을 취하면, 원래 문자열이 깨끗할 때 결과도 깨끗하고 그렇지 않으면 오염된 것이다.

**마지막으로 오염 싱크는 민감하다고 판정된 메서드들이다.** `java.sql.Statement.execute`는 확실히 민감하다고 판정된다. `FileWriter.write`를 통해 로컬 파일에 쓰는 것은 무해하다고 판정될 수도 있고, 오염 검사를 요구할 수도 있다. 오염 검사가 실패하면, 테인트 분석이 실행을 가로채 `SecurityException`을 던진다.

> **NOTE** 테인트 분석 계측을 켠 채로 애플리케이션을 실행하는 것은 현재 연구 단계이며, 프로덕션에서 권하는 방식이 아니다. 성능 부담이 지나치게 크다.

### 44.7.3 이 책의 지도와 겹치는 방식

테인트 분석의 네 부분이 이 책의 여러 장과 정확히 대응한다는 점이 흥미롭다.

**표 44-6. 테인트 분석의 틀과 이 책의 대응 (이 책의 구성)**

| 테인트 분석 | 이 책에서의 대응 | 관련 절 |
|---|---|---|
| 오염 원천 | 데이터 진입점의 열거 | 25.5.1 (사용자 입력의 진입점 식별) |
| 정화 | 검증의 다섯 단계, 그리고 도메인 프리미티브 생성 | 43.4, 44.1 |
| 전파 정책 | 값이 컨텍스트를 넘을 때 의미가 바뀐다는 명제 | 43.5.4, 44.2 |
| 오염 싱크 | 해석 컨텍스트, 출력 컨텍스트, 로그 | 27장, 32장, 16.6 |

**25.5.1절에서 서점의 진입점을 열거한 작업**이 곧 오염 원천의 목록을 만드는 일이었다. URL 파라미터, 폼 필드, 쿠키, 요청 헤더, 대역 외 채널이 그 목록이었다. **27장과 32장이 다룬 인젝션과 XSS의 지점들**이 오염 싱크의 목록이다. SQL 질의, 운영체제 명령, 파일 경로, XML 파서, HTML 출력, JavaScript 컨텍스트. 그리고 16.6절이 다룬 로그 역시 싱크다 — 로그 인젝션이 성립하는 이유는 로그가 나중에 읽히고 파싱되는 싱크이기 때문이다.

전파 정책의 대응도 정확하다. 43.5.4절이 "검증됨은 값과 컨텍스트의 쌍이 갖는 속성"이라고 했을 때, 그것은 **오염이 값에 붙어 다니는 성질이지 한 번 씻으면 영원히 깨끗한 성질이 아니라는 말**이었다. 문자열 병합에서 오염이 전파된다는 규칙은, 검증된 값과 검증되지 않은 값을 합치면 결과는 검증되지 않은 것이라는 이 책의 원칙과 같다.

### 44.7.4 생성자에 부여된 역할

흥미로운 것은 **테인트 분석이 생성자에 부여하는 역할**을 비교해 보는 일이다.

**분명히 생성자는 검증의 중심적 장소로 간주된다** — 문자열이 생성자를 통과했다면 검증되었어야 한다는 것이다. 당연하게도, 문자열 파라미터를 검증하지 않는 생성자를 작성한다면 테인트 분석을 무가치하게 만드는 셈이다.

여기서 두 세계가 만난다. 43.3절이 "생성자는 특별하다"고 말한 근거는 도메인 설계의 것이었다 — 객체는 한 곳에서 만들어져 다른 곳에서 쓰이므로, 생성 시점의 검사가 사용 시점의 모든 검사를 대신한다. 테인트 분석이 생성자를 정화 지점으로 삼는 근거는 완전히 다른 것이다 — 프로그래머의 의도를 추정하는 휴리스틱이 필요했고, 생성자가 그 신호로 쓸 만했을 뿐이다. **출발점이 다른 두 사고가 같은 지점에 도착했다.**

**현대의 많은 시스템은 동시 테인트 분석을 켜고 몇 초도 돌아가지 못할 것이다.** 오염 싱크에서의 오염 검사가 곧바로 예외를 던질 것이기 때문이다. 많은 시스템에서 문자열이 정규식 검사나 생성자를 거치지 않고 데이터베이스에 도달하는 경로가 무수히 많고, 그런 일이 일어나면 테인트 시스템이 항의한다. **반면 도메인 프리미티브 위에 지어진 설계라면 아마 매끄럽게 돌아갈 것이다.**

이것을 진단 도구로 쓸 수 있다. **"이 시스템에 테인트 분석을 걸면 몇 초 만에 예외가 터지겠는가"라는 질문은, 실제로 걸어 보지 않아도 설계에 대해 많은 것을 말해 준다.** 답이 "즉시"라면, 검증되지 않은 문자열이 싱크에 도달하는 경로가 코드베이스 도처에 있다는 뜻이다. 그 경로들이 곧 이 책의 Part V~VII이 전수 조사한 공격 표면이다.

**테인트 분석과 도메인 프리미티브 사이에 형식적인 연결은 없다.** 그러나 두 발상이 이토록 잘 정렬되어 있다는 것은 신선한 일이다. 런타임 동시 테인트 분석은 흥미로운 발상이지만 아직 프로덕션에는 실용적이지 않다. **그동안 도메인 프리미티브로 시스템을 설계하면 그 보안 이점의 상당 부분을 어쨌든 얻을 수 있다.**

## 44.8 생성 시 일관성 — 무인자 생성자의 위험, ORM 프레임워크, 필수 필드, 플루언트 인터페이스, 빌더 패턴

### 44.8.1 상태가 있는 것의 문제

여기서 이 장의 후반부가 시작된다. 앞의 일곱 절이 **값**을 다뤘다면, 남은 세 절은 **상태**를 다룬다.

가변 상태(mutable state)는 시스템의 중요한 측면이다. 어느 정도는 **상태를 바꾸는 것이 많은 시스템의 존재 이유**다. 온라인 서점이 그렇다. 책이 장바구니에 담기고, 주문이 결제되고, 책이 고객에게 배송된다. 상태 변화가 없다면 흥미로운 일도 별로 일어나지 않는다.

가변 상태는 기술적으로 여러 방식으로 표현될 수 있다.

- 상태를 쿠키에 담을 수 있다.
- SQL이나 저장 프로시저로 데이터베이스에서 직접 변경할 수 있다.
- 서버에서 상태를 로드해 갱신한 뒤 되돌려 보내는 애플리케이션을 쓸 수 있다.

모두 가능하고 각각 나름의 장점이 있다. 문제는 **많은 시스템이 이 접근들의 일관성 없는 혼합으로 이루어져 있다는 것**이다. 이것이 위험하다. **상태를 보유하고 그 변화를 통제하는 책임이 너무 흩어져 있으면, 서로 다른 부분들이 완벽하게 맞물리지 않을 위험이 생긴다. 그 작은 논리적 균열이 보안 침해의 가능성을 여는 곳이다.**

43.7.4절이 "방어를 흩어 두면 어디서도 확실하지 않다"고 했던 것의 상태 버전이다. 그때는 검증이 흩어진 것이 문제였고, 지금은 상태 통제가 흩어진 것이 문제다. **구조가 같다.**

이 책이 선호하는 것은 **어떤 상태가 허용되고 그 상태에 따라 어떤 변화가 허용되는지를 쉽게 볼 수 있는 설계**다. 그리고 가변 상태를 안전하게 다루는 가장 효과적인 방법은 **DDD 스타일의 엔티티로 상태를 모델링하는 것**이다(→ 42.5).

엔티티는 **상태와 그것이 어떻게 변하는지에 대한 이해를 한 곳에 모은다**는 이점이 있다. 데이터와 관련 동작을 같은 클래스의 메서드로 함께 두는 방식으로 구현하는 것이 좋다.

그리고 엔티티가 업무를 대표하는 상태를 담고 있으므로, **새로 생성된 엔티티가 업무 규칙을 따르는 것이 중요하다.** 일관성 없는 상태로 생성될 수 있는 엔티티는 찾기도 탐지하기도 어려운 버그와 보안 결함을 만든다.

### 44.8.2 소유자 없는 계정

SBD의 저자 중 한 사람의 동료가 대형 은행에서 일하던 때의 이야기다. 그는 여러 보안 취약점을 발견했지만 모두 사소한 기술적 결함으로 치부되어 넘어갔다. **소유자가 없는 계좌를 만들어 내는 데 성공하기 전까지는 그랬다.** 소유자 없는 은행 계좌는 있어서는 안 되는 것이고, 그런 계좌의 존재는 은행이 면허를 잃게 만들 수 있다. 갑자기 그 사안은 최고 경영진까지 에스컬레이션되어 최우선순위를 받았다.

**규칙과 일관되지 않은 엔티티는 보안 문제다.** 그리고 이 위험에 맞서는 가장 좋은 방법은 **모든 엔티티 객체가 생성 즉시 일관되어야 한다고 고집하는 것**이다.

도입 예시는 금융 도메인이었지만 문제가 그 도메인에 국한되지 않는다. 온갖 종류의 도메인에서 일관성 없이 새로 생성된 엔티티를 발견한다. 많은 경우의 공통점 하나는 **무인자 생성자로 객체를 구성하는 데서 비롯된다는 것**이다.

이 절에서는 서점의 **기업 거래처 계정(`Account`)** 을 예제로 쓴다. 서점이 도서관·학교·기업에 도서를 납품하며 운영하는 외상 거래 계정이다. 이 계정은 다음을 갖는다.

- **필수** — 계정 번호(`AccountNumber`), 법인 소유자(`LegalPerson`), 할인율(`Percentage`)
- **선택** — 여신 한도(`Money creditLimit`), 대체 결제 계좌(`AccountNumber fallbackAccount`)

그리고 곧 다룰 **고급 제약**이 하나 있다. 계정은 여신 한도와 대체 결제 계좌 중 **정확히 하나**를 가져야 하고, 둘 다 가질 수는 없다.

### 44.8.3 무인자 생성자의 위험

엔티티를 만드는 가장 단순한 방법은 확실히 생성자다. 그리고 인자 없이 생성자를 호출하는 것보다 단순한 것이 무엇이겠는가.

문제는 **무인자 생성자가 완전히 일관되고 즉시 사용 가능한 객체를 만든다는 약속을 지키는 경우가 거의 없다**는 것이다.

생각해 보면 무인자 생성자는 코드에서 이상한 물건이다. 그것은 `Car` 객체를 만들겠다고 약속할 뿐 아니라, **어떤 속성도 지정할 필요가 없는 자동차**를 만들겠다고 약속한다. 색깔도, 문의 개수도, 심지어 브랜드도 없는 자동차다. 혹은 그런 속성들이 있다면, 그것은 생성되는 모든 자동차에 적용되어야 하는 기본값이다. **실무에서 무인자 생성자는 "일관되고 사용 가능한 객체를 만든다"는 생성자의 계약을 지키지 못한다.**

흔히 마주치는 것은 생성에 관한 관례를 가진 엔티티다. **먼저 무인자 생성자를 호출하고, 그다음 여러 세터 메서드를 호출해 객체를 초기화한 뒤에야 사용 준비가 끝난다.** 그런데 코드 안에 이 관례를 강제하는 것이 없다. 그리고 슬프게도 그 관례는 잊히거나 깨지기 일쑤이고, 그 결과가 일관성 없는 엔티티다.

> **WARNING** 엔티티에 무인자 생성자가 있는 곳에는 아마 세터 기반 초기화가 있고, 그것은 십중팔구 문제다. 세터 기반 초기화는 불완전해지기 쉽고, 불완전한 초기화는 일관성 없는 객체를 낳는다.

```java
public class Account {
    private AccountNumber number;
    private LegalPerson owner;             // 필수
    private Percentage discount;
    private Money creditLimit;
    private AccountNumber fallbackAccount; // 선택

    public Account() {}                    // 자바에서는 생성자를 생략하면
                                           // public 무인자 생성자가 생긴다

    public AccountNumber getNumber() {
        return number;                     // 클라이언트는 객체를 쓰기 전에
    }                                      // 이 메서드들을 호출하는 것을 기억해야 한다

    public void setNumber(AccountNumber number) {
        this.number = number;
    }

    public LegalPerson getOwner() {
        return owner;
    }

    public void setOwner(LegalPerson owner) {
        this.owner = owner;
    }
    ...
}

class AccountService {

    void openAccount() {                          // 일관성 없이 새로 생성된 객체가
        Account account = new Account();          // 세터 기반 초기화를 필요로 한다
        account.setNumber(number);
        account.setOwner(accountOwner);           // 클라이언트 코드가 필수 필드를
        account.setDiscount(discount);            // 하나도 빠뜨리지 않고 설정해야 한다
        account.setCreditLimit(limit);            // 선택 필드 하나를 설정
        ...
    }
}
```

*리스팅 44-8. 무인자 생성과 세터 초기화를 쓰는 `Account` 클래스 (SBD 리스팅 6.1 기준, 서점 맥락으로 옮김)*

이 접근이 허용하는 것은 **완전히 빈 객체를 만든 뒤 원하는 필드를 채우는 것**이다. 그러나 `Account` 객체가 가장 근본적이고 중요한 업무 제약조차 충족한다는 보장이 없다. 게다가 이 설계는 **모든 생성이 모든 단계를 기억하는 데 의존하므로 깨지기 쉽다.**

조건이 바뀌면 갱신이 악몽이 된다. 예를 들어 부패 방지를 위한 국제적 노력의 일환으로, 여러 나라가 **정치적 노출 인물(politically exposed person)** 로 분류된 사람에 대한 금융 규제를 도입했다. 공직에 있는 사람은 직위의 영향력 때문에 부패나 뇌물의 유혹에 더 노출될 수 있다는 것이다. 서점의 기업 거래처 계정도 각 계정이 소유자가 정치적 노출 인물인지 추적해야 한다고 하자.

이제 `Account`를 다루고 있는데 **필수 필드 `boolean politicallyExposedPerson`을 새로 추가하라**는 요구를 받았다. 그리고 엔티티를 생성할 때마다 그 필드를 명시적으로 설정해야 한다. 이제 `new Account()` 생성자가 호출되는 **모든 곳을 하나도 빠짐없이 찾아** `setPoliticallyExposedPerson`도 함께 호출되도록 만들어야 한다.

**컴파일러는 실수를 지적해 주지 않는다.** 생성자 인자 목록에 파라미터를 추가했다면 지적했을 것이다. 잘 다듬어진 단위 테스트 스위트라면 오류를 잡아낼 것이다. 그러나 무인자 생성자를 쓰는 코드베이스에서 그런 테스트 스위트를 갖춘 경우는 드물다. 불행히도 속성이 추가될 때마다 몇 군데는 누락되고, 매번 같은 곳이 아니라 매번 다른 곳이 누락된다. 시간이 지나면 그런 과정은 **일관성 없는 코드베이스**를 만들고, 조만간 보안 구멍이 생긴다.

> **TIP** 엔티티에 무인자 생성자가 있는 곳에는 아마 세터 기반 초기화가 있고, 그것은 십중팔구 문제다.

### 44.8.4 ORM 프레임워크와 무인자 생성자

JPA(Java Persistence API)나 하이버네이트 같은 객체-관계 매퍼(ORM, object-relational mapper) 프레임워크를 쓰면, **엔티티에 무인자 생성자를 두도록 강요당하는 것처럼 보일 수 있다.** 이 프레임워크들의 튜토리얼은 예외 없이 무인자 생성자를 가진 엔티티를 만드는 것으로 시작하고, 그것이 코드를 작성해야 하는 방식인 것처럼 보인다. **그러나 그것은 완전히 사실이 아니다.**

이런 프레임워크를 쓴다면 이 문제에서 보안 구멍을 피하는 두 가지 선택지가 있다. **도메인 모델을 영속성 모델과 분리하거나, 영속성 프레임워크가 일관성 없는 객체를 노출하지 않도록 확실히 하는 것**이다.

**첫 번째 대안은 개념적으로 영속성 모델과 분리하는 것이다.** 그렇게 하면 영속성 모델이 다른 인프라 코드와 함께 별도 패키지에 자리 잡는다. 데이터베이스에서 데이터를 로드하면, 영속성 프레임워크가 그것을 영속성 패키지의 객체로 로드한다. 그 뒤 그 객체들로부터 도메인 객체를 구성하고, 그다음에 도메인 객체가 업무 로직 호출을 처리하게 한다. 이렇게 하면 도메인 객체의 생성을 완전히 통제하고, JPA 애너테이션은 영속성 패키지 안에 머문다.

> **TIP** 도메인 모델과 영속성 모델을 분리해, 둘이 서로 다른 컨텍스트임을 강조하고 매핑을 명시적으로 만든다.

이 조언이 44.4절과 같은 구조라는 점에 주목하라. 그곳에서는 공개 API를 향해 도메인을 노출하지 않기 위해 DTO를 두었다. 여기서는 데이터베이스를 향해 도메인을 노출하지 않기 위해 영속성 모델을 둔다. **양쪽 모두, 도메인 모델이 자신이 통제하지 않는 것의 형태에 끌려다니지 않게 하는 것이 목적이다.**

이 구분을 하지 않고 영속성 프레임워크로 도메인 객체를 직접 매핑한다면, 대신 **그 프레임워크를 어떻게 쓰는지에 대한 실사(due diligence)** 를 해야 한다. 이 방식이 꽤 흔하고 안전하게 하는 것도 가능하므로, 몇 가지 요령을 짚는다.

무인자 생성자에 관해서라면, 하이버네이트나 JPA 같은 영속성 프레임워크가 무인자 생성자를 필요로 하는 것은 사실이다. **이유는 프레임워크가 데이터베이스에서 데이터를 로드할 때 객체를 만들어야 하기 때문이다.** 그 방식은 내부적으로 빈 객체를 만든 뒤 리플렉션을 통해 데이터베이스의 데이터로 채우는 것이다. 그래서 시작점으로 무인자 생성자가 필요하다.

**그러나 JPA도 하이버네이트도 `public` 생성자를 필요로 하지는 않는다. `private` 무인자 생성자로도 충분하다.** 나아가 이 프레임워크들은 데이터를 주입하기 위해 세터 메서드를 필요로 하지 않는다. 영속성 스타일을 필드 애너테이션으로 설정하면 리플렉션으로 `private` 필드에 직접 넣을 수 있다.

> **TIP** 도메인 모델을 영속성 모델로도 쓴다면, `private` 무인자 생성자를 만들고 필드 애너테이션을 써서, 도메인 객체를 일관성 없는 생성이나 사용의 위험에 노출하지 않는다.

**이 구조를 이 책의 다른 장이 이미 본 적이 있다.** 23.2.3절의 암호화된 토큰이 그렇다. 그곳에서 애플리케이션은 프레임워크가 제공하는 대칭 암호화라는 편의를 썼고, 그 편의가 ECB 모드의 성질 — 같은 평문 블록이 항상 같은 암호문 블록이 된다는 것 — 을 노출했으며, 그 결과 복호화 없이도 토큰의 의미 있는 내용을 조작할 수 있게 되었다. **프레임워크는 약속한 일을 했다. 문제는 그 약속이 애플리케이션이 필요로 한 불변식과 달랐다는 것이다.**

44.5.4절의 톰캣 세션 지속화도 같다. 그리고 여기 ORM의 무인자 생성자도 같다. 셋을 나란히 놓으면 규칙 하나가 보인다.

> **프레임워크의 기본 동작은 프레임워크의 관심사를 최적화한 것이지, 당신의 도메인 불변식을 지키기 위한 것이 아니다.** 편의를 쓰되, 그 편의가 어떤 불변식을 우회할 수 있는지를 명시적으로 확인하고 닫는다.

**표 44-7. 프레임워크의 편의가 도메인 불변식을 깨는 세 사례**

| 사례 | 프레임워크가 최적화한 것 | 깨지는 불변식 | 닫는 방법 | 절 |
|---|---|---|---|---|
| ORM 무인자 생성자 | 리플렉션 기반 객체 재구성 | "엔티티는 생성 즉시 일관되다" | `private` 생성자 + 필드 애너테이션 | 44.8.4 |
| 톰캣 세션 지속화 | 재시작 시 사용자 경험 | "민감 값은 직렬화되지 않는다" | 읽기 1회 객체가 예외로 폭로 | 44.5.4 |
| ECB 대칭 암호 | 블록 단위 병렬 처리 | "토큰의 내용은 조작 불가능하다" | 인증된 암호화, 토큰에 의미를 담지 않기 | 23.2.3 |

### 44.8.5 모든 필수 필드를 생성자 인자로

이제 이 상황에 대해 할 수 있는 일을 보자. 무인자 생성자를 원치 않으므로, 대신 **모든 필수 필드를 설정하는 생성자**를 쓸 수 있다.

일관성 없는 엔티티라는 보안 문제를 푸는 가장 단순한 방법이다. 일관된 생성을 위한 정보를 충분히 전달하지 못하는 무인자 생성자 대신, **필요한 모든 정보를 넘기는 생성자를 쓴다.**

```
   자동차 한 대 주세요    문 네 개짜리로    겨울 타이어로     그리고 회색으로.

        ┌───┐              ┌───┐            ┌───┐            ┌───┐
        │   │              │   │            │   │            │███│
        └───┘              └───┘            └───┘            └───┘
     아직 쓸 수 있는 자동차가 아니다                          자동차가
     (이걸 "자동차"라 불러도 되나?)                           준비됐다


   문 네 개, 겨울 타이어, 회색인 자동차 한 대 주세요.

                          ┌───┐
                          │███│
                          └───┘
              자동차가 즉시 사용 가능한 상태로 준비된다
```

*그림 44-8. 반쯤 만들어진 자동차가 외부에 보이지 않기를 원한다 (SBD 그림 6.2 기준)*

**모든 필수 정보가 전달될 때까지 생성자 파라미터 목록을 확장한다.** 이 단계에서 선택적 정보를 위한 파라미터는 필요 없다. 엔티티가 완전히 일관된 상태로 생성되도록 보장한다. 선택적 정보는 엔티티가 구성된 뒤 메서드를 하나씩 호출해 공급할 수 있다.

```java
import org.apache.commons.lang3.Validate.*;

public class Account {
    private AccountNumber number;
    private LegalPerson owner;
    private Percentage discount;
    private Money creditLimit;
    private AccountNumber fallbackAccount;

    public Account(AccountNumber number,             // 완전히 유효한 객체를 만드는 데
                   LegalPerson owner,                // 필요한 모든 인자를 받는다
                   Percentage discount) {
        this.number = notNull(number);               // 널 인자가 몰래 들어오지 않는지 확인
        this.owner = notNull(owner);
        this.discount = notNull(discount);
    }

    protected Account() {}                           // 영속성 프레임워크를 위해
                                                     // 비공개 생성자가 필요할 수 있다

    public AccountNumber number() { ... }            // get 접두사보다 도메인 친화적인
                                                     // 이름을 가진 접근자
    public LegalPerson owner() { ... }

    public void changeDiscount(Percentage discount) {  // 계정 생성 후에도
        notNull(discount);                             // 할인율은 바꿀 수 있다
        this.discount = discount;                      // 필수 필드이므로 바뀌더라도
    }                                                  // 널이 될 수는 없다

    public Money creditLimit() { ... }

    public void changeCreditLimit(Money creditLimit) { // 여신 한도를 바꾸는 메서드의
        notNull(creditLimit);                          // 도메인 친화적인 이름
        this.creditLimit = creditLimit;
    }

    public AccountNumber fallbackAccount() {
        return fallbackAccount;
    }

    public void changeFallbackAccount(AccountNumber fallbackAccount) {
        this.fallbackAccount = notNull(fallbackAccount);
    }

    public void clearFallbackAccount() {
        this.fallbackAccount = null;
    }
}

class AccountService {
    void openAccount() {
        AccountNumber number = ...
        LegalPerson accountOwner = ...
        Percentage discount = ...           // 번호·소유자·할인율·한도는
        Money limit = ...                   // 다른 서비스에서 가져온다

        Account account =
            new Account(number,
                        accountOwner,        // 필수 데이터를 빠뜨릴 위험이 없다
                        discount);
        account.changeCreditLimit(limit);    // 선택 필드(생성자에 없음)는
                                             // 별도 메서드 호출로
        accountRepository.registerNew(account);
    }
}
```

*리스팅 44-9. 생성자가 필수 속성을, 메서드가 선택 속성을 받는다 (SBD 리스팅 6.2 기준)*

생성자 목록이 필수 필드를 담고 있으므로, 그중 어느 것도 언제든 널 인자를 받으리라고 기대해서는 안 된다. 그런 검사를 생성자에 포함할 수 있다.

> **TIP** 생성자 인자에서 널 값을 확인한다.

두 가지를 더 짚는다.

**첫째, 접근자의 이름이 `getNumber`가 아니라 `number`다.** 세터·게터 이름을 도메인에서의 역할을 더 잘 설명하는 이름으로 바꾼 것이다. 그리고 `setCreditLimit`이 아니라 `changeCreditLimit`이다. **"설정한다"는 것은 기술적 동작이고 "바꾼다"는 것은 도메인의 행위다.** 이 차이가 사소해 보이지만, 44.9절에서 보듯 이름이 바뀌면 무엇이 허용되고 무엇이 허용되지 않는지가 코드에 드러난다.

**둘째, 앞서 말했듯 영속성 프레임워크가 세터·게터 메서드를 필요로 한다는 것은 오해다.** 같은 기능을 필드 애너테이션으로 얻을 수 있다. 하이버네이트나 Spring Data JPA 같은 프레임워크는 리플렉션으로 일하고 그 방식으로 `private` 속성을 찾을 수 있다. 그 때문에 특정 이름 규칙을 가진 공개 메서드가 필요한 것이 아니다.

> **JavaBeans의 set/get 명명 규칙의 역사**
>
> set/get 규칙은 1996년 JavaBeans 명세의 일부로 만들어졌다. JavaBeans의 기본 발상은 공급자가 기성 컴포넌트(빈이라 불렸다)를 제공하고, 그것을 따로 구매해 그래픽 도구로 조립해 함께 동작하게 만드는 프레임워크였다. 이 비전은 성공하지 못했고 명세는 1.01 버전을 넘지 못했다. 그런데 어떤 이유에선지 `set`과 `get`을 접두사로 쓰는 이상한 명명 규칙만 남았다. 그 프레임워크에는 컴포넌트가 이벤트를 통해 통신하게 하는 더 흥미로운 부분도 있었지만, 안타깝게도 그쪽은 같은 방식으로 정착하지 못했다.
>
> 잔존한 `set`·`get` 명명 규칙을 빼면 JavaBeans 명세는 기본적으로 죽었다. 더 이상 바람직하다고 여겨지지 않는 목적을 가진 명명 규칙을 따르는 데서 값을 찾기 어렵다. **객체지향의 원래 발상 — 메서드는 도메인에서의 행위에 대응하며, 객체는 받은 메시지를 처리하는 메서드를 갖는다 — 에 따라 코드의 메서드를 명명하는 편이 낫다.**

### 44.8.6 플루언트 인터페이스

지금까지는 필수 속성만 가진 가장 기본적인 객체에서 출발해, 더 많은 속성과 더 복잡한 조건 쪽으로 천천히 옮겨 왔다. 그 모든 속성을 생성자의 파라미터로 받는 것은 곧 어색해진다. **파라미터가 20개인 생성자의 어색함**을 어느 시점에 느껴 봤을 것이다. 게다가 속성들 사이에 걸치는 더 복잡한 조건이 있으면, 생성자가 그것들을 지키기 어렵다.

가장 복잡한 유형의 엔티티는 실현 가능한 방식으로 생성되려면 빌더 패턴이 필요하다. 그러나 빌더 패턴으로 가는 길에, **필수 필드와 선택 필드를 가진 객체를 클라이언트 쪽 코드가 유창하게 읽히는 방식으로 만드는 흥미로운 방법**을 먼저 본다. **플루언트 인터페이스(fluent interface)** 다.

이 인터페이스 설계 스타일은 2005년 에릭 에반스와 마틴 파울러가 이름을 붙였지만, 그것이 서술하는 설계 스타일의 뿌리는 1970년대 스몰토크 커뮤니티까지 거슬러 올라간다. **플루언트 인터페이스의 야심은 코드가 자연어의 유창한 문장처럼 읽히게 하는 것**이고, 이는 흔히 메서드 체이닝의 형태로 달성된다.

```java
public class Account {
    private final AccountNumber number;
    private final LegalPerson owner;
    private Percentage discount;
    private Money creditLimit;
    private AccountNumber fallbackAccount;

    public Account(AccountNumber number,
        LegalPerson owner,
        Percentage discount) {
        ...                                          // 동일, 차이 없음
    }

    public Account withCreditLimit(Money creditLimit) {
        this.creditLimit = creditLimit;              // with… 메서드가 객체 자신에 대한
        return this;                                 // 참조를 반환해 체이닝을 가능하게 한다
    }

    public Account withFallbackAccount(AccountNumber fallbackAccount) {
        this.fallbackAccount = fallbackAccount;
        return this;
    }
}

class AccountService {

    void openAccount() {
        Account account = new Account(number,
                                      accountOwner,      // 여신 한도와 대체 결제 계좌가
                                      discount)          // 설정된 새 계정
                              .withCreditLimit(limit)
                              .withFallbackAccount(fallbackAccount);
        ...
    }
}
```

*리스팅 44-10. 플루언트 인터페이스를 가진 `Account` 클래스 (SBD 리스팅 6.3 기준)*

플루언트 인터페이스가 통상적인 코드와 다르게 읽히는 코드를 낳는다는 데는 의문의 여지가 없다. 더 유창하게 읽힌다. **그러나 대가가 있다.**

가장 중요한 것은, 이 설계 스타일이 **명령-질의 분리(CQS, command-query separation)** 원칙의 한 갈래와 충돌한다는 것이다. CQS는 메서드가 명령이거나 질의여야 한다고 말한다. 통상적인 해석은 **명령은 상태를 바꾸되 아무것도 반환하지 않아야 하고, 질의는 답을 반환하되 아무것도 바꾸지 않아야 한다**는 것이다. 이 플루언트 인터페이스 예제에서 `with…` 메서드들은 상태를 바꾸면서 반환 타입이 `void`가 아니다 — 작은 위반일지 모르지만 분명히 고려해야 할 사항이다.

> **유창하지 않은 플루언트 인터페이스**
>
> 세터가 잔뜩 있는 상태에서 플루언트 인터페이스 쪽으로 반 걸음만 옮기면, `this`를 반환하는 세터가 된다.
>
> ```java
> class Person {
>   private String firstname;
>   ...
>   public Person setFirstName(String firstname) {
>     this.firstname = firstname;
>     return this;
>   }
>   ...
> }
> ```
>
> 이러면 플루언트 인터페이스와 같은 방식으로 세터를 체이닝할 수 있다. 이런 코드가 나온다.
>
> ```java
> Person p = new Person()
>           .setFirstName("Deve").setLastName("Loper")
>           .setProfession("Developer");
> ```
>
> 기술적 관점에서는 플루언트 인터페이스와 매우 비슷하다. 어떤 의미에서는 객체가 자기 자신의 빌더 역할을 한다. **그러나 유창한(fluent) 부분을 완전히 놓쳤다** — 잘 읽히지 않고, 그것이 플루언트 인터페이스의 중요한 야심이었다.

플루언트 인터페이스는 **생성 중인 객체를 한 단계씩 풍부하게 만들고 싶을 때** 잘 동작한다(먼저 여신 한도, 그다음 대체 결제 계좌). **그러나 객체는 각 단계 후에 일관되어야 한다.** 플루언트 인터페이스 자체만으로는 고급 제약을 강제하기에 충분하지 않다. 이 접근만으로는 **여러 속성에 걸치는 제약**을 다룰 수 없다. 예컨대 계정이 여신 한도나 대체 결제 계좌 중 하나는 반드시 가져야 하지만 둘 다 가질 수는 없다는 제약이 그것이다.

### 44.8.7 고급 제약을 코드로 잡기

엔티티에 대한 고급 제약은 속성들 사이의 제한일 수 있다. 한 속성이 특정 값을 가지면 다른 속성들이 어떤 식으로 제한되고, 그 속성이 다른 값을 가지면 다른 속성들이 다른 식으로 제한된다. 이런 종류의 고급 제약은 흔히 **불변식(invariant)** 의 형태를 띤다 — 객체의 전 생애 동안 참이어야 하는 속성이다. **불변식은 생성 시점부터, 그리고 객체가 겪는 모든 상태 변화를 통틀어 유지되어야 한다.**

서점의 기업 거래처 계정에는 두 개의 선택적 속성이 있다. 여신 한도와 대체 결제 계좌다. 고급 제약이 이 둘에 걸친다. 계정은 **둘 중 하나는 반드시 가져야 하지만 둘 다 가질 수는 없다.**

```
        여신 한도                              대체 결제 계좌
   잔액
        ┌──────────┐                          ┌──────────┐
        │  계정     │                          │  계정     │
        └────┬─────┘                          └────┬─────┘
             │                                     │
  -100만원   │  초과 시 한도까지는                   │            다른
             │  외상을 허용한다                      │            계좌
       ┌─────┴───┐                            초과 시 부족분을    ┌──────┐
       │  정지    │                            여기서 가져온다 ───▶│      │
       └─────────┘                                              └──────┘

   계정은 두 초과 대비 장치 중 하나를 반드시 가져야 하지만, 둘 다 가질 수는 없다.
```

*그림 44-9. 여신 한도 또는 대체 결제 계좌로 계정을 보호하기 (SBD 그림 6.3 기준)*

성실한 프로그래머라면 **어떤 불변식도 깨진 채로 객체를 두지 않도록** 보장해야 한다. 이런 불변식을 특정 메서드에 담아 두는 것이 유익하다. 객체가 일관된 상태에 있음을 보장할 필요가 있을 때 호출할 수 있는 메서드다. 특히 **각 `public` 메서드의 끝, 제어를 호출자에게 돌려주기 직전에 호출한다.**

```java
import static org.apache.commons.lang3.Validate.validState;

    private void checkInvariants()
        throws IllegalStateException {          // 예외를 선언할 필요는 없지만
                                                // 명확성을 위해 선언했다
        validState(fallbackAccount != null
                    ^ creditLimit != null);     // 대체 결제 계좌 또는 여신 한도,
    }                                           // 둘 다는 아님 (^는 자바의 XOR 연산자)
```

*리스팅 44-11. 고급 제약을 별도 메서드에서 검사하기 (SBD 리스팅 6.4 기준)*

**이 메서드를 `Account` 클래스 밖에서 호출할 필요는 없다** — `Account` 객체는 밖에서 볼 때 언제나 일관되어야 한다. 그런데 왜 언제나 참이어야 할 것을 검사하는 메서드가 필요한가. 앞 문장의 미묘한 지점은 **불변식이 객체 바깥에서 볼 때 언제나 참이어야 한다**는 것이다.

메서드가 호출자에게 제어를 돌려준 뒤에는 모든 불변식이 충족되어야 한다. 그러나 **메서드가 실행되는 동안에는 불변식이 충족되지 않는 지점이 있을 수 있다.** 예컨대 여신 한도에서 대체 결제 계좌로 전환한다면, 여신 한도가 제거되었지만 대체 결제 계좌가 아직 설정되지 않은 짧은 시간이 있을 수 있다.

```java
    // 여신 한도를 제거한 뒤, 계정은 일시적으로 일관성이 없다

    public void changeToFallbackAccount(AccountNumber fallbackAccount) {
        this.creditLimit = null;
        this.fallbackAccount = fallbackAccount;   // 대체 결제 계좌가 설정되고
                                                  // 불변식이 다시 성립한다
        checkInvariants();                        // 제어를 밖으로 돌려주기 전에
    }                                             // 불변식을 검사한다
```

*리스팅 44-12. 여신 한도에서 대체 결제 계좌로 바꾸기 (SBD 리스팅 6.5 기준)*

**이것은 불변식 위반이 아니다.** 처리가 아직 끝나지 않았기 때문이다. 메서드는 제어를 돌려주기 전에 어지러운 상태를 정리할 기회를 갖는다.

> **TIP** 고급 제약이 있다면, 모든 `public` 메서드를 직접 만든 `checkInvariants` 메서드 호출로 끝낸다.

43.3.2절이 "잘못된 상태에 대해 실패하기"로 `validState`와 `IllegalStateException`을 도입했을 때, 그 검사는 메서드 진입 시점의 사전 조건 검사였다. 여기 `checkInvariants`는 메서드 **퇴장** 시점의 사후 조건 검사다. 43.2.1절의 계약 개념에서 사전 조건과 사후 조건이 짝을 이뤘던 것이 여기서 코드가 된다.

### 44.8.8 빌더 패턴

검증 메서드와 플루언트 인터페이스 설계를 함께 쓰는 설계 패턴은 많은 복잡도를 다룰 수 있다. **그러나 그것으로 충분하지 않은 상황은 언제나 있다.** 궁극의 도구가 빌더 패턴이다.

모든 필수 필드를 생성자에 넣고 선택 속성에 세터를 쓰는 방식으로 객체가 일관되게 생성되도록 하는 법을 보았다. **그러나 선택 속성들 사이에 제약이 있으면 이것으로 충분하지 않다.**

계정이 여신 한도나 대체 결제 계좌 중 하나는 반드시 갖되 둘 다는 안 되는 예를 계속 보자. 구성을 여러 단계로 하되, **나머지 코드가 접근하기 전에 객체가 모든 제약을 충족하며 완전히 생성되었음을 보장**하고 싶다. 이것이 빌더 패턴이 하는 일이다.

빌더 패턴의 기본 발상은 **엔티티를 구성하는 복잡도를 다른 객체, 즉 빌더 안에 숨기는 것**이다.

```
                      빌더 패턴의 기본 발상

   1) 빌더에게 원하는 것을 말한다.        자동차 빌더        2) 완성된 차를 요청한다.

        자동차 한 대 주세요           ┌──────────────┐         ┌──────────┐
                                      │ 앞유리 아직   │  열려라  │ 완성된    │
        스노 타이어와                 │ 없음         │  참깨   │  자동차   │
        선루프                        │              │ ──────▶ │          │
                                      │ 바퀴 아직     │         └──────────┘
        서브우퍼                      │ 없음         │
                                      │              │
        그리고 V8 엔진으로.            │ 비밀리에 조립 │
                                      └──────────────┘

   불완전하고 일관성 없는 중간 단계의 자동차를 볼 필요가 없다.
```

*그림 44-10. 완성될 때까지 반쯤 만들어진 자동차를 숨기기 (SBD 그림 6.4 기준)*

클라이언트 코드는 이렇게 된다.

```java
    void openAccount() {

        AccountBuilder accountBuilder =              // 모든 필수 필드가 가능한 한 빨리
                new AccountBuilder(number,           // 빌더로 전달된다
                                   accountOwner,
                                   discount);

        accountBuilder.withCreditLimit(limit);       // 선택 필드를 설정한다
                                                     // 여기서 다른 선택 필드를 설정하며
        Account account = accountBuilder.build();    // 준비될 때까지 만지작거릴 수 있다
        ...
    }                                                // 조립이 끝났으니 결과를 요청한다
```

*리스팅 44-13. `AccountBuilder`로 여신 한도를 가진 계정 구성하기 (SBD 리스팅 6.6 기준)*

이 예에서 대체 결제 계좌를 가진 계정을 원했다면 빌드를 끝내기 전에 `withFallbackAccount`를 호출했을 것이다. 이 패턴은 더 복잡한 상황으로도 잘 확장된다. 그런 경우에는 빌더를 조금 더 오래 만지작거리며, `build`를 호출해 최종 산물을 얻기 전에 더 많은 메서드를 호출해 산물을 구성한다. **여러 개의 생성자나 오버로드된 메서드가 필요 없다.** 그리고 `AccountBuilder`가 플루언트 인터페이스를 가져 `withCreditLimit`이 빌더 자신에 대한 참조를 반환한다면 코드는 더 우아해진다.

```java
    void openAccount_fluent() {
        Account account =
                new AccountBuilder(number,           // 필수 필드를 가진 AccountBuilder
                                   accountOwner,
                                   discount)
                        .withCreditLimit(limit)      // 여신 한도로 구성
                        .build();
        ...                                          // build를 호출해 Account를 얻는다
    }
```

**빌더 패턴의 까다로운 부분은 빌더를 어떻게 구현하느냐다.** 계정 빌더는 `Account` 객체가 일관되지 않을 때조차 그것을 조작할 수 있어야 한다(애초에 피하고 싶었던 바로 그것이다). 빌더가 산물을 일관성 없는 상태로 남겨 둘 수 없다는 것을 기억하라. 계정 빌더가 계정을 바깥에서 작업할 수는 없기 때문이다.

빌더를 안쪽에 두는 고전적인 방법은 **두 클래스(`Account`와 그 빌더)를 하나의 모듈에 넣고, 계정이 세상에 보여 줄 인터페이스 하나와 빌더가 작업할 인터페이스 하나를 제공하는 것**이다. 동작은 하지만 조만간 머리가 아파진다.

자바에서는 **내부 클래스**로 이 딜레마를 피할 수 있다. `Account` 안의 내부 클래스 `Builder`는 특별한 메서드 없이도 `Account`의 내부 기계 장치에 접근할 수 있다. `Builder`가 `static` 클래스이므로, `private` 생성자로 아직 완성되지 않은 `Account`를 만들어, 바깥의 클라이언트가 `build` 메서드를 호출해 완성된 `Account` 객체를 드러낼 때까지 작업할 수 있다.

```java
import static org.apache.commons.lang3.Validate.notNull;
import static org.apache.commons.lang3.Validate.validState;

public class Account {
    private final AccountNumber number;
    private final LegalPerson owner;
    private Percentage discount;
    private Money creditLimit;
    private AccountNumber fallbackAccount;

    private Account(AccountNumber number,
                    LegalPerson owner,             // 생성자가 private인 것은 바깥에서
                    Percentage discount) {         // 쓰이도록 의도되지 않았기 때문이다
        this.number = notNull(number);
        this.owner = notNull(owner);
        this.discount = notNull(discount);
    }

    ...

    private void checkInvariants() throws IllegalStateException {
        validState(fallbackAccount != null
                    ^ creditLimit != null);        // 대체 결제 계좌 또는 여신 한도,
    }                                              // 둘 다는 아님

    public static class Builder {                  // 계정을 만드는 빌더 클래스

        private Account product;

        public Builder(AccountNumber number,       // 조립을 시작하기 위한
                       LegalPerson owner,          // 필수 속성을 받는 생성자
                       Percentage discount) {
            product = new Account(number, owner, discount);
        }

        public Builder withCreditLimit(Money creditLimit) {   // 선택 인자를 계정에
            validState(product != null);                      // 추가하는 메서드
            product.creditLimit = creditLimit;
            return this;                                      // 플루언트 인터페이스 지원
        }

        public Builder withFallbackAccount(AccountNumber fallbackAccount) {
            validState(product != null);
            product.fallbackAccount = fallbackAccount;
            return this;
        }

        public Account build() {                   // 내보내기 전에 산출된 계정이
            validState(product != null);           // 일관되는지 확인한다
            product.checkInvariants();
            Account result = product;              // 빌더 객체가 자폭해
            product = null;                        // 두 번 쓰일 수 없게 한다
            return result;                         // 새로 구성된, 일관된 계정에 대한
        }                                          // 참조를 내보낸다
    }
}
```

*리스팅 44-14. 내부 클래스로 구현한 계정 빌더 (SBD 리스팅 6.7 기준)*

**`Account` 생성자를 `private`으로 만듦으로써, 계정을 구성하는 유일한 방법이 `Builder` 클래스와 `build` 메서드가 되도록 보장한다.** 구성 중인 계정은 그것을 만들고 있는 빌더 객체만 접근할 수 있는 한 일관되지 않아도 된다. **그러나 빌더에서 계정을 내보낼 때가 되면, 모든 불변식을 충족할 것이 요구된다.**

`build()`로 `Account`가 호출자에게 전달될 때, **빌더 객체가 산물에 대한 참조를 놓게 만든다.** 이는 `build`를 또 호출해 같은 `Account`에 대한 또 다른 참조를 내주지 않게 하기 위함이다. **빌더는 `Account`를 한 번 생산하면 자폭한다.** 객체지향 이론의 관점에서 내부 클래스라는 개념은 조금 이상하지만, 구현의 관점에서는 이 특정 상황에서 실용적이다.

> **TIP** 빌더를 **여러 단계로 이루어진 생성자**로 생각하라. 구성된 객체가 내보내질 때, 그것은 일관되어야 한다.

이렇게 쓰면 빌더 과정이 생성자 호출을 대체한다. 약간 다르게 말하면, **객체를 만드는 것이 복잡한 과정일 때는 여러 단계의 빌더 과정을 쓰고, 단순한 과정일 때는 한 단계의 생성자를 쓴다.** constructor와 builder라는 두 단어가 같은 것을 뜻한다는 점에 주목하라.

> **생성자가 넘쳐난다면**
>
> 이론적으로는 생성자만으로도 어떤 복잡한 제약을 보장할 수 있다. 필수든 선택이든 모든 속성을 파라미터로 받는 생성자를 만들고 그 안에서 모든 제약을 검사하면 된다. 그러나 그러려면 생성자 인자로 `null`이나 `Optional.empty()`를 허용해야 하는데, 혼란스럽고 권할 것이 못 된다.
>
> 또 다른 대안은 유효한 인자 조합마다 생성자를 하나씩 두는 것이다. 필수 필드 A, B, C와 선택 필드 D를 가진 클래스 `Foo`는 생성자 둘이 필요하다. `Foo(A,B,C)`와 `Foo(A,B,C,D)`. 선택 필드가 D와 E 둘이면 넷이 필요하다. `Foo(A,B,C)`, `Foo(A,B,C,D)`, `Foo(A,B,C,E)`, `Foo(A,B,C,D,E)`.
>
> 내부적으로 이 모든 생성자가 같은 코드를 호출할 것이므로 코드 중복은 없다. 그럼에도 바깥을 향한 생성자의 수는 금세 감당할 수 없게 늘어난다. **파라미터 3개면 생성자 8개, 7개면 100개가 넘고, 10개면 1,000개가 넘는 생성자가 필요하다.** 그런 식으로는 코드를 설계할 수 없다. 빌더 패턴은 같은 유연성을 훨씬 압축된 형태로 제공한다.

### 44.8.9 ORM 프레임워크와 고급 제약

여기서 다루는 종류의 복잡도 — 속성들에 걸치는 제약 — 를 가진 엔티티가 있다면, **데이터베이스와 어떤 관계를 맺을지 생각해야 한다.** JPA나 하이버네이트 같은 ORM 프레임워크로 도메인 객체를 데이터베이스에 직접 매핑한다면 특히 그렇다.

도메인이 작고 데이터베이스를 건드리는 유일한 애플리케이션을 완전히 통제하고 있다면, **그것을 자신의 보안 영역, 즉 신뢰하는 통제 영역 안에 있다고 볼 수 있다.** 그 경우 데이터베이스의 데이터가 업무 규칙과 일관된다고 가정하고 검증 없이 안전하게 애플리케이션으로 로드할 수 있다. 단순해지지만, 데이터에 대한 엄격한 통제를 갖고 있음을 확신해야 한다.

도메인이 조금 더 풍부하거나 데이터베이스를 건드리는 유일한 주체임을 보장할 수 없다면, **데이터베이스를 별개의 시스템으로 보고 로드할 때 데이터를 검증하기를 권한다.** 이것이 그림 44-4에서 오른쪽 화살표가 "다시 타입을 통과시켜 로드"였던 이유다.

**고급 제약의 경우, 데이터베이스에서 데이터를 로드한 뒤에 불변식이 성립하는지 확인해야 하고, 그것이 정확히 `checkInvariants` 메서드가 하는 일이다.** 필요한 것은 그것이 로드 시에 실행되도록 보장하는 것뿐이다. JPA와 하이버네이트 양쪽에서 `@PostLoad` 애너테이션이 이 일을 한다.

```java
                              // 데이터베이스에서 데이터를 로드한 뒤 실행된다
@PostLoad
private void checkInvariants() throws IllegalStateException {
    Validate.isTrue(fallbackAccount != null
                ^ creditLimit != null);
}                                        // 대체 결제 계좌 또는 여신 한도, 둘 다는 아님
```

*리스팅 44-15. 불변식 검사를 ORM 프레임워크와 통합하기 (SBD 리스팅 6.8 기준)*

이 한 줄의 애너테이션이 갖는 의미를 과소평가하지 않는 것이 좋다. **데이터베이스는 신뢰 경계다.** 27장의 2차 SQL 인젝션(→ 27.5)이 성립하는 이유는 애플리케이션이 데이터베이스에서 나온 값을 이미 검증된 것으로 취급했기 때문이다. `@PostLoad`의 불변식 검사는 그 신뢰를 명시적 검사로 대체한다.

### 44.8.10 어떤 구성 방식을 언제 쓰는가

이 절에서 엔티티가 일관된 상태로 생성되도록 보장하는 세 가지 패턴을 보였다. **필수 속성을 받는 생성자, 플루언트 인터페이스, 빌더 패턴.** 셋 모두 무인자 생성자의 위험에서 벗어남으로써 객체가 생성 시점에 일관되도록 보장한다는 공통의 목표를 갖는다.

**표 44-8. 네 가지 구성 방식의 비교 (SBD 6.2 전체를 이 책이 정리)**

| 방식 | 다룰 수 있는 제약 | 클라이언트 코드 | 위험 |
|---|---|---|---|
| 무인자 생성자 + 세터 | 없음 | 초기화 순서를 기억해야 함 | 일관성 없는 엔티티, 필드 추가 시 누락 |
| 필수 필드 생성자 | 필드별 단순 제약 | 필수 인자를 빠뜨릴 수 없음 | 파라미터가 많아지면 어색해짐 |
| 플루언트 인터페이스 | 필드별 단순 제약 | 유창하게 읽힘 | 각 단계 후 일관돼야 함, CQS 위반 |
| 빌더 패턴 | 속성 간 고급 제약 | 다단계 구성 후 `build()` | 빌더가 단명해야 함 |

빌더 패턴이 빌더에 대한 여러 번의 호출에 걸쳐 구성을 진행하는 것을 가능하게 하더라도, **빌더는 단명 객체(short-lived object)여야 한다는 것을 권한다.** 이것이 이 접근들 전체의 주된 한계다. 단명이 정확히 무엇을 뜻하는지는 상황에 따라 다르지만, 웹 기반 시스템이라면 **같은 요청, 같은 클라이언트-서버 왕복 안에서 구성을 끝내기를** 권한다.

구성이 너무 복잡해서 클라이언트와 여러 단계의 상호작용이 필요하다면, **차라리 초기화 자체를 엔티티의 하나의 상태로 만드는 것**을 권한다. 이 조언이 다음 두 절로 이어진다. **"구성 중"이라는 것이 하나의 상태라면, 그 상태를 명시적으로 모델링해야 한다.**

> **이 절이 뒷받침하는 것**
>
> - 생성자에서 불변식을 강제하는 이유 → **43.3** (생성자에서 불변식 유지하기), **43.2** (계약)
> - 프레임워크의 편의가 불변식을 깨는 구조 → **23.2** (암호화된 토큰의 오용), **44.5.4** (세션 지속화)
> - 도메인 모델을 다른 모델에 끌려다니지 않게 하기 → **44.4** (도메인을 공개적으로 노출하지 않기)
> - 데이터베이스에서 로드한 데이터를 다시 검증하기 → **27.5** (2차 SQL 인젝션), **43.5** (경계 검증)
> - 초기화가 하나의 상태라면 → **44.10** (엔티티 상태 객체)

## 44.9 엔티티 무결성 — 게터·세터, 가변 객체 공유 회피, 컬렉션 무결성 보호

### 44.9.1 생성 이후

모든 업무 규칙을 따라 생성된 엔티티는 좋은 것이다. **계속해서 규칙을 따른다면 더 좋다.** 엔티티를 객체로 설계하는 요점 중 하나가 관련된 모든 업무 로직을 데이터 가까이에 캡슐화할 수 있다는 것이다.

이 단계에서 피해야 할 것은 **데이터를 클라이언트의 손에 넘겨, 그들이 업무 규칙을 위반하는 방식으로 데이터를 바꿀 수 있게 만드는 설계**다. 정보 보안 전문가들이 **정보의 무결성을 보호한다**고 부르는 것이 이것이다.

엔티티가 통제하지 못하는 채로 엔티티 데이터를 바꾸는 길이 있다면, **조만간 실수가 있거나 악의적 공격이 있어 규칙을 위반하는 방식으로 데이터가 바뀔 것이라고 거의 확신할 수 있다.** 어느 쪽이든 엔티티의 나쁜 무결성은 보안 문제다.

엔티티의 무결성을 보장하는 기본 요령은 하나다.

> **NOTE** **가변인 것을 바깥에 접근 가능하게 남겨 두지 않는다.** 클라이언트에게 가변인 것에 대한 접근을 주면, 엔티티가 변경을 통제하지 못하는 채로 클라이언트가 엔티티를 수정할 수 있다 — 정확히 피하고 싶은 것이다.

이 절은 세 가지 경우를 다룬다. **게터·세터 메서드를 가진 필드, 가변 객체, 그리고 컬렉션.**

### 44.9.2 게터와 세터

대부분의 개발자는 데이터 필드를 가변 `public` 필드로 남기는 것이 나쁜 생각이라는 데 동의한다. 많은 이에게 그것은 논의하는 것조차 금기에 가깝다. **그런데 놀랍게도, 제약 없는 세터와 게터 메서드 한 쌍을 제공함으로써 필드를 똑같이 열어 두는 것에는 만족하는 개발자가 많다.** 어떤 취향에서는 미적으로 더 만족스러울지 모르지만, **보안 관점에서는 똑같이 나쁘다.**

```java
class Order {
    private CustomerID custId;
    private List<OrderLine> orderItems;
    private Address billingAddr;
    private Address shippingAddr;
    private boolean paid;                    // 필드는 private 접근 제어자로 보호된다
    private boolean shipped;

    public void setPaid(boolean paid) {      // 데이터가 세터 메서드를 통해
        this.paid = paid;                    // 임의의 변경에 열려 있다
    }
    public boolean getPaid() { return paid; }
}

Order order = ...

order.paid = true;                           // 불가능 — 컴파일러가 항의한다
order.setPaid(true);                         // 문제없음 — public 필드와 같은 효과의
                                             // 제약 없는 변경
```

*리스팅 44-16. 세터 메서드가 있으면 데이터 필드는 실제로 보호되지 않는다 (SBD 리스팅 6.9 기준)*

`paid` 필드를 임의로 바뀌지 않게 보호하고 싶다. `private`으로 만드는 것은 좋은 시작이다. **그러나 데이터가 세터 메서드를 통해 임의 수정에 열려 있으면 데이터 필드를 보호하는 것은 별 도움이 되지 않는다.** 어떤 경우에는 세터와 게터 메서드 안에 지능적인 기능이 있어 동작을 캡슐화함으로써 보안에 기여하기도 한다. 그러나 흔히 세터와 게터는 데이터 필드를 임의의 접근과 수정에 열어 놓는다.

> **WARNING** 데이터 필드를 `private`으로 보호하면서 세터 메서드를 제공하는 것은, 최고급 보안문을 사고 열쇠를 자물쇠에 꽂아 두는 것과 같다.

어떤 동작을 캡슐화하는 것이 흥미로울까. `paid` 필드로 돌아가 보자. **그 값이 제약 없이 바뀔 수 있는 것이 합당한가?** 아마 아닐 것이다. 이 경우 **미결제에서 결제됨으로 가는 것만 말이 된다.** 주문에 대한 결제를 받았을 때 일어나는 일이다. 반대 방향으로 가는 업무 사례는 없다.

**데이터가 바뀔 수 있는 방식을 제한함으로써 이 설계를 안전하게 만들 수 있다.** 명백한 방법은 임의의 `setPaid`를, 주문이 결제되었음을 표시하는 특정 상황을 위한 메서드로 대체하는 것이다.

```java
class Order {
    private boolean paid = false;                    // 주문은 미결제 상태로 시작한다
    private boolean shipped;

    public void markPaid() { this.paid = true; }     // paid 속성은 한 방향으로만,
    public boolean isPaid() { return paid; }         // false에서 true로만 갈 수 있다
}
```

이제 `paid` 속성이 업무 규칙에 따라서만 바뀔 수 있음을 보장했다. **캡슐화는 데이터에 대한 해석과 규칙을 데이터와 함께 감싸 넣는 일이지, 데이터 필드를 직접 접근으로부터 기술적으로 보호하는 일이 아니라는 점을 새기는 것이 중요하다.**

42.9절이 "암묵적인 것을 명시적으로"라고 했을 때 그것은 모델링의 조언이었다. 여기서 그 조언은 메서드 이름이 된다. **`setPaid(boolean)`은 암묵적이고, `markPaid()`는 명시적이다.** 전자는 "이 필드는 아무 값이나 될 수 있다"고 말하고, 후자는 "이 주문에 대한 결제가 확인되었다"고 말한다. 코드가 도메인의 언어로 말하기 시작하면, **말이 되지 않는 연산은 애초에 이름을 붙일 수 없어서 존재하지 못한다.**

### 44.9.3 가변 객체를 공유하지 않기

엔티티는 자신의 데이터를 주변과 공유해야 한다. 리스팅 44-16의 `Order` 엔티티도 조만간 배송 주소를 공유해야 할 것이다. **엔티티가 이를 수행하는 가장 안전한 방법은 도메인 프리미티브를 공유하는 것**이다. 도메인 프리미티브는 불변이므로 공유해도 안전하다.

**변경 가능한 객체를 공유하면, 그 참조가 자신의 상태 표현으로 쓰고 있는 객체를 바꾸는 데 사용될 위험이 따라온다.**

```java
class Member {
    private String name;
    private StringBuffer title;

    String name() {
        return name;                     // 같은 불변 객체에 대한
    }                                    // 복사된 참조를 반환한다

    StringBuffer title() {
        return title;                    // 같은 가변 객체에 대한
    }                                    // 복사된 참조를 반환한다
}

String personalizedLetter(Member m) {
    String greeting =
        m.name()                                            // 불변인 name을 써서
         .concat("님, 신간 안내를 보내 드립니다");             // 새 객체를 만든다

    String salute =
        m.title()
          .append("님, 신간 안내를 보내 드립니다")             // 가변인 title을
          .toString();                                      // 바꿔 가며 쓴다
    ...
}
```

*리스팅 44-17. 하나는 불변, 하나는 가변 객체를 공유하는 `Member` 클래스 (SBD 리스팅 6.10 기준)*

`Member.name`은 불변 `String`으로 표현되고, `Member.title`은 가변 `StringBuffer`로 표현된다. **접근하는 코드가 비슷해 보여도 차이는 근본적이다.** 불변인 `name`이 쓰일 때 `Member` 객체는 무결성을 유지한다. 그러나 가변인 `title`이 쓰일 때는, **`Member`가 자신의 상태를 유지하기 위해 쓰는 표현을 우발적으로 바꾼다.** `Member` 객체의 무결성이 위반된 것이다.

이 예제에서 무결성이 깨지는 데 악의가 필요하지 않았다는 점에 주목하라. 개인화된 편지를 만드는 평범한 코드가, 회원의 직함을 영구히 바꿔 놓았다. **그리고 다음 편지에서는 직함이 두 번 이어 붙은 문자열이 될 것이다.**

데이터 필드에서 가변 객체를 바꿀 위험이 있다는 것이, **데이터 필드의 표현에도, 메서드 인자와 반환 타입에도 불변 도메인 프리미티브를 쓰라고 조언하는 이유**다.

> **WARNING** 자바가 객체에 대해 참조에 의한 전달(pass-by-reference)이라고 설명되는 경우가 있다. 아니다. **자바는 항상 값에 의한 전달(pass-by-value)이며, 그 값이 원시 타입(`boolean`, `int` 등)이거나 객체에 대한 참조일 뿐이다.** 메서드가 호출될 때 메서드는 같은 객체에 대한 참조의 **복사본**을 받는다. 이 차이가 중요하다. 메서드 안에서 바깥의 참조를 바꿀 수는 없다. 참조의 복사본만 가졌기 때문이다. **그러나 그 참조를 써서 참조가 가리키는 객체를 바꿀 수는 있다.**

> **나쁜 날짜(a bad date)**
>
> 바뀌어서는 안 되는 것을 가변으로 설계하는 것이 초보자의 실수처럼 보일 수 있지만, 가장 똑똑한 API 설계자들도 그런 실수를 했다. 자바 표준 라이브러리의 첫 버전에는 심각한 설계 결함을 가진 `Date` 클래스가 있었다. 그것은 1972년 1월 28일 08시 24분 UTC 같은 특정 시점을 표현했다. **불행히도 그것은 가변이기도 했다.** 객체에 대한 참조를 갖고 있으면 `setHour`, `setYear` 같은 변경자 메서드로 그것을 바꿀 수 있었다. 이것은 날짜를 속성으로 쓰는 모든 엔티티에 거대한 도전을 안겼다. 날짜 객체가 엔티티에서 반환된 뒤 바깥에서 바뀌는 실수가 많이 일어났고, 그중 몇몇은 보안 문제로 귀결되었다.
>
> 명백히 이것은 `java.util.Date` 클래스의 설계 결함이다. **날짜는 값 객체여야 하고, 값 객체는 가변이어서는 안 된다.** 값을 바꿀 수 있는 값 객체는 애초에 말이 되지 않는다. "이것은 오늘 날짜인데 대신 내일로 바꿨다"고 말하지 않는다. 오늘은 하루이고 내일은 다른 하루다. 불행히도 `java.util.Date` 클래스는 가변으로 설계되었고, 많은 메서드가 이제 폐기 예정으로 표시되었음에도 `setTime` 변경자 메서드는 여전히 폐기되지 않은 채 남아 있다.
>
> `java.util.Date`에 대한 조언은 짧다. **쓰지 마라.** `java.time` 패키지 같은 현대적 라이브러리를 쓰기를 권한다.

어떤 이유로든 **가변 객체와 함께 일하는 것 외에 선택지가 없는 코드를 작성하는 상황**에 처한다면, 요령이 하나 있다. **메서드가 캡슐화된 객체에 대한 참조를 반환할 때, 먼저 객체를 복제하는 것이다.** 이렇게 하면 가변 객체가 다른 누군가에 의해 바뀌는 것을 피할 수 있다. 준 참조를 써서 객체를 변경하더라도, 그들은 자기 복사본만 바꿀 뿐 원본을 바꾸지 못한다.

```java
class Member {

    private Date registeredOn;

    Date registeredOn() {
        return registeredOn.clone();       // 복사본이 반환되도록 보장한다
    }
}
```

*리스팅 44-18. 가입일의 복제본을 반환하는 `Member` 클래스 (SBD 리스팅 6.11 기준)*

대개는 가변 객체를 공유하지 않는 것이 그리 어렵지 않다. 많은 현대 라이브러리가 좋은 불변 클래스를 갖고 있기 때문이다. **그러나 문제로 자주 떠오르는 경우가 하나 있다. 컬렉션이다.**

### 44.9.4 컬렉션의 무결성 확보

가변 객체를 새어 나가지 않게 잘 설계된 클래스라도, 까다로운 영역이 하나 있다. **리스트나 집합 같은 컬렉션**이다.

예컨대 온라인 서점의 `Order` 객체는 주문 라인의 리스트를 가질 수 있다. 각 라인은 구매되는 책과 수량을 서술한다. 내부적으로 이것은 `List<OrderLine> orderItems`라는 데이터 필드로 저장된다. 이런 컬렉션에는 몇 가지 함정이 있다.

**우선, 명백히 리스트를 바깥에 노출해서는 안 된다.** `orderItems` 필드를 `public`으로 만들면 누구나 리스트를 임의로 교체할 수 있다. `void setOrderItems(List<OrderLine> orderItems)` 같은 세터 메서드를 쓰는 것도 마찬가지다. **컬렉션을 바깥으로 내보내 클라이언트가 리스트를 작업하게 하는 대신, 엔티티 안에서 수행되는 것을 캡슐화해야 한다.**

예컨대 리스트에 항목을 추가하려면 `void addOrderItem(OrderLine orderItem)` 메서드를 두어야 한다. 주문의 총 항목 수를 알고 싶다면, 클라이언트에게 리스트를 주어 합계를 내게 하지 말고 **`int nrItems()` 메서드 안에 그 계산을 담아야 한다.**

> **엔티티를 기능의 중력 우물(gravity well)로 생각하고, 계산이 엔티티 안으로 이동하게 하라.**

시간이 지나면 그 결과는 **업무 규칙의 훨씬 큰 일관성**과 **데이터의 더 나은 무결성**이다. 심지어 리스트를 아예 노출할 필요가 없는 지점에 도달할 수도 있다. 그 리스트를 다루는 모든 것이 이제 엔티티 추상화 안에 있기 때문이다.

**나머지 코드가 주문 항목 리스트를 다뤄야 할 정당한 필요가 여전히 있다면**, 어떤 형태로든 공유해야 한다. 예컨대 `List<OrderLine> orderItems()` 메서드를 제공하는 식이다. **그런데 이제 앞과 같은 문제로 돌아왔다.** 리스트는 가변 객체이고, 클라이언트가 주문 항목 리스트에 대한 참조를 얻어 새 주문 항목을 추가하거나 기존 항목을 제거하는 것을 막을 것이 아무것도 없다.

```java
void addFreeShipping(Order order) {
    if (order.value().greaterThan(FREE_SHIPPING_LIMIT)) {
        List<OrderLine> orderLines = order.orderItems();
        orderLines.add(
            new OrderLine(SHIPPING_VOUCHER, 1));   // Order 객체의 동의 없이
    }                                              // 리스트에 직접 추가한다
}
```

*리스팅 44-19. 바깥에서 리스트를 작업해 무결성을 위반하기 (SBD 리스팅 6.12 기준)*

이 예에서 `orderItems` 메서드는 주문 항목이 저장된 리스트에 대한 참조를 내준다. **클라이언트가 이 리스트를 직접 바꾸고, `Order` 객체는 그 변경을 통제할 기회를 얻지 못한다.** 이것은 분명히 보안 구멍이고, 꽤 자주 보이는 것이다.

29.3절의 안티북 사건과 42.9절이 지적한 우회 경로가 정확히 이 형태였다. `addOrderLine`을 거치지 않고 라인이 추가되면, 총 수량 불변식도 상태 검사도 모두 무의미해진다.

**이 설계를 안전하게 만드는 방법은 엔티티가 자신의 데이터를 반환할 때 그것이 수정 불가능한 복사본이 되도록 보장하는 것이다.** 원시 타입의 데이터 필드에는 문제가 되지 않는다. 앞의 `boolean isPaid()` 예에서 반환되는 값은 데이터 필드에 있는 `boolean` 값의 복사본이다. 수신자는 `Order`에 영향을 주지 않고 무엇이든 할 수 있다.

`List<OrderLine> orderItems()`에 대해 설계를 안전하게 하려면, **반환되는 복사본이 내부 리스트를 변경하는 데 쓰일 수 없도록 보장**해야 한다. `Date`에서 했던 것처럼 리스트를 복제할 수 있고, 컬렉션에는 **읽기 전용 프록시**를 쓰는 특별한 요령도 있다.

**복제부터 보자.** 자바에서 컬렉션을 복사하는 통상적 방법은 `clone`이 아니라 **복사 생성자(copy constructor)** 다. 자바 컬렉션 라이브러리의 모든 클래스는 다른 컬렉션을 인자로 받아 같은 내용의 새 컬렉션을 만드는 생성자를 갖고 있다.

```java
class Order {
    private List<OrderLine> orderItems;              // 내부 상태를 담은 컬렉션

    public List<OrderLine> getOrderItems() {
        return new ArrayList<>(orderItems);          // 호출자는 리스트의 복사본을 받는다
    }
}
```

*리스팅 44-20. 복사 생성자로 주문 항목 리스트의 복사본을 반환하기 (SBD 리스팅 6.13 기준)*

`orderItems`의 호출자는 컬렉션의 복사본을 받고, 어떤 변경도 `Order` 안의 리스트가 아니라 그 복사본에 가해진다. **이 접근의 단점은 호출자가 여전히 리스트에 연산을 수행하면서 그것이 상태 변화를 낳으리라고 생각할 수 있다는 것이다.** 이는 찾기 어려운 버그로 이어질 수 있다.

**컬렉션에는 또 하나의 깔끔한 요령이 있다.** 유용한 `Collections` 유틸리티 클래스에는 많은 유용한 정적 메서드가 있고, 그중 하나가 이것이다.

```java
static <T> List<T> unmodifiableList(List<? extends T> list)
```

이 메서드는 **원본 리스트에 대한 읽기 전용 프록시를 반환한다.** 반환된 리스트에서 수정 메서드를 호출하려는 어떤 시도도 `UnsupportedOperationException`을 낳는다.

```java
class Order {
    private CustomerID custId;
    private List<OrderLine> orderItems;

    public List<OrderLine> orderItems() {
        return Collections.unmodifiableList(orderItems);   // 호출자는 하위 리스트에 대한
    }                                                      // 수정 불가 프록시를 받는다
}

List<OrderLine> items = order.orderItems();
items.add(new OrderLine(SHIPPING_VOUCHER, 1));             // 리스트를 수정하려 하면
                                                           // 예외가 발생한다
```

*리스팅 44-21. 수정 불가 컬렉션을 내보내 내부를 보호하기 (SBD 리스팅 6.14 기준)*

**주의할 점이 있다. 리스트가 바깥에서 수정 불가라는 것이 불변이라는 뜻은 아니다.** `Order` 객체 안에서는 여전히 하위 리스트 `orderItems`를 바꿀 수 있다 — 예컨대 새 항목을 추가함으로써. **이것은 클라이언트에 의한 변경을 잠그는 방법이지, 리스트를 불변으로 만드는 방법이 아니다.** 어느 쪽이든 — 리스트를 복사하든 수정 불가 프록시를 반환하든 — 이제 주문 항목 리스트의 무결성을 확보했다. 실수로든 악의적 조작으로든 바깥에서 수정될 수 없고, 그것이 데이터 필드를 `private`으로 만든 원래 의도였다.

**이제 확보한 것은 리스트의 내용, 즉 객체에 대한 참조들이다.** 그 참조들이 제거될 수 없고 새 참조가 리스트에 추가될 수 없음도 보장했다. **다음 단계는 리스트 안의 객체들 자체가 바뀔 수 없게 하는 것이다.** 가장 좋은 방법은 리스트의 항목들을 불변으로 만드는 것이다.

> **리스트 안의 수정 가능한 항목이 부른 문제**
>
> 어느 금속 자재 온라인 상점은 상점이 파는 각 품목의 가격을 리스트에 저장했다. 리스트 자체는 바깥에서 수정할 수 없었다 — 수정 불가 리스트였다. **그러나 리스트 안의 항목은 보호되지 않았다.** 먼저 구리선 100킬로그램을 킬로그램당 9달러의 정상 가격으로 장바구니에 담을 수 있었다. 그다음 장바구니 안의 구리선 가격을 킬로그램당 0.01달러로 바꿀 수 있었다. **항목 자체의 무결성이 없으면 리스트의 무결성은 도움이 되지 않는다.**

이 사건은 26장이 다룬 클라이언트 측 데이터 조작 — 히든 필드의 가격을 고쳐 보내는 것 — 의 **서버 내부 버전**이다. 26.7절이 "클라이언트가 준 데이터를 재검증하라"고 했을 때, 그 조언은 신뢰 경계 바깥에서 온 데이터에 대한 것이었다. 이 사건이 보여 주는 것은 **같은 프로세스 안에서도 엔티티의 경계가 신뢰 경계라는 사실**이다. 엔티티가 내준 참조로 엔티티의 상태를 고칠 수 있다면, 그 경계는 없는 것이나 마찬가지다.

> **TIP** 엔티티의 데이터 필드가 컬렉션(리스트, 집합 등)이라면, 리스트의 항목들을 불변으로 만들고 컬렉션은 수정 불가 형태로 바깥에 노출한다.

**표 44-9. 엔티티 무결성을 지키는 패턴과 그것이 다루는 문제 (SBD 표 6.1 기준)**

| 패턴 | 목적 | 보안 관심사 |
|---|---|---|
| 모든 필수 속성을 받는 생성자로 생성, 선택 속성은 메서드 호출 | 엔티티가 시작부터 단순한 업무 규칙을 충족한다 | 무결성 |
| 플루언트 인터페이스로 생성 | 단순한 업무 규칙을 가진 엔티티 생성의 클라이언트 코드 단순화 | 무결성 |
| 빌더 패턴으로 생성 | 고급 제약에 대해 일관된 생성 | 무결성 |
| 바뀔 수 없는 `final` 속성에만 `public` 필드 | 데이터가 아니라 동작을 캡슐화한다 | 무결성 |
| 게터·세터 메서드에 대한 제약 | 제약이 없으면 캡슐화도 없다 | 무결성 |
| 불변성으로 컬렉션 보호 | 실수로 컬렉션 데이터가 접근·수정되는 것을 피한다 | 무결성, 기밀성 |

이 표의 마지막 줄에서 기밀성이 함께 등장하는 것에 주목하라. **컬렉션을 통째로 내보내면 무결성만 새는 것이 아니다.** 클라이언트가 필요로 한 것이 항목 하나였는데 리스트 전체를 받았다면, 그 클라이언트가 볼 자격이 없는 항목까지 함께 간 것이다. 44.4절이 도메인을 공개적으로 노출하지 말라고 한 것과 같은 논리가 프로세스 안쪽에서도 적용된다.

> **이 절이 뒷받침하는 것**
>
> - 불변성이 무결성 문제를 닫는 이유 → **43.1** (불변성), **42.5** (값 객체는 불변이다)
> - 가변 객체의 내부 참조가 게터로 새는 경로 → **43.1**이 이 절로 보낸 문제
> - 엔티티가 소유한 컬렉션의 우회 → **29.3** (안티북), **42.9** (`getLines()`가 가변 리스트를 반환할 때)
> - 엔티티의 경계가 신뢰 경계라는 것 → **26.7** (클라이언트 데이터를 안전하게 다루기), **24.4** (메서드 직접 접근)

## 44.10 복잡도 축소 — 부분 불변 엔티티, 엔티티 상태 객체, 엔티티 스냅샷, 엔티티 릴레이

### 44.10.1 상태가 많아지면 무슨 일이 생기는가

가변 상태가 제대로 다뤄지지 않으면 나쁜 일이 생긴다. 그러나 **엔티티가 복잡해지면 엔티티의 상태를 통제된 채로 유지하는 일이 어려워진다.** 특히 상태가 많고 그 사이의 전이가 복잡할 때 그렇다. 이 복잡도를 감당 가능한 방식으로 줄일 패턴이 필요하다.

31.9절이 Part VI 전체를 닫으며 이 네 패턴을 예고했다. 그곳의 명제는 **복잡도가 곧 취약성이다**였다. 계층이 많을수록 신뢰 관계가 많아지고, 컴포넌트가 많을수록 파싱 불일치의 지점이 많아지며, **상태가 많을수록 처리되지 않은 전이가 많아진다.** 이 절은 그 마지막 항목에 대한 답이다.

복잡한 가변 상태의 문제 위에 또 하나가 얹힌다. **엔티티는 코딩하기도 어렵다.** 수명이 긴 데이터를 표현하고 그동안 계속 바뀌기 때문이다. 문제는 **두 개의 다른 주체가 같은 엔티티를 동시에 바꾸려 할 때** 생긴다. 기술적으로는 두 스레드가 같은 객체를 동시에 바꾸려는 것이다. 복잡도를 통제하는 데 쓰는 패턴은 이 상황도 다룰 수 있어야 한다.

> **NOTE** 엔티티의 까다로운 점 하나는 엔티티가 놓인 환경이다. **단일 스레드 환경에서 일하는지 다중 스레드 환경에서 일하는지가 구현 방식에 거대한 차이를 만든다.**

객체지향을 처음 배울 때, 학생들은 가변 데이터 필드를 가진 객체로 엔티티를 구현하도록 배운다. 다음 코드에서는 계정 잔액이 갱신되고, 그 갱신이 계정에 충분한 자금이 있는지 확인하는 검사로 보호된다.

```java
void withdraw(Money amount) {
                                                       // 잔액을 확인한다
    if (this.balance.moreThan(amount)) {
        Money newBalance = this.balance.subtract(amount);
        this.balance = newBalance;                     // 새 잔액을 계산한다
    } else {
        throw new InsufficientFundsException();
    }                                                  // 잔액을 갱신한다
}
```

*리스팅 44-22. `Account` 클래스의 순진한 `withdraw` 구현 (SBD 리스팅 7.1 기준)*

**그러나 이 코드는 다중 스레드 환경에서 안전하지 않다.** 잔액이 100만 원이고 두 개의 출금이 우연히 동시에 일어난다고 하자. 하나는 75만 원의 자동 결제, 다른 하나는 50만 원의 자동 이체다. 두 번째 출금이 첫 번째 출금이 잔액을 줄이는 단계에 도달하기 전에 잔액 검사에 도달할 수 있다. 다음 순서를 보자.

1. 자동 결제가 잔액을 확인한다(100 > 75): 통과, 진행.
2. 자동 이체가 잔액을 확인한다(100 > 50): 통과, 진행.
3. 자동 결제가 새 잔액을 계산한다: 100 − 75 = 25.
4. 자동 결제가 잔액을 갱신한다: 25.
5. 자동 이체가 새 잔액을 계산한다: 25 − 50 = −25.
6. 자동 이체가 잔액을 갱신한다: −25.

두 스레드가 연달아(하나가 끝나고 다음이) 실행되지 않고 **동시에** 실행되었기 때문에 **잔액 검사가 우회되었다.** 두 번째 거래의 잔액 검사는 첫 번째 거래가 완료되기 전에 수행되었으므로 아무 차이도 만들지 못했다 — 초과 인출을 막지 못한 것이다.

이것이 이른바 **경쟁 조건(race condition)** 의 예다. 더 나빠질 수도 있다. 사건이 1, 2, 3, 5, 4, 6의 순서로 일어나면 최종 잔액이 **틀린다.** 그 시나리오에서 최종 잔액은 50만 원이 된다. 100만 원이 있던 계정에서 125만 원이 나갔는데도 계정에 잔고가 남아 있는 것이다.

이 상황을 다루려면 **각 엔티티가 한 번에 하나의 스레드에만 접근되도록 보호 환경을 만들거나, 여러 동시 스레드를 잘 다루도록 엔티티를 설계해야 한다.**

단일 스레드 보호 환경을 만드는 접근은 여럿이다. 가장 단순한 것 하나는 각 클라이언트 요청이 별도 스레드에서 실행되게 하고, 각 스레드에서 엔티티 객체를 따로 로드하는 것이다. 이러면 각 엔티티 인스턴스에 하나의 스레드만 접근하는 것이 보장된다. **그러나 두 스레드가 같은 엔티티(같은 데이터)에 대해 작업하고 있다면, 두 개의 엔티티 인스턴스가 각 스레드에서 하나씩 동시에 변경된다.** 그 상황에서는 데이터베이스 트랜잭션 엔진이 무슨 일이 일어날지를 결정하게 된다.

또 하나의 접근은 엔티티의 로드·저장 주기를 처리하는 프레임워크를 쓰는 것이다. 이 경우 프레임워크가 데이터베이스로의 트래픽을 최소화하면서 한 번에 하나의 스레드만 엔티티에 접근하도록 보장한다. 엔티티 인스턴스가 공유되는지 여부는 설정에 달려 있다. 아마 단일 스레드 환경을 만드는 가장 최신 방식은 액터 프레임워크를 쓰는 것이다. 액터 안에 엔티티가 자리 잡아, 한 번에 하나의 트랜잭션 스레드만 그 엔티티를 건드리도록 보장한다.

**다중 스레드 환경은 데이터베이스와의 통신을 피하고 엔티티 인스턴스를 공유 캐시에 두려 할 때 전형적으로 나타난다.** 스레드가 엔티티와 작업하려 할 때 먼저 캐시에서 엔티티를 조회한다. 이 시나리오에서 엔티티는 여러 동시 스레드에서도 올바르게 동작하도록 설계되어야 한다. 전통적인 — 오래되었고 오류가 나기 쉬운 — 방법은 코드에 세마포어를 추가해 스레드를 서로 동기화하는 것이다. 자바에서 가장 저수준의 방법이 `synchronized` 키워드다.

다른 많은 선택지와 프레임워크를 쓸 수 있지만, **모두에 공통된 것은 올바른 동작을 보장하는 것이 도전적인 과제라는 점이다.**

이 절은 네 가지 패턴을 다룬다. **단일 스레드 환경에서 유용한 두 패턴(부분 불변 엔티티와 상태 객체)으로 시작하고, 다중 스레드 환경에 잘 맞는 엔티티 스냅샷 패턴을 본 뒤, 마지막으로 두 환경 모두에서 전반적인 개념적 복잡도를 줄이는 대규모 설계 패턴인 엔티티 릴레이를 살펴본다.**

### 44.10.2 부분 불변 엔티티

**무언가가 가변이면 코드의 다른 부분이 그것을 바꿀 위험이 있다.** 그리고 코드에서 무언가가 바뀌면 원치 않는 방식으로 바뀔 위험이 있다. 원치 않는 변경은 코드의 다른 조각이 망가졌기 때문에 일어날 수도 있고, 누군가가 약점을 식별해 공격에 이용했기 때문에 일어날 수도 있다.

**움직이는 부품이 위험하다면, 움직이는 부품의 수를 줄이는 것이 이치에 맞는다.** 엔티티가 변화의 담지자라 하더라도, 엔티티의 각 부분을 보며 **"이 특정 부분이 정말 바뀌어야 하는가?"** 를 묻는 것이 유익하다.

`Order` 클래스로 돌아가, 이번에는 고객 정체성 속성 `custId`를 보자. **고객 ID는 바뀔 필요가 없다.** 한 고객의 도서 장바구니가 왜 갑자기 다른 고객에게 넘어가야 하는가? 말이 되지 않고, 그 가능성을 열어 두는 것은 보안 문제로 이어질 수 있다.

주문이 결제되었지만 아직 배송되지 않았다고 하자. **공격자가 그 시점에 주문에 결부된 고객 ID를 바꿀 수 있다면, 그는 사실상 주문을 납치한 것이다.** 그 가능성을 열어 둘 이유가 없다.

이 문제를 설계로 피하는 효과적인 방법이 **엔티티를 부분적으로 불변으로 만드는 것**이다. 그렇게 하려면 고객 ID를 한 번 설정하고 그 뒤로는 바꿀 수 없게 하면 된다.

```java
class Order {
    private final CustomerID custId;         // Order 객체가 생성된 뒤에는
                                             // 이 필드가 바뀔 수 없음을 강제한다
    Order(CustomerID custId) {
        Validate.notNull(custId);
        this.custId = custId;
    }                                        // 컴파일러가 final 필드를 생성자가
                                             // 설정하도록 강제한다
    public CustomerID getCustId() {
        return custId;                       // 게터가 항상 같은 고객 ID를
    }                                        // 반환함을 보장한다
}

class SomeOtherPartOfFlow {
    void processPayment(Order order) {
        registerDebt(order.getCustId(), order.value());
        ...
    }
}
```

*리스팅 44-23. 불변 고객 정체성을 가진 `Order` 클래스 (SBD 리스팅 7.2 기준)*

`custId` 속성이 `private final`로 설정되었다. **이것은 `custId`가 생성자에서 설정되어야 하고 그 뒤로는 바뀔 수 없음을 강제한다.** `getCustId` 메서드는 호출될 때마다 같은 참조 — 같은 `CustomerID` 객체에 대한 참조 — 를 반환한다. 여기서 `CustomerID`는 도메인 프리미티브이며 불변으로 설계되었다.

이 코드를 더 생각해 보면 한 가지가 분명해진다. **`getCustId` 메서드는 흥미로운 것을 아무것도 캡슐화하지 않으며, 필드에 대한 직접 접근으로 대체할 수 있다.** 데이터 필드의 참조가 바뀔 수 없고, 그 참조가 가리키는 `CustomerID` 객체도 불변이어서 바뀔 수 없다. `processPayment`가 `order.custId` 필드에 직접 접근하더라도 그것으로 안전하지 않은 어떤 일도 할 수 없다.

```java
Order order = ...                       // 컴파일되지 않는다. custId는 final이다
order.custId = new CustomerID(...);
```

*리스팅 44-24. 컴파일 시점에 `Order`의 `custId` 속성 보호하기 (SBD 리스팅 7.3 기준)*

**이 코드의 흥미로운 특징은 `custId` 데이터 필드의 무결성을 보장하는 데 컴파일러의 도움을 얻었다는 것이다.** 그 속성을 바꾸려는 어떤 시도도 런타임에 이르지 못하고 컴파일 시점에 잡힌다.

44.9.2절에서 `public` 필드가 나쁘다고 했던 것과 이것이 모순되지 않는다는 점에 주목하라. 표 44-9의 네 번째 줄이 정확히 이 경우를 말한다. **"바뀔 수 없는 `final` 속성에만 `public` 필드"** 다. 핵심은 접근 제어자가 아니라 **변경 가능성**이다.

> **TIP** 바뀌어서는 안 되는 속성이 있다면, 무결성을 깨는 실수를 피하기 위해 엔티티를 부분적으로 불변으로 만든다.

이제 데이터 필드가 캡슐화(→ 44.9)로 보호되거나 부분 불변으로 만들어 보호될 수 있음을 보았다. **이제 엔티티의 더 까다로운 측면으로 넘어간다. 동작, 혹은 허용되는 동작이 엔티티가 어떤 상태에 있느냐에 따라 달라진다는 사실이다.**

### 44.10.3 엔티티 상태 객체

**엔티티를 다루기 어렵게 만드는 것 하나는 모든 동작이 모든 상태에서 허용되지는 않는다는 점이다.**

소프트웨어로 옮기면, 설계는 이런 엔티티 상태 규칙이 지켜지도록 보장해야 한다. 그렇게 하지 못하면 보안 문제로 이어질 수 있다 — 예컨대 **결제 없이 상품을 내주는 서점**이 그것이다. 그리고 이것은 드문 문제가 아니다. **엔티티 상태 관리가 없거나, 불완전하거나, 깨진 것은 규모 있는 코드베이스 거의 모두에서 자주 마주치는 문제다.**

이 보안 문제의 원인은 **상태 규칙이 아예 설계되지 않았거나, 암묵적이고 모호하다는 것**이다. 흔히 의식적인 설계 노력이 없었음이 명백하다. 오히려 규칙이 코드베이스에서 점진적으로 나타났고, 십중팔구 사례별로 하나씩 붙은 것이다.

> **WARNING** **"그냥 `if` 문 하나잖아요"** 같은 말을 듣는다면, 깨진 엔티티 상태를 향해 내리막을 굴러가는 위험한 비탈에 있다는 신호다. 스토리 기획이나 솔루션 설계 회의에서 이 말을 주의 깊게 들어라.

코드에서의 발현은 대개 두 변종 중 하나다. **서비스 메서드에 박힌 규칙, 또는 엔티티 메서드 안의 `if` 문.**

**첫 번째 변종부터 보자.** 온라인 서점에서 주문이 결제되었는지 확인한 뒤에 배송하는 것이 중요하다. 그 로직이 `Order` 클래스 바깥의 서비스 메서드 `processOrderShipment`에서 지켜진다면 이런 모습이다.

```java
class Order {
    final public CustomerID custId;
    Order(CustomerID custId) {
        Validate.notNull(custId);
        this.custId = custId;
    }
    ...
}

class SomeOtherPartOfFlow {
    void processOrderShipment(Order order) {
                                             // 배송이 배송 흐름 안의
                                             // if 문으로 보호된다
        if (order.getPaid()) {

            warehouse.prepareShipment(order.custId, order.getOrderItems());
        } else {
        ...
        }
        ...                                  // 여기에 어떤 종류의 오류 경보가
    }                                        // 있어야 한다
}
```

*리스팅 44-25. 서비스 메서드가 지키는 업무 규칙 (SBD 리스팅 7.6 기준)*

**결제되지 않은 상품이 배송되는 것을 막는 작은 `if` 문 하나가 `processOrderShipment` 안에 있고, 그 작은 `if` 문은 다른 클래스에 있다.** 시간이 지나며 코드가 계속 추가되는 동안 그런 검사가 누락되거나 점진적으로 침식되는 것을 상상하기는 쉽다. **주문이 배송되기 전에 결제되었는지 확인하는 것을 빠뜨리면, 고객이 상품 값을 지불하지 않는 구멍이 생긴다.** 그 구멍이 알려지면 결제되지 않은 상품이 창고에서 쏟아져 나가며 큰돈을 잃기 시작할 수 있다. **누락된 엔티티 상태 처리는 분명히 보안 문제다.**

이 코드를 다시 보면 이상한 점을 알게 된다. **"결제되지 않은 주문은 배송하지 않는다"는 것은 일반 규칙이다.** 그런데 코드베이스에서는 그것이 배송 처리 시나리오에만 특정하게 적용되는 규칙으로 나타난다. 이것은 **주문이 언제 배송될 수 있는가에 대한 규칙**으로 더 잘 어울린다. 그렇다면 그것은 `Order`의 배송 메서드 안에 있는 편이 낫다.

**현실의 코드베이스에서, 엔티티가 그저 구조체(private 데이터 필드와 세터·게터를 가진 클래스)인 경우를 자주 본다.** 그러면 엔티티가 어떻게 동작할 수 있는지에 대한 규칙을 서비스 메서드들이 지켜야 한다. 실용적으로는 시스템이 작을 때는 이것이 가능할 수 있다. **그러나 코드가 시간에 따라 진화하면 규칙 준수가 일관성을 잃는다.** 시스템의 어떤 부분은 어떤 규칙을 지키고 다른 부분은 지키지 않는다. 또한 어떤 규칙이 적용되는지 전체 그림을 얻기 어렵다. 그러려면 그 엔티티가 쓰이는 모든 코드를 파헤쳐 보호하는 `if` 문을 찾아야 한다. **요컨대 엔티티에 어떤 규칙이 적용되는지를 감사할 실용적인 방법이 없다.**

**감사하기 어려운 것과 밀접하게 연관된 것이 테스트하기 어렵다는 것이다.** "결제되지 않은 주문은 배송되지 않는다"를 확인하는 단위 테스트를 쓰고 싶다고 하자. 그러려면 `processOrderShipment` 메서드 안의 조건문을 테스트해야 하고, 그것은 그 메서드가 가질 수 있는 모든 의존성 — 데이터베이스 연결, 창고 시스템 — 을 모킹해야 한다는 뜻이다. 테스트 데이터도 만들어야 한다. 그리고 그 메서드가 부적절한 배송 시도를 보고하는 올바른 일을 하는지 확인해야 하므로, 로깅 프레임워크를 모킹하고 로그를 훑어야 한다. **그리고 코드베이스 어딘가에 `processExpressShipment` 메서드가 또 있다면, 거기서도 같은 일을 해야 한다.** 이것은 "결제되지 않은 주문은 배송되지 않는다"는 규칙을 테스트하는 쉬운 방법이 아니다.

**조금 나은 버전은 엔티티 메서드가 상태 규칙을 지키는 것이다.** 그러나 이 접근조차 익스플로잇 가능한 불일치로 이어질 수 있다.

이 접근은 확실히 올바른 방향으로 가는 한 걸음이다. 업무 규칙이 적어도 엔티티 클래스 안에 있다. 배송이 일반 배송과 특급 배송 양쪽에서 시작될 수 있다면, 적어도 같은 코드가 검사를 수행하므로 보안 결함으로 이어질 수 있는 불일치의 위험이 줄어든다.

**불행히도 상태 처리는 여전히 암묵적이거나, 적어도 뒤엉켜 있다.** 이런 `if` 문이 엔티티 메서드 깊숙한 곳에 흩뿌려진 것을 자주 본다. 코드의 이력을 파헤쳐 보면, 그것들이 어떤 특수 사례를 처리하기 위해 하나씩 추가되었다는 것이 대개 분명해진다. **때로는 모든 규칙의 큰 그림이 논리적으로 일관된 모델조차 아니다.**

> **TIP** 안에 `if` 가드가 잔뜩 있는 엔티티를 만나면, **상태 그래프를 그려 보고 각 상태에 이름을 붙여 보라.**

명백히 상태가 서비스 메서드나 엔티티 메서드의 `if` 문으로 구현되는 것은 좋은 설계가 아니다. 그런데 그것이 보안 문제인가. **그렇다.** 엔티티가 그 상태에서 열려 있어서는 안 되는 메서드를 쓸 수 있는 여지를 남기면, 그 여지는 실수를 익스플로잇하는 공격의 출발점으로 쓰일 수 있다. **예컨대 주문이 결제된 뒤에 항목을 추가할 수 있게 만드는 실수는, 공격자가 값을 치르지 않고 상품을 얻는 데 익스플로잇될 수 있다.**

> **온라인 도박 사이트와 공짜 돈**
>
> 온라인 도박 사이트는 흔히 무료 크레딧이나 무료 스핀을 주는 캠페인을 한다. 많은 사람들이 그것을 인출 가능한 실제 돈으로 바꾸려 애쓴다. 그 과정에서 크레딧을 조금 넣고, 조금 걸고, 조금 잃고, 조금 따고, 크레딧을 더 넣으며 **무엇이 진짜 돈이고 무엇이 아닌지에 대해 시스템을 혼란시키기를** 기대한다. 많은 도박 사이트가 그런 공격으로 실제 돈을 잃었다.
>
> 이 공격을 가장 잘 막아낸 사이트들은 **이 시나리오를 흥미로운 엔티티 집합으로 모델링하는 데 노력을 들인** 곳들이다. 의도된 규칙을 논리적으로 일관된 방식으로 포착한 것이다. 계정의 크레딧은 플레이 가능한가? 인출 가능한가, 가능하다면 얼마나? **크레딧은 그저 금액이 아니라 여러 상태를 가진 복잡한 엔티티다.**

**제안은 엔티티 상태를 명시적으로 설계하고 그 자체의 클래스로 구현하는 것이다.** 이 접근에서 상태 객체는 엔티티를 위한 위임된 헬퍼 객체로 쓰인다. **엔티티에 대한 모든 호출이 먼저 상태 객체와 함께 검사된다.**

온라인 서점의 주문 상태로 돌아가자. `OrderStatus` 헬퍼 객체는 다음과 같다.

```java
import static org.apache.commons.lang3.Validate.validState;

public class OrderStatus {

    private boolean paid = false;          // 주문은 미결제 상태로 시작한다
    private boolean shipped = false;

    public void addItem() {                // 항목 추가는 아직 결제되지 않았을 때만
        validState(!paid,                  // 허용된다
            "결제된 주문에는 항목을 추가할 수 없다");
    }

    public void pay() {                    // 결제는 미결제 상태에서만
        validState(!paid, "이미 결제된 주문이다");
        paid = true;
    }

    public void ship() {                   // 배송은 결제되었고 아직 배송되지
        validState(paid, "결제되지 않은 주문은 배송할 수 없다");
        validState(!shipped, "이미 배송된 주문이다");
        shipped = true;
    }
}
```

*리스팅 44-26. 주문 상태의 규칙을 캡슐화한 `OrderStatus` 헬퍼 객체 (SBD 리스팅 7.7의 구조를 서점 도메인에 적용)*

**헬퍼 객체의 코드는 간결하다.** 그리고 간결함의 직접적인 효과는 **테스트 가능하다는 것**이다.

```java
public class OrderStatusTest {

    @Test
    public void should_allow_adding_items_when_unpaid() {
        OrderStatus status = new OrderStatus();
        status.addItem();
    }

    @Test(expected = IllegalStateException.class)
    public void should_not_allow_adding_items_when_paid() {
        OrderStatus status = new OrderStatus();
        status.pay();
        status.addItem();
    }

    @Test(expected = IllegalStateException.class)
    public void should_not_allow_shipping_when_unpaid() {
        OrderStatus status = new OrderStatus();
        status.ship();
    }

    @Test
    public void should_allow_shipping_after_payment() {
        OrderStatus status = new OrderStatus();
        status.pay();
        status.ship();
    }
}
```

*리스팅 44-27. `OrderStatus`의 테스트 사례들 (SBD 리스팅 7.8의 구조를 서점 도메인에 적용)*

**코드가 얼마나 잘 읽히는지에 주목하라.** `should_not_allow_shipping_when_unpaid` 테스트는 결제되지 않은 주문을 배송할 수 없다고 명확히 말한다. 앞에서 이 규칙을 테스트하려면 창고 시스템과 데이터베이스와 로깅 프레임워크를 모킹해야 했다. 이제 세 줄이다. **도메인에 존재하는 개념으로 클래스 이름을 짓는 것 — 주문 상태 같은 — 이 도움이 된다.**

> **TIP** 상태 헬퍼 클래스에 좋은 이름을 찾아라. `OrderStatus`가 `OrderStateHelper`보다 훨씬 나은 이름이다. **좋은 이름이 좋은 사고를 돕는다.**

이제 이 상태 표현을 엔티티에 엮을 차례다. 엔티티 `Order`가 모든 `public` 메서드의 처음에 헬퍼 객체 `OrderStatus`를 참조해 그 호출이 적법한지 판단하게 한다.

```java
public class Order {

    private final CustomerID custId;
    private OrderStatus status = new OrderStatus();
    private List<OrderLine> orderItems = new ArrayList<>();

    public void addItem(ISBN isbn, Quantity qty) {
        status.addItem();               // 항목을 추가해도 되는지 확인하고,
                                        // 아니면 예외를 던진다
        ...
    }

    public void markPaid(PaymentReference ref) {
        status.pay();                   // 미결제 상태인지 확인하고 결제됨으로 바꾼다
        ...
    }

    public void ship(ShipmentId shipmentId) {
        status.ship();                  // 결제되었는지, 아직 배송되지 않았는지 확인한다
        ...
    }
}
```

*리스팅 44-28. `OrderStatus`의 도움을 받는 `Order` 클래스 (SBD 리스팅 7.9의 구조를 서점 도메인에 적용)*

44.6.4절에서 `addItem`의 `if (this.paid == false)`가 "여전히 어색하다"고 표시해 두었던 것을 기억할 것이다. 그것이 여기서 해결된다. **어색했던 이유는 그 `if` 문이 두 가지 다른 것을 섞고 있었기 때문이다.** 주문에 항목을 추가하는 방법(엔티티의 관심사)과, 지금 항목을 추가해도 되는지(상태의 관심사)를 하나의 메서드가 함께 다뤘다. 상태 객체가 그 둘을 분리한다.

**상태 관리를 별도 객체로 추출하면 엔티티 코드가 훨씬 견고해지고, 고객이 배송 전에 결제하지 않는 것 같은 미묘한 업무 무결성 문제에 훨씬 덜 취약해진다.**

**적어도 서로 다른 규칙을 가진 두 개의 상태가 있고, 그 사이의 전이가 완전히 사소하지 않을 때** 별도 상태 객체를 쓰기를 권한다. 전구의 상태(켜짐/꺼짐, 스위치는 항상 허용되고 항상 반대로 전환됨)를 표현하는 데 별도 상태 객체를 쓰지는 않을 것이다. **그러나 그보다 조금이라도 복잡한 것이라면 별도 상태 객체를 고려하기를 권한다.**

가변 객체로서의 이런 엔티티 표현은 앞서 말했듯 **단일 스레드 환경에서 잘 동작한다.** 그러나 다중 스레드 환경에서는 스레드들이 상태를 난도질하지 못하게 하려고 코드에 `synchronized` 키워드를 잔뜩 넣어야 한다. **불행히도 그것은 제한된 처리량과 잠재적 교착 상태 같은 다른 문제로 이어진다.** 다음은 다중 스레드 환경에서 잘 동작하는 다른 설계다.

### 44.10.4 엔티티 스냅샷

이제 **같은 엔티티 인스턴스가 여러 스레드에서 접근될 수 있는 다중 스레드 환경**으로 넘어간다.

응답 시간이 중요한 고성능 솔루션에서는 데이터베이스를 건드리는 것을 피하고 싶어진다. 금융 거래, 스트리밍, 다중 사용자 게임 애플리케이션, 그리고 반응성이 높은 웹사이트에서 흔한 일이다. **데이터베이스에서 데이터를 가져오는 왕복 시간이 이런 상황에서 원하는 빠른 응답을 죽여 버린다.** 대신 가능한 한 엔티티를 메모리에 — 예컨대 공유 캐시에 — 유지한다. 엔티티와 작업해야 하는 모든 스레드가 캐시에서 데이터를 가져오고, 엔티티 표현이 스레드 사이에 공유된다. 그 결과가 빠른 응답 시간과 높은 처리량이지만, **엔티티 설계에 추가 부담을 지운다. 여러 스레드가 있는 환경에서 잘 살아야 하는 것이다.**

이 상황을 다루는 한 가지 방법은 코드에 `synchronized` 키워드를 잔뜩 추가하는 것이다. 그러나 그러면 많은 스레드가 서로를 기다리게 되어 처리량이 급격히 줄어든다. 더 나쁘게는 **두 스레드가 서로를 무한정 기다리는 교착 상태(deadlock)** 를 일으킬 수도 있다.

대신 다른 설계 패턴을 보자. **엔티티를 엔티티 스냅샷(entity snapshot)으로 표현하는 것이다.**

엔티티 스냅샷으로 설계할 때, 엔티티는 있지만 **그 엔티티가 가변 엔티티 클래스로 코드에 표현되지 않는다.** 대신 그 엔티티를 들여다보고 행동을 취하는 데 쓰이는 **스냅샷들**이 있다. 은유로 설명하는 것이 가장 쉽다.

한동안 보지 못한 오랜 친구를 상상해 보라. 서로 다른 도시에 살지만 사진 공유 사이트에서 서로를 팔로우하며 연락을 유지한다. 정기적으로 친구의 사진을 보고, 그들이 시간에 따라 어떻게 변하는지 따라갈 수 있다. 새로운 머리 모양을 시도하거나 새집으로 이사할 수도 있고, 우리 모두처럼 천천히 나이를 먹는 것도 분명하다. **의심의 여지 없이 친구는 이 모든 속성 변화를 초월하는 정체성을 가진 사람이다.** 변화를 보고 연락을 유지하지만, 직접 만나지는 않는다.

```
    엔티티                   사진 공유 계정              한 번도 실제로
    스냅샷의                   (값 객체들)                 보지 못한 사람
    추론
                         ┌───┐ ┌───┐ ┌───┐
     ┌──┐                │   │ │   │ │   │                    ┌──┐
     │  │  ─── 사진만 ──▶ └───┘ └───┘ └───┘  ◀── 사진을 올림 ── │  │
     └──┘      본다                                            └──┘
     당신                                                      친구

           그럼에도 당신은 그를 한 사람(엔티티)으로 생각한다
```

*그림 44-11. 일련의 사진이 실제 사람에 대한 인상을 준다 (SBD 그림 7.2 기준)*

**사진들은 무엇인가? 그것이 친구인가? 물론 아니다. 그것은 친구의 스냅샷이다.** 각 사진은 특정 시점의 친구에 대한 표현이다. 사진은 복사되고 폐기될 수 있고, 복사본이 원본을 대체해도 신경 쓰지 않는다. 친구는 여전히 거기, 먼 도시에서 자기 삶을 살고 있다.

**엔티티 스냅샷 패턴이 같은 발상을 따른다.** 온라인 서점에서 고객이 상품을 구매하면 주문이 생성된다. 각 주문은 상당한 수명을 갖고, 고객이 항목을 추가하고 결제 수단을 선택하는 등의 과정에서 진화한다. 기술적으로 상태는 데이터베이스에 보관될 수 있다. **그러나 코드가 그 상태를 들여다볼 때가 되면, 그것의 스냅샷을 찍어 `OrderSnapshot` 클래스로 표현한다.** 이는 기저 엔티티의 불변 표현이다. 요청한 순간 주문이 어떻게 생겼는지에 대한 스냅샷을 제공한다.

```java
import static org.apache.commons.lang3.Validate.*;

public class OrderSnapshot {
    public final OrderID orderId;                    // 주문 엔티티 자체가 아니라
    public final CustomerID custId;                  // 그것의 스냅샷이다
    private final List<OrderItem> orderItemList;

    public OrderSnapshot(OrderID orderId,
                         CustomerID custId,
                         List<OrderItem> orderItemList) {
        this.orderId = notNull(orderId);
        this.custId = notNull(custId);
        this.orderItemList =
            Collections
                .unmodifiableList(                   // 항목 리스트가 곧바로
                    notNull(orderItemList));         // 불변으로 저장된다
        checkBusinessRuleInvariants();
    }

    public List<OrderItem> orderItems() {
        return orderItemList;
    }
                                                     // 엔티티 스냅샷은 상태를 관찰하는
                                                     // 지능적인 업무 로직을 담는다
    public int nrItems() {
        ...
    }

    private void checkBusinessRuleInvariants() {
        validState(nrItems() <= 38, "일반 배송으로는 너무 큰 주문이다");
    }
                                                     // 변경 메서드가 전혀 없다
}

public class OrderService {
    public OrderSnapshot findOrder(OrderID orderId) ...
    public List<OrderSnapshot> findOrdersByCustomer(CustomerID custId) ...
}
```

*리스팅 44-29. `OrderSnapshot` 클래스 (SBD 리스팅 7.10 기준)*

**주문 엔티티가 개념적으로는 여전히 존재하지만, 코드에서 가변 엔티티 클래스로 자신을 드러내지 않는다.** 대신 `OrderSnapshot` 클래스가 엔티티에 대해 필요한 정보를 가져다주는 일을 한다 — 아마 서점의 GUI에서 시각화하기 위해서일 것이다. 스냅샷 은유의 발상은 **도메인 서비스가 카메라를 들고 데이터베이스로 내려가, 주문이 어떻게 생겼는지 찍은 사진을 들고 돌아온다**는 것이다.

**`OrderSnapshot`은 멍청한 보고용 객체가 아니다. 고전적인 엔티티처럼 흥미로운 도메인 로직을 담는다.** 예컨대 주문의 총 항목 수를 계산하고, 그 수가 배송에 규정된 범위 안에 있는지 보장할 수 있다.

그러면 기저 엔티티는 어떻게 되는가. 가변 엔티티 클래스가 없는데도 존재하는가. **주문 엔티티는 개념적으로 여전히 존재한다.** 먼 도시의 친구와 같은 방식으로다. 친구처럼 주문 엔티티를 직접 보지 못하고 그 상태의 스냅샷만 본다. **주문이 가변 상태로 표현되는 유일한 장소는 데이터베이스다.** `Orders` 테이블의 행과 `OrderLines` 테이블의 대응 행들이 그것이다.

**그러나 이것이 진짜 엔티티라면 상태를 바꿀 수 있어야 한다.** 표현이 불변인데 어떻게 그것을 이루는가.

기저 엔티티(정확히는 기저 엔티티 데이터)를 변경할 메커니즘이 필요하다. 이를 위해 **갱신을 보내는 도메인 서비스를 제공**할 수 있다.

```java
class OrderService {

    public void addOrderItem(OrderID orderId,
                        ISBN isbn, Quantity qty) {
                                                  // 지정된 수량을 추가할 수 있는지
                                                  // 검증한다
        //...
        //...
    }                                             // 새 정보로 기저 데이터베이스를
}                                                 // 갱신한다
```

*리스팅 44-30. 데이터베이스의 주문을 갱신하는 메서드를 가진 `OrderService` (SBD 리스팅 7.11 기준)*

`addOrderItem` 메서드는 변경이 허용되는지 조건을 검증한 뒤 기저 데이터의 갱신을 수행한다 — 데이터베이스로 직접 보내는 SQL 명령을 통하거나, 쓰고 있는 영속성 프레임워크를 통해서다.

**이 접근으로 높은 가용성을 얻는다. 읽을 때 잠금을 피하기 때문이다.** 읽기는 (데이터를 바꾸는 형태의) 쓰기보다 훨씬 흔하다고 가정된다. **잠금이 필요할 수 있는 쓰기가 읽기와 분리되고, 데이터를 이용할 수 없게 되는 보안 문제를 피한다.**

**이 접근의 단점은 객체지향의 몇몇 발상 — 특히 데이터와 그에 수반하는 동작을 가까이, 되도록 같은 클래스에 두라는 지침 — 을 위반한다는 것이다.** 여기서는 엔티티를 찢어, 읽기 쪽은 한 클래스의 값 객체에, 쓰기 쪽은 다른 클래스의 도메인 서비스에 두었다. **아키텍처는 흔히 절충을 수반한다.** 이런 경우 가용성을 매우 높게 평가한 나머지 객체지향 코드의 어떤 원칙 같은 다른 것을 희생할 의사가 있을 수 있다.

이 발상이 들리는 것만큼 이상하지는 않다. 비슷한 접근이 다른 곳에서도, 때로는 약간 다른 배경에서 제안되었다. **그레그 영이 제안한 명령-질의 책임 분리(CQRS, Command Query Responsibility Segregation) 패턴과 마틴 톰프슨이 제안한 단일 작성자 원칙(Single Writer Principle)** 이 모두 비슷한 징표를 지닌다.

**가용성 외에 엔티티 스냅샷 패턴은 무결성도 뒷받침한다.** 스냅샷이 불변이므로 표현이 잘못된 상태로 변할 위험이 전혀 없다. 상태를 바꾸는 메서드를 가진 통상적인 엔티티는 그런 종류의 버그에 취약하지만 스냅샷은 아니다. 기저 데이터의 상태를 바꾸는 코드가 있고 그 코드는 버그를 담을 수 있지만, **적어도 엔티티의 상태를 보여 주는 데 쓰이는 스냅샷은 바뀔 수 없다.**

> **데이터베이스가 엔티티를 잠그게 만드는 방식**
>
> 어떤 상황에서는 (응답 시간과 처리량 양쪽에서) 읽기 성능이 중요하다. 온라인 서점에서는 예컨대 크리스마스 직전처럼 수많은 클라이언트가 살 책을 찾아보는 성수기가 있을 수 있다. 각 클라이언트는 책의 설명, 가격, 재고 수량을 빠른 응답으로 받고 싶어 한다. **각 조회가 그 책의 데이터베이스 행에 읽기/쓰기 잠금을 건다면, 상품 목록은 곧 완전히 멈춰 설 것이다.** "죄송하지만 지금 다른 분이 보고 계셔서 『햄릿』의 설명을 드릴 수 없습니다. 그분이 끝날 때까지 기다려 주시면 다시 안내하겠습니다"라고 고객에게 말하는 것은 실현 가능하지 않다.
>
> 데이터베이스에 저장된 엔티티와 작업할 때 데이터베이스 행에 어떤 종류의 잠금을 거는 것은 꽤 정상적이다. 정확히 어떤 유형의 잠금이고 어떻게 관리되는지는 영속성 프레임워크와 데이터베이스 관리 제품과 테이블 설정에 달렸지만, **가변 엔티티를 가져오는 것이 그 엔티티 행에 읽기/쓰기 잠금을 거는 일은 드물지 않다.** 이런 방식으로 데이터베이스는 다른 클라이언트가 같은 엔티티를 동시에 수정하지 않음을 보장한다.
>
> 엔티티가 이런 종류의 제약으로 이어진다면, 많은 클라이언트가 동시에 하나의 엔티티를 보고 싶어 하는 경우에 그것은 분명히 좋은 모델링 선택이 아니다.
>
> 서점으로 돌아가면, 주문을 엔티티로 모델링하는 것은 좋은 생각으로 보인다. 주문의 요점 자체가 책이 주문에 추가되고 주문이 결제되고 포장되고 배송될 때의 상태 변화를 포착하는 것이다. 각 주문은 몇 개의 테이블 — `Orders` 테이블, `OrderLines` 테이블, 그리고 아마 몇 개 더 — 에 저장된다. **높은 부하에서도 괜찮아야 하지 않은가?** 주문이 속한 고객 외에는 아무도 그 행들을 보지 않을 테니 두 클라이언트가 서로를 잠글 일이 없다.
>
> 원리적으로는 괜찮아 보이지만 실무에서는 조금 더 복잡하다. **문제는 많은 데이터베이스 관리 시스템이 개별 행을 따로 잠그지 않는다는 것이다.** 대신 효율을 위해 행의 블록에 잠금을 건다.
>
> ```
>      앨리스                                              밥
>
>   내 레코드만        ┌─────────────────────────┐     기다리는
>   원할 뿐인데       │  메모리 페이지 잠금이      │      수밖에
>                     │  같은 페이지의 모두를 막는다│      없겠군...
>                     └─────────────────────────┘
>
>              ┌──────────────────────────┐
>              │  앨리스 레코드            │
>              │  밥 레코드                │
>              └──────────────────────────┘
>              앨리스를 위해 로드되는 동안 잠김
>              (두 레코드를 함께 담은 메모리 페이지)
> ```
>
> 페이지 수준 잠금의 이유는 읽기/쓰기 효율이고, 그것은 데이터베이스 관리 시스템에 결정적이다. 트랜잭션 동안 시스템은 디스크에서 페이지 전체를 읽어 메모리로 로드한다. 트랜잭션이 그 페이지에 담긴 데이터를 일부 변경한다. 커밋 시 페이지 전체가 디스크에 다시 쓰인다. **입출력을 다루는 효율적인 방법이다.** 그러나 다른 클라이언트가 같은 페이지에 있는 데이터로 작업하고 싶다면 어떻게 되는가?
>
> 가장 단순하고 순진한 방법은 누군가 작업하는 동안 페이지 전체를 잠그는 것이다. 다른 클라이언트가 잠긴 페이지의 데이터에 접근하고 싶으면, 첫 클라이언트가 커밋할 때까지 대기 상태에 놓인다. **불행한 효과는 한 고객이 자기 주문에 접근하는 것이 자기 행뿐 아니라 이웃한 행들까지 잠근다는 것이다.** 다른 고객들이 같은 시각에 도착하면 잠금이 풀릴 때까지 기다려야 한다. 이는 클라이언트들이 서로를 기다리는 상황을 만들고, 응답 시간이 나빠지고 처리량이 낮아진다 — 좋지 않다. **시스템의 가용성이 위험에 처하고, 그것은 보안 관심사다.**

엔티티 스냅샷 패턴으로 엔티티를 구현하면, 코드에 `synchronized`를 흩뿌릴 때 얻는 단점 없이 다중 스레드 환경에서 잘 살 수 있다. **또한 데이터베이스가 트랜잭션 동기화를 처리하게 함으로써 경합을 피한다.**

**엔티티 클래스 없는 엔티티라는 발상이 통상적인 객체지향 교과서의 패턴을 따르지 않는다는 것은 의심의 여지가 없고, 반직관적으로 보일 수 있다.** 객체지향적 사고에는 엔티티의 데이터 정의가 한 곳에 있고 같은 데이터를 갱신하는 기계 장치가 다른 곳에 있는 것이 거슬릴 수 있다. 그럼에도 **까다로운 처리량과 가용성 요구가 있는 상황** — 트래픽이 많은 웹사이트이든, 의료진이 환자 기록에 즉시 접근해야 하는 병원이든 — 에서는 엔티티 스냅샷 패턴을 고려할 값이 충분하다.

**엔티티 스냅샷 설계의 또 하나의 흥미로운 보안 이점은, 데이터를 읽는 것과 바꾸고 쓰는 것에 다른 권한이 필요한 상황에 있다.** 데이터의 상태를 표시하기만 하려는 사용자 시나리오(장바구니 보기)에는 그 데이터를 가져오는 메서드가 필요하다. 데이터를 바꾸는 사용자 시나리오(장바구니에 항목 추가)에는 그 데이터를 바꾸는 메서드가 필요하다. **고전적인 객체지향에서는 엔티티가 읽기와 쓰기를 모두 지원하는 메서드를 갖는다. 데이터를 표시하는 사용자 시나리오 동안, 클라이언트 코드는 쓰기용 메서드에도 접근할 수 있다.** 읽기 시나리오 동안 엔티티 객체에 대한 변경이 없음을 보장하는 다른 종류의 보안 메커니즘이 필요해진다.

**엔티티 스냅샷 설계에서는 읽기 시나리오가 불변 스냅샷에만 접근하므로 변경 메서드를 호출하는 것이 불가능하다.** 변경이 허용된 클라이언트만이 기저 엔티티를 갱신하는 데 쓰이는 도메인 서비스에 접근한다. 이런 방식으로 엔티티 스냅샷 패턴은 흔한 시나리오들에 대해 무결성도 뒷받침한다.

24장이 접근 통제를 다루며 "수직적·수평적 권한 분리"를 이야기했을 때, 그것은 애플리케이션 계층의 통제였다. **엔티티 스냅샷은 같은 분리를 타입 시스템으로 옮긴다.** 읽기 경로에는 쓰기 메서드가 아예 존재하지 않으므로, 접근 통제 검사를 빠뜨려서 생기는 결함의 부류가 그 경로에서는 성립할 수 없다.

### 44.10.5 엔티티 릴레이

이제 두 가지 설계를 보았다. 하나는 단일 스레드 환경에서 잘 동작하고 하나는 다중 스레드 환경에서 잘 동작한다. **그러나 복잡도가 생겨나는 또 다른 길이 있다. 엔티티가 아주 많은 서로 다른 상태를 가질 때다.** 엔티티에서 10개가 넘는 상태를 다루는 것은 어색해질 수 있지만, 흔히 대안적인 설계를 적용할 수 있다 — **복잡한 상태를 엔티티 체인으로 쪼개는 것이다.**

많은 엔티티는 분리된 상태의 수가 합리적으로 적고 파악하기 꽤 쉽다. 그런 크기의 상태 그래프는 이해하기 쉽다. 44.10.3절의 상태 객체 패턴으로 구현하기도 쉬울 것이다.

**때때로 엔티티 상태 그래프가 자라나 꽤 커지고 파악하기 어려워진다.** 처음부터 그렇게 설계되었을 수도 있지만, 더 흔하게는 **오랜 세월에 걸친 많은 변경의 결과**다. 대부분의 변경은 그것이 이루어진 시점에는 작은 수정으로 인식되었을 것이다. 그러나 시간이 지나며 누적된 결과가 많은 상태다.

온라인 서점이 주문에 대해 **접수됨(received)** 과 **배송됨(shipped)** 두 상태로 시작했다고 상상할 수 있다. 얼마 후 상태 그래프는 이렇게 된다.

```
                                                      분실됨
                                                       ▲
                                                       │
                                            오배치됨 ──┘
                                              ▲
                                              │
                                           배송됨
                                              ▲
                                              │
                                              ├────────▶ 배달됨
                          결제됨 ─────────────┘             │
                            ▲                               ▼
                            │                            수취 거절
                            │                               │
       구성 완료,           │                               ▼
       미결제 ──────────────┘                            반품 중
          ▲                                                 │
          │        구성 완료,                                ▼
          │        결제 거절                                반품됨
          │                                                  │
       구성 중                                                ▼
          ▲                                                환불됨
          │
        시작
```

*그림 44-12. 도서 주문이 가질 수 있는 많은 상태, 각각 고유한 규칙과 제약을 갖는다 (SBD 그림 7.4 기준)*

**그래프를 들여다보고 있어도 그런 엔티티의 가능한 모든 상태와 전이를 이해하기는 어렵다.** 이 상태들을 코드로 구현하고 모든 다른 상태에서 모든 다른 규칙이 강제되도록 보장하는 것은 악몽일 것이다. 이 엔티티가 하나의 클래스로 구현되면, 그 클래스는 **찾기 어려운 불일치를 담을 위험이 있을 만큼 복잡해진다.**

**상태 다섯 개는 관리 가능하다. 열 개는 견딜 만하다. 열다섯 개를 저글링하는 것은 그저 너무 위험하다.** 여기가 엔티티 체이닝을 제안하는 지점이다.

**엔티티 릴레이의 기본 발상은 엔티티의 수명을 국면(phase)으로 쪼개고, 각 엔티티가 자기 국면을 대표하게 하는 것이다.** 한 국면이 끝나면 그 엔티티는 사라지고 다른 종류의 엔티티가 넘겨받는다 — 릴레이 경주처럼.

한 사람의 삶을 두 가지로 보자. 하나는 여러 삶의 상태를 거치는 하나의 엔티티로, 다른 하나는 엔티티의 연쇄로.

```
     하나의 엔티티가                      여러 엔티티의 연쇄.
     많은 국면·상태를                    한 국면이 끝나면 다음 국면의
     거쳐 간다                           새 엔티티가 불사조처럼 일어난다

       탄생                                       탄생
         │                                          │
      유년기                                        ▼
         │                                     ┌────────┐  더 이상 아이가
      청소년기                                 │  아이   │  아님 → 낳는다
         │                                     └────┬───┘
       성인기                                       ▼
         │                                     ┌────────┐  더 이상 젊은이가
       노년기                                  │ 젊은이  │  아님 → 낳는다
         │                                     └────┬───┘
       죽음                                         ▼
                                               ┌────────┐  더 이상 성인이
                                               │  성인   │  아님 → 낳는다
                                               └────┬───┘
                                                    ▼
                                               ┌────────┐      ┌──────┐
                                               │  노인   │ ───▶ │ 사망 │
                                               └────────┘      └──────┘
```

*그림 44-13. 한 사람의 삶을 두 가지로 보기 — 하나의 엔티티, 그리고 엔티티의 연쇄 (SBD 그림 7.5 기준)*

왼쪽에서는 사람의 삶이 하나의 엔티티로 보인다. 사람이 태어나 유년기를 보내고, 청소년기를 거쳐 성인의 책임을 짊어지고, 나이 들어 죽는다. 사람을 탄생·유년기·청소년기·성인기·노화·죽음의 상태를 통과하는 같은 엔티티로 볼 수 있다.

**오른쪽에서는 같은 삶이 엔티티의 연쇄로 보인다.** 아이가 태어나 자란다. 어느 날 아이는 사라지고, 그 자리에 젊은이가 서서 릴레이 바통을 넘겨받는다. 몇 년 뒤 젊은이는 사라지고 성인으로 대체된다. 성인은 결국 노인에게 자리를 내주고, 노인이 마침내 죽는다. **이 경우 삶을 서로 다른 인물들의 계승으로 볼 수 있다.**

**같은 것을 보는 두 가지 방식을 제시한 것이다. 어느 표현도 다른 것보다 더 참이거나 더 낫지 않다.** 둘은 서로 다른 측면에 초점을 맞추고 서로 다른 것에 능하다. 초점을 하나에서 다른 하나로 옮기는 것이 때때로 도움이 되는데, **상태가 아주 많은 엔티티를 가진 경우가 그런 경우 중 하나다.** 이 설계 전환이 상태가 지나치게 많은 엔티티를 다루는 강력한 방법이 될 수 있다. **너무 큰 상태 그래프를 국면으로 나누고, 각 국면을 자기 엔티티로 모델링하고, 그 엔티티들이 릴레이 체인을 이루게 한다. 릴레이의 각 엔티티는 관리할 상태가 몇 개뿐이고, 위험한 복잡도를 극복한 것이다.**

**엔티티 릴레이의 힘은 엔티티의 전체 수명을 국면으로 쪼개고, 대신 그 국면들을 하나가 다음을 잇는 엔티티로 모델링하는 능력에서 나온다.** 이것이 잘 동작하려면 **이전 국면으로 되돌아가는 일이 없어야 한다.** 되돌아감이 있다면 같은 발상을 여전히 적용할 수 있지만, 릴레이 은유의 단순함이 사라지고 이득의 상당 부분도 사라진다.

그림 44-12의 상태 그래프를 다시 보고 릴레이 경주로 재모델링해 보자. **한 무리의 상태가 다른 무리의 상태로 이어지는 지점을 찾는다. 되도록 한 번 떠나면 첫 무리로 돌아갈 길이 없어야 한다.**

이 그래프에서 그런 지점이 보인다. **결제 전까지와 결제 이후다.** 첫 국면을 **예비 주문(preliminary order)**, 두 번째 국면을 **확정 주문(definitive order)** 이라 부르자. 이것이 별개의 엔티티로 재설계하고 싶은 국면이다. 릴레이 경주를 구성하는 주자는 경주를 시작하는 첫 엔티티(예비 주문)와, 첫 엔티티가 완주했을 때 넘겨받는 두 번째 엔티티(확정 주문)다. **예비 주문이 결제되면 그 결과로 확정 주문이 태어난다.**

> **TIP** 이 전략을 적용할 때, **돌아갈 수 없는 지점**을 찾아라. 그래야 체인의 앞선 엔티티가 다시 태어날 필요가 없다. 릴레이의 각 엔티티에 **새 엔티티를 낳는 종료 상태가 하나뿐인 것**이 바람직하다.

상태 그래프를 다시 보면 이 요구를 충족하는 지점이 하나 더 있다. **배달된 소포가 수취인에게 거절될 때다.** 여기서의 차이는 배달된 모든 주문이 거절 주문을 낳지는 않고 일부만 그렇다는 것이다. **그래도 상태 그래프를 쪼갤 좋은 지점이다.** 거절 주문의 탄생이 자동이 아니라 수취인이 배달을 받지 않는다는 조건에 걸려 있다는 것을 기억하면 된다.

이 변환 뒤에는 더 단순한 구성을 갖게 된다. **압도적인 양의 상태를 가진 하나의 엔티티 대신, 각각이 합리적으로 단순한 세 개의 엔티티를 갖는다.**

```
    예비 주문                 확정 주문                    거절 주문
  ┌──────────┐   결제되면   ┌──────────┐   배달 시 거절   ┌──────────┐
  │ 구성 중   │   낳는다     │ 결제됨    │   되면 낳는다    │ 수취 거절 │
  │ 구성 완료 │ ──────────▶ │ 배송됨    │ ──────────────▶ │ 반품 중   │
  │ 결제 거절 │             │ 오배치됨  │                 │ 반품됨    │
  │ 결제됨    │             │ 분실됨    │                 │ 환불됨    │
  └──────────┘             │ 배달됨    │                 └──────────┘
    4개 상태                └──────────┘                    4개 상태
                              5개 상태
```

*그림 44-14. 세 엔티티의 연쇄로 본 도서 주문 (SBD 그림 7.7 기준)*

세 엔티티(예비 주문, 확정 주문, 거절 주문)는 각각 네다섯 개의 가능한 상태를 가지므로, 각각을 따로 구현하는 것은 꽤 간단하다. **앞의 상태 객체 설계를 쓰면 세 엔티티 모두를 안전한 방식으로 구현할 수 있다.**

전이, 즉 릴레이의 엔티티 사이 바통 인계를 잠깐 보자. **예비 주문이 마침내 완전히 구성되고 결제되면, 그것은 자신의 종료 상태인 "결제됨"으로 이동한다. 그때 확정 주문이 자신의 시작 상태인 "결제됨"에서 태어난다.** 바통이 목표에 도달한 예비 주문에서 이제 달리기를 시작하는 확정 주문으로 넘어간다. 젊은이 엔티티가 "더 이상 젊은이 아님" 상태로 이동하며 동시에 성인 엔티티가 일어나는 것과 같은 상황이다. **성인이 다시 젊은이로 돌아갈 수 없듯, 예비 주문은 자신의 종료 상태인 "결제됨" 이전으로 돌아갈 수 없다.**

확정 주문과 거절 주문 사이의 전이는 거의 같은 방식으로 동작하지만 작은 비틀림이 있다. **확정 주문이 자신의 종료 상태인 "배달됨"에 도달했을 때, 그것이 항상 다음 엔티티를 낳지는 않는다.** 거절 주문은 확정 주문이 배달 시 거절된 경우에만 일어난다(아무도 수령 서명을 하지 않았거나, 주소를 찾을 수 없었거나). 대부분의 경우 확정 주문의 배달은 거절 주문을 낳지 않는다.

**이 설계로 코드를 작성하는 일이 크게 단순해졌고 코드가 실수에 훨씬 덜 취약해졌다.** 그림 44-12 같은 크고 복잡한 상태 그래프로는 의도된 업무 규칙을 깨는 이상하고 난해한 경로가 없다고 보장하기가 어렵다. **각각 네다섯 개의 상태를 가진 세 엔티티라는 더 단순한 설계로는, 코드가 해야 할 일을 하는지 훨씬 쉽게 검증하고 테스트할 수 있다. 보안 취약점의 위험을 극적으로 낮춘 것이다.**

**이 패턴이 값을 하려면 세 가지 요인이 갖춰져야 한다.**

- **엔티티에 상태가 너무 많다.**
- **이전 국면으로 결코 돌아가지 않는 국면들이 있다.**
- **한 국면에서 다음 국면으로의 전이가 단순하고 전이점이 적다(되도록 하나).**

엔티티의 상태 수가 지금 그대로 관리 가능하다면, 이름이 다른 여러 엔티티라는 복잡도를 끌어들일 이유가 없다. **적어도 10개의 상태가 있지 않다면 엔티티를 릴레이로 쪼개는 것을 권하지 않는다.** 마찬가지로 엔티티가 나중 국면에서 이전 국면으로 돌아갈 길이 있다면 둘로 쪼개는 것을 권하지 않는다. **엔티티 체이닝의 힘은 이전 엔티티가 끝나면 그것으로 끝이라는 단순함에서 나온다.** 주문 예제에서 이는 (아직 구성 중인) 예비 주문이 결제되는 경우다. 그러면 그것이 확정 주문으로 바뀌고, 다시 예비 주문으로 돌아갈 길이 없다.

**이전 엔티티를 다시 열 수 있다면, 그것은 한 주자가 앞선 주자에게 바통을 넘겨주는 것과 같다.** 더 이상 한 주자가 다음 주자에게 바통을 넘기며 경주가 끝나는 단순한 계승이 아니다. 대신 서로 다른 국면의 엔티티들이 되살아날 수 있는 일종의 유향 그래프를 얻는다. **릴레이 경주의 단순함이 사라진다.**

이전 엔티티가 이후 엔티티를 낳는 길이 여럿이라면, 엔티티 릴레이의 이득이 비용을 능가하는지 고려해야 한다. **다음 엔티티가 태어나는 지점이 하나뿐인 것에 단순함이 있다.** 여럿이라면 재모델링을 고려하라. 그 국면에 종료 상태를 추가할 수 있는가? 그럴 수 없다면, 그 두 국면은 하나로 봐야 하는 것일지도 모른다.

**마지막으로, 때때로 상태가 아주 많고 전이가 엉킨 실타래처럼 보이는 거대한 상태 그래프를 만나게 된다. 릴레이를 만들어 그것을 해결하려 하지 말라.** 아무리 노력해서 잘 설계하려 해도 도움이 되지 않는다. **그런 종류의 엉망은 몇 가닥을 당긴다고 해서 엉망이 아니게 되지 않는다.** 대신 모델을 설계 테이블로 되가져가기를 권한다. 도메인 전문가와 마주 앉아 이야기하라.

- **이 모델이 이렇게 복잡한 진짜 동인은 무엇인가?**
- **그 복잡도가 정말 다 필요한가?**
- **복잡도의 각 부분에 타당한 업무 동인이 있는가?**
- **그 업무 동인이 그렇게 값진 나머지, 그런 복잡도의 비용과 어쩌면 안전하지 않은 시스템의 비용을 정당화하는가?**

이 질문들이 42장의 결론과 만난다. 42.9절이 "깊은 모델은 암묵적인 것을 명시적으로 만들 때 나타난다"고 했을 때, 그 작업의 결과물이 상태 그래프이기도 하다. **엉킨 상태 그래프는 코드의 문제가 아니라 이해의 문제이고, 이해의 문제는 코드에서 풀리지 않는다.**

### 44.10.6 네 패턴의 정리

**표 44-10. 이 절의 네 패턴 — 목적, 환경, 보안 관심사 (SBD 표 7.1을 이 책이 환경 열과 함께 정리)**

| 패턴 | 목적 | 적합한 환경 | 보안 관심사 |
|---|---|---|---|
| **부분 불변 엔티티** | 어차피 바뀌어서는 안 되는 엔티티의 부분을 잠근다 | 양쪽 모두 | 무결성 |
| **엔티티 상태 객체** | 엔티티가 어떤 상태를 가질 수 있는지 파악하기 쉽게 한다 | 단일 스레드 | 무결성 |
| **엔티티 스냅샷** | 잠금을 피해 높은 처리량과 빠른 응답 시간을 뒷받침한다 | 다중 스레드 | 가용성, 무결성 |
| **엔티티 릴레이** | 크고 복잡한 상태 그래프를 다루기 쉽게 한다 | 양쪽 모두 | 무결성 |

네 패턴이 서로 배타적이지 않다는 점을 강조해 둔다. **실제 설계에서는 이들이 겹쳐 쓰인다.** 릴레이로 쪼갠 세 엔티티 각각이 상태 객체를 갖고, 각 엔티티의 고객 ID가 `private final`이며, 읽기가 많은 화면은 스냅샷으로 서비스된다. **네 패턴은 선택지의 목록이 아니라 복잡도를 줄이는 네 방향이다.**

> **이 절이 뒷받침하는 것**
>
> - 복잡도가 곧 취약성이라는 명제의 상태 버전 → **31.9** (복잡도 축소가 곧 방어다)가 이 절로 보낸 상세
> - 읽기와 쓰기를 분리하면 불변 설계로도 변경을 지원할 수 있다 → **43.1.3**이 이 절로 보낸 문제
> - 경쟁 조건이 검사를 무의미하게 만드는 것 → **29.2** (로직 결함), **45.3** (가용성을 위한 설계)
> - 읽기 경로에 쓰기 메서드가 없다는 것 → **24장** (접근 통제)의 타입 수준 대응물
> - 엉킨 상태 그래프는 이해의 문제 → **42.9** (깊은 모델은 어떻게 나타나는가)

## 이 장의 요약

- **도메인 프리미티브는 유효하지 않은 인스턴스가 존재할 수 없는 값 객체다.** 값 객체에 두 조건을 더한 것이다 — 불변식이 반드시 존재하고, 그것이 생성 시점에 강제된다. 그 결과 **타입이 존재한다는 사실 자체가 검증이 끝났다는 증거**가 되고, 43.5절의 원칙 "통과한 값을 타입으로 만든다"가 코드에서 실현된다.

- **하나의 설계 결정이 세 계보의 취약점을 동시에 닫는다.** 인젝션은 해석기가 받는 값의 정체를 코드가 모르기 때문에 성립하고, XSS는 출력 계층이 값의 컨텍스트를 모르기 때문에 성립하며, 로직 결함은 문법적으로 유효한 값이 업무 규칙을 위반하기 때문에 성립한다. 도메인 프리미티브는 세 전제를 함께 없앤다.

- **의미는 컨텍스트 안에서 정의된다.** 이메일 주소의 유효성은 RFC가 아니라 이 도메인이 정한다. 반대로 ISBN처럼 외부에서 정의된 용어는 재정의하지 않고, 필요하면 `BookId`·`UnpublishedBookNumber` 같은 새 용어를 만든다. 같은 문자열이라도 컨텍스트가 다르면 타입이 다르다.

- **도메인 프리미티브 라이브러리는 유틸리티 모음이 아니라 유비쿼터스 언어의 목록이다.** 그것을 API의 인자·반환값·필드에 쓰면 코드베이스의 모든 메서드가 공짜로 입출력 검증을 얻는다. 그리고 그 라이브러리는 다른 도메인을 향한 공개 API에는 노출되지 않는다 — 노출하는 순간 도메인 모델이 공개 API가 되고, 모델을 고칠 수 없게 되며, 고칠 수 없는 모델은 안전해지지 못한다.

- **읽기 1회 객체는 누출을 막는 것이 아니라 탐지 가능하게 만든다.** 로깅·문자열 병합·직렬화·예외 메시지라는 네 갈래 누출 경로를 `toString`·`Externalizable`·`transient`·1회 소비로 닫는다. 톰캣 세션 지속화 사례가 보여 주듯, 이 패턴의 진짜 가치는 **누구도 잘못하지 않았는데 결함이 나타나는 조합**을 예외로 폭로하는 데 있다.

- **엔티티에서 도메인 프리미티브를 쓰면 엔티티는 의미 검증만 남긴다.** 열 줄짜리 `addItem`에 숨은 두 개의 실수 — 체크섬 미검증과 음수 수량 — 는 확증 편향 때문에 사람의 눈으로 찾기 어렵다. 검증을 타입으로 옮기면 그 실수가 애초에 표현될 수 없다.

- **테인트 분석의 네 부분이 이 책의 지도와 정확히 겹친다.** 오염 원천은 25.5절의 진입점 목록이고, 오염 싱크는 27·32장과 16.6절의 지점들이며, 정화는 43.4절의 다섯 단계다. 두 사고는 형식적 연결 없이 생성자를 검증의 중심으로 삼는 같은 결론에 도달했다.

- **엔티티는 생성 즉시 일관되어야 한다.** 무인자 생성자와 세터 초기화는 필수 필드가 추가될 때마다 조용히 누락 지점을 만든다. 단순한 제약에는 필수 필드 생성자를, 유창한 구성에는 플루언트 인터페이스를, 속성에 걸치는 고급 제약에는 빌더 패턴을 쓴다. ORM은 `private` 무인자 생성자와 필드 애너테이션으로 다룰 수 있다.

- **프레임워크의 기본 동작은 프레임워크의 관심사를 최적화한 것이지 도메인 불변식을 지키기 위한 것이 아니다.** ORM의 무인자 생성자, 톰캣의 세션 지속화, ECB 모드의 블록 독립성이 같은 구조의 세 사례다.

- **엔티티의 경계가 곧 신뢰 경계다.** `private` 필드에 제약 없는 세터를 다는 것은 보안문에 열쇠를 꽂아 두는 것이고, 가변 객체나 컬렉션의 내부 참조를 내주는 것은 문을 아예 여는 것이다. 컬렉션은 수정 불가 형태로 노출하고, 그 안의 항목도 불변이어야 한다.

- **복잡도를 줄이는 네 방향이 있다.** 바뀔 필요 없는 부분은 `private final`로 잠그고(부분 불변), 상태 규칙은 이름을 가진 객체로 뽑아내고(상태 객체), 읽기가 지배적인 다중 스레드 환경에서는 불변 스냅샷과 갱신 서비스로 나누고(스냅샷), 상태가 열 개를 넘으면 되돌아갈 수 없는 국면으로 쪼갠다(릴레이). 엉킨 실타래는 릴레이로 풀리지 않는다 — 그것은 이해의 문제다.

## 이어지는 장

이 장은 값과 상태를 다뤘다. 값이 유효하다는 것을 타입으로 보장하는 법, 상태가 일관되게 생성되고 일관되게 유지되게 하는 법, 그리고 상태의 복잡도를 감당 가능한 크기로 줄이는 법. 그러나 이 장 전체가 **성공 경로**를 가정하고 있었다는 점을 짚어야 한다.

`new Quantity(-1)`은 예외를 던진다. `new ISBN("nonsense")`도, `checkInvariants()`도, `status.ship()`도 그렇다. **이 장은 그 예외들을 만드는 데까지만 갔다. 던져진 다음에 무슨 일이 일어나야 하는지는 다루지 않았다.**

45장이 그것을 받는다. 45.1절은 예외를 어떻게 설계할 것인지, 그리고 예외 페이로드에 무엇을 담지 말아야 하는지를 다룬다 — 44.5절의 읽기 1회 객체가 예외 메시지를 누출 경로로 지목했던 그 문제의 반대편이다. 45.2절은 더 깊은 질문을 던진다. **애초에 실패를 예외로 표현하는 것이 옳은가.** 도메인 프리미티브 생성 실패는 예외적인 사건이 아니라 사용자가 잘못 입력했다는 일상적 사실이고, 일상적 사실을 예외로 다루면 그 처리가 예외 처리 코드로 흩어진다. 45.6절은 43.2.2절과 이 장이 함께 남긴 두 원칙 — 검증 전에 복구하지 말라, 입력을 반향하지 말라 — 을 실패 처리 설계의 관점에서 완성한다.

**가용성의 축도 45장이 이어받는다.** 44.10.4절에서 엔티티 스냅샷이 가용성을 뒷받침한다고 했을 때, 그것은 데이터베이스 잠금이라는 하나의 원인에 대한 답이었다. 45.3절부터 45.5절은 그 논의를 복원력과 응답성, 서킷 브레이커와 타임아웃, 벌크헤드 격리로 확장하고, 45.8절은 네트워크·HTTP·GraphQL 레벨의 DoS 방어가 왜 하나의 구조를 공유하는지를 정리한다.

**46장은 이 장이 만든 것을 지키는 법을 다룬다.** 44.5.3절에서 "이 실수는 지속적 전달 파이프라인의 테스트가 깨지기 때문에 이른 시점에 잡힌다"고 했다. 그 파이프라인이 46.8절의 주제이고, 46.9절은 도메인 규칙을 이해한 단위 테스트가 어떻게 설계를 지키는지를 다룬다. 도메인 프리미티브의 경계값 테스트 — 0과 1과 200과 201 — 가 그곳에서 체계가 된다. 46.2절은 44.5절이 다루지 않은 비밀의 다른 절반, 즉 **코드 안이 아니라 코드 바깥의 비밀**을 다룬다.

**47장은 이 장을 현실의 코드베이스에 적용한다.** 47.1절과 47.2절은 레거시 코드에서 도메인 프리미티브를 적용할 지점을 찾는 세 가지 접근법을, 47.3절은 44.5절이 다룬 암묵적 데이터 누출을 기존 코드에서 식별하는 법을, 47.5절과 47.6절은 이 장의 기법이 **불완전하게** 적용됐을 때 생기는 함정 — 검증이 부족한 도메인 타입, 암묵적 통화 단위를 가진 부분적 도메인 프리미티브 — 을 다룬다. 그리고 47.8절이 44.2절과 44.4절을 마이크로서비스의 규모로 확장한다. **각 서비스가 하나의 바운디드 컨텍스트라면, 서비스 사이의 모든 호출은 컨텍스트 경계를 넘는 일이고, 경계를 넘을 때마다 값은 다시 타입이 되어야 한다.**

한 문장으로 말하면 이렇다. **43장은 값이 유효하다는 것을 어떻게 보장하는지를 다뤘고, 44장은 그 보장을 타입과 엔티티에 담는 법을 다뤘으며, 45장은 보장이 깨졌을 때 무슨 일이 일어나야 하는지를 다룬다.**
