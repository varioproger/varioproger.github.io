# 16장. 로깅, 추적, 그리고 로봇

> **이 장에서 다루는 것**
>
> - 서버와 프록시가 트랜잭션마다 무엇을 기록하며, 그 각각의 필드를 얼마나 믿을 수 있는가
> - 표준 로그 포맷의 필드 구조 — 그리고 필드가 늘어날 때마다 함께 늘어나는 것
> - 캐시가 원 서버의 로그에 뚫는 구멍, 그리고 그것을 메우려던 프로토콜
> - 방어를 위해 더 많이 기록할수록 누출 시 피해가 커진다는 긴장, 그리고 그 긴장을 다루는 세 축
> - 검증되지 않은 문자열을 로그에 넣었을 때 생기는 두 가지 사고 — 로그 인젝션과 암묵적 데이터 누출
> - 우리 사이트를 읽어 가는 자동화된 주체들, 그들을 통제한다고 믿어 온 파일, 그리고 그 파일이 실제로 알려 주는 것

12장부터 15장까지는 요청이 **어디로 가고 누가 그것을 처리하는가**를 다뤘다. 그 서술은 매번 같은 자리에서 끝났다. 서버는 요청을 처리하고 응답을 보낸 다음 마지막으로 **기록한다**(→ 12.5). 이 장은 그 마지막 단계에서 시작한다.

로그는 이 책이 다뤄 온 대상 중 성격이 가장 이중적이다. 다른 어떤 메커니즘도 이렇게까지 양쪽을 동시에 하지 않는다. 침해가 일어난 뒤 무슨 일이 있었는지 재구성할 수 있는 유일한 근거가 로그다. 동시에 침해가 일어났을 때 공격자가 가장 먼저 찾는 것 중 하나도 로그다. 감사 로그 한 줄에 세션 토큰과 요청 파라미터가 들어 있다면, 그 로그 파일 하나를 읽는 것으로 애플리케이션 전체를 장악할 수 있다(→ 16.5). **방어 자산과 누출 경로가 같은 파일이다.**

이 이중성은 회피할 수 없다. 덜 기록하면 사건을 재구성하지 못하고, 더 기록하면 그 기록 자체가 표적이 된다. 이 장의 16.4절과 16.5절이 이 긴장을 정면으로 놓고, 16.6절과 16.7절이 그것을 다루는 두 가지 처방 — **무엇을 넣지 말 것인가**와 **어디에 둘 것인가** — 를 제시한다.

장의 후반부는 다른 질문으로 넘어간다. **누가 우리 사이트를 읽어 가는가.** 접근 로그에 남는 요청의 상당수는 사람이 만든 것이 아니다. 로봇은 사람보다 빠르고, 지치지 않으며, 링크를 발견하는 즉시 따라간다. 그리고 로봇을 통제한다고 알려진 메커니즘 — `robots.txt` — 은 강제력이 없을 뿐 아니라, **숨기려는 경로의 목록을 공개된 파일에 적어 두는 일**이기도 하다(→ 16.9). 로그의 이중성과 정확히 같은 구조가 여기서 한 번 더 나타난다.

## 16.1 무엇을 로깅할 것인가

거의 모든 서버와 프록시가 자신이 처리한 HTTP 트랜잭션의 요약을 기록한다. 이유는 하나가 아니다. 사용 추적, 보안, 과금, 오류 탐지가 모두 로그를 근거로 한다.

이 목적들을 크게 묶으면 **두 갈래**가 된다.

1. **서버나 프록시의 문제를 찾는 것.** 어떤 요청이 실패하고 있는가, 언제부터인가, 어떤 클라이언트에서인가.
2. **사이트가 어떻게 접근되는지에 대한 통계를 만드는 것.** 마케팅, 과금, 용량 계획 — 서버를 더 놓아야 하는지, 대역폭을 늘려야 하는지의 판단이 여기 근거한다.

이 장이 뒤에서 세 번째 갈래를 추가한다. **침해를 탐지하고 사후에 재구성하는 것**(16.5절)이다. HTTP-DG는 이 세 번째를 "보안"이라는 한 단어로만 언급하고 지나가지만, 이 책에서는 그것이 나머지 둘을 합친 것보다 중요하다.

### 16.1.1 전부 기록할 수는 없다

HTTP 트랜잭션의 모든 헤더를 기록하는 것은 원리적으로 가능하다. 그러나 하루에 수백만 건의 트랜잭션을 처리하는 서버나 프록시에서 그 데이터의 부피는 금방 감당할 수 없는 크기가 된다. 게다가 그렇게 모은 데이터의 대부분은 **관심 대상이 아니며 한 번도 열어 보지 않을 것**이다.

그래서 실제로는 트랜잭션의 기본 요소만 기록한다. 흔히 기록되는 필드는 다음과 같다.

- HTTP 메서드
- 클라이언트와 서버의 HTTP 버전
- 요청된 리소스의 URL
- 응답의 HTTP 상태 코드
- 요청 메시지와 응답 메시지의 크기(엔티티 본문 포함)
- 트랜잭션이 일어난 시각
- `Referer`와 `User-Agent` 헤더의 값

각 필드가 왜 거기 있는지는 목적과 짝을 이룬다.

**메서드와 URL**은 요청이 무엇을 하려 했는지를 말한다. 리소스를 `GET`했는지, 주문 폼을 `POST`했는지. URL은 사이트 안에서 어느 페이지가 인기 있는지를 추적하는 데도 쓰인다.

**버전 문자열**은 클라이언트와 서버에 대한 단서다. 클라이언트와 서버 사이의 이상한 상호작용을 디버깅할 때 유용하다. 예를 들어 요청 실패율이 예상보다 높게 나타난다면, 버전 정보가 서버와 상호작용하지 못하는 새 브라우저 릴리스를 가리켜 줄 수 있다.

**상태 코드**는 요청이 어떻게 되었는지를 말한다. 성공했는지, 인가 시도가 실패했는지, 리소스를 찾았는지(→ 8.4).

**크기와 타임스탬프**는 주로 회계 목적이다. 애플리케이션으로 들어오고 나가고 통과한 바이트가 얼마인지를 추적한다. 타임스탬프는 그 외에 **관측된 문제를 그 시각에 이루어지던 요청과 연결하는** 데 쓰인다. 사후 재구성의 축이 되는 것이 바로 이 필드다.

### 16.1.2 각 필드를 얼마나 믿을 수 있는가

여기서 이 책이 앞의 여러 장에서 반복해 온 질문을 로그에 적용해야 한다. **로그에 기록된 각 필드의 값은 어디에서 왔는가.**

로그는 서버가 쓰지만, 서버가 쓰는 값의 상당수는 **클라이언트가 보낸 문자열을 그대로 옮긴 것**이다. 로그를 증거로 쓰려면 어느 필드가 그런 성질을 갖는지 알아야 한다.

**표 16-1. 로그 필드의 출처와 신뢰도**

| 필드 | 값을 만든 주체 | 위조 비용 | 참조 |
|---|---|---|---|
| 타임스탬프 | 기록하는 서버 자신 | 높음(서버 시계를 건드려야 함) | — |
| 응답 상태 코드 | 기록하는 서버 자신 | 높음 | 8.4 |
| 응답 크기 | 기록하는 서버 자신 | 높음 | 10.2 |
| 메서드·URL·버전 | 클라이언트(요청 라인 그대로) | **없음** — 클라이언트가 쓴 텍스트 | 8.2 |
| `Referer` | 클라이언트 | **없음** | 8.6 |
| `User-Agent` | 클라이언트 | **없음** | 8.6 |
| 인증된 사용자명 | 서버의 인증 절차 | 인증 메커니즘의 강도에 종속 | 21장, 22장 |
| ident 사용자명 | 클라이언트 호스트의 ident 서비스 | 낮음(클라이언트 측 데몬의 응답) | 12.3 |
| 원격 호스트 IP | TCP 커넥션의 출발지 주소 | 중간 — 아래 참조 | 4.6 |

마지막 행이 가장 까다롭다. 클라이언트 IP 주소는 TCP 커넥션에서 왔으므로 헤더처럼 자유롭게 쓸 수 있는 값이 아니다. 3방향 핸드셰이크를 완료해야 하는 이상, 출발지 주소를 임의로 위조하고 HTTP 트랜잭션을 끝까지 진행할 수는 없다(→ 3.3). 그러나 그 주소가 **한 사람을 가리킨다는 보장은 어디에도 없다.**

- NAT 뒤에서는 수백, 수천 명이 하나의 공인 주소를 공유한다(→ 4.3).
- 프록시를 경유하면 서버가 보는 주소는 프록시의 것이다(→ 13.3).
- full NAT 방식의 로드 밸런서는 클라이언트 주소를 아예 지운다(→ 15.6).

이 소실을 메우려고 `X-Forwarded-For` 같은 헤더가 쓰인다. 그런데 그것은 헤더이므로 **위조 비용이 0인 값으로 돌아온다**(→ 4.6, 8.6). 신뢰할 수 있는 중간자가 덧붙인 항목과 클라이언트가 처음부터 넣어 보낸 항목이 같은 헤더 안에 나란히 들어 있고, 서버는 둘을 구별할 방법이 없다.

`Via` 헤더도 같은 성질을 갖는다. 경로 위의 각 홉이 자기를 기록하도록 되어 있지만, 클라이언트가 처음부터 가짜 `Via`를 넣어 보내면 로그에는 존재하지 않는 프록시가 남는다(→ 13.6).

> **이 절이 뒷받침하는 것**
>
> - 로그 필드의 절반 이상이 클라이언트가 쓴 문자열이다 → **16.6** (그 문자열이 로그 파일의 구조 자체를 바꾸는 경우)
> - 클라이언트 IP는 사람이 아니라 커넥션의 출발지다 → **20.2** (그 값으로 사용자를 식별하려는 시도의 실패)
> - 상태 코드와 응답 크기는 서버가 만든 값이다 → **30.3** (그래서 공격자에게는 추론의 채널이 된다)

## 16.2 로그 포맷 — CLF, Combined, Extended, 커스텀

몇 가지 로그 포맷이 사실상의 표준이 되었다. 상용·오픈소스 HTTP 애플리케이션 대부분이 이 중 하나 이상을 지원하며, 많은 경우 관리자가 포맷을 직접 구성할 수도 있다.

표준 포맷을 쓰는 이유는 단순하다. **도구 생태계**다. 이 포맷들을 처리하고 기본 통계를 만들어 내는 오픈소스·상용 패키지가 이미 많이 존재한다. 표준 포맷을 쓰면 애플리케이션과 관리자가 그 자원에 그대로 연결된다.

이 사실은 뒤에서 다시 나온다. **표준 포맷을 쓴다는 것은 그 포맷을 파싱하는 도구가 존재한다는 뜻이고, 파싱하는 도구가 존재한다는 것은 그 파서를 겨냥한 입력이 가능하다는 뜻이다**(→ 16.6).

### 16.2.1 Common Log Format

가장 널리 쓰이는 포맷은 이름 그대로 **Common Log Format(CLF)** 이다. 원래 NCSA가 정의했고 많은 서버가 이것을 기본값으로 쓴다.

**표 16-2. Common Log Format의 필드 (순서대로)**

| 필드 | 설명 |
|---|---|
| `remotehost` | 요청자 머신의 호스트명 또는 IP 주소(서버가 역DNS를 하도록 설정되지 않았거나 조회에 실패하면 IP) |
| `username` | ident 조회를 수행한 경우, 요청자의 인증된 사용자명 |
| `auth-username` | 인증을 수행한 경우, 요청자가 인증에 사용한 사용자명 |
| `timestamp` | 요청의 날짜와 시각 |
| `request-line` | HTTP 요청 라인의 **정확한 텍스트**. `"GET /index.html HTTP/1.1"` |
| `response-code` | 응답으로 반환된 HTTP 상태 코드 |
| `response-size` | 응답 엔티티의 `Content-Length`. 응답에 엔티티가 없으면 0 |

`username` 필드에 쓰이는 ident 조회는 RFC 931이 기술하는 방식이다. 이 프로토콜의 성질과 그것을 신뢰할 수 없는 이유는 12.3절에서 다뤘다.

```
209.1.32.44 - - [03/Oct/1999:14:16:00 -0400] "GET / HTTP/1.0" 200 1024
http-guide.com - dg [03/Oct/1999:14:16:32 -0400] "GET / HTTP/1.0" 200 477
http-guide.com - dg [03/Oct/1999:14:16:32 -0400] "GET /foo HTTP/1.0" 404 0
```

*예제 16-1. Common Log Format 항목 (HTTP-DG 예제 21-1)*

첫 항목의 필드는 다음과 같이 대응된다.

| 필드 | 값 |
|---|---|
| `remotehost` | `209.1.32.44` |
| `username` | (비어 있음) |
| `auth-username` | (비어 있음) |
| `timestamp` | `03/Oct/1999:14:16:00 -0400` |
| `request-line` | `GET / HTTP/1.0` |
| `response-code` | `200` |
| `response-size` | `1024` |

`remotehost` 필드는 예제에서 보듯 호스트명(`http-guide.com`)일 수도 IP 주소(`209.1.32.44`)일 수도 있다. 둘째·셋째 필드의 하이픈은 그 필드가 비어 있음을 뜻한다. 즉 ident 조회가 일어나지 않았거나(둘째) 인증이 수행되지 않았다(셋째).

여기서 포맷 자체의 성질 하나를 붙잡아 둬야 한다. **CLF는 줄 단위이고, 필드는 공백으로 구분되며, 두 개의 필드(요청 라인, 그리고 Combined의 `Referer`·`User-Agent`)는 큰따옴표로 감싼다.** 구분자는 공백·개행·큰따옴표 세 가지다. 그리고 그중 두 필드는 클라이언트가 보낸 문자열을 옮긴 것이다. 이 조합이 16.6절의 출발점이다.

### 16.2.2 Combined Log Format

Apache 등이 지원하는 **Combined Log Format**은 CLF를 정확히 그대로 두고 필드 두 개를 뒤에 덧붙인 것이다.

**표 16-3. Combined Log Format이 추가하는 필드**

| 필드 | 설명 |
|---|---|
| `Referer` | `Referer` HTTP 헤더의 내용 |
| `User-Agent` | `User-Agent` HTTP 헤더의 내용 |

`User-Agent` 필드는 어떤 HTTP 클라이언트 애플리케이션이 요청을 만들었는지 파악하는 데, `Referer` 필드는 요청자가 이 URL을 **어디에서 발견했는지**에 대한 정보를 얻는 데 쓰인다.

```
209.1.32.44 - - [03/Oct/1999:14:16:00 -0400] "GET / HTTP/1.0" 200 1024
"http://www.joes-hardware.com/" "5.0: Mozilla/4.0 (compatible; MSIE 5.0; Windows 98)"
```

*예제 16-2. Combined Log Format 항목 (HTTP-DG 예제 21-2. 지면 사정으로 두 줄로 접었으나 실제 로그에서는 한 줄이다)*

앞의 일곱 필드는 CLF와 완전히 동일하고, 새 필드 두 개가 끝에 붙는다.

이 두 필드가 추가된 순간 로그의 성격이 달라진다. 앞의 일곱 필드는 "무엇을 요청했고 어떻게 됐는가"였다. 새 두 필드는 **"누가, 어디에서 왔는가"** 다. 즉 이 시점부터 로그는 트랜잭션의 기록이 아니라 **사람의 이동 경로에 대한 기록**이 된다. 16.4절이 다루는 문제가 정확히 여기서 시작한다.

`Referer`가 담는 것이 이전 페이지의 **전체 URL**이라는 점도 기억해 둘 필요가 있다. 이전 페이지의 URL에 쿼리 문자열이 있었다면 그 내용도 함께 기록된다(→ 8.6, 26.1).

### 16.2.3 Netscape Extended와 Extended 2

넷스케이프가 상용 HTTP 애플리케이션 영역에 진입하면서 자사 서버를 위해 정의한 로그 포맷들이 다른 구현들에도 채택되었다. 넷스케이프의 포맷은 NCSA의 CLF에서 파생되었으되, **프록시와 웹 캐시 같은 HTTP 애플리케이션에 필요한 필드를 더한 것**이다.

**Netscape Extended Log Format**의 앞 일곱 필드는 CLF와 동일하다. 그 뒤에 다음 필드들이 순서대로 붙는다.

**표 16-4. Netscape Extended Log Format이 추가하는 필드**

| 필드 | 설명 |
|---|---|
| `proxy-response-code` | 트랜잭션이 프록시를 거친 경우, 서버가 프록시에게 준 HTTP 응답 코드 |
| `proxy-response-size` | 트랜잭션이 프록시를 거친 경우, 서버가 프록시에게 보낸 응답 엔티티의 `Content-Length` |
| `client-request-size` | 클라이언트가 프록시에게 보낸 요청의 본문·엔티티 `Content-Length` |
| `proxy-request-size` | 트랜잭션이 프록시를 거친 경우, 프록시가 서버에게 보낸 요청의 본문·엔티티 `Content-Length` |
| `client-request-hdr-size` | 클라이언트 요청 헤더의 길이(바이트) |
| `proxy-response-hdr-size` | 프록시가 요청자에게 보낸 응답 헤더의 길이(바이트) |
| `proxy-request-hdr-size` | 프록시가 서버에게 보낸 요청 헤더의 길이(바이트) |
| `server-response-hdr-size` | 서버 응답 헤더의 길이(바이트) |
| `proxy-timestamp` | 요청과 응답이 프록시를 통과하는 데 걸린 시간(초) |

```
209.1.32.44 - - [03/Oct/1999:14:16:00-0400] "GET / HTTP/1.0" 200 1024 200 1024 0 0
215 260 279 254 3
```

*예제 16-3. Netscape Extended Log Format 항목 (HTTP-DG 예제 21-3)*

여기서 확장 필드는 `proxy-response-code`=200, `proxy-response-size`=1024, `client-request-size`=0, `proxy-request-size`=0, `client-request-hdr-size`=215, `proxy-response-hdr-size`=260, `proxy-request-hdr-size`=279, `server-response-hdr-size`=254, `proxy-timestamp`=3이다.

**Netscape Extended 2 Log Format**은 여기에 프록시와 캐시 동작을 더 자세히 담는 네 필드를 더한다.

**표 16-5. Netscape Extended 2 Log Format이 추가하는 필드**

| 필드 | 설명 |
|---|---|
| `route` | 프록시가 클라이언트를 대신해 요청을 만들 때 사용한 경로 |
| `client-finish-status-code` | 클라이언트→프록시 요청이 정상 완료(`FIN`)되었는지 중단(`INTR`)되었는지 |
| `proxy-finish-status-code` | 프록시→서버 요청이 정상 완료되었는지 중단되었는지 |
| `cache-result-code` | 캐시가 이 요청에 어떻게 반응했는지 |

```
209.1.32.44 - - [03/Oct/1999:14:16:00-0400] "GET / HTTP/1.0" 200 1024 200 1024 0 0
215 260 279 254 3 DIRECT FIN FIN WRITTEN
```

*예제 16-4. Netscape Extended 2 Log Format 항목 (HTTP-DG 예제 21-4)*

`route` 필드의 값은 `DIRECT`(서버에서 직접 가져옴), `PROXY(host:port)`(해당 프록시를 거쳐 가져옴), `SOCKS(socks:port)`(해당 SOCKS 서버를 거쳐 가져옴) 세 가지다. finish 상태 코드는 `-`(요청이 시작조차 되지 않음), `FIN`(정상 완료), `INTR`(클라이언트가 중단했거나 프록시·서버가 종료), `TIMEOUT`(프록시·서버가 타임아웃 처리)이다.

**표 16-6. Netscape 캐시 결과 코드**

| 코드 | 설명 |
|---|---|
| `-` | 리소스가 캐시 불가였다 |
| `WRITTEN` | 리소스를 캐시에 기록했다 |
| `REFRESHED` | 캐시에 있던 리소스를 갱신했다 |
| `NO-CHECK` | 캐시된 리소스를 반환했다. 신선도 검사는 하지 않았다 |
| `UP-TO-DATE` | 캐시된 리소스를 반환했다. 신선도 검사를 했다 |
| `HOST-NOT-AVAILABLE` | 캐시된 리소스를 반환했다. 원격 서버에 접근할 수 없어 신선도 검사를 하지 못했다 |
| `CL-MISMATCH` | 캐시에 기록하지 않았다. `Content-Length`와 실제 리소스 크기가 달라 기록을 중단했다 |
| `ERROR` | 오류로 인해 캐시에 기록하지 못했다(타임아웃, 클라이언트의 트랜잭션 중단 등) |

이 표는 14장에서 다룬 캐시 처리 단계(→ 14.4)와 신선도 판정(→ 14.5)이 로그 한 글자로 압축된 형태다. `NO-CHECK`와 `UP-TO-DATE`의 구별, `HOST-NOT-AVAILABLE`이 남는 상황 — 이것들은 사후 조사에서 "그 시각 클라이언트가 실제로 본 것은 어느 버전인가"를 판정할 때 결정적인 단서가 된다.

### 16.2.4 Squid 프록시 로그 포맷

Squid 프록시 캐시는 초기 웹 프록시 캐시 프로젝트에서 출발한 오랜 오픈소스 프로젝트다. Squid를 관리하기 위한 도구 — 로그를 처리하고 감사하고 분석하는 것들을 포함해서 — 가 다수 만들어졌고, **이후의 많은 프록시 캐시가 그 도구들을 그대로 쓰기 위해 Squid의 로그 포맷을 채택했다.** 표준 포맷의 이점이 어떻게 작동하는지를 보여 주는 사례다.

**표 16-7. Squid Log Format의 필드**

| 필드 | 설명 |
|---|---|
| `timestamp` | 요청이 도착한 시각(1970년 1월 1일 GMT 기준 초) |
| `time-elapsed` | 요청과 응답이 프록시를 통과하는 데 걸린 시간(밀리초) |
| `host-ip` | 클라이언트 호스트 머신의 IP 주소 |
| `result-code/status` | result는 이 요청에서 프록시가 취한 동작(Squid 고유), code는 프록시가 클라이언트에게 보낸 HTTP 응답 코드 |
| `size` | 프록시가 클라이언트에게 보낸 응답의 길이(HTTP 응답 헤더와 본문 포함, 바이트) |
| `method` | 클라이언트 요청의 HTTP 메서드 |
| `url` | 클라이언트 요청의 URL |
| `rfc931-ident` | 클라이언트의 인증된 사용자명 |
| `hierarchy/from` | hierarchy는 프록시가 사용한 경로(넷스케이프의 `route`에 해당), from은 프록시가 요청을 보낸 서버의 이름 |
| `content-type` | 프록시 응답 엔티티의 `Content-Type` |

```
99823414 3001 209.1.32.44 TCP_MISS/200 4087 GET http://www.joes-hardware.com
- DIRECT/proxy.com text/html
```

*예제 16-5. Squid Log Format 항목 (HTTP-DG 예제 21-5)*

`url` 필드에 대해 HTTP-DG가 각주로 붙인 경고를 그대로 옮길 값이 있다. **프록시는 요청된 URL 전체를 기록하는 경우가 많고, 따라서 URL 안에 사용자명과 비밀번호 성분이 들어 있으면 프록시가 그 정보를 의도치 않게 기록하게 된다.** URL의 `userinfo` 성분(→ 7.2)이 왜 위험한지, `fat URL`(→ 20.4)이 왜 세션 관리 방식으로 부적절한지를 이 한 문장이 요약한다. 이것은 16.4절의 핵심 사례다.

Squid의 result code는 캐시 동작을 세분한 것이다. 주요 항목만 옮긴다.

**표 16-8. 주요 Squid result 코드**

| 동작 | 설명 |
|---|---|
| `TCP_HIT` | 유효한 사본을 캐시에서 서비스했다 |
| `TCP_MISS` | 리소스가 캐시에 없었다 |
| `TCP_REFRESH_HIT` | 캐시에 있었고 신선도 검사가 필요했다. 재검증 결과 사본이 여전히 신선했다 |
| `TCP_REF_FAIL_HIT` | 재검증이 실패해(예: 서버에 연결 불가) **오래된** 리소스를 반환했다 |
| `TCP_REFRESH_MISS` | 재검증 결과 캐시 사본이 낡았음을 알고 새 버전을 받았다 |
| `TCP_CLIENT_REFRESH_MISS` | 요청자가 `Pragma: no-cache` 등을 보내 프록시가 강제로 원본을 가져왔다 |
| `TCP_IMS_HIT` | 요청자가 조건부 요청을 보냈고 캐시 사본에 대해 검증되었다 |
| `TCP_SWAPFAIL_MISS` | 캐시에 있다고 판단했으나 어떤 이유로 접근하지 못했다 |
| `TCP_NEGATIVE_HIT` | 부정 캐시된 응답(예: 캐시된 404)을 반환했다 |
| `TCP_MEM_HIT` | 유효한 사본을 캐시에서, 그것도 메모리에서 서비스했다 |
| `TCP_DENIED` | 이 리소스에 대한 요청이 거부되었다(요청자에게 권한이 없을 가능성이 높다) |
| `TCP_OFFLINE_HIT` | 오프라인 모드에서 캐시로부터 반환했다. 오프라인 모드에서는 검증하지 않는다 |
| `UDP_*` | UDP 인터페이스로 받은 요청. HTTP가 아니라 ICP 등 캐시 간 프로토콜이다(→ 14.11) |

`TCP_REF_FAIL_HIT`와 `TCP_OFFLINE_HIT`는 특히 눈여겨볼 값이다. **둘 다 "신선하지 않을 수 있는 것을 반환했다"는 기록**이며, 사후 조사에서 "그때 사용자가 본 화면이 무엇이었는가"를 판정할 때 이 두 코드는 결론을 바꾼다.

### 16.2.5 커스텀 포맷 — 그리고 필드를 늘릴 때 함께 늘어나는 것

넷스케이프 애플리케이션을 포함한 많은 HTTP 애플리케이션이 Flexible Log Format 같은 추가 포맷과 커스텀 로그 필드 출력 수단을 제공한다. 관리자가 트랜잭션의 어느 부분(헤더, 상태, 크기 등)을 로그에 담을지 직접 고를 수 있다.

커스텀 포맷 기능이 추가된 이유는 **관리자가 로그에서 무엇을 얻고 싶어 할지 미리 예측하기 어렵기 때문**이다. 이 유연성은 필요하다. 그러나 이 장의 논지에서 보면 그것은 동시에 위험의 원천이다.

로그 포맷을 설계하는 일은 다음 두 축의 값을 동시에 정하는 일이다.

**표 16-9. 필드를 추가할 때 동시에 결정되는 두 가지**

| 필드를 추가하면 | 얻는 것 | 함께 생기는 것 |
|---|---|---|
| `Referer` | 유입 경로 분석, 링크 발견 경로 추적 | 이전 페이지 URL 전체 — 쿼리 문자열에 담긴 것 포함 |
| `User-Agent` | 클라이언트 종류 통계, 로봇 식별 | 사용자 환경 지문(→ 25.6) |
| `Cookie` | 세션 단위 추적, 사건 재구성 | **세션 토큰이 로그에 그대로 남음**(→ 23.3) |
| 요청 본문 전체 | 완전한 포렌식 기록(→ 16.5) | 모든 자격증명·개인정보·결제정보가 로그에 남음 |
| 응답 본문 | 사용자에게 실제로 전달된 것의 확증 | 위와 같음. 게다가 부피가 폭발함 |
| `X-Forwarded-For` | 프록시 뒤 클라이언트 주소 복구 | 위조 가능한 값을 사실인 것처럼 기록(→ 4.6) |

오른쪽 열이 16.4절과 16.5절의 긴장이다. 왼쪽 열이 필요하다는 것이 방어자의 입장이고, 오른쪽 열이 위험하다는 것도 같은 방어자의 입장이다. 어느 한쪽만 고르면 답이 되지 않는다.

> **이 절이 뒷받침하는 것**
>
> - 표준 로그 포맷은 줄 단위·공백 구분·따옴표 감싸기의 조합이며 두 필드는 클라이언트가 쓴다 → **16.6** (구분자를 담은 입력이 로그의 구조를 바꾸는 문제)
> - 프록시는 URL 전체를 기록하므로 URL에 담긴 비밀이 프록시 로그에 남는다 → **20.4**, **23.3** (URL을 세션 상태의 운반체로 쓰면 안 되는 이유)
> - 캐시 결과 코드는 "무엇이 반환되었는가"를 판정하는 단서다 → **14.8** (공유 캐시에서 사용자 간 응답이 섞이는 사건의 조사)

## 16.3 히트 미터링과 캐시 통계

원 서버는 과금을 위해 상세한 로그를 유지하는 경우가 많다. 콘텐츠 제공자는 URL이 얼마나 자주 접근되는지 알아야 하고, 광고주는 자기 광고가 몇 번 노출되었는지 알고 싶어 하며, 저자는 자기 콘텐츠가 얼마나 인기 있는지 알고 싶어 한다.

클라이언트가 웹 서버를 직접 방문할 때는 로깅이 이 일을 잘 해낸다. 그러나 **캐시가 클라이언트와 서버 사이에 서서 많은 접근이 서버에 도달하지 못하게 막는다.** 그것이 캐시의 존재 이유 자체다(→ 14.1). 그리고 브라우저 사실상 전부가 캐시를 갖고 있다.

캐시가 다수의 HTTP 요청을 원 서버를 방문하지 않고 처리하므로, **서버에는 클라이언트가 자기 콘텐츠에 접근했다는 기록이 남지 않는다.** 로그에 구멍이 생긴다.

### 16.3.1 캐시 버스팅과 그 대가

로그 데이터가 빠지는 것을 견디지 못한 콘텐츠 제공자는 가장 중요한 페이지에 대해 **캐시 버스팅(cache busting)** 에 의지하게 된다. 특정 콘텐츠를 의도적으로 캐시 불가로 표시해서 그 콘텐츠에 대한 모든 요청이 원 서버로 오게 만드는 것이다(→ 14.6). 그러면 원 서버가 접근을 기록할 수 있다.

캐싱을 무력화하면 로그는 나아진다. 그러나 그 대가로 **요청이 느려지고, 원 서버와 네트워크의 부하가 늘어난다.** 캐싱이 제공하던 모든 이점을 로그 한 줄과 바꾸는 셈이다.

이것은 이 책이 반복해 온 형태의 거래다. 14.12절이 광고와 캐시의 관계에서 같은 구조를 다뤘다. 성능을 위해 도입한 계층이 관측을 방해하고, 관측을 회복하려면 성능을 포기해야 한다.

### 16.3.2 Hit Metering 프로토콜

프록시 캐시(그리고 일부 클라이언트)는 자기 로그를 유지한다. 서버가 그 로그에 접근할 수 있다면 — 혹은 최소한 자기 콘텐츠가 프록시 캐시에 의해 몇 번 서비스되었는지 대략이라도 알 수 있다면 — 캐시 버스팅을 피할 수 있다.

**Hit Metering 프로토콜**(RFC 2227)은 이 문제에 대한 제안이다. 캐시가 원 서버에게 주기적으로 캐시 접근 통계를 보고하도록 요구한다.

이 프로토콜은 설계상 캐시가 로깅에 제기하는 문제의 완전한 해법이 아니다. 서버가 추적하고 싶어 하는 지표를 얻는 **기본적인 수단**을 제공할 뿐이다. 그리고 **널리 구현되거나 배포되지 않았고, 앞으로도 그럴 가능성이 낮다.**

Hit Metering은 `Meter`라는 헤더를 추가한다. `Cache-Control` 헤더가 캐싱 지시자를 주고받게 해 주듯, `Meter` 헤더는 캐시와 서버가 사용량과 보고에 관한 지시자를 주고받게 한다.

**표 16-10. Hit Metering 지시자**

| 지시자 | 약어 | 주체 | 설명 |
|---|---|---|---|
| `will-report-and-limit` | `w` | 캐시 | 사용량을 보고할 수 있고 서버가 지정한 사용 한도를 지킬 수 있다 |
| `wont-report` | `x` | 캐시 | 사용 한도는 지킬 수 있으나 사용량을 보고하지 않겠다 |
| `wont-limit` | `y` | 캐시 | 사용량은 보고할 수 있으나 사용을 제한하지 않겠다 |
| `count` | `c` | 캐시 | 보고 지시자. `uses/reuses` 정수쌍으로 지정한다(예: `count=2/4`) |
| `max-uses` | `u` | 서버 | 응답이 캐시에 의해 사용될 수 있는 최대 횟수 |
| `max-reuses` | `r` | 서버 | 응답이 캐시에 의해 재사용될 수 있는 최대 횟수 |
| `do-report` | `d` | 서버 | 프록시가 사용량 보고를 보내도록 요구한다 |
| `dont-report` | `e` | 서버 | 사용량 보고를 원하지 않는다 |
| `timeout` | `t` | 서버 | 리소스 미터링의 타임아웃(분). 캐시는 그 시각 ±1분 안에 보고해야 한다 |
| `wont-ask` | `n` | 서버 | 어떤 미터링 정보도 원하지 않는다 |

여기서 **use**는 응답으로 요청을 충족시키는 것이고, **reuse**는 클라이언트 요청을 재검증하는 것이다.

동작 흐름은 다음과 같다.

```
[1] 클라이언트 → 프록시
    GET http://joes-hardware.com/ HTTP/1.1
    Host: www.joes-hardware.com
    Accept: *

[2] 프록시 → 원 서버        ← 프록시가 미터링 능력을 알린다
    GET / HTTP/1.1
    Host: www.joes-hardware.com
    Meter: will-report-and-limit
    Connection: Meter

[3] 원 서버 → 프록시        ← 서버가 보고를 요구한다
    HTTP/1.1 200 OK
    Date: Fri, 06 Dec 1996 18:44:29 GMT
    Content-length: 3152
    Content-type: text/html
    Connection: Meter
    ETag: "v1.27"
    Meter: do-report

[4] 프록시 → 클라이언트: 응답 전달, 캐시에 저장, 이후 요청을 캐시에서 처리
    (이 사이의 요청들은 원 서버 로그에 남지 않는다)

[5] 나중에, 프록시가 재검증하면서 히트 수를 함께 보고한다
    GET / HTTP/1.1
    Host: www.joes-hardware.com
    Meter: 12/4
    If-None-Match: "v1.27"
    Connection: Meter

[6] 원 서버 → 프록시
    HTTP/1.1 304 Not Modified
```

*그림 16-1. Hit Metering의 메시지 흐름 (HTTP-DG 그림 21-1 기준)*

클라이언트 관점에서 요청은 평범하게 완료된다. 프록시는 서버를 대신해 그 리소스에 대한 히트를 추적하기 시작하고, 나중에 서버와 재검증할 때 **조건부 요청에 미터링 정보를 실어 보낸다.** 별도의 보고 트랜잭션을 만들지 않고 이미 발생할 예정이던 재검증에 얹는다는 점이 이 설계의 요점이다.

`Connection: Meter`가 붙어 있다는 사실도 짚어 둘 값이 있다. `Meter`가 **홉 단위 헤더**임을 선언하는 것이며, 이것을 빠뜨리면 중간 프록시가 그것을 그대로 전달해 버린다(→ 9.2).

### 16.3.3 로그의 구멍이 보안에서 뜻하는 것

Hit Metering은 배포되지 않았으므로, 실무에서 **캐시가 로그에 뚫는 구멍은 지금도 그대로 있다.**

과금과 통계의 관점에서 이것은 정확도의 문제다. 보안의 관점에서는 다른 문제가 된다.

**공유 캐시 뒤에서 이루어진 접근은 원 서버의 로그에 존재하지 않는다.** 사건을 조사할 때 이것이 무엇을 뜻하는지 생각해 보면 문제가 분명해진다.

- 어떤 민감한 응답이 공유 캐시에 잘못 저장되어 다른 사용자에게 반복 제공되었다면(→ 14.8), **그 반복 제공은 원 서버 로그의 어디에도 없다.** 원 서버 로그에는 최초의 한 번만 있다.
- 캐시 뒤에서 수천 번 일어난 접근을 원 서버는 한 번으로 센다. 요청 빈도를 근거로 하는 이상 탐지(→ 16.5)는 그 트래픽을 보지 못한다.
- `TCP_REF_FAIL_HIT`처럼 "낡은 것을 반환했다"는 사건은 **캐시의 로그에만 있다.** 원 서버는 그 트랜잭션이 있었다는 사실 자체를 모른다.

즉 **경로 위에 로그를 남기는 주체가 여럿이고, 어느 하나도 전체를 보지 못한다.** 15.10절이 계층 아키텍처에서 지적한 것 — 감사 로그가 사건의 주체를 "신뢰받는 계층"으로만 기록한다 — 과 같은 구조가 여기서는 시간 축에 나타난다. 완전한 재구성을 하려면 원 서버, 프록시, 캐시의 로그를 시각으로 맞춰 합쳐야 하고, 그러려면 세 곳의 시계가 맞아야 하며, 세 곳 모두가 로그를 보존하고 있어야 한다.

47.11절이 이 문제를 마이크로서비스 환경에서 다시 다룬다. 그곳에서는 로그의 주체가 셋이 아니라 수십 개다.

> **이 절이 뒷받침하는 것**
>
> - 캐시는 원 서버의 로그에 구멍을 뚫으며, 그 구멍은 표준으로 메워지지 않았다 → **14.12** (히트 미터링의 동기를 캐시 쪽에서 다시 봄)
> - 로그를 남기는 주체가 여럿이고 아무도 전체를 보지 못한다 → **47.11** (집계 로그의 무결성과 추적성)

## 16.4 로그가 누출하는 것 — 프라이버시에 관한 한마디

로깅은 서버와 프록시가 수행하는 **관리 기능**이므로, 그 동작 전체가 사용자에게 투명하다. 사용자는 자기 HTTP 트랜잭션이 기록되고 있다는 사실을 인지하지 못하는 경우가 많다. 실제로 많은 사용자는 웹에서 콘텐츠를 볼 때 자기가 HTTP라는 프로토콜을 쓰고 있다는 것조차 모른다.

웹 애플리케이션 개발자와 관리자는 **사용자의 HTTP 트랜잭션을 추적한다는 것이 무엇을 뜻하는지** 알고 있어야 한다. 한 사람이 무엇을 가져갔는지를 근거로 그 사람에 대해 알아낼 수 있는 것은 대단히 많다. 그리고 그 정보는 나쁜 용도로 쓰일 수 있다. 차별, 괴롭힘, 협박이 그 예다. 로그를 남기는 웹 서버와 프록시는 최종 사용자의 프라이버시를 보호하는 데 각별해야 한다.

직장 환경처럼 사용자의 이용 내역을 추적하는 것이 적절한 상황도 있다. 그러나 그런 경우에도 관리자는 **사람들의 트랜잭션이 모니터링되고 있다는 사실을 공개해야 한다.**

HTTP-DG는 이 절을 한 문단으로 닫는다. 로깅은 관리자와 개발자에게 매우 유용한 도구이며, 다만 **로그가 대상자의 허가나 인지 없이 프라이버시를 침해할 수 있다는 사실을 알고 있으라**는 것이다. 이 책은 여기서 한 걸음 더 나간다. 무엇이 어떻게 로그에 들어가는지를 구체적으로 열거해 두지 않으면 그 경고는 실행 가능한 조언이 되지 못한다.

### 16.4.1 로그에 남는 것의 목록

앞의 두 절에서 본 포맷들이 실제로 무엇을 담는지를 위험 관점으로 다시 정리하면 다음과 같다.

**표 16-11. 로그에 남는 항목과 그것이 드러내는 것**

| 로그 항목 | 원래 목적 | 실제로 드러나는 것 |
|---|---|---|
| 요청 라인의 URL | 인기 페이지 추적 | 쿼리 문자열 전체. 검색어, 폼으로 보낸 값, `GET`으로 보낸 자격증명, 세션 토큰 |
| URL의 `userinfo` 성분 | (없음. URL 문법의 잔재) | 사용자명과 **비밀번호 평문**(→ 7.2) |
| `Referer` | 유입 경로 | 직전 페이지의 URL 전체. 사내 시스템 URL, 검색어, 토큰이 담긴 링크 |
| `auth-username` | 인증 감사 | 누가 언제 무엇을 봤는지의 직접 연결 |
| `remotehost` | 접근 분포 | 위치의 근사, 조직의 식별, 시간대별 활동 패턴 |
| `User-Agent` | 클라이언트 통계 | OS·브라우저·버전·설치된 확장 — 지문(→ 25.6) |
| `Cookie`(커스텀 필드) | 세션 단위 재구성 | **유효한 세션 토큰 그 자체**(→ 23.3) |
| 요청 본문(커스텀 필드) | 완전한 포렌식 | 로그인 폼의 비밀번호, 결제 정보, 개인정보 전량 |
| 접근 시각의 연속 | 성능 분석 | **한 사람의 하루 전체의 이동 경로** |

마지막 행이 이 절의 핵심이다. 개별 필드 하나하나는 무해해 보인다. 그러나 **같은 식별자를 축으로 시간순으로 정렬하는 순간** 그것은 한 사람이 언제 일어나 무엇을 읽고 무엇을 검색하고 언제 잠들었는지의 기록이 된다. 어떤 개별 필드도 그 사실을 담고 있지 않지만 집합은 담고 있다.

### 16.4.2 가장 흔한 사고 — `GET` 쿼리 문자열에 담긴 비밀

실제 사고에서 압도적으로 자주 나타나는 형태는 단순하다. **자격증명이나 토큰을 `GET` 요청의 쿼리 문자열로 보내는 것**이다.

```
GET /login.pl?login=andreas&password=Sup3rS3cret HTTP/1.1
Host: www.joes-hardware.com
```

이 한 줄이 만들어 내는 결과를 따라가 보자.

1. **원 서버의 접근 로그에 그대로 남는다.** CLF의 `request-line` 필드는 요청 라인의 정확한 텍스트다(표 16-2).
2. **경로 위의 모든 프록시 로그에 남는다.** Squid 포맷의 `url` 필드는 전체 URL이다(표 16-7).
3. **다음 페이지에서 나가는 요청의 `Referer` 헤더에 실려 제3자에게 전달된다.** 그 사이트의 로그에도 남는다.
4. **브라우저 히스토리에 남는다**(→ 36.2).
5. 그 URL이 어딘가에 링크되어 있었다면 **검색 엔진이 색인한다**(→ 16.11).

이 다섯 가지 중 어느 것도 애플리케이션 코드의 결함이 아니다. **모두가 명세대로 동작한 결과다.** 8.3.2절이 `GET`과 `POST`의 의미 차이가 만드는 보안 격차를 다뤘고, 여기가 그 격차가 가장 구체적으로 나타나는 자리다.

WAHH가 이 문제의 실물을 보여 준다. 공개 디렉터리에 놓인 애플리케이션 로그 파일에 다음과 같은 항목들이 들어 있었다.

```
[05/Mar/2007:19:35:22 +0100] "GET /lx-office-erp/menuv3.pl?login=andreas&password=...
[05/Mar/2007:19:35:23 +0100] "GET /lx-office-erp/login.pl?login=andreas&password=...
```

*예제 16-6. 보호되지 않은 애플리케이션 로그에 담긴 다른 사용자의 자격증명 (WAHH 그림 2-7 기준)*

이 로그 파일을 읽을 수 있는 사람은 애플리케이션의 모든 계정으로 로그인할 수 있다. 취약점은 인증에도, 세션 관리에도, 접근 통제에도 없었다. **로그에 있었다.**

### 16.4.3 캐시 프라이버시와의 대조

14.9절이 다룬 클라이언트 캐시 프라이버시와 이 절을 나란히 놓으면 두 문제의 관계가 분명해진다.

**표 16-12. 캐시가 남기는 것과 로그가 남기는 것**

| | 클라이언트 캐시(→ 14.9) | 서버·프록시 로그(이 절) |
|---|---|---|
| 남는 것 | **콘텐츠 본체** — 렌더된 페이지, 이미지, 응답 본문 | **메타데이터** — 누가, 언제, 무엇을 요청했는가 |
| 남는 곳 | 사용자의 기기, 공유 캐시 | 서버 운영자, 프록시 운영자의 디스크 |
| 통제 주체 | 콘텐츠 제공자가 `Cache-Control`로 부분 통제 | **사용자에게 통제 수단이 전혀 없음** |
| 사용자의 인지 | 브라우저 UI로 일부 확인 가능 | **전혀 보이지 않음** |
| 삭제 가능성 | 사용자가 캐시를 비울 수 있음 | 사용자가 관여할 수 없음 |
| 위험의 형태 | 기기를 획득한 자가 내용을 복원 | 로그 파일을 읽은 자가 모두의 행적을 획득 |

두 문제는 대칭적이지 않다. 캐시 프라이버시는 **한 사용자의 콘텐츠가 그 사용자의 기기에** 남는 문제이고, 로그 프라이버시는 **모든 사용자의 행적이 한 곳에** 모이는 문제다. 후자의 피해 규모가 구조적으로 훨씬 크다.

그리고 후자는 사용자가 아무것도 할 수 없다. `Cache-Control: no-store`는 캐시에게 저장하지 말라고 말할 수 있지만(→ 14.6), **로그에 남기지 말라고 말하는 헤더는 존재하지 않는다.** 로깅은 프로토콜의 관심사가 아니라 구현의 관심사이기 때문이다.

> **이 책의 범위를 넘어서**
>
> 로그에 담긴 개인 데이터의 수집·보관·삭제는 오늘날 여러 관할권에서 법적 의무의 대상이다. 유럽연합의 GDPR을 비롯한 개인정보 보호 법제가 보관 기간의 상한, 정보 주체의 열람·삭제 요구권, 국외 이전의 조건 등을 규정하며, 이는 "로그를 얼마나 오래, 어디에, 누가 볼 수 있게 두는가"라는 이 절의 질문에 직접적인 제약을 건다. 다만 개별 법규의 조문과 그 해석은 이 책이 근거로 삼는 다섯 권의 범위 밖이고, 관할권마다 다르며, 시간이 지나면 바뀐다. 이 책은 **어떤 데이터가 어떤 경로로 로그에 들어가는가**라는 기술적 사실만을 다루고, 그 데이터를 얼마나 오래 보관해도 되는가는 다루지 않는다. 다만 16.7절이 서술하는 중앙 집중 로깅이 이 종류의 요구 — 특정 인물에 관한 데이터를 전부 찾아내거나 전부 지우는 일 — 를 구조적으로 가능하게 만든다는 점만 지적해 둔다.

## 16.5 방어자의 로그 — 감사 로그, 경보, 공격 대응

앞 절이 로그의 위험을 다뤘다면 이 절은 로그가 왜 필요한지를 다룬다. 두 절은 같은 대상을 반대편에서 본 것이며, 둘을 함께 읽지 않으면 어느 쪽도 실행 가능한 결론이 되지 않는다.

### 16.5.1 감사 로그가 하는 일

**감사 로그(audit log)** 의 가치는 주로 애플리케이션에 대한 침입 시도를 조사할 때 나타난다. 사고가 일어난 뒤, 효과적인 감사 로그는 애플리케이션 소유자가 다음 네 가지를 파악할 수 있게 해야 한다.

1. **정확히 무슨 일이 일어났는가**
2. **어떤 취약점이 익스플로잇되었는가**(있다면)
3. **공격자가 데이터에 무단으로 접근했거나 무단 행위를 수행했는가**
4. **가능한 한, 침입자의 신원에 대한 증거**

보안이 중요한 애플리케이션이라면 핵심 이벤트는 당연히 기록되어야 한다. 최소한 다음이 포함된다.

- **인증 기능과 관련된 모든 이벤트** — 로그인 성공과 실패, 비밀번호 변경
- **핵심 트랜잭션** — 카드 결제, 자금 이체
- **접근 통제 메커니즘에 의해 차단된 접근 시도**
- **알려진 공격 문자열을 담고 있어 명백히 악의적 의도를 드러내는 요청**

온라인 은행처럼 보안이 결정적인 애플리케이션에서는 **모든 클라이언트 요청을 전부 기록**해서 어떤 사고든 조사할 수 있는 완전한 포렌식 기록을 남기기도 한다.

효과적인 감사 로그는 보통 각 이벤트의 시각, 요청이 도착한 IP 주소, 그리고 (인증된 경우) 사용자의 계정을 기록한다. 앞 절의 표 16-11과 나란히 놓고 보면, **이 세 항목이 정확히 프라이버시 위험이 가장 큰 세 항목**임을 알 수 있다. 이것이 이 장의 중심 긴장이다.

### 16.5.2 감사 로그 자체를 보호하기

그래서 감사 로그는 **무단 읽기와 무단 쓰기 양쪽으로부터 강하게 보호되어야 한다.**

효과적인 접근법 하나는 감사 로그를 **자율적인(autonomous) 시스템에 저장하고, 그 시스템이 메인 애플리케이션으로부터 갱신 메시지만 받도록** 하는 것이다. 상황에 따라서는 성공적인 공격이 일어났을 때에도 무결성을 보장하기 위해 **한 번만 쓸 수 있는 매체(write-once media)** 로 로그를 내보내기도 한다.

이 두 처방의 구조를 보라. 첫째는 **로그를 애플리케이션과 다른 신뢰 경계에 두는 것**이고, 둘째는 **쓰기만 가능하고 되돌릴 수 없게 만드는 것**이다. 16.7절이 클라우드 환경에서 같은 두 원칙을 다시 제시한다.

공격 표면의 관점에서, **부실하게 보호된 감사 로그는 공격자에게 금광이다.** 세션 토큰과 요청 파라미터를 비롯한 온갖 민감 정보가 그 안에 있다. 그 정보만으로 애플리케이션 전체를 즉시 장악할 수 있다 — 앞 절의 예제 16-6이 바로 그 사례다.

### 16.5.3 관리자에게 경보하기

감사 로그는 사후에 침입 시도를 조사하고, 가능하면 가해자에 대해 법적 조치를 취할 수 있게 해 준다. 그러나 많은 경우 **실시간으로 훨씬 즉각적인 조치를 취하는 것**이 바람직하다. 관리자가 공격자가 쓰는 IP 주소나 사용자 계정을 차단할 수 있고, 극단적인 경우 조사와 조치를 하는 동안 애플리케이션을 내릴 수도 있다. 이미 침입이 성공했더라도 초기 단계에서 방어 조치를 취하면 실질적 피해를 줄일 수 있다.

경보 메커니즘은 대개 상충하는 두 목표 사이에서 균형을 잡아야 한다. **진짜 공격을 빠짐없이 보고하는 것**과 **경보가 너무 많아져 무시당하는 지경에 이르지 않는 것**이다. 잘 설계된 경보 메커니즘은 여러 요소를 조합해 "지금 작정한 공격이 진행 중"임을 진단하고, 가능하면 관련된 이벤트들을 하나의 경보로 묶는다.

경보가 감시하는 이상 징후는 대체로 다음과 같다.

- **사용 이상** — 단일 IP나 사용자로부터 대량의 요청이 들어오는 경우. 스크립트 기반 공격을 시사한다
- **비즈니스 이상** — 하나의 은행 계좌를 오가는 자금 이체 건수가 비정상적인 경우
- **알려진 공격 문자열을 담은 요청**
- **일반 사용자에게 감춰져 있는 데이터가 수정된 요청**

### 16.5.4 범용 제품의 한계와 통합된 경보

이 기능들 중 일부는 기성 애플리케이션 방화벽과 침입 탐지 제품이 상당히 잘 수행한다. 이들은 대개 시그니처 기반 규칙과 이상 기반 규칙을 섞어 악의적 사용을 식별하고, 경보를 발행할 뿐 아니라 악의적 요청을 반응적으로 차단하기도 한다. 특히 문제가 있다고 알려졌지만 당장 고칠 자원이 없는 기존 애플리케이션을 보호할 때 이런 제품은 가치 있는 방어 층이 된다.

그러나 그 효과에는 근본적인 한계가 있다. **웹 애플리케이션은 저마다 다르고, 따라서 그 규칙은 필연적으로 어느 정도 일반적일 수밖에 없다.** 12.11절이 WAF의 역할과 한계를 다룰 때 지적한 것과 같은 구조다.

웹 애플리케이션 방화벽은 공격자가 각 요청 파라미터에 표준적인 공격 문자열을 넣는 가장 뻔한 공격을 식별하는 데는 대체로 능하다. 그러나 많은 공격은 그보다 미묘하다. 히든 필드의 계정 번호를 바꿔 다른 사용자의 데이터에 접근하거나(→ 26.1), 애플리케이션 로직의 결함을 노려 요청을 순서에 어긋나게 제출하는 경우(→ 29장)를 생각해 보라. **이때 공격자가 보낸 요청은 정상 사용자가 보낸 요청과 문자 그대로 동일하다. 그것을 악의적으로 만드는 것은 그 요청이 이루어진 정황이다.**

그래서 보안이 결정적인 애플리케이션에서 실시간 경보를 구현하는 가장 효과적인 방법은 **애플리케이션 자신의 입력 검증 메커니즘과 여타 통제에 그것을 긴밀히 통합하는 것**이다.

예를 들어 쿠키가 특정한 값 집합 중 하나를 갖도록 되어 있다면, 그것을 위반하는 값은 **일반 사용자로서는 만들어 낼 수 없는 방식으로 값이 수정되었음**을 뜻한다. 히든 필드의 계정 번호가 다른 사용자의 계정을 가리키도록 바뀌었다면 그것은 강한 악의의 신호다. 애플리케이션은 이미 일차 방어의 일부로 이런 것들을 검사하고 있어야 하며, 그 보호 메커니즘이 경보 메커니즘에 연결되기만 하면 **완전히 맞춤화된 악성 활동 지표**가 만들어진다. 애플리케이션의 실제 로직에 맞춰 조율되어 있고 일반 사용자가 어떻게 행동해야 하는지를 세밀하게 알고 있으므로, 어떤 기성 솔루션보다도 오탐이 적다.

이 논증의 구조를 기억해 두자. **검증이 이미 하고 있는 판단을 경보가 재사용한다.** 43.4절의 검증 순서와 43.5절의 경계 검증이 설계 언어로 이것을 다시 다루고, 22.8절과 23.6절이 인증·세션 영역에서 같은 원칙을 반복한다.

### 16.5.5 공격에 반응하기

관리자에게 경보하는 것에 더해, 보안이 결정적인 많은 애플리케이션은 악의적일 가능성이 있다고 판단된 사용자에게 **방어적으로 반응하는 내장 메커니즘**을 갖는다.

애플리케이션은 저마다 다르므로 실제 공격은 대개 공격자가 **체계적으로 취약점을 탐색하는 과정**을 요구한다. 흔한 취약점들의 존재를 드러내도록 조작된 입력을 담은 요청을 다수 보내는 것이다. 효과적인 입력 검증 메커니즘은 이 요청들 중 상당수를 악의적일 수 있는 것으로 식별하고 그 입력이 애플리케이션에 영향을 주지 못하게 차단한다. 그러나 **그 필터에 우회로가 존재하고 애플리케이션에 발견되기를 기다리는 실제 취약점이 있다고 가정하는 것이 합리적이다.** 체계적으로 작업하는 공격자는 어느 시점엔가 그 결함을 발견한다.

그래서 일부 애플리케이션은 이런 방식으로 작업하는 공격자를 방해하는 자동 반응 조치를 취한다. 공격자의 요청에 **점점 더 느리게 응답하거나**, 공격자의 **세션을 종료해서** 계속하기 전에 다시 로그인하거나 다른 단계를 거치도록 만드는 것이다.

이 조치들이 가장 인내심 있고 결연한 공격자를 물리치지는 못한다. 그러나 **더 가벼운 마음으로 시도하는 다수를 단념시키고, 관리자가 상황을 관찰하고 필요하면 더 강한 조치를 취할 시간을 벌어 준다.**

명백한 단서를 붙여 둬야 한다. **공격자로 보이는 자에게 반응하는 것은 애플리케이션에 존재하는 취약점을 고치는 일의 대체재가 아니다.** 그러나 현실에서는 아무리 성실하게 결함을 제거해도 익스플로잇 가능한 결함이 일부 남는다. 공격자의 길에 장애물을 하나 더 놓는 것은 잔여 취약점이 발견되고 익스플로잇될 가능성을 낮추는 효과적인 심층 방어 조치다.

### 16.5.6 긴장을 정면으로 놓기

이제 16.4절과 이 절을 나란히 놓아야 한다.

16.5.1절은 **가능한 한 많이 기록하라**고 말했다. 온라인 은행은 모든 요청을 전부 기록한다. 16.4절은 **기록된 것 하나하나가 누출 시 피해가 된다**고 말했다. 두 문장은 같은 시스템에 대한 요구다.

이 긴장은 해소되지 않는다. 다만 **세 개의 축으로 분해할 수는 있다.**

**표 16-13. 로그의 이중성을 다루는 세 축**

| 축 | 질문 | 처방의 방향 | 이 책의 어디 |
|---|---|---|---|
| **무엇을** | 이 필드가 사건 재구성에 실제로 기여하는가 | 기여하지 않는 민감 필드는 넣지 않는다. 필요한 것은 식별자로 대체한다(토큰 자체가 아니라 토큰의 해시, 카드 번호가 아니라 마지막 네 자리) | 16.6, 23.3 |
| **어떻게** | 이 값이 로그 파일의 **구조**를 바꿀 수 있는가 | 검증되지 않은 문자열을 그대로 넣지 않는다. 도메인 프리미티브로 받고 명시적 접근자로 꺼낸다 | 16.6, 44.5 |
| **어디에** | 이 로그를 읽을 수 있는 자가 누구인가, 그리고 그것을 통제할 수 있는가 | 파일이 아니라 서비스에 쓴다. 카테고리를 나누고 읽기·쓰기를 분리한다 | 16.7, 46.4 |

첫 번째 축이 가장 값싸고 가장 자주 무시된다. **"혹시 필요할지 모르니 전부 기록한다"는 태도가 사고의 규모를 결정한다.** 요청 본문을 통째로 기록하는 결정 하나가, 그 로그가 유출되는 날 유출되는 것의 목록을 결정한다.

두 번째와 세 번째 축은 각각 16.6절과 16.7절의 주제다.

> **이 절이 뒷받침하는 것**
>
> - 감사 로그는 인증·핵심 트랜잭션·차단된 접근·공격 문자열을 기록해야 한다 → **22.8**, **23.6** (인증과 세션 영역에서의 구체적 목록)
> - 실시간 경보는 입력 검증과 통합될 때 가장 정확하다 → **43.5** (경계 검증이 그 판단을 어디에서 하는지)
> - 로그는 무단 읽기와 무단 쓰기 양쪽에서 보호되어야 한다 → **16.7**, **46.4** (그 보호를 구조로 얻는 방법)

## 16.6 로그에 검증되지 않은 문자열을 넣지 말라 — 로그 인젝션과 암묵적 데이터 누출

앞 절의 표 16-13에서 두 번째 축을 다룬다. **로그에 무엇을 어떻게 넣는가.**

이 절의 논지는 한 문장으로 요약된다. **검증되지 않은 문자열을 절대 로그에 쓰지 말라.** 여기서 문제는 문자열을 로그에 쓰는 것 자체가 아니다. 대부분의 로깅 프레임워크는 문자열만 받으므로 문자열을 피하는 것은 선택지가 아니다. 문제는 **검증되지 않은** 문자열이다. 이 둘 사이에는 큰 차이가 있고, 검증되지 않은 문자열은 사실 수많은 공격 벡터의 근원이다.

이 실수는 경력과 무관하게 반복해서 나타난다. 눈에 훤히 보이는 곳에 숨어 있기 때문이다.

### 16.6.1 문제의 형태

무엇을 찾아야 하는지 알아야 한다. 찾아야 할 것은 **검증되지 않은 `String` 객체를 로깅하는 코드** — 예컨대 사용자 입력이나 다른 시스템에서 온 데이터를 로깅하는 코드 — 다.

온라인 서점의 주문 조회 기능을 예로 든다. 주문 ID로 주문을 가져오는 서비스 메서드다.

```java
public Order fetch(final String orderId) {
    logger.info("Fetching order: " + orderId);   // ← 검증되지 않은 주문 ID를 로깅

    // 주문 조회 로직

    return order;
}
```

*예제 16-7. 검증되지 않은 입력을 로깅하는 코드 (SBD 리스트 12.6의 구조를 온라인 서점으로 옮긴 것)*

주문 ID를 왜 로깅하는지는 중요하지 않다. 중요한 것은 **입력 인자가 검사되지 않은 채 로깅된다는 사실**이다.

주문 ID에는 엄격한 도메인 규칙이 있다고 하자. 예컨대 `#` 기호로 시작하고 일곱 자리 숫자가 뒤따라야 한다. 그런데 개발자는 그것을 `String`으로 표현하기로 했다. 그 결과 **유효한 주문 ID가 들어올 것이라고 기대하지만, 공격자는 `String` 객체의 규칙에만 맞으면 무엇이든 넣을 수 있다.** 그리고 `String`의 규칙에 맞는 것은 문자 그대로 무엇이든이다. 1억 자짜리 문자열도, 스크립트도.

### 16.6.2 (a) 로그 인젝션

첫 번째 결과는 **로그 인젝션**이다.

16.2절에서 로그 포맷의 성질을 짚어 뒀다. **CLF와 그 파생 포맷은 줄 단위이고, 필드는 공백으로 구분되며, 일부 필드는 큰따옴표로 감싼다.** 즉 구분자는 개행·공백·큰따옴표다.

공격자가 개행 문자를 담은 값을 보내면 로그 파일에 **없었던 줄이 생긴다.**

```
GET /orders?id=%23000123%0a209.1.32.44%20-%20admin%20[03/Oct/1999:14:20:00%20-0400]%20
"POST%20/admin/grant%20HTTP/1.0"%20200%201024 HTTP/1.1
```

이 요청이 CLF로 기록되면 로그 파일에는 실제로 일어나지 않은 관리자 트랜잭션 한 줄이 정상적인 형태로 추가된다. 조사자가 그 줄을 읽으면 사건의 재구성이 통째로 틀어진다.

이 구조는 이 책이 이미 두 번 다룬 것과 정확히 같다.

- **응답 분할**(→ 8.7): CR/LF가 HTTP 메시지의 구조를 결정하므로, 헤더 값에 들어간 CR/LF가 메시지 하나를 둘로 나눈다.
- **본문 경계 혼동**(→ 10.4): 본문의 끝을 정하는 것이 데이터 안의 값이므로, 그 값을 조작하면 경계가 이동한다.

**구분자가 데이터와 같은 채널에 있으면, 데이터를 통제하는 자가 구조를 통제한다.** 로그 파일에서 이 명제가 다시 성립한다.

두 번째 형태는 **2차 인젝션(second-order injection)** 이다. 로그를 파싱하는 도구에 약점이 있다면, 공격자는 주문 ID인 척하는 악의적 문자열을 주입해 그것이 로그에 기록되게 만들고, 나중에 그 도구가 로그를 읽을 때 익스플로잇할 수 있다.

이 경로는 실무에서 특히 위험하다. 이유는 **로그 뷰어가 대개 웹 애플리케이션이기 때문**이다. 로그 항목을 HTML로 렌더하는 관리 콘솔이 있고, 그 콘솔이 로그의 내용을 이스케이프하지 않고 출력한다면, 공격자가 로그에 심어 둔 스크립트가 **관리자의 브라우저에서, 관리자의 세션으로** 실행된다. 저장형 XSS의 저장소가 데이터베이스가 아니라 로그 파일인 형태다(→ 32.6). 그리고 그 대상은 정의상 높은 권한을 가진 사용자다 — WAHH가 관리 인터페이스의 XSS에 대해 지적한 것과 같은 구조다.

> **경고**
>
> 검증되지 않은 사용자 입력을 절대 로깅하지 말라. 2차 인젝션 공격의 위험을 연다.

### 16.6.3 (b) 암묵적 데이터 누출

두 번째 결과는 더 조용하고 더 찾기 어렵다.

앞의 예제를 조금 확장한다. 저장소에서 주문 객체를 가져와서 그 내용을 로깅하는 코드다.

```java
public Order fetch(final String orderId) {
    logger.info("Fetching order: " + orderId);

    final Order order = repository.order(orderId);

    logger.info("Received " + order);   // ← Order 객체가 암묵적으로 문자열이 된다

    return order;
}
```

*예제 16-8. 도메인 객체를 문자열로 직렬화해 로깅하는 코드 (SBD 리스트 12.7의 구조를 온라인 서점으로 옮긴 것)*

주문을 로깅하는 것은 무해해 보인다. `Order`가 담고 있는 것이 주문 번호, 도서 ID, 수량, 주문 시각 정도라면 실제로 무해하다.

**그런데 도메인 모델이 진화하면 어떻게 되는가.**

누군가가 더 나은 서비스를 위해 주문에 회원 정보를 포함시키기로 결정한다고 하자. 그 순간 `Order` 객체는 갑자기 이름, 연락처, 배송 주소, 회원 번호를 담게 된다. 그리고 그것들이 **이 로그 문장을 통해 암묵적으로 새어 나간다.**

이 사고의 성질을 정확히 보라.

- **로깅 코드는 한 글자도 바뀌지 않았다.** 누구도 "회원 정보를 로그에 남기자"고 결정하지 않았다.
- **변경을 한 사람은 로그를 보지 않았다.** 그는 도메인 모델을 개선했을 뿐이다.
- **코드 리뷰에서 발견되지 않는다.** 리뷰 대상 diff에는 로깅 코드가 없다.

큰 시스템에서 데이터가 어떻게 소비되는지를 전부 추적하는 것은 사실상 불가능하다. 그래서 이 사고를 **예방**하는 것은 어렵다.

여기에 더해 문법 수준의 함정이 하나 더 있다. `logger.info("Received " + order)`에서 문자열 `"Received "`와 `order` 객체를 `+` 연산자로 이어 붙이는 것은 `order`의 `toString` 메서드를 **암묵적으로 호출**하는 일이다.

`toString`을 재정의하지 않았다면 이 연산은 대체로 무해하다. 클래스 이름과 해시 코드의 16진 표현이 나올 뿐이다. 그러나 **`toString`은 객체 내용을 디버깅하는 손쉬운 방법이므로 자주 재정의된다.** 그리고 필드가 추가되거나 수정될 때마다 `toString`을 갱신하는 수고를 피하려고 **리플렉션으로 모든 데이터를 동적으로 추출하도록 구현하는 경우가 많다.** 그러면 민감 데이터가 `toString` 구현을 통해 암묵적으로 누출된다.

### 16.6.4 세 가지 처방

**첫째, 도메인 프리미티브로 받는다.**

`String` 대신 도메인 프리미티브를 쓰면 **입력의 통제권이 공격자가 아니라 이쪽으로 넘어온다.** `OrderId` 타입이 생성 시점에 `#` + 일곱 자리 숫자라는 불변식을 강제한다면, 그 타입의 인스턴스가 존재한다는 사실 자체가 그 값이 안전하다는 증명이다. 개행도, 1억 자짜리 문자열도, 스크립트도 그 타입의 값이 될 수 없다.

```java
public Order fetch(final OrderId orderId) {
    logger.info("Fetching order: " + orderId);   // OrderId는 불변식을 통과한 값이다
    ...
}
```

*예제 16-9. 도메인 프리미티브로 받은 값을 로깅하는 코드*

이것이 44.1절과 44.3절의 주제이며, 레거시 코드에서 이 전환을 실제로 수행하는 방법이 47.2절과 47.3절이다. 여기서 중요한 것은 **로그 안전성이 로깅 코드의 문제가 아니라 타입의 문제라는 점**이다.

**둘째, `toString`에 의존하지 않고 명시적 접근자를 쓴다.**

로그에 담고 싶은 데이터는 명시적 접근자 메서드로 꺼내야 한다. 그래야 **새 필드가 실수로 로그에 들어가는 일이 절대 생기지 않는다.**

```java
logger.info("Received order " + order.id() + " with " + order.itemCount() + " items");
```

*예제 16-10. 명시적 접근자로 꺼낸 값만 로깅하는 코드*

이제 `Order`에 어떤 필드가 추가되어도 이 로그 문장의 출력은 바뀌지 않는다. **누출의 가능성이 코드 변경 없이 늘어나는 경로가 닫힌다.**

**셋째, 민감한 값은 읽기 1회 객체로 모델링해서 탐지한다.**

암묵적 데이터 누출을 **예방**하는 것은 어렵지만 **탐지**하는 것은 그렇게 어렵지 않다. 읽기 1회 객체(read-once object) 패턴은 어떤 값이 몇 번까지 읽힐 수 있는지를 정하고, 그 한도를 넘으면 계약 위반이 발생하게 한다.

시스템에서 민감한 데이터를 식별하고 그것을 그런 타입으로 모델링해 두기만 하면, **의도하지 않은 로그 연산처럼 허용한 것보다 자주 읽히는 상황이 자동으로 드러난다.** 회원 정보가 `Order`에 추가되고 그것이 로그 문장에서 두 번째로 읽히는 순간, 시스템이 그것을 알려 준다.

44.5절이 이 패턴을 온전히 다룬다. 22.9절이 비밀을 코드에서 다루는 문제로 같은 패턴을 인용한다.

> **처방**
>
> - 민감한 값이 코드 안에서 접근될 수 있는 횟수를 항상 제한하라. 그래야 의도하지 않은 접근을 탐지할 수 있다.
> - 로그에 담고 싶은 데이터는 항상 명시적 접근자 메서드로 꺼내라. 그러지 않으면 새 필드가 실수로 로그에 들어간다.

### 16.6.5 두 문제의 대비

**표 16-14. 로그 인젝션과 암묵적 데이터 누출**

| | 로그 인젝션 | 암묵적 데이터 누출 |
|---|---|---|
| 원인 | 검증되지 않은 **외부 입력**이 로그에 들어감 | **내부 도메인 객체**가 통째로 문자열화되어 로그에 들어감 |
| 통제 주체 | 공격자 | 아무도 아님(코드 진화의 부작용) |
| 시점 | 요청 시점 | **모델 변경 시점 — 로깅 코드는 그대로** |
| 발현 | 위조된 로그 줄, 로그 파서·뷰어 익스플로잇 | 민감 정보가 조용히 로그에 축적됨 |
| 탐지 | 로그의 이상한 줄, 파서 오류 | **거의 불가능** — 그래서 읽기 1회 객체로 탐지 장치를 심어 둔다 |
| 처방 | 도메인 프리미티브로 입력을 통제 | 명시적 접근자 + 읽기 1회 객체 |
| 이어받는 곳 | **47.3**, **45.6** | **44.5**, **47.3**, **47.9** |

두 문제 모두 근본 원인이 같다는 점이 중요하다. **`String`은 아무런 의미도 담고 있지 않은 타입이며, 그래서 무엇이든 담을 수 있다.** 로그는 그 무엇이든을 그대로 받아 적는다.

> **이 절이 뒷받침하는 것**
>
> - 검증되지 않은 문자열이 로그 파일의 구조를 바꾼다 → **8.7** (같은 원리가 HTTP 헤더에서 나타나는 형태), **45.6** (잘못된 데이터를 다루는 원칙)
> - 도메인 프리미티브가 로그 인젝션의 입력 경로를 닫는다 → **44.1**, **44.3**, **47.3**
> - 읽기 1회 객체가 암묵적 누출을 탐지 가능하게 만든다 → **44.5**, **22.9**

## 16.7 파일 로깅을 피하라 — 서비스로서의 로깅

표 16-13의 세 번째 축이다. **로그를 어디에 둘 것인가.**

로깅은 대부분의 애플리케이션에서 근본적인 부분이다. 무언가가 왜 일어났는지를 이해하는 데 도움을 주기 때문이다. 로그에는 사용자 상호작용부터 디버그 정보, 감사 데이터까지 온갖 것이 들어간다. 대부분의 사람이 지루하고 무의미하다고 여기는 정보이지만, **보안의 관점에서 그것은 엘도라도다.** 로그 데이터에는 민감한 데이터와 시스템을 익스플로잇할 때 유용한 기술적 세부 정보가 들어 있기 때문이다.

여기서 앞서 나온 모순이 다시, 이번에는 배치의 문제로 나타난다.

> **보안의 관점에서 로그는 잠가 두고 아무도 들여다보지 않아야 한다. 그러나 실무에서 로그는 완전히 반대로 소비된다.**

예상치 못한 동작이나 버그를 분석할 때 로그는 일차 정보원이다. 즉 **로그는 항상 접근 가능해야 하고, 동시에 그 안의 데이터는 민감하므로 잠겨 있어야 한다.** 말 그대로 모순처럼 보인다.

그러나 강한 보안과 높은 접근성이 상호 배타적인 것은 아니다. 클라우드 네이티브 애플리케이션이 이 이분법을 다루는 설계 패턴이 있다. **서비스로서의 로깅(logging as a service)** 이다.

이 절은 그 패턴을 상세히 다루지 않는다. 그것은 46.4절의 몫이다. 여기서는 **왜 파일이 잘못된 자리인가**만을 다룬다.

### 16.7.1 디스크 파일에 로깅할 때 — CIA 관점

**기밀성.** 디스크 파일에 로깅하는 이유는 여러 가지다. 하나는 코드 복잡도가 낮다는 것이다. 표준 출력 스트림이나 익숙한 로깅 프레임워크로 구현할 수 있다. 다른 하나는 개발이나 장애 조사 중 접근이 쉽다는 것이다. 서버에 원격 로그인해서 로그를 볼 수 있다.

**첫 번째 이유는 실제로 보안에 유리하다.** 복잡도가 낮은 것은 언제나 좋다. 문제는 두 번째다. 로그를 손쉽게 가져갈 수 있게 하는 것이 높은 접근성의 열쇠이지만, 동시에 기밀성의 문제를 만든다.

trace나 debug 레벨을 켜면 방대한 데이터를 로깅하도록 만들어 둔 경우가 많다. 장애 조사에는 확실히 도움이 된다. 그러나 **그렇게 기록된 정보는 민감할 수 있고 누군가를 식별하는 데 쓰일 수 있다.** 정치적 성향, 지리적 위치, 재정 상태 같은 것이 드러날 수 있다. 감사 추적을 구현하고 로그 데이터에 대한 접근을 제한하는 것은 필수이지만, **디스크 위의 파일에 그 절차를 적용하는 것은 어렵거나 불가능하다.**

같은 맥락의 또 다른 문제는 불법 접근의 차단이다. 로그 데이터를 디스크에 저장하고 원격 로그인으로 접근하게 하면 로그 접근이 IAM 문제가 된다. 처음에는 좋은 전략처럼 들린다. 인가 역할을 적용하고 전반적인 접근을 제한할 수 있으니까. **그러나 이 전략은 아무도 파일을 다운로드할 수 없는 동안만 유효하다.** 로그를 내려받을 수 있게 되는 순간 접근 권한을 유지하는 것은 극히 어려워지고, IAM의 목적 자체가 무의미해진다.

**무결성.** 로그 파일의 무결성을 유지하는 것은 대단히 중요하지만, 로깅 전략을 논할 때 자주 잊힌다. 로그가 주로 개발이나 장애 조사에만 쓰인다고 생각하면 로그 데이터의 수정을 막는 것이 우선순위가 되지 않는다. 애초에 로그 데이터를 왜 수정하겠는가? 로그에 무엇을 쓰든 시스템은 똑같이 동작하는데.

**그러나 로그를 증거나 증명으로 본다면 무결성이 갑자기 중요해진다.** 어떤 거래가 이루어졌다고 주장하는 법정에서 로그가 쓰인다면, 그 로그가 조작되지 않았음을 확신할 수 있어야 한다. 파일에 로깅할 때 이것이 문제가 된다. 원격 접근을 허용한다면 **애플리케이션 외에 아무도 로그 파일에 쓸 수 없도록 보장해야 한다.** 그러지 않으면 로그 무결성을 증명해야 하는 날 곤란한 상황에 처한다.

16.5.2절이 감사 로그를 자율 시스템에 두고 갱신 메시지만 받게 하라고 한 것, 그리고 write-once 매체를 언급한 것이 바로 이 요구에 대한 답이었다.

**가용성.** 파일에 로깅할 때 로그 데이터의 가용성을 보장하는 것은 쉬워 보이지만 실제로는 여러 문제가 숨어 있다.

디스크에 데이터를 저장하는 것은 편리하지만 **상태(state)의 문제**를 들여온다. 서버를 폐기하고 새 인스턴스로 교체할 때 로그를 보존해서 새 서버로 옮기는 절차가 필요하다. 그러지 않으면 결정적인 로그 데이터가 사라지고 **트랜잭션 타임라인에 공백이 생긴다.** 로그에 감사 데이터가 들어 있다면 이것은 심각한 문제다.

더 미묘한 문제는 디스크 크기의 한계다. 파일에 로깅할 때는 로그 파일이 너무 커지지 않도록 해야 한다. 그러지 않으면 디스크가 가득 찬다. 그리고 고전적인 딜레마가 있다. **애플리케이션의 로깅 프로세스가 디스크 공간 부족으로 죽었는데, 그 사실을 로그에 기록하려 해도 공간이 없어서 기록하지 못하는 상황이다.**

흔한 완화책은 관리 프로세스가 로그를 자동으로 로테이션하게 하는 것이다. `syslog`라는 로그 파일이 일정 크기나 나이에 도달하면 로테이션 프로세스가 그것을 `syslog.1`로 이름을 바꾸고 새 `syslog`를 만든다. 그러면 `syslog.1`을 현재 로그 파일에 영향을 주지 않고 옮기고 저장하고 분석할 수 있다. 간단해 보이지만 **흔한 함정은 로테이션된 로그가 옮겨지지 않아서 결국 디스크를 채워 버리는 것**이다.

### 16.7.2 서비스로서의 로깅이 바꾸는 것

클라우드에서 애플리케이션을 실행할 때는 로컬 서버 디스크 같은 외부 인프라에 의존할 수 없다. 서버 인스턴스가 언제든 교체될 수 있기 때문이다. 이것이 파일 로깅을 구조적으로 문제 있게 만든다.

**코드 관점에서 서비스에 로깅하는 것은 파일에 로깅하는 것과 크게 다르지 않다.** 익숙한 로깅 프레임워크를 그대로 쓰되, 로컬 디스크에 쓰는 대신 데이터가 네트워크로 나간다.

```java
public void cancel(final OrderId orderId) {
    notNull(orderId);

    orderRepository.cancel(orderId);
    loggingService.log(new OrderCancelled(orderId, Type.AUDIT));
}
```

*예제 16-11. 로그 호출이 네트워크 너머의 로깅 서비스로 나간다 (SBD 그림 10.3의 코드를 온라인 서점으로 옮긴 것)*

이 한 줄에 담긴 두 가지 결정을 보라. 첫째, 로깅되는 것은 문자열이 아니라 **도메인 이벤트 객체**다(16.6절). 둘째, 그 이벤트에 **카테고리(`Type.AUDIT`)** 가 붙어 있다.

**표 16-15. 파일 로깅과 서비스 로깅의 CIA 비교**

| | 디스크 파일 | 로깅 서비스 |
|---|---|---|
| **기밀성** | 특정 데이터에 대한 접근 제한이 어렵다. 파일을 내려받으면 IAM이 무력화된다 | 로그를 카테고리(Audit·System·Error)로 나누고 카테고리별로 접근을 제한할 수 있다 |
| 감사 추적 | 누가 언제 어떤 데이터를 봤는지 추적하기 어렵다 | 로그 데이터에 접근할 때마다 시스템이 그 행위를 기록하고 부적절한 접근에 경보한다 |
| **무결성** | 원격 접근을 허용하면 애플리케이션 외의 쓰기를 막아야 한다 | **읽기와 쓰기를 분리**한다. 애플리케이션만 쓰기 권한을 갖고 나머지는 읽기 전용. append-only로 두면 갱신·삭제·덮어쓰기가 원천 차단된다 |
| 집계 | 인스턴스마다 로그가 흩어진다. 수동 집계 과정이 수정을 허용하면 무결성 문제가 생긴다 | 설계상 추가하고 집계한다 |
| **가용성** | 상태를 가진 디스크. 서버 교체 시 로그 소실, 디스크 크기 한계, 로테이션의 함정 | 필요에 따라 저장 용량을 조정할 수 있다 |
| 실패 시 | 디스크 실패 처리 전략을 따른다 | **같은 전략을 따른다.** 롤백이 디스크 실패 처리 방식이면 로깅 서비스 접근 실패도 롤백으로 다룬다. 네트워크가 디스크보다 덜 신뢰할 만하고 데이터 손실 위험이 수용 가능하면 로컬 메모리에 버퍼링한다 |
| 데이터의 소재 | 수백 대의 서버에 흩어져 있고 일부는 이미 폐기되었다 | **모든 로그 데이터가 어디 있는지 암묵적으로 안다** |

마지막 행이 실무에서 자주 과소평가된다. 특정 인물에 관해 저장한 데이터를 전부 찾아내거나 전부 제거해야 하는 상황, 혹은 고급 분석 알고리즘을 돌려야 하는 상황에서 **로그 데이터가 전부 어디 있는지 아는 것은 대단히 값지다.**

### 16.7.3 신뢰 경계가 옮겨 간다

마지막으로 파일 기반과 서비스 기반 로깅 사이의 중요한 차이 하나를 남겨 둔다.

디스크에 로깅할 때는 **디스크가 애플리케이션과 같은 신뢰 경계 안에 있다고 볼 수 있다.** 그렇다면 전송 중(애플리케이션에서 디스크까지) 데이터를 보호할 걱정을 하지 않아도 된다.

그러나 로깅 서비스를 쓰면 데이터가 네트워크로 나간다. **로그 트래픽을 도청할 가능성이 열린다.** 서비스 기반 로깅은 전송 중 데이터 보호를 요구하며, 그것은 대개 TLS나 종단 간 암호화로 이루어진다.

이 문장을 이 책의 논지에 비추어 읽어야 한다. **서비스로서의 로깅은 문제를 없앤 것이 아니라 신뢰 경계를 하나 추가한 것이다.** 그 대가로 기밀성·무결성·가용성 세 축 모두에서 구조적 이점을 얻었지만, 대신 Part IV 전체가 다루는 문제 — 네트워크 위의 데이터를 어떻게 보호할 것인가 — 를 로깅 경로에 들여왔다. 47.10절이 이것을 마이크로서비스 환경에서 일반화한다. 서비스 사이의 호출은 함수 호출이 아니라 네트워크 요청이며, **Part I~IV가 다룬 모든 문제가 조직 내부망에서 다시 나타난다.**

46.4절이 이 패턴의 상세를, 47.11절이 마이크로서비스 환경에서의 집계 로그 무결성과 도메인 지향 로거 API를 다룬다.

> **이 절이 뒷받침하는 것**
>
> - 로그는 항상 접근 가능해야 하고 동시에 잠겨 있어야 한다 → **46.4** (그 모순을 배치로 해소하는 방법)
> - 로그를 카테고리로 나누고 읽기·쓰기를 분리한다 → **47.11** (도메인 지향 로거 API로 기밀성을 확보하기)
> - 로깅 경로가 네트워크가 되면 새 신뢰 경계가 생긴다 → **Part IV**, **47.10**

## 16.8 크롤러와 크롤링 / 로봇의 HTTP

앞의 일곱 절은 **우리가 무엇을 기록하는가**를 다뤘다. 남은 네 절은 그 기록에 남는 요청의 상당수를 만들어 내는 주체 — 그리고 우리 사이트를 읽어 가는 주체 — 를 다룬다.

**웹 로봇(web robot)** 은 사람의 개입 없이 일련의 웹 트랜잭션을 자동화하는 소프트웨어다. 많은 로봇이 사이트에서 사이트로 돌아다니며 콘텐츠를 가져오고, 하이퍼링크를 따라가고, 발견한 데이터를 처리한다. 스스로의 의지를 가진 듯 자동으로 사이트를 탐험하는 방식 때문에 크롤러, 스파이더, 웜, 봇 같은 이름이 붙었다.

예를 들면 이런 것들이다.

- **주가 그래프 로봇**은 몇 분마다 주식 시장 서버에 `GET`을 보내 그 데이터로 주가 추이 그래프를 만든다.
- **웹 센서스 로봇**은 웹의 규모와 진화에 대한 "인구 조사" 정보를 모은다. 웹을 돌아다니며 페이지 수를 세고 각 페이지의 크기, 언어, 미디어 타입을 기록한다.
- **검색 엔진 로봇**은 발견한 문서를 전부 수집해 검색 데이터베이스를 만든다.
- **비교 쇼핑 로봇**은 온라인 상점 카탈로그에서 웹 페이지를 모아 상품과 가격의 데이터베이스를 만든다.

이 목록에 이 책이 하나를 더한다. **애플리케이션 매핑 도구**다. 침투 테스터와 공격자가 쓰는 스파이더는 위의 목록과 기술적으로 같은 것이며, 목적만 다르다(→ 25.1, 25.8).

### 16.8.1 크롤러가 하는 일

**웹 크롤러**는 정보의 웹을 재귀적으로 순회하는 로봇이다. 먼저 한 페이지를 가져오고, 그 페이지가 가리키는 모든 페이지를 가져오고, 다시 그 페이지들이 가리키는 모든 페이지를 가져온다. 로봇이 웹 링크를 재귀적으로 따라가면 그것을 크롤러 또는 스파이더라 부른다. HTML 하이퍼링크가 만들어 낸 거미줄을 "기어다니기(crawl)" 때문이다.

**루트 집합.** 크롤러를 풀어놓기 전에 출발점을 줘야 한다. 크롤러가 처음 방문하는 URL의 집합을 **루트 집합(root set)** 이라 한다. 루트 집합을 고를 때는 충분히 다양한 곳에서 URL을 골라야 한다. 링크를 전부 따라갔을 때 관심 있는 페이지 대부분에 결국 도달할 수 있어야 하기 때문이다.

실제 웹에는 모든 문서로 결국 이어지는 단일 문서가 없다. 어떤 페이지들은 거의 고립되어 있다. 아무 링크도 그것을 가리키지 않는다. 새로 만들어져 아직 아무도 발견하지 못한 페이지일 수도 있고, 아주 오래되었거나 잊힌 페이지일 수도 있다.

일반적으로 웹의 큰 부분을 덮는 데 루트 집합의 페이지가 아주 많이 필요하지는 않다. 좋은 루트 집합은 대개 **큰 인기 사이트들, 새로 만들어진 페이지 목록, 자주 링크되지 않는 잘 알려지지 않은 페이지 목록**으로 구성된다. 검색 엔진이 쓰는 것 같은 대규모 크롤러는 사용자가 새 페이지나 잘 알려지지 않은 페이지를 루트 집합에 제출할 수 있는 수단을 갖는다. 이 루트 집합은 시간이 지나며 커지고, 이후의 모든 크롤에 대한 씨앗 목록이 된다.

**링크 추출과 상대 링크 정규화.** 크롤러는 웹을 돌아다니며 끊임없이 HTML 페이지를 가져온다. 가져온 페이지마다 URL 링크를 파싱해 내어 크롤할 페이지 목록에 추가해야 한다. 크롤이 진행되는 동안 이 목록은 새 링크가 발견되면서 빠르게 늘어난다. 크롤러는 링크를 추출하고 **상대 URL을 절대 형태로 변환**하기 위해 간단한 HTML 파싱을 해야 한다(→ 7.3).

### 16.8.2 사이클과 중복

로봇이 웹을 크롤할 때는 **루프, 즉 사이클에 갇히지 않도록 대단히 조심해야 한다.**

로봇이 페이지 A를 가져오고, A가 B를 링크하는 것을 보고 B를 가져온다. B가 C를 링크하므로 C를 가져온다. 그런데 C가 A를 링크한다면, 그리고 로봇이 A를 다시 가져온다면 사이클에 빠진다. A, B, C, A, B, C, A...

로봇은 자기가 어디에 있었는지 알아야 사이클을 피할 수 있다. 사이클은 로봇의 진행을 멈추거나 늦추는 **로봇 트랩**으로 이어질 수 있다.

사이클이 나쁜 이유는 최소한 세 가지다.

1. **크롤러가 루프에 갇힌다.** 설계가 부실한 크롤러는 뱅뱅 돌면서 같은 페이지를 계속 가져오는 데 모든 시간을 쓴다. 네트워크 대역폭을 태우고, 다른 페이지를 전혀 가져오지 못하게 될 수 있다.
2. **반대편의 웹 서버가 두들겨 맞는다.** 크롤러의 연결이 좋다면 사이트를 압도해서 실제 사용자가 사이트에 접근하지 못하게 만들 수 있다. **이런 서비스 거부는 법적 청구의 근거가 될 수 있다.**
3. **중복 페이지가 대량으로 쌓인다.** 루프 자체가 문제가 아니더라도 크롤러의 애플리케이션은 중복 콘텐츠로 넘쳐나고, 그 결과 애플리케이션이 쓸모없어질 수 있다. 정확히 같은 페이지를 수백 개 반환하는 검색 엔진이 그 예다.

**방문 기록의 규모.** 어디에 있었는지를 추적하는 일은 쉽지 않다. 웹의 큰 부분을 크롤하려면 수십억 개의 URL을 방문할 준비를 해야 한다. URL의 수가 워낙 많으므로 어떤 URL을 방문했는지 빠르게 판정할 정교한 자료구조가 필요하다. 속도와 메모리 양쪽에서 효율적이어야 한다.

메모리 요구를 계산해 보면 규모가 실감난다. 평균 URL 길이가 40자이고 로봇이 5억 개의 URL을 크롤한다면(웹의 작은 일부에 불과하다), URL을 담는 것만으로 **20GB 이상**이 필요하다.

대규모 크롤러가 쓰는 기법은 다음과 같다.

- **트리와 해시 테이블** — 방문한 URL을 추적하는 검색 트리나 해시 테이블. URL 조회를 훨씬 빠르게 한다.
- **손실 있는 존재 비트맵** — 공간을 최소화하기 위해 일부 대규모 크롤러는 presence bit array 같은 손실 자료구조를 쓴다. 각 URL을 해시 함수로 고정 크기 숫자로 바꾸고, 그 숫자에 대응하는 "존재 비트"를 배열에 둔다. URL을 크롤하면 해당 비트를 세운다. 이미 세워져 있으면 크롤러는 그 URL을 이미 크롤했다고 가정한다. **URL은 사실상 무한하고 비트는 유한하므로 충돌이 가능하다.** 충돌이 일어나면 크롤러는 크롤하지 않은 페이지를 크롤했다고 잘못 판단한다. 비트 수를 충분히 크게 하면 실무에서 이 상황은 매우 드물게 만들 수 있고, 충돌의 대가는 그 페이지가 크롤에서 빠지는 것이다.
- **체크포인트** — 로봇 프로그램이 죽을 경우에 대비해 방문한 URL 목록을 디스크에 저장한다.
- **파티셔닝** — 웹이 커지면서 컴퓨터 한 대의 로봇 하나로 크롤을 완료하는 것이 비현실적이 된다. 그래서 대규모 로봇은 각각이 별도의 컴퓨터인 로봇 "농장"을 함께 돌린다. 각 로봇은 특정한 URL "조각"을 할당받고 그것을 책임진다. 로봇들은 URL을 주고받거나 고장난 동료를 대신하기 위해 서로 통신해야 할 수 있다.

### 16.8.3 별칭과 정규화

올바른 자료구조를 써도 어떤 페이지를 이미 방문했는지 판정하기 어려울 때가 있다. **URL 별칭(aliasing)** 때문이다. 두 URL이 겉보기에 다르지만 실제로는 같은 리소스를 가리키면 그 둘은 별칭이다.

**표 16-16. 같은 문서를 가리키는 서로 다른 URL (HTTP-DG 표 9-1)**

| | 첫 번째 URL | 두 번째 URL | 별칭이 되는 조건 |
|---|---|---|---|
| a | `http://www.foo.com/bar.html` | `http://www.foo.com:80/bar.html` | 포트 기본값이 80 |
| b | `http://www.foo.com/~fred` | `http://www.foo.com/%7Ffred` | `%7F`가 `~`와 같음 |
| c | `http://www.foo.com/x.html#early` | `http://www.foo.com/x.html#middle` | 프래그먼트는 페이지를 바꾸지 않음 |
| d | `http://www.foo.com/readme.htm` | `http://www.foo.com/README.HTM` | 대소문자를 구별하지 않는 서버 |
| e | `http://www.foo.com/` | `http://www.foo.com/index.html` | 기본 페이지가 `index.html` |
| f | `http://www.foo.com/index.html` | `http://209.231.87.45/index.html` | `www.foo.com`이 그 IP 주소를 가짐 |

대부분의 로봇은 URL을 표준 형태로 **정규화(canonicalizing)** 해서 명백한 별칭을 미리 제거하려 한다. 로봇이 하는 정규화는 대체로 세 단계다.

1. 포트가 지정되지 않았으면 호스트명에 `:80`을 붙인다
2. `%xx` 이스케이프 문자를 전부 그에 해당하는 문자로 변환한다
3. `#` 프래그먼트를 제거한다

이 단계들은 표 16-16의 a~c를 제거한다. 그러나 **특정 웹 서버에 대한 정보 없이는 d~f의 중복을 피할 좋은 방법이 없다.**

- d를 피하려면 웹 서버가 대소문자를 구별하지 않는지 알아야 한다.
- e를 피하려면 그 디렉터리에 대한 웹 서버의 인덱스 페이지 설정을 알아야 한다(→ 12.4.2).
- f를 피하려면 웹 서버가 가상 호스팅을 하도록 설정되었는지 알아야 한다(→ 15.2). 호스트명과 IP 주소가 같은 물리 컴퓨터를 가리킨다는 것을 알더라도 그렇다.

URL 정규화는 기본적인 구문 수준의 별칭을 제거할 수 있지만, **표준 형태로의 변환으로는 제거할 수 없는 다른 별칭들이 남는다.**

이 서술을 7.7절과 나란히 놓아야 한다. 그곳에서 정규화는 **보안 검사를 우회하는 수단**이었다. 같은 리소스를 가리키는 표현이 여럿이므로, 어느 표현으로 검사하고 어느 표현으로 접근하는지가 어긋나면 검사가 무력해진다. 여기서 같은 사실이 **크롤러가 같은 것을 두 번 세는 문제**로 나타난다. 두 문제의 근본 원인은 하나다. **하나의 리소스에 대한 이름이 여러 개다.**

### 16.8.4 파일 시스템 링크 사이클과 동적 가상 웹 공간

파일 시스템의 심볼릭 링크는 특히 음험한 종류의 사이클을 만든다. 존재하지 않는 무한히 깊은 디렉터리 계층의 환상을 만들어 내기 때문이다. 심볼릭 링크 사이클은 대개 서버 관리자의 의도치 않은 실수의 결과이지만, **"악의적인 웹마스터"가 로봇을 잡는 함정으로 만들 수도 있다.**

`/index.html`이 `subdir/index.html`을 링크한다고 하자. `subdir`가 평범한 디렉터리라면 크롤은 이렇게 끝난다.

```
1. GET http://www.foo.com/index.html          → subdir/index.html 링크 발견
2. GET http://www.foo.com/subdir/index.html   → subdir/logo.gif 링크 발견
3. GET http://www.foo.com/subdir/logo.gif     → 링크 없음, 완료
```

그런데 `subdir`가 `/`를 가리키는 상향 심볼릭 링크라면 이렇게 된다.

```
1. GET http://www.foo.com/index.html                        → subdir/index.html 링크 발견
2. GET http://www.foo.com/subdir/index.html                 → 같은 index.html이 돌아옴
3. GET http://www.foo.com/subdir/subdir/index.html
4. GET http://www.foo.com/subdir/subdir/subdir/index.html
...
```

*그림 16-2. 심볼릭 링크가 만드는 사이클 (HTTP-DG 그림 9-3 기준)*

문제는 `subdir/`가 `/`로 돌아가는 사이클이지만 **URL이 서로 달라 보이기 때문에 로봇이 URL만으로는 문서가 동일함을 알 수 없다는 것**이다. 어떤 형태의 루프 탐지도 없다면 이 사이클은 URL의 길이가 로봇이나 서버의 한계를 넘어설 때까지 계속된다.

**동적 가상 웹 공간.** 악의적인 웹마스터가 순진한 로봇을 잡기 위해 정교한 크롤러 루프를 의도적으로 만들 수도 있다. 특히 평범한 파일처럼 보이지만 실제로는 게이트웨이 애플리케이션인 URL을 공개하는 것은 쉽다. 이 애플리케이션은 같은 서버의 가상 URL로의 링크를 담은 HTML을 즉석에서 만들어 낸다. 그 가상 URL이 요청되면 서버는 또 새로운 가상 URL을 담은 새 HTML 페이지를 만들어 낸다.

```
[요청] GET /index-fall.html HTTP/1.1
       Host: www.evil-joes-hardware.com
       User-agent: ShopBot

[응답] HTTP/1.1 200 OK
       Content-type: text/html
       <HTML><BODY><A HREF=/index-fall2.html>trick</A>[...]

[요청] GET /index-fall2.html HTTP/1.1
       ...

[응답] <A HREF=/index-fall3.html>trick</A>[...]
```

*그림 16-3. 가짜 콘텐츠를 만들어 내는 악성 웹 서버 (HTTP-DG 그림 9-4 기준)*

악성 웹 서버는 실제로는 파일을 하나도 갖고 있지 않으면서도 로봇을 무한한 가상 웹 공간의 여행으로 끌고 갈 수 있다. 더 나쁜 것은 **매번 URL과 HTML이 다르게 보일 수 있어 로봇이 사이클을 탐지하기가 매우 어렵다**는 점이다.

더 흔한 것은 선의의 웹마스터가 심볼릭 링크나 동적 콘텐츠로 **의도치 않게** 크롤러 트랩을 만드는 경우다. 월별 달력과 다음 달로의 링크를 생성하는 CGI 기반 달력 프로그램을 생각해 보라. 실제 사용자는 다음 달 링크를 영원히 요청하지 않는다. 그러나 콘텐츠의 동적 성격을 모르는 로봇은 그 리소스를 무한정 계속 요청할 수 있다. 이런 동적 콘텐츠 때문에 **많은 로봇이 URL 어디에든 `cgi`라는 부분 문자열이 있으면 크롤을 거부한다.**

### 16.8.5 루프와 중복을 피하는 휴리스틱

모든 사이클을 피하는 확실한 방법은 없다. 실무에서 잘 설계된 로봇은 사이클을 피하려는 휴리스틱의 집합을 포함해야 한다.

일반적으로 **크롤러가 자율적일수록(사람의 감독이 적을수록) 곤경에 빠질 가능성이 높다.** 로봇 구현자가 감수해야 하는 절충이 있다. 이 휴리스틱들은 문제를 피하는 데 도움을 주지만, 동시에 다소 "손실이 있다". 수상해 보이는 유효한 콘텐츠를 건너뛰게 될 수 있기 때문이다.

- **URL 정규화** — URL을 표준 형태로 변환해 구문적 별칭을 피한다.
- **너비 우선 크롤링** — 크롤러는 어느 시점에나 크롤할 잠재적 URL의 큰 집합을 갖는다. 사이트를 가로질러 너비 우선으로 방문 순서를 잡으면 사이클의 영향을 최소화할 수 있다. 로봇 트랩에 걸리더라도 그 사이클의 페이지로 돌아오기 전에 다른 사이트에서 수십만 페이지를 가져올 수 있다. 깊이 우선으로 한 사이트에 머리부터 뛰어들면 사이클에 걸려 빠져나오지 못할 수 있다. 너비 우선 크롤링은 요청을 더 고르게 분산해 어느 한 서버도 압도하지 않는다는 점에서도 일반적으로 좋은 생각이다.
- **스로틀링** — 로봇이 한 사이트에서 일정 기간에 가져올 수 있는 페이지 수를 제한한다. 사이클에 걸려 별칭에 계속 접근하려 해도 생성되는 중복의 총량과 그 서버에 대한 접근의 총량에 상한을 걸 수 있다.
- **URL 크기 제한** — 일정 길이(1KB가 흔하다)를 넘는 URL은 크롤을 거부한다. 사이클로 URL이 계속 길어지면 길이 제한이 결국 사이클을 멈춘다. **어떤 웹 서버는 긴 URL을 받으면 실패하며, URL이 늘어나는 사이클에 걸린 로봇은 취약한 웹 서버를 죽게 만들 수 있다.** 그러면 웹마스터가 그 로봇을 서비스 거부 공격자로 오해할 수 있다. 다만 이 기법은 콘텐츠 누락을 초래할 수 있다는 점을 주의해야 한다. 오늘날 많은 사이트가 사용자 상태 관리를 위해 URL을 쓴다(예: 페이지에서 참조하는 URL에 사용자 ID를 담기). URL 크기로 크롤을 제한하는 것은 까다로운 방법이지만, **요청 URL이 일정 크기에 도달할 때마다 오류를 로깅하면 특정 사이트에서 무슨 일이 벌어지는지 사람이 점검할 훌륭한 신호가 된다.**
- **URL/사이트 블랙리스트** — 로봇 사이클과 트랩에 해당하는 것으로 알려진 사이트와 URL 목록을 유지하고 그것들을 역병처럼 피한다. 새 문제가 발견되면 블랙리스트에 추가한다. 사람의 조치가 필요하다. 오늘날 대부분의 대규모 프로덕션 크롤러는 어떤 형태로든 블랙리스트를 갖고 있으며, 내재적 문제나 악의적 요소가 있는 사이트를 피하는 데 쓴다. **블랙리스트는 크롤당하는 것에 대해 항의한 사이트를 피하는 데도 쓸 수 있다.**
- **패턴 탐지** — 파일 시스템 심링크나 유사한 오설정이 만드는 사이클은 패턴을 따르는 경향이 있다. 예컨대 URL이 성분이 반복되며 길어진다. 어떤 로봇은 성분이 반복되는 URL을 잠재적 사이클로 보고 두세 개를 넘는 반복 성분이 있는 URL의 크롤을 거부한다. 모든 반복이 즉시 인접한 것은 아니다(`/subdir/subdir/subdir...`). 주기 2 이상의 사이클도 가능하다(`/subdir/images/subdir/images/subdir/images/...`). 어떤 로봇은 몇 가지 다른 주기의 반복 패턴을 찾는다.
- **콘텐츠 핑거프린팅** — 더 정교한 크롤러가 쓰는 더 직접적인 중복 탐지 방식이다. 페이지 콘텐츠의 바이트로 체크섬을 계산한다. 이 체크섬은 페이지 콘텐츠의 압축된 표현이다. 이전에 본 체크섬을 가진 페이지를 가져오면 그 페이지의 링크는 크롤하지 않는다. 이미 그 콘텐츠를 봤다면 그 페이지의 링크에 대한 크롤을 이미 시작했기 때문이다. 체크섬 함수는 서로 다른 두 페이지가 같은 체크섬을 가질 확률이 작도록 골라야 한다. MD5 같은 메시지 다이제스트 함수가 핑거프린팅에 널리 쓰인다(→ 10.6). 어떤 웹 서버는 페이지를 즉석에서 수정하므로 로봇은 임베드된 링크 같은 특정 부분을 체크섬 계산에서 빼기도 한다. 그럼에도 날짜나 접근 카운터를 더하는 등 임의의 페이지 콘텐츠를 맞춤 생성하는 서버 측 인클루드는 중복 탐지를 방해할 수 있다(→ 12.4.3).
- **사람의 감시** — 웹은 거친 곳이다. 어떤 기법으로도 잡지 못할 문제에 결국 부딪힌다. **프로덕션 품질의 로봇은 전부 진단과 로깅을 갖추도록 설계되어야 한다.** 사람이 로봇의 진행을 쉽게 관찰하고 이상한 일이 벌어지면 빨리 경고받을 수 있어야 한다. 어떤 경우에는 화난 네티즌이 험한 이메일을 보내 문제를 알려 주기도 한다.

마지막 항목이 이 장의 앞부분과 이어진다. **로봇을 운영하는 쪽도 로그와 모니터링과 경보가 필요하다.** 16.5절이 서버 쪽에서 서술한 것과 대칭이며, 16.10절이 그것을 에티켓의 항목으로 다시 다룬다.

### 16.8.6 로봇의 HTTP

로봇도 다른 HTTP 클라이언트 프로그램과 다르지 않다. HTTP 명세의 규칙을 지켜야 한다. HTTP 요청을 만들면서 자신을 HTTP/1.1 클라이언트로 광고하는 로봇은 적절한 HTTP 요청 헤더를 써야 한다.

그런데 많은 로봇이 원하는 콘텐츠를 요청하는 데 필요한 **최소한의 HTTP만 구현하려 한다.** 이것은 문제를 낳을 수 있지만 가까운 시일 안에 바뀔 가능성은 낮다. 그 결과 **많은 로봇이 HTTP/1.0 요청을 보낸다.** 그 프로토콜의 요구사항이 적기 때문이다.

이 사실은 방어자에게 중요한 단서다. 접근 로그에서 HTTP/1.0 요청 라인은 오늘날 사람이 쓰는 브라우저에서는 거의 나오지 않는다. 그것 자체가 자동화된 클라이언트를 시사한다.

**식별 헤더.** 로봇이 지원하는 HTTP가 최소한이더라도 대부분은 어떤 식별 헤더 — 특히 `User-Agent` — 를 구현해 보낸다. 로봇 구현자는 사이트에 로봇의 능력, 정체, 출처를 알리는 기본 헤더 정보를 보내는 것이 권장된다.

이 정보는 두 가지로 유용하다. **잘못 동작하는 크롤러의 소유자를 추적하는 것**과 **로봇이 어떤 종류의 콘텐츠를 다룰 수 있는지 서버에 알리는 것**이다.

로봇 구현자에게 권장되는 기본 식별 헤더는 다음과 같다.

**표 16-17. 로봇이 보내야 할 식별 헤더**

| 헤더 | 내용 |
|---|---|
| `User-Agent` | 요청을 만드는 로봇의 이름을 서버에 알린다 |
| `From` | 로봇 사용자·관리자의 이메일 주소(RFC 822 형식) |
| `Accept` | 서버에게 어떤 미디어 타입을 보내도 되는지 알린다. 로봇이 관심 있는 콘텐츠(텍스트, 이미지 등)만 받도록 하는 데 도움이 된다 |
| `Referer` | 현재 요청 URL을 담고 있는 문서의 URL을 제공한다 |

`Referer`는 **사이트 관리자가 로봇이 자기 사이트의 콘텐츠로 가는 링크를 어떻게 발견했는지 추적할 때 매우 유용하다.** 로그의 `Referer` 필드(표 16-3)가 여기서 진단 도구가 된다.

방어자 관점에서 이 표에는 한 가지 단서가 빠져 있다. **이 헤더들은 전부 클라이언트가 쓰는 값이며 아무런 강제력이 없다**(→ 8.6). 예의 바른 로봇은 자기를 정확히 밝히고, 예의 없는 로봇은 밝히지 않으며, 악의적인 로봇은 브라우저인 척한다. `User-Agent`로 로봇을 식별하는 것은 통계에는 쓸 수 있어도 **접근 통제의 근거로는 쓸 수 없다.**

**가상 호스팅.** 로봇 구현자는 **`Host` 헤더를 지원해야 한다.** 가상 호스팅이 만연한 상황에서(→ 15.2) 요청에 `Host` 헤더를 포함하지 않으면 로봇이 특정 URL에 대해 잘못된 콘텐츠를 식별하게 될 수 있다. HTTP/1.1이 `Host` 헤더 사용을 요구하는 이유가 바로 이것이다.

대부분의 서버는 기본으로 서비스할 사이트가 설정되어 있다. 두 사이트(`www.joes-hardware.com`과 `www.foo.com`)를 서비스하는 서버에 `Host` 헤더 없이 요청하는 크롤러를 생각해 보자. 서버가 `www.joes-hardware.com`을 기본으로 서비스하도록 설정되어 있고 `Host` 헤더를 요구하지 않는다면, `www.foo.com`의 페이지에 대한 요청이 Joe's Hardware 사이트의 콘텐츠를 받게 된다. **더 나쁜 것은 크롤러가 Joe's Hardware의 콘텐츠를 `www.foo.com`의 것이라고 여긴다는 점이다.**

```
[요청] GET /index.html HTTP/1.0          ← Host 헤더 없음
       User-agent: ShopBot 1.0

[응답] HTTP/1.0 200 OK
       <HTML><TITLE>Welcome to Joe's Hardware!</TITLE>
       ← foo.com을 요청했는데 joes-hardware.com의 콘텐츠가 왔다
```

*그림 16-4. `Host` 헤더 없는 요청과 가상 docroot (HTTP-DG 그림 9-5 기준)*

정치적 입장이나 다른 견해가 정반대인 두 사이트가 같은 서버에서 서비스되는 경우를 생각하면 이 오분류가 얼마나 곤란해질 수 있는지 분명해진다. 15.2절이 서술한 "목적지를 정하는 근거가 클라이언트가 보낸 값"이라는 구조가, **그 값을 아예 보내지 않는 클라이언트** 앞에서 어떻게 되는지를 보여 주는 사례다.

**조건부 요청.** 어떤 로봇의 작업 규모를 생각하면 로봇이 가져오는 콘텐츠의 양을 최소화하는 것이 합리적일 때가 많다. 검색 엔진 로봇처럼 잠재적으로 수십억 페이지를 내려받아야 하는 경우, **콘텐츠가 바뀌었을 때만 다시 가져오는 것**이 이치에 맞다.

그래서 일부 로봇은 조건부 HTTP 요청을 구현해 타임스탬프나 엔티티 태그를 비교하고 마지막으로 가져온 버전이 갱신되었는지 확인한다. 이것은 HTTP 캐시가 로컬 사본의 유효성을 검사하는 방식과 매우 유사하다(→ 14.5, 10.8).

**응답 처리.** 많은 로봇이 주로 단순한 `GET`으로 요청한 콘텐츠를 얻는 데만 관심이 있으므로 응답 처리를 많이 하지 않는다. 그러나 조건부 요청 같은 HTTP 기능을 쓰는 로봇, 그리고 서버를 더 잘 탐험하고 상호운용하려는 로봇은 여러 종류의 HTTP 응답을 다룰 수 있어야 한다.

일반적으로 로봇은 최소한 흔하거나 예상되는 상태 코드는 다룰 수 있어야 한다. 모든 로봇이 `200 OK`나 `404 Not Found` 같은 코드를 이해해야 한다. 명시적으로 이해하지 못하는 상태 코드도 응답의 일반적 범주에 근거해 다룰 수 있어야 한다(→ 8.4).

여기서 중요한 것은 **어떤 서버는 적절한 오류 코드를 항상 반환하지는 않는다**는 점이다. 어떤 서버는 오류를 설명하는 텍스트 본문과 함께 `200 OK` 상태 코드를 반환하기도 한다. 이에 대해 할 수 있는 일은 별로 없다. 구현자가 알고 있어야 할 사실일 뿐이다. 8.4절이 상태 코드의 오용 사례로 다룬 것과 같은 문제이며, 30.3절에서 그것이 공격자에게 어떤 채널이 되는지를 다룬다.

**엔티티 안의 정보.** HTTP 헤더에 담긴 정보와 함께 로봇은 엔티티 자체에서도 정보를 찾을 수 있다. `meta http-equiv` 같은 메타 HTML 태그는 콘텐츠 저자가 리소스에 대한 추가 정보를 심는 수단이다. `http-equiv` 태그 자체는 **콘텐츠 저자가 그 콘텐츠를 다루는 서버가 보내는 특정 헤더를 재정의하는 수단**이다.

```html
<meta http-equiv="Refresh" content="1;URL=index.html">
```

이 태그는 수신자에게 이 문서의 HTTP 응답 헤더에 값이 `1, URL=index.html`인 `Refresh` HTTP 헤더가 있었던 것처럼 다루라고 지시한다. `Refresh` 헤더는 때때로 사용자(여기서는 로봇)를 한 페이지에서 다른 페이지로 리다이렉트하는 수단으로 쓰인다.

어떤 서버는 HTML 페이지를 보내기 전에 그 내용을 실제로 파싱해서 `http-equiv` 지시자를 헤더로 포함시킨다. 그러나 그러지 않는 서버도 있다. 그래서 로봇 구현자는 HTML 문서의 `HEAD` 요소를 스캔해 `http-equiv` 정보를 찾을 필요가 있다. 메타 태그는 HTML 명세상 `HEAD` 섹션에 있어야 하지만, 모든 HTML 문서가 명세를 지키는 것은 아니므로 다른 섹션에 나타나기도 한다.

**`User-Agent` 타게팅.** 웹 관리자는 많은 로봇이 자기 사이트를 방문할 것이며 따라서 그들로부터의 요청을 예상해야 한다는 점을 염두에 둬야 한다. 많은 사이트가 다양한 사용자 에이전트에 맞춰 콘텐츠를 최적화하고, 여러 사이트 기능이 지원되는지 확인하려고 브라우저 종류를 탐지하려 한다. **그 결과 로봇에게 콘텐츠 대신 오류 페이지를 보내게 된다.**

일부 검색 엔진에서 "your browser does not support frames"라는 문구를 텍스트 검색해 보면 그 문구를 담은 오류 페이지의 결과 목록이 나온다. **HTTP 클라이언트가 브라우저가 아니라 로봇이었는데도 그런 페이지가 색인된 것이다.**

사이트 관리자는 로봇 요청을 다루는 전략을 세워야 한다. 예를 들어 특정 브라우저 지원으로 콘텐츠 개발을 제한하는 대신, 기능이 풍부하지 않은 브라우저와 로봇을 위한 catch-all 페이지를 만들 수 있다. 최소한 로봇이 자기 사이트를 방문할 것을 예상하고 실제로 방문했을 때 당황하지 않아야 한다.

> **이 절이 뒷받침하는 것**
>
> - 로봇은 링크를 발견하는 즉시 따라가며, 자율적일수록 통제하기 어렵다 → **16.10** (그 결과 서버에 나타나는 현상)
> - `User-Agent`와 `From`은 자발적으로 보내는 값이며 강제력이 없다 → **8.6**, **16.10** (로그에서 로봇을 식별하려는 시도의 한계)
> - 로봇은 URL 별칭 때문에 같은 리소스를 여러 번 센다 → **7.7** (같은 사실이 보안 검사에서 나타나는 형태)

## 16.9 로봇 배제 — robots.txt, 메타 태그, 그리고 그 오용

로봇 커뮤니티는 로봇의 사이트 접근이 일으킬 수 있는 문제를 이해하고 있었다. 1994년에 로봇이 있어서는 안 되는 곳에 들어가지 못하게 하고 웹마스터가 로봇의 행동을 더 잘 통제할 수 있게 하는 **단순하고 자발적인 기법**이 제안되었다. 표준의 이름은 "Robots Exclusion Standard"이지만, 접근 통제 정보가 저장되는 파일의 이름을 따서 흔히 **`robots.txt`** 라고 부른다.

`robots.txt`의 발상은 단순하다. 어떤 웹 서버든 문서 루트에 `robots.txt`라는 선택적 파일을 둘 수 있다. 이 파일에는 **어떤 로봇이 서버의 어느 부분에 접근할 수 있는지**에 대한 정보가 담긴다. 로봇이 이 자발적 표준을 따른다면, 사이트의 다른 리소스에 접근하기 전에 그 사이트의 `robots.txt` 파일을 요청한다.

```
[1] 로봇 → www.joes-hardware.com
    GET /robots.txt

[2] 로봇이 robots.txt를 파싱해 대상 파일에 접근해도 되는지 판정한다.
    접근 가능하다고 판정되었으므로 요청을 진행한다.

[3] 로봇 → www.joes-hardware.com
    GET /specials/acetylene-torches.html
```

*그림 16-5. `robots.txt`를 가져와 접근 가능성을 확인한 뒤 대상 파일을 크롤한다 (HTTP-DG 그림 9-6 기준)*

이 절의 나머지는 이 메커니즘의 문법과 동작을 다루고, 마지막 두 소절이 **이 메커니즘이 실제로 무엇인지, 그리고 무엇이 아닌지**를 다룬다.

### 16.9.1 표준의 지위와 버전

Robots Exclusion Standard는 **비공식(ad hoc) 표준**이다. HTTP-DG 집필 시점에 이 표준을 소유한 공식 표준화 기구가 없었고, 벤더마다 표준의 서로 다른 부분집합을 구현한다. 그럼에도 불완전하나마 로봇의 사이트 접근을 관리할 수 있는 것이 전혀 없는 것보다는 낫고, 주요 벤더와 검색 엔진 크롤러 대부분이 배제 표준 지원을 구현하고 있다.

**표 16-18. Robots Exclusion Standard의 세 판 (HTTP-DG 표 9-2)**

| 버전 | 제목과 설명 | 날짜 |
|---|---|---|
| 0.0 | A Standard for Robot Exclusion — Martijn Koster의 원래 `robots.txt` 메커니즘. `Disallow` 지시자 | 1994년 6월 |
| 1.0 | A Method for Web Robots Control — Martijn Koster의 IETF 드래프트. `Allow` 지원 추가 | 1996년 11월 |
| 2.0 | An Extended Standard for Robot Exclusion — Sean Conner의 확장. 정규식과 타이밍 정보 포함. 널리 지원되지 않음 | 1996년 11월 |

오늘날 대부분의 로봇은 v0.0이나 v1.0을 채택한다. v2.0은 훨씬 복잡하고 널리 채택되지 않았다. 이 절은 v1.0에 집중한다. 널리 쓰이고 v0.0과 완전히 호환되기 때문이다.

### 16.9.2 `robots.txt` 가져오기

로봇은 사이트의 어떤 URL을 방문하기 전에 그 사이트의 `robots.txt` 파일이 존재하면 그것을 가져와서 처리해야 한다. **호스트명과 포트 번호로 정의되는 웹 사이트 전체에 대해 `robots.txt` 리소스는 하나뿐이다.** 사이트가 가상 호스팅되고 있다면 다른 파일들과 마찬가지로 **가상 docroot마다 서로 다른 `robots.txt`가 있을 수 있다**(→ 15.2).

현재 웹 사이트의 개별 하위 디렉터리에 "지역" `robots.txt` 파일을 설치할 방법은 없다. 웹마스터는 사이트의 모든 콘텐츠에 대한 배제 규칙을 기술하는 **통합 `robots.txt` 파일**을 만들 책임이 있다.

`robots.txt`가 반드시 파일 시스템에 있어야 하는 것은 아니다. 게이트웨이 애플리케이션이 동적으로 생성해도 된다.

로봇은 다른 파일과 마찬가지로 HTTP `GET` 메서드로 `robots.txt` 리소스를 가져온다. 서버는 파일이 있으면 `text/plain` 본문으로 반환한다. 서버가 `404 Not Found`로 응답하면 로봇은 로봇 접근 제한이 없으며 어떤 파일이든 요청할 수 있다고 가정할 수 있다.

로봇은 사이트 관리자가 로봇의 접근을 추적하고 필요할 때 문의하거나 항의할 수 있도록 `From`과 `User-Agent` 헤더에 식별 정보를 실어 보내야 한다.

```
GET /robots.txt HTTP/1.0
Host: www.joes-hardware.com
User-Agent: Slurp/2.0
Date: Wed Oct 3 20:22:48 EST 2001
```

*예제 16-12. 상용 웹 로봇의 `robots.txt` 요청 (HTTP-DG 기준)*

많은 사이트에 `robots.txt` 리소스가 없지만 로봇은 그것을 모른다. **모든 사이트에서 `robots.txt`를 가져오려고 시도해야 한다.** 그 결과에 따라 로봇이 취해야 할 동작은 다음과 같다.

**표 16-19. `robots.txt` 응답 코드에 따른 로봇의 동작**

| 응답 | 로봇의 동작 |
|---|---|
| `2XX` 성공 | 내용을 파싱하고 그 사이트에 대한 가져오기에 배제 규칙을 적용해야 한다 |
| `404` 없음 | 활성화된 배제 규칙이 없다고 가정할 수 있다. 사이트 접근이 `robots.txt`로 제한되지 않는다 |
| `401` 또는 `403` 접근 제한 | 그 사이트에 대한 접근이 **완전히 제한된** 것으로 간주해야 한다 |
| `503` 일시적 실패 | 리소스를 가져올 수 있을 때까지 그 사이트 방문을 미뤄야 한다 |
| `3XX` 리다이렉션 | 리소스를 찾을 때까지 리다이렉트를 따라가야 한다 |

`401`/`403`에 대한 규정을 눈여겨보라. **`robots.txt`에 접근할 수 없으면 사이트 전체가 금지된 것으로 간주하라**는 것이다. 이 보수적 기본값은 잘 설계된 규칙이다. 접근 통제 앞에서 "모르면 하지 않는다"는 원칙은 30.6절과 45.2절이 실패 처리의 원칙으로 다시 다루는 것과 같은 형태다.

### 16.9.3 파일 포맷

`robots.txt` 파일은 아주 단순한 줄 지향 문법을 갖는다. 세 종류의 줄이 있다. 빈 줄, 주석 줄, 규칙 줄이다. 규칙 줄은 HTTP 헤더처럼 생겼고(`<필드>: <값>`) 패턴 매칭에 쓰인다.

```
# 이 robots.txt는 Slurp과 Webcrawler가 사이트의 공개 부분을 크롤하는 것을
# 허용하지만, 다른 로봇은 전부 막는다...

User-Agent: slurp
User-Agent: webcrawler
Disallow: /private

User-Agent: *
Disallow:
```

*예제 16-13. `robots.txt`의 기본 구조 (HTTP-DG 기준)*

`robots.txt`의 줄들은 논리적으로 **레코드**로 나뉜다. 각 레코드는 특정한 로봇 집합에 대한 배제 규칙의 집합을 기술한다. 이렇게 해서 서로 다른 로봇에게 서로 다른 배제 규칙을 적용할 수 있다.

각 레코드는 빈 줄이나 파일 끝 문자로 끝나는 규칙 줄들로 구성된다. 레코드는 이 레코드의 영향을 받는 로봇을 지정하는 하나 이상의 `User-Agent` 줄로 시작하고, 그 로봇들이 어떤 URL에 접근할 수 있는지 말하는 `Disallow`와 `Allow` 줄이 뒤따른다.

**`User-Agent` 줄.** 각 로봇의 레코드는 하나 이상의 `User-Agent` 줄로 시작한다.

```
User-Agent: <robot-name>
```
또는
```
User-Agent: *
```

로봇 이름(로봇 구현자가 정한다)은 로봇의 HTTP `GET` 요청의 `User-Agent` 헤더로 전송된다. 로봇이 `robots.txt`를 처리할 때는 다음 중 하나에 해당하는 레코드를 따라야 한다.

- **로봇 이름의 대소문자 무시 부분 문자열인 첫 번째 로봇 이름**
- **`*`인 첫 번째 로봇 이름**

로봇이 자기 이름에 매치되는 `User-Agent` 줄도, 와일드카드 `User-Agent: *` 줄도 찾지 못하면 매치되는 레코드가 없고 **접근은 제한되지 않는다.**

로봇 이름이 대소문자 무시 부분 문자열로 매치되므로 **잘못된 매치를 주의해야 한다.** 예를 들어 `User-Agent: bot`은 `Bot`, `Robot`, `Bottom-Feeder`, `Spambot`, `Dont-Bother-Me`라는 이름의 로봇 전부에 매치된다.

**`Disallow`와 `Allow` 줄.** `Disallow`와 `Allow` 줄은 배제 레코드의 `User-Agent` 줄 바로 뒤에 온다. 지정된 로봇에게 명시적으로 금지되거나 명시적으로 허용되는 URL 경로를 기술한다.

로봇은 원하는 URL을 그 배제 레코드의 모든 `Disallow`와 `Allow` 규칙에 대해 **순서대로** 매치해 봐야 한다. **처음 발견된 매치가 사용된다.** 매치가 발견되지 않으면 그 URL은 허용된다. (`robots.txt` URL 자체는 항상 허용되며 `Allow`/`Disallow` 규칙에 나타나서는 안 된다.)

`Allow`/`Disallow` 줄이 URL에 매치되려면 **규칙 경로가 URL 경로의 대소문자를 구별하는 접두사**여야 한다. 예컨대 `Disallow: /tmp`는 다음 URL 전부에 매치된다.

```
http://www.joes-hardware.com/tmp
http://www.joes-hardware.com/tmp/
http://www.joes-hardware.com/tmp/pliers.html
http://www.joes-hardware.com/tmpspc/stuff.txt
```

마지막 항목을 보라. `/tmpspc/`는 `/tmp` 디렉터리와 아무 관계가 없지만 문자열 접두사 매치이므로 걸린다. **이것이 접두사 매칭이라는 사실은 실무에서 자주 오해된다.**

접두사 매칭의 세부 규칙은 다음과 같다.

- `Disallow`와 `Allow` 규칙은 **대소문자를 구별하는** 접두사 매치를 요구한다. `User-Agent` 줄과 달리 애스터리스크에 특별한 의미가 없다. 다만 빈 문자열로 전체 와일드카드 효과를 낼 수 있다.
- 규칙 경로나 URL 경로의 `%XX` 이스케이프 문자는 비교 전에 바이트로 되돌려진다. **단 `%2F`(슬래시)는 예외이며 정확히 매치되어야 한다.**
- 규칙 경로가 빈 문자열이면 모든 것에 매치된다.

**표 16-20. 규칙 경로와 URL 경로의 매칭 (HTTP-DG 표 9-3)**

| 규칙 경로 | URL 경로 | 매치 | 설명 |
|---|---|---|---|
| `/tmp` | `/tmp` | O | 규칙 경로 == URL 경로 |
| `/tmp` | `/tmpfile.html` | O | 규칙 경로가 URL 경로의 접두사 |
| `/tmp` | `/tmp/a.html` | O | 규칙 경로가 URL 경로의 접두사 |
| `/tmp/` | `/tmp` | X | `/tmp/`는 `/tmp`의 접두사가 아니다 |
| (빈 문자열) | `README.TXT` | O | 빈 규칙 경로는 모든 것에 매치 |
| `/~fred/hi.html` | `/%7Efred/hi.html` | O | `%7E`는 `~`와 같게 취급 |
| `/%7Efred/hi.html` | `/~fred/hi.html` | O | `%7E`는 `~`와 같게 취급 |
| `/%7efred/hi.html` | `/%7Efred/hi.html` | O | 이스케이프에서 대소문자는 무의미 |
| `/~fred/hi.html` | `/~fred%2Fhi.html` | X | `%2F`는 슬래시이며 정확히 매치되어야 하는 특수 사례 |

접두사 매칭은 대체로 잘 작동하지만 **표현력이 부족한 곳이 몇 군데 있다.** 경로의 접두사가 무엇이든 상관없이 특정 하위 디렉터리의 크롤을 금지하고 싶다면 `robots.txt`는 그 수단을 제공하지 않는다. 예를 들어 RCS 버전 관리 하위 디렉터리의 크롤을 피하고 싶다면, `robots.txt` v1.0에는 **모든 RCS 하위 디렉터리로의 모든 경로를 하나하나 나열하는 것 외에 방법이 없다.**

이 한계를 기억해 두라. 16.9.6절에서 이것이 왜 위험한지가 드러난다. **개별 경로를 하나하나 나열해야 한다는 것은 곧 그 목록이 공개된다는 뜻이다.**

**그 밖의 규칙.**

- `robots.txt` 파일은 명세가 진화하면서 `User-Agent`, `Disallow`, `Allow` 외의 필드를 담을 수 있다. **로봇은 이해하지 못하는 필드를 무시해야 한다.**
- 하위 호환을 위해 줄 나눔은 허용되지 않는다.
- 주석은 파일 어디에나 올 수 있다. 선택적 공백, 주석 문자(`#`), 줄 끝까지의 주석으로 구성된다.
- v0.0은 `Allow` 줄을 지원하지 않았다. 일부 로봇은 v0.0만 구현하고 `Allow` 줄을 무시한다. **이 경우 로봇은 보수적으로 동작해서 허용된 URL을 가져오지 않는다.**

**캐싱과 만료.** 로봇이 파일 접근마다 `robots.txt`를 다시 가져와야 한다면 웹 서버의 부하가 두 배가 되고 로봇의 효율도 떨어진다. 대신 로봇은 `robots.txt`를 주기적으로 가져와 결과를 캐시하도록 되어 있다. 캐시된 사본은 `robots.txt`가 만료될 때까지 사용된다. 표준 HTTP 캐시 제어 메커니즘이 원 서버와 로봇 양쪽에서 `robots.txt`의 캐싱을 통제하는 데 쓰인다. 로봇은 `Cache-Control`과 `Expires` 헤더를 살펴야 한다(→ 14.5).

오늘날 많은 프로덕션 크롤러가 HTTP/1.1 클라이언트가 아니다. 웹마스터는 **그런 크롤러가 `robots.txt` 리소스에 대한 캐싱 지시자를 반드시 이해하지는 않는다**는 점을 알고 있어야 한다.

`Cache-Control` 지시자가 없으면 드래프트 명세는 **7일간의 캐싱**을 허용한다. 그러나 실무에서 이것은 대개 너무 길다. `robots.txt`를 모르던 서버 관리자가 로봇의 방문에 대응해 그것을 만드는 경우가 많은데, **`robots.txt`의 부재가 일주일 동안 캐시되면 새로 만든 `robots.txt`가 아무 효과도 없는 것처럼 보이고**, 사이트 관리자는 로봇 관리자가 배제 표준을 지키지 않는다고 비난하게 된다. 여러 대규모 크롤러가 활발히 크롤하는 동안 `robots.txt`를 매일 다시 가져오는 규칙을 쓴다.

### 16.9.4 완전한 예제

Mary's Antiques 사이트의 `robots.txt`를 예로 든다.

```
#####################################################################
# Mary's Antiques 웹 사이트의 robots.txt
#####################################################################

# Suzy의 로봇은 동적 URL을 이해하지 못하므로 전부 막고, 비공개 데이터도
# 막되, Mary가 Suzy를 위해 따로 마련해 둔 작은 구역만 허용한다.

User-Agent: Suzy-Spider
Disallow: /dynamic
Allow: /private/suzy-stuff
Disallow: /private

# Furniture-Finder 로봇은 Mary의 골동품 가구 재고 프로그램을 이해하도록
# 특별히 설계되었으므로 그 리소스는 크롤하게 하되, 다른 동적 리소스와
# 비공개 데이터는 전부 막는다.
```

### 16.9.5 HTML 로봇 제어 META 태그

`robots.txt`는 사이트 관리자가 로봇을 사이트의 일부나 전부에서 배제하게 해 준다. **`robots.txt`의 단점 하나는 그것이 사이트 관리자의 소유이지 개별 콘텐츠 저자의 소유가 아니라는 점이다.**

HTML 페이지 저자에게는 개별 페이지에 대해 로봇을 제한하는 더 직접적인 수단이 있다. HTML 문서에 로봇 제어 태그를 직접 넣는 것이다. 로봇 제어 HTML 태그를 따르는 로봇은 **문서를 가져올 수는 있지만**, 로봇 배제 태그가 있으면 그 문서를 무시한다. 예를 들어 검색 엔진 로봇은 그 문서를 검색 색인에 포함시키지 않는다. `robots.txt` 표준과 마찬가지로 **참여는 권장되지만 강제되지 않는다.**

이 문장을 반드시 붙잡아 둬야 한다. **로봇은 문서를 가져온다.** 태그를 읽으려면 문서를 가져와야 하기 때문이다. 메타 태그는 색인을 막을 뿐 **접근을 막지 않는다.**

로봇 배제 태그는 HTML META 태그로 구현된다.

```html
<META NAME="ROBOTS" CONTENT=directive-list>
```

**표 16-22. 로봇 META 지시자**

| 지시자 | 의미 |
|---|---|
| `NOINDEX` | 페이지 콘텐츠를 처리하지 말고 문서를 무시하라(어떤 색인이나 데이터베이스에도 넣지 말라) |
| `NOFOLLOW` | 페이지에서 나가는 어떤 링크도 크롤하지 말라 |
| `INDEX` | 페이지 콘텐츠를 색인해도 좋다 |
| `FOLLOW` | 페이지의 나가는 링크를 크롤해도 좋다 |
| `NOARCHIVE` | 페이지의 로컬 사본을 캐시하지 말라 |
| `ALL` | `INDEX, FOLLOW`와 동등 |
| `NONE` | `NOINDEX, NOFOLLOW`와 동등 |

`NOARCHIVE`는 Google 검색 엔진을 운영하는 쪽이 도입한 것이다. 웹마스터가 Google이 자기 콘텐츠의 캐시된 페이지를 제공하는 것을 거부할 수 있게 하는 수단이다. `META NAME="googlebot"`과 함께 쓸 수도 있다. 이 지시자가 왜 만들어졌는지는 16.11절에서 분명해진다.

로봇 META 태그는 다른 모든 HTML META 태그와 마찬가지로 HTML 페이지의 `HEAD` 섹션에 나타나야 한다.

```html
<html>
<head>
    <meta name="robots" content="noindex,nofollow">
    <title>...</title>
</head>
<body>
    ...
</body>
</html>
```

*예제 16-15. 로봇 META 태그의 배치*

태그의 `robots`라는 이름과 콘텐츠는 대소문자를 구별하지 않는다. 그리고 **충돌하거나 반복되는 지시자를 지정해서는 안 된다.**

```html
<meta name="robots" content="INDEX,NOINDEX,NOFOLLOW,FOLLOW,FOLLOW">
```

이런 태그의 동작은 정의되어 있지 않으며 로봇 구현마다 확실히 다를 것이다.

로봇 META 태그 외에 검색 엔진을 위한 다른 META 태그들도 있다.

**표 16-23. 그 밖의 META 태그 지시자 (HTTP-DG 표 9-5)**

| `name=` | `content=` | 설명 |
|---|---|---|
| `DESCRIPTION` | `<text>` | 저자가 웹 페이지의 짧은 텍스트 요약을 정의한다. 많은 검색 엔진이 이 태그를 보므로 저자가 적절한 요약을 지정할 수 있다 |
| `KEYWORDS` | `<comma list>` | 웹 페이지를 기술하는 쉼표로 구분된 단어 목록. 키워드 검색을 돕는다 |
| `REVISIT-AFTER` | `<no. days>` | 페이지가 변경될 수 있으므로 지정한 일수 후에 다시 방문하라고 지시한다. 널리 지원되지는 않는다 |

### 16.9.6 그 오용 — `robots.txt`가 실제로 알려 주는 것

지금까지의 서술을 다 읽고 나면 `robots.txt`를 접근 통제 메커니즘으로 착각하기 쉽다. **그것은 접근 통제가 아니다.** 세 가지 이유가 겹쳐 있다.

**첫째, 강제력이 없다.** 이 표준은 명시적으로 자발적이다. 로봇이 `robots.txt`를 요청할 의무도, 그 내용을 따를 의무도 없다. 예의 바른 크롤러는 따르고, 예의 없는 크롤러는 무시하며, **공격자의 스파이더는 따를 이유가 전혀 없다.**

**둘째, 그것은 누구나 읽을 수 있는 공개 파일이다.** `robots.txt`는 정의상 문서 루트에 있고, 인증 없이 `GET`할 수 있어야 하며(그러지 않으면 표 16-19에 따라 사이트 전체가 금지된 것으로 간주된다), 사이트마다 정확히 하나 있고 **위치가 완전히 예측 가능하다.**

**셋째 — 그리고 이것이 결정적이다 — 하위 디렉터리별 파일을 둘 수 없으므로 웹마스터는 통합 파일 하나에 사이트 전체의 배제 규칙을 적어야 한다.** 게다가 접두사 매칭은 표현력이 부족해서 특정 경로를 막으려면 그 경로를 하나하나 나열하는 것 외에 방법이 없을 때가 많다(16.9.3절).

이 세 가지를 합치면 결론은 하나다.

> **`robots.txt`는 "여기를 크롤하지 말라"고 적은 파일이 아니다. "여기에 크롤당하고 싶지 않은 것이 있다"고 공개적으로 적어 둔 파일이다.**

WAHH가 이 역설을 애플리케이션 매핑의 관점에서 그대로 서술한다. 많은 웹 서버가 웹 루트에 `robots.txt`를 두고 있고 거기에는 스파이더나 검색 엔진이 방문하지 않기를 바라는 URL 목록이 들어 있다. **그런데 이 파일은 종종 민감한 기능에 대한 참조를 담고 있으며, 그것은 스파이더링하는 쪽이 반드시 관심을 갖는 대상이다.** 웹 애플리케이션을 공격하기 위해 만들어진 일부 스파이더링 도구는 `robots.txt`를 확인하고 **그 안의 모든 URL을 스파이더링 과정의 씨앗으로 쓴다.** 이 경우 `robots.txt` 파일은 웹 애플리케이션의 보안에 역효과를 낳는다.

WAHH의 예제 애플리케이션에서 `robots.txt`가 참조하는 디렉터리는 `/mdsecportal`과 `/site-old` 두 개였다. **이 둘은 애플리케이션의 어디에서도 링크되어 있지 않으며, 공개된 콘텐츠의 링크만 따라가는 웹 스파이더로는 색인되지 않았을 것이다.** 즉 `robots.txt`가 없었다면 발견되지 않았을 경로를 `robots.txt`가 알려 준 것이다.

디렉터리 이름 두 개가 각각 무엇을 시사하는지도 보라. `/mdsecportal`은 관리 포털일 가능성이 높고, `/site-old`는 **더 이상 유지보수되지 않지만 여전히 동작하는 구버전 애플리케이션**일 가능성이 높다. 구버전은 현재 버전에 없는 취약점을 담고 있을 수 있다(→ 25.3).

이 문제는 이 책에서 반복되는 형태다. **무언가를 숨기려는 조치가 그것의 존재를 알린다.** 12.4.2절이 디렉터리 리스팅에서, 30.1절이 오류 메시지에서, 25.3절이 숨겨진 콘텐츠 발견에서 같은 구조를 다룬다.

### 16.9.7 강화 — 색인 통제와 접근 통제를 구별하기

처방은 개념 하나를 분리하는 데서 나온다.

> **`robots.txt`와 로봇 META 태그는 색인 통제(indexing control)이지 접근 통제(access control)가 아니다.**

**표 16-24. 두 가지를 구별하기**

| | 색인 통제 | 접근 통제 |
|---|---|---|
| 수단 | `robots.txt`, `NOINDEX`, `NOARCHIVE` | 인증, 인가, 네트워크 수준 통제 |
| 대상 | 예의 바른 로봇 | **모든 클라이언트** |
| 강제력 | 없음(자발적) | 있음 |
| 실패 시 | 콘텐츠가 검색 결과에 나타난다 | 콘텐츠가 유출된다 |
| 통제하는 것 | 리소스가 **어디에 나열되는가** | 리소스에 **누가 접근하는가** |

이 구별에서 실무 규칙이 따라 나온다.

1. **비공개 콘텐츠는 인증으로 보호하라.** `robots.txt`의 `Disallow`는 그 콘텐츠를 조금도 보호하지 않는다. 24.1절이 지적하는 "완전히 보호되지 않은 기능"의 전형적인 형태가 **링크되어 있지 않다는 것만으로 보호된다고 믿는 리소스**다. 정적 파일에 대한 접근 통제(→ 24.5)도 여기 포함된다.

2. **`robots.txt`에는 이미 공개된 것만 적어라.** `Disallow`에 적힌 경로는 그 경로가 존재한다는 사실을 공개한다. 검색 결과에 나오는 것이 곤란한 정도의 콘텐츠라면 `robots.txt`가 맞는 도구이고, 노출되면 안 되는 콘텐츠라면 그것은 애초에 인증 뒤에 있어야 한다.

3. **`Disallow` 항목을 가능한 한 일반화하라.** `Disallow: /admin/user-management/bulk-delete.jsp` 대신 `Disallow: /admin`을 쓴다. 접두사 매칭의 성질(표 16-20)상 후자가 전자를 포함한다. 개별 경로를 나열할수록 파일이 사이트 지도가 된다.

4. **로그를 보고 `robots.txt` 요청을 추적하라.** `GET /robots.txt`는 정상적인 브라우저가 보내지 않는 요청이다. 그 요청이 로그에 있다는 것 자체가 자동화된 클라이언트가 방문했다는 신호이며, 그 직후의 요청 패턴을 보면 그 클라이언트가 `robots.txt`를 **따르고 있는지 아니면 그것을 씨앗 목록으로 쓰고 있는지** 구별할 수 있다(→ 16.10).

5. **검색 결과에서 이미 색인된 것을 제거하는 것은 별개의 작업이다.** `robots.txt`에 `Disallow`를 추가해도 **이미 색인된 콘텐츠는 사라지지 않는다.** 오히려 크롤러가 그 페이지를 다시 방문해 상태를 갱신하는 것을 막기 때문에 상황이 더 나빠질 수도 있다. 16.11절이 이 문제를 다룬다.

> **이 절이 뒷받침하는 것**
>
> - `robots.txt`는 강제력 없는 자발적 규약이며 공개된 예측 가능한 위치의 파일이다 → **25.2** (공개 리소스 참조로서의 `robots.txt`), **25.3** (숨겨진 콘텐츠 발견의 씨앗)
> - 링크되어 있지 않다는 것은 보호가 아니다 → **24.1**, **24.5** (보호되지 않은 기능과 정적 리소스)
> - 숨기려는 조치가 존재를 알린다 → **12.4.2**, **30.1** (같은 구조가 나타나는 다른 자리)

## 16.10 오작동하는 로봇과 로봇 에티켓

길 잃은 로봇이 혼란을 일으키는 방식은 여러 가지다. 로봇이 저지를 수 있는 실수와 그 영향을 정리하면 다음과 같다.

**폭주 로봇(runaway robots).** 로봇은 사람이 웹을 서핑할 때보다 훨씬 빠르게 HTTP 요청을 보내고, 대개 빠른 컴퓨터에서 빠른 네트워크 링크로 동작한다. 로봇에 프로그래밍 논리 오류가 있거나 사이클에 갇히면 **웹 서버에 강한 부하를 던질 수 있고, 그것으로 서버를 과부하시켜 다른 모두에게 서비스를 거부하게 만들 수 있다.** 모든 로봇 저자는 폭주 로봇에 대비한 안전장치를 설계에 넣는 데 각별해야 한다.

**낡은 URL.** 어떤 로봇은 URL 목록을 방문한다. 그 목록은 오래된 것일 수 있다. 웹 사이트가 콘텐츠를 크게 바꾸면 로봇이 존재하지 않는 URL을 대량으로 요청하게 된다. 이것은 일부 사이트 관리자를 짜증나게 한다. **오류 로그가 존재하지 않는 문서에 대한 접근 요청으로 채워지는 것도, 오류 페이지를 서비스하는 오버헤드로 웹 서버 용량이 줄어드는 것도 반갑지 않다.**

**길고 잘못된 URL.** 사이클과 프로그래밍 오류의 결과로 로봇이 크고 무의미한 URL을 사이트에 요청할 수 있다. URL이 충분히 길면 **웹 서버의 성능을 떨어뜨리고, 접근 로그를 어지럽히고, 취약한 웹 서버를 죽게 만들 수도 있다.**

**캐묻는 로봇(nosy robots).** 어떤 로봇은 비공개 데이터를 가리키는 URL을 얻어서 **그 데이터를 검색 엔진과 다른 애플리케이션을 통해 손쉽게 접근 가능하게 만들 수 있다.** 데이터 소유자가 그 웹 페이지를 적극적으로 광고하지 않았다면, 그는 이 로봇에 의한 발행을 좋게 봐야 성가신 일로, 나쁘게 보면 프라이버시 침해로 여길 것이다.

이 항목의 세부를 그대로 옮길 값이 있다. **대개 이런 일이 벌어지는 이유는 그 "비공개" 콘텐츠로의 하이퍼링크가 이미 존재했기 때문이다.** 즉 콘텐츠가 소유자가 생각한 만큼 비밀이 아니었거나, 소유자가 기존 하이퍼링크를 제거하는 것을 잊었다. 가끔은 로봇이 명시적 하이퍼링크가 없는데도 디렉터리의 내용을 가져오는 등 지나치게 열성적으로 문서를 긁어모으다가 그렇게 되기도 한다(→ 12.4.2).

웹에서 대량의 데이터를 가져오는 로봇 구현자는 **자기 로봇이 어느 시점엔가 민감한 데이터 — 사이트 구현자가 인터넷을 통해 접근 가능하게 할 의도가 전혀 없었던 데이터 — 를 가져오게 될 가능성이 높다는 점을 알고 있어야 한다.** 이 민감한 데이터에는 비밀번호 파일이나 신용카드 정보까지 포함될 수 있다.

그래서 **지적을 받으면 그 콘텐츠를 무시하고 검색 색인이나 아카이브에서 제거하는 메커니즘이 중요하다.** 악의적인 검색 엔진·아카이브 사용자가 대규모 웹 크롤러의 능력을 익스플로잇해 콘텐츠를 찾아내는 일이 알려져 있다. **Google 같은 일부 검색 엔진은 크롤한 페이지의 표현을 실제로 아카이브하므로, 콘텐츠가 제거되어도 한동안 계속 발견되고 접근될 수 있다.**

이 마지막 문장이 16.11절로 가는 다리다.

**동적 게이트웨이 접근.** 로봇은 자기가 무엇에 접근하고 있는지 항상 아는 것이 아니다. 콘텐츠가 게이트웨이 애플리케이션에서 오는 URL을 가져올 수 있다. 이 경우 얻어진 데이터는 특수 목적일 수 있고 계산 비용이 클 수 있다. 많은 사이트 관리자는 순진한 로봇이 게이트웨이에서 오는 문서를 요청하는 것을 좋아하지 않는다.

### 16.10.1 로봇 에티켓

1993년, 웹 로봇 커뮤니티의 선구자인 Martijn Koster가 웹 로봇 저자를 위한 지침 목록을 작성했다. 일부는 오래되었지만 상당 부분은 여전히 유용하다.

**표 16-25. 웹 로봇 운영자를 위한 지침 (HTTP-DG 표 9-6 기준)**

| 범주 | 지침 | 내용 |
|---|---|---|
| **(1) 식별** | 로봇을 식별하라 | HTTP `User-Agent` 필드로 로봇의 이름을 웹 서버에 알린다. 관리자가 로봇이 무엇을 하는지 이해하는 데 도움이 된다. 일부 로봇은 로봇의 목적과 정책을 설명하는 URL을 `User-Agent` 헤더에 포함한다 |
| | 머신을 식별하라 | DNS 항목이 있는 머신에서 로봇을 돌려서 사이트가 로봇 IP를 역DNS로 호스트명으로 바꿀 수 있게 한다. 관리자가 로봇을 책임지는 조직을 식별하는 데 도움이 된다 |
| | 연락처를 식별하라 | HTTP `From` 필드로 연락 가능한 이메일 주소를 제공한다 |
| **(2) 운영** | 경계하라 | 로봇은 질문과 항의를 만들어 낸다. 일부는 로봇이 잘못 동작해서 생긴다. 로봇이 올바르게 동작하는지 조심스럽게 지켜봐야 한다. 로봇이 24시간 돌아간다면 더 각별해야 한다 |
| | 준비하라 | 큰 로봇 여정을 시작할 때는 조직 내 사람들에게 알린다. 조직은 네트워크 대역폭 소비를 지켜보고 외부 문의에 대비하고 싶어 할 것이다 |
| | 모니터하고 로깅하라 | **로봇에 진단과 로깅을 풍부하게 갖춰야 한다.** 진행을 추적하고 로봇 트랩을 식별하고 모든 것이 제대로 동작하는지 확인할 수 있어야 한다. 문제와 항의는 반드시 생기며, 크롤러 동작의 상세한 로그가 있어야 무슨 일이 있었는지 되짚을 수 있다. 이는 잘못 동작한 크롤러를 디버깅하는 데뿐 아니라 **부당한 항의에 대해 그 동작을 방어하는 데도** 중요하다 |
| | 배우고 적응하라 | 크롤할 때마다 새로운 것을 배운다. 매번 개선되고 흔한 함정을 피하도록 로봇을 적응시킨다 |
| **(3) 자제** | URL로 걸러라 | 이해하지 못하거나 관심 없는 데이터를 가리키는 것으로 보이는 URL은 건너뛴다. `.Z`, `.gz`, `.tar`, `.zip`으로 끝나는 URL은 압축 파일이나 아카이브일 가능성이 높고, `.exe`는 프로그램, `.gif`·`.tif`·`.jpg`는 이미지일 가능성이 높다 |
| | 동적 URL을 걸러라 | 보통 로봇은 동적 게이트웨이의 콘텐츠를 크롤하고 싶어 하지 않는다. 게이트웨이에 질의를 올바르게 만들어 보내는 법을 모르고, 결과는 불규칙하거나 일시적일 가능성이 높다. URL에 `cgi`가 있거나 `?`가 있으면 크롤을 피하는 것이 좋다 |
| | `Accept` 헤더로 걸러라 | HTTP `Accept` 헤더로 어떤 종류의 콘텐츠를 이해하는지 서버에 알린다 |
| | `robots.txt`를 지켜라 | 사이트의 `robots.txt` 통제를 따른다 |
| | 스스로 스로틀하라 | 각 사이트에 대한 접근 횟수와 시각을 세어 어느 사이트도 너무 자주 방문하지 않도록 한다. **로봇이 몇 분보다 자주 사이트에 접근하면 관리자가 의심하기 시작한다. 몇 초마다 접근하면 화를 내기 시작한다. 최대한 빠르게 두들겨 다른 트래픽을 막아 버리면 격노한다.** 일반적으로 로봇을 분당 몇 요청 정도로 제한하고 요청 사이에 몇 초를 두어야 한다. 루프를 방지하기 위해 한 사이트에 대한 총 접근 횟수도 제한해야 한다 |
| **(4) 루프·중복 감내** | 모든 반환 코드를 다뤄라 | 리다이렉트와 오류를 포함한 모든 HTTP 상태 코드를 다룰 준비를 해야 한다. 그 코드들을 로깅하고 모니터해야 한다. **한 사이트에서 비성공 결과가 대량으로 나오면 조사해야 한다.** URL이 대량으로 낡았거나 서버가 로봇에게 문서 서비스를 거부하는 것일 수 있다 |
| | URL을 정규화하라 | 모든 URL을 표준 형태로 정규화해 흔한 별칭을 제거한다 |
| | 사이클을 적극적으로 피하라 | 사이클 탐지와 회피에 매우 열심히 임한다. 크롤 운영을 피드백 루프로 다룬다. 문제와 그 해결의 결과를 다음 크롤에 반영해 반복할 때마다 크롤러를 개선한다 |
| | 트랩을 감시하라 | 어떤 종류의 사이클은 의도적이고 악의적이며, 탐지하기 어렵게 만들어져 있을 수 있다. **이상한 URL로 한 사이트에 대량 접근이 발생하는 것을 감시한다. 그것이 트랩일 수 있다** |
| | 블랙리스트를 유지하라 | 트랩, 사이클, 망가진 사이트, 로봇이 오지 않기를 바라는 사이트를 발견하면 블랙리스트에 넣고 다시 방문하지 않는다 |
| **(5) 확장성** | 공간을 이해하라 | 얼마나 큰 문제를 푸는지 미리 계산한다. 웹의 규모 때문에 필요한 메모리 양에 놀랄 수 있다 |
| | 대역폭을 이해하라 | 가용 네트워크 대역폭과 필요한 양을 이해하고 실제 사용량을 모니터한다. **나가는 대역폭(요청)이 들어오는 대역폭(응답)보다 훨씬 작다는 것을 알게 될 것이다.** 네트워크 사용을 모니터하면 TCP 커넥션을 더 잘 활용해 로봇을 최적화할 여지도 찾을 수 있다(→ 9.6) |
| | 시간을 이해하라 | 작업 완료에 걸릴 시간을 이해하고 진행이 추정과 맞는지 확인한다. 크게 어긋나면 조사할 문제가 있을 가능성이 높다 |
| | 나누어 정복하라 | 대규모 크롤에는 하드웨어를 더 투입해야 한다. 다중 네트워크 카드를 가진 대형 다중 프로세서 서버를 쓰거나 여러 작은 컴퓨터를 함께 돌린다 |
| **(6) 신뢰성** | 철저히 테스트하라 | 세상에 풀어놓기 전에 내부에서 철저히 테스트한다. 외부 테스트 준비가 되면 작은 처녀항해를 몇 번 먼저 돌린다. 결과를 많이 모아 성능과 메모리 사용을 분석하고 큰 문제로 확장했을 때를 추정한다 |
| | 체크포인트를 두라 | 진지한 로봇이라면 진행 상황의 스냅샷을 저장하고 실패 시 거기서 재시작할 수 있어야 한다. **실패는 반드시 일어난다.** 소프트웨어 버그가 있을 것이고 하드웨어가 고장 날 것이다. 처음부터 체크포인트·재시작 기능을 설계에 넣는다 |
| | 장애에 견디도록 하라 | 실패를 예상하고 실패가 일어나도 진행을 계속할 수 있도록 로봇을 설계한다 |
| **(7) 공보** | 준비하라 | 로봇은 여러 사람을 언짢게 만들 것이다. 그들의 문의에 빠르게 응답할 준비를 한다. 로봇을 설명하는 웹 페이지 정책 성명을 만들고 `robots.txt` 작성법의 상세한 안내를 포함한다 |
| | 이해하라 | 연락해 오는 사람 중 일부는 잘 알고 있고 우호적이다. 다른 이들은 순진하다. 몇몇은 유별나게 화가 나 있다. **로봇 사업의 중요성을 논하는 것은 일반적으로 생산적이지 않다.** Robots Exclusion Standard를 설명하고, 그래도 불만이면 그 URL을 즉시 크롤에서 제거하고 블랙리스트에 넣는다 |
| | 응답하라 | 불만인 웹마스터 대부분은 로봇에 대해 잘 모를 뿐이다. **즉시 전문적으로 응답하면 불만의 90%가 빠르게 사라진다.** 반면 며칠씩 기다리면서 로봇이 계속 그 사이트를 방문하면 목소리 크고 화난 반대자를 얻게 된다 |

이 표에서 (2)와 (4)의 항목들을 다시 보라. **모니터·로깅·경보에 대한 요구가 16.5절이 서버 쪽에서 서술한 것과 구조적으로 동일하다.** 자기가 무엇을 했는지 기록해 두지 않으면 문제를 진단할 수도, 부당한 비난을 반박할 수도 없다는 것이 양쪽에서 같은 결론이다.

### 16.10.2 방어자의 관점 — 로그에서 로봇을 구별하기

이 장의 앞부분과 뒷부분이 만나는 지점이 여기다. **접근 로그에 남은 요청 중 어느 것이 로봇의 것인가.**

가장 먼저 떠오르는 답 — `User-Agent`를 보는 것 — 이 가장 신뢰할 수 없는 답이다. `User-Agent`는 클라이언트가 쓰는 문자열이며 아무 강제력이 없다(→ 8.6). 예의 바른 로봇은 자기를 정확히 밝히고, 그렇지 않은 로봇은 브라우저를 흉내 낸다. **`User-Agent` 기반 판정은 협조적인 로봇만 걸러낸다.**

여러 신호를 조합해야 한다.

**표 16-26. 로봇을 시사하는 로그 상의 신호**

| 신호 | 근거 | 위조 가능성 |
|---|---|---|
| `User-Agent`가 알려진 로봇 이름 | 자발적 식별(표 16-17) | 높음(자유 문자열) |
| `From` 헤더의 존재 | 로봇 에티켓의 권장 사항 | 높음. 다만 **브라우저는 이 헤더를 보내지 않는다** |
| `GET /robots.txt` 요청 | 브라우저는 이 요청을 하지 않는다 | 낮음 — 요청 사실 자체는 위조할 수 없다 |
| HTTP/1.0 요청 라인 | 많은 로봇이 최소 HTTP만 구현한다 | 낮음 |
| `Referer` 없이 깊은 경로에 직접 접근 | 링크를 따라온 것이 아니다 | 중간 |
| 정적 자산(이미지·CSS·JS)을 함께 요청하지 않음 | 로봇은 HTML만 가져오는 경우가 많다 | 중간 |
| 요청률과 요청 간격의 규칙성 | 사람은 일정한 간격으로 클릭하지 않는다 | 중간(의도적으로 흩뜨릴 수 있다) |
| 역DNS로 조회한 호스트명 | 에티켓 (1)의 "머신을 식별하라" | 낮음 — 다만 **모든 로봇이 DNS 항목을 갖지는 않는다** |
| 넓이 우선 패턴의 경로 탐색 | 크롤러의 스케줄링 방식 | 중간 |

세 번째 행이 특히 유용하다. **`GET /robots.txt`는 로봇의 자기 신고가 아니라 로봇의 행동이다.** 그리고 그 직후의 요청을 보면 그 클라이언트가 `robots.txt`의 `Disallow` 항목을 **피하고 있는지 아니면 그것을 우선적으로 방문하고 있는지** 구별할 수 있다. 후자는 예의 바른 크롤러의 행동이 아니다. 16.9.6절이 서술한 씨앗 목록 사용의 흔적이며, **애플리케이션 매핑이 진행 중이라는 강한 신호**다.

이것을 16.5.3절의 경보 메커니즘에 연결하면 실행 가능한 규칙이 된다. `robots.txt`를 가져간 직후 그 안의 `Disallow` 경로들을 순서대로 요청하는 클라이언트는 이상 징후의 정의에 정확히 부합한다.

다만 여기에도 한계가 있다. **어느 신호도 결정적이지 않다.** 여러 신호가 겹칠 때 확신이 커지는 종류의 판정이며, 그래서 이 판정을 근거로 자동 차단을 걸면 오탐의 대가를 치른다. 16.5.5절이 서술한 점진적 반응 — 응답을 느리게 하거나 세션을 종료하는 것 — 이 이 불확실성에 맞는 대응 형태다.

### 16.10.3 트랩의 양면

로봇 트랩에 대해 마지막으로 짚어 둘 것이 있다. 16.8.4절은 트랩을 두 가지로 서술했다. **악의적인 웹마스터가 의도적으로 만든 것**과 **선의의 웹마스터가 심볼릭 링크나 동적 콘텐츠로 의도치 않게 만든 것**이다.

방어자의 입장에서 이 구별은 중요하다. **의도적으로 로봇 트랩을 놓는 것은 무차별 크롤링에 대한 방어 수단으로 제안되곤 하지만, 그것은 협조적인 로봇을 우선적으로 해친다.** 예의 바른 크롤러는 `robots.txt`를 따르고 스로틀링을 하고 사이클 탐지를 하므로 트랩에서 비교적 빨리 빠져나온다. 반면 악의적인 스크립트는 애초에 그 사이트의 콘텐츠에만 관심이 있고 무한 공간을 크롤할 이유가 없다.

그리고 **의도치 않은 트랩은 자기 사이트의 문제다.** 심볼릭 링크 사이클(그림 16-2)이나 무한 달력은 로봇만 괴롭히는 것이 아니라 **자기 서버의 자원을 소모하고 접근 로그를 오염시킨다.** 로봇의 반복 요청으로 로그가 부풀면 16.5절이 요구한 사후 재구성이 그만큼 어려워지고, 16.7절이 지적한 디스크 가득 참 문제가 현실이 된다.

즉 **로봇 위생은 로그 위생의 일부다.** 이 장의 두 절반이 여기서 만난다.

> **이 절이 뒷받침하는 것**
>
> - 로봇은 비공개 데이터를 가리키는 링크가 이미 존재했기 때문에 그것을 색인한다 → **16.11**, **25.3** (그 색인이 공격자에게 무엇이 되는가)
> - `User-Agent`는 자기 신고이고 `GET /robots.txt`는 행동이다 → **8.6**, **16.5** (신뢰할 수 없는 값과 관측 가능한 행동의 구별)
> - 검색 엔진은 크롤한 페이지의 표현을 아카이브하므로 제거된 콘텐츠도 한동안 접근 가능하다 → **16.11**, **25.2**

## 16.11 검색 엔진과 공개 리소스를 통한 정찰

가장 널리 퍼진 웹 로봇은 인터넷 검색 엔진의 것이다. 검색 엔진은 사용자가 전 세계의 어떤 주제에 관한 문서든 찾을 수 있게 해 준다. 오늘날 웹에서 가장 인기 있는 사이트 상당수가 검색 엔진이다. 많은 웹 사용자에게 출발점이 되고, 관심 있는 정보를 찾게 해 주는 값진 서비스를 제공한다.

웹 크롤러는 웹에 존재하는 문서를 가져와서 어떤 단어가 어떤 문서에 나타나는지의 색인을 만들 수 있게 함으로써 검색 엔진에 먹이를 준다. 이 책의 뒤에 있는 색인과 같은 원리다.

이 절은 그 메커니즘을 서술한 뒤, **같은 메커니즘이 공격자에게 무엇이 되는지**를 다룬다.

### 16.11.1 규모

웹이 초기일 때 검색 엔진은 사용자가 웹의 문서를 찾도록 돕는 비교적 단순한 데이터베이스였다. 오늘날 수십억 페이지에 접근 가능한 상황에서 검색 엔진은 필수적인 존재가 되었고, 웹의 순전한 규모를 다루기 위해 진화하면서 상당히 복잡해졌다.

프로덕션 웹 크롤러의 과업을 생각해 보자. 검색 색인에 필요한 페이지를 가져오려면 수십억 건의 HTTP 질의를 보내야 한다. 각 요청이 완료되는 데 0.5초가 걸린다면(어떤 서버에는 느리고 어떤 서버에는 빠른 값이다), 10억 문서에 대해 다음과 같다.

```
0.5초 × 1,000,000,000 / (60초/분 × 60분/시 × 24시/일) ≈ 5,700일
```

**요청을 순차적으로 보내면 약 5,700일이 걸린다.** 대규모 크롤러가 요청을 병렬화하고 여러 대의 머신을 동원해야 하는 이유가 이 계산에 있다. 그럼에도 웹 전체를 크롤하려는 시도는 규모 때문에 여전히 벅찬 도전이다.

### 16.11.2 현대 검색 엔진의 구조

오늘날의 검색 엔진은 전 세계 웹 페이지와 그 내용에 대한 복잡한 로컬 데이터베이스 — **전문 색인(full-text index)** — 를 만든다. 이 색인은 웹의 모든 문서에 대한 일종의 카드 목록 역할을 한다.

```
   사용자 ─┐                                              ┌─ 웹 서버
   사용자 ─┤   웹 검색     전문 색인      검색 엔진        ├─ 웹 서버
   사용자 ─┤   게이트웨이   데이터베이스   크롤러/인덱서    ├─ 웹 서버
   사용자 ─┘                                              └─ 웹 서버

        ← 질의 엔진 →                    ← 크롤링과 색인 →
```

*그림 16-6. 프로덕션 검색 엔진은 협력하는 크롤러와 질의 게이트웨이로 구성된다 (HTTP-DG 그림 9-7 기준)*

검색 엔진 크롤러가 웹 페이지를 모아 와서 전문 색인에 추가한다. 동시에 검색 엔진 사용자는 웹 검색 게이트웨이를 통해 전문 색인에 질의를 던진다.

**웹 페이지는 끊임없이 바뀌고, 웹의 큰 부분을 크롤하는 데는 시간이 걸리므로, 전문 색인은 잘해야 웹의 스냅샷이다.** 이 문장이 이 절 후반부의 핵심이다.

**전문 색인**은 단어를 받으면 그 단어를 담고 있는 모든 문서를 즉시 알려 주는 데이터베이스다. 색인이 만들어진 뒤에는 문서 자체를 스캔할 필요가 없다.

**질의와 결과.** 사용자가 웹 검색 엔진 게이트웨이에 질의를 던지면, HTML 폼이 브라우저를 통해 `GET`이나 `POST` 요청으로 게이트웨이에 전송된다. 게이트웨이 프로그램은 검색 질의를 추출해 웹 UI 질의를 전문 색인 검색에 쓰이는 표현으로 변환한다.

```
[요청] GET /search.html?query=drills HTTP/1.1
       Host: www.joes-hardware.com
       Accept: *
       User-agent: ShopBot

[응답] HTTP/1.1 200 OK
       Content-type: text/html
       <HTML><HEAD><TITLE>Search Results</TITLE>
       <A HREF=/BD.html>Black and Decker Drills</A>[...]
```

*그림 16-7. 검색 질의 요청의 예 (HTTP-DG 그림 9-9 기준)*

주어진 단어를 담은 웹 페이지가 많을 수 있으므로 검색 엔진은 결과의 순위를 매기는 영리한 알고리즘을 배치한다. 검색 결과 목록을 어떤 순서로 제시할지 알아야 사용자에게 가장 관련성 높은 결과를 보여 줄 수 있기 때문이다. 이것을 **관련도 순위(relevancy ranking)** 라 한다.

이 과정을 돕기 위해 큰 검색 엔진들은 **웹을 크롤하는 동안 수집한 인구 조사 데이터를 실제로 활용한다.** 예를 들어 주어진 페이지를 가리키는 링크가 몇 개인지 세면 그 페이지의 인기를 판단하는 데 도움이 되고, 그 정보로 결과 제시 순서에 가중치를 줄 수 있다. 검색 엔진이 쓰는 알고리즘, 크롤링에서 얻은 요령, 그 밖의 기법들은 그들이 가장 철저히 지키는 비밀에 속한다.

**스푸핑.** 사용자는 검색 질의의 첫 몇 결과에서 원하는 것을 보지 못하면 좌절하는 경우가 많으므로 **검색 결과의 순서는 사이트를 발견하는 데 중요하다.** 그래서 웹마스터는 자기 사이트를 가장 잘 기술한다고 생각하는 단어에 대해 결과 섹션 상단에 자기 사이트가 나오게 하려는 강한 유인을 갖는다.

### 16.11.3 색인은 스냅샷이며, 원본이 사라져도 남는다

여기까지가 검색 엔진의 메커니즘이다. 이제 방향을 바꾼다.

16.10절의 "캐묻는 로봇" 항목이 두 가지를 서술했다.

1. 로봇이 비공개 데이터를 색인하는 일은 대개 **그 콘텐츠로의 하이퍼링크가 이미 존재했기 때문**에 일어난다.
2. **일부 검색 엔진은 크롤한 페이지의 표현을 아카이브하므로, 콘텐츠가 제거되어도 한동안 계속 발견되고 접근될 수 있다.**

이 두 문장을 앞 절의 "전문 색인은 잘해야 웹의 스냅샷이다"와 합치면 공격자의 도구가 완성된다.

> **애플리케이션이 지금 링크하지 않는 콘텐츠와 기능이, 과거에는 링크되어 있었을 수 있다. 그 경우 여러 역사적 저장소가 여전히 그 숨겨진 콘텐츠에 대한 참조를 갖고 있을 가능성이 높다.**

WAHH가 이 목적에 유용한 공개 리소스를 두 종류로 나눈다.

**검색 엔진.** Google, Yahoo, MSN 같은 검색 엔진은 강력한 스파이더가 발견한 모든 콘텐츠에 대한 세밀한 색인을 유지하며, **그 콘텐츠 상당 부분의 캐시된 사본도 유지한다. 그 사본은 원본 콘텐츠가 제거된 뒤에도 존속한다.**

**웹 아카이브.** `www.archive.org`의 WayBack Machine 같은 아카이브는 다수의 웹 사이트에 대한 역사적 기록을 유지한다. 많은 경우 사용자가 주어진 사이트를 **여러 해 전 특정 날짜에 존재했던 모습 그대로 완전히 복제된 스냅샷으로 열람할 수 있게 한다.**

과거에 링크되었던 콘텐츠 외에, 이 리소스들은 **제3자 사이트에서는 링크되지만 대상 애플리케이션 자체에서는 링크되지 않는 콘텐츠에 대한 참조**도 담고 있을 가능성이 높다. 예를 들어 일부 애플리케이션은 비즈니스 파트너를 위한 제한된 기능을 갖는데, **그 파트너가 애플리케이션 자신은 하지 않는 방식으로 그 기능의 존재를 드러낼 수 있다.**

### 16.11.4 공격자가 실제로 하는 일

WAHH가 서술하는 절차는 다음과 같다. 이 책은 25.2절에서 이것을 애플리케이션 매핑의 한 단계로 다시 다루므로, 여기서는 **그것이 검색 엔진의 어떤 성질에 기대고 있는지**에 초점을 둔다.

1. **여러 검색 엔진과 웹 아카이브를 사용해** 대상 애플리케이션에 대해 무엇이 색인되거나 저장되어 있는지 알아낸다. 엔진마다 크롤한 시점과 범위가 다르므로 결과도 다르다.

2. **고급 검색 연산자를 쓴다.**

   - `site:www.target.com` — 검색 엔진이 참조를 갖고 있는 대상 사이트 내부의 모든 리소스를 반환한다.
   - `site:www.target.com login` — `login`이라는 표현을 담은 모든 페이지를 반환한다. **크고 복잡한 애플리케이션에서 사이트맵, 비밀번호 재설정 기능, 관리 메뉴 같은 흥미로운 리소스로 빠르게 좁혀 들어가는 데 쓸 수 있다.**
   - `link:www.target.com` — 대상으로의 링크를 담은 다른 사이트의 모든 페이지를 반환한다. **오래된 콘텐츠로의 링크나 파트너 링크처럼 제3자 전용으로 의도된 기능으로의 링크가 포함될 수 있다.**
   - `related:www.target.com` — 대상과 "유사한" 페이지를 반환한다. 관련 없는 자료가 많이 섞이지만, 다른 사이트에서 대상을 논한 내용이 있을 수 있다.

3. **각 검색을 웹 섹션뿐 아니라 다른 섹션에서도 수행한다.** 그룹이나 뉴스 섹션은 다른 결과를 담을 수 있다.

4. **주어진 질의의 마지막 결과 페이지로 가서 생략된 결과를 포함해 다시 검색한다.** 기본적으로 검색 엔진은 충분히 유사하다고 판단한 페이지를 제거해 중복 결과를 걸러 낸다. 이 동작을 무시하면 **미묘하게 다른 페이지들이 드러날 수 있다.**

5. **흥미로운 페이지의 캐시된 버전을 본다.** 실제 애플리케이션에 더 이상 존재하지 않는 콘텐츠도 포함된다. **어떤 경우에는 검색 엔진 캐시가 인증이나 결제 없이는 애플리케이션에서 직접 접근할 수 없는 리소스를 담고 있다.**

6. **같은 조직에 속한 다른 도메인 이름에 대해 같은 질의를 수행한다.** 대상 애플리케이션에 대한 유용한 정보를 담고 있을 수 있다.

이 목록에서 5번을 다시 읽어야 한다. **인증 뒤에 있는 콘텐츠가 검색 엔진 캐시에는 인증 없이 존재할 수 있다.** 그 이유는 두 가지다. 크롤러가 방문한 시점에 그 리소스가 인증 뒤에 있지 않았거나(설정 변경, 배포 사고), 혹은 애초에 접근 통제가 링크의 부재에만 의존하고 있었기 때문이다(→ 24.1).

연구를 통해 메인 애플리케이션에서 더 이상 링크되지 않는 오래된 콘텐츠와 기능을 발견했다면, **그것이 여전히 존재하고 사용 가능할 수 있다. 그 오래된 기능은 다른 곳에는 없는 취약점을 담고 있을 수 있다.**

오래된 콘텐츠가 라이브 애플리케이션에서 제거된 경우에도, 검색 엔진 캐시나 웹 아카이브에서 얻은 콘텐츠는 **여전히 라이브 애플리케이션에 존재하며 공격에 쓸 수 있는 다른 기능에 대한 참조나 단서를 담고 있을 수 있다.**

**개발자 포럼.** 대상 애플리케이션에 대한 유용한 정보의 또 다른 공개 출처는 개발자와 다른 이들이 인터넷 포럼에 올린 글이다. 소프트웨어 설계자와 프로그래머가 기술적 질문을 주고받는 포럼은 많다. 거기 올라온 항목들은 **사용 중인 기술, 구현된 기능, 개발 중에 부딪힌 문제, 알려진 보안 버그, 문제 해결을 돕기 위해 제출된 설정 파일과 로그 파일, 심지어 소스 코드의 발췌**까지 담고 있는 경우가 많다.

"문제 해결을 돕기 위해 제출된 로그 파일"이라는 항목을 보라. **이 장의 앞부분 전체가 여기서 되돌아온다.** 16.4절이 로그에 무엇이 들어가는지를, 16.6절이 검증되지 않은 문자열과 도메인 객체가 어떻게 로그에 들어가는지를 서술했다. 그 로그가 도움을 구하는 개발자에 의해 공개 포럼에 붙여진다. **로그의 이중성이 조직 밖으로 확장되는 마지막 경로다.**

### 16.11.5 방어자의 몫

이 절이 서술한 것 전부가 방어자에게 두 가지 작업을 남긴다.

**첫째, 무엇이 색인되었는지 아는 것은 방어자의 일이다.** 공격자가 `site:` 질의로 알아낼 수 있는 것은 방어자도 알아낼 수 있다. 그리고 방어자에게는 그것을 **정기적으로** 할 이유가 있다. 배포 사고로 잠깐 노출된 리소스, 폐기했다고 생각한 구버전 애플리케이션, 파트너가 공개한 제한된 기능의 URL — 이것들은 내부 자산 목록에는 없고 검색 결과에는 있다.

**둘째, 색인에서 제거하는 것과 접근을 막는 것은 다른 작업이다.** 16.9.7절의 구별이 여기서 다시 필요하다.

**표 16-27. 노출된 리소스를 발견했을 때의 조치**

| 조치 | 하는 일 | 하지 않는 일 |
|---|---|---|
| `robots.txt`에 `Disallow` 추가 | 앞으로의 크롤을 막는다(협조하는 로봇에 한해) | **이미 색인된 것을 제거하지 않는다.** 오히려 크롤러가 재방문해 상태를 갱신하는 것을 막을 수 있다. 그리고 그 경로를 공개한다(16.9.6절) |
| `NOINDEX` 메타 태그 | 크롤러가 다음에 방문했을 때 색인에서 빼도록 요청한다 | 접근을 막지 않는다. 그리고 **크롤러가 그 페이지를 다시 방문해야** 효과가 있다 |
| `NOARCHIVE` 메타 태그 | 캐시된 사본 제공을 거부하도록 요청한다 | 색인 자체는 막지 않는다. 이미 만들어진 아카이브에는 소급되지 않는다 |
| 검색 엔진의 제거 요청 절차 | 색인에서 제거한다 | 다른 검색 엔진과 웹 아카이브에는 적용되지 않는다 |
| **인증·인가를 적용한다** | **접근을 실제로 막는다** | 이미 유출된 콘텐츠를 회수하지 못한다 |
| **리소스를 실제로 제거한다** | 라이브 애플리케이션에서 그것을 없앤다 | 캐시와 아카이브의 사본을 없애지 못한다 |

마지막 두 행이 유일하게 강제력이 있는 조치이고, 그 둘조차 **이미 나간 것을 회수하지는 못한다.** 이것이 16.10절의 "캐묻는 로봇" 항목이 말한 것의 실무적 귀결이다. 노출은 되돌릴 수 없고, 되돌릴 수 없으므로 **처음부터 노출되지 않게 하는 것 외에 답이 없다.**

이 결론은 이 장의 앞부분과 정확히 같다. 16.4절이 로그에 대해 같은 말을 했다. 로그에 한 번 들어간 민감 정보는 그 로그의 모든 사본에서 지워야 지워지고, 로그의 사본이 몇 개인지는 대개 아무도 모른다.

> **이 절이 뒷받침하는 것**
>
> - 검색 엔진 색인과 웹 아카이브는 원본이 사라진 뒤에도 존속한다 → **25.2** (공개 리소스 참조를 정찰의 한 단계로 다룸)
> - 지금 링크되지 않는 것이 과거에 링크되어 있었을 수 있다 → **25.3** (숨겨진 콘텐츠 발견)
> - 개발자 포럼에 제출된 설정·로그 파일이 정보원이 된다 → **30.2** (공개 정보 활용), **16.4** (그 로그에 무엇이 들어 있는가)

## 이 장의 요약

- **로그는 방어 자산이면서 동시에 누출 경로다.** 침해를 사후에 재구성할 수 있는 유일한 근거이면서, 침해가 일어났을 때 공격자가 가장 먼저 찾는 대상이기도 하다. 이 이중성은 해소되지 않으며 다만 세 축 — 무엇을, 어떻게, 어디에 기록하는가 — 으로 분해될 뿐이다.

- **로그 필드의 상당수는 클라이언트가 쓴 문자열이다.** 요청 라인, `Referer`, `User-Agent`가 그렇다. 클라이언트 IP조차 커넥션의 출발지일 뿐 사람이 아니며, NAT와 프록시와 full NAT 로드 밸런서를 거치면서 그 의미가 계속 약해진다. 로그를 증거로 쓰려면 어느 필드가 어느 주체가 만든 값인지 알아야 한다.

- **표준 로그 포맷은 줄 단위이고 공백으로 필드를 구분하며 일부 필드를 따옴표로 감싼다.** 구분자가 데이터와 같은 채널에 있으므로, 데이터를 통제하는 자가 로그 파일의 구조를 통제한다. 응답 분할(8.7)과 본문 경계 혼동(10.4)에서 본 것과 정확히 같은 구조다.

- **캐시는 원 서버의 로그에 구멍을 뚫는다.** Hit Metering은 그 구멍을 메우려는 제안이었으나 배포되지 않았다. 그 결과 경로 위에 로그를 남기는 주체가 여럿이고 아무도 전체를 보지 못한다. 완전한 재구성은 여러 곳의 로그를 시각으로 맞춰 합쳐야만 가능하다.

- **방어를 위해 더 많이 기록할수록 누출 시 피해가 커진다.** 감사 로그가 요구하는 세 항목 — 시각, IP 주소, 인증된 계정 — 이 정확히 프라이버시 위험이 가장 큰 세 항목이다. "혹시 필요할지 모르니 전부 기록한다"는 결정 하나가 유출되는 날 유출되는 것의 목록을 결정한다.

- **실시간 경보는 애플리케이션의 입력 검증과 통합될 때 가장 정확하다.** 범용 제품의 규칙은 필연적으로 일반적이며, 많은 공격에서 공격자의 요청은 정상 사용자의 요청과 문자 그대로 동일하다. 그것을 악의적으로 만드는 것은 정황이고, 정황을 아는 것은 애플리케이션 자신뿐이다.

- **검증되지 않은 문자열은 두 가지 사고를 만든다.** 로그 인젝션은 공격자가 로그 파일에 없던 줄을 만들거나 로그 파서·뷰어를 익스플로잇하게 하고, 암묵적 데이터 누출은 도메인 모델이 진화할 때 아무도 결정하지 않은 필드가 로그에 쌓이게 한다. 전자는 도메인 프리미티브로, 후자는 명시적 접근자와 읽기 1회 객체로 다룬다.

- **파일은 로그의 잘못된 자리다.** 로그는 항상 접근 가능해야 하고 동시에 잠겨 있어야 한다는 모순을 안고 있는데, 디스크 파일은 기밀성(내려받으면 IAM이 무력화됨), 무결성(쓰기 주체를 제한하기 어려움), 가용성(상태, 디스크 크기, 로테이션의 함정) 세 축 모두에서 이 요구를 만족시키지 못한다.

- **`robots.txt`는 접근 통제가 아니라 색인 통제다.** 강제력이 없고, 위치가 완전히 예측 가능한 공개 파일이며, 하위 디렉터리별 파일을 둘 수 없으므로 사이트 전체의 배제 규칙을 한 곳에 나열해야 한다. 그 결과 그것은 "여기를 크롤하지 말라"가 아니라 **"여기에 크롤당하고 싶지 않은 것이 있다"고 공개적으로 적어 둔 파일**이 된다.

- **링크되어 있지 않다는 것은 보호가 아니다.** 로봇이 비공개 데이터를 색인하는 일은 대개 그 콘텐츠로의 링크가 이미 어딘가에 존재했기 때문에 일어난다. 그리고 검색 엔진 색인과 웹 아카이브는 원본이 제거된 뒤에도 존속하므로, **노출은 되돌릴 수 없다.**

## 이어지는 장

이 장은 Part III를 닫는다. 12장부터 여기까지가 다룬 것은 하나의 문장으로 압축된다. **요청 하나가 클라이언트에서 애플리케이션 코드까지 가는 동안 그것을 파싱하고 다시 직렬화하는 프로세스의 개수가 곧 공격 표면이다.** 이 장은 그 목록에 마지막 항목을 더했다. **그 프로세스들이 각자 남기는 기록, 그리고 그 기록을 읽어 가는 주체들.**

그리고 Part III 전체가 한 가지를 계속 미뤄 뒀다. **경로 위의 모든 중간자가 메시지를 읽을 수 있다는 전제다.** 프록시가 헤더를 고쳐 쓸 수 있는 것도(13장), 캐시가 응답 본문을 저장할 수 있는 것도(14장), 로드 밸런서가 `Host` 헤더를 보고 목적지를 정하는 것도(15장), 프록시 로그에 URL 전체가 남는 것도(16.2절) 전부 같은 전제에 기대고 있다. **평문이기 때문에 가능한 일들이다.**

**Part IV가 그 전제를 뒤집는다.** 17장이 암호학의 기초와 디지털 인증서를 다루면서 "이 통신 상대가 자기가 주장하는 그 사람인가"라는 질문에 답하는 방법을 세우고, 18장이 HTTPS 핸드셰이크의 실제 절차와 클라이언트가 무엇을 검증하는지를 다룬다. 19장이 그 위에서 재개·성능·중간자 문제를 다룬다.

그때 이 장의 내용 중 상당수가 다시 나타난다. TLS가 켜지면 **경로 위의 프록시는 URL을 로그에 남길 수 없다.** 대신 목적지 호스트명은 여전히 노출되고(→ 18.6), 트래픽의 크기와 타이밍은 그대로 관찰된다(→ 1.2). 즉 **로그의 위치가 이동할 뿐 로그가 사라지지는 않는다.** 프록시 로그에 남던 것이 이제 TLS를 종료하는 지점의 로그에 남고, 그 지점은 대개 조직 안에 있다. 16.4절의 표 16-11을 TLS 종료 지점의 관점에서 다시 읽으면 그 목록이 그대로 살아 있음을 알게 된다.

**Part V가 이 장의 16.4절과 16.5절을 인증·세션의 언어로 이어받는다.** 20.2절이 클라이언트 IP로 식별하려는 시도를, 23.3절이 로그에 남은 세션 토큰을, 22.8절과 23.6절이 로그·모니터·경보를 각각 다룬다. 이 장이 "무엇이 로그에 남는가"를 서술했다면, 그곳은 "그렇게 남은 것으로 무엇을 할 수 있는가"를 서술한다.

**Part VI가 이 장의 16.9절과 16.11절을 공격자의 방법론으로 다시 쓴다.** 25.2절이 공개 리소스 참조를, 25.3절이 숨겨진 콘텐츠 발견을 다루면서 `robots.txt`와 검색 엔진 캐시와 웹 아카이브를 정찰 도구로 배치한다. 이 장이 그 도구들이 **왜 그렇게 동작하는가**를 서술했으므로, 그곳의 절차는 설명 없이 읽힌다.

**마지막으로 Part IX가 이 장의 세 처방을 설계의 언어로 옮긴다.** 44.5절이 읽기 1회 객체를, 46.4절이 서비스로서의 로깅을, 47.3절이 레거시 코드에서 검증되지 않은 문자열 로깅과 암묵적 데이터 누출을 식별하는 방법을, 47.11절이 마이크로서비스 환경에서 집계 로그의 무결성과 도메인 지향 로거 API를 다룬다. 이 장이 남긴 가장 무거운 문장을 그곳이 받는다. **로그에 무엇이 들어가는지는 로깅 코드가 아니라 타입이 결정한다.**

> 16.6절: SBD 12장(Guidance in legacy code)의 12.3 "Logging unchecked strings" 전체 — "문자열을 로깅하지 않는 것과 검증되지 않은 문자열을 로깅하는 것 사이에는 큰 차이가 있다"는 논증과 "검증되지 않은 문자열은 많은 공격 벡터의 근원"이라는 평가, 12.3.1의 리스트 12.6과 그 분석(도메인 규칙이 있는 ID를 `String`으로 표현한 결정, "공격자가 `String`의 규칙에 맞는 무엇이든 넣을 수 있다"와 1억 자·스크립트 예시, 2차 인젝션과 로그 파싱 도구의 약점), **"검증되지 않은 사용자 입력을 절대 로깅하지 말라"는 WARNING**, 12.3.2의 리스트 12.7과 암묵적 데이터 누출 분석(도메인 모델 진화로 민감 필드가 추가되는 시나리오, "큰 시스템에서 데이터가 어떻게 소비되는지 추적하는 것은 사실상 불가능하다", "예방은 어렵지만 탐지는 어렵지 않다"와 읽기 1회 객체 패턴), `+` 연산자가 `toString`을 암묵적으로 호출한다는 지적과 재정의하지 않았을 때의 동작·`toString`이 자주 재정의되는 이유·리플렉션으로 모든 필드를 동적 추출하는 관행과 그로 인한 누출, **두 개의 TIP("민감한 값이 접근될 수 있는 횟수를 항상 제한하라", "로그에 담고 싶은 데이터는 항상 명시적 접근자로 꺼내라")**. 예제 16-7~16-10은 SBD의 식당 예약 예제(`TableReservation`, `reservationId`)를 이 책의 도메인 실행 예제인 온라인 서점(`Order`, `orderId`)으로 옮긴 것이며, 코드의 구조와 각 줄이 드러내는 문제는 원서와 동일하다.
