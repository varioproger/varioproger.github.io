# 13장. 프록시, 게이트웨이, 터널: 중간자의 구조

> **이 장에서 다루는 것**
>
> - 클라이언트와 서버 사이에 놓인 장치들이 서로 어떻게 다른가 — 프록시, 서러게이트, 게이트웨이, 터널, 릴레이
> - 프록시가 왜 배치되는가, 그리고 각 목적이 프록시에 어떤 권한을 요구하는가
> - 요청이 프록시로 흘러가게 만드는 네 가지 방법과, 그중 셋이 클라이언트 모르게 이뤄진다는 사실
> - 프록시 요청과 서버 요청의 문법이 다르다는 것이 목적지 결정에 남긴 두 개의 근거
> - `Via`, `TRACE`, `Max-Forwards`로 경로를 관측하는 방법과 그 관측이 동시에 노출하는 것
> - 요청 하나가 경로 위에서 몇 번 파싱되는가, 그리고 그 계수가 왜 곧 공격 표면인가

12장은 요청 경로 위의 마지막 프로세스를 열었다. 웹 서버는 하나의 프로그램이 아니라 일곱 단계의 파이프라인이었고, 오설정은 대부분 그 단계 사이의 이음매를 잘못 가정한 결과였다.

그러나 실제 배포에서 웹 서버는 요청을 처음 받는 주체가 아니다. 브라우저가 만든 문자열은 서버에 닿기 전에 여러 개의 독립적인 프로그램을 통과한다. 기업 방화벽의 프록시, ISP의 캐시, 데이터센터 앞단의 TLS 종료 장치, 웹 애플리케이션 방화벽, 리버스 프록시, 그리고 애플리케이션 서버의 게이트웨이 인터페이스. 이들은 서로 다른 회사가, 서로 다른 언어로, 서로 다른 시기에, 같은 명세를 서로 다르게 읽고 만든 프로그램이다. 그리고 **그 각각이 같은 바이트열을 자기 방식으로 파싱하고, 자기 방식으로 다시 조립해 다음 홉에 넘긴다.**

이 장은 그 중간자들을 하나씩 세운다. 무엇인지, 왜 거기 있는지, 무엇을 보고 무엇을 바꾸는지를 먼저 정확히 서술한다. 6.4절이 이 구성 요소들의 이름을 소개했다면, 이 장은 각각의 동작 규칙과 그 규칙이 남긴 틈을 다룬다.

그리고 13.12절에서 이 부의 명제를 수로 만든다. Part III의 도입부가 던진 질문 — "요청 하나가 클라이언트에서 애플리케이션 코드까지 가는 동안 몇 개의 프로세스가 그것을 파싱하고 다시 직렬화하는가" — 에 5.6절이 그림으로 답했고, 13.12절이 그 계수를 받아 **불일치가 발생할 수 있는 지점의 목록**으로 바꾼다. 1장 1.4절(계층 경계는 신뢰 경계가 아니다), 3장 3.1.2절(TCP는 메시지 경계를 주지 않는다), 9장 9.11절(커넥션 공유), 10장 10.4절(본문 경계 불일치), 11장 11.13절(프로토콜 번역 지점)이 모두 그 절로 모인다.

## 13.1 웹 중간자의 종류

프록시(proxy)는 클라이언트를 대신해 트랜잭션을 완결시키는 중간자다. 프록시가 없으면 HTTP 클라이언트는 HTTP 서버와 직접 대화한다. 프록시가 있으면 클라이언트는 프록시와 대화하고, 프록시가 클라이언트를 대신해 서버와 대화한다. 트랜잭션을 완결하는 것은 여전히 클라이언트지만, 그 과정은 프록시의 손을 거친다.

### 프록시는 서버이면서 클라이언트다

이 문장이 이 장 전체의 출발점이다.

```
   프록시는 클라이언트에게 서버처럼 행동한다        프록시는 서버에게 클라이언트처럼 행동한다
   (요청 메시지를 받고 응답 메시지를 돌려준다)      (요청 메시지를 보내고 응답 메시지를 받는다)

              요청  ────────────►                          요청  ────────────►
   클라이언트                       [ 프 록 시 ]                                서버
              ◄────────────  응답                          ◄────────────  응답
```

*그림 13-1. 프록시는 서버이면서 동시에 클라이언트다 (HTTP-DG 6장 그림 6-1 기준)*

HTTP 클라이언트가 프록시에 요청 메시지를 보내므로, 프록시는 웹 서버가 하듯 요청과 커넥션을 올바르게 처리하고 응답을 돌려줘야 한다. 동시에 프록시 자신이 서버에 요청을 보내므로 올바른 HTTP 클라이언트로도 동작해야 한다. 프록시를 직접 구현한다면 **클라이언트의 규칙과 서버의 규칙을 모두 지켜야 한다.**

보안 관점에서 이 이중성이 뜻하는 바는 분명하다. 프록시는 메시지를 **받아서 이해하고 다시 만든다.** 통과시키는 것이 아니다. 프록시를 지난 요청은 클라이언트가 만든 바이트열과 같다는 보장이 없으며, 실제로 거의 항상 다르다. 헤더가 추가되고, 홉 단위 헤더가 제거되고, 요청 대상의 표기가 바뀐다.

### 사설 프록시와 공용 프록시

프록시는 한 클라이언트 전용일 수도, 여러 클라이언트가 공유할 수도 있다.

- **공용 프록시(public proxy)** — 대부분의 프록시가 여기 속한다. 중앙집중식 프록시가 비용 면에서 효율적이고 관리하기 쉽다. 캐싱 프록시처럼 **사용자가 많이 몰릴수록 더 유용해지는** 종류도 있다. 사용자들 사이의 공통 요청을 활용할 수 있기 때문이다.
- **사설 프록시(private proxy)** — 전용 프록시는 흔하지 않지만 자리가 있다. 특히 클라이언트 컴퓨터 위에서 직접 도는 경우가 그렇다. 일부 브라우저 보조 제품과 ISP 서비스는 브라우저 기능 확장, 성능 개선, 또는 무료 서비스의 광고 노출을 위해 사용자 PC에서 작은 프록시를 돌린다.

이 구분은 뒤에서 두 번 되돌아온다. 공용 프록시는 **여러 사용자의 트래픽이 한 프로세스와 한 커넥션 풀을 공유한다**는 뜻이고(→ 9.11), 캐싱까지 하면 한 사용자의 응답이 다른 사용자에게 갈 수 있는 조건이 갖춰진다(→ 14.8). 사설 프록시는 사용자 기기 위에서 도는 신뢰받는 중간자이므로, 그 자체가 침해되면 TLS 종단까지 포함한 모든 것을 본다(→ 19.8).

### 프록시와 게이트웨이

엄밀히 말하면 **프록시는 같은 프로토콜을 말하는 둘 이상의 애플리케이션을 잇고, 게이트웨이(gateway)는 서로 다른 프로토콜을 말하는 둘 이상의 주체를 잇는다.** 게이트웨이는 "프로토콜 변환기"로 동작해, 클라이언트와 서버가 다른 프로토콜을 쓰더라도 트랜잭션이 완결되게 한다.

```
  (a) HTTP/HTTP 프록시

                  HTTP              HTTP
      브라우저  ─────── [웹 프록시] ─────── 웹 서버

  (b) HTTP/POP 게이트웨이

                  HTTP              POP
      브라우저  ─────── [웹/이메일  ] ─────── 이메일 서버
                        [ 게이트웨이 ]
```

*그림 13-2. 프록시는 같은 프로토콜을 말하고, 게이트웨이는 다른 프로토콜을 잇는다 (HTTP-DG 6장 그림 6-2 기준)*

그림 13-2(b)의 장치는 HTTP 프런트엔드를 POP 이메일 백엔드에 묶는다. 게이트웨이가 웹 트랜잭션을 적절한 POP 트랜잭션으로 변환해 사용자가 HTTP로 메일을 읽게 한다. 웹 기반 이메일 서비스가 이 형태다.

**실무에서 이 경계는 흐릿하다.** 브라우저와 서버가 서로 다른 HTTP 버전을 구현하므로 프록시는 어느 정도의 프로토콜 변환을 늘 수행한다. 상용 프록시 제품은 SSL, SOCKS 방화벽, FTP 접근, 웹 기반 애플리케이션을 지원하기 위해 게이트웨이 기능을 함께 구현한다. 이 장이 13.9절에서 게이트웨이를 따로 다루는 이유는 정의를 지키기 위해서가 아니라, **번역이 일어나는 지점이 파싱 불일치의 특별한 유형을 만들기 때문**이다(→ 11.13, 13.12).

### 중간자 분류표

이 장에서 다루는 중간자를 한 표로 정리한다. 6.4절의 소개를 동작 규칙 수준으로 확장한 것이다.

**표 13-1. 웹 중간자의 종류와 그 성질**

| 중간자 | 클라이언트가 존재를 아는가 | 무엇까지 파싱하는가 | 메시지를 바꾸는가 | 상세 |
|---|---|---|---|---|
| 명시적 프록시(forward proxy) | 안다 (직접 설정한다) | 시작줄 + 헤더, 필요하면 본문 | 그렇다 | 13.4, 13.5 |
| 서러게이트(surrogate, 리버스 프록시) | 모른다 (서버로 보인다) | 전부 | 그렇다 | 13.3 |
| 인터셉팅 프록시(intercepting proxy) | 모른다 (경로에서 가로챈다) | 시작줄 + 헤더 | 그렇다 | 13.3, 13.5 |
| 캐시 | 대개 모른다 | 시작줄 + 캐시 키에 드는 헤더 | 그렇다 (홉 단위 헤더 제거) | 14장 |
| 게이트웨이 | 경우에 따라 다르다 | 전부 (다른 프로토콜로 옮긴다) | 완전히 다시 만든다 | 13.9 |
| 터널(`CONNECT`) | 안다 (클라이언트가 요청한다) | **시작줄만** | 아니다 (맹목 전달) | 13.10 |
| 릴레이 | 모른다 | 커넥션을 세울 만큼만 | 부분적으로, 규칙을 어기며 | 13.11 |

표의 마지막 세 행이 이 장의 긴장을 요약한다. 게이트웨이는 메시지를 완전히 해체해 다른 규칙 체계로 옮기고, 터널은 첫 줄만 읽고 나머지를 아예 보지 않으며, 릴레이는 **읽는 척하면서 규칙의 일부만 구현한다.** 세 번째가 가장 위험하다. 종단들은 릴레이가 프로토콜을 지킨다고 가정하고 동작하기 때문이다.

> **이 절이 뒷받침하는 것**
>
> - 프록시가 메시지를 받아서 다시 만든다는 사실 → **13.12** (파싱 불일치의 전제), **10.4** (본문 경계 재결정)
> - 공용 프록시가 여러 사용자의 트래픽을 한 프로세스에서 다룬다는 사실 → **9.11** (커넥션 공유), **14.8** (사용자 간 응답 혼동)
> - 프록시와 게이트웨이의 경계가 실무에서 흐릿하다는 사실 → **13.9**, **11.13** (프로토콜 번역 지점)

## 13.2 프록시를 쓰는 이유 — 필터, 접근 제어, 캐싱, 익명화, 변환

프록시는 지나가는 모든 HTTP 트래픽을 **보고 만질 수 있다.** 그래서 트래픽을 감시하고 수정해 여러 부가 서비스를 구현할 수 있다. 아래는 HTTP-DG 6장이 드는 대표적 용도이며, 각각이 프록시에 요구하는 권한이 무엇인지를 함께 적는다.

### 콘텐츠 필터

초등학교는 필터링 프록시로 성인 콘텐츠 접근을 차단하면서 교육용 사이트는 자유롭게 열어 준다. 프록시는 교육 콘텐츠에는 제한 없는 접근을 허용하고, 부적절한 사이트에는 접근을 강제로 거부한다. 여러 기업과 비영리 단체가 필터링 소프트웨어를 제공하고 차단 목록을 관리한다.

이 용도가 프록시에 요구하는 것은 **요청 대상 URL을 정확히 읽고 정책과 대조할 수 있는 능력**이다. 그리고 바로 여기가 7.7절이 다룬 정규화 문제가 정책 판단으로 옮겨 오는 지점이다. 정책이 본 문자열과 서버가 연 리소스가 같다는 보장이 없으면 필터는 무력해진다(→ 13.12).

### 문서 접근 제어

프록시로 다수의 웹 서버와 리소스에 **균일한 접근 제어 정책**을 적용하고 감사 추적(audit trail)을 남길 수 있다. 대규모 기업 환경이나 분산된 조직에서 유용하다. 접근 제어를 중앙 프록시 한 곳에 설정하면, 제조사와 모델이 제각각이고 서로 다른 조직이 관리하는 수많은 웹 서버에 정책을 반복 반영하지 않아도 된다.

전형적인 배치는 이렇다. 클라이언트 1은 서버 A의 뉴스 페이지에 제한 없이 접근하고, 클라이언트 2는 인터넷 콘텐츠 전반에 제한이 없으며, 클라이언트 3은 서버 B에 접근하려면 프록시에 비밀번호를 제시해야 한다. 마지막 경우가 13.7절의 프록시 인증이다.

여기에는 한 가지 전제가 붙는다. **정교한 사용자가 통제 프록시를 의도적으로 우회하지 못하게 하려면, 웹 서버들이 프록시에서 온 요청만 받도록 정적으로 설정돼 있어야 한다.** 이 전제가 깨진 상태가 15.9절과 31.2절이 다루는 공유 환경의 문제이며, 12.8절이 다룬 "프록시로 오작동하는 서버"는 이 전제를 정반대 방향에서 깨뜨린다.

### 보안 방화벽

네트워크 보안 담당자는 프록시로 **어떤 애플리케이션 계층 프로토콜이 조직 안팎으로 흐를 수 있는지를 네트워크의 한 지점에서 통제한다.** 그리고 그 트래픽을 검사할 훅을 제공한다. 바이러스를 제거하는 웹·이메일 프록시가 그 예다.

이 용도는 **한 지점에 통제를 모은다**는 점에서 강력하고, 동시에 그 지점이 무엇을 보지 못하는지가 곧 구멍이 된다는 점에서 취약하다. 13.10절의 터널이 정확히 그 구멍이다. 터널로 흐르는 바이트는 방화벽 프록시에게 불투명하다.

### 웹 캐시

프록시 캐시는 인기 있는 문서의 사본을 지역에 두고 요청 시 제공해, 느리고 비싼 인터넷 통신을 줄인다. 같은 캐시를 쓰는 클라이언트들은 가까운 캐시에서 객체를 받고, 그렇지 않은 클라이언트는 원 서버에서 받는다.

**캐싱은 14장의 소관이다.** 이 장에서는 "프록시가 배치되는 이유 중 하나"로만 다룬다. 다만 이 목적이 프록시에 요구하는 권한은 여기서 짚어 둘 값이 있다. 캐시는 **두 요청이 같은지를 판단**해야 하고, **응답을 저장했다가 다른 트랜잭션에 재사용**해야 한다. 이 두 판단이 어긋날 때 무슨 일이 벌어지는지가 14.8절이다.

### 서러게이트 — 웹 서버 행세를 하는 프록시

프록시는 웹 서버로 가장할 수 있다. **서러게이트(surrogate)** 또는 **리버스 프록시(reverse proxy)** 라 불리는 이 형태는 진짜 웹 서버 요청을 받되, 웹 서버와 달리 요청받은 콘텐츠를 찾기 위해 다른 서버들과 통신을 시작할 수 있다.

서러게이트는 느린 웹 서버의 공통 콘텐츠 성능을 개선하는 데 쓰이며, 이 구성의 서러게이트를 **서버 액셀러레이터(server accelerator)** 라고 부른다. 콘텐츠 라우팅 기능과 결합하면 요청 시 복제되는 분산 콘텐츠 네트워크를 만들 수 있다.

서러게이트의 결정적 성질은 **클라이언트가 그것을 웹 서버와 구별할 수 없다**는 점이다. 이 성질이 13.5절에서 요청 형식 문제를 만든다.

### 콘텐츠 라우터

프록시는 인터넷 트래픽 상황과 콘텐츠 종류에 따라 요청을 특정 웹 서버로 향하게 하는 **콘텐츠 라우터**로 동작할 수 있다. 이를 이용해 서비스 등급을 구현하기도 한다. 사용자나 콘텐츠 제공자가 높은 성능에 비용을 지불했다면 가까운 복제 캐시로 요청을 넘기고, 사용자가 필터링 서비스에 가입했다면 필터링 프록시를 거치게 하는 식이다.

**요청 하나가 어디로 갈지가 요청의 내용에 따라 달라진다**는 것이 이 용도의 본질이다. 라우팅 판단의 입력이 곧 공격자가 통제하는 문자열이라는 뜻이기도 하다(→ 6.7).

### 트랜스코더

프록시는 콘텐츠를 클라이언트에 전달하기 전에 **본문의 형식을 바꿀 수 있다.** 데이터 표현 사이의 이 투명한 변환을 트랜스코딩(transcoding)이라 한다. 트랜스코딩 프록시는 지나가는 GIF 이미지를 JPEG으로 바꿔 크기를 줄이고, 이미지를 축소하거나 색 농도를 낮춰 작은 화면에 맞추며, 텍스트 파일을 압축하고, 웹 페이지의 짧은 텍스트 요약을 만들어 낸다. 문서를 다른 언어로 번역하는 것도 원리상 가능하다.

트랜스코딩은 이 장에서 특별히 중요하다. 앞의 용도들이 **헤더를 읽고 판단**했다면, 트랜스코딩은 **본문을 다시 만든다.** 10.5절이 다룬 콘텐츠 인코딩, 10.7절이 다룬 미디어 타입 선언이 이 지점에서 다시 결정된다. 그리고 다시 만들어진 본문의 길이는 원래 `Content-Length`와 다르다.

### 익명화 프록시

익명화 프록시는 HTTP 메시지에서 식별 가능한 특징을 **적극적으로 제거해** 프라이버시를 높인다. 클라이언트 IP 주소, `From` 헤더, `Referer` 헤더, 쿠키, URI에 실린 세션 ID 등이 대상이다.

```
  (클라이언트가 보낸 요청)                        (익명화 프록시가 보낸 요청)

  GET /something/file.html HTTP/1.0               GET /something/file.html HTTP/1.0
  Date: Sun, 01 Oct 2000 23:25:17 GMT             Date: Sun, 01 Oct 2000 23:25:17 GMT
  User-agent: Mozilla/4.75 (Win98; U)             User-agent: Mozilla/4.75
  From: joe@joes-hardware.com
  Referer: http://www.irs.gov/tax-audits.html
  Cookie: profile="football,lite beer"
  Cookie: income-bracket="30K-45K"
```

*그림 13-3. 익명화 프록시가 제거하는 헤더 (HTTP-DG 6장 그림 6-10 기준)*

프록시는 `User-Agent`에서 컴퓨터와 OS 종류를 지우고, 이메일 주소를 보호하기 위해 `From`을 지우고, 방문 이력을 가리기 위해 `Referer`를 지우고, 프로파일링과 신원 데이터를 없애기 위해 `Cookie`를 지웠다. 다만 식별 정보가 제거되므로 브라우징 경험의 품질이 떨어질 수 있고, 일부 사이트는 정상 동작하지 않는다.

이 예시는 8.6절의 결론을 프록시 쪽에서 다시 확인해 준다. **서버가 받은 헤더는 클라이언트가 보낸 헤더가 아니다.** 없어졌을 수도 있고, 값이 줄었을 수도 있고, 없던 것이 붙었을 수도 있다. 서버가 `User-Agent`나 `Referer`로 판단을 내린다면, 그 판단의 입력은 경로 위 어느 홉이든 바꿀 수 있는 값이다.

### 정리 — 목적이 요구하는 권한

**표 13-2. 프록시의 용도와 그 용도가 요구하는 권한 (이 책이 구성)**

| 용도 | 무엇을 읽어야 하는가 | 무엇을 바꾸는가 | 이 권한이 만드는 문제 | 참조 |
|---|---|---|---|---|
| 콘텐츠 필터 | 요청 URL | (차단만) | 정책이 본 URL ≠ 서버가 연 리소스 | 7.7, 13.12 |
| 접근 제어 | URL, 자격증명 | `Proxy-Authorization` 소비 | 우회 경로가 하나라도 있으면 무효 | 13.7, 12.8 |
| 보안 방화벽 | 프로토콜, 페이로드 | (검사·차단) | 불투명한 바이트는 검사할 수 없다 | 13.10 |
| 캐시 | 메서드, URL, `Vary` 대상 헤더 | 홉 단위 헤더 제거, 응답 재사용 | 동등성 판단이 곧 격리 경계 | 14.4, 14.8 |
| 서러게이트 | 전부 | 경로 재작성, 헤더 추가 | 클라이언트가 서버와 구별 못 한다 | 13.5, 15.2 |
| 콘텐츠 라우터 | URL, 헤더, 가입 정보 | 목적지 | 라우팅 입력이 공격자 통제 문자열 | 6.7 |
| 트랜스코더 | 본문 전체 | **본문과 그 길이·타입** | 본문 경계와 타입 선언이 재결정된다 | 10.5, 10.7 |
| 익명화 | 식별 헤더 | 헤더 제거 | 종단이 보는 헤더가 원본이 아니다 | 8.6, 20.2 |

이 표의 세로 축을 한 문장으로 읽으면 이렇다. **프록시가 유용해지는 정도는 그것이 메시지를 얼마나 깊이 이해하고 얼마나 많이 고치는가에 비례하고, 파싱 불일치의 위험도 같은 축을 따라 커진다.** 1.2절이 L4와 L7을 비교하며 한 말이 여기서 여덟 개의 용도로 구체화된 것이다.

## 13.3 프록시는 어디에 놓이는가

앞 절이 프록시가 **무엇을 하는가**를 다뤘다면, 이 절은 그것이 네트워크 어디에 **놓이는가**를 다룬다. 세 가지를 본다. 배치 위치, 프록시들이 사슬로 이어지는 방식, 그리고 트래픽이 애초에 프록시로 흘러가게 되는 경위다.

### 배치 위치 네 가지

```
  (a) 사설 LAN 이그레스 프록시            (b) ISP 액세스(인그레스) 프록시

   클라이언트 ─ 로컬망 ─[프록시]─ 인터넷 ─ 서버    클라이언트 ─[프록시]─ 인터넷 ─ 서버

  (c) 서러게이트                          (d) 네트워크 교환 프록시

   클라이언트 ─ 인터넷 ─[프록시]─ 로컬망 ─ 서버    망1 ─[라우터]─[프록시]─[라우터]─ 망2
```

*그림 13-4. 프록시의 네 가지 배치 (HTTP-DG 6장 그림 6-11 기준)*

- **이그레스 프록시(egress proxy)** — 로컬 네트워크의 출구에 놓아 로컬망과 인터넷 사이의 트래픽 흐름을 통제한다. 기업에서는 외부 공격자에 대한 방화벽 보호를 제공하거나 대역폭 비용을 줄이고 성능을 개선하는 데 쓴다. 학교에서는 필터링 이그레스 프록시로 부적절한 콘텐츠 열람을 막는다.
- **액세스(인그레스) 프록시(access proxy)** — ISP 접속 지점에 놓여 가입자들의 요청을 모아 처리한다. ISP는 캐싱 프록시로 인기 문서의 사본을 저장해 다운로드 속도를 높이고 인터넷 대역폭 비용을 줄인다.
- **서러게이트** — 네트워크 가장자리, 웹 서버 앞에 놓여 그 서버로 향하는 모든 요청을 받고, 필요할 때만 웹 서버에 리소스를 요청한다. 웹 서버에 보안 기능을 더하거나, 느린 서버 앞에 빠른 캐시를 놓아 성능을 높인다. **서러게이트는 대개 웹 서버의 이름과 IP 주소를 직접 가져가므로, 모든 요청이 서버 대신 프록시로 간다.**
- **네트워크 교환 프록시** — 충분한 처리 능력이 있으면 네트워크 간 피어링 교환 지점에 놓아 캐싱으로 혼잡을 완화하고 트래픽 흐름을 감시한다. 인터넷 대역폭이 비싼 지역에 주로 배치되며, 일부 국가는 국가 안보를 이유로 트래픽 감시용 배치를 검토해 왔다.

마지막 항목은 이 책이 여러 번 되돌아오는 사실을 다시 확인시킨다. **경로 위의 중간자는 반드시 사용자나 서비스 운영자의 통제 아래 있지 않다.**

### 프록시 계층

프록시는 사슬로 연결될 수 있고, 이를 **프록시 계층(proxy hierarchy)** 이라 한다. 계층 안에서 메시지는 프록시에서 프록시로 전달되다가 원 서버에 닿고, 응답은 역순으로 돌아온다.

계층 안의 프록시들에는 부모-자식 관계가 부여된다. **서버에 더 가까운 다음 인바운드 프록시를 부모(parent)라 하고, 클라이언트에 더 가까운 다음 아웃바운드 프록시를 자식(child)** 이라 한다.

```
클라이언트 ── 프록시 1 ── 프록시 2 ── 프록시 3 ── 원 서버
              (2의 자식)  (3의 자식,  (2의 부모)
                           1의 부모)
```

*그림 13-5. 3단 프록시 계층 (HTTP-DG 6장 그림 6-12 기준)*

계층이 항상 정적인 것은 아니다. 프록시는 여러 요인에 따라 변화하는 프록시·서버 집합으로 메시지를 전달할 수 있다. HTTP-DG가 드는 동적 부모 선택의 예는 다음과 같다.

- **부하 분산** — 자식 프록시가 부모들의 현재 부하 수준을 보고 부모를 고른다.
- **지리적 근접성 라우팅** — 원 서버의 지리적 권역을 담당하는 부모를 고른다.
- **프로토콜/타입 라우팅** — URI에 따라 다른 부모와 원 서버로 라우팅한다. 특정 종류의 URI는 특별한 프로토콜 처리를 위해 전용 프록시를 거치게 한다.
- **가입 기반 라우팅** — 발행자가 고성능 서비스에 추가 비용을 냈다면 해당 URI를 큰 캐시나 압축 엔진으로 보낸다.

동적 부모 선택 로직은 제품마다 다르게 구현된다. 설정 파일, 스크립트 언어, 동적 실행 플러그인이 쓰인다.

**보안적으로 읽으면 계층은 두 가지를 뜻한다.** 첫째, 파서의 개수가 늘어난다. 3단 계층은 요청 하나에 파싱-재직렬화 쌍을 셋 더한다(→ 13.12). 둘째, **경로가 요청마다 달라질 수 있다.** 같은 URL에 대한 두 요청이 서로 다른 중간자 집합을 통과하면, 어느 한쪽만 통과하는 정책은 신뢰할 수 없다. 스크립트 언어와 플러그인으로 구현된 라우팅 로직 자체가 공격 표면이라는 점도 덧붙일 만하다(→ 31.3).

### 트래픽은 어떻게 프록시로 가는가

클라이언트는 보통 웹 서버와 직접 대화하므로, HTTP 트래픽이 애초에 프록시로 가게 만드는 장치가 필요하다. HTTP-DG는 네 가지를 든다.

**표 13-3. 트래픽을 프록시로 보내는 네 가지 방법 (HTTP-DG 6장 기준)**

| 방법 | 무엇을 바꾸는가 | 클라이언트가 아는가 | 요청 형식 | 상세 |
|---|---|---|---|---|
| 클라이언트 수정 | 브라우저 프록시 설정 | **안다** | 절대 URI | 13.4 |
| 네트워크 수정 | 스위치·라우터가 가로챈다 | 모른다 | 상대 URI | 13.5 |
| DNS 네임스페이스 수정 | 이름이 서러게이트를 가리킨다 | 모른다 | 상대 URI | 15.6 |
| 웹 서버 수정 | `305` 응답으로 프록시를 지시한다 | 안다 (지시받는다) | 절대 URI | 15.5 |

- **클라이언트 수정** — 많은 웹 클라이언트가 수동·자동 프록시 설정을 지원한다. 프록시를 쓰도록 설정된 클라이언트는 HTTP 요청을 원 서버가 아니라 프록시로 **직접, 의도적으로** 보낸다.
- **네트워크 수정** — 클라이언트가 알거나 참여하지 않아도 네트워크 인프라가 웹 트래픽을 가로채 프록시로 몰아넣는 기법들이 있다. 대개 HTTP 트래픽을 감시하다 가로채 프록시로 넘기는 스위칭·라우팅 장비에 의존한다. 이런 프록시를 **인터셉팅 프록시(intercepting proxy)** 라 한다.
- **DNS 네임스페이스 수정** — 서러게이트는 웹 서버의 이름과 IP 주소를 그대로 가져가므로 모든 요청이 서버 대신 서러게이트로 간다. DNS 테이블을 직접 편집하거나, 요청 시점에 적절한 프록시·서버를 계산하는 동적 DNS 서버로 구현한다. 실제 서버의 주소와 이름을 바꾸고 옛 주소·이름을 서러게이트에 주는 설치 방식도 있다.
- **웹 서버 수정** — 일부 웹 서버는 `305` 리다이렉션 응답을 돌려보내 클라이언트 요청을 프록시로 넘기도록 설정할 수 있다. 리다이렉트를 받은 클라이언트는 프록시와 트랜잭션을 진행한다.

> **용어 정리 — "투명"과 "인터셉션"**
>
> 인터셉팅 프록시는 흔히 "투명 프록시(transparent proxy)"라 불린다. 존재를 인지하지 못한 채 접속하기 때문이다. 그러나 HTTP 명세에서 "투명성(transparency)"은 **의미론적 동작을 바꾸지 않는 기능**을 가리키는 데 이미 쓰이고 있다. 그래서 표준 커뮤니티는 트래픽 포획에는 "인터셉션"이라는 용어를 쓸 것을 권고했고, 이 책도 그 명명을 따른다. 용어의 혼동 자체가 시사적이다. **트래픽을 가로채는 프록시는 대개 의미론적으로 투명하지 않다.**

네 방법 중 셋에서 클라이언트는 중간자의 존재를 모른다. 그리고 그중 둘에서는 요청 문법마저 서버로 보내는 형식 그대로다. 13.5절이 이 사실에서 출발한다.

## 13.4 클라이언트 프록시 설정 — 수동, PAC, WPAD

모든 현대 브라우저가 프록시 사용 설정을 지원하며, 대개 여러 방식을 제공한다.

- **수동 설정** — 사용할 프록시를 명시적으로 지정한다.
- **브라우저 사전 설정** — 브라우저 벤더나 배포자가 고객에게 전달하기 전에 프록시 설정을 미리 넣어 둔다.
- **프록시 자동 설정(PAC)** — JavaScript로 된 PAC 파일의 URI를 제공하면, 클라이언트가 그 파일을 받아 실행해 프록시 사용 여부와 사용할 프록시를 결정한다.
- **WPAD 프록시 발견** — 브라우저가 "설정 서버"를 자동으로 찾아내고, 거기서 자동 설정 파일을 내려받는다.

### 수동 설정

브라우저마다 방법은 다르지만 개념은 같다. **프록시의 호스트와 포트를 지정하는 것**이다. 여러 ISP가 웹 트래픽을 프록시로 돌리도록 미리 설정된 브라우저나 맞춤 운영체제를 고객에게 제공해 왔다.

수동 설정은 단순하지만 경직돼 있다. 모든 콘텐츠에 대해 단 하나의 프록시만 지정할 수 있고 장애 조치(failover) 지원이 없다. 대규모 조직에서는 관리 문제도 생긴다. 설정된 브라우저가 많으면 변경이 필요할 때 전부 다시 설정하기가 어렵거나 불가능하다.

### PAC 파일

**프록시 자동 설정(proxy auto-configuration, PAC)** 파일은 프록시 설정을 그때그때 계산하는 작은 JavaScript 프로그램이다. 문서에 접근할 때마다 JavaScript 함수가 적절한 프록시 서버를 선택한다.

사용하려면 브라우저에 PAC 파일의 URI를 설정한다. 브라우저는 그 URI에서 PAC 파일을 가져와, 접근마다 JavaScript 로직으로 프록시를 계산한다. PAC 파일은 보통 `.pac` 확장자를 쓰고 MIME 타입은 `application/x-ns-proxy-autoconfig`다.

각 PAC 파일은 `FindProxyForURL(url, host)` 함수를 정의해야 한다. 반환값은 아래 셋 중 하나다.

**표 13-4. PAC 스크립트 반환값 (HTTP-DG 6장 표 6-1 기준)**

| 반환값 | 의미 |
|---|---|
| `DIRECT` | 프록시 없이 직접 연결한다 |
| `PROXY host:port` | 지정한 프록시를 사용한다 |
| `SOCKS host:port` | 지정한 SOCKS 서버를 사용한다 |

```javascript
function FindProxyForURL(url, host) {
    if (url.substring(0,5) == "http:") {
        return "PROXY http-proxy.mydomain.com:8080";
    } else if (url.substring(0,4) == "ftp:") {
        return "PROXY ftp-proxy.mydomain.com:8080";
    } else {
        return "DIRECT";
    }
}
```

*예제 13-1. HTTP 트랜잭션과 FTP 트랜잭션에 각각 다른 프록시를 지정하는 PAC 파일 (HTTP-DG 6장 예제 6-1 기준)*

### WPAD

**웹 프록시 자동 발견 프로토콜(Web Proxy Autodiscovery Protocol, WPAD)** 은 브라우저에 맞는 PAC 파일을 자동으로 찾아내는, 단계적으로 확장되는 발견 알고리즘이다. WPAD를 구현한 클라이언트는 다음 순서로 동작한다.

1. WPAD로 PAC 파일의 URI를 찾는다.
2. 그 URI에서 PAC 파일을 가져온다.
3. PAC 파일을 실행해 프록시 서버를 결정한다.
4. 그 프록시로 요청을 보낸다.

모든 조직이 모든 기법을 쓸 수 있는 것은 아니므로, WPAD는 여러 자원 발견 기법을 순서대로 시도하다 성공하면 멈춘다. 명세가 정의한 순서는 다음과 같다.

1. 동적 호스트 설정 프로토콜(DHCP)
2. 서비스 위치 프로토콜(SLP)
3. DNS의 잘 알려진 호스트명
4. DNS SRV 레코드
5. DNS TXT 레코드에 담긴 서비스 URI

리다이렉션 관점에서의 PAC·WPAD 상세는 15.7절이 다룬다.

### 이 설정 경로가 갖는 보안적 성질

세 가지를 짚는다. 셋 다 이 책 다른 곳의 논의를 여기에 적용한 것이다.

**첫째, PAC 파일은 요청 하나하나의 목적지를 결정하는 실행 코드다.** 정적 설정값이 아니라 브라우저가 실행하는 프로그램이며, 실행 결과가 "이 요청을 어디로 보낼 것인가"를 정한다. 그 파일의 출처와 무결성이 보장되지 않으면 **모든 요청의 경로가 그 출처의 통제 아래 놓인다.** 브라우저가 PAC를 가져오는 통로 자체가 보호되지 않을 수 있다는 점도 함께 고려해야 한다.

**둘째, WPAD의 단계적 발견은 이름 해석의 경주다.** 다섯 기법을 순서대로 시도해 **먼저 답한 쪽을 채택한다.** 2.7절이 "이름 해석의 결과를 신뢰할 수 있는가"라는 질문에 내린 결론이 여기 그대로 적용된다. 로컬 네트워크에서 응답할 수 있는 주체라면 누구든 이 경주에 참여할 수 있고, 승자는 조직 전체의 웹 트래픽 경로를 정한다. 이름 해석 시점의 차이가 만드는 문제(→ 2.8)와 같은 계열이다.

**셋째, 설정된 프록시는 클라이언트가 자발적으로 신뢰를 위임한 종단이다.** 클라이언트는 프록시에 절대 URI를 보내고, 목적지 이름 해석과 장애 조치를 프록시에 맡긴다(13.5절 뒷부분). 즉 **프록시 설정은 DNS와 라우팅 판단의 위임이기도 하다.**

**표 13-5. 프록시 설정 방식 비교 (이 책이 구성)**

| 방식 | 유연성 | 경로 결정 주체 | 신뢰의 근거 | 주요 취약 지점 |
|---|---|---|---|---|
| 수동 | 낮음 (프록시 하나, 장애 조치 없음) | 사용자·관리자 | 사람이 입력한 값 | 대규모 재설정의 어려움 |
| 사전 설정 | 낮음 | 벤더·배포자 | 배포 채널 | 사용자가 인지하지 못함 |
| PAC | 높음 (요청마다 계산) | **PAC 파일의 코드** | 파일의 출처와 전송 경로 | 파일 출처·무결성 |
| WPAD | 가장 높음 (자동 발견) | **먼저 응답한 발견 서비스** | 로컬 네트워크의 응답 | 발견 단계의 응답 경주 |

> **이 절이 뒷받침하는 것**
>
> - PAC·WPAD의 발견 순서가 이름 해석의 경주라는 사실 → **2.7**(이름과 신원), **2.8**(해석 시점 차이), **15.7**(프록시 리다이렉션 기법)
> - 프록시 설정이 목적지 결정의 위임이라는 사실 → **13.5**, **1.8**(하위 계층 공격의 지형)

## 13.5 프록시 요청의 까다로운 점 — 절대 URI vs 상대 URI, Host 헤더 의존

이 절은 프록시 요청에서 가장 자주 오해되는 부분을 다룬다. **웹 서버 메시지와 웹 프록시 메시지의 문법은 딱 한 군데를 빼고 같다.** 그 한 군데가 요청 라인의 URI다.

### 두 개의 요청 형식

클라이언트가 웹 서버에 요청을 보낼 때, 요청 라인에는 **스킴·호스트·포트가 없는 부분 URI**가 들어간다.

```
GET /index.html HTTP/1.0
User-Agent: SuperBrowser v1.3
```

클라이언트가 프록시에 요청을 보낼 때는 요청 라인에 **전체 URI**가 들어간다.

```
GET http://www.marys-antiques.com/index.html HTTP/1.0
User-Agent: SuperBrowser v1.3
```

왜 형식이 둘인가. 최초의 HTTP 설계에서 클라이언트는 단일 서버와 직접 대화했다. 가상 호스팅은 존재하지 않았고 프록시에 대한 고려도 없었다. **서버는 자기 호스트명과 포트를 이미 알고 있으므로, 중복 정보를 보내지 않기 위해 클라이언트는 스킴과 호스트(와 포트)를 뺀 부분 URI만 보냈다.**

프록시가 등장하면서 부분 URI가 문제가 됐다. 프록시는 자기 커넥션을 세우기 위해 **목적지 서버의 이름을 알아야** 했다. 그리고 프록시 기반 게이트웨이는 FTP를 비롯한 다른 스킴의 리소스에 접속하려면 **URI의 스킴**이 필요했다. HTTP/1.0은 프록시 요청에 전체 URI를 요구하는 것으로 문제를 풀되, 서버 요청에는 부분 URI를 유지했다. 이미 배포된 서버가 너무 많아 전부 바꿀 수 없었기 때문이다. HTTP/1.1은 프록시 요청과 서버 요청 모두에서 서버가 전체 URI를 처리하도록 요구하지만, **실제로는 부분 URI만 받는 서버가 여전히 많다.**

### 같은 문제, 다른 해법 — 가상 호스팅

프록시의 "빠진 스킴·호스트·포트" 문제는 가상 호스팅 웹 서버가 마주한 문제와 같다. 가상 호스팅 서버는 하나의 물리 서버를 여러 사이트가 공유한다. 부분 URI `/index.html`에 대한 요청이 들어오면, 서버는 **어느 사이트를 의도한 요청인지** 알아야 한다.

문제는 같지만 해법은 달랐다.

- **명시적 프록시는 요청 메시지에 전체 URI를 요구하는 것으로 해결했다.**
- **가상 호스팅 웹 서버는 `Host` 헤더가 호스트와 포트를 실어 나르도록 해서 해결했다.**

이 책의 논지에서 이 문장은 무겁다. **하나의 사실(목적지가 어디인가)에 대해 메시지 안에 두 개의 독립적인 출처가 생겼다.** 두 출처가 일치하지 않을 때 어느 쪽을 쓸지는 구현마다 다르며, 경로 위 서로 다른 홉이 서로 다른 선택을 할 수 있다. 13.12절이 이 지점을 목록의 한 항목으로 되받는다. 가상 호스팅 자체는 15.2절, `Host` 헤더의 신뢰성은 8.6절이 다룬다.

### 인터셉팅 프록시는 부분 URI를 받는다

클라이언트가 HTTP를 제대로 구현한다면, 명시적으로 설정된 프록시에는 전체 URI를 보낸다. 문제는 **클라이언트가 자기가 프록시와 말하고 있다는 사실을 늘 알지는 못한다**는 데 있다. 프록시를 쓰도록 설정하지 않았어도 트래픽이 서러게이트나 인터셉팅 프록시를 지날 수 있다. 두 경우 모두 클라이언트는 웹 서버와 말한다고 믿고 전체 URI를 보내지 않는다.

```
  (a) 서버 요청            GET /index.html HTTP/1.0
      클라이언트 ─────────────────────────────────► 원 서버

  (b) 명시적 프록시 요청   GET http://www.marys-antiques.com/index.html HTTP/1.0
      클라이언트 ─────────────────────────────────► 프록시 ──► 원 서버

  (c) 서러게이트 요청      GET /index.html HTTP/1.0
      클라이언트 ─────────────────────────────────► 서러게이트 ──► 원 서버
                            (서버 호스트명이 서러게이트를 가리킨다)

  (d) 인터셉팅 프록시 요청 GET /index.html HTTP/1.0
      클라이언트 ─────────────────────────────────► [가로챔] ──► 원 서버
```

*그림 13-6. 인터셉팅 프록시와 서러게이트는 서버 형식의 요청을 받는다 (HTTP-DG 6장 그림 6-15 기준)*

인터셉팅 프록시가 클라이언트-프록시 트래픽을 가로채 전체 URI를 받는 경우도 있지만 흔치 않다. 명시적 프록시는 대개 HTTP와 다른 포트(보통 80 대신 8080)를 쓰고, 인터셉팅 프록시는 보통 80번 포트만 가로채기 때문이다.

### 프록시는 두 형식을 모두 처리해야 한다

트래픽이 프록시로 흘러드는 경로가 여러 가지이므로, 범용 프록시 서버는 요청 메시지에서 전체 URI와 부분 URI를 **모두** 지원해야 한다. 명시적 프록시 요청이면 전체 URI를 쓰고, 웹 서버 요청이면 부분 URI와 가상 `Host` 헤더를 쓴다. HTTP-DG가 정리한 규칙은 다음과 같다.

1. **전체 URI가 제공되면 그것을 쓴다.**
2. **부분 URI가 제공되고 `Host` 헤더가 있으면, `Host` 헤더로 원 서버 이름과 포트를 정한다.**
3. **부분 URI가 제공되고 `Host` 헤더가 없으면**, 다른 방법으로 원 서버를 알아내야 한다.
   - 프록시가 원 서버를 대신하는 서러게이트라면, 실제 서버의 주소와 포트를 설정으로 지정해 둘 수 있다.
   - 트래픽이 가로채인 것이고 가로채기 장치가 원래 IP 주소와 포트를 알려 준다면, 그 값을 쓸 수 있다.
   - 그마저 안 되면 원 서버를 결정할 정보가 없으므로 오류를 반환해야 한다. 이 판단은 가볍게 내릴 일이 아니다. 사용자는 이전에 본 적 없는 알 수 없는 오류 페이지를 받게 된다.

**표 13-6. 요청 형식과 목적지 결정의 근거 (HTTP-DG 6장 규칙 기준)**

| 요청 형식 | `Host` 헤더 | 프록시가 목적지를 정하는 근거 | 불일치 가능성 |
|---|---|---|---|
| 전체 URI | 있음 | **요청 라인** (규칙 1) | `Host`와 다른 값일 수 있다 |
| 전체 URI | 없음 | 요청 라인 | — |
| 부분 URI | 있음 | **`Host` 헤더** (규칙 2) | 여러 개일 수 있다 |
| 부분 URI | 없음 | 설정값 또는 가로채기 계층의 IP·포트 | 계층 간 정보 전달의 정확성에 의존 |

표의 첫 행이 13.12절이 되받는 지점이다. **전체 URI와 `Host`가 함께 있고 서로 다른 곳을 가리킬 때, 규칙 1을 따르는 홉은 요청 라인을 보고 규칙 2를 따르는 홉은 `Host`를 본다.** 두 홉이 라우팅과 리소스 선택을 서로 다른 값으로 수행한다.

### 전송 중 URI 수정

프록시는 메시지를 전달하면서 요청 URI를 바꾸는 데 **매우 신중해야 한다.** 무해해 보이는 사소한 변경도 하류 서버와의 상호운용 문제를 만들 수 있다.

특히 일부 프록시는 다음 홉으로 넘기기 전에 URI를 표준형으로 "정규화(canonicalize)"하는 것으로 알려져 있다. 기본 HTTP 포트를 명시적인 `:80`으로 바꾸거나, 이스케이프되지 않은 예약 문자를 올바르게 이스케이프된 형태로 고치는 것 같은 무해해 보이는 변환이 상호운용 문제를 일으킨다.

일반적으로 프록시는 **가능한 한 관용적이어야 한다.** 엄격한 프로토콜 준수를 강제하는 "프로토콜 경찰"이 되려 해서는 안 된다. 그렇게 하면 그때까지 정상 동작하던 서비스가 크게 망가질 수 있다.

특히 **HTTP 명세는 일반적인 인터셉팅 프록시가 요청을 전달할 때 URI의 절대 경로 부분을 다시 쓰는 것을 금지한다.** 유일한 예외는 빈 경로를 `/`로 바꾸는 것이다.

이 권고가 이 책의 논지와 충돌한다는 점을 분명히 해 둘 필요가 있다. 상호운용성을 위한 관용은 **모호한 입력을 통과시키는 것**과 같은 말이다. 13.12절의 방어 항목에서 이 긴장을 정면으로 다룬다. 지금 짚어 둘 것은 하나다. **"프록시는 URI를 고치지 말라"는 규칙과 "정책 지점과 실행 지점이 같은 문자열을 봐야 한다"는 요구는 같은 방향을 가리키지 않는다.**

### URI 자동 확장과 호스트명 해석

브라우저는 프록시 유무에 따라 요청 URI를 다르게 해석한다.

**프록시가 없을 때**, 브라우저는 입력받은 URI에 대응하는 IP 주소를 찾는다. 호스트명이 발견되면 연결에 성공할 때까지 해당 IP들을 차례로 시도한다. 호스트를 찾지 못하면 많은 브라우저가 자동 "확장"을 시도한다. 사용자가 흔한 사이트 이름의 가운데 조각만 입력했을 가능성을 고려해 `www.` 접두사와 `.com` 접미사를 붙여 보고, 어떤 브라우저는 해석되지 않는 URI를 제3자 사이트에 넘겨 철자 교정과 후보 URI 제안을 받는다. 여기에 더해 대부분 시스템의 DNS 설정은 호스트명 접두사만 입력해도 도메인을 자동 검색하게 한다. `oreilly.com` 도메인 안에서 `host7`을 입력하면 DNS가 자동으로 `host7.oreilly.com`을 시도한다.

**명시적 프록시를 쓸 때**, 브라우저는 이런 편의 확장을 전혀 수행하지 않는다. 사용자의 URI가 프록시로 그대로 전달되기 때문이다. 사용자가 `oreilly`를 입력하면 프록시는 `http://oreilly/`를 받는다. 브라우저는 기본 스킴과 경로만 붙이고 호스트명은 입력된 그대로 둔다.

```
GET http://oreilly/ HTTP/1.0
Proxy-connection: Keep-Alive
User-agent: Mozilla/4.72 [en] (Win98; I)
Host: oreilly
Accept: */*
```

*예제 13-2. 명시적 프록시를 쓸 때 브라우저는 호스트명을 확장하지 않는다 (HTTP-DG 6장 그림 6-17 기준)*

이 때문에 일부 프록시는 브라우저의 편의 서비스를 최대한 흉내 내려 한다. `www...com` 자동 확장과 로컬 도메인 접미사 부가가 그것이다. 다만 널리 공유되는 프록시라면 개별 사용자에게 맞는 도메인 접미사를 알아내는 것이 불가능할 수 있다.

**인터셉팅 프록시가 있을 때**는 클라이언트가 보기에 프록시가 없으므로 자동 확장이 서버 경우와 똑같이 일어난다. 차이는 커넥션 수립에서 드러난다. 클라이언트는 호스트명을 해석해 IP 목록을 갖고 있고, 보통은 죽은 IP를 건너뛰며 성공할 때까지 차례로 시도한다. 그러나 인터셉팅 프록시가 있으면 **첫 연결 시도를 원 서버가 아니라 프록시가 종단한다.** 클라이언트는 웹 서버와 성공적으로 대화하고 있다고 믿지만 그 웹 서버는 살아 있지 않을 수도 있다. 프록시가 실제 원 서버와 통신할 단계가 되어서야 그 IP가 죽은 서버를 가리킨다는 것을 알게 된다.

브라우저가 제공하던 수준의 장애 내성을 유지하려면 프록시가 **다른 IP들을 직접 시도**해야 한다. `Host` 헤더의 이름을 다시 해석하거나 IP에 대해 역방향 DNS 조회를 하는 방법이 있다. 인터셉팅 프록시든 명시적 프록시든 죽은 서버에 대한 DNS 장애 내성을 지원해야 한다. **브라우저가 명시적 프록시를 쓰도록 설정되면 장애 내성을 프록시에 의존하기 때문이다.**

이 마지막 문장이 13.4절의 세 번째 관찰을 확인해 준다. 프록시 설정은 이름 해석과 장애 처리의 위임이며, 위임된 판단은 사용자가 검증할 수 없다.

> **이 절이 뒷받침하는 것**
>
> - 목적지에 대한 두 개의 독립적 출처(요청 라인과 `Host`) → **8.6**(`Host`는 값이 아니라 라우팅 입력이다), **15.2**(가상 호스팅), **13.12**(불일치 지점 목록)
> - 서러게이트·인터셉팅 프록시를 클라이언트가 구별할 수 없다는 사실 → **13.3**, **19.9**(중간자 성립 조건)
> - 프록시가 URI를 고치지 말아야 한다는 규칙과 정규화 요구의 충돌 → **7.7**, **7.8**, **13.12**(방어의 방향)
> - 이름 해석과 장애 내성이 프록시에 위임된다는 사실 → **2.7**, **13.4**

## 13.6 메시지 추적 — Via, TRACE, Max-Forwards

오늘날 웹 요청이 클라이언트에서 서버로 가는 길에 프록시 두 개 이상의 사슬을 지나는 것은 드문 일이 아니다. 많은 기업이 보안과 비용 절감을 위해 캐싱 프록시로 인터넷에 접속하고, 대형 ISP는 성능과 기능을 위해 프록시 캐시를 쓴다. 동시에 성능을 위해 콘텐츠를 전 세계에 흩어진 서러게이트 캐시 무리에 복제하는 방식이 널리 쓰인다.

프록시는 서로 다른 벤더가 개발한다. 기능도 버그도 다르고 관리 주체도 제각각이다. **IP 패킷이 여러 스위치와 라우터를 지나는 흐름을 추적하는 것이 중요하듯, 프록시를 가로지르는 메시지의 흐름을 추적하고 문제를 탐지할 수 있어야 한다.**

이 절이 다루는 세 가지 장치는 HTTP가 그 추적을 위해 마련한 것이다. 그리고 셋 다 **관측을 가능하게 하는 동시에 무언가를 노출한다.**

### Via 헤더

`Via` 헤더 필드는 메시지가 지나온 각 중간 노드(프록시 또는 게이트웨이)의 정보를 나열한다. 메시지가 노드를 지날 때마다 그 노드는 자신을 `Via` 목록 **끝에** 추가해야 한다.

```
Via: 1.1 proxy-62.irenes-isp.net, 1.0 cache.joes-hardware.com
```

이 문자열은 메시지가 프록시 둘을 지났음을 알려 준다. 첫 번째 프록시는 HTTP/1.1을 구현했고 이름이 `proxy-62.irenes-isp.net`이며, 두 번째는 HTTP/1.0을 구현했고 이름이 `cache.joes-hardware.com`이다.

`Via`는 세 가지 목적으로 쓰인다. **메시지 전달 추적, 메시지 루프 진단, 그리고 요청/응답 사슬 위 모든 송신자의 프로토콜 능력 식별**이다. 프록시는 `Via`로 라우팅 루프를 탐지할 수도 있다. 요청을 내보내기 전에 자신과 결부된 고유 문자열을 `Via`에 넣고, 들어오는 요청에 그 문자열이 있는지 검사하면 된다.

**문법.** `Via`는 쉼표로 구분된 경유점(waypoint) 목록이다.

```
Via               = "Via" ":" 1#( waypoint )
waypoint          = ( received-protocol received-by [ comment ] )
received-protocol = [ protocol-name "/" ] protocol-version
received-by       = ( host [ ":" port ] ) | pseudonym
```

각 경유점은 최대 네 개의 구성 요소를 가진다.

- **프로토콜 이름** — 중간자가 수신한 프로토콜. HTTP이면 생략할 수 있다. 아니면 `/`로 버전과 구분해 앞에 붙인다. 게이트웨이가 HTTP 요청을 다른 프로토콜로 연결할 때 HTTP가 아닌 값이 나타난다.
- **프로토콜 버전** — 수신한 메시지의 버전. HTTP이면 `1.0`, `1.1` 같은 표준 버전 번호를 쓴다. **버전을 `Via`에 넣는 이유는 뒤의 애플리케이션이 앞선 모든 중간자의 프로토콜 능력을 알 수 있게 하기 위해서다.**
- **노드 이름** — 중간자의 호스트와 선택적 포트 번호. 포트가 없으면 그 프로토콜의 기본 포트로 간주한다. 프라이버시를 이유로 실제 호스트명을 노출하고 싶지 않은 조직은 가명(pseudonym)으로 대체할 수 있다.
- **노드 주석** — 중간 노드를 더 설명하는 선택적 주석. 벤더와 버전 정보를 넣는 것이 흔하고, 일부 프록시는 그 장치에서 일어난 사건에 대한 진단 정보를 주석에 담는다. 캐싱 프록시가 히트/미스 정보를 넣는 것이 그 예다.

**요청 경로와 응답 경로.** 요청과 응답 모두 프록시를 지나므로 양쪽 다 `Via` 헤더를 가진다. 요청과 응답은 보통 같은 TCP 커넥션 위로 오가므로, 응답은 요청이 지나온 경로를 거꾸로 되짚는다. 요청이 프록시 A, B, C를 지났다면 응답은 C, B, A를 지난다. 따라서 **응답의 `Via`는 거의 언제나 요청의 `Via`를 뒤집은 것**이다.

**게이트웨이와 `Via`.** 일부 프록시는 HTTP가 아닌 프로토콜을 말하는 서버에 대해 게이트웨이 기능을 제공한다. `Via` 헤더는 이 프로토콜 변환을 기록해, HTTP 애플리케이션이 사슬 위의 프로토콜 능력과 변환을 알 수 있게 한다. HTTP 클라이언트가 HTTP/FTP 게이트웨이를 통해 FTP URI를 요청하는 경우를 보자.

```
(클라이언트 → 게이트웨이)
GET ftp://http-guide.com/pub/welcome.txt HTTP/1.0

(게이트웨이 → 클라이언트)
HTTP/1.0 200 OK
Date: Sun, 11 Nov 2001 21:01:59 GMT
Via: FTP/1.0 proxy.irenes-isp.net (Traffic-Server/5.0.1-17882 [cMsf])
Last-modified: Sun, 11 Nov 2001 21:05:24 GMT
Content-type: text/plain

Hi there. This is an FTP server.
```

*예제 13-3. HTTP/FTP 게이트웨이가 수신 프로토콜을 `Via`에 기록한다 (HTTP-DG 6장 그림 6-22 기준)*

수신 프로토콜이 `FTP`임에 주목하라. 선택적 주석에는 프록시 제품명과 버전, 벤더 진단 정보가 들어 있다.

**`Server` 헤더와의 구별.** `Server` 응답 헤더는 **원 서버**가 쓰는 소프트웨어를 기술한다. 응답이 프록시를 거쳐 전달될 때 **프록시가 `Server` 헤더를 수정해서는 안 된다.** `Server`는 원 서버의 것이다. 프록시는 대신 `Via` 항목을 추가해야 한다.

### Via의 프라이버시·보안 함의

`Via` 문자열에 정확한 호스트명이 들어가지 않기를 바라는 경우가 있다. 일반적으로 이 동작이 명시적으로 활성화되지 않는 한, **네트워크 방화벽의 일부인 프록시 서버는 방화벽 뒤 호스트들의 이름과 포트를 전달해서는 안 된다.** 방화벽 뒤 네트워크 구조에 대한 지식은 악의적 주체에게 유용할 수 있기 때문이다. 컴퓨터 이름과 버전 번호로 보안 경계 뒤의 네트워크 구조를 학습할 수 있고, 컴퓨터 이름 자체가 조직 내부 프로젝트의 단서가 되기도 한다.

노드 이름 전달이 활성화되지 않았다면, 보안 경계에 속한 프록시는 호스트명을 적절한 가명으로 대체해야 한다. 다만 실제 이름을 가리더라도 **각 프록시에 대한 `Via` 경유점 항목 자체는 유지하려고 노력해야 한다.**

내부 아키텍처의 설계와 토폴로지를 감춰야 하는 강한 프라이버시 요구가 있는 조직이라면, `received-protocol` 값이 동일한 연속된 경유점들을 하나로 합칠 수 있다.

```
Via: 1.0 foo, 1.1 devirus.company.com, 1.1 access-logger.company.com
```

는 다음으로 축약될 수 있다.

```
Via: 1.0 foo, 1.1 concealed-stuff
```

단, **같은 조직의 통제 아래 있고 호스트가 이미 가명으로 대체된 경우가 아니면 합쳐서는 안 되며, `received-protocol` 값이 다른 항목들도 합쳐서는 안 된다.**

이 규칙들이 말하는 바를 이 책의 언어로 옮기면 이렇다. **`Via`는 경로에 대한 진술이며, 진술의 정확성과 노출 사이에는 교환 관계가 있다.** 8.6절이 `Via`를 "경로에 대한 진술"로 분류하고 신뢰 등급을 매긴 것이 이 절의 구체적 근거를 얻은 셈이다. 그리고 25.6절의 정찰 관점에서 보면, `Via`와 `Server`는 **응답이 스스로 알려 주는 인프라 정보**다.

### TRACE 메서드

프록시는 메시지를 전달하면서 그것을 바꿀 수 있다. 헤더가 추가·수정·제거되고, 본문이 다른 형식으로 변환된다. 프록시가 정교해지고 더 많은 벤더가 프록시 제품을 배포할수록 상호운용 문제도 늘어난다. 프록시 네트워크를 쉽게 진단하려면 **메시지가 홉을 지나며 어떻게 바뀌는지를 직접 볼 방법**이 필요하다.

HTTP/1.1의 `TRACE` 메서드가 그 방법이다. `TRACE`는 요청 메시지가 프록시 사슬을 지나가는 것을 추적하게 해, 메시지가 어떤 프록시들을 지나는지와 각 프록시가 요청 메시지를 어떻게 수정하는지를 관찰하게 한다.

`TRACE` 요청이 목적지 서버에 닿으면, **전체 요청 메시지가 HTTP 응답의 본문에 담겨 송신자에게 그대로 반사된다.** `TRACE` 응답의 `Content-Type`은 `message/http`이고 상태 코드는 `200 OK`다. 응답이 도착하면 클라이언트는 서버가 실제로 받은 메시지와 그것이 지나온 프록시 목록(`Via` 헤더)을 확인할 수 있다.

```
(클라이언트가 보낸 TRACE 요청)
TRACE /index.html HTTP/1.1
Host: www.joes-hardware.com
Accept: text/html

(서버가 돌려준 TRACE 응답)
HTTP/1.1 200 OK
Content-Type: message/http
Content-Length: 269
Via: 1.1 cache.joes-hardware.com, 1.1 p1127.att.net, 1.1 proxy.irenes-isp.net

TRACE /index.html HTTP/1.1
Host: www.joes-hardware.com
Accept: text/html
Via: 1.1 proxy.irenes-isp.net, 1.1 p1127.att.net, 1.1 cache.joes-hardware.com
X-Magic-CDN-Thingy: 134-AF-0003
Cookie: access-isp="Irene's ISP, California"
Client-ip: 209.134.49.32
```

*예제 13-4. `TRACE` 응답은 수신된 요청 메시지를 그대로 반사한다 (HTTP-DG 6장 그림 6-23 기준)*

이 예시를 자세히 볼 값이 있다. 클라이언트가 보낸 요청에는 세 줄밖에 없었다. 서버가 받은 요청에는 **경로 위의 중간자들이 붙인 네 개의 헤더**가 더 있다. `Via`, `X-Magic-CDN-Thingy`, `Cookie`, `Client-ip`다. 클라이언트는 자신이 그런 헤더를 보낸 적이 없다.

이 사실이 이 장의 논지를 한 번에 보여 준다. **종단이 보는 메시지는 다른 종단이 보낸 메시지가 아니다.** 4.6절이 `X-Forwarded-For`에 대해, 8.6절이 헤더 일반에 대해 내린 결론이 여기서 눈에 보이는 형태를 얻는다. 그리고 `Client-ip`처럼 경로에서 삽입된 헤더를 서버가 신원 판단에 쓴다면(→ 20.2), 그 판단의 근거는 클라이언트도 서버도 통제하지 않는 값이다.

`TRACE`는 프록시 흐름 디버깅에 매우 유용하지만, HTTP-DG 집필 시점 기준으로 널리 구현되지는 않았다.

> **`TRACE`의 다른 얼굴 — 8.3.3절의 되풀이**
>
> 8.3.3절은 `TRACE`를 메서드의 관점에서 다루면서 그것이 **요청을 그대로 반사하는 메서드**임을 지적했다. 이 절은 왜 그런 메서드가 필요했는지를 설명한다. 두 서술을 겹쳐 놓으면 결론은 하나다. **진단을 위해 존재하는 반사 능력은, 그 자체로 클라이언트가 보지 못하던 값을 클라이언트에게 보여 주는 통로다.** 경로에서 삽입된 인증·식별 헤더가 그 안에 담긴다. 이것이 실무에서 `TRACE`를 서버와 프록시에서 끄도록 권고하는 이유이며, 메서드 제한이 실제로 강제되는지는 8.3.4절과 24.5절의 문제다.

### Max-Forwards

보통 `TRACE` 메시지는 중간 프록시 개수와 무관하게 목적지 서버까지 간다. `Max-Forwards` 헤더로 `TRACE`와 `OPTIONS` 요청의 프록시 홉 수를 제한할 수 있다. 무한 루프로 메시지를 돌리는 프록시 사슬을 시험하거나, 사슬 중간의 특정 프록시가 무슨 일을 하는지 확인할 때 유용하다.

`Max-Forwards` 요청 헤더는 이 요청 메시지가 앞으로 몇 번 더 전달될 수 있는지를 나타내는 정수 하나를 담는다.

- **값이 0이면**, 수신자는 자신이 원 서버가 아니더라도 `TRACE` 메시지를 더 전달하지 말고 클라이언트 쪽으로 반사해야 한다.
- **값이 0보다 크면**, 전달되는 메시지에는 값이 1 감소한 `Max-Forwards` 필드가 들어 있어야 한다.

모든 프록시와 게이트웨이는 `Max-Forwards`를 지원해야 한다. 이 헤더로 프록시 사슬의 임의 홉에서 요청이 어떤 모습인지를 볼 수 있다.

```
TRACE /index.html HTTP/1.1
Host: www.joes-hardware.com
Max-Forwards: 2
Accept: text/html

클라이언트 ──► 프록시1 ──► 프록시2 ──► 프록시3 ──► 서버
            (M-F: 2)   (M-F: 1)   (M-F: 0)
                                   여기서 반사된다
```

*그림 13-7. `Max-Forwards`로 전달 홉 수를 제한한다 (HTTP-DG 6장 그림 6-24 기준)*

여기서 "최종 수신자"의 정의가 중요하다. **최종 수신자는 원 서버이거나, `Max-Forwards` 값 0을 받은 첫 프록시 또는 게이트웨이다.** 즉 `Max-Forwards`는 메시지의 종착지를 요청자가 지정할 수 있게 하는 필드다. 13.12절이 "메서드 해석"을 불일치 지점 목록에 올리는 이유 중 하나가 여기 있다. 홉마다 이 값을 정확히 감소시키고 0에서 멈춘다는 규칙이 지켜지지 않으면, **어느 홉이 응답을 만들었는지가 불확정해진다.**

> **이 절이 뒷받침하는 것**
>
> - `Via`가 경로에 대한 진술이며 토폴로지를 노출한다는 사실 → **8.6**(헤더의 신뢰성), **25.6**(서버 핑거프린팅), **16.4**(로그가 누출하는 것)
> - `TRACE`가 경로에서 삽입된 헤더를 반사한다는 사실 → **8.3.3**(`TRACE` 메서드), **8.3.4**(메서드 제한 우회), **20.2**(IP 기반 식별)
> - 홉마다 메시지가 달라진다는 것을 실제로 볼 수 있다는 사실 → **13.12**(불일치 지점 목록), **5.6**(중간자 통과)

## 13.7 프록시 인증

프록시는 접근 제어 장치로 동작할 수 있다. HTTP는 사용자가 프록시에 유효한 접근 자격증명을 제시할 때까지 콘텐츠 요청을 막는 **프록시 인증(proxy authentication)** 메커니즘을 정의한다.

동작은 네 단계다.

1. 제한된 콘텐츠에 대한 요청이 프록시에 도착하면, 프록시는 **`407 Proxy Authorization Required`** 상태 코드로 자격증명을 요구하며, 자격증명을 어떻게 제시할지 기술하는 **`Proxy-Authenticate`** 헤더 필드를 함께 보낸다.
2. `407` 응답을 받은 클라이언트는 로컬 데이터베이스에서 찾거나 사용자에게 물어 필요한 자격증명을 모은다.
3. 자격증명을 얻으면 클라이언트는 **`Proxy-Authorization`** 헤더 필드에 자격증명을 담아 요청을 다시 보낸다.
4. 자격증명이 유효하면 프록시는 원 요청을 사슬 아래로 전달한다. 그렇지 않으면 또 다른 `407`을 보낸다.

```
(a) 클라이언트 → 프록시
    GET http://server.com/secret.jpg HTTP/1.0

(b) 프록시 → 클라이언트
    HTTP/1.0 407 Proxy Authorization Required
    Proxy-Authenticate: Basic realm="Secure Stuff"

(c) 클라이언트 → 프록시
    GET http://server.com/secret.jpg HTTP/1.0
    Proxy-Authorization: Basic YnJpOmZvbw==

(d) 프록시 → 클라이언트
    HTTP/1.0 200 OK
    Content-type: image/jpeg
    ...<이미지 데이터>...
```

*예제 13-5. 프록시 인증의 네 단계 (HTTP-DG 6장 그림 6-25 기준)*

### 401과 407 — 두 개의 인증 축

이 메커니즘은 21장이 다루는 서버 인증과 **문법적으로 평행하지만 의미적으로 다른 축**에 있다. 이 구별을 표로 고정한다.

**표 13-7. 서버 인증과 프록시 인증의 대응 (HTTP-DG 6장·12장 기준)**

| 항목 | 서버 인증 | 프록시 인증 |
|---|---|---|
| 챌린지 상태 코드 | `401 Unauthorized` | `407 Proxy Authorization Required` |
| 챌린지 헤더 | `WWW-Authenticate` | `Proxy-Authenticate` |
| 자격증명 헤더 | `Authorization` | `Proxy-Authorization` |
| 헤더의 범위 | **종단 간(end-to-end)** | **홉 단위(hop-by-hop)** |
| 누구에게 자신을 증명하는가 | 원 서버 | **바로 다음 프록시** |
| 원 서버가 이 신원을 아는가 | 그렇다 | **아니다** |

마지막 두 행이 이 절의 핵심이다. 프록시 인증 헤더는 **홉 단위 헤더**다(→ 8.5, 9.2). 즉 그것을 받은 프록시가 소비하고, 다음 홉으로 전달하지 않는다. 결과적으로 **프록시 인증은 사용자를 프록시에게 식별시킬 뿐 원 서버에게 식별시키지 않는다.** 원 서버가 보는 것은 프록시다.

이 성질이 두 가지를 함의한다.

**첫째, 프록시에서의 접근 제어는 애플리케이션의 인가와 다른 층에 있다.** 프록시가 "이 사용자는 서버 B에 접근할 수 있다"고 판단해도, 서버 B의 애플리케이션은 그 판단을 알지 못하고 자기 판단을 따로 해야 한다. 두 판단이 어긋나면 어느 쪽이 유효한지는 **경로에 의해 결정된다.** 13.2절이 짚은 전제 — 웹 서버가 프록시에서 온 요청만 받도록 설정돼야 한다 — 가 여기서 다시 필요해진다. 그 전제가 없으면 프록시를 우회한 직접 연결이 접근 제어 전체를 무효화한다.

**둘째, 사슬에서는 잘 동작하지 않는다.** HTTP-DG의 서술은 분명하다. **프록시 인증은 사슬에 여러 프록시가 있고 각자가 인증에 참여할 때 대체로 잘 동작하지 않는다.** 자격증명을 프록시 사슬의 특정 경유점과 결부시키자는 HTTP 확장 제안들이 있었으나 널리 구현되지 않았다. 홉 단위 헤더는 이름 그대로 **한 홉만을 위한 것**이므로, 두 번째 프록시가 자기 챌린지를 보내면 클라이언트는 어느 프록시가 무엇을 요구하는지 구별할 수단이 부족하다.

### 터널과의 관계

프록시 인증은 `CONNECT`로 만드는 터널에도 그대로 쓸 수 있다. 13.10절에서 다시 다룬다. 요점만 미리 적으면, **터널을 열 권리를 인증으로 통제할 수 있다**는 것이며, 이것이 터널의 남용을 제한하는 두 장치 중 하나다(다른 하나는 포트 제한).

인증 메커니즘 자체 — Basic의 base-64, Digest의 다이제스트 계산, 보호 공간, 다중 챌린지 — 는 21장의 소관이다. **프록시 인증과 대리 인증의 상세는 21.9절이 이어받는다.**

> **이 절이 뒷받침하는 것**
>
> - `Proxy-Authenticate`·`Proxy-Authorization`이 홉 단위 헤더라는 사실 → **8.5**, **9.2**(`Connection` 헤더와 홉 단위 처리), **부록 E.2**
> - 프록시 인증이 원 서버에 신원을 전달하지 않는다는 사실 → **21.9**(프록시 인증과 대리 인증), **24.7**(인가는 경계 검증의 한 형태)
> - 프록시 우회가 접근 제어를 무효화한다는 사실 → **12.8**, **15.9**(공유 환경), **24.1**(완전히 보호되지 않은 기능)

## 13.8 프록시 상호운용성과 헤더 보존 문제

클라이언트, 서버, 프록시는 여러 벤더가 서로 다른 버전의 HTTP 명세에 맞춰 만든다. 지원 기능이 제각각이고 버그도 제각각이다. 프록시는 **서로 다른 프로토콜을 구현하고 골치 아픈 특이 동작을 가진** 클라이언트 측 장치와 서버 측 장치 사이를 중재해야 한다.

이 절은 그 중재를 위해 명세가 프록시에 부과한 의무를 정리하고, 각 의무가 13.12절에서 어떤 항목으로 되돌아오는지를 표시한다.

### 알 수 없는 헤더와 메서드의 처리

프록시는 자신을 통과하는 모든 헤더 필드를 이해하지 못할 수 있다. 어떤 헤더는 프록시 자신보다 나중에 나온 것이고, 어떤 것은 특정 애플리케이션 고유의 맞춤 헤더다. 규칙은 두 가지다.

- **프록시는 인식하지 못하는 헤더 필드를 전달해야 한다.**
- **프록시는 같은 이름을 가진 헤더 필드들의 상대적 순서를 유지해야 한다.**

두 번째 규칙에는 근거가 있다. 같은 필드 이름을 가진 헤더 필드가 여러 개 있을 수 있지만, 그렇다면 그것들은 **쉼표로 구분된 목록으로 동등하게 결합될 수 있어야 한다.** 따라서 같은 이름의 필드가 수신된 **순서가 결합된 필드 값의 해석에 유의미하며**, 프록시는 메시지를 전달할 때 같은 이름 필드들의 상대 순서를 바꿀 수 없다.

메서드도 마찬가지다. **프록시가 어떤 메서드를 모르더라도, 가능하다면 다음 홉으로 메시지를 전달하려고 시도해야 한다.** 지원하지 않는 메서드를 터널링하지 못하는 프록시는 오늘날 대부분의 네트워크에서 쓸모가 없다. HTTP-DG 집필 시점의 근거는 실무적이었다. 아웃룩을 통한 핫메일 접근이 HTTP 확장 메서드를 광범위하게 사용했다.

이 두 규칙을 이 책의 논지로 읽으면 이렇게 된다.

> **프록시는 자신이 이해하지 못하는 것을 통과시키도록 요구받는다.** 그래야 프로토콜이 진화할 수 있기 때문이다. 그러나 통과시킨다는 것은 **그것이 하류에서 어떤 의미를 갖는지 모르는 채로 넘긴다**는 뜻이다.

중복 헤더의 순서 보존 규칙은 특히 시사적이다. 명세는 **중복 헤더가 존재할 수 있음을 전제**하고, 그 처리 방식을 "쉼표 결합과 동등해야 한다"는 조건으로만 규정한다. 어떤 구현이 첫 번째를 쓰고 어떤 구현이 마지막을 쓴다면, 두 구현 모두 자기 나름으로는 이 조건을 만족한다고 주장할 수 있다. 그 대상이 `Host`나 `Content-Length`라면 결과가 달라진다(→ 13.12).

### OPTIONS — 선택적 기능 지원의 발견

HTTP `OPTIONS` 메서드는 클라이언트(또는 프록시)가 웹 서버 또는 서버의 특정 리소스가 지원하는 기능을 발견하게 해 준다. 클라이언트는 서버와 상호작용하기 전에 `OPTIONS`로 서버의 능력을 파악해, 기능 수준이 다른 프록시·서버와의 상호운용을 쉽게 만들 수 있다.

`OPTIONS` 요청의 URI가 별표(`*`)이면 요청은 **서버 전체의 지원 기능**에 관한 것이다.

```
OPTIONS * HTTP/1.1
```

URI가 실제 리소스이면, 그 리소스에 대해 사용 가능한 기능을 묻는다.

```
OPTIONS http://www.joes-hardware.com/index.html HTTP/1.1
```

성공하면 `200 OK` 응답이 지원 기능을 기술하는 헤더 필드들과 함께 돌아온다. HTTP/1.1이 응답에 대해 명시한 유일한 헤더 필드는 **`Allow`** 헤더로, 서버(또는 특정 리소스)가 지원하는 메서드를 기술한다. `OPTIONS`는 더 많은 정보를 담은 선택적 응답 본문을 허용하지만 그 내용은 정의돼 있지 않다.

```
클라이언트 ──► [프록시] ──► 서버
              OPTIONS * HTTP/1.1

           ◄── HTTP/1.1 200 OK
               Allow: GET,PUT,POST,HEAD,TRACE,OPTIONS
```

*그림 13-8. `OPTIONS`로 서버가 지원하는 메서드를 찾는다 (HTTP-DG 6장 그림 6-26 기준)*

`Allow` 엔티티 헤더 필드는 요청 URI가 식별하는 리소스가 지원하는 메서드 집합을 나열한다. 요청 URI가 `*`이면 서버 전체가 대상이다.

```
Allow: GET, HEAD, PUT
```

`Allow`는 **요청 헤더로도 쓸 수 있어**, 새로 만들 리소스가 지원했으면 하는 메서드를 권고할 수 있다. 서버가 그 메서드들을 반드시 지원해야 하는 것은 아니다. 모든 리소스가 모든 메서드를 지원하지는 않는다. CGI 스크립트 질의는 파일 `PUT`을 지원하지 않을 수 있고, 정적 HTML 파일은 `POST`를 받지 않는다.

정찰 관점에서 `OPTIONS`와 `Allow`는 **서버가 스스로 공개하는 메서드 목록**이다. 25.6절이 이것을 기술 식별의 입력으로 쓰고, 24.5절이 그 목록과 실제 강제되는 제한이 일치하는지를 시험한다. `Max-Forwards`가 `OPTIONS`의 전달도 제한한다는 점은 13.6절에서 이미 봤다.

### 관용성이라는 설계 결정

13.5절이 "프록시는 프로토콜 경찰이 되려 해서는 안 된다"는 권고를 인용했다. 이 절의 규칙들 — 미지 헤더 전달, 미지 메서드 전달, 순서 보존 — 은 모두 같은 방향이다. **프록시의 미덕은 관용이며, 관용의 목적은 상호운용성이다.**

이 설계 결정의 대가를 표로 정리한다.

**표 13-8. 프록시의 관용성 규칙과 그 보안적 귀결 (이 책이 구성)**

| 명세가 요구하는 관용 | 이유 | 보안적 귀결 | 13.12의 항목 |
|---|---|---|---|
| 미지 헤더를 전달한다 | 프로토콜 진화 | 프록시가 의미를 모르는 값이 종단에 도달한다 | 헤더 이어쓰기, 중복 헤더 |
| 같은 이름 헤더의 순서를 유지한다 | 결합 의미 보존 | **중복 헤더의 존재 자체가 전제된다** | 중복 헤더 |
| 미지 메서드를 전달한다 | 확장 메서드 지원 | 메서드 기반 정책이 미지 메서드에 무력하다 | 메서드 해석 |
| URI를 다시 쓰지 않는다 | 하류 호환 | 정책 지점과 실행 지점이 다른 문자열을 본다 | URL 정규화 |
| 엄격한 준수를 강제하지 않는다 | 기존 서비스 보호 | **모호한 메시지가 걸러지지 않고 통과한다** | 전 항목 |

이 표의 오른쪽 열이 13.12절의 목록이 되고, 마지막 행이 그 절의 방어 항목 중 "모호한 입력을 거부한다"와 정면으로 충돌한다. 그 충돌을 어디서 해소해야 하는지가 13.12절의 결론이다.

## 13.9 게이트웨이 — 프로토콜 게이트웨이, 리소스 게이트웨이, 애플리케이션 인터페이스

웹은 콘텐츠를 배포하는 도구로 출발했지만, 사람들은 정적 문서를 올리는 데 그치지 않고 데이터베이스 콘텐츠나 동적으로 생성되는 페이지 같은 더 복잡한 리소스를 공유하고자 했다. 동시에 HTTP는 애플리케이션 개발자에게 **기반 구성 요소**가 됐다. 다른 프로토콜의 트래픽을 HTTP로 감싸 기업 방화벽을 통과시키는 식으로, HTTP 위에 다른 프로토콜을 얹는 방식이 널리 쓰인다.

**게이트웨이는 리소스와 애플리케이션 사이의 접착제다.** 애플리케이션이 HTTP나 다른 정의된 인터페이스로 게이트웨이에 요청 처리를 부탁하면, 게이트웨이가 응답을 제공한다. 게이트웨이는 데이터베이스에 질의 언어로 말하거나 동적 콘텐츠를 생성하며, 포털처럼 동작한다. 요청이 들어가고 응답이 나온다.

### 클라이언트 측과 서버 측

웹 게이트웨이는 한쪽에서 HTTP를 말하고 다른 쪽에서 다른 프로토콜을 말한다. 게이트웨이는 클라이언트 측과 서버 측 프로토콜을 슬래시로 구분해 기술한다.

```
<클라이언트 측 프로토콜>/<서버 측 프로토콜>
```

HTTP 클라이언트를 NNTP 뉴스 서버에 잇는 게이트웨이는 HTTP/NNTP 게이트웨이다. 변환이 어느 쪽을 위해 이뤄지는가에 따라 두 부류로 나눈다.

- **서버 측 게이트웨이(HTTP/\*)** — 클라이언트와는 HTTP를, 서버와는 외래 프로토콜을 말한다.
- **클라이언트 측 게이트웨이(\*/HTTP)** — 클라이언트와는 외래 프로토콜을, 서버와는 HTTP를 말한다.

> 서로 다른 HTTP 버전 사이를 변환하는 웹 프록시는 양쪽을 협상하기 위해 정교한 로직을 수행한다는 점에서 게이트웨이와 닮았다. 그러나 양쪽 모두에서 HTTP를 말하므로 기술적으로는 프록시다. 이 구별이 11.13절의 "프로토콜 번역 지점"과 이 절 사이의 경계다.

게이트웨이로 HTTP 트래픽을 보내는 방법은 프록시와 같다. 브라우저를 명시적으로 설정하거나, 트래픽을 투명하게 가로채거나, 게이트웨이를 서러게이트로 배치한다. 브라우저에서 FTP URL 전체를 특정 게이트웨이(예: `gw1.joes-hardware.com:8080`)로 보내도록 설정하면, 일반 HTTP 트래픽은 원 서버로 그대로 흐르고 FTP URL 요청만 HTTP 요청 형태로 게이트웨이에 간다.

### 프로토콜 게이트웨이 (1) — HTTP/FTP 서버 측 게이트웨이

서버 측 웹 게이트웨이는 인바운드로 향하는 클라이언트의 HTTP 요청을 외래 프로토콜로 변환한다. FTP 리소스에 대한 요청을 예로 보자.

```
(클라이언트 → 게이트웨이, HTTP)
GET ftp://ftp.irs.gov/pub/00-index.txt HTTP/1.0
Host: ftp.irs.gov
User-agent: SuperBrowser 4.2

(게이트웨이 → FTP 서버, 포트 21의 제어 커넥션)
USER anonymous
PASS joe
CWD /pub
TYPE A
MDTM 00-index.txt
PASV
RETR 00-index.txt
```

*예제 13-6. HTTP/FTP 게이트웨이는 HTTP 요청을 FTP 명령열로 옮긴다 (HTTP-DG 8장 그림 8-5 기준)*

게이트웨이가 하는 일은 순서대로 이렇다. `USER`와 `PASS`로 서버에 로그인하고, `CWD`로 올바른 디렉터리로 이동하고, 다운로드 타입을 ASCII로 설정하고, `MDTM`으로 문서의 최종 수정 시각을 가져오고, `PASV`로 수동 데이터 검색 요청을 예고하고, `RETR`로 객체 검색을 요청한 뒤, 제어 채널이 알려 준 포트로 데이터 커넥션을 연다. 데이터 채널이 열리는 즉시 객체 콘텐츠가 게이트웨이로 흘러오고, 검색이 끝나면 객체가 HTTP 응답으로 클라이언트에 전달된다.

**이 예제를 이 책의 눈으로 다시 보라.** URL 안의 경로 문자열 `/pub/00-index.txt`가 FTP의 `CWD` 인자와 `RETR` 인자로 **쪼개져 들어간다.** URL 문법에서 단순한 경로 구분자였던 `/`가 FTP 명령에서는 다른 의미를 얻고, FTP 프로토콜에서 줄 끝은 새로운 명령의 시작이다. 즉 **게이트웨이는 한 프로토콜의 데이터를 다른 프로토콜의 구조로 옮기는 지점**이며, 이것이 8.7절이 CR/LF에 대해, 28장이 백엔드 컴포넌트에 대해 서술한 문제와 정확히 같은 형태다.

### 프로토콜 게이트웨이 (2) — 보안 게이트웨이 두 방향

게이트웨이로 조직의 프라이버시와 보안을 높일 수 있다. 두 방향이 있고, 방향에 따라 성질이 크게 다르다.

**HTTP/HTTPS 서버 측 보안 게이트웨이**는 인바운드 웹 요청을 자동으로 암호화한다. 클라이언트는 평범한 HTTP로 웹을 이용하지만 게이트웨이가 세션을 암호화한다.

**HTTPS/HTTP 클라이언트 측 보안 액셀러레이터 게이트웨이**는 그 반대다. 웹 서버 앞에, 보통 눈에 보이지 않는 인터셉팅 게이트웨이나 리버스 프록시로 놓인다. 보안 HTTPS 트래픽을 받아 복호하고, 웹 서버에는 평범한 HTTP 요청을 보낸다.

```
   HTTPS(암호화)                     HTTP(평문)
브라우저 ─────────► [HTTPS/HTTP 보안 액셀러레이터] ─────────► www.example.com
                                                   보호된 내부 LAN
```

*그림 13-9. HTTPS/HTTP 보안 액셀러레이터 게이트웨이 (HTTP-DG 8장 그림 8-7 기준)*

이런 게이트웨이는 대개 특수 복호 하드웨어를 갖춰 원 서버보다 훨씬 효율적으로 보안 트래픽을 복호하고, 원 서버의 부하를 덜어 준다. **그러나 게이트웨이와 원 서버 사이에는 암호화되지 않은 트래픽이 흐르므로, 그 구간의 네트워크가 안전한지 반드시 확인해야 한다.**

이 한 문장이 19장 전체가 다시 다루는 주제의 씨앗이다. TLS 종료 지점은 **암호화의 종단**이며, 그 뒤는 평문이다. 조기 종료의 성능 논리(→ 19.2)와 혼합 콘텐츠·토큰 노출(→ 19.10)이 이 사실에서 나온다. 그리고 5.6절의 파서 계수에서 "TLS 종료 로드밸런서"가 복호 후 파싱을 수행하는 홉으로 등장한 이유이기도 하다.

### 리소스 게이트웨이 — 애플리케이션 서버

지금까지는 네트워크를 사이에 두고 클라이언트와 서버를 잇는 게이트웨이를 봤다. 그러나 **가장 흔한 형태의 게이트웨이는 애플리케이션 서버**이며, 이것은 목적지 서버와 게이트웨이를 하나의 서버로 합친 것이다. 애플리케이션 서버는 클라이언트와 HTTP로 말하고 서버 쪽에서 애플리케이션 프로그램에 연결하는 서버 측 게이트웨이다.

```
                          [ 애플리케이션 서버 ]
   클라이언트 A ──HTTP──►  웹 카메라 API      ──►  카메라 장치·소프트웨어
   클라이언트 B ──HTTP──►  전자상거래 API     ──►  전자상거래 애플리케이션
```

*그림 13-10. 애플리케이션 서버는 HTTP 클라이언트를 임의의 백엔드 애플리케이션에 잇는다 (HTTP-DG 8장 그림 8-8 기준)*

URI에 따라 요청이 서로 다른 API를 거쳐 서로 다른 프로그램으로 간다. 클라이언트 A의 요청은 디지털 카메라 애플리케이션으로 가고 결과 이미지가 HTTP 응답으로 포장돼 돌아온다. 클라이언트 B의 요청은 전자상거래 소프트웨어로 가고, 그 소프트웨어가 사용자를 일련의 HTML 페이지로 안내해 구매를 완료시킨다.

### CGI와 서버 확장 API

애플리케이션 게이트웨이의 첫 대중적 API는 **공통 게이트웨이 인터페이스(Common Gateway Interface, CGI)** 였다. CGI는 웹 서버가 특정 URL에 대한 HTTP 요청에 반응해 프로그램을 띄우고, 그 출력을 모아 HTTP 응답으로 돌려보내는 표준화된 인터페이스 집합이다.

게이트웨이가 필요한 리소스에 대한 요청이 오면 **서버는 요청을 처리할 헬퍼 애플리케이션을 새로 띄운다.** 헬퍼 애플리케이션에는 필요한 데이터가 전달된다. 대개 요청 전체이거나, URL의 질의 문자열에서 뽑은 "사용자가 데이터베이스에 돌리려는 질의" 같은 것이다. 헬퍼는 응답 또는 응답 데이터를 서버에 돌려주고, 서버가 그것을 클라이언트로 보낸다. **서버와 게이트웨이가 별개의 애플리케이션이므로 책임의 경계가 분명하다.**

CGI 처리는 사용자에게 보이지 않는다. 클라이언트 입장에서는 평범한 요청을 보낼 뿐, 서버와 CGI 애플리케이션 사이의 인계 절차를 전혀 알지 못한다. URL에 `cgi`라는 글자와 `?`가 있다는 것이 유일한 힌트다.

CGI에는 장단이 뚜렷하다. 서버와 거의 모든 종류의 리소스 사이에 단순하고 기능적인 접착제를 제공하고, 확장 기능을 서버 본체에서 분리해 **버그 있는 확장으로부터 서버를 보호한다.** 확장이 서버 자체에 붙어 있었다면 오류가 서버를 죽일 수 있다. 그러나 이 분리는 성능 비용을 치른다. **CGI 요청마다 새 프로세스를 띄우는 오버헤드가 상당히 크고**, 서버의 성능을 제한하며 기계 자원을 소모한다. 이를 우회하기 위해 나온 것이 **Fast CGI**로, CGI를 흉내 내되 상주 데몬으로 동작해 요청마다 프로세스를 만들고 없애는 비용을 제거한다.

CGI는 외부 인터프리터를 기성 HTTP 서버에 붙이는 깔끔한 방법이지만, 서버 자체의 동작을 바꾸거나 성능을 마지막 한 방울까지 짜내려면 부족하다. 이를 위해 서버 개발자들은 **서버 확장 API**를 제공한다. 확장 API는 개발자가 자기 코드를 서버에 접붙이거나 서버의 한 구성 요소를 통째로 교체하게 해 준다. 이 확장은 서버 아키텍처에 묶여 있어 대부분 특정 서버 종류에 종속된다.

서버 확장의 한 예가 마이크로소프트의 **FrontPage 서버 확장(FPSE)** 이다. FPSE는 FrontPage 클라이언트가 보내는 원격 프로시저 호출(RPC) 명령을 해석하며, **이 명령들은 HTTP 위에 얹혀 전달된다.** 구체적으로는 HTTP `POST` 메서드에 덧씌워진다. 발행 시스템으로서의 상세는 15.11절이 다룬다.

이 두 갈래의 차이가 보안에서 갖는 의미는 분명하다. **CGI는 별도 프로세스, 확장 API는 서버 프로세스 안이다.** 확장 API로 접붙인 코드의 결함은 서버 자체의 결함과 같은 권한을 갖는다(→ 31.3, 12.10). 그리고 요청마다 프로세스를 띄우는 구조는 자원 소모형 공격의 표적이 되기 쉽다(→ 45.8).

### 애플리케이션 인터페이스와 웹 서비스

웹 애플리케이션이 제공하는 서비스의 종류가 늘면서, HTTP가 **애플리케이션들을 서로 잇는 토대**의 일부가 될 수 있다는 점이 분명해졌다. 애플리케이션들을 엮을 때 까다로운 문제 중 하나는 둘이 데이터를 주고받을 프로토콜 인터페이스를 협상하는 일이며, 이는 대개 애플리케이션마다 개별적으로 이뤄진다.

함께 동작하려면 애플리케이션들은 보통 HTTP 헤더로 표현할 수 있는 것보다 복잡한 정보를 교환해야 한다. HTTP를 확장하거나 HTTP 위에 프로토콜을 얹는 두 가지 예가 앞에서 나왔다. **HTTP `POST` 메시지 위에 RPC를 얹는 방식**(FPSE)과 **HTTP 헤더에 XML을 더하는 방식**(WebDAV)이다. 후자는 15.11절, 서버 설정으로서의 위험은 12.7절이 다룬다.

인터넷 커뮤니티는 웹 애플리케이션들이 서로 대화하게 하는 표준과 프로토콜 집합을 만들었고, 이를 느슨하게 **웹 서비스(web services)** 라 부른다. 웹 서비스는 표준 웹 기술 위에 세워지며, **XML을 SOAP 위에 실어** 정보를 교환한다. XML(Extensible Markup Language)은 데이터 객체에 대한 맞춤 정보를 만들고 해석하는 방법을 제공하고, SOAP(Simple Object Access Protocol)은 XML 정보를 HTTP 메시지에 더하는 표준이다.

이 계열의 공격 표면 — SOAP 서비스 인젝션, XML 인터프리터의 외부 엔티티 처리 — 은 28.5절과 28.7절이 다룬다. 이 장이 짚을 것은 구조다. **HTTP 메시지 안에 다른 문법 체계가 통째로 들어앉고, 그 문법을 해석하는 파서가 하나 더 늘어난다.**

### 게이트웨이가 만드는 번역 지점 목록

**표 13-9. 게이트웨이 유형별 번역 대상과 그 지점의 해석 문제 (이 책이 구성)**

| 게이트웨이 유형 | HTTP 쪽 | 반대편 | 무엇이 번역되는가 | 그 지점의 문제 | 참조 |
|---|---|---|---|---|---|
| HTTP/FTP | URL 경로·스킴 | FTP 명령열 | 경로가 `CWD`·`RETR` 인자로 분해된다 | 줄 끝과 구분자의 의미가 달라진다 | 28.1 |
| HTTP/HTTPS (서버 측) | 평문 요청 | TLS 레코드 | 암호화 경계의 위치 | 암호화되지 않는 구간이 생긴다 | 19.2 |
| HTTPS/HTTP (액셀러레이터) | TLS 레코드 | 평문 요청 | 복호 후 재파싱 | **TLS 뒤의 평문 구간** | 19.2, 19.10 |
| HTTP/CGI | 요청 전체·질의 문자열 | 프로세스 인자·환경변수 | 문자열이 실행 컨텍스트로 넘어간다 | 인자 경계·인용 규칙 | 28.1 |
| 서버 확장 API | 요청 구조체 | 서버 내부 함수 호출 | 파싱된 구조가 그대로 전달된다 | 결함이 서버 권한을 갖는다 | 31.3 |
| HTTP/SOAP | 본문 | XML 문서 | 본문 안에 다른 문법 체계 | 파서가 하나 더 늘어난다 | 28.5, 28.7 |
| HTTP/DB (리소스 게이트웨이) | 질의 파라미터 | 질의 언어 | 값이 질의 구조로 들어간다 | 데이터와 구조의 혼동 | 27장 |

이 표의 다섯 번째 열이 전부 같은 말을 다르게 하고 있다. **번역 지점은 한 체계에서 데이터였던 것이 다른 체계에서 구조가 되는 자리다.** 11.13절이 HTTP/2.0에서 HTTP/1.x로의 번역에 대해 내린 판정 — "번역 지점은 필연적으로 메시지를 다시 파싱하고 다시 직렬화하는 지점이며, 따라서 10.4절이 정의한 의미의 파싱 불일치 지점이다" — 이 프로토콜 게이트웨이 전반으로 확장된 것이다.

> **이 절이 뒷받침하는 것**
>
> - 게이트웨이가 데이터를 다른 체계의 구조로 옮긴다는 사실 → **27장**(데이터 저장소 인젝션), **28.1**(OS 명령), **28.5**·**28.7**(XML·SOAP), **8.7**(CR/LF)
> - TLS 종료 뒤 평문 구간이 존재한다는 사실 → **19.2**(조기 종료), **19.10**(토큰 노출), **5.6**(파서 계수)
> - 서버 확장 API의 코드가 서버 권한을 갖는다는 사실 → **31.3**(프레임워크 결함), **12.10**(서버 강화)

## 13.10 터널 — CONNECT 메서드와 그 남용

**웹 터널(web tunnel)** 은 HTTP가 아닌 트래픽을 HTTP 커넥션으로 보내, 다른 프로토콜이 HTTP에 업혀 가게 한다. 터널을 쓰는 가장 흔한 이유는 **웹 트래픽만 허용하는 방화벽을 통과시키기 위해 비HTTP 트래픽을 HTTP 커넥션 안에 넣는 것**이다.

### CONNECT로 터널 세우기

웹 터널은 HTTP의 `CONNECT` 메서드로 만든다. `CONNECT` 프로토콜은 **HTTP/1.1 핵심 명세의 일부가 아니다.** HTTP/1.1 명세는 `CONNECT` 메서드를 예약해 두었을 뿐 그 기능을 기술하지 않는다. 그러나 널리 구현된 확장이며, 기술 규격은 Ari Luotonen의 만료된 인터넷 초안 "Tunneling TCP based protocols through Web proxy servers"와 그의 저서 *Web Proxy Servers*에 있다.

**`CONNECT` 메서드는 터널 게이트웨이에게 임의의 목적지 서버와 포트로 TCP 커넥션을 만들고, 그 후 클라이언트와 서버 사이의 데이터를 맹목적으로 중계할 것을 요청한다.**

```
(a) 클라이언트 → 게이트웨이
    CONNECT orders.joes-hardware.com:443 HTTP/1.0
    User-agent: SuperBrowser 4.2

(b),(c) 게이트웨이가 orders.joes-hardware.com:443 으로 TCP 커넥션을 연다

(d) 게이트웨이 → 클라이언트
    HTTP/1.0 200 Connection established
    Proxy-agent: Netscape-Proxy/1.1

(e) 이 시점부터 커넥션이 닫힐 때까지 원시 데이터가 양방향으로 자유롭게 흐른다
```

*예제 13-7. `CONNECT`로 터널을 세우는 절차 (HTTP-DG 8장 그림 8-10 기준)*

**요청 문법.** `CONNECT`의 문법은 시작줄을 제외하면 다른 HTTP 메서드와 형태가 같다. **요청 URI가 호스트명, 콜론, 포트 번호로 대체되며, 호스트와 포트를 모두 지정해야 한다.**

```
CONNECT home.netscape.com:443 HTTP/1.0
User-agent: Mozilla/4.0
```

시작줄 뒤에는 다른 HTTP 메시지와 마찬가지로 0개 이상의 요청 헤더 필드가 온다. 각 줄은 CRLF로 끝나고, 헤더 목록은 빈 CRLF로 끝난다.

**응답.** 요청을 보낸 클라이언트는 게이트웨이의 응답을 기다린다. 일반 HTTP 메시지처럼 `200` 응답 코드가 성공을 뜻한다. 관례적으로 이유 구절은 `Connection Established`로 쓴다. **일반 HTTP 응답과 달리 `Content-Type` 헤더를 포함할 필요가 없다.** 커넥션이 메시지 전달자가 아니라 **원시 바이트 중계기**가 되기 때문이다.

이 마지막 문장이 이 절의 핵심이다. 표 13-1에서 터널의 "파싱 범위"를 **시작줄만**이라고 적은 이유가 여기 있다. 터널을 세운 뒤로 게이트웨이는 흘러가는 바이트에 대해 **아무런 HTTP 구조도 가정하지 않는다.** 파서가 없으므로 파싱 불일치도 없다. 대신 검사도 없다.

### 데이터 터널링, 타이밍, 커넥션 관리

터널링되는 데이터는 게이트웨이에게 불투명하므로, **게이트웨이는 패킷의 순서와 흐름에 대해 어떤 가정도 할 수 없다.** 터널이 수립되면 데이터는 언제든 어느 방향으로든 자유롭게 흐른다. 터널의 두 끝(클라이언트와 게이트웨이)은 어느 커넥션에서든 언제든 패킷을 받을 준비가 돼 있어야 하고 즉시 전달해야 한다. 터널링되는 프로토콜에 데이터 의존성이 있을 수 있으므로 **어느 쪽도 입력 데이터를 무시해서는 안 된다.** 한쪽에서 데이터를 소비하지 않으면 반대편 생산자가 멈춰 교착에 빠질 수 있다.

성능 최적화로, 클라이언트는 `CONNECT` 요청을 보낸 뒤 **응답을 받기 전에** 터널 데이터를 보낼 수 있다. 데이터가 서버에 더 빨리 도달하지만, 게이트웨이가 요청 뒤에 따라오는 데이터를 제대로 처리할 수 있어야 한다는 뜻이기도 하다. 특히 **게이트웨이는 네트워크 I/O 요청이 헤더 데이터만 돌려줄 것이라고 가정해서는 안 되며**, 헤더와 함께 읽은 데이터를 커넥션이 준비되면 반드시 서버로 전달해야 한다. 요청 뒤에 데이터를 파이프라이닝하는 클라이언트는, 응답이 인증 챌린지나 그 밖의 `200`이 아닌 비치명적 상태로 돌아올 경우 **요청 데이터를 다시 보낼 준비**가 돼 있어야 한다. 요청의 TCP 패킷에 남은 공간보다 많은 데이터를 파이프라이닝하지 않는 편이 좋다. 게이트웨이가 파이프라이닝된 패킷을 다 받기 전에 커넥션을 닫으면 클라이언트 측 TCP 리셋이 발생할 수 있고, 그러면 클라이언트는 받은 게이트웨이 응답을 잃어 실패 원인이 네트워크 오류인지 접근 제어인지 인증 챌린지인지 구별할 수 없게 된다.

터널 종단 중 하나가 어느 시점에든 연결이 끊기면, 그 종단에서 온 미처리 데이터는 반대편으로 전달되고, 그 후 반대편 커넥션도 프록시에 의해 종료된다. 닫히는 종단으로 전달되지 못한 데이터가 있으면 그 데이터는 폐기된다.

이 서술을 9.9절과 겹쳐 읽으면 유용하다. **터널에는 메시지 경계가 없으므로, 커넥션 종료가 곧 데이터의 끝이라는 판정 외에 다른 판정이 없다.** 3.1.2절이 "TCP는 메시지 경계를 주지 않는다"고 한 상태 그대로다. HTTP가 그 위에 얹어 두었던 경계 규칙을 터널이 제거한 것이다.

### 왜 터널이 만들어졌는가 — SSL 터널링

웹 터널은 애초에 **암호화된 SSL 트래픽을 방화벽 너머로 나르기 위해** 개발됐다. 많은 조직이 보안을 위해 모든 트래픽을 패킷 필터링 라우터와 프록시 서버로 통과시킨다. 그런데 암호화된 SSL 같은 프로토콜은 정보가 암호화돼 있어 전통적 프록시로 프록싱할 수 없다. 터널은 SSL 트래픽을 HTTP 커넥션에 실어 80번 포트 HTTP 방화벽을 통과시킨다.

```
  (a) 직접 SSL 커넥션
      클라이언트 ──SSL──────────────────────────────► 서버 (포트 443)

  (b) HTTP 터널을 통한 SSL
      클라이언트 ──SSL 안의 HTTP──► [터널 종단, 포트 80] ──SSL──► 서버 (포트 443)
```

*그림 13-11. 직접 SSL 커넥션과 터널링된 SSL 커넥션 (HTTP-DG 8장 그림 8-12 기준)*

### SSL 터널링과 HTTP/HTTPS 게이트웨이의 차이

HTTPS는 다른 프로토콜과 마찬가지로 **게이트웨이 방식으로 처리할 수도 있다.** 클라이언트 대신 게이트웨이가 원격 HTTPS 서버와 SSL 세션을 열고 클라이언트를 대신해 HTTPS 트랜잭션을 수행하는 것이다. 응답은 프록시가 받아 복호하고 클라이언트에는 (안전하지 않은) HTTP로 보낸다. 게이트웨이가 FTP를 다루는 방식과 같다. 그러나 이 접근에는 세 가지 단점이 있다.

1. **클라이언트-게이트웨이 커넥션이 평범한, 안전하지 않은 HTTP다.**
2. **클라이언트가 원격 서버에 대해 SSL 클라이언트 인증(X.509 인증서 기반)을 수행할 수 없다.** 인증되는 주체가 프록시이기 때문이다.
3. **게이트웨이가 완전한 SSL 구현을 갖춰야 한다.**

반면 **SSL 터널링에 이 메커니즘을 쓰면 프록시에 SSL 구현이 필요 없다.** SSL 세션은 요청을 만드는 클라이언트와 목적지 보안 웹 서버 사이에 수립되고, 사이의 프록시는 암호화된 데이터를 터널링할 뿐 보안 트랜잭션에 다른 방식으로 관여하지 않는다.

이 대비가 19.8절이 이어받는 지점이다. **터널은 프록시가 내용을 보지 못하게 하고, 게이트웨이는 프록시가 내용을 보게 한다.** 기업이 후자를 선택하면 그것이 곧 조직 내부의 중간자다. 18.3절의 인증서 검증과 19.9절의 중간자 성립 조건이 그 배치에서 어떻게 재정의되는지가 19.8절의 주제다.

### 터널 인증

HTTP의 다른 기능도 적절한 경우 터널과 함께 쓸 수 있다. 특히 **프록시 인증으로 클라이언트가 터널을 사용할 권리를 인증할 수 있다.**

```
(a) CONNECT orders.joes-hardware.com:443 HTTP/1.0
    User-agent: SuperBrowser 4.2

(b) HTTP/1.0 407 Proxy authentication required
    Proxy-authenticate: Basic realm="wormhole"

(c) CONNECT orders.joes-hardware.com:443 HTTP/1.0
    User-agent: SuperBrowser 4.2
    Proxy-authorization: Basic YnJpYW4tdG90dHk6T3ch

(d),(e) 게이트웨이가 포트 443으로 TCP 커넥션을 연다

(f) HTTP/1.0 200 Connection established
```

*예제 13-8. 게이트웨이는 터널 사용 전에 클라이언트를 프록시 인증할 수 있다 (HTTP-DG 8장 그림 8-13 기준)*

13.7절이 설명한 `407` 흐름이 `CONNECT`에 그대로 적용된다. 다만 여기서 인증되는 것은 **"이 콘텐츠에 접근할 권리"가 아니라 "이 목적지로 터널을 열 권리"** 다.

### 터널의 보안 고려사항

**일반적으로 터널 게이트웨이는 실제로 말해지는 프로토콜이 터널링하기로 한 그 프로토콜인지 확인할 수 없다.** 따라서 장난스러운 사용자는 SSL용으로 마련된 터널로 인터넷 게임 트래픽을 기업 방화벽 너머로 보낼 수 있고, 악의적 사용자는 터널로 텔넷 세션을 열거나 기업 이메일 스캐너를 우회해 메일을 보낼 수 있다.

**터널 남용을 최소화하려면 게이트웨이는 443(HTTPS) 같은 특정한 잘 알려진 포트에 대해서만 터널을 열어야 한다.**

이 두 문장이 터널의 보안 모델 전체다. 다시 정리하면 이렇다.

**표 13-10. 터널의 통제 지점 (HTTP-DG 8장 기준)**

| 통제 지점 | 무엇을 검사하는가 | 검사할 수 없는 것 |
|---|---|---|
| `CONNECT` 시작줄의 목적지 | 호스트명과 포트 | 그 호스트에서 실제로 도는 서비스 |
| 포트 허용 목록 | 포트 번호가 443인가 | **443 위로 흐르는 것이 정말 TLS인가** |
| 프록시 인증(`407`) | 요청자의 신원 | 터널이 세워진 뒤의 사용 내용 |
| 터널 수립 후 | **없음** | 전부 |

마지막 행이 요점이다. **터널은 정책 판단을 전부 시작 시점 한 번에 몰아넣고, 그 후로는 아무것도 판단하지 않는다.** 프록시가 접근 제어 장치로서 갖는 가치(13.2, 13.7)와 정면으로 상충한다. 13.2절에서 "보안 방화벽" 용도를 설명하며 "그 지점이 무엇을 보지 못하는지가 곧 구멍이 된다"고 적은 것이 이 절이다.

### 12.8절과의 구별

12.8절이 이미 이 구별을 표로 세워 두었으므로 여기서는 방향만 확인한다.

- **12.8절**은 **서버 설정의 문제**다. 프록시 기능이 의도치 않게 켜져 있고 통제되지 않는다. 방어는 서버 설정을 잠그는 것이다.
- **13.10절(이 절)** 은 **`CONNECT`라는 메서드 자체**의 이야기다. 정상적인 터널이 무엇이고 어떻게 남용되는가. 방어는 목적지 포트 제한과 터널 인증이다.
- **28.8절**은 **애플리케이션 코드의 문제**다. 서버가 프록시로 설정되지 않았어도 애플리케이션이 사용자가 준 URL로 요청을 보내면 같은 결과가 난다.

세 층위는 방어 지점이 다르며, 하나를 막았다고 나머지가 막히지 않는다.

> **이 절이 뒷받침하는 것**
>
> - 터널 수립 후 어떤 파싱도 일어나지 않는다는 사실 → **13.12**(파서 계수), **3.1.2**(메시지 경계 부재)
> - 프록시가 SSL 구현 없이 암호화 트래픽을 나른다는 사실 → **19.8**(프록시를 통한 TLS 터널링), **18.1**(HTTPS의 계층 구조)
> - 게이트웨이 방식이 클라이언트 인증서 인증을 불가능하게 한다는 사실 → **18.5**(클라이언트 인증서), **19.9**
> - 터널이 포트 필터링을 우회한다는 사실 → **12.8**, **28.8**(SSRF), **37.7**(WebSocket의 프록시 통과)

## 13.11 릴레이 — 잘못 구현된 중간자

**HTTP 릴레이(relay)** 는 HTTP 명세를 온전히 따르지 않는 단순한 HTTP 프록시다. **릴레이는 커넥션을 세울 만큼만 HTTP를 처리한 다음, 바이트를 맹목적으로 전달한다.**

HTTP는 복잡하다. 그래서 헤더와 메서드 로직 전부를 수행하지 않고 트래픽을 그냥 전달하는 뼈대만 있는 프록시를 만드는 것이 때로 유용하다. 맹목 릴레이는 구현이 쉬워서 단순한 필터링, 진단, 콘텐츠 변환을 제공하는 데 쓰이기도 한다. **그러나 상호운용 문제를 일으킬 소지가 심각하므로 극도로 조심해서 배치해야 한다.**

### keep-alive를 멈춰 세우는 릴레이

단순 맹목 릴레이의 구현에서 가장 흔하고 악명 높은 문제는 **`Connection` 헤더를 제대로 처리하지 않아 keep-alive 커넥션을 멈춰 세우는 것**이다.

9.7절이 이 이야기를 커넥션 관리의 관점에서 이미 다뤘다. 여기서는 **중간자 설계의 관점**에서 같은 사건을 다시 본다. 순서는 이렇다.

1. 웹 클라이언트가 `Connection: Keep-Alive` 헤더를 담아 릴레이에 메시지를 보낸다. keep-alive 커넥션을 원한다는 요청이다. 클라이언트는 그 요청이 받아들여졌는지 알기 위해 응답을 기다린다.
2. 릴레이는 HTTP 요청을 받지만 `Connection` 헤더를 이해하지 못하므로, 메시지를 **글자 그대로** 사슬 아래 서버로 넘긴다. 그러나 **`Connection`은 홉 단위 헤더다.** 단일 전송 링크에만 적용되며 사슬 아래로 전달돼서는 안 된다.
3. 릴레이된 요청이 웹 서버에 도착한다. 프록시된 `Connection: Keep-Alive` 헤더를 받은 웹 서버는 **릴레이(서버가 보기엔 여느 클라이언트와 같다)가 keep-alive를 원한다고 잘못 결론짓는다.** 서버는 동의하고 `Connection: Keep-Alive` 응답 헤더를 돌려보낸다. 이 시점에 서버는 릴레이와 keep-alive로 말하고 있다고 믿고 그 규칙을 지킨다. 그러나 **릴레이는 keep-alive에 대해 아무것도 모른다.**
4. 릴레이는 웹 서버의 응답 메시지를 클라이언트로 전달하면서 `Connection: Keep-Alive` 헤더도 함께 넘긴다. 클라이언트는 그 헤더를 보고 릴레이가 keep-alive에 동의했다고 가정한다. **이제 클라이언트와 서버 둘 다 자신이 keep-alive로 말하고 있다고 믿지만, 정작 그들이 대화하는 릴레이는 keep-alive를 전혀 모른다.**
5. 릴레이는 keep-alive를 모르므로 받은 데이터를 전부 클라이언트로 전달한 뒤 **원 서버가 커넥션을 닫기를 기다린다.** 그러나 원 서버는 릴레이가 커넥션을 열어 두라고 요청했다고 믿으므로 닫지 않는다. 릴레이는 커넥션이 닫히기를 기다리며 멈춘다.
6. 응답을 받은 클라이언트는 곧바로 다음 요청으로 넘어가, keep-alive 커넥션 위로 릴레이에 또 다른 요청을 보낸다. **단순 릴레이는 같은 커넥션에서 또 다른 요청이 오리라고 예상하지 않는다.** 브라우저는 진전 없이 계속 돌기만 한다.

릴레이를 조금 더 똑똑하게 만들어 이 위험을 없애는 방법들이 있지만, **프록시를 단순화하는 어떤 시도든 상호운용 문제의 위험을 안는다.** 특정 목적으로 단순 HTTP 릴레이를 만든다면 사용에 신중해야 하고, 대규모 배포라면 **진짜 HTTP 준수 프록시 서버를 쓰는 편을 강하게 고려해야 한다.**

### 릴레이가 보여 주는 일반형

이 사건을 개별 버그로 읽으면 요점을 놓친다. 릴레이가 드러내는 것은 **부분 구현 중간자(partially-implementing intermediary)** 라는 일반형이다.

- 릴레이는 **참여자처럼 보인다.** 클라이언트와 서버 모두 릴레이를 정상적인 HTTP 주체로 취급한다.
- 그러나 릴레이는 **종단들이 가정하는 규칙의 일부만 구현한다.**
- 종단들은 그 사실을 알 방법이 없다. **`Connection: Keep-Alive`가 왕복해 돌아왔다는 것이 릴레이가 그 의미를 이해했다는 증거가 되지 못한다.**

세 번째 항목이 이 장이 반복해 온 문장의 가장 순수한 형태다. **메시지가 통과했다는 사실은 그것이 이해됐다는 증거가 아니다.**

그리고 이 형태는 릴레이에만 나타나지 않는다. 표 13-8이 정리한 관용성 규칙 — 미지 헤더를 전달하고, 미지 메서드를 전달하고, 엄격한 준수를 강제하지 않는다 — 은 **모든 준수 프록시를 부분적으로 릴레이처럼 행동하게 만든다.** 완전한 프록시조차 자기가 모르는 확장에 대해서는 맹목 전달자다. 릴레이는 그 성질을 극단으로 밀어 놓은 사례일 뿐이다.

**표 13-11. 중간자의 이해 수준과 그 결과 (이 책이 구성)**

| 중간자 | 무엇을 이해하는가 | 이해하지 못하는 것을 어떻게 다루는가 | 종단이 알 수 있는가 |
|---|---|---|---|
| 준수 프록시 | 자신의 버전이 정의한 전부 | 전달한다 (`Via`에 버전 기록) | **`Via`로 부분적으로** |
| 릴레이 | 커넥션을 세울 만큼만 | 전달한다 (홉 단위 헤더 포함) | **아니다** |
| 터널 | 시작줄만 | 전달한다 (전부) | 안다 (자신이 요청했다) |
| 게이트웨이 | 양쪽 프로토콜 | 번역하거나 버린다 | `Via`의 프로토콜 이름으로 |

`Via` 헤더가 프로토콜 버전을 기록하도록 설계된 이유가 이 표의 마지막 열에 있다(→ 13.6). 그것이 **"경로 위의 각 중간자가 무엇을 이해할 수 있는가"를 뒤의 애플리케이션에 알리기 위한 유일한 표준 장치**다. 그리고 릴레이는 `Via`를 붙이지 않는다.

> **이 절이 뒷받침하는 것**
>
> - 홉 단위 헤더가 전달되면 무슨 일이 벌어지는가 → **9.2**(`Connection` 헤더의 함정), **9.7**(멍청한 프록시), **13.12**(불일치 지점 목록)
> - 부분 구현 중간자가 일반형이라는 사실 → **13.8**(관용성 규칙), **13.12**(방어의 방향)

## 13.12 중간자 공격 표면 정리 — 파싱 불일치가 발생하는 지점 목록

이 절은 이 장의 절정이자 Part I과 Part II가 남겨 둔 명제들의 회수 지점이다. 다섯 개의 문장이 여기로 모인다.

- **1.4절** — 계층 경계는 신뢰 경계가 아니다. 하위 계층이 상위 계층을 보호해 주지 않는다.
- **3.1.2절** — TCP는 바이트 스트림이며 메시지 경계를 주지 않는다. 경계는 HTTP가 스스로 세워야 한다.
- **9.11절** — 하나의 커넥션은 여러 트랜잭션이 공유하는 단위이며, 프록시 뒤에서는 여러 사용자가 공유한다.
- **10.4절** — 본문 경계를 두 헤더가 다르게 지시할 때, 규칙을 실행하는 주체가 여럿이면 판단이 갈린다.
- **11.13절** — 프로토콜 번역 지점은 필연적으로 다시 파싱하고 다시 직렬화하는 지점이다.

이 다섯이 하나의 그림이 되려면 먼저 셈이 필요하다. **경로 위에 파서가 몇 개 있는가.**

### (1) 경로 위의 파서를 세다

5.6절이 이 계수를 예고했다. 전형적인 배포에서 요청 하나가 통과하는 파싱 지점을 다시 가져온다.

```
브라우저
   │  ① 직렬화
   ▼
[기업 프록시 / PAC]           ② 파싱 → 정책 판단 → ③ 재직렬화     (→ 13.4, 13.5)
   ▼
[TLS 종료 로드밸런서]         ④ 복호 → 파싱 → 라우팅 → ⑤ 재직렬화 (→ 13.9, 19.2)
   ▼
[WAF]                         ⑥ 파싱 → 시그니처 검사              (→ 12.11)
   ▼
[리버스 프록시 / 캐시]        ⑦ 파싱 → 캐시 키 계산 → ⑧ 재직렬화  (→ 13.3, 14.4)
   ▼
[웹 서버]                     ⑨ 파싱 → 리소스 매핑                (→ 12.2)
   ▼
[애플리케이션 프레임워크]     ⑩ 파싱 → 라우팅 → 파라미터 바인딩   (→ 13.9, 31.3)
   ▼
애플리케이션 코드
```

*그림 13-12. 요청 하나가 통과하는 파싱 지점 (5.6절 그림 5-3과 동일)*

**요청 메시지 하나는 여섯 번 파싱되고 네 번 직렬화된다.** 파싱은 ②④⑥⑦⑨⑩의 여섯 번이고, 직렬화는 ①③⑤⑧의 네 번이다. 그중 ①은 브라우저의 최초 직렬화이고 ③⑤⑧이 경로 위에서의 재직렬화다. 5.6절이 세어 둔 수가 이것이다.

이 셈에 네 가지를 덧붙여야 실제 규모가 보인다.

**첫째, 이것은 하한이다.** 프록시 계층(13.3)이 3단이면 파싱-재직렬화 쌍이 둘 더 붙는다. 게이트웨이가 있으면 프로토콜 번역 지점이 추가된다(13.9). TLS 종료가 두 번(엣지와 내부망) 일어나는 배포도 흔하다.

**둘째, 응답 방향에도 같은 수의 파서가 있다.** 응답은 같은 경로를 거꾸로 지나며(13.6의 `Via` 역순), 각 홉이 응답 메시지를 다시 파싱하고 다시 직렬화한다. 요청과 응답을 합치면 셈은 두 배가 된다.

**셋째, 불일치의 기회는 파서의 수가 아니라 인접한 파서 쌍의 수다.** 파서가 N개 있으면 서로 이웃한 쌍은 N−1개이며, 각 쌍마다 "앞 홉이 이해한 메시지"와 "뒤 홉이 이해한 메시지"가 다를 수 있다. 여섯 개의 파서는 **다섯 개의 불일치 기회**를 만든다. 프록시 계층 하나를 더하면 여섯이 된다.

**넷째, 각 파서는 독립적인 구현이다.** 서로 다른 언어로, 서로 다른 시기에, 서로 다른 명세 해석으로 작성됐다. 13.8절이 정리한 관용성 규칙은 각 구현이 **모호한 입력을 자기 방식으로 해석해 통과시키도록 요구한다.** 그리고 각 재직렬화가 원본과 완전히 같은 바이트를 만든다는 보장은 어디에도 없다.

**표 13-12. 경로 위의 파서와 그 판단 근거 (5.6절 표 5-5의 확장)**

| 홉 | 파싱 | 재직렬화 | 무엇을 근거로 판단하는가 | 다른 홉의 해석을 검증할 수 있는가 | 상세 |
|---|---|---|---|---|---|
| 브라우저 | — | ① | 사용자 입력, DOM | — | 5.5 |
| 기업 프록시 | ② | ③ | 요청 대상, `Host`, 정책 | 아니다 | 13.5, 13.7 |
| TLS 종료 LB | ④ | ⑤ | SNI, `Host`, 경로 규칙 | 아니다 | 13.9, 19.2 |
| WAF | ⑥ | — | 정규화된 경로, 파라미터 값 | **아니다 (하류의 재해석을 못 본다)** | 12.11 |
| 리버스 프록시·캐시 | ⑦ | ⑧ | 캐시 키, 경로 규칙 | 아니다 | 13.3, 14.4 |
| 웹 서버 | ⑨ | — | docroot 매핑, 가상 호스트 | 아니다 | 12.2, 12.4 |
| 앱 프레임워크 | ⑩ | — | 라우팅 테이블, 바인딩 규칙 | 아니다 | 31.3 |

다섯 번째 열이 전부 "아니다"인 것이 이 표의 결론이다. **경로 위의 어느 홉도 다른 홉이 같은 바이트열을 자기와 똑같이 이해했는지 확인할 수단이 없다.** 확인에 가장 가까운 장치가 `TRACE`이며(13.6), 그것은 진단 도구이지 런타임 검증 장치가 아니다.

여기서 이 부의 명제가 완성된다.

> **판단하는 주체와 실행하는 주체가 다른 메시지를 본다면, 판단은 무효다.**
> 그리고 경로 위에 파서가 여섯 개 있다는 것은, 그런 일이 일어날 수 있는 자리가 다섯 군데 있다는 뜻이다.

### (2) 파싱 불일치가 발생하는 지점 목록

각 지점을 세 요소로 기술한다. **(a) 어느 두 주체가, (b) 무엇을 다르게 해석할 수 있고, (c) 그 결과 무엇이 가능해지는가.** 기법의 이름은 쓰지 않는다. 구조만 적는다.

#### ① 본문 경계

**(a) 두 주체** — 요청을 전달하는 중간자와, 그 요청을 최종 처리하는 종단. 또는 인접한 두 중간자.

**(b) 다르게 해석되는 것** — 요청 본문이 어디서 끝나는가. 10.2절과 10.3절이 본문 길이를 결정하는 두 방법(`Content-Length`와 청크 전송 인코딩)을 서술했고, 10.4절이 둘이 함께 있을 때 판단이 갈린다는 것을 보였다. 여기에 세 변형이 더해진다. **`Content-Length`가 두 개 있고 값이 다를 때**, **청크 크기 표기가 관용적으로 쓰일 때**(선행 0, 앞뒤 공백, 세미콜론 뒤의 확장 파라미터), **전송 인코딩 토큰이 예상 밖의 형태일 때**다. 각 파서는 자기 관용 규칙에 따라 하나를 고른다.

**(c) 가능해지는 것** — 앞 홉이 **하나의 요청**으로 센 바이트열을 뒤 홉이 **하나 반** 또는 **둘**로 센다. 뒤 홉의 입력 버퍼에는 다음 요청의 앞에 붙을 바이트가 남는다. 9.11절이 세운 두 전제 — 커넥션은 여러 트랜잭션이 공유하는 단위이고, 프록시 뒤에서는 여러 사용자가 그 커넥션을 공유한다 — 가 여기서 결합한다. **남은 바이트는 다음 트랜잭션의 시작으로 해석되고, 그 다음 트랜잭션의 주체는 다른 사용자일 수 있다.**

**→ 10.2, 10.3, 10.4, 9.11, 3.1.2**

#### ② 홉 단위 헤더의 처리

**(a) 두 주체** — `Connection` 헤더의 의미를 구현한 중간자와, 구현하지 않았거나 다르게 구현한 중간자(13.11의 릴레이가 극단이다).

**(b) 다르게 해석되는 것** — 어떤 헤더가 다음 홉으로 전달되고 어떤 헤더가 이 홉에서 소비돼야 하는가. 9.2절이 규칙을 정리했다. `Connection` 헤더는 **자신이 나열한 헤더 이름들을 이 홉에서 제거하라고 지시한다.** 즉 **어떤 헤더가 다음 홉에 도착할지를 앞 홉의 설정이 아니라 메시지 자신이 정한다.** 어떤 파서는 이 지시를 수행하고 어떤 파서는 수행하지 않는다.

**(c) 가능해지는 것** — 세 방향이다. 첫째, 홉 단위 헤더가 종단까지 도달해 종단이 자기 앞 홉과의 커넥션 규약을 오해한다(13.11의 keep-alive 정지가 그 무해한 버전이다). 둘째, `Connection` 목록에 이름을 올리는 것으로 **종단 간 헤더를 중간에서 사라지게 할 수 있다.** 사라진 헤더가 인증·식별·경로 정보를 담고 있었다면 하류의 판단이 달라진다. 셋째, 프록시 인증 헤더(13.7)가 홉 단위라는 사실과 결합하면, 어떤 홉이 어떤 자격증명을 소비했는지가 불확정해진다.

**→ 9.2, 9.7, 13.7, 13.11, 8.5**

#### ③ 중복 헤더

**(a) 두 주체** — 같은 이름의 헤더가 여러 개일 때 **첫 번째를 쓰는 구현**과 **마지막을 쓰는 구현**, 그리고 **쉼표로 결합하는 구현**.

**(b) 다르게 해석되는 것** — 13.8절이 인용한 명세의 규칙은 "같은 이름 필드들은 쉼표 구분 목록으로 동등하게 결합될 수 있어야 하며, 프록시는 그 상대 순서를 유지해야 한다"이다. 이 규칙은 **중복 헤더의 존재를 전제하되 어느 것이 유효한지를 정하지 않는다.** 대상이 `Host`, `Content-Length`, `Transfer-Encoding`, `Cookie`, `Authorization`처럼 **값 하나만을 기대하는 헤더**일 때 각 구현의 선택이 갈린다.

**(c) 가능해지는 것** — 라우팅을 정하는 홉과 리소스를 정하는 홉이 **서로 다른 값**을 쓴다. `Host`가 둘이면 앞 홉은 첫 번째로 가상 호스트를 고르고 뒤 홉은 두 번째로 고를 수 있다(→ 15.2). `Content-Length`가 둘이면 ①의 본문 경계 문제가 된다.

**→ 13.8, 8.5, 8.6, 15.2, 10.2**

#### ④ 헤더 이어쓰기

**(a) 두 주체** — 공백으로 시작하는 줄을 **앞 헤더 값의 연속**으로 해석하는 구현과, **새로운 헤더 줄** 또는 **오류**로 해석하는 구현.

**(b) 다르게 해석되는 것** — 하나의 논리적 헤더가 몇 줄에 걸쳐 있는가. 8.1절이 인용한 관용 규칙과 8.5절의 헤더 문법이 이 여지를 남긴다. 한 파서에게 두 줄은 값 하나이고, 다른 파서에게는 헤더 둘이거나 잘못된 요청이다.

**(c) 가능해지는 것** — 정책 지점이 **값의 일부만** 보고 판단하거나, 반대로 **다음 헤더를 앞 헤더의 값으로 흡수해** 다음 헤더를 없앤 것과 같은 효과를 낸다. ②·③과 결합하면 어떤 헤더가 어떤 홉에 도착하는지가 완전히 갈라진다.

**→ 8.1, 8.5, 8.7**

#### ⑤ 대소문자와 공백의 처리

**(a) 두 주체** — 헤더 이름 비교와 줄 끝 판정을 서로 다르게 구현한 두 파서.

**(b) 다르게 해석되는 것** — 네 가지다. **헤더 이름의 대소문자**(명세상 무관하지만 비교 구현이 다를 수 있다), **이름과 콜론 사이의 공백**(명세상 금지이나 처리 방식이 갈린다), **값 앞뒤의 공백과 탭**, 그리고 **줄 끝 판정** — CR과 LF가 함께 와야 하는가, LF 하나로도 줄이 끝나는가, 값 안의 단독 CR을 무엇으로 볼 것인가.

11.7.1절이 이 문제군에 대해 중요한 판정을 내렸다. **HTTP/2.0의 바이너리 프레이밍은 이 모호성을 소멸시킨다.** 헤더 이름은 소문자로 강제되고, 길이 필드가 값의 경계를 정하므로 구분자 탐색이 필요 없다. 그러나 11.13절이 곧바로 그 판정을 제한했다. **번역 지점에서 소멸했던 모호성이 되살아난다.** 2.0의 바이너리 이름-값 쌍이 1.x의 `이름: 값\r\n` 텍스트로 옮겨지는 순간, 값 안의 CR과 LF가 다시 구조적 의미를 얻는다.

**(c) 가능해지는 것** — 두 파서가 같은 바이트열에서 **서로 다른 헤더 집합**을 읽는다. 한쪽이 헤더로 인식하지 못한 줄을 다른 쪽이 헤더로 인식하면, 정책 지점이 검사하지 않은 헤더가 실행 지점에 도달한다. 8.7절의 CR/LF 사다리가 이 지점의 특수한 경우다.

**→ 11.7.1, 11.13, 8.5, 8.7, 8.2**

#### ⑥ URL 정규화

**(a) 두 주체** — **정책을 적용하는 중간자**(콘텐츠 필터, 접근 제어 프록시, WAF, 캐시 키 계산기)와 **리소스를 실제로 여는 종단**(웹 서버의 리소스 매핑, 애플리케이션의 라우팅).

**(b) 다르게 해석되는 것** — 경로 문자열이 어떤 리소스를 가리키는가. 7.7절과 7.8절이 이 문제를 전면적으로 다뤘다. 퍼센트 인코딩을 몇 번 푸는가, 언제 푸는가, 상위 디렉터리 세그먼트를 언제 접는가, 대소문자를 어떻게 다루는가, 다중 인코딩과 오버롱 형식을 어떻게 처리하는가. 여기에 13.5절의 두 규칙이 더해진다. **프록시는 URI를 가능한 한 고치지 말아야 하고**(하류 호환), 그러나 **정책 판단에는 정규화된 형태가 필요하다**(정확한 대조).

**(c) 가능해지는 것** — **정책이 본 문자열과 실행이 연 리소스가 다르다.** 필터가 허용한 경로가 서버에서는 다른 파일이 되고, WAF가 검사한 파라미터 값이 애플리케이션에서는 다른 값으로 디코딩된다. 12.11절이 WAF의 한계로 지목한 "명세 해석 불일치와 사후 변형"이 이 항목의 다른 이름이다.

**→ 7.7, 7.8, 13.5, 12.11, 31.7**

#### ⑦ Host와 절대 URI의 불일치

**(a) 두 주체** — **요청 라인의 절대 URI로 목적지를 정하는 홉**(13.5의 규칙 1)과 **`Host` 헤더로 가상 호스트를 고르는 홉**(규칙 2).

**(b) 다르게 해석되는 것** — 이 요청이 어느 호스트를 향한 것인가. 13.5절이 서술했듯 두 근거는 역사적 이유로 별개로 도입됐고, 명시적 프록시는 전자를, 가상 호스팅 서버는 후자를 쓴다. **둘이 함께 있고 서로 다른 곳을 가리킬 때 명세의 우선순위는 정해져 있지만, 경로 위의 모든 홉이 같은 우선순위를 따른다는 보장은 없다.**

**(c) 가능해지는 것** — 앞 홉의 라우팅 판단과 뒤 홉의 리소스 선택이 **다른 호스트를 향한다.** 한 호스트에 대해 통과된 정책으로 다른 호스트의 리소스에 도달할 수 있고, 캐시가 계산한 키의 호스트와 응답이 실제로 온 호스트가 달라질 수 있다(→ 14.8). 15.2절이 가상 호스팅의 관점에서, 8.6절이 `Host` 헤더의 신뢰성 관점에서 이 문제를 다룬다.

**→ 13.5, 8.6, 15.2, 12.9, 14.8**

#### ⑧ 메서드 해석

**(a) 두 주체** — **메서드로 정책을 적용하는 중간자**와 **메서드를 실제로 실행하는 서버·프레임워크**.

**(b) 다르게 해석되는 것** — 이 요청이 무엇을 하려는 요청인가. 13.8절의 규칙 — **프록시는 모르는 메서드도 전달해야 한다** — 이 이 지점을 만든다. 정책이 이름으로 열거한 메서드 목록에 없는 메서드는 정책의 검사를 받지 않은 채 통과한다. 여기에 세 변형이 붙는다. **메서드 이름의 대소문자**, **메서드를 헤더나 파라미터로 덮어쓰는 관행**, 그리고 **`Max-Forwards`가 응답 주체를 바꾸는 경우**(13.6)다.

**(c) 가능해지는 것** — 정책이 `GET`과 `POST`만 통제하고 그 밖의 메서드가 서버에서 실제 동작을 일으킨다. 8.3.4절이 "메서드 제한 우회"로, 24.5절이 "메서드 직접 접근 테스트"로 다루는 것이 이 항목의 애플리케이션 쪽 얼굴이다. 12.7절의 WebDAV 메서드가 구체적 사례다.

**→ 13.8, 13.6, 8.3.3, 8.3.4, 24.5, 12.7**

#### ⑨ 프로토콜 번역

**(a) 두 주체** — **번역 지점의 양쪽**. HTTP/2.0 종단과 HTTP/1.x 애플리케이션 서버, 또는 HTTP 클라이언트와 FTP·SOAP·CGI·데이터베이스 백엔드.

**(b) 다르게 해석되는 것** — 한 체계에서 **데이터**였던 것이 다른 체계에서 **구조**가 되는가. 13.9절의 표 13-9가 유형별로 정리했다. URL 경로가 FTP 명령 인자로, 질의 파라미터가 질의 언어의 조각으로, 헤더 값이 프로세스 인자나 환경변수로, 본문이 XML 문서로 옮겨진다. 11.13절의 표 11-18이 2.0→1.x 번역에 대해 같은 목록을 만들었다.

**(c) 가능해지는 것** — 앞 체계에서 무해했던 문자가 뒤 체계에서 구분자가 된다. 이 항목은 앞의 여덟 항목과 성격이 다르다. **앞의 항목들이 "같은 프로토콜을 다르게 읽는" 문제라면, 이 항목은 "다른 프로토콜로 옮기는" 문제다.** Part VI 전체(27~28장)가 이 항목의 전개다.

**→ 11.13, 13.9, 27장, 28.1, 28.5, 28.7, 8.7**

#### ⑩ 검사되지 않는 구간 — 터널

**(a) 두 주체** — **터널 시작줄로 정책을 판단한 게이트웨이**와 **터널 안에서 실제로 말해지는 프로토콜의 양 끝**.

**(b) 다르게 해석되는 것** — 엄밀히 말해 이것은 해석의 불일치가 아니라 **해석의 부재**다. 13.10절이 정리했듯 게이트웨이는 목적지 호스트·포트와 요청자의 신원만 검사하고, 터널이 세워진 뒤로는 아무것도 검사하지 않는다. **443 포트로 열린 터널 위로 흐르는 것이 정말 TLS인지 확인할 방법이 없다.**

**(c) 가능해지는 것** — 프로토콜 수준의 통제 전체가 시작 시점 한 번의 판단으로 축소된다. 이 항목을 목록에 올리는 이유는, **파서를 없애는 것이 불일치를 없애는 방법이지만 동시에 검사도 없앤다**는 사실을 드러내기 위해서다. 다음 항목(방어의 방향)의 첫 처방 — 파서 수를 줄인다 — 이 이 항목과 정면으로 만난다.

**→ 13.10, 19.8, 12.8, 37.7**

### (3) 방어의 방향

목록을 만들었으니 방어를 말할 수 있다. 여기서 말하는 방어는 개별 항목에 대한 개별 처방이 아니라 **목록 전체를 줄이는 네 가지 방향**이다. 각 방향은 대가를 동반하며, 그 대가를 명시하지 않은 처방은 실무에서 채택되지 않는다.

#### 방향 1 — 파서의 수를 줄인다

불일치의 기회는 인접한 파서 쌍의 수(N−1)다. **N을 줄이면 기회가 줄어든다.** 구체적으로는 세 가지다.

- **경로에서 홉을 없앤다.** 같은 기능을 하는 중간자가 둘이면 하나로 합친다. 캐시와 리버스 프록시가 별개 제품일 이유가 없다면 하나로 만든다.
- **검사만 하고 통과시키는 홉의 값을 재평가한다.** 12.11절이 WAF에 대해 내린 판정이 여기 적용된다. WAF는 **파서를 하나 더 추가하면서** 하류의 재해석을 보지 못한다. 즉 항목 ⑥의 당사자가 되면서 그 항목을 스스로 해결하지 못한다. 그 홉이 막는 것과 그 홉이 새로 만드는 불일치 기회를 함께 계산해야 한다.
- **파싱하지 않는 홉을 선택한다.** L4 로드밸런서는 HTTP를 파싱하지 않으므로 요청 경계를 오해할 수 없다(→ 1.2). 터널도 마찬가지다(항목 ⑩).

**대가는 크다.** 파싱하지 않으면 판단할 수 없다. 항목 ⑩이 정확히 이 대가를 보여 준다. 터널은 파서가 없으므로 불일치가 없지만, 그 대신 통제도 없다. **파서 수를 줄이는 방향은 "검사를 어디서 할 것인가"라는 질문을 회피하지 못하고, 검사를 한 곳으로 모으라는 요구로 이어진다.** 그것이 방향 2다.

#### 방향 2 — 경로상 파서의 규칙을 일원화한다

파서를 없앨 수 없다면 **모든 파서가 같은 규칙으로 읽게 만든다.** 남은 N−1개의 쌍에서 불일치가 나지 않게 하는 것이다.

- **같은 구현을 쓴다.** 경로 위의 모든 홉이 같은 파싱 라이브러리를 쓰면 해석이 갈릴 여지가 원리적으로 줄어든다.
- **프로토콜 버전을 고정한다.** 항목 ⑨(프로토콜 번역)의 상당 부분이 버전 혼재에서 온다. 11.13절이 서술한 이중 프로토콜 전략의 대가가 여기서 다시 나타난다. 종단 간 같은 버전이면 번역 지점이 사라진다.
- **관용성 프로파일을 명시적으로 합의한다.** 13.8절의 규칙들이 각 홉에 관용을 요구한다면, **어느 정도까지 관용할 것인지를 경로 전체가 같은 값으로 설정해야 한다.** 이것이 설정 문제이며, 설정의 검증은 46.12절의 주제다.
- **`Via`를 유지한다.** 13.6절이 서술했듯 `Via`는 경로 위 각 중간자의 프로토콜 능력을 뒤의 애플리케이션에 알리는 유일한 표준 장치다. 프라이버시를 위해 호스트명을 가명으로 바꾸더라도 **경유점 항목 자체는 남기라**는 명세의 권고가 이 방향과 같은 편에 있다.

**대가는 유연성과 운영 자율성이다.** 조직 경계를 넘는 경로(ISP 프록시, CDN, 기업 프록시)에는 이 방향을 적용할 수 없다. 통제할 수 있는 것은 자기 인프라 안의 홉들뿐이다.

#### 방향 3 — 모호한 입력을 거부한다

일원화가 불가능한 구간이 반드시 남는다. 그 구간에서 할 수 있는 유일한 일은 **모호함 자체를 통과시키지 않는 것**이다.

- 본문 길이를 지시하는 헤더가 **둘 이상이거나 서로 모순되면 처리하지 않는다**(항목 ①).
- 값 하나만을 기대하는 헤더가 **중복되면 거부한다**(항목 ③).
- 줄 끝, 공백, 이어쓰기가 **명세의 엄격한 형태를 벗어나면 거부한다**(항목 ④⑤).
- 요청 라인의 절대 URI와 `Host`가 **불일치하면 거부한다**(항목 ⑦).

이것은 43.6절이 분류한 네 가지 입력 처리 방식 — 거부(reject), 정제(sanitize), 안전한 처리, 의미론적 검사 — 중 **거부**를 선택하는 것이며, 43.4절의 검증 순서에서 "구문(syntax)" 단계에 해당한다. 정제가 아니라 거부여야 하는 이유는 이 장이 이미 보여 줬다. **정제는 문자열을 바꾸는 일이고, 문자열을 바꾸는 홉은 그 자체로 재직렬화 지점이 되어 새로운 불일치 기회를 만든다.**

**대가가 이 방향의 핵심 문제다.** 13.5절과 13.8절이 인용한 명세의 권고는 정반대다. **"프록시는 프로토콜 경찰이 되려 해서는 안 되며, 엄격한 준수 강제는 그때까지 정상 동작하던 서비스를 크게 망가뜨릴 수 있다."** 이 충돌은 기술적으로 해소되지 않는다. **선택의 문제이며, 선택의 근거는 그 경로가 무엇을 나르는가다.** 조직 내부의 통제된 구간에서는 거부가 옳고, 임의의 레거시 클라이언트를 상대하는 공용 이그레스 프록시에서는 대가가 다르게 계산된다. 이 판단을 명시적으로 내리고 기록하는 것 자체가 방어의 일부다.

#### 방향 4 — 중간자에서 정규화한 뒤 전달한다

거부만으로는 부족한 경우가 있다. **경로 위의 한 지점에서 메시지를 명확한 형태로 다시 만들고, 그 지점 이후로는 재해석을 금지하는 것**이 네 번째 방향이다.

- **정규화 지점을 하나로 정한다.** 여러 홉이 각자 정규화하면 7.8절이 다룬 "정규화 순서 문제"가 경로 위에서 재현된다. 정규화는 **한 번만, 정해진 지점에서** 일어나야 한다.
- **정규화 지점은 정책 지점보다 앞에 있어야 한다.** 항목 ⑥의 문제는 정책이 정규화 이전 형태를 보고 실행이 정규화 이후 형태를 볼 때 생긴다. 순서를 뒤집으면 그 특정 불일치가 닫힌다.
- **정규화 이후 형태를 하류가 다시 해석하지 않도록 한다.** 이것이 이 방향의 가장 어려운 부분이며, 대개 하류 구현에 대한 통제를 요구한다.

이 방향은 13.5절이 인용한 명세의 금지 — **인터셉팅 프록시는 URI의 절대 경로 부분을 다시 써서는 안 된다** — 와 직접 충돌한다. 충돌의 해소 지점은 **중간자의 종류**에 있다. 클라이언트가 알지 못하는 인터셉팅 프록시가 URI를 고치는 것과, 조직이 자기 서비스 앞에 놓은 리버스 프록시가 자기 하류를 위해 정규화하는 것은 같은 행위가 아니다. **후자는 자기 신뢰 도메인 안의 경계에서 하는 일이고, 그 도메인 안에서는 하류의 해석 규칙을 통제할 수 있다.**

**표 13-14. 방어의 네 방향과 그 대가 (이 책이 구성)**

| 방향 | 무엇을 줄이는가 | 대가 | 어디까지 적용 가능한가 | 참조 |
|---|---|---|---|---|
| 파서 수를 줄인다 | 불일치 기회의 개수(N−1) | 검사 능력을 함께 잃는다 | 자기 인프라 | 1.2, 12.11, 13.10 |
| 규칙을 일원화한다 | 쌍마다의 해석 차이 | 유연성·운영 자율성 | 조직 경계 안 | 13.6, 11.13, 46.12 |
| 모호한 입력을 거부한다 | 모호함 자체 | **상호운용성** (명세 권고와 충돌) | 통제된 클라이언트 | 43.4, 43.6, 30.8 |

### 이 절이 남기는 것

네 방향 어디에도 "이 취약점을 막는 설정" 같은 항목이 없다. 그것이 이 절의 결론이다.

**파싱 불일치는 특정 소프트웨어의 버그가 아니라 아키텍처의 성질이다.** 10.4절이 "이것은 버그가 아니다"라고 적은 것을 이 절이 경로 전체로 확장했다. 요청 하나에 여섯 개의 독립적인 파서가 관여하고, 각 파서가 상호운용성을 위해 관용적으로 설계됐으며, 어느 파서도 다른 파서의 해석을 검증할 수 없다면, **불일치는 발생 가능한 것이 아니라 발생하는 것이다.** 문제는 그것이 언제 어디서 보안적 결과를 낳느냐다.

그래서 이 문제의 해결은 개별 홉의 설정이 아니라 **경로를 어떻게 설계했는가**에 달려 있다. 41장이 "보안은 기능이 아니라 관심사다"라는 명제로 시작하는 이유가 여기 있다. 파서를 몇 개 둘 것인가, 어느 지점에서 정규화할 것인가, 어디서 거부하고 어디서 관용할 것인가는 **설정 화면에 없는 결정**이며, 아키텍처를 그릴 때 내려지는 결정이다. 그리고 43.4절이 제시하는 검증 순서 — 데이터의 출처 → 크기 → 어휘적 내용 → 구문 → 의미 — 는 이 결정을 코드 안에서 표현하는 방법이다. **이 장의 목록은 그 순서의 "구문" 단계가 왜 경계에서 한 번, 명확하게 이뤄져야 하는지에 대한 근거 목록이다.**

> **이 책의 범위를 넘어서**
>
> 이 절이 구조로만 서술한 각 지점에는 보안 연구 문헌에서 널리 통용되는 고유한 기법 이름이 붙어 있고, 각각에 대해 탐지·검증 도구와 대규모 사례 연구가 축적돼 있다. 그 이름들과 그 이름 아래 정리된 변형들은 이 책이 근거로 삼은 다섯 권의 서술 범위 밖이므로 본문에 도입하지 않았다. 마찬가지로 이 장이 그린 경로 — 프록시, 게이트웨이, 터널, 릴레이 — 이후에 등장한 배포 형태들, 즉 서비스 사이의 통신을 전담하는 인프라 계층과 그 위에 얹히는 제품군, 그리고 전송 계층 자체를 교체한 최신 HTTP 버전은 파서의 개수와 위치를 다시 바꿔 놓았다. 그러나 이 절이 세운 셈법 — **경로 위의 파서 수와 그 쌍의 수가 곧 불일치 기회의 수이며, 어느 파서도 다른 파서의 해석을 검증할 수 없다** — 는 그 배포들에도 그대로 적용된다. 이름이 바뀌고 홉의 개수가 바뀔 뿐, 표 13-13의 열 가지 지점은 같은 자리에 남는다.

> **이 절이 뒷받침하는 것**
>
> - 경로 위의 파서 계수와 그 쌍의 수 → **5.6**(이 계수의 출처), **Part III 도입부**

## 이 장의 요약

- **프록시는 서버이면서 동시에 클라이언트다.** 메시지를 통과시키는 것이 아니라 받아서 이해하고 다시 만든다. 프록시를 지난 요청이 클라이언트가 만든 바이트열과 같다는 보장은 없다.
- **프록시의 유용성과 위험은 같은 축 위에 있다.** 필터, 접근 제어, 캐싱, 콘텐츠 라우팅, 트랜스코딩, 익명화는 모두 프록시가 메시지를 더 깊이 이해하고 더 많이 고칠수록 강력해지며, 파싱 불일치의 위험도 같은 방향으로 커진다.
- **트래픽을 프록시로 보내는 네 가지 방법 중 셋에서 클라이언트는 중간자의 존재를 모른다.** 서러게이트와 인터셉팅 프록시는 클라이언트가 웹 서버와 구별할 수 없으며, 그래서 서버 형식의 요청을 받는다.
- **목적지에 대한 근거가 메시지 안에 둘 있다.** 프록시는 요청 라인의 절대 URI로, 가상 호스팅 서버는 `Host` 헤더로 목적지를 정한다. 같은 문제에 대한 두 개의 해법이 남긴 이 이중성이 이 장 목록의 한 항목이 된다.
- **`Via`와 `TRACE`는 경로를 관측하는 유일한 표준 장치이며, 동시에 무언가를 노출한다.** `Via`는 내부 토폴로지를, `TRACE`는 경로에서 삽입된 헤더를 반사한다.
- **프록시 인증 헤더는 홉 단위다.** 프록시 인증은 사용자를 프록시에게 식별시킬 뿐 원 서버에게 식별시키지 않으며, 여러 프록시가 있는 사슬에서는 잘 동작하지 않는다.
- **명세는 프록시에 관용을 요구한다.** 미지 헤더와 미지 메서드를 전달하고, 같은 이름 헤더의 순서를 보존하고, URI를 다시 쓰지 말고, 엄격한 준수를 강제하지 말라는 규칙들이 상호운용성을 위해 존재하며, 그 대가로 모호한 메시지가 걸러지지 않고 통과한다.
- **게이트웨이는 한 체계에서 데이터였던 것이 다른 체계에서 구조가 되는 지점이고, 터널은 시작줄 이후 아무것도 파싱하지 않는 구간이며, 릴레이는 규칙의 일부만 구현하면서 참여자처럼 보이는 중간자다.**
- **요청 하나는 전형적 배포에서 여섯 번 파싱되고 네 번 직렬화된다.** 파서가 여섯이면 인접 쌍은 다섯이고, 각 쌍마다 앞 홉이 이해한 메시지와 뒤 홉이 이해한 메시지가 달라질 수 있다. **어느 홉도 다른 홉의 해석을 런타임에 검증할 수 없다.**
- **파싱 불일치는 버그가 아니라 아키텍처의 성질이다.** 방어는 개별 설정이 아니라 네 방향 — 파서 수 줄이기, 규칙 일원화, 모호한 입력 거부, 정규화 후 전달 — 의 조합이며, 각 방향은 상호운용성이나 검사 능력이라는 대가를 동반한다.

## 이어지는 장

이 장은 요청 경로 위의 참여자들을 세우고, 그 개수를 세고, 그 사이에서 해석이 갈릴 수 있는 열 개의 자리를 목록으로 만들었다. Part III의 도입부가 던진 질문에 대한 답이 13.12절의 표 13-12와 표 13-13이다.

**14장은 그 중간자 중 특별한 하나를 따로 다룬다.** 캐시는 다른 중간자와 결정적으로 다른 일을 한다. 메시지를 전달하는 데 그치지 않고 **응답을 저장했다가 다른 트랜잭션에 재사용한다.** 그러려면 두 가지를 판단해야 한다. "이 요청은 아까 그 요청과 같은가"와 "저장한 응답이 아직 유효한가"다. 이 장이 13.2절에서 캐싱을 목적으로만 언급하고 넘긴 이유가 여기 있다. **동등성과 신선도의 판단은 그 자체로 하나의 장을 요구한다.** 그리고 그 판단이 어긋날 때 벌어지는 일 — 한 사용자의 응답이 다른 사용자에게 가는 것 — 은 13.12절 목록의 항목들이 캐시라는 특수한 중간자 위에서 재현되는 형태다(14.8).

**15장은 이 장이 서러게이트와 `Host` 헤더에서 남긴 실을 이어받는다.** 13.3절이 "서러게이트는 웹 서버의 이름과 IP를 직접 가져간다"고 서술한 배치가 호스팅 서비스의 형태로, 13.5절이 서술한 `Host` 의존이 가상 호스팅의 위험으로, 13.4절의 PAC·WPAD가 프록시 리다이렉션 기법으로 확장된다. 그리고 13.12절의 목록이 **계층 아키텍처와 공유 환경**이라는 또 다른 배치 위에서 어떻게 재현되는지가 15.9절과 15.10절이다. 서로 다른 계층이 서로를 신뢰하는 관계, 그리고 그 신뢰가 비정상 조건에서 무너지는 방식은 이 장이 홉과 홉 사이에 대해 서술한 것과 같은 구조다.

그리고 이 장이 마지막에 가리킨 방향 — 문제의 해결이 개별 홉의 설정이 아니라 경로의 설계에 있다는 것 — 이 Part IX의 주제다. 41장이 "보안은 기능이 아니라 관심사다"로 시작하고, 43장이 검증의 순서를 코드 구조로 옮기며, 47.10절이 "서비스 간 통신은 다시 네트워크다"라는 문장으로 이 장 전체를 내부망 안에서 되풀이한다.

> 13.9~13.11절: HTTP-DG 8장(Integration Points: Gateways, Tunnels, and Relays) 전체 — 게이트웨이 개념과 `<클라이언트 측>/<서버 측>` 표기, 서버 측/클라이언트 측 게이트웨이, 프로토콜 게이트웨이(HTTP/FTP의 명령열, HTTP/HTTPS 보안 게이트웨이, HTTPS/HTTP 보안 액셀러레이터), 리소스 게이트웨이와 애플리케이션 서버, CGI·Fast CGI·서버 확장 API·FPSE, 애플리케이션 인터페이스와 웹 서비스(XML over SOAP), 터널(`CONNECT` 문법·응답·데이터 터널링과 타이밍·SSL 터널링·게이트웨이 방식과의 세 가지 차이·터널 인증·보안 고려사항), 릴레이와 `Connection` 헤더로 인한 keep-alive 정지.

> 13.12절 (2)의 항목 ⑤에서 인용한 HTTP/2.0의 파싱 모호성 소멸과 번역 지점에서의 부활은 HPBN 12장의 서술을 이 책 11.7.1·11.13절이 정리한 것을 근거로 한다. 13.12절 (3)이 언급한 계층 아키텍처의 신뢰 관계 재현(15.10·31.1)은 WAHH 17장(Attacking Application Architecture)의 계층 간 신뢰 관계 서술을 참조했다. 방어 방향 3·4의 입력 처리 분류와 검증 순서는 SBD 4장·6장을 근거로 하며, 이 책 43.4·43.6절의 소관이다.
