# 40장. GraphQL DoS, 인가 우회, 그리고 공개된 취약점

> **이 장에서 다루는 것**
>
> - GraphQL DoS가 왜 이 부의 유일한 새 취약점인지, 자원 소모 모델의 어디가 REST와 다른지
> - 순환 질의·필드 중복·앨리어스·디렉티브·배치가 각각 서버의 어느 자원을 어떻게 태우는가
> - 각 DoS 방어가 무엇을 막고 무엇을 놓치는지, 그리고 방어를 겹칠 때 생기는 상호작용
> - 인가를 리졸버에 둘 때 판단 지점이 왜 흩어지며, 어느 층에 두어야 하는가
> - 공개된 CVE와 버그바운티 사례가 이 책의 어느 장에 대응하는가

38장은 이 부의 논지를 못 박았다. GraphQL의 약점은 거의 전부 이 책이 이미 다룬 실패 유형의 재현이며, 단 하나 — **서비스 거부(denial of service, DoS)** — 만이 정말 새롭다(→ 38.10). 39장은 그 위에서 대상의 지도를 그렸다. 어떤 엔드포인트가 GraphQL을 받고, 어떤 구현체가 돌며, 스키마에 어떤 질의·뮤테이션·필드가 있는지를 인트로스펙션과 필드 스터핑으로 캐냈다. 이 장은 그 지도 위에서 실제 공격을 실행한다.

세 갈래다. 앞부분(40.1~40.6)은 이 부의 핵심 논점인 DoS를 완결한다. 40.1이 "왜 DoS만 새로운가"에 답하고, 40.2~40.5가 벡터를 하나씩 해부하며, 40.6이 방어로 닫는다. 가운데(40.7~40.8)는 인증·인가를 다룬다 — GraphQL이 인가 판단을 어디에 두어야 하는가라는 구조적 물음이 핵심이다. 마지막(40.9~40.10)은 공개된 취약점 사례를 이 책의 장 번호에 대응시키고, 이 부의 절차 전체를 체크리스트로 요약한다.

이 장을 닫으면 Part VIII이 끝난다. GraphQL이라는 현대 API가 옛 병을 어떻게 새 문으로 들이는지, 그리고 그 문 중 하나(DoS)만이 정말 새 문인지를 확인하는 것이 이 부 전체의 목적이었다.

## 40.1 GraphQL DoS 벡터 개관 — 자원 소모 모델과 서버 측 비용

이 절이 이 부의 핵심 논점이다. 38.10절의 대응표에서 여덟 부류의 약점 중 일곱이 "같음"으로 시작했고, 마지막 한 행 — DoS — 만이 "이것만 새롭다"였다. 그 한 행의 이유를 여기서 완결한다.

### 40.1.1 누가 응답의 비용을 정하는가

REST API에서는 **서버가 응답의 형태와 비용을 정한다.** 클라이언트가 `GET /pastes`를 보내면, 무엇을 얼마나 돌려줄지는 그 엔드포인트를 구현한 서버 코드가 결정한다. 클라이언트는 어느 엔드포인트를 부를지 고를 수 있을 뿐, 한 번의 요청이 서버에서 얼마나 많은 일을 시키는지는 서버가 미리 못 박아 둔 범위를 벗어나지 못한다. 응답이 무거우면 그것은 서버 설계자가 선택한 무게다.

GraphQL은 이 관계를 뒤집는다. GraphQL의 간판 기능은 **선언적 질의 언어**이며, 그 언어가 존재하는 이유는 클라이언트가 원하는 데이터 구조를 스스로 조립하게 하기 위해서다(→ 38.6). 클라이언트가 질의의 형태·깊이·필드 수·반복을 정한다. 그 말은 곧, **한 번의 요청이 서버에서 유발하는 자원 소모의 크기를 클라이언트가 제어한다**는 뜻이다. 서버가 아니라 클라이언트가 비용의 다이얼을 쥔다.

이것이 DoS를 이 부의 유일한 새 취약점으로 만드는 근본이다. 인젝션·인가·정보 노출은 REST에서도 클라이언트가 악용할 수 있었고 GraphQL은 진입점만 바꿨다. 그러나 "클라이언트가 서버 자원 소모의 다이얼을 쥔다"는 조건은 REST에는 없던 것이다. GraphQL의 선언적 질의 언어는 클라이언트를 강력한 위치에 놓았고, 그 힘이 곧 아킬레스건이 됐다.

신뢰할 수 없는 클라이언트가 그 다이얼을 쥐고 있으므로, GraphQL 서버는 스스로를 악의적 질의로부터 지킬 수단을 반드시 갖춰야 한다. 클라이언트가 서버에게 비싸게 먹힐 질의를 조립할 수 있다면, 그 질의는 서버의 자원을 굶긴다. 그 결과는 다운타임이거나 성능 저하 — 어느 쪽이든 애플리케이션의 **가용성**을 무너뜨린다.

### 40.1.2 증폭: 요청 크기와 서버 비용의 비율

DoS를 이해하는 핵심 개념은 **증폭(amplification)** 이다. 공격자가 보내는 요청의 크기와, 그 요청이 서버에서 유발하는 비용의 비율이 관건이다. 이 비율이 클수록 공격은 효율적이다 — 작은 입력으로 큰 소모를 일으킬수록 공격자는 적은 자원으로 방어자의 많은 자원을 태운다.

이것은 새로운 발상이 아니다. 4.7절에서 UDP 기반 서비스의 반사·증폭을 다뤘다. 공격자가 작은 질의를 위조된 출발지 주소로 DNS·NTP 서버에 보내면, 서버가 그 몇십 배 크기의 응답을 피해자에게 쏟아붓는다. 작은 입력, 큰 출력 — 그 비대칭이 공격의 동력이었다. GraphQL DoS는 **같은 개념을 다른 층위에서 반복한다.** 층위만 네트워크에서 애플리케이션으로 올라왔을 뿐, 구조는 동일하다. 순환 질의 하나가 이 증폭의 교과서적 예다. 몇 줄짜리 질의가 지수적으로 큰 응답을 서버에서 끌어낸다(→ 40.2).

증폭이 일어나는 자리는 벡터마다 다르다. **표 40-1**이 GraphQL DoS 벡터를 증폭의 성질로 분류한다.

**표 40-1. GraphQL DoS 벡터의 두 유형**

| 유형 | 질의 크기 | 서버 소모 | 대표 벡터 |
|---|---|---|---|
| **작은 질의, 큰 소모** | 작다 | 응답이 지수적으로 팽창 | 순환 질의(40.2), 객체 한도 재정의(40.4) |
| **큰 질의, 큰 소모** | 크다 | 파싱·해석·리졸브에 시간 소모 | 필드 중복·앨리어스·디렉티브 과부하(40.3), 배치(40.4) |

두 유형의 방어가 다르다는 점이 뒤의 40.6절에서 중요해진다. 작은 질의의 팽창은 **깊이 제한**으로 잡히고, 큰 질의의 소모는 **본문 크기 제한이나 복잡도 분석**으로 잡힌다. 하나의 방어가 둘 다 막지는 못한다.

### 40.1.3 공격자 비용 대 방어자 비용의 비대칭

3.9.2절이 DoS의 경제학이라는 틀을 세웠다. 커넥션 수립 비용을 논하며, 모든 DoS의 성패는 **공격자가 치르는 비용과 방어자가 강요당하는 비용의 비대칭**에 달려 있다고 정리했다. TCP SYN 플러드가 위험한 것은 공격자는 SYN 하나만 보내면 되는데 방어자는 반쯤 열린 커넥션을 위한 상태를 쌓아야 하기 때문이었다. 값싼 공격, 비싼 방어 — 그 기울기가 클수록 공격은 성립한다.

GraphQL DoS에 이 틀을 그대로 적용한다. 공격자에게 순환 질의 한 통을 보내는 비용은 HTTP 요청 하나의 대역폭뿐이다. 그 대가로 서버는 지수적으로 불어난 객체를 메모리에 로드하고 리졸버를 재귀적으로 돈다. 필드 중복 질의 하나를 조립하는 비용은 문자열 곱셈 한 줄이지만, 서버는 중복된 필드 각각을 따로 리졸브하느라 26밀리초짜리 질의를 958밀리초로 늘린다 — 36배다(→ 40.3). 앨리어스·배치는 이 비대칭을 한 단계 더 벌린다. 단일 HTTP 요청 안에 수천 개의 연산을 담아, 요청 수를 세는 방어(레이트 리밋)의 시야 밖에서 서버를 태운다(→ 40.4).

이 비대칭이 GraphQL DoS 방어의 목표를 정한다. 방어의 본질은 **비용의 기울기를 되돌리는 것** — 서버가 강요당하는 비용에 상한을 두어, 공격자가 값싸게 큰 소모를 일으키지 못하게 만드는 것이다. 40.6절의 모든 방어가 이 한 문장의 변주다. 깊이 제한은 재귀의 팽창에, 복잡도 제한은 질의당 소모에, 레이트 리밋은 시간당 누적에 상한을 씌운다.

### 40.1.4 무엇이 타는가, 어떻게 쏘는가

CWE(Common Weakness Enumeration)는 이 부류를 **통제되지 않은 자원 소모(Uncontrolled Resource Consumption)** 로 분류한다. 악용의 결과로 타는 것은 세 가지다.

- **CPU 사이클** — 파서가 거대한 질의를 분석하고, 리졸버가 수많은 필드를 처리하느라 프로세서를 점유한다.
- **메모리** — 순환 질의가 부풀린 객체 배열, 배치가 쌓은 응답이 서버 메모리를 삼킨다.
- **디스크** — 로그·임시 파일이 디스크를 채워, 다른 프로세스가 파일시스템에 쓰지 못하게 만든다.

공격자가 이 소모를 유발하는 방식은 다섯 형태로 정리된다.

1. 하나의 요청에 복잡한 질의 하나
2. 하나의 요청에 여러 개의 복잡한 질의(앨리어스·배치)
3. 여러 병렬 요청, 각각에 복잡한 질의 하나
4. 여러 병렬 요청, 각각에 여러 복잡한 질의
5. 서버에 대량의 객체를 요청(객체 한도 재정의)

이 벡터들 중 일부는 GraphQL 명세에 정의된 기능(앨리어스·디렉티브)을 악용하고, 일부는 명세 밖의 부가 기능(배열 기반 배치)에 기댄다. 이 구분이 방어에서 중요하다 — 명세에 있는 기능은 끌 수 없어 별도 미들웨어가 필요하고, 명세 밖 기능은 설정으로 끌 수 있다(→ 40.6).

## 40.2 순환 질의(circular query)

순환 질의 — 재귀 질의(recursive query)라고도 한다 — 는 **작은 질의, 큰 소모** 유형의 대표다. 스키마의 두 노드가 서로를 참조하는 양방향 관계(edge)를 가질 때, 클라이언트는 그 관계를 왕복하며 "원(circle)"을 그리는 질의를 조립할 수 있다. 원을 한 바퀴 돌 때마다 서버가 돌려줘야 할 응답이 지수적으로 커진다.

### 40.2.1 스키마의 순환 관계

38.7절이 GraphQL 스키마의 순환 관계를 전제로 세웠다. 여기서 그 관계가 DoS의 재료가 되는 과정을 본다. DVGA(Damn Vulnerable GraphQL Application)의 붙여넣기(paste) 모델을 예로 든다. 붙여넣기 하나에는 제목과 내용이 있고, 그것을 올린 소유자(owner)의 메타데이터를 별도 타입으로 분리했다고 하자.

```graphql
type Paste {
    title: String
    content: String
    owner: Owner
}

type Owner {
    name: String
    pastes: [Paste]
}
```

`Paste`는 `owner` 필드로 `Owner`를, `Owner`는 `pastes` 필드로 `Paste`를 참조한다. 두 타입이 서로를 가리킨다 — **순환 조건(circular condition)** 이다. 이 자체는 스키마 설계의 안티패턴이 아니다. 소유자와 그가 올린 붙여넣기 목록을 오가는 것은 자연스러운 데이터 모델이다. 문제는 애플리케이션이 복잡한 질의를 우아하게 처리하지 못할 때 이 관계가 악용된다는 데 있다.

클라이언트는 이 순환을 왕복하는 질의를 만들 수 있다.

```graphql
query {
  pastes {
    owner {
      pastes {
        owner {
          pastes {
            owner {
              name
            }
          }
        }
      }
    }
  }
}
```

질의 자체는 단순하다. 그러나 리졸버는 `pastes` → `owner` → `pastes` → `owner`를 돌 때마다 이전 단계의 각 객체에 대해 다음 단계 전체를 다시 로드한다. 원을 한 바퀴 더 돌 때마다 서버가 처리해야 할 객체 수가 곱으로 불어난다. 몇 줄짜리 질의가 지수적으로 큰 응답을 강요한다 — 40.1.2절이 말한 증폭의 교과서적 사례다.

순환 관계를 찾는 방법은 39장에서 이미 갖췄다. 화이트박스 테스트라면 SDL 파일에서 양방향 참조를 정적으로 읽고, 블랙박스라면 인트로스펙션이 켜져 있기를 바라며 스키마를 뽑는다. 39.2절에서 GraphQL Voyager로 객체 관계를 시각화했고, InQL은 Tarjan·Johnson 그래프 알고리즘으로 순환을 동적으로 찾아 `OwnerObject -[paste]-> PasteObject -[owner]-> OwnerObject` 같은 경로를 출력한다.

### 40.2.2 순환 인트로스펙션

순환 관계는 스키마 설계자가 만든 것만이 아니다. GraphQL의 **인트로스펙션 시스템 자체**에 순환이 내장돼 있다. 명세가 정의한 인트로스펙션 스키마에서 `__Type`의 `fields` 필드는 `[__Field!]`를 반환하고, `__Field`의 `type` 필드는 다시 `__Type`을 반환한다. `__Type.fields`와 `__Field.type`이 서로를 참조한다 — 순환이다.

```graphql
query {
  __schema {
    types {
      fields {
        type {
          fields {
            type {
              fields {
                name
              }
            }
          }
        }
      }
    }
  }
}
```

인트로스펙션이 켜져 있으면 스키마에 사용자 정의 순환 관계가 하나도 없어도 이 질의를 곧바로 쏠 수 있다는 뜻이다. 인트로스펙션을 켜 두는 것은 정보 노출만의 문제가 아니라(→ 39.2) DoS 벡터를 하나 열어 두는 일이기도 하다. 뒤의 40.9절에서 GitLab이 정확히 이 순환 인트로스펙션으로 무너진 사례를 본다 — 복잡도 검사를 구현해 두고도 인트로스펙션 질의에는 그 검사를 적용하지 않아 빈틈이 남았다.

### 40.2.3 순환 프래그먼트

프래그먼트(fragment)는 클라이언트가 질의 로직을 재사용하려고 정의하는 조각이다(→ 38.6). 클라이언트가 정의하므로 클라이언트는 어떤 로직이든 넣을 수 있고, 여기에 순환을 심을 수 있다. GraphQL 명세는 이를 명시적으로 금지한다.

> 프래그먼트 스프레드의 그래프는 자기 자신을 스프레드하는 것을 포함해 어떤 순환도 이뤄서는 안 된다. 그렇지 않으면 연산이 무한히 스프레드하거나 데이터의 순환에서 무한히 실행될 수 있다.

두 프래그먼트가 서로를 부르게 만들면 순환이 성립한다.

```graphql
query CircularFragment {
  pastes {
    ...Start
  }
}

fragment Start on PasteObject {
  title
  content
  ...End
}

fragment End on PasteObject {
  ...Start
}
```

`Start`가 `End`를, `End`가 `Start`를 스프레드한다. 명세가 경고한 대로 무한 실행 조건이다. 명세를 준수하는 서버는 이런 질의를 **실행 전에** 거부한다(→ 38.9의 검증 단계). 그러나 명세를 완전히 지키지 않는 커스텀 구현체는 이 질의를 그대로 실행하다 세그멘테이션 폴트로 즉시 죽는다. 40.9절의 Agoo 사례(CVE-2022-30288)가 바로 이것이다 — 검증 검사가 없어 순환 프래그먼트 하나에 서버가 얼어붙었다.

여기서 방어의 첫 교훈이 나온다. **명세 준수 여부가 방어의 일부다.** 명세를 지키는 서버는 순환 프래그먼트를 공짜로 막는다. 검증 단계를 건너뛴 구현체는 명세가 이미 경고한 함정에 그대로 빠진다.

> **이 절이 뒷받침하는 것**
>
> - 순환 관계가 DoS의 재료가 되는 과정 → **38.7** (스키마의 순환 관계), **39.2** (인트로스펙션과 Voyager 시각화)
> - 명세의 검증이 방어의 일부라는 점 → **38.9** (검증과 실행), **40.6** (깊이 제한과 방어 조합)

## 40.3 필드 중복, 앨리어스 과부하, 디렉티브 과부하

이 세 벡터는 **큰 질의, 큰 소모** 유형이다. 순환 질의가 작은 질의로 응답을 부풀렸다면, 이 셋은 질의 자체를 크게 만들어 서버의 파싱·리졸브 시간을 태운다. 공통점은 하나 — 효과를 내려면 큰 페이로드를 **끊임없이 계속 보내야** 한다. 한 방에 서버를 죽이기보다 자원을 지속적으로 바쁘게 만들어 성능을 갉는다.

### 40.3.1 필드 중복

필드 중복(field duplication)은 질의에 같은 필드를 반복해 채우는 공격이다. 원리는 단순하다 — 리졸브에 비쌀 법한 필드를 하나 고르고, 그 이름을 질의에 수백·수천 번 복사한다.

```graphql
query {
  pastes {
    title
    content
    content
    content
    content
    content
  }
}
```

흥미로운 점은 서버의 응답이다. GraphQL은 중복된 `content`를 응답에서 하나로 합쳐, JSON에는 `content` 필드가 한 번만 나온다. 클라이언트 관점에서는 서버가 중복을 무시한 것처럼 보인다. 그러나 그렇지 않다. **서버는 중복된 필드를 응답으로 내보내기 전에 각각을 따로 리졸브한다.** 합치는 것은 마지막 단계일 뿐, 리졸브 비용은 중복 횟수만큼 든다.

이 비용은 응답 시간 분석으로 드러난다. DVGA에서 `content` 필드 하나짜리 질의는 26밀리초에 돌아왔다. 같은 필드를 약 1,000번 반복한 질의는 958밀리초가 걸렸다 — **36배 느리다.** 어떤 필드는 리졸브에 더 많은 자원을 쓰므로(로컬 DB를 읽는 필드보다 여러 외부 서비스를 확인하는 필드가 무겁다), 어느 필드를 고르느냐에 따라 효과가 달라진다. 자동화된 익스플로잇은 `content`와 `title`을 각 1,000번 반복한 페이로드를 50개 스레드로 2초마다 무한히 쏘아 서버 자원을 계속 붙잡는다.

### 40.3.2 앨리어스 과부하

앨리어스(alias)는 같은 필드를 다른 이름으로 여러 번 부르는 기능이다(→ 38.6). 단일 HTTP 요청 안에서 여러 질의를 돌릴 수 있어 강력하다. 그리고 이 강력함이 방어를 피하는 데 쓰인다 — **보안 분석가도 WAF도 단일 HTTP 요청 하나를 의심스러운 트래픽으로 보지 않는다.** 요청 하나가 무슨 해를 끼치겠느냐는 통념이 앨리어스 과부하의 은신처다.

GraphQL 서버는 기본적으로 단일 요청의 앨리어스 개수를 제한하지 않는다. 앨리어스는 명세의 일부라, 지원을 없애거나 제한하는 일이 드물다. DVGA에는 시스템 업데이트를 흉내 내는 `systemUpdate`라는 느린 질의가 있다 — 응답에 약 50초가 걸린다. 이 질의를 앨리어스로 여러 번 부르면 한 요청이 그만큼 배로 무거워진다.

```graphql
query {
  one:systemUpdate
  two:systemUpdate
  three:systemUpdate
  four:systemUpdate
  five:systemUpdate
}
```

Python 한 줄로 수백 개의 앨리어스를 찍어낼 수 있다. 기본 상태에서 앨리어스 개수에 한계가 없으므로, 개발자가 별도 보호를 심지 않았거나 웹 서버가 본문 길이 제한을 걸지 않았다면, 단일 HTTP 요청에 수십·수백 개의 연산을 담아 서버를 태운다. 앨리어스의 한계는 하나 — **같은 루트 타입끼리만** 묶을 수 있다. 질의는 질의끼리, 뮤테이션은 뮤테이션끼리만 앨리어스할 수 있고, 둘을 섞지는 못한다. 이 한계를 넘는 것이 40.4절의 배열 기반 배치다.

앨리어스는 다른 취약점과 결합할 수도 있다. 순환 질의를 여러 앨리어스로 묶으면 한 요청에 여러 개의 순환을 담는다. 그리고 뒤의 40.8절에서 보듯, 앨리어스는 DoS 밖에서도 쓰인다 — 로그인 뮤테이션을 앨리어스로 수천 번 묶어 무차별 대입을 단일 요청에 압축하는 것이 인증 우회의 핵심 기법이다.

### 40.3.3 디렉티브 과부하

디렉티브(directive)는 `@` 기호로 필드나 객체를 장식하는 기능이다(→ 38.6). 명세는 디렉티브에 어떤 보안 통제를 둬야 하는지 논하지 않는다. 대부분의 구현체는 **존재하는** 디렉티브가 한 위치에 중복되는지는 검사한다 — `UniqueDirectivesPerLocation`, `UniqueDirectiveNames` 규칙이 그것이다. 그러나 **존재하지 않는** 디렉티브는 얼마든지 반복해 넣을 수 있다.

```graphql
query {
  pastes {
    title @aa@aa@aa@aa
    content @aa@aa@aa@aa
  }
}
```

`@aa`는 스키마에 없는 디렉티브다. 존재하지 않는 디렉티브의 개수에는 사실상 제한이 없다. 임의의 텍스트에 `@`만 붙이면 된다. 이 수많은 디렉티브가 서버의 **질의 파서**를 소모시킨다. 필드 중복과 비슷하게 여러 요청을 지속적으로 보내야 효과가 나지만, 실측에서 서버 성능 저하에 효과적이었다. 익스플로잇은 `@dos`를 3만 번 곱한 페이로드를 300개 스레드로 병렬 발사한다. 서버 하드웨어에 따라 데이터베이스 메모리 오류로 인한 크래시부터 성능 저하까지 다양하게 나타났다.

이 세 벡터에는 공통된 방어의 급소가 있다. 셋 다 **질의 안에 많은 것을 채워 넣는** 공격이므로, 단일 질의의 크기나 복잡도에 상한을 두는 방어 하나가 셋을 함께 막는다(→ 40.6의 복잡도 분석). 순환 질의의 깊이 제한과는 다른 방어라는 점이 40.1.2절 표 40-1의 두 유형 구분과 이어진다.

> **이 절이 뒷받침하는 것**
>
> - 앨리어스·디렉티브의 문법과 성질 → **38.6** (언어 — 앨리어스, 디렉티브, 프래그먼트)
> - 앨리어스가 요청 빈도 방어를 피하는 구조 → **40.8** (인증 무차별 대입), **40.6** (레이트 리밋의 한계)

## 40.4 객체 한도 재정의, 배열 기반 질의 배칭

### 40.4.1 객체 한도 재정의

배열을 반환하는 필드는 특별한 위험을 진다. DVGA의 `pastes` 질의는 `[PasteObject]!`를 반환한다 — 붙여넣기 객체의 배열이다. 질의를 명시적으로 제한하지 않으면 GraphQL은 데이터베이스의 모든 객체를 돌려준다. DB에 객체가 1만 개 있으면 1만 개를 다 반환한다. 이는 서버와 클라이언트 양쪽이 처리하기에 많은 데이터다.

그래서 서버는 반환 객체 수를 제한하는 로직을 둔다 — 생성 시각으로 정렬해 최근 100개만 돌려주는 식이다. 필터링은 DB 층에서, GraphQL 층에서, 또는 둘 다에서 일어난다. 문제는 일부 애플리케이션이 클라이언트가 이 서버 측 한도를 **재정의**하도록 허용한다는 데 있다.

```graphql
query {
  pastes(limit:100000, public: true) {
    content
  }
}
```

이 질의는 뒤에서 `SELECT content FROM pastes WHERE public = true LIMIT 100000` 같은 SQL로 번역될 수 있다. DVGA처럼 작은 DB에서는 큰 해가 없지만, 매우 큰 DB에서는 서버가 반환하는 행의 수를 클라이언트가 통제하는 것이 **데이터베이스 층 DoS**의 벡터가 된다. 인트로스펙션이 켜져 있으면 인자를 자동 완성으로 발견하고, 꺼져 있으면 `limit`, `offset`, `first`, `after`, `last`, `max`, `total` 같은 흔한 페이지네이션 키워드를 시도한다. 서버가 클라이언트에게 임의 개수의 레코드를 허용하는지 시험하는 것이 이 벡터의 테스트다.

### 40.4.2 배열 기반 질의 배칭

**질의 배칭(query batching)** 은 여러 질의를 묶어 GraphQL API에 병렬로 보내는 방법이다. 앨리어스도 배칭의 한 형태지만, 40.3.2절에서 봤듯 같은 루트 타입끼리만 묶는 한계가 있었다. **배열 기반 배칭(array-based batching)** 은 이 한계를 넘어 질의와 뮤테이션을 섞을 수 있다. 대신 배열은 명세의 일부가 아니라, 모든 서버에서 쓸 수 있는 것은 아니다.

배열 기반 배칭은 클라이언트가 여러 GraphQL 질의를 JSON 배열에 담아 보내게 한다.

```json
[
  {"query":"query {systemHealth}"},
  {"query":"query {systemHealth}"}
]
```

서버는 배열을 받으면 요소를 순차적으로 처리하고, 마지막 요소까지 리졸브한 뒤에야 모든 응답을 하나의 배열에 담아 단일 HTTP 응답으로 돌려준다. 여기 명백한 위험이 있다 — 클라이언트가 합리적인 개수의 질의를 보낸다고 **가정**하지만, 클라이언트가 배열에 수천 개의 질의를 담으면 어떻게 되는가.

이 기법의 진짜 위력은 방어 회피에 있다. 앨리어스와 마찬가지로, 배열 배칭은 로그에 **단일 HTTP 요청 하나**로만 남는다. 보안 분석가에게 악의적 패턴으로 보이지 않는다. 그래서 **초당·분당 요청 수를 제한하는 전통적 레이트 리밋을 우회한다** — 요청은 하나인데 그 안에 수천 개의 연산이 들었기 때문이다. 40.1.3절의 비대칭이 여기서 극단으로 벌어진다.

배열 배칭은 앞의 벡터들과 결합할 때 가장 위험하다. 순환 질의를 동적으로 깊게 만든 뒤 그것을 배열에 여러 개 담으면, 각 요소가 지수적으로 큰 응답을 유발하는 배열이 된다. 실측에서 순환 필드 반복을 500회 이상으로 올린 배열 질의는 DVGA를 세그멘테이션 폴트로 무너뜨렸다.

배칭 가능 여부는 BatchQL 같은 도구로 탐지한다. BatchQL은 존재하지 않을 법한 필드(`hacktheplanet`)로 질의를 만들어 배열에 두 개 담아 보내고, 돌아오는 오류 개수를 센다. 오류가 하나보다 많으면 서버가 두 질의를 모두 처리했다는 뜻 — 배칭이 가능하다는 신호다. 앨리어스 배칭도 같은 오류 계수 논리로 탐지한다.

> **이 절이 뒷받침하는 것**
>
> - 배칭이 레이트 리밋을 우회하는 구조 → **40.6** (레이트 리밋의 한계와 본문 크기 제한)
> - DB 층으로 흘러드는 인자 → **27.14** (GraphQL을 경유한 인젝션), **40.9** (SkyWalking 사례)

## 40.5 GraphQL Cop으로 DoS 감사

지금까지의 벡터를 손으로 하나씩 시험하는 대신, GraphQL Cop이 대부분을 자동으로 감사한다. Python 기반 보안 감사 유틸리티로, DoS와 정보 노출 약점을 찾는다. 매개변수가 거의 필요 없다 — 대상 엔드포인트만 주면 된다.

```
# python3 graphql-cop.py -t http://localhost:5013/graphql

[HIGH] Alias Overloading - Alias Overloading with 100+ aliases is allowed (Denial of Service)
[HIGH] Batch Queries - Batch queries allowed with 10+ simultaneous queries (Denial of Service)
[HIGH] Field Duplication - Queries are allowed with 500 of the same repeated field (Denial of Service)
[HIGH] Directive Overloading - Multiple duplicated directives allowed in a query (Denial of Service)
```

각 결과에 취약점 설명과 미리 정의된 심각도가 붙는다. 위 출력에서 GraphQL Cop은 DVGA에서 네 개의 DoS 벡터 — 앨리어스 과부하, 배치 질의, 필드 중복, 디렉티브 과부하 — 를 큰 노력 없이 찾아냈다. 침투 테스트에서 결과를 프로그램으로 파싱해야 하면 `-o json` 플래그로 기계 친화적 출력을 얻는다.

이런 자동 감사 도구는 침투 테스트의 첫 스윕에 유용하다. 손으로 각 벡터를 조립하기 전에, 어느 방어가 없는지를 빠르게 확정해 준다. 다만 도구의 발견은 시작점이지 끝이 아니다 — GraphQL Cop이 "앨리어스 과부하 허용"을 보고했다면, 실제로 그 앨리어스가 서버 성능에 미치는 영향은 대상의 하드웨어와 리졸버 비용에 따라 손으로 검증해야 한다. 자동 도구의 역할과 그 한계, 그리고 이 책이 다루는 GraphQL 도구 전체의 설치·옵션은 부록 B가 정리한다.

> **이 절이 뒷받침하는 것**
>
> - 자동 감사 도구의 역할과 한계 → **부록 B** (자동화 도구), **40.9** (도구가 못 잡는 애플리케이션 고유 취약점)

## 40.6 GraphQL의 DoS 방어 — 깊이·복잡도 제한, 비용 분석, 타임아웃, 레이트 리밋, 질의 허용목록

앞의 다섯 절이 공격이었다면 이 절은 방어다. 40.1.3절이 방어의 목표를 이미 정했다 — **공격자 대 방어자 비용의 기울기를 되돌리는 것.** 여기서는 각 방어가 그 기울기의 어느 지점에 상한을 씌우는지, **무엇을 막고 무엇을 놓치는지**, 그리고 방어를 겹칠 때 무엇이 달라지는지를 본다. 대부분의 GraphQL 구현체는 기본으로 포괄적 DoS 완화를 갖추지 않으므로(일부 예외를 빼면), 이 방어들은 개발자가 의식적으로 심어야 한다.

### 40.6.1 질의 비용 분석

**비용 분석(cost analysis)** 은 GraphQL 필드에 처리 비용의 수치를 매기고, 질의 전체의 비용이 상한을 넘으면 거부하는 방어다. 비용은 CPU·I/O·메모리·네트워크 소모를 뜻한다. 두 방식이 있다.

**정적 비용 할당**이 더 흔하다. 스키마 디렉티브로 필드·타입마다 비용 값을 미리 정한다.

```graphql
directive @cost(complexity: Int = 1) on FIELD_DEFINITION | OBJECT

type PasteObject {
  title: String @cost(complexity: 1)
  content: String @cost(complexity: 1)
  userAgent: String @cost(complexity: 5)
  ipAddr: String @cost(complexity: 5)
}
```

로컬 DB에서 읽는 필드는 1, 여러 외부 서비스를 확인하는 무거운 필드는 5처럼 자원 부담에 비례해 값을 준다. 질의가 요청한 필드들의 비용을 합쳐 상한과 비교한다. 위 스키마에서 네 필드를 모두 요청하면 총비용은 12다. 정적 분석의 한계는 **응답의 복잡도를 못 본다**는 것이다. 필드 하나를 요청했는데 서버가 1,000개 원소의 배열을 돌려주는 경우, 질의만 봐서는 이 복잡도를 알 수 없다.

**동적 비용 할당**은 질의를 실제로 리졸브한 뒤 응답의 복잡도로 비용을 매긴다. 서버가 먼저 처리해야 비용을 알 수 있다는 대가가 있지만, 정적 방식보다 정확하다.

정적 비용 분석의 위험한 빈틈은 **상태를 두지 않는다**는 점이다. 많은 정적 비용 라이브러리는 비용 정보를 DB나 캐시에 지속시키지 않고 질의마다 새로 평가한다. 서버가 최대 비용(`MAX_COST`)을 200으로 뒀다면, 비용 200짜리 질의는 하나하나 다 통과한다. 공격자가 정확히 200짜리 질의를 수천 개 병렬로 보내면 전부 승인된다. 상한이 너무 관대하면 병렬 공격에 그대로 뚫린다.

이 빈틈을 메우는 것이 **크레딧 기반 레이트 리밋**이다. 서버가 클라이언트 세션의 질의 비용을 누적 추적해, 시간당·일당 할당량(쿼터)을 두고 초과 시 거부한다. 시간당 1,000 크레딧을 주면 비용 200짜리 질의는 시간당 다섯 번만 가능하다. 단, 이것이 성립하려면 서버가 클라이언트의 API 사용량을 DB에 저장해 상태를 관리해야 한다. 그렇지 않으면 비용 기반 제한이 무상태가 되어 위의 병렬 공격 문제로 돌아간다.

일부 구현체는 응답의 `extensions` 필드로 비용 메타데이터(`credits_total`, `credits_remaining`)를 클라이언트에게 알려준다. 클라이언트가 언제 질의가 스로틀될지 알고 오류 처리를 개선하라는 배려지만, 공격자에게도 유용하다 — 크레딧이 언제 회복되는지 알면 차단당할 요청을 반복하는 대신 정확히 크레딧이 찰 때 다음 공격을 발사할 수 있다.

### 40.6.2 깊이 제한

**깊이 제한(depth limit)** 은 순환 질의를 겨냥한 방어다. `max_depth`를 10으로 두면 10단계를 넘는 중첩 질의는 거부된다. graphql-ruby는 `max_depth 10`을, Graphene은 `depth_limit_validator(max_depth=20)`를 스키마에 둔다. 성숙한 구현체는 이를 기본 또는 외부 라이브러리로 지원한다.

깊이 제한의 한계는 명확하다. 깊이는 보통 **질의당** 계산된다. 공격자가 깊이 제한 안쪽의 재귀 질의를 여러 개 동시에 보내면, 각각은 통과하되 합쳐서 서버에 심한 부하를 준다. 40.9절의 GitLab 순환 인트로스펙션 사례가 이 한계의 변주다 — 복잡도 검사가 있었는데도 인트로스펙션 질의에는 적용되지 않아, 깊이 방어의 사각이 그대로 노출됐다.

### 40.6.3 배칭·중복·레코드 제한

**앨리어스·배열 배칭 제한.** 앨리어스는 명세의 일부라 쉽게 끌 수 없다. 들어오는 질의를 파싱해 앨리어스 개수를 세고 상한을 넘으면 거부하는 커스텀 미들웨어가 필요하다. 이 통제가 존재하려면 개발자가 앨리어스의 위험을 애초에 알아야 한다. 반면 배열 배칭은 명세 밖이라 설정으로 끌 수 있다 — Graphene은 `batch=True`를 `False`로 바꾸면 배열을 거부한다. 어느 기능이 켜졌는지, 끌 수 있는지는 graphw00f로 구현체를 식별하고 GraphQL Threat Matrix로 확인한다(→ 39.3).

**필드 중복 제한.** GraphQL에는 중복 필드를 막는 기본 기능이 없다. 비용 분석이 간접적으로 막는다 — 필드가 많으면(중복이든 아니든) 비용이 올라 상한에 걸린다. 별도로 미들웨어가 중복 필드를 탐지해 질의를 거부하거나, 중복을 합쳐 안전한 질의로 정규화할 수도 있다. 질의의 "높이(height)"를 계산해 상한을 두는 방식도 있다.

**레코드 수 제한.** 리졸버에서 반환 객체 수의 상한을 서버 측에 고정하고 클라이언트가 재정의하지 못하게 한다 — Graphene 리졸버에 `.limit(100)`을 두는 식이다. API 페이지네이션으로 클라이언트가 청크 단위로만 받게 하는 것도 같은 방어다. 40.4.1절의 객체 한도 재정의를 정면으로 막는다.

### 40.6.4 타임아웃, 레이트 리밋, WAF, 게이트웨이

**타임아웃**은 오래 걸리는 질의에 시간 상한을 둔다. graphql-ruby는 `GraphQL::Schema::Timeout, max_seconds: 20`을 쓴다. 구현체가 질의 타임아웃을 지원하지 않으면 Nginx·Apache 같은 웹 서버 층에서 건다(둘 다 기본 60초 언저리). 타임아웃 값 설정은 까다롭다 — 너무 짧으면 정당한 클라이언트 요청을 떨어뜨려 사용자 경험을 해치므로 기본값이 높게 잡히는데, 그러면 방어로서 무뎌진다. 타임아웃은 단독 방어가 되어서는 안 된다.

**레이트 리밋**은 초당·분당 요청 수를 제한한다. 40.4.2절에서 봤듯 그 자체로는 배칭에 무력하다 — 요청 하나에 수천 연산을 담으면 요청 수 기준 방어의 시야 밖이다. 그래서 레이트 리밋은 비용 기반 크레딧과 결합해야 의미가 있다.

**WAF**는 악의적 트래픽을 애플리케이션에 닿기 전에 막는다. GraphQL 질의에 박힌 SQL 인젝션·XSS 같은 흔한 공격 페이로드는 GraphQL을 몰라도 패턴으로 잡는다. 본문 크기 제한(바이트 상한)이나 스로틀링으로 일부 DoS도 막는다. 그러나 GraphQL을 이해하지 못하는 WAF는 이 장의 많은 공격에 무력하다 — 앨리어스·배열 배칭으로 수천 질의를 담은 단일 HTTP 요청은 위험한 패턴을 포함하지 않으므로 그냥 통과시킨다. WAF의 이 한계는 12.11절에서 이미 다룬 것의 GraphQL판이다.

**게이트웨이 프록시**는 여러 GraphQL 스키마를 하나로 병합해 노출하는 리버스 프록시다. 정책 집행과 레이트 리밋을 강제하는 네트워크 초크 포인트로서, 감사·스키마 버전 관리·인가 통제·L7 DoS 보호를 제공한다. 인가를 이 층에 두는 문제는 40.7절에서 다룬다.

### 40.6.5 질의 허용목록

**질의 허용목록(query allow list)** 은 애플리케이션이 받아들일 질의를 미리 정의하고, 목록에 없는 질의는 전부 거부하는 방어다. 신뢰하는 질의의 안전 목록이다. 이 접근은 차단목록(deny list)보다 안전하다 — 악의적 페이로드는 여러 형태로 만들 수 있어, 모든 변형을 예상하지 못하면 차단목록은 우회된다. 허용목록은 이 책이 여러 장에서 반복한 원칙 — 허용할 것을 정의하는 것이 금지할 것을 나열하는 것보다 견고하다 — 의 GraphQL 적용이다. 다만 GraphQL 구현체나 외부 라이브러리가 허용목록을 기본 제공하는 경우는 드물어, 개발자가 호환 라이브러리를 찾거나 직접 만들어야 한다.

**표 40-2**가 각 방어가 어느 벡터를 막고 무엇을 놓치는지를 정리한다.

**표 40-2. DoS 방어와 그 사각지대**

| 방어 | 막는 것 | 놓치는 것 |
|---|---|---|
| **깊이 제한** | 순환 질의의 단일 질의 팽창 | 깊이 안쪽 재귀 질의의 병렬 발사 |
| **비용 분석(정적)** | 무거운 필드·필드 중복 | 무상태면 병렬 질의; 응답 복잡도 |
| **비용 분석(동적)** | 응답 복잡도까지 | 리졸브 후에야 판정(선처리 비용) |
| **크레딧 레이트 리밋** | 시간당 누적 소모 | 상태 저장 필요; 없으면 무력 |
| **본문 크기 제한** | 거대 페이로드(배칭·중복) | 작지만 깊은 순환 질의 |
| **타임아웃** | 오래 걸리는 질의 | 값이 높으면 무뎌짐; 단독으론 부족 |
| **요청 수 레이트 리밋** | 단순 요청 폭주 | 배칭(단일 요청에 수천 연산) |
| **질의 허용목록** | 미리 정의 안 된 모든 질의 | 정당 질의 목록 유지 부담 |

이 표가 40.6절의 결론을 담는다. **어떤 단일 방어도 모든 벡터를 막지 못한다.** 40.1.2절 표 40-1의 두 유형 — 작은 질의의 팽창과 큰 질의의 소모 — 은 서로 다른 방어를 요구하고, 그 방어들이 다시 서로의 사각을 만든다. 깊이 제한은 큰 질의를 못 막고, 본문 크기 제한은 작은 순환 질의를 못 막는다. 무상태 비용 분석은 병렬 공격에 뚫리고, 요청 수 레이트 리밋은 배칭에 뚫린다. 그래서 실전 방어는 **여러 방어를 겹쳐** 각각의 사각을 다른 방어로 메우는 것이다 — 깊이 제한과 복잡도 분석과 상태 저장 크레딧과 본문 크기 제한을 함께 두어야 비로소 두 유형 모두에 상한이 씌워진다. 이 "여러 처방을 겹쳐 서로의 빈틈을 메운다"는 구조는 GraphQL만의 것이 아니다. 45.8절이 네트워크·HTTP·GraphQL 세 층위의 DoS 처방이 실은 같은 골격 — 자원에 상한을 두고, 상한을 여러 층에 겹치는 것 — 임을 일반화한다.

> **이 절이 뒷받침하는 것**
>
> - 방어를 겹쳐 사각을 메운다는 구조 → **45.8** (DoS를 설계로 막기 — 세 층위 처방의 공통 골격), **45.3** (가용성 설계), **45.4** (타임아웃과 서킷 브레이커)
> - WAF가 GraphQL 배칭에 무력한 이유 → **12.11** (WAF의 역할과 한계)
> - 허용목록이 차단목록보다 견고하다는 원칙 → **30.4** (일반화된 방어), **45.6** (검증 전에 복구하지 말라)

> **이 책의 범위를 넘어서**
>
> 이 절은 GraphQL 질의 층의 DoS 방어만 다룬다. HTTP/2 스트림 리셋을 악용하는 프로토콜 층 DoS, 클라우드형 레이트 리밋·DDoS 완화 서비스, 그리고 자동 지속 질의(automatic persisted query)를 캐싱과 허용목록의 표준 조합으로 정착시킨 최근의 실무 관행은 이 책의 다섯 원서 범위 밖이라 다루지 않는다. 다만 원리는 이 절과 이어진다 — 지속 질의는 40.6.5절 허용목록의 캐싱된 형태이고, 프로토콜 층 DoS는 40.1.2절 증폭이 더 아래 층위에서 반복된 것이다.

## 40.7 GraphQL 인증·인가의 현실 — 어디에 두어야 하는가

GraphQL은 기본 상태에서 **인증도 인가도 갖지 않는다.** 명세가 이 둘에 대한 지침을 주지 않아, 생태계가 전통적 시스템의 방식을 빌려 오거나 직접 만들었다. 이 절의 핵심 물음은 하나다 — 그 인증·인가 로직을 **어느 층에 두어야 하는가.**

### 40.7.1 판단 지점이 흩어진다는 구조적 문제

REST에서는 인가 판단 지점이 URL 경로에 대응한다. `/admin/users`에 인가를 걸면 그 경로로 오는 요청이 한자리에서 걸러진다. GraphQL은 단일 엔드포인트라 경로 기반 통제가 불가능하다(→ 38.10). 인가는 **필드나 리졸버 단위**로 내려간다. 그리고 여기에 GraphQL 특유의 구조적 문제가 있다 — **하나의 요청이 여러 리졸버를 거친다.**

질의 하나가 `pastes` → `owner` → `pastes`를 타고 내려가면, 각 단계의 리졸버가 각각 인가를 판단해야 한다. 판단 지점이 질의의 경로를 따라 흩어진다. 개발자가 `pastes`에는 인가를 걸고 `owner.pastes`에는 빠뜨리면, 클라이언트는 우회 경로로 같은 데이터에 닿는다. 40.8절에서 볼 graphql-path-enum이 정확히 이 문제를 겨냥한다 — 한 객체 타입에 이르는 모든 경로를 열거해, 그중 인가가 빠진 경로를 찾는다. 인가 판단이 흩어질수록 하나를 빠뜨릴 확률이 커지고, 빠뜨린 지점이 곧 우회 경로가 된다.

이 문제는 24.7절이 세운 명제 — **인가는 경계 검증의 한 형태다** — 를 GraphQL에서 다시 묻게 만든다. 경계 검증은 경계가 하나로 모여 있을 때 견고하다. GraphQL은 그 경계를 필드마다 흩어 놓았으므로, 인가를 견고하게 하려면 흩어진 판단 지점을 하나의 진실로 다시 모아야 한다.

### 40.7.2 인밴드 대 아웃오브밴드

인증·인가 아키텍처는 두 모델로 갈린다.

**인밴드(in-band)** 는 로그인·가입·역할 기반 접근 통제를 GraphQL API 안에 직접 구현한다. 클라이언트에게 데이터를 주는 같은 GraphQL 인스턴스가 인증과 권한 부여도 맡는다. 로그인 자격증명을 받는 질의·뮤테이션을 두고, API가 검증 후 토큰을 발급한다.

**아웃오브밴드(out-of-band)** 는 접근 통제 로직을 별도 서비스나 외부 시스템 — API 게이트웨이, 컨테이너 사이드카, 다른 서버 — 에 둔다. GraphQL API는 인증·인가 결정을 그쪽에 위임하고, 인가 로직을 GraphQL에서 분리한다.

둘 중 **인밴드가 더 취약하다.** 복잡도가 API 공격 표면을 크게 늘린다. 인밴드 API는 서비스로 들어오는 진입점마다 권한 로직을 중복하는 경향이 있고 — 40.7.1절이 말한 흩어짐이 그것이다 — 그중 미세하게 어긋난 통제 하나가 공격의 발판이 된다.

### 40.7.3 인가를 어느 층에 두어야 하는가

그래서 생태계의 현재 모범 실무는 인증·인가 로직을 GraphQL 밖에 두는 것이다. **표 40-3**이 네 층의 역할을 정리한다.

**표 40-3. 인증·인가의 층 배치**

| 층 | 맡는 것 | 왜 |
|---|---|---|
| **게이트웨이 층** | 인증(authentication) | 전체 API의 진입을 한자리에서 통제, 인증된 사용자 컨텍스트를 API에 전달 |
| **GraphQL API 층** | (인가 판단을 갖지 않음) | 흩어진 필드·리졸버에 판단을 두면 누락 지점 발생 |
| **비즈니스 로직 층** | 인가(authorization) | 모든 도메인 규칙의 단일 진실 원천 |
| **영속성 층** | 데이터 저장 | — |

핵심은 **인가를 비즈니스 로직 층에 두는 것**이다. 이 층이 모든 비즈니스 도메인 규칙의 단일 진실 원천(single source of truth)이며, GraphQL 층과 영속성 층 사이에 앉는다. 인증은 외부 게이트웨이 층에서 일어나 인증된 사용자 컨텍스트를 API에 넘긴다.

이 배치는 이 책이 24장에서 세운 것을 그대로 적용한다. 24.6절의 **다층 권한 모델** — 인가를 한 층에만 의존하지 않고 여러 층에 배치한다 — 이 여기서 게이트웨이·비즈니스·영속성의 분업으로 나타난다. 24.7절의 **인가는 경계 검증** — 인가를 흩어진 리졸버가 아니라 명확한 경계(비즈니스 로직 층)에 모은다. 그리고 GraphQL 게이트웨이가 여러 백엔드 서비스의 스키마를 병합하는 순간, 24.8절의 **서비스 경계를 넘는 민감 데이터** 문제가 그대로 성립한다 — 게이트웨이 뒤의 어느 서비스가 어떤 데이터를 노출하는지, 인가가 서비스 경계에서 일관되게 적용되는지가 마이크로서비스 인가의 핵심이 된다. GraphQL의 필드 단위 인가는 이 경계 문제를 필드 수만큼 잘게 쪼갠 것이다.

### 40.7.4 흔한 통제 방식

실전에서 마주치는 인증·인가 통제는 다양하다. **표 40-4**가 주요 방식과 각각의 약점을 정리한다.

**표 40-4. GraphQL의 흔한 인증·인가 통제**

| 방식 | 성질 | 약점 |
|---|---|---|
| **HTTP 기본 인증** | Base64 인코딩 자격증명을 매 요청 헤더에 | 인코딩일 뿐 암호화 아님(→ 21.3); 로그아웃 없음, 매 요청 전송으로 탈취 창 넓음 |
| **OAuth 2.0 / JWT** | 토큰 기반, JWT는 헤더·페이로드·서명 3부 | `alg:none` 수용 시 위조; 서명 미검증 시 위조; 미암호화 시 페이로드 노출 |
| **GraphQL Modules** | 스키마를 미들웨어 모듈로 분리, login·signup·me 제공 | 인밴드 인증 연산이 배치 무차별 대입 대상(→ 40.8) |
| **GraphQL Shield** | 규칙 기반 인가 층(`isAuthenticated`, `isAdmin`) | `fallbackRule` 기본값이 `allow` — 규칙 없는 필드가 열림 |
| **스키마 디렉티브** | `@auth`, `@protect`, `@hasRole`로 필드 장식 | 디렉티브가 어디 적용됐는지 인트로스펙션에 안 드러남 |
| **IP 기반 허용목록** | 출발지 IP로 인가 | `X-Forwarded-For` 등 헤더 위조로 우회(→ 8.6) |

몇 가지를 짚는다. JWT는 헤더·페이로드·서명 세 부분을 마침표로 잇고 Base64로 인코딩한다. `alg` 헤더가 서명 알고리즘을 정하는데, 이를 `none`으로 두고 서명 없는 토큰을 수용하는 서버는 공격자가 신원을 바꾼 토큰을 그대로 받는다. 서명을 검증하지 않는 서버도 마찬가지로 위조에 뚫린다. JWT는 암호화가 아니라 서명이므로, 미암호화 페이로드에 민감 정보(하드코딩된 API 토큰 등)를 담으면 Base64 디코딩만으로 새어 나온다.

GraphQL Shield의 `fallbackRule`은 특히 위험하다. 규칙이 정의되지 않은 필드에 기본으로 적용되는데, 그 기본값이 `allow`다. 개발자가 규칙 거는 것을 잊은 필드가 열린 채 남는다 — 40.7.1절의 흩어진 판단 지점 문제가 라이브러리 기본값으로 구체화된 형태다. 코드 리뷰에서 `fallbackRule`이 `deny`로 뒤집혀 있는지 확인하는 것이 GraphQL Shield 감사의 급소다.

IP 기반 허용목록은 리버스 프록시가 전달하는 `X-Forwarded-For`, `X-Real-IP` 같은 헤더로 출발지를 판단한다. 클라이언트가 이 헤더를 위조할 수 있고 프록시가 그것을 맹목적으로 전달하면, 허용된 네트워크 대역(예: `10.0.0.0/24`)의 IP를 헤더에 넣어 통제를 우회한다. 8.6절이 "헤더의 신뢰성 — `X-Forwarded-For`를 믿을 수 있는가"에서 세운 원칙이 그대로 적용된다.

## 40.8 인증 테스트 / 인가 테스트

40.7절이 통제의 배치를 다뤘다면, 이 절은 그 통제를 뚫는 절차다. 39장이 뽑은 스키마가 여기서 좌표로 쓰인다 — 어떤 뮤테이션이 있는지 알아야 그것에 인증·인가가 걸렸는지 시험할 수 있다.

### 40.8.1 인증 층 탐지

인증 층이 있는지, 어느 유형인지는 **카나리아 질의(canary query)** 로 탐지한다. 인트로스펙션 질의나 직접 만든 탐침 질의를 보내고, 돌아오는 신호를 읽는다.

- **HTTP 상태 코드.** 대부분의 GraphQL 구현체는 오타·오류가 있어도 항상 `200 OK`를 돌려준다. `403 Forbidden`이 오면 게이트웨이나 WAF 같은 아웃오브밴드 통제가 요청을 API에 닿기 전에 막았을 가능성이 크다. 상태 코드가 인증 층의 위치(인밴드냐 아웃오브밴드냐)를 흘린다.
- **오류 메시지.** `Authentication credentials are missing`은 OAuth 2.0 Bearer + JWT, `Not Authorised!`는 GraphQL Shield, `Not logged in`은 GraphQL Modules를 시사한다. 오류 메시지는 커스터마이즈될 수 있어 확정이 아니라 단서다. `200 OK`와 오류 메시지의 조합은 인증이 필요하다는 신호다.
- **인증 관련 필드.** 뮤테이션을 인트로스펙션해 `login`, `logout`, `signup`, `register`, `createUser`, `me` 같은 이름이 나오면 인밴드 인증 층이 있다는 뜻이고, 그러면 무차별 대입 저항성을 시험할 수 있다.

### 40.8.2 배치로 인증 무차별 대입

40.3.2절에서 예고한 앨리어스의 비-DoS 용도가 여기다. 무차별 대입은 레이트 리밋을 못 갖춘 시스템에 수많은 로그인을 던지는 고전적 공격이다. WAF는 단일 클라이언트의 과도한 HTTP 요청을 잘 막는다 — 요청 하나하나를 세기 때문이다. 그런데 **배치는 여러 로그인 시도를 단일 HTTP 요청에 담는다.** 요청 수를 세는 방어가 무력해진다.

```graphql
mutation {
  alias1: login(username: "admin", password: "admin") { accessToken }
  alias2: login(username: "admin", password: "password") { accessToken }
  alias3: login(username: "admin", password: "pass123") { accessToken }
  # ... 수백·수천 개
  alias10: login(username: "operator", password: "password123") { accessToken }
}
```

모든 주요 GraphQL 구현체가 명세에 정의된 앨리어스 배칭을 지원하므로 이 기법은 거의 어디서나 통한다. 성공한 앨리어스만 `accessToken`을 담아 돌아오고, 나머지는 `Authentication Failure` 오류가 된다. 위 예에서 `alias10`이 유효 토큰을 돌려주면 operator의 비밀번호가 `password123`임이 확정된다. 분당 5회 로그인으로 제한하는 방어가 있어도, 단일 요청에 10회(혹은 수천 회)를 담았으므로 그 로직을 통째로 우회한다.

손으로 큰 문서를 짜는 것은 번거로우므로 CrackQL이 자동화한다. 단일 로그인 질의와 CSV 워드리스트를 받아 앨리어스 페이로드를 자동 생성한다. 비용 통제가 큰 배치를 막으면 `-b` 플래그로 앨리어스 수를 줄여 레이더 밑으로 난다. CrackQL은 2FA 토큰 무차별 대입, 계정 열거, IDOR용 식별자 퍼징에도 쓰인다.

인증을 우회하는 두 가지 방식이 더 있다. **허용목록 연산 이름 우회** — 일부 구현체는 인증 없는 클라이언트에게 특정 연산 이름(`RegisterAccount` 등)만 허용하는데, 연산 이름은 클라이언트가 정하므로 허용된 이름을 붙여 다른 뮤테이션을 실행한다. **JWT 위조** — 서명을 검증하지 않는 서버에서 jwt.io로 페이로드의 `"identity": "operator"`를 `"identity": "admin"`으로 바꾸면 관리자로 인증된다. 40.9절의 여러 사례가 이 위조 계열이다.

### 40.8.3 인가 테스트

인가 테스트의 목표는 제한된 계정으로 얼마나 권한을 상승시킬 수 있는지 — 읽지 말아야 할 데이터를 읽거나, 하지 말아야 할 기능을 수행할 수 있는지 — 를 확인하는 것이다. GraphQL 특유의 인가 결함은 **권한 검사가 리졸버 층에서, 또는 비즈니스 로직·상태 변경이 실행된 뒤에** 일어날 때 생긴다.

인가 층 탐지는 스키마 디렉티브 인트로스펙션으로 시작한다. `@auth`, `@authorize`, `@authz` 같은 디렉티브 이름이 나오면 스키마가 그것을 지원한다는 뜻이다. 다만 디렉티브가 **어디에** 적용됐는지는 인트로스펙션에 드러나지 않는다 — `password` 필드가 존재하는 줄은 알아도 거기 `@auth(requires: ADMIN)`이 걸렸는지는 SDL 파일이 없으면 모른다. 화이트박스 테스트에서만 이 배치가 보인다.

핵심 도구는 **graphql-path-enum**이다. 40.7.1절의 흩어진 판단 지점 문제를 정면으로 겨냥한다. 한 객체 타입에 이르는 모든 경로를 열거한다.

```
# ./graphql-path-enum -i introspection.json -t PasteObject

Found 3 ways to reach the "PasteObject" node:
- Query (pastes) -> PasteObject
- Query (paste) -> PasteObject
- Query (readAndBurn) -> PasteObject
```

`PasteObject`에 이르는 경로가 셋이다. 개발자가 인밴드 인가를 구현하며 이 셋 중 일부만 보호했을 수 있다. 세 질의를 각각 보내, 어느 하나가 다른 질의는 막는 객체에 접근을 허용하는지 확인한다. 스키마가 클수록 경로 열거의 자동화가 중요해진다.

그리고 CrackQL로 인가가 걸렸을 법한 인자·필드를 무차별 대입한다. `users(id: {{id|int}})`의 id를 1부터 100까지 밀어 넣어 접근하지 말아야 할 사용자의 `username`·`password`를 뽑는 것이 IDOR(insecure direct object reference) 테스트다. 원래 질의에 `accessToken`, `birthDate` 같은 필드를 추가해, 인가로 가려졌어야 할 필드가 실제로 나오는지도 시험한다.

> **이 절이 뒷받침하는 것**
>

## 40.9 공개된 취약점과 익스플로잇 사례 연구 — DoS, 깨진 인가, 정보 노출, 인젝션, CSRF

공개된 취약점 보고서는 랩이 못 가르치는 것을 가르친다 — 실제 애플리케이션의 고유한 취약점, 그것을 발견하고 책임 있게 공개하는 과정, 그리고 회사가 택한 완화책이다. 이 절은 BHGQL 10장의 실제 CVE·버그바운티 사례를 다루되, 각 사례가 **이 책의 어느 장에 대응하는지**를 38.10절 대응표의 축으로 표시한다. 대응 장을 아는 것이 사례를 고립된 일화가 아니라 이 책이 세운 실패 유형의 실증으로 읽게 한다.

### 40.9.1 서비스 거부

**대형 페이로드(HackerOne, 2020년 5월).** HackerOne은 자사 플랫폼에 GraphQL을 폭넓게 쓴다. 한 해커가 문서상 존재한다던 질의 입력 문자 수 제한이 실제로는 강제되지 않음을 발견했다. `createStructuredScope` 뮤테이션의 `instruction` 인자에 15만 자짜리 페이로드를 담아 몇 번 보내자 서버가 `500`, `502`, `504` 오류를 뱉으며 DoS에 빠졌다. 보상 $2,500. → **40.3·40.4** (필드 중복·거대 페이로드). DoS는 서버를 완전히 죽이지 않아도 자원을 태워 눈에 띄는 성능 저하를 일으키면 성립한다는 40.1.4절의 논점을 실증한다.

**정규식(CS Money, 2020년 10월).** 앞의 40.1~40.6절이 다루지 않은 형태인 ReDoS(정규식 DoS)다. `search`의 `q` 인자에 유니코드 널(`\u0000`)을 넣자 서버가 `(?=.*\u0000)`이 든 정규식 오류를 흘려, 입력이 정규식 매칭에 흘러듦을 노출했다. 마침 질의 추적이 `extensions`에 켜져 있어 처리 시간(`duration`)까지 드러났다 — 39.7절이 말한 오류·추적 메타데이터 남용이다. 해커는 악성 정규식 패턴을 `q`에 넣어 100회 실행으로 서버를 완전히 무너뜨렸다. 보상 $250. → **45.6** (잘못된 데이터 다루기), 정규식 처리의 자원 소모.

**순환 인트로스펙션(GitLab, 2019년 7월).** 해커 freddd가 `__schema` → `types` → `fields` → `type`의 재귀로 DoS를 유발했다. GitLab은 순환 질의 DoS를 막으려 복잡도 검사를 구현해 뒀지만 **그 검사가 인트로스펙션 질의에는 적용되지 않아** 빈틈이 남았다. 인증 없이도 악용 가능해 심각도가 높았다. → **40.2** (순환 질의), 40.6.2절 깊이 방어의 사각을 실증한다.

**앨리어스 필드 중복(Magento, 2021년 4월).** 이커머스 플랫폼 Magento가 필드를 수천 번 반복하는 질의를 막지 못했다. `countries` 질의에 `full_name_english`를 수천 번 반복하고 그것을 앨리어스로 배치해, 인증 없이 자원을 고갈시켰다. 이후 Magento는 `queryComplexity` 300, `queryDepth` 20의 기본 통제를 도입했다. → **40.3** (필드 중복·앨리어스), 40.6.1·40.6.2절 방어의 실제 적용.

**배열 배칭 필드 중복(WPGraphQL, 2021년 4월).** WordPress용 GraphQL 플러그인이 세 결함을 겹쳐 취약했다 — 배열 배칭 허용, 빈약한 보안 통제, 인증 없는 클라이언트 접근. 익스플로잇은 `FORCE_MULTIPLIER`(필드 중복 배수)와 `CHAINED_REQUESTS`(배열 요소 수)를 곱해, 둘을 100으로 두면 100개 중복 필드를 담은 질의 100개의 배열을 만들었다. → **40.4** (배열 배칭), 40.4.2절 결합 공격의 실증.

**순환 프래그먼트(Agoo, 2022년 5월, CVE-2022-30288).** Ruby 기반 서버 Agoo가 들어오는 질의를 검증하지 않아 — 명세 비준수 — 순환 프래그먼트에 얼어붙었다. `__Schema` 타입 위에 서로를 부르는 두 프래그먼트를 만들어 무한 실행을 유발했고, 복구 방법은 서버 프로세스 재시작뿐이었다. → **40.2** (순환 프래그먼트), 40.2.3절이 말한 "명세 준수가 방어의 일부"를 실증한다.

### 40.9.2 깨진 인가

**비활성 사용자의 데이터 접근(GitLab, 2021년 8월).** 해커 Joaxcar가 비활성화된 사용자 계정의 API 키로 GraphQL API를 호출해 `labelCreate` 뮤테이션을 실행했다. 비활성 계정은 재활성화 전까지 접근이 거부돼야 하는데, 유효 API 키가 그대로 먹혔다. 유출된 자격증명을 가진 위협 행위자가 비활성 계정으로도 행동할 수 있음을 뜻한다. → **24장** (접근 통제), 인가 판단이 계정 상태를 확인하지 않은 결함.

**비권한 직원의 고객 이메일 수정(Shopify, 2021년 9월).** 해커 ash_nz가 권한 없는 상점 직원 계정으로 `emailSenderConfigurationUpdate` 뮤테이션을 써서 고객 이메일을 수정했다. API 호출자에게 그럴 권한이 없는데도 변경이 성사됐다. 여러 권한 수준으로 API를 평가하고 교차 계정·교차 사용자 접근을 시도하는 것이 이런 결함을 드러낸다. 보상 $1,500. → **24장** (수평·수직 권한 상승), 40.8.3절 인가 테스트의 실증.

**팀 객체로 허용 해커 수 노출(HackerOne, 2018년 4월).** 해커 haxta4ok00이 `team` 객체의 `whitelisted_hackers.total_count` 필드에 접근해, 접근하지 말아야 할 필드를 읽었다. `handle` 인자로 프로그램을 검색할 수 있어, 비공개 프로그램의 존재를 추론하는 정보 노출로 이어졌다. 데이터 자체는 민감하지 않아도 그것으로 비공개 프로그램(=HackerOne의 고객)을 식별할 수 있었다. 보상 $2,500. → **24장 + 30장** (깨진 인가가 정보 노출로).

**비공개 노트 읽기(GitLab, 2019년 6월, CVE-2019-15576).** 해커 ngalog이 REST API에서는 제대로 제한된 이슈의 비공개 노트를, GraphQL API의 `issue.notes` 필드로 읽어냈다. **같은 데이터에 REST와 GraphQL의 인가가 어긋난** 전형이다. → **24장 + 30장**, 40.7.1절이 말한 "경로마다 인가가 흩어진다"가 프로토콜 경계에서 재현된 형태다.

**결제 거래 정보 노출(HackerOne, 2019년 10월).** 해커 msdian7이 `team`의 `payment_transactions.total_count`에 무인가 세션으로 접근해, 다른 버그바운티 프로그램의 거래 수 — 기밀이어야 할 정보 — 를 읽었다. → **24.8** (서비스 경계를 넘는 민감 데이터), 인가가 서비스 경계에서 일관되지 않은 결함.

### 40.9.3 정보 노출

**사용자 열거(GitLab, CVE-2021-4191).** Rapid7이 발견한 이 취약점은 사용자 등록 인터페이스를 제한한 비공개 GitLab 인스턴스에서도, `users` 필드로 인증 없이 사용자 정보(이름·사용자명·ID·이메일·위치·그룹 멤버십·계정 상태)를 뽑게 했다. 이메일은 피싱으로, 그룹 멤버십은 회사 구조 추론으로, 계정 상태는 무차별 대입 최적화로 이어진다. 인증이 필요 없어 심각도가 높았다. → **30장 + 39.5** (정보 노출), 열거 공격의 실증.

**WebSocket으로 인트로스펙션 접근(Nuri, 2020년 4월).** 해커 zerodivisi0n이 HTTP에서는 비활성인 인트로스펙션을, **WebSocket 전송으로** 접근했다. graphql-ws 같은 라이브러리는 서브스크립션뿐 아니라 질의·뮤테이션도 WebSocket으로 받는데, 인트로스펙션 차단이 HTTP 인터페이스에만 적용되고 WebSocket에는 적용되지 않았다. → **39.2** (인트로스펙션) + **37.7** (WebSocket 보안), 방어가 전송 계층마다 일관되지 않은 결함. 40.7.1절의 "판단 지점이 흩어진다"가 전송 계층으로 확장된 형태다.

### 40.9.4 인젝션

**GET 파라미터의 SQL 인젝션(HackerOne, 2018년 11월).** 해커 Jobert가 비표준 URL 파라미터 `embedded_submission_form_uuid`를 발견했다. 이 값이 검사 없이 `SET SESSION #{key} TO #{value}` 문자열 보간에 흘러들어 SQL 인젝션이 성립했다. `pg_sleep(10)`을 넣은 시간 기반 기법으로, 응답이 10.5초 걸림을 `time` 명령으로 확인해 취약점을 입증했다. → **27.14** (GraphQL을 경유한 SQL 인젝션). GraphQL 파라미터가 자동으로 소독되지 않는다는 27장의 논점을 실증한다.

**객체 인자의 SQL 인젝션(Apache SkyWalking, 2020년 6월, CVE-2020-9483).** 해커 Jumbo-WJB가 `getLinearIntValues`의 `metric` 인자 안 `id` 키에 SQL 구문을 담아 인젝션했다. `id`가 H2·MySQL 백엔드에 삽입되기 전에 소독되지 않았다. Java `StringBuilder`로 문자열을 조립해 SQL에 그대로 쓴 코드가 원인이었다. → **27.14**, 인자가 객체의 키로 중첩돼도 인젝션 경로가 됨을 보인다.

**XSS(GraphQL Playground, CVE-2021-41249).** GraphQL Playground IDE의 반사형 XSS다. 다른 사례와 달리 **API 소비자를 직접** 노린다. 공격자가 서버 스키마의 타입 이름을 악성 페이로드(`name = "MyMaliciousTypeName"` 자리에 스크립트)로 바꾸거나, 악성 서버 주소를 담은 링크로 피해자를 유인한다. 피해자가 링크를 열면 브라우저가 악성 API를 로드하고 그 페이로드가 Playground에서 실행된다. → **32장** (XSS), 데이터 전달 경로가 GraphQL 응답일 뿐 XSS 자체는 동일하다는 38.10절 대응의 실증.

### 40.9.5 요청 위조(CSRF)

**GET 기반 CSRF(GitLab, 2021년 3월).** 해커 az3z3l이 GitLab의 CSRF 보호 빈틈을 찾았다. GitLab은 POST 질의를 `X-CSRF-Token` 헤더로 보호했지만, **GET 질의도 지원**하면서 GET에는 그 보호가 적용되지 않았다. GET이 데이터 변경에 쓰이지 않는다는 통념 때문에 안티 CSRF 토큰을 걸지 않았는데, GraphQL은 GET으로도 뮤테이션을 받았다. HTML 폼을 `method="GET"`으로 자동 제출해 `CreateSnippet` 뮤테이션을 피해자 대신 실행했다. → **33.6** (GraphQL CSRF — GET 기반 질의). 39.8절이 예고한 대로, GET 허용이라는 한 번의 결정이 정보 노출과 CSRF 두 문을 동시에 여는 것을 실증한다.

## 40.10 GraphQL API 테스트 체크리스트

이 절은 이 부의 절차 전체를 흐름 속의 요약으로 묶는다. 독립 참조용 전체 체크리스트 — 침투 테스트 팁, 실습 랩, 참고 자료까지 — 는 부록 H가 담는다. 여기서는 본문의 각 절이 어느 점검 항목으로 이어지는지를 간결히 짚는다.

**정찰(→ 39장).** GraphQL 엔드포인트를 스캔하고(graphw00f 탐지 모드), 서버를 핑거프린팅하며(graphw00f 지문 모드), CVE·GraphQL Threat Matrix에서 서버 취약점·기능을 확인한다. 인트로스펙션 질의로 질의·뮤테이션·서브스크립션을 문서화하고 GraphQL Voyager로 시각화한다. IDE(GraphiQL·Playground)를 EyeWitness로 찾는다.

**서비스 거부(→ 40.1~40.6).** SDL에서 양방향 관계를 검토하고, 순환 질의·순환 프래그먼트·필드 중복·앨리어스 과부하·디렉티브 과부하·배열/앨리어스 배칭·객체 한도 재정의(`filter`·`max`·`limit`·`total` 인자)를 시험한다. GraphQL Cop으로 1차 스윕한다.

**정보 노출(→ 39.4~39.8).** 인트로스펙션이 꺼졌으면 필드 스터핑으로 스키마를 복원하고, 오작동 질의로 디버그 오류를, 응답에서 질의 추적을 찾으며, GET으로 보낸 PII를 점검한다.

**인증·인가(→ 40.7~40.8).** 인증 헤더 없이, 대체 경로로, GET·POST 양쪽으로 접근을 시험한다. JWT 서명 검증을 시험하고, 토큰·비밀번호를 받는 연산을 앨리어스·배열 배칭과 CrackQL로 무차별 대입한다.

**인젝션(→ 27.14, 28.10).** 질의 인자·필드 인자·디렉티브 인자·연산 이름에서 인젝션을, SQLmap·Commix로 SQLi·OS 명령 인젝션을 시험한다.

**요청 위조·하이재킹(→ 33.6, 37.7).** 안티 CSRF 토큰의 존재와 우회, GET 기반 질의·뮤테이션 지원을 점검한다. 서브스크립션 지원 여부와 WebSocket 핸드셰이크의 Origin 검증(→ 37.7)을 확인한다.

이 여섯 묶음이 Part VIII 전체의 실행 순서다. 정찰이 지도를 그리고, DoS·정보 노출·인증·인가·인젝션·요청 위조가 그 지도 위를 걷는다. 부록 H가 이 항목들을 도구·명령과 함께 독립 참조 형태로 완결한다.

> **이 절이 뒷받침하는 것**
>
> - 흐름 속 요약과 독립 참조의 분업 → **부록 H** (전체 체크리스트와 학습 자료)

## 이 장의 요약

- **GraphQL DoS가 이 부의 유일한 새 취약점인 이유는 하나다.** REST는 서버가 응답의 비용을 정하지만, GraphQL은 선언적 질의 언어로 클라이언트가 질의 구조를 정한다 — 클라이언트가 서버 자원 소모의 다이얼을 쥔다. 이것이 앞의 여덟 부에 대응 장이 없는 유일한 조건이다.
- **DoS는 증폭과 비대칭의 문제다.** 작은 요청이 큰 소모를 강요하는 증폭(→ 4.7의 UDP 반사와 같은 개념, 다른 층위)과, 값싼 공격 대 비싼 방어의 비대칭(→ 3.9.2)이 성패를 가른다. 방어의 목표는 그 비용 기울기를 되돌리는 것이다.
- **벡터는 두 유형이다.** 순환 질의·객체 한도 재정의는 작은 질의로 응답을 부풀리고(깊이 제한으로 방어), 필드 중복·앨리어스·디렉티브·배칭은 큰 질의로 파싱·리졸브를 태운다(복잡도·본문 크기 제한으로 방어). 하나의 방어가 둘 다 막지 못한다.
- **어떤 단일 DoS 방어도 완전하지 않다.** 깊이 제한은 병렬 재귀에, 무상태 비용 분석은 병렬 질의에, 요청 수 레이트 리밋은 배칭에 뚫린다. 실전 방어는 여러 처방을 겹쳐 서로의 사각을 메우며, 이 골격은 네트워크·HTTP·GraphQL 세 층위에 공통이다(→ 45.8).
- **GraphQL 인가의 구조적 문제는 판단 지점이 흩어진다는 것이다.** 한 요청이 여러 리졸버를 거치므로 인가가 필드마다 흩어지고, 하나를 빠뜨리면 우회 경로가 된다. 그래서 인가는 리졸버가 아니라 비즈니스 로직 층의 단일 진실 원천에 모아야 한다(→ 24.6·24.7·24.8).
- **인밴드 인증은 배치에 취약하다.** 앨리어스·배열 배칭이 수천 번의 로그인 시도를 단일 HTTP 요청에 담아 요청 수 기반 레이트 리밋을 우회한다. graphql-path-enum이 흩어진 경로 중 인가 누락 지점을, CrackQL이 IDOR·무차별 대입을 자동화한다.
- **공개된 17개 사례 중 열하나가 DoS 아닌 옛 취약점이다.** 24·27·30·32·33장에 대응하는 실제 프로덕션 취약점들이, "병은 옛것이고 GraphQL은 문의 모양만 바꿨다"는 이 부의 논지를 분포로 확인한다.
- **본문 체크리스트는 흐름의 요약, 부록 H는 독립 참조다.** 정찰→DoS→정보 노출→인증·인가→인젝션→요청 위조의 여섯 묶음이 Part VIII 전체의 실행 순서다.

## 이어지는 장

이 장으로 Part VIII이 끝난다. GraphQL이라는 현대 API가 옛 병을 어떻게 새 문으로 들이는지, 그리고 그 문 중 DoS 하나만이 정말 새 문인지를 여덟 부에 걸쳐 확인했다. 38장이 대응표로 예고하고, 39장이 정찰로 지도를 그렸으며, 이 장이 그 위에서 DoS·인가·공개 취약점을 실습으로 닫았다.

그런데 이 장이 남긴 가장 큰 질문은 방어 쪽에 있다. 40.6절은 여러 DoS 방어를 나열하고 각각의 사각을 짚었지만, "왜 이 방어들이 하나같이 불완전한가", "왜 개발자는 이 방어를 애초에 심지 않는가"에는 답하지 않았다. 40.7절은 인가를 비즈니스 로직 층에 모아야 한다고 했지만, "왜 GraphQL은 그것을 리졸버에 흩어 놓기 쉽게 설계됐는가"를 묻지 않았다. 이 물음들은 GraphQL만의 것이 아니다. 이 책이 여덟 부에 걸쳐 본 모든 취약점이 결국 같은 물음으로 수렴한다 — **왜 같은 것이 계속 깨지는가.**

Part IX가 이 물음을 정면으로 받는다. 앞의 여덟 부가 "무엇이 깨지는가"였다면, 이제부터는 "왜 같은 것이 계속 깨지며, 어떻게 설계로 그것을 막는가"다. 41장은 보안이 나중에 덧붙이는 기능이 아니라 설계에 스며드는 관심사임을 세우고, 45장은 이 장의 DoS 방어들을 "가용성을 위한 설계"라는 하나의 틀로 다시 묶는다(→ 45.3·45.4·45.8). 40.6절이 나열에 그친 것을 45.8절이 원리로 완성한다 — 네트워크·HTTP·GraphQL 세 층위의 DoS 처방이 실은 하나의 골격임을, 그리고 그 골격을 설계 단계에서 심는 법을.
