# 1장. 인터넷의 계층 구조: 패킷은 어떻게 목적지에 도달하는가

> **이 장에서 다루는 것**
>
> - 계층으로 나눈 설계가 얻어낸 것과 감춘 것
> - HTTP 메시지 하나가 링크 프레임이 되기까지의 변환 과정
> - 지연과 대역폭이 왜 독립적인 두 개의 제약인지
> - RTT라는 단위, 그리고 이 책이 그것을 반복해서 꺼내 쓰는 이유
> - 계층 경계가 신뢰 경계가 아니라는 사실이 뒤의 모든 장에서 갖는 함의

HTTP를 설명하는 대부분의 문헌은 "HTTP는 TCP 위에서 동작한다"는 한 문장으로 하위 계층을 처리한다. 애플리케이션을 만드는 데는 충분한 요약이다. 그러나 보안을 다루려면 그 한 문장이 감춘 것을 꺼내야 한다.

이 책에서 다루게 될 취약점 상당수는 상위 계층이 하위 계층의 성질을 잘못 가정한 결과다. 요청 본문의 경계를 두 개의 헤더가 서로 다르게 지시할 때 중간자와 종단이 다르게 해석하는 문제(→ 10.4)는 "TCP가 메시지 경계를 알려주지 않는다"는 사실에서 출발한다. 클라이언트 IP 주소로 사용자를 식별하려는 시도(→ 20.2)는 "주소가 한 사람을 가리킨다"는 가정이 NAT 앞에서 무너지기 때문에 실패한다. TLS 핸드셰이크를 한 번 줄이는 것이 왜 그렇게 값진지(→ 19.2)는 RTT라는 단위를 몸으로 알기 전에는 설득되지 않는다.

이 장의 목표는 네트워크 교과서를 대체하는 것이 아니다. 그 역할을 하는 좋은 책은 이미 많다. 이 장은 **뒤의 46개 장이 인용할 수 있는 형태로 하위 계층의 성질을 정리해 두는 것**을 목표로 한다. 그래서 각 절은 기술 서술로 시작하되, 그 서술이 어느 장의 어떤 논의를 뒷받침하는지를 밝히며 끝난다.

## 1.1 계층으로 나눈다는 것 — 관심사의 분리가 만든 것과 감춘 것

인터넷이 지금의 규모로 자란 이유를 하나만 꼽으라면, 그것은 **계층화(layering)** 다.

계층화의 규칙은 단순하다. 각 계층은 자기 아래 계층이 제공하는 서비스만 사용하고, 자기 위 계층에는 정해진 서비스만 제공한다. 계층 내부의 구현은 위아래 어느 쪽에도 노출되지 않는다. 이 규칙 덕분에 이더넷을 WiFi로 바꿔도 TCP를 고칠 필요가 없고, TCP의 혼잡 제어 알고리즘을 교체해도 HTTP는 아무것도 모른 채 계속 동작한다.

이것이 계층화가 **만들어낸** 것이다. 각 계층이 독립적으로 진화할 수 있게 됐고, 그 결과 30년 넘게 서로 다른 속도로 발전한 기술들이 하나의 스택 안에서 공존하게 됐다.

그런데 계층화는 동시에 무엇인가를 **감춘다.** 그리고 감춰진 것이 보안에서 문제가 된다.

계층화의 핵심 기법은 **추상화(abstraction)** 다. 추상화란 "이 아래에서 무슨 일이 일어나는지 신경 쓰지 않아도 된다"는 약속이다. 애플리케이션 개발자는 소켓에 바이트를 쓰면 상대편 소켓에서 같은 바이트가 같은 순서로 나온다고 믿는다. 그 믿음은 대체로 옳다. 문제는 **"대체로"** 에 있다.

추상화는 편의를 제공하는 대신 세 가지를 숨긴다.

**첫째, 실패의 양상을 숨긴다.** TCP는 "신뢰성 있는 전송"을 제공한다고 말한다. 그러나 이 문장의 실제 의미는 "전달되는 바이트는 순서대로, 손상 없이 전달된다"이지 "항상 전달된다"가 아니다. 커넥션이 끊기면 무엇이 전달되고 무엇이 전달되지 않았는지 애플리케이션은 알 수 없다. HTTP가 커넥션 종료를 다루는 방식이 그렇게 까다로운 이유(→ 9.9)가 여기에 있다.

**둘째, 비용을 숨긴다.** `connect()` 한 줄은 코드에서 한 줄이지만 네트워크에서는 최소 1왕복이다. 서울과 프랑크푸르트 사이라면 그 한 줄이 약 250밀리초다. 추상화는 이 비용을 코드의 형태에서 지운다. 그래서 성능 문제는 대개 "코드를 봐서는 알 수 없는" 형태로 나타난다.

**셋째, 의미의 불일치를 숨긴다.** 이것이 보안에서 가장 중요하다. TCP는 바이트 스트림을 전달한다. 그 스트림 안에서 "메시지 하나"가 어디서 끝나는지는 TCP의 관심사가 아니다. 그것은 HTTP의 관심사다. 그런데 그 스트림을 읽는 주체가 하나가 아니라면 — 클라이언트와 서버 사이에 프록시, 캐시, 로드밸런서, WAF가 있다면 — **각각이 "메시지 하나"를 다르게 셀 수 있다.** 계층화는 이 위험을 만들지 않았지만, 감췄다.

이 책의 논지를 한 문장으로 압축하면 이렇다.

> **계층은 관심사를 분리하지만 신뢰를 분리하지 않는다.**

1.4절에서 이 문장을 다시, 더 구체적으로 다룬다.

## 1.2 TCP/IP 4계층과 OSI 7계층의 대응

계층 모델은 두 종류가 통용된다. 실무에서 실제로 구현된 **TCP/IP 모델**과, 개념 정리와 교육에 쓰이는 **OSI 참조 모델**이다.

**표 1-1. 두 계층 모델의 대응**

| OSI 7계층 | TCP/IP 4계층 | 이 계층에서 다루는 주소·단위 | 대표 프로토콜 |
|---|---|---|---|
| 7 애플리케이션 | 애플리케이션 | URI, 메시지 | HTTP, SMTP, DNS |
| 6 프레젠테이션 | (애플리케이션에 포함) | — | TLS는 관행상 여기 또는 5계층 |
| 5 세션 | (애플리케이션에 포함) | — | — |
| 4 전송 | 전송 | 포트, 세그먼트 | TCP, UDP |
| 3 네트워크 | 인터넷 | IP 주소, 패킷 | IP, ICMP |
| 2 데이터링크 | 링크 | MAC 주소, 프레임 | 이더넷, WiFi(802.11) |
| 1 물리 | (링크에 포함) | 비트 | 전기·광·전파 신호 |

실무에서 통용되는 것은 TCP/IP 4계층 쪽이다. OSI의 5·6계층은 실제 구현에서 애플리케이션 계층에 흡수되어 별도 계층으로 존재하지 않는다. 그럼에도 OSI 모델의 번호를 알아 둘 값이 있다. 보안 제품과 문헌이 "L3 방화벽", "L4 로드밸런서", "L7 프록시"라는 표현을 쓰기 때문이다. 이 표현은 **그 장비가 어느 계층까지 패킷을 열어 보는가**를 뜻하며, 그것이 곧 그 장비가 무엇을 검사할 수 있고 무엇을 볼 수 없는지를 결정한다.

이 구분이 실무에서 갖는 의미를 하나만 미리 보자.

- **L4 로드밸런서**는 포트와 IP만 보고 트래픽을 나눈다. HTTP 메시지를 파싱하지 않으므로 요청 하나를 두 개로 오해할 여지가 없다.
- **L7 프록시**는 HTTP 메시지를 파싱해서 경로·헤더·쿠키를 보고 판단한다. 그래서 라우팅을 정교하게 할 수 있고, **동시에 파싱 불일치의 당사자가 된다.**

계층을 하나 더 올라가면 기능이 늘어나지만 공격 표면도 늘어난다. 13.12절에서 중간자별로 이 지점을 정리한다.

### TLS는 몇 계층인가

TLS의 계층 위치는 자주 논쟁이 된다. 실용적인 답은 **"TCP 위, HTTP 아래"** 이며, 그 이상 정확히 못 박을 필요가 없다. 중요한 것은 위치의 이름이 아니라 그 위치가 갖는 결과다.

HTTPS의 스택은 HTTP 스택에 계층 하나를 끼워 넣은 형태다.

```
        HTTP                    HTTP
         │                       │
         │                    TLS / SSL      ← 여기가 끼어든다
         │                       │
        TCP                     TCP
         │                       │
         IP                      IP
         │                       │
    네트워크 인터페이스      네트워크 인터페이스

      (a) HTTP               (b) HTTPS
```

*그림 1-1. HTTP와 HTTPS의 프로토콜 스택 (HTTP-DG 4장 기준)*

이 그림에서 읽어야 할 것은 세 가지다.

1. **HTTP는 바뀌지 않았다.** HTTPS는 새로운 애플리케이션 프로토콜이 아니라, 같은 HTTP를 암호화된 통로로 흘려보내는 것이다. `https://` URL에서 스킴과 기본 포트(443)가 달라질 뿐 메시지 문법은 동일하다.
2. **TLS는 TCP 위에 있다.** 따라서 TLS는 TCP가 이미 세운 커넥션 위에서 핸드셰이크를 한다. TCP 핸드셰이크 1왕복 **다음에** TLS 핸드셰이크가 온다. 이 누적이 18.2절에서 다룰 "추가 RTT"의 정체다.
3. **TLS는 IP 헤더와 TCP 헤더를 보호하지 않는다.** 암호화되는 것은 TCP가 실어 나르는 페이로드다. 출발지·목적지 IP, 포트 번호, 패킷 크기, 전송 시각은 그대로 노출된다. TLS를 켜도 관찰자가 "누가 어디와 얼마나 통신했는지"는 알 수 있다는 뜻이다. 이 사실은 19.9절에서 중간자 공격의 성립 조건을 다시 검토할 때 근거로 쓰인다.

> **용어 정리 — SSL과 TLS**
>
> SSL(Secure Sockets Layer)은 넷스케이프가 만든 원래 이름이고, TLS(Transport Layer Security)는 그것이 IETF 표준이 되면서 얻은 이름이다. 오늘날 실제로 쓰이는 것은 모두 TLS이지만 "SSL 인증서", "SSL 종료" 같은 관행적 표현이 남아 있다. 이 책은 프로토콜을 가리킬 때 TLS를 쓰고, 고유명사화된 표현(SSL 스트리핑 등)은 관행을 따른다.

## 1.3 캡슐화: 하나의 HTTP 요청이 프레임이 되기까지

계층 모델은 개념이고, **캡슐화(encapsulation)** 는 그 개념이 실제 바이트에서 구현되는 방식이다.

원리는 우편과 같다. 편지를 쓰고, 봉투에 넣고, 그 봉투를 상자에 담고, 상자에 운송장을 붙인다. 각 단계에서 내용물은 손대지 않고 **겉에 정보를 하나 더 붙인다.** 받는 쪽은 역순으로 벗긴다.

### 1.3.1 HTTP 메시지 → TCP 세그먼트 → IP 패킷 → 링크 프레임

Joe's Hardware Store에서 전동공구 가격표를 받아 오는 요청을 따라가 보자. 이 예제는 HTTP-DG가 책 전체에서 사용하는 것이고, 이 책도 프로토콜을 설명할 때 이어서 쓴다.

```
GET /power-tools.html HTTP/1.1
Host: www.joes-hardware.com
User-Agent: Mozilla/5.0
Accept: text/html

```

이 텍스트가 네트워크로 나가는 과정은 다음과 같다.

**1단계 — HTTP가 바이트 스트림을 넘긴다.** 애플리케이션은 위 텍스트를 열린 소켓에 순서대로 쓴다. 이 시점에서 HTTP가 하는 일은 끝이다. HTTP는 이 바이트가 어떻게 쪼개져 나갈지 알지 못하고 관여하지도 않는다.

**2단계 — TCP가 세그먼트로 쪼갠다.** TCP는 받은 스트림을 **세그먼트(segment)** 단위로 자르고, 각 세그먼트 앞에 보통 20바이트의 TCP 헤더를 붙인다. 헤더에는 출발지·목적지 포트 번호, 순서 번호(sequence number), 확인 응답 번호, 제어 플래그(SYN, ACK, FIN 등), 윈도우 크기, 체크섬이 들어간다.

여기서 중요한 것은 **자르는 위치가 HTTP의 구조와 아무 관계가 없다**는 점이다. TCP는 `Host:` 헤더 중간에서 세그먼트를 끊을 수 있고, 실제로 그렇게 한다. HTTP 요청 하나가 세 개의 세그먼트에 걸쳐 있을 수도 있고, 세 개의 HTTP 요청이 한 세그먼트에 들어 있을 수도 있다. 3.1.2절에서 이 성질을 다시 다룬다.

**3단계 — IP가 패킷에 담는다.** 각 TCP 세그먼트는 IP 헤더(보통 20바이트)를 붙여 **패킷(packet)** 또는 데이터그램이 된다. IP 헤더에는 출발지·목적지 IP 주소, 전체 길이, TTL(Time To Live), 상위 프로토콜 번호, 단편화 관련 필드가 들어간다.

**4단계 — 링크 계층이 프레임으로 만든다.** IP 패킷은 실제로 나가는 물리 매체에 맞는 **프레임(frame)** 에 담긴다. 이더넷이라면 출발지·목적지 MAC 주소가 붙고, WiFi라면 802.11 프레임이 된다. 그리고 전기 신호나 전파가 되어 나간다.

**표 1-2. 계층별 단위와 헤더 오버헤드**

| 계층 | 단위 이름 | 붙는 헤더 | 대표 주소 |
|---|---|---|---|
| 애플리케이션 | 메시지 | HTTP 헤더 (가변, 수백 바이트~) | URI |
| 전송 | 세그먼트 | TCP 헤더 20바이트(옵션 포함 최대 60) | 포트 번호 |
| 인터넷 | 패킷 / 데이터그램 | IP 헤더 20바이트(IPv4 기본) | IP 주소 |
| 링크 | 프레임 | 이더넷 헤더 14바이트 + 트레일러 4바이트 | MAC 주소 |

이 표에서 눈에 띄는 것은 오버헤드의 비율이다. TCP + IP 헤더만 40바이트다. 200바이트짜리 작은 요청을 보내면 실제 전송량의 20%가 헤더다. HTTP 헤더까지 세면 비율은 더 올라간다. 이것이 HTTP/2가 헤더 압축(HPACK)을 도입한 이유이고(→ 11.11), 작은 요청을 여러 번 보내는 것이 왜 비효율적인지의 절반이다. 나머지 절반은 지연이며 1.5절에서 다룬다.

### 1.3.2 MTU, 단편화, MSS

캡슐화에는 상한이 있다. 링크 계층이 한 번에 실어 나를 수 있는 최대 크기가 정해져 있기 때문이다. 이 값을 **MTU(Maximum Transmission Unit)** 라 한다.

이더넷의 MTU는 관행적으로 1500바이트다. 이 1500바이트 안에 IP 헤더와 TCP 헤더가 모두 들어가야 하므로, 실제로 데이터에 쓸 수 있는 공간은 다음과 같다.

```
1500 (이더넷 MTU)
 - 20 (IPv4 헤더)
 - 20 (TCP 헤더)
─────
1460 바이트  ← 이것이 일반적인 MSS
```

이 값을 **MSS(Maximum Segment Size)** 라 하고, TCP는 핸드셰이크 때 양쪽이 서로의 MSS를 알려 준다. 그래야 처음부터 넘치지 않는 크기로 자를 수 있다.

MTU보다 큰 IP 패킷을 보내야 하는 상황이 생기면 두 가지 길이 있다.

**단편화(fragmentation).** IP가 패킷을 쪼개서 보내고 받는 쪽에서 재조립한다. 그러나 조각 하나만 유실돼도 전체를 재전송해야 하고, 재조립 상태를 유지해야 하며, 재조립 과정 자체가 오랫동안 공격 대상이었다. 그래서 오늘날 IPv4에서는 대개 피하고, IPv6는 경로 중간 라우터의 단편화를 아예 금지한다.

**경로 MTU 탐색(Path MTU Discovery).** 보내는 쪽이 "단편화 금지" 플래그를 세운 패킷을 보내고, 너무 크면 라우터가 ICMP로 알려 주게 해서 적정 크기를 찾는다. 오늘날의 기본 동작이다.

여기에 실무에서 흔히 마주치는 함정이 있다. 경로 MTU 탐색은 **ICMP 메시지가 돌아올 수 있다는 전제**에서만 동작한다. 그런데 많은 조직이 방화벽에서 ICMP를 일괄 차단한다. 그러면 큰 패킷은 조용히 사라지고, 작은 패킷은 잘 가는 상태가 된다. 증상은 대개 이렇게 나타난다.

> TCP 핸드셰이크는 성공하고, 짧은 요청도 잘 되는데, 큰 파일을 올리거나 큰 응답을 받을 때만 커넥션이 멈춘다.

이 증상을 "애플리케이션 버그"로 오진하는 경우가 많다. 계층을 분리해 놓으면 편하지만, 문제가 났을 때는 계층을 거슬러 내려가 볼 수 있어야 한다는 예시다.

> **이 절이 뒷받침하는 것**
>
> - 캡슐화 구조와 헤더 오버헤드 → **11.11** (HPACK이 압축하는 대상)
> - MSS와 세그먼트 크기 → **18.7** (TLS 레코드 크기와 TCP 세그먼트의 관계), **19.4** (레코드 크기와 버퍼링 지연)
> - TCP가 HTTP 구조와 무관하게 자른다는 사실 → **3.1.2**, **10.4**

## 1.4 계층 경계는 신뢰 경계가 아니다

이제 1.1절에서 예고한 문장을 정면으로 다루자.

계층화는 **기능의 경계**를 만든다. 각 계층은 자기 일만 하고 나머지는 위아래에 맡긴다. 여기서 흔한 오해가 생긴다.

> "아래 계층이 처리해 주니까 위 계층은 신경 쓰지 않아도 된다."

기능에 관해서는 맞는 말이다. **보안에 관해서는 틀린 말이다.** 아래 계층이 제공하는 보장의 범위는 그 계층의 관심사에 한정되며, 그 밖의 것은 아무도 책임지지 않는다.

구체적으로 보자.

**표 1-3. 각 계층이 보장하는 것과 보장하지 않는 것**

| 계층 | 보장하는 것 | 보장하지 **않는** 것 |
|---|---|---|
| 링크(이더넷/WiFi) | 프레임 단위 오류 검출 | 발신자의 신원, 도청 방지, 같은 세그먼트 내 다른 호스트로부터의 격리 |
| IP | 최선 노력 전달 | 전달 자체, 순서, 출발지 주소의 진위 |
| TCP | 순서 보장, 재전송, 중복 제거, 무작위 오류 검출 | **메시지 경계**, 상대의 신원, 내용의 기밀성, 의도적 조작으로부터의 무결성 |
| TLS | 기밀성, 무결성, 서버 신원(인증서 검증을 실제로 할 경우) | 애플리케이션 계층의 논리, 인증서가 검증하는 "이름"이 곧 신뢰할 주체라는 것 |
| HTTP | 메시지 문법 | 내용의 진위, 클라이언트가 규칙을 지킬 것 |

이 표에서 이 책 전체에 걸쳐 되풀이될 세 개의 항목을 짚어 두자.

**1) TCP는 무결성을 보장하지 않는다.** TCP 체크섬은 16비트이고, 전송 중 발생하는 **무작위** 비트 오류를 잡기 위한 것이다. 공격자가 의도적으로 데이터를 바꾸면서 체크섬까지 맞추는 것은 아무 어려움이 없다. "TCP는 신뢰성 있으니 데이터가 변조되지 않았다"는 추론은 성립하지 않는다. 의도적 조작에 대한 무결성은 TLS가 담당한다.

**2) IP 출발지 주소는 발신자를 증명하지 않는다.** IP 헤더의 출발지 주소는 보내는 쪽이 적어 넣는 값이다. 위조할 수 있다. TCP의 경우 3-way handshake가 이를 실질적으로 어렵게 만들지만(응답을 받아야 커넥션이 성립하므로), UDP에는 그런 장치가 없다. 이것이 UDP 기반 반사·증폭 공격이 성립하는 이유다(→ 4.7).

**3) TCP는 메시지 경계를 알려주지 않는다.** 앞에서 두 번 언급했고, 이 책에서 가장 여러 번 인용될 항목이다. TCP가 전달하는 것은 바이트 스트림이며, 그 안에서 "요청 하나"를 세는 것은 전적으로 HTTP의 일이다. HTTP는 두 가지 방법으로 경계를 정한다. `Content-Length`가 알려주는 바이트 수만큼 읽거나, `Transfer-Encoding: chunked`의 청크 구조를 따라 읽는 것이다.

여기서 문제가 발생한다. 하나의 요청에 두 헤더가 모두 들어 있고 서로 다른 것을 지시할 때, 프록시는 한쪽을 따르고 서버는 다른 쪽을 따를 수 있다. 그러면 **프록시가 "요청 하나"라고 판단한 바이트 범위와 서버가 "요청 하나"라고 판단한 범위가 어긋난다.** 어긋난 나머지 부분은 서버 입장에서 다음 요청의 시작이 된다. 그 다음 요청은 다른 사용자의 것일 수 있다.

10.4절에서 이 구조를 자세히 다룬다. 지금 기억해야 할 것은 이 문제의 뿌리가 HTTP의 버그가 아니라 **계층 간 계약의 공백**이라는 점이다. TCP는 경계를 주지 않기로 했고, HTTP는 경계를 두 방법으로 정하기로 했고, 그 두 방법이 충돌할 때 무엇이 옳은지는 오랫동안 명확하지 않았다. 계층 사이에는 아무도 책임지지 않는 틈이 있다.

> 계층은 관심사를 분리하지만 신뢰를 분리하지 않는다.
> 각 계층은 자기 관심사 안에서만 보장하며, 그 보장을 넘어선 추론은 취약점이 된다.

41.9절에서 이 관점으로 책 전체를 다시 읽는다.

## 1.5 대역폭과 지연: 두 개의 독립적인 제약

네트워크 성능을 결정하는 값은 두 개다. 그리고 이 둘은 서로 독립적이다. 이 독립성을 이해하지 못하면 성능 판단과 보안 판단이 모두 어긋난다.

**지연(latency)**
: 메시지가 출발지에서 목적지에 도달하기까지 걸리는 시간.

**대역폭(bandwidth)**
: 통신 경로의 최대 처리량. 단위 시간에 밀어 넣을 수 있는 데이터의 양.

두 값의 관계를 파이프로 비유하면 이렇다. 대역폭은 파이프의 **굵기**이고, 지연은 파이프의 **길이**다. 파이프를 두 배로 굵게 만들어도 길이는 그대로다. 물이 반대편에 도달하는 시각은 굵기와 무관하다.

### 1.5.1 속도는 기능이다

성능을 부차적인 문제로 보는 관점은 실증적으로 반박됐다. 웹 성능 최적화(WPO)가 하나의 산업으로 성장한 배경에는 다음과 같은 반복 관찰이 있다.

- 빠른 사이트가 사용자 참여도를 높인다
- 빠른 사이트가 사용자 유지율을 높인다
- 빠른 사이트가 전환율을 높인다

지연이 얼마나 값비싼지를 보여주는 극단적 사례가 있다. 2011년 초, 런던과 뉴욕을 잇는 약 4,800km 길이의 새 해저 광케이블 공사가 시작됐다. 기존 대서양 횡단 링크보다 짧은 경로를 택해 **왕복 지연을 5밀리초 줄이는 것**이 유일한 목적이었다. 총 비용은 4억 달러를 넘겼다. 밀리초당 8천만 달러다. 고빈도 거래에서 몇 밀리초는 그만한 가치가 있었다.

여기서 이 책이 관심을 갖는 지점은 성능 자체가 아니라, **지연이 비싸기 때문에 사람들이 무엇을 포기하는가**다. TLS 핸드셰이크가 왕복을 추가하기 때문에 HTTPS 도입을 미루던 시기가 있었다. 검증 비용이 아까워서 인증서 검증을 건너뛰는 클라이언트 구현이 있었다. 왕복을 줄이려고 캐시를 더 공격적으로 쓰다가 민감한 응답을 공유 캐시에 남기는 설정이 있었다(→ 14.8). **성능 압력은 보안 결정을 왜곡하는 가장 흔한 힘이다.** 그 압력의 크기를 정량적으로 아는 것이 이 절의 목적이다.

### 1.5.2 지연의 구성 요소: 전파, 전송, 처리, 큐잉

"지연"은 하나의 값이 아니라 네 가지가 더해진 결과다. 인터넷상의 라우터 하나를 지날 때 발생하는 지연을 분해하면 다음과 같다.

**전파 지연(propagation delay)**
: 신호가 발신자에서 수신자까지 물리적으로 이동하는 데 걸리는 시간. **거리 ÷ 신호 전파 속도**로 결정된다. 대역폭과 무관하다.

**전송 지연(transmission delay)**
: 패킷의 모든 비트를 링크에 밀어 넣는 데 걸리는 시간. **패킷 길이 ÷ 링크 데이터 전송률**로 결정된다. 거리와 무관하다.

**처리 지연(processing delay)**
: 라우터가 패킷 헤더를 읽고, 오류를 검사하고, 목적지를 판단하는 데 걸리는 시간. 오늘날 대부분 하드웨어로 처리되어 매우 작지만 0은 아니다.

**큐잉 지연(queuing delay)**
: 라우터가 처리할 수 있는 속도보다 패킷이 빨리 도착할 때, 버퍼에서 기다리는 시간. **네 가지 중 가장 변동이 크다.**

전파 지연과 전송 지연이 각각 무엇에 의존하는지가 핵심이다. 10Mb 파일을 1Mbps 링크와 100Mbps 링크로 보낼 때, 링크에 다 밀어 넣는 데 걸리는 시간은 각각 10초와 0.1초다. 100배 차이다. 그러나 **첫 비트가 반대편에 도착하는 시각은 두 경우가 같다.** 그것은 거리가 결정한다.

큐잉 지연이 왜 골칫거리인지를 보여주는 사례가 **버퍼블로트(bufferbloat)** 다. 2010년 짐 게티스가 이름 붙인 문제로, 많은 라우터가 "패킷을 절대 버리지 말아야 한다"는 전제로 큰 입력 버퍼를 달고 출시된 데서 비롯됐다. 의도는 선했지만 결과는 나빴다. TCP의 혼잡 제어는 **패킷 손실을 혼잡의 신호로 읽는다**(→ 3.4). 버퍼가 크면 손실이 발생하지 않으므로 TCP는 혼잡을 감지하지 못하고 계속 밀어 넣는다. 그 결과 패킷은 버리지 않지만 지연이 폭증하고 변동이 커진다.

버퍼블로트는 이 장의 주제를 잘 보여준다. 링크 계층에서 "좋은 것"(패킷 손실 최소화)이 전송 계층의 메커니즘(혼잡 제어)을 무력화했다. 계층은 독립적으로 진화할 수 있지만, 각 계층의 가정을 깨뜨리면서 진화하면 전체가 나빠진다.

### 1.5.3 빛의 속도와 전파 지연, 그리고 라스트마일

전파 지연에는 물리학이 정한 하한이 있다.

진공에서 빛의 속도는 초당 299,792,458미터다. 그러나 패킷은 진공을 지나지 않는다. 구리선이나 광섬유를 지나며, 매질은 신호를 늦춘다. 빛의 속도와 매질 내 전파 속도의 비를 **굴절률(refractive index)** 이라 한다. 광섬유의 굴절률은 대체로 1.4~1.6이므로, 실무에서는 **광섬유 내 전파 속도를 초당 2억 미터**로 어림하면 된다.

**표 1-4. 주요 경로의 전파 지연 (HPBN 1장 기준)**

| 경로 | 거리 | 진공에서 | 광섬유에서 | 광섬유 왕복(RTT) |
|---|---|---|---|---|
| 뉴욕 → 샌프란시스코 | 4,148 km | 14 ms | 21 ms | **42 ms** |
| 뉴욕 → 런던 | 5,585 km | 19 ms | 28 ms | **56 ms** |
| 뉴욕 → 시드니 | 15,993 km | 53 ms | 80 ms | **160 ms** |
| 적도 일주 | 40,075 km | 133.7 ms | 200 ms | **200 ms** |

이 표의 수치는 **낙관적**이다. 두 지점 사이 최단 경로(대권 경로)로 광케이블이 깔려 있다고 가정한 값이기 때문이다. 실제로 그런 케이블은 없다. 패킷은 훨씬 돌아가는 경로를 타고, 경로상의 모든 홉에서 라우팅·처리·큐잉·전송 지연이 추가된다. 뉴욕과 시드니 사이 실제 RTT는 200~300밀리초 범위다.

이 수치를 사람의 지각과 맞춰 보면 다음과 같다.

- **100~200 ms** — 대부분의 사람이 "느리다"고 인지하기 시작하는 지점
- **300 ms 초과** — 상호작용이 "둔하다"고 보고되는 지점
- **1,000 ms** — 많은 사용자가 응답을 기다리며 이미 다른 생각으로 넘어가는 지점

즉 애플리케이션은 수백 밀리초 안에 응답해야 한다. 그런데 뉴욕–시드니 왕복 하나가 이미 200밀리초다. **왕복 횟수를 세는 것이 성능 설계의 기본 단위가 되는 이유**가 여기에 있다.

한국 기준으로 감을 잡아 두면 이후 장에서 유용하다.

**표 1-5. 서울 기준 대략적 RTT (실측 범위, 경로에 따라 변동)**

| 상대 위치 | 대략 RTT |
|---|---|
| 국내 (같은 ISP, 수도권) | 5~15 ms |
| 일본 도쿄 | 30~40 ms |
| 싱가포르 | 70~90 ms |
| 미국 서부 | 130~160 ms |
| 유럽 (프랑크푸르트) | 230~280 ms |
| 브라질 상파울루 | 300~350 ms |

### 라스트마일 지연

역설적이지만, 지연이 크게 붙는 지점은 대양이나 대륙을 건너는 구간이 아니라 **마지막 몇 킬로미터**인 경우가 많다. 이른바 라스트마일 문제다.

가정이나 사무실을 인터넷에 연결하려면 지역 ISP가 동네에 케이블을 깔고, 신호를 모으고, 지역 라우팅 노드로 전달해야 한다. 연결 방식과 배치에 따라 **ISP의 주 라우터에 닿기까지만 수십 밀리초**가 걸릴 수 있다.

미국 FCC의 2013년 "Measuring Broadband America" 보고서는 피크 시간대 평균 지연을 다음과 같이 보고했다.

| 접속 방식 | 피크 시간대 평균 지연 |
|---|---|
| 광가입자망(FTTH) | 18 ms |
| 케이블 | 26 ms |
| DSL | 44 ms |

이것은 목적지까지의 지연이 아니라, **ISP 코어망 내 가장 가까운 측정 노드까지의 지연**이다. 목적지로 라우팅되기 전에 이미 18~44밀리초가 쓰인 것이다.

자기 경로의 구조는 `traceroute`(윈도우에서는 `tracert`)로 직접 확인할 수 있다.

```
$ traceroute www.example.com
traceroute to www.example.com, 64 hops max, 52 byte packets
 1  192.168.0.1              1.2 ms   1.1 ms   1.3 ms     ← 집 안 공유기
 2  10.x.x.x                 8.9 ms   9.4 ms   8.7 ms     ← ISP 접속 노드
 3  x.x.x.x                 12.1 ms  11.8 ms  12.4 ms
 ...
```

`traceroute`의 동작 원리 자체가 1.3절의 캡슐화를 이용한다. IP 헤더의 TTL 값을 1, 2, 3으로 늘려 가며 패킷을 보내면, TTL이 0이 되는 지점의 라우터가 ICMP Time Exceeded 메시지를 돌려준다. 그 응답의 출발지 주소와 왕복 시간을 기록하면 경로와 홉별 지연이 나온다. 계층 하나 아래의 필드를 이용해 위 계층의 문제를 진단하는 좋은 예다.

### 1.5.4 코어망과 네트워크 엣지의 대역폭

대역폭 쪽 사정은 지연과 정반대다. 코어망은 남고, 엣지가 부족하다.

**코어망**은 광섬유로 연결된다. 광섬유의 강점은 **파장 분할 다중화(WDM)** 다. 하나의 섬유에 서로 다른 파장의 빛을 여러 개 실을 수 있으므로, 총 대역폭은 채널당 전송률 × 다중화된 채널 수가 된다. 2010년 무렵 연구 수준에서 400개 이상의 파장을 다중화해 채널당 최대 171Gbit/s, 단일 섬유 링크에서 70Tbit/s 이상의 총 대역폭이 확인됐다. 케이블 하나에는 보통 여러 가닥의 섬유가 들어가므로, 케이블당 용량은 수백 Tbit/s 급이다.

**네트워크 엣지**는 사정이 전혀 다르다. 사용자가 실제로 쓸 수 있는 대역폭은 클라이언트와 목적지 서버 사이 **가장 좁은 링크**가 결정한다. 그리고 그 링크는 거의 항상 사용자 쪽 마지막 구간이다.

Akamai가 자사 서버에서 관측한 2013년 1분기 평균 대역폭은 다음과 같다.

| 순위 | 국가 | 평균 Mbps |
|---|---|---|
| — | 전 세계 | 3.1 |
| 1 | 한국 | 14.2 |
| 2 | 일본 | 11.7 |
| 3 | 홍콩 | 10.9 |
| 9 | 미국 | 8.6 |

전 세계 평균이 3.1Mbps였다. 당시 HD 비디오 스트리밍이 해상도와 코덱에 따라 2~10Mbps를 요구했으므로, 평균적인 사용자는 낮은 해상도 스트림 하나로 링크 용량 대부분을 쓰는 상황이었다.

여기서 두 값의 비대칭이 드러난다. **대역폭은 돈으로 늘릴 수 있다.** 섬유를 더 넣고, 링크를 더 깔고, WDM 기술을 개선하면 된다. 실제로 2007~2011년 태평양 횡단 케이블 증설 용량의 절반 이상이 같은 섬유에 더 나은 다중화 기술을 적용한 결과였다.

**지연은 돈으로 늘릴 수 없다.** 광섬유 품질을 개선해 굴절률을 낮춰도, 현재 이미 광속의 약 1.5배 이내이므로 이 전략으로 기대할 수 있는 최대 개선은 30% 정도다. 그 이상은 물리학이 막는다. 남은 방법은 **거리를 줄이는 것**뿐이다. 그것이 CDN이 존재하는 이유다. 패킷을 더 빠르게 만들 수는 없으니, 서버를 사용자 쪽으로 옮기는 것이다.

이 비대칭이 만드는 실무적 결론은 하나다.

> 대역폭은 사면 되지만 왕복 횟수는 설계로만 줄일 수 있다.

이 결론이 프로토콜 설계에 어떻게 반영됐는지가 11장(HTTP 버전의 진화)과 19장(TLS 운영)의 주제다.

## 1.6 RTT가 모든 것의 단위인 이유

앞의 논의를 하나의 단위로 압축하자. **RTT(Round-Trip Time, 왕복 시간)** 다.

RTT가 특별한 단위인 이유는, 우리가 쓰는 프로토콜 대부분이 **상대의 응답을 확인한 뒤 다음 단계로 넘어가는 구조**이기 때문이다. 확인이 필요한 단계마다 최소 1왕복이 든다. 그래서 총 지연은 대체로 다음 형태가 된다.

```
총 지연 ≈ (필요한 왕복 횟수 × RTT) + 데이터 전송 시간
```

`https://` 요청 하나가 요구하는 왕복을 세어 보자.

**표 1-6. HTTPS 요청 하나의 왕복 예산 (HTTP/1.1, 최초 접속, TLS 1.2 가정)**

| 단계 | 왕복 | 비고 |
|---|---|---|
| DNS 조회 | 0~1+ | 캐시되어 있으면 0 (→ 2.4) |
| TCP 3-way handshake | 1 | 우회 불가 (→ 3.2) |
| TLS 핸드셰이크 | 2 | 전체 핸드셰이크 (→ 18.2) |
| HTTP 요청 → 응답 | 1 | |
| **합계** | **4~5+** | |

RTT가 50밀리초라면 250밀리초, RTT가 250밀리초(서울–유럽)라면 **1.25초**다. 아직 아무 데이터도 받지 않은 상태에서다.

이 계산이 이 책에서 반복적으로 쓰이는 이유는, **왕복을 줄이려는 압력이 프로토콜 설계와 보안 결정 대부분의 배후에 있기** 때문이다. 몇 가지만 미리 나열해 둔다.

| 왕복을 줄이려는 시도 | 다루는 곳 | 보안·운영 함의 |
|---|---|---|
| 커넥션을 재사용한다 (keep-alive) | 9.6 | 커넥션에 상태가 이월된다 (→ 9.10) |
| 커넥션을 여러 개 연다 (병렬·샤딩) | 9.4~9.5 | 오리진이 늘어나고 관리 대상이 늘어난다 |
| TLS 세션을 재개한다 | 19.1 | 세션 티켓의 관리가 새 문제가 된다 |
| TLS 종료 지점을 사용자 쪽으로 옮긴다 | 19.2 | 평문 구간이 생기고 중간자가 정당화된다 |
| 하나의 커넥션에 요청을 다중화한다 (HTTP/2) | 11.8 | 흐름 제어와 우선순위가 새 자원 소모 표면이 된다 |
| 서버를 사용자 쪽으로 옮긴다 (CDN) | 14장, 15장 | 캐시가 신뢰 경계가 되고 응답 혼동이 가능해진다 |
| 응답을 캐시한다 | 14.5~14.8 | 민감 응답이 공유 캐시에 남는다 |

이 표가 이 장에서 가장 실용적인 부분이다. **성능 최적화의 목록과 보안 취약점의 목록이 거의 일대일로 대응한다.** 우연이 아니다. 최적화는 대개 "중간에 무엇인가를 끼워 넣거나, 상태를 이월하거나, 검증을 생략하는" 형태로 왕복을 줄이며, 그 세 가지가 정확히 신뢰 경계를 흐리는 세 가지 방법이다.

## 1.7 마지막 구간의 특성: 유선, WiFi, 셀룰러

1.5.4절에서 사용자가 쓸 수 있는 대역폭은 가장 좁은 링크가 결정하며 그것은 거의 항상 마지막 구간이라고 했다. 그 마지막 구간의 성격을 조금 더 봐 두자.

이 절은 성능 공학을 다루려는 것이 아니다. 무선 구간의 특성은 두 가지 이유로 이 책에 필요하다. 첫째, **지연의 크기와 변동 폭이 유선과 질적으로 다르다.** 앞 절의 왕복 예산 계산이 무선에서는 다른 숫자가 된다. 둘째, **손실의 의미가 다르다.** 이것이 3.4절의 혼잡 제어 논의에 직접 영향을 준다.

### 1.7.1 무선 네트워크의 성능 기초: 대역폭, 신호 강도, 변조

무선 채널의 용량을 결정하는 것은 세 가지다.

**대역폭(주파수 폭).** 쓸 수 있는 주파수 구간의 폭이다. 넓으면 더 많이 보낼 수 있다. 그런데 주파수는 규제 자원이라 마음대로 넓힐 수 없다.

**신호 강도, 정확히는 신호 대 잡음비(SNR).** 수신 측이 신호와 잡음을 구별할 수 있는 정도다. 거리가 멀어지거나 장애물이 있거나 같은 주파수를 쓰는 다른 기기가 많으면 나빠진다.

**변조(modulation).** 하나의 심볼에 몇 비트를 실을지의 방식이다. 촘촘한 변조는 더 많이 실지만 SNR이 좋아야 한다.

이 세 값의 관계를 이론적 상한으로 표현한 것이 섀넌 용량 공식이다. 실무적으로 기억할 결론은 하나다. **무선 링크의 실제 속도는 고정값이 아니라 순간의 조건에 따라 변하는 값**이며, 기기는 조건이 나빠지면 더 견고한(느린) 변조로 자동 전환한다.

### 1.7.2 WiFi: 이더넷에서 무선 LAN으로, 그리고 손실의 성격 차이

WiFi(802.11)는 이더넷의 무선 사촌으로 설계됐고, 상위 계층에는 이더넷처럼 보이게 만들어졌다. 그러나 중요한 차이가 하나 있다.

이더넷은 스위치가 링크를 나눠 준다. WiFi는 **같은 주파수를 여러 기기가 공유**하고, 충돌을 피하기 위해 "보내기 전에 채널이 비었는지 듣는" 방식(CSMA/CA)을 쓴다. 그 결과 두 가지가 따라온다.

- **처리량이 접속 기기 수와 채널 혼잡도에 따라 크게 변한다.** 표시된 규격 속도는 상한이며 실측과 큰 차이가 난다.
- **패킷 손실이 혼잡 때문만이 아니라 무선 간섭 때문에도 발생한다.**

두 번째가 보안·프로토콜 관점에서 중요하다. TCP의 혼잡 제어는 **패킷 손실을 "네트워크가 붐빈다"는 신호로 해석**하도록 설계됐다(→ 3.4). 유선 네트워크에서 이 해석은 대체로 옳다. 무선에서는 틀릴 수 있다. 전자레인지가 돌아가서 프레임이 깨진 것을 TCP가 혼잡으로 읽고 전송률을 낮추면, 실제로는 한가한 링크에서 성능이 떨어진다.

이 불일치를 완화하기 위해 WiFi는 링크 계층에서 자체 재전송을 한다. 즉 **TCP가 손실을 보기 전에 링크 계층이 먼저 복구를 시도한다.** 덕분에 TCP의 오해는 줄지만, 대신 지연의 변동이 커진다. 계층 하나에서 문제를 감추면 다른 계층에서 다른 형태로 나타난다는, 이 장에서 세 번째로 등장하는 패턴이다.

### 1.7.3 셀룰러: RRC 상태 전이가 만드는 지연

셀룰러 네트워크에는 유선과 WiFi에 없는 지연 원인이 하나 더 있다. **라디오 자원 제어기(RRC, Radio Resource Controller)** 다.

배터리로 동작하는 기기가 무선 송수신기를 항상 켜 두면 배터리가 빨리 소모된다. 그래서 셀룰러 기기는 여러 개의 전력 상태를 오가며, 어느 상태에 있는지를 네트워크와 협상한다. 대략 다음과 같다.

| 상태 | 성격 | 데이터를 보내려면 |
|---|---|---|
| 활성(연결) | 송수신 가능, 전력 소모 큼 | 즉시 전송 |
| 유휴(대기) | 저전력, 무선 자원 미보유 | **상태 전이 필요** |

핵심은 유휴 상태에서 데이터를 보내려 할 때 **무선 자원을 다시 할당받는 과정 자체가 지연을 만든다**는 점이다. 세대와 사업자에 따라 다르지만 수십에서 수백 밀리초 규모다. 애플리케이션 입장에서는 다음 현상으로 나타난다.

> 같은 요청인데, 앱을 계속 쓰던 중에 보내면 빠르고 화면을 켜자마자 보내면 눈에 띄게 느리다.

여기서 나오는 실무 지침도 이 지연 구조에서 직접 도출된다. **작은 데이터를 자주 보내는 것이 큰 데이터를 한 번에 보내는 것보다 훨씬 비싸다.** 매번 무선 상태를 깨우기 때문이다. 그래서 셀룰러를 고려하는 애플리케이션은 전송을 모아서 한 번에 내보내고(burst) 곧바로 유휴로 돌아가도록 설계한다. 불필요한 주기적 keepalive를 없애라는 권고도 같은 이유다.

### 1.7.4 이 특성이 프로토콜 설계와 보안 판단에 미치는 영향

앞의 세 절을 이 책의 관심사로 번역하면 다음과 같다.

**1) 왕복 예산이 무선에서 훨씬 빡빡해진다.** 1.6절의 표에서 4~5왕복이 필요하다고 했다. 셀룰러에서 첫 요청은 여기에 상태 전이 지연까지 더해진다. 그래서 무선을 고려한 설계일수록 왕복을 줄이려는 압력이 세고, 1.6절 마지막 표에 있는 보안적 대가를 치를 유인이 커진다.

**2) 손실을 혼잡으로만 해석하면 안 되는 환경이 있다.** 3.4절에서 혼잡 제어를 다룰 때 이 전제를 다시 꺼낸다.

**3) 가용성 설계의 전제가 달라진다.** 클라이언트의 네트워크 인터페이스가 언제든 바뀌고(WiFi ↔ 셀룰러), 지연이 예고 없이 몇 배로 뛰는 환경에서는 타임아웃 값과 재시도 정책이 보안 문제가 된다. 너무 짧은 타임아웃은 정상 사용자를 실패시키고, 너무 관대한 재시도는 비멱등 요청을 중복 실행시킨다(→ 9.9). 45.3~45.4절에서 복원력 설계로 다시 다룬다.

**4) 무선 구간은 도청 조건이 다르다.** 유선 구간을 도청하려면 물리적 접근이 필요하다. 무선은 전파가 닿는 범위 안에 있으면 된다. 링크 계층 암호화(WPA2/WPA3 등)가 이를 완화하지만, 공개 WiFi나 잘못 구성된 네트워크에서는 그 완화가 없다. 1.8절에서 이 조건을 정리한다.

## 1.8 하위 계층 공격의 지형: 스니핑, 스푸핑, 중간자가 성립하는 조건

이 장의 마지막 절은 하위 계층 공격의 **조건**을 정리한다. 기법의 상세는 이 책의 범위가 아니다. 이 책이 필요한 것은 "어떤 조건이 갖춰지면 상위 계층의 어떤 가정이 무너지는가"다.

### 관찰(스니핑)

**성립 조건**: 공격자가 트래픽이 지나는 경로상의 한 지점에 접근할 수 있다.

구체적으로는 같은 무선 네트워크에 접속해 있거나, 같은 이더넷 세그먼트에 있거나, 경로상의 라우터·프록시를 통제하거나, 사용자가 공격자의 네트워크를 쓰도록 유도된 경우다.

**무너지는 가정**: "네트워크로 보낸 값은 상대만 본다."

이 가정에 기대는 것들이 이 책 곳곳에 있다. Basic 인증의 base-64 인코딩은 암호화가 아니므로 그대로 읽힌다(→ 21.3). URL 쿼리 문자열에 담긴 세션 토큰은 그대로 읽히고, 나아가 프록시 로그와 Referer 헤더에도 남는다(→ 23.3). 평문 HTTP 구간이 조금이라도 남아 있으면 쿠키는 그 구간에서 노출된다. `Secure` 속성이 존재하는 이유다(→ 20.6).

TLS는 이 조건 자체를 없애지는 못한다. 경로에 있는 자는 여전히 패킷을 볼 수 있다. TLS가 하는 일은 **볼 수 있어도 읽을 수 없게** 만드는 것이며, IP·포트·크기·타이밍은 여전히 노출된다(1.2절).

### 위조(스푸핑)

**성립 조건**: 프로토콜이 발신자를 검증하지 않는다.

IP 출발지 주소는 보내는 쪽이 적는 값이므로 위조할 수 있다. TCP는 3-way handshake 때문에 위조가 실질적으로 어렵다. 응답을 받아야 커넥션이 성립하므로, 위조한 주소로는 대화를 이어갈 수 없다. UDP에는 그런 장치가 없다.

**무너지는 가정**: "출발지 주소는 발신자를 가리킨다."

이 가정에 기대는 대표적 설계가 IP 기반 접근 제어와 IP 기반 사용자 식별이다(→ 20.2). 여기에 NAT까지 겹치면 문제가 더 커진다. 위조가 아니어도 **한 주소가 여러 사용자를 가리킬 수 있다**(→ 4.6). `X-Forwarded-For` 헤더는 이 문제를 해결하려는 시도지만, 그 헤더 자체가 클라이언트가 넣을 수 있는 값이라 새로운 위조 지점이 된다(→ 8.6).

### 개입(중간자)

**성립 조건**: 관찰 조건 + 트래픽을 변경하거나 자신을 목적지로 위장할 수 있다.

관찰만 하는 것과 개입하는 것 사이에는 큰 차이가 있다. 개입에는 트래픽 경로를 자신에게 끌어오는 수단이 추가로 필요하다. ARP 스푸핑, 악성 무선 AP, DNS 응답 조작, 라우팅 조작 등이 그런 수단이다. 그중 **DNS 응답 조작**은 이 책이 직접 다루는 항목이며, 2장에서 이름 해석의 신뢰 문제로 다시 등장한다(→ 2.7).

**무너지는 가정**: "내가 통신하는 상대는 내가 의도한 상대다."

이 가정을 회복하는 것이 TLS 서버 인증서의 목적이다. 그러나 회복은 조건부다. **클라이언트가 인증서를 실제로 검증해야** 하고, 검증에 쓰는 신뢰 저장소가 오염되지 않아야 하고, 사용자가 경고를 무시하고 넘어가지 않아야 한다. 이 세 조건 중 하나라도 깨지면 TLS는 켜져 있으면서 보호하지 않는다. 18.3~18.4절에서 검증의 실제 동작과 실패 유형을 다루고, 19.9절에서 이 조건을 다시 정리한다.

또 하나 짚어 둘 것이 있다. **중간자는 항상 공격자인 것이 아니다.** 기업 네트워크의 TLS 검사 장비, CDN의 TLS 종료, 개발자가 쓰는 인터셉팅 프록시는 모두 의도된 중간자다. 이들은 사용자 기기에 자기 루트 인증서를 설치해 정당한 중간자가 된다. 즉 **"의도된 중간자"와 "공격자"는 기술적으로 같은 위치에 있고, 차이는 신뢰 저장소에 무엇이 들어 있는지뿐이다.** 19.8절에서 이 구조를 다룬다.

### 정리: 세 조건과 무너지는 가정

| 공격 | 성립 조건 | 무너지는 상위 계층 가정 | 완화 수단 | 이 책에서 |
|---|---|---|---|---|
| 관찰 | 경로상 한 지점 접근 | 보낸 값은 상대만 본다 | TLS (내용에 한해) | 21.3, 23.3, 19.10 |
| 위조 | 발신자 미검증 프로토콜 | 출발지 주소 = 발신자 | TCP 핸드셰이크, 애플리케이션 인증 | 4.7, 8.6, 20.2 |

## 이 장의 요약

- **계층화**는 각 계층이 독립적으로 진화하게 해 주었고, 그 대가로 실패의 양상, 비용, 계층 간 의미의 불일치를 감췄다.
- **캡슐화**는 HTTP 메시지를 세그먼트 → 패킷 → 프레임으로 감싸며, 이 과정에서 자르는 위치는 HTTP의 구조와 무관하다. 이 사실이 10.4절의 본문 경계 문제의 뿌리다.
- **계층 경계는 신뢰 경계가 아니다.** TCP는 메시지 경계도 의도적 조작에 대한 무결성도 보장하지 않으며, IP 출발지 주소는 발신자를 증명하지 않는다. 각 계층의 보장을 넘어선 추론이 취약점이 된다.
- **지연과 대역폭은 독립적이다.** 대역폭은 돈으로 늘릴 수 있지만 지연은 물리학이 하한을 정한다. 남은 방법은 거리를 줄이거나 왕복 횟수를 줄이는 것뿐이다.
- **RTT는 이 책 전체의 단위다.** HTTPS 요청 하나가 4~5왕복을 요구하며, 그 왕복을 줄이려는 압력이 프로토콜 설계와 보안 결정 대부분의 배후에 있다. 성능 최적화 목록과 취약점 목록이 거의 일대일로 대응하는 것은 우연이 아니다.
- **무선 구간**은 지연의 크기와 변동이 유선과 질적으로 다르고, 손실이 혼잡을 의미하지 않을 수 있다.
- **하위 계층 공격은 세 가지 조건**으로 정리된다. 관찰은 경로 접근, 위조는 발신자 미검증, 개입은 관찰과 경로 탈취를 함께 요구한다. 각각이 무너뜨리는 상위 계층 가정을 표 1-7에 정리했다.

## 이어지는 장

2장은 이 장에서 "목적지 IP 주소는 이미 알고 있다"고 가정했던 부분을 채운다. 그 주소는 이름에서 나오며, 이름을 주소로 바꾸는 과정 자체가 지연의 일부이고 신뢰의 문제다.

3장은 이 장에서 "TCP는 순서를 보장한다"로 요약한 부분을 펼친다. 어떻게 보장하는지, 그 대가가 얼마인지, 그리고 보장하지 않는 것이 무엇인지.
