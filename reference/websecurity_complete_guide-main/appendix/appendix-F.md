# 부록 F. URI 스킴 · MIME 타입 · 문자셋 · 언어 태그 레퍼런스

7장은 URL을 **식별의 문법**으로 다뤘고, 10장은 엔티티를 **본문의 경계와 무결성** 문제로 다뤘다. 두 장이 공통으로 기대는 것이 네 개의 레지스트리다. 스킴은 URL의 첫 토큰이 어떤 해석기를 부르는지를 결정하고, MIME 타입은 바이트 열이 어떤 렌더러에 넘어갈지를 결정하며, 문자셋은 그 바이트가 어떤 문자로 읽힐지를 결정하고, 언어 태그는 같은 리소스의 어느 변형이 선택될지를 결정한다.

**네 레지스트리 모두 같은 구조의 위험을 갖는다.** 값이 하나의 이름을 갖는 것이 아니라 **별칭·확장·미등록 토큰을 허용**하고, 그래서 경로 위의 두 파서가 같은 문자열을 다르게 읽을 수 있다. 스킴에서는 `javascript:`가 URL로도 코드로도 읽히고, MIME 타입에서는 `text/plain`이 스니핑에 의해 `text/html`이 되며, 문자셋에서는 하나의 인코딩이 열 개가 넘는 별칭을 갖고, 언어 태그에서는 `x-` 접두사가 무엇이든 될 수 있다. 이 부록은 각 레지스트리의 내용을 조회표로 제공하되, **각 항목이 어느 신뢰 경계에 닿는지**를 함께 적는다.

각 절은 원서의 표를 그대로 옮기지 않는다. HTTP-DG 부록 A·D·G·H는 합쳐서 100페이지가 넘는 나열이며, 그중 상당수는 2002년 당시에도 사장된 항목이었다. 이 부록은 **선별 기준을 절마다 명시하고 그 기준으로 고른 것만** 담는다.

## F.1 URI 스킴

### 스킴이 결정하는 것

URL의 첫 토큰인 스킴은 **어떤 프로토콜로 말할지**를 정하는 값으로 흔히 설명되지만, 브라우저 안에서 그것은 더 강한 의미를 갖는다. **스킴은 그 URL을 누가 해석할지를 정한다.** `http:`는 네트워크 스택을 부르고, `file:`은 로컬 파일 시스템을 부르며, `javascript:`는 스크립트 엔진을 부르고, `data:`는 아무도 부르지 않고 URL 자체를 콘텐츠로 승격시킨다.

7.2절이 세운 문법과 7.5절이 다룬 "스킴의 바다"가 이 절의 근거다. 여기서는 **W3C·IANA 레지스트리에 올라간 스킴을 목록으로** 제공하되, 각 스킴이 브라우저나 서버에서 어떤 결정을 유발하는지를 함께 적는다.

원서는 약 90개를 나열하며 그중 다수가 사장됐거나 널리 쓰이지 않는다고 스스로 밝힌다. 이 부록은 세 기준으로 나눈다. **(1) 보안 판단이 필요한 스킴**, **(2) 실제로 널리 쓰이는 스킴**, **(3) 나머지**. 앞의 둘은 주석을 달아 표로, 나머지는 이름과 한 줄 설명만 묶어 싣는다.

### 보안 판단이 필요한 스킴

**표 F-1. 위험한 스킴 — 왜 위험한가 (스킴 설명은 HTTP-DG 부록 A 표 A-1 기준, 보안 주석은 이 책의 정리)**

| 스킴 | 원래의 용도 | 무엇이 위험한가 | 본문 참조 |
|---|---|---|---|
| `javascript` | 콜론 뒤의 식을 평가하고, 그 값의 문자열을 담은 페이지를 로드한다. Netscape가 도입했다 | **URL이 곧 코드다.** 링크의 `href`, 프레임의 `src`, 리다이렉션의 `Location`, `window.open`의 인자 — URL을 받는 모든 자리가 스크립트 실행 지점이 된다. 실행 출처는 **그 URL을 여는 문서의 출처**이므로 동일 출처 정책을 우회하지 않고도 그 문서의 권한을 그대로 얻는다 | **7.5**, **32.4**, **35.3** |
| `data` | 작은 상수 데이터를 URL 안에 직접 담는다. `data:A%20brief%20note` | **콘텐츠에 호스트가 없다.** 출처 판정의 재료인 스킴·호스트·포트 중 둘이 존재하지 않으므로, 이 URL로 만들어진 문서의 출처를 무엇으로 볼지가 구현마다 갈린다. 필터가 호스트명을 검사하는 방식으로 짜여 있으면 통째로 무력해진다 | **7.5**, **34.1**, **32.4** |
| `file` | 특정 호스트 컴퓨터의 파일을 가리킨다. 호스트명을 넣을 수는 있으나 **어떤 인터넷 프로토콜도, 접근 방법도 명시하지 않는다** | 원서 자신이 "호스트 간 네트워크 프로토콜에서의 유용성은 제한적"이라고 적은 스킴이다. 브라우저에서 이것은 **로컬 파일 시스템으로 가는 문**이며, 서버 측에서 이 스킴을 받아들이는 코드는 곧 경로 순회·파일 인클루전·SSRF의 표면이 된다 | **7.5**, **28.3**, **28.8** |
| `view-source` | Netscape Navigator의 소스 보기. JavaScript로 생성된 HTML을 표시한다 | 같은 리소스를 **다른 해석기로** 여는 두 번째 경로다. 접근 제어나 필터가 `http:` 경로만 가정하고 있으면 이 경로가 그 가정을 벗어난다 | **7.5**, **24.5** |
| `about` | 브라우저 내부 상태를 노출한다. `about:cache`는 디스크 캐시 통계를, `about:plugins`는 설정된 플러그인 정보를 보여 준다 | **브라우저 자신이 리소스가 된다.** 캐시 통계와 플러그인 목록은 그 자체로 지문이자 프라이버시 노출이다 | **36.1**, **36.5** |
| `res` | 모듈에서 리소스를 가져오는 Microsoft 스킴. 문자열·수치 리소스 타입과 ID로 구성된다 | 로컬 바이너리의 내용을 URL로 주소 지정한다. 존재 여부의 차이가 **설치된 소프트웨어의 열거 채널**이 된다 | **36.5** |
| `clsid` | Microsoft OLE/COM 클래스를 참조한다. 페이지에 액티브 객체를 삽입할 때 쓴다 | 페이지가 **네이티브 컴포넌트를 지목**한다. ActiveX 컨트롤 공격의 진입 문법이다 | **36.4** |
| `java`, `livescript`, `mocha` | 각각 Java 클래스 식별, JavaScript의 옛 이름, JavaScript의 옛 이름 | **같은 실행 능력에 다른 이름이 붙어 있다.** 스킴 차단 목록이 `javascript`만 막고 이 별칭들을 놓치면 우회가 성립한다. 목록 방식 방어의 전형적 실패 지점 | **7.5**, **32.5** |
| `telnet` | Telnet 프로토콜로 접근하는 대화형 서비스. `telnet://<user>:<password>@<host>:<port>/` 형태 | **URL 안에 비밀번호가 들어간다.** 문법이 자격증명 노출을 정식으로 허용하는 사례이며, 이 형태는 `http:` URL의 사용자정보 필드에서도 그대로 재현된다 | **7.2**, **22.3** |
| `mailto` | 개인이나 서비스의 인터넷 메일 주소를 지정한다 | 메일 헤더가 URL 파라미터로 표현되므로, 검증 없이 조립하면 **이메일 헤더 인젝션**의 통로가 된다 | **28.9** |
| `shttp` | S-HTTP. HTTP 커넥션을 보호하기 위한 HTTP의 상위 집합. 널리 배포되지 못했고 대부분 HTTPS로 대체됐다 | 보안 스킴이 **하나가 아니었다**는 역사적 증거다. 스킴 이름만으로 보안 수준을 판단할 수 없다는 원칙의 근거 | **18.1** |
| `opaquelocktoken`, `dav` | WebDAV가 IANA에 예약한 두 네임스페이스. 잠금 토큰과 명세 자체를 가리킨다 | WebDAV가 활성화된 서버는 **메서드 표면이 넓어진다**. 이 스킴이 보이면 그 서버의 메서드 집합을 다시 조사할 이유가 된다 | **8.3.3**, **12.7**, **15.11** |

> **`javascript:`와 `data:`를 하나의 규칙으로 묶는 법**
>
> 두 스킴의 공통점은 **네트워크로 나가지 않는다**는 것이다. 요청이 발생하지 않으므로 프록시·WAF·서버 로그 어디에도 흔적이 남지 않고, 방어는 오직 브라우저 안에서만 가능하다. 그래서 URL을 받는 모든 코드는 **차단 목록이 아니라 허용 목록으로** 스킴을 판정해야 한다. `http`와 `https`만 통과시키는 규칙 하나가 위 표의 절반을 무력화한다(→ **35.3**, **35.6**).

### 나머지 스킴

원서 표 A-1의 나머지 항목이다. 대부분 특정 벤더의 제품이나 만료된 인터넷 초안에 묶여 있으며, **오늘날 이 이름을 만난다면 그것은 대개 레거시 시스템의 흔적**이다. 정찰 관점에서는 이 흔적 자체가 정보다(→ **25.6**).

- **회의·통신**: `callto`(Microsoft NetMeeting 세션 개시), `h323`·`h324`·`lrq`·`t120`(멀티미디어 회의), `sdp`(세션 기술 프로토콜), `rvp`(사용자 도착 알림), `gsm-sms`(GSM 단문 메시지), `telephone`·`phone`(`tel`의 옛 초안)
- **스트리밍**: `pnm`(Real Networks 스트리밍), `mms`·`mmst`·`mmsu`(Microsoft Media Server. `mmsu`는 UDP, `mmst`는 TCP 강제), `chttp`(Real Networks의 캐싱 프로토콜 — `http://` 대신 `chttp://`를 써서 RealPlayer에 캐시 대상을 지정한다)
- **파일·디렉터리**: `afp`(Apple Filing Protocol), `afs`(Andrew File System 예약), `rwhois`(RWhois 디렉터리 접근), `finger`(`finger://host[:port][/<request>]`), `freenet`, `lifn`(위치 독립 파일 이름)
- **식별자·이름**: `uuid`(128비트 전역 고유 ID. 위치 정보를 담지 않고 DNS 이름 같은 물리적 루트 네임스페이스에 묶이지 않는다), `hdl`(Handle System의 지속 식별자), `isbn`, `path`, `lid`(로컬 식별자), `md5`(암호학적 체크섬), `STANF`(안정적 네트워크 파일명 옛 제안)
- **객체·미들웨어**: `iioploc`·`IOR`(CORBA 확장과 상호운용 객체 참조), `ilu`(다국어 객체 인터페이스 시스템), `jdbc`(Java SQL API), `rx`(웹 페이지 안에서 원격 그래픽 애플리케이션을 표시하는 구조)
- **기타**: `acap`(RFC 2244), `date`(`date:1999-03-04T20:42:08` 형태의 제안), `dns`(REBOL 소프트웨어), `eid`(외부 ID — URL 아닌 수단으로 얻은 데이터를 로컬 애플리케이션이 참조하게 하는 일반 탈출 장치. 논란이 있다), `hnews`(NNTP의 HTTP 터널링 변형), `irc`, `mailserver`(메시지 전체를 URL에 인코딩하려던 1994~1995년 제안), `printer`, `snews`(SSL 암호화 뉴스), `tip`(TIP 원자적 인터넷 트랜잭션), `tn3270`, `vemmi`(다목적 멀티미디어 인터페이스), `videotex`, `whodp`(다수의 이동 객체의 위치·상태를 통신), `z39.50r`·`z39.50s`(세션 지향 정보 검색)

> **이 절이 뒷받침하는 것**
>
> - 스킴이 URL의 해석기를 결정한다는 것 → **7.5** (스킴의 바다), **7.2** (URL 문법)
> - `javascript:`·`data:`가 네트워크를 거치지 않는다는 것 → **32.4** (XSS 전달 메커니즘), **35.3** (오픈 리다이렉션)
> - 스킴 판정은 차단 목록이 아니라 허용 목록이어야 한다는 것 → **35.6** (출력 위치별 검증, 화이트리스트), **43.6** (입력 처리 방식의 비교)
> - `file:`·`ftp:`를 서버 측 코드가 받아들일 때 → **28.8** (백엔드 HTTP 요청 인젝션과 SSRF)

## F.2 MIME 타입 구조와 IANA 등록

### 문법

MIME 미디어 타입은 **타입(type)**, **서브타입(subtype)**, 그리고 **선택적 파라미터 목록**으로 이루어진다. 타입과 서브타입은 슬래시로 나뉘고, 파라미터가 있으면 세미콜론으로 시작한다. HTTP에서 이 값은 `Content-Type`과 `Accept` 헤더에 쓰인다.

```
Content-Type: video/quicktime
Content-Type: text/html; charset="iso-8859-6"
Content-Type: multipart/mixed; boundary=gc0p4Jq0M2Yt08j34c0p
Accept: image/gif
```

*예제 F-1. MIME 타입이 쓰이는 자리 (HTTP-DG 부록 D)*

RFC 2046의 문법은 다음과 같다.

```
TYPE    := "application" | "audio" | "image" | "message" | "multipart" |
           "text" | "video" | IETF-TOKEN | X-TOKEN
SUBTYPE := IANA-SUBTOKEN | IETF-TOKEN | X-TOKEN

IETF-TOKEN    := <RFC를 동반하고 IANA에 등록된 확장 토큰>
IANA-SUBTOKEN := <IANA에 등록된 확장 토큰>
X-TOKEN       := <"X-" 또는 "x-" 접두사 뒤에 임의의 토큰>

PARAMETER := TOKEN "=" VALUE
VALUE     := TOKEN / QUOTED-STRING
TOKEN     := 1*<SPACE, CTL, TSPECIALS를 제외한 US-ASCII 문자>
TSPECIALS := "(" | ")" | "<" | ">" | "@" |
             "," | ";" | ":" | "\" | <"> |
             "/" | "[" | "]" | "?" | "="
```

*예제 F-2. MIME 타입 문법 (RFC 2046, HTTP-DG 부록 D 인용)*

**`TSPECIALS` 목록을 눈여겨봐야 한다.** 이 문자들은 타입·서브타입 이름에 금지되지만 **파라미터 값에는 따옴표로 묶여 들어올 수 있다.** `boundary`와 `charset` 값이 그 자리이며, 헤더를 조립하는 코드가 이 값을 검증하지 않으면 세미콜론과 따옴표로 헤더 구조 자체를 조작할 여지가 생긴다(→ **8.7**, **35.1**).

### 이산 타입, 복합 타입, 멀티파트

MIME 타입은 객체의 타입을 직접 기술하거나, 다른 객체들의 모음을 기술한다.

- **이산 타입(discrete type)** — 객체 타입을 직접 기술한다. 텍스트 파일, 비디오, 애플리케이션 고유 형식이 여기 속한다.
- **복합 타입(composite type)** — 다른 콘텐츠의 모음이나 캡슐화를 기술한다. **바깥 포장의 형식**을 말하며, 포장을 열면 안의 객체가 각각 자기 타입을 갖는다.
- **멀티파트 타입(multipart type)** — 복합 타입의 한 갈래로, 여러 구성 타입으로 이루어진다.

**이 구조가 파싱 불일치의 온상이다.** 복합 타입은 정의상 **한 번 더 파싱해야 하는 것**이고, 그 두 번째 파싱을 누가 하느냐가 구현마다 다르다. `multipart/mixed`의 각 파트가 자기 `Content-Type`을 갖는다는 사실은, **바깥 타입만 보고 통과시킨 필터가 안쪽 타입을 검사하지 못한다**는 뜻이다. 파일 업로드가 `multipart/form-data`로 이뤄진다는 사실과 함께 읽어야 한다(→ **10.7**, **12.4.3**).

**표 F-3. 주요 1차 타입 (HTTP-DG 부록 D 표 D-1)**

| 타입 | 설명 |
|---|---|
| `application` | 애플리케이션 고유 콘텐츠 형식 (이산 타입) |
| `audio` | 오디오 형식 (이산 타입) |
| `chemical` | 화학 데이터 집합 (이산 IETF 확장 타입) |
| `image` | 이미지 형식 (이산 타입) |
| `message` | 메시지 형식 (복합 타입) |
| `model` | 3차원 모델 형식 (이산 IETF 확장 타입) |
| `multipart` | 여러 객체의 모음 (복합 타입) |
| `text` | 텍스트 형식 (이산 타입) |
| `video` | 비디오 동영상 형식 (이산 타입) |

서브타입은 1차 타입일 수도 있고(`text/text`), IANA 등록 서브타입일 수도 있으며, `x-`로 시작하는 실험적 확장 토큰일 수도 있다.

### 등록 트리

MIME 타입 토큰은 **등록 트리(registration tree)** 라 불리는 네 부류로 나뉘며, 각 부류마다 등록 규칙이 다르다.

**표 F-4. 네 개의 MIME 미디어 타입 등록 트리 (HTTP-DG 부록 D 표 D-2)**

| 등록 트리 | 예 | 설명 | 보안·운영 주석 |
|---|---|---|---|
| IETF | `text/html` | 인터넷 커뮤니티 전반에 의미가 있는 타입. IESG 승인과 표준화 트랙 RFC가 필요하다. 토큰에 마침표가 없다 | 이 트리의 타입만이 **명세로 동작이 고정된다.** 나머지는 렌더러마다 다르게 처리될 수 있다 |
| 벤더 (`vnd.`) | `image/vnd.fpx` (Kodak FlashPix) | 상용 제품이 쓰는 미디어 타입. 공개 검토는 권장되나 필수가 아니다 | 이 접두사가 응답에 보이면 **어떤 상용 제품이 뒤에 있는지**가 드러난다. 핑거프린팅 재료 |
| 개인 (`prs.`) | `image/prs.btif` | 사적·개인·자기 이름 타입. 상업적으로 배포되지 않는다 | 형식 명세 또는 그 포인터를 제공해야 한다 |
| 실험 (`x-`, `x.`) | `application/x-tar` | 미등록·실험 타입. 벤더·개인 타입 등록이 비교적 간단하므로 **`x-` 타입으로 소프트웨어를 널리 배포해서는 안 된다** | **등록되지 않았다는 것은 동작이 정의되지 않았다는 뜻이다.** 클라이언트마다 다르게 처리되고, 그 차이가 곧 타입 혼동의 틈이다(→ **10.7**) |

### 등록 절차

RFC 2048이 정한 절차는 형식적 표준화 과정이 아니라 **행정 절차**다. 새 타입을 커뮤니티와 함께 점검하고 레지스트리에 기록하는 것이 목적이며, 지연을 최소화하도록 설계됐다.

1. **커뮤니티 검토에 제출한다.** 제안된 미디어 타입 등록을 `ietf-types@iana.org` 메일링 리스트에 보내 2주간 검토를 받는다. 공개 게시의 목적은 **이름 선택, 상호운용성, 그리고 보안 함의**에 대한 피드백을 얻는 것이다. 등록이 끝날 때까지는 RFC 2045의 `x-` 접두사를 쓸 수 있다.
2. **IESG 승인** — IETF 트리에 한한다. 표준화 트랙 RFC를 동반해야 한다.
3. **IANA 등록** — 승인 요건을 충족하면 등록 요청을 이메일 템플릿으로 제출한다.

벤더·개인 타입은 다음 네 조건만 충족하면 공식 검토 없이 자동 등록된다.

1. 미디어 타입은 **실제 미디어 형식으로 기능해야 한다.** 전송 인코딩이나 문자셋처럼 동작하는 타입은 미디어 타입으로 등록될 수 없다.
2. 적절한 타입·서브타입 이름을 가져야 한다. 모든 타입 이름은 표준화 트랙 RFC에 정의되어야 하고, 서브타입 이름은 유일해야 하며 문법에 맞고 올바른 트리 접두사를 포함해야 한다.
3. 개인 트리 타입은 형식 명세나 그 포인터를 제공해야 한다.
4. **제시된 보안 고려사항이 명백히 엉터리여서는 안 된다.** 인터넷 소프트웨어를 개발하는 모두가 보안 구멍을 막는 데 각자의 몫을 해야 한다.

네 번째 조건이 등록 템플릿의 `Security considerations:` 필드와 짝을 이룬다. 템플릿은 다음 항목을 요구한다 — 타입·서브타입 이름, 필수·선택 파라미터, **인코딩 고려사항**, **보안 고려사항**, 상호운용성 고려사항, 발행된 명세, 이 타입을 쓰는 애플리케이션, 부가 정보(매직 넘버, 파일 확장자, Macintosh 파일 타입 코드), 연락처, 의도된 용도(`COMMON`·`LIMITED USE`·`OBSOLETE` 중 하나), 저자·변경 관리자.

> 원서는 이 양식의 느슨한 구조 때문에 **사람이 읽기에는 괜찮지만 기계 처리는 어렵다**고 지적하며, 그것이 잘 정리된 MIME 타입 요약을 찾기 어려운 이유이자 자신들이 표를 만든 이유라고 밝힌다. 등록자마다 템플릿을 조금씩 다르게 채우므로 정보의 품질과 형식이 제출본마다 다르다.

## F.3 MIME 타입 표

### 선별 기준

원서 부록 D의 열 개 표는 수백 개의 MIME 타입을 담고 있으며, 원서 스스로 "아마 지금까지 편찬된 가장 상세한 MIME 타입 표 목록"이라고 적었다. 이 부록은 그것을 옮기지 않는다. **세 기준 중 하나 이상에 해당하는 타입만** 싣는다.

1. **웹에서 실제로 쓰인다** — 브라우저가 이 타입의 응답을 일상적으로 받고, 그에 따라 렌더링 경로가 갈린다.
2. **MIME 스니핑·타입 혼동에서 문제가 된다** — 선언된 타입과 실제 처리가 어긋날 수 있고, 그 어긋남이 실행 가능한 결과를 낳는다(→ **10.7**).
3. **HTTP 프로토콜 자체가 요구한다** — 청크·범위·멀티파트처럼 HTTP 메시지 구조와 직접 얽힌다.

이 기준을 벗어난 것 — `chemical/*` 전체, `model/*` 전체, 벤더 고유 오디오·비디오 형식 대부분, 사장된 그룹웨어 형식들 — 은 싣지 않는다. 필요하면 IANA 레지스트리를 직접 보는 것이 맞고, 그것이 원서 표가 애초에 대신하려던 일이다.

### 실행과 렌더링을 부르는 타입

**표 F-5. 브라우저가 능동적으로 처리하는 타입 (타입·설명·확장자는 HTTP-DG 부록 D 표 D-3·D-10 기준, 보안 주석은 이 책의 정리)**

| MIME 타입 | 설명 | 확장자 | 보안 주석 |
|---|---|---|---|
| `text/html` | HTML 파일 (RFC 2854) | `html`, `htm` | **스크립트 실행의 기본 경로.** 사용자 콘텐츠를 이 타입으로 서빙하는 순간 저장형 XSS가 성립한다. 업로드된 파일을 이 타입으로 되돌려 주지 않는 것이 파일 업로드 방어의 첫 줄이다(→ **32.6**) |
| `text/plain` | 순수 텍스트 | `asc`, `txt` | **가장 흔한 스니핑 대상.** 선언은 평문이지만 내용에 `<html>`이나 `<script>`가 보이면 HTML로 처리하는 구현이 있었다. "안전한 타입으로 내려보냈으니 괜찮다"는 가정이 여기서 깨진다(→ **10.7**) |
| `application/x-javascript` | JavaScript 파일 | `js` | 실험 트리(`x-`) 타입이 사실상 표준처럼 쓰인 사례다. **스크립트로 해석되는 응답은 동일 출처 정책의 보호를 받지 않는다** — `<script src>`로 크로스 도메인 로드가 되고, 이것이 JavaScript 하이재킹의 전제다(→ **34.4**) |
| `text/css` | 캐스케이딩 스타일 시트 (RFC 2318) | `css` | 스크립트가 아니지만 **크로스 도메인으로 로드되고 부분적으로 내용이 관찰된다.** CSS 인젝션을 통한 데이터 캡처의 기반(→ **34.3**) |
| `application/xml` | XML 형식 파일 (RFC 2376). 브라우저 등이 평문으로 취급하게 하려면 `text/xml`을 쓴다 | `xml`, `dtd` | XML 파서가 붙는다는 뜻이다. **외부 엔티티 해석이 켜져 있으면 XXE**가 된다(→ **28.5**, **28.6**) |
| `text/xml` | XML 형식 파일 (RFC 2376). 브라우저가 내려받아 저장하게 하려면 `application/xml`을 쓴다 | `xml` | 같은 바이트가 **두 타입 이름을 갖고 그 차이가 처리 방식을 바꾼다.** 타입 혼동의 교과서적 사례 |
| `application/x-shockwave-flash` | Macromedia Flash 파일 | `swf` | 페이지 안에서 **자체 실행 환경**이 열린다. 브라우저 확장 컴포넌트 공격과 크로스 도메인 정책의 별도 표면(→ **26.4**, **34.2**) |
| `application/postscript` | Adobe PostScript 그래픽 파일 — 원서 표기 그대로 **"프로그램"** (RFC 2046) | `ai`, `ps`, `eps` | 원서가 괄호로 "(program)"이라 적은 것이 핵심이다. **PostScript는 튜링 완전한 언어**이며, 이미지처럼 보이는 것이 실은 코드다 |
| `application/pdf` | Adobe PDF 파일 | `pdf` | 뷰어가 스크립트와 외부 참조를 처리한다. 첨부·업로드 경로에서 **실행 가능한 문서**로 취급해야 한다 |
| `application/octet-stream` | **분류되지 않은 이진 데이터** (RFC 1341) | `bin`, `dms`, `lha`, `lzh`, `exe`, `class` | 확장자 목록에 `exe`와 `class`가 들어 있다는 점을 보라. "모르는 바이트"의 기본값이며, **스니핑이 가장 적극적으로 개입하는 자리**다. 다운로드 강제의 관용적 수단이지만 그것만으로 실행을 막지는 못한다(→ **10.7**) |

### HTTP 메시지 구조와 얽힌 타입

**표 F-6. HTTP가 직접 쓰는 복합·멀티파트 타입 (HTTP-DG 부록 D 표 D-7·D-9)**

| MIME 타입 | 설명 | 보안 주석 | 본문 참조 |
|---|---|---|---|
| `multipart/form-data` | 사용자가 폼을 채운 결과의 값 묶음 (RFC 2388) | **파일 업로드의 컨테이너.** 바깥 타입은 하나지만 각 파트가 자기 `Content-Type`과 파일명을 갖는다. 검증은 파트 단위로 해야 하며, 파일명은 경로 순회의 입력이다 | **28.3**, **12.4.3** |
| `multipart/byteranges` | HTTP 메시지가 **여러 범위의 콘텐츠**를 담을 때의 형식 (RFC 2068) | 범위 요청의 응답 형식이다. 본문 경계가 `Content-Length`가 아니라 **바운더리 문자열로 결정되는 세 번째 방식**이며, 중간자와 종단의 해석이 갈릴 수 있는 지점 | **10.9**, **10.4** |
| `multipart/mixed` | 객체들의 모음 (RFC 1341) | 바깥 타입만 검사하는 필터가 안쪽 파트를 놓친다 | **10.7** |
| `multipart/alternative` | 같은 내용의 **대안 표현 목록**. 수신자가 하나를 고른다 (RFC 1341) | **같은 메시지가 여러 표현을 갖는다.** 필터가 보는 표현과 사용자가 보는 표현이 다를 수 있다 | **10.7**, **17.3** |
| `multipart/related` | 여러 부분이 하나의 복합 객체를 이루는 경우 (RFC 2387) | `cid:` 스킴과 함께 쓰여 내부 참조를 만든다 | F.1 |
| `multipart/encrypted`, `multipart/signed` | 암호 서비스를 위해 두 파트를 쓴다 (RFC 1847) | 서명 대상과 서명이 **같은 메시지 안에 나란히** 있다. 어느 바이트 범위가 서명 대상인지의 판정이 검증의 전부다 | **17.5** |
| `message/rfc822` | 완전한 이메일 메시지 (RFC 1341) | 메시지 안에 메시지가 있다. 재귀 파싱의 진입점 | **10.1** |
| `message/http` | HTTP 메시지 자체 (RFC 2616) | **HTTP 메시지가 본문에 담긴다.** `TRACE` 응답이 이 형식이며, 요청을 그대로 반사하므로 헤더 내용이 스크립트 컨텍스트로 되돌아온다 | **13.6**, **8.3.3** |
| `message/s-http` | 보안 HTTP 메시지 — SSL 위의 HTTP에 대한 대안 (RFC 2660) | F.1의 `shttp` 스킴과 짝 | **18.1** |

### 그 밖의 흔한 타입

> **이 절이 뒷받침하는 것**
>
> - 선언된 타입과 실제 처리가 어긋난다는 것 → **10.7** (미디어 타입과 문자셋 — MIME 스니핑과 타입 혼동)
> - 업로드된 콘텐츠의 응답 타입이 XSS를 결정한다는 것 → **32.6** (저장형 XSS), **12.4.3** (동적 콘텐츠 매핑)
> - 스크립트로 해석되는 응답이 SOP의 보호를 받지 않는다는 것 → **34.4** (JavaScript 하이재킹)
> - XML 파서가 붙는 타입이 XXE의 전제라는 것 → **28.5**, **28.6**
> - 멀티파트가 두 번째 파싱을 요구한다는 것 → **10.4** (본문 경계의 이중 결정), **13.12** (중간자 공격 표면)

## F.4 MIME 문자셋 레지스트리

### 레지스트리의 구조

MIME 문자셋 태그는 IANA에 등록된다. 레지스트리는 레코드의 평문 데이터베이스이며, 각 레코드는 **문자셋 이름, 참조 인용, 고유한 MIB 번호, 출처 설명, 별칭 목록**을 담는다. 이름이나 별칭 하나에 "preferred MIME name" 표시가 붙을 수 있다.

```
Name: ANSI_X3.4-1968                    [RFC1345, KXS2]
MIBenum: 3
Source: ECMA registry
Alias: iso-ir-6
Alias: ANSI_X3.4-1986
Alias: ISO_646.irv:1991
Alias: ASCII
Alias: ISO646-US
Alias: US-ASCII (preferred MIME name)
Alias: us
Alias: IBM367
Alias: cp367
Alias: csASCII
```

*예제 F-3. US-ASCII의 레지스트리 레코드 (HTTP-DG 부록 H)*

**이 레코드 하나가 이 절의 전체 논지다.** 하나의 문자셋이 **열두 개의 이름**을 갖는다. `Content-Type: text/html; charset=cp367`과 `charset=US-ASCII`는 같은 것을 뜻하지만, 두 문자열을 같다고 판정하려면 파서가 별칭 표를 완전히 갖고 있어야 한다. 경로 위의 두 파서가 서로 다른 별칭 표를 갖고 있으면 — 하나는 알고 하나는 모르면 — **한쪽은 지정된 인코딩으로, 다른 쪽은 기본 인코딩으로 같은 바이트를 읽는다.** 이것이 문자셋 층위의 파싱 불일치다(→ **10.7**, **7.7**).

문자셋 등록 절차는 RFC 2978에 정의되어 있다.

### 선호 MIME 이름 20개

원서 집필 시점에 등록된 235개 문자셋 중 **선호 MIME 이름을 가진 것은 20개뿐**이다. 이메일과 웹 애플리케이션이 실제로 쓰는 흔한 문자셋들이다.

```
Big5          EUC-JP        EUC-KR        GB2312
ISO-2022-JP   ISO-2022-JP-2 ISO-2022-KR   ISO-8859-1
ISO-8859-2    ISO-8859-3    ISO-8859-4    ISO-8859-5
ISO-8859-6    ISO-8859-7    ISO-8859-8    ISO-8859-9
ISO-8859-10   KOI8-R        Shift-JIS     US-ASCII
```

*예제 F-4. 선호 MIME 이름을 가진 20개 문자셋 (HTTP-DG 부록 H)*

**이 목록에 UTF-8이 없다는 사실을 그냥 지나쳐서는 안 된다.** 원서가 인용한 레지스트리 스냅숏은 2001년 3월 기준이고, 그 시점의 UTF-8은 등록은 되어 있으나(RFC 2279) 선호 이름 목록에는 들어 있지 않았다. 웹이 실제로 어떤 인코딩 위에서 돌아가는가는 시대에 따라 바뀌지만, **바뀌지 않는 것은 "선언된 것과 실제가 다를 수 있다"는 조건**이다.

### 문자셋이 보안 문제가 되는 세 지점

**첫째, 선언하지 않으면 추측된다.** `Content-Type`에 `charset` 파라미터가 없으면 수신자가 정한다. 무엇으로 정할지는 구현마다 다르고, 그 차이가 같은 바이트를 다른 문자로 만든다. **출력 인코딩은 어떤 문자셋으로 읽힐지를 아는 상태에서만 정확할 수 있다**(→ **32.10**).

**둘째, 별칭이 많다.** 위 표의 첫 행이 보여 주듯 하나의 문자셋이 열 개 넘는 이름을 갖는다. 정규화 없이 문자열 비교로 문자셋을 판정하는 코드는 **아는 이름에는 반응하고 모르는 별칭에는 기본값으로 떨어진다.**

**셋째, 멀티바이트 인코딩에서 바이트 하나는 문자 하나가 아니다.** `Shift_JIS`·`GB2312`·`Big5` 계열에서 2바이트 문자의 후행 바이트가 ASCII의 `\`나 `'`와 같은 값을 가질 수 있다. **바이트 단위로 이스케이프하는 필터는 문자의 절반을 이스케이프한다.** 그 결과 원래 없던 인용부호가 생기거나 있던 것이 사라진다. 7.7절의 정규화 논의와 31.7절의 인코딩 결함 재방문이 이 문제를 다룬다.

> **이 절이 뒷받침하는 것**
>
> - 문자셋 미선언이 해석을 수신자에게 넘긴다는 것 → **10.7** (미디어 타입과 문자셋), **10.10** (국제화)
> - 오버롱 UTF-8과 이중 디코딩 → **7.7** (정규화와 다중 인코딩), **7.8** (다단계 검증과 정규화 순서)
> - 멀티바이트 후행 바이트를 이용한 필터 우회 → **27.5** (SQL 필터 우회), **31.7** (인코딩·정규화 결함 재방문)
> - 시각적으로 구별되지 않는 문자 → **7.9** (국제화 URI와 IDN — 동형이의 문자)

## F.5 언어 태그와 ISO 639 / ISO 3166 코드

### 태그의 구조

언어 태그는 사람이 쓰는 언어를 이름 짓는 짧은 표준 문자열이다. `fr`(프랑스어), `en-GB`(영국 영어) 같은 형태이며, 하이픈으로 나뉜 하나 이상의 **서브태그(subtag)** 로 이루어진다. 10.10절이 언어 태그와 HTTP의 관계를 다뤘고, 이 절은 그 규칙과 코드 목록을 조회표로 정리한다.

**첫 서브태그 규칙**

| 첫 서브태그가 | 의미 |
|---|---|
| 두 글자 | ISO 639 및 639-1 표준의 언어 코드 |
| 세 글자 | ISO 639-2 표준에 실린 언어 코드 |
| 글자 `i` | IANA에 명시적으로 등록된 언어 태그 |
| 글자 `x` | **사적이고 비표준인 확장 서브태그** |

**둘째 서브태그 규칙**

| 둘째 서브태그가 | 의미 |
|---|---|
| 두 글자 | ISO 3166이 정의한 국가·지역 |
| 3~8 글자 | IANA에 등록되었을 수 있다 |
| 한 글자 | **불법** |

세 가지를 짚어 둔다.

**하나, `x-` 서브태그는 무엇이든 될 수 있다.** MIME 타입의 실험 트리와 같은 구조이며, 같은 결과를 낳는다 — 값의 의미가 명세로 고정되지 않는다. 언어 태그를 신뢰 결정에 쓰는 코드는 이 값을 허용 목록으로 걸러야 한다.

**둘, 국가 코드 중 예약된 것이 있다.** ISO 3166은 `AA`, `QM`–`QZ`, `XA`–`XZ`, `ZZ`를 사용자 지정 코드로 예약해 두었으며, **이 코드로 언어 태그를 만들어서는 안 된다.** 검증 코드가 "두 글자면 국가 코드"라는 규칙만 적용하면 이 예약 범위를 통과시킨다.

**셋, 태그는 서버가 아니라 클라이언트가 보낸다.** `Accept-Language`는 사용자 에이전트가 주장하는 값이며 검증되지 않는다. 그 값이 콘텐츠 협상의 입력이 되고, 협상 결과가 캐시 키에 반영되어야 한다는 것이 `Vary` 문제로 이어진다(→ **14.8**). 동시에 이 헤더는 **비교적 좁은 값 분포를 갖는 지문**이기도 하다(→ **36.1**).

| `i-tay` | 타얄어 | | |
| `i-tsu` | 초우어 | | |

`i-default`가 특별하다. **"기본 언어 컨텍스트"** 는 언어가 아니라 협상 실패 시의 대체값이다. 콘텐츠 협상 코드에서 이 값을 다른 언어 태그와 같은 방식으로 다루면, 협상 실패가 특정 언어 선택으로 잘못 해석된다.

`zh-*`와 `no-*` 항목들은 다른 문제를 보여 준다. **하나의 두 글자 코드 아래 서로 알아듣지 못하는 언어들이 묶여 있다.** 언어 태그의 두 글자 코드는 언어의 동일성을 보장하지 않는다.

### ISO 639 언어 코드

ISO 639는 두 글자 코드를, ISO 639-2는 세 글자 코드를 정의한다. 세 글자 코드는 두 글자 코드가 없는 언어까지 포함하므로 목록이 훨씬 길다. 원서 표 G-2는 수백 행이며, 여기서는 **웹에서 흔히 마주치는 것과 규칙을 설명하는 데 필요한 것**만 싣는다.

**표 F-10. ISO 639 / 639-2 언어 코드 발췌 (HTTP-DG 부록 G 표 G-2)**

| 언어 | ISO 639 | ISO 639-2 |
|---|---|---|
| Arabic (아랍어) | `ar` | `ara` |
| Bengali (벵골어) | `bn` | `ben` |
| Bulgarian (불가리아어) | `bg` | `bul` |
| Burmese (버마어) | `my` | `bur`/`mya` |
| Albanian (알바니아어) | `sq` | `alb`/`sqi` |
| Armenian (아르메니아어) | `hy` | `arm`/`hye` |
| Basque (바스크어) | `eu` | `baq`/`eus` |
| Afrikaans | `af` | `afr` |
| Amharic (암하라어) | `am` | `amh` |
| Azerbaijani (아제르바이잔어) | `az` | `aze` |
| Bashkir (바시키르어) | `ba` | `bak` |
| Achinese (아체어) | — | `ace` |
| Akkadian (아카드어) | — | `akk` |
| Bantu (기타) | — | `bnt` |

두 가지가 눈에 띈다. **첫째, 두 글자 코드가 없는 언어가 많다** — `ace`, `akk`, `bnt`처럼 세 글자 코드만 있는 항목이 표의 상당 부분을 차지한다. "언어 코드는 두 글자"라는 가정으로 짠 파서는 이 값들에서 실패한다. **둘째, 같은 언어에 세 글자 코드가 둘인 경우가 있다** — `alb`/`sqi`, `arm`/`hye`, `baq`/`eus`. 서지 코드와 용어 코드의 이중 체계이며, **두 문자열이 같은 언어를 뜻하지만 문자열 비교로는 다르다.** F.4절의 문자셋 별칭 문제가 언어 코드에서 반복된다.

### ISO 3166 국가 코드

둘째 서브태그로 쓰이는 두 글자 국가 코드다. 원서 표 G-3은 전 세계 국가를 나열한다.

**표 F-11. ISO 3166 국가 코드 발췌 (HTTP-DG 부록 G 표 G-3)**

| 국가 | 코드 | 국가 | 코드 |
|---|---|---|---|
| United States | `US` | Sweden | `SE` |
| United Kingdom | `GB` | Switzerland | `CH` |
| Taiwan, Province of China | `TW` | Turkey | `TR` |
| Thailand | `TH` | Ukraine | `UA` |
| Tunisia | `TN` | United Arab Emirates | `AE` |
| Uruguay | `UY` | Uzbekistan | `UZ` |
| Venezuela | `VE` | Viet Nam | `VN` |
| Yemen | `YE` | Zambia | `ZM` |

**United Kingdom의 코드가 `GB`라는 점을 확인해 두어야 한다.** 그러나 널리 쓰이는 언어 태그는 `en-GB`이면서 최상위 도메인은 `.uk`다. **국가 코드 체계가 하나가 아니며, 한 체계의 코드를 다른 체계에 그대로 대입하면 어긋난다.** 지역 기반 접근 제어나 리다이렉션 로직이 이 어긋남 위에 서 있으면 그 자체가 우회 지점이 된다(→ **15.6**).

### 유지 관리 기관

각 표준에는 추가·변경을 담당하는 유지 관리 기관이 지정되어 있다. 표준이 고정된 목록이 아니라 **시간에 따라 변하는 레지스트리**라는 사실이 실무적 함의를 갖는다 — 하드코딩된 코드 목록은 낡는다.

| 표준 | 유지 관리 기관 |
|---|---|
| ISO 639 | International Information Centre for Terminology (Infoterm), 오스트리아 빈 |
| ISO 639-2 | Library of Congress, Network Development and MARC Standards Office, 미국 워싱턴 D.C. |
| ISO 3166 | ISO 3166 Maintenance Agency Secretariat, c/o DIN Deutsches Institut für Normung, 독일 베를린 |

> **이 절이 뒷받침하는 것**
>
> - 언어 태그가 클라이언트의 주장이며 검증되지 않는다는 것 → **8.6** (헤더의 신뢰성), **10.10** (국제화)
> - 협상 결과가 캐시 키에 반영되어야 한다는 것 → **14.8** (공유 캐시의 보안 함의 — Vary 오설정)
> - `Accept-Language`가 지문이 된다는 것 → **36.1** (로컬 프라이버시 공격), **25.6** (사용 기술 식별)
> - 국가·언어 코드 체계의 불일치 → **15.6** (일반 리다이렉션 기법), **7.9** (국제화 URI와 IDN)

## 이 부록의 요약

- **네 레지스트리는 같은 형태의 위험을 공유한다.** 하나의 대상에 여러 이름이 붙고(문자셋 별칭, 언어 코드 이중 체계, `javascript`/`livescript`/`mocha`), 미등록 확장이 허용되며(`x-` 타입, `x-` 서브태그, 비공식 스킴), 그 결과 **경로 위의 두 파서가 같은 문자열을 다르게 읽는다.**
- **스킴은 해석기를 고른다.** `javascript:`와 `data:`는 네트워크를 거치지 않으므로 서버 측 방어가 닿지 않고, `file:`은 서버 측 코드에서 SSRF·경로 순회의 문이 된다. 스킴 판정은 반드시 허용 목록이어야 한다.
- **MIME 타입의 등록 트리가 곧 보장 수준이다.** IETF 트리만이 표준화 트랙 RFC로 동작이 고정되고, `vnd.`·`prs.`·`x-`는 그렇지 않다. 등록되지 않았다는 것은 **동작이 정의되지 않았다**는 뜻이며, 그 미정의 구간이 타입 혼동의 서식지다.
- **복합·멀티파트 타입은 두 번째 파싱을 요구한다.** 바깥 타입만 검사하는 필터는 안쪽 파트의 타입을 보지 못한다. 파일 업로드·범위 응답·서명 메시지가 모두 이 구조 위에 있다.
- **문자셋을 선언하지 않으면 수신자가 정한다.** 그 결정이 구현마다 다르고, 그 차이가 같은 바이트를 다른 문자로 만든다. 멀티바이트 인코딩에서는 **바이트 하나가 문자 하나가 아니라는 사실**이 바이트 단위 필터를 무력화한다.
- **언어 태그는 클라이언트의 주장이다.** 검증되지 않으며, 협상 결과가 캐시 키에 반영되지 않으면 사용자 간 응답 혼동이 된다. 동시에 그 값의 분포가 지문이 된다.
- **모든 레지스트리는 시간에 따라 변한다.** 각 표준에 유지 관리 기관이 지정되어 있다는 사실이 그 증거다. 코드 안에 박아 넣은 목록은 반드시 낡고, 낡은 목록은 **모르는 값을 기본값으로 떨어뜨리는 방식으로** 실패한다.

> **원서 대조**
>
> F.1절: HTTP-DG 부록 A "URI Schemes" 표 A-1 전체를 근거로 한다. 스킴 이름, 설명의 사실 부분, RFC 번호는 원서 표에서 인용했다. 원서는 W3C 레지스트리 기준 약 90개를 나열하며 "그중 다수가 널리 쓰이지 않거나 사장됐다"고 스스로 밝힌다. 표 F-1의 "무엇이 위험한가" 열과 본문 참조 열, 표 F-2의 선별, "나머지 스킴"의 분류는 이 책의 정리다. `javascript` 스킴의 동작(콜론 뒤 식을 평가하고 그 문자열 값의 페이지를 로드), `file` 스킴이 인터넷 프로토콜이나 접근 방법을 명시하지 않는다는 서술, `telnet` URL이 사용자명·비밀번호를 포함한다는 문법, `shttp`가 HTTPS로 대체됐다는 서술, `chttp`·`mms`·`uuid`·`eid`·`nntp`에 대한 설명은 모두 원서 표 A-1의 내용이다.
>
> F.2절: HTTP-DG 부록 D "MIME Types" 중 "Background", "MIME Type Structure", "MIME Type IANA Registration"을 근거로 한다. RFC 2045~2049의 역할 구분, 이산·복합·멀티파트 타입의 정의, 예제 F-1의 헤더 예시, 예제 F-2의 RFC 2046 문법, 표 F-3(원서 표 D-1), 표 F-4의 네 등록 트리와 예시(원서 표 D-2), 3단계 등록 절차, 벤더·개인 타입 자동 등록의 네 조건, 등록 템플릿의 항목 목록, 등록 양식이 기계 처리에 부적합하다는 원서의 지적이 모두 원서에서 인용되었다. 표 F-4의 "보안·운영 주석" 열과 `TSPECIALS`가 파라미터 값에서 갖는 함의는 이 책의 정리다.
>
> F.3절: HTTP-DG 부록 D의 열 개 MIME 타입 표(D-3~D-12)를 근거로 하되, 절 첫머리에 밝힌 세 기준으로 선별했다. 각 행의 MIME 타입 이름, 설명의 사실 부분, 확장자, RFC 번호는 원서 표에서 인용했다. `application/postscript`의 설명에 원서가 괄호로 "(program)"이라 적은 것, `application/octet-stream`의 확장자 목록에 `exe`와 `class`가 포함된 것, `application/xml`과 `text/xml`이 서로를 가리키며 브라우저 처리 차이를 설명하는 것, `x-conference/x-cooltalk`이 표 D-12의 유일한 항목인 것은 모두 원서 표의 내용이다. "보안 주석" 열 전체는 이 책의 정리이며, 원서 표 D-5(chemical)·D-8(model)과 오디오·비디오 벤더 타입 대부분은 선별 기준에 따라 싣지 않았다.
>
> F.4절: HTTP-DG 부록 H "MIME Charset Registry"를 근거로 한다. 레지스트리 레코드의 구성(이름, 참조, MIB 번호, 출처, 별칭), 예제 F-3의 US-ASCII 레코드, RFC 2978의 등록 절차, "등록된 235개 중 선호 MIME 이름을 가진 것은 20개"라는 수치와 그 목록, 표 F-8의 문자셋 태그·별칭·설명 열은 모두 원서 부록 H와 표 H-1에서 인용했다. 표 H-1이 2001년 3월 기준 스냅숏이라는 것도 원서의 명시다. `ISO-10646-UCS-2`의 "표준이 바이트 순서를 정하지 않았다"는 서술, `GB2312`의 바이트 범위(20–7E / A1–FE), `Shift_JIS`가 `csHalfWidthKatakana`의 확장이라는 서술은 원서 표 H-1의 내용이다. "보안 주석" 열과 "문자셋이 보안 문제가 되는 세 지점"은 이 책의 정리다.
>
> F.5절: HTTP-DG 부록 G "Language Tags"를 근거로 한다. 첫·둘째 서브태그 규칙, ISO 3166이 `AA`·`QM`–`QZ`·`XA`–`XZ`·`ZZ`를 사용자 지정 코드로 예약했으며 이것으로 언어 태그를 만들어서는 안 된다는 각주, 표 F-9의 IANA 등록 언어 태그 전체(원서 표 G-1), 표 F-10·F-11의 코드 값(원서 표 G-2·G-3), 세 유지 관리 기관의 명칭과 소재지는 모두 원서에서 인용했다. 원서 표 G-2·G-3은 수백 행이므로 발췌했으며, 발췌 기준은 규칙을 설명하는 데 필요한 사례(두 글자 코드가 없는 언어, 세 글자 코드가 둘인 언어)와 웹에서 흔히 마주치는 항목이다. `i-default`의 성격, `zh-*`·`no-*`가 하나의 두 글자 코드 아래 서로 다른 언어를 묶는다는 지적, `GB`와 `.uk`의 불일치, 하드코딩된 코드 목록이 낡는다는 정리는 이 책의 서술이다.
>
> 본문 참조 `(→ N.M)`은 이 책의 목차 절 번호를 가리킨다. 원서가 자기 장을 가리킨 자리 — 부록 G가 "16장의 Language Tags and HTTP 절에서 상세히 다뤘다"고 한 것, 부록 D가 MIME 타입을 3장·15장과 연결한 것 — 는 이 책의 대응 절(10.10, 10.7, 8.5)로 바꿨다.
