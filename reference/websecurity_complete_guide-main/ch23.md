# 23장. 세션 관리 공격과 강화

> **이 장에서 다루는 것**
>
> - HTTP가 상태를 잃은 자리에 세션이 들어선 이유, 그리고 세션을 쓰지 않는 두 대안이 무엇을 치르는지
> - 토큰이 발급되는 순간에 이미 깨지는 방식 — 의미를 담은 토큰, 예측 가능한 토큰, 암호화해도 조작되는 토큰
> - 발급된 뒤 토큰이 새는 세 경로 — 네트워크, 로그, 그리고 토큰과 세션을 잘못 이은 매핑
> - 세션이 끝나지 않거나 남의 손으로 시작되는 두 결함 — 취약한 종료와 세션 고정
> - 생성부터 폐기까지 토큰의 생애주기 전체를 지키는 강화의 축, 그리고 방어가 테스트를 막을 때 그것이 방어인지 아닌지의 물음

22장은 인증이 성공하기까지의 모든 실패를 훑었다. 그 끝에서 인증은 **세션 토큰**을 발급한다. 21장에서 자격증명이 매 요청에 실렸던 자리를, 폼 로그인은 한 번의 인증 뒤 발급되는 토큰으로 대체했다. 사용자는 다시 비밀번호를 대지 않고, 대신 그 토큰을 매 요청에 실어 보낸다. 세션 관리 메커니즘은 그 토큰을 근거로 **여러 요청에 걸쳐 같은 사용자를 식별하고, 그 사용자와의 상호작용에서 누적되는 상태를 관리한다.**

바로 이 근본적 역할 때문에 세션 관리는 공격의 일급 표적이다. 인증 메커니즘이 아무리 견고해도, 인증 이후의 요청은 오직 **세션을 통해서만** 그 인증에 연결된다. 세션 관리에 결함이 있으면 공격자는 견고한 인증을 우회하고, 남의 자격증명을 모른 채 그 사람으로 행세한다. 그리고 관리자 세션을 탈취하면 애플리케이션 전체를 손에 넣는다. "스마트카드로 인증하니 세션은 안전하다"는 흔한 믿음이 틀린 이유가 여기 있다. 인증이 무엇이든, 그 뒤를 잇는 것은 세션이다.

이 장은 세션 관리에서 발견되는 결함의 전 범위를 다룬다. 결함은 크게 두 범주로 갈린다. **토큰이 생성되는 방식의 약점**과 **생성된 뒤 토큰을 다루는 방식의 약점**이다. 앞의 절반(23.2)은 공격자가 남에게 발급된 토큰을 **추측하거나 계산해내는** 문제이고, 뒤의 절반(23.3~23.5)은 토큰이 견고하게 생성됐더라도 **어딘가로 새거나 남의 손에 심어지는** 문제다. 두 범주 모두 결국 하나의 목표로 수렴한다 — 정당한 사용자의 세션을 가로채 그 사람으로 행세하는 것. 이 장은 그 공격들을 하나씩 해부하고, 마지막 세 절에서 생애주기 전체를 지키는 강화(23.6), 방어가 테스트를 막는 역설(23.7), 그리고 상태를 아예 서버 밖으로 밀어내는 무상태 설계(23.8)로 닫는다.

이 장의 실행 예제는 **온라인 서점**이다. 로그인한 고객, 로그인하지 않고 장바구니에 책을 담는 손님, 그리고 그 둘 모두에게 발급되는 토큰을 따라가며 각 결함을 살핀다.

## 23.1 상태의 필요와 세션의 대안 — HTTP 인증, 무상태 토큰, sessionless state

HTTP는 본질적으로 상태가 없다(→ 6장). 요청-응답 한 쌍이 각각 독립된 트랜잭션이고, 프로토콜 자체에는 한 사용자의 연속된 요청을 다른 모든 요청과 구별해 묶는 장치가 없다. 웹 초창기, 누구나 보는 정적 HTML을 발행하던 시절에는 그런 장치가 필요 없었다. 오늘의 웹 "사이트"는 대부분 **웹 애플리케이션**이다. 등록하고 로그인하며, 물건을 사고팔고, 다음 방문 때 선호를 기억한다. 이 모든 기능은 **세션**이라는 개념을 요구한다.

세션의 가장 뚜렷한 쓰임은 로그인이다. 사용자명과 비밀번호를 넣고 나면, 로그아웃하거나 세션이 만료될 때까지 그 사용자로 애플리케이션을 쓴다. 세션이 없다면 페이지마다 비밀번호를 다시 입력해야 한다. 한 번 인증한 뒤 애플리케이션은 그 사용자를 위한 세션을 만들고, 그 세션에 속한 모든 요청을 같은 사용자에게서 온 것으로 취급한다.

로그인 기능이 없는 애플리케이션도 대개 세션이 필요하다. 온라인 서점이 계정 생성을 요구하지 않더라도, 손님은 목록을 훑고, 장바구니에 책을 담고, 배송 정보를 넣고, 결제를 한다. 이 시나리오에서 신원을 인증할 필요는 없다 — 방문의 대부분 동안 애플리케이션은 손님이 누구인지 알지도, 알 필요도 없다. 그러나 거래를 하려면 **어느 요청들이 같은 손님에게서 왔는지**는 알아야 한다.

세션을 구현하는 가장 단순하고 여전히 가장 흔한 방식은 각 사용자에게 고유한 **세션 토큰**을 발급하는 것이다. 이후 매 요청마다 사용자가 이 토큰을 재제출하면, 애플리케이션은 현재 요청이 어느 이전 요청 열에 속하는지 판정한다. 대부분의 경우 전송 수단은 HTTP 쿠키다(→ 20.5). 서버의 첫 응답은 다음과 같은 헤더를 담는다.

```
Set-Cookie: SESSIONID=mza2ji454s04cwbgwb2ttj55
```

이후 클라이언트 요청은 이 헤더를 담는다.

```
Cookie: SESSIONID=mza2ji454s04cwbgwb2ttj55
```

쿠키가 표준 전송 수단인 것은 이 책이 20장에서 쿠키를 다룬 이유이기도 하다. 세션 토큰은 쿠키라는 운반 수단에 실려 오가고, 따라서 쿠키의 성질 — 자동 재제출, 스킴을 구별하지 않는 범위, 무결성 통제의 부재(→ 20.6, 20.9) — 은 그대로 세션의 성질이 된다. 상용 서버와 플랫폼 대부분은 쿠키 기반의 기성 세션 관리 솔루션을 내장하고 API로 노출한다. 그러나 일부 기성 구현이 취약점을 드러냈고, 일부 개발자는 내장 솔루션보다 세밀한 통제를 원하거나 쿠키 기반의 고유한 약점을 피하려 한다. 그래서 온라인 뱅킹처럼 보안이 중요한 애플리케이션에서는 맞춤형이거나 비쿠키 기반의 세션 메커니즘을 어렵지 않게 만난다.

### 23.1.1 세션을 쓰지 않는 두 대안

모든 애플리케이션이 세션을 쓰는 것은 아니다. 인증 메커니즘과 복잡한 기능을 갖춘 일부 보안 중요 애플리케이션은 상태 관리에 다른 기법을 택한다. 마주칠 수 있는 대안은 둘이다.

**첫째, HTTP 인증.** Basic, Digest, NTLM 같은 HTTP 기반 인증 기술을 쓰는 애플리케이션은 세션을 아예 두지 않기도 한다(→ 21장). HTTP 인증에서 클라이언트는 개별 페이지의 애플리케이션 코드가 아니라 **브라우저를 통해 HTTP 헤더로 인증 메커니즘과 직접 상호작용한다.** 사용자가 브라우저 대화상자에 자격증명을 넣으면, 브라우저는 같은 서버로 가는 **모든 후속 요청에 그 자격증명을(또는 요구되는 핸드셰이크를) 다시 실어 보낸다.** 이것은 폼 기반 인증을 쓰면서 모든 페이지에 로그인 폼을 두어 매 동작마다 재인증을 요구하는 것과 같다. 그래서 HTTP 인증을 쓰면 세션 없이도 여러 요청에 걸쳐 사용자를 재식별할 수 있다. 다만 복잡한 인터넷 애플리케이션에서 HTTP 인증은 드물게만 쓰이고, 본격적인 세션 메커니즘이 주는 다재다능함 때문에 사실상 거의 모든 웹 애플리케이션이 세션을 채택한다.

> 여기에는 3.9.3절이 짚은 함정이 하나 겹친다. 인증 상태를 **커넥션**에 거는 설계 — NTLM처럼 TCP 커넥션 단위로 인증을 유지하는 방식 — 는 프록시 뒤에서 커넥션이 여러 사용자에게 공유될 때(→ 9.11) 한 사람의 인증 상태가 다른 사람의 요청에 붙는 사고를 낳는다. 세션 없는 인증이 세션의 문제를 지우는 대신 커넥션 공유의 문제로 옮겨 놓는 셈이다.

**둘째, 무상태 상태 메커니즘(sessionless state).** 일부 애플리케이션은 세션 토큰을 발급해 상태를 관리하지 않는다. 대신 상태 관리에 필요한 **모든 데이터를 클라이언트를 통해 전송한다** — 보통 쿠키나 히든 폼 필드에 담는다. ASP.NET의 viewstate가 하는 것과 같은 방식이다. 이 메커니즘이 안전하려면 클라이언트를 통해 오가는 데이터가 제대로 보호되어야 한다. 대개 모든 상태 정보를 담은 이진 blob을 구성해 인정된 알고리즘으로 **암호화하거나 서명한다.** 데이터 안에 충분한 문맥을 넣어, 공격자가 애플리케이션의 한 위치에서 상태 객체를 수집해 다른 위치에 제출함으로써 원치 않는 동작을 일으키는 것을 막아야 한다. 세션 타임아웃에 해당하는 것으로 객체 안에 만료 시각을 넣기도 한다. 클라이언트를 통해 데이터를 안전하게 전송하는 메커니즘은 26장이 상세히 다룬다.

무상태 상태 메커니즘은 이 장의 끝(23.8)이 무상태 설계로 다시 받는 주제와 연결된다. 다만 그 절이 다루는 것은 **처리 인스턴스가 상태를 갖지 않는** 서버 측 무상태성이고, 여기서 말하는 것은 **상태를 클라이언트로 밀어낸** 것이다. 둘은 방향이 반대다. 하나는 상태를 백엔드의 공유 저장소로 밀고, 다른 하나는 클라이언트로 민다. 클라이언트로 민 상태는 반드시 암호학적 보호를 요구하며, 그 보호가 어떻게 오용되는지가 23.2절 후반의 주제다.

**표 23-1. 상태를 만드는 세 가지 방식 (WAHH 7장 기준)**

| 방식 | 상태가 사는 곳 | 재식별 근거 | 이 장·책의 절 |
|---|---|---|---|
| 세션 토큰 | 서버(세션 객체) | 불투명 토큰 | 23장 전체 |
| HTTP 인증 | 매 요청 재전송되는 자격증명 | 자격증명 자체 | 21장, 3.9.3 |
| sessionless state | 클라이언트(암호화된 blob) | 서명·암호화된 상태 | 26장, 23.8 |

세션 토큰의 정체를 확인하는 일이 늘 자명하지는 않다. 애플리케이션은 여러 데이터 항목 — 쿠키, URL 파라미터, 히든 폼 필드 — 을 **집합적으로** 토큰으로 쓸 수 있고, 그중 일부는 서로 다른 백엔드 컴포넌트의 세션 상태를 유지하는 데 쓰인다. 서버가 발급한 표준 세션 쿠키가 존재하지만 애플리케이션이 실제로는 쓰지 않는 경우도 있다. 무엇이 실제 토큰인지는 증명해야 한다 — 세션 의존 페이지(예: 내 주문 내역)를 반복 요청하면서 의심 항목을 하나씩 빼 보고, 어떤 항목을 제거했을 때 그 페이지가 더는 반환되지 않으면 그 항목이 세션 토큰임이 확인된다.

> **이 절이 뒷받침하는 것**
>
> - 세션을 쓰지 않는 대안으로서의 HTTP 인증 → **21장** (Basic·Digest의 구조와 한계)
> - 쿠키가 세션 토큰의 운반 수단이라는 것 → **20.5** (쿠키의 동작), **20.6** (쿠키 속성이 세션 토큰에 주는 보호)
> - sessionless state의 클라이언트 측 상태 보호 → **26장** (클라이언트 사이드 통제), **23.8** (서버 측 무상태 설계와의 대비)

## 23.2 토큰 생성의 약점 — 의미 있는 토큰, 예측 가능한 토큰, 암호화된 토큰의 오용

세션 관리가 취약해지는 첫 번째 큰 이유는 토큰이 **안전하지 않게 생성되어**, 공격자가 남에게 발급된 토큰 값을 알아낼 수 있게 되는 것이다.

토큰의 예측 불가능성에 의존하는 것은 세션 토큰만이 아니라는 점을 먼저 새겨야 한다. 이메일로 보내는 비밀번호 복구 토큰, CSRF 방지용 히든 필드 토큰(→ 33.4), 보호 자원에 일회성 접근을 주는 토큰, "로그인 상태 유지"의 지속 토큰(→ 22.4), 그리고 인증 없는 서점에서 손님이 기존 주문 상태를 조회하는 토큰 — 이 모두가 예측 불가능성에 기댄다. 오늘날 많은 애플리케이션이 성숙한 플랫폼 메커니즘으로 세션 토큰을 생성하기 때문에, 익스플로잇 가능한 생성 약점은 오히려 이런 **주변 기능**에서 발견되는 일이 잦다. 아래의 논의는 그 모두에 적용된다.

### 23.2.1 의미 있는 토큰

어떤 세션 토큰은 사용자명이나 이메일 주소, 그 사람과 결부된 다른 정보를 **변환해서** 만든다. 정보는 인코딩되거나 난독화되고, 다른 데이터와 결합되기도 한다. 다음 토큰은 처음엔 긴 무작위 문자열로 보인다.

```
757365723d6a6f653b6170703d61646d696e3b646174653d31302f30392f3131
```

그러나 자세히 보면 16진수 문자만 있다. 이 문자열이 ASCII 문자열의 hex 인코딩이라 짐작하고 디코더에 넣으면 다음이 드러난다.

```
user=joe;app=admin;date=10/09/11
```

공격자는 이 토큰에 담긴 의미를 이용해 다른 사용자의 현재 세션을 추측한다. 열거했거나 흔한 사용자명 목록으로 **잠재적으로 유효한 토큰을 대량 생성해** 어느 것이 유효한지 확인하면 된다. 서점의 관리 계정 사용자명이 `admin`이라면, 위 구조를 안 공격자는 `user=admin`으로 토큰을 조립해 관리자 세션을 노린다.

의미를 담은 토큰은 대개 **구조**를 드러낸다 — 구분자로 나뉜 여러 성분을 따로 뽑아 분석할 수 있다. 구조화된 토큰에서 마주치는 성분은 다음과 같다.

- 계정 사용자명
- 애플리케이션이 계정을 구분하는 데 쓰는 수치 식별자
- 사용자의 이름과 성
- 이메일 주소
- 애플리케이션 안에서의 그룹·역할
- 날짜/시각 스탬프
- 증가하거나 예측 가능한 번호
- 클라이언트 IP 주소

각 성분은, 또는 토큰 전체는 서로 다른 방식으로 인코딩될 수 있다 — 내용을 감추려는 의도든, 이진 데이터를 HTTP로 안전하게 나르려는 것이든. 흔한 인코딩은 XOR, Base64, ASCII를 쓴 16진 표현이다. 각 성분에 여러 디코딩을 시도해 원형으로 풀어야 할 때가 있다.

한 가지 주의. 애플리케이션은 구조화된 토큰을 받아도 **모든 성분을 처리하지는 않는다.** 위 예에서 서버가 Base64 디코드 후 `user`와 `date`만 볼 수도 있다. 토큰 안에 이진 blob이 있으면 그 대부분이 패딩이고, 검증에 실제로 쓰이는 것은 작은 일부일 수 있다. 토큰을 한 바이트씩(혹은 한 비트씩) 바꿔 재제출하며 **어느 부분이 실제로 검증되는지** 좁히면, 겉보기 엔트로피와 복잡도를 크게 줄일 수 있다. 서로 다른 시각에 여러 사용자로 로그인해 토큰을 기록하고, 자기 등록이 가능하다면 `A, AA, AAA, AAAB, AAAC`처럼 조금씩 다른 사용자명으로 로그인해 토큰의 대응 변화를 관찰하면 인코딩과 상관관계가 드러난다.

### 23.2.2 예측 가능한 토큰

어떤 토큰은 사용자와 결부된 의미를 담지 않는다. 그럼에도 추측된다 — 표본에서 다른 유효 토큰으로 **외삽할 수 있는 시퀀스나 패턴**을 담기 때문이다. 외삽에 시행착오가 좀 섞여도(예: 1,000번 시도당 유효 추측 1개) 자동화 공격이 짧은 시간에 대량의 유효 토큰을 잡아내기에 충분하다.

이런 약점은 맞춤형 애플리케이션보다 상용 구현(서버·플랫폼)에서 발견하기 훨씬 쉬울 수 있다. 맞춤형을 원격에서 노릴 때 표본은 서버 용량, 다른 사용자 활동, 대역폭, 지연에 제약된다. 그러나 실험실 환경이라면 정확히 순서 매기고 시각 표시된 토큰을 초당 수백만 개 만들 수 있고, 다른 사용자의 간섭도 없앨 수 있다.

가장 단순하고 노골적으로 취약한 경우는 **순차 번호**를 토큰으로 쓰는 것이다. 두세 개만 얻으면 현재 유효한 세션을 100퍼센트 잡는 공격을 시작할 수 있다. 응답 길이가 유효 세션의 신뢰할 만한 지표가 되고, 응답에서 로그인 사용자명을 뽑아 붙이면 어느 세션이 누구인지까지 알 수 있다. 더 정교한 경우는 세 갈래에서 온다 — **은닉 시퀀스, 시각 의존, 약한 난수 생성.**

**은닉 시퀀스.** 원형으로는 예측이 어렵지만 적절히 디코딩·언팩하면 시퀀스가 드러나는 경우다. 서점의 토큰에서 다음 성분 열을 뽑았다고 하자.

```
lwjVJA  Ls3Ajg  xpKr+A  XleXYg  9hyCzA  jeFuNg  JaZZoA
```

즉각적 패턴은 없지만 `+`가 섞인 것을 보아 Base64로 짐작된다. 디코드하면 비출력 문자가 섞인 이진 데이터가 나오고, 16진수로 렌더링하면 다음이 된다.

```
9708D524  2ECDC08E  C692ABF8  5E579762  F61C82CC  8DE16E36  25A659A0
```

여전히 패턴이 없다. 그러나 **각 수에서 앞의 수를 빼면** 다음이 나온다.

```
FF97C4EB6A
  97C4EB6A
FF97C4EB6A
  97C4EB6A
FF97C4EB6A
FF97C4EB6A
```

숨은 패턴이 드러난다. 알고리즘은 앞 값에 `0x97C4EB6A`를 더하고, 결과를 32비트로 잘라, Base64로 인코딩한다. 이제 서버가 다음에 낼 토큰 열과, 표본 이전에 낸 토큰 열을 스크립트로 재생할 수 있다.

**시각 의존.** 어떤 서버는 생성 시각을 토큰 값의 입력으로 쓴다. 다른 엔트로피가 부족하면 남의 토큰을 예측할 수 있다. 어떤 토큰 열 자체는 무작위로 보여도, 각 토큰이 생성된 시각 정보와 짝지으면 패턴이 드러난다. 초당 다수의 세션이 만들어지는 바쁜 서점에서 스크립트 공격은 대량의 토큰을 잡는다. 실제로 온라인 소매업체에서 다음 토큰 열을 만난다.

```
3124538-1172764258718
3124539-1172764259062
3124540-1172764259281
3124541-1172764259734
3124542-1172764260046
```

각 토큰은 두 수치 성분이다. 첫 수는 단순 증가라 예측이 쉽다. 둘째 수는 매번 다른 폭으로 증가한다. 몇 분 기다렸다 두 번째 표본을 모으면 두 가지가 명백해진다. 첫 수열은 여전히 증가하되 **다섯 값이 건너뛰어졌다**(그 사이 다른 사용자 다섯이 로그인했다는 뜻). 둘째 수열의 첫 값은 이전보다 무려 539,578 크다 — 약 10분이 흘렀는데 다섯 토큰만 발급됐으니, **둘째 수는 시각 의존이며 밀리초 카운트**임이 드러난다. 코드 리뷰가 이를 확증한다.

```java
String sessId = Integer.toString(s_SessionIndex++)
              + "-"
              + System.currentTimeMillis();
```

공격 스크립트의 구조는 이렇다. 서버를 빠르게 폴링해 새 토큰을 얻고, 첫 수가 1보다 크게 증가하면 그 사이 다른 사용자에게 토큰이 발급됐음을 안다. 그 사용자에게 발급된 둘째 수의 상·하한을 우리가 가진 직전·직후 토큰이 알려 주고, 자주 폴링하므로 그 범위는 대개 수백 값에 불과하다. 그 범위를 무차별 대입해 그 사용자의 세션을 침해한다. 관리자가 로그인하는 순간 서점 전체가 넘어간다.

**약한 난수 생성.** 컴퓨터 안에서 진짜로 무작위인 것은 거의 없다. 소프트웨어는 유사난수 기법을 쓰는데, 그 출력이 확률적으로 보이고 값의 분포가 고르더라도 **작은 표본만 얻으면 앞뒤로 완벽히 외삽할 수 있는** 것이 많다. 2006년 Chris Anley는 100퍼센트 자바로 쓰인 인기 서버 Jetty의 세션 메커니즘이 토큰 예측에 취약함을 발견했다. 서버는 `java.util.Random`으로 토큰을 만들었고, 이는 **선형 합동 생성기**를 구현한다.

```java
synchronized protected int next(int bits) {
    seed = (seed * 0x5DEECE66DL + 0xBL) & ((1L << 48) - 1);
    return (int)(seed >>> (48 - bits));
}
```

앞 값에 상수를 곱하고 다른 상수를 더해 다음 값을 얻는 이 알고리즘은, 하나의 출력만 알면 다음 열을 쉽게 유도할 수 있고 약간의 정수론으로 이전 열도 유도할 수 있다. 서버에서 **세션 토큰 하나만 얻은 공격자가 현재와 미래의 모든 세션 토큰을 얻는다.** 여기서 흔한 실수 하나. 개발자는 더 길고 "강한" 토큰을 만들려고 생성기의 연속 출력 여러 개를 이어 붙이곤 한다. 그러나 이것은 대개 역효과다 — 연속 출력을 여러 개 얻으면 생성기의 내부 상태를 추론하기가 오히려 쉬워진다. PHP 5.3.2 이하의 세션 토큰은 클라이언트 IP, 생성 시각(초), 마이크로초, 그리고 선형 합동 생성기에 기반했는데, 소셜 사이트가 사용자의 로그인 시각과 IP를 노출하면 미지 값 상당수가 좁혀졌다.

**무작위성의 품질 검사.** 육안이나 약간의 수작업으로 패턴이 보일 때도 있지만, 일반적으로는 더 엄밀한 통계적 가설 검정을 쓴다. "토큰이 무작위로 생성된다"는 가설을 세우고, 무작위라면 특정 성질을 보일 검정들을 적용해, 관측된 특성이 나올 확률이 유의수준 아래로 떨어지면 가설을 기각한다. 이때 두 가지 주의가 결과 해석을 가른다.

- **완전히 결정론적으로 생성된 토큰이 통계 검정을 통과할 수 있다.** 선형 합동 생성기나 순차 번호의 해시는 검정을 통과하는 출력을 내지만, 알고리즘과 내부 상태를 아는 공격자는 앞뒤로 완벽히 외삽한다. 검정 통과가 예측 불가능성의 증명이 아니다.
- **검정에 실패한 토큰이 실제로는 예측 불가능할 수 있다.** 어떤 비트가 검정에 실패한다는 것은 그 위치의 비트열이 진짜 무작위에서 나오기 어려운 특성을 지녔다는 뜻일 뿐, 다음 토큰의 그 비트를 맞히는 일은 눈먼 추측과 별로 다르지 않을 수 있다. 다수의 비트를 **동시에** 맞혀야 한다면 성공 확률은 극히 낮아진다.

검정은 토큰의 각 문자·비트를 개별로 본다. 구조화된 토큰의 큰 부분이 무작위가 아니어도, **무작위성 검정을 통과하는 비트가 충분히 많으면** 그 자체로는 약점이 아니다. 1,000비트 토큰에서 50비트만 검정을 통과한다면, 그 토큰은 검정을 완전히 통과하는 50비트 토큰과 다르지 않다.

### 23.2.3 암호화된 토큰의 오용

어떤 애플리케이션은 사용자에 관한 의미 있는 정보를 담되, 그것을 발급 전에 **암호화해서** 의미 있는 토큰의 문제를 피하려 한다. 사용자가 모르는 비밀 키로 암호화하니 견고해 보인다 — 사용자는 복호화도, 내용 조작도 못 할 것이다. 그러나 **암호화 알고리즘과 애플리케이션의 처리 방식에 따라, 복호화 없이도 의미 있는 내용을 조작하는 것이 가능하다.** 기괴하게 들리지만 실제로 성립하는 공격이고, 수많은 실제 애플리케이션이 취약했다.

**ECB 암호.** 암호화 토큰을 쓰는 애플리케이션은 대칭 알고리즘을 쓴다. 그중 **전자 코드북(ECB)** 방식은 평문을 같은 크기의 블록(예: 8바이트)으로 나눠 각 블록을 같은 키로 독립 암호화한다. 특징은 **같은 평문 블록이 항상 같은 암호문 블록이 된다는 것.** 서점 토큰이 여러 의미 성분을 담는다고 하자.

```
rnd=2458992;app=BookStoreEUR_1;uid=218;username=joe;time=634430423694715
```

암호화하면 무의미해 보이고 통계 검정을 통과할 것이다. 그러나 8바이트 블록 단위이므로 평문 블록과 암호문 블록이 1:1로 대응한다. 각 암호문 블록이 항상 같은 평문으로 복호화되므로, **공격자는 암호문 블록 순서를 조작해 대응 평문을 의미 있게 바꿀 수 있다.** 둘째 블록을 넷째 블록 뒤에 복제하면 복호화된 토큰의 `uid` 값이 바뀐다. 애플리케이션이 복호화된 토큰의 일부(예: `uid`)만 검사한다면, 원래 218이 아니라 992 사용자의 문맥에서 요청을 처리한다.

더 신뢰할 만한 변형은, **수치가 알맞은 오프셋에 들어가도록 사용자명을 등록하는 것.** `joe1` 같은 사용자명을 등록해 발급받은 토큰에서, 그 사용자명의 숫자 `1`이 담긴 블록을 복제해 기존 `uid` 블록을 대체하면 `uid=1`이 된다. 알맞은 사용자명 범위를 등록하며 이를 반복하면 유효 `uid` 전 범위를 훑어 모든 사용자로 행세할 수 있다. ECB 조작은 순수 블랙박스에서 식별·익스플로잇이 어렵다 — 토큰 안의 암호문 블록을 눈먼 채 복제·이동하며 자기 문맥에, 남의 문맥에, 혹은 아무 세션에도 남지 않는지를 볼 뿐이다.

**CBC 암호와 비트 플리핑.** ECB의 결함이 **암호 블록 체이닝(CBC)**을 낳았다. CBC는 각 평문 블록을 암호화하기 전에 **앞 블록의 암호문과 XOR한다.** 같은 평문 블록이 같은 암호문이 되는 것을 막는다. 복호화 때는 각 복호 블록을 앞 암호문 블록과 XOR해 원래 평문을 복원한다. DES·AES를 CBC 모드로 흔히 쓴다. 그러나 웹에서 CBC 토큰을 쓰는 방식 때문에, 공격자가 키 없이도 복호 토큰의 일부를 조작할 수 있다. 서점의 CBC 토큰을 이렇게 하자.

```
rnd=191432758301;app=eBookProdTC;uid=216;time=6343303;
```

공격자가 **암호문(자기가 받은 토큰)의 일부를 바꾸면**, 그 블록 자체는 쓰레기로 복호화된다. 그러나 **바로 다음 블록**은 바뀐 암호문과 XOR되므로 **변형됐지만 여전히 의미 있는 평문**으로 복호화된다. 즉 한 블록을 조작하면 그 다음 블록의 복호 내용을 체계적으로 바꿀 수 있다. 공격자가 토큰을 한 문자씩 바꿔 보내면 복호 결과는 다음처럼 나온다(`????`는 쓰레기).

```
????????32758321;app=eBookProdTC;uid=216;time=6343303;
rnd=1914????????;aqp=eBookProdTC;uid=216;time=6343303;
rnd=191432758301;app=eBa????????;uie=216;time=6343303;
rnd=191432758301;app=eBa????????;uid=226;time=6343303;
```

공격자는 복호 값을 직접 보지 못하지만, 애플리케이션이 그것을 처리하고 그 결과가 응답에 나타난다. 애플리케이션이 `uid`만 검사한다면 네 번째 예가 성공해 216이 아니라 226 사용자로 처리된다. 이 취약점은 토큰 전체에 대해 "비트 플리퍼" 페이로드로 한 문자 위치마다 각 비트를 뒤집는 공격(바이트당 8요청)으로 거의 항상 식별된다. 공격 초반 요청들은 응답을 바꾸지 않고(토큰 앞부분이 신원 식별에 안 쓰인다는 뜻), 많은 요청은 로그인 페이지로 리다이렉트되며(토큰이 무효화됨), 그 사이에 **유효 세션이되 원래 신원이 아닌** 응답의 구간이 나타난다. 이것이 `uid`를 담은 블록이다. "알 수 없는 사용자"가 나오면 그 `uid`가 실재하지 않은 것이고, 다른 등록 사용자명이 나오면 공격이 결정적으로 성공한 것이다.

여기에 한 가지 지렛대가 더 있다. 애플리케이션이 대칭 암호로 변조를 막을 때, 같은 알고리즘·키를 애플리케이션 전체에 쓰는 일이 흔하다. 이때 어떤 기능이든 **임의의 암호문의 복호 값을 사용자에게 노출하면**, 그것을 지렛대 삼아 세션 토큰을 포함한 모든 보호 문자열을 완전히 복호화할 수 있다. 실제로 한 애플리케이션은 파일 다운로드에서 파일명을 암호화했는데, 삭제된 파일을 요청하면 **오류 메시지가 복호화된 파일명을 보여 주었다.** 이 동작으로 임의 암호문의 평문을 알아낼 수 있었고, 텍스트 사용자명·역할을 담은 토큰을 조립해 관리자 세션을 만들 수 있었다. 이런 "노출(reveal)" 오라클과 패딩 오라클 측면 채널은 암호화 토큰을 침해하는 또 다른 길이다(상세는 이 책의 범위 밖 주제로, 30장의 오류 노출과 31장의 서버 공격이 인접 개념을 다룬다).

이 대목이 20.9절과 맞물린다. 20.9절은 쿠키에 **무결성 통제가 없다**는 것을 결론으로 남겼고, 그 방어의 하나로 "무결성을 애플리케이션 계층에서 얹으라 — 서명·암호화하라"를 제시하면서 "다만 암호화된 토큰이 새로운 공격면을 만드는 경우가 있고, 23.2절이 그것을 다룬다"고 예고했다. 여기가 그 자리다. **암호화는 기밀성을 주지만 무결성을 주지 않는다.** ECB 블록 조작과 CBC 비트 플리핑은 둘 다 "복호화 없이 조작"이라는 같은 결론의 두 얼굴이다. 무결성이 필요하면 **암호화가 아니라 인증된 암호화나 서명(MAC)**이 답이며, 강화 절(23.6)이 그 방향을 정리한다.

**표 23-2. 토큰 생성의 세 약점과 공격 (WAHH 7장 "Weaknesses in Token Generation" 기준)**

| 약점 | 공격자가 하는 일 | 결정적 지표 | 대응(→23.6) |
|---|---|---|---|
| 의미 있는 토큰 | 디코드해 성분 파악 → 남의 값 조립 | hex/Base64로 풀리는 구조, 사용자명·역할 노출 | 토큰에 의미·구조를 담지 않음 |
| 예측 가능(은닉 시퀀스) | 디코드 후 차분으로 시퀀스 복원 | 값 사이 일정한 차분 | CSPRNG, 큰 값 공간 |
| 예측 가능(시각 의존) | 시각 정보와 짝지어 범위 좁힘 | 시간 경과 대비 값 도약 | 시각을 유일 엔트로피로 쓰지 않음 |

## 23.3 토큰 처리의 약점 — 네트워크 노출, 로그 노출, 잘못된 토큰-세션 매핑

토큰이 아무리 무의미하고 예측 불가능해도, 생성 뒤 **부주의하게 다뤄지면** 세션 메커니즘은 활짝 열린다. 토큰이 어떤 수단으로든 공격자에게 노출되면, 예측이 불가능해도 세션이 탈취된다. "우리는 SSL을 쓰니 토큰이 제3자에게 노출되지 않는다"는 믿음은 틀렸다 — SSL이 있어도 평문 전송이 일어나는 실수가 여럿 있고, 사용자를 겨냥한 직접 공격도 있다.

### 23.3.1 네트워크상의 노출

세션 토큰이 **암호화되지 않은 채 네트워크로 오가면**, 적절히 위치한 도청자가 토큰을 얻어 정당한 사용자로 행세한다. 도청에 적합한 위치는 사용자의 로컬 네트워크, 사내 IT 부서, ISP, 인터넷 백본, 애플리케이션 측 ISP, 호스팅 조직의 IT 부서 — 그 각각의 정규 인력과, 인프라를 침해한 외부 공격자 모두를 포함한다. 이 노출의 상세한 지형, 그리고 HTTPS를 부분적으로만 쓸 때 토큰이 새는 여러 경로 — 로그인만 HTTPS로 하고 이후 HTTP로 되돌아가는 웹메일형 패턴, 사전 인증 페이지에서 발급된 토큰이 로그인 후에도 갱신되지 않는 패턴, 전면 HTTPS라도 포트 80이 열려 있거나 공격자가 평문 요청을 유도할 수 있는 경우, 혼합 콘텐츠(HTTPS 페이지가 HTTP로 이미지·스크립트를 불러 그 요청에 쿠키가 실리는 것) — 는 **19.10절**이 상세히 다뤘다. Firesheep 도구가 웹메일형 패턴의 세션 탈취를 손쉽게 만든 사례도 그 절에 있다.

여기서는 세션 관점의 결론만 확정한다. **평문으로 전송된 토큰은 오염된 것(tainted)으로 간주해야 한다** — 사용자 신원을 보증하지 못한다. 그리고 확인해야 할 것은 다음이다. 정상적 사용 흐름에서 토큰이 한 번이라도 평문으로 오가는가. 쿠키를 쓴다면 `Secure` 플래그가 설정되어 평문 전송을 원천 차단하는가(→ 20.6.3). 시작 페이지가 HTTP이고 로그인부터 HTTPS로 바뀐다면, 로그인 뒤 새 토큰이 발급되는가 아니면 HTTP 단계의 토큰이 그대로 인증 세션을 추적하는가. 인증 세션의 토큰이 서버에 HTTP로 전송된 경우, 그 토큰이 계속 유효한가 아니면 즉시 종료되는가.

### 23.3.2 로그상의 노출

네트워크 평문 전송 다음으로 토큰이 무단 열람에 노출되는 가장 흔한 곳은 **각종 시스템 로그**다. 드물지만 결과는 대개 더 심각하다 — 로그는 도청 위치에 있는 한 사람이 아니라 훨씬 넓은 범위의 잠재 공격자에게 열리기 때문이다. 두 가지 원인이 있다.

**첫째, 세션 모니터링·관리 기능.** 관리자나 지원 인력이 런타임 상태를 모니터링·통제하는 기능 — 서점 고객센터 상담원이 문제를 겪는 고객을 돕느라 사용자명으로 세션을 찾아 세부를 보는 기능 — 이 실제 세션 토큰을 노출하는 일이 잦다. 그리고 그 기능이 허술하게 보호되어, 무단 사용자가 현재 세션 토큰 목록에 접근해 **모든 사용자의 세션을 탈취**할 수 있다.

**둘째, URL을 통한 토큰 전송.** 애플리케이션이 쿠키나 POST 본문이 아니라 **URL 쿼리 문자열**로 토큰을 나르면, 그 토큰은 무단 접근이 가능한 여러 로그에 남는다.

```
https://www.example-books.com/account;jsessionid=F27ED2A6AAE4C6DA409A3044E79B8B48?category=327
```

`inurl:jsessionid` 검색이 이런 애플리케이션을 수천 개 드러낸다. 이 방식일 때 토큰이 남는 곳은 다음과 같다.

- 사용자 브라우저 히스토리
- 웹 서버 로그
- 사내·ISP 프록시 서버 로그
- 호스팅 환경의 리버스 프록시 로그
- 사용자가 외부 링크를 따라간 서버의 **Referer 로그**

마지막 항목이 **16.4절**이 다룬 로그 프라이버시 문제의 정확한 재현이다. 16.4절은 로그가 무엇을 누출하는지, 특히 `GET` 쿼리 문자열에 담긴 비밀이 어떻게 새는지를 다뤘다. URL에 담긴 세션 토큰이 바로 그 비밀이다. 사용자가 외부 링크를 클릭하거나 브라우저가 외부 리소스를 로드하면, **그 토큰이 `Referer` 헤더에 실려** 제3자 서버로 간다. 서점이 URL로 토큰을 나른다면, 공격자는 자기가 통제하는 서버로의 링크를 게시판·후기·문의 기능에 심어 두고, 사용자가 그 링크에 닿는 순간(클릭하거나, HTML 메일의 이미지가 로드되거나) **실시간으로 사용자의 세션 토큰을 Referer 로그로 받는다.** 받은 토큰마다 세션을 탈취하는 스크립트를 돌려 스팸 발송·개인정보 수확·비밀번호 변경을 자동으로 수행한다.

주의할 점. HTTPS 페이지에서 외부 링크를 따라갈 때 브라우저가 `Referer`를 붙이는지는 브라우저·조건마다 다르지만, **URL에 놓인 민감 데이터는 SSL을 써도 Referer 로그 누출에 취약**하다는 결론은 변하지 않는다. 그래서 강화의 철칙은 하나다 — **세션 토큰을 절대 URL에 두지 않는다**(→ 23.6).

### 23.3.3 토큰과 세션의 잘못된 매핑

토큰 생성·처리가 견고해도, **토큰과 개별 사용자 세션을 잇는 방식**의 약점에서 취약점이 생긴다.

**동시 세션 허용.** 가장 단순한 약점은 같은 계정에 여러 유효 토큰이 동시에 배정되는 것이다. 거의 모든 애플리케이션에서 한 사용자가 동시에 둘 이상의 세션을 가질 정당한 이유는 없다. 물론 브라우저 창을 닫거나 다른 컴퓨터로 옮기며 활성 세션을 버리는 일은 흔하다. 그러나 한 사용자가 **동시에** 두 세션을 쓰는 것으로 보이면 대개 보안 침해의 신호다 — 자격증명을 남에게 줬거나, 공격자가 자격증명을 얻었거나. 두 경우 모두 동시 세션 허용은 바람직하지 않다. 사용자가 나쁜 관행을 불편 없이 지속하게 하고, 공격자가 탈취한 자격증명을 **탐지 위험 없이** 쓰게 한다.

**정적 토큰.** 관련되지만 뚜렷이 다른 약점. 세션 토큰처럼 보이고 처음엔 그렇게 작동하는 듯하지만 실은 아닌 것이다. 각 사용자에게 토큰이 하나 배정되고, **로그인할 때마다 같은 토큰이 재발급된다.** 애플리케이션은 최근 로그인 여부와 무관하게 그 토큰을 늘 유효한 것으로 받아들인다. 세션이라는 개념 자체를 오해한 것이다. 대개 허술하게 설계된 "로그인 상태 유지" 기능의 구현으로 나타나고, 정적 토큰은 지속 쿠키에 저장된다(→ 22.4). 게다가 그 토큰 자체가 예측 공격에 취약하면 사태는 훨씬 심각해진다 — 현재 로그인한 사용자의 세션이 아니라 **모든 등록 사용자의 계정을 영구히** 침해하는 공격이 된다.

**세션 밖에서 결정되는 사용자 문맥.** 더 근본적인 결함. 사용자명과 무작위 성분으로 의미 있는 토큰을 만든 경우를 보자.

```
dXNlcj1qb2U7cjE9MTMwOTQxODEyMTM0NTkwMTI=
```

Base64로 풀면 다음이 된다.

```
user=joe;r1=13094181213459012
```

`r1` 성분을 충분히 분석해 **예측 불가능하다**고 결론지었다 하자. 그럼에도 애플리케이션의 세션 처리 로직이 어긋나 있으면, 공격자는 **아무 유효한 `r1`과 아무 `user` 값**을 제출하는 것만으로 지정한 사용자의 보안 문맥에서 세션에 접근할 수 있다. 이것은 본질적으로 **접근 제어 취약점**이다(→ 24장) — 접근 결정이 세션 밖의, 사용자가 제공한 데이터로 이뤄지기 때문이다. 애플리케이션은 토큰을 "요청자가 유효한 세션을 수립했다"는 표지로 쓰지만, 그 세션이 처리되는 **사용자 문맥은 세션의 본질적 속성이 아니라 매 요청 다른 수단으로 결정되고, 그 수단을 요청자가 직접 통제**한다. 무작위 성분의 예측 불가능성은 여기서 아무것도 지키지 못한다.

**표 23-3. 토큰-세션 매핑의 세 결함 (WAHH 7장 "Vulnerable Mapping of Tokens to Sessions" 기준)**

| 결함 | 무엇이 잘못됐나 | 공격자가 얻는 것 | 확인 방법 |
|---|---|---|---|
| 동시 세션 허용 | 한 계정에 다중 유효 토큰 | 탈취 자격증명을 탐지 없이 사용 | 두 곳에서 로그인, 둘 다 유효한가 |
| 정적 토큰 | 매 로그인 같은 토큰 재발급 | 모든 등록 계정을 영구 침해 | 로그인·로그아웃 반복, 토큰이 늘 같은가 |
| 세션 밖 문맥 결정 | 사용자 문맥이 요청 데이터로 결정 | 임의 사용자로 행세 | `user` 성분만 바꿔 제출, 수용되는가 |

> **이 절이 뒷받침하는 것**
>
> - 네트워크상 토큰 노출의 전체 지형 → **19.10** (네트워크상의 토큰 노출과 혼합 콘텐츠), **20.6.3** (`Secure`가 막는 것)
> - URL 토큰이 Referer·프록시·히스토리에 남는 경로 → **16.4** (로그가 누출하는 것), **14.8** (캐시에 남는 개인화 응답과의 대조)
> - 세션 밖에서 문맥이 결정되는 것 → **24장** (접근 제어 — 요청 데이터로 접근을 결정하는 결함)

## 23.4 취약한 세션 종료와 세션 고정

### 23.4.1 취약한 세션 종료

세션을 제대로 끝내는 일은 두 이유로 중요하다. **첫째, 세션의 수명을 필요한 만큼 짧게 유지하면 공격자가 유효 토큰을 포착·추측·오용할 기회의 창이 줄어든다.** 둘째, 사용자가 더는 필요 없는 세션을 무효화할 수단을 얻어, 공유 컴퓨터 환경에서 자기 세션을 지킬 책임을 일부 진다. 종료의 주된 약점은 이 두 목표를 못 지키는 것이다.

**세션 만료 미비.** 어떤 애플리케이션은 효과적 만료를 강제하지 않는다. 한 번 만든 세션이 마지막 요청 뒤 며칠이 지나도록 유효하다. 토큰에 익스플로잇이 매우 어려운 시퀀싱 결함이(예: 유효 토큰당 10만 추측) 있더라도, 공격자는 **최근 애플리케이션에 접근한 모든 사용자의 토큰을 잡을** 수 있게 된다. 만료가 짧으면 성립하지 않았을 공격이다.

**로그아웃 미비.** 세 갈래로 나타난다. 로그아웃 기능이 아예 구현되지 않아 사용자가 세션을 무효화할 수단이 없는 경우. 로그아웃이 서버 세션을 실제로 무효화하지 않는 경우 — 서버가 `Set-Cookie`로 브라우저의 토큰을 지우지만, 사용자가 계속 그 토큰을 제출하면 서버가 여전히 받아들인다. 가장 나쁜 경우는 로그아웃 클릭이 서버에 전달조차 되지 않고 **클라이언트 사이드 스크립트가 쿠키만 비우는** 것 — 이후 요청이 로그인 페이지로 돌아가니 로그아웃된 것처럼 보이지만, 그 쿠키에 접근한 공격자는 사용자가 로그아웃하지 않은 듯 세션을 쓴다. 인증 없이 민감 데이터를 쌓는 서점의 손님 세션에도 로그아웃에 해당하는 종료 수단이 없는 일이 흔하다.

종료를 검사할 때 함정은 **클라이언트 측 토큰에 일어나는 일에 현혹되는 것**이다. 새 `Set-Cookie`로 쿠키를 무효화하든, 클라이언트 스크립트가 지우든, 만료 시각 속성을 붙이든 — 세션 종료의 관점에서 클라이언트 브라우저 안의 토큰에 무슨 일이 일어나는지는 거의 중요하지 않다. 확인할 것은 **서버 측에서 만료가 구현되는가**다. 유효 토큰을 얻고, 한동안 쓰지 않다가 보호 페이지를 요청해 여전히 활성인지 본다. 로그아웃 뒤 옛 토큰을 재사용해 여전히 유효한지 본다. 로그아웃 후에도 토큰이 유효하면, 사용자는 "로그아웃"했어도 일부 세션 탈취에 여전히 취약하다.

### 23.4.2 세션 고정

세션 고정은 토큰-세션 매핑 결함의 특수하고 중요한 형태다. 20.9절(쿠키 인젝션)이 이 공격의 **전달 경로**를 다뤘다 — 공격자가 어떻게 피해자 브라우저에 임의의 쿠키를 심는가. 여기서 공격의 **구조 전체**를 완성한다.

세션 고정 공격의 뼈대는 세 단계다.

1. **공격자가 애플리케이션에서 유효한 세션 토큰을 직접 얻는다.** 서점의 시작 페이지에 접속하면 익명 토큰이 발급된다.
2. **공격자가 그 토큰을 피해자의 브라우저에 고정시킨다.** 이 단계가 20.9절의 쿠키 인젝션 기법 중 하나를 쓴다 — 선호 저장 기능, 헤더 인젝션, 관련 도메인 XSS, 능동적 중간자. 토큰이 URL 파라미터로 실린다면 20.4절의 fat URL을 통해 피해자에게 그 URL을 건넨다.
3. **피해자가 그 토큰으로 로그인한다.** 애플리케이션이 로그인 시 새 토큰을 발급하지 않으면, 피해자의 인증된 세션은 **공격자가 아는 바로 그 토큰**에 묶인다. 공격자는 그 토큰으로 피해자의 인증 세션을 탈취한다.

이 공격의 결정적 성립 조건은 **애플리케이션이 인증 성공 후에도 토큰을 갱신하지 않는다는 것.** 익명이던 세션이 로그인으로 인증 세션으로 "승격"될 뿐 토큰은 그대로면, 공격자가 미리 심은 토큰이 그대로 인증 세션의 열쇠가 된다. 22장에서 본 인증의 견고함은 여기서 아무 소용이 없다 — 공격자는 피해자의 비밀번호를 몰라도, 피해자가 **자기 비밀번호로** 인증한 세션을 손에 넣는다.

고정 취약점의 확인은 다음과 같다. 애플리케이션이 미인증 사용자에게 토큰을 발급하면, 토큰을 얻고 로그인해 **로그인 뒤 새 토큰이 발급되는지** 본다. 발급되지 않으면 고정에 취약하다. 미인증 사용자에게 토큰을 발급하지 않더라도, 로그인해 토큰을 얻은 뒤 로그인 페이지로 되돌아가 **같은 토큰으로 다른 사용자로 재로그인**했을 때 새 토큰이 안 나오면 역시 취약하다. 형식만 유효한 **날조된 토큰**으로 로그인이 되면 — 애플리케이션이 스스로 발급하지 않은 값으로 인증 세션을 만들면 — 이 역시 고정에 취약하다. 로그인이 없는 서점이라도 손님이 개인·결제 정보를 쌓고 "주문 확인" 페이지에서 그것을 되보는 흐름이 있으면, 익명 사용 중 설정된 토큰이 나중에 그 민감 정보를 되불러올 수 있는지로 같은 검사를 한다.

세션 고정의 방어는 단 하나의 원칙으로 요약된다 — **인증 성공 후 항상 새 세션을 만든다**(→ 23.6). 로그인을 안 쓰지만 민감 데이터를 받는 경우엔 그 데이터 제출 시퀀스를 짧게 유지하고, 그 첫 페이지에서 새 세션을 만들며(필요하면 장바구니 같은 데이터를 옮겨 복사), 페이지별 토큰(23.6)으로 첫 페이지의 토큰을 아는 공격자가 이후 페이지에 접근하지 못하게 한다.

> **이 절이 뒷받침하는 것**
>
> - 고정 토큰의 전달 경로(쿠키 인젝션) → **20.9** (쿠키 인젝션의 네 경로), **20.4** (fat URL을 통한 URL 파라미터 전달)
> - 인증의 견고함이 세션 실패로 무효화된다는 것 → **22장** (인증 강화가 세션 갱신을 전제로 함)
> - 세션 밖 문맥 결정과의 연속성 → **23.3.3**, **24장** (접근 제어)

## 23.5 클라이언트의 토큰 하이재킹 노출

앞의 세 절은 공격자가 토큰을 **추측하거나, 네트워크·로그에서 줍거나, 매핑 결함을 이용**하는 경로였다. 그러나 공격자는 애플리케이션의 다른 사용자를 **직접 겨냥해** 피해자의 토큰을 포착하거나 오용할 수도 있다. 이 절은 그 클라이언트 측 노출을 세 갈래로 예고한다 — 상세한 익스플로잇은 각각 32~34장의 것이다.

**첫째, XSS를 통한 토큰 절취.** 크로스 사이트 스크립팅의 가장 뚜렷한 페이로드 하나는 사용자의 쿠키를 조회해 세션 토큰을 얻고, 그것을 공격자 서버로 전송하는 것이다. 페이로드가 실행되는 순간 피해자의 세션은 공격자의 것이 된다. `HttpOnly`(→ 20.6.4)가 이 특정 경로를 막지만 — 스크립트가 쿠키를 읽지 못하게 한다 — XSS가 존재하는 한 스크립트는 세션 문맥에서 **임의의 권한 있는 행위를 대신 수행**할 수 있으므로, 토큰을 훔치지 못해도 세션은 사실상 하이재킹된다. 이 형태 전부는 **32.3절**(XSS 페이로드로서의 세션 하이재킹)이 다룬다.

**둘째, 세션 고정과 CSRF.** 사용자를 겨냥한 다른 공격들도 세션을 하이재킹한다. 세션 고정(→ 23.4)은 공격자가 아는 토큰을 사용자에게 먹이고 로그인을 기다린다. 크로스 사이트 요청 위조는 공격자가 통제하는 사이트에서 애플리케이션으로 조작된 요청을 보내고, **사용자 브라우저가 현재 쿠키를 자동 제출한다는 사실**을 이용한다. 쿠키를 세션 토큰 전송에 쓰는 애플리케이션은 CSRF에 취약할 수 있다 — 다른 애플리케이션의 페이지에서 온 요청이 사용자의 토큰 제출을 유발하는지 확인하면 된다. CSRF의 상세와 방어는 **33장**이 다룬다.

**셋째, 실시간 채널과 크로스 도메인.** 세션 하이재킹의 표면은 전통적 요청-응답을 넘어선다. WebSocket 커넥션이 핸드셰이크 때 쿠키를 자동으로 실어 보내면, 크로스 사이트 WebSocket 하이재킹이 성립한다(→ **33.7**). 애플리케이션이 세션 문맥에서 자바스크립트로 민감 데이터를 반환하면, JavaScript 하이재킹이 그것을 크로스 도메인으로 캡처한다(→ **34.4**). 이 채널들은 쿠키의 자동 제출이라는 같은 성질을, 20장이 다룬 것과 다른 전송 위에서 재현한다.

이 절이 짧은 이유는, 세션 토큰의 **생성·처리·종료**라는 이 장의 주제가 여기서 끝나고, 토큰을 겨냥한 **클라이언트 측 공격**이라는 새 주제가 시작되기 때문이다. 그 새 주제는 Part VII 전체(32~36장)가 받는다. 이 장은 다만, 아무리 견고하게 생성·처리·종료된 토큰이라도 **클라이언트가 뚫리면 무너진다**는 것을 표시해 둔다. 그래서 강화의 마지막 조각(23.6)은 XSS 감사를 세션 방어의 필수 항목으로 포함한다.

> **이 절이 뒷받침하는 것**
>
> - XSS 페이로드로서의 세션 하이재킹 → **32.3** (XSS 페이로드 — 세션 하이재킹, 권한 있는 행위)
> - 크로스 사이트 WebSocket 하이재킹 → **33.7**
> - JavaScript 하이재킹 → **34.4**
> - CSRF를 통한 세션 오용 → **33.2**, **33.4** (CSRF와 그 방어)

## 23.6 세션 관리 강화 — 강한 토큰 생성, 생애주기 전체 보호, 로그·모니터·경보

세션 관리를 안전하게 하려면 두 가지를 해야 한다 — **견고하게 토큰을 생성**하고, **생성부터 폐기까지 생애주기 전체에서 토큰을 보호**하는 것. 앞 절들의 취약점 두 범주에 정확히 대응한다.

### 23.6.1 강한 토큰 생성

토큰은 공격자가 통상적 방법으로 대량 표본을 얻더라도 남에게 발급된 토큰을 예측·외삽할 여지를 주지 않는 방식으로 생성되어야 한다. 가장 효과적인 생성 메커니즘은 **극히 큰 값 공간을 쓰고, 강한 유사난수원을 담아 값이 공간 전체에 고르고 예측 불가능하게 퍼지도록** 한다. 목표는 이렇다 — 큰 대역폭과 처리 자원을 가진 결연한 공격자조차 토큰의 유효 수명 안에 유효 토큰 하나를 추측하는 것이 극히 어려워야 한다.

**토큰은 서버가 해당 세션 객체를 찾는 식별자, 그 이상도 이하도 아니어야 한다.** 겉으로든 인코딩·난독화의 겹 아래로든, 아무 의미나 구조도 담아선 안 된다. 세션 소유자와 상태에 관한 모든 데이터는 토큰이 가리키는 **서버의 세션 객체**에 저장한다. 이것이 23.2.1(의미 있는 토큰)과 23.2.3(암호화 오용)을 원천에서 닫는다 — 담긴 의미가 없으면 디코드할 것도, 블록을 조작할 것도 없다.

난수원 선택에 주의한다. `java.util.Random` 같은 것은 많은 용도에 유용하지만 하나의 출력으로 앞뒤가 완벽히 외삽된다. 알고리즘이 **명시적으로 암호학적으로 안전하다(cryptographically secure)**고 기술되지 않았다면 예측 가능하다고 가정해야 한다. 강한 난수원은 엔트로피를 모으느라 다음 값 반환이 느려 고volume 애플리케이션엔 부족할 수 있다는 점도 고려한다.

가장 견고한 난수원에 더해, **요청별 정보를 엔트로피로 섞는 것**이 좋은 관행이다. 그 정보가 요청마다 유일하진 않아도 핵심 PRNG의 약점을 완화한다 — 요청의 출발지 IP·포트, `User-Agent` 헤더, 밀리초 단위 요청 시각. 효과적인 공식은 이렇다. **유사난수 + 위의 요청별 데이터 + 재부팅마다 새로 생성되어 서버만 아는 비밀 문자열**을 이어 붙이고, 이 문자열의 해시(예: SHA-256)를 취해 고정 길이 토큰으로 삼는다. 가장 변화가 큰 항목을 입력 앞쪽에 두면 해시의 눈사태 효과가 극대화된다. 유용한 사고 실험 — "내 유사난수원이 고장 나 항상 같은 값을 낸다면, 대량 표본을 얻은 공격자가 남의 토큰을 외삽할 수 있는가?" 위 공식이라면 대개 불가능하다. 출발지 IP·포트·`User-Agent`·시각이 방대한 엔트로피를 만들고, 그것을 다 알아도 **서버의 비밀 문자열** 없이는 대응 토큰을 만들 수 없기 때문이다.

### 23.6.2 생애주기 전체 보호 — 생성 → 전송 → 저장 → 사용 → 폐기

값이 예측 불가능한 토큰을 만들었다면, 이제 그것이 발급 대상 외 누구에게도 노출되지 않도록 생애주기 전체를 지켜야 한다.

**생성.** 위 23.6.1의 강한 생성. 인증 성공 시 **항상 새 세션을 만든다** — 이것이 세션 고정(23.4.2)을 완화하는 핵심이다. 로그인을 안 쓰지만 민감 데이터를 받는 서점 손님 흐름은, 그 시퀀스를 짧게 유지하고 첫 페이지에서 새 세션을 만들며 필요한 데이터(장바구니)를 옮긴다.

**전송.** 토큰은 **HTTPS로만** 전송한다. 평문으로 전송된 토큰은 오염된 것으로 간주한다. 쿠키를 쓰면 `Secure` 플래그로 브라우저가 평문으로 절대 보내지 않게 한다(→ 20.6.3). 가능하면 도움말·이미지 등 정적 콘텐츠까지 모든 페이지에 HTTPS를 쓰고, 그렇지 않다면 민감 콘텐츠(로그인 페이지 포함) 요청을 HTTPS로 리다이렉트한다. 정적 리소스는 대개 민감하지 않으므로, 쿠키 범위 지시를 함께 써서 그 리소스 요청엔 토큰이 실리지 않게 `Secure` 쿠키를 뒷받침한다. **토큰을 절대 URL에 두지 않는다** — URL 전송은 세션 고정의 손쉬운 매개이자 각종 로그 노출(23.3.2)의 원인이다. 쿠키가 비활성인 브라우저를 지원해야 한다면, URL 대신 **모든 내비게이션을 POST로 하고 토큰을 HTML 폼의 히든 필드**에 담는다.

**저장.** 세션 상태는 서버의 세션 객체에 두고, 토큰은 그 식별자로만 쓴다(23.6.1). 관리·진단 기능이 세션 토큰을 볼 수 있게 한다면 그 기능을 무단 접근에서 견고하게 방어하고, **대개 실제 토큰을 표시할 필요가 없으므로** 소유자 식별에 충분한 정보만 보이고 토큰 값 자체는 감춘다.

**사용.** **동시 로그인을 막는다** — 로그인할 때마다 다른 토큰을 발급하고 기존 세션을 로그아웃한 것처럼 폐기한다. 옛 토큰은 잠시 보관해, 이후 그 토큰으로 온 요청엔 "다른 위치에서 로그인해 세션이 종료되었다"는 보안 경고를 낸다. **서버가 모르는 임의 토큰은 받지 않는다** — 브라우저에서 즉시 취소하고 시작 페이지로 돌린다. 자금 이체 같은 중대 동작 전에는 **2단계 확인이나 재인증**을 요구해 CSRF와 여러 세션 공격을 어렵게 만든다.

**폐기.** **로그아웃을 구현**해 서버가 보유한 모든 세션 자원을 처분하고 토큰을 무효화한다. **비활동 후 세션 만료**(예: 10분)를 구현해 명시적 로그아웃과 같은 결과를 낸다. 종료는 반드시 **서버 측**에서 일어나야 한다 — 클라이언트의 쿠키를 비우는 것으로는 부족하다.

**쿠키 범위.** 세션 쿠키의 `domain`·`path` 범위를 **가능한 한 좁게** 설정한다(→ 20.8). 그 범위 안의 도메인·경로로 다른 애플리케이션이나 신뢰할 수 없는 기능이 접근되지 않아야 한다. 과도하게 넓은 범위는 대개 개발자가 아니라 허술하게 설정된 플랫폼·서버가 만든다. 서브도메인에 특히 주의하고, 필요하면 조직의 도메인·경로 명명 체계 자체를 바꾼다.

**클라이언트 측 방어.** 코드베이스를 엄밀히 감사해 XSS를 제거한다(→ 32장). 대부분의 XSS는 세션 메커니즘 공격에 익스플로잇되며, 특히 저장형(2차) XSS는 세션 오용·하이재킹에 대한 거의 모든 방어를 무력화한다. CSRF는 쿠키에만 의존해 토큰을 전송하지 않음으로써 방어한다 — 토큰을 늘 HTML 폼의 히든 필드로 전송하면, 공격자는 토큰 값을 이미 알지 않는 한 무단 동작을 일으키는 폼을 만들 수 없다(→ 33.4).

**페이지별 토큰.** 세션 토큰에 더해 **페이지별 토큰**을 쓰면 세밀한 통제가 가능하다. 사용자가 애플리케이션 페이지를 요청할 때마다(이미지는 제외) 새 페이지 토큰이 생성되어 쿠키나 히든 필드로 전달되고, 매 요청 직전 값과 대조된다. 불일치면 **세션 전체를 종료**한다. 온라인 뱅킹 같은 가장 보안 중요한 애플리케이션이 이를 쓴다. 뒤로·앞으로 버튼과 다중 창 사용에 제약을 주지만, **세션 고정을 효과적으로 막고**, 하이재킹된 세션을 정당한 사용자와 공격자가 동시에 쓰면 각자 한 번 요청한 직후 차단된다. 페이지별 토큰은 사용자의 이동을 추적하고, 정의된 순서 밖의 기능 접근을 탐지해 일부 접근 제어 결함(→ 24장)도 막는다.

### 23.6.3 로그, 모니터, 경보

세션 관리 기능은 로깅·모니터링·경보와 긴밀히 통합되어 이상 활동을 기록하고 방어 조치를 가능하게 해야 한다.

- **무효 토큰을 담은 요청을 모니터링한다.** 가장 예측 가능한 경우를 빼면, 남의 토큰을 추측하려는 성공적 공격은 대개 무효 토큰을 담은 대량 요청을 수반하며 로그에 뚜렷한 흔적을 남긴다.
- 세션 토큰에 대한 무차별 대입은 완전히 막기 어렵다 — 특정 계정·세션을 정지시켜 멈출 수 없기 때문이다. 무효 토큰 요청이 일정 수를 넘으면 **출발지 IP를 한동안 차단**하는 조치가 있으나, 한 사용자의 요청이 여러 IP에서 오거나(대형 ISP) 여러 사용자가 한 IP에서 올(NAT 뒤) 때 효과가 제한된다(→ 4.6, 20.2.3).
- 실시간으로 막지 못해도 **상세 로그와 관리자 경보**는 사후 조사와 대응을 가능케 한다.
- 가능하면 **사용자에게 세션 관련 이상을 알린다** — 동시 로그인, 페이지별 토큰으로 탐지된 하이재킹 정황. 이미 침해가 일어났더라도 사용자가 무단 이체 등을 확인할 수 있다.

**반응형 세션 종료.** 세션 메커니즘은 다른 여러 공격에 대한 강력한 방어로도 쓸 수 있다. 온라인 뱅킹 같은 곳은 이상 요청 — 수정된 히든 필드나 쿼리 파라미터, SQL 인젝션·XSS 문자열, 클라이언트 검증으로 차단됐어야 할 입력 — 을 받을 때마다 세션을 매우 공격적으로 종료한다. 물론 실제 취약점은 근원에서 고쳐야 하지만, 무효 요청마다 재인증을 강제하면 자동화를 써도 취약점 탐색 과정이 수십·수백 배 느려진다. 다만 이 방어에는 역설이 있고 — 정당한 침투 테스트도 같은 방식으로 느려진다 — 이것이 다음 절의 주제다.

> **이 절이 뒷받침하는 것**
>
> - `Secure`·쿠키 범위로 전송·저장을 지키는 것 → **20.6** (쿠키 속성), **20.8** (쿠키 범위 최소화)
> - CSRF를 쿠키 비의존으로 막는 것 → **33.4** (CSRF 방어 — 토큰, 재인증)
> - XSS 감사가 세션 방어의 필수라는 것 → **32.8** (XSS 방어)
> - 무차별 대입 IP 차단의 한계 → **4.6** (NAT와 X-Forwarded-For), **20.2.3** (IP를 보안 판정에 쓸 때)

## 23.7 세션 핸들링 메커니즘이 자동화 테스트를 막는 방식

앞 절 끝의 반응형 세션 종료는 흥미로운 물음을 남긴다. **방어자의 세션 핸들링이 자동화 테스트를 막는 것은 방어인가, 아닌가?**

먼저 사실을 정리한다. 자동화 공격 — 파라미터를 퍼징하고, 유효 식별자를 열거하고, 데이터를 수확하는 것(상세는 부록 B) — 은 많은 애플리케이션에서 별 문제 없이 적용된다. 그러나 **세션 핸들링 메커니즘**이 자동화의 장벽이 되는 상황이 있다. 세 가지 형태다.

- **방어적 세션 종료.** 테스트 중 애플리케이션이 예상 밖 요청에 반응해 테스트용 세션을 종료한다. 이후 테스트가 전부 무효가 된다.
- **요청마다 바뀌는 토큰.** 어떤 기능이 매 요청 바뀌는 토큰(예: 요청 위조를 막는 anti-CSRF 토큰 → 33.4)을 요구한다. 앞 응답에서 그 값을 얻어 다음 요청에 실어야 한다.
- **다단계 프로세스.** 테스트할 요청이 다단계 프로세스 안에 있어, 다른 요청들을 먼저 보내 애플리케이션을 적절한 상태로 만들어야만 그 요청이 제대로 처리된다.

이런 장벽은 원리적으로 **자동화 기법을 정교하게 다듬어** 우회할 수 있다. 직접 테스트 코드를 짜서 특정 토큰 처리나 다단계 메커니즘을 구현할 수도 있으나, 이 접근은 복잡하고 대형 애플리케이션에 잘 확장되지 않는다. 매 새 사례마다 새 코드를 짜야 한다는 것 자체가 자동화 사용의 큰 장벽이 되어, 결국 느린 수동 기법으로 되돌아가게 만든다. 실무 도구(예: 인터셉팅 프록시)는 이를 위해 세 요소를 조합한다 — **쿠키 병**(브라우저와 도구가 쓰는 쿠키를 추적), **요청 매크로**(로그인이나 토큰 획득 같은 사전 요청 시퀀스), **세션 핸들링 규칙**(요청 범위와 동작을 정의해, 세션이 유효한지 검사하고 무효면 매크로로 재로그인하고, 앞 응답에서 파라미터·토큰 값을 끌어와 갱신하며, 필요하면 사용자에게 브라우저 내 세션 복구를 요청). 이 조합은 세션이 종료되면 자동으로 재로그인하고, 물리 토큰의 숫자 입력이나 CAPTCHA 풀이가 필요한 로그인까지 다룬다.

이제 물음으로 돌아온다. 방어자 관점에서 이것은 방어인가.

**부분적으로는 방어다.** 무효 요청마다 재인증을 강제하면 취약점 탐색이 수십·수백 배 느려지고, 잔존 취약점이 실전에서 발견될 확률이 크게 낮아진다. 결정적이지 않은 다수의 공격자를 단념시킨다는 점에서, 22.10절의 CAPTCHA와 같은 종류의 **마찰**이다.

**그러나 근본적으로는 방어가 아니다.** 세 이유가 있다.

1. **실제 취약점을 고치지 않는다.** 반응형 종료는 취약점 탐색을 늦출 뿐, 취약점 자체는 근원에서 고쳐야 한다. 마찰이 있는 동안 취약점은 그대로 남아 있다.
2. **정당한 테스트도 같은 방식으로 막는다.** 합법적 침투 테스트가 실제 공격자와 똑같이 느려지면 그 효과가 급감한다. 그 결과 **이 메커니즘이 있을 때 production 코드에 더 많은 취약점이 남을 가능성이 높다** — 테스트가 덜 철저해지기 때문이다. 그래서 이 방어를 쓸 때는 **테스트 목적으로 쉽게 끌 수 있게** 하는 것이 권장된다.
3. **결연한 공격자에게는 자동화로 우회된다.** 앞서 본 쿠키 병·매크로·세션 핸들링 규칙의 조합이 바로 그 우회다. 강제 로그아웃을 탐지해 자동 재로그인하고 새 세션과 페이지를 돌려주는 확장을 짜면, 문제가 사라지진 않아도 상당히 완화된다.

정리하면, 세션 핸들링이 자동화를 막는 것은 **결연하지 않은 다수를 걸러내는 마찰이되, 결연한 공격자를 막는 벽도 아니고 취약점을 고치는 방어도 아니다.** 그것을 방어로 착각하면 두 가지 대가를 치른다 — 근본 취약점을 방치하고, 자기편의 테스트를 스스로 무력화한다. 22.10절이 CAPTCHA에 대해 내린 결론과 정확히 같은 구조다. 어느 마찰도 단독으로 완전하지 않고, 실제 방어(취약점 제거, 강한 토큰, 생애주기 보호)와 겹칠 때만 의미가 있다.

자동화 공격 일반의 구조 — 유효 식별자 열거, 데이터 수확, 퍼징, 그리고 세션 핸들링·CAPTCHA라는 자동화의 장벽 — 는 **부록 B**가 이어받아 다룬다.

> **이 절이 뒷받침하는 것**
>
> - 자동화의 장벽과 그 우회(쿠키 병·매크로·세션 규칙) → **부록 B** (자동화의 장벽 — 세션 핸들링, CAPTCHA)
> - 마찰과 실제 방어의 구분 → **22.10** (CAPTCHA의 실제 효과)와 같은 결론 구조
> - 요청마다 바뀌는 토큰 → **33.4** (anti-CSRF 토큰)

## 23.8 무상태 설계 — 처리 인스턴스가 상태를 갖지 않을 때의 보안 이점

이 장은 상태의 필요에서 출발했다(23.1). HTTP가 상태를 잃은 자리에 세션이 들어섰고, 그 세션 상태는 지금까지 암묵적으로 **서버가 보관하는 것**이었다. 이 마지막 절은 그 보관 방식 자체를 뒤집는 설계를 본다 — **처리 인스턴스가 상태를 갖지 않는(stateless)** 무상태 설계다. 클라우드 네이티브 애플리케이션의 핵심 원칙이자, SBD가 보안 이점으로 재해석한 것이다.

### 23.8.1 처리 인스턴스가 상태를 갖지 않는다는 것

클라우드 환경에서 애플리케이션을 운영하는 주된 조언은 **분리된 무상태 프로세스로 실행**하는 것이다. 무상태 프로세스는 요청 사이에 클라이언트 상태를 유지하지 않고, 데이터베이스나 분산 캐시 같은 **백킹 서비스**를 통해서만 통신한다.

서점 예로 보자. 고객이 먼저 『햄릿』을 장바구니에 담고, 나중에 『Secure by Design』을 담는다. 이 두 요청은 활성 인스턴스 집합이 처리한다. 잘 설계된 클라우드 애플리케이션은 **특정 인스턴스가 특정 클라이언트에 묶인다고 가정하지 않는다.** 첫 요청(『햄릿』)과 둘째 요청(『Secure by Design』)은 같은 인스턴스가 처리할 수도 있지만, 그것에 의존해선 안 된다. 둘째 요청은 다른 인스턴스가 처리할 수 있고 — 부하 급증에 대응해 방금 뜬, 첫 요청 때는 없던 인스턴스일 수 있다 — 똑같이 잘 동작해야 한다. 첫 인스턴스는 관리 루틴으로 이미 종료됐을 수도 있다. 어느 쪽이든 결과는 같아야 한다. 이를 위해 **프로세스는 호출 사이에 클라이언트 대화 상태를 저장하지 않는다.** 요청 처리의 모든 결과는 클라이언트로 돌려보내거나, 상태를 가진 백킹 서비스(대개 데이터베이스)에 저장한다.

무거운 처리는 작은 단계로 쪼개고, "가져왔으나 아직 구조화·분석 안 함" 같은 상태 플래그를 각 단계가 갱신한다. 로컬 파일시스템은 처리 중 임시 저장에 쓸 수 있으나 **주기억장치만큼 휘발적이고 신뢰할 수 없는 것으로** 취급한다 — 처리가 완료되어 결과가 백킹 데이터베이스에 커밋되기 전에는 영구 저장된 것으로 볼 수 없다. 프로세스는 장시간 처리 도중에도 언제든 중단·종료될 수 있다.

### 23.8.2 무상태 설계의 보안 이점과 대가

무상태 프로세스의 보안 이점은 CIA-T 세 축 모두에 걸친다.

- **가용성(Availability).** 무상태이고 (백킹 서비스 외) 아무것도 공유하지 않으면 부하에 따라 용량을 쉽게 늘리고 줄인다. 서버 몇 대를 더 띄우면 즉시 부하를 나눈다. 새 버전 서버를 띄우며 옛 서버를 죽여 무중단 배포도 한다.
- **무결성(Integrity).** **어느 서버든 언제든 죽일 수 있다는 것**이 무결성에 좋다. 특정 서버가 감염된 정황이 있으면 즉시 죽이고 교체한다. 진행 중이던 작업은 잃지만 데이터는 일관된 상태로 남고, 새 서버가 그 작업을 다시 한다. 이 능력은 뒤에서 볼 엔터프라이즈 보안의 3R(회전·재포장·수리 → 46.7)의 토대가 된다.
- **최소 권한과의 결합.** 설치·배포를 실행과 분리하면 최소 권한 원칙과 잘 맞는다(→ 46.3). 배포는 높은 권한이 필요하지만, 웹 애플리케이션 실행은 수신 소켓 열기, DB 소켓 열기, 임시 디렉터리 쓰기 정도의 좁은 권한이면 된다. 실행 프로세스가 좁은 권한만 가지면, 그 프로세스가 침해돼도 공격자가 할 수 있는 일이 애플리케이션의 의도된 동작 안으로 제한된다 — 시스템 자체의 무결성은 침해하지 못한다.

이 절이 이 장에 있는 이유는 23.1의 대안 논의와 짝을 이루기 때문이다. 23.1의 sessionless state는 상태를 **클라이언트로** 밀었고, 여기 무상태 설계는 상태를 **백킹 서비스로** 민다. 방향은 반대지만 둘 다 "처리 인스턴스에 상태를 두지 않는다"는 같은 규율을 공유한다. 세션 관점에서 함의는 분명하다 — **세션 상태를 개별 인스턴스의 메모리에 두면 무상태 설계와 충돌한다.** 세션 객체는 공유 백킹 서비스(분산 캐시·데이터베이스)에 두어야, 어느 인스턴스가 요청을 받아도 같은 세션을 본다. 그리고 이 규율이 세션에도 보안 이점을 준다 — 감염 정황이 있는 인스턴스를 세션 손실 없이 죽일 수 있다.

그러나 이 설계에는 **대가**가 있다. 상태를 처리 인스턴스 밖으로 밀면, 그 상태를 나르는 토큰이나 blob이 **스스로 상태를 담게** 되는 유혹이 생긴다 — sessionless state처럼 클라이언트가 상태 전체를 들고 다니는 형태다. 이때 토큰이 상태를 담는 순간 이 장 전반의 문제가 되돌아온다. 상태를 담은 토큰은 **위조**될 수 있고(23.2 — 의미 있는 토큰, 암호화 오용), **폐기**가 어려워진다(서버에 세션 객체가 없으니 무효화할 대상이 없다 — 23.4의 종료 문제가 새 형태로 재현된다). 서버가 세션 객체를 들고 있으면 로그아웃 한 번으로 그 객체를 지우면 되지만, 상태가 토큰 안에 있으면 그 토큰을 이미 가진 자를 막을 방법이 마땅치 않다. 무상태성은 확장성과 무결성을 주는 대신, **위조 방지와 폐기라는 두 부담을 토큰 설계로 떠넘긴다.** 그 부담을 인증된 암호화·서명·짧은 만료·서버 측 폐기 목록으로 어떻게 다루는가는 설계의 문제이고, **46.3절**(프로세스 분리 — 처리 인스턴스는 상태를 갖지 않는다)이 클라우드 사고의 맥락에서 이를 잇는다.

> **이 책의 범위를 넘어서**
>
> 상태를 담은 토큰이 위조 방지와 만료를 스스로 해결하도록, 토큰의 형식과 서명 방식을 표준화한 흐름이 존재한다. 서명된 클레임 집합을 토큰 안에 담아 서버가 상태를 보관하지 않고도 검증하는 방식이다. 이런 표준은 폐기의 어려움(서명이 유효한 한 서버가 능동적으로 무효화하기 어렵다)이라는 대가를 짧은 만료와 별도의 폐기 목록으로 다룬다. 이 책은 그 표준의 구체를 다루지 않는다 — 다만 이 장이 반복해 보인 원리, "토큰이 상태를 담으면 위조와 폐기가 문제가 된다"는 것이, 그 표준들이 씨름하는 바로 그 문제임을 표시해 둔다.

> **이 절이 뒷받침하는 것**
>
> - 처리 인스턴스가 상태를 갖지 않는 설계 → **46.3** (프로세스 분리 — 배포와 실행의 분리, 상태 없는 인스턴스)
> - 무상태성이 3R의 토대가 된다는 것 → **46.7** (엔터프라이즈 보안의 3R — 회전·재포장·수리)
> - 최소 권한과 실행 프로세스 격리 → **46.3**, **31장** (애플리케이션 서버·아키텍처)
> - 상태를 클라이언트로 미는 대안 → **23.1** (sessionless state), **26장** (클라이언트 사이드 상태 보호)

## 이 장의 요약

- **인증이 무엇이든 그 뒤를 잇는 것은 세션이다.** 인증 이후의 요청은 오직 세션 토큰으로만 그 인증에 연결되므로, 세션 관리가 깨지면 견고한 인증이 통째로 우회된다. 관리자 세션을 탈취하면 애플리케이션 전체가 넘어간다.
- **토큰은 발급되는 순간에 이미 깨질 수 있다.** 의미 있는 토큰은 디코드하면 사용자명·역할·시각이 드러나고, 예측 가능한 토큰은 은닉 시퀀스·시각 의존·약한 난수에서 앞뒤로 외삽되며, 암호화된 토큰조차 ECB 블록 조작과 CBC 비트 플리핑으로 복호화 없이 변조된다. 암호화는 기밀성을 줄 뿐 무결성을 주지 않는다.
- **견고하게 생성된 토큰도 처리에서 샌다.** 평문 네트워크 전송(→19.10), URL에 담겨 Referer·프록시·히스토리 로그에 남는 노출(→16.4), 그리고 동시 세션·정적 토큰·세션 밖에서 결정되는 문맥이라는 매핑 결함이 각각 토큰을 공격자에게 넘긴다.
- **세션 고정은 인증의 견고함을 무력화한다.** 공격자가 아는 토큰을 피해자에게 심고(→20.9의 쿠키 인젝션), 피해자가 그 토큰으로 로그인하면, 애플리케이션이 로그인 시 토큰을 갱신하지 않는 한 공격자가 인증 세션을 손에 넣는다. 방어의 핵심은 인증 성공 후 항상 새 세션을 만드는 것이다.
- **아무리 잘 만든 토큰도 클라이언트가 뚫리면 무너진다.** XSS는 토큰을 훔치거나 세션 문맥에서 권한 있는 행위를 수행하고(→32.3), CSRF·WebSocket 하이재킹·JavaScript 하이재킹(→33.7, 34.4)은 쿠키 자동 제출을 다른 전송 위에서 재현한다.
- **강화의 축은 둘 — 강한 생성과 생애주기 전체 보호다.** 토큰은 의미 없는 식별자로만 두고 CSPRNG와 큰 값 공간에 요청별 엔트로피와 서버 비밀을 섞어 만든다. 그리고 생성→전송(HTTPS·`Secure`·URL 금지)→저장(서버 세션 객체)→사용(동시 로그인 차단·재인증·페이지별 토큰)→폐기(서버 측 로그아웃·만료)의 매 단계를 지킨다.
- **세션 핸들링이 자동화를 막는 것은 마찰이지 방어가 아니다.** 취약점 탐색을 느리게 하지만 취약점 자체는 고치지 않고, 정당한 테스트도 똑같이 막으며, 결연한 공격자는 쿠키 병·매크로·세션 규칙으로 우회한다. CAPTCHA와 같은 결론이다 — 실제 방어와 겹칠 때만 의미가 있다.
- **무상태 설계는 상태를 처리 인스턴스 밖으로 밀어 CIA-T를 얻지만 대가를 치른다.** 어느 인스턴스든 죽여 교체할 수 있어 무결성과 가용성이 오르고 최소 권한과 맞물린다. 그러나 상태가 토큰 안으로 들어가면 위조 방지와 폐기라는 부담이 토큰 설계로 넘어온다.

## 이어지는 장

이 장은 세션이 깨지는 모든 방식을 훑고, 생애주기 전체를 지키는 강화로 닫았다. 그러나 세션이 완벽하게 관리되어 "이 요청이 누구에게서 왔는가"에 정확히 답하더라도, 아직 답하지 않은 물음이 하나 남는다 — **그 사람이 이 요청을 할 자격이 있는가.**

24장은 그 물음을 받는다. 접근 제어는 논리적으로 인증과 세션 관리 위에 세워진다. 인증이 신원을 확인하고, 세션이 그 신원을 여러 요청에 걸쳐 잇고 나면, 접근 제어가 **각 요청이 시도하는 동작을 허용할지**를 결정한다. 이 장의 23.3.3절이 이미 그 경계를 넘봤다 — 사용자 문맥이 세션 밖에서 결정되는 결함은 본질적으로 접근 제어 결함이었다. 24장은 완전히 보호되지 않은 기능, 식별자 기반 접근, 다단계 프로세스의 허점을 다루고, 다층 권한 모델로 그 결함들을 닫는다. 세션이 "누구"에 답한 자리에서, 접근 제어는 "무엇을 해도 되는가"에 답한다.
