# 19장. TLS 운영: 재개, 성능, 그리고 중간자

> **이 장에서 다루는 것**
>
> - 18.2절이 계산한 3왕복의 청구서를 어떤 처방들이 어떻게 갚는지, 그리고 각 처방이 그 대가로 무엇을 옮기는지
> - TLS 종료 지점을 사용자 쪽으로 옮기는 결정이 왜 성능 결정이자 신뢰 경계 결정인지
> - 압축·레코드 크기·인증서 사슬 길이처럼 순수하게 성능 문제로 보이는 설정들이 보안 판정에 개입하는 지점
> - HSTS가 무엇을 해결하고 무엇을 남기는지 — 특히 최초 접속의 창
> - TLS를 켠 뒤의 중간자 성립 조건. 표 1-7을 다시 쓰면 어떤 줄이 지워지고 어떤 줄이 남는가

18장은 HTTPS의 순서를 열고 검증을 펼쳤다. 그 장이 남긴 것은 두 가지다. 하나는 **청구서**다. 표 18-3이 계산한 TCP 1왕복 + TLS 2왕복, 그리고 그것이 새 커넥션마다 발생한다는 사실. 다른 하나는 **미완의 계산**이다. 17.10절이 "공격의 조건이 네트워크 접근에서 네트워크 접근 + PKI 공격으로 올라갔다"고 적고, 그 상승분이 검증 조건이 깨지는 만큼 깎인다고 덧붙인 뒤, 정확한 계산을 19.9절로 넘겼다.

이 장은 두 가지를 함께 다룬다. 그리고 그것이 이 장의 구조다. **왜냐하면 둘이 같은 대상의 두 얼굴이기 때문이다.**

1.6절이 표 하나를 남겼다. 왕복을 줄이려는 시도와 그 각각의 보안·운영 함의를 나란히 놓은 표다. 그 표의 한 줄이 이 장의 것이다. **"TLS 종료 지점을 사용자 쪽으로 옮긴다 → 평문 구간이 생기고 중간자가 정당화된다."** 그 줄에 붙은 절 번호가 19.2다. 성능 최적화의 목록과 보안 취약점의 목록이 거의 일대일로 대응한다는 1.6절의 관찰이, TLS라는 한 계층 안에서 가장 선명하게 확인되는 자리가 이 장이다.

그래서 이 장의 각 절은 두 번 읽혀야 한다. 첫 번째 읽기에서는 성능 처방이다. 재개는 왕복을 하나 없애고, 조기 종료는 왕복의 길이를 줄이고, 사슬 단축은 혼잡 윈도우 초과를 막는다. 두 번째 읽기에서는 신뢰 경계의 이동이다. 재개는 세션 비밀의 보관 장소를 옮기고, 조기 종료는 평문을 보는 주체를 늘리며, 사슬 단축은 검증의 재료를 줄인다. **어느 읽기도 다른 쪽을 대체하지 못한다.** 그리고 두 읽기를 합친 결과를 19.9절이 표 하나로 정리하며 Part IV를 닫는다.

## 19.1 세션 재개 — 세션 ID와 세션 티켓

18.2절의 표 18-3을 다시 펴 놓자. 이 절이 지우는 것은 그 표의 두 줄, **84밀리초와 112밀리초**다.

전체 핸드셰이크에서 그 두 줄이 하는 일은 하나다. **양쪽이 공유할 대칭 세션 키를 새로 만드는 것.** 서버가 인증서를 보내고(84밀리초), 클라이언트가 그것을 검증한 뒤 사전 마스터 비밀을 서버의 공개키로 암호화해 되돌려 보낸다(112밀리초). 17.4절이 혼합 암호 시스템으로 설명한 절차이고, 18.2절이 "공개키 연산이 쓰이는 자리는 한 곳뿐"이라고 적은 그 한 곳이다.

그렇다면 질문은 이렇게 선다. **이미 한 번 그 일을 한 상대와 다시 연결할 때, 그 일을 또 해야 하는가.**

TLS의 답은 "아니다"이며, 그 답을 구현하는 방식이 **세션 재개(session resumption)** 다. 전체 핸드셰이크의 비용 — 추가 지연과 계산 비용 — 이 보안 통신을 요구하는 모든 애플리케이션에 실질적인 성능 부담을 지운다는 것이 원서의 출발점이다. 그 부담을 덜기 위해 TLS는 **협상된 비밀 키 데이터를 여러 커넥션 사이에서 재사용하거나 공유하는 능력**을 제공한다.

재개 메커니즘은 두 종류가 있다. 먼저 나온 것이 세션 ID이고, 그 배포상의 문제를 해결하려고 나온 것이 세션 티켓이다.

### 세션 ID — 서버가 기억한다

첫 번째 재개 메커니즘인 **세션 식별자(Session Identifier)** 는 SSL 2.0에서 도입됐다. 동작은 단순하다.

1. 전체 핸드셰이크 도중, 서버가 `ServerHello` 메시지에 **32바이트 세션 식별자**를 실어 보낸다.
2. 서버는 내부적으로 세션 ID와 그에 대응하는 협상된 세션 파라미터의 **캐시**를 유지한다.
3. 클라이언트도 그 세션 ID를 저장한다.
4. 다음 세션의 `ClientHello`에 그 ID를 실어 보낸다. **이것은 "나는 지난번 핸드셰이크에서 협상한 암호 스위트와 키를 아직 기억하고 있고 그것을 재사용할 수 있다"는 표시다.**
5. 클라이언트와 서버가 각자의 캐시에서 그 세션 ID에 해당하는 파라미터를 찾을 수 있으면 **축약 핸드셰이크(abbreviated handshake)** 가 성립한다. 찾지 못하면 전체 협상을 새로 하고, 그 결과로 새 세션 ID가 발급된다.

축약 핸드셰이크의 메시지 순서는 이렇다. 18.2절의 그림 18-2와 나란히 놓고 보면 무엇이 사라졌는지가 바로 보인다.

```
클라이언트                                             서버

ClientHello                     ────────▶
 (Session ID 포함)
                                              ServerHello
                                          (같은 Session ID)
                                       [ChangeCipherSpec]
                                ◀────────         Finished

[ChangeCipherSpec]
Finished                        ────────▶

애플리케이션 데이터              ◀───────▶  애플리케이션 데이터
```

*그림 19-1. 축약 TLS 핸드셰이크의 메시지 순서 (HPBN 그림 4-3 기준)*

**`Certificate`가 없고 `ClientKeyExchange`가 없다.** 서버는 인증서를 다시 보내지 않고, 클라이언트는 사전 마스터 비밀을 다시 만들어 암호화하지 않는다. 양쪽은 이전에 합의한 마스터 비밀에서 이번 커넥션의 키를 파생하고, `Finished`로 서로가 같은 비밀을 갖고 있음을 확인한다.

원서의 정리는 두 문장이다. **세션 식별자를 활용하면 왕복 하나를 통째로 제거할 수 있고, 공유 비밀 키를 협상하는 데 쓰이던 공개키 암호의 오버헤드도 함께 제거된다. 그리고 이전에 협상한 세션 데이터를 재사용하는 것이므로 보안의 손실이 없다.**

표 18-3의 언어로 다시 쓰면 이렇다.

**표 19-1. 전체 핸드셰이크와 축약 핸드셰이크의 타임라인 대조 (뉴욕↔런던, RTT 56 ms)**

| 시각 | 전체 핸드셰이크 | 축약 핸드셰이크 |
|---|---|---|
| 0 ms | SYN | SYN |
| 28 ms | SYN-ACK | SYN-ACK |
| 56 ms | ACK + `ClientHello` | ACK + `ClientHello` (세션 ID 포함) |
| 84 ms | `ServerHello` + **`Certificate`** + `ServerHelloDone` | `ServerHello` + `ChangeCipherSpec` + `Finished` |
| 112 ms | **인증서 검증** + `ClientKeyExchange` + `Finished` | `ChangeCipherSpec` + `Finished` — **첫 HTTP 요청이 함께 나간다** |
| 140 ms | 서버 `Finished` | — |
| 168 ms | **첫 HTTP 요청** | — |

**TCP 1왕복 + TLS 1왕복 = 2왕복.** 168밀리초가 112밀리초가 된다. 원서가 같은 예로 계산한 수치가 정확히 이것이다. 전체 TCP·TLS 셋업이 168밀리초, 재개된 TLS 세션이 112밀리초.

그리고 지워지는 것은 시간만이 아니다. **인증서 사슬 전송이 사라진다.** 18.2절이 3,571바이트라는 실측값을 인용하며 그것이 초기 혼잡 윈도우에 가깝다고 적었다. 축약 핸드셰이크에서는 그 바이트가 회선에 실리지 않는다. 19.6절이 사슬 길이를 다루며 계산할 왕복 하나가 여기서는 애초에 발생하지 않는다.

> 대부분의 웹 애플리케이션은 같은 호스트에 여러 커넥션을 맺어 리소스를 병렬로 가져오려 한다. 그래서 세션 재개는 양쪽의 지연과 계산 비용을 줄이는 **필수 최적화**다. 현대 브라우저 대부분은 **의도적으로 첫 TLS 커넥션이 완료될 때까지 기다린 뒤** 같은 서버로의 새 커넥션을 연다. 뒤따르는 TLS 커넥션들이 SSL 세션 파라미터를 재사용해 비싼 핸드셰이크를 피할 수 있게 하기 위해서다.

이 상자의 두 번째 문장은 9장이 커넥션 관리에서 다룬 병렬 커넥션 전략(→ 9.4)과 정면으로 부딪히는 결정이다. 브라우저가 병렬성을 일부러 늦춘다. **첫 커넥션의 완료를 기다리는 비용보다 나머지 커넥션 전부에서 왕복 하나씩을 아끼는 이득이 크기 때문이다.** 최적화가 서로 경쟁할 때 무엇이 이기는지를 보여주는 사례이며, 이 판단의 근거가 되는 것은 결국 1.5절이 정리한 지연의 성질 — 왕복은 거리의 함수이고 거리는 줄지 않는다 — 이다.

### 세션 ID의 배포상 한계

세션 ID 방식에는 실무적 제약이 하나 있고, 그 제약이 두 번째 메커니즘을 낳았다. **서버가 모든 클라이언트에 대해 세션 캐시를 만들고 유지해야 한다는 것.**

매일 수만에서 수백만 개의 고유 커넥션을 보는 서버에서 이것은 여러 문제를 만든다. 원서가 세 가지를 든다.

- **열린 TLS 커넥션마다 소비되는 메모리**
- **세션 ID 캐시와 축출(eviction) 정책의 필요**
- **여러 서버로 구성된 인기 사이트의 배포 난이도** — 최선의 성능을 내려면 이상적으로는 **공유 TLS 세션 캐시**를 써야 한다

원서는 곧바로 단서를 단다. **위 문제들 중 어느 것도 풀 수 없는 문제가 아니며, 오늘날 많은 고트래픽 사이트가 세션 식별자를 성공적으로 쓰고 있다.** 다만 다중 서버 배포라면 세션 캐시가 제대로 동작하도록 신중한 설계와 시스템 아키텍처가 필요하다. 그 설계의 구체적 항목이 19.3절의 주제다.

### 세션 티켓 — 클라이언트가 들고 다닌다

서버 측 TLS 세션 캐시 배포의 이 부담을 덜기 위해 도입된 대체 메커니즘이 **세션 티켓(Session Ticket)** 이다. 이 방식은 **서버가 클라이언트별 세션 상태를 보관해야 한다는 요구 자체를 제거한다.**

동작은 이렇다. 클라이언트가 세션 티켓을 지원한다고 표시하면, 전체 TLS 핸드셰이크의 마지막 교환에서 서버가 **New Session Ticket** 레코드를 함께 보낸다. 그 레코드에는 **모든 세션 데이터가 서버만 아는 비밀 키로 암호화되어** 들어 있다.

클라이언트는 이 티켓을 저장한다. 그리고 다음 세션의 `ClientHello`에 있는 `SessionTicket` 확장에 그것을 실어 보낸다. **결과적으로 모든 세션 데이터는 클라이언트에만 저장되지만, 티켓은 서버만 아는 키로 암호화되어 있으므로 여전히 안전하다.**

관행적으로 두 메커니즘은 각각 **세션 캐싱(session caching)** 과 **무상태 재개(stateless resumption)** 라고 불린다. 무상태 재개의 주된 개선점은 **서버 측 세션 캐시의 제거**이며, 그 대가로 클라이언트가 서버로의 새 커넥션마다 티켓을 제시해야 한다 — 티켓이 만료될 때까지.

여기서 한 문장을 강조해 둘 필요가 있다.

> **세션 티켓은 서버의 상태를 클라이언트가 대신 들고 다니게 만든 것이다.**

이 형태를 이 책은 이미 여러 번 만났고 앞으로도 만난다. 20.4절의 fat URL, 20.5절의 쿠키, 23.1절의 무상태 토큰이 모두 같은 형태다. **서버가 기억하기 부담스러운 상태를 클라이언트에게 맡기되, 그 상태가 위조되지 않도록 암호학적 수단으로 봉인한다.** 세션 티켓에서 그 봉인은 서버만 아는 키에 의한 암호화다. 23.2절이 "암호화된 토큰의 오용"이라는 제목으로 이 형태의 실패 방식을 다루는데, 거기서 다룰 질문들이 여기에도 그대로 적용된다. **봉인에 쓰는 키를 누가 갖는가. 그 키가 유출되면 무엇이 무너지는가. 키를 교체하면 이미 발급된 봉인은 어떻게 되는가.**

원서 자신이 그 질문에 대한 배포상의 답을 상자 하나로 남겼다.

> 실무에서 로드밸런싱된 서버 집합에 세션 티켓을 배포하는 것도 신중한 설계와 시스템 아키텍처를 요구한다. **모든 서버가 같은 세션 키로 초기화되어야 하며**, 공유 키를 모든 서버에서 주기적으로 **회전(rotate)** 시키는 추가 메커니즘이 필요할 수 있다.

두 요구가 나란히 있다는 점을 놓치지 말아야 한다. 첫 번째는 성능·정합성 요구다. 서버마다 키가 다르면 클라이언트의 티켓이 어느 서버에서는 열리고 어느 서버에서는 열리지 않아 재개가 무작위로 실패한다. 두 번째는 보안 요구다. **하나의 티켓 암호화 키는 그 키로 봉인된 모든 세션의 비밀을 연다.** 회전하지 않은 키가 오래 살아 있으면, 그 키 하나를 얻은 자가 그동안의 모든 재개 세션에 대해 마스터 비밀을 복원할 수 있다.

그리고 두 요구는 서로 당긴다. **키를 자주 회전할수록 노출 창은 좁아지지만, 회전 시점 전후로 재개 실패가 늘고 배포는 복잡해진다.** 어느 쪽으로 기울일 것인가는 배포가 정하며, 그 결정은 대개 성능 담당자가 내리고 보안 문서에는 기록되지 않는다.

### 두 메커니즘 비교

**표 19-2. 세션 ID와 세션 티켓 (HPBN 4장 "TLS Session Resumption" 기준, 보안 항목은 이 책이 구성)**

| 항목 | 세션 ID (세션 캐싱) | 세션 티켓 (무상태 재개) |
|---|---|---|
| 도입 | SSL 2.0 (RFC 5246) | RFC 5077 |
| 세션 데이터의 소재 | **서버의 캐시** | **클라이언트** (서버 키로 암호화된 채) |
| `ClientHello`에 실리는 것 | 32바이트 식별자 | `SessionTicket` 확장의 티켓 전체 |
| 서버 메모리 | 커넥션마다 소비 | 없음 |
| 다중 서버 배포 | sticky 라우팅 또는 공유 캐시 필요 | **모든 서버가 같은 티켓 키**를 가져야 함 |
| 만료 통제 | 서버가 캐시 타임아웃으로 | 티켓 자체의 유효 기간 |
| 클라이언트 지원 | 대부분의 클라이언트·서버 | 상대적으로 새 확장, 미지원 클라이언트 존재 |
| 비밀을 여는 열쇠 | 서버 캐시에 대한 접근 | **티켓 암호화 키 하나** |
| 이 책의 대응 형태 | 서버 측 세션 저장소 (→ 23.1) | 클라이언트가 들고 다니는 봉인된 상태 (→ 20.4, 23.2) |

마지막 두 줄이 이 표에서 가장 중요하다. **두 메커니즘은 성능상으로는 같은 것을 달성하지만, 비밀이 어디에 있고 무엇이 그것을 여는지가 다르다.** 세션 캐시를 노리려면 서버에 들어가야 한다. 티켓 키를 노리면 서버에 들어가지 않고도 — 예컨대 설정 관리 시스템이나 배포 파이프라인을 통해 — 같은 결과를 얻을 수 있다. 46장이 배포 파이프라인을 공격 표면으로 다루는 이유가 이런 자리에 있다.

### 재개가 만드는 또 하나의 값

성능 절에서 잘 언급되지 않지만 적어 두어야 할 것이 하나 있다. **세션 ID와 세션 티켓은 둘 다 재방문을 식별하는 값이다.**

세션 ID는 서버가 발급하고 클라이언트가 저장했다가 다시 제시하는 32바이트의 값이다. 티켓도 마찬가지다. 기능적으로 이것은 쿠키와 구분되지 않는다. **서버가 준 값을 클라이언트가 보관했다가 다음번에 되돌려 준다.** 20장이 클라이언트 식별을 다루며 정리할 형태가 정확히 이것이고, 차이는 계층뿐이다.

그러므로 이 값은 두 가지 성질을 갖는다. 첫째, **경로상의 관찰자에게 재방문을 알린다.** `ClientHello`는 평문이므로(→ 18.2), 같은 세션 ID나 티켓이 다시 실려 나가는 것을 관찰자가 볼 수 있다. 둘째, **서버 측에서 커넥션들을 하나로 묶는 키가 된다.** HTTP 계층의 쿠키를 지운 사용자라도 TLS 계층의 재개 값이 남아 있으면 커넥션들이 연결된다. 16.4절이 로그가 누출하는 것을 다루며 던진 질문 — 무엇이 하나의 주체를 가리키는 값인가 — 이 한 계층 아래에서 반복되는 자리다.

이 책은 이 지점에서 멈춘다. 재개 값을 이용한 추적의 구체적 형태는 다섯 권의 원서 범위 밖이다. 다만 구조는 기록해 둔다. **성능을 위해 도입된 상태 이월은, 그것이 무엇을 위한 것이든, 식별자가 될 수 있다.** 9.10절이 keep-alive 커넥션에 대해 같은 관찰을 남겼다.

> **이 절이 뒷받침하는 것**
>
> - 축약 핸드셰이크가 왕복 하나와 인증서 전송을 제거한다 → **19.3** (그것을 실제로 켜는 배포 항목), **19.6** (제거되지 않은 경우의 바이트 계산)
> - 세션 티켓은 서버 상태를 클라이언트가 들고 다니게 한 것이다 → **20.4** (fat URL), **23.1** (무상태 토큰), **23.2** (암호화된 토큰의 오용)
> - 티켓 키 하나가 그것으로 봉인된 모든 세션을 연다 → **19.3** (키 회전), **46장** (배포 파이프라인)
> - 재개 값은 재방문을 식별한다 → **16.4** (로그와 프라이버시), **20.2** (무엇이 한 주체를 가리키는가)

## 19.2 계산 비용과 조기 종료(early termination) — RTT를 줄이는 위치 전략

이 절은 이 장에서, 그리고 아마 Part IV 전체에서 특별한 자리를 갖는다. **여기서 다루는 처방은 성능 문헌에서는 논쟁의 여지 없는 모범 사례이고, 보안 문헌에서는 신뢰 경계의 이동으로 기술된다. 그리고 둘은 같은 배치를 말하고 있다.**

1.6절의 표에서 예고한 줄이 이것이다.

| 왕복을 줄이려는 시도 | 다루는 곳 | 보안·운영 함의 |
|---|---|---|
| TLS 종료 지점을 사용자 쪽으로 옮긴다 | **19.2** | 평문 구간이 생기고 중간자가 정당화된다 |

먼저 성능 쪽을 정확히 서술하고, 그다음 같은 배치를 신뢰의 언어로 다시 쓴다.

### 계산 비용 — 신화와 실측

암호화된 채널을 수립하고 유지하는 데는 양쪽 모두에 추가 계산 비용이 든다. 비용은 두 곳에서 발생한다. **첫째, TLS 핸드셰이크 중에 쓰이는 비대칭(공개키) 암호. 둘째, 핸드셰이크에서 공유 비밀이 수립된 뒤 그것을 대칭 키로 삼아 모든 TLS 레코드를 암호화하는 비용.**

17.4절과 18.2절이 적었듯 공개키 암호는 대칭키 암호에 비해 계산 비용이 훨씬 크다. 웹 초창기에는 이 비용 때문에 **"SSL 오프로딩(SSL offloading)"** 을 수행할 별도의 하드웨어가 요구되는 일이 흔했다. 원서의 판정은 명확하다. **더 이상 그렇지 않다.** 현대 하드웨어가 이 비용을 크게 줄였고, 한때 별도 하드웨어를 요구하던 일이 이제 CPU에서 직접 처리된다. 수억 명에게 TLS를 제공하는 대형 조직들이 필요한 TLS 협상과 계산 전부를 **소프트웨어로, 범용 하드웨어에서** 수행한다.

원서가 인용한 두 증언이 이 절의 근거다.

> 2010년 1월, Gmail이 모든 것을 기본적으로 HTTPS로 전환했다. 이전에는 옵션으로 도입되어 있었지만 이제 모든 사용자가 브라우저와 구글 사이의 메일을 항상 HTTPS로 보호한다. 이를 위해 **추가 장비도 특수 하드웨어도 배치하지 않았다.** 프로덕션 프론트엔드 장비에서 SSL/TLS는 **CPU 부하의 1% 미만, 커넥션당 메모리 10KB 미만, 네트워크 오버헤드 2% 미만**을 차지한다. 많은 사람이 SSL/TLS가 CPU를 많이 쓴다고 믿는데, 위 수치가 그 오해를 없애는 데 도움이 되기를 바란다. 여기서 읽기를 멈춘다면 한 가지만 기억하면 된다. **SSL/TLS는 더 이상 계산 비용이 비싸지 않다.**
>
> — Adam Langley (Google)

> 우리는 하드웨어 로드밸런서와 소프트웨어 로드밸런서 양쪽으로 대규모 TLS를 배포해 봤다. **범용 CPU에서 도는 현대적 소프트웨어 TLS 구현이 전용 암호 하드웨어 없이도 무거운 HTTPS 트래픽 부하를 감당할 만큼 충분히 빠르다**는 것을 확인했다. 우리는 모든 HTTPS 트래픽을 범용 하드웨어에서 도는 소프트웨어로 처리한다.
>
> — Doug Beaver (Facebook)

이 두 인용이 이 장의 나머지를 읽는 방식을 정한다. **TLS의 비용은 CPU가 아니라 왕복이다.** 그러므로 최적화의 초점도 CPU가 아니라 왕복이어야 한다.

다만 원서는 곧바로 단서를 단다. **위 경험들과 무관하게, 세션 재개 같은 기법은 여전히 중요한 최적화다.** 핸드셰이크에서 수행되는 공개키 암호의 계산 비용과 지연을 함께 줄여 주기 때문이다. **하지 않아도 되는 일에 CPU 사이클을 쓸 이유가 없다.**

그리고 실무적인 조언 하나. **SSL 라이브러리를 최신 릴리스로 올리고, 웹 서버나 프록시를 그 라이브러리에 대해 다시 빌드하라.** 최근의 OpenSSL은 상당한 성능 개선을 이뤘고, 시스템 기본 OpenSSL 라이브러리는 대체로 낡아 있을 가능성이 높다. 이 조언은 성능 조언이면서 동시에 보안 조언이다. **암호 라이브러리의 버전은 성능 수치이자 알려진 결함의 목록이다.**

여기서 SSL 오프로딩의 역사를 한 번 짚어 둘 필요가 있다. 그것은 성능 문제의 해결책으로 도입됐지만, 그 해결책의 형태는 **"TLS를 끝내는 별도의 장비를 앞에 둔다"** 였다. 즉 계산 비용 문제에 대한 답이 **배치 문제에 대한 답의 형태를 하고 있었다.** 그 장비가 TLS를 끝낸다는 것은 그 장비가 평문을 본다는 뜻이고, 그 장비 뒤로는 평문이 흐른다는 뜻이다. 계산 비용이 사라진 지금도 그 배치는 남았다. 이유가 성능에서 다른 것들 — 라우팅, 검사, 캐싱, 운영 편의 — 로 바뀌었을 뿐이다. **아래에서 다루는 조기 종료는 그 배치의 지리적 확장판이다.**

### 조기 종료 — 거리를 줄인다

새 커넥션이든 재개된 커넥션이든, 모든 TLS 커넥션에 부과되는 셋업 지연은 중요한 최적화 대상이다. 다시 세어 보자. 모든 TCP 커넥션은 SYN/SYN-ACK의 3-way handshake로 시작하며 이것이 한 왕복이다(→ 3.2). 그 뒤에 TLS 핸드셰이크가 전체 과정에 최대 두 왕복을, 재개가 가능하면 한 왕복을 요구한다. **최악의 경우 애플리케이션 데이터 한 바이트가 오가기 전에 세 왕복이다.** 뉴욕–런던 56밀리초 기준 168밀리초이고, 재개된 세션이라도 112밀리초다. 그리고 원서가 덧붙인다. **양단의 지연이 클수록 벌점은 커지며, 56밀리초는 분명히 낙관적인 숫자다.**

모든 TLS 세션이 TCP 위에서 돌기 때문에, TCP 최적화에 관한 모든 조언(→ 3.8)이 여기에도 그대로 적용된다. 그리고 원서의 강조가 하나 더 있다. **평문 트래픽에서 커넥션 재사용이 중요한 고려 사항이었다면, TLS 위에서 도는 모든 애플리케이션에서 그것은 결정적인 최적화다. 핸드셰이크를 피할 수 있다면 피하라.** 9장이 keep-alive와 커넥션 관리에 할애한 논의 전체가 여기서 세 배의 무게를 갖는다.

그러나 핸드셰이크를 해야만 한다면, **조기 종료(early termination)** 기법을 검토하게 된다.

1장이 정리했듯 미래에 지연이 극적으로 개선되기를 기대할 수는 없다. 패킷은 이미 빛의 속도의 작은 상수배 안에서 이동하고 있다. **패킷을 더 빠르게 만들 수는 없지만, 더 짧은 거리를 이동하게 만들 수는 있다.** 조기 종료란 **서버를 사용자 가까이 배치해 클라이언트–서버 왕복마다의 지연 비용을 최소화하는 단순한 기법**이다.

가장 단순한 실현 방법은 데이터와 서비스를 전 세계의 서버에 복제하거나 캐시해서, 모든 사용자가 대양과 대륙 간 링크를 건너 오리진 서버까지 가지 않게 하는 것이다. 이것이 다수의 콘텐츠 전송 네트워크(CDN)가 제공하는 서비스이며, 14장과 15장이 캐시와 로드 밸런싱의 언어로 이미 다뤘다.

그런데 지리적으로 분산된 서버의 용처는 정적 자산의 전달 최적화에서 끝나지 않는다. **가까운 서버는 TLS 세션을 종료할 수도 있다.** 그러면 TCP와 TLS 핸드셰이크 왕복이 훨씬 짧아지고, 총 커넥션 셋업 지연이 크게 줄어든다. 그리고 그 같은 가까운 서버가 오리진 서버들과 **장수(long-lived)하는 보안 커넥션의 풀**을 유지하면서, 들어오는 모든 요청과 나가는 응답을 오리진과 중계한다.

```
        [ 조기 종료 없음 ]

  클라이언트 ═══════════════════════════════════ 오리진
   (서울)     RTT 250 ms · TCP 1 + TLS 2 = 3왕복    (프랑크푸르트)
              첫 요청까지 750 ms


        [ 조기 종료 ]

  클라이언트 ══════ 엣지 ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ 오리진
   (서울)   RTT 10 ms (서울)   미리 맺어 둔 커넥션 풀  (프랑크푸르트)
            TCP 1 + TLS 2 = 3왕복      (핸드셰이크 없음)
            첫 요청까지 30 ms
```

*그림 19-2. 조기 종료의 구조 (HPBN 그림 4-9 기준, 수치는 이 책이 1.5절 기준으로 구성)*

**한 문장으로 요약하면, TCP와 TLS 핸드셰이크를 가속하기 위해 서버를 클라이언트 가까이 옮기는 것이다.** 대부분의 CDN 사업자가 이 서비스를 제공하며, 직접 구축하는 비용도 크지 않다. 몇 개 데이터센터에 클라우드 서버를 띄우고, 각각에 오리진으로 요청을 전달하는 프록시 서버를 설정하고, 지리 기반 DNS 로드 밸런싱(→ 15.6)을 더하면 된다.

> **캐시되지 않는 오리진 페치 (Uncached Origin Fetch)**
>
> CDN이나 프록시 서버를 써서, 사용자별로 맞춤화되어야 하거나 다른 사적 데이터를 담고 있어서 엣지에서 전역적으로 캐시할 수 없는 리소스를 가져오는 기법을 관행적으로 **"캐시되지 않는 오리진 페치"** 라고 부른다.
>
> CDN은 데이터가 전 세계에 분산된 서버에 캐시될 때 가장 잘 동작하지만, 캐시되지 않는 오리진 페치도 매우 중요한 최적화를 제공한다. **클라이언트 커넥션이 가까운 서버에서 종료되므로 핸드셰이크 지연 비용이 극적으로 줄어든다.** 그리고 CDN이나 자체 프록시 서버는 오리진 서버로 데이터를 중계할 **"따뜻한 커넥션 풀(warm connection pool)"** 을 유지하고 있어서 빠른 응답을 클라이언트에게 돌려줄 수 있다.
>
> 최적화의 한 층을 더 얹어, 일부 CDN 사업자는 **커넥션의 양쪽 끝 모두에 가까운 서버를 쓴다.** 클라이언트 커넥션은 가까운 CDN 노드에서 종료되고, 그 노드가 오리진에 가까운 CDN 노드로 요청을 중계하며, 거기서 오리진으로 라우팅된다. CDN 네트워크 안의 이 추가 홉 덕분에 트래픽이 최적화된 CDN 백본을 타게 되어 클라이언트–오리진 지연을 더 줄일 수 있다.

여기까지가 성능의 언어다. 정확하고, 검증 가능하며, 실제로 효과가 크다. 이제 같은 배치를 다시 읽는다.

### 같은 배치를 신뢰의 언어로 다시 쓰기

위 서술에서 결정적인 문장은 이것이다. **"가까운 서버가 TLS 세션을 종료한다."**

TLS 세션을 종료한다는 것이 무엇인지를 18장의 재료로 정확히 풀면 이렇다.

1. **그 지점이 클라이언트에게 인증서를 제시한다.** 그러므로 **그 지점이 그 이름의 개인키를 갖고 있다.** 17.5절의 언어로, 그 지점이 그 이름으로 서명할 수 있다.
2. **그 지점이 사전 마스터 비밀을 복호한다.** 그러므로 세션 키를 안다.
3. **그 지점이 레코드를 복호한다.** 그러므로 **요청과 응답의 평문 전체를 본다.** 헤더, 쿠키, 본문, 자격 증명 전부다.
4. **그 지점 이후의 구간은 별개의 문제다.** 클라이언트의 TLS 커넥션은 거기서 끝났다.

4번이 이 절의 핵심이다. 클라이언트가 맺은 TLS 커넥션은 엣지에서 **끝난다.** 엣지와 오리진 사이에 무엇이 있는지는 클라이언트가 검증한 것 안에 포함되어 있지 않다. 클라이언트가 확인한 것은 "내가 입력한 이름에 대해 유효한 인증서를 제시한 무엇인가와 암호화된 채널을 맺었다"까지이며, **그 무엇인가의 뒤편은 검증의 대상이 아니다.**

그러므로 엣지–오리진 구간은 배포가 결정한다. 실무에서 흔한 세 가지 배치가 있다.

**표 19-3. TLS 종료 지점 이후 구간의 세 배치 (이 책이 구성)**

| 배치 | 엣지–오리진 구간 | 클라이언트가 아는가 | 무엇이 성립하는가 |
|---|---|---|---|
| **(a) 평문 백홀** | HTTP 평문 | **모른다.** 자물쇠는 표시된다 | 그 구간에서 관찰·개입이 전면 가능하다. 사설 네트워크라는 전제에 전적으로 의존한다 |
| **(b) 재암호화, 검증 없음** | TLS이되 엣지가 오리진 인증서를 검증하지 않음 | **모른다** | **TLS는 켜져 있으면서 보호하지 않는다**(→ 17.10 조건 1). 그 구간의 중간자는 아무 인증서나 제시하면 된다 |
| **(c) 재암호화, 검증 수행** | TLS + 엣지가 오리진 인증서를 정상 검증 | **모른다** | 구간 자체는 보호된다. **그러나 엣지는 여전히 평문을 본다** |

세 배치의 성능 이득은 거의 같다. **클라이언트가 보는 자물쇠도 셋 다 같다.** 그리고 클라이언트가 이 셋을 구별할 방법은 없다. 클라이언트가 검증한 것은 엣지의 인증서이고, 엣지 뒤편은 그 검증의 범위 밖이기 때문이다.

이 관찰을 17.10절의 세 조건과 나란히 놓으면 배치 (b)의 성격이 분명해진다. 17.10절은 **"클라이언트가 실제로 검증할 것"** 을 첫 번째 조건으로 세웠고, 18.3절이 그 조건이 깨지는 방식을 나열했다. 배치 (b)에서 그 조건을 깨는 주체는 사용자의 브라우저가 아니라 **엣지 서버**다. 그리고 엣지는 브라우저와 달리 경고를 띄우지 않는다. 사람이 보고 있지 않기 때문이다. **검증을 생략한 결정은 설정 파일 한 줄로 존재하고, 그 한 줄을 읽는 사람은 대개 그것이 무엇을 끄는지 모른다.**

배치 (c)조차도 "안전하다"로 끝나지 않는다. **엣지가 평문을 본다는 사실은 어떤 배치로도 없어지지 않는다.** 그것이 조기 종료의 정의다. TLS를 종료하지 않으면 핸드셰이크 왕복이 짧아지지 않는다. **성능 이득의 원천이 곧 평문 노출의 원천이다.** 이 둘은 같은 것의 두 이름이다.

### 종료 지점이 신뢰 경계다

18.6절이 11.12절의 두 질문을 인용하며 절을 닫았다. **인프라의 어느 구성 요소가 TLS 커넥션을 종료하는가. 그 구성 요소가 필요한 협상을 수행할 수 있는가.** 이 절은 그 질문에 답을 하나 더 붙인다.

> **TLS를 종료하는 지점이 신뢰 경계다. 그리고 그 지점을 정하는 것은 대개 성능 판단이다.**

이 문장의 무게를 재려면 15.10절로 가야 한다. 그 절은 계층 아키텍처를 다루며 이렇게 적었다. **계층은 관심사를 분리하지만 신뢰를 분리하지 않는다. 관심사의 분리는 계층을 나누는 것만으로 얻어지지만, 신뢰의 분리는 별도의 조치를 필요로 한다.** 그리고 부실한 계층 분리가 가능하게 하는 세 범주의 공격을 열거했다. 그중 첫 번째가 **계층 간 신뢰 관계를 악용해 한 계층에서 다른 계층으로 공격을 진전시키는 것**이다.

조기 종료 배치에서 그 신뢰 관계는 이런 형태를 갖는다. **오리진은 엣지에서 오는 요청을 이미 검증된 것으로 취급한다.** 실제로 그렇게 하지 않을 이유가 없어 보인다. 엣지가 WAF 역할을 하고, 속도 제한을 걸고, 잘못된 요청을 걸러 냈다. 그런데 이 신뢰가 코드로 표현되는 순간 — 예컨대 오리진이 `X-Forwarded-For`를 그대로 클라이언트 IP로 쓰거나(→ 20.2), 엣지가 붙인 인증 헤더를 검증 없이 신뢰하거나 — **오리진에 직접 도달할 수 있는 자는 엣지가 붙이는 모든 표시를 위조할 수 있다.**

13.12절이 정리한 파싱 불일치 지점 목록에 이 배치가 들어가는 이유도 같다. **엣지와 오리진은 같은 바이트열을 두 번 파싱한다.** 엣지가 TLS를 풀고 HTTP를 파싱해서 판정하고, 오리진이 다시 파싱해서 처리한다. 10.4절이 본문 경계에 대해 지적한 문제, 15.2절이 `Host` 헤더에 대해 지적한 문제, 18.6절이 SNI와 `Host`의 불일치에 대해 지적한 문제가 **모두 이 배치에서 동시에 성립한다.** 조기 종료는 그 문제들을 만들지 않았지만, 그 문제들이 성립할 지점을 하나 더 놓는다.

그리고 18.5절이 지적한 것 하나가 여기서 되돌아온다. **TLS 종료가 신원을 지운다.** 클라이언트 인증서로 인증하는 배치에서, 클라이언트의 TLS 커넥션이 엣지에서 끝나면 **오리진은 클라이언트 인증서를 볼 수 없다.** 그 신원은 엣지가 본 것이고, 오리진에 전달하려면 엣지가 헤더 같은 애플리케이션 계층 수단으로 다시 적어 보내야 한다. **암호학적으로 검증된 신원이 신뢰된 헤더 문자열로 강등된다.** 13.10절이 게이트웨이 방식에 대해 같은 지적을 남겼다.

### 그래서 무엇을 할 것인가

조기 종료를 쓰지 말라는 것이 이 절의 결론이 아니다. 그것은 실제로 효과가 크고, 지연이 물리적 하한을 갖는 이상 대안이 마땅치 않다. 결론은 **그 결정이 무엇을 함께 결정하는지를 문서에 적으라**는 것이다.

- **평문을 보는 주체의 목록을 만든다.** 엣지 사업자, 그 사업자의 운영 인력, 엣지 노드가 놓인 관할권. WAHH가 토큰 노출의 위치를 열거한 목록(→ 19.10)과 같은 종류의 목록이다.
- **엣지–오리진 구간을 표 19-3의 어느 배치로 운영하는지를 명시한다.** 특히 (b)인지 (c)인지. 이 구별은 설정 항목 하나로 갈리며 기본값이 (b)인 제품이 존재한다.
- **오리진이 엣지를 어떻게 신뢰하는지를 코드에서 찾는다.** 엣지가 붙인 헤더를 신뢰한다면, 오리진에 직접 도달하는 경로를 막았는지 확인한다. 15.10절의 방어 항목이 그대로 적용된다.
- **로그의 경계를 확인한다.** 16장이 다룬 로그가 이제 두 곳에서 생성된다. 엣지의 로그에는 평문 요청이 남는다.

> **이 절이 뒷받침하는 것**
>
> - TLS 종료 지점이 평문을 본다 → **19.8** (같은 구조의 조직 내부 버전), **19.9** (중간자 성립 조건의 재계산)
> - 클라이언트는 엣지 뒤편을 검증하지 않는다 → **17.10** (검증의 세 조건), **18.3** (검증이 무엇을 확인하는가)
> - 엣지–오리진의 신뢰가 헤더로 표현된다 → **15.10** (계층 간 신뢰 관계), **13.12** (파싱 불일치 지점), **20.2** (클라이언트 IP로 식별하기)
> - 성능 판단이 신뢰 경계를 정한다 → **1.6** (표의 그 줄), **14장·15장** (CDN이 캐시 계층에서 만든 같은 문제)

## 19.3 세션 캐싱과 무상태 재개

19.1절이 메커니즘을 설명했다면 이 절은 **배포**를 다룬다. 두 절을 나눈 것은 목차의 구성이지만 실제로 나뉘는 지점도 여기가 맞다. **재개는 프로토콜이 제공하는 능력이지만, 그 능력이 실제로 발휘되는지는 전적으로 서버 설정의 문제이기 때문이다.**

원서의 도입 문장이 이 절의 논리를 압축한다. **커넥션을 사용자 가까이에서 종료하는 것(→ 19.2)은 모든 경우에 사용자의 지연을 줄여 주는 최적화다. 그러나 다시 한번, 보내지 않은 비트보다 빠른 비트는 없다 — 더 적은 비트를 보내라.** TLS 세션 캐싱과 무상태 재개를 켜면 **재방문자에 대해 왕복 하나를 통째로 제거**할 수 있다.

### 켜져 있다고 가정하지 말 것

세션 캐싱이 의존하는 세션 식별자는 SSL 2.0에서 도입되어 대부분의 클라이언트와 서버가 폭넓게 지원한다. **그러나 서버에서 SSL/TLS를 설정하고 있다면, 세션 지원이 기본으로 켜져 있다고 가정하지 말라.** 원서의 표현은 더 강하다. **실제로는 대부분의 서버에서 기본으로 꺼져 있는 편이 더 흔하다.**

이 문장은 이 장에서 가장 실용적인 한 문장일 수 있다. 18.2절이 계산한 왕복 하나 — RTT 250밀리초 환경에서 250밀리초 — 가 **설정 항목 하나가 기본값으로 꺼져 있다는 이유만으로** 매 커넥션마다 지불되고 있을 수 있다. 그리고 그 사실은 애플리케이션 코드 어디에도 나타나지 않는다. 1.1절이 "추상화는 비용을 숨긴다"고 적은 것의 정확한 사례다.

### 세션 캐싱 배포 점검 항목

원서가 세션 캐싱 설정을 이중으로 확인하라며 여섯 항목을 제시한다.

- **여러 프로세스나 워커를 쓰는 서버는 공유 세션 캐시를 써야 한다.** 워커마다 별도 캐시를 가지면 같은 클라이언트의 두 번째 커넥션이 다른 워커로 갈 때 캐시 미스가 난다.
- **공유 세션 캐시의 크기를 트래픽 수준에 맞춰 조정해야 한다.**
- **세션 타임아웃 기간을 지정해야 한다.**
- **다중 서버 구성에서는, 같은 클라이언트 IP 또는 같은 TLS 세션 ID를 같은 서버로 라우팅하는 것이 세션 캐시 활용률을 높이는 한 방법이다.**
- **"스티키(sticky)" 로드 밸런싱이 불가능한 경우, 서버들 사이에 공유 캐시를 두어 세션 캐시 활용률을 확보해야 한다.**
- **SSL/TLS 세션 캐시 통계를 확인하고 모니터링해야 최선의 성능을 얻는다.**

네 번째 항목을 15장의 렌즈로 읽어 두자. **같은 클라이언트 IP를 같은 서버로 보낸다**는 것은 15.6절이 다룬 로드 밸런싱 정책의 하나이며, 20.2절이 지적할 문제 — IP 주소가 한 주체를 가리키지 않는다 — 를 그대로 물려받는다. NAT 뒤의 수천 명이 하나의 IP를 공유하면 그들 전부가 한 서버로 몰린다. 세션 캐시 활용률을 위한 라우팅 정책이 부하 분산을 저해하는 구조이며, 이것은 성능 결정이 다른 성능 결정과 충돌하는 사례다.

여섯 번째 항목은 이 책이 여러 번 반복한 형태다. **켰다고 믿는 것과 동작하고 있는 것은 다르다.** 세션 캐시 히트율은 측정 가능한 값이며, 측정하지 않으면 캐시가 사실상 항상 미스인 상태로 몇 년을 운영할 수 있다. 14.2절이 캐시 히트율에 대해, 16.5절이 방어자의 로그에 대해 같은 말을 했다.

### 무상태 재개 배포

클라이언트와 서버가 모두 세션 티켓을 지원하면 **모든 세션 데이터가 클라이언트에 저장되고, 위의 어떤 단계도 필요 없다.** 원서의 표현 그대로 "훨씬, 훨씬 단순하다."

그러나 세션 티켓은 TLS의 상대적으로 새로운 확장이라 **모든 클라이언트가 지원하지는 않는다.** 그래서 실무적으로 최선의 결과를 위해서는 **둘 다 켜라**는 것이 원서의 처방이다. 지원하는 클라이언트에는 세션 티켓이 쓰이고, 오래된 클라이언트에는 세션 식별자가 폴백으로 쓰인다. **두 메커니즘은 배타적이지 않으며 함께 잘 동작한다.**

19.1절이 인용한 상자를 여기서 다시 꺼내야 한다. 로드밸런싱된 서버 집합에 세션 티켓을 배포하려면 **모든 서버가 같은 세션 키로 초기화되어야 하고, 공유 키를 주기적으로 회전시키는 추가 메커니즘이 필요할 수 있다.**

**표 19-4. 두 재개 방식의 배포 요구와 실패 양상 (HPBN 4장 "Session Caching and Stateless Resumption" 기준, 실패 양상은 이 책이 구성)**

| | 세션 캐싱 (세션 ID) | 무상태 재개 (세션 티켓) |
|---|---|---|
| 단일 서버 | 캐시 켜기, 크기·타임아웃 설정 | 티켓 키 설정 |
| 다중 프로세스 | **공유 캐시 필수** | 티켓 키 공유 |
| 다중 서버 | 스티키 라우팅 **또는** 서버 간 공유 캐시 | **모든 서버가 동일 티켓 키** |
| 조용한 실패 | 캐시 미스율 100% — 성능만 나빠지고 오류는 없다 | 티켓 복호 실패 — 전체 핸드셰이크로 폴백, 오류 없음 |
| 관측 방법 | 세션 캐시 히트율 통계 | 재개율 모니터링, `s_client -reconnect` (→ 19.11) |
| 보안상 관리 대상 | 캐시 저장소에 대한 접근 | **티켓 키의 배포·보관·회전** |

네 번째 줄이 이 표에서 가장 중요하다. **두 방식 모두 실패가 조용하다.** 재개가 되지 않으면 전체 핸드셰이크로 폴백할 뿐 아무 오류도 나지 않는다. 사용자는 조금 느린 사이트를 경험하고, 운영자는 아무것도 알지 못한다. 이 성질이 여섯 번째 점검 항목 — 통계를 모니터링하라 — 을 필수로 만든다.

### 공유 캐시는 공유 상태다

이 절이 열거한 배포 항목 중 보안 관점에서 가장 주목할 것은 **공유(shared)** 라는 단어가 반복된다는 사실이다. 공유 세션 캐시, 서버 간 공유 캐시, 모든 서버가 공유하는 티켓 키.

14.8절이 공유 캐시의 보안 함의를 다루며 세운 질문을 그대로 가져올 수 있다. **캐시 키가 무엇이고, 누가 그 키를 제시할 수 있으며, 키가 같으면 무엇이 반환되는가.** TLS 세션 캐시에서 그 질문의 답은 이렇다.

- **캐시 키**는 32바이트 세션 ID다.
- **그 키를 제시할 수 있는 자**는 그 값을 아는 누구든이다. 값은 `ClientHello`에 평문으로 실린다(→ 18.2).
- **키가 같으면 반환되는 것**은 협상된 세션 파라미터, 즉 마스터 비밀이다.

여기서 즉시 따라 나오는 요구가 있다. **세션 ID를 제시하는 것만으로 재개가 성립해서는 안 되고, 재개된 세션의 `Finished` 검증을 통과해야 한다.** 실제로 축약 핸드셰이크가 그렇게 설계되어 있다. 그림 19-1의 `Finished` 교환이 그 역할을 한다. **세션 ID를 아는 것과 마스터 비밀을 아는 것은 다르며, `Finished`가 후자를 요구한다.** 이 설계 덕분에 세션 ID의 평문 노출이 곧 세션 탈취가 되지는 않는다.

그러나 그 반대편에 진짜 문제가 있다. **캐시 저장소나 티켓 키에 접근할 수 있는 자는 마스터 비밀 자체에 접근한다.** 그리고 다중 서버 배포는 그 저장소를 **여러 서버가 접근 가능한 곳**으로 옮기라고 요구한다. 15.9절이 공유 호스팅과 테넌트 격리 실패를 다루며 정리한 구조 — 하나의 인프라 위에 여러 주체가 얹히면 격리는 별도의 조치를 요구한다 — 가 여기에 적용된다.

**표 19-5. 재개 관련 비밀의 소재와 그것을 얻은 자가 할 수 있는 일 (이 책이 구성)**

| 얻은 것 | 어디에 있는가 | 무엇이 가능한가 |
|---|---|---|
| 세션 ID | `ClientHello` 평문, 경로상의 모두가 본다 | 재방문 관찰. 재개 자체는 불가(`Finished`가 막는다) |
| 서버의 세션 캐시 내용 | 서버 메모리 또는 공유 저장소 | 캐시에 있는 세션들의 마스터 비밀 |
| 세션 티켓 (봉인된 채) | 클라이언트, 그리고 `ClientHello` 평문 | 봉인을 열 수 없으면 아무것도 |
| **티켓 암호화 키** | 모든 서버의 설정, 배포 파이프라인, 키 관리 시스템 | **그 키로 봉인된 모든 티켓의 마스터 비밀** |
| 서버의 인증서 개인키 | 서버, 그리고 TLS 종료 지점 전부(→ 19.2) | 그 이름으로 인증. 새 세션의 수립 |

마지막 두 줄이 이 표의 요점이다. **재개를 도입하면 "그 이름의 개인키" 외에 지켜야 할 비밀이 하나 더 생긴다.** 그리고 그 새 비밀은 성능을 위해 도입되었으므로 대개 보안 자산 목록에 오르지 않는다. 인증서 개인키는 갱신 절차와 보관 정책이 있고 만료가 강제되지만, 티켓 키에는 아무것도 없다. **회전 메커니즘이 필요할 수 있다는 원서의 조건절이 실무에서는 대개 "아무도 회전시키지 않는다"로 실현된다.**

이 구조를 이 책의 다른 자리와 나란히 놓아 두자. 23.2절이 "암호화된 토큰의 오용"이라는 제목으로 다룰 형태가 같다. **봉인된 상태를 클라이언트에게 맡기는 설계는 봉인 키의 생애주기 관리를 요구하며, 그 요구는 대개 이행되지 않는다.** 계층이 다를 뿐 실패 방식은 같다.

> **이 절이 뒷받침하는 것**
>
> - 재개는 기본으로 꺼져 있는 경우가 흔하고, 실패가 조용하다 → **19.11** (검증 방법), **14.2** (히트율을 측정하지 않으면 모른다)
> - 세션 ID 기반 라우팅과 IP 기반 라우팅 → **15.6** (로드 밸런싱 기법), **20.2** (IP가 한 주체를 가리키지 않는다)
> - 공유 캐시와 공유 티켓 키는 공유 상태다 → **14.8** (공유 캐시), **15.9** (테넌트 격리), **46장** (키 배포)
> - 봉인 키의 생애주기가 관리되지 않는다 → **23.2** (암호화된 토큰의 오용)

## 19.4 TLS 레코드 크기와 버퍼링 지연

18.7절이 레코드 프로토콜의 구조를 펼치고, 레코드와 TCP 세그먼트가 정렬되지 않는다는 사실을 확인한 뒤, **"19.4절이 이 균형을 정면으로 다룬다. 여기서는 그것이 왜 균형인지를 확인하는 데서 멈춘다"** 고 적었다. 이 절이 그 균형을 실제 값으로 잡는다.

### 오버헤드의 산수

TLS로 전달되는 모든 애플리케이션 데이터는 레코드 프로토콜 안에서 운반된다. **각 레코드의 최대 크기는 16 KB이고, 선택된 암호에 따라 헤더·MAC·선택적 패딩으로 레코드마다 20~40바이트의 오버헤드가 붙는다.** 그 레코드가 하나의 TCP 패킷에 들어간다면 IP와 TCP의 오버헤드를 더해야 한다. **옵션 없는 IP 헤더 20바이트, 옵션 없는 TCP 헤더 20바이트.** 결과적으로 **레코드마다 60~100바이트의 오버헤드가 발생할 여지**가 있다. 회선상 일반적인 MTU 1,500바이트를 기준으로 하면 이 패킷 구조는 **최소 6%의 프레이밍 오버헤드**를 뜻한다.

**레코드가 작을수록 프레이밍 오버헤드 비율은 높아진다.** 극단적으로, 1바이트를 담은 레코드가 회선에서 40바이트 가까이 차지한다는 것을 18.7절이 이미 계산했다.

그렇다면 레코드를 최대 크기인 16 KB로 키우면 되는가. **그것도 좋은 생각이 아니다.**

### 큰 레코드가 만드는 지연

레코드가 여러 TCP 패킷에 걸치면, **TLS 계층은 그 TCP 패킷들이 모두 도착할 때까지 기다려야 복호할 수 있다.** 그 패킷 중 하나라도 손실되거나, 재정렬되거나, 혼잡 제어에 의해 지연되면, **TLS 레코드의 각 조각들은 디코딩될 수 있을 때까지 버퍼링되어야 하고 그만큼 추가 지연이 발생한다.**

원서가 강조하는 것은 그 지연의 수신자다. **실무에서 이 지연은 브라우저에게 상당한 병목을 만들 수 있다. 브라우저는 데이터를 바이트 단위로, 가능한 한 빨리 소비하려 하기 때문이다.** 5장이 요청 하나의 생애를 따라가며 확인했듯, 브라우저는 HTML을 받는 대로 파싱을 시작하고 자원 요청을 발행한다. **16 KB 레코드는 그 점진적 처리를 16 KB 단위의 계단으로 만든다.**

원서가 인용한 실측 사례가 하나 있다. **11,211바이트짜리 TLS 레코드 하나가 8개의 TCP 세그먼트로 쪼개진 캡처.** 그 8개가 모두 도착하기 전까지 애플리케이션은 아무것도 받지 못한다.

여기에 3.4절이 하나를 더 얹는다. **새 커넥션에서는 그 세그먼트들이 혼잡 윈도우 아래에 있다.** 초기 혼잡 윈도우가 3~4세그먼트라면, 8개 세그먼트짜리 레코드 하나를 전달하는 데 여러 왕복이 필요하다. 레코드 크기를 키워서 얻으려던 오버헤드 절감이, 왕복 추가라는 훨씬 비싼 대가로 상쇄된다.

### 권고값

**작은 레코드는 오버헤드를 부르고 큰 레코드는 지연을 부르며, "올바른" 레코드 크기에 대한 단일한 답은 없다.** 그러나 브라우저가 소비하는 웹 애플리케이션에 대해서는 권고되는 모범 사례가 단순하다.

> **각 TCP 패킷이 정확히 하나의 TLS 레코드를 담아야 하고, 그 TLS 레코드는 TCP가 할당한 최대 세그먼트 크기(MSS)를 가득 채워야 한다.**

다시 말해 **여러 TCP 패킷에 걸치는 레코드 크기를 쓰지 말고, 각 레코드 안에 담을 수 있는 만큼의 데이터를 담아 보내라.** 배포에 맞는 최적 레코드 크기를 정하는 절차는 이렇다.

- **IPv4 프레이밍 오버헤드로 20바이트, IPv6로는 40바이트를 할당한다.**
- **TCP 프레이밍 오버헤드로 20바이트를 할당한다.**
- **TCP 옵션 오버헤드(타임스탬프, SACK)로 40바이트를 할당한다.**

흔한 출발점인 MTU 1,500바이트를 가정하면, **IPv4로 전달되는 TLS 레코드에는 1,420바이트가, IPv6에는 1,400바이트가 남는다.** 미래를 대비하려면 IPv6 기준인 **1,400바이트**를 쓰고, MTU가 더 작다면 그보다 줄인다.

**표 19-6. MTU 1,500바이트 기준 레코드 크기 계산 (HPBN 4장 "TLS Record Size" 기준)**

| 항목 | IPv4 | IPv6 |
|---|---|---|
| MTU | 1,500 | 1,500 |
| IP 프레이밍 | −20 | −40 |
| TCP 프레이밍 | −20 | −20 |
| TCP 옵션(타임스탬프, SACK) | −40 | −40 |
| **TLS 레코드에 남는 크기** | **1,420** | **1,400** |

1.3.2절이 MTU와 MSS를 다루며 "경로상의 가장 작은 MTU가 전체를 지배한다"고 적은 것이 여기서 값을 정한다. **MTU가 1,500이 아닌 경로 — 터널링, PPPoE, 일부 모바일 망 — 에서는 이 계산의 출발점 자체가 달라진다.**

### 애플리케이션은 이 값을 정할 수 없다

원서가 곧바로 단서를 단다. **아쉽게도 TLS 레코드 크기는 애플리케이션 계층에서 제어할 수 있는 것이 아니다.** 그것은 TLS 서버의 설정이며, 경우에 따라서는 **컴파일 타임 상수나 플래그**다. 값을 바꾸는 방법은 서버 문서에서 확인해야 한다.

이 문장은 1.1절의 "추상화는 비용을 숨긴다"가 갖는 또 다른 결과를 보여준다. **성능에 직접 영향을 주는 값이 애플리케이션 코드에서 보이지 않을 뿐 아니라, 애플리케이션이 바꿀 수도 없는 자리에 있다.** 그리고 그 값의 기본치는 대체로 16 KB에 가깝게 잡혀 있다.

### 메모리 — 커넥션당 비용

원서가 상자 하나를 덧붙인다.

> 서버가 많은 수의 TLS 커넥션을 처리한다면, **커넥션당 메모리 사용량을 최소화하는 것이 결정적인 최적화**가 될 수 있다. OpenSSL 같은 널리 쓰이는 라이브러리는 기본적으로 **커넥션당 최대 50 KB의 메모리를 할당**한다. 레코드 크기와 마찬가지로 이 값을 조정하는 방법은 문서나 소스 코드를 확인해야 할 수 있다. 구글의 서버는 OpenSSL 버퍼를 **약 5 KB로** 줄여 쓴다.

50 KB와 5 KB의 차이는 커넥션 하나에서는 무의미하지만 커넥션 십만 개에서는 5 GB와 500 MB의 차이다. 그리고 이 값은 성능 항목이면서 동시에 **가용성 항목**이다. 45장이 안전한 실패 처리와 가용성 설계를 다루며 정리할 형태가 여기에도 있다. **커넥션당 고정 비용이 있는 자원은 커넥션 수로 곱해지며, 커넥션을 여는 비용이 그 곱보다 싸면 자원 고갈이 성립한다.**

TLS에서 이 비대칭은 특히 눈에 띈다. 클라이언트가 TCP 커넥션 하나를 열고 `ClientHello`를 보내는 데 드는 비용은 작다. 그 시점에 서버는 이미 커넥션 상태와 버퍼를 할당한다. **핸드셰이크를 완료하지 않는 커넥션이 서버 자원을 붙들 수 있다는 뜻이고**, 그 구조는 3장이 TCP 연결 수립에서 본 것과 같다. 원서가 이 비대칭을 공격의 언어로 다루지는 않으므로 이 책도 여기서 멈추되, 설정값 하나가 성능표와 가용성표에 동시에 오른다는 사실은 적어 둔다.

### 레코드 크기는 관찰 가능한 값이다

마지막으로, 이 절의 값이 18.7절의 세 번째 관찰과 만나는 지점을 적어야 한다. **레코드 헤더는 암호화되지 않는다.** 그러므로 경로상의 관찰자는 레코드가 몇 개인지, 각각이 얼마나 큰지, 각각이 핸드셰이크인지 알림인지 애플리케이션 데이터인지를 안다.

레코드 크기를 MSS에 맞춰 고정하면 이 관찰 해상도에 어떤 일이 생기는가. **대부분의 레코드가 같은 크기가 되므로 개별 레코드 크기에서 얻을 수 있는 정보는 줄어든다.** 남는 것은 레코드의 개수, 즉 **총 전송량과 그 타이밍**이다. 반대로 레코드 크기를 콘텐츠 경계에 맞춰 가변적으로 잡는 구현 — 예컨대 응답 하나를 레코드 하나에 담는 — 은 **레코드 크기 그 자체가 응답 크기를 알려준다.**

이 관찰이 다음 절로 이어진다. **압축은 바로 그 관찰 가능한 길이를 내용에 의존하게 만드는 장치다.**

> **이 절이 뒷받침하는 것**
>
> - 레코드는 전체가 확보되어야 복호된다 → **18.7** (그 구조), **3.4** (혼잡 윈도우 아래에서의 도착), **5장** (브라우저의 점진적 처리)
> - 레코드 크기는 애플리케이션이 제어할 수 없다 → **1.1** (추상화가 숨기는 비용), **19.11** (그래서 서버에서 확인해야 한다)
> - 커넥션당 버퍼가 커넥션 수로 곱해진다 → **45장** (가용성 설계)
> - 레코드 길이는 평문으로 관찰된다 → **19.5** (압축이 그 길이를 내용에 묶는다), **18.7**

---

## 19.5 TLS 압축 — 왜 끄는가

TLS에는 잘 알려지지 않은 기능이 하나 있다. **레코드 프로토콜 안에서 전송되는 데이터에 대한 내장 무손실 압축 지원이다.** 압축 알고리즘은 TLS 핸드셰이크에서 협상되며 — 18.2절의 표 18-2가 `ClientHello`의 내용물에 "압축 방법"을 적어 둔 것이 이것이다 — **압축은 각 레코드의 암호화 이전에 적용된다.** 18.7절이 레코드 처리 흐름의 세 번째 단계로 "애플리케이션 데이터를 선택적으로 압축한다"고 적은 그 단계다.

이 절의 결론은 원서가 명령형으로 적어 두었다. **실무에서는 여러 이유로 서버의 TLS 압축을 꺼야 한다.** 두 이유를 순서대로 본다. 두 번째가 더 단순하므로 그것을 먼저 처리하자.

### 이유 둘 — 콘텐츠를 모르는 압축

**전송 계층의 TLS 압축은 콘텐츠를 인식하지 못하며(not content aware), 결국 이미 압축된 데이터를 다시 압축하려 든다.** 이미지, 비디오 같은 것들이다.

이중 압축은 서버와 클라이언트 양쪽에서 CPU 시간을 낭비한다. 그리고 얻는 것은 거의 없다. 이미 엔트로피가 높은 데이터는 다시 압축해도 줄지 않으며, 경우에 따라 미세하게 늘어난다. 10.5절이 콘텐츠 인코딩을 다루며 이 지점을 이미 적었다. **압축은 대상의 성질을 아는 계층에서 수행되어야 효율적이다.**

원서의 처방도 그것이다. **TLS 압축에 의존하는 대신, 텍스트 기반 자산 전부를 Gzip으로 압축하도록 서버를 설정하고, 이미지·비디오·오디오 같은 다른 미디어 타입에는 각각에 최적인 압축 포맷을 쓰라.** 즉 **압축을 한 계층 위로, 콘텐츠를 아는 자리로 올려라.** 10.5절이 `Content-Encoding`으로 다룬 것이 그 자리다.

### 이유 하나 — 압축이 비밀을 누출하는 구조

이제 본론이다. 이 이유가 이 절의 제목이 "왜 끄는가"인 까닭이며, 10.5절과 11.11절이 이 절로 모이도록 배치된 이유다.

10.5절이 "압축의 대가"를 다루며 남긴 문장을 그대로 가져온다.

> 두 문장을 이으면, 암호화된 채널 위에서도 관찰자가 볼 수 있는 값 하나 — **압축 후 길이** — 가 내용에 관한 정보를 담고 있다는 결론이 나온다.

이 결론을 원리 수준에서 완전히 풀어 두자. 압축이 하는 일은 **반복을 줄이는 것**이다. 어떤 알고리즘을 쓰든 무손실 압축의 기본 원리는 같다. 이미 나온 것과 같은 조각이 다시 나오면, 그 조각을 통째로 다시 쓰는 대신 **"앞의 그것과 같다"는 짧은 표시로 대체한다.**

여기서 즉시 따라 나오는 성질이 있다.

> **하나의 압축 컨텍스트 안에 두 조각이 함께 들어 있을 때, 두 조각이 서로 닮아 있을수록 압축 결과가 짧아진다.**

이 성질 자체는 압축의 목적이다. 문제는 그 두 조각 중 하나가 **비밀**이고 다른 하나가 **공격자가 정하는 값**일 때 발생한다. 그 경우 압축 결과의 길이는 **"공격자가 넣은 값이 비밀과 얼마나 닮았는가"** 라는 질문에 대한 답이 된다. 그리고 그 답은 복호 없이 읽을 수 있다. **길이는 암호화되지 않기 때문이다**(→ 18.7).

이 구조가 성립하려면 세 조건이 동시에 필요하다.

**표 19-7. 압축이 비밀을 누출하기 위한 세 조건 (10.5절의 원리를 이 책이 조건으로 정리)**

| 조건 | 내용 | TLS 압축에서의 상태 |
|---|---|---|
| **① 같은 컨텍스트** | 비밀과 공격자가 통제하는 데이터가 **하나의 압축 컨텍스트** 안에 들어간다 | **자동으로 성립한다.** 레코드 계층은 콘텐츠를 모르므로 요청 전체를 한 스트림으로 압축한다 |
| **② 반복 시도** | 공격자가 자기 쪽 데이터를 조금씩 바꿔 가며 **여러 번** 같은 구조를 재현할 수 있다 | **자동으로 성립한다.** 브라우저는 공격자 페이지가 유발한 요청도 같은 커넥션·같은 형식으로 보낸다 |
| **③ 길이 관찰** | 각 시도의 **압축 후 길이**를 관찰할 수 있다 | **자동으로 성립한다.** 레코드 헤더의 길이 필드는 평문이다(→ 18.7) |

이 표의 오른쪽 열이 이 절의 답이다. **TLS 압축은 세 조건을 모두 자동으로 만족시킨다.** 어느 하나도 배포자가 조정할 수 있는 것이 아니다.

각 줄을 조금 더 풀자.

**① 같은 컨텍스트.** TLS 레코드 계층은 자기가 나르는 것이 무엇인지 모른다. HTTP 요청 하나가 통째로 하나의 바이트열로 들어오고, 그것을 압축한다. 그 바이트열 안에는 **세션 토큰을 담은 `Cookie` 헤더**와 **요청 경로나 파라미터** 가 나란히 들어 있다. 하나는 비밀이고 다른 하나는 공격자가 정할 수 있다. **레코드 계층은 이 둘을 구별할 어떤 수단도 갖고 있지 않다.** 계층화가 "아래 계층은 위 계층의 의미를 모른다"는 규칙 위에 서 있기 때문이고(→ 1.1), 그 규칙이 여기서 비용을 청구한다.

**② 반복 시도.** 33장이 다룰 요청 위조의 기본 성질이 여기서 재료가 된다. 공격자가 통제하는 페이지는 사용자의 브라우저로 하여금 대상 사이트에 요청을 보내게 할 수 있고, **브라우저는 그 요청에 해당 사이트의 쿠키를 자동으로 붙인다**(→ 20.5). 공격자는 요청의 일부 — 경로, 쿼리 문자열 — 를 정할 수 있고, 그 값을 바꿔 가며 요청을 반복 유발할 수 있다.

**③ 길이 관찰.** 공격자는 복호할 필요가 없다. **경로상에서 레코드의 길이 필드를 읽거나, 심지어 패킷 크기만 재도 된다.** 1.2절이 "TLS는 패킷 크기와 전송 시각을 가리지 않는다"고 적은 문장이 여기서 세 번째 조건을 무료로 제공한다.

세 조건이 갖춰지면, 공격자는 **자기가 넣은 값이 비밀과 얼마나 닮았는지를 길이로 읽으면서** 시도를 반복한다. 닮음이 늘어나는 방향으로 값을 조정해 나가면, 비밀은 한 번에 전부가 아니라 **조금씩** 드러난다. 이것이 원리의 전부다.

이 책은 여기서 멈춘다. **이 구조를 이용하는 구체적 공격 기법과 그 기법들에 붙은 이름은 이 책이 근거로 삼는 다섯 권의 범위 밖이며**, 10.5절과 11.11절이 각각 "압축의 대가"와 "왜 긴장인가"에서 밝힌 방침을 여기서도 유지한다. **구조와 원리는 본문에서 완전히 다루고, 기법의 이름과 분류는 도입하지 않는다.** 필요한 것은 원리이며, 원리는 위 표가 전부다.

### 그래서 끈다

원서의 결론은 짧다. **이중 압축은 서버와 클라이언트 양쪽에서 CPU 시간을 낭비하고, 보안 침해의 함의는 상당히 심각하다. TLS 압축을 끄라.** 그리고 조건절이 붙는다. **실무에서 대부분의 브라우저는 TLS 압축 지원을 이미 껐다. 그럼에도 사용자를 보호하기 위해 서버 설정에서도 명시적으로 꺼야 한다.**

마지막 문장의 논리를 짚어 두자. **브라우저가 껐으므로 협상이 성립하지 않고, 따라서 안전하다** — 이것은 참이지만 조건부다. 18.2절이 확인했듯 압축 방법은 `ClientHello`가 제시하고 `ServerHello`가 선택한다. **제시하지 않는 클라이언트에 대해서는 성립하지 않는다.** 그러나 서버는 브라우저만 상대하지 않는다. 라이브러리 클라이언트, 오래된 클라이언트, 직접 만든 클라이언트가 있다. **끄는 주체가 상대편일 때, 그것은 자기 정책이 아니라 상대의 정책이다.** 서버에서 끄는 것은 그 정책을 자기 것으로 만드는 일이다.

이 논리는 이 책이 반복해 온 형태다. **방어를 상대편의 동작에 의존시키지 말라.** 26장이 클라이언트 사이드 통제 우회를 다루며 같은 명제를 전면에 놓는다.

### 11.11절과의 대조 — 왜 TLS 압축은 끄고 HPACK은 켜는가

11.11절이 HTTP/2의 헤더 압축을 "압축과 보안의 긴장"이라는 제목으로 다루면서, 그 절이 HPACK을 끄라고 말하지 않는 이유를 이 절에서 정리하겠다고 예고했다. 표 19-7의 세 조건이 그 대조를 정확하게 해 준다.

**표 19-8. 세 조건에 대한 TLS 압축과 HPACK의 차이 (11.11절과 이 책이 구성)**

| 조건 | TLS 압축 | HPACK |
|---|---|---|
| ① 같은 컨텍스트 | 요청 전체가 한 스트림. **구별 불가** | 헤더가 **필드 단위**로 다뤄진다. 어떤 필드를 인덱싱할지 선택할 수 있다 |
| ② 반복 시도 | 막지 못한다 | 막지 못한다 |
| ③ 길이 관찰 | 막지 못한다 | 막지 못한다 |
| 결론 | **세 조건이 모두 성립** → 끈다 | **①을 프로토콜이 깰 수 있다** → 켜되 ①을 관리한다 |

핵심은 ①이다. **HPACK은 압축의 대상을 "바이트 스트림"이 아니라 "헤더 필드의 목록"으로 본다.** 그러므로 특정 필드를 압축 컨텍스트에 넣지 않도록 지시할 수 있다. 민감한 필드를 인덱싱 대상에서 제외하는 표시가 프로토콜에 마련되어 있고, 그 표시를 쓰면 그 필드는 이전 값들과 대조되지 않는다. **①이 깨지면 나머지 두 조건이 성립해도 누출이 성립하지 않는다.**

TLS 압축에는 그런 수단이 원리적으로 존재할 수 없다. **레코드 계층은 필드가 무엇인지 모르기 때문이다.** 이것이 두 판단이 모순되지 않는 정확한 이유이며, 동시에 이 책의 논지가 다시 확인되는 자리다. **같은 기능이라도 어느 계층에 놓이느냐에 따라 안전하게 쓸 수 있는지가 달라진다.** 압축은 콘텐츠를 아는 계층에서는 관리 가능하고, 콘텐츠를 모르는 계층에서는 관리 불가능하다.

10.5절이 "압축은 정의상 내용에 관한 정보를 길이라는 관찰 가능한 값으로 옮긴다"고 적었다. 그 명제는 세 계층에서 모두 참이다. 다른 것은 **각 계층이 그 사실에 대해 무엇을 할 수 있는가**다.

**표 19-9. 세 계층의 압축과 각 계층이 취할 수 있는 조치 (10.5, 11.11, 19.5 종합)**

| 계층 | 압축 대상 | 콘텐츠 인식 | 취할 수 있는 조치 | 이 책의 판정 |
|---|---|---|---|---|
| 콘텐츠 (`Content-Encoding`) | 엔티티 본문 | **있다** | 대상 타입 선택, 민감 응답 제외 | 켠다 (→ 10.5) |
| 헤더 (HPACK) | 헤더 필드 목록 | **필드 단위로 있다** | 민감 필드를 인덱싱에서 제외 | 켜되 관리한다 (→ 11.11) |
| 전송 (TLS 압축) | 레코드의 바이트열 | **없다** | **없다** | **끈다 (이 절)** |

> **이 절이 뒷받침하는 것**
>
> - 압축 후 길이가 내용에 의존한다 → **10.5** (원리의 출처), **11.11** (헤더에서의 형태), **18.7** (길이가 평문인 이유)
> - 세 조건 중 ①을 깰 수 있는 계층만이 압축을 안전하게 쓴다 → **11.11** (HPACK), **1.1** (계층은 위 계층의 의미를 모른다)
> - 브라우저가 껐다는 것은 자기 정책이 아니다 → **26장** (클라이언트 사이드 통제에 의존하지 않기)
> - 압축을 콘텐츠 계층으로 올린다 → **10.5** (`Content-Encoding`)

## 19.6 인증서 체인 길이와 OCSP 스테이플링

표 18-3의 **84밀리초 줄**로 돌아간다. 그 줄에서 서버가 하는 일은 "버전과 암호 스위트를 고르고, **인증서를 붙여** 회신"이다. 이 절은 그 "붙여"의 바이트를 계산한다.

### 사슬은 전부 보내야 한다 — 그러나 필요한 것만

신뢰 사슬 검증은 사이트 인증서에서 출발해 사슬을 거슬러 오르며 부모의 인증서를 재귀적으로 검증해 신뢰된 루트에 도달할 때까지 계속된다. 17.8절이 "사슬을 실제로 걸어 보기"에서 다룬 절차다.

따라서 **첫 번째 최적화는 서버가 핸드셰이크에서 중간 인증서를 빠뜨리지 않는지 확인하는 것**이다. 빠뜨리면 **많은 브라우저가 여전히 동작하기는 하지만, 검증을 멈추고 중간 인증서를 스스로 가져와서 검증한 뒤 계속해야 한다.** 이것은 십중팔구 **새 DNS 조회, 새 TCP 커넥션, HTTP GET 요청**을 요구하며, 핸드셰이크에 **수백 밀리초를 더한다.**

> **브라우저는 그것을 어디서 가져와야 하는지 어떻게 아는가?** 자식 인증서가 대체로 부모의 URL을 담고 있다.

17.6절이 X.509v3 확장 필드를 다루며 정리한 구조가 여기서 성능 항목이 된다. 그리고 그 사실 자체가 하나의 관찰을 낳는다. **인증서에 적힌 URL로 브라우저가 나가 본다는 것은, 그 URL이 응답하지 않으면 검증이 지연되거나 실패한다는 뜻이다.** 17.9절이 폐기 확인의 가용성 문제로 정리한 것과 같은 형태이며, 아래 OCSP 스테이플링 항목에서 다시 나온다.

반대 방향의 잘못도 있다. **필요 없는 인증서를 사슬에 넣지 말라.** 더 일반적으로, **인증서 사슬의 크기를 최소화하는 것을 목표로 삼아야 한다.**

이유는 바이트다. 서버 인증서는 TLS 핸드셰이크 중에 전송되는데, **그 핸드셰이크는 십중팔구 slow-start 알고리즘의 초기 단계에 있는 새 TCP 커넥션 위에서 돈다**(→ 3.4). **인증서 사슬이 TCP의 초기 혼잡 윈도우를 초과하면, 우리는 의도치 않게 핸드셰이크에 왕복 하나를 더하게 된다.** 인증서 길이가 혼잡 윈도우를 넘치고, 서버는 진행하기 전에 클라이언트의 ACK를 기다리며 멈춘다.

원서가 인용한 실측이 두 개 있다. 하나는 **5,323바이트짜리 TLS 인증서 사슬**이다. 이 크기는 **오래된 서버의 초기 혼잡 윈도우를 초과해 핸드셰이크에 왕복 하나만큼의 지연을 강제한다.** 다른 하나는 18.2절과 19.11절이 인용하는 `s_client` 출력의 **3,571바이트**로, 원서의 표현으로 **3~4세그먼트짜리 초기 TCP 혼잡 윈도우 크기에 매우 가깝다.**

한 가지 해법은 초기 혼잡 윈도우를 키우는 것이다(→ 3.4). 그와 별개로 보내는 인증서의 크기를 줄일 수 있는지 검토해야 한다. 원서의 세 항목이다.

- **중간 CA의 수를 최소화한다.** 이상적으로, 보내는 인증서 사슬에는 **정확히 두 장** — 사이트 인증서와 CA의 중간 인증서 — 만 들어 있어야 한다. **세 번째인 CA 루트는 이미 브라우저의 신뢰 루트에 있어야 하므로 보낼 필요가 없다.** 이 점을 **CA 선정의 기준으로 삼으라.**
- **많은 사이트가 자기 CA의 루트 인증서를 사슬에 포함시키는데, 이것은 전혀 불필요하다.** 브라우저의 신뢰 저장소에 그 인증서가 이미 없다면 신뢰되지 않을 것이고, **루트 인증서를 함께 보낸다고 해서 그 사실이 바뀌지 않는다.**
- **잘 관리된 인증서 사슬은 2~3 KB까지 줄어들 수 있으며**, 그러면서도 브라우저가 인증서 자체를 얻기 위한 불필요한 왕복이나 대역외(out-of-band) 요청을 하지 않도록 필요한 정보를 모두 제공한다. **모든 새 TLS 커넥션이 핸드셰이크 오버헤드의 지배를 받으므로, 핸드셰이크 최적화는 결정적인 성능 병목을 완화한다.**

두 번째 항목은 성능 조언의 형태를 하고 있지만 실제로는 17.8절의 논리를 다시 적은 것이다. **신뢰는 사슬을 따라 흐르지 않는다. 신뢰는 신뢰 저장소에서 시작한다.** 루트를 함께 보내는 것은 "이 루트를 믿어 달라"고 요청하는 것인데, 검증은 그런 요청을 받지 않는다. **믿는 루트의 목록은 클라이언트가 갖고 있고, 서버가 보낸 것은 그 목록과 대조될 뿐이다.** 이 문장은 19.8절에서 다시 필요하다. 신뢰 저장소를 바꿀 수 있는 자가 무엇을 할 수 있는지가 그곳의 주제이기 때문이다.

**표 19-10. 사슬 구성별 바이트와 왕복 (HPBN 4장 수치 기준, 표는 이 책이 구성)**

| 사슬 구성 | 대략 크기 | 초기 cwnd(≈4 KB) 대비 | 결과 |
|---|---|---|---|
| 중간 인증서 누락 | 작다 | 여유 | **DNS + TCP + GET 추가** — 수백 ms |
| 사이트 + 중간 CA 1장 | **2~3 KB** | 여유 | 추가 왕복 없음. **권장** |
| 사이트 + 중간 CA 1장 (실측) | 3,571 B | **매우 근접** | 아슬아슬. OCSP 스테이플링을 더하면 넘칠 수 있다 |
| 중간 CA 여러 장 또는 루트 포함 | 5 KB+ | **초과** | **왕복 1회 추가** |

세 번째 줄이 다음 항목으로 이어진다.

### OCSP 스테이플링

모든 새 TLS 커넥션에서 브라우저는 전송된 인증서 사슬의 서명을 검증해야 한다. 그런데 잊으면 안 되는 단계가 하나 더 있다. **브라우저는 그 인증서가 폐기되지 않았음도 확인해야 한다.** 18.3절이 검증의 네 번째 단계로 적은 것이고, 17.9절이 CRL과 OCSP로 정리한 것이다.

그러기 위해 브라우저는 **CA의 CRL을 주기적으로 내려받아 캐시할 수도 있고, 검증 과정에서 "실시간" 확인을 위해 OCSP 요청을 발행할 수도 있다.** 문제는 **이 과정에 대한 브라우저의 동작이 제각각이라는 것**이다. 원서가 세 가지를 든다.

- **어떤 브라우저는** 온디맨드 요청에 의존하는 대신 **자체 업데이트 메커니즘으로 갱신된 CRL 목록을 밀어 넣는다.**
- **어떤 브라우저는** 확장 검증(EV) 인증서에 대해서만 실시간 OCSP와 CRL 확인을 한다.
- **어떤 브라우저는** 두 폐기 확인 방법 중 하나에서 TLS 핸드셰이크를 블로킹하고, **어떤 브라우저는 하지 않는다.** 그리고 이 동작은 **벤더·플랫폼·브라우저 버전에 따라 달라진다.**

17.9절이 "실제 클라이언트의 동작은 제각각이다"라는 소제목으로 이미 이 목록을 다뤘다. 원서의 판정도 같다. **복잡한 영역이며 단일한 최선의 해법이 없다.**

그러나 일부 브라우저에 대해 취할 수 있는 최적화가 하나 있다. **OCSP 스테이플링(OCSP stapling)** 이다. **서버가 CA로부터 받은 OCSP 응답을 자기 인증서 사슬에 함께 붙여(staple) 보내면, 브라우저는 온라인 확인을 건너뛸 수 있다.** OCSP 조회를 서버 쪽으로 옮기면 서버가 **서명된 OCSP 응답을 캐시**해 두고 많은 클라이언트에 대해 추가 요청을 절약할 수 있다.

다만 주의할 점이 둘 있다.

- **OCSP 응답의 크기는 400에서 4,000바이트까지 다양하다.** 이 응답을 인증서 사슬에 붙이면 **다시 한번 TCP 혼잡 윈도우를 넘칠 수 있다.** 총 크기에 각별히 주의해야 한다.
- **OCSP 응답은 하나만 포함할 수 있다.** 그러므로 브라우저가 아직 캐시하지 않은 **다른 중간 인증서들에 대해서는 여전히 OCSP 요청을 발행해야 할 수도 있다.**

첫 번째 주의는 표 19-10의 세 번째 줄과 직접 만난다. **3,571바이트 사슬에 4,000바이트 OCSP 응답을 붙이면 확실히 초과한다.** 두 최적화가 서로를 상쇄할 수 있다는 뜻이며, 이 계산은 실제 값을 재 보지 않으면 알 수 없다(→ 19.11).

마지막으로, 스테이플링을 켜려면 그것을 지원하는 서버가 필요하다. **Nginx, Apache, IIS 같은 널리 쓰이는 서버들이 이 조건을 만족한다.** 지원 여부와 설정 방법은 각 서버 문서를 확인해야 한다.

### 스테이플링은 17.9절의 비대칭을 없애지 않는다

성능 관점의 서술은 여기까지다. 보안 관점에서 한 가지를 덧붙여야 한다.

17.9절이 폐기 모델의 비대칭을 이렇게 정리했다. **발급은 즉시 전 세계에서 효력을 갖고, 폐기는 캐시와 가용성과 클라이언트 정책을 거쳐 지연되어 전파된다.** 스테이플링이 이 비대칭에 하는 일은 **전파 경로를 하나 더 만드는 것**이지 비대칭을 없애는 것이 아니다.

구조를 정확히 보자. 스테이플링에서 **폐기 상태를 클라이언트에게 전달하는 주체는 서버 자신**이다. 그런데 폐기가 문제가 되는 상황은 정확히 **그 서버(또는 그 인증서를 쓰는 자)를 믿을 수 없게 된 상황**이다. 즉 **폐기되었음을 알릴 위치에 폐기 대상이 서 있다.**

이 구조가 붕괴하지 않는 이유는 OCSP 응답이 **CA의 서명을 달고 있고 유효 기간이 있기 때문**이다. 서버는 응답을 위조할 수 없고, 오래된 "정상" 응답을 무한정 재사용할 수도 없다. 그러나 서버가 할 수 있는 일이 하나 남는다. **아무것도 붙이지 않는 것.**

그러면 클라이언트는 어떻게 하는가. 스테이플이 없다는 것은 두 가지를 뜻할 수 있다. 서버가 스테이플링을 설정하지 않았거나, 붙이지 않기로 했거나. **클라이언트는 둘을 구별할 수 없다.** 그리고 스테이플링을 지원하지 않는 서버가 여전히 많은 세계에서, "스테이플이 없으면 거부한다"는 정책은 대다수의 정상 사이트를 차단한다. 그러므로 실제 클라이언트는 **스테이플이 없으면 다른 경로로 확인하거나, 확인하지 못하면 통과시킨다.**

**이것이 17.9절이 폐기 확인 전반에 대해 내린 판정과 정확히 같은 형태다.** 확인에 실패했을 때 통과시키는 정책(soft-fail)은 **확인을 우회하려는 자에게 "확인을 실패하게 만들라"는 단순한 지침을 준다.** 그리고 경로를 통제하는 자에게 그것은 어려운 일이 아니다.

그래서 이 절의 정확한 결론은 이렇다.

> **OCSP 스테이플링은 폐기 확인의 성능 문제를 개선하는 좋은 최적화다. 그것이 폐기 확인의 신뢰성 문제를 해결하지는 않는다.**

두 문장을 함께 적어 두는 이유는, 성능 체크리스트에서 이 항목을 켠 조직이 폐기 문제를 해결했다고 기록하는 일이 흔하기 때문이다. 19.9절이 중간자 성립 조건을 다시 셀 때, 폐기는 여전히 **믿을 수 없는 조건** 쪽에 남는다.

> **이 절이 뒷받침하는 것**
>
> - 사슬 바이트가 초기 혼잡 윈도우 안에 있어야 한다 → **3.4** (slow-start), **18.2** (3,571바이트 실측), **19.1** (재개하면 이 문제가 없다)
> - 루트를 보내도 신뢰가 생기지 않는다 → **17.8** (신뢰는 저장소에서 시작한다), **19.8** (그 저장소를 바꾸는 것)
> - 스테이플링은 폐기 확인의 성능을 고치되 신뢰성을 고치지 않는다 → **17.9** (폐기 모델의 비대칭), **19.9** (조건 재계산에서 폐기의 자리)
> - OCSP 응답 크기가 사슬 최적화를 상쇄할 수 있다 → **19.11** (실제로 재 보는 방법)

## 19.7 HSTS — 다운그레이드와 SSL 스트리핑에 대한 응답

18.1절이 HTTPS의 스킴을 다루며 한 가지를 남겼다. **TLS를 쓸 것인가 말 것인가가 URL 문자열의 앞 다섯 글자로 정해진다.** 그리고 18.4절이 다른 하나를 남겼다. **검증에 실패했을 때 결정을 사용자에게 떠넘긴다.** 이 절의 처방은 두 문제를 함께 겨냥한다.

### 무엇이 문제인가 — 경고가 뜨지 않는 실패

18.4절이 다룬 실패는 **경고가 뜨는** 실패였다. 이름이 맞지 않거나, 만료되었거나, 신뢰 사슬이 끊겼을 때 브라우저는 대화상자를 띄우고, 사용자는 그것을 클릭해 넘긴다. 그 절의 판정은 **결정할 수 없는 자리에 결정을 놓았다**는 것이었다.

그런데 그보다 앞에 놓인 실패가 하나 더 있다. **애초에 HTTPS로 가지 않는 경우.**

구조는 이렇다. 사용자가 주소창에 `joes-hardware.com`을 입력한다. 스킴을 입력하지 않았으므로 브라우저는 평문 HTTP로 요청을 보낸다. 서버는 대개 `301`이나 `302`로 `https://`로 리다이렉트한다(→ 15.4). **그 리다이렉트 응답은 평문으로 흐른다.**

경로를 통제하는 참여자가 여기서 할 수 있는 일이 있다. 리다이렉트를 없애고, 자기가 대신 서버와 HTTPS로 대화하며, 사용자에게는 평문 HTTP로 응답을 돌려주는 것이다. 응답 본문 안의 `https://` 링크들을 `http://`로 바꿔 두면, 사용자는 그 사이트를 끝까지 평문으로 이용한다.

```
   사용자 ══════════════ 중간자 ══════════════ 서버
           평문 HTTP              정상 HTTPS

   · 서버 쪽에서는 아무 이상이 없다. 정상적인 HTTPS 클라이언트로 보인다.
   · 사용자 쪽에서는 인증서 오류가 없다. 인증서를 쓰지 않았기 때문이다.
   · 브라우저는 경고를 띄우지 않는다. 경고할 오류가 없다.
   · 없는 것은 자물쇠뿐이고, 그 부재를 알아채는 것은 사용자의 몫이다.
```

*그림 19-3. 스킴 다운그레이드(SSL 스트리핑)의 구조*

관행적으로 **SSL 스트리핑**이라 불리는 이 배치가 18.4절의 문제와 다른 점은 결정적이다. **18.4절에서는 브라우저가 물어보기라도 했다. 여기서는 물어볼 것이 없다.** 프로토콜 수준에서 아무 이상도 발생하지 않았기 때문이다. 사용자가 "이 사이트는 HTTPS여야 한다"는 사실을 스스로 기억하고 주소창을 확인해야만 알아챌 수 있다.

18.2절이 확인한 것과 대조하면 차이가 선명하다. **`Finished`가 핸드셰이크 전체를 해시하므로 프로토콜 내부의 다운그레이드는 탐지된다.** 암호 스위트 목록을 깎거나 ALPN 목록을 바꾸면 해시가 어긋난다(→ 11.12). **그러나 TLS를 아예 시작하지 않는 것은 TLS가 탐지할 수 없다.** 존재하지 않는 핸드셰이크는 무결성 검사의 대상이 아니다.

> **프로토콜 다운그레이드는 프로토콜이 막고, 스킴 다운그레이드는 프로토콜이 막을 수 없다.**

이 문장이 HSTS가 존재하는 이유의 전부다.

### HSTS가 하는 일

**HTTP 엄격 전송 보안(HTTP Strict Transport Security, HSTS)** 은 서버가 **단순한 HTTP 헤더 하나**로 규격을 준수하는 브라우저에게 접근 규칙을 선언하게 해 주는 보안 정책 메커니즘이다.

```
Strict-Transport-Security: max-age=31536000
```

이 헤더는 사용자 에이전트에게 다음 규칙들을 강제하도록 지시한다.

- **이 오리진으로 가는 모든 요청은 HTTPS로 보내야 한다.**
- **모든 비보안 링크와 클라이언트 요청은 요청이 나가기 전에 클라이언트에서 자동으로 HTTPS로 변환되어야 한다.**
- **인증서 오류가 발생하면 오류 메시지가 표시되고, 사용자는 그 경고를 우회할 수 없다.**
- **`max-age`는 지정된 HSTS 규칙 집합의 수명을 초 단위로 지정한다.** 예를 들어 `max-age=31536000`은 365일의 캐시 수명과 같다.
- **선택적으로, 사용자 에이전트에게 지정된 인증서 사슬 안의 호스트 지문을 기억("핀")하도록 지시할 수 있으며, 이는 그 인증서를 인증할 수 있는 기관의 범위를 실질적으로 제한한다.**

원서의 요약은 이렇다. **HSTS는 오리진을 HTTPS 전용 목적지로 전환하며, 사용자를 겨냥한 다양한 수동적·능동적 네트워크 공격으로부터 애플리케이션을 보호하는 데 도움을 준다.** 그리고 성능 면에서도 **불필요한 HTTP→HTTPS 리다이렉트를 없앤다.** 그 책임을 클라이언트로 옮겨, 클라이언트가 모든 링크를 자동으로 HTTPS로 다시 쓰게 하기 때문이다.

마지막 문장을 표 18-3의 언어로 읽으면, HSTS는 **왕복 하나를 더 지운다.** 리다이렉트는 TCP 커넥션 하나와 요청·응답 한 쌍을 요구하는데, 브라우저가 스킴을 미리 바꿔 버리면 그 전부가 사라진다. **이 장에서 성능과 보안이 같은 방향을 가리키는 드문 항목이다.**

### 세 규칙이 각각 무엇을 받는가

위의 세 규칙을 이 책의 앞선 절들에 대응시키면 HSTS의 설계 의도가 정확히 보인다.

**표 19-11. HSTS의 세 규칙과 그것이 응답하는 문제 (HPBN 4장 "HSTS" 기준, 대응은 이 책이 구성)**

| HSTS 규칙 | 무엇에 응답하는가 | 이 책에서 |
|---|---|---|
| 모든 요청을 HTTPS로 | **TLS 사용 여부가 URL 문자열로 정해진다** | 18.1 |
| 비보안 링크를 클라이언트에서 자동 변환 | **평문 응답 안의 링크가 바꿔치기될 수 있다**, 혼합 콘텐츠 | 그림 19-3, 19.10 |
| 인증서 오류 시 **우회 불가** | **결정할 수 없는 자리에 놓인 결정** | 18.4 |
| (선택) 인증서 지문 핀 | **어느 CA든 어느 이름에 대해서든 발급할 수 있다** | 17.10 논점 3 |

세 번째 줄이 18.4절이 이 절로 넘긴 것이다. 18.4절의 판정을 다시 적으면 **판단에 필요한 정보를 갖지 못한 주체에게 판단을 위임하는 구조**였다. HSTS가 하는 일은 그 판단을 **없애는** 것이 아니라 **옮기는** 것이다.

> **HSTS는 결정을 사용자에게서 사이트로 옮긴다.**

사이트는 자기 배포를 안다. 자기가 항상 HTTPS를 제공하는지, 인증서를 제대로 관리하고 있는지, 평문으로 서비스하는 자원이 있는지를 안다. **사용자는 그 어느 것도 모른다.** 그러므로 "이 사이트에서 인증서 오류가 났을 때 계속 진행해도 되는가"라는 질문의 답을 가진 쪽은 사이트다. HSTS는 그 답을 **사고가 나기 전에 미리 받아 두는** 장치다.

30장이 오류 처리에서, 45장이 실패 설계에서 반복할 명제가 여기서 실물을 얻는다. **결정은 그 결정을 내릴 수 있는 자리에 놓여야 한다.** 그리고 그 자리는 대개 **사고가 난 시점의 사용자**가 아니라 **평상시의 설계자**다.

네 번째 줄의 핀 옵션도 같은 성격이다. 17.10절이 "어느 CA든 어느 이름에 대해서든 발급할 수 있다"를 웹 PKI의 가장 무거운 성질로 지목했다. 핀은 그 OR를 **사이트가 스스로 좁히는** 선언이다. 발급은 여전히 OR이지만, **이 사이트에 대해서만은** 클라이언트가 좁은 집합만 받아들인다.

### 무엇을 남기는가 — 최초 접속의 창

여기까지가 HSTS가 해결하는 것이다. 이제 해결하지 않는 것을 적는다. **그리고 이 부분이 이 절에서 가장 중요하다.**

HSTS의 선언은 **HTTP 응답 헤더로 전달된다.** 그리고 그 헤더가 신뢰될 수 있으려면 **HTTPS 응답에 실려 와야 한다.** 평문 HTTP 응답에 실린 `Strict-Transport-Security` 헤더는 경로상의 누구든 붙이거나 뗄 수 있으므로 의미가 없다.

여기서 순환이 발생한다.

> **HSTS 선언을 받으려면 이미 HTTPS로 접속해 있어야 하고, HTTPS로 접속하게 만드는 것이 HSTS다.**

이 순환이 남기는 것을 **최초 접속(bootstrap) 문제**라고 부른다. **사용자가 그 사이트에 처음 접속하는 그 한 번은 보호되지 않는다.** 그리고 그 한 번에 그림 19-3의 배치가 성립하면, 사용자는 HSTS 선언을 영영 받지 못한 채로 계속 평문을 쓴다. **선언을 받지 못하게 만드는 것이 곧 선언을 무력화하는 방법이다.**

"처음 한 번"이 실제로 언제인지를 열거하면 창은 생각보다 넓다.

**표 19-12. HSTS 선언이 없는 상태가 발생하는 경우 (이 책이 구성)**

| 상황 | 왜 선언이 없는가 |
|---|---|
| 그 사이트 **첫 방문** | 아직 받은 적이 없다 |
| `max-age` **만료 후** | 선언에는 수명이 있다. 오래 방문하지 않으면 지워진다 |
| **새 기기·새 브라우저·새 프로필** | 선언은 브라우저의 로컬 상태다 |
| **시크릿/사생활 보호 모드** | 세션 종료와 함께 상태가 버려진다 |
| 브라우저 데이터 **삭제 후** | 36.3절이 권하는 방어가 이 상태를 만든다 |
| **`includeSubDomains` 없이** 서브도메인 접근 | 선언의 범위가 그 호스트에 한정된다 |
| 시스템 **시계가 조작된 경우** | `max-age`는 시간에 의존한다 |

여섯 번째 줄을 강조해 둘 필요가 있다. HSTS의 범위는 **오리진**이며, 서브도메인을 포함시키려면 명시적인 지시가 필요하다. 20.8절이 관대한 쿠키 스코프를 다루며 정리할 문제 — 도메인 경계를 어디에 긋는가 — 가 여기서 반대 방향으로 나타난다. **쿠키에서는 범위를 넓게 잡는 것이 위험이었고, HSTS에서는 좁게 잡는 것이 구멍이다.** 같은 이름 계층 위에서 두 메커니즘이 반대 방향의 실수를 유발한다.

다섯 번째 줄은 더 불편하다. 36.3절이 로컬 프라이버시 공격에 대한 방어로 브라우저 데이터 삭제를 권하는데, **그 조치가 HSTS 선언도 함께 지운다.** 프라이버시 방어와 전송 보안이 같은 저장소를 공유하기 때문에 생기는 충돌이며, 이 책이 여러 번 만난 형태 — **두 보안 목표가 같은 자원을 두고 경쟁한다** — 의 사례다.

### 그래서 어떻게 평가할 것인가

HSTS의 정확한 평가는 이렇다.

- **HSTS는 스킴 다운그레이드를 "매번 가능"에서 "선언 이전에만 가능"으로 축소한다.** 이것은 큰 축소다. 표 19-12의 상황들을 제외하면, 선언을 받은 브라우저에서 그림 19-3의 배치는 성립하지 않는다.
- **HSTS는 경고 클릭을 없앤다.** 18.4절이 "기저율이 클릭을 학습시킨다"고 정리한 문제를, 적어도 선언한 사이트에 대해서는 무효화한다. 우회 버튼이 없기 때문이다.
- **HSTS는 최초 접속을 보호하지 않는다.** 그리고 그 창은 표 19-12만큼 넓다.
- **HSTS는 인증서 검증을 대신하지 않는다.** 17.10절의 세 조건 중 첫 번째와 두 번째는 그대로 남는다. 클라이언트가 검증해야 하고, 신뢰 저장소가 오염되지 않아야 한다. **신뢰 저장소에 공격자의 루트가 들어 있으면 HSTS는 아무것도 하지 않는다.** 오히려 그 상황에서 HSTS는 **경고 없는 통과를 보장하는 쪽으로 작동한다.** 인증서가 정상적으로 검증되기 때문이다.

마지막 항목이 19.8절과 19.9절의 문을 연다. **HSTS는 "TLS를 켜라"는 요구를 강제하지만, "누구와의 TLS인가"는 여전히 신뢰 저장소가 정한다.**

> **이 절이 뒷받침하는 것**
>
> - 스킴 다운그레이드는 프로토콜 무결성 밖에 있다 → **18.1** (스킴이 결정을 내린다), **18.2** (`Finished`가 보호하는 범위), **11.12** (프로토콜 다운그레이드와의 대조)
> - 결정을 사용자에서 사이트로 옮긴다 → **18.4** (떠넘기기), **30장·45장** (결정 가능한 자리에 결정을 놓기)
> - 최초 접속의 창이 남는다 → **19.10** (그 창에서 토큰이 새는 방식), **36.8** (능동적 중간자)
> - 핀은 발급의 OR를 사이트가 좁히는 선언이다 → **17.10** (CA는 단일 실패 지점)

## 19.8 프록시를 통한 보안 트래픽 터널링 — CONNECT와 기업 MITM

이 절은 13.10절이 예고하며 남긴 자리를 채운다. 그 절이 이렇게 적었다. **터널은 프록시가 내용을 보지 못하게 하고, 게이트웨이는 프록시가 내용을 보게 한다. 기업이 후자를 선택하면 그것이 곧 조직 내부의 중간자다.**

### 왜 CONNECT가 필요한가

클라이언트는 자기를 대신해 웹 서버에 접근하도록 웹 프록시 서버를 흔히 쓴다(→ 13장). 예를 들어 많은 기업이 **사내 네트워크와 공용 인터넷의 보안 경계에 프록시를 둔다.** 그 프록시는 방화벽 라우터가 HTTP 트래픽을 주고받도록 허용한 **유일한 장비**이며, **바이러스 검사나 그 밖의 콘텐츠 통제를 수행할 수 있다.**

그런데 클라이언트가 서버의 공개키로 데이터를 암호화하기 시작하면, **프록시는 더 이상 HTTP 헤더를 읽을 수 없다.** 그리고 HTTP 헤더를 읽지 못하면 **요청을 어디로 전달해야 하는지 알 수 없다.**

이 문제를 짚고 넘어가야 한다. 13.5절이 프록시 요청의 까다로운 점을 다루며 정리했듯, 프록시는 **요청 줄의 절대 URI나 `Host` 헤더**를 읽어 목적지를 정한다. 둘 다 HTTP 계층의 값이다. **TLS는 HTTP 아래에 있으므로, TLS를 먼저 세우면 그 값들은 이미 암호문 안에 있다.** 1.2절의 스택 그림이 이 순서를 결정한다.

해법은 **암호화가 시작되기 전에, 평문으로 목적지를 알려주는 것**이다. 널리 쓰이는 기법이 **HTTPS SSL 터널링 프로토콜**이며, 그 수단이 `CONNECT` 메서드다.

### CONNECT의 문법

HTTPS 터널링 프로토콜에서 **클라이언트는 먼저 프록시에게 자기가 접속하려는 보안 호스트와 포트를 알려준다. 암호화가 시작되기 전에 평문으로 알려주므로 프록시가 그 정보를 읽을 수 있다.**

평문 종단점 정보를 보내는 데 HTTP가 쓰이며, 그것을 위해 **`CONNECT`라는 새 확장 메서드**가 도입되었다. **`CONNECT` 메서드는 프록시에게 원하는 호스트와 포트 번호로 커넥션을 열고, 그것이 완료되면 클라이언트와 서버 사이의 데이터를 직접 터널링하도록 지시한다.**

문법은 이렇다. **`CONNECT`는 한 줄짜리 텍스트 명령으로, 보안 오리진 서버의 호스트명과 포트를 콜론으로 구분해 제공한다. `host:port` 뒤에 공백, HTTP 버전 문자열, CRLF가 온다. 그 뒤에 0개 이상의 HTTP 요청 헤더 줄이 오고, 빈 줄이 온다. 빈 줄 다음부터, 커넥션 수립 핸드셰이크가 성공했다면 SSL 데이터 전송이 시작될 수 있다.**

```
CONNECT home.netscape.com:443 HTTP/1.0
User-agent: Mozilla/1.1N

<여기부터 원시 SSL 암호화 데이터가 이어진다>
```

요청의 빈 줄 뒤에서 클라이언트는 프록시의 응답을 기다린다. **프록시는 요청이 유효한지, 그리고 사용자가 그런 커넥션을 요청할 권한이 있는지 확인한다.** 문제가 없으면 목적지 서버로 커넥션을 만들고, 성공하면 클라이언트에게 `200 Connection established` 응답을 보낸다.

```
HTTP/1.0 200 Connection established
Proxy-agent: Netscape-Proxy/1.1
```

13.10절이 이 절차를 그림 13-7과 예제 13-7로 이미 상세히 다뤘다. 여기서 반복하지 않고, **이 배치가 보안에 대해 말하는 것**으로 바로 넘어간다.

### 배치 1 — 터널: 프록시가 아는 것은 한 줄뿐이다

`CONNECT`가 성공하면 프록시는 **맹목적인 중계기**가 된다. 클라이언트와 오리진 서버 사이에 TLS 커넥션이 직접 수립되고, 프록시는 그 위를 흐르는 바이트를 양방향으로 옮길 뿐이다. **프록시는 SSL을 구현할 필요조차 없다.**

이 배치의 성질을 정확히 적자.

- **프록시가 아는 것**: `CONNECT` 줄의 `host:port`, 커넥션의 시각과 지속 시간, 오간 바이트의 양. 그리고 그 뒤로 흐르는 `ClientHello`를 파싱한다면 **SNI와 ALPN**(→ 18.6). 이것들은 전부 평문이다.
- **프록시가 모르는 것**: 요청 경로, 헤더, 쿠키, 본문, 응답 전부.
- **따라서 콘텐츠 통제가 불가능하다.** 바이러스 검사도, URL 필터링도, 데이터 유출 검사도 할 수 없다.
- **정책 집행의 근거는 `CONNECT` 줄 한 줄이다.** 13.10절이 그 한 줄의 남용을 다뤘다. **프록시가 검증할 수 있는 것은 "그 호스트의 그 포트로 터널을 열어도 되는가"뿐이고, 그 포트에서 실제로 도는 것이 무엇인지는 알 수 없다.**

마지막 항목이 13.10절의 표에 있던 대조 — `CONNECT` 시작줄의 목적지가 말하는 것과 그 호스트에서 실제로 도는 서비스 — 이며, 그래서 방어가 **목적지 포트 제한과 터널 인증**(→ 13.7)이 되는 것이다.

### 배치 2 — 검사: 프록시가 TLS를 종료한다

콘텐츠 통제를 포기할 수 없는 조직은 다른 배치를 택한다. **프록시가 TLS를 종료한다.**

구조는 이렇다.

```
  클라이언트 ══════════ 검사 프록시 ══════════ 오리진 서버
              TLS 세션 A              TLS 세션 B

  · 세션 A: 프록시가 "www.joes-hardware.com"의 인증서를 제시한다.
            그 인증서는 프록시가 즉석에서 발급한 것이고,
            서명한 것은 조직의 내부 CA다.
  · 세션 B: 프록시가 클라이언트 역할을 하며 진짜 서버와 TLS를 맺는다.
  · 프록시는 두 세션 사이에서 평문을 본다. 전부를.
  · 클라이언트의 브라우저는 아무 경고도 띄우지 않는다.
    조직의 내부 CA 루트가 그 기기의 신뢰 저장소에 설치되어 있기 때문이다.
```

*그림 19-4. TLS 종료형 검사 프록시의 구조*

이 배치가 성립하는 조건은 **정확히 하나**다. **클라이언트의 신뢰 저장소에 프록시의 루트 인증서가 들어 있을 것.**

17.10절이 검증 성립의 세 조건을 세우며 두 번째로 적은 것이 이것이다. **"신뢰 저장소가 오염되지 않았을 것 — 깨지는 방식: 기기에 설치된 추가 루트 인증서, 기업 검사 장비, 인터셉팅 프록시, 악성 소프트웨어."** 그 절이 이 조건의 실물을 19.8절로 넘겼고, 지금 그것을 보고 있다.

18.8절이 `openssl s_client`의 `-CAfile` 옵션을 두고 남긴 문장도 여기서 값을 갖는다. **신뢰 저장소는 주어진 것이 아니라 설정이다.** 브라우저의 신뢰 목록은 자연법칙이 아니라 파일이며, 파일은 쓸 수 있다. 기기를 관리하는 자는 그 파일을 쓸 수 있다.

### 기술적으로 같은 위치

이제 이 장에서, 그리고 아마 Part IV 전체에서 가장 중요한 문장을 적을 자리다. 1.8절이 처음 적었고 17.10절이 인용했다.

> **의도된 중간자와 공격자는 기술적으로 같은 위치에 있고, 차이는 신뢰 저장소에 무엇이 들어 있는지뿐이다.**

이 문장을 배치의 목록으로 확인하자.

**표 19-13. TLS를 종료하는 네 배치의 기술적 동일성 (이 책이 구성. 1.8절·17.10절의 관찰을 배치별로 전개)**

| 배치 | 신뢰 저장소에 루트를 넣은 주체 | 사용자가 동의했는가 | 기술적 동작 | 클라이언트가 구별할 수 있는가 |
|---|---|---|---|---|
| 기업 TLS 검사 장비 | 조직의 기기 관리 | 고용 계약의 형태로, 대개 명시적으로 읽지 않고 | 그림 19-4 | **아니오** |
| CDN·엣지의 TLS 종료 | (루트 설치 불필요 — 사이트가 개인키를 위임) | 사이트가 동의, **사용자는 모른다** | 19.2절 표 19-3 | **아니오** |
| 개발자의 인터셉팅 프록시 | 개발자 본인 | 본인이 명시적으로 | 그림 19-4 | **아니오** |
| 악성 소프트웨어 | 침해자 | **아니오** | 그림 19-4 | **아니오** |

오른쪽 두 열이 이 표의 요점이다. **네 배치의 기술적 동작은 같고, 클라이언트는 넷을 구별할 수 없다.** 다른 것은 **누가 루트를 넣었는가**와 **사용자가 그것을 알고 있는가**뿐이며, 두 값 모두 TLS 프로토콜 안에는 존재하지 않는다.

그리고 즉시 따라 나오는 귀결이 있다. **그 설치를 수행할 수 있는 자는 누구든 같은 일을 할 수 있다.** 기업이 검사 장비를 위해 기기에 루트를 설치했다면, 그 설치 경로 — 기기 관리 시스템, 배포 이미지, 설정 도구 — 를 장악한 자도 같은 일을 할 수 있다. **정당한 중간자의 존재는 부당한 중간자의 진입로를 함께 만든다.**

두 번째 줄이 조금 다르다는 점도 짚어야 한다. CDN 종료는 신뢰 저장소를 건드리지 않는다. **사이트가 자기 이름의 개인키(또는 그 이름으로 인증서를 발급받을 권한)를 엣지 사업자에게 넘김으로써** 같은 결과에 도달한다. 17.10절의 언어로, 그것은 신뢰 저장소를 오염시키는 것이 아니라 **"이름의 통제권"의 범위를 넓히는 것**이다. 결과는 같다. **경로상의 어떤 지점이 그 이름으로 인증할 수 있게 된다.**

### 검사 배치가 실제로 바꾸는 것들

이 배치를 택한 조직이 무엇을 함께 받아들이는지를 나열해 두자. 성능 문헌과 보안 제품 문서 어느 쪽에도 잘 정리되어 있지 않은 목록이다.

**첫째, 종단 간 무결성이 사라진다.** 18.7절이 레코드 계층의 MAC과 일련번호가 순서와 재생을 막는다고 적었다. 그 보호는 **커넥션 하나 안에서만 성립한다.** 두 개의 커넥션으로 쪼개면 중간에서의 변경은 프로토콜적으로 탐지되지 않는다. 프록시가 응답을 고쳐서 전달하면 클라이언트는 그것이 서버의 응답이라고 판단한다.

**둘째, 클라이언트 인증서가 무력화된다.** 18.5절이 "TLS 종료가 신원을 지운다"고 적은 그대로다. 클라이언트가 인증서로 인증하려 해도, 그 인증서에 대한 소유 증명(`CertificateVerify`)은 클라이언트의 개인키로만 만들 수 있고 **프록시는 그 개인키를 갖고 있지 않다.** 그러므로 프록시는 클라이언트를 대신해 오리진에 인증할 수 없다. 13.10절이 게이트웨이 방식에 대해 같은 지적을 남겼다.

**셋째, 조직 전체의 TLS 품질이 그 장비 하나의 품질이 된다.** 이것이 가장 과소평가된 항목이다. 클라이언트가 하던 검증(→ 18.3)을 이제 프록시가 대신 수행한다. 그러므로 **프록시가 오리진 인증서를 어떻게 검증하는지가 조직 전체의 검증 정책이다.** 프록시가 폐기를 확인하지 않으면 조직 전체가 확인하지 않는 것이고, 프록시가 이름 일치를 느슨하게 보면 조직 전체가 느슨한 것이며, 프록시가 약한 암호 스위트를 받아들이면 조직 전체가 그것을 받아들인다.

그리고 사용자는 이 사실을 볼 수 없다. **브라우저가 표시하는 자물쇠는 프록시와의 세션 A에 대한 것이고, 실제 위험은 세션 B에 있다.** 표 19-3의 배치 (b)와 완전히 같은 구조이며, 19.2절이 CDN에 대해 적은 것을 조직 내부로 옮긴 것이다.

**넷째, 모든 평문이 한 곳에 모인다.** 그 지점은 조직 구성원 전체의 자격 증명, 세션 토큰, 개인정보, 그리고 조직이 접근하는 모든 외부 서비스의 내용을 본다. **정의상 조직에서 가장 가치 있는 표적이 된다.** 15.10절이 계층 아키텍처 공격의 세 번째 범주로 적은 것 — 한 계층의 제한적 장악을 다른 계층으로 확장 — 에서, 이 장비는 확장의 출발점으로 이상적이다.

**다섯째, 로그가 생긴다.** 16장이 다룬 문제 전부가 이 장비에서 발생한다. 16.4절의 프라이버시, 16.6절의 로그 인젝션, 그리고 무엇보다 **평문 본문을 로깅하는 설정이 존재한다는 사실 자체**가 그렇다.

### 19.2절과 같은 구조

이 절과 19.2절이 다른 절로 나뉘어 있는 것은 목차의 구성이지만, 두 절이 서술하는 것은 같은 구조다.

**표 19-14. 두 종류의 정당한 중간자 (이 책이 구성)**

| | 조기 종료 (19.2) | 검사 프록시 (19.8) |
|---|---|---|
| 목적 | **성능** | **통제** (검사, 필터링, 감사) |
| 종료 지점의 위치 | 사용자 가까운 엣지 | 조직 경계 |
| 그 이름으로 인증할 권한의 출처 | 사이트가 개인키·발급 권한을 위임 | **기기의 신뢰 저장소에 루트 설치** |
| 누가 결정했는가 | **사이트** | **조직** |
| 사용자가 아는가 | 아니오 | 정책 문서상으로는, 실질적으로는 대개 아니오 |
| 평문을 보는 주체 | 엣지 사업자 | 조직의 보안 운영 |
| 클라이언트가 검증하는 것 | 엣지의 인증서 | 프록시의 인증서 |
| 뒤 구간의 보호 | 배포가 정한다 (표 19-3) | 프록시의 검증 정책이 정한다 |

**두 열의 마지막 세 줄이 동일하다.** 목적과 위치와 권한의 출처가 다를 뿐, **클라이언트가 검증하는 대상이 진짜 서버가 아니고, 그 뒤 구간의 보호가 검증 범위 밖에 있으며, 사용자는 그 사실을 알 수 없다**는 성질은 같다.

이것이 19.9절이 필요한 이유다. **TLS를 켠 뒤의 세계를 정확히 서술하려면, "TLS가 켜져 있다"는 사실만으로는 아무 조건도 확정되지 않는다는 것에서 출발해야 한다.**

> **이 절이 뒷받침하는 것**
>
> - `CONNECT`는 목적지를 평문으로 알린다 → **13.10** (메서드 자체와 그 남용), **13.5** (프록시가 목적지를 정하는 방식)
> - 터널에서 프록시가 아는 것은 한 줄과 SNI뿐이다 → **18.6** (SNI가 선택자가 된다), **19.9** (남는 메타데이터)
> - 검사 배치의 성립 조건은 신뢰 저장소 하나다 → **17.10** (검증의 두 번째 조건), **18.8** (`-CAfile`), **19.9**
> - 프록시의 검증 정책이 조직의 검증 정책이 된다 → **18.3** (검증의 다섯 단계), **17.9** (폐기 확인)
> - 두 종류의 정당한 중간자가 같은 구조다 → **19.2** (성능 쪽), **15.10** (계층 간 신뢰)

## 19.9 중간자 공격의 성립 조건 재검토 — TLS가 무엇을 더하는가

1.8절이 표 1-7을 남겼다. 하위 계층 공격을 세 줄로 정리한 표다.

**표 1-7 (1.8절, 재게재). 하위 계층 공격 조건과 상위 계층 가정**

| 공격 | 성립 조건 | 무너지는 상위 계층 가정 | 완화 수단 | 이 책에서 |
|---|---|---|---|---|
| 관찰 | 경로상 한 지점 접근 | 보낸 값은 상대만 본다 | TLS (내용에 한해) | 21.3, 23.3, 19.10 |
| 위조 | 발신자 미검증 프로토콜 | 출발지 주소 = 발신자 | TCP 핸드셰이크, 애플리케이션 인증 | 4.7, 8.6, 20.2 |
| 개입 | 관찰 + 경로 탈취 | 상대는 내가 의도한 상대다 | 인증서 검증, HSTS | 2.7, 18.3, 19.7, 19.9, 36.8 |

그 표의 "완화 수단" 열에 적힌 것들을 Part IV가 전부 펼쳤다. 17장이 인증서를, 18장이 검증을, 19.7절이 HSTS를 다뤘다. 이제 그 완화 수단들을 실제로 적용한 뒤의 상태를 다시 적을 차례다.

이 절의 방법은 단순하다. **TLS를 켜고, 무엇이 지워지고 무엇이 남는지를 하나씩 확인한 뒤, 표를 다시 쓴다.**

### 하나 — TLS를 켠 뒤에도 남는 것

가장 먼저 확인해야 할 것은 **관찰**이다. 표 1-7의 완화 수단 열에 이미 조건이 붙어 있었다. **"TLS (내용에 한해)."** 그 괄호를 지금 펼친다.

1.2절이 그림 1-1을 설명하며 세 번째 관찰로 적었다. **암호화되는 것은 TCP가 실어 나르는 페이로드다. 출발지·목적지 IP, 포트 번호, 패킷 크기, 전송 시각은 그대로 노출된다.** 그리고 18장이 그 목록에 세 줄을 더했다.

**표 19-15. TLS를 켠 뒤에도 관찰자가 얻는 것**

| 관찰 가능한 값 | 왜 남는가 | 이 책에서 | 무엇을 알려주는가 |
|---|---|---|---|
| 출발지·목적지 **IP 주소** | TLS는 IP 헤더 아래에 있지 않다 | 1.2 | 누가 누구와 통신하는가 |
| **포트 번호** | TCP 헤더는 암호화되지 않는다 | 1.2 | 어떤 서비스인가 (443 = HTTPS) |
| **패킷·레코드 크기** | 레코드 헤더의 길이 필드는 평문 | 1.2, 18.7 | 응답의 크기, 자원의 개수 |
| **전송 시각과 간격** | 암호화는 타이밍을 바꾸지 않는다 | 1.2 | 상호작용의 리듬, 페이지 전환 |
| **레코드의 종류** | 콘텐츠 타입 필드는 평문 | 18.7 | 핸드셰이크인지 데이터인지 알림인지 |
| **SNI의 호스트명** | `ClientHello`는 키 합의 이전이다 | 18.2, 18.6 | **정확히 어느 사이트인가** |
| **ALPN의 프로토콜 목록** | 같은 이유 | 18.2, 18.6 | 클라이언트의 성격 |
| **인증서 사슬 전체** | `Certificate`는 평문으로 전달된다 | 18.2 | 목적지의 신원, 사이트의 CA |
| **세션 ID / 세션 티켓** | `ClientHello`에 평문으로 실린다 | 19.1 | **재방문 여부** |
| **DNS 질의** | TLS 이전에 일어난다 | 2.7, 18.6 | 어느 이름을 찾았는가 |

이 표를 한 문장으로 요약하면 이렇다.

> **TLS는 "무엇을 말했는가"를 가리지만, "누가 누구와 언제 얼마나 말했는가"는 가리지 않는다.**

18.7절이 이미 같은 결론을 적었다. **관찰자가 얻는 것은 "누가 어느 사이트와 언제 얼마나"다.**

그리고 두 가지를 덧붙여야 한다.

**첫째, 이 값들은 선택자(selector)로 쓸 수 있다.** 18.6절이 SNI에 대해 지적한 것이다. **특정 이름으로 가는 커넥션만 골라 리셋하거나 다른 곳으로 돌리는 것이 가능하고, 그 판정에 복호는 필요하지 않다.** 즉 이 값들은 관찰의 재료일 뿐 아니라 **개입의 재료**이기도 하다. 내용을 읽지 못하는 참여자도 **어떤 커넥션을 끊을지는 정확히 고를 수 있다.**

**둘째, 크기와 타이밍은 그 자체로 정보다.** 19.5절이 압축을 다루며 확인한 구조가 그 극단적인 형태다. **길이가 내용에 의존하게 만들면, 길이의 관찰이 내용의 관찰이 된다.** 압축을 끄면 그 의존은 크게 줄지만 완전히 사라지지는 않는다. 응답의 크기는 여전히 응답의 크기이며, 크기가 다른 자원들 사이의 선택은 크기로 드러난다.

**따라서 표 1-7의 "관찰" 행은 지워지지 않는다. 축소될 뿐이다.**

### 둘 — 검증이 깨지면 TLS는 켜져 있으면서 보호하지 않는다

두 번째로 확인할 것은 **개입**이다. 표 1-7이 완화 수단으로 "인증서 검증"을 적었다. 17.10절이 그 검증이 성립하기 위한 세 조건을 세웠고, 표 17-16으로 정리했다. Part IV가 각 조건이 깨지는 방식을 절별로 다뤘으므로 이제 채워 넣을 수 있다.

**표 19-16. 검증 성립의 세 조건과 이 책이 확인한 깨짐의 실물**

| 조건 | 깨지는 방식 | 어디서 확인했는가 | 깨졌을 때의 상태 |
|---|---|---|---|
| **① 클라이언트가 실제로 검증한다** | 검증을 끄는 설정, 검증하지 않는 라이브러리 기본값, 삼켜지는 검증 실패 | 18.3 | 자물쇠는 표시되고 암호화도 실제로 된다. **상대가 다르다** |
| | **엣지가 오리진을 검증하지 않는 배치** | **19.2 표 19-3 (b)** | 사용자는 이 구간의 존재조차 모른다 |
| | **검사 프록시가 오리진을 검증하지 않는 배치** | **19.8** | 조직 전체가 검증하지 않는 것이 된다 |
| **② 신뢰 저장소가 오염되지 않았다** | 기기에 설치된 추가 루트 인증서 | 17.10, **19.8 표 19-13** | **경고 없이** 완전한 중간자가 성립한다 |
| | 사이트가 이름의 통제권을 위임 (CDN·엣지) | **19.2, 19.8** | 위임받은 지점이 그 이름으로 인증한다 |
| **③ 사용자가 경고를 무시하지 않는다** | 경고 대화상자 클릭 | 18.4 | 사용자가 스스로 중간자를 승인한다 |
| | **경고 자체가 없는 경우 (스킴 다운그레이드)** | **19.7 그림 19-3** | 무시할 경고조차 없다 |

굵게 표시한 줄들이 이 장이 더한 것이다. 17.10절은 세 조건을 원리로 세웠고, 19장은 **그 조건들이 실제로 깨지는 자리가 사용자의 부주의가 아니라 배포 결정이라는 것**을 보였다.

이 점이 중요하다. 조건 ①과 ②가 깨지는 가장 흔한 방식은 **악의적 공격이 아니라 정상적인 운영 결정**이다. 성능을 위한 조기 종료, 통제를 위한 검사 프록시, 편의를 위한 검증 비활성화. 그리고 그 결정들은 대개 **보안 검토를 거치지 않는다.** 성능 항목과 인프라 항목으로 분류되기 때문이다.

17.10절이 남긴 문장을 여기서 다시 적는다.

> **세 조건 중 하나라도 깨지면 TLS는 켜져 있으면서 보호하지 않는다.**

그리고 이 상태의 관측 불가능성을 강조해야 한다. **자물쇠 아이콘은 표시된다. 트래픽은 실제로 암호화된다. 수동적 관찰자는 아무것도 읽지 못한다. 브라우저의 인증서 정보 화면은 정상적인 인증서를 보여 준다.** 사용자가 이 상태와 정상 상태를 구별할 방법은 **없다.**

### 셋 — 의도된 중간자와 공격자

세 번째 확인 사항이 이 절의 중심이며, 앞의 두 절이 준비한 문장이다.

> **의도된 중간자와 공격자는 기술적으로 같은 위치에 있고, 차이는 신뢰 저장소에 무엇이 들어 있는지뿐이다.**

19.8절의 표 19-13이 이 명제를 배치별로 확인했다. 기업 검사 장비, CDN 종료, 개발자 프록시, 악성 소프트웨어 — **넷의 기술적 동작이 같고, 클라이언트는 넷을 구별할 수 없다.**

이 명제가 왜 이 장의 절정인지를 정확히 말해야 한다. 그것은 **TLS가 답하는 질문의 형태**에 관한 것이기 때문이다.

17.10절이 인증서가 무엇을 했는지를 이렇게 적었다. **인증서는 "내가 통신하는 상대는 내가 의도한 상대다"라는 가정을 "내가 통신하는 상대는 내가 입력한 이름의 통제권을 CA에게 증명한 주체다"로 바꿔 놓았다.**

이 전환은 실질적이다. 그러나 새 문장을 자세히 읽으면 두 개의 참조가 들어 있다.

- **"내가 입력한 이름"** — 이것을 정하는 것은 URL의 스킴과 호스트다. 19.7절이 다룬 스킴 다운그레이드가 이 참조를 공격한다.
- **"CA에게 증명한"** — 어느 CA인가. 그 답은 **내 신뢰 저장소에 있는 CA 중 아무나**다(17.10 논점 3). 그리고 그 저장소는 파일이다.

**두 번째 참조가 이 절의 결론을 만든다.** TLS의 인증은 "이 주체가 진짜인가"를 묻지 않는다. **"내 신뢰 저장소에 있는 누군가가 이 주체를 보증했는가"를 묻는다.** 그러므로 **신뢰 저장소를 쓸 수 있는 자는 이 질문의 답을 쓸 수 있다.**

기업이 검사 장비를 위해 루트를 설치할 때 하는 일이 정확히 그것이다. 그리고 악성 소프트웨어가 같은 일을 할 때, **프로토콜은 두 경우를 구별하지 않는다. 구별할 재료를 갖고 있지 않기 때문이다.**

여기서 이 책의 논지가 다시 확인된다. **HTTP의 모든 확장은 신뢰 경계를 하나씩 추가하는 일이었다.** TLS는 그 목록에서 예외처럼 보인다. 경계를 추가한 것이 아니라 경계를 **세운** 것처럼 보이기 때문이다. 그러나 정확히 말하면 TLS가 한 일은 **경계를 신뢰 저장소라는 하나의 파일로 옮긴 것**이다. 경계는 여전히 있고, 그것을 정하는 것은 이제 파일의 내용이다.

### 넷 — 갱신된 표

이제 표 1-7을 다시 쓴다. 이 표가 이 장의 산출물이고, Part IV 전체의 산출물이다.

**표 19-17. TLS를 켠 뒤의 공격 조건 — 표 1-7의 갱신 (이 책이 구성. 근거: 1.2, 1.8, 17.7~17.10, 18.2~18.7, 19.2, 19.5~19.8)**

| 공격 | TLS 이전의 성립 조건 | **TLS 이후의 성립 조건** | 여전히 무너지는 가정 | 남는 이유 |
|---|---|---|---|---|
| **관찰 (내용)** | 경로상 한 지점 접근 | 경로 접근 + **다음 중 하나**: ① 종료 지점에 접근 ② 신뢰 저장소에 루트 설치 ③ 스킴 다운그레이드 성공 ④ 검증 미수행 | — (조건을 만족하면 전면 관찰) | 조건 ①~④가 배포 결정으로 자주 성립한다 |
| **관찰 (메타데이터)** | 경로상 한 지점 접근 | **경로상 한 지점 접근 — 변화 없음** | "누구와 통신하는지는 내 일이다" | **TLS는 헤더 아래를 가리지 않는다** (표 19-15) |
| **위조 (출발지)** | 발신자 미검증 프로토콜 | **TCP 위에서는 이미 어려웠고, TLS가 세션 단위로 봉인한다** | — | 커넥션이 세워진 뒤의 주입은 MAC이 막는다 (→ 18.7) |
| **개입 (내용 변경)** | 관찰 + 경로 탈취 | 경로 탈취 + **그 이름으로 인증할 능력** | "상대는 내가 의도한 상대다" | 능력의 출처가 넷이다 (표 19-13) |
| **개입 (커넥션 차단·선별)** | 경로 탈취 | **경로 탈취 — 변화 없음** | "연결은 방해받지 않는다" | **SNI·IP·크기로 선별 가능** (→ 18.6) |
| **개입 (평문 유도)** | — | **HTTPS 이전의 한 번**을 잡으면 된다 | "나는 HTTPS를 쓰고 있다" | 최초 접속의 창 (표 19-12), 혼합 콘텐츠 (→ 19.10) |

여섯 줄 중 **세 줄이 "변화 없음" 또는 새로 생긴 줄**이라는 점이 이 표의 요점이다.

한 줄씩 읽어 두자.

**관찰(내용) 줄이 TLS가 실제로 해낸 것이다.** 조건이 "경로 접근"에서 "경로 접근 + α"로 올라갔다. 17.10절이 "공격의 조건이 네트워크 접근에서 네트워크 접근 + CA 체계에 대한 공격으로 올라갔다"고 적은 것이 이 줄이며, 이 장이 α의 목록을 네 항목으로 채웠다. **그리고 α의 네 항목 중 셋이 공격이 아니라 배포다.**

**관찰(메타데이터) 줄은 새로 만든 줄이다.** 표 1-7은 관찰을 한 줄로 다뤘고 완화 수단에 "(내용에 한해)"라는 괄호를 달았다. 그 괄호가 이제 독립된 줄이 될 만큼 자랐다. 표 19-15가 그 내용이며, **이 줄의 성립 조건은 TLS 이전과 정확히 같다.**

**위조 줄이 유일하게 확실히 개선된 줄이다.** 커넥션이 수립된 뒤에는 레코드마다 MAC이 붙고 일련번호가 계산에 포함되므로(→ 18.7), 경로상의 참여자가 바이트를 주입하거나 재정렬하거나 삭제하면 즉시 드러난다. **표 1-7의 "출발지 주소 = 발신자"라는 가정을, TLS는 세션 단위로 실제로 보증한다.** 단, 그 보증은 **커넥션 하나 안에서만** 성립한다는 조건이 붙는다.

**개입(내용 변경) 줄이 이 표에서 가장 중요하다.** 조건이 "관찰 + 경로 탈취"에서 "경로 탈취 + 그 이름으로 인증할 능력"으로 바뀌었다. 능력의 출처는 넷이다. 신뢰 저장소에 루트를 넣기, 사이트로부터 개인키·발급 권한을 위임받기, CA 하나를 오용하기, 클라이언트가 검증하지 않게 만들기. **첫 두 항목은 정당한 운영 절차이고, 세 번째는 17.10절이 웹 PKI의 가장 무거운 성질로 지목한 것이며, 네 번째는 설정 항목이다.**

**개입(차단·선별) 줄도 새로 만든 줄이다.** 표 1-7은 개입을 "내용 변경"의 의미로만 다뤘다. 그러나 경로를 통제하는 자에게는 다른 선택지가 있다. **끊는 것.** 그리고 표 19-15의 값들이 무엇을 끊을지 고르는 데 충분하다. **가용성에 대한 공격에는 TLS가 아무것도 하지 않는다.** 45장이 가용성을 별도로 다루는 이유가 이런 자리에 있다.

**개입(평문 유도) 줄은 TLS 때문에 생긴 줄이다.** TLS 이전에는 이런 공격이 필요 없었다. 모든 것이 평문이었기 때문이다. TLS가 켜지자 **평문 구간을 찾거나 만드는 것 자체가 하나의 공격 유형**이 되었다. 19.7절의 스킴 다운그레이드와 19.10절의 혼합 콘텐츠가 이 줄의 두 형태다.

### 능동적 중간자가 무엇을 할 수 있는가

마지막 줄을 조금 더 구체적으로 채워 두자. WAHH가 이 지점에 관해 남긴 관찰이 있고, 그것이 19.10절과 36.8절로 이어진다.

원서의 출발 문장이 이렇다. **애플리케이션이 민감한 데이터 전부에 HTTPS를 쓰고 대상 사용자가 HTTPS가 제대로 쓰이는지를 항상 확인하더라도, 여전히 심각한 공격이 성립할 수 있다는 것이 더 놀라운 사실이다.**

이 공격들은 **능동적(active) 중간자**를 요구한다. 다른 사용자의 트래픽을 수동적으로 감시하는 데서 그치지 않고 **그 트래픽의 일부를 실시간으로 변경하는** 유형이다. 더 정교한 공격이지만 **공용 무선 핫스팟, 공유 사무실 네트워크를 비롯한 여러 흔한 상황에서, 그리고 그럴 의향이 있는 정부에 의해 충분히 실행될 수 있다.**

핵심 기법은 **평문 HTTP 요청을 유도하는 것**이다. 그리고 원서가 지적하는 것은 그 유도가 대상 사이트를 경유하지 않아도 된다는 점이다. **공격자는 사용자가 다른 아무 도메인에 보내는 HTTP 요청에 대해 리다이렉션 응답을 돌려주는 것만으로 대상 도메인에 대한 평문 요청을 유도할 수 있다.** 애플리케이션이 80번 포트에서 아예 듣고 있지 않더라도, **공격자가 그 유도된 요청을 가로채 임의의 콘텐츠로 응답할 수 있다.**

여기서 원서가 던지는 질문이 이 절의 마지막 조각이다. **보안에 극도로 신경 쓰는 사용자라면 안전한가?** 한 번에 한 사이트만 접속하고, 새 사이트에 접속할 때마다 브라우저를 재시작하고, 깨끗한 새 브라우저에서 순수 HTTPS만 쓰는 은행 애플리케이션에 로그인한다면?

**원서의 답은 "그래도 아마 뚫린다"이다.** 이유는 이렇다. **오늘날의 브라우저는 사용자가 어느 도메인을 방문하든 상관없이 배경에서 수많은 평문 HTTP 요청을 보낸다.** 안티피싱 목록, 버전 핑, RSS 피드 요청 같은 것들이다. **공격자는 그 요청들 중 아무것에나 대상 도메인으로의 HTTP 리다이렉션으로 응답할 수 있다.** 브라우저가 그 리다이렉션을 조용히 따라가면, 앞서 서술한 공격 중 하나가 전달되어 **먼저 대상 도메인의 HTTP 오리진을 장악하고, 그다음 그것을 HTTPS 오리진으로 확대한다.**

이 서술이 표 19-17의 마지막 줄에 실체를 준다. **"HTTPS 이전의 한 번"은 사용자가 만드는 것이 아니라 브라우저가 만든다.** 그러므로 사용자의 주의로 막을 수 있는 것이 아니다.

그리고 이 관찰이 19.7절의 HSTS 평가를 다시 조정한다. HSTS 선언을 받아 둔 도메인에 대해서는 브라우저가 평문 요청을 아예 보내지 않으므로 이 경로가 막힌다. **HSTS의 가치가 표 19-12의 창 크기에 반비례해서 결정된다는 뜻이며, 그래서 그 창을 좁히는 일 — `max-age`를 길게, `includeSubDomains`를 켜서 — 이 실질적인 보안 조치가 된다.**

HTTP 오리진에서 HTTPS 오리진으로 장악을 확대하는 구체적 경로 — 쿠키 주입, 절대 URL 스크립트 인클루드 — 는 19.10절이 다룬다. 그리고 **36.8절이 이 전체를 브라우저 공격의 실행 층위에서 다시 받는다.** 이 절이 조건의 언어로 적은 것을, 그 절은 브라우저가 실제로 무엇을 하는지의 언어로 적는다.

### Part IV가 남기는 것

이 절을 이 문장으로 닫는다.

> **TLS를 켰다는 사실만으로는 표 19-17의 어느 줄도 확정되지 않는다. 확정하는 것은 배포다.**

Part IV의 네 장이 이 문장의 근거를 하나씩 쌓았다. 17장이 인증서가 무엇을 묶는지를 정확히 적었고, 18장이 검증이 실제로 무엇을 확인하는지를 다섯 단계로 펼쳤으며, 19장이 그 검증이 놓이는 자리 — 종료 지점, 신뢰 저장소, 최초 접속의 창 — 를 배포의 언어로 서술했다.

그리고 남은 질문 하나가 Part V로 넘어간다. **채널이 이 정도로만 보호될 때, 그 채널 위로 흐르는 신원과 세션은 어떻게 다뤄야 하는가.** 19.10절이 그 질문의 첫 조각을 다룬다.

> **이 절이 뒷받침하는 것**
>
> - 메타데이터는 TLS 이전과 같은 조건으로 관찰된다 → **1.2** (TLS가 가리지 않는 것), **18.6** (SNI), **18.7** (레코드 헤더)
> - 검증의 세 조건이 배포 결정으로 깨진다 → **17.10** (조건의 원리), **19.2, 19.8** (깨지는 배치)
> - 의도된 중간자와 공격자는 같은 위치에 있다 → **19.8 표 19-13**, **1.8**
> - 표 19-17 전체 → **36.8** (브라우저 실행 층위에서의 같은 공격), **23.3, 23.5** (세션 층위에서의 귀결), **45장** (가용성 줄)
> - 브라우저가 배경 평문 요청을 보낸다 → **19.7** (HSTS의 창), **19.10** (그 창에서 일어나는 일)

## 19.10 네트워크상의 토큰 노출과 혼합 콘텐츠

표 19-17의 마지막 줄 — **평문 유도** — 이 실제로 무엇을 가져가는지를 이 절이 다룬다. 답은 대개 **세션 토큰**이다.

### 노출의 위치

이 취약점 영역은 **세션 토큰이 암호화되지 않은 형태로 네트워크를 건널 때** 발생한다. 그러면 적절한 위치에 있는 도청자가 토큰을 얻어 **정당한 사용자로 위장할 수 있다.**

원서가 도청에 적합한 위치를 열거한 목록은 그대로 옮길 값이 있다.

**표 19-18. 토큰 도청이 가능한 위치 (WAHH 7장 "Disclosure of Tokens on the Network" 기준)**

| 위치 | 누가 |
|---|---|
| 사용자의 로컬 네트워크 | 같은 네트워크의 누구든 |
| 사용자의 IT 부서 내부 | 권한 있는 인력, 그리고 그 인프라를 침해한 외부 공격자 |
| 사용자의 ISP 내부 | 〃 |
| 인터넷 백본 | 〃 |
| 애플리케이션의 ISP 내부 | 〃 |
| 애플리케이션을 호스팅하는 조직의 IT 부서 내부 | 〃 |

원서가 각 항목에 붙인 단서가 중요하다. **각 경우에 해당 조직의 권한 있는 인력과, 그 인프라를 침해한 외부 공격자가 모두 포함된다.**

이 목록을 19.2절의 마지막 항목 — "평문을 보는 주체의 목록을 만든다" — 과 나란히 놓아야 한다. **조기 종료를 도입하면 이 표에 줄이 하나 추가된다. 엣지 사업자와 그 인력, 그리고 엣지 노드가 놓인 관할권.** 19.8절의 검사 프록시를 도입하면 또 한 줄이 추가된다. **두 배치 모두 "그 구간에서 토큰은 평문이다"라는 성질을 공유한다.**

전면 평문 HTTP를 쓰는 가장 단순한 경우에는 **공격자가 클라이언트–서버 사이의 모든 데이터를 잡을 수 있다.** 로그인 자격 증명, 개인정보, 결제 정보 전부다. **이 상황에서는 사용자의 세션을 노리는 공격이 대개 불필요하다.** 이미 특권 정보를 볼 수 있고, 잡은 자격 증명으로 직접 로그인해 다른 악의적 행위를 할 수 있기 때문이다.

그럼에도 **세션 자체가 주된 표적이 되는 경우**가 있다. 원서가 두 가지를 든다.

- **잡은 자격 증명만으로는 두 번째 로그인을 수행할 수 없는 경우.** 예컨대 은행 애플리케이션에서 자격 증명에 **변화하는 물리 토큰의 숫자**나 **PIN의 특정 자릿수**가 포함된다면, 공격자는 도청한 세션을 하이재킹해야 임의의 행위를 할 수 있다.
- **로그인이 면밀히 감사되고 사용자가 성공적인 로그인마다 통보를 받는 경우.** 공격자는 가능한 한 은밀하기 위해 자기 로그인을 수행하지 않으려 할 수 있다.

두 번째 항목은 16.5절이 방어자의 로그를 다루며 정리한 구조가 실제로 공격자의 행동을 바꾸는 사례다. **감사와 경보가 공격을 막지 못해도 공격의 형태를 바꾼다.**

### HTTPS를 써도 토큰이 새는 여섯 경로

이 절의 본론은 여기다. **애플리케이션이 핵심 클라이언트–서버 통신을 보호하기 위해 HTTPS를 쓰면서도 여전히 네트워크상의 세션 토큰 가로채기에 취약할 수 있다.** 이 약점은 여러 방식으로 발생하며, **그중 다수는 HTTP 쿠키가 세션 토큰의 전송 수단으로 쓰일 때 특히 발생한다.**

**표 19-19. HTTPS 사이트에서 토큰이 평문으로 나가는 경로 (WAHH 7장 기준, 대응 절은 이 책이 구성)**

| # | 경로 | 무엇이 새는가 | 대응 |
|---|---|---|---|
| ① | **로그인만 HTTPS**, 이후 세션 전체는 HTTP | 자격 증명은 안전하지만 **세션 토큰이 통째로** 노출 | 20.6, 19.7 |
| ② | 사전 인증 영역은 HTTP, 로그인부터 HTTPS. **그런데 로그인 시 토큰을 교체하지 않는다** | 로그인 전에 잡은 토큰이 **로그인 후 인증된 세션의 토큰이 된다** | **23.4** (세션 고정), 23.6 |
| ③ | 로그인 후 새 토큰을 발급하고 이후 HTTPS를 쓰지만, 사용자가 **사전 인증 페이지를 재방문** | 인증된 세션의 토큰이 그 요청에 실려 평문으로 | 20.6 (`Secure`) |
| ④ | 로그인 링크를 클릭할 때 HTTPS로 전환하지만, **URL을 고치면 HTTP 로그인도 받아준다** | 능동적 중간자가 사전 인증 페이지의 로그인 링크를 HTTP로 바꾼다 → **자격 증명과 토큰 모두** | 19.7 (HSTS), 서버에서 HTTP 로그인 거부 |
| ⑤ | **정적 콘텐츠(이미지·스크립트·스타일시트·템플릿)만 HTTP** — 혼합 콘텐츠 | 그 요청에 쿠키가 실린다. **브라우저 경고가 뜰 때는 이미 전송된 뒤다** | 20.6, 상대 URL |
| ⑥ | 전면 HTTPS여도 **공격자가 사용자에게 HTTP 요청을 유발** | 유발된 요청에 토큰이 실린다 | 20.6, 19.7 |

각 줄에 붙일 설명이 있다.

**①번.** 많은 웹메일 애플리케이션이 이렇게 동작했다. **도청자는 자격 증명을 가로챌 수 없지만 세션 토큰은 잡을 수 있다.** 원서는 이 과정을 손쉽게 만든 브라우저 확장 도구가 공개되었다고 적는다. 자격 증명을 지켰다는 사실이 **세션을 지켰다는 뜻이 아니라는 것**을 이 줄이 보여준다. 22장이 인증을, 23장이 세션을 별도의 장으로 다루는 이유가 이런 자리다.

**②번.** 사용자가 첫 페이지를 방문한 시점에 토큰이 발급되고, **로그인해도 그 토큰이 바뀌지 않는다.** 원래 인증되지 않았던 세션이 로그인 후 인증된 세션으로 **승격(upgrade)** 된다. 이 경우 도청자는 **로그인 전에 토큰을 가로챈 뒤, 사용자의 통신이 HTTPS로 전환되는 것을 보고 로그인했음을 알아채고, 그 토큰으로 보호된 페이지(예: 내 계정)에 접근을 시도한다.**

이 형태는 23.4절이 다룰 **세션 고정(session fixation)** 과 정확히 같은 구조를 다른 방향에서 본 것이다. 세션 고정에서는 공격자가 토큰을 심고, 여기서는 공격자가 토큰을 훔치지만, **문제의 뿌리는 같다. 인증 상태가 바뀔 때 토큰이 바뀌지 않는다.** 23.6절이 세션 강화의 항목으로 "인증 상태 전환 시 토큰 재발급"을 두는 근거가 여기와 그곳 양쪽에 있다.

**③번.** 로그인 후 새 토큰을 발급하고 로그인 페이지부터 HTTPS를 쓰더라도, **인증된 세션의 토큰이 여전히 노출될 수 있다.** 사용자가 사전 인증 페이지(도움말, 소개 등)를 다시 방문하면 그렇게 된다. **인증 영역 안의 링크를 따라가거나, 뒤로 가기 버튼을 쓰거나, URL을 직접 입력해서.**

이 줄이 보여주는 것은 **애플리케이션의 어느 한 부분이 평문이면 그 부분으로 가는 모든 경로가 노출 경로가 된다**는 사실이다. 그리고 그 경로에는 사용자가 의식적으로 만드는 것(링크 클릭)뿐 아니라 브라우저가 만드는 것(뒤로 가기)도 포함된다.

**④번.** 이것이 표 19-17의 "평문 유도" 줄의 전형이다. **적절한 위치에 있는 공격자가 사이트의 사전 인증 영역에서 반환되는 페이지를 변경해 로그인 링크가 HTTP 페이지를 가리키게 만든다.** 애플리케이션이 로그인 성공 후 새 세션 토큰을 발급하더라도, **공격자가 사용자의 커넥션을 HTTP로 다운그레이드하는 데 성공했다면 그 토큰도 가로챌 수 있다.**

19.7절의 그림 19-3이 이 배치이며, HSTS의 두 번째 규칙 — **비보안 링크를 클라이언트에서 자동으로 HTTPS로 변환** — 이 정확히 이것을 겨냥한다.

**⑤번이 혼합 콘텐츠(mixed content)다.** 애플리케이션이 이미지, 스크립트, 스타일시트, 페이지 템플릿 같은 **정적 콘텐츠 전부를 HTTP로** 서비스하는 경우다. 이 동작은 대개 브라우저의 경고로 나타나는데, 원서가 강조하는 것은 그 경고의 타이밍이다.

> **브라우저가 이 경고를 표시하는 시점에는 이미 해당 항목을 HTTP로 가져온 뒤이며, 따라서 세션 토큰은 이미 전송되었다.** 브라우저 경고의 목적은 사용자로 하여금 HTTP로 받아 오염되었을 수 있는 응답 데이터를 처리하지 않도록 거부할 기회를 주는 것이다.

**경고는 유출을 막지 못한다. 유출된 뒤에 오염을 막으려는 것이다.** 18.4절이 경고 대화상자에 대해 내린 판정 — 결정할 수 없는 자리에 놓인 결정 — 에 한 줄을 더할 수 있다. **어떤 경고는 결정할 수 없는 자리에 놓였을 뿐 아니라 결정이 무의미해진 시점에 놓인다.**

**⑥번.** 애플리케이션이 모든 페이지에, 비인증 영역과 정적 콘텐츠까지 포함해 HTTPS를 쓰더라도 토큰이 HTTP로 전송되는 상황이 있을 수 있다. **공격자가 어떻게든 사용자로 하여금 HTTP 요청을 하게 만들 수 있다면** — 같은 서버에서 HTTP 서비스가 돌고 있다면 그쪽으로, 아니면 `http://server:443/` 같은 형태로 — 토큰이 제출될 수 있다.

원서가 드는 유발 수단은 **이메일이나 인스턴트 메시지로 URL 보내기, 공격자가 통제하는 웹사이트에 자동 로드되는 링크 넣기, 클릭 가능한 배너 광고 이용하기**다. 그리고 19.9절이 인용한 WAHH 13장의 관찰을 더하면 목록이 하나 더 늘어난다. **브라우저가 배경에서 스스로 보내는 평문 요청.**

`http://server:443/`이라는 형태를 눈여겨 둘 값이 있다. **포트 443에 평문 HTTP 요청을 보내는 것**이다. 서버는 그것을 TLS 레코드로 해석하려다 실패하고 커넥션을 닫을 것이다 — 18.1절이 인용한 원서의 문장, "SSL과 HTTP 트래픽이 모두 80번 포트로 도착한다면 대부분의 웹 서버는 바이너리 SSL 트래픽을 잘못된 HTTP로 해석하고 커넥션을 닫을 것이다"의 반대 방향이다. **그러나 요청은 이미 나갔고, 그 안에 쿠키가 들어 있었다.** 서버가 그것을 어떻게 처리하는지는 중요하지 않다. 경로상의 관찰자에게는 이미 도착했다.

### 혼합 콘텐츠의 두 번째 얼굴 — 능동적 콘텐츠

지금까지는 혼합 콘텐츠를 **노출**의 문제로 다뤘다. 다른 얼굴이 하나 더 있고, 그것이 더 심각하다.

WAHH 13장이 이 지점을 다룬다. **많은 애플리케이션이 제품 설명이나 도움말 페이지 같은 비민감 콘텐츠에 HTTP를 쓴다. 그런 콘텐츠가 절대 URL로 스크립트를 인클루드한다면, 능동적 중간자 공격으로 같은 도메인의 HTTPS 보호 요청을 침해할 수 있다.**

```html
<script src="http://joes-hardware.com/help.js"></script>
```

원서는 이 형태 — **HTTP로 스크립트를 인클루드하는 절대 URL** — 가 오늘날 웹의 수많은 유명 애플리케이션에 나타난다고 적는다.

공격의 구조는 두 단계다.

**첫 단계.** 능동적 중간자는 물론 아무 HTTP 응답이나 변경해 임의의 스크립트 코드를 실행시킬 수 있다. **그러나 동일 출처 정책은 일반적으로 HTTP로 로드된 콘텐츠와 HTTPS로 로드된 콘텐츠를 서로 다른 오리진으로 취급하므로**, 그것만으로는 HTTPS로 접근된 콘텐츠를 침해할 수 없다. 34장이 동일 출처 정책을 다루며 정리할 규칙 — **스킴도 오리진의 일부다** — 이 여기서 방어선 역할을 한다.

**둘째 단계가 그 방어선을 넘는다.** 공격자는 **HTTP 응답을 변경해 리다이렉션을 일으키거나 다른 응답에서 링크의 대상을 다시 씀으로써, 사용자가 같은 페이지를 HTTPS로 로드하도록 유도한다.** 사용자가 도움말 페이지를 HTTPS로 로드하면, **브라우저는 그 안에 지정된 스크립트 인클루드를 HTTP로 수행한다.** 그리고 원서가 강조한다. **결정적으로, 일부 브라우저는 이 상황에서 아무 경고도 표시하지 않는다.** 공격자는 인클루드된 스크립트에 대한 응답으로 임의의 코드를 돌려준다. **그 스크립트는 HTTPS 응답의 컨텍스트에서 실행되며, 공격자가 이 콘텐츠와 HTTPS로 접근되는 이후의 콘텐츠를 침해할 수 있게 한다.**

**즉 HTTPS 페이지가 부른 HTTP 스크립트는 HTTPS 오리진의 권한으로 실행된다.** 이것이 혼합 콘텐츠에서 **수동적 콘텐츠(이미지)** 와 **능동적 콘텐츠(스크립트)** 를 구별하는 이유다.

**표 19-20. 혼합 콘텐츠의 두 유형 (WAHH 7장·13장 기준, 구분은 이 책이 구성)**

| 유형 | 예 | 무엇이 새는가 | 무엇이 더 가능한가 |
|---|---|---|---|
| **수동적** | 이미지, 미디어 | 그 요청에 실린 **세션 토큰** | 표시되는 이미지의 교체 |
| **능동적** | 스크립트, 스타일시트, 프레임 | 세션 토큰 | **HTTPS 오리진에서의 코드 실행** — 페이지 전체의 장악 |

능동적 콘텐츠 줄이 32장(XSS)의 결과와 같다는 점을 적어 둔다. **다른 점은 취약점이 애플리케이션 코드가 아니라 네트워크 배치에 있다는 것뿐이다.** 애플리케이션에 XSS가 하나도 없어도 이 경로는 열려 있다.

### 애플리케이션이 순수 HTTPS일 때도

원서는 한 걸음 더 나간다. **대상 애플리케이션이 어떤 콘텐츠에도 평문 HTTP를 쓰지 않는다고 하자.** 그래도 공격자는 앞서 본 방법으로 대상 도메인에 대한 평문 HTTP 요청을 유도할 수 있고, **애플리케이션이 80번 포트에서 듣고 있지 않더라도 그 유도된 요청을 가로채 임의의 콘텐츠로 응답할 수 있다.**

그 상태에서 HTTPS 오리진으로 침해를 확대하는 두 기법을 원서가 든다.

**첫째, 쿠키 주입.** 공격자는 **평문 HTTP 응답을 이용해 HTTPS 요청에 쓰이는 쿠키 값을 설정하거나 갱신할 수 있다.** 그리고 원서가 강조하는 것은 그 대상 범위다. **원래 HTTPS로 설정되었고 `Secure` 플래그가 붙은 쿠키에 대해서도 이것이 가능하다.** 어떤 쿠키 값이 HTTPS 오리진에서 도는 스크립트 코드에 의해 안전하지 않게 처리된다면, **쿠키 주입 공격으로 그 쿠키를 통해 XSS 익스플로잇을 전달할 수 있다.**

이 사실이 20.6절의 `Secure` 속성 평가를 정확하게 만든다. **`Secure`는 쿠키가 평문으로 나가는 것을 막지만, 평문으로 들어오는 것을 막지 않는다.** 기밀성은 보호하고 무결성은 보호하지 않는다. 17.7절이 세운 명제 — **암호화, 인증, 무결성은 서로 다른 문제다** — 가 쿠키 속성 하나에서 확인되는 자리다. 20.9절이 쿠키 인젝션과 쿠키 조작을 별도 절로 다루는 근거가 여기에 있다.

**둘째, 브라우저 확장.** 원서의 지적은 **일부 브라우저 확장이 HTTP로 로드된 콘텐츠와 HTTPS로 로드된 콘텐츠를 제대로 분리하지 않고 사실상 하나의 오리진으로 취급한다**는 것이다. 유도된 HTTP 요청의 응답으로 반환된 공격자의 스크립트가 그런 확장을 이용해 **사용자가 HTTPS로 접근한 페이지의 내용을 읽거나 쓸 수 있다.** 36장이 브라우저 자체에 대한 공격을 다루며 이 범주를 확장한다.

### 무엇을 하는가

이 절의 방어 항목을 정리하면 이렇다. 대부분이 다른 장에서 상세히 다뤄지므로 여기서는 목록과 참조를 남긴다.

- **세션 토큰 쿠키에 `Secure` 속성을 설정한다.** 그러면 그 쿠키는 암호화되지 않은 커넥션으로 절대 전송되지 않는다(→ 20.6). **단, 위에서 본 대로 이것은 유출만 막고 주입은 막지 못한다.**
- **애플리케이션 전체를 HTTPS로 서비스한다.** 사전 인증 영역과 정적 콘텐츠를 포함해서. 표 19-19의 ①~⑤가 모두 이 조치 하나로 닫힌다.
- **HSTS를 선언하고 창을 좁힌다**(→ 19.7). ⑥과 ④에 대한 대응이며, `max-age`를 충분히 길게, 서브도메인 포함을 켜서 표 19-12의 창을 줄인다.
- **인증 상태가 전환될 때 토큰을 재발급한다**(→ 23.4, 23.6). ②에 대한 대응.
- **HTTP로 도착한 인증 세션 토큰을 즉시 무효화한다.** 원서의 확인 항목 6번이 그것을 확인하라고 지시한다. 노출된 토큰은 노출된 것이며, 계속 유효하게 두는 것은 노출을 이용 가능하게 두는 것이다.
- **절대 URL로 자기 도메인의 자원을 인클루드하지 않는다.** 상대 경로를 쓰면 스킴이 현재 페이지를 따라간다. 이것이 능동적 혼합 콘텐츠에 대한 가장 단순한 구조적 방어다.
- **80번 포트에서 무엇이 도는지 확인한다.** 전면 HTTPS를 선언한 서버가 여전히 80번에서 무언가를 서비스하고 있는 일이 흔하다.

### 확인 절차

원서가 제시하는 점검 절차를 이 책의 형태로 옮긴다. 25장이 애플리케이션 매핑을 다루며 같은 방법을 일반화한다.

1. **애플리케이션을 처음 접속(시작 URL)부터 로그인 과정을 거쳐 모든 기능까지 정상적으로 순회한다.** 방문한 모든 URL을 기록하고, **새 세션 토큰이 발급되는 모든 지점을 기록한다.** 로그인 기능과 **HTTP·HTTPS 사이의 전환 지점**에 특히 주의한다. 네트워크 스니퍼로 수동으로 하거나, 인터셉팅 프록시의 로깅 기능으로 부분 자동화할 수 있다.
2. **세션 토큰의 전송 수단이 HTTP 쿠키라면 `Secure` 플래그가 설정되어 있는지 확인한다.**
3. **애플리케이션의 정상적인 사용 과정에서 세션 토큰이 암호화되지 않은 커넥션으로 전송되는 일이 있는지 판정한다.** 있다면 그 토큰은 **가로채기에 취약한 것으로 간주해야 한다.**
4. **시작 페이지가 HTTP이고 로그인·인증 영역에서 HTTPS로 전환되는 경우**, 로그인 후 새 토큰이 발급되는지, 아니면 HTTP 단계에서 전송된 토큰이 인증된 세션의 추적에 계속 쓰이는지 확인한다. **로그인 URL을 고쳐서 HTTP 로그인을 시도하면 애플리케이션이 받아들이는지도 확인한다.**
5. **모든 페이지에 HTTPS를 쓰더라도 서버가 80번 포트에서도 듣고 있는지 확인한다.** 그렇다면 인증된 세션 안에서 HTTP URL을 직접 방문해 **세션 토큰이 전송되는지 확인한다.**
6. **인증 세션의 토큰이 HTTP로 서버에 전송된 경우, 그 토큰이 계속 유효한지 아니면 서버가 즉시 종료하는지 확인한다.**

> **이 절이 뒷받침하는 것**
>
> - `Secure`는 유출을 막고 주입을 막지 않는다 → **20.6** (쿠키 속성), **20.9** (쿠키 인젝션), **17.7** (기밀성과 무결성은 다른 문제)
> - 인증 전환 시 토큰이 바뀌지 않으면 사전 인증 토큰이 승격된다 → **23.4** (세션 고정), **23.6** (세션 강화)
> - 토큰의 네트워크 노출 전반 → **23.3** (토큰 처리의 약점), **1.8** (표 1-7의 관찰 행)
> - HTTPS 페이지가 부른 HTTP 스크립트는 HTTPS 오리진에서 실행된다 → **34장** (동일 출처 정책과 스킴), **32장** (같은 결과를 만드는 다른 경로), **36.8**
> - 혼합 콘텐츠 경고는 전송 후에 뜬다 → **18.4** (경고의 자리), **19.7** (HSTS의 자동 변환)

### 성능 체크리스트

### 검증 방법

원서의 조언은 두 갈래다. **첫째, Qualys SSL Server Test 같은 온라인 서비스로 공개 서버를 스캔해 흔한 설정·보안 결함을 찾을 수 있다. 둘째, `openssl` 명령줄 인터페이스에 익숙해져야 한다.** 그것으로 **서버의 전체 핸드셰이크와 설정을 로컬에서 검사할 수 있다.**

기본 사용법과 출력 읽는 법은 18.8절이 그림 18-6과 표 18-13으로 다뤘다. 여기서는 **19장의 각 절이 요구하는 확인**을 붙인다.

**표 19-23. 19장의 각 절을 확인하는 방법 (도구 사용법은 이 책이 구성)**

| 확인할 것 | 방법 | 무엇을 보는가 | 절 |
|---|---|---|---|
| **재개가 실제로 동작하는가** | `openssl s_client -connect HOST:443 -reconnect` | 두 번째 이후 연결에서 `Reused` 표시. 나오지 않으면 재개가 꺼져 있다 | **19.1, 19.3** |
| 세션 ID가 발급되는가 | 출력의 `Session-ID` 줄이 비어 있지 않은지 | 비어 있으면 세션 캐싱이 꺼져 있다 | 19.1 |
| 세션 티켓이 발급되는가 | 출력의 `TLS session ticket` 블록 유무 | 없으면 무상태 재개가 꺼져 있다 | 19.1 |
| 세션 타임아웃 | 출력의 `Timeout : NNN (sec)` | 캐시/티켓 수명 | 19.3 |
| 세션 캐시 히트율 | 서버의 통계 (예: 상태 모듈, 로그) | **재개율이 낮으면 설정이 무효** | 19.3 |
| **사슬의 바이트 수** | 출력의 `SSL handshake has read N bytes` | **N이 초기 cwnd(약 4 KB)에 가까운지** | **19.6** |
| 사슬의 인증서 수 | 출력의 `Certificate chain` 항목 수 | **2장이 이상. 루트가 포함되어 있으면 제거** | 19.6 |
| 사슬의 각 인증서 확인 | `openssl s_client -showcerts -connect HOST:443` | 발급자 관계, 불필요한 인증서 | 19.6, 17.8 |
| **압축이 꺼져 있는가** | 출력의 `Compression:` 줄 | **`NONE`이어야 한다** | **19.5** |
| **OCSP 스테이플링** | `openssl s_client -status -connect HOST:443` | `OCSP Response Status: successful` 유무. **없으면 붙지 않는 것이다** | **19.6** |
| 스테이플 포함 후 총 크기 | `-status` 실행 시의 `read N bytes` 대조 | **스테이플이 사슬을 혼잡 윈도우 밖으로 밀어내는가** | 19.6 |
| **HSTS 헤더** | `curl -sI https://HOST/ \| grep -i strict` | `max-age` 값, `includeSubDomains` 유무 | **19.7** |
| **80번 포트의 상태** | `curl -sI http://HOST/` | 무엇이 응답하는가. 리다이렉트인가 콘텐츠인가 | **19.10** |
| 혼합 콘텐츠 | 페이지 소스에서 `http://` 절대 URL 검색, 브라우저 개발자 도구의 네트워크 탭 | **HTTPS 페이지가 부르는 HTTP 자원** | 19.10 |
| 레코드 크기 | 패킷 캡처에서 TLS 레코드 길이 분포 | 세그먼트를 넘치는 레코드가 있는가 | 19.4 |
| 종료 지점의 오리진 검증 | **설정 파일 확인** — 도구로 볼 수 없다 | 엣지·프록시가 오리진 인증서를 검증하는가 | **19.2, 19.8** |

마지막 줄에 주목해야 한다. **이 장에서 보안상 가장 중요한 항목이 외부에서 관측 불가능하다.** 클라이언트 쪽에서 아무리 정교하게 스캔해도, 엣지 뒤편에서 무슨 일이 일어나는지는 볼 수 없다. 19.2절이 표 19-3에서 세 배치의 자물쇠가 모두 같다고 적은 것이 여기서 진단의 한계로 나타난다. **그 항목은 스캔이 아니라 설정 검토와 아키텍처 문서로만 확인된다.**

첫 번째 줄도 실용적으로 중요하다. `-reconnect` 옵션은 같은 서버에 연달아 여러 번 접속하며 재개를 시도한다. **재개가 켜져 있으면 두 번째 이후 연결에서 세션이 재사용되었다는 표시가 나타나고, 꺼져 있으면 매번 전체 핸드셰이크가 반복된다.** 19.3절이 "대부분의 서버에서 기본으로 꺼져 있는 편이 더 흔하다"고 적은 상태를 30초 안에 확인하는 방법이며, 그 확인 하나가 왕복 하나를 되찾는다.

### 확인의 순서

우선순위를 매기면 이렇게 된다. **위에서 아래로 갈수록 확인 비용이 커지고, 발견의 가치도 커진다.**

1. **명령 한 줄로 끝나는 것들부터.** 압축이 `NONE`인지, HSTS 헤더가 있는지, 80번 포트가 무엇을 하는지, 사슬이 몇 장인지. 넷 다 1분 안에 끝난다.
2. **재개가 동작하는지.** `-reconnect` 한 번. 대부분의 서버에서 여기서 무언가가 나온다.
3. **바이트 계산.** 사슬 크기와 스테이플 포함 후 크기. 초기 혼잡 윈도우와 대조.
4. **혼합 콘텐츠 순회.** 19.10절의 확인 절차 여섯 단계. 인터셉팅 프록시를 켜고 애플리케이션을 처음부터 끝까지 걷는다.
5. **아키텍처 검토.** TLS를 종료하는 모든 지점을 목록으로 만들고, 각 지점의 오리진 검증 정책을 확인한다. **이것이 가장 오래 걸리고 가장 중요하다.**

> **이 책의 범위를 넘어서**
>
> 이 장의 여러 절이 원리만 서술하고 이름을 붙이지 않은 것들이 있다. 19.5절이 다룬 압축 누출 구조를 실제로 이용하는 공격 기법들에는 각각 고유한 이름이 붙어 있고, 그 기법들은 TLS 압축뿐 아니라 HTTP 응답 본문 압축과 헤더 압축에 대해서도 변형되어 발표되었다. 이 장이 정면으로 다루지 않은 표준들도 있다. 이 절의 체크리스트가 전제하는 TLS 1.2 이후 표준화된 TLS 1.3은 전체 핸드셰이크를 1왕복으로 줄이면서 압축 협상 자체를 제거했고, 재개 메커니즘을 재설계하면서 이전에 접속한 서버에 첫 요청 데이터를 핸드셰이크와 함께 보내는 0왕복(0-RTT) 모드를 도입했다 — 이 모드는 19.1절이 다룬 재개의 성능 이득을 더 밀어붙이는 대신 재생(replay)에 관한 새로운 조건을 만든다. 19.6절이 다룬 폐기의 신뢰성 문제에 대해서는 발급된 모든 인증서를 공개 로그에 기록하는 인증서 투명성(Certificate Transparency)이, 18.6절과 19.9절이 지적한 SNI 평문 노출에 대해서는 `ClientHello` 자체를 암호화하는 암호화된 클라이언트 헬로(ECH)가 각각 응답으로 배치되었다. 이 책이 근거로 삼는 다섯 권은 그 이전에 쓰였고 상세는 이 책의 범위 밖이다. **다만 이 장의 방법 — 왕복을 세고, 무엇이 평문인지 묻고, 종료 지점이 어디인지 묻고, 검증의 세 조건이 어디서 깨지는지 확인하는 것 — 은 어느 버전에서도 그대로 쓰인다.**

> **이 절이 뒷받침하는 것**
>
> - 성능 항목이 함께 결정하는 것의 목록 → **1.6** (표의 일대일 대응), **19.2, 19.6, 19.7**
> - 종료 지점의 검증 정책은 외부에서 관측되지 않는다 → **19.2, 19.8, 19.9**
> - 재개가 꺼져 있는지를 명령 하나로 확인한다 → **19.1, 19.3**, **18.8** (같은 도구의 다른 줄)

## 이 장의 요약

- **세션 재개는 표 18-3의 두 줄을 지운다.** 인증서 전송과 공개키 연산이 사라지고 왕복 하나가 줄어 168밀리초가 112밀리초가 된다. 세션 ID는 서버가 캐시를 유지하는 방식이고, 세션 티켓은 **서버의 상태를 클라이언트가 봉인된 채로 들고 다니는** 방식이다. 후자는 서버 캐시를 없애는 대신 **티켓 암호화 키라는 새 비밀의 생애주기 관리**를 요구하며, 그 요구는 성능 문서에 조건절로만 적힌다.

- **TLS의 비용은 CPU가 아니라 왕복이다.** 현대 하드웨어에서 TLS는 CPU 부하의 1% 미만을 차지한다. 그러므로 최적화의 초점은 왕복이며, 왕복의 길이는 거리의 함수다. **조기 종료는 서버를 사용자 가까이 옮겨 거리를 줄인다.** 그리고 그 순간 **TLS를 종료하는 그 지점이 신뢰 경계가 된다.** 엣지가 평문을 보고, 엣지 뒤 구간의 보호는 클라이언트가 검증한 것 안에 들어 있지 않으며, 세 가지 배치의 자물쇠가 모두 같아 보인다. **성능 이득의 원천과 평문 노출의 원천이 같은 것이다.**

- **레코드 크기는 오버헤드와 지연 사이의 균형이며, 답은 "TCP 세그먼트 하나에 레코드 하나"다.** MTU 1,500 기준으로 IPv6에서 1,400바이트가 남는다. 이 값은 애플리케이션이 제어할 수 없는 서버 설정이며, 기본값은 대개 16 KB에 가깝다.

- **TLS 압축을 끄는 이유는 세 조건이 모두 자동으로 성립하기 때문이다.** 비밀과 공격자 입력이 하나의 압축 컨텍스트에 들어가고, 공격자가 시도를 반복할 수 있으며, 압축 후 길이가 평문으로 관찰된다. **레코드 계층은 콘텐츠를 모르므로 첫 번째 조건을 깰 수단이 원리적으로 없다.** HPACK을 끄지 않는 이유가 정확히 그 차이다. **같은 기능이라도 어느 계층에 놓이느냐에 따라 안전하게 쓸 수 있는지가 달라진다.**

- **인증서 사슬은 2~3 KB, 두 장이 이상이다.** 중간 인증서를 빠뜨리면 브라우저가 스스로 가져오느라 수백 밀리초를 쓰고, 루트를 넣으면 바이트만 늘 뿐 신뢰는 생기지 않는다. **신뢰는 사슬을 따라 흐르지 않고 신뢰 저장소에서 시작하기 때문이다.** OCSP 스테이플링은 폐기 확인의 **성능**을 개선하지만 **신뢰성**은 개선하지 않는다. 스테이플이 없을 때 통과시키는 정책이 남아 있는 한 그렇다.

- **HSTS는 결정을 사용자에게서 사이트로 옮긴다.** 스킴 다운그레이드는 프로토콜 무결성 밖에 있어서 `Finished`가 막지 못하고, 경고가 뜨지 않는다. HSTS는 사이트가 미리 선언해 두는 방식으로 그 실패와 18.4절의 경고 클릭을 함께 없앤다. **남는 것은 최초 접속의 창이며, 그 창은 첫 방문·만료·새 기기·시크릿 모드·데이터 삭제·서브도메인까지 넓다.**

- **의도된 중간자와 공격자는 기술적으로 같은 위치에 있고, 차이는 신뢰 저장소에 무엇이 들어 있는지뿐이다.** 기업 검사 장비, CDN 종료, 개발자 프록시, 악성 소프트웨어의 기술적 동작이 같고 클라이언트는 넷을 구별할 수 없다. TLS의 인증은 "이 주체가 진짜인가"가 아니라 **"내 신뢰 저장소에 있는 누군가가 이 주체를 보증했는가"** 를 묻기 때문이며, 그 저장소는 파일이다.

- **표 1-7을 다시 쓰면 여섯 줄이 된다(표 19-17).** TLS가 실제로 올린 것은 **내용 관찰**과 **내용 변경**의 조건이다. **메타데이터 관찰과 커넥션 차단·선별의 조건은 변하지 않았고**, **평문 유도**라는 줄이 새로 생겼다. 그리고 조건을 올린 α의 항목 중 셋이 공격이 아니라 **배포 결정**이다.

- **HTTPS를 쓰는 사이트에서도 세션 토큰이 평문으로 나가는 경로가 여섯 가지 있다.** 로그인만 HTTPS, 로그인 시 토큰 미교체, 사전 인증 페이지 재방문, 로그인 링크 다운그레이드, 혼합 콘텐츠, 유발된 HTTP 요청. **혼합 콘텐츠 경고는 전송이 끝난 뒤에 뜬다.** 그리고 능동적 혼합 콘텐츠 — HTTPS 페이지가 부르는 HTTP 스크립트 — 는 **HTTPS 오리진의 권한으로 실행되어** 애플리케이션 코드에 XSS가 하나도 없어도 같은 결과를 만든다.

- **TLS를 켰다는 사실만으로는 표 19-17의 어느 줄도 확정되지 않는다. 확정하는 것은 배포다.** 그러므로 배포 문서에 적혀야 할 것은 "TLS를 쓴다"가 아니라 **"TLS를 종료하는 지점의 목록과 각 지점의 검증 정책"** 이다.

## 이어지는 장

Part IV가 여기서 닫힌다. 네 장이 한 일을 한 문장으로 적으면 이렇다. **채널을 보호하는 방법과, 그 보호가 성립하기 위한 조건의 목록.**

그리고 그 목록이 Part V의 전제가 된다. 20장부터 다루는 것은 **그 채널 위로 흐르는 신원과 세션**이다. HTTP는 상태가 없고, 상태를 만들어낸 세 층 — 식별, 인증, 인가 — 이 각각 어떻게 깨지는지가 Part V의 주제다. 그 세 층 전부가 **"채널이 보호된다"는 전제 위에 서 있다.** 그러므로 이 장이 그 전제에 붙인 조건들이 Part V 내내 각주로 따라붙는다.

가장 직접적인 연결은 19.10절이다. 그 절이 열거한 여섯 경로가 20.6절에서 **쿠키의 `Secure` 속성**이라는 하나의 대응으로 수렴하고, 그 속성의 정확한 한계 — **유출은 막고 주입은 막지 않는다** — 가 20.9절에서 쿠키 인젝션의 조건이 된다. 그리고 23.3절이 "토큰 처리의 약점"이라는 제목으로 이 절의 목록 전체를 세션 관리의 언어로 다시 쓴다.

19.1절과 19.3절이 남긴 형태도 Part V로 넘어간다. **서버가 기억할 것인가, 클라이언트가 봉인된 채 들고 다닐 것인가.** TLS 계층에서 세션 캐시와 세션 티켓이 갈라졌던 이 질문이, HTTP 계층에서는 서버 측 세션 저장소와 무상태 토큰으로 갈라진다(→ 23.1, 23.8). **두 계층에서 같은 선택지가 제시되고 같은 실패 방식이 따라온다.** 봉인 키의 관리, 만료의 통제, 그리고 봉인된 값이 결국은 클라이언트가 들고 있는 문자열이라는 사실.

마지막으로 19.9절의 표 19-17이 두 곳에서 다시 필요해진다. **23.5절**이 클라이언트의 토큰 하이재킹 노출을 다룰 때 그 표의 "평문 유도" 줄이 전제가 되고, **36.8절**이 브라우저 자체에 대한 중간자 공격을 다룰 때 그 표 전체가 실행 층위로 옮겨진다. 이 장이 조건의 언어로 적은 것을, 그 절은 브라우저가 실제로 무엇을 하는지의 언어로 적는다.

> **원서 대조**
>
> 19.1절: HPBN 4장 "TLS Session Resumption" 절 전체 — 전체 TLS 핸드셰이크의 추가 지연과 계산 비용이 보안 통신을 요구하는 모든 애플리케이션에 심각한 성능 벌점을 지운다는 것과 TLS가 **협상된 비밀 키 데이터를 여러 커넥션 사이에서 재개하거나 공유하는 능력**을 제공한다는 것, "Session Identifiers" 항목(첫 재개 메커니즘이 SSL 2.0에서 도입되었고 RFC 5246이며 서버가 전체 협상 중 `ServerHello`의 일부로 **32바이트 세션 식별자**를 만들어 보낸다는 것, 서버가 피어별로 세션 ID와 협상된 세션 파라미터의 캐시를 유지한다는 것, 클라이언트가 그것을 저장했다가 다음 세션의 `ClientHello`에 실어 보내며 이것이 **이전 핸드셰이크의 암호 스위트와 키를 기억하고 재사용할 수 있다는 표시**라는 것, 양쪽이 각자의 캐시에서 찾으면 그림 4-3의 축약 핸드셰이크가 성립하고 그렇지 않으면 새 협상이 필요하며 새 세션 ID가 발급된다는 것, **세션 식별자로 왕복 하나와 공유 비밀 키 협상에 쓰이던 공개키 암호의 오버헤드를 함께 제거할 수 있고 이전에 협상된 세션 데이터를 재사용하므로 보안 손실이 없다**는 것, 대부분의 웹 애플리케이션이 같은 호스트에 여러 커넥션을 맺어 병렬로 리소스를 가져오므로 재개가 필수 최적화라는 상자와 **현대 브라우저 대부분이 의도적으로 첫 TLS 커넥션의 완료를 기다린 뒤 같은 서버로의 새 커넥션을 연다**는 것, 실무적 한계로서 **서버가 모든 클라이언트에 대해 세션 캐시를 만들고 유지해야 한다**는 요구와 그로 인한 세 문제 — **열린 TLS 커넥션마다의 메모리 소비, 세션 ID 캐시와 축출 정책의 필요, 여러 서버를 쓰는 인기 사이트의 배포 난이도와 이상적으로 공유 TLS 세션 캐시를 써야 한다는 것** — 과 **어느 문제도 풀 수 없는 것은 아니며 많은 고트래픽 사이트가 오늘날 세션 식별자를 성공적으로 쓰고 있지만 다중 서버 배포에는 신중한 설계가 필요하다**는 단서), "Session Tickets" 항목(RFC 5077이며 **서버가 클라이언트별 세션 상태를 유지해야 한다는 요구를 제거**한다는 것, 클라이언트가 지원을 표시하면 전체 핸드셰이크의 마지막 교환에서 서버가 **서버만 아는 비밀 키로 암호화된 모든 세션 데이터를 담은 New Session Ticket 레코드**를 포함시킬 수 있다는 것, 클라이언트가 저장했다가 다음 세션 `ClientHello`의 `SessionTicket` 확장에 실어 보내며 **모든 세션 데이터가 클라이언트에만 저장되지만 서버만 아는 키로 암호화되어 있으므로 여전히 안전하다**는 것, 두 메커니즘이 각각 **세션 캐싱**과 **무상태 재개**로 불린다는 것과 무상태 재개의 주된 개선점이 **서버 측 세션 캐시의 제거**이며 그 대가로 클라이언트가 티켓이 만료될 때까지 새 커넥션마다 티켓을 제시해야 한다는 것, **로드밸런싱된 서버 집합에 세션 티켓을 배포하려면 모든 서버가 같은 세션 키로 초기화되어야 하고 공유 키를 주기적으로 회전시키는 추가 메커니즘이 필요할 수 있다**는 상자). 표 19-1의 타임라인은 이 책 18.2절 표 18-3에 원서의 "재개된 세션은 112밀리초"라는 수치를 적용해 구성했다. 재개 값이 재방문 식별자가 된다는 관찰과 세션 티켓을 fat URL·쿠키·무상태 토큰과 같은 형태로 분류하는 것은 이 책의 것이며, 근거는 이 책 20.4·23.1·23.2절의 예고다.

> 19.2절: HPBN 4장 "Computational Costs" 절과 "Early Termination" 절 전체 — 암호화 채널의 수립과 유지가 양쪽에 추가 계산 비용을 지운다는 것과 **핸드셰이크의 비대칭(공개키) 암호**와 **그 뒤 모든 TLS 레코드를 암호화하는 대칭 키**라는 두 지점, 공개키 암호가 대칭키보다 계산 비용이 크고 **웹 초창기에는 "SSL 오프로딩"을 위한 추가 하드웨어를 요구하는 일이 많았으나 더 이상 그렇지 않다**는 것과 현대 하드웨어가 이 비용을 최소화했으며 한때 추가 하드웨어를 요구하던 일이 CPU에서 직접 처리된다는 것, 수억 명에게 TLS를 제공하는 대형 조직들이 필요한 TLS 협상과 계산 전부를 **소프트웨어로 범용 하드웨어에서** 수행한다는 것, **Adam Langley(Google)의 인용 전체**(2010년 1월 Gmail의 전면 HTTPS 전환, 추가 장비도 특수 하드웨어도 배치하지 않았다는 것, 프로덕션 프론트엔드에서 SSL/TLS가 **CPU 부하 1% 미만·커넥션당 메모리 10 KB 미만·네트워크 오버헤드 2% 미만**이라는 것, "여기서 읽기를 멈춘다면 한 가지만 기억하라: SSL/TLS는 더 이상 계산 비용이 비싸지 않다"), **Doug Beaver(Facebook)의 인용 전체**(하드웨어·소프트웨어 로드밸런서 양쪽으로 대규모 TLS를 배포했고 범용 CPU의 현대적 소프트웨어 TLS 구현이 전용 암호 하드웨어 없이 무거운 HTTPS 부하를 감당할 만큼 빠르다는 것), **위 경험들과 무관하게 세션 재개 같은 기법이 여전히 중요한 최적화이며 "하지 않아도 되는 일에 CPU 사이클을 쓸 이유가 없다"**는 것, **SSL 라이브러리를 최신 릴리스로 올리고 웹 서버나 프록시를 그것에 대해 다시 빌드하라**는 상자와 최근 OpenSSL의 성능 개선 및 시스템 기본 라이브러리가 낡아 있을 가능성. "Early Termination"에서는 새 커넥션이든 재개든 모든 TLS 커넥션에 부과되는 셋업 지연이 중요한 최적화 영역이라는 것, TCP 3-way handshake 한 왕복과 TLS의 최대 두 왕복(재개 시 한 왕복), **최악의 경우 애플리케이션 데이터 전에 세 왕복이며 뉴욕–런던 56밀리초 기준 전체 168밀리초·재개 112밀리초이고 지연이 클수록 벌점이 커지며 56밀리초는 낙관적인 숫자**라는 것, 모든 TLS 세션이 TCP 위에서 돌므로 TCP 최적화 조언이 그대로 적용되며 **평문에서 커넥션 재사용이 중요한 고려였다면 TLS에서는 결정적 최적화이고 핸드셰이크를 피할 수 있다면 피하라**는 것, 1장의 결론대로 지연의 극적 개선을 기대할 수 없고 패킷이 이미 빛의 속도의 작은 상수배 안에서 이동하지만 **더 짧은 거리를 이동하게 만들 수는 있다**는 것과 조기 종료가 **서버를 사용자 가까이 배치해 왕복마다의 지연 비용을 최소화하는 단순한 기법**(그림 4-9)이라는 것, 가장 단순한 실현이 데이터와 서비스를 전 세계 서버에 복제·캐시하는 것이며 이것이 다수 CDN의 서비스라는 것, **가까운 서버가 TLS 세션을 종료할 수 있고 그러면 TCP·TLS 핸드셰이크 왕복이 훨씬 빨라져 총 커넥션 셋업 지연이 크게 줄며, 같은 가까운 서버가 오리진들과 장수하는 보안 커넥션의 풀을 유지하며 요청·응답을 중계한다**는 것, **"요약하면 TCP·TLS 핸드셰이크를 가속하기 위해 서버를 클라이언트 가까이 옮기는 것"** 과 몇 개 데이터센터의 클라우드 서버·프록시 설정·지리 기반 DNS 로드 밸런싱으로 직접 구축 가능하다는 것, **"Uncached Origin Fetch" 상자 전체**(사용자별 맞춤이거나 사적 데이터를 담아 엣지에서 전역 캐시할 수 없는 리소스를 CDN이나 프록시로 가져오는 기법의 이름, **클라이언트 커넥션이 가까운 서버에서 종료되어 핸드셰이크 지연 비용이 극적으로 줄어든다**는 것과 **"따뜻한 커넥션 풀"**, 일부 CDN이 **커넥션 양쪽 끝 모두에 가까운 서버를 써서** 클라이언트 커넥션을 가까운 노드에서 종료하고 오리진에 가까운 노드로 중계하며 그 추가 홉이 최적화된 CDN 백본을 타게 한다는 것). **표 19-3의 세 배치, "TLS를 종료하는 지점이 신뢰 경계다"라는 명제, 엣지–오리진 신뢰 관계와 파싱 불일치에 관한 서술, SSL 오프로딩의 역사를 배치 문제로 읽는 것, 그리고 절 말미의 네 가지 실행 항목은 모두 이 책의 것이다.** 근거는 이 책 1.6절 표의 해당 행, 13.12절, 15.10절(WAHH 17장 기준), 18.5·18.6절이다.

> 19.3절: HPBN 4장 "Session Caching and Stateless Resumption" 절 전체 — **커넥션을 사용자 가까이에서 종료하는 것이 모든 경우에 지연을 줄이지만 "보내지 않은 비트보다 빠른 비트는 없다 — 더 적은 비트를 보내라"** 는 것과 세션 캐싱·무상태 재개가 **재방문자에 대해 왕복 하나를 통째로 제거**한다는 것, 세션 캐싱이 의존하는 세션 식별자가 SSL 2.0에서 도입되어 대부분의 클라이언트·서버가 지원하지만 **서버에서 SSL/TLS를 설정한다면 세션 지원이 기본으로 켜져 있다고 가정하지 말라, 실제로는 대부분의 서버에서 기본으로 꺼져 있는 편이 더 흔하다**는 것, 설정을 이중으로 확인하라는 **여섯 항목 전체**(여러 프로세스·워커를 쓰는 서버는 공유 세션 캐시를 쓸 것 / 공유 세션 캐시의 크기를 트래픽 수준에 맞춰 조정할 것 / 세션 타임아웃 기간을 지정할 것 / 다중 서버 구성에서 같은 클라이언트 IP 또는 같은 TLS 세션 ID를 같은 서버로 라우팅하는 것이 세션 캐시 활용률을 높이는 한 방법이라는 것 / 스티키 로드 밸런싱이 불가능하면 서버 간 공유 캐시를 쓸 것 / 세션 캐시 통계를 확인하고 모니터링할 것), 클라이언트와 서버가 모두 세션 티켓을 지원하면 **모든 세션 데이터가 클라이언트에 저장되어 위의 어떤 단계도 필요 없다("훨씬, 훨씬 단순하다")** 는 것, 다만 세션 티켓이 상대적으로 새 확장이라 모든 클라이언트가 지원하지는 않으므로 **최선의 결과를 위해 둘 다 켜라 — 지원하는 클라이언트에는 세션 티켓이, 오래된 클라이언트에는 세션 식별자가 폴백으로 쓰이며 두 메커니즘은 배타적이지 않고 함께 잘 동작한다**는 것. 표 19-4·19-5, 공유 캐시를 14.8절의 캐시 키 질문으로 읽는 것, `Finished`가 세션 ID 노출을 세션 탈취로 만들지 않는다는 논증, 티켓 키의 생애주기가 관리되지 않는다는 관찰은 이 책의 것이다.

> 19.4절: HPBN 4장 "TLS Record Size" 절 전체 — 모든 애플리케이션 데이터가 레코드 프로토콜 안에서 운반되며 **최대 크기 16 KB**이고 선택된 암호에 따라 **헤더·MAC·선택적 패딩으로 20~40바이트**가 붙는다는 것, 레코드가 하나의 TCP 패킷에 들어가면 **IP 20바이트와 옵션 없는 TCP 20바이트**를 더해 **레코드마다 60~100바이트의 오버헤드**가 가능하며 **MTU 1,500바이트 기준 최소 6%의 프레이밍 오버헤드**라는 것, **레코드가 작을수록 프레이밍 오버헤드가 높다**는 것, **그러나 최대 크기로 키우는 것이 반드시 좋은 생각은 아니며** 레코드가 여러 TCP 패킷에 걸치면 **TLS 계층이 모든 패킷의 도착을 기다려야 복호할 수 있고**(그림 4-10), 그 패킷 중 하나라도 손실·재정렬되거나 혼잡 제어로 지연되면 **조각들이 디코딩될 때까지 버퍼링되어 추가 지연이 발생**하며 **실무에서 이 지연이 데이터를 바이트 단위로 가능한 한 빨리 소비하려는 브라우저에게 상당한 병목을 만들 수 있다**는 것, **11,211바이트 레코드가 8개 TCP 세그먼트로 쪼개진 캡처**(그림 4-10), **"작은 레코드는 오버헤드를, 큰 레코드는 지연을 부르며 올바른 레코드 크기에 대한 단일한 답은 없다"** 는 것과 브라우저가 소비하는 웹 애플리케이션에 대한 권고 — **각 TCP 패킷이 정확히 하나의 TLS 레코드를 담고 그 레코드가 MSS를 가득 채워야 하며, 여러 패킷에 걸치는 레코드 크기를 쓰지 말고 각 레코드에 최대한 담아 보내라** — 와 최적 크기 결정 절차 세 항목(**IPv4 20바이트·IPv6 40바이트, TCP 20바이트, TCP 옵션 40바이트**)과 **MTU 1,500 기준 IPv4 1,420바이트·IPv6 1,400바이트이며 미래 대비로 1,400바이트를 쓰라**는 결론, **레코드 크기가 애플리케이션 계층에서 제어할 수 있는 것이 아니라 TLS 서버의 설정이며 컴파일 타임 상수나 플래그일 수 있다**는 것, **커넥션당 메모리 최소화가 결정적 최적화일 수 있고 OpenSSL이 기본적으로 커넥션당 최대 50 KB를 할당하며 구글의 서버는 약 5 KB로 줄여 쓴다**는 상자. 커넥션당 버퍼를 가용성 항목으로 읽는 것과 레코드 크기가 관찰 가능한 값이라는 서술은 이 책의 것이며 근거는 이 책 18.7절과 45장의 예고다.

> 19.5절: HPBN 4장 "TLS Compression" 절 전체 — **레코드 프로토콜 안에서 전송되는 데이터에 대한 무손실 압축 지원이 TLS의 잘 알려지지 않은 기능**이며 **압축 알고리즘이 핸드셰이크에서 협상되고 각 레코드의 암호화 이전에 압축이 적용된다**는 것, **실무에서 여러 이유로 서버의 TLS 압축을 꺼야 한다**는 것과 두 이유 — 2012년에 발표된 공격이 TLS 압축을 이용해 **비밀 인증 쿠키를 복원하고 세션 하이재킹을 가능하게 한다**는 것, 그리고 **전송 계층 TLS 압축이 콘텐츠를 인식하지 못하며 이미 압축된 데이터(이미지·비디오 등)를 다시 압축하려 든다**는 것 — 과 **이중 압축이 양쪽에서 CPU 시간을 낭비하고 보안 침해의 함의가 상당히 심각하므로 TLS 압축을 끄라**는 결론, **실무에서 대부분의 브라우저가 TLS 압축 지원을 껐지만 사용자를 보호하기 위해 서버 설정에서도 명시적으로 꺼야 한다**는 것, **TLS 압축에 의존하는 대신 텍스트 기반 자산 전부를 Gzip으로 압축하도록 서버를 설정하고 다른 미디어 타입에는 각각 최적인 압축 포맷을 쓰라**는 상자. **원서가 명시한 공격 기법의 이름은 이 책의 방침(집필지침 §3-4, 이 책 10.4·10.5·11.11절의 방침)에 따라 본문에 도입하지 않았고, 그 대신 압축 누출의 성립 조건을 표 19-7의 세 조건으로 재구성했다.** 세 조건의 원리, HPACK과의 대조표(표 19-8), 세 계층의 압축 비교표(표 19-9)는 이 책의 것이며 근거는 이 책 10.5절과 11.11절이다.

> 19.6절: HPBN 4장 "Certificate-Chain Length" 절과 "OCSP Stapling" 절 전체 — 신뢰 사슬 검증이 사이트 인증서에서 시작해 재귀적으로 부모를 검증하며 신뢰된 루트까지 올라간다는 것과 **첫 최적화가 서버가 핸드셰이크에서 중간 인증서를 빠뜨리지 않는지 확인하는 것**이며 빠뜨리면 **많은 브라우저가 여전히 동작하지만 검증을 멈추고 중간 인증서를 스스로 가져와 검증한 뒤 계속해야 하고 이는 십중팔구 새 DNS 조회·TCP 커넥션·HTTP GET을 요구해 핸드셰이크에 수백 밀리초를 더한다**는 것, **자식 인증서가 대체로 부모의 URL을 담고 있어 브라우저가 어디서 가져올지 안다**는 상자, **반대로 불필요한 인증서를 사슬에 넣지 말고 사슬 크기를 최소화하라**는 것과 서버 인증서가 **slow-start 초기 단계의 새 TCP 커넥션 위에서 전송되므로 사슬이 초기 혼잡 윈도우를 초과하면 의도치 않게 왕복 하나를 더하게 되고 인증서 길이가 혼잡 윈도우를 넘쳐 서버가 클라이언트 ACK를 기다리며 멈춘다**는 것(그림 4-11), **5 KB가 넘는 사슬이 오래된 서버의 초기 혼잡 윈도우를 초과해 왕복 하나의 지연을 강제한다**는 것과 **초기 혼잡 윈도우를 키우는 해법**, 크기를 줄이는 **세 항목 전체**(중간 CA 수 최소화 — **이상적으로 사이트와 CA 중간 인증서 정확히 두 장이며 세 번째인 CA 루트는 이미 브라우저 신뢰 루트에 있어야 하므로 보낼 필요가 없고 이것을 CA 선정 기준으로 삼으라** / **많은 사이트가 자기 CA의 루트를 포함시키는데 전혀 불필요하며 브라우저 신뢰 저장소에 없다면 함께 보내도 신뢰되지 않는다** / **잘 관리된 사슬은 2~3 KB까지 줄어들면서도 불필요한 왕복이나 대역외 요청을 피할 정보를 모두 제공하며, 모든 새 TLS 커넥션이 핸드셰이크 오버헤드의 지배를 받으므로 핸드셰이크 최적화가 결정적 병목을 완화한다**). "OCSP Stapling"에서는 모든 새 TLS 커넥션에서 브라우저가 사슬의 서명을 검증해야 하고 **인증서가 폐기되지 않았음도 확인해야 한다**는 것과 CRL을 주기적으로 내려받아 캐시하거나 검증 중 OCSP 요청을 발행할 수 있다는 것, **브라우저 동작이 제각각인 세 가지**(자체 업데이트 메커니즘으로 갱신된 CRL을 푸시 / EV 인증서에 대해서만 실시간 확인 / 폐기 확인에 핸드셰이크를 블로킹하는 브라우저와 하지 않는 브라우저가 있고 벤더·플랫폼·버전에 따라 다름)와 **복잡한 영역이며 단일한 최선의 해법이 없다**는 판정, **OCSP 스테이플링 — 서버가 CA의 OCSP 응답을 인증서 사슬에 붙여 보내 브라우저가 온라인 확인을 건너뛰게 하고 서버가 서명된 응답을 캐시해 많은 클라이언트에 대해 추가 요청을 절약한다** — 과 두 주의 사항(**OCSP 응답이 400~4,000바이트로 다양하며 붙이면 다시 혼잡 윈도우를 넘칠 수 있으니 총 크기에 주의할 것** / **응답은 하나만 포함 가능하므로 캐시되지 않은 다른 중간 인증서에 대해서는 여전히 OCSP 요청이 필요할 수 있음**), **Nginx·Apache·IIS가 스테이플링을 지원한다**는 것. 표 19-10과 "스테이플링이 폐기 모델의 비대칭을 없애지 않는다"는 절 후반부는 이 책의 것이며, 근거는 이 책 17.9절이다.

> 19.7절: HPBN 4장 "HTTP Strict Transport Security (HSTS)" 절 전체 — **서버가 단순한 HTTP 헤더 하나로 규격 준수 브라우저에게 접근 규칙을 선언하게 해 주는 보안 정책 메커니즘**이라는 것과 `Strict-Transport-Security: max-age=31536000` 예시, 강제되는 **다섯 항목 전체**(오리진으로 가는 모든 요청을 HTTPS로 / 모든 비보안 링크와 클라이언트 요청을 요청 전송 전에 클라이언트에서 자동으로 HTTPS로 변환 / **인증서 오류 시 오류 메시지를 표시하고 사용자가 경고를 우회할 수 없게** / `max-age`가 규칙 집합의 수명을 초 단위로 지정하며 `31536000`이 365일 / 선택적으로 **지정된 인증서 사슬의 호스트 지문을 "핀"하도록 지시해 그 인증서를 인증할 수 있는 기관의 범위를 실질적으로 제한**), **HSTS가 오리진을 HTTPS 전용 목적지로 전환하며 다양한 수동적·능동적 네트워크 공격으로부터 애플리케이션을 보호하는 데 도움을 주고, 성능 면에서도 불필요한 HTTP→HTTPS 리다이렉트를 없애 그 책임을 클라이언트로 옮겨 모든 링크를 자동으로 HTTPS로 다시 쓰게 한다**는 것. **SSL 스트리핑의 구조(그림 19-3), "프로토콜 다운그레이드는 프로토콜이 막고 스킴 다운그레이드는 프로토콜이 막을 수 없다"는 명제, "HSTS는 결정을 사용자에게서 사이트로 옮긴다"는 정식화, 최초 접속 문제와 표 19-12의 일곱 상황은 모두 이 책의 것이다.** 근거는 이 책 18.1·18.2·18.4절과 WAHH 7장·13장이 서술한 다운그레이드 시나리오(→ 19.10)다.

> 19.8절: HTTP-DG 14장 "Tunneling Secure Traffic Through Proxies" 절 전체 — 클라이언트가 자기를 대신해 웹 서버에 접근하도록 웹 프록시를 흔히 쓴다는 것과 **많은 기업이 사내 네트워크와 공용 인터넷의 보안 경계에 프록시를 두며**(그림 14-19) **그 프록시가 방화벽 라우터가 HTTP 트래픽 교환을 허용한 유일한 장비이고 바이러스 검사나 그 밖의 콘텐츠 통제를 수행할 수 있다**는 것, **클라이언트가 서버의 공개키로 데이터를 암호화하기 시작하면 프록시가 더 이상 HTTP 헤더를 읽을 수 없고 헤더를 읽지 못하면 요청을 어디로 전달할지 알 수 없다**는 것(그림 14-20), HTTPS를 프록시와 함께 동작시키려면 프록시에게 어디로 연결할지 알려 주는 수정이 필요하며 **널리 쓰이는 기법이 HTTPS SSL 터널링 프로토콜**이라는 것, **클라이언트가 먼저 프록시에게 접속하려는 보안 호스트와 포트를 암호화 시작 전에 평문으로 알려주어 프록시가 읽을 수 있게 한다**는 것과 **`CONNECT`라는 새 확장 메서드**가 **프록시에게 원하는 호스트와 포트로 커넥션을 열고 완료되면 클라이언트와 서버 사이의 데이터를 직접 터널링하도록 지시**한다는 것, **문법 전체**(한 줄짜리 텍스트 명령으로 호스트명과 포트를 콜론으로 구분, `host:port` 뒤에 공백·HTTP 버전 문자열·CRLF, 그 뒤 0개 이상의 요청 헤더 줄과 빈 줄, 빈 줄 다음부터 SSL 데이터 전송 시작)와 `CONNECT home.netscape.com:443 HTTP/1.0` 예시, **프록시가 요청의 유효성과 사용자의 권한을 확인하고 문제없으면 목적지로 커넥션을 만든 뒤 `200 Connection established`를 보낸다**는 것과 그 응답 예시. **그림 19-4의 검사 프록시 구조, 표 19-13의 네 배치 비교, 표 19-14의 두 종류 정당한 중간자 비교, 그리고 "검사 배치가 실제로 바꾸는 것들" 다섯 항목은 모두 이 책의 것이다.** 근거는 이 책 1.8절("의도된 중간자와 공격자는 기술적으로 같은 위치에 있다"), 13.10절, 17.10절 표 17-16의 두 번째 조건, 18.5·18.8절이다.

> 19.9절: 이 절은 **이 책이 구성한 종합 절**이며 새로운 원서 사실을 도입하지 않는다. 표 19-15·19-16·19-17의 재료는 전부 앞선 절들에서 왔다 — 1.2절(TLS가 가리지 않는 것: IP·포트·크기·타이밍), 1.8절 표 1-7, 17.7절(암호화·인증·무결성의 분리), 17.9절(폐기 모델의 비대칭), 17.10절 표 17-16(검증의 세 조건)과 표 17-17, 18.2절(`ClientKeyExchange` 이전은 전부 평문), 18.6절(SNI 평문과 선택자), 18.7절(레코드 헤더 평문, MAC과 일련번호), 19.2절 표 19-3, 19.5절, 19.7절 표 19-12, 19.8절 표 19-13. 절 후반의 능동적 중간자 서술은 WAHH 13장 "Man-in-the-Middle Attacks" 절 — **애플리케이션이 민감 데이터 전부에 HTTPS를 쓰고 사용자가 HTTPS가 제대로 쓰이는지 항상 확인해도 심각한 공격이 성립할 수 있다는 것이 더 놀랍다**는 것, 이 공격들이 **수동적 감시에 그치지 않고 트래픽을 실시간으로 변경하는 "능동적" 중간자**를 요구하며 **공용 무선 핫스팟·공유 사무실 네트워크를 비롯한 흔한 상황과 그럴 의향이 있는 정부에 의해 충분히 실행 가능**하다는 것, **공격자가 사용자가 다른 아무 도메인에 보내는 HTTP 요청에 리다이렉션으로 응답해 대상 도메인에 대한 평문 요청을 유도할 수 있고 애플리케이션이 80번 포트에서 듣고 있지 않더라도 그 유도된 요청을 가로채 임의의 콘텐츠로 응답할 수 있다**는 것, 그리고 **보안에 극도로 신경 쓰는 사용자(한 번에 한 사이트, 사이트마다 브라우저 재시작, 깨끗한 새 브라우저에서 순수 HTTPS 은행 앱)도 "아마 뚫린다"는 답과 그 이유 — 오늘날의 브라우저가 사용자가 어느 도메인을 방문하든 배경에서 수많은 평문 HTTP 요청(안티피싱 목록, 버전 핑, RSS 피드 요청)을 보내며 공격자가 그중 아무것에나 대상 도메인으로의 HTTP 리다이렉션으로 응답할 수 있고 브라우저가 조용히 따라가면 먼저 HTTP 오리진을 장악하고 그것을 HTTPS 오리진으로 확대한다**는 것 — 을 근거로 한다.

> 19.10절: WAHH 7장 "Disclosure of Tokens on the Network" 절 전체와 13장 "Man-in-the-Middle Attacks" 절의 후반 — 세션 토큰이 암호화되지 않은 형태로 네트워크를 건널 때 **적절히 위치한 도청자가 토큰을 얻어 정당한 사용자로 위장할 수 있다**는 것과 **도청에 적합한 위치 목록**(사용자의 로컬 네트워크, 사용자의 IT 부서, 사용자의 ISP, 인터넷 백본, 애플리케이션의 ISP, 애플리케이션을 호스팅하는 조직의 IT 부서)과 **각 경우에 해당 조직의 권한 있는 인력과 그 인프라를 침해한 외부 공격자가 모두 포함된다**는 단서, 전면 평문일 때 **공격자가 로그인 자격 증명·개인정보·결제 정보를 포함한 모든 데이터를 잡을 발급하고 이후 HTTPS를 써도 **사용자가 사전 인증 페이지를 링크·뒤로 가기·URL 직접 입력으로 재방문**하면 노출되는 것 / 로그인 링크 클릭 시 HTTPS로 전환하지만 **URL을 고치면 HTTP 로그인을 받아들여** 능동적 공격자가 사전 인증 페이지의 로그인 링크를 HTTP로 바꿔 다운그레이드하는 것 / **정적 콘텐츠만 HTTP인 혼합 콘텐츠와
