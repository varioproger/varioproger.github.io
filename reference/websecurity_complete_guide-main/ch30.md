# 30장. 오류, 정보 노출, 그리고 안전한 실패

> **이 장에서 다루는 것**
>
> - 애플리케이션이 실패할 때 무엇을 흘리는가 — 스크립트 오류, 스택 트레이스, 디버그 덤프, 백엔드 메시지가 각각 무엇을 알려주는가
> - 오류 메시지가 하나도 없어도 정보가 새는 채널 — 응답 시간과 상태 코드라는, 27장·22장에서 이미 본 것과 같은 구조
> - 예외를 실패 신호로 쓸 때 무엇을 페이로드에 담지 말아야 하는가, 그리고 실패를 예외적 사건이 아니라 정상 결과로 설계한다는 것
> - "입력을 그대로 반향하지 말라"와 "검증 전에 데이터를 복구하지 말라" — 32장 XSS 방어와 43장 검증 순서의 설계적 뿌리
> - 같은 정보 노출이 현대 GraphQL API에서 어떻게 재현되는가 — 오류 메시지 남용, 필드 제안, 인트로스펙션 우회

앞의 다섯 장(27~29)은 애플리케이션이 **공격받는** 순간을 다뤘다. 인젝션은 인터프리터의 문법을 뒤집었고, 백엔드 컴포넌트 공격은 서버가 열어야 할 커넥션의 목적지를 바꿨으며, 로직 결함은 개발자가 세운 가정을 무너뜨렸다. 이 장은 그 모든 순간에 공통으로 따라붙는 부산물 하나를 다룬다. **애플리케이션은 공격받을 때 말을 흘린다.**

정상적으로 쓰이는 애플리케이션은 대체로 조용하다. 출시 전의 사용성 테스트가 일상적으로 발생하는 오류 조건 대부분을 걸러내기 때문에, 평범한 사용 경로에서는 기술적 메시지가 사용자에게 노출되지 않는다. 그러나 애플리케이션이 능동적으로 공격받는 동안에는 훨씬 넓은 범위의 오류 조건이 발생한다. 그리고 그 조건들은 개발자가 상상하지 못했던 것이므로, 우아하게 처리되지 못하고 **상세한 내부 정보를 담은 채** 사용자에게 되돌아온다. 온라인 은행처럼 보안이 가장 중요한 애플리케이션조차, 충분히 이례적인 오류 조건 앞에서는 장황한 디버깅 출력을 뱉는 것이 확인된 바 있다.

이 장은 같은 실패를 세 개의 렌즈로 본다. 앞의 네 절(30.1~30.4)은 공격자의 렌즈다. 흘러나온 정보를 어떻게 줍고, 어떻게 그것을 유도하고, 정보가 전혀 흐르지 않는 것처럼 보이는 상황에서도 어떻게 추론으로 정보를 짜내는가. 다음 다섯 절(30.5~30.9)은 설계자의 렌즈다. 실패를 어떻게 코드로 표현해야 정보가 새지 않는가 — 예외 페이로드, 실패의 모델링, 반향 금지, 복구 순서, 설정 검증. 마지막 한 절(30.10)은 현대 API의 렌즈다. 같은 병이 GraphQL에서 어떻게 더 친절한 얼굴로 재현되는가. 세 렌즈가 겨누는 것은 하나다. **실패의 순간에 신뢰 경계 안쪽이 바깥으로 새는 일**이다.

## 30.1 오류 메시지 익스플로잇 — 스크립트 오류, 스택 트레이스, 디버그 메시지, 서버·DB 메시지

애플리케이션이 반환하는 오류 메시지는 정보량의 스펙트럼 위에 놓인다. 한쪽 끝에는 오류의 범주만 알려주는 단순한 내장 메시지가 있고, 반대쪽 끝에는 애플리케이션의 상태를 낱낱이 드러내는 완전한 디버깅 정보가 있다. 공격자에게 이 스펙트럼은 곧 **채굴 가능한 광맥의 등급표**다. 종류별로 무엇을 캐낼 수 있는지 보자.

### 30.1.1 스크립트 오류 메시지 — 코드 경로를 그리는 지도

VBScript 같은 인터프리터형 스크립트 언어에서 오류가 나면, 애플리케이션은 대개 오류의 성격과 오류가 난 파일의 줄 번호를 담은 단순한 메시지를 반환한다. 온라인 서점의 주문 확인 스크립트에 비정상 입력을 넣었을 때 이런 메시지가 돌아왔다고 하자.

```
Microsoft VBScript runtime error '800a000d'

Type mismatch: '[string: ]'

/scripts/confirmOrder.asp, line 715
```

이 메시지 자체에는 애플리케이션 상태나 처리 중인 데이터에 관한 민감한 정보가 없다. 그러나 공격의 초점을 좁혀 준다. `Type mismatch`는 우리가 수정한 값이 **숫자 변수에 대입되고 있는데** 비숫자 문자를 넣어서 대입이 실패했다는 뜻이다. 이 상황이 알려주는 것은 분명하다. 이 파라미터에 비숫자 공격 문자열을 넣어 봐야 얻을 것이 없다. 여러 범주의 버그에 대해, 이 파라미터는 포기하고 다른 파라미터를 노리는 편이 낫다.

스크립트 오류가 주는 두 번째 쓸모는 **서버 측 로직의 순서를 재구성**하는 것이다. 메시지가 오류가 난 줄 번호를 공개하므로, 서로 다른 두 개의 비정상 요청이 같은 오류를 일으키는지 다른 오류를 일으키는지 확인할 수 있다. 여러 파라미터에 동시에 잘못된 입력을 넣고 오류가 나는 위치를 관찰하면, 파라미터들이 어떤 순서로 처리되는지도 알 수 있다. 이렇게 파라미터를 체계적으로 조작하면 서버에서 실행되는 여러 **코드 경로를 지도로 그릴 수** 있다.

### 30.1.2 스택 트레이스 — 호출 계층과 플랫폼 버전

Java, C#, VB.NET처럼 관리형 실행 환경에서 도는 언어에서 처리되지 않은 오류가 나면, 완전한 스택 트레이스가 브라우저로 반환되는 일이 흔하다. 스택 트레이스는 실제 오류에 대한 설명으로 시작해서, 오류 발생 시점의 호출 스택 상태를 한 줄씩 나열하는 구조화된 오류 메시지다. 맨 윗줄은 오류를 낸 함수를, 그다음 줄은 그 함수를 호출한 함수를 보여주며, 호출 계층이 소진될 때까지 내려간다.

```
[HttpException (0x80004005): Cannot use a leading .. to exit above the top directory.]

System.Web.Util.UrlPath.Reduce(String path) +701
System.Web.Util.UrlPath.Combine(String basepath, String relative) +304
System.Web.UI.Control.ResolveUrl(String relativeUrl) +143
BookApp.Catalog.Web.MemberAwarePage.Redirect(String url) +130
BookApp.Catalog.Web.MemberAwarePage.Process() +201
BookApp.Catalog.Web.MemberAwarePage.OnLoad(EventArgs e)
System.Web.UI.Page.ProcessRequestMain() +750

Version Information: Microsoft .NET Framework Version:1.1.4322.2300;
ASP.NET Version:1.1.4322.2300
```

이 한 덩어리가 공격자에게 넘겨주는 것을 항목별로 보면 이렇다.

- **오류의 정확한 원인.** 첫 줄이 "선행 `..`로 최상위 디렉터리 위로 나갈 수 없다"고 말한다. 입력을 조정해 이 오류 조건을 피하면서 공격을 진전시킬 실마리가 된다.
- **서드파티·라이브러리 컴포넌트의 이름.** 호출 스택은 애플리케이션이 사용하는 라이브러리와 프레임워크 컴포넌트를 참조한다. 그 문서를 읽어 의도된 동작과 전제를 파악할 수 있고, 로컬에 같은 컴포넌트를 구현해 비정상 입력에 어떻게 반응하는지 시험할 수도 있다.
- **자체 코드의 내부 구조.** `BookApp.Catalog.Web.MemberAwarePage` 같은 독자 개발 컴포넌트의 이름과 그 상호관계가, 애플리케이션 내부 구조와 기능을 추론할 단서를 준다.
- **줄 번호.** 스크립트 오류와 마찬가지로 개별 컴포넌트의 내부 로직을 탐침하게 해 준다.
- **플랫폼 버전.** 위 예시에서 ASP.NET의 정확한 버전을 알 수 있다. 이 버전에 알려진 취약점이나 흔한 설정 오류가 있는지 곧바로 조사할 수 있다. 이 값은 25.6절의 서버 핑거프린팅이 다른 신호와 대조하는 재료가 된다.

### 30.1.3 상세 디버그 메시지 — 개발자가 잊고 간 창

일부 애플리케이션은 개발·테스트 편의를 위해 만든 커스텀 오류 메시지가 운영 코드에 그대로 남아 있어서, 런타임 상태를 풍부하게 담은 덤프를 뱉는다. 예를 들면 이런 식이다.

```
***SESSION***
i5agor2n2pw3gp551pszsb55
SessionUser.Auth       1
SessionUser.BranchID   103
SessionUser.CompanyID  76
SessionUser.UserID     229
SessionUser.Key        f7e50aef8fadd30f31f3aea104cef26ed2ce2be5
SessionDatabase        fd219.prod.bookstore-internal.com
```

장황한 디버그 메시지에 흔히 담기는 것은 다음과 같다. 사용자 입력으로 조작 가능한 핵심 세션 변수의 값, 데이터베이스 같은 백엔드 컴포넌트의 호스트명과 자격증명, 서버의 파일·디렉터리 이름, 의미 있는 세션 토큰에 박힌 정보, 클라이언트를 통해 전달되는 데이터를 보호하는 암호화 키, 그리고 네이티브 컴포넌트 예외의 CPU 레지스터 값과 스택 내용까지. 이런 리포팅 기능이 라이브 운영 코드에 있다면 그 자체가 애플리케이션 보안의 치명적 약점이다. 위 예시의 `SessionUser.Auth`나 `BranchID`처럼 조작하면 상태를 바꿀 수 있는 값이 있는지, `SessionDatabase`처럼 다음 공격의 발판이 될 값이 있는지를 자세히 살펴야 한다.

### 30.1.4 서버와 데이터베이스 메시지 — 백엔드가 직접 말할 때

정보성 오류 메시지는 애플리케이션 자신이 아니라 데이터베이스, 메일 서버, SOAP 서버 같은 백엔드 컴포넌트가 반환하는 경우가 많다. 완전히 처리되지 않은 오류가 나면 애플리케이션은 대개 HTTP 500을 반환하고, 응답 본문에 오류에 관한 추가 정보가 실린다. 특정 공격이 백엔드 컴포넌트를 정면으로 겨냥할 때, 그 컴포넌트는 마주친 오류에 직접 피드백을 준다. 데이터베이스 오류 메시지는 특히 유용하다. 오류를 낸 질의를 그대로 노출해서 SQL 인젝션 공격을 미세 조정하게 해 주기 때문이다.

```
Failed to retrieve row with statement - SELECT title, price FROM catalog
WHERE book_id = 'BK00012' AND category_id = 'FIC' and 1=2--'
```

여기서 우리가 주입한 `and 1=2--`가 질의에 그대로 들어간 것이 보인다. 이는 우리 입력이 SQL 문법 안으로 들어가고 있다는 확증이며, 27.3절의 버그 찾기 방법론이 바로 이 피드백을 신호로 삼는다. 백엔드 오류가 정보 노출의 도관이 되는 이유는, 그 노출이 대체로 **의도하지 않은 것**이기 때문이다. 조직의 보안 절차는 의도한 출력만 검토하므로, 예외나 디버그 메시지로 새는 정보의 존재 자체를 통째로 간과하기 쉽다.

> **탐침 실무 — 화면이 아니라 원시 응답을 검색하라**
>
> 오류 정보가 서버 응답에 담겨 있어도 브라우저 화면에 렌더링되지 않을 수 있다. 여러 요청을 던지며 버그를 찾을 때는 각 **원시 응답**을 다음 키워드로 검색하는 것이 효율적이다: `error`, `exception`, `invalid`, `stack`, `directory`, `varchar`, `ODBC`, `SQL`, `SELECT`. 다만 기준 요청의 원래 응답에 이미 이 단어들이 있는지 먼저 확인해 거짓 양성을 걸러야 한다. 일부 브라우저는 기본 설정에서 오류 페이지를 일반 페이지로 대체해 숨기므로, 인터셉팅 프록시로 원시 응답을 보는 편이 안전하다.

> **이 절이 뒷받침하는 것**
>
> - 스택 트레이스의 플랫폼 버전과 서버 배너 → **25.6** (핑거프린팅이 이 값을 다른 신호와 교차 검증한다), **12.6** (기본 콘텐츠·샘플 앱이 같은 방식으로 기술 스택을 누설한다)
> - DB 오류가 질의를 반향하는 것 → **27.3** (SQL 인젝션 버그 찾기와 DB 핑거프린팅이 이 피드백을 신호로 쓴다)
> - 디버그 덤프의 세션 토큰·암호화 키 → **23.2** (의미 있는 토큰), **26.7** (클라이언트로 전달된 데이터의 서명·암호화)

## 30.2 공개 정보 활용과 정보성 오류 메시지 유도

노출된 정보를 줍는 것과 노출을 **일으키는** 것은 다르다. 이 절은 두 가지 능동적 기법을 다룬다. 낯선 메시지의 의미를 외부 자료로 해독하는 것, 그리고 오류 조건을 의도적으로 조립해 민감 정보를 오류 메시지 안으로 끌어내는 것이다.

### 30.2.1 공개 자료로 메시지 해독하기

웹 기술과 컴포넌트가 워낙 다양하므로, 처음 보는 데다 오류의 성격이 곧바로 드러나지 않는 메시지를 자주 만나게 된다. 이럴 때는 공개 자료에서 그 의미의 실마리를 얻을 수 있다. 낯선 오류 메시지는 대개 특정 API의 실패에서 나오므로, 메시지 텍스트를 그대로 검색하면 그 API의 문서나 같은 문제를 논의한 개발자 포럼으로 이어진다. 검색, 장바구니, 사이트 피드백 같은 흔한 기능은 서드파티 컴포넌트로 구현되는 경우가 많고, 그 컴포넌트가 내는 오류는 다른 애플리케이션에서도 났을 것이므로 어딘가에 논의가 남아 있다. 공개된 소스 코드를 쓰는 애플리케이션이라면, 오류 메시지에 하드코딩된 표현을 검색해 그 기능을 구현한 소스를 찾아 우리 입력이 정확히 어떻게 처리되는지 읽어낼 수도 있다. 라이브 애플리케이션에서 이미 사라진 메시지의 예시는 검색 엔진 캐시로 되살릴 수 있다.

이것이 25.2절이 다루는 공개 리소스 참조의 한 형태다. 애플리케이션이 스스로 흘린 문자열 한 조각이, 조직 바깥에 축적된 지식과 결합해 내부 구조의 지도가 된다.

### 30.2.2 정보성 오류 메시지 유도하기

더 능동적인 기법은, 민감 정보 자체가 오류 메시지 안에 실려 나오도록 오류 조건을 **체계적으로 조립**하는 것이다. 흔한 상황은 특정 데이터 항목에 대해 애플리케이션이 잘못된 동작을 시도하게 만드는 것이다. 그 결과 오류 메시지가 그 데이터의 값을 노출하고, 우리가 흥미로운 정보 항목을 그런 식으로 처리되게 만들 수 있다면, 임의의 데이터를 애플리케이션에서 뽑아낼 수 있다.

장황한 ODBC 오류 메시지는 SQL 인젝션에서 임의 질의의 결과를 되받는 데 이용된다. 다음 SQL을 `WHERE` 절에 주입하면, 데이터베이스는 users 테이블 첫 사용자의 비밀번호를 정수로 형변환하려다 실패한다.

```sql
' and 1=(select password from users where uid=1)--
```

그 결과 이런 정보성 오류가 나온다.

```
Error: Conversion failed when converting the varchar value
'37CE1CCA75308590E4D6A35F288B58FACDBB0841' to data type int.
```

형변환은 실패했지만, 실패하는 과정에서 **뽑아내려던 값이 오류 메시지에 실렸다.** 같은 원리를 스택 트레이스로도 쓸 수 있다. 일부 데이터베이스는 Java로 사용자 정의 함수를 만들 수 있으므로, SQL 인젝션으로 임의 명령을 실행하고 그 출력을 담은 예외를 던지면, 스택 트레이스의 첫 줄에 디렉터리 목록 같은 결과가 실려 브라우저로 돌아온다.

이 기법의 핵심은, **오류 메시지가 데이터의 전달 통로**라는 점이다. 이 원리는 30.10절의 GraphQL 오류 메시지 남용에서 정확히 같은 형태로 재현된다. 그리고 이 통로를 막는 설계적 해법 — 예외 페이로드에 무엇을 담지 말 것인가 — 이 30.5절의 주제다.

### 30.2.3 그냥 발행된 정보 줍기

오류를 유도하지 않아도, 애플리케이션이 정보를 **직접 발행**해 버리는 경우가 있다. 이유는 여럿이다. 설계상 핵심 기능의 일부로, 다른 기능의 의도치 않은 부작용으로, 라이브에 남은 디버그 기능으로, 혹은 접근 제어 결함 같은 취약점 때문에. 흔히 발행되는 민감 정보에는 유효한 사용자명·계정 번호·문서 ID 목록, 사용자 역할과 권한과 마지막 로그인 시각을 담은 프로필, 화면에는 마스킹되지만 페이지 소스에는 남아 있는 현재 비밀번호, 그리고 클라이언트 HTML에 주석으로 남은 링크·폼 필드·버그 메모가 있다. 화면에 마스킹된 값도 서버 응답 원문에는 그대로 있으므로, 접근 제어나 세션 처리에 다른 취약점이 함께 있으면 다른 사용자의 정보까지 이 통로로 얻을 수 있다.

## 30.3 추론(inference)을 통한 정보 수집 — 응답 시간과 상태 코드라는 채널

지금까지는 애플리케이션이 무언가를 **말해 주는** 상황이었다. 이 절의 전제는 정반대다. 애플리케이션이 우리에게 아무 데이터도 직접 내주지 않는데도, 우리가 정보를 안정적으로 **추론**할 수 있는 방식으로 행동하는 경우다.

이 현상은 이 책의 다른 장에서 이미 여러 번 만났다. 존재하는 사용자명을 고르면 다른 오류가 나는 등록 기능은, 오류 메시지의 차이만으로 유효 사용자명을 열거하게 한다(→ 22.2). 검색 엔진은 직접 볼 권한이 없는 문서의 내용을 결과의 유무로 추론하게 한다. 블라인드 SQL 인젝션은 기존 질의에 참·거짓 조건을 덧붙여 애플리케이션의 동작을 바꿈으로써 한 번에 1비트씩 정보를 뽑아낸다(→ 27.6). **공통 구조는 하나다. 직접적인 답 대신, 관찰 가능한 이진 차이를 채널로 삼는다.** 오류 메시지는 그 차이를 실어 나르는 여러 매체 중 하나일 뿐이다. 오류 메시지가 사라져도 채널은 남는다. 응답 시간과 상태 코드와 응답 길이가 그것이다.

### 30.3.1 응답 시간이라는 채널

서로 다른 연산이 서로 다른 시간을 소모하고, 그 시간 차이가 공격자에게 흥미로운 어떤 사실에 좌우된다면, 시간 자체가 정보 채널이 된다. 이 차이는 몇 가지 이유로 생긴다.

- **캐시와 지연 로딩.** 크고 복잡한 애플리케이션은 여러 백엔드에서 데이터를 가져오며, 자주 쓰는 데이터를 캐시하거나 필요할 때만 로드한다. 최근 접근된 데이터는 로컬 캐시에서 빠르게 오고, 그렇지 않은 데이터는 원본에서 느리게 온다. 온라인 은행에서 관측된 사례가 있다. 휴면 계좌에 접근하는 요청이 활성 계좌보다 오래 걸려서, 숙련된 공격자가 **다른 사용자들이 최근 접근한 계좌를 열거**할 수 있었다.
- **입력 유효성에 따라 달라지는 처리량.** 유효한 사용자명이 로그인 폼에 들어오면 애플리케이션은 계정 정보를 조회하고 감사 로그를 갱신하며, 저장된 해시와 비밀번호를 대조하는 계산 집약적 연산을 수행한다. 존재하지 않는 사용자명은 이 처리 중 상당 부분을 건너뛴다. 이 시간 차이를 감지하면 유효 사용자명을 열거할 수 있다.
- **타임아웃이 걸리는 동작.** 프런트엔드 로드밸런서 뒤의 호스트 주소를 쿠키에 담는 애플리케이션이 있다고 하자. 이 주소를 조작해 내부망의 웹 서버를 훑을 수 있다. 실제 서버 주소를 넣으면 즉시 오류가 나지만, 존재하지 않는 주소를 넣으면 애플리케이션이 접속을 시도하다 타임아웃이 난 뒤에야 같은 일반 오류를 낸다. 두 경우의 오류 메시지는 **동일**하지만, 응답 시간이 둘을 갈라놓는다. 이것은 28.8절의 SSRF 탐지가 응답 시간을 신호로 쓰는 것과 정확히 같은 구조다.

이 세 경우에서 오류 메시지는 아무 도움이 되지 않는다. 채널은 오로지 시간이다.

### 30.3.2 이 채널을 탐침하는 법

응답 시간 차이는 미묘하고 감지하기 어렵다. 그래서 무차별로 시도하기보다, **결정적 데이터 항목이 제출되고 그 처리가 시간 차를 낳을 법한 핵심 지점**에서만 선택적으로 탐침하는 것이 실용적이다. 절차는 다음과 같다. 유효한(또는 최근 접근된) 항목 목록과 무효한(또는 휴면인) 항목 목록을 각각 만든다. 한 번에 하나씩 요청을 던지며 응답까지 걸린 시간을 기록한다. 항목의 상태와 응답 시간 사이에 상관관계가 있는지 판정한다. 인터셉팅 프록시의 자동 공격 도구는 각 요청의 응답 시작 시각과 완료 시각을 자동으로 기록하므로, 결과 표를 시간으로 정렬하면 명백한 상관관계를 빠르게 찾을 수 있다.

이 방법론이 22장·27장의 것과 같다는 점을 다시 강조한다. 22.2절이 "상세한 실패 메시지"를 다룰 때 문제 삼은 것은 메시지의 내용만이 아니라, 유효·무효를 가르는 **관찰 가능한 차이**의 존재 자체였다. 27.6절의 시간 기반 블라인드 인젝션은 공격자가 그 차이를 인위적으로 **만들어낸** 경우다. 이 절의 추론은 애플리케이션이 스스로 만든 차이를 줍는 경우다. 방어의 관점에서 둘은 하나의 문제로 수렴한다. 유효·무효, 활성·휴면, 존재·부재를 가르는 어떤 관찰 가능한 차이도 남기지 않는 것.

> **이 책의 범위를 넘어서**
>
> 응답 시간을 정보 채널로 쓰는 이 발상은, 이후 사이드채널 공격이라는 이름 아래 훨씬 정교한 분류 체계로 발전했다. 특히 암호 연산의 실행 시간에서 키 비트를 복원하는 타이밍 공격의 암호학적 형태는, 상수 시간 비교나 블라인딩 같은 대응책과 함께 별도의 연구 분야를 이룬다. 이 책은 그 분류와 암호학적 형태를 다루지 않는다. 여기서 다루는 것은 애플리케이션 로직의 시간 차이가 정보를 흘리는 웹 계층의 현상까지이며, 방어의 원리는 동일하다. 관찰 가능한 차이를 없애는 것이다.

## 30.4 정보 누출 방어 — 일반화된 오류 메시지, 민감 정보 보호, 클라이언트 측 누출 최소화

공격자가 유용하다고 여길 모든 정보의 노출을 막는 것은 가능하지도 바람직하지도 않다. 그러나 비교적 단순한 조치들로 누출을 최소한으로 줄이고, 노출되면 애플리케이션 보안을 치명적으로 무너뜨릴 가장 민감한 데이터를 지킬 수 있다. 이 절은 30.1~30.3에서 본 공격을 방어의 언어로 뒤집는다.

### 30.4.1 일반화된 오류 메시지

애플리케이션은 장황한 오류 메시지나 디버그 정보를 사용자 브라우저로 절대 반환해서는 안 된다. 데이터베이스 질의 오류든, 디스크 읽기 실패든, 외부 API 예외든, 예기치 못한 사건이 일어나면 애플리케이션은 **언제나 동일한 일반 메시지**로 오류 발생 사실만 알려야 한다. 진단을 위해 디버그 정보를 남겨야 한다면, 공개 접근이 불가능한 서버 측 로그에 보관하고, 필요하면 해당 로그 항목의 색인 번호만 사용자에게 주어 헬프데스크 문의 시 참조하게 한다.

대부분의 플랫폼과 웹 서버는 오류 정보를 브라우저에서 가리도록 설정할 수 있다. ASP.NET은 `web.config`의 `customErrors` 요소에서 `mode`를 `On` 또는 `RemoteOnly`로 두고 커스텀 오류 페이지를 지정한다. Java 플랫폼은 `web.xml`의 `error-page` 요소로 예외 타입이나 상태 코드별 커스텀 페이지를 지정한다. Apache는 `httpd.conf`의 `ErrorDocument` 지시자를 쓴다.

```apache
ErrorDocument 500 /generalerror.html
```

여기서 반드시 구별해야 할 것이 있다. **오류 메시지를 가리는 것과 결함을 고치는 것은 다르다.** 커스텀 오류 페이지는 30.1의 스택 트레이스가 브라우저에 뜨는 것을 막지만, 그 스택 트레이스를 유발한 경로 순회 취약점(→ 28.3) 자체는 그대로 있다. 이것은 12.11절이 WAF의 한계로 지적한 것과 같은 함정이다. WAF가 공격 문자열을 차단해도 그 문자열이 노리던 인젝션 결함은 코드에 남아 있다. 오류를 가리는 조치는 **정보 누출**을 줄일 뿐, 그 정보가 가리키던 **근본 결함**을 없애지 않는다. 표면을 덮는 것과 병을 고치는 것을 혼동하면, 가려진 결함은 다른 채널 — 이를테면 30.3의 응답 시간 — 로 다시 드러난다.

### 30.4.2 민감 정보 보호

애플리케이션은 사용자명, 로그 항목, 프로필 상세처럼 공격자에게 쓸모 있는 정보를 가능한 한 발행하지 말아야 한다. 그런 정보가 꼭 필요한 사용자에게만, 유효한 접근 제어로 보호한 채 제공한다. 인가된 사용자에게 민감 정보를 보여줘야 하는 경우(예: 사용자가 자기 계정 정보를 갱신할 때)에도 **불필요하게 기존 데이터를 노출하지 않는다.** 저장된 신용카드 번호는 잘린 형태로만 표시하고, 비밀번호 필드는 화면에 마스킹되더라도 미리 채워 넣지 않는다. 이 조치들은 인증·세션·접근 제어라는 핵심 보안 메커니즘에 심각한 결함이 있더라도 그 충격을 완화하는 심층 방어의 한 겹이다.

### 30.4.3 클라이언트 측 누출 최소화

서버 배너는 가능하면 제거하거나 수정해 특정 소프트웨어 버전 노출을 줄인다. 이 정보가 25.6절의 핑거프린팅에 재료가 되기 때문이다. 라이브 환경에 배포되는 클라이언트 코드에서는 HTML과 JavaScript의 **모든 주석을 제거**한다. 30.2.3에서 봤듯 주석에 남은 링크·필드·버그 메모가 정찰의 출발점이 된다. 자바 애플릿이나 브라우저 확장 컴포넌트에는 어떤 민감 정보도 숨기지 말아야 한다. 숙련된 공격자는 이들을 디컴파일해 사실상 소스를 복원할 수 있으므로, "클라이언트에 숨긴다"는 것은 보호가 아니다(→ 26장).

> **이 절이 뒷받침하는 것**
>
> - 일반화된 오류 페이지가 결함을 고치지는 않는다 → **12.11** (WAF가 공격을 가려도 인젝션 결함은 코드에 남는다 — 같은 함정)
> - 배너 제거·주석 제거 → **25.6** (핑거프린팅이 이 재료를 잃는다), **25.2** (공개 리소스 참조의 재료가 줄어든다)
> - 클라이언트에 숨긴 값은 보호가 아니다 → **26.7** (클라이언트로 전달된 데이터의 안전한 처리)

## 30.5 예외로 실패를 다루기 — 던지기, 처리하기, 예외 페이로드에 무엇을 담지 말 것인가

여기서 렌즈가 바뀐다. 30.1~30.4는 실패의 순간에 무엇이 새는지를 공격자와 방어자의 눈으로 봤다. 30.5부터는 그 실패를 **애초에 어떻게 코드로 표현하는가**를 설계자의 눈으로 본다. 실패와 보안이 함께 간다는 인식은 안전한 소프트웨어를 설계할 때 결정적이다. 많은 시스템이 실패할 때 내부의 비밀을 드러내며, 실패를 어떻게 다루느냐가 곧 시스템의 보안 수준을 정의하기 때문이다.

가장 흔한 설계 선택부터 보자. 예외다. 예외는 프로그램의 정상 흐름을 끊을 수 있기 때문에 실패를 나타내는 데 자주 쓰인다. 그래서 예외는 흐름이 끊긴 **이유**(메시지)와 **위치**(스택 트레이스)에 관한 정보를 실어 나른다. 30.1.2에서 공격자의 눈으로 본 스택 트레이스를, 이제 그것을 생산하는 코드의 눈으로 본다. `java.sql.SQLException`이라는 첫 줄 하나가, 데이터가 관계형 데이터베이스에 저장되어 SQL 인젝션에 취약할 수 있다는 것과 코드가 Java로 쓰였다는 것을 동시에 알린다. 스택 트레이스의 상세함은 공유가 아니라 문제 해결을 위한 것인데, 왜 그것이 종종 최종 사용자에게 드러나는가. 답은 허술한 설계와, **예외가 왜 던져지는지 이해하지 못한 것**의 결합에 있다.

### 30.5.1 왜 던지는가 — 업무 예외와 기술 예외를 섞지 말라

애플리케이션에서 예외가 던져지는 이유는 크게 셋이다. 업무 규칙 위반, 기술적 오류, 그리고 하위 프레임워크의 실패. 셋 다 불법적 동작을 막는다는 목표는 같지만 목적은 다르다. **업무 예외**는 도메인 관점에서 불법인 동작을 막는다. 잔액이 부족한 계좌에서 출금하거나 이미 결제된 주문에 항목을 더하는 것 같은. **기술 예외**는 도메인 규칙과 무관하게, 메모리가 부족해 주문에 항목을 더할 수 없는 것처럼 기술적으로 불법인 동작을 막는다.

이 둘을 같은 예외 타입으로 섞으면 복잡성과 보안 문제로 가는 문이 열린다. 온라인 서점의 회원 계정 조회를 예로 보자. 고객의 계정들을 데이터베이스에서 가져와 주어진 계정 번호와 일치하는 것을 반환하는데, 일치하는 계정이 없으면 `IllegalStateException`을 던지고, 데이터베이스 오류가 나도 `IllegalStateException`을 던진다.

```java
public Account fetchAccountFor(final Customer customer,
                               final AccountNumber accountNumber) {
    try {
        return accountDatabase.selectAccountsFor(customer).stream()
                .filter(account -> account.number().equals(accountNumber))
                .findFirst()
                .orElseThrow(() -> new IllegalStateException(
                    format("No account matching %s for %s",
                           accountNumber.value(), customer)));
    } catch (SQLException e) {
        throw new IllegalStateException(
            format("Unable to retrieve account %s for %s",
                   accountNumber.value(), customer), e);
    }
}
```

계정이 없는 것은 업무 관점의 사건("계정 번호가 틀렸습니다")이고, 데이터베이스 오류는 기술 관점의 사건("일시적 기술 문제입니다")이다. 하나는 도메인이 처리해야 하고, 다른 하나는 도메인이 규칙을 가질 필요조차 없이 주변 프레임워크가 일반 메시지로 처리해야 한다. 그런데 둘 다 `IllegalStateException`이라면, 이것을 받는 쪽은 무엇으로 둘을 구별할 것인가. 유일한 차이는 내부 메시지 문자열("No account matching" 대 "Unable to retrieve account")뿐이다. 메시지 문자열을 판별자로 쓰는 코드는 극도로 취약하다. 메시지를 바꾸거나 다른 업무 예외를 추가하는 순간, 업무 예외가 도메인 밖으로 새어 나가고, **바로 이것이 민감 데이터가 로그에 남거나 최종 사용자에게 표시되는 경로**다.

올바른 해법은 업무적으로 중요한 예외를 명시적 타입으로 정의하는 것이다. `AccountNotFound`가 `AccountException`(마커 타입)을 상속하게 하면, 처리 로직은 메시지를 파싱하지 않고 타입으로 분기한다. `AccountException`을 포괄적으로 잡는 안전망 덕분에 **모든 업무 예외가 처리되고, 기술 예외만 전역 예외 핸들러로 전파된다**는 것을 보장할 수 있다.

### 30.5.2 예외 페이로드 — 담지 말아야 할 것

예외를 명시적으로 분리해도 절반만 온 것이다. 나머지 절반은 페이로드에 있다. 예외는 타입과 페이로드로 이뤄지고, 개발자는 실패 분석에 도움이 되도록 페이로드에 업무 정보를 잔뜩 담는 경향이 있다. 앞의 코드에서 `SQLException`을 감싼 `IllegalStateException`이 계정 번호와 고객 데이터를 담고 있는 것을 보라.

```java
catch (SQLException e) {
    throw new IllegalStateException(
        format("Unable to retrieve account %s for %s",
               accountNumber.value(), customer), e);   // 계정 번호·고객 데이터 누출
}
```

이것은 **기술 예외**인데도 업무 데이터를 실었다. 모든 기술 예외는 전역 예외 핸들러로 전파되고, 핸들러는 롤백 전에 모든 예외 데이터를 로그에 남긴다. 그 결과 계정 번호와 주민번호·주소·고객 ID가 데이터베이스 오류가 날 때마다 로그에 기록된다. 이는 16.6절이 "로그에 검증되지 않은 문자열을 넣지 말라"고 경고하는 것과 같은 병의 다른 얼굴이며, 16.4절이 지적한 "로그가 누출하는 것"의 구체적 사례다.

문제를 더 어렵게 만드는 것은, 무엇이 민감한지 알기 어렵다는 점이다. 예외는 컨텍스트 경계를 넘나들고, 한 컨텍스트에서 무해한 데이터가 다른 컨텍스트로 들어가면 민감해진다. 자동차 번호판은 공개 정보처럼 보이지만, 그것으로 차량 등록 정보를 조회해 소유자를 특정하는 순간 공유하고 싶지 않은 정보가 된다. 이로부터 두 가지 원칙이 나온다.

첫째, **기술 예외에는 업무 데이터를 절대 담지 않는다.** 민감하든 아니든 상관없다. 기술 관점에서 말이 되는 정보만 담는다. 계정 번호와 고객 데이터 대신 "ID XYZ 데이터베이스에 연결할 수 없음"처럼. 둘째, **도메인 안에서 민감 데이터를 민감한 것으로 모델링한다.** 44.5절의 읽기 1회 객체(read-once object)를 쓰면, 계정 번호와 고객 데이터가 전역 예외 핸들러에서 두 번째로 읽힐 때(즉 로그로 직렬화될 때) 그 불법적 접근이 탐지된다. 이것이 22.9절이 "비밀을 코드에서 다루는 법"으로 다루는 바로 그 기법이다. 예외를 흐름 제어에 쓰는 선택이 데이터 누출의 문을 여는 것이므로, 업무·기술 예외의 분리와 읽기 1회 패턴을 함께 써야 그 문을 닫을 수 있다.

## 30.6 실패는 예외적이지 않다 — 예외 없는 실패 처리와 실패를 위한 설계

예외로 실패를 표현하는 것은 흔한 관행이지만, 그만큼 흔한 또 하나의 접근은 예외를 아예 쓰지 않는 것이다. 이 접근의 출발점은 하나의 설계 마인드셋이다. **실패는 우리가 하는 모든 일의 자연스럽고 예상된 결과다.** 예외(exception)는 이름 그대로 예외적인 것을 뜻하는데, 실패가 예상된 결과라면 그것을 예외로 모델링하는 것은 애초에 말이 되지 않는다. 실패는 성공과 똑같이, 수행된 연산의 **가능한 결과 중 하나**로 모델링되어야 한다.

계좌 간 송금을 예로 보자. 은행 도메인에서 송금은 두 결과를 가질 수 있다. 성공하거나, 잔액 부족으로 실패하거나. 예외로 설계하면 잔액이 부족할 때 `InsufficientFundsException`을 던진다. 이때 우리는 프로그래밍 언어의 두 메커니즘 — 메서드의 반환값과 예외 — 을 동시에 흐름 제어에 쓰고 있으며, **잔액 부족을 예외적 사건으로 취급**하고 있다. 그러나 은행에서 잔액보다 큰 금액의 송금을 시도하는 것은 드문 일이 아니다. 금액을 잘못 입력했거나, 잔액을 실제보다 많다고 착각했거나. 잔액 부족은 "송금을 시도한다"는 연산의 **예상된 결과**다. 예상된 결과라면 예외가 아니라 결과로 모델링해야 한다.

```java
public Result transfer(final Amount amount, final Account toAccount) {
    notNull(amount);
    notNull(toAccount);
    if (balance().isLessThan(amount)) {
        return INSUFFICIENT_FUNDS.failure();   // 예외를 던지지 않고 결과를 반환
    }
    return executeTransfer(amount, toAccount);
}
```

`transfer`는 이제 예외를 던지지 않는다. 성공 또는 실패를 나타내는 `Result`를 반환하고, 호출 측은 결과를 검사해 어떤 실패였는지 안다. 이렇게 실패를 예상된 무해한 결과로 설계하면 예외를 도메인 로직에서 완전히 제거할 수 있고, 그와 함께 예외가 낳던 보안 문제들도 사라진다.

**표 30-1. 실패를 예상된 결과로 설계할 때의 보안 이점 (SBD 표 9.1 기준)**

| 예외로 설계할 때의 보안 문제 | 결과로 설계하면 |
|---|---|
| 도메인 예외와 기술 예외의 모호성 | 도메인 예외가 통째로 사라진다 |
| 예외 페이로드가 로그로 새는 것 | 실패를 일반 오류 처리 코드가 다루지 않으므로, 페이로드가 오류 로그에 흘러들지 않는다 |
| 민감 정보의 의도치 않은 누출 | 실패가, 무엇이 민감한지 아는 컨텍스트에서 처리되므로 민감 데이터를 올바르게 다룬다 |

여기에 더해 실용적 이점이 하나 더 있다. 성공과 실패를 모두 결과로 설계하고 나면, 그래도 여전히 일어나는 예외는 **버그나 불변식 위반이 원인인 것뿐**이다. 즉 예외의 존재 자체가 "무언가 정말로 잘못됐다"는 명확한 신호가 된다. 이것은 43.2절이 "계약으로 빠르게 실패하기"에서 말하는 것과 통한다. 정상 흐름의 예상된 실패는 결과로 흡수하고, 예외는 오직 계약 위반 — 절대 일어나서는 안 되는 일 — 에만 남겨 두는 것이다.

한편 실패를 정상 경로로 설계한다는 것은 **가용성**을 설계한다는 것과 이어진다. 가용성은 CIA(기밀성·무결성·가용성)의 한 축인 명백한 보안 목표다. 복원력 있는(resilient) 시스템은 실패가 있어도 계속 서비스를 제공하므로, 정의상 더 안전한 시스템이다. 서킷 브레이커, 타임아웃, 벌크헤드 같은 복원력 패턴이 곧 보안 패턴인 이유가 여기에 있다. 다만 이 절의 초점은 실패를 코드 수준에서 안전하게 표현하는 데 있으므로, 가용성 설계의 상세 — 서킷 브레이커의 세 상태, 벌크헤드의 격리, 폴백 응답을 도메인 전문가와 함께 정하는 문제 — 는 45장에서 본격적으로 다룬다.

## 30.7 입력을 절대 그대로 반향하지 말라

30.5에서 예외 페이로드에 업무 데이터를 담지 말라고 했다. 이 절은 그 원칙의 형제다. **실패한 입력 자체를 오류 메시지나 로그에 그대로 되돌려 담지 말라.**

계약이 실패했을 때, 개발자는 그 원인을 알고 싶어 한다. 프로그래밍 오류였는가, 잘못된 입력이었는가. 그래서 실패 분석을 돕기 위해 입력을 오류 메시지에 그대로 반향하는 경우가 많다. 온라인 서점의 회원 이름을 검증하는 도메인 프리미티브를 보자. 이름은 알파벳과 공백만 허용하고 2~100자로 제한된다.

```java
Validate.matchesPattern(value, "^[a-zA-Z ]+[a-zA-Z]+$",
                        "Invalid name. Got: " + value);   // 입력을 그대로 반향
```

공격자가 이름 필드에 `%3Cscript%3Ealert("XSS")%3C/script%3E`를 넣으면 정규식 검증이 실패하고, 이 문자열을 그대로 담은 오류 메시지가 만들어진다. 이 메시지가 로그에 남거나 사용자에게 표시되면, 애플리케이션은 사실상 **공격자에게 출력을 통제할 권한을 넘긴 것**이다. `%3Cscript%3E...`를 로그에 남기는 것은 무해해 보이지만, 브라우저 기반 로그 분석 도구가 적절한 이스케이프 없이 이 데이터를 해석하면, 그것은 코드로 실행된다. 이 예시는 경고창 하나를 띄우는 데 그치지만, JavaScript가 실행될 수 있다는 사실 자체가 극도로 위험하다. 공격자는 이를 이용해 키로거를 심거나, 자격증명을 훔치거나, 세션을 탈취할 수 있다.

이 공격에는 이름이 있다. **2차(second-order) 공격**이다. 공격자는 자신이 마주한 시스템(회원 등록 폼)이 아니라, 그 뒤에 있는 두 번째 시스템(로그 분석 도구)을 공격한다. 공격 문자열을 로그에 남게 만든 뒤, 관리자가 취약한 도구로 그 로그 항목을 열어 보기를 기다리는 것이다. 이것이 성립하는 이유는 데이터가 컨텍스트 경계를 넘을 때 의미가 달라지기 때문이다. 회원 컨텍스트에 들어온 JavaScript 문자열은 그 자체로는 무해하다. 그것이 실행되는 로그 분석기 컨텍스트에서 코드로 해석될 때만 해로워진다.

**이 절은 32장 XSS 방어의 설계적 뿌리다.** 32장은 반사형·저장형·DOM 기반 XSS를 유형별로 나누고 출력 컨텍스트별 인코딩을 상세히 다루지만, 그 모든 처방이 자라난 하나의 원리가 여기에 있다. **사용자가 보낸 데이터를 애플리케이션의 어떤 출력에도 그대로 실어 보내지 말라.** XSS란 결국 이 원리가 HTML 출력이라는 특정 컨텍스트에서 깨진 것이다. 로그, 오류 메시지, HTTP 헤더(→ 8.7), 그리고 30.10에서 볼 GraphQL 오류 응답까지 — 반향이 일어나는 자리는 HTML만이 아니다. 확신이 서지 않으면 안전하게 가라. 입력을 반향하지 마라.

## 30.8 잘못된 데이터를 검증 전에 복구하지 말라

30.7이 실패한 입력을 되돌려 보내는 문제였다면, 이 절은 그 입력을 **검증하기 전에 고쳐 쓰는** 문제다. 둘은 온라인 서점의 같은 사례에서 결합해 하나의 취약점을 이룬다.

데이터를 다룰 때 — 데이터베이스든, 사용자 입력이든, 외부 소스든 — 그것이 후행 공백, 누락된 문자, 그 밖의 결함으로 부분적으로 깨져 있을 가능성은 늘 있다. 계약(→ 43.2)으로 잘못된 상태와 입력을 막으면 설계가 단단해지고 가정이 명시화되지만, 그 대가로 하나의 유혹이 따라온다. **불필요한 거부를 피하려고 검증 전에 데이터를 복구하는 것**이다. 이 선택은 극도로 위험하다. 취약점을 노출하고 거짓 안전감을 낳기 때문이다.

서점이 회원 데이터베이스를 다른 시스템의 데이터로 확장하기로 했다고 하자. 그런데 새 데이터의 품질이 나쁘다. 어떤 이름은 비어 있고, 어떤 이름은 특수문자를 담았으며, 몇 년 전 잘못된 XML 임포트에서 온 `<`와 `>` 문자를 담은 것도 있다. `Name` 계약이 이것들을 무더기로 거부한다. 근본 해법은 데이터를 원천에서 고치는 것이지만, 이 데이터는 여러 시스템이 공유하므로 회원 컨텍스트에 맞춘 수정이 다른 시스템에는 부적절할 수 있다. 그래서 사업부는 데이터를 그대로 두고, **회원 컨텍스트에서 검증되기 전에 복구 필터를 적용**하기로 한다. 불필요한 거부가 크게 줄어드는 성공이 확인되자, 이 필터를 모든 입력 소스에 적용하기로 확대한다.

바로 여기서 보안이 무너진다. 필터는 입력이 통과할 때마다 그것을 변형해 **원본에서 파생된 새 문자열**을 만든다. `<`와 `>`를 제거하면 `<script>` 태그가 해체되어 XSS를 막을 수 있다고 많은 이가 믿는다. 그러나 이것은 거짓 안전감일 뿐이다. 다음을 복구 필터에 주입한다고 하자.

```
%3<Cscript%3>Ealert("XSS")%3<C/script%3>E
```

`<`와 `>`를 떨어내면 이렇게 된다.

```
%3Cscript%3Ealert("XSS")%3C/script%3E
```

이것은 `<script>alert("XSS")</script>`와 정확히 같은 JavaScript다. `<`와 `>`가 16진 인코딩으로 표현되었을 뿐이다. **복구 필터가 위험한 입력을 없앤 것이 아니라, 안전해 보이는 입력을 위험한 것으로 바꿔 놓았다.** 그리고 이 파생 문자열이 검증에 실패해 30.7의 반향을 거쳐 로그에 남으면, 두 결함이 하나로 합쳐진다.

이것이 검증 전 복구가 위험한 근본 이유다. 복구는 데이터를 변형하고, 변형된 데이터는 원본이 통과하지 못했을 검증을 통과하거나, 원본에 없던 위험한 형태를 얻는다. 이 문제는 7.7절의 다중 인코딩·정규화 문제와 정확히 같은 뿌리에서 나온다. 오버롱 UTF-8이나 이중 디코딩이 위험한 이유도, 디코딩(일종의 복구)이 검증 이후에 일어나거나 검증과 뒤섞여서 검증이 본 것과 인터프리터가 받는 것이 달라지기 때문이다. 그래서 처방은 **순서**의 문제로 수렴한다. 43.4절이 정식화하는 검증의 순서 — 출처 → 크기 → 어휘적 내용 → 구문 → 의미 — 에서, 복구나 정규화는 검증의 **앞**이 아니라 정해진 자리에 놓여야 하며, 검증을 우회하는 지름길이 되어서는 안 된다. 데이터를 고쳐야 한다면 원천에서 고치고, 그럴 수 없다면 거부하되 복구로 검증을 무력화하지 말라.

> **이 절이 뒷받침하는 것**
>
> - 검증 전 복구가 검증을 무력화한다 → **43.4** (검증의 순서가 이 문제를 정식으로 다룬다), **7.7** (다중 인코딩·정규화가 같은 뿌리의 문제다)
> - 복구된 문자열이 반향되어 2차 공격이 된다 → **30.7**, **32.8** (XSS 방어의 입력 검증)

## 30.9 설정 관련 보안 결함의 원인과 설정 검증 자동화

앞의 여덟 절이 코드가 실패하는 방식이었다면, 이 절은 코드를 한 줄도 바꾸지 않고도 시스템이 취약해지는 방식을 다룬다. 현대 개발에서 흔한 기능은 대개 **설정**으로 실현된다. 기존 라이브러리나 프레임워크를 들여와, 직접 구현하지 않고도 기능을 켜고 끄고 조정한다. HTTPS 구현이나 ORM 프레임워크를 손수 짜는 대신 검증된 외부 구현을 쓰는 것은 대부분 합리적이다. 그러나 그 결과, 애플리케이션의 중요한 기능이 현재 팀 바깥의 코드로 제공되고 **설정으로 통제된다.** 그 기능이 보안에서 중심 역할을 한다면, 설정의 오류가 곧바로 보안 문제가 된다.

### 30.9.1 설정 결함의 세 원인

잘못된 설정에서 비롯된 보안 결함은 크게 세 원인으로 나뉜다.

- **의도하지 않은 변경.** 설정 한 줄을 실수로 바꾸거나 문자열 파라미터의 철자를 틀리면, 애플리케이션의 동작이 조용히 바뀐다. 예외도 오류도 나지 않는다. 운이 나쁘면 그 바뀐 동작이 애플리케이션을 취약하게 만들고, 더 나쁘면 운영에 배포된 뒤에야 알아챈다. 오타, 잘못된 병합(bad merge), 빠진 테스트가 이 범주다.
- **의도한 변경의 부작용.** 새 기능을 위해 설정을 바꾸고 새 동작을 검증까지 했는데, 그 변경이 **애플리케이션의 다른 부분**의 동작도 바꿨다는 것을 알아채지 못하는 경우다. 바꾼 설정이 과거 보안 감사나 침투 테스트의 결과로 다른 개발자가 신중히 넣어 둔 것이었다면, 그것을 건드리면서 보안 기능을 꺼 버린 것이다. 여기서 개발자는 잘못한 것이 없다. 올바른 변경을 의도대로 했을 뿐이다. 더 조심하거나 절차를 강화하는 것으로는 막을 수 없다.
- **오해한 설정.** 설정 메커니즘 자체를 이해하지 못해, 어떤 동작을 설정한다고 믿지만 실제로는 다른 것을 설정하는 경우다. 정수 값, 매직 스트링, 부정문(negating statement)은 모호한 설정 API의 전형적 징후다. 그런 설정을 쓸 때는 자신이 생각한 것을 얻지 못하고 있을 가능성이 크다.

### 30.9.2 자동 테스트라는 안전망

세 원인 모두에 대한 효과적 대응은 하나다. 설정으로 켜지는 동작을 검증하는 **자동 테스트를 작성해 배포 파이프라인의 회귀 스위트로 삼는 것**이다. 이때 유용한 개념이 **설정 핫스팟(configuration hot spot)** 이다. 핫스팟이란 통제하는 동작이 시스템 보안에 직접·간접으로 영향을 주는 설정 영역을 말한다. 대표적 핫스팟은 다음과 같다.

**표 30-2. 테스트해야 할 설정 핫스팟 (SBD 표 8.5 기준)**

| 설정의 종류 | 통제되는 동작의 예 |
|---|---|
| 웹 컨테이너 | HTTP 헤더, CSRF 토큰, 출력 인코딩 |
| 네트워크 통신 | 전송 계층 보안(HTTPS 등) |
| 데이터 파싱 | XML·JSON 파서의 동작 |
| 인증 메커니즘 | 인증 켜기/끄기, LDAP 등 통합 설정 |

여기서 핵심은, 우리가 검증하는 것이 **설정 자체가 아니라 설정이 낳는 동작**이라는 점이다. 단순히 값을 설정하는 세터를 테스트하는 것과 혼동해 "가치가 없다"는 반론이 나오곤 하지만, 우리가 테스트하는 것은 애플리케이션의 동작을 바꾸는 설정이다. 웹 애플리케이션에서 적절한 HTTP 헤더가 붙는지, 폼이 CSRF 토큰을 쓰는지 확인하는 테스트는 어렵지 않게 짤 수 있다.

### 30.9.3 기본값을 알고 검증하라

명시적으로 설정한 동작뿐 아니라, 설정 없이 얻는 **암묵적(기본) 동작**도 검증해야 한다. 기본 동작은 설정이 없기 때문에, 검증할 중요한 기능이 있다는 사실 자체를 알기 어렵다는 것이 까다로운 지점이다. 그래서 쓰는 도구의 기본값을 알아야 한다. 현대 웹 프레임워크는 합리적 기본 동작으로 생산성을 높이지만, 어떤 기본값은 편의를 위해 보안을 일부 희생한다. 그 트레이드오프를 모르면 자신도 모르게 취약점을 노출한다.

한 예로 HTTP 서비스를 짤 때는 공격 표면을 줄이기 위해 API가 요구하는 HTTP 메서드만 활성화하는 것이 좋다. GET으로 데이터를 제공하는 엔드포인트가 다른 메서드에도 정상 응답하지 않도록 하고, 지원하지 않는 메서드에는 `405 Method Not Allowed`나 `501 Not Implemented`로 답해야 한다. 특히 `TRACE`는 크로스 사이트 트레이싱(XST) 공격에 쓰일 수 있으므로 꼭 필요하지 않으면 켜지 말아야 한다(→ 8.3.3). 아래처럼 엔드포인트에 활성화된 메서드가 기대한 것뿐인지 확인하는 테스트를 두면, 프레임워크의 기본값이 조용히 여분의 메서드를 열어 두었는지 잡아낼 수 있다.

```java
@Test
public void verify_only_expected_HTTP_methods_are_enabled() {
    givenEndpoint("http://bookstore.example.com/catalog");
    whenTestingMethods(HTTPMethod.values());
    thenTheOnlyMethodsEnabledAre(GET, HEAD);
}
```

이 절은 문제의 원인과 안전망의 원리를 세우는 데 그친다. 설정 검증을 배포 파이프라인 전체와 코드형 인프라 안에 어떻게 짜 넣는지 — 기능 토글의 조합 복잡도, 감사 대상으로서의 토글, 기본값 확인의 실전 — 는 46.12절이 상세히 다룬다.

## 30.10 GraphQL의 정보 노출 — 오류 메시지 남용, 필드 제안, 인트로스펙션 노출

세 번째 렌즈다. 지금까지 본 정보 노출의 모든 형태 — 오류 메시지가 내부를 흘리고, 스택 트레이스가 파일 경로와 프레임워크를 드러내고, 실패가 백엔드의 구조를 노출하는 것 — 이 현대 GraphQL API에서 **더 친절한 얼굴로** 재현된다. GraphQL은 개발자 경험을 위해 기본적으로 클라이언트에게 많은 것을 알려주도록 설계되었고, 그 친절함이 곧 정보 노출의 표면이다.

이 절은 "정보 노출"이라는 하나의 관점에서만 GraphQL을 다룬다. 같은 기법들을 **정찰**의 관점 — 스키마를 재구성하고 구현체를 핑거프린팅하는 능동적 지도 그리기 — 에서 상세히 다루는 것은 39장이다. 여기서 개관하는 InQL 자동 추출, 인트로스펙션 비활성 우회, Clairvoyance, 오류 메시지 남용은 각각 39.4~39.7절이 도구와 절차 수준까지 파고든다. 이 절의 목표는 그 기법들이 30.1~30.4에서 본 **고전적 정보 노출의 재현**임을 보이는 것이다.

### 30.10.1 오류 메시지 남용 — 30.1과 30.2의 재현

GraphQL 오류 응답은 REST와 달리 표준 HTTP 상태 코드에 의존하지 않고, `message`·`location`·`path` 세 필드를 담은 JSON 배열로 온다. 대부분의 정보 노출은 `message` 필드에서 일어난다. 온라인 서점의 GraphQL API에 이미 존재하는 사용자명으로 회원 생성 뮤테이션을 보내면 이런 응답이 온다.

```json
{
  "errors": [
    {
      "message": "(sqlite3.IntegrityError) UNIQUE constraint failed: users.username\n[SQL: INSERT INTO users (username, password) VALUES (?, ?)]\n[parameters: ('tom', 'secret')]",
      "path": ["createUser"]
    }
  ]
}
```

이 한 응답이 과도하게 공유하는 것을 보라. `message`가 SQLite3 데이터베이스에서 곧장 나왔고, 사용자 레코드를 삽입하는 **SQL 문 전체**를 준다. `username` 컬럼과, 삽입 시 암호화되지 않는 `password` 컬럼이 그대로 드러난다. 이 하나의 오류로 공격자는 SQL 데이터베이스를 핑거프린팅하고(→ 27.3), 유효 계정을 열거할 실마리를 얻으며, SQL 질의 구조를 알아 인젝션 공격을 미세 조정할 수 있다(→ 27.14). 이것은 30.1.4에서 본 백엔드 DB 메시지 노출과, 30.2.2에서 본 정보성 오류 유도가 GraphQL에서 정확히 같은 형태로 재현된 것이다.

디버그 모드가 켜졌거나 특정 엔드포인트가 다르게 설정된 경우, 오류의 `extensions` 필드에 **스택 트레이스**가 실려 온다. 그것은 30.1.2의 스택 트레이스와 똑같이 파일시스템 경로, 사용자 계정, 운영체제, 프레임워크 버전, 소스 코드 조각을 넘겨준다. 같은 서버의 `/graphql` 엔드포인트는 스택 트레이스를 던지지 않는데 `/graphiql` 엔드포인트는 던지는 식으로, 엔드포인트마다 설정이 다를 수 있으므로 여러 엔드포인트를 모두 시험해야 한다. 이는 30.9의 설정 결함이 GraphQL 표면에서 드러나는 자리다.

### 30.10.2 필드 제안 — GraphQL만의 정보 노출

여기서부터는 GraphQL 특유의 것이다. **필드 제안(field suggestion)** 은 클라이언트가 오타를 보내면 서버가 가능한 정정을 제안하는 기능이다. REST가 잘못된 질의에 `400 Bad Request`로 답하는 것과 달리, GraphQL은 훨씬 친절하게 존재하는 필드를 알려준다. 서점 API에서 `pastes` 대신 `title`을 `titlr`로 오타 내면 이렇게 답한다.

```json
{
  "errors": [
    {
      "message": "Cannot query field \"titlr\" on type \"PasteObject\". Did you mean \"title\"?"
    }
  ]
}
```

`Cannot query field ... Did you mean ...?`라는 이 메시지가 스키마의 실제 필드 이름을 흘린다. 서버는 편집 거리(edit-distance) 알고리즘으로 오타와 유효 필드의 유사도를 재고, 임계값 안에 드는 필드를 **모두** 제안한다. 한 요청에 오타를 몇 개든 담을 수 있고 서버는 각각에 제안을 주므로, 대량 정보 수집이 가능하다. 위험의 핵심은, **인트로스펙션이 꺼져 있어도 필드 제안이 스키마를 조금씩 누설**한다는 점이다. 이 누설을 자동화해 스키마 전체를 재구성하는 것이 39.6절의 Clairvoyance다.

여기에 **필드 스터핑(field stuffing)** 이 겹친다. 객체의 필드가 데이터베이스 컬럼과 가깝게 대응한다는 점을 이용해, `password`, `ssn`, `apiKey`, `token` 같은 민감할 법한 필드 이름을 질의에 밀어 넣어 보는 것이다. 운이 좋으면 하나가 실제로 해석되어 데이터를 반환하거나, 편집 거리 안에서 대안 필드 이름을 제안받는다. 이것은 25.3절의 "숨겨진 콘텐츠 발견 — 무차별 대입·추론"이 GraphQL 스키마를 대상으로 재현된 것이다.

### 30.10.3 인트로스펙션 노출과 그 우회

GraphQL의 **인트로스펙션**은 스키마 전체를 질의로 뽑아내는 기능이며, 대부분의 구현체에서 기본으로 켜져 있다. 이것이 켜져 있으면 InQL 같은 도구로 스키마를 통째로 자동 추출할 수 있다(→ 39.2, 39.4). 개발자가 이를 위험으로 인식해 인트로스펙션을 끄더라도, 그 차단이 허술하면 우회된다.

- **`__type` 메타필드.** 많은 구현체가 `__schema` 키워드만 필터링하는데, `__type` 메타필드도 타입 정보를 뽑아낼 수 있다. 2022년 AWS AppSync에서, WAF가 `__schema`만 차단하고 `__type`은 고려하지 않아 인트로스펙션이 우회된 사례가 있다. `__schema` 차단이 30.4의 "오류를 가리는 것"에 해당한다면, `__type` 우회는 그것이 "결함을 고치는 것"이 아님을 보여준다. 이는 12.11절의 WAF 한계, 30.4.1의 "가리는 것과 고치는 것은 다르다"가 GraphQL에서 반복되는 자리다.
- **비운영 환경.** 운영에서 인트로스펙션이 꺼졌어도 `staging`이나 `dev` 서브도메인에서는 켜져 있을 수 있고, 거기서 얻은 스키마는 운영과 대개 비슷하다.
- **필드 제안을 통한 재구성.** 인트로스펙션과 필드 제안이 둘 다 꺼져 있어도, 앞서 본 필드 스터핑으로 스키마를 조각조각 복원할 수 있다.

그리고 GET 기반 질의는 별도의 누출 통로다. 일부 구현체는 GET으로 질의(때로는 뮤테이션)를 허용하는데, GET은 데이터를 URL 쿼리 파라미터로 실어 나르므로 전화번호 같은 PII가 웹 서버 접근 로그, 리퍼러 헤더, 경로상의 프록시에 남는다. 이것은 16.4절이 "로그가 누출하는 것"으로 다룬 문제가 GraphQL에서 재현된 것이다.

이 모든 GraphQL 정보 노출의 방어 원리는 앞 절들과 다르지 않다. 오류 메시지를 일반화하고(→ 30.4.1), 예외 페이로드에 업무·시스템 데이터를 담지 않으며(→ 30.5.2), 운영에서 인트로스펙션·필드 제안·디버그 모드를 끄고, 그 설정을 자동 테스트로 검증하는 것(→ 30.9)이다. 같은 병에는 같은 처방이 듣는다.

## 이 장의 요약

- **애플리케이션은 공격받을 때 말을 흘린다.** 정상 사용에서 조용하던 시스템도 개발자가 상상하지 못한 오류 조건 앞에서는 스택 트레이스와 디버그 덤프를 뱉는다. 스크립트 오류는 코드 경로를, 스택 트레이스는 라이브러리와 플랫폼 버전을, 디버그 메시지는 세션 변수와 자격증명을, 백엔드 메시지는 질의 구조를 넘겨준다.
- **오류 메시지는 데이터의 전달 통로가 된다.** 잘못된 형변환을 유도해 비밀번호 해시를 오류 메시지에 실어 나르게 하듯, 오류 조건을 체계적으로 조립하면 임의 데이터를 뽑아낼 수 있다. 애플리케이션이 스스로 발행한 정보와 공개 자료를 결합하면 내부 구조의 지도가 된다.
- **오류 메시지가 없어도 정보는 샌다.** 응답 시간, 상태 코드, 응답 길이의 차이가 채널이 된다. 이것은 22.2의 상세한 실패 메시지, 27.6의 시간 기반 블라인드 인젝션과 같은 구조다. 유효·무효, 활성·휴면을 가르는 어떤 관찰 가능한 차이도 정보다.
- **오류를 가리는 것과 결함을 고치는 것은 다르다.** 커스텀 오류 페이지는 스택 트레이스를 감추지만 그것을 유발한 경로 순회 결함은 그대로다. 이는 12.11의 WAF 한계와 같은 함정이며, 가려진 결함은 다른 채널로 다시 드러난다.
- **업무 예외와 기술 예외를 같은 타입으로 섞지 말라.** 메시지 문자열로 둘을 구별하는 코드는 취약하고, 그 취약함이 민감 데이터가 로그와 화면으로 새는 경로다. 명시적 예외 타입과 마커 타입으로 분리해야 기술 예외만 전역 핸들러로 전파됨을 보장한다.
- **기술 예외에 업무 데이터를 절대 담지 말라.** 무해해 보이는 데이터도 컨텍스트를 넘으면 민감해진다. 읽기 1회 객체(→ 44.5)로 민감 데이터를 모델링하면 로그로의 불법 직렬화가 탐지된다(→ 16.6, 22.9). 나아가 실패를 예외가 아니라 예상된 결과로 설계하면 이 누출 경로 자체가 사라진다.
- **입력을 그대로 반향하지 말라.** 실패한 입력을 오류 메시지나 로그에 되돌려 담으면 공격자가 출력을 통제하게 되고, 2차 공격의 발판이 된다. 이 원리가 32장 XSS 방어의 설계적 뿌리다. 반향이 일어나는 자리는 HTML만이 아니라 로그, 헤더, GraphQL 응답을 포함한다.
- **검증 전에 데이터를 복구하지 말라.** 복구 필터는 안전해 보이는 입력을 위험한 형태로 바꿔 놓을 수 있다(`%3<Cscript%3>E` → `%3Cscript%3E`). 이는 7.7의 다중 인코딩 문제와 같은 뿌리이며, 처방은 43.4의 검증 순서다. 복구가 검증을 우회하는 지름길이 되어서는 안 된다.
- **설정 결함은 코드를 바꾸지 않고도 시스템을 취약하게 만든다.** 의도하지 않은 변경, 의도한 변경의 부작용, 오해한 설정이 세 원인이다. 설정 핫스팟의 동작을 검증하는 자동 테스트가 안전망이며, 명시적 설정뿐 아니라 프레임워크 기본값도 검증해야 한다(→ 46.12).
- **같은 정보 노출이 GraphQL에서 더 친절한 얼굴로 재현된다.** 오류 메시지가 SQL 문 전체와 스택 트레이스를 넘겨주고, 필드 제안과 필드 스터핑이 인트로스펙션이 꺼져 있어도 스키마를 누설한다. 방어 원리는 앞 절들과 같다. 정찰 관점의 상세는 39.4~39.7이 다룬다.

## 이어지는 장

이 장은 실패의 순간을 세 렌즈로 봤다. 공격자는 흘러나온 정보를 줍고, 설계자는 실패를 코드로 안전하게 표현하며, 현대 API는 같은 병을 다시 앓는다. 세 렌즈가 겨눈 것은 하나였다. 신뢰 경계 안쪽이 실패의 순간에 바깥으로 새는 일이다.

31장은 이 장이 여러 번 지목한 두 개의 실 끝을 이어받는다. 30.1의 스택 트레이스가 노출한 애플리케이션 서버와 프레임워크, 30.9의 설정 결함이 드러낸 공유 호스팅 환경이, 이제 그 자체로 공격 표면이 된다. 계층 아키텍처, 공유 애플리케이션 서비스의 격리 실패, 프레임워크 결함, 그리고 네이티브 컴파일 코드의 메모리 취약점을 다루며, 31.7절은 이 장 30.8에서 예고한 인코딩·정규화 결함을 다시 방문한다.

그리고 이 장이 30.5~30.9에서 스케치한 설계 원리 — 예외 페이로드, 실패의 모델링, 반향 금지, 복구 순서, 설정 검증 — 는 Part IX가 완성한다. 43장이 불변성과 계약과 검증 순서를 코드 구조로 세우고, 44.5절이 읽기 1회 객체로 비밀의 누출을 막으며, 45장이 안전한 실패 처리와 가용성 설계를 도메인의 언어로 다룬다. 46.12절은 30.9의 설정 검증을 배포 파이프라인 전체로 확장한다. 이 장에서 우리는 "입력을 반향하지 말라"와 "검증 전에 복구하지 말라"를 두 개의 문장으로 제시했다. 그 두 문장이 왜 하나의 설계 원리 — 데이터가 컨텍스트를 넘을 때 그 의미가 바뀐다는 것 — 의 두 얼굴인지가 Part IX의 주제다.

> 30.1~30.4절: WAHH 15장 "Exploiting Information Disclosure" 전체를 근거로 한다. 스크립트 오류 메시지(`Type mismatch`, VBScript 800a000d), 스택 트레이스(ASP.NET `HttpException`과 버전 정보), 상세 디버그 메시지의 세션 덤프와 담기는 항목 목록, 백엔드·DB 메시지와 HTTP 500, 오류 유도(ODBC 형변환으로 비밀번호 해시 추출, Java UDF로 명령 실행 결과를 예외에 담기), 공개 정보 활용(검색 엔진·소스 검색·캐시), 발행된 정보 줍기, 추론(등록 기능의 사용자명 열거·검색 엔진 추론·블라인드 SQL·패딩 오라클, 캐시/지연 로딩에 의한 시간차, 입력 유효성에 따른 처리량 차, 타임아웃), 방어(일반화된 오류 메시지와 ASP.NET·Java·IIS·Apache 설정, 민감 정보 보호, 배너·주석 제거)는 원서 기준이다. 원시 응답 검색 키워드 목록도 원서의 것이다. 실행 예제의 도메인은 집필지침 §5에 따라 온라인 서점 맥락(`confirmOrder.asp`, `BookApp.Catalog`, 도서 카탈로그 질의)으로 옮겼고, 온라인 은행의 시간차 열거 사례는 구조가 흐려지는 것을 피해 원서 맥락을 유지했다. WAHH 15장 말미의 연습문제는 집필지침 §7에 따라 옮기지 않았다.
>
> 30.5~30.6절: Secure by Design 9장 "Handling failures securely"의 §9.1(Using exceptions to deal with failure — Throwing, Handling, Dealing with exception payload)과 §9.2(Handling failures without exceptions — Failures aren't exceptional, Designing for failures), 그리고 §9.3의 도입(Designing for availability, Resilience)을 근거로 한다. 닫힌 DB 커넥션의 `java.sql.SQLException` 스택 트레이스가 누설하는 것, 업무·기술 예외의 세 발생 이유(도메인 규칙·기술·프레임워크 위반), `fetchAccountFor`의 `IllegalStateException` 혼용과 메시지 문자열 판별의 취약성, `AccountNotFound extends AccountException` 마커 타입, 예외 페이로드에 업무 데이터를 담는 문제와 번호판 비유, 기술 예외에 업무 데이터를 담지 말라는 원칙, 읽기 1회 패턴 연결, `Result` 객체로 송금 실패를 결과로 모델링하기, 표 30-1(SBD 표 9.1)의 세 보안 이점, "남는 예외는 버그나 불변식 위반뿐"이라는 관찰은 원서와 동일하다. 코드 예제의 계정·송금 도메인은 SBD 원서의 것을 유지했다(집필지침 §5의 온라인 서점과 같은 은행·금융 도메인 계열).
>
> 30.7~30.8절: Secure by Design 9장 §9.4 "Handling bad data"(§9.4.1 Don't repair data before validation, §9.4.2 Never echo input verbatim)를 근거로 한다. `Name` 도메인 프리미티브의 정규식과 2~100자 제약, 다른 시스템 데이터 임포트로 인한 계약 실패와 복구 필터 도입 및 전 소스 확대, 복구 필터가 파생 문자열을 만든다는 관찰, `%3<Cscript%3>E...` 주입이 `<`·`>` 제거 후 `%3Cscript%3E...`가 되어 XSS로 성립하는 것, `matchesPattern`의 입력 반향과 2차 공격, 컨텍스트 경계를 넘을 때 데이터 의미가 바뀐다는 분석은 원서와 동일하다. 실행 예제의 회원 등록 도메인은 SBD 원서의 웹숍을 온라인 서점으로 옮긴 것이다. XSS 폴리글롯 사이드바는 이 절의 논지(반향·복구 금지)에서 벗어나므로 32장으로 미뤘고 본문에 넣지 않았다.
>
> 30.9절: Secure by Design 8장 §8.6 "Validating configuration"(§8.6.1 Causes for configuration-related security flaws, §8.6.2 Automated tests as your safety net, §8.6.3 Knowing your defaults and verifying them)을 근거로 한다. 설정 결함의 세 원인(의도하지 않은 변경·의도한 변경의 부작용·오해한 설정)과 각각의 세부(오타·bad merge·빠진 테스트, 과거 감사 설정을 끄는 부작용, 정수·매직 스트링·부정문이라는 모호성 징후), 설정 핫스팟 개념과 표 30-2(SBD 표 8.5), "설정 자체가 아니라 동작을 테스트한다"는 원칙, 기본값 검증과 HTTP 메서드 제한 테스트(`TRACE`와 XST, 405/501), 코드 예제는 원서 기준이며 엔드포인트만 온라인 서점 카탈로그로 옮겼다.
>
> 30.10절: Black Hat GraphQL 6장 "Information Disclosure" 전체를 근거로 한다. GraphQL 오류의 `message`·`location`·`path`·`extensions` 필드 구조, `createUser` 중복 사용자명 시 SQLite3 `IntegrityError`와 SQL 문 전체 노출, `extensions`의 스택 트레이스와 `/graphql`·`/graphiql` 엔드포인트별 설정 차이, 필드 제안(`Cannot query field ... Did you mean ...?`)과 편집 거리 알고리즘·임계값, 다중 오타 대량 수집, 필드 스터핑(MySQL 컬럼↔GraphQL 필드 대응, `password`·`ssn`·`apiKey` 등 스터핑), `__type` 메타필드 우회와 AWS AppSync WAF 우회(2022), 비운영 환경(staging·dev), 인트로스펙션 비활성 우회, GET 기반 질의의 PII 로그 노출, InQL·Clairvoyance 도구는 원서 기준이다. DVGA·paste 예제 대신 온라인 서점의 회원(`createUser`, users 테이블)·도서 카탈로그 맥락으로 옮겼다. 집필지침에 따라 이 절은 "정보 노출" 관점에 한정했고, 정찰 관점의 도구·절차 상세(InQL·Clairvoyance 실행, 구현체 핑거프린팅)는 39.4~39.7로 미뤘다.
