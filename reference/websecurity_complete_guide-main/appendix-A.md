# 부록 A. 웹 애플리케이션 해커의 방법론

이 부록은 웹 애플리케이션 하나를 처음부터 끝까지 점검할 때 밟아야 할 작업을 **실행 가능한 체크리스트**로 정리한 것이다. 본문 22장부터 36장까지가 각 취약점의 원리와 방어를 설명했다면, 이 부록은 그 지식을 **실제 점검 절차**로 압축한다. 각 항목은 "무엇을 할 것인가"를 명령형 한 문장으로 먼저 말하고, 필요하면 방법과 도구를 덧붙인 뒤, 그 항목의 배경이 되는 본문 장절을 `(→ N.M)`으로 지목한다. 배경 이론이 필요하면 참조된 절로 돌아가고, 손을 움직여야 할 때는 이 부록으로 돌아온다.

이 방법론은 순서대로 배열되어 있지만, 그 순서에 지나치게 얽매일 필요는 없다. 한 단계에서 얻은 정보가 앞 단계로 되돌아가 더 정밀한 공격을 가능하게 하는 일이 잦다. 예를 들어 접근 제어 결함으로 전체 사용자 목록을 얻으면, 그것이 곧 인증 함수에 대한 더 효과적인 비밀번호 추측 공격의 재료가 된다. 한 영역에서 발견한 핵심 취약점이 다른 영역의 작업을 통째로 건너뛰게 해 주기도 한다. 파일 노출 취약점 하나가 블랙박스 점검을 소스 코드 리뷰로 바꿔 놓는 식이다. **이 목록은 누락을 막는 장치이지, 창의성을 대신하는 장치가 아니다.** 웹 애플리케이션을 상대로 한 가장 인상적인 공격은 언제나 이 목록 너머를 생각하는 데서 나온다.

> **이 체크리스트가 서 있는 시점**
>
> 이 방법론은 원서 『The Web Application Hacker's Handbook』 2판(2011)의 21장을 뼈대로 삼는다. 본문에서 언급하는 구체적 도구 — Burp Suite, WebScarab, Nikto, Httprint, Nessus, Paros, Absinthe, COMRaider, THC-SSLCheck 등 — 은 모두 2011년 기준의 도구다. 그 이후 등장한 기법과 도구, 그리고 이 책의 5권 원서 범위를 넘어서는 최신 주제(HTTP/2·3 특유의 스머글링, 최신 CSP·SameSite 정책, 현대 JWT·OAuth 공격 등)는 이 부록에 담지 않는다. 도구 이름은 그 자리에서 해야 할 **작업의 성격**을 가리키는 이름표로 읽으면 된다. 인터셉팅 프록시, 능동·수동 스파이더, 퍼저, 통계적 무작위성 검정기 같은 역할은 도구가 바뀌어도 그대로 남는다. 실제 점검에서는 각자 손에 익은 최신 도구로 같은 역할을 수행하면 된다.

이 부록은 다음 순서로 진행한다. 먼저 모든 작업에 공통으로 적용되는 일반 지침(A.1)을 둔다. 그다음 **정찰과 분석**(A.2, A.3), **클라이언트 측 통제**(A.4), **인증·세션·접근 제어**(A.5~A.7), **입력 기반 취약점**(A.8, A.9), **로직 결함**(A.10), **호스팅·서버 인프라**(A.11, A.12), 그리고 **기타 점검 항목**(A.13)으로 이어진다. 컨설팅 의뢰의 일부로 이 방법론을 수행한다면, 시작 전에 반드시 대상 호스트명·URL·기능의 범위와 허용된 점검 유형을 서면으로 합의하고, 블랙박스 대상에 대한 침투 테스트에 내재된 위험을 소유자에게 알린 뒤, 중요한 데이터를 백업하도록 권고한다.

## A.1 일반 지침

세부 작업에 들어가기 전에, 모든 영역과 기법에 두루 적용되는 고려 사항을 정리한다.

### A.1.1 특수 문자를 URL 인코딩하라

**요청 데이터를 조작할 때, HTTP 요청의 각 부분에서 특수한 의미를 갖는 문자는 의도대로 해석되도록 URL 인코딩하라.** 리터럴로 넣고 싶은 문자를 인코딩하지 않으면 요청의 구조 자체가 바뀐다 (→ 7.4).

- `&` — URL 쿼리 문자열과 메시지 본문에서 파라미터를 구분한다. 리터럴은 `%26`.
- `=` — 파라미터의 이름과 값을 구분한다. 리터럴은 `%3d`.
- `?` — 쿼리 문자열의 시작을 표시한다. 리터럴은 `%3f`.
- 공백 — 요청 첫 줄에서 URL의 끝을, Cookie 헤더에서 쿠키 값의 끝을 표시한다. 리터럴은 `%20` 또는 `+`.
- `+` — 인코딩된 공백을 뜻한다. 리터럴 `+`는 `%2b`.
- `;` — Cookie 헤더에서 개별 쿠키를 구분한다. 리터럴은 `%3b`.
- `#` — URL의 프래그먼트 식별자를 표시하며, 브라우저에 입력하면 서버로 전송되는 URL을 그 지점에서 잘라 버린다. 리터럴은 `%23`.
- `%` — URL 인코딩 스킴의 접두사다. 리터럴 `%`는 `%25`.
- 널 바이트·개행 등 비출력 문자는 ASCII 코드로 인코딩한다. 널은 `%00`, 개행은 `%0a`.

### A.1.2 브라우저의 이중 인코딩에 주의하라

**폼에 URL 인코딩된 데이터를 직접 입력하면 브라우저가 인코딩을 한 겹 더 씌운다는 점에 유의하라.** 폼에 `%00`을 넣으면 서버에는 `%2500`이 도달할 수 있다. 이런 이유로, 최종적으로 전송되는 요청은 항상 인터셉팅 프록시에서 확인하는 것이 안전하다 (→ 7.7, 7.8).

### A.1.3 거짓 양성을 걸러라

**특정 조작 입력이 취약점과 연관된 동작(예: 특정 오류 메시지)을 유발하면, 무해한 입력을 같은 파라미터에 넣어도 같은 동작이 나타나는지 반드시 재확인하라.** 무해한 입력에도 같은 결과가 나온다면, 그 발견은 거짓 양성일 가능성이 높다. 어떤 취약점은 트리거 여부와 무관하게 응답 안에 그 시그니처를 항상 포함하기도 한다.

### A.1.4 누적된 상태를 제거하라

**모호한 이상 동작의 정확한 원인을 분리할 때는, 이전 요청들이 애플리케이션에 남긴 누적 상태를 걷어내라.** 새 브라우저 프로세스로 새 세션을 시작해 무해한 요청만으로 해당 위치까지 이동한 뒤 조작 입력을 다시 보낸다. 쿠키와 캐싱 관련 부분을 조정하거나, Burp Repeater 같은 도구로 요청 하나를 고립시켜 원하는 만큼 재발행하면 같은 효과를 얻는다 (→ 23.1).

### A.1.5 로드 밸런싱 환경을 감안하라

**연속된 요청이 서로 다른 백엔드 서버로 분산될 수 있음을 감안하라.** 서버마다 설정에 작은 차이가 있어 결과가 흔들릴 수 있고, 어떤 공격은 요청을 처리한 특정 서버의 상태만 바꾼다(예: 웹 루트에 새 파일 생성). 특정 행위의 효과를 분리하려면 동일한 요청을 연달아 여러 번 보내며 관련 서버가 처리할 때까지 각 결과를 확인해야 할 수 있다 (→ 15.10).

## A.2 애플리케이션 콘텐츠 매핑

목표는 애플리케이션이 노출하는 모든 콘텐츠와 기능을 빠짐없이 목록화하는 것이다 (→ 25.1~25.4).

### A.2.1 가시적 콘텐츠 탐색

1. 브라우저를 통합 프록시·스파이더 도구를 거치도록 설정한다. Burp와 WebScarab은 프록시를 지나는 콘텐츠를 파싱해 수동적으로(passive) 사이트를 스파이더링한다 (→ 25.8).
2. 애플리케이션 전체를 정상적인 방식으로 탐색한다. 모든 링크와 URL을 방문하고, 모든 폼을 제출하고, 다단계 기능은 끝까지 진행한다. JavaScript와 쿠키를 각각 켠 상태와 끈 상태로 탐색해 서로 다른 코드 경로에 도달하는지 확인한다.
3. 인증이 있고 계정을 만들 수 있다면 로그인해 보호된 기능에 접근한다.
4. 탐색하는 동안 프록시를 지나는 요청·응답을 관찰해, 어떤 데이터가 제출되고 클라이언트가 서버 동작을 어떻게 제어하는지 파악한다.
5. 수동 스파이더링이 만든 사이트맵을 검토해 브라우저로 밟지 않은 콘텐츠를 찾는다. 각 항목이 어디서 발견됐는지(Burp Spider의 Linked From) 확인하고, 브라우저로 접근해 스파이더가 응답을 다시 파싱하도록 한다. 새 콘텐츠가 더 나오지 않을 때까지 재귀적으로 반복한다.
6. 수동 탐색이 끝나면 발견한 URL을 시드 삼아 능동적으로(active) 크롤링한다. 그 전에 애플리케이션 세션을 깨뜨리거나 위험한 URL을 식별해 스파이더 범위에서 제외한다.

### A.2.2 공개 리소스 참조

1. 검색 엔진과 아카이브(Wayback Machine 등)를 이용해 대상 애플리케이션에 대해 색인·저장된 콘텐츠를 확인한다 (→ 25.2, 16.11).
2. 고급 검색을 활용한다. Google의 `site:`로 대상 사이트의 콘텐츠를, `link:`로 대상을 링크한 사이트를 찾는다. 라이브 애플리케이션에 더는 없는 콘텐츠는 검색 엔진 캐시로 열람할 수 있고, 여기에 아직 제거되지 않은 추가 리소스로의 링크가 남아 있을 수 있다.
3. 애플리케이션에서 발견한 이름·이메일 주소로 검색한다. HTML 주석처럼 화면에 렌더링되지 않는 항목도 포함하고, 웹·뉴스·그룹 검색으로 관련 기술 정보가 포럼에 게시됐는지 살핀다.
4. 공개된 WSDL 파일을 검토해 애플리케이션이 쓰는 함수명과 파라미터 값 목록을 뽑는다.

### A.2.3 숨겨진 콘텐츠 발견

1. 존재하지 않는 항목에 대한 애플리케이션의 응답 방식을 확인한다. 유효·무효 리소스를 수동으로 요청해 응답을 비교하고, 항목이 없을 때를 식별하는 쉬운 기준을 세운다 (→ 25.3).
2. 흔한 파일·디렉터리 이름과 확장자 목록을 확보한다. 실제 관찰된 항목과 그로부터 추론한 항목을 목록에 더한다. 개발자의 명명 규칙을 이해한다. `AddDocument.jsp`와 `ViewDocument.jsp`가 있다면 `EditDocument.jsp`, `RemoveDocument.jsp`도 있을 수 있다.
3. 모든 클라이언트 측 코드를 검토해 숨은 서버 콘텐츠의 단서(HTML 주석, 비활성 폼 요소)를 찾는다.
4. 자동화 기법으로 디렉터리·파일명·확장자 목록에 기반한 대량 요청을 보내고, 서버 응답으로 어떤 항목이 존재하고 접근 가능한지 확인한다 (→ B.2).
5. 새로 열거한 콘텐츠와 패턴을 재귀적으로 다시 스파이더링과 자동 발견의 기반으로 삼는다.

### A.2.4 기본 콘텐츠 발견

1. 웹 서버를 상대로 Nikto를 실행해 기본·잘 알려진 콘텐츠를 탐지한다. `-root`로 검사할 디렉터리를, `-404`로 커스텀 404 페이지를 식별할 문자열을 지정해 효과를 높인다 (→ 12.6).
2. 흥미로워 보이는 발견은 수동으로 검증해 거짓 양성을 제거한다.
3. Host 헤더에 IP 주소를 넣어 루트 디렉터리를 요청하고, 다른 콘텐츠가 반환되는지 확인한다. 그렇다면 서버 이름뿐 아니라 IP 주소를 대상으로도 Nikto를 실행한다 (→ 12.9).
4. 다양한 User-Agent 헤더를 지정해 루트 디렉터리를 요청한다.

### A.2.5 식별자 지정 기능 열거

1. 요청 파라미터로 함수 식별자를 전달해 특정 기능에 접근하는 사례를 식별한다(예: `/admin.jsp?action=editUser`, `/main.php?func=A21`) (→ 25.4).
2. A.2.3의 콘텐츠 발견 기법을 이 함수 접근 메커니즘에 적용한다. 무효 함수를 지정했을 때의 동작을 먼저 확인해 유효 함수를 식별하는 기준을 세우고, 흔한 함수명 목록이나 관찰된 식별자의 구문 범위를 순회하며 자동으로 열거한다.
3. 가능하면 URL이 아니라 기능 경로에 기반한 콘텐츠 지도를 작성해, 열거한 기능과 그 논리적 경로·의존 관계를 표시한다.

### A.2.6 디버그 파라미터 테스트

1. 숨은 디버그 파라미터(예: `debug=true`)가 구현됐을 법한 페이지·기능을 고른다. 로그인·검색·파일 업로드/다운로드 같은 핵심 기능에 가장 흔하다 (→ 25.4).
2. 흔한 디버그 파라미터 이름(`debug`, `test`, `hide`, `source`)과 값(`true`, `yes`, `on`, `1`)의 목록으로 모든 조합을 만들어 각 대상 기능에 제출한다. POST 요청은 URL 쿼리 문자열과 본문 양쪽에 넣는다. Burp Intruder의 cluster bomb 공격 유형으로 두 페이로드 목록의 모든 조합을 만들 수 있다 (→ B.4).
3. 추가한 파라미터가 처리에 영향을 준 이상 징후가 응답에 있는지 검토한다.

## A.3 애플리케이션 분석

콘텐츠를 목록화했다면, 이제 애플리케이션이 무엇을 하고 어떤 기술로 구현됐는지 분석해 공격 표면 지도를 완성한다 (→ 25.5~25.7).

### A.3.1 기능 식별

1. 애플리케이션이 만들어진 핵심 기능과, 각 기능이 정상적으로 쓰일 때 수행하도록 설계된 동작을 식별한다 (→ 25.5).
2. 인증·세션 관리·접근 제어를 다루는 핵심 보안 메커니즘과 그것들을 뒷받침하는 기능(사용자 등록, 계정 복구)이 어떻게 작동하는지 파악한다.
3. 리다이렉트, 외부 링크, 오류 메시지, 관리·로깅 기능 같은 주변부 동작을 식별한다.
4. 다른 곳과 GUI 외양·파라미터 명명·내비게이션이 다른 기능을 골라내 심층 점검 대상으로 표시한다.

### A.3.2 데이터 진입점 식별

1. 사용자 입력이 애플리케이션 처리로 들어가는 모든 진입점을 식별한다. URL, 쿼리 문자열 파라미터, POST 데이터, 쿠키, 그리고 애플리케이션이 처리하는 그 밖의 HTTP 헤더를 포함한다 (→ 25.5, 8.6).
2. 비표준 쿼리 문자열 형식 같은 커스텀 데이터 전송·인코딩 메커니즘을 조사한다. 제출 데이터가 파라미터 이름·값을 캡슐화하는지, 아니면 다른 표현 방식을 쓰는지 이해한다.
3. 사용자 제어 데이터나 제3자 데이터가 들어오는 대역 외(out-of-band) 채널을 식별한다. SMTP로 받은 메시지를 렌더링하는 웹메일 애플리케이션이 그 예다 (→ A.9).

### A.3.3 사용 기술 식별과 서버 핑거프린팅

1. 클라이언트 측에 쓰인 기술(폼, 스크립트, 쿠키, Java 애플릿, ActiveX 컨트롤, Flash 객체)을 각각 식별한다 (→ 25.6).
2. 가능한 한 서버 측 기술을 파악한다. 스크립트 언어, 애플리케이션 플랫폼, 데이터베이스·이메일 등 백엔드 컴포넌트와의 상호작용을 포함한다.
3. 응답의 HTTP `Server` 헤더를 확인하고, 커스텀 HTTP 헤더나 HTML 소스 주석에 담긴 소프트웨어 식별자도 확인한다. 영역마다 다른 백엔드가 처리하면 서로 다른 배너가 나올 수 있다 (→ 8.6).
4. Httprint 같은 도구로 웹 서버를 핑거프린팅한다.
5. 콘텐츠 매핑 결과에서 흥미로운 확장자·디렉터리·URL 조각을 식별하고, 세션 토큰과 쿠키 이름을 검토해 관련 기술을 검색한다.
6. 제3자 코드 컴포넌트에 속할 법한 스크립트명·파라미터를 `inurl:` 한정자로 검색해 같은 컴포넌트를 쓰는 다른 애플리케이션을 찾고, 비침습적으로 검토한다.

### A.3.4 공격 표면 지도 만들기

1. 클라이언트에서 보이는 동작을 서버가 내부적으로 어떤 구조·메커니즘으로 구현하는지 추정한다. 고객 주문 조회 기능이라면 데이터베이스와 상호작용할 가능성이 높다 (→ 25.7).
2. 각 기능에 대해 흔히 연관되는 취약점 유형을 식별한다. 파일 업로드는 경로 순회, 사용자 간 메시징은 XSS, 문의 기능은 SMTP 인젝션에 취약하기 쉽다.
3. 공격 계획을 세운다. 가장 흥미로운 기능과 가장 심각한 잠재 취약점에 우선순위를 두고, 이 계획으로 나머지 영역에 들일 시간과 노력을 배분한다.

## A.4 클라이언트 사이드 통제 테스트

클라이언트를 신뢰하는 모든 지점을 찾아, 서버가 클라이언트 측 통제에 의존하는지 검증한다 (→ 26장).

### A.4.1 클라이언트를 통한 데이터 전송 테스트

1. 히든 폼 필드, 쿠키, URL 파라미터가 클라이언트를 통해 데이터를 전달하는 데 쓰이는 모든 사례를 찾는다 (→ 26.1).
2. 항목의 이름·값과 등장 맥락에 근거해 그것이 애플리케이션 로직에서 하는 역할을 추정한다.
3. 항목의 값을 역할에 맞게 변형해, 애플리케이션이 임의 값을 처리하는지, 그리고 그것으로 로직을 교란하거나 보안 통제를 전복할 수 있는지 판단한다 (→ 26.7).
4. 불투명(opaque) 데이터가 클라이언트를 통해 전달되면 여러 방식으로 공격한다. 난독화됐다면 알고리즘을 해독해 임의 데이터를 넣고, 안전하게 암호화됐더라도 다른 맥락에서 재생(replay)해 로직을 교란한다.
5. ASP.NET ViewState가 쓰이면 변조 가능 여부와 민감 정보 포함 여부를 검증한다 (→ 26.2).
   1. Burp Suite의 ViewState 분석기로 `EnableViewStateMac` 활성화 여부(내용 변조 가능 여부)를 확인한다.
   2. 디코딩한 ViewState에서 민감 데이터를 식별한다.
   3. 디코딩한 파라미터 값 하나를 변형해 재인코딩·제출한다. 변형 값이 수용되면 ViewState를 임의 데이터 입력 채널로 간주하고, 다른 요청 파라미터와 똑같이 점검한다.

### A.4.2 클라이언트 측 입력 통제 테스트

1. 길이 제한, JavaScript 검사 같은 클라이언트 측 통제가 제출 전 입력을 검증하는 사례를 식별한다. 이런 통제는 임의 요청을 서버로 보내면 쉽게 우회된다 (→ 26.3).
2. 영향받는 각 입력 필드에 대해, 클라이언트 측에서 차단됐을 입력을 제출해 서버에서도 같은 검증이 이뤄지는지 확인한다.
3. 클라이언트 측 검증 우회 자체는 반드시 취약점은 아니다. 그러나 어떤 검증이 이뤄지는지 면밀히 검토하고, 애플리케이션이 잘못된 입력으로부터 자신을 보호하는 데 클라이언트 측 통제에 의존하는지, 그런 입력으로 익스플로잇 가능한 조건이 생기는지 확인한다.
4. 각 HTML 폼에서 비활성 요소(회색 처리된 제출 버튼 등)를 찾는다. 발견하면 다른 파라미터와 함께 서버로 제출해 처리에 영향을 주는지 본다. Burp Proxy의 HTML 수정 규칙으로 비활성 필드를 자동 활성화할 수 있다.

### A.4.3 브라우저 확장 컴포넌트 테스트

1. **클라이언트 동작 이해** — 검토 대상 클라이언트 기술에 로컬 인터셉팅 프록시를 설정해 모든 트래픽을 관찰한다. 데이터가 직렬화됐다면 역직렬화 도구를 쓴다. 클라이언트의 기능을 하나씩 밟으며 민감·강력한 함수를 파악한다 (→ 26.4).
2. **클라이언트 디컴파일** — `.class`/`.jar`(Java), `.swf`(Flash), `.xap`(Silverlight) 요청이나 HTML의 `applet` 태그로 애플릿을 식별한다. 바이트코드를 내려받아 적절한 도구(Java는 Jad, Flash는 SWFScan·Flasm/Flare, Silverlight는 .NET Reflector)로 디컴파일하고, 불투명 데이터를 반환하는 메서드 구현부터 소스를 검토한다. 임의 입력을 난독화하는 공개 메서드가 없으면, 소스를 수정해 검증을 무력화한 뒤 벤더 도구로 재컴파일한다 (→ 26.5).
3. **디버거 부착** — 통째로 디컴파일하기 어려운 큰 클라이언트는 런타임 디버거를 프로세스에 붙이는 편이 빠르다(Java는 JavaSnoop, Silverlight는 Silverlight Spy). 보안 로직을 좌우하는 핵심 함수·값에 중단점을 걸고, 호출 시 인자나 반환값을 수정해 우회를 달성한다.
4. **ActiveX 컨트롤 테스트** — `.cab` 요청이나 `object` 태그로 컨트롤을 식별한다. COMRaider로 내보낸 메서드를 열거해 검증을 무력화할 수 있는지 시험하고, `LaunchExe`처럼 위험해 보이는 이름의 메서드를 찾는다. Filemon·Regmon으로 컨트롤이 수집하는 정보를 관찰하고, COMRaider로 기초적인 퍼즈 테스트를 수행해 버퍼 오버플로 같은 결함을 찾는다 (→ 26.6, 31.4).

## A.5 인증 메커니즘 테스트

목표는 인증을 우회하거나, 다른 사용자로 — 되도록 관리자 권한 사용자로 — 인증하는 것이다 (→ 22장).

### A.5.1 메커니즘 이해

1. 쓰이는 인증 기술(폼, 인증서, 다중 인증 등)을 확인한다 (→ 22.1).
2. 인증 관련 기능(로그인, 등록, 계정 복구 등)을 모두 찾는다.
3. 자동 자가 등록이 없다면, 여러 사용자 계정을 확보할 다른 수단이 있는지 판단한다.

### A.5.2 비밀번호 품질 테스트

1. 사용자 비밀번호에 강제되는 최소 품질 규칙에 대한 기술이 있는지 검토한다 (→ 22.2).
2. 자가 등록이나 비밀번호 변경 기능으로 여러 약한 비밀번호를 설정해 실제 규칙을 파악한다. 짧은 것, 알파벳만, 단일 대소문자, 사전 단어, 현재 사용자명을 시도한다.
3. 불완전한 자격증명 검증을 테스트한다. 강하고 복잡한 비밀번호를 설정한 뒤, 마지막 글자 제거·대소문자 변경·특수문자 제거 등 변형으로 로그인을 시도한다. 하나라도 성공하면 어떤 검증이 실제로 이뤄지는지 체계적으로 규명한다.
4. 파악한 최소 품질 규칙과 검증 범위에 근거해, 비밀번호 추측 공격이 다뤄야 할 값의 범위를 산정한다. 표준 복잡도 요건을 적용받지 않았을 내장 계정을 찾는다.

### A.5.3 사용자명 열거 테스트

1. 사용자명이 제출되는 모든 위치(화면 입력 필드, 히든 필드, 쿠키)를 식별한다. 주 로그인, 자가 등록, 비밀번호 변경, 로그아웃, 계정 복구가 흔한 위치다 (→ 22.2).
2. 각 위치에서 유효·무효 사용자명을 담은 두 요청을 보내고, 서버 응답의 모든 세부(HTTP 상태 코드, 리다이렉트, 화면 정보, HTML 소스에 숨은 차이, 응답 시간)를 비교한다. 같은 오류 메시지의 사소한 오탈자 차이처럼 미묘한 경우도 있다.
3. 차이가 관찰되면 다른 값 쌍으로 반복해, 자동 열거의 근거가 될 체계적 차이가 존재함을 확인한다.
4. 유효 사용자명 목록을 만들 수 있는 다른 정보 누출원(로깅 기능, 등록 사용자 목록, 소스 주석의 이름·이메일)을 점검한다.
5. 사용자명을 받는 보조 인증(특히 사용자명 지정을 허용하는 등록 페이지)이 열거에 쓰일 수 있는지 확인한다.

### A.5.4 비밀번호 추측 저항성 테스트

1. 자격증명이 제출되는 모든 위치를 식별한다. 주 로그인과 (임의 사용자명 지정이 가능한 경우의) 비밀번호 변경이 대표적이다 (→ 22.2).
2. 통제하는 계정으로, 유효 사용자명에 무효 자격증명을 담은 요청을 여러 번 보낸다. 약 10회 실패 뒤에도 계정 잠금 메시지가 없으면 유효 자격증명을 보내 성공하는지 본다. 성공하면 잠금 정책이 없을 가능성이 높다.
3. 통제하는 계정이 없으면 유효 사용자명을 열거·추측해 무효 요청을 여러 번 보내며 잠금 메시지를 관찰한다. 이 테스트가 타인의 계정을 정지·비활성화할 수 있음에 유의한다.

### A.5.5 계정 복구 기능 테스트

1. 자격증명을 잊은 사용자가 계정을 되찾는 기능이 있는지 식별한다. 주 로그인 근처의 "비밀번호 찾기" 링크가 흔한 표지다 (→ 22.4, 22.8).
2. 통제하는 계정으로 복구 과정을 끝까지 밟아 작동 방식을 파악한다.
3. 비밀 질문 같은 챌린지를 쓰고 사용자가 직접 설정·선택한다면, 열거·추측한 사용자명 목록으로 챌린지를 수집해 쉽게 추측 가능한 것을 찾는다. 비밀번호 힌트도 같은 방식으로 수집·검토한다.
4. 복구 챌린지에 대해 주 로그인에서 한 것과 같은 자동 추측 취약성 테스트를 수행한다.
5. 복구가 이메일 발송을 수반하면, 발송 주소를 제어할 수 있는지 판단한다. 메시지에 고유 복구 URL이 담기면 여러 개를 확보해 예측 가능한 패턴이 있는지 분석한다(A.6.3의 방법 적용).

### A.5.6 로그인 상태 유지 기능 테스트

1. "로그인 상태 유지(Remember Me)" 기능이 있으면 활성화해 효과를 검토한다. 이후 자격증명 없이 로그인되게 한다면 면밀히 점검한다 (→ 22.4).
2. 이 기능으로 설정되는 지속 쿠키를 자세히 조사한다. 사용자를 명시하거나 예측 가능한 식별자를 담은 데이터를 찾는다.
3. 데이터가 강하게 인코딩·난독화된 듯해도, 매우 유사한 사용자명·비밀번호를 기억시킨 결과를 비교해 원본을 역설계할 여지를 찾는다(A.6.2의 방법 적용).
4. 결과에 따라 쿠키 내용을 조작해 다른 사용자로 가장한다.

### A.5.7 사용자 가장 기능 테스트

1. 한 사용자가 다른 사용자를 가장하도록 허용하는 기능이 있으면, 인가 없이 임의 사용자를 가장할 취약점을 면밀히 점검한다 (→ 22.4).
2. 가장 대상을 결정하는 사용자 제공 데이터를 찾아, 이를 조작해 다른 사용자 — 특히 권한 상승으로 이어지는 관리자 — 를 가장한다.
3. 자동 비밀번호 추측 중, 유효 비밀번호가 둘 이상인 계정이나 같은 비밀번호를 쓰는 여러 계정을 찾는다. 관리자가 임의 사용자로 접근하는 백도어 비밀번호의 존재를 시사할 수 있다.

### A.5.8 사용자명 유일성 테스트

1. 원하는 사용자명을 지정하는 자가 등록이 있으면, 같은 사용자명을 다른 비밀번호로 두 번 등록해 본다 (→ 22.5).
2. 두 번째 등록이 차단되면 이 동작으로 등록 사용자명을 열거할 수 있다.
3. 두 계정 모두 등록되면 사용자명·비밀번호 충돌 시 동작을 조사한다. 한 계정의 비밀번호를 다른 계정과 같게 바꿔 보고, 동일 사용자명·비밀번호로 두 계정을 등록해 본다.
4. 충돌 시 경고·오류가 나면, 열거·추측한 사용자명을 대상으로 다른 비밀번호로 계정 생성을 시도해 자동 추측 공격을 수행한다. 특정 비밀번호가 거부되면 그 계정의 기존 비밀번호를 찾은 것이다.

### A.5.9 자동 생성 자격증명의 예측 가능성 테스트

1. 사용자명·비밀번호를 자동 생성하면 여러 값을 빠르게 확보해 탐지 가능한 순서·패턴을 식별한다 (→ 22.5).
2. 사용자명이 예측 가능하게 생성되면 역으로 추정해 유효 사용자명 목록을 얻는다.
3. 비밀번호가 예측 가능하게 생성되면 패턴을 외삽해 다른 사용자에게 발급된 비밀번호 목록을 얻고, 사용자명 목록과 결합해 추측 공격을 수행한다.

### A.5.10 자격증명의 안전하지 않은 전송 점검

1. 자격증명을 전송하는 모든 인증 관련 기능(주 로그인, 등록, 비밀번호 변경, 프로필 조회·갱신)을 프록시로 양방향 관찰한다 (→ 22.3).
2. 자격증명이 어느 방향으로든 전송되는 모든 경우를 식별한다. 프록시 인터셉트 규칙으로 특정 문자열이 담긴 메시지를 표시한다.
3. 자격증명이 URL 쿼리 문자열로 전송되면, 브라우저 히스토리·화면·서버 로그·Referer 헤더로 노출될 수 있다.
4. 자격증명이 쿠키에 저장되면 XSS나 로컬 프라이버시 공격으로 노출될 수 있다.
5. 자격증명이 서버에서 클라이언트로 전송되면 세션 관리·접근 제어 취약점이나 XSS로 탈취될 수 있다.
6. 자격증명이 비암호화 커넥션으로 전송되면 도청자에게 가로채인다 (→ 19.10).
7. 자격증명은 HTTPS로 제출되지만 로그인 폼 자체가 HTTP로 로드되면, 중간자 공격으로 자격증명이 탈취될 수 있다 (→ 19.7).

### A.5.11 자격증명의 안전하지 않은 배포 점검

1. 계정이 대역 외 채널로 생성되거나 자가 등록이 초기 자격증명을 모두 결정하지 않으면, 자격증명이 신규 사용자에게 배포되는 방식(이메일·우편 등)을 파악한다 (→ 22.3, 22.8).
2. 계정 활성화 URL이 대역 외로 배포되면, 여러 계정을 연달아 등록해 URL의 순서를 식별한다. 패턴을 찾으면 최근·향후 사용자의 URL을 예측해 계정 탈취를 시도한다.
3. 단일 활성화 URL을 여러 번 재사용해 본다. 불가하면 대상 계정을 잠근 뒤 URL이 여전히 동작하는지, 활성 계정에 새 비밀번호를 설정할 수 있는지 확인한다.

### A.5.12 안전하지 않은 저장 테스트

1. 해시된 비밀번호에 접근하면 같은 해시 값을 공유하는 계정을 찾고, 가장 흔한 해시 값에 대해 흔한 비밀번호로 로그인을 시도한다 (→ 22.3, 22.9).
2. 해당 해시 알고리즘의 오프라인 레인보 테이블로 평문 값을 복구한다.

### A.5.13 로직 결함 테스트

1. **fail-open 조건** — 자격증명을 검사하는 각 기능을 정상적으로 밟으며 모든 요청 파라미터를 기록한 뒤, 각 파라미터를 차례로 변형한다. 빈 문자열 제출, 이름/값 쌍 제거, 매우 길거나 짧은 값, 숫자↔문자열 교환, 같은 파라미터의 다중 제출을 시도한다. 기준 동작에서 예기치 않게 벗어나면 관찰을 후속 테스트에 반영하고, 여러 변형을 조합해 로직의 한계까지 밀어붙인다 (→ 22.6).
2. **다단계 메커니즘** — 자격증명을 여러 요청에 걸쳐 제출한다면 각 단계의 목적과 파라미터를 파악한 뒤, 순서를 어겨 진행하기·각 단계로 직접 진입하기·각 단계를 건너뛰기를 시도한다. 사용자명 등 한 정보가 여러 단계에서 제출되면 단계마다 다른 값(유효·무효)을 넣어, 한 단계에서 검증된 뒤 이후 단계에서 무조건 신뢰되는지 조사한다. 사용자에게서 캡처되지 않고 클라이언트를 통해 전달되는 상태 추적용 히든 파라미터를 조작한다. 무작위 챌린지가 있으면, 챌린지 지정 파라미터를 변형해 챌린지를 직접 고를 수 있는지, 또는 원하는 챌린지가 나올 때까지 반복 진행할 수 있는지 확인한다 (→ 22.6).

### A.5.14 취약점을 이용한 무단 접근

1. 식별한 인증 취약점 중 목표 달성에 활용할 수 있는 것을 골라, 다른 사용자 — 되도록 관리자 — 로 인증을 시도한다 (→ 22.10, B.2).
2. 자동 공격 전에 파악한 계정 잠금 방어를 감안한다. 사용자명 열거 시에는 임의 값 대신 흔한 비밀번호를 함께 보내 실패 시도를 낭비하지 않고, 추측 공격은 깊이 우선이 아니라 너비 우선으로 — 가장 흔한 약한 비밀번호부터 모든 사용자명에 시도 — 수행한다.
3. 비밀번호 품질 규칙과 검증 완전성을 감안해 단어 목록을 구성해 불가능·불필요한 테스트를 줄인다.

## A.6 세션 관리 메커니즘 테스트

목표는 다른 사용자의 토큰을 획득하거나 예측·위조해 그 사용자로 가장하는 것이다 (→ 23장).

### A.6.1 메커니즘 이해

1. 세션·상태 관리 메커니즘을 분석한다. 세션 토큰을 쓰는지, 다른 방법을 쓰는지 확인한다. HTTP 인증처럼 완전한 세션 메커니즘이 필요 없는 기술도 있고, 모든 상태를 암호화·난독화해 클라이언트로 전달하는 무상태(sessionless) 방식도 있다 (→ 23.1).
2. 세션 토큰을 쓴다면 사용자 재식별에 실제로 쓰이는 데이터가 정확히 무엇인지 확인한다. HTTP 쿠키, 쿼리 문자열 파라미터, 히든 필드가 후보다. 여러 조각이 함께 쓰이거나, 웹 서버 기본 쿠키처럼 토큰처럼 보여도 실제로는 쓰이지 않는 항목도 있다.
3. 세션 의존 페이지(예: "내 정보")를 찾아, 토큰으로 의심되는 항목을 하나씩 제거하며 요청해 어느 항목이 실제 토큰인지 확인한다.
4. 실제 토큰이 전체로 검증되는지, 일부 하위 요소가 무시되는지 확인한다. 토큰 값을 1바이트씩 바꿔 수용되는지 보고, 세션 유지에 쓰이지 않는 부분은 이후 분석에서 제외한다.

### A.6.2 토큰의 의미 테스트

1. 여러 사용자로 여러 시점에 로그인해 받은 토큰을 기록한다. 사용자명을 고를 수 있으면 `A`, `AA`, `AAA`, `AAAA`, `AAAB`처럼 작게 변형한 사용자명으로, 이메일 등 다른 사용자별 데이터가 제출되면 그것도 체계적으로 변형해 결과 토큰을 수집한다 (→ 23.2).
2. 받은 토큰에서 사용자명·사용자 제어 데이터와 상관관계가 있어 보이는 부분을 분석한다.
3. 인코딩·난독화 흔적을 분석한다. 사용자명 길이와 토큰 길이의 상관은 인코딩을, 같은 문자열에 대응하는 토큰 내 문자열은 XOR 난독화를, 16진 문자만의 시퀀스는 16진 인코딩을, `=`로 끝나거나 Base64 문자만 담긴 시퀀스는 Base64를 시사한다.
4. 의미 있는 데이터를 식별하면, 그것으로 다른 사용자에게 최근 발급된 토큰을 추측하는 공격이 가능한지 판단하고 자동화한다 (→ B.2).

### A.6.3 토큰의 예측 가능성 테스트

1. 새 토큰을 반환하는 요청(예: 로그인 성공)으로 다수의 토큰을 빠르게 연속 수집한다 (→ 23.2).
2. 표본에서 패턴을 식별한다. 모든 경우에 Burp Sequencer로 무작위성의 통계 검정을 수행한다. 추가로 수동 분석을 병행한다. 실제로 쓰이는 부분만 보고, 여러 디코딩을 순차 적용해 보고, 연속 값의 차이를 계산하고, 몇 분 뒤 표본을 다시 얻어 시간 의존성을 탐지한다.
3. 패턴을 찾으면 다른 IP·사용자명으로 두 번째 표본을 수집해, 같은 패턴이 재현되고 첫 표본으로 두 번째를 외삽할 수 있는지 확인한다.
4. 익스플로잇 가능한 순서·시간 의존성을 찾으면 다른 사용자의 최근 토큰을 추측하는 공격을 자동화한다. 커스텀 스크립트가 필요할 때가 많다.
5. 세션 ID가 직접 작성된 듯하면 Burp Intruder의 bit flipper로 각 비트를 차례로 바꾸며, 유효 세션을 유지하는지, 다른 사용자의 세션인지 응답 문자열로 판별한다.

### A.6.4 토큰의 안전하지 않은 전송 점검

1. 시작 URL의 미인증 콘텐츠부터 로그인 과정, 이후 전 기능까지 정상적으로 밟으며, 새 토큰이 발급되는 시점과 HTTP·HTTPS 사용 구간을 기록한다 (→ 23.3).
2. 쿠키로 토큰을 전송하면 `Secure` 플래그가 설정돼 HTTP로 전송되지 않는지 검증한다.
3. 정상 사용 중 토큰이 HTTP로 전송되는 경우가 있으면 가로채기에 취약하다.
4. 미인증 영역은 HTTP, 로그인·인증 영역은 HTTPS로 전환하는 경우, HTTPS 구간에서 새 토큰이 발급되는지, HTTP 단계 토큰이 그대로 유지되는지 검증한다. 유지되면 가로채기에 취약하다.
5. HTTPS 영역에 HTTP URL 링크가 있으면 따라가 토큰이 제출되는지, 계속 유효한지 확인한다.

### A.6.5 로그의 토큰 노출 점검

1. 매핑에서 식별한 로깅·모니터링·진단 기능을 검토해 세션 토큰이 노출되는지 확인한다. 관리자 전용이라면 저권한 사용자가 접근할 다른 취약점이 있는지 판단한다 (→ 23.3, 16.6).
2. 토큰이 URL로 전송되는 사례를 식별한다. 특정 문제를 우회하려 URL을 쓴 경우, 사용자가 외부 링크를 따라갈 때 Referer 헤더로 노출될 수 있다. 다른 사용자 페이지에 임의 외부 링크를 주입할 기능이 있는지 점검한다.
3. 다른 사용자의 유효 토큰을 수집할 방법을 찾으면, 각 토큰이 관리자 사용자의 것인지 시험할 방법을 찾는다.

### A.6.6 토큰-세션 매핑 점검

1. 같은 계정으로 (다른 브라우저·컴퓨터에서) 두 번 로그인해 두 세션이 동시에 유효한지 확인한다. 동시 세션을 지원하면 탈취한 자격증명을 탐지 없이 쓸 수 있다 (→ 23.3).
2. 같은 계정으로 여러 번 로그인·로그아웃해 매번 새 토큰이 발급되는지, 같은 토큰이 재발급되는지 확인한다. 후자라면 실제 세션 토큰이 아니라 사용자 재식별용 고정 문자열이며, 동시 로그인 방지와 세션 타임아웃 강제가 불가능하다.
3. 토큰에 구조·의미가 있으면 사용자 식별 부분을 분리해 다른 알려진 사용자를 가리키도록 변형하고, 애플리케이션이 이를 수용해 그 사용자로 가장하게 되는지 검증한다.

### A.6.7 세션 종료 테스트

1. 세션 타임아웃·로그아웃 결함은 클라이언트가 아니라 **서버의 세션·토큰 처리**에만 집중해 테스트한다 (→ 23.4).
2. 서버에서 세션 만료가 구현됐는지 확인한다. 유효 토큰을 얻고, 일정 시간 쓰지 않다가 보호 페이지를 요청한다. 정상 표시되면 토큰이 아직 유효한 것이다. 시행착오로 만료 시간을 판별한다. Burp Intruder로 요청 간 시간 간격을 늘려 자동화한다.
3. 로그아웃 기능이 서버에서 세션을 실제로 무효화하는지 테스트한다. 로그아웃 후 옛 토큰으로 보호 페이지를 요청해 여전히 유효한지 확인한다. 유효하면 로그아웃 후에도 세션 하이재킹에 취약하다.

### A.6.8 세션 고정 점검

1. 미인증 사용자에게 토큰을 발급하면, 토큰을 얻은 뒤 로그인한다. 로그인 후 새 토큰이 발급되지 않으면 세션 고정에 취약하다 (→ 23.4).
2. 미인증 사용자에게 토큰을 발급하지 않아도, 로그인으로 토큰을 얻고 로그인 페이지로 돌아가 같은 토큰으로 다른 사용자로 로그인한다. 두 번째 로그인 후에도 새 토큰이 없으면 취약하다.
3. 토큰 형식을 파악해, 유효한 형식의 가공 값으로 로그인을 시도한다. 가공 토큰으로 인증 세션이 생성되면 취약하다.
4. 로그인이 없어도 민감 정보(개인·결제 정보)를 처리·표시하면(예: "주문 확인" 페이지), 위 세 테스트를 그 페이지에 대해 수행한다.

### A.6.9 CSRF 점검

1. 세션 토큰 전송에 HTTP 쿠키만 의존하면 크로스 사이트 요청 위조에 취약할 수 있다 (→ 33.2).
2. 핵심 기능을 검토해 민감 행위를 수행하는 요청을 식별한다. 공격자가 요청의 모든 파라미터(세션 토큰·예측 불가 데이터·비밀 없이)를 미리 완전히 결정할 수 있으면 거의 확실히 취약하다.
3. 사용자 상호작용 없이 원하는 요청을 발행하는 HTML 페이지를 만든다. GET은 `<img>`의 `src`로, POST는 히든 필드를 담은 폼을 JavaScript로 자동 제출한다. 로그인한 상태의 같은 브라우저로 그 페이지를 열어 행위가 수행되는지 검증한다.
4. CSRF 방지용 추가 토큰을 쓰면 세션 토큰과 같은 방식으로 견고성을 시험하고, UI 리드레스(클릭재킹)에 취약한지도 테스트한다 (→ 33.3, 33.4).

### A.6.10 쿠키 범위 점검

1. 쿠키로 세션 토큰(또는 민감 데이터)을 전송하면 `Set-Cookie`의 `domain`·`path` 속성을 검토한다 (→ 20.8).
2. 쿠키 범위를 상위 도메인·상위 디렉터리로 명시적으로 넓히면, 그 상위에 호스팅된 다른 애플리케이션을 통한 공격에 노출된다.
3. 범위를 자기 도메인으로 설정하거나 `domain`을 지정하지 않아도, 서브도메인에 호스팅된 애플리케이션을 통한 공격에는 여전히 노출된다. 이는 쿠키 스코핑의 작동 방식의 결과이며, 보안 민감 애플리케이션의 서브도메인에 다른 애플리케이션을 두지 않는 것 외에는 피할 수 없다.
4. `/site/main`, `/site/demo`처럼 경로에 의한 분리 의존이 있으면, XSS 공격 시 전복될 수 있음을 확인한다.
5. 발급 쿠키를 받게 될 모든 도메인·경로를 식별해, 그것들로 접근 가능한 다른 애플리케이션을 통해 대상 사용자의 쿠키를 탈취할 수 있는지 확인한다.

## A.7 접근 제어 테스트

목표는 수직·수평 권한 분리가 모든 요청 지점에서 실제로 강제되는지 확인하는 것이다 (→ 24장).

### A.7.1 접근 제어 요구사항 이해

1. 핵심 기능에 근거해 수직 분리(권한 수준별 기능 차등)와 수평 분리(같은 권한 수준의 데이터 부분집합 차등)의 요구를 이해한다. 흔히 둘 다 존재한다 (→ 24.1).
2. 매핑 결과에서 권한 상승의 가장 유망한 대상이 될 기능·데이터를 식별한다.
3. 효과적인 테스트를 위해 서로 다른 수직·수평 권한의 계정을 여럿 확보한다. 수평 계정은 자가 등록으로, 수직 계정은 소유자의 협조나 취약점 익스플로잇으로 얻는다. 확보 가능한 계정 종류가 수행 가능한 테스트를 좌우한다.

### A.7.2 다중 계정으로 테스트

1. 수직 분리가 있으면 먼저 강한 계정으로 접근 가능한 모든 기능을 찾고, 저권한 계정으로 각 기능에 접근을 시도한다 (→ 24.3).
   1. Burp로 한 사용자 컨텍스트에서 전 콘텐츠를 탐색한다.
   2. 사이트맵을 검토해 대상 기능을 확인한 뒤, 로그아웃하고 다른 컨텍스트로 로그인해 "compare site maps"로 저권한 사용자에게 접근 가능한 고권한 요청을 식별한다.
2. 수평 분리가 있으면 같은 권한 수준의 두 계정으로, 한 계정으로 다른 계정의 데이터에 접근을 시도한다. 대개 요청 안의 식별자(문서 ID 등)를 다른 사용자 리소스로 교체하는 방식이다.
3. 각 권한별로 사용 가능한 리소스를 검토하고, 인가되지 않은 사용자의 세션 토큰으로 요청을 재생해 접근을 시도한다.
4. 모든 접근 제어 테스트에서, 다단계 기능은 각 단계를 개별적으로 테스트한다. 폼이 담긴 관리 페이지가 보호돼 있어도, 실제 폼 제출도 접근 제어를 받는지 확인한다.

### A.7.3 제한된 접근으로 테스트

1. 권한별·다중 계정이 없으면 많은 취약점을 찾기가 훨씬 어렵다. 익스플로잇에 필요한 URL·식별자·파라미터 이름을 모르기 때문이다 (→ 24.4).
2. 저권한 계정 매핑에서 관리 인터페이스 같은 고권한 URL을 이미 식별했을 수 있고, 적절히 보호되지 않았다면 이미 알고 있을 것이다.
3. 존재하는 컴파일 클라이언트를 모두 디컴파일해 서버 측 기능 참조를 추출한다.
4. 수평 접근 제어 대상 데이터는 대개 식별자(계정 번호·주문 참조)로 접근한다. 식별자를 빠르게 연속 생성해 다른 사용자의 식별자를 예측할 패턴을 찾는다. 생성이 불가하면 이미 가진 것만으로 추측한다.
5. 식별자를 예측할 방법을 찾으면 자동 공격으로 다른 사용자의 데이터를 수확하고, Burp Intruder의 Extract Grep으로 응답에서 정보를 추출한다 (→ B.2, B.3).

### A.7.4 안전하지 않은 접근 제어 방식 테스트

1. `edit=false`, `access=read`처럼 요청 파라미터에 기반한 안전하지 않은 접근 제어를 찾아, 역할에 맞게 변형해 로직을 교란한다 (→ 24.2).
2. Referer 헤더에 기반한 접근 제어를 테스트한다. 인가된 권한 행위에서 Referer를 누락·변형해 차단되는지 보고, 차단되면 인가되지 않은 사용자로 원본 Referer를 넣어 성공하는지 확인한다.
3. `HEAD`가 허용되면, 컨테이너 관리 접근 제어의 안전하지 않은 구현을 `HEAD` 요청으로 테스트한다 (→ 24.5, 8.3.3).

## A.8 입력 기반 취약점 테스트

많은 중요한 취약점은 예기치 않은 사용자 입력으로 유발되며 어디서든 나타날 수 있다. 모든 요청의 모든 파라미터를 공격 문자열로 퍼징하는 것이 효과적이다 (→ 27장, 28장).

### A.8.1 모든 요청 파라미터 퍼징

1. 매핑 결과에서 서버가 처리하는 파라미터를 제출하는 모든 요청을 식별한다. URL 쿼리 문자열, 본문 파라미터, 쿠키, 그리고 영향이 관찰된 Referer·User-Agent 헤더를 포함한다 (→ B.4).
2. 각 요청을 퍼저(예: Burp Intruder)에 실어 모든 파라미터 값을 페이로드 위치로 표시한다.
3. 흔한 취약점 범주를 겨냥한 공격 페이로드를 구성한다. 이상 응답으로 쉽게 탐지되고 특정 기능이 아니라 어디서든 나타나는 유형을 노린다. SQL 인젝션(`waitfor delay` 계열), XSS·헤더 인젝션, OS 명령 인젝션(`ping` 지연 계열), 경로 순회(`/etc/passwd`, `\boot.ini`), 스크립트 인젝션, 파일 인클루전(자신이 통제하는 서버 URL) 페이로드가 그 예다.
4. `?`, `;`, `&`, `+`, `=`, 공백은 URL 인코딩한다. Burp Intruder는 기본으로 인코딩하므로 이 옵션이 꺼지지 않았는지 확인한다.
5. Grep 기능으로 응답 내 흔한 오류 문자열(`error`, `exception`, `invalid`, `ODBC`, `SQL`, `SELECT` 등)과 스크립트 인젝션 성공 표지 문자열(`111111`)을 표시하고, 페이로드 자체의 반향(XSS·헤더 인젝션 표지)도 표시한다.
6. 파일 인클루전 페이로드에 지정한 호스트에 웹 서버나 netcat 리스너를 띄워, 원격 파일 인클루전 성공 시 들어오는 커넥션을 관찰한다.
7. 공격을 실행하고, 완료 후 HTTP 상태 코드·응답 길이·응답 시간·설정 표현식·페이로드 반향의 편차로 이상 응답을 식별한다. 열 머리글로 정렬하면 두드러지는 이상을 빠르게 찾는다.
8. 각 잠재 취약점에 대해 아래 해당 절(A.8.2~A.8.7)의 상세 절차로 존재를 검증하고 익스플로잇한다.
9. 대역 외 입력 채널이 있으면 그것도 유사하게 퍼징한다. 필요하면 커스텀 스크립트나 하네스를 만든다.
10. 자동 취약점 스캐너가 있으면 함께 실행해 자신의 발견과 비교 기준으로 삼는다.

### A.8.2 SQL 인젝션 테스트

1. 퍼징의 SQL 문자열이 이상 응답을 냈으면 해당 파라미터를 수동으로 조사한다 (→ 27.2~27.8).
2. 데이터베이스 오류 메시지가 반환됐으면 그 의미를 조사한다. SQL 구문·오류 레퍼런스로 플랫폼별 메시지를 해석한다 (→ 27.8).
3. 작은따옴표 하나로 오류·이상이 나면 두 개를 넣는다. 이상이 사라지면 SQL 인젝션 가능성이 높다.
4. 문자열 연결로 무해한 입력과 동등한 값을 구성한다(예: `foo`에 대해 `'||'FOO`, `'+'FOO`, `'FOO'`). 원래 무해한 입력과 같은 응답이면 취약할 수 있다.
5. 입력이 숫자면 동등한 수식(`1+1`, `3-1`)을 넣는다. 같은 응답이면, 특히 값이 동작에 체계적 영향을 주면 취약할 수 있다.
6. SQL 특유의 수식(`67-ASCII('A')` 등)으로 특정 값을 구성해 로직이 체계적으로 조작되면 거의 확실히 취약하다.
7. `waitfor` 테스트가 비정상 지연을 냈으면 DB 유형이 MS-SQL이고 취약할 가능성이 높다. `waitfor` 값을 바꿔 지연이 체계적으로 변하는지 확인한다.
8. 취약하면 목표에 맞는 공격을 선택한다. WHERE 조건 조작(`or 1=1--`로 로그인 우회), UNION으로 임의 쿼리 결합, DB 핑거프린팅, ODBC 오류 이용, 블라인드·시간 기반·대역 외 데이터 추출, 필터 우회, DB·서버로의 권한 상승을 검토한다 (→ 27.4~27.7).

### A.8.3 XSS와 응답 인젝션 테스트

1. **반향 파라미터 식별** — Payload Grep 정렬로 XSS 페이로드가 수정 없이 반향된 경우를 식별한다. 반향 위치가 응답 본문이면 XSS를, HTTP 헤더면 헤더 인젝션을, 302 응답의 Location이면 리다이렉션을 테스트한다. 같은 입력이 여러 위치에 복사될 수 있다 (→ 32.5).
2. **반사형 XSS** — 반향 위치의 주변 HTML을 검토해 `<script>` 태그 주입, 기존 스크립트로의 주입, 태그 속성 삽입 등으로 JavaScript 실행을 유도한다. 시그니처 필터 우회 기법을 참조하고, 브라우저로 실제 실행(알림 창 등)을 확정한다. POST의 XSS는 GET으로도 되는지 시험해 전달 수단을 넓힌다 (→ 32.5, 32.8).
3. **HTTP 헤더 인젝션** — 응답 헤더 반향 위치에서 URL 인코딩된 CR(`%0d`)·LF(`%0a`)가 정제 없이 응답에 나타나는지 검증한다. 실제 개행이 응답 헤더에 나타나면 취약하다. 개행이 차단·정제되면 `foo%00%0d%0abar`, `foo%250d%250abar` 등으로 필터를 시험한다 (→ 8.7, 35.1).
4. **오픈 리다이렉션** — 반향 입력이 리다이렉트 대상을 지정하면 임의 외부 사이트로의 리다이렉트가 가능한지 시험한다. 절대 URL이면 도메인을, 상대 URL이면 절대 URL로 바꿔 리다이렉트되는지 본다. 검증이 있으면 우회를 시도한다 (→ 35.3).
5. **저장형 공격** — 퍼징 후, 그 문자열을 담지 않은 요청의 응답에 공격 문자열이 나타나면 저장 지점을 식별한다. 다단계로만 저장되는 데이터는 수동으로 밟아 테스트한다. 저권한 사용자 데이터가 고권한 세션에 렌더링되는 관리 기능의 저장형 XSS는 곧바로 권한 상승으로 이어진다. 파일 업로드·다운로드가 있으면 반드시 저장형 XSS를 점검한다. 필터로 저장형 XSS가 막힌 위치는 온사이트 요청 위조 취약성을 검토한다 (→ 32.6, 33.2).

### A.8.4 OS 명령 인젝션 테스트

1. 명령 인젝션 문자열이 비정상 지연을 냈으면 OS 명령 인젝션 가능성이 높다. `-i`·`-n` 값을 바꿔 응답 시간이 체계적으로 변하는지 확인한다 (→ 28.1).
2. 성공한 주입 문자열로 더 흥미로운 명령(`ls`, `dir`)을 주입해 결과를 브라우저로 회수할 수 있는지 판단한다.
3. 직접 회수가 안 되면 대역 외 채널(TFTP·telnet·netcat 역방향 셸·mail)을 열거나, 결과를 웹 루트의 파일로 리다이렉트해 브라우저로 회수한다 (→ 28.2).
4. 주입·회수에 성공하면 권한 수준을 판별(`whoami`)하고 권한 상승·백도어·타 호스트 공격을 모색한다.
5. 문자열이 실패하면 `<`·`>`로 파일 입출력을 시도하고, 실제 실행 명령을 알면 명령행 파라미터를 주입한다.
6. 핵심 문자가 이스케이프되면 이스케이프 문자 자체를 앞에 붙이고, 공백이 차단되면 UNIX에서 `$IFS`를 쓴다.

### A.8.5 경로 순회 테스트

1. 퍼징의 경로 순회 문자열 결과에서, 비정상 오류·길이의 응답이 지정 파일 내용이나 이상 파일 연산의 증거를 담는지 검토한다 (→ 28.3).
2. 파일 읽기·쓰기를 지원하는 기능은 일반 퍼징 외에 매우 신중하게 수동 테스트한다.
3. 파일명·디렉터리로 보이는 파라미터에 임의 하위 디렉터리와 단일 순회 시퀀스를 넣는다(`file=foo/file1.txt` → `file=foo/bar/../file1.txt`). 두 경우의 동작이 같으면 취약할 수 있고, 다르면 순회 시퀀스를 차단·제거·정제하는 것이므로 인코딩 등으로 우회를 시도한다.
4. 기저 디렉터리 내 순회가 성공하면 추가 시퀀스로 상위로 올라가 알려진 OS 파일에 접근한다.
5. 확장자 검사가 있으면 널 바이트·개행과 허용 확장자를 결합해 우회한다(`/boot.ini%00.jpg`).
6. 경로가 특정 디렉터리로 시작하는지 검사하면 허용 스템 뒤에 순회 시퀀스를 붙여 우회한다(`/images/../../../../etc/passwd`).
7. 실패하면 여러 우회를 조합하며, 우선 기저 디렉터리 안에서 필터를 이해한다.
8. 임의 읽기에 성공하면 OS·애플리케이션 비밀번호 파일, 설정 파일, DB 자격증명이 담긴 인클루드 파일, 데이터 소스, 서버 실행 페이지 소스, 세션 토큰이 담긴 로그를 회수한다.
9. 임의 쓰기에 성공하면 시작 폴더 스크립트, `in.ftpd` 수정, 실행 권한 웹 디렉터리로의 스크립트 작성 같은 상승을 검토한다.

### A.8.6 스크립트 인젝션 테스트

1. 퍼징 결과에서 (테스트 문자열의 나머지 없이) `111111` 문자열만 단독으로 나타나고 Payload Grep 표시가 없는 경우를 찾는다. 스크립트 명령 주입에 취약할 가능성이 높다 (→ 28.1).
2. 스크립트 인젝션 문자열을 쓴 테스트 중 스크립트 오류 메시지를 담은 경우를 식별한다. 입력이 실행되다 오류를 낸 것이므로 미세 조정이 필요할 수 있다.
3. 취약해 보이면 플랫폼 특유 명령(`system('ping%20127.0.0.1')` 등)을 주입해 검증한다.

### A.8.7 파일 인클루전 테스트

1. 퍼징 중 대상 인프라에서 들어오는 HTTP 커넥션을 받았으면 원격 파일 인클루전(RFI)에 거의 확실히 취약하다. 단일 스레드·시간 제한으로 반복해 원인 파라미터를 특정한다 (→ 28.4).
2. 파일 인클루전 테스트에서 비정상 지연을 낸 경우를 식별한다. 애플리케이션은 취약하나 네트워크 필터로 HTTP 요청이 타임아웃됐을 수 있다.
3. RFI를 찾으면 대상 언어의 악성 스크립트를 담은 웹 서버를 띄우고, 스크립트 인젝션과 유사한 명령으로 실행을 검증한다.

## A.9 기능별 특정 입력 취약점 테스트

일부 취약점은 특정 기능에서만 나타난다. 절차에 들어가기 전에 공격 표면 평가를 다시 보고 이런 결함이 생길 만한 기능을 특정해 그곳에 집중한다 (→ 27.11~27.13, 28.9).

### A.9.1 SMTP 인젝션 테스트

1. 이메일 관련 기능의 각 요청에 대해, 자신의 이메일 주소를 넣은 SMTP 인젝션 테스트 문자열(`<메일>%0aCc:<메일>`, `%0d%0aBcc:` 계열, `%0aDATA%0a...MAIL+FROM:` 계열 등)을 각 파라미터에 차례로 제출한다. 이미 인코딩됐으므로 추가 인코딩하지 않는다 (→ 28.9).
2. 이메일 기능 관련 오류 메시지가 있으면 익스플로잇 위해 입력을 미세 조정할지 조사한다.
3. 지정한 이메일 주소로 메시지가 수신되는지 관찰한다.
4. 관련 요청을 만드는 HTML 폼을 검토한다. 서버 소프트웨어의 단서나, 직접 수정 가능한 To 주소 히든·비활성 필드가 있을 수 있다.

### A.9.2 네이티브 소프트웨어 취약점 테스트

1. **버퍼 오버플로** — 각 데이터 항목에 흔한 버퍼 크기보다 다소 긴 문자열(1100·4200·33000 등)을 하나씩 제출한다. HTTP 500·외부 네이티브 컴포넌트 실패 메시지·부분·기형 응답·TCP 커넥션의 급작스러운 종료·애플리케이션 전체 무응답·널 종료 손실을 시사하는 예기치 않은 데이터를 관찰한다 (→ 31.4).
2. **정수 취약점** — 길이 지시자 등 정수 데이터에 부호·무부호 정수 크기별 경계값(`0x7f`/`0x80`, `0xff`/`0x100`, `0xffff`/`0x10000`, `0xffffffff`/`0x0` 등)을 보낸다. 16진 표현이면 리틀·빅 엔디언 양쪽을 보낸다 (→ 31.5).
3. **포맷 스트링** — 각 파라미터에 포맷 지정자를 길게 이어붙인 문자열(`%n%n...`, `%s%s...`)을 제출한다. `%`는 `%25`로 인코딩한다. 위와 같은 이상 이벤트를 관찰한다 (→ 31.5).

### A.9.3 SOAP 인젝션 테스트

1. SOAP 메시지로 처리될 법한 각 파라미터에 잘못된 XML 닫는 태그(`</foo>`)를 제출한다. 오류가 없으면 SOAP 메시지에 삽입되지 않거나 정제되는 것이다 (→ 28.7).
2. 오류가 났으면 유효한 여닫는 태그 쌍(`<foo></foo>`)을 제출한다. 오류가 사라지면 취약할 수 있다.
3. 항목이 응답에 반향되면 `test<foo/>`와 `test<foo></foo>`를 차례로 제출한다. 하나가 다른 것으로, 또는 단순히 `test`로 반환되면 입력이 XML 메시지에 삽입되는 것이다.
4. 여러 파라미터가 SOAP 메시지에 들어갈 법하면, 한 파라미터에 여는 주석(`<!--`)을, 다른 파라미터에 닫는 주석(`-->`)을 넣고 서로 바꿔 본다. 서버 SOAP 메시지 일부를 주석 처리해 로직 변경이나 정보 노출 오류를 유발할 수 있다.

### A.9.4 LDAP 인젝션 테스트

1. 디렉터리 서비스에서 정보를 조회하는 기능에서 각 파라미터를 LDAP 쿼리 주입 대상으로 삼는다 (→ 27.13).
2. `*` 문자를 제출한다. 대량 결과가 반환되면 LDAP 쿼리임을 시사한다.
3. 닫는 괄호 여러 개(`))))))`)를 넣는다. 쿼리 구문을 무효화하므로 오류·이상이 나면 취약할 수 있다.
4. 여러 표현식(`)(cn=*`, `*))(|(cn=*`, `*))%00`)으로 반환 결과에 영향을 줄 수 있는지 본다. `cn` 속성은 모든 LDAP 구현이 지원한다.
5. 입력 끝에 쉼표로 속성(`cn`, `mail`, `givenname`, `ou`, `objectclass`, `sn` 등)을 추가해 각각 시험한다. 오류는 그 속성이 현재 맥락에서 무효임을 뜻한다.

### A.9.5 XPath 인젝션 테스트

1. `' or count(parent::*[position()=1])=0 or 'a'='b` 계열 값을 제출해 오류 없이 동작이 달라지는지 판단한다 (→ 27.12).
2. 파라미터가 숫자면 `1 or count(parent::*[position()=1])=0` 계열도 시험한다.
3. 오류 없이 차등 동작이 나면 `substring(name(parent::*[position()=1]),1,1)='a'` 형식의 조건으로 부모 노드명을 한 바이트씩 추출한다.
4. 부모 노드명을 얻으면 `substring(//부모노드명[position()=1]/child::node()[position()=1]/text(),1,1)='a'` 형식으로 XML 트리 전체를 추출한다.

### A.9.6 백엔드 요청 인젝션 테스트

1. 내부 서버명·IP가 파라미터로 지정되는 사례를 찾는다. 임의 서버·포트를 제출해 타임아웃을, `localhost`를, 마지막으로 자신의 IP를 제출해 들어오는 커넥션을 관찰한다 (→ 28.8).
2. 특정 값에 특정 페이지를 반환하는 파라미터에, 여러 구문(`%26foo%3dbar`, `%3bfoo%3dbar`, 이중 인코딩 `%252 6foo%253dbar`)으로 새 파라미터를 덧붙인다. 원본 파라미터가 그대로인 듯 동작하면 HTTP 파라미터 인젝션 가능성이 있으므로, 백엔드 로직을 바꿀 이름/값 쌍을 주입한다.

### A.9.7 XXE 인젝션 테스트

1. 사용자가 서버에 XML을 제출하면 외부 엔티티 주입이 가능할 수 있다. 응답에 반환되는 필드를 알면 외부 엔티티를 지정한다(`<!DOCTYPE foo [ <!ENTITY xxe SYSTEM "file:///windows/win.ini" > ]>` 후 `&xxe;` 참조) (→ 28.5, 28.6).
2. 반환 필드를 모르면 `http://192.168.1.1:25` 같은 외부 엔티티를 지정하고 응답 시간을 관찰한다. 현저히 길어지거나 타임아웃되면 취약할 수 있다.

## A.10 로직 결함 테스트

로직 결함은 형태가 매우 다양하고 어디에나 존재할 수 있어 스캐너가 찾지 못한다. 먼저 공격 표면을 수동 테스트가 가능한 범위로 좁힌다 (→ 29장).

### A.10.1 핵심 공격 표면 식별

1. 매핑 결과에서 다음 특징을 가진 곳을 식별한다 (→ 29.1).
   - 다단계 프로세스
   - 로그인 같은 핵심 보안 기능
   - 신뢰 경계 전환(익명 → 자가 등록 → 로그인)
   - 맥락에 따라 사용자에게 제시되는 기능
   - 거래 가격·수량에 대한 검사·조정

### A.10.2 다단계 프로세스 테스트

1. 정해진 요청 순서를 가진 다단계 프로세스에서, 요청을 예상 순서를 벗어나 제출한다. 단계 건너뛰기, 한 단계 반복 접근, 뒷 단계 후 앞 단계 접근을 시도한다 (→ 29.2).
2. 단계 접근 메커니즘(구별된 URL로의 GET·POST, 같은 URL에 다른 파라미터, 함수명·인덱스 파라미터)을 완전히 이해한다.
3. 순서 교란 외에, 한 단계에서 제출되는 파라미터를 다른 단계에서 제출한다. 상태가 갱신되면 로직 교란 가능성을 조사한다.
4. 여러 사용자가 같은 데이터를 다루는 프로세스면, 한 사용자의 파라미터를 다른 사용자로 제출해 수용·처리되는지 본다.
5. 개발자가 세운 가정과 핵심 공격 표면을 파악하고, 그 가정을 위반해 바람직하지 않은 동작을 유발할 방법을 찾는다.
6. 순서를 벗어나면 널·미초기화 변수, 부분·불일치 상태 등 이상 조건이 흔하다. 흥미로운 오류·디버그 출력으로 내부 동작을 더 이해한다.

### A.10.3 불완전한 입력 처리 테스트

1. 여러 입력을 처리해 결정을 내리는 핵심 보안 기능에서, 불완전한 입력에 대한 복원력을 테스트한다 (→ 29.1, 30.8).
2. 각 파라미터의 이름과 값을 함께 제거하고, 동작 편차와 로직을 드러내는 오류를 관찰한다.
3. 다단계의 일부면 끝까지 진행한다. 앞 단계 데이터가 세션에 저장돼 뒤에서 처리될 수 있다.

### A.10.4 신뢰 경계 테스트

1. 서로 다른 신뢰 상태 간 전환을 조사한다. 주어진 신뢰 상태의 사용자가 신원 관련 상태를 축적할 수 있는 기능(익명 사용자의 자가 등록 개인 정보 제공, 계정 복구 진행 등)을 찾는다 (→ 29.2).
2. 한 영역에서 상태를 축적한 뒤 정상적으로는 일어나지 않을 방식으로 다른 영역으로 전환해, 신뢰 경계를 부적절하게 넘는 방법을 찾는다. 계정 복구 일부를 마친 뒤 인증 전용 페이지로 전환해, 부적절한 신뢰 수준이 부여되는지 테스트한다.
3. 고권한 기능을 직·간접적으로 이용해 정보에 접근·추론할 수 있는지 판단한다.

### A.10.5 거래 로직 테스트

1. 거래 한도가 있으면 음수 값 제출의 효과를 테스트한다. 수용되면 반대 방향의 큰 거래로 한도를 우회할 수 있다 (→ 29.3, 29.4).
2. 연속 거래로 익스플로잇 가능한 상태에 이를 수 있는지 조사한다. 여러 저가 이체로 로직이 막으려던 큰 잔액을 축적하는 식이다.
3. 사용자 제어 데이터·행위에 따라 가격 등을 조정하면, 알고리즘과 조정 지점을 이해한다. 조정이 일회성인지, 이후 행위에 따라 갱신되는지 식별한다.
4. 조정이 설계자가 의도한 기준에 대응하지 않는 상태에 이르도록 동작을 조작한다 (→ 29.5).

## A.11 공유 호스팅 취약점 테스트

목표는 공유 환경의 격리 실패를 이용해 한 애플리케이션에서 다른 애플리케이션·환경으로 공격을 확장하는 것이다 (→ 15.9, 31.2).

### A.11.1 공유 인프라의 분리 테스트

1. 공유 인프라에 호스팅됐으면 고객이 콘텐츠·기능을 갱신·관리하는 접근 메커니즘을 조사한다. 원격 접근이 안전한 프로토콜과 강화된 인프라를 쓰는지, 고객이 정당하게 접근할 필요 없는 파일·데이터·리소스에 접근할 수 있는지, 대화형 셸로 임의 명령을 실행할 수 있는지 검토한다 (→ 15.9).
2. 고객이 공유 환경을 구성·커스터마이즈하는 독점 애플리케이션이 있으면, 그것을 환경·개별 애플리케이션 장악의 경로로 삼는다.
3. 한 애플리케이션에서 명령 실행·SQL 인젝션·임의 파일 접근을 달성하면, 그것으로 다른 애플리케이션으로 공격을 확장할 수 있는지 신중히 조사한다 (→ 31.2).

### A.11.2 ASP 호스팅 애플리케이션 간 분리 테스트

1. 공유·커스텀 컴포넌트가 섞인 ASP 호스팅 서비스면, 공유 컴포넌트(로깅 메커니즘, 관리 기능, DB 코드 컴포넌트)를 식별해 그것으로 공유 부분을 장악하고 다른 애플리케이션을 공격한다 (→ 15.9, 31.2).
2. 공유 환경에 공통 데이터베이스가 쓰이면, DB 스캐닝 도구로 설정·패치 수준·테이블 구조·권한을 종합 감사한다. DB 보안 모델의 결함이 애플리케이션 간 공격 확장의 경로가 될 수 있다.

## A.12 애플리케이션 서버 취약점 테스트

목표는 애플리케이션 코드가 아니라 그것을 떠받치는 서버·플랫폼의 오설정과 알려진 결함을 찾는 것이다 (→ 12.6~12.10, 31.3).

### A.12.1 기본 자격증명 테스트

1. 매핑 결과에서 접근 가능한 관리 인터페이스를 가진 웹 서버·기술을 식별한다 (→ 12.6).
2. 웹 서버를 포트 스캔해 주 애플리케이션과 다른 포트의 관리 인터페이스를 찾는다.
3. 식별한 인터페이스에 대해 제조사 문서와 기본 비밀번호 목록으로 기본 자격증명을 얻는다.
4. 기본 자격증명이 안 되면 A.5의 단계로 유효 자격증명을 추측한다.
5. 관리 인터페이스에 접근하면 그 기능으로 호스트·주 애플리케이션을 더 장악할 수 있는지 검토한다.

### A.12.2 기본 콘텐츠 테스트

1. Nikto 스캔(A.2.4) 결과에서 애플리케이션의 필수 부분이 아닌 기본 콘텐츠를 식별한다 (→ 12.6).
2. 검색 엔진과 exploit-db·osvdb 같은 자료로 알려진 기술의 기본 콘텐츠·기능을 식별한다. 가능하면 로컬 설치해 활용 가능한 기본 기능을 검토한다.
3. 기본 콘텐츠에서 서버·애플리케이션 공격에 활용할 기능·취약점을 조사한다.

### A.12.3 위험한 HTTP 메서드 테스트

1. `OPTIONS` 메서드로 서버가 가용하다고 밝히는 메서드를 나열한다. 디렉터리마다 다를 수 있다 (→ 12.7, 8.3.3).
2. 보고된 각 메서드를 수동으로 시험해 실제 사용 가능한지 확인한다.
3. WebDAV 메서드가 활성이면 WebDAV 클라이언트로 더 조사한다.

### A.12.4 프록시 기능 테스트

1. `GET`·`CONNECT` 요청으로 웹 서버를 프록시 삼아 인터넷의 다른 서버에 연결해 콘텐츠를 회수할 수 있는지 시험한다 (→ 12.8, 13.10).
2. `GET`·`CONNECT`로 호스팅 인프라 내 다른 IP·포트에 연결을 시도한다.
3. `GET`·`CONNECT`로 대상 호스트를 `127.0.0.1`로 지정해 웹 서버 자신의 흔한 포트에 연결을 시도한다.

### A.12.5 가상 호스팅 오설정 테스트

1. 루트 디렉터리에 올바른 Host 헤더, 가짜 Host 헤더, 서버 IP를 담은 Host 헤더, Host 헤더 없음(HTTP/1.0)으로 `GET`을 제출한다 (→ 12.9, 15.2).
2. 응답을 비교한다. 서버 IP를 Host로 쓸 때 디렉터리 리스팅이 나오거나 다른 기본 콘텐츠에 접근되는 일이 흔하다.
3. 다른 동작이 관찰되면 그 호스트명으로 A.2의 매핑을 반복하고, Nikto를 `-vhost` 옵션으로 실행한다.

### A.12.6 웹 서버 소프트웨어 버그 테스트

1. Nessus 등 스캐너로 웹 서버 소프트웨어의 알려진 취약점을 식별한다 (→ 12.10, 31.3).
2. Security Focus·Bugtraq·Full Disclosure 등에서 대상에 미패치됐을 최근 취약점을 찾는다.
3. 애플리케이션이 제3자 제작이면 자체 웹 서버(흔히 오픈소스)를 함께 배포하는지 조사한다. 그렇다면 그 서버의 취약점을 조사하되, 표준 배너가 수정됐을 수 있음에 유의한다.
4. 가능하면 대상 소프트웨어를 로컬 설치해 아직 공개되지 않은 새 취약점을 직접 찾는다.

### A.12.7 웹 애플리케이션 방화벽 테스트

1. 애플리케이션이 이름·값을 응답에 포함하는 위치에, 임의 파라미터 이름과 명백한 공격 페이로드를 제출한다. 차단되면 외부 방어 때문일 가능성이 높다 (→ 12.11).
2. 응답에 반환되는 변수에 다양한 퍼즈 문자열·인코딩 변형을 제출해 방어 동작을 파악하고, 애플리케이션 내부 변수에 같은 공격을 수행해 확인한다.
3. 표준 시그니처 DB에 없을 페이로드를 쓴다. `/etc/passwd`, `<script>`, `alert()`, `xss` 같은 흔한 문자열은 피한다.
4. 특정 요청이 차단되면 같은 파라미터를 다른 위치·맥락(URL의 GET, POST 본문, POST의 URL)에 제출한다. ASP.NET이면 쿠키로도 제출한다.
5. 직렬화·인코딩 같은 비표준 형식으로 입력을 제출할 수 있는 위치를 찾는다. 없으면 공격 문자열을 연결하거나 여러 변수에 걸쳐 나눈다(ASP.NET은 HPP로 같은 변수의 다중 지정을 이용).

## A.13 기타 점검 항목

앞 절에 속하지 않는 클라이언트 측·전송 계층 점검과 정보 누출 추적을 모은다 (→ 30장, 32~36장).

### A.13.1 DOM 기반 공격 점검

1. 애플리케이션에서 받은 모든 JavaScript(독립 파일과 HTML 내 스크립트)를 간략히 코드 리뷰해, 가공 URL로 DOM에 악성 데이터를 넣어 유발되는 XSS·리다이렉션 취약점을 식별한다 (→ 32.7).
2. 가공 URL로 제어 가능한 DOM 데이터에 접근하는 API(`document.location`, `document.URL`, `document.referrer`, `window.location`)의 사용을 모두 찾는다.
3. 그 데이터가 `document.write()`, `document.body.innerHTML`, `eval()`, `window.setTimeout()` 등으로 전달되면 XSS에, `document.location`, `window.open()`, `window.location.href` 등으로 전달되면 리다이렉션에 취약할 수 있다.

### A.13.2 로컬 프라이버시 취약점 점검

1. 프록시 로그에서 모든 `Set-Cookie` 지시자를 식별한다. 미래 날짜의 `expires` 속성이 있으면 지속 쿠키이며, 그 내용에서 민감 데이터를 검토한다 (→ 36.1).
2. 민감 데이터를 담은 지속 쿠키는 로컬 공격자에게 탈취될 수 있다. 암호화됐어도 재제출로 접근을 얻을 수 있다.
3. 민감 데이터가 HTTP로 접근되면 응답의 캐시 지시자를 본다. `Expires: 0`, `Cache-control: no-cache`, `Pragma: no-cache`가 (헤더나 메타 태그에) 없으면 브라우저가 캐시할 수 있다 (→ 14.9).
4. 민감 데이터가 URL 파라미터로 전송되는 사례를 식별하고, 브라우저 히스토리에 저장됐는지 검증한다.
5. 민감 데이터를 캡처하는 모든 폼의 소스에서 `autocomplete=off`가 설정됐는지 검토한다.
6. 기술별 로컬 저장소를 점검한다. Flash 로컬 객체, Silverlight 격리 저장소, HTML5 로컬 저장소 사용을 확인한다 (→ 36.2).

### A.13.3 약한 SSL 암호 점검

1. SSL을 쓰면 THC-SSLCheck 같은 도구로 지원 암호·프로토콜을 나열한다 (→ 19.11).
2. 약하거나 구식인 암호·프로토콜이 지원되면, 적절히 위치한 공격자가 다운그레이드·복호화 공격을 수행할 수 있다 (→ 19.5, 19.7).
3. 일부 서버는 약한 암호를 지원한다고 광고하나 실제 핸드셰이크는 거부해 거짓 양성을 낸다. 지정 프로토콜로 완전한 핸드셰이크를 시도해 실제 사용 가능 여부를 확인한다.

### A.13.4 동일 출처 정책 설정 점검

1. `/crossdomain.xml` 파일을 점검한다. `<allow-access-from domain="*" />`처럼 무제한 접근을 허용하면 임의 사이트의 Flash 객체가 사용자 세션에 편승해 양방향 상호작용을 할 수 있다 (→ 34.1).
2. `/clientaccesspolicy.xml` 파일을 점검한다. `<cross-domain-access>` 설정이 지나치게 관대하면 다른 사이트가 양방향 상호작용을 할 수 있다.
3. XMLHttpRequest로 다른 도메인을 지정한 Origin 헤더를 넣어 크로스 도메인 요청 처리를 테스트하고, 반환되는 `Access-Control` 헤더를 검토한다. 임의·지정 도메인의 양방향 접근 허용의 보안 함의는 Flash 정책과 같다 (→ 34.7, 34.11).

### A.13.5 정보 누출 추적

1. 모든 점검 과정에서, 오류 원인·사용 기술·내부 구조·기능에 대한 유용한 정보를 담은 오류 메시지를 관찰한다 (→ 30.1, 30.2).
2. 특이한 오류 메시지는 검색 엔진으로 조사한다. `filetype:` 등 고급 검색으로 결과를 좁힌다.
3. 검색 결과에서 오류 메시지에 대한 논의와 같은 메시지가 나타난 다른 사이트를 찾는다. 더 상세한 맥락으로 오류 조건을 이해하고, 캐시로 사라진 예시를 회수한다.
4. 코드 검색으로 특정 오류 메시지를 낼 만한 공개 코드를 찾는다. 소스에 하드코딩됐을 오류 메시지 조각을 검색한다.
5. 라이브러리·제3자 컴포넌트 이름이 담긴 스택 트레이스를 받으면 그 이름을 검색 엔진과 코드 검색 양쪽에서 찾는다 (→ 30.3).
