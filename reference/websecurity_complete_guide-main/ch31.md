# 31장. 애플리케이션 서버, 아키텍처, 그리고 네이티브 코드

> **이 장에서 다루는 것**
>
> - 계층 아키텍처를 마주한 공격자가 실제로 무엇을 어떤 순서로 시도하는가 — 15장이 배치 형태로 설명한 것을 방법론으로 다시 본다
> - 공유 호스팅·ASP 환경을 안에서부터 무너뜨리는 절차, 그리고 `phpinfo()`와 PHP safe mode 점검이 그 절차의 어디에 놓이는가
> - 프레임워크 하나의 결함이 그 위의 수많은 애플리케이션을 한꺼번에 취약하게 만드는 방식
> - 버퍼 오버플로·정수 취약점·포맷 스트링이라는 고전적 네이티브 코드 결함의 구조 — 오늘날 드물지만 패턴으로 익혀 둘 값이 있는 것
> - 인코딩·정규화 결함이 서버 소프트웨어 층위에서 되풀이되는 이유, 그리고 그것이 파싱 불일치와 같은 구조라는 사실
> - 서버 측 공격 표면을 다룬 일곱 장이 결국 하나의 문제 — 복잡도 — 였다는 정리

Part VI의 앞 여섯 장은 애플리케이션을 정면에서 공격했다. 기술을 매핑하고(25장), 클라이언트 통제를 우회하고(26장), 데이터 저장소와 백엔드 컴포넌트에 주입하고(27·28장), 로직 결함을 파고들고(29장), 실패의 순간에 새어 나오는 정보를 주웠다(30장). 이 장은 시선을 애플리케이션 코드 **바깥** — 그 코드가 얹혀 돌아가는 환경 — 으로 옮긴다. 계층으로 나뉜 아키텍처, 여러 고객이 나눠 쓰는 인프라, 애플리케이션을 떠받치는 프레임워크와 서버 소프트웨어, 그리고 드물게는 네이티브로 컴파일된 코드 자체가 이 장의 표적이다.

30장이 이 장을 예고하며 두 개의 실 끝을 남겼다. 30.1의 스택 트레이스가 드러낸 애플리케이션 서버·프레임워크와, 30.9의 설정 결함이 드러낸 공유 호스팅 환경이다. 이제 그것들이 정보 누출의 원천이 아니라 그 자체로 공격의 대상이 된다. 공격자가 개별 애플리케이션에서 찾은 제한적인 결함 하나가 — SQL 주입 한 건, 명령 실행 한 번, 파일 읽기 한 곳이 — 아키텍처의 신뢰 관계를 타고 어떻게 전체 침해로 번지는지가 이 장의 첫 두 절이다.

**이 장의 처음 두 절은 15장과 역할을 나눈다.** 15.9절과 15.10절은 공유 호스팅·ASP 환경과 계층 아키텍처를 **배치 형태(deployment topology)의 성질**로 다뤘다 — 무엇을 어디에 얹었기에 이런 문제가 생기는가로. 이 장은 같은 대상을 **공격자의 방법론**으로 다룬다 — 애플리케이션을 마주한 테스터가 무엇을 어떤 순서로 시도하는가로. 두 서술의 근거는 같은 WAHH 17장이며, 15장이 남겨 둔 HACK STEPS와 PHP `phpinfo()`·safe mode 점검 절차가 이 장의 몫이다. 배치 형태가 왜 그렇게 생겼는지는 15장을, 그것을 마주한 공격자가 무엇을 하는지는 이 장을 보면 된다.

이 장의 뒷부분은 성격이 다르다. 네이티브 코드 취약점(31.4~31.6)은 오늘날 대다수 웹 애플리케이션에서 드물다. 관리 실행 환경(managed execution environment)에서 도는 언어 — C#, Java — 는 버퍼 관리와 포인터 산술의 문제를 프로그래머에게서 걷어 갔기 때문이다. 그럼에도 이 절들을 두는 이유는 두 가지다. 하나는 하드웨어 장치나 레거시 외부 컴포넌트를 호출하는 애플리케이션에서 이 결함이 여전히 나타나기 때문이고, 다른 하나는 **이 고전 결함들이 이 책이 반복해 온 하나의 패턴 — 데이터의 길이와 경계에 관한 가정이 무너지는 것 — 의 가장 순수한 형태이기 때문이다.** 그리고 이 장은 그 모든 것을 하나의 관찰로 닫는다. 서버 측 공격 표면을 다룬 일곱 장이 겨눈 것은 결국 복잡도였다는 것이다.

## 31.1 계층 아키텍처 — 공격과 방어

15.10절이 계층 아키텍처를 배치 형태로 정리했다. 프레젠테이션·애플리케이션·데이터의 세 계층이 어떻게 나뉘고, 그 경계가 어디에 그어지며, 왜 그 경계가 강제되지 않으면 신뢰 경계가 되지 못하는지를 다뤘다. 이 절은 그 배치를 마주한 공격자의 시선으로 같은 대상을 본다. **다계층 모델을 이해하는 일이 공격자에게 왜 유용한가.** 그것은 서로 다른 보안 방어 — 접근 통제, 입력 검증 — 가 어디에 구현되어 있고, 그것들이 계층 경계에서 어떻게 무너지는지를 짚어 주기 때문이다.

WAHH는 부실하게 설계된 계층 아키텍처가 세 부류의 공격을 가능하게 한다고 분류한다. 15.10.2절이 이 세 범주를 배치의 관점에서 나열했다. 여기서는 공격자가 각 범주에서 실제로 무엇을 하는지를 본다.

**표 31-1. 계층 아키텍처 공격의 세 범주 (WAHH 17장 기준)**

| 범주 | 공격자가 노리는 것 | 전형적 진입점 |
|---|---|---|
| **계층 간 신뢰 관계 악용** | 한 계층이 다른 계층을 신뢰하는 가정을 무너뜨려 공격을 한 계층에서 다른 계층으로 전진시킨다 | SQL 주입, 명령 주입 |
| **다른 계층을 밑에서 무력화** | 계층 간 격리가 부실할 때, 한 계층의 결함으로 다른 계층의 보호를 직접 우회한다 | 복호화 함수 접근, 로컬 파일 읽기 |
| **인프라 확장 공격** | 한 계층을 제한적으로 침해한 뒤, 다른 계층을 떠받치는 인프라를 네트워크·OS 층위에서 직접 공격한다 | 임의 명령 실행 후 내부 스캔 |

### 31.1.1 신뢰 관계를 타고 전진하기

계층 사이에는 흔히 **신뢰 관계**가 있다. 애플리케이션이 정상 동작할 때 이 가정은 대체로 옳다. 그러나 비정상 조건이나 적극적 공격 아래에서는 무너진다.

엔터프라이즈 애플리케이션에서 가장 흔한 신뢰 관계는 이렇다. **애플리케이션 계층이 사용자 접근 관리를 단독으로 책임진다.** 이 계층이 인증과 세션 관리를 처리하고, 어떤 요청을 허가할지 결정한다. 애플리케이션 계층이 요청을 허가하기로 하면 그것은 다른 계층에 명령을 내려 요청된 동작을 수행시킨다. 다른 계층들은 애플리케이션 계층이 접근 통제 검사를 제대로 수행했으리라 믿고, 받은 명령을 모두 이행한다.

이 신뢰 관계가 앞 장들에서 본 흔한 취약점들을 **증폭한다.** SQL 주입 결함이 있으면, 대개 그것으로 애플리케이션이 소유한 모든 데이터에 접근할 수 있다. 애플리케이션이 DBA로 데이터베이스에 접속하지 않더라도, 보통은 애플리케이션의 모든 데이터를 읽고 쓸 수 있는 단일 계정을 쓴다. **데이터베이스 계층이 애플리케이션 계층더러 자기 데이터에 대한 접근을 제대로 통제하라고 신뢰하기 때문이다.** 마찬가지로, 애플리케이션 컴포넌트는 흔히 민감한 동작과 핵심 파일 접근 권한을 가진 강력한 OS 계정으로 돈다. 이 구성에서 OS 계층은 애플리케이션 계층더러 바람직하지 않은 동작을 하지 않으리라 신뢰한다. 공격자가 명령 주입 결함을 찾으면, 대개 침해된 애플리케이션 계층을 떠받치는 운영체제 전체를 장악할 수 있다.

신뢰 관계는 다른 문제도 낳는다. 한 계층의 프로그래밍 오류가 다른 계층에서 이상 동작을 유발하는 것이다. 29장에서 본 경쟁 조건(race condition)은 백엔드 데이터베이스가 엉뚱한 사용자의 계정 정보를 내주게 만들었다. 또한 관리자가 사고를 조사할 때, **신뢰하는 계층의 감사 로그는 무슨 일이 일어났는지 온전히 파악하기에 부족하다.** 그 로그가 사건의 행위자로 기록하는 것은 신뢰된 계층뿐이기 때문이다. SQL 주입 공격 뒤 데이터베이스 로그는 공격자가 주입한 모든 질의를 기록할 수 있지만, 책임자를 특정하려면 애플리케이션 계층의 로그와 교차 대조해야 하고, 그것으로 범인을 식별할 수 있을지는 장담할 수 없다.

### 31.1.2 다른 계층을 밑에서 무력화하기

계층들이 부실하게 격리되어 있으면, 한 계층을 침해한 공격자가 다른 계층의 보호를 직접 우회할 수 있다. 이 취약점은 여러 계층이 **같은 물리 컴퓨터**에 구현된 상황에서 자주 생긴다. 비용이 핵심 요인일 때 흔한 구성이다.

15.10.4절이 이 부류의 세 사례 — 복호화 알고리즘 접근, 파일 읽기로 MySQL 데이터 추출, 로컬 파일 인클루전으로 명령 실행 — 를 배치의 관점에서 상세히 서술했으므로, 여기서는 공격자의 결론만 짚는다. 첫째, **암호화는 이 맥락에서 최소한의 보호만 제공한다.** 많은 애플리케이션이 규제(PCI 등)를 맞추려 민감 데이터를 암호화하지만, 애플리케이션이 데이터를 복호화할 수 있는 한, 애플리케이션이 완전히 침해되면 공격자는 언제나 복호화 알고리즘으로 가는 논리적 경로를 찾아낸다. 인증·인가 검사를 우회하고 겉보기에 합법적인 데이터 요청을 만들면, 스택 하위의 컴포넌트가 복호화 함수를 자동으로 호출한다. 둘째, 암호화 키와 암호화된 데이터 사이에 논리적 분리가 없을 때 — 예를 들어 알고리즘과 키를 데이터 계층 안에 두는 흔한 결함 — 데이터 계층이 SQL 주입으로 침해되면 복호화 함수를 찾아 실행하는 것은 공격자에게 사소한 단계가 된다.

### 31.1.3 HACK STEPS — 제한적 결함을 전면 침해로

계층 아키텍처를 마주한 공격자의 방법론은 두 개의 원칙으로 압축된다. WAHH가 이 두 단계를 이 장 전체의 핵심으로 제시한다.

1. **찾아낸 어떤 취약점이든, 그것을 목표 달성에 어떻게 활용할지 상상력을 발휘하라.** 웹 애플리케이션에 대한 수많은 성공적 침해가 본질적으로 영향이 제한된 취약점 하나에서 출발한다. 다른 곳에 구현된 통제를 신뢰 관계로 잠식하고 밑에서 무력화함으로써, 사소해 보이는 결함 하나를 심각한 침해로 지렛대질할 수 있다. 이것이 앞 장들에서 "제한적"이라 평가하고 넘어간 결함들을 다시 봐야 하는 이유다.

2. **어느 컴포넌트에서든 임의 명령 실행에 성공하고 다른 호스트로 네트워크 연결을 열 수 있다면, 네트워크·OS 층위에서 다른 인프라 요소를 직접 공격해 침해 범위를 넓힐 방법을 고려하라.** 한 계층의 명령 실행은 그 계층에 갇히지 않는다. 그것은 다른 계층을 떠받치는 인프라로 가는 발판이 된다.

15.10.4절의 로컬 파일 인클루전 사례가 이 두 원칙을 결합해 보인다. 세션 파일에 자기 닉네임으로 서버 실행 가능한 스크립트(`<?php passthru(id); ?>`)를 심어 두고, 로컬 파일 인클루전으로 그 세션 파일을 포함시켜 `id` 명령을 실행하는 것이다. 애초에는 사용자 프로필의 닉네임 필드라는 사소한 입력점이, 파일 인클루전이라는 별개의 결함과 만나 명령 실행으로 번졌다.

### 31.1.4 계층 아키텍처의 방어 — 침해의 국지화

계층 아키텍처는 세심하게 구현되면 **애플리케이션의 보안을 상당히 강화한다.** 성공한 공격의 영향을 국지화하기 때문이다. 모든 컴포넌트가 한 컴퓨터에서 도는 기본 LAMP 구성에서는, 어느 한 계층의 침해가 애플리케이션 전체의 침해로 이어지기 쉽다. 더 안전한 아키텍처에서는 한 계층의 침해가 애플리케이션 데이터·처리의 부분적 통제로 그치고, 영향이 침해된 계층에 갇힐 수 있다. WAHH가 드는 세 방어 원칙을 정리한다.

**첫째, 신뢰 관계를 최소화한다.** 각 계층은 가능한 한 자기 통제를 스스로 구현하고, 자기가 막을 수 있는 침해를 다른 컴포넌트가 막아 주리라 신뢰하지 않는다.

- **애플리케이션 서버 계층**은 특정 리소스·URL 경로에 대해 역할 기반 접근 통제를 강제할 수 있다. 예컨대 `/admin` 경로에 대한 요청이 관리자에게서 왔는지를 애플리케이션 서버가 검증한다. 이는 웹 애플리케이션 계층의 특정 접근 통제 결함의 영향을 완화한다. 인가되지 않은 사용자의 요청이 그 계층에 닿기 전에 차단되기 때문이다.
- **데이터베이스 서버 계층**은 사용자·동작별로 서로 다른 계정을 제공할 수 있다. 미인증 사용자를 대신한 동작은 제한된 데이터에 읽기 전용으로만 접근하는 저권한 계정으로 수행한다. 이는 많은 SQL 주입 취약점의 영향을 완화한다. 성공한 공격도 사용자가 애플리케이션을 정상적으로 써서 얻을 수 있는 것 이상의 접근을 주지 못하게 된다.
- **모든 컴포넌트**는 정상 동작에 필요한 최소 권한만 가진 OS 계정으로 돈다. 이는 명령 주입·파일 접근 결함의 영향을 완화한다. 잘 설계되고 완전히 강화된 아키텍처에서는 이런 취약점이 공격자에게 쓸모 있는 기회를 아예 주지 못할 수 있다.

**둘째, 컴포넌트를 분리한다.** 각 계층이 다른 계층과 의도치 않은 방식으로 상호작용하지 못하게 격리한다. 경우에 따라 서로 다른 물리 호스트에서 컴포넌트를 돌려야 한다.

- 서로 다른 계층은 다른 계층이 쓰는 파일에 읽기·쓰기 접근을 갖지 않는다. 애플리케이션 계층은 데이터베이스 데이터를 저장하는 물리 파일에 어떤 접근도 갖지 않고, 오직 적절한 계정의 데이터베이스 질의로만 그 데이터에 접근한다.
- 인프라 컴포넌트 사이의 네트워크 접근은 의도된 서비스로만 걸러진다. 주 로직 서버가 데이터베이스 서버와는 SQL 질의 포트로만 통신하게 하면, 그 서비스를 실제로 이용하는 공격은 못 막아도 인프라 층위의 데이터베이스 공격은 막고, OS 층위의 침해가 조직의 더 넓은 네트워크로 번지는 것을 가둔다.

**셋째, 심층 방어를 적용한다.** 스택의 모든 계층을 설정과 패치 양면에서 강화하고, 각 계층에 저장되는 민감 데이터를 암호화해 그 계층이 침해되어도 쉬운 노출을 막는다. 사용자 자격증명과 신용카드 번호는 데이터베이스에 암호화 형태로 저장하고, 웹 애플리케이션 계층이 쥔 데이터베이스 자격증명은 플랫폼이 제공하는 보호 메커니즘으로 지킨다.

## 31.2 공유 호스팅과 공유 애플리케이션 서비스 — 환경 공격과 격리 강화

많은 조직이 웹 애플리케이션을 대중에게 전달하기 위해 외부 제공자를 쓴다. 그 형태는 단순 호스팅부터 완전한 애플리케이션 서비스 제공자(ASP)까지 걸쳐 있다. 15.9절이 이 배치의 성질을 다뤘다 — 무엇이 공유되고 격리의 단위가 어디로 내려가며, 테넌트 격리가 실제로 어떻게 실패하는지를. 이 절은 그 환경을 마주한 공격자의 방법론과, 15.9절이 이 장의 몫으로 남겨 둔 점검 절차를 다룬다.

공유 환경은 단일 호스팅 애플리케이션에는 없는 새로운 위협을 도입한다. 15.9.1절이 정리한 두 위협 — 악의적 고객과 부주의한 고객 — 이 공격자에게는 두 개의 진입 경로다. 다른 고객이 될 수 있고, 취약한 다른 고객의 애플리케이션을 발판 삼을 수 있다. 어느 쪽이든 공격자의 핵심 초점은 **공유 환경 그 자체**다. 개별 애플리케이션 하나에서 공유 환경을 침해할 수 있는지, 취약한 애플리케이션 하나를 지렛대 삼아 다른 애플리케이션을 공격할 수 있는지를 겨눈다.

### 31.2.1 HACK STEPS — 공유 환경을 안에서 공격하기

WAHH가 제시하는 공유 환경 공격의 절차는 다섯 단계다.

1. **고객이 콘텐츠·기능을 갱신·관리하기 위해 제공받는 접근 메커니즘을 조사하라.** 다음 질문을 던진다.
   - 원격 접근 설비가 안전한 프로토콜과 적절히 강화된 인프라를 쓰는가?
   - 고객이 정당하게 접근할 필요가 없는 파일·데이터·자원에 접근할 수 있는가?
   - 고객이 호스팅 환경 안에서 대화형 셸을 얻어 임의 명령을 수행할 수 있는가?

2. **고객이 공유 환경을 설정·맞춤하도록 독자 애플리케이션이 제공된다면, 그 애플리케이션 자체를 표적으로 삼으라.** 환경 자체와 그 안에서 도는 개별 애플리케이션을 침해하는 수단이 될 수 있다.

3. **한 애플리케이션 안에서 명령 실행·SQL 주입·임의 파일 접근을 달성했다면, 그것이 다른 애플리케이션을 공격하도록 확장할 수단을 주는지 면밀히 조사하라.**

4. **공유·맞춤 컴포넌트로 이루어진 ASP 호스팅 애플리케이션을 공격한다면, 공유 컴포넌트를 식별하라.** 로깅 메커니즘, 관리 기능, 데이터베이스 코드 컴포넌트 같은 것들이다. 이를 지렛대 삼아 애플리케이션의 공유 부분을 침해하고, 그럼으로써 다른 개별 애플리케이션을 공격한다.

5. **어떤 종류든 공유 환경에서 공용 데이터베이스가 쓰인다면, 데이터베이스 설정·패치 수준·테이블 구조·권한을 종합 감사하라.** 데이터베이스 보안 모델의 결함이 한 애플리케이션에서 다른 애플리케이션으로 공격을 확장하는 수단을 줄 수 있다.

특히 ASP는 흔히 모든 고객의 데이터를 담는 공유 데이터베이스를 쓴다. 데이터 접근의 엄격한 분리가 애플리케이션·데이터베이스 층에서 강제될 수도, 되지 않을 수도 있다. 어느 경우든 여러 고객의 데이터를 처리하는 공유 컴포넌트 — 저장 프로시저 같은 — 가 대개 존재한다. **정의자 권한(definer privileges)으로 도는 공유 저장 프로시저에 SQL 주입 취약점이 있으면, 공유 데이터베이스 전체가 침해될 수 있다.**

### 31.2.2 PHP 환경 점검 — `phpinfo()`와 safe mode

LAMP 모델 기반의 공유 호스팅 환경은 흔히 PHP의 **safe mode**로 악의적이거나 취약한 스크립트의 잠재적 영향을 제한하려 했다. 15.9.6절이 safe mode가 왜 구조적으로 잘못된 자리인지를 설명했다 — 운영체제가 애플리케이션 계층더러 자기 행동을 통제하라고 신뢰하는 일이기 때문이다. 여기서는 그 환경을 마주한 공격자가 실제로 무엇을 점검하는지를 본다. 15.9절이 이 절차를 31장의 몫으로 남겨 두었다.

**서버에서 임의 PHP 명령을 실행할 수 있다면, `phpinfo()` 함수로 PHP 환경의 설정 세부를 반환받으라.** 이 출력을 검토해 safe mode가 켜져 있는지, 다른 설정 옵션이 쉽게 수행할 수 있는 동작에 어떤 영향을 주는지를 확정한다. `phpinfo()`는 공격자에게 환경의 지도를 통째로 건넨다. 확인할 핵심 지시자를 정리한다.

**표 31-2. `phpinfo()`로 확인하는 PHP 보안 설정 (WAHH 19장 기준)**

| 지시자 | 켜졌을 때의 위험 | 공격자의 활용 |
|---|---|---|
| `register_globals` | 모든 요청 파라미터가 전역 변수로 생성됨. 초기화되지 않은 변수를 임의 값으로 설정 가능 | `$authenticated`를 파라미터로 주입해 인증 우회 |
| `safe_mode` | (켜졌을 때) `shell_exec` 무효화, `exec`는 `safe_mode_exec_dir` 내로 제한, `mail`의 위험 파라미터 무효화 | 어떤 함수가 제한되는지 파악하고 우회로를 찾음 |
| `allow_url_fopen` / `allow_url_include` | 원격 URL을 파일처럼 열거나 포함 가능 | 원격 파일 인클루전 |
| `magic_quotes_gpc` | 요청의 따옴표·백슬래시·널을 자동 이스케이프 | SQL 주입 시도의 처리 방식을 조정. 숫자 필드 주입과 2차 공격에는 무력 |

**safe mode의 한계를 공격자는 정확히 안다.** 모든 위험 함수가 safe mode로 제한되는 것은 아니고, 일부 제약은 다른 설정 옵션에 좌우되며, 여러 제약에는 우회 방법이 존재한다. **safe mode는 PHP 애플리케이션의 보안 문제에 대한 만병통치약이 아니며**, PHP 6에서 제거됐다. `magic_quotes_gpc`도 마찬가지로 모든 SQL 주입을 막지 못한다. 숫자 필드로의 주입은 따옴표가 필요 없고, 이스케이프된 데이터도 나중에 데이터베이스에서 다시 읽힐 때 2차 공격에 쓰일 수 있다. 게다가 애플리케이션이 필요할 때만 `addslashes`로 직접 이스케이프하는데 magic quotes까지 켜져 있으면, 이중 이스케이프가 발생해 백슬래시가 문자 그대로 해석되고 악성 문자가 오히려 이스케이프되지 않은 채 남는다.

### 31.2.3 공유 환경의 강화

공유 환경은 같은 시설의 악의적 고객과, 환경에 취약점을 들이는 부주의한 고객이라는 이중의 위험을 진다. 이를 다루려면 고객 접근·격리·신뢰의 관점에서 세심하게 설계해야 한다. WAHH가 드는 강화책을 세 묶음으로 정리한다.

**안전한 고객 접근.**

- 원격 접근 메커니즘은 견고한 인증을 구현하고, 도청에 취약하지 않은 암호 기술을 쓰며, 완전히 강화한다.
- 개별 고객에게는 최소 권한 기준으로 접근을 부여한다. 가상 호스팅 서버에 스크립트를 올리는 고객은 자기 문서 루트에 대해서만 읽기·쓰기 권한을 갖는다. 공유 데이터베이스에 접근한다면, 다른 고객의 데이터·컴포넌트에 접근할 수 없는 저권한 계정으로 한다.
- 고객 접근에 맞춤 애플리케이션을 쓴다면, 공유 환경의 보안을 지키는 그 중대한 역할에 걸맞게 엄격한 보안 요구사항과 테스트를 적용한다.

**고객 기능의 분리.** 공유 환경의 고객이 오직 무해하고 취약점 없는 기능만 만들리라 신뢰할 수 없다. 각 고객 코드에 허용되는 능력을 다음과 같이 격리해, 의도적이든 뜻하지 않든 침해가 국지화되고 다른 고객에 영향을 주지 못하게 한다.

- 각 고객의 애플리케이션은 별도의 OS 계정으로 파일시스템에 접근하며, 그 계정은 해당 애플리케이션의 파일 경로에만 읽기·쓰기 권한을 갖는다.
- 강력한 시스템 함수·명령에 접근하는 능력을 OS 층위에서 최소 권한 기준으로 제한한다.
- 공유 데이터베이스 안에도 같은 보호를 구현한다. 고객마다 별도의 데이터베이스 인스턴스를 쓰고, 저권한 계정을 배정해 자기 데이터에만 접근하게 한다.

**공유 애플리케이션 안의 컴포넌트 분리.** 하나의 애플리케이션이 여러 공유·맞춤 컴포넌트로 이루어진 ASP 환경에서는, 서로 다른 당사자의 통제 아래 있는 컴포넌트 사이에 신뢰 경계를 강제한다. **공유 컴포넌트(예: 데이터베이스 저장 프로시저)가 개별 고객의 맞춤 컴포넌트로부터 데이터를 받을 때, 그 데이터를 최종 사용자에게서 직접 온 것과 같은 수준으로 불신해야 한다.** 각 컴포넌트를 인접한 컴포넌트 — 자기 신뢰 경계 바깥의 — 로부터 출발한 공격으로 엄격히 테스트한다. 공유 로깅·관리 기능에 특히 주의를 기울인다.

15.9절이 지적했듯 이 강화책의 근저에는 하나의 원리가 있다. **safe mode처럼 애플리케이션 계층이 스스로를 통제하도록 신뢰하는 방어는 구조적으로 잘못된 자리에 있다.** 격리는 격리되는 대상보다 아래에 있는 층 — OS 계정, 별도 인스턴스, 네트워크 필터 — 에서 강제되어야 한다.

## 31.3 애플리케이션 프레임워크 결함

웹 애플리케이션 프레임워크는 수년간 여러 심각한 결함의 무대였다. 프레임워크 결함이 특별히 위험한 이유는 그 **파급 범위**에 있다. 하나의 애플리케이션에 있는 버그는 그 애플리케이션 하나를 취약하게 만들지만, **프레임워크 하나에 있는 결함은 그 프레임워크 위에서 도는 수많은 애플리케이션을 한꺼번에 취약하게 만든다.** 12.10절이 이 결함을 서버 소프트웨어 결함의 한 부류로 분류하며 표 12-8에 넣었다. 이 절은 그 대표 사례인 .NET 패딩 오라클을 방법론의 관점에서 상세히 본다.

### 31.3.1 .NET 패딩 오라클

근래 가장 유명한 공개 중 하나가 .NET의 "패딩 오라클(padding oracle)" 익스플로잇이다. .NET은 CBC 블록 암호에 PKCS #5 패딩을 쓰는데, 그 구조가 결함의 무대가 됐다.

블록 암호는 고정 블록 크기로 동작한다. .NET에서는 흔히 8바이트 또는 16바이트다. PKCS #5 표준은 평문 문자열 길이가 블록 크기의 배수가 되도록 패딩 바이트를 덧붙인다. **패딩에 임의 값을 쓰는 대신, 패딩 바이트의 개수를 그 값으로 쓴다.** 모든 문자열이 패딩되므로, 원래 문자열이 마침 블록 크기의 배수라도 한 블록 전체가 패딩으로 붙는다. 블록 크기가 8일 때, 메시지는 `0x01` 한 바이트, 또는 `0x02` 두 바이트, ... 최대 `0x08` 여덟 바이트로 패딩된다. 그런 다음 첫 평문 블록을 초기화 벡터(IV)와 XOR하고, 이후 블록은 앞 블록의 암호문과 XOR해 순환 블록 체인(CBC)을 이룬다.

**2010년 9월까지의 취약한 .NET 버전에는 작아 보이는 정보 노출 결함이 있었다.** 메시지에서 잘못된 패딩이 발견되면 애플리케이션이 오류를 보고했고, 그 결과 사용자에게 HTTP `500` 응답이 갔다. PKCS #5 패딩 알고리즘과 CBC의 동작을 함께 이용하면, 이 한 비트의 정보로 .NET 보안 메커니즘 전체를 침해할 수 있었다.

원리는 이렇다. 유효한 평문 문자열은 최소 한 바이트의 패딩을 포함해야 한다. 공격자는 IV와 첫 암호문 블록, 두 블록만 담은 문자열을 애플리케이션에 보낸다. IV를 전부 0으로 채운 뒤, IV의 마지막 바이트를 순차로 증가시키며 일련의 요청을 보낸다. 이 마지막 바이트는 암호문의 마지막 바이트와 XOR되는데, 그 결과가 `0x01`이 아니면 암호 알고리즘이 오류를 던진다. 공격자는 결국 XOR 결과가 `0x01`이 되는 값에 도달하고, 그 시점에서 `x XOR y = 0x01`이라는 관계로 암호문 마지막 바이트의 평문 값을 알아낸다. 같은 과정을 마지막에서 두 번째 바이트로, 다음 블록으로 재귀적으로 적용하면 **메시지 전체를 복호화할 수 있다.**

흥미롭게도 같은 메커니즘으로 공격자는 메시지를 **암호화**할 수도 있다. 평문 문자열을 복원하고 나면 IV를 조작해 원하는 평문을 만들 수 있다. 최적의 표적 중 하나가 `ScriptResource.axd`였다. 그 `d` 인자는 암호화된 파일명인데, 공격자가 `web.config`를 파일명으로 선택하면 실제 설정 파일이 서빙됐다. ASP.NET이 IIS가 부과하는 정상 제약을 우회해 파일을 내주기 때문이다.

### 31.3.2 프레임워크 결함이 가르치는 것

이 공격은 CBC 암호에 PKCS #5 패딩을 쓰는 어떤 시스템에도 더 일반적으로 적용된다. 원래 2002년에 논의됐으나, .NET은 세션 토큰·ViewState·`ScriptResource.axd`에 이 패딩을 써서 특히 좋은 표적이 됐다. **작아 보이는 이상(anomaly) — 패딩이 틀리면 `500` 오류가 난다는 것 — 이 파국적 결과로 실용적으로 익스플로잇될 수 있음**을 이 사례가 증명한다. WAHH의 결론 문장이 이 책의 태도와 일치한다. **"직접 만든 암호 알고리즘을 절대 쓰지 말라"** 는 흔한 격언이 실제로 얼마나 값진지를 이 사례가 보인다.

이 절이 12.10절과 나누는 역할을 분명히 한다. 12.10절은 이 결함을 서버 소프트웨어 결함의 한 부류로 **분류**하며 어느 단계의 결함인지를 표시했다(5단계, 응답 생성). 이 절은 그 결함이 실제로 어떻게 익스플로잇되는지를 **방법론**으로 풀었다. 그리고 오류가 정보 채널이 되는 일반적 문제는 30장이 다뤘다. 패딩 오라클은 그 문제의 가장 날카로운 사례다 — 오류 응답 하나가 암호 시스템 전체를 여는 오라클이 된다.

> **이 절이 뒷받침하는 것**
>
> - 프레임워크 결함의 분류와 대응 단계 → **12.10** (표 12-8, 서버 소프트웨어 결함의 부류)
> - 오류 응답이 정보 채널이 되는 일반 문제 → **30장** (오류와 정보 노출), **30.3** (추론을 통한 정보 수집)
> - CBC·XOR·패턴 노출의 암호학적 배경 → **7장** (엔티티와 인코딩의 보안적 함의 맥락)

## 31.4 메모리 관리 취약점 — 버퍼 오버플로(스택·힙), off-by-one

여기서부터 세 절은 성격이 다르다. **네이티브 실행 환경에서 도는 컴파일된 소프트웨어**의 고전적 결함을 다룬다. 버퍼 오버플로와 포맷 스트링 버그는 역사적으로 C·C++로 개발된 소프트웨어를 괴롭혀 왔고, 그 소프트웨어에서 발견된 심각한 버그의 다수를 낳았다.

대다수 웹 애플리케이션은 **관리 실행 환경(managed execution environment)**에서 도는 언어·플랫폼으로 작성된다. C#과 Java 같은 언어의 가장 큰 이점 하나가, 프로그래머가 네이티브 언어에서 문제가 되는 버퍼 관리와 포인터 산술을 걱정할 필요가 없다는 것이다. 그럼에도 이 절들을 두는 이유는 서두에서 밝혔다. 프린터·스위치 같은 하드웨어 장치에서 도는 웹 애플리케이션은 흔히 네이티브 코드를 포함하고, 주로 관리 코드로 작성된 애플리케이션도 네이티브 코드 부분을 담거나 비관리 컨텍스트에서 도는 외부 컴포넌트를 호출한다. 이름에 `dll`·`exe` 같은 네이티브 코드 지표가 들어간 페이지나, 로깅 메커니즘처럼 레거시 외부 컴포넌트를 호출하는 것으로 알려진 기능이 유력한 표적이다.

이 절은 세 부류의 고전적 소프트웨어 취약점 중 첫째인 버퍼 오버플로를 다룬다. 26.6절이 다룬 네이티브 클라이언트 컴포넌트가 같은 결함을 클라이언트 측에서 만나는 자리였다면, 이 절은 그것을 서버 측에서 본다.

### 31.4.1 스택 오버플로

**버퍼 오버플로 취약점은 애플리케이션이 사용자가 통제하는 데이터를, 그것을 담기에 충분히 크지 않은 메모리 버퍼로 복사할 때 생긴다.** 목적지 버퍼가 넘치고, 인접 메모리가 사용자의 데이터로 덮어써진다. 결함의 성질에 따라 공격자는 이를 익스플로잇해 서버에서 임의 코드를 실행하거나 다른 무단 동작을 할 수 있다.

버퍼 오버플로는 흔히 애플리케이션이 **경계를 확인하지 않는 복사 연산**(C의 `strcpy` 같은)으로, 가변 크기 버퍼를 고정 크기 버퍼가 충분히 큰지 검증하지 않은 채 복사할 때 생긴다. 다음 함수는 사용자명 문자열을 스택에 할당된 고정 크기 버퍼로 복사한다.

```c
bool CheckLogin(char* username, char* password)
{
    char _username[32];
    strcpy(_username, username);
    ...
}
```

`username` 문자열이 32자를 넘으면 `_username` 버퍼가 넘치고, 공격자는 인접 메모리의 데이터를 덮어쓴다.

스택 기반 버퍼 오버플로에서 성공적 익스플로잇은 대개 **스택에 저장된 복귀 주소(saved return address)를 덮어쓰는 것**을 수반한다. `CheckLogin` 함수가 호출되면 프로세서는 호출 다음 명령의 주소를 스택에 넣는다. 함수가 끝나면 프로세서는 이 주소를 스택에서 꺼내 그 명령으로 실행을 되돌린다. 그런데 `CheckLogin`은 `_username` 버퍼를 이 저장된 복귀 주소 바로 옆에 할당한다. 공격자가 `_username`을 넘치게 할 수 있으면, 복귀 주소를 자기가 고른 값으로 덮어써서 프로세서가 그 주소로 점프해 **임의 코드를 실행하게** 만든다.

### 31.4.2 힙 오버플로

힙 기반 버퍼 오버플로는 본질적으로 같은 안전하지 않은 연산을 수반하되, 넘치는 목적지 버퍼가 스택이 아니라 힙에 할당된다는 점이 다르다.

```c
bool CheckLogin(char* username, char* password)
{
    char* _username = (char*) malloc(32);
    strcpy(_username, username);
    ...
}
```

힙 기반 오버플로에서 목적지 버퍼에 인접한 것은 저장된 복귀 주소가 아니라 다른 힙 메모리 블록이며, 그것들은 **힙 제어 구조(heap control structure)**로 구분된다. 힙은 이중 연결 리스트로 구현된다. 각 블록 앞에는 블록 크기, 이전 블록 포인터, 다음 블록 포인터를 담은 제어 구조가 있다. 힙 버퍼가 넘치면 인접 힙 블록의 제어 구조가 사용자가 통제하는 데이터로 덮어써진다.

이 부류는 스택 기반 오버플로보다 익스플로잇이 덜 직관적이다. 흔한 접근은 덮어써진 힙 제어 구조에 조작된 값을 써서, 미래 어느 시점에 **핵심 포인터의 임의 덮어쓰기**를 유발하는 것이다. 제어 구조가 덮어써진 힙 블록이 메모리에서 해제되면, 힙 관리자는 연결 리스트를 갱신해야 한다. 이를 위해 다음 블록의 뒤 링크 포인터와 앞 블록의 앞 링크 포인터를 서로를 가리키게 갱신하는데, 이때 덮어써진 제어 구조의 값을 쓴다. 구체적으로, 힙 관리자는 덮어써진 구조에서 가져온 앞 링크 포인터를 역참조해, 그 주소에 뒤 링크 포인터 값을 쓴다. **즉 사용자가 통제하는 값을 사용자가 통제하는 주소에 쓰는 것이다.** 공격자가 오버플로 데이터를 적절히 조작했다면, 메모리의 어떤 포인터든 자기가 고른 값으로 덮어쓸 수 있다. 임의 포인터 덮어쓰기의 전형적 표적은 애플리케이션이 나중에 호출할 함수 포인터 값과, 다음 예외 발생 시 호출될 예외 핸들러의 주소다.

### 31.4.3 off-by-one 취약점

특정 종류의 오버플로가 프로그래밍 오류로 인해 공격자가 할당된 버퍼 끝을 **단 한 바이트**(또는 소수의 바이트) 넘겨 쓸 수 있을 때 생긴다.

```c
bool CheckLogin(char* username, char* password)
{
    char _username[32];
    int i;
    for (i = 0; username[i] && i < 32; i++)
        _username[i] = username[i];
    _username[i] = 0;
    ...
}
```

이 코드는 최대 32바이트를 복사한 뒤 널 종결자를 붙인다. 따라서 사용자명이 32바이트 이상이면 널 바이트가 `_username` 버퍼 끝을 넘겨 써져 인접 메모리를 손상시킨다. 스택의 인접 항목이 호출 프레임의 저장된 프레임 포인터라면, 하위 바이트를 0으로 만드는 것이 그 포인터를 `_username` 버퍼로 — 즉 공격자가 통제하는 데이터로 — 가리키게 할 수 있고, 호출 함수가 복귀할 때 실행 흐름을 장악하게 할 수 있다.

비슷한 취약점이 **널 종결자를 위한 공간을 개발자가 간과할 때** 생긴다. 힙 오버플로의 다음 "수정"을 보자.

```c
char* _username = (char*) malloc(32);
strncpy(_username, username, 32);
```

프로그래머는 개수를 센 복사로 버퍼가 넘치지 않게 하려 했다. 그러나 사용자명이 버퍼보다 길면 버퍼가 사용자명 문자로 완전히 채워지고, 끝에 널 바이트를 붙일 공간이 남지 않는다. **복사된 문자열이 널 종결자를 잃는다.** C 같은 언어는 문자열 길이의 별도 기록을 갖지 않는다. 문자열의 끝은 널 바이트로 표시된다. 문자열이 널 종결자를 잃으면, 그것은 사실상 길이가 늘어나 메모리의 다음 0 바이트까지 이어진다.

WAHH 저자들이 하드웨어 장치에서 도는 웹 애플리케이션에서 이 부류의 취약점을 만난 사례가 이 결함의 실제 위력을 보인다. 그 애플리케이션에는 임의 파라미터를 POST로 받아, 그 이름과 값을 숨은 필드로 담은 HTML 폼을 되돌려 주는 페이지가 있었다. 이 페이지가 온갖 종류의 사용자 입력 — 많은 경우 민감한 — 을 처리하는 데 두루 쓰였다. 그런데 **4096바이트 이상의 데이터를 보내면, 되돌아온 폼에 그 페이지에 대한 이전 요청의 파라미터가 — 다른 사용자가 보낸 것이라도 — 함께 담겼다.**

```
POST /formRelay.cgi HTTP/1.0
Content-Length: 4096

a=bbbbbbbbbbbbb[b가 잔뜩]
```

```
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 4598

...
<input type="hidden" name="a" value="bbbbbbbbbbbbb[b가 잔뜩]">
<input type="hidden" name="strUsername" value="agriffiths">
<input type="hidden" name="strPassword" value="aufwiedersehen">
<input type="hidden" name="Log_in" value="Log+In">
...
```

이 취약점을 식별한 뒤에는, 취약한 페이지를 과길이 데이터로 계속 폴링하고 응답을 파싱해 다른 사용자가 그 페이지에 제출한 모든 데이터 — 로그인 자격증명을 포함해 — 를 기록할 수 있었다. **근본 원인**은 사용자 데이터가 4096바이트 블록 안에 널 종결 문자열로 저장됐다는 것이다. 데이터는 검사된 연산으로 복사됐으므로 직접 오버플로는 불가능했다. 그러나 과길이 입력이 제출되면 복사 연산에서 널 종결자가 사라졌고, 문자열이 메모리의 다음 데이터로 흘러들었다. 그래서 애플리케이션이 요청 파라미터를 파싱할 때 다음 널 바이트까지 계속 읽어 다른 사용자의 파라미터를 포함했다.

이 사례가 왜 중요한가. off-by-one은 크래시를 일으키지 않고도 **이상 데이터 노출**이라는 형태로 익스플로잇될 수 있음을 보인다. 그리고 그것은 이 장이 반복하는 주제 — 길이와 경계에 관한 가정이 무너지는 것 — 의 순수한 형태다. 개발자는 "검사된 복사를 쓰니 안전하다"고 가정했지만, 검사가 널 종결자의 공간까지 셈하지는 않았다.

## 31.5 정수 취약점과 포맷 스트링 취약점

### 31.5.1 정수 취약점

정수 관련 취약점은 애플리케이션이 버퍼 연산 전에 길이 값에 산술을 수행하되, 컴파일러와 프로세서가 정수를 다루는 특정 방식을 고려하지 않을 때 생긴다. 두 종류가 주목할 만하다 — 오버플로와 부호 오류다.

**정수 오버플로(integer overflow).** 정수 값에 대한 연산이 그 값을 최댓값 위로 올리거나 최솟값 아래로 내릴 때 생긴다. 이때 숫자가 **래핑(wrapping)** 된다 — 아주 큰 수가 아주 작은 수가 되거나 그 반대다. 힙 오버플로의 다음 "수정"을 보자.

```c
unsigned short len = strlen(username) + 1;
char* _username = (char*) malloc(len);
strcpy(_username, username);
```

애플리케이션은 사용자명 길이를 재고, 널을 위해 1을 더하고, 그 크기의 버퍼를 할당한 뒤 사용자명을 복사한다. 정상 크기 입력에서는 의도대로 동작한다. 그러나 사용자가 **65,535자**의 사용자명을 제출하면 정수 오버플로가 생긴다. `short` 크기 정수는 16비트로 0~65,535를 표현한다. 길이 65,535 문자열에 1을 더하면 값이 래핑되어 0이 된다. **길이 0의 버퍼가 할당되고, 긴 사용자명이 그 안으로 복사되어 힙 오버플로가 발생한다.** 공격자가 "목적지 버퍼를 충분히 크게 하려는" 프로그래머의 시도를 사실상 뒤엎은 것이다.

**부호 오류(signedness error).** 애플리케이션이 버퍼 길이를 재는 데 부호 있는 정수와 부호 없는 정수를 함께 쓰고 어느 지점에서 둘을 혼동할 때 생긴다. 부호 있는 값과 없는 값을 직접 비교하거나, 부호 있는 값을 부호 없는 값을 받는 함수에 넘기는 경우다. 두 경우 모두 부호 있는 값이 부호 없는 등가로 취급되어, **음수가 큰 양수가 된다.**

```c
bool CheckLogin(char* username, int len, char* password)
{
    char _username[32];
    if (len < 32)
        strncpy(_username, username, len);
    ...
}
```

함수는 사용자명과 그 길이를 나타내는 부호 있는 정수를 받는다. `len`이 양수면 의도대로 동작한다. 그러나 공격자가 음수 값을 넘길 수 있으면 보호 검사가 뒤엎어진다. `32`와의 비교는 여전히 성공한다. 컴파일러가 두 수를 모두 부호 있는 정수로 다루기 때문이다. 그리하여 음수 길이가 `strncpy`의 개수 파라미터로 넘어간다. `strncpy`는 이 파라미터로 부호 없는 정수를 받으므로 컴파일러가 `len` 값을 암묵적으로 형변환하고, **음수가 큰 양수로 취급되어** 사용자명이 32바이트보다 길면 버퍼가 표준 스택 오버플로처럼 넘친다. 이 공격은 대개 공격자가 길이 파라미터를 직접 통제할 수 있을 때만 가능하다 — 예컨대 길이가 클라이언트 측 자바스크립트로 계산되어 문자열과 함께 제출되는 경우다.

### 31.5.2 포맷 스트링 취약점

포맷 스트링 취약점은 사용자가 통제하는 입력이, 오용될 수 있는 포맷 지정자(format specifier)를 받는 함수의 **포맷 스트링 파라미터**로 넘어갈 때 생긴다. C의 `printf` 계열이 그렇다. 이 함수들은 가변 개수의 파라미터를 받고, 포맷 스트링의 지정자가 각 파라미터의 종류와 렌더링 형식을 알려준다.

가장 위험한 지정자는 `%n`이다. 이것은 데이터를 출력하지 않는다. 대신 **지금까지 출력된 바이트 수를, 연관된 가변 파라미터로 넘어온 포인터의 주소에 쓴다.**

```c
int count = 43; int written = 0;
printf("The value of count is %d%n.\n", count, &written);
printf("%d bytes were printed.\n", written);
```

는 다음을 출력한다.

```
The value of count is 43.
24 bytes were printed.
```

포맷 스트링이 넘어온 가변 파라미터 수보다 많은 지정자를 담으면, 함수는 이를 탐지할 방법이 없어 그냥 호출 스택에서 파라미터를 계속 처리한다. **공격자가 `printf` 계열 함수에 넘어가는 포맷 스트링의 전부 또는 일부를 통제하면, 대개 이를 익스플로잇해 프로세스 메모리의 핵심 부분을 덮어쓰고 궁극적으로 임의 코드 실행을 일으킬 수 있다.** 공격자가 포맷 스트링을 통제하므로 함수가 출력하는 바이트 수와, 그 수로 덮어써지는 스택 상의 포인터를 모두 통제한다. 이로써 저장된 복귀 주소나 예외 핸들러 포인터를 덮어써 스택 오버플로와 거의 같은 방식으로 실행을 장악한다.

정수 취약점과 포맷 스트링 취약점은 서로 다른 결함이지만 공통점이 있다. 둘 다 **데이터의 수치적 해석에 관한 가정** — 길이 값이 항상 양수이고 래핑되지 않는다는 것, 포맷 스트링에 사용자가 손대지 않는다는 것 — 이 무너질 때 성립한다. 앞 절의 버퍼 오버플로가 길이와 경계의 가정을 겨눴다면, 이 절은 값 자체의 해석을 겨눈다.

## 31.6 네이티브 컴파일 애플리케이션 취약점 탐지

앞 두 절이 세 부류의 결함이 무엇인지를 다뤘다면, 이 절은 원격에서 그것들을 어떻게 **탐지**하는지를 다룬다. 세 부류의 탐지 방법론은 하나로 수렴한다. **식별된 표적에 긴 문자열·경계값·포맷 지정자를 보내고, 이상 결과를 관찰하는 것이다.**

### 31.6.1 버퍼 오버플로 탐지

기본 방법론은 식별된 표적에 긴 데이터 문자열을 보내고 이상 결과를 감시하는 것이다. 어떤 경우에는 특정 길이 또는 좁은 길이 범위의 과길이 문자열로만 탐지되는 미묘한 취약점이 있지만, 대부분은 애플리케이션이 예상하는 것보다 긴 문자열만 보내도 탐지된다. 프로그래머는 흔히 10진·16진의 라운드 넘버 — 32, 100, 1024, 4096 — 로 고정 크기 버퍼를 만든다.

**HACK STEPS — 버퍼 오버플로 탐지**

1. **표적이 되는 각 데이터 항목마다, 흔한 버퍼 크기보다 다소 긴 길이의 문자열을 범위로 제출한다.** 예: 1,100 / 4,200 / 33,000.
2. **한 번에 한 항목만 표적으로 삼아** 애플리케이션 내 코드 경로의 커버리지를 최대화한다.
3. 애플리케이션 응답에서 이상을 식별한다. 통제되지 않은 오버플로는 거의 확실히 예외를 일으킨다. 원격 프로세스에서 이를 탐지하기는 어렵지만, 다음 이상 이벤트를 살핀다.
   - 다른 잘못된(그러나 과길이가 아닌) 입력에는 없던 **HTTP `500`** 상태 코드나 오류 메시지
   - 네이티브 코드 컴포넌트에서 실패가 났음을 알리는 정보성 메시지
   - 서버로부터의 부분적·잘못된 응답
   - 응답 없이 TCP 커넥션이 갑자기 닫힘
   - 웹 애플리케이션 전체가 응답을 멈춤
4. **힙 기반 오버플로는 즉시가 아니라 미래 어느 시점에 크래시를 일으킬 수 있다.** 힙 손상을 일으키는 테스트 케이스를 식별하려면 실험이 필요하다.
5. **off-by-one은 크래시를 일으키지 않고** 예상 밖 데이터 반환 같은 이상 동작만 낳을 수 있다.

테스트 케이스가 애플리케이션 자체나 웹 서버의 입력 검증에 막힐 수 있다. 과길이 데이터가 URL 쿼리 문자열에 담기면 "URL too long" 같은 일반 메시지가 뜨곤 한다. 이때는 허용되는 최대 URL 길이(흔히 약 2,000자)를 실험으로 알아내 버퍼 크기를 맞춘다. 필터 뒤에도 오버플로가 존재할 수 있고, 필터를 통과할 만큼 짧은 문자열로 촉발될 수 있다. 또한 필터가 특정 파라미터에 허용되는 문자 범위를 제한하면, **애플리케이션이 받아들이는 정상 요청을 포착해 각 표적 파라미터를 그것이 이미 담은 문자로 늘리는 기법**으로 내용 기반 필터를 통과시킨다.

### 31.6.2 정수·포맷 스트링 탐지

**정수 취약점**의 일차 탐지 지점은 클라이언트에서 서버로 정수 값이 제출되는 모든 곳이다. 쿼리 문자열·쿠키·본문에 10진 ASCII로 담긴 정수가 흔하며, 특히 함께 제출되는 문자열의 길이를 나타내는 듯한 필드가 유력한 표적이다. 클라이언트 측 컴포넌트(ActiveX 등)에서 온 이진 blob 안에 16진으로 박혀 문자열 바로 앞에 오는 경우도 있다(Base64 등으로 인코딩되어 전송되기도 한다 — 5장 참조).

**HACK STEPS — 정수 취약점 탐지**

1. 각 표적 항목마다, 여러 크기의 정수의 부호 있는·없는 버전의 **경계 케이스**를 차례로 보낸다.
   - `0x7f`와 `0x80` (127, 128)
   - `0xff`와 `0x100` (255, 256)
   - `0x7fff`와 `0x8000` (32767, 32768)
   - `0xffff`와 `0x10000` (65535, 65536)
   - `0x7fffffff`와 `0x80000000` (2147483647, 2147483648)
   - `0xffffffff`와 `0x0` (4294967295, 0)
2. 데이터가 16진으로 표현되면 **리틀엔디언과 빅엔디언 양쪽**을 보낸다 — `7fff`뿐 아니라 `ff7f`도. ASCII 16진이면 애플리케이션이 쓰는 대소문자를 맞춘다.
3. 버퍼 오버플로와 같은 방식으로 이상 이벤트를 감시한다.

**포맷 스트링 취약점**의 가장 신뢰할 만한 원격 탐지법은 여러 포맷 지정자를 담은 데이터를 제출하고 이상 동작을 감시하는 것이다.

**HACK STEPS — 포맷 스트링 탐지**

1. 각 파라미터를 차례로 표적으로 삼아, `%n`과 `%s` 지정자를 대량으로 담은 문자열을 제출한다.
   ```
   %s%s%s%s%s%s%s%s%s%s%s%s%s%s%s%s%s%s%s%s
   ```
   일부 포맷 스트링 연산은 보안상 `%n`을 무시한다. 대신 `%s`를 주면 함수가 스택의 각 파라미터를 역참조해, 취약하면 접근 위반을 일으킬 공산이 크다.
2. Windows `FormatMessage` 함수는 지정자를 `printf` 계열과 다르게 쓰므로, 그 함수의 취약 호출을 시험하려면 `%1!n!%2!n!...` 형태의 문자열을 쓴다.
3. `%` 문자를 `%25`로 URL 인코딩하는 것을 잊지 않는다.
4. 이상 이벤트를 감시한다.

### 31.6.3 탐지 자체가 DoS를 부른다

이 장의 다른 취약점과 대조되는 결정적 특징이 있다. **고전적 소프트웨어 결함은 탐지 행위 자체가 서비스 거부(DoS)를 일으킬 공산이 크다.** 약한 인증이나 경로 순회 같은 취약점과 달리, 이 결함들의 단순한 탐지조차 표적 애플리케이션 안에서 처리되지 않은 예외를 일으키기 쉽고, 그것이 애플리케이션을 멈추게 할 수 있다. **살아 있는 애플리케이션에서 이 버그들을 탐침하려면, 시작 전에 애플리케이션 소유자가 그 위험을 수용했는지 반드시 확인해야 한다.**

이것이 이 부류 취약점의 실무적 결론이다. 네이티브 코드 결함의 상당 비율은 특정 테스트 케이스 집합을 서버에 보내고 그 동작을 관찰함으로써 탐지할 수 있다. off-by-one 같은 일부는 익스플로잇도 비교적 쉽다. 그러나 대부분은 원격 접근만으로 임의 코드 실행을 달성하기가 극히 어렵고, 탐지 단계에서 이미 애플리케이션을 무너뜨릴 위험을 진다.

> **이 책의 범위를 넘어서**
>
> 현대의 컴파일러와 운영체제는 버퍼 오버플로로 이어지는 프로그래밍 오류로부터 소프트웨어를 지키는 여러 방어 — 스택 카나리, 실행 방지 메모리, 주소 공간 배치 무작위화, 제어 흐름 무결성 같은 것들 — 를 구현했다. 이 방어들 때문에 오늘날 실세계의 오버플로는 이 장의 예제보다 익스플로잇이 대체로 훨씬 어렵다. 그리고 애초에 이 결함들을 언어 층위에서 제거하는 메모리 안전 언어로의 전환도 진행 중이다. 이 완화 기술들의 상세, 그것들의 우회 기법, 컨테이너 격리, 메모리 안전 언어의 설계 논의는 모두 이 책의 범위 밖이다. 이 장이 이 결함들을 다룬 목적은 익스플로잇 실무를 가르치는 것이 아니라, **길이·경계·값의 해석에 관한 가정이 무너질 때 무슨 일이 일어나는가**라는 패턴을 그 가장 순수한 형태로 보이는 데 있다.

## 31.7 인코딩·정규화 결함 재방문

이 책은 인코딩·정규화 결함을 이미 두 번 다뤘다. 7.7절이 그 **원리**를 정리했고 — 오버롱 UTF-8, 이중 디코딩, 최적 적합 매핑, 그리고 정규화 후 검증이라는 유일한 올바른 순서 — 28.3절이 그것을 **경로 순회 우회**의 맥락에서 파일시스템 층위의 구체적 변형으로 다뤘다. 이 절은 같은 결함을 세 번째 층위 — **웹 서버 소프트웨어 자체** — 에서 본다. 그리고 이 결함이 이 책이 반복해 온 하나의 구조 — 파싱 불일치 — 와 같은 것임을 밝힌다.

### 31.7.1 결함의 공통 구조

HTTP를 통한 안전한 전송을 위해 특수 문자·콘텐츠를 인코딩하는 여러 스킴이 존재한다(3장). 앞 장들에서 공격자가 이 스킴을 이용해 입력 검증을 회피하는 방식을 여러 번 봤다. **인코딩 결함은 같은 사용자 데이터가 서로 다른 기술로 만든 여러 층에서 처리되는 상황에서 본질적 위협이 된다.**

전형적 웹 요청은 웹 서버, 애플리케이션 플랫폼, 여러 관리·비관리 API, 다른 소프트웨어 컴포넌트, 그리고 밑바탕 운영체제가 처리한다. **서로 다른 컴포넌트가 인코딩 스킴을 다르게 다루거나, 이미 부분 처리된 데이터를 추가로 디코딩·해석하면, 이 사실을 이용해 필터를 우회하거나 이상 동작을 유발할 수 있다.** 이것이 결함의 공통 구조다. 그리고 이 문장은 이 책이 5.6절과 13.12절에서 세운 파싱 불일치의 정의 — 하나의 바이트열을 읽는 주체가 여럿일 때 각자가 그것을 다르게 해석한다 — 와 정확히 같다. **차이는 그 여러 주체가 클라이언트와 서버 사이의 중간자들이 아니라, 하나의 서버 안에 겹겹이 쌓인 소프트웨어 층이라는 것뿐이다.**

### 31.7.2 서버 소프트웨어 층위의 경로 순회

경로 순회는 정규화 결함으로 가장 흔히 익스플로잇되는 취약점이다. 언제나 운영체제와의 통신을 수반하기 때문이다. 28.3절이 웹 애플리케이션에서의 경로 순회를 다뤘다면, 같은 종류의 문제가 여러 웹 서버 소프트웨어에서도 나타나, 웹 루트 밖의 임의 파일을 읽거나 쓰게 했다.

**표 31-3. 웹 서버 소프트웨어의 인코딩·정규화 결함 (WAHH 18장 기준)**

| 제품 / 연도 | 우회 페이로드 | 결함의 층위 |
|---|---|---|
| **Apple iDisk Server** (2009) | `%2E%2E%2F`로 public에서 private로 순회 | 유니코드 순회 |
| **Ruby WEBrick** | `..%5c..%5c..%5c/boot.ini` | 백슬래시 인코딩 순회 |
| **Java Web Server / Tomcat** | `%c0%ae%c0%ae/`로 `../` (JVM이 UTF-8 미디코드) | 오버롱 UTF-8 |
| **Allaire JRun** (2001) | `dir/%3f.jsp`로 디렉터리 리스팅 | `%3f`(?)의 파서 간 해석 차 |
| **IIS 유니코드** (2000) | `..%c0%af..%c0%af../winnt/system32/cmd.exe` | 불법 유니코드 순회 |
| **IIS 이중 인코딩** (2001) | `..%255c..%255c..%255c...` | 이중 인코딩 순회 |
| **IIS WebDAV** (2009) | `/prote%c0%afcted/protected.zip` + `Translate: f` | 앞단이 못 본 rogue 문자열 |

두 IIS 취약점이 이 구조를 가장 선명하게 보인다. 경로 순회를 막기 위해 IIS는 점-점-슬래시 시퀀스를 문자 그대로와 URL 인코딩 형태 양쪽으로 검사했다. 요청에 이 표현이 없으면 추가 처리를 위해 받아들였다. **그러나 서버는 그다음 요청 URL에 추가 정규화를 수행했고, 그것이 공격자로 하여금 필터를 우회하고 서버가 순회 시퀀스를 처리하게 했다.**

- 첫 취약점(2000)에서 공격자는 `..%c0%af` 같은 불법 유니코드 인코딩 형태의 점-점-슬래시를 줬다. 이 표현은 IIS의 앞단 필터에 걸리지 않았지만, **이후 처리가 불법 인코딩을 관대하게 다뤄 문자 그대로의 순회 시퀀스로 되돌렸다.** 이로써 웹 루트를 벗어나 `cmd.exe`로 임의 명령을 실행할 수 있었다.
- 둘째 취약점(2001)에서 공격자는 `..%255c` 같은 **이중 인코딩** 형태를 줬다. 역시 앞단 필터에 걸리지 않았지만, 이후 처리가 불필요한 추가 디코딩을 수행해 문자 그대로의 순회 시퀀스로 되돌렸다.

앞단 필터가 검사하는 형태와 뒷단 처리가 되돌리는 형태 사이의 틈 — 이것이 결함의 전부다. 9년 뒤 IIS의 WebDAV에서 유사한 취약점이 재등장했다는 사실이 이 결함의 끈질긴 중요성을 보인다. `Translate: f` 헤더로 요청을 WebDAV 확장이 처리하게 하고, URL에 rogue `%c0%af` 문자열을 넣으면 IIS가 보호된 파일 요청으로 보지 않아 접근을 허가하지만, 그 rogue 문자열은 나중에 요청에서 벗겨진다.

### 31.7.3 필터와 해석기 사이의 틈 — PL/SQL 제외 목록

같은 구조가 인코딩 밖에서도 나타난다. Oracle의 PL/SQL 게이트웨이로 접근 가능한 위험 기능을 막기 위해 Oracle은 **PL/SQL 제외 목록**을 만들어 `owa`·`sys` 같은 표현으로 시작하는 패키지 접근을 차단했다. David Litchfield는 2001~2007년 이 목록에 대한 일련의 우회를 찾아냈다.

- 패키지명 앞에 공백(개행·스페이스·탭)을 넣기: `%0ASYS.package.procedure` — 필터는 우회되고, 데이터베이스는 공백을 무시해 위험 패키지를 실행한다.
- `Y`를 `%ff`로 바꾸기: `S%FFS.package.procedure` — 데이터베이스가 문자를 표준 `Y`로 정규화한다.
- 차단 표현을 따옴표로 감싸기: `"SYS".package.procedure` — 데이터베이스가 따옴표 붙은 패키지명을 관대하게 받는다.
- goto 라벨을 앞에 두기: `«FOO»SYS.package.procedure` — 데이터베이스가 goto 라벨을 무시한다.

각 우회는 하나의 원리에서 나온다. **앞단 필터링은 단순한 텍스트 기반 패턴 매칭으로 한 컴포넌트가 수행하고, 이후 처리는 입력의 구문·의미를 자기 규칙으로 해석하는 다른 컴포넌트가 수행한다. 두 규칙 집합의 어떤 차이든 우회의 여지가 된다.** Oracle 데이터베이스가 워낙 기능이 많아 그런 차이가 생길 여지가 넉넉했다.

### 31.7.4 이것은 13.12의 서버 내부 버전이다

이 절의 모든 사례가 하나의 구조를 공유한다. 그리고 그 구조는 이 책의 핵심 주제인 **파싱 불일치**와 같다. 13.12절이 중간자 공격 표면을 정리하며 파싱 불일치가 발생하는 지점의 목록을 만들었다. 프록시, 캐시, 로드밸런서, WAF — 하나의 요청을 각자 파싱하고 다시 직렬화하는 중간자들이 그 목록이었다. **이 절이 보인 것은 같은 불일치가 하나의 서버 안에서, 겹겹이 쌓인 소프트웨어 층 사이에서 일어나는 버전이다.**

IIS 앞단 필터와 IIS 정규화 루틴은 같은 서버 안에 있지만, 요청 URL을 서로 다르게 읽는다. Oracle 앞단 필터와 Oracle 데이터베이스도 같다. 중간자든 서버 내부 층이든, **하나의 바이트열을 두 주체가 다르게 해석하면 그 틈이 공격 표면이 된다**는 원리는 동일하다. 이것이 이 책이 인코딩·정규화 결함을 세 층위 — 원리(7.7), 파일시스템(28.3), 서버 소프트웨어(이 절) — 에서 반복해 다룬 이유다. 표면은 매번 다르지만 구조는 하나다.

**방어도 하나로 수렴한다.** 12.10절이 이 결함의 방어를 이 절의 소관으로 미뤘다. 답은 세 겹이다. 첫째, **정규화를 끝낸 뒤에 검증한다** — 7.7.5절이 세운 유일한 올바른 순서다. 검증 후 추가 디코딩이 일어나면 검증이 무의미해진다. 둘째, **경로상의 각 층이 같은 규칙으로 디코딩하도록 강제하거나, 층 사이에 데이터가 넘어갈 때 그것을 다시 불신한다** — 31.2.3절이 공유 컴포넌트에 대해 세운 원칙과 같다. 셋째, 근본적으로는 **도메인 프리미티브로 인코딩을 구조적으로 다뤄**, 값이 층을 넘을 때마다 그 의미가 재해석될 여지를 없앤다(→ 44.1). 경계에서 문자열을 걸러내는 필터는 원리적으로 우회되지만, 값을 받는 코드가 그 값을 신뢰하지 않으면 우회할 틈이 없다.

> **이 절이 뒷받침하는 것**
>
> - 인코딩·정규화의 원리와 정규화 후 검증 → **7.7** (오버롱 UTF-8·이중 디코딩·정규화 순서)
> - 경로 순회 우회의 파일시스템 변형 → **28.3** (같은 원리의 파일 경로 맥락)
> - 파싱 불일치라는 같은 구조 → **13.12** (중간자 버전), **5.6** (각 파서가 같은 바이트를 다르게 읽음)
> - 값을 신뢰하지 않는 코드 → **44.1** (도메인 프리미티브로 인코딩을 구조화)

## 31.8 웹 서버 결함 찾기와 소프트웨어 강화

이 장의 앞 절들이 여러 웹 서버 결함의 구조를 봤다. 이 절은 그 결함들을 실무에서 **어떻게 찾고, 어떻게 막는가**를 다룬다. 25.6절의 서버 핑거프린팅이 이 절의 입력이 되고, 12.6·12.10절의 서버 강화가 이 절과 짝을 이룬다.

### 31.8.1 웹 서버 결함 찾기

운이 좋다면 표적 웹 서버가 이 장에 서술된 실제 취약점 중 일부를 담고 있을 수 있다. 그러나 대개는 최신 수준으로 패치되어 있어, 서버를 공격할 상당히 최신이거나 새로운 것을 찾아야 한다.

**출발점은 자동 스캔 도구다.** 웹 애플리케이션은 대개 맞춤 제작이지만, 웹 서버 배치는 거의 모두 수많은 다른 사람이 설치·설정한 것과 같은 제3자 소프트웨어를 쓴다. 이 상황에서 자동 스캐너는 조작된 요청을 대량으로 보내고 알려진 취약점의 시그니처를 감시함으로써 손쉬운 표적(low-hanging fruit)을 빠르게 찾는 데 효과적이다. Nessus 같은 무료 취약점 스캐너와 여러 상용 대안이 있다.

**그러나 스캔만으로는 부족하다.** 공격 대상 소프트웨어에 대해 직접 조사해야 한다. Security Focus, OSVDB, Bugtraq·Full Disclosure 메일링 리스트에서 표적에 아직 적용되지 않았을 최근 취약점의 세부를 찾는다. Exploit Database와 Metasploit을 늘 확인해 누군가 이미 대응 익스플로잇을 만들어 뒀는지 본다.

한 가지 주의할 지점이 있다. **일부 웹 애플리케이션 제품은 Apache나 Jetty 같은 오픈소스 웹 서버를 설치의 일부로 포함한다.** 이 번들 서버에 대한 보안 갱신은 더 느리게 적용될 수 있다. 관리자가 그 서버를 자기 책임인 인프라가 아니라 설치된 애플리케이션의 일부로 보기 때문이다. 벤더 패치를 기다리지 않고 직접 갱신하면 지원 계약이 무효가 되기 쉽다는 점도 지연 요인이다. 그래서 이 소프트웨어에 대한 수동 테스트와 조사가 자동 스캐너가 놓치는 결함을 찾는 데 매우 효과적일 수 있다. 가능하면 공격 대상 소프트웨어를 로컬에 설치해 직접 테스트함으로써 아직 발견·유포되지 않은 새 취약점을 찾는 것도 방법이다.

### 31.8.2 웹 서버 소프트웨어 강화

제3자 웹 서버 제품을 배치하는 조직은 어느 정도 그 운명을 소프트웨어 벤더의 손에 맡기게 된다. 그럼에도 보안을 의식하는 조직은 이 장에 서술된 소프트웨어 취약점으로부터 자신을 지키기 위해 많은 것을 할 수 있다. WAHH가 드는 강화책을 정리한다. 12.10절의 소프트웨어 강화 목록과 같은 근거이므로, 여기서는 이 장의 맥락에서 재확인한다.

- **track record가 좋은 소프트웨어를 고른다.** 제품마다 심각한 취약점의 양, 벤더의 해결 속도, 배포된 수정이 이후 연구자의 테스트를 견디는 정도가 크게 다르다. 선택 전에 최근 이력을 조사한다.
- **벤더 패치를 적용한다.** 패치가 나오는 즉시 유능한 리버스 엔지니어가 그것이 고친 문제를 짚어내 익스플로잇을 개발할 수 있다. 그러므로 가능한 한 빨리 적용한다.
- **보안 강화를 수행한다.** 필요 없는 기본 기능(예: 기본 ISAPI 확장)을 끄고, 남긴 기능은 업무 요구에 맞는 한 가장 제한적으로 설정한다. 매핑된 파일 확장자·웹 서버 모듈·데이터베이스 컴포넌트를 제거하고, IIS Lockdown 같은 도구를 쓴다. **애플리케이션이 네이티브 코드로 개발된 커스텀 서버 확장을 포함한다면, 그것을 관리 코드로 다시 쓰는 것을 고려한다.** 그럴 수 없다면 관리 코드 환경에서 그 함수로 넘기기 전에 추가 입력 검증을 수행한다(31.4~31.6절의 네이티브 결함에 대한 직접적 완화다). 남겨야 하는 함수·리소스를 기본 이름에서 바꿔 최소한의 장벽을 더한다. 최소 권한 원칙을 스택 전체에 적용해, 웹 서버 프로세스를 가능한 한 약한 OS 계정으로 돌리고, Unix에서는 chroot 환경으로 침해의 영향을 가둔다.
- **새 취약점을 모니터링한다.** 조직의 누군가가 Bugtraq·Full Disclosure를 추적해 쓰는 소프트웨어의 새 취약점 논의를 파악한다. 기술적 세부를 알면 벤더의 정식 수정 전에 효과적인 임시 우회책을 마련할 수 있다.
- **심층 방어를 쓴다.** 웹 서버가 완전히 침해돼도 대응 시간을 벌도록 층을 쌓는다. 애플리케이션의 DB 계정에 감사 로그 테이블에 대한 `INSERT` 권한만 주면, 서버를 침해한 공격자도 이미 생성된 로그를 지울 수 없다. 서버 트래픽에 엄격한 네트워크 계층 필터를 걸고, IDS로 침해 후의 이상 활동 — 인터넷으로의 역방향 커넥션 시도, DMZ 스캔 — 을 실시간 탐지한다.

이 강화책들이 **막지 못하는 것**을 분명히 하는 것도 중요하다. 12.11절이 판정한 대로, 웹 애플리케이션 방화벽은 강하게 커스터마이즈된 규칙 없이는 이 장의 결함 대부분을 막지 못한다. 그리고 이 절의 강화가 하는 일은 침해를 **불가능하게** 만드는 것이 아니라 **국지화**하는 것이다. 완전한 침해가 일어나도 조직이 데이터 손실 전에 사고에 대응할 시간을 벌어 주는 것이 목표다.

이 심층 방어의 사고가 배포·운영 층위로 확장되면 46장의 주제가 된다. **엔터프라이즈 보안의 3R** — 회전(rotate), 재포장(repave), 수리(repair) — 는 이 절의 "침해를 국지화하고 대응 시간을 번다"를 클라우드 인프라의 운영 원리로 정식화한다(→ 46.7). 서버를 강화하는 것을 넘어, 서버가 침해됐다고 가정하고 주기적으로 자격증명을 회전하고 인프라를 알려진 좋은 상태로 재포장하는 것이다.

> **이 절이 뒷받침하는 것**
>
> - 서버 핑거프린팅으로 얻은 버전이 취약점 검색의 입력 → **25.6** (사용 기술 식별)
> - 서버 설정 강화와 소프트웨어 강화 → **12.6** (취약한 서버 설정), **12.10** (취약한 서버 소프트웨어)
> - 침해 국지화의 운영 원리화 → **46.7** (3R: 회전·재포장·수리), **46장** (클라우드 사고와 배포 파이프라인)
> - WAF가 이 결함들에 무력한 이유 → **12.11** (WAF의 역할과 한계)

## 31.9 복잡도 축소가 곧 방어다 — 부분 불변 엔티티, 상태 객체, 스냅샷, 엔티티 릴레이 예고

이 절은 Part VI 전체를 닫는다. 그래서 이 절의 임무는 두 가지다. 하나는 앞의 일곱 장이 무엇이었는지를 하나의 문장으로 정리하는 것이고, 다른 하나는 그 정리가 Part IX에서 어떤 설계로 답을 얻는지를 예고하는 것이다.

### 31.9.1 서버 측 공격 표면은 결국 복잡도였다

Part VI를 되짚어 보자. 25장은 공격 표면을 매핑했다 — 표면이 크다는 것이 문제의 출발이었다. 26장은 클라이언트 통제가 서버에서 재검증되지 않는 틈을 팠고, 27·28장은 데이터가 SQL·명령·경로·XML로 층을 넘을 때 그 의미가 바뀌는 틈을 팠다. 29장은 정상적인 값들의 잘못된 조합 — 상태가 너무 많아 설계자가 다 셈하지 못한 것 — 을 팠고, 30장은 실패의 순간에 내부 상태가 밖으로 새는 틈을 팠다. 그리고 이 장은 계층이 서로를 신뢰하는 틈, 테넌트가 인프라를 공유하는 틈, 프레임워크와 서버 소프트웨어의 여러 층이 같은 입력을 다르게 읽는 틈을 팠다.

**이 모든 틈에는 공통된 원천이 있다. 복잡도다.** 계층이 많을수록 신뢰 관계가 많아지고, 컴포넌트가 많을수록 파싱 불일치의 지점이 많아지며, 상태가 많을수록 처리되지 않은 전이가 많아진다. 공격 표면이란 결국 **시스템이 관리하지 못하는 복잡도의 총량**이다. 30장이 "실패는 예외적이지 않다"고 했고 29장이 "얕은 모델이 로직 결함을 만든다"고 했다. 두 문장이 겨눈 것은 하나다 — 시스템이 자기 상태의 복잡도를 감당하지 못할 때 보안이 무너진다는 것이다.

Secure by Design은 이것을 정면으로 다룬다. **가변 상태(mutable state)가 제대로 다뤄지지 않으면 나쁜 일이 생긴다.** 그리고 엔티티가 복잡해질수록 — 특히 상태가 많고 그 사이 전이가 복잡할수록 — 상태를 통제된 채로 유지하기가 어려워진다. 게다가 두 에이전트가 같은 엔티티를 동시에 바꾸려 하면(기술적으로는 두 스레드가 같은 객체를 동시에 바꾸는 것) 문제가 생긴다. 29장이 든 경쟁 조건이 바로 이것이었다. 잔액이 $100인 계좌에서 $75 인출과 $50 이체가 동시에 일어나면, 둘 다 잔액 검사를 통과한 뒤 최종 잔액이 음수가 된다. **동시성이 검사를 무의미하게 만든 것이다.**

### 31.9.2 복잡도를 줄이는 네 가지 설계 — 44.10 예고

Secure by Design은 이 복잡도를 관리 가능하게 줄이는 네 가지 패턴을 제시한다. 44.10절이 이것들을 상세히 다룬다. 여기서는 그 예고로서 각각이 무엇을 줄이는지만 스케치한다.

**첫째, 부분 불변 엔티티(partially immutable entity).** 무언가가 가변이면 코드의 다른 부분이 그것을 바꿀 위험이 있고, 바뀌면 원치 않는 방식으로 바뀔 위험이 있다. **움직이는 부품이 위험하다면, 움직이는 부품의 수를 줄이는 것이 이치에 맞는다.** 엔티티의 각 부분을 보며 "이 부분이 정말 바뀌어야 하는가?"를 묻는다. 주문의 고객 ID는 바뀔 필요가 없다 — 한 고객의 장바구니가 왜 갑자기 다른 고객에게 넘어가야 하는가? 결제됐으나 아직 배송되지 않은 주문의 고객 ID를 공격자가 그 순간에 바꿀 수 있다면, 그는 주문을 사실상 납치한 것이다. 고객 ID를 `private final`로 만들어 생성자에서 한 번 설정되고 이후 바뀌지 않게 하면, **컴파일러가 무결성을 강제한다.** 속성을 바꾸려는 시도는 런타임에 이르지 못하고 컴파일 시점에 잡힌다.

**둘째, 엔티티 상태 객체(entity state object).** 엔티티를 다루기 어렵게 만드는 것은 모든 동작이 모든 상태에서 허용되지는 않는다는 사실이다. 미혼 상태에서는 결혼할 수 있지만 이혼할 수 없고, 기혼 상태에서는 그 반대다. 소프트웨어가 이 상태 규칙을 지키게 하지 못하면 보안 문제 — 예컨대 결제 없이 상품을 내주는 서점 — 가 생긴다. **상태 규칙이 아예 설계되지 않았거나, 불완전하거나, 깨진 것은 규모 있는 코드베이스 거의 모두에서 자주 마주치는 문제다.** 이것이 29장이 "얕은 모델"이라 부른 것의 상태 버전이다. 상태 전이를 명시적 객체로 포착하면 어떤 상태가 가능한지 파악하기 쉬워진다.

**셋째, 엔티티 스냅샷(entity snapshot).** 앞의 두 패턴이 단일 스레드 환경을 위한 것이라면, 스냅샷은 다중 스레드 환경 — 같은 엔티티 인스턴스가 여러 스레드에서 접근되는 — 을 위한 것이다. 고성능이 필요해 데이터베이스 왕복을 피하고 엔티티를 공유 캐시(Memcached 등)에 두는 상황이다. `synchronized` 키워드를 잔뜩 붙이면 스레드들이 서로를 기다려 처리량이 급감하고 교착 상태의 위험까지 생긴다. 대신 엔티티를 **불변 스냅샷**으로 표현한다. 읽기 시나리오는 불변 스냅샷에만 접근하므로 변경 메서드를 호출할 수 없고, 변경 권한을 가진 클라이언트만 갱신용 도메인 서비스에 접근한다. 이로써 스냅샷은 **가용성과 무결성을 동시에** 지원한다 — 30장이 다룬 가용성 설계와 이어지는 지점이다.

**넷째, 엔티티 릴레이(entity relay).** 엔티티가 아주 많은 상태를 가질 때 — 10개를 넘으면 다루기 어색해진다 — 복잡한 상태 그래프를 **엔티티 체인**으로 쪼갠다. 온라인 서점의 주문이 처음엔 "접수"와 "배송" 두 상태로 시작했다가, 오랜 세월의 작은 수정들이 쌓여 얽힌 실타래 같은 그래프가 된 경우다. 릴레이는 상태 그래프를 **국면(phase)**으로 나눈다. 한 국면이 끝나면 다시 이전 국면으로 돌아가지 않는다는 성질을 이용해, 각 국면을 별개의 엔티티로 만들고 릴레이 경주의 바통처럼 다음 엔티티에 넘긴다. 예비 주문이 결제되면 확정 주문이 되고, 다시 예비 주문으로 돌아갈 길은 없다. **한 엔티티가 끝나면 그것으로 끝이라는 단순함**이 릴레이의 힘이다.

**표 31-4. 복잡도를 줄이는 네 패턴과 그것이 다루는 보안 관심사 (SBD 7장 표 7.1 기준)**

| 패턴 | 목적 | 보안 관심사 |
|---|---|---|
| **부분 불변 엔티티** | 바뀔 필요 없는 부분을 잠근다 | 무결성 |
| **엔티티 상태 객체** | 엔티티가 가질 수 있는 상태를 파악하기 쉽게 한다 | 무결성 |
| **엔티티 스냅샷** | 잠금을 피해 높은 처리량과 빠른 응답을 지원한다 | 가용성, 무결성 |
| **엔티티 릴레이** | 크고 복잡한 상태 그래프를 다루기 쉽게 한다 | 무결성 |

### 31.9.3 복잡도가 감당 못할 지경이면 설계 테이블로

엔티티 릴레이에는 조건이 있다. 상태가 10개를 넘고, 이전 국면으로 돌아가지 않으며, 국면 전이가 단순하고 전이점이 적을(가급적 하나일) 때만 값이 있다. 만약 상태 그래프가 어느 방향으로든 얽힌 실타래라면, **릴레이로 그것을 풀려 하지 말라.** 어떤 노력으로도 엉망은 엉망으로 남는다. 몇 가닥 당긴다고 나아지지 않는다.

그럴 때 SBD가 권하는 것은 모델을 설계 테이블로 되가져가 도메인 전문가와 함께 따져 보는 것이다. **이 모델이 이렇게 복잡한 진짜 동인은 무엇인가? 그 복잡도가 정말 필요한가? 각 복잡도에 타당한 업무 동인이 있는가? 그 동인이 그렇게 값진 나머지, 이런 복잡도와 어쩌면 안전하지 않은 시스템의 비용을 정당화하는가?** 이 질문들이 이 절의, 그리고 Part VI 전체의 결론을 담는다. **복잡도는 공짜가 아니다. 감당하지 못하는 복잡도는 곧 공격 표면이다.** 앞의 일곱 장이 그 표면의 여러 얼굴을 보였다면, 이 네 패턴은 표면을 줄이는 설계의 시작이다.

이것이 Part VI에서 Part IX로 가는 다리다. Part VI가 "서버 측에서 무엇이 깨지는가"를 전수 조사했다면, Part IX는 "왜 같은 것이 계속 깨지는가"에 답한다. 41장이 왜 설계가 보안을 결정하는지를 세우고, 42장이 얕은 모델을 깊은 모델로 바꾸며, 43장이 불변성과 계약과 검증을 코드 구조로 세우고, 44장이 도메인 프리미티브와 상태 무결성 — 이 절이 예고한 네 패턴을 포함해 — 을 완성한다. 이 절에서 우리는 복잡도가 곧 방어의 대상임을 선언했다. 그 방어를 코드로 표현하는 법이 Part IX의 주제다.

> - 경쟁 조건과 동시성이 검사를 무의미하게 만드는 것 → **29.2** (로직 결함), **45장** (가용성 설계)

> - 값을 신뢰하지 않는 코드로의 전환 → **41장** (설계에 의한 방어)

## 이 장의 요약

- **계층 아키텍처 공격은 세 범주로 나뉜다.** 신뢰 관계를 타고 전진하기, 다른 계층을 밑에서 무력화하기, 인프라를 직접 공격해 확장하기. 공격자의 방법론은 두 원칙으로 압축된다 — 어떤 사소한 결함이든 상상력으로 지렛대질하고, 명령 실행을 얻으면 인프라로 확장하라. (15.10이 배치 형태를, 이 장이 방법론을 다룬다.)
- **공유 호스팅·ASP 환경에서 공격자의 초점은 공유 환경 그 자체다.** 접근 메커니즘을 조사하고, 맞춤 관리 애플리케이션을 표적으로 삼고, 한 애플리케이션의 침해를 다른 애플리케이션으로 확장한다. `phpinfo()`로 환경을 지도화하고 safe mode의 설정과 우회로를 점검한다.
- **PHP safe mode는 구조적으로 잘못된 자리의 방어다.** 운영체제가 애플리케이션 계층더러 자기 행동을 통제하라고 신뢰하기 때문이며, 우회에 취약해 PHP 6에서 제거됐다. 격리는 대상보다 아래에 있는 층에서 강제되어야 한다.
- **프레임워크 하나의 결함은 그 위의 수많은 애플리케이션을 한꺼번에 취약하게 만든다.** .NET 패딩 오라클은 "패딩이 틀리면 500 오류"라는 한 비트의 정보 노출이 암호 시스템 전체를 복호화·암호화하는 오라클이 됨을 보인 사례다.
- **버퍼 오버플로·정수 취약점·포맷 스트링은 길이·경계·값의 해석에 관한 가정이 무너질 때 성립한다.** 스택 오버플로는 복귀 주소를, 힙 오버플로는 제어 구조를 덮어쓴다. off-by-one은 크래시 없이도 널 종결자 손실로 다른 사용자의 데이터를 노출할 수 있다.
- **이 네이티브 결함들은 탐지 자체가 DoS를 부른다.** 긴 문자열·경계값·포맷 지정자를 보내 이상을 관찰하는 탐지 방법론은 표적에 처리되지 않은 예외를 일으키기 쉬우므로, 살아 있는 애플리케이션에서는 소유자의 위험 수용이 전제되어야 한다.
- **인코딩·정규화 결함은 파싱 불일치의 서버 내부 버전이다.** IIS 유니코드·이중 인코딩 순회, PL/SQL 제외 목록 우회는 모두 앞단 필터가 검사하는 형태와 뒷단 처리가 되돌리는 형태 사이의 틈에서 나온다. 13.12의 중간자 불일치와 같은 구조이며, 방어는 정규화 후 검증(7.7.5)과 도메인 프리미티브(44.1)로 수렴한다.
- **웹 서버 결함은 자동 스캔과 수동 조사를 병행해 찾고, 강화로 침해를 국지화한다.** 번들 오픈소스 서버의 패치 지연에 주의하고, 강화의 목표는 침해를 불가능하게 하는 것이 아니라 대응 시간을 버는 것이다(→ 46.7의 3R).
- **서버 측 공격 표면은 결국 복잡도였다.** 계층이 많을수록 신뢰 관계가, 컴포넌트가 많을수록 파싱 불일치가, 상태가 많을수록 처리되지 않은 전이가 늘어난다. 복잡도를 줄이는 네 패턴 — 부분 불변 엔티티·상태 객체·스냅샷·릴레이 — 이 44.10에서 상세히 다뤄진다.

## 이어지는 장

이 장으로 Part VI가 닫힌다. 서버 측 공격 표면 — 기술 매핑, 클라이언트 통제 우회, 데이터 저장소·백엔드 주입, 로직 결함, 정보 노출, 그리고 이 장의 아키텍처·프레임워크·네이티브 코드 — 을 일곱 장에 걸쳐 전수 조사했다. 마지막 절이 그 모든 것을 하나의 단어로 묶었다. 복잡도다.

Part VII는 시선을 반대편으로 돌린다. 지금까지 공격 표면은 서버였다. 다음 부에서 그것은 **클라이언트** — 브라우저와 그 실행 환경 — 가 된다. 크로스 사이트 스크립팅, 요청 위조, 그리고 동일 출처 정책을 축으로 한 브라우저 네트워킹의 공격 표면이다. 이 장 31.4~31.6이 다룬 네이티브 코드 결함은 서버 측의 드문 사례였지만, 26.6절이 다룬 네이티브 클라이언트 컴포넌트에서 같은 결함이 클라이언트 측에 나타났음을 상기하면, 공격 표면의 이동이 결함의 소멸을 뜻하지 않음을 알 수 있다. 표면이 옮겨 갈 뿐 구조는 되풀이된다.

그리고 이 장이 예고한 설계의 답 — 복잡도를 줄이는 네 패턴 — 은 Part IX가 완성한다. 44장이 그 패턴들을 코드로 세울 때, 그것들이 겨냥하는 것은 이 장이 조사한 서버 측 공격 표면만이 아니라 Part VII의 클라이언트 측 표면과 Part VIII의 API 표면까지다. 복잡도는 어느 표면에서든 같은 방식으로 방어의 대상이 되기 때문이다.

> 31.9절: Secure by Design 7장 "Reducing complexity of state"를 근거로 한다. 가변 상태가 제대로 다뤄지지 않으면 생기는 문제, 복잡한 상태·전이와 동시성(두 스레드가 같은 엔티티를 바꿀 때)의 어려움, 잔액 검사를 무의미하게 만드는 경쟁 조건 예시($100 계좌의 $75 인출과 $50 이체), 네 패턴(부분 불변 엔티티의 `private final` 고객 ID와 주문 납치, 상태 객체와 미혼·기혼 상태 규칙, 스냅샷과 다중 스레드·읽기/쓰기 권한 분리, 릴레이와 국면 분할·예비→확정 주문), 표 31-4(SBD 표 7.1), 릴레이의 세 조건(10개 초과 상태·되돌아가지 않는 국면·단순한 전이점)과 얽힌 실타래는 설계 테이블로 가져가라는 조언, 네 개의 설계 질문은 원서와 동일하다. 온라인 서점 주문 예시는 SBD 원서의 것이다. 이 절이 Part VI 전체를 복잡도로 정리하고 44.10을 예고하는 구성은 집필지침 §3(31.9는 Part VI를 닫는 절)에 따른 것이며, 네 패턴의 상세와 코드는 44.10절이 다룬다.
