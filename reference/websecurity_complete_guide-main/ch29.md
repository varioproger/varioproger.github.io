# 29장. 애플리케이션 로직 결함

> **이 장에서 다루는 것**
>
> - 로직 결함에 왜 공통 시그니처가 없는지, 그래서 왜 스캐너와 정규 침투 테스트가 이것을 놓치는지
> - 실제로 발견된 열두 개의 로직 결함을 "무엇을 가정했는가 → 그 가정이 어떻게 깨지는가"의 형태로 해부하는 법
> - 기술적으로 아무것도 깨지지 않은 채 회사가 돈을 잃는 방식 — 비즈니스 무결성이라는 개념
> - 여러 시스템이 서로 **일관되게 거짓말할 때** 어떤 보고서도 이상을 감지하지 못한다는 사실
> - 로직 결함의 상당수가 왜 "얕은 모델"이라는 하나의 원인으로 수렴하는지

27장과 28장이 다룬 결함에는 공통점이 있었다. 사용자가 보낸 바이트가 어떤 인터프리터의 문법 안으로 들어가 데이터에서 코드로 승격되는 순간이 있었고, 그 순간은 SQL 파서든 셸이든 XML 파서든 **기계적으로 재현 가능한 형태**로 존재했다. 그래서 그 결함들에는 시그니처가 있다. 작은따옴표 하나를 넣고 오류가 나는지 보는 것으로 SQL 인젝션의 존재를 추정할 수 있고, 그 추정은 대체로 맞는다.

이 장의 결함에는 그런 것이 없다. 문법은 하나도 깨지지 않는다. 요청은 전부 정상적인 HTTP 요청이고, 파라미터 값은 전부 애플리케이션이 기대하는 타입이며, 데이터베이스는 아무 오류도 뱉지 않는다. 그런데 서점이 고객에게 돈을 보내고, 보험사가 보험료를 받지 않은 사람에게 유효한 증서를 우편으로 부친다. 애플리케이션은 **설계된 대로 정확히 동작하면서** 회사에 손해를 입힌다.

이 장은 이 책에서 WAHH와 SBD가 정면으로 만나는 자리다. 앞의 두 절(29.1~29.2)은 공격자의 관점이다. 로직 결함이란 무엇이며, 그것을 어떻게 찾아내는가. 실제로 발견된 열두 개의 사례를 "설계자가 무엇을 가정했는가"라는 하나의 틀로 해부한다. 뒤의 세 절(29.3~29.5)은 설계자의 관점이다. 같은 종류의 결함을 **왜 그런 코드가 쓰였는가**의 방향에서 되짚는다. 그리고 29.6이 두 관점을 잇는다. 열두 개의 사례가 왜 생겼는지를, 온라인 서점과 보험사의 사례가 남긴 개념 — 얕은 모델과 암묵적 개념 — 으로 다시 읽는다.

이 순서에는 이유가 있다. 로직 결함을 사례의 목록으로만 배우면 얻는 것은 체크리스트뿐이다. 체크리스트는 이미 알려진 열두 가지를 다시 찾는 데는 쓸모가 있지만, 열세 번째를 찾는 데는 쓸모가 없다. 로직 결함의 정의상 열세 번째는 앞의 열둘과 닮지 않았을 것이기 때문이다. 이 장이 목표하는 것은 열세 번째를 만들지 않는 방법이고, 그 답은 사례가 아니라 모델에 있다.

## 29.1 로직 결함의 본질 — 왜 스캐너가 찾지 못하는가

로직 결함(logic flaw)이란 애플리케이션이 구현한 논리 자체가 결함이 있는 경우를 말한다. 정의가 이렇게 넓은 것은 이 부류에 공통 형태가 없기 때문이다. 몇 줄짜리 코드에 들어 있는 단순한 버그일 수도 있고, 서로 다른 팀이 만든 여러 핵심 컴포넌트가 상호작용하는 방식에서만 나타나는 복합적 취약점일 수도 있다. 어떤 것은 화면을 한 번 보면 드러나고, 어떤 것은 가장 엄격한 코드 리뷰와 침투 테스트도 통과한다.

### 결함을 가정으로 환원하기

형태가 제각각인 이 부류를 다루려면 하나의 환원 장치가 필요하다. WAHH가 제시하는 장치는 이것이다. **대부분의 로직 결함은 설계자나 개발자가 명시적으로 혹은 암묵적으로 세운 하나의 가정으로 환원된다.**

프로그래머의 머릿속에서 일어난 추론은 대개 이런 모양이다.

> A가 일어나면 B일 수밖에 없다. 그러니 C를 하자.

이 추론 자체는 틀리지 않았을 수 있다. 문제는 그가 **묻지 않은 질문**에 있다.

> 그런데 X가 일어나면?

X는 A와 B 사이의 함의를 깨뜨리는 사건이다. 그 사건을 상상하지 못했기 때문에 그것을 처리하는 코드 경로도 존재하지 않는다. 로직 결함을 찾는다는 것은 결국 이 X를 찾는 일이다. 그리고 X를 찾으려면 먼저 A와 B, 즉 **개발자가 무엇을 당연하게 여겼는지**를 재구성해야 한다.

이것이 로직 결함 탐색이 다른 취약점 탐색과 근본적으로 다른 이유다. SQL 인젝션을 찾을 때 우리는 코드를 읽지 않고도 페이로드를 던질 수 있다. 로직 결함을 찾을 때 우리가 하는 일은 페이로드를 던지는 것이 아니라 **개발자의 머릿속으로 들어가는 것**이다. 마감에 쫓기며, 보안이 아니라 기능을 걱정하고, 남이 쓴 문서 없는 API 위에 새 기능을 얹고 있는 사람이 무엇을 놓쳤을지 상상하는 일이다.

### 왜 자동 도구가 실패하는가

**표 29-1. 인젝션 계열 결함과 로직 결함의 탐지 특성 비교**

| 항목 | 인젝션 계열 (27~28장) | 로직 결함 (이 장) |
|---|---|---|
| 공통 시그니처 | 있다 — 메타문자, 오류 메시지, 시간 지연 | 없다 |
| 판정 기준 | 인터프리터의 문법 위반 여부 | 비즈니스 규칙 위반 여부 |
| 정상 응답과의 구분 | 응답이 비정상(오류·지연·구조 변화) | 응답이 완전히 정상 |
| 자동 스캐너 | 상당수 탐지 가능 | 거의 탐지 불가 |
| 필요한 사전 지식 | 대상 인터프리터의 문법 | 대상 **업무 도메인**의 규칙 |
| 재현성 | 결정적(deterministic) | 다단계·상태 의존, 때로 비결정적 |
| 발견 방식 | 체계적 퍼징 | 체계적 탐침 + 측면적 사고 |

취약점 스캐너가 로직 결함을 찾지 못하는 이유는 도구가 게을러서가 아니라 **판정 기준을 도구가 알 수 없기 때문**이다. 스캐너는 응답을 보고 "이것이 비정상인가"를 판정한다. 하지만 수량 `-1`인 주문이 정상 처리되고 200 응답이 돌아왔을 때, 그 응답의 어느 바이트도 비정상이 아니다. 비정상인 것은 응답이 아니라 **"서점은 손님에게 책값을 지불하지 않는다"는 업무 규칙**이며, 그 규칙은 HTTP 어디에도 적혀 있지 않다.

같은 이유로 코드 감사 도구도 실패한다. 정적 분석기는 `amount <= threshold`라는 비교식을 보고 아무 경고도 내지 않는다. 이 비교식에는 문법적 결함도, 위험한 API 호출도 없다. 결함은 "amount가 음수일 수 있다"는 사실과 "음수 이체는 반대 방향 양수 이체로 처리된다"는 별개 모듈의 동작이 만나는 지점에 있고, 그 지점은 어떤 파일에도 적혀 있지 않다.

그래서 보안 인식이 높아지면서 XSS와 SQL 인젝션의 발생률이 눈에 띄게 떨어진 지난 몇 년 동안에도 로직 결함은 줄지 않았다. 안전한 개발 표준, 코드 감사 도구, 정규 침투 테스트 중 어느 것도 이 부류를 겨냥하지 못한다. 진지한 공격자가 로직에 주목하는 이유가 여기에 있다. 남들이 이미 훑고 지나간 표면 아래에, 아무도 자동으로 훑을 수 없는 표면이 그대로 남아 있다.

### 기본 탐침 세 가지

로직 결함 전체를 잡는 만능 절차는 없지만, 개발자의 가정을 흔들어 보는 데 반복적으로 유효한 조작이 셋 있다. 29.2절의 열두 사례 중 절반 이상이 이 셋 중 하나로 드러난다.

**첫째, 파라미터를 제거한다.** 값을 바꾸는 것이 아니라 **이름째로 지운다.** 쿠키, 쿼리 스트링, POST 본문의 항목을 하나씩 차례로 없앤다. 빈 문자열을 보내는 것과는 다르다. 서버 측 코드에서 `getParameter("x")`가 `null`을 반환하는 경로와 빈 문자열을 반환하는 경로는 대개 다르고, 결함은 `null` 쪽에 있다. 한 번에 하나씩만 지워야 모든 코드 경로에 도달한다.

**둘째, 순서를 어긴다.** 다단계 기능을 정해진 순서 밖으로 접근한다. 단계를 건너뛰고, 같은 단계를 두 번 밟고, 나중 단계 뒤에 앞 단계로 되돌아간다. 이것을 **강제 브라우징(forced browsing)** 이라 부른다. 브라우저의 링크와 폼이 부과하는 항해 순서는 서버가 강제하는 순서가 아니다(→ 6.7). 순서를 어기면 초기화되지 않은 변수, 부분적으로만 정의된 상태, 예상하지 못한 오류 메시지가 튀어나오고, 그 자체가 다음 공격의 정보가 된다(→ 30.1).

**셋째, 파라미터를 다른 곳으로 옮긴다.** 한 단계에서 제출되는 파라미터를 다른 단계에 제출한다. 한 종류의 사용자가 제출하는 파라미터를 다른 종류의 사용자로서 제출한다. 애플리케이션의 상태가 그 값으로 갱신된다면, 그 갱신이 다른 기능에 어떤 파급을 일으키는지를 추적한다.

이 세 조작의 공통점은 **브라우저가 제시한 인터페이스가 곧 서버가 받아들이는 인터페이스라는 가정**을 겨냥한다는 것이다. 26장이 클라이언트 측 통제 전반에 대해 말한 것을 로직의 층위에서 되풀이하는 셈이다. 다만 26장의 조작이 "값을 바꿀 수 있다"였다면, 여기서는 "요청의 **형태 자체**를 바꿀 수 있다"가 된다.

> **이 절이 뒷받침하는 것**
>
> - 사용자가 요청의 모든 측면을 통제한다는 전제 → **6.7** (핵심 보안 문제), **26.1** (클라이언트를 통한 데이터 전달)
> - 강제 브라우징으로 드러나는 다단계 기능의 접근 통제 공백 → **24.1** (다단계 기능), **24.3** (다단계 프로세스 테스트)
> - 순서 위반이 유도하는 비정상 상태와 그 오류 출력 → **30.1** (오류 메시지 익스플로잇)
> - 로직 결함을 체계적으로 훑는 절차 → **부록 A.10** (로직 결함 테스트)

## 29.2 실제 로직 결함 12선 해부

이론으로 배울 수 없는 것을 사례로 배운다. 아래 열두 개는 실제 애플리케이션에서 발견된 결함이며, 각각 다른 종류의 논리적 결점을 드러낸다. 개별 사례는 서로 전혀 닮지 않았지만, 하나의 틀로 읽으면 공통 주제가 보인다.

각 사례를 네 부분으로 나눠 본다.

1. **기능의 의도** — 이 코드는 무엇을 하려고 만들어졌는가
2. **가정** — 그것이 동작하려면 무엇이 참이어야 한다고 믿었는가
3. **가정이 깨지는 방식** — 공격자가 그 믿음을 어떻게 위반하는가
4. **교훈** — 이 결함이 남기는 일반화 가능한 원칙

실행 예제로 쓰는 도메인은 온라인 서점이다(→ 0.3). 서점 맥락으로 자연스럽게 옮겨지는 사례는 옮겼고, 은행 자금 이체나 보험 인수 심사처럼 옮기면 오히려 구조가 흐려지는 사례는 원래 맥락을 유지했다.

### 사례 1. 오라클에게 묻기

**기능의 의도.** 서점이 "로그인 상태 유지" 기능을 제공한다. 방문할 때마다 로그인하지 않아도 되도록 영구 쿠키를 심는데, 이 쿠키가 변조되거나 읽히면 안 되므로 암호화한다. 암호문의 평문은 이름·사용자 ID·재생 공격을 막기 위한 휘발성 데이터·클라이언트 IP 주소를 이어 붙인 문자열이다. 알고리즘은 Triple DES, 키는 충분히 강하다. 여기까지는 흠잡을 데가 없다.

같은 애플리케이션에 별도의 기능이 하나 더 있다. 사용자가 지정한 표시 이름(screen name)을 쿠키에 저장해 두었다가 화면 구석에 "환영합니다, ○○○님"을 띄우는 개인화 기능이다. 개발자들은 이 이름도 일종의 보안 정보라고 판단해 **같은 암호화 루틴**으로 보호했다.

**가정.** 표시 이름 쿠키는 로그인 유지 쿠키보다 가치가 낮으니 같은 알고리즘을 재사용해도 상관없다. 이 가정 안에 들어 있지 않은 사실이 하나 있다. **표시 이름은 사용자가 직접 정하고, 그 결과를 화면에서 눈으로 확인한다.**

**가정이 깨지는 방식.** 사용자에게 암호화 함수와 복호화 함수가 동시에 열린 셈이 된다. 먼저 복호화 방향이다. 로그인 유지 쿠키의 암호문을 표시 이름 쿠키 자리에 넣고 페이지를 연다. 애플리케이션은 그 값을 복호화하고, 복호화가 성공했음을 확인하고, 결과를 화면에 출력한다.

```
Welcome, marcus|734|192.168.4.2|82750184
```

이 자체로는 대단치 않다. 사용자명, 사용자 ID, IP 주소가 드러났을 뿐 비밀번호는 들어 있지 않다. 진짜 문제는 암호화 방향에 있다. 사용자가 자기 표시 이름을 이렇게 정한다.

```
admin|1|192.168.4.2|82750184
```

로그아웃했다가 다시 로그인하면 애플리케이션이 이 문자열을 **암호화해서** 표시 이름 쿠키로 브라우저에 넣어 준다. 그 암호문을 그대로 로그인 유지 쿠키 자리에 제출하면, 애플리케이션은 복호화하고 사용자 ID 1을 읽어 관리자로 로그인시킨다. 암호 알고리즘은 한 번도 깨지지 않았다. 애플리케이션 자신이 **암호화 오라클(encryption oracle)** 로 징발되었을 뿐이다.

**교훈.** 암호화된 값을 클라이언트에 보내는 지점, 클라이언트가 준 암호문을 복호화하는 지점을 모두 목록으로 만든다. 그리고 그 목록의 어느 두 항목이 **같은 키와 같은 알고리즘을 공유하는지** 확인한다. 공유한다면 한 항목의 암호문을 다른 항목 자리에 대입해 본다. 복호화 결과가 화면에 나오는 곳이 있으면 "오라클 노출"이고, 평문을 주면 대응 암호문을 돌려주는 곳이 있으면 "오라클 암호화"다. 두 방향이 같은 애플리케이션 안에 함께 있으면 그 암호화는 무의미하다. 계정 복구 토큰, 인증된 리소스에 대한 토큰 기반 접근, 그 밖에 클라이언트로 내려가는 모든 "변조 불가·판독 불가" 값이 같은 검사 대상이다(→ 23.2, 26.7).

### 사례 2. 비밀번호 변경 기능 속이기

**기능의 의도.** 서점 계정의 비밀번호 변경 기능이다. 일반 사용자는 사용자명, 기존 비밀번호, 새 비밀번호, 새 비밀번호 확인의 네 필드를 채운다. 별도로 관리자용 비밀번호 변경 기능도 있는데, 관리자는 기존 비밀번호를 모르는 상태에서 임의 사용자의 비밀번호를 바꿀 수 있어야 하므로 기존 비밀번호 필드가 없다. 두 기능은 **하나의 서버 측 스크립트**로 구현되어 있다.

**가정.** 두 인터페이스의 유일한 차이는 기존 비밀번호 필드의 유무다. 그래서 서버는 그 파라미터의 존재 여부로 요청자가 관리자인지 일반 사용자인지 판별한다. 즉 **일반 사용자는 언제나 기존 비밀번호 파라미터를 보낼 것**이라고 가정한다.

```java
String existingPassword = request.getParameter("existingPassword");
if (null == existingPassword) {
    trace("Old password not supplied, must be an administrator");
    return true;
} else {
    trace("Verifying user's old password");
    // ...
}
```

**가정이 깨지는 방식.** 가정을 이렇게 명시적으로 적어 놓으면 결함은 자명해진다. 일반 사용자도 그 파라미터가 없는 요청을 보낼 수 있다. 사용자는 자기가 보내는 요청의 모든 측면을 통제하기 때문이다. 값을 비워 보내는 것으로는 안 된다. `""`는 `null`이 아니고, 위 코드는 빈 문자열이면 `else` 가지로 간다. **이름째로 지워야** `null`이 되고, 그때 함수는 검증 없이 `true`를 반환한다. 임의 사용자의 비밀번호를 재설정하고 계정을 통째로 가져올 수 있다.

**교훈.** 이 결함이 29.1절의 첫 번째 탐침 — 파라미터를 이름째 제거하기 — 이 존재하는 이유다. 그리고 더 근본적인 교훈은 **파라미터의 존재 여부로 권한을 판별하지 말라**는 것이다. 사용자의 신원과 지위에 관한 모든 결정은 세션에서 끌어와야 하며, 요청의 다른 어떤 특징으로도 — 그 요청이 도착했다는 사실 자체를 포함해서 — 권한을 추론해서는 안 된다(→ 22.4, 24.2). 두 종류의 사용자를 한 스크립트로 처리하기로 한 결정 자체가 나쁜 것은 아니다. 나쁜 것은 그 스크립트가 **요청의 모양**을 역할의 증거로 삼은 것이다.

### 사례 3. 체크아웃으로 진행하기

**기능의 의도.** 서점의 주문 과정은 네 단계다.

```
1단계  도서 목록을 둘러보고 장바구니에 담는다
2단계  장바구니로 돌아와 주문을 확정한다
3단계  결제 정보를 입력한다
4단계  배송 정보를 입력한다
```

**가정.** 사용자는 언제나 의도된 순서로 각 단계에 접근한다. 브라우저에 제시되는 링크와 폼이 그 순서대로 이어져 있기 때문이다. 따라서 주문 과정을 완료한 사용자는 도중에 반드시 유효한 결제 정보를 제출했을 것이다.

**가정이 깨지는 방식.** 사용자는 자기가 보내는 모든 요청을 통제하므로 어떤 순서로든 어떤 단계에든 접근할 수 있다. 2단계에서 곧장 4단계로 건너뛰면 **결제되지 않았지만 배송 확정된 주문**이 만들어진다.

**교훈.** 접근 제어 취약점의 상당수가 이 로직 결함과 같은 구조다. 여러 단계로 이뤄진 권한 있는 기능에서 애플리케이션은 초기 단계에 엄격한 접근 통제를 걸고, 후반 단계에 도달한 사용자는 이미 인가를 통과한 것으로 간주한다. 낮은 권한의 사용자가 후반 단계로 직행하면 아무 제한 없이 접근한다(→ 24.1, 24.3). 다단계 프로세스에서 지켜야 할 원칙은 하나다. **각 단계는 자신이 전제하는 상태를 스스로 확인해야 한다.** "결제됨"이 주문의 명시적 상태로 존재하고 배송 단계가 그 상태를 검사한다면, 순서를 어기는 것으로는 아무 일도 일어나지 않는다. 이 결함이 29.6절에서 다시 등장하는 이유가 여기에 있다. 결함의 뿌리는 순서 검사의 부재가 아니라 **"주문의 상태"라는 개념이 모델에 없었다는 것**이다.

### 사례 4. 보험을 직접 만들기

**기능의 의도.** 금융 회사의 온라인 보험 가입 애플리케이션이다. 열두 단계에 걸쳐 진행된다. 첫 단계에서 가입 희망자가 기본 정보와 함께 **희망 월 보험료** 또는 **보장 금액** 중 하나를 지정하면, 애플리케이션이 나머지 하나를 계산해 견적을 제시한다. 이후 여러 단계에 걸쳐 건강 상태, 직업, 취미 등을 입력한다. 마지막으로 신청서가 보험사의 인수 심사역(underwriter)에게 전달되고, 심사역은 **같은 웹 애플리케이션**에서 내용을 검토해 원안대로 인수할지 추가 위험을 반영해 견적을 수정할지 결정한다.

모든 단계는 하나의 공유 컴포넌트를 거친다. 이 컴포넌트는 POST 본문의 모든 데이터를 이름/값 쌍으로 파싱해 상태 정보를 갱신한다.

**가정.** 각 요청에는 그 단계의 HTML 폼이 요구한 파라미터만 들어 있다. 개발자들은 사용자가 **요구되지 않은 파라미터를 보내면 어떻게 되는지**를 생각하지 않았다.

**가정이 깨지는 방식.** 세 갈래로 무너진다.

첫째, **서버 측 입력 검증이 통째로 우회된다.** 각 단계는 그 단계에서 기대되는 데이터에 대해 엄격한 검증을 수행하고 실패하면 거부한다. 그런데 공유 컴포넌트는 순서와 무관하게 모든 파라미터로 상태를 갱신한다. 앞 단계에서 기대되는 이름/값 쌍을 뒤 단계에서 제출하면 그 데이터는 **아무 검증도 거치지 않고** 받아들여진다. 실제로 이 경로를 통해 심사역을 겨냥한 저장형 XSS가 가능했고, 그것으로 다른 가입 희망자들의 개인 정보에 접근할 수 있었다(→ 32.6).

둘째, **임의의 가격으로 보험을 살 수 있다.** 첫 단계에서만 지정하기로 되어 있던 보험료와 보장 금액을 나중 단계에서 다시 보내면 상태가 그 값으로 갱신된다. 계산 로직은 첫 단계에서 이미 실행되었으므로 다시 돌지 않는다. 원하는 보장 금액과 원하는 월 보험료를 동시에 지정한 견적이 만들어진다.

셋째, **인수 심사 자체를 건너뛸 수 있다.** 어떤 종류의 사용자가 어떤 파라미터를 보낼 수 있는지에 대한 접근 통제가 없다. 심사역이 검토 시 갱신하는 항목 — 인수 승인 결정을 포함해 — 은 일반 사용자가 보낸 데이터와 똑같이 공유 컴포넌트가 처리한다. 파라미터 이름을 알거나 추측하면 자기 신청서를 스스로 승인할 수 있다.

**교훈.** 이 애플리케이션의 결함은 보안의 근간을 무너뜨리는 것이었지만, 브라우저 요청을 가로채 **값만** 바꿔 보는 공격자는 하나도 발견하지 못했을 것이다. 핵심 조작은 값의 변경이 아니라 **파라미터의 이동**이다. 한 단계의 파라미터를 다른 단계로 옮기고, 한 종류의 사용자의 파라미터를 다른 종류의 사용자로서 보낸다. 그리고 이 사례는 29.5절의 이야기와 짝을 이룬다. 그쪽에서는 보험 증서가 결제 없이 나가고, 여기서는 심사 없이 나간다. 둘 다 **"이 상태에 도달했다면 그 전 단계는 통과했을 것"** 이라는 같은 가정에서 나왔다.

### 사례 5. 은행 털기

**기능의 의도.** 대형 금융사의 온라인 뱅킹 애플리케이션에 온라인 서비스 신규 등록 기능이 있다. 기존 오프라인 고객이 온라인 접근을 처음 신청하는 절차다. 신청자는 이름, 주소, 생년월일 같은 기본 개인 정보를 입력한다. 여기에는 비밀번호나 PIN 같은 비밀은 포함되지 않는다. 정보가 맞으면 요청이 백엔드로 넘어가고, 고객의 **등록된 자택 주소로** 안내 우편이 발송된다. 우편에는 콜센터에 전화해 본인 확인을 거쳐 온라인 접근을 활성화하는 방법과 최초 로그인용 일회용 비밀번호가 들어 있다.

이 설계에는 세 겹의 방어가 있다. 남의 이름으로 장난치기 어렵게 하는 최소한의 개인 정보, 대역 외 채널(우편)로 전달되는 핵심 비밀, 그리고 콜센터에서의 재인증. 설계는 견고했다. 결함은 구현에 있었다.

**가정.** 등록 절차를 구현하는 개발자에게는 사용자가 제출한 개인 정보를 담아 두었다가 사내 데이터베이스의 고유 고객 번호와 대응시킬 자료구조가 필요했다. 기존 코드를 재사용하려던 그들은 마침 딱 맞아 보이는 클래스를 발견했다.

```java
class CCustomer {
    String   firstName;
    String   lastName;
    CDoB     dob;
    CAddress homeAddress;
    long     custNumber;
    // ...
}
```

정보를 받으면 이 객체를 만들어 채우고 **세션에 저장**한다. 애플리케이션이 정보를 검증하고, 유효하면 그 고객의 고유 번호를 조회해 객체에 채운 뒤 백엔드로 전달한다. 개발자들은 이 컴포넌트를 재사용하는 것이 무해하다고 가정했다.

**가정이 깨지는 방식.** 같은 클래스가 애플리케이션의 **핵심 기능부에서도** 쓰이고 있었다. 인증된 사용자가 계좌 상세, 거래 내역, 자금 이체에 접근할 때, 로그인에 성공한 시점에 같은 객체가 생성되어 세션에 저장되고, 대다수 기능이 이 객체의 정보를 참조해 동작한다. 메인 화면에 표시되는 계좌 정보도 이 객체 안의 고유 고객 번호를 근거로 만들어진다.

공격은 세 걸음이다.

```
1. 자신의 정상 자격증명으로 로그인한다.
2. 인증된 세션을 유지한 채 등록 기능에 접근해 다른 고객의 개인 정보를 제출한다.
   → 세션 안의 CCustomer 객체가 그 고객의 것으로 덮어써진다.
3. 핵심 기능부로 돌아가 그 고객의 계좌에 접근한다.
```

접근 통제는 여러 층에 걸려 있었고 모두 정상 동작했다. 공격자는 **완전히 인증된 세션**을 갖고 있었으므로 그 통제를 전부 통과한다. 통제가 검사한 것은 "이 세션이 인증되었는가"였고, 세션이 **누구의 것인지**는 그 객체가 결정했다.

**교훈.** 블랙박스 관점에서 탐지하기 어렵고, 소스 코드를 읽어도 알아채기 어려운 종류다. 애플리케이션 전체와 각 컴포넌트가 어디에서 어떻게 쓰이는지에 대한 그림 없이는 개발자의 잘못된 가정이 드러나지 않는다. 탐침 방법은 이렇다. 수평·수직 권한 분리가 있는 복잡한 애플리케이션에서, **한 사용자가 자기 세션 안에 자기 신원과 관련된 상태를 축적할 수 있는 지점**을 찾는다. 그다음 한 기능 영역을 밟은 뒤 전혀 무관한 영역으로 이동해, 축적된 상태가 그쪽 동작에 영향을 주는지 확인한다.

그리고 설계 관점의 교훈이 있다. 이 결함은 재사용이 나빠서 생긴 것이 아니다. **하나의 타입이 두 개의 다른 개념을 표현하고 있었기** 때문에 생겼다. 세션의 주체인 "지금 로그인한 사람"과 등록 절차의 대상인 "지금 신청서를 쓰고 있는 고객"은 서로 다른 개념인데 코드에서는 같은 `CCustomer`였다. 29.6절에서 이 지점을 다시 본다.

### 사례 6. 비즈니스 한도 우회하기

**기능의 의도.** 제조 회사에서 쓰는 웹 기반 전사 자원 관리(ERP) 애플리케이션이다. 재무 담당자가 회사와 주요 고객·공급사의 계좌 사이에서 자금을 이체할 수 있다. 사기 방지를 위해 대부분의 사용자는 1만 달러를 넘는 이체를 처리할 수 없고, 그 이상은 고위 관리자의 승인이 필요하다.

**가정.** 검사 코드는 단순하다.

```cpp
bool CAuthCheck::RequiresApproval(int amount)
{
    if (amount <= m_apprThreshold)
        return false;
    else
        return true;
}
```

개발자들은 이 투명한 검사가 완벽하다고 믿었다. 설정된 한도를 넘는 거래는 어떤 것도 2차 승인 요건을 빠져나갈 수 없다고 보았다.

**가정이 깨지는 방식.** **음수**를 고려하지 않았다. 어떤 음수도 한도보다 작으므로 승인 검사를 통과한다. 그리고 애플리케이션의 뱅킹 모듈은 음수 이체를 거부하지 않고 **반대 방향의 양수 이체로 처리**했다. A 계좌에서 B 계좌로 2만 달러를 옮기고 싶은 사용자는 B에서 A로 −2만 달러를 이체하면 된다. 결과는 같고 승인은 필요 없다.

**교훈.** 수치 한도를 쓰는 애플리케이션은 흔하다. 소매 애플리케이션은 재고 수량을 넘는 주문을 막고, 뱅킹 애플리케이션은 잔고를 넘는 결제를 막고, 보험 애플리케이션은 연령 구간에 따라 견적을 조정한다. 이런 한도를 우회하는 것이 애플리케이션 자체의 보안 침해는 아닐 수 있다. 그러나 **소유자가 애플리케이션에 의존해 강제하고 있던 통제의 붕괴**이며, 심각한 사업적 결과를 낳는다.

가장 노골적인 형태는 출시 전 사용자 인수 테스트에서 걸리는 경우가 많다. 남는 것은 미묘한 변형들, 특히 히든 파라미터가 조작되는 경우다. 실무의 처방은 두 가지다. 첫째, 수치 한도와 임계값에 근거한 검사를 하기 전에 **엄격한 정규화와 데이터 검증**을 수행한다. 음수가 기대되지 않으면 음수를 포함한 요청을 명시적으로 거부한다. 둘째 — 그리고 이것이 이 책이 강조하는 쪽인데 — **애초에 음수가 표현될 수 없는 타입**을 쓴다. 금액이 `int`인 한 검사는 언제나 사후적이다. 29.3절의 서점 사례가 정확히 같은 결함의 소매 버전이며, 29.6절이 그 처방을 다룬다.

### 사례 7. 대량 할인 속이기

**기능의 의도.** 서점이 묶음 구매 할인을 제공한다. 특정 조합을 함께 사면 개별 정가에서 일정 비율을 깎아 준다. 예를 들어 어떤 전집의 1권·2권·3권을 함께 담으면 세 권 모두 25퍼센트 할인이다.

**가정.** 사용자가 장바구니에 상품을 담을 때마다 애플리케이션이 여러 규칙을 돌려 이 조합이 할인 대상인지 판정한다. 대상이면 장바구니 안 해당 상품들의 가격을 할인가로 조정한다. 개발자들은 **사용자가 그 조합을 그대로 결제할 것**이라고 가정했다.

**가정이 깨지는 방식.** 사용자는 담은 뒤에 뺄 수 있다. 판매 중인 모든 상품을 대량으로 장바구니에 담아 가능한 최대 할인을 전부 발동시킨 다음, 원하지 않는 상품을 빼면 된다. 할인은 이미 남은 상품에 적용된 상태로 유지된다.

**교훈.** 가격이나 그 밖의 민감한 값이 **사용자가 통제하는 데이터나 행위**를 기준으로 조정되는 모든 지점에서, 먼저 조정 알고리즘과 조정이 일어나는 위치를 파악한다. 그다음 그 조정이 일회성인지, 이후 행위에 반응해 다시 계산되는지를 확인한다. 이 사례에서는 할인이 일회성이었고 되돌아보는 재계산이 없었다.

방어의 원칙은 간단하다. **주문이 확정된 뒤에 할인을 적용한다.** 장바구니의 중간 상태에 최종 가격을 써 두지 않는다. 더 일반화하면, 사용자가 계속 바꿀 수 있는 데이터에 **파생된 값을 저장해 두고 그것을 최종 판정의 근거로 삼지 말라**는 것이다. 파생 값은 확정 시점에 원본으로부터 다시 계산되어야 한다. 29.4절의 "자작 할인 쿠폰"이 같은 주제의 더 파괴적인 변주다.

### 사례 8. 이스케이프에서 탈출하기

**기능의 의도.** 네트워크 침입 탐지 제품의 웹 관리 인터페이스를 포함한 여러 애플리케이션에서 발견된 결함이다. 사용자가 통제하는 입력을 운영체제 명령의 인자로 넘겨야 하는 기능이 있었다. 개발자들은 그 위험을 알고 있었고(→ 28.1), 방어책으로 위험 문자를 백슬래시로 이스케이프하기로 했다. 대상 문자는 다음과 같았다.

```
|  &  ;  <  >  '  "  공백  개행
```

이렇게 이스케이프하면 셸 명령 해석기는 해당 문자를 셸 메타문자가 아니라 인자의 일부로 취급한다. 추가 명령 주입, 인자 추가, 출력 리다이렉션이 모두 막힌다.

**가정.** 공격자에게 도움이 될 만한 문자를 하나도 빠짐없이 브레인스토밍했고, 전부 제대로 이스케이프했다. 완전한 방어라고 확신했다.

**가정이 깨지는 방식.** **이스케이프 문자 자체를 이스케이프하는 것을 잊었다.**

백슬래시는 단순한 명령 주입에서 공격자에게 직접적으로 쓸모가 없다. 그래서 위험 문자 목록에 들어가지 않았다. 그러나 그것을 이스케이프하지 않음으로써, 이스케이프 메커니즘 전체를 무력화할 수단을 제공했다.

공격자가 이렇게 입력한다.

```
foo\;ls
```

애플리케이션이 이스케이프를 적용하면 세미콜론 앞에 백슬래시가 하나 붙는다.

```
foo\;ls
```

이 데이터가 명령의 인자로 넘어가면 셸은 첫 번째 백슬래시를 이스케이프 문자로 읽는다. 따라서 **두 번째 백슬래시를 리터럴 백슬래시**로, 즉 인자의 일부로 취급한다. 그다음에 만나는 세미콜론에는 앞에 이스케이프 문자가 없다. 셸은 그것을 명령 구분자로 읽고 뒤에 붙은 명령을 실행한다.

**교훈.** 명령 인젝션을 비롯한 인젝션을 탐침할 때, 메타문자를 넣어 보고 막히면 **각 메타문자 바로 앞에 백슬래시를 하나 붙여** 다시 시도한다. 이 검사는 30초면 끝나고, 통째로 뚫는 경우가 있다.

같은 결함이 XSS 방어에도 있다. 사용자 입력이 자바스크립트 문자열 리터럴 안으로 복사될 때 많은 애플리케이션이 따옴표를 백슬래시로 이스케이프한다. 백슬래시 자체를 이스케이프하지 않으면 공격자는 `\'`를 제출해 문자열 밖으로 나와 스크립트를 장악한다. 초기 버전의 Ruby on Rails `escape_javascript` 함수에 정확히 이 버그가 있었다.

이 사례는 27.5절(필터 우회)과 7.7절(다중 인코딩)이 다룬 문제와 같은 계열이다. 다만 여기서 깨지는 것은 인코딩의 다단계 해석이 아니라 **이스케이프 규칙의 자기 완결성**이다. 이스케이프 메커니즘은 자신이 도입하는 문자에 대해서도 닫혀 있어야 한다. 그 조건이 성립하지 않으면 이스케이프는 방어가 아니라 공격자의 도구가 된다. 이것이 이 책이 인젝션 방어로 이스케이프가 아니라 파라미터화·구조적 분리를 권하는 이유이기도 하다(→ 27.9, 28.2).

### 사례 9. 입력 검증 무력화하기

**기능의 의도.** 전자상거래 사이트에 여러 공격을 막기 위한 입력 검증 루틴 모음이 있었다. 그중 둘이 문제의 주인공이다.

첫째, **SQL 인젝션 필터**. 문자열 입력에 나타나는 작은따옴표를 전부 두 개로 늘린다. 두 개의 연속된 작은따옴표는 SQL에서 리터럴 작은따옴표 하나를 나타내는 이스케이프 시퀀스이므로, 데이터베이스는 그것을 문자열 종료가 아니라 문자열 안의 데이터로 해석한다. 많은 개발자가 이 방식으로 SQL 인젝션을 막을 수 있다고 추론한다.

둘째, **길이 제한기**. 모든 입력에 적용되어 어떤 변수도 128자를 넘지 않게 한다. 넘으면 **128자로 잘라낸다**.

**가정.** 두 방어 모두 보안 관점에서 바람직하므로 둘 다 적용해야 한다. 이 가정에서 빠진 것은 **적용 순서와 상호작용**이다. 개발자들은 정제된 입력이 잘림 함수에 넘겨질 때 어떻게 되는지를 생각하지 않았다.

**가정이 깨지는 방식.** 로그인 폼에 사용자명으로 `admin'--`를 넣으면 따옴표가 두 배가 되어 다음 질의가 만들어지고, 우회는 실패한다.

```sql
SELECT * FROM users WHERE username = 'admin''--' and password = ''
```

이번에는 **a를 127개 쓰고 그 뒤에 작은따옴표 하나**를 붙인 사용자명을 보낸다. 애플리케이션은 먼저 따옴표를 두 배로 늘린다. 문자열은 127 + 2 = 129자가 된다. 그다음 128자로 자른다. 마지막 따옴표 하나가 잘려 나가면서 입력은 **원래 형태 — a 127개 + 따옴표 하나 — 로 되돌아온다.** 정제가 취소된 것이다.

여기에 비밀번호로 `or 1=1--`를 함께 보낸다. 질의는 이렇게 조립된다.

```sql
SELECT * FROM users WHERE username = 'aaaa...aaa'' and password = 'or 1=1--'
```

문자열 리터럴은 첫 따옴표에서 시작해 a 127개를 지나고, 이어지는 두 개의 따옴표를 **이스케이프된 리터럴 따옴표**로 흡수한 뒤, ` and password = ` 까지 계속되다가 비밀번호 값을 열려던 따옴표에서 끝난다. 데이터베이스가 이해하는 사용자명은 이 문자열이다.

```
aaaa...aaa' and password = 
```

그 뒤에 남는 `or 1=1--`는 질의의 일부로 해석되어 조건 전체를 참으로 만든다. 로그인이 뚫린다.

정확한 길이 제한을 모를 때도 검사할 수 있다. 홀수 개와 짝수 개의 따옴표로 이뤄진 긴 문자열을 각각 보내 본다. 이스케이프된 입력의 잘림은 짝수 번째 문자 뒤에서 일어나거나 홀수 번째 문자 뒤에서 일어난다. 어느 쪽이든 두 시도 중 하나는 질의에 홀수 개의 따옴표를 남겨 문법 오류를 일으킨다.

**교훈.** 애플리케이션이 사용자 입력을 **수정하는** 모든 지점을 기록해 둔다. 잘라내기, 특정 문자열 제거, 인코딩, 디코딩이 전부 해당한다. 그리고 각 지점에 대해 그 수정을 역이용하는 문자열을 만들 수 있는지 확인한다.

- 데이터가 **한 번만(비재귀적으로)** 제거된다면 그 제거를 상쇄하는 문자열을 보낸다. `select` 키워드를 걸러 낸다면 `selselectect`를 제출해 안쪽 `select`가 제거된 뒤 바깥이 `select`로 남는지 본다.
- 검증이 **정해진 순서로** 이뤄지고 그중 하나가 데이터를 수정한다면, 그 수정으로 앞선 검증을 무력화할 수 있는지 본다. URL 디코딩 뒤에 `<script>` 태그를 제거한다면 이런 문자열이 통한다.

```
%<script>3cscript%<script>3ealert(1)%<script>3c/script%<script>3e
```

XSS 필터가 `<tag1>aaaaa</tag1>`처럼 태그 쌍 사이의 데이터를 통째로 제거하도록 만들어진 경우가 흔한데, 이런 필터는 대개 이 공격에 취약하다.

일반화하면 이렇다. **정제(sanitization)와 변형(transformation)을 같은 파이프라인에 섞어 두면, 순서가 곧 취약점이 된다.** 43.4절이 검증의 순서를 — 데이터의 출처, 크기, 어휘적 내용, 구문, 의미의 순으로 — 규정하는 이유가 여기에 있다. 크기 제한은 **검증 전에**, 그것도 잘라내기가 아니라 거부로 이뤄져야 한다.

### 사례 10. 검색 기능 남용하기

**기능의 의도.** 금융 뉴스·정보를 구독 기반으로 제공하는 애플리케이션이다. 기업 보고서와 재무제표, 보도자료, 시장 분석 등 방대한 아카이브를 보유하고 있고, 대부분은 유료 구독자만 볼 수 있다.

검색 기능은 강력하고 세밀하며 **모든 사용자가 쓸 수 있다.** 비로그인 사용자가 질의하면 검색 기능은 조건에 맞는 모든 문서로의 링크를 돌려준다. 다만 실제 보호 문서를 열려면 구독해야 한다. 운영자는 이것을 유용한 마케팅 전술로 여겼다.

**가정.** 사용자가 검색 기능만으로는 대가를 지불하지 않고 유용한 정보를 뽑아낼 수 없다. 검색 결과에 나오는 문서 제목은 대개 "2010 연간 실적", "보도자료 08-03-2011"처럼 무미건조하기 때문이다.

**가정이 깨지는 방식.** 검색 기능이 **몇 건이 일치하는지**를 알려 준다. 그것으로 충분하다. 많은 수의 질의를 던지고 결과의 일치 여부로 추론하면, 돈을 내야 얻을 수 있는 정보를 검색 기능에서 뽑아낼 수 있다. 특정 문서의 내용에 좁혀 들어가는 질의는 이런 모양이다.

```
"08-03-2011" takeover ngs announced   → 0건
"08-03-2011" takeover ngs cancelled   → 0건
"08-03-2011" takeover ngs completed   → 1건
```

문서 자체를 볼 수는 없지만, 충분한 상상력과 스크립트를 동원하면 내용에 대한 상당히 정확한 그림을 만들 수 있다.

이 기법이 특히 위력적인 곳은 사내 문서 관리 소프트웨어다. WAHH 저자들은 위키에 저장된 설정 파일에서 핵심 비밀번호를 이 방식으로 무차별 대입해 알아냈다. 그 위키는 검색어가 페이지 어디에든 나타나면 — 단어 단위가 아니라 부분 문자열로 — 히트를 돌려주었기 때문에, 한 글자씩 확장해 가며 비밀번호를 복원할 수 있었다.

```
Password=A    → 0건
Password=B    → 1건
Password=BA   → 0건
Password=BB   → 0건
...
```

**교훈.** 이 결함은 30.3절이 다루는 **추론(inference)** 의 한 형태다. 응답 시간, 상태 코드, 일치 건수 — 무엇이든 입력에 따라 값이 달라지는 관찰 가능한 양이면 채널이 된다. 검색 기능은 그 채널의 대역폭이 유난히 넓은 경우일 뿐이다.

방어는 접근 통제를 검색 인덱스까지 밀어 넣는 것이다. 검색 기능이 일부 사용자가 볼 수 없는 민감 데이터를 색인한다면, 그 사용자들이 검색 결과로 정보를 **추론할 수 있는 어떤 수단도 제공하지 않아야** 한다. 필요하다면 권한 수준별로 여러 개의 인덱스를 유지하거나, 요청자의 권한으로 저장소를 동적으로 검색한다. "링크는 보여 주되 문서는 막는다"는 절충은 마케팅 전술로는 그럴듯하지만 접근 통제로는 무효다.

### 사례 11. 디버그 메시지 수집하기

**기능의 의도.** 금융 회사가 최근 배포한 애플리케이션이다. 새 소프트웨어가 대개 그렇듯 기능 관련 버그가 남아 있었고, 여러 작업이 간헐적으로 예측 불가능하게 실패하며 사용자에게 오류 메시지가 표시되었다.

오류 조사를 돕기 위해 개발자들은 이 메시지에 상세한 정보를 담기로 했다.

```
사용자 신원
현재 세션의 토큰
접근 중이던 URL
오류를 일으킨 요청에 함께 제출된 모든 파라미터
```

이 메시지는 헬프데스크 인력이 장애를 조사하고 복구하는 데 유용했고, 남은 기능 버그를 잡는 데도 도움이 되었다.

**가정.** 보안 자문의 통상적인 경고에도 불구하고 개발자들은 이것이 취약점을 여는 것이 아니라고 판단했다. 디버깅 메시지에 담긴 정보는 **사용자가 자기 브라우저가 처리하는 요청과 응답을 들여다보면 모두 얻을 수 있는 것**이었기 때문이다. 스택 트레이스처럼 실제 실패에 관한 세부는 담지 않았으므로 공격을 만드는 데 도움이 되지 않는다고 보았다.

**가정이 깨지는 방식.** 메시지의 **내용**에 대한 추론은 옳았다. 결함은 메시지 생성을 **구현한 방식**에 있었다.

오류가 발생하면 어떤 컴포넌트가 필요한 정보를 모아 저장하고, 사용자에게는 그 저장된 정보를 표시하는 URL로 HTTP 리다이렉트를 내보냈다. 문제는 디버그 정보의 저장과 오류 메시지에 대한 사용자 접근이 **세션 기반이 아니었다**는 것이다. 디버그 정보는 정적(static) 컨테이너에 저장되었고, 오류 메시지 URL은 언제나 **그 컨테이너에 마지막으로 들어간 정보**를 표시했다. 개발자들은 리다이렉트를 따라간 사용자가 자기 오류에 해당하는 정보만 보게 될 것이라고 가정했다.

실제로는 두 오류가 거의 동시에 발생하면 일반 사용자가 다른 사용자의 디버깅 정보를 보게 되는 일이 이따금 일어났다. 그러나 이것은 단순한 경쟁 조건이 아니었다. 오류 메커니즘의 동작 방식을 알아낸 공격자는 **그 메시지 URL을 반복해서 폴링하며 값이 바뀔 때마다 기록하기만 하면 된다.** 몇 시간이면 로그에는 다음이 쌓인다.

- 비밀번호 추측 공격에 쓸 수 있는 사용자명 집합
- 세션을 탈취하는 데 쓸 수 있는 세션 토큰 집합
- 비밀번호를 비롯한 민감 항목이 포함될 수 있는 사용자 제출 입력 집합

관리자도 이따금 이 상세 오류 메시지를 받았으므로, 오류 메시지를 감시하던 공격자는 머지않아 애플리케이션 전체를 장악하기에 충분한 정보를 얻는다.

**교훈.** 이 결함의 정체는 **사용자별로 저장되어야 할 데이터가 전역 저장소에 놓인 것**이다. 30.1절이 다루는 오류 메시지 정보 노출의 변종처럼 보이지만, 실제 병은 오류 메시지의 상세함이 아니라 저장 위치다. 같은 메시지를 세션 스코프에 저장했다면 아무 일도 없었다.

탐지 방법은 이렇다. 사용자별 정보가 통상적이지 않은 방식으로 브라우저에 돌아오는 비정상 이벤트와 조건을 전부 목록으로 만든다. 그다음 **두 명의 사용자로 애플리케이션을 동시에 사용하면서** 각 조건을 체계적으로 유발하고, 한쪽의 행위가 다른 쪽에 영향을 주는지 확인한다.

### 사례 12. 로그인과 경쟁하기

**기능의 의도.** 최근 몇몇 대형 애플리케이션에 영향을 준 결함이다. 대상 애플리케이션은 여러 종류의 자격증명을 요구하는 견고한 다단계 로그인을 구현하고 있었다. 인증 메커니즘은 여러 차례의 설계 리뷰와 침투 테스트를 거쳤다.

**가정.** 소유자들은 이 메커니즘을 공격해 무단 접근을 얻는 실행 가능한 방법이 존재하지 않는다고 확신했다.

**가정이 깨지는 방식.** 메커니즘에는 미묘한 결함이 있었다. 이따금 고객이 로그인하면 **전혀 다른 사용자의 계정**으로 들어갔다. 그 사용자의 금융 정보를 전부 볼 수 있었고 심지어 그 계정에서 결제도 할 수 있었다. 동작은 처음에 무작위로 보였다. 피해자는 특별한 행동을 한 적이 없었고, 다시 로그인하면 재현되지 않았다.

조사 끝에 원인이 밝혀졌다. **두 사용자가 정확히 같은 순간에 로그인할 때** 발생하며, 그런 경우 전부가 아니라 일부에서만 발생했다. 근본 원인은 애플리케이션이 새로 인증된 각 사용자에 대한 핵심 식별자를 **정적(비세션) 변수에 잠깐 저장**하고 있었다는 것이다. 값을 쓴 뒤 아주 짧은 순간 뒤에 다시 읽었는데, 그 사이에 다른 스레드가 — 다른 로그인을 처리하며 — 같은 변수에 썼다면, 먼저 로그인한 사용자가 나중 사용자의 인증된 세션에 도착한다.

**경쟁 조건(race condition)** 이란 특정 상황에서 아주 짧은 시간 동안만 존재하는 취약점을 가리킨다. 공격자는 애플리케이션이 그 창을 닫기 전에 도달하려고 "경쟁"한다. 공격자가 애플리케이션과 같은 머신에 있다면 조건을 정확히 조성해 안정적으로 익스플로잇할 수 있는 경우가 많다. 원격에서는 훨씬 어렵다. 이 결함을 이해한 원격 공격자가 스크립트로 계속 로그인하며 접근한 계정의 정보를 확인하는 공격을 고안할 수는 있지만, 창이 워낙 좁아 엄청난 수의 요청이 필요하다.

이 결함이 정규 침투 테스트에서 발견되지 않은 것은 놀랍지 않다. 결함이 나타나는 조건은 애플리케이션이 충분히 큰 사용자 기반을 확보해 무작위 이상 현상이 발생하고 그것이 고객에 의해 신고될 때에야 성립했다. 그러나 **인증과 세션 관리 로직에 대한 면밀한 코드 리뷰였다면 이 문제를 찾아냈을 것이다.**

**교훈.** 사례 11과 사례 12는 같은 종류의 실수에서 나왔다. **스레드별 또는 세션별로 저장되어야 할 정보를 정적 저장소에 두었다.** 사례 11은 재현이 쉽고 원격에서 안정적으로 수확할 수 있어 즉시 치명적이었고, 사례 12는 탐지도 익스플로잇도 훨씬 어렵지만 원인은 동일하다.

원격 블랙박스로 이런 스레드 안전성 문제를 검사하는 것은 간단하지 않으며, 가장 보안이 중요한 애플리케이션에서만 정당화되는 전문 작업으로 봐야 한다. 절차는 이렇다.

1. 로그인, 비밀번호 변경, 자금 이체처럼 핵심 기능을 표적으로 고른다.
2. 각 기능에 대해 한 사용자가 한 번의 행위를 수행하는 데 필요한 최소한의 요청과, 결과를 확인하는 가장 단순한 수단을 찾는다.
3. 사양이 좋은 여러 대의 머신을 서로 다른 네트워크 위치에 두고, 여러 사용자를 대신해 같은 행위를 반복 수행하는 스크립트를 돌린다. 각 행위가 기대한 결과를 냈는지 확인한다.
4. 대량의 거짓 양성을 각오한다. 인프라 규모에 따라 이 작업은 사실상 부하 테스트가 되며, 보안과 무관한 이유로 이상 현상이 나타난다.

경쟁 조건은 부하가 올라가야 드러난다는 점에서 **가용성과 같은 축에 놓인다.** 45.3절이 가용성 설계에서 상태 공유와 격리를 다루는 이유가 여기에 있고, 46.3절이 "처리 인스턴스는 상태를 갖지 않는다"를 원칙으로 세우는 이유도 마찬가지다. 상태 없는 처리 인스턴스에는 두 요청이 공유할 정적 변수가 애초에 없다.

이 세 군집은 뒤에서 하나로 합쳐진다. 요청의 순서가 강제되지 않은 것도, 두 개념이 하나의 타입을 공유한 것도, 금액이 임의의 정수였던 것도 결국 **애플리케이션이 자기 업무 도메인을 얕게 모델링했기 때문**이다. 29.3절부터 29.5절까지 세 개의 이야기를 본 뒤 29.6절에서 이 명제를 다시 꺼낸다.

> - 정제와 변형의 순서 문제 → **43.4** (검증의 순서), **7.8** (다단계 검증과 정규화 순서)
> - 정적 저장소에 놓인 사용자별 상태 → **45.3** (가용성 설계), **46.3** (상태 없는 처리 인스턴스)
> - 일치 건수·응답 시간을 통한 추론 → **30.3** (추론을 통한 정보 수집)
> - 수치 한도를 타입으로 강제하기 → **44.1** (도메인 프리미티브와 불변식)

## 29.3 온라인 서점의 비즈니스 무결성 결함 — 미수금 원장, 재고 시스템, "안티북" 배송

앞 절의 열두 사례는 공격자의 시선으로 본 것이다. 이제 시선을 바꾼다. 같은 종류의 결함을 **왜 그런 코드가 쓰였는가**의 방향에서 본다. 무대는 국제적으로 사업하는 소매 기업의 온라인 서점이다.

이 이야기의 특징은 두 가지다. 첫째, 심각한 보안 문제가 **아무것도 기술적으로 깨지지 않은 채** 오랫동안 프로덕션에서 지속되었다. 둘째, 그럼에도 회사에서 계속 돈이 새어 나갔다.

### 정상 흐름

서점은 특별할 것이 없다. 고객이 책을 장바구니에 담고, 체크아웃하고, 신용카드로 결제하면 책이 배송된다. 조 테스터(Joe Tester)가 39달러짜리 『햄릿』 두 권을 산다고 하자.

```
        조 테스터: 39달러 햄릿 2권
                    │
                    ▼
              ┌───────────┐
              │  온라인 서점 │
              └─────┬─────┘
         78달러  ┌──┴──┐  햄릿 2권    햄릿 2권
            ┌───┘     └────┐      ┌────────┐
            ▼              ▼      ▼        │
      ┌──────────┐    ┌────────┐  ┌────────┴─┐
      │  경리 시스템 │    │ 재고    │  │  배송     │
      └─────┬────┘    │ 17 → 15 │  │ 2권 피킹  │
            │          └────────┘  └──────────┘
       78달러│
            ▼
      ┌──────────┐
      │ 미수금 원장 │  조: +78달러
      └─────┬────┘   (결제 완료까지 조가 서점에 빚진 금액)
            │
       78달러▼
      ┌──────────┐
      │ 카드 결제  │
      └──────────┘
```

*그림 29-1. 조가 39달러짜리 햄릿 두 권을 살 때의 정상 흐름 (SBD 2장 그림 2.1 기준)*

주문 하나가 네 개의 하위 시스템에 각각 다른 언어로 도착한다. 경리 시스템에는 금액으로, 미수금 원장에는 고객별 잔액으로, 재고 시스템에는 판매 가능 수량의 감소로, 배송 시스템에는 피킹 목록으로.

### 침투 테스트에서 벌어진 일

기업이 보안 팀을 불러 감사와 테스트를 맡긴다. 팀은 프로덕션 설정과 코드베이스를 감사하고, 바깥에서 시스템을 조작해 보안 결함을 찾는 테스트를 수행한다. 이상한 것이 나오면 끝까지 파고들 권한도 받았다.

인프라는 견고했다. 방화벽을 찔러 보고, 열린 포트를 스캔하고, 웹 서버에 악성 패킷을 던져도 전부 정상이었다. 놀랄 일은 아니다. 요즘 보안 문제가 깨진 인프라에서 비롯되는 경우는 드물다. 노출되면 안 되는 것은 노출하지 않는다는 교훈은 널리 학습되었다.

다른 팀원들이 애플리케이션을 기술적 관점에서 조사한다. 로그인을 우회할 방법을 찾고, 열린 세션을 가로채 보고, 쿠키를 오염시켜 본다. 여기서도 성과가 없다. 웹 서버 설정 문서를 제대로 읽고 구현한 사람이 있었던 것이 분명했다.

돌파구는 조 테스터가 주문 폼의 **수량(Quantity) 필드**에 호기심을 가지면서 열린다. 자바스크립트 조각을 넣어 실행되는지 본다. 아무 일도 없다. SQL 인젝션을 유발해 본다. 역시 없다. 마지막으로 그는 39달러짜리 『햄릿』의 수량으로 **`-1`** 을 입력한다. 달리 말하면, 조 테스터는 **음수의 햄릿 — 안티햄릿(anti-Hamlet)** 을 사려고 한다.

오류 메시지가 나오지 않는 것에 그는 놀란다. 서점은 주문을 받아들이고, 주문 흐름 끝까지 정상적으로 진행시킨다. 신용카드로 체크아웃하고 주문 접수 확인 이메일까지 받는다. "이상하네." 그는 수첩에 메모를 남기고 다른 작업을 계속한다.

다음 날 오후, 보안 팀 방문을 누군가 두드린다. 한 여성이 머뭇거리며 들어온다.

> "경리부에서 왔는데요, 혹시 조 테스터라는 사람에 대해 아는 분 계신가요?"
> "네, 저희 테스트 고객입니다. 왜 그러시죠?"
> "미수금 원장을 돌렸는데 시스템이 그분에게 39달러짜리 **대변 청구서(credit invoice)** 를 발행했어요. 그런데 책을 부치려고 보니 고객 주소가 이상하더군요. 본사 주소하고 똑같아요. 그래서 수상해서 물어보고 다닌 거예요."

시스템이 조 테스터에게 **진짜 돈을 지불하려 하고 있었다.**

### 논리적 결과를 따라가기

한 발 물러서서 무슨 일이 일어났는지 보자. 서점이 『햄릿』 −1권 주문을 받아들인 것은 분명히 이상하다. 하지만 일단 그 일이 일어났다면, 그다음의 논리적 귀결은 무엇인가.

39달러짜리 책을 사면 주문의 가치는 39달러이고 고객이 서점에 39달러를 내는 것이 합당하다. 조 테스터는 『햄릿』을 산 것이 아니라 **음수 권의 『햄릿』**을 샀으므로 주문의 가치는 −39달러다. 그는 서점에 −39달러를 내야 하고, 다시 말해 **서점이 그에게 39달러를 지불해야 한다.** 게다가 조 테스터가 서점에 『햄릿』 한 권을 건네줘야 할 것이다.

보안 관점에서 이것은 침해다. 보안의 한 축인 **무결성(integrity)** 은 대략 "데이터가 규칙에 어긋나게 변경되거나 생성되지 않는 것"을 뜻한다. 무결성은 보통 체크섬과 암호학적 서명 같은 기술적 수단으로 다뤄진다. 그런데 이 사례에서 위반된 규칙은 기술적 규칙이 아니라 **업무 규칙**이다. 서점이 안티북에 대해 고객에게 돈을 보내는 것은 건전한 사업이 아니다. 여기서 일어난 것은 **비즈니스 무결성(business integrity)의 침해**다(→ 41.4).

이 개념이 중요한 이유는, 이 침해를 탐지할 수 있는 기술적 지표가 하나도 없기 때문이다. 체크섬은 맞고, 서명은 유효하고, 트랜잭션은 원자적으로 커밋되었으며, 데이터베이스 제약 조건은 아무것도 위반되지 않았다. 무너진 것은 데이터가 아니라 **데이터가 의미해야 할 세계**다.

### −39달러가 지나가는 길

수상함을 감지한 보안 팀이 조사를 시작한다. 온라인 서점 시스템은 이 주문의 "지불할 금액"을 −39달러로 계산한다. 논리적이지만 기이하다. 그리고 이 −39달러가 여러 시스템을 차례로 통과한다.

이 이야기의 흥미로운 점은, **각 시스템이 어떻게 반응하고 서로 어떻게 상호작용하는지를 모두 이해하지 않으면 이 보안 문제를 이해할 수 없다**는 것이다. 하나씩 본다.

**청구 시스템.** 목적은 고객으로부터 대금을 회수하는 것이다. 결제 수단을 신용카드로 지정하고 347달러짜리 주문을 체크아웃하면 그 금액이 카드에 청구된다. 다른 결제 수단도 있다. 청구서, 누적 청구, 상품권 등이다. 금액대별로 다른 결제 수단을 쓰는 고객도 있다. 큰 금액은 즉시 결제하고 작은 금액은 월말 청구서로 누적하는 식이다.

조 테스터의 −39달러 주문이 체크아웃되면 그 금액이 청구 시스템으로 간다. 그런데 청구 시스템의 신용카드 모듈은 **음수 금액을 처리할 줄 모른다.** 청구 시스템의 관점에서 음수 금액이란 회수할 결제가 없다는 뜻이다. 결제 작업은 아무 동작 없이 그냥 통과한다. 예외도, 경고도 없다.

**미수금 원장.** 회계 시스템의 일부인 이 원장은 회사에 돈을 빚진 고객을 추적한다. 책을 샀지만 회사가 아직 대금을 받지 못한 상태가 그것이다. 요컨대 미수금 원장은 고객별 잔액을 관리한다. 347달러 주문을 청구서 결제로 체크아웃하면 그 고객의 잔액에 347달러가 더해지고, 나중에 회사가 대금을 받으면 잔액이 정리된다.

가끔 고객이 과다 납부하는 일이 있다. 350달러를 냈다면 잔액은 −3달러가 되고, 이것은 **회사가 고객에게 빚졌다**는 뜻이다. 은행이라면 회사가 고객에게 빚진 상태가 장기적으로도 정상이다. 그러나 온라인 서점에서 그런 상태는 일시적으로만 허용된다. 발생하면 서점은 가능한 한 빨리 빚을 청산해야 한다.

서점이 고객에게 빚진 돈을 갚는 정상 절차는 **대변 청구서를 발송하는 것**이다. 이 점검은 배치 작업으로 돌아간다. 경리부 여성이 "미수금 원장을 돌렸다"고 한 것이 이 작업이다. 조 테스터가 안티구매를 하면 온라인 서점이 −39달러의 결제 금액을 미수금 원장으로 보내고, 그 즉시 조는 회사에 대해 유리한 위치에 선다. 그날 밤 배치 작업이 돌면서 이 미결 채무를 발견하고, 원장을 정리하기 위해 그에게 보낼 대변 청구서를 만든다. 사실상 테스터에게 돈을 보내는 것이다.

```
          ┌─────────────┐
          │  미수금 원장   │   "조에게 빚진 상태를 없애자"
          │              │
          │  채무          │            ┌──────────────┐
          │  조   -39달러  │ ─────────▶ │ 대변 청구서     │
          └─────────────┘             │ 조 테스터에게   │
                                       │ 39달러         │
                                       └──────────────┘
```

*그림 29-2. 미수금 원장이 대변 청구서를 발행하고 원장을 정리한다 (SBD 2장 그림 2.4 기준)*

이 테스트가 프로덕션에서 수행되었으므로, 프로덕션 시스템에 이 결함이 이미 한동안 존재했다는 것이 분명하다. 이번 건이 잡힌 유일한 이유는 주소가 이상해서 의심을 샀기 때문이다. 이전에도 비슷한 사례가 있었을 수 있다.

재무 조사가 시작된다. 운영 팀과 보안 팀이 발행된 모든 대변 청구서를 교차 점검한다. 공급사·파트너 대상 대변 청구서를 걸러 내면 고객 대상만 남는다. 그중 대부분은 파손 상품 등 정당한 사유의 유효한 대변이다. 남는 것은 작은 일부여서, 문제는 그리 크지 않아 **보인다.** 적어도 그 시점에는 그렇게 보였다.

### 재고 시스템은 어떻게 책을 세는가

기술적 조사가 계속되면서 두 시스템이 더 등장한다. 재고와 배송이다.

재고 시스템은 서점이 각 도서를 몇 권 보유하고 있으며 창고에서 몇 권을 팔 수 있는지를 추적한다. 출발점은 창고 선반 위의 권수지만, 그렇게 단순하지 않다.

창고에 『햄릿』이 17권 있다고 하자. 고객이 두 권을 샀지만 아직 선반에서 꺼내지도 배송하지도 않았다. 이 두 권은 세면 안 된다. 팔 수 없고, 더 이상 서점의 것도 아니기 때문이다. 『햄릿』의 재고는 17이 아니라 **15**여야 한다.

다른 상황도 있다. 『오만과 편견』 선반이 비어 있다. 소매업체가 출판사로부터 100권을 더 사들였지만 아직 창고에 도착하지 않은 트럭 위에 있다. 그 책들은 서점의 소유이므로 판매 가능하고 재고에 포함되어야 한다. 『오만과 편견』의 재고는 0이 아니라 **100**이다.

이런 기묘한 상황이 여럿 더 있다. 재고 시스템은 그 자체로 복잡한 로직 덩어리다.

온라인 서점이 『햄릿』 세 권을 팔면 재고 시스템에 메시지를 보내 재고 수준을 15에서 12로 낮춘다. 그런데 조 테스터가 **−1권**을 사면 어떻게 되는가. 재고 수준 15에서 −1을 빼야 하므로 결과는 **16**이다.

**안티햄릿 한 권을 파는 것이 재고 수준을 하나 올린다.**

```
   조 테스터: 39달러 햄릿 -1권
                 │
                 ▼
           ┌──────────┐
           │ 온라인 서점 │
           └────┬─────┘
     -39달러 ┌──┴──┐  -1권       -1권
        ┌───┘     └───┐        ┌──────┐
        ▼             ▼        ▼      │
   ┌─────────┐   ┌──────────┐  ┌──────┴────┐
   │ 경리 시스템 │   │ 재고       │  │ 배송        │
   └────┬────┘   │ 15 → 16   │  │  ??        │
        │         └──────────┘  └───────────┘
   -39달러
        ▼
   ┌──────────┐
   │ 미수금 원장 │  조: -39달러
   └────┬─────┘   → 나중에 대변 청구서
        │
   -39달러
        ▼
   ┌──────────┐
   │ 카드 결제  │  "회수할 결제가 없음" → 무동작
   └──────────┘
```

*그림 29-3. 조 테스터가 햄릿 −1권을 주문할 때의 비정상 흐름 (SBD 2장 그림 2.5 기준)*

### 안티북 배송하기

배송 시스템은 책이 고객에게 배송되도록 한다. 온라인 서점에서 주문이 도착하면 주문 라인을 순회하며 창고 작업자가 상자를 꾸릴 수 있도록 피킹 목록을 만든다. 이것도 복잡한 시스템이다. 여러 주문의 책을 동시에 집어 오게 하는 등 창고 작업자의 동선을 최소화하려 애쓴다. 그 최적화는 잘 동작한다.

배송 시스템이 잘 처리하지 못하는 것은 **음수 권수**다. 그런 주문 라인은 런타임 예외를 일으키고, 그 예외는 다른 수많은 메시지와 함께 시스템 로그에 기록된다. 그리고 아무도 그 로그를 보지 않는다. 결과적으로 해당 주문 라인은 그냥 버려진다.

이 대목은 로깅에 관해 이 책이 반복해 온 논점을 정확히 예시한다. 로그에 기록되었다는 것은 탐지되었다는 뜻이 아니다. 아무도 읽지 않는 로그는 존재하지 않는 로그와 같다(→ 16.5). 그리고 예외를 삼키고 조용히 진행하는 코드는 **실패를 실패로 다루지 않는 코드**다(→ 45.2). 이 배송 시스템이 예외를 던지고 주문 전체를 보류시켰다면, 결함은 첫날에 드러났을 것이다.

> **이 절이 뒷받침하는 것**
>
> - 기술적 무결성과 구분되는 비즈니스 무결성 → **41.4** (보안 관심사의 분류 — CIA-T), **41.1** (보안은 기능이 아니라 관심사다)
> - 아무도 읽지 않는 로그가 탐지 수단이 되지 못한다는 사실 → **16.5** (방어자의 로그), **46.4** (파일 로깅을 피하라)
> - 삼켜진 예외와 조용한 진행 → **45.2** (실패는 예외적이지 않다), **30.5** (예외로 실패를 다루기)
> - 수량이 임의의 정수인 것이 결함의 뿌리라는 관찰 → **29.6**, **44.1** (도메인 프리미티브와 불변식)

## 29.4 자작 할인 쿠폰 — 같은 거짓말을 공유하는 시스템들

여기서 이 이야기의 가장 중요한 관찰이 나온다. 왜 이 결함이 몇 달 동안 아무에게도 들키지 않았는가.

### 재무적으로는 아무 모순이 없다

네 시스템의 상태를 정리해 보자. 청구 시스템과 배송 시스템은 상태를 바꾸지 않았으므로 중요도가 낮다. 흥미로운 것은 재고 시스템과 미수금 원장이다.

- **재고 시스템**은 『햄릿』 재고가 16권이라고 잘못 믿는다. 실제로는 15권이다.
- **미수금 원장**은 서점이 누군가에게 돈을 빚졌다고 잘못 믿는다.

그런데 재무적 관점에서 이 둘은 **정확히 상쇄된다.** 책 15권을 갖고 아무 빚도 없는 대신, 책 16권을 갖고 책 한 권 값만큼의 빚을 진 것이다. 자산과 부채가 맞아떨어진다.

**두 시스템 모두 거짓말을 하고 있지만, 같은 거짓말을 하고 있다. 환상은 일관되다.**

시스템들이 서로 일관되므로 정기 보고서는 어떤 불일치도 보여 주지 않는다. 실제로 매일 밤 보고서가 돌고, 분기마다 재무 보고의 일부로 더 포괄적인 보고서가 돌지만, 어느 것도 이상을 보고한 적이 없다. **IT 시스템들 사이에는 불일치가 없기 때문이다.**

존재하는 불일치는 재고 시스템(16권)과 **창고에 실제로 있는 것**(15권) 사이의 불일치다. 그리고 그것은 연말 재고 실사 — 창고 재고를 수작업으로 세어 부기 시스템에 입력하는 작업 — 전까지는 드러나지 않는다. 그때가 되어서야 사라진 책 한 권이 눈에 띈다.

**표 29-3. 어떤 감시 장치가 무엇을 보는가**

| 감시 수단 | 이 결함을 잡을 수 있는가 | 이유 |
|---|---|---|
| 방화벽·포트 스캔 | 아니오 | 네트워크 계층에서 아무 일도 일어나지 않는다 |
| 웹 애플리케이션 방화벽 | 아니오 | 요청은 문법적으로 완전히 정상이다 |
| 취약점 스캐너 | 아니오 | 판정할 시그니처가 없다 |
| 데이터베이스 제약 조건 | 아니오 | `quantity INT`에 −1은 유효한 값이다 |
| 트랜잭션 무결성·체크섬 | 아니오 | 데이터는 규칙대로 커밋되었다 |
| 일일·분기 재무 보고서 | 아니오 | **시스템 간 불일치가 없다** |
| 시스템 로그 | 원리상 예 | 배송 시스템의 예외가 기록되지만 아무도 읽지 않는다 |
| 연말 재고 실사 | 부분적으로 | 차이가 보이지만 다른 원인으로 해석된다 |

### 재고 실사가 남긴 오해

연말 재고 실사에서 차이가 나오는 것은 이상한 일이 아니다. 책은 물리적 물건이고 창고에서는 별일이 다 일어난다. 공급사 납품이 134권이어야 하는데 133권만 들어 있을 수 있다. 모든 상자를 세지는 않고, 세다가 틀리기도 한다. 책이 떨어져 파손되어 폐기될 수 있다. 그러면 기록해야 하지만 바쁘면 잊는다. 그리고 가끔은 절도가 있다. 이것들을 뭉뚱그려 재무 부서는 **창고 손실(loss-on-warehouse)** 로 보고하고, 일정 수준까지는 예상된 값이다.

실제로 몇 달 전 연말 재고 실사에서 평소보다 높은 창고 손실이 보고되었다. 경영진의 분석은 창고 인력에게 동기 부여 문제가 있다는 것이었다. 부주의해져서 책을 더 많이 파손시켰거나, 책을 훔치기 시작했거나. 그 결과 경영진은 창고 직원들을 동기 부여 코치와 함께하는 하루 워크숍에 보내 회사 윤리에 가치관을 맞추도록 했다. 창고 사람들은 어리둥절했고 기분이 좋지 않았다.

이 삽화는 재미있는 일화가 아니다. **탐지 실패는 무해한 공백으로 끝나지 않는다.** 설명되지 않은 지표는 반드시 어떤 설명을 얻게 되고, 그 설명이 틀리면 조직은 엉뚱한 대상에 조치를 취한다. 로직 결함의 비용에는 잘못된 귀인의 비용이 포함된다.

### 자작 할인 쿠폰

불일치를 더 파고들자 상황은 처음 보였던 것보다 나빴다. 창고의 재고 차이가 대변 청구서 총건수보다 **훨씬 컸다.** 다른 일이 벌어지고 있었다.

통상적인 보고서를 믿을 수 없다는 것을 알게 된 팀이 더 깊은 조사를 시작한다. 드러난 사실은 이렇다. 대변 청구서를 받아 내는 것은 이 결함을 악용하는 **가장 흔한 방식이 아니었다.** 훨씬 인기 있는 방식은, 결제 전에 장바구니에 음수 권의 책을 얹어 **주문 총액을 깎는 것**이었다. 스스로에게 할인을 주는 것이다.

```
   246달러어치 책          "너무 비싸네.        246달러
                          할인을 좀 얹자."       -1  햄릿  -39달러
                                              ───────────────
   합계 246달러                                 합계 207달러
```

*그림 29-4. 자작 할인 — 안티햄릿을 담아 총액을 낮춘다 (SBD 2장 그림 2.6 기준)*

이 "이상한 기능"에 대한 소문이 퍼졌던 것이 분명했다. 꽤 많은 고객이 그것을 사용하고 있었다.

이 변형이 대변 청구서 변형보다 위험한 이유가 몇 가지 있다. 첫째, **눈에 덜 띈다.** 대변 청구서는 사람이 발행 목록을 훑는 절차가 존재하지만, 총액이 조금 낮은 정상 주문은 어떤 예외 처리 경로도 밟지 않는다. 둘째, **결제가 실제로 성립한다.** 207달러가 카드로 청구되고 고객은 246달러어치 책을 받는다. 결제 실패도, 대금 미회수도 없다. 셋째, **반복 사용이 쉽다.** 대변 청구서는 우편으로 오지만 자작 할인은 주문마다 즉시 작동한다.

조사 결과 회사는 이 구멍으로 상당한 금액을 잃었다는 사실이 드러났다. 이제 무엇을 할지 결정해야 한다.

기술적 결함은 고칠 것이다. 그런데 스스로 할인을 챙긴 고객들이 회사에 빚진 돈은 어떻게 하는가. 결국 이사회가 결정을 내린다. 신중한 검토 끝에 그들은 **그대로 두기로** 결정한다. 상당수가 재방문 단골인 고객들을 쫓아다니는 것은 손실을 그냥 받아들이고 구멍을 막고 나아가는 것보다 더 큰 악감정을 만들고 회사에 더 해로울 것이라는 판단이었다.

이 결정 자체가 로직 결함의 성질을 말해 준다. **로직 결함의 피해는 사후에 회수되지 않는다.** 유출된 데이터는 폐기를 요구할 수라도 있지만, 부당하게 낮은 가격에 팔린 책은 되돌릴 방법이 없다. 침해가 정상 거래의 외형을 갖고 있었기 때문이다.

### 두 가지 결론

이 이야기에서 끌어내야 할 결론은 두 개다.

**첫째, 시스템 간 일관성은 정확성의 증거가 아니다.** 서로 대조하는 시스템이 여럿이라는 사실이 안심의 근거가 되곤 하지만, 이 사례에서 그 다중성은 오히려 결함을 은폐했다. 대조는 **한 세계관 안에서** 이뤄지고, 결함은 그 세계관 자체에 있었기 때문이다. 진짜 대조는 IT 시스템과 IT 시스템 사이가 아니라 **IT 시스템과 물리적 현실 사이**에서 이뤄져야 한다. 연말 재고 실사가 그 유일한 접점이었고, 그 접점은 1년에 한 번밖에 열리지 않았으며, 열렸을 때조차 다른 원인으로 오해되었다.

**둘째, 기술적으로 아무것도 깨지지 않는 침해가 존재한다.** 이 비즈니스 무결성의 지속적 침해는 몇 달 동안 계속되었고 그동안 기술적으로 깨진 것은 하나도 없었다. 호기심 많은 경리부 직원과, 책 판매라는 **업무 도메인**에 관심을 가진 보안 테스터가 없었다면 아마 계속되었을 것이다. 이런 종류의 결함이 오늘 이 순간에도 세계 곳곳에서 아무 경보도 울리지 않은 채 악용되고 있다고 보는 편이 현실적이다.

이 두 번째 결론은 침투 테스트에 대한 함의를 갖는다. 조 테스터가 수량 필드에 자바스크립트를 넣고 SQL 인젝션을 시도한 것은 표준 절차였다. `-1`을 넣어 본 것은 표준 절차가 아니었다. 그것은 **"이 필드가 업무에서 무엇을 의미하는가"** 라는 질문에서 나왔다. 로직 결함을 찾는 테스터에게 필요한 것은 페이로드 목록이 아니라 도메인에 대한 호기심이다(→ 47.14).

> **이 절이 뒷받침하는 것**
>
> - 시스템 간 일관성이 정확성을 보장하지 않는다는 관찰 → **47.9** (서비스를 넘나드는 민감 데이터), **29.5** (같은 구조의 보험 사례)
> - 도메인 규칙을 겨냥한 테스트의 필요 → **45.7** (도메인 규칙 악용 찾기), **46.9** (단위 테스트로 설계를 지키기), **47.14** (침투 테스트 실행)
> - 결함을 만들지 않는 방향의 처방 → **44.1** (도메인 프리미티브), **43.2** (계약으로 빠르게 실패하기)

## 29.5 무료 보험 증서 — 서비스 분리와 새 결제 유형이 만든 구멍

서점 이야기가 **하나의 값**(수량)이 잘못 모델링되었을 때 무슨 일이 벌어지는지를 보여 줬다면, 이 이야기는 **하나의 단어**(결제)가 두 시스템에서 다르게 이해될 때 무슨 일이 벌어지는지를 보여 준다. 그리고 여기서는 어느 시스템도 자기 도메인의 관점에서 잘못한 것이 없다.

무대는 오래된 오프라인 보험사다. 주 사업은 부동산(주택과 사업장)과 자동차 보험이며, 영업 구역의 모든 도시에 지점을 두고 지역 밀착으로 영업해 왔다.

### 창구에서 팔던 보험

모든 거래는 창구에서 이뤄진다. 신규 고객이 보험에 가입하면 지점에서 서류에 서명하고 창구에서 돈을 낸다. 그러면 회사가 유효한 보험을 증명하는 **증서 우편(policy letter)** 을 보낸다. 갱신도 마찬가지다. 고객이 지점에 와서 창구에서 돈을 내면 갱신 증서가 발송된다.

최근 몇 년 사이 백오피스 시스템이 인쇄·발송 서비스를 쓰기 시작해서 지점 직원이 인쇄와 우편을 신경 쓰지 않아도 되게 되었다. **결제가 등록되는 즉시 시스템이 자동으로 증서를 발송한다.**

내부적으로 시스템은 `Payment`를 새로운 `PolicyPeriod`와 결합하고, 그것이 새 발송을 촉발한다. 전부 하나의 코드베이스이고 모놀리스로 개발·배포된다. 이 시점에 컨텍스트 맵을 그린다면 이렇게 된다.

```
   ┌─────────────────────────────┐
   │                             │
   │   Payment  ───▶  PolicyPeriod │
   │                             │
   └─────────────────────────────┘
              단일 컨텍스트
```

*그림 29-5. 모놀리스의 단일 컨텍스트 (SBD 11장 그림 11.2 기준)*

지도라 부를 것도 못 되지만, 이야기가 진행되면서 이것이 어떻게 변하는지를 보는 것이 요점이다.

### 시스템을 분리하다

팀이 커진다. 지원해야 할 보험 플랜 종류가 늘고 계속 추가된다. 동시에 재무 관련 기능도 방대해진다. 고객 결제 추적, 보험금 지급, 자동차 정비소 같은 파트너에 대한 지불 등이다. 팀이 커졌는데도 개발·지원해야 할 기능의 양에 압도된다.

그래서 팀과 시스템을 둘로 나누기로 한다. **재무 시스템**과 **보험 시스템**이다. 재무 팀은 결제 추적, 파트너 계약, 보험금 지급을 맡는다. 보험 팀은 끝없이 늘어나는 보험 상품 변형에 집중한다. 각각 더 작아진 팀이 자기 도메인에 집중할 수 있게 된다.

이 시점의 컨텍스트 맵은 조금 더 흥미로워진다.

```
      재무 컨텍스트                        보험 컨텍스트

      ┌──────────┐                    ┌──────────┐
      │  Payment  │ ─────────────────▶ │  Payment  │
      └──────────┘                    └─────┬────┘
                                             │
                                             ▼
                                       ┌─────────────┐
                                       │ PolicyPeriod │
                                       └─────────────┘

      새 결제가 발생하면...            그것이 감지되어 새 보험 기간이
                                     시작되고 증서가 발송된다
```

*그림 29-6. 재무와 보험 두 도메인에 걸친 보험료 결제 (SBD 11장 그림 11.3 기준)*

모놀리스를 두 시스템으로 나누는 전환은 꽤 순조롭다. 아마도 모두가 아직 도메인 전체에 익숙하고 무엇이 `Payment`이고 무엇이 `PolicyPeriod`인지 분명하기 때문일 것이다. 그러나 그것도 곧 변한다.

두 시스템은 여러 방식으로 서로 의존한다. 주요 연결 중 하나가 이것이다. 재무 시스템에서 `Payment`가 발생하면 그 이벤트가 보험 시스템에 보고되고, 보험 시스템은 새 `PolicyPeriod`를 만들어 증서를 자동 인쇄·발송한다. 보험 시스템이 재무 시스템의 결제 등록에 반응한다는 것은 분명하다. 보험 시스템은 `Payment`를 개념으로 알고 있지만, **그런 결제가 어떻게 이뤄지는지의 세부는 알 필요가 없다.**

시간이 흐르며 두 팀은 점점 멀어진다. 재무 흐름 추적만으로도 일이 충분한데, 회사가 정비소와 배관공·목수 같은 기술자들과 새 파트너 프로그램을 계속 맺는다. 특이한 보험 상품을 관리하는 것도 종일 걸리는 일이다. 영업이 고객을 끌고 유지하려고 결합 상품과 리베이트를 계속 만들어 낸다. 두 팀은 함께 보내는 시간이 줄고 서로의 도메인에 대한 통찰도 줄어든다. 한 팀이 다른 팀이 구독하는 이벤트를 바꿔서 상대 코드를 깨뜨리는 일이 몇 번 있었고, 그때는 사이가 험악해지기도 했다.

그래도 어쨌든 굴러간다. 그것도 곧 변한다.

### 새로운 결제 유형

조직이 계속 성장해 이제 제품 관리자가 둘이 되었다. 보험 시스템과 그 팀을 맡는 사람, 재무 시스템과 그 팀을 맡는 사람이다. 각자 자기 백로그를 관리하고 서로 거의 소통하지 않는다. 경영진은 소통이 적은 것을 좋은 신호로 받아들인다. 개발 조직을 **서로 독립적으로 일할 수 있는 단위로 잘 쪼갠 증거**로 본 것이다. 그리고 이제 새 결제 유형이 도입되면서 치명적인 실수가 벌어진다.

재무 팀 백로그 최상단에 창구 현금 대신 **은행 지로(bank giro)** 로 결제하는 방법을 지원하라는 스토리가 올라온다. 지로는 고객이 자기 은행에 지시해 계좌에서 보험사로 자금을 이체하는 방식이다. 수표를 쓸 필요가 없고, 고객은 보험사의 계좌번호를 알 필요도 없다. 특별한 지로 번호를 쓰면 된다. 보험사는 고객이 알거나 신경 쓸 필요 없이 계좌를 재편하거나 은행을 바꿀 수 있다.

사업 부서가 지로 서비스를 제공하는 은행과 계약을 맺는다. 재무 시스템 제품 관리자가 "지로 결제 구현" 스토리를 백로그 상단에 올린다. 몇 스프린트 뒤 구현할 차례가 되고, 재무 개발 팀은 은행의 지로 결제 시스템과 연동하는 방법에 대한 문서를 받는다.

문서에 따르면 은행에서 가져올 수 있는 메시지는 세 종류다. `Payment`, `Confirm`, `Bounce`. `Payment`의 설명은 "지로 결제가 등록되었다"이다. 재무 팀은 이 메시지들을 은행에서 가져오기 시작한다. 그리고 은행에서 `Payment` 메시지를 받으면 그것을 **재무 시스템의 `Payment`로 간주한다.**

결제는 결제라는 것이 논리적으로 보인다. 그러나 **컨텍스트에 주의를 기울이는 것이 결정적**이라는 사실을 팀은 나중에 알게 된다. 문자열을 서로 맞춰 시스템 통합을 하는 것은 위험한 관행이다. 군대에서의 "명령(order)"이 창고에서의 "주문(order)"과 같지 않듯, 한 컨텍스트에서의 결제가 다른 컨텍스트에서 자동으로 결제로 해석되어서는 안 된다. 솔직히 말해 문서도 별 도움이 되지 않는다. 지로 이체의 속사정을 이미 알고 있지 않다면 말이다.

**표 29-4. 은행 지로 결제 메시지 (SBD 11장 표 11.1 기준)**

| 메시지 | 문서의 설명 | 자연스러운 해석 | 실제 의미 |
|---|---|---|---|
| `Payment` | 지로 결제가 등록되었다 | 좋아, 결제 완료 | **아직 돈이 이체되지 않았다.** 이체를 시도하겠다고 등록만 했다 |
| `Confirm` | 결제 처리 확인 | 어? 뭐 그러든지 | **돈이 이체되었다** |
| `Bounce` | 확인 대기 중, 재시도 예정 | 별일 아니군 | 이체 실패. 남은 시도 횟수가 0이면 **영구 실패** |

재무 팀은 보험 시스템과의 연동 지점을 건드리지 않으려고 조심한다. 앞서 말했듯 한 팀이 다른 팀 시스템을 깨뜨린 소동이 몇 번 있었다. 재무 팀은 **이전과 똑같은 방식으로** 보험 팀에 `Payment` 메시지를 보내도록 신경 쓴다.

보험 시스템 쪽에서는 재무의 `Payment` 메시지를 계속 대기한다. 그런 메시지를 받으면 대응하는 `PolicyPeriod`를 만들고, 그것이 새 증서를 구매자에게 발송하게 만든다. 그들은 그것이 현금 결제인지 지로 결제인지 모른다. **그리고 그것이 바로 좋은 점 아닌가?** 알 수 없고 알 필요도 없다. 관심사의 분리가 작동하고 있다.

그런데 함정이 있다. 이제 컨텍스트 맵을 다시 그리면 세 컨텍스트가 모두 보인다.

```
      은행 지로                재무                    보험

     ┌─────────┐          ┌─────────┐            ┌─────────┐
     │ Payment  │ ───────▶ │ Payment  │ ─────────▶ │ Payment  │
     └─────────┘          └─────────┘            └────┬────┘
     ┌─────────┐                                      ▼
     │ Confirm  │  ← 진짜 결제 완료를 의미        ┌─────────────┐
     └─────────┘     하는 것은 이것이다           │ PolicyPeriod │
     ┌─────────┐                                └─────────────┘
     │ Bounce   │
     └─────────┘

   지로 컨텍스트의 "Payment"는
   결제가 이뤄졌다는 뜻이 아니라
   등록되었다는 뜻일 뿐이다
```

*그림 29-7. 지로 결제가 세 도메인을 통과하는 경로 (SBD 11장 그림 11.5·11.7 기준)*

### 두 개의 미묘함

지로의 `Payment`가 재무의 `Payment`로, 그것이 다시 `PolicyPeriod`로 매핑된다. 자연스러워 보인다. 결제는 결제다. 그러나 두 개의 미묘함 때문에 이 접근은 건전하지 않다. 하나는 보험 도메인에, 하나는 지로 도메인에 있다.

**보험 도메인의 미묘함.** 보험 증서는 대부분의 상품과 다르다. 목걸이를 산다면 판매자가 나중에 받기로 합의할 수 있다. 제때 내지 않으면 판매자는 구매를 취소하고 목걸이를 돌려 달라고 요구할 수 있다. 이것이 통상적인 상거래 관행이다.

그런데 어떤 상품에서는 이것이 통하지 않는다. 보험 증서가 그렇다. 구매자가 돈을 내지 않았다고 해서 구매를 취소하는 것이 성립하지 않는 종류의 상품이다. 그동안 구매자는 이미 **보장의 혜택을 누린 뒤**이고, 그것은 되돌려 받을 수 없다.

보험을 파는 것은 복권을 파는 것과 같다. 추첨 전에 구매자가 표값을 내도록 판매자가 보장해야 한다. 추첨 후에 꽝이 된 표에 돈을 내려는 사람은 거의 없기 때문이다. 마찬가지로, 사고 하나 없이 지나간 기간에 대해 자동차 보험료를 내려는 사람이 누가 있겠는가.

보험사(또는 복권 판매자)가 신뢰할 만한 단골 고객으로부터 **미수 채권 형태의 결제** — 채무 증서 같은 것 — 를 받아들일 수는 있다. 그렇게 하는 것은 고객이 나중에 빚을 청산할 것이라고 신뢰하는 일이다. 그러나 이 이야기의 회사를 포함해 대부분의 보험사는 **보험이 효력을 갖기 전에 돈이 들어와 있을 것**을 요구한다.

**지로 도메인의 미묘함.** 앞의 표에서 봤듯, 은행의 `Payment` 메시지는 지로 결제가 **등록되었다**는 뜻이지 돈이 이체되었다는 뜻이 아니다. 지로 용어로 그것은 결제 요청이 접수되었고 적절한 시점(예컨대 그날 밤의 대규모 배치 처리 시간)에 처리될 것이라는 신호다. 돈이 실제로 이체되면 지로 결제가 완료된 것이고 확인될 수 있다. 그래서 `Confirm` 메시지가 있다. 이체가 완료되지 못하면 — 예컨대 출금 계좌에 잔고가 없어서 — 지로 결제는 반송(bounce)되었다고 하며 보통 몇 차례 재시도된다. 그래서 `Bounce` 메시지가 있다.

이 두 미묘함이 결합하면 재앙이 된다. **고객이 보험료를 내기 전에 자동차 보험의 보장을 누린다.** 그러나 이야기 속의 재무 팀과 보험 팀, 보험 계약자들, 회사 전체는 아직 앞일을 모른 채 행복하다. 회사는 새 결제 방식을 출시한다.

### 사고 차량, 늦은 결제, 그리고 소송

기존 고객들이 편리한 새 결제 방식을 쓰기 시작하고 신규 고객도 가입한다. 한동안 잘 굴러간다. 그러던 어느 날 한 고객이 자동차 보험 보험금을 청구한다. 증거로 그는 우편으로 받은 **보험 증서**를 제시한다. 그 증서에는 새 기간을 보장하는 연장된 날짜가 찍혀 있다. 문제는 그가 그 기간의 보험료를 내지 않았다는 것이다.

무슨 일이 있었는가. 지로 결제는 정상적으로 등록되었다. 그러나 결제일에 고객의 계좌에 잔고가 부족해 출금이 거절되었다. 그다음 주에 몇 차례 재시도가 있었지만 끝까지 잔고가 없어 결제는 완료되지 않았다. 그런데도 보험 시스템은 갱신 증서를 그에게 발송했다. 돈을 내지 않아도 되는 것이 반가웠던 고객은 이 상태를 몇 달이고 이어 갔다. 자기 차를 들이받기 전까지는. 그러자 고객은 서둘러 밀린 보험료를 냈다. **사후에.**

이상한 일은 하나도 일어나지 않았다. **시스템은 설계된 대로 동작했다.**

지로로 결제하는 고객의 보험이 갱신 시점에 도달하면, 재무 시스템이 새 결제 요청을 만들어 고객의 은행으로 보낸다. 요청을 받은 은행은 재무 시스템에 `Payment` 메시지를 회신한다. 재무 시스템은 이것을 창구 현금 결제와 **똑같이 취급한다.** 두 가지가 같은 것으로 개념화되어 있기 때문이다. `Payment` 메시지를 받으면 그것을 보험 시스템으로 전달하고, 보험 시스템은 보험 기간을 연장하고 갱신 증서를 계약자에게 발송한다.

흥미로운 것은 **일어나지 않은 일**이다. 계좌에 잔고가 없었으므로 이체는 결코 일어나지 않았고 `Confirm` 메시지도 결코 오지 않았다. 그런데 재무 시스템은 `Payment` 메시지만 듣고 있었으므로 **누락된 `Confirm`은 아무도 알아채지 못했다.** 은행 시스템은 `Bounce{remaining_attempts: 3}` 메시지를 보내 이체하지 못했지만 세 번 더 시도하겠다고 알렸다. 재무 시스템은 `Bounce{remaining_attempts: 0}` — 은행이 마침내 출금을 포기했다는 뜻 — 이 올 때까지 이 메시지들을 무시해도 무방했다.

보험사가 지로 결제를 처음 받기 시작했을 때 반송 후 포기 시나리오는 완전히 무시되었다. 이런 경우를 잡아 낼 (번거롭지만) 수작업 절차가 따로 있었기 때문이다. 나중에 재무 시스템에 이런 상황을 탐지해 고객을 감시 목록에 올리는 기능이 개발되었다. 회사는 연체 고객에게 연락하고 독촉장을 발송하기 시작했다. 그런데 **이 기능은 순수하게 재무 문제로 간주되었다.** 보험 시스템은 이 마지막 `Bounce`를 끝내 알지 못했고, 고객이 결제했다고 계속 믿었다.

여기가 어긋나는 지점이다. 우리가 두 가지 모두를 "결제"라는 말로 부르지만, **지로 결제는 창구 현금 결제와 같지 않다.** 후자의 경우 보험사는 돈을 즉시 손에 넣는다. 전자의 경우 은행이 지로 결제를 처리하기 전까지 보험사는 돈을 받지 못한다. 세 번 재시도 후에도 계좌에 돈이 없으면 이체는 없고 보험사는 대금을 받지 못하지만, 보험 시스템은 그럼에도 새 증서를 발송한 뒤다.

### 판결이 정한 것

회사는 사고 차량 소유자가 보상받을 자격이 없다고 주장했다. 그는 기한 내에 보험료를 내지 않았다. 발송된 증서는 시스템 버그의 결과다. 사고 후에 보험료를 낸 것은 유효한 결제로 인정되지 않으며 명백히 사후 무마 시도다. 사고 후에 결제했다고 해서 결제하지 않은 기간에 대한 소급 보장을 받을 자격이 생기지는 않는다.

반면 차주는 사고 당일 자기에게 **유효한 증서가 있었고**, 보험료를 냄으로써 금전적 의무를 이행했다고 주장했다. 양측 모두 물러서지 않아 사건은 법정으로 갔다.

재판에서 판사는 **계약자의 손을 들어 주었다.** 판사는 갱신 증서를 회사가 계약의 계속을 승낙했다는 증거로 해석했다. 결제가 아직 완납되지 않았다면, 회사는 **미수 채권 형태의 결제를 명백히 승낙한 것**이다. 법적으로 회사는 자신이 발행한 증서에 구속된다.

증서가 없었다면 판사가 어떻게 판단했을지는 짐작만 할 수 있다. 그러나 갱신 증서가 발송되지 않았더라면 회사는 미수 채권을 결제로 받아들이지 않았다고 다툴 수 있었을 것이고, 판결은 회사에 유리하게 났을 가능성이 높다. 요점은 이것이다. **회사가 실제로 사업을 영위한 방식이 그 의도가 법적으로 어떻게 해석되는지를 규정했다.**

지로 결제와 현금 결제를 동렬에 놓은 개념화가 실수였다 해도, 그것이 회사가 사업을 한 방식이었으므로 의도적인 것으로 해석되었다. 법원은 증서 발송이 버그인지, 실수인지, 잘못된 사업 판단인지에 관심이 없었다. 회사는 지로 결제(요청)를 현금 결제처럼 취급하는 것**처럼 행동했고**, 그 행동에 책임을 져야 했다.

이 판결은 이 책 전체에서 되풀이되는 명제의 가장 극적인 사례다. **소프트웨어가 무엇을 하는가는 조직이 무엇을 의도하는가로 해석된다.** 26.8절이 데이터의 출처 검증을 설계 관점에서 재정리하며 말한 것, 30.7절이 입력을 그대로 반향하지 말라고 하는 것도 결국 같은 이야기다. 시스템이 하는 말은 조직의 말이다.

### 버그는 어디에 있는가

회사가 증서를 내주면 안 되는데 내주는 이 상황은 분명히 버그다. 그런데 **그 버그는 어디에 있는가.** 개별 시스템으로 돌아가 보면, **어느 것도 자기 도메인의 기준에서 부당한 일을 하지 않는다.**

- **은행 지로 시스템**은 마땅히 할 일을 한다. 명명이 좀 이상하다고 할 수는 있지만, 그렇지 않은 도메인이 어디 있는가.
- **재무 시스템**은 완결되지 않은 자금 이체(지로 결제)를 고객으로부터의 결제로 간주한다. 버그라고 주장할 수 있다. 그러나 엄격히 재무 도메인의 관점에서 이것은 완벽하게 합당하다. 결제는 여러 형태로 이뤄질 수 있고 현금은 그중 하나일 뿐이다. 많은 맥락에서 차용증(IOU)이나 다른 미수 채권 형태의 결제를 받아들이는 것이 정상이다.
- **보험 시스템**도 정확히 해야 할 일을 한다. 보험료 결제를 감지하고 새 보험을 발행한다.

시스템 통합 중 어느 하나에 버그가 있다고 말하기도 어렵다. 외부 은행과 재무 시스템 사이의 통합을 보자. 등록되었지만 완료되지 않은 지로 결제는 **고객이 지불 의사를 선언한 것**으로, 그리고 회사가 그것을 승낙해 돈이 이체될 때까지 채권 상태에 있는 것으로 충분히 해석될 수 있다.

**세 도메인의 미묘함을 한자리에 모아 동시에 볼 때에만** 이 상황이 건전하지 않다는 것이 보인다. 이것이 이 사례가 서점 사례와 다른 점이자, 마이크로서비스 아키텍처에서 특히 위험한 점이다. 서점에서는 적어도 `-1`이라는 값이 어딘가에 찍혀 있었다. 여기서는 어느 시스템의 어느 로그를 뒤져도 잘못된 값이 없다.

### 어떻게 피할 수 있었는가

이 상황을 피하려면 세 도메인 — 지로 이체, 재무, 보험 — 전문가들 사이의 협업과 소통이 필요했다. 어떻게 그들이 서로 이야기하게 만들 수 있었을까. 늦게라도, 그러나 되도록 일찍.

**기술적 의존을 깨뜨리지 않으려는 태도가 명백한 방해 요인이었다.** 그 태도가 재무 팀으로 하여금 의미가 갈라졌는데도 같은 기술적 구성물 `Payment`를 재사용하게 만들었다. 그 시점에 "결제"라는 단어는 **창구에서의 즉시 결제**와 **은행에 보낸 결제 요청** 두 가지를 동시에 뜻하게 되었다. 그런데도 보험 팀을 방해하지 않으려는 마음에 재무 팀은 두 경우 모두에 `Payment`라는 이름을 계속 썼다. 안타깝게도 **바로 그것이 보험 팀에게 재앙을 안긴 원인이었다.** 보험 팀에게 두 종류의 결제는 같은 것이 아니었기 때문이다. 창구에서의 즉시 결제는 갱신 증서를 발행할 건전한 근거였지만, 은행에 보낸 결제 요청은 그렇지 않았다.

대신 무엇을 했어야 하는가. 명백한 답은 재무 팀이 `Payment`가 아니라 지로의 `Confirm` 메시지를 들었어야 한다는 것이다. `Confirm`이 거래 완료를 표시하고, 그것이 보험사가 증서 발행의 건전한 근거로 여기는 것이다. 그런데 **어떻게 그런 일이 일어날 수 있었을까.** 무엇이 재무 팀으로 하여금 다른 매핑을 하게 만들었을까.

다른 시나리오를 그려 보자. 새 결제 옵션이 도입되는 시점에 당신이 재무 팀의 프로젝트 관리자나 기술 리드라고 하자. 당신은 **의도적인 컨텍스트 매핑**으로 이것을 구현하도록 팀을 이끌기로 한다. 그리고 지금까지 팀이 결제라고 불러 온 것이 무엇이었는지 멈춰서 생각한다. 현금 결제만이 존재하던 시절에 그 개념은 충분히 구체적이었다. 그러나 지로 결제를 추가하려는 지금은 더 이상 그렇지 않다.

팀과 논의한 끝에 당신은 용기를 내어 도메인을 리팩터링해 기존의 `Payment`를 **`CashPayment`로 바꾼다.** 그것이 실제로 그것이기 때문이다. 양쪽 모두의 이익을 위해, 하류에 있는 보험 팀과 이 이름 변경에 대해 이야기해야 한다고 메모해 둔다.

그런데 잊어버린다면? 혹은 보험 팀과 이야기할 생각이 아예 들지 않는다면? 그들이 바로 그 `Payment` 메시지를 듣고 있다는 사실을 모른다면? `Payment`를 `CashPayment`로 리팩터링해 프로덕션에 배포하고 나면, 보험 팀의 누군가가 찾아와 기대하던 `Payment` 메시지가 어디 갔느냐고 묻는 것은 시간 문제다. 다른 것은 몰라도 **논의가 일어난다.** 그때는 외교력이 필요하겠지만.

농담을 걷어 내고 말하면, 기술적 의존을 깨뜨리는 것이 바람직하지는 않다. **그러나 결정적인 도메인 논의가 일어나게 하는 데 그것이 필요하다면, 그럴 만한 가치가 있다.** 이것이 47.8절의 "각 서비스는 하나의 바운디드 컨텍스트다"가 실무에서 뜻하는 바이며, 47.4절이 잘못 적용된 DRY를 경고하는 이유이기도 하다. 같은 이름의 두 개념을 하나로 유지하는 것은 재사용이 아니라 **의미의 은폐**다.

이름을 바꾸고 나면 재무 도메인과 이웃 도메인들의 컨텍스트 맵을 그릴 수 있다. 지도를 보면 무엇이 무엇에 매핑되어야 하는지 검토할 수 있다. **지로 결제가 매핑될 만한 것이 재무 도메인에 아무것도 없다**는 사실이 꽤 분명해진다. `CashPayment`는 확실히 맞지 않는다. `CashPayment`를 추상화해서 지로 결제까지 담을 수 있는 무언가로 만들고 싶은 유혹이 생긴다. 그러나 그 유혹을 이겨야 한다. **먼저 깊은 통찰을 얻고 나서 추상화하는 것이, 통찰 없이 성급히 추상화하는 것보다 훨씬 낫다.**

구체적인 것을 먼저 선호해 재무 도메인에 새 타입 `GiroPayment`를 추가한다. 그런데 그것이 무엇에 매핑되어야 하는지에서 여전히 막힌다. 지로 도메인의 `Payment`가 좋은 후보로 보이지만, 지로 결제의 미묘함에 대한 통찰이 부족해 성급한 결론을 내릴 위험이 있다.

### 의도적 발견

혼자서 갈 수 있는 데까지 갔다고 느낀 당신은 관련된 모든 분야의 전문가를 만날 때가 되었다고 판단한다. 보험 팀의 도메인 전문가와 재무 부서(또는 은행)의 전문가 — 그중 지로 결제에 밝은 사람 — 를 작은 워크숍에 초대한다. 이 시점에 당신이 찾는 것은 **외부 지로 도메인이 재무 도메인에 어떻게 매핑되는지를, 보험 도메인을 고려하면서 의도적으로 발견하는 것**이다. 사소한 일이 아니며, 그래서 그 발견이 일어나도록 무대를 의도적으로 마련한다.

**의도적 발견(deliberate discovery)의 소리**는 한 도메인의 전문가가 다른 도메인의 전문가에게 통찰을 얻고 "아, 알겠다"고 말하는 소리다. 반대로 **늦은 발견의 소리**는 마감 직전에 근본적인 실수를 발견한 사람이 "아니, 그럴 리가 없어!"라고 외치는 소리다. 그는 그것을 고치느라 밤낮으로 일하게 된다.

```
  획득한 통찰
      ▲
필요 수준 ┼─ ─ ─ ─ ─ ─ ─ ─"아, 알겠다" ─ ─ ─ ─ ─ ─ ─ ─ ─   ← 아낀 고통의 영역
      │              ╱  의도적 발견의 경로
      │           ╱
      │        ╱   프로젝트 초기의
      │     ╱      놀라운 통찰
      │  ╱                        ╱ 우연한 발견의 경로 ──── "아, 안 돼!"
시작 수준 ┼───────────────────────╱                        프로젝트 후반의
      └────────────────────────────────────────▶          결정적 통찰
                                          시간
```

*그림 29-8. 이른 의도적 발견과 늦은 우연한 발견의 차이 (SBD 11장 그림 11.12 기준)*

워크숍에서 오갈 법한 대화는 이렇다. 보험 전문가 폴리, 재무의 앤, 은행 시스템을 잘 아는 방크가 참석한다.

> "새 결제가 들어오면 무슨 일이 일어나죠?" 폴리가 묻는다.
> "글쎄요, 지로로 결제를 받는 거죠." 재무의 앤이 답한다.
> "그게 은행에서 `Payment` 메시지를 받는 시점인가요?" 폴리가 확인한다.
> "네, 결제가 등록되는 시점입니다." 은행 시스템 전문가 방크가 말한다.
> "좋아요, 그러면 우리 손에 돈이 있는 거고, 새 증서를 발행할 수 있겠네요." 폴리가 결론을 내린다.
> "잠깐요. 저는 돈이 우리 손에 있다고 말한 적 없는데요." 방크가 항의한다.
> "방금 그러셨잖아요." 앤이 어리둥절해하며 반박한다.
> "아니요, 결제가 **등록되었다**고 했지 **확인되었다**고는 안 했습니다." 방크가 설명한다.
> "그러면 우리가 돈을 못 받았다는 뜻인가요?" 폴리가 소리 내어 묻는다.
> "맞습니다. 은행은 결제 요청을 등록했을 뿐이고 돈은 아직 이체되지 않았어요. 보내는 계좌에 잔고가 충분하면 다음 야간 배치에서 이체될 겁니다." 방크가 명확히 한다.
> "아, 그건 문제가 안 되죠." 재무의 앤이 말한다. "이체될 때까지 고객이 우리에게 빚진 상태라는 뜻이니까요. 그래도 자산의 이전은 이전이잖아요. 그걸로 됩니다."
> "안 됩니다!" 폴리가 자기 보험 전문성을 발휘하며 강하게 반박한다. "**진짜로-받은-결제**가 아니라 **주겠다고-약속한-결제**로는 보험을 시작할 수 없어요."
> "그렇다면 기다려야 할 것은 `Confirm` 메시지군요." 방크가 말한다.
> "아, 알겠다." 앤이 결론짓는다. 지로와 보험 도메인의 상호작용에 관해 미묘한 것을 하나 배운 것이다.

### 무엇이 진짜로 매핑되는가

이 회의에서 당신은 도메인들이 서로 어떻게 매핑되어야 하는지에 관한 의도적 발견을 촉진하는 데 성공한다. 새 매핑은 이렇게 된다.

```
      은행 지로                재무                        보험

     ┌─────────┐          ┌──────────────┐        ┌──────────────┐
     │ Payment  │          │ CashPayment   │───────▶│ CashPayment   │
     └─────────┘          └──────────────┘        └──────────────┘
     ┌─────────┐          ┌──────────────┐        ┌──────────────┐
     │ Confirm  │─────────▶│ GiroPayment   │───────▶│ GiroPayment   │
     └─────────┘          └──────────────┘        └──────┬───────┘
     ┌─────────┐                 ▲                        ▼
     │ Bounce   │                 │              ┌──────────────┐
     └─────────┘         진짜로 매핑되는 것은      │ PolicyPeriod  │
                          이쪽이다                └──────────────┘
```

*그림 29-9. 완전한 매핑을 갖춘 세 도메인의 지도 (SBD 11장 그림 11.13 기준)*

이 시점에서 당신은 이 업무에 대한 깊은 지식을 갖게 되었다. 보험이 갱신되려면 **돈이 이체되었다는 확인이 있어야 한다**는 것을 이해한다. 이제 추상화를 정의할 준비가 되었다. 앞서 통찰을 얻을 때까지 미뤄 두기로 한 바로 그 일이다.

한 가지 선택지는 새 추상화 **`PolicyPayment`** 를 추가하는 것이다. 이것은 재무 시스템이 새 보험 기간에 대한 결제를 수령했을 때 생성된다.

- `CashPayment`의 경우 창구에서 전액이 지불되었음을 알기 때문에 **즉시** 생성된다.
- `GiroPayment`의 경우 재무 시스템이 은행으로부터 결제 완료를 알리는 **`Confirm` 메시지를 받았을 때에만** 생성된다.

보험 시스템은 기존의 `Payment` 메시지 대신 이 새 메시지 유형을 듣고, `PolicyPayment`를 받으면 새 `PolicyPeriod`를 만든다.

이 해법에서 주목할 점은 **`PolicyPayment`가 재무 도메인의 개념이 아니라 두 도메인의 계약**이라는 것이다. 이름 자체가 "보험을 발행해도 되는 결제"라는 의미를 담고 있다. 처음의 `Payment`는 이 의미를 담고 있지 않았고, 담고 있는 척했다. 결함은 그 척함에서 나왔다.

> **이 절이 뒷받침하는 것**
>
> - 서비스 경계가 곧 컨텍스트 경계라는 원칙 → **47.7** (마이크로서비스란 무엇인가), **47.8** (각 서비스는 하나의 바운디드 컨텍스트다)
> - 서비스를 넘나드는 데이터의 의미 변질 → **47.9** (서비스를 넘나드는 민감 데이터), **24.8** (서비스 경계를 넘는 민감 데이터)
> - 컨텍스트와 컨텍스트 맵의 개념 자체 → **42.6** (바운디드 컨텍스트), **42.7** (컨텍스트 간 상호작용)
> - 같은 이름을 공유하는 두 개념을 억지로 하나로 유지하는 위험 → **47.4** (잘못 적용된 DRY)
> - 시스템이 하는 일이 조직의 의도로 해석된다는 사실 → **26.8** (데이터의 출처를 검증하라), **41.1** (보안은 관심사다)

## 29.6 얕은 모델이 로직 결함을 만든다 — 얕은 모델의 발생 경로, 암묵적 개념의 위험

앞의 세 절은 서로 다른 세 개의 이야기였다. 서점은 하나의 값이, 보험사는 하나의 단어가 문제였다. 29.2절의 열두 사례는 그보다 더 잡다했다. 이제 이 전부를 하나의 진단으로 묶는다.

이런 상황은 대개 **처음 그럴듯해 보이는 모델에서 멈춘 모델링**의 결과다. 더 파고들지 않고, 의심하지 않고, 계획이나 숙고 없이 멈춘다. 이 즉흥적 방식을 **얕은 모델링(shallow modeling)** 이라 부르자. 그 반대편에 **깊은 모델링(deep modeling)** 이 있다.

### 얕은 모델은 어떻게 생기는가

"어떻게 이런 일이 벌어질 수 있었는가"부터 묻자. 사후에 보면 수량이 아무 제약 없는 정수일 수 없다는 것은 자명해 보인다. 그런데 왜 누군가는 그렇게 설계했는가.

설계란 소프트웨어를 개발하며 내리는 모든 능동적 결정이다. 이 경우 설계에는 **수량을 제약 없는 정수로 만든다는 (능동적) 선택**이 포함되어 있었다. 깊이 숙고된 결정이 아니었을 수는 있지만, 그럼에도 결정이었다.

온라인 판매 도메인에는 개념이 많다. 어떤 것은 더 중요하고 어떤 것은 덜하다. 설계할 때 누군가는 가장 핵심적인 개념을 고른다. 주문, 주문 라인, 도서, 수량 같은 것들이다. 그런데 설계의 주된 관심이 **"이것을 어떻게 표현하지?"** 라는 질문에 답하는 데 쏠려 있는 경우를 자주 본다. 이 사고방식에서 설계란 코드로 옮길 방법을 찾는 일이고, 그 방법을 찾으면 끝난다. 그리고 업무와 코드 사이의 최단 거리는 **언어 기본형** — 정수, 실수, 불리언, 문자열 — 으로 표현하는 것이다.

도메인의 서로 다른 것들이 서로 다른 방식으로 표현된다. 어떤 것은 명시적으로, 어떤 것은 암묵적으로.

- 모델에는 **주문**이라는 개념이 있고, 주문에는 금액이 있다.
- 주문은 **주문 라인**들로 이뤄지고, 각 라인에는 **도서**와 **수량**이 있다.
- 도서에는 제목, ISBN, 가격이 있다.

주문, 주문 라인, 도서는 **명시적 개념**이다. 수량, 제목, ISBN, 가격은 정수와 문자열로 표현된 **암묵적 개념**이다. 달리 말해 수량은 제약 없는 정수다. 이렇게 놓고 보면 이상하다. 주문·주문 라인·도서는 잘 다듬어졌는데 수량만 아무 고려 없이 정수로 남았다. 왜 이렇게 되었을까.

원인의 상당 부분은 **모델링이 불완전했거나 아예 없었다**는 데 있다. 프로젝트 초기에 영업 담당 살(Sal Esperson)과 개발자 데브(Deve Loper) 사이에 오갔을 법한 대화를 상상해 보자.

> "그다음에 주문에 책을 담을 수 있어요." 살이 말한다.
> "책은 어떻게 기술하죠?" 데브가 묻는다.
> "제목하고 가격을 보여 줍니다." 살이 답한다.
> "가격은 어떤 값이 될 수 있죠? 항상 정수인가요?" 데브가 묻는다.
> "아니요, 책값이 19.50달러일 수 있어요. 세금 별도로요." 살이 명확히 한다.
> 데브는 생각한다. "그러니까 책은 제목과 가격을 속성으로 갖는다. 제목은 문자열. 가격은 int가 아니라 float."
>
> "책에 그게 전부인가요?" 데브가 묻는다.
> "아뇨," 살이 답한다. "ISBN도 중요해요. 양장본하고 문고본을 구분해야 하니까요."
> "알겠습니다. 그리고 주문에 책을 담고요." 데브가 말한다. "예를 들면 『모비 딕』, 『오만과 편견』, 『햄릿』, 『모비 딕』 하나 더, 『1984』, 『모비 딕』 또 하나?"
> "거의 맞아요. 저희는 『모비 딕』 세 권이라고 말하죠. 어떤 순서로 사는지는 중요하지 않으니까요."
> 데브는 생각한다. "float가 아니라 int군."

여기서 두 개의 경고가 필요하다. 첫째, **돈을 절대로 float로 표현하지 말 것.** 둘째 — 그리고 이 장의 주제인데 — **모델링을 "정수예요"에서 끝내지 말 것.**

나중에 이 논의가 코드가 된다. 데브는 `title`, `isbn`, `price` 속성을 갖는 `Book` 클래스를 만든다. `Order` 클래스에는 `addOrderLine(Book book, int quantity)` 메서드가 생긴다.

```java
class Book {
    String title;
    String isbn;
    double price;
    // ...
}

class Order {
    void addOrderLine(Book book, int quantity) {
        // ...
    }
}
```

주문·주문 라인·도서는 명시적 표현을 얻었으므로 각각 클래스가 되었다. 타입 시스템이 이것들이 올바른 자리에 쓰이도록 강제한다. `Book`이 기대되는 자리에 다른 것을 넘기면 컴파일 오류가 난다.

반면 수량은 기본형 `int`로 암묵적으로 표현되었다. 수량의 사용은 타입 시스템과 컴파일러의 강제를 받지 않는다. 바깥 기온 같은 다른 정수를 실수로 넘겨도 컴파일 오류가 나지 않는다. 수량이 기대된다는 유일한 힌트는 `quantity`라는 **파라미터 이름**뿐이다.

이 대화에서 데브는 제목이 무엇인지, ISBN이 무엇인지에 대해 더 묻지 않는다. 그냥 텍스트라고 결론짓고 `String`으로 표현한다. 그러나 제목이 아무 문자열이나 될 수는 없을 것이고, ISBN은 확실히 아니다.

데브가 모델링에 무능한 것도 아니다. 그는 가격의 성질에 대해 흥미로운 질문("항상 정수인가요?")을 던진다. 그러나 거기서 멈춘다. 살이 "세금 별도로요"라고 답할 때 가격이 더 복잡할 수 있다는 힌트도 완전히 놓친다. 데브를 움직인 동기는 **"이것을 코드로 표현할 수 있는가"** 였지 **"이것이 어떻게 동작하는지 내가 이해하는가"** 가 아니었다.

### 암묵적 개념의 위험

이런 얕은 모델링은 흥미로운 업무 개념을 기본형 — `int`, `float`/`double`, `String`, `boolean` — 으로 표현하는 결과를 낳는다. 그리고 이런 암묵적 표현은 실무에서 대단히 흔하다. 거의 모든 것이 문자열과 정수와 실수로 표현된 시스템을 자주 본다. 여기에는 몇 가지 부작용이 있다.

**첫째, 타입이 결정적 제약을 담지 못한다.** 수량을 기본형 정수로 남긴 것이 심각한 보안 문제를 일으킬 수 있다는 것을 우리는 이미 보았다. 마찬가지로 제목과 ISBN을 제약 없는 문자열로 두면 너무 많은 여지를 준다. 시스템이 어떤 데이터가 올바른 ISBN 형식이라고 가정하는데 실제로는 아닐 때 기묘한 일들이 벌어진다.

> −20억에서 20억 사이의 아무 정수나 될 수 있다는 것은 무언가의 좋은 표현인 경우가 드물다.

**둘째, 취급 규칙이 타입에 붙지 못한다.** 신용카드 번호와 주민등록번호는 문자열로 표현된 암묵적 개념의 흔한 예다. 이렇게 하면 유효하지 않은 카드 번호나 주민번호가 들어올 위험, 형식조차 맞지 않을 위험이 생긴다. 그런데 더 나쁜 것은 **제대로 취급하지 않을 위험**이다. 카드 번호와 주민번호는 노출, 로그 기록 등에 강한 제약이 있다. 문자열로 표현되면 실수로 로그에 남거나 화면에 표시될 위험이 있다. 이것을 도메인 클래스로 표현하면 그런 실수를 피할 수 있다. 예컨대 읽기 1회 객체(read-once object)가 그런 장치다(→ 44.5).

**셋째, 기본형은 서로 구별되지 않는다.** 다음 메서드 시그니처를 보자.

```java
void addCust(String name, String phone, String fax, int creditStatus,
             int vipLevel, String contact, String contactPhone, boolean partner)
```

파라미터가 여덟 개뿐인데, 두 개를 실수로 바꿔 넣으면 고객이 받아서는 안 될 신용 등급이나 VIP 등급을 받게 된다. `creditStatus`와 `vipLevel`이 모두 `int`이므로 컴파일러는 순서가 바뀐 것을 잡아 주지 못한다. 이런 실수는 미묘하고 찾기 어려운 버그로 이어지며, 때로는 보안적 함의를 갖는다. 여덟 개는 긴 목록도 아니다. 전부 문자열인 수십 개의 파라미터 목록도 있다. 특히 생성자가 이 문제에 취약하다(→ 47.2, 44.8).

**얕은 모델링과 그 결과인 암묵적 개념은 버그가 많고 안전하지 않은 코드를 낳을 위험을 크게 높인다.**

### 깊은 모델은 어떻게 나타나는가

대안은 깊은 모델링과 명시적 개념을 향한 더 의식적인 접근이다. 앞의 대화가 깊은 모델링의 사고방식으로 진행되었다면 어떻게 달라졌을지 보자. 가격에 대한 질문까지는 같다. 다만 데브는 "세금 별도"라는 힌트를 놓치지 않고 나중에 파고들 문제로 메모해 둔다. 그리고 수량에서 멈추지 않는다.

> "『모비 딕』을 반 권 살 수 있나요?" 데브가 묻는다.
> "당연히 안 되죠."
> "**수량**이라는 말을 쓰셨는데요," 데브가 말한다. "그걸 더 이해하고 싶습니다. 『모비 딕』 수량 3이 있다가 전부 빼면 수량 0인 『모비 딕』이 되는 건가요?"
> "음, 아니에요. 수량 0은 사실 수량이 아니죠. 저희는 수량이 없다고 말합니다." 살이 명확히 한다.
> "이 수량에는 규칙이 좀 있는 것 같군요." 데브가 말한다. "그럼 수량은 얼마나 클 수 있죠? 20억 권?"
> "하하. 그럴 리가요. 진지하게 답하면, 매장 통과 물류 흐름에 제약이 있어서 총수량 240을 넘는 주문은 처리할 수 없어요."
> "매장 통과 흐름이요?" 데브가 묻는다.
> "네, 그렇게 부릅니다. 온라인 주문이 창고에서 처리되는 방식인데, 상자 크기하고 포장 스테이션 같은 것들이죠. 그보다 큰 주문은 창고 벌크 흐름으로 가야 하는데, 온라인 서점에서는 그걸 쓸 수 없어요."
> "주문의 총수량이란 게 뭐죠? 예를 들어 주실 수 있나요?"
> "모든 책의 수량을 더한 겁니다. 『햄릿』 3권, 『오만과 편견』 4권, 『모비 딕』 1권이면 총수량 8이죠."

**모델링할 때는 상한을 논의하라. 언제나 흥미로운 정보가 나온다.**

데브는 개별 수량이 240을 넘을 수 없고 주문 총수량도 마찬가지라고 메모한다. 나중에 이 지식이 코드로 포착된다.

```java
class Book {
    BookTitle title;      // 도서가 자기 클래스를 갖듯
    ISBN      isbn;       // 제목과 ISBN도 자기 클래스를 갖는다
    Money     price;
    // ...
}

class Quantity {
    // 수량이 얼마나 작거나 클 수 있는지의 제약을 담는다
    // — 업무적 통찰이 코드로 포착된 것
    Quantity(int quantityOfBooks) {
        isTrue(0 < quantityOfBooks, "Quantity must be positive");
        isTrue(quantityOfBooks <= 240,
               "Quantity must fit in through-store flow, which is limited to 240");
        // ...
    }
}

class Order {
    // 잘못된 수량이 들어올 위험이 없다. 컴파일러가 허용하지 않는다.
    void addOrderLine(Book book, Quantity quantity) {
        // ...
    }

    Quantity totalQuantity() {
        // ...
    }
}
```

`Quantity` 클래스가 존재하는 순간 안티햄릿은 **표현 불가능해진다.** 방어 코드를 어디에 넣을지 고민할 필요가 없다. 애초에 `-1`을 담은 `Quantity` 객체를 만들 수 없기 때문이다. 서점 이야기의 온갖 하위 시스템 — 청구, 미수금 원장, 재고, 배송 — 은 아무것도 고칠 필요가 없다. 그들이 음수를 받게 되는 경로가 사라졌다.

이런 개념을 전부 명시적으로 만들면 클래스가 너무 많아진다는 반론이 흔하다. 그러나 **그 클래스들 안의 코드는 어차피 필요한 코드다.** 흥미로운 업무 규칙은 어딘가에는 코드로 잡혀야 하고, 그러지 않으면 더 나쁜 시스템을 만드는 것이다. 개념을 클래스로 갖는 것은 **코드의 조직 방식**을 바꾼다. 흥미로운 개념을 자기 클래스로 뽑아내면, 같은 코드가 거대한 서비스 클래스의 메서드들 안에 흩어져 있을 때보다 찾기 쉬워진다.

> **모델링할 때는 암묵적 개념을 명시적으로 만들라.**

`Quantity`는 **도메인 프리미티브(domain primitive)** 라 불리는 것의 한 예다. 이 개념과 그것으로 만드는 코드 구조는 43장과 44장이 본격적으로 다룬다. 그리고 얕은 모델이 어떻게 생기고 깊은 모델이 어떻게 나타나는지의 일반 이론은 42.8~42.9절에서 다시 정리한다. 여기서 필요한 것은 그 이론이 아니라, **로직 결함이라는 현상과 얕은 모델이라는 원인을 잇는 다리**다. 이제 그 다리를 놓자.

### 열두 사례를 얕은 모델로 다시 읽기

29.2절의 열두 사례는 서로 닮지 않았다. 그러나 그중 상당수는 **어떤 개념이 암묵적으로 남아 있었기 때문에** 생겼다. 코드에는 그 개념을 담을 이름이 없었고, 이름이 없으니 규칙도 붙지 못했으며, 규칙이 없으니 어긴 것을 아무도 알아채지 못했다. 몇 개를 골라 다시 읽어 본다.

**사례 6, 비즈니스 한도 우회하기.** 겉보기 결함은 `amount <= threshold`가 음수를 걸러 내지 못한 것이다. 그러나 암묵적으로 남은 개념은 **"이체 금액"** 이다. 이체 금액은 어떤 정수든 될 수 있는 값이 아니다. 양수여야 하고, 상한이 있으며, 통화 단위가 있고, 방향은 계좌 쌍이 정하는 것이지 부호가 정하는 것이 아니다. 이 규칙 중 어느 것도 `int`에는 붙어 있지 않다. `TransferAmount`라는 타입이 있었다면 승인 검사가 무엇을 하든 음수 이체는 존재할 수 없다. 서점의 `Quantity`와 정확히 같은 구조다(→ 47.6).

**사례 3, 체크아웃으로 진행하기.** 겉보기 결함은 단계 순서를 강제하지 않은 것이다. 암묵적으로 남은 개념은 **"주문의 상태"** 다. 코드에는 장바구니가 있고 결제 화면이 있고 배송 화면이 있었지만, "결제 완료된 주문"과 "결제 전 주문"을 구분하는 개념은 화면의 순서 안에만 있었다. 순서는 브라우저에 있고 브라우저는 사용자의 것이다. 주문이 `Unpaid`와 `Paid`라는 명시적 상태를 갖고, 배송이 `Paid` 상태의 주문만 받는 타입 시그니처를 가졌다면 강제 브라우징은 아무것도 하지 못한다(→ 44.10).

**사례 2, 비밀번호 변경 기능 속이기.** 암묵적으로 남은 개념은 **"요청자의 역할"** 이다. 역할이라는 개념이 코드에 존재하지 않았기 때문에, 개발자는 그것을 **파라미터의 유무**라는 간접 증거로 표현해야 했다. 간접 증거는 사용자가 통제한다. 세션에서 끌어온 명시적 `Role` 값을 검사했다면 이 결함은 성립하지 않는다.

**사례 5, 은행 털기.** 여기서는 서로 다른 두 개념이 **하나의 타입을 공유**했다. "지금 로그인한 사람"과 "신청서의 대상 고객"은 다른 개념인데 둘 다 `CCustomer`였다. 세션에 `AuthenticatedUser`가 있고 등록 절차가 `RegistrationApplicant`를 다뤘다면, 한쪽을 덮어써서 다른 쪽 권한을 얻는 경로가 없다. 재사용이 문제가 아니라 **의미가 다른 것에 같은 이름을 준 것**이 문제였다. 29.5절 보험사의 `Payment`와 같은 병이다.

**사례 1, 오라클에게 묻기.** 암묵적으로 남은 개념은 **"이 암호문이 무엇의 암호문인가"** 다. 인증 토큰과 표시 이름은 완전히 다른 신뢰 수준을 갖는 값인데, 코드에서는 둘 다 그냥 "암호화된 문자열"이었다. 타입이 같으니 서로의 자리에 대입할 수 있었고, 키가 같으니 실제로 작동했다. 토큰의 종류가 타입으로 구분되었다면 — 그리고 그 타입마다 키가 갈렸다면 — 대입 자체가 성립하지 않는다.

**사례 11과 12, 디버그 메시지와 로그인 경쟁.** 암묵적으로 남은 것은 **"이 데이터의 소유자"** 다. 오류 정보에도 인증 식별자에도 "누구의 것인가"라는 속성이 붙어 있지 않았고, 그래서 그것을 어디에 저장해야 하는지도 결정되지 않은 채 편한 곳 — 정적 변수 — 에 놓였다. 데이터에 소유자가 명시되어 있으면 저장 위치는 자동으로 결정된다. 세션에 속한 것은 세션에, 스레드에 속한 것은 스레드에.

**사례 7, 대량 할인 속이기.** 암묵적으로 남은 개념은 **"확정된 주문"** 이다. 장바구니와 주문이 같은 것으로 모델링되어 있었기 때문에, 아직 바뀔 수 있는 것 위에 최종 가격이 계산되어 저장되었다. 둘이 다른 타입이고 할인이 `Order`를 만드는 시점에만 계산된다면 담았다 빼는 조작으로 얻을 것이 없다.

**표 29-5. 사례별 암묵적 개념과 그것을 명시화한 이름**

| 사례 | 암묵적으로 남은 개념 | 명시화하면 |
|---|---|---|
| 6 비즈니스 한도 | 이체 금액의 허용 범위 | `TransferAmount` (양수, 상한, 통화) |
| 3 체크아웃 진행 | 주문의 결제 상태 | `Order` 상태 객체 (`Unpaid`/`Paid`) |
| 2 비밀번호 변경 | 요청자의 역할 | 세션에서 끌어온 `Role` |
| 5 은행 털기 | 세션 주체 vs 신청 대상 | `AuthenticatedUser` vs `Applicant` |
| 1 암호화 오라클 | 암호문의 종류 | 토큰 타입별 분리와 키 분리 |
| 11·12 정적 저장소 | 데이터의 소유자 | 세션 스코프·스레드 스코프 |
| 7 대량 할인 | 확정 전 장바구니 vs 확정된 주문 | `Basket` vs `Order` |
| — 서점 안티북 | 수량의 허용 범위 | `Quantity` (1 이상 240 이하) |
| — 보험 무료 증서 | 결제의 종류와 완결성 | `CashPayment`/`GiroPayment`/`PolicyPayment` |

물론 열두 사례 전부가 이렇게 환원되지는 않는다. 사례 8(이스케이프 문자 미이스케이프)과 사례 9(정제와 잘라내기의 순서)는 모델의 문제라기보다 **처리 파이프라인의 문제**이고, 그 처방은 43.4절의 검증 순서와 27.9절의 파라미터화에 있다. 사례 10(검색 남용)은 접근 통제가 인덱스까지 내려가지 않은 문제다. 그러나 나머지 대다수에서 진단은 하나로 모인다.

> **로직 결함의 상당수는 코드가 업무를 표현하지 못해서가 아니라, 업무의 어떤 개념이 코드에 이름을 갖지 못해서 생긴다.**

이름이 없는 개념은 규칙을 가질 수 없고, 규칙이 없는 개념은 위반될 수 없다 — 위반이 위반으로 인식되지 않기 때문이다. 안티햄릿이 몇 달 동안 아무 경보도 울리지 않은 이유가 이것이고, 무료 보험 증서가 법정에서 회사의 의도로 인정된 이유도 이것이다.

> **이 절이 뒷받침하는 것**
>
> - 얕은 모델의 발생 경로와 깊은 모델의 출현 → **42.8** (얕은 모델은 어떻게 생기는가), **42.9** (깊은 모델은 어떻게 나타나는가)
> - 암묵적 개념을 클래스로 만들어 불변식을 담기 → **44.1** (도메인 프리미티브와 불변식), **43.2** (계약으로 빠르게 실패하기)
> - 비밀을 담는 값의 취급 규칙을 타입에 붙이기 → **44.5** (읽기 1회 객체), **22.9** (비밀을 코드에서 다루는 법)
> - 모호한 기본형 파라미터 목록의 정리 → **47.2** (모호한 파라미터 목록), **44.8** (생성 시 일관성)
> - 상태를 타입으로 표현해 순서를 강제하기 → **44.10** (엔티티 상태 객체)

## 29.7 로직 결함을 피하는 설계 습관

로직 결함을 식별하는 고유한 시그니처가 없듯, 그것을 막아 줄 은탄환도 없다. "위험한 API 대신 안전한 API를 쓰라"처럼 간명한 조언에 해당하는 것이 존재하지 않는다. 그럼에도 결함 발생 위험을 유의미하게 줄이는 실천들은 있다. 이 절은 그것을 세 층으로 정리한다. 문서와 리뷰의 층, 코드 습관의 층, 그리고 모델의 층이다.

### 첫째 층 — 가정을 적어 두고 의심하기

로직 결함이 하나의 잘못된 가정으로 환원된다면, 방어의 출발점은 **가정을 문서에 드러내는 것**이다.

**설계의 모든 측면을, 외부인이 설계자가 세운 모든 가정을 이해할 수 있을 만큼 상세히 문서화한다.** 그런 가정은 전부 설계 문서에 명시적으로 기록되어야 한다. 29.1절에서 보았듯 가정은 명시적으로 진술되는 순간 종종 자명하게 틀려 보인다. 사례 2의 "일반 사용자는 항상 기존 비밀번호를 보낼 것"이 그랬다. 문제는 그것이 누구의 머릿속에도 문장으로 존재한 적이 없었다는 데 있다.

**모든 소스 코드에 다음을 담는 주석을 의무화한다.**

- 각 코드 컴포넌트의 목적과 의도된 용도
- 각 컴포넌트가 **자기 통제 밖의 것에 대해 세우는 가정**
- 그 컴포넌트를 사용하는 모든 클라이언트 코드에 대한 참조

세 번째 항목이 사례 5(은행 털기)를 막았을 것이다. `CCustomer`가 어디에서 쓰이는지가 적혀 있었다면, 등록 기능에 재사용하려던 개발자가 그것이 인증된 세션의 신원 저장소이기도 하다는 사실을 보았을 것이다. 여기서 "클라이언트"는 클라이언트/서버의 클라이언트가 아니라, 그 컴포넌트를 직접 의존하는 다른 코드를 뜻한다.

**보안 중심의 설계 리뷰에서 설계 안의 모든 가정을 되짚고, 각 가정이 위반될 수 있는 상황을 상상한다.** 특히 **애플리케이션 사용자의 통제 아래 있을 수 있는 가정**에 집중한다.

**보안 중심의 코드 리뷰에서 두 영역을 측면적으로 사고한다.** 애플리케이션이 예상치 못한 사용자 행위를 어떻게 처리하는가, 그리고 서로 다른 코드 컴포넌트와 서로 다른 기능 사이의 의존과 상호 동작이 어떤 부수 효과를 낳는가.

사례 12(로그인 경쟁)에서 확인했듯, 이 층은 침투 테스트가 잡지 못하는 것을 잡는다. 그 경쟁 조건은 원격 블랙박스 테스트로는 사실상 발견 불가능했지만 **인증·세션 관리 로직의 면밀한 코드 리뷰였다면 발견되었을 것**이다(→ 47.12).

### 둘째 층 — 개별 사례가 남긴 코드 습관

앞의 사례들에서 곧바로 끌어낼 수 있는 구체적 지침들이다.

**사용자가 요청의 모든 측면을 통제한다는 사실을 항상 의식한다**(→ 6.7). 사용자는 다단계 기능에 임의 순서로 접근할 수 있다. 요구하지 않은 파라미터를 제출할 수 있다. 값을 조작하는 것을 넘어 **파라미터를 생략**할 수 있다.

**사용자의 신원과 지위에 관한 모든 결정은 세션에서 끌어온다**(→ 24.6). 요청의 다른 어떤 특징으로도 권한을 추정하지 않는다. 그 요청이 도착했다는 사실 자체도 포함해서다.

**사용자 입력이나 행위에 따라 세션 데이터를 갱신하는 기능을 구현할 때, 그 갱신이 애플리케이션의 다른 기능에 미칠 영향을 신중히 검토한다.** 예상치 못한 부수 효과가 다른 프로그래머, 심지어 다른 개발 팀이 작성한 전혀 무관한 기능에서 나타날 수 있다.

**검색 기능이 일부 사용자가 접근 권한이 없는 민감 데이터를 색인한다면, 그 사용자들이 검색 결과로부터 정보를 추론할 수 있는 어떤 수단도 제공하지 않는다.** 필요하면 권한 수준별 인덱스를 여럿 두거나, 요청자의 권한으로 저장소를 동적으로 검색한다.

**감사 추적에서 항목을 삭제할 수 있게 하는 기능은 극도로 경계한다.** 감사가 중요한 애플리케이션과 이중 승인 모델에서, 높은 권한의 사용자가 같은 권한의 다른 사용자를 생성할 수 있게 하는 것의 영향도 고려한다.

**수치 한도와 임계값에 근거한 검사를 할 때는 처리 전에 모든 사용자 입력에 엄격한 정규화와 데이터 검증을 수행한다.** 음수가 기대되지 않으면 음수를 담은 요청을 **명시적으로 거부한다.**

**주문 물량에 따른 할인을 구현할 때는 할인을 실제로 적용하기 전에 주문을 확정한다.**

**취약할 수 있는 컴포넌트에 사용자 데이터를 넘기기 전에 이스케이프할 때는 반드시 이스케이프 문자 자체도 이스케이프한다.** 그러지 않으면 검증 메커니즘 전체가 무너질 수 있다.

**개별 사용자와 관련된 데이터는 언제나 적절한 저장소 — 세션 또는 사용자 프로필 — 에 유지한다.** 정적 컨테이너에 두지 않는다.

### 셋째 층 — 모델의 습관

29.6절의 진단이 옳다면, 위의 지침들은 대체로 **사후적**이다. 각각은 이미 벌어진 실수의 재발을 막지만, 실수의 발생 조건 자체를 없애지는 않는다. 발생 조건을 없애는 쪽의 실천은 이렇다.

**모델링할 때 상한과 하한을 논의한다.** "이 값은 얼마나 클 수 있나요?"와 "0이면 어떻게 되나요?"는 언제나 흥미로운 정보를 낳는다. 살이 "총수량 240"이라는 물류 제약을 말한 것은 데브가 물었기 때문이다. 아무도 묻지 않았다면 그 지식은 창고에만 남았을 것이고 코드는 20억까지 받았을 것이다.

**암묵적 개념을 명시적으로 만든다.** 이야기 속에서 "수량", "결제", "주문 상태", "역할" 같은 암묵적 개념을 발견하면 몇 분을 들여 조금 더 깊이 논의한다. 충분히 흥미롭다면 설계의 일부로 명시하고, 코드에서 자기 클래스로 만들어 자기 제약을 스스로 지키게 한다.

**같은 이름의 두 개념을 억지로 하나로 유지하지 않는다.** 29.5절의 보험사가 겪은 일이 이것이다. 기술적 의존을 깨뜨리지 않으려는 선의가 의미의 분기를 은폐했다. 이름이 갈라질 때가 되었다면 갈라야 하고, 그것이 하류 팀과의 논의를 강제한다면 그 논의야말로 필요한 것이다.

**서비스 경계를 넘는 개념은 양쪽 도메인 전문가가 함께 매핑한다.** 문자열이 같다고 개념이 같은 것이 아니다. 한 도메인의 `Payment`와 다른 도메인의 `Payment`는 다른 것이며, 그 차이는 두 도메인을 모두 아는 사람이 한자리에 있을 때에만 드러난다. **의도적 발견**은 회의를 잡는 일이며, 그 회의의 비용은 늦은 발견의 비용보다 언제나 싸다.

**시스템 간 일관성이 아니라 물리적 현실과 대조한다.** 29.4절이 보여 준 대로, 서로 대조하는 IT 시스템이 여럿이라는 사실은 안심의 근거가 아니다. 그들은 같은 거짓말을 공유할 수 있다. 진짜 검증은 재고 실사처럼 시스템 바깥의 현실과 만나는 지점에서 이뤄지며, 그 지점은 1년에 한 번이 아니라 자주 열려야 한다.

**업무 규칙을 테스트한다.** 정상 입력만이 아니라 경계 입력, 비정상 입력, 극단 입력을 테스트한다(→ 46.9). "수량 −1인 주문을 넣으면 거부되는가"는 보안 테스트가 아니라 **도메인 테스트**이고, 그래서 개발 팀이 자기 손으로 쓸 수 있는 종류의 테스트다. 침투 테스터가 오기를 기다릴 필요가 없다(→ 45.7).

> **이 책의 범위를 넘어서**
>
> 이 장이 다룬 다섯 권의 원서는 로직 결함을 사례와 모델링의 언어로 다룬다. 이후 업계에서는 이 부류를 "비즈니스 로직 취약점"이라는 이름 아래 유형별로 분류하려는 시도가 이어졌고, 상태 전이를 명시적 사건의 열로 기록해 사후에 재구성 가능하게 만드는 아키텍처 패턴들도 이 문제의 부분적 해법으로 논의된다. 이 책은 그 분류 체계나 특정 아키텍처 패턴을 다루지 않는다. 이유는 두 가지다. 첫째, 로직 결함의 정의상 완결된 분류는 존재할 수 없으며, 분류표는 이미 알려진 것을 다시 찾는 데만 유용하다. 둘째, 아키텍처 선택은 이 책의 논지 — 신뢰 경계를 어디에 두고 그것을 코드로 어떻게 표현하는가 — 와 층위가 다르다. 이 장이 제시하는 처방은 아키텍처 이전의 것, 즉 **업무의 개념에 코드가 이름을 주는가**에 관한 것이다.

## 이 장의 요약

- **로직 결함에는 공통 시그니처가 없다.** SQL 인젝션이나 XSS와 달리 판정 기준이 인터프리터의 문법이 아니라 업무 도메인의 규칙에 있고, 그 규칙은 HTTP 어디에도 적혀 있지 않다. 그래서 취약점 스캐너도 정적 분석기도 이 부류를 겨냥하지 못하며, 안전한 개발 표준과 정규 침투 테스트로도 근절되지 않는다.
- **대부분의 로직 결함은 하나의 잘못된 가정으로 환원된다.** "A면 B이므로 C를 하자"라는 추론에서 "그런데 X가 일어나면?"이 빠진 것이다. 결함을 찾는 일은 페이로드를 던지는 일이 아니라 개발자가 무엇을 당연하게 여겼는지를 재구성하는 일이다.
- **기본 탐침은 셋이다.** 파라미터를 이름째 제거하기, 다단계 기능의 순서를 어기는 강제 브라우징, 파라미터를 다른 단계·다른 역할로 옮기기. 29.2절 열두 사례 중 절반 이상이 이 셋 중 하나로 드러난다.
- **열두 사례는 세 군집으로 묶인다.** 요청의 형태와 순서에 관한 가정이 깨진 것(2·3·4·7), 저장 위치와 개념의 소유자에 관한 가정이 깨진 것(1·5·11·12), 값의 범위와 처리 규칙에 관한 가정이 깨진 것(6·8·9·10)이다.
- **기술적으로 아무것도 깨지지 않은 채 회사가 돈을 잃을 수 있다.** 온라인 서점의 안티북 결함에서 체크섬도, 서명도, 트랜잭션 무결성도, 데이터베이스 제약도 위반되지 않았다. 위반된 것은 **비즈니스 무결성**, 즉 데이터가 의미해야 할 세계였다.
- **여러 시스템이 같은 거짓말을 공유하면 어떤 대조도 결함을 잡지 못한다.** 재고 시스템은 책이 하나 더 있다고 믿고 미수금 원장은 그만큼 빚졌다고 믿는다. 재무적으로 상쇄되므로 일일·분기 보고서에 불일치가 없다. 진짜 검증은 시스템끼리가 아니라 **물리적 현실과의 대조**에서만 나온다.
- **서비스를 분리하면 같은 단어가 다른 의미로 갈라진다.** 보험사에서 지로의 `Payment`(등록됨)와 재무의 `Payment`(수령함)와 보험의 `Payment`(증서 발행 근거)는 이름만 같았다. 어느 시스템도 자기 도메인 기준으로 잘못하지 않았고, 세 도메인을 동시에 볼 때에만 결함이 보였다. 그리고 법원은 시스템이 한 일을 회사의 의도로 판단했다.
- **로직 결함의 상당수는 업무의 어떤 개념이 코드에 이름을 갖지 못해서 생긴다.** 수량이 `int`이고, 주문 상태가 화면 순서에만 있고, 요청자의 역할이 파라미터의 유무로 표현되고, 두 개의 다른 개념이 같은 타입을 공유했다. 이름 없는 개념은 규칙을 가질 수 없고, 규칙 없는 개념은 위반이 위반으로 인식되지 않는다.
- **처방은 세 층이지만 층마다 신뢰도가 다르다.** 가정의 문서화와 코드 리뷰는 사람의 주의력에 의존하고 마감 앞에서 얇아진다. 반면 `Quantity` 같은 명시적 개념은 피곤한 개발자에게도 똑같이 작동한다. 우회하려면 의도적으로 우회하는 코드를 써야 하기 때문이다.

## 이어지는 장

이 장은 두 개의 시선을 하나의 진단으로 합쳤다. 공격자는 "무엇을 가정했는가"를 묻고, 설계자는 "왜 그런 코드를 썼는가"를 묻는다. 두 질문의 답은 같은 곳 — 도메인 모델의 깊이 — 에서 만난다.

30장은 **오류, 정보 노출, 그리고 안전한 실패**로 넘어간다. 이 장의 사례 11(디버그 메시지 수집하기)이 그 장의 문을 미리 열어 두었다. 그 사례에서 우리가 확인한 것은 상세한 오류 메시지가 위험하다는 통상적 교훈이 아니라, **정보가 어디에 저장되었는가**가 실제 병이었다는 사실이다. 30장은 오류 메시지가 무엇을 흘리는지, 응답 시간과 상태 코드가 어떻게 채널이 되는지, 그리고 실패를 예외적인 사건이 아니라 정상적인 경로로 설계한다는 것이 무엇인지를 다룬다. 29.3절에서 배송 시스템이 예외를 삼키고 아무도 읽지 않는 로그에 던진 장면은 그 장에서 다시 검토된다.

그리고 이 장이 남긴 더 큰 약속은 Part IX가 받는다. 42.8~42.9절이 얕은 모델과 깊은 모델의 일반 이론을 세우고, 43장이 불변식과 계약과 검증 순서를 코드 구조로 만들며, 44장이 도메인 프리미티브와 상태 무결성으로 그것을 완성한다. 47.7~47.9절은 보험사 이야기를 마이크로서비스의 언어로 다시 다룬다. 이 장에서 우리는 안티햄릿을 표현 불가능하게 만드는 `Quantity` 클래스를 스케치했다. 그 클래스가 왜 하나의 예외적 기법이 아니라 **설계의 일반 원리**인지가 Part IX의 주제다.
