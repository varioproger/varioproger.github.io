# 26장. 클라이언트 사이드 통제 우회

> **이 장에서 다루는 것**
>
> - 클라이언트에 둔 통제는 왜 통제가 아닌가 — 6.7절의 명제가 낳는 첫 번째 구체적 결과
> - 서버가 클라이언트를 경유해 데이터를 되돌려받을 때(히든 필드·쿠키·URL 파라미터·Referer·불투명 값) 무엇을 잘못 가정하는가
> - 클라이언트가 사용자 입력을 붙잡아 검증할 때(HTML 폼·브라우저 확장·네이티브 컴포넌트) 그 검증이 왜 서버를 지켜주지 못하는가
> - 클라이언트를 경유하는 데이터를 그래도 다뤄야 할 때의 실무 처방 — 전달하지 않기, 서명·암호화, 서버 재검증, 로깅·경보
> - 이 모든 처방이 하나의 설계 원칙으로 수렴한다는 것 — **검증은 데이터의 출처를 확인하는 데서 시작한다** (→ 43.4)

25장은 대상 시스템의 지도를 그렸다. 눈에 보이는 콘텐츠, 숨은 콘텐츠, 사용자 입력이 들어가는 모든 진입점의 목록. 그 지도의 각 진입점은 하나의 질문을 남긴다. **이 값이 서버에 도착했을 때 서버는 그것을 얼마나 믿는가.** 이 장은 그 질문에 답한다.

6.7절에서 이 책은 웹 애플리케이션 보안의 근본 문제를 한 문장으로 세웠다. **사용자는 임의의 입력을 보낼 수 있다.** 클라이언트와 그 위에서 벌어지는 모든 처리는 사용자의 통제 아래 있고, 서버는 도착한 바이트만 볼 뿐 그 바이트가 어떤 경로로 어떤 손을 거쳐 왔는지 알 수 없다. 이 장은 그 명제의 첫 번째 구체적 귀결이다. 명제 자체는 추상적이지만, 이 장에서 그것은 아주 구체적인 형태를 띤다. 히든 필드에 담긴 가격, 쿠키에 담긴 할인율, JavaScript가 검사하는 수량, 자바 애플릿이 난독화한 주문 값 — 이들 하나하나가 "클라이언트에 둔 통제는 통제가 아니다"라는 명제의 증명이다.

애플리케이션이 클라이언트 사이드 통제에 의존하는 방식은 크게 두 갈래다. **첫째, 서버가 어떤 데이터를 클라이언트를 통해 전달하고, 나중에 그것을 되돌려받으면서 그 값이 그대로일 것이라고 가정한다.** 상품 가격을 히든 필드에 넣어 보내고 폼이 제출될 때 그 값을 그대로 신뢰하는 경우가 여기 속한다. **둘째, 서버가 클라이언트 쪽에 통제 장치를 심어 사용자의 입력을 서버에 도달하기 전에 제한하거나 검증한다.** HTML 폼의 길이 제한, JavaScript 검증, 브라우저 확장이나 네이티브 컴포넌트의 검사 로직이 여기 속한다. 두 갈래 모두 같은 오류를 공유한다. **통제가 사용자의 손이 닿는 곳에 있다.** 이 장은 각 갈래의 구체적 사례와, 그것들이 어떻게 우회되는지를 다루고, 마지막 두 절에서 그럼에도 클라이언트를 안전하게 다루는 법을 실무(26.7)와 설계(26.8) 두 관점으로 닫는다.

이 장의 실행 예제는 온라인 서점이다. 상품 가격을 히든 필드로 보내는 장바구니, 클라이언트에서만 수량을 검증하는 주문 폼, 할인율을 쿠키에 담아 되돌려받는 결제 흐름 — 도메인 설계를 설명할 때 이 책이 쓰는 온라인 서점(→ 0.3)이 여기서도 무대가 된다.

## 26.1 클라이언트를 통해 데이터를 전달할 때

서버가 어떤 값을 알고 있고 지정도 한다면, 그 값을 굳이 클라이언트로 보냈다가 다시 읽어 오는 이유는 무엇인가. 합리적으로 던질 수 있는 질문이다. 그런데 실무에서 이렇게 짜는 데에는 개발자에게 편한 이유들이 있다.

- **세션에 상태를 쌓지 않아도 된다.** 서버 측 세션에 보관하는 데이터를 줄이면 구현이 단순해지고, 세션 저장소의 부하도 줄어 성능에도 이롭다.
- **여러 서버에 분산 배치된 경우 상태 공유가 어렵다.** 사용자가 여러 서버에 걸쳐 다단계 작업을 수행할 때, 서버 간에 세션 데이터를 공유하는 것보다 클라이언트에 실어 나르는 편이 손쉬운 해법으로 보인다.
- **서드파티 컴포넌트를 우회하기 쉽다.** 장바구니 같은 외부 컴포넌트를 서버에서 고치기 어렵거나 불가능할 때, 클라이언트를 경유해 값을 넘기는 것이 통합의 지름길이 된다.
- **정식 변경 절차를 피할 수 있다.** 서버 측 핵심 API에 새 데이터를 하나 추가하는 일이 전면적인 변경 관리 절차와 회귀 테스트를 촉발한다면, 클라이언트 전달이라는 부분적 편법으로 마감을 맞추려는 유혹이 생긴다.

이유가 무엇이든 결과는 같다. **클라이언트에서 서버로 오는 모든 것은 사용자의 통제 안에 있으므로, "클라이언트를 경유한 데이터는 변조되지 않는다"는 가정은 대개 거짓이며, 애플리케이션을 하나 이상의 공격에 노출시킨다.** 아래에서 전달 수단별로 무엇이 위험한지를 본다. 수단은 다르지만 결론은 하나로 모인다 — 어느 수단도 변조를 막지 못한다.

### 26.1.1 히든 폼 필드

히든 필드는 클라이언트를 통해 데이터를 "겉보기에 수정 불가능한" 형태로 전달하는 가장 흔한 수단이다. `type="hidden"`으로 표시된 필드는 화면에 그려지지 않지만, 이름과 값은 폼 안에 그대로 저장되어 제출 시 서버로 되돌아간다.

이 결함의 고전적 사례가 상품 가격을 히든 필드에 담는 소매 애플리케이션이다. 웹 초창기에 극도로 널리 퍼졌던 취약점이고, 오늘날에도 결코 근절되지 않았다. 온라인 서점의 상품 상세 페이지에서 "장바구니 담기"를 누를 때 아래와 같은 폼이 제출된다고 하자.

```html
<form method="post" action="/cart/add">
  상품: 『설계로 푸는 보안』 <br/>
  가격: 28,000 <br/>
  수량: <input type="text" name="quantity"> (최대 50권)<br/>
  <input type="hidden" name="price" value="28000">
  <input type="submit" value="담기">
</form>
```

`price` 필드는 히든으로 표시되어 화면에 보이지 않고 사용자가 편집할 수도 없다. 그러나 이는 오직 애플리케이션이 브라우저에게 그 필드를 숨기라고 지시했기 때문일 뿐이다. 폼이 제출되면 서버로 가는 요청은 다음과 같다.

```http
POST /cart/add HTTP/1.1
Host: www.example-books.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 21

quantity=1&price=28000
```

클라이언트에서 일어나는 모든 일은 궁극적으로 사용자의 통제 안에 있으므로, 이 제약은 얼마든지 우회되어 가격이 편집된다. 한 가지 방법은 HTML 소스를 저장해 필드 값을 고친 뒤 브라우저로 다시 여는 것이지만, 더 간편하고 우아한 방법은 **인터셉팅 프록시**로 제출 요청을 가로채 값을 즉석에서 바꾸는 것이다(→ 25.8). 프록시는 브라우저와 애플리케이션 사이에 앉아 HTTP·HTTPS 요청과 응답을 모두 가로챈다. `price=28000`을 `price=100`으로, 혹은 음수로 바꾼 뒤 흘려보내면, 서버가 제출된 가격을 근거로 거래를 처리하는 한 사용자는 자기가 정한 가격에 상품을 산다.

> **팁.** 이런 식으로 취약한 애플리케이션을 만나면 **음수 가격**을 넣어 보라. 실제로 음수 가격 거래를 받아들인 사례가 있다. 공격자는 주문한 물건을 받는 동시에 신용카드로 환불까지 받는다.

### 26.1.2 쿠키

쿠키도 히든 필드와 마찬가지로 보통 화면에 표시되지 않고 사용자가 직접 수정하지 못하는 데이터 전달 수단이다. 그러나 프록시로 값을 세팅하는 서버 응답을, 혹은 그 값을 실어 보내는 이후 요청을 가로채면 얼마든지 조작된다. 온라인 서점에서 로그인한 고객이 다음 응답을 받았다고 하자.

```http
HTTP/1.1 200 OK
Set-Cookie: DiscountAgreed=15
Content-Length: 1530
```

이 `DiscountAgreed` 쿠키는 클라이언트 사이드 통제(쿠키는 보통 수정할 수 없다는 사실)에 기대어 클라이언트 경유 데이터를 지키려는 전형적 사례다. 애플리케이션이 이 쿠키 값을 신뢰한다면, 고객은 값을 고쳐 임의의 할인을 받는다.

```http
POST /cart/add HTTP/1.1
Host: www.example-books.com
Cookie: DiscountAgreed=90
Content-Length: 10

quantity=1
```

`DiscountAgreed=15`를 `90`으로 바꾸면 90퍼센트 할인이 적용된다. 쿠키를 조작하는 구체적 기법 — 응답의 `Set-Cookie`를 바꾸는 것과 요청의 `Cookie` 헤더를 바꾸는 것, 그리고 서브도메인·경로 범위를 악용한 주입 — 은 20.9절에서 다뤘다. 여기서 강조할 점은 쿠키가 헤더에 실린다는 이유로 특별한 보호를 받지 않는다는 것이다.

### 26.1.3 URL 파라미터

애플리케이션은 미리 설정된 URL 파라미터로 데이터를 클라이언트에 전달하기도 한다. 사용자가 카탈로그를 훑을 때 다음과 같은 하이퍼링크가 제공될 수 있다.

```
http://www.example-books.com/shop/?prod=372&pricecode=32
```

URL이 브라우저 주소창에 그대로 보일 때는 어떤 파라미터든 도구 없이 손쉽게 고쳐진다. 그럼에도 애플리케이션은 종종 일반 사용자가 URL 파라미터를 보거나 고칠 수 없다고 기대한다.

- 파라미터가 담긴 URL로 이미지를 로드할 때
- 파라미터가 담긴 URL로 프레임 콘텐츠를 로드할 때
- 폼이 POST 메서드를 쓰면서 대상 URL에 미리 설정된 파라미터를 담을 때
- 팝업 창 등으로 브라우저 주소창을 감출 때

이런 경우라도 URL 파라미터 값은 앞서와 같이 인터셉팅 프록시로 얼마든지 수정된다. 주소창에 보이지 않는다는 것이 값을 바꿀 수 없다는 뜻은 아니다.

### 26.1.4 Referer 헤더

브라우저는 대부분의 요청에 `Referer` 헤더를 포함한다. 이 헤더는 현재 요청이 비롯된 페이지의 URL을 가리킨다 — 사용자가 링크를 클릭했든, 폼을 제출했든, 페이지가 이미지 같은 다른 리소스를 참조했든. 애플리케이션이 처리하는 URL은 자기 통제 아래 있으므로, 개발자는 `Referer`로 특정 요청이 어느 URL에서 생성됐는지 신뢰성 있게 판단할 수 있다고 가정하곤 한다.

비밀번호 재설정 기능을 예로 들자. 사용자가 실제 비밀번호를 바꾸는 마지막 요청에 도달하기 전에 정해진 순서대로 여러 단계를 거치도록 강제한다.

```http
GET /auth/472/CreateUser.ashx HTTP/1.1
Host: www.example-books.com
Referer: https://www.example-books.com/auth/472/Admin.ashx
```

애플리케이션은 `Referer`를 보고 이 요청이 올바른 단계(`Admin.ashx`)에서 왔는지 확인한다. 그러나 사용자는 헤더를 포함한 요청의 모든 측면을 통제하므로, `CreateUser.ashx`로 곧장 진입한 뒤 프록시로 `Referer` 값을 애플리케이션이 원하는 값으로 바꾸면 이 통제는 간단히 무너진다.

`Referer` 헤더는 w3.org 표준상 엄격히 선택 사항이다. 대부분의 브라우저가 구현하지만, 이것으로 애플리케이션 기능을 통제하는 것은 **편법으로 봐야 한다.** 헤더의 신뢰성 문제 전반 — `Referer`, `Host`, `X-Forwarded-For`, `User-Agent`를 믿을 수 있는가 — 은 8.6절에서 다뤘다. 8.6절의 결론을 여기서 한 문장으로 재확인한다. **어떤 요청 헤더도 위조 불가능하지 않다.**

> **흔한 오해 — 헤더는 URL보다 "변조에 강하다"?**
>
> HTTP 헤더가 URL 같은 요청의 다른 부분보다 어쩐지 "변조하기 어렵다"고 자주 가정한다. 그래서 개발자는 URL 파라미터는 제대로 검증하면서 `Cookie`나 `Referer` 같은 헤더에 실린 값은 믿는 기능을 짜기도 한다. 이 인식은 틀렸다. 무료로 구할 수 있는 수많은 인터셉팅 프록시 앞에서, 어떤 아마추어 해커도 요청 데이터 전부를 손쉽게 바꾼다. 헤더에 숨기는 것은, 선생님이 책상을 뒤질 때 물총을 맨 아래 서랍에 숨기면 더 안전하리라 여기는 것과 같다. 선생님이 허리를 조금 더 굽혀야 할 뿐이다.

### 26.1.5 불투명 데이터

클라이언트를 경유하는 데이터가 암호화되거나 난독화되어 투명하게 읽히지 않는 경우도 있다. 상품 가격이 히든 필드에 평문으로 담기는 대신, 암호 같은 값이 오갈 수 있다.

```html
<form method="post" action="/cart/add">
  상품: 『도메인 주도 설계』 <br/>
  가격: 45,000 <br/>
  수량: <input type="text" name="quantity"> (최대 50권)<br/>
  <input type="hidden" name="price" value="45000">
  <input type="hidden" name="pricing_token"
         value="E76D213D291B8F216D694A34383150265C989229">
  <input type="submit" value="담기">
</form>
```

이런 값을 보면, 폼이 제출될 때 서버가 이 불투명 문자열의 무결성을 검사하거나, 복호화·역난독화해서 평문 값으로 처리하리라고 추론할 수 있다. 그 후속 처리는 온갖 버그에 취약할 수 있다. 다만 이를 탐지하고 익스플로잇하려면 먼저 페이로드를 적절히 포장해야 한다. 불투명 데이터를 만났을 때 취할 수 있는 공격 경로는 다음과 같다.

1. **평문을 안다면** 난독화 알고리즘을 역추적해 볼 수 있다.
2. **다른 기능을 지렛대로 삼는다.** 애플리케이션 어딘가에, 내가 통제하는 평문을 넣으면 그에 대응하는 불투명 문자열을 돌려주는 기능이 있을 수 있다(→ 25.5). 그렇다면 원하는 페이로드에 해당하는 불투명 값을 직접 얻어낸다.
3. **재생(replay)한다.** 불투명 문자열이 아무리 뚫기 어려워도, 그 값을 다른 문맥에서 되쓰면 악의적 효과를 낼 수 있다. 위 폼의 `pricing_token`이 상품 가격의 암호화 버전이라면, 임의 가격의 암호문을 만들어낼 수는 없어도 **더 싼 상품의 암호화된 가격을 복사해 이 상품 자리에 제출**할 수는 있다.
4. **다 실패하면** 과도하게 긴 값, 다른 문자셋 등 변형된 불투명 값을 던져 서버의 복호화·역난독화 로직 자체를 공격한다.

여기서 놓치지 말아야 할 구조적 사실이 있다. **불투명 데이터를 클라이언트에 맡기는 것은, 암호화된 세션 토큰을 클라이언트에 맡기는 것과 같은 문제다.** 23.2절에서 다룬 "암호화된 토큰의 오용"이 바로 이 구조다. 값을 읽지 못한다는 것과 값을 오용하지 못한다는 것은 전혀 다른 이야기이며, 특히 3번 재생 공격은 암호를 한 글자도 깨지 않고 성립한다. 클라이언트를 경유하는 불투명 데이터 항목은 세션 처리 메커니즘의 일부인 경우가 많다 — 쿠키의 세션 토큰, 히든 필드의 안티-CSRF 토큰, 리소스 접근용 일회성 URL 토큰이 모두 클라이언트 측 변조의 표적이다. 이 토큰들에 특화된 고려사항은 23장에서 깊이 다뤘다.

> **이 절이 뒷받침하는 것**
>
> - 전달 수단별 위험(히든 필드·쿠키·URL·Referer·불투명 값) → 이 목록이 **A.4** (클라이언트 사이드 통제 테스트)의 점검 항목이 된다.
> - 불투명 데이터의 재생 가능성 → **23.2** (암호화된 토큰의 오용)과 동일한 실패 구조.
> - Referer 신뢰 → **8.6** (헤더의 신뢰성), 쿠키 조작 → **20.9** (쿠키 인젝션과 조작).

## 26.2 ASP.NET ViewState

클라이언트를 경유해 불투명 데이터를 전달하는, 실무에서 흔히 마주치는 메커니즘이 ASP.NET **ViewState**다. 모든 ASP.NET 웹 애플리케이션에 기본으로 생성되는 히든 필드로, 현재 페이지 상태의 직렬화된 정보를 담는다.

ViewState의 본래 목적은 서버 성능 향상이다. 서버는 관련 상태 정보를 전부 서버 측에 유지하지 않고도, 연속된 요청에 걸쳐 UI 요소를 보존할 수 있다. 예컨대 사용자가 제출한 파라미터로 드롭다운 목록을 채웠다고 하자. 이후 요청에서 브라우저는 목록 내용을 다시 보내지 않지만, 목록의 직렬화된 형태를 담은 히든 ViewState 필드는 보낸다. 서버는 이를 역직렬화해 같은 목록을 재구성한다.

이 핵심 목적 외에도, 개발자는 ViewState에 임의의 정보를 얹어 여러 요청에 걸쳐 저장할 수 있다. 가격을 히든 필드가 아니라 ViewState에 담는 식이다.

```csharp
string price = getPrice(prodno);
ViewState.Add("price", price);
```

이렇게 하면 사용자에게 돌아가는 폼은 다음과 같아진다.

```html
<form method="post" action="/shop/Shop.aspx?prod=3">
  <input type="hidden" name="__VIEWSTATE" id="__VIEWSTATE"
         value="/wEPDwULLTElODcxNjkwNjIPFgIeBXByaWNlBQMzOTlkZA==" />
  상품: 『리팩터링』 <br/>
  가격: 39,000 <br/>
  수량: <input type="text" name="quantity"> (최대 50권)<br/>
  <input type="submit" value="담기">
</form>
```

폼을 제출하면 요청에는 겉보기에 가격이 들어 있지 않다 — 수량과 불투명한 ViewState 파라미터만 있다. 이 파라미터를 아무렇게나 바꾸면 오류 메시지가 나고 구매는 처리되지 않는다. 그러나 ViewState 파라미터는 사실 Base64 인코딩 문자열이라, 간단히 디코딩하면 그 안에 심어진 `price` 파라미터가 드러난다.

```
... 05 0B 2D 31 35 38 37 31 36 39 30 36 32 ...  -15871690
... 70 72 69 63 65 05 03 33 39 39 ...            price..399
```

기본적으로 ASP.NET 플랫폼은 ViewState에 키 기반 해시(MAC 보호)를 붙여 변조를 막는다. 그러나 일부 애플리케이션은 이 기본 보호를 꺼 둔다. 그런 경우 ViewState 값을 고쳐 서버 측 처리에 영향을 주는지 확인할 수 있다. ViewState를 공격할 때의 절차는 이렇다.

1. **MAC 보호 여부를 확인한다.** ViewState 구조 끝에 20바이트 해시가 있는지로 판별한다. Burp의 ViewState 파서로 확인할 수 있다.
2. **보호돼 있어도** 여러 페이지의 ViewState를 디코딩해 애플리케이션이 이를 통해 민감한 데이터를 클라이언트로 전달하는지 살핀다.
3. 구조를 깨지 않고 **특정 파라미터 값만 수정**해 오류가 나는지 본다.
4. 오류 없이 수정된다면 각 파라미터의 역할을 검토하고, 임의의 데이터를 심어 여느 클라이언트 경유 데이터처럼 공격한다.
5. **MAC 보호는 페이지 단위로 켜고 끌 수 있으므로** 주요 페이지마다 개별 테스트가 필요하다.

ViewState는 26.1.5절 불투명 데이터의 한 특수형이다. 그리고 같은 함정을 공유한다. **MAC 보호가 없으면 불투명함은 보호가 아니다 — Base64는 암호가 아니라 인코딩이기 때문이다.** MAC 보호가 있어도, 값이 변조되지 않는다는 것이지 그 안에 민감 데이터를 실어도 된다는 뜻은 아니다. 디코딩만으로 내용이 노출된다. 23.2절의 논지가 여기서 그대로 재현된다 — 클라이언트에 맡긴 상태는, 그것이 아무리 복잡하게 포장돼 있어도 클라이언트에 맡긴 상태다.

## 26.3 사용자 입력 캡처 (1) HTML 폼

지금까지는 서버가 클라이언트를 경유해 자기 데이터를 되돌려받는 경우였다. 애플리케이션이 클라이언트 사이드 통제를 쓰는 두 번째 방식은 다르다. **원래 서버가 지정한 값이 아니라, 클라이언트 컴퓨터에서 수집된 사용자 입력**을 제출 전에 제한하거나 검증하는 것이다.

HTML 폼은 사용자 입력을 캡처해 서버로 보내는 가장 단순하고 흔한 수단이다. 기본적으로 사용자는 이름 붙은 텍스트 필드에 데이터를 입력하고, 이는 이름/값 쌍으로 제출된다. 그러나 폼은 입력에 제한을 걸거나 검증을 수행하는 데도 쓰인다. 이런 클라이언트 측 통제를 악의적 입력에 대한 방어 수단으로 쓸 때, 그 통제는 대개 손쉽게 우회되어 애플리케이션을 취약하게 남긴다.

### 26.3.1 길이 제한

원래 폼에 수량 필드의 최대 길이를 1로 거는 변형을 보자.

```html
<form method="post" action="/cart/add">
  상품: 『설계로 푸는 보안』 <br/>
  가격: 28,000 <br/>
  수량: <input type="text" name="quantity" maxlength="1"><br/>
  <input type="hidden" name="price" value="28000">
  <input type="submit" value="담기">
</form>
```

브라우저는 사용자가 이 입력 필드에 한 글자를 넘겨 입력하지 못하게 막는다. 그래서 서버 측 애플리케이션은 받게 될 `quantity` 값이 10 미만이라고 가정할 수 있다. 그러나 이 제약은 두 가지로 간단히 우회된다 — 폼 제출 요청을 가로채 임의 값을 넣거나, 폼이 담긴 응답을 가로채 `maxlength` 속성을 제거하거나.

길이 제한 우회의 절차는 이렇다. `maxlength` 속성을 가진 폼 요소를 찾고, 그보다 긴 데이터를(형식은 올바르게, 예컨대 숫자를 기대하면 숫자로) 제출한다. 애플리케이션이 이 과도한 데이터를 받아들이면 클라이언트 측 검증이 서버에 복제돼 있지 않다고 추론한다. 이 검증 결함은 후속 처리에 따라 SQL 인젝션, 크로스 사이트 스크립팅, 버퍼 오버플로 같은 다른 취약점의 지렛대가 된다.

> **응답 가로채기와 304.** 서버 응답을 가로채려 할 때 프록시에 `304 Not Modified`가 보일 수 있다. 브라우저가 캐시된 사본을 갖고 있어 `If-Modified-Since`·`If-None-Match` 헤더를 붙여 요청했기 때문이다. 이때 원본 리소스를 가로채 수정하려면 요청에서 이 두 헤더를 제거하면 된다. 그러면 서버가 전체 응답을 되돌려 준다. Burp Proxy에는 모든 요청에서 이 헤더를 벗겨 캐시 정보를 무시하게 하는 옵션이 있다. (조건부 요청과 검증자 ETag/Last-Modified의 원리는 → 10.8, 14.5.)

### 26.3.2 스크립트 기반 검증

HTML 폼 자체에 내장된 입력 검증은 극히 단순해서 여러 종류의 입력을 제대로 검증하기에는 세밀함이 부족하다. 등록 폼 하나에도 이름·이메일·전화번호·우편번호가 있고 저마다 다른 형식을 기대한다. 그래서 스크립트로 맞춤형 클라이언트 측 검증을 구현하는 경우가 흔하다.

```html
<form method="post" action="/cart/add" onsubmit="return validateForm(this)">
  상품: 『클린 코드』 <br/>
  가격: 33,000 <br/>
  수량: <input type="text" name="quantity"> (최대 50권)<br/>
  <input type="submit" value="담기">
</form>
<script>
function validateForm(theForm) {
  var isInteger = /^\d+$/;
  var q = theForm.quantity.value;
  var valid = isInteger.test(q) && q > 0 && q <= 50;
  if (!valid) alert('올바른 수량을 입력하세요');
  return valid;
}
</script>
```

폼 태그의 `onsubmit` 속성은 제출 버튼을 누를 때 `validateForm` 함수를 실행하게 하고, 이 함수가 `true`를 반환할 때만 폼을 제출한다. 위 예에서 검증은 수량이 정수이고 1과 50 사이인지를 본다. 이런 통제는 대개 우회하기 쉽다.

- 가장 단순하게는 **브라우저에서 JavaScript를 끈다.** 그러면 `onsubmit`이 무시되고 폼은 검증 없이 제출된다. 다만 애플리케이션이 UI 구성 등에 스크립트를 쓰면 이 방법이 애플리케이션을 망가뜨릴 수 있다.
- 더 깔끔하게는 **양성(known good) 값을 입력해 통과시킨 뒤, 프록시로 제출을 가로채 원하는 값으로 바꾼다.** JavaScript 검증을 무력화하는 가장 손쉽고 우아한 방법이다.
- 또는 **검증 루틴이 담긴 서버 응답을 가로채** 스크립트를 고친다 — 위 예라면 `validateForm`이 항상 `true`를 반환하게.

여러 필드에 클라이언트 검증이 걸려 있으면 각 필드를 개별적으로, 나머지 필드에는 유효한 값을 둔 채 하나씩 무효 데이터로 시험해야 한다. 여러 필드를 동시에 무효로 채우면 서버가 첫 무효 필드에서 처리를 멈춰, 모든 코드 경로에 도달하지 못할 수 있다.

> **주의.** 클라이언트 측 JavaScript 검증이 흔하다고 해서 모든 그런 애플리케이션이 취약하다고 결론짓지 말라. 애플리케이션이 노출되는 것은 **클라이언트 측 검증이 서버에 복제되지 않았을 때**, 그리고 그 검증을 우회한 조작 입력이 실제로 바람직하지 않은 동작을 일으킬 때뿐이다. 대다수의 경우 클라이언트 검증은 성능과 사용자 경험을 높이는 유익한 효과를 낸다. 등록 폼에서 형식이 틀린 전화번호를 즉시 짚어 주는 것은 서버 왕복 없이 매끄러운 경험을 준다. 클라이언트 검증은 좋다 — 그것을 **보안 통제로 삼는 것**이 문제다.

### 26.3.3 비활성(disabled) 요소

HTML 폼 요소가 `disabled`로 표시되면 화면에는 보이되 대개 회색으로 처리되어 편집·사용할 수 없고, 폼 제출 시 서버로 전송되지 않는다.

```html
<form method="post" action="/cart/add">
  상품: 『실용주의 프로그래머』 <br/>
  가격: <input type="text" disabled="true" name="price" value="29900"><br/>
  수량: <input type="text" name="quantity"> (최대 50권)<br/>
  <input type="submit" value="담기">
</form>
```

이 폼을 제출하면 `quantity`만 서버로 간다. 그러나 비활성 필드의 존재는, 원래 `price` 파라미터가 애플리케이션에서 쓰였을 수 있음을 — 아마 개발 중 테스트 목적으로 — 시사한다. 그 파라미터는 서버로 제출되어 처리됐을 것이고, 여전히 처리될지 모른다. 그렇다면 그 사실을 익스플로잇한다.

비활성 요소를 다룰 때 유의할 점이 있다. 브라우저는 비활성 폼 요소를 제출에 포함하지 않으므로, **애플리케이션 기능을 그냥 따라 걸으며 브라우저가 보내는 요청만 관찰해서는 이런 요소를 발견하지 못한다.** 서버의 응답을 관찰하거나 브라우저에서 페이지 소스를 봐야 한다. 또한 제출 버튼이 비활성으로 표시되어(해당 동작이 불가능한 문맥에서 회색으로 보이게) 있을 때, 그 이름을 제출해 서버가 동작 전에 서버 측 검사를 하는지 확인해야 한다. Burp Proxy의 HTML 수정 기능으로 비활성 필드를 자동으로 다시 활성화할 수 있다.

## 26.4 사용자 입력 캡처 (2) 브라우저 확장

HTML 폼 외에 사용자 데이터를 캡처·검증·제출하는 또 하나의 주요 방법은, 브라우저 확장에서 실행되는 클라이언트 측 컴포넌트를 쓰는 것이다. 자바 애플릿, Flash 같은 기술이다. 초기에는 단순하거나 장식적인 작업에 쓰였으나, 점차 완전한 기능을 갖춘 클라이언트 컴포넌트를 만드는 데 쓰이게 됐다. 이들은 브라우저 안에서, 여러 플랫폼에 걸쳐, 데스크톱 애플리케이션에 준하는 피드백과 유연성을 제공한다.

그 부작용으로, 예전에 서버에서 일어나던 처리가 속도와 사용자 경험을 위해 클라이언트로 옮겨진다. 온라인 트레이딩처럼 속도가 결정적인 경우에는 핵심 애플리케이션 로직 상당 부분이 클라이언트에서 벌어진다. 설계가 속도를 위해 의도적으로 보안을 희생하는 것이다 — 트레이더는 신뢰할 수 있는 사용자라거나, 브라우저 확장이 자체 방어를 갖췄다는 잘못된 믿음에서. **6.7절과 이 장 앞부분에서 확인한바, 클라이언트 측 컴포넌트가 자기 비즈니스 로직을 스스로 지킨다는 개념 자체가 성립하지 않는다.**

브라우저 확장은 입력 폼으로, 때로는 클라이언트 운영체제의 파일시스템·레지스트리와 상호작용해 데이터를 캡처한다. 서버로 보내기 전에 임의로 복잡한 검증·조작을 수행한다. 게다가 그 내부 동작이 HTML 폼이나 JavaScript보다 덜 투명하기 때문에, 개발자는 자신의 검증이 우회될 수 없다고 가정하기 쉽다. 바로 그 이유로 브라우저 확장은 취약점을 발견하기 좋은 표적이 된다.

고전적 예가 카지노 컴포넌트다. 클라이언트 측 통제의 미덥지 못함을 생각하면, 잠재적 공격자의 머신에서 로컬로 돌아가는 브라우저 확장으로 온라인 도박을 구현한다는 발상은 흥미롭다. 게임 플레이의 어떤 측면이 서버가 아니라 클라이언트에서 통제된다면, 공격자는 게임을 정밀하게 조작해 승률을 높이거나, 규칙을 바꾸거나, 서버로 보내는 점수를 고칠 수 있다. 가능한 공격은 이렇다.

- 클라이언트 컴포넌트가 **게임 상태를 유지**하도록 신뢰받는 경우 — 로컬에서 상태를 변조해 이득을 얻는다.
- 클라이언트 측 통제를 우회해 **불법 동작**을 수행한다.
- 호출 시 서버 리소스에 부정 접근하게 하는 **숨은 함수·파라미터·리소스**를 찾는다.
- 게임에 상대나 하우스 플레이어가 있다면, 컴포넌트가 **다른 플레이어에 관한 정보**를 받아 처리할 수 있고, 그것을 알면 공격자에게 유리하다.

### 26.4.1 흔한 브라우저 확장 기술

가장 자주 마주치는 브라우저 확장 기술은 **자바 애플릿, Flash, Silverlight**다. 유사한 목표를 두고 경쟁했기에, 보안상 관련된 아키텍처 속성도 서로 닮았다.

- **중간 바이트코드로 컴파일된다.**
- 실행을 위한 **샌드박스 환경을 제공하는 가상 머신**에서 돈다.
- 복잡한 데이터 구조나 객체를 HTTP로 전송하기 위해 **직렬화를 쓰는 리모팅 프레임워크**를 사용할 수 있다.

| 기술 | 실행 환경 | 패키지 | 바이트코드 | 직렬화 형식(Content-Type) |
|---|---|---|---|---|
| 자바 애플릿 | JVM (자바 보안 정책 샌드박스) | `.jar`(zip) | `.class` | `application/x-java-serialized-object` |
| Flash | Flash VM | `.swf` | ActionScript 바이트코드 | AMF, `application/x-amf` |
| Silverlight | 축소된 .NET 런타임 | `.xap`(zip) | `.dll` | NBFS, `application/soap+msbin1` |

*표 26-1. 세 브라우저 확장 기술의 보안 관련 속성 (WAHH 5장 기준)*

자바 애플릿은 웹 역사 초기부터 있었고 핵심 개념이 비교적 안 변해, 공격·방어 지식과 도구가 풍부하다. Flash는 애니메이션 전달 수단에서 출발해 ActionScript 3와 AMF 리모팅으로 본격 데스크톱 애플리케이션까지 담게 됐다. Silverlight는 마이크로소프트의 Flash 대안으로, 브라우저 안에서 축소된 .NET 경험을 샌드박스로 제공한다. C#이 가장 흔하지만 어떤 .NET 호환 언어로도 개발할 수 있다.

> **이 기술들은 오늘날 폐기됐다.** 자바 애플릿·Flash·Silverlight는 모두 현대 브라우저에서 지원이 끊겼다. 그럼에도 이 절과 다음 절을 보존하는 이유는, 이들이 **패턴 학습용 표본**이기 때문이다. "클라이언트에서 실행되는 코드는 분석되고 변조된다"는 명제는 실행 환경이 바이트코드 VM이든, WebAssembly든, 모바일 앱이든 바뀌지 않는다. 기술은 바뀌어도 명제는 유효하다. 아래 디컴파일·디버깅 절차는 그 명제가 구체적으로 어떻게 실현되는지를 보여 주는 예시로 읽어야 한다.

### 26.4.2 두 가지 접근법

브라우저 확장 컴포넌트를 쓰는 애플리케이션을 공략할 때 크게 두 기법을 쓴다.

**첫째, 컴포넌트가 주고받는 요청·응답을 가로채 수정한다.** 대개 가장 빠르고 손쉬운 출발점이다. 그러나 한계가 있다. 전송 데이터가 난독화·암호화됐거나, 그 기술 특유의 직렬화 스킴으로 포장됐을 수 있다. 컴포넌트가 생성한 트래픽만 봐서는, 컴포넌트 자체를 분석해야만 드러나는 핵심 기능·비즈니스 로직을 놓칠 수 있다.

**둘째, 컴포넌트 자체를 직접 겨냥해 바이트코드를 디컴파일하거나, 디버거로 동적으로 상호작용한다.** 철저히 하면 컴포넌트가 지원·참조하는 모든 기능을 식별할 수 있고, 전송 중 난독화·암호화와 무관하게 요청의 핵심 데이터를 수정할 수 있다는 이점이 있다. 단점은 시간이 많이 들고 해당 기술·언어에 대한 이해가 필요하다는 것이다.

많은 경우 두 기법의 조합이 적절하다. 다음 절이 각각을 상세히 본다.

## 26.5 브라우저 확장 트래픽 가로채기 · 디컴파일 · 디버거 부착

### 26.5.1 트래픽 가로채기와 직렬화 데이터

브라우저가 이미 인터셉팅 프록시를 쓰도록 설정돼 있고 애플리케이션이 확장 컴포넌트를 로드하면, 그 컴포넌트의 요청이 프록시를 지나는 것을 볼 수 있다. 컴포넌트가 검증한 데이터를 서버로 투명하게 제출한다면, HTML 폼 데이터와 똑같이 프록시로 수정된다. 인증 컴포넌트가 자격증명을 캡처·검증해 평문 파라미터로 보낸다면, 컴포넌트를 분석하지 않고도 검증이 쉽게 우회된다.

그러나 데이터가 직렬화돼 있으면 얘기가 달라진다. 원시 직렬화 데이터를 그냥 편집하면 형식이 깨져 파싱 오류가 난다. 먼저 언패킹하고, 편집하고, 올바르게 다시 직렬화해야 한다. 각 기술은 자체 직렬화 스킴을 갖는데, 앞의 표 26-1처럼 대개 `Content-Type` 헤더로 형식을 알 수 있다. 자바 직렬화 객체는 DSer 같은 Burp 플러그인으로 XML로 풀어 편집한 뒤 재직렬화한다. Flash의 AMF는 Burp가 기본 지원해 트리 형태로 보여 준다. Silverlight의 NBFS는 별도 플러그인으로 디코딩한다. 요점은 하나다 — **직렬화는 인코딩이지 보안이 아니다.** 도구가 갖춰지면 어떤 직렬화 형식도 열리고 편집된다.

프록시가 확장 트래픽을 못 가로채는 경우도 있다. 컴포넌트가 브라우저의 프록시 설정을 따르지 않고 자체 HTTP 요청을 발행하거나, 프록시가 제시하는 SSL 인증서를 거부하는 경우다. 전자는 hosts 파일 수정과 비가시 프록싱으로, 후자는 마스터 CA 인증서를 신뢰 저장소에 설치해 우회한다(→ 25.8, 부록 B). HTTP가 아닌 프로토콜을 쓰면 프록시로는 안 되고, Echo Mirage 같은 소켓 API 후킹 도구나 스니퍼로 다뤄야 한다.

트래픽 가로채기의 실무 절차에서 특히 값진 지점이 있다. **핵심 클라이언트 로직을 촉발하는 서버 응답을 가로채 수정하면, 잠긴 클라이언트 GUI를 "열어" 복잡하거나 다단계의 특권 동작을 손쉽게 수행하게 만들 수 있다.** 그리고 도박 앱의 카드 뽑기·주사위 굴리기처럼 클라이언트가 수행해선 안 될 핵심 로직이 있다면, 그 실행과 서버 통신 사이의 상관을 찾는다. **클라이언트가 결과를 정하는 데 서버와 통신하지 않는다면, 그 애플리케이션은 확실히 취약하다.**

### 26.5.2 디컴파일

브라우저 확장을 공격하는 가장 철저한 방법은, 객체를 디컴파일해 소스 코드를 전면 검토하고, 필요하면 코드를 고쳐 동작을 바꾼 뒤 재컴파일하는 것이다. 바이트코드는 고수준의 플랫폼 독립적 이진 표현이라, 이론상 언제나 원본 소스에 가깝게 디컴파일할 수 있다. 다만 디컴파일러를 실패시키거나 읽기 어려운 소스를 뱉게 하는 방어 기법(난독화)이 적용될 수 있다.

**바이트코드 내려받기.** 바이트코드는 대개 애플리케이션 페이지 HTML 소스에 지정된 URL에서 단일 파일로 로드된다. 자바 애플릿은 `<applet>` 태그로, 다른 컴포넌트는 보통 `<object>` 태그로 로드된다.

```html
<applet code="CheckQuantity.class" codebase="/scripts"
        id="CheckQuantityApplet"></applet>
```

URL이 덜 분명하면 프록시 히스토리에서 찾는다. 이때 두 장애물에 유의한다 — 프록시가 이미지·스타일시트를 히스토리에서 숨기는 필터를 걸어 뒀을 수 있으니 모든 항목을 보이게 하고, 브라우저가 확장 바이트코드를 다른 정적 리소스보다 공격적으로 캐시하므로 캐시를 완전히 비우고 브라우저를 새로 띄워야 다시 요청하게 만들 수 있다.

**언패킹과 디컴파일.** 자바 애플릿은 `.jar`, Silverlight는 `.xap`로 패키징되며 둘 다 zip 형식이라, 확장자를 `.zip`으로 바꿔 풀면 `.class`·`.dll` 바이트코드가 나온다. Flash의 `.swf`는 언패킹이 필요 없다. 디컴파일 도구는 자바는 Jad, Flash는 Flasm·Flare·SWFScan, Silverlight는 .NET Reflector 등을 쓴다.

**소스에서 무엇을 찾는가.** 클라이언트에서 일어나는 입력 검증·보안 관련 로직, 서버로 보내기 전에 데이터를 감싸는 난독화·암호화 루틴, UI에는 안 보이지만 컴포넌트를 고쳐 열 수 있는 "숨은" 기능, 매핑에서 발견 못 한 서버 측 기능 참조.

**워크드 예제 — 온라인 서점의 수량 검증 애플릿.** 주문 수량을 검증하는 자바 애플릿을 예로 들자. 폼은 사용자 수량과 `obfpad`(난독화 패드)를 애플릿의 `doCheck` 메서드에 넘기고, 애플릿은 검증 후 난독화된 수량을 돌려주며, 그 값이 서버로 제출된다.

```java
public String doCheck(String s, String s1) {
    int i = Integer.parseInt(s);
    if (i <= 0 || i > 50) return null;               // 1~50 검증
    String s2 = "rand=" + Math.random() + "&q="
              + Integer.toString(i) + "&checked=true";
    StringBuilder sb = new StringBuilder();
    for (int j = 0; j < s2.length(); j++) {          // obfpad와 XOR
        String s3 = "0" + Integer.toHexString(
            (byte) s1.charAt((j*19 + 7) % s1.length()) ^ s2.charAt(j));
        int k = s3.length();
        if (k > 2) s3 = s3.substring(k - 2, k);
        sb.append(s3);
    }
    return sb.toString();
}
```

디컴파일해 보면 로직은 단순하다 — 수량이 1~50인지 검증하고, 이름/값 문자열을 만든 뒤, `obfpad` 문자열과 XOR로 피상적 난독화를 건다. 이 애플릿을 뒤엎는 가장 쉬운 길은, `doCheck`에서 입력 검증을 제거해 임의 문자열을 수량으로 넣게 하고, `main` 메서드를 추가해 명령줄에서 실행해 난독화 결과를 콘솔에 찍게 하는 것이다.

```java
public static void main(String[] a) {
    System.out.println(doCheck("999", "klGSB8X9xOWFv9KG..."));
}
```

`javac`로 재컴파일해 실행하면 임의 수량 999에 대한 유효한 난독화 문자열이 나온다. 정상 입력으로 주문 폼을 제출해 요청을 프록시로 가로챈 뒤, 난독화된 수량을 이 값으로 치환하면 공격이 서버에 전달된다. **여기서 999 대신 비숫자 입력을 넣으면, 이 진입점을 통해 온갖 입력 기반 취약점을 탐침할 수 있다.** 난독화라는 클라이언트 측 통제가, 서버로 가는 임의 페이로드의 관문이 되어 버린 것이다.

바이트코드 난독화에 부딪히면 — 의미 있는 이름을 `a`, `b`로 치환하거나, 예약어를 식별자로 쓰거나, 디버그 정보를 제거하거나, 무의미한 중복 코드와 뒤틀린 실행 경로를 넣는 기법 — 다음으로 대처한다. 공개 메서드는 소스를 완전히 이해하지 않고도 시그니처를 파악해 시험할 수 있고, 의미 없는 이름은 IDE의 리네임 기능으로 쓰임을 추적하며 의미를 부여하고, 난독화 자체를 다시 난독화 도구(Jode 등)에 통과시켜 상당 부분 되돌릴 수 있다.

### 26.5.3 디버거 부착

디컴파일이 가장 완전한 방법이지만, 수만 줄의 크고 복잡한 컴포넌트에서는 실행 중에 관찰하며 메서드·클래스를 UI의 핵심 동작과 연관 짓는 편이 거의 언제나 훨씬 빠르다. 이 접근은 난독화된 바이트코드의 해석·재컴파일 어려움도 피한다. 특정 목표를 이루는 것이 핵심 함수 하나를 실행해 그 동작을 바꾸는 일만큼 단순할 때가 많다.

디버거는 바이트코드 수준에서 동작하므로 실행 흐름을 통제·이해하기 쉽고, 디컴파일로 소스를 얻었다면 특정 줄에 브레이크포인트를 걸어 관찰로 뒷받침할 수 있다. 자바 애플릿은 디버깅 지원이 잘 돼 있다. JavaSnoop은 Jad를 통합해 소스를 디컴파일하고, 변수를 추적하며, 메서드에 브레이크포인트를 걸어 파라미터를 보고 수정하고, **메서드의 반환값을 변조**할 수 있다. JSwat은 핵심 클래스를 디컴파일·수정·재컴파일해 실행 중인 애플리케이션에 핫스왑하는 데 유용하다. Silverlight는 Silverlight Spy로 런타임 실행을 관찰한다.

> **주의.** JavaSnoop 같은 도구는 대상에 작용하기 위해 자바 보안 정책의 제약을 끈다. Windows에서는 시스템의 모든 자바 프로그램에 전체 권한을 부여하는 식이므로, 작업을 마치면 도구가 깨끗이 종료되어 권한이 복원되는지 확인해야 한다.

## 26.6 네이티브 클라이언트 컴포넌트

일부 애플리케이션은 브라우저 기반 VM 샌드박스 안에서는 할 수 없는 동작을 사용자 컴퓨터에서 수행해야 한다. 클라이언트 측 보안 통제의 맥락에서 예를 들면 다음과 같다.

- 사용자가 최신 바이러스 스캐너를 갖췄는지 확인
- 프록시 설정 등 기업 구성이 적용됐는지 확인
- 스마트카드 리더와의 통합

이런 동작은 대개 로컬 애플리케이션 기능을 웹 애플리케이션 기능과 통합하는 **네이티브 코드 컴포넌트**를 요구한다. 네이티브 클라이언트 컴포넌트는 흔히 ActiveX 컨트롤로 전달된다. 브라우저 샌드박스 밖에서 도는 맞춤 브라우저 확장이다.

네이티브 컴포넌트는 중간 바이트코드에 해당하는 것이 없어 다른 브라우저 확장보다 해독이 상당히 어렵다. 그러나 **클라이언트 측 통제 우회의 원리는 그대로 적용된다** — 다른 도구를 요구할 뿐이다. OllyDbg는 네이티브 실행 코드를 단계 실행하고 브레이크포인트를 걸며 디스크·런타임에서 패치하는 Windows 디버거이고, IDA Pro는 다양한 플랫폼의 네이티브 코드에서 사람이 읽을 수 있는 어셈블리를 뽑는 디스어셈블러다.

여기서 26.5절과 이 절의 논지가 만난다. 바이트코드 VM이든 네이티브 코드든, **클라이언트에서 도는 코드는 분석되고 변조된다.** 분석의 난이도가 다를 뿐 가능성은 다르지 않다. 네이티브 컴파일 애플리케이션 자체의 취약점 — 버퍼 오버플로, 정수 취약점, 포맷 스트링 — 을 찾고 익스플로잇하는 방법은 31.4~31.6절에서 서버 측 네이티브 코드를 대상으로 다룬다. 클라이언트 측 네이티브 컴포넌트도 같은 부류의 결함을 안고 있으며, 같은 분석 기법이 적용된다.

> **이 책의 범위를 넘어서**
>
> 현대의 클라이언트 측 리버싱 — 단일 페이지 애플리케이션의 번들 분석, WebAssembly 모듈 디스어셈블, 모바일 앱 리버싱, 그리고 이를 막으려는 상용 코드 난독화·무결성 검증 제품 — 은 이 책이 근거로 삼는 다섯 권의 범위를 넘는다. 다만 이 장의 명제는 그 영역에서도 그대로 유효하다는 점만 지적해 둔다. DRM 기술이 매번 짧은 시간 안에 깨져 온 역사가 그 증거다. 클라이언트에 둔 방어는 결정적 공격자를 잠시 늦출 뿐 막지는 못한다. 실행 환경이 무엇이든, 코드가 사용자의 기계에서 돌면 사용자가 그것을 지배한다.

## 26.7 클라이언트 데이터를 안전하게 다루기

지금까지의 모든 절은 하나를 증명했다 — 클라이언트, 그리고 그로부터 받는 모든 데이터는 본질적으로 신뢰할 수 없다. 그렇다면 애플리케이션은 무엇을 해야 하는가. 이 절은 WAHH의 실무 처방을, 다음 절은 그 처방의 밑에 깔린 설계 원칙을 정리한다.

### 26.7.1 가능하면 클라이언트를 경유해 전달하지 말라

많은 애플리케이션이 가격·할인율 같은 결정적 데이터를 클라이언트로 안전하지 않게 전달해 스스로를 노출시킨다. **가능한 한 이런 데이터를 클라이언트로 보내지 말아야 한다.** 거의 모든 시나리오에서 이런 데이터는 서버에 보관하고 필요할 때 서버 측 로직에서 직접 참조할 수 있다.

온라인 서점의 주문 처리를 보자. 사용자는 **상품 코드와 수량**만 제출하면 되고, 각 상품의 가격은 서버 측 데이터베이스에서 조회한다. 가격을 서버로 되돌려 보낼 이유가 없다. 사용자마다 다른 가격·할인을 제공하더라도 이 모델을 벗어날 필요가 없다 — 가격은 사용자별로 데이터베이스에 보관하고, 할인율은 사용자 프로필이나 세션 객체에 저장한다. **애플리케이션은 이미 서버 측에 특정 사용자의 특정 상품 가격을 계산하는 데 필요한 모든 정보를 갖고 있다. 갖고 있을 수밖에 없다** — 안전하지 않은 모델에서도 그 가격을 히든 필드에 넣으려면 먼저 서버가 그 값을 알아야 하기 때문이다.

### 26.7.2 부득이하면 서명·암호화하되 재생을 막으라

결정적 데이터를 클라이언트로 전달할 수밖에 없다고 판단되면, 그 데이터에 **서명하거나 암호화해** 변조를 막아야 한다. 이때 피해야 할 두 함정이 있다.

- **재생 공격.** 상품 가격을 암호화해 히든 필드에 넣으면, 더 싼 상품의 암호화된 가격을 복사해 원래 가격 자리에 제출할 수 있다(→ 26.1.5의 3번). 이를 막으려면 암호화된 데이터에 **충분한 문맥**을 포함해 다른 문맥에서 재생되지 못하게 해야 한다. 예컨대 상품 코드와 가격을 이어 붙여 하나의 항목으로 암호화하고, 주문과 함께 제출된 암호문이 실제 주문 상품과 일치하는지 검증한다.
- **키 유도 공격.** 사용자가 암호화된 문자열의 평문을 알거나 통제하면, 여러 암호 공격으로 서버의 암호화 키를 알아낼 수 있다. 키가 노출되면 임의 값을 암호화해 보호를 완전히 무력화한다.

ASP.NET에서는 ViewState에 맞춤 데이터를, 특히 화면에 노출하고 싶지 않은 민감 데이터를 절대 저장하지 말아야 하며, **ViewState MAC 옵션은 항상 켜 두어야 한다**(→ 26.2).

### 26.7.3 클라이언트가 생성한 데이터는 서버에서 재검증하라

클라이언트에서 생성돼 서버로 전송된 데이터는 원리상 클라이언트에서 안전하게 검증할 수 없다.

- HTML 폼 필드·JavaScript 같은 가벼운 클라이언트 통제는 손쉽게 우회되며, 서버가 받는 입력에 대해 아무것도 보장하지 못한다.
- 브라우저 확장 컴포넌트의 통제는 때로 우회가 더 어렵지만, 공격자를 잠시 늦출 뿐이다.
- 무겁게 난독화·패킹된 클라이언트 코드는 장애물을 더할 뿐, 결정적 공격자는 언제나 극복한다.

**클라이언트가 생성한 데이터를 안전하게 검증하는 유일한 방법은 서버 측에서 하는 것이다. 클라이언트에서 받는 모든 데이터 항목은 오염됐고 잠재적으로 악의적이라고 간주해야 한다.** 클라이언트 측 검증 자체가 나쁜 것은 아니다 — 사용성을 위한 클라이언트 스크립트 검증, DOM 기반 XSS에 대한 방어로서의 클라이언트 검증(→ 32.7, 32.9), 재생 불가능하게 설계된 암호화 데이터 전달은 모두 보안 결함을 낳지 않는 정당한 쓰임이다. 문제는 클라이언트 검증을 **서버가 하지 않고 대신** 신뢰할 때다.

### 26.7.4 로깅과 경보

길이 제한이나 JavaScript 검증처럼 성능·사용성을 위한 메커니즘을 쓸 때, 이를 **서버 측 침입 탐지 방어와 통합**해야 한다. 검증을 수행하는 서버 측 로직은 클라이언트에서 이미 어떤 검증이 일어났는지 알고 있어야 한다. **클라이언트 검증이라면 막았을 데이터가 도착했다면, 사용자가 능동적으로 그 검증을 우회하고 있으며 따라서 악의적일 가능성이 높다고 추론할 수 있다.** 이상 징후는 로깅하고, 필요하면 관리자에게 실시간으로 경보해 공격 시도를 모니터링하고 대응하게 한다. 애플리케이션은 세션을 종료하거나 계정을 정지시켜 능동적으로 방어할 수도 있다. 다만 JavaScript를 끈 사용자는 검증 코드를 건너뛰고 원시 입력을 제출하므로, 오탐을 피하려면 로깅·경보 메커니즘이 이 상황을 인지하고 있어야 한다. (방어자의 로그·경보·공격 대응 전반은 → 16.5.)

> **이 절이 뒷받침하는 것**
>
> - 클라이언트 경유 전달을 피하라 → 이 처방이 **29장** (로직 결함)의 여러 사례, 특히 가격·수량 조작을 원천 차단한다.
> - 서버 재검증 → **27장·28장** (인젝션)과 **32장** (XSS)은 이 재검증이 없을 때 성립하는 공격이다.
> - 재생 방지 문맥 결합 → **23.2** (토큰 생성의 약점)의 방어와 같은 원리.

## 26.8 데이터의 출처를 검증하라

26.7절은 "무엇을 하라"의 목록이었다. 이 절은 그 목록이 왜 그런 순서로 서 있는지, 하나의 설계 원칙으로 되짚는다. WAHH가 실무 처방을 주었다면, SBD(Secure by Design)는 그 처방을 검증의 순서라는 설계 관점으로 정리한다.

"입력을 검증하라"는 조언은 너무 자주 들려서 무의미해졌다. "운전할 때 충돌을 피하라"만큼이나 옳지만 도움이 안 된다. 어떤 값이 유효한지는 상황에 달렸다 — 도서 주문에서 수량 42는 유효하지만 -1은 아니고, 기온 보고에서는 -1이 멀쩡하며, `<script>` 문자열조차 보안 버그를 접수하는 사이트에서는 정당한 입력이다. 검증을 유용하게 만들려면 그것을 종류별로 나누고, 좋은 순서를 정해야 한다. SBD가 제시하는 순서는 다섯 단계다.

1. **출처(Origin)** — 데이터가 정당한 발신자에게서 왔는가?
2. **크기(Size)** — 합리적인 크기인가?
3. **어휘적 내용(Lexical content)** — 올바른 문자와 인코딩을 담았는가?
4. **구문(Syntax)** — 형식이 맞는가?
5. **의미(Semantics)** — 데이터가 말이 되는가?

이 순서에는 이유가 있다. **비싼 검사를 값싼 검사가 가려 준다.** 출처와 크기 확인은 값싸고 빠르다. 어휘 검사는 스캔이 필요해 조금 더 든다. 구문 검사는 파싱을 요구해 CPU를 쓰고 스레드를 점유한다. 의미 검사는 대개 데이터베이스로의 무거운 왕복을 수반한다. 이른 검사가 나중의 비싼 검사가 불필요하게 수행되는 것을 막는다. **43.4절이 이 다섯 단계 검증을 코드 구조의 관점에서 상세히 다룬다.** 이 장에서 답할 것은 하나다 — 왜 첫 단계가 "출처"인가.

### 26.8.1 왜 첫 단계가 출처인가

많은 공격이 **비대칭적**이기 때문이다. 비대칭이란, 공격자가 악의적 데이터를 보내는 데 드는 노력이, 시스템이 그것을 처리하는 데 드는 노력보다 훨씬 적다는 뜻이다. 이것이 서비스 거부(DoS) 공격의 기본 논리다 — 시스템에 쓰레기 데이터를 잔뜩 보내 그것을 처리하느라 정작 할 일을 못 하게 만든다. 데이터의 출처를 확인하는 것은 이 비대칭을 방어자에게 유리하게 뒤집는 **첫 단계**다. 정당한 출처에서 왔으면 계속 처리하고, 아니면 버린다. 처리에 노력을 쓰기 전에, 처리할 가치가 있는 데이터인지부터 값싸게 거른다.

출처를 확인하는 방법은 크게 둘이다.

- **IP 주소 확인.** 가장 단순하다. 마이크로서비스 아키텍처에서 내부 서비스는 다른 서비스의 특정 IP 범위에서 오는 트래픽만 받도록 제한할 수 있다. 실무에서는 애플리케이션 내부가 아니라 네트워크 설정 — 물리 라우터, 클라우드의 보안 그룹 — 으로 강제한다. 다만 **IP·MAC 필터는 아무것도 보장하지 못한다.** MAC은 OS에서 바꿀 수 있고, IP는 스푸핑되거나 실제 머신이 탈취될 수 있다. 그래도 최소한의 1차 방어선은 된다.
- **접근 키(access key).** 인터넷 어디에서든 오는 요청이라면 IP로 거를 수 없으므로 — 공개 서비스는 거의 다 그렇다 — 정당한 클라이언트에게 키를 발급한다. 키의 보유가 곧 발신 자격의 증명이 된다. 다만 키만 보내는 것으로는 부족하다. 공격자가 키를 스푸핑해 사칭할 수 있으므로, 메시지 내용을 비밀 키로 서명해 함께 보낸다. AWS의 REST API가 `Authorization` 헤더에 접근 키와 서명을 함께 싣는 방식이 이 구조다. 접근 키 자체도 검증(길이·문자셋·형식)해야 공격 벡터가 되지 않는다.

출처 확인이 모든 경우에 통하는 것은 아니다. 그러나 이 장 전체가 말한 것과 연결하면 그림이 완성된다. **26.1절의 히든 필드·쿠키·Referer가 실패한 근본 이유는, 그것들이 데이터의 "출처"를 증명하지 못했기 때문이다.** `Referer: .../Admin.ashx`는 요청이 관리 페이지에서 왔다는 주장일 뿐 증명이 아니다. `DiscountAgreed=15` 쿠키는 서버가 그 할인을 승인했다는 주장일 뿐 증명이 아니다. 클라이언트가 통제하는 어떤 값도 출처를 증명하지 못한다 — 증명은 서명된 토큰이나 검증된 접근 키처럼, 클라이언트가 위조할 수 없는 무언가를 요구한다. 그래서 검증의 첫 단계가 출처이고, 그래서 클라이언트에 둔 통제는 통제가 아니다.

Basic 인증이 자격증명을 매 요청 평문으로 실어 나르면서도 그것을 신뢰의 근거로 삼았던 결함(→ 21.3)도 같은 문제의 다른 얼굴이다 — 클라이언트가 보낸 값을, 그 출처를 위조 불가능하게 확인하지 않고 믿었다. 이 장이 클라이언트 경유 데이터에서 본 것을, 21장은 인증에서, 23장은 세션에서, 24장은 인가에서 각각 보았다. **모두 하나의 문제다 — 서버는 도착한 바이트가 어디서 왔는지, 위조 불가능한 방식으로 확인하기 전에는 믿어서는 안 된다.**

> **이 절이 뒷받침하는 것**
>
> - 다섯 단계 검증의 첫 단계 "출처" → **43.4** (검증의 순서)가 코드 구조로 상세화하고, **43.5** (경계 검증)와 대응시킨다.
> - 출처 확인의 비대칭 논리 → **45.8** (DoS를 설계로 막기)의 근거.
> - 위조 불가능한 출처 증명의 부재 → **21.3**(Basic 인증), **23.2**(토큰), **24.7**(인가는 경계 검증의 한 형태)과 같은 뿌리.

## 이 장의 요약

- **클라이언트에 둔 통제는 통제가 아니다.** 6.7절의 명제("사용자는 임의의 입력을 보낼 수 있다")의 첫 번째 구체적 귀결이며, 이 장의 여덟 절이 각기 다른 각도에서 이 하나를 증명한다.
- **클라이언트를 경유해 데이터를 되돌려받는 모든 수단 — 히든 필드, 쿠키, URL 파라미터, Referer, 불투명 값, ViewState — 은 변조된다.** 화면에 안 보이는 것, 헤더에 실린 것, 인코딩·직렬화된 것은 모두 인터셉팅 프록시 앞에서 편집 가능하다.
- **불투명 데이터와 ViewState는 값을 읽지 못해도 재생될 수 있다.** 23.2절의 암호화된 토큰 오용과 같은 실패 구조이며, 암호를 한 글자도 깨지 않고 성립한다.
- **HTML 폼의 길이 제한·스크립트 검증·비활성 요소는 사용성 장치이지 보안 통제가 아니다.** 서버에 복제되지 않은 클라이언트 검증은 우회된 뒤 인젝션·XSS의 관문이 된다.
- **브라우저 확장과 네이티브 컴포넌트의 통제는 우회가 더 어려울 뿐 불가능하지 않다.** 자바 애플릿·Flash·Silverlight는 폐기됐지만, "클라이언트에서 도는 코드는 분석되고 변조된다"는 명제는 실행 환경이 바뀌어도 유효하다.
- **클라이언트 데이터를 안전하게 다루는 실무 처방은 넷이다** — 가능하면 전달하지 않기, 부득이하면 재생 불가능하게 서명·암호화하기, 서버에서 반드시 재검증하기, 우회 시도를 로깅·경보하기.
- **모든 처방은 하나의 설계 원칙으로 수렴한다 — 검증은 데이터의 출처를 확인하는 데서 시작한다.** 출처 확인이 검증의 첫 단계인 것은 공격의 비대칭성 때문이며, 클라이언트 경유 데이터가 실패하는 근본 이유는 그것이 출처를 위조 불가능하게 증명하지 못하기 때문이다.

## 이어지는 장

이 장은 25장이 그린 진입점 목록의 각 항목에 대해 "서버가 이 값을 얼마나 믿는가"를 물었고, 답은 한결같았다 — 믿어서는 안 된다. 그런데 이 장이 다룬 것은 주로 **비즈니스 데이터의 조작**이었다. 가격을 바꾸고, 할인을 얻고, 수량 제한을 넘는 것. 다음 두 장은 같은 진입점에 전혀 다른 종류의 페이로드를 넣는다.

27장과 28장은 클라이언트 통제를 우회해 서버에 도달한 입력을, 서버 측 **해석 컨텍스트**를 겨냥한 무기로 바꾼다. 26.3절에서 우회한 수량 필드에 `' OR 1=1--`을 넣으면 SQL 인젝션이 되고, 26.5절에서 애플릿을 고쳐 임의 문자열을 넣을 수 있게 된 진입점에 명령 문자열을 넣으면 OS 명령 인젝션이 된다. **이 장이 "클라이언트 검증은 우회된다"를 증명했기에, 다음 장들은 그 우회를 전제로 삼을 수 있다.** 27장이 SQL·NoSQL·XPath·LDAP를, 28장이 명령·경로·XML·요청 인젝션을 다룬다.

그리고 이 장의 마지막 두 절이 던진 설계 관점 — 클라이언트 데이터를 안전하게 다루는 처방과, 검증은 출처에서 시작한다는 원칙 — 은 Part IX에서 온전히 회수된다. 43.4절이 다섯 단계 검증을 코드 구조로 구현하고, 44장이 도메인 프리미티브로 오염된 입력을 타입 수준에서 차단한다. 이 장에서 우리는 "클라이언트를 믿지 말라"고 말했다. 그 명령을 코드가 저절로 지키게 만드는 방법이 설계다.
