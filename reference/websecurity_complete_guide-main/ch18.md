# 18장. HTTPS: 핸드셰이크에서 검증까지

> **이 장에서 다루는 것**
>
> - `https` 스킴 하나가 실제로 무엇을 바꾸고 무엇을 그대로 두는가
> - TCP 핸드셰이크 위에 TLS 핸드셰이크가 누적되는 구조와, 첫 HTTP 바이트가 나가기까지의 정확한 왕복 횟수
> - 실제 클라이언트가 서버 인증서에서 무엇을, 어떤 순서로 확인하는가 — 그리고 이름 일치 규칙의 정확한 형태
> - 검증이 실패했을 때 무슨 일이 일어나는가, 그리고 그 판단이 왜 사용자에게 넘어가는가
> - 이름이 핸드셰이크 안(SNI)과 HTTP 헤더 안(`Host`)에 두 번 실리게 된 경위와 그 결과
> - TLS 레코드가 TCP 세그먼트와 어떻게 어긋나는가

17장은 재료를 다뤘다. 대칭키 암호, 공개키 암호, 서명, 인증서, 신뢰 사슬, 폐기. 그 장의 마지막 절은 인증서가 답하는 문장을 한 줄로 적고, 그 문장이 성립하기 위한 세 조건을 나열한 뒤 상세를 이 장으로 넘겼다. **클라이언트가 실제로 검증할 것, 신뢰 저장소가 오염되지 않았을 것, 사용자가 경고를 무시하지 않을 것.** 첫 번째와 세 번째가 이 장의 18.3절과 18.4절이다.

그러나 검증을 다루기 전에 순서를 열어야 한다. 인증서는 허공에서 나타나지 않는다. 그것은 핸드셰이크라는 정해진 메시지 교환의 두 번째 왕복에서, 정해진 자리에 실려 온다. 그 자리를 알아야 무엇이 그 앞에 있고 무엇이 그 뒤에 있는지 — 즉 **무엇이 평문이고 무엇이 암호화되는지** — 를 말할 수 있다. 18.6절이 SNI를 다룰 때 필요한 것이 정확히 그 구분이다.

이 장은 세 개의 무게중심을 갖는다. **18.2절은 비용의 장부**다. 1.6절이 RTT를 단위로 세웠고 3.2절이 TCP 핸드셰이크에 1왕복을 청구했다. 여기에 TLS가 2왕복을 더한다. 19장 전체가 이 청구서를 깎는 작업이다. **18.3~18.4절은 이 장의 논지**다. 검증은 알고리즘이지만, 그 알고리즘이 실패했을 때 무엇을 할 것인가는 알고리즘이 아니다. **18.6~18.7절은 경계의 재발견**이다. 가상 호스팅이 만든 문제(15.2)와 프레이밍이 만든 문제(1.3.2)가 TLS 계층에서 한 번씩 더 나타난다.

## 18.1 HTTPS의 세부 — 스킴, 포트, 계층 구조

HTTPS는 새로운 애플리케이션 프로토콜이 아니다. **같은 HTTP를 안전한 전송 계층 위로 보내는 것**이다. HTTP 메시지를 암호화하지 않은 채 TCP로 넘기는 대신, 먼저 보안 계층으로 넘겨 암호화한 뒤 TCP로 넘긴다. 그것이 전부다.

계층 구조는 1.2절 그림 1-1에서 이미 그렸다. HTTP 스택에 계층 하나가 끼어들고, 그 아래는 그대로다. 여기서 다시 그리지 않는다. 대신 그 구조가 **표면에서 어떤 형태로 드러나는가**를 본다. 스킴, 포트, 그리고 트랜잭션의 순서다.

### 스킴이 결정을 내린다

오늘날 보안 HTTP는 선택 사항이다. 따라서 클라이언트에게 "이번에는 보안 버전으로 하라"고 말할 방법이 필요하다. 그 방법이 **URL의 스킴**이다.

```
http://www.joes-hardware.com/power-tools.html
https://www.joes-hardware.com/power-tools.html
```

클라이언트가 리소스에 대한 트랜잭션을 수행하라는 요청을 받으면 URL의 스킴을 검사한다.

- 스킴이 `http`이면 기본 포트 **80**으로 커넥션을 열고 평범한 HTTP 명령을 보낸다.
- 스킴이 `https`이면 기본 포트 **443**으로 커넥션을 열고, 서버와 **핸드셰이크**를 해서 바이너리 형식으로 보안 파라미터를 교환한 뒤, 암호화된 HTTP 명령을 보낸다.

이 두 줄에 이 절의 내용이 거의 다 들어 있다. 그러나 짚어야 할 것이 세 가지 남는다.

**첫째, 포트가 왜 따로인가.** SSL 트래픽은 HTTP와 완전히 다른 바이너리 프로토콜이다. 만약 SSL과 HTTP가 같은 80번 포트로 도착한다면, 대부분의 웹 서버는 바이너리 SSL 트래픽을 잘못된 HTTP로 해석하고 커넥션을 닫을 것이다. **보안 서비스를 HTTP 안에 더 통합적으로 계층화했더라면 목적지 포트를 여러 개 둘 필요가 없었겠지만**, 실무에서 이것이 심각한 문제를 일으키지는 않는다는 것이 원서의 평가다.

이 결정은 21년 뒤까지 영향을 남겼다. 포트가 다르다는 것은 **경로상의 모든 장비가 두 트래픽을 다르게 취급한다**는 뜻이다. 방화벽은 80과 443을 따로 열고, 프록시는 443으로 가는 트래픽을 `CONNECT` 터널로 처리하며(→ 19.8), 로드밸런서는 두 포트에 서로 다른 처리 경로를 배정한다. 11.12절이 정리한 "왜 새 프로토콜은 결국 443번 포트로 오는가"의 배경이 여기에 있다. **중간자가 통과시키는 포트가 두 개뿐이므로, 새로 만드는 것은 그 두 개 중 하나를 써야 한다.**

**둘째, 스킴은 네트워크 접촉 이전에 결정된다.** 클라이언트가 TLS를 쓸지 말지는 URL 문자열을 읽는 순간 정해진다. 서버는 이 결정에 참여하지 않는다. 그렇다면 그 문자열은 어디서 오는가. 사용자가 타이핑한 주소창, 문서 안의 링크, 이전 응답의 `Location` 헤더, 북마크, 검색 결과다. **이 중 어느 것도 아직 인증된 채널을 통해 오지 않았다.**

이것이 이 장이 남기고 19장이 받는 문제다. 인증서 검증이 아무리 엄격해도 그 검증은 **`https`로 시작한 요청에 대해서만** 수행된다. `http`로 시작하면 검증할 인증서 자체가 없다. 경로상의 참여자가 응답 본문의 `https://` 링크를 `http://`로 바꾸면, 클라이언트는 아무 경고 없이 평문으로 간다. 19.7절이 HSTS를 다루는 이유이고, 19.10절이 혼합 콘텐츠를 다루는 이유다.

**셋째, 스킴과 포트가 출처(origin)의 일부다.** `http://www.joes-hardware.com`과 `https://www.joes-hardware.com`은 **서로 다른 출처**다. 같은 호스트명이지만 브라우저의 보안 모델에서는 다른 두 곳이다. 이 사실이 쿠키의 `Secure` 속성(→ 20.6), 혼합 콘텐츠 차단(→ 19.10), 그리고 캐시 키의 구성(→ 14.5)에서 각각 다르게 나타난다.

**표 18-1. `http`와 `https`의 표면 차이**

| 항목 | `http` | `https` |
|---|---|---|
| 기본 포트 | 80 | 443 |
| TCP 커넥션 수립 후 첫 바이트 | HTTP 요청 라인 | TLS `ClientHello` (바이너리) |
| HTTP 메시지 문법 | 동일 | **동일** |
| 경로상 관찰자가 보는 것 | 메시지 전체 | IP, 포트, 크기, 타이밍, `ClientHello`의 평문 부분(→ 18.6) |
| 트랜잭션 단계 수 | 4 | 6 (핸드셰이크와 종료 통지가 추가) |
| 출처(origin) | `(http, host, 80)` | `(https, host, 443)` — 다른 출처 |

### 트랜잭션의 순서

암호화되지 않은 HTTP에서 클라이언트는 서버의 80번 포트로 TCP 커넥션을 열고, 요청 메시지를 보내고, 응답 메시지를 받고, 커넥션을 닫는다. 네 단계다.

HTTPS에서는 보안 계층 때문에 절차가 조금 더 복잡해진다. 클라이언트는 먼저 443번 포트로 커넥션을 연다. TCP 커넥션이 수립되면 클라이언트와 서버가 SSL 계층을 초기화하며 암호 파라미터를 협상하고 키를 교환한다. 핸드셰이크가 끝나면 초기화가 완료되고, 그때부터 클라이언트는 보안 계층으로 요청 메시지를 보낼 수 있다. 그 메시지들은 TCP로 넘겨지기 전에 암호화된다.

```
(a) 평문 HTTP                          (b) HTTPS

1. TCP 커넥션 수립 (포트 80)           1. TCP 커넥션 수립 (포트 443)
                                       2. TLS 보안 파라미터 핸드셰이크
2. HTTP 요청을 TCP로 전송              3. HTTP 요청을 TLS로 → 암호화되어 TCP로
3. HTTP 응답을 TCP로 수신              4. 암호화된 응답을 TCP로 → TLS가 복호
                                       5. TLS 종료 통지 (close_notify)
4. TCP 커넥션 종료                     6. TCP 커넥션 종료
```

*그림 18-1. 평문 HTTP 트랜잭션과 HTTPS 트랜잭션의 단계 (HTTP-DG 그림 14-15 기준)*

추가된 두 단계가 각각 이 장의 한 절이 된다. **2단계가 18.2절**이고, **5단계가 18.7절의 알림(alert) 프로토콜**이다.

5단계를 지금 한 번 짚어 둘 값이 있다. 평문 HTTP에서 커넥션 종료는 TCP의 FIN 하나로 끝난다. 3.7절이 그 절차를 다뤘고 9.9절이 그것이 HTTP에서 만드는 모호함 — 응답이 다 온 것인지 끊긴 것인지 — 을 다뤘다. **TLS는 그 모호함에 대한 답을 프로토콜 안에 갖고 있다.** `close_notify`라는 명시적 종료 알림이 그것이다. 이 알림 없이 TCP 커넥션이 끊기면, TLS 계층은 스트림이 잘렸다는 것을 알 수 있다. 18.7절에서 이 사실이 왜 중요한지를 다시 본다.

> **이 절이 뒷받침하는 것**
>
> - HTTPS는 HTTP를 바꾸지 않는다 → **Part V~VII 전체** (쿠키, 세션, 인젝션, 파싱 불일치는 TLS 안에서 그대로 성립한다)
> - TLS 사용 여부가 URL 문자열로 결정된다 → **19.7** (HSTS), **19.10** (혼합 콘텐츠)
> - 443번 포트만이 중간자를 통과한다 → **11.12** (ALPN), **19.8** (`CONNECT` 터널)

## 18.2 TLS 핸드셰이크의 단계별 해부 — 추가 RTT의 정체

암호화된 HTTP 메시지를 보내기 전에 클라이언트와 서버는 핸드셰이크를 해야 한다. 그 핸드셰이크에서 하는 일은 네 가지다.

1. **프로토콜 버전 번호를 교환한다.**
2. **양쪽이 아는 암호(cipher)를 고른다.**
3. **각 측의 신원을 인증한다.**
4. **채널을 암호화할 임시 세션 키를 생성한다.**

17장의 재료가 여기에 하나씩 대응한다. 2번이 17.3절의 대칭키 알고리즘 선택이고, 3번이 17.6~17.8절의 인증서와 신뢰 사슬이며, 4번이 17.4절의 혼합 암호 시스템 — 느린 공개키 연산으로 빠른 대칭 세션 키에 합의한다는 것 — 이다. 1번은 나머지 셋의 문법을 정하는 메타 협상이다.

### 메시지의 순서

전체 핸드셰이크의 메시지 순서는 다음과 같다. `*` 표시는 조건부로만 나타나는 메시지다.

```
클라이언트                                             서버

ClientHello                     ────────▶
                                              ServerHello
                                             Certificate*
                                       ServerKeyExchange*
                                      CertificateRequest*
                                ◀────────  ServerHelloDone

Certificate*
ClientKeyExchange
CertificateVerify*
[ChangeCipherSpec]
Finished                        ────────▶

                                       [ChangeCipherSpec]
                                ◀────────         Finished

애플리케이션 데이터              ◀───────▶  애플리케이션 데이터
```

*그림 18-2. 전체 핸드셰이크의 메시지 순서 (TLS 1.2 기준. HTTP-DG 그림 14-16과 HPBN 그림 4-2가 이 순서의 단순화된 형태다)*

각 메시지가 무엇을 나르는지는 아래 표에 정리한다.

**표 18-2. 핸드셰이크 메시지와 그 내용**

| 메시지 | 보내는 쪽 | 무엇이 들어 있는가 | 대응하는 17장 절 |
|---|---|---|---|
| `ClientHello` | 클라이언트 | 지원하는 최고 프로토콜 버전, 클라이언트 난수, 지원 암호 스위트 **목록**, 압축 방법, 확장(SNI·ALPN 등) | 17.3 |
| `ServerHello` | 서버 | **선택된** 버전 하나, 서버 난수, **선택된** 암호 스위트 하나, 선택된 확장 | 17.3 |
| `Certificate` | 서버 | 서버 인증서와 중간 인증서들 — 즉 **사슬** | 17.6, 17.8 |
| `ServerKeyExchange` | 서버 | 키 교환에 인증서만으로 부족할 때의 추가 파라미터 | 17.4 |
| `CertificateRequest` | 서버 | 클라이언트 인증서를 요구한다는 표시, 받아들일 CA 이름 목록 | 18.5 |
| `ServerHelloDone` | 서버 | "내가 보낼 것은 다 보냈다" | — |
| `Certificate` | 클라이언트 | 클라이언트 인증서 (요구받은 경우) | 18.5 |
| `ClientKeyExchange` | 클라이언트 | 사전 마스터 비밀 — **서버의 공개키로 암호화되어 있다** | 17.4 |
| `CertificateVerify` | 클라이언트 | 지금까지의 핸드셰이크 전체에 대한 클라이언트의 서명 — 개인키 소유 증명 | 17.5, 18.5 |
| `ChangeCipherSpec` | 양쪽 | "다음 레코드부터 협상된 암호를 적용한다" | — |
| `Finished` | 양쪽 | 지금까지 오간 **모든 핸드셰이크 메시지의 해시** — 협상 내용의 무결성 검사 | 17.5 |

세 가지를 강조해 둔다.

**첫째, `ChangeCipherSpec`은 핸드셰이크 메시지가 아니다.** 그것은 별도의 콘텐츠 타입을 갖는 독립 프로토콜의 한 바이트짜리 메시지다. 그림 18-2에서 대괄호로 표시한 이유가 그것이다. 이 구분은 18.7절에서 레코드 계층의 콘텐츠 타입 필드를 볼 때 다시 나온다.

**둘째, `Finished`가 협상 자체를 보호한다.** `Finished`는 지금까지 오간 모든 핸드셰이크 메시지를 해시해서, 협상된 키로 MAC을 걸어 보낸다. 양쪽이 서로의 `Finished`를 검증하면, **핸드셰이크 도중에 경로상의 누군가가 메시지를 고쳤다면 그 사실이 드러난다.** 예를 들어 `ClientHello`의 암호 스위트 목록에서 강한 것들을 지워 약한 것만 남긴다면, 클라이언트가 기억하는 원본과 서버가 받은 것이 다르므로 해시가 어긋난다.

이것이 11.12절이 "ALPN은 핸드셰이크의 무결성 안에 있다"고 적은 것의 근거다. `ClientHello`의 확장 필드에 실린 프로토콜 목록도 `Finished`의 해시 범위 안에 있다. 평문 `Upgrade` 헤더에는 그런 보호가 없다.

**셋째, `ClientKeyExchange` 이전의 모든 것은 평문이다.** 이것이 이 절에서 가장 중요한 사실이다. 원서의 표현을 빌리면, **새 대칭 키가 서버의 공개키로 암호화된 것을 제외하면 지금까지의 모든 데이터가 평문으로 교환되었다.** 버전, 암호 스위트 목록, 서버 인증서 전체, 그리고 `ClientHello`의 모든 확장이 그렇다. **SNI가 평문으로 나가는 이유가 여기에 있다**(→ 18.6).

### 왕복을 세어 보기

1.6절이 RTT를 단위로 세웠고 3.2절이 TCP 핸드셰이크에 1왕복을 청구했다. 그 위에 TLS가 얹힌다. 3장이 쓴 것과 같은 조건 — 뉴욕의 클라이언트와 런던의 서버, 편도 전파 28밀리초, **왕복 56밀리초** — 으로 시각을 매겨 보자.

**표 18-3. 전체 핸드셰이크의 타임라인 (뉴욕↔런던, RTT 56 ms. HPBN 그림 4-2 기준)**

| 시각 | 일어나는 일 | 계층 | 이 책의 절 |
|---|---|---|---|
| 0 ms | 클라이언트가 SYN 전송 | TCP | 3.2 |
| 28 ms | 서버가 SYN-ACK 전송 | TCP | 3.2 |
| 56 ms | 클라이언트가 ACK와 함께 **`ClientHello`** 전송 — 버전, 암호 스위트 목록, 확장을 **평문**으로 | TLS | 18.2 |
| 84 ms | 서버가 버전과 암호 스위트를 고르고, **인증서를 붙여** `ServerHello`·`Certificate`·`ServerHelloDone` 전송. 선택적으로 클라이언트 인증서 요청 | TLS | 18.2, 18.5 |
| 112 ms | 클라이언트가 **인증서를 검증**하고, 새 대칭 키를 만들어 서버 공개키로 암호화해 전송(`ClientKeyExchange`), `ChangeCipherSpec`·`Finished` 전송 | TLS | **18.3** |
| 140 ms | 서버가 대칭 키를 복호하고, MAC으로 무결성을 확인한 뒤, 암호화된 `Finished`를 회신 | TLS | 18.2 |
| 168 ms | 클라이언트가 그 메시지를 복호하고 MAC을 검증한다. 이상이 없으면 **터널 수립 완료** | TLS | 18.2 |
| 168 ms | **첫 HTTP 요청 바이트가 나간다** | HTTP | 5.5 |
| 224 ms | 응답의 첫 바이트가 도착할 수 있는 가장 이른 시각 | HTTP | — |

**TCP 1왕복 + TLS 2왕복 = 3왕복.** 애플리케이션 데이터 한 바이트가 흐르기 전에 168밀리초가 지나간다. 같은 조건에서 평문 HTTP라면 요청이 56밀리초에 나갔다(3.2절 표). **TLS가 청구하는 것은 112밀리초, 즉 정확히 2왕복이다.**

이 숫자는 대역폭과 무관하다. 3.2절이 TCP 핸드셰이크에 대해 적은 것과 같은 이유다. 링크가 1Mbps든 10Gbps든 168밀리초다. 핸드셰이크에서 오가는 바이트는 몇 킬로바이트에 불과하고, 지연을 지배하는 것은 거리다.

그리고 여기에 3.4절이 하나를 더 얹는다. **핸드셰이크의 바이트도 혼잡 윈도우의 지배를 받는다.** 서버가 보내는 `Certificate` 메시지는 사슬 전체를 담으므로 수 킬로바이트가 되기 쉽다. 18.8절에서 볼 실제 출력에서 그 값은 3,571바이트인데, 이것은 초기 혼잡 윈도우 3~4세그먼트의 크기에 매우 가깝다. **사슬이 조금만 길어지면 인증서 전송 자체가 한 왕복을 더 먹는다.** 19.6절이 이 계산을 정면으로 다룬다.

### 공개키 연산은 어디에 쓰이는가

핸드셰이크 전체에서 공개키 암호가 쓰이는 자리는 **한 곳뿐**이다. 서버가 공개키를 제공하고, 클라이언트가 대칭 키를 만들어 그 공개키로 암호화해 되돌려 보내고, 서버가 자기 개인키로 복호한다. 그 이후의 모든 통신은 그 대칭 키로 처리된다.

17.4절이 혼합 암호 시스템을 설명하며 적은 것이 이 문장이다. 이유는 성능이다. **공개키 암호는 계산 비용이 훨씬 크다.** 직접 확인할 수 있다.

```bash
openssl speed rsa      # 키 길이별 초당 연산 수
openssl speed aes      # 초당 바이트 수
```

두 결과의 단위는 직접 비교할 수 없다. RSA는 키 길이별 **초당 연산 수** 표를 주고, AES는 **초당 바이트 수**로 측정된다. 그럼에도 읽어야 할 것은 분명하다. 권장 키 길이 1,024비트 또는 2,048비트에서의 **RSA 연산 수 — 즉 전체 핸드셰이크 수 — 가 병목이 될 가능성이 높다.** 이 숫자가 19.2절에서 서버 용량 계획의 입력이 된다.

정확한 수치는 하드웨어, 코어 수, TLS 버전, 서버 설정에 따라 크게 달라진다. 마케팅 자료나 철 지난 벤치마크를 믿지 말고 **자기 하드웨어에서 직접 측정하라**는 것이 원서의 조언이다.

### 이 비용을 누가 갚는가

이 절이 계산한 3왕복은 **새 커넥션마다** 발생한다. 9장이 커넥션 관리를 다루며 반복해서 지적한 것 — 새 커넥션은 비싸다 — 이 TLS에서 세 배로 비싸진다.

19장 전체가 이 청구서에 대한 응답이다.

- **19.1·19.3절**: 이미 협상한 비밀 키를 재사용해서 두 번째 왕복을 없앤다. 전체 핸드셰이크가 2왕복이라면, 축약 핸드셰이크는 1왕복이다.
- **19.2절**: 왕복 자체의 길이를 줄인다. 서버를 사용자 가까이 두면 56밀리초가 20밀리초가 된다. 3왕복이 그대로여도 총 시간은 3분의 1이 된다.
- **19.6절**: 사슬을 짧게 만들어 인증서 전송이 추가 왕복을 만들지 않게 한다.

**세 처방이 같은 표(표 18-3)의 서로 다른 줄을 공격한다.** 19장을 읽을 때 이 표를 옆에 두면 각 절이 어느 줄을 지우는지가 보인다.

> **이 책의 범위를 넘어서**
>
> 이 절이 센 2왕복은 TLS 1.2까지의 전체 핸드셰이크 기준이다. 이후 표준화된 TLS 1.3은 이 교환을 재설계해 **새 커넥션의 전체 핸드셰이크를 1왕복으로 줄였고**, 이전에 접속한 적이 있는 서버에 대해서는 첫 요청 데이터를 핸드셰이크와 함께 보내는 **0왕복(0-RTT)** 모드를 도입했다. 같은 개정에서 협상 가능한 약한 선택지 다수가 제거되었고, 핸드셰이크의 더 많은 부분이 암호화 범위 안으로 들어왔다. 그와 별개로 발급된 모든 인증서를 공개 로그에 기록하는 인증서 투명성(Certificate Transparency), `ClientHello` 자체를 암호화해 SNI 노출을 없애려는 암호화된 클라이언트 헬로(ECH), 특정 키나 CA만 받아들이도록 클라이언트에 못 박는 현대적 핀닝이 각각 이 장의 18.3·18.4·18.6절이 지적하는 문제에 대한 응답으로 배치되었다. 이 책이 다루는 다섯 권의 원서는 그 이전에 쓰였고, 상세는 이 책의 범위 밖이다. **다만 이 절의 구조 — 왕복 횟수를 세고, 무엇이 평문이며, 협상 결과가 무엇으로 보호되는지를 묻는 것 — 는 어느 버전에서도 그대로 쓰인다.**

> **이 절이 뒷받침하는 것**
>
> - TCP 1왕복 위에 TLS 2왕복이 누적된다 → **19.1, 19.2, 19.3** (각각 다른 줄을 지운다)
> - `ClientKeyExchange` 이전은 전부 평문이다 → **18.6** (SNI가 왜 노출되는가), **1.2** (TLS가 가리지 않는 것의 목록)
> - `Finished`가 핸드셰이크 전체를 해시한다 → **11.12** (ALPN이 다운그레이드에 저항하는 이유), **19.7** (프로토콜 차원의 다운그레이드는 다른 문제다)
> - 인증서 사슬의 바이트가 혼잡 윈도우 안에 있다 → **19.6** (사슬 길이와 OCSP 스테이플링), **3.4** (slow-start)

## 18.3 서버 인증서 검증 — 실제 클라이언트는 무엇을 확인하는가

표 18-3의 112밀리초 줄에 한 단어로 적힌 것이 있다. **"클라이언트가 인증서를 검증하고."** 이 절이 그 한 단어를 펼친다.

먼저 원서의 문장 하나를 그대로 인용해야 한다. 이 절 전체가 이 문장 위에 서 있기 때문이다.

> **SSL 자체는 웹 서버 인증서를 검사하도록 요구하지 않는다.**

프로토콜은 검증을 강제하지 않는다. 핸드셰이크는 인증서를 **배달**할 뿐이고, 그것을 열어 볼 것인가는 클라이언트의 정책이다. 인증서를 받아서 즉시 버리고 `ClientKeyExchange`로 넘어가도 핸드셰이크는 정상적으로 완료되며, 터널은 암호화되고, 양쪽은 만족스럽게 데이터를 주고받는다. **암호화는 상대가 누구인지 묻지 않는다**(17.7절). 검증은 그 질문을 던지기로 한 클라이언트만 던진다.

17.10절이 나열한 세 조건 중 첫 번째 — "클라이언트가 실제로 검증할 것" — 이 프로토콜의 성질이 아니라 구현의 선택인 이유가 이것이다.

그렇다면 검증하기로 한 클라이언트는 무엇을 하는가. 넷스케이프가 제안한 웹 서버 인증서 검증 알고리즘이 대부분의 브라우저 검증 기법의 기초를 이룬다. 원서는 이 알고리즘을 네 단계로 적었다. **날짜 검사, 서명자 신뢰 검사, 서명 검사, 사이트 신원 검사.** 여기에 17.9절이 다룬 폐기 확인과 17.6절이 다룬 용도 제약을 더하면 실제 클라이언트가 수행하는 검증의 전체 목록이 된다.

**아래에서는 논리적 의존 순서로 다시 배열한다.** 원서가 날짜부터 적은 것은 가장 싼 검사를 먼저 한다는 실무적 순서이고, 아래 순서는 각 단계가 앞 단계의 결과를 필요로 하는 순서다.

### 단계 1 — 사슬 구성과 서명 검증

서버가 보낸 `Certificate` 메시지에는 서버 인증서와 그것을 발급한 중간 인증서들이 들어 있다. 클라이언트는 이것을 **사슬로 조립**한다. 각 인증서의 발급자(Issuer) 이름이 다음 인증서의 주체(Subject) 이름과 맞물리도록 이어 붙이고, 마지막 고리가 **자기 신뢰 저장소에 있는 루트 CA**에 닿는지를 확인한다.

닿았으면 그다음이 서명 검증이다. 각 고리에 대해, **발급자의 공개키로 서명을 열어** 인증서 내용의 다이제스트와 비교한다(17.5절의 절차 그대로). 하나라도 어긋나면 그 인증서는 위조되었거나 전송 중 변경된 것이다.

원서는 이 둘을 두 단계로 나눠 적었고, 그 구별이 의미가 있다.

- **서명자 신뢰 검사**: 이 사슬의 끝이 내가 신뢰하는 기관인가. 브라우저는 신뢰하는 서명 기관 목록을 **탑재한 채 배포된다.** 알 수 없는(그리고 어쩌면 악의적인) 기관이 서명한 인증서를 받으면 대개 경고를 표시한다. 브라우저는 **신뢰받는 CA로 이어지는 유효한 서명 경로를 가진 인증서라면 받아들이기로 선택할 수도 있다.** 신뢰받는 CA가 "Sam's Signing Shop"에 인증서를 발급하고 Sam's Signing Shop이 사이트 인증서에 서명했다면, 브라우저는 그것을 유효한 CA 경로에서 유래한 것으로 받아들일 수 있다.
- **서명 검사**: 서명 기관이 신뢰할 만하다고 판정된 뒤, 브라우저는 **서명 기관의 공개키를 서명에 적용해 체크섬과 비교함으로써** 인증서의 무결성을 확인한다.

여기서 17.8절의 정식화가 다시 나온다. **검증은 AND로 이뤄지지만 발급은 OR로 이뤄진다.** 사슬의 모든 고리가 유효해야 검증이 통과하지만, 어떤 이름에 대한 유효한 인증서가 존재하려면 신뢰 목록의 어느 CA 하나만 서명하면 된다.

### 단계 2 — 유효 기간

브라우저는 인증서의 시작 날짜와 종료 날짜를 확인해서 아직 유효한지를 본다. **만료되었거나 아직 활성화되지 않았으면 검증은 실패하고 브라우저는 오류를 표시한다.** X.509의 `Validity Period` 필드(17.6절 표)가 이 검사의 대상이다.

이 단계는 두 개의 전제를 갖는다. **첫째, 클라이언트의 시계가 맞아야 한다.** 시계가 어긋난 기기에서는 정상 인증서가 만료로 보이거나 만료된 인증서가 유효로 보인다. **둘째, 사슬의 모든 고리에 대해 확인해야 한다.** 서버 인증서가 유효 기간 안이어도 중간 CA 인증서가 만료되었으면 그 사슬은 성립하지 않는다.

### 단계 3 — 이름 일치

**서버가 다른 사람의 인증서를 복사하거나 그들의 트래픽을 가로채는 것을 막기 위해, 대부분의 브라우저는 인증서의 도메인 이름이 자기가 대화한 서버의 도메인 이름과 일치하는지 검증하려 한다.** 서버 인증서는 보통 도메인 이름 하나를 담지만, 일부 CA는 서버 클러스터나 팜을 위해 **서버 이름 목록이나 와일드카드 도메인 이름**을 담은 인증서를 만든다. **호스트명이 인증서의 신원과 일치하지 않으면, 사용자 지향 클라이언트는 사용자에게 통지하거나 잘못된 인증서 오류로 커넥션을 종료해야 한다.**

이 단계가 이 절에서 가장 오해가 많은 자리다. 세 가지를 정확히 해야 한다.

**첫째, 무엇과 무엇을 비교하는가.** 비교의 왼쪽은 인증서 안의 이름이고, 오른쪽은 **클라이언트가 접속하려고 의도한 이름**이다. 그 이름의 출처는 **URL의 호스트 부분**이다. DNS가 답한 IP 주소가 아니고, 실제로 연결된 소켓의 주소도 아니며, 서버가 뭐라고 주장하든 그것도 아니다.

이 구분이 왜 결정적인지는 2.7절과 17.10절이 이미 준비해 두었다. DNS 응답은 신뢰할 수 없고 경로도 신뢰할 수 없다. 그러므로 검증의 기준점은 **네트워크가 알려준 어떤 값도 아닌, 애플리케이션이 처음부터 가지고 있던 문자열**이어야 한다. 그 문자열이 URL의 호스트명이다.

**둘째, 이름이 인증서의 어디에 있는가.** 역사적으로는 주체 이름(Subject)의 공통 이름(Common Name, CN) 필드에 호스트명을 넣었다. 그러나 CN은 원래 사람이 읽을 이름을 담는 자리이고 하나뿐이므로, 여러 이름을 담을 수 없다. 그래서 X.509 v3의 확장(17.6절)에 **주체 대체 이름(subjectAltName, SAN)** 이 도입되었고, 호스트명은 그 안의 `dNSName` 항목에 넣는다.

두 자리가 공존하면 우선순위가 필요하다. 규칙은 명확하다. **SAN에 `dNSName` 항목이 하나라도 있으면 CN은 무시한다.** SAN이 없을 때에만 CN을 호스트명으로 해석한다. 이 규칙을 지키지 않고 CN을 먼저 보거나 CN도 함께 받아들이는 구현은, SAN에 없는 이름을 CN에 적어 넣은 인증서를 통과시킨다.

IP 주소로 접속하는 경우는 또 다르다. **URL의 호스트가 IP 주소라면 SAN의 `iPAddress` 항목과 비교해야 한다.** `dNSName`에 IP 주소처럼 보이는 문자열이 적혀 있어도 그것은 이름이지 주소가 아니다.

**셋째, 와일드카드의 범위.** `*.securesites.com` 같은 이름이 무엇에 대응하는지는 규칙이 정해져 있다.

**표 18-4. 이름 일치 판정 예시**

| 인증서의 이름 | 접속하려는 호스트명 | 일치 | 근거 |
|---|---|---|---|
| `www.joes-hardware.com` | `www.joes-hardware.com` | **O** | 정확히 같다 |
| `www.joes-hardware.com` | `WWW.Joes-Hardware.COM` | **O** | 호스트명 비교는 대소문자를 구별하지 않는다 |
| `www.joes-hardware.com` | `joes-hardware.com` | **X** | 다른 이름이다. 접두 레이블은 무료로 붙지 않는다 |
| `joes-hardware.com` | `www.joes-hardware.com` | **X** | 같은 이유 |
| `*.joes-hardware.com` | `www.joes-hardware.com` | **O** | `*`가 최좌측 레이블 **하나**에 대응 |
| `*.joes-hardware.com` | `store.joes-hardware.com` | **O** | 같은 이유 |
| `*.joes-hardware.com` | `joes-hardware.com` | **X** | `*`는 **빈 레이블**에 대응하지 않는다 |
| `*.joes-hardware.com` | `shop.eu.joes-hardware.com` | **X** | `*`는 레이블 **하나**에만 대응한다 |
| `shop.*.joes-hardware.com` | `shop.eu.joes-hardware.com` | **X** | 와일드카드는 **최좌측 레이블**에만 허용된다 |
| `*.securesites.com` | `www.cajun-shop.com` | **X** | 아래 사례. 도메인 자체가 다르다 |
| `*.com` | `www.joes-hardware.com` | **X** | 공용 접미사에 대한 와일드카드는 허용하지 않는다 |
| `192.0.2.10` (CN 문자열) | `https://192.0.2.10/` | **X** | IP는 `iPAddress` 형식 SAN으로만 일치한다 |

표의 열한 번째 줄이 원서가 실제 사례로 든 것이다. 루이지애나를 테마로 한 전자상거래 사이트 `Cajun-Shop.com`은 호스팅 제공자로부터 `cajun-shop.securesites.com`이라는 공식 이름을 받았다. 사용자가 `https://www.cajun-shop.com`으로 가면, 서버 인증서에 적힌 공식 호스트명 `*.securesites.com`이 사용자가 브라우징한 가상 호스트명 `www.cajun-shop.com`과 일치하지 않고, 경고 상자가 뜬다. **이 문제를 막기 위해 Cajun-Shop.com의 소유자는 보안 트랜잭션을 시작할 때 모든 사용자를 `cajun-shop.securesites.com`으로 리다이렉트한다.** 원서의 결론은 짧다. **"가상 호스팅된 사이트의 인증서 관리는 좀 까다로울 수 있다."**

이 사례는 이 장의 세 절을 동시에 건드린다. **18.4절**이 이 경고 상자에서 무슨 일이 일어나는지를 다루고, **18.6절**이 SNI가 이 문제의 근본 — 하나의 서버 프로그램이 인증서 하나만 지원한다는 것 — 을 어떻게 없앴는지를 다루며, **15.2절**이 애초에 왜 하나의 IP에 여러 이름이 얹히게 되었는지를 다뤘다.

### 단계 4 — 폐기 확인

인증서 자체가 폐기 확인 방법에 대한 지시를 담고 있다(17.9절). 클라이언트는 사슬을 올라가면서 각 인증서의 서명과 함께 **그 인증서에 박힌 지시를 따라 상태를 확인**한다. CRL을 가져와 일련번호가 목록에 있는지 보거나, OCSP로 그 일련번호 하나를 직접 질의한다.

17.9절이 정리한 대로 **실제 클라이언트의 동작은 제각각이다.** 자체 CRL 목록을 배포하는 클라이언트, CA에서 CRL 파일을 가져와 캐시하는 클라이언트, 실시간 OCSP 검사를 하는 클라이언트가 모두 있고, **OCSP 요청이 실패했을 때의 동작은 브라우저마다 다르다.**

여기가 검증 알고리즘 전체에서 유일하게 **네트워크 접근을 요구하는 단계**라는 점이 중요하다. 앞의 세 단계는 이미 받은 바이트와 이미 가진 신뢰 저장소만으로 판정할 수 있다. 폐기 확인만이 제3자에게 물어야 한다. 그리고 그 제3자가 응답하지 않을 때 무엇을 할 것인가는 **검증의 문제가 아니라 실패 처리의 문제**다. 18.4절이 그것을 다룬다.

### 단계 5 — 용도 제약

마지막으로, 인증서에 적힌 **용도**가 지금의 쓰임과 맞는지를 본다. 17.6절이 표로 정리한 X.509 v3 확장들이 이 검사의 대상이다.

**표 18-5. 용도 관련 확장과 그 검사 (17.6절 표 14-2의 확장 필드)**

| 확장 | 무엇을 제한하는가 | 위반의 예 |
|---|---|---|
| `Basic Constraints` | 이 인증서가 CA인가 아닌가, 사슬의 깊이 제한 | CA가 아닌 인증서로 다른 인증서를 서명 |
| `Key Usage` | 이 키로 무엇을 할 수 있는가 — 서명, 키 암호화, 인증서 서명 | 인증서 서명 권한이 없는 키로 서명된 사슬 |
| `Certificate Policy` | 어떤 정책 아래 발급되었는가 | 정책이 요구하는 조건 밖의 사용 |

그리고 17.6절이 인용한 원서의 규칙 하나가 여기서 다시 나온다. **인식하지 못하는 critical 확장이 있으면 인증서를 거부해야 한다.** 이것은 실패 설계의 원칙이 프로토콜에 박힌 드문 사례다. **모르는 제약은 무시하는 것이 아니라 거부하는 것**이라는 규칙이고, 45장이 실패 설계에서 다시 만날 형태다.

### 이 다섯 단계에 대한 세 가지 관찰

**첫째, 다섯 단계는 AND로 묶인다.** 하나라도 실패하면 검증은 실패한다. 순서는 오류 메시지의 내용을 정하지만 최종 판정을 바꾸지 않는다.

**둘째, 이 알고리즘 어디에도 "이 사이트가 내가 생각하는 조직인가"를 판정할 자리가 없다.** 17.10절 논점 1이 이미 적었다. `joes-hardware-store.com`을 등록하고 통제권을 증명해 인증서를 받으면, 그 인증서는 위 다섯 단계를 **완벽하게 통과한다.** 검증은 문자열 비교이고, 문자열과 조직의 대응은 사용자의 머릿속에 있다.

**셋째, 그리고 가장 중요하게 — 이 알고리즘의 존재 여부 자체가 애플리케이션의 선택이다.** 다섯 단계를 하나도 수행하지 않아도 TLS 커넥션은 수립된다. 표 18-3의 168밀리초 줄에는 "터널 수립 완료"라고 적혀 있고, 검증을 건너뛴 클라이언트에게도 그 줄은 그대로 적힌다.

**표 18-6. 검증 단계와 그것이 없을 때 무엇이 성립하는가**

| 수행하지 않은 단계 | 여전히 성립하는 것 | 무너지는 것 |
|---|---|---|
| 사슬·서명 검증 | 암호화, 무결성 | 상대가 누구든 자기가 만든 인증서를 내면 통과 |
| 유효 기간 | 암호화, 무결성, CA의 보증 | 침해되어 폐기·만료된 키가 영원히 유효 |
| **이름 일치** | 암호화, 무결성, "어떤 정당한 사이트"임 | **아무 유효한 인증서나 통과** — 경로를 잡은 자가 자기 도메인의 정상 인증서로 사칭 |
| 폐기 확인 | 위 전부 | 폐기 이후의 창 |
| 용도 제약 | 위 전부 | 최종 인증서로 다른 이름을 서명하는 사슬 |

세 번째 줄을 특히 봐야 한다. **사슬 검증은 하면서 이름 검사를 빼먹는 구현**이 실무에서 압도적으로 흔한 오류 형태다. 그 상태에서는 공격자가 자기가 소유한 도메인에 대해 **완벽하게 정상적인 인증서**를 발급받아 제시하면 된다. CA를 공격할 필요도, 자체 서명 인증서를 만들 필요도 없다. **17.10절이 계산한 "공격 조건의 상승분"이 정확히 0이 되는 지점이다.** 18.8절에서 이 오류가 코드의 어느 줄에서 발생하는지를 본다.

## 18.4 검증 실패의 유형 — 이름 불일치, 만료, 신뢰 사슬 단절, 그리고 사용자에게 떠넘기기

18.3절은 검증이 성공하는 조건을 적었다. 이 절은 실패했을 때 무슨 일이 일어나는지를 적는다. 그리고 이 장의 논지가 여기에 있다.

### 실패의 유형

**표 18-7. 검증 실패의 유형과 그 해석**

| 실패 유형 | 어느 단계 | 무해한 원인 (실무에서 압도적으로 흔함) | 공격일 때의 의미 |
|---|---|---|---|
| **이름 불일치** | 3 | 가상 호스팅 인증서(`*.securesites.com` 사례), 이름 변경 후 갱신 누락, `www` 유무, IP로 직접 접속 | 경로를 잡은 자가 **자기 것인 정상 인증서**를 제시. 가장 값싼 사칭 |
| **만료 / 아직 유효하지 않음** | 2 | 갱신을 잊음, 클라이언트 시계 오차, 새 인증서 배포 직전 | 폐기·만료된 키를 손에 넣은 자의 재사용 |
| **신뢰 사슬 단절** | 1 | **중간 인증서 미전송**(서버 설정 실수 중 최다), 사설 CA, 자체 서명, 오래된 신뢰 저장소 | 공격자가 만든 인증서. 사슬이 없거나 아무도 모르는 CA로 끝난다 |
| **서명 불일치** | 1 | 사실상 없음 | 인증서 내용이 변조됨 |
| **폐기됨** | 4 | 사실상 없음 | 침해가 이미 알려진 키 |
| **폐기 확인 불가** | 4 | OCSP 응답자 장애, 폐쇄망, 프록시 차단 | 공격자가 폐기 조회 자체를 막음 |
| **용도 위반 / 모르는 critical 확장** | 5 | 잘못 발급된 인증서, 구형 클라이언트 | 최종 인증서를 CA처럼 쓰는 사슬 |

이 표에서 읽어야 할 것은 **왼쪽 두 열이 아니라 오른쪽 두 열의 대비**다.

거의 모든 행에서 **무해한 원인이 악의적 원인보다 몇 자릿수 더 흔하다.** 인증서 갱신을 잊는 관리자는 매일 있고, 중간 인증서를 빠뜨린 서버 설정은 어디에나 있으며, 시계가 어긋난 기기는 흔하다. 반면 실제 중간자 공격은 드물다. **그리고 이 비대칭이 다음 절의 모든 것을 결정한다.**

두 가지 유형은 따로 짚어야 한다.

**신뢰 사슬 단절 중 "중간 인증서 미전송"** 은 서버 설정 오류인데도 **일부 클라이언트에서만 실패한다.** 그 중간 인증서를 이미 캐시하고 있거나 자체 저장소에 갖고 있는 클라이언트는 사슬을 완성할 수 있기 때문이다. 그래서 "내 브라우저에서는 되는데 다른 데서는 안 된다"는 형태로 나타난다. 18.8절의 `openssl s_client`가 이 증상을 진단하는 표준 도구다.

**폐기 확인 불가**는 다른 여섯 행과 성질이 다르다. 나머지는 **받은 것을 검사해서 얻은 부정적 결론**이지만, 이것은 **결론을 얻지 못한 상태**다. 17.9절이 OCSP의 네 문제 중 하나로 "클라이언트가 탐색을 진행하기 전에 OCSP 요청에서 블로킹해야 한다"를 적었다. 응답자가 죽었을 때 커넥션을 막으면 CA의 장애가 전 세계 사이트의 장애가 되고, 통과시키면 **공격자가 OCSP 질의를 차단하는 것만으로 폐기 확인을 무력화**할 수 있다. 대부분의 클라이언트가 후자를 택했다. 그것이 17.9절이 말한 "폐기 모델의 비대칭"이 실제로 청구되는 자리다. 19.6절의 OCSP 스테이플링이 이 딜레마에 대한 부분적 응답이다.

### 사용자에게 떠넘기기

원서에는 그림 하나가 있다. 그 그림의 네 캡션을 순서대로 읽어 보자.

> (a) 이 URL의 호스트명(`www.cajun-shop.com`)이 인증서의 이름과 일치하지 않는다. 사이트가 가상 호스팅되어 있고 인증서는 `*.securesites.com`에 발급되었기 때문이다.
>
> (b) 대화상자가 사용자에게 경고한다. 사이트의 인증서는 **유효한 날짜를 가지고 있고 유효한 인증 기관에서 발급되었지만**, 인증서에 적힌 이름이 URL에서 요청한 사이트와 일치하지 않는다고.
>
> (c) 더 자세한 내용을 보려면 사용자가 "인증서 보기" 버튼을 누른다. 그러면 그것이 `*.securesites.com`에 발급된 와일드카드 인증서임을 알게 된다. **이 정보를 가지고 사용자는 인증서를 받아들일지 거절할지 결정할 수 있다.**
>
> (d) 인증서를 받아들이면 페이지가 안전한 HTTPS 프로토콜로 로드된다.

*그림 18-3. 이름 불일치 경고의 흐름 (HTTP-DG 그림 14-18의 캡션)*

(c)의 문장이 이 절의 표적이다. **"이 정보를 가지고 사용자는 결정할 수 있다."**

무엇을 가지고 무엇을 결정하는가. 사용자가 손에 쥔 정보는 인증서에 적힌 이름이 `*.securesites.com`이라는 것 하나다. 그 정보로 답해야 하는 질문은 이것이다.

> **`www.cajun-shop.com`이라는 사이트가 `securesites.com`이라는 이름의 조직에게 자기 HTTPS 트래픽을 맡기는 것이 정당한가?**

이 질문에 답하려면 최소한 두 가지를 알아야 한다. 첫째, Cajun-Shop.com이 실제로 어느 호스팅 제공자와 계약했는가. 둘째, `securesites.com`이 그 제공자인가. **둘 다 대화상자에 없다.** 그리고 둘 다 사용자가 알아낼 방법이 없다. 알아낼 방법이 있다면 그것은 인증서 자체일 텐데, 그 인증서가 지금 의심받고 있는 대상이다.

이 책이 17.10절에서 이미 판정을 내렸다. 다시 적는다.

> **판단에 필요한 정보를 갖지 못한 주체에게 판단을 위임하는 구조다.**
>
> **결정할 수 없는 자리에 결정을 놓으면 그 결정은 형식적으로만 존재한다.**

이 판정이 이 책의 논지 — 신뢰 경계 — 위에서 정확히 어떤 뜻인지를 적어야 한다.

**검증은 신뢰 경계의 판정이다.** "이 커넥션의 반대편이 내가 의도한 상대인가"라는 질문에 예/아니오로 답하는 것이 검증의 전부다. 그 판정을 수행할 수 있는 위치에 있는 것은 클라이언트 소프트웨어다. 클라이언트는 URL의 이름을 알고, 신뢰 저장소를 알고, 서명 알고리즘을 실행할 수 있다. **사용자는 그 셋 중 어느 것도 갖고 있지 않다.**

그런데 판정 결과가 "아니오"일 때, 소프트웨어는 그 결과를 집행하는 대신 **판정 권한 자체를 사용자에게 이양한다.** 이것은 경계를 옮기는 것이다. 검증 로직 안에 있던 경계가, 대화상자의 버튼 두 개 사이로 옮겨간다. 그리고 그 버튼을 누르는 사람은 경계의 양쪽 중 어느 쪽도 볼 수 없다.

### 기저율이 클릭을 학습시킨다

구조적 결함은 여기서 끝나지 않는다. 표 18-7의 비대칭이 두 번째 결함을 만든다.

경고를 만나는 100번 중 99번은 만료된 인증서이거나 중간 인증서를 빠뜨린 사내 서버이거나 시계가 틀린 기기다. 사용자는 매번 "계속"을 누르고, 매번 아무 일도 일어나지 않는다. **사용자는 정확히 학습한다. 이 경고는 무시해도 되는 것이라고.** 그 학습은 합리적이다. 관측된 증거가 실제로 그렇게 말하기 때문이다.

그리고 100번째, 실제 공격일 때 사용자는 **같은 버튼을 같은 속도로** 누른다. 경고는 표시되었고, 판단은 위임되었고, 절차는 지켜졌다. 그러나 아무것도 막지 못했다.

세 번째 결함은 타이밍이다. **경고는 사용자가 어딘가에 가장 가고 싶은 순간에 뜬다.** 결제를 하려던 참이거나, 로그인을 하려던 참이거나, 링크를 눌러 도착한 참이다. 이 순간에 사용자에게 제시되는 선택지는 "목적을 포기한다"와 "계속한다"이고, **경고가 제공하는 정보량은 그 선택을 바꾸기에 턱없이 부족하다.**

**표 18-8. 검증 실패 처리의 세 가지 구조적 결함**

| 결함 | 형태 | 이 책에서 |
|---|---|---|
| **정보 없는 주체에게 위임** | 결정에 필요한 사실이 대화상자 안에도 사용자 손에도 없다 | 17.10 논점 2, **45장** (실패 설계) |
| **기저율이 무시를 학습시킨다** | 무해한 실패가 악의적 실패보다 몇 자릿수 흔하다 | 30장 (오류 처리) |
| **실패가 열림(fail-open)으로 설계됨** | 기본 동작이 "차단"이 아니라 "물어보고 통과 가능" | **45장**, 19.7 |

세 번째 줄이 설계의 언어로 옮긴 형태다. **검증 실패의 기본 동작이 fail-open이다.** 이것은 이 책이 반복해서 만나는 안티패턴이다. 인가 검사에 실패했을 때 통과시키는 것(→ 24장), 입력 검증에 실패했을 때 원본을 넘기는 것(→ 27장), 인증 백엔드가 죽었을 때 로그인을 허용하는 것(→ 22.6의 fail-open 로그인)과 **정확히 같은 구조**다. 다만 여기서는 실패의 순간에 사람이 끼어 있어서, 그 통과가 "사용자의 결정"이라는 이름을 얻는다.

### 같은 구조가 한 계층 아래에서 반복된다

이 절이 지금까지 다룬 것은 브라우저의 대화상자다. 그러나 **똑같은 구조가 개발자에게도 제시된다.**

TLS 라이브러리로 클라이언트를 만드는 개발자가 검증 실패를 만난다. 사내 테스트 서버의 인증서가 자체 서명이거나, CI 환경의 신뢰 저장소가 비어 있거나, 스테이징 도메인 이름이 인증서와 다르다. 개발자에게 제시되는 선택지는 두 개다. 원인을 규명하고 고치거나, **검증을 끄거나.**

```bash
curl -k https://staging.joes-hardware.com/       # --insecure
```

```python
requests.get("https://staging.joes-hardware.com/", verify=False)
```

```java
// 모든 인증서를 받아들이는 TrustManager
public void checkServerTrusted(X509Certificate[] chain, String authType) { }
```

세 줄 모두 "지금 당장 동작하게 만드는" 가장 짧은 경로다. 그리고 세 줄 모두 **표 18-6의 모든 행을 한꺼번에 무너뜨린다.** 개발자가 사용자와 다른 점은 원인을 규명할 능력이 있다는 것뿐이고, 같은 점은 **기저율이 그에게도 "이건 그냥 환경 문제"라고 가르친다**는 것이다.

그리고 결정적으로, **이 코드는 스테이징에서 프로덕션으로 그대로 간다.** 사용자의 클릭은 그 세션 하나에만 적용되지만, 개발자의 한 줄은 배포된 모든 클라이언트에 영구히 적용된다. 17.10절의 첫 번째 조건 — "클라이언트가 실제로 검증할 것" — 이 깨지는 가장 흔한 경로가 이것이다.

### 그래서 무엇을 하는가

이 절의 진단은 "사용자를 교육하라"로 이어지지 않는다. **결정할 수 없는 자리에 놓인 결정은 교육으로 고쳐지지 않는다.** 구조적 응답은 셋뿐이다.

**첫째, 결정을 다시 거둬들인다.** 사이트가 미리 "나는 항상 HTTPS이며, 내 인증서 오류는 사용자가 무시할 수 없다"고 선언해 두면, 브라우저는 경고 대화상자 대신 **차단**을 표시한다. 결정이 대화상자에서 사이트의 사전 선언으로 옮겨간다. **19.7절의 HSTS**가 정확히 이것이다.

**둘째, 무해한 실패의 기저율 자체를 낮춘다.** 표 18-7의 왼쪽 열에 있는 원인들 — 갱신 누락, 중간 인증서 미전송, 이름 불일치 — 은 전부 운영의 문제이고, 전부 자동화와 점검으로 제거할 수 있다. **경고가 드물어지면 경고가 의미를 되찾는다.** 19.11절의 체크리스트가 그 목록이다.

**셋째, 개발자 쪽의 fail-open을 코드 리뷰의 대상으로 만든다.** 18.8절이 그 검토 항목을 네 줄로 정리한다.

> **이 절이 뒷받침하는 것**
>
> - 검증 실패의 기본 동작이 fail-open이다 → **19.7** (HSTS가 결정을 거둬들이는 방식), **45장** (실패 설계 일반)
> - 무해한 원인이 압도적으로 흔하다 → **19.11** (운영 체크리스트가 기저율을 낮춘다)
> - 개발자에게도 같은 대화상자가 제시된다 → **18.8** (코드에서 그 자리를 찾는 법)
> - 폐기 확인 불가는 결론이 아니라 결론의 부재다 → **17.9** (폐기 모델의 비대칭), **19.6** (스테이플링)

## 18.5 클라이언트 인증서

SSL은 **상호 인증(mutual authentication)** 을 지원한다. 서버 인증서를 클라이언트로 나르고, 클라이언트 인증서를 서버로 나른다. 그런데 원서의 다음 문장이 이 절의 출발점이다.

> **오늘날 클라이언트 인증서는 브라우징에 흔히 쓰이지 않는다. 대부분의 사용자는 개인 클라이언트 인증서를 갖고 있지도 않다. 웹 서버가 클라이언트 인증서를 요구할 수는 있지만 실무에서 그런 일은 드물다.**

반면 **보안 HTTPS 트랜잭션은 항상 서버 인증서를 요구한다.** 웹 서버에서 신용카드 정보를 보내는 것 같은 보안 트랜잭션을 수행할 때, 사용자는 자기가 생각하는 그 조직과 대화하고 있다는 것을 알고 싶어 한다. 널리 알려진 기관이 서명한 서버 인증서가 그 판단을 돕는다.

**인증은 양방향이 가능하지만 실제 배포는 심하게 비대칭이다.** 17.7절이 "인증의 방향"이라는 제목으로 이 비대칭을 다뤘다. 이 절은 그중 쓰이지 않는 쪽 — 클라이언트 방향 — 이 프로토콜에서 어떻게 표현되고, 쓰일 때 어떤 성질을 갖는지를 본다.

### 핸드셰이크에서의 자리

표 18-2의 세 메시지가 클라이언트 인증에 쓰인다.

1. **`CertificateRequest`** (서버 → 클라이언트). `ServerHelloDone` 직전에 온다. 서버가 클라이언트 인증서를 원한다는 표시이며, **받아들일 수 있는 CA 이름의 목록**을 함께 보낸다. 클라이언트는 그 목록을 보고 자기가 가진 인증서 중 맞는 것을 고른다. 18.8절에서 볼 `openssl s_client` 출력의 `No client certificate CA names sent`가 이 메시지가 없었다는 뜻이다.
2. **`Certificate`** (클라이언트 → 서버). 클라이언트가 자기 인증서 사슬을 보낸다. 가진 것이 없으면 빈 목록을 보낸다.
3. **`CertificateVerify`** (클라이언트 → 서버). **지금까지 오간 모든 핸드셰이크 메시지에 대한 클라이언트의 서명**이다. 이것이 결정적이다. 인증서는 누구나 복사할 수 있는 공개 문서다. 인증서를 보내는 것만으로는 아무것도 증명되지 않는다. **개인키를 실제로 갖고 있다는 증명이 `CertificateVerify`다.**

서버 방향에서는 이 증명이 따로 필요 없다. 클라이언트가 사전 마스터 비밀을 서버의 공개키로 암호화해 보내고, 서버가 그것을 복호해서 만든 키로 `Finished`를 만들기 때문에 **개인키 소유가 자동으로 증명된다.** 17.10절 표 17-15의 첫 줄 — "상대가 이 공개키의 개인키를 가지고 있는가: 예" — 가 성립하는 메커니즘이 방향에 따라 다른 것이다.

### 이 인증이 갖는 성질

클라이언트 인증서 인증은 **21장이 다룰 HTTP 인증과 근본적으로 다른 자리에 있다.**

**표 18-9. HTTP 계층 인증과 TLS 계층 클라이언트 인증**

| 항목 | Basic / Digest (→ 21장) | 클라이언트 인증서 |
|---|---|---|
| 어느 계층에서 | HTTP | TLS |
| 언제 | 요청마다 (챌린지 후 매 요청에 헤더 반복) | **커넥션 수립 시 한 번** |
| 무엇이 실려 가는가 | 자격증명 자체 또는 그 다이제스트 | 인증서(공개)와 **개인키로 만든 서명** |
| 재생 가능한가 | Basic은 그대로 재생 가능 (→ 21.3) | 서명이 그 핸드셰이크에 묶여 있어 불가 |
| 신원이 붙는 대상 | **요청** | **커넥션** |
| 중간자가 TLS를 종료하면 | 헤더가 그대로 전달됨 | **소멸한다** |

다섯 번째 줄이 이 절이 이 장에 있는 이유다. **클라이언트 인증서 인증에서 신원은 요청의 속성이 아니라 커넥션의 속성이다.** 핸드셰이크가 끝나는 순간 그 커넥션에는 하나의 신원이 붙고, 그 위로 흐르는 모든 요청이 그 신원을 물려받는다.

9.10절이 "커넥션 재사용 시 무엇이 이월되는가"라는 제목으로 이 문제의 일반형을 다뤘다. **커넥션에 상태를 걸면, 그 커넥션을 재사용하는 모든 요청이 그 상태를 상속한다.** keep-alive와 다중화(→ 11장)가 커넥션의 수명을 늘릴수록 이 상속 범위는 넓어진다. 그리고 커넥션 풀이 여러 사용자를 대신해 커넥션을 공유하는 순간 — 프록시, 게이트웨이, 애플리케이션 서버의 커넥션 풀 — **그 상속은 사용자 간 신원 혼동이 된다.** 21.9절이 프록시 인증과 대리 인증에서 같은 축을 다룬다.

여기에 하나가 더 붙는다. **서버가 경로에 따라 클라이언트 인증서를 요구하고 싶다면 어떻게 하는가.** `/admin` 아래에서만 인증서를 요구하려면, 어느 경로로 요청이 왔는지를 알아야 하는데 그 정보는 HTTP 메시지 안에 있고 HTTP 메시지는 핸드셰이크가 끝나야 읽을 수 있다. 15.2절이 SNI에 대해 지적한 것과 **정확히 같은 순서 문제**다.

해법은 **재협상(renegotiation)** 이다. 이미 수립된 TLS 커넥션 위에서 새 핸드셰이크를 시작해, 이번에는 `CertificateRequest`를 붙인다. 그러나 이 해법은 구조상 문제가 있다. **요청은 이미 보내진 뒤**다. 서버가 인증서를 요구할지 결정하는 시점에 요청 라인, 헤더, 그리고 경우에 따라 본문까지 이미 서버에 도착해 있다. 신원이 확정되기 **전에** 그 신원으로만 접근 가능해야 할 리소스에 대한 요청이 파싱된 것이다. 커넥션 하나 위에서 **인증 이전 구간과 인증 이후 구간이 나뉘고, 그 경계가 애플리케이션에게 명확하게 보이지 않는다.** 13.12절이 정리한 파싱 불일치 지점 목록과 같은 성질의 이음매다.

### TLS 종료가 신원을 지운다

표 18-9의 마지막 줄이 배포에서 가장 자주 문제가 되는 자리다.

19.2절이 다룰 조기 종료, 19.8절이 다룰 기업 MITM, 11.12절이 다룬 로드밸런서에서의 TLS 종료 — 이 셋은 모두 **TLS 커넥션이 최종 서버가 아닌 곳에서 끝난다**는 공통점을 갖는다. 그 지점에서 클라이언트 인증서로 확립된 신원은 **소멸한다.** 종료 지점 뒤의 서버는 새 커넥션(또는 평문)으로 요청을 받으며, 그 커넥션에는 클라이언트의 인증서가 붙어 있지 않다.

관행적 해법은 종료 지점이 검증 결과를 **HTTP 헤더로 주입**하는 것이다.

```
X-Client-Cert-Subject: /C=US/O=Joe's Hardware/CN=warehouse-terminal-07
X-Client-Cert-Verified: SUCCESS
```

이 순간 무슨 일이 일어났는지를 정확히 적어야 한다. **암호학적으로 증명된 신원이, 평범한 텍스트 헤더로 강등되었다.** 그 헤더의 신뢰성은 이제 다음 두 가지에만 의존한다.

1. 종료 지점이 클라이언트가 보낸 동명의 헤더를 **반드시 제거**할 것.
2. 백엔드가 그 헤더를 **종료 지점에서 온 것만** 받아들일 것.

둘 중 하나라도 깨지면 누구나 자기 신원을 선언할 수 있다. 이것은 20.2절이 `X-Forwarded-For`에 대해, 15.2절이 `Host`에 대해, 13장이 프록시가 붙이는 헤더 일반에 대해 반복해 지적한 형태와 **같은 구조**다. **신뢰 경계를 넘을 때 증명이 주장으로 바뀌고, 그 주장을 검증할 방법이 헤더의 출처뿐이다.**

### 왜 널리 쓰이지 않았는가

원서의 각주 두 개가 실제 사용처를 알려준다. **일부 기업 환경의 웹 브라우징과 보안 이메일**, 그리고 **일부 조직의 인트라넷이 직원의 정보 접근을 통제하기 위해** 쓴다. HPBN이 든 예도 같다. **회사 프록시 서버가 모든 직원을 인증하며 각자 회사가 서명한 고유 인증서를 갖는다.**

공통점은 셋이다. 발급 주체와 사용 주체가 같은 조직 안에 있고, 기기의 수가 관리 가능하며, 사용자가 설치 절차를 강제받을 수 있다. **이 세 조건이 성립하지 않는 공개 웹에서 클라이언트 인증서가 실패한 이유가 그대로 이 조건들의 부정이다.**

- **키 배포 문제가 사용자에게 전가된다.** 17.4절이 공개키 암호가 푼 문제라고 적은 것 — 사전에 비밀을 공유하지 않고도 통신할 수 있다는 것 — 이 클라이언트 방향에서는 되살아난다. 사용자가 인증서를 **미리 발급받아 설치해 두어야** 한다.
- **분실 복구 절차가 없다.** 비밀번호는 잊으면 재설정한다. 개인키는 잃으면 끝이고, 재발급은 다시 신원 확인 절차 전체다(→ 22.4의 분실 자격증명 처리와 대조).
- **기기에 묶인다.** 개인키는 파일이거나 하드웨어 토큰이다. 새 기기에서 접속하려면 옮겨야 하고, 옮길 수 있으면 훔칠 수도 있다.
- **사용자 인터페이스가 없다.** 인증서 선택 대화상자는 18.4절이 비판한 것과 정확히 같은 문제를 갖는다. 여러 인증서 중 어느 것을 이 사이트에 제시할 것인지를 사용자가 판단해야 한다.

**서버 인증서는 이 문제들을 겪지 않았다.** 서버는 수가 적고, 관리자가 있고, 발급 비용을 감당할 수 있으며, 신뢰 앵커가 클라이언트에 미리 배포되어 있었기 때문이다(17.8절). **같은 기술이 방향에 따라 완전히 다른 배포 결과를 낳았고, 그 차이는 암호학이 아니라 운영에서 왔다.**

## 18.6 ALPN과 SNI — 프로토콜 협상과 가상 호스팅의 교차점

`ClientHello`에는 확장(extension) 필드가 있다. 클라이언트가 지원하는 선택적 기능을 나열하는 자리다. 이 절은 그중 두 개를 다룬다. **하나는 무엇을 말할지를 정하고(ALPN), 다른 하나는 누구에게 말하는지를 정한다(SNI).** 둘 다 이 책의 앞 장이 남긴 문제를 받는다.

### ALPN — 협상을 핸드셰이크 안으로

두 네트워크 상대가 사용자 정의 애플리케이션 프로토콜로 통신하고 싶다고 하자. 한 가지 방법은 프로토콜을 미리 정해서 잘 알려진 포트를 배정하고 모든 클라이언트와 서버를 그렇게 설정하는 것이다. **그러나 실무에서 이것은 느리고 비현실적인 과정이다.** 포트 배정마다 승인을 받아야 하고, 더 나쁘게는 **방화벽과 다른 중간자들이 대개 80번과 443번 포트로만 트래픽을 허용한다.**

그래서 사용자 정의 프로토콜을 쉽게 배포하려면 80이나 443을 재사용하고, 애플리케이션 프로토콜을 협상할 추가 메커니즘을 써야 한다. 80번은 HTTP에 예약되어 있고, HTTP 명세는 바로 이 목적을 위한 특별한 `Upgrade` 흐름을 제공한다. **그러나 `Upgrade`의 사용은 네트워크 왕복 하나를 추가할 수 있고, 실무에서는 수많은 중간자가 존재하는 환경에서 종종 신뢰할 수 없다.**

해법은 443번 포트다. **종단 간 암호화 터널을 쓰면 중간 프록시에게서 데이터가 가려지고, 새롭고 임의적인 애플리케이션 프로토콜을 빠르고 신뢰성 있게 배포할 수 있게 된다.** 그러나 TLS가 신뢰성 문제를 해결해도 **프로토콜을 협상할 방법은 여전히 필요하다.** HTTPS 세션에서 HTTP `Upgrade` 메커니즘을 재사용할 수도 있지만, 그러면 또 한 번의 완전한 왕복 지연이 생긴다. **핸드셰이크 자체의 일부로 프로토콜을 협상할 수는 없을까?**

**ALPN(Application Layer Protocol Negotiation)** 이 그것이다. 이름 그대로, 애플리케이션 프로토콜 협상을 TLS 핸드셰이크 안으로 들여오는 TLS 확장이며, `Upgrade` 워크플로가 요구하는 추가 왕복을 없앤다. 절차는 두 줄이다.

- 클라이언트가 지원하는 애플리케이션 프로토콜 목록을 담은 **`ProtocolNameList` 필드를 `ClientHello`에 붙인다.**
- 서버가 그 필드를 검사하고 **선택된 프로토콜을 가리키는 `ProtocolName` 필드를 `ServerHello`의 일부로 반환한다.**

서버는 **단 하나의 프로토콜 이름으로만 응답할 수 있으며**, 클라이언트가 요청한 것 중 지원하는 것이 하나도 없으면 커넥션을 중단하는 쪽을 택할 수 있다. 그 결과 핸드셰이크가 끝나는 순간 보안 터널이 수립되어 있고 **동시에** 어느 애플리케이션 프로토콜을 쓸지에 대한 합의도 끝나 있다. 양쪽은 즉시 통신을 시작할 수 있다.

정확히 해 둘 것이 하나 있다. **ALPN이 협상을 더 빠르게 만드는 것은 아니다.** TLS 핸드셰이크 자체는 여전히 수행해야 한다. ALPN이 보장하는 것은 **TLS 위에서의 프로토콜 협상이 암호화되지 않은 채널에서의 `Upgrade`보다 더 느려지지 않는다**는 것이다.

> **NPN과 ALPN**
>
> **NPN(Next Protocol Negotiation)** 은 구글의 SPDY 작업의 일부로 개발된 TLS 확장으로, 기능적으로 ALPN과 동등한 결과를 냈다. ALPN은 NPN을 개정해 IETF가 승인한 버전이다. 차이는 방향이다. **NPN에서는 서버가 지원 프로토콜을 광고하고 클라이언트가 골라 확정했다. ALPN에서는 이 교환이 뒤집혀, 클라이언트가 지원 프로토콜을 명시하고 서버가 고르고 확정한다.** 다른 프로토콜 협상 표준들과 정렬시키기 위한 변경이다. NPN은 폐기되었다.

11.12절이 이 확장을 HTTP/2.0의 발견 수단으로 다뤘고, 거기서 이미 결론 하나를 적었다. **ALPN 협상 결과는 `Finished`가 해시하는 범위 안에 있다**(18.2절). 그러므로 경로상의 참여자가 목록을 잘라내 능력이 낮은 프로토콜로 떨어뜨릴 수 없다. 평문 `Upgrade`에는 그 보호가 없어서, `Upgrade` 헤더를 지우거나 `101` 응답을 가로채는 것만으로 다운그레이드가 성립한다. **성능을 위해 도입된 확장이 다운그레이드 저항이라는 보안 성질을 부수 효과로 얻은 드문 사례다.**

### SNI — 이름을 핸드셰이크 안으로

암호화된 TLS 터널은 **임의의 두 TCP 상대 사이에** 수립될 수 있다. 클라이언트는 상대의 IP 주소만 알면 커넥션을 맺고 핸드셰이크를 수행할 수 있다. 그런데 서버가 **같은 IP 주소 위에 각각 자기 TLS 인증서를 가진 여러 독립 사이트를 호스팅**하고 싶다면 어떻게 되는가. 원서의 답은 짧다. **"함정 질문이다. 안 된다."**

왜 안 되는지는 15.2절과 2.9절이 이미 준비해 두었다. 이름 기반 가상 호스팅에서 **어느 사이트인지를 결정하는 것은 `Host` 헤더**다. 그리고 `Host`는 HTTP 헤더이며, HTTPS에서 HTTP 메시지는 TLS 안에 있다. 서버가 `Host`를 읽을 수 있는 시점은 **핸드셰이크가 끝난 뒤**인데, 어느 인증서를 제시할지는 **핸드셰이크 도중에** 정해야 한다.

**순서가 맞지 않는다.** 이것이 18.3절에서 본 `*.securesites.com` 사례의 근본 원인이다. 원서가 "일부 인기 있는 웹 서버 프로그램은 인증서 하나만 지원한다"고 적은 것도, "가상 호스팅된 사이트의 인증서 관리는 좀 까다로울 수 있다"고 적은 것도 이 순서 문제의 증상이다.

**SNI(Server Name Indication)** 확장이 이 문제를 푼다. **클라이언트가 접속하려는 호스트명을 핸드셰이크 시작 시점에 표시할 수 있게 한다.** 그 결과 웹 서버는 **SNI 호스트명을 검사해 적절한 인증서를 골라 핸드셰이크를 계속할 수 있다.**

원서는 이 구조를 한 문장으로 요약했다. **"TLS+SNI 워크플로는 HTTP에서의 `Host` 헤더 광고와 동일하다. 같은 IP 주소가 여러 다른 도메인을 호스팅할 수 있고, 그것들을 구별하려면 SNI와 `Host`가 모두 필요하다."**

배포상의 제약도 있었다. 상당수의 구형 클라이언트가 SNI를 지원하지 않았고, 그런 클라이언트에게 TLS를 제공해야 한다면 **호스트마다 전용 IP 주소가 필요할 수 있다.**

### 여기서 무엇이 교차하는가

15.2절이 이름 기반 가상 호스팅에 대해 내린 판정을 그대로 다시 적는다.

> **이름 기반 가상 호스팅은 목적지를 정하는 권한을 클라이언트가 보낸 문자열에 넘겼다.**

**SNI는 같은 판정을 TLS 계층에 복사한다.** 서버가 어느 인증서를 제시할지 — 즉 **어느 신원으로 자기를 증명할지** — 를 결정하는 근거가, 클라이언트가 보낸 문자열이다. 15.2절에서 그 결과는 라우팅 오분류, 서버 생성 URL의 통제, 캐시 키의 흔들림이었다. 여기서는 다른 것들이 따라 나온다.

**첫째, SNI는 평문이다.** 18.2절이 세 번째로 강조한 사실이 여기서 대가를 청구한다. `ClientHello`는 핸드셰이크의 첫 메시지이고, 그 시점에는 아직 어떤 키에도 합의하지 않았다. 그러므로 **SNI에 실린 호스트명은 그대로 회선 위에 노출된다.**

1.2절이 TLS의 보호 범위를 정리하며 세 번째 항목으로 적었다. **암호화되는 것은 TCP가 실어 나르는 페이로드이고, 출발지·목적지 IP, 포트 번호, 패킷 크기, 전송 시각은 그대로 노출된다.** 이 목록에 한 줄을 더해야 한다. **그리고 `ClientHello`에 실린 호스트명도 노출된다.**

차이는 작지 않다. IP 주소만 노출될 때, 하나의 IP 뒤에 수천 개의 사이트가 있는 공유 호스팅이나 CDN에서는 관찰자가 어느 사이트인지를 알 수 없다. **SNI는 그 모호성을 없앤다.** 관찰자는 암호문의 내용은 읽지 못하지만 **어느 사이트와 대화하는지는 정확히 안다.** 그리고 이것은 관찰만의 문제가 아니다. **SNI 값은 경로상의 장비가 판정에 쓸 수 있는 선택자(selector)가 된다.** 특정 이름으로 가는 커넥션만 골라 리셋하거나 다른 곳으로 돌리는 것이 가능하고, 그 판정에 복호는 필요하지 않다.

**둘째, 같은 이름이 두 곳에 실린다.** 15.2절이 이 지점을 예고하며 적었다. **"프로토콜상 둘이 같아야 할 이유는 없다."**

**표 18-10. 하나의 HTTPS 요청에서 이름이 실리는 네 자리**

| 자리 | 계층 | 암호화 | 누가 읽는가 | 무엇을 결정하는가 |
|---|---|---|---|---|
| DNS 질의의 이름 | DNS | **아니오** | 리졸버, 경로상의 모두 | 어느 IP로 갈 것인가 (→ 2.7) |
| **SNI** (`ClientHello` 확장) | TLS | **아니오** | 서버, 경로상의 모두 | **어느 인증서를 제시할 것인가** |
| 인증서의 SAN·CN | TLS | 아니오 (평문으로 전달됨) | 클라이언트가 검증 | **이름 일치 판정의 왼쪽**(→ 18.3) |
| `Host` 헤더 | HTTP | **예** | 서버 (TLS 종료 지점 이후) | **어느 가상 호스트가 응답할 것인가**(→ 15.2) |

네 줄 중 **세 줄이 평문**이고, 넷 중 **어느 둘도 서로를 검증하지 않는다.** 클라이언트가 검증하는 것은 세 번째 줄과, 자기가 URL에서 얻은 이름이다(18.3절 단계 3). SNI가 그 이름과 같은지는 클라이언트가 스스로 보낸 값이므로 문제가 되지 않는다. **문제는 두 번째 줄과 네 번째 줄 사이다.**

시나리오는 이렇다. 클라이언트가 SNI에 `a.joes-hardware.com`을 실어 핸드셰이크한다. 서버가 그 이름의 인증서를 제시하고, 클라이언트가 검증에 성공한다. 터널이 열린다. 그리고 그 터널 위로 클라이언트가 `Host: b.joes-hardware.com`인 요청을 보낸다. **이 요청을 서버는 어떻게 처리해야 하는가.**

프로토콜은 답을 주지 않는다. 답은 배포가 정한다. 그리고 두 가지 배포가 다르게 답한다.

- **엣지가 SNI로 라우팅하고 오리진이 `Host`로 라우팅하는 구성**에서는, 커넥션이 `a`의 백엔드로 갔는데 요청은 `b`용으로 처리될 수 있다. 13.12절이 정리한 파싱 불일치 지점 목록에 정확히 들어맞는 형태다. **하나의 요청에 대해 두 참여자가 서로 다른 목적지를 판정한다.**
- **커넥션을 재사용하는 구성**에서는 더 나아간다. 인증서가 여러 이름에 대해 유효하면(와일드카드나 다중 SAN), 클라이언트는 **하나의 커넥션 위에서 그 인증서가 권한을 갖는 모든 이름에 요청을 보내는 것이 정당하다고 판단할 수 있다.** 11장이 커넥션 병합(coalescing)을 다루며 이 지점을 짚었다. **인증서가 넓게 발급될수록 하나의 커넥션이 권한을 갖는 이름의 집합이 넓어진다.**

두 경우 모두에서 답해야 할 질문은 하나로 압축된다. **이 커넥션은 어느 이름의 집합에 대해 권한을 갖는가.** 그 집합을 정의하는 것은 SNI가 아니라 **제시된 인증서**다. 그리고 그 집합의 크기는 인증서를 발급받을 때의 편의 판단 — 와일드카드 하나로 묶을 것인가 — 이 정한다. **운영 편의를 위해 넓힌 이름 경계가 신뢰 경계가 된다.**

**셋째, ALPN과 SNI가 같은 자리에 있다.** 둘 다 `ClientHello`의 확장이다. 그러므로 둘 다 평문이고, 둘 다 `Finished`의 해시 범위 안에 있다. **다운그레이드는 막히지만 관찰은 막히지 않는다.** 무결성과 기밀성이 서로 다른 문제라는 17.7절의 명제가, 확장 필드 하나에서 동시에 확인되는 자리다.

그리고 배포 쪽에서 둘은 같은 질문을 만든다. 11.12절이 마지막에 던진 두 질문이 그것이다. **인프라의 어느 구성 요소가 TLS 커넥션을 종료하는가. 그 구성 요소가 필요한 협상을 수행할 수 있는가.** SNI를 읽어 인증서를 고르는 것도, ALPN을 읽어 프로토콜을 정하는 것도, **TLS를 종료하는 그 지점**의 일이다. 19.2절의 조기 종료와 19.8절의 기업 MITM이 같은 축 위에 있는 이유다.

> **이 절이 뒷받침하는 것**
>
> - SNI가 인증서 선택의 근거를 클라이언트가 보낸 값으로 만든다 → **15.2** (같은 판정의 HTTP 계층 버전), **2.9** (호스트명 기반 가상 호스팅의 전제)
> - SNI는 평문이다 → **1.2** (TLS가 가리지 않는 것의 목록에 한 줄 추가), **19.9** (중간자 성립 조건의 재검토)
> - SNI와 `Host`가 다를 수 있다 → **13.12** (파싱 불일치 지점), **11장** (커넥션 병합과 인증서의 이름 집합)
> - ALPN 결과가 핸드셰이크 무결성 안에 있다 → **11.12** (h2c와의 대조), **19.7** (프로토콜 다운그레이드와 스킴 다운그레이드는 다른 문제다)

## 18.7 TLS 레코드 프로토콜 — 레코드와 TCP 세그먼트의 관계

**그 아래의 IP나 TCP 계층과 마찬가지로, TLS 세션 안에서 교환되는 모든 데이터도 잘 정의된 프로토콜로 프레이밍된다.** TLS 레코드 프로토콜이 담당하는 것은 두 가지다. **`Content Type` 필드로 서로 다른 종류의 메시지(핸드셰이크, 알림, 데이터)를 식별하는 것, 그리고 각 메시지의 무결성을 보장하고 검증하는 것.**

### 레코드의 구조와 처리 흐름

```
 ┌──────────┬──────────┬──────────┬─────────────────────────────┐
 │  Type    │ Version  │  Length  │        Payload              │
 │  1 byte  │ 2 bytes  │ 2 bytes  │   ≤ 2^14 (16,384) bytes     │
 └──────────┴──────────┴──────────┴─────────────────────────────┘
   ↑ 22=handshake                      ↑ 압축(선택) → MAC 부착 → 암호화
     21=alert
     20=change_cipher_spec
     23=application_data
```

*그림 18-4. TLS 레코드의 구조 (HPBN 그림 4-8 기준)*

애플리케이션 데이터를 전달하는 전형적인 흐름은 다섯 단계다.

1. 레코드 프로토콜이 애플리케이션 데이터를 받는다.
2. 받은 데이터를 블록으로 나눈다. **레코드당 최대 2¹⁴ 바이트, 즉 16 KB.**
3. 애플리케이션 데이터를 **선택적으로 압축**한다.
4. **MAC 또는 HMAC를 붙인다.**
5. 협상된 암호로 **데이터를 암호화한다.**

이 단계들이 끝나면 암호화된 데이터가 전송을 위해 TCP 계층으로 내려간다. 수신 측에서는 같은 흐름이 역순으로 적용된다. 협상된 암호로 복호하고, MAC을 검증하고, 데이터를 추출해 위의 애플리케이션에 전달한다.

세 번째 단계를 지금은 그냥 지나간다. **압축이 왜 실무에서 꺼져 있는지는 19.5절이 다룬다.** 여기서는 그 자리가 레코드 계층에 있다는 것만 확인한다.

네 번째와 다섯 번째 단계의 **순서**는 기억해 둘 값이 있다. MAC을 먼저 붙이고 그 결과를 암호화한다. 17.5절이 MAC을 "단방향 암호학적 해시 함수이며 그 키는 두 통신 상대가 협상한다"고 적었고, 17.7절이 무결성과 기밀성이 서로 다른 문제라고 적었다. **레코드 계층은 그 둘을 이 순서로 조합한다.**

원서가 정리한 세 가지 함의는 다음과 같다.

- **최대 TLS 레코드 크기는 16 KB다.**
- **각 레코드는 5바이트 헤더, MAC(SSLv3·TLS 1.0·TLS 1.1에서 최대 20바이트, TLS 1.2에서 최대 32바이트), 그리고 블록 암호를 쓸 경우 패딩을 포함한다.**
- **레코드를 복호하고 검증하려면 레코드 전체가 확보되어야 한다.**

세 번째가 이 절의 핵심이다.

### 레코드와 세그먼트는 정렬되지 않는다

1.3.2절이 TCP 세그먼트와 MSS를 다뤘고, 3.1절이 TCP가 약속하는 것과 약속하지 않는 것을 정리했다. 그 두 절이 반복해서 적은 사실 하나가 여기서 다시 필요하다. **TCP는 바이트 스트림을 전달한다. 그 스트림 안에서 "메시지 하나"가 어디서 끝나는지는 TCP의 관심사가 아니다.**

TLS는 그 스트림 위에 자기 프레이밍을 다시 세운다. 그리고 **그 프레임의 경계는 아래 계층의 어떤 경계와도 정렬되지 않는다.**

```
TLS 레코드 (16 KB)
├────────────────────────────────────────────────────────────┤

TCP 세그먼트 (MSS = 1,460 바이트)
├──────┤──────┤──────┤──────┤──────┤──────┤──────┤──────┤──... (약 12개)
   ↑ 여기까지 도착해도 애플리케이션은 아무것도 받지 못한다
                                                    ↑ 마지막 세그먼트가
                                                      도착해야 복호가 시작된다
```

*그림 18-5. 16 KB 레코드 하나와 MSS 크기 세그먼트의 관계*

**하나의 레코드가 여러 세그먼트에 걸쳐 있을 수 있고, 하나의 세그먼트가 여러 레코드를 담거나 한 레코드의 조각만 담을 수 있다.** 이 관계는 1.3.2절이 "HTTP 메시지 하나와 TCP 세그먼트 하나가 대응하지 않는다"고 적은 것과 **완전히 같은 구조**다. 다만 이번에는 그 어긋남이 성능과 지연에 직접 청구된다.

**16 KB 레코드 하나는 MSS 1,460바이트 기준으로 약 12개의 세그먼트를 요구한다.** 그 12개가 모두 도착하기 전까지 TLS 계층은 복호를 시작할 수 없고, 따라서 **애플리케이션은 단 한 바이트도 받지 못한다.** 첫 세그먼트가 도착한 시점과 애플리케이션이 첫 바이트를 얻는 시점 사이에 11개 세그먼트만큼의 지연이 끼어든다. 그리고 그 12개의 세그먼트는 3.4절의 혼잡 윈도우 아래에 있으므로, 새 커넥션에서는 여러 왕복에 나뉘어 도착할 수도 있다.

반대 방향의 문제도 있다. **작은 레코드는 프레이밍 때문에 상대적으로 큰 오버헤드를 발생시킨다.** 레코드마다 5바이트 헤더와 최대 32바이트 MAC과 패딩이 붙는다. 1바이트를 담은 레코드가 40바이트 가까이 될 수 있다.

원서의 결론은 그래서 균형의 문제다. **애플리케이션에 맞는 레코드 크기를 고를 수 있다면, 그것을 고르는 일이 중요한 최적화가 될 수 있다. 작은 레코드는 레코드 프레이밍 때문에 오버헤드가 크고, 큰 레코드는 TLS 계층이 처리해 애플리케이션에 전달하기 전에 TCP 계층이 먼저 전달하고 재조립해야 한다.**

**19.4절이 이 균형을 정면으로 다룬다.** 여기서는 그것이 왜 균형인지를 확인하는 데서 멈춘다.

### 레코드 계층이 남기는 것과 지우는 것

이 계층이 보안에서 갖는 함의는 셋이다.

**첫째, 레코드 헤더는 암호화되지 않는다.** 타입, 버전, 길이 세 필드는 평문이다. 그럴 수밖에 없다. 길이를 모르면 어디까지가 한 레코드인지 알 수 없고, 레코드를 확보하지 못하면 복호할 수 없다. **경계를 알아야 복호할 수 있고, 경계는 복호 이전에 읽혀야 한다.**

결과적으로 경로상의 관찰자는 다음을 안다. 레코드가 몇 개인지, 각각이 얼마나 큰지, 그리고 각각이 **핸드셰이크인지 알림인지 애플리케이션 데이터인지**. 1.2절의 목록 — TLS는 크기와 타이밍을 가리지 않는다 — 이 레코드 단위의 해상도로 확인되는 자리다. 18.6절이 SNI에 대해 지적한 것과 합치면, **관찰자가 얻는 것은 "누가 어느 사이트와 언제 얼마나"** 가 된다.

**둘째, 알림 프로토콜과 종료의 무결성.** 타입 21의 알림 레코드 중 하나가 `close_notify`다. 18.1절에서 그림 18-1의 5단계로 표시한 것이 이것이다.

이 메시지의 존재 이유는 9.9절이 제기한 문제에 있다. **평문 HTTP에서 커넥션이 끊겼을 때, 응답이 완결된 것인지 잘린 것인지를 구별할 수단은 `Content-Length`나 청크 종결자 같은 HTTP 계층의 표시뿐이다.** 그리고 커넥션 종료로 본문의 끝을 표시하는 경우(→ 10.4), 그 구별은 아예 불가능하다.

`close_notify`는 **TLS 계층에서 그 구별을 가능하게 한다.** 이 알림 없이 TCP FIN이 오면, TLS는 스트림이 예정에 없이 잘렸다는 것을 안다. 그러므로 **`close_notify` 없는 종료를 정상 종료로 취급하는 구현은 이 보호를 스스로 버린다.** 경로상의 참여자가 TCP FIN이나 RST를 주입하는 것만으로 응답을 임의의 지점에서 자를 수 있고, 애플리케이션은 잘린 응답을 완전한 응답으로 받는다.

이것은 이 책이 여러 번 만난 형태의 또 다른 사례다. **경계를 표시하는 수단이 여러 계층에 있고, 상위 계층이 하위 계층의 표시를 신뢰하거나 무시하는 방식에서 불일치가 생긴다.** 10.4절의 `Content-Length`와 `Transfer-Encoding`, 13.12절의 파싱 불일치 목록, 그리고 여기의 `close_notify`가 같은 목록에 속한다.

**셋째, 레코드는 순서와 재생을 함께 막는다.** MAC 계산에는 레코드의 일련번호가 포함된다. 이 번호는 회선에 실리지 않고 양쪽이 각자 센다. 그 결과 **레코드를 재정렬하거나, 삭제하거나, 이전 레코드를 다시 보내면 MAC이 맞지 않는다.** 21장이 Digest 인증에서 재생 방지를 위해 nonce와 nc를 도입하며 겪는 문제 — 상태를 어디에 두고 누가 세는가 — 를 레코드 계층은 커넥션 상태로 해결한다. 그리고 그 대가로 **이 보호는 커넥션 하나 안에서만 성립한다.**

> **이 절이 뒷받침하는 것**
>
> - 레코드는 최대 16 KB이고, 전체가 있어야 복호된다 → **19.4** (레코드 크기와 버퍼링 지연), **1.3.2** (MSS), **3.4** (혼잡 윈도우 아래에서의 도착)
> - 압축이 레코드 계층에 있다 → **19.5** (왜 끄는가)
> - 레코드 헤더는 평문이다 → **1.2** (TLS가 가리지 않는 것), **18.6** (SNI와 합쳐질 때의 관찰 해상도)
> - `close_notify`가 절단을 탐지한다 → **9.9** (커넥션 종료의 모호함), **10.4** (본문 경계 표시)

## 18.8 실전 HTTPS 클라이언트 구현 읽기

5.11절이 "최소 구현으로 확인하기"라는 제목으로 손으로 쓴 HTTP 클라이언트를 다뤘다. 그 절의 마지막 부분은 `openssl s_client`와 `curl -v`로 TLS 계층을 들여다보는 방법을 소개했지만, **그 도구들이 무엇을 대신해 주고 있는지는 열지 않았다.** 이 절이 그것을 연다.

### 3페이지짜리 HTTPS 클라이언트

원서가 제시한 OpenSSL 기반 HTTPS 클라이언트는 아홉 개의 구간으로 나뉜다. **오류 처리와 인증서 처리 로직이 제거되어 있으므로 설명용으로만 봐야 한다**는 것이 원서의 경고다. 각 구간이 이 장의 어느 절에 대응하는지를 붙여 보자.

**표 18-11. OpenSSL HTTPS 클라이언트의 아홉 구간 (HTTP-DG 14장의 예제 프로그램)**

| 구간 | 호출 | 하는 일 | 이 책의 절 |
|---|---|---|---|
| (1) | `SSL_CTX_new` | **핸드셰이크 파라미터와 커넥션 상태를 추적할 로컬 컨텍스트 생성** | 18.2 |
| (2) | `gethostbyname` | 호스트명을 IP 주소로 변환 | 2.7 |
| (3) | `socket`, `connect` | **443번 포트로 TCP 커넥션 수립** | 3.2, 18.1 |
| (4) | `SSL_new`, `SSL_set_fd`, `SSL_connect` | TCP 커넥션에 SSL 계층을 붙이고 **핸드셰이크 수행** | **18.2** |
| (5) | `SSL_get_cipher` | 선택된 대량 암호화 암호를 출력 | 17.3 |
| (6) | `SSL_get_peer_certificate`, `X509_get_subject_name` | 서버 인증서의 주체와 발급자를 출력 | 17.6 |
| (7) | `SSL_write` | 암호화된 채널로 HTTP 요청 전송 | 18.7, 5.5 |
| (8) | `SSL_read` | 응답을 읽어 화면에 출력 | 18.7 |
| (9) | `SSL_shutdown`, `close` | 정리 | 18.1 (그림 18-1의 5·6단계) |

원서의 평가 두 개가 이 표를 읽는 방법을 알려준다.

> **암호화와 키와 인증서 관리를 전부 포함해 이 프로그램 전체가 3페이지짜리 C 프로그램 안에 들어간다.**
>
> **SSL 계층이 모든 암호화와 복호를 처리해 주므로, 우리는 그냥 평범한 HTTP 명령을 쓰고 읽으면 된다.**

17.1절이 인용한 원서의 문장 — **"대체로 TCP 입출력 호출을 SSL 호출로 교체하고 보안 정보를 설정·관리하는 호출 몇 개를 추가하면 된다"** — 이 표 18-11에서 문자 그대로 확인된다. `write`가 `SSL_write`가 되고 `read`가 `SSL_read`가 된다. 나머지는 같다.

그리고 여기에 1.1절이 계층화에 대해 적은 것이 그대로 나타난다. **추상화는 비용을 숨긴다.** 표 18-3의 여섯 줄, 168밀리초, 두 번의 왕복이 **`SSL_connect(ssl)` 한 줄**이다. 코드를 봐서는 그 비용이 보이지 않는다.

### 이 프로그램의 6번 구간에 있는 주석

원서의 코드에서 가장 중요한 한 줄은 실행되는 코드가 아니라 주석이다.

```c
server_cert = SSL_get_peer_certificate(ssl);

str = X509_NAME_oneline(X509_get_subject_name(server_cert), 0, 0);
printf("      subject: %s\n", str);

str = X509_NAME_oneline(X509_get_issuer_name(server_cert), 0, 0);
printf("      issuer: %s\n\n", str);

/* certificate verification would happen here */

X509_free(server_cert);
```

*예제 18-1. 인증서 검증이 있어야 할 자리 (HTTP-DG 14장의 예제 프로그램에서 발췌)*

**"인증서 검증은 여기서 일어날 것이다."** 원서 자신이 이 자리에 대해 설명을 붙였다. **OpenSSL 라이브러리는 서버 인증서의 정보로 특별한 일을 하지 않는다. 웹 브라우저 같은 실제 SSL 애플리케이션이라면 인증서가 제대로 서명되었고 올바른 호스트에서 왔는지를 검사할 것이다.**

18.3절이 인용한 문장 — **"SSL 자체는 웹 서버 인증서를 검사하도록 요구하지 않는다"** — 이 코드에서 갖는 형태가 이것이다. **라이브러리는 재료를 건네주고, 판정은 애플리케이션의 몫이며, 아무것도 쓰지 않았을 때의 기본 동작은 "전부 받아들임"이다.**

17.10절이 나열한 첫 번째 조건이 깨지는 지점의 **정확한 좌표**가 이 주석이다. 그리고 이 프로그램은 그것을 감추지 않았다. 실무의 코드가 위험한 것은 대개 이 주석이 없기 때문이다. 검증이 없다는 사실이 **코드에 흔적을 남기지 않는다.** 없는 것은 보이지 않는다.

이 구조가 낳은 결과는 역사적이다. **오랫동안 호스트명 검사는 TLS 라이브러리가 해 주지 않았다.** 사슬 검증은 라이브러리가 하지만, "이 인증서의 이름이 내가 접속하려던 이름과 같은가"는 애플리케이션이 직접 비교해야 했다. 브라우저는 그것을 했다. **브라우저가 아닌 수많은 HTTPS 클라이언트 — 결제 SDK, 모바일 앱, 서버 간 API 호출 라이브러리 — 는 하지 않았다.** 18.3절 표 18-6의 세 번째 줄, "사슬 검증은 하면서 이름 검사를 빼먹는 구현"이 압도적으로 흔한 오류 형태인 이유가 여기에 있다.

현대 OpenSSL에는 이 검사를 라이브러리에 맡기는 API가 있다.

```c
/* (1) 신뢰 저장소를 설정한다 — 없으면 사슬을 검증할 앵커가 없다 */
SSL_CTX_set_default_verify_paths(ctx);
SSL_CTX_set_verify(ctx, SSL_VERIFY_PEER, NULL);

/* (2) 검증할 호스트명을 명시한다 — 이것이 18.3절 단계 3이다 */
SSL_set1_host(ssl, hostname);

/* (3) SNI를 보낸다 — 이것이 18.6절이다 */
SSL_set_tlsext_host_name(ssl, hostname);

err = SSL_connect(ssl);

/* (4) 검증 결과를 실제로 읽는다 */
if (SSL_get_verify_result(ssl) != X509_V_OK) { /* 커넥션을 닫는다 */ }
```

*예제 18-2. 예제 18-1의 주석 자리를 채우는 네 가지*

네 항목이 이 장의 네 절에 하나씩 대응한다. 그리고 이 네 줄이 **어떤 TLS 클라이언트 코드를 읽을 때든 찾아야 할 것의 목록**이 된다.

**표 18-12. TLS 클라이언트 코드 검토 항목**

| 확인할 것 | 없으면 무엇이 무너지는가 | 표 18-6의 행 |
|---|---|---|
| 1. **신뢰 저장소가 설정되는가** | 사슬을 검증할 앵커가 없다 | 1행 |
| 2. **검증 모드가 켜져 있는가** | 검증 자체가 수행되지 않는다 | 전부 |
| 3. **호스트명이 비교되는가** | 아무 유효한 인증서나 통과한다 | **3행** |
| 4. **검증 실패 시 커넥션이 닫히는가** | 결과가 계산되고 무시된다 | 전부 |

네 번째 항목이 18.4절과 이어진다. **검증은 수행되었지만 그 결과가 예외 처리로 삼켜지거나 로그로만 남는 코드**가 실무에 존재한다. 17.10절 표 17-16의 첫 행에 "예외 처리로 삼켜지는 검증 실패"가 적혀 있는 이유다.

같은 네 항목을 다른 언어에서 확인하면 이렇게 된다.

```python
import ssl, socket

# 안전한 기본값: 신뢰 저장소·검증 모드·호스트명 검사가 모두 켜져 있다
ctx = ssl.create_default_context()          # 항목 1, 2
ctx.check_hostname = True                    # 항목 3 (기본값 True)
ctx.verify_mode = ssl.CERT_REQUIRED          # 항목 2 (기본값)

with socket.create_connection(("www.joes-hardware.com", 443)) as sock:
    # server_hostname 인자가 SNI이자 호스트명 검증의 기준점이다 (18.6, 18.3)
    with ctx.wrap_socket(sock, server_hostname="www.joes-hardware.com") as tls:
        print(tls.version())                 # 협상된 프로토콜 버전
        print(tls.cipher())                  # 협상된 암호 스위트 (18.2)
        print(tls.getpeercert()["subject"])  # 인증서 주체 (17.6)
        tls.sendall(b"GET / HTTP/1.1\r\nHost: www.joes-hardware.com\r\n"
                    b"Connection: close\r\n\r\n")
        print(tls.recv(4096).decode(errors="replace"))
```

*예제 18-3. 네 항목이 모두 켜진 최소 HTTPS 클라이언트*

`server_hostname` 인자 하나가 두 가지 일을 한다는 점을 봐야 한다. **그 값이 SNI로 나가고, 동시에 인증서 이름 일치 판정의 기준점이 된다.** 18.3절이 "비교의 오른쪽은 클라이언트가 접속하려고 의도한 이름"이라고 적은 것이 API에서 이 형태를 갖는다. **의도한 이름이 하나의 변수에서 나오므로, SNI와 검증 기준이 어긋날 수 없다.**

그리고 이 코드에서 `ctx.check_hostname = False`로 바꾸거나 `verify_mode = ssl.CERT_NONE`으로 바꾸는 것이 18.4절이 말한 개발자용 대화상자다. **한 줄이고, 즉시 동작하며, 배포에 그대로 실려 간다.**

**둘째, `Certificate chain`의 항목 수.** 서버가 중간 인증서를 보내지 않으면 여기에 `0`번 항목만 나온다. 18.4절이 "서버 설정 실수 중 최다"라고 적은 증상을 진단하는 자리다. 브라우저에서는 잘 되는데 다른 클라이언트에서 실패하는 사이트라면 먼저 이 줄을 본다.

**셋째, `SSL handshake has read ... bytes`.** 사슬 전체가 몇 바이트인지다. 여기서는 3,571바이트인데, **이것은 초기 TCP 혼잡 윈도우 3~4세그먼트 크기에 매우 가깝다.** 원서의 조언은 명확하다. **그것을 넘치게 하지 않도록 조심하거나, 서버의 `cwnd` 크기를 올려야 한다.** 18.2절이 예고하고 19.6절이 받는다.

**넷째, `-CAfile`의 존재 자체.** 원서가 강조한 대로, **`s_client`는 알려진 루트 인증서에 대해 아무 가정도 하지 않으므로 루트 인증서 경로를 수동으로 지정해야 한다. 이것이 중요하다. 브라우저는 이미 그 루트 인증서를 갖고 있어서 사슬을 검증할 수 있지만, `s_client`는 그런 가정을 하지 않는다. 루트 인증서를 빼고 실행해 보면 로그에서 검증 오류를 보게 된다.**

이 한 문단이 17.10절의 두 번째 조건 — "신뢰 저장소가 오염되지 않았을 것" — 의 앞면이다. **신뢰 저장소는 주어진 것이 아니라 설정이다.** 브라우저에서는 벤더가 채워 두었고, `s_client`에서는 비어 있으며, 사내 기기에서는 관리자가 추가한 루트가 들어 있을 수 있다(→ 19.8). **같은 인증서가 어느 저장소를 기준으로 검증되느냐에 따라 유효하기도 하고 아니기도 하다.**

## 이 장의 요약

- **HTTPS는 새 애플리케이션 프로토콜이 아니라 계층 하나가 끼워진 HTTP다.** `https` 스킴이 기본 포트를 443으로 바꾸고 핸드셰이크를 요구할 뿐, HTTP 메시지 문법은 동일하다. 포트를 분리한 이유는 SSL이 HTTP와 완전히 다른 바이너리 프로토콜이어서 같은 포트로 오면 서버가 잘못된 HTTP로 해석하고 끊기 때문이다. **그리고 TLS를 쓸지 말지는 URL 문자열 하나가 정하며, 그 문자열은 아직 인증된 채널로 오지 않았다.**

- **전체 핸드셰이크는 TCP 1왕복 위에 TLS 2왕복을 얹는다.** 뉴욕–런던 56밀리초 기준으로 첫 HTTP 바이트가 나가기까지 168밀리초다. 이 비용은 대역폭과 무관하며 새 커넥션마다 발생한다. 핸드셰이크가 하는 일은 넷 — 버전 교환, 암호 선택, 신원 인증, 세션 키 생성 — 이고, 공개키 연산은 그중 세션 키 합의에서 **단 한 번** 쓰인다.

- **`ClientKeyExchange` 이전의 모든 메시지는 평문이다.** 버전, 암호 스위트 목록, 서버 인증서 전체, `ClientHello`의 모든 확장이 그렇다. 반면 `Finished`가 그때까지의 모든 핸드셰이크 메시지를 해시하므로 **협상 내용은 무결성 보호를 받는다.** 노출은 되지만 조작은 안 된다.

- **SSL 자체는 인증서를 검사하도록 요구하지 않는다. 검증은 클라이언트의 정책이다.** 실제 클라이언트는 다섯 가지를 확인한다. 사슬 구성과 서명, 유효 기간, 이름 일치, 폐기, 용도 제약. 다섯은 AND로 묶이고, 이름 일치는 **인증서 안의 SAN(없으면 CN)과 URL의 호스트명** 사이의 규칙 있는 문자열 비교다. 와일드카드는 최좌측 레이블 하나에만 대응하며 빈 레이블에는 대응하지 않는다.

- **사슬은 검증하면서 이름을 검사하지 않는 구현이 가장 흔하고 가장 위험하다.** 그 상태에서 공격자는 CA를 공격할 필요도 자체 서명 인증서를 만들 필요도 없다. **자기가 정당하게 소유한 도메인의 완벽하게 정상적인 인증서**를 제시하면 된다. 17.10절이 계산한 공격 조건의 상승분이 정확히 0이 된다.

- **검증 실패 처리에는 세 가지 구조적 결함이 있다.** 판단에 필요한 정보를 갖지 못한 주체에게 결정을 위임하고, 무해한 실패가 악의적 실패보다 몇 자릿수 흔해서 무시를 학습시키며, 실패의 기본 동작이 fail-open이다. **경고 대화상자는 신뢰 경계의 판정을 그 경계의 양쪽을 볼 수 없는 주체에게 옮긴다.** 그리고 같은 구조가 한 계층 아래에서 `curl -k`와 `verify=False`로 개발자에게 반복된다.

- **클라이언트 인증서에서 신원은 요청이 아니라 커넥션의 속성이다.** `CertificateVerify`가 개인키 소유를 증명하고, 그 신원이 커넥션 위의 모든 요청에 상속된다. TLS가 최종 서버가 아닌 곳에서 종료되면 그 신원은 소멸하고, 관행적으로 헤더로 재주입되면서 **암호학적 증명이 평범한 텍스트 주장으로 강등된다.**

- **SNI는 15.2절의 판정을 TLS 계층에 복사한다.** 어느 인증서로 자기를 증명할지를 클라이언트가 보낸 문자열이 결정한다. 그리고 그 문자열은 평문이다. **TLS가 가리지 않는 것의 목록 — IP, 포트, 크기, 타이밍 — 에 호스트명이 추가된다.** 같은 이름이 SNI와 `Host` 두 곳에 실리고 프로토콜은 둘이 같아야 한다고 요구하지 않으므로, 커넥션이 권한을 갖는 이름의 집합을 정의하는 것은 결국 **제시된 인증서의 범위**다.

- **TLS 레코드는 최대 16 KB이고 전체가 확보되어야 복호된다.** 레코드 경계는 TCP 세그먼트 경계와 정렬되지 않으며, 16 KB 레코드 하나는 MSS 기준 약 12개 세그먼트를 요구한다. 작은 레코드는 프레이밍 오버헤드가 크고 큰 레코드는 버퍼링 지연이 크다. **레코드 헤더는 평문이므로 관찰자는 레코드의 개수·크기·종류를 안다.**

## 이어지는 장

이 장은 순서를 열었고 검증을 펼쳤다. 남은 것은 **비용과 배포**다.

표 18-3은 이 장이 19장에 넘기는 청구서다. **TCP 1왕복 + TLS 2왕복, 그리고 새 커넥션마다.** 19.1절과 19.3절이 두 번째 왕복을 없앤다. 이미 협상한 비밀 키를 세션 ID나 세션 티켓으로 기억해 두면 축약 핸드셰이크가 성립한다. 이 장이 표 18-2에서 `ClientKeyExchange`가 하는 일을 적었고, 재개란 **그 메시지를 다시 만들지 않아도 되게 하는 것**이다. 그리고 그것을 어디에 기억할 것인가 — 서버의 메모리인가, 클라이언트가 들고 다니는 티켓인가 — 가 상태를 어디에 두는가라는 이 책의 반복 질문(→ 20장, 23장)의 또 다른 사례가 된다.

19.2절은 왕복 자체를 짧게 만든다. 이 장이 계산한 168밀리초는 거리의 함수이므로, 서버를 사용자 가까이 두면 왕복 횟수를 줄이지 않고도 총 시간이 줄어든다. 11.12절이 남긴 두 질문 — 어느 구성 요소가 TLS를 종료하는가, 그 구성 요소가 협상을 수행할 수 있는가 — 이 여기서 성능의 언어로 다시 나온다. 그리고 **그 답이 곧 신뢰 경계가 어디에 그어지는지의 답**이라는 것을 18.5절과 18.6절이 이미 보여주었다.

19.4절이 18.7절을 직접 받는다. 레코드 크기가 지연과 오버헤드 사이의 균형이라는 것을 이 장이 확인했고, 그 균형을 실제 값으로 어떻게 잡는지가 그곳의 주제다. 19.5절이 레코드 계층의 압축 단계로 돌아와 **왜 그 단계를 끄는지**를 설명한다. 19.6절이 표 18-3의 84밀리초 줄 — 서버가 인증서를 붙여 보내는 줄 — 을 바이트로 계산하고, 17.9절이 남긴 폐기 문제를 스테이플링으로 이어받는다.

**그리고 19.7절이 18.4절을 정면으로 받는다.** 이 장은 경고 대화상자가 결정할 수 없는 자리에 놓인 결정이라고 판정했다. HSTS는 그 결정을 **대화상자에서 사이트의 사전 선언으로 옮기는** 처방이다. 사이트가 미리 "나는 항상 HTTPS이며 내 인증서 오류는 무시할 수 없다"고 선언해 두면, 브라우저는 물어보는 대신 차단한다. 동시에 18.1절이 남긴 문제 — TLS 사용 여부가 URL 문자열로 정해진다는 것 — 에도 답한다. 그 처방이 무엇을 해결하고 무엇을 남기는지, 특히 **선언을 처음 받기 전의 창**이 왜 남는지가 그곳의 주제다.

19.8절이 17.10절의 두 번째 조건을 실물로 만난다. 이 장이 18.8절에서 `-CAfile`을 두고 "신뢰 저장소는 주어진 것이 아니라 설정이다"라고 적었다. 기업 네트워크의 TLS 검사 장비가 하는 일이 그 설정을 바꾸는 것이며, **의도된 중간자와 공격자가 기술적으로 같은 위치에 있다**는 1.8절의 관찰이 그곳에서 구체적인 배포 형태를 얻는다.

**19.9절이 Part IV를 닫는다.** 표 1-7의 세 줄 — 관찰, 위조, 개입 — 을 TLS가 켜진 상태에서 다시 쓴다. 그때 이 장이 제공한 항목들이 하나씩 필요하다. 무엇이 평문으로 남는가(18.2, 18.6, 18.7). 검증이 실제로 수행되는가(18.3). 실패했을 때 무엇이 일어나는가(18.4). 그리고 관찰자가 SNI와 레코드 크기와 타이밍만으로 무엇을 알 수 있는가.

SSL과 HTTP 트래픽이 모두 80번 포트로 도착한다면 대부분의 웹 서버는 바이너리 SSL 트래픽을 잘못된 HTTP로 해석하고 커넥션을 닫을 것이다"**와 **"보안 서비스를 HTTP에 더 통합적으로 계층화했더라면 여러 목적지 포트가 필요 없었겠지만 실무에서 심각한 문제를 일으키지는 않는다"**, "Secure Transport Setup"의 평문 HTTP 4단계와 HTTPS 절차(포트 443 커넥션 → SSL 계층 초기화, 암호 파라미터 협상과 키 교환 → 핸드셰이크 완료 후 요청 메시지를 보안 계층으로 → TCP로 가기 전 암호화), **그림 14-15의 6단계 대조**(SSL 종료 통지가 별도 단계로 있다는 것 포함). 계층 구조 그림은 이 책 1.2절 그림 1-1에서 이미 다뤘으므로 재서술하지 않았다. 출처(origin) 개념과 스킴 다운그레이드에 대한 서술은 이 책의 것이며, 근거는 이 책 1.2절·15.2절과 Part IV·V의 예고다.

> 18.2절: HPBN 4장 "TLS Handshake" 절 전체 — 암호화 터널을 협상해야 애플리케이션 데이터를 교환할 수 있다는 것과 버전 합의·암호 스위트 선택·필요 시 인증서 검증이라는 세 항목, **"각 단계가 새로운 패킷 왕복을 요구하며 이것이 모든 TLS 커넥션에 시작 지연을 더한다"**, 그림 4-2와 **뉴욕–런던 28밀리초 편도 지연 가정**, **다섯 시점의 타임라인 전체**(0 ms TCP 3-way handshake 1왕복 / 56 ms 클라이언트가 TLS 버전·지원 암호 스위트 목록·기타 옵션을 **평문으로** 전송 / 84 ms 서버가 버전과 암호 스위트를 고르고 인증서를 붙여 응답하며 선택적으로 클라이언트 인증서와 다른 확장의 파라미터를 요청 / 112 ms 클라이언트가 새 대칭 키를 생성해 서버 공개키로 암호화해 보내고 암호화 통신으로의 전환을 알리며, **"지금까지 서버 공개키로 암호화된 새 대칭 키를 제외한 모든 데이터가 평문으로 교환되었다"** / 140 ms 서버가 대칭 키를 복호하고 MAC 검증으로 무결성을 확인한 뒤 암호화된 `Finished`를 회신 / 168 ms 클라이언트가 복호하고 MAC을 검증하면 터널이 수립되어 애플리케이션 데이터를 보낼 수 있다), **"새 TLS 커넥션은 전체 핸드셰이크에 두 번의 왕복을 요구한다"**와 축약 핸드셰이크가 한 번을 요구한다는 예고, **"모든 TLS 커넥션이 TCP 핸드셰이크 위에 최대 두 번의 추가 왕복을 요구한다는 것을 인식하는 것이 중요하다"**와 "잘 관리하지 않으면 수백에서 수천 밀리초의 네트워크 지연을 더할 수 있다", "Performance of Public vs. Symmetric Key Cryptography" 상자 전체(공개키 암호가 TLS 터널의 세션 셋업에만 쓰인다는 것, `openssl speed rsa`·`openssl speed aes`, **두 테스트의 단위가 직접 비교 가능하지 않다**는 단서와 "1,024 또는 2,048비트 권장 키 길이에서의 RSA 연산 수(전체 TLS 핸드셰이크 수)가 병목일 가능성이 높다", **"마케팅이나 철 지난 벤치마크에 속지 말고 항상 자기 하드웨어에서 성능 테스트를 실행하라"**). 핸드셰이크 네 항목(버전 교환, 양쪽이 아는 암호 선택, 각 측 신원 인증, 임시 세션 키 생성)은 HTTP-DG 14장 "SSL Handshake" 절의 네 불릿이며 그림 14-16의 4단계 단순화도 같은 절이다. 그림 18-2의 메시지 순서와 표 18-2의 메시지별 내용은 원서 두 권이 모두 단순화된 형태로만 제시한 것을 TLS 1.2의 실제 순서로 복원한 것이다. 인증서 사슬 바이트가 초기 혼잡 윈도우에 근접한다는 관찰은 HPBN 4장 "Testing and Verification" 절의 3,571바이트 계산에서 왔다.
>
> 18.3절: HTTP-DG 14장 "Server Certificates"와 "Site Certificate Validation" 절 전체 — 보안 HTTPS 트랜잭션이 항상 서버 인증서를 요구한다는 것, 서버 인증서가 조직 이름·주소·서버 DNS 도메인 이름 등을 담은 X.509 v3 파생 인증서라는 것과 그림 14-17의 다섯 필드, **"SSL 자체는 웹 서버 인증서를 검사하도록 요구하지 않지만 대부분의 현대 브라우저는 인증서에 대해 몇 가지 단순한 온전성 검사를 수행하고 더 철저한 검사를 할 수단을 제공한다"**, **"넷스케이프가 제안한 웹 서버 인증서 검증 알고리즘 하나가 대부분의 브라우저 검증 기법의 기초를 이룬다"**와 **네 단계 전체**(Date check: 시작·종료 날짜 확인, 만료되었거나 아직 활성화되지 않았으면 검증 실패와 오류 표시 / Signer trust check: 모든 인증서가 어떤 CA에 의해 서명되며 인증서 수준마다 다른 배경 검증이 요구된다는 것, 전자상거래 서버 인증서에는 보통 법인 설립의 법적 증명이 필요하다는 것, **"누구나 인증서를 생성할 수 있지만 일부 CA는 신청자의 신원과 정상적 사업 행위를 검증하는 잘 이해된 절차를 가진 잘 알려진 조직이다. 이 때문에 브라우저는 신뢰받는 서명 기관 목록을 탑재하고 배포된다"**, 알 수 없는 기관이 서명한 인증서를 받으면 대개 경고를 표시한다는 것, **"Sam's Signing Shop" 예시**와 유효한 서명 경로를 가진 인증서를 받아들일 수 있다는 것 / Signature check: **"서명 기관이 신뢰할 만하다고 판정되면 브라우저는 서명 기관의 공개키를 서명에 적용해 체크섬과 비교함으로써 인증서의 무결성을 검사한다"** / Site identity check: **"서버가 다른 사람의 인증서를 복사하거나 그들의 트래픽을 가로채는 것을 막기 위해 대부분의 브라우저는 인증서의 도메인 이름이 자기가 대화한 서버의 도메인 이름과 일치하는지 검증하려 한다"**, **"서버 인증서는 보통 도메인 이름 하나를 담지만 일부 CA는 서버 클러스터나 팜을 위해 서버 이름 목록이나 와일드카드 도메인 이름을 담은 인증서를 만든다"**, **"호스트명이 인증서의 신원과 일치하지 않으면 사용자 지향 클라이언트는 사용자에게 통지하거나 잘못된 인증서 오류로 커넥션을 종료해야 한다"**), "Virtual Hosting and Certificates" 절 전체(가상 호스팅 사이트의 보안 트래픽 처리가 까다롭다는 것, **일부 인기 웹 서버 프로그램이 인증서 하나만 지원한다**는 것, 인증서 이름과 엄밀히 일치하지 않는 가상 호스트명으로 오면 경고 상자가 표시된다는 것, **Cajun-Shop.com 사례 전체**(호스팅 제공자가 준 공식 이름 `cajun-shop.securesites.com`, `www.cajun-shop.com`으로 갔을 때의 불일치, 이를 막기 위해 보안 트랜잭션 시작 시 모두를 `cajun-shop.securesites.com`으로 리다이렉트한다는 것), **"가상 호스팅된 사이트의 인증서 관리는 좀 까다로울 수 있다"**). 폐기 확인 단계와 용도 제약 단계는 이 책 17.9절·17.6절의 내용을 검증 절차의 자리에 배치한 것이다. **표 18-4의 이름 일치 규칙 세부**(SAN이 있으면 CN 무시, 와일드카드는 최좌측 레이블 하나에만 대응하고 빈 레이블에 대응하지 않으며 공용 접미사에 허용되지 않음, IP는 `iPAddress` 형식으로만)는 원서 두 권이 명시적으로 열거하지 않은 것으로, HTTPS 위의 이름 검증을 규정하는 표준의 규칙이며 원서의 "단일 도메인 이름 / 이름 목록 / 와일드카드 도메인 이름"이라는 서술을 정확한 판정 규칙으로 펼친 것이다. **재검토가 필요하다면 이 표다.** 표 18-6과 그에 대한 세 가지 관찰은 이 책의 것이며, 근거는 위 인용문들과 이 책 17.7절·17.10절이다.
>
> 18.4절: HTTP-DG 14장 그림 14-18의 **네 캡션 전체**((a) 호스트명 `www.cajun-shop.com`이 인증서 이름과 불일치하며 사이트가 가상 호스팅되어 인증서가 `*.securesites.com`에 발급되었기 때문이라는 것 / (b) **대화상자가 인증서는 유효한 날짜를 갖고 유효한 인증 기관에서 왔지만 이름이 URL에서 요청한 사이트와 일치하지 않는다고 경고한다**는 것 / (c) "인증서 보기" 버튼을 눌러 `*.securesites.com` 와일드카드 인증서임을 확인하며 **"이 정보를 가지고 사용자는 인증서를 받아들일지 거절할지 결정할 수 있다"** / (d) 받아들이면 HTTPS로 페이지가 로드된다는 것, 그리고 **"이런 종류의 사용자 오류를 피하기 위해 이 사이트는 모든 HTTPS 트래픽을 호스트명 별칭 `cajun-shop.securesites.com`으로 보낸다"**), 그리고 17.6절이 인용한 **"서명 기관을 모를 때 브라우저가 사용자에게 대화상자를 띄운다"**는 서술. 폐기 확인 실패에 대한 서술은 HPBN 4장 "Online Certificate Status Protocol" 절의 네 문제 중 **클라이언트가 탐색을 진행하기 전에 OCSP 요청에서 블로킹해야 한다**는 것과 **"OCSP 요청이 실패했을 때의 동작이 브라우저마다 다르다"**에서 왔다. **표 18-7의 무해한 원인 열, 표 18-8의 세 가지 구조적 결함, 기저율 논증, 개발자에게 반복되는 같은 구조(`curl -k`·`verify=False`·빈 `TrustManager`)에 대한 서술은 전부 이 책의 논지다.** 원서에는 대응하는 절이 없으며, 재료는 위 캡션 인용과 이 책 17.10절 논점 2의 세 번째 조건, 그리고 이 책이 30장·45장에서 다룰 실패 설계의 원칙이다.
>
> 18.5절: HTTP-DG 14장 "Server Certificates" 절 도입부 — **"SSL은 상호 인증을 지원해 서버 인증서를 클라이언트로, 클라이언트 인증서를 서버로 나른다. 그러나 오늘날 클라이언트 인증서는 브라우징에 흔히 쓰이지 않는다. 대부분의 사용자는 개인 클라이언트 인증서를 갖고 있지도 않다. 웹 서버가 클라이언트 인증서를 요구할 수는 있지만 실무에서 그런 일은 드물다"**와 **두 각주**(일부 기업 환경의 웹 브라우징과 보안 이메일에 쓰이며 미래에는 더 흔해질 수 있으나 매우 느리게 확산되었다는 것 / 일부 조직의 인트라넷이 직원의 정보 접근을 통제하기 위해 클라이언트 인증서를 쓴다는 것), **"반면 보안 HTTPS 트랜잭션은 항상 서버 인증서를 요구한다"**와 신용카드 정보를 보낼 때 자기가 생각하는 조직과 대화하고 있음을 알고 싶어 한다는 동기. 인증이 양방향 가능하다는 것과 **회사 프록시 서버가 모든 직원을 인증하며 각자 회사가 서명한 고유 인증서를 갖는 예**는 HPBN 4장 "Encryption, Authentication, and Integrity" 절이며 이 책 17.7절이 이미 인용했다. `No client certificate CA names sent` 줄은 HPBN 4장 "Testing and Verification" 절의 출력에 있다. **표 18-9의 대조, 신원이 커넥션의 속성이라는 정식화, 재협상의 순서 문제, TLS 종료가 신원을 지우고 헤더로 강등된다는 서술, 클라이언트 인증서가 널리 쓰이지 않은 네 가지 이유는 이 책의 것이다.** 근거는 위 인용문들과 이 책 9.10절·13.12절·15.2절·20.2절이 각각 다룬 "커넥션에 걸린 상태"와 "신뢰 경계를 넘을 때 증명이 주장으로 바뀐다"는 형태다.

> 18.6절: HPBN 4장 "Application Layer Protocol Negotiation (ALPN)"과 "Server Name Indication (SNI)" 절 전체 — 사용자 정의 프로토콜을 위해 포트를 미리 배정하는 방식이 **"느리고 비현실적인 과정"**이며 **"방화벽과 다른 중간자들이 대개 80번과 443번 포트로만 트래픽을 허용한다"**는 것, 포트 80이 HTTP에 예약되어 있고 명세가 `Upgrade` 흐름을 제공하지만 **"`Upgrade`의 사용은 추가 네트워크 왕복을 더할 수 있고 실무에서는 많은 중간자가 존재할 때 종종 신뢰할 수 없다"**는 것, **"종단 간 암호화 터널의 사용이 중간 프록시에게서 데이터를 가리고 새롭고 임의적인 애플리케이션 프로토콜을 빠르고 신뢰성 있게 배포할 수 있게 한다"**와 그럼에도 협상 방법이 필요하다는 것, HTTPS 세션이 `Upgrade`를 재사용하면 또 한 번의 완전한 왕복이 든다는 것과 **"핸드셰이크 자체의 일부로 프로토콜을 협상할 수는 없을까?"**, ALPN의 정의와 **두 단계 절차 전체**(클라이언트가 `ProtocolNameList`를 `ClientHello`에 붙임 / 서버가 검사해 `ProtocolName`을 `ServerHello`의 일부로 반환), **"서버는 단 하나의 프로토콜 이름으로만 응답할 수 있고 클라이언트가 요청한 것 중 지원하는 것이 없으면 커넥션을 중단하는 쪽을 택할 수 있다"**, **"ALPN이 HTTP `Upgrade` 교환의 필요를 없애 추가 왕복을 아끼지만 TLS 핸드셰이크 자체는 여전히 수행되어야 하므로 ALPN 협상이 암호화되지 않은 채널에서의 HTTP `Upgrade`보다 빠른 것은 아니다. 대신 TLS 위의 애플리케이션 프로토콜 협상이 더 느려지지 않게 보장한다"**, "History and Relationship of NPN and ALPN" 상자 전체(NPN이 구글의 SPDY 작업의 일부였다는 것, ALPN이 개정되고 IETF가 승인한 버전이라는 것, **NPN에서는 서버가 광고하고 클라이언트가 골랐으나 ALPN에서는 뒤집혔다**는 것과 그 근거, NPN이 폐기되었다는 것), SNI 절의 **"암호화된 TLS 터널은 임의의 두 TCP 상대 사이에 수립될 수 있으며 클라이언트는 상대의 IP 주소만 알면 된다"**와 **"서버가 같은 IP 주소 위에 각각 자기 TLS 인증서를 가진 여러 독립 사이트를 호스팅하고 싶다면 어떻게 되는가? 함정 질문이다. 안 된다"**, SNI가 **"클라이언트가 접속하려는 호스트명을 핸드셰이크 시작 시점에 표시할 수 있게 한다"**는 것과 **"웹 서버가 SNI 호스트명을 검사해 적절한 인증서를 골라 핸드셰이크를 계속할 수 있다"**, "TLS, HTTP, and Dedicated IPs" 상자(**"TLS+SNI 워크플로는 HTTP에서의 `Host` 헤더 광고와 동일하다. 같은 IP 주소가 여러 다른 도메인을 호스팅할 수 있고 SNI와 `Host` 둘 다 그것들을 구별하기 위해 필요하다"**, 많은 구형 클라이언트가 SNI를 지원하지 않으며 그런 클라이언트에 TLS를 제공하려면 호스트마다 전용 IP가 필요할 수 있다는 것). ALPN이 핸드셰이크 무결성 안에 있다는 논점은 이 책 11.12절이 이미 세웠다. **SNI가 평문이라는 사실의 함의(관찰 해상도의 상승, 선택자로서의 SNI), 표 18-10의 네 자리, SNI와 `Host`의 불일치가 만드는 두 시나리오, "커넥션이 권한을 갖는 이름의 집합을 정의하는 것은 제시된 인증서다"라는 정식화는 이 책의 것이다.** 근거는 이 책 1.2절(TLS의 보호 범위), 15.2절(가상 호스팅의 판정), 13.12절(파싱 불일치 지점), 11장(커넥션 병합)이다.

> 18.7절: HPBN 4장 "TLS Record Protocol" 절 전체 — **"그 아래의 IP나 TCP 계층과 마찬가지로 TLS 세션 안에서 교환되는 모든 데이터도 잘 정의된 프로토콜로 프레이밍된다"**와 그림 4-8, **레코드 프로토콜의 두 책임**(`Content Type` 필드로 핸드셰이크·알림·데이터를 식별 / 각 메시지의 무결성 보장과 검증), **애플리케이션 데이터 전달의 다섯 단계 전체**(레코드 프로토콜이 애플리케이션 데이터를 받음 / 최대 2¹⁴ 바이트, 즉 16 KB의 블록으로 나눔 / 선택적 압축 / MAC 또는 HMAC 부착 / 협상된 암호로 암호화), 수신 측에서 역순으로 적용된다는 것, **세 가지 함의 전체**(최대 레코드 크기 16 KB / 각 레코드가 5바이트 헤더와 MAC — SSLv3·TLS 1.0·TLS 1.1은 최대 20바이트, TLS 1.2는 최대 32바이트 — 과 블록 암호 사용 시 패딩을 포함 / **"레코드를 복호하고 검증하려면 레코드 전체가 확보되어야 한다"**), **"올바른 레코드 크기를 고르는 것이 중요한 최적화가 될 수 있다. 작은 레코드는 레코드 프레이밍 때문에 오버헤드가 크고, 큰 레코드는 TLS 계층이 처리해 애플리케이션에 전달하기 전에 TCP 계층이 전달하고 재조립해야 한다"**. 그림 18-5의 세그먼트 대조와 16 KB를 MSS 1,460으로 나눈 계산은 이 책 1.3.2절과 3.4절의 값을 적용한 것이다. `close_notify`는 HTTP-DG 그림 14-15의 5단계("SSL close notification")이며, **그것이 절단 탐지를 가능하게 한다는 논점과 그 보호를 버리는 구현에 대한 서술, 레코드 일련번호가 재생·재정렬을 막는다는 서술, 레코드 헤더가 평문일 수밖에 없다는 논증은 이 책의 것이다.** 근거는 이 책 9.9절(커넥션 종료의 모호함), 10.4절(본문 경계), 1.2절(TLS가 가리지 않는 것)이다.

> 18.8절: HTTP-DG 14장 "A Real HTTPS Client", "OpenSSL", "A Simple HTTPS Client", "Executing Our Simple OpenSSL Client" 절 전체 — **"SSL은 복잡한 바이너리 프로토콜이다. 암호 전문가가 아니라면 원시 SSL 트래픽을 직접 보내지 말아야 한다"**와 상용·오픈소스 라이브러리의 존재, OpenSSL이 SSL과 TLS의 가장 인기 있는 오픈소스 구현이며 SSLeay의 후속이라는 것, **아홉 구간짜리 예제 프로그램 전체**와 구간별 설명(`SSL_CTX_new`가 **핸드셰이크 파라미터와 SSL 커넥션 상태를 추적하는 로컬 컨텍스트를 만든다**는 것, `gethostbyname`, 443번 포트로의 TCP 커넥션, `SSL_new`·`SSL_set_fd`·`SSL_connect`로 **"암호가 선택되고 인증서가 교환된 동작하는 SSL 채널"**이 만들어진다는 것, `SSL_get_cipher`, `SSL_get_peer_certificate`와 **"OpenSSL 라이브러리는 서버 인증서의 정보로 특별한 일을 하지 않는다. 웹 브라우저 같은 실제 SSL 애플리케이션이라면 인증서가 제대로 서명되었고 올바른 호스트에서 왔는지 온전성 검사를 할 것이다"**, `SSL_write`·`SSL_read`와 **"SSL 계층이 모든 암호화와 복호를 처리하므로 그냥 평범한 HTTP 명령을 쓰고 읽으면 된다"**, 정리 구간), **소스의 `/* certificate verification would happen here */` 주석**, **"오류 처리가 제거되었으므로 설명용으로만 써야 하며 정상적인 오류 조건에서 크래시하거나 오작동할 것이다"**는 경고, **"암호화와 키와 인증서 관리를 전부 포함해 이 프로그램 전체가 3페이지짜리 C 프로그램에 들어간다"**, 실행 출력의 아홉 단계와 **"첫 네 구간이 완료되는 즉시 클라이언트는 열린 SSL 커넥션을 갖는다. 그 뒤 커넥션 상태와 선택된 파라미터를 조회하고 서버 인증서를 검사할 수 있다"**. 그림 18-6의 `openssl s_client -state` 출력은 HPBN 4장 "Testing and Verification" 절의 출력을 이 책의 실행 예제(Joe's Hardware Store)로 옮긴 것이며, 원서의 실제 사이트·CA 이름은 쓰지 않았다. 같은 절에서 인용한 것은 **"`s_client`는 알려진 루트 인증서에 대해 아무 가정도 하지 않으므로 루트 인증서 경로를 수동으로 지정해야 한다. 이것이 중요하다. 브라우저는 이미 그 루트 인증서를 갖고 있어 사슬을 검증할 수 있지만 `s_client`는 그런 가정을 하지 않는다. 루트 인증서를 빼면 로그에서 검증 오류를 보게 된다"**와 **"사슬 검사 결과 서버가 두 개의 인증서를 보냈고 합계 3,571바이트로 이는 초기 TCP 혼잡 윈도우 3~4세그먼트 크기에 매우 가깝다. 그것을 넘치게 하지 않도록, 또는 서버의 `cwnd` 크기를 올리도록 조심해야 한다"**, 그리고 Qualys SSL Server Test 같은 온라인 서비스와 `openssl` 명령줄 인터페이스에 익숙해지라는 권고다. **예제 18-2·18-3의 네 항목, 표 18-12의 검토 항목, 호스트명 검사가 오랫동안 라이브러리의 일이 아니었다는 역사적 서술, 표 18-13의 실험 목록은 이 책의 것이다.** 근거는 예제 프로그램의 주석 자리와 이 책 5.11절·17.10절이다.
