# 부록 H. GraphQL API 테스트 체크리스트와 학습 자료

40.10절은 Part VIII의 절차를 **본문 흐름 속의 요약**으로 묶었다. 정찰이 지도를 그리고 DoS·정보 노출·인증·인가·인젝션·요청 위조가 그 위를 걷는다는 실행 순서를, 각 절이 어느 점검 항목으로 이어지는지와 함께 짚은 것이 그 절의 역할이었다. 이 부록은 같은 대상을 **독립 참조용 전체 체크리스트**로 다시 세운다.

**역할 분담은 이렇다.** 40.10절은 읽는 순서 안에서 "무엇을 언제 하는가"를 서술로 보였다. 이 부록은 실제 테스트를 수행할 때 곁에 두고 **하나씩 지워 나가는 목록**이다. 그래서 도구 이름과 명령, 각 항목이 무엇을 확인하는지, 그리고 그 항목의 근거가 본문 어디에 있는지를 함께 적는다. 40.10절이 안내라면 이 부록은 작업 시트다.

체크리스트는 BHGQL 부록 A를, 학습 자료는 부록 B를 근거로 한다. 각 묶음의 제목 옆에 본문 참조를 걸어 두었으니, 항목의 원리가 궁금하면 그 절로 돌아가면 된다. 실행 예제는 취약 GraphQL 서버 **DVGA(Damn Vulnerable GraphQL Application)** 를 가정하며, 도메인 맥락이 필요한 자리는 **온라인 서점**을 예로 든다.

> **이 체크리스트를 쓰기 전에**
>
> 0.6절과 이 책 서두가 세운 경계를 다시 확인한다. **아래 항목은 테스트 권한이 있는 대상에만 수행한다.** DoS 항목은 특히 그렇다 — 순환 질의나 배열 배칭은 운영 중인 서버를 실제로 멈출 수 있다. 랩(38.4절이 구축한 환경)이나 명시적 허가가 있는 대상, 또는 취약점 공개 프로그램의 범위 안에서만 실행한다.

## H.1 정찰 (→ 39.1~39.3)

지도를 그리는 단계다. 엔드포인트를 찾고, 서버를 식별하고, 스키마를 확보한다. 이 단계의 산출물이 이후 모든 단계의 입력이 된다.

- ☐ **포트 스캔.** Nmap으로 웹 애플리케이션 포트를 식별한다. GraphQL은 대개 기존 웹 서버 위의 단일 엔드포인트이므로, 먼저 웹 포트를 찾는다(→ **39.1**).
- ☐ **엔드포인트 탐지.** `graphw00f`의 탐지 모드로 웹 서버에서 GraphQL 엔드포인트를 스캔한다. `/graphql`, `/api`, `/query` 등 관용 경로를 확인한다(→ **39.1**).
- ☐ **서버 핑거프린팅.** `graphw00f`의 지문 모드로 구현체를 식별한다. Apollo, graphql-ruby, Graphene, Hasura 등 구현마다 방어 기능과 알려진 결함이 다르다(→ **39.3**).
- ☐ **서버 취약점 검색.** 식별된 구현·버전을 MITRE CVE 데이터베이스에서 조회한다(→ **39.3**).
- ☐ **보안 기능 검색.** GraphQL Threat Matrix에서 그 구현의 서버 수준 보안 기능을 확인한다 — 깊이 제한, 비용 분석, 인트로스펙션 기본값 등(→ **39.3**, **40.6**).
- ☐ **IDE 탐지.** `EyeWitness`로 GraphiQL Explorer나 GraphQL Playground 같은 IDE의 노출을 찾는다. 이들은 그 자체로 공격 표면이자 인트로스펙션 창구다(→ **39.1**).
- ☐ **인트로스펙션 질의.** 인트로스펙션 질의를 보내 사용 가능한 모든 질의(query)·뮤테이션(mutation)·서브스크립션(subscription)을 문서화한다. 스키마 전체가 한 요청에 드러난다(→ **39.2**).
- ☐ **스키마 시각화.** 인트로스펙션 응답을 GraphQL Voyager로 시각화해 타입 간 관계를 파악한다. 이 관계 그래프가 이후 순환 질의(H.2)와 인가 경로(H.4)의 재료가 된다(→ **39.2**).

## H.2 서비스 거부 (→ 40.1~40.6)

**GraphQL이 앞의 여덟 부에 대응 장이 없는 유일한 새 취약점 부류다.** 클라이언트가 선언적 질의로 서버의 자원 소모를 좌우하기 때문이다(→ **40.1**). 두 유형 — 작은 질의로 응답을 부풀리는 것과 큰 질의로 파싱·리졸브를 태우는 것 — 을 모두 확인한다.

- ☐ **양방향 관계 검토.** API의 SDL 파일에서 양방향 관계를 찾는다. 온라인 서점의 `Book`↔`Author`처럼 서로를 참조하는 타입이 순환 질의의 토대다(→ **40.2**).
- ☐ 다음을 시험한다:
  - ☐ **순환 질의·뮤테이션(circular query).** 양방향 관계를 반복해 파고들어 응답을 지수적으로 부풀린다. `book { author { books { author { … } } } }`(→ **40.2**).
  - ☐ **순환 프래그먼트(circular fragment).** 프래그먼트가 서로를 참조하게 한다. 명세는 이를 금지하지만, 검증하지 않는 구현은 세그폴트에 이를 수 있다(→ **40.2**).
  - ☐ **필드 중복(field duplication).** 같은 필드를 한 질의 안에서 여러 번 요청한다. 응답은 통합돼도 리졸버는 개별 실행되어, 응답 시간이 배로 뛴다(→ **40.3**).
  - ☐ **앨리어스 과부하(alias overloading).** 앨리어스로 같은 필드를 수백·수천 번 호출한다. 단일 요청에 은신하면서 서버를 소모시킨다(→ **40.3**).
  - ☐ **디렉티브 과부하(directive overloading).** 존재하지 않는 디렉티브(`@aa @aa @aa …`)를 무제한 붙여 파서를 소모시킨다(→ **40.3**).
  - ☐ **배열 기반·앨리어스 기반 질의 배칭(query batching).** 여러 연산을 하나의 HTTP 요청에 담는다. 순차 처리되므로 요청 수 기반 레이트 리밋을 우회한다(→ **40.4**).
  - ☐ **객체 한도 재정의(object limit overriding).** 페이지네이션 인자 — `filter`, `max`, `limit`, `total` — 에 `limit:100000` 같은 큰 값을 넣어 DB 층에 부하를 준다(→ **40.4**).
- ☐ **자동 감사.** `GraphQL Cop`으로 위 벡터를 1차 스윕한다. 네 벡터에 대해 위험도를 출력한다(→ **40.5**).

> **주의.** 이 묶음의 모든 항목은 대상 서버를 실제로 마비시킬 수 있다. 랩이나 명시적 허가 범위에서만, 그리고 작은 값에서 시작해 점진적으로 실행한다.

## H.3 정보 노출 (→ 30.10, 39.4~39.8)

인트로스펙션이 꺼져 있어도 스키마는 새어 나온다. 오류 메시지, 필드 제안, GET 질의의 흔적이 그 통로다(→ **30.10**).

- ☐ **필드 스터핑으로 스키마 복원.** 인트로스펙션이 비활성일 때 필드 스터핑으로 스키마를 추출한다. `Clairvoyance` 같은 도구가 필드 제안 응답을 모아 스키마를 재구성한다(→ **39.5**, **39.6**).
- ☐ **디버그 오류 식별.** 오작동하는(malformed) 질의를 보내 응답의 디버그 오류를 확인한다. 스택 트레이스나 내부 경로가 새는지 본다(→ **39.7**, **30.10**).
- ☐ **질의 추적(query tracing) 식별.** 응답에 실행 시간·리졸버 경로 같은 추적 정보가 붙는지 확인한다. 이것이 켜져 있으면 내부 구조가 드러난다(→ **39.5**).
- ☐ **GET으로 보낸 PII 점검.** `GET` 메서드로 보낸 질의에 개인식별정보(PII)가 실렸는지 확인한다. GET 질의는 **URL에 남으므로 프록시 로그·브라우저 히스토리·Referer에 기록된다**(→ **39.8**).

> InQL로 스키마 추출을 자동화할 수도 있다(→ **39.4**). 인트로스펙션이 켜져 있으면 InQL이 스키마를 그대로 뽑고, 꺼져 있으면 Clairvoyance의 필드 제안 경로로 넘어간다.

## H.4 인증과 인가 (→ 40.7~40.8)

**GraphQL 인가의 구조적 문제는 판단 지점이 흩어진다는 것이다.** 한 요청이 여러 리졸버를 거치므로 인가가 필드마다 흩어지고, 하나를 빠뜨리면 우회 경로가 된다(→ **40.7**). 인증(누구인가)과 인가(무엇을 할 수 있는가)를 나눠 시험한다.

- ☐ 다음에 대한 접근을 시험한다:
  - ☐ **인증 헤더 없는 API 접근.** 인증 헤더를 빼고 각 연산에 접근해 본다. 어느 필드가 인증 없이 응답하는지 확인한다(→ **40.8**).
  - ☐ **대체 경로를 통한 제한된 필드 접근.** 스키마 그래프에서 같은 객체로 가는 다른 경로를 찾는다. 한 경로는 막혀 있어도 다른 경로가 열려 있을 수 있다. `graphql-path-enum`이 흩어진 경로 중 인가 누락 지점을 찾아 준다(→ **40.8**).
  - ☐ **GET·POST 양쪽 접근.** 두 메서드로 같은 연산을 보낸다. 한쪽에만 걸린 통제가 있는지 확인한다(→ **40.8**, **39.8**).
- ☐ **JWT 서명 검증 시험.** JSON Web Token의 서명 검증을 시험한다. `alg:none`, 서명 미검증, 페이로드 노출을 확인하고 `jwt.io`로 토큰을 조작해 본다 — 예컨대 identity 필드를 `admin`으로 바꿔 본다(→ **40.7**, **40.8**).
- ☐ **비밀을 받는 연산 무차별 대입.** 토큰이나 비밀번호 같은 비밀을 인자로 받는 뮤테이션·질의를 무차별 대입한다. **인밴드 인증은 배치에 취약하다** — 수천 번의 시도를 단일 HTTP 요청에 담아 요청 수 레이트 리밋을 우회한다:
  - ☐ 앨리어스 기반 질의 배칭
  - ☐ 배열 기반 질의 배칭
  - ☐ `CrackQL` (IDOR·무차별 대입 자동화)
  - ☐ `Burp Suite`

## H.5 인젝션 (→ 27.14, 28.10, 32.11)

**GraphQL은 인젝션의 새 통로일 뿐 새 인젝션이 아니다.** 리졸버 뒤의 SQL·OS 명령·XSS는 옛 병이고, GraphQL은 문의 모양만 바꿨다(→ **27.14**, **28.10**, **32.11**).

- ☐ 다음 위치의 인젝션을 시험한다:
  - ☐ **질의 인자(query arguments).** 최상위 질의의 인자에 인젝션 페이로드를 넣는다(→ **27.14**).
  - ☐ **필드 인자(field arguments).** 중첩된 필드의 인자에 넣는다. 리졸버가 이 값을 SQL·명령으로 넘기면 인젝션이 성립한다(→ **28.10**).
  - ☐ **질의 디렉티브 인자(directive arguments).** 디렉티브에 전달되는 값도 검증되지 않을 수 있다(→ **27.14**).
  - ☐ **연산 이름(operation names).** 연산 이름이 로깅이나 처리에 그대로 쓰이면 그 자리도 인젝션 표면이다(→ **28.10**).
- ☐ **SQLi 자동 시험.** `SQLmap`으로 SQL 인젝션을 자동 탐지한다. GraphQL 요청을 SQLmap에 넘겨 리졸버 뒤의 DB를 시험한다(→ **27.14**).
- ☐ **OS 명령 인젝션 자동 시험.** `Commix`로 OS 명령 인젝션을 자동 탐지한다. 리졸버가 셸 명령을 조립하면 여기서 드러난다(→ **28.10**).
- ☐ **응답 경유 XSS.** GraphQL 응답이 저장 후 다른 사용자의 브라우저에서 렌더링되는 경로를 확인한다. 저장형 XSS가 GraphQL 저장·조회를 통해 성립한다(→ **32.11**).

## H.6 요청 위조와 하이재킹 (→ 33.6~33.7, 37.7)

**GraphQL CSRF는 GET 기반 질의와 콘텐츠 타입 우회에서 성립하고, WebSocket 하이재킹은 서브스크립션의 Origin 미검증에서 성립한다**(→ **33.6**, **33.7**, **37.7**).

### 요청 위조 (→ 33.6)

- ☐ 다음을 점검한다:
  - ☐ **HTTP 헤더·본문의 안티 CSRF 토큰 존재 여부.** 상태를 바꾸는 연산이 토큰으로 보호되는지 확인한다(→ **33.6**, **33.4**).
  - ☐ **안티 CSRF 토큰 우회 가능성.** 토큰이 있어도 검증이 느슨한지 — 빈 값·임의 값이 통과하는지 — 시험한다(→ **33.6**).
  - ☐ **GET 기반 질의 지원.** 서버가 `GET`으로 질의를 받는지 확인한다. GET 질의는 이미지 태그나 링크로 유발할 수 있어 CSRF의 고전적 통로다(→ **33.6**, **39.8**).
  - ☐ **GET 기반 뮤테이션 지원.** 상태를 바꾸는 뮤테이션까지 `GET`으로 받는다면 방어가 크게 무너진 것이다(→ **33.6**).
- ☐ **상태 변경 뮤테이션을 GET으로 수행.** 실제로 `GET`으로 상태 변경 뮤테이션을 보내 본다. 콘텐츠 타입 검사가 없으면 통과한다(→ **33.6**).
- ☐ **상태 변경 뮤테이션을 POST로 수행.** `POST`이더라도 콘텐츠 타입 우회(예: `text/plain`, `multipart/form-data`)로 CSRF가 가능한지 확인한다. 온라인 서점의 "장바구니에 담기"나 "주소 변경"이 이 시험의 대상이다(→ **33.6**).

### 요청 하이재킹 (→ 33.7, 37.7)

- ☐ GraphQL 서버가 다음을 하는지 식별한다:
  - ☐ **서브스크립션 지원 여부.** 서버가 서브스크립션을 지원하면 WebSocket 채널이 열린다(→ **37.4**, **37.5**).
  - ☐ **WebSocket 핸드셰이크의 Origin 헤더 검증 여부.** 핸드셰이크에서 `Origin`을 검증하지 않으면 **크로스 사이트 WebSocket 하이재킹(CSWSH)** 이 성립한다 — 쿠키가 자동 전송되고 SOP가 WebSocket에 적용되지 않기 때문이다(→ **33.7**, **37.7**).

## 이 부록의 요약

- **이 부록은 독립 참조용 전체 체크리스트다.** 40.10절이 읽는 순서 안의 요약이라면, 이 부록은 실제 테스트에서 곁에 두고 지워 나가는 작업 시트다. 두 곳의 항목은 같되 목적이 다르다.
- **여섯 묶음이 Part VIII의 실행 순서다.** 정찰(H.1)이 지도를 그리고, 서비스 거부(H.2)·정보 노출(H.3)·인증과 인가(H.4)·인젝션(H.5)·요청 위조와 하이재킹(H.6)이 그 지도 위를 걷는다.
- **서비스 거부만이 GraphQL의 새 취약점이다.** 나머지 다섯 묶음은 옛 병이 새 문으로 들어온 것이며, 각 항목의 본문 참조가 그 대응을 가리킨다 — 인젝션은 27·28·32장, 요청 위조는 33·37장으로.
- **DoS 항목은 실제로 서버를 멈출 수 있다.** 권한이 있는 대상, 랩, 또는 공개 프로그램 범위에서만, 작은 값부터 실행한다.
- **인밴드 인증은 배치에 취약하다.** 앨리어스·배열 배칭이 요청 수 기반 방어를 우회하므로, 무차별 대입 시험은 배칭을 반드시 포함한다.
- **도구는 전통적 도구의 GraphQL 대응물이다.** 표 H-1이 단계별로 정리했으며, 25.8절의 도구 절과 함께 보면 대응이 보인다.
