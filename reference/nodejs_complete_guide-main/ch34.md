# 34장. 보안

보안은 기능이 아니라 성질이다. "보안 모듈"을 하나 붙여서 얻을 수 있는 것이 아니라, 코드·의존성·설정·운영 절차 전체에 걸쳐 유지되는 상태다. 그래서 이 장은 하나의 라이브러리 사용법이 아니라, Node.js 서비스가 공격당하는 실제 경로를 하나씩 열거하고 각각을 막는 구체적 코드와 절차를 다룬다.

다루는 순서는 침투 경로가 열리는 순서와 같다. 먼저 코드 저장소에 비밀이 새는 경로를 막고, 서비스가 외부로 노출한 공격 표면(attack surface)을 좁히고, 우리가 직접 쓰지 않은 코드(의존성)를 통해 들어오는 공급망 공격(supply chain attack)을 방어하고, 설정과 시크릿을 안전하게 주입하고, 시간이 지나며 자연히 쌓이는 취약점과 EOL 런타임을 관리한다. 마지막으로 신뢰할 수 없는 코드를 다루는 격리 수단과 프로덕션 체크리스트로 마무리한다.

이 장은 전부 방어 관점이다. 공격 도구나 익스플로잇 작성법은 다루지 않는다. 필요한 것은 "어떻게 뚫는가"가 아니라 "무엇이 뚫리는 구조인가"이며, 후자만 알아도 방어는 설계할 수 있다.

## 34.1 저장소와 비밀 관리

### 비밀이 저장소에 들어가는 네 가지 경로

비밀(secret)이 유출되는 사고의 상당수는 정교한 공격이 아니라 커밋(commit) 실수다. 실제로 반복되는 경로는 네 가지다.

**첫째, 하드코딩이다.** "일단 돌려보고 나중에 빼자"고 넣은 API 키가 그대로 머지된다. 특히 예제 코드, 마이그레이션 스크립트, 일회성 운영 스크립트에서 자주 발생한다.

**둘째, `.env` 커밋이다.** `.env`를 `.gitignore`에 넣는 것은 상식이지만 `.env.production`, `.env.local`, `config/secrets.json` 같은 변형은 패턴에서 빠지기 쉽다. 무시 규칙은 화이트리스트가 아니라 블랙리스트이므로 언제나 누락 가능성이 있다.

**셋째, 로그다.** 요청 객체 전체를 로깅하면 `Authorization` 헤더와 쿠키가 함께 남는다. 오류 객체를 그대로 직렬화하면 데이터베이스 접속 문자열이 오류 메시지에 포함되어 나온다. 로그는 대개 별도 시스템으로 전송되고 장기 보관되므로, 로그로 샌 비밀은 회수 범위가 가장 넓다.

**넷째, 테스트 픽스처(fixture)다.** "테스트용이니까 괜찮다"며 넣은 스테이징 토큰이 실제로는 프로덕션과 같은 사용자 데이터를 가리키는 경우가 흔하다. 녹화된 HTTP 응답(VCR 스타일 픽스처)에 실제 토큰이 그대로 남는 것도 전형적이다.

로그 유출을 막는 가장 확실한 방법은 로거 계층에서 구조적으로 지우는 것이다(31장 참조).

```js
import pino from 'pino'

// 로거 자체에 편집(redaction) 규칙을 넣는다.
// 호출부의 주의력에 의존하지 않는 것이 핵심이다.
export const logger = pino({
  redact: {
    paths: [
      'req.headers.authorization',
      'req.headers.cookie',
      'req.body.password',
      'req.body.token',
      '*.creditCard',
      'config.databaseUrl'
    ],
    censor: '[REDACTED]'
  }
})
```

오류 직렬화도 마찬가지다. 오류에 붙은 임의 속성을 그대로 내보내지 말고, 내보낼 필드를 명시적으로 고른다.

```js
// 오류를 로그로 보낼 때 허용 목록(allowlist)만 통과시킨다
function serializeError(err) {
  return {
    name: err.name,
    message: err.message,
    code: err.code,
    // stack은 내부 로그에만, 응답 본문에는 절대 넣지 않는다
    stack: err.stack
  }
}
```

### 한 번 커밋된 비밀은 유출된 비밀이다

이 절에서 가장 중요한 원칙은 하나다. **비밀이 한 번이라도 커밋되어 원격 저장소에 푸시되었다면, 히스토리에서 지우더라도 유출로 간주하고 회전(rotate)해야 한다.**

이유는 기술적이다. 푸시된 커밋은 CI 러너, 개발자 로컬 클론, 포크(fork), 미러, 백업, 코드 검색 인덱스, 풀 리퀘스트 이벤트 웹훅 등 최소 여섯 군데로 이미 복제되었다. GitHub의 경우 포크 네트워크에 들어간 객체는 원본 저장소에서 히스토리를 재작성해도 접근 가능한 상태로 남을 수 있다. 그리고 공개 저장소에 푸시된 키는 자동 스캐너에 의해 수십 초 안에 수집된다.

따라서 대응 순서는 다음과 같다.

1. **즉시 회전한다.** 해당 키를 무효화하고 새 키를 발급한다. 이것이 1순위다.
2. **사용 흔적을 조사한다.** 해당 키로 발생한 접근 로그를 노출 시점부터 회전 시점까지 확인한다.
3. **그 다음에 히스토리를 정리한다.** `git filter-repo` 등으로 지우는 것은 재발 방지와 위생 목적이지 대응이 아니다.
4. **경로를 막는다.** 왜 커밋되었는지 원인을 제거한다(무시 규칙, 로컬 설정 분리, 스캐닝).

순서를 뒤집으면 안 된다. 히스토리 재작성에 반나절을 쓰는 동안 키는 여전히 유효하다.

### 비밀 스캐닝을 CI에 넣는다

사람의 주의력은 방어선이 되지 못한다. 커밋 전(pre-commit 훅)과 CI 양쪽에서 자동으로 검사한다(33장 참조). 훅은 개발자가 우회할 수 있으므로 CI 검사가 실질적인 게이트다.

```yaml
# .github/workflows/security.yml
name: security
on: [push, pull_request]

jobs:
  secret-scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0   # 전체 히스토리를 스캔하려면 얕은 클론을 풀어야 한다
      - name: 비밀 스캐닝
        uses: gitleaks/gitleaks-action@v2
        env:
          GITLEAKS_CONFIG: .gitleaks.toml
```

오탐(false positive)이 나오면 규칙을 끄지 말고 예외를 좁게 등록한다. 규칙 하나를 통째로 끄는 순간 그 규칙이 잡아야 했던 진짜 유출도 지나간다.

```toml
# .gitleaks.toml — 예외는 파일 단위가 아니라 지문(fingerprint) 단위로
[allowlist]
description = "테스트용 더미 키"
regexes = ['''AKIAIOSFODNN7EXAMPLE''']   # 문서에 공개된 예제 값
paths = ['''^test/fixtures/dummy-keys\.json$''']
```

## 34.2 공격 표면 인식: 파라미터 검증과 역직렬화

공격 표면은 "외부에서 들어온 값이 우리 코드의 판단에 영향을 주는 모든 지점"이다. Node.js 웹 서비스에서 이 지점은 생각보다 많다. HTTP 요청의 본문·쿼리·경로 파라미터·헤더·쿠키, 업로드 파일의 이름과 내용, 메시지 큐의 페이로드, 웹훅, 그리고 다른 내부 서비스가 보낸 응답까지 포함된다. 마지막 항목이 자주 빠진다. 내부 서비스라도 그 서비스가 외부 입력을 그대로 전달했다면 그 값은 외부 입력이다.

### 입력 검증: 경계에서 한 번, 스키마로

검증의 원칙은 두 가지다. 첫째, **경계(boundary)에서 한 번에 검증한다.** 핸들러 내부 곳곳에서 `if (!x) throw`를 흩뿌리면 어느 경로가 검증되었는지 아무도 모른다. 둘째, **허용 목록 방식이다.** 나쁜 값을 걸러내는 것이 아니라 좋은 값의 모양을 정의하고 나머지를 전부 거부한다(16장 참조).

```js
import { z } from 'zod'

// 스키마가 곧 계약이다. 모르는 필드는 통과시키지 않는다.
const CreateOrderSchema = z.object({
  productId: z.string().uuid(),
  quantity: z.number().int().min(1).max(100),
  couponCode: z.string().regex(/^[A-Z0-9]{4,16}$/).optional(),
  note: z.string().max(500).optional()
}).strict()   // strict: 정의되지 않은 키가 있으면 거부

app.post('/orders', async (req, res) => {
  const parsed = CreateOrderSchema.safeParse(req.body)
  if (!parsed.success) {
    // 내부 스키마 구조를 그대로 노출하지 않는다
    return res.status(400).json({ error: 'invalid_request' })
  }
  // 이 지점 이후로 parsed.data는 타입과 범위가 보장된 값이다
  const order = await createOrder(parsed.data)
  res.status(201).json(order)
})
```

`.strict()`가 중요하다. 알 수 없는 필드를 조용히 무시하면, 나중에 그 객체를 데이터베이스나 다른 서비스에 그대로 전달할 때 의도하지 않은 필드가 함께 흘러간다(이른바 대량 할당, mass assignment). 반대로 출력에서도 허용 목록을 쓴다. 사용자 객체를 통째로 `res.json(user)` 하면 언젠가 누군가 `passwordHash` 컬럼을 추가한 날 그것이 API로 나간다.

### 프로토타입 오염

프로토타입 오염(prototype pollution)은 JavaScript 고유의 문제다. 공격자가 제어하는 JSON에 `__proto__`, `constructor`, `prototype` 키를 넣고, 애플리케이션이 그것을 재귀적으로 병합(deep merge)하면 `Object.prototype`이 오염된다. 그 이후로는 프로그램 전체의 모든 객체가 오염된 속성을 상속받는다. 권한 검사에 쓰이는 `if (user.isAdmin)`이 `Object.prototype.isAdmin = true` 하나로 무너지는 식이다.

`JSON.parse` 자체는 `__proto__`를 일반 키로 만들 뿐 프로토타입을 바꾸지 않는다. 위험한 것은 그 결과를 병합·할당하는 코드다.

```js
// 위험: 재귀 병합이 __proto__ 키를 그대로 따라간다
function unsafeMerge(target, source) {
  for (const key of Object.keys(source)) {
    if (typeof source[key] === 'object' && source[key] !== null) {
      target[key] ??= {}
      unsafeMerge(target[key], source[key])   // key가 '__proto__'면 전역 오염
    } else {
      target[key] = source[key]
    }
  }
  return target
}
```

방어는 세 겹이다.

```js
const FORBIDDEN = new Set(['__proto__', 'constructor', 'prototype'])

// 1) 위험한 키를 차단한다
function safeMerge(target, source) {
  for (const key of Object.keys(source)) {
    if (FORBIDDEN.has(key)) continue
    const value = source[key]
    if (value !== null && typeof value === 'object' && !Array.isArray(value)) {
      // 2) 중간 객체도 프로토타입 없는 객체로 만든다
      if (typeof target[key] !== 'object' || target[key] === null) {
        target[key] = Object.create(null)
      }
      safeMerge(target[key], value)
    } else {
      // 3) 대입 대신 정의를 써서 세터(setter) 호출을 피한다
      Object.defineProperty(target, key, {
        value, writable: true, enumerable: true, configurable: true
      })
    }
  }
  return target
}

// 사용자 입력으로 만든 맵은 프로토타입 없는 객체나 Map을 쓴다
const lookup = Object.create(null)   // lookup.toString 같은 상속 속성이 없다
```

근본적인 예방은 더 단순하다. **외부 입력을 재귀 병합하지 않는다.** 스키마로 파싱한 뒤 필요한 필드만 명시적으로 꺼내 쓰면 병합 자체가 필요 없다. `Object.freeze(Object.prototype)`으로 전역을 잠그는 방법도 있지만, 일부 라이브러리가 깨질 수 있으므로 통합 테스트로 확인한 뒤 적용한다.

### ReDoS: 정규식이 CPU를 태운다

정규식 서비스 거부(ReDoS, Regular expression Denial of Service)는 역추적(backtracking)이 지수적으로 폭발하는 패턴에 긴 입력을 넣어 이벤트 루프를 정지시키는 공격이다. Node.js는 단일 스레드로 요청을 처리하므로, 정규식 하나가 CPU를 붙잡으면 그 프로세스의 모든 요청이 멈춘다(3장 참조). 데이터베이스도 멀쩡하고 메모리도 여유로운데 응답이 전부 타임아웃되는, 원인 찾기 가장 어려운 장애 유형이다.

위험 신호는 **중첩된 수량자(quantifier)**와 **겹치는 대안(alternation)**이다. `(a+)+`, `(\s*,\s*)*`, `(\w+\s?)*$` 같은 형태에서 매칭 실패 시 경우의 수가 폭발한다.

```js
// 위험한 패턴: 중첩 수량자
const bad = /^(\w+\s?)*$/

// 안전한 방향
// 1) 길이를 먼저 제한한다 — 대부분의 ReDoS는 긴 입력을 필요로 한다
// 2) 수량자 중첩을 없앤다
const good = /^[\w ]{1,64}$/

function validateName(input) {
  if (typeof input !== 'string' || input.length > 64) return false
  return good.test(input)
}
```

운영에서 지켜야 할 규칙은 다음과 같다. 사용자 입력을 정규식 패턴 자체로 받지 않는다(받아야 한다면 이스케이프한다). 정규식은 리뷰 항목에 넣고, `eslint-plugin-security`의 `detect-unsafe-regex`나 전용 분석 도구를 CI에서 돌린다. 복잡한 파싱은 정규식 대신 파서를 쓴다. 그리고 이벤트 루프 지연(event loop delay)을 항상 계측해 두면 ReDoS가 발생했을 때 즉시 보인다(31장 참조).

### 경로 탐색

경로 탐색(path traversal)은 사용자 입력이 파일 경로에 들어갈 때 `../`로 의도한 디렉터리를 벗어나는 공격이다(8장 참조). 정규화만으로는 부족하고, **정규화한 절대 경로가 허용 루트 아래에 있는지 확인**해야 한다.

```js
import path from 'node:path'
import fs from 'node:fs/promises'

const ROOT = path.resolve('/srv/app/public')

async function readPublicFile(userPath) {
  // resolve가 '..'를 해석한 뒤에 검사하는 것이 핵심 순서다
  const resolved = path.resolve(ROOT, userPath)
  const rel = path.relative(ROOT, resolved)
  if (rel.startsWith('..') || path.isAbsolute(rel)) {
    throw new Error('경로가 허용 범위를 벗어남')
  }
  // 심볼릭 링크로 밖을 가리킬 수 있으므로 실제 경로도 확인한다
  const real = await fs.realpath(resolved)
  if (!real.startsWith(ROOT + path.sep)) {
    throw new Error('심볼릭 링크가 허용 범위를 벗어남')
  }
  return fs.readFile(real)
}
```

널 바이트(`\0`)가 포함된 경로는 Node.js가 거부하지만, 입력 검증 단계에서 미리 거르는 편이 낫다. 가장 안전한 설계는 사용자 입력을 경로로 쓰지 않는 것이다. 파일을 식별자(UUID)로 관리하고, 식별자를 경로로 변환하는 매핑을 서버가 소유한다.

### 명령 주입

`exec`와 `execSync`는 셸을 거친다. 즉 입력에 `;`, `|`, `` ` ``, `$()`가 들어가면 별도의 명령이 실행된다(11장 참조). 방어는 이스케이프가 아니라 **셸을 쓰지 않는 것**이다.

```js
import { execFile } from 'node:child_process'
import { promisify } from 'node:util'
const execFileAsync = promisify(execFile)

// 위험: 셸 해석을 거친다
// exec(`convert ${userFile} out.png`)

// 안전: 인자를 배열로 전달하면 셸이 개입하지 않는다
async function convert(inputPath) {
  if (!/^[a-zA-Z0-9_-]+\.(png|jpg)$/.test(path.basename(inputPath))) {
    throw new Error('허용되지 않은 파일 이름')
  }
  return execFileAsync('convert', [inputPath, '-resize', '800x600', 'out.png'], {
    timeout: 10_000,        // 무한 실행 방지
    maxBuffer: 1024 * 1024  // 출력 폭탄 방지
  })
}
```

인자가 `-`로 시작하면 옵션으로 해석된다는 점도 주의한다. 사용자 값이 파일 이름 자리에 들어간다면 `--`로 옵션 끝을 표시하거나 값 앞에 `./`를 붙인다.

### SQL 주입

SQL 주입 방어는 30년째 같은 답이다. **문자열 연결 대신 파라미터화 질의(parameterized query)를 쓴다**(19장 참조).

```js
// 위험
// db.query(`SELECT * FROM users WHERE email = '${email}'`)

// 안전: 값은 별도 채널로 전달되어 SQL 문법으로 해석되지 않는다
const { rows } = await db.query(
  'SELECT id, email FROM users WHERE email = $1 AND tenant_id = $2',
  [email, tenantId]
)
```

파라미터로 바인딩할 수 없는 자리가 문제다. 테이블명, 컬럼명, `ORDER BY` 방향은 값이 아니라 식별자이므로 바인딩되지 않는다. 이때는 반드시 허용 목록으로 매핑한다.

```js
const SORTABLE = { createdAt: 'created_at', price: 'price', name: 'name' }
const DIRECTION = { asc: 'ASC', desc: 'DESC' }

function buildOrderBy(sort, dir) {
  const column = SORTABLE[sort] ?? 'created_at'      // 매핑에 없으면 기본값
  const direction = DIRECTION[String(dir).toLowerCase()] ?? 'DESC'
  return `ORDER BY ${column} ${direction}`           // 값은 코드에서 온 상수뿐
}
```

ORM을 쓴다고 안전해지는 것이 아니다. 대부분의 ORM에는 원시 SQL 탈출구가 있고, 사고는 거기서 난다.

### SSRF

서버측 요청 위조(SSRF, Server-Side Request Forgery)는 "사용자가 준 URL로 서버가 요청을 보내는" 기능이 있을 때 성립한다. 웹훅 등록, 이미지 URL 가져오기, 링크 미리보기가 전형적이다. 서버는 대개 내부망에 있으므로, 공격자는 이 기능을 통해 클라우드 메타데이터 서비스나 내부 관리 API에 접근을 시도한다.

방어는 **호스트 이름 검사가 아니라 실제 접속 대상 IP 검사**여야 한다. DNS는 공격자가 제어하므로 검사 시점과 접속 시점 사이에 응답이 바뀔 수 있다(DNS 리바인딩).

```js
import dns from 'node:dns/promises'
import net from 'node:net'
import http from 'node:http'
import https from 'node:https'

function isPrivateAddress(ip) {
  if (net.isIPv4(ip)) {
    const [a, b] = ip.split('.').map(Number)
    if (a === 10 || a === 127 || a === 0) return true
    if (a === 172 && b >= 16 && b <= 31) return true
    if (a === 192 && b === 168) return true
    if (a === 169 && b === 254) return true   // 클라우드 메타데이터 대역
    return false
  }
  const lower = ip.toLowerCase()
  return lower === '::1' || lower.startsWith('fc') ||
         lower.startsWith('fd') || lower.startsWith('fe80')
}

// 핵심: 소켓이 실제로 연결될 주소를 검사한다.
// lookup 훅에서 막으면 DNS 리바인딩도 함께 차단된다.
const guardedLookup = (hostname, options, callback) => {
  dns.lookup(hostname, { all: true, verbatim: true })
    .then((addresses) => {
      const safe = addresses.filter((a) => !isPrivateAddress(a.address))
      if (safe.length === 0) return callback(new Error('내부 주소로의 요청 차단'))
      callback(null, safe[0].address, safe[0].family)
    })
    .catch(callback)
}

export async function fetchUserUrl(rawUrl) {
  const url = new URL(rawUrl)
  if (url.protocol !== 'https:') throw new Error('https만 허용')   // file:, gopher: 차단

  const agent = new https.Agent({ lookup: guardedLookup })
  const res = await fetch(url, {
    // @ts-expect-error undici dispatcher 또는 agent 옵션은 런타임에 따라 다르다
    agent,
    redirect: 'manual',            // 리다이렉트를 따라가면 검사가 무력화된다
    signal: AbortSignal.timeout(5000)
  })
  if (res.status >= 300 && res.status < 400) throw new Error('리다이렉트 거부')
  return res
}
```

리다이렉트를 수동으로 처리하는 이유는, 자동 추적이 허용된 URL에서 시작해 내부 주소로 이동하는 것을 그대로 허용하기 때문이다. 리다이렉트를 지원해야 한다면 각 홉마다 같은 검사를 반복한다. 가능하다면 외부 요청 전용 프록시나 이그레스(egress) 정책으로 네트워크 계층에서도 함께 막는다.

### 대용량 페이로드와 DoS

크기 제한이 없는 입력은 그 자체로 취약점이다. 본문 크기, 배열 길이, 문자열 길이, 업로드 파일 크기, JSON 중첩 깊이를 전부 제한한다.

```js
import express from 'express'
const app = express()

// 본문 크기 제한: 기본값에 의존하지 말고 명시한다
app.use(express.json({ limit: '100kb' }))

// 압축 폭탄 방어: 압축 해제 후 크기도 제한 대상이다
// (역방향 프록시나 API 게이트웨이 계층에서도 동일 제한을 건다)
```

깊이 제한은 스키마에서 처리한다. 재귀 스키마를 정의할 때 최대 깊이를 두지 않으면 깊게 중첩된 JSON 하나로 스택을 소진시킬 수 있다. 배열 필드에는 항상 `.max(n)`을 붙인다. 그리고 요청 수준의 방어로 속도 제한(rate limiting)과 동시 요청 제한을 둔다(24장 참조).

## 34.3 악성 npm 패키지와 공급망 공격

### 위협의 실제 형태

현대 Node.js 애플리케이션에서 우리가 직접 쓴 코드는 전체 실행 코드의 1% 미만인 경우가 많다. 나머지는 전이 의존성(transitive dependency)이며, 그 코드는 우리 프로세스의 모든 권한을 그대로 가진다. 파일 시스템, 네트워크, 환경 변수 전부에 접근한다. 공급망 공격은 이 사실을 이용한다.

실제로 반복 관측된 형태는 셋이다.

**타이포스쿼팅(typosquatting).** 널리 쓰이는 패키지와 한 글자 다른 이름을 등록한다. `cross-env`와 `crossenv`, 스코프가 빠진 이름 등이다. 오타 한 번, 혹은 AI가 제안한 존재하지 않는 패키지 이름을 그대로 설치하면 걸린다.

**정상 패키지의 악성 버전 게시.** 유지보수자의 npm 계정이 탈취되거나, 번아웃된 유지보수자가 소유권을 넘긴 뒤 새 소유자가 악성 코드를 넣는다. 패키지 이름은 그대로이므로 이름 검사로는 잡히지 않는다. 악성 코드는 대개 다음 마이너/패치 버전에 조용히 들어가고, 캐럿 범위(`^1.2.3`)를 쓰는 모든 사용자가 다음 설치에서 그것을 받는다.

**설치 스크립트.** `preinstall`, `install`, `postinstall` 스크립트는 `npm install` 시점에 임의 코드를 실행한다. 즉 **애플리케이션을 실행하지 않아도, `import`하지 않아도** 코드가 돈다. 개발자 노트북과 CI 러너가 1차 표적이며, 목표는 대개 환경 변수·SSH 키·클라우드 자격 증명 탈취다.

### 방어

**락 파일을 고정하고 CI에서 강제한다.** `package-lock.json`은 정확한 버전과 무결성 해시를 담는다. CI에서는 `npm ci`만 쓴다. `npm install`은 락 파일을 갱신할 수 있지만 `npm ci`는 락 파일과 `package.json`이 어긋나면 실패한다.

```bash
# CI에서는 반드시 이것만 쓴다. 락 파일을 재현 가능하게 설치한다.
npm ci --ignore-scripts

# 락 파일의 무결성 해시가 레지스트리 내용과 맞는지 검증
npm audit signatures
```

**설치 스크립트를 기본 차단한다.** `--ignore-scripts`를 기본값으로 두고, 정말로 스크립트가 필요한 패키지(네이티브 모듈 빌드 등)만 예외로 관리한다.

```ini
# .npmrc — 저장소에 커밋해 팀 전체에 적용한다
ignore-scripts=true
audit-level=high
provenance=true
```

스크립트 차단으로 깨지는 패키지가 있다면, 그 패키지가 설치 시점에 무엇을 하는지 확인하는 것 자체가 유용한 검토다. 대개 바이너리 다운로드이며, 그것은 곧 "설치할 때 인터넷에서 실행 파일을 받아 온다"는 뜻이다.

**의존성 수를 줄인다.** 가장 효과 큰 방어는 코드를 덜 가져오는 것이다. 열 줄이면 되는 유틸리티에 패키지를 추가하지 않는다. 표준 라이브러리로 가능한지 먼저 본다. 현대 Node.js는 과거에 패키지가 필요했던 상당 부분을 내장한다. `node:test`(테스트 러너), `fetch`(HTTP 클라이언트), `structuredClone`(깊은 복사), `crypto.randomUUID`, `AbortSignal.timeout`, `util.parseArgs`, `--env-file` 등이다.

**게시 프로비넌스(provenance)를 확인한다.** npm은 패키지가 어느 저장소의 어느 커밋에서, 어떤 CI 워크플로로 빌드되었는지 증명하는 서명된 출처 정보를 지원한다. 프로비넌스가 있는 패키지는 유지보수자의 로컬 노트북이 아니라 검증 가능한 파이프라인에서 나왔다는 뜻이다.

```bash
# 우리 패키지를 게시할 때 프로비넌스를 붙인다 (CI에서 실행)
npm publish --provenance --access public
```

**사내 레지스트리 프록시를 둔다.** 업스트림 npm을 캐싱하는 프록시(Verdaccio, Artifactory 등)를 두면 세 가지를 얻는다. 첫째, 패키지 삭제나 레지스트리 장애로부터 빌드를 보호한다. 둘째, 어떤 패키지가 조직에 들어왔는지 중앙에서 관측한다. 셋째, 차단 목록과 격리 기간(예: 게시 후 N일이 지난 버전만 허용) 정책을 적용할 수 있다. 악성 버전은 대개 며칠 안에 발견되고 내려가므로, 이 지연 정책 하나가 상당한 방어가 된다(33장 참조).

### 새 의존성 도입 체크리스트

의존성 추가는 코드 리뷰 항목이어야 한다. 다음을 확인한다.

- 이 기능이 정말 필요한가. 표준 라이브러리나 이미 있는 의존성으로 되는가.
- 유지보수 상태는 어떤가. 최근 커밋, 미해결 이슈, 유지보수자 수.
- 전이 의존성이 몇 개 늘어나는가. `npm ls --all` 또는 설치 전 영향 확인.
- 설치 스크립트가 있는가. 있다면 무엇을 하는가.
- 네트워크나 파일 시스템에 접근하는가. 그럴 이유가 있는 패키지인가.
- 라이선스가 조직 정책에 맞는가.
- 다운로드 수와 이름이 유명 패키지와 헷갈리게 비슷하지 않은가.
- 프로비넌스 정보가 있는가.

## 34.4 애플리케이션 설정: 환경 변수, 설정 파일, 시크릿

### 설정은 코드가 아니라 환경에서 온다

12-factor 원칙의 세 번째 항목은 "설정을 환경에 저장하라"이다. 핵심 판별 기준은 단순하다. **배포 환경마다 달라지는 값은 설정이고, 어느 환경에서나 같은 값은 코드다.** 데이터베이스 URL, 외부 API 엔드포인트, 기능 플래그 기본값, 로그 레벨은 설정이다. 재시도 횟수의 기본값이나 라우팅 규칙은 대개 코드다.

이 구분을 지키면 같은 아티팩트(컨테이너 이미지)를 스테이징과 프로덕션에 그대로 배포할 수 있다. 반대로 `if (process.env.NODE_ENV === 'production')` 분기가 코드 곳곳에 흩어지면, 스테이징에서 통과한 코드 경로와 프로덕션에서 실행되는 코드 경로가 달라진다. 테스트되지 않은 경로가 프로덕션에서만 도는 것이야말로 가장 흔한 사고 원인이다. 환경 분기는 설정 로딩 지점 한 곳에 모으고, 나머지 코드는 값만 본다.

### 환경 변수의 한계

환경 변수는 편리하지만 비밀 저장소로서는 한계가 뚜렷하다.

**첫째, 프로세스 목록과 진단 출력에 노출된다.** `/proc/<pid>/environ`은 같은 사용자 권한이면 읽을 수 있다. 컨테이너 검사 명령(`docker inspect`, `kubectl describe pod`)에도 값이 그대로 나온다. 크래시 리포터나 APM 에이전트가 환경 전체를 수집해 외부로 전송하는 경우도 있다.

**둘째, 자식 프로세스에 상속된다.** `child_process.spawn`은 기본적으로 부모의 `process.env` 전체를 넘긴다. 이미지 변환 도구를 실행하려고 만든 자식 프로세스가 데이터베이스 비밀번호와 결제 API 키를 전부 받는다. 필요한 것만 명시적으로 넘긴다.

```js
import { execFile } from 'node:child_process'

// 위험: 부모 환경 전체 상속
// execFile('ffmpeg', args)

// 안전: 환경을 명시적으로 구성한다
execFile('ffmpeg', args, {
  env: {
    PATH: process.env.PATH,
    HOME: process.env.HOME,
    TMPDIR: process.env.TMPDIR ?? '/tmp'
  }
})
```

**셋째, 회전이 어렵다.** 환경 변수는 프로세스 시작 시점에 고정되므로, 키를 회전하려면 재배포가 필요하다. 짧은 수명의 자격 증명을 쓰려면 실행 중에 다시 읽을 수 있는 경로(마운트된 파일, 시크릿 매니저 SDK)가 필요하다.

그래서 실무 권장은 이렇다. 비밀이 아닌 설정은 환경 변수로, 비밀은 **파일로 마운트하거나 시크릿 매니저에서 런타임에 가져온다.** 파일 마운트는 환경 변수보다 노출 표면이 좁고 회전 시 파일만 갱신하면 된다.

```js
import fs from 'node:fs'

// 값 자체 또는 값이 담긴 파일 경로 둘 다 지원하는 패턴
function readSecret(name) {
  const filePath = process.env[`${name}_FILE`]
  if (filePath) return fs.readFileSync(filePath, 'utf8').trim()
  const inline = process.env[name]
  if (inline) return inline
  throw new Error(`시크릿 ${name}이(가) 설정되지 않음`)
}
```

### Kubernetes Secret의 base64는 암호화가 아니다

반드시 짚어야 할 오해가 있다. Kubernetes `Secret` 오브젝트의 값이 base64로 인코딩되어 있다는 사실은 보안과 아무 관계가 없다. base64는 바이너리를 텍스트로 옮기기 위한 인코딩이며, 키 없이 누구나 되돌린다. 기본 설정에서 Secret은 etcd에 평문으로 저장되고, 네임스페이스에 대한 읽기 권한이 있는 사람은 그대로 읽는다.

제대로 하려면 셋 중 하나 이상이 필요하다. etcd 저장 시 암호화(encryption at rest) 활성화, RBAC로 Secret 읽기 권한을 최소화, 그리고 외부 시크릿 저장소(HashiCorp Vault, AWS Secrets Manager, GCP Secret Manager 등)를 External Secrets Operator나 CSI 드라이버로 연동하는 것이다. 외부 저장소를 쓰면 회전 자동화, 접근 감사 로그, 짧은 수명 자격 증명 같은 것들을 함께 얻는다.

또한 시크릿을 컨테이너 이미지에 넣지 않는다. 이미지 레이어는 캐시되고 배포되며, `ARG`로 전달한 값도 빌드 히스토리에 남을 수 있다.

### 시작 시 설정을 검증한다

잘못된 설정으로 인한 장애의 특징은, **문제가 배포 직후가 아니라 그 설정을 처음 쓰는 코드 경로가 실행될 때 드러난다**는 점이다. 오타 난 큐 이름은 첫 메시지 발행 시점에, 빠뜨린 API 키는 첫 결제 시점에 터진다. 이것을 막는 방법은 하나다. **프로세스 시작 시 전체 설정을 스키마로 검증하고, 실패하면 즉시 종료한다.**

```js
// config.js — 애플리케이션에서 process.env를 읽는 유일한 파일
import { z } from 'zod'

const ConfigSchema = z.object({
  NODE_ENV: z.enum(['development', 'test', 'production']),
  PORT: z.coerce.number().int().min(1).max(65535).default(3000),
  DATABASE_URL: z.string().url(),
  REDIS_URL: z.string().url(),
  JWT_SECRET: z.string().min(32, 'JWT_SECRET은 32자 이상이어야 한다'),
  LOG_LEVEL: z.enum(['debug', 'info', 'warn', 'error']).default('info'),
  EXTERNAL_API_TIMEOUT_MS: z.coerce.number().int().positive().default(5000)
})

const parsed = ConfigSchema.safeParse(process.env)
if (!parsed.success) {
  // 값은 절대 출력하지 않는다. 어떤 키가 왜 틀렸는지만 알린다.
  for (const issue of parsed.error.issues) {
    console.error(`설정 오류: ${issue.path.join('.')} — ${issue.message}`)
  }
  process.exit(1)   // 잘못된 설정으로는 시작조차 하지 않는다
}

export const config = Object.freeze(parsed.data)
```

이 파일을 두면 부수 효과가 여럿 생긴다. `process.env` 참조가 한 곳에 모이므로 어떤 설정이 존재하는지 스키마만 보면 알 수 있다. 타입이 강제되므로 `PORT`가 문자열 `"3000"`인 채로 흘러다니지 않는다. 그리고 `Object.freeze`로 런타임 변조를 막는다. Node.js 20 이상의 `--env-file=.env` 플래그를 쓰면 개발 환경에서 별도 라이브러리 없이 `.env`를 읽을 수 있다. 다만 프로덕션에서는 `.env` 파일이 아니라 오케스트레이터가 주입한 값을 쓴다.

## 34.5 의존성 업그레이드와 취약점 대응

### 취약점 대응 절차

취약점 공지를 받았을 때 필요한 것은 즉흥적 판단이 아니라 정해진 절차다. 절차가 없으면 두 가지 실패 모드로 간다. 모든 경고에 즉시 반응하다가 개발이 멈추거나, 전부 무시하다가 실제로 중요한 것을 놓친다.

**1단계: 알림 수신.** `npm audit`을 CI에 넣고, GitHub의 Dependabot 알림이나 GitHub Advisory Database를 구독한다. 알림 경로가 개인 이메일 한 곳뿐이면 그 사람이 휴가일 때 절차가 멈춘다. 팀 채널로 보낸다.

**2단계: 영향 판단.** 가장 중요한 단계이고 가장 자주 생략되는 단계다. 질문은 "이 취약점이 우리 실행 경로에 있는가"다. 확인할 것은 다음과 같다.

- 취약한 코드 경로를 실제로 호출하는가. 예를 들어 서버측 렌더링에만 있는 XSS 취약점은 그 기능을 쓰지 않으면 해당되지 않는다.
- 취약점이 어떤 입력을 요구하는가. 신뢰할 수 없는 입력이 그 지점에 도달하는가.
- 개발 의존성인가 런타임 의존성인가. 빌드 도구의 취약점은 심각도가 다르지만 0은 아니다. CI가 공격당하면 배포되는 모든 것이 오염된다.

```bash
# 어떤 경로로 그 패키지가 들어왔는지 추적한다
npm ls minimist

# 프로덕션 의존성만 감사한다
npm audit --omit=dev

# 기계 판독용 출력으로 심각도별 처리
npm audit --json --audit-level=high
```

CVSS 점수만 보고 판단하지 않는다. 점수는 최악의 시나리오를 가정하며 우리 맥락을 모른다. 판단 결과와 근거를 기록으로 남긴다. 6개월 뒤 같은 경고를 다시 만났을 때 처음부터 조사하지 않기 위해서다.

**3단계: 패치 적용.** 패치 버전이 있으면 올린다. 전이 의존성이라 직접 올릴 수 없으면 `overrides`로 강제한다.

```json
{
  "overrides": {
    "vulnerable-lib": "^2.4.1"
  }
}
```

`overrides`는 상위 패키지가 요구하는 범위를 무시하고 버전을 고정하므로, 적용 후 반드시 통합 테스트를 돌린다. 임시 조치임을 주석이나 이슈로 남기고, 상위 패키지가 정식으로 올라가면 제거한다.

**4단계: 패치가 없을 때의 완화.** 유지보수가 끊긴 패키지에는 패치가 오지 않는다. 선택지는 다음과 같다.

- **우회.** 취약한 함수 대신 다른 API를 쓰거나, 호출 전에 입력을 제한한다.
- **격리.** 해당 처리를 별도 프로세스나 워커로 옮겨 폭발 반경을 줄인다(34.7절 참조).
- **기능 비활성화.** 위험 대비 가치가 낮은 기능이면 끈다. 이것도 정당한 답이다.
- **교체 또는 내재화.** 대안 패키지로 옮기거나, 쓰는 부분이 작다면 직접 구현해 의존성을 제거한다.

### 자동화와 자동 병합의 조건

Dependabot이나 Renovate로 업그레이드 PR을 자동 생성하면, 업그레이드가 "가끔 하는 큰 작업"에서 "항상 도는 작은 작업"으로 바뀐다. 이 차이가 핵심이다. 6개월 묵힌 업그레이드는 위험하고 오래 걸리지만, 주 단위 업그레이드는 대개 몇 분이다.

```yaml
# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: npm
    directory: "/"
    schedule:
      interval: weekly
    open-pull-requests-limit: 10
    groups:
      # 패치 업데이트는 하나의 PR로 묶어 리뷰 부담을 줄인다
      patch-updates:
        update-types: ["patch"]
      dev-dependencies:
        dependency-type: "development"
    ignore:
      # 메이저는 사람이 계획해서 올린다
      - dependency-name: "*"
        update-types: ["version-update:semver-major"]
```

자동 병합(auto-merge)은 조건을 갖췄을 때만 켠다. 다음이 전부 참이어야 한다.

- CI가 실질적인 신뢰도를 제공한다. 단위·통합 테스트가 실제 동작을 검증하며 커버리지가 의미 있는 수준이다(30장, 33장 참조).
- 대상이 패치 또는 마이너 업데이트다. 메이저는 사람이 본다.
- 배포 파이프라인에 롤백 수단이 있고, 카나리 또는 단계적 배포로 문제를 조기에 잡는다(33장 참조).
- 락 파일 무결성 검증(`npm audit signatures`)이 파이프라인에 있다.

이 조건이 갖춰지지 않았다면 자동 병합은 검증되지 않은 코드를 자동으로 프로덕션에 넣는 장치가 된다. 자동화의 전제는 언제나 신뢰할 수 있는 검증이다.

## 34.6 Node.js LTS 일정과 업그레이드 전략

### 릴리스 라인의 구조

Node.js 릴리스는 규칙이 명확하다. 매년 4월 짝수 메이저 버전이, 10월 홀수 메이저 버전이 나온다. **짝수 버전만 LTS(Long Term Support)가 된다.** 홀수 버전은 6개월간 Current로만 유지되고 끝난다. 즉 프로덕션에는 짝수 버전만 쓴다.

짝수 버전의 수명은 세 단계다.

| 단계 | 기간 | 들어오는 변경 |
| --- | --- | --- |
| Current | 릴리스 후 약 6개월 | 새 기능, 준수한 범위의 변경 |
| Active LTS | 10월부터 약 12개월 | 버그 수정, 보안 수정, 저위험 기능 백포트 |
| Maintenance LTS | 이후 약 12개월 | 심각한 버그와 보안 수정만 |
| EOL | 그 이후 | 없음. 보안 수정도 없다 |

결과적으로 각 LTS 버전은 최초 릴리스로부터 약 30개월간 지원된다. 매년 새 LTS가 등장하므로, 항상 두세 개의 지원 버전이 겹쳐 존재한다. 이 겹치는 구간이 업그레이드 창(window)이다.

### EOL 버전을 쓰는 것 자체가 취약점이다

EOL(End of Life)에 도달한 Node.js 버전에는 **보안 패치가 나오지 않는다.** 이후 발견되는 V8, OpenSSL, HTTP 파서, 의존 라이브러리의 취약점은 그 버전에서 영원히 고쳐지지 않는다. 그리고 공지는 공개되므로, 어떤 취약점이 어떤 버전에 존재하는지는 누구나 안다.

이것이 왜 심각한지는 계층을 보면 분명하다. 애플리케이션 코드의 취약점은 우리가 고칠 수 있고, 의존성 취약점은 버전을 올려 고칠 수 있다. 그러나 런타임 자체의 취약점은 런타임을 올리는 것 외에 방법이 없다. 예를 들어 HTTP 요청 밀반입(request smuggling)이나 TLS 처리 결함은 애플리케이션 코드로 우회할 수 없다.

부가적인 대가도 크다. 최신 라이브러리들이 EOL 버전 지원을 끊으므로 의존성도 함께 낡는다. 그러면 의존성 취약점 패치도 받을 수 없게 되고, 결국 "런타임을 못 올려서 라이브러리를 못 올리고, 라이브러리를 못 올려서 취약점을 못 고치는" 상태로 굳는다. 그 상태에서의 업그레이드는 몇 배 비싸진다.

### 업그레이드를 정기 작업으로 만든다

업그레이드를 사건이 아니라 일정으로 만드는 절차는 다음과 같다.

**1. 현재 버전을 명시적으로 고정한다.** 어떤 버전으로 도는지 여러 곳에서 일관되게 선언한다.

```json
{
  "engines": { "node": ">=20.11.0 <23" }
}
```

```bash
# .nvmrc — 개발 환경
20.11.0
```

```dockerfile
# Dockerfile — 프로덕션. 태그를 다이제스트까지 고정하면 재현성이 올라간다
FROM node:20.11.0-bookworm-slim
```

세 곳이 서로 다르면 "로컬에서는 되는데" 문제가 생긴다. CI에서 일치를 검사한다.

**2. 새 LTS가 Active가 되면 CI에 매트릭스로 추가한다.** 정식 이전 전에 호환성 문제를 미리 발견한다.

```yaml
strategy:
  matrix:
    node: ['20.x', '22.x']   # 현재 운영 버전과 다음 LTS를 함께 테스트
```

**3. 분기마다 점검일을 잡는다.** 릴리스 일정을 캘린더에 넣고, EOL 3~6개월 전에 이전을 시작한다. 마감에 몰려 하는 업그레이드가 위험한 업그레이드다.

**4. 이전 시 확인할 것.** 네이티브 모듈은 V8 ABI가 바뀌면 재빌드가 필요하다(N-API를 쓰는 모듈은 대체로 안전하다). 제거·비권장(deprecated)된 API를 확인하고, `NODE_OPTIONS`와 V8 플래그가 여전히 유효한지 본다. 그리고 부하 테스트로 성능 회귀를 확인한다. 메이저 업그레이드는 대개 성능이 좋아지지만, GC 동작 변화로 메모리 프로파일이 달라질 수 있다(28장 참조).

## 34.7 런타임 권한 모델과 샌드박싱

### Node.js 권한 모델

Node.js 20에서 도입된 권한 모델(permission model)은 프로세스가 접근할 수 있는 자원을 플래그로 제한한다. 기존의 "실행된 코드는 프로세스의 모든 권한을 가진다"는 전제를 처음으로 좁힌 기능이다.

```bash
# 파일 시스템 접근을 명시한 경로로만 제한하고,
# 자식 프로세스 생성과 네이티브 애드온 로딩을 차단한다
node --permission \
     --allow-fs-read=/srv/app \
     --allow-fs-read=/etc/ssl/certs \
     --allow-fs-write=/var/log/app \
     app.js
```

권한 모델이 켜지면 기본적으로 파일 시스템 읽기·쓰기, 자식 프로세스 생성(`--allow-child-process`), 워커 스레드 생성(`--allow-worker`), 네이티브 애드온 로딩(`--allow-addons`)이 모두 차단되고, 명시한 것만 허용된다. 허용되지 않은 접근은 `ERR_ACCESS_DENIED` 오류로 실패한다.

효과는 실재한다. 악성 전이 의존성이 `~/.ssh/id_rsa`를 읽으려 하거나 `curl`을 실행하려 할 때, 권한 모델이 그것을 막는다. 그러나 한계를 정확히 알아야 한다.

**첫째, 네트워크는 제어 대상이 아니다.** 현재 권한 모델에는 네트워크 접근을 제한하는 플래그가 없다. 데이터 유출(exfiltration)의 주 경로가 네트워크이므로 이것은 큰 공백이다. 네트워크 제한은 컨테이너 네트워크 정책이나 이그레스 방화벽으로 해야 한다.

**둘째, 프로세스 단위이지 모듈 단위가 아니다.** 우리 코드와 의존성이 같은 권한을 공유한다. "이 패키지만 파일 접근 금지" 같은 세분화는 불가능하다.

**셋째, 여전히 안정성 등급이 낮고 우회 가능성이 보고되어 왔다.** 심층 방어(defense in depth)의 한 겹으로 쓰되, 이것 하나에 의존하지 않는다.

### vm 모듈은 샌드박스가 아니다

이 절에서 가장 중요한 문장이다. **`node:vm` 모듈은 보안 경계가 아니다.** 공식 문서가 명시적으로 그렇게 말한다. `vm`은 별개의 전역 컨텍스트에서 코드를 실행할 뿐, 신뢰할 수 없는 코드를 격리하도록 설계되지 않았다.

이유는 구조적이다. 컨텍스트 안의 코드는 자신에게 전달된 객체를 통해 바깥 realm의 함수와 프로토타입 체인에 도달할 수 있고, 거기서 생성자를 타고 올라가면 결국 호스트의 실행 능력에 닿는다. 알려진 탈출 경로가 하나 막히면 다른 경로가 발견되는 식이 반복되어 왔다. 이는 특정 버그가 아니라 설계 목적의 문제다.

같은 이유로 `vm2` 같은 "안전한 vm" 라이브러리들도 반복적으로 치명적 탈출 취약점이 보고되었고, 대표적인 프로젝트는 결국 유지보수를 중단하며 "이 접근 자체가 안전할 수 없다"고 공지했다. 무한 루프 방지(`timeout` 옵션)조차 완전하지 않다. 동기 루프는 중단할 수 있어도, 코드가 다른 방식으로 자원을 소진하는 것은 막지 못한다.

`vm`이 적절한 용도는 **신뢰하는 코드**를 별도 전역에서 평가할 때다. 설정 파일 평가, 템플릿 컴파일, 테스트 도구의 모듈 로딩 같은 것들이다. 입력이 신뢰할 수 없다면 다른 수단이 필요하다.

### 진짜 격리 수단

신뢰할 수 없는 코드를 실행해야 한다면, 격리는 JavaScript 계층이 아니라 그 아래에서 이루어져야 한다. 선택지는 셋이다.

**1. 별도 프로세스 + OS 수준 격리.** 코드를 전용 프로세스에서 실행하고, OS가 제공하는 제한을 건다. 별도 사용자, seccomp 프로파일, cgroup 기반 CPU·메모리 제한, 네트워크 네임스페이스 분리, 읽기 전용 파일 시스템. 프로세스는 죽여도 되는 대상이므로 타임아웃 처리가 확실하다.

```js
import { fork } from 'node:child_process'

// 격리된 자식에서 실행하고, 시간 초과 시 강제 종료한다.
// 워커 스레드는 같은 프로세스를 공유하므로 이 목적에는 적합하지 않다.
function runIsolated(taskPath, payload, timeoutMs = 3000) {
  return new Promise((resolve, reject) => {
    const child = fork(taskPath, {
      execArgv: [
        '--permission',
        '--allow-fs-read=/srv/sandbox',
        '--max-old-space-size=128'   // 메모리 상한
      ],
      env: {},                       // 환경 변수를 물려주지 않는다
      cwd: '/srv/sandbox',
      stdio: ['ignore', 'pipe', 'pipe', 'ipc']
    })

    const timer = setTimeout(() => {
      child.kill('SIGKILL')          // 협조를 기대하지 않는다
      reject(new Error('실행 시간 초과'))
    }, timeoutMs)

    child.once('message', (result) => {
      clearTimeout(timer)
      child.kill('SIGKILL')
      resolve(result)
    })
    child.once('error', (err) => { clearTimeout(timer); reject(err) })
    child.send(payload)
  })
}
```

**2. 컨테이너 또는 마이크로VM.** 실행 단위마다 컨테이너를 띄우면 파일 시스템·네트워크·프로세스 네임스페이스가 분리된다. 커널을 공유한다는 한계가 있으므로, 적대적 입력을 다룬다면 gVisor나 Firecracker 같은 마이크로VM으로 커널 경계까지 분리하는 편이 낫다. 대가는 시작 지연과 운영 복잡도다.

**3. WebAssembly.** WASM은 애초에 능력 기반(capability-based) 모델로 설계되었다. 모듈은 호스트가 명시적으로 넘겨준 임포트 외에는 아무것도 할 수 없다. 파일 시스템도, 네트워크도, 시스템 시간도 주지 않으면 접근 경로 자체가 없다. 메모리는 선형 메모리로 분리되고, 연료(fuel) 개념으로 실행량을 제한하는 런타임도 있다. 사용자 정의 로직(플러그인, 규칙 스크립트)을 실행하는 용도라면 현재 가장 견고한 선택이다. 다만 실행할 코드를 WASM으로 컴파일해야 하므로 임의의 JavaScript를 그대로 받는 시나리오에는 바로 맞지 않는다.

선택 기준은 단순하다. 신뢰할 수 없는 코드가 임의 JavaScript이고 성능이 중요하지 않다면 별도 프로세스에 컨테이너 격리를 더한다. 제한된 계산 로직이라면 WASM이 낫다. 그리고 어떤 경우에도 **네트워크 이그레스를 기본 차단**한다. 코드가 무엇을 계산하든, 밖으로 내보내지 못하면 유출은 일어나지 않는다.

## 34.8 프로덕션 보안 체크리스트

항목마다 왜 필요한지 한 줄 근거를 붙인다. 근거 없이 관행으로만 따르는 항목은 상황이 바뀌었을 때 잘못 적용된다.

**저장소와 비밀**

- [ ] CI에 비밀 스캐닝이 있고 실패 시 머지가 막힌다 — 사람의 주의력은 방어선이 되지 못한다.
- [ ] 커밋된 적 있는 비밀은 전부 회전되었다 — 푸시된 순간 이미 여러 곳에 복제되었다.
- [ ] 로거에 편집 규칙이 있다 — 로그는 장기 보관되고 널리 전송되므로 유출 범위가 가장 넓다.
- [ ] 오류 응답에 스택 트레이스와 내부 경로가 없다 — 내부 구조 노출은 다음 공격의 재료다.

**입력과 공격 표면**

- [ ] 모든 외부 입력이 경계에서 스키마로 검증되고 미지 필드를 거부한다 — 검증되지 않은 필드는 언젠가 하류로 흘러간다.
- [ ] 외부 입력을 재귀 병합하지 않는다 — 프로토타입 오염의 유일한 진입 경로다.
- [ ] 정규식이 리뷰 대상이고 입력 길이 제한이 선행한다 — ReDoS는 단일 스레드 전체를 정지시킨다.
- [ ] 사용자 입력이 파일 경로로 쓰이지 않거나 루트 검사가 있다 — 정규화 후 검사만이 `..`를 막는다.
- [ ] 셸을 쓰는 API(`exec`) 대신 `execFile`을 쓴다 — 셸 메타문자 해석이 없으면 명령 주입도 없다.
- [ ] 모든 SQL이 파라미터화되어 있고 식별자는 허용 목록으로 매핑된다 — 값과 코드를 분리하는 것이 유일한 근본 방어다.
- [ ] 사용자 URL로 요청 보내기 전 실제 연결 IP를 검사하고 리다이렉트를 수동 처리한다 — DNS는 공격자가 제어한다.
- [ ] 본문 크기, 배열 길이, 중첩 깊이, 업로드 크기에 상한이 있다 — 제한 없는 입력은 그 자체로 DoS 벡터다.
- [ ] 속도 제한과 인증 실패 제한이 있다 — 자동화된 시도는 비용이 들어야 멈춘다.
- [ ] 보안 헤더(HSTS, CSP, `X-Content-Type-Options`)를 설정했다 — 브라우저 클라이언트의 피해 범위를 줄인다.

**의존성**

- [ ] CI가 `npm ci`만 쓰고 락 파일이 커밋되어 있다 — 재현 가능한 설치가 모든 검증의 전제다.
- [ ] `ignore-scripts=true`가 기본이며 예외가 문서화되어 있다 — 설치만으로 코드가 실행되는 경로를 막는다.
- [ ] `npm audit signatures`가 파이프라인에 있다 — 레지스트리 내용이 락 파일 해시와 맞는지 확인한다.
- [ ] 새 의존성 도입에 리뷰 체크리스트가 있다 — 의존성 추가는 신뢰 결정이지 편의 결정이 아니다.
- [ ] Dependabot/Renovate가 주 단위로 돌고 있다 — 작게 자주 하면 업그레이드가 위험한 사건이 되지 않는다.

**설정과 런타임**

- [ ] `process.env`를 읽는 곳이 한 파일이고 시작 시 스키마 검증 후 실패하면 종료한다 — 잘못된 설정은 배포 시점에 드러나야 한다.
- [ ] 비밀은 이미지에 없고, 외부 시크릿 저장소나 마운트된 파일로 주입된다 — base64는 암호화가 아니다.
- [ ] 자식 프로세스에 환경 전체를 상속시키지 않는다 — 이미지 변환 도구가 결제 키를 알 이유가 없다.
- [ ] 운영 중인 Node.js가 EOL이 아니고 다음 LTS가 CI 매트릭스에 있다 — 런타임 취약점은 코드로 우회할 수 없다.
- [ ] 컨테이너를 비루트(non-root) 사용자로, 읽기 전용 루트 파일 시스템으로 실행한다 — 침해 후 활동 범위를 줄인다.
- [ ] 네트워크 이그레스가 기본 차단이고 필요한 대상만 허용된다 — 유출은 밖으로 나가는 경로가 있어야 성립한다.
- [ ] 신뢰할 수 없는 코드는 `vm`이 아니라 별도 프로세스와 OS 격리로 실행된다 — `vm`은 보안 경계가 아니다.

**운영**

- [ ] 인증·권한 결정과 관리자 행위가 감사 로그로 남는다 — 사고 조사는 로그가 있어야 가능하다.
- [ ] 취약점 대응 절차와 담당이 문서화되어 있다 — 절차 없는 대응은 과잉 반응이나 무시로 귀결된다.
- [ ] 배포 롤백 경로가 검증되어 있다 — 가장 빠른 완화책은 대개 되돌리기다.
- [ ] 보안 사고 시 연락 경로와 키 회전 절차를 실제로 리허설했다 — 처음 해보는 절차는 사고 중에 작동하지 않는다.

## 요약

- 비밀이 저장소에 들어가는 경로는 하드코딩, `.env` 커밋, 로그, 테스트 픽스처 네 가지이며, 한 번 푸시된 비밀은 히스토리에서 지우더라도 유출로 간주하고 즉시 회전해야 한다. 회전이 1순위이고 히스토리 정리는 그 다음이다.
- Node.js 웹 서비스의 공격 표면은 스키마 기반 입력 검증으로 좁힌다. 프로토타입 오염은 외부 입력을 재귀 병합하지 않는 것으로, ReDoS는 길이 제한과 수량자 중첩 제거로, 경로 탐색은 정규화 후 루트 검사로, 명령 주입은 `execFile`로, SQL 주입은 파라미터화로, SSRF는 실제 연결 IP 검사와 리다이렉트 수동 처리로 막는다.
- 공급망 공격은 타이포스쿼팅, 계정 탈취 후 악성 버전 게시, 설치 스크립트라는 세 형태로 나타난다. 락 파일 고정과 `npm ci`, `ignore-scripts`, 의존성 수 축소, 프로비넌스 검증, 사내 레지스트리 프록시의 격리 기간 정책이 방어의 축이다.
- 설정은 환경에서 주입하되 환경 변수의 한계(프로세스 목록 노출, 자식 프로세스 상속, 회전 곤란)를 인식하고, 비밀은 마운트된 파일이나 외부 시크릿 저장소로 다룬다. Kubernetes Secret의 base64는 암호화가 아니다. 시작 시 설정 스키마를 검증해 잘못된 설정으로는 프로세스가 뜨지 못하게 한다.
- 취약점 대응은 알림 수신, 실제 실행 경로 기준 영향 판단, 패치 적용, 패치가 없을 때의 완화(우회·격리·기능 비활성화) 순으로 절차화한다. 자동 병합은 신뢰할 수 있는 CI와 롤백 경로가 갖춰졌을 때만 켠다.
- 짝수 메이저 버전만 LTS가 되며 약 30개월 지원된다. EOL 버전은 보안 패치를 받지 못하고 런타임 취약점은 애플리케이션 코드로 우회할 수 없으므로, EOL 사용 자체가 취약점이다. 업그레이드는 사건이 아니라 일정이어야 한다.
- `--permission` 권한 모델은 파일 시스템과 자식 프로세스를 제한하지만 네트워크는 다루지 못하고 프로세스 단위로만 동작한다. `node:vm`은 샌드박스가 아니다. 신뢰할 수 없는 코드의 진짜 격리는 별도 프로세스와 OS 수준 제한, 컨테이너/마이크로VM, WASM으로 이루어진다.

## 연습문제

1. 사용자가 등록한 웹훅 URL로 이벤트를 전송하는 기능을 구현하라. 요구사항은 다음과 같다. `https`만 허용하고, 실제 연결 대상 IP가 사설 대역이나 링크 로컬 대역이면 거부하며, 리다이렉트를 따라가지 않고, 5초 타임아웃과 응답 본문 크기 상한을 둔다. 그리고 이 구현이 DNS 리바인딩을 어떻게 막는지 세 문장으로 설명하라.

2. 다음 두 조각이 왜 위험한지 각각 설명하고 안전하게 고쳐라. (a) 사용자 프로필 업데이트에서 `Object.assign(user, req.body)`로 요청 본문을 병합하는 코드. (b) 사용자가 고른 정렬 기준을 `ORDER BY ${req.query.sort}`로 문자열 보간하는 코드. (b)의 경우 파라미터화 질의만으로는 해결되지 않는 이유도 함께 서술하라.

3. 운영 중인 서비스가 EOL이 지난 Node.js 18에서 돌고 있고, 세 개의 네이티브 모듈과 200개가 넘는 전이 의존성을 가진다고 하자. Node.js 22로 이전하는 계획을 단계별로 작성하라. 각 단계마다 무엇을 검증하는지, 문제가 발견되었을 때 어떻게 되돌리는지 포함한다. 이전을 미룰 때의 비용이 시간이 갈수록 왜 커지는지도 근거와 함께 설명하라.

## 맺음말

이 책은 이벤트 루프 한 개에서 시작해 분산된 여러 프로세스로, 그리고 그것을 안전하게 운영하는 절차까지 왔다. 34개 장을 관통하는 주제가 하나 있었다면, 그것은 **Node.js가 무엇을 하는지 정확히 아는 것이 곧 그것을 잘 쓰는 방법**이라는 사실이다. 이벤트 루프가 단일 스레드라는 사실을 알면 ReDoS가 왜 서비스 전체를 멈추는지 이해된다. 스트림이 역압(backpressure)을 어떻게 전달하는지 알면 메모리가 왜 새는지 보인다. 프로세스가 어떤 경로로 죽는지 알면 복원력 설계가 구체화된다. 추상화는 편리하지만, 그 아래가 보이지 않으면 문제가 생겼을 때 할 수 있는 일이 없다.

보안을 마지막 장에 둔 것은 순서상의 이유이지 중요도의 순서가 아니다. 보안은 마지막에 덧붙이는 계층이 아니라 앞의 모든 장에 이미 스며 있어야 하는 성질이다. 스트림 처리에 크기 상한을 두는 것, 자식 프로세스에 환경을 넘기지 않는 것, 설정을 시작 시 검증하는 것은 각각 성능·설계·운영의 주제이면서 동시에 보안의 주제였다. 좋은 엔지니어링과 안전한 엔지니어링은 대체로 같은 것을 가리킨다.

다음에 할 일을 세 가지로 제안한다. 첫째, 34.8절의 체크리스트를 지금 운영 중인 서비스 하나에 실제로 적용해 본다. 전부 통과하는 서비스는 없을 것이고, 통과하지 못한 항목이 이 책에서 가장 먼저 다시 읽어야 할 장을 알려 준다. 둘째, 이 책의 코드를 그대로 쓰지 말고 자신의 맥락에서 다시 써 본다. 예제는 원리를 보이기 위해 단순화되어 있고, 실제 시스템에는 언제나 예제가 다루지 않은 제약이 있다. 셋째, 프로덕션에서 실제로 일어난 장애를 하나 골라 끝까지 파고들어 본다. 잘 조사한 장애 하나가 책 한 권보다 많은 것을 가르친다.

기술은 계속 바뀐다. 이 책이 v20~v22 기준으로 서술한 세부 사항 중 일부는 몇 년 안에 낡을 것이다. 권한 모델은 더 촘촘해질 것이고, 표준 라이브러리는 지금 의존성으로 해결하는 일들을 흡수할 것이며, 모듈 시스템과 타입 지원도 계속 정리될 것이다. 그러나 이벤트 기반 동시성의 성질, 역압의 원리, 부분 실패를 전제한 분산 설계, 신뢰 경계를 명시하는 보안 사고방식은 바뀌지 않는다. 세부는 릴리스 노트에서 갱신하고, 원리는 몸에 남기면 된다.

마지막으로, 좋은 시스템은 한 번에 설계되지 않고 반복해서 고쳐진다. 완벽한 첫 버전을 만들려 하기보다, 관측 가능하고 되돌릴 수 있으며 고치기 쉬운 시스템을 만드는 편이 언제나 낫다. 그런 시스템은 실수를 감당하고, 그 위에서 팀은 계속 배운다. 여기까지 온 독자에게 필요한 것은 더 많은 지식이 아니라 그것을 적용할 실제 문제다. 좋은 문제를 만나기를 바란다.
