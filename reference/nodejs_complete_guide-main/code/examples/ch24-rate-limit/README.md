# ch24 — 레이트 리미팅

24장 「Redis와 원자적 연산」의 레이트 리미터를 알고리즘 관점에서 비교한다.

| 파일 | 무엇을 보여주는가 | 대응 절 |
|---|---|---|
| `algorithms.js` | 고정 윈도 / 슬라이딩 윈도(로그·카운터) / 토큰 버킷의 경계 문제 시뮬레이션 | 24.6 |
| `token-bucket.lua` | 원자적 토큰 버킷 Redis Lua 스크립트 | 24.4, 24.6 |

## 실행

```bash
node algorithms.js     # Redis 없이 동작한다. 가상 시계를 쓰므로 즉시 끝난다
```

`token-bucket.lua` 는 Redis 에서 실행한다.

```bash
docker compose -f ../../infra/docker-compose.yml up -d redis
SHA=$(docker exec -i ncg-redis redis-cli -x SCRIPT LOAD < token-bucket.lua)
# capacity=10, refill=10/s, now=현재ms, requested=1
docker exec ncg-redis redis-cli EVALSHA "$SHA" 1 rl:user:1 10 10 "$(date +%s%3N)" 1
# → 1) 1  2) 9  3) 0     (allowed, remaining, retry_after_ms)
```

11번을 연속으로 호출하면 마지막이 `1) 0` 과 함께 `retry_after_ms` 를 돌려준다.

## 관찰 포인트

### 시나리오 1 — 윈도 경계 공격

950ms 에 10개, 1000ms 에 10개를 보낸다. 한도는 1초에 10회다.

| 알고리즘 | 1초 구간 최대 허용 | 판정 |
|---|---|---|
| 고정 윈도 | **20** | 한도의 2배를 통과시켰다 |
| 슬라이딩 윈도 로그 | 10 | 정확 |
| 슬라이딩 윈도 카운터 | 11 | 근사 — 오차 1 |
| 토큰 버킷 | 10 | 정확 |

허용(○)/거부(×) 타임라인을 함께 출력하므로 어느 요청이 통과했는지 눈으로 볼 수 있다.
고정 윈도는 20개가 전부 ○ 다. 공격자는 이 경계를 노려 순간 부하를 두 배로 만들 수 있다.

### 시나리오 2 — 한도의 2배 속도로 5초간 균일하게

세 알고리즘 모두 이상값(50개)에 수렴한다. 토큰 버킷만 118% 인데,
**처음에 가득 찬 버킷으로 시작**하므로 초기 버스트가 한 번 허용되기 때문이다.

### 시나리오 3 — 쉬었다가 몰아 보내기

용량 20 · 충전 10/s 버킷만 20개를 통과시킨다.
**평균 속도와 순간 허용량을 따로 정할 수 있다**는 것이 토큰 버킷의 핵심 장점이다.
사람이 쓰는 API 에서는 이 성질이 오히려 자연스럽다 —
페이지를 열면 요청이 몰리고, 읽는 동안은 조용하다.

## 선택 기준

| 상황 | 알고리즘 |
|---|---|
| 구현을 최대한 단순하게 (Redis `INCR`+`EXPIRE` 하나) | 고정 윈도. 단 한도를 필요치의 절반으로 |
| 정확도가 계약(SLA)인 경우 | 슬라이딩 윈도 로그. 메모리 비용을 감수한다 |
| 대부분의 실무 | 슬라이딩 윈도 카운터 |
| 버스트를 허용하고 싶다 | 토큰 버킷 |

## 왜 Lua 인가

`algorithms.js` 의 구현은 전부 인메모리다. **서버가 3대면 실제 한도는 3배가 된다.**
상태를 Redis 로 옮기면 이번엔 GET → 계산 → SET 사이에 다른 프로세스가 끼어든다.
두 인스턴스가 동시에 "토큰 1개 남음"을 읽고 둘 다 통과시키는 것이 전형적인 사고다.

Redis 는 Lua 스크립트를 하나의 명령처럼 원자적으로 실행한다. `token-bucket.lua` 의
주석에 운영에서 걸리는 네 가지(시각을 호출자가 넘기는 이유, 클러스터 슬롯, `EVALSHA`,
Redis 장애 시 fail-open/fail-closed 선택)를 정리해 두었다.
