# ch11 — 워커 스레드

11장 「멀티프로세스와 멀티스레드」의 CPU 바운드 처리 전략을 실제로 측정한다.

| 파일 | 무엇을 보여주는가 | 대응 절 |
|---|---|---|
| `subset-sum.js` | 부분집합 합 문제를 동기 / setImmediate / 워커 풀 세 가지로 풀고 비교 | 11.6 |
| `worker-pool.js` | 재사용 가능한 워커 스레드 풀 구현 (라이브러리 + 단독 데모) | 11.4, 11.6 |
| `worker-task.js` | 워커 측 스크립트. 직접 실행하지 않는다 | 11.4 |

## 실행

```bash
node subset-sum.js      # 약 2초
node worker-pool.js     # 풀 자체의 데모 (약 2초)
```

## 관찰 포인트

### subset-sum.js

원소 22개(약 420만 가지 조합)의 부분집합 합을 세 가지 방식으로 계산한다.
세 결과가 **모두 같은 값**인지 함께 확인한다.

측정 항목이 두 종류라는 점이 핵심이다.

- **소요 시간** — 작업이 얼마나 빨리 끝났는가
- **루프 지연 p99 / 하트비트** — 그동안 이 프로세스가 다른 일을 할 수 있었는가

2코어 환경의 예시 결과다.

| 방식 | 소요 | 루프 지연 max | 하트비트 |
|---|---|---|---|
| 동기 | 약 275ms | **약 280ms** | 1 / 13 |
| setImmediate 인터리빙 | 약 280ms | 약 16ms | 13 / 13 |
| 워커 풀 (2 스레드) | 약 165ms | 약 6ms | 9 / 8 |

- 동기 버전은 계산에는 성공하지만 그동안 **헬스 체크조차 응답하지 못한다**.
  로드 밸런서는 이 인스턴스를 죽은 것으로 보고 로테이션에서 뺀다(26장)
- setImmediate 인터리빙은 응답성을 회복시키지만 CPU 는 여전히 메인 스레드가 태운다
- 워커 풀은 메인 스레드가 계산에 전혀 참여하지 않는다. 코어가 여러 개면 총 시간까지 짧아진다

> `monitorEventLoopDelay` 를 쓸 때의 함정도 코드에 담겨 있다.
> `enable()` 직후 바로 동기 작업에 들어가면 표본이 하나도 없어 **지연이 0으로 나온다**.
> 측정 전후로 루프에 제어를 한 번씩 넘겨야 한다.

### worker-pool.js

단독 실행하면 세 가지를 보여준다.

1. **생성 비용**: 작업 20개를 매번 `new Worker` 로 처리할 때와 풀을 재사용할 때의 차이
   (보통 10배 이상). 차이는 전부 스레드 생성 비용이다
2. **큐잉**: 풀 크기보다 많은 작업을 넣으면 `running`/`pending` 이 어떻게 변하는지
3. **오류 전파**: 워커 안에서 던진 예외가 호출자의 프로미스로 전달되는지

구현에서 눈여겨볼 지점.

- `worker.unref()` — 풀 때문에 프로세스가 종료되지 못하는 것을 막는다
- `'error'` / `'exit'` 처리 — 워커가 죽으면 진행 중이던 작업을 **실패시키고** 대체 워커를 만든다.
  이 처리가 없으면 호출자의 프로미스가 영원히 정착하지 않는다
- `destroy()` — 반드시 불러야 프로세스가 깔끔하게 끝난다
- `worker-task.js` 는 예외를 **잡아서 메시지로 되돌려 준다**.
  그냥 던지면 워커가 통째로 죽어 재사용할 수 없다

## 선택 기준

- 수십 ms 안에 끝난다 → 그냥 동기로. 워커 통신 비용이 더 크다
- 수백 ms 이상이거나 입력 크기를 사용자가 정한다 → 워커 풀
- 코드를 크게 못 고치는 상황의 임시 완화 → setImmediate 인터리빙
- 넘길 데이터가 크면 직렬화 비용을 먼저 측정한다. `SharedArrayBuffer` / `transferList` 로
  복사를 피할 수 있다 (11.5절)
