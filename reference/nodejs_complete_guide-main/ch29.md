# 29장. 복원력

복원력(resilience)은 장애가 일어나지 않게 만드는 기술이 아니라, 장애가 일어난다는 전제 위에서 시스템이 계속 쓸 만한 상태로 남게 만드는 기술이다. 프로세스는 죽고, 데이터베이스는 페일오버하고, 네트워크는 끊기고, 메시지는 두 번 도착한다. 이 사실을 부정하는 설계는 예외 없이 운영 중에 대가를 치른다.

이 장은 Node.js 프로세스가 죽는 모든 경로를 먼저 정리하고, 죽어도 괜찮은 프로세스를 만드는 무상태 설계, 오래 살아 있을 때 프로세스를 서서히 죽이는 메모리 누수, 끊어지는 의존성(데이터베이스와 메시지 브로커)을 견디는 방법, 그리고 재시도·백오프·서킷 브레이커를 직접 구현한다. 마지막 절은 이 모든 대비가 실제로 동작하는지 확인하는 카오스 테스트다.

핵심 문장 하나를 미리 적어둔다. **복원력은 프로세스를 죽지 않게 만드는 것이 아니라, 죽는 것이 사건이 되지 않게 만드는 것이다.**

## 29.1 Node.js 프로세스는 어떻게 죽는가: 종료, 예외, 거부, 시그널

### 왜 필요한가

운영 중인 서비스에서 "프로세스가 사라졌다"는 보고를 받았을 때 가장 먼저 답해야 하는 질문은 "어떤 경로로 죽었는가"다. 경로마다 남는 흔적이 다르고, 대응도 다르다. `uncaughtException`으로 죽은 프로세스는 코드 버그이고, OOM으로 죽은 프로세스는 메모리 문제이고, `SIGTERM`으로 죽은 프로세스는 오케스트레이터가 의도적으로 내린 결정이다. 이 셋을 구분하지 못하면 재시작 루프를 도는 컨테이너 앞에서 몇 시간을 낭비한다.

Node.js 프로세스가 종료되는 경로는 다음과 같다.

| 경로 | 트리거 | 종료 코드 | 정리 코드 실행 가능 |
| --- | --- | --- | --- |
| 정상 종료 | 이벤트 루프에 남은 작업 없음 | 0 | `beforeExit`, `exit` |
| 명시적 종료 | `process.exit(code)` | 지정값 | `exit`만(동기 코드만) |
| 처리되지 않은 예외 | 동기 스택에서 던져진 오류 | 1 | `uncaughtException` |
| 처리되지 않은 거부 | `await` 없는 실패 프로미스 | 1 | `unhandledRejection` |
| 힙 한계 초과 | V8 힙이 `--max-old-space-size` 도달 | 134(SIGABRT) | 사실상 불가 |
| 컨테이너 OOM | 커널 OOM Killer의 SIGKILL | 137 | 불가 |
| 시그널 | `SIGTERM`, `SIGINT`, `SIGHUP` | 128+시그널 번호 | 핸들러 등록 시 가능 |
| 강제 종료 | `SIGKILL` | 137 | 불가 |

### 정상 종료와 명시적 종료

Node.js는 이벤트 루프에 처리할 작업이 남지 않으면 스스로 종료한다. 열린 서버 소켓, 활성 타이머, 진행 중인 파일 핸들이 전부 사라지면 프로세스는 코드 0으로 끝난다. 스크립트성 프로그램이 "왜 안 끝나지"라며 매달려 있다면 대개 닫지 않은 데이터베이스 풀이나 `setInterval`이 이벤트 루프를 붙잡고 있는 것이다.

`process.exit()`는 이 자연스러운 종료를 건너뛴다. 위험한 것은 이것이 **버퍼링된 비동기 쓰기를 버린다**는 점이다.

```js
// 나쁜 예: 로그가 유실될 수 있다
process.on('uncaughtException', (err) => {
  logger.fatal({ err }, '처리되지 않은 예외')  // 비동기 전송 큐에 들어감
  process.exit(1)                              // 큐를 비우지 않고 즉시 종료
})
```

파이프로 연결된 stdout이나 네트워크 전송 로거는 쓰기가 비동기다. `process.exit()`는 이벤트 루프를 더 돌리지 않으므로 큐에 남은 로그는 그대로 사라진다. 정작 원인을 알려줄 마지막 로그가 없어지는 것이다. 해결책은 종료 코드를 지정한 뒤 이벤트 루프가 자연스럽게 비워지길 기다리거나, 로거의 플러시(flush)를 명시적으로 기다리는 것이다.

```js
import process from 'node:process'

async function fatalExit(err, code = 1) {
  try {
    logger.fatal({ err }, '치명적 오류로 종료한다')
    await logger.flush?.()          // 전송 큐를 비운다
  } catch {
    // 로깅 자체가 실패하면 더 할 수 있는 일이 없다
    console.error(err)
  }
  process.exitCode = code           // 즉시 죽이지 않고 종료 코드만 예약한다
  // 강제 종료 안전망: 정리가 끝나지 않으면 5초 뒤 확실히 죽는다
  setTimeout(() => process.exit(code), 5000).unref()
}
```

`process.exitCode`에 값을 넣어두면 이벤트 루프가 비었을 때 그 코드로 종료된다. 마지막 줄의 `unref()`는 이 타이머가 이벤트 루프를 붙잡지 않게 해서, 정리가 5초보다 빨리 끝나면 그냥 종료되게 한다. 이 조합이 "가능한 한 깨끗하게, 그러나 반드시 죽는다"를 표현하는 관용구다.

### 처리되지 않은 예외

`uncaughtException`은 어떤 `try/catch`에도 잡히지 않고 이벤트 루프 최상단까지 올라온 동기 예외다. 여기서 가장 중요한 원칙은 하나다.

> **`uncaughtException`을 잡고 프로세스를 계속 실행하지 마라.**

이유는 감성적인 것이 아니라 기술적이다. 예외가 스택을 뚫고 올라왔다는 것은 **그 스택 중간의 어떤 함수도 정리 코드를 실행하지 못했다**는 뜻이다. 획득한 락은 해제되지 않았고, 시작한 트랜잭션은 커밋도 롤백도 되지 않은 채 커넥션을 점유하고 있으며, 반쯤 갱신된 캐시 항목은 일관성이 깨진 상태로 남았고, `finally`에서 닫으려던 파일 디스크립터는 열린 채다. 프로세스의 메모리 상태는 이미 오염되었다. 이 상태로 계속 요청을 받으면 원래 버그보다 훨씬 진단하기 어려운 2차 오류가 무작위 위치에서 튀어나온다.

`uncaughtException` 핸들러의 유일하게 정당한 용도는 **마지막 로그를 남기고 죽는 것**이다.

```js
import process from 'node:process'

process.on('uncaughtException', (err, origin) => {
  // origin은 'uncaughtException' 또는 'unhandledRejection'
  logger.fatal({ err, origin }, '복구 불가능한 오류 — 프로세스를 종료한다')
  // 진행 중인 요청에 대해서만 짧게 정리를 시도한 뒤 반드시 죽는다
  shutdown({ reason: 'uncaughtException', code: 1 })
})
```

여기서 호출하는 `shutdown()`은 새 연결 수락 중단, 진행 중 요청 마무리, 리소스 해제, 타임아웃 강제 종료로 이어지는 우아한 종료(graceful shutdown) 시퀀스다. 구현은 9장을 참조한다. 다만 `uncaughtException` 경로에서는 그 시퀀스를 **짧은 타임아웃**으로 돌려야 한다. 상태가 오염된 프로세스에 30초를 주는 것은 의미가 없다.

한 가지 예외적 활용은 있다. 예외 발생 시점에 어떤 비동기 컨텍스트에 있었는지를 `AsyncLocalStorage`로 붙여 남기는 것이다(31장 참조). 어떤 요청을 처리하다 죽었는지 알면 재현이 훨씬 쉬워진다.

### 처리되지 않은 거부

Node.js 15부터 처리되지 않은 프로미스 거부(unhandled rejection)의 기본 동작은 **경고가 아니라 프로세스 종료**다(`--unhandled-rejections=throw`가 기본값). 이는 올바른 변경이다. 거부가 무시된 프로미스는 조용히 사라진 오류이고, 조용히 사라진 오류는 데이터 손상으로 이어진다.

전형적인 발생 패턴은 셋이다.

```js
// 1) await를 빠뜨린 호출
async function handler(req, res) {
  saveAuditLog(req)          // await 없음 — 실패하면 unhandledRejection
  res.end('ok')
}

// 2) 이벤트 핸들러 안의 async 함수 — 던져도 받을 곳이 없다
emitter.on('data', async (chunk) => {
  await process(chunk)       // 거부되면 아무도 잡지 않는다
})

// 3) 병렬 실행에서 일부만 기다림
const [a] = await Promise.all([fetchA(), fetchB()])  // 이건 괜찮다
const p = fetchB()
const a2 = await fetchA()   // fetchA가 먼저 던지면 p의 거부는 미아가 된다
```

세 번째 패턴은 특히 함정이다. `Promise.all`은 거부를 하나로 모아주지만, 프로미스를 따로 만들어두고 순차적으로 `await`하면 먼저 실패한 쪽이 나머지 프로미스를 미아로 만든다. 이럴 때는 `Promise.allSettled`를 쓰거나, 프로미스를 만드는 즉시 `.catch()`로 최소한의 처리기를 붙인다.

핸들러는 예외와 같은 원칙으로 등록한다. 잡아서 로그를 남기고 죽는다.

```js
process.on('unhandledRejection', (reason, promise) => {
  logger.fatal({ reason, promise }, '처리되지 않은 프로미스 거부')
  shutdown({ reason: 'unhandledRejection', code: 1 })
})
```

의도적으로 결과를 무시하는 호출은 무시한다는 사실을 코드에 드러낸다.

```js
// 실패해도 요청 처리에 영향을 주지 않는 부수 작업
void saveAuditLog(req).catch((err) => logger.warn({ err }, '감사 로그 실패'))
```

`void`와 명시적 `.catch()` 조합은 "이 실패는 알고 있고 삼킨다"는 의도를 표현한다. 아무것도 붙이지 않은 호출과 코드 리뷰에서 구분된다는 것이 핵심이다.

### 메모리 고갈: 힙 한계와 컨테이너 OOM

메모리로 죽는 경로는 둘인데, 완전히 다르므로 반드시 구분해야 한다.

**V8 힙 한계 초과**는 자바스크립트 객체가 오래된 세대(old space)의 상한에 도달했을 때 V8이 스스로 프로세스를 중단시키는 것이다. `FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory`라는 메시지와 스택 트레이스가 남고, 종료 코드는 134(SIGABRT)다. 로그가 남으므로 진단이 가능하다.

**컨테이너 OOM Killer**는 다르다. cgroup 메모리 한계를 넘어선 프로세스에게 커널이 `SIGKILL`을 보낸다. 프로세스는 아무 로그도 남기지 못하고 즉시 사라지며, 종료 코드는 137(128+9)이다. 쿠버네티스에서는 파드 상태가 `OOMKilled`로 표시된다. 여기서 흔한 오해가 있다. **컨테이너 메모리 사용량은 V8 힙보다 크다.** 힙 외에도 버퍼(`Buffer`는 힙 밖에 할당된다), 네이티브 애드온, 스레드 스택, glibc 할당자의 단편화가 모두 RSS에 잡힌다.

따라서 힙 한계는 컨테이너 한계보다 명확히 낮게 잡아야 한다. 경험칙은 컨테이너 한계의 70~75%다.

```bash
# 컨테이너 메모리 한계가 1Gi일 때
node --max-old-space-size=768 server.js

# 또는 환경 변수로 (Node 20+)
NODE_OPTIONS="--max-old-space-size=768" node server.js
```

이렇게 하면 메모리가 새더라도 커널의 `SIGKILL` 대신 V8의 힙 한계 오류가 먼저 발생한다. 로그와 힙 스냅숏이 남는 쪽으로 죽는 것이 언제나 낫다. 실제로 힙 한계 도달 시 스냅숏을 자동으로 남기게 할 수도 있다.

```bash
node --max-old-space-size=768 --heapsnapshot-near-heap-limit=2 server.js
```

이 플래그는 힙 한계에 근접했을 때 최대 2개의 `.heapsnapshot` 파일을 남긴다. 파일이 수백 MB가 될 수 있으므로 쓰기 가능한 볼륨이 있는지 먼저 확인해야 한다.

### 시그널

시그널은 외부에서 프로세스에게 보내는 종료 요청이다. 실무에서 다뤄야 하는 것은 셋이다.

- `SIGTERM`(15): 오케스트레이터의 표준 종료 요청. 쿠버네티스가 파드를 내릴 때, `docker stop`이 컨테이너를 멈출 때 보낸다. **반드시 핸들러를 등록해야 한다.**
- `SIGINT`(2): 터미널에서 Ctrl+C. 로컬 개발에서 주로 만난다.
- `SIGKILL`(9): 잡을 수 없다. 커널이 즉시 프로세스를 제거한다. 오케스트레이터는 `SIGTERM` 후 유예 기간(쿠버네티스 기본 30초)이 지나면 이것을 보낸다.

```js
import process from 'node:process'

let shuttingDown = false

function onSignal(signal) {
  if (shuttingDown) {
    // 두 번째 시그널은 "당장 죽어라"는 뜻으로 해석한다
    logger.warn({ signal }, '종료 중 재차 시그널 수신 — 즉시 종료한다')
    process.exit(130)
  }
  shuttingDown = true
  logger.info({ signal }, '종료 시그널 수신 — 우아한 종료를 시작한다')
  shutdown({ reason: signal, code: 0 })
}

for (const signal of ['SIGTERM', 'SIGINT']) {
  process.on(signal, () => onSignal(signal))
}
```

컨테이너에서 자주 겪는 함정이 있다. Dockerfile에서 `CMD npm start`처럼 셸 형식(shell form)을 쓰면 PID 1이 셸이 되고, 셸은 `SIGTERM`을 자식 Node 프로세스에게 전달하지 않는다. 결과적으로 우아한 종료 코드가 한 번도 실행되지 않고 30초 뒤 `SIGKILL`로 죽는다. 배포 후 종료가 항상 30초씩 걸린다면 십중팔구 이것이 원인이다.

```dockerfile
# 나쁜 예: 셸이 PID 1이 되어 시그널이 전달되지 않는다
CMD npm start

# 좋은 예: node가 직접 PID 1이 된다
CMD ["node", "server.js"]
```

Node.js가 PID 1이 되는 것 자체도 완벽하지는 않다. PID 1은 좀비 프로세스 회수 책임을 지는데 Node.js는 그 일을 하지 않기 때문이다. 자식 프로세스를 자주 만드는 애플리케이션이라면 `tini` 같은 최소 init을 `ENTRYPOINT`로 두는 편이 안전하다.

### 흔한 실수

- `uncaughtException`을 잡고 계속 실행하기. 앞서 설명한 이유로 반드시 죽어야 한다.
- 종료 핸들러 안에서 `await`을 쓰면서 `process.exit()`을 같은 함수 안에 두기. `exit()`는 대기 중인 프로미스를 기다리지 않는다.
- `exit` 이벤트 핸들러에서 비동기 작업 시도하기. `exit` 핸들러는 동기 코드만 실행된다. 파일 쓰기가 필요하면 `writeFileSync`를 써야 한다.
- 헬스 체크가 프로세스 생존만 확인하기. 이벤트 루프가 막힌 프로세스는 살아 있지만 아무 요청도 처리하지 못한다. 활성 프로브(liveness probe)는 실제 HTTP 응답을 확인해야 한다.

## 29.2 무상태 서비스 설계

### 무상태란 정확히 무엇인가

"무상태(stateless)"는 자주 쓰이지만 자주 오해되는 말이다. 서비스가 아무것도 기억하지 않는다는 뜻이 아니다. 정확한 정의는 이것이다.

> **한 요청을 처리하는 데 필요한 모든 정보가 그 요청 자체와 외부 저장소에 있고, 프로세스 메모리에는 요청 간에 유지되어야 하는 상태가 없다.**

즉 프로세스 메모리에 무언가를 담는 것 자체는 문제가 아니다. 요청 A가 프로세스 메모리에 남긴 것을 요청 B가 **의존**할 때 문제가 된다. 이 구분이 중요한 이유는 캐시 때문이다. 캐시는 메모리에 남지만, 사라져도 정확성에 영향을 주지 않는다면 무상태 원칙을 위반하지 않는다. 반면 세션 데이터는 사라지면 사용자가 로그아웃되므로 상태다.

무상태가 주는 것은 세 가지다. 첫째, **아무 인스턴스나 아무 요청을 처리할 수 있다**. 로드 밸런서는 스티키 세션 없이 자유롭게 분배하고, 인스턴스 하나가 죽어도 진행 중이던 요청만 실패한다. 둘째, **수평 확장이 선형적이다**. 인스턴스를 추가하는 것 외에 조율할 것이 없다. 셋째, **재시작이 안전하다**. 배포와 스케일 인이 데이터 손실을 일으키지 않는다.

### 상태를 밖으로 밀어내기

실무에서 프로세스 메모리에 잘못 남는 상태는 다음과 같다. 각각 어디로 옮겨야 하는지 정리한다.

**1) 세션**

가장 흔한 위반이다. `express-session`의 기본 `MemoryStore`는 인스턴스가 하나일 때만 동작한다.

```js
// 나쁜 예: 인스턴스가 둘이 되는 순간 사용자가 무작위로 로그아웃된다
app.use(session({ secret: process.env.SESSION_SECRET }))

// 좋은 예: 세션 상태를 Redis로 밀어낸다
import RedisStore from 'connect-redis'
app.use(session({
  store: new RedisStore({ client: redis }),
  secret: process.env.SESSION_SECRET,
  resave: false,
  saveUninitialized: false
}))
```

더 나아가면 서명된 토큰(JWT 등)을 써서 세션 저장소 자체를 없앨 수 있다. 다만 토큰은 즉시 무효화가 어렵다는 대가가 있으므로, 로그아웃과 권한 회수가 즉시 반영되어야 하는 서비스라면 Redis 세션이 더 단순하다(17장 참조).

**2) 캐시**

프로세스 로컬 캐시는 인스턴스마다 내용이 달라진다. 읽기 전용 데이터라면 문제가 없지만, 무효화(invalidation)가 필요한 데이터라면 인스턴스 간 불일치가 생긴다. 사용자가 프로필을 수정했는데 새로고침할 때마다 옛날 값과 새 값이 번갈아 보이는 현상이 여기서 온다. 공유 캐시(Redis)를 진실의 원천으로 두고, 프로세스 로컬 캐시는 짧은 TTL의 2차 캐시로만 쓴다.

**3) 업로드 임시 파일**

`multer`의 디스크 스토리지처럼 로컬 파일 시스템에 파일을 쓰고, 다음 요청에서 그 파일을 참조하는 다단계 업로드는 인스턴스가 바뀌는 순간 깨진다. 컨테이너 파일 시스템은 재시작하면 사라지기도 한다. 업로드는 객체 스토리지(S3 등)로 직접 보내거나, 서명된 URL로 클라이언트가 직접 올리게 한다.

**4) 스케줄러**

`setInterval`로 도는 배치 작업은 인스턴스 수만큼 중복 실행된다. 인스턴스가 셋이면 정산 배치가 세 번 돈다. 스케줄링은 외부 스케줄러(쿠버네티스 CronJob)나 분산 락으로 리더를 하나만 뽑는 방식으로 옮긴다(24장 참조).

**5) 진행 중 작업**

요청을 받고 즉시 응답한 뒤 백그라운드에서 계속 처리하는 패턴은, 프로세스가 죽으면 그 작업이 흔적 없이 사라진다. 클라이언트는 성공 응답을 받았는데 작업은 수행되지 않은 상태다. 오래 걸리는 작업은 메시지 큐에 넣고 워커가 소비하게 한다(23장 참조).

**6) 인메모리 카운터와 레이트 리미터**

`let requestCount = 0` 같은 카운터는 인스턴스별로 따로 센다. 레이트 리미트가 인스턴스 수만큼 느슨해진다. 공유 저장소 기반으로 구현한다(24장 참조).

### 남아도 되는 것

반대로 프로세스 메모리에 두어도 무방한 것들이 있다. 판단 기준은 "프로세스가 지금 죽어도 정확성이 유지되는가"다.

- **설정값과 파생 상수**: 시작 시 읽어 불변으로 유지되는 값
- **커넥션 풀**: 프로세스에 종속된 자원이므로 당연히 로컬이다
- **경계가 있는 읽기 캐시**: 없으면 다시 조회하면 되는 값
- **회로 차단기 상태**: 인스턴스마다 자기가 본 실패를 근거로 판단하는 것이 오히려 정확하다
- **메트릭 카운터**: 주기적으로 수집기로 밀어내는 값

### 흔한 실수

- 로컬 파일 시스템을 영속 저장소로 취급하기. 컨테이너에서 로컬 디스크는 임시 공간이다.
- 스티키 세션으로 문제를 덮기. 인스턴스가 죽으면 그 인스턴스에 묶인 사용자만 골라서 문제를 겪는다.
- 그레이스풀 셧다운만으로 진행 중 작업을 보호할 수 있다고 믿기. `SIGKILL`과 하드웨어 장애 앞에서는 무력하다.

## 29.3 메모리 누수 회피와 경계 있는 인프로세스 캐시

### 왜 필요한가

Node.js 프로세스는 오래 산다. 웹 요청 하나마다 프로세스가 죽는 PHP와 달리, Node.js 서버는 몇 주 동안 같은 힙을 재사용한다. 요청당 몇 KB의 누수도 수백만 요청 뒤에는 힙을 채운다. 메모리 누수의 증상은 특징적이다. 재시작 직후에는 멀쩡하다가, 며칠 뒤 응답 지연이 서서히 늘고(GC 압박), 결국 OOM으로 죽고, 재시작하면 다시 멀쩡해진다. 이 톱니 모양 그래프를 보면 누수를 의심해야 한다.

자바스크립트는 GC 언어지만 누수가 없는 것이 아니다. GC는 **도달 불가능한(unreachable)** 객체만 회수한다. 어딘가에서 여전히 참조하고 있는 객체는, 논리적으로 다시는 쓰이지 않더라도 영원히 살아 있다. 누수란 곧 **의도치 않은 참조**다.

### 대표 유형 다섯 가지

**1) 무한히 커지는 모듈 레벨 컬렉션**

가장 흔하다.

```js
// 누수: 이 Map은 절대 줄어들지 않는다
const requestContext = new Map()

export function trackRequest(req) {
  requestContext.set(req.id, {
    startedAt: Date.now(),
    user: req.user,
    body: req.body        // 요청 본문 전체를 붙잡고 있다
  })
}
```

삭제하는 코드가 없으면 요청 수만큼 항목이 쌓인다. 삭제 코드가 있어도, 예외가 발생하는 경로에서 삭제를 건너뛰면 서서히 샌다. 이런 자료구조는 반드시 크기 상한이나 TTL을 가져야 한다.

**2) 제거하지 않은 이벤트 리스너**

```js
// 누수: 요청마다 리스너가 하나씩 늘어난다
export function handler(req, res) {
  eventBus.on('config-changed', () => {
    res.write('설정이 변경되었다\n')   // res를 영원히 붙잡는다
  })
}
```

`eventBus`는 애플리케이션 수명 동안 살아 있고, 등록된 클로저는 `res`를, `res`는 소켓과 요청 객체를 참조한다. 요청 하나마다 응답 객체 하나가 영구히 남는다. Node.js는 한 이미터에 같은 이벤트의 리스너가 11개를 넘으면 `MaxListenersExceededWarning`을 출력하는데, 이 경고는 대부분 진짜 누수의 신호다. 무시하지 말아야 한다(4장 참조).

해결책은 정리를 보장하는 것이다. `AbortSignal`을 쓰면 정리를 한 곳으로 모을 수 있다.

```js
export function handler(req, res) {
  const ac = new AbortController()
  eventBus.on('config-changed', onChange, { signal: ac.signal })
  // 응답이 끝나면 어떤 경로로 끝났든 리스너가 제거된다
  res.on('close', () => ac.abort())

  function onChange() {
    res.write('설정이 변경되었다\n')
  }
}
```

`{ signal }` 옵션은 Node.js 15부터 `EventEmitter.on`이 지원한다. `once`로 충분한 경우에는 `once`를 쓰는 것이 더 간단하다.

**3) 클로저가 붙잡은 큰 객체**

```js
// 누수: 작은 값 하나 때문에 거대한 버퍼가 살아남는다
function makeFormatter(uploadedFile) {   // uploadedFile.buffer는 50MB
  const name = uploadedFile.originalName
  return () => `파일: ${name}`           // name만 쓰지만…
}
```

V8은 클로저가 실제로 참조하는 변수만 컨텍스트에 남기는 최적화를 하지만, 같은 스코프의 다른 클로저가 해당 변수를 쓰면 컨텍스트가 공유되어 함께 살아남는다. 큰 객체에서 필요한 값만 뽑아 별도 변수로 만들고, 큰 객체 참조를 스코프 밖에 두는 것이 안전하다.

**4) 정리하지 않은 타이머**

```js
// 누수: 소켓이 끊겨도 타이머는 계속 돈다
socket.on('connect', () => {
  setInterval(() => socket.ping(), 30_000)  // clearInterval이 없다
})
```

`setInterval`은 콜백과 그 클로저가 참조하는 모든 것을 영구히 붙잡는다. 연결 수만큼 인터벌이 쌓이면 CPU까지 소모한다. 반드시 핸들을 보관하고 `clearInterval`로 정리한다.

**5) 끝나지 않는 프로미스**

절대 이행되지도 거부되지도 않는 프로미스는 그 프로미스에 등록된 모든 `then` 콜백과 `await` 중인 async 함수의 프레임을 붙잡는다. 타임아웃 없는 네트워크 호출이 대표적이다. 모든 외부 호출에는 타임아웃이 있어야 한다는 원칙(29.6)은 메모리 관점에서도 정당하다.

### 경계 있는 LRU 캐시

인프로세스 캐시는 유용하다. Redis 왕복(1ms 내외)조차 아까운 뜨거운 데이터가 있고, 네트워크 장애 시 마지막 방어선이 되기도 한다. 조건은 **반드시 경계가 있어야 한다**는 것이다. 상한 없는 캐시는 캐시가 아니라 메모리 누수다.

LRU(Least Recently Used)는 가장 오래 사용되지 않은 항목을 먼저 버리는 정책이다. 자바스크립트의 `Map`은 삽입 순서를 보존하므로, 이것만으로 LRU를 간결하게 구현할 수 있다.

```js
export class LruCache {
  #map = new Map()
  #maxSize
  #ttlMs

  constructor({ maxSize = 1000, ttlMs = 60_000 } = {}) {
    this.#maxSize = maxSize
    this.#ttlMs = ttlMs
  }

  get(key) {
    const entry = this.#map.get(key)
    if (entry === undefined) return undefined

    if (entry.expiresAt <= Date.now()) {
      this.#map.delete(key)
      return undefined
    }

    // 사용한 항목을 맨 뒤로 옮긴다 — Map의 삽입 순서가 곧 LRU 순서다
    this.#map.delete(key)
    this.#map.set(key, entry)
    return entry.value
  }

  set(key, value) {
    // 이미 있으면 지웠다 다시 넣어 순서를 갱신한다
    if (this.#map.has(key)) this.#map.delete(key)
    this.#map.set(key, { value, expiresAt: Date.now() + this.#ttlMs })

    // 상한을 넘으면 가장 오래된 항목(첫 번째)부터 버린다
    while (this.#map.size > this.#maxSize) {
      const oldestKey = this.#map.keys().next().value
      this.#map.delete(oldestKey)
    }
  }

  get size() {
    return this.#map.size
  }
}
```

`while` 루프를 쓴 이유는 `maxSize`를 런타임에 줄이는 경우에도 정확히 동작하게 하기 위함이다. 여기서 만료된 항목은 접근할 때만 제거되므로, 접근되지 않는 만료 항목은 상한에 도달할 때까지 메모리를 차지한다. 이 성질이 문제가 되는 경우는 드물지만, 항목이 매우 크다면 주기적 청소 타이머를 `unref()`와 함께 두면 된다.

**상한을 무엇으로 잴 것인가**도 중요한 질문이다. 항목 수로 재는 것은 항목 크기가 균일할 때만 안전하다. 캐시하는 값이 API 응답 본문처럼 크기가 제각각이라면, 바이트 기준 상한이 필요하다. `production-grade`가 필요하다면 `lru-cache` 패키지가 `maxSize`와 `sizeCalculation` 옵션으로 이를 지원한다.

### WeakMap과 WeakRef

약한 참조는 GC를 방해하지 않는 참조다. 오해가 많으므로 용도를 분명히 한다.

**`WeakMap`은 "키 객체의 수명에 부가 데이터를 묶을 때" 쓴다.** 키가 도달 불가능해지면 항목이 자동으로 사라진다.

```js
// 요청 객체에 파싱 결과를 캐시한다 — 요청이 끝나면 자동으로 회수된다
const parsedBody = new WeakMap()

export function getParsedBody(req) {
  let parsed = parsedBody.get(req)
  if (parsed === undefined) {
    parsed = JSON.parse(req.rawBody)
    parsedBody.set(req, parsed)
  }
  return parsed
}
```

여기서 `WeakMap`은 정확히 맞는 도구다. 정리 코드를 쓸 필요 없이 요청 객체가 회수되면 파싱 결과도 함께 사라진다.

**`WeakMap`이 잘못된 도구인 경우가 더 많다.** 문자열 키로는 쓸 수 없고(키는 객체여야 한다), 순회할 수 없으며, 크기를 알 수 없다. 무엇보다 **캐시의 경계 수단으로 부적절하다.** 캐시의 목적은 값을 살려두는 것인데, 값을 참조하는 다른 곳이 없다면 GC가 언제든 가져가버려 캐시 적중률이 예측 불가능해진다.

**`WeakRef`와 `FinalizationRegistry`는 최후의 수단이다.** MDN과 V8 문서 모두 "가능하면 쓰지 마라"고 명시한다. GC 시점은 명세되지 않았고 엔진 버전에 따라 달라진다. 정리(cleanup) 콜백은 호출이 보장되지 않으며, 프로세스가 종료될 때는 아예 호출되지 않는다. 리소스 해제 로직을 `FinalizationRegistry`에 의존하는 설계는 운영에서 반드시 문제를 일으킨다. 명시적 해제(`close()`, `dispose()`, `using` 선언)를 쓰고, 약한 참조는 "있으면 좋고 없어도 되는" 보조 캐시에만 쓴다.

### 누수를 찾는 절차

1. **RSS와 힙을 분리해 관측한다.** `process.memoryUsage()`의 `heapUsed`가 자라면 자바스크립트 객체 누수이고, `rss`만 자라고 `heapUsed`가 평평하면 버퍼나 네이티브 자원 누수다.
2. **부하를 준 뒤 힙 스냅숏을 두 번 뜬다.** `node --inspect`로 붙어 Chrome DevTools의 Memory 탭에서 스냅숏을 찍고, 두 스냅숏 사이의 차이(Comparison 뷰)에서 개수가 크게 늘어난 생성자를 본다.
3. **Retainers를 따라간다.** 늘어난 객체를 선택하면 무엇이 그것을 붙잡고 있는지 경로가 나온다. 대개 모듈 레벨 배열, `EventEmitter._events`, 타이머 리스트 중 하나로 이어진다.

```js
// 간단한 관측: 30초마다 메모리 지표를 로그로 남긴다
const timer = setInterval(() => {
  const { heapUsed, heapTotal, rss, external, arrayBuffers } = process.memoryUsage()
  logger.info({
    heapUsedMb: Math.round(heapUsed / 1024 / 1024),
    heapTotalMb: Math.round(heapTotal / 1024 / 1024),
    rssMb: Math.round(rss / 1024 / 1024),
    externalMb: Math.round(external / 1024 / 1024),
    arrayBuffersMb: Math.round(arrayBuffers / 1024 / 1024)
  }, 'memory')
}, 30_000)
timer.unref()   // 이 타이머가 프로세스 종료를 막지 않게 한다
```

`external`과 `arrayBuffers`가 자라는데 `heapUsed`가 평평하다면 `Buffer` 누수를 의심한다. 스트림을 소비하지 않고 방치하는 코드가 흔한 원인이다(9장 참조).

## 29.4 데이터베이스 연결 복원력: 자동 재연결과 풀링

### 연결은 반드시 끊긴다

애플리케이션 개발자는 데이터베이스 연결을 한 번 맺으면 유지되는 것으로 가정하는 경향이 있다. 운영 환경에서 연결이 끊기는 이유는 셀 수 없이 많다.

- **데이터베이스 재시작**: 버전 업그레이드, 설정 변경, 계획된 유지보수
- **페일오버**: 관리형 데이터베이스(RDS, Cloud SQL)는 몇 달에 한 번 프라이머리를 교체한다. 이때 기존 연결은 전부 끊긴다
- **유휴 타임아웃**: 데이터베이스의 `idle_session_timeout`, 중간의 로드 밸런서나 NAT 게이트웨이가 유휴 TCP 연결을 조용히 끊는다
- **연결 수 상한**: `max_connections`에 도달하면 새 연결이 거부된다
- **네트워크 단절**: 가용 영역 간 순간적 패킷 손실, 보안 그룹 변경

특히 NAT 게이트웨이의 유휴 타임아웃은 악명 높다. AWS NAT 게이트웨이는 350초 동안 트래픽이 없는 연결을 끊는데, **끊었다는 사실을 양쪽에 알리지 않는다.** 애플리케이션은 연결이 살아 있다고 믿고 쿼리를 보내지만 응답이 오지 않고, TCP 재전송 타임아웃까지 수십 초를 기다린다. 이런 유령 연결(zombie connection)은 TCP keepalive로 예방한다.

### 풀 설정의 의미

Node.js에서 데이터베이스 접근은 항상 커넥션 풀(connection pool)을 거쳐야 한다. 요청마다 연결을 만들면 TCP 핸드셰이크와 인증에 수 밀리초씩 낭비되고, 동시 요청이 몰리면 데이터베이스의 연결 상한을 순식간에 소진한다. PostgreSQL의 `pg`를 예로 든다.

```js
import pg from 'pg'

const pool = new pg.Pool({
  connectionString: process.env.DATABASE_URL,

  // 이 프로세스가 점유할 최대 연결 수
  max: 10,
  // 유휴 연결을 몇 ms 뒤에 닫을지 — DB의 idle timeout보다 짧아야 한다
  idleTimeoutMillis: 30_000,
  // 풀에서 연결을 얻지 못하고 기다리는 최대 시간
  connectionTimeoutMillis: 5_000,
  // 개별 쿼리 상한 (서버 측에서 강제된다)
  statement_timeout: 10_000,
  // 연결을 일정 횟수 사용 후 폐기해 서버 측 상태 누적을 막는다
  maxUses: 7_500,
  // 유령 연결 방지
  keepAlive: true,
  keepAliveInitialDelayMillis: 10_000
})
```

`max` 값을 정할 때 가장 흔한 실수는 **인스턴스 수를 곱하지 않는 것**이다. 데이터베이스의 `max_connections`가 100인데 `max: 20`인 애플리케이션을 10개 인스턴스로 띄우면 최대 200개를 요구하게 되고, 절반은 연결 실패한다. 오토스케일링이 인스턴스를 늘리는 순간 데이터베이스가 먼저 무너지는 시나리오다. 계산식은 단순하다.

```text
인스턴스 수 × 프로세스당 max ≤ max_connections − (운영 도구용 여유분)
```

Node.js는 단일 스레드이므로 `max`가 클 필요도 없다. 쿼리는 어차피 순차적으로 발행되며, `max`를 늘려도 데이터베이스 쪽 병렬성이 늘 뿐이다. 대개 5~20 사이가 적절하고, 그 이상이 필요하다면 PgBouncer 같은 외부 풀러를 두는 편이 낫다.

`connectionTimeoutMillis`는 특히 중요하다. 이 값이 없으면 데이터베이스가 느려졌을 때 요청들이 풀 대기열에 무한정 쌓이고, 각 요청이 붙잡고 있는 메모리가 함께 쌓여 결국 OOM으로 이어진다. **대기열은 반드시 유한해야 한다**는 원칙은 29.6의 재시도 예산과 같은 사상이다.

### 풀 오류를 반드시 처리한다

`pg.Pool`은 유휴 연결에서 오류가 발생하면 `error` 이벤트를 발생시킨다. 이 리스너를 등록하지 않으면 `EventEmitter`의 규칙에 따라 **처리되지 않은 `error` 이벤트가 예외로 던져져 프로세스가 죽는다.** 데이터베이스가 재시작할 때마다 애플리케이션이 죽는 사고의 흔한 원인이다.

```js
pool.on('error', (err, client) => {
  // 유휴 연결에서 발생한 오류다. 풀이 알아서 해당 연결을 버리고 새로 만든다.
  logger.error({ err }, '유휴 DB 연결 오류 — 풀이 연결을 교체한다')
})

pool.on('connect', () => logger.debug('DB 연결 생성'))
pool.on('remove', () => logger.debug('DB 연결 제거'))
```

`pg.Pool`은 이미 자동 재연결을 한다는 점을 이해하는 것이 중요하다. 풀에서 연결을 꺼내려 할 때 유효한 유휴 연결이 없으면 새로 만든다. 별도의 재연결 루프를 직접 짤 필요가 없다. 진짜로 필요한 것은 **연결 실패 시 실패한 쿼리를 재시도할지 결정하는 로직**이다.

```js
// 재시도해도 안전한 오류인지 판별한다
const RETRYABLE_PG_CODES = new Set([
  '57P01',  // admin_shutdown — 관리자에 의한 종료
  '57P02',  // crash_shutdown
  '57P03',  // cannot_connect_now — 시작 중
  '08000',  // connection_exception
  '08006',  // connection_failure
  '40001',  // serialization_failure — 직렬화 충돌
  '40P01'   // deadlock_detected
])

function isRetryableDbError(err) {
  if (RETRYABLE_PG_CODES.has(err.code)) return true
  // 소켓 레벨 오류
  return ['ECONNRESET', 'ECONNREFUSED', 'ETIMEDOUT', 'EPIPE'].includes(err.code)
}
```

**여기서 반드시 지켜야 할 경계가 있다.** 재시도는 **읽기 쿼리와 명시적으로 멱등한 쓰기**에만 안전하다. `INSERT`를 재시도했는데 원래 요청이 사실은 커밋되었고 응답만 유실된 것이었다면 중복 행이 생긴다. 쓰기 재시도는 29.5의 멱등성 장치와 함께여야만 안전하다.

### 시작 시 재시도

컨테이너 오케스트레이션 환경에서는 애플리케이션이 데이터베이스보다 먼저 뜨는 일이 흔하다. 이때 시작 즉시 연결에 실패하고 프로세스가 죽으면, 오케스트레이터가 재시작하고 다시 실패하는 `CrashLoopBackOff`에 빠진다. 결국 복구되긴 하지만 재시작 백오프 때문에 몇 분이 낭비된다. 시작 시에는 인내심 있게 기다리는 편이 낫다.

```js
import { setTimeout as sleep } from 'node:timers/promises'

export async function waitForDatabase(pool, { attempts = 30, baseMs = 500, maxMs = 5_000 } = {}) {
  let lastError
  for (let i = 0; i < attempts; i++) {
    try {
      const client = await pool.connect()
      try {
        await client.query('SELECT 1')
      } finally {
        client.release()   // 성공하든 실패하든 반드시 반납한다
      }
      logger.info({ attempt: i + 1 }, '데이터베이스 연결 확인')
      return
    } catch (err) {
      lastError = err
      const delay = Math.min(maxMs, baseMs * 2 ** i)
      logger.warn({ err, attempt: i + 1, delay }, 'DB 연결 대기 중')
      await sleep(delay)
    }
  }
  throw new Error(`데이터베이스 연결 실패 (${attempts}회 시도)`, { cause: lastError })
}
```

`client.release()`를 `finally`에 두는 것이 핵심이다. 연결을 반납하지 않으면 풀이 고갈되고, 이는 데이터베이스 관련 장애 중 가장 진단하기 어려운 축에 속한다. 증상이 "쿼리가 갑자기 전부 타임아웃"이라서 데이터베이스를 의심하게 되지만, 실제로는 애플리케이션이 연결을 새고 있는 것이다. 가능하면 연결을 직접 다루지 말고 래퍼를 쓴다.

```js
export async function withTransaction(pool, fn) {
  const client = await pool.connect()
  try {
    await client.query('BEGIN')
    const result = await fn(client)
    await client.query('COMMIT')
    return result
  } catch (err) {
    // 롤백 자체가 실패할 수 있다(연결이 이미 죽은 경우) — 원본 오류를 가리면 안 된다
    try {
      await client.query('ROLLBACK')
    } catch (rollbackErr) {
      logger.error({ err: rollbackErr }, '롤백 실패')
    }
    throw err
  } finally {
    client.release()
  }
}
```

롤백 실패를 삼키고 원본 오류를 던지는 것이 중요하다. 롤백이 실패하는 상황은 대개 연결이 이미 끊긴 경우인데, 이때 롤백 오류를 던지면 진짜 원인이 사라진다.

### 준비 상태와 활성 상태를 구분한다

쿠버네티스의 두 프로브는 목적이 다르다. 데이터베이스 상태를 반영해야 하는 것은 **준비(readiness)** 프로브다.

```js
// 활성 프로브: 이벤트 루프가 살아 있는가 — 의존성을 확인하지 않는다
app.get('/healthz', (req, res) => res.status(200).send('ok'))

// 준비 프로브: 지금 트래픽을 받을 수 있는가 — 의존성을 확인한다
app.get('/readyz', async (req, res) => {
  try {
    await pool.query('SELECT 1')
    res.status(200).json({ status: 'ready' })
  } catch (err) {
    res.status(503).json({ status: 'not-ready', reason: 'database' })
  }
})
```

활성 프로브에서 데이터베이스를 확인하면 안 된다. 데이터베이스가 잠깐 흔들렸을 때 오케스트레이터가 **모든 애플리케이션 인스턴스를 동시에 재시작**하기 때문이다. 데이터베이스 장애가 애플리케이션 전면 장애로 증폭된다. 준비 프로브는 트래픽만 차단하므로 데이터베이스가 돌아오면 자동으로 회복된다.

## 29.5 멱등성과 메시징 복원력

### 중복은 예외가 아니라 기본값이다

분산 시스템에서 메시지 전달 보장은 세 등급으로 나뉜다. 최대 한 번(at-most-once)은 유실을 허용하고, 정확히 한 번(exactly-once)은 종단 간으로는 사실상 불가능하며, 실무에서 쓰는 것은 **최소 한 번(at-least-once)**이다(23장 참조). 최소 한 번은 정의상 중복 전달을 허용한다. 즉 **중복 처리는 버그가 아니라 정상 동작이며, 이를 견디는 것은 소비자(consumer)의 책임이다.**

중복이 발생하는 구체적 경로를 보면 왜 피할 수 없는지 분명해진다.

```text
소비자가 메시지 처리 완료 → DB 커밋 성공 → ACK 전송 → 네트워크 유실
                                                        ↓
                                        브로커는 ACK를 못 받음
                                                        ↓
                                        가시성 타임아웃 후 재전달
```

처리와 ACK 사이에는 원자성이 없다. 어느 쪽을 먼저 하든 사이에 죽으면 문제가 생긴다. ACK를 먼저 하면 유실이고, 처리를 먼저 하면 중복이다. 유실보다 중복이 낫기 때문에 처리를 먼저 하고, 중복은 멱등성으로 흡수한다.

### 방법 1: 자연 멱등 연산

가장 좋은 해결책은 연산 자체를 여러 번 수행해도 결과가 같게 설계하는 것이다.

```js
// 멱등하지 않다 — 두 번 실행되면 잔액이 두 배로 준다
await db.query('UPDATE accounts SET balance = balance - $1 WHERE id = $2', [amount, id])

// 멱등하다 — 몇 번 실행해도 결과가 같다
await db.query('UPDATE accounts SET balance = $1 WHERE id = $2', [newBalance, id])
```

같은 원리가 다른 곳에도 적용된다. `상태 = 'SHIPPED'`로 설정하는 것은 멱등하지만 `상태를 다음 단계로 진행`은 멱등하지 않다. 집합에 원소를 추가하는 `SADD`는 멱등하지만 리스트에 추가하는 `LPUSH`는 아니다. 절대 갱신(absolute update)이 상대 갱신(relative update)보다 낫다는 원칙이다.

`UPSERT`도 자연 멱등의 대표적 도구다.

```js
await db.query(`
  INSERT INTO user_settings (user_id, theme, updated_at)
  VALUES ($1, $2, $3)
  ON CONFLICT (user_id) DO UPDATE
    SET theme = EXCLUDED.theme, updated_at = EXCLUDED.updated_at
    -- 오래된 메시지가 새 값을 덮어쓰지 않게 한다
    WHERE user_settings.updated_at < EXCLUDED.updated_at
`, [userId, theme, updatedAt])
```

`WHERE` 절이 중요하다. 메시지 순서는 보장되지 않으므로, 타임스탬프나 버전으로 오래된 갱신을 걸러내야 한다. 이것이 없으면 중복은 막아도 순서 역전은 막지 못한다.

### 방법 2: 멱등성 키와 처리 기록 테이블

연산 자체를 멱등하게 만들 수 없을 때(이메일 발송, 외부 결제 호출 등) 쓰는 방법이다. 각 메시지에 고유한 멱등성 키(idempotency key)를 부여하고, 처리한 키를 기록해 두 번째 시도를 걸러낸다.

핵심은 **처리 기록과 비즈니스 로직이 같은 트랜잭션 안에 있어야 한다**는 것이다. 따로 하면 "처리는 했는데 기록은 못 한" 창이 생겨 중복이 새어 나간다.

```sql
CREATE TABLE processed_messages (
  idempotency_key TEXT PRIMARY KEY,
  result          JSONB,
  processed_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
-- 오래된 기록은 주기적으로 삭제한다(브로커의 최대 재전달 기간보다 길게 보관)
CREATE INDEX ON processed_messages (processed_at);
```

```js
export async function processOnce(pool, key, work) {
  return withTransaction(pool, async (client) => {
    // 같은 키를 동시에 처리하는 다른 소비자를 차단한다
    const claimed = await client.query(
      `INSERT INTO processed_messages (idempotency_key)
       VALUES ($1)
       ON CONFLICT (idempotency_key) DO NOTHING
       RETURNING idempotency_key`,
      [key]
    )

    if (claimed.rowCount === 0) {
      // 이미 처리된 메시지다. 저장된 결과를 그대로 돌려준다.
      const prev = await client.query(
        'SELECT result FROM processed_messages WHERE idempotency_key = $1',
        [key]
      )
      logger.info({ key }, '중복 메시지 — 저장된 결과를 반환한다')
      return { duplicate: true, result: prev.rows[0]?.result ?? null }
    }

    // 비즈니스 로직을 같은 트랜잭션에서 수행한다
    const result = await work(client)

    await client.query(
      'UPDATE processed_messages SET result = $2 WHERE idempotency_key = $1',
      [key, result ?? null]
    )
    return { duplicate: false, result }
  })
}
```

`INSERT ... ON CONFLICT DO NOTHING RETURNING`은 "선점에 성공했는가"를 원자적으로 알려준다. 동시에 두 소비자가 같은 메시지를 받아도 한쪽만 `rowCount === 1`을 받는다. 나머지 한쪽은 트랜잭션이 끝날 때까지 잠깐 대기하다가 0을 받는다.

**멱등성 키는 어디서 오는가.** 브로커가 주는 메시지 ID를 그대로 쓰면 안 되는 경우가 있다. 브로커가 재전달할 때 새 ID를 부여한다면 중복 판별에 쓸모가 없다. 가장 안전한 것은 **메시지를 만드는 쪽(producer)이 비즈니스 의미를 담아 키를 생성**하는 것이다. 예를 들어 `order-${orderId}-payment-captured`처럼 만들면 같은 사건에 대해 항상 같은 키가 나온다. 클라이언트가 `Idempotency-Key` 헤더로 직접 제공하는 방식도 결제 API에서 표준적으로 쓰인다.

**외부 부수 효과의 한계**도 인정해야 한다. `work()` 안에서 이메일을 보냈다면, 그 뒤 트랜잭션이 롤백되어도 이메일은 이미 나갔다. 데이터베이스 트랜잭션은 외부 시스템을 되돌리지 못한다. 이 문제의 정석적인 해법은 트랜잭셔널 아웃박스(transactional outbox)로, 부수 효과를 DB 테이블에 기록만 하고 별도 프로세스가 그 테이블을 읽어 실행하는 것이다(23장 참조).

### 방법 3: 유니크 제약

가장 단순하면서 가장 견고한 방법이다. 데이터베이스가 중복을 물리적으로 거부하게 한다.

```js
try {
  await db.query(
    'INSERT INTO payments (order_id, amount, external_ref) VALUES ($1, $2, $3)',
    [orderId, amount, externalRef]
  )
} catch (err) {
  if (err.code === '23505') {   // unique_violation
    // 중복 시도다 — 이미 처리되었으므로 성공으로 취급한다
    logger.info({ orderId }, '중복 결제 시도 차단')
    return { alreadyProcessed: true }
  }
  throw err
}
```

애플리케이션 레벨의 `SELECT` 후 `INSERT` 검사는 경합 조건에 취약하다. 두 프로세스가 동시에 `SELECT`해서 둘 다 없다고 판단하면 둘 다 `INSERT`한다. 유니크 제약은 이 경합을 데이터베이스 수준에서 원천 차단한다. **정확성을 애플리케이션 코드가 아니라 스키마에 새기는 것**이 요점이다.

### 소비자의 실패 처리

멱등성이 갖춰졌다면 소비자는 실패한 메시지를 안심하고 다시 처리할 수 있다. 남은 문제는 **영원히 실패하는 메시지**다. 잘못된 형식이거나 참조하는 데이터가 삭제된 메시지는 몇 번을 재시도해도 성공하지 않는다. 이런 메시지가 큐 앞을 막으면 뒤의 정상 메시지가 전부 밀린다(head-of-line blocking).

해결책은 데드 레터 큐(dead letter queue, DLQ)다. 재시도 횟수를 세고, 상한을 넘으면 별도 큐로 보낸 뒤 원래 큐에서는 ACK한다.

```js
const MAX_DELIVERIES = 5

async function onMessage(msg) {
  const key = msg.headers['idempotency-key'] ?? msg.id
  const deliveries = Number(msg.headers['x-delivery-count'] ?? 1)

  try {
    await processOnce(pool, key, (client) => handleBusinessLogic(client, msg.body))
    await msg.ack()
  } catch (err) {
    if (deliveries >= MAX_DELIVERIES) {
      logger.error({ err, key, deliveries }, '재시도 상한 도달 — DLQ로 이동')
      await deadLetterQueue.send(msg, { reason: err.message })
      await msg.ack()   // 원본 큐에서는 제거한다
      return
    }
    logger.warn({ err, key, deliveries }, '메시지 처리 실패 — 재전달을 요청한다')
    await msg.nack()    // 브로커가 백오프 후 재전달한다
  }
}
```

DLQ는 만들어두고 보지 않으면 의미가 없다. DLQ 크기에 알림을 걸어두고, 쌓이면 사람이 원인을 확인하고 재투입하는 절차까지가 설계에 포함되어야 한다.

## 29.6 재시도, 지수 백오프, 서킷 브레이커

### 세 장치의 역할 분담

원격 호출을 안전하게 만드는 세 장치는 서로 다른 층위에서 동작한다. 혼동하면 잘못 조합하게 된다.

- **재시도(retry)**는 **일시적 실패**를 흡수한다. 패킷 하나가 유실되었거나 서버 인스턴스 하나가 방금 재시작 중일 때, 다시 시도하면 성공한다.
- **백오프(backoff)**는 재시도가 **상대를 더 밀어붙이지 않게** 한다. 이미 과부하인 서버에 즉시 재시도를 퍼붓는 것은 불을 끄려고 기름을 붓는 것과 같다.
- **서킷 브레이커(circuit breaker)**는 **지속적 실패**에 대응한다. 상대가 완전히 죽었다면 재시도는 시간 낭비이자 자원 낭비다. 아예 시도하지 않고 즉시 실패하는 것이 낫다.

정리하면 재시도는 "한 번 더 해보자", 서킷 브레이커는 "당분간 하지 말자"다.

### 재시도해도 되는 오류 판별

재시도의 첫 번째 규칙은 **아무거나 재시도하지 않는 것**이다. `400 Bad Request`를 재시도하면 같은 응답이 돌아온다. 시간과 자원만 낭비하고 지연만 늘어난다. 판별 기준은 두 축이다. 오류가 일시적인가, 그리고 연산이 멱등한가.

```js
// 재시도 가능한 HTTP 상태 코드
const RETRYABLE_STATUS = new Set([408, 429, 500, 502, 503, 504])
// 재시도 가능한 소켓 오류
const RETRYABLE_SYSCALL = new Set([
  'ECONNRESET', 'ECONNREFUSED', 'ETIMEDOUT', 'EPIPE',
  'EAI_AGAIN',        // DNS 일시 실패
  'ENOTFOUND',        // DNS 캐시 갱신 중일 수 있다
  'UND_ERR_CONNECT_TIMEOUT'
])
// 재시도해도 안전한 HTTP 메서드 (멱등성이 규약으로 보장된다)
const IDEMPOTENT_METHODS = new Set(['GET', 'HEAD', 'OPTIONS', 'PUT', 'DELETE'])

export function isRetryable(err, { method = 'GET' } = {}) {
  // 호출자가 취소한 것은 재시도 대상이 아니다
  if (err.name === 'AbortError' && err.cause?.name === 'UserAbort') return false

  if (!IDEMPOTENT_METHODS.has(method) && !err.hasIdempotencyKey) return false
  if (RETRYABLE_SYSCALL.has(err.code)) return true
  if (typeof err.status === 'number') return RETRYABLE_STATUS.has(err.status)
  return false
}
```

`POST`는 기본적으로 재시도하지 않는다는 점이 중요하다. `POST` 재시도가 안전해지려면 29.5의 멱등성 키가 함께 있어야 한다. 코드에서 `err.hasIdempotencyKey`로 그 조건을 명시적으로 표현했다.

`429 Too Many Requests`와 `503`은 특별 취급할 가치가 있다. 서버가 `Retry-After` 헤더를 주면 그 값을 따르는 것이 예의이자 최선이다. 서버가 자기 회복 시점을 가장 잘 알기 때문이다.

### 지수 백오프와 지터

지수 백오프는 재시도 간격을 시도할 때마다 배로 늘리는 것이다. 1초, 2초, 4초, 8초. 실패가 계속되면 압력을 급격히 줄여 상대에게 회복할 시간을 준다.

여기에 **지터(jitter)**가 반드시 필요하다. 이유는 다음 시나리오로 분명해진다. 데이터베이스가 5초간 멈췄다가 회복한다고 하자. 그 사이 1,000개의 요청이 실패했고, 전부 정확히 1초 뒤 재시도하도록 예약되었다. 1초 뒤, 1,000개의 요청이 **동시에** 데이터베이스를 때린다. 방금 회복한 데이터베이스는 다시 무너진다. 그리고 다시 1,000개가 2초 뒤로 예약된다. 이 동기화 현상을 **재시도 무리 짓기(thundering herd)**라고 한다.

지터는 각 재시도 시점을 무작위로 흩뿌려 이 동기화를 깬다.

```js
/**
 * 완전 지터(full jitter): [0, exponential] 구간의 균등 난수를 대기 시간으로 쓴다.
 * AWS 아키텍처 블로그의 실험에서 총 완료 시간과 서버 부하 양쪽에서
 * 가장 좋은 결과를 낸 방식이다.
 */
function fullJitterDelay(attempt, { baseMs = 200, maxMs = 30_000 } = {}) {
  const exponential = Math.min(maxMs, baseMs * 2 ** attempt)
  return Math.random() * exponential
}

/**
 * 균등 지터(equal jitter): 절반은 고정, 절반은 난수.
 * 최소 대기를 보장하고 싶을 때 쓴다.
 */
function equalJitterDelay(attempt, { baseMs = 200, maxMs = 30_000 } = {}) {
  const exponential = Math.min(maxMs, baseMs * 2 ** attempt)
  return exponential / 2 + Math.random() * (exponential / 2)
}
```

지터 없는 지수 백오프는 절반만 구현한 것이다. 무리 짓기를 막지 못하면 백오프의 목적 자체가 달성되지 않는다.

### 재시도 폭풍과 재시도 예산

재시도가 장애를 **증폭**시키는 방식을 이해해야 한다. 서비스 A가 B를, B가 C를 호출하는 3계층 구조에서 각 계층이 3번씩 재시도한다고 하자. C가 죽으면 B는 3번 시도하고, A는 그 B 호출을 다시 3번 시도한다. 원래 요청 하나가 C에 대한 9번의 호출이 된다. 계층이 하나 더 있으면 27번이다. 이것이 **재시도 폭풍(retry storm)**이다. C가 잠깐 흔들렸을 뿐인데 트래픽이 9배로 뛰어 완전히 무너지고, 그 상태가 고착된다.

대응책은 셋이다.

**첫째, 재시도는 한 계층에서만 한다.** 대개 최전방(사용자와 맞닿은 층)이나 가장 안쪽(실제 호출) 중 하나를 고른다. 중간 계층은 재시도 없이 오류를 그대로 전파한다.

**둘째, 재시도 예산(retry budget)을 둔다.** "재시도는 전체 요청의 N%를 넘지 않는다"는 제약이다. 정상 상황에서는 실패가 드물어 예산이 남고 재시도가 자유롭게 일어난다. 대규모 장애 상황에서는 실패율이 높아 예산이 즉시 소진되고, 재시도가 자동으로 멈춘다. 정확히 필요할 때 필요한 만큼만 억제하는 셈이다.

```js
/**
 * 토큰 버킷 기반 재시도 예산.
 * 성공적인 요청이 토큰을 적립하고, 재시도가 토큰을 소비한다.
 * ratio=0.1이면 재시도는 전체 트래픽의 약 10%로 제한된다.
 */
export class RetryBudget {
  #tokens
  #maxTokens
  #ratio

  constructor({ maxTokens = 100, ratio = 0.1 } = {}) {
    this.#tokens = maxTokens
    this.#maxTokens = maxTokens
    this.#ratio = ratio
  }

  // 요청을 한 번 시도할 때마다 호출한다
  recordAttempt() {
    this.#tokens = Math.min(this.#maxTokens, this.#tokens + this.#ratio)
  }

  // 재시도 허가를 요청한다. 예산이 없으면 false.
  tryConsume() {
    if (this.#tokens < 1) return false
    this.#tokens -= 1
    return true
  }

  get remaining() {
    return Math.floor(this.#tokens)
  }
}
```

**셋째, 데드라인을 전파한다.** 요청 전체에 남은 시간을 계산해, 재시도가 그 시간을 넘길 것 같으면 시도하지 않는다. 이미 클라이언트가 포기한 요청을 재시도하는 것은 순수한 낭비다.

### 서킷 브레이커

서킷 브레이커는 전기 회로의 차단기에서 이름을 따왔다. 상태가 셋이다.

- **닫힘(closed)**: 정상. 요청이 그대로 통과한다. 실패를 세다가 임계치를 넘으면 열림으로 전이한다.
- **열림(open)**: 차단. 모든 요청이 실제 호출 없이 즉시 실패한다. 일정 시간(리셋 타임아웃)이 지나면 반열림으로 전이한다.
- **반열림(half-open)**: 탐색. 제한된 수의 요청만 통과시켜 상대가 회복했는지 확인한다. 성공하면 닫힘으로, 실패하면 다시 열림으로 간다.

열림 상태의 가치는 두 가지다. 첫째, 죽은 서비스를 기다리느라 스레드와 메모리를 낭비하지 않는다. 타임아웃 30초를 기다리는 요청 1,000개는 그 자체로 자원 고갈이다. 둘째, 회복 중인 서비스에 트래픽을 보내지 않아 회복을 방해하지 않는다.

```js
export class CircuitBreaker {
  static CLOSED = 'closed'
  static OPEN = 'open'
  static HALF_OPEN = 'half-open'

  #state = CircuitBreaker.CLOSED
  #failures = 0
  #successes = 0
  #openedAt = 0
  #halfOpenInFlight = 0

  #failureThreshold
  #successThreshold
  #resetTimeoutMs
  #halfOpenMaxConcurrent
  #name

  constructor({
    name = 'default',
    failureThreshold = 5,      // 연속 실패 몇 번에 열 것인가
    successThreshold = 2,      // 반열림에서 몇 번 성공하면 닫을 것인가
    resetTimeoutMs = 30_000,   // 열림 상태를 얼마나 유지할 것인가
    halfOpenMaxConcurrent = 1  // 반열림에서 동시에 몇 개를 통과시킬 것인가
  } = {}) {
    this.#name = name
    this.#failureThreshold = failureThreshold
    this.#successThreshold = successThreshold
    this.#resetTimeoutMs = resetTimeoutMs
    this.#halfOpenMaxConcurrent = halfOpenMaxConcurrent
  }

  get state() {
    // 열림 상태의 만료를 지연 평가한다 — 타이머가 필요 없다
    if (this.#state === CircuitBreaker.OPEN &&
        Date.now() - this.#openedAt >= this.#resetTimeoutMs) {
      this.#transitionTo(CircuitBreaker.HALF_OPEN)
    }
    return this.#state
  }

  async execute(fn) {
    const state = this.state

    if (state === CircuitBreaker.OPEN) {
      throw new CircuitOpenError(this.#name, this.#retryAfterMs())
    }

    if (state === CircuitBreaker.HALF_OPEN) {
      // 탐색 요청은 소수만 통과시킨다. 전부 통과시키면
      // 아직 회복 못 한 서비스에 다시 부하를 몰아주게 된다.
      if (this.#halfOpenInFlight >= this.#halfOpenMaxConcurrent) {
        throw new CircuitOpenError(this.#name, this.#retryAfterMs())
      }
      this.#halfOpenInFlight++
    }

    try {
      const result = await fn()
      this.#onSuccess()
      return result
    } catch (err) {
      this.#onFailure(err)
      throw err
    } finally {
      if (state === CircuitBreaker.HALF_OPEN) this.#halfOpenInFlight--
    }
  }

  #onSuccess() {
    if (this.#state === CircuitBreaker.HALF_OPEN) {
      this.#successes++
      if (this.#successes >= this.#successThreshold) {
        this.#transitionTo(CircuitBreaker.CLOSED)
      }
      return
    }
    this.#failures = 0
  }

  #onFailure(err) {
    // 4xx 같은 클라이언트 오류는 상대의 건강 문제가 아니다.
    // 이런 오류로 회로를 열면 내 버그 때문에 정상 서비스를 차단하게 된다.
    if (!this.#countsAsFailure(err)) return

    if (this.#state === CircuitBreaker.HALF_OPEN) {
      this.#transitionTo(CircuitBreaker.OPEN)
      return
    }
    this.#failures++
    if (this.#failures >= this.#failureThreshold) {
      this.#transitionTo(CircuitBreaker.OPEN)
    }
  }

  #countsAsFailure(err) {
    if (typeof err.status === 'number' && err.status >= 400 && err.status < 500) {
      return err.status === 429   // 레이트 리밋만 건강 문제로 센다
    }
    return true
  }

  #transitionTo(next) {
    const prev = this.#state
    if (prev === next) return
    this.#state = next
    this.#failures = 0
    this.#successes = 0
    if (next === CircuitBreaker.OPEN) this.#openedAt = Date.now()
    logger.warn({ breaker: this.#name, from: prev, to: next }, '서킷 브레이커 상태 전이')
  }

  #retryAfterMs() {
    return Math.max(0, this.#resetTimeoutMs - (Date.now() - this.#openedAt))
  }
}

export class CircuitOpenError extends Error {
  constructor(name, retryAfterMs) {
    super(`서킷 브레이커 '${name}'가 열려 있다`)
    this.name = 'CircuitOpenError'
    this.code = 'CIRCUIT_OPEN'
    this.retryAfterMs = retryAfterMs
  }
}
```

세 가지 설계 판단을 짚어둔다.

**연속 실패 대신 실패율을 쓸 수도 있다.** 위 구현은 연속 실패를 센다. 단순하지만, 성공과 실패가 번갈아 나오는 부분 장애에서는 절대 열리지 않는다. 프로덕션에서는 슬라이딩 윈도 안의 실패율(예: 최근 20건 중 50% 실패)을 쓰는 편이 정확하다. `opossum` 같은 라이브러리가 이 방식을 제공한다.

**반열림의 동시성을 반드시 제한해야 한다.** 이 제한이 없으면, 열림 시간이 끝나는 순간 대기하던 모든 요청이 한꺼번에 통과해 회복 중인 서비스를 다시 무너뜨린다. 앞서 본 무리 짓기가 서킷 브레이커 안에서 재현되는 것이다.

**4xx를 실패로 세지 않는다.** 내 코드가 잘못된 요청을 보내는 버그가 있을 때, 그것으로 회로를 열면 멀쩡한 상대 서비스를 스스로 차단하게 된다. 429는 예외인데, 이건 상대가 "지금 나에게 부담을 주지 마라"고 말하는 것이므로 차단이 옳은 반응이다.

### 세 장치를 조합한 클라이언트

이제 타임아웃, 재시도, 백오프, 예산, 서킷 브레이커를 하나로 묶는다. **순서가 중요하다.** 서킷 브레이커는 재시도 루프의 **안쪽**에 있어야 한다. 그래야 회로가 열린 순간 남은 재시도가 즉시 중단된다. 바깥에 두면 회로가 열려도 재시도 루프가 계속 돌아 지연만 늘어난다.

```js
import { setTimeout as sleep } from 'node:timers/promises'

export class ResilientClient {
  #breaker
  #budget
  #maxAttempts
  #baseMs
  #timeoutMs

  constructor({ name, maxAttempts = 3, baseMs = 200, timeoutMs = 3_000, breaker, budget } = {}) {
    this.#breaker = breaker ?? new CircuitBreaker({ name })
    this.#budget = budget ?? new RetryBudget()
    this.#maxAttempts = maxAttempts
    this.#baseMs = baseMs
    this.#timeoutMs = timeoutMs
  }

  /**
   * @param {string} url
   * @param {object} options - method, body, headers, deadline(절대 시각 ms)
   */
  async request(url, options = {}) {
    const { method = 'GET', deadline = Date.now() + 10_000, signal } = options
    let lastError

    for (let attempt = 0; attempt < this.#maxAttempts; attempt++) {
      // 데드라인을 넘겼으면 시도 자체를 하지 않는다
      if (Date.now() >= deadline) {
        throw new Error('데드라인 초과', { cause: lastError })
      }

      // 첫 시도가 아니라면 예산을 소비해야 한다
      if (attempt > 0 && !this.#budget.tryConsume()) {
        logger.warn({ url }, '재시도 예산 소진 — 재시도를 포기한다')
        throw lastError
      }
      this.#budget.recordAttempt()

      try {
        return await this.#breaker.execute(() =>
          this.#fetchWithTimeout(url, options, deadline, signal)
        )
      } catch (err) {
        lastError = err

        // 회로가 열렸다면 더 시도해봐야 전부 즉시 실패한다
        if (err.code === 'CIRCUIT_OPEN') throw err
        if (!isRetryable(err, { method })) throw err
        if (attempt === this.#maxAttempts - 1) throw err

        const delay = this.#nextDelay(attempt, err)
        // 대기했다가 데드라인을 넘길 것 같으면 지금 포기한다
        if (Date.now() + delay >= deadline) throw err

        logger.info({ url, attempt: attempt + 1, delay, err: err.message }, '재시도 대기')
        await sleep(delay, undefined, { signal })
      }
    }
    throw lastError
  }

  #nextDelay(attempt, err) {
    // 서버가 Retry-After를 줬다면 그 값을 존중한다
    if (err.retryAfterMs != null) {
      return err.retryAfterMs + Math.random() * 250   // 약간의 지터는 여전히 필요하다
    }
    return fullJitterDelay(attempt, { baseMs: this.#baseMs })
  }

  async #fetchWithTimeout(url, options, deadline, outerSignal) {
    // 개별 시도의 타임아웃과 전체 데드라인 중 짧은 쪽을 쓴다
    const budgetMs = Math.min(this.#timeoutMs, deadline - Date.now())
    const timeoutSignal = AbortSignal.timeout(budgetMs)
    const signal = outerSignal
      ? AbortSignal.any([outerSignal, timeoutSignal])
      : timeoutSignal

    const res = await fetch(url, { ...options, signal })

    if (!res.ok) {
      const err = new Error(`HTTP ${res.status} ${res.statusText}`)
      err.status = res.status
      const retryAfter = res.headers.get('retry-after')
      if (retryAfter) err.retryAfterMs = Number(retryAfter) * 1000
      throw err
    }
    return res
  }
}
```

`AbortSignal.timeout()`과 `AbortSignal.any()`는 Node.js 20에서 안정화된 API다. 예전처럼 `AbortController`와 `setTimeout`을 직접 조합할 필요가 없고, 타이머 정리도 알아서 된다. `AbortSignal.any()`는 여러 신호 중 하나라도 중단되면 중단되는 신호를 만든다. 호출자의 취소와 자체 타임아웃을 함께 존중해야 하는 상황에 정확히 맞는다.

**타임아웃은 재시도보다 근본적이다.** 타임아웃 없는 호출은 재시도할 기회조차 없다. 영원히 응답을 기다리며 자원을 붙잡고 있을 뿐이다. 외부로 나가는 모든 호출에 타임아웃을 붙이는 것이 복원력의 출발점이다.

### 폴백과 우아한 성능 저하

세 장치가 전부 작동해도 결국 호출은 실패한다. 그때 무엇을 반환할지가 사용자 경험을 결정한다. 전면 500 응답 대신, 기능 일부를 줄여 서비스를 유지하는 것을 **우아한 성능 저하(graceful degradation)**라고 한다.

```js
export async function getRecommendations(userId) {
  try {
    return await recommendationClient.request(`/users/${userId}/recommendations`)
  } catch (err) {
    if (err.code === 'CIRCUIT_OPEN' || isRetryable(err)) {
      logger.warn({ err, userId }, '추천 서비스 실패 — 인기 상품으로 대체한다')
      // 캐시된 인기 상품 목록은 개인화되지 않았지만 빈 화면보다 낫다
      return popularItemsCache.get('global') ?? []
    }
    throw err
  }
}
```

무엇을 저하시킬 수 있는지는 도메인 지식이다. 추천은 대체 가능하고, 결제는 아니다. 핵심 경로와 부가 경로를 미리 구분해두면 장애 시 어디를 포기할지 판단이 빨라진다.

## 29.7 복원력 테스트: 무작위 크래시, 이벤트 루프 정지, 비동기 실패 주입

### 왜 필요한가

지금까지 만든 장치는 전부 **장애 상황에서만 실행되는 코드**다. 그리고 장애 상황에서만 실행되는 코드는 정의상 평소에 검증되지 않는다. 실제로 운영 중 장애가 났을 때 서킷 브레이커의 로그 문장에 오타가 있어 `TypeError`가 나거나, 종료 핸들러가 `await`을 빠뜨려 아무것도 정리하지 못하는 일이 흔하다. 정작 필요한 순간에 안전장치가 고장 나 있는 것이다.

카오스 엔지니어링(chaos engineering)은 이 문제를 정면으로 다룬다. 통제된 조건에서 의도적으로 장애를 일으켜, 시스템이 예상대로 견디는지 확인한다. 원칙은 셋이다.

1. **정상 상태(steady state)를 먼저 정의한다.** "p99 지연 200ms 이하, 오류율 0.1% 이하"처럼 측정 가능해야 한다. 이 기준이 없으면 실험 결과를 판정할 수 없다.
2. **가설을 세운다.** "인스턴스 하나를 죽여도 오류율이 0.5%를 넘지 않는다"처럼 반증 가능해야 한다.
3. **폭발 반경(blast radius)을 제한한다.** 스테이징에서 시작하고, 즉시 중단할 수 있는 스위치를 둔다.

### 무작위 크래시 주입

가장 단순하면서 가장 많은 것을 드러내는 실험이다. 프로세스가 예고 없이 죽었을 때 진행 중이던 요청, 소비 중이던 메시지, 잡고 있던 락이 어떻게 되는지 확인한다.

```js
// chaos/crash.js
import process from 'node:process'

const enabled = process.env.CHAOS_CRASH === 'on'

/**
 * 무작위 시점에 프로세스를 죽인다.
 * mode에 따라 죽는 방식이 다르며, 각각이 다른 코드 경로를 검증한다.
 *  - 'sigterm': 우아한 종료 경로 (배포/스케일인 시뮬레이션)
 *  - 'sigkill': 즉사 (하드웨어 장애/OOM Killer 시뮬레이션)
 *  - 'throw'  : uncaughtException 경로
 */
export function startCrashChaos({
  minMs = 30_000,
  maxMs = 300_000,
  mode = 'sigkill'
} = {}) {
  if (!enabled) return () => {}
  if (process.env.NODE_ENV === 'production' && !process.env.CHAOS_ALLOW_PROD) {
    throw new Error('프로덕션에서 크래시 카오스를 켜려면 CHAOS_ALLOW_PROD가 필요하다')
  }

  const delay = minMs + Math.random() * (maxMs - minMs)
  const timer = setTimeout(() => {
    logger.warn({ mode, delay }, '카오스: 프로세스를 죽인다')
    switch (mode) {
      case 'sigterm':
        process.kill(process.pid, 'SIGTERM')
        break
      case 'throw':
        // 다음 틱에 던져 어떤 try/catch에도 잡히지 않게 한다
        setImmediate(() => { throw new Error('카오스 주입 예외') })
        break
      default:
        process.kill(process.pid, 'SIGKILL')
    }
  }, delay)

  timer.unref()   // 이 타이머가 정상 종료를 막지 않게 한다
  return () => clearTimeout(timer)
}
```

`SIGKILL` 모드와 `SIGTERM` 모드는 완전히 다른 것을 검증한다. `SIGTERM`은 우아한 종료 코드가 실제로 동작하는지, 로드 밸런서에서 빠지는 시간이 충분한지, 진행 중인 요청이 끝까지 처리되는지를 본다. `SIGKILL`은 아무 정리도 없이 사라졌을 때 시스템 전체가 회복되는지를 본다. **후자가 훨씬 가혹하고, 훨씬 많은 것을 알려준다.** 미처리 메시지가 재전달되는가, 분산 락이 TTL로 풀리는가, 커넥션 풀이 정리되는가.

관측해야 할 지표는 명확하다. 죽는 순간의 오류율 스파이크 크기, 회복까지 걸린 시간, 그리고 **데이터 정합성**이다. 마지막 것이 가장 중요하다. 실험 후 중복 처리된 주문이나 유실된 메시지가 있다면 29.5의 멱등성 설계에 구멍이 있는 것이다.

### 이벤트 루프 정지 주입

Node.js에 고유한 장애 유형이다. 동기 CPU 작업이 이벤트 루프를 막으면 프로세스는 살아 있지만 아무 요청도 처리하지 못한다. 헬스 체크조차 응답하지 못해 오케스트레이터가 인스턴스를 죽인다. 큰 JSON을 파싱하거나, 정규식 백트래킹이 폭발하거나, 동기 암호화 함수를 쓸 때 실제로 일어난다(3장 참조).

```js
// chaos/block.js
const enabled = process.env.CHAOS_BLOCK === 'on'

/** 지정 시간만큼 이벤트 루프를 완전히 막는다 */
export function blockEventLoop(ms) {
  const until = Date.now() + ms
  // 바쁜 대기 — 실제 CPU 바운드 작업을 흉내낸다
  while (Date.now() < until) { /* 의도적 스핀 */ }
}

/** 주기적으로 무작위 길이만큼 이벤트 루프를 막는다 */
export function startBlockChaos({
  intervalMs = 20_000,
  minBlockMs = 100,
  maxBlockMs = 2_000,
  probability = 0.3
} = {}) {
  if (!enabled) return () => {}

  const timer = setInterval(() => {
    if (Math.random() > probability) return
    const blockMs = minBlockMs + Math.random() * (maxBlockMs - minBlockMs)
    logger.warn({ blockMs }, '카오스: 이벤트 루프를 막는다')
    blockEventLoop(blockMs)
  }, intervalMs)

  timer.unref()
  return () => clearInterval(timer)
}
```

이 실험이 드러내는 것은 **타임아웃 설정의 현실성**이다. 이벤트 루프가 500ms 막히면 그 사이 모든 요청의 지연이 500ms씩 늘어난다. 상류 서비스의 타임아웃이 300ms라면 전부 실패한다. 서킷 브레이커가 열리고, 재시도가 몰리고, 회복이 늦어진다.

실험과 함께 이벤트 루프 지연을 측정하는 코드를 붙여두면 인과관계를 확인할 수 있다.

```js
import { monitorEventLoopDelay } from 'node:perf_hooks'

const histogram = monitorEventLoopDelay({ resolution: 10 })
histogram.enable()

setInterval(() => {
  logger.info({
    // 나노초 단위이므로 밀리초로 변환한다
    meanMs: +(histogram.mean / 1e6).toFixed(2),
    p99Ms: +(histogram.percentile(99) / 1e6).toFixed(2),
    maxMs: +(histogram.max / 1e6).toFixed(2)
  }, 'event-loop-delay')
  histogram.reset()
}, 10_000).unref()
```

p99 이벤트 루프 지연은 Node.js 서비스에서 가장 중요한 단일 지표에 가깝다. 이 값이 100ms를 넘기 시작하면 무언가가 루프를 막고 있는 것이다(31장 참조).

### 비동기 실패 주입

가장 실용적인 카오스다. 외부 의존성 호출을 확률적으로 실패시키거나 느리게 만들어, 재시도·백오프·서킷 브레이커·폴백이 실제로 동작하는지 확인한다. 프로세스를 죽이지 않으므로 폭발 반경이 작고, 개발 환경에서도 켜둘 수 있다.

```js
// chaos/inject.js
class ChaosError extends Error {
  constructor(kind) {
    super(`카오스 주입 실패: ${kind}`)
    this.name = 'ChaosError'
    this.code = kind === 'timeout' ? 'ETIMEDOUT' : 'ECONNRESET'
    this.isChaos = true
  }
}

/**
 * 임의의 async 함수를 감싸 확률적으로 실패/지연시킨다.
 *
 * @param {Function} fn      감쌀 async 함수
 * @param {object}   config
 *  - failureRate: 즉시 실패시킬 확률 (0~1)
 *  - slowRate:    지연시킬 확률 (0~1)
 *  - slowMs:      지연 시간
 *  - label:       로그용 이름
 */
export function withChaos(fn, { failureRate = 0, slowRate = 0, slowMs = 3_000, label = 'unknown' } = {}) {
  if (process.env.CHAOS_ASYNC !== 'on') return fn

  return async function chaosWrapped(...args) {
    const roll = Math.random()

    if (roll < failureRate) {
      logger.warn({ label }, '카오스: 호출을 실패시킨다')
      throw new ChaosError('reset')
    }

    if (roll < failureRate + slowRate) {
      logger.warn({ label, slowMs }, '카오스: 호출을 지연시킨다')
      await new Promise((resolve) => setTimeout(resolve, slowMs))
    }

    return fn.apply(this, args)
  }
}
```

지연 주입이 실패 주입보다 중요하다는 점을 강조할 만하다. 즉시 실패하는 의존성은 다루기 쉽다. 오류가 명확하게 나고 폴백이 즉시 실행된다. **느린 의존성이 훨씬 위험하다.** 요청들이 응답을 기다리며 쌓이고, 메모리가 차고, 커넥션 풀이 고갈되고, 그 결과 이 의존성과 무관한 요청까지 실패한다. 하나의 느린 의존성이 전체 서비스를 마비시키는 것을 격벽(bulkhead) 없는 시스템의 전형적 실패 양상이라고 부른다.

의존성 경계에서 한 번에 적용하면 코드 침투가 최소화된다.

```js
// infra/payment-client.js
import { withChaos } from '../chaos/inject.js'

const rawCharge = async (orderId, amount) => {
  return paymentApi.request('/charges', {
    method: 'POST',
    body: JSON.stringify({ orderId, amount })
  })
}

// 프로덕션 코드는 이 함수만 안다. 카오스가 꺼져 있으면 원본 함수 그대로다.
export const charge = withChaos(rawCharge, {
  failureRate: 0.05,
  slowRate: 0.05,
  slowMs: 5_000,
  label: 'payment.charge'
})
```

### 스테이징에서 돌리는 절차

카오스 실험은 즉흥적으로 하는 것이 아니라 절차를 따른다.

**1) 사전 준비.** 실험 대상 환경에 프로덕션과 유사한 부하를 걸어둔다. 트래픽이 없는 환경에서 프로세스를 죽여봐야 아무것도 배우지 못한다. 그리고 정상 상태 지표를 최소 30분간 기록해 기준선을 만든다.

**2) 가설 문서화.** 실험 전에 예상 결과를 적는다. "인스턴스 3개 중 1개를 `SIGKILL`하면, 5초 내에 로드 밸런서가 제외하고, 그 사이 진행 중이던 최대 20건의 요청만 실패하며, 큐의 미처리 메시지는 30초 내 다른 인스턴스가 재처리한다." 적어두지 않으면 결과를 사후에 합리화하게 된다.

**3) 중단 조건 설정.** 실험을 즉시 멈출 조건을 미리 정한다. "오류율 5% 초과" 같은 것이다. 환경 변수 하나로 모든 카오스를 끌 수 있어야 하고, 그 사실을 실험 참가자 전원이 알아야 한다.

**4) 한 번에 하나씩.** 크래시와 지연을 동시에 주입하면 어느 것이 무엇을 유발했는지 알 수 없다. 변수를 하나만 바꾼다.

**5) 결과 기록과 수정.** 가설이 틀렸다면 그것이 발견이다. 수정하고 같은 실험을 다시 돌려 개선을 확인한다. 이 재실행이 없으면 카오스 테스트는 흥미로운 관찰로 끝난다.

```js
// chaos/index.js — 진입점에서 한 번에 제어한다
import { startCrashChaos } from './crash.js'
import { startBlockChaos } from './block.js'

export function initChaos() {
  if (process.env.CHAOS !== 'on') {
    logger.info('카오스 비활성')
    return () => {}
  }
  logger.warn('카오스 활성 — 이 프로세스는 의도적으로 불안정하다')

  const stoppers = [
    startCrashChaos({ mode: process.env.CHAOS_CRASH_MODE ?? 'sigkill' }),
    startBlockChaos()
  ]
  return () => stoppers.forEach((stop) => stop())
}
```

### 자동화된 복원력 테스트

카오스는 수동 실험만이 아니다. 앞서 만든 장치들은 단위 테스트로 검증할 수 있고, 검증해야 한다.

```js
import { test } from 'node:test'
import assert from 'node:assert/strict'
import { CircuitBreaker, CircuitOpenError } from '../src/circuit-breaker.js'

test('연속 실패가 임계치에 도달하면 회로가 열린다', async () => {
  const breaker = new CircuitBreaker({ failureThreshold: 3, resetTimeoutMs: 50 })
  const failing = () => Promise.reject(new Error('boom'))

  for (let i = 0; i < 3; i++) {
    await assert.rejects(breaker.execute(failing))
  }
  assert.equal(breaker.state, 'open')

  // 열린 상태에서는 실제 호출 없이 즉시 실패한다
  let called = false
  await assert.rejects(
    breaker.execute(() => { called = true; return Promise.resolve() }),
    CircuitOpenError
  )
  assert.equal(called, false, '열린 회로는 함수를 호출하지 않아야 한다')
})

test('리셋 타임아웃 후 반열림에서 성공하면 닫힌다', async () => {
  const breaker = new CircuitBreaker({
    failureThreshold: 1, successThreshold: 1, resetTimeoutMs: 20
  })
  await assert.rejects(breaker.execute(() => Promise.reject(new Error('boom'))))
  assert.equal(breaker.state, 'open')

  await new Promise((r) => setTimeout(r, 30))
  assert.equal(breaker.state, 'half-open')

  await breaker.execute(() => Promise.resolve('ok'))
  assert.equal(breaker.state, 'closed')
})

test('4xx는 회로를 열지 않는다', async () => {
  const breaker = new CircuitBreaker({ failureThreshold: 2 })
  const badRequest = () => Promise.reject(Object.assign(new Error('bad'), { status: 400 }))

  for (let i = 0; i < 5; i++) {
    await assert.rejects(breaker.execute(badRequest))
  }
  assert.equal(breaker.state, 'closed', '클라이언트 오류로 회로가 열리면 안 된다')
})
```

이런 테스트를 CI에 두면 복원력 로직이 리팩터링 중에 조용히 망가지는 것을 막을 수 있다. 장애 상황에서만 실행되는 코드를 평시에 실행시키는 가장 값싼 방법이다.

### 흔한 실수

- **프로덕션에서 먼저 시작하기.** 스테이징에서 가설이 통과한 뒤에만, 그리고 폭발 반경을 제한한 뒤에만 프로덕션으로 옮긴다.
- **관측 없이 실험하기.** 지표와 로그가 없으면 무슨 일이 일어났는지 모른 채 서비스만 흔든 것이 된다.
- **카오스 코드가 프로덕션 경로에 남기.** 환경 변수 기본값이 반드시 꺼짐이어야 하고, 켜는 순간 경고 로그가 남아야 한다.
- **한 번 하고 끝내기.** 시스템은 계속 변한다. 정기적으로(예: 스프린트마다) 반복해야 회귀를 잡는다.

## 요약

- Node.js 프로세스가 죽는 경로는 정상 종료, `process.exit()`, `uncaughtException`, `unhandledRejection`, V8 힙 한계 초과, 컨테이너 OOM Killer, 시그널로 나뉜다. 종료 코드(0, 1, 134, 137, 128+N)로 어느 경로인지 구분할 수 있다.
- `uncaughtException`을 잡고 실행을 계속해서는 안 된다. 예외가 스택을 뚫고 올라왔다는 것은 중간의 정리 코드가 전부 건너뛰어졌다는 뜻이며, 프로세스 메모리 상태는 이미 오염되었다. 핸들러의 정당한 용도는 마지막 로그를 남기고 종료하는 것뿐이다.
- 무상태란 요청 간에 유지되어야 하는 상태를 프로세스 메모리에 두지 않는다는 뜻이다. 세션, 캐시, 업로드 임시 파일, 스케줄러, 진행 중 작업, 카운터를 외부 저장소로 밀어내면 아무 인스턴스나 아무 요청을 처리할 수 있고 재시작이 안전해진다.
- 메모리 누수는 의도치 않은 참조다. 무한히 커지는 모듈 레벨 컬렉션, 제거하지 않은 이벤트 리스너, 큰 객체를 붙잡은 클로저, 정리하지 않은 타이머, 끝나지 않는 프로미스가 대표 유형이다. 인프로세스 캐시는 반드시 LRU와 TTL로 경계를 둔다.
- 데이터베이스 연결은 재시작, 페일오버, 유휴 타임아웃, 네트워크 단절로 반드시 끊긴다. 풀의 `max`는 인스턴스 수를 곱해 계산하고, `connectionTimeoutMillis`로 대기열을 유한하게 만들며, 풀의 `error` 이벤트를 반드시 처리한다. 활성 프로브에서 데이터베이스를 확인하면 DB 장애가 전면 재시작으로 증폭된다.
- 최소 한 번 전달에서 중복은 정상 동작이므로 소비자가 멱등성을 책임진다. 자연 멱등 연산(절대 갱신, UPSERT), 멱등성 키와 처리 기록 테이블(비즈니스 로직과 같은 트랜잭션), 유니크 제약 세 가지가 도구이며, 마지막 것이 가장 견고하다.
- 재시도는 일시적 실패를, 서킷 브레이커는 지속적 실패를 다룬다. 지터 없는 백오프는 재시도를 동기화시켜 무리 짓기를 만들고, 계층마다 재시도하면 재시도 폭풍으로 장애가 증폭된다. 재시도 예산과 데드라인 전파로 이를 억제하고, 서킷 브레이커는 재시도 루프 안쪽에 둔다.
- 장애 시에만 실행되는 코드는 평소에 검증되지 않는다. 무작위 크래시, 이벤트 루프 정지, 비동기 실패·지연 주입을 통제된 조건에서 돌려 안전장치가 실제로 동작하는지 확인한다. 즉시 실패보다 느린 응답이 시스템을 더 위험하게 만든다.

## 연습문제

**1. 종료 경로 분류기**

다음 다섯 가지 방식으로 프로세스를 죽이는 스크립트를 각각 작성하고, 종료 코드와 남는 로그를 표로 정리하라. (a) 처리되지 않은 예외, (b) `await` 없는 실패 프로미스, (c) `--max-old-space-size=64`로 실행 후 배열에 계속 문자열을 밀어넣기, (d) 다른 터미널에서 `kill -TERM`, (e) `kill -9`. 각 경우에 29.1의 핸들러를 등록한 버전과 등록하지 않은 버전을 비교하고, 핸들러가 실행되지 않는 경우가 어느 것이며 왜인지 설명하라. 추가로 (c)에서 `--heapsnapshot-near-heap-limit=1`을 붙였을 때 생성되는 스냅숏을 Chrome DevTools로 열어 어떤 객체가 힙을 채웠는지 확인하라.

**2. 경계 있는 캐시와 누수 재현**

29.3의 `LruCache`를 확장해 (a) 바이트 기준 상한(`maxBytes`와 값의 크기를 계산하는 `sizeOf` 콜백), (b) 적중률·축출 수·현재 크기를 노출하는 `stats()` 메서드, (c) 만료된 항목을 주기적으로 청소하는 `unref()`된 타이머를 추가하라. 그리고 이 캐시를 쓰지 않는 무한 `Map` 버전과 쓰는 버전을 각각 HTTP 서버에 붙여, `autocannon`으로 2분간 부하를 준 뒤 `process.memoryUsage().heapUsed` 추이를 비교하라. 두 그래프의 모양이 어떻게 다른지, 그리고 무한 `Map` 버전에서 힙 스냅숏의 Retainers 경로가 어디를 가리키는지 서술하라.

**3. 복원력 클라이언트 통합 실험**

29.6의 `ResilientClient`와 29.7의 `withChaos`를 조합해 다음을 수행하라. 먼저 확률적으로 실패·지연하는 모의 서버를 만든다(예: 처음 30초는 정상, 다음 30초는 100% 실패, 이후 정상으로 복귀). 이 서버를 향해 초당 50건의 요청을 보내면서 (a) 재시도만 있는 클라이언트, (b) 재시도 + 지터 백오프, (c) 재시도 + 백오프 + 서킷 브레이커 세 구성의 **모의 서버가 받은 총 요청 수**와 **클라이언트 측 p99 지연**을 각각 측정하라. 서킷 브레이커가 있을 때 서버가 받는 요청 수가 얼마나 줄어드는지, 그리고 회복 이후 정상으로 돌아가기까지 걸린 시간이 구성별로 어떻게 다른지 비교하라. 마지막으로 지터를 제거했을 때 서버가 받는 요청의 시간 분포가 어떻게 변하는지 히스토그램으로 확인하라.
