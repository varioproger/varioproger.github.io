# 7장. 스트림

스트림(stream)은 Node.js를 다른 서버 플랫폼과 구별짓는 가장 특징적인 추상화다. 이벤트 기반 논블로킹 I/O가 Node.js의 엔진이라면, 스트림은 그 엔진 위에서 데이터를 흘려보내는 배관이다. 파일 읽기, HTTP 요청과 응답, 압축, 암호화, 프로세스 간 통신, 소켓 통신은 모두 스트림 인터페이스를 공유하며, 이 공통 인터페이스 덕분에 서로 다른 출처의 데이터 처리를 레고 블록처럼 조립할 수 있다.

이 장에서는 왜 스트림이 버퍼링보다 우월한지를 실측으로 확인하고, 네 가지 스트림 타입을 하나씩 구현해 본 뒤, 백프레셔(backpressure)와 오류 전파라는 두 개의 큰 함정을 정면으로 다룬다. 마지막으로 스트림을 조립해 제어 흐름과 분산 처리 패턴을 만드는 방법, 그리고 웹 표준 스트림(Web Streams)과의 상호 운용까지 살펴본다.

## 7.1 버퍼링 vs 스트리밍: 공간 효율과 시간 효율

### 왜 필요한가

데이터를 처리하는 방식은 크게 둘이다. 하나는 **버퍼링(buffering)** 으로, 입력 전체를 메모리에 모은 뒤 한 번에 처리한다. 다른 하나는 **스트리밍(streaming)** 으로, 데이터가 도착하는 즉시 조각(chunk) 단위로 처리하고 흘려보낸다. 대부분의 언어에서 버퍼링은 편하고 스트리밍은 번거롭다. Node.js에서는 그 관계가 역전된다.

### 어떻게 동작하는가

파일 하나를 gzip으로 압축하는 작업을 두 방식으로 구현해 비교해 보자. 먼저 버퍼링 방식이다.

```js
// gzip-buffered.mjs — 입력 전체를 메모리에 올린 뒤 압축한다
import { readFile, writeFile } from 'node:fs/promises'
import { gzip } from 'node:zlib'
import { promisify } from 'node:util'

const gzipAsync = promisify(gzip)

const filename = process.argv[2]
const raw = await readFile(filename)          // 파일 전체가 메모리에 올라온다
const compressed = await gzipAsync(raw)        // 압축 결과도 통째로 메모리에 올라온다
await writeFile(`${filename}.gz`, compressed)
console.log('완료')
```

이 코드는 짧고 읽기 쉽지만 두 가지 치명적인 한계를 가진다. 첫째는 **용량 한계**다. `Buffer`는 무한히 커질 수 없다.

```js
import { constants } from 'node:buffer'

console.log(constants.MAX_LENGTH)         // 64비트 환경에서 약 4GiB(2**32)
console.log(constants.MAX_STRING_LENGTH)  // 약 512MiB (2**29 - 24)
```

즉 4GiB를 넘는 파일은 `readFile`이 애초에 `ERR_FS_FILE_TOO_LARGE`로 실패한다. 인코딩을 지정해 문자열로 읽으면 한계는 훨씬 더 낮아져서 512MiB 부근에서 `ERR_STRING_TOO_LONG`이 터진다. 로그 파일을 `readFile(path, 'utf8')`로 읽는 코드가 프로덕션에서 갑자기 죽는 전형적인 이유가 이것이다.

용량 한계보다 실무에서 더 자주 문제가 되는 것은 **동시성**이다. 위 코드가 200MiB 파일을 처리한다면 요청 하나당 최소 200MiB의 힙이 필요하다. 동시 요청 10개면 2GiB다. V8의 기본 힙 상한을 가볍게 넘긴다. 반면 스트리밍 방식은 요청 수와 무관하게 청크 크기만큼만 메모리를 쓴다.

```js
// gzip-stream.mjs — 조각 단위로 읽고, 압축하고, 쓴다
import { createReadStream, createWriteStream } from 'node:fs'
import { createGzip } from 'node:zlib'
import { pipeline } from 'node:stream/promises'

const filename = process.argv[2]

await pipeline(
  createReadStream(filename),
  createGzip(),
  createWriteStream(`${filename}.gz`)
)
console.log('완료')
```

코드 길이는 오히려 짧아졌는데, 파일 크기가 4GiB든 400GiB든 동작하고, 메모리 사용량은 대략 수백 KiB에서 평평하게 유지된다. 두 방식의 최대 RSS(resident set size)를 직접 재 보면 차이가 분명하다. 1GiB 파일 기준으로 버퍼링 방식은 최대 RSS가 2GiB를 넘어서고(원본 + 압축 결과 + zlib 내부 버퍼), 스트리밍 방식은 60~80MiB 수준에서 멈춘다.

```js
// 어느 스크립트에든 붙여 쓸 수 있는 최대 RSS 측정 코드
let peak = 0
const timer = setInterval(() => {
  peak = Math.max(peak, process.memoryUsage.rss())
}, 50)
timer.unref()
process.on('exit', () => {
  console.log(`최대 RSS: ${(peak / 1024 / 1024).toFixed(1)} MiB`)
})
```

### 시간 효율: 첫 바이트까지의 지연

공간 효율만큼 중요한 것이 **시간 효율**이다. 버퍼링 방식은 입력을 전부 받아야 처리를 시작하므로, 각 단계의 지연이 직렬로 누적된다. 파일을 읽는 데 3초, 압축에 2초, 전송에 3초가 걸린다면 총 8초가 걸리고 그동안 수신 측은 아무것도 받지 못한다. 스트리밍에서는 첫 청크가 읽히는 즉시 압축기로 넘어가고, 압축된 첫 청크가 즉시 소켓으로 나간다. 세 단계가 파이프라인처럼 겹쳐 돌기 때문에 전체 소요 시간은 가장 느린 단계에 수렴하고, 무엇보다 **첫 바이트까지의 지연(time to first byte)** 이 수 밀리초로 떨어진다.

이 차이는 사용자가 체감하는 성능에 직결된다. HTTP 응답을 만들 때 `res.end(JSON.stringify(bigArray))` 대신 스트림으로 흘려보내면, 브라우저는 서버가 아직 데이터를 만들고 있는 동안에도 파싱과 렌더링을 시작한다.

### 조합 가능성

스트림의 세 번째 장점은 **조합 가능성(composability)** 이다. 모든 스트림이 같은 인터페이스를 공유하므로, 새 처리 단계를 파이프라인 중간에 끼워 넣는 것으로 기능을 확장할 수 있다. 클라이언트가 파일을 압축하고 암호화해 업로드하면 서버가 복호화하고 압축을 풀어 저장하는 예제를 보자.

```js
// client.mjs — 압축 → 암호화 → 업로드
import { createReadStream } from 'node:fs'
import { createGzip, constants } from 'node:zlib'
import { createCipheriv, randomBytes, scryptSync } from 'node:crypto'
import { pipeline } from 'node:stream/promises'
import { request } from 'node:http'

const filename = process.argv[2]
const secret = process.env.SECRET
const key = scryptSync(secret, 'nodejs-complete-guide', 32) // 실무에서는 솔트를 무작위로
const iv = randomBytes(16)

const req = request({
  hostname: 'localhost',
  port: 3000,
  method: 'PUT',
  path: '/upload',
  headers: {
    'x-filename': encodeURIComponent(filename),
    'x-iv': iv.toString('hex')
  }
})

await pipeline(
  createReadStream(filename),
  createGzip({ level: constants.Z_BEST_SPEED }),
  createCipheriv('aes-256-ctr', key, iv),
  req
)
console.log('업로드 완료')
```

```js
// server.mjs — 복호화 → 압축 해제 → 저장
import { createServer } from 'node:http'
import { createWriteStream } from 'node:fs'
import { createGunzip } from 'node:zlib'
import { createDecipheriv, scryptSync } from 'node:crypto'
import { pipeline } from 'node:stream/promises'
import { basename, join } from 'node:path'

const key = scryptSync(process.env.SECRET, 'nodejs-complete-guide', 32)

createServer(async (req, res) => {
  const filename = basename(decodeURIComponent(req.headers['x-filename']))
  const iv = Buffer.from(req.headers['x-iv'], 'hex')
  try {
    await pipeline(
      req,
      createDecipheriv('aes-256-ctr', key, iv),
      createGunzip(),
      createWriteStream(join('uploads', filename))
    )
    res.writeHead(201).end('ok')
  } catch (err) {
    console.error(err)
    res.writeHead(500).end('error')
  }
}).listen(3000)
```

주목할 점은 이 파이프라인이 **디스크에 중간 결과를 남기지 않고**, 파일 크기와 무관하게 일정 메모리로 동작하며, 클라이언트가 첫 청크를 보내는 순간 서버의 복호화가 이미 시작된다는 것이다. 단계를 하나 추가하고 싶다면(예: 진행률 측정, 체크섬 계산) 파이프라인 배열에 스트림 하나를 끼워 넣으면 된다.

### 실무 함정

- `readFile`/`writeFile`은 파일 크기를 확실히 통제할 수 있는 경우(설정 파일, 소량 JSON)에만 쓴다. 사용자 입력이 크기를 결정한다면 무조건 스트림이다.
- 스트리밍은 청크가 논리적 경계와 일치하지 않는다. `data` 이벤트로 받은 청크가 JSON 한 줄, UTF-8 한 글자와 일치한다는 보장이 없다. 멀티바이트 문자를 다룰 때는 `StringDecoder`나 `readline`, 또는 라인 단위 Transform을 써야 한다.
- 압축 레벨을 높이면 CPU 사용량이 급증해 이벤트 루프를 막을 수 있다. zlib은 스레드 풀에서 동작하지만 풀 크기(`UV_THREADPOOL_SIZE`)가 제한되어 있어 다른 I/O를 굶길 수 있다(11장 참조).

## 7.2 스트림의 해부: 4가지 타입과 객체 모드

### 왜 필요한가

`node:stream` 모듈은 네 개의 추상 클래스를 노출한다. 이들의 역할과 상속 관계를 정확히 알아야 어떤 클래스를 확장할지 판단할 수 있다.

### 어떻게 동작하는가

| 타입 | 역할 | 대표 예 |
|---|---|---|
| `Readable` | 데이터 소스. 읽을 수 있다 | `fs.createReadStream`, HTTP 요청(서버), `process.stdin` |
| `Writable` | 데이터 목적지. 쓸 수 있다 | `fs.createWriteStream`, HTTP 응답(서버), `process.stdout` |
| `Duplex` | 읽기와 쓰기가 모두 가능하되 서로 독립 | `net.Socket`, `WebSocket` 래퍼 |
| `Transform` | Duplex의 특수형. 쓴 데이터를 변환해 읽게 한다 | `zlib.createGzip`, `crypto.createCipheriv` |

모든 스트림은 `EventEmitter`를 상속하므로 `error`, `close`, `end`, `finish` 같은 이벤트를 발생시킨다(4장 참조). Duplex는 읽기 쪽과 쓰기 쪽이 **논리적으로 무관하다**. TCP 소켓에 쓴 바이트가 그 소켓에서 다시 읽히지는 않는다. 반면 Transform은 쓰기 쪽에 들어온 데이터가 변환되어 읽기 쪽으로 나온다는 인과 관계를 보장한다. 이 차이가 두 클래스를 나누는 유일한 기준이다.

### 이진 모드와 객체 모드

스트림은 기본적으로 `Buffer`(또는 인코딩이 지정되면 문자열)를 다루는 **이진 모드(binary mode)** 로 동작한다. 생성자에 `objectMode: true`를 주면 임의의 JavaScript 값을 청크로 흘려보내는 **객체 모드(object mode)** 가 된다. 객체 모드는 스트림을 I/O 도구에서 범용 데이터 파이프라인 도구로 확장시킨다. 데이터베이스 레코드, 파싱된 로그 항목, 도메인 이벤트를 흘려보낼 수 있다.

두 모드는 **내부 버퍼 크기의 단위**도 다르게 해석한다.

```js
import { Readable, Writable } from 'node:stream'

const binary = new Readable({ read () {} })
console.log(binary.readableHighWaterMark) // 16384 (바이트)

const objects = new Readable({ objectMode: true, read () {} })
console.log(objects.readableHighWaterMark) // 16 (개수)
```

`highWaterMark`는 내부 버퍼가 이만큼 차면 "더 이상 밀어 넣지 말라"는 신호를 보내는 임계값이다. 이진 모드에서는 바이트 수(기본 16KiB, `fs` 읽기 스트림은 64KiB), 객체 모드에서는 청크 개수(기본 16)를 뜻한다. 이 값은 하드 리밋이 아니라 **힌트**다. 넘겨도 데이터가 버려지지 않고, 다만 `write()`가 `false`를 반환할 뿐이다(7.4절 참조).

### 실무 함정

- 객체 모드 스트림에 `null`을 쓰면 안 된다. `null`은 스트림 종료 신호(EOF)로 예약되어 있다. "값 없음"을 표현해야 한다면 `undefined`나 센티널 객체를 쓴다.
- 객체 모드의 `highWaterMark: 16`은 객체 하나가 100MiB짜리 버퍼를 품고 있어도 16개까지 버퍼링한다는 뜻이다. 큰 객체를 흘릴 때는 `highWaterMark`를 1~2로 낮춰야 한다.
- `readableObjectMode`와 `writableObjectMode`를 따로 지정할 수 있다. 문자열을 받아 객체를 뱉는 파서 Transform이 대표적이다.

## 7.3 Readable 스트림: 읽기, 구현, 비동기 이터레이션

### 왜 필요한가

Readable은 데이터가 "언제 도착할지 모르는" 소스를 다루는 표준 인터페이스다. 소비 방법이 세 가지(비흐름 모드, 흐름 모드, 비동기 이터레이션)이고 각각 동작이 미묘하게 달라 혼동이 잦다.

### 비흐름 모드와 흐름 모드

Readable은 두 가지 모드를 가진다. 기본은 **비흐름 모드(paused mode)** 로, 소비자가 `read()`를 호출해 능동적으로 당겨 온다. 데이터가 준비되면 `readable` 이벤트가 발생한다.

```js
// paused 모드: 소비자가 주도권을 가진다
process.stdin.on('readable', () => {
  let chunk
  // read()는 버퍼가 빌 때까지 반복 호출한다
  while ((chunk = process.stdin.read()) !== null) {
    console.log(`청크 ${chunk.length}바이트 수신`)
  }
})
process.stdin.on('end', () => console.log('입력 종료'))
```

`read(size)`에 크기를 지정하면 정확히 그만큼만 꺼내고, 버퍼에 그만큼이 없으면 `null`을 반환한다. 고정 길이 프로토콜 파서를 만들 때 유용하다.

`data` 이벤트 리스너를 붙이거나 `pipe()`를 호출하거나 `resume()`을 부르면 **흐름 모드(flowing mode)** 로 전환된다. 이때는 스트림이 주도권을 갖고 데이터를 최대한 빨리 밀어낸다.

```js
process.stdin.on('data', chunk => console.log(`${chunk.length}바이트`))
```

흐름 모드의 위험은 소비자가 느려도 스트림이 계속 밀어낸다는 점이다. `data` 핸들러 안에서 비동기 작업을 하면 그 작업이 무한정 쌓인다. `pause()`와 `resume()`으로 직접 제어할 수 있지만, 실무에서는 `pipe()`나 비동기 이터레이션에 맡기는 편이 안전하다.

### Readable 구현하기

커스텀 소스를 만들려면 `Readable`을 확장하고 `_read(size)`를 구현한다. `_read` 안에서 `push()`로 데이터를 밀어 넣고, 끝났으면 `push(null)`을 호출한다.

```js
import { Readable } from 'node:stream'
import { randomBytes } from 'node:crypto'

class RandomStream extends Readable {
  #remaining

  constructor (totalBytes, options) {
    super(options)
    this.#remaining = totalBytes
  }

  _read (size) {
    const chunkSize = Math.min(size, this.#remaining, 16 * 1024)
    if (chunkSize === 0) {
      this.push(null)  // EOF 신호
      return
    }
    const chunk = randomBytes(chunkSize)
    this.#remaining -= chunkSize
    // push()의 반환값: false면 내부 버퍼가 highWaterMark를 넘었다는 뜻
    const canPushMore = this.push(chunk)
    if (!canPushMore) {
      // 더 밀어 넣지 않고 반환한다. 소비자가 읽어 가면 _read가 다시 호출된다
      return
    }
  }
}

for await (const chunk of new RandomStream(1024 * 1024)) {
  console.log(chunk.length)
}
```

`push()`의 반환값이 핵심이다. `true`면 계속 밀어도 되고, `false`면 내부 버퍼가 임계값을 넘었으니 멈춰야 한다. 이 값을 무시하고 루프에서 계속 `push`하면 내부 버퍼가 무한정 커진다. 이것이 읽기 쪽 백프레셔다.

간단한 경우에는 클래스를 만들 필요 없이 생성자에 `read` 옵션을 넘기거나, `Readable.from()`으로 이터러블을 감싼다.

```js
import { Readable } from 'node:stream'

// 배열, 제너레이터, 비동기 제너레이터 모두 받는다
const fromArray = Readable.from(['a', 'b', 'c'])

async function * fetchPages (baseUrl) {
  let next = baseUrl
  while (next) {
    const res = await fetch(next)
    const body = await res.json()
    for (const item of body.items) {
      yield item          // 객체 모드 스트림의 청크가 된다
    }
    next = body.nextUrl
  }
}

// 페이지네이션 API를 스트림으로 바꾼다. objectMode는 기본 true
const pages = Readable.from(fetchPages('https://api.example.com/items'))
```

`Readable.from()`은 비동기 제너레이터를 스트림으로 바꾸는 가장 간결한 방법이며, 제너레이터가 자연스럽게 백프레셔를 따른다. 소비자가 느리면 `yield`에서 대기하기 때문이다.

### 비동기 이터레이션

Node.js 10 이후 모든 Readable은 비동기 이터러블이다. `for await...of`는 흐름 모드의 편리함과 비흐름 모드의 안전성을 동시에 준다. 루프 본문이 `await`로 멈추면 스트림도 자연스럽게 멈춘다.

```js
import { createReadStream } from 'node:fs'
import { createInterface } from 'node:readline'

const rl = createInterface({
  input: createReadStream('access.log'),
  crlfDelay: Infinity
})

let errors = 0
for await (const line of rl) {
  if (line.includes(' 500 ')) {
    await reportError(line)   // 여기서 대기하는 동안 파일 읽기도 멈춘다
    errors++
  }
}
console.log(`5xx ${errors}건`)
```

Node 18 이후에는 `map`, `filter`, `take`, `reduce`, `toArray` 같은 이터레이터 헬퍼도 Readable에 직접 붙어 있다.

```js
const total = await Readable.from(records)
  .filter(r => r.status === 'active')
  .map(async r => enrich(r), { concurrency: 8 })  // 동시 8개까지 병렬
  .reduce((sum, r) => sum + r.amount, 0)
```

### 실무 함정

- `for await...of` 루프를 `break`나 예외로 빠져나오면 스트림이 자동으로 `destroy()`된다. 파일 디스크립터는 정리되지만, 같은 스트림을 나중에 다시 읽을 수 없다는 뜻이기도 하다.
- 루프 도중 스트림에서 `error`가 발생하면 `for await`가 예외를 던진다. 반드시 `try/catch`로 감싼다.
- `data` 리스너와 `for await`를 동시에 쓰면 청크를 나눠 갖게 되어 데이터가 유실된 것처럼 보인다. 소비자는 항상 하나여야 한다.
- `_read`는 재진입 호출되지 않는다. `push`를 하지 않고 반환하면 스트림이 그대로 멈춘다. 비동기 소스에서 데이터를 기다린다면 도착 후 반드시 `push`를 호출해야 다음 `_read`가 예약된다.

## 7.4 Writable 스트림: 쓰기, 백프레셔, 구현

### 왜 필요한가

Writable은 데이터의 목적지다. 그리고 이 절에서 다루는 **백프레셔(backpressure)** 는 이 장 전체에서 가장 중요한 개념이다. 백프레셔를 무시한 코드는 벤치마크에서는 멀쩡하다가 실제 부하에서 메모리를 폭발시킨다. 스트림 관련 장애의 대부분이 여기서 나온다.

### 어떻게 동작하는가

```js
writable.write(chunk[, encoding][, callback])
writable.end([chunk][, encoding][, callback])
```

`write()`는 **불리언을 반환한다.** 반환값이 `true`면 내부 버퍼에 여유가 있다는 뜻이고, `false`면 버퍼가 `highWaterMark`를 넘었다는 뜻이다. 중요한 것은 `false`를 반환해도 **데이터가 버려지지 않는다**는 점이다. Node.js는 얌전히 메모리에 쌓아 둔다. 그래서 `false`를 무시해도 프로그램은 "동작"한다. 다만 메모리가 계속 늘어날 뿐이다.

`false`를 받으면 소비자는 쓰기를 멈추고 `drain` 이벤트를 기다려야 한다. `drain`은 내부 버퍼가 `highWaterMark` 아래로 다시 내려갔을 때 발생한다.

### 백프레셔를 무시하면 어떻게 되는가

빠른 생산자(메모리 생성)와 느린 소비자(디스크 쓰기)를 붙여 놓고 메모리를 실측해 보자.

```js
// backpressure-bad.mjs — write()의 반환값을 무시한다
import { createWriteStream } from 'node:fs'

const out = createWriteStream('/tmp/big.bin')
const chunk = Buffer.alloc(64 * 1024, 0x61)   // 64KiB

let peak = 0
const t = setInterval(() => {
  peak = Math.max(peak, process.memoryUsage().rss)
}, 20)

for (let i = 0; i < 100_000; i++) {   // 총 6.4GiB
  out.write(chunk)                    // 반환값을 버린다
}
out.end(() => {
  clearInterval(t)
  console.log(`최대 RSS ${(peak / 1024 ** 2).toFixed(0)} MiB`)
})
```

이 루프는 동기적으로 끝까지 돌고, 그동안 이벤트 루프가 한 번도 돌지 않으므로 디스크 쓰기가 단 한 바이트도 진행되지 않는다. 6.4GiB 전부가 `out`의 내부 링크드 리스트에 쌓인다. 실행하면 대개 최대 RSS가 수 GiB까지 치솟다가 `ERR_WORKER_OUT_OF_MEMORY` 또는 OOM 킬로 끝난다. `writableLength`를 찍어 보면 상황이 그대로 보인다.

```js
setInterval(() => {
  console.log(`대기 중 ${(out.writableLength / 1024 ** 2).toFixed(1)} MiB`)
}, 100).unref()
```

이제 백프레셔를 존중하는 버전이다.

```js
// backpressure-good.mjs — false를 받으면 drain을 기다린다
import { createWriteStream } from 'node:fs'
import { once } from 'node:events'

const out = createWriteStream('/tmp/big.bin')
const chunk = Buffer.alloc(64 * 1024, 0x61)

let peak = 0
const t = setInterval(() => {
  peak = Math.max(peak, process.memoryUsage().rss)
}, 20)

for (let i = 0; i < 100_000; i++) {
  if (!out.write(chunk)) {
    await once(out, 'drain')   // 버퍼가 빌 때까지 대기
  }
}
out.end()
clearInterval(t)
console.log(`최대 RSS ${(peak / 1024 ** 2).toFixed(0)} MiB`)
```

같은 6.4GiB를 쓰지만 최대 RSS는 60~90MiB 수준에서 평평하다. 처리 시간도 오히려 빨라진다. GC 압박이 사라지고 디스크 쓰기와 데이터 생성이 겹쳐 돌기 때문이다.

`highWaterMark`는 이 임계값을 결정한다. 기본 16KiB는 "디스크에 16KiB를 던져 두면 그동안 다음 청크를 만들 시간이 충분하다"는 경험칙에서 나온 값이다. 값을 키우면 시스템 콜 횟수가 줄어 처리량이 올라가지만 대기 메모리가 늘고, 줄이면 반대가 된다. 대량 파일 복사처럼 처리량이 중요한 작업에서는 1MiB 정도로 올리는 것이 도움이 된다.

### Writable 구현하기

`_write(chunk, encoding, callback)`을 구현한다. 처리가 끝나면 반드시 `callback()`을 호출해야 다음 청크가 전달된다. 오류가 있으면 `callback(err)`을 넘긴다.

```js
import { Writable } from 'node:stream'
import { setTimeout as delay } from 'node:timers/promises'

// 레코드를 모아 배치로 전송하는 Writable
class BatchWriter extends Writable {
  #buffer = []

  constructor ({ size = 100, flushFn, ...options } = {}) {
    super({ objectMode: true, highWaterMark: 2, ...options })
    this.batchSize = size
    this.flushFn = flushFn
  }

  async _write (record, encoding, callback) {
    this.#buffer.push(record)
    if (this.#buffer.length < this.batchSize) {
      return callback()      // 아직 배치가 안 찼다. 즉시 다음 청크를 받는다
    }
    try {
      await this.#flush()
      callback()
    } catch (err) {
      callback(err)          // 스트림에 error 이벤트를 발생시킨다
    }
  }

  // 여러 청크를 한 번에 받는다. 구현하면 Node가 자동으로 묶어 호출한다
  _writev (chunks, callback) {
    for (const { chunk } of chunks) this.#buffer.push(chunk)
    this.#flush().then(() => callback(), callback)
  }

  // end() 호출 후, finish 이벤트 직전에 한 번 호출된다
  async _final (callback) {
    try {
      await this.#flush()
      callback()
    } catch (err) {
      callback(err)
    }
  }

  async #flush () {
    if (this.#buffer.length === 0) return
    const batch = this.#buffer
    this.#buffer = []
    await this.flushFn(batch)
  }
}
```

`_final`은 스트림이 닫히기 직전에 남은 데이터를 비울 마지막 기회다. 이걸 빼먹으면 마지막 배치가 조용히 사라진다. 실무에서 흔한 데이터 유실 원인이다. 자원을 정리해야 한다면 `_destroy(err, callback)`도 구현한다. `_destroy`는 정상 종료와 오류 종료 모두에서 호출되므로 커넥션 반납 같은 정리 코드가 들어갈 자리다.

### 실무 함정

- `write()`의 콜백 인자와 `drain` 이벤트는 다르다. 콜백은 "그 청크가 처리됐다", `drain`은 "버퍼에 여유가 생겼다"를 뜻한다. 백프레셔 제어에는 `drain`을 쓴다.
- `end()` 호출 후 `write()`를 하면 `ERR_STREAM_WRITE_AFTER_END`가 발생한다. 비동기 코드가 뒤늦게 쓰려 할 때 자주 터진다.
- `finish` 이벤트는 "모든 데이터가 하위 시스템에 넘겨졌다"는 뜻이지 "디스크에 기록됐다"는 뜻이 아니다. 파일이 확실히 닫혔는지 확인하려면 `close` 이벤트를 본다.
- `drain`을 `once`가 아니라 `on`으로 등록하고 루프를 돌리면 리스너가 누적되어 `MaxListenersExceededWarning`이 뜬다.

## 7.5 Duplex와 Transform 스트림

### 왜 필요한가

읽기와 쓰기를 동시에 하는 객체(소켓, 파이프)를 표현하려면 Duplex가 필요하고, 파이프라인 중간에서 데이터를 가공하려면 Transform이 필요하다. 실무에서 직접 구현할 일이 가장 많은 것은 Transform이다.

### Duplex

`Duplex`를 확장하고 `_read`와 `_write`를 모두 구현한다. 두 쪽은 완전히 독립적인 버퍼와 `highWaterMark`를 갖는다.

```js
import { Duplex } from 'node:stream'

// 요청을 보내고 응답을 받는 양방향 채널을 스트림으로 감싼다
class RpcChannel extends Duplex {
  #conn

  constructor (conn, options) {
    super({ objectMode: true, ...options })
    this.#conn = conn
    this.#conn.on('message', msg => {
      // push()가 false를 반환하면 하위 소스를 멈춘다
      if (!this.push(msg)) this.#conn.pause()
    })
    this.#conn.on('close', () => this.push(null))
    this.#conn.on('error', err => this.destroy(err))
  }

  _read () {
    this.#conn.resume()   // 소비자가 읽어 갔으니 다시 흘려보낸다
  }

  _write (msg, encoding, callback) {
    this.#conn.send(msg, callback)
  }

  _destroy (err, callback) {
    this.#conn.close()
    callback(err)
  }
}
```

`readableObjectMode`와 `writableObjectMode`, `readableHighWaterMark`와 `writableHighWaterMark`를 따로 지정할 수 있다는 점을 기억해 두자.

### Transform

Transform은 `_transform(chunk, encoding, callback)`과 선택적으로 `_flush(callback)`을 구현한다. `_transform` 안에서 `this.push()`로 결과를 내보내고, 처리가 끝나면 `callback()`을 호출한다. 입력 하나에 출력이 0개일 수도, 여러 개일 수도 있다.

```js
import { Transform } from 'node:stream'

// 스트림 경계를 넘나드는 패턴도 안전하게 치환하는 Transform
class ReplaceStream extends Transform {
  #tail = ''

  constructor (searchStr, replaceStr, options) {
    super({ ...options })
    this.searchStr = searchStr
    this.replaceStr = replaceStr
  }

  _transform (chunk, encoding, callback) {
    const text = this.#tail + chunk.toString()
    const pieces = text.split(this.searchStr)
    // 마지막 조각은 다음 청크와 이어질 수 있으므로 보류한다
    const lastPiece = pieces.pop()
    const keep = this.searchStr.length - 1
    this.#tail = lastPiece.slice(-keep)
    const out = pieces.join(this.replaceStr) + lastPiece.slice(0, -keep || undefined)
    this.push(out)
    callback()
  }

  // 입력이 끝난 뒤 남은 꼬리를 흘려보낸다
  _flush (callback) {
    this.push(this.#tail)
    callback()
  }
}
```

이 예제의 핵심은 `#tail`이다. 청크 경계가 검색어 중간을 자를 수 있으므로 검색어 길이에서 1을 뺀 만큼을 항상 보류했다가 다음 청크에 이어 붙인다. 상태를 가진 Transform을 만들 때 반드시 고려해야 하는 문제다.

간단한 변환은 클래스 없이 생성자 옵션이나 비동기 제너레이터로 충분하다. `pipeline()`은 비동기 제너레이터 함수를 중간 단계로 직접 받는다.

```js
import { pipeline } from 'node:stream/promises'
import { createReadStream, createWriteStream } from 'node:fs'

await pipeline(
  createReadStream('in.txt'),
  async function * (source) {
    source.setEncoding('utf8')
    for await (const chunk of source) {
      yield chunk.toUpperCase()      // 백프레셔는 자동으로 처리된다
    }
  },
  createWriteStream('out.txt')
)
```

### 실무 함정

- `_transform`에서 `callback()`을 호출하지 않으면 파이프라인이 조용히 멈춘다. 오류도, 로그도 남지 않는다. 스트림이 "그냥 멈췄다"면 가장 먼저 의심할 곳이다.
- `callback(null, value)`는 `push(value); callback()`의 축약이다. 출력이 정확히 하나일 때만 쓴다.
- `_flush`에서 남은 상태를 내보내는 것을 잊으면 마지막 데이터가 유실된다. 파서, 집계기, 배치 처리기에서 특히 자주 발생한다.
- Transform을 여러 파이프라인에서 재사용하면 안 된다. 내부 상태와 버퍼가 오염된다. 항상 새 인스턴스를 만든다(그래서 `zlib`도 `createGzip()` 팩토리를 제공한다).

## 7.6 PassThrough와 지연(lazy) 스트림

### 왜 필요한가

`PassThrough`는 아무 변환도 하지 않고 입력을 그대로 출력하는 Transform이다. 쓸모없어 보이지만 두 가지 강력한 용도가 있다. 파이프라인을 관찰하는 지점을 만드는 것과, 아직 존재하지 않는 스트림의 자리를 미리 잡아 두는 것이다.

### 관찰자로서의 PassThrough

파이프라인 중간에 끼워 넣어 진행률, 처리량, 체크섬을 계산할 수 있다.

```js
import { PassThrough, pipeline } from 'node:stream'
import { pipeline as pipelineAsync } from 'node:stream/promises'
import { createReadStream, createWriteStream, statSync } from 'node:fs'
import { createGzip } from 'node:zlib'

function createProgressMonitor (total, onProgress) {
  let transferred = 0
  const monitor = new PassThrough()
  monitor.on('data', chunk => {
    transferred += chunk.length
    onProgress(transferred / total)
  })
  return monitor
}

const src = 'archive.tar'
const total = statSync(src).size

await pipelineAsync(
  createReadStream(src),
  createProgressMonitor(total, p => {
    process.stdout.write(`\r진행률 ${(p * 100).toFixed(1)}%`)
  }),
  createGzip(),
  createWriteStream(`${src}.gz`)
)
```

주의할 점은 `monitor.on('data', ...)` 리스너가 스트림을 흐름 모드로 전환한다는 것이다. 하지만 이미 `pipeline`에 의해 다음 단계로 파이프되어 있으므로 문제가 없다. 파이프되지 않은 PassThrough에 `data` 리스너만 붙이면 데이터가 그냥 버려진다.

### 지연 스트림

어떤 API는 스트림을 즉시 요구하는데, 실제 소스는 나중에야 준비될 수 있다. 파일을 수백 개 열어야 하는데 파일 디스크립터 한계에 걸리는 상황이 대표적이다. `fs.createReadStream`은 호출 즉시 파일을 여는 반면, PassThrough는 아무 자원도 잡지 않는다.

```js
import { PassThrough } from 'node:stream'
import { createReadStream } from 'node:fs'

// 실제로 읽히기 시작할 때까지 파일을 열지 않는다
function lazyReadStream (path) {
  const placeholder = new PassThrough()
  let started = false
  placeholder.on('newListener', function onListener (event) {
    if (event !== 'data' && event !== 'readable') return
    if (started) return
    started = true
    // 실제 소스를 이제서야 만들어 연결한다
    createReadStream(path)
      .on('error', err => placeholder.destroy(err))
      .pipe(placeholder)
  })
  return placeholder
}

const streams = filePaths.map(lazyReadStream)  // 아직 fd는 0개
```

Node 20부터는 이런 상황에 더 깔끔한 답이 있다. `Readable.from()`에 비동기 제너레이터를 넘기면 소비가 시작될 때 비로소 제너레이터 본문이 실행된다.

```js
function lazyReadStream (path) {
  return Readable.from(async function * () {
    yield * createReadStream(path)   // 이 시점에 파일이 열린다
  }())
}
```

### 실무 함정

- PassThrough도 `highWaterMark`를 가진 실제 버퍼다. 파이프라인에 여러 개를 끼우면 그만큼 대기 메모리가 늘어난다.
- 지연 스트림 패턴에서 오류 전파를 잊기 쉽다. 원본의 `error`를 플레이스홀더로 옮겨 주지 않으면 오류가 사라진다.
- 진행률 측정은 `data` 리스너 대신 Transform의 `_transform`에서 하는 편이 안전하다. 모드 전환 부작용이 없기 때문이다.

## 7.7 `pipe`와 `pipeline()`: 오류 처리의 정석

### 왜 필요한가

`readable.pipe(writable)`는 Node.js 스트림의 상징 같은 API지만, **오류를 전파하지 않는다.** 이 한 가지 결함 때문에 `pipe()`로 만든 파이프라인은 오류가 났을 때 파일 디스크립터와 소켓을 누수시킨다. 프로덕션 코드에서 `pipe()`를 직접 쓰는 것은 사실상 버그다.

### pipe()의 결함

```js
// 위험한 코드 — 절대 프로덕션에 넣지 말 것
import { createReadStream, createWriteStream } from 'node:fs'
import { createGunzip } from 'node:zlib'

createReadStream('data.gz')
  .pipe(createGunzip())
  .pipe(createWriteStream('data.txt'))
  .on('error', err => console.error(err))  // gunzip 오류는 여기 안 온다
```

문제는 두 가지다. 첫째, `pipe()`는 소스의 오류를 목적지로 전달하지 않는다. 위 코드의 `error` 핸들러는 마지막 `createWriteStream`의 오류만 잡는다. `data.gz`가 손상되어 `createGunzip()`이 `Z_DATA_ERROR`를 던지면 아무도 잡지 않아 `uncaughtException`으로 프로세스가 죽는다.

둘째, 한 스트림에서 오류가 나도 **다른 스트림들은 파괴되지 않는다.** 각 스트림에 `error` 핸들러를 빠짐없이 붙여 프로세스 종료는 막았다 해도, 읽기 스트림의 fd와 쓰기 스트림의 fd는 열린 채로 남는다. 요청마다 이런 파이프라인을 만드는 HTTP 서버라면 손상된 파일 요청이 들어올 때마다 fd가 하나씩 새고, 결국 `EMFILE: too many open files`로 서버 전체가 멈춘다.

```bash
# 누수 확인
$ ls -l /proc/$(pgrep -f server.mjs)/fd | wc -l
```

### 정답: stream.pipeline()

`stream.pipeline()`은 이 두 문제를 모두 해결한다. 어느 단계에서든 오류가 나면 **모든 스트림을 destroy하고** 콜백으로 오류를 전달한다.

```js
import { pipeline } from 'node:stream'

pipeline(
  createReadStream('data.gz'),
  createGunzip(),
  createWriteStream('data.txt'),
  err => {
    if (err) return console.error('실패:', err)
    console.log('성공')
  }
)
```

프로미스 버전은 `node:stream/promises`에 있다. 현대 코드에서는 이쪽을 기본으로 쓴다.

```js
import { pipeline } from 'node:stream/promises'

try {
  await pipeline(
    createReadStream('data.gz'),
    createGunzip(),
    createWriteStream('data.txt')
  )
} catch (err) {
  // 이 시점에 모든 스트림은 이미 정리되어 있다
  console.error('실패:', err)
}
```

HTTP 핸들러에 적용하면 이렇게 된다.

```js
createServer(async (req, res) => {
  try {
    await pipeline(createReadStream(resolvePath(req.url)), createGzip(), res)
  } catch (err) {
    // res가 이미 파괴되었을 수 있으므로 헤더 전송 여부를 확인한다
    if (!res.headersSent) res.writeHead(500)
    res.end()
  }
})
```

### AbortSignal로 취소하기

`pipeline()`은 마지막 인자로 옵션 객체를 받으며, `signal`에 `AbortSignal`을 넘기면 외부에서 파이프라인을 중단할 수 있다. 클라이언트가 연결을 끊었을 때 서버 측 작업을 즉시 취소하는 데 필수적이다.

```js
import { pipeline } from 'node:stream/promises'

const ac = new AbortController()
// 클라이언트가 끊으면 파이프라인도 취소한다
req.on('close', () => ac.abort())
// 30초 제한도 함께 건다
const signal = AbortSignal.any([ac.signal, AbortSignal.timeout(30_000)])

try {
  await pipeline(source, transform, destination, { signal })
} catch (err) {
  if (err.name === 'AbortError') {
    console.log('취소됨')
  } else {
    throw err
  }
}
```

`stream.finished()`(및 `node:stream/promises`의 프로미스 버전)는 개별 스트림이 더 이상 읽거나 쓸 수 없게 된 시점을 기다린다. 파이프라인 전체가 아니라 한 스트림의 종료만 감지하고 싶을 때 쓴다.

```js
import { finished } from 'node:stream/promises'

await finished(res)   // 응답이 완전히 끝날 때까지 대기
```

### 실무 함정

- `pipeline()`의 마지막 인자가 함수면 콜백, 객체면 옵션으로 해석된다. 프로미스 버전에 콜백을 넘기면 스트림으로 착각해 `ERR_INVALID_ARG_TYPE`이 난다.
- `pipeline()`은 `process.stdout`과 `process.stderr`를 자동으로 파괴하지 않는다. 하지만 그 외의 목적지는 모두 파괴한다. HTTP 응답을 여러 파이프라인에서 나눠 쓰려 하면 첫 파이프라인이 끝나며 응답을 닫아 버린다.
- `pipeline()`으로 감싼 스트림에 별도로 `error` 핸들러를 붙이면 오류가 두 번 처리될 수 있다. 파이프라인 안의 스트림에는 핸들러를 붙이지 않는 것이 원칙이다.
- `signal`로 취소하면 `AbortError`가 던져진다. 이를 실패로 로깅하면 정상적인 클라이언트 연결 해제가 오류 알림으로 쏟아진다.

## 7.8 스트림 기반 제어 흐름: 순차·비순차·순서 보장 병렬

### 왜 필요한가

5장과 6장에서 다룬 순차·병렬 제어 흐름 패턴은 스트림에서도 그대로 필요하다. 다만 스트림에서는 백프레셔가 자연스러운 동시성 제한 장치로 작동하기 때문에, 별도의 세마포어 없이도 동시 실행 수를 통제할 수 있다는 이점이 있다. 예제로 URL 목록을 읽어 각 사이트의 상태를 확인하는 모니터링 애플리케이션을 만든다.

입력은 한 줄에 URL 하나가 적힌 텍스트 파일이고, 출력은 살아 있는 URL만 담긴 파일이다.

### 순차 실행

`Transform`의 `_transform`은 `callback()`이 호출되기 전에는 다음 청크를 받지 않는다. 즉 **기본 동작이 순차 실행이다.**

```js
// sequential.mjs
import { createReadStream, createWriteStream } from 'node:fs'
import { pipeline } from 'node:stream/promises'
import { Transform } from 'node:stream'
import split from 'split2'   // 라인 단위 분할 Transform

class SequentialCheck extends Transform {
  constructor () {
    super({ objectMode: true })
  }

  async _transform (url, encoding, callback) {
    if (!url) return callback()
    try {
      const res = await fetch(url, { method: 'HEAD', signal: AbortSignal.timeout(5000) })
      if (res.ok) this.push(`${url}\n`)
    } catch {
      // 실패한 URL은 그냥 버린다
    }
    callback()   // 이 호출 전까지 다음 URL은 들어오지 않는다
  }
}

await pipeline(
  createReadStream('urls.txt'),
  split(),
  new SequentialCheck(),
  createWriteStream('alive.txt')
)
```

정확하지만 느리다. URL 1,000개에 각각 200ms가 걸리면 200초다. 네트워크 I/O는 대기 시간이 대부분이므로 병렬화의 이득이 크다.

### 비순차 병렬 실행

`callback()`을 즉시 호출하고 실제 작업은 백그라운드에서 진행시키면 병렬이 된다. 대신 모든 작업이 끝나기 전에 스트림이 종료되지 않도록 `_flush`에서 기다려야 한다.

```js
// unordered-parallel.mjs
import { Transform } from 'node:stream'

class ParallelCheck extends Transform {
  #running = 0
  #queueCb = null
  #terminateCb = null

  constructor (concurrency = 8) {
    super({ objectMode: true })
    this.concurrency = concurrency
  }

  _transform (url, encoding, callback) {
    if (!url) return callback()
    this.#running++
    this.#check(url).finally(() => {
      this.#running--
      // 대기 중이던 _transform을 깨운다
      const cb = this.#queueCb
      this.#queueCb = null
      cb?.()
      // 모든 작업이 끝났고 종료 대기 중이면 종료시킨다
      if (this.#running === 0) this.#terminateCb?.()
    })
    // 동시 실행 한도에 도달했으면 콜백을 보류해 백프레셔를 만든다
    if (this.#running < this.concurrency) callback()
    else this.#queueCb = callback
  }

  _flush (callback) {
    if (this.#running === 0) return callback()
    this.#terminateCb = callback   // 남은 작업이 모두 끝나면 호출된다
  }

  async #check (url) {
    try {
      const res = await fetch(url, { method: 'HEAD', signal: AbortSignal.timeout(5000) })
      if (res.ok) this.push(`${url}\n`)
    } catch { /* 무시 */ }
  }
}
```

동시 실행 수를 8로 제한하면 1,000개 URL이 25초 안에 처리된다. 여기서 `#queueCb`로 콜백을 보류하는 것이 백프레셔를 만드는 장치다. 이 장치가 없으면 파일의 URL 100만 개가 한꺼번에 `fetch`로 날아가 소켓이 고갈된다.

### 순서 보장 병렬 실행

비순차 병렬은 출력 순서가 완료 순서로 뒤섞인다. 로그 처리나 CSV 변환처럼 입력 순서가 의미를 갖는 경우에는 곤란하다. 해법은 **작업을 즉시 시작하되 결과는 순서대로 내보내는 것**이다. 진행 중인 작업의 프로미스를 큐에 순서대로 담고, 큐의 앞에서부터 완료를 기다리며 꺼낸다.

```js
// ordered-parallel.mjs
import { Transform } from 'node:stream'

class OrderedParallel extends Transform {
  #queue = []

  constructor (task, concurrency = 8, options = {}) {
    super({ objectMode: true, ...options })
    this.task = task
    this.concurrency = concurrency
  }

  async _transform (item, encoding, callback) {
    // 즉시 작업을 시작하고 프로미스를 순서대로 큐에 넣는다
    this.#queue.push(this.task(item))
    // 한도를 넘으면 가장 오래된 것부터 비워 낸다
    while (this.#queue.length >= this.concurrency) {
      await this.#drainOne()
    }
    callback()
  }

  async _flush (callback) {
    try {
      while (this.#queue.length > 0) await this.#drainOne()
      callback()
    } catch (err) {
      callback(err)
    }
  }

  async #drainOne () {
    const result = await this.#queue.shift()   // 입력 순서대로 대기
    if (result !== undefined) this.push(result)
  }
}

// 사용 예
const checker = new OrderedParallel(async url => {
  if (!url) return undefined
  try {
    const res = await fetch(url, { method: 'HEAD', signal: AbortSignal.timeout(5000) })
    return res.ok ? `${url} OK\n` : `${url} ${res.status}\n`
  } catch {
    return `${url} DOWN\n`
  }
}, 8)
```

이 구현은 "가장 느린 항목이 뒤의 완료된 항목들을 막는" 헤드 오브 라인 블로킹(head-of-line blocking)을 감수한다. 순서를 보장하려면 피할 수 없는 대가다.

Node 18 이상에서는 같은 일을 내장 헬퍼로 훨씬 짧게 쓸 수 있다. `readable.map()`은 `concurrency` 옵션을 받으면서도 **출력 순서를 보장한다.**

```js
import { pipeline } from 'node:stream/promises'

await pipeline(
  createReadStream('urls.txt'),
  split(),
  Readable.prototype.map.call(source, checkUrl, { concurrency: 8 }),
  createWriteStream('status.txt')
)
```

직접 구현하기 전에 내장 헬퍼로 충분한지 먼저 확인하는 습관을 들이자.

### 실무 함정

- 병렬 Transform에서 `_flush`를 잘못 구현하면 마지막 몇 건이 사라진다. 진행 중 작업 수가 0인지 반드시 확인한다.
- 병렬 실행 중 한 작업이 던진 오류를 `destroy(err)`로 전파하지 않으면 스트림이 멈춘 채 남는다.
- `concurrency`는 대상 시스템의 한계를 기준으로 정한다. 외부 API 레이트 리밋, 데이터베이스 커넥션 풀 크기가 상한이다.

## 7.9 파이핑 패턴: 결합, 분기, 병합, 다중화/역다중화

### 결합(combining)

여러 스트림을 하나의 스트림처럼 다루고 싶을 때가 있다. "gzip 압축 후 암호화"를 하나의 재사용 가능한 단위로 만드는 식이다. Node 16 이후의 `stream.compose()`가 이를 표준으로 제공한다.

```js
import { compose } from 'node:stream'
import { createGzip, createGunzip } from 'node:zlib'
import { createCipheriv, createDecipheriv } from 'node:crypto'

// 하나의 Duplex처럼 동작한다: 쓰면 압축·암호화되어 읽힌다
export const compressAndEncrypt = (key, iv) =>
  compose(createGzip(), createCipheriv('aes-256-ctr', key, iv))

export const decryptAndDecompress = (key, iv) =>
  compose(createDecipheriv('aes-256-ctr', key, iv), createGunzip())

await pipeline(
  createReadStream('report.csv'),
  compressAndEncrypt(key, iv),
  createWriteStream('report.enc')
)
```

결합의 이점은 캡슐화만이 아니다. 내부 단계 중 어디서 오류가 나든 결합된 스트림의 `error` 하나로 올라오므로 오류 처리 지점이 단일화된다.

### 분기(forking)

하나의 소스를 여러 목적지로 보내는 패턴이다. 파일 하나에서 여러 해시를 동시에 계산하는 예를 보자.

각 분기를 독립된 완전한 파이프라인으로 구성하는 것이 안전하다.

```js
import { createReadStream } from 'node:fs'
import { createHash } from 'node:crypto'
import { pipeline } from 'node:stream/promises'
import { PassThrough } from 'node:stream'

async function multiChecksum (path, algorithms) {
  const source = createReadStream(path)
  const jobs = algorithms.map(algo => {
    const branch = new PassThrough()
    const hash = createHash(algo)
    const done = pipeline(branch, hash).then(() => [algo, hash.digest('hex')])
    source.pipe(branch)
    return done
  })
  source.on('error', err => { /* 각 분기를 destroy */ })
  return Object.fromEntries(await Promise.all(jobs))
}

console.log(await multiChecksum('image.iso', ['sha256', 'sha1', 'md5']))
```

분기의 핵심 주의점은 **가장 느린 분기가 전체 속도를 결정한다**는 것이다. `pipe()`는 모든 목적지의 백프레셔를 존중하기 때문이다. 한 분기가 막히면 소스 전체가 멈춘다. 느린 분기를 분리하고 싶다면 그 분기 앞에 큰 버퍼를 두거나, 유실을 허용하는 별도 채널로 빼야 한다.

### 병합(merging)

여러 소스를 하나의 목적지로 모은다. 로그 파일 여러 개를 하나로 합치는 예다.

```js
import { createReadStream, createWriteStream } from 'node:fs'
import { pipeline } from 'node:stream/promises'
import { Readable } from 'node:stream'

// 순서를 보장하며 순차로 합친다
async function * concatFiles (paths) {
  for (const path of paths) {
    yield * createReadStream(path)
  }
}

await pipeline(
  Readable.from(concatFiles(['a.log', 'b.log', 'c.log'])),
  createWriteStream('all.log')
)
```

순서가 상관없고 도착 즉시 합치고 싶다면 각 소스를 `end: false` 옵션으로 목적지에 파이프하고, 모두 끝났을 때 직접 `end()`를 호출한다.

```js
function mergeStreams (sources, destination) {
  let pending = sources.length
  for (const src of sources) {
    src.pipe(destination, { end: false })
    src.once('end', () => { if (--pending === 0) destination.end() })
    src.once('error', err => destination.destroy(err))
  }
  return destination
}
```

`end: false`를 빼먹으면 첫 소스가 끝나는 순간 목적지가 닫혀 나머지 데이터가 `ERR_STREAM_WRITE_AFTER_END`로 실패한다. 병합에서 가장 흔한 버그다.

### 다중화와 역다중화

여러 논리 채널을 하나의 물리 채널로 합치는 것이 **다중화(multiplexing)**, 반대편에서 되돌리는 것이 **역다중화(demultiplexing)** 다. 각 청크 앞에 채널 ID와 길이를 붙이는 간단한 패킷 프레이밍으로 구현한다. 원격 로거를 예로 들어 자식 프로세스의 `stdout`과 `stderr`를 소켓 하나로 보내 보자.

```js
// mux-client.mjs — 자식 프로세스의 두 출력을 소켓 하나로 다중화한다
import { connect } from 'node:net'
import { spawn } from 'node:child_process'

function multiplexChannels (sources, destination) {
  let open = sources.length
  sources.forEach((source, channelId) => {
    source.on('readable', function () {
      let chunk
      while ((chunk = this.read()) !== null) {
        // 헤더 5바이트: [채널ID 1바이트][길이 4바이트 BE]
        const header = Buffer.alloc(5)
        header.writeUInt8(channelId, 0)
        header.writeUInt32BE(chunk.length, 1)
        destination.write(Buffer.concat([header, chunk]))
      }
    })
    source.on('end', () => { if (--open === 0) destination.end() })
  })
}

const socket = connect(3100, () => {
  const child = spawn(process.argv[2], process.argv.slice(3))
  multiplexChannels([child.stdout, child.stderr], socket)
})
```

```js
// demux-server.mjs — 받은 패킷을 채널별 목적지로 되돌린다
import { createServer } from 'node:net'
import { createWriteStream } from 'node:fs'

function demultiplexChannel (source, destinations) {
  let currentChannel = null
  let currentLength = null
  source.on('readable', () => {
    let chunk
    if (currentChannel === null) {
      chunk = source.read(5)          // 헤더를 통째로 읽는다
      if (chunk === null) return
      currentChannel = chunk.readUInt8(0)
      currentLength = chunk.readUInt32BE(1)
    }
    chunk = source.read(currentLength) // 본문을 정확한 길이만큼 읽는다
    if (chunk === null) return
    destinations[currentChannel].write(chunk)
    currentChannel = null
    currentLength = null
  })
  source.on('end', () => destinations.forEach(d => d.end()))
}

createServer(socket => {
  demultiplexChannel(socket, [
    createWriteStream('child-stdout.log'),
    createWriteStream('child-stderr.log')
  ])
}).listen(3100)
```

여기서 비흐름 모드의 `read(size)`가 빛을 발한다. 정확히 헤더 5바이트, 정확히 본문 N바이트를 요청할 수 있어 프레이밍 코드가 단순해진다. 흐름 모드였다면 청크 경계를 직접 관리하는 상태 기계를 써야 한다.

객체 모드 스트림을 다중화한다면 프레이밍 대신 `{ channel, payload }` 형태로 감싸는 것으로 충분하다. 이 패턴은 WebSocket 위의 다중 구독, 워커 스레드와의 통신(11장 참조)에 그대로 응용된다.

## 7.10 Web Streams와의 상호 운용

### 왜 필요한가

브라우저, Deno, Cloudflare Workers, 그리고 Node.js의 `fetch`는 모두 WHATWG **Web Streams**(`ReadableStream`, `WritableStream`, `TransformStream`)를 쓴다. Node.js는 v16.5에서 Web Streams를 도입하고 v21에서 안정화했다. 이제 한 프로세스 안에 두 종류의 스트림이 공존하므로, 둘을 오가는 법을 알아야 한다.

### 두 API의 차이

| 항목 | Node 스트림 | Web Streams |
|---|---|---|
| 소비 | `for await`, `pipe`, 이벤트 | `getReader()`, `pipeTo`, `for await` |
| 백프레셔 | `write()` 반환값, `drain` | `writer.ready`, `desiredSize` |
| 오류 처리 | `error` 이벤트, `pipeline()` | 프로미스 거부 |
| 객체 모드 | `objectMode` 지원 | 임의 값 지원(별도 플래그 없음) |
| 조립 | `pipeline()` | `pipeThrough()`, `pipeTo()` |
| 취소 | `destroy()`, `AbortSignal` | `cancel()`, `AbortSignal` |

Web Streams는 프로미스 기반이라 오류 처리가 일관되고, `pipeThrough()`는 오류를 자동으로 전파한다는 점에서 `pipe()`보다 `pipeline()`에 가깝다. 반면 Node 스트림은 생태계 지원과 성능(특히 대용량 바이너리)에서 앞선다. **프로세스 내부 처리는 Node 스트림, 플랫폼 경계는 Web Streams**가 현실적인 기준이다.

### 변환

```js
import { Readable, Writable, Duplex } from 'node:stream'

const webReadable = Readable.toWeb(nodeReadable)
const nodeReadable2 = Readable.fromWeb(webReadable)

const webWritable = Writable.toWeb(nodeWritable)
const nodeWritable2 = Writable.fromWeb(webWritable)

// Transform은 Duplex로 오간다
const webTransform = Duplex.toWeb(nodeTransform)   // { readable, writable }
const nodeDuplex = Duplex.fromWeb(webTransformStream)
```

### fetch 응답 본문 다루기

`fetch` 응답의 `body`는 Web `ReadableStream`이다. 이를 Node 파이프라인에 넣으려면 `Readable.fromWeb()`을 쓴다.

```js
import { Readable } from 'node:stream'
import { pipeline } from 'node:stream/promises'
import { createWriteStream } from 'node:fs'
import { createGunzip } from 'node:zlib'

const res = await fetch('https://example.com/dataset.jsonl.gz')
if (!res.ok) throw new Error(`HTTP ${res.status}`)

await pipeline(
  Readable.fromWeb(res.body),   // Web → Node
  createGunzip(),
  createWriteStream('dataset.jsonl')
)
```

`pipeline()`은 Node 17 이후 Web Streams를 인자로 직접 받기도 하므로, 간단한 경우 변환 없이 넘겨도 된다.

```js
await pipeline(res.body, createGunzip(), createWriteStream('dataset.jsonl'))
```

반대 방향으로, Node 스트림을 `fetch`의 요청 본문이나 `Response`로 내보낼 때는 `toWeb()`을 쓴다.

```js
const body = Readable.toWeb(createReadStream('upload.bin'))
await fetch('https://example.com/upload', {
  method: 'POST',
  body,
  duplex: 'half'   // 스트리밍 본문에는 필수
})
```

`duplex: 'half'`를 빼먹으면 `RequestInit: duplex option is required` 오류가 난다. 스트리밍 업로드에서 반드시 걸리는 함정이다.

Web Streams만으로 변환 단계를 만들 수도 있다.

```js
const upper = new TransformStream({
  transform (chunk, controller) {
    controller.enqueue(chunk.toUpperCase())
  }
})

await res.body
  .pipeThrough(new TextDecoderStream())
  .pipeThrough(upper)
  .pipeTo(Writable.toWeb(process.stdout))
```

`TextDecoderStream`, `TextEncoderStream`, `CompressionStream`, `DecompressionStream`은 Node.js에도 전역으로 제공되므로 브라우저와 동일한 코드를 그대로 쓸 수 있다.

### 실무 함정

- 변환 후에는 원본 스트림을 직접 건드리면 안 된다. `toWeb()`은 원본을 잠그며(lock), 이후 원본에서 읽으면 예외가 난다.
- `res.body`는 한 번만 소비할 수 있다. 본문을 두 번 읽어야 한다면 `res.body.tee()`로 갈라 두거나 `res.clone()`을 먼저 호출한다.
- Web Streams의 기본 `highWaterMark`는 1(청크 수)이라 Node 스트림보다 훨씬 작다. 대용량 바이너리를 웹 스트림으로 흘리면 청크 왕복이 잦아 처리량이 떨어질 수 있다.
- `Readable.fromWeb()`으로 만든 스트림을 `destroy()`하면 원본 Web 스트림이 `cancel()`된다. HTTP 커넥션도 함께 끊긴다는 뜻이므로 재사용을 기대하면 안 된다.

## 요약

- 버퍼링은 입력 전체를 메모리에 올리므로 `buffer.constants.MAX_LENGTH`(약 4GiB)와 문자열 한계(약 512MiB)에 묶이고 동시 요청 수만큼 메모리를 곱해 쓴다. 스트리밍은 크기와 무관하게 일정 메모리로 동작하고, 첫 바이트까지의 지연을 밀리초 단위로 줄이며, 단계를 조립할 수 있다.
- 스트림에는 `Readable`, `Writable`, `Duplex`, `Transform` 네 타입이 있고, `objectMode`를 켜면 임의의 JavaScript 값을 흘려보내는 범용 데이터 파이프라인이 된다. `highWaterMark`는 하드 리밋이 아니라 백프레셔 신호의 임계값이다.
- 백프레셔는 스트림에서 가장 중요한 개념이다. `write()`가 `false`를 반환하면 `drain`을 기다려야 하고, `push()`가 `false`를 반환하면 밀어 넣기를 멈춰야 한다. 이를 무시해도 데이터는 유실되지 않고 메모리에 쌓이기 때문에, 장애는 부하가 걸린 프로덕션에서야 드러난다.
- `pipe()`는 오류를 전파하지 않아 파일 디스크립터를 누수시킨다. 프로덕션에서는 항상 `node:stream/promises`의 `pipeline()`을 쓰고, 취소가 필요하면 `signal` 옵션으로 `AbortSignal`을 넘긴다.
- Transform은 기본이 순차 실행이다. 콜백을 즉시 호출하면 비순차 병렬이 되고, 진행 중 프로미스를 순서대로 큐에 담아 앞에서부터 꺼내면 순서 보장 병렬이 된다. Node 18 이상의 `readable.map({ concurrency })`가 이 일을 대신해 준다.
- 결합은 `stream.compose()`, 분기는 여러 `PassThrough`로의 `pipe`, 병합은 `end: false`, 다중화·역다중화는 채널 ID와 길이를 담은 헤더 프레이밍으로 구현한다. 분기에서는 가장 느린 목적지가 전체 속도를 결정한다.
- Web Streams는 플랫폼 경계(fetch, 워커, 엣지 런타임)의 공용어다. `Readable.toWeb()`/`fromWeb()`으로 오갈 수 있고, `pipeline()`은 Web 스트림을 직접 받는다. 스트리밍 요청 본문에는 `duplex: 'half'`가 필수다.

## 연습문제

1. **백프레셔 실측.** 64KiB 청크를 10만 번 쓰는 두 버전(반환값 무시 / `drain` 대기)을 각각 작성하고 최대 RSS와 총 소요 시간을 측정하라. 이어서 `highWaterMark`를 16KiB, 256KiB, 4MiB로 바꿔 가며 처리량과 대기 메모리의 트레이드오프를 표로 정리하라.

2. **라인 단위 CSV 변환 파이프라인.** 대용량 CSV를 읽어 각 행을 객체로 파싱하고, 외부 API로 한 필드를 보강한 뒤(동시 실행 10 제한, **입력 순서 보장**), JSON Lines로 저장하는 파이프라인을 `pipeline()`으로 구성하라. 헤더 행 처리와 마지막 불완전 행 처리를 `_flush`에서 올바르게 다루고, `AbortSignal.timeout()`으로 전체 작업에 5분 제한을 걸어라. 같은 기능을 `Readable.prototype.map({ concurrency: 10 })`으로도 구현해 코드량과 성능을 비교하라.

3. **다중화 원격 로거 확장.** 7.9절의 다중화·역다중화 예제를 확장해, (a) 채널을 8개까지 지원하고, (b) 각 패킷에 8바이트 타임스탬프를 추가하며, (c) 클라이언트가 재연결하면 서버가 같은 파일에 이어 쓰도록 만들어라. 이어서 소켓 중간이 잘린 상황(패킷 헤더만 도착하고 본문이 오지 않는 경우)에서 역다중화기가 멈추지 않고 다음 연결을 정상 처리하는지 확인하고, 필요하면 `AbortSignal`과 `finished()`로 정리 로직을 보강하라.
