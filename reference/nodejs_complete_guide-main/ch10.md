# 10장. 네트워킹

Node.js가 태어난 이유는 네트워킹이다. 파일 시스템 API도, 스트림도, 이벤트 루프도 결국 "수많은 동시 연결을 적은 스레드로 감당한다"는 하나의 목표를 위해 설계됐다. 그래서 Node.js의 네트워크 API는 다른 플랫폼과 달리 계층이 얇다. 소켓은 스트림이고, HTTP 요청과 응답도 스트림이며, 프록시는 파이프 한 줄이다.

이 장에서는 TCP 소켓부터 시작해 HTTP 서버와 클라이언트, 헤더와 본문 처리, TLS, 프록시, UDP, DNS까지 올라간다. 각 계층에서 "프레임워크가 대신 해 주던 일"이 실제로 무엇이었는지 드러내는 데 초점을 맞춘다. Express나 Fastify를 쓰더라도 그 아래에서 무슨 일이 벌어지는지 알아야 타임아웃 설정을 고르고, 소켓 고갈을 진단하고, 프록시 뒤에서 클라이언트 IP를 잃어버리지 않는다.

## 10.1 TCP 서버와 클라이언트: `net` 모듈

### 왜 필요한가

대부분의 애플리케이션은 HTTP만 쓰면 된다. 그럼에도 TCP를 알아야 하는 이유는 HTTP, TLS, WebSocket, Redis 프로토콜, PostgreSQL 와이어 프로토콜이 전부 TCP 위에 얹혀 있고, 프로덕션에서 터지는 문제의 상당수가 HTTP 계층이 아니라 그 아래 소켓 계층에서 발생하기 때문이다. 커넥션이 끊기고, 지연이 튀고, 메시지가 반쪽만 도착하는 현상은 TCP의 성질을 알아야 설명된다.

### 어떻게 동작하는가

`net.Socket`은 `Duplex` 스트림이다(7장 참조). 읽기 쪽은 상대가 보낸 바이트, 쓰기 쪽은 내가 보낼 바이트다. 스트림이라는 사실은 문법적 편의가 아니라 의미론적 선언이다. **TCP는 바이트 스트림이지 메시지 큐가 아니다.** 내가 `write()`를 세 번 호출해도 상대는 한 번에 받을 수 있고, 한 번 호출해도 상대는 세 조각으로 나눠 받을 수 있다.

이 사실을 코드로 증명해 보자.

```js
// tcp-no-boundaries.mjs — TCP에는 메시지 경계가 없다
import net from 'node:net'

const server = net.createServer((socket) => {
  socket.on('data', (chunk) => {
    console.log(`서버 수신 ${chunk.length}바이트:`, JSON.stringify(chunk.toString()))
  })
})

server.listen(9000, () => {
  const client = net.connect(9000, () => {
    // 논리적으로는 메시지 3개를 보냈다
    client.write('안녕')
    client.write('하세')
    client.write('요')
    setTimeout(() => client.end(), 100)
  })
})
```

실행하면 대개 `서버 수신 16바이트: "안녕하세요"` 한 줄만 출력된다. 세 번의 `write()`가 커널 송신 버퍼에서 하나의 세그먼트로 합쳐졌기 때문이다. 반대로 큰 데이터를 한 번에 쓰면 MTU와 수신 버퍼 크기에 따라 여러 조각으로 쪼개져 도착한다. 즉 `data` 이벤트 한 번은 애플리케이션 메시지 한 개와 아무 관계가 없다.

따라서 메시지 경계는 애플리케이션이 직접 만들어야 한다. 가장 견고한 방법이 **길이 접두사 프레이밍(length-prefixed framing)** 이다. 각 메시지 앞에 본문 길이를 고정 크기 정수로 붙인다.

```js
// framing.mjs — 4바이트 길이 접두사 프레이밍
import { Transform } from 'node:stream'

export function encodeFrame(payload) {
  const body = Buffer.isBuffer(payload) ? payload : Buffer.from(payload)
  const header = Buffer.allocUnsafe(4)
  header.writeUInt32BE(body.length, 0)
  return Buffer.concat([header, body])
}

export class FrameDecoder extends Transform {
  #buffer = Buffer.alloc(0)
  #maxFrame

  constructor({ maxFrame = 1024 * 1024 } = {}) {
    super({ readableObjectMode: true })
    this.#maxFrame = maxFrame
  }

  _transform(chunk, _enc, cb) {
    this.#buffer = Buffer.concat([this.#buffer, chunk])
    // 헤더 + 본문이 모두 모였을 때만 프레임을 방출한다
    while (this.#buffer.length >= 4) {
      const length = this.#buffer.readUInt32BE(0)
      if (length > this.#maxFrame) {
        return cb(new Error(`프레임이 너무 큼: ${length}`))  // 메모리 폭탄 방어
      }
      if (this.#buffer.length < 4 + length) break             // 아직 덜 왔다
      this.push(this.#buffer.subarray(4, 4 + length))
      this.#buffer = this.#buffer.subarray(4 + length)
    }
    cb()
  }

  _flush(cb) {
    // 연결이 끊겼는데 조각이 남아 있으면 잘린 프레임이다
    cb(this.#buffer.length > 0 ? new Error('불완전한 프레임으로 연결 종료') : null)
  }
}
```

서버 쪽은 소켓을 디코더에 파이프하기만 하면 된다.

```js
import net from 'node:net'
import { pipeline } from 'node:stream/promises'
import { FrameDecoder, encodeFrame } from './framing.mjs'

const server = net.createServer(async (socket) => {
  socket.setNoDelay(true)          // Nagle 알고리즘 비활성화
  socket.setKeepAlive(true, 30_000) // 30초 후부터 keep-alive 프로브 전송
  socket.setTimeout(120_000)
  socket.on('timeout', () => socket.destroy(new Error('유휴 타임아웃')))

  try {
    const decoder = new FrameDecoder({ maxFrame: 256 * 1024 })
    await pipeline(socket, decoder, async function* (frames) {
      for await (const frame of frames) {
        yield encodeFrame(frame.toString().toUpperCase()) // 에코 서버
      }
    }, socket)
  } catch (err) {
    console.error('세션 오류:', err.message)
  }
})

server.listen(9000)
```

프레이밍 대안으로 구분자(delimiter) 방식이 있다. 줄바꿈으로 나누는 JSON Lines가 대표적이고 사람이 읽기 좋다는 장점이 있지만, 본문에 구분자가 들어가면 이스케이프해야 하고 스캔 비용이 있다. 바이너리 프로토콜에는 길이 접두사가 정답이다.

`setNoDelay(true)`는 **Nagle 알고리즘**을 끈다. Nagle은 작은 패킷을 모아서 보내 대역폭을 아끼는 최적화인데, 지연 ACK(delayed ACK)와 겹치면 최대 40ms의 지연이 생긴다. 요청-응답이 잦은 RPC 프로토콜에서는 이 40ms가 치명적이다. `http` 모듈의 소켓은 Node.js가 기본으로 `setNoDelay(true)`를 걸어 주지만, `net`으로 직접 만든 소켓은 그렇지 않다.

`setKeepAlive(true, delay)`는 TCP 계층의 keep-alive 프로브를 켠다. HTTP keep-alive(커넥션 재사용)와는 완전히 다른 개념이다. TCP keep-alive는 유휴 상태가 오래 지속될 때 상대가 살아 있는지 확인하는 프로브를 보낸다. NAT 게이트웨이나 클라우드 로드밸런서는 유휴 커넥션을 조용히 끊는데(AWS NLB는 350초), 프로브가 없으면 애플리케이션은 커넥션이 죽은 줄 모르고 쓰다가 `ECONNRESET`을 맞는다.

### 실무 함정

- `socket.write()`의 반환값을 무시하면 백프레셔가 깨진다. 상대가 느린데 계속 쓰면 데이터는 유실되지 않고 Node.js 힙에 쌓인다. `socket.writableLength`를 모니터링하거나 `pipeline()`을 쓴다.
- `'close'`와 `'end'`는 다르다. `'end'`는 상대가 FIN을 보냈다는 뜻이고, 이때도 내 쪽 쓰기는 열려 있다(half-open). `allowHalfOpen: true`가 아니면 Node.js가 자동으로 `end()`를 호출한다.
- `'error'` 핸들러를 등록하지 않은 소켓에서 오류가 나면 프로세스가 죽는다. 모든 소켓에 예외 없이 등록한다.
- `server.close()`는 새 연결만 막고 기존 연결은 유지한다. 우아한 종료에는 `server.closeIdleConnections()`(Node 18.2+)와 타임아웃 후 `closeAllConnections()` 조합이 필요하다(9장 참조).

## 10.2 HTTP 서버 만들기: 요청과 응답 객체

### 왜 필요한가

`http.createServer`는 Express, Fastify, Koa, Next.js가 모두 최종적으로 호출하는 지점이다. 프레임워크가 감춘 계층을 한 번은 직접 봐야 요청 본문이 왜 스트림인지, `res.end()`를 두 번 부르면 왜 터지는지, 타임아웃 설정 세 가지가 왜 각각 따로 있는지 이해할 수 있다.

### 어떻게 동작하는가

핸들러가 받는 `req`는 `IncomingMessage`, 즉 `Readable` 스트림이다. `res`는 `ServerResponse`, 즉 `Writable` 스트림이다. HTTP 파서는 헤더를 다 읽는 즉시 핸들러를 호출하며, **본문은 아직 도착하지 않았다.** 이것이 Node.js HTTP 서버의 가장 중요한 성질이다.

```js
// http-basics.mjs
import http from 'node:http'
import { pipeline } from 'node:stream/promises'

const server = http.createServer(async (req, res) => {
  // req는 Readable, res는 Writable — 둘 다 스트림이다
  if (req.method === 'POST' && req.url === '/echo') {
    res.writeHead(200, { 'content-type': 'application/octet-stream' })
    await pipeline(req, res)   // 본문을 그대로 되돌려준다. 메모리 사용량은 청크 크기뿐
    return
  }

  res.writeHead(404, { 'content-type': 'text/plain; charset=utf-8' })
  res.end('없음\n')
})

// 타임아웃 3종 — 기본값에 의존하지 말 것
server.headersTimeout = 10_000     // 첫 바이트부터 헤더 완성까지
server.requestTimeout = 60_000     // 요청 전체(본문 포함) 수신 제한
server.keepAliveTimeout = 65_000   // 응답 후 다음 요청을 기다리는 시간
server.timeout = 0                 // 소켓 유휴 타임아웃(0 = 비활성)

server.listen(3000)
```

세 타임아웃의 역할이 각각 다르다. `headersTimeout`은 Slowloris 공격 방어용으로, 헤더를 1바이트씩 흘려보내며 소켓을 점유하는 공격을 차단한다. `requestTimeout`(Node 18부터 기본 300초)은 본문까지 포함한 전체 수신 시간을 제한한다. `keepAliveTimeout`은 응답을 다 보낸 뒤 같은 커넥션으로 다음 요청이 오기를 기다리는 시간이다.

`keepAliveTimeout`에는 유명한 함정이 있다. **로드밸런서의 유휴 타임아웃보다 반드시 길어야 한다.** 짧으면 서버가 커넥션을 닫는 순간 로드밸런서가 그 커넥션으로 요청을 보내는 경쟁 상태가 생기고, 사용자는 산발적인 502를 본다. AWS ALB의 기본값이 60초이므로 서버는 65초 이상으로 설정한다.

응답 쪽에서 자주 걸리는 문제는 헤더 전송 시점이다. `res.write()`나 `res.end()`가 처음 호출되는 순간 헤더가 전송되고, 그 후에는 상태 코드도 헤더도 바꿀 수 없다.

```js
const server = http.createServer(async (req, res) => {
  try {
    res.writeHead(200, { 'content-type': 'application/json' })
    await pipeline(makeSlowStream(), res)
  } catch (err) {
    // 이미 헤더가 나갔다면 500을 보낼 방법이 없다
    if (res.headersSent) {
      res.destroy()   // 커넥션을 끊어 클라이언트에게 불완전한 응답임을 알린다
      return
    }
    res.writeHead(500).end('내부 오류')
  }
})
```

스트리밍 응답 중간에 오류가 나면 이미 200을 보낸 뒤다. 이때 정직한 대응은 `res.destroy()`로 커넥션을 끊는 것이다. `Content-Length`를 알고 있었다면 클라이언트는 본문이 잘렸음을 감지하고, 청크 인코딩이었다면 종료 청크가 없어 역시 오류로 처리한다. 조용히 `res.end()`를 부르면 클라이언트는 잘린 데이터를 정상 응답으로 오인한다.

### HTTP/1.1과 HTTP/2

HTTP/1.1은 커넥션 하나에 요청 하나를 순차 처리한다. 파이프라이닝은 사실상 죽은 기능이고, 브라우저는 호스트당 6개 커넥션을 열어 병렬성을 확보한다. 응답이 순서대로 나가야 하므로 앞 요청이 느리면 뒤가 막히는 **헤드 오브 라인 블로킹(head-of-line blocking)** 이 발생한다.

HTTP/2는 커넥션 하나 위에 다수의 스트림을 다중화하고, 헤더를 HPACK으로 압축하며, 서버 푸시(사실상 폐기됨)를 지원한다. Node.js는 별도 모듈 `node:http2`로 제공한다.

```js
// http2-server.mjs
import http2 from 'node:http2'
import { readFileSync } from 'node:fs'

const server = http2.createSecureServer({
  key: readFileSync('key.pem'),
  cert: readFileSync('cert.pem'),
  // http1로 접속한 클라이언트도 함께 받는다
  allowHTTP1: true
})

server.on('stream', (stream, headers) => {
  // http2에서는 의사 헤더(:method, :path)를 쓴다
  stream.respond({ ':status': 200, 'content-type': 'text/plain; charset=utf-8' })
  stream.end(`${headers[':method']} ${headers[':path']}\n`)
})

server.listen(8443)
```

`http2.createSecureServer`가 아니라 `createServer`를 쓰면 평문 HTTP/2(h2c)가 되지만 브라우저는 지원하지 않는다. 호환성 API(`http2.createSecureServer`의 `'request'` 이벤트)를 쓰면 Express 미들웨어를 거의 그대로 재사용할 수 있으나, 소켓 직접 조작이나 `Connection` 헤더에 의존하는 코드는 깨진다. HTTP/2에서는 홉 바이 홉 헤더(`Connection`, `Transfer-Encoding`, `Keep-Alive`)가 금지되기 때문이다.

실무 판단은 대체로 이렇다. 서비스가 인터넷에 직접 노출된다면 HTTP/2 종료는 로드밸런서나 리버스 프록시에 맡기고 백엔드는 HTTP/1.1로 두는 편이 운영이 단순하다. 반면 gRPC처럼 HTTP/2를 요구하는 내부 통신, 혹은 다중화가 실제 이득이 되는 대용량 팬아웃에서는 `node:http2`를 직접 쓸 이유가 있다.

### 실무 함정

- `req.on('data')`를 등록하지 않으면 본문이 소비되지 않아 커넥션이 keep-alive 상태에서 막힌다. 본문이 필요 없어도 `req.resume()`으로 버려야 한다.
- `res.end()`를 두 번 호출하면 `ERR_STREAM_WRITE_AFTER_END`가 난다. 미들웨어에서 조건 분기 후 `return`을 빠뜨리는 것이 전형적인 원인이다.
- `req.url`은 경로와 쿼리만 담긴 상대 경로다. 전체 URL이 필요하면 ``new URL(req.url, `http://${req.headers.host}`)``로 조립하되, `Host` 헤더는 클라이언트가 조작할 수 있으므로 신뢰 경계로 쓰면 안 된다.
- 클라이언트가 도중에 끊으면 `req`에서 `'aborted'`가 아니라 `'close'`가 발생한다(`aborted`는 deprecated). 무거운 작업 전에 `res.writableEnded`나 `AbortSignal`로 취소를 확인해 낭비를 줄인다.

## 10.3 HTTP 클라이언트: `fetch`, `undici`, 커넥션 풀링

### 왜 필요한가

마이크로서비스 환경에서 애플리케이션은 서버인 동시에 클라이언트다. 그리고 성능 문제의 대부분은 서버 코드가 아니라 아웃바운드 HTTP 호출에서 발생한다. 커넥션을 재사용하지 않는 클라이언트는 요청마다 TCP 3-way 핸드셰이크와 TLS 핸드셰이크를 반복하고, 사용한 소켓을 `TIME_WAIT` 상태로 쌓아 결국 포트를 고갈시킨다.

### 어떻게 동작하는가

Node 18부터 전역 `fetch`가 표준으로 제공된다. 내부 구현은 `undici`이며, Node 22 기준으로 안정 API다. `node:http`의 `http.request`와 달리 프로미스 기반이고 Web 표준과 동일한 인터페이스를 갖는다.

```js
// fetch-basic.mjs
const res = await fetch('https://api.example.com/users/1', {
  headers: { accept: 'application/json' },
  signal: AbortSignal.timeout(3000)   // 3초 후 자동 중단
})

if (!res.ok) {
  // fetch는 4xx/5xx에서 예외를 던지지 않는다. 반드시 직접 확인한다
  throw new Error(`HTTP ${res.status} ${res.statusText}`)
}
const user = await res.json()
```

`fetch`가 예외를 던지는 경우는 네트워크 실패, DNS 실패, 중단(`AbortError`)뿐이다. 404도 500도 "성공적으로 응답을 받은 것"이므로 `res.ok` 확인을 빠뜨리면 오류 응답 본문을 JSON으로 파싱하려다 엉뚱한 곳에서 터진다.

전역 `fetch`는 내부적으로 전역 `Agent`를 쓰며, 이 에이전트는 이미 커넥션 풀링을 한다. 그러나 기본값이 항상 적절하지는 않다. 세밀한 제어가 필요하면 `undici`를 직접 설치해 `Agent`나 `Pool`을 구성하고 `dispatcher` 옵션으로 넘긴다.

```js
// undici-pool.mjs
import { Agent, setGlobalDispatcher, request } from 'undici'

const agent = new Agent({
  connections: 128,            // 오리진당 최대 커넥션 수
  pipelining: 1,               // HTTP/1.1 파이프라이닝 깊이(대개 1 유지)
  keepAliveTimeout: 10_000,    // 유휴 커넥션 유지 시간
  keepAliveMaxTimeout: 60_000,
  connectTimeout: 2_000,
  headersTimeout: 5_000,
  bodyTimeout: 10_000
})

setGlobalDispatcher(agent)     // 이후 전역 fetch도 이 에이전트를 쓴다

// undici의 저수준 API — fetch보다 오버헤드가 작다
const { statusCode, body } = await request('https://api.example.com/users/1')
const user = await body.json()
```

커넥션 재사용의 효과는 극적이다. 같은 로컬 HTTPS 오리진에 1,000회 순차 요청을 보내는 실험에서, keep-alive를 끄면 요청당 평균 약 4.2ms(TCP 핸드셰이크 0.3ms + TLS 핸드셰이크 3.1ms + 요청 처리 0.8ms)가 들고, 켜면 약 0.9ms로 떨어진다. 4배 이상의 차이이며, 원격 데이터센터처럼 RTT가 20ms인 환경에서는 TLS 핸드셰이크가 2 RTT(TLS 1.3은 1 RTT)를 추가로 요구하므로 격차가 훨씬 커진다.

성능보다 더 무서운 것은 **소켓 고갈**이다. keep-alive 없이 초당 500건을 호출하면 매초 500개의 소켓이 닫히고, 능동 종료(active close) 측인 클라이언트에는 각 소켓이 `TIME_WAIT` 상태로 60초(리눅스 기본 `2*MSL`) 남는다. 정상 상태에서 3만 개의 `TIME_WAIT` 소켓이 쌓이며, 기본 로컬 포트 범위(`net.ipv4.ip_local_port_range`, 약 28,000개)를 넘기는 순간 `EADDRNOTAVAIL`이 발생한다. 진단 명령은 다음과 같다.

```bash
ss -tan state time-wait | wc -l     # TIME_WAIT 소켓 수
ss -tan state established | wc -l   # 재사용 중인 커넥션 수
```

해법은 커널 파라미터 튜닝이 아니라 keep-alive를 켜는 것이다. `node:http`를 직접 쓴다면 `new http.Agent({ keepAlive: true, maxSockets: 128 })`을 명시해야 한다. Node 19부터 `http.globalAgent`의 `keepAlive` 기본값이 `true`가 되었지만, 라이브러리가 자체 에이전트를 만들어 쓰는 경우가 많으므로 방심할 수 없다.

타임아웃과 재시도는 항상 함께 설계한다.

```js
// retry.mjs — 지수 백오프 + 지터, 멱등 요청만 재시도
async function fetchWithRetry(url, options = {}, { retries = 3, baseMs = 100 } = {}) {
  let lastError
  for (let attempt = 0; attempt <= retries; attempt++) {
    try {
      const res = await fetch(url, {
        ...options,
        signal: AbortSignal.any([
          AbortSignal.timeout(2000),          // 시도별 타임아웃
          options.signal ?? new AbortController().signal
        ])
      })
      if (res.status >= 500 || res.status === 429) {
        throw new Error(`재시도 가능 상태: ${res.status}`)
      }
      return res
    } catch (err) {
      lastError = err
      if (attempt === retries) break
      // 지터를 넣지 않으면 재시도가 동시에 몰려 서버를 재차 쓰러뜨린다
      const delay = baseMs * 2 ** attempt * (0.5 + Math.random())
      await new Promise((r) => setTimeout(r, delay))
    }
  }
  throw lastError
}
```

`AbortSignal.timeout(ms)`는 지정 시간 후 `TimeoutError`로 중단되는 시그널을 만든다. `AbortSignal.any([...])`는 여러 시그널 중 하나라도 발동하면 중단시킨다. 요청별 타임아웃과 전체 작업 타임아웃, 그리고 서버 종료 시그널을 함께 묶을 때 유용하다.

### 실무 함정

- 응답 본문을 소비하지 않으면 커넥션이 풀로 돌아오지 않는다. 상태 코드만 필요해도 `await res.body?.cancel()`이나 `await res.arrayBuffer()`로 반드시 배출한다. 이 누수는 "왜 요청이 128건째부터 멈추는가"라는 형태로 나타난다.
- 시도별 타임아웃 × 재시도 횟수가 상위 서비스의 타임아웃을 넘으면 재시도는 무의미한 부하일 뿐이다. 타임아웃 예산은 호출 체인 전체에서 계산한다.
- 비멱등 요청(POST)의 재시도는 중복 실행을 낳는다. 멱등 키(Idempotency-Key)를 서버가 지원할 때만 재시도한다.
- `maxSockets`를 무한대로 두면 다운스트림 서비스를 압도한다. 커넥션 풀은 사실상 부하 제한 장치이기도 하다(19장 참조).

## 10.4 헤더, 쿠키, 콘텐츠 타입, POST 본문 처리

### 왜 필요한가

HTTP 메시지의 의미는 대부분 헤더와 본문 인코딩에 담긴다. 여기서 생기는 버그는 조용하다. 헤더 대소문자를 잘못 비교하면 인증이 통과되고, 문자셋을 무시하면 한글이 깨지고, 본문 크기를 제한하지 않으면 서버가 메모리 부족으로 죽는다.

### 어떻게 동작하는가

HTTP 헤더 이름은 **대소문자를 구분하지 않는다**(RFC 9110). Node.js는 `req.headers`의 키를 모두 소문자로 정규화한다. 따라서 `req.headers['Content-Type']`은 항상 `undefined`다.

```js
req.headers['content-type']      // 올바름
req.headers['Content-Type']      // 항상 undefined — 전형적인 버그
req.rawHeaders                   // 원본 대소문자와 중복까지 보존한 평평한 배열
```

같은 이름의 헤더가 여러 번 오면 Node.js는 쉼표로 합친다. 단 `set-cookie`만은 예외로 항상 배열로 유지된다. 쿠키는 값에 쉼표가 들어갈 수 있어 합치면 복원이 불가능하기 때문이다. `fetch` 응답에서도 마찬가지로 `res.headers.getSetCookie()`라는 전용 메서드를 쓴다.

```js
// 응답에 쿠키 두 개를 설정한다 — 배열로 넘긴다
res.setHeader('Set-Cookie', [
  'session=abc123; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=3600',
  'theme=dark; Path=/; Max-Age=31536000'
])
```

쿠키 속성은 보안 그 자체다. `HttpOnly`는 JavaScript 접근을 막아 XSS로 인한 세션 탈취를 줄이고, `Secure`는 HTTPS에서만 전송하며, `SameSite=Lax`는 크로스 사이트 요청에서 쿠키가 자동으로 실려 나가는 CSRF를 대부분 차단한다. 서브도메인 간 공유가 필요하지 않다면 `Domain`은 생략하는 편이 안전하다.

`Content-Type`은 미디어 타입과 파라미터로 구성된다. `application/json; charset=utf-8`에서 `charset`은 파라미터다. 실제로 JSON은 명세상 UTF-8이 강제되므로 `charset`이 무의미하지만, `text/*` 계열에서는 필수다. 이를 빠뜨리면 브라우저가 레거시 인코딩으로 추측해 한글이 깨진다.

본문 파싱은 반드시 크기 제한과 함께 구현한다.

```js
// body.mjs — 크기 제한이 있는 본문 수집기
const MAX_BODY = 1024 * 1024   // 1MiB

export async function readBody(req, { limit = MAX_BODY } = {}) {
  // 선언된 길이부터 검사해 큰 요청은 읽기 전에 거절한다
  const declared = Number(req.headers['content-length'])
  if (Number.isFinite(declared) && declared > limit) {
    const err = new Error('본문이 너무 큼')
    err.statusCode = 413
    throw err
  }

  const chunks = []
  let received = 0
  for await (const chunk of req) {
    received += chunk.length
    // Content-Length는 거짓일 수 있으므로 실제 수신량도 검사한다
    if (received > limit) {
      const err = new Error('본문이 너무 큼')
      err.statusCode = 413
      req.destroy()
      throw err
    }
    chunks.push(chunk)
  }
  return Buffer.concat(chunks)
}

export async function readJson(req, options) {
  const type = (req.headers['content-type'] ?? '').split(';')[0].trim()
  if (type !== 'application/json') {
    const err = new Error('지원하지 않는 미디어 타입')
    err.statusCode = 415
    throw err
  }
  const raw = await readBody(req, options)
  try {
    return JSON.parse(raw.toString('utf8'))
  } catch {
    const err = new Error('잘못된 JSON')
    err.statusCode = 400
    throw err
  }
}
```

**본문 크기 제한이 없는 파서는 그 자체로 DoS 취약점이다.** 공격자가 `Transfer-Encoding: chunked`로 무한한 본문을 흘려보내면 서버는 그것을 전부 힙에 모으다 죽는다. Content-Length만 검사하는 것도 부족하다. 청크 인코딩에서는 그 헤더가 아예 없고, 있더라도 거짓일 수 있으므로 실제 누적 바이트를 세야 한다. Express의 `express.json()` 기본 제한이 100KB인 것도 같은 이유다.

`application/x-www-form-urlencoded`는 `URLSearchParams`로 파싱한다. 다만 `a=1&a=2` 같은 중복 키에서 `Object.fromEntries(params)`는 마지막 값만 남기므로, 배열 필드를 다룬다면 `params.getAll('a')`를 써야 한다. 프로토타입 오염을 피하려면 `Object.create(null)`을 베이스로 객체를 만든다.

대용량 업로드(`multipart/form-data`)는 절대 메모리에 모으지 않는다. `busboy`나 `@fastify/multipart` 같은 스트리밍 파서로 파트 단위 처리하고, 파일 파트는 곧바로 디스크나 오브젝트 스토리지로 파이프한다.

```js
import busboy from 'busboy'
import { pipeline } from 'node:stream/promises'
import { createWriteStream } from 'node:fs'

const bb = busboy({ headers: req.headers, limits: { fileSize: 20 * 1024 * 1024, files: 5 } })
bb.on('file', async (name, file, info) => {
  // limits를 넘으면 file 스트림에 'limit' 이벤트가 발생한다
  await pipeline(file, createWriteStream(`/tmp/upload-${Date.now()}`))
})
req.pipe(bb)
```

### 실무 함정

- `req.headers.host`, `X-Forwarded-For`, `Referer`는 전부 클라이언트가 조작 가능하다. 신뢰 프록시를 명시적으로 설정한 경우에만 값을 신뢰한다.
- 헤더 값에 개행을 넣으면 응답 분할(response splitting) 공격이 된다. Node.js가 검증해 `ERR_INVALID_CHAR`를 던지므로 사용자 입력을 헤더에 넣을 때는 예외 처리를 준비한다.
- `Content-Type` 비교 시 파라미터를 잘라내지 않으면 `application/json; charset=utf-8`이 거부된다.
- 413으로 거절하면서 요청 본문을 배출하지 않으면, 클라이언트는 계속 쓰다 `ECONNRESET`을 보고 원인을 오해한다. 응답 후 `req.destroy()`로 명확히 끊는 편이 낫다.

## 10.5 HTTPS와 TLS: 인증서, 자체 서명, 종료 지점

### 왜 필요한가

평문 HTTP는 도청과 변조에 무방비다. 오늘날 공개 서비스에서 TLS는 선택이 아니다. 문제는 TLS를 "어디서" 종료할 것인가, 그리고 내부 통신까지 암호화할 것인가라는 아키텍처 판단이며, 이를 위해서는 핸드셰이크가 무엇을 하는지 알아야 한다.

### 어떻게 동작하는가

TLS 핸드셰이크는 세 가지를 동시에 해결한다. 첫째 **키 합의**로, 타원곡선 디피-헬만(ECDHE)으로 세션 키를 만든다. 둘째 **인증**으로, 서버가 제시한 인증서 체인을 클라이언트가 신뢰 저장소의 루트 CA까지 검증한다. 셋째 **협상**으로, 암호 스위트와 애플리케이션 프로토콜을 정한다. TLS 1.2는 2 RTT를 쓰지만 TLS 1.3은 1 RTT로 줄였고, 세션 재개(session resumption) 시에는 0-RTT도 가능하다.

로컬 개발에는 자체 서명(self-signed) 인증서를 만든다.

```bash
# SAN(Subject Alternative Name)을 포함한 자체 서명 인증서 — 최신 클라이언트는 CN을 보지 않는다
openssl req -x509 -newkey rsa:2048 -nodes -days 365 \
  -keyout key.pem -out cert.pem \
  -subj "/CN=localhost" \
  -addext "subjectAltName=DNS:localhost,DNS:api.local,IP:127.0.0.1"
```

`-addext subjectAltName`을 빠뜨리면 브라우저와 Node.js 클라이언트 모두 `ERR_TLS_CERT_ALTNAME_INVALID`로 거부한다. 요즘 클라이언트는 Common Name을 호스트명 검증에 쓰지 않는다.

서버 구성은 다음과 같다.

```js
// tls-server.mjs
import https from 'node:https'
import { readFileSync } from 'node:fs'

const server = https.createServer({
  key: readFileSync('key.pem'),
  cert: readFileSync('cert.pem'),
  minVersion: 'TLSv1.2',                 // 1.0/1.1은 폐기됐다
  ALPNProtocols: ['h2', 'http/1.1'],     // 프로토콜 협상
  // SNI: 하나의 IP에서 여러 도메인을 서비스할 때 도메인별 인증서를 고른다
  SNICallback: (servername, cb) => {
    const ctx = contexts.get(servername)
    cb(ctx ? null : new Error(`알 수 없는 호스트: ${servername}`), ctx)
  }
})

server.on('secureConnection', (socket) => {
  console.log(socket.getProtocol(), socket.getCipher().name, socket.alpnProtocol)
})
server.listen(8443)
```

**SNI(Server Name Indication)** 는 클라이언트가 핸드셰이크 시작 시 접속하려는 호스트명을 평문으로 알려 주는 확장이다. 서버는 이 이름으로 인증서를 선택한다. 이것이 없으면 IP 하나당 인증서 하나만 서비스할 수 있다. **ALPN(Application-Layer Protocol Negotiation)** 은 핸드셰이크 중에 HTTP/2를 쓸지 HTTP/1.1을 쓸지 정한다. 별도 왕복 없이 협상되므로 HTTP/2는 사실상 ALPN 없이는 성립하지 않는다.

내부 서비스 간 통신에는 **mTLS(상호 TLS)** 를 쓴다. 서버뿐 아니라 클라이언트도 인증서를 제시해 신원을 증명하므로, API 키를 나눠 주는 방식보다 관리가 명확하고 유출 시 폐기가 쉽다.

```js
// mtls-server.mjs
const server = https.createServer({
  key: readFileSync('server-key.pem'),
  cert: readFileSync('server-cert.pem'),
  ca: readFileSync('internal-ca.pem'),  // 클라이언트 인증서를 검증할 CA
  requestCert: true,
  rejectUnauthorized: true              // false면 검증 실패도 통과시킨다 — 사실상 무방비
}, (req, res) => {
  const cert = req.socket.getPeerCertificate()
  // 인증서 주체를 애플리케이션 신원으로 사용한다
  res.end(`안녕하세요, ${cert.subject.CN}\n`)
})
```

클라이언트 쪽은 `undici`의 `Agent`에 `connect` 옵션으로 키와 인증서를 넘긴다.

```js
import { Agent } from 'undici'

const agent = new Agent({
  connect: {
    key: readFileSync('client-key.pem'),
    cert: readFileSync('client-cert.pem'),
    ca: readFileSync('internal-ca.pem')
  }
})
await fetch('https://internal.svc/health', { dispatcher: agent })
```

**TLS 종료를 어디에 둘 것인가**는 성능과 운영의 트레이드오프다. Node.js에서 직접 종료하면 인증서 갱신, OCSP 스테이플링, 암호 스위트 관리, 핸드셰이크 CPU 비용을 애플리케이션이 떠안는다. 핸드셰이크는 비대칭 암호 연산이라 상대적으로 비싸고, 이벤트 루프를 점유한다. 반면 nginx, Envoy, 클라우드 로드밸런서에서 종료하면 인증서 관리가 중앙화되고 애플리케이션은 평문 HTTP만 다루면 된다. 대부분의 조직에서 후자가 정답이다. 다만 종료 지점부터 애플리케이션까지의 구간이 신뢰 가능한 네트워크인지 확인해야 하며, 규제 요건이 종단 간 암호화를 요구한다면 프록시에서 재암호화하거나 서비스 메시로 mTLS를 자동화한다(26장 참조).

### 실무 함정

- `rejectUnauthorized: false`나 `NODE_TLS_REJECT_UNAUTHORIZED=0`은 중간자 공격을 허용한다. 개발 환경에서는 자체 CA를 `NODE_EXTRA_CA_CERTS`로 등록하는 방법을 쓴다.
- 인증서 만료는 가장 흔한 장애 원인이다. 갱신 자동화와 만료 30일 전 알림을 함께 둔다.
- `readFileSync`로 시작 시 한 번만 읽으면 갱신된 인증서가 반영되지 않는다. `server.setSecureContext()`로 무중단 교체가 가능하다.
- 프록시에서 TLS를 종료하면 애플리케이션은 원래 스킴을 알 수 없다. `X-Forwarded-Proto`를 신뢰 프록시 목록과 함께 처리해야 리다이렉트 루프를 피한다.

## 10.6 프록시와 터널링

### 왜 필요한가

프록시는 현대 인프라의 기본 구성 요소다. 로드밸런서, API 게이트웨이, 서비스 메시 사이드카, 사내 아웃바운드 프록시가 모두 프록시다. 직접 하나를 만들어 보면 `X-Forwarded-For`가 왜 필요한지, 왜 홉 바이 홉 헤더를 제거해야 하는지, HTTPS 트래픽을 프록시가 어떻게 통과시키는지가 한 번에 이해된다.

### 어떻게 동작하는가

**정방향 프록시(forward proxy)** 는 클라이언트를 대신해 임의의 목적지로 요청을 보낸다. 클라이언트가 프록시를 명시적으로 설정하고, 요청 라인에 절대 URL이 들어간다. 사내망 아웃바운드 통제, 캐싱, 콘텐츠 필터링이 용도다. **역방향 프록시(reverse proxy)** 는 서버 앞에 서서 고정된 백엔드로 요청을 넘긴다. 클라이언트는 프록시의 존재를 모른다. TLS 종료, 로드 밸런싱, 라우팅, 속도 제한이 용도다.

스트림을 이용하면 최소한의 역방향 프록시를 짧게 만들 수 있다.

```js
// reverse-proxy.mjs
import http from 'node:http'

const TARGET = { host: '127.0.0.1', port: 8080 }
const HOP_BY_HOP = new Set([
  'connection', 'keep-alive', 'proxy-authenticate', 'proxy-authorization',
  'te', 'trailer', 'transfer-encoding', 'upgrade'
])

http.createServer((req, res) => {
  const headers = {}
  for (const [k, v] of Object.entries(req.headers)) {
    if (!HOP_BY_HOP.has(k)) headers[k] = v   // 홉 바이 홉 헤더는 전달하지 않는다
  }
  // 원래 클라이언트 정보를 체인에 덧붙인다
  headers['x-forwarded-for'] = [req.headers['x-forwarded-for'], req.socket.remoteAddress]
    .filter(Boolean).join(', ')
  headers['x-forwarded-proto'] = 'http'
  headers['x-forwarded-host'] = req.headers.host

  const upstream = http.request({ ...TARGET, method: req.method, path: req.url, headers }, (up) => {
    res.writeHead(up.statusCode, up.headers)
    up.pipe(res)          // 응답 본문을 그대로 흘려보낸다 — 버퍼링 없음
  })

  upstream.on('error', (err) => {
    if (!res.headersSent) res.writeHead(502, { 'content-type': 'text/plain' })
    res.end(`업스트림 오류: ${err.code}\n`)
  })

  req.pipe(upstream)      // 요청 본문도 스트리밍으로 전달
}).listen(3000)
```

핵심은 `req.pipe(upstream)`과 `up.pipe(res)` 두 줄이다. 본문을 메모리에 모으지 않으므로 1GB 업로드도 일정 메모리로 중계한다. 홉 바이 홉 헤더를 제거하는 이유는 이 헤더들이 "이 커넥션 구간에만 유효"하다는 의미를 갖기 때문이다. `Connection: close`를 그대로 전달하면 업스트림과의 keep-alive가 매번 끊긴다.

HTTPS 트래픽은 프록시가 내용을 볼 수 없다. 그래서 클라이언트는 `CONNECT` 메서드로 프록시에게 "이 호스트로 TCP 터널을 뚫어 달라"고 요청하고, 그 뒤로는 프록시가 바이트를 양방향으로 중계하기만 한다.

```js
// connect-tunnel.mjs — HTTP CONNECT 터널링
import http from 'node:http'
import net from 'node:net'

const proxy = http.createServer((req, res) => {
  res.writeHead(405).end('이 프록시는 CONNECT만 지원한다\n')
})

proxy.on('connect', (req, clientSocket, head) => {
  const [host, port = '443'] = req.url.split(':')   // CONNECT의 요청 대상은 host:port
  const serverSocket = net.connect(Number(port), host, () => {
    clientSocket.write('HTTP/1.1 200 Connection Established\r\n\r\n')
    if (head?.length) serverSocket.write(head)      // 파서가 미리 읽은 바이트를 흘려보낸다
    // 이후로는 순수 바이트 중계 — TLS 내용은 프록시가 알지 못한다
    serverSocket.pipe(clientSocket)
    clientSocket.pipe(serverSocket)
  })

  const kill = () => { serverSocket.destroy(); clientSocket.destroy() }
  serverSocket.on('error', kill)
  clientSocket.on('error', kill)
})

proxy.listen(8888)
```

`head` 인자를 처리하지 않는 것이 이 코드의 대표적 버그다. HTTP 파서는 성능을 위해 소켓에서 한 번에 큰 덩어리를 읽는데, `CONNECT` 헤더 뒤에 이미 TLS ClientHello의 첫 바이트가 딸려 왔을 수 있다. 이를 버리면 핸드셰이크가 영원히 멈춘다.

`undici`에서 프록시를 쓰려면 `ProxyAgent`를 사용한다. 이 에이전트는 HTTPS 목적지에 대해 자동으로 `CONNECT` 터널을 맺는다.

```js
import { ProxyAgent } from 'undici'
const dispatcher = new ProxyAgent('http://corp-proxy.internal:8888')
await fetch('https://api.example.com/health', { dispatcher })
```

### 실무 함정

- `X-Forwarded-For`는 누적 목록이며 클라이언트가 위조할 수 있다. 신뢰하는 프록시 홉 수를 세어 오른쪽에서부터 계산해야 실제 클라이언트 IP를 얻는다. 왼쪽 첫 값을 그대로 쓰면 IP 기반 속도 제한이 무력화된다.
- WebSocket은 `Upgrade` 요청이므로 별도로 `'upgrade'` 이벤트를 처리하지 않으면 프록시를 통과하지 못한다.
- 업스트림 요청에 타임아웃이 없으면 프록시의 소켓이 무한정 쌓인다. `connectTimeout`, `headersTimeout`, `bodyTimeout`을 모두 건다.
- 프록시가 응답을 버퍼링하면 SSE(Server-Sent Events)나 스트리밍 응답이 끊긴다. nginx라면 `proxy_buffering off`가 필요하다.

## 10.7 UDP와 멀티캐스트: `dgram` 모듈

### 왜 필요한가

TCP는 순서와 도달을 보장하는 대신 핸드셰이크, 재전송, 혼잡 제어의 비용을 치른다. 어떤 데이터는 그 대가가 아깝다. 매초 수만 건의 메트릭, 1초마다 갱신되는 상태 브로드캐스트, 로컬 네트워크의 서비스 디스커버리는 몇 개쯤 사라져도 무방하며, 오히려 지연과 오버헤드가 더 중요하다. 이럴 때 UDP가 답이다.

### 어떻게 동작하는가

UDP는 커넥션이 없다. 핸드셰이크도, 순서 보장도, 재전송도, 흐름 제어도 없다. 보낸 데이터그램이 도착할 수도, 사라질 수도, 순서가 뒤바뀔 수도, 중복될 수도 있다. 그 대신 데이터그램은 **메시지 경계를 보존한다.** TCP와 정반대로 프레이밍이 필요 없다.

```js
// udp-server.mjs
import dgram from 'node:dgram'

const socket = dgram.createSocket({ type: 'udp4', reuseAddr: true })

socket.on('message', (msg, rinfo) => {
  // 데이터그램 한 개 = message 이벤트 한 번. 조립할 필요가 없다
  console.log(`${rinfo.address}:${rinfo.port} → ${msg.toString()}`)
})

socket.on('error', (err) => {
  console.error('소켓 오류:', err)
  socket.close()
})

socket.bind(41234, () => {
  socket.setRecvBufferSize(4 * 1024 * 1024)  // 버스트를 흡수할 커널 수신 버퍼
})
```

클라이언트는 더 단순하다.

```js
import dgram from 'node:dgram'

const client = dgram.createSocket('udp4')
// 콜백은 "커널에 전달됨"만 의미한다. 도착 여부와는 무관하다
client.send(Buffer.from('api.latency:120|ms'), 41234, '127.0.0.1', (err) => {
  client.close()
})
```

데이터그램 크기에는 실질적 상한이 있다. IPv4의 이론적 최대는 65,507바이트지만, MTU(보통 1,500바이트)를 넘으면 IP 단편화가 일어나고 조각 하나만 유실돼도 데이터그램 전체가 버려진다. 실무 권장치는 이더넷에서 약 1,400바이트, 인터넷 경유라면 512바이트 이하다.

**멀티캐스트(multicast)** 는 하나의 데이터그램을 그룹에 가입한 모든 수신자에게 전달한다. 브로드캐스트와 달리 관심 있는 호스트만 받으므로 네트워크 낭비가 적다.

```js
// multicast.mjs — 로컬 네트워크 서비스 디스커버리
import dgram from 'node:dgram'

const GROUP = '239.255.42.99'   // 239.0.0.0/8은 조직 내부용 주소 범위
const PORT = 5353

const socket = dgram.createSocket({ type: 'udp4', reuseAddr: true })

socket.bind(PORT, () => {
  socket.addMembership(GROUP)      // IGMP로 그룹 가입
  socket.setMulticastTTL(1)        // TTL 1 = 로컬 서브넷 밖으로 나가지 않는다
  socket.setMulticastLoopback(true)

  // 5초마다 자신의 존재를 알린다
  setInterval(() => {
    const announce = JSON.stringify({ id: process.pid, service: 'worker', port: 3000 })
    socket.send(announce, PORT, GROUP)
  }, 5000).unref()
})

const peers = new Map()
socket.on('message', (msg, rinfo) => {
  try {
    const info = JSON.parse(msg)
    peers.set(`${rinfo.address}:${info.port}`, { ...info, lastSeen: Date.now() })
  } catch { /* 잘못된 패킷은 조용히 버린다 */ }
})

// 15초간 소식이 없는 피어는 죽은 것으로 간주한다
setInterval(() => {
  const cutoff = Date.now() - 15_000
  for (const [key, p] of peers) if (p.lastSeen < cutoff) peers.delete(key)
}, 5000).unref()
```

이 패턴이 mDNS/Bonjour, SSDP(UPnP), 그리고 여러 클러스터링 라이브러리의 피어 발견 방식이다. 유실을 전제로 설계했기 때문에 패킷 하나가 사라져도 다음 주기에 복구된다. 이것이 UDP를 안전하게 쓰는 유일한 방법이다. **재시도나 상태 복구가 애플리케이션 논리에 이미 내장되어 있어야 한다.**

메트릭 전송의 표준인 **StatsD**도 같은 이유로 UDP를 쓴다. 애플리케이션이 메트릭을 보내다 메트릭 서버가 느려져 블로킹되면 본말이 전도된다. UDP는 `send()`가 커널 버퍼에 넣는 즉시 반환하므로 수집기가 죽어도 애플리케이션은 전혀 영향받지 않는다. 대신 부하가 높을 때 메트릭 일부가 사라지는데, 통계량에서 그 정도 손실은 대개 허용된다.

```js
// statsd-client.mjs — 배칭으로 시스템 콜을 줄인다
class StatsD {
  #buffer = []
  constructor(host = '127.0.0.1', port = 8125) {
    this.socket = dgram.createSocket('udp4')
    this.socket.unref()      // 이 소켓 때문에 프로세스가 살아 있지 않도록
    Object.assign(this, { host, port })
    setInterval(() => this.flush(), 100).unref()
  }
  timing(name, ms) { this.#push(`${name}:${ms}|ms`) }
  increment(name, n = 1) { this.#push(`${name}:${n}|c`) }
  #push(line) {
    this.#buffer.push(line)
    if (this.#buffer.join('\n').length > 1200) this.flush()  // MTU 이내로 유지
  }
  flush() {
    if (this.#buffer.length === 0) return
    const payload = this.#buffer.join('\n')
    this.#buffer = []
    this.socket.send(payload, this.port, this.host, () => {})  // 오류는 무시한다
  }
}
```

### 실무 함정

- `send()` 콜백의 성공은 도착을 뜻하지 않는다. UDP에 ACK는 없다.
- 커널 수신 버퍼가 넘치면 패킷이 조용히 버려진다. 리눅스에서 `netstat -su`의 `receive buffer errors`로 확인하고 `setRecvBufferSize()`나 `net.core.rmem_max`를 올린다.
- 이벤트 루프가 오래 블로킹되면 그 사이 도착한 데이터그램이 버퍼를 넘쳐 유실된다. UDP 수신 프로세스에서 동기 CPU 작업은 금물이다.
- 멀티캐스트는 클라우드 VPC 대부분에서 지원되지 않는다. AWS/GCP에서는 서비스 디스커버리에 DNS 기반이나 전용 레지스트리를 써야 한다.
- 인터페이스가 여러 개인 호스트에서는 `addMembership(group, multicastInterface)`로 인터페이스를 명시하지 않으면 엉뚱한 곳으로 가입된다.

## 10.8 DNS 조회와 이름 해석 전략

### 왜 필요한가

DNS는 모든 아웃바운드 요청의 첫 단계이고, 가장 자주 간과되는 지연 원인이다. Node.js에서 DNS는 특히 위험하다. 기본 조회 함수가 스레드풀을 쓰기 때문에, 잘못 쓰면 파일 I/O와 암호 연산까지 함께 굶긴다.

### 어떻게 동작하는가

Node.js의 DNS API는 성격이 전혀 다른 두 계열로 나뉜다.

`dns.lookup()`은 운영체제의 `getaddrinfo(3)`를 호출한다. `/etc/hosts`, NSS 설정, mDNS 등 OS의 이름 해석 규칙을 전부 따르므로 결과가 시스템의 다른 도구와 일치한다. 그러나 `getaddrinfo`는 **블로킹 시스템 콜**이라 libuv 스레드풀에서 실행된다. 기본 스레드풀 크기는 4다.

`dns.resolve*()`는 c-ares 라이브러리로 DNS 서버에 직접 질의한다. 완전히 비동기이며 스레드풀을 쓰지 않는다. 대신 `/etc/hosts`를 보지 않는다.

```js
import dns from 'node:dns/promises'

// OS 경유 — /etc/hosts 반영, 스레드풀 점유
const { address, family } = await dns.lookup('api.example.com', { family: 0, all: false })

// DNS 직접 질의 — 논블로킹, /etc/hosts 무시
const addrs = await dns.resolve4('api.example.com')
const srv = await dns.resolveSrv('_grpc._tcp.internal')  // 서비스 디스커버리
```

이 차이가 실전에서 문제가 되는 지점은 명확하다. `http.request`와 `fetch`는 내부적으로 `dns.lookup()`을 쓴다. DNS 서버가 느려져 조회에 3초가 걸리면, 동시 조회 4건이 스레드풀 4개를 전부 점유한다. 그 순간 `fs.readFile`, `crypto.pbkdf2`, `zlib` 압축이 모두 대기열에 갇힌다. 겉으로는 "DNS 장애"인데 증상은 "파일 읽기가 멈춤"으로 나타나므로 진단이 어렵다. 완화책은 두 가지다. `UV_THREADPOOL_SIZE`를 올리는 것(근본 해결은 아니다), 그리고 DNS 캐싱을 도입하는 것이다.

**Node.js에는 DNS 캐시가 없다.** OS에 nscd나 systemd-resolved가 없는 컨테이너 환경에서는 매 요청마다 실제 DNS 질의가 나간다. 초당 1,000건을 호출하면 초당 1,000번의 UDP 왕복이 발생하고, 각 요청에 1~5ms가 더해진다. 해법은 애플리케이션 레벨 캐시다.

```js
// dns-cache.mjs — TTL을 존중하는 lookup 캐시
import dns from 'node:dns'
import { Agent } from 'undici'

const cache = new Map()

function cachedLookup(hostname, options, callback) {
  const hit = cache.get(hostname)
  if (hit && hit.expires > Date.now()) {
    return process.nextTick(callback, null, hit.address, hit.family)
  }
  dns.lookup(hostname, options, (err, address, family) => {
    if (err) return callback(err)
    // 실제 TTL을 쓰려면 dns.resolve4의 { ttl: true } 옵션을 활용한다
    cache.set(hostname, { address, family, expires: Date.now() + 30_000 })
    callback(null, address, family)
  })
}

const agent = new Agent({ connect: { lookup: cachedLookup } })
```

캐시 TTL은 짧게 잡는다. 블루/그린 배포나 오토스케일링으로 IP가 바뀌는 환경에서 오래된 항목을 붙들면 죽은 인스턴스로 요청이 계속 나간다. 30초 정도가 무난한 절충이며, `cacheable-lookup` 같은 검증된 라이브러리를 쓰면 레코드의 실제 TTL을 존중해 준다.

IPv6가 배포된 환경에서는 **Happy Eyeballs**가 중요하다. 호스트가 A 레코드와 AAAA 레코드를 모두 가지는데 IPv6 경로가 고장 났다면, 순차 시도 방식은 IPv6 타임아웃(수십 초)을 다 기다린 뒤에야 IPv4로 넘어간다. Happy Eyeballs(RFC 8305)는 두 계열을 짧은 간격으로 병렬 시도해 먼저 연결된 쪽을 채택한다. Node 20부터 `autoSelectFamily`가 기본으로 켜져 있다.

```js
import net from 'node:net'

const socket = net.connect({
  host: 'dual-stack.example.com',
  port: 443,
  autoSelectFamily: true,             // Node 20+ 기본값
  autoSelectFamilyAttemptTimeout: 250 // 다음 주소를 시도하기까지의 간격(ms)
})
```

컨테이너 환경에서는 **ndots 문제**가 지연의 숨은 원인이다. 쿠버네티스는 파드의 `/etc/resolv.conf`에 `options ndots:5`를 넣는다. 점이 5개 미만인 이름은 상대 이름으로 간주되어 `search` 도메인을 차례로 붙여 먼저 질의한다. `api.example.com`(점 2개)을 조회하면 `api.example.com.default.svc.cluster.local`, `...svc.cluster.local`, `...cluster.local`을 먼저 시도하고 전부 NXDOMAIN을 받은 뒤에야 원래 이름을 질의한다. 외부 API 호출마다 4~5회의 헛된 왕복이 붙는 셈이다. 해결책은 두 가지다. 외부 도메인을 `api.example.com.`처럼 마침표로 끝내 절대 이름(FQDN)으로 만들거나, 파드 스펙의 `dnsConfig.options`에서 `ndots`를 1이나 2로 낮춘다.

### 실무 함정

- `dns.setDefaultResultOrder('ipv4first')`로 정렬을 바꾸면 IPv6 우선이 야기하는 문제를 피할 수 있지만, IPv6 전용 환경에서는 오히려 장애가 된다. 환경별로 판단한다.
- `dns.lookup`은 기본적으로 주소 하나만 반환한다. `{ all: true }`로 전체 목록을 받아 클라이언트 사이드 로드 밸런싱에 쓸 수 있다.
- DNS 기반 로드 밸런싱과 커넥션 keep-alive는 상충한다. 커넥션을 오래 유지하면 DNS가 새 IP를 알려 줘도 트래픽이 이동하지 않는다. 커넥션 최대 수명(`keepAliveMaxTimeout`)을 두어 주기적으로 재해석시킨다.
- `resolve*()`는 `/etc/hosts`를 무시하므로 로컬 개발에서 hosts 파일로 도메인을 덮어쓴 설정이 먹지 않는다.

## 요약

- TCP는 바이트 스트림이지 메시지 큐가 아니다. `write()` 횟수와 상대의 `data` 이벤트 횟수는 무관하며, 메시지 경계는 길이 접두사 프레이밍 같은 애플리케이션 프로토콜로 직접 만들어야 한다. `setNoDelay()`로 Nagle 지연을 없애고, TCP keep-alive로 중간 장비가 끊은 죽은 커넥션을 감지한다.
- `http.createServer`의 요청과 응답은 스트림이며, 핸들러가 호출되는 시점에 본문은 아직 도착하지 않았다. `headersTimeout`(Slowloris 방어), `requestTimeout`(전체 수신), `keepAliveTimeout`(로드밸런서보다 길게)을 각각 명시적으로 설정한다. HTTP/2는 `node:http2`로 제공되며 다중화가 필요한 경우에만 직접 쓴다.
- 아웃바운드 HTTP에서 커넥션 재사용은 선택이 아니다. keep-alive를 끄면 요청당 지연이 4배 이상 늘고 `TIME_WAIT` 소켓이 쌓여 포트가 고갈된다. `fetch`는 4xx/5xx에 예외를 던지지 않으며, 본문을 소비하지 않으면 커넥션이 풀로 반환되지 않는다.
- 헤더 이름은 소문자로 정규화되고 `set-cookie`만 배열로 유지된다. **크기 제한 없는 본문 파서는 DoS 취약점이다.** `Content-Length`와 실제 누적 바이트를 모두 검사하고, 파일 업로드는 스트리밍 파서로 처리한다.
- TLS는 SNI로 인증서를 고르고 ALPN으로 프로토콜을 협상한다. 자체 서명 인증서에는 SAN이 필수다. 대부분의 조직에서 TLS 종료는 프록시나 로드밸런서에 맡기는 편이 낫고, 내부 통신 인증에는 mTLS가 API 키보다 관리하기 쉽다.
- 프록시의 본질은 `req.pipe(upstream)`과 `up.pipe(res)` 두 줄이다. 홉 바이 홉 헤더를 제거하고 `X-Forwarded-*`를 덧붙이며, HTTPS는 `CONNECT` 터널로 통과시킨다. 이때 `head` 인자를 버리면 핸드셰이크가 멈춘다.
- UDP는 도달을 보장하지 않는 대신 메시지 경계를 보존하고 블로킹되지 않는다. 유실을 전제로 주기적 재전송과 상태 복구를 설계에 내장할 때만 안전하다. 메트릭 전송과 로컬 서비스 디스커버리가 대표 용도다.
- `dns.lookup()`은 스레드풀을 점유해 DNS 지연이 파일 I/O 장애로 번지게 만들고, `dns.resolve*()`는 논블로킹이지만 `/etc/hosts`를 무시한다. Node.js에는 DNS 캐시가 없으므로 직접 도입하고, 쿠버네티스에서는 `ndots` 설정이 외부 호출마다 헛된 질의를 유발한다.

## 연습문제

1. **프레이밍의 견고성 검증.** 10.1절의 `FrameDecoder`를 대상으로, (a) 4바이트 헤더가 두 개의 TCP 세그먼트에 걸쳐 도착하는 경우, (b) 한 청크에 완전한 프레임 3개와 잘린 프레임 1개가 함께 들어오는 경우, (c) 길이 필드가 `maxFrame`을 넘는 악의적 입력이 오는 경우를 각각 재현하는 테스트를 작성하라. 이어서 같은 프로토콜을 줄바꿈 구분자 방식으로 다시 구현하고, 본문에 줄바꿈이 포함될 때 어떤 이스케이프가 필요한지, 1MiB 페이로드에서 두 방식의 처리량 차이가 어느 정도인지 측정하라.

2. **소켓 고갈 재현과 해소.** 로컬에 HTTPS 에코 서버를 띄우고, `new http.Agent({ keepAlive: false })`를 쓰는 클라이언트로 초당 500건씩 60초간 요청을 보내라. `ss -tan state time-wait | wc -l`로 `TIME_WAIT` 소켓 증가를 관찰하고, 포트 범위를 좁혀(`net.ipv4.ip_local_port_range`) `EADDRNOTAVAIL`을 실제로 재현하라. 이어서 `undici`의 `Agent`로 `connections`를 8, 64, 512로 바꿔 가며 처리량(RPS)과 p99 지연, 그리고 열린 소켓 수를 표로 정리하고, 어느 지점부터 커넥션을 늘려도 이득이 없는지 설명하라.

3. **관측 가능한 역방향 프록시.** 10.6절의 역방향 프록시를 확장해, (a) `Upgrade` 요청을 처리해 WebSocket을 통과시키고, (b) `CONNECT` 터널링을 지원하며, (c) 백엔드 목록을 두고 라운드로빈으로 분배하되 연속 3회 실패한 백엔드를 30초간 제외하는 서킷 브레이커를 붙여라. 여기에 요청별 지연과 상태 코드를 StatsD로 전송하는 계측(10.7절)을 추가하고, 업스트림이 응답 도중 죽었을 때 클라이언트가 잘린 응답을 정상으로 오인하지 않는지 `Content-Length`와 청크 인코딩 두 경우 모두에서 확인하라.
