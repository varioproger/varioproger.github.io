# 33장. 빌드와 배포

코드가 개발자의 노트북을 떠나 사용자에게 도달하기까지의 경로를 다룬다. 이 경로는 대부분의 팀에서 가장 오래 방치되는 영역이고, 동시에 개발 속도에 가장 직접적으로 영향을 주는 영역이다.

이 장은 두 갈래로 진행한다. 앞부분(33.1~33.2)은 변경을 검증하는 파이프라인, 가운데(33.3~33.6)는 코드를 패키지로 묶어 배포 가능한 단위로 만드는 규약과 도구, 마지막(33.7)은 그 산출물을 실제 트래픽 위에 올리는 전략이다. 예시는 GitHub Actions로 쓰지만 여기서 다루는 원리는 특정 서비스에 묶여 있지 않다. 어떤 CI 도구를 쓰든 단계의 구성, 캐시의 위치, 실패 시 차단 지점은 같은 문제이며, 도구는 문법만 다를 뿐이다.

## 33.1 CI 파이프라인 구성하기

지속적 통합(continuous integration, CI)의 목적은 "메인 브랜치가 항상 배포 가능한 상태임을 자동으로 증명하는 것"이다. 이 문장에서 중요한 단어는 **자동**과 **항상**이다. 사람이 기억해서 실행하는 검증은 검증이 아니고, 머지 후에만 도는 검증은 이미 깨진 것을 알려줄 뿐이다.

### 파이프라인의 표준 단계

Node.js 프로젝트의 CI는 사실상 아래 순서로 수렴한다. 순서에는 이유가 있다. 싸고 빠른 검증을 앞에, 비싸고 느린 검증을 뒤에 둔다. 린트에서 걸릴 코드를 위해 통합 테스트를 5분간 돌릴 이유가 없다.

1. **체크아웃(checkout)** — 소스 가져오기
2. **런타임 준비** — Node 버전 고정
3. **의존성 설치** — 락 파일 기준의 결정적 설치
4. **린트(lint)** — 정적 스타일·오류 검사
5. **타입 검사(type check)** — TypeScript 또는 JSDoc 기반 검사
6. **테스트** — 단위 → 통합 순
7. **빌드** — 번들 또는 트랜스파일 산출물 생성
8. **이미지 빌드와 푸시** — 컨테이너 레지스트리에 업로드

앞의 4~6번은 병렬화 가능한 독립 검증이고, 7~8번은 앞 단계가 모두 성공했을 때만 의미가 있다. 이 구분이 워크플로 설계의 뼈대가 된다.

### GitHub Actions 워크플로

```yaml
# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:

# 같은 브랜치에 새 커밋이 오면 진행 중인 실행을 취소한다.
# 이미 낡은 커밋을 검증하느라 러너를 점유할 이유가 없다.
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  verify:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false          # 한 버전이 깨져도 나머지 결과를 끝까지 본다
      matrix:
        node: ['20', '22', '24']
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
          cache: npm            # ~/.npm 캐시를 락 파일 해시 기준으로 복원한다

      - run: npm ci             # 락 파일 그대로, 결정적으로 설치 (33.4 참조)

      - run: npm run lint
      - run: npm run typecheck
      - run: npm test -- --coverage

      - name: 커버리지 업로드
        if: matrix.node == '22'   # 대표 버전 하나에서만 수행
        uses: actions/upload-artifact@v4
        with:
          name: coverage
          path: coverage/

  build-image:
    needs: verify               # 검증이 전부 통과해야 실행된다
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
      id-token: write           # OIDC 기반 서명·프로비넌스에 필요 (33.6 참조)
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3

      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - uses: docker/build-push-action@v6
        with:
          push: true
          # 태그에 커밋 SHA를 쓴다. latest만으로는 무엇이 배포됐는지 알 수 없다
          tags: |
            ghcr.io/${{ github.repository }}:${{ github.sha }}
            ghcr.io/${{ github.repository }}:latest
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

### 캐시가 실제로 줄이는 것

의존성 설치는 대부분 프로젝트에서 CI 시간의 30~60%를 차지한다. `setup-node`의 `cache: npm`은 npm의 **다운로드 캐시**(`~/.npm`)를 복원한다. `node_modules` 자체를 캐시하는 것과는 다르다. 후자는 빠르지만 위험하다. 플랫폼별 네이티브 바인딩이나 설치 스크립트의 결과가 캐시에 굳어 재현 불가능한 상태를 만들기 때문이다. 다운로드 캐시만 복원하고 설치는 매번 수행하는 편이 안전하며, 네트워크 왕복이 사라지므로 체감 이득의 대부분은 그대로 얻는다.

Docker 이미지 빌드에서는 레이어 캐시가 더 큰 변수다. `Dockerfile`에서 `package*.json`을 먼저 복사해 설치하고 소스는 그 뒤에 복사하는 순서를 지켜야 소스 변경이 의존성 레이어를 무효화하지 않는다(32장 참조).

### 매트릭스 빌드의 실제 용도

여러 Node 버전에서 돌리는 이유는 두 가지다. 라이브러리라면 `engines` 필드에 선언한 범위가 거짓말이 아님을 증명해야 한다. 애플리케이션이라면 다음 LTS로 넘어갈 준비를 미리 하는 것이 목적이다. 현재 프로덕션이 20이라면 매트릭스에 22와 24를 넣어두면, 업그레이드 시점에 발견될 문제를 지금 발견한다.

다만 매트릭스는 곱셈이다. Node 3개 × OS 3개 = 9개 작업이고, 각 작업이 4분이면 러너 36분을 소비한다. 애플리케이션에서 OS 축까지 넓히는 것은 대개 낭비다. 프로덕션이 리눅스 컨테이너라면 리눅스만 검증하면 된다.

### 느린 파이프라인은 없는 파이프라인이다

실무에서 반복해 확인되는 사실 하나를 강조한다. **CI가 느려지면 사람들은 그것을 보지 않는다.** 15분짜리 파이프라인 앞에서 개발자는 결과를 기다리지 않고 다른 작업으로 전환하며, 컨텍스트 전환 후 돌아왔을 때는 실패 원인을 다시 파악해야 한다. 그 비용이 쌓이면 "일단 머지하고 나중에 고치자"는 문화가 자리 잡는다.

경험적 기준은 PR 검증 10분 이내, 이상적으로는 5분이다. 이 예산을 지키기 위해 쓸 수 있는 수단은 다음과 같다.

- **병렬화**: 린트·타입 검사·단위 테스트를 별도 잡으로 분리해 동시에 돌린다.
- **변경 범위 한정**: 모노레포라면 변경된 워크스페이스만 검증한다(33.4 참조).
- **테스트 분할**: 느린 통합 테스트를 여러 잡에 샤딩한다.
- **단계 이동**: E2E나 부하 테스트처럼 10분이 넘는 검증은 PR이 아니라 머지 후 또는 야간 스케줄로 옮긴다.

마지막 항목은 타협처럼 보이지만 합리적이다. 모든 검증을 모든 PR에 붙이면 결국 아무도 PR을 열지 않게 된다.

## 33.2 풀 리퀘스트 검증과 자동 테스트

CI가 "무엇을 검사하는가"라면, PR 검증은 "무엇을 강제하는가"이다. 검사 결과가 있어도 머지를 막지 않으면 그것은 권고에 불과하다.

### 무엇을 필수로 만들 것인가

강제 대상은 다음 다섯 가지로 정리된다. 각각을 필수(blocking)로 할지 경고로 할지는 팀이 정하지만, 앞의 셋은 예외 없이 필수여야 한다.

**테스트 통과.** 협상 대상이 아니다. 다만 불안정한 테스트(flaky test)가 섞여 있으면 이 규칙이 곧바로 무너진다. 사람들이 "또 그거네" 하며 재실행 버튼을 누르기 시작하면 필수 검사는 의미를 잃는다. 불안정한 테스트는 고치거나 즉시 격리해야 한다(30장 참조).

**커버리지 임계.** 절대 수치보다 **하락 금지**가 실용적이다. "전체 80% 이상"은 레거시가 많은 코드베이스에서 달성 불가능한 목표가 되어 무시되지만, "이 PR이 추가한 라인의 커버리지 80% 이상"은 항상 달성 가능하다.

**린트.** 자동 수정이 가능한 것은 CI에서 실패시키기보다 pre-commit 훅에서 처리하는 편이 마찰이 적다. CI 린트는 훅을 우회한 경우의 안전망 역할이다.

**보안 감사.** `npm audit`을 파이프라인에 넣되 임계를 신중히 정한다. 자세한 한계는 33.4에서 다룬다.

**커밋 규약.** Conventional Commits를 강제하면 릴리스 노트와 버전 결정을 자동화할 수 있다(33.3 참조). 강제 자체가 목적이 아니라 자동화의 입력을 확보하는 것이 목적이다.

```yaml
# .github/workflows/pr-checks.yml — 검증 잡을 쪼개 병렬로 돌린다
name: PR Checks
on: pull_request

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '22', cache: npm }
      - run: npm ci
      - run: npm run lint

  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }   # 기준 브랜치와 비교하려면 전체 히스토리 필요
      - uses: actions/setup-node@v4
        with: { node-version: '22', cache: npm }
      - run: npm ci
      - run: npm test -- --coverage --coverage-reporter=lcov
      # 변경된 라인의 커버리지만 판정한다
      - run: npx diff-cover coverage/lcov.info --compare-branch=origin/${{ github.base_ref }} --fail-under=80

  audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '22', cache: npm }
      - run: npm ci
      # high 이상만 차단한다. low/moderate까지 막으면 곧 무시된다
      - run: npm audit --audit-level=high

  commits:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - run: npx commitlint --from origin/${{ github.base_ref }} --to HEAD
```

### 브랜치 보호 규칙

검사를 필수로 만드는 것은 CI 설정이 아니라 저장소의 브랜치 보호(branch protection) 규칙이다. 최소 구성은 다음과 같다.

- 필수 상태 검사(required status checks) 지정: `lint`, `test`, `audit`
- "머지 전 최신 기준 브랜치 필요" 활성화 — A와 B가 각각 통과했지만 합쳐지면 깨지는 의미론적 충돌(semantic conflict)을 막는다
- 최소 1인 승인, 새 커밋이 푸시되면 기존 승인 무효화
- 메인 브랜치 직접 푸시 금지, 강제 푸시 금지

여기서 흔한 함정이 있다. 잡 이름을 바꾸면 필수 검사 설정이 그 이름을 찾지 못해 **검증 없이 머지 가능한 상태**가 조용히 만들어진다. 오류가 아니라 침묵이라 더 위험하다. 잡 이름 변경은 브랜치 보호 설정 갱신과 반드시 함께 처리한다.

또한 매트릭스 잡은 이름이 `verify (20)`처럼 확장되므로, 필수 검사로는 매트릭스 전체를 `needs`로 묶은 요약 잡 하나를 두고 그것을 지정하는 편이 관리하기 쉽다.

```yaml
  # 매트릭스 전체의 성공 여부를 하나의 상태로 집약한다
  verify-all:
    needs: [lint, test, audit]
    if: always()
    runs-on: ubuntu-latest
    steps:
      - name: 결과 판정
        run: |
          if [ "${{ contains(needs.*.result, 'failure') }}" = "true" ]; then
            echo "선행 잡 중 실패가 있다"; exit 1
          fi
```

## 33.3 모듈, 패키지, SemVer

패키지는 배포의 최소 단위다. 애플리케이션을 컨테이너로 배포하더라도 그 안의 의존성은 전부 패키지이고, 패키지 간 호환성 판단의 기준이 유의적 버전(semantic versioning, SemVer)이다.

### 규칙

버전은 `MAJOR.MINOR.PATCH`이며 의미는 다음과 같다.

- **PATCH** — 동작을 바꾸지 않는 버그 수정
- **MINOR** — 하위 호환을 유지하는 기능 추가
- **MAJOR** — 하위 호환을 깨는 변경

핵심은 숫자가 아니라 약속이다. "MINOR 업그레이드는 내 코드를 깨뜨리지 않는다"는 약속이 있어야 `^` 범위 지정이 성립한다.

### 현실

그리고 이 약속은 자주 지켜지지 않는다. 원인은 악의가 아니라 **공개 API의 경계가 모호하기 때문**이다.

- 성능 개선이 타이밍을 바꾸어 경쟁 상태를 노출한다. 저자에게는 PATCH지만 사용자에게는 장애다.
- 오류 메시지 문구가 바뀐다. 그 문구를 정규식으로 매칭하던 코드가 깨진다.
- 타입 정의만 엄격해진다. 런타임은 동일하지만 빌드가 실패한다.
- 최소 Node 버전이 올라간다. MAJOR로 올리는 저자도 있고 MINOR로 처리하는 저자도 있다.
- 버그를 고쳤더니 그 버그에 의존하던 코드가 깨진다. 헤이럼의 법칙(Hyrum's law)이다.

결론은 SemVer를 신뢰하되 검증 없이 신뢰하지 않는 것이다. 실무적 태도는 "범위로 받되 락 파일로 고정하고, 갱신은 CI가 검증하는 명시적 행위로 만든다"이다.

### 범위 지정자

```json
{
  "dependencies": {
    "fastify": "^5.2.0",   // >=5.2.0 <6.0.0 — MINOR/PATCH 허용
    "pino": "~9.6.0",      // >=9.6.0 <9.7.0 — PATCH만 허용
    "left-pad": "1.3.0"    // 정확히 이 버전만
  }
}
```

`^`는 npm의 기본값이며 대부분의 경우 옳은 선택이다. 다만 `0.x` 버전에서는 규칙이 달라진다. `^0.4.2`는 `>=0.4.2 <0.5.0`으로, MINOR 자리가 MAJOR처럼 취급된다. 1.0.0 이전 패키지는 SemVer 보증 자체가 없다는 뜻이므로, 핵심 경로에 0.x 의존성을 두는 것은 그 자체로 위험 항목이다.

`~`는 과도한 방어처럼 보이지만 대상에 따라 합리적이다. 암호화, 인증, 결제 관련 라이브러리처럼 동작 변화의 대가가 큰 곳에서 쓸 만하다. 정확 버전 고정은 애플리케이션의 직접 의존성에는 큰 이득이 없다. 어차피 락 파일이 고정하고 있고, 갱신만 번거로워지기 때문이다. 반대로 라이브러리를 배포한다면 정확 버전 고정은 해악이다. 소비자 쪽에서 중복 설치와 버전 충돌을 유발한다.

### 락 파일이 필요한 이유

`^5.2.0`이 설치 시점마다 다른 버전을 가져온다는 사실을 다시 보자. 락 파일(`package-lock.json`)이 없으면 개발자 노트북, CI, 프로덕션이 각각 다른 의존성 트리를 갖는다. 재현 불가능한 버그의 대표적 원인이며, "내 로컬에서는 되는데"의 가장 흔한 실체다.

락 파일은 전체 트리의 정확한 버전과 무결성 해시(integrity hash)를 기록한다. 해시가 있으므로 레지스트리의 특정 버전이 몰래 교체되는 상황도 감지한다. 라이브러리 저장소라 하더라도 락 파일은 커밋한다. 게시되는 tarball에는 포함되지 않으므로 소비자에게 영향이 없고, 저장소의 CI는 결정적으로 실행된다.

### 프리릴리스 태그

```bash
1.4.0-alpha.1 < 1.4.0-beta.1 < 1.4.0-rc.1 < 1.4.0
```

프리릴리스 버전은 어떤 범위 지정자에도 자동으로 매칭되지 않는다. `^1.0.0`은 `1.4.0-rc.1`을 설치하지 않으며, 받으려면 명시해야 한다. 게시할 때는 dist-tag를 함께 지정해 `latest`가 오염되지 않게 한다.

```bash
npm version prerelease --preid=rc     # 1.4.0-rc.1
npm publish --tag next                # latest는 그대로, next 태그로만 배포
npm install my-pkg@next               # 소비자는 명시적으로 받는다
```

`--tag`를 빠뜨리고 RC를 게시하면 모든 사용자가 다음 설치에서 RC를 받게 된다. 게시 파이프라인에서 반드시 자동화해야 할 지점이다.

## 33.4 npm CLI와 의존성 관리

### npm ci와 npm install

두 명령의 차이는 CI 설정에서 가장 자주 틀리는 부분이다.

| | `npm install` | `npm ci` |
|---|---|---|
| 락 파일 | 필요 시 갱신한다 | 그대로 따르고, 어긋나면 실패한다 |
| `node_modules` | 기존 상태에 맞춰 조정 | 통째로 삭제 후 재설치 |
| 락 파일 없음 | 새로 생성 | 즉시 실패 |
| 용도 | 로컬 개발 | CI, 컨테이너 빌드, 프로덕션 |

`npm ci`는 락 파일과 `package.json`이 불일치하면 설치를 진행하지 않고 실패한다. 이것이 기능이다. 누군가 `package.json`만 고치고 락 파일을 커밋하지 않은 PR은 CI에서 즉시 드러난다. 반대로 `npm install`을 CI에서 쓰면 그 불일치가 조용히 해소되면서, 검증한 트리와 프로덕션의 트리가 달라진다.

```bash
npm ci                      # 결정적 설치
npm ci --omit=dev           # 런타임 이미지: devDependencies 제외
npm ci --ignore-scripts     # 설치 스크립트 실행 차단 (34장 참조)
```

`--ignore-scripts`는 공급망 공격의 주요 경로인 `postinstall` 스크립트를 막는다. 네이티브 모듈이 있으면 빌드가 필요하므로 전면 적용은 어렵지만, 필요한 패키지만 예외로 두는 방식으로 접근할 수 있다.

### npm audit과 그 한계

`npm audit`은 설치된 트리를 취약점 데이터베이스와 대조한다. 유용하지만 다음 한계를 알고 써야 한다.

**오탐이 많다.** 감사는 "이 패키지의 이 버전에 알려진 취약점이 있다"만 판단하며, **그 코드 경로를 실제로 사용하는지**는 보지 않는다. 빌드 도구의 의존성에서 발견된 ReDoS 취약점은 사용자 입력이 닿지 않는 곳이므로 실질 위험이 0에 가깝지만 동일한 심각도로 보고된다.

**수정 불가능한 경고가 쌓인다.** 상위 패키지가 갱신되지 않으면 하위 취약점을 고칠 방법이 없다. 이런 경고가 누적되면 팀은 감사 결과 전체를 무시하기 시작한다. 이것이 진짜 위험이다. 소음이 신호를 덮는다.

대응은 두 가지다. 임계를 `--audit-level=high`로 올려 실질적 신호만 차단하고, 판단이 끝난 항목은 기록으로 남긴다.

```bash
npm audit --audit-level=high --omit=dev   # 런타임 의존성만, high 이상만
npm audit signatures                       # 레지스트리 서명 검증
```

### overrides로 하위 의존성 고정

상위 패키지가 취약한 버전을 고정하고 있을 때 사용하는 탈출구다.

```json
{
  "overrides": {
    "tar": "^7.4.3",
    "some-lib": {
      "semver": "^7.6.3"
    }
  }
}
```

첫 항목은 트리 전체의 `tar`를 강제하고, 둘째 항목은 `some-lib` 하위의 `semver`만 바꾼다. 강력하지만 저자가 검증하지 않은 조합을 만드는 것이므로, 임시 조치로 다루고 상위 패키지가 갱신되면 반드시 제거한다. 남겨두면 다음 사람이 이유를 모르는 채 유지하게 된다. 주석을 남길 수 없는 JSON이므로, 제거 조건을 별도 문서나 이슈로 연결해두는 편이 낫다.

### 의존성 수를 줄이는 것이 곧 공격 표면을 줄이는 것

직접 의존성 20개가 전이 의존성 900개가 되는 일은 드물지 않다. 그 900개 각각이 코드 실행 권한을 가진 서드파티다. 공급망 공격의 실제 사례들은 예외 없이 아무도 이름을 모르는 하위 의존성을 통해 일어났다(34장 참조).

새 의존성을 추가하기 전 판단 기준은 다음과 같다.

- 표준 라이브러리로 되는가? Node.js는 이제 `fetch`, `test`, `parseArgs`, `styleText`, `.env` 로딩을 내장한다.
- 필요한 것이 그 패키지의 몇 퍼센트인가? 함수 하나 때문에 300개의 전이 의존성을 들이는가?
- 유지보수 상태는? 마지막 커밋, 미해결 이슈, 관리자 수를 본다. 관리자 1인 패키지는 계정 탈취 한 번으로 무너진다.

```bash
npm ls --all | wc -l              # 전체 트리 규모
npm ls --omit=dev --all | wc -l   # 프로덕션에 실제로 실리는 규모
npx depcheck                      # 선언됐지만 쓰이지 않는 의존성 탐지
```

### workspaces

모노레포에서 여러 패키지를 하나의 락 파일과 하나의 `node_modules`로 관리한다.

```json
{
  "name": "acme-platform",
  "private": true,
  "workspaces": ["packages/*", "services/*"]
}
```

```bash
npm ci                                   # 전체 워크스페이스 한 번에 설치
npm run build -w @acme/core              # 특정 워크스페이스에서 실행
npm run test --workspaces --if-present   # 전부 실행, 스크립트 없으면 건너뜀
npm install lodash -w @acme/api          # 특정 워크스페이스에 의존성 추가
```

워크스페이스 간 참조는 심볼릭 링크로 연결되므로 로컬 변경이 즉시 반영된다. 루트 `package.json`에 `"private": true`를 넣는 것을 잊지 않는다. 실수로 저장소 전체를 게시하는 사고를 막는 최소 장치다.

## 33.5 내부 npm 레지스트리 운영

조직이 커지면 공개하고 싶지 않은 공통 코드가 생긴다. 로깅 설정, 인증 클라이언트, 내부 API 타입 정의 같은 것들이다. 이것을 저장소 URL로 직접 의존하거나 파일 복사로 공유하면 버전 개념이 사라진다. 내부 레지스트리는 이 문제를 표준 도구로 푸는 방법이다.

Verdaccio는 가장 가볍게 시작할 수 있는 선택지다. 단일 Node.js 프로세스로 동작하고, 자체 저장소와 **업스트림 프록시 캐시**를 함께 제공한다.

```yaml
# docker-compose.yml
services:
  registry:
    image: verdaccio/verdaccio:6
    ports: ['4873:4873']
    volumes:
      - ./storage:/verdaccio/storage      # 게시된 패키지와 캐시 (영속 필수)
      - ./config:/verdaccio/conf
```

```yaml
# config/config.yaml
storage: /verdaccio/storage
auth:
  htpasswd:
    file: /verdaccio/storage/htpasswd
    max_users: -1        # 셀프 가입 차단, 관리자만 계정 생성

uplinks:
  npmjs:
    url: https://registry.npmjs.org/
    cache: true          # 다운로드한 tarball을 로컬에 보관한다
    timeout: 30s
    max_fails: 5

packages:
  '@acme/*':             # 사내 스코프: 인증된 사용자만, 외부로 나가지 않는다
    access: $authenticated
    publish: $authenticated
    # proxy 항목이 없다 — 오타로 인한 외부 유출을 막는다

  '**':                  # 그 외 전부: 읽기는 공개, 게시는 금지, 업스트림 프록시
    access: $all
    publish: $nobody
    proxy: npmjs
```

`@acme/*` 블록에 `proxy`를 두지 않는 것이 중요하다. 이 설정이 없으면 사내 패키지 이름을 외부 레지스트리에 조회하게 되고, 공격자가 같은 이름을 공개 레지스트리에 선점하는 의존성 혼동(dependency confusion) 공격에 노출된다(34장 참조).

### 클라이언트 설정

스코프별로 레지스트리를 나눠 지정한다.

```ini
# .npmrc (저장소에 커밋)
@acme:registry=https://npm.acme.internal/
//npm.acme.internal/:_authToken=${NPM_TOKEN}   # 값이 아니라 환경변수 참조
```

토큰을 파일에 직접 적지 않고 `${NPM_TOKEN}` 형태로 두면 커밋해도 안전하다. npm은 설치 시점에 환경변수를 치환한다. CI에서는 시크릿으로 주입한다.

```bash
npm login --scope=@acme --registry=https://npm.acme.internal/
npm whoami --registry=https://npm.acme.internal/
```

### 사내 패키지 게시

```bash
cd packages/logger
npm version minor              # 1.3.0 → 1.4.0, 커밋과 태그 생성
npm publish                    # @acme 스코프이므로 내부 레지스트리로 간다
npm view @acme/logger versions --registry=https://npm.acme.internal/
```

패키지 이름이 `@acme/logger`이므로 `.npmrc`의 스코프 매핑에 따라 자동으로 내부 레지스트리를 향한다. 스코프 없는 이름을 쓰면 공개 레지스트리로 나갈 수 있으므로, 사내 패키지는 예외 없이 스코프를 붙인다.

### 프록시 캐시라는 부수 효과

내부 레지스트리를 도입하면 종종 원래 목적보다 이 효과가 더 크게 체감된다. 업스트림에서 한 번 받은 tarball이 로컬에 남으므로,

- 외부 레지스트리 장애나 네트워크 단절 중에도 이미 캐시된 패키지로 빌드가 가능하다.
- 패키지가 삭제되거나 특정 버전이 사라져도 캐시본이 남는다.
- 설치가 빨라진다. 특히 CI 러너가 여러 대일수록 효과가 크다.

다만 캐시 저장소가 곧 단일 장애점이 된다. 볼륨을 영속화하고 백업 대상에 포함시켜야 한다. 그렇지 않으면 컨테이너 재생성 한 번으로 사내 패키지 전체를 잃는다.

## 33.6 패키지 게시와 배포 전략

게시는 되돌릴 수 없는 행위다. 이 전제에서 체크리스트가 나온다.

### 게시 전 체크리스트

**`files` 필드.** 무엇을 tarball에 넣을지 명시적으로 지정한다. `.npmignore`로 제외하는 방식은 새 파일이 기본 포함되므로 사고가 나기 쉽다. 화이트리스트가 안전하다.

**`exports` 맵.** 공개 진입점을 정의한다. 여기에 없는 내부 경로는 소비자가 임의로 접근할 수 없으므로, 내부 구조를 자유롭게 리팩터링할 수 있다.

**`prepublishOnly`.** 게시 직전에 자동 실행된다. 빌드와 테스트를 여기에 걸면 산출물 없이 게시하는 사고를 막는다.

```json
{
  "name": "@acme/logger",
  "version": "1.4.0",
  "type": "module",
  "files": ["dist", "README.md"],
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js"
    },
    "./transport": "./dist/transport.js"
  },
  "engines": { "node": ">=20.11" },
  "scripts": {
    "build": "tsc -p tsconfig.build.json",
    "prepublishOnly": "npm run build && npm test"
  },
  "publishConfig": {
    "access": "public",
    "provenance": true
  }
}
```

게시 전에 실제 내용물을 반드시 확인한다.

```bash
npm pack --dry-run        # tarball에 들어갈 파일 목록 출력
npx publint               # exports/files/type 설정의 흔한 오류 검사
npx are-the-types-wrong   # 타입 정의 해석 경로 검증
```

`npm pack --dry-run`을 습관으로 만들면 `.env`나 테스트 픽스처가 함께 나가는 사고를 대부분 막을 수 있다.

### 프로비넌스

`provenance: true`는 CI에서 게시할 때 어떤 저장소의 어떤 커밋에서 만들어졌는지를 증명하는 서명된 증명서를 함께 게시한다. 소비자는 패키지 페이지에서 빌드 출처를 확인할 수 있다. OIDC 기반이므로 워크플로에 `id-token: write` 권한이 필요하다.

### CI에서 자동 게시

수동 게시는 두 가지 사고를 반복한다. 빌드하지 않고 게시하거나, 잘못된 계정으로 게시한다. 태그 푸시를 트리거로 자동화한다.

```yaml
# .github/workflows/release.yml
name: Release
on:
  push:
    tags: ['v*']

jobs:
  publish:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      id-token: write            # 프로비넌스 서명용
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
          registry-url: https://registry.npmjs.org/
      - run: npm ci
      - run: npm test
      # 태그와 package.json 버전이 일치하는지 확인한다
      - name: 버전 일치 검사
        run: |
          PKG=$(node -p "require('./package.json').version")
          TAG="${GITHUB_REF_NAME#v}"
          [ "$PKG" = "$TAG" ] || { echo "불일치: $PKG != $TAG"; exit 1; }
      - run: npm publish
        env:
          NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}
```

### 되돌릴 수 없다

게시된 버전은 사실상 영구적이다. `npm unpublish`는 게시 후 72시간 이내, 그리고 다른 패키지가 의존하지 않는 경우로 제한된다. 이 제한은 2016년 `left-pad` 사건 이후 도입됐다. 널리 쓰이던 패키지 하나가 삭제되면서 수많은 빌드가 동시에 실패한 사건이었다.

실무에서 쓸 수 있는 수단은 사실상 두 가지다.

```bash
npm deprecate @acme/logger@1.4.0 "심각한 버그. 1.4.1로 올릴 것"
npm dist-tag add @acme/logger@1.3.9 latest    # latest를 이전 버전으로 되돌린다
```

`deprecate`는 설치 시 경고를 띄우고, `dist-tag` 변경은 신규 설치자가 문제 버전을 받지 않게 한다. 이미 락 파일에 그 버전을 고정한 소비자에게는 아무 영향이 없다. 그래서 결론은 단순하다. **되돌리는 것보다 다음 패치를 빨리 내는 것이 항상 낫다.** 잘못 게시했다면 버전 번호를 하나 올려 수정본을 내고 문제 버전을 deprecate 한다.

## 33.7 배포 전략: 롤링, 블루/그린, 카나리

여기서부터는 패키지가 아니라 실행 중인 서비스를 교체하는 이야기다. 세 전략은 "얼마나 많은 사용자에게, 얼마나 오래, 새 버전을 노출할 것인가"를 다르게 답한다.

### 공통 전제 조건

전략을 고르기 전에 아래가 충족돼야 한다. 하나라도 빠지면 어떤 전략도 안전하지 않다.

- **무상태(stateless)** — 인스턴스가 언제 사라져도 되어야 한다. 세션이나 진행 중 작업이 프로세스 메모리에 있으면 교체가 곧 데이터 손실이다.
- **정상 종료(graceful shutdown)** — `SIGTERM`을 받으면 새 연결을 거부하고 진행 중 요청을 마친 뒤 종료한다(32장 참조).
- **하위 호환 스키마** — 신·구 버전이 동시에 같은 데이터베이스를 쓰는 구간이 반드시 존재한다(19장 참조).
- **관측성** — 새 버전이 나쁘다는 것을 사람보다 먼저 알아야 한다. 오류율, 지연 시간 백분위수, 포화도가 버전 레이블로 분리돼야 한다(31장 참조).
- **헬스 체크 분리** — liveness와 readiness를 구분한다. readiness가 의존성 상태까지 반영해야 트래픽이 준비 안 된 인스턴스로 가지 않는다.

### 롤링 업데이트

인스턴스를 몇 개씩 순차 교체한다. 오케스트레이터의 기본값이며 추가 자원이 거의 필요 없다(32장 참조).

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 0    # 용량을 줄이지 않는다
    maxSurge: 2          # 새 파드 2개를 먼저 띄운 뒤 구버전을 내린다
```

- 장점: 비용이 낮고 설정이 단순하다.
- 단점: 전환 도중 두 버전이 동시에 서비스한다. 롤백도 롤링이라 되돌리는 데 나갈 때와 같은 시간이 걸린다.

### 블루/그린

동일 규모의 환경을 두 벌 운영한다. 블루가 프로덕션 트래픽을 받는 동안 그린에 새 버전을 배포하고, 검증이 끝나면 라우터에서 한 번에 전환한다.

- 장점: 전환이 즉각적이고 롤백도 즉각적이다. 전환 전에 실제 환경에서 스모크 테스트를 돌릴 수 있다.
- 단점: 인프라 비용이 두 배다. 그리고 데이터베이스는 두 벌로 만들 수 없다.

마지막 문장이 핵심 난점이다. 블루와 그린이 같은 데이터베이스를 공유하므로 스키마는 양쪽 모두와 호환돼야 한다. 컬럼 삭제나 이름 변경을 배포와 함께 수행하면 롤백이 불가능해진다. 되돌아간 구버전이 이미 사라진 컬럼을 찾기 때문이다.

해법은 확장-수축(expand-contract) 패턴이다. 릴리스 1에서 새 컬럼을 추가하고 양쪽에 쓴다. 릴리스 2에서 읽기를 새 컬럼으로 옮긴다. 릴리스 3, 즉 **롤백 가능성이 사라진 뒤에** 옛 컬럼을 지운다. 스키마 변경은 배포와 분리된 별도의 릴리스여야 한다.

### 카나리

새 버전에 트래픽의 일부만 보내고, 지표를 관찰하며 비중을 늘린다. 5% → 25% → 50% → 100%가 전형적인 단계다.

```yaml
# 트래픽 가중치로 카나리 비중을 조절한다 (게이트웨이 설정 예)
routes:
  - service: api-stable
    weight: 95
  - service: api-canary
    weight: 5
```

- 장점: 장애의 영향 범위가 트래픽 비중만큼으로 제한된다. 지표 기반 자동 승격과 자동 롤백이 가능하다.
- 단점: 라우팅 제어, 버전별 지표 분리, 자동 판정 규칙이 모두 필요하다.

자동 판정은 절대값이 아니라 **안정 버전과의 비교**로 세우는 것이 옳다. "카나리 오류율 1% 미만"은 전체 오류율이 원래 2%인 시스템에서는 항상 실패하고, 원래 0.01%인 시스템에서는 100배 악화를 통과시킨다. "카나리 오류율이 안정 버전의 1.5배를 넘으면 롤백", "p99 지연이 20% 이상 악화되면 롤백"처럼 상대 기준으로 정의한다.

또 하나 유의할 점은 5% 트래픽으로는 통계적 유의성을 얻기 어렵다는 것이다. 초당 10건을 받는 서비스에서 5% 카나리는 30분에 900건이고, 여기서 오류율 차이를 판정하는 것은 사실상 노이즈를 읽는 일이다. 저트래픽 서비스에서는 카나리 비중을 높이거나 관찰 시간을 늘려야 한다.

### 기능 플래그: 배포와 릴리스의 분리

세 전략 모두 "배포 단위 = 릴리스 단위"를 전제한다. 기능 플래그(feature flag)는 이 결합을 끊는다. 코드는 배포하되 기능은 꺼둔 채로 두고, 이후 플래그로 켜는 것이다.

```js
// 배포와 릴리스가 분리된다: 코드는 이미 프로덕션에 있고 노출만 제어한다
import { flags } from './flags.js'

app.post('/checkout', async (req, reply) => {
  if (await flags.enabled('new-pricing-engine', { userId: req.user.id })) {
    return newPricingEngine(req.body)
  }
  return legacyPricingEngine(req.body)
})
```

이 방식의 이점은 롤백 속도다. 재배포는 수 분이 걸리지만 플래그를 끄는 것은 수 초다. 대상 지정도 자유롭다. 내부 직원에게만, 특정 지역에만, 사용자의 1%에만 켤 수 있다.

비용도 분명하다. 모든 플래그는 코드 경로를 두 배로 만들고 테스트 조합을 늘린다. 그래서 플래그에는 반드시 수명과 제거 담당자를 정해둔다. 몇 년 된 죽은 플래그가 수십 개 쌓인 코드베이스는 플래그가 없던 시절보다 이해하기 어렵다.

### 선택 기준

정리하면 이렇다. 대부분의 내부 서비스는 롤링으로 충분하다. 전환 순간의 통제가 중요하고 예산이 허용되면 블루/그린이다. 실패 비용이 크고 관측성과 라우팅 제어가 이미 갖춰진 사용자 대면 서비스라면 카나리다. 그리고 어떤 전략을 쓰든 기능 플래그는 별도로 도입할 가치가 있다. 배포 전략은 코드 교체의 위험을 다루지만, 기능 플래그는 기능 자체의 위험을 다루기 때문이다.

## 요약

- CI 파이프라인은 싸고 빠른 검증을 앞에 두고, 캐시는 `node_modules`가 아니라 다운로드 캐시를 대상으로 한다. PR 검증 예산은 10분이며, 느린 파이프라인은 결국 아무도 보지 않는 파이프라인이 된다.
- 검사 결과는 브랜치 보호 규칙으로 필수 상태 검사에 연결해야 강제력을 갖는다. 잡 이름을 바꾸면 검증이 조용히 사라질 수 있다.
- SemVer는 약속이지 보증이 아니다. 범위로 받되 락 파일로 고정하고, 갱신은 CI가 검증하는 명시적 행위로 만든다.
- CI와 컨테이너 빌드에서는 `npm ci`를 쓴다. 락 파일 불일치에서 실패하는 동작이 결함이 아니라 기능이다.
- `npm audit`은 오탐이 많으므로 임계를 `high` 이상으로 두어 신호를 지킨다. 의존성 수를 줄이는 것이 감사보다 근본적인 방어다.
- 내부 레지스트리는 사내 패키지 공유와 업스트림 프록시 캐시를 함께 제공한다. 사내 스코프에는 절대 프록시를 설정하지 않는다.
- 게시는 되돌릴 수 없다. `files`, `exports`, `prepublishOnly`, `npm pack --dry-run`으로 사고를 막고, 문제가 생기면 되돌리기보다 다음 패치를 빨리 낸다.
- 롤링·블루/그린·카나리는 모두 무상태, 정상 종료, 하위 호환 스키마, 관측성을 전제한다. 기능 플래그는 배포와 릴리스를 분리해 초 단위 롤백을 가능하게 한다.

## 연습문제

1. 린트·타입 검사·단위 테스트를 각각 별도 잡으로 분리하고, 세 잡의 결과를 하나의 상태로 집약하는 요약 잡을 추가한 워크플로를 작성하라. 분리 전후의 전체 실행 시간을 측정해 병렬화의 실제 이득을 확인하고, 러너 사용 시간(과금 대상)은 어떻게 변했는지 함께 보고하라.

2. 의존성 하나가 취약한 하위 의존성을 고정하고 있는 상황을 만들고(예: 구버전 패키지 설치), `overrides`로 그 하위 의존성만 안전한 버전으로 고정하라. 적용 전후의 `npm ls <패키지명>` 출력과 `npm audit` 결과를 비교하고, 이 override를 언제 제거해야 하는지 판단 기준을 문서화하라.

3. 두 개의 버전을 각각 `stable`과 `canary`로 배포하고, 게이트웨이 가중치로 5%를 카나리에 보내라. 두 버전의 오류율과 p99 지연을 버전 레이블로 분리해 수집한 뒤, "카나리 오류율이 안정 버전의 1.5배를 초과하면 자동 롤백"하는 판정 스크립트를 작성하라. 서비스의 초당 요청 수를 고려할 때 이 판정이 신뢰할 만해지려면 관찰 시간이 얼마나 필요한지 계산하라.
