# 15장. 고급 레시피

앞의 장들에서 다룬 패턴들은 대체로 하나의 문제에 하나의 구조를 대응시켰다. 이 장은 그 반대다. 실무에서 반복적으로 마주치지만 교과서적인 패턴 이름이 붙어 있지 않은 문제들, 그러니까 "생성자는 비동기가 될 수 없는데 컴포넌트는 비동기 초기화가 필요하다", "같은 데이터를 동시에 100명이 요청한다", "이미 시작한 작업을 중간에 그만두고 싶다", "재시도를 넣었더니 장애가 더 커졌다" 같은 문제들을 다룬다.

이 레시피들의 공통점은 해법이 하나가 아니라는 것이다. 각 해법은 서로 다른 비용을 호출자에게 전가한다. 이 장의 목표는 코드를 외우는 것이 아니라 그 비용의 위치를 알아보는 눈을 기르는 데 있다.

## 15.1 비동기 초기화 컴포넌트 다루기

### 문제 상황

JavaScript의 생성자(constructor)는 동기적이다. `new` 연산자는 객체를 즉시 반환해야 하며, 생성자에서 `await`를 쓸 수 없다. 그런데 현실의 컴포넌트 대부분은 사용 가능한 상태가 되기까지 비동기 작업을 필요로 한다. 데이터베이스 클라이언트는 TCP 연결과 핸드셰이크를 마쳐야 하고, 설정 로더는 파일이나 원격 설정 서버를 읽어야 하며, 암호화 모듈은 키를 유도(derive)해야 한다.

이 간극이 만드는 버그는 유난히 잡기 어렵다. 객체는 멀쩡히 존재하는데 내부 상태가 아직 준비되지 않았을 뿐이므로, 테스트 환경처럼 로컬 연결이 빠른 곳에서는 통과하고 네트워크 지연이 있는 프로덕션에서만 터진다.

가상의 데이터베이스 클라이언트를 예로 삼자.

```js
// db.mjs — 비동기 초기화가 필요한 컴포넌트
import { EventEmitter } from 'node:events'
import { setTimeout as delay } from 'node:timers/promises'

class DB extends EventEmitter {
  connected = false

  async connect () {
    // 실제로는 소켓 연결과 인증 핸드셰이크가 일어난다
    await delay(500)
    this.connected = true
    this.emit('connected')
  }

  async query (sql) {
    if (!this.connected) {
      throw new Error('아직 연결되지 않았습니다')
    }
    return [{ sql }]
  }
}

export const db = new DB()
```

`db.query()`를 `connect()`가 끝나기 전에 호출하면 예외가 난다. 문제는 이 컴포넌트를 임포트하는 쪽이 "언제 준비되는지"를 알아야 한다는 점이다. 이 부담을 누가 지느냐에 따라 세 가지 해법이 갈린다.

### 해법 1: 로컬 초기화 검사

가장 단순한 방법은 호출자가 매번 준비 상태를 확인하는 것이다.

```js
// consumer-check.mjs — 호출자가 상태를 검사한다
import { once } from 'node:events'
import { db } from './db.mjs'

db.connect()

export async function updateLastAccess (userId) {
  if (!db.connected) {
    await once(db, 'connected')   // 준비될 때까지 기다린다
  }
  return db.query(`UPDATE users SET last_access = now() WHERE id = ${userId}`)
}
```

동작은 한다. 그러나 이 방식은 컴포넌트의 내부 사정을 모든 호출 지점으로 유출시킨다. `db`를 쓰는 함수가 서른 개라면 서른 곳에 같은 세 줄이 복사된다. 한 곳이라도 빠뜨리면 그 경로만 간헐적으로 실패한다. 게다가 `connected` 플래그와 `'connected'` 이벤트라는 두 개의 내부 구현 세부사항이 공개 API가 되어 버린다.

### 해법 2: 지연 시작

두 번째 방법은 초기화 자체를 미루고, 모든 공개 메서드가 초기화를 보장하도록 감싸는 것이다.

```js
// db-lazy.mjs — 첫 사용 시점에 초기화하고, 그 프로미스를 재사용한다
class LazyDB {
  #ready = null

  #ensureReady () {
    // 초기화 프로미스를 한 번만 만들어 캐싱한다 (배칭과 같은 원리, 15.3 참조)
    this.#ready ??= this.#init()
    return this.#ready
  }

  async #init () {
    await delay(500)
  }

  async query (sql) {
    await this.#ensureReady()
    return [{ sql }]
  }
}
```

호출자는 아무것도 몰라도 된다. `query()`만 부르면 된다. 대신 비용이 두 가지 생긴다. 첫째, 모든 공개 메서드에 `await this.#ensureReady()`를 빠짐없이 넣어야 하며, 메서드를 추가할 때마다 이 규칙을 기억해야 한다. 둘째, 초기화 지연이 첫 요청의 지연 시간에 그대로 얹힌다. 애플리케이션 부팅 시점에 미리 치를 수 있었던 500밀리초를, 하필 첫 사용자가 대신 지불한다. 헬스 체크가 통과한 직후 들어온 첫 트래픽이 유독 느린 현상의 흔한 원인이다.

### 해법 3: 사전 초기화 큐

세 번째는 초기화 중에 들어온 호출을 버리지도, 실패시키지도 않고 큐에 쌓아 두었다가 초기화가 끝나면 한꺼번에 흘려보내는 방식이다. 호출자는 지연 시작과 마찬가지로 아무것도 몰라도 되고, 초기화는 지연 시작과 달리 부팅 시점에 미리 시작할 수 있다. 구현이 가장 복잡한 대신 부담을 온전히 컴포넌트가 진다. 다음 절에서 상태 패턴(14장 참조)으로 이를 구현한다.

### 실무 함정

세 해법 모두에 공통으로 적용되는 함정이 있다. **초기화 실패의 캐싱**이다. 해법 2의 `#ready ??= this.#init()`는 초기화가 거부(reject)된 프로미스도 그대로 캐싱한다. 그러면 일시적인 네트워크 오류로 한 번 실패한 클라이언트가 프로세스 수명이 다할 때까지 영원히 같은 오류만 되풀이한다. 재시도를 허용하려면 실패 시 캐시를 비워야 한다.

```js
#ensureReady () {
  this.#ready ??= this.#init().catch(err => {
    this.#ready = null     // 실패한 프로미스를 캐시에서 제거해 다음 호출이 재시도하게 한다
    throw err
  })
  return this.#ready
}
```

다만 이 재시도는 무제한이어서는 안 된다. 데이터베이스가 죽어 있는 동안 초당 수천 건의 연결 시도가 쏟아지면 복구 중인 데이터베이스를 다시 쓰러뜨린다. 백오프와 서킷 브레이커(circuit breaker)를 함께 걸어야 한다(15.6 참조).

또 하나는 `top-level await`의 유혹이다. ESM에서는 모듈 최상위에서 `await db.connect()`를 쓸 수 있으므로 문제가 사라진 것처럼 보인다. 그러나 그 모듈을 임포트하는 모든 모듈의 평가가 연결이 끝날 때까지 블록된다. 임포트 그래프 어딘가에 느린 원격 호출이 숨어 있으면 부팅 시간이 예측 불가능해지고, 실패 시 스택 트레이스는 모듈 로더 내부를 가리켜 원인 파악이 어렵다. 라이브러리 모듈에서는 피하고, 애플리케이션 진입점에서 명시적으로 조립하는 편이 낫다.

## 15.2 사전 초기화 큐(pre-initialization queue)

### 문제 상황

앞 절의 해법 3을 구체화하자. 요구사항은 이렇다. 컴포넌트는 부팅 시점에 초기화를 시작한다. 초기화가 진행 중일 때 들어온 메서드 호출은 실패하지 않고 대기한다. 초기화가 끝나면 대기 중인 호출을 순서대로 실행하고, 이후 호출은 대기 없이 곧장 실행된다. 호출자 코드에는 어떤 조건 분기도 노출되지 않는다.

핵심은 "대기 중"과 "준비됨"이라는 두 상태에서 **같은 메서드가 다르게 동작해야 한다**는 것이다. 이것은 상태 패턴(State pattern, 14장 참조)이 정확히 겨냥하는 구조다. 조건문으로 매 호출마다 상태를 검사하는 대신, 상태가 바뀔 때 메서드 구현 자체를 교체한다.

### 해법

초기화 중에는 호출을 큐에 저장하는 구현을, 초기화 후에는 실제 작업을 수행하는 구현을 메서드에 바인딩한다.

```js
// initialized-db.mjs — 사전 초기화 큐를 상태 패턴으로 구현한다
import { setTimeout as delay } from 'node:timers/promises'

class InitializedDB {
  #queue = []          // 초기화 대기 중 쌓인 호출들
  #state = 'pending'   // 'pending' | 'ready' | 'failed'
  #error = null

  constructor () {
    // 대기 상태의 구현을 먼저 붙인다
    this.query = this.#queuedQuery
    this.#init()
  }

  async #init () {
    try {
      await delay(500)                  // 실제 연결/핸드셰이크
      this.#state = 'ready'
      this.query = this.#readyQuery     // 구현을 교체한다
      this.#flush()
    } catch (err) {
      this.#state = 'failed'
      this.#error = err
      this.query = this.#failedQuery
      this.#drain(err)
    }
  }

  #flush () {
    // 큐에 쌓인 순서대로 실제 구현에 위임한다
    for (const { args, resolve, reject } of this.#queue.splice(0)) {
      this.#readyQuery(...args).then(resolve, reject)
    }
  }

  #drain (err) {
    // 초기화 실패: 대기 중이던 모든 호출을 같은 오류로 거부한다
    for (const { reject } of this.#queue.splice(0)) {
      reject(err)
    }
  }

  #queuedQuery (...args) {
    return new Promise((resolve, reject) => {
      this.#queue.push({ args, resolve, reject })
    })
  }

  async #readyQuery (sql) {
    return [{ sql }]
  }

  async #failedQuery () {
    throw this.#error
  }
}
```

호출자 입장에서는 다음 한 줄이 전부다.

```js
const db = new InitializedDB()
const rows = await db.query('SELECT 1')   // 초기화 완료를 알 필요가 없다
```

메서드가 늘어나면 같은 골격이 반복되므로, `Proxy`로 일반화하면 신규 메서드에 큐잉 로직을 자동으로 적용할 수 있다.

```js
// queuing-proxy.mjs — 준비 전 호출을 자동으로 큐에 넣는 프록시
export function createQueuingProxy (target, readyPromise) {
  let ready = false
  readyPromise.then(() => { ready = true })

  return new Proxy(target, {
    get (obj, prop, receiver) {
      const value = Reflect.get(obj, prop, receiver)
      if (typeof value !== 'function' || ready) return value
      // 준비 전이면 호출을 readyPromise 이후로 미룬다
      return (...args) => readyPromise.then(() => value.apply(obj, args))
    }
  })
}
```

### 실무 함정

첫 번째 함정은 **큐의 무한 성장**이다. 초기화가 30초 걸리는 동안 초당 1,000건이 들어오면 큐에 3만 개의 프로미스와 인자가 쌓인다. 각 항목이 요청 본문을 참조하고 있으면 그대로 메모리 폭증이다. 큐에는 반드시 상한을 두고, 넘치면 즉시 거부해 호출자가 백프레셔를 인지하게 해야 한다.

```js
const MAX_QUEUE = 1000

#queuedQuery (...args) {
  if (this.#queue.length >= MAX_QUEUE) {
    // 초기화가 끝나기를 기다리는 대신 빠르게 실패시킨다
    return Promise.reject(new Error('초기화 대기 큐가 가득 찼습니다'))
  }
  return new Promise((resolve, reject) => this.#queue.push({ args, resolve, reject }))
}
```

두 번째는 **초기화 실패 처리 정책**이다. 위 구현은 대기 중인 호출을 모두 거부하고 이후 호출도 영구히 거부한다. 이는 "빠른 실패" 정책이며, 클라이언트가 죽어 있음을 명확히 알린다는 장점이 있다. 반대로 재시도 정책을 택하면 실패 후 상태를 `pending`으로 되돌리고 백오프를 두고 `#init()`을 다시 부른다. 이때 큐를 비우지 않고 유지하면 이미 대기하던 호출이 재시도의 혜택을 받지만, 호출자 입장의 지연은 재시도 횟수만큼 늘어난다. 어느 쪽이든 **호출자에게 최대 대기 시간의 상한을 보장해야** 한다. 큐에 넣을 때 데드라인을 함께 저장하고, 만료된 항목은 초기화 성공 여부와 무관하게 타임아웃으로 거부하는 것이 안전하다(15.6 참조).

세 번째는 **순서 보장에 대한 착각**이다. `#flush()`는 큐를 순서대로 순회하지만 각 호출을 `await` 없이 발사하므로, 실제 완료 순서는 하부 구현에 달려 있다. 쓰기 작업처럼 순서가 의미를 갖는 경우에는 `for await` 루프로 직렬화하거나, 애초에 순서 의존성을 API 계약에 명시해야 한다.

## 15.3 비동기 요청 배칭

### 문제 상황

같은 자원에 대한 요청이 짧은 시간에 몰릴 때, 순진한 서버는 요청 수만큼 하부 작업을 반복한다. 트래픽이 몰릴수록 데이터베이스 부하가 비례해 커지고, 결국 데이터베이스가 병목이 되어 응답 시간이 무너진다.

측정 가능한 예제를 만들자. 총 판매액을 계산하는 느린 조회를 가진 HTTP 서버다.

```js
// server-naive.mjs — 배칭도 캐싱도 없는 서버
import { createServer } from 'node:http'
import { totalSales } from './total-sales.mjs'

createServer(async (req, res) => {
  const url = new URL(req.url, 'http://localhost')
  const product = url.searchParams.get('product') ?? 'book'
  const total = await totalSales(product)   // 200ms대의 무거운 집계 쿼리
  res.writeHead(200, { 'content-type': 'application/json' })
  res.end(JSON.stringify({ product, total }))
}).listen(8000)
```

`autocannon -c 200 -d 10 'http://localhost:8000/?product=book'`으로 측정하면, 동시성 200에서 초당 처리량은 하부 조회의 처리 능력에 그대로 갇힌다. 필자의 환경(Node.js 20, 4코어)에서는 **약 950 req/s, p99 지연 약 260밀리초**가 나왔다. 요청 200개가 모두 서로 다른 조회를 발생시키기 때문이다.

### 해법

핵심 관찰은 이렇다. 어떤 순간에 `product=book`에 대한 조회가 이미 진행 중이라면, 같은 인자로 들어온 새 요청은 **새 조회를 시작할 필요 없이 진행 중인 프로미스에 편승하면 된다**. 이것이 배칭(batching)이다. 프로미스는 여러 번 `then` 할 수 있고 한 번 해결되면 모든 대기자에게 같은 값을 전달하므로, 구현은 놀랄 만큼 짧다.

```js
// total-sales-batch.mjs — 진행 중인 요청을 공유한다
import { totalSalesRaw } from './total-sales.mjs'

const runningRequests = new Map()

export function totalSales (product) {
  const running = runningRequests.get(product)
  if (running) {
    // 이미 같은 조회가 진행 중이므로 그 프로미스를 그대로 돌려준다
    return running
  }

  const promise = totalSalesRaw(product)
    .finally(() => runningRequests.delete(product))   // 완료 즉시 맵에서 제거

  runningRequests.set(product, promise)
  return promise
}
```

같은 조건으로 다시 측정하면 처리량이 **약 12,000 req/s, p99 약 22밀리초**로 뛴다. 하부 조회는 초당 5회 남짓만 실행된다. 개선의 크기는 전적으로 요청의 중복도에 달려 있다. 모든 요청이 서로 다른 `product`를 조회한다면 배칭은 아무 이득이 없고, `Map` 조작 비용만 남는다.

### 배칭과 캐싱의 차이

이 둘은 자주 혼동되지만 성질이 완전히 다르다.

- **배칭**은 *진행 중인* 요청을 공유한다. 요청이 완료되는 순간 공유 대상은 사라진다. 따라서 배칭은 **항상 최신 데이터를 반환한다**. 조회가 시작된 시점 이후의 변경만 반영되지 않을 뿐이며, 이는 동시에 도착한 요청 사이에서 구분할 수 없는 차이다.
- **캐싱**은 *완료된* 결과를 재사용한다. 결과가 유효한 동안 하부 조회를 아예 하지 않으므로 이득이 훨씬 크지만, 그 대가로 **오래된 데이터(stale data)** 를 반환할 수 있다.

즉 배칭은 정합성을 거의 희생하지 않는 공짜 최적화에 가깝고, 캐싱은 정합성과 성능을 맞바꾸는 설계 결정이다. 그래서 배칭은 기본으로 켜도 무방하지만 캐싱은 도메인별 판단이 필요하다.

### 실무 함정

가장 흔한 실수는 **키 설계**다. 위 예제는 인자가 문자열 하나라 `product`를 그대로 키로 썼다. 인자가 객체라면 직렬화가 필요한데, `JSON.stringify`는 키 순서에 따라 다른 문자열을 만들어 같은 질의를 다른 키로 취급한다. 또한 **인증된 사용자별로 결과가 다른 질의를 사용자 식별자 없이 배칭하면 다른 사용자의 데이터가 유출된다**. 배칭 키에는 결과에 영향을 주는 모든 입력이 빠짐없이 들어가야 하며, 여기에는 테넌트 ID와 권한 범위가 포함된다.

두 번째는 **오류 공유**다. 진행 중 프로미스가 거부되면 편승한 모든 호출자가 동일한 오류를 받는다. 일시적 오류에서 한 명만 실패하면 될 일을 200명이 함께 실패한다. 재시도는 배칭 계층 안쪽, 즉 `totalSalesRaw` 내부에 두어 재시도 결과가 모든 편승자에게 공유되도록 하는 편이 낫다.

세 번째는 `finally` 누락이다. 완료 후 맵에서 제거하지 않으면 배칭이 아니라 무기한 캐싱이 되며, `Map`은 계속 자라 메모리 누수가 된다. `.finally()`는 성공과 실패 모두에서 실행되므로 반드시 이 형태로 정리해야 한다.

## 15.4 비동기 요청 캐싱과 캐시 무효화

### 문제 상황

배칭으로 얻은 12,000 req/s도 결국 하부 조회의 지연에 묶여 있다. 매 순간 최소 한 개의 조회가 돌고 있어야 하기 때문이다. 초당 5회의 집계 쿼리조차 부담스러운 경우, 또는 하부 시스템이 과금되는 외부 API인 경우에는 완료된 결과를 재사용해야 한다.

### 해법

배칭 구현에서 `finally`의 삭제를 제거하고, 결과를 만료 시각과 함께 보관하면 캐시가 된다.

```js
// total-sales-cache.mjs — 진행 중 요청 공유 + 완료 결과 재사용
import { totalSalesRaw } from './total-sales.mjs'

const cache = new Map()          // key -> { value, expiresAt }
const inflight = new Map()       // key -> Promise (배칭 계층)
const TTL = 30_000

export function totalSales (product) {
  const hit = cache.get(product)
  if (hit && hit.expiresAt > Date.now()) {
    return Promise.resolve(hit.value)      // 완료된 결과 재사용
  }

  const running = inflight.get(product)
  if (running) return running              // 캐시 미스가 겹쳐도 조회는 한 번만

  const promise = totalSalesRaw(product)
    .then(value => {
      cache.set(product, { value, expiresAt: Date.now() + TTL })
      return value
    })
    .finally(() => inflight.delete(product))

  inflight.set(product, promise)
  return promise
}
```

같은 부하 조건에서 측정하면 **약 27,000 req/s, p99 약 9밀리초**로, 이제 처리량은 하부 시스템이 아니라 Node.js 프로세스 자체의 한계에 가까워진다. 하부 조회는 30초에 한 번만 실행된다. 세 단계를 정리하면 다음과 같다.

| 구현 | 처리량(req/s) | p99 지연 | 하부 조회 빈도 | 데이터 신선도 |
|---|---|---|---|---|
| 순진한 서버 | 약 950 | 260ms | 요청당 1회 | 항상 최신 |
| 배칭 | 약 12,000 | 22ms | 초당 5회 | 사실상 최신 |
| 배칭 + 캐싱 | 약 27,000 | 9ms | 30초당 1회 | 최대 30초 지연 |

수치의 절대값은 환경마다 다르지만 **자릿수의 변화**가 중요하다. 배칭은 하부 병목을 제거하고, 캐싱은 하부 호출 자체를 제거한다.

### 캐시 무효화 전략

캐시의 어려움은 채우기가 아니라 비우기에 있다.

**TTL(time to live)** 은 가장 단순하다. 정합성 요구를 시간으로 환산해 "이 데이터는 몇 초까지 낡아도 되는가"에 답하면 된다. 구현과 추론이 쉽고 어떤 데이터에도 적용된다. 대신 TTL이 만료되기 전까지는 원본이 바뀌어도 반영되지 않고, 만료 직후에는 반드시 한 번의 미스가 발생한다.

**명시적 무효화(explicit invalidation)** 는 쓰기 경로에서 해당 키를 삭제한다. 정합성은 훨씬 좋아지지만, 하나의 쓰기가 어떤 캐시 키들에 영향을 주는지 추적해야 한다. 집계 결과처럼 여러 원본에서 파생된 값은 이 매핑이 급격히 복잡해진다. 실무에서는 TTL을 안전망으로 깔고 명시적 무효화를 얹는 조합이 가장 견고하다.

**stale-while-revalidate** 는 만료된 값을 즉시 반환하면서 백그라운드로 갱신을 시작한다. 사용자는 만료 시점에도 대기하지 않고, 다음 요청부터 새 값을 받는다.

```js
// swr.mjs — 낡은 값을 즉시 주고 뒤에서 갱신한다
export function totalSales (product) {
  const hit = cache.get(product)
  const now = Date.now()

  if (hit && hit.freshUntil > now) return Promise.resolve(hit.value)

  if (hit && hit.staleUntil > now) {
    revalidate(product)                    // 대기하지 않고 갱신만 예약
    return Promise.resolve(hit.value)      // 낡았지만 즉시 응답
  }

  return revalidate(product)               // 완전히 만료됨: 기다린다
}
```

이 전략은 지연 시간을 극적으로 안정화하지만, 트래픽이 없는 키는 영원히 낡은 채로 남을 수 있고 `staleUntil` 상한을 두지 않으면 장애가 난 하부 시스템의 오래된 값을 무한히 제공하게 된다.

### 캐시 스탬피드

인기 있는 키의 TTL이 만료되는 순간, 그 키를 기다리던 수천 개의 요청이 동시에 캐시 미스를 겪고 일제히 하부 시스템으로 몰린다. 이를 **캐시 스탬피드(cache stampede)** 또는 dog-piling이라 한다. 트래픽이 많을수록 붕괴가 커지는 고약한 성질이 있다.

첫 번째 방어선은 이미 갖고 있다. 위 구현의 `inflight` 맵, 즉 배칭이다. 미스가 동시에 1,000개 발생해도 하부 조회는 한 번만 나간다. 단일 프로세스 안에서는 이것으로 충분하다.

두 번째는 **만료 시각 지터(jitter)** 다. 여러 키의 TTL을 동일하게 주면 대량 적재된 캐시가 한꺼번에 만료된다. `TTL * (0.8 + Math.random() * 0.4)` 처럼 흩뿌리면 만료가 시간축에 분산된다.

세 번째가 stale-while-revalidate다. 만료 순간에도 대기자가 생기지 않으므로 스탬피드 자체가 성립하지 않는다.

### 실무 함정

가장 큰 함정은 **다중 프로세스**다. 지금까지의 캐시는 모두 인프로세스(in-process) 캐시다. `cluster`로 워커를 8개 띄우거나(25장 참조) 컨테이너를 여러 개 굴리는 순간, 캐시는 프로세스 수만큼 쪼개진다. 적중률이 떨어지고 하부 호출은 프로세스 수에 비례해 늘어난다. 더 나쁜 것은 **무효화가 깨지는 것**이다. 한 워커에서 `cache.delete(key)`를 해도 다른 일곱 워커는 여전히 낡은 값을 제공한다. 사용자는 새로고침할 때마다 옛 값과 새 값을 번갈아 보게 된다.

해결은 Redis 같은 공유 캐시로 옮기는 것이다(25장 참조). 이때 배칭 계층은 여전히 프로세스별로 유지하는 것이 좋다. 인프로세스 배칭이 공유 캐시에 대한 중복 조회까지 흡수해 주기 때문이다. 공유 캐시로 옮기면 직렬화 비용과 네트워크 왕복이 추가되므로, "인프로세스에 아주 짧은 TTL + 공유 캐시에 긴 TTL"의 2계층 구성이 흔히 쓰인다.

두 번째 함정은 **오류 캐싱**이다. `then` 안에서만 캐시에 저장하므로 위 구현은 오류를 캐싱하지 않는다. 이는 대개 옳지만, 404처럼 결정적인 결과는 짧은 TTL로 캐싱하지 않으면 존재하지 않는 키에 대한 요청이 매번 하부로 흘러가 부하 증폭기가 된다. 이를 네거티브 캐싱이라 하며, TTL은 성공 캐시보다 훨씬 짧게 잡는다.

세 번째는 **메모리 상한 부재**다. `Map`을 캐시로 쓰면 키 종류가 늘어나는 만큼 무한히 자란다. 만료된 항목은 접근하기 전까지 지워지지 않으므로 TTL만으로는 메모리가 회수되지 않는다. LRU 상한을 가진 구현(`lru-cache` 등)을 쓰거나 주기적 청소를 명시적으로 돌려야 한다.

## 15.5 취소 가능한 비동기 함수

### 문제 상황

사용자가 검색을 입력하다 지우면 진행 중인 검색은 쓸모없어진다. HTTP 클라이언트가 연결을 끊었는데 서버는 여전히 무거운 리포트를 생성한다. 배치 작업이 종료 신호를 받았는데 남은 1만 건을 계속 처리한다. 세 경우 모두 결과가 버려질 작업에 자원을 쓰고 있다.

프로미스에는 취소가 없다. `Promise`는 한 번 시작하면 정착(settle)될 때까지 외부에서 개입할 수 없고, `await`는 중단점이 아니다. 취소는 언어가 아니라 우리가 설계로 만들어야 하는 규약이다. 취소에는 세 가지 수준이 있다.

### 수준 1: 취소 토큰을 수동으로 검사한다

가장 원시적인 방법은 취소 여부를 담은 객체를 넘기고, 함수가 중요한 지점마다 직접 확인하는 것이다.

```js
// manual-cancel.mjs — 각 단계 사이에서 취소를 검사한다
class CancelError extends Error {
  constructor () { super('취소되었습니다'); this.name = 'CancelError' }
}

async function cancelableTask (token) {
  const a = await stepOne()
  if (token.cancelled) throw new CancelError()   // 검사 1

  const b = await stepTwo(a)
  if (token.cancelled) throw new CancelError()   // 검사 2

  return stepThree(b)
}
```

동작은 하지만 검사문이 로직 사이에 흩뿌려진다. 한 곳이라도 빠뜨리면 그만큼 취소가 늦어지고, 코드 리뷰에서 발견하기 어렵다.

### 수준 2: 비동기 호출을 감싸는 헬퍼

검사를 호출 지점에 묶어 버리면 반복이 줄어든다.

```js
// cancel-wrapper.mjs — 취소 검사를 await 래퍼로 옮긴다
function createCancelWrapper () {
  let cancelRequested = false
  function cancelWrapper (fn, ...args) {
    if (cancelRequested) return Promise.reject(new CancelError())
    return fn(...args).then(res => {
      // 호출이 끝난 직후에도 다시 검사한다
      if (cancelRequested) throw new CancelError()
      return res
    })
  }
  cancelWrapper.cancel = () => { cancelRequested = true }
  return cancelWrapper
}

async function cancelableTask (cancelWrap) {
  const a = await cancelWrap(stepOne)
  const b = await cancelWrap(stepTwo, a)
  return cancelWrap(stepThree, b)
}
```

호출마다 `cancelWrap(...)`으로 감싸야 한다는 부담은 남지만, 검사 로직은 한 곳에 모였다.

### 수준 3: AbortSignal — 표준 방식

Node.js 20 이상에서는 `AbortController`와 `AbortSignal`이 취소의 사실상 표준이다(6장 참조). `fetch`, `fs/promises`, `timers/promises`, `events.once`, 스트림의 `pipeline` 등 대부분의 코어 API가 `signal` 옵션을 받아들이며, 취소 시 `AbortError`로 거부하고 **하부 자원까지 실제로 해제한다**. 수준 1·2가 결과를 버리기만 하는 것과 달리, 진행 중인 소켓이나 파일 핸들을 실제로 닫는다는 점이 결정적인 차이다.

```js
// abort-task.mjs — 표준 취소 신호를 아래로 전파한다
import { setTimeout as delay } from 'node:timers/promises'

export async function fetchReport (userId, { signal } = {}) {
  const res = await fetch(`https://api.example.com/users/${userId}`, { signal })
  const user = await res.json()

  await delay(100, undefined, { signal })   // 대기 중에도 취소가 먹는다

  signal?.throwIfAborted()                  // 취소 비대응 구간 앞에서 명시적 검사
  return buildReport(user)
}

const controller = new AbortController()
setTimeout(() => controller.abort(), 2_000)   // 2초 예산

try {
  await fetchReport(42, { signal: controller.signal })
} catch (err) {
  if (err.name === 'AbortError') console.log('취소됨')
  else throw err
}
```

`AbortSignal.timeout(ms)`는 타임아웃 전용 신호를, `AbortSignal.any([a, b])`는 여러 신호의 결합을 만들어 준다. 상위 요청의 취소와 자체 타임아웃을 함께 걸 때 이 조합이 그대로 쓰인다.

### 제너레이터로 취소 지점 자동화하기

수준 2의 래퍼조차 귀찮다면, 제너레이터(generator)로 취소를 프레임워크화할 수 있다. 함수를 제너레이터로 쓰고 `await` 대신 `yield`를 사용하면, 실행기(runner)가 매 `yield`마다 제어를 되찾으므로 **모든 중단점에서 자동으로 취소를 검사**할 수 있다.

```js
// cancelable-runner.mjs — yield 지점마다 취소를 검사하는 실행기
export function createCancelable (generatorFn) {
  return function (...args) {
    const it = generatorFn(...args)
    let cancelled = false

    const promise = (async () => {
      let prev
      while (true) {
        if (cancelled) throw new CancelError()   // 모든 중단점에서 검사
        const { value, done } = it.next(prev)
        if (done) return value
        prev = await value
      }
    })()

    promise.cancel = () => { cancelled = true }
    return promise
  }
}

const task = createCancelable(function * (userId) {
  const user = yield fetchUser(userId)      // await 대신 yield
  const orders = yield fetchOrders(user.id)
  return { user, orders }
})

const running = task(42)
running.cancel()
```

취소 지점을 하나도 빠뜨릴 수 없다는 점이 매력이지만, 대가는 크다. `async/await`를 포기해야 하고, 타입 추론이 나빠지며, 팀 전체가 이 관습을 알아야 한다. 실무에서는 `AbortSignal`을 기본으로 삼고 이 기법은 정말로 취소 지점이 촘촘해야 하는 작업 루프에만 제한적으로 쓰는 편이 낫다.

### 실무 함정

첫째, **취소는 롤백이 아니다**. 취소된 시점까지 발생한 부수 효과는 그대로 남는다. 결제 요청을 보낸 뒤 취소하면 결제는 이미 진행 중일 수 있다. 취소는 "결과를 기다리지 않겠다"는 선언일 뿐이며, 상태를 되돌리려면 보상 트랜잭션이 따로 필요하다.

둘째, **신호 전파 누락**이다. 함수가 `signal`을 받아 놓고 내부 호출에 넘기지 않으면 취소는 그 지점에서 멈춘다. 신호는 호출 그래프 전체를 타고 끝까지 내려가야 의미가 있다.

셋째, **AbortError를 실패로 집계하는 것**이다. 클라이언트가 연결을 끊어 생긴 취소를 오류율 지표나 재시도 대상으로 취급하면, 사용자가 브라우저 탭을 닫을 때마다 알람이 울리고 불필요한 재시도가 발생한다. `AbortError`는 정상 종료 경로로 분리해 처리해야 한다.

넷째, **리스너 누수**다. `signal.addEventListener('abort', ...)`를 붙였다면 작업 완료 시 반드시 제거해야 한다. 장수명 신호 하나에 요청마다 리스너가 쌓이면 조용한 메모리 누수가 된다. `{ once: true }`나 `AbortSignal`을 옵션으로 받는 API를 쓰면 대부분 자동으로 정리된다.

## 15.6 재시도·타임아웃·데드라인의 조합

### 문제 상황

재시도, 타임아웃, 서킷 브레이커는 각각 놓고 보면 모두 좋은 관행이다. 그런데 이 셋이 잘못 조합되면 장애를 막기는커녕 증폭시킨다. 실제로 대규모 장애 사후 분석에서 가장 자주 등장하는 조합이 "타임아웃이 관대하고 재시도가 공격적인 클라이언트"다.

계산해 보면 즉시 드러난다. 서비스 A가 B를, B가 C를 호출하는 3계층 구조에서 각 계층이 "타임아웃 3초, 재시도 3회"를 걸었다고 하자. 각 계층의 최악 지연은 3초 × 3회 = 9초다. 그런데 이것이 계층마다 곱해진다.

- C 호출 1회의 최악 지연: 9초
- B는 C 호출을 3회까지 재시도: 27초
- A는 B 호출을 3회까지 재시도: 81초

사용자는 3초 타임아웃을 설정했다고 믿지만 실제 최악 지연은 81초다. 게다가 요청 하나가 하부에 만드는 부하는 27배다. C가 느려지기 시작하면 재시도가 곱절로 밀려들어 C를 완전히 무너뜨린다. 이것이 **재시도 폭풍(retry storm)** 이며, 부분 저하로 끝날 사건을 전면 장애로 바꾸는 전형적인 경로다.

### 해법: 데드라인 전파

근본 해결은 각 계층이 자기 타임아웃을 독립적으로 정하지 않는 것이다. 대신 요청의 진입점에서 **절대 시각으로 된 데드라인(deadline)** 을 하나 정하고, 그 데드라인을 호출 그래프 전체에 전파한다. 각 계층은 "내게 몇 초가 필요한가"가 아니라 "남은 예산이 얼마인가"를 묻는다. 남은 예산이 없으면 하부 호출을 아예 시작하지 않는다.

```js
// deadline.mjs — 절대 시각 예산과 그로부터 파생되는 신호
export class Deadline {
  constructor (at) { this.at = at }

  static in (ms) { return new Deadline(Date.now() + ms) }

  get remaining () { return this.at - Date.now() }
  get expired () { return this.remaining <= 0 }

  // 남은 예산만큼만 유효한 AbortSignal을 만든다
  toSignal (parentSignal) {
    const timeout = AbortSignal.timeout(Math.max(0, this.remaining))
    return parentSignal ? AbortSignal.any([parentSignal, timeout]) : timeout
  }
}
```

이제 재시도는 "몇 번"이 아니라 "예산이 남아 있는 동안"으로 표현된다.

```js
// retry.mjs — 데드라인 안에서만 재시도한다
import { setTimeout as delay } from 'node:timers/promises'

export async function withRetry (fn, { deadline, maxAttempts = 3, baseMs = 100 }) {
  let lastError
  for (let attempt = 0; attempt < maxAttempts; attempt++) {
    if (deadline.expired) break            // 예산 소진: 시도하지 않는다
    try {
      return await fn(deadline.toSignal())
    } catch (err) {
      if (!isRetryable(err)) throw err     // 재시도 무의미한 오류는 즉시 전파
      lastError = err

      // 지수 백오프 + 풀 지터(full jitter)
      const backoff = Math.random() * baseMs * 2 ** attempt
      if (backoff >= deadline.remaining) break   // 대기만 하다 예산을 넘길 상황
      await delay(backoff)
    }
  }
  throw lastError ?? new Error('데드라인 초과')
}
```

호출 그래프의 각 계층은 상위에서 받은 데드라인을 그대로 넘긴다. HTTP 경계를 넘을 때는 남은 밀리초를 헤더(예: `x-request-deadline-ms`)나 gRPC의 deadline 메타데이터로 실어 보내고, 수신 측이 이를 자기 데드라인으로 복원한다. 그 결과 **전체 호출 트리의 최악 지연은 진입점에서 정한 값 하나로 상한이 잡힌다**. 재시도를 몇 계층에서 하든 총합은 예산을 넘지 못한다.

### 지수 백오프와 지터

재시도 간격을 고정하면 실패한 클라이언트들이 같은 리듬으로 동기화되어 하부 시스템을 주기적으로 두드린다. 지수 백오프(exponential backoff)는 시도마다 간격을 배로 늘려 부하를 줄이고, 지터(jitter)는 그 간격에 무작위성을 섞어 클라이언트 간 동기화를 깬다.

위 코드가 쓴 `Math.random() * base * 2 ** attempt`가 **풀 지터**이며, 0부터 상한까지 균등하게 흩뿌린다. 백오프 상한 없이 지수만 키우면 대기가 폭주하므로 실무에서는 `Math.min(cap, ...)`으로 상한(보통 수 초)을 둔다. 지터 없는 지수 백오프는 지터 있는 고정 간격보다 나쁠 수 있다는 점을 기억할 만하다.

### 재시도해도 되는 오류와 안 되는 오류

재시도의 전제는 **멱등성(idempotency)** 이다. 같은 요청을 두 번 보내도 결과가 한 번 보낸 것과 같아야 한다(29장 참조). 이 전제가 깨지면 재시도는 중복 결제, 중복 주문, 중복 이메일을 만든다.

- **재시도 가능**: 연결 거부(`ECONNREFUSED`), 연결 초기화(`ECONNRESET`), DNS 일시 실패, 503/429, 그리고 **응답을 받기 전에 끊긴 요청**. 요청이 서버에 도달하지 않았음이 확실한 경우가 가장 안전하다.
- **재시도 불가**: 400, 401, 403, 404, 422 같은 클라이언트 오류. 같은 요청을 다시 보내도 같은 답이 온다. 재시도는 지연과 부하만 늘린다.
- **판단 필요**: 500과 타임아웃. 요청이 서버에서 이미 처리되었을 수도 있다. 비멱등 연산(POST 결제 등)이라면 재시도 전에 멱등성 키(idempotency key)를 도입해 서버가 중복을 인지하고 같은 결과를 돌려주게 만들어야 한다.

```js
function isRetryable (err) {
  if (err.name === 'AbortError') return false          // 취소는 재시도 대상이 아니다
  if (['ECONNREFUSED', 'ECONNRESET', 'ETIMEDOUT', 'EAI_AGAIN'].includes(err.code)) return true
  if (err.status === 429 || (err.status >= 500 && err.status !== 501)) return true
  return false
}
```

### 실무 함정

첫째, **재시도 계층의 중복**이다. HTTP 클라이언트 라이브러리, 서비스 메시 사이드카, 애플리케이션 코드가 각각 재시도를 켜 두면 앞서 본 곱셈이 그대로 일어난다. 재시도는 호출 그래프에서 **정확히 한 계층에만** 두는 것이 원칙이며, 대개 가장 아래쪽 클라이언트가 적임이다.

둘째, **재시도 예산 부재**다. 개별 요청의 재시도 횟수를 제한해도, 하부가 완전히 죽으면 모든 요청이 최대 횟수까지 재시도해 부하가 몇 배로 뛴다. 클라이언트 전체 차원에서 "전체 요청 대비 재시도 비율 10% 이내" 같은 예산을 두거나, 연속 실패 시 회로를 여는 서킷 브레이커를 함께 걸어야 한다.

셋째, **타임아웃을 상대 시간으로 다시 계산하는 것**이다. 데드라인은 반드시 절대 시각으로 전파해야 한다. 각 계층에서 "남은 시간의 80%" 식으로 새 타임아웃을 만들면 계층이 깊어질수록 오차가 누적되고, 큐 대기 시간이 예산에서 누락된다.

넷째, **큐 대기 시간을 예산에 넣지 않는 것**이다. 요청이 이벤트 루프나 커넥션 풀에서 2초를 기다렸다면 그 2초는 이미 사용자의 예산에서 빠져나갔다. 데드라인을 절대 시각으로 두면 이 시간이 자동으로 반영되며, 이미 만료된 요청은 처리를 시작하기 전에 버려 낭비를 막을 수 있다. 부하가 걸린 시스템에서 이 한 가지 규칙만으로 회복 속도가 크게 달라진다.

## 요약

- 생성자는 비동기가 될 수 없으므로 비동기 초기화 컴포넌트는 로컬 초기화 검사, 지연 시작, 사전 초기화 큐 중 하나를 택해야 한다. 세 해법은 각각 호출자, 첫 요청, 컴포넌트 구현에 비용을 지운다.
- 사전 초기화 큐는 상태 패턴으로 메서드 구현을 교체해 구현한다. 큐 상한, 초기화 실패 시 대기 요청 처리 정책, 대기 시간 상한을 반드시 함께 설계한다.
- 배칭은 진행 중인 요청을 공유하고, 캐싱은 완료된 결과를 재사용한다. 배칭은 정합성을 거의 희생하지 않는 반면 캐싱은 신선도와 성능을 맞바꾸는 설계 결정이다.
- 예제 서버는 순진한 구현에서 배칭으로, 다시 캐싱으로 발전하며 처리량이 약 950 → 12,000 → 27,000 req/s로 자릿수 단위로 올라갔다. 개선 폭은 요청의 중복도에 비례한다.
- 캐시 무효화는 TTL, 명시적 무효화, stale-while-revalidate를 조합해 쓴다. 스탬피드는 인프로세스 배칭과 만료 지터로 막고, 인프로세스 캐시는 다중 프로세스에서 적중률과 무효화가 모두 깨지므로 공유 캐시로 옮긴다.
- 취소는 언어 기능이 아니라 규약이다. `AbortSignal`을 표준으로 삼고 호출 그래프 끝까지 전파하며, 취소가 롤백은 아니라는 점을 잊지 않는다.
- 재시도와 타임아웃은 계층마다 곱해져 지연과 부하를 폭발시킨다. 절대 시각 데드라인을 진입점에서 정해 전파하고, 지터를 곁들인 지수 백오프를 쓰며, 멱등하지 않은 연산은 멱등성 키 없이 재시도하지 않는다.

## 연습문제

1. **초기화 재시도가 가능한 큐** — 15.2의 `InitializedDB`를 확장해, 초기화 실패 시 지수 백오프로 최대 3회까지 재시도하도록 만들어라. 대기 중인 호출은 재시도 동안 큐에 유지하되, 큐에 넣을 때 기록한 데드라인이 만료된 항목은 초기화 성공 여부와 무관하게 타임아웃 오류로 거부해야 한다. 재시도가 모두 실패하면 이후 호출이 어떻게 동작해야 하는지 정하고 그 근거를 서술하라.

2. **stale-while-revalidate 캐시 계측** — 15.4의 캐시를 stale-while-revalidate로 바꾸고, 적중(fresh hit), 낡은 적중(stale hit), 미스 세 가지를 카운터로 계측하라. `autocannon`으로 60초간 부하를 준 뒤 TTL을 30초와 1초로 바꿔가며 세 카운터의 비율과 p99 지연이 어떻게 달라지는지 표로 정리하라. 갱신 중 하부 조회가 실패했을 때 낡은 값을 계속 제공할지 오류를 낼지 결정하고, 그 정책을 코드에 반영하라.

3. **데드라인 전파 체인** — HTTP 서버 세 개(A → B → C)를 만들고 C는 300밀리초 지연 후 응답하도록 하라. A의 진입점에서 500밀리초 데드라인을 만들어 `x-request-deadline-ms` 헤더로 B와 C에 전파하고, 각 계층은 남은 예산으로만 `AbortSignal`을 만들어 호출하도록 구현하라. C의 지연을 400밀리초로 늘렸을 때 전체 응답이 500밀리초 안에 실패로 끝나는지 확인하고, 데드라인 전파를 제거한 버전과 최악 지연을 비교하라.
