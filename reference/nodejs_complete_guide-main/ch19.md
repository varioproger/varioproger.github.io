# 19장. 데이터 계층

애플리케이션 코드는 다시 짤 수 있지만 데이터는 그렇지 않다. 배포를 되돌리는 데는 몇 분이면 충분한데, 잘못 실행된 `UPDATE` 한 줄을 되돌리는 데는 백업 복구와 몇 시간의 다운타임이 필요하다. 데이터 계층(data layer)이 애플리케이션의 다른 어떤 부분보다 보수적으로 다뤄져야 하는 이유가 여기에 있다.

이 장은 Node.js 애플리케이션이 상태를 보관하는 세 가지 저장소를 다룬다. 관계형 데이터베이스(relational database)는 진실의 원천(source of truth)이고, Redis는 빠르지만 잃어도 되는 것을 담으며, 객체 스토리지(object storage)는 크고 변하지 않는 것을 담는다. 각각을 어떻게 연결하고, 어떻게 스키마를 바꾸며, 어떻게 캐시를 얹는지가 이 장의 주제다.

특히 19.3의 무중단 마이그레이션은 이 장에서 가장 중요한 절이다. 실무에서 데이터 계층이 사고를 일으키는 순간은 대부분 배포와 스키마 변경이 만나는 지점이기 때문이다.

## 19.1 관계형 데이터베이스 연결: 드라이버와 커넥션 풀

### 왜 필요한가

PostgreSQL은 클라이언트 연결 하나당 서버 측에 별도의 OS 프로세스를 띄운다. 이 프로세스는 수 MB의 메모리를 점유하고, 연결을 맺을 때는 TCP 핸드셰이크에 더해 인증과 세션 초기화가 일어난다. 요청마다 연결을 새로 맺으면 쿼리 자체보다 연결 비용이 커지고, 트래픽이 몰리면 데이터베이스가 프로세스를 만들다가 먼저 쓰러진다.

커넥션 풀(connection pool)은 미리 만들어 둔 연결을 재사용하는 구조다. 애플리케이션은 풀에서 연결을 빌려 쿼리를 실행하고 반납한다. Node.js에서는 여기에 한 가지 특성이 더해진다. 단일 스레드 이벤트 루프이므로 애플리케이션 프로세스 하나가 동시에 실행할 수 있는 쿼리 수는 결국 풀 크기로 결정된다. 풀은 성능 최적화 장치인 동시에, 데이터베이스로 가는 동시성을 제한하는 백프레셔(backpressure) 장치다.

### 어떻게 동작하는가

먼저 로컬 개발용 PostgreSQL을 Docker로 띄운다.

```bash
docker run -d --name pg16 \
  -e POSTGRES_PASSWORD=devpass \
  -e POSTGRES_USER=app \
  -e POSTGRES_DB=appdb \
  -p 5432:5432 \
  postgres:16-alpine

# 현재 설정된 최대 연결 수 확인
docker exec -it pg16 psql -U app -d appdb -c 'SHOW max_connections;'
```

Node.js에서는 `pg` 드라이버의 `Pool`을 쓴다. `pg`는 순수 JavaScript 구현이라 네이티브 빌드가 필요 없고, 프로토콜 파싱까지 자바스크립트로 처리한다.

```js
// db/pool.mjs
import pg from 'pg'

const { Pool } = pg

export const pool = new Pool({
  host: process.env.PGHOST ?? '127.0.0.1',
  port: Number(process.env.PGPORT ?? 5432),
  user: process.env.PGUSER,
  password: process.env.PGPASSWORD,
  database: process.env.PGDATABASE,
  max: Number(process.env.PG_POOL_MAX ?? 10),      // 풀 최대 연결 수
  idleTimeoutMillis: 30_000,                        // 유휴 연결 정리
  connectionTimeoutMillis: 3_000,                   // 풀 고갈 시 대기 상한
  application_name: 'orders-api'                    // pg_stat_activity에서 식별용
})

// 백그라운드 연결이 끊길 때 발생한다. 핸들러가 없으면 프로세스가 죽는다.
pool.on('error', (err) => {
  console.error({ err }, 'idle client error')
})
```

`connectionTimeoutMillis`를 반드시 설정한다. 이 값이 없으면 풀이 고갈됐을 때 요청이 무한정 대기하고, 대기 중인 요청이 쌓이면서 메모리와 이벤트 루프 지연이 함께 증가한다. 상한이 있어야 빠르게 실패하고 그 실패가 지표에 드러난다(29장 참조).

### 풀 크기를 정하는 근거

풀 크기는 감으로 정하는 값이 아니라 나눗셈으로 정하는 값이다.

```text
인스턴스당 풀 크기 = (max_connections - 예약분) / (애플리케이션 인스턴스 수 × 프로세스 수)
```

`max_connections`가 100이고, 관리 도구·마이그레이션 러너·모니터링용으로 20을 예약하며, 애플리케이션 인스턴스가 4대인데 각 인스턴스가 클러스터로 워커 2개를 띄운다면 80 / 8 = 10이 된다. 여기서 흔한 실수는 오토스케일링을 계산에 넣지 않는 것이다. 최대 인스턴스 수를 기준으로 나눠야 스케일 아웃 순간에 데이터베이스가 연결을 거부하지 않는다.

풀을 크게 잡는다고 처리량이 늘지도 않는다. PostgreSQL의 처리량은 대체로 CPU 코어 수의 2~4배 정도의 동시 실행 쿼리에서 정점을 찍고 그 뒤로는 컨텍스트 스위칭과 락 경합으로 떨어진다. 인스턴스가 많아 나눗셈 결과가 2~3까지 내려간다면 그때는 PgBouncer 같은 외부 풀러를 트랜잭션 모드로 앞에 두는 편이 낫다.

### 풀 고갈의 증상

풀 고갈(pool exhaustion)은 데이터베이스 장애처럼 보이지 않는다. 데이터베이스의 CPU는 한가하고 느린 쿼리 로그도 조용한데, 애플리케이션의 응답 시간만 계단식으로 뛴다. 원인은 대개 다음 셋 중 하나다. 릴리스하지 않은 클라이언트가 새는 경우, 하나의 느린 쿼리가 모든 연결을 오래 붙잡는 경우, 그리고 외부 HTTP 호출을 트랜잭션 안에서 하는 경우다. 마지막이 특히 악질적인데, 외부 API가 3초 느려지면 그 3초 동안 연결이 묶이고 풀이 순식간에 마른다.

진단은 풀의 내부 지표를 노출하는 것에서 시작한다.

```js
// 주기적으로 계측 지표로 내보낸다
setInterval(() => {
  metrics.gauge('pg.pool.total', pool.totalCount)     // 생성된 연결
  metrics.gauge('pg.pool.idle', pool.idleCount)       // 유휴 연결
  metrics.gauge('pg.pool.waiting', pool.waitingCount) // 연결을 기다리는 요청
}, 5_000).unref()
```

`waitingCount`가 0보다 큰 상태가 지속되면 풀이 병목이다. 이 지표가 없으면 같은 증상을 두고 "DB가 느리다"는 잘못된 결론에 도달하게 된다(31장 참조).

### 파라미터화 쿼리

SQL 주입(SQL injection)을 막는 방법은 이스케이프 함수가 아니라 파라미터화 쿼리(parameterized query)다. 값과 SQL 텍스트를 서로 다른 프로토콜 필드로 보내면 값이 문법으로 해석될 여지 자체가 사라진다.

```js
// 잘못된 코드 — 문자열 연결은 어떤 이스케이프를 쓰더라도 하지 않는다
const bad = await pool.query(`SELECT * FROM users WHERE email = '${email}'`)

// 올바른 코드 — $1, $2 자리표시자
const { rows } = await pool.query(
  'SELECT id, email, created_at FROM users WHERE email = $1 AND status = $2',
  [email, 'active']
)
```

주의할 점은 자리표시자가 값에만 쓸 수 있다는 것이다. 테이블명, 컬럼명, `ORDER BY` 방향은 파라미터로 바인딩되지 않는다. 정렬 컬럼을 사용자 입력으로 받아야 한다면 허용 목록(allowlist)으로 매핑한다.

```js
const SORTABLE = { created: 'created_at', name: 'display_name' }
const column = SORTABLE[req.query.sort] ?? 'created_at'
const direction = req.query.dir === 'asc' ? 'ASC' : 'DESC'
const sql = `SELECT id FROM users ORDER BY ${column} ${direction} LIMIT $1`
```

### 트랜잭션과 release

`pool.query()`는 연결을 빌리고 반납하는 일을 알아서 처리하지만, 트랜잭션은 여러 쿼리가 같은 연결에서 실행되어야 하므로 직접 `connect()`로 클라이언트를 빌려야 한다. 이때 `release()`를 빠뜨리면 연결이 영구히 샌다.

```js
// db/tx.mjs
export async function withTransaction (fn) {
  const client = await pool.connect()
  try {
    await client.query('BEGIN')
    const result = await fn(client)
    await client.query('COMMIT')
    return result
  } catch (err) {
    // 롤백 자체가 실패해도 원래 에러를 잃지 않는다
    try { await client.query('ROLLBACK') } catch { /* 연결이 이미 끊긴 경우 */ }
    throw err
  } finally {
    client.release()  // 어떤 경로로 빠져나가든 반드시 반납된다
  }
}

// 사용
await withTransaction(async (client) => {
  const { rows } = await client.query(
    'UPDATE accounts SET balance = balance - $1 WHERE id = $2 RETURNING balance',
    [amount, fromId]
  )
  if (rows[0].balance < 0) throw new Error('INSUFFICIENT_FUNDS')
  await client.query('UPDATE accounts SET balance = balance + $1 WHERE id = $2', [amount, toId])
})
```

핵심은 `finally` 블록이다. 그리고 `fn` 안에서 실수로 `pool.query()`를 호출하면 그 쿼리는 다른 연결에서 실행되어 트랜잭션 밖에 놓인다. 이런 실수를 구조적으로 막으려면 리포지토리 함수가 항상 실행기(executor)를 첫 인자로 받게 설계한다.

### 실무 함정

트랜잭션을 열어 둔 채 외부 네트워크 호출을 하지 않는다. 결제 API 호출은 트랜잭션 커밋 이후로 미루거나, 아웃박스(outbox) 테이블에 기록해 두고 별도 워커가 처리하게 한다(23장 참조). 또한 `SET search_path`나 임시 테이블처럼 세션 상태를 바꾸는 명령을 풀 클라이언트에 실행한 뒤 되돌리지 않으면, 그 연결을 다음에 빌려 쓰는 코드가 오염된 세션을 물려받는다.

## 19.2 Knex를 이용한 스키마 마이그레이션

### 왜 필요한가

스키마는 코드와 함께 변한다. 새 기능은 새 컬럼을 요구하고, 성능 문제는 새 인덱스를 요구한다. 문제는 이 변경이 어디에 기록되는가다. 누군가 프로덕션 콘솔에서 `ALTER TABLE`을 실행하고 슬랙에 공유하는 방식은 처음 몇 번은 동작하지만, 스테이징과 프로덕션의 스키마가 미묘하게 갈라지는 순간부터 무너진다. 새로 합류한 개발자가 로컬 데이터베이스를 어떻게 만들어야 하는지 아무도 정확히 답하지 못하는 상태가 그 종착점이다.

마이그레이션(migration)은 스키마 변경을 코드 저장소에 커밋되는 순서 있는 파일로 만드는 방법이다. 스키마의 현재 모습이 아니라 스키마가 여기까지 온 과정을 버전 관리한다. 이 덕분에 "빈 데이터베이스에서 시작해 모든 마이그레이션을 순서대로 적용하면 프로덕션과 같은 스키마가 나온다"는 성질이 보장되고, CI가 매번 이를 검증할 수 있다.

Knex는 쿼리 빌더(query builder)이면서 마이그레이션 러너를 함께 제공한다. ORM처럼 객체 매핑을 강요하지 않으므로 쿼리는 SQL로 쓰고 마이그레이션 기능만 빌려 쓰는 조합도 흔하다.

### 어떻게 동작하는가

Knex는 데이터베이스 안에 `knex_migrations` 테이블을 만들고, 적용된 마이그레이션 파일명과 배치(batch) 번호를 기록한다. `migrate:latest`를 실행하면 디스크의 파일 목록과 이 테이블을 비교해 아직 적용되지 않은 것만 파일명 순서대로 실행한다. 파일명이 타임스탬프로 시작하는 이유가 여기에 있다. 여러 브랜치에서 만들어진 마이그레이션이 병합되더라도 생성 시각 순으로 결정론적인 순서가 잡힌다.

설정 파일부터 만든다.

```js
// knexfile.mjs
export default {
  client: 'pg',
  connection: {
    host: process.env.PGHOST,
    user: process.env.PGUSER,
    password: process.env.PGPASSWORD,
    database: process.env.PGDATABASE
  },
  pool: { min: 0, max: 4 },  // 마이그레이션 러너는 풀이 클 필요가 없다
  migrations: {
    directory: './migrations',
    tableName: 'knex_migrations',
    extension: 'js'
  },
  seeds: { directory: './seeds' }
}
```

마이그레이션 파일은 `npx knex migrate:make create_orders`로 생성한다. `20260901120000_create_orders.js` 같은 이름이 만들어지고, 그 안에 `up`과 `down` 두 함수를 채운다.

```js
// migrations/20260901120000_create_orders.js
export async function up (knex) {
  await knex.schema.createTable('orders', (t) => {
    t.uuid('id').primary().defaultTo(knex.raw('gen_random_uuid()'))
    t.uuid('user_id').notNullable()
    t.text('status').notNullable().defaultTo('pending')
    t.bigInteger('amount_cents').notNullable()   // 금액은 정수 최소 단위로
    t.timestamptz('created_at').notNullable().defaultTo(knex.fn.now())
    t.foreign('user_id').references('users.id').onDelete('RESTRICT')
  })

  // 사용자별 최근 주문 조회를 위한 복합 인덱스
  await knex.schema.alterTable('orders', (t) => {
    t.index(['user_id', 'created_at'], 'orders_user_created_idx')
  })
}

export async function down (knex) {
  await knex.schema.dropTableIfExists('orders')
}
```

Knex의 스키마 빌더로 표현되지 않는 것은 `knex.raw()`로 직접 쓴다. 부분 인덱스, `CHECK` 제약, 확장 설치 같은 PostgreSQL 고유 기능이 여기에 해당한다.

```js
export async function up (knex) {
  await knex.raw(`
    ALTER TABLE orders
      ADD CONSTRAINT orders_amount_positive CHECK (amount_cents > 0)
  `)
  // 활성 주문만 대상으로 하는 부분 인덱스 — 인덱스 크기가 크게 줄어든다
  await knex.raw(`
    CREATE INDEX orders_active_idx ON orders (created_at)
    WHERE status IN ('pending', 'paid')
  `)
}
```

### 트랜잭션 경계

Knex는 기본적으로 각 마이그레이션 파일을 하나의 트랜잭션으로 감싼다. PostgreSQL은 DDL이 트랜잭션 안에서 동작하므로, 파일 중간에서 실패하면 그 파일의 변경 전체가 되돌려진다. 이 성질은 대단히 유용하지만, `CREATE INDEX CONCURRENTLY`처럼 트랜잭션 안에서 실행할 수 없는 명령을 쓸 때는 꺼야 한다.

```js
// 이 마이그레이션은 트랜잭션 없이 실행된다
export const config = { transaction: false }

export async function up (knex) {
  await knex.raw('CREATE INDEX CONCURRENTLY IF NOT EXISTS orders_status_idx ON orders (status)')
}

export async function down (knex) {
  await knex.raw('DROP INDEX CONCURRENTLY IF EXISTS orders_status_idx')
}
```

트랜잭션을 끈 마이그레이션은 중간에 실패하면 부분 적용 상태로 남는다. `IF NOT EXISTS`를 붙여 재실행 가능(idempotent)하게 만드는 습관이 여기서 값을 한다.

### 시드 데이터

시드(seed)는 마이그레이션과 성격이 다르다. 마이그레이션은 한 번만 실행되는 순서 있는 변경이고, 시드는 몇 번을 실행해도 같은 결과를 내야 하는 데이터 채우기다.

```js
// seeds/01_plans.js
export async function seed (knex) {
  // 개발용 더미 데이터가 아니라 애플리케이션이 의존하는 기준 데이터
  await knex('plans')
    .insert([
      { code: 'free', monthly_cents: 0, seat_limit: 3 },
      { code: 'team', monthly_cents: 4900, seat_limit: 25 }
    ])
    .onConflict('code')
    .merge()   // UPSERT — 재실행해도 안전하다
}
```

여기서 구분해야 할 것이 있다. 요금제 코드나 권한 종류처럼 애플리케이션 로직이 존재를 전제하는 기준 데이터(reference data)는 시드가 아니라 마이그레이션에 넣어야 한다. 시드는 프로덕션에서 실행되지 않는 것이 보통이기 때문이다. 시드에는 로컬 개발과 통합 테스트에서 쓸 표본 데이터만 담는다.

### 실무 함정

이미 적용된 마이그레이션 파일은 절대 수정하지 않는다. 내 로컬에서는 아직 적용 전이라 고쳐도 문제가 없어 보이지만, 프로덕션에는 옛 버전이 이미 실행된 상태다. Knex는 파일 내용의 해시를 검사하지 않으므로 이 불일치를 알려 주지도 않는다. 잘못된 마이그레이션은 새 마이그레이션으로 고친다.

마이그레이션 실행 주체도 정해야 한다. 애플리케이션 부팅 시점에 `migrate:latest`를 실행하는 방식은 인스턴스가 여러 대일 때 동시 실행 경합을 만든다. Knex는 마이그레이션 락 테이블로 이를 막지만, 락을 잡지 못한 인스턴스가 기다리다 헬스 체크에 실패하는 문제가 남는다. 배포 파이프라인의 별도 단계나 Kubernetes의 초기화 잡으로 분리하는 편이 안전하다(33장 참조).

## 19.3 마이그레이션 롤백과 무중단 마이그레이션

### 롤백은 왜 실무에서 동작하지 않는가

모든 마이그레이션 도구는 `down` 함수를 제공하고, 모든 튜토리얼은 "문제가 생기면 롤백하면 된다"고 말한다. 그러나 프로덕션에서 `migrate:rollback`을 눌러 본 사람은 그 말이 절반만 맞다는 것을 안다.

이유는 단순하다. 스키마 변경은 되돌릴 수 있지만 데이터 변경은 되돌릴 수 없다. `DROP COLUMN phone`을 실행한 마이그레이션의 `down`은 `ADD COLUMN phone`이지만, 그렇게 되살아난 컬럼은 전부 `NULL`이다. 컬럼에 들어 있던 값은 `DROP` 순간에 사라졌다. 타입을 `text`에서 `integer`로 바꾼 마이그레이션도 마찬가지다. `down`으로 타입을 되돌려도 변환 과정에서 잘려 나간 값은 돌아오지 않는다.

두 번째 이유는 시간이다. 롤백이 의미가 있으려면 마이그레이션 직후, 아직 새 스키마에 데이터가 쌓이기 전에 실행해야 한다. 그런데 문제는 대개 배포 몇 분 뒤 트래픽이 실려서야 드러난다. 그 시점에는 이미 새 컬럼에 수만 건의 실제 데이터가 들어가 있고, 롤백은 그것을 버리는 행위가 된다.

세 번째 이유는 배포와의 순서다. 애플리케이션 코드 v2는 새 스키마를 전제로 짜여 있다. 스키마만 롤백하면 아직 살아 있는 v2 인스턴스가 없는 컬럼을 참조하며 500을 뿜는다. 스키마와 코드를 동시에 되돌리는 원자적 방법은 존재하지 않는다.

그래서 현실적인 원칙은 이렇게 정리된다. `down`은 로컬 개발과 CI에서 마이그레이션을 반복 검증하기 위해 작성하되, 프로덕션의 복구 전략으로 삼지 않는다. 프로덕션에서는 롤백이 필요 없도록 파괴적이지 않은(non-destructive) 변경만 배포한다. 롤백 대신 앞으로 굴러가는 수정 마이그레이션(roll-forward)을 준비한다.

### 확장-수축 패턴

파괴적이지 않은 변경만으로 스키마를 바꾸는 절차가 확장-수축(expand-contract) 패턴이다. 이름을 그대로 읽으면 된다. 먼저 스키마를 넓혀 옛 코드와 새 코드가 동시에 동작할 수 있는 상태를 만들고(expand), 모든 코드가 새 형태로 넘어간 뒤에 옛 구조를 걷어낸다(contract).

핵심 전제는 **모든 시점에 스키마가 이전 버전 코드와 다음 버전 코드를 동시에 만족해야 한다**는 것이다. 롤링 배포(rolling deployment) 중에는 v1 인스턴스와 v2 인스턴스가 같은 데이터베이스를 바라보며 몇 분간 공존하기 때문이다.

`users.name` 하나를 `first_name`과 `last_name` 둘로 쪼개는 변경을 예로 들어 다섯 단계를 밟아 보자. **각 단계 사이에는 반드시 배포가 한 번씩 끼어든다.** 이것이 이 패턴에서 가장 자주 오해되는 부분이다. 다섯 단계는 다섯 개의 마이그레이션이 아니라 마이그레이션과 배포가 번갈아 나오는 순서열이다.

**1단계 — 컬럼 추가 (마이그레이션 M1).** 새 컬럼을 nullable로, 기본값 없이 추가한다.

```js
// migrations/..._add_name_parts.js
export async function up (knex) {
  await knex.schema.alterTable('users', (t) => {
    t.text('first_name').nullable()   // NOT NULL 금지 — 기존 행이 위반한다
    t.text('last_name').nullable()
  })
}
```

이 시점의 애플리케이션은 아직 v1이고 새 컬럼을 전혀 모른다. 그래도 아무 문제가 없다. nullable 컬럼 추가는 기존 코드에 완전히 투명하다.

**2단계 — 양쪽 쓰기 (배포 D1).** `name`과 `first_name`/`last_name`을 모두 쓰는 코드를 배포한다. 읽기는 여전히 `name`에서 한다.

```js
// 쓰기 경로: 두 표현을 동시에 갱신한다
export async function updateName (client, userId, full) {
  const [first, ...rest] = full.trim().split(/\s+/)
  await client.query(
    `UPDATE users SET name = $1, first_name = $2, last_name = $3 WHERE id = $4`,
    [full, first, rest.join(' ') || null, userId]
  )
}

// 읽기 경로: 아직 옛 컬럼이 진실이다
export function displayName (row) {
  return row.name
}
```

이 배포가 완료된 순간부터, 새로 들어오거나 수정되는 모든 행은 두 표현이 일치한다. 남은 것은 이 배포 이전에 만들어진 옛 행들이다.

**3단계 — 백필 (마이그레이션 M2 또는 별도 잡).** 옛 행을 배치로 채운다. 한 번의 거대한 `UPDATE`는 테이블 전체에 락과 대량의 WAL을 만들고 복제 지연(replication lag)을 일으키므로, 반드시 쪼개서 돌린다.

```js
// scripts/backfill-name-parts.mjs
import { pool } from '../db/pool.mjs'
import { setTimeout as delay } from 'node:timers/promises'

const BATCH = 5_000

while (true) {
  const { rowCount } = await pool.query(`
    WITH batch AS (
      SELECT id FROM users
      WHERE first_name IS NULL AND name IS NOT NULL
      LIMIT $1
      FOR UPDATE SKIP LOCKED       -- 동시 실행과 경합하지 않는다
    )
    UPDATE users u
       SET first_name = split_part(u.name, ' ', 1),
           last_name  = NULLIF(substr(u.name, strpos(u.name, ' ') + 1), u.name)
      FROM batch WHERE u.id = batch.id
  `, [BATCH])

  if (rowCount === 0) break
  console.log(`backfilled ${rowCount}`)
  await delay(200)   // 복제 지연에 숨 쉴 틈을 준다
}
```

백필은 재실행 가능해야 한다. 위 쿼리는 `first_name IS NULL`을 조건으로 삼으므로 중간에 죽어도 다시 실행하면 이어서 진행된다.

**4단계 — 읽기 전환 (배포 D2).** 백필이 끝나고 검증 쿼리(`SELECT count(*) FROM users WHERE first_name IS NULL AND name IS NOT NULL`)가 0을 반환하면, 읽기를 새 컬럼으로 옮긴 코드를 배포한다. 쓰기는 여전히 양쪽에 한다. 이 상태를 최소 한 번의 배포 주기 동안 유지하는 것이 중요하다. 문제가 생기면 D1으로 되돌리는 것만으로 완전히 복구되기 때문이다. 이것이 진짜 롤백 안전망이다.

**5단계 — 구 컬럼 제거 (배포 D3 + 마이그레이션 M3).** 먼저 `name`에 대한 쓰기를 제거한 코드를 배포하고, 모든 인스턴스가 교체된 것을 확인한 뒤에 컬럼을 지운다.

```js
export async function up (knex) {
  await knex.schema.alterTable('users', (t) => t.dropColumn('name'))
  await knex.schema.alterTable('users', (t) => t.text('first_name').notNullable().alter())
}
export async function down () {
  throw new Error('되돌릴 수 없음 — 수정 마이그레이션을 앞으로 적용할 것')
}
```

이 마지막 단계는 앞의 네 단계와 성격이 다르다. 유일하게 파괴적이고, 유일하게 되돌릴 수 없다. 그래서 가능한 한 늦게, 그리고 별도의 배포에서 실행한다. 몇 주 뒤에 해도 늦지 않다.

### 큰 테이블의 인덱스와 잠금

무중단을 깨는 또 하나의 원인은 잠금(lock)이다. PostgreSQL에서 평범한 `CREATE INDEX`는 대상 테이블에 `SHARE` 락을 잡는다. 읽기는 가능하지만 `INSERT`/`UPDATE`/`DELETE`가 전부 막힌다. 1억 행 테이블에서 인덱스를 만드는 데 20분이 걸린다면 20분 동안 쓰기가 멈춘다. 배포는 무사히 끝났는데 서비스는 죽어 있는 상태다.

```sql
-- 쓰기를 막지 않는다. 대신 테이블을 두 번 스캔하므로 더 오래 걸린다.
CREATE INDEX CONCURRENTLY orders_user_created_idx ON orders (user_id, created_at);
```

`CONCURRENTLY`에는 대가가 있다. 트랜잭션 블록 안에서 실행할 수 없고(그래서 19.2의 `transaction: false`가 필요하다), 실패하면 `INVALID` 상태의 무효 인덱스가 남는다. 무효 인덱스는 플래너가 쓰지 않으면서 쓰기 비용만 발생시키므로 반드시 정리해야 한다.

```sql
-- 무효 인덱스 탐지
SELECT c.relname FROM pg_index i
JOIN pg_class c ON c.oid = i.indexrelid
WHERE NOT i.indisvalid;

DROP INDEX CONCURRENTLY orders_user_created_idx;  -- 정리 후 재시도
```

같은 원리가 다른 DDL에도 적용된다. `ALTER TABLE ... ADD COLUMN`에 non-null 기본값을 주는 것은 PostgreSQL 11부터 테이블 재작성 없이 즉시 끝나지만, 타입 변경은 여전히 전체 재작성과 `ACCESS EXCLUSIVE` 락을 유발한다. 제약 추가는 `NOT VALID`로 먼저 붙이고 나중에 `VALIDATE CONSTRAINT`로 검증하면 긴 락을 피할 수 있다.

```sql
ALTER TABLE orders ADD CONSTRAINT orders_amount_positive
  CHECK (amount_cents > 0) NOT VALID;        -- 즉시 완료, 신규 행만 검사
ALTER TABLE orders VALIDATE CONSTRAINT orders_amount_positive;  -- 약한 락으로 기존 행 검사
```

### 실무 함정

DDL이 락을 잡으려고 기다리는 동안 그 뒤에 도착한 모든 쿼리가 함께 줄을 선다는 점을 놓치기 쉽다. 긴 `SELECT` 하나가 실행 중이면 `ALTER TABLE`이 대기하고, 그 대기가 후속 `SELECT`까지 막아 순식간에 전면 장애가 된다. 마이그레이션 세션에 `SET lock_timeout = '3s'`를 걸어 두면 락을 못 잡을 때 조용히 대기하는 대신 빠르게 실패한다. 실패는 재시도하면 되지만 전면 장애는 그렇지 않다.

## 19.4 Redis 기본기: 문자열, 리스트, 셋, 해시, 정렬된 셋

### 왜 필요한가

Redis를 "빠른 키-값 저장소"로만 이해하면 절반만 쓰게 된다. Redis의 진짜 가치는 자료구조 서버(data structure server)라는 데 있다. 리스트에 밀어 넣고 빼는 연산, 셋의 합집합, 정렬된 셋의 범위 조회 같은 것이 서버 안에서 원자적으로 실행된다. 애플리케이션이 데이터를 내려받아 가공하고 다시 올리는 왕복이 사라지고, 그 왕복 사이에 끼어들던 경쟁 상태(race condition)도 함께 사라진다.

또한 Redis는 단일 스레드로 명령을 처리한다. 이 제약이 오히려 보증이 된다. 하나의 명령은 언제나 원자적이며, 락 없이도 카운터 증가나 큐 팝이 안전하다. 반대로 오래 걸리는 명령 하나가 모든 클라이언트를 막는다는 뜻이기도 하다(뒤에서 다룰 `KEYS`가 그 대표다).

Node.js에서는 `ioredis`나 `node-redis`를 쓴다. 여기서는 클러스터 지원과 파이프라이닝 API가 편한 `ioredis`를 기준으로 한다.

```bash
docker run -d --name redis7 -p 6379:6379 redis:7-alpine \
  redis-server --maxmemory 512mb --maxmemory-policy allkeys-lru
```

```js
// cache/redis.mjs
import Redis from 'ioredis'

export const redis = new Redis({
  host: process.env.REDIS_HOST ?? '127.0.0.1',
  port: 6379,
  maxRetriesPerRequest: 2,     // 무한 재시도로 요청이 매달리지 않게
  enableReadyCheck: true,
  keyPrefix: 'app:'            // 네임스페이스 분리
})
```

### 다섯 가지 자료구조와 그 용도

**문자열(string)은 캐시다.** 가장 단순하고 가장 많이 쓰인다. 직렬화한 JSON을 TTL과 함께 넣는다.

```js
// SET key value EX seconds — 값과 만료를 한 번에 원자적으로 설정
await redis.set(`user:${id}`, JSON.stringify(user), 'EX', 300)
const raw = await redis.get(`user:${id}`)

// NX 옵션은 분산 락의 기초가 된다 (24장 참조)
const acquired = await redis.set('lock:report', token, 'PX', 10_000, 'NX')
```

`SET`에 `EX`를 함께 주는 것이 중요하다. `SET` 후 별도로 `EXPIRE`를 호출하면 그 사이에 프로세스가 죽었을 때 만료 없는 키가 영원히 남는다.

**리스트(list)는 큐다.** `LPUSH`로 넣고 `BRPOP`으로 블로킹 팝을 하면 단순한 작업 큐가 된다.

```js
await redis.lpush('queue:emails', JSON.stringify({ to, template }))

// 별도 커넥션에서 소비한다 — 블로킹 명령은 그 연결을 점유한다
const worker = redis.duplicate()
while (running) {
  const res = await worker.brpop('queue:emails', 5)  // 5초 타임아웃
  if (!res) continue
  await sendEmail(JSON.parse(res[1]))
}
```

여기에는 중요한 한계가 있다. `BRPOP`으로 꺼낸 메시지는 처리 중 프로세스가 죽으면 사라진다. 유실이 허용되지 않는다면 `LMOVE`로 처리 중 리스트에 옮겨 두는 신뢰 큐(reliable queue) 패턴을 쓰거나, 아예 Redis Streams나 전용 브로커를 쓴다(23장 참조).

**셋(set)은 중복 제거다.** 멤버십 검사가 O(1)이다.

```js
// 오늘 이 글을 본 사용자 — 중복 조회는 자동으로 무시된다
await redis.sadd(`post:${postId}:viewers:${today}`, userId)
const uniqueViews = await redis.scard(`post:${postId}:viewers:${today}`)
await redis.expire(`post:${postId}:viewers:${today}`, 86_400 * 7)
```

정확한 수가 아니라 대략의 규모만 필요하다면 HyperLogLog(`PFADD`/`PFCOUNT`)가 낫다. 오차 0.81%에 키 하나당 12KB 고정이므로 수억 개의 원소도 감당한다.

**해시(hash)는 객체다.** 필드 단위로 읽고 쓸 수 있어, 객체 전체를 역직렬화하지 않고 한 필드만 갱신할 수 있다.

```js
await redis.hset(`session:${sid}`, { userId, role: 'admin', lastSeen: Date.now() })
const role = await redis.hget(`session:${sid}`, 'role')   // 한 필드만
await redis.hincrby(`stats:${day}`, 'signups', 1)          // 원자적 증가
```

**정렬된 셋(sorted set)이 가장 활용도가 높다.** 각 멤버에 점수(score)를 붙여 정렬된 상태로 유지한다. 세 가지 대표 용도가 있다.

리더보드는 교과서적인 예다.

```js
await redis.zincrby('leaderboard:weekly', points, userId)
const top10 = await redis.zrevrange('leaderboard:weekly', 0, 9, 'WITHSCORES')
const myRank = await redis.zrevrank('leaderboard:weekly', userId)
```

슬라이딩 윈도 레이트 리미터는 점수를 타임스탬프로 쓴다. 고정 윈도와 달리 경계에서 두 배 트래픽이 통과하는 문제가 없다.

```js
// 60초 동안 100회 제한
const now = Date.now()
const key = `rl:${userId}`
const [, , count] = await redis.multi()
  .zremrangebyscore(key, 0, now - 60_000)   // 윈도 밖 기록 제거
  .zadd(key, now, `${now}-${Math.random()}`)
  .zcard(key)
  .expire(key, 60)
  .exec()
  .then((r) => r.map(([, v]) => v))
if (count > 100) throw new Error('RATE_LIMITED')
```

지연 큐는 점수를 실행 예정 시각으로 쓴다. `ZRANGEBYSCORE key 0 <now>`로 지금 실행할 것만 꺼내면 된다.

### TTL, SCAN, 파이프라이닝

Redis의 만료는 게으르다(lazy). 키는 만료 시각이 지나도 즉시 사라지지 않고, 접근되는 순간이나 백그라운드 샘플링에서 정리된다. 그래서 `used_memory`는 논리적으로 만료된 키를 포함할 수 있다. 캐시 용도라면 `maxmemory`와 `allkeys-lru` 정책을 함께 설정해, 메모리가 차면 Redis가 알아서 오래된 키를 밀어내게 한다. 이 설정이 없으면 메모리 한계에서 쓰기가 거부되며 캐시가 아니라 장애 원인이 된다.

키를 훑어야 할 때 `KEYS`는 프로덕션에서 절대 쓰지 않는다. 전체 키스페이스를 한 번에 스캔하는 O(N) 명령이고, 단일 스레드를 그동안 완전히 점유한다. 키가 천만 개면 수 초 동안 Redis 전체가 멈춘다. 대신 커서 기반의 `SCAN`을 쓴다.

```js
// 커서 방식 — 한 번에 조금씩, 다른 명령을 막지 않는다
const stream = redis.scanStream({ match: 'app:session:*', count: 500 })
for await (const keys of stream) {
  if (keys.length) await redis.unlink(...keys)   // DEL 대신 UNLINK: 해제를 백그라운드로
}
```

`SCAN`은 약한 보증만 제공한다. 스캔 시작부터 끝까지 존재한 키는 반드시 반환되지만, 중간에 생성된 키는 나올 수도 안 나올 수도 있고 같은 키가 두 번 나올 수도 있다. 이 성질을 견디는 로직으로 짜야 한다.

마지막으로 파이프라이닝(pipelining)이다. Redis 명령 하나하나는 마이크로초 단위지만 왕복 시간(RTT)은 그보다 훨씬 크다. 100개의 명령을 순차로 보내면 100번의 왕복이 든다. 파이프라인은 이를 한 번의 왕복으로 묶는다.

```js
const pipeline = redis.pipeline()
for (const id of ids) pipeline.hgetall(`user:${id}`)
const results = await pipeline.exec()   // [[err, value], ...]
```

`multi()`도 파이프라인처럼 동작하지만 `MULTI/EXEC` 트랜잭션 의미(중간에 다른 클라이언트 명령이 끼어들지 않음)를 추가로 보장한다. 원자성이 필요 없으면 `pipeline()`이 더 가볍다.

### 실무 함정

파이프라인의 결과 배열에서 개별 에러를 확인하지 않는 코드가 많다. `exec()`는 명령 하나가 실패해도 거부되지 않으며, 각 항목의 첫 요소에 에러가 담긴다. 그리고 `ioredis`의 `keyPrefix`는 클라이언트 측에서 붙는 것이라, `SCAN`의 `match` 패턴에는 프리픽스가 자동으로 적용되지 않는다는 점도 자주 걸린다.

## 19.5 캐싱 전략: 인프로세스 캐시의 한계와 Memcached/Redis

### 왜 필요한가

가장 빠른 캐시는 프로세스 안에 있는 `Map`이다. 네트워크 왕복이 없고 직렬화도 없다. 15장에서 다룬 배칭·캐싱 레시피도 이 형태에서 출발했다(15장 참조). 문제는 이 캐시가 인스턴스를 한 대 넘어가는 순간부터 세 가지 방식으로 무너진다는 것이다.

**첫째, 인스턴스마다 내용이 다르다.** 인스턴스가 네 대면 같은 사용자가 요청마다 다른 캐시를 만난다. 첫 히트율이 낮아지는 것은 부차적인 문제고, 진짜 문제는 일관성이다. 사용자가 프로필을 수정하면 요청을 받은 인스턴스의 캐시만 갱신된다. 나머지 세 대는 옛 값을 TTL이 끝날 때까지 계속 내보낸다. "새로고침하면 예전 이름이 나왔다 새 이름이 나왔다 한다"는 버그 제보가 여기서 나온다.

**둘째, 메모리 압박이다.** 상한 없는 `Map`은 캐시가 아니라 메모리 누수다. 힙이 커지면 V8의 마크-스윕 GC가 길어지고, 이벤트 루프가 수백 밀리초씩 멈춘다. 캐시로 지연 시간을 줄이려다 GC로 지연 시간을 늘리는 역전이 일어난다.

**셋째, 재시작 시 소실이다.** 배포는 매일 일어난다. 배포 직후 모든 인스턴스의 캐시가 비어 있는 상태에서 트래픽이 들어오면 데이터베이스로 가는 요청이 순간적으로 몇 배가 된다. 이 콜드 스타트(cold start) 부하가 데이터베이스를 넘어뜨리면 배포할 때마다 장애가 나는 시스템이 된다.

### 경계 있는 LRU 캐시

인프로세스 캐시를 쓰더라도 최소한 크기 상한은 있어야 한다. LRU(Least Recently Used)는 가장 오래 참조되지 않은 항목부터 밀어내는 정책이다. JavaScript의 `Map`은 삽입 순서를 유지하므로 이것만으로 LRU를 구현할 수 있다.

```js
// cache/lru.mjs — Map의 삽입 순서를 이용한 최소 LRU
export class LruCache {
  #map = new Map()

  constructor (max = 1000, ttlMs = 60_000) {
    this.max = max
    this.ttlMs = ttlMs
  }

  get (key) {
    const entry = this.#map.get(key)
    if (!entry) return undefined
    if (entry.expires < Date.now()) {
      this.#map.delete(key)
      return undefined
    }
    // 재삽입으로 "최근 사용" 위치로 옮긴다
    this.#map.delete(key)
    this.#map.set(key, entry)
    return entry.value
  }

  set (key, value) {
    if (this.#map.has(key)) this.#map.delete(key)
    this.#map.set(key, { value, expires: Date.now() + this.ttlMs })
    if (this.#map.size > this.max) {
      // 첫 번째 키가 가장 오래 참조되지 않은 항목이다
      this.#map.delete(this.#map.keys().next().value)
    }
  }
}
```

실무에서는 `lru-cache` 패키지를 쓰는 편이 낫다. 항목 개수뿐 아니라 바이트 크기 기준 상한, 백그라운드 갱신(stale-while-revalidate), 히트/미스 통계를 제공한다. 어느 쪽이든 상한을 명시적으로 정하는 것이 핵심이다. "얼마나 잡아야 하나"의 기준은 힙 사용량이다. `--max-old-space-size`의 30%를 넘지 않게 잡고, 실측으로 조정한다.

### 외부 캐시로의 이행

앞의 세 가지 한계를 모두 해결하는 방법은 캐시를 프로세스 밖으로 빼는 것이다. Redis와 Memcached가 표준적인 선택이다. Memcached는 단순한 키-값 캐시에 특화되어 있고 멀티스레드로 동작해 대용량 단일 노드에서 유리하다. Redis는 자료구조와 지속성(persistence), 복제, Lua 스크립팅을 제공한다. 캐시 외의 용도(큐, 레이트 리미터, 락)를 같은 인프라에서 함께 쓸 생각이라면 Redis가 사실상 정답이다.

가장 흔한 패턴은 캐시 어사이드(cache-aside)다.

```js
// cache/aside.mjs
const inflight = new Map()   // 캐시 스탬피드 방지

export async function cached (key, ttlSec, loader) {
  const hit = await redis.get(key)
  if (hit !== null) return JSON.parse(hit)

  // 같은 키에 대한 동시 미스를 하나의 로더 호출로 합친다
  if (inflight.has(key)) return inflight.get(key)

  const promise = (async () => {
    try {
      const value = await loader()
      // null도 캐시한다 — 존재하지 않는 키에 대한 반복 조회를 막는다
      await redis.set(key, JSON.stringify(value), 'EX', ttlSec)
      return value
    } finally {
      inflight.delete(key)
    }
  })()

  inflight.set(key, promise)
  return promise
}
```

`inflight` 맵이 하는 일이 캐시 스탬피드(cache stampede) 방지다. 인기 있는 키의 TTL이 만료되는 순간 동시 요청 500개가 모두 미스를 겪고 500번의 데이터베이스 조회가 동시에 발생하는 현상이다. 프로세스 내 병합만으로도 부하가 인스턴스 수만큼으로 줄고, 더 엄격하게 막으려면 Redis의 `SET NX` 락으로 한 인스턴스만 로더를 실행하게 한다.

### 두 계층 캐시

L1(인프로세스)과 L2(Redis)를 겹쳐 쓰면 각각의 장점을 취할 수 있다. L1은 나노초 단위 접근과 네트워크 절약을, L2는 인스턴스 간 공유와 재시작 내성을 담당한다.

```js
// cache/tiered.mjs
const l1 = new LruCache(5_000, 10_000)   // L1의 TTL은 짧게 — 불일치 창을 좁힌다

export async function getUser (id) {
  const key = `user:${id}`
  const local = l1.get(key)
  if (local !== undefined) return local

  const remote = await redis.get(key)
  if (remote !== null) {
    const parsed = JSON.parse(remote)
    l1.set(key, parsed)
    return parsed
  }

  const fresh = await loadUserFromDb(id)
  await redis.set(key, JSON.stringify(fresh), 'EX', 300)
  l1.set(key, fresh)
  return fresh
}
```

L1의 TTL을 짧게(수 초에서 수십 초) 잡는 것이 설계의 요점이다. L1은 인스턴스별로 갈라지므로 TTL이 곧 최대 불일치 시간이 된다. 짧은 TTL로도 초당 수천 건이 들어오는 핫 키의 부하는 대부분 흡수된다.

### 무효화 전파

L2를 지워도 각 인스턴스의 L1은 남는다. 이를 해결하려면 무효화를 브로드캐스트해야 한다. Redis의 Pub/Sub이 가장 간단한 수단이다.

```js
// 갱신하는 쪽
export async function invalidate (key) {
  await redis.del(key)
  await redis.publish('cache:invalidate', key)
}

// 모든 인스턴스가 구독한다 (구독 전용 연결이 필요하다)
const sub = redis.duplicate()
await sub.subscribe('cache:invalidate')
sub.on('message', (_channel, key) => l1.delete(key))
```

Pub/Sub은 전달을 보장하지 않는다는 점을 기억해야 한다. 메시지 발행 순간 연결이 끊겨 있던 인스턴스는 무효화를 놓친다. 그래서 Pub/Sub 무효화는 L1의 짧은 TTL과 함께 쓴다. 브로드캐스트는 보통의 경우를 빠르게 만들고, TTL이 최악의 경우를 유한하게 만든다. 이 조합이 실무에서 가장 견고하다.

### 실무 함정

캐시 키에 버전 접두사를 넣지 않으면 값의 스키마가 바뀌는 배포에서 문제가 생긴다. 새 코드가 옛 형태의 JSON을 읽고 `undefined`를 참조하며 터진다. `user:v2:${id}`처럼 키에 버전을 넣으면 배포가 곧 무효화가 된다. 또한 캐시 실패가 요청 실패가 되어서는 안 된다. Redis가 죽었을 때 `get`이 던지는 에러를 잡아 미스로 처리하고 원본을 조회하도록 감싸 둔다.

## 19.6 객체 스토리지와 대용량 파일

### 왜 파일을 데이터베이스에 넣지 않는가

사용자가 올린 이미지를 `bytea` 컬럼에 넣는 선택은 처음에는 매력적으로 보인다. 트랜잭션 하나로 메타데이터와 파일이 함께 저장되고, 백업도 하나면 된다. 그러나 이 선택은 몇 가지 비용을 조용히 누적시킨다.

먼저 데이터베이스의 작업 집합(working set)이 오염된다. PostgreSQL의 공유 버퍼는 자주 쓰이는 인덱스와 행을 메모리에 두려고 하는데, 10MB짜리 이미지 하나를 읽으면 그만큼의 유용한 페이지가 밀려난다. 파일은 한 번 읽고 마는 데이터인데 캐시를 차지한다. 다음으로 백업과 복제가 무거워진다. 파일이 늘어나는 만큼 덤프 시간과 복구 시간이 선형으로 늘고, 스키마 마이그레이션의 위험도 함께 커진다. 마지막으로 확장 경로가 없다. 데이터베이스는 수직 확장이 기본이고 스토리지 비용이 가장 비싼 계층이다.

객체 스토리지(object storage)는 정확히 이 문제를 위해 설계됐다. 파일은 S3 호환 스토리지에 넣고, 데이터베이스에는 키와 메타데이터만 저장한다. 진실의 원천은 여전히 데이터베이스이되, 바이트는 값싸고 무한히 늘어나는 곳에 둔다.

```sql
CREATE TABLE attachments (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  owner_id    uuid NOT NULL,
  bucket      text NOT NULL,
  object_key  text NOT NULL,        -- 스토리지의 키만 보관한다
  content_type text NOT NULL,
  size_bytes  bigint NOT NULL,
  checksum    text,
  created_at  timestamptz NOT NULL DEFAULT now()
);
```

로컬 개발은 MinIO로 한다. S3 API 호환이므로 같은 SDK 코드가 그대로 동작한다.

```bash
docker run -d --name minio -p 9000:9000 -p 9001:9001 \
  -e MINIO_ROOT_USER=minioadmin -e MINIO_ROOT_PASSWORD=minioadmin \
  minio/minio server /data --console-address ':9001'
```

### 스트리밍 업로드

파일을 버퍼로 전부 메모리에 올린 뒤 업로드하면 100MB 파일 열 개가 동시에 들어올 때 1GB의 힙이 필요하다. Node.js의 스트림을 그대로 스토리지로 흘려보내야 한다. AWS SDK v3의 `@aws-sdk/lib-storage`가 제공하는 `Upload`는 스트림을 받아 내부적으로 멀티파트로 쪼개 보낸다.

```js
// storage/client.mjs
import { S3Client } from '@aws-sdk/client-s3'

export const s3 = new S3Client({
  region: process.env.S3_REGION ?? 'us-east-1',
  endpoint: process.env.S3_ENDPOINT,      // MinIO 등 S3 호환 스토리지
  forcePathStyle: true,                    // MinIO는 경로 스타일이 필요하다
  credentials: {
    accessKeyId: process.env.S3_KEY,
    secretAccessKey: process.env.S3_SECRET
  }
})
```

```js
// storage/upload.mjs
import { Upload } from '@aws-sdk/lib-storage'
import { s3 } from './client.mjs'

export async function uploadStream ({ bucket, key, body, contentType }) {
  const upload = new Upload({
    client: s3,
    params: { Bucket: bucket, Key: key, Body: body, ContentType: contentType },
    queueSize: 4,                 // 동시 파트 업로드 수
    partSize: 8 * 1024 * 1024,    // 파트 크기 8MB (최소 5MB)
    leavePartsOnError: false      // 실패 시 미완성 파트를 정리한다
  })

  upload.on('httpUploadProgress', (p) => {
    // 진행률을 클라이언트에 알릴 때 쓴다
  })

  return upload.done()
}
```

HTTP 요청 본문을 그대로 넘기면 디스크에도 메모리에도 전체를 담지 않는다.

```js
// Fastify 예시 — multipart 파트의 파일 스트림을 그대로 전달한다
app.post('/attachments', async (req, reply) => {
  const part = await req.file()
  const key = `u/${req.user.id}/${crypto.randomUUID()}`
  await uploadStream({
    bucket: 'uploads', key,
    body: part.file,                        // Readable 스트림
    contentType: part.mimetype
  })
  await pool.query(
    'INSERT INTO attachments (owner_id, bucket, object_key, content_type, size_bytes) VALUES ($1,$2,$3,$4,$5)',
    [req.user.id, 'uploads', key, part.mimetype, part.file.bytesRead]
  )
  return reply.code(201).send({ key })
})
```

### 프리사인드 URL

스트리밍 업로드도 여전히 애플리케이션 서버를 거친다. 100MB 업로드가 진행되는 동안 그 요청은 서버의 소켓과 대역폭, 그리고 이벤트 루프의 관심을 붙잡는다. 업로드가 서비스의 주된 트래픽이라면 서버를 아예 경로에서 빼는 편이 낫다.

프리사인드 URL(presigned URL)은 서버가 자신의 자격 증명으로 서명한, 시간 제한이 있는 URL이다. 클라이언트는 이 URL로 스토리지에 직접 `PUT`한다. 서버는 서명 발급이라는 수 밀리초짜리 작업만 한다.

```js
// storage/presign.mjs
import { PutObjectCommand, GetObjectCommand } from '@aws-sdk/client-s3'
import { getSignedUrl } from '@aws-sdk/s3-request-presigner'

export async function presignUpload ({ userId, contentType, sizeBytes }) {
  // 서명 전에 서버가 검증한다 — 클라이언트가 정하게 두지 않는다
  if (!['image/jpeg', 'image/png', 'application/pdf'].includes(contentType)) {
    throw new Error('UNSUPPORTED_TYPE')
  }
  if (sizeBytes > 20 * 1024 * 1024) throw new Error('TOO_LARGE')

  const key = `u/${userId}/${crypto.randomUUID()}`
  const url = await getSignedUrl(
    s3,
    new PutObjectCommand({
      Bucket: 'uploads',
      Key: key,
      ContentType: contentType,
      ContentLength: sizeBytes      // 서명에 포함되므로 클라이언트가 어길 수 없다
    }),
    { expiresIn: 300 }              // 5분
  )
  return { url, key }
}

// 다운로드도 같은 방식으로 — 버킷을 공개하지 않고도 배포할 수 있다
export function presignDownload (key) {
  return getSignedUrl(s3, new GetObjectCommand({ Bucket: 'uploads', Key: key }), { expiresIn: 60 })
}
```

여기서 반드시 지켜야 할 것은 서명 파라미터를 서버가 결정한다는 원칙이다. 키를 클라이언트가 보내는 파일명으로 만들면 다른 사용자의 객체를 덮어쓰는 경로 조작이 가능해진다. 키는 서버가 UUID로 만들고, 소유자 식별자를 접두사에 넣는다(34장 참조).

프리사인드 업로드에는 순서 문제가 따라온다. 클라이언트가 업로드를 마쳤는지 서버가 알 수 없다는 것이다. 두 가지 해법이 있다. 업로드 완료 후 클라이언트가 확인 API를 호출하게 하고 서버가 `HeadObject`로 실제 존재와 크기를 검증하는 방식, 그리고 스토리지의 이벤트 알림을 큐로 받아 처리하는 방식이다. 어느 쪽이든 데이터베이스 행을 `pending` 상태로 먼저 만들고 확인 시점에 `ready`로 바꾸는 2단계 모델이 된다. 확인되지 않은 채 남은 `pending` 행과 고아 객체는 주기적인 정리 잡이 지운다.

### 멀티파트 업로드

S3의 단일 `PUT`은 5GB가 상한이고, 대용량 파일에서는 전송 중 한 번의 네트워크 오류가 전체 재전송을 의미한다. 멀티파트 업로드(multipart upload)는 파일을 파트로 쪼개 각각 독립적으로 올리고 마지막에 합친다. 파트 단위 재시도가 가능하고 병렬 전송으로 처리량도 올라간다.

`lib-storage`의 `Upload`는 이 과정을 자동화하지만, 브라우저가 파트를 직접 올리게 하려면 각 파트에 프리사인드 URL을 발급하는 흐름을 직접 구성해야 한다.

```js
import { CreateMultipartUploadCommand, UploadPartCommand,
         CompleteMultipartUploadCommand } from '@aws-sdk/client-s3'

// 1) 업로드 시작 — uploadId를 받는다
const { UploadId } = await s3.send(new CreateMultipartUploadCommand({
  Bucket: 'uploads', Key: key, ContentType: contentType
}))

// 2) 파트별 프리사인드 URL 발급 (클라이언트가 병렬로 PUT)
const partUrls = await Promise.all(
  Array.from({ length: partCount }, (_, i) =>
    getSignedUrl(s3, new UploadPartCommand({
      Bucket: 'uploads', Key: key, UploadId, PartNumber: i + 1
    }), { expiresIn: 3600 }))
)

// 3) 클라이언트가 각 응답의 ETag를 모아 보내면 완료 처리
await s3.send(new CompleteMultipartUploadCommand({
  Bucket: 'uploads', Key: key, UploadId,
  MultipartUpload: { Parts: parts.map((p, i) => ({ ETag: p.etag, PartNumber: i + 1 })) }
}))
```

### 실무 함정

가장 비싸게 치르는 실수는 미완성 멀티파트 업로드를 방치하는 것이다. 완료되지도 취소되지도 않은 파트는 목록에 보이지 않으면서 스토리지 요금은 그대로 청구된다. 버킷에 수명 주기 규칙(lifecycle rule)을 걸어 7일 지난 미완성 업로드를 자동으로 중단시킨다. 같은 규칙으로 `tmp/` 접두사의 객체를 만료시키면 고아 객체 문제도 함께 정리된다.

그리고 콘텐츠 타입을 클라이언트가 보낸 값 그대로 저장한 뒤, 다운로드 시 그대로 내보내지 않는다. `text/html`로 올린 파일이 같은 도메인에서 서빙되면 저장형 XSS가 된다. 다운로드 응답에 `Content-Disposition: attachment`를 강제하거나, 사용자 콘텐츠를 별도 도메인에서 서빙한다.

## 요약

- 커넥션 풀의 크기는 `max_connections`를 최대 인스턴스 수로 나눈 값에서 출발한다. 크게 잡는다고 처리량이 늘지 않으며, `waitingCount`가 0보다 큰 상태가 풀 고갈의 신호다.
- 트랜잭션은 `pool.connect()`로 빌린 클라이언트에서 실행하고 `finally`에서 반드시 `release()`한다. 트랜잭션 안에서 외부 네트워크 호출을 하지 않는다.
- 마이그레이션은 코드와 함께 커밋되는 순서 있는 파일이다. 이미 적용된 파일은 수정하지 않고, 실행은 배포 파이프라인의 별도 단계로 분리한다.
- 프로덕션에서 롤백은 신뢰할 수 없다. 데이터 손실은 되돌아오지 않으므로, 확장-수축 패턴(컬럼 추가 → 양쪽 쓰기 → 백필 → 읽기 전환 → 구 컬럼 제거)으로 각 단계 사이에 배포를 끼워 넣는다.
- 큰 테이블의 인덱스는 `CREATE INDEX CONCURRENTLY`로 만들고, DDL 세션에는 `lock_timeout`을 걸어 락 대기가 전면 장애로 번지지 않게 한다.
- Redis는 자료구조 서버다. 문자열은 캐시, 리스트는 큐, 셋은 중복 제거, 해시는 객체, 정렬된 셋은 리더보드·레이트 리미터·지연 큐에 쓴다. `KEYS`는 프로덕션에서 금지하고 `SCAN`을 쓰며, 다건 명령은 파이프라인으로 묶는다.
- 인프로세스 캐시는 인스턴스마다 다르고, 메모리를 압박하며, 재시작에 소실된다. 짧은 TTL의 L1과 Redis L2를 겹치고 Pub/Sub으로 무효화를 전파한다.
- 파일은 데이터베이스가 아니라 객체 스토리지에 넣고, 업로드는 프리사인드 URL로 서버를 우회시킨다. 서명 파라미터는 언제나 서버가 결정한다.

## 연습문제

1. 애플리케이션 인스턴스가 최대 12대까지 오토스케일되고 각 인스턴스가 워커 프로세스 2개를 띄우는 서비스가 있다. PostgreSQL의 `max_connections`가 200이고 운영 도구용으로 30을 예약해야 한다면 인스턴스당 풀 크기는 얼마여야 하는가. 이 계산 결과가 3 이하로 내려갔을 때 취할 수 있는 두 가지 대응책을 각각의 트레이드오프와 함께 설명하라.

2. `orders` 테이블의 `status` 컬럼(`text`)을 `status_id`(정수 외래 키)로 교체하려고 한다. 테이블에는 8천만 행이 있고 서비스는 무중단이어야 한다. 확장-수축 패턴의 다섯 단계를 이 사례에 맞게 구체적으로 작성하고, 각 단계가 마이그레이션인지 배포인지 표시하라. 3단계 백필 스크립트를 복제 지연을 고려해 구현하라.

3. 두 계층 캐시(L1 인프로세스 + L2 Redis)를 사용하는 서비스에서 Redis 인스턴스가 30초간 완전히 응답하지 않는 장애가 발생했다. 이때 (a) 캐시 조회, (b) 캐시 무효화 Pub/Sub, (c) 원본 데이터베이스 부하가 각각 어떻게 되는지 서술하고, 장애가 요청 실패로 번지지 않게 만드는 코드를 작성하라. L1의 TTL을 10초에서 5분으로 늘리면 이 장애 상황과 평상시 일관성에 각각 어떤 영향이 있는가.
