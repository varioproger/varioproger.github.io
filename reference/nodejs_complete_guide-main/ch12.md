# 12장. 생성 패턴

객체를 만드는 일은 사소해 보이지만, 대부분의 설계 결정은 바로 그 지점에서 굳어진다. 무엇을 어떻게 만들 것인지가 정해지는 순간 결합(coupling)의 방향과 테스트 가능성, 교체 가능성이 함께 정해지기 때문이다. 생성 패턴(creational pattern)은 "객체를 만드는 방법"을 코드의 나머지 부분에서 떼어내어 그 결정을 나중으로 미루거나 한곳에 모으는 기법이다.

전통적인 GoF 문헌의 생성 패턴은 정적 타입 언어의 제약 — 클래스만이 타입이고, `new`는 반드시 그 클래스의 인스턴스를 돌려주며, 인터페이스는 컴파일 시점에 선언되어야 한다 — 을 우회하기 위한 장치였다. JavaScript에는 그 제약이 대부분 없다. 함수가 일급 값이고, 객체 리터럴이 곧 구조적 타입이며, 클로저가 진짜 은닉을 제공한다. 그래서 같은 이름의 패턴이라도 Node.js에서는 형태와 목적이 상당히 달라진다. 이 장은 그 차이를 중심으로 팩토리, 빌더, 노출 생성자를 다루고, Node.js 고유의 주제인 모듈 캐시와 싱글턴의 관계, 그리고 모듈을 서로 연결하는 두 가지 전략을 대조한다.

## 12.1 팩토리: 객체 생성과 구현의 분리

### 문제 상황

이미지 처리 라이브러리를 만든다고 하자. 초기 버전은 PNG만 다루므로 `PngImage` 클래스 하나면 충분하다.

```js
// image.js — 순진한 첫 버전
export class PngImage {
  constructor (path) {
    this.path = path
  }
  // ...
}
```

호출부는 `new PngImage('logo.png')`라고 쓴다. 몇 달 뒤 JPEG와 GIF를 지원해야 한다. `JpegImage`, `GifImage` 클래스를 추가하면 되지만, 문제는 이미 배포된 호출부다. `new PngImage(...)`라고 쓴 모든 코드가 구체 클래스 이름에 묶여 있다. 확장자에 따라 알맞은 클래스를 고르는 로직은 이제 라이브러리를 쓰는 쪽마다 중복된다. 클래스 이름을 그대로 유지하면서 `PngImage`가 JPEG도 처리하게 만들 수도 없다. `new`는 반드시 그 클래스의 인스턴스를 돌려주기 때문이다.

### 패턴의 정의

팩토리(factory)는 객체를 생성하는 책임을 별도의 함수로 감싸서, **무엇이 만들어지는지를 호출부로부터 감추는** 패턴이다. JavaScript에서 팩토리가 클래스보다 유연한 이유는 두 가지다.

첫째, **반환 타입이 자유롭다.** 팩토리는 클래스 인스턴스를 돌려줘도 되고, 평범한 객체 리터럴을 돌려줘도 되고, 상황에 따라 매번 다른 클래스의 인스턴스를 돌려줘도 된다. 심지어 호출마다 다른 프로토타입 체인을 가진 객체를 만들어도 호출부는 알 필요가 없다. 생성자는 이런 자유가 없다. `new Foo()`는 언제나 `Foo.prototype`을 상속한 객체다.

둘째, **`new`가 필요 없다.** `new`를 빠뜨렸을 때 발생하는 미묘한 버그가 사라지고, 팩토리 함수 자체를 다른 고차 함수에 값으로 넘길 수 있다. `items.map(createUser)`는 자연스럽지만 `items.map(User)`는 동작하지 않는다.

### 구현

앞의 이미지 예제를 팩토리로 바꾸면 이렇게 된다.

```js
// image.js
import { extname } from 'node:path'

class PngImage { constructor (path) { this.path = path } }
class JpegImage { constructor (path) { this.path = path } }
class GifImage { constructor (path) { this.path = path } }

// 확장자를 보고 구현체를 고른다. 호출부는 어떤 클래스인지 모른다
export function createImage (path) {
  switch (extname(path).toLowerCase()) {
    case '.png': return new PngImage(path)
    case '.jpg':
    case '.jpeg': return new JpegImage(path)
    case '.gif': return new GifImage(path)
    default: throw new Error(`지원하지 않는 형식: ${path}`)
  }
}
```

이제 새 포맷을 추가해도 호출부는 손대지 않는다. 세 클래스는 모듈 밖으로 내보내지 않았으므로 외부에서 `new PngImage`를 직접 부를 방법이 아예 없다. **팩토리를 유일한 진입점으로 만들면 그 자체가 API 표면을 좁히는 장치가 된다.**

### 클로저로 강제하는 캡슐화

팩토리의 두 번째 용도는 진짜 은닉이다. ES2022의 `#private` 필드는 문법적으로 깔끔하지만, 클래스 인스턴스가 존재한다는 사실 자체는 감추지 못하고 상속 계층에서 제약이 생긴다. 클로저를 쓰면 변수는 물리적으로 함수 스코프 안에만 존재한다.

```js
// counter.js
export function createCounter () {
  let count = 0                    // 이 바인딩에 도달할 경로가 존재하지 않는다

  return {
    increment () { count += 1; return count },
    get value () { return count }
  }
}

const c = createCounter()
c.increment()
console.log(c.value)               // 1
console.log(Object.keys(c))        // ['increment', 'value'] — count는 흔적조차 없다
```

`#private` 필드와 비교해 보자.

```js
class Counter {
  #count = 0
  increment () { return ++this.#count }
  get value () { return this.#count }
}

const c2 = new Counter()
// 리플렉션으로 값을 읽을 수는 없지만, 존재는 관측된다
console.log(Object.getOwnPropertyNames(Counter.prototype)) // ['constructor','increment','value']
```

실무적인 차이는 세 가지다. `#private`은 디버거와 `util.inspect`에 노출되고, 힙 스냅숏에서 필드 이름이 보이며, `Object.freeze`로 인스턴스를 얼려도 내부 상태는 여전히 메서드를 통해 바뀐다. 반면 클로저 기반 객체는 반환된 객체를 `Object.freeze` 하면 외부 인터페이스가 완전히 고정된다. 대신 대가가 있다. 인스턴스마다 메서드 함수 객체가 새로 만들어지므로 수만 개 단위로 찍어내는 값 객체(value object)에는 프로토타입 공유가 가능한 클래스가 메모리 면에서 유리하다. 은닉이 보안 경계에 해당하는가, 아니면 단순한 규율인가에 따라 고르면 된다.

### 실전 사례(In the wild)

환경에 따라 다른 구현을 돌려주는 것은 팩토리의 대표적 활용이다. 개발 환경에서는 실제로 시간을 재고, 운영 환경에서는 아무 일도 하지 않는 프로파일러를 생각해 보자.

```js
// profiler.js
class Profiler {
  constructor (label) {
    this.label = label
    this.start = null
  }
  begin () { this.start = process.hrtime.bigint() }
  end () {
    const ns = process.hrtime.bigint() - this.start
    console.log(`${this.label}: ${Number(ns) / 1e6}ms`)
  }
}

// 같은 인터페이스를 가진 빈 구현. 호출부는 분기하지 않는다
const noopProfiler = {
  begin () {},
  end () {}
}

export function createProfiler (label) {
  return process.env.NODE_ENV === 'production'
    ? noopProfiler
    : new Profiler(label)
}
```

호출부에는 `if (process.env.NODE_ENV !== 'production')` 같은 분기가 한 줄도 없다. 운영 환경에서는 상태 없는 싱글턴 객체 하나를 재사용하므로 할당 비용도 사라진다. 이런 널 객체(null object) 치환은 로거, 메트릭 수집기, 트레이서처럼 "켜고 끌 수 있어야 하는 횡단 관심사"에 그대로 적용된다.

### 언제 쓰지 말아야 하는가

만들어지는 타입이 하나뿐이고 앞으로도 하나일 것이 분명하다면 팩토리는 간접 층을 하나 더할 뿐이다. `createPoint(x, y)`가 언제나 `new Point(x, y)`만 돌려준다면 그냥 클래스를 내보내는 편이 스택 트레이스도 읽기 쉽고 타입 추론도 정확하다. 상속을 통한 확장을 사용자에게 열어 주고 싶을 때도 팩토리는 방해가 된다. 사용자가 `class MyImage extends PngImage`를 쓸 수 없기 때문이다. 그리고 팩토리 안의 `switch`가 열 갈래를 넘어가기 시작하면 그것은 팩토리의 문제가 아니라 레지스트리(registry)가 필요하다는 신호다. 이름을 키로 하는 `Map`에 생성 함수를 등록하는 구조로 바꾸면 새 타입을 추가할 때 팩토리 본문을 수정하지 않아도 된다.

## 12.2 빌더: 복잡한 생성자 길들이기

### 문제 상황

인자가 많은 생성자는 조용히 썩는다. 다음 코드가 무엇을 만드는지 한눈에 알아볼 수 있는 사람은 없다.

```js
const boat = new Boat(true, 'Blue Sky', false, 2, 'Yamaha', 250, null, 6)
```

호출부만 봐서는 두 번째 불리언이 무엇을 뜻하는지, `null`이 어느 자리인지 알 수 없다. 인자 순서를 하나만 바꿔도 컴파일 오류 없이 잘못된 객체가 만들어진다. 여기에 "선체(hull) 색을 지정하면 재질도 반드시 지정해야 한다"거나 "돛이 없으면 엔진 정보는 필수"처럼 인자 사이의 의존 규칙까지 얹히면, 생성자 본문은 검증 코드로 뒤덮이고 오버로드 대용의 `arguments.length` 분기가 자라난다.

객체 리터럴 하나를 인자로 받는 방식은 이 문제의 절반을 해결한다.

```js
const boat = new Boat({ hasMotor: true, name: 'Blue Sky', motorCount: 2, motorBrand: 'Yamaha' })
```

이름이 붙었으니 순서 문제는 사라졌다. 그러나 "어떤 조합이 유효한가"는 여전히 런타임 검증에 맡겨진다. 사용자는 문서를 읽기 전까지 `motorBrand`만 주고 `motorCount`를 빠뜨리는 실수를 계속한다.

### 패턴의 정의

빌더(builder)는 복잡한 객체의 생성을 **여러 단계로 나누고, 각 단계를 이름 붙은 메서드로 노출한 뒤, 마지막에 하나의 완성 메서드로 결과를 만들어 내는** 패턴이다. 핵심은 세 가지다. 각 단계는 자기 자신(`this`)을 돌려주어 체이닝(chaining)을 가능하게 하고, 관련 있는 인자들은 하나의 메서드로 묶여 함께 전달되며, 최종 `build()` 호출 시점에 한 번만 검증한다.

Java의 빌더가 "생성자 오버로드 폭발"을 막기 위한 장치라면, JavaScript의 빌더는 오히려 **유창한 도메인 언어(fluent API)를 만들기 위한** 장치에 가깝다. 선택적 인자 문제는 객체 리터럴로 이미 해결되므로, 빌더를 도입할 만한 이유는 "단계적으로 누적되는 상태"가 있을 때다.

### 구현

URL을 조립하는 빌더를 만들어 보자. 쿼리 파라미터처럼 여러 번 누적되는 요소가 있고, 인코딩 규칙이 까다로우며, 최종 결과가 문자열 하나라는 점에서 빌더가 잘 맞는 대상이다.

```js
// url-builder.js
export class UrlBuilder {
  #protocol = 'https'
  #host = null
  #port = null
  #segments = []
  #query = new URLSearchParams()

  static create () { return new UrlBuilder() }

  protocol (value) { this.#protocol = value; return this }
  host (value) { this.#host = value; return this }
  port (value) { this.#port = value; return this }

  // 경로는 누적된다. 인코딩은 빌더가 책임진다
  path (...segments) {
    for (const s of segments) this.#segments.push(encodeURIComponent(s))
    return this
  }

  // 같은 키를 여러 번 붙일 수 있다
  query (key, value) { this.#query.append(key, value); return this }

  build () {
    if (this.#host === null) throw new Error('host는 필수다')
    const authority = this.#port ? `${this.#host}:${this.#port}` : this.#host
    const url = new URL(`${this.#protocol}://${authority}`)
    url.pathname = '/' + this.#segments.join('/')
    url.search = this.#query.toString()
    return url.toString()
  }
}
```

사용하는 쪽은 이렇게 읽힌다.

```js
const url = UrlBuilder.create()
  .host('api.example.com')
  .path('v2', 'users', '42', 'orders')
  .query('status', 'shipped')
  .query('status', 'delivered')     // 같은 키 두 번 — 배열 인자 없이 자연스럽다
  .query('limit', '50')
  .build()

console.log(url)
// https://api.example.com/v2/users/42/orders?status=shipped&status=delivered&limit=50
```

정적 `create()`를 둔 이유는 `new`를 없애 체이닝의 시작을 매끄럽게 하기 위해서다(12.1의 팩토리와 같은 이유다). `build()`가 매번 새 문자열을 만들므로 빌더 인스턴스를 재사용해 변형을 파생시킬 수도 있다.

빌더가 진짜 값을 하는 지점은 **단계마다 다른 인터페이스를 노출할 수 있다**는 데 있다. 예를 들어 `auth()` 메서드가 인증 방식별로 다른 하위 빌더를 돌려주게 하면, `basic(user, pass)`와 `bearer(token)`을 뒤섞어 호출하는 실수가 구조적으로 불가능해진다.

```js
auth () {
  return {
    basic: (user, pass) => { this.#query.append('auth', `basic:${user}:${pass}`); return this },
    bearer: (token) => { this.#headers.set('authorization', `Bearer ${token}`); return this }
  }
}
```

### 실전 사례(In the wild)

Node.js 생태계에서 가장 널리 쓰이는 빌더는 SQL 쿼리 빌더다. `knex('users').where('age', '>', 18).orderBy('name').limit(10)`은 각 절이 누적되고 마지막에 `then()` 또는 `toSQL()`이 문장을 조립한다. 테스트 도구 `supertest`의 `request(app).get('/users').set('Accept', 'json').expect(200)` 역시 같은 형태다. 두 사례 모두 "선택적 절이 임의 순서로 여러 번 누적되고, 최종 산출물은 하나"라는 조건을 만족한다.

### 언제 쓰지 말아야 하는가

인자가 서너 개이고 서로 독립적이라면 빌더는 순수한 낭비다. 객체 리터럴 하나로 끝날 일에 클래스와 메서드 열두 개를 만드는 셈이다. 판단 기준은 단순하다. **누적되는 요소가 없고, 인자 간 상호 배타 규칙이 없으며, 부분 완성 상태를 들고 다닐 이유가 없다면 옵션 객체를 쓴다.** 또한 빌더는 중간 상태가 가변(mutable)이라는 점에서 위험을 안고 있다. 빌더 인스턴스를 여러 곳에 넘겨 각자 체이닝하게 두면 서로의 상태를 오염시킨다. 이 문제가 걱정된다면 각 메서드가 `this`를 변형하는 대신 새 빌더를 반환하는 불변 빌더로 만들되, 그 비용이 정당한지 먼저 따져야 한다.

## 12.3 노출 생성자(Revealing Constructor)

### 문제 상황

객체를 만들 때는 내부 상태를 자유롭게 조작해야 하지만, 만들어진 뒤에는 아무도 건드리지 못하게 하고 싶은 경우가 있다. 이벤트를 발행하는 주체는 오직 생성자를 호출한 쪽이어야 하고, 그 객체를 받은 소비자는 구독만 할 수 있어야 한다. 접근 제어자만으로는 이 구분을 표현할 수 없다. `public`이면 누구나 쓰고, `private`이면 아무도 못 쓴다. 필요한 것은 "생성 시점에만 열리는 권한"이다.

### 패턴의 정의

노출 생성자(revealing constructor) 패턴은 **생성자가 인자로 함수를 받고, 그 함수에게만 객체의 내부 조작 권한을 넘겨주는** 기법이다. 그 함수를 실행자(executor)라고 부른다. 실행자는 생성 과정에서 단 한 번 동기적으로 호출되고, 그 호출이 끝나면 넘겨받은 권한을 되돌려 줄 방법이 없어진다. 즉 권한의 수명이 생성 시점으로 한정된다.

이 패턴의 정본은 `Promise` 생성자다.

```js
const p = new Promise((resolve, reject) => {
  // 이 안에서만 resolve/reject를 호출할 수 있다
  setTimeout(() => resolve(42), 100)
})

// 바깥에서는 관측만 가능하다. p.resolve 같은 것은 존재하지 않는다
p.then(v => console.log(v))
```

`resolve`와 `reject`는 프로미스의 상태를 바꾸는 유일한 통로이며, 실행자 함수 밖에서는 접근할 수 없다. 프로미스를 넘겨받은 코드는 절대 그 프로미스를 이행시킬 수 없다. 이것이 프로미스가 신뢰할 수 있는 값 전달 수단이 되는 이유다. 같은 패턴은 웹 표준 스트림의 `new ReadableStream({ start(controller) { ... } })`에서도 볼 수 있다. `controller`가 곧 노출된 권한이다.

### 구현

생성 시점에만 쓸 수 있는 불변 버퍼를 만들어 보자. 생성자는 실행자에게 쓰기 가능한 버퍼를 넘기고, 생성이 끝나면 읽기 전용 뷰만 남긴다.

```js
// immutable-buffer.js
const MODIFIER_NAMES = new Set(['swap16', 'swap32', 'swap64', 'write', 'fill', 'set'])

export class ImmutableBuffer {
  #buffer

  constructor (size, executor) {
    const buffer = Buffer.alloc(size)

    // 쓰기 메서드만 골라 실행자에게 넘긴다
    const modifiers = {}
    for (const prop of Object.getOwnPropertyNames(Buffer.prototype)) {
      if (MODIFIER_NAMES.has(prop) || prop.startsWith('write') || prop.startsWith('fill')) {
        modifiers[prop] = buffer[prop].bind(buffer)
      }
    }

    // 읽기 메서드는 인스턴스에 그대로 노출한다
    for (const prop of Object.getOwnPropertyNames(Buffer.prototype)) {
      if (typeof buffer[prop] === 'function' && !(prop in modifiers)) {
        this[prop] = buffer[prop].bind(buffer)
      }
    }

    this.#buffer = buffer
    executor(modifiers)          // 권한은 여기서만 유효하다
    Object.freeze(this)          // 이후로는 인스턴스 자체도 고정된다
  }

  get length () { return this.#buffer.length }
  inspect () { return this.#buffer.inspect() }
}
```

사용하는 모습은 프로미스와 정확히 같은 형태다.

```js
const greeting = new ImmutableBuffer(16, ({ write, fill }) => {
  fill(0)
  write('Hello!')
})

console.log(greeting.toString())     // 'Hello!' — 읽기는 자유롭다
console.log(greeting.length)         // 16
greeting.write('보안 위반')          // TypeError: greeting.write is not a function
```

`write`는 인스턴스에 아예 존재하지 않는다. 실행자 클로저 안에 있던 참조가 사라지면 그 버퍼를 수정할 방법은 남지 않는다. 여기서 중요한 것은 **실행자를 동기적으로 호출한다**는 규칙이다. 비동기로 미루면 생성자가 반환된 뒤에도 권한이 살아 있게 되어 패턴의 보장이 무너진다. 프로미스 생성자도 실행자를 동기 호출한다.

### 실전 사례(In the wild)

Node.js 코어에서 이 패턴은 스트림 컨트롤러 계열에 집중되어 있다. `ReadableStream`, `WritableStream`, `TransformStream`은 모두 생성자에 넘긴 소스 객체의 `start`/`transform` 콜백으로 `controller`를 전달한다. 애플리케이션 레벨에서는 "설정 객체를 만들되 이후 재설정을 금지하고 싶은" 경우 — 예를 들어 부트스트랩 단계에서 한 번 채워지고 그 뒤로는 전 애플리케이션이 읽기만 하는 설정(config) 객체 — 에 잘 맞는다.

### 언제 쓰지 말아야 하는가

권한 분리가 실제 요구사항이 아니라면 이 패턴은 읽기 어려운 간접 층에 불과하다. 단순히 "실수로 바꾸지 말자" 수준의 규율이면 `Object.freeze`나 `structuredClone` 한 줄이면 충분하다. 또한 실행자 안에서 던진 예외를 어떻게 다룰지 명확하지 않으면 객체가 반쯤 만들어진 채 새어 나갈 수 있다. `Promise`는 실행자의 예외를 `reject`로 흡수하도록 명세되어 있지만, 직접 만드는 클래스에서는 그 정책을 스스로 정하고 문서화해야 한다. 마지막으로, 노출한 권한 객체를 실행자가 바깥 변수에 저장해 버리면 보장은 그대로 깨진다. 이 패턴은 악의적 코드에 대한 방어가 아니라 **실수에 대한 방어**라는 점을 분명히 해야 한다.

## 12.4 싱글턴과 모듈 캐시의 관계

### 문제 상황

데이터베이스 커넥션 풀은 애플리케이션 전체에서 하나만 존재해야 한다. 여러 개가 만들어지면 커넥션 수가 설정값의 배수로 늘어나 데이터베이스가 먼저 쓰러진다. 로거, 설정 객체, 메트릭 레지스트리도 마찬가지다. 다른 언어에서는 이를 위해 `getInstance()` 정적 메서드와 사설 정적 필드를 조합한 싱글턴(singleton) 클래스를 만든다.

Node.js에서 이 코드를 쓰는 것은 대개 불필요하다. **모듈 시스템이 이미 싱글턴을 구현하고 있기 때문이다.**

### 패턴의 정의: 모듈 캐시가 곧 싱글턴이다

CommonJS의 `require`는 해석된 절대 경로를 키로 `require.cache`에 모듈 객체를 저장한다. 같은 경로를 두 번 `require`하면 두 번째부터는 캐시된 `module.exports`를 그대로 돌려준다. 모듈 본문은 단 한 번만 실행된다. ESM도 마찬가지로 URL을 키로 하는 모듈 맵을 유지하며, 같은 URL의 모듈은 한 번만 평가된다.

```js
// db.js — 이것이 Node.js의 싱글턴이다. getInstance()도, 정적 필드도 필요 없다
import { MongoClient } from 'mongodb'

const client = new MongoClient(process.env.MONGO_URL)
await client.connect()             // ESM의 최상위 await

export const db = client.db('blog')
```

```js
// 어디에서 import 하든 같은 db 인스턴스다
import { db } from './db.js'
```

여기서 반드시 짚어야 할 점이 있다. 우리가 얻은 것은 **정확히는 싱글턴이 아니라 "모듈 인스턴스당 하나"** 라는 보장이다. 그리고 그 보장은 생각보다 쉽게 깨진다. 아래 세 가지 조건은 실무에서 실제로 발생한다.

### 보장이 깨지는 조건 1: node_modules 중복 설치

npm은 의존성 트리에서 버전이 충돌하면 중첩 설치로 해결한다. `mydb` 패키지를 두 라이브러리가 서로 다른 버전으로 요구하면 디렉터리는 이렇게 된다.

```text
app/
├── node_modules/
│   ├── mydb/                 <- 1.0.0
│   ├── package-a/
│   │   └── node_modules/
│   │       └── mydb/         <- 2.0.0 (별도 설치)
│   └── package-b/
└── index.js
```

`app/index.js`와 `package-b`는 `app/node_modules/mydb`를 로드하고, `package-a`는 자기 아래의 `mydb`를 로드한다. 경로가 다르므로 캐시 키가 다르고, 모듈 본문이 **두 번** 실행된다. 커넥션 풀도 두 개다. 더 나쁜 것은 두 인스턴스의 클래스가 서로 다른 함수 객체라는 사실이다.

```js
// package-a가 만든 객체를 app에서 검사하면
import { Connection } from 'mydb'
console.log(objFromPackageA instanceof Connection)  // false — 같은 이름, 다른 클래스
```

`instanceof`가 거짓을 돌려주고, `Symbol` 기반 브랜드 검사도 실패한다. 이 문제는 라이브러리 저자의 책임 영역이다. 해결책은 상태를 가진 싱글턴을 패키지가 스스로 소유하지 않는 것 — 즉 인스턴스를 사용자가 만들어 넘기게 하는 것(12.5) — 이거나, 정말 프로세스 전역이어야 한다면 `globalThis`에 심볼 키로 등록하는 것이다.

```js
// 프로세스 전역 레지스트리. 중복 설치되어도 인스턴스는 하나다
const KEY = Symbol.for('mydb.pool')          // Symbol.for는 전역 심볼 레지스트리를 쓴다
globalThis[KEY] ??= createPool()
export const pool = globalThis[KEY]
```

`Symbol.for`를 쓰는 이유는 `Symbol('mydb.pool')`이 호출할 때마다 새 심볼을 만들기 때문이다. 전역 심볼 레지스트리는 realm 단위로 공유되므로 중복 로드된 두 모듈이 같은 키에 도달한다.

### 보장이 깨지는 조건 2: ESM/CJS 이중 로드

패키지가 `package.json`의 `exports` 필드로 CJS와 ESM 양쪽 진입점을 제공하는 경우(듀얼 패키지), 어떤 코드는 `require('pkg')`로, 다른 코드는 `import 'pkg'`로 같은 패키지를 로드할 수 있다.

```json
{
  "name": "pkg",
  "exports": {
    ".": {
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    }
  }
}
```

두 파일은 서로 다른 경로이므로 각각 평가되고, 모듈 스코프의 상태도 각각 존재한다. 이것이 널리 알려진 **듀얼 패키지 해저드(dual package hazard)** 다. 카운터 하나를 두 진입점이 각자 갖게 되면 증상은 조용하고 진단은 어렵다. Node.js 22 이상에서는 `require()`로 ESM을 동기 로드할 수 있게 되어 CJS 래퍼를 없애는 선택지가 생겼다. 상태를 가진 패키지라면 ESM 파일 하나만 두고 CJS 진입점은 그것을 다시 내보내는 얇은 껍데기로 만드는 편이 안전하다.

### 보장이 깨지는 조건 3: 워커 스레드와 프로세스

`worker_threads`의 각 워커는 **독립된 V8 아이솔레이트와 힙**을 가진다. 모듈 캐시도, `globalThis`도 워커마다 별개다. 메인 스레드에서 만든 싱글턴은 워커에서 보이지 않는다.

```js
// main.js
import { Worker } from 'node:worker_threads'
import { counter } from './counter.js'

counter.increment()
console.log('main:', counter.value)         // 1
new Worker(new URL('./worker.js', import.meta.url))
```

```js
// worker.js — counter.js가 이 스레드에서 다시 평가된다
import { counter } from './counter.js'
console.log('worker:', counter.value)       // 0
```

`cluster`나 컨테이너 복제본에서는 더 말할 것도 없다. 따라서 **"프로세스당 하나"와 "애플리케이션당 하나"는 전혀 다른 보장**이다. 캐시, 세션, 레이트 리미터처럼 진짜로 전 인스턴스가 공유해야 하는 상태는 모듈 싱글턴이 아니라 Redis 같은 외부 저장소로 옮겨야 한다(24장 참조). 모듈 싱글턴이 안전한 대상은 커넥션 풀, 설정, 컴파일된 정규식 캐시처럼 **인스턴스마다 하나씩 있어도 정상인 자원**뿐이다.

### 언제 쓰지 말아야 하는가

가장 큰 문제는 테스트다. 모듈 최상위에서 커넥션을 여는 코드는 그 모듈을 `import`하는 순간 네트워크에 접속한다. 단위 테스트에서 이를 피하려면 모듈 캐시를 조작하거나 로더 훅을 붙여야 하는데, 둘 다 깨지기 쉽다. 또한 모듈 싱글턴은 전역 변수와 같은 종류의 결합을 만든다. 그 모듈을 `import`하는 모든 파일이 구체적인 구현에 직접 묶인다. 다음 절이 이 문제를 정면으로 다룬다.

## 12.5 모듈 연결하기: 싱글턴 의존성 vs 의존성 주입

### 문제 상황

간단한 블로그 애플리케이션을 생각하자. `blog.js`가 게시글을 저장하고 조회하며, 데이터베이스는 SQLite다. 두 가지 연결 방식이 있다.

### 방식 1: 싱글턴 의존성

```js
// db.js — 모듈이 인스턴스를 소유한다
import { DatabaseSync } from 'node:sqlite'

export const db = new DatabaseSync('data.sqlite')
db.exec(`CREATE TABLE IF NOT EXISTS posts (
  id TEXT PRIMARY KEY, title TEXT, content TEXT, created_at TEXT
)`)
```

```js
// blog.js — 필요한 것을 직접 가져다 쓴다
import { db } from './db.js'

export class Blog {
  createPost (id, title, content) {
    db.prepare('INSERT INTO posts VALUES (?, ?, ?, ?)')
      .run(id, title, content, new Date().toISOString())
  }
  getAllPosts () {
    return db.prepare('SELECT * FROM posts ORDER BY created_at DESC').all()
  }
}
```

```js
// index.js
import { Blog } from './blog.js'
const blog = new Blog()
blog.createPost('1', '첫 글', '안녕')
```

장점은 명백하다. 배선(wiring) 코드가 없다. 파일이 세 개든 삼백 개든 각자 필요한 것을 `import`하면 끝이고, 의존성이 늘어나도 중간 파일들을 수정할 필요가 없다. 소규모 애플리케이션에서는 이 단순함이 다른 모든 고려사항을 이긴다.

단점도 명백하다. `Blog`는 `data.sqlite`라는 특정 파일에 묶인 특정 데이터베이스에 하드코딩되어 있다. 테스트에서 인메모리 DB를 쓰려면 `blog.js`를 고치거나 모듈 로더를 속여야 한다. 같은 프로세스에서 두 개의 다른 DB를 상대로 `Blog` 두 개를 운용하는 것은 불가능하다. 그리고 `db.js`가 초기화에 실패하면 `blog.js`를 `import`하는 것만으로 애플리케이션이 죽는다.

### 방식 2: 의존성 주입

```js
// db.js — 팩토리만 내보낸다. 인스턴스는 소유하지 않는다
import { DatabaseSync } from 'node:sqlite'

export function createDb (filename) {
  const db = new DatabaseSync(filename)
  db.exec(`CREATE TABLE IF NOT EXISTS posts (
    id TEXT PRIMARY KEY, title TEXT, content TEXT, created_at TEXT
  )`)
  return db
}
```

```js
// blog.js — 무엇을 쓸지는 바깥이 정한다
export class Blog {
  #db
  constructor (db) { this.#db = db }        // 생성자 주입

  createPost (id, title, content) {
    this.#db.prepare('INSERT INTO posts VALUES (?, ?, ?, ?)')
      .run(id, title, content, new Date().toISOString())
  }
  getAllPosts () {
    return this.#db.prepare('SELECT * FROM posts ORDER BY created_at DESC').all()
  }
}
```

```js
// index.js — 조립은 진입점 한 곳에서만 일어난다
import { createDb } from './db.js'
import { Blog } from './blog.js'

const db = createDb('data.sqlite')
const blog = new Blog(db)
```

이제 `blog.js`는 SQLite를 모른다. `prepare().run()`과 `prepare().all()`을 가진 무언가만 알 뿐이다. 테스트는 이렇게 쓴다.

```js
// blog.test.js
import { test } from 'node:test'
import assert from 'node:assert/strict'
import { createDb } from './db.js'
import { Blog } from './blog.js'

test('게시글을 저장하고 조회한다', () => {
  const blog = new Blog(createDb(':memory:'))   // 테스트마다 깨끗한 DB
  blog.createPost('1', '제목', '본문')
  assert.equal(blog.getAllPosts().length, 1)
})
```

모듈 캐시를 건드리지 않고, 파일도 남기지 않으며, 테스트끼리 서로 오염시키지도 않는다. 이것이 의존성 주입(dependency injection)이 주는 실질적 이득이다.

대가는 배선 코드다. 모듈이 늘어나면 `index.js`의 조립부가 길어지고, 의존성의 순서를 사람이 관리해야 하며, 순환 의존이 생기면 직접 풀어야 한다. 또 각 모듈이 어떤 구현과 함께 동작하는지는 이제 코드만 봐서는 알 수 없다.

### DI 컨테이너를 쓸 것인가

배선 코드가 감당하기 어려워지면 `awilix`, `tsyringe`, `InversifyJS` 같은 DI 컨테이너를 고려하게 된다. 판단 기준을 명확히 하자.

컨테이너가 값을 하는 조건은 **의존성 그래프가 깊고(3단계 이상), 같은 인터페이스에 대해 실제로 여러 구현을 교체하며, 요청 스코프(request-scoped) 인스턴스가 필요한 경우**다. HTTP 요청마다 트랜잭션 객체를 새로 만들고 그 요청 안의 모든 서비스가 같은 트랜잭션을 공유해야 한다면, 손으로 짠 배선은 금방 무너진다.

반대로 다음 상황에서는 컨테이너가 손해다. 모듈이 스무 개 미만이고, 구현이 각각 하나뿐이며, 팀에 컨테이너 경험이 없는 경우다. 컨테이너는 의존성 해석을 런타임으로 미루기 때문에 오타 하나가 시작 시점의 예외로 바뀌고, 정적 분석 도구와 IDE의 "정의로 이동"이 무력해진다. 데코레이터 기반 컨테이너는 트랜스파일 설정까지 요구한다.

현실적인 절충안은 **계층별로 다른 전략**을 쓰는 것이다. 커넥션 풀, 로거, 설정처럼 프로세스 전체에서 하나이고 교체할 일이 없는 것은 모듈 싱글턴으로 두고, 비즈니스 로직을 담은 서비스와 리포지터리는 생성자 주입으로 조립한다. 그러면 배선 코드는 짧게 유지되면서 테스트가 필요한 부분은 격리된다.

## 12.6 실전 사례 분석

패턴의 가치를 확인하는 가장 좋은 방법은 널리 쓰이는 패키지의 공개 API를 읽는 것이다. 세 가지를 보자.

### express(): 팩토리가 반환하는 함수

Express의 진입점은 클래스가 아니라 함수다.

```js
import express from 'express'

const app = express()          // new 없음
app.get('/', (req, res) => res.send('ok'))
app.listen(3000)
```

`express()`가 돌려주는 `app`은 **함수인 동시에 객체**다. `app(req, res)`로 호출 가능하며, 동시에 `app.get`, `app.use`, `app.listen` 같은 메서드를 가진다. 이 이중성이 결정적으로 중요하다. `app` 자체가 `(req, res) => {}` 시그니처를 만족하므로 `http.createServer(app)`에 그대로 넘길 수 있고, 다른 Express 앱에 `app.use('/api', subApp)`으로 마운트할 수도 있다. 클래스로는 이런 객체를 만들 수 없다. `new`는 함수를 돌려주지 못하기 때문이다(정확히는 생성자에서 함수를 반환하면 되지만, 그러면 `instanceof`가 깨진다). **팩토리는 반환 타입이 자유롭다는 성질을 Express가 아키텍처의 근간으로 삼은 사례다.**

### knex: 팩토리이면서 빌더

`knex`는 12.1과 12.2를 한 패키지에서 결합한다.

```js
import knexFactory from 'knex'

const knex = knexFactory({
  client: 'pg',                          // 클라이언트 이름으로 방언 구현을 고른다
  connection: process.env.DATABASE_URL,
  pool: { min: 2, max: 10 }
})

const rows = await knex('users')
  .where('age', '>', 18)
  .whereIn('country', ['KR', 'JP'])
  .orderBy('created_at', 'desc')
  .limit(20)
```

바깥층은 팩토리다. `client` 값에 따라 PostgreSQL, MySQL, SQLite 방언 객체를 골라 조립하며, 호출부는 어떤 클래스가 만들어졌는지 알 필요가 없다. 안쪽 층은 빌더다. `where`, `orderBy`, `limit`이 각각 조건을 누적하고 자기 자신을 반환하며, `await`이 걸리는 순간(`then`이 호출되는 순간) SQL 문자열이 조립되어 실행된다. 즉 **지연 실행되는 빌더**다. `toSQL()`로 실행 없이 결과만 볼 수도 있다. 반환값이 항상 `knex` 인스턴스에 묶여 있으므로, 12.5 관점에서 보면 `knexFactory(...)`의 결과를 애플리케이션 진입점에서 한 번 만들어 주입하는 것이 권장 사용법이다.

### node-redis의 createClient: 팩토리 + 명시적 생명주기

```js
import { createClient } from 'redis'

const client = createClient({ url: process.env.REDIS_URL })
client.on('error', err => console.error('redis 오류', err))
await client.connect()          // 연결은 명시적 단계다
```

여기서 눈여겨볼 것은 `createClient`가 **연결하지 않은 클라이언트를 돌려준다**는 점이다. 생성과 연결을 분리했기 때문에 이벤트 핸들러를 붙일 시간이 확보되고, 재연결 전략을 옵션으로 주입할 수 있으며, 테스트에서는 연결하지 않은 채 명령 직렬화만 검증할 수도 있다. 12.4의 관점에서도 의미가 있다. node-redis는 모듈 최상위에서 클라이언트를 만들지 않는다. 인스턴스의 소유권을 애플리케이션에 넘겼기 때문에 중복 설치나 워커 스레드 문제가 라이브러리의 문제가 되지 않는다. **상태를 가진 라이브러리는 싱글턴을 스스로 소유하지 말아야 한다**는 원칙의 좋은 예다.

세 사례를 관통하는 공통점은 하나다. 어느 것도 GoF 다이어그램을 그대로 옮기지 않았다. `AbstractFactory` 인터페이스도, `Director` 클래스도 없다. JavaScript의 함수와 객체가 이미 그 역할을 하고 있기 때문에, 남은 것은 패턴의 **의도** — 생성 결정의 분리, 단계적 조립, 권한의 시간 제한 — 뿐이다.

## 요약

- 팩토리는 반환 타입이 자유롭고 `new`가 필요 없다는 점에서 JavaScript에서 클래스보다 유연하며, 클로저와 결합하면 `#private` 필드보다 강한 은닉을 제공한다. 대신 인스턴스마다 메서드 객체가 생기는 메모리 비용을 진다.
- 빌더는 선택적 인자 문제를 푸는 도구가 아니다. 그 문제는 옵션 객체로 이미 해결된다. 빌더의 가치는 **누적되는 요소**와 유창한 API에 있으며, 인자 서너 개짜리 생성자에 도입하면 순수한 낭비다.
- 노출 생성자는 `Promise` 생성자가 대표하는 패턴으로, 실행자 함수에게만 내부 조작 권한을 동기적으로 넘겨 "생성 시점에만 변경 가능한 객체"를 만든다. 실수 방어이지 보안 경계가 아니다.
- Node.js에서 싱글턴은 모듈 캐시로 이미 구현되어 있으므로 `getInstance()`를 직접 만들 이유가 없다. 다만 그것은 "모듈 인스턴스당 하나"일 뿐이다.
- 그 보장은 세 조건에서 깨진다. `node_modules` 중복 설치(경로가 다르면 캐시 키도 다르고 `instanceof`도 실패한다), ESM/CJS 듀얼 패키지 해저드, 워커 스레드마다 분리된 힙이다.
- 싱글턴 의존성은 배선 코드가 없어 소규모에 유리하고, 의존성 주입은 테스트와 교체 가능성을 얻는 대신 조립 비용을 치른다. 계층별로 다르게 적용하는 절충이 현실적이다.
- DI 컨테이너는 의존성 그래프가 깊고 요청 스코프가 필요할 때만 값을 한다. 모듈 스무 개 규모에서는 정적 분석을 잃는 손해가 더 크다.

## 연습문제

1. **레지스트리 기반 팩토리 리팩터링** — 12.1의 `createImage`에서 `switch` 문을 제거하고, 확장자를 키로 생성 함수를 담는 `Map` 레지스트리로 바꾸어라. 새 포맷을 추가하는 `registerFormat(ext, factory)` 함수를 공개 API로 노출하되, 이미 등록된 확장자를 덮어쓰려 하면 오류를 던지게 하라. 그다음 `createProfiler` 예제를 참고해 "지원하지 않는 형식일 때 예외 대신 널 객체를 반환하는" 모드를 옵션으로 추가하고, 두 정책 중 어느 쪽이 라이브러리 API로 적절한지 근거를 들어 설명하라.

2. **듀얼 패키지 해저드 재현** — 모듈 스코프에 카운터를 두고 `increment()`와 `value` getter를 내보내는 작은 패키지를 만들어라. `package.json`의 `exports`에 `import`와 `require` 진입점을 각각 다른 파일로 지정한 뒤, 한 애플리케이션에서 두 방식으로 모두 로드해 카운터가 분리되는 것을 실제로 관측하라. 이어서 `Symbol.for`를 이용한 전역 레지스트리로 이 문제를 해결하고, 그 해법이 워커 스레드에서도 유효한지 `worker_threads`로 검증하라. 결과가 왜 그렇게 나오는지 힙 분리 관점에서 서술하라.

3. **주입 전략 비교** — 12.5의 블로그 예제를 확장해 `Blog`가 `db` 외에 `logger`와 `cache` 두 의존성을 더 받도록 만들어라. (a) 세 의존성을 모두 모듈 싱글턴으로 `import`하는 버전, (b) 생성자 주입 버전, (c) `logger`와 `cache`는 싱글턴, `db`만 주입하는 혼합 버전을 각각 구현하라. 세 버전에 대해 "인메모리 DB로 테스트하기", "두 번째 블로그 인스턴스를 다른 DB로 띄우기", "새 의존성 하나 더 추가하기" 세 가지 작업을 수행해 보고, 각 작업에서 수정해야 하는 파일 수를 표로 정리하라. 어느 규모에서 (c)가 (b)보다 유리한지 결론을 내려라.
