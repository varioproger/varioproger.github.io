# 13장. 구조 패턴

생성 패턴이 객체를 어떻게 만들 것인가를 다뤘다면(12장 참조), 구조 패턴(structural pattern)은 이미 존재하는 객체들을 어떻게 조합하고 감쌀 것인가를 다룬다. 프록시, 데코레이터, 어댑터가 이 범주의 핵심 삼형제다.

세 패턴은 겉모습이 비슷하다. 모두 "다른 객체를 감싸는 객체"를 만든다. 그래서 Java나 C++ 교재에서 배운 클래스 다이어그램만 들고 오면 실무에서 반드시 헷갈린다. JavaScript에는 인터페이스 선언이 없고, 객체의 속성을 런타임에 바꿔치기할 수 있으며, 언어 차원에서 `Proxy`라는 메타프로그래밍 도구를 제공한다. 이 세 가지 특성 때문에 구조 패턴의 구현 기법은 정적 타입 언어와 완전히 달라진다.

이 장에서는 각 패턴을 정의부터 다시 쌓되, "어떤 기법으로 구현할 수 있는가"와 "그 기법의 비용은 무엇인가"를 항상 함께 따진다. 마지막 절에서는 Express, undici, OpenTelemetry가 실제로 이 패턴들을 어떻게 쓰는지 코드 수준에서 확인한다.

## 13.1 프록시: 객체 합성, 객체 증강, 내장 Proxy

### 문제 상황

운영 중인 서비스에서 특정 파일에 무엇이 쓰이는지 추적해야 한다고 하자. `createWriteStream`이 돌려주는 `Writable` 스트림에 쓰이는 모든 데이터를 로그로 남기고 싶다. 스트림을 만드는 코드는 여기저기 흩어져 있고, 스트림을 소비하는 쪽은 `pipeline()`이나 `res.pipe()`처럼 남의 코드다. 소비하는 쪽이 "그냥 평범한 `Writable`"이라고 믿는 상태를 깨뜨리지 않으면서, 쓰기 동작만 가로채야 한다.

이것이 프록시(proxy)가 필요한 상황이다.

### 패턴의 정의

프록시는 다른 객체(대상, subject)로의 접근을 제어하는 객체다. 핵심 제약이 하나 있다. **프록시는 대상과 동일한 인터페이스를 제공해야 한다.** 클라이언트는 자기가 프록시를 쥐고 있는지 실제 객체를 쥐고 있는지 몰라야 하며, 알 필요도 없어야 한다. 프록시가 하는 일은 접근 경로에 끼어들어 검증, 로깅, 캐싱, 지연 초기화, 접근 제어 같은 부가 동작을 수행하는 것이다.

인터페이스가 동일하다는 제약이 프록시를 데코레이터와 가르는 기준이다(13.4절에서 다시 다룬다). 프록시를 씌워도 대상이 할 수 있는 일의 목록은 그대로다. 다만 그 일을 하는 방식이 달라진다.

JavaScript에서 프록시를 만드는 기법은 세 가지다. 같은 예제로 셋 다 구현해 보자. 대상은 스택처럼 동작하는 단순한 객체이고, 프록시는 모든 `push` 호출을 로그로 남긴다.

```js
// subject.js — 대상 객체
export class Stack {
  #items = []

  push (value) {
    this.#items.push(value)
    return this.#items.length
  }

  pop () {
    return this.#items.pop()
  }

  get size () {
    return this.#items.length
  }
}
```

### 기법 1: 객체 합성(composition)

가장 고전적이고 가장 안전한 방법이다. 새 객체를 만들고, 대상을 내부에 품고, 인터페이스에 해당하는 모든 메서드를 하나씩 정의해 위임(delegate)한다.

```js
// proxy-composition.js
export function createLoggingStack (subject) {
  return {
    push (value) {
      console.log(`[log] push(${value})`)   // 가로채는 지점
      return subject.push(value)             // 위임
    },
    pop () {
      return subject.pop()                   // 그대로 위임
    },
    get size () {
      return subject.size
    }
  }
}
```

클래스로 쓰고 싶다면 대상을 필드로 보관하면 된다.

```js
export class LoggingStack {
  #subject

  constructor (subject) {
    this.#subject = subject
  }

  push (value) {
    console.log(`[log] push(${value})`)
    return this.#subject.push(value)
  }

  pop () { return this.#subject.pop() }
  get size () { return this.#subject.size }
}
```

합성의 장점은 명시성이다. 프록시가 어떤 인터페이스를 제공하는지 코드만 봐도 알 수 있고, 대상 객체는 전혀 오염되지 않으므로 같은 대상에 대해 프록시가 있는 참조와 없는 참조가 공존할 수 있다. 단점은 지루함이다. 인터페이스가 30개 메서드라면 29개를 무의미하게 받아 넘겨야 하고, 대상 라이브러리가 버전업하며 메서드를 추가하면 프록시는 조용히 뒤처진다.

`Object.create`로 대상을 프로토타입에 두면 위임 코드를 줄일 수 있다.

```js
export function createLoggingStack (subject) {
  const proto = Object.getPrototypeOf(subject)
  const proxy = Object.create(proto)          // 대상의 프로토타입을 상속
  proxy.push = function (value) {
    console.log(`[log] push(${value})`)
    return subject.push(value)
  }
  return proxy
}
```

다만 이 변형은 대상이 프라이빗 필드(`#items`)나 클로저 상태를 쓰는 순간 깨진다. 상속받은 `pop`이 `this`로 프록시 객체를 받는데, 그 객체에는 `#items`가 없어서 `TypeError`가 난다. 실무에서 이 기법은 상태가 프로토타입 바깥에 없는 경우로 한정해야 한다.

### 기법 2: 객체 증강(object augmentation, 몽키 패칭)

대상 객체의 속성을 직접 덮어쓰는 방법이다. 흔히 몽키 패칭(monkey patching)이라 부른다.

```js
// proxy-augmentation.js
export function patchStack (subject) {
  const original = subject.push          // 원본 메서드를 보관
  subject.push = function (value) {
    console.log(`[log] push(${value})`)
    return original.call(this, value)    // this 바인딩 유지가 핵심
  }
  return subject                          // 대상 자체를 돌려준다
}
```

가장 짧고 가장 위험하다. 짧은 이유는 나머지 메서드를 건드릴 필요가 없기 때문이고, 위험한 이유는 **대상 객체가 전역적으로 변하기 때문**이다. 다른 모듈이 이미 그 객체를 참조하고 있다면 그쪽에서도 로그가 찍힌다. 되돌리려면 원본을 다시 대입하는 정리 함수를 제공해야 한다.

```js
export function patchStack (subject) {
  const original = subject.push
  subject.push = function (value) {
    console.log(`[log] push(${value})`)
    return original.call(this, value)
  }
  return () => { subject.push = original }   // 원복 함수를 돌려준다
}
```

몽키 패칭은 나쁜 관행으로 자주 비난받지만, 사실 Node.js 생태계에서 가장 널리 쓰이는 프록시 기법이다. APM 에이전트와 계측 라이브러리가 남의 코드를 수정하지 않고 훅을 걸 수 있는 유일한 수단이기 때문이다(13.6절 참조).

### 기법 3: 내장 Proxy

ES2015가 도입한 `Proxy`는 객체에 대한 근본적인 연산(fundamental operation)을 가로채는 메타프로그래밍 장치다. 대상과 핸들러(handler)를 받고, 핸들러에 정의된 트랩(trap)이 해당 연산을 대체한다.

```js
// proxy-builtin.js
export function createLoggingStack (subject) {
  return new Proxy(subject, {
    get (target, prop, receiver) {
      if (prop === 'push') {
        return function (value) {
          console.log(`[log] push(${value})`)
          return target.push(value)      // target에 바인딩해 호출해야 한다
        }
      }
      return Reflect.get(target, prop, target)   // 나머지는 그대로 통과
    }
  })
}
```

`Reflect.get(target, prop, target)`에서 세 번째 인자를 `receiver`가 아닌 `target`으로 넘긴 점에 주목한다. 프라이빗 필드를 쓰는 클래스에서는 게터가 `this`로 프록시를 받으면 `#items`를 찾지 못해 실패한다. 프록시로 클래스 인스턴스를 감쌀 때 가장 흔한 버그가 이것이다.

주요 트랩은 다음과 같다.

| 트랩 | 가로채는 연산 | 대표 용도 |
| --- | --- | --- |
| `get` | `obj.prop`, `obj[key]` | 지연 로딩, 로깅, 가상 속성 |
| `set` | `obj.prop = v` | 유효성 검사, 변경 감지 |
| `has` | `'prop' in obj` | 속성 숨기기, 가상 네임스페이스 |
| `deleteProperty` | `delete obj.prop` | 삭제 금지, 삭제 감사 로그 |
| `apply` | `fn(...)` | 함수 호출 계측, 인자 검증 |
| `construct` | `new Cls(...)` | 인스턴스 생성 추적, 풀링 |
| `ownKeys` | `Object.keys`, `for...in` | 내부 속성 은닉 |

`apply` 트랩은 함수를 감쌀 때 쓴다. 함수도 객체이므로 그대로 프록시 대상이 된다.

```js
// 호출 시간을 재는 함수 프록시
function timed (fn, label = fn.name) {
  return new Proxy(fn, {
    apply (target, thisArg, args) {
      const start = performance.now()
      try {
        return Reflect.apply(target, thisArg, args)
      } finally {
        console.log(`${label}: ${(performance.now() - start).toFixed(2)}ms`)
      }
    }
  })
}
```

`Proxy`의 강력함에는 대가가 있다. **모든 속성 접근이 최적화 장벽을 만난다.** V8은 일반 객체의 속성 접근을 인라인 캐시(inline cache)와 히든 클래스로 최적화하지만, 프록시는 접근할 때마다 핸들러 함수를 호출해야 하므로 이 최적화가 통째로 무력화된다. 마이크로벤치마크에서 프록시를 통한 속성 읽기는 직접 읽기보다 수 배에서 수십 배 느리다. 초당 수백만 번 접근하는 뜨거운 경로(hot path)에 프록시를 두면 프로파일러에 바로 잡힌다.

또 하나, 프록시는 되돌릴 수 없는 흔적을 남긴다. `Proxy`로 감싼 객체는 대상과 `===` 비교에서 다르며, `WeakMap` 키로 쓸 때 서로 다른 항목이 된다. 라이브러리가 내부적으로 객체 동일성에 의존한다면 프록시가 그 가정을 깬다.

### 세 기법 비교

| 기준 | 객체 합성 | 객체 증강 | 내장 Proxy |
| --- | --- | --- | --- |
| 대상 오염 | 없음 | 있음(전역 영향) | 없음 |
| 코드 분량 | 인터페이스 크기에 비례 | 최소 | 최소 |
| 신규 메서드 자동 대응 | 안 됨 | 해당 없음 | 됨 |
| 객체 동일성 유지 | 깨짐 | 유지 | 깨짐 |
| 성능 | 위임 1회, 무시 가능 | 사실상 0 | 접근마다 트랩, 최대 수십 배 |
| 원복 가능성 | 참조를 버리면 됨 | 정리 함수 필요 | 참조를 버리면 됨 |
| 인터페이스 명시성 | 높음 | 낮음 | 낮음 |

선택 기준은 단순하다. 인터페이스가 작고 명확하면 합성이 정답이다. 남의 객체를 내가 만들지 않은 지점에서 가로채야 하면 증강이 유일한 수단이다. 인터페이스가 동적이거나 알 수 없을 때, 또는 속성 접근 자체를 가상화해야 할 때만 `Proxy`를 꺼낸다.

### 실전 사례: 로깅 Writable 스트림

7장에서 다룬 `Writable` 스트림에 프록시를 씌워 보자. 목표는 `write`와 `end`로 흘러가는 데이터를 로그로 남기되, `pipeline()`이 요구하는 스트림 계약(이벤트, `destroy`, `writableEnded` 등)을 전혀 손상시키지 않는 것이다.

인터페이스가 크고(이벤트 이미터 메서드까지 포함하면 수십 개), 미래에 메서드가 추가될 수 있으며, 우리는 두 메서드만 관심 있다. `Proxy`가 적합한 조건이다.

```js
// logging-writable.js
import { createWriteStream } from 'node:fs'

export function createLoggingWritable (writable, log = console.log) {
  return new Proxy(writable, {
    get (target, prop, receiver) {
      if (prop === 'write') {
        return function (chunk, encoding, callback) {
          log('[write]', Buffer.isBuffer(chunk) ? chunk.length + 'B' : chunk)
          return target.write(chunk, encoding, callback)
        }
      }
      if (prop === 'end') {
        return function (...args) {
          log('[end]')
          return target.end(...args)
        }
      }
      const value = Reflect.get(target, prop, target)
      // 메서드는 반드시 target에 바인딩해야 내부 상태 접근이 깨지지 않는다
      return typeof value === 'function' ? value.bind(target) : value
    }
  })
}

const file = createLoggingWritable(createWriteStream('out.txt'))
file.write('첫 줄\n')
file.write('둘째 줄\n')
file.end()
```

`typeof value === 'function' ? value.bind(target) : value` 한 줄이 이 구현의 안전장치다. 스트림 내부 메서드는 심벌 키 상태와 프라이빗 필드를 자유롭게 쓰므로, `this`가 프록시로 들어오는 순간 예측 불가능하게 깨진다. 다만 이 바인딩은 매 접근마다 새 함수를 만들므로, 함수 동일성 비교(`stream.write === stream.write`가 `false`가 된다)와 할당 비용이 생긴다. 뜨거운 경로라면 바인딩 결과를 `WeakMap`에 캐시한다.

같은 목적을 객체 증강으로 구현하면 세 줄로 끝난다.

```js
const original = writable.write.bind(writable)
writable.write = (chunk, enc, cb) => { log('[write]', chunk); return original(chunk, enc, cb) }
```

짧지만 이 스트림을 참조하는 다른 모든 코드가 영향을 받는다. 스트림을 만든 곳에서 즉시 감싸고 원본 참조를 밖으로 내보내지 않는다면 증강이 더 실용적이고, 이미 남에게 넘어간 스트림이라면 프록시로 새 참조를 만드는 편이 낫다.

### 언제 쓰지 말아야 하는가

프록시를 남용하면 디버깅이 지옥이 된다. 스택 트레이스에는 프록시 핸들러가 찍히고, 디버거에서 객체를 펼치면 실제 값 대신 트랩이 실행되며, 로그로 찍은 객체가 실제 상태와 다를 수 있다.

구체적으로 다음 상황에서는 피한다. 첫째, 초당 수만 회 이상 속성에 접근하는 경로다. 둘째, 객체 동일성에 의존하는 코드에 넘길 객체다. 셋째, 단순히 "한 메서드에 로그를 추가"하는 정도의 목적이다. 이때는 대상 코드를 직접 고치거나 함수로 감싸는 편이 정직하다. 넷째, 직렬화 대상 객체다. `JSON.stringify`는 `ownKeys`와 `get` 트랩을 연쇄 호출하므로 프록시가 예상 밖의 결과를 만들기 쉽다.

## 13.2 변경 관찰자(Change Observer) 구현

### 문제 상황

설정 객체가 있고, 그 값이 바뀔 때마다 파일에 저장하거나 다른 서비스에 알려야 한다고 하자. 가장 흔한 해법은 세터 메서드를 만들어 강제하는 것이다.

```js
config.set('port', 8080)   // 이렇게만 바꾸세요
```

문제는 강제가 불가능하다는 점이다. 누군가는 `config.port = 8080`이라고 쓸 것이고, 그 대입은 조용히 성공하고 알림은 발생하지 않는다. 규약(convention)에 의존하는 API는 결국 깨진다. 대입 연산 자체를 가로챌 수 있어야 한다.

### 패턴의 정의

변경 관찰자(change observer)는 프록시 패턴의 특수한 적용이다. 대상 객체와 동일한 인터페이스를 유지하되, 속성의 변경(할당, 삭제)을 감지해 구독자에게 통지한다. 옵저버 패턴(4장 참조)이 "이벤트를 명시적으로 발행"하는 데 비해, 변경 관찰자는 "평범한 대입문이 곧 이벤트"가 되게 만든다.

`set`과 `deleteProperty` 트랩이 이 패턴의 전부다.

### 구현 코드

```js
// observable.js
export function createObservable (target, observer) {
  return new Proxy(target, {
    set (obj, prop, value, receiver) {
      const prev = obj[prop]
      const had = Object.prototype.hasOwnProperty.call(obj, prop)
      const ok = Reflect.set(obj, prop, value, obj)
      // 값이 실제로 달라졌을 때만 통지한다(SameValueZero 비교)
      if (ok && (!had || !Object.is(prev, value))) {
        observer({ type: had ? 'update' : 'add', prop, prev, value })
      }
      return ok
    },
    deleteProperty (obj, prop) {
      const had = Object.prototype.hasOwnProperty.call(obj, prop)
      const prev = obj[prop]
      const ok = Reflect.deleteProperty(obj, prop)
      if (ok && had) observer({ type: 'delete', prop, prev, value: undefined })
      return ok
    }
  })
}

const config = createObservable({ port: 3000 }, (change) => {
  console.log(`${change.type} ${String(change.prop)}: ${change.prev} -> ${change.value}`)
})

config.port = 8080          // update port: 3000 -> 8080
config.host = 'localhost'   // add host: undefined -> localhost
delete config.host          // delete host: localhost -> undefined
```

`Object.is`로 이전 값과 비교해 실제 변화가 있을 때만 통지하는 부분이 중요하다. 이 가드가 없으면 `config.port = config.port` 같은 무의미한 대입이 저장 로직을 깨우고, 값을 다시 대입하는 루프에서 무한 통지가 발생한다.

### 중첩 객체 처리

위 구현은 한 겹만 관찰한다. `config.db.host = 'x'`는 감지되지 않는다. `config.db`를 읽는 순간 평범한 내부 객체가 그대로 반환되고, 그 객체에 대한 대입은 프록시를 거치지 않기 때문이다.

해법은 `get` 트랩에서 객체를 반환할 때 그 객체도 프록시로 감싸는 것이다. 재귀적으로 감싸되, 같은 객체를 두 번 감싸지 않도록 `WeakMap`에 캐시한다.

```js
// deep-observable.js
export function createDeepObservable (target, observer) {
  const cache = new WeakMap()

  function wrap (obj, path) {
    if (cache.has(obj)) return cache.get(obj)

    const proxy = new Proxy(obj, {
      get (o, prop, receiver) {
        const value = Reflect.get(o, prop, o)
        // 객체이면 지연 방식으로 감싼다(전체 순회는 하지 않는다)
        if (value !== null && typeof value === 'object' && !isImmutable(value)) {
          return wrap(value, [...path, prop])
        }
        return value
      },
      set (o, prop, value) {
        const prev = o[prop]
        const ok = Reflect.set(o, prop, value, o)
        if (ok && !Object.is(prev, value)) {
          observer({ type: 'set', path: [...path, prop].join('.'), prev, value })
        }
        return ok
      },
      deleteProperty (o, prop) {
        const prev = o[prop]
        const ok = Reflect.deleteProperty(o, prop)
        if (ok) observer({ type: 'delete', path: [...path, prop].join('.'), prev })
        return ok
      }
    })

    cache.set(obj, proxy)
    return proxy
  }

  function isImmutable (v) {
    return v instanceof Date || v instanceof RegExp ||
           v instanceof WeakMap || v instanceof WeakSet
  }

  return wrap(target, [])
}
```

`WeakMap` 캐시는 두 가지를 동시에 해결한다. 하나는 성능이다. `config.db`를 백 번 읽어도 프록시는 한 번만 만든다. 다른 하나는 동일성이다. 캐시가 없으면 `config.db === config.db`가 `false`가 되어 리액티브 프레임워크의 비교 로직이 전부 무너진다.

지연 방식(lazy)으로 감싸는 점도 중요하다. 객체 트리 전체를 미리 순회해 감싸면 큰 설정 객체에서 시작 비용이 폭발하고, 순환 참조가 있으면 무한 재귀에 빠진다. 접근할 때 감싸면 실제로 쓰이는 경로만 비용을 낸다.

### 배열 변경 감지의 함정

배열을 관찰하려 하면 예상 밖의 통지가 쏟아진다.

```js
const list = createObservable([], (c) => console.log(c.type, String(c.prop), c.value))
list.push('a')
// set 0 a
// set length 1     <- 이 통지가 함께 발생한다
```

`Array.prototype.push`는 내부적으로 인덱스에 값을 대입하고 `length`를 갱신한다. 둘 다 별개의 `set` 트랩을 발동시킨다. `splice`처럼 여러 원소를 옮기는 메서드는 요소 개수만큼 통지가 발생하고, 마지막에 `length` 통지가 한 번 더 붙는다. 배열 하나를 정렬하면 수십 개의 변경 이벤트가 만들어진다.

실용적인 대응은 세 가지다.

첫째, `length` 통지를 걸러낸다. 인덱스 대입만으로도 배열 내용 변화는 충분히 감지되기 때문이다. 다만 `list.length = 0`으로 배열을 비우는 관용구는 이때 놓친다.

```js
set (o, prop, value) {
  if (Array.isArray(o) && prop === 'length') {
    return Reflect.set(o, prop, value, o)   // 통지 없이 통과
  }
  // ...
}
```

둘째, 통지를 마이크로태스크 단위로 모은다. 한 틱 안에서 발생한 변경을 배열에 쌓아 두었다가 `queueMicrotask`로 한 번에 흘려보낸다. 프레임워크가 실제로 쓰는 방식이다.

```js
function batched (observer) {
  let queue = null
  return (change) => {
    if (queue === null) {
      queue = []
      queueMicrotask(() => { const q = queue; queue = null; observer(q) })
    }
    queue.push(change)
  }
}
```

셋째, 배열 메서드 자체를 프록시의 `get` 트랩에서 가로채 의미 단위 이벤트(`push`, `splice`)로 바꾼다. 정밀하지만 구현할 메서드가 많고, 새 배열 메서드가 표준에 추가되면 뒤처진다.

### 실전 사례: 프레임워크가 쓰는 원리

Vue 3의 반응성 시스템(`@vue/reactivity`)이 정확히 이 구조다. `reactive()`는 `Proxy`로 객체를 감싸고, `get` 트랩에서 현재 실행 중인 이펙트(effect)를 의존성으로 등록(track)하며, `set` 트랩에서 그 의존성들을 실행(trigger)한다. 중첩 객체는 위 코드처럼 `get` 시점에 지연 방식으로 감싸고, `WeakMap`으로 프록시를 캐시한다. Vue 2가 `Object.defineProperty`로 같은 일을 하려다 "객체에 새 속성을 추가하면 반응하지 않는다", "배열 인덱스 대입을 감지하지 못한다"는 유명한 제약을 안았던 것과 대비된다. `Proxy`는 존재하지 않는 속성에 대한 대입까지 가로챌 수 있기 때문에 그 제약이 사라졌다.

MobX 역시 `observable()`에서 프록시 기반 구현을 기본으로 쓴다. 배열의 `length` 문제, 동일성 유지 문제, 지연 래핑 문제를 모두 위와 같은 방식으로 다룬다.

서버 사이드에서는 설정 핫 리로드, 도메인 객체의 변경 감사 로그(audit log), 캐시 무효화 트리거에 유용하다.

### 언제 쓰지 말아야 하는가

변경 관찰자는 "대입문이 부수 효과를 일으킨다"는 사실을 코드에서 숨긴다. `user.name = 'x'` 한 줄이 네트워크 요청을 유발할 수 있다는 뜻이다. 팀 전체가 그 객체가 관찰 대상이라는 사실을 인지하지 못하면 원인을 알 수 없는 성능 문제와 순환 갱신이 생긴다.

관찰 대상 객체를 함수 경계 밖으로 넘기지 말아야 한다. 특히 서드파티 라이브러리에 넘기면 그쪽의 내부 대입까지 전부 통지된다. 대량 데이터(수만 개 원소의 배열)에도 쓰지 않는다. 통지 비용이 데이터 처리 비용을 넘어선다. 이럴 때는 불변 데이터를 새로 만들고 참조를 교체하는 방식이 훨씬 예측 가능하다.

## 13.3 데코레이터: 세 가지 구현 기법

### 문제 상황

레디스 같은 키-값 저장소 클라이언트가 있다. 기본 기능은 `get`, `set`, `del` 셋이다. 여기에 팀마다 다른 요구가 붙는다. 어떤 서비스는 값의 만료 시각을 자동 관리하고 싶고, 어떤 서비스는 저장 전에 값을 압축하고 싶고, 어떤 서비스는 키를 네임스페이스로 격리하고 싶다.

이 요구를 모두 클라이언트 클래스에 넣으면 클래스가 비대해지고, 쓰지 않는 기능까지 로딩된다. 상속으로 풀면 조합 폭발이 일어난다. 만료 + 압축, 압축 + 네임스페이스, 셋 다인 경우까지 클래스를 만들 수는 없다.

### 패턴의 정의

데코레이터(decorator)는 기존 객체에 **새로운 동작을 동적으로 추가**하는 패턴이다. 프록시와 구조는 같지만 목적이 정반대다. 프록시는 인터페이스를 그대로 두고 접근만 제어하며, 데코레이터는 인터페이스를 넓힌다. 데코레이터를 씌운 객체는 원래 객체가 할 수 없던 일을 할 수 있다.

상속과의 차이도 분명하다. 상속은 클래스 정의 시점에 정해지지만, 데코레이터는 런타임에 인스턴스 단위로 조합된다. 같은 클라이언트 클래스로 만든 인스턴스 A에는 압축만, B에는 압축과 네임스페이스를 씌울 수 있다.

### 기법 1: 객체 합성

프록시와 마찬가지로 대상을 품고 위임하되, 대상에 없던 메서드를 추가한다.

```js
// decorator-composition.js
export function withExpiry (client) {
  return {
    // 기존 인터페이스는 그대로 위임한다
    get: (key) => client.get(key),
    set: (key, value) => client.set(key, value),
    del: (key) => client.del(key),

    // 새로운 기능을 더한다
    async setWithTTL (key, value, ttlMs) {
      await client.set(key, JSON.stringify({ v: value, exp: Date.now() + ttlMs }))
    },
    async getFresh (key) {
      const raw = await client.get(key)
      if (raw == null) return undefined
      const { v, exp } = JSON.parse(raw)
      if (Date.now() > exp) { await client.del(key); return undefined }
      return v
    }
  }
}
```

명시적이지만 기존 메서드를 전부 다시 써야 한다. 클라이언트에 메서드가 20개면 20줄의 잡음이 생긴다.

### 기법 2: 객체 증강

대상 객체에 속성을 직접 추가한다. 기존 메서드는 손대지 않으므로 프록시 때보다 훨씬 안전하다.

```js
// decorator-augmentation.js
export function withExpiry (client) {
  client.setWithTTL = async function (key, value, ttlMs) {
    await this.set(key, JSON.stringify({ v: value, exp: Date.now() + ttlMs }))
  }
  client.getFresh = async function (key) {
    const raw = await this.get(key)
    if (raw == null) return undefined
    const { v, exp } = JSON.parse(raw)
    if (Date.now() > exp) { await this.del(key); return undefined }
    return v
  }
  return client
}
```

`this`를 통해 기존 메서드를 호출하는 점이 중요하다. 이렇게 하면 데코레이터를 여러 개 겹쳐도 각 계층이 서로의 결과를 볼 수 있다. 예를 들어 압축 데코레이터가 `set`을 재정의했다면, `setWithTTL`은 그 재정의된 `set`을 타게 된다.

단점은 여전히 원본 객체를 오염시킨다는 것과, 이름 충돌 위험이다. 라이브러리가 다음 버전에서 `getFresh`를 추가하면 조용히 덮어써진다. 실무에서는 접두사(`app_`)나 심벌 키로 완화한다.

### 기법 3: 내장 Proxy

`get` 트랩에서 대상에 없는 속성을 요청받으면 데코레이터가 제공하는 구현을 돌려준다.

```js
// decorator-proxy.js
export function withExpiry (client) {
  const extras = {
    async setWithTTL (key, value, ttlMs) {
      return client.set(key, JSON.stringify({ v: value, exp: Date.now() + ttlMs }))
    },
    async getFresh (key) {
      const raw = await client.get(key)
      if (raw == null) return undefined
      const { v, exp } = JSON.parse(raw)
      if (Date.now() > exp) { await client.del(key); return undefined }
      return v
    }
  }

  return new Proxy(client, {
    get: (target, prop, receiver) =>
      prop in extras ? extras[prop] : Reflect.get(target, prop, target),
    has: (target, prop) => prop in extras || Reflect.has(target, prop)
  })
}
```

`has` 트랩까지 구현해야 `'getFresh' in decorated`가 참이 된다. `ownKeys`를 함께 구현하지 않으면 `Object.keys(decorated)`에는 추가 메서드가 나타나지 않는다. 데코레이터를 프록시로 만들 때 자주 빠뜨리는 부분이다.

### 실전 사례: 플러그인 가능한 키-값 클라이언트

세 데코레이터를 겹쳐 하나의 클라이언트를 조립해 보자. 각 데코레이터는 인터페이스를 넓히거나(만료 관리) 기존 동작을 감싼다(압축, 네임스페이스).

```js
// kv-plugins.js
import { gzipSync, gunzipSync } from 'node:zlib'

// 네임스페이스: 키에 접두사를 붙인다(인터페이스 유지 — 사실상 프록시)
export function withNamespace (client, ns) {
  const k = (key) => `${ns}:${key}`
  return Object.create(client, {
    get: { value: (key) => client.get(k(key)) },
    set: { value: (key, v) => client.set(k(key), v) },
    del: { value: (key) => client.del(k(key)) }
  })
}

// 압축: 저장 전 압축, 조회 후 해제(인터페이스 유지)
export function withCompression (client) {
  return Object.create(client, {
    set: {
      value: (key, value) => client.set(key, gzipSync(Buffer.from(value)).toString('base64'))
    },
    get: {
      value: async (key) => {
        const raw = await client.get(key)
        return raw == null ? raw : gunzipSync(Buffer.from(raw, 'base64')).toString()
      }
    }
  })
}

// 통계: 새 메서드를 추가한다(진짜 데코레이터)
export function withStats (client) {
  const stats = { hit: 0, miss: 0 }
  return Object.create(client, {
    get: {
      value: async (key) => {
        const v = await client.get(key)
        v == null ? stats.miss++ : stats.hit++
        return v
      }
    },
    stats: { get: () => ({ ...stats, ratio: stats.hit / (stats.hit + stats.miss || 1) }) }
  })
}

// 조립: 안쪽부터 바깥쪽 순서로 겹친다
const kv = withStats(withCompression(withNamespace(baseClient, 'session')))

await kv.set('u1', JSON.stringify({ name: '민수' }))
console.log(await kv.get('u1'))
console.log(kv.stats)   // { hit: 1, miss: 0, ratio: 1 }
```

`Object.create(client, descriptors)`를 쓰면 대상을 프로토타입에 두고 필요한 메서드만 덮어쓸 수 있어, 합성의 명시성과 증강의 간결함을 절충할 수 있다. 대상이 프라이빗 필드에 의존하지 않고, 재정의한 메서드가 항상 `client`를 클로저로 잡아 호출한다는 조건에서만 안전하다.

조립 순서가 의미를 바꾼다는 점을 유의한다. 위 코드는 압축이 네임스페이스 바깥에 있으므로 키는 평문, 값만 압축된다. 순서를 뒤집으면 압축된 값이 다시 네임스페이스 계층을 지나간다. 데코레이터 스택은 미들웨어 스택(14장 참조)과 같은 방식으로 사고해야 한다.

### 언제 쓰지 말아야 하는가

데코레이터를 세 겹 이상 쌓으면 어떤 계층이 무엇을 했는지 추적이 어려워진다. 오류 스택 트레이스에 익명 함수가 겹겹이 쌓이고, 성능 문제가 생겼을 때 어느 계층 탓인지 알기 어렵다. 계층마다 이름을 부여하고 디버그 로그를 남길 수 없다면 두 겹에서 멈추는 편이 낫다.

또한 데코레이터가 대상의 내부 상태에 의존하기 시작하면 이미 잘못된 설계다. 데코레이터는 공개 인터페이스만 사용해야 한다. 내부 필드를 건드려야 한다면 그 기능은 대상 클래스에 들어가는 편이 옳다.

TC39의 데코레이터 문법(`@decorator`)은 3단계(stage 3)를 거쳐 표준화됐고 TypeScript 5.x가 지원하지만, Node.js 런타임은 자체적으로 이를 실행하지 못한다(v24 기준). 트랜스파일 없이 순수 Node.js로 동작해야 하는 코드에서는 위의 함수형 기법을 쓴다.

## 13.4 프록시와 데코레이터의 경계

### 문제 상황

앞 절의 `withCompression`을 다시 보자. 이것은 프록시인가 데코레이터인가. `get`과 `set`의 시그니처는 그대로이고 새 메서드도 없다. 정의대로라면 프록시다. 그런데 우리는 "압축 기능을 추가했다"고 말한다. 기능을 추가했으니 데코레이터 아닌가.

코드 리뷰에서 이 논쟁이 벌어지고, 파일 이름을 `cacheProxy.js`로 할지 `cacheDecorator.js`로 할지로 30분이 사라진다. 이 혼란은 우연이 아니다. 구조적 원인이 있다.

### 왜 헷갈리는가

첫째, JavaScript에는 인터페이스 선언이 없다. 정적 타입 언어에서는 프록시가 `interface Cache`를 구현하고 데코레이터가 `interface Cache`를 구현하되 메서드를 더 노출한다는 사실이 타입 시그니처에 박제된다. JavaScript에서는 그 경계가 코드 어디에도 적히지 않는다. 실행해 보기 전에는 인터페이스가 넓어졌는지 알 수 없다.

둘째, 구현 기법이 완전히 동일하다. 합성, 증강, `Proxy` 세 기법이 두 패턴에 그대로 적용된다. 코드를 봐서는 구분할 근거가 없고 오직 의도만이 다르다.

셋째, 실무의 래퍼는 대개 둘 다 한다. 재시도 로직을 넣은 HTTP 클라이언트 래퍼는 `request` 시그니처를 유지하면서(프록시적) `retryStats` 같은 속성을 노출한다(데코레이터적). 순수한 프록시나 순수한 데코레이터는 교재에나 있다.

### 판단 기준

두 질문으로 정리한다.

**질문 1: 감싼 객체를 원래 객체 자리에 그대로 넣을 수 있는가?**

넣을 수 있으면 프록시 성질을 갖는다. 호출자 코드를 한 줄도 고치지 않고 래퍼로 교체할 수 있다는 뜻이다. 캐싱, 로깅, 재시도, 접근 제어, 지연 초기화가 여기 속한다.

**질문 2: 호출자가 새로운 무언가를 호출하기 위해 이 래퍼를 쓰는가?**

그렇다면 데코레이터다. 호출자가 `kv.stats`를 읽으려고 `withStats`를 씌웠다면, 래퍼를 벗기는 순간 코드가 깨진다. 교체 가능성이 사라졌으므로 프록시가 아니다.

두 질문을 표로 정리하면 다음과 같다.

| 질문 | 프록시 | 데코레이터 |
| --- | --- | --- |
| 인터페이스 | 동일 | 확장 |
| 대상 자리에 투명 대체 | 가능 | 대체는 되지만 새 기능은 소실 |
| 호출자 코드 수정 필요 | 없음 | 새 기능을 쓰려면 있음 |
| 대표 목적 | 접근 제어, 부가 효과 | 기능 확장 |
| 존재를 감춰도 되는가 | 감춰야 정상 | 드러나야 의미 있다 |

**실무 규칙**: 어느 쪽인지 5초 안에 결론이 안 나면 이름에 패턴명을 넣지 않는다. `cachedUserRepository`, `retryingHttpClient`, `namespacedStore`처럼 무엇을 하는지로 이름 짓는다. 패턴명은 설계를 논의할 때의 어휘이지 파일명 규칙이 아니다.

### 실전 사례: 두 성질이 섞인 래퍼

실제로 섞이는 경우를 어떻게 다루는지 보자.

```js
// 프록시 성질과 데코레이터 성질이 공존하는 래퍼
export function withRetry (client, { attempts = 3, baseDelayMs = 100 } = {}) {
  const metrics = { retries: 0, failures: 0 }

  const wrapped = {
    // 프록시 성질: 시그니처 동일, 투명 대체 가능
    async request (options) {
      let lastError
      for (let i = 0; i < attempts; i++) {
        try {
          return await client.request(options)
        } catch (err) {
          lastError = err
          if (!isRetryable(err) || i === attempts - 1) break
          metrics.retries++
          await sleep(baseDelayMs * 2 ** i)   // 지수 백오프(29장 참조)
        }
      }
      metrics.failures++
      throw lastError
    },
    // 데코레이터 성질: 새 인터페이스
    get retryMetrics () { return { ...metrics } }
  }

  return wrapped
}
```

이 래퍼는 `request`만 쓰는 코드에는 투명하고, 관측이 필요한 코드에는 추가 정보를 준다. 이런 설계는 권장할 만하다. **핵심 인터페이스는 프록시로 유지하고, 부가 정보는 별도 이름으로 덧붙이는 것**이다. 이렇게 하면 래퍼를 벗기거나 다른 래퍼로 교체할 때 영향 범위가 부가 기능 사용처로 한정된다.

반대로 피해야 할 설계는 기존 메서드의 시그니처를 조용히 바꾸는 것이다. `get(key)`를 `get(key, options)`로 확장하면 겉보기에는 하위 호환이지만, 그 래퍼를 통과하는 코드와 통과하지 않는 코드가 서로 다르게 동작하기 시작한다. 이때는 새 메서드 이름을 쓰는 편이 정직하다.

### 언제 쓰지 말아야 하는가

패턴 구분에 시간을 쓰는 것 자체가 낭비인 경우가 대부분이다. 다음 상황에서는 논쟁을 멈추고 코드를 쓴다. 래퍼가 한 개뿐이고 한 곳에서만 쓰일 때, 감싸는 대상이 우리 코드라 직접 고칠 수 있을 때, 래핑 계층을 만드는 이유가 "언젠가 교체할지도 모르니까"뿐일 때다. 마지막 경우는 특히 흔한 과잉 설계다. 실제 교체 요구가 생겼을 때 래퍼를 넣어도 늦지 않다.

## 13.5 어댑터: 인터페이스 맞추기

### 문제 상황

이미 작성한 코드가 `fs` 모듈의 인터페이스(`readFile`, `writeFile`)를 기대한다. 그런데 데이터를 파일 시스템이 아니라 키-값 저장소에 두고 싶다. 코드를 다시 쓸 수는 없다. 테스트 코드도, 유틸리티도 전부 `fs` 모양을 전제하고 있다.

혹은 반대 상황이다. 세 가지 로거 라이브러리를 쓰는 세 팀의 코드를 하나의 서비스로 합쳤다. `pino`는 `logger.info(obj, msg)`, `winston`은 `logger.info(msg, meta)`, 자체 구현은 `logger.log('info', msg)`다. 공통 관측 계층을 만들려면 셋을 하나로 봐야 한다.

### 패턴의 정의

어댑터(adapter)는 한 객체의 인터페이스를 다른 인터페이스로 변환한다. 프록시와 데코레이터가 "같은 인터페이스를 유지하거나 넓힌다"면, 어댑터는 **인터페이스를 다른 모양으로 바꾼다**. 대상이 할 수 있는 일의 총량은 대개 줄어든다. 목표 인터페이스가 요구하는 만큼만 노출하기 때문이다.

어댑터는 세 패턴 중 유일하게 "감싼 객체와 겉모습이 다른" 패턴이다. 그래서 실무에서 가장 덜 헷갈린다.

### 구현 코드: 키-값 저장소를 fs처럼 쓰기

```js
// fs-adapter.js — LevelDB 스타일 저장소를 fs API 모양으로 변환한다
import { resolve } from 'node:path'

export function createFsAdapter (db) {
  return {
    async readFile (filename, options = {}) {
      const encoding = typeof options === 'string' ? options : options.encoding
      let value
      try {
        value = await db.get(resolve(filename))
      } catch (err) {
        if (err.code === 'LEVEL_NOT_FOUND') {
          // 호출자가 기대하는 오류 모양으로 번역하는 것이 어댑터의 핵심이다
          const e = new Error(`ENOENT: no such file or directory, open '${filename}'`)
          e.code = 'ENOENT'
          e.errno = -2
          e.path = filename
          throw e
        }
        throw err
      }
      const buf = Buffer.from(value)
      return encoding ? buf.toString(encoding) : buf
    },

    async writeFile (filename, contents, options = {}) {
      const encoding = typeof options === 'string' ? options : options.encoding
      const buf = Buffer.isBuffer(contents)
        ? contents
        : Buffer.from(String(contents), encoding ?? 'utf8')
      await db.put(resolve(filename), buf)
    },

    async unlink (filename) {
      await db.del(resolve(filename))
    }
  }
}
```

이 구현에서 가장 중요한 부분은 오류 번역이다. 인터페이스를 맞춘다는 것은 시그니처만 맞추는 게 아니라 **실패 방식까지 맞추는 것**이다. 호출자는 `err.code === 'ENOENT'`로 분기할 것이고, 저장소의 `LEVEL_NOT_FOUND`를 그대로 흘려보내면 어댑터는 무용지물이 된다. 어댑터 작성 시간의 절반은 오류 매핑에 들어간다고 봐도 된다.

### 구현 코드: 콜백 라이브러리를 프로미스로

Node.js에서 가장 자주 쓰이는 어댑터다. 콜백 규약(error-first callback)을 프로미스 인터페이스로 바꾼다. `node:util`의 `promisify`가 표준 도구다(5장 참조).

```js
import { promisify } from 'node:util'
import legacy from 'legacy-driver'

const query = promisify(legacy.query.bind(legacy))
const rows = await query('SELECT 1')
```

`promisify`가 통하지 않는 경우도 많다. 콜백이 마지막 인자가 아니거나, 콜백이 여러 값을 넘기거나, 오류를 첫 인자로 주지 않는 라이브러리다. 이때는 직접 어댑터를 쓴다.

```js
// 콜백이 (result, error) 순서인 비표준 라이브러리를 감싼다
function adaptQuery (driver) {
  return (sql, params) => new Promise((resolve, reject) => {
    driver.query(sql, params, (result, error) => {
      if (error) reject(Object.assign(new Error(error.message), { code: error.code }))
      else resolve(result)
    })
  })
}
```

객체 전체를 한 번에 변환하려면 `Proxy`가 유용하다. 어떤 메서드가 있는지 미리 몰라도 되기 때문이다.

```js
// 모든 메서드를 프로미스 인터페이스로 바꾸는 어댑터
export function promisifyAll (target) {
  const cache = new Map()
  return new Proxy(target, {
    get (obj, prop) {
      const value = Reflect.get(obj, prop, obj)
      if (typeof value !== 'function') return value
      if (!cache.has(prop)) cache.set(prop, promisify(value.bind(obj)))
      return cache.get(prop)
    }
  })
}
```

`Map` 캐시가 없으면 접근마다 새 함수가 생성되어, 이벤트 핸들러 등록과 해제가 짝이 맞지 않는 버그가 생긴다.

### 구현 코드: 여러 로거를 하나의 인터페이스로

```js
// logger-adapter.js
const LEVELS = ['debug', 'info', 'warn', 'error']

export function adaptPino (pino) {
  return Object.fromEntries(
    LEVELS.map((lv) => [lv, (msg, fields = {}) => pino[lv](fields, msg)])
  )
}

export function adaptWinston (winston) {
  return Object.fromEntries(
    LEVELS.map((lv) => [lv, (msg, fields = {}) => winston[lv](msg, fields)])
  )
}

export function adaptLegacy (legacy) {
  return Object.fromEntries(
    LEVELS.map((lv) => [lv, (msg, fields = {}) => {
      legacy.log(lv, fields && Object.keys(fields).length
        ? `${msg} ${JSON.stringify(fields)}`
        : msg)
    }])
  )
}

// 애플리케이션 전역에서는 항상 이 모양만 본다: log.info('요청 처리', { reqId })
```

세 어댑터 모두 `{ debug, info, warn, error }`라는 동일한 목표 인터페이스를 제공한다. 애플리케이션 코드는 어떤 라이브러리가 뒤에 있는지 모른 채 동작하고, 로거를 교체할 때 어댑터 파일 하나만 바꾸면 된다. 의존성 주입(12장 참조)과 결합하면 테스트에서 메모리 배열에 쌓는 어댑터로 갈아끼우기도 쉽다.

### 실전 사례: 스토리지 추상화

프로덕션에서 어댑터가 가장 값어치를 하는 지점은 개발 환경과 운영 환경의 저장소가 다를 때다. 운영은 S3, 개발은 로컬 디스크, 테스트는 메모리를 쓰되 애플리케이션 코드는 `storage.put(key, buffer)` / `storage.get(key)` 하나만 안다. 세 어댑터를 만들고 환경 변수로 선택하면, 통합 테스트에서 네트워크 없이 전체 흐름을 검증할 수 있다.

이때 주의할 점은 목표 인터페이스를 **가장 제약이 심한 백엔드에 맞춰 설계**해야 한다는 것이다. 로컬 파일 시스템의 원자적 이름 변경(atomic rename)을 전제로 인터페이스를 만들면 S3 어댑터가 그 의미를 흉내 낼 수 없다. 반대로 S3의 최종 일관성(eventual consistency)을 전제로 만들면 모든 백엔드가 구현할 수 있다.

### 언제 쓰지 말아야 하는가

어댑터는 인터페이스를 하나 더 만드는 일이므로 유지 비용이 발생한다. 백엔드가 하나뿐이고 바뀔 계획이 없다면 어댑터 계층은 순수한 부채다. 대상 라이브러리의 API를 그냥 쓰는 편이 낫다.

또한 어댑터가 대상 인터페이스의 의미를 왜곡하기 시작하면 위험하다. 트랜잭션을 지원하지 않는 저장소를 트랜잭션이 있는 인터페이스로 어댑팅하면, 호출자는 롤백이 된다고 믿지만 실제로는 되지 않는다. 어댑터가 흉내 낼 수 없는 보장은 목표 인터페이스에서 빼야 한다. 불가능한 메서드는 `NotSupportedError`를 던지는 편이 조용히 반쯤 동작하는 것보다 훨씬 낫다.

## 13.6 실전 사례 분석

### Express: res 객체 증강

Express의 미들웨어 체인에서 `res.json()`, `res.status()`, `res.redirect()`를 쓸 수 있는 이유는 Express가 Node.js의 `http.ServerResponse` 인스턴스를 증강하기 때문이다. Express는 응답 객체마다 새 클래스를 만들지 않는다. 요청이 들어오면 `res`의 프로토타입을 Express가 준비한 객체로 교체한다.

```js
// Express 내부 로직의 요지
res.__proto__ = app.response      // 프로토타입 체인에 Express 메서드를 끼워 넣는다
req.__proto__ = app.request
```

`app.response` 자체가 `http.ServerResponse.prototype`을 상속하므로, 원래 메서드(`writeHead`, `end`)는 그대로 살아 있고 Express 메서드가 추가된다. 즉 **프로토타입 수준의 데코레이터**다. 인스턴스마다 수십 개 메서드를 복사하는 비용을 피하면서 인터페이스를 넓힌다.

이 설계 덕분에 서드파티 미들웨어도 같은 방식으로 기능을 더할 수 있다. `res.cookie`는 `cookie-parser`가 아니라 Express 본체가 제공하지만, 많은 미들웨어가 `res.locals`에 값을 얹거나 `res` 자체에 헬퍼를 붙인다. 대가는 이름 충돌이다. 두 미들웨어가 같은 이름의 헬퍼를 붙이면 나중에 등록된 쪽이 이긴다. Fastify가 `decorate()` API에서 중복 이름을 명시적으로 거부하는 이유가 이것이다.

### undici: 인터셉터와 디스패처

`undici`는 Node.js의 내장 HTTP 클라이언트 구현이다. `fetch()`의 실체이기도 하다. undici는 요청 파이프라인 확장에 프록시 패턴을 정면으로 쓴다.

```js
import { Agent, interceptors, setGlobalDispatcher } from 'undici'

const dispatcher = new Agent().compose(
  interceptors.retry({ maxRetries: 3 }),
  interceptors.redirect({ maxRedirections: 5 }),
  interceptors.cache()
)
setGlobalDispatcher(dispatcher)
```

`compose()`는 디스패처를 인터셉터로 겹겹이 감싼다. 각 인터셉터는 `dispatch(options, handler)`라는 동일한 시그니처를 유지하면서 재시도, 리디렉션 추적, 캐시 조회를 끼워 넣는다. 인터페이스가 그대로이므로 프록시이고, 스택으로 조립되므로 미들웨어이며, 사용자는 `fetch`를 평소처럼 쓰면서 동작만 바뀐다.

이 구조가 좋은 이유는 각 인터셉터가 독립적으로 테스트 가능하고, 순서를 바꿔 의미를 조정할 수 있다는 점이다. 캐시를 재시도 안쪽에 두면 캐시 미스만 재시도되고, 바깥에 두면 재시도 결과가 캐시된다.

### OpenTelemetry: 자동 계측은 몽키 패칭이다

분산 추적을 도입할 때 가장 놀라운 점은 애플리케이션 코드를 한 줄도 고치지 않아도 HTTP 요청, 데이터베이스 쿼리, 큐 발행에 스팬(span)이 붙는다는 것이다. 이 마법의 정체가 몽키 패칭이다.

```js
// instrumentation.js — 애플리케이션보다 먼저 로드되어야 한다
import { NodeSDK } from '@opentelemetry/sdk-node'
import { getNodeAutoInstrumentations } from '@opentelemetry/auto-instrumentations-node'

const sdk = new NodeSDK({ instrumentations: [getNodeAutoInstrumentations()] })
sdk.start()
```

```bash
node --import ./instrumentation.js app.js
```

내부에서 벌어지는 일은 이렇다. OpenTelemetry는 모듈 로딩을 가로채는 훅(`require-in-the-middle`, ESM에서는 `import-in-the-middle`)을 설치한다. 애플리케이션이 `node:http`를 로드하면, 훅이 원본 모듈을 받아 `http.request`와 `http.Server.prototype.emit`을 계측 버전으로 교체한 뒤 애플리케이션에 넘긴다. 계측 버전은 스팬을 시작하고, 추적 헤더를 주입하고, 원본을 호출하고, 응답이 끝나면 스팬을 종료한다. `pg`, `ioredis`, `mysql2` 계측도 원리가 같다. 각 드라이버의 쿼리 메서드를 감싼다.

여기서 몽키 패칭의 세 가지 전제 조건을 확인할 수 있다. 첫째, **로드 순서가 결정적이다.** 애플리케이션이 먼저 모듈을 잡아 두면 패치가 늦어 아무 효과가 없다. `--import`나 `--require`로 먼저 실행해야 하는 이유다. 둘째, **대상 라이브러리의 내부 구조에 결합된다.** 드라이버가 내부 함수 이름을 바꾸면 계측이 조용히 실패한다. 그래서 계측 패키지는 지원하는 버전 범위를 명시하고 범위 밖이면 패치를 건너뛴다. 셋째, **비동기 컨텍스트가 필요하다.** 패치한 함수에서 시작한 스팬을 콜백 안에서 이어가려면 `AsyncLocalStorage`가 있어야 한다(31장 참조). 이 API가 없던 시절의 APM들이 도메인(domain) 모듈이나 `async_hooks`에 의존해 불안정했던 이유다.

### 세 사례가 말하는 것

Express는 프로토타입 교체로 인터페이스를 넓히고(데코레이터), undici는 동일 인터페이스를 유지한 채 파이프라인을 겹치며(프록시), OpenTelemetry는 남의 모듈을 실행 시점에 바꿔치기한다(객체 증강). 세 프로젝트 모두 "감싸는 객체"라는 같은 도구를 쓰면서 목적에 따라 다른 기법을 골랐다.

공통점도 있다. 셋 다 감싸는 계층이 실패해도 원본 동작이 유지되도록 설계했다는 점이다. OpenTelemetry의 계측이 예외를 던져도 HTTP 요청 자체는 성공해야 한다. 부가 계층은 본질 기능보다 항상 덜 중요하다는 원칙이 구조 패턴 구현의 마지막 규칙이다.

## 요약

- 프록시는 대상과 동일한 인터페이스를 유지하며 접근을 제어한다. JavaScript에서는 객체 합성, 객체 증강(몽키 패칭), 내장 `Proxy` 세 기법으로 구현하며, 각각 오염 범위와 성능 특성이 다르다.
- 내장 `Proxy`는 `get`/`set`/`has`/`deleteProperty`/`apply` 트랩으로 근본 연산을 가로챈다. 대신 V8의 인라인 캐시 최적화를 무력화하므로 뜨거운 경로에서는 수 배 이상 느려질 수 있고, 객체 동일성도 깨진다.
- 프라이빗 필드를 쓰는 클래스를 프록시로 감쌀 때는 `Reflect.get(target, prop, target)`처럼 `this`를 대상에 묶어야 한다. 프록시 기반 래핑의 가장 흔한 버그가 이 지점에서 발생한다.
- 변경 관찰자는 `set`/`deleteProperty` 트랩으로 대입문 자체를 이벤트로 만든다. 중첩 객체는 `get` 시점에 지연 방식으로 감싸고 `WeakMap`으로 캐시해야 하며, 배열은 `length` 변경이라는 추가 통지를 낳는다. Vue 3와 MobX가 이 원리를 쓴다.
- 데코레이터는 인터페이스를 넓힌다는 점에서 프록시와 다르다. 상속과 달리 런타임에 인스턴스 단위로 조합되므로 조합 폭발을 피할 수 있고, 스택 순서가 의미를 바꾼다.
- 두 패턴이 헷갈리면 "래퍼를 벗겨도 호출자 코드가 동작하는가"로 판단한다. 동작하면 프록시, 깨지면 데코레이터다. 결론이 빨리 나지 않으면 패턴명 대신 하는 일로 이름 짓는다.
- 어댑터는 인터페이스를 다른 모양으로 바꾼다. 시그니처뿐 아니라 오류 코드와 실패 방식까지 목표 인터페이스에 맞춰야 하며, 목표 인터페이스는 가장 제약이 심한 백엔드 기준으로 설계한다.

## 연습문제

1. 13.1절의 로깅 `Writable` 프록시를 세 가지 기법으로 각각 구현하고, `pipeline()`으로 1GiB 파일을 복사하며 처리량을 측정하라. `Proxy` 구현에서 `value.bind(target)` 결과를 `WeakMap`에 캐시했을 때와 하지 않았을 때의 차이도 함께 비교하고, 어느 기법을 프로덕션에 선택할지 근거와 함께 서술하라.

2. 13.2절의 `createDeepObservable`을 확장해 배열 변경을 의미 단위 이벤트로 통지하도록 만들어라. `push`, `pop`, `splice`, `sort`, `length = 0`을 각각 하나의 이벤트로 보고해야 하며, 순환 참조가 있는 객체에서도 무한 재귀에 빠지지 않아야 한다. 구현 후 원소 10,000개 배열에 대한 `sort()` 호출에서 통지 횟수와 소요 시간을 측정하라.

3. 인메모리, 로컬 디스크, S3 호환 저장소 세 가지를 지원하는 스토리지 어댑터를 설계하라. 목표 인터페이스는 `put`, `get`, `delete`, `list` 네 메서드로 하되, 각 백엔드가 흉내 낼 수 없는 보장(원자적 이름 변경, 즉시 일관성, 디렉터리 개념)을 식별해 인터페이스에서 제외하고 그 판단 근거를 문서화하라. 세 어댑터가 동일한 통합 테스트 스위트를 통과하는지 확인하라.
