# 21장. 왜 분산인가

여기까지 우리는 하나의 Node.js 프로세스 안에서 할 수 있는 거의 모든 것을 다뤘다. 이벤트 루프를 이해했고, 스트림으로 메모리를 아꼈고, 패턴으로 구조를 정리했고, 라우팅·인증·데이터베이스를 붙여 실제로 동작하는 웹 서비스를 만들었다.

6부는 그 프로세스 바깥으로 나간다. 그런데 나가기 전에 두 가지를 정직하게 확인해야 한다. 첫째, 프로세스 하나로는 왜 부족한가. 둘째, 프로세스를 여러 개로 쪼개는 순간 무엇을 잃는가.

두 번째 질문이 이 장의 무게중심이다. 분산 시스템에 관한 대부분의 자료는 이득만 이야기하지만, 실무에서 사람을 지치게 만드는 것은 언제나 대가 쪽이다. 이 장을 마치면 "분산해야 하는가"를 근거를 들어 판단할 수 있고, 6부부터 8부까지 우리가 발전시킬 예제 시스템의 전체 지도를 갖게 된다.

## 21.1 단일 프로세스의 한계

### 코어 하나만 쓴다

Node.js 프로세스에서 JavaScript는 단일 스레드로 실행된다(3장 참조). 이 사실이 용량 산정에서 갖는 의미는 단순하다. **16코어 머신에서 프로세스 하나를 띄우면 CPU의 6.25%만 쓸 수 있다.** libuv 스레드 풀과 GC 스레드가 다른 코어를 조금 쓰지만, 애플리케이션 로직이 실행되는 코어는 여전히 하나다.

이 한계가 장애로 나타나는 형태는 특징적이다. 모니터링 대시보드에는 CPU 사용률 10%가 찍혀 있는데 p99 응답 시간이 2초를 넘는다. 운영자는 "서버에 여유가 넘치는데 왜 느린가"라고 묻는다. 실제로는 그 10%가 한 코어의 100%이고, 이벤트 루프 큐에 요청이 쌓여 있는 상태다. 호스트 단위 CPU 지표만 보면 이 상황은 영원히 보이지 않는다. 이벤트 루프 지연(`perf_hooks.monitorEventLoopDelay`)을 함께 보지 않으면 진단 자체가 불가능하다(31장 참조).

수치로 보면 더 분명하다. 요청 하나가 CPU를 5밀리초 쓰는 핸들러라면 단일 프로세스의 이론적 상한은 초당 200건이다. 코어가 16개인 머신을 쓰든 64개인 머신을 쓰든 이 숫자는 변하지 않는다. 세로 확장으로 얻을 수 있는 것은 코어 하나의 클럭 향상뿐이며, 그것은 기껏해야 수십 퍼센트다.

### 힙에는 천장이 있다

V8의 old space에는 상한이 있고, 그 상한은 물리 메모리에서 유도된다. 정확한 값은 버전과 머신에 따라 다르므로 짐작하지 말고 직접 확인하는 습관이 낫다.

```bash
# 이 머신에서 실제로 적용된 힙 한도(MB)를 확인한다
node -e "console.log(require('node:v8').getHeapStatistics().heap_size_limit / 1024 / 1024)"

# 명시적으로 지정한다 (컨테이너 메모리 한도의 70~80%가 출발점)
node --max-old-space-size=1536 server.js
```

여기서 컨테이너가 함정을 만든다. Node.js는 오랫동안 cgroup 메모리 한도가 아니라 **호스트의 전체 메모리**를 기준으로 힙 상한을 계산했다. 64GB 호스트에서 메모리 한도 512MB로 실행되는 컨테이너 안의 Node.js는 자기가 수 GB를 써도 된다고 믿는다. 결과는 두 가지 서로 다른 죽음이다. V8이 스스로 한계를 인지하면 `FATAL ERROR: Reached heap limit Allocation failed`를 남기고 죽지만, 커널이 먼저 개입하면 로그 한 줄 없이 종료 코드 137(SIGKILL)로 사라진다. 후자는 애플리케이션 로그에 아무 흔적이 없어서 원인 파악에 며칠이 걸리기도 한다. `--max-old-space-size`를 명시하는 것만으로 이 부류의 사고 대부분이 사라진다.

힙이 크다고 좋은 것도 아니다. old space가 4GB까지 자라면 메이저 GC 한 번의 정지 시간이 수백 밀리초에 달할 수 있다. 그동안 이벤트 루프는 완전히 멈춘다. 4GB 힙 하나보다 1GB 힙 네 개가 응답 시간 분포 측면에서 거의 항상 낫다.

### 파일 디스크립터와 커넥션

프로세스가 열 수 있는 파일 디스크립터 수는 `ulimit -n`으로 제한되며, 여전히 1024가 기본인 배포판이 많다. 소켓, 로그 파일, DB 커넥션 풀, 감시 중인 파일이 모두 이 예산을 나눠 쓴다. 한계에 닿으면 `EMFILE`이 발생하고, `accept` 루프가 실패를 반복하며 CPU만 태우는 상태에 빠진다. 프로덕션에서는 `LimitNOFILE=65535` 이상으로 올려 두는 것이 사실상 표준이다.

### 배포는 곧 다운타임이다

프로세스가 하나면 배포는 정의상 전면 중단이다. 코드를 바꾸고 재시작하는 데 Node.js 부팅 1초, 커넥션 풀 준비 1초, 캐시 워밍 3초가 걸린다면 배포 한 번에 5초의 다운타임이 생긴다. 하루 20회 배포하는 팀이라면 월 50분, 연간 10시간이다. 이 숫자 하나만으로 99.9% 가용성 목표(연간 8.76시간 다운타임 허용)는 이미 달성 불가능하다.

### 모든 것이 단일 장애점이다

프로세스가 하나면 그 프로세스에서 일어나는 모든 사고가 전면 장애다. 처리되지 않은 예외 하나, 백트래킹이 폭발하는 정규식 하나(ReDoS), 어느 라우트의 메모리 누수 하나, 무한 루프에 빠진 동기 코드 하나가 전체 서비스를 멈춘다. 관리자 페이지의 CSV 내보내기 기능이 이벤트 루프를 8초 막으면, 그 8초 동안 결제 API도 함께 죽는다. 기능 사이의 **장애 격리(fault isolation)** 가 존재하지 않는다는 것이 단일 프로세스의 가장 근본적인 약점이다.

이 다섯 가지 한계 중 앞의 셋은 세로 확장(더 큰 머신)으로 어느 정도 미룰 수 있다. 그러나 뒤의 둘 — 무중단 배포와 장애 격리 — 은 머신을 아무리 키워도 해결되지 않는다. **프로세스를 늘리는 것 외에 방법이 없다.** 분산의 출발점은 성능이 아니라 여기다.

## 21.2 분산이 가져오는 새로운 문제들

프로세스를 늘리는 순간, 우리는 함수 호출을 네트워크 호출로 바꾼 것이 아니라 **문제의 종류를 바꾼** 것이다.

### 부분 실패: 성공도 실패도 아닌 제3의 상태

단일 프로세스에서 함수 호출의 결과는 두 가지다. 값을 반환하거나 예외를 던진다. 어느 쪽이든 호출자는 무슨 일이 일어났는지 안다.

네트워크 호출의 결과는 세 가지다. 성공, 실패, 그리고 **모름**. 타임아웃이 났을 때 요청이 상대에게 도달하지 않은 것인지, 도달해서 처리까지 끝났는데 응답만 유실된 것인지 호출자는 구분할 수 없다. 이 구분 불가능성이 실무에서 만드는 문제가 중복 처리다. "결제 요청이 타임아웃 났으니 재시도한다"는 판단이 이중 청구를 만든다. 그래서 분산 시스템의 모든 쓰기 연산은 **멱등(idempotent)** 하게 설계되거나, 멱등 키로 중복을 걸러내야 한다(29장 참조). 읽기만 하던 시절에는 존재하지 않던 요구사항이다.

부분 실패는 시스템의 상태 공간도 폭발시킨다. 서비스 5개가 각각 정상/느림/죽음의 세 상태를 가지면 조합은 243가지다. 이 중 대부분은 테스트되지 않은 상태이며, 장애는 거의 언제나 그 테스트되지 않은 조합에서 발생한다.

### 분산 컴퓨팅의 여덟 가지 오류

피터 도이치(Peter Deutsch)와 제임스 고슬링(James Gosling)이 정리한 목록은 40년 가까이 지난 지금도 그대로 유효하다. 각 항목은 "우리가 무심코 참이라고 가정하는 명제"이며, 모두 거짓이다.

1. **네트워크는 신뢰할 수 있다.** 패킷은 유실되고 연결은 끊긴다. 클라우드 환경에서 인스턴스는 예고 없이 회수된다.
2. **지연은 0이다.** 인프로세스 함수 호출은 나노초 단위지만, 같은 데이터센터 안의 HTTP 왕복도 밀리초 단위다. 대략 10만 배 차이다.
3. **대역폭은 무한하다.** 응답에 필요 없는 필드를 담으면 그대로 비용이 된다. 목록 API가 항목당 2KB를 반환하면 1,000개 목록은 2MB이고, 이것이 초당 100회면 1.6Gbps다.
4. **네트워크는 안전하다.** 내부 네트워크도 안전하지 않다. 서비스 간 통신에도 TLS와 인증이 필요하다(22장 참조).
5. **토폴로지는 변하지 않는다.** 오토스케일링과 재배포로 IP는 계속 바뀐다. 주소를 하드코딩하는 순간 실패한다(26장 참조).
6. **관리자는 한 명이다.** 서비스마다 담당 팀이 다르면 배포 일정도, 장애 대응 속도도 다르다.
7. **전송 비용은 0이다.** 직렬화·역직렬화의 CPU 비용과 리전 간 트래픽 요금은 실재한다.
8. **네트워크는 균질하다.** 프로토콜, 인코딩, 버전이 서로 다른 시스템이 섞인다.

목록을 외울 필요는 없다. 다만 설계 리뷰에서 "이 가정이 깨지면 어떻게 되는가"를 묻는 체크리스트로는 대단히 유용하다.

### 지연, 일관성, 디버깅

**지연은 반드시 늘어난다.** 인프로세스 함수 호출을 HTTP 호출로 바꾸면 직렬화, 소켓 쓰기, 커널 컨텍스트 스위치, 네트워크 전송, 역직렬화가 추가된다. 같은 호스트의 루프백이라도 왕복 0.2~0.5밀리초, 같은 가용 영역이면 0.5~1밀리초, 리전이 다르면 수십에서 100밀리초를 넘긴다. 이 비용은 호출 횟수만큼 곱해진다.

**일관성이 깨진다.** 단일 프로세스에서 `Map`에 값을 넣고 바로 읽으면 항상 방금 넣은 값이 나온다. 인스턴스 세 대가 각자 캐시를 들고 있으면, 방금 수정한 데이터를 다시 조회했을 때 예전 값이 나올 수 있다. 사용자에게는 "저장했는데 반영이 안 된다"는 버그로 보인다. 이를 막으려면 캐시 무효화 전략, 세션 고정, 또는 공유 저장소가 필요하고, 셋 다 새로운 복잡도다(15장, 24장 참조).

**디버깅 난이도가 질적으로 달라진다.** 스택 트레이스는 프로세스 경계에서 끊긴다. web-api 로그의 "502 upstream_unavailable"과 recipe-api 로그의 "connection reset"이 같은 사건인지 확인하려면, 두 로그를 시각으로 대조해야 한다. 요청이 다섯 서비스를 거치면 이 대조는 사람이 할 수 있는 일이 아니게 된다. 상관 ID(correlation ID)와 분산 추적이 선택이 아니라 필수가 되는 지점이다(31장 참조).

**운영 비용이 서비스 수에 비례해 늘어난다.** 서비스 하나를 추가한다는 것은 저장소 하나, CI 파이프라인 하나, 배포 설정 하나, 대시보드 하나, 알림 규칙 하나, 온콜 문서 하나, 그리고 그것을 아는 사람이 필요하다는 뜻이다. 이 비용은 코드가 아니라 조직이 지불한다.

### 그래서: 모놀리스로 충분한지 먼저 물어라

이 조언은 보수적인 취향의 문제가 아니라 계산의 문제다. 근거는 셋이다.

첫째, **성능 문제 대부분은 분산 없이 해결된다.** 단일 프로세스의 CPU 한계는 `cluster`나 프로세스 매니저로 같은 코드를 코어 수만큼 띄우면 사라진다(25장 참조). 이것은 코드를 쪼개는 것이 아니라 복제하는 것이므로, 21.2에서 나열한 문제 중 어느 것도 발생하지 않는다. 16코어 머신에서 처리량이 16배가 되기까지는 분산 아키텍처가 필요하지 않다.

둘째, **분산의 진짜 동기는 대개 기술이 아니라 조직이다.** 서비스를 쪼갤 만한 정당한 이유는 독립 배포(팀 A가 팀 B를 기다리지 않는다), 장애 격리(리포트 생성이 결제를 죽이지 않는다), 이질적 자원 요구(이미지 처리에는 CPU가, 알림 발송에는 대기 커넥션이 필요하다), 그리고 서로 다른 확장 곡선이다. 이 중 어느 것도 해당하지 않는데 쪼갠다면, 비용만 지불하고 이득은 없다.

셋째, **경계를 잘못 그으면 되돌리기가 매우 비싸다.** 모놀리스 안에서 모듈 경계를 옮기는 것은 리팩터링이지만, 서비스 경계를 옮기는 것은 데이터 마이그레이션과 API 버전 관리와 두 팀의 배포 조율이다. 도메인 이해가 얕은 초기에 경계를 확정하는 것은 가장 비싼 실수다. 27장에서 이 분해 기준을 본격적으로 다룬다.

실용적인 판단 기준 하나. **모놀리스를 잘 운영하지 못하는 팀은 마이크로서비스도 운영하지 못한다.** 구조화 로깅, 메트릭, 자동화된 배포, 헬스 체크가 없는 상태에서 서비스를 쪼개면, 관측되지 않는 프로세스가 여러 개로 늘어날 뿐이다.

## 21.3 서비스 관계 모델링: 프로듀서와 컨슈머

### 역할은 고정된 정체성이 아니다

분산 시스템을 설명할 때 흔히 "클라이언트"와 "서버"라는 말을 쓰지만, 서비스가 여럿이면 이 용어는 금방 무너진다. 대신 관계 단위로 이름을 붙인다. 어떤 호출에서 데이터를 제공하는 쪽이 **프로듀서(producer)**, 요청하는 쪽이 **컨슈머(consumer)** 다.

핵심은 이것이 서비스의 속성이 아니라 **호출 관계의 속성**이라는 점이다. web-api는 브라우저에 대해서는 프로듀서이고 recipe-api에 대해서는 컨슈머다. 서비스가 열 개쯤 되면 이 관계는 방향이 있는 그래프가 되며, 아키텍처 문서에서 실제로 유용한 것은 서비스 목록이 아니라 이 그래프다. 그래프에 순환이 있는가(A가 B를, B가 A를 호출하는가)는 배포 순서와 장애 전파를 결정하는 결정적인 질문이다.

### 가용성은 곱해진다

동기 호출 사슬의 가장 중요한 성질은 가용성이 더해지지 않고 **곱해진다**는 것이다. 컨슈머가 요청 하나를 처리하기 위해 프로듀서 N개를 순차 호출하고, 그중 하나라도 실패하면 전체가 실패한다면, 종단 가용성은 각 서비스 가용성의 곱이다.

| 직렬 호출 서비스 수 | 개별 가용성 99.9%일 때 종단 가용성 | 연간 다운타임 |
|---|---|---|
| 1 | 99.900% | 8.8시간 |
| 2 | 99.800% | 17.5시간 |
| 3 | 99.700% | 26.3시간 |
| 4 | 99.601% | 35.0시간 |
| 5 | 99.501% | 43.7시간 |

각 서비스가 "세 개의 9"라는 훌륭한 수치를 지켜도, 다섯 개를 직렬로 엮으면 시스템은 43시간을 멈춘다. 여기에는 각 서비스를 잇는 네트워크의 신뢰도가 아직 포함되지도 않았다.

여기서 나오는 설계 원칙은 명확하다. **요청 경로의 동기 의존성 수를 줄여라.** 방법은 넷이다. 호출을 병렬화해서 지연을 줄이고(가용성 자체는 개선되지 않는다), 응답을 캐시해서 프로듀서 장애 시에도 오래된 값을 제공하고, 의존성을 필수와 선택으로 분류해 선택 의존성이 죽어도 축약된 응답을 내보내며(graceful degradation), 응답이 즉시 필요 없는 작업은 아예 메시지 큐로 밀어내 동기 사슬에서 제거한다(23장 참조).

세 번째 항목이 특히 중요하다. 추천 서비스가 죽었다고 상품 상세 페이지 전체가 502를 반환할 이유는 없다. "이 프로듀서가 죽으면 응답의 어느 부분이 사라지는가"를 의존성마다 미리 답해 두는 것만으로 종단 가용성이 극적으로 개선된다.

또 하나 기억할 것은 이 곱셈이 **의존성 그래프의 깊이를 따라 누적된다**는 점이다. web-api가 recipe-api 하나만 호출하더라도, recipe-api가 내부적으로 캐시와 데이터베이스와 인증 서비스를 동기 호출한다면 web-api의 실질 의존성은 넷이다. 컨슈머 입장에서는 보이지 않는 이 깊이가 종단 가용성을 결정하므로, 서비스 계약에 "이 API는 어떤 것들에 의존하는가"를 명시하는 팀이 결국 장애를 덜 겪는다.

### 팬아웃, 팬인, 요청 증폭

컨슈머가 여러 프로듀서에게 동시에 요청을 보내는 것을 **팬아웃(fan-out)**, 그 응답들을 모아 하나로 합치는 것을 **팬인(fan-in)** 이라고 한다. API 게이트웨이나 BFF(Backend For Frontend)의 기본 동작이다.

팬아웃에서 조심할 것은 **요청 증폭(request amplification)** 이다. web-api가 레시피 하나를 반환하기 위해 recipe-api를 1회, 재료 정보를 재료 수만큼, 작성자 정보를 1회 호출한다고 하자. 재료가 10개면 외부 요청 1건이 내부 요청 12건이 된다. 사용자 트래픽이 초당 1,000건이면 내부 네트워크에는 초당 12,000건이 흐른다. 프런트엔드 팀이 화면에 항목을 몇 개 더 노출하기로 결정하는 것만으로 내부 부하가 배로 뛰는 구조이며, 이런 시스템은 캐시가 식는 순간 자기 자신을 무너뜨린다.

두 번째로 조심할 것은 **꼬리 지연 증폭**이다. 프로듀서 한 개의 p99가 100밀리초라고 하자. 팬아웃으로 10개를 병렬 호출하고 전부 기다린다면, 적어도 하나가 p99 구간에 걸릴 확률은 `1 - 0.99^10`, 약 9.6%다. 즉 **개별 서비스의 p99가 통합 응답의 p90이 된다.** 병렬 호출은 지연의 합을 최댓값으로 바꿔주지만, 그 최댓값은 호출 수가 늘수록 나빠진다.

```js
// web-api: 팬아웃 후 팬인. 필수/선택 의존성을 구분한다
async function buildRecipeView(id, signal) {
  const [recipe, author, related] = await Promise.allSettled([
    fetchJSON(`${RECIPE_API}/recipes/${id}`, signal),   // 필수
    fetchJSON(`${USER_API}/authors/${id}`, signal),     // 선택
    fetchJSON(`${RECO_API}/related/${id}`, signal),     // 선택
  ]);

  // 필수 의존성이 실패하면 요청 전체가 실패한다
  if (recipe.status === 'rejected') throw new UpstreamError('recipe-api', recipe.reason);

  // 선택 의존성은 없으면 없는 대로 응답을 축약한다
  return {
    recipe: recipe.value,
    author: author.status === 'fulfilled' ? author.value : null,
    related: related.status === 'fulfilled' ? related.value : [],
    degraded: author.status === 'rejected' || related.status === 'rejected',
  };
}
```

`Promise.all` 대신 `Promise.allSettled`를 쓴 것이 이 코드의 전부다. 전자는 하나만 거부돼도 전체를 거부시키므로 가용성을 곱셈으로 만들고, 후자는 실패를 값으로 다루게 해서 부분 응답을 가능하게 한다. `degraded` 플래그를 응답에 남긴 이유는 31장에서 이 값을 메트릭으로 집계해 "얼마나 자주 축약 응답을 내보내고 있는가"를 추적하기 위해서다.

## 21.4 이 부에서 만들 예제 시스템

### 왜 이 두 서비스인가

예제 시스템은 최소한이면서도 21.3의 관계 모델을 전부 담아야 한다. 서비스가 하나면 프로듀서/컨슈머 관계가 성립하지 않고, 다섯이면 각 장에서 다루려는 주제보다 예제를 따라가는 비용이 커진다. 두 개가 그 최소 단위다. 하나는 외부에 노출되고 하나는 내부 전용이며, 둘 사이에 동기 호출이 하나 있고, 그 호출이 바로 앞으로 우리가 프로토콜을 바꾸고, 비동기로 떼어내고, 복제하고, 추적하고, 컨테이너에 담을 대상이다.

역할 분리도 의도적이다. recipe-api는 **상태를 소유하는** 서비스다. 데이터가 어디에 있고 어떻게 조회되는지는 이 서비스만 안다. web-api는 **상태를 소유하지 않는** 서비스다. 자기 데이터베이스가 없고, 하는 일은 프로듀서 응답을 사용자에게 맞는 모양으로 다듬는 것뿐이다. 이 비대칭이 뒤 장들에서 중요해진다. 25장에서 web-api는 아무 고민 없이 복제되지만 recipe-api는 데이터 계층과의 커넥션 수를 함께 계산해야 하고, 32장에서 web-api는 무상태 컨테이너로 자유롭게 재배치되지만 recipe-api는 그렇지 않다.

### 두 서비스

1장에서 소개한 recipe-api와 web-api가 6부부터 8부까지 우리가 계속 손댈 대상이다. 5부까지 오면서 두 서비스는 Fastify 기반이 되었고, 스키마 검증과 헬스 체크, 우아한 종료를 갖췄다. 6부의 출발점은 다음 상태다.

```text
nodejs-guide/
├── recipe-api/          # 프로듀서: 내부 전용, 외부 노출 없음
│   ├── server.js
│   ├── recipes.js       # 데이터 접근 계층 (19장)
│   └── package.json
├── web-api/             # 컨슈머: 외부 노출, recipe-api 호출
│   ├── server.js
│   ├── clients/recipe.js
│   └── package.json
└── package.json         # 워크스페이스 루트
```

```js
// recipe-api/server.js — 프로듀서
import Fastify from 'fastify';
import { findRecipe } from './recipes.js';

const app = Fastify({ logger: true });
const PORT = Number(process.env.PORT ?? 4000);
const HOST = process.env.HOST ?? '127.0.0.1';

// 로드 밸런서와 오케스트레이터가 사용한다 (26장, 32장 참조)
app.get('/health', async () => ({ status: 'ok', uptime: process.uptime() }));

app.get('/recipes/:id', {
  schema: {
    params: { type: 'object', properties: { id: { type: 'integer' } }, required: ['id'] },
  },
}, async (req, reply) => {
  const recipe = await findRecipe(req.params.id);
  if (!recipe) return reply.code(404).send({ error: 'not_found' });
  // 어느 인스턴스가 응답했는지 추적한다. 25장에서 이 값이 매 요청 달라진다
  return { producer_pid: process.pid, recipe };
});

await app.listen({ port: PORT, host: HOST });
```

```js
// web-api/server.js — 컨슈머
import Fastify from 'fastify';

const app = Fastify({ logger: true });
const PORT = Number(process.env.PORT ?? 3000);
const HOST = process.env.HOST ?? '127.0.0.1';
const RECIPE_API = process.env.RECIPE_API ?? 'http://127.0.0.1:4000';
const TIMEOUT_MS = Number(process.env.UPSTREAM_TIMEOUT_MS ?? 1000);

app.get('/health', async () => ({ status: 'ok', uptime: process.uptime() }));

app.get('/recipes/:id', async (req, reply) => {
  try {
    // 업스트림 호출에는 예외 없이 타임아웃을 건다. 없으면 장애가 그대로 전파된다
    const res = await fetch(`${RECIPE_API}/recipes/${req.params.id}`, {
      signal: AbortSignal.timeout(TIMEOUT_MS),
    });
    if (res.status === 404) return reply.code(404).send({ error: 'not_found' });
    if (!res.ok) throw new Error(`upstream_status_${res.status}`);

    return { consumer_pid: process.pid, ...(await res.json()) };
  } catch (err) {
    // 업스트림 실패를 502로 번역한다. 내부 오류 내용은 노출하지 않는다
    req.log.error({ err }, 'upstream_failed');
    return reply.code(502).send({ error: 'upstream_unavailable' });
  }
});

await app.listen({ port: PORT, host: HOST });
```

```bash
# 터미널 1
node recipe-api/server.js
# 터미널 2
node web-api/server.js
# 터미널 3
curl -s http://127.0.0.1:3000/recipes/42 | jq

# 프로듀서를 꺼 보면 21.2의 부분 실패를 직접 관찰할 수 있다
# → web-api는 1초 뒤 502를 반환한다. 타임아웃이 없었다면 커넥션이 쌓였을 것이다
```

### 실행 규약

앞으로의 모든 장이 같은 약속을 따른다. 포트는 web-api가 3000번대, recipe-api가 4000번대를 쓴다. 25장에서 인스턴스를 여러 개 띄우면 3000, 3001, 3002처럼 번호가 올라가므로 두 서비스의 포트 대역이 섞이지 않는 것이 중요하다. 설정은 예외 없이 환경 변수로 주입한다(`PORT`, `HOST`, `RECIPE_API`, `UPSTREAM_TIMEOUT_MS`). 하드코딩된 주소는 21.2의 다섯 번째 오류 — 토폴로지는 변하지 않는다 — 를 코드에 새겨 넣는 일이며, 26장에서 서비스 레지스트리를 붙일 때 가장 먼저 걷어내야 할 부채가 된다.

바인딩 주소도 같은 이유로 변수다. 로컬에서는 `127.0.0.1`이 안전하지만 컨테이너 안에서는 `0.0.0.0`이어야 외부에서 접근된다. 32장에서 이 값 하나 때문에 "컨테이너는 떴는데 헬스 체크가 실패한다"는 상황을 만나지 않으려면 지금부터 환경 변수로 두는 편이 낫다.

응답에 `producer_pid`와 `consumer_pid`를 넣어 둔 것도 계속 유지한다. 지금은 값이 매번 같지만, 25장에서 클러스터를 켜고 26장에서 로드 밸런서를 붙이는 순간 이 두 값이 요청마다 바뀌기 시작한다. 분산이 실제로 일어나고 있는지를 `curl` 한 번으로 확인할 수 있는 가장 값싼 장치다.

이 구성은 21.1의 한계를 하나도 해결하지 못한 상태다. 두 서비스 모두 프로세스 하나이고, 재시도도 서킷 브레이커도 없으며, 로그는 두 곳에 흩어져 있고, 배포는 수동이다. 앞으로의 장이 이것을 순서대로 고친다.

### 로드맵

| 장 | 두 서비스에 일어나는 일 |
|---|---|
| 22장 | HTTP/JSON 위에 GraphQL과 gRPC를 얹어 같은 기능을 세 프로토콜로 구현하고 성능·계약 측면에서 비교한다 |
| 23장 | 레시피 조회 로그 적재와 알림 발송을 메시지 브로커로 옮겨 동기 사슬에서 제거한다 |

## 요약

- 단일 Node.js 프로세스는 코어 하나, 물리 메모리에서 유도되는 힙 상한, `ulimit -n` 파일 디스크립터라는 물리적 천장을 갖는다. 앞의 셋은 더 큰 머신으로 미룰 수 있지만, 무중단 배포와 장애 격리는 프로세스를 늘리는 것 외에 해결책이 없다.
- 컨테이너 안의 Node.js는 호스트 메모리를 기준으로 힙 상한을 잡을 수 있다. `--max-old-space-size`를 메모리 한도의 70~80%로 명시하지 않으면 로그 없는 종료 코드 137을 만나게 된다.
- 분산은 함수 호출을 네트워크 호출로 바꾸는 것이 아니라 문제의 종류를 바꾼다. 성공도 실패도 아닌 "모름" 상태가 생기고, 그 결과 모든 쓰기 연산에 멱등성이 요구된다.
- 분산 컴퓨팅의 여덟 가지 오류는 설계 리뷰 체크리스트로 쓸 때 가장 유용하다. "이 가정이 깨지면 어떻게 되는가"를 의존성마다 물어라.
- 동기 호출 사슬에서 가용성은 곱해진다. 99.9% 서비스 다섯 개를 직렬로 엮으면 99.5%, 연간 43시간의 다운타임이 된다. 요청 경로의 동기 의존성 수를 줄이는 것이 가용성 설계의 첫 번째 수단이다.
- 팬아웃은 요청 증폭과 꼬리 지연 증폭을 낳는다. 프로듀서 10개를 병렬 호출하면 개별 p99가 통합 응답의 p90이 된다. 필수와 선택 의존성을 구분하고 `Promise.allSettled`로 부분 응답을 허용하라.
- 분산의 정당한 동기는 성능이 아니라 독립 배포, 장애 격리, 이질적 자원 요구, 서로 다른 확장 곡선이다. 이 중 어느 것도 해당하지 않으면 `cluster`로 복제하는 편이 거의 항상 낫다(27장 참조).

## 연습문제

1. **단일 프로세스의 천장 측정.** recipe-api를 실행하고 `autocannon`으로 부하를 주면서 처리량과 p99를 기록하라. 그다음 `--max-old-space-size=64`로 실행해 응답 객체를 인위적으로 키웠을 때 어떤 오류 메시지와 종료 코드가 나오는지 관찰하고, 같은 실험을 메모리 한도 96MB의 컨테이너 안에서 `--max-old-space-size` 없이 반복해 종료 방식이 어떻게 달라지는지 비교하라. 두 죽음의 로그 차이를 설명하라.

2. **가용성 곱셈 계산.** 개별 가용성이 각각 99.95%, 99.9%, 99.5%인 프로듀서 세 개를 직렬로 호출하는 컨슈머의 종단 가용성과 연간 다운타임을 계산하라. 이어서 셋 중 가장 낮은 하나를 선택 의존성으로 강등해 21.3의 `buildRecipeView` 방식으로 축약 응답을 허용했을 때의 종단 가용성을 다시 계산하고, 어느 쪽 개선이 더 큰지 — 가장 약한 서비스를 99.9%로 올리는 것과 그것을 선택 의존성으로 만드는 것 — 숫자로 답하라.

3. **부분 실패 관찰.** web-api와 recipe-api를 띄운 상태에서 recipe-api 핸들러에 `await setTimeout(3000)`(`node:timers/promises`)을 넣어 인위적으로 느리게 만들어라. web-api의 `UPSTREAM_TIMEOUT_MS`를 1000으로 둔 채 동시 요청 200건을 보내고, recipe-api 쪽 로그에서 **web-api가 이미 포기한 요청을 recipe-api가 계속 처리하고 있는지** 확인하라. 이 현상이 왜 위험한지 설명하고, `AbortSignal`을 프로듀서 쪽까지 전파하려면 무엇이 필요한지 조사하라.
