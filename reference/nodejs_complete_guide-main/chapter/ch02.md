# 2장. 모듈 시스템

Node.js를 배우는 개발자가 가장 먼저 만나는 벽은 이벤트 루프가 아니라 모듈 시스템이다. `require`가 되던 코드가 `import`로 바꾸자 깨지고, `__dirname`이 없다는 오류가 나고, 잘 쓰던 라이브러리가 "ERR_REQUIRE_ESM"을 뱉는다. 이 혼란은 Node.js가 표준 이전에 자체 모듈 시스템(CommonJS)을 만들었고, 나중에 등장한 언어 표준(ESM)을 뒤늦게 흡수해야 했던 역사에서 나온다.

이 장은 두 시스템을 각각 내부 동작 수준까지 파헤친 뒤, 둘이 만나는 지점에서 실무 코드가 어떻게 깨지는지를 다룬다. `require`를 20줄짜리 코드로 직접 구현해 보고, 순환 의존성이 만드는 부분 완성 객체를 실제 출력값으로 확인하고, 마지막에는 `package.json`의 `exports` 맵으로 패키지의 공개 표면을 설계한다.

## 2.1 모듈이 필요한 이유와 정보 은닉

### 전역 스코프라는 공유 자원

모듈 시스템이 없는 JavaScript에서 최상위 스코프는 전역이다. 브라우저에서 `<script>` 두 개를 나란히 넣으면 두 파일의 모든 최상위 선언이 같은 공간에 쌓인다. 파일 A가 `const config = {...}`를 선언하고 파일 B도 같은 이름을 쓰면, 로드 순서에 따라 조용히 덮이거나 `SyntaxError`로 터진다. 규모가 커질수록 이 충돌은 확률이 아니라 필연이 된다.

전역 오염보다 더 나쁜 것은 **의존 관계가 코드에 드러나지 않는다**는 점이다. 파일 B가 파일 A의 `config`를 쓴다는 사실은 어디에도 적혀 있지 않다. HTML의 `<script>` 순서라는, 코드 바깥의 암묵적 계약에만 존재한다. 이런 코드베이스는 파일 하나를 옮기는 것만으로 무너진다.

### 모듈이 제공해야 하는 네 가지

쓸 만한 모듈 시스템은 최소한 다음 네 가지를 제공해야 한다.

1. **독립 스코프**: 모듈 안의 선언이 밖으로 새지 않는다.
2. **명시적 의존성**: 무엇을 쓰는지가 코드 안에 적혀 있다.
3. **명시적 공개 인터페이스**: 무엇을 노출할지 저자가 고른다.
4. **재사용과 교체 가능성**: 같은 인터페이스를 만족하는 다른 구현으로 바꿔치기할 수 있다.

3번이 **정보 은닉(information hiding)**이다. 모듈의 내부 상태와 헬퍼 함수를 감추고, 계약으로 삼을 최소한만 노출한다. 노출하지 않은 것은 자유롭게 바꿔도 되므로, 정보 은닉은 곧 변경 비용의 문제다.

### 함수 스코프로 만드는 원시 모듈

ES2015 이전 JavaScript에는 함수 스코프밖에 없었다. 그래서 즉시 실행 함수(IIFE, Immediately Invoked Function Expression)로 모듈을 흉내 냈다. 이것이 **드러내기 모듈 패턴(revealing module pattern)**이다.

```js
const counter = (() => {
  // count는 밖에서 접근할 방법이 전혀 없다 — 진짜 private
  let count = 0;
  const clamp = (n) => Math.max(0, n); // 내부 헬퍼, 노출하지 않는다

  return {
    increment: () => ++count,
    decrement: () => (count = clamp(count - 1)),
    get value() { return count; }
  };
})();

counter.increment();
console.log(counter.value);  // 1
console.log(counter.count);  // undefined — 내부 상태는 보이지 않는다
```

반환된 객체가 공개 인터페이스이고, 클로저에 갇힌 `count`와 `clamp`는 외부에서 접근할 방법이 없다. 이 아이디어 — "코드를 함수로 감싸고, 반환값을 공개 인터페이스로 삼는다" — 가 CommonJS의 구현 원리 그대로다. 2.2에서 확인한다.

### 실무 조언

클래스의 `#private` 필드나 클로저로 은닉하는 것은 언어 차원의 은닉이고, 모듈이 무엇을 export하지 않는가는 **패키지 차원의 은닉**이다. 둘은 층위가 다르다. 실무에서 훨씬 자주 문제를 일으키는 쪽은 후자다. 내부 유틸리티를 실수로 export해 두면, 누군가 그것을 import하는 순간 그 함수는 사실상 공개 API가 되고 마음대로 고칠 수 없게 된다. "export하지 않으면 존재하지 않는 것과 같다"는 원칙을 지키고, 공개 표면은 2.8의 `exports` 필드로 패키지 경계에서 한 번 더 잠근다.

## 2.2 CommonJS: 해석 알고리즘, 캐시, 순환 의존성

### 왜 CommonJS인가

Node.js가 2009년 등장했을 때 JavaScript에는 모듈 표준이 없었다. 서버에서 수백 개 파일을 다루려면 모듈이 필수였으므로, Node.js는 CommonJS라는 명세를 채택해 `require`/`module.exports`를 구현했다. 이 결정 덕에 npm 생태계가 폭발했고, 그 대가로 오늘날 우리는 두 개의 모듈 시스템을 동시에 다뤄야 한다.

### require를 직접 만들어 본다

`require`는 마법이 아니라 그냥 함수다. 핵심만 추리면 20줄 남짓이다.

```js
import fs from 'node:fs';
import path from 'node:path';
import vm from 'node:vm';

function loadModule(filename, module, require) {
  // 파일 내용을 함수로 감싼다 — 이것이 '모듈 래퍼(module wrapper)'다
  const src = `(function (exports, require, module, __filename, __dirname) {
    ${fs.readFileSync(filename, 'utf-8')}
  })`;
  const fn = vm.runInThisContext(src, { filename });
  fn(module.exports, require, module, filename, path.dirname(filename));
}

function myRequire(moduleName) {
  const id = myRequire.resolve(moduleName);        // 1) 절대 경로로 해석
  if (myRequire.cache[id]) {                       // 2) 캐시 확인
    return myRequire.cache[id].exports;
  }
  const module = { exports: {}, id, loaded: false };
  myRequire.cache[id] = module;                    // 3) 로드 '전에' 캐시 등록 (순환 대비)
  loadModule(id, module, myRequire);               // 4) 실행
  module.loaded = true;
  return module.exports;                           // 5) exports 반환
}

myRequire.cache = Object.create(null);
myRequire.resolve = (moduleName) => import.meta.resolve(moduleName).slice(7);
```

이 20줄에 CommonJS의 모든 성질이 들어 있다.

- 모듈 코드는 **함수 본문으로 감싸여** 실행된다. 그래서 최상위 `const`가 전역을 오염시키지 않고, `exports`·`require`·`module`·`__filename`·`__dirname`이 마법처럼 존재하는 것처럼 보인다. 사실은 그냥 **함수 인자**다.
- 실행 **전에** 캐시에 등록한다(3번). 이것이 순환 의존성을 무한 루프 대신 부분 완성 객체로 만드는 원인이다.
- `require`는 **동기(synchronous)**다. `readFileSync`로 파일을 읽고 그 자리에서 실행한다. 그래서 CommonJS 모듈 그래프는 언제나 동기적으로 완성되며, 대신 최상위에서 `await`를 쓸 수 없다.

### 해석 알고리즘

`require('x')`가 어떤 파일을 가리키는지 정하는 것이 해석(resolving)이다. `/app/src/service.js`에서 호출했다고 하자.

**1) 코어 모듈 (`node:fs`, `fs`, `path` 등)**
접두사 `node:`가 붙었거나 이름이 내장 모듈과 일치하면 즉시 내장 구현을 반환한다. 파일 시스템을 뒤지지 않는다. `node:` 접두사를 항상 붙이는 습관을 권한다. npm에 `path`, `events` 같은 이름의 패키지가 실제로 존재해서, 접두사가 없으면 의도치 않게 그쪽이 잡힐 여지가 있다.

**2) 상대/절대 경로 (`./`, `../`, `/`로 시작)**
`/app/src/util`이라면 순서대로 시도한다.
- `/app/src/util` 파일 그대로
- `/app/src/util.js` → `/app/src/util.json` → `/app/src/util.node`
- 디렉터리라면 `/app/src/util/package.json`의 `main` 필드
- 그것도 없으면 `/app/src/util/index.js` → `index.json` → `index.node`

**3) 패키지 이름 (`lodash`, `@scope/pkg`)**
호출한 파일의 디렉터리부터 **위로 올라가며** `node_modules`를 찾는다.
```text
/app/src/node_modules/lodash
/app/node_modules/lodash
/node_modules/lodash
```
찾은 첫 번째가 이긴다. 그 다음 그 디렉터리에 대해 2번의 규칙(`exports` 필드 → `main` → `index.js`)을 적용한다.

이 "위로 올라가며 탐색" 규칙 때문에 같은 패키지의 서로 다른 버전이 트리의 여러 깊이에 동시에 설치될 수 있다. 그래서 `npm ls lodash`가 여러 줄을 뱉는 일이 생기고, 뒤에서 볼 듯 패키지 인스턴스가 둘로 갈라지는 문제(2.8의 듀얼 패키지 해저드와 같은 종류)가 발생한다.

### 캐시

캐시는 **해석된 절대 경로**를 키로 삼는다. 여기서 두 가지 성질이 나온다.

- 같은 파일을 몇 번 `require`해도 모듈 코드는 **한 번만** 실행된다. 그래서 CommonJS 모듈은 자연스럽게 싱글턴처럼 동작한다.
- 경로가 다르면 다른 모듈이다. `/app/node_modules/lib`와 `/app/src/node_modules/lib`는 내용이 같아도 서로 다른 인스턴스다.

캐시는 `require.cache`로 노출된다. 테스트에서 모듈을 다시 로드하려고 `delete require.cache[require.resolve('./x.js')]`를 쓰는 코드를 종종 보는데, 위험하다. 이미 그 모듈을 참조하고 있는 다른 모듈들은 **옛 인스턴스를 계속 들고 있으므로** 같은 클래스가 두 벌 존재하게 되고 `instanceof`가 실패한다. 테스트 격리가 필요하면 캐시를 건드리는 대신 의존성을 인자로 주입하는 설계(12장 참조)를 쓰거나, 워커/서브프로세스로 격리한다.

### 순환 의존성이 만드는 부분 완성 객체

두 모듈이 서로를 `require`하면 어떻게 될까. 캐시를 실행 전에 등록하므로 무한 루프는 아니지만, 대신 **아직 다 만들어지지 않은 exports**를 받는다.

```js
// a.js
exports.loaded = false;
const b = require('./b.js');
module.exports = { b, loaded: true };
```

```js
// b.js
exports.loaded = false;
const a = require('./a.js');
module.exports = { a, loaded: true };
```

```js
// main.js
const a = require('./a.js');
const b = require('./b.js');
console.log('a ->', a);
console.log('b ->', b);
```

실행 결과는 다음과 같다.

```text
a -> { b: { a: { loaded: false }, loaded: true }, loaded: true }
b -> { a: { loaded: false }, loaded: true }
```

`b`가 들고 있는 `a`의 `loaded`가 **false로 굳어 있다**. 순서를 따라가 보면 이유가 분명하다.

1. `main`이 `a.js`를 요청 → `a`의 `module.exports`(빈 객체)가 캐시에 등록되고 실행 시작
2. `a`가 `exports.loaded = false` 설정 → 캐시된 객체는 `{ loaded: false }`
3. `a`가 `b.js`를 요청 → `b` 실행 시작
4. `b`가 `a.js`를 요청 → **캐시 적중**, 지금 시점의 `{ loaded: false }`를 그대로 받는다
5. `b`가 `module.exports = { a, loaded: true }`로 **객체를 통째로 교체**하고 종료
6. `a`가 완성된 `b`를 받아 `module.exports`를 교체하고 종료

결정적인 지점은 5번과 6번이다. `module.exports`에 **새 객체를 대입**하는 순간, 4번에서 `b`가 붙잡아 둔 옛 객체는 버려진다. `b.a`는 영원히 그 옛 객체를 가리키고, `a`가 나중에 무슨 짓을 해도 반영되지 않는다.

반대로 `module.exports = {...}` 대신 `exports.x = ...`로 **기존 객체를 변형**만 했다면 참조가 살아 있어 값은 결국 채워진다. 하지만 이것도 안전하지 않다. `b`가 로딩 시점(최상위)에 `a.someFn()`을 호출하면 그 시점에는 아직 `someFn`이 대입되지 않아 `TypeError: a.someFn is not a function`이 난다. 참조는 살아 있어도 **시간이 맞지 않는다**.

### 실무 함정과 조언

가장 고약한 성질은 **진입점에 따라 결과가 달라진다**는 것이다. 위 예제에서 `main.js`가 `b`를 먼저 `require`하면 이번엔 `a.b.loaded`가 false가 된다. 즉 순환 의존성이 있는 모듈은 "누가 먼저 로드되는가"에 따라 동작이 바뀐다. 프로덕션에서 이런 버그는 배포 순서나 사소한 import 정리 커밋으로 갑자기 나타난다.

실무 지침은 명확하다.

- 순환은 **설계 냄새**다. 대개 두 모듈이 공유하는 세 번째 개념(타입, 상수, 인터페이스)을 별도 모듈로 뽑으면 사라진다.
- 굳이 순환을 남겨야 한다면 최상위에서 상대 모듈을 **사용하지 말고** 함수 안으로 미룬다. `const b = require('./b.js')`를 함수 본문 안에서 호출하면 그 시점에는 `b`가 완성돼 있다.
- `madge --circular src/`나 ESLint의 `import/no-cycle` 규칙으로 CI에서 순환을 차단한다.
- 순환 의존성은 ESM에서 다르게(그리고 대체로 더 낫게) 해결된다. 2.6에서 같은 예제를 ESM으로 다시 본다.

## 2.3 `module.exports` vs `exports`

### 왜 두 개인가

2.2의 모듈 래퍼를 다시 보면 답이 나온다.

```js
fn(module.exports, require, module, filename, path.dirname(filename));
//  ^^^^^^^^^^^^^^ 이것이 exports 인자로 들어간다
```

`exports`는 **`module.exports`를 가리키는 지역 변수(별칭)**일 뿐이다. 모듈이 시작될 때 둘은 같은 빈 객체를 가리킨다. 그리고 `require`가 반환하는 것은 `exports`가 아니라 **`module.exports`**다. 이 비대칭이 초보자를 잡는 함정 전체의 근원이다.

### 되는 것과 안 되는 것

```js
// OK — 두 변수가 가리키는 같은 객체를 변형한다
exports.hello = () => 'hi';
module.exports.bye = () => 'bye';

// 동작하지 않는다 — 지역 변수 exports만 새 객체를 가리키게 바꿨을 뿐,
// module.exports는 여전히 원래의 빈 객체다
exports = () => 'hi';

// OK — 실제로 반환되는 참조 자체를 교체한다
module.exports = () => 'hi';
```

세 번째 줄이 조용히 실패하는 것이 문제다. 오류도 경고도 없고, 그저 `require`한 쪽이 빈 객체 `{}`를 받는다. 함수나 클래스 하나만 내보내려는 모듈에서 흔히 나온다.

### 대입과 변형이 섞일 때

또 하나의 흔한 실수는 대입 후에 `exports`를 계속 쓰는 경우다.

```js
module.exports = class Repository { /* ... */ };
exports.createRepository = () => new Repository(); // 사라진다
```

`exports`는 여전히 옛 빈 객체를 가리키므로 `createRepository`는 아무도 볼 수 없는 곳에 붙는다. 클래스에 정적 헬퍼를 붙이려면 `module.exports.createRepository = ...`로 써야 한다.

`module.exports`를 함수로 대입한 뒤 프로퍼티를 붙이는 패턴 자체는 유효하다. Express가 대표적이다.

```js
function createApp() { /* ... */ }
createApp.Router = Router;   // express() 도 되고 express.Router 도 된다
createApp.static = serveStatic;
module.exports = createApp;
```

### 실무 조언

혼동을 없애는 가장 단순한 규칙은 **모듈 한 개당 한 가지 스타일만 쓰는 것**이다. 이름 있는 여러 값을 내보낼 것이면 `exports.x = ...`만 쓰고 `module.exports`에는 손대지 않는다. 단일 값을 내보낼 것이면 파일 맨 아래에서 `module.exports = ...` 한 줄로 끝낸다. 섞지 않는다.

한 가지 더. `module.exports`를 대입하는 위치는 **파일 맨 아래**가 안전하다. 2.2에서 봤듯 순환 의존성 상황에서는 대입 시점 이전에 다른 모듈이 exports 객체를 붙잡을 수 있는데, 대입을 늦출수록 그 창이 넓어져 문제가 잘 드러난다. 반대로 대입을 맨 위에서 하고 프로퍼티를 아래에서 채우면(`module.exports = {}` 후 변형) 참조는 유지되지만 값은 미완성인 상태로 새어 나간다. 어느 쪽이든 순환 자체를 없애는 것이 정답이다.

## 2.4 모듈 정의 패턴: 이름 내보내기, 함수, 클래스, 인스턴스

모듈을 설계할 때 던져야 할 질문은 하나다. "이 모듈은 무엇을 내보내는가 — 여러 개의 함수인가, 하나의 팩토리인가, 타입인가, 상태를 가진 객체인가." 각 선택은 확장성과 테스트 용이성에서 서로 다른 대가를 치른다.

### 이름 내보내기(named exports)

가장 기본이고 가장 자주 옳은 선택이다.

```js
// logger.js
export function info(message) { console.log(`[INFO] ${message}`); }
export function warn(message) { console.warn(`[WARN] ${message}`); }
```

가장 큰 장점은 **트리 셰이킹(tree shaking)**이다. 번들러가 정적으로 사용 여부를 판단할 수 있어 안 쓰는 export는 결과물에서 빠진다. 또 IDE의 자동 완성과 이름 변경 리팩터링이 잘 동작한다. Node.js 코어가 `node:fs`에서 `readFile`, `writeFile`을 개별로 내보내는 것도 같은 이유다. 특별한 이유가 없으면 이 패턴에서 시작한다.

단점은 상태를 담기 어렵고, 함수 개수가 늘면 모듈 응집도가 흐려진다는 것이다. 20개짜리 `utils.js`가 생겼다면 그건 모듈이 아니라 서랍이다.

### 함수 내보내기(substack 패턴)

모듈이 함수 **하나**를 내보낸다. 그 함수가 곧 모듈의 진입점이자 유일한 공개 표면이 된다.

```js
// logger.js
export default function createLogger(prefix) {
  const write = (level, msg) => console.log(`[${level}] ${prefix}: ${msg}`);
  return {
    info: (msg) => write('INFO', msg),
    warn: (msg) => write('WARN', msg)
  };
}
```

호출부는 `createLogger('payment')`로 자기만의 인스턴스를 얻는다. 공개 표면이 함수 하나로 최소화되므로 정보 은닉이 극단적으로 잘 되고, 각 호출자가 독립된 상태를 갖는다. 부가 기능이 필요하면 함수에 프로퍼티를 붙여 네임스페이스처럼 확장할 수도 있다(2.3의 Express 예).

### 클래스 내보내기

```js
export class Logger {
  #prefix;                                  // 진짜 private 필드
  constructor(prefix) { this.#prefix = prefix; }
  info(msg) { console.log(`[INFO] ${this.#prefix}: ${msg}`); }
}
```

팩토리와 달리 **확장 가능성을 명시적으로 노출**한다. 사용자가 `extends Logger`로 동작을 바꿀 수 있고, `instanceof`로 타입을 검사할 수 있다. 도메인 엔티티, 커스텀 에러, `EventEmitter` 상속처럼 "타입"이 개념적으로 의미 있을 때 적합하다.

반대로 그것이 정확히 단점이기도 하다. 클래스를 내보내는 순간 내부 구조가 상속 계약의 일부가 되어, 프로토타입 체인에 손을 대는 사용자가 생기면 리팩터링이 막힌다. 팩토리로 감싸 두면 나중에 구현을 통째로 바꿔도 호출부는 모른다. 확장을 실제로 의도할 때만 클래스를 내보내고, 그렇지 않으면 팩토리를 쓴다.

### 인스턴스 내보내기(싱글턴)

```js
// db.js
class Database { /* ... */ }
export default new Database(process.env.DATABASE_URL);
```

모듈 캐시 덕분에 이 인스턴스는 프로세스 안에서 하나만 존재한다. 커넥션 풀, 설정 객체, 로거처럼 "하나여야 하는 것"에 편리하다.

하지만 대가가 크다. **모듈이 로드되는 시점에 부수 효과(side effect)가 실행된다.** 위 코드는 `import` 하는 것만으로 DB 연결을 시도한다. 테스트에서 이 모듈을 건드리는 순간 실제 DB에 붙으려 하고, 설정을 바꾸려면 환경 변수를 미리 세팅해야 한다. 게다가 2.2에서 봤듯 캐시 키는 해석된 경로이므로, 같은 패키지가 `node_modules` 트리의 두 위치에 설치되면 **싱글턴이 두 개**가 된다.

권장 형태는 인스턴스를 직접 내보내는 대신 **팩토리를 내보내고, 애플리케이션 조립 지점(컴포지션 루트)에서 한 번 만들어 주입**하는 것이다.

```js
// db.js — 부수 효과 없음
export function createDatabase({ url, poolSize = 10 }) { /* ... */ }

// main.js — 여기서만 인스턴스를 만든다
import { createDatabase } from './db.js';
const db = createDatabase({ url: process.env.DATABASE_URL });
```

이 구조는 테스트에서 가짜 구현을 넣기 쉽고, 인스턴스 수명을 명시적으로 통제할 수 있다. 의존성 주입과 컴포지션 루트 설계는 9장에서 자세히 다룬다.

### 실무 조언

패턴 선택의 실질적 기준은 **부수 효과의 유무**다. `import` 만으로 무언가가 실행되는 모듈은 순환 의존성, 테스트 격리, 시작 순서 문제를 한꺼번에 불러온다. 모듈 최상위에서는 선언만 하고, 실행은 호출자가 하도록 미룬다.

## 2.5 ESM: ECMAScript 모듈

### 표준의 등장

CommonJS는 Node.js의 사설 규약이었고 브라우저에서 그대로 쓸 수 없었다. ES2015가 `import`/`export` 문법을 언어 표준으로 정의했고, Node.js는 v12에서 실험적으로, v14~16을 거치며 정식으로 이를 지원하게 됐다. 오늘날 새 프로젝트의 기본값은 ESM이다.

### ESM을 켜는 방법

Node.js는 파일 단위로 모듈 종류를 판정한다.

- 확장자 `.mjs` → 항상 ESM
- 확장자 `.cjs` → 항상 CommonJS
- 확장자 `.js` → 가장 가까운 상위 `package.json`의 `"type"` 필드를 따른다. `"module"`이면 ESM, `"commonjs"`이거나 없으면 CommonJS

즉 `package.json`에 `"type": "module"` 한 줄을 넣는 것이 프로젝트 전체를 ESM으로 전환하는 스위치다. (Node.js 22부터는 `type` 필드가 없고 확장자가 `.js`인 파일에 대해 문법을 보고 ESM으로 자동 판정하는 동작이 들어왔지만, 명시적으로 `type`을 적는 편이 예측 가능하다.)

### 문법

```js
// math.js
export const PI = 3.14159;
export function area(r) { return PI * r * r; }

class Circle { /* ... */ }
export { Circle };                       // 선언과 분리해서 내보내기
export { Circle as Round };              // 이름 바꿔 내보내기
export default function circumference(r) { return 2 * PI * r; }
```

```js
// main.js
import circumference from './math.js';          // default
import { PI, area } from './math.js';           // named
import { area as circleArea } from './math.js'; // 별칭
import * as math from './math.js';              // 네임스페이스 객체
import './side-effect.js';                      // 실행만
export * from './math.js';                      // 재수출(re-export)
export { area } from './math.js';               // 선택적 재수출
```

`import * as math`가 주는 것은 평범한 객체가 아니라 **모듈 네임스페이스 객체(module namespace object)**다. 동결(frozen)돼 있어 `math.PI = 3`은 조용히 무시되거나 strict 모드에서 `TypeError`를 던진다. CommonJS에서 `require`한 객체에 프로퍼티를 꽂아 몽키 패칭하던 습관은 ESM에서 통하지 않는다.

### CommonJS와 다른 규칙들

ESM으로 넘어오면 다음이 달라진다. 처음 전환할 때 대부분 여기서 걸린다.

- **확장자가 필수다.** `import './util'`은 실패한다. `import './util.js'`로 써야 한다. 디렉터리의 `index.js` 자동 탐색도 없다. 번들러가 해 주던 편의를 Node.js는 하지 않는다. 이는 브라우저와 동일한 해석 규칙을 유지하기 위한 의도적 선택이다.
- **항상 strict 모드다.** `"use strict"`를 적을 필요가 없고, 끌 수도 없다.
- **최상위 `this`가 `undefined`다.** CommonJS에서는 `module.exports`였다.
- **`__dirname`, `__filename`, `require`, `module`, `exports`가 없다.** 2.7에서 대안을 다룬다.
- **최상위 await(top-level await)를 쓸 수 있다.** 모듈 평가가 비동기일 수 있기 때문이다.

```js
// config.js — CommonJS로는 불가능한 코드
const res = await fetch(process.env.CONFIG_URL);
export const config = await res.json();
```

이 모듈을 import하는 쪽은 `config`가 채워질 때까지 자동으로 기다린다. 편리하지만 대가가 있다. 최상위 await가 있는 모듈은 그래프 전체의 평가를 지연시키고, 2.7에서 볼 `require(esm)` 경로로는 로드할 수 없다. 라이브러리 코드에서는 신중히 쓴다.

## 2.6 로딩 단계, 읽기 전용 라이브 바인딩, 비동기 import

### 왜 단계를 나누는가

CommonJS는 "필요할 때 파일을 읽어서 즉시 실행"하는 단순한 모델이다. 대신 그래프의 모양을 실행 전에 알 수 없다. `require`가 `if` 안에 있을 수도, 문자열을 조립해 만든 경로일 수도 있기 때문이다. 그래서 정적 분석(트리 셰이킹, 미사용 export 검출)이 사실상 불가능하고, 브라우저처럼 네트워크로 모듈을 받아야 하는 환경에서는 동기 로딩 자체가 성립하지 않는다.

ESM은 이를 뒤집었다. `import` 선언은 최상위에만 올 수 있고 경로는 정적 문자열이어야 한다. 덕분에 **코드를 실행하기 전에 그래프 전체를 알 수 있고**, 로딩을 세 단계로 나눌 수 있다.

### 세 단계

**1) 구성(construction) — 파싱과 그래프 탐색**
진입점부터 시작해 파일을 읽고 파싱해서 `import` 선언을 찾는다. 각 지정자를 절대 URL로 해석하고, 아직 방문하지 않은 모듈이면 다시 읽는다. 이 과정을 깊이 우선으로 반복해 모듈 레코드의 그래프를 만든다. **이 단계에서는 코드가 한 줄도 실행되지 않는다.** 그래서 문법 오류나 존재하지 않는 파일은 아무것도 실행되기 전에 잡힌다.

**2) 인스턴스화(instantiation) — 링킹**
각 모듈의 export를 위한 메모리 슬롯(바인딩)을 만들고, import하는 쪽의 이름을 그 슬롯에 **연결**한다. 값은 아직 없다. 슬롯만 있고 초기화되지 않은 상태다. 이때 "b가 export하지 않는 이름을 a가 import한다" 같은 문제가 **실행 전에** `SyntaxError`로 잡힌다. CommonJS라면 런타임에 `undefined`가 흘러다니다 엉뚱한 곳에서 터질 오류다.

**3) 평가(evaluation) — 실행**
그래프를 깊이 우선, 후위(post-order)로 돌며 각 모듈의 본문을 실행해 슬롯을 값으로 채운다. 각 모듈은 한 번만 평가된다.

### 읽기 전용 라이브 바인딩

2단계에서 "이름을 슬롯에 연결한다"는 말의 의미가 핵심이다. import된 이름은 값의 **복사본이 아니라 원본 슬롯에 대한 참조**다. 이것이 라이브 바인딩(live binding)이다.

```js
// counter.js
export let count = 0;
export function increment() { count += 1; }
```

```js
// main.js
import { count, increment } from './counter.js';
console.log(count);   // 0
increment();
console.log(count);   // 1  ← 다시 import하지 않았는데 값이 바뀐다
count = 100;          // TypeError: Assignment to constant variable.
```

CommonJS로 같은 코드를 짜면 `count`는 `require` 시점의 값이 복사돼 영원히 0이다. 값을 갱신하려면 객체로 감싸 `state.count`처럼 참조를 공유해야 했다. ESM에서는 원시값도 살아 있다.

동시에 바인딩은 **읽기 전용**이다. 값을 바꿀 권한은 그 값을 선언한 모듈에만 있다. 소비자가 남의 모듈 상태를 마음대로 덮어쓰는 일이 문법적으로 차단된다. 몽키 패칭으로 라이브러리를 고치던 코드가 ESM에서 안 되는 이유이며, 테스트 목킹 라이브러리들이 ESM 지원에 애를 먹은 이유이기도 하다. (해법은 로더 훅이나 `node:test`의 `mock.module` 같은 런타임 지원이다. 24장 참조.)

### ESM의 순환 의존성

2.2의 순환 예제를 ESM으로 옮겨 본다.

```js
// a.mjs
import { loadB } from './b.mjs';
export function loadA() { return 'A'; }
console.log(loadB());
```

```js
// b.mjs
import { loadA } from './a.mjs';
export function loadB() { return `B + ${loadA()}`; }
```

`node a.mjs`를 실행하면 `B + A`가 정상 출력된다. CommonJS로 동일하게 옮기면 `TypeError: loadA is not a function`이 난다.

차이는 인스턴스화 단계에 있다. ESM은 평가 전에 이미 `loadA`라는 바인딩을 만들어 연결해 뒀다. 그리고 함수 선언은 호이스팅되어 모듈 평가가 시작되는 순간 값이 채워진다. 그래서 `b.mjs`가 먼저 평가되더라도 `loadA` 슬롯을 참조하는 데 문제가 없다.

다만 만능은 아니다. `let`/`const`로 선언한 값을 순환 상대가 평가 전에 읽으면 **일시적 사각지대(TDZ, Temporal Dead Zone)** 오류가 난다.

```js
// a.mjs
import { B } from './b.mjs';
export const A = 'a';
console.log(B);
// b.mjs
import { A } from './a.mjs';
export const B = `b uses ${A}`;   // ReferenceError: Cannot access 'A' before initialization
```

정리하면 ESM의 순환은 **함수 참조라면 안전하고, 값 참조는 여전히 위험하다.** CommonJS와 달리 조용히 `undefined`가 흘러다니지 않고 명확한 오류로 터진다는 점이 개선이다. 그래도 순환은 없애는 것이 맞다.

### 동적 import

정적 `import`는 최상위에만 올 수 있으므로 조건부 로딩이 불가능하다. 이를 위한 것이 `import()` 연산자다. 프로미스를 반환하며, 어디서든 호출할 수 있고 지정자를 런타임에 계산할 수 있다.

```js
const locale = process.env.LOCALE ?? 'ko';
const { messages } = await import(`./i18n/${locale}.js`);
```

용도는 세 가지다. 조건부 로딩(플러그인, 로케일), 시작 시간 단축(무거운 의존성을 실제로 필요할 때까지 미룸), 그리고 2.7에서 볼 **CommonJS에서 ESM을 로드하는 유일한 이식성 있는 방법**이다.

주의할 점. 동적 import는 정적 분석을 무력화하므로 번들러가 경로를 추론하지 못하면 트리 셰이킹이 깨진다. 템플릿 리터럴로 만든 경로는 특히 그렇다. 또 사용자 입력을 그대로 지정자에 넣으면 임의 파일 실행 취약점이 된다. 반드시 허용 목록으로 걸러야 한다.

```js
const LOADERS = { ko: () => import('./i18n/ko.js'), en: () => import('./i18n/en.js') };
const load = LOADERS[locale] ?? LOADERS.ko;   // 허용된 경로만 정적으로 나열
```

## 2.7 ESM과 CommonJS의 차이와 상호 운용

실무에서 모듈 시스템 때문에 시간을 가장 많이 잃는 지점이 여기다. 하나씩 정리한다.

### 요약 비교

| 항목 | CommonJS | ESM |
|---|---|---|
| 로딩 | 동기, 런타임 해석 | 비동기, 정적 그래프 |
| 지정자 | 확장자·index 생략 가능 | 확장자 필수 |
| 바인딩 | 값 복사 | 읽기 전용 라이브 바인딩 |
| 최상위 await | 불가 | 가능 |
| 순환 | 부분 완성 객체 | 함수는 안전, 값은 TDZ 오류 |
| `__dirname` | 있음 | 없음 (`import.meta.url` 사용) |
| 몽키 패칭 | 가능 | 불가(네임스페이스 동결) |

### ESM에서 CommonJS 부르기

가능하다. CommonJS는 동기적으로 로드되므로 ESM 그래프에 문제없이 끼워 넣을 수 있다.

```js
import lodash from 'lodash';           // module.exports 전체가 default로 들어온다
import { readFile } from 'node:fs';    // 코어 모듈은 이름 내보내기도 지원
```

주의할 점은 **이름 내보내기가 보장되지 않는다**는 것이다. Node.js는 CommonJS 모듈을 정적 분석해 `exports.foo = ...` 같은 단순한 패턴에서 이름 export를 추론해 준다(cjs-module-lexer). 하지만 `Object.assign(exports, obj)`나 반복문으로 프로퍼티를 붙이는 코드는 추론에 실패한다. 그러면 `import { foo } from 'pkg'`가 `SyntaxError: The requested module does not provide an export named 'foo'`로 터진다. 안전한 회피책은 default로 받아 구조 분해하는 것이다.

```js
import pkg from 'some-cjs-lib';
const { foo, bar } = pkg;
```

### CommonJS에서 ESM 부르기

전통적으로 이것이 불가능했다. `require('esm-only-package')`는 `ERR_REQUIRE_ESM`을 던진다. ESM 평가가 비동기일 수 있는데 `require`는 동기이기 때문이다. 2020년대 초 많은 인기 패키지가 ESM 전용으로 전환하면서 이 오류가 생태계 전반의 골칫거리가 됐다.

Node.js 20.19와 22.12부터는 제한적으로 허용된다. 대상 ESM 그래프에 **최상위 await가 없으면** `require`가 성공하고 모듈 네임스페이스 객체를 반환한다.

```js
// CommonJS 파일
const ns = require('esm-only-package');
ns.default;      // ESM의 default export
ns.namedThing;   // 이름 export
```

다만 라이브러리를 배포한다면 여전히 구버전 Node.js 사용자를 고려해야 하므로, 이식성 있는 방법은 동적 import다.

```js
// CommonJS 파일
async function main() {
  const { default: chalk } = await import('chalk');
  console.log(chalk.green('ok'));
}
```

`import()`는 CommonJS 안에서도 쓸 수 있으며, 번들러가 `require`로 바꿔치기하지 않도록 TypeScript를 쓴다면 `module` 설정을 확인해야 한다(`CommonJS` 타깃에서 `import()`가 `require`로 다운레벨되면 다시 `ERR_REQUIRE_ESM`이 난다. `Node16`/`NodeNext` 설정을 쓴다).

### `__dirname`과 `require`의 대안

ESM에는 `__dirname`, `__filename`, `require`가 없다. 대신 `import.meta`가 있다.

```js
import { fileURLToPath } from 'node:url';
import path from 'node:path';

const __filename = fileURLToPath(import.meta.url);
const __dirname = path.dirname(__filename);
```

Node.js 20.11 이상에서는 훨씬 짧게 쓸 수 있다.

```js
console.log(import.meta.dirname);   // __dirname과 동일
console.log(import.meta.filename);  // __filename과 동일
```

`import.meta.url`은 문자열 경로가 아니라 **파일 URL**(`file:///app/src/x.js`)이라는 점에 주의한다. 공백이나 한글이 든 경로는 퍼센트 인코딩되므로, 문자열을 잘라 쓰지 말고 반드시 `fileURLToPath`를 거쳐야 한다. Windows에서는 이 실수가 곧바로 깨진 경로로 나타난다.

`require`가 꼭 필요하면 만들어 쓸 수 있다.

```js
import { createRequire } from 'node:module';
const require = createRequire(import.meta.url);

const legacy = require('./legacy-cjs-config.cjs');
const addon = require('./build/Release/native.node');   // 네이티브 애드온은 여전히 require가 필요
```

`createRequire`는 인자로 준 URL을 기준으로 해석하는 진짜 `require`를 만든다. `require.resolve`도 함께 쓸 수 있어 패키지의 실제 설치 경로를 알아낼 때 유용하다.

### JSON import

CommonJS에서는 `require('./config.json')`이면 끝이었다. ESM에서는 **import 속성(import attributes)**이 필요하다.

```js
import config from './config.json' with { type: 'json' };
```

`with` 구문은 Node.js 20.10 이상에서 쓸 수 있다. 그 이전 버전에서는 `assert { type: 'json' }`였는데, 이 문법은 폐기됐으므로 새 코드에 쓰지 않는다. 라이브러리에서 넓은 버전 호환이 필요하다면 아예 import를 피하는 편이 안전하다.

```js
import { readFile } from 'node:fs/promises';
const config = JSON.parse(await readFile(new URL('./config.json', import.meta.url), 'utf-8'));
```

특히 자기 패키지의 `package.json`에서 버전을 읽는 흔한 코드는 위 방식이나 `createRequire`를 쓰는 것이 무난하다.

### 실무 함정

- **`.js` 확장자를 빠뜨린 import.** TypeScript로 ESM을 낼 때 `import './x'`로 쓰면 컴파일은 되지만 런타임에 `ERR_MODULE_NOT_FOUND`가 난다. `NodeNext` 모드에서는 소스에서도 `.js`를 붙여야 한다(`.ts`가 아니라 `.js`다).
- **의존성이 조용히 ESM 전용으로 올라감.** 마이너 버전 업데이트 후 갑자기 `ERR_REQUIRE_ESM`이 나면 대개 이것이다. 변경 로그를 확인하고 동적 import로 감싸거나 버전을 고정한다.
- **테스트 러너와 로더.** ESM에서 목킹은 CommonJS만큼 자유롭지 않다. 목을 많이 쓰는 코드라면 그 자체가 설계 신호이니 의존성 주입으로 전환하는 편이 낫다(12장 참조).

## 2.8 패키지 구성: `package.json`, `exports` 필드, 듀얼 패키지

### 패키지는 공개 표면을 설계하는 단위다

모듈 하나의 공개 표면이 `export`라면, 패키지 하나의 공개 표면은 `package.json`이 정한다. 어떤 파일을 import할 수 있는지, 그 파일이 ESM인지 CommonJS인지, 어떤 조건에서 무엇을 줄지가 모두 여기서 결정된다.

### 핵심 필드

```json
{
  "name": "@acme/orders",
  "version": "1.0.0",
  "type": "module",
  "main": "./dist/index.cjs",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js",
      "require": "./dist/index.cjs",
      "default": "./dist/index.js"
    },
    "./testing": "./dist/testing.js",
    "./package.json": "./package.json"
  },
  "imports": {
    "#config": "./src/config.js",
    "#logger": { "node": "./src/logger.node.js", "default": "./src/logger.browser.js" }
  },
  "engines": { "node": ">=20.19" },
  "sideEffects": false
}
```

- **`type`**: 이 패키지의 `.js` 파일을 어떤 모듈로 볼지 정한다(2.5 참조).
- **`main`**: 레거시 진입점. `exports`가 있으면 무시되지만, 아주 오래된 도구를 위해 남겨 두는 경우가 있다.
- **`exports`**: 현대적 진입점 맵. 아래에서 자세히 본다.
- **`imports`**: 패키지 **내부**에서만 쓰는 별칭. 반드시 `#`로 시작한다.
- **`sideEffects: false`**: 번들러에게 "이 패키지의 모듈은 import만으로 부수 효과를 내지 않는다"고 알려 트리 셰이킹을 허용한다. 실제로 부수 효과가 있는데 이 값을 켜면 코드가 사라지는 버그가 난다.

### `exports` 맵과 캡슐화

`exports`가 존재하면 그 맵에 나열되지 않은 경로는 **밖에서 접근할 수 없다.** `main`만 있던 시절에는 누구나 `require('pkg/lib/internal/util.js')`로 내부를 파고들 수 있었고, 그렇게 노출된 파일은 사실상 공개 API가 되어 리팩터링을 막았다. `exports`는 이 문을 닫는다.

```js
import { createOrder } from '@acme/orders';           // OK — "." 에 매핑됨
import { fixtures } from '@acme/orders/testing';      // OK — "./testing" 에 매핑됨
import x from '@acme/orders/dist/internal/db.js';     // ERR_PACKAGE_PATH_NOT_EXPORTED
```

패턴 매핑도 가능하다. `"./features/*": "./dist/features/*.js"`처럼 쓰면 하위 경로를 한꺼번에 열 수 있다. `exports`를 도입할 때 흔히 잊는 것이 `"./package.json": "./package.json"` 항목이다. 여러 도구가 패키지의 `package.json`을 직접 읽으려 하는데, 막혀 있으면 원인을 짐작하기 어려운 오류가 난다.

### 조건부 exports

`exports`의 값은 문자열 대신 **조건 객체**일 수 있다. Node.js는 위에서 아래로 순회하며 처음 일치하는 조건을 쓴다. **순서가 의미를 가진다.**

주요 조건은 다음과 같다.

- `types`: TypeScript용 선언 파일. **반드시 맨 위에 둔다.** 아래에 두면 TypeScript가 먼저 매칭된 JS 경로를 잡아 타입을 못 찾는다.
- `node`: Node.js 런타임
- `browser`: 번들러가 브라우저 대상으로 빌드할 때
- `import`: `import`나 `import()`로 불렸을 때
- `require`: `require`로 불렸을 때
- `default`: 아무것도 일치하지 않을 때의 최종 후보. 맨 아래에 둔다.

`import`/`require` 조건이 뜻하는 것은 "이 패키지가 ESM인가"가 아니라 **"호출자가 어떤 문법으로 불렀는가"**다. 이 구분을 놓치면 다음 절의 문제로 직행한다.

### 내부 별칭: `imports`

깊은 상대 경로(`../../../config.js`)는 파일을 옮길 때마다 깨진다. `imports` 필드가 이를 패키지 루트 기준 별칭으로 대체한다.

```js
import { load } from '#config';    // package.json의 imports가 해석한다
```

`#`로 시작하는 이름만 허용되며, 이 별칭은 패키지 내부에서만 유효하다. 밖에서 `import '#config'`를 할 방법은 없다. 번들러 설정이나 `tsconfig`의 `paths`와 달리 **Node.js가 직접 이해하는 표준 기능**이라는 점이 장점이다. 빌드 도구 없이도 동작하고, 조건부 매핑까지 쓸 수 있어 브라우저용과 Node.js용 구현을 갈라 놓는 데 유용하다.

### 듀얼 패키지 해저드

한 패키지가 ESM 빌드와 CommonJS 빌드를 **둘 다** 담고 조건부 exports로 갈라 주면, 하나의 프로세스 안에서 같은 패키지가 **두 번 로드**될 수 있다. 애플리케이션이 `import 'pkg'`를 하고, 의존하는 다른 라이브러리가 `require('pkg')`를 하면 서로 다른 두 인스턴스가 생긴다. 이것이 듀얼 패키지 해저드(dual package hazard)다.

증상은 이렇게 나타난다.

```js
import { AppError } from 'lib';          // ESM 빌드의 클래스
const err = someCjsLib.doWork();         // 내부에서 CJS 빌드의 클래스로 만든 에러
console.log(err instanceof AppError);    // false — 같은 이름, 다른 클래스
```

- `instanceof`가 실패한다. 클래스 식별자가 빌드마다 다르기 때문이다.
- 싱글턴이 둘이 된다. 커넥션 풀이 두 벌 만들어지거나, 한쪽에 등록한 플러그인이 다른 쪽에 보이지 않는다.
- 모듈 수준 캐시나 카운터가 갈라져 통계가 절반만 잡힌다.
- 심볼 레지스트리처럼 전역이라고 가정한 상태가 깨진다.

디버깅이 특히 괴로운 이유는 오류 메시지가 원인을 전혀 가리키지 않기 때문이다. `instanceof`가 false인 이유를 찾으려면 `require.resolve`와 `import.meta.resolve`로 실제 로드된 파일 경로를 찍어 보는 수밖에 없다.

### 회피 전략

**1) ESM 단일 배포.** 가장 깨끗하다. `"type": "module"`로 ESM만 내고, CommonJS 사용자는 Node.js 20.19+/22.12+의 `require(esm)`이나 동적 import로 접근하게 한다. 최상위 await를 쓰지 않으면 `require(esm)`이 동작하므로 실질적 장벽이 낮아졌다. 새 패키지의 기본 선택으로 권한다.

**2) 상태 없는 코어 분리.** 반드시 듀얼로 내야 한다면, 클래스와 가변 상태를 **CommonJS 코어 한 벌**에만 두고 ESM 빌드는 그것을 `import`해 다시 export하는 얇은 래퍼로 만든다. 실제 클래스 식별자가 하나뿐이므로 `instanceof`가 깨지지 않는다.

**3) 상태를 아예 두지 않는다.** 순수 함수만 내보내는 패키지라면 두 벌이 로드돼도 관찰 가능한 차이가 없다. 인스턴스를 내보내지 말라는 2.4의 조언이 여기서 다시 힘을 얻는다.

### 검증

`exports` 맵은 손으로 검증하기 어렵다. 배포 전에 다음을 습관화한다.

- `npm pack`으로 실제 배포될 파일 목록을 확인한다. `files` 필드나 `.npmignore` 실수로 `dist`가 통째로 빠지는 사고가 흔하다.
- `npx publint`와 `npx @arethetypeswrong/cli`로 `exports`/`types` 배치 오류를 자동 점검한다.
- ESM 소비자용과 CommonJS 소비자용 스모크 테스트 프로젝트를 각각 만들어 CI에서 실제로 import해 본다.

## 요약

- 모듈의 본질은 독립 스코프, 명시적 의존성, 통제된 공개 표면이다. 노출하지 않은 것만이 자유롭게 바꿀 수 있다.
- `require`는 파일을 함수로 감싸 실행하고 결과를 절대 경로 기준으로 캐시하는 동기 함수다. `exports`·`require`·`module`·`__dirname`은 마법이 아니라 모듈 래퍼 함수의 인자다.
- CommonJS의 순환 의존성은 부분 완성 객체를 만든다. 특히 `module.exports`를 재대입하면 상대가 붙잡은 옛 객체가 영원히 갱신되지 않고, 진입점 순서에 따라 결과가 달라진다.
- `exports`는 `module.exports`의 별칭일 뿐이다. 재대입은 `module.exports`에만 해야 하며, 한 모듈 안에서 두 스타일을 섞지 않는다.
- ESM은 구성·인스턴스화·평가의 3단계로 로드된다. 인스턴스화 덕분에 import 이름 오류를 실행 전에 잡고, 순환 상황에서도 함수 참조가 안전하게 동작한다.
- import된 이름은 읽기 전용 라이브 바인딩이다. 원본 모듈이 값을 바꾸면 소비자에게 즉시 반영되지만, 소비자가 덮어쓸 수는 없다.
- 상호 운용의 핵심은 `import.meta.url`·`import.meta.dirname`·`createRequire`·import 속성이며, CommonJS에서 ESM을 부르는 이식성 있는 방법은 동적 `import()`다.
- `package.json`의 `exports`는 패키지의 공개 표면을 잠그고, `imports`는 내부 별칭을 제공한다. 듀얼 배포는 인스턴스가 둘로 갈라지는 해저드를 부르므로 ESM 단일 배포를 우선 검토한다.

## 연습문제

**1.** 2.2의 `myRequire` 구현에서 캐시 등록(`myRequire.cache[id] = module`)을 `loadModule` 호출 **뒤로** 옮기면 무슨 일이 벌어지는지 설명하고, 서로를 참조하는 두 모듈로 실제 재현해 보라. 그다음 이 실험 결과를 근거로 "실행 전에 캐시를 등록한다"는 설계가 무엇을 포기하고 무엇을 얻은 것인지 서술하라.

**2.** 카운터 모듈을 CommonJS와 ESM 두 벌로 작성한다. 각각 `count`(숫자)와 `increment()`를 내보내고, 소비자 모듈에서 `increment()` 호출 전후의 `count`를 출력해 값이 달라지는지 확인하라. 두 결과가 왜 다른지 라이브 바인딩 관점에서 설명하고, CommonJS에서 같은 효과를 내려면 인터페이스를 어떻게 바꿔야 하는지 제시하라.

**3.** 클래스 `AppError`를 내보내는 작은 패키지를 만들어 ESM 빌드와 CommonJS 빌드를 조건부 `exports`로 갈라 배포한다(`npm link` 또는 `file:` 의존성 사용). 소비 애플리케이션에서 한쪽은 `import`로, 다른 쪽은 `require`로 같은 패키지를 로드한 뒤 `instanceof`가 false가 되는 상황을 재현하라. 이어서 2.8의 전략 중 하나를 적용해 문제를 제거하고, 선택한 전략의 대가가 무엇인지 정리하라.
