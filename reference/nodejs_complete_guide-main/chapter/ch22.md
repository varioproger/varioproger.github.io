# 22장. 통신 프로토콜

21장에서 하나의 서비스를 둘로 쪼갰다. 쪼갠 순간 함수 호출이던 것이 네트워크 호출이 되었고, 그때부터 "어떤 형식으로 무엇을 주고받을 것인가"라는 질문이 새로 생겼다.

이 장은 그 질문에 대한 세 가지 답을 다룬다. HTTP/JSON, GraphQL, gRPC. 세 프로토콜로 **같은 기능을 세 번 구현**하는 것이 이 장의 구조다. 21장에서 만든 recipe-api(프로듀서)와 web-api(컨슈머)를 매번 처음부터 다시 짜면서, 같은 요구사항이 프로토콜에 따라 어떻게 다른 코드로 굳어지는지 관찰한다.

세 번 다 만들어 보는 이유는 취향을 고르기 위해서가 아니다. 각 프로토콜이 무엇을 쉽게 만들고 무엇을 어렵게 만드는지는 코드를 나란히 놓고 보기 전까지는 잘 보이지 않는다.

## 22.1 HTTP로 하는 요청/응답

### 왜 HTTP가 기본값인가

서비스 간 통신에서 HTTP는 사실상 무설정 기본값이다. 이유는 성능이 아니라 **보편성**이다. 어떤 언어에도 클라이언트가 있고, 어떤 프록시도 이해하며, `curl` 한 줄로 디버깅되고, 모든 관측 도구가 이미 계측할 줄 안다. 21장에서 본 것처럼 분산 시스템의 비용 대부분은 통신 자체가 아니라 통신을 **관찰하고 고치는 일**에서 나오므로, 이 보편성은 종종 몇 밀리초의 지연보다 값지다.

다만 "HTTP를 쓴다"는 결정은 생각보다 적은 것을 결정한다. 메서드를 어떻게 쓸지, 본문을 무엇으로 인코딩할지, 오류를 어떤 모양으로 돌려줄지는 전부 따로 정해야 한다. 이 절은 그 나머지 결정들에 관한 것이다.

### 페이로드와 시맨틱

HTTP 요청은 네 부분으로 구성된다. 메서드, 경로, 헤더, 본문. 이 중 서비스 간 통신에서 가장 자주 오용되는 것이 메서드다. 메서드는 단순한 이름표가 아니라 **계약**이며, 그 계약의 핵심은 안전성(safety)과 멱등성(idempotency) 두 가지다.

**안전한(safe)** 메서드는 서버의 상태를 변경하지 않는다. `GET`, `HEAD`, `OPTIONS`가 여기 해당한다. **멱등한(idempotent)** 메서드는 같은 요청을 N번 보낸 결과가 1번 보낸 결과와 같다. 안전한 메서드는 전부 멱등하며, 여기에 `PUT`과 `DELETE`가 추가된다. `POST`와 `PATCH`만이 안전하지도 멱등하지도 않다.

| 메서드 | 안전 | 멱등 | 재시도 가능 | 캐시 가능 |
|---|---|---|---|---|
| `GET` | 예 | 예 | 예 | 예 |
| `HEAD` | 예 | 예 | 예 | 예 |
| `PUT` | 아니오 | 예 | 예 | 아니오 |
| `DELETE` | 아니오 | 예 | 예 | 아니오 |
| `POST` | 아니오 | 아니오 | **조건부** | 거의 아니오 |
| `PATCH` | 아니오 | 아니오 | **조건부** | 아니오 |

이 표는 장식이 아니다. 이것이 곧 **재시도 정책**이다. 15장에서 다룬 재시도는 멱등한 요청에만 무조건 안전하게 적용할 수 있고, `POST`에 재시도를 걸려면 멱등성 키(idempotency key)를 함께 보내 서버가 중복을 걸러 주어야 한다. 프록시, 서비스 메시, HTTP 클라이언트 라이브러리 대부분이 "멱등한 메서드만 자동 재시도한다"를 기본 정책으로 삼는 이유가 여기 있다. 상태를 바꾸는 연산을 `GET`으로 노출하면 이 기본 정책이 조용히 무너진다. 크롤러가 `GET /orders/42/cancel`을 밟는 사고는 지금도 일어난다.

응답 쪽에서는 상태 코드가 같은 역할을 한다. 서비스 간 통신에서 실무적으로 중요한 구분은 딱 하나다. **4xx는 재시도하면 안 되고, 5xx와 429는 재시도해도 된다.** 컨슈머의 재시도 로직 전체가 이 구분 위에 서 있으므로, 프로듀서가 잘못된 입력에 500을 돌려주면 컨슈머는 절대 성공하지 않을 요청을 지수 백오프로 계속 두드리게 된다.

### recipe-api: HTTP 프로듀서

21장의 예제를 HTTP로 구현한다. recipe-api는 레시피 데이터를 소유하고, 조회 두 개를 노출한다.

```js
// recipe-api/producer-http.mjs
import Fastify from 'fastify'
import { recipes, ingredientsOf } from './data.mjs'

const server = Fastify({ logger: true })
const HOST = process.env.HOST ?? '127.0.0.1'
const PORT = Number(process.env.PORT ?? 4000)

// 응답 스키마를 명시한다. Fastify는 이 스키마로 직렬화기를 컴파일하며,
// 스키마에 없는 필드는 응답에서 자동으로 제거된다(22.1 후반부 참조)
const recipeSchema = {
  type: 'object',
  properties: {
    id: { type: 'integer' },
    name: { type: 'string' },
    servings: { type: 'integer' },
    updatedAt: { type: 'string' }
  },
  required: ['id', 'name', 'servings']
}

server.get('/recipes/:id', {
  schema: {
    params: { type: 'object', properties: { id: { type: 'integer' } } },
    response: { 200: recipeSchema }
  }
}, async (req, reply) => {
  const recipe = recipes.get(req.params.id)
  if (!recipe) {
    // 없는 자원은 404. 500이 아니다 — 컨슈머가 재시도하면 안 되는 오류다
    return reply.code(404).send({ error: 'recipe_not_found', id: req.params.id })
  }
  return recipe.toJSON()   // 명시적 직렬화. 이유는 곧 설명한다
})

server.get('/recipes/:id/ingredients', async (req, reply) => {
  const list = ingredientsOf(req.params.id)
  if (!list) return reply.code(404).send({ error: 'recipe_not_found' })
  return { id: req.params.id, ingredients: list.map((i) => i.toJSON()) }
})

await server.listen({ host: HOST, port: PORT })
```

`/recipes/:id`와 `/recipes/:id/ingredients`가 분리되어 있다는 점을 기억해 두자. 레시피와 재료를 함께 필요로 하는 컨슈머는 **왕복 두 번**을 해야 한다. 이 사실이 22.2에서 GraphQL을 도입하는 동기가 된다.

### web-api: HTTP 컨슈머

```js
// web-api/consumer-http.mjs
import Fastify from 'fastify'

const server = Fastify({ logger: true })
const TARGET = process.env.RECIPE_API ?? 'http://127.0.0.1:4000'

// undici 기반 글로벌 fetch를 쓴다(10장 참조).
// 프로덕션에서는 keep-alive 커넥션 풀을 명시적으로 구성하는 편이 낫다
async function call(path, signal) {
  const res = await fetch(`${TARGET}${path}`, {
    signal,
    headers: { accept: 'application/json' }
  })
  if (res.status === 404) return null
  if (!res.ok) {
    // 상태 코드를 그대로 던지지 말고 재시도 가능 여부를 붙여 전달한다
    const err = new Error(`upstream_${res.status}`)
    err.retryable = res.status >= 500 || res.status === 429
    throw err
  }
  return res.json()
}

server.get('/dishes/:id', async (req, reply) => {
  // 진입점에서 데드라인을 하나 만들고 하위 호출 전체에 전파한다(15장 참조)
  const ac = new AbortController()
  const timer = setTimeout(() => ac.abort(), 800)
  try {
    // 두 호출은 서로 독립적이므로 병렬로 보낸다.
    // 순차로 보내면 왕복 지연이 그대로 더해진다
    const [recipe, ingredients] = await Promise.all([
      call(`/recipes/${req.params.id}`, ac.signal),
      call(`/recipes/${req.params.id}/ingredients`, ac.signal)
    ])
    if (!recipe) return reply.code(404).send({ error: 'not_found' })
    return { recipe, ingredients: ingredients?.ingredients ?? [] }
  } finally {
    clearTimeout(timer)
  }
}) 

await server.listen({ host: '127.0.0.1', port: 3000 })
```

`Promise.all`로 두 호출을 겹쳤다는 점이 중요하다. 순차로 짜면 recipe-api가 각각 5밀리초에 응답해도 web-api의 지연은 10밀리초가 된다. 리소스가 세 개, 네 개로 늘면 이 덧셈은 그대로 커진다. **HTTP/1.1에서 왕복 수는 컨슈머가 직접 관리해야 하는 비용**이며, 이것이 언더페칭(under-fetching) 문제의 실체다.

### 압축: 서비스 간 통신에서 켜야 하는가

브라우저를 상대하는 서버라면 gzip 압축은 논쟁의 여지가 없다. 사용자의 네트워크가 느리고 비싸기 때문이다. 그런데 같은 데이터센터 안에서 도는 두 서비스 사이라면 계산이 달라진다.

대략의 수치를 놓고 보자. 1KB짜리 JSON 응답을 gzip 레벨 6으로 압축하면 대체로 400~600바이트가 되고, 압축에 드는 CPU 시간은 Node.js에서 요청당 30~80마이크로초 수준이다. 100KB짜리 응답이라면 압축 후 10~20KB, 압축 시간은 1~3밀리초로 올라간다. 반대편 네트워크 비용은 어떤가. 같은 가용 영역 안의 10Gbps 링크에서 100KB를 전송하는 데 드는 시간은 80마이크로초 안팎이고 왕복 지연은 0.2~0.5밀리초다.

즉 **작은 페이로드를 저지연 내부 네트워크로 보낼 때 압축은 순손해**다. 절약하는 전송 시간보다 태우는 CPU 시간이 크고, 그 CPU는 이벤트 루프를 점유해 다른 모든 요청의 지연으로 전가된다(3장 참조). 반대로 페이로드가 수십 KB를 넘어가거나, 가용 영역·리전을 넘어가거나, 대역폭에 요금이 붙는 구간이라면 압축이 확실히 이긴다.

실무 판단 기준은 세 가지다.

1. **임계값을 둔다.** 대부분의 압축 미들웨어는 `threshold` 옵션을 제공한다. 1KB 미만은 압축하지 않는 것이 기본이어야 하며, 내부 통신이라면 8~16KB로 올려도 좋다.
2. **레벨을 낮춘다.** gzip 레벨 6(기본값) 대신 레벨 1을 쓰면 CPU가 절반 이하로 줄고 압축률은 10~15%만 손해 본다. 내부 통신에서는 이 교환이 거의 항상 유리하다.
3. **가능하면 위임한다.** 리버스 프록시나 서비스 메시 사이드카가 압축을 처리하면 Node.js의 단일 이벤트 루프에서 CPU를 빼낼 수 있다(26장 참조).

```js
// 내부 통신용 압축 설정: 임계값을 높이고 레벨을 낮춘다
import compress from '@fastify/compress'

await server.register(compress, {
  threshold: 8192,          // 8KB 미만은 압축하지 않는다
  zlibOptions: { level: 1 },// 속도 우선
  encodings: ['gzip']       // br은 압축률이 높지만 CPU를 더 쓴다
})
```

브로틀리(Brotli)는 같은 데이터를 gzip보다 15~20% 더 줄이지만 압축 시간은 기본 설정에서 몇 배 더 든다. 정적 파일처럼 **한 번 압축해 여러 번 보내는** 경우에는 브로틀리가 압도적으로 유리하고, 매 요청 새로 압축해야 하는 동적 API 응답에서는 대체로 불리하다.

### HTTPS와 TLS

TLS는 서비스 간 통신에서 두 가지를 준다. 도청 방지와 **상대의 신원 확인**이다. 내부 네트워크는 안전하다는 가정은 오래전에 폐기되었고, 지금의 표준은 제로 트러스트, 즉 내부 호출에도 상호 TLS(mTLS)를 거는 것이다.

비용은 두 군데서 발생한다. 첫째는 핸드셰이크다. TLS 1.3에서 전체 핸드셰이크는 1-RTT이며 Node.js에서 RSA 2048 키 기준 서버 측 CPU 비용이 대체로 1~2밀리초다. 둘째는 레코드 암복호화인데, AES-NI가 있는 현대 CPU에서는 처리량당 비용이 몇 퍼센트 수준으로 무시할 만하다.

결론적으로 **TLS의 실질 비용은 거의 전부 핸드셰이크에 있고, 핸드셰이크는 연결 재사용으로 상쇄된다.** 그래서 내부 통신의 TLS 설계에서 가장 중요한 항목은 암호 스위트가 아니라 keep-alive다.

```js
// 컨슈머 쪽 커넥션 풀. 핸드셰이크를 재사용해 TLS 비용을 상수로 만든다
import { Agent, setGlobalDispatcher } from 'undici'

setGlobalDispatcher(new Agent({
  connections: 64,            // 오리진당 최대 소켓 수
  keepAliveTimeout: 60_000,   // 유휴 연결 유지 시간
  keepAliveMaxTimeout: 600_000,
  connect: {
    ca: process.env.INTERNAL_CA,     // 사설 CA
    cert: process.env.CLIENT_CERT,   // mTLS 클라이언트 인증서
    key: process.env.CLIENT_KEY
  }
}))
```

연결을 재사용하지 않으면 요청마다 핸드셰이크가 붙어, 5밀리초짜리 조회 API가 7밀리초짜리가 된다. 부하 테스트에서 "TLS를 켜니 처리량이 절반이 되었다"는 보고는 거의 예외 없이 연결 재사용이 안 되고 있다는 신호다.

### JSON over HTTP와 POJO 직렬화의 위험

여기가 이 절에서 가장 중요한 부분이다.

`JSON.stringify`는 편리해서 위험하다. 도메인 객체를 그대로 응답에 넣는 코드는 어디에나 있다.

```js
// 위험한 코드
server.get('/recipes/:id', async (req) => {
  const recipe = await Recipe.findById(req.params.id)
  return recipe          // 클래스 인스턴스를 그대로 반환한다
})
```

이 한 줄이 만드는 문제는 셋이다.

**첫째, 메서드가 사라진다.** `JSON.stringify`는 열거 가능한 자기 소유(own enumerable) 속성만 직렬화한다. 프로토타입에 있는 메서드, `Symbol` 키, `undefined` 값 속성, 그리고 게터로 계산되는 파생 필드 중 일부가 조용히 빠진다. 컨슈머 쪽에서 `recipe.totalCalories()`를 부르려던 코드는 `TypeError: recipe.totalCalories is not a function`으로 죽는다. 네트워크를 건너간 것은 객체가 아니라 객체의 **그림자**다. `Date`는 문자열이 되고, `Map`과 `Set`은 `{}`가 되며, `BigInt`는 아예 예외를 던진다.

**둘째, 필드가 조용히 유출된다.** ORM이 반환한 엔티티에는 대개 도메인 모델에 없던 것들이 붙어 있다. `passwordHash`, `internalCostCents`, `deletedAt`, `_rawRow` 같은 필드가 컬럼 추가 한 번으로 응답에 딸려 나간다. 무서운 점은 **이 유출이 아무 오류도 일으키지 않는다**는 것이다. 테스트는 전부 통과하고, 응답에 필드가 하나 늘었을 뿐이며, 아무도 눈치채지 못한다. 실제 사고의 상당수가 "새 컬럼을 추가했더니 그게 공개 API 응답에 나타났다"는 형태다.

**셋째, 스키마 없는 응답이 컨슈머를 깨뜨린다.** 응답 모양이 코드의 부수 효과로 결정되면, 그 모양은 아무도 의도하지 않은 채로 바뀐다. 필드 이름을 리팩터링하면 API가 바뀌고, ORM을 업그레이드하면 API가 바뀐다. 컨슈머는 문서화되지 않은 필드에 의존하게 되고, 프로듀서는 자기가 무엇을 약속했는지 모른다. 22.2의 GraphQL과 22.3의 gRPC가 스키마를 강제하는 이유가 바로 이 문제다.

해법은 단순하고, 예외 없이 적용해야 한다. **명시적 직렬화 함수를 둔다.**

```js
// recipe-api/serializers.mjs — 응답 모양을 코드에 못 박는다
export function serializeRecipe(recipe) {
  return {
    id: recipe.id,
    name: recipe.name,
    servings: recipe.servings,
    // Date는 명시적으로 ISO 문자열로 바꾼다. 암묵적 변환에 기대지 않는다
    updatedAt: recipe.updatedAt.toISOString()
  }
}

export function serializeIngredient(ingredient) {
  return {
    id: ingredient.id,
    name: ingredient.name,
    quantity: ingredient.quantity,
    unit: ingredient.unit
  }
}
```

이 함수는 **허용 목록(allowlist)** 이다. 새 컬럼이 생겨도 여기 적지 않으면 나가지 않는다. 필드를 지우면 함수가 깨지므로 파괴적 변경이 컴파일 시점 비슷한 지점에서 드러난다. 그리고 이 함수 자체가 API 문서다.

클래스에 `toJSON()`을 두는 방식도 같은 효과를 내며, `JSON.stringify`가 자동으로 호출해 주므로 실수로 원본을 반환해도 안전하다는 장점이 있다.

```js
class Recipe {
  #costCents            // private 필드는 애초에 직렬화되지 않는다
  constructor (row) {
    this.id = row.id
    this.name = row.name
    this.servings = row.servings
    this.updatedAt = row.updated_at
    this.#costCents = row.cost_cents
  }
  // JSON.stringify가 이 메서드를 자동으로 호출한다
  toJSON () {
    return { id: this.id, name: this.name, servings: this.servings,
             updatedAt: this.updatedAt.toISOString() }
  }
}
```

세 번째 방어선은 **응답 스키마**다. 앞서 recipe-api 코드에서 Fastify에 `response` 스키마를 준 것이 그것이다. Fastify는 이 스키마로 전용 직렬화 함수를 컴파일하는데, 부수 효과로 **스키마에 없는 필드를 응답에서 제거한다**. 유출 방지 장치인 동시에 성능 최적화이기도 하다. 컴파일된 직렬화기는 범용 `JSON.stringify`보다 대체로 2배 안팎 빠르다. 명시적 직렬화 함수와 응답 스키마를 함께 쓰면 실수 하나가 사고로 이어지지 않는다.

### 실무 함정

**부동소수점과 큰 정수.** JSON의 수는 IEEE 754 배정밀도다. 데이터베이스의 `BIGINT` ID나 원 단위 금액이 2^53을 넘으면 정밀도가 조용히 사라진다. 큰 식별자는 문자열로 보내는 것이 정답이며, `JSON.parse`가 `BigInt`를 만들어 주지 않는다는 사실도 기억해야 한다.

**오류 응답 모양의 불일치.** 성공 응답은 스키마로 관리하면서 오류 응답은 프레임워크 기본값에 맡기는 경우가 많다. 그러면 컨슈머는 `{ error }`, `{ message }`, `{ statusCode, error, message }`를 모두 상대해야 한다. 오류 포맷도 스키마로 못 박고, 가능하면 RFC 9457(Problem Details)처럼 표준화된 모양을 쓴다.

**`Content-Type` 검사 생략.** 컨슈머가 `res.json()`을 무조건 부르면, 프록시가 끼워 넣은 HTML 오류 페이지를 받았을 때 `SyntaxError: Unexpected token <`로 죽는다. 원인 진단이 오래 걸리는 부류의 오류다.

**파싱 상한 미설정.** 본문 크기 제한(`bodyLimit`)을 두지 않으면 큰 JSON 하나가 파싱 동안 이벤트 루프를 통째로 막는다. `JSON.parse`는 동기 함수이며 중단할 수 없다.

## 22.2 GraphQL: API 파사드

### 무엇을 해결하는가

22.1의 web-api 코드를 다시 보자. 요리 상세 화면 하나를 그리려고 recipe-api에 두 번 요청했다. 화면에 조리 단계와 영양 정보가 추가되면 네 번이 되고, 관련 레시피 목록까지 붙으면 다섯 번이 된다. 이것이 **언더페칭(under-fetching)**, 정확히는 N+1 라운드트립 문제다. 리소스 단위로 잘 설계된 REST API일수록 화면 하나를 그리는 데 필요한 왕복이 늘어난다.

반대 방향의 문제도 있다. 모바일 앱의 목록 화면은 레시피 이름과 썸네일만 필요한데, `/recipes/:id`는 재료 20개와 조리 단계 12개를 통째로 돌려준다. 이것이 **오버페칭(over-fetching)** 이다. 대응책으로 `?fields=name,image` 같은 파라미터를 붙이기 시작하면, 결국 질의 언어를 하나 발명하게 된다.

GraphQL은 그 질의 언어를 이미 만들어 둔 것이다. 컨슈머가 필요한 필드를 정확히 기술하고, 프로듀서는 단 한 번의 왕복으로 그 모양대로 돌려준다. 그래서 GraphQL은 데이터베이스도 아니고 REST의 대체재도 아니며, **여러 백엔드 앞에 놓는 파사드(facade)** 로 볼 때 가장 정확하다.

### 스키마

GraphQL의 출발점은 스키마다. HTTP/JSON에서는 응답 모양을 명시적 직렬화 함수로 겨우 붙들어야 했지만, GraphQL에서는 스키마가 없으면 서버가 뜨지 않는다. 스키마가 곧 계약이고, 문서이며, 검증기다.

```graphql
# recipe-api/schema.graphql
type Recipe {
  id: ID!
  name: String!
  servings: Int!
  updatedAt: String!
  # 재료는 별도 리졸버로 채운다. 컨슈머가 요청하지 않으면 조회 자체가 일어나지 않는다
  ingredients: [Ingredient!]!
}

type Ingredient {
  id: ID!
  name: String!
  quantity: Float!
  unit: Unit!
}

enum Unit { GRAM MILLILITER PIECE TEASPOON }

type Query {
  recipe(id: ID!): Recipe
  recipes(limit: Int = 20, offset: Int = 0): [Recipe!]!
}
```

느낌표는 널 불가(non-null)를 뜻한다. `[Ingredient!]!`는 "리스트 자체도 널이 아니고 원소도 널이 아니다"라는 의미다. 이 표기는 문서가 아니라 런타임 검증이다. 널이 아니라고 선언한 필드에 리졸버가 `null`을 반환하면 GraphQL은 그 오류를 부모로 전파해 부모 필드까지 `null`로 만든다. 널 가능성 설계를 대충 하면 필드 하나의 실패가 응답 전체를 지우는 사태가 벌어진다.

### 프로듀서 구현

Node.js에서 GraphQL 서버를 올리는 방법은 여럿이지만, 여기서는 Fastify 위에 Mercurius를 얹는다.

```js
// recipe-api/producer-graphql.mjs
import Fastify from 'fastify'
import mercurius from 'mercurius'
import { readFile } from 'node:fs/promises'
import { db } from './db.mjs'

const schema = await readFile(new URL('./schema.graphql', import.meta.url), 'utf8')

const resolvers = {
  Query: {
    recipe: (_root, { id }) => db.findRecipe(Number(id)),
    recipes: (_root, { limit, offset }) => db.listRecipes(limit, offset)
  },
  Recipe: {
    // 이 리졸버는 컨슈머가 ingredients 필드를 요청했을 때만 실행된다.
    // 요청하지 않으면 DB 조회 자체가 발생하지 않는다 — 오버페칭 해소의 실체
    ingredients: (recipe, _args, ctx) => ctx.loaders.ingredients.load(recipe.id)
  }
}

const server = Fastify({ logger: true })

await server.register(mercurius, {
  schema,
  resolvers,
  graphiql: process.env.NODE_ENV !== 'production',
  // 요청마다 새 컨텍스트를 만든다. DataLoader 캐시가 요청 범위여야 하기 때문이다
  context: () => ({ loaders: createLoaders() }),
  queryDepth: 8   // 재귀 쿼리 방어. 아래 '새로 만드는 문제' 참조
})

await server.listen({ host: '127.0.0.1', port: 4000 })
```

리졸버는 트리 형태로 실행된다. `Query.recipe`가 먼저 실행되어 레시피 객체를 반환하면, 그 결과가 `Recipe.ingredients`의 첫 인자(`root`)로 전달된다. 컨슈머가 `ingredients`를 요청하지 않았다면 그 리졸버는 아예 호출되지 않는다. 이것이 오버페칭이 사라지는 메커니즘이며, 동시에 뒤에서 볼 N+1 문제의 원인이기도 하다.

### 컨슈머 구현

컨슈머 쪽은 놀랄 만큼 단순하다. 전용 클라이언트 라이브러리 없이 `fetch` 하나면 된다. GraphQL은 결국 `POST /graphql`에 JSON 본문 하나를 보내는 것이기 때문이다.

```js
// web-api/consumer-graphql.mjs
import Fastify from 'fastify'

const TARGET = process.env.RECIPE_API ?? 'http://127.0.0.1:4000/graphql'

// 쿼리는 상수로 밖에 빼 둔다. 문자열 보간으로 만들지 않는다 —
// 값은 반드시 variables로 넘겨야 파싱 캐시가 적중하고 주입 위험도 없다
const DISH_QUERY = `
  query Dish($id: ID!) {
    recipe(id: $id) {
      id
      name
      servings
      ingredients { name quantity unit }
    }
  }
`

async function graphql(query, variables, signal) {
  const res = await fetch(TARGET, {
    method: 'POST',
    signal,
    headers: { 'content-type': 'application/json' },
    body: JSON.stringify({ query, variables })
  })
  const body = await res.json()
  // 함정: GraphQL은 오류가 있어도 HTTP 200을 돌려준다.
  // res.ok만 보고 성공으로 판단하면 안 된다
  if (body.errors?.length) {
    const err = new Error(body.errors[0].message)
    err.graphQLErrors = body.errors
    throw err
  }
  return body.data
}

const server = Fastify({ logger: true })

server.get('/dishes/:id', async (req, reply) => {
  const ac = new AbortController()
  const timer = setTimeout(() => ac.abort(), 800)
  try {
    // 왕복 한 번으로 레시피와 재료를 모두 받는다.
    // 22.1에서 Promise.all로 겹쳐야 했던 두 호출이 하나로 합쳐졌다
    const { recipe } = await graphql(DISH_QUERY, { id: req.params.id }, ac.signal)
    if (!recipe) return reply.code(404).send({ error: 'not_found' })
    return recipe
  } finally {
    clearTimeout(timer)
  }
})

await server.listen({ host: '127.0.0.1', port: 3000 })
```

응답은 요청한 모양과 정확히 같은 구조로 온다.

```js
{
  "data": {
    "recipe": {
      "id": "42", "name": "김치찌개", "servings": 2,
      "ingredients": [ { "name": "김치", "quantity": 300, "unit": "GRAM" } ]
    }
  }
}
```

응답 모양이 쿼리와 일대일로 대응한다는 점이 GraphQL의 실질적인 개발 경험상 이점이다. 컨슈머는 자기가 무엇을 받을지 코드만 보고 알 수 있다.

### GraphQL이 새로 만드는 문제

여기까지만 보면 GraphQL은 순수한 이득처럼 보인다. 그렇지 않다. GraphQL은 문제를 없앤 것이 아니라 **문제의 위치를 옮겼다**. 왕복 횟수 문제를 컨슈머에서 프로듀서로 옮겼고, 그 대가로 세 가지를 새로 만들었다.

**첫째, N+1 리졸버 쿼리.** 컨슈머가 레시피 20개를 목록으로 요청하고 각각의 재료를 함께 달라고 하면, `Recipe.ingredients` 리졸버가 20번 호출된다. 리졸버가 각각 DB 쿼리를 날리면 쿼리 21개가 나간다. 컨슈머 입장에서는 왕복이 한 번으로 줄었지만, 프로듀서와 DB 사이에서는 왕복이 오히려 늘었다. 네트워크 홉 하나를 없애고 다른 홉에 21배 부하를 얹은 셈이다.

표준 해법은 DataLoader다. 같은 틱(tick) 안에 들어온 개별 `load(id)` 호출을 모아 한 번의 배치 조회로 바꾼다. 15장에서 다룬 비동기 요청 배칭 패턴의 정확한 사례다.

```js
// recipe-api/loaders.mjs
import DataLoader from 'dataloader'
import { db } from './db.mjs'

export function createLoaders () {
  return {
    // 배치 함수는 키 배열을 받아 같은 순서·같은 길이의 결과 배열을 반환해야 한다.
    // 순서가 어긋나면 엉뚱한 레시피에 남의 재료가 붙는다 — 조용한 데이터 오염이다
    ingredients: new DataLoader(async (recipeIds) => {
      const rows = await db.findIngredientsByRecipeIds(recipeIds) // IN (...) 한 번
      const byRecipe = new Map(recipeIds.map((id) => [id, []]))
      for (const row of rows) byRecipe.get(row.recipe_id)?.push(row)
      return recipeIds.map((id) => byRecipe.get(id))
    })
  }
}
```

DataLoader 인스턴스는 반드시 **요청마다 새로 만들어야 한다**. 모듈 수준에 하나 두면 요청 범위 캐시가 프로세스 범위 캐시가 되어, 사용자 A의 데이터가 사용자 B에게 보이는 인가 사고로 직결된다. 앞의 서버 코드에서 `context: () => ({ loaders: createLoaders() })`로 매 요청 생성한 이유가 이것이다.

**둘째, 쿼리 복잡도 공격.** REST에서는 컨슈머가 요청할 수 있는 것이 엔드포인트 목록으로 제한된다. GraphQL에서는 컨슈머가 쿼리를 조립하므로, 스키마에 순환이 있으면 비용을 임의로 키울 수 있다.

```graphql
# 레시피 → 재료 → 그 재료를 쓰는 레시피 → 재료 → ... 를 반복하는 악성 쿼리
query Bomb {
  recipes { ingredients { usedIn { ingredients { usedIn { ingredients { name } } } } } }
}
```

짧은 쿼리 하나가 리졸버 수백만 회 실행으로 번역된다. 인증된 사용자 한 명이 서비스를 멈출 수 있다는 뜻이다. 방어는 네 겹으로 쌓는다.

1. **깊이 제한(depth limit).** 중첩 깊이 상한을 둔다. 가장 싸고 즉시 효과가 있다.
2. **복잡도 점수(query cost).** 필드마다 비용을 매기고 요청 총합에 상한을 둔다. 리스트 필드는 예상 개수를 곱한다.
3. **영속 쿼리(persisted query).** 클라이언트가 보내는 것은 쿼리 문자열이 아니라 미리 등록된 쿼리의 해시뿐이다. 내부 서비스나 자사 앱만 상대한다면 이것이 가장 확실한 방어다.
4. **페이지네이션 강제.** 상한 없는 리스트 필드를 스키마에서 아예 없앤다.

**셋째, 캐싱이 어려워진다.** HTTP 캐싱은 URL을 키로 삼는다. GraphQL은 모든 요청이 같은 URL에 대한 `POST`이므로 CDN도, 리버스 프록시도, 브라우저 캐시도 아무 일을 할 수 없다. 22.1의 `GET /recipes/42`가 `Cache-Control` 헤더 한 줄로 공짜로 얻던 것을 GraphQL에서는 애플리케이션 계층에서 직접 만들어야 한다. 영속 쿼리를 `GET`으로 보내 URL 캐싱을 되살리거나, 리졸버 수준에서 Redis 캐시를 두거나(19장 참조), 클라이언트 측 정규화 캐시에 기대는 선택지가 있다. 어느 쪽이든 REST에서 공짜였던 것을 돈 주고 사는 일이다.

### 실무 함정

**HTTP 상태 코드가 항상 200이다.** 앞의 컨슈머 코드에서 본 그대로다. 오류는 본문의 `errors` 배열에 담겨 오고, 여기에는 파생 문제가 따라온다. 모니터링이 HTTP 상태 코드만 보면 오류율이 영원히 0%로 나온다. 로드 밸런서의 5xx 기반 자동 배제도 동작하지 않는다. GraphQL 서비스를 운영한다면 `errors` 배열을 파싱해 별도 메트릭으로 올려야 한다.

**부분 성공.** GraphQL 응답은 `data`와 `errors`를 동시에 가질 수 있다. 필드 셋 중 하나만 실패한 상태다. 컨슈머는 "성공이거나 실패거나" 대신 "일부만 성공"을 다루는 코드를 써야 하며, 이 분기를 빠뜨리면 화면에 빈 칸이 조용히 뜬다.

**타임아웃과 취소의 부재.** 리졸버 하나가 느리면 응답 전체가 느려진다. 리졸버에 `AbortSignal`을 컨텍스트로 전파해 두지 않으면, 클라이언트가 끊은 뒤에도 하부 조회가 계속 돌아간다.

**스키마의 조기 일반화.** "나중에 어떤 쿼리가 올지 모르니 다 열어 두자"는 접근은 방어할 수 없는 표면적을 만든다. 스키마는 실제 화면이 필요로 하는 것에서 출발해 필요할 때 넓히는 편이 안전하다.

## 22.3 gRPC: 프로토콜 버퍼 기반 RPC

### 왜 필요한가

HTTP/JSON과 GraphQL은 둘 다 텍스트 기반이고, 둘 다 요청마다 필드 이름을 반복해서 실어 보낸다. `{"id":42,"name":"김치찌개","servings":2}`에서 실제 데이터는 열 몇 바이트고 나머지는 이름과 구두점이다. 사람이 읽어야 하는 API에서는 이 낭비가 값을 하지만, 초당 수만 번 오가는 내부 서비스 간 통신에서는 그냥 낭비다.

gRPC는 다른 지점을 선택한다. 스키마(`.proto`)를 미리 공유하므로 전송 시에는 **필드 번호와 값만** 보내면 된다. 전송 계층은 HTTP/2이고, 코드 생성 덕분에 원격 호출이 로컬 함수 호출처럼 보인다. 대가는 사람이 못 읽는 바이너리와 브라우저에서 직접 못 쓴다는 제약이다.

### 프로토콜 버퍼 정의

```proto
// proto/recipe.proto
syntax = "proto3";

package recipe.v1;   // 패키지에 버전을 넣는다. 파괴적 변경 시 v2를 새로 만든다

service RecipeService {
  // 유너리: 요청 하나, 응답 하나
  rpc GetRecipe (GetRecipeRequest) returns (Recipe);
  // 서버 스트리밍: 요청 하나, 응답 여러 개
  rpc ListRecipes (ListRecipesRequest) returns (stream Recipe);
  // 클라이언트 스트리밍: 요청 여러 개, 응답 하나
  rpc ImportRecipes (stream Recipe) returns (ImportSummary);
  // 양방향 스트리밍
  rpc Watch (stream WatchRequest) returns (stream RecipeEvent);
}

message Recipe {
  uint32 id = 1;
  string name = 2;
  uint32 servings = 3;
  repeated Ingredient ingredients = 4;
  // 5번은 예전에 bool is_draft 였다. 재사용 금지
  reserved 5;
  reserved "is_draft";
  int64 updated_at_unix_ms = 6;
}

message Ingredient {
  uint32 id = 1;
  string name = 2;
  double quantity = 3;
  Unit unit = 4;
}

enum Unit {
  UNIT_UNSPECIFIED = 0;   // proto3에서 0번은 반드시 '지정되지 않음'이어야 한다
  UNIT_GRAM = 1;
  UNIT_MILLILITER = 2;
  UNIT_PIECE = 3;
}

message GetRecipeRequest { uint32 id = 1; }
message ListRecipesRequest { uint32 limit = 1; uint32 offset = 2; }
message ImportSummary { uint32 imported = 1; uint32 skipped = 2; }
message WatchRequest { repeated uint32 recipe_ids = 1; }
message RecipeEvent { uint32 recipe_id = 1; string kind = 2; }
```

`=` 뒤의 숫자는 기본값이 아니라 **필드 번호**다. 인코딩된 바이트열에는 필드 이름이 들어가지 않고 이 번호만 들어간다. 이것이 페이로드가 작아지는 이유이자, 다음에 볼 하위 호환 규칙 전체의 근거다.

### 필드 번호와 하위 호환

프로토콜 버퍼의 호환성 규칙은 전부 필드 번호에서 나온다. 실무에서 반드시 지켜야 하는 것은 다섯 가지다.

1. **필드 번호를 절대 바꾸지 않는다.** 번호를 바꾸는 것은 필드를 지우고 새로 만드는 것과 같다. 구버전 컨슈머는 새 번호를 모르는 필드로 무시하고, 옛 번호 자리에 다른 타입이 오면 값을 잘못 해석한다.
2. **삭제한 필드 번호는 `reserved`로 봉인한다.** 위 예제의 `reserved 5;`가 그것이다. 봉인하지 않으면 몇 달 뒤 누군가 5번을 `string image_url`로 재사용하고, 아직 배포되지 않은 구버전 서비스가 그 바이트를 `bool`로 읽는다. 타입이 우연히 호환되면 오류조차 나지 않고 값만 틀린다. 이름도 함께 예약(`reserved "is_draft"`)해 JSON 매핑에서의 충돌까지 막는다.
3. **필드 추가는 항상 안전하다.** 모르는 필드 번호를 만나면 파서는 그것을 건너뛴다. 그래서 새 필드를 붙이는 변경은 프로듀서와 컨슈머 배포 순서에 무관하게 안전하다.
4. **필수 필드라는 개념이 없다.** proto3에서 모든 필드는 선택적이며, 없으면 타입의 기본값(수는 0, 문자열은 빈 문자열)이 된다. 즉 **"보내지 않음"과 "0을 보냄"을 프로토콜이 구분해 주지 않는다.** 이 구분이 필요하면 `optional` 키워드를 붙이거나 래퍼 메시지를 쓴다. 이것을 모르고 "수량 0"과 "수량 미입력"을 같은 값으로 저장하는 버그가 흔하다.
5. **1~15번은 아껴 쓴다.** 필드 번호 1~15는 태그가 1바이트로 인코딩되고 16번부터는 2바이트다. 자주 등장하는 필드, 특히 `repeated` 안에 들어가는 메시지의 필드에 낮은 번호를 배정하면 페이로드가 실제로 줄어든다.

### 코드 생성 vs 동적 로딩

Node.js에서 `.proto`를 다루는 방법은 두 가지다.

**동적 로딩(dynamic codegen)** 은 런타임에 `.proto`를 파싱해 서비스 정의를 만든다. `@grpc/proto-loader`가 이 방식이며, 빌드 단계가 없어 시작이 빠르다.

**정적 코드 생성(static codegen)** 은 `protoc`로 미리 JavaScript/TypeScript 스텁을 생성한다. 타입 정의가 따라오고, 시작 시간이 짧으며, 런타임에 `.proto` 파일이 없어도 된다.

판단 기준은 단순하다. **JavaScript로 프로토타이핑한다면 동적 로딩, TypeScript로 프로덕션 서비스를 만든다면 정적 생성.** 타입 안전성이 gRPC를 쓰는 이유의 절반인데 동적 로딩은 그 절반을 포기하는 셈이기 때문이다. 프로세스 기동 시간도 무시할 수 없다. 큰 `.proto` 트리를 런타임에 파싱하면 콜드 스타트가 수백 밀리초 늘어난다.

여기서는 코드가 짧은 동적 로딩으로 보인다.

### recipe-api: gRPC 프로듀서

```js
// recipe-api/producer-grpc.mjs
import grpc from '@grpc/grpc-js'
import protoLoader from '@grpc/proto-loader'
import { db } from './db.mjs'

const def = protoLoader.loadSync(new URL('../proto/recipe.proto', import.meta.url).pathname, {
  keepCase: false,   // snake_case를 camelCase로 바꾼다. 팀 전체가 같은 값을 써야 한다
  longs: String,     // int64는 Number로 안전하지 않다. 문자열로 받는다
  enums: String,
  defaults: true
})
const proto = grpc.loadPackageDefinition(def).recipe.v1

const server = new grpc.Server({
  'grpc.max_receive_message_length': 8 * 1024 * 1024
})

server.addService(proto.RecipeService.service, {
  // 유너리: 콜백 스타일이다. async 함수를 그대로 넘길 수 없으므로 감싼다
  GetRecipe (call, callback) {
    const recipe = db.findRecipe(call.request.id)
    if (!recipe) {
      // gRPC 상태 코드는 HTTP와 다르다. NOT_FOUND는 5번이다
      return callback({ code: grpc.status.NOT_FOUND, details: 'recipe not found' })
    }
    callback(null, toProtoRecipe(recipe))
  },

  // 서버 스트리밍: call은 Writable 스트림이다
  async ListRecipes (call) {
    try {
      for await (const recipe of db.streamRecipes(call.request.limit)) {
        // 백프레셔를 존중한다. write가 false를 반환하면 drain을 기다린다(7장 참조)
        if (!call.write(toProtoRecipe(recipe))) {
          await new Promise((resolve) => call.once('drain', resolve))
        }
      }
      call.end()
    } catch (err) {
      call.destroy({ code: grpc.status.INTERNAL, details: err.message })
    }
  },

  // 클라이언트 스트리밍: call은 Readable 스트림이다
  async ImportRecipes (call, callback) {
    let imported = 0, skipped = 0
    for await (const recipe of call) {
      if (db.upsertRecipe(recipe)) imported++
      else skipped++
    }
    callback(null, { imported, skipped })
  },

  // 양방향 스트리밍: 읽기와 쓰기가 독립적으로 진행된다
  Watch (call) {
    const unsubscribe = db.subscribe((event) => call.write(event))
    call.on('data', (req) => db.updateWatchSet(call, req.recipeIds))
    call.on('end', () => { unsubscribe(); call.end() })
    call.on('error', unsubscribe)   // 클라이언트가 끊어도 구독은 반드시 정리한다
  }
})

server.bindAsync('127.0.0.1:4000', grpc.ServerCredentials.createInsecure(), () => {
  console.log('gRPC producer listening on 4000')
})
```

`toProtoRecipe`가 22.1에서 강조한 명시적 직렬화 함수의 gRPC판이다. gRPC에서는 스키마에 없는 필드가 애초에 인코딩되지 않으므로 유출 위험은 훨씬 낮지만, 도메인 객체와 전송 객체를 분리하는 습관 자체는 그대로 유지할 가치가 있다.

### 네 가지 스트리밍 모드

`.proto`에 `stream` 키워드를 어느 쪽에 붙이느냐로 네 가지 호출 모양이 결정된다.

| 모드 | 정의 | Node.js에서의 모양 | 쓰는 곳 |
|---|---|---|---|
| 유너리(unary) | `(Req) returns (Res)` | 콜백 / 프로미스 | 일반 조회·명령. 호출의 90% |
| 서버 스트리밍 | `(Req) returns (stream Res)` | Readable | 큰 목록, 진행 상황 보고, 구독 |
| 클라이언트 스트리밍 | `(stream Req) returns (Res)` | Writable | 대량 적재, 로그 전송, 파일 업로드 |
| 양방향 | `(stream Req) returns (stream Res)` | Duplex | 채팅, 실시간 동기화, 협상 프로토콜 |

스트리밍의 실질적 이점은 **메모리다**. 레시피 10만 개를 유너리로 돌려주려면 프로듀서가 배열 전체를 메모리에 만들고 직렬화해야 하지만, 서버 스트리밍은 한 건씩 흘려보내므로 상수 메모리로 끝난다(7장 참조). 다만 스트림은 상태를 가지므로 로드 밸런싱과 재시도가 어렵다. 유너리 호출은 실패하면 다른 인스턴스로 다시 보내면 되지만, 30분째 열려 있던 양방향 스트림이 끊기면 재개 지점을 애플리케이션이 직접 관리해야 한다. **기본은 유너리로 두고, 스트리밍은 이유가 있을 때만 쓴다.**

### HTTP/2 멀티플렉싱

gRPC가 HTTP/2 위에 있다는 사실은 성능에 직접 영향을 준다. HTTP/1.1에서는 하나의 TCP 연결에 요청 하나만 실을 수 있어서, 동시 요청 수만큼 연결이 필요했다. 22.1의 컨슈머가 `Promise.all`로 두 호출을 겹칠 때 실제로는 소켓 두 개가 쓰였다.

HTTP/2는 하나의 연결 안에 **스트림**을 여럿 만들어 요청을 병렬로 실어 나른다. 소켓 하나로 동시 요청 수백 개를 처리할 수 있으니 연결 수, TLS 핸드셰이크, 파일 디스크립터 소모가 모두 줄어든다. 헤더는 HPACK으로 압축되고 반복되는 헤더는 인덱스 참조로 대체되므로, 메타데이터 오버헤드도 크게 낮다.

두 가지 함정이 따라온다. 첫째, **L4 로드 밸런서 뒤에서 부하가 쏠린다.** 연결 하나가 오래 유지되면서 그 위로 모든 요청이 흐르므로, 연결 단위로 분배하는 로드 밸런서는 백엔드 하나에 트래픽을 몰아준다. HTTP/2를 이해하는 L7 프록시를 쓰거나, 클라이언트 측 로드 밸런싱을 쓰거나, 주기적으로 연결을 재수립해야 한다(26장 참조). 둘째, **HOL 블로킹이 TCP 계층으로 이동한다.** 애플리케이션 계층의 head-of-line 블로킹은 사라졌지만, 패킷 손실이 나면 하나의 TCP 연결을 공유하는 모든 스트림이 함께 멈춘다. 손실률이 높은 네트워크에서는 오히려 불리할 수 있다.

### web-api: gRPC 컨슈머

```js
// web-api/consumer-grpc.mjs
import grpc from '@grpc/grpc-js'
import protoLoader from '@grpc/proto-loader'
import Fastify from 'fastify'
import { promisify } from 'node:util'

const def = protoLoader.loadSync(new URL('../proto/recipe.proto', import.meta.url).pathname,
  { keepCase: false, longs: String, enums: String, defaults: true })
const proto = grpc.loadPackageDefinition(def).recipe.v1

const client = new proto.RecipeService('127.0.0.1:4000',
  grpc.credentials.createInsecure(), {
    // 유휴 연결이 죽는 것을 막는다. NAT/로드 밸런서 뒤에서 특히 중요하다
    'grpc.keepalive_time_ms': 30_000,
    'grpc.keepalive_timeout_ms': 10_000
  })

// 콜백 API를 프로미스로 바꾼다(6장 참조)
const getRecipe = promisify(client.GetRecipe.bind(client))

const server = Fastify({ logger: true })

server.get('/dishes/:id', async (req, reply) => {
  try {
    // deadline은 절대 시각이다. gRPC는 이 데드라인을 헤더로 전파하므로
    // 하위 서비스까지 자동으로 이어진다 — HTTP에서 직접 만들어야 했던 것이다
    const recipe = await getRecipe(
      { id: Number(req.params.id) },
      { deadline: Date.now() + 800 }
    )
    return recipe
  } catch (err) {
    if (err.code === grpc.status.NOT_FOUND) return reply.code(404).send({ error: 'not_found' })
    if (err.code === grpc.status.DEADLINE_EXCEEDED) return reply.code(504).send({ error: 'timeout' })
    throw err
  }
})

await server.listen({ host: '127.0.0.1', port: 3000 })
```

데드라인이 프로토콜에 내장되어 있다는 점이 눈에 띈다. HTTP에서는 15장에서 본 것처럼 데드라인 헤더를 직접 정의하고 계층마다 전파해야 했지만, gRPC는 데드라인을 `grpc-timeout` 헤더로 자동 전파하고 만료 시 진행 중인 작업을 취소한다. 분산 시스템에서 이것은 작지 않은 이점이다.

### 실무 함정

**`int64`와 JavaScript의 수.** `longs: String` 옵션을 빼먹으면 큰 정수가 조용히 망가진다. 타임스탬프와 ID는 특히 위험하다.

**gRPC 상태 코드를 HTTP 상태 코드로 착각하는 것.** gRPC의 코드 체계는 17개로 별도이며, `INVALID_ARGUMENT`(3), `NOT_FOUND`(5), `UNAVAILABLE`(14), `DEADLINE_EXCEEDED`(4)가 자주 쓰인다. 게이트웨이에서 HTTP로 번역할 때 매핑 표를 한 곳에 두어야 한다.

**메시지 크기 상한.** 기본 수신 상한은 4MB다. 초과하면 `RESOURCE_EXHAUSTED`로 끊기는데, 큰 목록을 유너리로 돌려주다 프로덕션에서 처음 만나는 경우가 많다. 상한을 올리기보다 서버 스트리밍이나 페이지네이션으로 바꾸는 것이 옳은 대응이다.

**스트림 정리 누락.** 위 `Watch` 구현에서 `error`와 `end` 양쪽에서 구독을 해제한 이유다. 한쪽만 처리하면 클라이언트가 비정상 종료할 때마다 리스너가 쌓여 메모리 누수가 된다(4장 참조).

**디버깅 도구를 준비하지 않는 것.** 바이너리라서 `curl`과 브라우저 개발자 도구가 무력하다. `grpcurl`을 CI에 넣어 두고, 서버 리플렉션(reflection)을 개발 환경에서 켜 두면 고통이 크게 줄어든다.

## 22.4 프로토콜 선택 기준과 성능 비교

같은 기능을 세 번 구현했으니 이제 비교할 수 있다. 먼저 수치를 보고, 그다음 수치가 결정하지 못하는 것들을 본다.

### 페이로드 크기

레시피 한 건에 재료 여섯 개가 붙은 응답을 세 방식으로 인코딩하면 대략 이렇게 나온다.

| 인코딩 | 크기 | 기준 대비 |
|---|---|---|
| JSON (들여쓰기 포함) | 약 780B | 1.55× |
| JSON (최소화) | 약 500B | 1.00× |
| JSON + gzip 레벨 6 | 약 260B | 0.52× |
| GraphQL 응답 (요청 필드만) | 약 320B | 0.64× |
| 프로토콜 버퍼 | 약 180B | 0.36× |
| 프로토콜 버퍼 + gzip | 약 160B | 0.32× |

두 가지가 눈에 띈다. 첫째, GraphQL이 JSON보다 작은 이유는 인코딩이 효율적이어서가 아니라 **필요 없는 필드를 애초에 안 보내기 때문**이다. 전체 필드를 요청하면 JSON과 같아진다. 둘째, 프로토콜 버퍼는 이미 압축된 것에 가까워서 gzip을 추가해도 이득이 작다. 필드 이름이 없고 정수가 varint로 인코딩되어 있으니 압축기가 제거할 중복이 별로 남아 있지 않다.

### 처리량

`autocannon`(HTTP/GraphQL)과 `ghz`(gRPC)로 같은 기계에서 같은 핸들러를 때렸을 때 나오는 대략적인 비율은 다음과 같다. **절대값은 의미가 없고 배수만 보라.** 페이로드 크기, 핸들러의 실제 작업량, keep-alive 설정, TLS 여부, 코어 수에 따라 결과가 크게 달라진다.

| 구성 | 상대 처리량 | p99 지연(상대) |
|---|---|---|
| HTTP/JSON, keep-alive, 응답 스키마 있음 | 1.00× | 1.00× |
| HTTP/JSON, keep-alive 없음 | 0.25~0.4× | 2~4× |
| HTTP/JSON + gzip(작은 페이로드) | 0.75~0.9× | 1.1~1.3× |
| GraphQL(같은 데이터, 단순 쿼리) | 0.5~0.7× | 1.3~1.8× |
| gRPC 유너리 | 1.5~2.5× | 0.5~0.8× |
| gRPC 서버 스트리밍(건당) | 3~8× | — |

읽어 낼 것은 세 가지다.

첫째, **연결 재사용이 프로토콜 선택보다 영향이 크다.** keep-alive를 끄면 같은 HTTP/JSON이 4배 가까이 느려진다. gRPC로 바꿔 얻는 2배보다 큰 차이다. 프로토콜을 바꾸기 전에 커넥션 풀부터 확인하는 것이 순서다.

둘째, **GraphQL은 같은 데이터에 대해 순수한 오버헤드다.** 쿼리를 파싱하고 검증하고 리졸버 트리를 실행하는 비용이 붙는다. GraphQL이 이기는 지점은 초당 처리량이 아니라 **왕복 횟수**이므로, 화면 하나에 REST 호출 다섯 번이 필요하던 상황과 비교해야 정당한 비교가 된다. 그 비교에서는 GraphQL이 압도한다.

셋째, **gRPC의 이점은 페이로드가 클수록 커진다.** 200바이트짜리 응답에서는 직렬화 비용 차이가 미미하지만, 수천 건의 목록을 주고받으면 JSON 파싱이 CPU를 크게 먹는다. 대량 데이터 이동이 있는 내부 서비스 간 통신에서 gRPC가 가장 확실하게 이기는 이유다.

### 종합 비교

| 항목 | HTTP/JSON | GraphQL | gRPC |
|---|---|---|---|
| 페이로드 크기 | 보통 | 요청에 따라 가변 | 작음 (약 1/3) |
| 처리량 | 기준 | 기준의 0.5~0.7× | 기준의 1.5~2.5× |
| 스키마 강제 | 없음(OpenAPI로 별도 관리) | 강제 (런타임 검증) | 강제 (컴파일/생성 시점) |
| 하위 호환 관리 | 규율에 의존 | 스키마 폐기(deprecation) | 필드 번호 규칙으로 구조적 보장 |
| 브라우저 지원 | 네이티브 | 네이티브(그냥 POST) | 불가 — grpc-web 프록시 필요 |
| 스트리밍 | SSE/WebSocket 별도 | 구독(subscription) 별도 | 프로토콜에 내장 (4가지 모드) |
| 디버깅 | `curl` 한 줄 | GraphiQL, 본문이 텍스트 | `grpcurl` 필요, 바이너리 |
| 캐싱 | HTTP 캐시 그대로 사용 | 어려움(전부 POST) | 없음(직접 구현) |
| 관측성 도구 | 모든 APM이 기본 지원 | 쿼리 단위 계측 필요 | 대부분 지원, 설정 필요 |
| 도구 생태계 | 가장 넓음 | 프런트엔드 도구가 강함 | 폴리글랏 코드 생성이 강함 |
| 데드라인 전파 | 직접 구현 | 직접 구현 | 프로토콜 내장 |
| 학습 비용 | 낮음 | 중간 | 중간~높음 |

### 판단 기준

수치보다 중요한 것은 **누가 이 API를 쓰는가**다. 세 가지 답이 곧 세 가지 선택이다.

**외부에 공개하는 API라면 HTTP/JSON이다.** 통제할 수 없는 다양한 컨슈머가 상대이므로 보편성과 디버깅 편의성이 다른 모든 항목을 압도한다. 파트너사 개발자가 `curl`로 5분 만에 첫 호출에 성공하는 것이, 페이로드가 3배 작은 것보다 훨씬 큰 가치를 만든다. OpenAPI 스펙과 명시적 직렬화 함수로 스키마 부재를 보완하면 실무에서 충분하다.

**프런트엔드가 여러 백엔드의 데이터를 조합해야 한다면 GraphQL이다.** 화면 하나에 서비스 서너 개의 데이터가 필요하고, 웹·iOS·안드로이드가 각각 다른 필드를 요구하며, 화면 변경 주기가 백엔드 배포 주기보다 훨씬 짧은 상황. 이 조건이 갖춰졌을 때 GraphQL은 백엔드 팀을 화면 변경 요청에서 해방시킨다. 조건이 갖춰지지 않았는데 도입하면 DataLoader와 복잡도 제한과 캐싱 문제만 떠안는다. **GraphQL은 프런트엔드 조직이 여럿일 때 값을 하는 기술**이지, 성능 기술이 아니다.

**내부 서비스 간 고빈도 통신이라면 gRPC다.** 양쪽 모두를 우리가 통제하고, 호출 빈도가 높고, 스키마 불일치가 장애로 이어지는 구간. 여기서 gRPC는 처리량과 페이로드 크기뿐 아니라 **스키마 강제와 데드라인 전파**로 값을 한다. 특히 서비스 수가 늘고 언어가 섞이기 시작하면 `.proto` 하나로 여러 언어의 클라이언트를 생성하는 능력이 결정적이다.

세 가지를 배타적으로 고를 필요는 없다는 점도 덧붙인다. 실무에서 가장 흔한 조합은 **경계에서는 HTTP/JSON 또는 GraphQL, 내부에서는 gRPC**다. 22.1의 web-api를 외부에는 HTTP/JSON으로 노출하고 recipe-api와는 gRPC로 통신하게 두는 형태다. 각 프로토콜이 잘하는 자리에 배치하는 것이 하나를 고르는 것보다 대체로 낫다.

마지막으로 경고를 하나 남긴다. 프로토콜 교체는 **거의 언제나 병목이 아니다**. 응답이 느린 이유의 대부분은 직렬화가 아니라 인덱스 없는 쿼리, 순차 실행된 하위 호출, 이벤트 루프를 막는 계산이다. gRPC로 갈아타서 2배를 얻기 전에, 병렬화와 캐싱으로 10배를 얻을 여지가 남아 있지 않은지부터 확인하는 것이 순서다.

## 요약

- HTTP 메서드는 이름표가 아니라 안전성·멱등성 계약이며, 이 계약이 곧 컨슈머의 재시도 정책이다. 4xx는 재시도 불가, 5xx와 429는 재시도 가능이라는 구분을 프로듀서가 지켜야 컨슈머의 재시도가 의미를 갖는다.
- 서비스 간 통신에서 압축은 무조건적 이득이 아니다. 저지연 내부 네트워크에서 작은 페이로드를 압축하면 절약하는 전송 시간보다 태우는 CPU가 크다. 임계값을 8KB 이상으로 올리고 레벨을 낮추거나, 프록시에 위임한다. TLS 비용은 거의 전부 핸드셰이크에 있으므로 연결 재사용으로 상수화한다.
- 클래스 인스턴스를 그대로 `JSON.stringify`하면 메서드가 사라지고, 새로 생긴 내부 필드가 아무 오류 없이 유출되며, 응답 모양이 코드의 부수 효과로 바뀐다. 명시적 직렬화 함수(허용 목록)와 응답 스키마를 함께 둔다.
- GraphQL은 오버페칭과 왕복 횟수 문제를 컨슈머에서 프로듀서로 옮긴다. 대신 N+1 리졸버 쿼리(DataLoader로 배칭, 요청마다 새 인스턴스), 쿼리 복잡도 공격(깊이 제한·복잡도 점수·영속 쿼리), HTTP 캐싱 불가라는 세 가지 문제를 새로 만든다.
- gRPC의 하위 호환성은 전부 필드 번호 규칙에서 나온다. 번호를 바꾸지 않고, 삭제한 번호는 `reserved`로 봉인하며, 추가는 언제나 안전하다. proto3에는 필수 필드가 없어 "미전송"과 "기본값"이 구분되지 않는다는 점을 설계에 반영해야 한다.
- gRPC는 네 가지 스트리밍 모드와 HTTP/2 멀티플렉싱, 데드라인 전파를 프로토콜 수준에서 제공한다. 대신 브라우저에서 직접 쓸 수 없고, L4 로드 밸런서 뒤에서 부하가 쏠린다.
- 선택 기준은 성능이 아니라 컨슈머다. 외부 공개 API는 HTTP/JSON, 프런트엔드 집약은 GraphQL, 내부 고빈도 통신은 gRPC. 경계와 내부에 서로 다른 프로토콜을 두는 조합이 실무에서 가장 흔하다. 그리고 프로토콜 교체는 거의 언제나 진짜 병목이 아니다.

## 연습문제

1. **직렬화 유출 재현과 방어** — recipe-api의 `Recipe` 클래스에 `costCents`와 `internalNote` 필드를 추가하되 응답 스키마와 직렬화 함수는 건드리지 마라. 그다음 (가) 도메인 객체를 그대로 반환하는 핸들러, (나) `toJSON()`을 둔 핸들러, (다) Fastify 응답 스키마를 지정한 핸들러 세 가지를 만들어 각각의 실제 응답 본문을 비교하라. 어느 경우에 새 필드가 유출되는지 확인하고, `Date`·`Map`·`BigInt` 필드를 추가했을 때 세 방식이 각각 어떻게 동작하는지 표로 정리하라.

2. **DataLoader 유무의 쿼리 수 측정** — 22.2의 GraphQL 프로듀서에서 DB 계층에 쿼리 카운터를 붙여라. `recipes(limit: 20) { name ingredients { name } }` 쿼리를 DataLoader 없이, 그리고 있게 실행해 발생한 쿼리 수와 p99 지연을 비교하라. 이어서 DataLoader 인스턴스를 모듈 수준 싱글턴으로 옮겼을 때 어떤 문제가 생기는지 서로 다른 인증 주체로 두 요청을 보내 실증하고, 왜 요청 범위여야 하는지 서술하라. 마지막으로 `queryDepth` 제한을 끄고 순환 쿼리를 보내 리졸버 호출 수가 어떻게 증가하는지 측정하라.

3. **세 프로토콜 벤치마크와 호환성 실험** — 같은 조회 기능을 HTTP/JSON, GraphQL, gRPC 유너리로 구현하고 `autocannon`과 `ghz`로 처리량·p99·페이로드 크기를 측정해 22.4의 표와 비교하라. 이어서 응답에 재료를 6개에서 500개로 늘려 세 방식의 배수 차이가 어떻게 변하는지 확인하라. 마지막으로 `.proto`에서 `servings` 필드의 번호를 3에서 7로 바꾼 뒤 구버전 클라이언트로 호출해 어떤 값이 오는지 관찰하고, `reserved`를 쓰지 않고 3번을 `string`으로 재사용했을 때 벌어지는 일을 기록하라.
