# 30장. 테스팅

테스트는 코드가 옳다는 것을 증명하지 않는다. 특정 조건에서 특정 관찰이 성립한다는 것만 보여줄 뿐이다. 이 한계를 인정하는 순간 질문이 달라진다. "얼마나 많이 테스트할 것인가"가 아니라 "무엇을 관찰해야 배포를 결정할 수 있는가"가 된다.

이 장은 그 질문에 답하는 도구를 다룬다. Node.js에 내장된 `node:test` 러너를 1급 도구로 놓고, 비동기 코드 특유의 함정, 테스트 더블의 정확한 구분, 실제 HTTP와 실제 데이터베이스를 쓰는 통합 테스트, 그리고 커버리지 숫자가 무엇을 말하고 무엇을 말하지 않는지를 정리한다. 마지막 절에서는 테스트가 실패한 뒤에 필요한 것, 즉 디버깅을 다룬다.

외부 러너를 쓰든 내장 러너를 쓰든 이 장의 개념은 그대로 옮겨진다. 달라지는 것은 API의 철자뿐이다.

## 30.1 테스트 피라미드: 단위·통합·기능 테스트

### 각 층이 보장하는 것

테스트 피라미드는 세 층을 비용과 개수의 반비례 관계로 배치한다. 아래로 갈수록 싸고 많고, 위로 갈수록 비싸고 적다. 그러나 이 그림의 핵심은 개수가 아니라 **각 층이 보장하는 명제가 다르다**는 점이다.

**단위 테스트(unit test)**는 하나의 함수 또는 하나의 모듈이 주어진 입력에 대해 명세된 출력을 낸다는 것을 보장한다. 프로세스 하나 안에서 밀리초 단위로 끝나고, 실패했을 때 원인 위치가 거의 확정된다. 반대로 보장하지 않는 것이 많다. 그 모듈이 실제로 호출되는지, 호출하는 쪽이 넘기는 인자의 모양이 테스트에서 쓴 것과 같은지, 의존성을 대체한 스텁이 실제 구현과 같은 계약을 지키는지는 전혀 알려주지 않는다. 단위 테스트가 100% 통과하는데 애플리케이션이 부팅조차 못 하는 상황은 흔하다.

**통합 테스트(integration test)**는 두 개 이상의 구성 요소가 실제 경계를 넘어 상호작용할 때 계약이 맞는다는 것을 보장한다. 리포지토리가 실제 PostgreSQL에 던지는 SQL이 문법적으로 유효하고, 컬럼 이름이 실제 스키마와 일치하며, 트랜잭션 경계가 의도대로 동작한다는 사실은 오직 실제 데이터베이스에 붙어야만 알 수 있다. 대신 느리고, 외부 상태에 의존하므로 격리가 깨지면 순서 의존성과 플레이키(flaky) 실패가 생긴다.

**기능 테스트(functional test) 또는 E2E**는 사용자가 실제로 하는 일이 끝에서 끝까지 성립한다는 것을 보장한다. 라우팅, 직렬화, 인증 미들웨어, 에러 핸들러, 상태 코드까지 전부 포함된다. 대신 가장 비싸고, 실패했을 때 원인이 어디인지 알려주지 않는다. "결제 API가 500을 반환한다"는 정보만으로는 디버깅이 시작조차 되지 않는다.

### 비용과 신뢰도의 트레이드오프

이 세 층의 관계를 두 축으로 요약할 수 있다. 첫째 축은 **실행 비용**이다. 단위 테스트 1,000개가 2초에 끝나는 동안 E2E 10개가 3분을 쓴다. 둘째 축은 **결함 검출력**, 즉 실패했을 때 그 실패가 진짜 사용자 문제를 뜻할 확률이다. 여기서는 순서가 정확히 뒤집힌다. 단위 테스트 실패의 상당수는 리팩터링에 따른 잡음이고, E2E 실패는 거의 항상 진짜 문제다.

여기서 세 번째 축이 숨어 있다. **변경에 대한 저항성**이다. 내부 구현에 밀착한 단위 테스트는 동작이 그대로여도 구조를 바꾸면 깨진다. 이런 테스트는 회귀를 잡아주는 대신 리팩터링 비용을 올린다. 좋은 테스트의 기준은 "구현이 아니라 관찰 가능한 동작을 검증하는가"이며, 이 기준을 지키면 단위 테스트도 리팩터링에 살아남는다.

실무의 판단 기준은 단순하다. **이 테스트가 실패했을 때 배포를 막을 것인가.** 막지 않을 테스트라면 CI에 넣을 이유가 약하다. 반대로 막을 테스트라면 그 실패가 진짜여야 하므로, 플레이키한 테스트는 즉시 격리하거나 고쳐야 한다. 무시되기 시작한 실패는 전체 스위트의 신뢰를 무너뜨린다.

### 아이스크림 콘 안티패턴

피라미드가 뒤집힌 형태를 아이스크림 콘(ice cream cone)이라 부른다. 맨 위에 수동 테스트가 두껍게 얹히고, 그 아래 E2E가 많고, 통합이 조금, 단위가 거의 없는 구조다.

이 구조는 대개 의도적으로 만들어지지 않는다. 단위 테스트를 쓰기 어려운 코드에서 자연스럽게 발생한다. 모듈이 임포트 시점에 데이터베이스 커넥션을 만들고, 설정을 전역에서 읽고, 시간과 난수를 직접 참조하면 그 모듈은 단위로 테스트할 수 없다. 남은 선택지는 전체를 띄워서 밖에서 두드리는 것뿐이다. 즉 아이스크림 콘은 테스트 전략의 실패이기 이전에 **설계의 실패**다. 의존성 주입(12장 참조)이 테스트 전략의 문제로 다뤄지는 이유가 여기 있다.

증상은 명확하다. CI가 40분씩 걸리고, 실패하면 일단 재실행부터 하며, "그 테스트는 원래 가끔 깨진다"는 말이 팀 내에서 통용된다. 이 상태에서 E2E를 더 늘리면 상황은 악화된다. 해법은 E2E를 줄이는 것이 아니라, E2E가 잡던 결함 중 아래 층에서 잡을 수 있는 것을 아래로 내리는 것이다. 스키마 불일치는 통합 테스트로, 계산 로직 오류는 단위 테스트로 내려간다. E2E에는 핵심 사용자 여정 몇 개만 남긴다.

반대 극단도 있다. 단위 테스트만 잔뜩 있고 통합이 없는 구조다. 이 경우 모든 테스트가 통과하는데 프로덕션이 깨진다. 실무에서 가장 투자 대비 효과가 좋은 층은 대체로 중간, 즉 실제 프로세스와 실제 데이터 저장소를 쓰되 브라우저나 외부 SaaS는 제외한 통합 테스트다.

## 30.2 `node:test`와 `node:assert` 내장 러너

### 왜 내장 러너인가

Node.js 20 LTS부터 `node:test`는 안정화된 표준 모듈이다. 의존성이 0개이고, 러너를 위한 설정 파일이 필요 없으며, Node.js 버전과 함께 업그레이드된다. 라이브러리나 서버 애플리케이션처럼 브라우저 DOM이 필요 없는 코드에서는 이것으로 충분한 경우가 대부분이다.

### 기본 구조

```js
// src/money.js
export function splitEvenly(amountCents, parts) {
  if (!Number.isInteger(amountCents)) throw new TypeError('amountCents must be an integer')
  if (parts < 1) throw new RangeError('parts must be >= 1')
  const base = Math.floor(amountCents / parts)
  const remainder = amountCents - base * parts
  // 나머지는 앞쪽 몫에 1센트씩 분배해 합계가 보존되게 한다
  return Array.from({ length: parts }, (_, i) => base + (i < remainder ? 1 : 0))
}
```

```js
// test/money.test.js
import { describe, it } from 'node:test'
import assert from 'node:assert/strict'
import { splitEvenly } from '../src/money.js'

describe('splitEvenly', () => {
  it('나눠떨어지는 금액을 균등 분할한다', () => {
    assert.deepStrictEqual(splitEvenly(1000, 4), [250, 250, 250, 250])
  })

  it('나머지를 앞쪽부터 1센트씩 분배한다', () => {
    assert.deepStrictEqual(splitEvenly(1001, 3), [334, 334, 333])
  })

  it('분할 후 합계가 보존된다', () => {
    for (const amount of [1, 7, 99, 100003]) {
      const parts = splitEvenly(amount, 7)
      assert.equal(parts.reduce((a, b) => a + b, 0), amount)
    }
  })

  it('정수가 아닌 금액을 거부한다', () => {
    assert.throws(() => splitEvenly(10.5, 2), TypeError)
  })
})
```

실행은 `node --test`다. Node.js 22부터는 `**/*.test.js`, `**/test-*.js`, `test/` 디렉터리 아래 파일 등을 기본 패턴으로 탐색하므로 별도 인자가 필요 없다. 명시적으로 좁히려면 `node --test test/`처럼 경로를 준다.

`test`와 `it`은 같은 함수이고, `describe`/`it`은 다른 러너에서 온 사람을 위한 별칭 계층이다. 중첩은 자유롭다.

```js
import { test } from 'node:test'
import assert from 'node:assert/strict'

test('parser', async (t) => {
  await t.test('헤더를 읽는다', () => {
    assert.equal(1, 1)
  })
  await t.test('본문을 읽는다', () => {
    assert.equal(2, 2)
  })
})
```

중첩 테스트에서 `await`를 빠뜨리면 하위 테스트가 부모 완료 이후에 끝나 결과가 어긋난다. `t.test()`를 쓸 때는 항상 `await`하거나 `describe`/`it` 형태를 쓴다.

### 훅

`before`/`after`는 스위트 전체에 한 번, `beforeEach`/`afterEach`는 각 테스트마다 실행된다.

```js
import { describe, it, before, after, beforeEach } from 'node:test'
import assert from 'node:assert/strict'
import { createDb } from '../src/db.js'

describe('UserRepository', () => {
  let db

  before(async () => {
    db = await createDb(process.env.TEST_DATABASE_URL)
    await db.migrate()
  })

  after(async () => {
    await db.close()
  })

  beforeEach(async () => {
    await db.query('TRUNCATE users RESTART IDENTITY CASCADE')
  })

  it('사용자를 저장하고 다시 읽는다', async () => {
    const saved = await db.users.insert({ email: 'a@example.com' })
    assert.equal((await db.users.findById(saved.id)).email, 'a@example.com')
  })
})
```

훅이 비동기라면 반드시 프로미스를 반환해야 한다. `before(async () => { ... })`처럼 `async` 함수를 넘기면 러너가 완료를 기다린다. 콜백 스타일이 필요하면 두 번째 인자 `done`을 받는다.

테스트 컨텍스트에도 `t.after()`가 있어 정리 코드를 생성 지점 옆에 둘 수 있다. 서버나 컨테이너처럼 테스트마다 자원을 만드는 경우에 훨씬 안전하다.

```js
it('임시 서버를 띄운다', async (t) => {
  const server = await startServer()
  t.after(() => server.close())   // 실패해도 반드시 실행된다
  assert.ok(server.address().port > 0)
})
```

### 스킵, todo, only

```js
it('아직 구현되지 않았다', { todo: true }, () => {})
it('리눅스에서만 유효하다', { skip: process.platform !== 'linux' }, () => {})

it('런타임 조건으로 건너뛴다', (t) => {
  if (!process.env.REDIS_URL) return t.skip('REDIS_URL 미설정')
  // ...
})

it('이것만 실행', { only: true }, () => {})   // node --test --test-only
```

`skip`은 "지금 실행할 수 없다", `todo`는 "아직 작성되지 않았다"로 의미가 다르다. `todo` 테스트는 실패해도 스위트를 실패시키지 않으므로, 명세를 먼저 적어두는 용도로 쓴다.

### 동시 실행

Node.js는 기본적으로 **파일 단위로 별도 프로세스**를 띄워 병렬 실행한다. 기본 병렬도는 CPU 코어 수이며 `--test-concurrency=N`으로 조절한다. 파일 간 격리는 프로세스 격리이므로 전역 오염 걱정이 없다.

한 파일 안의 테스트는 기본적으로 순차 실행된다. I/O 대기가 지배적인 테스트라면 파일 내부 병렬화가 크게 이득이다.

```js
describe('외부 API 클라이언트', { concurrency: 4 }, () => {
  it('a', async () => { /* ... */ })
  it('b', async () => { /* ... */ })
})
```

`concurrency: true`는 무제한을 뜻한다. 주의할 점은 **훅의 의미가 달라진다**는 것이다. 동시 실행 중인 테스트들이 `beforeEach`에서 같은 데이터베이스 테이블을 비우면 서로의 데이터를 지운다. 공유 상태를 건드리는 테스트는 동시 실행하지 않거나, 테스트마다 독립 스키마를 잡아야 한다(30.6 참조).

### 스냅숏

Node.js 22.3부터 테스트 컨텍스트에 스냅숏 어서션이 있다.

```js
it('렌더 결과가 유지된다', (t) => {
  t.assert.snapshot(renderInvoice({ total: 1999, currency: 'KRW' }))
})
```

첫 실행은 `--test-update-snapshots`로 `*.snapshot` 파일을 만들고, 이후 실행은 그 파일과 비교한다. 스냅숏은 직렬화 가능한 출력(HTML 조각, 설정 객체, 에러 메시지 포맷)에 유효하다. 남용하면 "무엇이 왜 옳은지" 대신 "지난번과 같은지"만 검증하게 되어, 잘못된 출력이 그대로 고착된다. 리뷰에서 스냅숏 diff를 실제로 읽지 않는 순간 이 테스트는 가치를 잃는다.

### 필터링, 워치, 리포터

```bash
# 이름으로 필터 (정규식)
node --test --test-name-pattern="rate limit"
# 파일 변경 시 관련 테스트 재실행
node --test --watch
# 리포터 지정: spec, tap, dot, junit, lcov
node --test --test-reporter=spec
# CI용: 사람이 읽을 출력과 기계용 리포트를 동시에
node --test \
  --test-reporter=spec --test-reporter-destination=stdout \
  --test-reporter=junit --test-reporter-destination=test-results.xml
```

`--test-name-pattern`은 부모 이름과 자식 이름 모두에 적용되므로, `describe` 블록 이름으로 묶어 필터링하면 편하다.

### `node:assert`의 strict 모드

`node:assert/strict`를 쓰면 모든 어서션이 엄격 비교를 쓴다. 느슨한 `assert.equal`(== 비교)은 `'1' == 1`을 통과시켜 타입 버그를 숨기므로, 예외 없이 strict를 임포트한다.

Node.js 22부터는 테스트 컨텍스트에 어서션이 붙어 있어 별도 임포트 없이 쓸 수 있고, 어서션 횟수 검증도 가능하다.

```js
it('정확히 두 번 검증한다', (t) => {
  t.plan(2)
  t.assert.equal(1 + 1, 2)
  t.assert.ok(true)
})
```

`t.plan()`은 비동기 콜백 안의 어서션이 실행되지 않고 테스트가 끝나버리는 사고를 막아준다(30.4 참조).

### `deepStrictEqual`의 함정

`deepStrictEqual`은 편리하지만 규칙이 많다. 실무에서 걸리는 지점을 정리한다.

**프로토타입까지 비교한다.** 클래스 인스턴스와 같은 속성을 가진 평범한 객체는 같지 않다. ORM이 돌려주는 모델 인스턴스를 리터럴과 비교하면 실패한다.

```js
class User { constructor(id) { this.id = id } }
assert.deepStrictEqual(new User(1), { id: 1 })   // 실패: 프로토타입 불일치
assert.deepStrictEqual({ ...new User(1) }, { id: 1 })   // 통과
```

**`undefined` 값을 가진 키와 없는 키는 다르다.** `{ a: 1, b: undefined }`와 `{ a: 1 }`은 같지 않다. JSON 직렬화를 거치면 사라지는 차이라서 특히 헷갈린다.

**타입이 정확히 일치해야 한다.** `Buffer`와 `Uint8Array`, `1`과 `1n`, `new Date(0)`과 `0`은 모두 다르다.

**`NaN`은 자기 자신과 같고, `+0`과 `-0`은 다르다.** `Object.is` 의미론을 따른다.

**`Map`과 `Set`은 순서를 보지 않지만 배열은 본다.** 정렬이 보장되지 않는 쿼리 결과를 배열로 비교하면 간헐적으로 실패한다. 비교 전에 정렬하거나 `Set`으로 바꾼다.

**에러는 이름과 메시지, 그리고 자체 열거 가능 속성으로 비교된다.** 스택은 비교하지 않는다. 에러 검증은 `assert.throws`의 두 번째 인자로 하는 편이 명확하다.

```js
assert.throws(
  () => splitEvenly(1000, 0),
  { name: 'RangeError', message: /parts must be/ }
)
```

부분 비교가 필요하면 Node.js 22.13 이상의 `assert.partialDeepStrictEqual`을 쓰거나, 비교 전에 관심 있는 필드만 뽑아낸다. 후자가 테스트의 의도를 더 잘 드러낸다. 응답 객체 전체를 통째로 비교하는 테스트는 무관한 필드가 추가될 때마다 깨지면서, 정작 중요한 필드가 무엇인지는 알려주지 않는다.

## 30.3 대안 러너: Vitest, Jest의 선택 기준

### 내장 러너로 충분한 경우

다음 조건이 모두 참이면 `node:test`로 충분하고, 외부 러너를 도입하는 것은 순수한 비용이다.

- 코드가 서버·CLI·라이브러리이고 DOM이나 브라우저 API를 흉내 낼 필요가 없다.
- 소스가 자바스크립트이거나, 타입스크립트라도 Node.js의 타입 제거(`--experimental-strip-types`, Node.js 22.6 이상, 23.6부터 기본 활성) 또는 사전 빌드로 처리된다.
- 의존성을 생성자·팩터리 인자로 받는 구조여서 모듈 자체를 가로챌 필요가 거의 없다.
- 어서션이 `strict` 계열과 `throws`/`rejects`로 표현 가능하다.

이 경우 얻는 것이 분명하다. `node_modules`에 러너 트리가 없고, 러너 설정 파일과 트랜스폼 파이프라인이라는 두 번째 빌드 시스템이 생기지 않으며, 러너 버전과 Node.js 버전이 어긋나 생기는 문제가 없다. 특히 오픈소스 라이브러리라면 기여자가 설치할 것이 줄어드는 이점이 크다.

### 외부 러너가 필요한 경우

**브라우저 환경 모사.** React 컴포넌트나 DOM을 다루는 코드는 `document`가 필요하다. Vitest는 `environment: 'jsdom'` 또는 `happy-dom` 한 줄로 제공하고, 실제 브라우저에서 돌리는 브라우저 모드도 있다. `node:test`에는 이런 계층이 없다.

**변환 파이프라인.** JSX, 데코레이터, 경로 별칭(`@/utils`), CSS 임포트처럼 Node.js가 그대로 이해하지 못하는 것을 소스에서 쓴다면 트랜스폼이 필요하다. Vitest는 애플리케이션이 이미 쓰는 Vite 설정을 그대로 재사용하므로 테스트와 프로덕션 빌드의 해석 규칙이 자동으로 일치한다. 이 일관성이 Vitest의 가장 큰 실용적 장점이다.

**모듈 모킹.** 임포트한 모듈 자체를 통째로 바꿔치기해야 하는 코드베이스라면 성숙한 지원이 필요하다.

**리치 매처와 생태계.** `expect(x).toMatchObject(...)`, `toHaveBeenCalledWith(...)` 같은 매처, 커스텀 매처 확장, 대규모 스냅숏 워크플로, 테스팅 라이브러리 계열 통합은 Jest/Vitest 쪽이 압도적으로 두껍다.

Jest와 Vitest 사이의 선택은 대체로 단순하다. 새 프로젝트에서 번들러가 Vite라면 Vitest가 자연스럽고, 기존 Jest 스위트가 크다면 굳이 옮길 이유가 약하다. Jest는 ESM 지원이 오랫동안 실험적 상태였고 CommonJS 전제 위에 설계되었으므로, 순수 ESM 프로젝트를 새로 시작하며 Jest를 고르는 것은 권하기 어렵다.

### ESM에서 모듈 모킹이 어려운 이유

CommonJS에서는 모킹이 쉬웠다. `require`가 런타임 함수 호출이고 결과가 `require.cache`에 담기므로, 캐시 항목을 바꿔치기하면 이후의 모든 `require`가 가짜를 받는다. 프록시 방식 모킹 도구들은 전부 이 성질에 기대고 있었다.

ESM은 다르다(2장 참조). `import` 선언은 실행문이 아니라 정적 구문이며, 모듈 그래프는 코드가 한 줄도 실행되기 전에 **파싱 시점에 결정**된다. 임포트된 바인딩은 복사본이 아니라 원본을 가리키는 **라이브 바인딩(live binding)**이고 읽기 전용이다. 즉 소비자 모듈이 이미 링크된 뒤에는 바깥에서 `mod.fetchUser = fake`처럼 덮어쓸 수 없다. 네임스페이스 객체가 봉인되어 있기 때문이다.

그래서 ESM에서 모듈을 모킹하려면 그래프가 만들어지기 **전에** 개입해야 한다. 방법은 둘뿐이다. 하나는 로더/변환 계층에서 소스를 바꿔치기하는 것(Vitest가 Vite의 모듈 그래프에서 하는 일), 다른 하나는 Node.js의 모듈 커스터마이제이션 훅으로 특정 지정자의 해석 결과를 갈아치우는 것이다. `node:test`의 `mock.module()`이 후자에 해당한다.

```js
import { test, mock } from 'node:test'
import assert from 'node:assert/strict'

test('결제 게이트웨이를 모듈 단위로 대체한다', async (t) => {
  mock.module('../src/gateway.js', {
    namedExports: {
      charge: async () => ({ status: 'approved', id: 'ch_test' })
    }
  })
  t.after(() => mock.reset())

  // 모킹 등록 이후에 동적 임포트해야 훅이 적용된다
  const { placeOrder } = await import('../src/order.js')
  const result = await placeOrder({ amountCents: 1000 })
  assert.equal(result.status, 'paid')
})
```

두 가지가 중요하다. 첫째, 파일 상단의 정적 `import`로 대상 모듈을 이미 불러왔다면 모킹은 적용되지 않는다. 반드시 `mock.module()` 호출 뒤에 동적 `import()`로 가져와야 한다. 둘째, 이 기능은 실험적이며 `--experimental-test-module-mocks` 플래그가 필요하다(Node.js 22 기준). 안정성이 필요한 코드베이스라면 의존성 주입으로 문제 자체를 없애는 편이 낫다. 실제로 모듈 모킹을 자주 필요로 한다는 것은 대개 결합도가 높다는 신호다.

## 30.4 비동기 코드 테스트하기

### 항상 통과하는 테스트

비동기 테스트에서 가장 위험한 실패 모드는 실패가 아니라 **거짓 통과**다.

```js
// 잘못된 코드: 이 테스트는 절대 실패하지 않는다
it('없는 사용자는 에러를 던진다', () => {
  assert.rejects(loadUser('nope'))   // await 없음
})
```

`assert.rejects`는 프로미스를 반환한다. `await`하지 않으면 테스트 함수는 즉시 반환하고 러너는 성공으로 기록한다. 어서션이 나중에 실패하더라도 이미 끝난 테스트에 붙을 곳이 없다. 운이 나쁘면 처리되지 않은 거부(unhandled rejection)로 전혀 다른 테스트가 죽는다.

```js
// 올바른 코드
it('없는 사용자는 에러를 던진다', async () => {
  await assert.rejects(
    () => loadUser('nope'),
    { name: 'NotFoundError' }
  )
})
```

규칙은 하나다. **프로미스를 반환하는 모든 호출 앞에 `await`를 붙인다.** 이 실수는 사람 눈으로 잡기 어려우므로 린터로 강제한다. `no-floating-promises`(타입스크립트 ESLint) 또는 `require-await` 계열 규칙을 CI에서 에러로 설정해두면 클래스 전체가 사라진다.

콜백 안에서 어서션을 하는 경우는 `t.plan()`으로 방어한다.

```js
it('스트림이 두 청크를 낸다', async (t) => {
  t.plan(2)
  const stream = readChunks()
  for await (const chunk of stream) {
    t.assert.ok(chunk.length > 0)
  }
})
```

청크가 하나만 오면 어서션 횟수가 모자라 테스트가 실패한다. 이벤트 기반 코드에서 특히 유용하다.

### 끝나지 않는 테스트

반대 방향의 실패는 테스트가 완료되지 않는 것이다. 원인은 대개 셋 중 하나다. 결코 이행되지 않는 프로미스를 기다리거나, 이벤트가 오지 않는데 리스너에서 `resolve`를 기다리거나, 열린 핸들(서버 소켓, DB 풀, `setInterval`)이 남아 프로세스가 종료되지 않는 것이다.

앞의 둘은 타임아웃으로 잡는다.

```js
it('5초 안에 응답한다', { timeout: 5000 }, async () => {
  await callSlowService()
})
```

세 번째는 타임아웃으로 잡히지 않고 러너가 매달린 채 끝나지 않는다. 반드시 `t.after()`나 `after()`에서 자원을 닫아야 한다. 어떤 핸들이 남았는지 모를 때는 진단이 필요하다.

```bash
# 종료되지 않는 원인 핸들을 출력한다
node --test --test-force-exit    # 임시 회피
node --trace-exit --test         # 종료 경로 추적
```

`--test-force-exit`는 증상을 가릴 뿐 원인을 고치지 않는다. 열린 핸들이 남았다는 것은 프로덕션에서도 우아한 종료(graceful shutdown)가 안 된다는 뜻인 경우가 많다.

### 타이머 의존 테스트와 가짜 타이머

재시도 백오프, 디바운스, 캐시 TTL처럼 시간이 개입하는 로직을 실제 시간으로 테스트하면 스위트가 느려지고 CI 부하에 따라 플레이키해진다. `mock.timers`가 시간을 통제한다.

```js
import { test, mock } from 'node:test'
import assert from 'node:assert/strict'
import { retryWithBackoff } from '../src/retry.js'

test('지수 백오프로 세 번 재시도한다', async (t) => {
  t.mock.timers.enable({ apis: ['setTimeout', 'Date'] })

  let attempts = 0
  const op = async () => {
    attempts++
    if (attempts < 3) throw new Error('ECONNRESET')
    return 'ok'
  }

  const promise = retryWithBackoff(op, { retries: 5, baseMs: 100 })

  // 100ms → 200ms 대기를 즉시 통과시킨다
  await t.mock.timers.tickAsync(100)
  await t.mock.timers.tickAsync(200)

  assert.equal(await promise, 'ok')
  assert.equal(attempts, 3)
})
```

`tickAsync`를 쓰는 이유는 각 틱 사이에 마이크로태스크 큐가 비워져야 하기 때문이다. 동기 `tick`만 쓰면 타이머 콜백이 만든 프로미스 체인이 진행되지 않아 테스트가 멈춘다. 이것이 가짜 타이머에서 가장 자주 만나는 함정이다.

`Date`를 함께 모킹하면 만료 로직도 검증할 수 있다. 다만 `t.mock.timers.enable()`은 테스트 컨텍스트 종료 시 자동 복원되는 반면, 최상위 `mock.timers`를 쓰면 명시적으로 `reset()`해야 한다. 복원을 잊으면 이후 테스트에서 실제 타이머가 동작하지 않아 원인을 찾기 어려운 행(hang)이 발생한다.

가짜 타이머로 대체할 수 없는 것도 있다. 실제 네트워크 지연, OS 스케줄링, 이벤트 루프 포화 같은 것은 시간을 조작해도 재현되지 않는다. 그런 성질은 복원력 테스트의 영역이다(29장 참조).

### 플레이키 테스트와 재시도의 유혹

간헐적으로 실패하는 테스트를 자동 재시도로 덮는 것은 거의 항상 나쁜 거래다. 플레이키의 원인은 대개 셋이다.

첫째, **경쟁 조건**. 테스트가 비동기 작업의 완료를 기다리지 않고 상태를 확인한다. 흔한 임시방편이 `await sleep(50)`인데, 느린 CI에서는 부족하고 빠른 로컬에서는 낭비다. 올바른 해법은 완료 신호를 기다리는 것이다. `events.once(emitter, 'done')`으로 이벤트를 기다리거나, 조건이 참이 될 때까지 마감 시한을 두고 폴링한다.

```js
import { setTimeout as delay } from 'node:timers/promises'

async function waitFor(fn, { timeoutMs = 2000, intervalMs = 20 } = {}) {
  const deadline = Date.now() + timeoutMs
  let lastError
  while (Date.now() < deadline) {
    try {
      const value = await fn()
      if (value) return value
    } catch (err) { lastError = err }
    await delay(intervalMs)
  }
  throw new Error(`waitFor 시간 초과${lastError ? `: ${lastError.message}` : ''}`)
}
```

둘째, **공유 상태**. 병렬 실행되는 테스트가 같은 테이블, 같은 포트, 같은 임시 디렉터리를 쓴다. 해법은 격리다(30.6 참조).

셋째, **시간과 순서 가정**. 정렬 없는 쿼리 결과의 순서, 현재 시각, 난수, 타임존에 의존한다. 시간과 난수는 주입 가능한 의존성으로 다루면 테스트에서 고정할 수 있다.

플레이키 테스트를 발견하면 재시도를 붙이는 대신 즉시 격리(`skip`)하고 이슈를 만드는 편이 낫다. 재시도로 감춘 플레이키는 나중에 프로덕션의 실제 경쟁 조건으로 돌아오는 경우가 많다. 특히 애플리케이션 코드 자체의 경쟁 조건이 원인이라면, 테스트가 그 버그를 정확히 잡아낸 것인데 재시도가 그 신호를 지운 셈이 된다.

## 30.5 테스트 더블: 스텁, 목, 페이크

### 다섯 가지를 구분한다

"목(mock)"은 일상적으로 모든 가짜를 뭉뚱그리는 말로 쓰이지만, 정확히 구분하면 무엇을 검증하는 테스트인지가 드러난다.

**더미(dummy)**는 자리를 채우기만 하고 절대 쓰이지 않는 값이다. 필수 인자를 넘겨야 할 때 쓰는 `null`이나 빈 객체가 여기 해당한다.

**스텁(stub)**은 미리 정해둔 값을 돌려주는 가짜다. 상태를 갖지 않고, 호출 기록도 검증하지 않는다. "환율 API가 1,300을 준다면 결과는 얼마인가"처럼 **입력 조건을 만드는 데** 쓴다.

**스파이(spy)**는 실제 동작을 그대로 두거나 스텁처럼 대체하면서, 호출 횟수와 인자를 기록한다. 사후에 기록을 검사한다.

**목(mock)**은 스파이와 비슷하지만 **기대를 미리 선언**하고 그 기대의 충족 여부 자체가 테스트의 판정 기준이 된다. "결제 실패 시 알림 서비스가 정확히 한 번, 이 인자로 호출되어야 한다"처럼 **부수 효과를 검증**할 때 쓴다.

**페이크(fake)**는 실제로 동작하는 간소화 구현이다. 인메모리 리포지토리, 메모리 큐, 임시 파일시스템이 대표적이다. 진짜 로직을 갖고 있으므로 상태 변화가 자연스럽게 반영된다.

핵심 구분은 **상태 검증이냐 상호작용 검증이냐**다. 스텁과 페이크는 상태 검증을 돕고, 목은 상호작용을 검증한다. 상호작용 검증은 구현 세부에 밀착하므로 리팩터링에 약하다. 가능하면 상태 검증을 택하고, 관찰 가능한 결과가 오직 외부 호출뿐일 때(이메일 발송, 메시지 발행 등)만 목을 쓴다.

### `node:test`의 mock API로 각각 만들기

```js
import { test, mock } from 'node:test'
import assert from 'node:assert/strict'
import { PaymentService } from '../src/payment-service.js'

test('스텁: 정해진 값을 돌려준다', async (t) => {
  const rates = { get: async () => 1300 }              // 손으로 만든 스텁
  const svc = new PaymentService({ rates, gateway: { charge: async () => ({ ok: true }) } })
  assert.equal(await svc.toKrw(10), 13000)
})

test('스파이: 실제 구현을 감시한다', (t) => {
  const logger = { warn(msg) { /* 실제 구현 */ } }
  t.mock.method(logger, 'warn')                        // 원본 유지 + 기록
  logger.warn('low balance')
  assert.equal(logger.warn.mock.callCount(), 1)
  assert.deepStrictEqual(logger.warn.mock.calls[0].arguments, ['low balance'])
})

test('목: 부수 효과를 기대로 검증한다', async (t) => {
  const notifier = { send: t.mock.fn(async () => {}) }
  const gateway = { charge: t.mock.fn(async () => { throw new Error('declined') }) }
  const svc = new PaymentService({ rates: { get: async () => 1 }, gateway, notifier })

  await assert.rejects(() => svc.pay({ userId: 'u1', amountCents: 500 }))

  assert.equal(notifier.send.mock.callCount(), 1)
  const [arg] = notifier.send.mock.calls[0].arguments
  assert.equal(arg.userId, 'u1')
  assert.match(arg.reason, /declined/)
})
```

`mock.fn`의 첫 인자는 기본 구현, 두 번째는 대체 구현, 세 번째는 옵션이다. 호출별로 다른 결과를 주려면 `mockImplementationOnce`를 쓴다.

```js
const fetchUser = mock.fn(async () => ({ id: 1 }))
fetchUser.mock.mockImplementationOnce(async () => { throw new Error('ETIMEDOUT') })
// 첫 호출은 실패, 이후 호출은 성공 → 재시도 로직 검증에 유용하다
```

테스트 컨텍스트의 `t.mock`은 테스트가 끝날 때 자동으로 원복된다. 전역 `mock`을 쓰면 `mock.restoreAll()` 또는 `mock.reset()`을 직접 호출해야 하며, 잊으면 다음 테스트가 오염된다. 특별한 이유가 없으면 항상 `t.mock`을 쓴다.

### 페이크가 더 나은 경우

리포지토리처럼 상태를 다루는 협력자는 스텁보다 페이크가 낫다. 스텁으로 만들면 "저장했다"는 사실이 "읽을 수 있다"로 이어지지 않아, 테스트가 시나리오를 표현하지 못한다.

```js
// test/helpers/in-memory-user-repo.js
export class InMemoryUserRepository {
  #rows = new Map()
  #seq = 0

  async insert(user) {
    if ([...this.#rows.values()].some((r) => r.email === user.email)) {
      throw Object.assign(new Error('duplicate email'), { code: 'UNIQUE_VIOLATION' })
    }
    const row = { ...user, id: ++this.#seq }
    this.#rows.set(row.id, row)
    return structuredClone(row)   // 내부 상태가 밖에서 변형되지 않게 한다
  }

  async findByEmail(email) {
    const found = [...this.#rows.values()].find((r) => r.email === email)
    return found ? structuredClone(found) : null
  }
}
```

이 페이크는 유니크 제약 위반을 실제 구현과 같은 `code`로 던진다. 이것이 페이크의 위험과 가치를 동시에 보여준다. 페이크가 실제 구현과 다르게 행동하면 테스트는 통과하는데 프로덕션이 깨진다. 그래서 페이크는 **실제 구현과 같은 계약 테스트 스위트를 통과시키는 것**이 원칙이다. 같은 테스트 파일을 두 구현에 대해 돌린다.

```js
for (const makeRepo of [makeInMemoryRepo, makePostgresRepo]) {
  describe(`UserRepository 계약: ${makeRepo.name}`, () => {
    // 동일한 테스트 본문
  })
}
```

### 의존성 주입과 과도한 모킹

앞의 모든 예제가 협력자를 생성자 인자로 받는다는 점에 주목한다. 이것이 모킹을 쉽게 만드는 유일한 구조적 조건이다(12장 참조). 모듈 상단에서 클라이언트를 직접 생성하는 코드는 모듈 모킹 같은 무거운 도구를 강요하고, 그 도구가 실험적이거나 러너 종속적이라는 대가를 치르게 한다.

반대 방향의 실패도 흔하다. **모든 것을 모킹하면 아무것도 검증하지 않게 된다.** 협력자를 전부 목으로 바꾸고 "A를 호출하면 B를 호출한다"만 확인하는 테스트는, 코드를 자연어로 한 번 더 옮겨 쓴 것에 지나지 않는다. 구현을 바꾸면 반드시 깨지고, 버그는 거의 잡지 못한다.

경계는 이렇게 잡는다. **프로세스 밖으로 나가는 것과 통제 불가능한 것만 대체한다.** 네트워크, 결제 게이트웨이, 이메일 발송, 현재 시각, 난수가 여기 해당한다. 같은 프로세스 안의 순수한 협력자(값 객체, 계산 모듈, 포매터)는 진짜를 쓴다. 데이터베이스는 판단이 갈리는데, 실제 DB를 쓸 수 있다면 쓰는 편이 SQL과 스키마까지 검증하므로 낫다(30.7 참조).

## 30.6 HTTP 서비스 통합 테스트

### 포트 0으로 실제 서버 띄우기

HTTP 계층을 검증하면서 실제 소켓을 쓰지 않는 방법도 있지만, 실제로 서버를 띄우는 편이 라우팅·헤더 파싱·압축·타임아웃까지 포함해 검증할 수 있고 프레임워크에 덜 묶인다. 병렬 실행에서 포트가 충돌하지 않게 하는 열쇠는 **포트 0**이다. OS가 사용 가능한 포트를 골라준다.

```js
// test/helpers/app.js
import { createApp } from '../../src/app.js'

export async function startTestApp(deps) {
  const app = createApp(deps)
  const server = app.listen(0)                    // OS가 포트를 할당한다
  await new Promise((resolve, reject) => {
    server.once('listening', resolve)
    server.once('error', reject)
  })
  const { port } = server.address()
  return {
    baseUrl: `http://127.0.0.1:${port}`,
    async close() {
      await new Promise((resolve) => server.close(resolve))
    }
  }
}
```

```js
// test/orders.test.js
import { describe, it, before, after, beforeEach } from 'node:test'
import assert from 'node:assert/strict'
import { startTestApp } from './helpers/app.js'
import { createPool, migrate, truncateAll } from './helpers/db.js'

describe('POST /orders', () => {
  let app, pool

  before(async () => {
    pool = createPool(process.env.TEST_DATABASE_URL)
    await migrate(pool)
    app = await startTestApp({ pool })
  })

  after(async () => {
    await app.close()
    await pool.end()
  })

  beforeEach(() => truncateAll(pool))

  it('주문을 생성하고 201과 Location을 반환한다', async () => {
    const res = await fetch(`${app.baseUrl}/orders`, {
      method: 'POST',
      headers: { 'content-type': 'application/json' },
      body: JSON.stringify({ sku: 'A-1', qty: 2 })
    })

    assert.equal(res.status, 201)
    const body = await res.json()
    assert.match(res.headers.get('location'), new RegExp(`/orders/${body.id}$`))

    const { rows } = await pool.query('SELECT sku, qty FROM orders WHERE id = $1', [body.id])
    assert.deepStrictEqual(rows, [{ sku: 'A-1', qty: 2 }])
  })

  it('잘못된 본문에 400과 문제 상세를 반환한다', async () => {
    const res = await fetch(`${app.baseUrl}/orders`, {
      method: 'POST',
      headers: { 'content-type': 'application/json' },
      body: JSON.stringify({ qty: -1 })
    })
    assert.equal(res.status, 400)
    assert.equal(res.headers.get('content-type'), 'application/problem+json')
  })
})
```

전역 `fetch`를 쓰면 별도 HTTP 클라이언트 의존성이 없다. 응답 본문을 소비하지 않으면 커넥션이 열린 채 남아 프로세스가 종료되지 않을 수 있으므로, 상태 코드만 볼 때도 `await res.body?.cancel()` 또는 `await res.text()`로 소비한다.

주목할 점은 마지막 어서션이다. HTTP 응답만 확인하지 않고 **데이터베이스 상태까지 확인**했다. 통합 테스트의 가치는 이 지점, 즉 계층 사이의 계약이 실제로 맞는지 보는 데 있다.

### 데이터베이스 상태 초기화: 롤백과 트렁케이트

테스트 간 격리 방식은 두 갈래다.

**트랜잭션 롤백**은 테스트 시작 시 `BEGIN`, 종료 시 `ROLLBACK`을 실행한다. 빠르고 완전히 되돌려진다. 단점이 결정적이다. 애플리케이션 코드가 그 트랜잭션과 같은 커넥션을 써야 하는데, HTTP 요청은 별도 커넥션을 풀에서 가져간다. 이를 맞추려면 테스트 전용으로 풀을 단일 커넥션으로 고정하고 애플리케이션이 그 커넥션을 쓰도록 주입해야 한다. 게다가 애플리케이션이 자체 트랜잭션을 쓰면 중첩이 생겨 세이브포인트로 흉내 내야 하고, 커밋 후 동작(트리거 이후 조회, `LISTEN/NOTIFY`)은 검증할 수 없다.

**트렁케이트**는 각 테스트 전에 테이블을 비운다. 느리지만 단순하고, 애플리케이션이 커넥션과 트랜잭션을 자유롭게 쓸 수 있다. 속도는 한 번의 문장으로 모든 테이블을 처리해 확보한다.

```js
export async function truncateAll(pool) {
  const { rows } = await pool.query(`
    SELECT tablename FROM pg_tables
    WHERE schemaname = current_schema() AND tablename <> 'schema_migrations'
  `)
  if (rows.length === 0) return
  const list = rows.map((r) => `"${r.tablename}"`).join(', ')
  // 한 문장으로 처리해 왕복과 잠금 획득을 최소화한다
  await pool.query(`TRUNCATE ${list} RESTART IDENTITY CASCADE`)
}
```

판단 기준은 단순하다. 저장소 계층의 단위성 높은 테스트가 많고 애플리케이션이 트랜잭션을 단순하게 쓴다면 롤백이 빠르다. HTTP 레벨의 통합 테스트라면 트렁케이트가 안전하다.

### 병렬 실행에서의 충돌 방지

`node --test`는 파일마다 프로세스를 띄우므로, 여러 파일이 같은 데이터베이스를 트렁케이트하면 서로의 데이터를 지운다. 포트는 포트 0으로 해결되지만 데이터베이스는 그렇지 않다.

가장 실용적인 해법은 **워커별 논리 격리**다. PostgreSQL이라면 스키마를, MySQL이라면 데이터베이스를 워커마다 하나씩 준다.

```js
// test/helpers/db.js
import { Pool } from 'pg'

// 파일마다 별도 프로세스이므로 PID로 고유 스키마 이름을 만든다
const schema = `test_${process.pid}`

export function createPool(url) {
  const pool = new Pool({ connectionString: url })
  pool.on('connect', (client) => {
    // 이 풀의 모든 커넥션이 전용 스키마만 보게 한다
    client.query(`SET search_path TO ${schema}, public`)
  })
  return pool
}

export async function migrate(pool) {
  await pool.query(`CREATE SCHEMA IF NOT EXISTS ${schema}`)
  await applyMigrations(pool)
}

export async function dropSchema(pool) {
  await pool.query(`DROP SCHEMA IF EXISTS ${schema} CASCADE`)
}
```

스키마마다 마이그레이션을 다시 도는 비용이 부담이면, 미리 마이그레이션이 적용된 템플릿 데이터베이스를 만들어 두고 `CREATE DATABASE test_x TEMPLATE test_template`로 복제하는 방법이 훨씬 빠르다. 파일 복사 수준이라 수십 밀리초에 끝난다.

한 파일 안에서 `concurrency`를 켜는 경우에는 논리 격리로 부족하다. 같은 프로세스 안에서 같은 스키마를 공유하기 때문이다. 이때는 테스트마다 데이터를 다른 키 공간에 쓰도록 설계한다. 사용자 이메일이나 주문 번호에 테스트별 고유 접두사를 붙이고, 트렁케이트 대신 그 접두사에 해당하는 행만 검증하는 식이다. 다만 복잡도가 빠르게 올라가므로, 파일 단위 병렬로 충분한 경우가 대부분이다. 파일을 잘게 나누는 것이 파일 안에서 병렬화하는 것보다 거의 항상 낫다.

## 30.7 컨테이너 기반 통합 테스트 환경

### 문제: 실제 의존성을 어디서 얻는가

30.6의 테스트는 `TEST_DATABASE_URL`이 가리키는 PostgreSQL이 이미 떠 있다고 가정했다. 그 전제를 누가 만족시키느냐가 이 절의 주제다. 개발자 노트북에 로컬 설치를 요구하는 방식은 버전 드리프트를 낳는다. 누군가는 PostgreSQL 14, CI는 16을 쓰면서 "내 머신에서는 되는데"가 시작된다.

컨테이너로 의존성을 고정하는 방법은 두 갈래다.

### docker-compose 방식

`compose.yaml`에 PostgreSQL과 Redis를 정의하고, 테스트 전에 `docker compose up -d`, 후에 `down`을 실행한다.

```yaml
# compose.test.yaml
services:
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: test
      POSTGRES_DB: app_test
    # 포트를 호스트에 고정하지 않고 매핑만 열어 충돌을 피한다
    ports: ["5432"]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 1s
      timeout: 3s
      retries: 30
  redis:
    image: redis:7-alpine
    ports: ["6379"]
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 1s
      retries: 30
```

```bash
docker compose -f compose.test.yaml up -d --wait
export TEST_DATABASE_URL="postgres://postgres:test@127.0.0.1:$(docker compose -f compose.test.yaml port postgres 5432 | cut -d: -f2)/app_test"
node --test
docker compose -f compose.test.yaml down -v
```

장점은 단순함과 재사용성이다. 컨테이너가 한 번 뜨고 전체 스위트가 공유하므로 총 실행 시간이 짧다. 개발 중에는 컨테이너를 계속 띄워두고 테스트만 반복 실행할 수 있다. 단점은 **테스트 코드와 환경 정의가 분리**된다는 점이다. 새 의존성이 필요해지면 YAML과 CI 스크립트를 같이 고쳐야 하고, 누군가 컨테이너를 띄우지 않고 테스트를 돌리면 알 수 없는 연결 에러를 본다.

### testcontainers 방식

Testcontainers는 컨테이너 수명을 테스트 코드 안에서 관리한다. 환경 정의가 테스트와 같은 파일에 있으므로 어긋날 수 없다.

```js
// test/helpers/containers.js
import { PostgreSqlContainer } from '@testcontainers/postgresql'
import { GenericContainer, Wait } from 'testcontainers'

export async function startPostgres() {
  const container = await new PostgreSqlContainer('postgres:16-alpine')
    .withDatabase('app_test')
    // 테스트용이므로 내구성을 버리고 속도를 얻는다
    .withCommand(['postgres', '-c', 'fsync=off', '-c', 'full_page_writes=off',
                  '-c', 'synchronous_commit=off'])
    .withReuse()          // 같은 설정의 컨테이너가 있으면 재사용한다
    .start()
  return { url: container.getConnectionUri(), stop: () => container.stop() }
}

export async function startRedis() {
  const container = await new GenericContainer('redis:7-alpine')
    .withExposedPorts(6379)
    .withWaitStrategy(Wait.forLogMessage('Ready to accept connections'))
    .withReuse()
    .start()
  return {
    url: `redis://${container.getHost()}:${container.getMappedPort(6379)}`,
    stop: () => container.stop()
  }
}
```

호스트 포트는 항상 무작위로 매핑되므로 병렬 실행에서 충돌하지 않는다. `Wait` 전략이 중요하다. 컨테이너가 시작됐다는 것과 서비스가 연결을 받을 준비가 됐다는 것은 다르며, 이를 구분하지 않으면 CI에서 간헐적으로 연결 거부가 난다.

### CI에서의 실행 시간 문제와 절충안

testcontainers의 대가는 시간이다. `node --test`가 파일마다 프로세스를 띄우는데, 각 파일이 `before`에서 컨테이너를 만들면 파일 수만큼 PostgreSQL이 뜬다. 파일 30개면 컨테이너 30개이고, 이미지 풀과 초기화에 각각 2~5초가 붙어 스위트가 분 단위로 늘어난다. 메모리도 함께 터진다.

현실적인 절충안은 다음과 같다.

**컨테이너는 스위트당 하나, 격리는 논리적으로.** 컨테이너를 전역 셋업에서 한 번만 띄우고 URL을 환경 변수로 넘긴 뒤, 파일별 격리는 30.6의 스키마 분리로 처리한다. `--test-global-setup`(Node.js 22.13 이상) 또는 컨테이너를 띄우고 `node --test`를 자식 프로세스로 실행하는 짧은 스크립트로 구현한다.

```js
// test/global-setup.js  (node --test --test-global-setup=./test/global-setup.js)
import { startPostgres, startRedis } from './helpers/containers.js'

let pg, redis

export async function globalSetup() {
  ;[pg, redis] = await Promise.all([startPostgres(), startRedis()])
  process.env.TEST_DATABASE_URL = pg.url
  process.env.TEST_REDIS_URL = redis.url
}

export async function globalTeardown() {
  await Promise.all([pg?.stop(), redis?.stop()])
}
```

**로컬은 재사용, CI는 일회성.** `withReuse()`는 로컬 반복 실행에서 컨테이너 기동 시간을 0으로 만든다. CI에서는 잔여 상태가 결과를 오염시킬 수 있으므로 재사용을 끄고 매번 새로 띄운다. 환경 변수 하나로 분기하면 된다.

**CI 러너의 서비스 컨테이너를 쓴다.** GitHub Actions의 `services:`처럼 CI 플랫폼이 제공하는 사이드카는 잡 시작과 함께 병렬로 준비되므로 테스트 시간에 계산되지 않는다. 로컬에서는 testcontainers, CI에서는 서비스 컨테이너를 쓰고 둘 다 같은 환경 변수로 접근하는 구성이 흔하다. 이미지 태그를 한 곳에서 관리해 두 경로가 어긋나지 않게 한다.

**계층을 나눈다.** 컨테이너가 필요한 테스트와 필요 없는 테스트를 디렉터리로 분리해, `node --test test/unit`은 몇 초 만에 끝나고 `test/integration`은 필요할 때만 돌린다. 커밋 훅에서는 앞의 것만, CI에서는 둘 다 실행한다.

이미지 태그는 반드시 고정한다. `postgres:latest`는 어느 날 조용히 메이저 버전을 올려 스위트를 통째로 깨뜨린다. 프로덕션이 쓰는 버전과 같은 태그를 쓰는 것이 이 방식의 존재 이유다(32장 참조).

## 30.8 코드 커버리지 측정과 강제

### 내장 커버리지

Node.js는 V8의 커버리지 정보를 그대로 사용하므로 별도 계측 도구가 필요 없다.

```bash
# Node.js 22 기준
node --test --experimental-test-coverage

# 리포트를 파일로 (lcov는 CI 시각화 도구가 읽는 표준 포맷)
node --test --experimental-test-coverage \
  --test-reporter=spec --test-reporter-destination=stdout \
  --test-reporter=lcov --test-reporter-destination=lcov.info
```

출력은 파일별 라인·브랜치·함수 커버리지와 커버되지 않은 라인 번호를 보여준다. 제외 패턴도 지원한다.

```bash
node --test --experimental-test-coverage \
  --test-coverage-exclude='test/**' \
  --test-coverage-exclude='**/*.config.js' \
  --test-coverage-include='src/**'
```

`c8`은 같은 V8 커버리지를 수집하는 외부 도구다. 내장 기능이 나오기 전부터 표준이었고, 여러 리포터와 세밀한 설정, 자식 프로세스 커버리지 병합에서 아직 앞선다. 이미 `c8`을 쓰고 있고 잘 동작한다면 바꿀 이유가 크지 않다. 새로 시작한다면 내장 커버리지로 충분하다. 반면 소스맵이 필요한 트랜스파일 환경(타입스크립트를 별도 빌드하는 경우)에서는 도구별 소스맵 지원 성숙도를 확인해야 한다. 커버리지가 빌드 산출물 기준으로 잡히면 숫자가 원본 코드와 어긋난다.

### CI에서 임계값 강제하기

Node.js 22부터 임계값 플래그가 있고, 미달 시 종료 코드가 0이 아니게 되어 CI가 실패한다.

```bash
node --test --experimental-test-coverage \
  --test-coverage-lines=80 \
  --test-coverage-branches=70 \
  --test-coverage-functions=80
```

임계값 설정에서 자주 저지르는 실수는 처음부터 높은 숫자를 박아 넣는 것이다. 기존 코드베이스에 90%를 걸면 아무도 통과시킬 수 없고, 결국 임계값을 낮추거나 CI 단계를 꺼버린다. **래칫(ratchet) 방식**이 현실적이다. 현재 수치를 바닥으로 삼아 임계값으로 박고, 올라갔을 때만 갱신한다. 내려가는 변경은 CI가 막는다.

더 유용한 것은 **변경분 커버리지(diff coverage)**다. 전체 커버리지 대신 이번 PR이 추가·수정한 라인의 커버리지만 본다. 새 코드에는 높은 기준을 요구하면서 레거시를 인질로 잡지 않는다. lcov 리포트와 diff를 조합하는 도구로 구현한다.

### 커버리지 수치의 함정

커버리지는 **실행되지 않은 코드**를 알려준다. 그 이상은 알려주지 않는다.

**100%는 정확성을 뜻하지 않는다.** 다음 테스트는 라인 커버리지 100%를 만들지만 아무것도 검증하지 않는다.

```js
it('동작한다', async () => {
  await processOrder({ sku: 'A', qty: 1 })   // 어서션이 없다
})
```

예외만 안 나면 통과한다. 커버리지 리포트에는 초록색으로 표시된다.

**라인 커버리지는 브랜치를 감춘다.** `const label = user.isAdmin ? 'admin' : 'user'`는 한 줄이고, 어느 쪽 분기만 타도 그 줄은 커버된 것으로 집계될 수 있다. 브랜치 커버리지를 함께 봐야 하는 이유다. 옵셔널 체이닝(`a?.b`)과 기본 매개변수도 눈에 보이지 않는 분기를 만든다.

**커버되지 않은 코드에는 확실한 정보가 있다.** 리포트에서 실제로 가치 있는 부분은 초록색이 아니라 **빨간색**이다. 특히 에러 처리 경로가 통째로 비어 있는 경우가 많고, 이는 프로덕션에서 가장 먼저 문제를 일으키는 코드다.

**목표를 숫자로 바꾸면 숫자를 최적화하게 된다.** 커버리지 강제가 게터·DTO·설정 파일에 의미 없는 테스트를 양산하는 방향으로 작동하기 시작하면, 임계값이 목적을 벗어난 것이다.

테스트의 질을 실제로 측정하려면 **뮤테이션 테스팅(mutation testing)**이 정직한 도구다. Stryker 같은 도구가 소스에 의도적 변형(비교 연산자 뒤집기, 반환값 제거)을 가하고 테스트가 그것을 잡아내는지 본다. 잡아내지 못한 변형은 어서션이 부족하다는 명확한 증거다. 실행이 느려 전체 스위트에 상시 적용하기는 어렵지만, 결제·권한·요금 계산처럼 결함 비용이 큰 모듈에 국한해 주기적으로 돌리면 커버리지 숫자보다 훨씬 많은 것을 알려준다.

## 30.9 디버깅: 인스펙터, 브레이크포인트, 원격 디버깅

### 인스펙터 켜기

Node.js는 V8 인스펙터 프로토콜(Chrome DevTools Protocol)을 내장한다.

```bash
node --inspect server.js         # 인스펙터를 열고 즉시 실행
node --inspect-brk server.js     # 첫 줄에서 멈춘 채 디버거를 기다린다
node --inspect-wait server.js    # 실행은 하되 디버거가 붙을 때까지 대기 (Node.js 22+)
```

기본 바인드 주소는 `127.0.0.1:9229`다. `--inspect-brk`는 부팅 코드나 모듈 최상위에서 발생하는 문제를 볼 때 필수적이다. 서버가 뜨자마자 죽는 문제는 `--inspect`로는 붙기 전에 끝나버린다.

테스트도 같은 방식으로 디버깅한다. 다만 러너가 파일마다 자식 프로세스를 띄우므로 포트가 겹친다. 격리를 끄고 한 프로세스에서 돌리는 편이 편하다.

```bash
node --inspect-brk --test --test-concurrency=1 test/orders.test.js
```

붙는 방법은 셋이다. Chrome에서 `chrome://inspect`를 열면 로컬 대상이 자동으로 목록에 뜬다. VS Code에서는 "Auto Attach"를 켜두면 통합 터미널에서 실행한 `node --inspect`에 자동으로 연결되고, 수동으로는 `attach` 구성을 쓴다.

```json
// .vscode/launch.json
{
  "version": "0.2.0",
  "configurations": [
    {
      "type": "node", "request": "attach", "name": "Attach 9229",
      "port": 9229, "restart": true,
      "skipFiles": ["<node_internals>/**", "**/node_modules/**"]
    },
    {
      "type": "node", "request": "launch", "name": "Debug current test",
      "program": "${file}",
      "runtimeArgs": ["--test", "--test-concurrency=1"],
      "console": "integratedTerminal"
    }
  ]
}
```

`skipFiles`를 설정하지 않으면 스텝 실행이 Node.js 내부 코드와 라이브러리 안으로 계속 들어가 쓸모없어진다.

코드에 `debugger` 문을 직접 넣는 방법도 있다. 인스펙터가 붙어 있지 않으면 무시되므로 안전하지만, 커밋되면 남에게 혼란을 주므로 린트 규칙으로 막는 것이 좋다.

### 원격 디버깅과 보안 경고

컨테이너나 원격 서버 안의 프로세스에 붙으려면 포트가 필요하다. **인스펙터 포트를 외부에 노출하는 것은 원격 코드 실행을 허용하는 것과 같다.** 인스펙터에 붙은 클라이언트는 임의의 자바스크립트를 프로세스 권한으로 실행할 수 있고, 인증이 전혀 없다. `--inspect=0.0.0.0:9229`로 열고 방화벽이 열려 있으면 그 프로세스는 이미 남의 것이다.

올바른 방법은 **루프백에만 바인딩하고 터널로 연결**하는 것이다.

```bash
# 컨테이너 안: 루프백이 아니면 붙을 수 없으므로 컨테이너 내부 주소로만 연다
node --inspect=127.0.0.1:9229 server.js

# 호스트에서 컨테이너로 터널
docker exec -it app kill -USR1 1        # 이미 떠 있는 프로세스에 인스펙터를 켠다
kubectl port-forward pod/app-7d9f 9229:9229
ssh -N -L 9229:127.0.0.1:9229 user@remote-host
```

`SIGUSR1`은 실행 중인 Node.js 프로세스에 인스펙터를 켜는 신호다. 재시작 없이 붙을 수 있다는 뜻이며, 동시에 **프로세스에 신호를 보낼 수 있는 사람은 누구나 인스펙터를 켤 수 있다**는 뜻이기도 하다. 프로덕션 컨테이너의 실행 권한 관리가 그만큼 중요하다.

프로덕션 디버깅 자체를 최소화하는 것이 원칙이다. 브레이크포인트는 이벤트 루프를 멈추므로 요청을 처리 중인 인스턴스에서는 타임아웃과 헬스체크 실패를 연쇄시킨다. 붙어야 한다면 로드밸런서에서 먼저 뺀 인스턴스에 붙는다. 대부분의 프로덕션 문제는 디버거가 아니라 로그·메트릭·추적으로 좁히는 것이 옳다(31장 참조).

### `debuglog`와 조건부 로깅

디버거를 붙일 수 없는 상황에서 필요한 것은 평소에는 꺼져 있고 필요할 때만 켜지는 로깅이다. `node:util`의 `debuglog`가 정확히 이 용도다.

```js
// src/cache.js
import { debuglog } from 'node:util'

const debug = debuglog('app:cache')

export async function get(key) {
  const hit = store.get(key)
  // 활성화되지 않으면 이 호출은 사실상 no-op이다
  debug('lookup key=%s hit=%o', key, Boolean(hit))
  return hit
}
```

```bash
NODE_DEBUG=app:cache node server.js
NODE_DEBUG=app:* node server.js          # 와일드카드 지원
NODE_DEBUG=stream,net node server.js     # Node.js 내부 서브시스템도 같은 방식이다
```

`debuglog`의 장점은 비용 구조다. 해당 이름이 활성화되지 않으면 반환된 함수는 아무 일도 하지 않으며, 인자 포매팅도 일어나지 않는다. `debug.enabled`로 감싸면 인자를 만드는 비용까지 없앨 수 있다.

```js
if (debug.enabled) {
  debug('entry=%o', expensiveSerialize(entry))   // 켜져 있을 때만 계산한다
}
```

이 패턴이 중요한 이유는, 구조화 로거를 쓰더라도 인자 계산은 로그 레벨과 무관하게 항상 일어나기 때문이다. `logger.debug('%o', serialize(x))`는 debug 레벨이 꺼져 있어도 `serialize(x)`를 실행한다. 뜨거운 경로에서 이 비용은 실제로 측정에 잡힌다.

`NODE_DEBUG`는 프로세스 시작 시에만 읽히므로 런타임에 켤 수 없다. 재시작 없이 로그 레벨을 바꿔야 한다면 애플리케이션 로거의 레벨을 신호나 관리용 엔드포인트로 조정하는 장치를 따로 둔다(31장 참조). 마지막으로, 디버그 로그에 개인정보나 자격 증명이 들어가지 않도록 직렬화 단계에서 필드를 마스킹한다. 평소에 꺼져 있다는 사실이 위험을 없애주지는 않는다. 켜지는 순간이 대개 장애 상황이고, 그때 남은 로그가 가장 오래 보관된다.

## 요약

- 테스트 피라미드의 각 층은 개수가 아니라 보장하는 명제가 다르다. 단위는 로직을, 통합은 경계의 계약을, 기능은 사용자 여정을 보장하며 어느 하나도 다른 층을 대체하지 못한다.
- 아이스크림 콘은 테스트 전략이 아니라 설계의 실패다. 의존성을 주입받지 않는 코드는 단위로 테스트할 수 없어 모든 검증이 위층으로 밀려 올라간다.
- `node:test`는 의존성 없이 중첩·훅·동시 실행·스냅숏·필터링·리포터를 제공하며, 파일 단위 프로세스 격리가 기본이다. 어서션은 예외 없이 `node:assert/strict`를 쓰고, `deepStrictEqual`의 프로토타입·`undefined` 키·타입 일치 규칙을 알고 있어야 한다.
- Vitest/Jest는 브라우저 환경 모사, 변환 파이프라인, 성숙한 모듈 모킹, 리치 매처가 필요할 때 값을 한다. ESM에서 모듈 모킹이 어려운 것은 그래프가 실행 전에 정적으로 결정되고 바인딩이 읽기 전용이기 때문이며, `mock.module()`은 로더 훅으로 이 문제를 우회한다.
- 비동기 테스트의 최대 위험은 실패가 아니라 `await` 누락으로 인한 거짓 통과다. 타이머 의존 로직은 `mock.timers`와 `tickAsync`로 통제하고, 플레이키는 재시도로 덮지 말고 원인(경쟁 조건·공유 상태·시간 가정)을 제거한다.
- 스텁·스파이·목·페이크는 상태 검증과 상호작용 검증으로 갈린다. 프로세스 밖으로 나가는 것과 통제 불가능한 것만 대체하고, 페이크는 실제 구현과 같은 계약 테스트를 통과시켜 드리프트를 막는다.
- HTTP 통합 테스트는 포트 0으로 실제 서버를 띄우고 응답과 저장소 상태를 함께 검증한다. 병렬 격리는 워커별 스키마와 템플릿 데이터베이스 복제로, 초기화는 롤백 또는 트렁케이트로 처리한다.
- 컨테이너는 스위트당 하나만 띄우고 격리는 논리적으로 하는 것이 CI 시간과 신뢰도의 균형점이다. 이미지 태그는 프로덕션과 동일하게 고정한다.
- 커버리지는 실행되지 않은 코드만 알려준다. 임계값은 래칫이나 변경분 기준으로 걸고, 테스트의 질 자체는 뮤테이션 테스팅으로 확인한다.
- 인스펙터 포트 노출은 인증 없는 원격 코드 실행과 같다. 루프백에 바인딩하고 SSH 터널이나 포트 포워딩으로만 접근하며, 프로덕션 상시 진단은 `debuglog`와 관측성 도구가 담당한다.

## 연습문제

1. 의도적으로 `await`를 빠뜨린 비동기 테스트, 어서션이 하나도 없는 테스트, 그리고 라인 커버리지만 채우고 브랜치를 검증하지 않는 테스트를 각각 하나씩 포함한 스위트를 만들어라. `--experimental-test-coverage`로 세 테스트 모두 초록색이 나오는 것을 확인한 뒤, `t.plan()`·브랜치 임계값·린트 규칙 중 어떤 장치가 각 결함을 잡아내는지 실험으로 확인하고 그 이유를 설명하라.

2. 30.6의 HTTP 통합 테스트를 트랜잭션 롤백 방식과 트렁케이트 방식으로 각각 구현하라. 테스트 100개 기준 전체 실행 시간을 측정하고, 애플리케이션 코드가 자체 트랜잭션을 시작하는 경우와 커밋 후 트리거 결과를 검증해야 하는 경우에 롤백 방식이 어디서 무너지는지 재현해 보여라.

3. testcontainers로 PostgreSQL을 파일마다 띄우는 구성과, 전역 셋업에서 하나만 띄우고 파일별 스키마로 격리하는 구성을 각각 만들어 테스트 파일 20개짜리 스위트의 총 실행 시간과 최대 메모리 사용량을 비교하라. 그다음 템플릿 데이터베이스 복제를 추가해 마이그레이션 비용이 얼마나 줄어드는지 측정하고, 세 구성의 손익 분기점을 파일 수의 함수로 서술하라.
