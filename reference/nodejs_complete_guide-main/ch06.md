# 6장. Promise와 async/await

5장에서 우리는 콜백만으로 순차 실행, 병렬 실행, 동시성 제한을 직접 구현했다. 동작은 했지만 대가가 컸다. 오류는 모든 콜백에서 손으로 전달해야 했고, 제어 흐름은 라이브러리 없이는 읽기 어려웠다. 이 장에서는 그 모든 코드를 프로미스(Promise)와 `async`/`await`로 다시 쓴다. 단순한 문법 교체가 아니다. 프로미스는 "아직 없는 값"을 일급 객체로 만들어 함수의 반환값·조합·오류 전파를 다시 정의한 모델이다. 예제는 5장의 웹 스파이더를 그대로 이어받아, 같은 기능을 훨씬 적은 코드로 재구현하며 진행한다.

## 6.1 Promise의 정체와 Promises/A+

### 왜 필요한가

콜백 규율(callback discipline)의 근본 한계는 비동기 결과가 **값이 아니라는** 데 있다. `readFile(path, cb)`는 아무것도 돌려주지 않는다. 결과는 오직 콜백 인자로만 존재하므로, 결과를 변수에 담을 수도, 배열에 모을 수도, 함수 반환값으로 위로 올릴 수도 없다. 그래서 5장의 모든 조합 로직은 "결과를 어디에 어떻게 모을 것인가"라는 배관 작업이었다. 프로미스는 이 문제를 정면으로 해결한다. 프로미스는 *미래에 확정될 값을 대신하는 객체*이며, 객체이므로 변수에 담기고, 배열에 들어가고, 함수에서 반환되고, `await`될 수 있다.

### 어떻게 동작하는가

프로미스는 세 가지 상태를 가지는 상태 기계(state machine)다.

- **대기(pending)**: 아직 결과가 확정되지 않은 초기 상태
- **이행(fulfilled)**: 값(value)과 함께 성공적으로 확정된 상태
- **거부(rejected)**: 사유(reason)와 함께 실패로 확정된 상태

전이는 `pending → fulfilled` 또는 `pending → rejected` 단 한 번만 일어난다. 이 **불변성(immutability)**이 콜백과의 결정적 차이다. 콜백은 실수로 두 번 호출될 수 있고, 5장에서 우리는 그것을 막기 위해 `called` 플래그를 손으로 관리했다. 프로미스는 두 번째 `resolve` 호출을 언어 차원에서 무시한다.

프로미스의 계약은 Promises/A+ 명세로 정의되며, ECMAScript의 `Promise`는 이를 포함하는 상위 집합이다. 명세의 핵심은 `then(onFulfilled, onRejected)` 하나다. `then`은 **새로운 프로미스를 반환**하며, 그 프로미스는 다음 규칙으로 확정된다.

- 핸들러가 값 `x`를 반환하면 새 프로미스는 `x`로 이행한다.
- 핸들러가 예외를 던지면 새 프로미스는 그 예외로 거부한다.
- 핸들러가 프로미스(정확히는 thenable)를 반환하면 새 프로미스는 **그것에 동화(assimilate)** 되어, 반환된 프로미스가 확정될 때까지 대기한 뒤 같은 결과로 확정된다.
- 핸들러가 생략되면 결과가 그대로 다음 단계로 통과한다. `onRejected`가 없으면 거부가 체인 아래로 전파된다.

세 번째 규칙이 체이닝(chaining)의 전부다. 중첩 없이 비동기 단계를 나열할 수 있는 이유가 여기에 있다.

**thenable**은 `then` 메서드를 가진 임의의 객체를 말한다. 명세가 클래스가 아니라 덕 타이핑(duck typing)으로 정의된 덕분에, 서로 다른 프로미스 구현(Bluebird, jQuery Deferred, 각종 ORM의 쿼리 빌더)이 서로 섞여도 `await`와 `then`이 정상 동작한다.

### Zalgo 문제의 해결

3장에서 다룬 Zalgo — 같은 API가 상황에 따라 동기적으로도, 비동기적으로도 콜백을 호출해 호출 순서를 예측할 수 없게 만드는 문제 — 는 프로미스에서 구조적으로 불가능하다. Promises/A+는 `onFulfilled`/`onRejected`가 **실행 컨텍스트 스택이 비워진 뒤에만** 호출되어야 한다고 못박는다. Node.js에서 이는 마이크로태스크 큐(microtask queue)를 통한 스케줄링으로 구현된다.

```js
// 이미 이행된 프로미스라도 then 콜백은 결코 동기적으로 실행되지 않는다
const p = Promise.resolve('완료')

console.log('A')
p.then(v => console.log('B:', v))
console.log('C')

// 출력 순서는 항상 A, C, B — 프로미스 상태와 무관하게 결정적이다
```

이 보장 덕분에 "캐시 히트일 때만 동기 반환"하는 함수가 만드는 미묘한 버그가 사라진다. 값이 이미 있어도 `Promise.resolve(value)`로 감싸 반환하면 호출자는 항상 같은 순서를 본다.

### 실무 함정

- **`then` 콜백은 마이크로태스크지 `nextTick`이 아니다.** `process.nextTick` 큐가 마이크로태스크 큐보다 먼저 비워진다(3장 참조). 두 API를 섞어 순서를 가정하지 않는다.
- **재귀적으로 마이크로태스크를 생성하면 이벤트 루프가 굶는다.** 마이크로태스크 큐는 완전히 빌 때까지 처리되므로, `then` 안에서 무한히 새 프로미스를 확정하면 타이머와 I/O가 영원히 실행되지 않는다.
- **`Promise.resolve(thenable)`은 값이 아니라 동화를 수행한다.** 신뢰할 수 없는 객체를 그대로 넘기면 남의 `then`이 호출된다.

## 6.2 Promise API와 프로미스화(promisification)

### 왜 필요한가

Node.js 코어의 상당 부분은 이제 프로미스 버전을 직접 제공한다(`node:fs/promises`, `node:timers/promises`, `node:dns/promises`, `node:stream/promises`). 그러나 사내 레거시 모듈, 오래된 npm 패키지, C++ 애드온은 여전히 오류 우선 콜백(error-first callback) 규약만 노출한다. 이 경계를 프로미스로 끌어올리는 작업이 프로미스화다. 경계에서 한 번만 변환해 두면, 그 위의 모든 코드는 `async`/`await`로 통일된다.

### 어떻게 동작하는가

생성자는 실행자(executor) 함수를 받는다. 실행자는 즉시(동기적으로) 호출되며, `resolve`와 `reject`를 인자로 받는다.

```js
const delay = ms => new Promise(resolve => {
  setTimeout(() => resolve(Date.now()), ms)
})
```

실행자 안에서 던진 예외는 자동으로 `reject`로 변환된다. 단, **비동기 콜백 안에서 던진 예외는 잡히지 않는다.** `setTimeout` 콜백 내부의 `throw`는 실행자의 스택을 이미 벗어났으므로 프로세스를 죽인다. 이것이 프로미스 생성자를 쓸 때 가장 흔한 사고다.

정적 메서드로 `Promise.resolve(x)`(값이면 이행된 프로미스, thenable이면 동화), `Promise.reject(e)`가 있고, 인스턴스 메서드로 `then`, `catch`(= `then(undefined, fn)`), `finally`가 있다. `finally`는 **값을 통과시킨다**. 즉 `finally` 핸들러의 반환값은 무시되고 원래 결과가 그대로 흐른다. 다만 `finally` 안에서 예외를 던지면 그 예외가 결과를 덮어쓴다.

### 직접 구현하는 promisify

```js
// 오류 우선 콜백 규약의 함수를 프로미스 반환 함수로 변환한다
function promisify(fn) {
  return function promisified(...args) {
    return new Promise((resolve, reject) => {
      // this 바인딩을 보존해야 메서드도 변환할 수 있다
      fn.call(this, ...args, (err, ...results) => {
        if (err) return reject(err)
        // 콜백이 값을 하나만 넘기면 그 값을, 여럿이면 배열을 이행값으로 삼는다
        resolve(results.length > 1 ? results : results[0])
      })
    })
  }
}

import { readFile } from 'node:fs'
const readFileAsync = promisify(readFile)
const text = await readFileAsync('package.json', 'utf8')
```

핵심은 마지막 세 줄이다. 콜백이 `(err, stdout, stderr)`처럼 여러 값을 넘기는 경우가 실재하므로, 나머지 인자를 모아 처리해야 한다. 위 구현은 "하나면 값, 여럿이면 배열"이라는 편의적 규칙을 쓴다.

### util.promisify와의 차이

`node:util`의 `promisify`는 표준 구현이며 세 가지가 다르다.

1. **다중 콜백 인자를 지원하지 않는다.** 항상 첫 번째 결과값만 이행값이 된다. 나머지는 버려진다.
2. **`util.promisify.custom` 심볼을 존중한다.** 함수에 이 심볼로 커스텀 프로미스 구현이 붙어 있으면 그것을 그대로 반환한다. 예를 들어 `child_process.exec`는 커스텀 구현을 제공해 `{ stdout, stderr }` 객체로 이행한다. 직접 만든 promisify는 이 규약을 놓친다.
3. **함수가 아니거나 콜백 규약을 따르지 않으면 `TypeError`를 던진다.**

```js
import { promisify } from 'node:util'
import { exec } from 'node:child_process'

const execAsync = promisify(exec)
const { stdout, stderr } = await execAsync('node --version')
// 커스텀 구현 덕분에 두 값이 객체로 함께 온다
```

### 실무 함정

- **이벤트를 여러 번 발생시키는 API는 프로미스화하면 안 된다.** 프로미스는 한 번만 확정된다. 스트림·이벤트 이미터는 비동기 이터레이터(7장 참조)로 다뤄야 한다.
- **콜백이 성공 시 `err` 자리에 `null`이 아니라 `false`나 `0`을 넘기는 비표준 API가 있다.** `if (err)`가 오작동할 수 있으니 규약을 확인한다.
- **이미 프로미스 버전이 있으면 그것을 쓴다.** `fs.promises.readFile`은 promisify한 `fs.readFile`보다 오버헤드가 적고 `AbortSignal`을 지원한다.
- **프로미스 생성자로 프로미스를 감싸지 않는다.** `new Promise(r => somePromise.then(r))`는 불필요한 래핑이며 거부를 잃는다. 이는 explicit construction anti-pattern으로 불린다.

## 6.3 `async` 함수와 `await` 표현식

### 왜 필요한가

프로미스 체인은 콜백 지옥을 평평하게 폈지만 여전히 함수 리터럴의 나열이다. 조건 분기, 반복문, `try...catch`, `for` 루프 같은 언어의 기본 제어 구조를 그대로 쓸 수 없다. `async`/`await`는 프로미스 위에 얹힌 문법 계층으로, 비동기 코드를 동기 코드와 같은 문법으로 쓰게 해 준다. 중요한 것은 이것이 *새로운 비동기 모델이 아니라는* 점이다. 밑바닥은 여전히 프로미스이고, 규칙을 이해하려면 6.1의 상태 기계를 기억해야 한다.

### 어떻게 동작하는가

`async` 키워드가 붙은 함수는 **항상 프로미스를 반환한다**. 본문이 값 `v`를 반환하면 그 프로미스는 `v`로 이행하고, 예외를 던지면 그 예외로 거부한다. 본문에 `await`가 하나도 없어도 마찬가지다.

`await`는 피연산자를 `Promise.resolve`로 감싼 뒤, 그 프로미스가 확정될 때까지 **함수의 실행을 중단(suspend)** 한다. 중단은 스레드를 막는 것이 아니다. 함수의 나머지 부분이 그 프로미스의 `then` 핸들러로 등록되고, 제어권은 즉시 호출자에게 돌아간다. 이벤트 루프는 그동안 다른 일을 계속한다. 프로미스가 이행되면 함수는 마이크로태스크로 재개되어 중단 지점부터 이어진다. 거부되면 중단 지점에서 예외가 *던져진* 것처럼 동작한다.

```js
async function fetchTitle(url) {
  const res = await fetch(url)                 // 여기서 함수가 중단된다
  if (!res.ok) throw new Error(`HTTP ${res.status}`)
  const html = await res.text()                // 두 번째 중단 지점
  return html.match(/<title>(.*?)<\/title>/is)?.[1] ?? '(제목 없음)'
}
```

`await`는 프로미스가 아닌 값에도 쓸 수 있다. 이때도 함수는 최소 한 틱 중단된다. 즉 `await 42`는 값을 즉시 주지 않고 마이크로태스크 하나를 소비한다. 이는 6.1의 "then은 항상 비동기"라는 보장의 연장이며, 성능이 아니라 순서 예측 가능성을 위한 설계다.

ESM 모듈에서는 **최상위 await(top-level await)** 를 쓸 수 있다(2장 참조). 모듈 본문이 비동기 함수처럼 동작하며, 해당 모듈을 import하는 모듈은 평가가 끝날 때까지 대기한다. 설정 파일 로드나 DB 커넥션 준비에 유용하지만, 모듈 그래프 전체를 지연시키므로 진입점 근처에서만 쓴다.

### 스파이더 재구현

5장의 콜백 기반 `spiderLinks`를 `async`로 다시 쓰면 배관이 사라진다.

```js
import { mkdir, writeFile, readFile } from 'node:fs/promises'
import { dirname } from 'node:path'
import { urlToFilename, getPageLinks } from './utils.js'

// 페이지 하나를 내려받아 저장하고, 본문을 반환한다
async function download(url, filename) {
  console.log(`다운로드 중: ${url}`)
  const res = await fetch(url)
  const content = await res.text()
  await mkdir(dirname(filename), { recursive: true })
  await writeFile(filename, content)
  return content
}

export async function spider(url, depth = 2) {
  const filename = urlToFilename(url)
  let content
  try {
    content = await readFile(filename, 'utf8')   // 이미 받아둔 페이지면 재사용
  } catch (err) {
    if (err.code !== 'ENOENT') throw err          // 파일 없음 외의 오류는 전파
    content = await download(url, filename)
  }
  if (depth === 0) return
  for (const link of getPageLinks(url, content)) {
    await spider(link, depth - 1)                 // 순차 크롤링
  }
}
```

5장 버전과 비교하면 콜백 중첩, `done` 카운터, 오류 수동 전달이 전부 사라졌다. 남은 것은 도메인 로직뿐이다.

### 실무 함정

- **`await`는 `async` 함수 본문(또는 ESM 최상위)에서만 유효하다.** 콜백 안에 `await`를 쓰려면 그 콜백 자체가 `async`여야 하고, 그러면 6.8의 문제가 시작된다.
- **`await`는 병렬성을 죽인다.** 위 스파이더는 링크를 하나씩 처리한다. 의도한 것이라면 옳지만, 무심코 쓰면 성능이 수십 배 나빠진다. 6.6에서 고친다.
- **`async` 함수는 동기 예외를 던지지 않는다.** 인자 검증 실패조차 거부된 프로미스가 된다. 호출자가 `try`로 감싸지 않고 `.catch`도 없으면 조용히 사라진다.

## 6.4 오류 처리: 통합된 `try...catch`, `return` vs `return await`

### 왜 필요한가

5장에서 오류 처리는 규율의 문제였다. 모든 콜백의 첫 인자를 검사하고, 잊으면 오류가 사라졌다. `async`/`await`에서는 동기 예외와 비동기 거부가 **하나의 `try...catch`로 통합된다.** 하지만 새로운 함정이 생긴다. 그 중 가장 악명 높은 것이 `return`과 `return await`의 차이다.

### 어떻게 동작하는가

`await` 표현식이 거부된 프로미스를 만나면 해당 지점에서 예외가 던져진다. 따라서 `try` 블록으로 감싸면 잡힌다.

```js
async function loadConfig(path) {
  try {
    const raw = await readFile(path, 'utf8')     // 비동기 실패
    return JSON.parse(raw)                       // 동기 실패
  } catch (err) {
    // 두 종류 모두 여기로 온다
    throw new Error(`설정 로드 실패: ${path}`, { cause: err })
  } finally {
    console.log('설정 로드 시도 종료')
  }
}
```

`cause` 옵션(ES2022)은 원인 오류를 보존하면서 상위 문맥을 덧붙이는 표준 방법이다. 스택 트레이스를 잃지 않으려면 새 오류를 만들 때 항상 `cause`를 채운다.

### `return` vs `return await`

거부된 프로미스를 **그대로 반환**하는 것과 **`await`한 뒤 반환**하는 것은 의미가 다르다.

```js
async function inner() {
  await null
  throw new Error('실패 지점')
}

// (A) await 없이 반환 — 프로미스가 호출자에게 그대로 넘어간다
async function plainReturn() {
  return inner()
}

// (B) await 후 반환 — 이 함수 안에서 거부가 예외로 실체화된다
async function returnAwait() {
  return await inner()
}
```

**차이 1: `try` 블록 안에서의 동작.** 이것이 실제 버그를 만든다.

```js
async function withoutAwait() {
  try {
    return inner()          // 프로미스를 반환할 뿐, 거부는 아직 일어나지 않았다
  } catch (err) {
    console.log('잡힘 A')    // 결코 실행되지 않는다
    return 'fallback'
  }
}

async function withAwait() {
  try {
    return await inner()    // 여기서 거부가 예외로 던져진다
  } catch (err) {
    console.log('잡힘 B')    // 실행된다
    return 'fallback'
  }
}

console.log(await withoutAwait().catch(e => `밖에서 잡힘: ${e.message}`))
// → 밖에서 잡힘: 실패 지점   (catch 블록이 무력화되었다)
console.log(await withAwait())
// → 잡힘 B 출력 후 fallback
```

`return inner()`는 `try` 블록을 *빠져나가면서* 프로미스를 넘긴다. 거부는 그 이후 호출자 쪽에서 발생하므로 이 함수의 `catch`는 절대 실행되지 않는다. `finally` 블록도 마찬가지로 정리 시점이 어긋난다. **`try` 안에서 비동기 결과를 반환할 때는 반드시 `return await`를 쓴다.**

**차이 2: 스택 트레이스.** V8의 비동기 스택 트레이스는 `await` 지점을 기준으로 프레임을 이어 붙인다. `await` 없이 반환하면 중간 함수가 이미 스택에서 제거된 뒤 거부가 전파되므로 프레임이 빠진다.

```text
// return inner() 의 스택
Error: 실패 지점
    at inner (file:///app/x.js:3:9)
// plainReturn 프레임이 없다 — 어느 경로로 왔는지 알 수 없다

// return await inner() 의 스택
Error: 실패 지점
    at inner (file:///app/x.js:3:9)
    at async returnAwait (file:///app/x.js:12:10)
    at async main (file:///app/x.js:20:3)
```

프로덕션에서 로그만 보고 원인을 추적해야 하는 상황이라면 이 차이는 결정적이다.

### 실무 함정

- **처리되지 않은 거부(unhandled rejection)는 Node.js 15부터 기본적으로 프로세스를 종료시킨다.** `process.on('unhandledRejection')`으로 로깅하되, 종료를 막아 상태가 깨진 채 계속 도는 것보다는 종료 후 재시작이 낫다(29장 참조).
- **`catch (err)`에서 오류를 삼키지 않는다.** 로깅만 하고 되던지지 않으면 함수는 `undefined`로 이행하고, 호출자는 성공으로 착각한다.
- **성능을 이유로 `return await`를 피하라는 조언은 낡았다.** 현재 V8은 `return await`의 추가 마이크로태스크 비용을 대부분 제거했다. 정확성이 우선이다.

## 6.5 순차 실행과 반복

### 왜 필요한가

5장에서 순차 반복(sequential iteration)은 별도의 `iterate` 재귀 함수를 만들어야 했다. 다음 항목을 처리하려면 이전 콜백 안에서 자기 자신을 다시 호출하는 구조였고, 인덱스 관리와 종료 조건이 모두 수작업이었다. `async`/`await`에서는 이 패턴이 언어의 `for` 루프로 환원된다. 그런데도 순차 실행 코드가 여전히 자주 틀린다. 배열 메서드가 프로미스를 이해하지 못하기 때문이다.

### 어떻게 동작하는가

`for...of` 루프 본문 안의 `await`는 루프 자체를 중단시킨다. 따라서 반복은 완전히 순차적이다.

```js
// 링크를 하나씩, 앞의 것이 끝난 뒤에만 다음 것을 처리한다
async function crawlSequential(links, depth) {
  const results = []
  for (const link of links) {
    results.push(await spider(link, depth))
  }
  return results
}
```

`while`, `do...while`, `for` 어느 것을 써도 동일하다. 중요한 것은 `Array.prototype.forEach`, `map`, `filter`, `reduce`는 이 규칙을 따르지 않는다는 점이다. 이들은 콜백의 반환값이 프로미스라는 사실을 모르므로 기다리지 않는다(6.8 참조).

**순차 실행이 필요한 실제 상황**은 생각보다 많다.

- 앞 단계의 결과가 다음 단계의 입력인 경우(토큰 발급 → 조회 → 갱신)
- 외부 API의 요청 순서가 의미를 갖는 경우(계좌 이체의 출금·입금)
- 레이트 리밋이 매우 빡빡해 동시 요청이 즉시 429를 부르는 경우
- 커서 기반 페이지네이션처럼 다음 요청의 커서를 앞 응답에서 얻는 경우

### 동적 체인 구성

항목 수를 미리 모를 때는 `reduce`로 프로미스 체인을 접어 만들 수도 있다. `async` 이전 시대의 관용구지만, 지금도 "체인을 값으로 만들어 나중에 실행"해야 할 때 유용하다.

```js
// 각 작업을 앞 작업의 then에 이어 붙여 순차 체인을 구성한다
const runSequentially = tasks =>
  tasks.reduce(
    (chain, task) => chain.then(acc => task().then(r => [...acc, r])),
    Promise.resolve([])
  )
```

가독성 면에서는 `for...of`가 낫다. 다만 `reduce` 버전은 각 작업이 아직 실행되지 않은 **작업 팩토리(task factory)** 라는 점이 명확히 드러난다. 이 구분은 6.7에서 결정적으로 중요해진다. 프로미스는 생성되는 즉시 실행이 시작되므로, 실행을 미루려면 프로미스가 아니라 "프로미스를 만드는 함수"를 다뤄야 한다.

### 비동기 이터레이터를 이용한 순차 스트리밍

Node.js 코어의 여러 API는 비동기 이터러블(async iterable)을 반환하며, `for await...of`로 순차 소비한다.

```js
import { opendir } from 'node:fs/promises'

// 디렉터리 항목을 메모리에 전부 올리지 않고 하나씩 순차 처리한다
const dir = await opendir('./pages')
for await (const entry of dir) {
  if (entry.isFile()) await indexPage(entry.name)
}
```

`for await...of`는 각 반복마다 `next()`가 반환한 프로미스를 기다린다. 스트림(7장 참조)과 결합하면 메모리 상한이 고정된 순차 파이프라인을 만들 수 있다.

### 실무 함정

- **순차 루프에서 하나가 실패하면 루프 전체가 중단된다.** 부분 실패를 허용하려면 루프 안에 `try...catch`를 넣고 실패를 수집한다.
- **불필요한 순차화는 가장 흔한 성능 문제다.** 각 반복이 서로 독립적이라면 6.6의 병렬 조합자를 쓴다. 100개 항목 × 200ms 지연이면 순차는 20초, 병렬은 0.2초다.
- **`for await...of`를 `break`로 빠져나가면 이터레이터의 `return()`이 호출된다.** 스트림은 이때 정리되지만, 직접 만든 비동기 제너레이터라면 `finally` 블록으로 정리를 보장해야 한다.

## 6.6 병렬 실행: `all` / `allSettled` / `race` / `any`

### 왜 필요한가

Node.js의 I/O는 비동기이므로, 서로 독립적인 작업은 동시에 진행할 수 있다. 5장에서는 완료 카운터와 `finished` 플래그를 손으로 관리해 이를 구현했다. 프로미스는 네 가지 조합자(combinator)로 이를 표준화한다. 각각이 언제 확정되는지, 실패를 어떻게 다루는지가 다르므로 정확히 구분해서 써야 한다.

### 네 조합자 비교

| 조합자 | 이행 조건 | 거부 조건 | 이행값 | 주 용도 |
|---|---|---|---|---|
| `Promise.all` | 전부 이행 | 하나라도 거부 (즉시) | 값 배열(입력 순서) | 전부 성공해야 의미 있는 작업 |
| `Promise.allSettled` | 항상(모두 확정 시) | 없음 | `{status, value\|reason}` 배열 | 부분 실패 허용 |
| `Promise.race` | 첫 확정이 이행 | 첫 확정이 거부 | 첫 확정값 | 타임아웃, 최초 응답 채택 |
| `Promise.any` | 첫 이행 | 전부 거부 시 `AggregateError` | 첫 이행값 | 다중 미러 중 아무거나 성공 |

`race`와 `any`의 차이가 자주 혼동된다. `race`는 **가장 먼저 확정된 것**을 채택하므로 첫 응답이 실패면 전체가 실패한다. `any`는 **가장 먼저 성공한 것**을 채택하므로 실패는 무시하고 기다린다. 폴백 미러를 쓰려면 `any`, 타임아웃을 붙이려면 `race`다.

```js
// 스파이더의 병렬 버전 — 링크들을 동시에 처리한다
async function spiderLinks(currentUrl, content, depth) {
  if (depth === 0) return
  const links = getPageLinks(currentUrl, content)
  // 모든 프로미스를 먼저 만든 뒤 한꺼번에 기다린다
  const promises = links.map(link => spider(link, depth - 1))
  await Promise.all(promises)
}
```

`links.map(...)`이 실행되는 순간 모든 `spider` 호출이 시작된다. `Promise.all`은 시작시키는 것이 아니라 **기다릴 뿐이다.** 이 구분을 이해하면 다음 오해도 자연히 풀린다.

### `Promise.all`에 대한 흔한 오해 바로잡기

"`Promise.all`은 하나가 실패하면 나머지를 취소한다"는 말은 **틀렸다.** 프로미스에는 취소 개념이 없다. `Promise.all`이 반환한 프로미스는 첫 거부에서 즉시 거부되지만, 나머지 작업들은 **계속 실행되고 완료된다.** 그들의 결과는 아무도 보지 않을 뿐이다.

결과는 세 가지 실제 문제다.

1. **자원이 계속 소모된다.** 실패를 알고도 나머지 200개의 HTTP 요청이 끝까지 나간다.
2. **부수 효과가 남는다.** 실패 후에도 다른 작업들이 DB에 쓰기를 마쳐, 일부만 반영된 상태가 된다.
3. **뒤늦은 거부가 처리되지 않은 거부가 된다.** 다른 프로미스도 실패하면 그 거부에는 핸들러가 없어 `unhandledRejection`이 발생한다.

실제로 중단하려면 6.9의 `AbortController`로 취소 신호를 명시적으로 전파해야 한다.

### `allSettled`를 써야 하는 상황

부분 실패가 정상인 시나리오에서는 `all`이 오히려 해롭다. 구체적인 예를 든다.

- **대시보드 위젯 집계**: 6개 마이크로서비스에서 데이터를 모아 화면을 그린다. 하나가 죽었다고 페이지 전체를 500으로 반환하면 안 된다. 나머지 5개는 그리고, 죽은 칸에는 "일시적 오류"를 표시한다.
- **알림 팬아웃(fan-out)**: 1,000명에게 푸시를 보낸다. 3명이 실패했다고 나머지 997명의 발송을 실패로 보고할 수 없다.
- **스파이더의 링크 크롤링**: 깨진 링크 하나 때문에 전체 크롤링이 죽으면 안 된다.

```js
const results = await Promise.allSettled(links.map(l => spider(l, depth - 1)))

const failed = results
  .map((r, i) => ({ ...r, url: links[i] }))
  .filter(r => r.status === 'rejected')

if (failed.length) {
  console.warn(`${failed.length}/${links.length}개 링크 실패`)
  for (const f of failed) console.warn(`  ${f.url}: ${f.reason.message}`)
}
// 성공한 것만으로 진행한다
const ok = results.filter(r => r.status === 'fulfilled').map(r => r.value)
```

`allSettled`는 절대 거부하지 않으므로, 실패 임계값 판단은 호출자의 몫이다. "절반 이상 실패하면 전체 실패로 간주" 같은 정책을 직접 구현한다.

### 실무 함정

- **`Promise.all`에 `async` 함수 배열이 아니라 호출 결과 배열을 넘겨야 한다.** `Promise.all(tasks)`에서 `tasks`가 함수 배열이면 즉시 이행되며 아무것도 실행되지 않는다.
- **무한정 병렬은 병렬이 아니다.** 링크 5,000개를 동시에 요청하면 소켓 고갈, `EMFILE`, 상대 서버의 차단이 뒤따른다. 6.7의 동시성 제한이 필요하다.
- **`Promise.race`에 넘긴 지지 않은 프로미스도 계속 산다.** 타임아웃 패턴에서 원 작업의 타이머를 `clearTimeout`으로 정리하지 않으면 프로세스가 종료되지 않는다.

## 6.7 동시성 제한: `TaskQueue` 구현

### 왜 필요한가

6.6의 무제한 병렬은 링크가 수천 개인 사이트에서 즉시 무너진다. 파일 디스크립터가 고갈되어 `EMFILE`이 뜨거나, 상대 서버가 429/503으로 응답하거나, 로컬 메모리가 동시 응답 버퍼로 가득 찬다. 5장에서 우리는 콜백 기반 `TaskQueue`로 이를 해결했다. 같은 개념을 프로미스로 다시 구현하면 훨씬 짧고, 각 작업의 결과를 호출자에게 프로미스로 돌려줄 수 있다는 이점이 생긴다.

### 어떻게 동작하는가

핵심은 6.5에서 언급한 구분이다. 프로미스는 생성 즉시 실행되므로, 실행을 미루려면 큐에 프로미스가 아니라 **작업 팩토리**(호출하면 프로미스를 반환하는 함수)를 담아야 한다. 큐는 실행 중인 작업 수를 세고, 상한 미만일 때만 다음 팩토리를 꺼내 호출한다. 작업이 끝나면 카운터를 줄이고 다음을 당긴다.

```js
export class TaskQueue {
  #concurrency
  #running = 0
  #queue = []

  constructor(concurrency) {
    this.#concurrency = concurrency
  }

  // 작업 팩토리를 큐에 넣고, 그 작업의 결과를 나타내는 프로미스를 반환한다
  runTask(taskFactory) {
    return new Promise((resolve, reject) => {
      this.#queue.push({ taskFactory, resolve, reject })
      process.nextTick(() => this.#next())
    })
  }

  #next() {
    while (this.#running < this.#concurrency && this.#queue.length) {
      const { taskFactory, resolve, reject } = this.#queue.shift()
      this.#running++
      // 팩토리가 동기적으로 던져도 거부로 흡수되도록 resolve로 감싼다
      Promise.resolve()
        .then(taskFactory)
        .then(resolve, reject)
        .finally(() => {
          this.#running--
          this.#next()   // 슬롯이 비었으니 다음 작업을 당긴다
        })
    }
  }
}
```

`runTask`가 프로미스를 반환하는 것이 5장 버전과의 결정적 차이다. 호출자는 큐에 넣은 각 작업을 개별적으로 `await`할 수 있고, 그 결과들을 다시 `Promise.all`이나 `allSettled`로 묶을 수 있다.

```js
const queue = new TaskQueue(4)   // 동시 4개까지만

async function spiderLinks(currentUrl, content, depth) {
  if (depth === 0) return
  const links = getPageLinks(currentUrl, content)
  const results = await Promise.allSettled(
    links.map(link => queue.runTask(() => spider(link, depth - 1)))
  )
  return results
}
```

`links.map`은 즉시 실행되지만, 이제 각 항목은 `runTask` 호출일 뿐이다. 실제 `spider` 호출은 큐가 슬롯을 내줄 때까지 지연된다. 링크가 5,000개여도 네트워크에는 동시에 4개만 나간다.

### 왜 `finally`인가

`finally`를 쓰면 성공·실패에 관계없이 슬롯이 반환된다. `then(onFulfilled)`만 썼다면 실패한 작업의 슬롯이 영구히 점유되어, 실패가 누적될수록 처리량이 0으로 수렴하는 조용한 데드락이 생긴다. 실제 장애에서 흔히 보이는 형태이므로 반드시 `finally`(또는 `try...finally`)로 자원을 회수한다.

### p-limit 계열 라이브러리와의 비교

프로덕션에서는 보통 `p-limit`, `p-queue`, `p-map` 같은 검증된 패키지를 쓴다.

- **`p-limit`**: 위 `TaskQueue`와 사실상 같은 것을 최소한으로 제공한다. `const limit = pLimit(4)` 후 `limit(() => task())`로 감싼다. API가 함수 하나라 바꿔 끼우기 쉽다.
- **`p-map`**: 배열 매핑에 동시성 상한을 붙인 형태다. `pMap(links, spider, { concurrency: 4 })`. `stopOnError: false`로 `allSettled`와 비슷한 동작을 얻는다. 대부분의 실무 사례는 이것으로 충분하다.
- **`p-queue`**: 우선순위(priority), 일시 정지/재개, 초당 처리량 제한(`intervalCap`), 큐 길이 이벤트를 지원한다. 레이트 리밋이 "초당 10회"처럼 시간 기반일 때는 동시성 상한만으로는 부족하므로 이쪽이 맞다.

직접 구현할 가치가 있는 경우는 세 가지다. 의존성을 늘릴 수 없는 라이브러리 코드일 때, 큐에 도메인 고유 정책(호스트별 상한, 백오프 연동)을 넣어야 할 때, 그리고 학습 목적일 때다. 그 외에는 라이브러리를 쓰는 편이 낫다. 특히 우선순위나 시간 기반 제한이 필요해지는 순간 자체 구현의 복잡도가 급격히 올라간다.

### 실무 함정

- **동시성 상한을 하나만 두면 병목이 엉뚱한 곳으로 옮겨간다.** DB 커넥션 풀 크기, HTTP `Agent`의 `maxSockets`, 큐 상한을 함께 맞춰야 한다. 큐 상한이 풀 크기보다 크면 대기가 풀 안쪽에서 일어나 타임아웃을 만든다.
- **큐가 무한히 자란다.** 생산 속도가 소비 속도보다 빠르면 `#queue` 배열이 메모리를 잠식한다. 상한을 두고 초과 시 거부하거나 백프레셔를 위로 전달한다(7장 참조).
- **재귀적으로 큐를 쓰는 작업은 데드락을 만들 수 있다.** 스파이더처럼 큐 안의 작업이 다시 같은 큐에 작업을 넣고 그것을 `await`하면, 모든 슬롯이 대기 상태로 점유되어 진행이 멈춘다. 위 예제는 `spiderLinks`가 큐 밖에서 호출되므로 안전하지만, 구조를 바꿀 때 반드시 이 점을 점검한다.

## 6.8 안티패턴 모음: `forEach` + `async`, 무한 재귀 체인, 잊혀진 `await`

### 왜 필요한가

`async`/`await`는 비동기 코드를 동기 코드처럼 보이게 한다. 이 장점이 곧 위험이다. 동기적으로 *보이지만* 동기가 아닌 코드는 눈으로 검토할 때 넘어가기 쉽다. 아래 세 가지는 실제 코드 리뷰에서 가장 자주 발견되는 형태다.

### 안티패턴 1: 배열 메서드 + `async` 콜백

**잘못된 코드**

```js
async function saveAll(items) {
  items.forEach(async item => {
    await db.insert(item)
  })
  console.log('모두 저장 완료')   // 거짓말이다
}
```

**왜 문제인가.** `forEach`는 콜백의 반환값을 버린다. `async` 콜백이 반환한 프로미스는 아무도 잡지 않으므로 `forEach`는 즉시 끝나고, `console.log`가 저장 완료 전에 찍힌다. 더 나쁜 것은 오류다. `db.insert`가 실패하면 그 거부는 처리되지 않은 거부가 되어 프로세스를 죽인다. `map`, `filter`, `sort`의 비교 함수도 같은 문제를 갖는다. 특히 `filter(async x => ...)`는 모든 프로미스가 truthy이므로 **항상 전체 배열을 통과시킨다.**

**올바른 코드**

```js
// 순차가 필요하면 for...of
for (const item of items) await db.insert(item)

// 병렬이면 map으로 프로미스를 만들고 all로 기다린다
await Promise.all(items.map(item => db.insert(item)))

// 동시성 상한이 필요하면 6.7의 큐를 쓴다
await Promise.all(items.map(item => queue.runTask(() => db.insert(item))))
```

비동기 필터링은 값을 먼저 계산한 뒤 동기 필터를 적용한다.

```js
const flags = await Promise.all(items.map(isValid))
const valid = items.filter((_, i) => flags[i])
```

### 안티패턴 2: 무한 재귀 프로미스 체인

**잘못된 코드**

```js
function poll() {
  return checkQueue()
    .then(job => job ? handle(job) : delay(1000))
    .then(() => poll())      // 자기 자신을 체인에 이어 붙인다
}
poll()
```

**왜 문제인가.** `then`은 새 프로미스를 만들고, 그 프로미스는 체인 뒤쪽이 확정될 때까지 앞쪽 프로미스를 **참조로 붙잡는다.** 재귀가 끝나지 않으므로 이 참조 사슬은 절대 해제되지 않고, 반복마다 프로미스 객체와 핸들러 클로저가 힙에 쌓인다. 초당 한 번 폴링하는 프로세스에서 프로미스 하나가 대략 수백 바이트라면, 하루 86,400회 × 체인당 여러 객체로 수십 MB가 누적된다. 실제로 초당 100회 반복하는 워커에서는 시작 시 힙 사용량 40MB가 30분 만에 400MB를 넘고, 이후 GC 시간이 급증하다가 결국 `JavaScript heap out of memory`로 죽는 패턴을 흔히 본다. 힙 스냅숏을 뜨면 `Promise`와 그것이 붙잡은 클로저가 유지 크기(retained size) 상위를 독점한다(28장 참조).

**올바른 코드**

`async` 함수 안의 루프로 바꾸면 각 반복이 끝날 때 프레임이 해제되어 누적이 사라진다.

```js
async function poll(signal) {
  while (!signal.aborted) {
    const job = await checkQueue()
    if (job) await handle(job)
    else await setTimeout(1000, undefined, { signal })  // timers/promises
  }
}
```

`async` 함수의 `await`는 매 반복마다 별개의 마이크로태스크로 재개되며, 이전 반복의 프로미스는 확정 후 참조가 끊겨 회수된다. 재귀가 꼭 필요하다면 반환값으로 체인을 잇지 말고 트램폴린 구조로 평탄화한다.

### 안티패턴 3: 잊혀진 `await`

**잘못된 코드**

```js
async function transfer(from, to, amount) {
  const tx = await db.begin()
  try {
    tx.debit(from, amount)      // await 누락
    await tx.credit(to, amount)
    await tx.commit()
  } catch (err) {
    await tx.rollback()
    throw err
  }
}
```

**왜 문제인가.** `tx.debit`의 프로미스는 버려진다. 출금이 완료되기 전에 입금과 커밋이 진행되어 순서가 뒤집히고, 출금이 실패해도 `catch`가 잡지 못한다. 롤백은 이미 커밋된 트랜잭션에 대해 아무 일도 하지 않는다. 돈이 사라지는 종류의 버그다. 잊혀진 `await`는 조용하다는 점에서 최악이다. 테스트가 통과하기도 한다. 부하가 걸려 타이밍이 달라질 때만 드러난다.

**올바른 코드**

```js
await tx.debit(from, amount)
```

**어떻게 예방하는가.** 사람의 주의력에 의존하지 않는다. TypeScript의 `no-floating-promises`(typescript-eslint) 규칙을 켜면 처리되지 않은 프로미스를 컴파일 단계에서 잡는다. 순수 JavaScript라면 `eslint-plugin-promise`의 `catch-or-return`과 `require-await`가 부분적으로 도움이 된다. 의도적으로 기다리지 않는 경우에는 `void doSomething().catch(logError)`처럼 의도를 코드에 명시한다. `void` 표기는 린터를 침묵시키는 동시에 리뷰어에게 "이건 일부러 안 기다린다"는 신호를 준다.

## 6.9 `AbortController`로 취소 가능한 비동기 작업 만들기

### 왜 필요한가

6.6에서 확인했듯 프로미스는 취소할 수 없다. 이미 확정된 상태로 가는 중인 작업을 되돌릴 방법이 명세에 없다. 그러나 실무에서 취소는 필수다. 사용자가 검색어를 바꾸면 이전 요청은 낭비이고, HTTP 요청이 데드라인을 넘기면 뒤에서 계속 도는 작업은 자원 누수이며, 서버가 그레이스풀 셧다운(graceful shutdown)에 들어가면 진행 중인 배치를 멈춰야 한다. `AbortController`는 이 문제를 프로미스 밖에서 해결한다. 취소를 프로미스의 기능이 아니라 **별도의 신호 채널**로 모델링한 것이다.

### 어떻게 동작하는가

`AbortController`는 `signal` 프로퍼티(`AbortSignal` 인스턴스)와 `abort(reason)` 메서드를 갖는다. `abort`를 호출하면 신호의 `aborted`가 `true`가 되고 `abort` 이벤트가 발생한다. 신호를 받은 쪽이 스스로 중단하는 **협조적 취소(cooperative cancellation)** 모델이다. 신호는 취소를 강제하지 않는다. 신호를 무시하는 함수는 그냥 계속 실행된다.

`AbortSignal`은 한 번만 발동하며 재사용할 수 없다. 재시도할 때마다 새 컨트롤러를 만든다.

Node.js 코어의 주요 API는 대부분 `signal` 옵션을 받는다.

```js
import { readFile } from 'node:fs/promises'
import { setTimeout as delay } from 'node:timers/promises'
import { pipeline } from 'node:stream/promises'

const ac = new AbortController()
const { signal } = ac

// 글로벌 fetch
const res = await fetch(url, { signal })
// 파일 시스템
const data = await readFile('big.log', { signal })
// 타이머
await delay(5000, undefined, { signal })
// 스트림 파이프라인 — 중단 시 모든 스트림이 파괴된다
await pipeline(src, transform, dest, { signal })
```

취소되면 해당 프로미스는 `AbortError`(`err.name === 'AbortError'`)로 거부된다. `code`는 `ABORT_ERR`다. 일반 오류와 구분해 처리해야 로그가 오염되지 않는다.

### 정적 팩토리

- **`AbortSignal.timeout(ms)`**: 지정 시간 후 자동으로 발동하는 신호를 만든다. `TimeoutError`로 거부된다. 6.6의 `Promise.race` 타임아웃 패턴을 대체하며, 타이머 정리까지 알아서 한다. 이 타이머는 `unref`되어 있어 프로세스 종료를 막지 않는다.
- **`AbortSignal.any([...signals])`**: 여러 신호 중 하나라도 발동하면 발동하는 합성 신호를 만든다. "요청별 타임아웃 + 전역 셧다운 신호"를 결합할 때 쓴다.
- **`AbortSignal.abort(reason)`**: 이미 발동된 신호를 즉시 만든다. 테스트에 유용하다.

```js
// 요청 데드라인과 서버 셧다운 신호를 함께 존중한다
const signal = AbortSignal.any([
  AbortSignal.timeout(3000),
  shutdownController.signal
])
const res = await fetch(url, { signal })
```

### 사용자 정의 함수에서 신호 존중하기

직접 만든 비동기 함수도 `signal`을 받아 협조해야 취소가 체인 전체에 전파된다. 세 가지를 지킨다. 시작 전에 이미 발동했는지 확인하고, 각 중단 지점 사이에서 다시 확인하며, 하위 호출에 신호를 그대로 넘긴다.

```js
export async function spider(url, depth, { signal } = {}) {
  signal?.throwIfAborted()            // 시작 전 확인 — AbortError를 던진다
  const filename = urlToFilename(url)

  let content
  try {
    content = await readFile(filename, 'utf8', { signal })
  } catch (err) {
    if (err.name === 'AbortError') throw err
    if (err.code !== 'ENOENT') throw err
    const res = await fetch(url, { signal })
    content = await res.text()
    await writeFile(filename, content, { signal })
  }

  if (depth === 0) return
  for (const link of getPageLinks(url, content)) {
    signal?.throwIfAborted()          // 반복마다 재확인 — 긴 루프의 핵심
    await spider(link, depth - 1, { signal })
  }
}
```

`throwIfAborted()`는 발동 상태면 `signal.reason`을 던지고, 아니면 아무 일도 하지 않는다. 긴 루프나 배치 처리에서는 반복마다 호출해야 취소가 즉시 반영된다. 이벤트 기반으로 대기해야 한다면 `signal.addEventListener('abort', handler, { once: true })`를 쓰되, 작업이 정상 종료되면 `removeEventListener`로 반드시 해제한다. 하지 않으면 오래 사는 신호에 리스너가 쌓여 누수가 된다.

### 취소 후 정리

취소는 작업을 중간에 끊으므로, 열어 둔 자원이 남는다. 정리는 `try...finally`로 보장한다.

```js
async function exportReport(signal) {
  const tmp = await createTempFile()
  const conn = await pool.acquire()
  try {
    await runQuery(conn, { signal })
    await streamToFile(conn, tmp, { signal })
    return await finalize(tmp)
  } finally {
    // 성공·실패·취소 어느 경로로 나가든 반드시 실행된다
    pool.release(conn)
    await rm(tmp, { force: true })   // 취소된 경우 반쯤 쓰인 임시 파일 제거
  }
}
```

정리 코드 안에서는 **이미 발동한 신호를 다시 넘기지 않는다.** 정리 작업 자체가 즉시 `AbortError`로 실패해 자원이 남는다. 정리에는 신호 없는 호출이나 별도의 짧은 타임아웃을 쓴다.

### 실무 함정

- **`AbortError`를 실패로 로깅하지 않는다.** 정상적인 취소는 오류가 아니다. `if (err.name === 'AbortError') return`으로 조용히 빠져나가되, 상위 호출자에게는 취소되었음을 알린다.
- **`fetch`의 취소는 응답 본문까지 미친다.** 헤더를 받은 뒤 `res.text()` 중에 취소하면 본문 읽기가 거부된다. 부분 데이터를 쓰지 않도록 주의한다.
- **`AbortSignal.timeout`은 전체 요청의 데드라인이지 유휴 타임아웃이 아니다.** 느리게 계속 흘러오는 응답도 시간이 되면 끊긴다. 유휴 기준이 필요하면 직접 타이머를 갱신하는 컨트롤러를 만든다.
- **컨트롤러를 재사용하지 않는다.** 재시도 루프에서 같은 컨트롤러를 쓰면 첫 취소 이후 모든 시도가 즉시 실패한다(15장 참조).

## 요약

- 프로미스는 대기·이행·거부 세 상태를 한 번만 전이하는 상태 기계이며, `then`이 항상 마이크로태스크로 호출된다는 보장이 Zalgo 문제를 구조적으로 제거한다.
- `then`이 새 프로미스를 반환하고 thenable을 동화한다는 규칙 하나가 체이닝, 오류 전파, `await`의 동작 전부를 설명한다.
- 콜백 기반 API는 경계에서 `util.promisify`로 한 번만 변환한다. 직접 구현할 때는 `this` 바인딩과 다중 콜백 인자를 고려하되, 커스텀 심볼 규약은 표준 구현만 존중한다.
- `try` 블록 안에서 비동기 결과를 반환할 때는 반드시 `return await`를 쓴다. 그렇지 않으면 `catch`와 `finally`가 무력화되고 비동기 스택 트레이스에서 프레임이 사라진다.
- `Promise.all`은 첫 거부에서 즉시 거부하지만 나머지 작업을 **취소하지 않는다.** 부분 실패가 정상인 상황에서는 `allSettled`를 쓰고, 진짜 중단이 필요하면 `AbortSignal`을 전파한다.
- 배열 메서드에 `async` 콜백을 넘기는 것, 재귀 프로미스 체인, 잊혀진 `await`는 모두 조용히 실패한다. 린터 규칙으로 기계적으로 막는다.
- 동시성 제한은 프로미스가 아닌 **작업 팩토리**를 큐에 담아 구현하며, 슬롯 반환은 반드시 `finally`로 보장한다.

## 연습문제

1. `util.promisify`가 `util.promisify.custom` 심볼을 존중한다는 사실을 이용해, 콜백이 `(err, stdout, stderr)`를 넘기는 사내 함수에 커스텀 프로미스 구현을 붙여 `{ stdout, stderr }` 객체로 이행하게 만들어라. 커스텀 구현이 있을 때와 없을 때의 이행값 차이를 테스트로 확인한다.

2. 6.4의 `withoutAwait`/`withAwait` 예제를 확장해, `try`에 `finally` 블록을 추가한 뒤 두 경우의 실행 순서를 로그로 비교하라. 이어서 `--stack-trace-limit=20` 옵션으로 실행해 두 버전의 스택 트레이스를 나란히 출력하고, 사라진 프레임이 무엇인지 설명한다.

3. 6.7의 `TaskQueue`를 확장해 (a) 큐 길이 상한을 두고 초과 시 `runTask`가 즉시 거부하도록, (b) 생성자에서 받은 `AbortSignal`이 발동하면 대기 중인 작업을 모두 `AbortError`로 거부하고 새 작업 추가를 막도록 구현하라. 실행 중인 작업에는 각자의 신호가 전달되어야 한다. 동시성 3, 작업 20개, 5번째 작업 완료 시점에 취소하는 시나리오로 동작을 검증한다.
