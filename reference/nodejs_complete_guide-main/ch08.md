# 8장. 파일 시스템

파일 시스템은 Node.js가 다루는 I/O 중 가장 오래되고 가장 자주 쓰이는 대상이다. 설정 파일을 읽고, 로그를 쓰고, 업로드된 이미지를 저장하고, 정적 자산을 서빙하는 일은 거의 모든 서버 애플리케이션에 등장한다. 그런데 파일 시스템은 네트워크와 달리 "빠르니까 괜찮겠지"라는 착각을 부른다. 로컬 디스크가 빠른 것은 사실이지만, 이벤트 루프를 붙잡는 동기 호출 하나가 초당 수천 건의 요청을 처리하던 서버를 그대로 멈춰 세운다.

이 장에서는 경로와 파일 메타데이터라는 기초부터 시작해, `fs/promises`를 중심으로 한 현대적 API 선택 기준, 파일 크기에 따라 달라지는 세 가지 읽기 전략, 대용량 디렉터리 순회, 파일 감시의 플랫폼별 함정, 정적 파일 서빙의 보안과 캐싱, 업로드 스트리밍 처리, 그리고 프로세스가 죽어도 파일이 깨지지 않게 만드는 원자적 쓰기까지 다룬다. 스트림 기반 처리는 7장에서 다룬 개념을 전제로 하므로, 백프레셔가 낯설다면 7장을 먼저 읽는 편이 좋다.

## 8.1 경로, 파일 타입, 파일 속성

### 왜 필요한가

파일 시스템 코드에서 가장 흔한 버그는 파일 자체가 아니라 **경로(path)** 를 잘못 다루는 데서 나온다. 문자열을 `+`로 이어 붙여 경로를 만들면 구분자가 중복되거나 빠지고, 윈도우에서만 깨지는 코드가 되며, 사용자 입력이 섞이는 순간 경로 탐색(path traversal) 취약점이 된다. 파일의 **속성(attribute)** 도 마찬가지다. 심볼릭 링크를 일반 파일로 착각하거나, 디렉터리를 파일로 열려다 `EISDIR`로 죽는 코드가 실제 운영에서 자주 발견된다.

### 어떻게 동작하는가

`node:path` 모듈은 실행 중인 플랫폼에 맞는 구현을 기본으로 노출하고, `path.posix`와 `path.win32`로 특정 플랫폼 규칙을 명시적으로 선택할 수 있다. 이 구분이 중요한 이유는, 서버가 리눅스에서 돌더라도 처리해야 할 경로 문자열이 항상 POSIX 규칙을 따르지는 않기 때문이다. 예를 들어 URL 경로는 언제나 `/` 구분자를 쓰므로 `path.posix`로 다뤄야 하고, 윈도우 클라이언트가 보낸 파일명에는 `\`가 섞여 들어온다.

```js
import path from 'node:path'

// 플랫폼 기본 구현 — 리눅스에서는 posix, 윈도우에서는 win32와 동일하다
path.join('a', 'b', '..', 'c')        // 'a/c' (리눅스)

// 명시적 선택
path.win32.join('C:\\app', 'logs')    // 'C:\\app\\logs'
path.posix.join('/app', 'logs')       // '/app/logs'

// 구분자 상수
path.sep        // 리눅스 '/', 윈도우 '\\'
path.delimiter  // PATH 환경변수 구분자. 리눅스 ':', 윈도우 ';'

// URL 경로는 언제나 posix로 다룬다
path.posix.normalize('/static//img/../css/app.css')  // '/static/css/app.css'
```

`join`과 `resolve`의 차이는 반드시 구분해야 한다. `join`은 조각을 이어 붙이고 정규화만 하지만, `resolve`는 **오른쪽에서 왼쪽으로** 훑으면서 절대 경로가 완성될 때까지 진행하고, 끝까지 절대 경로가 없으면 현재 작업 디렉터리(`process.cwd()`)를 앞에 붙인다. 즉 `resolve`의 결과는 언제나 절대 경로다.

```js
path.join('/app', '/etc/passwd')     // '/app/etc/passwd' — 그냥 이어 붙인다
path.resolve('/app', '/etc/passwd')  // '/etc/passwd'     — 절대 경로가 앞을 덮어쓴다
```

이 차이는 8.6절의 경로 탐색 방어에서 다시 등장한다. 사용자 입력을 `resolve`에 넘기면 앞의 기준 디렉터리가 통째로 무시될 수 있다는 점을 기억해 두자.

ESM 모듈에는 `__dirname`과 `__filename`이 없다. 대신 `import.meta.dirname`(Node 20.11+)을 쓰거나, 구버전 호환이 필요하면 `fileURLToPath`를 쓴다.

```js
import { fileURLToPath } from 'node:url'
import path from 'node:path'

// Node 20.11 이상
const here = import.meta.dirname

// 하위 호환이 필요한 경우
const here2 = path.dirname(fileURLToPath(import.meta.url))
```

파일의 속성은 `stat` 계열 함수가 돌려주는 `Stats` 객체에 담긴다. 여기서 세 함수의 차이가 결정적이다. `stat`은 심볼릭 링크를 **따라가서** 최종 대상의 정보를 주고, `lstat`은 링크 **자체**의 정보를 주며, `fstat`(`FileHandle.stat()`)은 이미 열린 파일 디스크립터의 정보를 준다.

```js
import { stat, lstat, realpath } from 'node:fs/promises'

const info = await lstat('/var/log/current')
if (info.isSymbolicLink()) {
  const target = await realpath('/var/log/current')  // 링크가 최종적으로 가리키는 실제 경로
  const real = await stat('/var/log/current')        // 대상 파일의 크기·시각
  console.log(target, real.size)
}

console.log(info.isFile(), info.isDirectory(), info.isSymbolicLink())
console.log(info.size)     // 바이트. 디렉터리의 size는 의미가 없다
console.log(info.mtimeMs)  // 최종 수정 시각(밀리초). 캐시 검증에 쓴다
console.log(info.ino, info.dev)  // inode 번호와 디바이스 ID — 파일 동일성 판정에 쓴다
```

`mtime`(수정), `atime`(접근), `ctime`(inode 변경), `birthtime`(생성) 네 가지 시각이 있고, 각각 `Date` 객체 버전과 `Ms` 접미사가 붙은 숫자 버전이 함께 제공된다. 캐시 헤더나 변경 감지에는 부동소수점 오차가 없는 `mtimeMs`를 쓰는 편이 안전하다. 다만 파일 시스템에 따라 mtime 해상도가 1초 단위인 경우가 있어(일부 ext3, HFS+), 1초 안에 두 번 바뀐 파일은 같은 mtime을 갖는다. 정확한 변경 감지가 필요하면 크기와 inode를 함께 본다.

`mode` 필드는 파일 타입 비트와 권한 비트가 합쳐진 숫자다. `node:fs`의 `constants`와 비트 연산으로 해석한다.

```js
import { constants } from 'node:fs'
import { stat, chmod, access } from 'node:fs/promises'

const s = await stat('deploy.sh')
console.log((s.mode & 0o777).toString(8))            // '755' — 권한만 8진수로
console.log(Boolean(s.mode & constants.S_IXUSR))     // 소유자 실행 가능 여부

await chmod('deploy.sh', 0o750)  // rwxr-x---

// 권한 확인은 access로. 실패 시 예외를 던진다
try {
  await access('config.json', constants.R_OK | constants.W_OK)
} catch {
  console.error('읽기/쓰기 권한이 없다')
}
```

### 실무 함정

- **`access`로 확인한 뒤 열지 마라.** 확인과 사용 사이에 파일이 바뀔 수 있다(TOCTOU, time-of-check to time-of-use). 권한이 있는지 미리 묻는 대신 그냥 열고 `EACCES`/`ENOENT`를 잡는 편이 안전하고 빠르다. `access`는 "이 파일을 여는 게 아니라 존재 여부만 알고 싶다"는 진단 목적에만 쓴다.
- **`fs.exists`는 폐기(deprecated)됐다.** 콜백 시그니처가 다른 API와 달라 오용을 부른다. 존재 확인이 정말 필요하면 `access` 또는 `stat`의 `ENOENT`를 잡는다.
- **`path.join`으로 사용자 입력을 처리하면 `..`가 살아 있다.** `join`은 정규화하면서 `..`를 실제로 적용하기 때문에 `path.join('/upload', '../../etc/passwd')`는 `/etc/passwd`가 된다. 반드시 8.6절의 접두사 검사를 거쳐야 한다.
- **`stat().size`를 신뢰해 버퍼를 미리 할당하지 마라.** 다른 프로세스가 쓰는 중이면 크기가 변한다. 스트림이나 `readFile`은 이 문제를 알아서 처리한다.

## 8.2 `fs/promises` 중심의 파일 조작

### 왜 필요한가

Node.js의 파일 시스템 API는 역사적 이유로 세 벌이 공존한다. 콜백 기반 `node:fs`, 동기 `fs.*Sync`, 그리고 프로미스 기반 `node:fs/promises`다. 같은 기능이 세 가지 형태로 존재하니 초보자는 아무거나 고르고, 그 선택이 서버 전체의 처리량을 좌우한다. 선택 기준을 명확히 못박아 두는 것이 이 절의 목적이다.

### 어떻게 동작하는가

세 API는 이렇게 동작한다. 콜백과 프로미스 버전은 작업을 **libuv의 스레드 풀**에 넘기고 즉시 반환한다. 이벤트 루프는 그동안 다른 요청을 처리한다. 동기 버전은 스레드 풀을 쓰지 않고 호출 스레드에서 시스템 콜을 그대로 실행한다. 즉 **이벤트 루프가 통째로 멈춘다**.

```js
import { readFile } from 'node:fs/promises'
import { readFile as readFileCb, readFileSync } from 'node:fs'

// 1. 프로미스 — 기본 선택
const buf = await readFile('data.json')

// 2. 콜백 — 성능이 극도로 중요한 핫 패스, 또는 레거시 코드
readFileCb('data.json', (err, data) => { /* ... */ })

// 3. 동기 — 부팅 시점에만
const config = JSON.parse(readFileSync('config.json', 'utf8'))
```

선택 기준은 다음과 같다.

**`fs/promises`를 기본으로 쓴다.** `async/await`와 자연스럽게 맞물리고, 오류가 예외로 전파되어 `try/catch`로 다룰 수 있으며, `AbortSignal`을 옵션으로 받아 취소가 가능하다. 대부분의 애플리케이션 코드는 여기서 끝난다.

**콜백 API는 마이크로 최적화가 필요할 때만 쓴다.** 프로미스 래핑에는 프로미스 객체 할당과 마이크로태스크 큐 왕복이라는 오버헤드가 있다. 초당 수만 건의 작은 파일 접근이 일어나는 경로에서는 10~20% 차이가 나기도 한다. 하지만 코드 가독성 손실이 크므로, 벤치마크로 병목을 확인하기 전에는 손대지 않는다.

**동기 API를 써도 되는 유일한 경우는 프로세스 부팅 시점이다.** 정확히는 "아직 요청을 받지 않는 시점, 즉 서버가 `listen()`을 호출하기 전"이다. 이때는 이벤트 루프가 막혀도 영향을 받는 사용자가 없다. 설정 파일 읽기, 인증서 로드, 마이그레이션 파일 목록 스캔이 여기 해당한다. 그 외의 모든 곳 — 요청 핸들러, 타이머 콜백, 이벤트 리스너, 워커의 작업 루프 — 에서 동기 API는 금지다.

```js
// server.mjs
import { readFileSync } from 'node:fs'
import { readFile } from 'node:fs/promises'
import http from 'node:http'

// 부팅 시점: 동기 호출 허용. 실패하면 어차피 프로세스를 띄우면 안 된다
const key = readFileSync('./certs/server.key')
const cert = readFileSync('./certs/server.crt')
const config = JSON.parse(readFileSync('./config.json', 'utf8'))

const server = http.createServer(async (req, res) => {
  // 요청 처리 시점: 반드시 비동기
  const template = await readFile('./views/index.html', 'utf8')
  res.end(template)
})

server.listen(config.port)  // 이 줄 이후로는 동기 fs 호출 금지
```

동기 호출이 왜 그렇게 치명적인지는 숫자로 봐야 실감이 난다. NVMe SSD에서 1MB 파일 하나를 읽는 데 약 1~2ms가 걸린다. 초당 5,000건을 처리하는 서버에서 요청마다 이 동기 호출을 하면, 이벤트 루프는 초당 5~10초어치의 작업을 해야 한다. 즉 서버가 즉시 무너진다. 콜드 캐시나 네트워크 파일 시스템(NFS)이라면 한 번의 호출이 수백 밀리초로 늘어나고, 그동안 **모든** 연결이 응답을 받지 못한다.

`fs/promises`의 주요 조작 함수는 다음과 같다.

```js
import {
  readFile, writeFile, appendFile, copyFile,
  rename, rm, mkdir, unlink, truncate, utimes
} from 'node:fs/promises'
import { constants } from 'node:fs'

await writeFile('out.txt', '내용', 'utf8')
await appendFile('app.log', '한 줄 더\n')

// 중간 디렉터리까지 만들기. 이미 있어도 오류가 아니다
await mkdir('data/2026/09', { recursive: true })

// 재귀 삭제. force는 없는 경로를 무시한다 (rm -rf와 같다)
await rm('build', { recursive: true, force: true })

// 복사. COPYFILE_EXCL을 주면 대상이 이미 있을 때 실패한다
await copyFile('a.txt', 'b.txt', constants.COPYFILE_EXCL)
```

취소는 `AbortSignal`로 한다. 특히 대용량 파일 읽기에 타임아웃을 거는 데 유용하다.

```js
try {
  const data = await readFile('huge.bin', { signal: AbortSignal.timeout(3000) })
} catch (err) {
  if (err.name === 'AbortError' || err.name === 'TimeoutError') {
    console.error('3초 안에 읽지 못했다')
  } else throw err
}
```

### 실무 함정

- **`writeFile`은 원자적이지 않다.** 큰 데이터를 쓰다가 프로세스가 죽으면 잘린 파일이 남는다. 8.8절의 원자적 교체 패턴을 써야 한다.
- **`appendFile`을 동시성 있게 호출하면 순서가 보장되지 않는다.** 매 호출이 파일을 열고 쓰고 닫는다. 로그처럼 잦은 추가 쓰기는 `createWriteStream(path, { flags: 'a' })`로 핸들 하나를 유지하는 편이 훨씬 빠르고 안전하다.
- **`rm`의 `force: true`는 존재하지 않는 경로의 오류만 무시한다.** 권한 오류는 그대로 던진다. `force`를 붙였으니 안전하다고 착각하지 마라.
- **스레드 풀 크기는 기본 4다.** 동시에 여러 대용량 파일을 읽으면 5번째 작업부터 큐에서 대기한다. `UV_THREADPOOL_SIZE` 환경 변수로 늘릴 수 있지만(최대 1024), CPU 코어 수를 크게 넘기면 컨텍스트 스위칭 비용이 늘어난다. 크립토와 DNS 조회도 같은 풀을 쓴다는 점을 기억해야 한다(11장 참조).
- **에러 코드로 분기하라.** 메시지 문자열이 아니라 `err.code`를 본다. `ENOENT`(없음), `EACCES`(권한), `EISDIR`(디렉터리), `ENOTDIR`, `EMFILE`(파일 디스크립터 고갈), `ENOSPC`(디스크 가득)가 자주 만나는 값이다.

## 8.3 파일 열기·읽기·쓰기의 세 가지 방식

### 왜 필요한가

"파일을 읽는다"는 한 문장 뒤에는 완전히 다른 성능 특성을 가진 세 가지 전략이 있다. 전체를 메모리에 올리는 방식, 필요한 구간만 읽는 방식, 그리고 조각 단위로 흘려보내는 방식이다. 파일 크기와 접근 패턴에 따라 답이 달라지는데, 실무에서는 "일단 `readFile`"로 시작했다가 사용자가 500MB 파일을 올리는 순간 프로세스가 OOM으로 죽는 사고가 반복된다.

### 어떻게 동작하는가

**첫째, 전체 읽기 (`readFile`).** 파일 전체를 하나의 `Buffer`나 문자열로 만든다. 코드가 가장 짧고, 파싱 라이브러리(JSON, YAML, 이미지 디코더)가 통짜 버퍼를 요구하는 경우에 적합하다. 대가는 메모리다. 100MB 파일을 `utf8`로 읽으면 디코딩 과정에서 순간적으로 원본 버퍼와 문자열이 함께 존재해 200MB 이상을 쓴다. 동시 요청 10건이면 2GB다.

```js
import { readFile } from 'node:fs/promises'

const config = JSON.parse(await readFile('config.json', 'utf8'))
```

한계도 명확하다. `Buffer`는 약 4GiB(`buffer.constants.MAX_LENGTH`), 문자열은 약 512MiB(`MAX_STRING_LENGTH`)를 넘을 수 없다(7장 참조). 이 선을 넘으면 `ERR_FS_FILE_TOO_LARGE`나 문자열 길이 오류가 난다.

**둘째, 부분 읽기 (`FileHandle.read`).** 파일을 열어 핸들을 유지하고, 원하는 오프셋에서 원하는 바이트 수만 읽는다. 헤더 몇 바이트로 파일 형식을 판별하거나, 고정 길이 레코드 파일에 무작위 접근할 때 최적이다.

```js
import { open } from 'node:fs/promises'

// PNG 매직 넘버 검사 — 8바이트만 읽으면 충분하다
const PNG_MAGIC = Buffer.from([0x89, 0x50, 0x4e, 0x47, 0x0d, 0x0a, 0x1a, 0x0a])

async function isPng(filePath) {
  const fh = await open(filePath, 'r')
  try {
    const buf = Buffer.alloc(8)
    const { bytesRead } = await fh.read(buf, 0, 8, 0)  // position 0에서 8바이트
    return bytesRead === 8 && buf.equals(PNG_MAGIC)
  } finally {
    await fh.close()   // 반드시 닫는다. 누락하면 EMFILE로 죽는다
  }
}
```

`FileHandle`은 `read`, `write`, `stat`, `truncate`, `sync`, `createReadStream`, `readableWebStream` 등을 메서드로 갖는다. 핸들 하나로 여러 번 읽고 쓸 수 있어, 같은 파일에 반복 접근할 때 `open` 시스템 콜 비용을 아낀다.

**셋째, 스트림 (`createReadStream`).** 파일을 청크 단위(기본 64KiB)로 읽어 흘려보낸다. 메모리 사용량이 파일 크기와 무관하게 일정하고, 첫 바이트를 즉시 처리할 수 있으며, 압축·암호화·변환 단계를 파이프로 조립할 수 있다.

```js
import { createReadStream, createWriteStream } from 'node:fs'
import { pipeline } from 'node:stream/promises'
import { createGzip } from 'node:zlib'

await pipeline(
  createReadStream('access.log'),
  createGzip(),
  createWriteStream('access.log.gz')
)
```

세 방식을 파일 크기별로 비교하면 선택 기준이 뚜렷해진다. 아래는 일반적인 x86-64 리눅스 서버(NVMe SSD, Node 20)에서 관측되는 대략적인 수치다.

| 파일 크기 | `readFile` 최대 RSS | 스트림 최대 RSS | 권장 |
|---|---|---|---|
| 10KB | ~40MB (기저값) | ~40MB | `readFile` — 스트림 설정 비용이 더 크다 |
| 1MB | ~42MB | ~40MB | `readFile` |
| 50MB | ~95MB | ~41MB | 상황에 따라. 동시 요청이 있으면 스트림 |
| 500MB | ~550MB+ | ~41MB | 스트림 필수 |
| 5GB | 실패 (`ERR_FS_FILE_TOO_LARGE`) | ~41MB | 스트림 외 방법 없음 |

경험칙은 이렇다. **10MB 미만이고 동시성이 낮으면 `readFile`, 그 이상이거나 크기를 예측할 수 없으면 스트림, 파일의 특정 구간만 필요하면 `FileHandle.read`.** 사용자가 올린 파일처럼 크기를 통제할 수 없는 입력은 예외 없이 스트림으로 다룬다.

**한 줄씩 읽기.** 로그나 CSV처럼 줄 단위 텍스트를 처리할 때 직접 청크를 잘라 개행을 찾는 코드를 짜면 멀티바이트 문자가 청크 경계에 걸리는 버그가 반드시 생긴다. `node:readline`이 이 문제를 해결해 준다.

```js
import { createReadStream } from 'node:fs'
import { createInterface } from 'node:readline/promises'

const rl = createInterface({
  input: createReadStream('access.log', { encoding: 'utf8' }),
  crlfDelay: Infinity   // \r\n을 하나의 줄바꿈으로 취급 (윈도우 파일 대응)
})

let errors = 0
for await (const line of rl) {
  if (line.includes(' 500 ')) errors++
}
console.log(`5xx 응답 ${errors}건`)
```

`for await`는 백프레셔를 자동으로 지킨다. 루프 본문에서 `await`로 느린 작업을 하면 그동안 파일 읽기가 자연히 멈춘다.

### 실무 함정

- **`FileHandle`을 닫지 않으면 `EMFILE`이 난다.** 반드시 `try/finally`로 감싼다. Node 20+에는 `FileHandle`에 `Symbol.asyncDispose`가 구현되어 있어, 명시적 자원 관리 문법을 쓸 수 있는 환경이라면 `await using fh = await open(...)`으로 자동 정리가 가능하다.
- **`fh.read()`의 `bytesRead`를 확인하지 않으면 파일 끝에서 쓰레기 데이터를 읽는다.** 버퍼는 재사용되므로 이전 내용이 남아 있다.
- **`createReadStream`의 `start`/`end` 옵션은 양끝을 포함한다.** HTTP `Range` 헤더와 규칙이 같아 8.6절에서 그대로 쓴다.
- **`readFile`에 인코딩을 주지 않으면 `Buffer`가 온다.** JSON 파싱에는 `Buffer`도 동작하지만(V8이 내부에서 변환한다), 명시적으로 `'utf8'`을 주는 편이 의도가 분명하다.

## 8.4 디렉터리 순회와 `opendir`, 재귀 탐색

### 왜 필요한가

빌드 도구, 정적 사이트 생성기, 파일 인덱서, 백업 스크립트는 모두 디렉터리를 훑는다. 작은 프로젝트에서는 `readdir`로 배열을 받아 반복하면 그만이지만, `node_modules`처럼 수십만 개 엔트리를 가진 트리나 사용자 데이터가 무한정 쌓이는 디렉터리에서는 "목록 전체를 배열로 만든다"는 전제 자체가 메모리 폭탄이 된다. 게다가 순진한 재귀 탐색은 심볼릭 링크 순환에 빠져 영원히 돌거나 스택을 넘긴다.

### 어떻게 동작하는가

`readdir`은 기본적으로 파일명 문자열 배열을 준다. 각 엔트리가 파일인지 디렉터리인지 알려면 다시 `stat`을 호출해야 하는데, 엔트리 하나당 시스템 콜이 하나씩 더 붙는다. `withFileTypes: true`를 주면 `Dirent` 객체가 오고, 대부분의 파일 시스템에서는 디렉터리를 읽을 때 타입 정보가 함께 오므로 추가 `stat` 없이 판별할 수 있다.

```js
import { readdir } from 'node:fs/promises'

const entries = await readdir('./src', { withFileTypes: true })
for (const e of entries) {
  console.log(e.name, e.isDirectory() ? 'dir' : e.isSymbolicLink() ? 'link' : 'file')
  console.log(e.parentPath)   // Node 20.12+ — 엔트리가 속한 디렉터리 경로
}
```

Node 20.1부터는 `recursive: true`도 지원한다. 반환되는 이름은 기준 디렉터리로부터의 **상대 경로**다.

```js
// 상대 경로 문자열 배열: ['index.js', 'lib/util.js', 'lib/deep/a.js', ...]
const all = await readdir('./src', { recursive: true })

// Dirent와 함께 쓰면 name은 파일명만, parentPath에 디렉터리가 담긴다
import path from 'node:path'
const dirents = await readdir('./src', { recursive: true, withFileTypes: true })
const files = dirents
  .filter((d) => d.isFile())
  .map((d) => path.join(d.parentPath, d.name))
```

편리하지만 결과를 **배열로 전부 모은다**는 점이 문제다. 10만 개 파일이면 10만 개의 `Dirent` 객체가 동시에 메모리에 존재한다. 그리고 순회가 끝날 때까지 첫 결과도 얻지 못한다.

대용량 디렉터리에는 `opendir`을 쓴다. `Dir` 객체는 비동기 이터러블이라 `for await`로 한 엔트리씩 꺼낼 수 있고, 내부적으로는 `bufferSize`(기본 32) 만큼만 미리 읽어 둔다. 메모리 사용량이 디렉터리 크기와 무관하게 일정하다.

```js
import { opendir } from 'node:fs/promises'
import path from 'node:path'

// 심볼릭 링크 순환에 빠지지 않는 안전한 재귀 탐색기
async function* walk(dir, { followSymlinks = false, seen = new Set() } = {}) {
  const handle = await opendir(dir, { bufferSize: 64 })
  try {
    for await (const entry of handle) {
      const full = path.join(dir, entry.name)

      if (entry.isDirectory()) {
        yield* walk(full, { followSymlinks, seen })
      } else if (entry.isSymbolicLink() && followSymlinks) {
        // 링크를 따라갈 때만 실제 대상을 확인하고, 이미 본 경로면 건너뛴다
        const { realpath, stat } = await import('node:fs/promises')
        const real = await realpath(full)
        if (seen.has(real)) continue
        seen.add(real)
        const st = await stat(real)
        if (st.isDirectory()) yield* walk(real, { followSymlinks, seen })
        else yield real
      } else if (entry.isFile()) {
        yield full
      }
    }
  } finally {
    // for await가 정상 종료되면 Dir은 자동으로 닫히지만,
    // 소비자가 중간에 break하면 닫히지 않으므로 명시적으로 정리한다
    await handle.close().catch(() => {})
  }
}

for await (const file of walk('./src')) {
  console.log(file)
}
```

제너레이터로 만들면 소비자가 원하는 만큼만 꺼내 쓸 수 있다. "첫 번째로 발견되는 `package.json`을 찾아라" 같은 작업에서 `break`로 즉시 중단하면 나머지 트리는 아예 읽지 않는다.

깊이 제한과 무시 목록은 실무에서 거의 필수다. `node_modules`, `.git`, `dist`를 건너뛰지 않으면 탐색 시간이 수십 배로 늘어난다.

```js
const IGNORED = new Set(['node_modules', '.git', 'dist', 'coverage'])

async function* walkFiltered(dir, depth = 0, maxDepth = 10) {
  if (depth > maxDepth) return
  const handle = await opendir(dir)
  try {
    for await (const entry of handle) {
      if (IGNORED.has(entry.name)) continue
      const full = path.join(dir, entry.name)
      if (entry.isDirectory()) yield* walkFiltered(full, depth + 1, maxDepth)
      else if (entry.isFile()) yield full
    }
  } finally {
    await handle.close().catch(() => {})
  }
}
```

**glob 패턴.** Node 22부터 `node:fs/promises`에 `glob`이 내장되어 외부 의존성 없이 패턴 매칭 탐색이 가능하다. Node 20에서는 `glob` 또는 `fast-glob` 패키지를 쓴다.

```js
// Node 22+
import { glob } from 'node:fs/promises'

for await (const file of glob('src/**/*.{js,mjs}', { exclude: ['**/node_modules/**'] })) {
  console.log(file)
}
```

`*`는 구분자를 제외한 임의 문자열, `**`는 구분자를 포함한 임의 깊이, `?`는 한 글자, `{a,b}`는 대안을 뜻한다. 주의할 점은 glob 패턴이 언제나 `/`를 구분자로 쓴다는 것이다. 윈도우에서도 패턴에는 `\`를 넣지 않는다.

### 실무 함정

- **`readdir`은 순서를 보장하지 않는다.** 파일 시스템이 주는 순서 그대로다. 재현 가능한 빌드 산출물이 필요하면 직접 정렬한다. `entries.sort((a, b) => a.name.localeCompare(b.name))`처럼 로케일 의존 비교를 쓰면 환경에 따라 결과가 달라지므로, 결정론이 중요하면 `a.name < b.name` 같은 코드 포인트 비교를 쓴다.
- **`Dirent.isDirectory()`는 심볼릭 링크에 대해 `false`다.** `readdir`은 `lstat` 의미론을 따른다. 링크가 가리키는 대상이 디렉터리인지 알려면 별도로 `stat`을 호출해야 한다.
- **`for await`를 `break`로 빠져나오면 `Dir`이 열린 채 남을 수 있다.** 반드시 `finally`에서 `close()`를 부른다.
- **네트워크 파일 시스템에서 재귀 탐색은 재앙이다.** NFS나 SMB 마운트에서 엔트리 하나당 왕복 지연이 수 밀리초 붙는다. 10만 개면 수 분이다. 이런 환경에서는 탐색 결과를 캐시하고 변경 감시로 갱신하는 구조를 택한다.
- **`recursive: true`는 심볼릭 링크를 따라가지 않는다.** 링크된 디렉터리 내용이 필요하면 직접 순회를 구현해야 한다.

## 8.5 파일 변경 감시: `fs.watch`의 함정

### 왜 필요한가

개발 서버의 핫 리로드, 설정 파일 자동 반영, 로그 수집기의 tail 동작은 모두 "파일이 바뀌면 알려 달라"를 필요로 한다. Node.js는 `fs.watch`와 `fs.watchFile` 두 가지를 제공하는데, 문서만 보면 간단해 보이지만 실제로 써 보면 이벤트가 두 번씩 오고, 파일명이 `null`로 오고, macOS와 리눅스가 다르게 동작하고, 에디터로 저장하면 `rename`이 오는 등 온갖 이상 현상을 만난다. 이 절은 그 이유를 설명하고 실무에서 통하는 대응을 제시한다.

### 어떻게 동작하는가

`fs.watch`는 운영체제의 네이티브 알림 메커니즘을 그대로 노출한다. 리눅스는 **inotify**, macOS는 **FSEvents**(또는 kqueue), 윈도우는 **ReadDirectoryChangesW**를 쓴다. 성능은 뛰어나지만 — 폴링이 없으므로 CPU를 거의 쓰지 않는다 — 세 메커니즘의 의미론이 서로 달라 이식성이 떨어진다.

```js
import { watch } from 'node:fs'

const watcher = watch('./config', { recursive: true }, (eventType, filename) => {
  // eventType: 'rename' 또는 'change' — 이 둘뿐이다
  // filename: 플랫폼에 따라 null일 수 있다
  console.log(eventType, filename)
})

// 정리
process.on('SIGINT', () => watcher.close())
```

플랫폼별 비일관성은 다음과 같다.

**중복 이벤트.** 텍스트 에디터가 파일을 저장하는 방식은 대개 "임시 파일에 쓰고 → rename으로 교체"다(8.8절의 원자적 쓰기와 같은 패턴이다). 그 결과 하나의 저장에 대해 `rename`, `change`, 또 `change`가 연달아 발생한다. Vim은 백업 파일까지 만들어 이벤트가 4~5개 나온다. 반면 `echo x > file` 같은 단순 덮어쓰기는 `change` 하나만 낸다.

**`rename`만 오는 경우.** 파일이 rename으로 교체되면 원래의 inode를 감시하던 watcher는 새 파일을 못 본다. 이후 변경에 대해 아무 이벤트도 오지 않는다. 감시 대상이 사라진 것이다. 그래서 개별 파일이 아니라 **부모 디렉터리를 감시**하는 것이 실무의 정석이다.

**`recursive` 옵션의 제약.** macOS와 윈도우에서는 오래전부터 지원됐지만, 리눅스에서는 Node 20부터 지원된다. 그것도 네이티브 재귀가 아니라 Node가 하위 디렉터리마다 inotify watch를 거는 방식이라, 디렉터리가 많으면 `inotify.max_user_watches` 한계(기본 8192 또는 65536)에 부딪혀 `ENOSPC`가 난다. `node_modules`를 재귀 감시하려다 이 오류를 만나는 것이 전형적이다.

**`filename`이 `null`.** 일부 플랫폼과 상황에서 어떤 파일이 바뀌었는지 알려주지 않는다. 이 경우 전체를 다시 스캔하는 것 말고는 방법이 없다.

`fs.watchFile`은 완전히 다른 방식이다. 네이티브 알림 대신 주기적으로 `stat`을 호출해 이전 결과와 비교한다. 즉 **폴링(polling)** 이다.

```js
import { watchFile, unwatchFile } from 'node:fs'

watchFile('./config.json', { interval: 1000 }, (curr, prev) => {
  if (curr.mtimeMs !== prev.mtimeMs) console.log('변경됨')
  if (curr.ino === 0) console.log('삭제됨')   // 파일이 사라지면 빈 Stats가 온다
})

unwatchFile('./config.json')
```

장점은 플랫폼 독립적이고 rename 교체에도 계속 동작한다는 것이다. 단점은 비용이다. 감시 대상 하나당 `interval`마다 시스템 콜이 하나씩 발생한다. 파일 1,000개를 1초 간격으로 감시하면 초당 1,000회의 `stat`이다. 로컬 디스크에서는 견딜 만하지만 NFS에서는 네트워크 왕복 1,000회다. 게다가 최대 `interval` 만큼 감지가 늦는다. 결론적으로 `watchFile`은 **감시 대상이 몇 개뿐이고 `fs.watch`가 신뢰할 수 없는 환경(NFS, 도커 볼륨 마운트)** 에서만 쓴다.

실무에서 `chokidar` 같은 라이브러리를 쓰는 이유가 여기 있다. chokidar는 기본적으로 `fs.watch`를 쓰되, 플랫폼별 차이를 흡수하고, 중복 이벤트를 정규화하며, `add`/`change`/`unlink`/`addDir`/`unlinkDir`처럼 의미 있는 이벤트로 변환하고, 필요하면 폴링으로 자동 전환하며, `awaitWriteFinish` 옵션으로 "쓰기가 끝난 뒤에" 알려 준다. 이 마지막 기능이 특히 중요하다. 대용량 파일을 복사 중일 때 `fs.watch`는 쓰기 도중에도 이벤트를 내므로, 그 시점에 파일을 읽으면 잘린 내용을 읽게 된다.

직접 `fs.watch`를 쓴다면 최소한 **디바운스(debounce)** 는 반드시 구현해야 한다. 아래는 파일 경로별로 독립적인 타이머를 두고, 마지막 이벤트로부터 일정 시간이 지난 뒤 한 번만 콜백을 호출하는 구현이다.

```js
import { watch } from 'node:fs'
import { stat } from 'node:fs/promises'
import path from 'node:path'

/**
 * 디렉터리를 감시하며 경로별로 디바운스된 변경 알림을 보낸다.
 * 파일 크기가 안정될 때까지 기다려 쓰기 도중 읽는 사고를 막는다.
 */
function watchDebounced(dir, onChange, { delay = 100, settleChecks = 2 } = {}) {
  const timers = new Map()

  const watcher = watch(dir, { recursive: true }, (eventType, filename) => {
    if (!filename) return                       // 어떤 파일인지 모르면 무시
    const full = path.join(dir, filename)

    clearTimeout(timers.get(full))              // 이전 타이머 취소 — 마지막 이벤트만 살아남는다
    timers.set(full, setTimeout(async () => {
      timers.delete(full)

      // 크기가 연속으로 같아질 때까지 기다린다 (쓰기 완료 대기)
      let prevSize = -1
      for (let i = 0; i < settleChecks; i++) {
        let size
        try {
          size = (await stat(full)).size
        } catch (err) {
          if (err.code === 'ENOENT') return onChange('unlink', full)
          throw err
        }
        if (size === prevSize) break
        prevSize = size
        await new Promise((r) => setTimeout(r, delay))
      }

      onChange(eventType === 'rename' ? 'rename' : 'change', full)
    }, delay))
  })

  return () => {
    for (const t of timers.values()) clearTimeout(t)
    timers.clear()
    watcher.close()
  }
}

const stop = watchDebounced('./src', (type, file) => {
  console.log(`[${type}] ${file}`)
})

process.on('SIGINT', () => { stop(); process.exit(0) })
```

`delay` 값은 트레이드오프다. 너무 짧으면 중복 이벤트가 그대로 새어 나오고, 너무 길면 반응이 굼뜨다. 개발 서버 리로드에는 50~150ms가 보통이고, 대용량 파일이 오가는 감시에는 500ms 이상을 준다.

### 실무 함정

- **watcher를 `close()`하지 않으면 프로세스가 종료되지 않는다.** `fs.watch`는 이벤트 루프를 붙잡는 핸들이다. 테스트 러너가 끝나지 않는 원인 1순위다. `watcher.unref()`로 붙잡지 않게 만들 수도 있다.
- **도커 컨테이너에서 호스트 볼륨을 감시하면 이벤트가 아예 오지 않는 경우가 있다.** macOS/윈도우의 도커 데스크톱은 파일 공유 계층에서 inotify 이벤트를 전달하지 못한다. 이 환경에서는 폴링(`chokidar`의 `usePolling: true`)이 유일한 답이다.
- **`ENOSPC`는 디스크가 아니라 inotify watch 한계다.** 메시지가 오해를 부른다. `cat /proc/sys/fs/inotify/max_user_watches`로 확인하고, 감시 범위를 좁히거나 커널 파라미터를 올린다.
- **감시 대상 디렉터리가 삭제되면 watcher는 조용히 죽는다.** `error` 이벤트를 반드시 구독하고, 필요하면 부모 디렉터리를 감시해 재생성을 감지한다.
- **감시 콜백에서 같은 디렉터리에 파일을 쓰면 무한 루프가 된다.** 빌드 산출물을 소스와 같은 트리에 쓸 때 흔히 발생한다. 출력 경로를 감시 대상에서 제외한다.

## 8.6 정적 파일 서빙과 캐싱 헤더

### 왜 필요한가

정적 파일 서빙은 "파일을 읽어 응답으로 흘려보낸다"는 한 줄로 요약되지만, 그 한 줄을 직접 구현하면 세 가지가 빠진다. 캐싱 헤더가 없어 같은 파일을 매번 전송하고, `Range` 요청을 무시해 동영상 탐색이 안 되며, 무엇보다 **경로 탐색(path traversal) 공격**에 그대로 뚫린다. 프레임워크의 정적 미들웨어가 이 셋을 해 주지만, 무엇을 해 주는지 모르면 커스텀 다운로드 엔드포인트를 만들 때 그대로 구멍을 낸다.

### 어떻게 동작하는가

**경로 탐색 방어가 최우선이다.** 공격자는 `GET /static/../../etc/passwd`를 보낸다. 앞서 봤듯 `path.join`은 `..`를 실제로 적용하므로, 기준 디렉터리 밖으로 나가는 것을 막지 못한다. 유일하게 신뢰할 수 있는 방법은 **`resolve`로 절대 경로를 만든 뒤, 그것이 허용된 루트로 시작하는지 검사**하는 것이다.

```js
import path from 'node:path'

const ROOT = path.resolve('./public')

function safeResolve(root, userPath) {
  // 1. URL 디코딩. %2e%2e%2f 같은 인코딩된 ..를 먼저 푼다
  let decoded
  try {
    decoded = decodeURIComponent(userPath)
  } catch {
    return null   // 잘못된 퍼센트 인코딩은 거부
  }

  // 2. NUL 바이트 차단. 일부 하위 계층에서 문자열을 잘라 버린다
  if (decoded.includes('\0')) return null

  // 3. 절대 경로로 만든다. 이 시점에 ..가 모두 적용된다
  const target = path.resolve(root, '.' + path.posix.normalize('/' + decoded))

  // 4. 접두사 검사. 구분자까지 포함해야 /public-secret 같은 형제 경로를 막는다
  if (target !== root && !target.startsWith(root + path.sep)) return null

  return target
}

safeResolve(ROOT, '/css/app.css')          // '<...>/public/css/app.css'
safeResolve(ROOT, '/../../etc/passwd')     // null
safeResolve(ROOT, '/%2e%2e%2fsecret')      // null
```

3단계의 `'.' + normalize('/' + decoded)` 관용구가 핵심이다. 사용자 입력 앞에 `/`를 붙여 정규화하면 `..`가 루트를 넘어 올라가지 못하고 소멸한다. 그 결과 앞에 `.`을 붙여 상대 경로로 만들면 `resolve`가 루트를 덮어쓸 수 없다.

이것으로 끝이 아니다. 심볼릭 링크가 루트 밖을 가리키면 접두사 검사를 통과한 경로가 실제로는 외부 파일일 수 있다. 사용자가 파일을 올릴 수 있는 디렉터리를 서빙한다면 `realpath`로 한 번 더 검사한다.

```js
import { realpath } from 'node:fs/promises'

async function safeResolveStrict(root, userPath) {
  const target = safeResolve(root, userPath)
  if (!target) return null
  try {
    const real = await realpath(target)
    if (real !== root && !real.startsWith(root + path.sep)) return null
    return real
  } catch (err) {
    if (err.code === 'ENOENT') return null
    throw err
  }
}
```

**캐싱 헤더.** 브라우저에 "이 응답을 얼마나 재사용해도 되는지"를 알려 준다. 두 축이 있다. `Cache-Control`은 유효 기간을 정하고, `ETag`/`Last-Modified`는 만료 후 "바뀌었는지만" 물어보는 조건부 요청(conditional request)을 가능하게 한다. 조건부 요청에서 서버가 `304 Not Modified`를 돌려주면 본문 전송이 통째로 생략된다.

`ETag`는 파일 내용의 지문이다. 해시를 쓰면 정확하지만 파일을 읽어야 하므로 비싸다. 정적 파일에는 `Stats`의 크기와 mtime을 조합한 약한(weak) ETag가 사실상 표준이다.

```js
function makeETag(stats) {
  // W/"크기-수정시각" — 내용이 아니라 메타데이터 기반이므로 weak
  return `W/"${stats.size.toString(16)}-${stats.mtimeMs.toString(16)}"`
}

function cacheControlFor(filePath) {
  // 파일명에 콘텐츠 해시가 박힌 자산은 영원히 캐시해도 안전하다
  if (/\.[0-9a-f]{8,}\.(js|css|woff2?|png|jpg|svg)$/.test(filePath)) {
    return 'public, max-age=31536000, immutable'
  }
  // HTML은 항상 재검증. 배포가 즉시 반영돼야 한다
  if (filePath.endsWith('.html')) return 'no-cache'
  return 'public, max-age=3600'
}
```

`immutable`은 "유효 기간 안에는 사용자가 새로고침해도 재검증하지 마라"는 뜻이다. 콘텐츠 해시가 파일명에 들어간 번들에만 붙인다. `no-cache`는 "캐시하되 쓸 때마다 반드시 재검증하라"이지 "캐시하지 마라"가 아니다. 후자는 `no-store`다.

**`Range` 요청.** 동영상 탐색, 이어받기, 큰 파일의 부분 다운로드에 쓰인다. 클라이언트가 `Range: bytes=1000-1999`를 보내면 서버는 `206 Partial Content`와 `Content-Range: bytes 1000-1999/5000`으로 답한다. `createReadStream`의 `start`/`end`가 정확히 이 의미론이라 그대로 넘기면 된다.

아래는 지금까지의 요소를 모두 담은 정적 서빙 핸들러다.

```js
import http from 'node:http'
import path from 'node:path'
import { stat } from 'node:fs/promises'
import { createReadStream } from 'node:fs'
import { pipeline } from 'node:stream/promises'

const ROOT = path.resolve('./public')

const MIME = {
  '.html': 'text/html; charset=utf-8',
  '.css': 'text/css; charset=utf-8',
  '.js': 'text/javascript; charset=utf-8',
  '.json': 'application/json; charset=utf-8',
  '.png': 'image/png',
  '.mp4': 'video/mp4',
  '.woff2': 'font/woff2'
}

function parseRange(header, size) {
  const m = /^bytes=(\d*)-(\d*)$/.exec(header ?? '')
  if (!m) return null
  const [, s, e] = m
  let start, end
  if (s === '') {                       // 'bytes=-500' — 마지막 500바이트
    if (e === '') return null
    start = Math.max(0, size - Number(e))
    end = size - 1
  } else {
    start = Number(s)
    end = e === '' ? size - 1 : Math.min(Number(e), size - 1)
  }
  if (!Number.isFinite(start) || !Number.isFinite(end) || start > end || start >= size) return null
  return { start, end }
}

const server = http.createServer(async (req, res) => {
  try {
    if (req.method !== 'GET' && req.method !== 'HEAD') {
      res.writeHead(405, { Allow: 'GET, HEAD' }).end()
      return
    }

    const urlPath = new URL(req.url, 'http://localhost').pathname
    const filePath = safeResolve(ROOT, urlPath)
    if (!filePath) { res.writeHead(403).end('Forbidden'); return }

    let st
    try {
      st = await stat(filePath)
    } catch (err) {
      if (err.code === 'ENOENT' || err.code === 'ENOTDIR') {
        res.writeHead(404).end('Not Found'); return
      }
      throw err
    }
    if (st.isDirectory()) { res.writeHead(404).end('Not Found'); return }

    const etag = makeETag(st)
    const lastModified = st.mtime.toUTCString()

    const baseHeaders = {
      'Content-Type': MIME[path.extname(filePath).toLowerCase()] ?? 'application/octet-stream',
      'Cache-Control': cacheControlFor(filePath),
      'ETag': etag,
      'Last-Modified': lastModified,
      'Accept-Ranges': 'bytes',
      'X-Content-Type-Options': 'nosniff'   // MIME 스니핑으로 인한 XSS 차단
    }

    // 조건부 요청 처리. If-None-Match가 If-Modified-Since보다 우선한다
    const inm = req.headers['if-none-match']
    if (inm && inm.split(',').some((t) => t.trim() === etag)) {
      res.writeHead(304, { ETag: etag, 'Cache-Control': baseHeaders['Cache-Control'] }).end()
      return
    }
    const ims = req.headers['if-modified-since']
    if (!inm && ims && Date.parse(ims) >= Math.floor(st.mtimeMs / 1000) * 1000) {
      res.writeHead(304, baseHeaders).end()
      return
    }

    const range = req.headers.range ? parseRange(req.headers.range, st.size) : null
    if (req.headers.range && !range) {
      res.writeHead(416, { 'Content-Range': `bytes */${st.size}` }).end()
      return
    }

    if (range) {
      res.writeHead(206, {
        ...baseHeaders,
        'Content-Range': `bytes ${range.start}-${range.end}/${st.size}`,
        'Content-Length': range.end - range.start + 1
      })
    } else {
      res.writeHead(200, { ...baseHeaders, 'Content-Length': st.size })
    }

    if (req.method === 'HEAD') { res.end(); return }

    // pipeline은 클라이언트가 끊으면 읽기 스트림도 정리해 준다 (7장 참조)
    await pipeline(createReadStream(filePath, range ?? {}), res)
  } catch (err) {
    if (err.code === 'ERR_STREAM_PREMATURE_CLOSE') return   // 클라이언트가 끊음. 정상
    console.error(err)
    if (!res.headersSent) res.writeHead(500).end('Internal Server Error')
    else res.destroy()
  }
})

server.listen(3000)
```

### 실무 함정

- **`Content-Type`을 확장자로만 결정하면 위험하다.** 사용자가 업로드한 파일을 서빙할 때 `.html`을 그대로 내보내면 저장형 XSS가 된다. 업로드 파일은 항상 `application/octet-stream`과 `Content-Disposition: attachment`로 내보내거나, 별도 도메인에서 서빙한다.
- **`Last-Modified`는 초 단위 해상도다.** `Date.parse(ims)`와 `mtimeMs`를 그대로 비교하면 밀리초 부분 때문에 항상 불일치한다. 위 코드처럼 초 단위로 내려 맞춘다.
- **`Content-Length`를 쓰고 나서 스트림 오류가 나면 응답이 잘린 채 끝난다.** 헤더를 이미 보냈으므로 500을 보낼 수 없다. `res.destroy()`로 연결을 끊어 클라이언트가 불완전 응답임을 알게 한다.
- **디렉터리 인덱싱을 기본으로 켜지 마라.** 파일 목록 노출은 정보 유출이다.
- **프로덕션에서는 정적 파일을 Node가 직접 서빙하지 않는 편이 낫다.** nginx나 CDN이 `sendfile(2)`로 커널 공간에서 바로 전송하므로 훨씬 빠르다. Node의 정적 서빙은 개발 환경과 소규모 배포용으로 본다.

## 8.7 파일 업로드 처리

### 왜 필요한가

파일 업로드는 서버가 통제할 수 없는 크기의 데이터를 받는 거의 유일한 경로다. 그래서 메모리 고갈, 디스크 고갈, 악성 파일 저장이라는 세 가지 위험이 한꺼번에 걸린다. `req`를 통째로 버퍼에 모으는 코드는 100MB 파일 열 개가 동시에 오면 1GB를 쓰고 죽는다. 업로드는 처음부터 끝까지 스트리밍으로 다뤄야 한다.

### 어떻게 동작하는가

브라우저의 `multipart/form-data`는 요청 본문을 경계 문자열(boundary)로 구분된 파트들로 나눈다. 각 파트는 자체 헤더(`Content-Disposition`, `Content-Type`)와 본문을 갖는다. 이 형식을 직접 파싱하는 것은 가능하지만 경계가 청크 사이에 걸치는 경우 등 까다로운 부분이 많아, 검증된 라이브러리를 쓰는 편이 옳다. `busboy`는 스트리밍 파서로 널리 쓰이며, 파일 파트를 **스트림으로** 넘겨 주므로 디스크로 바로 흘려보낼 수 있다.

```js
import http from 'node:http'
import path from 'node:path'
import crypto from 'node:crypto'
import { createWriteStream } from 'node:fs'
import { mkdir, rm } from 'node:fs/promises'
import { pipeline } from 'node:stream/promises'
import Busboy from 'busboy'

const UPLOAD_DIR = path.resolve('./uploads')
const MAX_FILE_BYTES = 20 * 1024 * 1024   // 파일 하나당 20MB
const MAX_FILES = 5
const ALLOWED = new Set(['image/png', 'image/jpeg', 'application/pdf'])

await mkdir(UPLOAD_DIR, { recursive: true })

function handleUpload(req, res) {
  const bb = Busboy({
    headers: req.headers,
    limits: {
      fileSize: MAX_FILE_BYTES,
      files: MAX_FILES,
      fields: 20,
      fieldSize: 64 * 1024
    }
  })

  const saved = []
  const fields = {}
  let aborted = false

  const fail = (status, message) => {
    if (aborted) return
    aborted = true
    // 이미 저장된 부분 파일들을 정리한다
    Promise.all(saved.map((p) => rm(p, { force: true }))).catch(() => {})
    req.unpipe(bb)
    req.resume()                            // 남은 본문을 버려 소켓을 재사용 가능하게 한다
    if (!res.headersSent) res.writeHead(status, { 'Content-Type': 'text/plain' })
    res.end(message)
  }

  bb.on('field', (name, value) => { fields[name] = value })

  bb.on('file', (name, stream, info) => {
    const { filename, mimeType } = info

    if (!ALLOWED.has(mimeType)) {
      stream.resume()                       // 이 파트는 버리고 계속 읽는다
      return fail(415, `허용되지 않는 타입: ${mimeType}`)
    }

    // 사용자 파일명을 절대 그대로 쓰지 않는다. 확장자만 취하고 이름은 서버가 만든다
    const ext = path.extname(filename).toLowerCase().slice(0, 10)
    const dest = path.join(UPLOAD_DIR, `${crypto.randomUUID()}${ext}`)
    saved.push(dest)

    // limits.fileSize를 넘으면 busboy가 이 이벤트를 낸다
    stream.on('limit', () => fail(413, '파일이 너무 큽니다'))

    pipeline(stream, createWriteStream(dest)).catch((err) => {
      if (!aborted) fail(500, '저장 실패')
      else console.error(err)
    })
  })

  bb.on('filesLimit', () => fail(413, `파일은 최대 ${MAX_FILES}개까지 가능합니다`))
  bb.on('error', (err) => fail(400, `잘못된 요청 본문: ${err.message}`))

  bb.on('close', () => {
    if (aborted) return
    res.writeHead(201, { 'Content-Type': 'application/json' })
    res.end(JSON.stringify({ files: saved.map((p) => path.basename(p)), fields }))
  })

  req.pipe(bb)
}

http.createServer((req, res) => {
  if (req.method === 'POST' && req.url === '/upload') return handleUpload(req, res)
  res.writeHead(404).end()
}).listen(3000)
```

**조기 중단이 핵심이다.** 20MB 제한을 걸어 놓고도 100MB를 다 받은 뒤 거절하면 대역폭과 디스크를 이미 낭비한 것이다. `limits.fileSize`는 busboy가 그 지점에서 파일 스트림에 `limit` 이벤트를 내고 더 이상의 데이터를 그 파트로 흘리지 않게 만든다. 여기에 더해 요청 전체 크기를 리버스 프록시(nginx의 `client_max_body_size`)나 진입 미들웨어에서 한 번 더 막아 두는 것이 좋다. 애플리케이션에 도달하기 전에 거절하는 것이 가장 싸다.

응답을 보낸 뒤에도 클라이언트가 계속 데이터를 밀어 넣는 경우가 있다. HTTP는 서버가 본문을 다 읽기 전에 응답할 수 있게 허용하지만, 남은 본문을 읽지 않으면 소켓이 어정쩡한 상태로 남는다. 위 코드의 `req.resume()`이 남은 데이터를 소비해 버려 이 문제를 막는다.

**MIME 타입은 신뢰할 수 없다.** `Content-Type`은 클라이언트가 보내는 값이라 얼마든지 위조된다. `.png`로 올라온 파일이 실제로는 셸 스크립트일 수 있다. 저장 후 8.3절의 매직 넘버 검사로 실제 형식을 확인하고, 불일치하면 삭제한다.

```js
import { open } from 'node:fs/promises'

const SIGNATURES = [
  { mime: 'image/png', bytes: [0x89, 0x50, 0x4e, 0x47] },
  { mime: 'image/jpeg', bytes: [0xff, 0xd8, 0xff] },
  { mime: 'application/pdf', bytes: [0x25, 0x50, 0x44, 0x46] }
]

async function detectMime(filePath) {
  const fh = await open(filePath, 'r')
  try {
    const buf = Buffer.alloc(8)
    const { bytesRead } = await fh.read(buf, 0, 8, 0)
    for (const sig of SIGNATURES) {
      if (bytesRead >= sig.bytes.length && buf.subarray(0, sig.bytes.length).equals(Buffer.from(sig.bytes))) {
        return sig.mime
      }
    }
    return null
  } finally {
    await fh.close()
  }
}
```

### 실무 함정

- **업로드 디렉터리를 웹 루트 안에 두지 마라.** 정적 서빙 경로와 겹치면 사용자가 올린 HTML이나 스크립트가 같은 오리진에서 실행된다. 별도 디렉터리에 저장하고 인증된 다운로드 엔드포인트로만 노출한다.
- **사용자 파일명을 그대로 쓰지 마라.** `../`, NUL 바이트, 윈도우 예약어(`CON`, `NUL`, `PRN`), 지나치게 긴 이름이 모두 문제를 일으킨다. 위 코드처럼 UUID로 저장하고 원래 이름은 DB에 메타데이터로 보관한다.
- **실패 시 부분 파일을 지워야 한다.** 중단된 업로드가 디스크에 쌓이면 결국 `ENOSPC`가 난다. 주기적으로 오래된 고아 파일을 청소하는 작업도 함께 둔다.
- **`bb.on('close')`는 성공을 뜻하지 않는다.** 중단 여부를 별도 플래그로 추적해야 이중 응답(`ERR_HTTP_HEADERS_SENT`)을 피한다.
- **동시 업로드 수를 제한하라.** 20MB 제한이 있어도 동시 1,000건이면 디스크 쓰기 대역폭이 포화된다. 큐나 세마포어로 동시 처리량을 통제한다.

## 8.8 원자적 쓰기와 임시 파일 다루기

### 왜 필요한가

`writeFile`로 설정 파일을 갱신하는 도중에 프로세스가 SIGKILL을 받거나, 컨테이너가 재시작되거나, 전원이 나가면 어떻게 될까. 파일은 이미 잘려 있고(`open`의 `w` 플래그가 즉시 truncate한다) 새 내용은 절반만 쓰였다. 다음 부팅에서 애플리케이션은 깨진 JSON을 읽고 시작조차 못 한다. 이것은 이론적 위험이 아니라 오토스케일링 환경에서 실제로 재현되는 사고다. 상태를 파일로 보관하는 모든 코드는 이 문제를 다뤄야 한다.

### 어떻게 동작하는가

해법의 핵심은 POSIX가 보장하는 성질 하나다. **같은 파일 시스템 안에서의 `rename`은 원자적이다.** 즉 다른 프로세스 입장에서 대상 경로는 "옛 파일" 아니면 "새 파일"이며, 중간 상태는 관측되지 않는다. 그래서 절차는 이렇게 된다.

1. 같은 디렉터리에 임시 파일을 만든다(다른 파일 시스템이면 rename이 `EXDEV`로 실패한다).
2. 새 내용을 전부 쓴다.
3. `fsync`로 데이터를 디스크에 강제로 내린다.
4. 임시 파일을 목표 경로로 `rename`한다.
5. 디렉터리 엔트리 자체를 지속시키기 위해 부모 디렉터리도 `fsync`한다.

3번과 5번이 빠지면 "원자적이지만 지속적이지 않은" 상태가 된다. `rename`은 성공했지만 데이터가 아직 페이지 캐시에만 있어, 전원이 나가면 이름은 바뀌었는데 내용은 0바이트인 파일이 남을 수 있다.

```js
import { open, rename, unlink } from 'node:fs/promises'
import path from 'node:path'
import crypto from 'node:crypto'

/**
 * 원자적 파일 교체. 성공하면 목표 경로는 항상 완전한 옛 내용 또는 완전한 새 내용이다.
 */
export async function writeFileAtomic(target, data, { mode = 0o644, fsyncDir = true } = {}) {
  const dir = path.dirname(target)
  // 임시 파일은 반드시 같은 디렉터리에. /tmp에 만들면 rename이 EXDEV로 실패한다
  const tmp = path.join(dir, `.${path.basename(target)}.${process.pid}.${crypto.randomUUID()}.tmp`)

  let fh
  try {
    // wx: 이미 존재하면 실패. 임시 파일 이름 충돌을 오류로 드러낸다
    fh = await open(tmp, 'wx', mode)
    await fh.writeFile(data)
    await fh.sync()          // fsync(2) — 데이터와 메타데이터를 디스크로
    await fh.close()
    fh = null

    await rename(tmp, target)   // 여기서 교체가 원자적으로 일어난다

    if (fsyncDir) {
      // 디렉터리 엔트리 변경을 지속시킨다. 윈도우에서는 지원되지 않으므로 무시한다
      let dh
      try {
        dh = await open(dir, 'r')
        await dh.sync()
      } catch { /* EISDIR/EPERM 등은 무시 */ } finally {
        await dh?.close()
      }
    }
  } catch (err) {
    await fh?.close().catch(() => {})
    await unlink(tmp).catch(() => {})   // 임시 파일 잔해를 남기지 않는다
    throw err
  }
}

await writeFileAtomic('./state.json', JSON.stringify({ cursor: 12345 }, null, 2))
```

`fsync`에는 비용이 따른다. NVMe SSD에서 한 번에 0.1~1ms, 회전 디스크나 네트워크 스토리지에서는 수 밀리초에서 수십 밀리초다. 초당 수천 번 상태를 저장하는 경로라면 매번 fsync하는 대신, 변경을 메모리에 모아 일정 주기로 한 번씩 원자적 스냅숏을 쓰는 편이 낫다. 반대로 "잃으면 안 되는" 데이터라면 비용을 지불해야 한다. 데이터베이스가 하는 일이 정확히 이 트레이드오프의 관리다.

**임시 디렉터리.** 여러 파일을 임시로 다루거나 작업 공간이 필요할 때는 `mkdtemp`를 쓴다. 고유한 접미사를 붙여 디렉터리를 만들어 주므로 이름 충돌과 심볼릭 링크 공격을 함께 피한다. 직접 `Math.random()`으로 이름을 만들어 `/tmp`에 두는 코드는 공격자가 미리 같은 이름의 심볼릭 링크를 만들어 두는 고전적 취약점에 노출된다.

```js
import { mkdtemp, rm } from 'node:fs/promises'
import { tmpdir } from 'node:os'
import path from 'node:path'

async function withTempDir(fn) {
  // 접두사 뒤에 6자리 무작위 문자열이 붙는다. 구분자를 직접 넣어야 한다
  const dir = await mkdtemp(path.join(tmpdir(), 'build-'))
  try {
    return await fn(dir)
  } finally {
    await rm(dir, { recursive: true, force: true })
  }
}

const result = await withTempDir(async (dir) => {
  // dir 안에서 마음껏 작업한다. 함수가 끝나면 통째로 사라진다
  return path.join(dir, 'out.bin')
})
```

**잠금 파일.** 여러 프로세스가 같은 파일을 동시에 갱신하면 원자적 쓰기만으로는 부족하다. 마지막 쓰기가 이긴다(lost update). 상호 배제가 필요하면 잠금 파일(lock file)을 쓴다. 원리는 `open`의 `wx` 플래그다. 이 플래그는 "파일이 없으면 만들고, 있으면 `EEXIST`로 실패"를 **원자적으로** 수행한다.

```js
import { open, unlink, readFile } from 'node:fs/promises'

const STALE_MS = 30_000

export async function acquireLock(lockPath, { timeoutMs = 10_000, retryMs = 50 } = {}) {
  const deadline = Date.now() + timeoutMs

  for (;;) {
    try {
      // wx는 원자적 create-if-not-exists. 이것이 상호 배제의 근거다
      const fh = await open(lockPath, 'wx')
      await fh.writeFile(JSON.stringify({ pid: process.pid, at: Date.now() }))
      await fh.close()

      let released = false
      return async function release() {
        if (released) return
        released = true
        await unlink(lockPath).catch(() => {})
      }
    } catch (err) {
      if (err.code !== 'EEXIST') throw err

      // 잠금 소유 프로세스가 죽어 남은 유령 잠금(stale lock) 처리
      try {
        const info = JSON.parse(await readFile(lockPath, 'utf8'))
        const dead = Date.now() - info.at > STALE_MS || !isAlive(info.pid)
        if (dead) { await unlink(lockPath).catch(() => {}); continue }
      } catch { /* 잠금 파일이 깨졌거나 방금 사라졌다. 재시도한다 */ }

      if (Date.now() > deadline) throw new Error(`잠금 획득 실패: ${lockPath}`)
      await new Promise((r) => setTimeout(r, retryMs))
    }
  }
}

function isAlive(pid) {
  try { process.kill(pid, 0); return true } catch { return false }
}

// 사용
const release = await acquireLock('./state.json.lock')
try {
  const state = JSON.parse(await readFile('./state.json', 'utf8'))
  state.cursor += 1
  await writeFileAtomic('./state.json', JSON.stringify(state))
} finally {
  await release()
}
```

`isAlive`의 PID 검사는 같은 머신에서만 의미가 있고, PID 재사용 문제도 있다. 여러 컨테이너나 여러 호스트가 공유 볼륨을 쓰는 환경에서는 파일 기반 잠금 대신 Redis나 데이터베이스의 분산 락을 쓴다(24장 참조).

### 실무 함정

- **임시 파일을 `/tmp`에 만들고 목표 경로로 rename하면 `EXDEV`가 난다.** 도커에서 `/tmp`와 애플리케이션 디렉터리는 대개 다른 마운트다. 반드시 목표와 같은 디렉터리에 만든다.
- **`rename`은 대상 파일의 권한이 아니라 임시 파일의 권한을 가져간다.** 기존 파일의 모드를 유지하려면 `stat`으로 읽어 `open`의 `mode`로 넘긴다. 소유자(uid/gid)도 마찬가지로 바뀔 수 있다.
- **`fsync`를 `writeFile` 대신 `write` 뒤에만 부르면 부족하다.** `FileHandle.sync()`는 fsync(2)에 해당하며 데이터와 메타데이터를 모두 내린다. 데이터만 필요하면 `datasync()`가 더 싸다.
- **윈도우에서 `rename`은 대상이 존재하면 실패할 수 있다.** Node의 `fs.rename`은 내부적으로 `MoveFileEx`를 `MOVEFILE_REPLACE_EXISTING`과 함께 호출해 대부분 동작하지만, 대상 파일이 다른 프로세스에 열려 있으면 `EPERM`이 난다. 윈도우를 지원해야 한다면 재시도 로직이 필요하다.
- **잠금 파일을 프로세스 종료 시 지우는 코드에 의존하지 마라.** SIGKILL이나 OOM 킬은 핸들러를 실행시켜 주지 않는다. 유령 잠금 만료(TTL)를 반드시 함께 구현한다.
- **`mkdtemp`의 접두사 뒤에 구분자를 직접 넣어야 한다.** `mkdtemp('/tmp/build')`는 `/tmp/buildXk3n9a`를 만든다. `path.join(tmpdir(), 'build-')`처럼 써야 의도한 모양이 된다.

## 요약

- 경로는 문자열 연결이 아니라 `node:path`로 다룬다. `join`은 조각을 이어 붙이고 `resolve`는 절대 경로를 만든다. URL 경로는 언제나 `path.posix`로 처리하고, ESM에서는 `import.meta.dirname`을 쓴다.
- `stat`은 심볼릭 링크를 따라가고 `lstat`은 링크 자체를 본다. 캐시 검증에는 `mtimeMs`를, 파일 동일성 판정에는 `ino`/`dev`를 쓴다. `access`로 확인한 뒤 여는 패턴은 TOCTOU 경합을 만든다.
- `fs/promises`가 기본이다. 콜백 API는 벤치마크로 병목을 확인한 핫 패스에만, 동기 API는 `listen()` 이전의 부팅 시점에만 허용된다. 요청 처리 중의 동기 호출 하나가 서버 전체를 멈춘다.
- 읽기 전략은 크기가 결정한다. 10MB 미만이고 동시성이 낮으면 `readFile`, 크기를 통제할 수 없으면 `createReadStream`, 특정 구간만 필요하면 `FileHandle.read`. 줄 단위 처리는 `readline`이 멀티바이트 경계 문제를 해결해 준다.
- 디렉터리 순회는 `readdir({ withFileTypes: true })`로 추가 `stat`을 없애고, 대용량 디렉터리는 `opendir`의 비동기 이터레이션으로 메모리를 일정하게 유지한다. 심볼릭 링크 순환은 `realpath` 집합으로 막는다.
- `fs.watch`는 네이티브 알림을 그대로 노출하므로 중복 이벤트, `null` 파일명, rename 후 감시 중단, 리눅스 inotify 한계라는 함정이 있다. 최소한 경로별 디바운스를 구현하고, 이식성과 안정성이 필요하면 chokidar를 쓴다. `watchFile`은 폴링이라 감시 대상이 몇 개뿐일 때만 쓴다.
- 정적 서빙에서 경로 탐색 방어는 선택이 아니다. 디코딩 → NUL 검사 → `resolve` → 루트 접두사(구분자 포함) 검사 순서를 지키고, 사용자 업로드 디렉터리라면 `realpath`로 심볼릭 링크까지 확인한다. `ETag`/`Last-Modified`로 `304`를, `Range`로 `206`을 지원한다.
- 업로드는 처음부터 끝까지 스트리밍이다. 크기·개수 제한으로 조기 중단하고, 파일명은 서버가 생성하며, MIME 타입은 매직 넘버로 재검증하고, 실패 시 부분 파일을 반드시 정리한다.
- 원자적 쓰기는 "같은 디렉터리의 임시 파일 → fsync → rename → 디렉터리 fsync"다. 여러 프로세스가 경쟁하면 `open`의 `wx` 플래그로 잠금 파일을 만들되, 반드시 유령 잠금 만료를 함께 구현한다.

## 연습문제

1. **읽기 전략 실측.** 1MB, 50MB, 500MB, 2GB 크기의 파일을 생성한 뒤, 각 파일에 대해 (a) `readFile` 전체 읽기, (b) `createReadStream` + `pipeline`, (c) `readline` 줄 단위 순회로 SHA-256 해시를 계산하는 세 구현을 작성하라. 각각의 최대 RSS(`process.memoryUsage().rss`를 주기적으로 샘플링)와 총 소요 시간을 표로 정리하고, `readFile`이 실패하기 시작하는 지점과 그때의 오류 코드를 기록하라. 이어서 `highWaterMark`를 16KiB/64KiB/1MiB로 바꿔 가며 스트림 처리량이 어떻게 변하는지 확인하라.

2. **안전한 파일 브라우저 API.** 지정한 루트 아래의 파일을 목록·다운로드하는 HTTP 엔드포인트를 구현하라. 요구 사항은 다음과 같다. (a) `GET /list?dir=...`는 `opendir`로 순회해 이름·크기·수정 시각을 반환하되 한 번에 최대 200개와 커서 기반 페이지네이션을 지원한다. (b) `GET /file?path=...`는 8.6절의 `safeResolve`와 `realpath` 검사를 모두 적용하고 `ETag`, `Cache-Control`, `Range`, `304`, `416`을 올바르게 처리한다. (c) 루트 밖을 가리키는 심볼릭 링크를 실제로 만들어 두고, 이를 통한 접근이 차단되는지 테스트 코드로 증명하라. (d) `%2e%2e%2f`, `....//`, NUL 바이트를 포함한 최소 5가지 공격 페이로드에 대한 테스트를 작성하라.

3. **크래시에 안전한 카운터 서비스.** 여러 프로세스가 동시에 하나의 JSON 파일에 담긴 카운터를 증가시키는 서비스를 구현하라. `acquireLock`으로 상호 배제를 걸고 `writeFileAtomic`으로 갱신한다. 이어서 (a) 프로세스 8개가 각각 1,000번 증가시킨 뒤 최종값이 정확히 8,000인지 확인하고, (b) 쓰기 도중 무작위 시점에 `process.kill(pid, 'SIGKILL')`을 100회 반복 실행한 뒤에도 JSON 파일이 항상 파싱 가능한지 검증하며, (c) `fsync` 호출을 제거한 버전과 성능(초당 갱신 횟수)을 비교하라. (d) 잠금을 쥔 프로세스를 SIGKILL로 죽였을 때 다른 프로세스가 유령 잠금을 만료시키고 진행하는지 확인하라.
