# 17장. 상태, 세션, 인증

HTTP는 상태가 없는(stateless) 프로토콜이다. 그런데 우리가 만드는 애플리케이션은 거의 예외 없이 상태를 요구한다. "지금 이 요청을 보낸 사람이 누구인가"라는 단순한 질문에 답하려면, 서로 독립적인 요청들 사이에 무언가를 이어 붙여야 한다.

이 장은 그 이어 붙이는 방법에 관한 것이다. 상태를 클라이언트에 둘 것인가 서버에 둘 것인가, 서버에 둔다면 어느 서버에 둘 것인가, 그 상태를 신뢰할 수 있는 근거는 무엇인가. 세션과 인증은 이 질문의 서로 다른 답이며, 각각의 답에는 대가가 따른다.

시작은 조금 다른 곳에서 한다. 상태를 논하기 전에, Node.js가 애초에 어떤 방식으로 여러 사용자를 동시에 상대하는지 정확히 이해해야 하기 때문이다. 상태 설계의 제약 대부분이 거기서 나온다.

## 17.1 동시성은 병렬성이 아니다: 많은 연결 다루기

### 왜 필요한가

두 단어는 일상어에서 거의 같은 뜻으로 쓰이지만 시스템 설계에서는 전혀 다른 개념이다. 동시성(concurrency)은 **여러 작업이 겹치는 시간 구간에 진행 중인 상태**를 뜻한다. 병렬성(parallelism)은 **여러 작업이 같은 물리적 순간에 실행되는 상태**를 뜻한다. 동시성은 구조에 관한 성질이고, 병렬성은 실행에 관한 성질이다. 코어가 하나뿐인 기계에서도 동시성은 얼마든지 가능하지만 병렬성은 불가능하다.

로브 파이크(Rob Pike)의 유명한 정의를 빌리면 "동시성은 많은 일을 한꺼번에 다루는 것이고, 병렬성은 많은 일을 한꺼번에 하는 것"이다. Node.js는 전자에 극단적으로 최적화된 런타임이다. 하나의 스레드에서 이벤트 루프를 돌리며 수만 개의 연결을 "다루지만", 자바스크립트 코드 자체는 어느 순간에도 하나만 실행된다.

이 구분이 실무에서 중요한 이유는, 두 개념을 혼동하면 성능 문제의 원인을 정반대로 진단하기 때문이다. "요청이 느리니 인스턴스를 늘리자"는 병렬성 처방인데, 병목이 이벤트 루프 블로킹이라면 인스턴스를 늘려도 각 인스턴스가 똑같이 멈춘다. 반대로 "동시 연결이 많으니 코드를 최적화하자"는 처방은, 실제 병목이 파일 디스크립터 한계라면 아무 효과가 없다.

### 어떻게 동작하는가

전통적인 스레드 기반 서버는 연결 하나마다 스레드를 하나 배정한다. 리눅스에서 스레드 하나의 기본 스택 크기는 8MB이며, 실제로 커밋되는 물리 메모리는 그보다 훨씬 적지만 가상 주소 공간과 커널의 태스크 구조체는 실재하는 비용이다. 여기에 컨텍스트 스위치 비용이 붙는다. 스레드 수가 코어 수를 크게 넘어가면 CPU는 일하는 시간보다 스케줄링하는 시간이 늘어난다. 이것이 이른바 C10K 문제의 고전적 형태였다.

Node.js는 다른 선택을 했다. 커널의 이벤트 통지 메커니즘(리눅스의 `epoll`, macOS의 `kqueue`, 윈도우의 IOCP)을 libuv로 감싸고, 연결마다 스레드 대신 **파일 디스크립터 하나와 자바스크립트 객체 하나**만 배정한다. 이벤트 루프는 "지금 읽을 데이터가 준비된 디스크립터 목록"을 커널에서 받아 해당하는 콜백만 실행한다. 유휴 연결은 비용이 거의 없다. 10,000개의 연결이 열려 있어도 그중 실제로 데이터를 보내는 것이 20개라면, 이벤트 루프는 20개분의 일만 한다.

그래서 연결당 실제 비용은 스레드가 아니라 메모리와 디스크립터로 환산된다. 대략적인 수치를 알아 두면 용량 산정에 도움이 된다. 평문 HTTP 연결 하나는 Node.js 힙에서 `net.Socket` 객체와 HTTP 파서 상태를 합쳐 대체로 10~30KB를 차지하고, 커널 쪽 소켓 버퍼가 수신·송신 합쳐 수십 KB를 더 쓴다. TLS 연결은 여기에 OpenSSL의 레코드 버퍼가 방향당 약 16KB씩 더해져 연결당 60~80KB 수준으로 뛴다. 즉 유휴 연결 50,000개를 TLS로 유지하려면 힙만으로 3GB를 넘길 수 있다. 반면 평문이라면 같은 수가 1GB 안쪽에서 해결된다.

### 세 가지 실제 한계

첫 번째 한계는 **파일 디스크립터**다. 리눅스의 프로세스별 열린 파일 수 소프트 제한(`ulimit -n`)은 배포판에 따라 1024인 경우가 여전히 많다. Node.js 프로세스는 소켓뿐 아니라 로그 파일, DB 커넥션 풀, 감시 중인 파일까지 모두 디스크립터를 쓰므로, 실제 수용 가능한 연결 수는 제한값보다 수십 개 적다. 한계에 닿으면 `EMFILE` 오류가 나면서 새 연결을 수락하지 못하는데, 이때 문제가 되는 것은 `accept` 루프가 계속 실패하며 CPU를 태우는 현상이다. 운영 환경에서는 소프트 제한을 하드 제한 수준(흔히 524288 또는 1048576)까지 올려 두는 것이 사실상 표준이다.

```bash
# 현재 프로세스의 제한 확인
ulimit -Sn   # soft: 예) 1024
ulimit -Hn   # hard: 예) 1048576

# systemd 유닛에서 올리는 방법
# [Service]
# LimitNOFILE=65535
```

두 번째 한계는 **연결당 메모리**다. 앞서 본 수치대로라면 메모리는 연결 수에 선형으로 증가한다. 문제는 Node.js의 기본 힙 상한이다. 64비트에서 V8의 기본 old space 상한은 대략 4GB 안팎이며, 컨테이너에 2GB 메모리 제한을 걸어 두면 그보다 먼저 OOM 킬러가 개입한다. 연결 수가 늘면서 GC가 잦아지면 그 자체가 이벤트 루프 지연으로 나타나므로, 메모리 한계는 대개 "연결이 안 된다"가 아니라 "응답이 갑자기 느려진다"는 증상으로 먼저 드러난다.

세 번째 한계이자 가장 자주 만나는 것은 **이벤트 루프 지연(event loop lag)** 이다. 자바스크립트 코드가 한 번에 20밀리초를 소비하면, 그 20밀리초 동안 대기 중인 모든 연결의 콜백이 밀린다. 연결이 10,000개면 이 지연은 10,000명에게 동시에 전가된다. 여기가 동시성과 병렬성의 구분이 뼈아프게 체감되는 지점이다. Node.js는 I/O를 기다리는 동안 다른 일을 하지만, 계산을 하는 동안에는 아무것도 하지 못한다.

측정하지 않으면 알 수 없으므로, `perf_hooks`의 히스토그램을 붙여 두는 것이 좋다.

```js
// loop-lag.mjs — 이벤트 루프 지연 계측
import { monitorEventLoopDelay } from 'node:perf_hooks'
import http from 'node:http'

const histogram = monitorEventLoopDelay({ resolution: 10 })
histogram.enable()

// 나노초 단위 값을 밀리초로 환산한다
const ms = (ns) => (ns / 1e6).toFixed(1)

setInterval(() => {
  console.log(
    `연결=${server.connections ?? '-'} ` +
    `p50=${ms(histogram.percentile(50))}ms ` +
    `p99=${ms(histogram.percentile(99))}ms ` +
    `max=${ms(histogram.max)}ms ` +
    `rss=${(process.memoryUsage.rss() / 1e6).toFixed(0)}MB`
  )
  histogram.reset()
}, 1000).unref()

const server = http.createServer((req, res) => {
  if (req.url === '/blocking') {
    // 의도적으로 이벤트 루프를 막는다: 약 50ms
    const until = Date.now() + 50
    while (Date.now() < until) { /* busy wait */ }
    res.end('blocked\n')
    return
  }
  res.end('ok\n')
})

// 연결 수 상한을 명시하면 한계 도달 시 동작이 예측 가능해진다
server.maxConnections = 10_000
server.keepAliveTimeout = 5_000     // 유휴 keep-alive 연결 정리
server.headersTimeout = 10_000      // 헤더 지연 공격 방어
server.requestTimeout = 30_000      // 요청 전체 상한

server.listen(3000)
```

`/`만 호출하면 p99가 1밀리초 안쪽에 머물지만, `/blocking`을 동시 요청 50개로 때리는 순간 p99는 수백 밀리초로 치솟는다. 이 지표가 100밀리초를 넘어가기 시작하면 그때부터는 "얼마나 많은 연결을 열 수 있는가"가 아니라 "열려 있는 연결이 얼마나 오래 기다리는가"가 문제다.

### 실무 함정

가장 흔한 함정은 **연결 수를 처리량으로 착각하는 것**이다. `netstat`으로 ESTABLISHED 연결이 8,000개 보인다고 초당 8,000건을 처리하는 것은 아니다. 대부분은 keep-alive로 유휴 상태이며, 실질 처리량은 이벤트 루프가 초당 소화하는 콜백 수로 결정된다.

두 번째 함정은 **타임아웃을 손대지 않는 것**이다. Node.js 18 이후 `requestTimeout` 기본값은 300초, `headersTimeout`은 60초다. 느린 클라이언트가 헤더를 1바이트씩 흘려보내며 연결만 붙잡고 있는 슬로로리스(Slowloris) 공격은 이 값을 줄이는 것만으로 대부분 막힌다.

세 번째 함정은 **CPU 작업을 그대로 두는 것**이다. 이미지 리사이즈, 큰 JSON 직렬화, 비밀번호 해시 같은 작업은 워커 스레드(`node:worker_threads`)나 별도 프로세스로 밀어내야 한다. 특히 뒤에서 다룰 bcrypt/scrypt 계열 비밀번호 해시는 **의도적으로 느리게 설계된 함수**이므로, 동기 API를 쓰면 로그인 요청 하나가 이벤트 루프를 100밀리초 넘게 점유한다. 반드시 비동기 버전을 쓰고, 부하가 크다면 별도 워커로 분리한다.

## 17.2 쿠키와 클라이언트 상태

### 왜 필요한가

HTTP 요청 하나하나는 서로 완전히 독립적이다. 서버는 방금 로그인한 사용자가 다음 요청을 보낸 그 사용자인지 알 방법이 없다. TCP 연결로 식별하려는 시도는 즉시 무너진다. keep-alive 연결은 프록시에서 끊기고, HTTP/2는 여러 요청을 한 연결에 다중화하며, 모바일 클라이언트는 셀 기지국을 옮길 때마다 연결이 새로 맺힌다. IP 주소도 마찬가지다. NAT 뒤의 수백 명이 같은 IP를 공유하고, 한 사용자의 IP는 이동 중에 수시로 바뀐다.

그래서 필요한 것이 **클라이언트가 스스로 들고 다니는 식별자**다. 쿠키(cookie)는 서버가 `Set-Cookie` 헤더로 값을 심으면 브라우저가 같은 출처(origin)의 이후 요청마다 `Cookie` 헤더로 되돌려 보내는 아주 단순한 메커니즘이다. 단순하기 때문에 30년 가까이 살아남았고, 단순하기 때문에 공격 표면이 넓다. 쿠키의 속성(attribute)들은 대부분 이 공격 표면을 하나씩 막기 위해 나중에 덧붙여진 것들이다.

### 어떻게 동작하는가

각 속성이 막는 공격을 하나씩 짚어 보자.

**`HttpOnly`** 는 자바스크립트의 `document.cookie`로 해당 쿠키를 읽지 못하게 한다. 막는 것은 XSS(교차 사이트 스크립팅)를 통한 세션 탈취다. 공격자가 페이지에 스크립트를 주입하는 데 성공하더라도 세션 쿠키 값 자체를 외부로 빼돌리지는 못한다. 다만 오해하면 안 되는 점은, XSS가 성공한 시점에서 공격자는 이미 사용자의 브라우저에서 임의 요청을 보낼 수 있다는 것이다. `HttpOnly`는 "쿠키 값을 훔쳐 다른 기계에서 재사용하는" 경로를 막을 뿐 XSS 자체의 피해를 막지는 않는다.

**`Secure`** 는 HTTPS 연결에서만 쿠키를 전송하게 한다. 막는 것은 네트워크 도청과 SSL 스트리핑이다. 전 구간 HTTPS인 서비스라도 반드시 켜야 한다. 사용자가 `http://` 주소를 실수로 입력하는 단 한 번의 요청에 세션 쿠키가 평문으로 나가면 그것으로 끝이다.

**`SameSite`** 는 다른 사이트에서 시작된 요청에 쿠키를 붙일지 결정한다. 막는 것은 CSRF(교차 사이트 요청 위조)다. 값은 세 가지다. `Strict`는 어떤 교차 사이트 요청에도 쿠키를 보내지 않는다. 안전하지만 외부 링크를 타고 들어온 사용자가 로그아웃 상태로 보이는 문제가 생긴다. `Lax`는 최상위 내비게이션의 GET 요청에만 쿠키를 허용한다. 즉 링크 클릭은 되지만 교차 사이트 POST나 `<img>`, `fetch`에는 붙지 않는다. `None`은 제한을 두지 않으며, 이 값을 쓰려면 반드시 `Secure`가 함께 있어야 한다.

**`Domain`** 은 쿠키가 유효한 호스트 범위를 넓힌다. 생략하면 쿠키를 발급한 호스트에만 전송되고(host-only), `Domain=example.com`으로 지정하면 `api.example.com`, `blog.example.com` 등 모든 하위 도메인으로 전송된다. 범위를 넓히는 것은 편리해 보이지만, 하위 도메인 하나가 탈취되면(이른바 서브도메인 테이크오버) 그 쿠키가 전부 노출된다. 기본값인 host-only가 거의 항상 옳다.

**`Path`** 는 경로 범위를 제한한다. 보안 경계로서의 가치는 거의 없다. 같은 출처의 자바스크립트는 `Path`를 우회해 쿠키를 다룰 수 있으므로, 이 속성은 보안 장치가 아니라 정리 도구로 이해해야 한다.

**`Max-Age` / `Expires`** 는 수명을 정한다. 둘 다 없으면 브라우저를 닫을 때 사라지는 세션 쿠키가 된다. 노출 창(window of exposure)을 줄인다는 점에서 짧은 수명이 유리하지만, 쿠키 만료는 어디까지나 클라이언트 측 정리일 뿐이다. 공격자가 값을 이미 복사해 뒀다면 서버가 그 세션을 무효화하지 않는 한 계속 쓸 수 있다. **만료는 서버에서도 반드시 강제해야 한다.**

### SameSite 기본값 변경이 남긴 것

2020년 크롬 80을 시작으로 주요 브라우저는 `SameSite`를 지정하지 않은 쿠키를 `Lax`로 취급하기 시작했다. 그 전까지 기본값은 사실상 `None`이었다. 이 변경은 웹 전체의 CSRF 노출을 크게 줄였지만, 동시에 상당한 실무 파장을 남겼다.

가장 큰 피해는 **교차 사이트 POST에 의존하던 흐름**이었다. 결제 게이트웨이나 SAML 아이덴티티 공급자(IdP)가 결과를 POST로 리다이렉트해 돌려보내는 구조에서, 돌아온 요청에 세션 쿠키가 붙지 않아 "결제는 됐는데 로그인이 풀린" 상태가 되는 사고가 속출했다. 두 번째는 **iframe 임베드**다. 다른 사이트에 위젯으로 삽입되는 서비스는 `SameSite=None; Secure` 없이는 아예 동작하지 않게 됐고, 이는 곧 HTTPS 강제를 의미했다. 세 번째는 **로컬 개발 환경**이다. `http://localhost`에서는 `Secure` 쿠키가 브라우저마다 다르게 취급되어, 개발에서는 되는데 스테이징에서 안 되는 문제가 흔했다.

교훈은 명확하다. `SameSite`는 이제 기본값에 기대지 말고 명시적으로 선언해야 하며, 교차 사이트 흐름이 필요하다면 그 흐름을 담당하는 쿠키만 따로 발급해 범위를 최소화해야 한다.

### 코드

Node.js 20 이상에서는 표준 `Set-Cookie` 문자열을 직접 만들어도 무리가 없지만, 파싱과 서명은 검증된 라이브러리에 맡기는 편이 낫다. 아래는 속성을 명시적으로 다루는 최소 구현이다.

```js
// cookies.mjs — 쿠키 직렬화와 파싱
export function serializeCookie (name, value, opts = {}) {
  const parts = [`${name}=${encodeURIComponent(value)}`]

  if (opts.maxAge != null) parts.push(`Max-Age=${Math.floor(opts.maxAge)}`)
  if (opts.domain) parts.push(`Domain=${opts.domain}`)
  parts.push(`Path=${opts.path ?? '/'}`)
  if (opts.httpOnly !== false) parts.push('HttpOnly')
  if (opts.secure !== false) parts.push('Secure')
  parts.push(`SameSite=${opts.sameSite ?? 'Lax'}`)

  return parts.join('; ')
}

export function parseCookies (header = '') {
  const out = Object.create(null) // 프로토타입 오염 방지
  for (const pair of header.split(';')) {
    const idx = pair.indexOf('=')
    if (idx < 0) continue
    const key = pair.slice(0, idx).trim()
    if (!key) continue
    out[key] = decodeURIComponent(pair.slice(idx + 1).trim())
  }
  return out
}
```

세션 식별자를 담는 쿠키의 안전한 기본값은 다음과 같다.

```js
// 로그인 성공 후
res.setHeader('Set-Cookie', serializeCookie('sid', sessionId, {
  httpOnly: true,     // JS 접근 차단
  secure: true,       // HTTPS 전용
  sameSite: 'Lax',    // CSRF 완화
  maxAge: 60 * 60 * 8 // 8시간
  // domain 생략 → host-only가 기본이자 최선
}))
```

### 실무 함정

첫째, **쿠키에 상태 자체를 담는 것**이다. 쿠키는 브라우저당 도메인별로 대략 50개, 개당 4KB라는 제한이 있고, 무엇보다 **모든 요청에 함께 전송된다**. 4KB짜리 쿠키는 CSS와 이미지 요청에도 4KB를 얹는다. 쿠키에는 식별자만 담고 나머지는 서버에 두는 것이 원칙이다.

둘째, **서명 없는 값을 신뢰하는 것**이다. `role=admin` 같은 값을 쿠키에 넣으면 사용자가 그대로 고쳐 보낸다. 클라이언트에 값을 둬야 한다면 HMAC 서명이 필수이고, 그럴 바에는 세션 식별자를 쓰는 편이 대개 낫다.

셋째, **`SameSite=Lax`를 CSRF 방어의 전부로 여기는 것**이다. `Lax`는 GET 내비게이션에 쿠키를 허용하므로, 상태를 바꾸는 GET 엔드포인트가 하나라도 있으면 그대로 뚫린다. 상태 변경은 반드시 POST/PUT/DELETE로 하고, 민감한 작업에는 CSRF 토큰이나 `Origin` 헤더 검증을 이중으로 두는 것이 여전히 권장된다. 프레임워크가 제공하는 CSRF 미들웨어를 쓰고 직접 구현하지 않는 편이 안전하다(16장 참조).

## 17.3 세션 저장소와 Redis

### 왜 필요한가

쿠키에 식별자만 담기로 했다면, 그 식별자에 대응하는 실제 데이터는 서버 어딘가에 있어야 한다. 가장 쉬운 구현은 프로세스 메모리의 `Map` 하나다. 실제로 튜토리얼 대부분이 그렇게 시작하고, 개발 환경에서는 완벽하게 동작한다.

문제는 이 구현이 **인스턴스가 둘 이상이 되는 순간 조용히 깨진다**는 것이다. 조용히 깨진다는 표현이 중요하다. 오류가 나지 않는다. 로드 밸런서가 요청을 A 인스턴스로 보내면 로그인 상태이고 B 인스턴스로 보내면 로그아웃 상태가 되는, 사용자 입장에서 "가끔 로그아웃된다"는 유령 같은 증상으로 나타난다. 재시작할 때마다 전원이 로그아웃되는 것도 같은 원인이다. `cluster` 모듈로 워커를 4개 띄우는 순간 한 대의 기계 안에서도 똑같은 일이 벌어진다(25장 참조).

### 어떻게 동작하는가

해결책은 세션 데이터를 **모든 인스턴스가 공유하는 외부 저장소**로 옮기는 것이다. 세션은 키-값 구조이고, 접근 패턴은 요청당 읽기 한 번과 가끔의 쓰기이며, 만료가 필요하고, 영속성 요구는 상대적으로 약하다. 이 조건에 가장 잘 맞는 것이 Redis다. `SET key value EX seconds` 한 번으로 만료까지 위임할 수 있고, 왕복 지연이 밀리초 아래라 요청 경로에 넣어도 부담이 적다.

관계형 데이터베이스를 세션 저장소로 쓸 수도 있지만, 모든 요청이 DB 쓰기를 유발하고(마지막 접근 시각 갱신) 만료된 행을 주기적으로 지워야 한다는 부담이 있다. 전용 세션 저장소로는 Redis가 사실상 표준이다.

### 코드

`express-session`과 `connect-redis` 조합이 가장 널리 쓰이는 구성이다. 세션 자체를 직접 구현하지 않는 이유는 뒤에서 다룰 세션 고정 방어, 쿠키 서명, 동시 갱신 처리 같은 세부가 생각보다 많기 때문이다.

```js
// session.mjs — Redis 기반 세션
import session from 'express-session'
import { RedisStore } from 'connect-redis'
import { createClient } from 'redis'

const redis = createClient({ url: process.env.REDIS_URL })
redis.on('error', (err) => console.error('redis 오류', err))
await redis.connect()

export const sessionMiddleware = session({
  store: new RedisStore({ client: redis, prefix: 'sess:' }),
  secret: process.env.SESSION_SECRET,  // 쿠키 서명 키
  name: 'sid',                         // 기본값 connect.sid 대신 무난한 이름
  resave: false,                       // 변경 없으면 쓰지 않는다
  saveUninitialized: false,            // 빈 세션을 만들지 않는다
  rolling: true,                       // 활동이 있으면 만료를 연장한다
  cookie: {
    httpOnly: true,
    secure: process.env.NODE_ENV === 'production',
    sameSite: 'lax',
    maxAge: 1000 * 60 * 30             // 30분 유휴 만료
  }
})
```

`saveUninitialized: false`는 성능상 중요하다. 이 값이 `true`면 로그인하지 않은 방문자, 심지어 크롤러의 요청마다 Redis에 빈 세션이 하나씩 쌓인다. 트래픽이 많은 사이트에서 세션 키가 수백만 개로 부풀어 오르는 사고의 대부분이 이 설정에서 온다.

### 세션 만료의 두 가지 축

세션 만료는 서로 다른 두 개념을 함께 설계해야 한다. **유휴 만료(idle timeout)** 는 마지막 활동 이후 일정 시간이 지나면 끊는 것이고, **절대 만료(absolute timeout)** 는 로그인 시각으로부터 일정 시간이 지나면 활동 여부와 무관하게 끊는 것이다. `rolling: true`는 유휴 만료만 구현하므로, 활동이 계속되는 세션은 무한히 살아남는다. 금융이나 관리자 콘솔처럼 민감한 영역에서는 절대 만료를 별도로 강제해야 한다.

```js
// 절대 만료 강제
const ABSOLUTE_MAX_MS = 1000 * 60 * 60 * 12 // 12시간

export function enforceAbsoluteTimeout (req, res, next) {
  const s = req.session
  if (!s?.userId) return next()

  if (Date.now() - s.createdAt > ABSOLUTE_MAX_MS) {
    return s.destroy(() => {
      res.status(401).json({ error: '세션이 만료되었습니다. 다시 로그인하세요.' })
    })
  }
  next()
}
```

### 세션 고정 공격과 세션 재발급

세션 고정(session fixation)은 이해하고 나면 허탈할 만큼 단순한 공격이다. 공격자가 먼저 사이트를 방문해 세션 식별자 `X`를 발급받는다. 그리고 피해자가 `X`를 자기 브라우저에 갖게 만든다(예전에는 URL 파라미터로 세션을 전달하는 사이트가 많아 쉬웠고, 지금도 하위 도메인 XSS나 잘못 설정된 `Domain` 쿠키로 가능하다). 피해자가 그 상태로 로그인한다. 서버가 로그인 시 세션 식별자를 그대로 유지하면, 공격자가 들고 있던 `X`는 이제 **인증된 세션**이 된다.

방어는 하나뿐이다. **권한 수준이 바뀌는 모든 시점에 세션 식별자를 새로 발급한다.** 로그인이 대표적이고, 비밀번호 변경이나 권한 상승도 포함된다.

```js
// login.mjs — 로그인 시 세션 재발급
import { verifyPassword } from './password.mjs' // argon2 등 검증된 라이브러리 래퍼

app.post('/login', async (req, res, next) => {
  const user = await findUserByEmail(req.body.email)
  // 사용자가 없어도 동일한 시간을 쓰도록 더미 해시를 검증한다(타이밍 노출 완화)
  const ok = await verifyPassword(user?.passwordHash ?? DUMMY_HASH, req.body.password)
  if (!user || !ok) {
    return res.status(401).json({ error: '이메일 또는 비밀번호가 올바르지 않습니다' })
  }

  // 핵심: 기존 세션 데이터를 버리고 새 식별자를 발급한다
  req.session.regenerate((err) => {
    if (err) return next(err)

    req.session.userId = user.id
    req.session.createdAt = Date.now()

    req.session.save((err2) => {
      if (err2) return next(err2)
      res.json({ ok: true })
    })
  })
})
```

`regenerate` 후에 `save`를 명시적으로 호출하는 이유는, 응답이 먼저 나가고 세션 쓰기가 뒤에 완료되는 경합을 막기 위해서다. 클라이언트가 응답을 받자마자 다음 요청을 보냈는데 Redis에는 아직 세션이 없는 상황은 실제로 발생한다.

로그아웃도 대칭적으로 처리한다. 쿠키만 지우고 서버 세션을 남겨 두면 복사된 쿠키로 계속 접근할 수 있으므로, `destroy`로 저장소에서 지우고 쿠키도 함께 만료시킨다.

### 실무 함정

첫째, **Redis 장애가 곧 전면 로그아웃**이라는 점이다. 세션 저장소는 가용성 측면에서 애플리케이션의 단일 장애점이 된다. Redis Sentinel이나 클러스터로 이중화하고, 연결 실패 시 요청을 어떻게 처리할지(500을 낼지, 익명으로 강등할지) 미리 정해야 한다.

둘째, **세션에 큰 객체를 넣는 것**이다. 사용자 프로필 전체나 장바구니 목록을 세션에 넣으면 요청마다 수십 KB를 직렬화·역직렬화한다. 세션에는 `userId`와 권한 수준 정도만 두고 나머지는 필요할 때 조회한다.

셋째, **동시 요청의 덮어쓰기**다. 브라우저가 동시에 보낸 두 요청이 각각 세션을 읽고 수정한 뒤 저장하면 나중 것이 앞의 것을 덮는다. 세션에 카운터나 누적 데이터를 두면 값이 어긋난다. 그런 데이터는 세션이 아니라 원자적 연산이 가능한 곳에 둬야 한다.

## 17.4 인증: 토큰 기반, JWT, 세션 기반의 트레이드오프

### 왜 필요한가

인증(authentication)은 "당신이 누구인지"를 확인하는 절차다. 앞 절에서 본 세션은 그 확인 결과를 이어 나가는 한 가지 방법이고, JWT(JSON Web Token)는 다른 방법이다. 두 방식의 차이는 표면적으로는 저장 위치의 차이지만, 본질은 **신뢰의 근거를 어디에 두느냐**의 차이다.

세션 방식에서 쿠키에 담긴 값은 의미 없는 난수다. 그 난수가 무엇을 뜻하는지는 오직 서버의 저장소만 안다. 서버는 매 요청마다 저장소를 조회해 "이 식별자가 아직 유효한가"를 확인한다. **신뢰의 근거가 서버 상태에 있다.**

JWT 방식에서 토큰은 자기 자신을 설명한다. 헤더, 페이로드, 서명 세 부분이 점으로 연결되어 있고, 페이로드에는 사용자 ID와 만료 시각 같은 클레임(claim)이 그대로 들어 있다. 서버는 서명만 검증하면 저장소 조회 없이 내용을 신뢰한다. **신뢰의 근거가 암호학적 서명에 있다.**

이 차이에서 모든 장단점이 파생된다.

### 어떻게 동작하는가

JWT의 구조를 뜯어보면 왜 그런 문제가 생기는지 바로 보인다.

```text
eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiIxMjMiLCJleHAiOjE3MDAwMDAwMDB9 . 4f3a...
        헤더                          페이로드                        서명
```

앞의 두 부분은 **암호화가 아니라 Base64URL 인코딩**이다. 누구나 디코딩해서 읽을 수 있다. 서명은 위변조를 막을 뿐 내용을 숨기지 않는다. JWT 페이로드에 이메일, 전화번호, 내부 권한 구조를 넣는 것은 그 정보를 클라이언트와 중간의 모든 로그에 공개하는 것과 같다.

### JWT의 진짜 문제

**첫째, 즉시 취소가 불가능하다.** 이것이 가장 근본적인 문제다. 발급된 토큰은 만료 시각까지 유효하며, 서버는 그것을 취소할 수단이 없다. 사용자가 로그아웃해도, 관리자가 계정을 정지시켜도, 비밀번호가 유출되어 급히 바꿔도, 이미 발급된 토큰은 만료될 때까지 살아 있다. 이를 막으려고 취소 목록(blocklist)을 두면, 매 요청마다 그 목록을 조회하게 되므로 **저장소 조회를 없앤다는 JWT의 유일한 장점이 사라진다.** 그 시점에서 그것은 이름만 JWT인 세션이다.

**둘째, 크기다.** 세션 쿠키는 32바이트 남짓이지만 JWT는 클레임을 몇 개만 넣어도 300~800바이트가 되고, 권한 목록을 담기 시작하면 수 KB로 부푼다. 이 값이 **모든 요청 헤더에 붙는다.** 초당 5,000요청 서비스에서 토큰이 1KB라면 초당 5MB의 추가 상향 트래픽이 발생한다. 헤더 크기 상한(대부분의 프록시가 8KB)을 넘기면 요청이 통째로 거부되는데, 이 장애는 권한이 많은 관리자 계정에서만 재현되어 원인 파악이 늦어진다.

**셋째, 알고리즘 혼동(algorithm confusion) 취약점이다.** JWT 헤더에는 서명 알고리즘이 토큰 자신에 의해 명시된다. 즉 **검증자가 아니라 토큰이 검증 방법을 지시한다.** 이 설계에서 두 가지 고전적 공격이 나온다. 하나는 `alg: "none"`이다. 공격자가 알고리즘을 `none`으로 바꾸고 서명을 비우면, 이를 그대로 수용하는 순진한 구현은 임의로 조작된 페이로드를 통과시킨다. 다른 하나는 RS256(비대칭)으로 서명된 토큰을 HS256(대칭)으로 바꾸는 것이다. 서버가 검증 키로 RSA 공개 키를 넘기는데 알고리즘이 HS256이면, **공개된 공개 키가 HMAC 비밀 키로 사용된다.** 누구나 유효한 토큰을 만들 수 있다.

방어는 단순하다. **검증할 알고리즘을 서버가 고정한다.**

```js
// verify.mjs — 안전한 JWT 검증
import jwt from 'jsonwebtoken'

export function verifyAccessToken (token) {
  return jwt.verify(token, ACCESS_SECRET, {
    algorithms: ['HS256'],       // 필수: 허용 알고리즘 고정. 생략하면 alg 혼동에 노출된다
    issuer: 'https://api.example.com',
    audience: 'example-web',
    clockTolerance: 5,           // 초 단위 시계 오차 허용
    maxAge: '15m'
  })
}
```

**넷째, 만료 관리의 난이도다.** 만료를 길게 잡으면 취소 불가 문제가 심각해지고, 짧게 잡으면 사용자가 자주 튕긴다. 이 딜레마의 표준적 해법이 액세스 토큰과 리프레시 토큰의 분리다.

### 액세스 토큰과 리프레시 토큰

구조는 이렇다. **액세스 토큰**은 수명이 짧고(5~15분) 매 요청에 실려 API 접근에 쓰인다. 취소 불가 문제는 수명이 짧다는 사실로 완화한다. 최악의 경우에도 노출 창은 15분이다. **리프레시 토큰**은 수명이 길고(며칠~몇 주) 오직 새 액세스 토큰을 받는 데만 쓰인다. 이것은 **서버 저장소에 기록되며 취소 가능하다.** 즉 리프레시 토큰은 사실상 세션이고, 액세스 토큰은 그 세션이 발급하는 단기 통행증이다.

리프레시 토큰은 반드시 회전(rotation)시켜야 한다. 사용될 때마다 새 것을 발급하고 이전 것을 폐기한다. 이미 사용된 리프레시 토큰이 다시 제출되면 그것은 탈취의 신호이므로, 해당 사용자의 토큰 계열(family) 전체를 무효화한다.

```js
// refresh.mjs — 회전과 재사용 탐지
app.post('/auth/refresh', async (req, res) => {
  const presented = req.cookies.rt
  if (!presented) return res.status(401).end()

  // 저장소에는 원문이 아니라 해시를 보관한다
  const hash = sha256(presented)
  const record = await store.findRefreshToken(hash)

  if (!record) return res.status(401).end()

  if (record.usedAt) {
    // 이미 사용된 토큰의 재제출 = 탈취 의심 → 계열 전체 폐기
    await store.revokeFamily(record.familyId)
    return res.status(401).json({ error: '세션이 무효화되었습니다. 다시 로그인하세요.' })
  }

  await store.markUsed(hash)
  const next = await store.issueRefreshToken(record.userId, record.familyId)

  res.setHeader('Set-Cookie', serializeCookie('rt', next, {
    httpOnly: true, secure: true, sameSite: 'Strict', path: '/auth/refresh'
  }))
  res.json({ accessToken: signAccessToken(record.userId) })
})
```

`path: '/auth/refresh'`에 주목하자. 리프레시 토큰이 모든 요청에 실려 나가지 않도록 경로를 좁히는 실무적 조치다.

### 무엇을 기본값으로 삼을 것인가

이 책의 입장은 분명하다. **세션이 기본이고, JWT는 이유가 있을 때 쓴다.**

근거는 세 가지다. 첫째, 대부분의 서비스에서 JWT가 약속하는 이득(저장소 조회 제거)은 실제로 실현되지 않는다. 취소가 필요하면 조회가 돌아오고, 취소가 필요 없는 서비스는 거의 없다. 둘째, Redis 조회 한 번의 비용은 보통 1밀리초 미만이다. 이것을 아끼려고 취소 불가능성을 감수하는 거래는 대부분의 경우 손해다. 셋째, 세션은 실패 모드가 단순하다. 세션이 없으면 401이다. JWT는 서명 검증 설정 하나를 잘못 두면 인증 우회로 이어진다.

JWT가 정당한 경우는 명확하다. **서로 다른 신뢰 도메인 사이에서 인증 정보를 전달할 때**, 즉 OIDC 아이덴티티 토큰, 서비스 간 호출의 단기 자격 증명, 저장소를 공유할 수 없는 조직 경계를 넘는 경우다. 여기서 JWT의 자기 기술성은 실제 가치가 있다.

### 실무 함정

첫째, **인증을 직접 구현하는 것**이다. 비밀번호 해시 파라미터, 계정 열거 방지, 무차별 대입 제한, 비밀번호 재설정 토큰의 일회성, 다중 인증(MFA)까지 올바르게 구현하려면 생각보다 훨씬 많은 세부가 필요하고, 하나만 틀려도 전체가 무너진다. 원리는 이해하되 구현은 검증된 것을 쓰는 편이 낫다. 자체 호스팅이라면 Passport, Lucia, Auth.js 같은 라이브러리를, 가능하다면 Keycloak이나 Auth0, AWS Cognito 같은 아이덴티티 공급자에 위임하는 것이 현실적인 선택이다.

둘째, **토큰을 `localStorage`에 넣는 것**이다. XSS에 그대로 노출된다. `HttpOnly` 쿠키가 여전히 더 안전하다.

셋째, **비밀번호 해시로 SHA-256을 쓰는 것**이다. 빠른 해시는 비밀번호에 부적합하다. Argon2id를 우선하고, 없으면 scrypt나 bcrypt를 쓴다.

## 17.5 인가와 권한 모델

### 왜 필요한가

인증이 "당신이 누구인가"라면 인가(authorization)는 "당신이 이것을 해도 되는가"이다. 두 질문은 자주 한 덩어리로 취급되지만 실패 양상은 전혀 다르다. 인증 실패는 대체로 눈에 띈다. 로그인이 안 되거나 401이 난다. 인가 실패는 조용하다. 아무 오류 없이 남의 데이터를 반환한다.

OWASP가 매년 집계하는 웹 취약점 순위에서 접근 제어 실패(Broken Access Control)가 오랫동안 1위를 지켜 온 이유가 여기에 있다. 인가 버그는 테스트를 통과한다. 개발자가 자기 계정으로 테스트하면 자기 데이터가 잘 나오기 때문이다.

### 어떻게 동작하는가: RBAC와 ABAC

**RBAC(Role-Based Access Control)** 는 사용자에게 역할(role)을 부여하고, 역할에 권한(permission)을 묶는다. `admin`, `editor`, `viewer` 같은 것이다. 장점은 이해와 감사가 쉽다는 것이다. "누가 무엇을 할 수 있는가"를 역할 표 하나로 설명할 수 있다. 단점은 조건이 늘어날 때 역할이 폭발한다는 것이다. "자기 팀의 문서만 편집할 수 있는 편집자"를 표현하려면 팀마다 역할을 만들어야 하고, 여기에 "업무 시간에만"이 붙으면 다시 두 배가 된다.

**ABAC(Attribute-Based Access Control)** 는 주체(subject), 대상(resource), 행위(action), 환경(environment)의 속성을 조합한 규칙으로 판단한다. "문서의 소유 팀이 사용자의 팀과 같고, 문서 상태가 `draft`이며, 사용자의 등급이 `editor` 이상이면 허용" 같은 식이다. 표현력이 높고 역할 폭발이 없지만, 규칙이 흩어지면 "이 사용자가 결국 무엇을 할 수 있는가"를 아무도 답하지 못하는 상태가 된다.

현실적인 선택은 대개 혼합이다. 굵은 결의 접근은 RBAC로 나누고(관리자 영역 진입 여부 등), 개별 리소스에 대한 판단은 속성 기반으로 한다. 중요한 것은 모델의 이름이 아니라 **결정 지점이 한 곳에 모여 있는가**이다.

### 인가 검사를 어느 계층에 둘 것인가

세 후보가 있다.

**라우터/미들웨어 계층**은 경로 단위의 굵은 검사에 적합하다. `/admin/*`에 관리자 역할을 요구하는 식이다. 구현이 명확하고 감사하기 쉽다. 한계는 리소스를 모르는 상태에서 판단한다는 것이다. `/documents/:id`에 대해 "이 문서가 당신 것인가"를 미들웨어는 알 수 없다.

**서비스/도메인 계층**은 리소스를 조회한 뒤 소유권과 상태를 함께 판단할 수 있다. 인가 규칙이 도메인 규칙과 같은 곳에 있어 일관성이 높다. 이 계층이 **리소스 수준 인가의 제자리**다.

**데이터 접근 계층**은 쿼리 자체에 조건을 넣는 방식이다. `WHERE owner_id = ?`를 항상 붙이거나 PostgreSQL의 행 수준 보안(RLS)을 쓴다. 가장 누락이 적지만 규칙 표현력이 제한되고 디버깅이 어렵다.

권장 구성은 **미들웨어에서 굵게 거르고, 서비스 계층에서 리소스 소유권을 반드시 확인하며, 특히 민감한 테이블은 데이터 계층에서 한 번 더 방어하는** 삼중 구조다. 컨트롤러에 흩뿌리는 것만은 피해야 한다. 검사가 흩어지면 새 엔드포인트를 추가할 때 빠뜨리는 것이 시간 문제다.

### 수평 권한 상승과 IDOR

수직 권한 상승은 일반 사용자가 관리자 기능에 접근하는 것이고, **수평 권한 상승(horizontal privilege escalation)** 은 같은 권한 수준의 다른 사용자 데이터에 접근하는 것이다. 후자의 가장 흔한 형태가 IDOR(Insecure Direct Object Reference)이다.

전형적인 취약 코드는 이렇게 생겼다.

```js
// 취약: 인증만 하고 소유권을 확인하지 않는다
app.get('/api/invoices/:id', requireLogin, async (req, res) => {
  const invoice = await db.invoices.findById(req.params.id)
  if (!invoice) return res.status(404).end()
  res.json(invoice)   // 남의 청구서도 그대로 반환된다
})
```

`requireLogin`이 있으니 안전해 보이지만, 로그인한 아무나 `id`를 1씩 바꿔 가며 전체 청구서를 긁어 갈 수 있다. 이 버그는 정상 사용 시 절대 드러나지 않는다.

올바른 형태는 **인증된 주체와 리소스를 함께 판단**하는 것이다.

```js
// authorize.mjs — 정책을 한 곳에 모은다
const policies = {
  invoice: {
    read: (user, invoice) =>
      invoice.ownerId === user.id ||
      user.roles.includes('admin') ||
      (user.roles.includes('accountant') && invoice.orgId === user.orgId),

    update: (user, invoice) =>
      invoice.status === 'draft' &&
      (invoice.ownerId === user.id || user.roles.includes('admin'))
  }
}

export function can (user, action, type, resource) {
  const rule = policies[type]?.[action]
  if (!rule) return false      // 정의되지 않은 조합은 거부가 기본
  return rule(user, resource)
}
```

```js
// 리소스를 먼저 불러오고, 정책으로 판단한다
app.get('/api/invoices/:id', requireLogin, async (req, res) => {
  const invoice = await db.invoices.findById(req.params.id)

  // 존재하지 않는 경우와 권한이 없는 경우를 같은 응답으로 처리한다.
  // 그렇지 않으면 404/403의 차이로 리소스 존재 여부가 새어 나간다.
  if (!invoice || !can(req.user, 'read', 'invoice', invoice)) {
    return res.status(404).json({ error: '찾을 수 없습니다' })
  }

  res.json(invoice)
})
```

주석에 적힌 응답 통일은 사소해 보이지만 실제로 중요하다. 403과 404를 구분해서 응답하면 공격자는 "존재하지만 권한이 없는" ID를 열거해 고객 수나 주문량 같은 사업 정보를 추론할 수 있다.

식별자를 순차 정수 대신 UUID로 바꾸는 것은 **보완책이지 해법이 아니다.** 추측을 어렵게 할 뿐 소유권 검사를 대신하지 못한다. 링크 공유나 로그 유출로 UUID가 노출되는 순간 그대로 뚫린다.

### 실무 함정

첫째, **프런트엔드에서 버튼을 숨긴 것으로 인가를 대신하는 것**이다. UI는 편의이고 강제는 서버에서만 유효하다.

둘째, **대량 조회 엔드포인트를 빠뜨리는 것**이다. 단건 조회에는 소유권 검사를 넣고 목록 조회에는 넣지 않는 경우가 흔하다. 목록 쿼리에는 항상 범위 조건이 들어가야 한다.

셋째, **기본값이 허용인 정책**이다. 새 리소스 타입이나 새 행위가 추가됐을 때 정책이 없으면 거부되도록, 위 코드처럼 명시적 거부를 기본값으로 둬야 한다.

넷째, **인가 결정을 로그로 남기지 않는 것**이다. 거부된 접근 시도는 공격 탐지의 1차 신호다. 사용자 ID, 리소스, 행위, 결정 결과를 구조화된 로그로 남겨 두면 사고 조사 시간이 극적으로 줄어든다(31장 참조).

## 17.6 상태를 여러 인스턴스에 공유하기

### 왜 필요한가

지금까지 다룬 모든 주제가 하나의 질문으로 수렴한다. **상태를 어디에 둘 것인가.** 인스턴스가 하나일 때는 이 질문이 존재하지 않는다. 프로세스 메모리에 두면 되고, 그것이 가장 빠르다. 인스턴스가 둘이 되는 순간 질문이 생기고, 그 답에 따라 아키텍처가 갈린다.

선택지는 사실상 세 가지다. 상태를 **한 인스턴스에 묶어 두거나**, **모든 인스턴스가 공유하는 외부 저장소로 밀어내거나**, **아예 없애거나**.

### 선택지 1: 스티키 세션

스티키 세션(sticky session)은 로드 밸런서가 같은 클라이언트의 요청을 항상 같은 인스턴스로 보내는 방식이다. 쿠키 기반(밸런서가 자체 쿠키를 심음)이나 IP 해시로 구현한다. 코드를 한 줄도 고치지 않고 인메모리 상태를 유지할 수 있다는 점에서 매력적이고, 그래서 자주 선택된다.

대가는 생각보다 크다. **첫째, 부하가 고르지 않다.** 세션은 수명이 제각각이라 시간이 지나면 특정 인스턴스에 장기 사용자가 몰린다. 밸런서는 요청 수를 균등하게 나눌 뿐 작업량을 나누지 못한다. **둘째, 인스턴스 하나의 죽음이 그 인스턴스에 묶인 모든 사용자의 상태 손실로 이어진다.** 무상태였다면 아무도 눈치채지 못했을 재시작이 수천 명의 로그아웃이 된다. **셋째, 배포가 어려워진다.** 롤링 배포는 인스턴스를 순차적으로 교체하는데, 스티키 세션 환경에서는 그때마다 사용자 일부가 상태를 잃는다. 연결 드레이닝으로 완화할 수 있지만 완전히 없애지는 못한다. **넷째, 오토스케일링과 상성이 나쁘다.** 인스턴스를 줄이면 그쪽 세션이 사라지고, 늘려도 기존 사용자는 옮겨 가지 않아 새 인스턴스가 한동안 놀게 된다.

이 대가들은 확장 전략 전반에서 반복적으로 등장하는 주제이므로 25장에서 더 자세히 다룬다(25장 참조). 여기서 기억할 원칙은 하나다. **스티키 세션은 상태 문제를 해결하는 것이 아니라 연기하는 것이다.** WebSocket처럼 연결 자체가 상태인 경우(18장 참조)에는 불가피하지만, 일반적인 HTTP 세션 때문에 스티키를 켜는 것은 대개 잘못된 거래다.

### 선택지 2: 상태를 외부로 밀어내기

두 번째 선택지가 이 장에서 계속 이야기해 온 방향이다. 세션은 Redis로, 파일은 오브젝트 스토리지(S3 등)로, 캐시는 공유 캐시로, 작업 큐는 메시지 브로커로 옮긴다. 그러면 인스턴스 자체는 **무상태(stateless)** 가 된다.

무상태 인스턴스의 정의는 "메모리에 아무것도 없다"가 아니라 **"임의의 시점에 죽여도 어떤 요청도 복구 불가능한 상태를 잃지 않는다"** 이다. 이 성질이 확보되면 많은 것이 따라온다. 어느 인스턴스가 요청을 받아도 결과가 같으므로 라운드 로빈으로 충분하고, 인스턴스를 늘리고 줄이는 것이 자유로우며, 배포는 그냥 교체가 되고, 헬스 체크에 실패한 인스턴스는 고민 없이 버릴 수 있다. 복원력 설계의 상당 부분이 이 성질 위에 서 있다(29장 참조).

비용도 있다. 요청 경로에 네트워크 왕복이 하나 추가되고(Redis 조회 0.3~1밀리초), 외부 저장소가 새로운 단일 장애점이 되며, 운영해야 할 구성 요소가 늘어난다. 그럼에도 이 거래가 거의 항상 이득인 이유는, 상태를 다루는 어려운 문제(복제, 만료, 일관성, 백업)를 애플리케이션이 아니라 그 일에 특화된 시스템이 맡게 되기 때문이다.

### 선택지 3: 상태를 없애기

가장 좋은 상태는 존재하지 않는 상태다. 실무에서 세션에 들어 있는 데이터를 하나씩 검토해 보면 상당수가 애초에 없어도 되는 것들이다. 사용자 프로필은 필요할 때 조회하면 되고, 장바구니는 DB에 있는 편이 기기 간 동기화까지 얻는다. UI 설정 같은 것은 클라이언트에 두면 그만이다. 남는 것은 대개 `userId`와 인증 시각 정도다.

그리고 이 남은 것을 어떻게 다룰지가 17.4에서 논한 세션 대 JWT의 문제로 되돌아온다. 원을 한 바퀴 돈 셈이다.

### 코드: 공유 상태에는 원자적 연산을 쓴다

상태를 Redis로 옮긴 뒤에도 흔히 남는 실수가 있다. 읽고 계산해서 쓰는 패턴을 그대로 옮기는 것이다. 인스턴스가 여럿이면 이 패턴은 경합한다.

```js
// 잘못된 이식: read-modify-write는 인스턴스 간에 경합한다
const count = Number(await redis.get(key) ?? 0)
await redis.set(key, count + 1)   // 다른 인스턴스의 증가분이 사라진다
```

```js
// ratelimit.mjs — 원자적 연산으로 공유 카운터 다루기
export async function hitRateLimit (redis, userId, limit = 100, windowSec = 60) {
  const key = `rl:${userId}:${Math.floor(Date.now() / 1000 / windowSec)}`

  // MULTI로 증가와 만료를 한 번에 보낸다. INCR 자체가 원자적이다
  const [count] = await redis
    .multi()
    .incr(key)
    .expire(key, windowSec)
    .exec()

  return { allowed: Number(count) <= limit, count: Number(count) }
}
```

여러 키에 걸친 조건부 갱신처럼 단일 명령으로 표현되지 않는 경우에는 Lua 스크립트(`EVAL`)로 원자성을 확보하거나, 분산 락을 도입한다. 다만 분산 락은 시계와 장애 상황에서 다루기 까다로운 프리미티브이므로, 가능하면 원자적 명령이나 멱등한 설계로 회피하는 편이 낫다(24장 참조).

### 실무 함정

첫째, **"무상태"를 선언만 하는 것**이다. 코드 어딘가에 모듈 스코프 `Map` 하나가 남아 있으면 그것으로 무상태가 아니다. 인메모리 캐시, 진행 중 작업 목록, 업로드 임시 파일이 대표적인 잔여물이다. 인스턴스를 무작위로 죽여 보는 테스트가 이런 것들을 가장 확실하게 찾아낸다.

둘째, **로컬 디스크에 쓰는 것**이다. 업로드 파일이나 생성된 이미지를 컨테이너 파일 시스템에 두면 다음 요청이 다른 인스턴스로 갔을 때 사라진다. 컨테이너는 언제든 교체된다고 가정해야 한다(32장 참조).

셋째, **공유 저장소 지연을 무시하는 것**이다. 인메모리에서 마이크로초에 끝나던 조회가 밀리초가 되면, 요청당 조회를 다섯 번 하던 코드는 그대로 5밀리초를 더 쓴다. 세션 조회는 요청당 한 번으로 묶고, 필요하면 짧은 TTL의 로컬 캐시를 앞에 두되 그 순간 일관성을 일부 포기한다는 사실을 명시적으로 인지해야 한다.

## 요약

- 동시성은 여러 일을 겹쳐서 다루는 구조적 성질이고 병렬성은 같은 순간에 실행하는 실행적 성질이다. Node.js는 스레드 대신 이벤트 통지로 동시성을 얻으므로 유휴 연결의 비용이 매우 낮지만, 계산이 이벤트 루프를 막는 순간 그 지연이 모든 연결에 동시에 전가된다.
- 많은 연결을 다룰 때의 실제 한계는 파일 디스크립터(`ulimit -n`), 연결당 메모리(평문 10~30KB, TLS 60~80KB), 이벤트 루프 지연 세 가지다. `monitorEventLoopDelay`로 p99를 상시 계측하고, `headersTimeout`과 `requestTimeout`을 기본값보다 짧게 조정한다.
- 쿠키 속성은 각각 다른 공격을 막는다. `HttpOnly`는 XSS를 통한 값 탈취, `Secure`는 도청, `SameSite`는 CSRF를 겨냥한다. `Domain`은 기본값인 host-only가 거의 항상 옳고, `Path`는 보안 경계가 아니다. 2020년 이후 `SameSite` 기본값이 `Lax`가 되면서 교차 사이트 POST와 iframe 임베드 흐름은 명시적 설계가 필요해졌다.
- 인메모리 세션은 인스턴스가 둘이 되는 순간 오류 없이 깨진다. Redis 같은 공유 저장소로 옮기고, 유휴 만료와 절대 만료를 함께 설계하며, 로그인처럼 권한 수준이 바뀌는 시점에는 반드시 세션 식별자를 재발급해 세션 고정 공격을 막는다.
- JWT의 자기 기술성은 즉시 취소 불가, 헤더 크기 증가, 알고리즘 혼동 취약점이라는 대가를 동반한다. 검증 시 허용 알고리즘을 고정하고, 짧은 액세스 토큰과 회전하는 리프레시 토큰으로 완화한다. 기본값은 세션이며, JWT는 신뢰 도메인을 넘을 때 쓴다.
- 인가 실패는 조용하다. RBAC로 굵게 나누고 리소스 소유권은 서비스 계층에서 정책 함수로 판단하며, 권한 없음과 존재하지 않음을 같은 응답으로 통일해 정보 유출을 막는다. UUID는 IDOR의 해법이 아니라 보완책이다.
- 상태는 한 인스턴스에 묶거나, 외부로 밀어내거나, 없앤다. 스티키 세션은 문제를 연기할 뿐이며 부하 편중, 장애 시 상태 손실, 배포와 오토스케일링의 어려움이라는 대가를 치른다. 무상태 인스턴스란 임의의 시점에 죽여도 복구 불가능한 상태를 잃지 않는 인스턴스를 뜻한다.

## 연습문제

1. **연결 한계 측정** — 유휴 keep-alive 연결을 유지하는 HTTP 서버를 만들고, 클라이언트 스크립트로 연결 수를 1,000 → 5,000 → 20,000으로 늘려 가며 RSS와 이벤트 루프 p99를 기록하라. 같은 실험을 TLS로 반복해 연결당 메모리 증가분을 비교하고, `ulimit -n`을 1024로 낮췄을 때 어떤 오류가 어느 시점에 발생하는지, 그때 서버의 CPU 사용률이 어떻게 변하는지 관찰해 서술하라.

2. **세션 고정 재현과 방어** — `express-session`을 쓰되 로그인 시 `regenerate`를 호출하지 않는 서버를 만들고, 로그인 전후로 세션 쿠키 값이 동일하게 유지되는 것을 확인하라. 그 상태에서 공격자가 미리 발급받은 식별자로 인증된 세션에 접근할 수 있음을 스크립트로 재현한 뒤, `regenerate`와 `save`를 추가해 공격이 실패하는 것을 보여라. `save` 콜백 없이 응답을 먼저 보냈을 때 발생 가능한 경합도 함께 설명하라.

3. **JWT에서 세션으로의 전환 비용 산정** — 액세스 토큰만으로 인증하는 API를 만들고, 사용자 정지 기능을 추가하라. 먼저 취소 목록을 Redis에 두는 방식으로 구현해 정지가 즉시 반영되게 한 뒤, 요청당 Redis 조회 횟수와 p99 지연을 측정하라. 이어서 같은 API를 세션 방식으로 다시 구현해 두 구조의 요청당 조회 횟수, 헤더 크기, 정지 반영 지연을 표로 비교하고, 어떤 조건에서 JWT가 여전히 유리한지 근거와 함께 결론을 내려라.
