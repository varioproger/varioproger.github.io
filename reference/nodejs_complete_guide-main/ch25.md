# 25장. 확장 전략

Node.js는 단일 스레드로 이벤트 루프를 돌린다. 이 설계 덕분에 I/O 위주의 작업에서는 스레드 하나로도 수만 개의 연결을 감당하지만, 대가로 프로세스 하나가 CPU 코어 하나 이상을 쓰지 못한다. 16코어 장비에 Node.js 프로세스를 하나 띄우면 열다섯 개의 코어가 논다.

이 장은 그 벽을 넘는 방법을 다룬다. 먼저 확장을 세 축으로 분해해 어떤 문제에 어떤 축이 답인지 정리하고, 그다음 `cluster` 모듈이 실제로 어떻게 동작하는지를 커널 수준까지 내려가 살펴본다. 클러스터로 얻는 복원력과 무중단 재시작을 완전한 코드로 구현한 뒤, 반대로 `cluster`를 쓰지 말아야 할 이유를 정직하게 나열한다. 마지막 두 절은 상태 있는 통신을 확장하는 문제와, 실무에서 가장 자주 나오는 질문—프로세스 매니저와 오케스트레이터 중 무엇을 쓸 것인가—에 답한다.

25.4와 25.6은 이 장에서 결론이 가장 뒤집히기 쉬운 절이다. 2015년에 옳았던 답이 2025년에는 대체로 틀렸기 때문이다.

## 25.1 확장성의 세 가지 축

### 왜 필요한가

"확장한다"는 말은 최소 세 가지 서로 다른 작업을 뭉뚱그린다. 인스턴스를 늘리는 것, 애플리케이션을 쪼개는 것, 데이터를 나누는 것은 해결하는 문제도 지불하는 비용도 전혀 다르다. 마틴 애벗(Martin Abbott)과 마이클 피셔(Michael Fisher)가 제시한 확장 큐브(scale cube)는 이 셋을 3차원 공간의 세 축으로 놓는다. 이 모델의 쓸모는 분류 자체가 아니라, 지금 겪는 병목이 어느 축의 문제인지 먼저 묻게 만든다는 데 있다. 축을 잘못 고르면 노력의 대부분이 낭비된다.

### 어떻게 동작하는가

**X축은 복제(cloning)다.** 동일한 애플리케이션 인스턴스를 N개 띄우고 앞에 로드 밸런서를 둔다. 각 인스턴스는 전체 코드베이스와 전체 데이터에 접근하며, 어떤 요청이든 처리할 수 있다.

```text
        [로드 밸런서]
         /    |    \
    [앱#1] [앱#2] [앱#3]     ← 셋 다 동일한 코드, 동일한 DB
         \    |    /
          [데이터베이스]
```

가장 싸고 가장 빠른 축이다. 코드를 한 줄도 고치지 않고 처리량을 N배로 늘릴 수 있다—애플리케이션이 무상태(stateless)라면. 대가는 두 가지다. 첫째, 모든 인스턴스가 같은 데이터베이스를 때리므로 데이터 계층의 부하는 전혀 줄지 않는다. 오히려 커넥션 풀이 인스턴스 수만큼 곱해져 데이터베이스가 먼저 무너진다. 둘째, 데이터셋 전체가 여전히 한 곳에 있어야 하므로 데이터 크기 문제는 손도 대지 못한다.

**Y축은 기능 분해(functional decomposition)다.** 애플리케이션을 책임 단위로 쪼갠다. 주문, 결제, 알림, 검색이 각각 별도 서비스가 되어 독립적으로 배포되고 독립적으로 확장된다(27장 참조).

X축이 "같은 것을 더 많이"라면 Y축은 "다른 것을 따로"다. 이 축이 해결하는 것은 처리량이 아니라 이질성이다. 검색이 CPU를 먹고 알림이 메모리를 먹고 결제가 극도의 가용성을 요구할 때, 하나의 프로세스 안에서는 셋 모두에게 맞는 배포 단위를 정할 수 없다. 무거운 이미지 처리 한 곳 때문에 전체 인스턴스를 8코어로 띄우는 상황이 Y축이 필요하다는 신호다. 대가는 크다. 프로세스 내부 함수 호출이던 것이 네트워크 호출이 되고, 트랜잭션이 사라지고, 조직에 서비스 경계를 운영할 능력이 요구된다.

**Z축은 데이터 분할(sharding)이다.** 데이터를 어떤 키로 나눠 각 인스턴스가 전체의 일부만 담당하게 한다. 고객 ID의 해시로 나누거나, 지역으로 나누거나, 테넌트(tenant)로 나눈다.

```text
   [라우터: shard = hash(tenantId) % 3]
         /        |        \
    [앱+DB#0] [앱+DB#1] [앱+DB#2]
    테넌트 A,D  테넌트 B,E  테넌트 C,F
```

Z축은 X축이 못 하는 것을 한다. 각 샤드의 데이터셋이 1/N로 줄어들므로 인덱스가 메모리에 들어가고, 쓰기 부하가 실제로 분산된다. 대가는 라우팅 계층이 필요하다는 것, 샤드 경계를 넘는 질의가 극도로 비싸진다는 것, 그리고 리샤딩(resharding)이 운영에서 가장 두려운 작업 중 하나라는 것이다.

### 실무 관점

판단 기준은 단순하다. **무엇이 부족한가**를 먼저 특정한다.

- **CPU 시간이나 이벤트 루프 처리량이 부족하다** → X축. 인스턴스를 늘린다. 데이터베이스에 여유가 있는 한 이 축이 압도적으로 싸다. `cluster`도, 컨테이너 복제도 전부 X축이다.
- **컴포넌트마다 요구사항이 충돌한다** → Y축. 배포 주기가 다르거나, 자원 프로파일이 다르거나, 장애 격리가 필요할 때다. 단순히 코드가 커졌다는 이유로 이 축을 타는 것은 거의 항상 실수다.
- **데이터가 한 노드에 안 들어가거나 쓰기가 병목이다** → Z축. 읽기 병목이라면 Z축 이전에 읽기 복제본(read replica)과 캐시를 먼저 검토한다. 읽기 복제본은 사실상 데이터 계층의 X축이다.

순서도 중요하다. 거의 모든 시스템은 X축을 끝까지 밀어붙인 뒤에 다른 축을 검토해야 한다. X축의 한계는 대개 "인스턴스를 더 못 늘려서"가 아니라 "인스턴스를 늘려도 데이터베이스가 못 버텨서" 온다. 그 시점이 오면 그때 Y축과 Z축 중 무엇이 실제 병목을 푸는지 데이터로 판단한다. 세 축은 배타적이지 않다. 성숙한 시스템은 Y축으로 쪼갠 각 서비스를 X축으로 복제하고, 그중 데이터가 큰 서비스만 Z축으로 샤딩한다.

이 장의 나머지는 X축, 그중에서도 단일 머신 안에서의 X축을 다룬다.

## 25.2 `cluster` 모듈: 동작 원리와 요청 분배

### 왜 필요한가

한 대의 머신에서 코어를 다 쓰려면 프로세스가 여러 개여야 한다. 문제는 여러 프로세스가 같은 포트를 어떻게 나눠 쓰느냐다. 그냥 프로세스를 네 개 띄우고 모두 3000번 포트에 `listen`하면 두 번째부터 `EADDRINUSE`로 죽는다.

`cluster` 모듈은 이 문제를 부모 프로세스가 소켓을 소유하는 방식으로 푼다.

```js
// server.js
import cluster from 'node:cluster'
import http from 'node:http'
import { availableParallelism } from 'node:os'

if (cluster.isPrimary) {
  const workers = availableParallelism()
  console.log(`primary ${process.pid}: 워커 ${workers}개 기동`)
  for (let i = 0; i < workers; i++) cluster.fork()
} else {
  http.createServer((req, res) => {
    res.end(`handled by ${process.pid}\n`)
  }).listen(3000)
}
```

이 코드가 왜 `EADDRINUSE`를 내지 않는지가 이 절의 핵심이다.

### 어떻게 동작하는가

`cluster.fork()`는 `child_process.fork()`를 호출해 같은 스크립트를 새 프로세스로 실행하되, 부모와 자식 사이에 IPC 채널을 열어둔다(11장 참조). 자식 쪽에서는 `cluster` 모듈이 `net.Server.prototype.listen`을 가로챈다. 워커가 `listen(3000)`을 부르면 실제로 소켓을 만들지 않고, IPC로 프라이머리에게 "3000번 포트가 필요하다"는 메시지를 보낸다.

프라이머리는 그 포트에 대한 소켓을 자기가 한 번만 만든다. 그다음 무슨 일이 벌어지는지는 스케줄링 정책에 따라 갈린다.

**`SCHED_NONE`—OS에 맡기기.** 프라이머리가 만든 리스닝 소켓의 파일 디스크립터를 IPC의 핸들 전달 기능으로 워커에게 그대로 넘긴다. 유닉스 도메인 소켓의 `SCM_RIGHTS`를 통해 커널이 자식 프로세스의 디스크립터 테이블에 같은 소켓을 등록해주는 것이다. 이제 모든 워커가 **동일한 리스닝 소켓** 하나를 공유하며 각자 `accept()`를 호출한다. 어느 워커가 연결을 가져갈지는 전적으로 커널이 정한다.

**`SCHED_RR`—프라이머리가 분배하기.** 프라이머리만 소켓을 갖고 `accept()`한다. 연결이 수락되면 그 연결 소켓(리스닝 소켓이 아니라)의 핸들을 워커에게 라운드 로빈으로 넘긴다. 워커는 자기가 `accept`한 적 없는 완성된 연결을 IPC로 받아 처리한다.

Node.js는 윈도우를 제외한 모든 플랫폼에서 `SCHED_RR`을 기본값으로 쓴다. 바꾸려면 코드나 환경 변수로 지정한다.

```js
import cluster from 'node:cluster'
cluster.schedulingPolicy = cluster.SCHED_NONE // fork() 호출 전에 설정해야 한다
```

```bash
# 환경 변수로도 지정할 수 있다 ('rr' 또는 'none')
NODE_CLUSTER_SCHED_POLICY=none node server.js
```

두 방식의 부하 편중 특성은 정반대 방향으로 어긋난다.

`SCHED_NONE`에서는 커널의 `accept` 경쟁이 공정하지 않다. 리눅스에서 여러 프로세스가 같은 소켓에 대기할 때 커널은 대기 큐의 마지막에 들어온 프로세스를 먼저 깨우는 LIFO 성향을 보인다. CPU 캐시 지역성 측면에서는 합리적인 선택이지만, 결과적으로 방금 일을 끝내 캐시가 따뜻한 워커가 다음 연결도 가져간다. 부하가 낮을 때는 워커 하나가 트래픽의 70~80%를 처리하고 나머지는 거의 놀며, 부하가 올라가야 비로소 분산되기 시작한다. 이 편중은 벤치마크에서 흔히 관측되며, 라운드 로빈이 기본값이 된 이유이기도 하다.

`SCHED_RR`은 연결을 정확히 균등하게 나눈다. 그러나 **연결을 나누는 것이지 부하를 나누는 것이 아니다.** 이 차이가 실무에서 문제가 되는 지점은 HTTP keep-alive다. 클라이언트가 연결 하나를 열어 그 위로 요청 1,000개를 보내면, 그 1,000개는 전부 같은 워커로 간다. 프론트에 리버스 프록시가 있고 프록시가 업스트림 연결을 풀링하고 있다면(26장 참조), 프록시가 유지하는 연결 여덟 개가 워커 여덟 개에 하나씩 배정된 뒤로는 라운드 로빈이 더 이상 개입할 여지가 없다. 요청의 무게가 제각각이면 워커별 CPU 사용률은 얼마든지 어긋난다.

`SCHED_RR`에는 비용도 있다. 모든 연결이 프라이머리를 한 번 거치고, 소켓 핸들이 IPC로 전달된다. 프라이머리는 애플리케이션 코드를 실행하지 않으니 대개 여유롭지만, 초당 수만 건의 짧은 연결이 들어오는 워크로드에서는 프라이머리의 이벤트 루프 자체가 상한선이 된다. 그런 경우에만 `SCHED_NONE`을 검토할 가치가 있다.

Node.js 22.12부터는 세 번째 선택지가 생겼다. 커널의 `SO_REUSEPORT`를 직접 쓰는 방식이다.

```js
// 프라이머리 없이 독립 프로세스들이 같은 포트를 공유한다 (Node.js 22.12+)
import http from 'node:http'

http.createServer(handler).listen({ port: 3000, reusePort: true })
```

`SO_REUSEPORT`는 커널이 각 리스닝 소켓마다 별도의 accept 큐를 두고, 들어오는 연결을 4-튜플 해시로 분배한다. `SCHED_NONE`의 깨어남 경쟁 문제도 없고 `SCHED_RR`의 프라이머리 병목도 없다. 무엇보다 프로세스들이 서로 부모-자식 관계일 필요가 없어서, 각 프로세스를 별개의 유닛으로 관리할 수 있다. 다만 리눅스 커널의 해시 분배는 여전히 연결 단위이므로 keep-alive 편중은 그대로다.

### 실무 관점

워커 수를 코어 수로 잡는 관행에는 함정이 있다. `os.cpus().length`는 호스트 머신의 논리 코어 수를 반환한다. 컨테이너 안에서 실행해도 마찬가지다. 64코어 노드에서 CPU 0.5개로 제한된 파드가 워커 64개를 띄우는 사고가 이렇게 난다(9장 참조).

Node.js 18.14부터 제공되는 `os.availableParallelism()`은 이보다 낫다. libuv가 리눅스에서 `sched_getaffinity`로 CPU 어피니티 마스크를 확인하므로, `taskset`이나 파드의 CPU 매니저가 코어를 고정 할당한 경우는 정확히 반영한다. 그러나 **cgroup의 CFS 쿼터는 보지 않는다.** 쿠버네티스의 `resources.limits.cpu: "2"`는 어피니티 마스크가 아니라 `cpu.max` 쿼터로 구현되는 것이 기본이므로, `availableParallelism()`은 여전히 64를 반환한다.

컨테이너에서는 쿼터를 직접 읽거나 오케스트레이터가 주입한 값을 쓰는 편이 안전하다.

```js
// cpu-count.js — cgroup v2 쿼터를 고려한 워커 수 결정
import { readFileSync } from 'node:fs'
import { availableParallelism } from 'node:os'

function cgroupCpuLimit() {
  try {
    // cgroup v2: "<quota> <period>" 또는 "max <period>"
    const raw = readFileSync('/sys/fs/cgroup/cpu.max', 'utf8').trim()
    const [quota, period] = raw.split(/\s+/)
    if (quota === 'max') return null // 제한 없음
    return Number(quota) / Number(period)
  } catch {
    return null // cgroup v1이거나 컨테이너가 아님
  }
}

export function workerCount() {
  // 명시적 설정이 최우선. 오케스트레이터에서 주입하는 것이 가장 확실하다.
  if (process.env.WEB_CONCURRENCY) {
    return Math.max(1, Number(process.env.WEB_CONCURRENCY))
  }
  const limit = cgroupCpuLimit()
  const cpus = limit ?? availableParallelism()
  // 소수 코어(0.5 등)에서도 최소 1개는 필요하다
  return Math.max(1, Math.floor(cpus))
}
```

코어 수와 워커 수를 1:1로 맞추는 것도 절대 규칙이 아니다. 순수 I/O 워크로드는 코어보다 조금 많게 잡아 대기 시간을 메울 수 있고, 반대로 프로세스마다 메모리가 큰 애플리케이션은 코어보다 적게 잡아야 한다(25.4 참조). CPU 쿼터가 1 이하라면 워커를 여러 개 띄우는 것은 순손해다. 컨텍스트 스위칭과 메모리만 늘고 병렬성은 전혀 늘지 않는다.

## 25.3 클러스터로 얻는 복원력과 무중단 재시작

### 왜 필요한가

`cluster`의 가치는 처리량만이 아니다. 프로세스가 여러 개라는 사실 자체가 두 가지 운영 능력을 만든다. 하나는 워커 하나가 죽어도 나머지가 트래픽을 계속 받는 복원력이고, 다른 하나는 워커를 하나씩 교체해 배포 중에도 서비스가 끊기지 않게 하는 무중단 재시작(zero-downtime restart)이다.

두 능력 모두 자동으로 얻어지지 않는다. 앞 절의 열 줄짜리 예제는 워커가 죽으면 그냥 워커 수가 줄어든다. 감시와 교체 로직을 직접 써야 한다.

### 어떻게 동작하는가

먼저 워커 쪽이다. 워커는 종료 신호를 받으면 **새 연결을 그만 받되 진행 중인 요청은 끝까지 처리하고** 나가야 한다. 이 부분이 빠지면 무중단 재시작을 아무리 정교하게 짜도 배포할 때마다 일정 비율의 요청이 실패한다.

```js
// worker.js
import http from 'node:http'

const server = http.createServer(async (req, res) => {
  await new Promise((r) => setTimeout(r, 50)) // 실제 작업을 흉내
  res.end(JSON.stringify({ pid: process.pid, url: req.url }))
})

// keep-alive 연결이 종료를 무한정 붙잡지 않도록 짧게 잡는다
server.keepAliveTimeout = 5_000
server.headersTimeout = 6_000

server.listen(process.env.PORT ?? 3000)

let shuttingDown = false

async function shutdown() {
  if (shuttingDown) return
  shuttingDown = true

  // 1) 새 연결 수락 중단. 콜백은 모든 연결이 닫힌 뒤에 호출된다.
  server.close(() => {
    closeResources().then(() => process.exit(0))
  })

  // 2) 요청 없이 대기 중인 keep-alive 연결은 즉시 끊는다 (Node.js 18.2+)
  server.closeIdleConnections()

  // 3) 유예 시간이 지나면 남은 연결을 강제로 끊는다
  const grace = Number(process.env.SHUTDOWN_GRACE_MS ?? 10_000)
  const timer = setTimeout(() => {
    server.closeAllConnections()
    closeResources().then(() => process.exit(0))
  }, grace)
  timer.unref() // 이 타이머 때문에 프로세스가 살아있지 않도록
}

async function closeResources() {
  // DB 풀, Redis 클라이언트, 큐 컨슈머 등을 여기서 정리한다
}

process.on('SIGTERM', shutdown)
// 프라이머리의 worker.disconnect() 는 워커에 'disconnect' 이벤트를 준다
process.on('disconnect', shutdown)
```

`closeIdleConnections()`가 핵심이다. `server.close()`는 리스닝 소켓만 닫을 뿐 이미 열린 keep-alive 연결은 건드리지 않으므로, 이 호출이 없으면 유휴 연결이 keep-alive 타임아웃까지 프로세스를 붙잡는다. 예전에는 이 동작을 직접 구현하느라 소켓을 전부 추적해야 했지만 지금은 표준 API로 해결된다.

이제 프라이머리다. 감시, 재시작 폭주 방지, 롤링 교체를 한 파일에 담는다.

```js
// primary.js
import cluster from 'node:cluster'
import { workerCount } from './cpu-count.js'

const DESIRED = workerCount()
const MIN_UPTIME_MS = 10_000    // 이 시간 안에 죽으면 '조기 사망'으로 본다
const MAX_CRASHES = 5           // 창(window) 안에서 허용할 조기 사망 횟수
const CRASH_WINDOW_MS = 60_000  // 조기 사망을 세는 창
const KILL_TIMEOUT_MS = 15_000  // graceful 종료를 기다리는 상한

const startedAt = new Map()     // worker.id -> 기동 시각
const crashes = []              // 최근 조기 사망 시각들
let restartDelay = 0            // 지수 백오프 현재값
let stopping = false

function fork() {
  const worker = cluster.fork()
  startedAt.set(worker.id, Date.now())
  return worker
}

// 워커가 실제로 포트를 잡았을 때 resolve 되는 프로미스
function forkAndWaitListening(timeoutMs = 30_000) {
  return new Promise((resolve, reject) => {
    const worker = fork()
    const timer = setTimeout(() => {
      cleanup()
      worker.kill('SIGKILL')
      reject(new Error(`worker ${worker.process.pid} listening 타임아웃`))
    }, timeoutMs)

    function onListening() { cleanup(); resolve(worker) }
    function onExit() { cleanup(); reject(new Error('워커가 기동 중 종료됨')) }
    function cleanup() {
      clearTimeout(timer)
      worker.off('listening', onListening)
      worker.off('exit', onExit)
    }

    worker.once('listening', onListening)
    worker.once('exit', onExit)
  })
}

cluster.on('exit', (worker, code, signal) => {
  const uptime = Date.now() - (startedAt.get(worker.id) ?? Date.now())
  startedAt.delete(worker.id)

  if (stopping || worker.exitedAfterDisconnect) {
    // 우리가 의도적으로 내린 워커다. 재시작하지 않는다.
    return
  }

  console.error(
    `worker ${worker.process.pid} 종료 (code=${code} signal=${signal} uptime=${uptime}ms)`
  )

  const now = Date.now()
  if (uptime < MIN_UPTIME_MS) {
    crashes.push(now)
    // 창 밖으로 나간 기록은 버린다
    while (crashes.length && now - crashes[0] > CRASH_WINDOW_MS) crashes.shift()

    if (crashes.length >= MAX_CRASHES) {
      // 재시작 폭주(crash loop). 계속 되살리는 것은 상황을 악화시킬 뿐이다.
      console.error('재시작 폭주 감지. 프라이머리를 종료한다.')
      stopping = true
      for (const w of Object.values(cluster.workers)) w.kill('SIGKILL')
      process.exit(1)
    }
    // 조기 사망일 때만 지수 백오프. 1s → 2s → 4s → 8s (상한 30s)
    restartDelay = Math.min(restartDelay ? restartDelay * 2 : 1_000, 30_000)
  } else {
    // 오래 살다 죽었다면 일시적 장애로 보고 백오프를 초기화한다
    restartDelay = 0
  }

  setTimeout(fork, restartDelay).unref()
})

for (let i = 0; i < DESIRED; i++) fork()
```

재시작 폭주 방지는 생략되기 쉬운데, 없으면 가장 나쁜 방식으로 실패한다. 설정 오류나 DB 접속 실패로 워커가 기동 직후 죽는 상황에서 무조건 재시작하면 프라이머리는 초당 수백 번 `fork()`를 호출한다. CPU가 포화되고 로그가 폭증하며, 재시도 트래픽이 이미 아픈 의존 서비스를 더 때린다. 위 코드는 두 겹으로 막는다. 조기 사망에만 지수 백오프를 걸고, 창 안에서 임계치를 넘으면 되살리기를 포기하고 프라이머리 자신이 0이 아닌 코드로 죽는다. 마지막 동작이 중요하다. 컨테이너 환경에서 프라이머리가 죽으면 오케스트레이터가 파드를 재생성하며 백오프를 적용하고, 실패 상태가 헬스 체크에 정직하게 드러난다. 반쯤 죽은 채로 살아있는 프로세스가 가장 다루기 어렵다.

`worker.exitedAfterDisconnect` 검사도 빠뜨리면 안 된다. 이 플래그가 참이면 우리가 `disconnect()`나 `kill()`로 의도적으로 내린 워커라는 뜻이다. 이 검사가 없으면 롤링 재시작으로 내린 워커를 감시 코드가 즉시 되살려 워커 수가 계속 늘어난다.

이제 롤링 재시작이다. 규칙은 하나다. **새 워커가 실제로 `listening` 상태가 된 뒤에야 헌 워커를 내린다.** 순서를 뒤집으면 그 순간 용량이 부족해지고, 최악의 경우 살아있는 워커가 0이 되는 창이 생긴다.

```js
// primary.js (계속) — 롤링 재시작
let reloading = false

async function rollingRestart() {
  if (reloading) return
  reloading = true
  try {
    const olds = Object.values(cluster.workers)
    console.log(`롤링 재시작 시작: 교체 대상 ${olds.length}개`)

    for (const old of olds) {
      // 1) 먼저 새 워커를 띄우고 포트를 잡을 때까지 기다린다
      const fresh = await forkAndWaitListening()
      console.log(`  새 워커 ${fresh.process.pid} 준비 완료`)

      // 2) 그다음에 헌 워커를 내린다
      await retire(old)
      console.log(`  헌 워커 ${old.process.pid} 정리 완료`)
    }
    console.log('롤링 재시작 완료')
  } catch (err) {
    // 새 워커가 뜨지 못했다면 헌 워커를 그대로 두는 것이 옳다.
    console.error('롤링 재시작 중단:', err.message)
  } finally {
    reloading = false
  }
}

function retire(worker) {
  return new Promise((resolve) => {
    if (worker.isDead()) return resolve()

    const timer = setTimeout(() => {
      console.warn(`  worker ${worker.process.pid} 유예 초과. SIGKILL.`)
      worker.process.kill('SIGKILL')
    }, KILL_TIMEOUT_MS)

    worker.once('exit', () => { clearTimeout(timer); resolve() })

    // disconnect()는 IPC 채널을 닫고 워커의 서버를 닫게 한다.
    // 워커의 'disconnect' 핸들러가 graceful shutdown을 수행한다.
    worker.disconnect()
  })
}

process.on('SIGHUP', rollingRestart)

// 프라이머리 자신의 graceful 종료
process.on('SIGTERM', async () => {
  stopping = true
  await Promise.all(Object.values(cluster.workers).map(retire))
  process.exit(0)
})
```

`kill -HUP <프라이머리 PID>`로 재시작을 트리거하는 것은 nginx를 비롯한 유닉스 데몬의 오랜 관습이다. 새 코드를 배포한 뒤 이 신호 하나로 워커가 하나씩 교체된다.

여기에는 한 가지 중요한 제약이 있다. 프라이머리 프로세스는 **재시작되지 않는다.** `cluster.fork()`는 프라이머리가 처음 로드한 스크립트를 다시 실행하므로 워커 코드는 새로 읽히지만, 프라이머리 자신의 코드와 이미 로드된 모듈은 그대로다. `primary.js`를 고쳤거나 Node.js 버전을 올렸다면 롤링 재시작으로는 반영되지 않는다. 그래서 프라이머리 코드는 최대한 얇게 유지하고, 프로세스 전체 교체는 로드 밸런서 수준에서 처리하는 것이 맞다.

### 실무 관점

무중단이라는 말은 과장이기 쉽다. 위 구현으로도 다음은 여전히 발생한다.

첫째, `SCHED_RR`에서 헌 워커에 붙어 있던 keep-alive 연결은 끊어진다. HTTP/1.1 클라이언트는 유휴 연결이 끊기면 조용히 재연결하므로 대개 문제가 없지만, 요청 전송 중에 끊기면 실패로 보인다. `closeIdleConnections()`를 먼저 부르는 이유가 이 창을 최소화하기 위해서다.

둘째, 롤링 중에는 헌 코드와 새 코드가 동시에 돌아간다. 응답 스키마를 바꾸는 배포라면 두 버전이 공존해도 안전한지 먼저 확인해야 한다. 데이터베이스 마이그레이션이라면 확장-축소(expand-contract) 패턴으로 나눠서 배포한다.

셋째, 유예 시간이 실제 최장 요청 시간보다 짧으면 그 요청은 잘린다. 파일 업로드나 리포트 생성처럼 오래 걸리는 엔드포인트가 있다면 유예 시간을 그에 맞추거나, 그런 작업을 애초에 워커 큐로 빼야 한다(9장 참조).

## 25.4 `cluster`의 한계

앞 절까지 읽으면 `cluster`가 만능처럼 보인다. 이 절은 반대편을 본다. 실무에서 `cluster`를 걷어내는 결정은 도입하는 결정만큼 흔하다.

**메모리가 워커 수만큼 곱해진다.** 각 워커는 독립된 V8 인스턴스다. 힙, 코드 캐시, 로드된 모듈 그래프가 전부 복제된다. `fork()`는 리눅스의 copy-on-write를 쓰지만 Node.js에서는 거의 도움이 안 된다. V8이 힙 페이지에 계속 쓰기를 하고(GC의 마크 비트만으로도 페이지가 더러워진다) `cluster.fork()`는 사실 `fork(2)`가 아니라 새 프로세스를 `exec`하는 `child_process.fork()`이기 때문이다. 애플리케이션이 워커당 300MB를 쓴다면 워커 8개는 2.4GB다. 16코어 장비에서 코어 수만큼 워커를 띄웠다가 OOM으로 죽는 경우가 드물지 않다. 워커 수는 코어 수와 `(가용 메모리 / 워커당 RSS)` 중 **작은 쪽**으로 정해야 한다.

**인프로세스 캐시가 워커마다 분리된다.** 이것이 메모리 곱셈보다 더 자주 문제가 된다. 워커 8개가 각자 1,000개짜리 LRU 캐시를 들고 있으면, 메모리는 8배를 쓰면서 캐시 적중률은 1,000개짜리 캐시 하나만도 못하다. 요청이 라운드 로빈으로 흩어지므로 같은 키를 여덟 번 각각 미스하고 여덟 번 원본을 조회한다. 게다가 캐시 무효화가 지옥이 된다. 워커 A가 데이터를 갱신해도 워커 B~H는 낡은 값을 계속 반환한다. 이 문제를 IPC 브로드캐스트로 풀려는 시도가 종종 보이는데, 정합성 문제를 프로세스 간 메시징으로 옮길 뿐 근본 해법이 아니다. 인프로세스 캐시가 중요한 애플리케이션이라면 캐시를 외부화(Redis)하거나, 워커 수를 줄이고 프로세스당 캐시를 크게 잡는 편이 낫다.

**컨테이너 환경에서 오케스트레이터와 역할이 겹친다.** 쿠버네티스는 이미 프로세스 복제, 헬스 체크 기반 재시작, 롤링 업데이트, 오토스케일링을 전부 제공한다(32장 참조). 그 위에 `cluster`를 얹으면 같은 일을 하는 계층이 둘이 된다. 파드 하나에 워커 8개를 띄우면 HPA가 보는 CPU 지표는 8개의 평균이 되어 개별 워커의 포화를 가린다. 워커 하나가 무한 루프에 빠져도 파드의 readiness probe는 다른 워커가 응답해 통과시킨다. 스케일링 단위가 8워커 뭉치가 되어 세밀한 조정도 어려워진다.

**디버깅과 프로파일링이 어려워진다.** `--inspect`로 클러스터를 띄우면 워커마다 디버그 포트가 필요해 Node.js가 자동으로 포트를 증가시키는데, 어느 포트가 어느 워커인지 매번 확인해야 한다. CPU 프로파일과 힙 스냅숏은 프로세스 단위로 나오므로 여덟 개를 따로 뜨고 사람이 머릿속에서 합쳐야 한다. 특히 "가끔 느린 요청"을 추적할 때 그 요청이 어느 워커로 갔는지부터 알아내야 하므로, 모든 로그에 `process.pid`를 넣는 것이 사실상 필수가 된다. 로컬에서 재현이 안 되는 문제의 상당수가 여기서 시간을 잡아먹는다.

**프라이머리가 단일 장애점이다.** `SCHED_RR`에서는 모든 연결이 프라이머리를 통과한다. 프라이머리가 죽으면 워커가 멀쩡해도 새 연결을 받지 못한다. 프라이머리 코드에 실수로 동기 작업을 넣으면(예: 워커에서 올라온 메트릭을 프라이머리에서 집계하며 JSON을 파싱하는 코드) 그 순간 모든 워커가 굶는다. 프라이머리에서는 애플리케이션 로직을 절대 실행하지 않는다는 규율이 필요하다.

정리하면 `cluster`가 적합한 곳은 **한 대의 큰 머신에 직접 배포하는 환경**, 컨테이너를 쓰더라도 **파드에 CPU를 여러 개 할당하고 파드 수를 늘리는 비용이 비싼 환경**, 그리고 **로컬 개발에서 병렬성을 흉내 내야 할 때**다. 파드 하나에 CPU 1 이하를 주고 파드 수로 확장하는 표준적인 쿠버네티스 배포에서 `cluster`는 얻는 것 없이 복잡도만 더한다.

## 25.5 상태 있는 통신 다루기: 상태 공유와 스티키 로드 밸런싱

### 왜 필요한가

X축 확장의 전제는 "어떤 인스턴스가 처리해도 결과가 같다"였다. 상태를 프로세스 메모리에 두는 순간 이 전제가 깨진다(17장 참조).

전형적인 코드를 보자.

```js
// 인스턴스가 하나일 때만 옳은 코드
const sessions = new Map() // ← 이 프로세스의 메모리에만 존재한다

app.post('/login', (req, res) => {
  const sid = randomUUID()
  sessions.set(sid, { userId: req.body.userId, cart: [] })
  res.setHeader('Set-Cookie', `sid=${sid}; HttpOnly`)
  res.end()
})

app.get('/cart', (req, res) => {
  const s = sessions.get(parseCookie(req).sid)
  if (!s) return res.status(401).end() // 다른 인스턴스로 가면 여기로 온다
  res.json(s.cart)
})
```

워커가 넷이면 로그인은 워커 1에서 되고 장바구니 조회는 워커 3으로 간다. 사용자는 로그인이 무작위로 풀리는 것처럼 느낀다. 확장하기 전에는 아무 문제 없던 코드가 워커를 늘리는 순간 25%의 확률로만 동작한다.

해법은 두 갈래다. 상태를 밖으로 빼거나, 요청을 상태가 있는 곳으로 보내거나.

### 어떻게 동작하는가

**상태 공유(외부 저장소).** 세션을 Redis 같은 공유 저장소로 옮긴다. 모든 인스턴스가 같은 데이터를 보므로 어느 인스턴스가 처리해도 결과가 같다. 애플리케이션은 다시 무상태가 된다.

```js
import { createClient } from 'redis'
const redis = createClient({ url: process.env.REDIS_URL })
await redis.connect()

const TTL_SECONDS = 30 * 60

async function loadSession(sid) {
  const raw = await redis.get(`sess:${sid}`)
  return raw ? JSON.parse(raw) : null
}

async function saveSession(sid, data) {
  // 접근할 때마다 TTL을 갱신해 활성 세션이 만료되지 않게 한다
  await redis.set(`sess:${sid}`, JSON.stringify(data), { EX: TTL_SECONDS })
}
```

대가는 명확하다. 요청마다 네트워크 왕복이 하나 늘고, Redis가 새로운 단일 장애점이 되며, 세션 데이터의 동시 갱신 문제가 생긴다(19장 참조). 그러나 이 비용은 예측 가능하고 운영 도구가 성숙해 있다.

세션이 인증 정보뿐이라면 저장소조차 필요 없다. 서명된 토큰(JWT)에 담아 클라이언트가 들고 다니게 하면 상태 자체가 사라진다. 대신 토큰을 즉시 무효화할 수 없으므로, 만료를 짧게 잡고 갱신 토큰을 저장소에 두는 절충이 일반적이다.

**스티키 로드 밸런싱.** 반대 방향의 해법이다. 같은 클라이언트의 요청을 항상 같은 인스턴스로 보내 메모리의 상태를 그대로 쓴다. 구현은 두 층에서 가능하다. L4에서 출발지 IP를 해시하거나, L7에서 쿠키를 심는다.

```nginx
upstream app {
    # L4 방식: 출발지 IP 해시. 클라이언트가 NAT 뒤에 있으면 편중이 심하다.
    # ip_hash;

    # L7 방식: 밸런서가 쿠키를 심어 인스턴스를 기억한다 (nginx plus / haproxy)
    sticky cookie srv_id expires=1h httponly;

    server app1:3000;
    server app2:3000;
    server app3:3000;
}
```

`cluster` 안에서 스티키를 구현하려면 라운드 로빈을 끄고 프라이머리가 직접 분배해야 한다. 실제로 `socket.io`의 클러스터 배포에서 오래 쓰인 방식이지만, 프라이머리에 커스텀 분배 로직이 들어가는 순간 25.4에서 지적한 단일 장애점 문제가 커진다.

웹소켓(WebSocket)은 상황이 조금 다르다. 연결 자체가 특정 인스턴스에 물리적으로 묶이므로 스티키는 선택이 아니라 물리적 사실이다. 여기서 진짜 문제는 라우팅이 아니라 **팬아웃(fan-out)**이다. 인스턴스 A에 붙은 사용자가 보낸 메시지를 인스턴스 B에 붙은 사용자에게 전달해야 한다. 답은 스티키가 아니라 인스턴스 간 메시지 버스다.

```js
// Redis pub/sub 으로 인스턴스 경계를 넘는 브로드캐스트
const sub = redis.duplicate()
await sub.connect()
await sub.subscribe('room:general', (raw) => {
  const msg = JSON.parse(raw)
  // 이 인스턴스에 붙어 있는 소켓에만 전달한다
  for (const ws of localSockets) ws.send(msg.text)
})

async function publish(text) {
  await redis.publish('room:general', JSON.stringify({ text }))
}
```

### 실무 관점

스티키 세션은 "코드를 안 고쳐도 된다"는 이유로 선택되지만, 확장 관점에서 지불하는 비용이 크다.

**부하가 균등해지지 않는다.** 밸런서는 연결이나 클라이언트를 나눌 뿐 부하를 나누지 못한다. 헤비 유저가 우연히 같은 인스턴스에 몰리면 그 인스턴스만 포화된다. 출발지 IP 해시는 특히 취약하다. 회사망이나 모바일 캐리어 NAT 뒤의 수천 명이 하나의 IP로 보이면 통째로 한 인스턴스에 붙는다.

**배포할 때 대량 재연결이 발생한다.** 인스턴스를 하나 내리면 거기 붙어 있던 모든 클라이언트가 동시에 끊기고 동시에 재연결을 시도한다. 웹소켓 애플리케이션에서 이 재연결 폭풍은 남은 인스턴스를 무너뜨릴 수 있고, 무너지면 다시 대량 재연결이 발생하는 악순환에 들어간다. 클라이언트에 지수 백오프와 지터(jitter)를 반드시 넣어야 하는 이유다.

**오토스케일링이 듣지 않는다.** 부하가 올라 인스턴스를 두 배로 늘려도, 기존 클라이언트는 이미 붙은 인스턴스에 그대로 남는다. 새 인스턴스는 신규 연결만 받으므로 한동안 놀고, 과부하 인스턴스는 계속 과부하다. 리밸런싱을 하려면 결국 연결을 강제로 끊어야 하고, 그러면 위의 재연결 문제로 돌아온다.

**장애 시 상태가 사라진다.** 인스턴스가 죽으면 거기 있던 세션이 통째로 증발한다. 스티키는 상태를 지켜주지 않는다. 라우팅만 고정할 뿐이다.

결론은 명확하다. **가능하면 무상태로 만든다.** 상태를 외부 저장소로 빼는 비용은 요청당 1~2ms 수준이고, 그 대가로 인스턴스를 자유롭게 늘리고 줄이고 죽이고 되살릴 수 있다. 스티키는 그 자체로 목적이 아니라, 웹소켓처럼 연결이 물리적으로 묶이는 경우나 인스턴스별 로컬 캐시의 적중률이 결정적인 경우에만 쓰는 최적화다. 그때조차 상태는 외부에 두고 로컬에는 캐시만 두어, 어느 인스턴스가 죽어도 데이터가 사라지지 않게 설계한다.

## 25.6 프로세스 매니저와 컨테이너 오케스트레이터 중 무엇을 쓸 것인가

### 왜 필요한가

PM2 같은 프로세스 매니저는 클러스터 모드, 자동 재시작, 무중단 리로드, 로그 수집, 모니터링을 한 줄로 제공한다.

```bash
pm2 start app.js -i max          # 코어 수만큼 클러스터 모드로 기동
pm2 reload app                    # 무중단 롤링 재시작
pm2 logs && pm2 monit             # 로그 취합과 실시간 모니터링
```

쿠버네티스도 정확히 같은 목록을 제공한다. 레플리카 수로 프로세스를 복제하고, liveness probe로 재시작하고, 롤링 업데이트로 무중단 배포하고, 로그와 메트릭을 수집한다(32장 참조). 두 계층을 겹쳐 쓰면 같은 일을 두 번 하는 것이고, 두 번 하는 것으로 끝나지 않고 서로 방해한다.

### 어떻게 동작하는가

겹쳤을 때 구체적으로 무엇이 깨지는지가 판단의 근거다.

**신호가 제대로 전달되지 않는다.** 쿠버네티스가 파드를 내릴 때 PID 1에게 `SIGTERM`을 보낸다. 컨테이너의 PID 1이 프로세스 매니저라면, 그 매니저가 신호를 자식에게 정확히 전파하고 자식이 다 나갈 때까지 기다려야 한다. 전파가 부실하면 애플리케이션은 유예 시간 없이 `SIGKILL`로 죽고, 진행 중이던 요청이 잘린다. 셸을 거쳐 실행하면(`CMD npm start`) 셸이 PID 1이 되어 신호를 전혀 전달하지 않는 고전적인 함정도 여기 붙는다.

**헬스 체크의 해상도가 떨어진다.** 파드 안에 워커가 8개면 readiness probe는 그중 아무나 응답하면 통과한다. 워커 세 개가 이벤트 루프 블로킹으로 멈춰 있어도 파드는 건강한 것으로 보고되고 계속 트래픽을 받는다. 프로세스 하나에 컨테이너 하나면 그 프로세스가 멈추는 즉시 파드가 트래픽에서 빠진다.

**자원 회계가 흐려진다.** 컨테이너 메트릭은 컨테이너 단위로 나온다. 워커 8개의 CPU와 메모리가 하나의 숫자로 합쳐지면, 메모리 누수가 있는 워커 하나를 지목할 수 없고 HPA가 보는 평균은 개별 포화를 감춘다. 메모리 제한도 마찬가지다. 파드에 2GB를 주고 워커 8개를 띄우면 워커 하나가 폭주해 파드 전체가 OOM킬 당한다.

**재시작 정책이 이중으로 걸린다.** 프로세스 매니저가 죽은 워커를 되살리는 동안 쿠버네티스는 파드가 건강하다고 판단한다. 실패가 오케스트레이터에게 보이지 않으므로 백오프도, 이벤트 기록도, 알람도 동작하지 않는다.

이래서 "컨테이너 하나에 프로세스 하나"가 원칙이 된다. 컨테이너를 프로세스의 격리 단위로 보면 자연스러운 결론이다.

```dockerfile
# 프로세스 매니저 없이 애플리케이션을 PID 1로 실행한다
FROM node:22-slim
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
USER node
# exec 형식(JSON 배열)이어야 셸이 끼어들지 않고 node가 PID 1이 된다
CMD ["node", "server.js"]
```

Node.js가 PID 1이 되면 좀비 프로세스 수거 책임이 생긴다. 애플리케이션이 자식 프로세스를 만든다면 `--init` 플래그나 `tini` 같은 최소 init을 쓴다. 이것은 프로세스 매니저를 다시 들이는 것과 다르다. init은 신호 전달과 좀비 수거만 하고 재시작이나 복제를 하지 않는다.

원칙에는 예외가 있다. **파드에 CPU를 2개 이상 할당하는 것이 유리한 경우**다. 서비스 메시 사이드카나 로그 수집기가 파드마다 붙는 환경에서는 파드 수를 늘릴수록 사이드카 오버헤드가 선형으로 늘어난다. CPU 4개짜리 파드 하나에 워커 4개가, CPU 1개짜리 파드 4개보다 총 자원을 적게 쓰는 지점이 생긴다. 또한 파드 기동 시간이 길거나(JIT 워밍업, 대용량 캐시 로드) 노드당 파드 수 상한에 걸리는 대규모 클러스터에서도 파드 하나에 프로세스를 여럿 두는 선택이 합리적일 수 있다. 이 경우에도 프로세스 매니저를 쓰기보다 Node.js 내장 `cluster`로 얇은 프라이머리를 두는 편이 낫다. 의존성이 하나 줄고, 신호 처리와 종료 로직을 직접 통제할 수 있기 때문이다.

### 실무 관점

결정 트리는 다음과 같다.

```text
컨테이너 오케스트레이터(쿠버네티스 등)를 쓰는가?
├─ 아니오
│   └─ 배포 대상이 한 대의 서버인가?
│       ├─ 예 → 프로세스 매니저(PM2, systemd)를 쓴다.
│       │        systemd는 이미 있고 신호 처리가 견고하다.
│       │        여러 프로세스가 필요하면 systemd 템플릿 유닛 +
│       │        reusePort, 또는 PM2 클러스터 모드.
│       └─ 아니오 → 여러 대라면 앞단 로드 밸런서 + 서버별 프로세스 매니저.
│                   이 조합이 무거워지는 시점이 오케스트레이터 도입 시점이다.
└─ 예
    └─ 파드에 할당하는 CPU 제한이 1 이하인가?
        ├─ 예 → 프로세스 하나, 컨테이너 하나. cluster도 PM2도 쓰지 않는다.
        │        확장은 레플리카 수로 한다. (대다수의 경우가 여기다)
        └─ 아니오 (CPU 2 이상)
            └─ 워커당 메모리 × 워커 수가 파드 메모리 제한에 들어가는가?
                ├─ 아니오 → 워커 수를 메모리 기준으로 줄이거나,
                │            파드를 작게 쪼개고 레플리카를 늘린다.
                └─ 예 → cluster로 CPU 제한만큼 워커를 띄운다.
                         프라이머리는 얇게. 재시작 폭주 시 프라이머리가 죽어
                         오케스트레이터에 실패를 노출하도록 한다.
```

한 가지 더 있다. 개발 환경에서 PM2를 쓰는 것과 프로덕션에서 쓰는 것은 다른 결정이다. `pm2 monit`이나 `pm2 logs`는 서버에 직접 접속해 상태를 볼 때 유용하지만, 오케스트레이터 환경에서는 로그를 stdout으로 흘려보내고 수집기가 가져가는 것이 표준이다(31장 참조). 애플리케이션이 로그 파일을 쓰거나 로테이션을 신경 쓰고 있다면 그 자체가 배포 모델과 어긋나 있다는 신호다.

## 요약

- 확장은 세 축으로 분해된다. X축은 복제, Y축은 기능 분해, Z축은 데이터 분할이다. 처리량 부족은 X축, 컴포넌트 간 요구사항 충돌은 Y축, 데이터 크기와 쓰기 병목은 Z축의 문제다. 거의 모든 시스템은 X축을 끝까지 밀어붙인 뒤에 나머지를 검토해야 한다.
- `cluster`는 프라이머리가 리스닝 소켓을 소유하는 방식으로 포트 공유를 해결한다. `SCHED_NONE`은 소켓 핸들을 워커에 넘겨 커널의 accept 경쟁에 맡기므로 부하가 편중되고, 기본값인 `SCHED_RR`은 프라이머리가 연결을 균등 분배하지만 keep-alive 때문에 연결 균등이 부하 균등을 뜻하지는 않는다.
- 워커 수를 `os.cpus().length`로 정하면 컨테이너에서 호스트 코어 수를 보게 된다. `availableParallelism()`도 cgroup CPU 쿼터는 반영하지 않으므로, 쿼터를 직접 읽거나 오케스트레이터가 주입한 값을 쓴다.
- 무중단 재시작의 규칙은 하나다. 새 워커가 `listening`이 된 뒤에 헌 워커를 내린다. 워커 쪽에서는 `server.close()`와 `closeIdleConnections()`로 진행 중인 요청을 마치고, 프라이머리 쪽에서는 `exitedAfterDisconnect`로 의도적 종료와 장애를 구분한다.
- 재시작 폭주 방지는 필수다. 조기 사망에 지수 백오프를 걸고, 임계치를 넘으면 되살리기를 포기하고 프라이머리가 죽어 실패를 오케스트레이터에 노출한다.
- `cluster`의 대가는 메모리 곱셈, 인프로세스 캐시 분리로 인한 적중률 하락과 무효화 문제, 오케스트레이터와의 역할 중복, 프로파일링 난이도, 프라이머리라는 단일 장애점이다.
- 상태 있는 통신은 외부 저장소로 상태를 빼는 것이 기본이다. 스티키 로드 밸런싱은 부하 불균형, 배포 시 재연결 폭풍, 오토스케일링 무력화를 대가로 지불하므로 웹소켓처럼 연결이 물리적으로 묶이는 경우에만 쓴다.
- 오케스트레이터 환경에서는 컨테이너 하나에 프로세스 하나가 기본이다. 파드 CPU 제한이 2 이상이고 사이드카 오버헤드나 기동 비용이 큰 경우에만 `cluster`를 얹되, 프로세스 매니저를 추가로 들이지는 않는다.

## 연습문제

1. 워커 4개짜리 클러스터를 `SCHED_RR`과 `SCHED_NONE`으로 각각 띄우고, 워커별 처리 요청 수를 집계하도록 계측하라. `autocannon`으로 (a) keep-alive를 끄고 동시성 100, (b) keep-alive를 켜고 커넥션 4개, (c) keep-alive를 켜고 커넥션 200으로 부하를 준다. 여섯 가지 조합의 분포를 표로 만들고, 세 워크로드에서 두 정책의 우열이 어떻게 뒤집히는지 설명하라. 여유가 있다면 `reusePort: true`로 띄운 독립 프로세스 4개를 같은 조건에서 비교해 세 번째 열을 채워라.

2. 25.3의 프라이머리와 워커 코드를 완성한 뒤 다음 세 상황을 재현하고, 각각에서 실패한 요청 수를 측정하라. (a) 부하를 주는 중에 `SIGHUP`으로 롤링 재시작, (b) 워커 코드에 `closeIdleConnections()` 호출을 제거한 뒤 같은 실험, (c) 워커의 핸들러가 30초 걸리도록 만든 뒤 유예 시간 10초로 롤링 재시작. (b)와 (c)에서 발생한 실패의 원인이 서로 어떻게 다른지 서술하라.

3. 인메모리 LRU 캐시(용량 1,000)를 쓰는 API를 만들고, 지프(Zipf) 분포로 10,000개 키를 조회하는 부하를 준다. 단일 프로세스일 때와 워커 8개일 때의 전체 캐시 적중률과 백엔드 조회 횟수를 측정하라. 그다음 캐시를 Redis로 옮겨 같은 실험을 반복하고, 적중률·응답 지연·총 메모리 사용량 세 지표의 트레이드오프를 정리하라. 워커 8개에서 캐시 용량을 125(=1000/8)로 줄이면 무슨 일이 일어나는지도 함께 측정하라.
