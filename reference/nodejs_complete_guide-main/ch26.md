# 26장. 리버스 프록시와 로드 밸런싱

25장에서 한 대의 머신 안에서 프로세스를 늘리는 방법을 다뤘다면, 이 장은 그 프로세스들 앞에 무엇을 세울 것인가를 다룬다. 인스턴스가 둘 이상이 되는 순간 "요청을 누구에게 보낼 것인가"라는 질문이 생기고, 그 질문에 답하는 계층이 리버스 프록시(reverse proxy)다.

리버스 프록시는 단순한 분배기가 아니다. TLS 종료, 압축, 정적 파일 서빙, 레이트 리미팅, 느린 클라이언트 흡수 같은 일들이 이 계층으로 올라가면 Node.js 프로세스는 비즈니스 로직만 남기고 훨씬 가벼워진다. 이 장에서는 HAProxy와 Nginx로 같은 일을 두 번 해보면서 각자의 성격을 비교하고, 인스턴스가 뜨고 지는 환경에서 정적 설정이 무너지는 지점과 그 해법까지 나아간다.

## 26.1 정방향 프록시와 역방향 프록시

### 방향이 다르다

두 프록시는 이름이 비슷하지만 서 있는 위치가 정반대다. 정방향 프록시(forward proxy)는 클라이언트 쪽에 서서 클라이언트를 대신해 임의의 서버로 나간다. 사내망에서 외부 인터넷 접근을 통제하는 게이트웨이, 개발 머신에서 HTTPS 트래픽을 가로채 검사하는 디버깅 프록시가 여기 속한다. 핵심은 클라이언트가 프록시의 존재를 알고 명시적으로 설정한다는 점이다. `HTTPS_PROXY` 환경 변수를 읽어 요청을 그쪽으로 보내는 코드가 바로 정방향 프록시와의 계약이다. 프록시는 자기가 대신하는 클라이언트가 누구인지 알지만, 앞으로 어떤 서버로 가게 될지는 요청이 오기 전까지 모른다.

역방향 프록시(reverse proxy)는 서버 쪽에 서서 서버를 대신해 클라이언트를 맞는다. 클라이언트는 프록시의 존재를 모른다. `api.example.com`에 접속했다고 믿을 뿐, 그 뒤에 Node.js 인스턴스가 여덟 개 있는지 하나 있는지 알 방법이 없다. 프록시는 뒤에 있는 서버 집합(backend)을 미리 알고 있고, 대신 앞에서 들어오는 클라이언트가 누구일지는 모른다. 정방향 프록시가 "나가는 쪽의 미지"를 다룬다면 역방향 프록시는 "들어오는 쪽의 미지"를 다룬다.

이 장에서 다루는 것은 전적으로 역방향 프록시다. 앞으로 "프록시"라고만 쓰면 역방향 프록시를 뜻한다.

### 프록시가 애플리케이션에서 덜어내는 것

프록시를 세우는 이유를 로드 밸런싱 하나로만 이해하면 절반만 쓰는 것이다. 실제로 프록시가 가져가는 책임은 다음과 같다.

**TLS 종료(TLS termination).** 인증서 관리와 핸드셰이크 연산이 전부 프록시로 간다. 애플리케이션은 평문 HTTP만 다룬다.

**압축.** gzip이나 브로틀리(Brotli) 인코딩은 응답 크기에 비례하는 CPU 작업이다. 프록시가 하면 애플리케이션 프로세스의 CPU 예산에서 빠진다.

**정적 파일 서빙.** 이미지, 번들된 JS, 폰트는 디스크에서 읽어 소켓으로 밀어넣는 일이 전부다. Nginx는 이 경로에서 `sendfile(2)`로 커널 안에서 복사를 끝내지만, Node.js는 파일 내용을 유저 공간 버퍼로 올렸다가 다시 내려보낸다.

**레이트 리미팅.** 악의적인 트래픽을 애플리케이션에 도달하기 전에 끊는다. 애플리케이션에서 거절하려면 이미 요청 파싱, 라우팅, 미들웨어 체인을 통과한 뒤다.

**느린 클라이언트 흡수.** 이것이 가장 과소평가되는 항목이다. 모바일 네트워크의 클라이언트가 요청 바디를 30초에 걸쳐 조금씩 보낸다고 하자. Node.js가 직접 그 소켓을 잡고 있으면 소켓 하나, `IncomingMessage` 객체 하나, 그리고 그 요청을 기다리는 핸들러의 클로저가 30초 동안 메모리에 머문다. 프록시를 앞에 두면 프록시가 요청 전체를 버퍼링해 완성된 뒤에야 백엔드로 넘긴다. 백엔드가 그 요청을 붙잡고 있는 시간은 밀리초 단위로 줄어든다. 응답 방향도 마찬가지다. 프록시가 응답을 다 받아 자기 버퍼에 넣고 느린 클라이언트에게 천천히 흘려보내는 동안, Node.js 쪽 연결은 이미 닫혀 있다. 슬로로리스(Slowloris) 류의 공격이 Node.js 앞에 프록시를 둔 구성에서 잘 통하지 않는 이유가 여기 있다.

### Node.js가 할 수 있다고 해서 해야 하는 것은 아니다

위의 모든 일은 Node.js로도 할 수 있다. `https.createServer`로 TLS를 받을 수 있고, `compression` 미들웨어로 gzip을 걸 수 있으며, `express.static`으로 파일을 서빙할 수 있다. 그럼에도 프로덕션에서 이 일들을 프록시로 옮기는 데는 세 가지 근거가 있다.

첫째, **이벤트 루프의 성격**이다. TLS 핸드셰이크의 비대칭 암호 연산과 gzip 압축은 CPU 바운드 작업이다. Node.js의 `zlib`는 libuv 스레드풀에서 돌지만 기본 스레드는 넷뿐이고, 이 풀은 `fs` 연산, DNS 조회, `crypto.pbkdf2`와 공유된다. 큰 응답 몇 개를 동시에 압축하면 스레드풀이 포화되고, 그 순간 애플리케이션의 파일 읽기와 DNS 조회까지 함께 밀린다. 압축 자체는 비동기지만 그 대가는 시스템 전체가 나눠 낸다. TLS 핸드셰이크는 더 나쁘다. 이쪽은 스레드풀도 아니고 상당 부분이 메인 스레드에서 처리되므로 접속 폭주 시 이벤트 루프 지연에 그대로 나타난다.

둘째, **구현의 성숙도**다. HAProxy와 Nginx는 20년 넘게 이 한 가지 일만 해온 C 프로그램이다. `sendfile`, `splice`, TCP 패스트 오픈, 커널 TLS 오프로드처럼 Node.js 표준 라이브러리가 노출하지 않는 시스템 콜을 쓴다. HTTP 요청 스머글링, 헤더 인젝션, 청크 인코딩 파싱 같은 프로토콜 수준 공격에 대해서도 훨씬 긴 감사 이력을 갖는다.

셋째, **수명 주기의 분리**다. 애플리케이션은 하루에도 몇 번씩 배포되고 재시작한다. TLS 인증서와 레이트 리밋 규칙이 애플리케이션 코드 안에 있으면 이 둘의 변경 주기가 강제로 묶인다. 인증서 갱신 때문에 애플리케이션을 배포해야 하고, 애플리케이션 배포 실수 하나로 인증서 설정이 날아갈 수 있다. 프록시로 옮기면 두 계층이 독립적으로 바뀐다.

원칙은 이렇게 정리된다. **프로토콜과 전송에 관한 일은 프록시로, 도메인과 상태에 관한 일은 애플리케이션으로 보낸다.** 이 경계선은 뒤에서 레이트 리미팅을 다룰 때 다시 등장한다(26.5).

## 26.2 HAProxy 입문: 로드 밸런싱과 헬스 체크

### 최소 설정에서 시작하기

HAProxy는 설정 파일 하나로 동작한다. 백엔드로 쓸 Node.js 서버를 먼저 준비하자. 어느 인스턴스가 응답했는지 확인할 수 있게 포트를 응답에 실었다.

```js
// server.js — PORT 환경변수로 여러 개 띄운다
import { createServer } from 'node:http'

const PORT = Number(process.env.PORT ?? 3000)
let healthy = true

const server = createServer((req, res) => {
  if (req.url === '/health') {
    // 헬스 체크 전용 엔드포인트. 실패를 흉내 낼 수 있게 상태를 토글한다.
    res.writeHead(healthy ? 200 : 503).end(healthy ? 'ok' : 'draining')
    return
  }
  if (req.url === '/toggle') {
    healthy = !healthy
    res.end(`healthy=${healthy}`)
    return
  }
  res.setHeader('content-type', 'application/json')
  res.end(JSON.stringify({ port: PORT, pid: process.pid }))
})

server.listen(PORT, () => console.log(`listening on ${PORT}`))
```

```bash
PORT=3001 node server.js &
PORT=3002 node server.js &
PORT=3003 node server.js &
```

가장 단순한 `haproxy.cfg`는 다음과 같다.

```haproxy
global
  # 전체 프로세스가 동시에 처리할 수 있는 연결 수 상한
  maxconn 50000
  log stdout format raw local0 info

defaults
  mode http
  log global
  option httplog
  # 클라이언트가 요청 헤더를 다 보낼 때까지 기다리는 최대 시간
  timeout http-request 10s
  # 큐에서 백엔드 서버를 기다리는 최대 시간
  timeout queue 5s
  timeout connect 3s
  timeout client 30s
  timeout server 30s

frontend web
  bind :8080
  default_backend nodes

backend nodes
  balance roundrobin
  server node1 127.0.0.1:3001
  server node2 127.0.0.1:3002
  server node3 127.0.0.1:3003
```

구조가 프록시의 두 방향을 그대로 반영한다. `frontend`는 클라이언트를 향한 면이고 `bind`로 어디서 받을지 정한다. `backend`는 서버를 향한 면이고 `server` 줄로 후보를 나열한다. `defaults`는 두 블록 모두에 적용되는 기본값이다.

도커로 실행하려면 설정 파일을 마운트한다.

```bash
docker run --rm --name haproxy \
  --network host \
  -v "$PWD/haproxy.cfg:/usr/local/etc/haproxy/haproxy.cfg:ro" \
  haproxy:3.0-alpine
```

`--network host`는 리눅스에서 호스트의 `127.0.0.1:3001`을 그대로 가리키기 위한 것이다. macOS나 Windows의 Docker Desktop에서는 호스트 네트워크가 같은 의미로 동작하지 않으므로, `-p 8080:8080`으로 포트를 열고 백엔드 주소를 `host.docker.internal`로 바꾼다.

이제 `curl` 세 번을 날리면 포트가 3001, 3002, 3003 순으로 돌아온다.

### 로드 밸런싱 알고리즘을 고르는 기준

`balance` 지시자가 분배 방식을 정한다. 셋만 알아도 대부분의 상황을 덮는다.

**`roundrobin`**은 순서대로 하나씩 나눠준다. 모든 요청의 처리 비용이 비슷하고 모든 서버의 성능이 같다는 두 가정이 성립할 때 가장 균등하다. `server` 줄에 `weight 2`를 붙이면 그 서버가 두 배를 받으므로, 성능이 다른 머신이 섞여 있어도 가중치로 보정할 수 있다.

**`leastconn`**은 현재 활성 연결이 가장 적은 서버로 보낸다. 요청 처리 시간의 편차가 큰 워크로드에서 라운드 로빈보다 확실히 낫다. 어떤 요청은 5ms에 끝나고 어떤 요청은 3초가 걸리는 API를 라운드 로빈으로 돌리면, 무거운 요청을 연달아 받은 서버가 뒤처져도 순서는 계속 그 서버 차례를 만든다. `leastconn`은 그 서버의 연결 수가 높은 동안 자연스럽게 건너뛴다. 웹소켓처럼 연결이 오래 유지되는 트래픽에서는 사실상 유일한 합리적 선택이다.

**`source`**는 클라이언트 IP를 해시해 항상 같은 서버로 보낸다. 서버가 세션을 메모리에 들고 있어 고정(sticky)이 필요할 때 쓴다. 다만 이건 해결책이라기보다 유예다. 서버 한 대가 빠지면 해시 대상이 바뀌면서 상당수 클라이언트의 매핑이 재배치되고, 그 클라이언트들은 세션을 잃는다. 또 캐리어 그레이드 NAT 뒤의 모바일 사용자 수만 명이 같은 IP로 보이면 분배가 심하게 기운다. 세션 상태를 Redis 같은 공유 저장소로 빼서(17장 참조) 서버를 진짜 무상태로 만드는 것이 정답이고, `source`는 그 작업이 끝날 때까지의 임시방편으로 이해하는 편이 낫다.

### 능동 헬스 체크

프로세스가 죽으면 커널이 TCP 연결을 거절하므로 HAProxy는 즉시 알아챈다. 문제는 프로세스가 살아 있는데 정상이 아닌 경우다. 데이터베이스 커넥션 풀이 고갈됐거나, 이벤트 루프가 막혔거나, 종료 절차에 들어가 새 요청을 받지 않으려는 상태다. TCP 수준으로는 이 모두가 "정상"으로 보인다.

능동 헬스 체크는 프록시가 주기적으로 HTTP 요청을 보내 상태를 직접 묻는다.

```haproxy
backend nodes
  balance leastconn

  # 헬스 체크로 보낼 요청. 응답이 2xx/3xx면 정상으로 본다.
  option httpchk GET /health
  http-check expect status 200

  # check: 헬스 체크 활성화
  # inter: 체크 주기, fall: 연속 실패 몇 번에 제거, rise: 연속 성공 몇 번에 복귀
  default-server check inter 2s fall 3 rise 2 maxconn 200

  server node1 127.0.0.1:3001
  server node2 127.0.0.1:3002
  server node3 127.0.0.1:3003
```

`fall 3`과 `inter 2s`의 조합은 "6초 동안 죽어 있어야 뺀다"는 뜻이다. 이 값들의 균형이 중요하다. 너무 민감하면 GC 일시 정지 한 번에 멀쩡한 서버가 빠졌다 들어왔다 하면서 트래픽이 요동치고, 너무 둔하면 죽은 서버로 요청이 계속 흘러간다. `rise 2`가 복귀를 즉시 허용하지 않는 이유도 같다. 막 살아난 서버가 캐시도 비어 있고 커넥션 풀도 차오르지 않은 상태에서 전체 트래픽의 3분의 1을 받으면 다시 넘어지기 쉽다.

`/health` 엔드포인트를 무엇으로 채울지가 실제 설계 지점이다. 흔한 실수는 여기서 데이터베이스에 쿼리를 날리는 것이다. 그러면 데이터베이스가 잠깐 느려진 순간 모든 인스턴스가 동시에 실패로 판정되어 백엔드 전체가 비고, 프록시는 트래픽을 보낼 곳이 없어 503을 뿌린다. 부분 장애가 전면 장애로 증폭된다. 헬스 체크는 "이 프로세스가 요청을 받을 수 있는가"만 물어야 하고, 의존성의 건강은 별도의 준비성(readiness) 신호나 서킷 브레이커로 다루는 편이 안전하다.

반대로 헬스 체크가 유용하게 쓰이는 자리는 무중단 배포다. 종료 신호를 받으면 즉시 `/health`를 503으로 바꾸고, HAProxy가 자신을 빼낼 때까지(`inter × fall`) 기다린 뒤 서버를 닫는다.

```js
process.on('SIGTERM', () => {
  healthy = false // 프록시가 먼저 알아채게 한다
  // fall × inter 보다 넉넉히 기다린 뒤 실제 종료
  setTimeout(() => {
    server.close(() => process.exit(0))
  }, 8000).unref()
})
```

`maxconn 200`은 서버당 동시 연결 상한이다. 이 값을 넘는 요청은 거절되는 게 아니라 HAProxy의 큐에서 기다린다. 큐잉과 부하 흘리기는 26.5에서 다시 본다.

### 통계 페이지

HAProxy는 내장 대시보드를 제공한다. 별도 프론트엔드로 열어두면 각 서버의 상태, 처리한 요청 수, 큐 길이, 헬스 체크 실패 이력을 실시간으로 볼 수 있다.

```haproxy
frontend stats
  bind :8404
  stats enable
  stats uri /
  stats refresh 5s
  # 운영 환경에서는 반드시 인증을 걸고 외부에 노출하지 않는다
  stats auth admin:change-me
```

`http://localhost:8404`을 열고 백엔드 하나에 `curl localhost:3002/toggle`을 날려보면, 몇 초 뒤 그 서버 행이 빨갛게 바뀌고 트래픽이 나머지 둘로만 흐르는 것을 눈으로 확인할 수 있다. 다시 토글하면 `rise 2` 조건을 채운 뒤 복귀한다.

## 26.3 Nginx로 하는 로드 밸런싱

### 같은 일, 다른 문법

Nginx로 같은 구성을 만들면 이렇게 된다.

```nginx
upstream nodes {
    # 기본은 라운드 로빈. 아래 줄을 넣으면 최소 연결 방식이 된다.
    least_conn;

    server 127.0.0.1:3001 max_fails=3 fail_timeout=10s;
    server 127.0.0.1:3002 max_fails=3 fail_timeout=10s;
    server 127.0.0.1:3003 max_fails=3 fail_timeout=10s;

    # 업스트림으로 유지할 유휴 keep-alive 연결 수.
    # 이 줄이 없으면 매 요청마다 TCP 핸드셰이크가 새로 일어난다.
    keepalive 64;
}

server {
    listen 8080;

    # 정적 파일은 Node.js까지 가지 않고 여기서 끝낸다
    location /assets/ {
        root /var/www;
        expires 1y;
        add_header Cache-Control "public, immutable";
        access_log off;
    }

    location / {
        proxy_pass http://nodes;

        # keepalive를 실제로 쓰려면 HTTP/1.1과 빈 Connection 헤더가 필요하다
        proxy_http_version 1.1;
        proxy_set_header Connection "";

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_connect_timeout 3s;
        proxy_read_timeout 30s;

        # 업스트림이 실패하면 다음 서버로 재시도할 조건
        proxy_next_upstream error timeout http_502 http_503;
    }
}
```

```bash
docker run --rm --name nginx --network host \
  -v "$PWD/nginx.conf:/etc/nginx/conf.d/default.conf:ro" \
  nginx:1.27-alpine
```

### 두 도구의 성격 차이

**헬스 체크가 다르다.** 오픈 소스 Nginx의 `max_fails`/`fail_timeout`은 수동(passive) 체크다. 실제 트래픽이 실패했을 때만 그것을 세고, 실패가 누적되면 `fail_timeout` 동안 그 서버를 뺀다. 즉 서버가 죽었다는 사실을 알기 위해 실제 사용자 요청 몇 개를 희생해야 한다. HAProxy의 `option httpchk`처럼 사용자 트래픽과 무관하게 주기적으로 찔러보는 능동 체크는 상용 Nginx Plus의 기능이거나, `nginx_upstream_check_module` 같은 서드파티 모듈을 넣어 빌드해야 한다. 로드 밸런싱만 놓고 보면 HAProxy가 기본기에서 앞서는 지점이다.

**동적 재설정이 다르다.** 두 제품 모두 설정 리로드는 무중단이다. Nginx는 `nginx -s reload`로 새 워커를 띄우고 기존 워커가 진행 중인 요청을 마칠 때까지 놔둔다. HAProxy는 `-sf` 옵션으로 같은 일을 하고, 더불어 런타임 API를 제공한다. 유닉스 소켓으로 명령을 보내 프로세스를 리로드하지 않고도 서버를 빼고 넣고 가중치를 바꿀 수 있다.

```bash
# 리로드 없이 node2를 유지보수 모드로 전환
echo "disable server nodes/node2" | socat stdio /var/run/haproxy.sock
# 가중치만 조정
echo "set weight nodes/node1 50" | socat stdio /var/run/haproxy.sock
```

이 차이는 26.6에서 백엔드 목록이 수시로 바뀌는 상황을 다룰 때 결정적으로 작용한다.

**정적 파일 서빙이 다르다.** Nginx는 원래 웹 서버이고 파일 서빙이 일급 기능이다. `root`, `try_files`, `expires`, `gzip_static`처럼 파일을 다루는 지시자가 풍부하고, 커널의 `sendfile`을 써서 유저 공간 복사 없이 내보낸다. HAProxy는 순수한 프록시이고 정적 파일을 다루지 않는다. 극히 단순한 응답을 돌려주는 `errorfile` 정도가 전부다.

**설정 언어의 성격이 다르다.** Nginx 설정은 위치 기반 매칭(`location`)이 중심인 선언적 블록 구조이고, `$remote_addr` 같은 변수와 `map`, `if`를 통해 확장한다. HAProxy는 ACL과 액션의 조합이다.

```haproxy
frontend web
  bind :8080
  acl is_api path_beg /api/
  acl is_admin path_beg /admin/
  use_backend api_nodes if is_api
  use_backend admin_nodes if is_admin
  default_backend web_nodes
```

조건을 이름 붙여 정의하고 재사용하는 이 방식은 라우팅 규칙이 복잡해질수록 읽기 쉬워진다.

정리하면, HTTP 트래픽만 다루고 정적 파일과 TLS를 한곳에서 처리하고 싶으면 Nginx가 편하고, 정교한 헬스 체크와 큐잉 제어, TCP 레이어 프록시(`mode tcp`로 PostgreSQL이나 Redis 앞에 세울 수 있다)까지 필요하면 HAProxy가 낫다. 둘을 겹쳐 쓰는 구성도 흔하다. Nginx가 바깥에서 TLS와 정적 파일을 맡고, 그 뒤의 HAProxy가 서비스별 백엔드 풀을 관리한다.

## 26.4 TLS 종료와 압축을 프록시로 옮기기

### 이득과 대가

TLS 종료란 클라이언트와의 암호화 연결을 프록시에서 끝내고, 프록시와 애플리케이션 사이는 평문 HTTP로 통신하는 구성이다.

```nginx
server {
    listen 443 ssl;
    http2 on;

    ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

    # TLS 1.2 미만은 받지 않는다
    ssl_protocols TLSv1.2 TLSv1.3;
    # 세션 재개용 캐시. 재방문 클라이언트의 핸드셰이크 비용을 크게 줄인다
    ssl_session_cache shared:SSL:20m;
    ssl_session_timeout 1d;
    ssl_session_tickets off;

    location / {
        proxy_pass http://nodes;  # 여기서부터는 평문
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

이득은 두 가지다. 첫째는 **CPU 오프로드**다. TLS 비용의 대부분은 데이터 암호화가 아니라 핸드셰이크의 비대칭 연산에 있다. AES-GCM 같은 대칭 암호는 현대 CPU의 AES-NI 명령으로 처리되어 기가바이트당 비용이 무시할 만한 수준이지만, 핸드셰이크의 ECDHE 키 교환과 서명 검증은 연결마다 반복되는 실제 계산이다. 짧은 API 응답을 주고받는 서비스라면 전송량 대비 핸드셰이크 비율이 높아 이 비용이 지배적이 된다. 이 계산이 Node.js 프로세스 안에서 일어나면 이벤트 루프와 CPU를 다투지만, 프록시로 옮기면 별도 프로세스의 예산에서 나간다. 게다가 프록시는 세션 티켓과 세션 캐시를 전체 클라이언트에 걸쳐 하나로 관리하므로 재접속 시 핸드셰이크를 생략할 확률이 훨씬 높다. Node.js 인스턴스마다 따로 TLS를 받으면 각 프로세스가 자기만의 세션 캐시를 갖게 되어, 다음 접속이 다른 인스턴스로 가는 순간 캐시가 무용지물이 된다.

둘째는 **인증서 관리의 일원화**다. Let's Encrypt 갱신은 90일마다 돌아오고, 인증서 파일은 프록시 한 곳에만 있으면 된다. 애플리케이션 컨테이너 이미지에 개인 키를 넣을 이유가 사라지고, 갱신과 배포가 분리된다.

대가도 분명하다.

**프록시-앱 구간이 평문이다.** 같은 호스트의 루프백이나 신뢰할 수 있는 사설 네트워크 안이면 대개 수용 가능한 위험이다. 그러나 프록시와 애플리케이션이 다른 가용 영역이나 다른 데이터센터에 있다면 그 구간도 암호화해야 한다. 이 경우 `proxy_pass https://...`로 재암호화하거나, 사이드카 프록시를 두어 mTLS 터널을 만드는 서비스 메시 방식을 쓴다.

**클라이언트 IP가 사라진다.** 애플리케이션이 보는 `req.socket.remoteAddress`는 항상 프록시의 주소다. 감사 로그, 지역 기반 라우팅, 애플리케이션 레벨 레이트 리미팅이 전부 망가진다. 해법은 프록시가 `X-Forwarded-For`에 원래 주소를 실어 보내는 것이고, 애플리케이션은 그 헤더를 신뢰하도록 설정해야 한다.

```js
import express from 'express'
const app = express()

// 앞단 프록시가 몇 겹인지 숫자로 정확히 지정한다.
// true(무조건 신뢰)는 위험하다 — 클라이언트가 보낸 가짜 XFF까지 믿게 된다.
app.set('trust proxy', 1)

app.get('/whoami', (req, res) => {
  res.json({ ip: req.ip, protocol: req.protocol })
})
```

`trust proxy`를 `1`로 두면 Express는 `X-Forwarded-For` 목록의 **오른쪽에서 한 칸 안쪽** 값을 클라이언트 IP로 채택한다. 이 방향이 중요하다. 헤더는 각 프록시가 뒤에 덧붙이는 구조이므로 왼쪽 값들은 클라이언트가 얼마든지 위조해 넣을 수 있고, 오른쪽 끝부터가 내가 통제하는 인프라가 기록한 값이다. `trust proxy: true`로 두면 목록의 가장 왼쪽, 즉 완전히 위조 가능한 값을 믿게 된다. 이 설정 하나로 IP 기반 레이트 리미터가 통째로 무력화되는 사고가 흔하다. 프록시가 두 겹이면(예: CDN → Nginx) `2`를 준다. `X-Forwarded-Proto`를 함께 봐야 `req.protocol`이 `https`로 나오고, HTTPS 리다이렉트 로직이 무한 루프에 빠지지 않는다.

**클라이언트 인증서 정보가 사라진다.** mTLS로 클라이언트를 인증하는 경우, 인증서 검증은 프록시에서 끝나므로 애플리케이션은 누가 인증됐는지 알 수 없다. 프록시가 검증 결과를 헤더로 전달해야 한다.

```nginx
proxy_set_header X-Client-Verify $ssl_client_verify;   # SUCCESS / FAILED / NONE
proxy_set_header X-Client-DN      $ssl_client_s_dn;
```

이 헤더들은 **프록시가 클라이언트로부터 온 동명의 헤더를 반드시 지운 뒤 자기 값으로 덮어써야** 의미가 있다. `proxy_set_header`는 덮어쓰기이므로 이 조건은 만족되지만, 애플리케이션이 프록시를 우회해 직접 접근 가능한 상태로 노출되어 있다면 누구나 `X-Client-Verify: SUCCESS`를 붙여 인증을 통과할 수 있다. 프록시 뒤의 애플리케이션 포트는 반드시 네트워크 수준에서 막아야 한다.

### 압축은 어디서 할 것인가

압축도 프록시로 옮기는 것이 기본이지만, 수치로 판단할 여지가 있다.

Nginx에서 압축을 켜는 설정은 다음과 같다.

```nginx
gzip on;
gzip_types application/json text/css application/javascript text/plain image/svg+xml;
# 이 크기 미만은 압축하지 않는다. 작은 응답은 압축해도 이득이 없다
gzip_min_length 1024;
gzip_comp_level 5;
# 업스트림 응답도 압축 대상에 포함
gzip_proxied any;
gzip_vary on;
```

판단 기준은 세 가지 수치다.

**응답 크기.** 200바이트 JSON을 gzip으로 압축하면 헤더 오버헤드 때문에 오히려 커지거나 거의 줄지 않는다. 반면 50KB JSON은 대개 8~10% 수준으로 줄어든다. 손익분기점은 대략 1KB 언저리이고, `gzip_min_length`가 바로 이 선을 긋는 값이다.

**압축 레벨의 한계 수익.** gzip 레벨 1에서 9로 올리면 CPU 시간은 몇 배로 늘지만 크기는 몇 퍼센트밖에 더 줄지 않는다. 실무에서 레벨 4~6이 권장되는 이유다. 브로틀리는 정적 자산에서 gzip 대비 15~20% 더 줄여주지만 높은 레벨의 압축 비용이 커서, 미리 압축해 파일로 두고 서빙하는 방식(`brotli_static`)이 적합하다. 동적 응답에는 브로틀리 레벨 4~5 정도가 현실적이다.

**압축 대상의 성질.** 이미 압축된 것을 다시 압축하면 CPU만 태운다. JPEG, PNG, MP4, 그리고 이미 gzip된 아카이브가 그렇다. `gzip_types`에 이들을 넣지 않는 것이 중요하고, `image/svg+xml`은 텍스트이므로 넣어야 한다.

프록시가 아니라 애플리케이션에서 압축해야 하는 경우도 있다. 프록시가 응답을 버퍼링하지 않고 흘려보내야 하는 스트리밍 응답(SSE, 청크 단위 생성)에서는 프록시 압축이 버퍼링을 유발해 첫 바이트 도달 시간을 망칠 수 있다. 이때는 애플리케이션이 `zlib.createGzip()`으로 직접 압축하며 흘려보내고 프록시는 `gzip_proxied off`로 손을 떼는 편이 낫다. 반대로 프록시에서 압축하고 캐싱까지 하는 경우, 같은 응답을 여러 클라이언트에게 재사용하면 압축 비용을 한 번만 내면 되므로 효율이 극대화된다.

## 26.5 레이트 리미팅과 백프레셔

### 두 계층의 역할 분담

레이트 리미팅은 프록시와 애플리케이션 양쪽에 존재하며, 서로 다른 것을 막는다.

**프록시 계층은 출처(source) 기준으로 막는다.** IP 하나가 초당 수천 요청을 던지는 상황, 스크래퍼, 단순한 볼류메트릭 공격이 대상이다. 판단에 필요한 정보가 요청 헤더 안에 다 있으므로 애플리케이션에 도달하기 전에 끊을 수 있고, 그것이 이 계층의 존재 이유다. 여기서 거절되는 요청은 Node.js의 이벤트 루프를 한 번도 건드리지 않는다.

```nginx
# 존 하나를 10MB 잡으면 IP 약 16만 개를 추적할 수 있다
limit_req_zone $binary_remote_addr zone=perip:10m rate=20r/s;
limit_conn_zone $binary_remote_addr zone=conn_perip:10m;

server {
    location /api/ {
        # burst: 순간적으로 40개까지는 큐에 넣어 흡수
        # nodelay: 큐에 넣되 지연 없이 즉시 통과시킴(토큰만 소비)
        limit_req zone=perip burst=40 nodelay;
        limit_conn conn_perip 20;
        limit_req_status 429;
        proxy_pass http://nodes;
    }
}
```

**애플리케이션 계층은 주체(principal) 기준으로 막는다.** "이 API 키는 시간당 1,000회", "무료 플랜은 하루 100회", "이 사용자는 결제 시도를 분당 3회까지"처럼 인증과 요금제와 도메인 규칙이 필요한 판단이다. 프록시는 토큰을 검증할 수도, 그 토큰이 어느 요금제인지 알 수도 없으므로 이 판단을 대신할 수 없다. 구현은 여러 인스턴스가 카운터를 공유해야 하므로 Redis 기반 슬라이딩 윈도우가 된다(24장 참조).

경계선은 이렇게 그어진다. **프록시는 인프라를 지키고, 애플리케이션은 비즈니스 규칙을 집행한다.** 둘 중 하나만 두면 반드시 구멍이 생긴다. 프록시만 있으면 정상 속도로 요청하는 유료 플랜 초과 사용자를 못 막고, 애플리케이션만 있으면 인증조차 안 된 폭주 트래픽이 이벤트 루프까지 도달해 정상 사용자의 지연 시간을 끌어올린다.

### 백프레셔를 시스템 수준으로 확장하기

스트림에서의 백프레셔(backpressure)는 소비자가 느릴 때 생산자를 멈추게 하는 메커니즘이다. 같은 개념이 시스템 전체에도 적용된다. 백엔드가 초당 500건을 처리할 수 있는데 초당 800건이 들어오면, 초과분 300건은 어딘가로 가야 한다. 선택지는 둘뿐이다. 큐에 쌓거나, 버리거나.

무한 큐잉이 재앙인 이유는 리틀의 법칙(Little's Law)이 설명한다. 큐 대기 시간은 큐 길이를 처리율로 나눈 값이다. 처리율이 초당 500건인데 큐에 5,000건이 쌓이면 새로 들어온 요청은 10초를 기다린 뒤에야 처리가 시작된다. 그런데 클라이언트의 타임아웃이 보통 5초다. 즉 10초 뒤에 처리되는 그 요청은 **이미 아무도 기다리지 않는 요청**이다. 서버는 응답을 받아줄 사람이 없는 작업에 CPU를 쓰고, 그동안 새 요청은 계속 쌓인다. 클라이언트는 타임아웃 후 재시도하므로 큐는 더 빨리 자란다. 이것이 데스 스파이럴(death spiral)이며, 부하가 걷힌 뒤에도 시스템이 스스로 회복하지 못하는 상태로 들어간다.

부하 흘리기(load shedding)는 이 지점에서 정직한 선택이다. 처리할 수 없는 요청을 빠르게 503으로 거절하면, 클라이언트는 즉시 실패를 알고 폴백 경로나 백오프 재시도를 택할 수 있다. 10초 기다린 끝의 타임아웃보다 50ms 만의 503이 모든 면에서 낫다. 사용자 경험도, 자원 사용도, 시스템 회복력도 그렇다.

HAProxy는 이 정책을 설정으로 직접 표현할 수 있다.

```haproxy
frontend web
  bind :8080
  maxconn 20000          # 프론트엔드가 동시에 붙잡을 연결 상한
  default_backend nodes

backend nodes
  balance leastconn
  option httpchk GET /health

  # 서버당 200 동시 연결. 초과분은 큐로 간다
  default-server check inter 2s fall 3 rise 2 maxconn 200

  # 큐에서 3초 넘게 기다린 요청은 503으로 흘려보낸다
  timeout queue 3s

  server node1 10.0.1.11:3000
  server node2 10.0.1.12:3000
```

`maxconn 200`이 백엔드 하나가 실제로 소화 가능한 동시 요청 수를 반영해야 한다. 이 숫자는 추측이 아니라 측정에서 나온다. 부하 테스트로 지연 시간이 급격히 꺾이는 지점을 찾아 그 직전 값을 쓴다(28장 참조). 그리고 `timeout queue`가 클라이언트 타임아웃보다 **짧아야** 한다. 그래야 프록시가 클라이언트보다 먼저 포기하고, 클라이언트는 침묵이 아니라 명시적인 503을 받는다.

애플리케이션 쪽에서도 자기 상태를 근거로 흘려보낼 수 있다. 이벤트 루프 지연이 임계값을 넘으면 새 요청을 거절하는 방식이다.

```js
import { monitorEventLoopDelay } from 'node:perf_hooks'

const loopDelay = monitorEventLoopDelay({ resolution: 10 })
loopDelay.enable()

// 500ms마다 창을 리셋해 최근 상태만 본다
setInterval(() => loopDelay.reset(), 500).unref()

app.use((req, res, next) => {
  // 헬스 체크는 항상 통과시킨다 — 아니면 과부하 시 서버가 통째로 빠진다
  if (req.url === '/health') return next()

  const p99 = loopDelay.percentile(99) / 1e6 // ns -> ms
  if (p99 > 200) {
    res.set('Retry-After', '2')
    return res.status(503).json({ error: 'overloaded' })
  }
  next()
})
```

이벤트 루프 지연은 Node.js 프로세스의 과부하를 나타내는 가장 직접적인 지표다. 이 값이 200ms를 넘었다는 것은 이미 큐에 밀린 콜백이 그만큼 있다는 뜻이고, 새 요청을 받아도 대기만 길어진다. `/health`를 예외로 두는 이유가 중요하다. 이 미들웨어가 헬스 체크까지 503으로 만들면 부하가 걸린 순간 모든 인스턴스가 프록시에서 제거되어, 부분적으로라도 처리하고 있던 트래픽이 완전히 끊긴다.

## 26.6 동적 수평 확장: 서비스 레지스트리와 Consul

### 정적 설정이 무너지는 지점

지금까지의 설정에는 IP 주소가 하드코딩되어 있다. 서버 목록이 고정된 환경에서는 문제가 없다. 그러나 오토스케일링 그룹, 컨테이너 오케스트레이터, 스팟 인스턴스가 섞이는 순간 전제가 무너진다. 인스턴스는 부하에 따라 5분마다 뜨고 지고, 배포할 때마다 IP가 전부 바뀌며, 클라우드 제공자가 예고 없이 노드를 회수한다. 새 인스턴스가 떴는데 프록시가 모르면 그 인스턴스는 트래픽을 한 건도 받지 못하고, 사라진 인스턴스가 목록에 남아 있으면 헬스 체크가 걸러낼 때까지 요청이 새어나간다.

해법은 목록을 사람이 관리하지 않는 것이다. 서비스 레지스트리(service registry)는 "지금 살아 있는 인스턴스가 누구인가"를 담는 데이터베이스이고, 인스턴스가 스스로 등록하고 주기적으로 살아 있음을 알린다. Consul, etcd, ZooKeeper, 그리고 쿠버네티스의 Endpoints 객체가 모두 이 역할을 한다.

### Consul에 스스로 등록하기

Consul을 띄운다.

```bash
docker run --rm -d --name consul -p 8500:8500 \
  hashicorp/consul:1.19 agent -dev -client=0.0.0.0
```

인스턴스는 기동 시 자신을 등록하고, 종료 시 등록을 해제한다.

```js
// registry.js
const CONSUL = process.env.CONSUL_URL ?? 'http://127.0.0.1:8500'

export async function register({ name, id, address, port }) {
  const res = await fetch(`${CONSUL}/v1/agent/service/register`, {
    method: 'PUT',
    headers: { 'content-type': 'application/json' },
    body: JSON.stringify({
      ID: id,
      Name: name,
      Address: address,
      Port: port,
      // Consul이 직접 HTTP 헬스 체크를 수행한다
      Check: {
        HTTP: `http://${address}:${port}/health`,
        Interval: '5s',
        Timeout: '2s',
        // 체크가 계속 실패하면 60초 뒤 등록 자체를 지운다
        DeregisterCriticalServiceAfter: '60s'
      }
    })
  })
  if (!res.ok) throw new Error(`register failed: ${res.status}`)
}

export async function deregister(id) {
  await fetch(`${CONSUL}/v1/agent/service/deregister/${id}`, { method: 'PUT' })
}
```

```js
// app.js 일부
import { randomUUID } from 'node:crypto'
import { register, deregister } from './registry.js'

const id = `api-${process.env.PORT}-${randomUUID().slice(0, 8)}`

server.listen(PORT, async () => {
  await register({ name: 'api', id, address: '127.0.0.1', port: PORT })
})

// 종료 시 반드시 등록을 해제한다. 빠뜨리면 죽은 인스턴스가
// DeregisterCriticalServiceAfter 시간만큼 목록에 남는다.
for (const sig of ['SIGTERM', 'SIGINT']) {
  process.on(sig, async () => {
    await deregister(id).catch(() => {})
    server.close(() => process.exit(0))
  })
}
```

`DeregisterCriticalServiceAfter`가 중요하다. 프로세스가 `SIGKILL`로 죽거나 머신이 통째로 사라지면 해제 요청을 보낼 기회가 없다. 이 옵션이 그런 좀비 항목을 자동으로 청소한다.

### 동적 로드 밸런서 직접 만들기

Consul의 블로킹 쿼리(blocking query)를 쓰면 폴링 없이 변화를 감지할 수 있다. `index` 파라미터에 마지막으로 본 인덱스를 넣어 요청하면, Consul은 그 인덱스가 바뀔 때까지 응답을 붙잡고 있다가 변화가 생기는 즉시 돌려준다. 롱 폴링(long polling)이다.

```js
// balancer.js
import { createServer } from 'node:http'
import httpProxy from 'http-proxy'

const CONSUL = process.env.CONSUL_URL ?? 'http://127.0.0.1:8500'
const SERVICE = 'api'

let targets = []
let cursor = 0 // 라운드 로빈 포인터

async function watchService() {
  let index = '0'
  for (;;) {
    try {
      const url = new URL(`${CONSUL}/v1/health/service/${SERVICE}`)
      url.searchParams.set('passing', 'true') // 헬스 체크 통과 인스턴스만
      url.searchParams.set('index', index)
      url.searchParams.set('wait', '5m')      // 최대 5분 대기

      const res = await fetch(url, { signal: AbortSignal.timeout(6 * 60_000) })
      const nextIndex = res.headers.get('x-consul-index')
      const entries = await res.json()

      targets = entries.map(e => ({
        host: e.Service.Address || e.Node.Address,
        port: e.Service.Port
      }))
      console.log(`backends updated: ${targets.length}`)

      // 인덱스가 되감기면(서버 재시작 등) 0으로 리셋해야 한다
      index = (Number(nextIndex) < Number(index)) ? '0' : nextIndex
    } catch (err) {
      // 실패해도 마지막으로 알던 목록을 유지한 채 재시도한다.
      // 레지스트리 장애가 트래픽 전면 중단으로 번지지 않게 하는 핵심이다.
      console.error('watch error, retrying', err.message)
      await new Promise(r => setTimeout(r, 2000))
    }
  }
}

const proxy = httpProxy.createProxyServer({ xfwd: true })

proxy.on('error', (err, req, res) => {
  if (!res.headersSent) res.writeHead(502, { 'content-type': 'text/plain' })
  res.end('bad gateway')
})

createServer((req, res) => {
  if (targets.length === 0) {
    res.writeHead(503).end('no healthy backends')
    return
  }
  const t = targets[cursor++ % targets.length]
  proxy.web(req, res, { target: `http://${t.host}:${t.port}` })
}).listen(8080, () => console.log('balancer on :8080'))

watchService()
```

이 60줄이 하는 일은 HAProxy가 하는 일의 핵심 골격과 같다. 백엔드 목록을 유지하고, 알고리즘으로 하나를 고르고, 요청을 전달하고, 실패하면 502를 돌려준다. 직접 만들어보면 프로덕션 프록시가 추가로 무엇을 해주는지도 선명해진다. 커넥션 풀링, 재시도, 큐잉, 서킷 브레이킹, 청크 인코딩과 HTTP/2 처리, 헤더 정규화가 모두 빠져 있다.

`http-proxy` 패키지는 오랫동안 사실상의 표준이었지만 현재 유지보수가 활발하지 않다. 새로 짓는다면 포크인 `http-proxy-3`나, `undici`의 `ProxyAgent`와 스트림 파이핑으로 직접 구성하는 편이 낫다. 실무에서는 이런 직접 구현 대신 Consul Template이나 `consul-connect`로 HAProxy 설정 파일을 생성해 리로드하거나, HAProxy의 `server-template`과 DNS SRV 조회를 조합하는 방식을 더 많이 쓴다.

```haproxy
resolvers consul
  nameserver consul 127.0.0.1:8600
  accepted_payload_size 8192
  hold valid 5s

backend nodes
  balance leastconn
  # 미리 10개 슬롯을 만들어두고 DNS SRV 결과로 채운다.
  # 인스턴스가 바뀌어도 리로드가 필요 없다.
  server-template api 10 _api._tcp.service.consul resolvers consul check
```

## 26.7 P2P 로드 밸런싱

### 프록시를 없애면

지금까지는 모든 요청이 중앙의 프록시를 거쳤다. 이 구조에는 두 가지 비용이 있다. 홉이 하나 늘어나 지연 시간이 더해지고, 프록시가 단일 실패 지점이자 병목이 된다. 프록시 자체를 이중화하고 그 앞에 또 무언가를 두는 식으로 대응하지만, 그럴수록 계층이 깊어진다.

P2P 로드 밸런싱(클라이언트 사이드 로드 밸런싱)은 이 홉을 없앤다. 클라이언트가 서비스 레지스트리에서 인스턴스 목록을 직접 받아, 자기가 알고리즘을 돌려 대상을 고르고 직접 연결한다. 중앙 프록시가 사라지므로 홉이 하나 줄고 단일 병목도 없다.

```js
// peer-balancer.js — 서비스별 인스턴스 목록을 들고 직접 고르는 클라이언트
import { Agent, request } from 'undici'

export class PeerBalancer {
  #targets = []
  #cursor = 0
  #failures = new Map() // key -> 연속 실패 횟수
  #agent = new Agent({ connections: 32, keepAliveTimeout: 30_000 })

  constructor(consulUrl, service) {
    this.consulUrl = consulUrl
    this.service = service
  }

  async start() {
    this.#watch() // 백그라운드에서 목록을 갱신
    await this.#refresh() // 첫 목록은 기다렸다 받는다
  }

  async #refresh(index = '0') {
    const url = new URL(`${this.consulUrl}/v1/health/service/${this.service}`)
    url.searchParams.set('passing', 'true')
    url.searchParams.set('index', index)
    url.searchParams.set('wait', '2m')
    const res = await fetch(url)
    this.#targets = (await res.json()).map(
      e => `http://${e.Service.Address}:${e.Service.Port}`
    )
    return res.headers.get('x-consul-index') ?? '0'
  }

  async #watch() {
    let index = '0'
    for (;;) {
      try {
        index = await this.#refresh(index)
      } catch {
        await new Promise(r => setTimeout(r, 2000))
      }
    }
  }

  #pick() {
    const live = this.#targets.filter(t => (this.#failures.get(t) ?? 0) < 3)
    const pool = live.length > 0 ? live : this.#targets // 전부 죽었으면 그냥 시도
    if (pool.length === 0) throw new Error('no backends known')
    return pool[this.#cursor++ % pool.length]
  }

  async call(path, options = {}) {
    let lastErr
    // 다른 인스턴스로 최대 3번까지 재시도한다
    for (let attempt = 0; attempt < 3; attempt++) {
      const target = this.#pick()
      try {
        const res = await request(target + path, {
          ...options,
          dispatcher: this.#agent,
          headersTimeout: 2000
        })
        if (res.statusCode >= 500) throw new Error(`upstream ${res.statusCode}`)
        this.#failures.set(target, 0) // 성공하면 실패 카운터 초기화
        return res
      } catch (err) {
        lastErr = err
        this.#failures.set(target, (this.#failures.get(target) ?? 0) + 1)
      }
    }
    throw lastErr
  }
}
```

핵심은 세 조각이다. 레지스트리를 감시해 목록을 유지하는 부분, 목록에서 하나를 고르는 부분, 그리고 실패를 기억해 나쁜 인스턴스를 잠시 빼는 부분이다. 마지막 조각이 없으면 클라이언트는 죽은 인스턴스를 계속 순번대로 고른다. 중앙 프록시가 헬스 체크로 해주던 일을 클라이언트가 자기 관측만으로 근사하는 셈이다.

### 어디에 쓰이고 무엇이 문제인가

이 방식이 실제로 널리 쓰이는 자리는 gRPC와 서비스 메시다.

gRPC는 HTTP/2 위에서 하나의 TCP 연결에 여러 스트림을 다중화한다. 그래서 L4 프록시로 gRPC를 분배하면 분배가 망가진다. 연결 하나가 백엔드 하나에 고정되고, 그 연결 위로 흐르는 수천 개의 RPC가 전부 같은 서버로 간다. 클라이언트가 여러 백엔드에 각각 연결을 열고 RPC 단위로 분배하는 것이 자연스러운 해법이고, 그래서 gRPC 라이브러리들은 처음부터 클라이언트 사이드 로드 밸런서를 내장하고 있다.

서비스 메시(Istio, Linkerd 등)는 절충안이다. 클라이언트 프로세스마다 사이드카 프록시(Envoy 등)를 붙여, 애플리케이션 코드는 로컬 프록시로만 요청을 보내고 사이드카가 분배와 재시도, mTLS, 관측을 담당한다. 애플리케이션 입장에서는 클라이언트 사이드 로드 밸런싱의 이점(중앙 병목 없음, 홉 최소화)을 누리면서 구현은 프록시에 맡긴다. 중앙 제어 평면이 모든 사이드카에 설정을 밀어주므로 정책의 일관성도 유지된다.

단점도 분명하다.

**클라이언트마다 구현이 필요하다.** Node.js, Java, Go, Python 서비스가 섞여 있으면 언어마다 같은 로직을 만들고 같은 수준으로 검증해야 한다. 재시도 정책, 서킷 브레이커 임계값, 헬스 판정 기준이 언어별로 미묘하게 달라지고, 장애 상황에서 그 차이가 드러난다. 중앙 프록시라면 한 곳만 고치면 될 정책 변경이 여러 저장소의 배포로 번진다. 서비스 메시가 사이드카 방식을 택한 근본 이유가 이것이다.

**상태 갱신이 지연된다.** 각 클라이언트가 레지스트리 사본을 들고 있으므로, 인스턴스가 사라진 뒤 모든 클라이언트가 그 사실을 알기까지 시차가 생긴다. 그 사이 요청은 실패하고 재시도로 메워야 한다. 클라이언트 수가 늘면 레지스트리에 붙는 워처 수도 함께 늘어 레지스트리 자체가 새로운 병목이 된다. 인스턴스 1,000개가 서로를 감시하면 감시 연결이 수만 개가 된다.

**분배가 국소적으로만 최적이다.** 각 클라이언트는 자기가 보낸 요청만 안다. 클라이언트 100개가 각자 라운드 로빈을 돌리면 전역적으로는 균등해 보이지만, 최소 연결 방식은 제대로 구현할 수 없다. 어떤 백엔드가 지금 전체적으로 얼마나 바쁜지는 아무도 모르기 때문이다. gRPC와 Envoy가 쓰는 "두 개 무작위 선택(power of two random choices)"이 이 문제의 실용적 타협안이다. 무작위로 둘을 고른 뒤 그중 자기가 관측한 부하가 낮은 쪽을 택하는 것만으로, 전역 정보 없이도 순수 무작위보다 훨씬 균등한 분배가 나온다.

선택 기준은 이렇게 정리된다. 외부 인터넷 트래픽을 받는 진입점에는 중앙 프록시가 맞다. TLS, 레이트 리미팅, WAF가 필요하고 클라이언트를 통제할 수 없기 때문이다. 내부 서비스 간 통신에는 클라이언트 사이드 로드 밸런싱이 유리하고, 언어가 여러 개라면 그것을 직접 구현하기보다 사이드카에 위임하는 편이 낫다(27장 참조).

## 요약

- 정방향 프록시는 클라이언트를 대신해 임의의 서버로 나가고, 역방향 프록시는 서버 집합을 대신해 미지의 클라이언트를 맞는다. 프록시가 애플리케이션에서 덜어내는 것은 TLS, 압축, 정적 파일, 레이트 리미팅, 그리고 느린 클라이언트 흡수다.
- Node.js로 이 일들을 할 수 있어도 프록시로 옮기는 이유는 이벤트 루프와 libuv 스레드풀을 CPU 바운드 작업으로부터 지키고, 검증된 구현을 쓰고, 인증서·정책의 변경 주기를 애플리케이션 배포에서 분리하기 위해서다.
- 로드 밸런싱 알고리즘은 워크로드가 정한다. 처리 비용이 균일하면 `roundrobin`, 편차가 크거나 연결이 오래 유지되면 `leastconn`, 세션 고정이 불가피할 때만 `source`를 쓰되 이는 상태를 외부화할 때까지의 유예다.
- 능동 헬스 체크(`option httpchk`)는 프로세스는 살아 있지만 요청을 받을 수 없는 상태를 잡아낸다. `/health`에서 데이터베이스를 확인하면 부분 장애가 전면 장애로 증폭되므로, 프로세스 자신의 상태만 보고해야 한다.
- TLS 종료는 핸드셰이크 CPU를 오프로드하고 인증서를 한곳으로 모으는 대신 클라이언트 IP를 잃는다. `X-Forwarded-For`와 `trust proxy`를 정확한 홉 수로 설정해야 하며, `trust proxy: true`는 위조 가능한 값을 신뢰하게 만드는 보안 결함이다.
- 무한 큐잉은 아무도 기다리지 않는 요청을 처리하느라 시스템을 데스 스파이럴로 몰아넣는다. `maxconn`으로 상한을 정하고 `timeout queue`를 클라이언트 타임아웃보다 짧게 두어, 늦은 성공 대신 빠른 503을 돌려주는 부하 흘리기가 낫다.
- 인스턴스가 수시로 뜨고 지는 환경에서는 서비스 레지스트리가 백엔드 목록의 진실이 된다. Consul의 블로킹 쿼리로 변화를 즉시 반영할 수 있고, 레지스트리 장애 시에는 마지막으로 알던 목록을 유지해 트래픽 중단을 막아야 한다.
- 클라이언트 사이드 로드 밸런싱은 홉과 중앙 병목을 없애지만 언어마다 구현이 필요하고 상태 갱신이 지연된다. gRPC처럼 연결 다중화 때문에 L4 분배가 불가능한 경우에 특히 유효하며, 언어가 여러 개면 사이드카 프록시로 위임하는 편이 현실적이다.

## 연습문제

1. 26.2의 `haproxy.cfg`에 응답 지연이 극단적으로 갈리는 백엔드를 섞어 실험하라. `/fast`는 즉시, `/slow`는 2초 뒤 응답하는 서버 세 대를 띄우고, `balance roundrobin`과 `balance leastconn`으로 각각 부하를 건 뒤 p99 지연 시간을 비교하라. 두 알고리즘의 차이가 나타나기 시작하는 동시 접속 수는 얼마인가.

2. `trust proxy` 설정이 IP 기반 레이트 리미터를 어떻게 무력화하는지 재현하라. Express에 `app.set('trust proxy', true)`를 두고 IP당 분당 10회 제한을 건 뒤, `X-Forwarded-For` 헤더에 매번 다른 가짜 IP를 넣어 요청하면 제한이 통하지 않음을 확인하라. 그다음 `trust proxy`를 정확한 홉 수로 바꾸고, 프록시를 통과한 요청과 프록시를 우회한 직접 요청이 각각 어떤 IP로 기록되는지 비교하라.

3. 26.6의 동적 밸런서에 최소 연결 알고리즘과 서킷 브레이커를 추가하라. 각 대상의 진행 중인 요청 수를 세어 가장 적은 곳으로 보내고, 연속 실패가 임계값을 넘으면 일정 시간 그 대상을 후보에서 제외한 뒤 요청 하나를 시험 삼아 보내 복구를 판단하는 반열림(half-open) 상태를 구현하라. Consul을 강제로 중단시킨 상태에서 백엔드 하나를 죽였을 때, 밸런서가 몇 초 만에 그 백엔드를 걸러내는지 측정하라.
