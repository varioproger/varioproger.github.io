순서는 실무의 순서와 같다. 먼저 무엇을 볼지 정하고(28.1), 재현 가능하게 측정하고(28.2), 기준선을 남겨 회귀를 감시하고(28.3), 그 위에 조직이 합의할 수 있는 목표를 세운다(28.4). 목표를 못 맞추면 프로파일러를 꺼내고(28.5), 원인이 이미 알려진 열 가지 중 하나라는 사실을 확인한다(28.6).

## 28.1 지연 시간, 처리량, 백분위수 이해하기

### 평균은 아무도 겪지 않는 값이다

응답 시간 대시보드에서 가장 흔히 보이는 숫자는 평균이다. 그리고 가장 쓸모없는 숫자이기도 하다. 이유는 응답 시간 분포의 모양에 있다. 지연 시간은 아래로 유한하고(0보다 작을 수 없다) 위로는 열려 있다. 대부분의 요청은 캐시에 맞고, 커넥션이 이미 열려 있고, 데이터가 버퍼 캐시에 있어 빠르게 끝난다. 소수의 요청은 커넥션 풀에서 대기하고, 가비지 컬렉션 정지에 걸리고, 재시도를 한 번 하고, 디스크를 읽는다. 결과는 왼쪽에 봉우리가 있고 오른쪽으로 길게 꼬리를 끄는 분포다.

이런 분포에서 평균은 꼬리에 끌려간다. 요청 1,000개 중 990개가 10ms, 10개가 2,000ms라면 평균은 29.8ms다. 이 값은 두 집단 어느 쪽도 설명하지 못한다. 10ms를 겪은 사람도 2,000ms를 겪은 사람도 29.8ms를 경험하지 않았다. 평균은 존재하지 않는 사용자를 묘사한다.

### 백분위수가 답하는 질문

백분위수(percentile)는 "요청의 N%가 이 값 이하였다"를 말한다. p50(중앙값)은 전형적인 사용자가 겪는 시간이고, p99는 100명 중 가장 느린 한 명이 겪는 시간이다. 각각이 답하는 질문이 다르다.

| 지표 | 답하는 질문 | 주로 반응하는 원인 |
|---|---|---|
| p50 | 평상시 이 기능은 얼마나 빠른가 | 알고리즘, 쿼리 자체의 비용 |
| p95 | 체감상 "가끔 느리다"의 실체는 무엇인가 | 커넥션 풀 대기, 캐시 미스 |
| p99 | 최악에 가까운 경험은 어느 정도인가 | GC 정지, 재시도, 락 경합 |
| p99.9 | 시스템이 무너질 때 어떤 모습인가 | 타임아웃, 스로틀링, 노드 이상 |

p99.9는 측정 자체가 까다롭다. 30초 부하 테스트에서 초당 5,000요청이면 표본이 15만 개이고 p99.9는 상위 150개가 결정한다. 이 정도면 쓸 만하지만, 초당 50요청인 내부 API에서 p99.9를 논하는 것은 표본 두 개를 보고 이야기하는 것과 같다. 표본 수가 백분위수의 신뢰도를 결정한다는 점을 항상 함께 본다.

### 백분위수는 평균낼 수 없다

가장 자주 저지르는 실수다. 인스턴스 A의 p99가 100ms, 인스턴스 B의 p99가 200ms일 때 전체 p99는 150ms가 아니다. 계산할 방법이 아예 없다. p99는 원본 분포에서만 나오는 값이고, 두 요약값에서 원본을 복원할 수 없기 때문이다.

극단적인 예를 보면 명확하다. A는 요청 100만 건 전부 100ms, B는 요청 100건 중 99건이 1ms, 1건이 200ms라고 하자. 각각의 p99는 100ms와 200ms이지만, 합친 분포의 p99는 100ms다. B의 표본이 전체의 0.01%에 불과해 꼬리에 영향을 주지 못한다.

같은 이유로 다음 두 가지도 틀렸다.

- **시간에 대한 평균**: 1분 단위 p99를 60개 모아 평균 내어 "한 시간 p99"라고 부르는 것. 사고가 5분 동안 났다면 이 평균은 사고를 12분의 1로 희석한다.
- **엔드포인트에 대한 평균**: 엔드포인트별 p99를 평균 내어 서비스 p99라고 부르는 것.

올바른 방법은 백분위수 대신 **히스토그램**을 집계하는 것이다. 각 인스턴스가 버킷별 카운트를 내보내면 버킷은 더할 수 있고, 합친 히스토그램에서 임의의 백분위수를 다시 계산할 수 있다. Prometheus의 `histogram_quantile`이나 OpenTelemetry의 명시적 버킷 히스토그램이 이 구조를 쓰는 이유다(31장 참조). 반대로 각 인스턴스가 이미 계산된 p99를 게이지로 내보내면 그 값은 합칠 수 없는 죽은 숫자가 된다.

### 팬아웃에서 p99는 예외가 아니라 기본값이다

사용자 요청 하나가 하위 호출 여러 개로 갈라지고(팬아웃), 모든 응답이 도착해야 페이지를 그릴 수 있다면, 사용자가 겪는 지연은 하위 호출들의 **최댓값**이다. 여기서 확률이 개입한다.

하위 호출 하나가 p99 임계값을 넘을 확률은 정의상 1%다. 호출이 독립이라고 가정하면 N개 중 최소 하나가 임계값을 넘을 확률은 다음과 같다.

```text
P(적어도 하나가 p99 초과) = 1 - 0.99^N

N=1    →  1.0%
N=10   →  9.6%
N=50   →  39.5%
N=100  →  63.4%
```

한 페이지가 백엔드 서비스 5개를 부르고 각 서비스가 데이터베이스를 2회 조회하면 하위 호출은 이미 10개다. 사용자 요청의 약 10%가 백엔드 p99 지연을 겪는다. 즉 **백엔드의 p99는 사용자의 p90이 된다.** 팬아웃이 100이면 사용자의 절반 이상이 백엔드 p99를 경험하므로, 백엔드의 p99가 사용자의 p50을 지배한다.

이 계산은 두 가지 실무 결론을 강제한다. 첫째, 내부 서비스의 SLO는 p99 기준으로 세워야 한다. 내부 p50이 아무리 좋아도 팬아웃을 통과하면 사라진다. 둘째, 팬아웃 폭을 줄이는 일이 개별 호출을 최적화하는 일보다 대체로 효과가 크다. N을 100에서 10으로 줄이면 꼬리에 걸릴 확률이 63%에서 9.6%로 떨어지는데, 이는 개별 호출을 6배 빠르게 만드는 것보다 쉬운 경우가 많다.

### 리틀의 법칙: 처리량과 지연을 잇는 다리

처리량(throughput)과 지연(latency)은 독립된 축이 아니다. 안정 상태의 대기 시스템에서 둘은 리틀의 법칙(Little's law)으로 묶인다.

```text
L = λ × W

L: 시스템 안에 동시에 존재하는 요청 수 (동시성)
λ: 초당 도착률 (처리량, rps)
W: 요청 하나의 체류 시간 (지연, 초)
```

이 식은 가정이 거의 없어서 어디에나 적용된다. 서비스가 초당 2,000요청을 처리하고 평균 응답 시간이 50ms면, 어느 순간이든 평균 100건이 처리 중이다. 이 100이라는 숫자가 커넥션, 소켓, 힙에 올라간 요청 객체의 수를 결정한다.

역방향으로 쓰면 용량 계획이 된다. 데이터베이스 커넥션 풀이 20개이고 쿼리 하나가 50ms 걸린다면, 이 풀이 지탱할 수 있는 최대 처리량은 `20 / 0.05 = 400 rps`다. 400을 넘는 부하가 들어오면 초과분은 풀 대기 큐에 쌓이고, W가 커지면서 지연만 늘고 처리량은 평탄해진다. 부하 테스트에서 "동시성을 올리는데 rps는 그대로이고 지연만 비례해서 증가하는" 곡선을 보면, 어딘가에 이런 고정 크기 자원이 포화되었다는 신호다. 병목의 위치를 리틀의 법칙으로 역산할 수 있다는 뜻이다.

## 28.2 Autocannon으로 하는 부하 테스트

### 첫 측정

autocannon은 Node.js로 작성된 HTTP 벤치마크 도구다. 같은 런타임을 쓰기 때문에 설치가 쉽고, 프로그래밍 방식 API가 있어 CI에 넣기 좋다.

```bash
npm i -D autocannon

# -c 커넥션 수, -d 지속 시간(초), -p 커넥션당 파이프라인 깊이
npx autocannon -c 50 -d 30 -w 5 http://127.0.0.1:3000/recipes/42
```

`-w 5`는 워밍업(warmup) 옵션으로, 처음 5초의 측정값을 결과에서 제외한다. 아래는 전형적인 출력이다.

```text
Running 30s test @ http://127.0.0.1:3000/recipes/42
50 connections

┌─────────┬──────┬──────┬───────┬───────┬─────────┬─────────┬────────┐
│ Stat    │ 2.5% │ 50%  │ 97.5% │ 99%   │ Avg     │ Stdev   │ Max    │
├─────────┼──────┼──────┼───────┼───────┼─────────┼─────────┼────────┤
│ Latency │ 3 ms │ 5 ms │ 21 ms │ 48 ms │ 6.71 ms │ 9.42 ms │ 312 ms │
└─────────┴──────┴──────┴───────┴───────┴─────────┴─────────┴────────┘
┌───────────┬────────┬────────┬────────┬────────┬─────────┬─────────┬────────┐
│ Stat      │ 1%     │ 2.5%   │ 50%    │ 97.5%  │ Avg     │ Stdev   │ Min    │
├───────────┼────────┼────────┼────────┼────────┼─────────┼─────────┼────────┤
│ Req/Sec   │ 5,102  │ 5,102  │ 7,431  │ 7,905  │ 7,289   │ 502.1   │ 5,101  │
└───────────┴────────┴────────┴────────┴────────┴─────────┴─────────┴────────┘

219k requests in 30.05s, 41.2 MB read
```

읽는 순서가 중요하다. 첫째, **오류 줄부터 본다.** `non-2xx responses`나 `errors`, `timeouts` 항목이 출력에 나타나면 그 아래 숫자는 전부 무의미하다. 실패는 대개 성공보다 빨라서, 오류가 섞인 측정은 지연을 실제보다 좋게 보이게 만든다. 둘째, 지연 표의 Max와 99%의 간격을 본다. 위 예에서 p99는 48ms인데 Max는 312ms다. 6배 넘는 격차는 주기적인 정지 — 대개 메이저 GC나 로그 플러시 — 를 의심할 근거가 된다. 셋째, Req/Sec 표의 Stdev를 본다. 표준편차가 평균의 10%를 넘으면 측정 환경이 불안정하다는 뜻이므로 결론을 내리기 전에 원인을 없애야 한다.

전체 백분위수 스펙트럼이 필요하면 `-l` 옵션을 쓴다. 0.001%부터 99.999%까지의 히스토그램을 출력하므로 꼬리의 모양을 직접 볼 수 있다.

### 부하 테스트가 거짓말하는 여섯 가지 방식

측정 도구는 정직하지만 측정 설계는 쉽게 틀린다. 아래 여섯 가지가 반복해서 나타난다.

**1) 클라이언트가 병목이다.** autocannon도 Node.js 프로세스이므로 코어 하나를 쓴다. 대상 서버가 같은 머신에서 클러스터로 8개 워커를 돌리고 있다면, 측정된 숫자는 서버가 아니라 클라이언트의 한계다. 증상은 명확하다. 커넥션 수를 늘려도 rps가 오르지 않고, 클라이언트 프로세스의 CPU가 100%에 붙어 있다. 대책은 부하 생성기를 별도 머신에 두거나, `-w`(worker) 옵션으로 autocannon 자체를 여러 워커 스레드로 돌리는 것이다.

**2) 커넥션을 재사용하지 않는다.** 요청마다 TCP 핸드셰이크를 새로 하면 측정하는 것은 애플리케이션이 아니라 커널의 소켓 생성 비용이다. autocannon은 기본적으로 커넥션을 유지하지만, 서버 쪽 `keepAliveTimeout`이 짧거나 중간 프록시가 `Connection: close`를 붙이면 무너진다. 측정 중 `ss -s`로 TIME_WAIT 소켓이 급증하는지 확인하면 바로 드러난다.

**3) 워밍업이 없다.** V8은 함수가 충분히 여러 번 호출된 뒤에야 최적화 컴파일을 수행한다. 처음 몇 초의 처리량은 인터프리터와 베이스라인 컴파일러의 성능이고, 정상 상태의 절반 이하인 경우가 흔하다. 여기에 커넥션 풀 채우기, JIT 워밍업, 캐시 채우기가 겹치므로 최소 5~10초는 버려야 한다.

**4) 캐시 히트만 측정한다.** `-a`나 고정 URL로 같은 레시피 ID만 30초 동안 조회하면, 두 번째 요청부터는 애플리케이션 캐시와 데이터베이스 버퍼 캐시에 모두 맞는다. 실제 트래픽의 키 분포는 대개 지프(Zipf) 분포에 가깝다. 인기 항목이 대부분을 차지하되 롱테일이 존재한다. autocannon의 `requests` 배열과 `setupRequest` 훅으로 ID를 바꿔가며 요청하는 것이 최소한의 현실 반영이다.

**5) 프로덕션과 다른 하드웨어다.** 개발자의 노트북은 코어가 적고, 부스트 클럭이 높고, 서멀 스로틀링이 있고, 네트워크 지연이 0에 가깝다. 컨테이너의 CPU 할당량(cgroup quota)도 없다. 노트북에서 잰 절대값은 용량 계획에 쓸 수 없다. 노트북 측정은 "변경 전후의 상대 비교"에만 쓰고, 절대값은 프로덕션과 같은 인스턴스 타입에서 잰다.

**6) 조율 누락(coordinated omission)이다.** 가장 미묘하다. 고정 커넥션 수 방식의 부하 도구는 응답이 와야 다음 요청을 보낸다. 서버가 1초 멈추면 그동안 요청이 아예 발사되지 않으므로, 원래대로라면 그 1초 동안 도착해 1초씩 기다렸어야 할 요청들이 표본에서 통째로 빠진다. 결과적으로 꼬리 지연이 실제보다 훨씬 낙관적으로 나온다. 부하 도구가 보고하는 p99를 프로덕션의 사용자 체감 p99와 동일시하면 안 되는 근본적인 이유이며, 최종 판단은 항상 실제 트래픽에서 나온 서버 측 히스토그램으로 해야 한다.

## 28.3 기준선 측정과 회귀 감지

### 기준선은 파일로 남긴다

성능은 기억이 아니라 기록으로 관리한다. autocannon의 프로그래밍 방식 API를 쓰면 측정 결과를 구조화된 JSON으로 남길 수 있다.

```js
// bench/run.js — 시나리오를 반복 측정해 중앙값을 기준선으로 기록한다
import autocannon from 'autocannon'
import { writeFile } from 'node:fs/promises'

const SCENARIOS = [
  { name: 'recipe_by_id', url: 'http://127.0.0.1:3000/recipes/42' },
  { name: 'health',       url: 'http://127.0.0.1:3000/health' },
]

async function measure(scenario) {
  const result = await autocannon({
    url: scenario.url,
    connections: 50,
    duration: 20,
    warmup: { connections: 10, duration: 5 }, // JIT와 커넥션 풀을 데운다
  })
  if (result.non2xx > 0 || result.errors > 0) {
    throw new Error(`${scenario.name}: 실패 응답이 섞였다. 측정 무효`)
  }
  return { rps: result.requests.average, p99: result.latency.p99, p50: result.latency.p50 }
}

const median = (xs) => xs.slice().sort((a, b) => a - b)[Math.floor(xs.length / 2)]

const baseline = { node: process.version, createdAt: new Date().toISOString(), scenarios: {} }

for (const scenario of SCENARIOS) {
  // 한 번의 측정은 노이즈다. 3회 반복해 중앙값을 취한다
  const runs = []
  for (let i = 0; i < 3; i++) runs.push(await measure(scenario))
  baseline.scenarios[scenario.name] = {
    rps: median(runs.map((r) => r.rps)),
    p50: median(runs.map((r) => r.p50)),
    p99: median(runs.map((r) => r.p99)),
  }
}

await writeFile('bench/baseline.json', JSON.stringify(baseline, null, 2))
```

핵심은 세 가지다. 실패 응답이 섞이면 예외로 중단한다는 것, 한 번이 아니라 여러 번 재고 중앙값을 쓴다는 것(평균이 아니라 중앙값인 이유는 28.1과 같다 — 한 번의 이상치가 평균을 오염시킨다), 그리고 런타임 버전을 함께 기록한다는 것이다. Node.js 마이너 버전 업그레이드만으로도 처리량이 10% 이상 변하는 일이 드물지 않으므로, 버전 없는 기준선은 나중에 해석할 수 없다.

### 비교 실험 설계

기준선의 진짜 쓸모는 "무엇이 더 빠른가"라는 질문에 답할 때다. 22장에서 세 프로토콜로 같은 기능을 구현했다면, 비교는 다음 표처럼 설계한다.

| 축 | 수준 | 통제할 것 |
|---|---|---|
| 프로토콜 | HTTP/JSON, GraphQL, gRPC | 동일한 페이로드 크기와 필드 |
| 리버스 프록시 | 없음, HAProxy 경유 | 동일한 백엔드 인스턴스 수 |
| 인스턴스 수 | 1, 4(cluster) | 동일한 커넥션 총량 |

한 번에 한 축만 바꾼다. 프로토콜을 gRPC로 바꾸면서 동시에 프록시를 넣으면, 결과가 좋아져도 어느 쪽 덕분인지 알 수 없다. 그리고 각 조합에서 반드시 **부하 수준을 여러 단계로** 잰다. 커넥션 25, 50, 100, 200으로 올려가며 rps와 p99를 함께 기록하면 두 가지가 드러난다. 처리량이 더 이상 오르지 않는 포화점, 그리고 그 이후 지연이 선형으로 치솟는 구간이다. 단일 부하 수준의 측정 하나로는 이 곡선을 알 수 없고, 곡선을 모르면 용량 계획을 세울 수 없다.

프록시 유무 비교에서 흔히 놓치는 점이 있다. 프록시는 대개 p50을 조금 나쁘게 만들고(홉이 하나 늘었으니 당연하다) p99를 크게 좋게 만든다. 여러 백엔드로 분산되면서 한 인스턴스의 GC 정지에 요청이 갇히는 일이 줄기 때문이다. 평균만 보면 프록시가 손해로 보이고, 백분위수를 보면 이득으로 보인다. 28.1의 주장을 실측으로 확인할 수 있는 좋은 실험이다.

### 노이즈를 줄이고 CI에서 회귀를 잡는다

CI 러너는 성능 측정에 최악의 환경이다. 공유 하드웨어이고, 이웃 작업의 부하가 보이지 않으며, CPU 할당량이 가변적이다. 이 환경에서 유의미한 신호를 얻으려면 노이즈를 억제하는 장치가 필요하다.

- **여러 번 재고 중앙값을 쓴다.** 최소 3회, 가능하면 5회.
- **절대값 대신 비율로 판단한다.** "p99가 50ms 이하" 대신 "기준선 대비 p99가 20% 이상 악화되지 않을 것".
- **임계값을 넉넉히 잡는다.** CI에서 10% 임계값은 거의 매일 거짓 경보를 낸다. 20~25%에서 시작해 실제 거짓 양성 비율을 보고 조정한다.
- **한 번의 실패로 빌드를 깨뜨리지 않는다.** 첫 실패 시 자동으로 한 번 더 측정하고, 두 번 연속 초과할 때만 실패로 처리한다.
- **부하 생성기와 대상을 같은 러너에 두었다면 그 사실을 기록한다.** 이 구성의 측정값은 서버 성능이 아니라 "서버+클라이언트 합산"이다. 상대 비교에는 여전히 쓸 수 있지만, 절대값으로 인용하면 안 된다.

```js
// bench/check.js — 기준선과 비교해 회귀를 판정한다
import { readFile } from 'node:fs/promises'

const THRESHOLD = { rps: 0.80, p99: 1.25 } // rps는 80% 미만, p99는 125% 초과면 회귀

const baseline = JSON.parse(await readFile('bench/baseline.json', 'utf8'))
const current = JSON.parse(await readFile('bench/current.json', 'utf8'))

const failures = []
for (const [name, base] of Object.entries(baseline.scenarios)) {
  const now = current.scenarios[name]
  if (!now) { failures.push(`${name}: 측정 누락`); continue }
  if (now.rps < base.rps * THRESHOLD.rps) {
    failures.push(`${name}: rps ${base.rps.toFixed(0)} → ${now.rps.toFixed(0)}`)
  }
  if (now.p99 > base.p99 * THRESHOLD.p99) {
    failures.push(`${name}: p99 ${base.p99}ms → ${now.p99}ms`)
  }
}

if (failures.length > 0) {
  console.error('성능 회귀 감지:\n' + failures.map((f) => `  - ${f}`).join('\n'))
  process.exit(1)
}
console.log('성능 회귀 없음')
```

기준선 갱신은 자동화하지 않는다. 의도적인 변경(더 무거운 검증 로직 추가 등)으로 성능이 나빠졌다면 사람이 판단해 기준선을 커밋에 포함시켜야 한다. 자동 갱신은 매일 3%씩 느려지는 것을 아무도 눈치채지 못하게 만드는 가장 확실한 방법이다.

## 28.4 SLO/SLA 수립하기

### 세 단어의 차이

세 용어가 자주 뒤섞여 쓰이지만 층위가 다르다.

- **SLI(Service Level Indicator, 서비스 수준 지표)**는 측정값이다. "성공한 요청의 비율", "p99 응답 시간" 같은 것. 숫자 그 자체이고 목표가 없다.
- **SLO(Service Level Objective, 서비스 수준 목표)**는 SLI에 붙인 내부 목표다. "지난 30일 동안 요청의 99.9%가 300ms 이내에 성공한다". 위반해도 계약상 책임은 없지만, 엔지니어링 우선순위를 바꾼다.
- **SLA(Service Level Agreement, 서비스 수준 협약)**는 고객과 맺은 계약이다. 위반하면 환불이나 크레딧 같은 금전적 결과가 따른다.

이 셋의 관계에는 하나의 철칙이 있다. **SLA는 SLO보다 반드시 느슨해야 한다.** SLO를 99.9%로 잡았다면 SLA는 99.5% 정도여야 한다. SLO 위반은 "고쳐야 한다"는 내부 신호이고, 그 신호와 계약 위반 사이에 완충 구간이 있어야 대응할 시간이 생긴다. SLO와 SLA를 같은 값으로 두면 SLO를 어기는 순간이 곧 돈을 잃는 순간이 되고, 조직은 SLO를 정직하게 측정하기를 그만둔다.

### 쓸 만한 SLO를 세우는 절차

**1단계, 사용자 여정에서 SLI를 고른다.** SLI는 시스템 내부 지표가 아니라 사용자가 겪는 것이어야 한다. CPU 사용률은 SLI가 아니다. 사용자는 CPU가 90%든 10%든 관심이 없다. "레시피 상세 페이지 조회가 성공하고 300ms 안에 끝났는가"가 SLI다. 대부분의 서비스는 두 종류로 충분하다. 가용성(성공 요청 / 유효 요청)과 지연(임계값 이내에 끝난 요청 / 성공 요청)이다.

여기서 "유효 요청"의 정의가 중요하다. 클라이언트가 잘못 보낸 400 응답은 서비스의 잘못이 아니므로 분모에서 빼거나 성공으로 센다. 반대로 502와 503, 그리고 클라이언트가 타임아웃으로 끊은 요청은 실패다. 이 경계를 문서로 못 박지 않으면 사고 후 회의에서 매번 다시 다툰다.

**2단계, 목표치를 정한다.** 출발점은 야심이 아니라 관측이다. 지난 4주의 실제 성능을 그려보고, 그 값보다 아주 조금 엄격하게 잡는다. 이미 달성 못 하는 목표를 세우면 첫날부터 위반 상태이므로 아무도 신경 쓰지 않게 된다. 반대로 현재보다 느슨하게 잡으면 성능이 나빠져도 경보가 울리지 않는다.

지연 SLO는 백분위수 형태("p99 < 300ms")보다 **비율 형태**("요청의 99%가 300ms 이내")로 쓰는 편이 낫다. 후자는 시간 창 전체에 걸쳐 성공/실패로 셀 수 있어 여러 인스턴스와 여러 시간 구간에 걸쳐 더할 수 있기 때문이다. 28.1에서 본 "백분위수는 합칠 수 없다"는 문제를 SLO 정의 단계에서 피해가는 방법이다.

**3단계, 측정 창을 정한다.** 롤링 30일이 표준이다. 창이 짧으면 짧은 사고 하나에 과민 반응하고, 창이 길면 문제가 오래 묻힌다. 캘린더 월 대신 롤링 창을 쓰면 매월 1일에 예산이 리셋되면서 위험한 배포가 몰리는 현상을 막을 수 있다.

**4단계, 오류 예산을 계산한다.** 오류 예산(error budget)은 SLO의 여집합이다. 가용성 목표가 99.9%면 예산은 0.1%다. 30일 기준으로 환산하면 다음과 같다.

| 가용성 목표 | 30일 오류 예산 | 100만 요청 기준 실패 허용 |
|---|---|---|
| 99% | 7시간 12분 | 10,000건 |
| 99.9% | 43분 12초 | 1,000건 |
| 99.95% | 21분 36초 | 500건 |
| 99.99% | 4분 19초 | 100건 |

이 표는 목표치 한 자리 차이의 비용을 보여준다. 99.9%에서 99.99%로 가면 허용 다운타임이 10분의 1로 줄고, 이를 달성하려면 다중 리전, 자동 장애 조치, 배포 자동화 같은 것들이 전부 필요해진다. "가능한 한 높게"가 답이 아닌 이유다.

### 오류 예산은 배포 속도를 조절하는 장치다

오류 예산의 진짜 목적은 사고를 세는 것이 아니라 **개발 속도와 안정성 사이의 갈등을 숫자로 중재하는 것**이다. 규칙은 단순하다.

- 예산이 남아 있으면 배포한다. 실험적 기능도, 리스크 있는 마이그레이션도 진행한다. 예산은 쓰라고 있는 것이다.
- 예산이 소진되면 기능 배포를 멈추고 안정성 작업만 한다. 예산이 회복될 때까지.

이 규칙이 있으면 "이번 배포를 해도 되는가"라는 논쟁이 사라진다. 예산 잔액이 답한다. 반대로 예산이 계속 남아돈다면 그것도 신호다. SLO가 너무 느슨하거나, 팀이 필요 이상으로 조심하느라 기능 출시가 느려지고 있다는 뜻이다.

경보는 예산 잔액이 아니라 **소진율(burn rate)**에 걸어야 한다. 소진율 1은 30일 동안 예산을 정확히 다 쓰는 속도다. 소진율 14.4가 1시간 지속되면 전체 예산의 2%가 사라진다. 구글 SRE 문헌이 제안하는 다중 창 경보는 이 두 축을 조합한다.

| 소진율 | 관측 창 | 소진되는 예산 | 대응 |
|---|---|---|---|
| 14.4배 | 1시간 | 2% | 즉시 호출(page) |
| 6배 | 6시간 | 5% | 즉시 호출 |
| 1배 | 3일 | 10% | 티켓 |

짧은 창만 보면 순간적인 스파이크에 새벽마다 깨고, 긴 창만 보면 심각한 장애를 몇 시간 뒤에 안다. 두 창을 동시에 만족할 때만 경보를 울리는 방식(짧은 창과 긴 창의 AND 조건)이 거짓 경보를 줄이면서 반응 속도를 유지한다.

## 28.5 성능 프로파일링: CPU 프로파일과 힙 스냅숏

### CPU 프로파일 뜨기

부하 테스트가 "느리다"를 알려준다면, 프로파일러는 "어디가"를 알려준다. Node.js는 외부 도구 없이 V8 샘플링 프로파일러를 켤 수 있다.

```bash
# 프로세스가 종료될 때 .cpuprofile 파일이 디렉터리에 기록된다
node --cpu-prof --cpu-prof-dir=./profiles recipe-api/server.js

# 다른 터미널에서 부하를 준 뒤 SIGINT로 종료한다
npx autocannon -c 50 -d 20 http://127.0.0.1:4000/recipes/42
```

생성된 `.cpuprofile` 파일은 Chrome DevTools의 Performance 패널에서 "Load profile"로 연다. 여기서 봐야 할 것은 두 가지 시간이다. **총 시간(total time)**은 그 함수와 그 함수가 부른 모든 것의 합이고, **자기 시간(self time)**은 그 함수 본문에서만 소비한 시간이다. 최적화 대상은 자기 시간이 큰 함수다. 총 시간이 큰 함수는 대개 라우터나 미들웨어 체인처럼 "아래에 전부 들어 있는" 프레임이라 손댈 것이 없다.

플레임 그래프(flame graph)를 읽는 규칙은 세 가지다. 가로축은 시간 순서가 아니라 **표본 수의 비율**이므로, 넓은 프레임이 비싼 프레임이다. 세로축은 호출 스택 깊이이며, 아래가 호출자, 위가 피호출자다. 그리고 **넓고 평평한 꼭대기**를 찾는다. 그것이 실제로 CPU를 태우고 있는 코드다. Node.js 서비스에서 자주 보이는 넓은 꼭대기는 `JSON.stringify`, `Buffer` 변환, 정규식 실행, 그리고 회색으로 표시되는 GC 프레임이다.

전체 표본에서 GC가 차지하는 비율은 특히 중요한 신호다. 5%를 넘으면 할당이 과도하다는 뜻이고, 이때 손댈 곳은 GC 옵션이 아니라 요청당 만들어지는 객체의 수다.

### 힙 스냅숏 두 장으로 누수 찾기

메모리 누수 진단의 표준 절차는 스냅숏 비교다. 원리는 단순하다. 서비스가 안정 상태라면 요청 처리 전후의 살아 있는 객체 집합은 같아야 한다. 다르다면 무언가가 참조를 놓지 않고 있다.

```bash
node --heap-prof --heap-prof-dir=./profiles recipe-api/server.js
```

`--heap-prof`는 시간에 따른 할당 위치를 샘플링하므로 "어디서 많이 할당하는가"를 알려준다. 하지만 "무엇이 해제되지 않는가"는 힙 스냅숏이 답한다.

```js
// heap.js — 신호를 받으면 힙 스냅숏을 파일로 남긴다
import { writeHeapSnapshot } from 'node:v8'

process.on('SIGUSR2', () => {
  // 주의: 스냅숏 생성은 이벤트 루프를 멈춘다. 힙 1GB에 수 초가 걸릴 수 있다
  const file = writeHeapSnapshot(`/tmp/heap-${process.pid}-${Date.now()}.heapsnapshot`)
  console.log('heap snapshot written', file)
})
```

절차는 세 장을 뜨는 것이 정석이다. 첫째, 서비스를 띄우고 부하를 한 차례 준 뒤 첫 스냅숏(A)을 뜬다. 워밍업으로 생긴 정상적인 캐시를 A에 포함시켜 기준으로 삼기 위해서다. 둘째, 같은 부하를 한 번 더 주고 스냅숏(B)을 뜬다. 셋째, 다시 같은 부하 후 스냅숏(C)을 뜬다. DevTools의 Memory 패널에서 C를 선택하고 비교 대상(Comparison)을 B로 지정하면, **B와 C 사이에 새로 할당되었고 C 시점에도 살아 있는 객체**만 남는다. A→B에서만 늘고 B→C에서 늘지 않는 것은 캐시가 채워진 것이고, 두 구간 모두에서 선형으로 늘어나는 것이 누수다.

용의자를 찾았다면 그 객체를 선택하고 Retainers(보유자) 트리를 따라 올라간다. 루트까지의 경로가 누수의 원인이다. Node.js 서비스에서 이 경로 끝에 자주 등장하는 것은 무한히 자라는 `Map` 캐시, 해제되지 않은 이벤트 리스너, 클로저에 잡힌 요청 객체, 그리고 `setInterval` 콜백이다.

### clinic.js와 이벤트 루프 관측

`clinic` 도구군은 위 작업들을 진단 순서대로 묶어준다.

```bash
npx clinic doctor -- node recipe-api/server.js    # 무엇이 문제인지 분류한다
npx clinic flame -- node recipe-api/server.js     # CPU 플레임 그래프
npx clinic bubbleprof -- node recipe-api/server.js # 비동기 흐름의 대기 시간
```

`clinic doctor`부터 시작하는 것이 순서다. CPU 사용률, 이벤트 루프 지연, 힙 사용량, 활성 핸들 수를 함께 그려놓고 "이벤트 루프가 막혀 있다", "I/O 대기가 지배적이다", "GC 압력이 높다" 같은 1차 분류를 내려준다. 분류에 따라 다음 도구가 갈린다. 이벤트 루프가 막혔으면 `flame`, I/O 대기가 문제면 `bubbleprof`다.

상시 관측용으로는 이벤트 루프 지연 히스토그램을 지표로 내보내는 것이 가장 비용 대비 효과가 좋다.

```js
import { monitorEventLoopDelay } from 'node:perf_hooks'

const loop = monitorEventLoopDelay({ resolution: 10 })
loop.enable()

setInterval(() => {
  // 나노초 단위이므로 밀리초로 변환한다
  const p99 = loop.percentile(99) / 1e6
  if (p99 > 100) console.warn({ eventLoopDelayP99: p99 }, '이벤트 루프 지연 경고')
  loop.reset() // 창을 리셋해야 최근 값을 본다
}, 10_000).unref()
```

이벤트 루프 지연의 p99가 커지는 것은 거의 항상 다른 모든 지표보다 먼저 나타나는 선행 신호다. 이 값이 100ms를 넘으면 어딘가에서 동기 작업이 실행되고 있다는 뜻이고, 사용자가 겪는 p99에 그대로 더해진다.

### 프로덕션에서 안전하게 프로파일 뜨기

`--cpu-prof`는 프로세스 종료 시에 파일을 쓰므로 프로덕션에 쓰기 곤란하다. `--inspect`로 디버거 포트를 여는 것은 더 나쁘다. 그 포트에 접근하면 임의 코드 실행이 가능하므로 절대 `0.0.0.0`에 바인딩해서는 안 된다. 프로덕션에서는 인스펙터 세션을 프로세스 내부에서 프로그래밍 방식으로 여는 것이 정답이다.

```js
// profiler.js — 신호를 받으면 정해진 시간 동안만 프로파일을 수집한다
import { Session } from 'node:inspector/promises'
import { writeFile } from 'node:fs/promises'

let capturing = false

async function captureCpuProfile(durationMs = 20_000) {
  if (capturing) return // 중복 수집 방지
  capturing = true
  const session = new Session()
  session.connect()
  try {
    await session.post('Profiler.enable')
    // 기본 샘플링 간격은 1000µs. 값을 키우면 오버헤드가 준다
    await session.post('Profiler.setSamplingInterval', { interval: 1000 })
    await session.post('Profiler.start')
    await new Promise((resolve) => setTimeout(resolve, durationMs))
    const { profile } = await session.post('Profiler.stop')
    const file = `/tmp/cpu-${process.pid}-${Date.now()}.cpuprofile`
    await writeFile(file, JSON.stringify(profile))
    console.log('cpu profile written', file)
  } finally {
    session.disconnect() // 반드시 닫는다. 열린 세션은 그 자체로 오버헤드다
    capturing = false
  }
}

// SIGUSR1은 Node.js가 디버거 활성화에 예약해 두었으므로 SIGUSR2를 쓴다
process.on('SIGUSR2', () => { captureCpuProfile().catch((err) => console.error(err)) })
```

운영 규칙은 네 가지다. 첫째, 한 인스턴스만 프로파일한다. 가능하면 로드 밸런서에서 그 인스턴스를 빼고(26장 참조) 낮은 부하 상태에서 뜬 뒤 되돌린다. 둘째, 수집 시간을 20~30초로 제한한다. 샘플링 프로파일러의 오버헤드는 대개 5% 미만이지만 무기한 켜둘 이유가 없다. 셋째, 힙 스냅숏은 CPU 프로파일과 성격이 다르다는 것을 기억한다. 스냅숏은 샘플링이 아니라 전수 조사이고 이벤트 루프를 완전히 멈추므로, 트래픽을 받는 인스턴스에서 뜨면 그 순간이 곧 장애다. 반드시 로드 밸런서에서 분리한 뒤에 뜬다. 넷째, 생성된 프로파일 파일에는 힙에 있던 문자열 — 즉 실제 사용자 데이터 — 이 포함될 수 있으므로 접근 통제 대상으로 다룬다.

## 28.6 흔한 성능 병목과 처방

실제 현장에서 발견되는 병목은 놀랄 만큼 반복적이다. 아래 열 가지가 대부분을 차지한다.

**1) 동기 함수 호출.** 요청 경로에 `readFileSync`, `crypto.pbkdf2Sync`, `zlib.gzipSync`, 동기 `bcrypt` 같은 것이 하나라도 있으면 그 시간 동안 모든 요청이 멈춘다. *진단*: 이벤트 루프 지연 p99 급등, 플레임 그래프에서 `...Sync` 프레임의 자기 시간. *처방*: 비동기 대응 API로 교체하고, 대체 불가능한 CPU 작업(해싱, 암호화)은 워커 스레드로 옮긴다. 설정 파일 읽기처럼 한 번만 하면 되는 것은 부팅 시점으로 이동한다. *효과*: 지연 p99가 동기 작업 시간만큼 즉시 감소한다. 종종 수백 밀리초 단위다.

**2) 과도한 JSON 직렬화.** 응답 객체가 클수록 `JSON.stringify`가 CPU를 지배한다. *진단*: 플레임 그래프에서 `stringify`/`parse`의 자기 시간이 5% 이상. *처방*: Fastify의 응답 스키마를 채워 `fast-json-stringify`가 스키마 기반 직렬화 코드를 생성하게 한다. 응답에서 쓰지 않는 필드를 제거한다. web-api처럼 프로듀서 응답을 거의 그대로 전달하는 경우, 파싱했다가 다시 직렬화하지 말고 본문을 스트림으로 통과시킨다. *효과*: 직렬화 구간에서 2~4배.

**3) 정규식 백트래킹.** `(a+)+$` 같은 중첩 수량자는 입력 길이에 지수적으로 반응한다(ReDoS). *진단*: 특정 입력에서만 이벤트 루프가 수 초간 멈추고, 프로파일에 `RegExp` 프레임이 홀로 서 있다. 입력 길이를 2배로 늘렸을 때 시간이 4배 이상 늘면 확정이다. *처방*: 중첩 수량자를 제거하고 앵커를 붙인다. 입력 길이를 사전에 제한한다. 사용자 제공 패턴을 실행해야 한다면 선형 시간을 보장하는 RE2 엔진을 쓴다. *효과*: 지수 시간에서 선형 시간으로.

**4) 로깅 과다.** 요청당 로그 열 줄은 직렬화 비용에 더해 stdout 쓰기 비용을 낳는다. 특히 stdout이 파이프로 연결되어 있고 소비자가 느리면 쓰기가 블로킹된다. *진단*: 프로파일에서 로거와 그 직렬화가 차지하는 비율, 로그 레벨을 낮췄을 때의 rps 변화. *처방*: `pino` 같은 저비용 로거를 쓰고, 프로덕션 레벨을 `info`로 고정하고, 고빈도 이벤트는 샘플링한다. 전송 처리는 별도 스레드로 분리한다(31장 참조). *효과*: 로그가 과도한 서비스에서 처리량 10~30% 회복.

**5) 커넥션 풀 부족.** 리틀의 법칙이 알려주는 상한에 걸린 상태다. *진단*: 부하를 올려도 rps가 평탄하고 지연만 선형 증가한다. 풀의 대기 큐 길이 지표가 0이 아니다. *처방*: `필요 풀 크기 = 목표 rps × 평균 쿼리 시간`으로 계산해 조정하되, 데이터베이스 쪽 상한(대개 코어 수의 2~4배)을 넘기지 않는다. 풀 획득에 타임아웃을 걸어 무한 대기를 막는다. *효과*: 상한이 계산값까지 선형으로 이동한다.

**6) keep-alive 미사용.** 업스트림 호출마다 TCP와 TLS 핸드셰이크를 새로 한다. *진단*: `ss -s`의 TIME_WAIT 급증, 프로파일의 TLS 프레임, 업스트림 호출 지연의 최솟값이 왕복 시간의 두세 배. *처방*: `undici`의 `Agent`/`Pool`을 전역 디스패처로 설정해 커넥션을 재사용한다. 서버 쪽 `keepAliveTimeout`은 앞단 로드 밸런서의 유휴 타임아웃보다 **길게** 잡는다. 반대면 프록시가 재사용하려던 커넥션을 서버가 먼저 닫아 간헐적 502가 발생한다. *효과*: 업스트림 호출 지연에서 핸드셰이크 왕복만큼 감소. TLS면 요청당 수 밀리초에서 수십 밀리초.

**7) N+1 쿼리.** 목록 하나를 얻고 각 항목마다 추가 조회를 한다. *진단*: 분산 추적에서 요청 하나에 매달린 스팬 수가 목록 길이에 비례한다(31장 참조). 요청당 쿼리 수를 지표로 내보내면 즉시 보인다. *처방*: `IN` 절 배치 조회나 조인으로 바꾼다. GraphQL 리졸버라면 DataLoader로 같은 틱의 조회를 모은다. *효과*: 왕복 N회가 1회로. 목록 100개면 지연이 한 자릿수 배로 줄어든다.

**8) 압축 CPU.** 모든 응답을 최고 레벨로 gzip하면 CPU가 압축에 소진된다. 200바이트 JSON을 압축하면 전송량은 거의 안 줄고 CPU만 쓴다. *진단*: 프로파일에서 `zlib` 프레임 비중. *처방*: 압축 임계값을 1KB 이상으로 두고, 레벨을 기본보다 낮춘다. 가능하면 압축을 리버스 프록시나 CDN으로 이관한다. 정적 자산은 빌드 시점에 미리 압축해 둔다. *효과*: JSON API에서 CPU 10~20% 회수.

**9) 큰 객체 복사.** 미들웨어마다 `{ ...req.body }`로 객체를 펼치면 요청당 사본이 여러 벌 생긴다. *진단*: GC 표본 비율 상승, 힙 프로파일에서 특정 지점의 할당량 집중. *처방*: 불필요한 스프레드와 `structuredClone`을 제거한다. `Buffer.subarray`는 메모리를 공유하지만 `Buffer.from`은 복사한다는 차이를 정확히 쓴다. 큰 페이로드는 전체를 메모리에 올리지 말고 스트림으로 처리한다. *효과*: GC 비중이 낮아지면서 꼬리 지연이 개선된다. p99 개선폭이 p50보다 크게 나타나는 것이 특징이다.

**10) 이벤트 루프 지연 그 자체.** 위 아홉 가지의 공통 증상이자 독립된 항목이기도 하다. 반복문이 수만 건을 한 번에 돌면 그 시간 동안 새 요청을 받지 못한다. *진단*: `monitorEventLoopDelay`의 p99. *처방*: 배치 크기를 상한으로 제한하고, 긴 루프는 `setImmediate`로 청크를 나눠 사이사이 I/O가 진행되게 한다. 근본적으로 CPU 바운드인 작업은 워커 스레드나 별도 서비스로 분리한다. *효과*: 이벤트 루프 지연 p99가 곧 응답 지연 p99의 하한이므로, 여기서 줄인 만큼 모든 엔드포인트의 꼬리가 함께 개선된다.

이 목록이 주는 실무적 교훈은 순서에 있다. 위에서 아래로 갈수록 진단은 어려워지고 개선 효과는 완만해진다. 성능 작업을 시작할 때는 항상 1번부터 확인한다. 요청 경로에 동기 호출이 하나 남아 있는 서비스에서 JSON 직렬화를 최적화하는 것은 순서가 뒤바뀐 일이다.

## 요약

- 평균 응답 시간은 꼬리가 긴 분포에서 아무도 겪지 않는 값을 만들어낸다. p50, p95, p99, p99.9는 각각 다른 원인에 반응하므로 함께 본다.
- 백분위수는 인스턴스에 대해서도 시간에 대해서도 평균낼 수 없다. 집계는 히스토그램 버킷으로 하고, 백분위수는 합친 히스토그램에서 다시 계산한다.
- 팬아웃 N개 호출 중 하나라도 p99를 넘을 확률은 `1 - 0.99^N`이다. N=10에서 9.6%, N=100에서 63.4%이므로, 내부 서비스의 p99가 사용자의 p90 또는 p50이 된다.
- 리틀의 법칙(`L = λW`)은 처리량과 지연을 잇는다. 풀 크기 같은 고정 자원에서 최대 처리량을 역산할 수 있고, 부하 곡선의 포화점 해석 근거가 된다.
- 부하 테스트는 클라이언트 병목, 커넥션 미재사용, 워밍업 누락, 캐시 히트 편향, 하드웨어 차이, 조율 누락이라는 여섯 가지 방식으로 거짓말한다. 오류 응답이 섞인 측정은 무효다.
- SLI는 사용자 여정에서 고르고, SLO는 관측된 성능보다 조금 엄격하게, SLA는 SLO보다 느슨하게 잡는다. 오류 예산은 배포 속도를 조절하는 장치이며 경보는 잔액이 아니라 소진율에 건다.
- 프로파일링은 자기 시간이 큰 넓고 평평한 프레임을 찾는 일이고, 누수 진단은 스냅숏 세 장의 비교다. 프로덕션에서는 인스펙터 세션을 프로세스 내부에서 시간 제한을 두고 연다.
- Node.js 병목은 대부분 열 가지 안에 있다. 동기 호출부터 확인하는 것이 언제나 옳은 순서다.

## 연습문제

1. 21장의 recipe-api에 인위적인 지연을 주입하라. 요청의 1%에 200ms를 추가하고 나머지는 5ms로 응답하게 한 뒤, web-api가 이 서비스를 1회 호출하는 경로와 10회 병렬 호출해 모두 기다리는 경로를 각각 만든다. 두 경로를 autocannon으로 측정해 사용자 관점의 p50과 p99를 비교하고, 관측된 값이 `1 - 0.99^N` 계산과 얼마나 일치하는지 서술하라. 일치하지 않는다면 독립 가정이 깨진 지점을 찾아라.

2. recipe-api의 응답 처리 경로에 `JSON.parse`로 5MB 파일을 읽어 파싱하는 동기 코드를 넣고, 100요청당 1회 실행되게 하라. `monitorEventLoopDelay`로 이벤트 루프 지연 히스토그램을, autocannon으로 응답 지연을 동시에 측정해 두 p99의 관계를 그래프로 그려라. 그다음 이 작업을 워커 스레드로 옮겨 같은 측정을 반복하고, p50과 p99 중 어느 쪽이 더 크게 개선되는지와 그 이유를 설명하라.

3. 자신이 운영하거나 만든 서비스 하나에 대해 SLI 두 개(가용성, 지연)를 정의하고, 최근 4주 데이터로 달성 가능한 SLO와 30일 오류 예산을 계산하라. 그리고 소진율 14.4배/1시간과 6배/6시간 조건을 AND로 묶은 경보 규칙을 작성한 뒤, 지난 4주 데이터에 대입해 이 규칙이 몇 번 발화했을지 세어라. 발화 횟수가 0이거나 10회를 넘는다면 SLO 목표치를 어떻게 조정해야 하는지 논하라.
