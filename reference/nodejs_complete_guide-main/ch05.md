# 5장. 콜백 기반 제어 흐름 패턴

4장에서 연속 전달 스타일(continuation-passing style)과 Node.js의 오류 우선 콜백 규약을 익혔다. 그러나 콜백 하나를 다루는 법을 안다고 해서 콜백 수십 개가 얽힌 프로그램을 다룰 수 있는 것은 아니다. 동기 코드에서는 언어가 공짜로 제공하던 순차 실행, 반복, 조건 분기, 오류 전파를 비동기 세계에서는 개발자가 직접 조립해야 한다. 이 장은 그 조립 기법을 다룬다. Promise와 `async/await`가 표준이 된 지금 왜 여전히 콜백 제어 흐름을 배우는가에 대한 답은 5.6절에서 하겠지만, 미리 말하면 이 장에서 익히는 실행 모델은 문법이 바뀌어도 그대로 남기 때문이다.

이 장 전체를 관통하는 예제는 **웹 스파이더(web spider)**다. URL을 입력받아 해당 페이지를 내려받아 파일로 저장하고, 문서에서 링크를 추출해 재귀적으로 따라가는 프로그램이다. 5.1절에서 가장 순진한 형태로 만든 다음, 절이 진행될수록 순차·병렬·동시성 제한 버전으로 발전시킨다.

## 5.1 콜백 지옥의 해부

### 왜 콜백 지옥이 생기는가

콜백 지옥(callback hell)은 게으름의 산물이 아니다. 오히려 각 단계를 "지금 필요한 자리에서 바로" 처리하려는 자연스러운 충동의 산물이다. 비동기 함수의 결과는 반환값이 아니라 콜백의 인자로 도착하므로, 그 결과를 쓰려면 콜백 **안**으로 들어가야 한다. 결과 세 개가 순서대로 필요하면 세 겹 안으로 들어간다. 각 단계마다 오류 검사를 붙이면 검사 코드도 함께 중첩된다. 이렇게 만들어진 삼각형 모양의 코드를 흔히 "죽음의 피라미드(pyramid of doom)"라고 부른다.

### 어떻게 동작하는가

스파이더의 최소 요구사항은 이렇다. (1) URL을 파일 경로로 변환한다. (2) 이미 받은 파일이면 건너뛴다. (3) 아니면 내려받는다. (4) 저장할 디렉터리를 만든다. (5) 파일을 쓴다. 각 단계가 비동기이므로 다섯 단계가 그대로 다섯 겹이 된다.

```js
// spider-v1.js — 의도적으로 나쁘게 작성한 버전
import fs from 'node:fs'
import path from 'node:path'
import { urlToFilename } from './utils.js'

export function spider (url, cb) {
  const filename = urlToFilename(url)
  fs.access(filename, err => {
    if (err && err.code === 'ENOENT') {
      // 아직 받지 않은 페이지다
      fetch(url)
        .then(res => res.text())
        .then(body => {
          fs.mkdir(path.dirname(filename), { recursive: true }, err => {
            if (err) {
              cb(err)
            } else {
              fs.writeFile(filename, body, err => {
                if (err) {
                  cb(err)
                } else {
                  cb(null, filename, true)
                }
              })
            }
          })
        })
        .catch(err => cb(err))
    } else if (err) {
      cb(err) // ENOENT가 아닌 진짜 오류
    } else {
      cb(null, filename, false) // 이미 받은 페이지
    }
  })
}
```

동작 자체는 맞다. 문제는 이 코드가 가진 성질이다.

첫째, **들여쓰기가 의미를 잃는다.** 동기 코드에서 들여쓰기 깊이는 논리적 중첩(조건, 반복)을 뜻하지만 여기서는 단순히 "몇 번째 비동기 단계인가"를 뜻한다. 정보량이 없는 깊이가 화면 폭을 잡아먹는다.

둘째, **오류 처리가 복제된다.** `if (err) { cb(err) } else { ... }`가 단계마다 반복된다. 단계 하나를 추가하면 처리 코드도 하나 늘고, `else` 블록 안에 또 한 겹이 생긴다. 복제된 코드는 한 곳만 빠뜨려도 오류가 조용히 사라지는 경로를 만든다.

셋째, **클로저가 무겁다.** 가장 안쪽 콜백은 `url`, `filename`, `body`를 모두 클로저로 붙잡고 있다. 페이지 본문 `body`가 수 MB라면, 파일 쓰기가 끝날 때까지 그 메모리는 해제되지 않는다. 중첩이 깊어질수록 살아 있는 클로저 체인이 길어지고, 이는 곧 메모리 사용량과 GC 압력으로 나타난다.

넷째, **재사용이 불가능하다.** 익명 함수로 인라인 작성된 각 단계는 이름이 없어서 다른 곳에서 호출할 수도, 단위 테스트를 붙일 수도 없다. 스택 트레이스에도 `<anonymous>`만 찍힌다.

### 실무 함정

콜백 지옥의 진짜 비용은 가독성이 아니라 **수정 비용**이다. "저장 전에 HTML을 정규화한다"는 요구가 들어오면 어느 겹에 넣을지 판단해야 하고, 넣는 순간 그 아래 전부가 한 칸 더 들어간다. 리뷰어는 diff에서 공백만 바뀐 줄과 실제로 바뀐 줄을 구분하지 못한다. 이 시점부터 사람들은 코드를 고치는 대신 옆에 새 함수를 만들기 시작하고, 중복 로직이 번식한다.

## 5.2 콜백 규율(callback discipline)

### 왜 필요한가

콜백 지옥은 라이브러리 없이도 상당 부분 해소된다. 필요한 것은 새로운 도구가 아니라 **일관되게 적용하는 몇 가지 규칙**이다. 이를 콜백 규율이라 부른다. 규율의 목표는 "중첩을 없애는 것"이 아니라 "중첩의 깊이를 코드의 논리적 복잡도에 비례하게 만드는 것"이다.

### 규칙 목록

**규칙 1 — 조기 반환(early return).** 콜백을 호출한 뒤에는 반드시 `return`한다. `if (err) { cb(err) } else { ... }` 대신 `if (err) { return cb(err) }`를 쓴다. 이것만으로 `else` 블록 하나가 통째로 사라지고 들여쓰기가 한 단계 줄어든다. 더 중요한 것은 안전성이다. `return`을 빠뜨리면 오류 콜백을 호출한 뒤에도 아래 코드가 계속 실행되어, 콜백이 두 번 호출되는 최악의 버그가 생긴다. `return cb(err)`에서 반환값 자체는 의미가 없다. 제어 흐름을 끊는 것이 목적이다.

**규칙 2 — 명명 함수로 분리한다.** 재사용 가능한 단위, 또는 이름을 붙이면 의도가 드러나는 단위는 인라인 익명 함수 대신 이름 있는 함수로 뽑는다. 클로저에 의존하지 않는 부분일수록 좋은 후보다. 이름이 있으면 스택 트레이스가 읽히고, 테스트가 가능해지며, 클로저로 붙잡는 변수 수가 줄어 메모리도 가벼워진다.

**규칙 3 — 모듈화한다.** 함수로 뽑는 것으로 부족하면 파일로 뽑는다. "다운로드", "링크 추출", "파일 저장"은 각각 독립 모듈이 될 수 있다. 모듈 경계는 자연스럽게 인터페이스를 강제하고, 인터페이스는 중첩을 끊는다.

**규칙 4 — 들여쓰기 깊이를 제한한다.** 한 함수 안에서 콜백 중첩은 두 단계를 넘기지 않는다는 상한을 팀 규칙으로 정한다. 세 번째 단계가 필요하면 그것은 함수를 나누라는 신호다. ESLint의 `max-nested-callbacks` 규칙(권장값 3)으로 기계적으로 강제할 수 있다.

**규칙 5 — 오류 처리를 한 곳으로 모은다.** 단계마다 흩어진 `cb(err)` 호출은 결국 같은 곳으로 향한다. 함수를 잘게 나누면 각 함수는 자기 오류만 상위로 넘기고, 최종 소비자 한 곳에서만 실제 처리(로깅, 재시도, 종료)를 한다.

### 코드

위 규칙을 스파이더에 적용하면 다음과 같다.

```js
// spider-v2.js — 규율을 적용한 버전
import fs from 'node:fs'
import path from 'node:path'
import { urlToFilename } from './utils.js'

function saveFile (filename, contents, cb) {
  fs.mkdir(path.dirname(filename), { recursive: true }, err => {
    if (err) {
      return cb(err) // 규칙 1: 조기 반환
    }
    fs.writeFile(filename, contents, cb) // 콜백을 그대로 위임
  })
}

function download (url, filename, cb) {
  console.log(`다운로드 시작: ${url}`)
  fetch(url)
    .then(res => {
      if (!res.ok) {
        throw new Error(`HTTP ${res.status} — ${url}`)
      }
      return res.text()
    })
    .then(body => saveFile(filename, body, err => {
      if (err) {
        return cb(err)
      }
      console.log(`다운로드 완료: ${url}`)
      cb(null, body)
    }))
    .catch(err => cb(err)) // 규칙 5: 오류 경로는 하나
}

export function spider (url, cb) {
  const filename = urlToFilename(url)
  fs.access(filename, err => {
    if (!err) {
      return cb(null, filename, false) // 이미 존재
    }
    if (err.code !== 'ENOENT') {
      return cb(err)
    }
    download(url, filename, err => {
      if (err) {
        return cb(err)
      }
      cb(null, filename, true)
    })
  })
}
```

중첩은 최대 두 단계로 줄었고, `saveFile`과 `download`는 각각 독립적으로 테스트할 수 있다. `fs.writeFile(filename, contents, cb)`처럼 콜백 시그니처가 같을 때 콜백을 그대로 넘기는 것도 유용한 기법이다. 다만 이 위임은 "아래 함수의 오류 규약이 내 규약과 정확히 같을 때"만 안전하다. 인자 개수나 의미가 다르면 감싸야 한다.

### 실무 함정

규율을 적용할 때 흔히 저지르는 실수는 **조기 반환을 넣으면서 정리(cleanup) 코드를 건너뛰는 것**이다. 파일 디스크립터를 열어 둔 상태에서 `return cb(err)`로 빠져나가면 디스크립터가 새어 나간다. 자원을 획득한 뒤의 조기 반환은 반드시 해제와 짝을 이뤄야 한다. 또 하나, 명명 함수로 뽑을 때 클로저 변수를 인자로 바꾸지 않고 상위 스코프에 그대로 두면 함수만 밖으로 나오고 결합은 그대로 남는다. 뽑을 때는 필요한 값을 명시적 인자로 받게 만들어야 진짜 분리다.

## 5.3 순차 실행과 순차 반복

### 왜 필요한가

스파이더를 재귀적으로 만들려면 페이지에서 링크를 뽑아 각 링크를 다시 스파이더에 넘겨야 한다. 링크가 몇 개인지는 실행 전에 알 수 없다. 동기 코드라면 `for` 루프 한 줄이면 끝이지만, 비동기 작업에서는 루프가 작동하지 않는다. `for` 루프는 각 반복의 완료를 기다리지 않고 끝까지 돌아 버린다. 개수를 미리 모르는 비동기 작업을 하나씩 순서대로 실행하려면 **반복을 재귀로 바꿔야 한다**.

순차 실행이 필요한 이유는 여러 가지다. 뒤 작업이 앞 작업의 결과를 입력으로 쓸 때, 외부 API가 요청 순서를 보장받아야 할 때, 그리고 가장 흔하게는 상대 서버나 로컬 자원에 부하를 주지 않기 위해서다.

### 어떻게 동작하는가

핵심은 **비동기 이터레이터 패턴**이다. 인덱스를 인자로 받는 함수를 정의하고, 각 단계의 콜백 안에서 인덱스를 하나 증가시켜 자기 자신을 다시 호출한다. 인덱스가 배열 끝에 닿으면 최종 콜백을 부르고 끝낸다.

```js
function iterate (index) {
  if (index === tasks.length) {
    return finish()      // 종료 조건
  }
  const task = tasks[index]
  task(() => iterate(index + 1))   // 완료 시 다음으로
}

function finish () { /* 모두 끝났다 */ }

iterate(0)
```

이 골격을 스파이더에 적용해 링크를 순차적으로 따라가게 만든다.

```js
// spider-v3.js — 순차 재귀 스파이더
import { getPageLinks } from './utils.js'
import path from 'node:path'

function spiderLinks (currentUrl, body, nesting, cb) {
  if (nesting === 0) {
    // 깊이 제한에 도달. 비동기성 보장을 위해 process.nextTick 사용 (4장 참조)
    return process.nextTick(cb)
  }

  const links = getPageLinks(currentUrl, body)
  if (links.length === 0) {
    return process.nextTick(cb)
  }

  function iterate (index) {
    if (index === links.length) {
      return cb()
    }
    spider(links[index], nesting - 1, err => {
      if (err) {
        return cb(err)   // 첫 오류에서 전체 중단
      }
      iterate(index + 1)
    })
  }

  iterate(0)
}

export function spider (url, nesting, cb) {
  const filename = urlToFilename(url)
  fs.readFile(filename, 'utf8', (err, body) => {
    if (err) {
      if (err.code !== 'ENOENT') {
        return cb(err)
      }
      return download(url, filename, (err, body) => {
        if (err) {
          return cb(err)
        }
        spiderLinks(url, body, nesting, cb)
      })
    }
    spiderLinks(url, body, nesting, cb)
  })
}
```

`nesting`은 재귀 깊이 제한이다. 이것이 없으면 스파이더는 링크가 이어지는 한 웹 전체를 긁는다.

### 실무 함정

**함정 1 — 스택 오버플로 우려는 대부분 근거가 없다.** `iterate`가 자기를 재귀 호출하지만, `spider` 안의 콜백이 진짜 비동기(파일 I/O, 네트워크)라면 각 호출은 새 이벤트 루프 틱에서 시작되므로 스택이 쌓이지 않는다. 위험한 경우는 반대다. 작업이 **동기적으로 콜백을 부를 때**(캐시 히트, 조기 검증 실패) 재귀가 그대로 스택에 쌓여 링크 1만 개에서 `RangeError: Maximum call stack size exceeded`가 난다. 이것이 4장에서 다룬 Zalgo 문제가 제어 흐름 층위에서 나타나는 형태다. 라이브러리 경계에서 항상 비동기를 보장하거나(`process.nextTick`), 이터레이터가 동기 완료를 감지해 루프로 되돌아가게 만들어야 한다.

**함정 2 — 오류 발생 시의 정책이 암묵적이다.** 위 코드는 첫 오류에서 전체를 중단한다(fail-fast). 스파이더 입장에서는 링크 하나가 404라고 전체를 포기하는 것이 대개 잘못된 정책이다. 오류를 수집하되 계속 진행하려면 `iterate` 안에서 오류를 배열에 모으고 다음으로 넘어가면 된다. 중요한 것은 이 정책이 **코드에 명시적으로 드러나야** 한다는 점이다.

**함정 3 — 순차 실행은 느리다.** 링크 20개를 각 200ms에 순차 처리하면 4초가 걸린다. 각 작업이 서로 독립적이라면 이 4초는 통째로 낭비다. 다음 절이 이 문제를 다룬다.

## 5.4 병렬 실행과 경쟁 상태 해결

### Node.js에서 "병렬"이 의미하는 것

먼저 용어를 정확히 하자. Node.js의 JavaScript 실행은 단일 스레드다. 두 개의 `spider()` 호출이 같은 순간에 CPU에서 실행되는 일은 없다. 여기서 말하는 병렬은 **동시 I/O(concurrent I/O)**다. 작업 A가 소켓 응답을 기다리는 동안 이벤트 루프는 놀지 않고 작업 B의 콜백을 실행한다. 대기 구간이 겹치기 때문에 전체 소요 시간이 줄어든다. 병렬성(parallelism)이 아니라 동시성(concurrency)이며, 이득의 크기는 작업이 I/O에 쓰는 시간의 비율에 비례한다. CPU 바운드 작업을 이 방식으로 "병렬화"하면 아무 이득이 없다. 그런 작업은 워커 스레드로 보내야 한다(11장 참조).

따라서 실행 순서에 대한 어떤 가정도 하면 안 된다. 20개 작업을 동시에 띄우면 완료 순서는 네트워크 상태에 따라 매번 달라진다.

### 완료 카운터 패턴

동시 실행의 어려움은 시작이 아니라 **끝을 아는 것**이다. 모든 작업이 끝난 시점을 감지하려면 완료 카운터(completion counter)를 쓴다.

```js
function spiderLinks (currentUrl, body, nesting, cb) {
  if (nesting === 0) {
    return process.nextTick(cb)
  }

  const links = getPageLinks(currentUrl, body)
  if (links.length === 0) {
    return process.nextTick(cb)
  }

  let completed = 0
  let hasErrors = false

  function done (err) {
    if (err) {
      hasErrors = true
      return cb(err)          // 첫 오류를 즉시 전파
    }
    if (++completed === links.length && !hasErrors) {
      cb()                    // 마지막 완료에서만 최종 콜백
    }
  }

  for (const link of links) {
    spider(link, nesting - 1, done)   // 전부 한 번에 띄운다
  }
}
```

`for` 루프가 즉시 끝나면서 모든 다운로드가 시작되고, 이벤트 루프가 도착하는 응답부터 처리한다. `done`은 카운터가 총 개수에 도달할 때만 최종 콜백을 부른다. `hasErrors` 플래그가 없으면 오류로 이미 `cb(err)`를 부른 뒤 나머지 작업이 완료되면서 `cb()`가 또 호출된다. 최종 콜백이 두 번 불리는 것은 상위 코드의 상태를 망가뜨리는 심각한 버그다.

### 경쟁 상태: 같은 URL을 두 번 내려받기

순차 버전에서는 없던 버그가 동시 버전에서 나타난다. 페이지 A와 페이지 B가 모두 페이지 C를 링크한다고 하자. 순차 실행에서는 A가 C를 받아 파일로 저장한 뒤 B가 C를 처리하므로 `fs.readFile`이 성공해 재다운로드가 없다. 그러나 동시 실행에서는 A의 C 다운로드가 **끝나기 전에** B가 C를 검사한다. 파일은 아직 없다. 결과적으로 C를 두 번 내려받고, 두 번 쓰고, 그 하위 링크를 두 번 따라간다. 최악의 경우 순환 링크와 결합해 무한 증식한다.

이것이 전형적인 경쟁 상태(race condition)다. Node.js가 단일 스레드라고 해서 경쟁 상태가 없는 것이 아니다. 검사(check)와 사용(use) 사이에 이벤트 루프가 끼어들 수 있는 모든 지점이 잠재적 경쟁 구간이다.

해결책은 "완료된 작업"이 아니라 **"진행 중인 작업"을 기록하는 것**이다.

```js
const spidering = new Set()   // 진행 중 또는 처리 완료된 URL

export function spider (url, nesting, cb) {
  if (spidering.has(url)) {
    return process.nextTick(cb)   // 이미 누군가 처리 중
  }
  spidering.add(url)              // 검사 직후, 어떤 await/콜백보다 먼저 등록

  const filename = urlToFilename(url)
  fs.readFile(filename, 'utf8', (err, body) => {
    if (err) {
      if (err.code !== 'ENOENT') {
        return cb(err)
      }
      return download(url, filename, (err, body) => {
        if (err) {
          return cb(err)
        }
        spiderLinks(url, body, nesting, cb)
      })
    }
    spiderLinks(url, body, nesting, cb)
  })
}
```

핵심은 `spidering.add(url)`의 **위치**다. 검사와 등록 사이에 비동기 경계가 하나라도 있으면 방어는 무효가 된다. 두 코드는 반드시 같은 틱 안에서 연속으로 실행되어야 한다.

### 실무 함정

**함정 1 — 무제한 팬아웃.** 위 코드는 링크 개수만큼 다운로드를 동시에 띄운다. 페이지 하나에 링크 200개가 있고 각각이 또 200개를 링크하면 두 단계 만에 4만 개의 동시 연결을 시도한다. 5.5절에서 다룰 문제다.

**함정 2 — 진행 중 집합이 영원히 커진다.** `spidering`은 실행 내내 URL을 축적한다. 짧은 배치 작업이면 문제없지만, 장기 실행 서비스에서 같은 자료구조를 쓰면 메모리 누수가 된다. 크기 상한이 있는 캐시(LRU)나 작업 종료 시 정리가 필요하다(29장 참조).

**함정 3 — 진행 중 집합이 결과를 공유하지 않는다.** 위 구현은 중복 요청을 "그냥 무시"한다. 두 번째 호출자가 첫 번째 호출의 결과를 받아야 한다면 집합이 아니라 "URL → 대기 중인 콜백 배열" 맵이 필요하다. 이것이 비동기 요청 배칭 패턴이며 15장에서 본격적으로 다룬다.

## 5.5 동시성 제한 병렬 실행

### 왜 필요한가 — 무제한 동시성이 만드는 실제 장애

"동시에 다 띄우면 가장 빠르다"는 직관은 특정 수준을 넘으면 뒤집힌다. 무제한 팬아웃(unbounded fan-out)이 만드는 장애는 크게 셋이다.

**파일 디스크립터 고갈.** 리눅스의 프로세스당 열린 파일 상한은 기본값이 대개 1024다(`ulimit -n`). 소켓과 파일이 모두 이 예산을 쓴다. 동시 요청이 1024를 넘는 순간 `fs.open`은 `EMFILE`, 소켓 생성은 `EMFILE` 또는 `ENFILE`로 실패한다. 문제는 실패 방식이다. 이미 진행 중이던 정상 요청까지 함께 무너지고, 스파이더처럼 오류를 상위로 전파하는 구조에서는 작업 전체가 한 번에 종료된다. 컨테이너 환경에서 상한을 65536으로 올려도 근본 해결이 아니다. 상한을 올리면 그다음에 메모리가 먼저 터진다. 소켓 하나당 커널 버퍼와 Node.js 측 버퍼를 합쳐 대략 수십 KB가 필요하므로, 동시 연결 5만 개는 수 GB의 메모리를 뜻한다.

**임시 포트(ephemeral port) 고갈.** 아웃바운드 연결은 로컬 포트를 하나씩 소비하며, 기본 범위는 대략 28,000개다. TCP `TIME_WAIT` 상태가 60초 유지되므로, 초당 500개의 짧은 연결을 만들면 30,000개가 묶여 새 연결이 `EADDRNOTAVAIL`로 실패한다.

**상대 서버 과부하.** 가장 흔하고 가장 정치적인 문제다. 스파이더가 한 도메인에 초당 1,000 요청을 보내면 상대 입장에서는 소규모 DoS다. 429 응답, IP 차단, 그리고 사내 서비스라면 장애 보고서가 따라온다.

적정 동시성은 대상에 따라 다르다. 외부 HTTP API는 보통 5~20, 로컬 디스크 I/O는 CPU 코어 수의 2~4배, 데이터베이스는 커넥션 풀 크기와 같게 잡는 것이 출발점이다. 이 값은 추측이 아니라 측정으로 정한다(28장 참조).

### 어떻게 동작하는가 — TaskQueue

동시성을 제한하는 구조는 단순하다. 실행 대기 중인 작업을 큐에 넣고, "지금 실행 중인 개수"를 세면서 상한 미만일 때만 큐에서 꺼내 실행한다. 작업이 끝날 때마다 카운터를 줄이고 다시 꺼낸다.

```js
// task-queue.js
import { EventEmitter } from 'node:events'

export class TaskQueue extends EventEmitter {
  constructor (concurrency) {
    super()
    this.concurrency = concurrency
    this.running = 0
    this.queue = []
  }

  pushTask (task) {
    this.queue.push(task)
    process.nextTick(this.next.bind(this))  // 항상 비동기로 시작
    return this
  }

  next () {
    if (this.running === 0 && this.queue.length === 0) {
      return this.emit('empty')
    }
    while (this.running < this.concurrency && this.queue.length) {
      const task = this.queue.shift()
      this.running++
      task(err => {
        if (err) {
          this.emit('error', err)   // 큐는 멈추지 않는다
        }
        this.running--
        process.nextTick(this.next.bind(this))
      })
    }
  }
}
```

스파이더에서는 `spiderLinks`가 직접 `spider`를 부르는 대신 큐에 밀어 넣는다.

```js
function spiderLinks (currentUrl, body, nesting, queue) {
  if (nesting === 0) {
    return
  }
  for (const link of getPageLinks(currentUrl, body)) {
    spiderTask(link, nesting - 1, queue)
  }
}

function spiderTask (url, nesting, queue) {
  if (spidering.has(url)) {
    return
  }
  spidering.add(url)
  queue.pushTask(done => {
    // ...파일 확인, 다운로드, 저장 후 spiderLinks 호출...
    // 하위 링크는 다시 같은 큐에 들어간다
    done()
  })
}

const spiderQueue = new TaskQueue(4)
spiderQueue.on('error', err => console.error('작업 실패:', err.message))
spiderQueue.on('empty', () => console.log('모든 작업 완료'))
spiderTask(process.argv[2], 2, spiderQueue)
```

이 구조에서 흥미로운 점은 최종 완료 콜백이 사라졌다는 것이다. 작업이 실행 중에 새 작업을 큐에 추가하므로 "총 개수"를 미리 알 수 없다. 대신 큐가 비고 실행 중인 작업도 없는 상태를 `empty` 이벤트로 알린다. 콜백이 아니라 이벤트가 맞는 도구인 상황이다(4장 참조).

### 전역 동시성 제한과 지역 동시성 제한

`TaskQueue` 인스턴스 하나를 프로그램 전체가 공유하면 **전역 동시성 제한(global concurrency limit)**이다. 시스템 자원(파일 디스크립터, 메모리, 총 대역폭)을 보호하는 것이 목적이며, 스파이더의 예처럼 재귀 구조에서 폭발을 막는 유일한 방법이다.

반면 요청마다, 또는 대상 호스트마다 큐를 새로 만들면 **지역 동시성 제한(local concurrency limit)**이다. 이쪽은 "특정 상대에게 예의를 지키는 것"이 목적이다. 둘은 대체재가 아니라 조합 대상이다. 도메인별 큐를 5로 두어 상대 서버를 보호하고, 그 위에 전역 큐를 50으로 두어 내 프로세스를 보호하는 2단 구성이 실무의 표준 형태다. 지역 제한만 두면 도메인 100개를 동시에 긁을 때 총 500개 연결이 열려 전역 자원이 무너지고, 전역 제한만 두면 한 느린 도메인이 전체 슬롯을 점유해 나머지가 굶는다.

### 실무 함정

**함정 1 — 큐 자체는 무한하다.** `TaskQueue`는 동시 **실행** 개수만 제한할 뿐, 대기 큐 길이는 제한하지 않는다. 생산 속도가 소비 속도보다 빠르면 `this.queue` 배열이 무한히 커져 메모리를 소진한다. 실행 시간이 유한한 배치라면 괜찮지만, 서버가 요청마다 작업을 밀어 넣는 구조라면 큐 길이 상한과 초과 시 거부(backpressure)가 필요하다.

**함정 2 — `done`이 두 번 호출되면 카운터가 음수로 향한다.** `this.running--`이 실제보다 많이 실행되면 동시성 제한이 무력화된다. 작업 함수 안에서 조기 반환 시 `return done(err)`를 지키고, 필요하면 `done`을 한 번만 통과시키는 가드로 감싼다.

**함정 3 — 오류 정책을 이벤트로 흘려보내는 것의 의미.** 위 구현은 오류를 `error` 이벤트로 내보내고 큐를 계속 돌린다. 스파이더에는 맞는 정책이지만, "하나라도 실패하면 전체 중단"이 필요한 작업에는 맞지 않는다. 그런 경우 큐에 `stop()`을 두어 대기 작업을 비우도록 한다. 또한 `EventEmitter`의 `error` 이벤트에 리스너가 없으면 프로세스가 죽는다는 점을 잊지 말아야 한다(4장 참조).

## 5.6 레거시 콜백 코드와 마주쳤을 때의 대응 전략

### 왜 이 절이 필요한가

새 코드를 콜백으로 쓸 이유는 이제 거의 없다. 그러나 콜백은 사라지지 않는다. `fs`의 콜백 API, `EventEmitter` 위에 얹힌 오래된 드라이버, 사내에서 10년째 굴러가는 유틸리티 모듈은 여전히 콜백 규약을 쓴다. 실무의 질문은 "콜백으로 어떻게 쓸까"가 아니라 **"이 콜백 코드를 현대 코드와 어떻게 안전하게 잇는가"**다.

### 첫 번째 도구 — util.promisify

대상 함수가 Node.js 표준 규약(마지막 인자가 콜백, 콜백의 첫 인자가 오류, 두 번째가 결과 하나)을 정확히 따르면 `util.promisify`가 기계적으로 변환한다.

```js
import { promisify } from 'node:util'
import fs from 'node:fs'

const readFile = promisify(fs.readFile)
const body = await readFile('page.html', 'utf8')
```

규약을 벗어나는 경우는 두 가지다. 콜백이 결과를 여러 개 넘기는 함수(예: `child_process.exec`의 `stdout`, `stderr`)는 `util.promisify.custom` 심벌로 지정된 구현이 있으면 그것을 쓰고, 없으면 첫 결과만 살아남는다. 그리고 객체 메서드는 `this` 바인딩이 끊어지므로 `promisify(obj.method.bind(obj))`로 감싸야 한다.

### 두 번째 도구 — util.callbackify

방향이 반대인 경우도 있다. 콜백 규약을 기대하는 오래된 프레임워크에 `async` 함수를 넘겨야 할 때 `util.callbackify`를 쓴다. 이 함수는 거부(rejection) 값을 콜백의 첫 인자로 전달하는데, 거부 값이 `undefined`나 `null`이면 "오류 없음"으로 오해되지 않도록 `reason` 속성을 가진 `Error`로 감싸 준다. 콜백을 기대하는 자리에 `async` 함수를 그냥 넘기면, 반환된 Promise가 누구에게도 관찰되지 않아 예외가 통째로 사라진다. 이 실수는 조용해서 특히 위험하다.

### 세 번째 도구 — 직접 감싸기와 그 함정

표준 규약을 벗어난 API는 손으로 감싸야 한다.

```js
function once (fn) {
  let called = false
  return (...args) => {
    if (called) {
      // 두 번째 호출은 무시하되 반드시 관측 가능하게 남긴다
      return console.error('콜백이 두 번 호출됨', new Error().stack)
    }
    called = true
    fn(...args)
  }
}

function fetchLegacy (url) {
  return new Promise((resolve, reject) => {
    const settle = once(err => (err ? reject(err) : resolve()))
    legacyClient.get(url, settle)
    legacyClient.on('error', settle)   // 두 경로 모두 settle로 향한다
  })
}
```

가장 중요한 주의점은 **콜백이 두 번 호출되는 경우**다. Promise는 한 번만 정착(settle)하므로 두 번째 `resolve`/`reject`는 조용히 무시된다. 이는 안전해 보이지만 사실은 위험하다. 버그가 예외로 드러나지 않고 은폐되기 때문이다. 잘못된 콜백 API에 Promise를 씌우면 "간헐적으로 응답이 하나 사라지는" 유령 버그가 남는다. 위처럼 `once` 가드를 두고 두 번째 호출을 로그로 남기면 원인이 드러난다.

두 번째 주의점은 실행자(executor) 함수 안에서 던져지는 동기 예외다. `new Promise(executor)`의 실행자에서 던진 예외는 자동으로 거부로 변환되지만, **콜백 안에서** 던진 예외는 그렇지 않다. 그것은 실행자 바깥의 다른 틱에서 발생하므로 잡히지 않고 `uncaughtException`으로 올라간다. 래퍼 안에서는 예외를 던지지 말고 항상 `reject`로 전달한다.

### 네 번째 판단 — async 라이브러리를 만났을 때

`async` 패키지(`async.series`, `async.eachLimit`, `waterfall` 등)에 의존하는 코드는 여전히 흔하다. 판단 기준은 세 가지다. 첫째, 그 코드를 **어차피 손대야 하는가**. 기능 변경이 예정된 모듈이라면 Promise로 옮기는 편이 총비용이 낮다. 둘째, 사용하는 기능이 표준으로 **대체 가능한가**. `async.series`는 `for await`, `async.parallel`은 `Promise.all`, `async.waterfall`은 순차 `await`로 1:1 대응된다. 대체가 어려운 것은 `async.cargo`, `async.priorityQueue` 같은 큐 계열인데, 이는 5.5절의 `TaskQueue`를 Promise 버전으로 옮긴 형태로 대체된다(6장 참조). 셋째, **경계에서만 바꿀 수 있는가**. 모듈 전체를 다시 쓰는 대신 `promisify`로 공개 API만 감싸고 내부는 그대로 두는 선택이 대개 가장 합리적이다. 동작하는 코드를 문법 취향 때문에 다시 쓰는 것은 리스크를 사는 일이다.

### 6장으로

이 장에서 만든 세 가지 패턴 — 순차, 병렬, 동시성 제한 — 은 문법이 아니라 실행 모델이다. 다음 장에서는 같은 세 패턴을 Promise와 `async/await`로 다시 구현한다. 코드 줄 수는 크게 줄지만, "언제 기다리고 언제 동시에 띄우며 몇 개까지 허용할 것인가"라는 판단은 조금도 줄지 않는다는 사실을 확인하게 될 것이다.

## 요약

- 콜백 지옥은 게으름이 아니라 CPS의 구조적 결과이며, 진짜 비용은 가독성이 아니라 수정 비용과 은폐된 오류 경로다.
- 콜백 규율 — 조기 반환, 명명 함수 분리, 모듈화, 들여쓰기 깊이 제한, 오류 처리 집중 — 만으로 라이브러리 없이 대부분의 중첩이 사라진다.
- 개수를 모르는 비동기 작업의 순차 실행은 반복문이 아니라 인덱스를 넘기는 재귀 이터레이터로 구현한다.
- Node.js의 "병렬"은 동시 I/O를 뜻하며, 완료 시점은 완료 카운터로 감지한다. 오류 전파 후 카운터가 다시 최종 콜백을 부르지 않도록 플래그가 필요하다.
- 동시 실행은 순차 실행에 없던 경쟁 상태를 만든다. "완료된 작업"이 아니라 "진행 중인 작업"을 같은 틱 안에서 등록해야 중복 실행을 막을 수 있다.
- 무제한 동시성은 파일 디스크립터 고갈(`EMFILE`), 임시 포트 고갈(`EADDRNOTAVAIL`), 상대 서버 과부하라는 구체적 장애로 나타난다. `TaskQueue`로 전역·지역 제한을 조합해 막는다.
- 레거시 콜백 코드는 `util.promisify`와 `util.callbackify`로 경계에서 잇되, 콜백이 두 번 호출되는 경우를 `once` 가드로 드러내야 유령 버그를 피할 수 있다.

## 연습문제

1. **오류를 수집하는 순차 스파이더.** 5.3절의 `spiderLinks`를 수정해, 링크 하나가 실패해도 나머지를 계속 처리하고 마지막에 `cb(null, { succeeded, failed })` 형태로 결과를 요약해 넘기도록 만들어라. `failed` 항목에는 URL과 오류 메시지를 함께 담는다.

2. **경쟁 상태 재현과 검증.** 5.4절의 `spidering` 집합을 제거한 뒤, 서로를 링크하는 두 페이지를 가진 로컬 서버를 띄워 같은 URL이 두 번 이상 다운로드되는 것을 로그로 확인하라. 그다음 `spidering.add(url)`을 `fs.readFile` 콜백 **안쪽**으로 옮기면 왜 방어가 무효화되는지 설명하고, 그 상태에서도 중복이 재현됨을 보여라.

3. **경계 있는 TaskQueue.** `TaskQueue`에 `maxQueueLength` 옵션을 추가하라. 대기 큐가 상한에 도달하면 `pushTask`가 `false`를 반환하고 작업을 버리며 `saturated` 이벤트를 발생시킨다. 큐 길이가 상한의 절반 아래로 내려가면 `drain` 이벤트를 발생시킨다. 이 두 이벤트를 사용해 생산 측이 스스로 속도를 늦추는 예제를 작성하라.
