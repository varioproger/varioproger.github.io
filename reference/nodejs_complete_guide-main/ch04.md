# 4장. 콜백과 이벤트

Node.js에서 비동기 코드를 다루는 방식은 크게 두 갈래다. 하나는 "작업이 끝나면 이 함수를 불러 달라"고 요청하는 콜백(callback)이고, 다른 하나는 "이 객체에서 어떤 일이 생기면 알려 달라"고 구독하는 이벤트(event)다. 프로미스(promise)와 `async/await`가 표준이 된 지금도 이 두 메커니즘은 사라지지 않았다. 프로미스는 콜백 위에 세워진 추상이고, 스트림·HTTP 서버·자식 프로세스 등 Node.js 코어의 절반은 여전히 `EventEmitter`로 동작하기 때문이다.

이 장은 두 메커니즘의 규약, 그 규약을 어겼을 때 발생하는 구체적인 버그, 그리고 현대 Node.js(v20 LTS 이상)가 제공하는 정리 도구를 다룬다. 여기서 확립한 원칙은 5장의 콜백 제어 흐름 패턴과 6장의 프로미스·async/await로 그대로 이어진다.

## 4.1 연속 전달 스타일(CPS)

### 왜 필요한가

동기 함수는 결과를 반환값으로 돌려준다. 호출자는 `const result = f(x)`라고 쓰고 다음 줄로 넘어간다. 이 모델은 함수가 즉시 끝날 때만 성립한다. 그런데 Node.js가 잘하는 일 대부분(파일 읽기, 소켓 통신, 데이터베이스 질의)은 즉시 끝나지 않는다. 결과가 나올 때까지 스레드를 붙잡고 기다리면 단일 스레드 이벤트 루프 전체가 멈춘다(3장 참조). 따라서 "결과를 반환한다"가 아니라 "결과를 어디로 보낼지 미리 알려 준다"는 다른 모델이 필요하다.

그 모델이 연속 전달 스타일(Continuation-Passing Style, CPS)이다. 계산이 끝난 뒤 이어서 실행할 나머지 계산, 즉 연속(continuation)을 함수 인자로 넘긴다. Node.js에서 이 연속은 대개 일반 함수, 즉 콜백이다.

### 어떻게 동작하는가

CPS 자체는 비동기와 무관한 순수한 스타일 문제다. 동기 CPS도 얼마든지 가능하다.

```js
// 직접 스타일(direct style): 결과를 반환한다
function add(a, b) {
  return a + b;
}

// 동기 CPS: 결과를 콜백으로 전달한다. 여전히 동기적으로 실행된다
function addCps(a, b, cb) {
  cb(a + b);
}

console.log('before');
addCps(1, 2, (sum) => console.log('sum =', sum));
console.log('after');
// before → sum = 3 → after
```

비동기 CPS는 여기에 "콜백 호출을 이벤트 루프의 다음 기회로 미룬다"는 요소가 추가된 것뿐이다.

```js
import { readFile } from 'node:fs';

function addAsync(a, b, cb) {
  // setTimeout은 타이머 단계에서 콜백을 실행한다
  setTimeout(() => cb(a + b), 0);
}

console.log('before');
addAsync(1, 2, (sum) => console.log('sum =', sum));
console.log('after');
// before → after → sum = 3

// 실제 I/O도 같은 형태다. 오류가 첫 번째 인자로 온다
readFile('./package.json', 'utf8', (err, data) => {
  if (err) return console.error('읽기 실패:', err.message);
  console.log('길이:', data.length);
});
```

핵심 차이는 제어권 반환 시점이다. 동기 CPS는 `addCps`가 반환되기 전에 콜백이 이미 실행을 마쳤다. 비동기 CPS는 `addAsync`가 즉시 반환되고, 콜백은 현재 호출 스택이 완전히 비워진 뒤 이벤트 루프가 다시 돌면서 실행된다. 이 시점 차이가 다음 절의 모든 문제를 만든다.

### 실무 함정

첫째, 모든 콜백이 CPS인 것은 아니다. `[1, 2, 3].map((x) => x * 2)`의 `map` 콜백은 결과를 반환값으로 돌려주는 직접 스타일이다. 함수가 콜백을 받는다는 사실만으로 비동기라고 단정하면 안 된다. 판단 기준은 "함수가 반환된 뒤에 콜백이 불리는가"이지 "콜백을 받는가"가 아니다.

둘째, CPS는 반환값이라는 언어의 기본 흐름을 포기하는 대가로 성립한다. 그래서 `try/catch`, `return`, `for` 루프 같은 동기 제어 구조가 비동기 경계를 넘지 못한다. 이 손실을 어떻게 메울지가 5장 전체의 주제다.

셋째, CPS 함수는 콜백을 정확히 한 번만 호출해야 한다. 두 번 호출하면 호출자의 후속 로직이 두 번 실행되고, 프로미스로 감쌌을 때는 두 번째 호출이 조용히 무시되어 원인을 찾기 어려운 버그가 된다. `return cb(err)` 형태로 조기 반환을 습관화하면 대부분 예방된다.

## 4.2 동기인가 비동기인가: Zalgo 문제

### 왜 필요한가

가장 위험한 API는 느린 API가 아니라 **일관성이 없는** API다. 어떤 조건에서는 콜백을 동기적으로 부르고 다른 조건에서는 비동기적으로 부르는 함수를 두고, 아이작 슐레이터(Isaac Z. Schlueter)는 "Zalgo를 풀어놓지 말라(Don't release Zalgo)"고 표현했다. 이런 함수는 대부분의 테스트를 통과하다가 프로덕션의 특정 조건에서만 실행 순서를 뒤집어 놓는다.

전형적인 발생 원인은 캐시다. 캐시 미스면 I/O를 하니 비동기, 캐시 히트면 즉시 결과가 있으니 동기로 부르고 싶은 유혹이 생긴다.

### 어떻게 동작하는가

아래 `readCached`는 Zalgo 그 자체다.

```js
import { readFile } from 'node:fs';

const cache = new Map();

// 위험: 캐시 히트면 동기, 미스면 비동기로 콜백을 호출한다
function readCached(filename, cb) {
  if (cache.has(filename)) {
    return cb(null, cache.get(filename)); // 동기 경로
  }
  readFile(filename, 'utf8', (err, data) => { // 비동기 경로
    if (err) return cb(err);
    cache.set(filename, data);
    cb(null, data);
  });
}
```

이제 이 함수를 쓰는 평범한 호출자를 보자.

```js
function createHandler(filename) {
  const listeners = [];

  readCached(filename, (err, data) => {
    if (err) return listeners.forEach((l) => l(err));
    listeners.forEach((l) => l(null, data)); // 완료 통지
  });

  return {
    onReady(l) { listeners.push(l); }
  };
}

const h = createHandler('./config.json');
h.onReady((err, data) => console.log('첫 번째 호출:', err ?? data.length));
```

첫 호출은 캐시 미스이므로 `readCached`가 즉시 반환되고, `onReady`로 리스너가 등록된 뒤 파일이 읽히면서 리스너가 호출된다. 정상이다. 그런데 같은 파일로 두 번째 핸들러를 만들면 캐시 히트가 되어 `listeners.forEach`가 `createHandler`가 반환되기 **전에** 실행된다. 그 시점의 `listeners`는 빈 배열이다. 콜백은 영원히 불리지 않고, 예외도 오류 로그도 남지 않는다. 그냥 아무 일도 일어나지 않는다.

```js
const h2 = createHandler('./config.json');
h2.onReady((err, data) => console.log('두 번째 호출:', err ?? data.length));
// 아무것도 출력되지 않는다
```

이 버그가 악질인 이유는 재현 조건이 상태에 의존하기 때문이다. 서버를 재시작한 직후 첫 요청은 잘 되고, 두 번째 요청부터 응답이 멈춘다. 부하 테스트에서는 정상이었는데 프로덕션 캐시가 워밍업된 뒤에 장애가 나는 형태로도 나타난다.

### 코드: 비동기성 보장

해법은 하나다. **API가 비동기라면 언제나 비동기여야 한다.** 동기 경로에서도 콜백 호출을 다음 틱으로 미룬다.

```js
import { readFile } from 'node:fs';

const cache = new Map();

function readCached(filename, cb) {
  if (cache.has(filename)) {
    const data = cache.get(filename);
    // 항상 비동기로 호출되도록 보장한다
    return process.nextTick(() => cb(null, data));
  }
  readFile(filename, 'utf8', (err, data) => {
    if (err) return cb(err);
    cache.set(filename, data);
    cb(null, data);
  });
}
```

`process.nextTick`은 현재 실행 중인 동작이 끝난 직후, 이벤트 루프가 다음 단계로 넘어가기 전에 콜백을 실행한다. `queueMicrotask`는 V8의 마이크로태스크 큐에 넣으며 프로미스 `then`과 같은 우선순위다. 둘 다 "현재 스택이 비워진 뒤"를 보장하므로 Zalgo를 막는 목적으로는 동등하다. 실무 기준은 다음과 같다.

- `queueMicrotask`: 표준 API이고 프로미스와 순서가 일관되므로 기본 선택으로 삼는다.
- `process.nextTick`: nextTick 큐는 마이크로태스크 큐보다 먼저 비워진다. 리스너를 붙일 기회를 반드시 먼저 줘야 하는 코어 스타일 API에서 쓴다. 재귀적으로 스스로를 예약하면 I/O가 굶는다는 점에 주의한다(3장 참조).
- `setImmediate`: 한 틱 더 뒤, 체크 단계에서 실행된다. 지연이 커지지만 I/O를 굶기지 않는다.

가장 깔끔한 해법은 아예 프로미스로 감싸는 것이다. 프로미스는 이미 이행된 값을 `then`으로 받아도 항상 마이크로태스크로 실행되므로 Zalgo가 구조적으로 불가능하다.

```js
import { readFile } from 'node:fs/promises';

const cache = new Map();

export async function readCached(filename) {
  if (!cache.has(filename)) {
    cache.set(filename, await readFile(filename, 'utf8'));
  }
  return cache.get(filename); // await 지점이 비동기성을 보장한다
}
```

### 실무 함정

인플라이트(in-flight) 중복 요청은 위 프로미스 버전에서도 남는 문제다. 같은 파일에 대한 두 번째 호출이 첫 번째 `await`이 끝나기 전에 오면 파일을 두 번 읽는다. 값이 아니라 **프로미스 자체를 캐시**하면 해결된다. 다만 실패한 프로미스가 캐시에 남지 않도록 `catch`에서 항목을 지워야 한다.

반대 방향의 실수도 있다. 순수 동기 함수를 "혹시 모르니" 콜백 스타일로 만들면 호출자에게 불필요한 비동기 비용과 복잡도를 떠넘긴다. 동기 함수는 당당히 동기로 두고 반환값을 돌려주는 편이 낫다. 규칙은 "동기와 비동기를 섞지 말라"이지 "전부 비동기로 만들라"가 아니다.

## 4.3 Node.js 콜백 규약과 오류 전파

### 왜 필요한가

CPS는 스타일일 뿐 규약이 아니다. 콜백의 인자 순서와 의미를 저자마다 다르게 정하면 라이브러리를 조합할 때마다 문서를 읽어야 한다. Node.js는 코어 전체에 걸쳐 하나의 규약을 강제함으로써 이 비용을 없앴다. 오류 우선 콜백(error-first callback)이다.

### 어떻게 동작하는가

규약은 세 줄로 요약된다.

1. 콜백은 함수의 **마지막** 인자다.
2. 콜백의 **첫 번째** 인자는 오류다. 성공하면 `null`(관례상 `undefined`도 허용)이다.
3. 결과는 두 번째 이후 인자로 전달된다.

그리고 오류는 반드시 `Error` 인스턴스여야 한다. 문자열을 던지면 스택 트레이스가 없어 원인 추적이 불가능해진다.

```js
import { readFile } from 'node:fs';

function readJson(filename, cb) {
  readFile(filename, 'utf8', (err, data) => {
    if (err) return cb(err); // 오류를 그대로 위로 전파한다

    let parsed;
    try {
      // 동기 코드에서 발생하는 예외는 try/catch로 잡아 콜백으로 변환한다
      parsed = JSON.parse(data);
    } catch (parseErr) {
      // 원인을 잃지 않도록 cause로 연결한다
      return cb(new Error(`JSON 파싱 실패: ${filename}`, { cause: parseErr }));
    }

    cb(null, parsed); // 성공 경로는 try 블록 바깥에서 호출한다
  });
}
```

여기서 `cb(null, parsed)`를 `try` 블록 안에 두면 안 된다. 콜백 내부에서 예외가 나면 그 예외를 `catch`가 잡아 콜백을 두 번 호출하게 된다. 성공 콜백은 항상 `try` 바깥에서 부른다.

### 오류 전파의 두 경로

동기 코드에서 오류는 `throw`로 위로 던져지고 `try/catch`가 잡는다. 비동기 CPS에서는 그 경로가 끊긴다. 콜백은 호출자의 스택이 이미 사라진 뒤 이벤트 루프가 실행하기 때문에, 콜백 안에서 던진 예외를 호출자의 `try/catch`가 잡을 방법이 없다.

```js
try {
  readJson('./broken.json', (err, data) => {
    if (err) throw err; // 이 예외는 아래 catch에 도달하지 않는다
  });
} catch (e) {
  console.error('여기는 절대 실행되지 않는다');
}
```

따라서 비동기 함수 안에서 인자 검증처럼 즉시 판정 가능한 오류를 만났을 때도 `throw`가 아니라 콜백으로 전달하는 편이 일관적이다. 던질 거라면 함수가 어떤 비동기 작업도 시작하기 전에, 프로그래머 실수(programmer error)에 한해서만 던진다. 사용자 입력이나 네트워크 실패 같은 운영 오류(operational error)는 언제나 콜백으로 보낸다.

### uncaughtException의 위험성

콜백에서 던져진 예외는 어디에도 잡히지 않고 이벤트 루프까지 올라가 `uncaughtException` 이벤트를 발생시킨다. 핸들러가 없으면 프로세스는 스택 트레이스를 출력하고 종료한다.

```js
process.on('uncaughtException', (err) => {
  console.error('치명적 오류:', err);
  // 절대 여기서 그냥 넘어가지 말 것
});
```

이 핸들러를 등록해 두고 아무 일 없다는 듯 계속 실행하는 것은 흔하지만 명백히 잘못된 패턴이다. 예외가 스택을 관통해 올라왔다는 것은 그 사이에 있던 모든 함수가 정리 코드를 실행하지 못한 채 중단됐다는 뜻이다. 열린 파일 디스크립터, 잡히지 않은 락, 절반만 갱신된 자료구조가 프로세스에 남는다. 이 상태에서 계속 요청을 처리하면 오염된 응답을 내보내거나 메모리를 누수한다.

올바른 사용법은 **마지막 정리 후 반드시 종료**하는 것이다.

```js
process.on('uncaughtException', (err) => {
  logger.fatal({ err }, 'uncaughtException, 프로세스를 종료한다');
  // 새 연결을 받지 않고 진행 중인 요청만 마무리한 뒤 종료
  server.close(() => process.exit(1));
  // 정리가 끝나지 않아도 강제 종료할 안전장치
  setTimeout(() => process.exit(1), 5000).unref();
});
```

프로세스가 죽어도 서비스가 유지되도록 만드는 것은 프로세스 매니저나 오케스트레이터의 책임이다(25장 참조). 애플리케이션 코드가 할 일은 "죽어야 할 때 깨끗하게 죽는 것"이다. `unhandledRejection`도 v15부터 기본 동작이 프로세스 종료로 바뀌었으며 같은 원칙이 적용된다.

### 실무 함정

`if (err) return cb(err);`의 `return`을 빠뜨리는 실수가 콜백 코드 버그의 상당수를 차지한다. 오류를 보고한 뒤에도 성공 경로가 이어서 실행되어 콜백이 두 번 불린다. 린터의 `callback-return` 규칙으로 기계적으로 막는다.

또 하나는 오류를 삼키는 것이다. `if (err) return;`은 문법적으로 멀쩡하고 테스트도 통과하지만, 장애 시 아무 단서도 남지 않는다. 처리할 수 없는 오류는 반드시 위로 올린다.

## 4.4 관찰자 패턴과 `EventEmitter`

### 왜 필요한가

콜백은 "작업 하나에 결과 하나"를 표현한다. 그런데 TCP 서버는 연결을 계속 받고, 스트림은 데이터 청크를 여러 번 내보내며, 자식 프로세스는 stdout 출력과 종료를 각각 알려야 한다. 결과가 여러 번, 여러 종류로 발생하는 상황을 콜백 하나로 표현하려면 결국 "콜백을 여러 번 호출"해야 하는데 이는 4.1에서 본 규약 위반이다.

관찰자 패턴(observer pattern)이 이 자리를 채운다. 주체(subject)가 상태 변화를 이름 붙은 이벤트로 알리고, 관심 있는 관찰자(observer)들이 각자 구독한다. Node.js의 구현체가 `node:events` 모듈의 `EventEmitter`다.

### 어떻게 동작하는가

`EventEmitter`는 이벤트 이름별로 리스너 배열을 유지하는 단순한 구조다. `emit`은 해당 배열을 **동기적으로, 등록 순서대로** 순회하며 호출한다. 여기서 비동기성은 전혀 개입하지 않는다.

```js
import { EventEmitter } from 'node:events';

const bus = new EventEmitter();

bus.on('tick', (n) => console.log('리스너 A:', n));
bus.once('tick', (n) => console.log('리스너 B(한 번만):', n));

bus.emit('tick', 1); // A: 1, B: 1
bus.emit('tick', 2); // A: 2

console.log(bus.listenerCount('tick')); // 1
```

주요 메서드는 다음과 같다. `on`(별칭 `addListener`)은 구독, `once`는 한 번만 실행되고 자동 해제되는 구독, `off`(별칭 `removeListener`)는 해제, `emit`은 발행이다. `emit`은 리스너가 하나라도 있었으면 `true`를 반환한다. `prependListener`는 배열 앞에 끼워 넣어 먼저 실행시킨다.

### `error` 이벤트라는 특례

`EventEmitter`에서 단 하나 특별 취급되는 이벤트 이름이 `'error'`다. 리스너가 등록되지 않은 상태에서 `'error'`를 emit하면 `EventEmitter`는 그 오류 객체를 **던진다**. 이 예외는 대개 아무도 잡지 않으므로 `uncaughtException`으로 이어져 프로세스가 죽는다.

```js
const conn = new EventEmitter();
conn.emit('error', new Error('연결 끊김'));
// 리스너가 없으면 프로세스가 종료된다

// 반드시 리스너를 붙인다
conn.on('error', (err) => logger.warn({ err }, '연결 오류'));
```

이것은 결함이 아니라 의도된 설계다. 오류를 조용히 무시하는 대신 시끄럽게 실패하도록 강제한다. 실무에서 "잘 돌던 서버가 새벽에 갑자기 죽는" 사례의 상당수는 소켓이나 스트림에 `error` 리스너가 없어서 발생한다. 소켓, 스트림, 자식 프로세스처럼 실패할 수 있는 이미터를 만들면 **생성 즉시** `error` 리스너부터 붙이는 습관을 들인다.

### 프로미스와 이터레이터로 다리 놓기

현대 Node.js는 이미터를 `async/await` 세계로 옮기는 두 함수를 제공한다.

```js
import { once, on, EventEmitter } from 'node:events';
import { setTimeout as delay } from 'node:timers/promises';

const emitter = new EventEmitter();

// 1) events.once(): 다음 한 번의 이벤트를 프로미스로 기다린다
setTimeout(() => emitter.emit('ready', 'ok'), 100);
const [value] = await once(emitter, 'ready');
console.log(value); // 'ok'
```

`once(emitter, name)`은 인자 배열로 이행되는 프로미스를 돌려준다. 중요한 점은 이 함수가 `'error'` 이벤트를 자동으로 감시해 프로미스를 거부시킨다는 것이다. `AbortSignal`을 세 번째 인자로 넘겨 대기를 취소할 수도 있다.

```js
// 2) events.on(): 이벤트 스트림을 비동기 이터레이터로 소비한다
const ac = new AbortController();

(async () => {
  for await (const [chunk] of on(emitter, 'data', { signal: ac.signal })) {
    console.log('청크:', chunk);
  }
})().catch((err) => {
  if (err.name !== 'AbortError') throw err;
});

emitter.emit('data', 'a');
await delay(10);
emitter.emit('data', 'b');
await delay(10);
ac.abort(); // 반복을 끝낸다
```

`events.on`은 내부에 큐를 두고 이벤트를 버퍼링한다. 소비 속도가 발행 속도보다 느리면 큐가 무한히 커진다는 뜻이다. 백프레셔(backpressure)이 필요한 대용량 흐름은 이벤트가 아니라 스트림으로 다뤄야 한다(7장 참조).

### 실무 함정

`emit`이 동기라는 사실이 자주 잊힌다. 리스너 안에서 무거운 연산을 하면 `emit`을 호출한 코드가 그만큼 멈추고, 리스너가 예외를 던지면 그 뒤에 등록된 리스너들이 아예 실행되지 않는다. 리스너는 짧고 예외를 던지지 않게 작성한다.

또한 이미터가 만들어지기 **전에** 발생한 이벤트는 받을 수 없다. 생성자 안에서 `emit`을 하면 호출자가 리스너를 붙일 기회 자체가 없다. 이 경우 4.2에서 본 것처럼 `process.nextTick`으로 발행을 한 틱 미뤄야 한다.

## 4.5 임의의 객체를 관찰 가능하게 만들기

### 왜 필요한가

`EventEmitter`를 그 자체로 쓰는 일은 드물다. 보통은 "파일들을 탐색하면서 찾을 때마다 알려 주는 객체", "작업 큐가 진행 상황을 보고하는 객체"처럼 **자기 일이 따로 있는 객체**가 부수적으로 관찰 가능해야 한다. 이때 선택지는 두 가지다. `EventEmitter`를 상속하거나, 인스턴스를 내부에 두고 합성(composition)하는 것이다.

### 어떻게 동작하는가: 상속

`class X extends EventEmitter`는 가장 흔한 방식이다. `on`, `emit` 같은 메서드가 그대로 공개 API가 되므로 사용자가 별도 학습 없이 쓴다. Node.js 코어의 `net.Server`, `stream.Readable`, `ChildProcess`가 모두 이 방식이다.

```js
import { EventEmitter } from 'node:events';
import { readdir, readFile } from 'node:fs/promises';
import { join, extname } from 'node:path';

class FileScanner extends EventEmitter {
  #root;

  constructor(root) {
    super();
    this.#root = root;
  }

  // 스캔은 호출자가 리스너를 붙인 뒤 명시적으로 시작한다
  async start(pattern) {
    try {
      const entries = await readdir(this.#root, { withFileTypes: true });
      for (const entry of entries) {
        if (!entry.isFile() || extname(entry.name) !== '.js') continue;
        const full = join(this.#root, entry.name);
        const content = await readFile(full, 'utf8');
        if (content.includes(pattern)) {
          this.emit('match', full, content.length);
        }
        this.emit('scanned', full);
      }
      this.emit('end');
    } catch (err) {
      this.emit('error', err); // 오류도 이벤트로 보고한다
    }
    return this; // 체이닝을 위해 자신을 반환한다
  }
}

const scanner = new FileScanner('./src');
scanner
  .on('match', (file, size) => console.log('발견:', file, size))
  .on('error', (err) => console.error('스캔 실패:', err.message))
  .on('end', () => console.log('완료'));

scanner.start('TODO');
```

여기서 `start`를 생성자와 분리한 것이 중요하다. 생성자 안에서 비동기 작업을 시작하면 호출자가 `on`을 부르기 전에 첫 이벤트가 나갈 수 있다. 코어의 `net.Server`도 `listen`을 따로 부르게 만든 이유가 같다. 만약 생성자에서 시작해야 한다면 첫 `emit`을 `process.nextTick`으로 미뤄 리스너 등록 기회를 준다.

### 어떻게 동작하는가: 합성

상속은 `EventEmitter`의 모든 메서드를 공개 API에 노출한다는 부작용이 있다. 외부 코드가 내 객체의 내부 이벤트를 마음대로 `emit`하거나 `removeAllListeners()`로 다른 모듈의 리스너까지 지울 수 있다. 이미 다른 클래스를 상속해야 하는 경우에도 상속은 불가능하다. 이럴 때는 이미터를 내부에 두고 필요한 부분만 위임한다.

```js
class Job {
  #emitter = new EventEmitter();

  // 구독만 노출하고 emit은 감춘다
  on(event, listener) {
    this.#emitter.on(event, listener);
    return this;
  }

  off(event, listener) {
    this.#emitter.off(event, listener);
    return this;
  }

  async run(tasks) {
    for (const [i, task] of tasks.entries()) {
      await task();
      this.#emitter.emit('progress', i + 1, tasks.length);
    }
    this.#emitter.emit('done');
  }
}
```

선택 기준은 간단하다. 객체의 **본질이 이벤트 소스**이고 사용자가 자유롭게 구독·해제해야 하면 상속이 적합하다. 이벤트가 부가 기능이고 발행 권한을 내부로 제한하고 싶으면 합성이 낫다. 라이브러리를 공개할 때는 합성이 API 표면을 좁게 유지해 준다.

### 실무 함정

이벤트 이름을 문자열 리터럴로 흩뿌리면 오타가 조용한 버그가 된다. `emit('finish')`와 `on('finished')`는 아무 오류 없이 서로를 못 만난다. 이름을 상수 객체로 모아 두고 그것만 쓰는 편이 안전하다.

프로미스와 이벤트를 섞을 때는 오류 경로가 둘로 갈린다는 점을 기억한다. 위 `FileScanner.start`는 `async` 함수라 프로미스를 반환하지만 오류는 `error` 이벤트로만 보고한다. 반환된 프로미스는 항상 이행되므로 `await scanner.start()`만 하고 `error` 리스너를 안 붙이면 프로세스가 죽는다. 오류 보고 경로는 하나로 정하고 문서에 명시한다.

## 4.6 `EventEmitter`와 메모리 누수

### 왜 필요한가

`EventEmitter`는 리스너에 대한 강한 참조(strong reference)를 보유한다. 리스너 함수가 클로저로 큰 객체(요청 컨텍스트, 응답 버퍼, 데이터베이스 커넥션)를 붙잡고 있으면 그 객체 전체가 가비지 컬렉션 대상에서 제외된다. 이미터가 애플리케이션 수명 내내 살아 있는 싱글턴이라면 누수는 무제한으로 누적된다.

### 어떻게 동작하는가

Node.js는 이 상황을 조기에 알리려고 이미터마다 리스너 상한을 둔다. 한 이벤트 이름에 리스너가 11개 이상 등록되면 경고를 낸다.

```text
MaxListenersExceededWarning: Possible EventEmitter memory leak detected.
11 data listeners added to [MyEmitter]. Use emitter.setMaxListeners() to increase limit
```

이 경고를 오해하는 경우가 많다. **11개가 위험하다는 뜻이 아니다.** "리스너 수가 계속 늘어나고 있으니 등록만 하고 해제하지 않는 코드가 있는지 확인하라"는 신호다. 정말로 리스너가 20개 필요한 설계라면 `emitter.setMaxListeners(20)`로 올리는 것이 옳다. 반대로 경고를 없애려고 무작정 `setMaxListeners(0)`(무제한)을 부르는 것은 화재 경보기를 떼는 일과 같다.

전형적인 프로덕션 누수는 이런 모습이다.

```js
// 위험: 요청마다 프로세스 전역 이미터에 리스너를 등록한다
const shutdownBus = new EventEmitter();

app.get('/report', async (req, res) => {
  const stream = createHeavyReportStream(req.query);

  // 종료 신호가 오면 스트림을 닫으려는 의도
  shutdownBus.on('shutdown', () => stream.destroy());

  stream.pipe(res);
  // 요청이 끝나도 리스너는 shutdownBus에 그대로 남는다
});
```

요청 1만 건을 처리하면 리스너 1만 개가 쌓이고, 각 클로저가 붙잡은 스트림과 응답 객체가 힙에 남는다. 힙 스냅숏을 보면 `Array` 하나가 수만 개의 클로저를 참조하고 있는 형태로 나타난다.

### 코드: AbortSignal로 정리하기

전통적인 해법은 `off`를 명시적으로 부르는 것이다.

```js
const onShutdown = () => stream.destroy();
shutdownBus.on('shutdown', onShutdown);
res.on('close', () => shutdownBus.off('shutdown', onShutdown));
```

동작은 하지만 리스너를 변수에 담고 해제 시점마다 짝을 맞춰야 해서, 정리 경로가 여럿(정상 종료, 오류, 클라이언트 연결 끊김)이면 금세 빠뜨린다. 현대 Node.js는 `AbortSignal`을 리스너 옵션으로 받아 이 문제를 구조적으로 해결한다.

```js
app.get('/report', async (req, res) => {
  const ac = new AbortController();
  const stream = createHeavyReportStream(req.query);

  // signal이 abort되면 리스너가 자동으로 해제된다
  shutdownBus.on('shutdown', () => stream.destroy(), { signal: ac.signal });
  stream.on('error', (err) => { ac.abort(); res.destroy(err); });

  // 요청이 어떤 이유로 끝나든 한 곳에서 정리한다
  res.on('close', () => ac.abort());

  stream.pipe(res);
});
```

`{ signal }`을 넘긴 모든 리스너는 abort 한 번으로 함께 해제된다. 정리 지점이 하나로 모이므로 경로가 늘어나도 누락되지 않는다. `events.once`, `events.on`, `setTimeout`(`node:timers/promises`), `fetch`, 스트림 API가 모두 같은 `AbortSignal`을 받으므로 요청 단위 취소 컨텍스트를 하나 만들어 전체에 전달하는 패턴이 자연스럽게 성립한다.

### 실무 함정

`process`와 `globalThis`에 붙는 리스너가 특히 위험하다. `process.on('SIGTERM', ...)`이나 `process.on('unhandledRejection', ...)`을 모듈 초기화가 아닌 요청 처리 경로에서 부르는 코드가 실제로 발견된다. 전역 이미터에 대한 등록은 반드시 모듈 최상위에서 한 번만 한다.

`once`는 이벤트가 발생하면 자동 해제되지만, **발생하지 않으면 영원히 남는다.** 절대 오지 않을 응답을 `once('response')`로 기다리는 리스너는 누수다. 타임아웃이나 `AbortSignal`을 함께 걸어 반드시 해제 경로를 만든다.

진단은 `emitter.listenerCount(name)`을 주기적으로 로깅하거나, 힙 스냅숏(`--heapsnapshot-signal`)을 시간 간격을 두고 두 번 떠서 리스너 배열이 커지는지 비교한다(28장 참조).

## 4.7 콜백과 이벤트의 선택 기준, 그리고 조합

### 왜 필요한가

두 메커니즘은 겹치는 영역이 있다. `EventEmitter`로 `success`/`failure` 이벤트를 만들면 콜백이 하는 일을 흉내 낼 수 있고, 콜백을 여러 번 호출하면 이벤트처럼 쓸 수도 있다. 그래서 API를 설계할 때마다 "이 결과를 무엇으로 돌려줄 것인가"라는 질문이 반복된다. 판단 기준이 없으면 같은 코드베이스 안에서 스타일이 뒤섞이고, 사용하는 쪽이 매번 문서를 확인해야 한다.

### 어떻게 동작하는가: 판단 기준

기준은 **결과의 발생 횟수와 종류**다.

- 결과가 **한 번, 한 종류**로 끝나면 콜백 또는 프로미스를 쓴다. 파일 읽기, HTTP 요청 한 건, 트랜잭션 커밋이 여기 해당한다. `async/await`로 자연스럽게 조합되고, `try/catch`로 오류를 다룰 수 있으며, 반환값이라는 언어의 기본 흐름을 회복한다.
- 결과가 **여러 번** 발생하거나 **종류가 여럿**이면 이벤트를 쓴다. 서버의 연결 수락, 스트림의 데이터 청크, 진행률 보고, "시작-진행-완료-오류"처럼 의미가 다른 알림이 섞이는 경우다.
- 결과가 여러 번 발생하고 **소비 속도 제어가 필요하면** 이벤트로도 부족하다. 스트림이나 비동기 이터레이터를 쓴다(7장 참조). `EventEmitter`에는 백프레셔 개념이 없어서, 발행 측을 늦출 방법이 없기 때문이다.

보조 기준도 있다. 구독자가 **여러 명**일 수 있으면 이벤트다. 콜백은 본질적으로 1:1 관계이므로 여러 곳에서 같은 완료 통지를 받아야 하면 이벤트가 맞다. 반대로 "이 작업의 결과를 정확히 이 호출자에게" 돌려주는 관계라면 프로미스가 의도를 더 정확히 표현한다.

### 코드: 두 가지를 동시에 제공하기

실무에서 가장 자주 마주치는 형태는 둘 다 필요한 경우다. 파일 탐색기를 예로 들면, 파일을 찾을 때마다 즉시 처리하고 싶은 사용자도 있고 전체 목록만 있으면 되는 사용자도 있다. `glob` 계열 라이브러리가 오래전부터 쓰던 방식이 이 조합이다. **동기적으로 이미터를 반환하면서, 프로미스도 함께 제공한다.**

```js
import { EventEmitter } from 'node:events';
import { readdir } from 'node:fs/promises';
import { join } from 'node:path';

export function findFiles(root, { signal } = {}) {
  const emitter = new EventEmitter();
  const found = [];

  // 결과 전체를 원하는 사용자를 위한 프로미스
  emitter.promise = new Promise((resolve, reject) => {
    emitter.once('end', () => resolve(found));
    emitter.once('error', reject);
  });

  // 호출자가 리스너를 붙일 시간을 확보한 뒤 시작한다
  process.nextTick(async () => {
    try {
      const stack = [root];
      while (stack.length > 0) {
        signal?.throwIfAborted();
        const dir = stack.pop();
        for (const entry of await readdir(dir, { withFileTypes: true })) {
          const full = join(dir, entry.name);
          if (entry.isDirectory()) stack.push(full);
          else {
            found.push(full);
            emitter.emit('file', full); // 스트리밍 소비자용
          }
        }
      }
      emitter.emit('end', found);
    } catch (err) {
      emitter.emit('error', err);
    }
  });

  return emitter;
}
```

이제 두 가지 사용법이 모두 성립한다.

```js
// 1) 이벤트로 즉시 소비한다
findFiles('./src')
  .on('file', (f) => console.log('찾음:', f))
  .on('error', (e) => console.error(e))
  .on('end', (all) => console.log('총', all.length, '개'));

// 2) 프로미스로 전체 결과를 받는다
const all = await findFiles('./src').promise;
```

`emitter.promise`를 미리 만들면서 `once('error', reject)`를 붙였기 때문에, 2번 방식에서도 `error` 이벤트에 리스너가 존재한다. 4.4에서 본 "리스너 없는 error는 프로세스를 죽인다" 함정을 설계 단계에서 막은 것이다.

### 실무 함정

첫째, 프로미스를 **즉시 반환하지 말고** 이미터를 반환해야 한다. `async function findFiles()`로 만들면 함수가 프로미스를 반환하므로 `.on()`을 체이닝할 수 없다. 동기 반환 + 부가 프로미스 프로퍼티라는 순서가 이 패턴의 핵심이다.

둘째, 이미터를 반환한 뒤 이벤트를 **즉시** 발행하면 안 된다. 위 코드가 `process.nextTick`으로 시작을 미룬 이유가 그것이다. 미루지 않으면 첫 `file` 이벤트가 `findFiles`가 반환되기 전에 나가서, 4.2의 Zalgo 문제가 그대로 재현된다.

셋째, 프로미스 경로만 쓰는 사용자에게 이벤트 리스너 누수가 생기지 않도록 `once`를 쓰고, 취소 가능하게 `AbortSignal`을 받는다. 위 구현은 `signal?.throwIfAborted()`로 각 디렉터리 처리 전에 취소를 확인하므로, 호출자가 abort하면 `AbortError`가 `error` 이벤트와 프로미스 거부로 동시에 전파된다.

넷째, 이 패턴을 남용하지 않는다. 두 API를 유지하는 비용은 문서, 테스트, 오류 경로 모두에서 두 배가 된다. 스트리밍 소비 수요가 실제로 있을 때만 제공하고, 그렇지 않으면 프로미스 하나로 충분하다.

## 요약

- 연속 전달 스타일(CPS)은 결과를 반환값이 아니라 콜백으로 넘기는 방식이며, 콜백을 받는다는 사실만으로 비동기임이 보장되지는 않는다.
- 같은 함수가 조건에 따라 동기와 비동기를 오가면(Zalgo) 리스너 등록 전에 콜백이 실행되어 조용히 실패한다. `queueMicrotask`나 `process.nextTick`으로 비동기성을 항상 보장하거나, 아예 프로미스로 감싼다.
- Node.js 콜백 규약은 오류 우선, 콜백은 마지막 인자, 오류는 `Error` 인스턴스다. 비동기 경계를 넘어 `throw`한 예외는 호출자의 `try/catch`에 잡히지 않는다.
- `uncaughtException` 핸들러에서 실행을 계속하면 오염된 상태로 서비스를 이어 가는 것이다. 로깅과 정리 후 반드시 프로세스를 종료한다.
- `EventEmitter`의 `emit`은 동기이며 등록 순서대로 리스너를 호출한다. 리스너 없는 `'error'` 이벤트는 예외를 던져 프로세스를 죽이므로 실패 가능한 이미터에는 즉시 `error` 리스너를 붙인다.
- 이미터는 상속 또는 합성으로 만든다. 본질이 이벤트 소스면 상속, 발행 권한을 감추고 API 표면을 좁히려면 합성이다. `events.once`와 `events.on`이 이미터를 프로미스·비동기 이터레이터 세계로 연결한다.
- 리스너 누수는 요청마다 전역 이미터에 등록하는 코드에서 발생한다. `MaxListenersExceededWarning`은 상한을 올리라는 뜻이 아니라 해제 누락을 확인하라는 신호이며, `{ signal }` 옵션으로 정리 지점을 하나로 모으는 것이 현대적 해법이다.
- 결과가 한 번이면 콜백·프로미스, 여러 번이면 이벤트, 속도 제어가 필요하면 스트림을 쓴다. 둘 다 필요하면 이미터를 동기 반환하면서 프로미스를 함께 노출한다.

## 연습문제

1. 메모리 캐시를 가진 HTTP GET 래퍼 `fetchCached(url, cb)`를 오류 우선 콜백 규약으로 구현하라. 캐시 히트일 때도 콜백이 반드시 비동기로 호출되는지 검증하는 테스트를 `node:test`로 작성하되, 함수 호출 직후 설정한 플래그가 콜백 시점에 이미 `true`인지 확인하는 방식을 쓴다. 이어서 같은 URL에 대한 동시 요청이 네트워크 호출을 한 번만 발생시키도록 인플라이트 프로미스를 캐시하는 버전으로 다시 작성하라.

2. `TaskQueue` 클래스를 `EventEmitter`를 **합성**하여 구현하라. `add(task)`로 비동기 작업을 등록하고, 동시 실행 수를 생성자 인자로 제한하며, `start`·`task-done`(완료 개수와 전체 개수 전달)·`drain`·`error` 이벤트를 발행해야 한다. 외부에서 임의로 `emit`할 수 없어야 하고, `on`은 체이닝이 가능해야 한다. 그다음 같은 클래스를 상속 방식으로 다시 작성해 공개 API 표면이 어떻게 달라지는지 비교하고, 어느 쪽을 라이브러리로 배포하겠는지 근거와 함께 정리하라.

3. 요청마다 전역 `EventEmitter`에 `shutdown` 리스너를 등록하지만 해제하지 않는 HTTP 서버를 작성하고, 1,000건의 요청을 보낸 뒤 `emitter.listenerCount('shutdown')`와 `process.memoryUsage().heapUsed`를 출력해 누수를 관측하라. 이어서 요청마다 `AbortController`를 만들어 `{ signal }` 옵션으로 리스너를 등록하고 응답의 `close` 이벤트에서 `abort()`를 호출하도록 수정한 뒤 같은 측정을 반복해, 리스너 수와 힙 사용량이 어떻게 달라지는지 비교하라.
