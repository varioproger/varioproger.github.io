# 31장. 관측성

프로덕션에서 무언가 잘못됐을 때 우리가 던지는 질문은 사실 세 가지뿐이다. "무슨 일이 있었나", "얼마나 나쁜가", "어디서 느린가". 관측성(observability)의 세 기둥이라 불리는 로그·메트릭·트레이스는 각각 이 세 질문 하나씩에 답한다. 로그(log)는 개별 사건의 서사를 남기고, 메트릭(metric)은 시스템 전체의 상태를 숫자로 압축하며, 트레이스(trace)는 하나의 요청이 여러 서비스를 지나며 어디서 시간을 썼는지를 그린다.

셋은 대체재가 아니라 보완재다. 로그만 있으면 "이 요청이 실패했다"는 알지만 "지금 몇 퍼센트가 실패 중인가"는 모른다. 메트릭만 있으면 "p99가 2초"라는 사실은 알지만 그 2초가 어느 구간에서 만들어졌는지는 모른다. 트레이스만 있으면 느린 요청 하나의 해부도는 얻지만 그것이 어제도 그랬는지는 모른다. 이 장은 세 기둥을 Node.js에서 실제로 구축하는 방법과, 그 위에 얹히는 헬스 체크와 알림까지 다룬다. 그리고 그 모든 것이 성립하려면 먼저 "지금 보고 있는 이 신호가 어느 환경의 것인가"가 명확해야 하므로, 환경 분리에서 시작한다.

## 31.1 환경 분리: 개발, 스테이징, 프로덕션

### NODE_ENV라는 함정

Node.js 생태계에서 가장 오래되고 가장 널리 오해받는 환경 변수는 `NODE_ENV`다. 이 값을 "환경 이름을 담는 자유 문자열"로 생각하면 사고가 난다. 생태계의 다수 라이브러리는 `NODE_ENV`를 사실상 불리언(boolean)으로 취급한다. `production`이면 최적화 경로, 그 외의 모든 값이면 개발 경로다.

```js
// 라이브러리 내부에서 흔히 보이는 패턴
if (process.env.NODE_ENV !== 'production') {
  // 상세 에러 스택 노출, 템플릿 캐시 비활성화, 개발용 경고 출력,
  // PropTypes 검증, 추가 assertion ...
}
```

여기서 `NODE_ENV=staging`을 설정하면 어떤 일이 벌어지는지 보자. 스테이징 서버는 뷰 템플릿을 매 요청마다 다시 컴파일하고, 에러 응답에 전체 스택 트레이스를 실어 보내며, 개발용 검증 코드를 전부 실행한다. 프로덕션과 성능 특성이 완전히 달라지므로 스테이징에서 측정한 지연 시간은 프로덕션을 예측하지 못한다. 게다가 `npm ci --omit=dev`는 `NODE_ENV=production`일 때의 의존성 트리와 다른 결과를 낼 수 있어, "스테이징에는 있는데 프로덕션에는 없는 모듈"이라는 최악의 사고까지 만들어진다.

규칙은 단순하다. **`NODE_ENV`는 `production`과 `development` 두 값만 갖는다.** 그리고 배포 환경의 이름은 별도의 변수로 분리한다.

```bash
# 스테이징 서버의 환경 변수
NODE_ENV=production        # 런타임 최적화 모드. 라이브러리가 보는 값
APP_ENV=staging            # 우리 코드가 보는 배포 환경 이름
SERVICE_NAME=orders-api
SERVICE_VERSION=2.14.3
```

이렇게 나누면 "프로덕션과 동일한 런타임 동작을 하되 스테이징이라는 사실을 아는" 서버가 된다. 우리 코드에서 환경 분기가 필요할 때는 `APP_ENV`를 본다. 다만 환경 분기 자체를 최소화하는 것이 더 중요하다. 코드 안에 `if (APP_ENV === 'staging')`가 늘어날수록 스테이징에서 검증한 코드 경로와 프로덕션에서 실행되는 코드 경로가 달라지고, 그것은 스테이징의 존재 이유를 스스로 무너뜨린다.

### 설정 주입과 부팅 시 검증

환경 간 차이는 코드가 아니라 **설정 값**으로 표현되어야 한다. 12요소 앱(twelve-factor app)의 원칙대로 설정은 환경 변수로 주입하고, 코드에는 어떤 환경의 값도 하드코딩하지 않는다. 여기서 중요한 실무 규칙 하나는 **부팅 시 즉시 검증하고 실패하기(fail fast)**다.

설정 오류의 최악 시나리오는 애플리케이션이 정상적으로 기동한 뒤 세 시간 후 첫 결제 요청에서 "undefined는 URL이 아닙니다"로 죽는 것이다. 스키마 검증을 부팅 경로에 넣으면 이 실패가 배포 직후 헬스 체크 실패로 바뀌고, 롤아웃은 자동으로 중단된다.

```js
// config.js — 전 애플리케이션에서 유일한 process.env 접근 지점
import { z } from 'zod'

const schema = z.object({
  NODE_ENV: z.enum(['development', 'production']).default('development'),
  APP_ENV: z.enum(['local', 'ci', 'staging', 'production']),
  SERVICE_NAME: z.string().min(1),
  SERVICE_VERSION: z.string().min(1),
  PORT: z.coerce.number().int().positive().default(3000),
  DATABASE_URL: z.string().url(),
  REDIS_URL: z.string().url(),
  LOG_LEVEL: z.enum(['trace', 'debug', 'info', 'warn', 'error', 'fatal']).default('info'),
  OTEL_EXPORTER_OTLP_ENDPOINT: z.string().url().optional(),
  // 샘플링 비율처럼 환경마다 다른 값도 설정으로 뺀다
  TRACE_SAMPLE_RATIO: z.coerce.number().min(0).max(1).default(0.1),
  SHUTDOWN_GRACE_MS: z.coerce.number().int().default(15_000)
})

const parsed = schema.safeParse(process.env)
if (!parsed.success) {
  // 여기서 로거를 쓰지 않는다. 로거 자체가 설정에 의존하기 때문이다
  console.error('설정 검증 실패:', z.treeifyError(parsed.error))
  process.exit(78) // EX_CONFIG. 재시작해도 낫지 않는 실패임을 종료 코드로 알린다
}

export const config = Object.freeze(parsed.data)
export const isProduction = config.APP_ENV === 'production'
```

`process.env`에 접근하는 곳을 이 파일 하나로 제한하는 것이 핵심이다. 코드 곳곳에서 `process.env.X`를 직접 읽으면 어떤 변수가 필요한지 아무도 알 수 없고, 검증도 불가능하다. 이 규칙은 린트 규칙(`no-process-env`)으로 강제할 수 있다.

시크릿(secret)은 같은 방식으로 주입하되 저장소가 다르다. 데이터베이스 비밀번호나 API 키는 환경 변수 파일이 아니라 시크릿 관리자에서 컨테이너로 주입되고, 우리 코드는 그것이 어디서 왔는지 알 필요가 없다. 다만 로그와 에러 리포트에 시크릿이 새지 않도록 설정 객체를 통째로 출력하는 코드는 금지하고, 부팅 시 출력할 때는 마스킹된 요약만 남긴다.

```js
// 부팅 로그: 어떤 설정으로 떴는지는 사고 조사에 반드시 필요하다
logger.info({
  appEnv: config.APP_ENV,
  version: config.SERVICE_VERSION,
  port: config.PORT,
  logLevel: config.LOG_LEVEL,
  // URL은 자격 증명을 제거한 뒤 호스트만 남긴다
  database: new URL(config.DATABASE_URL).host,
  nodeVersion: process.version
}, 'service starting')
```

### 스테이징이 프로덕션과 다를 때 생기는 사고

스테이징의 목적은 하나다. **프로덕션에서 처음 발견될 문제를 프로덕션 이전에 발견하는 것.** 그러므로 스테이징이 프로덕션과 다른 모든 차원은 곧 검증 사각지대다. 실무에서 반복적으로 사고를 만드는 차이는 다음과 같다.

**데이터 규모.** 스테이징 데이터베이스에 1만 행, 프로덕션에 8천만 행이 있다면 인덱스 누락은 스테이징에서 절대 드러나지 않는다. 풀 스캔이 5ms로 끝나기 때문이다. 같은 쿼리가 프로덕션에서 12초가 되고, 커넥션 풀이 고갈되고, 무관해 보이는 다른 엔드포인트까지 타임아웃된다. 완화책은 프로덕션 규모의 익명화된 데이터 세트를 스테이징에 유지하거나, 최소한 CI에서 쿼리 실행 계획(`EXPLAIN`)을 검사하는 것이다.

**인스턴스 수.** 스테이징은 인스턴스 1개, 프로덕션은 12개인 구성은 매우 흔하다. 이때 인메모리 캐시, 인메모리 세션, 인메모리 레이트 리밋, 프로세스 로컬 잠금은 스테이징에서 완벽하게 동작하고 프로덕션에서 완전히 깨진다. 스케줄러도 마찬가지다. 프로세스마다 `setInterval`로 도는 배치는 스테이징에서 하루 1번, 프로덕션에서 하루 12번 실행된다. 정산 배치라면 이것은 금전 사고다.

**앞단 구성.** 스테이징에는 TLS 종료 프록시가 없고 프로덕션에는 있다면, `X-Forwarded-For`와 `X-Forwarded-Proto` 처리, 프록시 타임아웃, 요청 본문 크기 제한, 헤더 크기 제한이 전부 미검증 상태로 프로덕션에 나간다. 리다이렉트 루프와 잘못된 클라이언트 IP 기반 레이트 리밋이 이 범주의 단골 사고다.

**외부 의존성.** 결제 게이트웨이의 샌드박스는 응답이 항상 빠르고 항상 성공한다. 프로덕션 엔드포인트는 느리고, 간헐적으로 5xx를 반환하고, 레이트 리밋이 있다. 샌드박스만 보고 만든 코드에는 타임아웃도, 재시도도, 서킷 브레이커도 없다(29장 참조).

이 차이들은 완전히 없앨 수 없다. 현실적인 대응은 **차이 목록을 명시적으로 문서화하고, 각 차이에 대해 "그래서 이 위험은 어떻게 검증하는가"를 적어두는 것**이다. 문서화되지 않은 차이는 사고가 나기 전까지 아무도 모른다. 그리고 스테이징으로 잡을 수 없는 위험은 프로덕션 안에서 안전하게 검증하는 방법(카나리 배포, 기능 플래그, 섀도 트래픽)으로 옮긴다.

### 모든 신호에 환경 태그를 붙인다

환경 분리가 관측성 장의 첫 절에 오는 이유는, 앞으로 만들 모든 신호에 동일한 식별 속성이 붙어야 하기 때문이다. OpenTelemetry는 이것을 리소스 속성(resource attribute)이라 부르고, 세 가지가 사실상 필수다.

```js
// 로그, 메트릭, 트레이스가 모두 공유하는 식별자
export const resourceAttributes = {
  'service.name': config.SERVICE_NAME,
  'service.version': config.SERVICE_VERSION,
  'deployment.environment': config.APP_ENV
}
```

이 세 값이 모든 신호에 일관되게 붙어 있어야 "스테이징 로그가 프로덕션 대시보드에 섞여 들어와 착시를 만드는" 사고를 막을 수 있고, 배포 버전 단위로 오류율을 비교하는 것도 가능해진다. 카나리 배포에서 "새 버전만 오류율이 높은가"를 판정하는 근거가 바로 `service.version` 라벨이다.

## 31.2 구조화된 로깅과 로그 수집

### 사람이 읽는 로그에서 기계가 읽는 로그로

혼자 서버 한 대를 운영할 때 로그는 사람이 읽는 문장이었다.

```text
2026-09-01 10:22:31 주문 처리 실패: 사용자 8812, 주문 A-4471, 재고 부족
```

이 형식은 인스턴스가 늘어나는 순간 무너진다. 서버 12대의 로그가 하나의 스트림으로 합쳐지면 `grep`으로 "어제 오후 3시에서 4시 사이, 결제 서비스에서, 특정 사용자에게 발생한 5xx"를 찾는 일이 텍스트 파싱 문제가 된다. 스택 트레이스는 여러 줄에 걸쳐 있어 줄 단위 도구와 궁합이 나쁘고, 메시지 포맷은 개발자마다 달라 정규식이 매번 다시 필요하다. 무엇보다 집계가 불가능하다. "재고 부족 실패가 시간당 몇 건인가"를 답하려면 문장에서 숫자를 다시 추출해야 한다.

구조화된 로깅(structured logging)은 로그 한 줄을 문장이 아니라 **필드를 가진 이벤트**로 본다.

```json
{"level":50,"time":1756721551123,"service.name":"orders-api","deployment.environment":"production","reqId":"01J9Z4","trace_id":"4bf92f3577b34da6a3ce929d0e0e4736","userId":8812,"orderId":"A-4471","reason":"out_of_stock","msg":"order failed"}
```

이제 질의는 텍스트 검색이 아니라 필드 조건이 된다. `reason="out_of_stock"`으로 필터하고 분 단위로 집계하는 일이 한 줄짜리 쿼리로 끝난다. 사람이 읽기 어려워졌다는 대가는 개발 환경에서 예쁜 출력기(pretty printer)를 붙여 해결한다. 프로덕션의 소비자는 사람이 아니라 로그 시스템이다.

### pino로 구현하기

Node.js에서 구조화된 로깅의 사실상 표준은 pino다. 빠른 이유는 단순하다. JSON 직렬화를 최소 비용으로 하고, 포매팅과 전송을 별도 워커 스레드로 넘기며, 기본 출력이 그냥 stdout이다.

```js
// logger.js
import pino from 'pino'
import { config, isProduction } from './config.js'
import { resourceAttributes } from './resource.js'

export const logger = pino({
  level: config.LOG_LEVEL,
  // 모든 줄에 붙는 공통 필드
  base: { ...resourceAttributes, pid: process.pid, host: process.env.HOSTNAME },
  // 기본 level은 숫자다. 수집기가 문자열을 기대하면 여기서 변환한다
  formatters: {
    level: (label, number) => ({ level: label, levelValue: number })
  },
  timestamp: pino.stdTimeFunctions.isoTime,
  // 민감 정보 마스킹
  redact: {
    paths: [
      'req.headers.authorization',
      'req.headers.cookie',
      'req.headers["x-api-key"]',
      'user.email',
      'user.phone',
      '*.password',
      '*.cardNumber',
      'body.paymentToken'
    ],
    censor: '[REDACTED]'
  },
  // 개발에서만 사람이 읽는 형식으로. 프로덕션은 순수 JSON
  transport: isProduction
    ? undefined
    : { target: 'pino-pretty', options: { colorize: true, translateTime: 'SYS:standard' } }
})
```

`redact`는 방어선이지 해결책이 아니라는 점을 강조할 필요가 있다. 경로 기반 마스킹은 우리가 예상한 위치의 값만 가린다. 누군가 `logger.info({ payload: req.body }, 'received')`처럼 통째로 찍으면 경로가 달라져 마스킹이 비껴간다. 실무에서는 두 가지를 함께 쓴다. 첫째, 요청·응답 객체를 통으로 로깅하지 않고 필요한 필드만 명시적으로 뽑는 직렬화기(serializer)를 정의한다. 둘째, 로그 파이프라인 쪽에도 신용카드 번호 패턴 같은 2차 마스킹 규칙을 둔다.

```js
// 통째로 찍지 않고 뽑아 쓴다
export const serializers = {
  req: (req) => ({ method: req.method, route: req.routeOptions?.url ?? req.url, ip: req.ip }),
  res: (res) => ({ statusCode: res.statusCode }),
  err: pino.stdSerializers.err
}
```

### 로그 레벨의 실무 기준

레벨은 "중요도"라는 모호한 기준이 아니라 **누가, 언제 이것을 보는가**로 정의해야 팀 안에서 일관성이 생긴다.

| 레벨 | 의미 | 기준 질문 |
|---|---|---|
| `fatal` | 프로세스가 계속 살 수 없다 | 이 직후 프로세스가 종료되는가 |
| `error` | 사람이 언젠가 봐야 하는 실패 | 이것이 100건 발생하면 조사할 것인가 |
| `warn` | 이상하지만 자동 복구됨 | 재시도로 성공했거나 폴백이 동작했는가 |
| `info` | 정상 운영 중의 의미 있는 사건 | 사고 조사 때 이 줄이 필요한가 |
| `debug` | 개발자용 상세 흐름 | 프로덕션에서 기본 꺼져 있어도 되는가 |
| `trace` | 극단적으로 상세한 추적 | 로컬 디버깅 전용인가 |

가장 흔한 오류는 두 가지다. 첫째, 클라이언트 오류를 `error`로 찍는 것. 사용자가 잘못된 JSON을 보낸 400 응답은 우리 시스템의 실패가 아니다. 이것을 `error`로 찍으면 오류 로그가 노이즈로 가득 차고, 진짜 500이 그 안에 묻힌다. 400번대는 `info` 또는 `warn`, 500번대는 `error`가 기본선이다. 둘째, 잡아서 처리한 예외를 `error`로 찍고 다시 던지는 것. 같은 실패가 호출 스택을 올라가며 세 번 기록되면 오류 건수 집계가 세 배로 부풀려진다. **예외는 최종적으로 처리되는 곳에서 한 번만 기록한다.**

### 상관관계 ID와 AsyncLocalStorage

분산 환경에서 로그의 가치는 **하나의 요청에 속한 모든 줄을 모을 수 있는가**에 달려 있다. 이를 위해 요청마다 상관관계 ID(correlation ID)를 부여하고 모든 로그 줄에 붙인다. 문제는 이 ID를 함수 인자로 끝까지 들고 다니는 것이 현실적이지 않다는 점이다. 라우터에서 서비스로, 서비스에서 리포지토리로, 리포지토리에서 재시도 유틸리티로 내려가는 모든 시그니처에 `ctx`를 추가할 수는 없다.

`AsyncLocalStorage`가 정확히 이 문제를 푼다(16장 참조). 비동기 호출 체인 전체에 걸쳐 유지되는 저장소를 만들고, 로거가 로그를 찍는 시점에 그 저장소를 조회하게 하면 된다.

```js
// request-context.js
import { AsyncLocalStorage } from 'node:async_hooks'

const storage = new AsyncLocalStorage()

export function runWithContext(context, fn) {
  return storage.run(context, fn)
}

export function getContext() {
  return storage.getStore()
}

// 요청 처리 도중 컨텍스트에 값을 추가한다 (인증 후 userId 등)
export function setContextValue(key, value) {
  const store = storage.getStore()
  if (store) store[key] = value
}
```

여기에 pino의 `mixin` 옵션을 결합하면, 애플리케이션 코드는 상관관계 ID의 존재조차 몰라도 된다. `mixin`은 로그를 찍을 때마다 호출되어 추가 필드를 반환하는 함수다.

```js
// logger.js에 추가
import { getContext } from './request-context.js'

export const logger = pino({
  // ... 앞의 설정 ...
  mixin() {
    const ctx = getContext()
    if (!ctx) return {}
    // 트레이스 ID까지 함께 넣으면 로그에서 트레이스로 바로 점프할 수 있다
    return { reqId: ctx.reqId, trace_id: ctx.traceId, span_id: ctx.spanId, userId: ctx.userId }
  }
})
```

요청 진입점에서 컨텍스트를 연다. 상관관계 ID는 상류 서비스가 이미 부여했을 수 있으므로 헤더를 먼저 확인하고, 없을 때만 생성한다. 이 규칙을 지켜야 게이트웨이부터 최말단 서비스까지 하나의 ID로 이어진다.

```js
// server.js (Fastify 기준, Express도 동일한 구조)
import { randomUUID } from 'node:crypto'
import { trace } from '@opentelemetry/api'
import { runWithContext } from './request-context.js'

app.addHook('onRequest', (req, reply, done) => {
  const reqId = req.headers['x-request-id'] ?? randomUUID()
  const spanCtx = trace.getActiveSpan()?.spanContext()

  reply.header('x-request-id', reqId) // 클라이언트에게도 돌려준다

  runWithContext(
    { reqId, traceId: spanCtx?.traceId, spanId: spanCtx?.spanId },
    () => done()
  )
})

// 하류 서비스 호출 시 ID를 전파한다
export async function callInventory(path, init = {}) {
  const ctx = getContext()
  return fetch(new URL(path, config.INVENTORY_URL), {
    ...init,
    headers: { ...init.headers, 'x-request-id': ctx?.reqId ?? '' }
  })
}
```

`AsyncLocalStorage`에는 비용이 있다. 컨텍스트 전환마다 추가 작업이 발생하므로 극단적으로 처리량이 중요한 경로에서는 측정해볼 가치가 있다. 다만 현대 Node.js(v20 이상)에서 이 비용은 과거보다 크게 줄었고, 대부분의 I/O 바운드 웹 서비스에서는 상관관계 ID가 주는 조사 능력이 그 비용을 압도한다.

### 로그 볼륨, 비용, 샘플링

로그는 무료가 아니다. 규모를 감각적으로 잡아보자. 초당 2,000 요청을 받는 서비스가 요청당 3줄, 줄당 400바이트를 남긴다면 하루 볼륨은 다음과 같다.

```text
2,000 req/s × 3 line × 400 B × 86,400 s ≈ 207 GB/day
```

30일 보존이면 6TB가 넘고, 여기에 색인 오버헤드와 복제본까지 더하면 실제 스토리지는 그 몇 배가 된다. 많은 조직에서 관측성 비용이 컴퓨트 비용을 넘어서는 지점이 바로 여기다.

비용을 줄이는 방법은 네 가지다.

**첫째, 로그로 세지 말고 메트릭으로 센다.** "요청 수", "오류율", "지연 시간 분포"를 알고 싶어서 모든 요청을 로깅하는 것은 가장 비싼 카운터다. 이런 질문에는 31.3의 메트릭이 몇 자릿수 싸게 답한다. 로그는 "이 특정 요청에 무슨 일이 있었나"라는, 집계로 답할 수 없는 질문을 위해 남긴다.

**둘째, 성공 요청을 샘플링한다.** 오류와 느린 요청은 100% 남기고, 정상 요청은 일부만 남긴다. 트레이스 ID를 기준으로 샘플링하면 같은 요청의 모든 서비스 로그가 함께 남거나 함께 버려져 일관성이 유지된다.

```js
// 트레이스 ID 기반 결정론적 샘플링. 서비스가 달라도 같은 판정이 나온다
function shouldSampleRequest({ traceId, statusCode, durationMs }) {
  if (statusCode >= 500) return true          // 서버 오류는 전량
  if (durationMs > 1_000) return true          // 느린 요청은 전량
  if (!traceId) return Math.random() < 0.1
  // trace ID의 마지막 4자리를 16진수로 읽어 균등 분포를 얻는다
  const bucket = parseInt(traceId.slice(-4), 16) / 0xffff
  return bucket < config.LOG_SAMPLE_RATIO
}
```

**셋째, 레벨을 런타임에 바꾼다.** 평시에는 `info`, 사고 조사 중에는 특정 인스턴스만 `debug`로 올린다. pino는 `logger.level = 'debug'`로 즉시 바뀌므로, 관리용 엔드포인트나 설정 감시로 제어할 수 있다. 다만 이 엔드포인트는 반드시 인증 뒤에 둔다.

**넷째, 보존 기간을 계층화한다.** 최근 7일은 빠른 검색이 가능한 핫 스토리지, 그 이후 90일은 압축된 객체 스토리지, 규제 대상 감사 로그만 장기 보관으로 나눈다. 모든 로그를 같은 기간 같은 성능으로 보관할 이유는 없다.

### 수집 파이프라인: 앱은 stdout에만 쓴다

컨테이너 환경에서 애플리케이션의 로깅 책임은 **stdout에 한 줄씩 JSON을 쓰는 것까지**다. 파일 회전, 원격 전송, 재시도, 버퍼링은 애플리케이션의 일이 아니다. 이유는 세 가지다. 로그 전송이 애플리케이션과 생명주기를 공유하면 전송 지연이 애플리케이션 지연이 되고, 컨테이너가 죽을 때 버퍼에 남은 로그가 사라지며, 수집 백엔드를 바꿀 때마다 애플리케이션을 재배포해야 한다.

파이프라인의 개념적 단계는 벤더와 무관하게 동일하다.

1. **수집(collection).** 노드마다 하나씩 도는 에이전트가 컨테이너 stdout을 읽는다. Promtail, Fluent Bit, Vector가 이 역할이다.
2. **정규화(processing).** JSON을 파싱하고, 쿠버네티스 메타데이터(파드명, 네임스페이스, 라벨)를 붙이고, 2차 마스킹과 드롭 규칙을 적용한다.
3. **저장·색인(storage).** 여기서 아키텍처가 갈린다. Elasticsearch 계열은 로그 본문 전체를 역색인하므로 임의의 전문 검색이 빠르지만 저장 비용과 색인 부하가 크다. Loki 계열은 라벨만 색인하고 본문은 압축 청크로 저장하므로 저렴하지만, 검색은 라벨로 후보를 좁힌 뒤 스캔하는 방식이다. **"어떤 필드로 좁힐 것인가"가 미리 정해져 있으면 라벨 색인이 유리하고, 임의 탐색이 잦으면 전문 색인이 유리하다.**
4. **조회(query).** 대시보드와 조사 도구.

## 31.3 메트릭: 수집, 저장, 대시보드

### 네 가지 메트릭 타입과 잘못 고를 때의 대가

메트릭은 시간에 따른 숫자의 나열이다. 타입 선택이 사소해 보이지만, 잘못 고르면 나중에 답할 수 없는 질문이 생긴다. 저장된 데이터의 형태가 가능한 질의를 결정하기 때문이다.

**카운터(counter)**는 단조 증가하는 누적값이다. 처리한 요청 수, 발생한 오류 수, 전송한 바이트 수가 여기 속한다. 카운터 자체의 값은 거의 의미가 없고, 우리가 보는 것은 언제나 그 변화율이다. Prometheus에서 `rate(http_requests_total[5m])`가 초당 요청 수를 준다. 카운터는 프로세스가 재시작하면 0으로 돌아가는데, `rate()`는 이 리셋을 감지해 자동으로 보정한다. 이것이 카운터를 쓰는 실질적 이유 중 하나다.

**게이지(gauge)**는 오르내리는 순간값이다. 현재 활성 커넥션 수, 큐 길이, 힙 사용량, 이벤트 루프 지연이 여기 속한다.

**히스토그램(histogram)**은 관측값의 분포를 미리 정한 버킷(bucket)에 누적한다. 요청 지연 시간, 응답 크기가 대표적이다. 각 버킷은 "이 값 이하가 몇 건"이라는 누적 카운터이므로, 여러 인스턴스의 버킷을 그냥 더하면 전체 분포가 된다. 이 **합산 가능성(additivity)**이 히스토그램의 핵심 가치다. 백분위수는 조회 시점에 서버가 계산한다.

**서머리(summary)**는 클라이언트에서 백분위수를 직접 계산해 내보낸다. 개별 인스턴스의 p99는 정확하지만, **여러 인스턴스의 p99를 합칠 수 없다.** 인스턴스 12개의 p99를 평균 낸 값은 전체 p99가 아니며 통계적으로 아무 의미가 없다.

잘못 고르면 어떻게 되는지 구체적으로 보자.

- **지연 시간을 게이지에 평균으로 저장한 경우.** "평균 응답 시간 120ms"라는 대시보드는 사실상 아무것도 알려주지 않는다. 요청의 1%가 8초를 쓰고 있어도 평균은 조용하다. 사용자가 겪는 것은 평균이 아니라 꼬리(tail)이고, 이것을 보려면 처음부터 분포를 저장했어야 한다. 게이지로 저장한 평균에서 p99를 사후에 복원할 방법은 없다.
- **여러 인스턴스에 서머리를 쓴 경우.** 서비스 전체 p99를 물었을 때 답할 수 없다. 히스토그램으로 바꾸는 순간 해결되지만, 과거 데이터는 복구되지 않는다.
- **누적값을 게이지로 노출한 경우.** 재시작 시 값이 떨어지고, `rate()` 대신 `increase()`나 차분을 쓰면 음수 구간이 생겨 그래프가 망가진다.

실무 규칙은 단순하다. **세는 것은 카운터, 현재 상태는 게이지, 분포는 히스토그램. 서머리는 단일 인스턴스에서 백분위수 정확도가 특별히 중요할 때만.**

### prom-client로 계측하기

```js
// metrics.js
import client from 'prom-client'
import { config } from './config.js'
import { resourceAttributes } from './resource.js'

export const registry = new client.Registry()
registry.setDefaultLabels({
  service: resourceAttributes['service.name'],
  version: resourceAttributes['service.version'],
  env: resourceAttributes['deployment.environment']
})

// Node.js 기본 지표: 힙, GC, 이벤트 루프 지연, 활성 핸들, 파일 디스크립터

export const httpDuration = new client.Histogram({
  name: 'http_server_request_duration_seconds',
  help: 'HTTP 요청 처리 시간(초)',
  // 라벨은 값의 종류가 유한한 것만. route는 반드시 템플릿이어야 한다
  labelNames: ['method', 'route', 'status_code'],
```

### RED와 USE: 무엇을 볼 것인가

메트릭을 무한정 만들 수는 있지만, 대시보드에 무엇을 올릴지는 두 가지 프레임으로 정리된다.

**RED 메서드**는 요청을 처리하는 서비스에 적용한다. Rate(초당 요청 수), Errors(초당 실패 수 또는 실패 비율), Duration(지연 시간 분포). 서비스 하나당 이 세 그래프면 "사용자가 지금 나쁜 경험을 하고 있는가"에 답할 수 있다.

```promql
# Rate
sum by (route) (rate(http_server_request_duration_seconds_count[5m]))

# Errors — 비율로 본다. 절대 건수는 트래픽 변화와 구분되지 않는다
sum(rate(http_server_request_duration_seconds_count{status_code=~"5.."}[5m]))
  / sum(rate(http_server_request_duration_seconds_count[5m]))

# Duration — 히스토그램에서 서버가 분위수를 계산한다
histogram_quantile(
  0.99,
  sum by (le, route) (rate(http_server_request_duration_seconds_bucket[5m]))
)
```

**USE 메서드**는 자원에 적용한다. Utilization(사용률), Saturation(포화, 대기가 발생하는 정도), Errors(자원 자체의 오류). 커넥션 풀이라면 사용 중인 커넥션 비율, 커넥션을 기다리는 요청 수, 커넥션 획득 실패 수가 각각 대응한다. 포화 지표가 가장 자주 빠지는데, 사고의 전조는 대개 사용률이 아니라 포화에서 먼저 보인다. 사용률 100%는 정상 운영일 수도 있지만, 대기 큐가 자라기 시작하면 항상 문제다.

### Node.js 고유 지표

Node.js는 단일 스레드 이벤트 루프 위에서 돌기 때문에, 다른 런타임에는 없는 고유한 실패 양상이 있다. CPU 사용률이 40%인데 응답이 느린 상황은 Node.js에서 흔하고, 이때 봐야 할 것은 CPU가 아니라 **이벤트 루프 지연(event loop delay)**이다.

```js
// node-metrics.js
import { monitorEventLoopDelay, PerformanceObserver, constants } from 'node:perf_hooks'
import client from 'prom-client'
import { registry } from './metrics.js'

// 이벤트 루프 지연: 타이머가 예정 시각보다 얼마나 늦게 실행됐는가
const loopDelay = monitorEventLoopDelay({ resolution: 10 })
loopDelay.enable()

new client.Gauge({
  name: 'nodejs_event_loop_delay_p99_seconds',
  help: '이벤트 루프 지연 p99',
  registers: [registry],
  collect() {
    // 나노초 → 초
    this.set(loopDelay.percentile(99) / 1e9)
    loopDelay.reset() // 스크레이프 주기마다 창을 비운다
  }
})

// GC 일시 정지 시간: 종류별로 나눠 본다
const gcPause = new client.Histogram({
  name: 'nodejs_gc_pause_seconds',
  help: 'GC 일시 정지 시간',
  labelNames: ['kind'],
  buckets: [0.0005, 0.001, 0.005, 0.01, 0.05, 0.1, 0.5],
  registers: [registry]
})

const gcKinds = {
  [constants.NODE_PERFORMANCE_GC_MINOR]: 'minor',
  [constants.NODE_PERFORMANCE_GC_MAJOR]: 'major',
  [constants.NODE_PERFORMANCE_GC_INCREMENTAL]: 'incremental',
  [constants.NODE_PERFORMANCE_GC_WEAKCB]: 'weakcb'
}

new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    gcPause.observe({ kind: gcKinds[entry.detail?.kind] ?? 'unknown' }, entry.duration / 1000)
  }
}).observe({ entryTypes: ['gc'] })

// 활성 핸들·요청 수: 누수의 조기 경보
new client.Gauge({
  name: 'nodejs_active_resources',
  help: '활성 핸들 및 요청 수',
  labelNames: ['type'],
  registers: [registry],
  collect() {
    const counts = {}
    for (const type of process.getActiveResourcesInfo()) {
      counts[type] = (counts[type] ?? 0) + 1
    }
    for (const [type, n] of Object.entries(counts)) this.set({ type }, n)
  }
})
```

해석 기준을 함께 정해두면 대시보드가 의미를 갖는다. 이벤트 루프 지연 p99가 수십 밀리초를 넘기면 어딘가에서 동기 작업이 루프를 붙잡고 있다는 뜻이고, 그 상태에서는 모든 요청이 함께 느려진다. `major` GC의 빈도와 시간이 함께 증가하는데 힙이 줄지 않으면 메모리 누수를 의심한다. 활성 소켓 핸들 수가 단조 증가하면 응답을 소비하지 않은 HTTP 요청이나 닫히지 않는 커넥션이 있다는 신호다(29장 참조).

### 히스토그램 버킷 설계와 카디널리티 폭발

히스토그램의 버킷은 나중에 바꾸기 어렵다. 버킷을 바꾸면 과거 데이터와 비교가 깨지기 때문이다. 설계 원칙은 세 가지다.

첫째, **SLO 경계를 버킷 경계에 반드시 포함한다.** "요청의 99%가 300ms 이내"가 목표라면 `0.3`이 버킷 경계에 있어야 한다. 없으면 `histogram_quantile`이 인접 버킷 사이를 선형 보간하므로 오차가 생기고, 오류 예산 계산이 부정확해진다. 사실 SLO 판정에는 백분위수보다 **"경계 이하 비율"**을 직접 쓰는 것이 정확하다.

```promql
# 300ms 이내로 처리된 요청의 비율. 보간 오차가 없다
sum(rate(http_server_request_duration_seconds_bucket{le="0.3"}[30m]))
  / sum(rate(http_server_request_duration_seconds_count[30m]))
```

둘째, **관심 영역에 버킷을 몰아준다.** 지연 시간은 로그 스케일로 퍼지므로 등간격 버킷은 낭비다. 밀리초 단위 서비스에 `[1, 2, 3, ... 10]`초 버킷을 두면 대부분의 관측값이 첫 버킷에 몰려 아무것도 구분하지 못한다.

셋째, **버킷 수는 시계열 수를 곱셈으로 늘린다.** 이것이 다음 주제로 이어진다.

**카디널리티 폭발(cardinality explosion)**은 메트릭 시스템을 죽이는 가장 흔한 원인이다. Prometheus에서 하나의 시계열은 "메트릭 이름 + 라벨 값 조합" 단위로 생성되고, 각 시계열은 메모리에 상주하는 인덱스 항목과 청크를 갖는다. 조합 수는 라벨 값 종류의 곱이다.

```text
http_server_request_duration_seconds_bucket
  route(40) × method(5) × status_code(12) × bucket(13, +Inf 포함)
  = 31,200 시계열   ← 감당 가능
```

여기에 `user_id` 라벨을 추가하면 어떻게 되는가. 사용자가 50만 명이면 시계열 수는 156억 개가 된다. 실제로는 그 전에 Prometheus가 메모리를 다 쓰고 OOM으로 죽고, 그 인스턴스가 담당하던 **모든 서비스의 메트릭이 동시에 사라진다.** 관측 도구가 사고를 만드는 것이다.

라벨에 절대 넣지 말아야 할 것들은 다음과 같다.

- 사용자 ID, 세션 ID, 요청 ID, 트레이스 ID, 주문 번호 등 모든 고유 식별자
- 원본 URL 경로(`/orders/A-4471`). 반드시 라우트 템플릿(`/orders/:id`)으로 정규화한다
- 이메일, IP 주소, User-Agent 전체 문자열
- 외부 시스템이 주는 임의의 오류 메시지. 유한한 오류 코드로 매핑한 뒤 라벨로 쓴다
- 타임스탬프나 버전 해시처럼 배포마다 증가하는 값(단, `version`은 배포 빈도가 낮고 옛 시계열이 곧 정지하므로 통상 허용된다)

고유 식별자 단위의 조사는 메트릭이 아니라 로그와 트레이스의 일이다. 이 역할 분담이 세 기둥을 나누는 실질적 이유다. 안전장치로 스크레이프 단계에 시계열 상한을 두고, 상한 초과 시 그 대상만 거부되도록 설정한다.

```yaml
# prometheus.yml
global:
  scrape_interval: 15s
  external_labels: { cluster: prod-apne1 }

scrape_configs:
  - job_name: orders-api
    kubernetes_sd_configs: [{ role: pod }]
    # 대상 하나가 시계열 20만 개를 뿜어도 나머지 대상은 보호된다
    sample_limit: 200000
    label_limit: 30
    relabel_configs:
      - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape]
        action: keep
        regex: "true"
      - source_labels: [__meta_kubernetes_pod_label_app]
        target_label: service
```

### pull과 push, 그리고 대시보드

Prometheus는 **풀(pull) 모델**이다. 서버가 각 인스턴스의 `/metrics`를 주기적으로 긁어간다. 이 방식의 장점은 스크레이프 성공 여부 자체가 `up` 메트릭이 되어 "인스턴스가 살아 있는가"를 별도 장치 없이 알려준다는 것, 그리고 서비스 디스커버리와 결합해 대상 목록이 자동 관리된다는 것이다. 단점은 수명이 짧은 프로세스를 놓친다는 점이다. 30초 만에 끝나는 배치 작업은 스크레이프 주기 사이에 사라진다. 이 경우 Pushgateway에 결과를 밀어 넣고 Prometheus가 그것을 긁는 우회 경로를 쓴다.

StatsD/Graphite 계열은 **푸시(push) 모델**이다. 애플리케이션이 UDP로 로컬 에이전트에 값을 쏘고, 에이전트가 집계해 저장소로 보낸다. 방화벽을 넘기 쉽고, 서버가 대상 목록을 알 필요가 없으며, 단명 프로세스에 자연스럽다. 대신 UDP 손실이 조용히 발생할 수 있고, 인스턴스가 죽었는지 그냥 아무것도 안 보내는 건지 구분하기 어렵다. 서버리스나 크론 잡이 많은 환경에서는 푸시가, 장기 실행 서비스가 중심인 환경에서는 풀이 대체로 잘 맞는다. OpenTelemetry는 두 모델을 모두 지원하므로, 계측을 OTel API로 해두면 이 선택을 나중으로 미룰 수 있다.

대시보드는 계층으로 구성한다. 최상단에 서비스별 RED 지표와 SLO 소진율 하나, 그 아래에 의존성(데이터베이스, 캐시, 외부 API)별 지표, 가장 아래에 런타임 내부 지표(이벤트 루프, 힙, GC)를 둔다. 사고 대응은 위에서 아래로 내려가며 범위를 좁히는 작업이고, 대시보드는 그 순서를 그대로 반영해야 한다. 모든 그래프를 한 화면에 늘어놓은 대시보드는 새벽 3시에 아무 도움이 되지 않는다.

## 31.4 분산 추적: OpenTelemetry

### 메트릭이 답할 수 없는 질문

"결제 API의 p99가 2.4초"라는 사실을 알았다고 하자. 다음 질문은 언제나 "그 2.4초가 어디서 생겼는가"다. 이 서비스가 사용자 서비스와 재고 서비스를 호출하고, 각각이 다시 데이터베이스와 캐시를 부른다면 후보는 열 곳이 넘는다. 각 서비스의 메트릭을 따로 보며 시간대를 맞춰 추측하는 것은 가능하지만 느리고 자주 틀린다.

분산 추적(distributed tracing)은 **하나의 요청**이 시스템을 통과하는 경로를 하나의 트리로 재구성한다.

- **트레이스(trace)**: 하나의 논리적 요청 전체. 128비트 ID로 식별된다.
- **스팬(span)**: 트레이스 안의 개별 작업 단위. 이름, 시작·종료 시각, 부모 스팬 ID, 속성(attribute), 이벤트, 상태를 갖는다.
- **컨텍스트 전파(context propagation)**: 현재 트레이스·스팬 ID를 프로세스 경계 너머로 전달하는 것.

W3C Trace Context 표준은 이 전파를 `traceparent` HTTP 헤더로 규정한다.

```text
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  │                                │                │
             │  │                                │                └ 플래그(01 = 샘플됨)
             │  │                                └ 부모 스팬 ID (64비트)
             │  └ 트레이스 ID (128비트)
             └ 버전
```

표준 헤더를 쓴다는 것이 중요하다. 자체 헤더를 쓰면 프록시, API 게이트웨이, 관리형 데이터베이스, 서드파티 SDK가 트레이스를 이어주지 못한다. `traceparent`는 이들이 이미 이해하는 언어다.

### OpenTelemetry 구성과 자동 계측

OpenTelemetry(OTel)는 계측 API와 SDK, 그리고 신호를 백엔드로 보내는 익스포터(exporter)의 표준이다. 백엔드는 Jaeger, Zipkin, Tempo, 또는 상용 서비스 중 무엇이든 될 수 있고, 이 선택이 애플리케이션 코드에 영향을 주지 않는다는 점이 OTel을 쓰는 가장 실용적인 이유다.

Node.js에서 자동 계측은 모듈 로딩을 가로채 라이브러리 호출을 감싸는 방식으로 동작한다. 따라서 **애플리케이션 코드보다 먼저 초기화되어야 한다.** ESM에서는 `--import` 플래그를 쓴다.

```js
// telemetry.js — 애플리케이션 코드보다 먼저 로드된다
import { NodeSDK } from '@opentelemetry/sdk-node'
import { getNodeAutoInstrumentations } from '@opentelemetry/auto-instrumentations-node'
import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-http'
import { resourceFromAttributes } from '@opentelemetry/resources'
import { ParentBasedSampler, TraceIdRatioBasedSampler } from '@opentelemetry/sdk-trace-base'

const sdk = new NodeSDK({
  resource: resourceFromAttributes({
    'service.name': process.env.SERVICE_NAME,
    'service.version': process.env.SERVICE_VERSION,
    'deployment.environment': process.env.APP_ENV
  }),
  traceExporter: new OTLPTraceExporter({
    url: `${process.env.OTEL_EXPORTER_OTLP_ENDPOINT}/v1/traces`
  }),
  // 부모가 샘플됐으면 따라간다. 루트에서만 비율로 판단한다
  sampler: new ParentBasedSampler({
    root: new TraceIdRatioBasedSampler(Number(process.env.TRACE_SAMPLE_RATIO ?? 0.1))
  }),
  instrumentations: [
    getNodeAutoInstrumentations({
      // 헬스 체크는 트레이스에서 제외한다. 볼륨의 대부분을 차지하면서 정보가 없다
      '@opentelemetry/instrumentation-http': {
        ignoreIncomingRequestHook: (req) => /^\/(healthz|readyz|metrics)/.test(req.url ?? '')
      },
      // 파일 시스템 계측은 스팬을 폭발적으로 만든다. 기본 비활성 유지
      '@opentelemetry/instrumentation-fs': { enabled: false }
    })
  ]
})

sdk.start()

process.on('SIGTERM', () => {
  // 종료 전에 버퍼에 남은 스팬을 반드시 내보낸다
  sdk.shutdown().finally(() => process.exit(0))
})
```

```bash
# 실행. 애플리케이션 진입점보다 먼저 telemetry.js가 평가된다
node --import ./telemetry.js ./src/server.js
```

자동 계측만으로 HTTP 서버·클라이언트, 주요 데이터베이스 드라이버, Redis, gRPC, 메시지 브로커의 스팬이 생성되고 부모-자식 관계가 이어진다. 여기까지가 투자 대비 효과가 가장 큰 구간이다.

### 수동 스팬으로 의미를 채우기

자동 계측은 "무엇을 호출했는가"를 보여주지만 "왜"는 모른다. 비즈니스적으로 의미 있는 구간과 도메인 속성은 직접 추가한다.

```js
import { trace, SpanStatusCode } from '@opentelemetry/api'

const tracer = trace.getTracer('orders-api')

export async function placeOrder(userId, items) {
  return tracer.startActiveSpan('order.place', async (span) => {
    try {
      // 카디널리티 걱정 없이 속성을 붙일 수 있다. 메트릭 라벨과 달리
      // 스팬 속성은 시계열을 만들지 않는다
      span.setAttribute('order.item_count', items.length)
      span.setAttribute('user.tier', await getUserTier(userId))

      const reserved = await reserveInventory(items)   // 자식 스팬이 자동 생성된다
      span.addEvent('inventory.reserved', { count: reserved.length })

      const payment = await chargePayment(userId, items)
      span.setAttribute('payment.provider', payment.provider)

      return await persistOrder(userId, items, payment)
    } catch (err) {
      span.recordException(err)
      span.setStatus({ code: SpanStatusCode.ERROR, message: err.message })
      throw err
    } finally {
      span.end() // end를 빠뜨리면 스팬이 영원히 미완료로 남는다
    }
  })
}
```

`span.end()`를 `finally`에 두는 것은 타협 불가능한 규칙이다. 예외 경로에서 스팬을 닫지 않으면 그 트레이스는 백엔드에서 미완성으로 버려지고, 하필 우리가 가장 보고 싶은 실패 트레이스만 사라진다.

### 큐를 건너는 컨텍스트 전파

HTTP는 자동 계측이 헤더를 알아서 넣고 뺀다. 그러나 메시지 큐, 작업 큐, 이벤트 버스를 지나는 흐름은 대개 직접 처리해야 한다. 이 구간을 놓치면 트레이스가 큐 앞에서 끊기고, "요청이 큐에 들어간 뒤 3분 뒤에 처리된" 사실을 트레이스로 볼 수 없게 된다.

```js
import { context, propagation, trace } from '@opentelemetry/api'

// 생산자: 현재 컨텍스트를 메시지 헤더에 주입한다
export async function enqueue(queue, payload) {
  const carrier = {}
  propagation.inject(context.active(), carrier)   // traceparent 등이 채워진다
  await queue.add({ payload, _otel: carrier })
}

// 소비자: 메시지에서 컨텍스트를 복원한 뒤 그 안에서 스팬을 연다
export async function handleJob(job) {
  const parentCtx = propagation.extract(context.active(), job.data._otel ?? {})
  const span = tracer.startSpan(
    'job.process',
    { attributes: { 'messaging.destination': job.queueName } },
    parentCtx
  )
  return context.with(trace.setSpan(parentCtx, span), async () => {
    try {
      return await doWork(job.data.payload)
    } finally {
      span.end()
    }
  })
}
```

### 샘플링: head와 tail

모든 요청의 모든 스팬을 저장하는 것은 대개 비현실적이다. 트레이스 볼륨은 로그보다 크게 자라기 쉽다. 샘플링 전략은 두 갈래다.

**헤드 샘플링(head sampling)**은 트레이스 시작 시점에 결정한다. 위 코드의 `TraceIdRatioBasedSampler`가 그것이다. 장점은 저렴하다는 것이다. 샘플되지 않은 요청은 스팬을 생성조차 하지 않으므로 런타임 비용이 거의 없다. `ParentBasedSampler`로 감싸면 판정이 트레이스 전체에서 일관되어, 절반만 저장된 반쪽 트레이스가 생기지 않는다. 치명적 단점은 **결정 시점에 그 요청이 흥미로운지 알 수 없다는 것**이다. 1% 샘플링에서 하루 세 번 발생하는 8초짜리 요청은 거의 확실히 버려진다. 그런데 우리가 보고 싶은 것이 정확히 그것이다.

**테일 샘플링(tail sampling)**은 트레이스가 끝난 뒤 결정한다. 애플리케이션은 100% 내보내고, OTel Collector가 트레이스를 일정 시간 메모리에 모아 완성된 모습을 보고 판정한다.

```yaml
# otel-collector.yaml
processors:
  tail_sampling:
    decision_wait: 10s          # 트레이스 완성을 기다리는 시간
    num_traces: 100000          # 메모리에 보관할 트레이스 수
    policies:
      - name: errors
        type: status_code
        status_code: { status_codes: [ERROR] }
      - name: slow
        type: latency
        latency: { threshold_ms: 1000 }
      - name: baseline
        type: probabilistic
        probabilistic: { sampling_percentage: 5 }
```

이 설정은 오류와 1초 초과 트레이스를 전량 보존하고 나머지는 5%만 남긴다. 대가는 Collector의 메모리와 `decision_wait`만큼의 지연, 그리고 한 트레이스의 모든 스팬이 같은 Collector 인스턴스에 도착하도록 트레이스 ID 기반 라우팅을 구성해야 한다는 운영 복잡도다. 실무의 일반적인 절충은 **애플리케이션에서는 헤드 샘플링을 넉넉하게(또는 100%) 하고, Collector에서 테일 샘플링으로 좁히는 2단 구성**이다. 트래픽이 아주 크지 않다면 이 조합이 비용과 정보량의 균형점에 가깝다.

### 트레이스로 실제로 알아내는 것

추상적인 설명보다 실제로 트레이스가 드러내는 패턴을 아는 것이 유용하다.

**N+1 질의.** 주문 상세 요청 하나에 `db.query` 스팬이 200개 늘어서 있고 각각 3ms를 쓴다. 개별 질의는 빠르므로 데이터베이스 메트릭은 아무 이상을 보고하지 않는다. 트레이스의 폭포수 그림에서는 즉시 보인다.

**직렬화된 독립 호출.** 사용자 조회, 배송지 조회, 쿠폰 조회 스팬이 계단처럼 순차 배치되어 있다. 서로 의존하지 않는데 `await`를 연달아 썼기 때문이다. `Promise.all`로 묶으면 세 구간의 합이 최대값으로 줄어든다. 이 패턴은 코드 리뷰에서 놓치기 쉽고 트레이스에서 명백하다.

**재시도 폭풍.** 하나의 하류 호출이 스팬 5개로 반복되고 각각 타임아웃까지 3초를 채운다. 총 15초. 재시도 상한과 백오프가 없거나, 여러 계층에서 각각 재시도하고 있어 곱셈으로 증폭된 경우다(29장 참조).

**미인지 의존성.** 서비스 의존 그래프를 그려보면 아무도 몰랐던 화살표가 나온다. "결제 서비스가 왜 추천 서비스를 부르는가"는 대개 오래전 임시 코드다. 이 그래프는 장애 반경(blast radius)을 판단하는 근거이자, 서비스 분해가 제대로 되어 있는지의 지표이기도 하다(27장 참조).

마지막으로 세 기둥을 서로 연결하면 조사 속도가 크게 달라진다. 로그에 `trace_id`를 넣어(31.2의 `mixin`) 로그에서 트레이스로 점프하고, 히스토그램에 예제(exemplar)를 붙여 "p99 지점을 만든 실제 트레이스"로 대시보드에서 직접 이동한다. 세 기둥을 각각 구축하는 것보다, 셋을 잇는 이 마지막 연결이 실제 조사 시간을 가장 크게 줄인다.

## 31.5 헬스 체크 엔드포인트 설계와 테스트

### liveness와 readiness는 다른 질문이다

헬스 체크를 하나의 `/health`로 통합하는 것은 흔하고, 거의 항상 잘못이다. 오케스트레이터는 두 가지 다른 질문을 하고, 각 답에 대해 완전히 다른 조치를 취하기 때문이다(32장 참조).

- **liveness**: "이 프로세스를 죽이고 다시 띄우면 나아지는가?" 실패 시 조치는 **재시작**이다.
- **readiness**: "지금 이 인스턴스에 트래픽을 보내도 되는가?" 실패 시 조치는 **로드 밸런서 대상에서 제외**다. 프로세스는 살아 있다.
- **startup**: "아직 기동 중인가?" 기동이 느린 애플리케이션에서 liveness가 조급하게 재시작하는 것을 막는다.

두 체크를 합치면 어떤 일이 생기는지 보자. `/health`가 데이터베이스를 검사하고 오케스트레이터가 그것을 liveness로 쓴다면, 데이터베이스가 30초 장애를 겪는 동안 **모든 애플리케이션 파드가 죽고 재시작된다.** 데이터베이스가 돌아왔을 때 애플리케이션은 전부 콜드 스타트 상태이고, 커넥션 풀은 비어 있으며, 캐시도 비어 있다. 30초짜리 데이터베이스 장애가 10분짜리 서비스 장애로 증폭된다.

**따라서 liveness 체크는 외부 의존성을 절대 검사하지 않는다.** 프로세스가 응답할 수 있는지만 본다. 사실상 "HTTP 서버가 요청을 처리하고 있는가"이며, 이벤트 루프가 완전히 막히면 이 엔드포인트도 응답하지 못하므로 그것만으로 충분한 신호가 된다.

```js
// liveness: 의존성 검사 없음. 이벤트 루프가 살아 있으면 200
app.get('/healthz', async (req, reply) => {
  // 이벤트 루프가 심각하게 막혔다면 재시작이 실제로 도움이 된다
  const delayMs = loopDelay.percentile(99) / 1e6
  if (delayMs > config.LIVENESS_LOOP_DELAY_MS) {
    reply.code(503)
    return { status: 'unhealthy', eventLoopDelayP99Ms: delayMs }
  }
  return { status: 'ok' }
})
```

### readiness가 의존성을 검사할 때의 위험

readiness는 의존성을 볼 여지가 있다. 데이터베이스에 연결하지 못하는 인스턴스가 트래픽을 받아봐야 500만 반환하기 때문이다. 그러나 여기에 더 큰 함정이 있다.

**모든 인스턴스가 같은 데이터베이스를 보고 있으므로, 데이터베이스가 느려지면 모든 인스턴스가 동시에 not ready가 된다.** 로드 밸런서는 건강한 대상을 하나도 찾지 못하고 모든 트래픽을 거부한다. 부분적으로만 저하됐을 서비스가 완전 중단이 된다. 게다가 데이터베이스가 회복되면 모든 인스턴스가 동시에 ready로 돌아오며 커넥션을 한꺼번에 요청해 데이터베이스를 다시 쓰러뜨린다. 이것이 readiness 체크가 만드는 전형적인 연쇄 장애(cascading failure)다.

완화 원칙은 네 가지다.

**필수 의존성과 선택 의존성을 구분한다.** 데이터베이스 없이는 아무 일도 못 하지만, 추천 엔진이나 검색 인덱스가 없어도 핵심 기능은 동작한다면 후자는 readiness에 넣지 않는다. 대신 부분 저하(degraded) 상태를 응답 본문에 담아 대시보드와 알림이 보게 한다.

**체크에 짧은 타임아웃을 건다.** 의존성 검사가 응답 없이 매달리면 readiness 요청 자체가 타임아웃되고, 오케스트레이터는 그것을 실패로 본다. 검사 타임아웃은 프로브 타임아웃보다 훨씬 짧아야 한다.

**결과를 캐시하고 백그라운드에서 갱신한다.** 프로브는 2초마다 인스턴스당 한 번씩 온다. 인스턴스 50개면 데이터베이스는 초당 25번의 헬스 질의를 추가로 받는다. 부하가 높을 때 이 질의가 마지막 한 방이 되는 사고가 실제로 있다. 백그라운드 타이머가 주기적으로 검사하고, 엔드포인트는 캐시된 결과만 즉시 반환하게 한다.

**히스테리시스를 둔다.** 한 번 실패했다고 즉시 not ready로 뒤집지 않고 연속 N회 실패에서 전환하며, 회복은 연속 M회 성공에서 전환한다. 순간적인 흔들림에 트래픽 라우팅이 진동하는 것을 막는다.

```js
// health.js
const CACHE_TTL_MS = 5_000
const CHECK_TIMEOUT_MS = 1_000
const FAIL_THRESHOLD = 3
const RECOVER_THRESHOLD = 2

function withTimeout(promise, ms, label) {
  return Promise.race([
    promise,
    new Promise((_, reject) =>
      setTimeout(() => reject(new Error(`${label} check timed out`)), ms).unref()
    )
  ])
}

class DependencyCheck {
  #failures = 0
  #successes = 0
  #healthy = false          // 기동 시에는 아직 확인되지 않았다
  #lastError = null

  constructor({ name, critical, probe }) {
    Object.assign(this, { name, critical, probe })
  }

  async run() {
    const startedAt = performance.now()
    try {
      await withTimeout(this.probe(), CHECK_TIMEOUT_MS, this.name)
      this.#successes += 1
      this.#failures = 0
      if (this.#successes >= RECOVER_THRESHOLD) this.#healthy = true
      this.#lastError = null
    } catch (err) {
      this.#failures += 1
      this.#successes = 0
      this.#lastError = err.message
      if (this.#failures >= FAIL_THRESHOLD) this.#healthy = false
    }
    return {
      name: this.name,
      healthy: this.#healthy,
      critical: this.critical,
      latencyMs: Math.round(performance.now() - startedAt),
      error: this.#lastError
    }
  }

  get snapshot() {
    return { name: this.name, healthy: this.#healthy, critical: this.critical, error: this.#lastError }
  }
}

export function createHealthMonitor({ db, cache, search }) {
  const checks = [
    new DependencyCheck({ name: 'postgres', critical: true, probe: () => db.query('SELECT 1') }),
    new DependencyCheck({ name: 'redis', critical: true, probe: () => cache.ping() }),
    // 검색이 죽어도 주문은 받는다. 필수가 아니다
    new DependencyCheck({ name: 'search', critical: false, probe: () => search.ping() })
  ]

  let accepting = true // graceful shutdown 시 false로 내린다
  let timer = null

  async function refresh() {
    await Promise.allSettled(checks.map((c) => c.run()))
  }

  return {
    start() {
      timer = setInterval(refresh, CACHE_TTL_MS)
      timer.unref()
      return refresh() // 기동 시 1회는 즉시 수행
    },
    refresh, // 테스트에서 타이머 없이 한 주기를 강제한다
    stop() { clearInterval(timer) },
    beginShutdown() { accepting = false },
    // 프로브는 캐시만 읽는다. I/O 없음, 항상 즉시 응답
    report() {
      const deps = checks.map((c) => c.snapshot)
      const criticalDown = deps.filter((d) => d.critical && !d.healthy)
      const optionalDown = deps.filter((d) => !d.critical && !d.healthy)
      return {
        ready: accepting && criticalDown.length === 0,
        status: criticalDown.length > 0 ? 'unhealthy' : optionalDown.length > 0 ? 'degraded' : 'ok',
        dependencies: deps
      }
    }
  }
}
```

```js
// readiness와 startup 엔드포인트
app.get('/readyz', async (req, reply) => {
  const report = health.report()
  if (!report.ready) reply.code(503)
  return report
})

// startup: 기동 완료 여부만. 마이그레이션·캐시 워밍 등이 끝났는가
app.get('/startupz', async (req, reply) => {
  if (!bootstrapComplete) reply.code(503)
  return { started: bootstrapComplete }
})

// SIGTERM 시 readiness부터 내린다. LB가 대상에서 빼는 데 걸리는 시간을 벌어야
// 진행 중이던 요청이 끊기지 않는다 (32장 참조)
process.on('SIGTERM', async () => {
  health.beginShutdown()                                   // /readyz가 503을 반환하기 시작
  await setTimeout(config.SHUTDOWN_GRACE_MS)               // LB 전파 대기
  await app.close()
  health.stop()
})
```

쿠버네티스 매니페스트에서 프로브 주기와 임계값은 위 설계와 짝을 이뤄야 한다. `failureThreshold × periodSeconds`가 실제 감내 시간이라는 점을 기억한다.

```yaml
livenessProbe:
  httpGet: { path: /healthz, port: 3000 }
  periodSeconds: 10
  timeoutSeconds: 2
  failureThreshold: 3        # 30초간 계속 실패해야 재시작
readinessProbe:
  httpGet: { path: /readyz, port: 3000 }
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 2
startupProbe:
  httpGet: { path: /startupz, port: 3000 }
  periodSeconds: 5
  failureThreshold: 60       # 기동에 최대 5분 허용. 그동안 liveness는 유예된다
```

### 헬스 체크를 테스트한다

헬스 체크는 사고 상황에서만 중요해지는 코드다. 그래서 조용히 망가진 채로 몇 달을 지내다가, 정작 필요한 순간에 항상 200을 반환하는 것으로 밝혀지는 일이 잦다. 명시적으로 테스트해야 한다.

```js
// health.test.js
import { test } from 'node:test'
import assert from 'node:assert/strict'
import { createHealthMonitor } from './health.js'

const ok = () => Promise.resolve()
const fail = () => Promise.reject(new Error('down'))
const hang = () => new Promise(() => {})   // 영원히 응답하지 않는 의존성

test('필수 의존성이 연속 실패하면 not ready가 된다', async () => {
  const health = createHealthMonitor({
    db: { query: fail }, cache: { ping: ok }, search: { ping: ok }
  })
  await health.refresh()
  await health.refresh()
  await health.refresh()   // FAIL_THRESHOLD 도달
  const report = health.report()
  assert.equal(report.ready, false)
  assert.equal(report.status, 'unhealthy')
})

test('선택 의존성 실패는 degraded일 뿐 ready를 유지한다', async () => {
  const health = createHealthMonitor({
    db: { query: ok }, cache: { ping: ok }, search: { ping: fail }
  })
  for (let i = 0; i < 3; i++) await health.refresh()
  const report = health.report()
  assert.equal(report.ready, true)          // 트래픽은 계속 받는다
  assert.equal(report.status, 'degraded')
})

test('응답하지 않는 의존성이 프로브를 매달리게 하지 않는다', async () => {
  const health = createHealthMonitor({
    db: { query: hang }, cache: { ping: ok }, search: { ping: ok }
  })
  const startedAt = performance.now()
  await health.refresh()
  // 타임아웃(1s) 안에 반드시 돌아와야 한다. 프로브 타임아웃(2s)보다 짧다
  assert.ok(performance.now() - startedAt < 1_500)
})

test('shutdown이 시작되면 즉시 not ready가 된다', async () => {
  const health = createHealthMonitor({
    db: { query: ok }, cache: { ping: ok }, search: { ping: ok }
  })
  for (let i = 0; i < 2; i++) await health.refresh()
  assert.equal(health.report().ready, true)
  health.beginShutdown()
  assert.equal(health.report().ready, false)
})
```

여기에 더해 통합 수준에서 두 가지를 확인할 가치가 있다. 첫째, 의존성 컨테이너를 실제로 정지시킨 뒤 `/readyz`가 503이 되고 다시 띄우면 200으로 돌아오는지 확인한다. 둘째, 배포 파이프라인에서 프로브 설정값 자체를 검증한다. `failureThreshold × periodSeconds`가 정상 GC 일시 정지나 기동 시간보다 짧게 설정되어 있으면 아무 문제 없는 파드가 주기적으로 재시작되는 사고가 난다. 이 값은 코드가 아니라 매니페스트에 있으므로 코드 리뷰를 빠져나가기 쉽다.

## 31.6 알림(alerting)과 온콜 설계

### 좋은 알림의 세 조건

알림 시스템의 실패는 두 방향이다. 놓치거나, 너무 많이 울리거나. 실무에서 훨씬 흔하고 훨씬 해로운 쪽은 후자다. 오탐이 반복되면 사람은 알림을 무시하도록 학습하고, 그러면 알림 시스템은 존재하지 않는 것과 같아진다. 좋은 알림은 세 조건을 만족한다.

**증상 기반이다.** 사용자가 겪는 것을 알린다. "5xx 비율이 오류 예산을 빠르게 소진 중"은 증상이고, "CPU 사용률 85%"는 원인 후보다. 원인 기반 알림은 두 방향으로 틀린다. CPU 85%인데 사용자는 아무 불편이 없을 수 있고(오탐), 반대로 CPU가 20%인데도 하류 의존성 타임아웃으로 서비스가 완전히 죽어 있을 수 있다(미탐). 원인 지표는 대시보드에 두고 조사에 쓰되, 사람을 깨우는 것은 증상 지표여야 한다.

**실행 가능하다.** 알림을 받은 사람이 지금 할 수 있는 일이 있어야 한다. 없다면 그것은 알림이 아니라 정보이고, 대시보드나 주간 리포트에 있어야 한다. "디스크가 90일 뒤 가득 찹니다"는 새벽 3시에 페이지할 이유가 없다.

**오탐이 낮다.** 알림 하나하나에 대해 "지난 분기에 몇 번 울렸고, 그중 몇 번이 진짜 조치를 유발했는가"를 답할 수 있어야 한다. 조치율이 낮은 알림은 임계값을 고치거나 삭제한다. 삭제를 두려워하지 않는 것이 중요하다. 아무도 반응하지 않는 알림은 이미 삭제된 것이고, 남아 있으면 다른 알림까지 오염시킨다.

### SLO와 오류 예산 소진율

임계값 알림("오류율 1% 초과")의 문제는 시간 차원이 없다는 것이다. 1.2%가 3분 지속된 것과 8시간 지속된 것은 사용자 영향이 완전히 다른데 같은 알림을 만든다.

서비스 수준 목표(SLO, service level objective)는 이 문제를 예산의 언어로 바꾼다. "30일 동안 요청의 99.9%가 성공하고 300ms 이내에 처리된다"는 목표는 곧 **0.1%의 실패 예산**을 의미한다. 30일 기준으로 약 43분의 완전 중단, 또는 그에 상응하는 부분 저하에 해당한다.

여기서 알릴 대상은 "지금 오류율이 얼마인가"가 아니라 **"이 속도로 가면 예산이 언제 바닥나는가"**, 즉 소진율(burn rate)이다. 소진율 1은 30일 동안 예산을 정확히 다 쓰는 속도다. 소진율 14.4는 남은 예산을 약 2일 만에 태우는 속도다.

실무에서 검증된 구성은 **다중 창(multi-window) 다중 소진율(multi-burn-rate)** 알림이다. 짧은 창은 급격한 사고를 빠르게 잡고, 긴 창은 느리게 새는 문제를 잡으며, 짧은 창을 함께 요구해 이미 끝난 사고가 계속 울리는 것을 막는다.

```yaml
# prometheus-rules.yaml
groups:
  - name: orders-api-slo
    rules:
      # 재사용을 위해 실패 비율을 창 길이별로 미리 계산해둔다
      - record: job:slo_error_ratio:ratio5m
        expr: |
          sum(rate(http_server_request_duration_seconds_count{job="orders-api",status_code=~"5.."}[5m]))
            / sum(rate(http_server_request_duration_seconds_count{job="orders-api"}[5m]))

      # 빠른 소진: 1시간 창 + 5분 창을 함께 요구한다.
      # 0.1% 예산 기준 소진율 14.4 → 임계 0.00144
      - alert: OrdersApiErrorBudgetBurnFast
        expr: |
          job:slo_error_ratio:ratio1h > 0.00144 and job:slo_error_ratio:ratio5m > 0.00144
        for: 2m
        labels: { severity: page, service: orders-api }
        annotations:
          summary: "orders-api 오류 예산이 2일 내 소진되는 속도로 감소 중"
          runbook: "https://runbooks.example.com/orders-api/error-budget-burn"
          dashboard: "https://grafana.example.com/d/orders-api"

      # 느린 소진: 티켓으로만. 사람을 깨우지 않는다
      - alert: OrdersApiErrorBudgetBurnSlow
        expr: |
          job:slo_error_ratio:ratio6h > 0.0006 and job:slo_error_ratio:ratio30m > 0.0006
        for: 15m
        labels: { severity: ticket, service: orders-api }
        annotations:
          summary: "orders-api 오류 예산이 느리게 소진 중"
          runbook: "https://runbooks.example.com/orders-api/error-budget-burn"
```

`severity` 라벨로 전달 경로를 나누는 것이 핵심이다. `page`만 전화를 울리고, `ticket`은 업무 시간에 처리하는 대기열로 간다. 이 구분이 없으면 모든 알림이 결국 같은 채널로 흘러 알림 피로를 만든다.

SLO 기반 알림에는 부수 효과가 있다. 오류 예산이 남아 있으면 팀은 안심하고 배포하고 실험할 수 있고, 예산이 소진되면 기능 개발을 멈추고 안정성 작업으로 전환한다는 규칙을 세울 수 있다. 신뢰성과 개발 속도 사이의 협상이 정치가 아니라 숫자가 된다.

### 알림 피로와 알림 위생

알림 피로(alert fatigue)는 측정 가능한 문제다. 두 가지 숫자를 추적한다. **교대 1회당 페이지 수**와 **업무 시간 외 페이지 수**다. 널리 쓰이는 경험칙은 한 교대(보통 12시간 또는 24시간)당 페이지 2건 이하다. 이 선을 넘으면 대응 품질이 급격히 떨어지고, 온콜이 번아웃되며, 사람들이 온콜 로테이션을 회피하기 시작한다.

정기적인 알림 리뷰가 필요하다. 격주로 지난 기간의 모든 페이지를 훑고 각각에 대해 세 가지를 판정한다. 진짜였는가, 조치가 필요했는가, 자동화할 수 있었는가. 세 번째 질문이 특히 중요하다. "메모리가 차면 재시작한다"는 대응은 알림이 아니라 오케스트레이터가 해야 할 일이다. 사람이 매번 같은 절차를 수행하고 있다면 그것은 알림이 아니라 미구현 자동화다.

억제(inhibition)와 그룹화(grouping)도 위생의 일부다. 데이터베이스가 죽으면 그것에 의존하는 서비스 여덟 개가 동시에 알림을 낸다. 알림 관리자에서 상위 원인 알림이 발화 중일 때 하위 알림을 억제하도록 설정하면, 새벽에 아홉 통이 아니라 한 통이 온다.

### 런북

알림에는 런북(runbook) 링크가 붙어야 한다. 런북은 문서가 아니라 **새벽 3시에 깬 사람이 따라갈 수 있는 절차**다. 다음 다섯 가지가 있으면 충분하다.

1. **이 알림이 의미하는 것.** 한 문장. "결제 API의 5xx 비율이 SLO 소진 속도를 넘었다."
2. **사용자 영향.** "결제가 실패한다. 주문 조회와 배송 추적은 정상."
3. **확인 절차.** 볼 대시보드 링크, 실행할 쿼리, 확인할 최근 배포 목록.
4. **완화 조치.** 순서대로. 롤백 명령, 기능 플래그 끄기, 레이트 리밋 조정, 트래픽 우회. **원인 규명보다 완화가 먼저다.**
5. **에스컬레이션.** 15분 내에 완화되지 않으면 누구를 부르는가.

런북에 넣지 말아야 할 것은 시스템 아키텍처 설명이다. 그것은 평시에 읽는 문서이고, 링크로 연결하면 된다. 런북은 짧을수록 좋다.

### 온콜 로테이션

온콜은 지속 가능해야 한다. 실무에서 작동하는 구성은 다음과 같다.

**로테이션 크기.** 최소 6명, 이상적으로는 8명 이상이 한 로테이션에 있어야 주당 1회 교대가 6~8주에 한 번 돌아온다. 4명 이하 로테이션은 예외 없이 번아웃으로 끝난다. 팀이 작다면 여러 팀을 묶거나, 야간 페이지 대상 알림을 극단적으로 줄이는 쪽을 택한다.

**1차와 2차.** 1차가 응답하지 않으면 자동으로 2차로 넘어간다. 1차가 혼자 판단하지 않아도 되는 장치이기도 하다. "확신이 없으면 2차를 깨워도 된다"는 것을 명시적인 규범으로 만들어야 실제로 그렇게 한다.

**인수인계.** 교대가 바뀔 때 짧은 인수인계를 남긴다. 진행 중인 문제, 알려진 불안정 요소, 예정된 배포, 임시로 억제해둔 알림. 이 기록이 없으면 다음 온콜이 같은 조사를 처음부터 반복한다.

**후속 조치 시간.** 온콜 교대가 끝난 사람에게는 사고 후속 작업을 할 시간이 배정되어야 한다. 사고에서 배운 것이 코드나 알림 설정으로 돌아가지 않으면 같은 사고가 반복되고, 온콜은 영원히 같은 일을 한다.

**비난 없는 사후분석.** 사고 후 사후분석(postmortem)의 목적은 책임자 지목이 아니라 시스템이 그 실수를 허용한 이유를 찾는 것이다. "배포 전에 확인했어야 했다"는 결론은 아무것도 바꾸지 못한다. "확인하지 않으면 배포되지 않게 파이프라인을 바꾼다"가 바꾼다.

**알림 소유권.** 모든 알림에는 소유 팀이 있어야 한다. 소유자 없는 알림은 아무도 고치지 않고, 아무도 삭제하지 않으며, 영원히 울린다. 알림 규칙 파일을 코드로 관리하고(alerting as code) 코드 소유자 규칙을 걸어두면 이 문제가 구조적으로 해결된다.

## 요약

- 관측성의 세 기둥은 서로 다른 질문에 답한다. 로그는 "무슨 일이 있었나", 메트릭은 "얼마나 나쁜가", 트레이스는 "어디서 느린가"다. 셋을 `trace_id`와 예제(exemplar)로 연결할 때 조사 시간이 가장 크게 줄어든다.
- `NODE_ENV`는 `production`과 `development` 두 값만 갖는 런타임 스위치이고, 배포 환경 이름은 `APP_ENV` 같은 별도 변수로 분리한다. 설정은 부팅 시 스키마로 검증하고 실패하면 즉시 종료한다. 모든 신호에는 `service.name`, `service.version`, `deployment.environment`가 붙어야 한다.
- 프로덕션 로그는 사람이 아니라 기계가 읽는다. pino로 JSON을 stdout에만 쓰고, 상관관계 ID는 `AsyncLocalStorage`와 `mixin`으로 자동 전파하며, 민감 정보는 `redact`와 명시적 직렬화기로 이중 차단한다. 볼륨은 메트릭으로 대체하고 성공 요청을 샘플링해 줄인다.
- 메트릭 타입은 나중에 답할 수 있는 질문을 결정한다. 세는 것은 카운터, 상태는 게이지, 분포는 히스토그램이다. 라벨에 고유 식별자를 넣으면 카디널리티 폭발로 메트릭 시스템 전체가 죽는다. 히스토그램 버킷 경계에는 SLO 임계값을 반드시 포함시킨다.
- Node.js 고유 지표(이벤트 루프 지연, GC 일시 정지, 힙, 활성 핸들)는 CPU 사용률이 설명하지 못하는 지연을 설명한다.
- OpenTelemetry로 계측하고 백엔드는 교체 가능하게 둔다. 컨텍스트는 W3C `traceparent`로 전파하되 큐 경계는 직접 inject/extract해야 한다. 헤드 샘플링은 싸지만 희귀한 느린 요청을 놓치므로, Collector의 테일 샘플링과 조합해 오류와 느린 트레이스를 전량 보존한다.
- liveness는 의존성을 검사하지 않는다. readiness는 필수 의존성만 보되 타임아웃·캐시·히스테리시스로 연쇄 장애를 막고, 종료 시 가장 먼저 내려간다. 헬스 체크는 실패 주입 테스트로 검증한다.
- 알림은 증상 기반·실행 가능·낮은 오탐이어야 한다. SLO 오류 예산 소진율을 다중 창으로 알리고, `severity`로 페이지와 티켓을 분리하며, 모든 알림에 런북과 소유 팀을 붙인다.

## 연습문제

1. 요청당 3줄, 줄당 평균 500바이트의 로그를 남기는 서비스가 초당 1,500 요청을 처리한다. 30일 보존 시 원시 로그 볼륨을 계산하라. 이어서 (a) 요청 로그를 히스토그램 메트릭으로 대체하고, (b) 성공 요청을 5%만 샘플링하며, (c) 최근 7일만 핫 스토리지에 두는 세 가지 조치를 각각 적용했을 때의 절감량을 추정하고, 각 조치로 **답할 수 없게 되는 질문**이 무엇인지 하나씩 쓰라.

2. 어떤 팀이 `http_requests_total` 카운터에 `method`(5종), `route`(60종), `status_code`(15종), `user_id`, `client_version`(활성 20종) 라벨을 붙였다. 사용자는 12만 명이다. 최악의 경우 시계열 수를 계산하고, 이 메트릭이 Prometheus에 미칠 영향을 서술하라. 그다음, 원래 답하려던 질문("어떤 사용자가 오류를 겪는가", "특정 클라이언트 버전에서 오류율이 높은가")을 카디널리티를 폭발시키지 않고 답하는 설계를 각각 제시하라.

3. 다음 readiness 체크가 실제 프로덕션에서 일으킬 연쇄 장애 시나리오를 단계별로 서술하고, 31.5에서 다룬 네 가지 완화 원칙을 모두 적용해 다시 작성하라. 그리고 재작성한 구현이 올바른지 검증하는 `node:test` 테스트를 세 개 이상 작성하라.

```js
app.get('/health', async (req, reply) => {
  await db.query('SELECT count(*) FROM orders')
  await redis.ping()
  await fetch('https://payments.vendor.com/api/status')
  await search.cluster.health()
  return { status: 'ok' }
})
```
