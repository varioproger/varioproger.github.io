# 3장. 첫 클러스터 만들기

> **학습목표**
> - 목적(학습·개발·프로덕션)에 맞는 클러스터 설치 방식을 선택할 수 있다.
> - kind로 멀티 노드 클러스터를 만들고 구성 요소를 확인할 수 있다.
> - kubectl의 컨텍스트·출력 포맷·디버깅 명령을 능숙하게 사용한다.
> - YAML 매니페스트의 문법과 작성 규칙을 이해한다.
> - 2장에서 만든 이미지를 클러스터에 배포하고 접속까지 완주한다.

---

## 3.1 학습용 클러스터: Minikube와 kind

클러스터를 만드는 방법은 목적에 따라 셋으로 나뉜다.

| 목적 | 방법 | 특징 |
|---|---|---|
| **학습·개발** | Minikube, kind, k3d | 노트북에서 몇 분 만에. 버리고 다시 만들기 쉬움 |
| **직접 구축** | kubeadm, Kubespray, Talos | 온프레미스. 컨트롤 플레인까지 직접 운영 |
| **매니지드** | GKE, EKS, AKS | 컨트롤 플레인을 클라우드가 운영. 프로덕션 표준 |

이 책의 실습은 **kind**를 기준으로 한다. 이유는 세 가지다.

1. **멀티 노드를 무료로.** Docker 컨테이너를 노드로 쓰기 때문에 3노드, 5노드 클러스터를 노트북에서 만들 수 있다. 스케줄링·어피니티·DaemonSet 실습에 필수적이다.
2. **빠르다.** 생성 1~2분, 삭제 몇 초. 실습을 망쳐도 부담 없이 다시 만든다.
3. **CI에서도 같은 환경.** 쿠버네티스 프로젝트 자체가 테스트에 kind를 쓴다.

### Minikube

가장 널리 알려진 로컬 도구다. VM 또는 컨테이너를 노드로 쓴다.

```bash
# 설치 (Linux x86_64)
curl -LO https://storage.googleapis.com/minikube/releases/latest/minikube-linux-amd64
sudo install minikube-linux-amd64 /usr/local/bin/minikube

# 클러스터 시작
minikube start --nodes=2 --cpus=2 --memory=4g

# 상태 확인
minikube status
kubectl get nodes
```

Minikube의 장점은 **애드온 생태계**다.

```bash
minikube addons list
minikube addons enable ingress            # NGINX Ingress Controller
minikube addons enable metrics-server     # HPA 실습에 필요
minikube dashboard                        # 웹 UI
```

11장의 인그레스 실습이나 16장의 오토스케일링 실습에서 이 애드온들이 편리하다.

### kind (Kubernetes IN Docker)

각 노드가 Docker 컨테이너다. 그 컨테이너 안에서 kubelet과 containerd가 돌아간다.

```bash
# 설치
curl -Lo ./kind https://kind.sigs.k8s.io/dl/latest/kind-linux-amd64
chmod +x ./kind && sudo mv ./kind /usr/local/bin/kind

# 가장 단순한 클러스터 (단일 노드)
kind create cluster --name quick
kind delete cluster --name quick
```

### 도구 설치 확인

실습을 시작하기 전에 필요한 것들을 점검한다.

```bash
docker version        # 2장에서 이미 설치했을 것
kind version
kubectl version --client
```

kubectl이 없다면:

```bash
curl -LO "https://dl.k8s.io/release/$(curl -Ls https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
sudo install -o root -g root -m 0755 kubectl /usr/local/bin/kubectl
```

> **버전 스큐 규칙**
> kubectl은 API 서버와 **마이너 버전 ±1** 이내여야 한다. 서버가 v1.31이면 kubectl은 v1.30~v1.32가 안전하다. 32장에서 클러스터 업그레이드를 다룰 때 이 규칙이 다시 나온다.

## 3.2 실습: kind로 3노드 클러스터 만들기

이제 이 책 전체에서 쓸 실습 클러스터를 만든다.

**① 클러스터 설정 파일 작성**

`kind-cluster.yaml`:
```yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: k8s-guide

nodes:
  # 컨트롤 플레인 노드
  - role: control-plane
    kubeadmConfigPatches:
      - |
        kind: InitConfiguration
        nodeRegistration:
          kubeletExtraArgs:
            node-labels: "ingress-ready=true"
    extraPortMappings:
      # 호스트 8080 → 노드 30080 (NodePort 실습용)
      - containerPort: 30080
        hostPort: 8080
        protocol: TCP
      # 인그레스 실습용 (11장)
      - containerPort: 80
        hostPort: 80
        protocol: TCP

  # 워커 노드 2개
  - role: worker
  - role: worker
```

**② 클러스터 생성**

```bash
kind create cluster --config kind-cluster.yaml
```

출력이 이렇게 진행된다.

```
Creating cluster "k8s-guide" ...
 ✓ Ensuring node image (kindest/node:v1.31.x) 🖼
 ✓ Preparing nodes 📦 📦 📦
 ✓ Writing configuration 📜
 ✓ Starting control-plane 🕹️
 ✓ Installing CNI 🔌
 ✓ Installing StorageClass 💾
 ✓ Joining worker nodes 🚜
Set kubectl context to "kind-k8s-guide"
```

여기서 이미 1~2장의 개념들이 보인다. CNI를 설치하고(23장), StorageClass를 만들고(12장), 워커 노드를 조인시킨다.

**③ 클러스터 확인**

```bash
kubectl get nodes -o wide
```

```

k8s-guide-worker          Ready    <none>          45s   v1.31.0   containerd://1.7.18
k8s-guide-worker2         Ready    <none>          45s   v1.31.0   containerd://1.7.18
```

`CONTAINER-RUNTIME` 열에 containerd가 보인다. 2.5절에서 본 CRI 런타임이다.

**④ 노드가 실제로는 Docker 컨테이너임을 확인**

```bash
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}'
```

```

k8s-guide-worker2         kindest/node:v1.31.0   Up 2 minutes
k8s-guide-worker          kindest/node:v1.31.0   Up 2 minutes
k8s-guide-control-plane   kindest/node:v1.31.0   Up 2 minutes
```

노드 안으로 들어가 볼 수도 있다.

```bash

ps aux | grep -E 'kubelet|containerd'   # 노드 안의 프로세스
crictl ps                                # 이 노드의 컨테이너들
exit
```

**⑤ 컨트롤 플레인 컴포넌트 확인**

1.4절에서 그림으로만 봤던 컴포넌트들이 실제로 어떻게 떠 있는지 본다.

```bash
kubectl get pods -n kube-system
```

```

coredns-7db6d8ff4d-4mfvq                          1/1     Running   3m
coredns-7db6d8ff4d-x2sxb                          1/1     Running   3m

kube-controller-manager-k8s-guide-control-plane   1/1     Running   3m

kube-proxy-pw4kt                                  1/1     Running   3m
kube-scheduler-k8s-guide-control-plane            1/1     Running   3m
```

읽는 법을 익혀 두자.

- **etcd, kube-apiserver, kube-controller-manager, kube-scheduler**: 컨트롤 플레인 노드에 하나씩. 이들은 **static Pod** 로 실행된다. 즉 kubelet이 API 서버 없이 로컬 파일(`/etc/kubernetes/manifests/`)을 읽어 직접 띄운다. API 서버 자체가 API 서버에 의존할 수 없기 때문이다(20장에서 상세히 다룬다).
- **kube-proxy, kindnet**: 노드 수만큼(3개씩). DaemonSet으로 배포되기 때문이다(8.4절).
- **coredns**: 2개. Deployment로 배포되며 DNS를 제공한다(10장).

**⑥ 로컬 레지스트리를 클러스터에 연결**

2장에서 만든 이미지를 이 클러스터에서 쓸 수 있게 한다. kind는 노드가 별도 Docker 네트워크에 있으므로 연결 작업이 필요하다.

```bash
# 레지스트리 컨테이너를 kind 네트워크에 연결
docker network connect kind registry 2>/dev/null || true

# 각 노드에 레지스트리를 신뢰하도록 설정
for node in $(kind get nodes --name k8s-guide); do
  docker exec "$node" mkdir -p /etc/containerd/certs.d/localhost:5000
  cat <<EOF | docker exec -i "$node" tee /etc/containerd/certs.d/localhost:5000/hosts.toml >/dev/null
[host."http://registry:5000"]
EOF
done
```

> **더 간단한 방법**
> 이 설정이 번거롭다면 kind가 제공하는 이미지 직접 적재 기능을 써도 된다.
> ```bash
> kind load docker-image hello:1.0 --name k8s-guide
> ```
> 실습 규모에서는 이쪽이 훨씬 편하다. 다만 이미지를 바꿀 때마다 다시 적재해야 한다.

## 3.3 매니지드 쿠버네티스 개요와 선택 기준

프로덕션에서는 대부분 매니지드 서비스를 쓴다. 여기서는 개요만 잡고, 실제 구축은 29장에서 다룬다.

### 매니지드가 대신해 주는 것

```
┌─────────────────────────────────────────┐
│  컨트롤 플레인                            │  ← 클라우드가 운영
│  (apiserver, etcd, scheduler, cm)       │     · 고가용성 구성
│                                         │     · 백업
│                                         │     · 보안 패치
├─────────────────────────────────────────┤
│  워커 노드                               │  ← 여전히 내 책임
│  (OS 패치, 노드 스케일링, 문제 노드 교체)   │     (Autopilot/Fargate는 예외)
├─────────────────────────────────────────┤
│  워크로드, 네트워크 정책, RBAC, 리소스 튜닝 │  ← 전적으로 내 책임
└─────────────────────────────────────────┘
```

**"매니지드를 쓰면 쿠버네티스를 몰라도 된다"는 오해가 흔하다.** 매니지드는 컨트롤 플레인 운영 부담만 덜어 줄 뿐, 이 책의 4부(운영)와 5부(내부)에서 다룰 내용은 여전히 필요하다.

### 세 서비스 빠른 비교

| | **GKE** (Google) | **EKS** (AWS) | **AKS** (Azure) |
|---|---|---|---|
| 컨트롤 플레인 비용 | 클러스터당 과금 (무료 티어 있음) | 클러스터당 시간 과금 | 무료 (SLA 필요 시 유료) |
| 노드 완전 위임 | Autopilot | Fargate | (Virtual Nodes) |
| ID 연동 | Workload Identity | IRSA / Pod Identity | Entra ID + Workload Identity |
| 기본 CNI | GKE Dataplane V2 (Cilium) | VPC CNI | Azure CNI / kubenet |
| 업그레이드 | 릴리스 채널 자동 | 수동 트리거 중심 | 자동 채널 지원 |
| 강점 | 가장 성숙, 자동화 수준 높음 | AWS 서비스 통합 폭 | 마이크로소프트 스택 통합 |

### 선택 기준

실무에서 선택은 대개 기술이 아니라 맥락으로 결정된다.

1. **이미 쓰는 클라우드가 있다면 그것을 쓴다.** 네트워크 지연, VPC 연동, IAM, 청구 통합의 이점이 다른 모든 차이를 압도한다.
2. **팀 규모가 작다면 자동화 수준이 높은 쪽.** GKE Autopilot이나 EKS Fargate는 노드 관리 부담을 없앤다.
3. **규제·데이터 주권 요구가 있다면 리전과 인증서를 먼저 확인한다.**
4. **온프레미스가 필수라면** kubeadm이나 Talos, 또는 상용 배포판(OpenShift, Rancher).

## 3.4 kubectl 기본기

kubectl은 API 서버와 대화하는 클라이언트다. 이 절의 명령들은 앞으로 계속 쓰게 되므로 손에 익혀 두자.

### kubeconfig와 컨텍스트

kubectl은 `~/.kube/config` 파일에서 접속 정보를 읽는다.

```yaml
apiVersion: v1
kind: Config
clusters:                      # 어떤 클러스터들이 있는가
  - name: kind-k8s-guide
    cluster:
      server: https://127.0.0.1:6443
      certificate-authority-data: LS0tLS1CRUdJTi...
users:                         # 어떤 자격 증명이 있는가
  - name: kind-k8s-guide
    user:
      client-certificate-data: LS0tLS1CRUdJTi...
      client-key-data: LS0tLS1CRUdJTi...
contexts:                      # 클러스터 + 사용자 + 네임스페이스 조합
  - name: kind-k8s-guide
    context:
      cluster: kind-k8s-guide
      user: kind-k8s-guide
      namespace: default
current-context: kind-k8s-guide
```

컨텍스트는 **(클러스터, 사용자, 기본 네임스페이스)** 의 조합이다.

```bash
kubectl config get-contexts               # 목록
kubectl config current-context            # 현재
kubectl config use-context kind-k8s-guide # 전환
kubectl config set-context --current --namespace=dev   # 기본 네임스페이스 변경
```

> **⚠️ 실무에서 가장 흔한 사고**
> 프로덕션 컨텍스트인 줄 모르고 명령을 실행하는 것이다. 프롬프트에 현재 컨텍스트를 표시하는 도구(`kube-ps1`)나 컨텍스트 전환 도구(`kubectx`, `kubens`)를 반드시 설치하길 권한다.
> ```bash
> kubectl krew install ctx ns    # krew 플러그인 매니저 사용 시
> ```

### 필수 명령 패턴

**조회**
```bash
kubectl get pods                          # 현재 네임스페이스
kubectl get pods -A                       # 모든 네임스페이스
kubectl get pods -o wide                  # 노드·IP까지
kubectl get pods -w                       # 변화를 실시간 추적
kubectl get pods --show-labels            # 라벨 표시
kubectl get pods -l app=web               # 라벨 셀렉터
kubectl get pods --sort-by=.metadata.creationTimestamp
```

**상세 정보와 디버깅**
```bash
kubectl describe pod <name>               # 이벤트 포함 상세 (문제 해결의 1순위)
kubectl logs <pod>                        # 로그
kubectl logs <pod> -c <container>         # 멀티 컨테이너 중 하나
kubectl logs <pod> --previous             # 재시작 전 로그 (크래시 원인 추적)
kubectl logs -f <pod>                     # 실시간
kubectl logs -l app=web --tail=50         # 라벨로 여러 Pod 동시에
kubectl exec -it <pod> -- sh              # 컨테이너 안으로
kubectl get events --sort-by=.lastTimestamp   # 클러스터 이벤트
```

**출력 포맷**
```bash
kubectl get pod <name> -o yaml            # 전체 오브젝트
kubectl get pod <name> -o json
kubectl get pods -o jsonpath='{.items[*].metadata.name}'
kubectl get pods -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.podIP}{"\n"}{end}'
kubectl get pods -o custom-columns=NAME:.metadata.name,NODE:.spec.nodeName
```

**API 탐색 — 문서 없이 필드 찾기**
```bash
kubectl api-resources                     # 사용 가능한 모든 리소스 종류
kubectl api-versions                      # API 그룹/버전 목록
kubectl explain pod.spec.containers       # 필드 설명
kubectl explain pod.spec.containers.resources --recursive
```

`kubectl explain`은 매우 유용하다. 웹 문서를 찾기 전에 이것부터 써 보는 습관을 들이자.

**적용과 삭제**
```bash
kubectl apply -f manifest.yaml            # 선언적 적용 (권장)
kubectl apply -f ./manifests/             # 디렉터리 전체
kubectl apply -f manifest.yaml --dry-run=server   # 실제 적용 없이 검증
kubectl diff -f manifest.yaml             # 현재 상태와의 차이 확인
kubectl delete -f manifest.yaml
```

> **`apply` vs `create`**
> `create`는 새로 만들기만 한다. 이미 있으면 에러다.
> `apply`는 없으면 만들고, 있으면 차이만 반영한다. 1장에서 본 **선언적 접근**에 부합하므로 실무에서는 `apply`를 쓴다.

**임시 디버깅 Pod**
```bash
kubectl run tmp --rm -it --image=nicolaka/netshoot -- bash
```
`netshoot`에는 `dig`, `curl`, `tcpdump`, `nmap` 등 네트워크 도구가 모두 들어 있다. 10장과 23장의 네트워크 트러블슈팅에서 계속 쓴다.

### 편의 설정

```bash
# 자동완성 (bash)
echo 'source <(kubectl completion bash)' >> ~/.bashrc
echo 'alias k=kubectl' >> ~/.bashrc
echo 'complete -o default -F __start_kubectl k' >> ~/.bashrc
source ~/.bashrc

# zsh
echo 'source <(kubectl completion zsh)' >> ~/.zshrc
```

krew(플러그인 매니저)도 설치해 두면 좋다.

```bash
# 설치 후 유용한 플러그인들
kubectl krew install ctx ns tree neat stern
```

- `ctx`/`ns`: 컨텍스트·네임스페이스 빠른 전환
- `tree`: 오브젝트 소유 관계를 트리로 (Deployment → ReplicaSet → Pod)
- `neat`: 서버가 추가한 필드를 걷어낸 깨끗한 YAML 출력
- `stern`: 여러 Pod 로그를 색상으로 구분해 동시 스트리밍

## 3.5 YAML 문법과 매니페스트 작성 규칙

쿠버네티스 매니페스트는 YAML로 쓴다. 문법 자체는 단순하지만 실수하기 쉬운 지점들이 있다.

### 기본 구조

모든 쿠버네티스 오브젝트는 네 개의 최상위 필드를 갖는다.

```yaml
apiVersion: apps/v1        # ① 어떤 API 그룹/버전인가
kind: Deployment           # ② 어떤 종류인가
metadata:                  # ③ 이름·라벨 등 식별 정보
  name: web
  namespace: default
  labels:
    app: web
spec:                      # ④ 원하는 상태 (kind마다 구조가 다름)
  replicas: 3
  ...
```

여기에 **`status`** 가 더해지지만, 이것은 시스템이 채우는 필드이므로 사람이 쓰지 않는다. 1장에서 본 조정 루프가 `spec`(원하는 상태)과 `status`(현재 상태)를 비교하는 것이다.

`apiVersion`은 두 형태가 있다.

- `v1` — 코어 그룹 (Pod, Service, ConfigMap, Secret, Namespace 등)
- `<그룹>/<버전>` — 그 외 (`apps/v1`, `batch/v1`, `networking.k8s.io/v1` 등)

어떤 것을 써야 할지 모를 때:
```bash
kubectl api-resources | grep -i deployment
# deployments  deploy  apps/v1  true  Deployment
```

### 자주 하는 실수 다섯 가지

**① 탭 문자 사용**
YAML은 탭을 허용하지 않는다. 반드시 스페이스를 쓴다. 에디터에서 탭을 스페이스로 변환하도록 설정해 두자.

**② 불리언처럼 보이는 문자열**
```yaml
# ❌ 위험
data:
  enabled: yes        # YAML 1.1에서 true로 해석될 수 있다
  country: NO         # 노르웨이가 아니라 false
  version: 1.10       # 문자열이 아니라 숫자 1.1

# ✅ 안전
data:
  enabled: "yes"
  country: "NO"
  version: "1.10"
```
ConfigMap의 `data` 필드는 모든 값이 문자열이어야 하므로 특히 주의한다.

**③ 리스트 들여쓰기 혼동**
```yaml
# 둘 다 유효하다 (헷갈리기 쉬움)
containers:
- name: web        # 하이픈이 부모와 같은 열
  image: nginx

containers:
  - name: web      # 들여쓴 형태
    image: nginx
```
어느 쪽이든 팀 내에서 하나로 통일한다.

**④ 여러 문서를 한 파일에**
```yaml
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  ...
---              # 문서 구분자
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  ...
```
`---`로 여러 오브젝트를 한 파일에 담을 수 있다. 관련된 오브젝트를 묶어 두면 관리가 쉽다.

**⑤ 멀티라인 문자열**
```yaml
data:
  config.yaml: |          # | 는 개행을 보존
    server:
      port: 8080
  message: >              # > 는 개행을 공백으로 접음
    이 문장은
    한 줄로 합쳐진다
```
설정 파일을 ConfigMap에 담을 때는 거의 항상 `|`를 쓴다(7장).

### 매니페스트 작성 워크플로

처음부터 YAML을 손으로 다 쓸 필요는 없다. 실무에서 쓰는 요령이 있다.

```bash
# ① 명령형으로 뼈대 생성
kubectl create deployment web --image=hello:1.0 \
  --dry-run=client -o yaml > deployment.yaml

# ② 파일을 열어 필요한 필드 추가·수정

# ③ 서버 측 검증 (실제 적용 없이)
kubectl apply -f deployment.yaml --dry-run=server

# ④ 기존 상태와의 차이 확인
kubectl diff -f deployment.yaml

# ⑤ 적용
kubectl apply -f deployment.yaml
```

`--dry-run=client -o yaml`은 매우 자주 쓰는 패턴이다. Service, ConfigMap, Job 등 대부분의 리소스에 쓸 수 있다.

```bash
kubectl create service clusterip web --tcp=80:8080 --dry-run=client -o yaml
kubectl create configmap app-config --from-literal=KEY=value --dry-run=client -o yaml
kubectl create job backup --image=busybox --dry-run=client -o yaml -- /bin/sh -c 'echo hi'
```

### 검증 도구

```bash
# 스키마 검증
kubectl apply --dry-run=server -f manifest.yaml

# 정적 분석 (별도 설치)
kubeconform -summary manifest.yaml      # 스키마 검증
kube-linter lint manifest.yaml          # 모범 사례 위반 탐지
```

30장의 CI 파이프라인에서 이 검증들을 자동화한다.

## 3.6 실습: 첫 애플리케이션 배포와 접속

2장에서 만든 `hello` 이미지를 클러스터에 배포한다.

**① 이미지를 클러스터에 적재**

```bash
kind load docker-image hello:1.0 --name k8s-guide
```

**② 매니페스트 작성**

`hello-app.yaml`:
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello
  labels:
    app: hello
spec:
  replicas: 3
  selector:
    matchLabels:
      app: hello
  template:
    metadata:
      labels:
        app: hello
    spec:
      containers:
        - name: hello
          image: hello:1.0
          imagePullPolicy: IfNotPresent   # kind에 적재한 로컬 이미지 사용
          ports:
            - containerPort: 8080
              name: http
          env:
            - name: APP_VERSION
              value: "1.0"
          readinessProbe:                  # 6장에서 자세히
            httpGet:
              path: /healthz
              port: 8080
            initialDelaySeconds: 2
          resources:                       # 14장에서 자세히
            requests:
              cpu: 50m
              memory: 32Mi
            limits:
              memory: 128Mi
---
apiVersion: v1
kind: Service
metadata:
  name: hello
spec:
  type: NodePort
  selector:
    app: hello                             # 이 라벨을 가진 Pod로 트래픽 전달
  ports:
    - port: 80                             # 서비스 포트
      targetPort: 8080                     # 컨테이너 포트
      nodePort: 30080                      # 노드에 열리는 포트
```

**③ 적용**

```bash
kubectl apply -f hello-app.yaml
```

```
deployment.apps/hello created
service/hello created
```

**④ 배포 상태 관찰**

```bash
kubectl get pods -w
```

```
NAME                     READY   STATUS              RESTARTS   AGE
hello-6c8b4f9d7c-2xk4p   0/1     ContainerCreating   0          2s
hello-6c8b4f9d7c-8mnvz   0/1     ContainerCreating   0          2s
hello-6c8b4f9d7c-qw7lr   0/1     ContainerCreating   0          2s
hello-6c8b4f9d7c-2xk4p   0/1     Running             0          4s
hello-6c8b4f9d7c-2xk4p   1/1     Running             0          6s   ← readiness 통과
...
```

`0/1 Running`에서 `1/1 Running`으로 바뀌는 순간이 readiness 프로브가 통과한 시점이다. 6장에서 이 차이를 자세히 다룬다.

**⑤ 어느 노드에 배치됐는지 확인**

```bash
kubectl get pods -o wide
```

```
NAME                     READY   STATUS    IP           NODE
hello-6c8b4f9d7c-2xk4p   1/1     Running   10.244.1.3   k8s-guide-worker
hello-6c8b4f9d7c-8mnvz   1/1     Running   10.244.2.4   k8s-guide-worker2

```bash

# Taints: node-role.kubernetes.io/control-plane:NoSchedule
```

**⑥ 접속 확인 — 세 가지 방법**

*방법 1: NodePort (설정 파일에서 8080 → 30080 매핑을 해 뒀다)*
```bash
for i in $(seq 1 6); do curl -s localhost:8080; done
```
```
hello from hello-6c8b4f9d7c-2xk4p (v1.0)
hello from hello-6c8b4f9d7c-8mnvz (v1.0)
hello from hello-6c8b4f9d7c-qw7lr (v1.0)

```
**호스트명이 바뀌는 것이 로드밸런싱이 동작하는 증거다.** 이것이 9장에서 배울 Service의 실체다.

*방법 2: port-forward (개발 중 가장 자주 쓴다)*
```bash
kubectl port-forward svc/hello 9090:80
# 다른 터미널에서
curl localhost:9090
```

*방법 3: 클러스터 내부에서*
```bash
kubectl run tmp --rm -it --image=nicolaka/netshoot -- \
  curl -s http://hello.default.svc.cluster.local
```
`hello.default.svc.cluster.local`이라는 DNS 이름으로 접근했다. 10장에서 이 이름이 어떻게 해석되는지 다룬다.

**⑦ 오브젝트 관계 확인**

**Deployment → ReplicaSet → Pod** 의 3단 구조가 보인다. Deployment를 만들었을 뿐인데 ReplicaSet이 자동으로 생겼다. 이 소유 관계는 `krew tree` 플러그인으로 더 명확히 볼 수 있다.

```bash

```

**⑧ 조정 루프 체험하기**

1장에서 개념으로 배운 조정 루프를 눈으로 확인해 보자.

**과제 1 — 5노드 클러스터와 노드 라벨**

kubectl label node <node> disktype=ssd

15장에서 이 라벨로 스케줄링을 제어한다.

**과제 2 — 매니페스트를 처음부터 만들어 보기**
`kubectl create ... --dry-run=client -o yaml`로 뼈대를 만든 뒤, `hello:2.0` 이미지를 쓰는 Deployment와 ClusterIP Service를 작성한다. 2장의 `app.py`에서 `APP_VERSION` 환경변수를 `2.0`으로 바꿔 새 이미지를 빌드하고, 두 버전이 동시에 떠 있을 때 응답이 어떻게 섞이는지 관찰한다.

**과제 3 — 진단 명령 익히기**
일부러 잘못된 이미지 이름(`hello:9.9`)으로 Deployment를 만들고, 다음 순서로 원인을 추적한다.
```bash
kubectl get pods                  # STATUS 확인
kubectl describe pod <name>       # Events 섹션 확인
kubectl get events --sort-by=.lastTimestamp
```
`ImagePullBackOff`가 무엇을 의미하는지, `describe`의 어느 줄에서 원인을 찾을 수 있는지 확인한다. 이 순서가 앞으로 모든 문제 해결의 기본 경로다.

**과제 4 — 컨트롤 플레인 들여다보기**
```bash
docker exec -it k8s-guide-control-plane bash
ls /etc/kubernetes/manifests/     # static Pod 매니페스트들
cat /etc/kubernetes/manifests/kube-apiserver.yaml | head -40
```
API 서버가 어떤 플래그로 실행되는지 살펴본다. 17장(인증·인가)과 21장(컨트롤 플레인)에서 이 플래그들의 의미를 다룬다.

## 요약

- 클러스터 생성 방법은 목적에 따라 **학습용(kind/Minikube)**, **직접 구축(kubeadm)**, **매니지드(GKE/EKS/AKS)** 로 나뉜다. 이 책의 실습은 멀티 노드를 무료로 만들 수 있는 kind를 쓴다.
- 컨트롤 플레인 컴포넌트(etcd, apiserver, scheduler, controller-manager)는 **static Pod**로 실행된다. kube-proxy와 CNI는 **DaemonSet**으로 노드마다 하나씩 뜬다.
- kubectl의 핵심은 **컨텍스트 관리**, **`describe`/`logs`/`events`로 이어지는 디버깅 경로**, **`explain`으로 API 탐색**, 그리고 **`apply`를 통한 선언적 적용**이다.
- YAML 매니페스트는 `apiVersion`/`kind`/`metadata`/`spec` 네 필드로 구성된다. `--dry-run=client -o yaml`로 뼈대를 만들고 `--dry-run=server`와 `diff`로 검증하는 워크플로가 실무 표준이다.
- Pod를 삭제해도 자동으로 다시 생기는 것을 확인했다. **Deployment → ReplicaSet → Pod** 의 소유 구조와 조정 루프가 실제로 동작하는 모습이다.

**1부를 마치며** — 여기까지가 쿠버네티스에 발을 들이는 데 필요한 최소한이다. 2부에서는 쿠버네티스 API 오브젝트 모델을 체계적으로 배우고, Pod의 내부 동작과 생명주기, 설정 주입, 그리고 다섯 가지 워크로드 컨트롤러를 차례로 다룬다. 이 클러스터를 그대로 유지한 채 다음 장으로 넘어가자.
