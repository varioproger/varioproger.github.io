# 29장. 매니지드 쿠버네티스 실전

> **학습목표**
> - 매니지드가 대신해 주는 것과 여전히 내 책임인 것을 정확히 구분한다.
> - GKE, EKS, AKS의 노드 관리·ID 연동·네트워킹 차이를 설명할 수 있다.
> - 워크로드 아이덴티티를 각 클라우드에서 구성할 수 있다.
> - Terraform이나 Crossplane으로 클러스터를 코드로 관리할 수 있다.
> - 클라우드 종속을 줄이면서 통합 이점을 취하는 균형을 잡을 수 있다.

---

## 들어가며

3.3절에서 매니지드 서비스의 개요를 봤다. 4~6부를 거친 지금은 그 표를 훨씬 정확히 읽을 수 있다.

이 장은 실제로 프로덕션 클러스터를 구성할 때 내려야 하는 결정들을 다룬다.

## 29.1 책임 경계

### 무엇을 대신해 주는가

```
┌──────────────────────────────────────────────────┐
│  컨트롤 플레인            ← 클라우드가 운영          │
│  · apiserver, etcd, scheduler, controller-manager│
│  · 고가용성 구성 (멀티 AZ)                          │
│  · etcd 백업 (일부는 복원 API도 제공)                │
│  · 보안 패치와 버전 업그레이드 실행                   │
├──────────────────────────────────────────────────┤
│  워커 노드               ← 공유 책임                │
│  · 클라우드: 이미지 제공, 자동 복구 옵션              │
│  · 나: 업그레이드 시점 결정, 노드 크기·수량, 드레인    │
│  · (Autopilot/Fargate는 이것도 위임)                │
├──────────────────────────────────────────────────┤
│  클러스터 설정            ← 전적으로 내 책임          │
│  · RBAC (17장)                                    │
│  · NetworkPolicy (18장)                           │
│  · ResourceQuota, LimitRange (13장)               │
│  · Pod Security Admission (18장)                  │
│  · 애드온 선택과 운영                                │
├──────────────────────────────────────────────────┤
│  워크로드                ← 전적으로 내 책임          │
│  · 매니페스트, 리소스 설정, 프로브                    │
│  · 이미지 보안, 시크릿 관리                          │
│  · 관측성, 백업                                     │
└──────────────────────────────────────────────────┘
```

> **"매니지드를 쓰면 쿠버네티스를 몰라도 된다"는 오해**
>
> 매니지드가 없애 주는 것은 **21장과 22장의 운영 부담**뿐이다. 컨트롤 플레인이 어떻게 동작하는지는 여전히 알아야 진단할 수 있다.
>
> 4부(운영)와 5부(내부)에서 다룬 내용은 매니지드에서도 그대로 필요하다.

### 매니지드에서도 반드시 해야 할 것

```
□ 노드 그룹 설계 (크기, 수량, 스팟 비율)
□ 업그레이드 정책과 실행 (32장)
□ RBAC과 클라우드 IAM 연동 (17장)
□ NetworkPolicy (18장) — CNI가 지원하는지 확인
□ 워크로드 아이덴티티 구성 (17.4절)
□ 로깅·모니터링 (31장)
□ 백업 (12.6절의 Velero — etcd 백업으로는 부족하다)
□ 비용 관리 (13.7절)
```

## 29.2 GKE (Google Kubernetes Engine)

### 두 가지 모드

**Standard** — 노드를 직접 관리한다.

```bash
gcloud container clusters create prod \
  --region asia-northeast3 \
  --num-nodes 2 \
  --machine-type e2-standard-4 \
  --enable-autoscaling --min-nodes 2 --max-nodes 10 \
  --release-channel regular \
  --workload-pool=$PROJECT.svc.id.goog \
  --enable-ip-alias \
  --enable-network-policy \
  --enable-shielded-nodes \
  --logging=SYSTEM,WORKLOAD \
  --monitoring=SYSTEM
```

**Autopilot** — 노드 관리를 전부 위임한다.

```bash
gcloud container clusters create-auto prod-auto --region asia-northeast3
```

| | Standard | Autopilot |
|---|---|---|
| 과금 | **노드 단위** (놀아도 과금) | **Pod의 requests 단위** |
| 노드 관리 | 내가 | 구글이 |
| DaemonSet | 자유 | **제한적** (허용 목록만) |
| 특권 컨테이너 | 가능 | **불가** |
| hostPath | 가능 | **불가** (일부 예외) |
| 노드 SSH | 가능 | 불가 |
| 최소 리소스 | 제약 없음 | **자동 상향 조정** (0.25 vCPU 등) |

> **Autopilot의 제약이 실무에서 문제가 되는 경우**
> - 노드 수준 에이전트(보안, 모니터링)가 hostPath나 특권을 요구할 때
> - 20장에서 배운 `crictl`로 노드를 진단할 수 없다
> - 리소스가 자동 상향되어 예상보다 비용이 높아질 수 있다
>
> **작은 팀이 표준적인 워크로드만 돌린다면 Autopilot이 매우 편하다.** 특수 요구가 있으면 Standard를 쓴다.

```bash

# GPU 노드 풀
gcloud container node-pools create gpu \
  --cluster prod --region asia-northeast3 \
  --machine-type n1-standard-8 \
  --accelerator type=nvidia-tesla-t4,count=1 \
  --node-taints=nvidia.com/gpu=present:NoSchedule
```

**15.4절에서 배운 테인트 + 어피니티 패턴**이 여기서 쓰인다.

```yaml
# 스팟 노드를 쓰는 배치 워크로드
spec:
  tolerations:
    - key: cloud.google.com/gke-spot
      operator: Equal
      value: "true"
      effect: NoSchedule
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: workload
                operator: In
                values: [batch]
```

17.4절에서 본 원리의 GKE 구현이다.

```bash

### 릴리스 채널

32장의 업그레이드와 직결된다.

| 채널 | 특징 |
|---|---|
| `rapid` | 최신. 새 기능을 빨리 받지만 검증 기간이 짧다 |

gcloud container clusters update prod \

```

### GKE 특유의 기능

- **Dataplane V2**: Cilium 기반 eBPF(23.3절). NetworkPolicy와 관측성이 강하다
- **GKE Gateway**: Gateway API 네이티브 지원(11.5절)
- **Backup for GKE**: 관리형 백업 서비스
- **Config Sync**: 구글판 GitOps (30.4절의 대안)
- **Binary Authorization**: 이미지 서명 검증(18.5절)

## 29.3 EKS (Amazon Elastic Kubernetes Service)

### 세 가지 컴퓨트 옵션

```bash
# ① 관리형 노드 그룹 (권장)
eksctl create nodegroup \
  --cluster prod --region ap-northeast-2 \
  --name general \
  --node-type m6i.xlarge \
  --nodes 3 --nodes-min 2 --nodes-max 20 \
  --managed

# ② Fargate — 서버리스
eksctl create fargateprofile \
  --cluster prod \
  --name serverless \
  --namespace batch

# ③ Karpenter (16.5절) — 노드 그룹 없이 동적 프로비저닝
```

| | 관리형 노드 그룹 | Fargate | Karpenter |
|---|---|---|---|
| 노드 관리 | AWS가 AMI 제공, 내가 스케일 | 없음 | Karpenter가 |
| DaemonSet | ✅ | **❌ 불가** | ✅ |
| 과금 | 인스턴스 | Pod requests | 인스턴스 |
| 인스턴스 타입 | 그룹에 고정 | 자동 | **Pod에 맞춰 동적** |
| 스팟 | 별도 그룹 | ❌ | **자동 폴백** |

> **⚠️ Fargate에서는 DaemonSet이 동작하지 않는다**
> 로그 수집기(8.4절), 모니터링 에이전트, 서비스 메시 사이드카가 DaemonSet이라면 Fargate에 배포할 수 없다. 로그는 Fargate 로그 라우터로 별도 구성해야 한다.

**Karpenter가 EKS에서 사실상 표준이 되고 있다**(16.5절).

```yaml
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: default
spec:
  template:
    spec:
      requirements:
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["spot", "on-demand"]
        - key: karpenter.k8s.aws/instance-category
          operator: In
          values: ["c", "m", "r"]
        - key: karpenter.k8s.aws/instance-generation
          operator: Gt
          values: ["5"]
      nodeClassRef:
        group: karpenter.k8s.aws
        kind: EC2NodeClass
        name: default
      expireAfter: 720h
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    consolidateAfter: 1m
  limits:
    cpu: "1000"
```

### VPC CNI와 IP 관리

23.2절에서 본 "네이티브 IP" 방식이다. **Pod가 VPC의 실제 IP를 받는다.**

**장점**: VPC 보안 그룹과 플로우 로그를 Pod에 직접 적용할 수 있다.
**단점**: IP 고갈이 심각한 제약이 된다.

```
노드당 최대 Pod = (ENI 수 × ENI당 IP 수) - 1

m5.large:   3 × 10 - 1 = 29
m5.xlarge:  4 × 15 - 1 = 59
m5.4xlarge: 8 × 30 - 1 = 234
```

**접두사 위임으로 크게 늘릴 수 있다.**

```bash
kubectl set env daemonset aws-node -n kube-system ENABLE_PREFIX_DELEGATION=true
kubectl set env daemonset aws-node -n kube-system WARM_PREFIX_TARGET=1
```

`/28` 접두사(16개 IP)를 한 번에 할당해 **m5.large가 110 Pod까지 가능**해진다.

**대안**: 커스텀 네트워킹으로 Pod를 별도 서브넷에 두거나, Cilium 같은 오버레이 CNI로 교체한다.

### IRSA와 Pod Identity

**IRSA** (17.4절)

```bash
eksctl create iamserviceaccount \
  --cluster prod \
  --namespace default \
  --name s3-reader \
  --attach-policy-arn arn:aws:iam::aws:policy/AmazonS3ReadOnlyAccess \
  --approve
```

**EKS Pod Identity** (더 새로운 방식)

```bash
aws eks create-pod-identity-association \
  --cluster-name prod \
  --namespace default \
  --service-account s3-reader \
  --role-arn arn:aws:iam::123456789012:role/S3ReaderRole
```

| | IRSA | Pod Identity |
|---|---|---|
| OIDC 제공자 설정 | 필요 | **불필요** |
| 신뢰 정책 | 클러스터마다 다름 | **재사용 가능** |
| 역할 세션 태그 | 제한적 | 지원 |
| 클러스터 밖 사용 | 가능 | EKS 전용 |

**새 클러스터에는 Pod Identity가 더 간단하다.**

### EKS 특유의 고려사항

- **aws-auth ConfigMap → Access Entries**: 예전에는 ConfigMap으로 IAM ↔ RBAC을 매핑했지만, 실수로 자기 접근을 끊는 사고가 잦았다. **Access Entries API**가 이를 대체한다.
- **애드온 관리**: VPC CNI, CoreDNS, kube-proxy를 EKS 애드온으로 관리하면 버전 호환성이 보장된다.
- **컨트롤 플레인 로깅**: 기본으로 꺼져 있다. **반드시 켜자**(31.6절).

```bash
eksctl utils update-cluster-logging --cluster prod \
  --enable-types api,audit,authenticator,controllerManager,scheduler --approve
```

## 29.4 AKS (Azure Kubernetes Service)

```bash
az aks create \
  --resource-group prod-rg \
  --name prod \
  --location koreacentral \
  --node-count 3 \
  --node-vm-size Standard_D4s_v5 \
  --enable-cluster-autoscaler --min-count 2 --max-count 20 \
  --network-plugin azure --network-plugin-mode overlay \
  --network-policy calico \
  --enable-aad --enable-azure-rbac \
  --enable-oidc-issuer --enable-workload-identity \
  --enable-managed-identity \
  --auto-upgrade-channel stable \
  --zones 1 2 3
```

### 네트워킹 옵션

| 모드 | 특징 |
|---|---|
| `kubenet` | 오버레이. IP 절약. 레거시 |
| `azure` (CNI) | Pod가 VNet IP. IP 소모 큼 |
| **`azure` + `--network-plugin-mode overlay`** | Pod는 오버레이, 노드는 VNet. **권장** |
| Cilium (Azure CNI powered by Cilium) | eBPF 데이터 플레인 |

**overlay 모드가 EKS의 IP 고갈 문제를 피하면서 Azure 통합을 유지한다.**

### Entra ID 통합

```bash
# Entra ID 그룹과 클러스터 관리자 연결
az aks update --resource-group prod-rg --name prod \
  --enable-aad --aad-admin-group-object-ids <GROUP_OBJECT_ID>
```

**Azure RBAC 모드**에서는 쿠버네티스 RBAC 대신 Azure 역할 할당으로 권한을 관리할 수 있다.

```bash
az role assignment create \
  --role "Azure Kubernetes Service RBAC Reader" \
  --assignee alice@example.com \
  --scope "$(az aks show -g prod-rg -n prod --query id -o tsv)/namespaces/dev"
```

**17.2절의 OIDC 인증**이 이 방식으로 구현된다.

### Workload Identity

```bash
# ① OIDC 발급자 URL 확인
export OIDC_URL=$(az aks show -g prod-rg -n prod --query oidcIssuerProfile.issuerUrl -o tsv)

# ② 관리 ID 생성
az identity create -g prod-rg -n kv-reader
export CLIENT_ID=$(az identity show -g prod-rg -n kv-reader --query clientId -o tsv)

# ③ 페더레이션 자격증명
az identity federated-credential create \
  --name kv-reader-fc \
  --identity-name kv-reader \
  --resource-group prod-rg \
  --issuer $OIDC_URL \
  --subject system:serviceaccount:default:kv-reader
```

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: kv-reader
  annotations:
    azure.workload.identity/client-id: <CLIENT_ID>
---
apiVersion: apps/v1
kind: Deployment
spec:
  template:
    metadata:
      labels:
        azure.workload.identity/use: "true"    # ★ 이 라벨이 필수
```

### 노드 풀

```bash
# 시스템 노드 풀 (필수, CoreDNS 등이 여기)
az aks nodepool add -g prod-rg --cluster-name prod \
  --name system --mode System --node-count 3

# 사용자 노드 풀
az aks nodepool add -g prod-rg --cluster-name prod \
  --name user --mode User \
  --node-vm-size Standard_D8s_v5 \
  --enable-cluster-autoscaler --min-count 0 --max-count 30

# 스팟 노드 풀
az aks nodepool add -g prod-rg --cluster-name prod \
  --name spot --priority Spot --eviction-policy Delete \
  --spot-max-price -1 \
  --node-taints kubernetes.azure.com/scalesetpriority=spot:NoSchedule
```

**System 노드 풀이 별도로 있다는 것**이 AKS의 특징이다. 시스템 Pod가 사용자 워크로드와 자원을 다투지 않는다.

## 29.5 세 서비스 비교

| 항목 | **GKE** | **EKS** | **AKS** |
|---|---|---|---|
| 컨트롤 플레인 요금 | 클러스터당 시간 과금 (무료 티어 1개) | 클러스터당 시간 과금 | **무료** (SLA 필요 시 유료) |
| 노드 완전 위임 | **Autopilot** | Fargate | (Virtual Nodes) |
| 기본 CNI | Dataplane V2 (Cilium) | VPC CNI | Azure CNI Overlay |
| NetworkPolicy | ✅ 기본 | ✅ (v1.14+) | ✅ (Calico/Cilium) |
| 워크로드 아이덴티티 | Workload Identity | IRSA / Pod Identity | Workload Identity |
| 자동 업그레이드 | **릴리스 채널** | 수동 트리거 중심 | 자동 채널 |
| 노드 오토스케일 | CA (Karpenter 지원 추가) | **Karpenter** | CA / NAP |
| 성숙도 | 가장 성숙 | 생태계 최대 | MS 스택 통합 |
| 관리형 백업 | Backup for GKE | (Velero 직접) | Azure Backup |

### 선택은 대개 기술이 아니다

**이미 쓰는 클라우드가 있다면 그것을 쓴다.** 이유:

- 네트워크 지연 (같은 VPC 안의 DB, 캐시)
- IAM 통합 (17.4절의 워크로드 아이덴티티)
- 청구 통합
- 팀의 기존 지식

**멀티 클라우드는 이식성이 아니라 비용과 복잡도를 만든다.** 정말 필요한 요구(규제, 벤더 리스크 분산)가 있을 때만 선택한다.

## 29.6 이식성 확보 전략

클라우드를 완전히 벗어날 수는 없지만, **종속의 표면적을 줄일 수는 있다.**

### 종속이 생기는 지점

```
┌─────────────────────────────────────────────┐
│  높은 종속 (교체 어려움)                       │
│  · 클라우드 전용 오퍼레이터                     │
│  · 클라우드 네이티브 Ingress (ALB, AGIC)       │
│  · 관리형 서비스 직접 참조 (RDS, Cloud SQL)     │
├─────────────────────────────────────────────┤
│  중간 종속 (애노테이션 수준)                    │
│  · Service의 LoadBalancer 애노테이션           │
│  · StorageClass 파라미터                       │
│  · 워크로드 아이덴티티 애노테이션                 │
├─────────────────────────────────────────────┤
│  낮은 종속 (표준 API)                          │
│  · Deployment, Service, ConfigMap             │
│  · Ingress / Gateway API                      │
│  · PVC (StorageClass 이름만 다름)              │
└─────────────────────────────────────────────┘
```

### 실용적 전략

**① 클라우드별 차이를 오버레이로 격리한다** (30.2절의 Kustomize)

```
base/
  deployment.yaml            # 클라우드 무관
  service.yaml
  ingress.yaml
overlays/
  gke/
    kustomization.yaml
    service-patch.yaml       # GCP LB 애노테이션
    storageclass.yaml        # standard-rwo
  eks/
    kustomization.yaml
    service-patch.yaml       # NLB 애노테이션
    storageclass.yaml        # gp3
```

**② 이식 가능한 컴포넌트를 선택한다**

| 영역 | 이식 가능 | 클라우드 종속 |
|---|---|---|
| 인그레스 | ingress-nginx | ALB Controller, AGIC |
| 인증서 | cert-manager | ACM, Key Vault |
| DNS | external-dns (멀티 제공자) | 클라우드 DNS 직접 |
| 시크릿 | External Secrets Operator | 각 클라우드 SDK |
| 백업 | Velero | Backup for GKE |
| 오토스케일 | Cluster Autoscaler | Karpenter (AWS 중심) |

**③ 애플리케이션은 표준 인터페이스만 쓴다**

```yaml
# ❌ 클라우드 종속
env:
  - name: DB_HOST
    value: "prod-db.abc123.ap-northeast-2.rds.amazonaws.com"

# ✅ 추상화
env:
  - name: DB_HOST
    valueFrom:
      configMapKeyRef: { name: db-config, key: host }
```

**④ 그래도 통합의 이점은 취한다**

> **완전한 이식성을 추구하면 클라우드의 가치를 잃는다.**
>
> 워크로드 아이덴티티(17.4절)는 클라우드마다 다르지만, 정적 키를 없애는 이점이 이식성 손실보다 훨씬 크다. 관리형 데이터베이스도 마찬가지다.
>
> **판단 기준: "이것을 옮기는 데 며칠이 걸리는가?"** 며칠이면 감수할 만하고, 몇 달이면 재고한다.

## 29.7 Infrastructure as Code

### Terraform

```hcl
# eks.tf
module "eks" {
  source  = "terraform-aws-modules/eks/aws"
  version = "~> 20.0"

  cluster_name    = "prod"
  cluster_version = "1.31"

  vpc_id     = module.vpc.vpc_id
  subnet_ids = module.vpc.private_subnets

  cluster_endpoint_public_access = false      # 프라이빗 엔드포인트
  enable_irsa                    = true

  cluster_enabled_log_types = [
    "api", "audit", "authenticator", "controllerManager", "scheduler"
  ]

  eks_managed_node_groups = {
    general = {
      min_size       = 2
      max_size       = 20
      desired_size   = 3
      instance_types = ["m6i.xlarge"]
      capacity_type  = "ON_DEMAND"
      labels = { workload = "general" }
    }
    spot = {
      min_size       = 0
      max_size       = 50
      desired_size   = 0
      instance_types = ["m6i.xlarge", "m6a.xlarge", "m5.xlarge"]
      capacity_type  = "SPOT"
      labels = { workload = "batch" }
      taints = [{
        key    = "spot"
        value  = "true"
        effect = "NO_SCHEDULE"
      }]
    }
  }
}
```

**주의**: Terraform으로 쿠버네티스 리소스까지 관리하려는 유혹이 있다.

```hcl
# ⚠️ 권장하지 않는다
resource "kubernetes_deployment" "app" { ... }
```

**클러스터 인프라는 Terraform, 워크로드는 GitOps로 분리하는 것이 낫다**(30.4절). Terraform의 상태 관리와 쿠버네티스의 조정 루프가 충돌하기 때문이다.

### Crossplane

**쿠버네티스 API로 클라우드 리소스를 관리한다.** 27장에서 본 오퍼레이터 패턴이 인프라에 적용된 것이다.

```yaml
apiVersion: eks.aws.upbound.io/v1beta1
kind: Cluster
metadata:
  name: prod
spec:
  forProvider:
    region: ap-northeast-2
    version: "1.31"
    roleArnSelector:
      matchControllerRef: true
    vpcConfig:
      - subnetIdSelector:
          matchLabels: { type: private }
        endpointPublicAccess: false
  providerConfigRef:
    name: aws-provider
```

**Composition으로 추상화**하면 개발자가 클라우드를 몰라도 된다(27.5절).

```yaml
apiVersion: platform.example.com/v1
kind: PostgresInstance
metadata:
  name: orders-db
spec:
  size: medium
  region: seoul
  # 뒤에서 RDS든 Cloud SQL이든 프로비저닝된다
```

**장점**: GitOps와 자연스럽게 통합된다. 조정 루프가 드리프트를 자동 교정한다.
**단점**: 학습 곡선이 있고, Terraform만큼 성숙하지 않은 영역이 있다.

### 부트스트랩 순서

```
① Terraform / Crossplane
   VPC, 클러스터, 노드 그룹, IAM 역할
        ↓
② 부트스트랩 애드온 (Terraform의 Helm provider 또는 스크립트)
   · Argo CD 또는 Flux         ← GitOps 진입점
        ↓
③ GitOps가 나머지를 배포 (30.4절)
   · cert-manager, external-dns, ingress-nginx
   · Prometheus, Loki
   · 정책 엔진 (Kyverno)
   · 애플리케이션
```

**"부트스트랩만 IaC로, 나머지는 GitOps로"** 가 실무 패턴이다.

## 요약

- 매니지드가 없애 주는 것은 **컨트롤 플레인 운영**(21, 22장)뿐이다. RBAC, NetworkPolicy, 쿼터, PSA, 관측성, 백업은 여전히 내 책임이다.
- **GKE Autopilot**은 노드 관리를 완전히 위임하지만 DaemonSet·특권·hostPath에 제약이 있다. 노드 수준 에이전트가 필요하면 Standard를 쓴다.
- **EKS의 VPC CNI는 Pod가 VPC IP를 받아** IP 고갈이 제약이 된다. **접두사 위임**으로 노드당 Pod 수를 크게 늘릴 수 있다. **Fargate에서는 DaemonSet이 동작하지 않는다.**
- **AKS의 Azure CNI Overlay 모드**가 IP 고갈을 피하면서 Azure 통합을 유지한다. System 노드 풀이 별도로 있어 시스템 Pod가 격리된다.
- 워크로드 아이덴티티는 세 클라우드 모두 **OIDC 신뢰를 통한 토큰 교환**이라는 같은 원리다(17.4절). 구현 세부만 다르다.
- **클라우드 선택은 대개 기술이 아니라 맥락**으로 결정된다. 이미 쓰는 클라우드가 있으면 그것을 쓰는 편이 네트워크·IAM·청구 통합 면에서 압도적으로 유리하다.
- 이식성은 **클라우드별 차이를 Kustomize 오버레이로 격리**하고, **이식 가능한 컴포넌트**(ingress-nginx, cert-manager, external-dns, ESO, Velero)를 선택해 확보한다. 다만 **완전한 이식성을 추구하면 클라우드의 가치를 잃는다.**
- IaC는 **클러스터 인프라만 Terraform/Crossplane으로, 워크로드는 GitOps로** 분리한다. 부트스트랩에서 Argo CD나 Flux를 심고, 나머지는 그것이 배포하게 한다.

**다음 장에서는** 그 GitOps를 다룬다. 매니페스트를 재사용 가능하게 패키징하고, Git을 진실의 원천으로 삼아 배포를 자동화하는 방법을 살펴본다.
