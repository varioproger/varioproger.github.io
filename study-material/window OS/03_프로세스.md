# 3장. 프로세스

## 3.1 프로세스란 무엇인가

프로세스는 "실행 중인 프로그램 하나에 대한 OS의 관리 단위"다. 실제로는 다음의 묶음이다.

- **가상 주소 공간**: 이 프로세스만 보는 독립된 메모리 뷰 ([5장](05_메모리.md))
- **핸들/파일 디스크립터 테이블**: 열린 파일, 소켓, 뮤텍스, 이벤트 등 커널 객체에 대한 참조
- **최소 1개의 스레드**: 실제로 코드를 실행하는 주체 ([4장](04_스레드와_동시성.md))
- **환경**: 커맨드라인 인자, 환경변수, 작업 디렉터리, 보안 토큰/권한
- **프로세스 제어 블록(PCB)** 또는 Windows의 **EPROCESS**: 커널이 이 프로세스를 관리하기 위해 들고 있는 메타데이터 구조체

핵심은: **프로세스는 "그릇"이고, 실제 실행은 스레드가 한다.** 프로세스 자체는 코드를 실행하지 않는다.

## 3.2 프로세스 생성: `fork`와 `CreateProcess`의 철학 차이

리눅스와 Windows는 프로세스를 만드는 철학이 근본적으로 다르다.

**리눅스: `fork()` + `exec()`**

```c
pid_t pid = fork();      // 현재 프로세스를 "복제"
if (pid == 0) {
    execve("/bin/ls", argv, envp);  // 복제본을 다른 프로그램으로 교체
} else {
    waitpid(pid, &status, 0);
}
```

`fork()`는 부모의 주소 공간을 "복제"하지만, 실제로 페이지를 복사하지는 않는다. **Copy-on-Write(COW)**로 부모/자식이 같은 물리 페이지를 공유하다가, 한쪽이 쓰기를 시도하는 순간에만 그 페이지를 실제로 복사한다. 그래서 `fork()` 직후 `exec()`로 이어지는 흔한 패턴은 생각보다 저렴하다.

**Windows: `CreateProcess()`**

```c
STARTUPINFO si = { sizeof(si) };
PROCESS_INFORMATION pi;
CreateProcess(L"C:\\app.exe", cmdLine, NULL, NULL, FALSE,
              0, NULL, NULL, &si, &pi);
```

Windows는 "복제" 개념이 없다. 처음부터 "이 실행 파일로 새 프로세스를 만들어라"고 한 번에 요청한다. 그래서 리눅스식 `fork()` 흉내(예: 인터프리터가 자기 자신을 복제해서 워커를 만드는 패턴)를 Windows에서 그대로 못 쓰고, 별도의 IPC로 상태를 넘기거나 스레드/프로세스 풀을 다시 설계해야 하는 경우가 많다.

## 3.3 프로세스 종료와 좀비/고아

- **정상 종료**: `exit()`/`ExitProcess()` — 모든 스레드 종료, 핸들 정리, 종료 코드 저장.
- **좀비(Zombie, 리눅스 용어)**: 자식이 종료했지만 부모가 `wait()`로 종료 상태를 아직 회수하지 않은 상태. 커널이 종료 코드를 들고 있는 최소한의 흔적만 남긴다. 부모가 영원히 `wait()`하지 않으면 좀비가 쌓여 PID를 낭비한다.
- **고아(Orphan)**: 부모가 먼저 죽은 자식. 리눅스에서는 init(PID 1)에게 재입양된다.
- Windows에는 좀비/고아라는 용어 자체는 없지만, **핸들을 안 닫으면 프로세스 객체 자체가 커널에 남아있는** 유사한 문제가 있다 — "프로세스는 죽었는데 handle leak 때문에 커널 객체가 안 사라진다"는 현상.

**실무 함정**: 자식 프로세스를 스폰하고 종료 코드를 절대 회수하지 않는 서버 코드는 좀비/핸들 누수로 서서히 자원을 고갈시킨다.

## 3.4 프로세스 격리와 핸들/디스크립터

각 프로세스는 자기만의 **핸들 테이블**(Windows)/**파일 디스크립터 테이블**(POSIX)을 가진다. 정수 하나(fd)나 핸들 값은 "이 프로세스 안에서만 의미 있는" 간접 참조다 — 같은 값 `3`이 프로세스 A에서는 로그 파일, 프로세스 B에서는 소켓을 가리킬 수 있다.

이게 왜 중요한가: **커널 객체(파일, 소켓, 뮤텍스, 프로세스 자체)는 참조 카운트로 관리된다.** 핸들을 닫지 않으면(`CloseHandle`/`close`) 참조 카운트가 안 줄어서 자원이 해제되지 않는다 — 이것이 "핸들 누수(handle leak)"이며, 장시간 실행되는 서버에서 흔한 버그 원인이다.

## 3.5 프로세스 간 통신(IPC)

프로세스는 주소 공간이 격리되어 있으므로, 데이터를 주고받으려면 커널이 중재하는 명시적 메커니즘이 필요하다.

| 방식 | 특징 | 용도 |
|---|---|---|
| 파이프 (Anonymous/Named Pipe) | 스트림 기반, 단방향/양방향 | 부모-자식, 로컬 서비스 통신 |
| 공유 메모리 (Shared Memory / Memory-Mapped File) | 커널 개입 없이 직접 메모리 접근, 가장 빠름 | 대용량 데이터 공유, 저지연 IPC |
| 소켓 (로컬/Unix Domain Socket) | 네트워크 소켓과 동일 API | 이질적 프로세스 간, 언어 무관 |
| 메시지 큐 / 시그널 (POSIX), 메일슬롯/윈도우 메시지 (Windows) | 작은 메시지 전달 | 이벤트 통지 |
| RPC (예: gRPC, COM, DCOM) | 구조화된 호출 규약을 얹은 것 | 서비스 간 호출 |

공유 메모리가 가장 빠른 이유: 파이프/소켓은 데이터를 커널 버퍼로 복사했다가 다시 유저 버퍼로 복사하는 과정을 거치지만, 공유 메모리는 **같은 물리 페이지를 두 프로세스의 가상 주소 공간에 매핑**만 해두면 복사 없이 바로 접근한다 (5장의 메모리 매핑과 직결).

## 3.6 프로세스 vs 스레드, 언제 무엇을 쓰나

| 기준 | 여러 프로세스 | 여러 스레드 |
|---|---|---|
| 격리/안정성 | 하나가 죽어도 다른 것에 영향 없음 | 하나가 죽으면(크래시) 전체가 죽음 |
| 통신 비용 | IPC 필요, 상대적으로 비쌈 | 메모리 공유, 저렴하지만 동기화 필요 |
| 생성 비용 | 상대적으로 비쌈 (주소 공간 새로 구성) | 저렴 (주소 공간 공유) |
| 대표 사례 | 브라우저의 탭별 프로세스, nginx worker | 웹 서버의 요청 처리 스레드 풀 |

## 3.7 컨테이너: 프로세스 격리의 진화

Docker/Kubernetes로 대표되는 **컨테이너**는 새로운 프로세스 개념이 아니라, 지금까지 본 격리 메커니즘을 리눅스 커널 기능으로 더 강하게 조합한 것이다.

- **네임스페이스(Namespace)**: PID, 네트워크, 마운트, 사용자 등을 프로세스(그룹)마다 독립된 뷰로 보이게 함 — 컨테이너 안에서 `ps`를 치면 자기 프로세스만 PID 1부터 보이는 이유.
- **cgroups(Control Groups)**: 프로세스 그룹이 쓸 수 있는 CPU/메모리/디스크 I/O 상한을 강제 — "컨테이너 메모리 제한"이 실제로는 그 컨테이너에 속한 프로세스들의 cgroup 메모리 한도다. 이 한도를 넘으면 [5장](05_메모리.md)에서 다룰 OOM killer가 해당 프로세스를 강제 종료한다.
- **컨테이너는 별도의 커널을 갖지 않는다** — VM과 달리 호스트 커널을 그대로 공유하는 "격리된 프로세스 묶음"일 뿐이다. 그래서 VM보다 훨씬 가볍게 뜨지만, 커널 자체의 취약점에는 VM만큼 격리되지 않는다.

Windows는 네이티브 리눅스 네임스페이스가 없으므로, WSL2나 Windows 컨테이너는 실제로는 경량 VM(Hyper-V) 위에서 리눅스 커널을 돌리거나 Windows 커널의 자체 격리 기능(Job Object, 서버 사일로)을 쓴다. "컨테이너 = 리눅스 프로세스 격리 기능의 조합"이라는 것만 기억하면, 컨테이너 관련 도구(Docker, Kubernetes)를 다룰 때 "이 설정이 실제로 어떤 커널 기능을 건드리는가"를 짐작할 수 있다.

## 3.9 다른 OS에서는

| 개념 | Windows | Linux |
|---|---|---|
| 생성 | `CreateProcess` (즉시 새 이미지) | `fork` + `exec` (복제 후 교체) |
| 식별자 | PID (Process ID), 핸들 | PID |
| 관리 구조체 | EPROCESS | `task_struct` |
| 부모 사망 시 자식 | 독립적으로 계속 실행 | init에 재입양 (고아) |
| 자원 제한/격리 | Job Object | cgroups + namespace |

다음 장에서는 프로세스 안에서 실제로 실행을 담당하는 "스레드"와, 여러 스레드가 동시에 돌 때 생기는 동시성 문제를 다룬다.
