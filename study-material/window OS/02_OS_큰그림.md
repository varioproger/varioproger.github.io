# 2장. OS의 큰 그림

이 장에서는 이후 모든 장(프로세스, 스레드, 메모리, 네트워크)에서 계속 등장할 공통 개념 — 커널/유저 모드, 시스템 콜, 인터럽트, 스케줄러 — 을 먼저 잡는다.

## 2.1 커널 모드와 유저 모드

CPU는 최소 두 가지 **권한 레벨**로 동작한다.

- **커널 모드(Ring 0)**: 모든 메모리, 모든 명령어에 접근 가능. OS 커널과 드라이버가 여기서 돈다.
- **유저 모드(Ring 3)**: 제한된 권한. 일반 애플리케이션이 여기서 돈다. 직접 하드웨어를 만지거나 다른 프로세스의 메모리를 볼 수 없다.

애플리케이션이 파일을 읽거나 네트워크를 쓰거나 메모리를 할당하려면, "커널 모드로 전환해서 커널에게 대신 해달라고 요청"해야 한다. 이 요청이 **시스템 콜(system call)**이다.

```
[유저 모드]  ReadFile(handle, buf, size, ...)   /  read(fd, buf, size)
      │  (라이브러리가 syscall 명령어 실행)
      ▼
[커널 모드]  실제 디스크 컨트롤러에 명령, 완료 대기, 데이터 복사
      │
      ▼
[유저 모드]  함수가 리턴, 실행 계속
```

이 전환에는 비용이 든다(레지스터 저장, 권한 전환, TLB/캐시 영향 등). **시스템 콜을 자주 하는 코드는 그 자체로 느리다** — 이 사실이 버퍼링(7장), 배치 I/O, IOCP 같은 설계를 정당화한다.

## 2.2 인터럽트와 예외

CPU가 지금 하던 일을 멈추고 커널로 강제 전환되는 경로는 시스템 콜 말고도 두 가지가 더 있다.

- **하드웨어 인터럽트**: 타이머, 네트워크 카드, 디스크 컨트롤러 등이 "일이 끝났다/이벤트가 생겼다"고 CPU에 신호를 보냄. 예: 네트워크 패킷 도착, 타이머 틱.
- **예외(Exception/Fault)**: 실행 중인 명령어 자체가 문제를 일으킴. 예: 0으로 나누기, 잘못된 메모리 접근(Access Violation / Segmentation Fault), **페이지 폴트**(5장에서 핵심적으로 다룸).

페이지 폴트가 중요한 이유: 프로그래머 입장에서는 그냥 메모리를 읽은 것뿐인데, 그 메모리가 아직 물리 메모리에 없으면(디스크에서 스와핑된 상태 등) CPU가 자동으로 커널에 예외를 던지고, 커널이 페이지를 채워준 뒤 실행을 이어간다. **이것이 가상 메모리가 동작하는 근본 메커니즘이다.**

## 2.3 스케줄러: CPU 시분할의 핵심

코어 4개짜리 CPU에서 스레드 200개가 동시에 "실행 중"처럼 보이는 이유는 **스케줄러**가 아주 짧은 시간 단위로 스레드를 바꿔 끼우기 때문이다. 이 시간 단위를 **퀀텀(quantum)**이라 부르는데, 고정된 절대값이 아니라 OS와 설정에 따라 다르다. Windows는 내부적으로 "클럭 틱(보통 x86/x64 멀티프로세서 기준 약 15.6ms)" 단위로 퀀텀을 세는데, 클라이언트 에디션은 기본 2클럭틱(약 30ms 정도)을, 서버 에디션은 기본 12클럭틱(약 190ms 정도)을 쓴다 — 서버가 더 긴 이유는 요청 처리 도중 잦은 컨텍스트 스위칭을 줄이기 위해서다(*Windows Internals* 7판, 4장 "Quantum" 참고). 리눅스 CFS(Completely Fair Scheduler)는 애초에 고정 퀀텀 개념이 아니라 각 스레드가 사용한 실행 시간(vruntime)을 비교해 가장 적게 실행된 스레드를 동적으로 우선시한다.

```
Core 0:  [Thread A]---[Thread C]---[Thread A]---[Thread B]---...
Core 1:  [Thread B]---[Thread D]---[Thread D]---[Thread A]---...
              ↑ 타이머 인터럽트마다 스케줄러가 "다음엔 누구?" 결정
```

스케줄러가 다음에 누구를 돌릴지 결정하는 요소:

- **우선순위(Priority)**: Windows는 0~31 우선순위 레벨(실시간/가변 클래스), 리눅스는 nice 값 + CFS의 vruntime.
- **상태**: Ready(대기 중, 실행 가능) / Running(실행 중) / Waiting(I/O나 락 대기 중, 스케줄러가 아예 후보로 안 봄) / Terminated.
- **친화도(Affinity)**: 특정 스레드를 특정 코어에 묶을 수 있음. 캐시 지역성 때문에 종종 성능에 중요.

**컨텍스트 스위칭(context switch)**은 스케줄러가 실행 중인 스레드를 바꾸는 행위다. 레지스터, 스택 포인터, (프로세스가 바뀌면) 주소 공간 매핑까지 교체해야 하므로 공짜가 아니다 — "스레드를 늘리면 무조건 빨라진다"가 틀린 이유 중 하나가 바로 이 비용이다. 자세한 내용은 [4장](04_스레드와_동시성.md)에서.

## 2.4 부팅부터 "내 프로그램이 실행되기"까지 (요약)

1. 펌웨어(UEFI/BIOS)가 부트로더를 찾아 실행
2. 부트로더가 커널 이미지를 메모리에 올리고 제어권을 넘김
3. 커널이 하드웨어 초기화, 드라이버 로드, 스케줄러/메모리 관리자 초기화
4. 최초 유저 프로세스 실행 (Windows: `smss.exe` → `wininit.exe`/`winlogon.exe`, Linux: `init`/`systemd`)
5. 여기서부터 우리가 만든 `.exe`/ELF 바이너리도 그냥 하나의 프로세스로 생성됨 ([3장](03_프로세스.md))

## 2.5 실전 체크리스트

- [ ] 내가 자주 호출하는 API가 시스템 콜을 유발하는지 알고 있는가? (예: `malloc` 대부분은 아니지만, `mmap`/`VirtualAlloc`은 그렇다)
- [ ] "이 코드가 느린 게 CPU 연산 때문인지, 시스템 콜/컨텍스트 스위칭 때문인지" 구분해서 프로파일링하고 있는가?
- [ ] 스레드 우선순위를 임의로 올려본 적이 있다면, 그게 다른 스레드를 굶길 수 있다는 걸 알고 있는가?

## 2.6 다른 OS에서는

| 개념 | Windows | Linux |
|---|---|---|
| 시스템 콜 진입 | `syscall`/`sysenter`, ntdll이 래핑 | `syscall` 명령, glibc가 래핑 |
| 스케줄러 | 우선순위 기반 선점형, 32단계 | CFS(Completely Fair Scheduler), nice/vruntime |
| 예외 처리 | SEH(구조적 예외 처리) | 시그널(SIGSEGV 등) |
