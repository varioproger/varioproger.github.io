# 7장. 파일 시스템과 I/O (보너스)

메모리, 프로세스, 스레드, 네트워크만큼 자주 언급되진 않지만, "왜 로그 쓰기가 갑자기 느려지지?", "파일 지웠는데 용량이 안 줄어드는 이유는?" 같은 질문에 답하려면 필요한 최소한의 지식이다.

## 7.1 파일 I/O도 결국 시스템 콜이다

```c
FILE* f = fopen("log.txt", "a");
fwrite(data, 1, len, f);   // 보통은 시스템 콜을 안 함! (아래 참고)
fclose(f);                  // 여기서 실제로 flush + write 시스템 콜
```

`fwrite`/`fprintf` 같은 C 표준 라이브러리 함수는 **유저 모드 버퍼**를 거친다 — 매번 시스템 콜을 하면 [2장](02_OS_큰그림.md)에서 봤듯 비싸기 때문에, 라이브러리가 일정 크기(보통 4KB 근처)만큼 모아서 한 번에 `write()` 시스템 콜을 호출한다. 반면 `write(fd, ...)`(POSIX 저수준 API)나 `WriteFile`(Windows)은 직접 시스템 콜이다.

## 7.2 커널의 페이지 캐시(파일 캐시)

시스템 콜로 커널까지 가더라도, 디스크에 바로 쓰는 게 아니다. 커널은 **페이지 캐시**(리눅스)/**캐시 매니저**(Windows)라는 메모리 영역에 파일 데이터를 캐싱한다.

```
애플리케이션 write()
      │
      ▼
[커널 페이지 캐시]  ← 여기서 "쓰기 완료"로 리턴 (지연 쓰기, write-back)
      │  (백그라운드에서 나중에)
      ▼
   실제 디스크
```

**왜 중요한가**: (1) 같은 파일을 반복해서 읽으면 두 번째부터는 디스크 접근 없이 메모리 캐시에서 바로 옴 — 그래서 "방금 만든 큰 파일을 다시 읽으면 이상하게 빠르다." (2) `write()`가 리턴했다고 데이터가 디스크에 안전하게 저장됐다는 보장이 없다 — 정전/크래시가 나면 캐시에만 있던 데이터가 사라질 수 있다.

**강제로 디스크까지 내리려면**: `fsync()`(POSIX)/`FlushFileBuffers()`(Windows)를 명시적으로 호출해야 한다. DB나 트랜잭션 로그처럼 내구성이 중요한 코드는 이걸 신경 써야 한다 — 반대로 매번 `fsync`를 부르면 성능이 크게 떨어지므로, "언제 안전을 보장해야 하는가"를 명확히 설계해야 한다.

## 7.3 메모리 매핑 파일(mmap)

파일을 읽고 쓰는 대신, 파일을 가상 주소 공간에 직접 매핑해서 **메모리처럼 접근**할 수 있다.

```c
// Windows
HANDLE hFile = CreateFile(L"data.bin", ...);
HANDLE hMap = CreateFileMapping(hFile, NULL, PAGE_READWRITE, 0, 0, NULL);
void* p = MapViewOfFile(hMap, FILE_MAP_ALL_ACCESS, 0, 0, 0);
// 이제 p[0], p[1], ... 로 파일 내용에 직접 접근 — read()/write() 호출 없이
```

```c
// Linux
int fd = open("data.bin", O_RDWR);
void* p = mmap(NULL, size, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
```

내부적으로는 [5장](05_메모리.md)의 페이지 폴트 메커니즘을 그대로 쓴다 — 처음 접근하는 페이지는 폴트가 나서 커널이 디스크에서 읽어와 채워준다. 큰 파일을 랜덤 액세스할 때(DB 엔진, 인덱스 파일 등) `read`/`write` 반복보다 훨씬 효율적인 경우가 많고, 여러 프로세스가 같은 파일을 매핑하면 그 자체로 [3장](03_프로세스.md)의 공유 메모리 IPC가 된다.

## 7.4 파일 삭제와 "핸들이 열려있으면" (플랫폼 차이가 큰 지점)

- **리눅스**: 파일을 `unlink`(삭제)해도, 어떤 프로세스가 그 파일을 열어서 fd를 들고 있으면 실제 디스크 공간은 그 fd가 닫힐 때까지 회수되지 않는다. 디렉터리 목록에서는 즉시 사라지지만 공간은 안 줄 수 있다 — 로그 파일을 삭제했는데 `df`상 용량이 안 줄어드는 흔한 원인.
- **Windows**: 기본적으로 파일이 열려 있으면 **삭제 자체가 실패**한다("다른 프로그램에서 사용 중이므로 액세스가 거부되었습니다"). `FILE_SHARE_DELETE` 플래그로 열었을 때만 삭제 예약(그리고 마지막 핸들이 닫힐 때 실제 삭제)이 가능하다.

## 7.5 실전 체크리스트

- [ ] 데이터 내구성이 중요한 경로에서 `fsync`/`FlushFileBuffers`를 명시적으로 호출하는가?
- [ ] "파일 지웠는데 용량이 안 줄어든다"를 마주치면, 어떤 프로세스가 그 파일을 열고 있는지 확인하는가? (`lsof`/Process Explorer의 Handle Search)
