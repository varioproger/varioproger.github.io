# 6장. 네트워크

네트워크 프로그래밍은 결국 "커널이 관리하는 소켓이라는 커널 객체를 통해, OS의 TCP/IP 스택과 대화하는 것"이다. 이 장은 그 대화 방식(I/O 모델)에 초점을 둔다.

## 6.1 소켓은 파일이다 (POSIX 관점)

리눅스/POSIX에서 소켓은 파일 디스크립터로 표현되고, `read`/`write`와 거의 같은 API로 다룬다("모든 것은 파일이다"). Windows는 별도의 `SOCKET` 핸들과 `Winsock` API(`send`/`recv`, BSD 소켓 API와 유사)를 쓰지만 개념은 같다.

```c
int sock = socket(AF_INET, SOCK_STREAM, 0);   // TCP 소켓 생성
connect(sock, &addr, sizeof(addr));
write(sock, buf, len);
read(sock, buf, len);
close(sock);
```

소켓을 만든다고 네트워크 연결이 바로 생기는 게 아니다 — `connect`/`accept` 시점에 OS가 TCP 3-way handshake 같은 프로토콜 절차를 수행한다.

## 6.2 TCP/IP 스택을 아주 간단히

```
애플리케이션          "hello" 라는 바이트를 send()
    │
전송 계층 (TCP/UDP)    세그먼트로 분할, 순서 보장/재전송(TCP) 또는 안 함(UDP)
    │
네트워크 계층 (IP)      목적지 라우팅, 패킷 단위
    │
링크 계층              실제 네트워크 카드로 프레임 전송
```

- **TCP**: 연결 지향, 순서 보장, 재전송, 흐름/혼잡 제어. 느리지만 신뢰성 있음. HTTP, 대부분의 RPC.
- **UDP**: 비연결, 순서/재전송 없음. 빠르지만 신뢰성 없음. 게임, 스트리밍, DNS.

**프로그래머가 자주 놓치는 점**: `send()`가 성공했다는 건 "커널의 송신 버퍼에 데이터를 넘겼다"는 뜻일 뿐, 상대방이 받았다는 보장은 아니다. 마찬가지로 `send()`를 한 번 호출했다고 상대방이 `recv()`를 한 번에 같은 크기로 받는 게 아니다 — **TCP는 스트림이지, 메시지 경계를 보존하지 않는다.** 메시지 경계가 필요하면 애플리케이션 레벨에서 길이 헤더나 구분자를 직접 넣어야 한다.

## 6.3 블로킹 I/O의 한계

```c
while (1) {
    int client = accept(server_sock, ...);   // 연결 하나 받음
    handle_client(client);                    // 이 함수가 끝나야 다음 accept
}
```

이 코드는 클라이언트 1개만 동시에 처리할 수 있다. "그럼 클라이언트마다 스레드를 만들자"가 가장 흔한 다음 단계지만, [4장](04_스레드와_동시성.md)에서 봤듯 스레드는 공짜가 아니다 — 커넥션 1만 개 = 스레드 1만 개는 컨텍스트 스위칭과 메모리(스택)만으로 시스템을 마비시킬 수 있다("C10K 문제").

## 6.4 I/O 멀티플렉싱: `select`/`poll`/`epoll`

하나의 스레드로 여러 소켓을 동시에 감시하는 방법.

- **`select`/`poll`**: "이 소켓 목록 중에 준비된 게 있으면 알려달라"고 매번 전체 목록을 커널에 넘김. 소켓 수가 늘면 O(N) 비용 — 대규모 커넥션에는 비효율.
- **`epoll`(리눅스)**: 커널에 "감시할 소켓 목록"을 한 번 등록해두고, 이후에는 "준비된 것만" 알려달라고 요청. 커넥션 수가 많아져도 효율적 — 이벤트 기반 서버(nginx, Node.js의 libuv 등)의 핵심 메커니즘.

```
select/poll: [매 호출마다] "얘, 얘, 얘, 얘 중에 누구 준비됐어?" → O(N) 스캔
epoll:       [한 번 등록] "얘네 목록 감시해줘" → [이후] "얘랑 얘가 준비됐어" → O(준비된 개수)
```

## 6.5 Windows의 답: IOCP (I/O Completion Port)

Windows는 epoll과 다른 접근을 쓴다. **"준비되면 알려줘"가 아니라 "작업을 미리 시켜놓고, 끝나면 알려줘."**

```c
HANDLE iocp = CreateIoCompletionPort(INVALID_HANDLE_VALUE, NULL, 0, 0);
CreateIoCompletionPort((HANDLE)socket, iocp, (ULONG_PTR)ctx, 0);

WSARecv(socket, &buf, 1, NULL, &flags, &overlapped, NULL);  // "받으면 완료 알려줘" 등록 후 즉시 리턴

// 워커 스레드 풀에서:
GetQueuedCompletionStatus(iocp, &bytes, &key, &overlapped, INFINITE);
// 완료된 I/O 작업이 여기로 들어옴 — 어떤 스레드가 처리할지도 OS가 로드밸런싱
```

이걸 **완료 기반(completion-based) 비동기 I/O**라고 부르고, epoll류의 **준비 기반(readiness-based)**과 대조된다. 리눅스도 최근 `io_uring`으로 완료 기반 모델에 가까워지고 있다 — 두 진영의 설계가 점차 수렴하는 추세다.

| 모델 | 대표 API | 알려주는 시점 |
|---|---|---|
| 블로킹 | `recv`/`read` | 호출자가 그냥 멈춰서 기다림 |
| 논블로킹 + 폴링 | `recv`(O_NONBLOCK) | "지금 데이터 없음"을 즉시 리턴, 반복 확인 |
| 준비 기반 멀티플렉싱 | `select`/`poll`/`epoll` | "이 소켓이 읽을 준비가 됐다" |
| 완료 기반 비동기 | IOCP, `io_uring`, POSIX AIO | "이미 요청한 읽기가 완료됐다, 데이터도 여기 있다" |

## 6.6 Nagle 알고리즘과 지연

TCP는 기본적으로 작은 패킷을 모아서 보내는 **Nagle 알고리즘**을 쓴다 — 네트워크 효율을 높이지만, 실시간성이 중요한 애플리케이션(게임, 저지연 RPC)에서는 응답 지연의 원인이 될 수 있다. `TCP_NODELAY` 소켓 옵션으로 끌 수 있다.

이 지연은 수신 측의 **지연 ACK(Delayed ACK)**과 겹치면 특히 커진다 — Nagle은 "이전에 보낸 데이터의 ACK를 받을 때까지 작은 패킷을 더 안 보내고 모은다"는 규칙인데, 상대방도 ACK를 즉시 안 보내고 지연시키면 둘이 서로를 기다리며 정체된다. 지연 ACK의 기본 타임아웃은 OS마다 다르다 — Windows는 기본 약 200ms(레지스트리 `TcpAckFrequency`로 조정 가능)이고, 리눅스는 최소 약 40ms에서 최대 200ms 사이에서 동적으로 결정된다(`TCP_QUICKACK`으로 즉시 ACK를 요청할 수 있다). "왜 요청-응답 지연이 딱 40ms 혹은 200ms만큼 튀지?"라는 질문의 흔한 답이 이 Nagle + 지연 ACK 조합이다. 해결책은 송신 측 `TCP_NODELAY` 또는 수신 측 지연 ACK 비활성화 중 하나(보통 송신 측 `TCP_NODELAY`)면 충분하다.

## 6.7 TIME_WAIT와 포트 재사용

소켓을 정상적으로 닫아도(`close`/`closesocket`), 먼저 연결을 끊은 쪽(active close를 수행한 쪽)의 소켓은 곧바로 사라지지 않고 **TIME_WAIT** 상태로 일정 시간(전통적으로 2×MSL) 머문다. 이 값은 OS마다 기본값이 다르다 — Windows는 기본 240초(4분, 레지스트리 `TcpTimedWaitDelay`로 30~300초 범위에서 조정 가능), 리눅스는 하드코딩된 60초다.

**왜 이런 상태가 필요한가**: (1) 마지막 ACK이 유실돼서 상대가 재전송한 FIN을 받아 다시 응답해줄 여지를 남겨야 하고, (2) 같은 4-tuple(출발지/목적지 IP·포트)을 쓰는 새 연결이 너무 빨리 생겨서 이전 연결의 지연된 패킷과 뒤섞이는 걸 막아야 하기 때문이다.

**실무에서 겪는 증상**: 서버 프로세스를 강제 종료(`kill -9`, 작업 관리자에서 강제 종료)했다가 바로 재시작하면, 서버가 듣던 포트로 다시 `bind()`할 때 "Address already in use"(리눅스)/"통상적으로 각 소켓 주소는 한 번만 사용할 수 있습니다"(Windows) 오류가 나는 경우가 흔하다 — 죽은 프로세스의 연결들이 아직 TIME_WAIT로 남아 그 포트를 점유하고 있기 때문이다.

여기서 `SO_REUSEADDR`의 의미가 플랫폼마다 크게 다르다는 점을 주의해야 한다. **리눅스**에서 `SO_REUSEADDR`는 정확히 이 목적(TIME_WAIT 상태의 주소 재바인딩 허용)으로 동작한다. 반면 **Windows**에서 `SO_REUSEADDR`는 훨씬 느슨해서, 이미 다른 소켓이 바인딩해 활성 사용 중인 주소/포트까지 다른 프로세스가 "가로채기(steal)"할 수 있게 허용해버린다 — 이는 보안상 위험할 수 있는 동작이다. 그래서 Microsoft는 서버가 포트를 독점하려는 의도라면 `SO_REUSEADDR` 대신 **`SO_EXCLUSIVEADDRUSE`**를 쓰도록 권장한다. 즉, "TIME_WAIT 회피용 재시작 옵션"이라는 통념은 리눅스 기준이며, Windows 코드를 리눅스 습관대로 짜면 의도와 다른(더 위험한) 동작을 하게 된다.

이는 서버가 아니라 **클라이언트 역할**로 짧은 연결을 아주 많이 맺었다 끊는 프로그램(예: 매 요청마다 새 소켓으로 외부 API를 호출)에서도 문제가 된다 — 로컬 포트(대개 약 6만 개 한도)가 TIME_WAIT 상태로 소진되어 더 이상 새 연결을 못 맺는 **포트 고갈(port exhaustion)** 현상으로 이어질 수 있다. 해결책은 연결을 매번 새로 맺지 말고 **커넥션 풀/keep-alive**로 재사용하는 것이다.

## 6.8 실전 체크리스트

- [ ] 내 서버가 커넥션당 스레드 1개 모델이라면, 예상 최대 동시 커넥션 수에서 스레드 수가 감당 가능한 범위인가?
- [ ] `send`/`recv`가 요청한 바이트 수만큼 정확히 처리된다고 가정하고 있지 않은가? (부분 전송 처리 필요)
- [ ] 메시지 경계가 필요한 프로토콜을 TCP 위에 만들 때, 길이 헤더나 구분자를 명시적으로 두었는가?
- [ ] 지연에 민감한데 `TCP_NODELAY`를 검토해본 적이 있는가?
- [ ] 서버 재시작 시 "포트가 이미 사용 중" 오류를 봤다면, TIME_WAIT을 이해하고 대응하는가? Windows라면 `SO_REUSEADDR`가 리눅스와 다르게 "포트 가로채기"를 허용한다는 것도 알고 있는가?
- [ ] 외부 API를 매 요청마다 새 소켓으로 호출하고 있다면, 커넥션 풀/keep-alive로 바꿀 여지가 있는가?

## 6.9 다른 OS에서는

| 개념 | Windows | Linux |
|---|---|---|
| 소켓 API | Winsock (BSD 유사) | BSD 소켓 |
| 확장 가능한 비동기 I/O | IOCP (완료 기반) | epoll(준비 기반) / io_uring(완료 기반) |
| 논블로킹 설정 | `ioctlsocket(FIONBIO)` | `fcntl(O_NONBLOCK)` |
| 지연 ACK 기본값 | 약 200ms(`TcpAckFrequency`) | 40~200ms 사이 동적(`TCP_QUICKACK`으로 해제 가능) |
| TIME_WAIT 기본 지속시간 | 약 240초(4분, `TcpTimedWaitDelay`) | 60초(고정) |
| 주소 재사용 옵션 | `SO_REUSEADDR`(포트 가로채기 허용, TIME_WAIT 전용 아님), `SO_EXCLUSIVEADDRUSE`(독점 바인딩) | `SO_REUSEADDR`(TIME_WAIT 재사용), `SO_REUSEPORT` |

다음 장에서는 네트워크와 마찬가지로 "버퍼링"과 "커널 캐시"가 핵심인 파일 시스템/파일 I/O를 짧게 다룬다.
