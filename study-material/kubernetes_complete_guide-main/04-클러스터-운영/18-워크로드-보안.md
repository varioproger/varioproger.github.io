# 18장. 워크로드 보안

> **학습목표**
> - 블래스트 레이디어스 관점에서 보안 설계를 판단할 수 있다.
> - securityContext의 각 필드가 커널 수준에서 무엇을 하는지 안다.
> - Pod Security Admission의 세 프로파일을 적용하고 점진 도입할 수 있다.
> - NetworkPolicy로 기본 거부 정책을 구성하고 필요한 통신만 열 수 있다.
> - 이미지 공급망을 스캐닝·서명·검증으로 보호할 수 있다.
> - 정책 엔진으로 조직 규칙을 강제할 수 있다.

---

## 들어가며

17장에서 "누가 API를 호출할 수 있는가"를 다뤘다. 이 장은 **"그 워크로드가 실행된 뒤에 무엇을 할 수 있는가"** 를 다룬다.

두 질문은 다르다. RBAC이 완벽해도, 특권 컨테이너 하나가 노드를 장악하면 소용이 없다.

## 18.1 블래스트 레이디어스

### 사고 방식

보안을 "뚫리지 않게 하는 것"으로만 생각하면 설계가 어렵다. 더 유용한 질문은 이것이다.

> **"이것이 침해되면 피해가 어디까지 번지는가?"**

이것이 **블래스트 레이디어스(blast radius, 폭발 반경)** 다.

```
┌─────────────────────────────────────────────────────┐
│  컨테이너 하나가 침해됐다                              │
│                                                     │
│  ① 그 컨테이너 안에서 무엇을 할 수 있나?               │
│     · root인가? 쓰기 가능한 파일 시스템인가?           │
│     · 어떤 capability를 갖고 있나?                    │
│         ↓ 막는 것: securityContext                   │
│                                                     │
│  ② 같은 Pod의 다른 컨테이너로 갈 수 있나?              │
│     · 공유 볼륨, localhost, PID 네임스페이스          │
│         ↓ 막는 것: 최소 권한, 볼륨 분리                │
│                                                     │
│  ③ 노드로 탈출할 수 있나?                             │
│     · hostPath, hostNetwork, privileged, 커널 익스플로잇│
│         ↓ 막는 것: Pod Security Admission, 샌드박스   │
│                                                     │
│  ④ 다른 Pod와 통신할 수 있나?                         │
│     · 기본적으로 모든 Pod와 통신 가능                  │
│         ↓ 막는 것: NetworkPolicy                     │
│                                                     │
│  ⑤ API 서버를 호출할 수 있나?                         │
│     · SA 토큰이 마운트되어 있나? 권한은?               │
│         ↓ 막는 것: automountSAToken: false, RBAC     │
│                                                     │
│  ⑥ 클라우드 자원에 접근할 수 있나?                     │
│     · IMDS(메타데이터 서비스), IAM 역할                │
│         ↓ 막는 것: IMDSv2, 워크로드 아이덴티티          │
└─────────────────────────────────────────────────────┘
```

**각 층에서 반경을 좁히는 것이 이 장의 내용이다.**

### 잊기 쉬운 경로: 클라우드 메타데이터 서비스

```bash
kubectl run t --rm -it --image=nicolaka/netshoot --restart=Never -- \
  curl -s http://169.254.169.254/latest/meta-data/iam/security-credentials/
```

노드에 IAM 역할이 붙어 있으면, **어떤 Pod든 그 역할의 자격증명을 훔칠 수 있다.** 노드 역할은 대개 강력하므로 심각한 문제다.

**대책**
1. **IMDSv2 강제 + hop limit = 1** — 컨테이너에서 접근 불가
2. **워크로드 아이덴티티 사용**(17.4절) — 노드 역할을 최소화
3. **NetworkPolicy로 169.254.169.254 차단**

```bash
# AWS: IMDSv2 강제, hop limit 1
aws ec2 modify-instance-metadata-options \
  --instance-id i-xxx \
  --http-tokens required \
  --http-put-response-hop-limit 1
```

## 18.2 securityContext

### 컨테이너 수준

```yaml
containers:
  - name: app
    securityContext:
      runAsNonRoot: true                # ★ root면 컨테이너 시작 거부
      runAsUser: 10001
      runAsGroup: 10001
      allowPrivilegeEscalation: false   # ★ setuid로 권한 상승 차단
      readOnlyRootFilesystem: true      # ★ 루트 FS 쓰기 금지
      privileged: false
      capabilities:
        drop: ["ALL"]                   # ★ 모든 capability 제거
        add: ["NET_BIND_SERVICE"]       # 필요한 것만 추가
      seccompProfile:
        type: RuntimeDefault            # ★ 시스템콜 필터링
```

**각 필드가 하는 일** (2.4절의 리눅스 프리미티브가 여기서 쓰인다)

| 필드 | 커널 수준 동작 | 막는 공격 |
|---|---|---|
| `runAsNonRoot` | UID 0이면 kubelet이 시작을 거부 | root 권한 남용 |
| `allowPrivilegeEscalation: false` | `no_new_privs` 비트 설정 | setuid 바이너리로 권한 상승 |
| `readOnlyRootFilesystem` | 루트를 읽기 전용으로 마운트 | 악성 코드 설치, 바이너리 변조 |
| `capabilities.drop: ALL` | 모든 capability 제거 | 네트워크 조작, 마운트, 커널 모듈 |
| `privileged: false` | 모든 capability + 디바이스 접근 차단 | **노드 탈출** |
| `seccompProfile` | 허용된 시스템콜만 통과 | 커널 익스플로잇 표면 축소 |

**`privileged: true`가 가장 위험하다.** 사실상 노드의 root와 같다. `/dev`에 접근할 수 있으므로 호스트 디스크를 마운트하거나 커널 모듈을 로드할 수 있다.

### Pod 수준

```yaml
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001
    runAsGroup: 10001
    fsGroup: 10001                    # 볼륨의 그룹 소유권
    fsGroupChangePolicy: OnRootMismatch
    supplementalGroups: [4000]
    seccompProfile:
      type: RuntimeDefault
    sysctls:
      - name: net.core.somaxconn
        value: "1024"
```

**Pod 수준 설정은 모든 컨테이너에 상속되고, 컨테이너 수준이 우선한다.**

**`fsGroup`** 이 실무에서 자주 필요하다. 볼륨을 마운트할 때 소유권을 이 GID로 바꿔 주므로, 비루트 사용자가 쓸 수 있게 된다.

> **⚠️ `fsGroup`과 대용량 볼륨**
> `fsGroupChangePolicy` 기본값(`Always`)은 마운트할 때마다 **모든 파일의 소유권을 재귀적으로 변경**한다. 파일이 수백만 개면 Pod 시작이 몇 분씩 걸린다.
>
> `OnRootMismatch`로 바꾸면 루트 디렉터리의 소유권만 확인하고, 이미 맞으면 건너뛴다.

### readOnlyRootFilesystem의 실전 적용

이 설정을 켜면 대부분의 앱이 죽는다. 임시 파일을 쓸 곳이 없기 때문이다.

```yaml
spec:
  containers:
    - name: app
      securityContext:
        readOnlyRootFilesystem: true
      volumeMounts:
        - { name: tmp,      mountPath: /tmp }
        - { name: cache,    mountPath: /var/cache/nginx }
        - { name: run,      mountPath: /var/run }
  volumes:
    - name: tmp
      emptyDir: { sizeLimit: 100Mi }
    - name: cache
      emptyDir: {}
    - name: run
      emptyDir: {}
```

**어디에 쓰는지 찾는 법**

```bash
# 앱을 실행하고 쓰기 시도를 추적
kubectl exec <pod> -- sh -c 'ls -la /proc/1/root' 2>&1
# 또는 strace로 (권한 필요)
```

실무에서는 앱 문서를 보거나, 먼저 `false`로 띄워 `find / -newer /etc/hostname -type f` 같은 방법으로 확인한 뒤 적용한다.

### seccomp

시스템콜을 필터링한다. 리눅스에는 350개 이상의 시스템콜이 있는데, 일반 애플리케이션은 50개 정도만 쓴다. 나머지는 공격 표면일 뿐이다.

```yaml
securityContext:
  seccompProfile:
    type: RuntimeDefault      # 컨테이너 런타임의 기본 프로파일
```

`RuntimeDefault`는 containerd/CRI-O가 제공하는 프로파일로, 위험한 시스템콜(`mount`, `reboot`, `kexec_load`, `bpf` 등)을 차단한다. **오버헤드가 거의 없으므로 항상 켜자.**

**커스텀 프로파일**도 가능하다.

```yaml
securityContext:
  seccompProfile:
    type: Localhost
    localhostProfile: profiles/my-app.json
```

**Security Profiles Operator**를 쓰면 앱을 실행하며 사용하는 시스템콜을 기록해 프로파일을 자동 생성할 수 있다.

### AppArmor / SELinux

더 세밀한 강제 접근 제어(MAC)다.

```yaml
# AppArmor (v1.30+ 필드로 승격)
spec:
  securityContext:
    appArmorProfile:
      type: RuntimeDefault      # 또는 Localhost + localhostProfile
```

```yaml
# SELinux
securityContext:
  seLinuxOptions:
    level: "s0:c123,c456"
```

**Red Hat 계열(OpenShift)에서는 SELinux가 기본 활성화**되어 강력한 격리를 제공한다.

### 안전한 컨테이너 템플릿

```yaml
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001
    runAsGroup: 10001
    fsGroup: 10001
    seccompProfile:
      type: RuntimeDefault
  automountServiceAccountToken: false     # 17.4절
  containers:
    - name: app
      image: registry.example.com/app@sha256:abc...   # 다이제스트 고정
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        privileged: false
        capabilities:
          drop: ["ALL"]
      resources:                          # 14장
        requests: { cpu: 100m, memory: 128Mi }
        limits:   { memory: 512Mi }
      volumeMounts:
        - { name: tmp, mountPath: /tmp }
  volumes:
    - name: tmp
      emptyDir: { sizeLimit: 64Mi }
```

## 18.3 Pod Security Admission

### PSP의 후계

PodSecurityPolicy는 v1.25에서 제거됐다. 이유는 사용성이 나빴기 때문이다. PSP는 RBAC과 얽혀 있어 "어떤 PSP가 적용될지" 예측하기 어려웠다.

**Pod Security Admission(PSA)** 은 훨씬 단순하다. **네임스페이스 라벨 하나로 프로파일을 지정한다.**

### 세 프로파일

| 프로파일 | 내용 |
|---|---|
| `privileged` | 제한 없음 (시스템 컴포넌트용) |
| `baseline` | 알려진 권한 상승을 차단. 대부분의 앱이 수정 없이 통과 |
| `restricted` | 강력한 하드닝. 모범 사례 강제 |

**`baseline`이 금지하는 것**
- `privileged: true`
- hostNetwork, hostPID, hostIPC
- hostPath 볼륨
- 기본 외의 capability 추가 (`NET_RAW` 등 일부만 허용)
- 호스트 포트 사용
- `/proc` 마운트 타입 변경
- 위험한 sysctl

**`restricted`가 추가로 요구하는 것**
- `runAsNonRoot: true`
- `allowPrivilegeEscalation: false`
- `capabilities.drop: ["ALL"]` (`NET_BIND_SERVICE`만 추가 허용)
- `seccompProfile.type: RuntimeDefault` 또는 `Localhost`
- 허용된 볼륨 타입만 (configMap, secret, emptyDir, PVC, projected, downwardAPI, ephemeral)

### 세 가지 모드

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: production
  labels:
    # ① 강제 — 위반하면 Pod 생성 거부
    pod-security.kubernetes.io/enforce: baseline
    pod-security.kubernetes.io/enforce-version: v1.31

    # ② 경고 — kubectl 응답에 경고 표시 (생성은 됨)
    pod-security.kubernetes.io/warn: restricted
    pod-security.kubernetes.io/warn-version: v1.31

    # ③ 감사 — 감사 로그에만 기록
    pod-security.kubernetes.io/audit: restricted
    pod-security.kubernetes.io/audit-version: v1.31
```

**점진 도입 전략**이 이 설계의 핵심이다.

```
1단계: warn + audit만 설정 → 무엇이 위반인지 파악
        ↓
2단계: 위반 워크로드 수정
        ↓
3단계: enforce: baseline
        ↓
4단계: warn/audit을 restricted로
        ↓
5단계: enforce: restricted
```

**한 번에 강제하면 배포가 전부 실패한다.** 반드시 경고 단계를 거친다.

### 클러스터 기본값

```yaml
# AdmissionConfiguration
apiVersion: apiserver.config.k8s.io/v1
kind: AdmissionConfiguration
plugins:
  - name: PodSecurity
    configuration:
      apiVersion: pod-security.admission.config.k8s.io/v1
      kind: PodSecurityConfiguration
      defaults:
        enforce: baseline
        enforce-version: latest
        warn: restricted
        audit: restricted
      exemptions:
        namespaces: [kube-system]
        runtimeClasses: []
        usernames: []
```

**모든 네임스페이스에 기본 적용**하고, 예외만 라벨로 완화하는 방식이다.

### 실습: PSA 적용

```bash
# ① 네임스페이스에 restricted 강제
kubectl create namespace secure-ns
kubectl label namespace secure-ns \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/enforce-version=latest

# ② 평범한 Pod 시도 → 거부된다
kubectl run nginx -n secure-ns --image=nginx:alpine
```

```
Error from server (Forbidden): pods "nginx" is forbidden:
violates PodSecurity "restricted:latest":
  allowPrivilegeEscalation != false (container "nginx" must set ...),
  unrestricted capabilities (container "nginx" must set securityContext.capabilities.drop=["ALL"]),
  runAsNonRoot != true,
  seccompProfile (pod or container must set securityContext.seccompProfile.type to "RuntimeDefault" or "Localhost")
```

**에러 메시지가 정확히 무엇을 고쳐야 하는지 알려 준다.**

```yaml
# ③ 준수하는 Pod
apiVersion: v1
kind: Pod
metadata:
  name: compliant
  namespace: secure-ns
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: app
      image: nginxinc/nginx-unprivileged:alpine     # 비루트 이미지
      securityContext:
        allowPrivilegeEscalation: false
        capabilities:
          drop: ["ALL"]
      volumeMounts:
        - { name: tmp, mountPath: /tmp }
  volumes:
    - name: tmp
      emptyDir: {}
```

```bash
kubectl apply -f compliant.yaml
kubectl get pod compliant -n secure-ns
```

```bash
# ④ 경고 모드 체험
kubectl label namespace default pod-security.kubernetes.io/warn=restricted
kubectl run test --image=nginx:alpine
# Warning: would violate PodSecurity "restricted:latest": ...
# pod/test created                                    ← 생성은 된다
```

```bash
# ⑤ 정리
kubectl delete namespace secure-ns
kubectl label namespace default pod-security.kubernetes.io/warn-
kubectl delete pod test --ignore-not-found
```

### 샌드박스 런타임

2.1절과 13.5절에서 언급한 하드 멀티테넌시의 답이다.

```yaml
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: gvisor
handler: runsc
---
apiVersion: v1
kind: Pod
spec:
  runtimeClassName: gvisor        # ★ 이 Pod만 샌드박스에서
  containers:
    - name: untrusted
      image: user-submitted:latest
```

| 런타임 | 방식 | 오버헤드 |
|---|---|---|
| **gVisor** (`runsc`) | 사용자 공간 커널이 시스템콜 가로챔 | 시스템콜 집약적 작업에서 20~50% |
| **Kata Containers** | 컨테이너당 경량 VM | 메모리 ~50MB, 시작 시간 증가 |
| **Firecracker** | 마이크로 VM (AWS Lambda/Fargate) | 낮음 |

**신뢰할 수 없는 코드를 실행한다면 비용을 감수할 가치가 있다.**

## 18.4 NetworkPolicy

### 기본은 전부 허용

9장에서 본 대로, 쿠버네티스의 기본 네트워크 모델은 **모든 Pod가 모든 Pod와 통신 가능**이다. NetworkPolicy는 이것을 제한한다.

> **⚠️ CNI가 지원해야 동작한다**
> NetworkPolicy 오브젝트를 만들어도 **CNI 플러그인이 구현하지 않으면 아무 일도 일어나지 않는다.** 조용히 무시된다.
>
> | CNI | NetworkPolicy 지원 |
> |---|---|
> | Calico, Cilium, Antrea, Weave | ✅ |
> | AWS VPC CNI | ✅ (v1.14+) |
> | Flannel | ❌ |
> | kindnet (kind 기본) | ❌ |
>
> **실습하려면 Calico를 설치해야 한다.**

### 기본 구조

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-policy
  namespace: production
spec:
  podSelector:                        # 이 정책이 적용될 Pod
    matchLabels:
      app: api
  policyTypes: [Ingress, Egress]

  ingress:
    - from:
        - podSelector:                # 같은 네임스페이스의 Pod
            matchLabels:
              app: frontend
        - namespaceSelector:          # 다른 네임스페이스 전체
            matchLabels:
              team: platform
        - ipBlock:                    # IP 대역
            cidr: 10.0.0.0/8
            except: [10.0.5.0/24]
      ports:
        - protocol: TCP
          port: 8080

  egress:
    - to:
        - podSelector:
            matchLabels:
              app: database
      ports:
        - { protocol: TCP, port: 5432 }
```

### 핵심 규칙 세 가지

**① 정책이 하나라도 적용되면 그 Pod는 "기본 거부"가 된다**

```
Pod에 적용되는 NetworkPolicy가 없다 → 전부 허용
Pod에 Ingress 정책이 하나라도 있다 → 명시된 것 외 전부 거부
```

**② 정책은 누적된다(OR)**

여러 정책이 같은 Pod에 적용되면 **합집합**이다. 거부 규칙은 없고 허용 규칙만 있다.

**③ `podSelector`와 `namespaceSelector`의 조합이 헷갈린다**

```yaml
# ① OR — 리스트의 각 항목은 별개
from:
  - podSelector:
      matchLabels: { app: frontend }
  - namespaceSelector:
      matchLabels: { team: platform }
# 의미: (같은 NS의 app=frontend) 또는 (team=platform NS의 모든 Pod)

# ② AND — 한 항목 안에 둘 다
from:
  - namespaceSelector:
      matchLabels: { team: platform }
    podSelector:
      matchLabels: { app: frontend }
# 의미: team=platform 네임스페이스의 app=frontend Pod만
```

**하이픈(`-`)의 위치가 의미를 완전히 바꾼다.** 실무에서 가장 흔한 실수다.

### 기본 거부 정책

```yaml
# 모든 Ingress 거부
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: production
spec:
  podSelector: {}                    # 모든 Pod
  policyTypes: [Ingress]
  # ingress 규칙 없음 = 전부 거부
---
# 모든 Egress 거부
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-egress
  namespace: production
spec:
  podSelector: {}
  policyTypes: [Egress]
```

> **⚠️ DNS를 반드시 열어야 한다**
> 10.6절에서 경고한 그 함정이다. Egress를 막으면 DNS도 막힌다. **NetworkPolicy 적용 후 모든 것이 깨지는 사고의 대부분이 이것이다.**
>
> ```yaml
> apiVersion: networking.k8s.io/v1
> kind: NetworkPolicy
> metadata:
>   name: allow-dns
>   namespace: production
> spec:
>   podSelector: {}
>   policyTypes: [Egress]
>   egress:
>     - to:
>         - namespaceSelector:
>             matchLabels:
>               kubernetes.io/metadata.name: kube-system
>           podSelector:
>             matchLabels:
>               k8s-app: kube-dns
>       ports:
>         - { protocol: UDP, port: 53 }
>         - { protocol: TCP, port: 53 }
> ```

### 메타데이터 서비스 차단

18.1절에서 본 IMDS 접근을 막는다.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-external-except-metadata
  namespace: production
```

### 티어별 정책 예제

3계층 애플리케이션의 전형적 구성이다.

```yaml
# frontend: 인그레스에서만 받고, backend로만 나간다
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: frontend, namespace: shop }
spec:
  podSelector: { matchLabels: { tier: frontend } }
  policyTypes: [Ingress, Egress]
  ingress:
    - from:
        - namespaceSelector:
            matchLabels: { kubernetes.io/metadata.name: ingress-nginx }
      ports: [{ protocol: TCP, port: 8080 }]
  egress:
    - to:
        - podSelector: { matchLabels: { tier: backend } }
      ports: [{ protocol: TCP, port: 8080 }]
    - to:                                        # DNS
        - namespaceSelector:
            matchLabels: { kubernetes.io/metadata.name: kube-system }
      ports: [{ protocol: UDP, port: 53 }]
---
# backend: frontend에서만 받고, database로만 나간다
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: backend, namespace: shop }
spec:
  podSelector: { matchLabels: { tier: backend } }
  policyTypes: [Ingress, Egress]
  ingress:
    - from:
        - podSelector: { matchLabels: { tier: frontend } }
      ports: [{ protocol: TCP, port: 8080 }]
  egress:
    - to:
        - podSelector: { matchLabels: { tier: database } }
      ports: [{ protocol: TCP, port: 5432 }]
    - to:
        - namespaceSelector:
            matchLabels: { kubernetes.io/metadata.name: kube-system }
      ports: [{ protocol: UDP, port: 53 }]
---
# database: backend에서만 받고, 나가는 것 없음
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: database, namespace: shop }
spec:
  podSelector: { matchLabels: { tier: database } }
  policyTypes: [Ingress, Egress]
  ingress:
    - from:
        - podSelector: { matchLabels: { tier: backend } }
      ports: [{ protocol: TCP, port: 5432 }]
  egress: []                                     # 아무 데도 못 나간다
```

### 표준 NetworkPolicy의 한계

- **L3/L4만.** HTTP 경로나 메서드로 제어할 수 없다
- **거부 규칙이 없다.** 허용만 있고 우선순위도 없다
- **클러스터 전역 정책이 없다.** 네임스페이스마다 만들어야 한다
- **egress에 도메인 이름을 쓸 수 없다.** IP만 가능

**CNI별 확장**이 이를 보완한다.

```yaml
# Cilium: L7 정책
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
spec:
  endpointSelector:
    matchLabels: { app: api }
  ingress:
    - fromEndpoints:
        - matchLabels: { app: frontend }
      toPorts:
        - ports: [{ port: "8080", protocol: TCP }]
          rules:
            http:
              - method: "GET"
                path: "/api/v1/.*"
  egress:
    - toFQDNs:                              # ★ 도메인 기반
        - matchName: "api.stripe.com"
```

Calico의 `GlobalNetworkPolicy`는 클러스터 전역 정책과 거부 규칙, 우선순위를 지원한다.

## 18.5 이미지 공급망 보안

### 세 단계

```
① 스캐닝   — 취약점이 있는가?
② 서명     — 정말 우리가 만든 것인가?
③ 검증     — 서명되지 않은 이미지는 거부
```

### 스캐닝

```bash

trivy image --exit-code 1 --severity CRITICAL myapp:1.0    # CI에서 게이트

# 클러스터 전체 스캔
trivy k8s --report summary cluster
```

**CI 파이프라인에 넣는다**(30장).

**취약점을 줄이는 근본 대책은 이미지를 작게 만드는 것이다**(2.2절). distroless 이미지는 셸도 패키지 매니저도 없어 CVE가 거의 없다.

### SBOM (Software Bill of Materials)

이미지에 무엇이 들어 있는지의 명세다.

```bash
syft myapp:1.0 -o spdx-json > sbom.json
grype sbom:sbom.json                      # SBOM으로 취약점 검사
```

새 CVE가 공개됐을 때 **"우리 이미지 중 영향받는 것이 무엇인가"** 를 즉시 답할 수 있게 된다. Log4Shell 같은 사건에서 결정적 차이를 만든다.

### 서명 — Sigstore/Cosign

```bash
# 키 없이 서명 (OIDC 기반, 권장)
COSIGN_EXPERIMENTAL=1 cosign sign registry.example.com/myapp:1.0

# 검증
cosign verify registry.example.com/myapp:1.0 \
  --certificate-identity-regexp="https://github.com/myorg/.*" \
  --certificate-oidc-issuer="https://token.actions.githubusercontent.com"
```

**키리스 서명**이 인상적이다. 장기 키를 관리하지 않고, CI의 OIDC 신원으로 단기 인증서를 발급받아 서명한다. 서명 기록은 투명성 로그(Rekor)에 남는다.

**증명(attestation)** 도 붙일 수 있다.
```bash
cosign attest --predicate sbom.json --type spdxjson myapp:1.0
```

### 검증 — 어드미션에서 차단

**Kyverno**로 서명되지 않은 이미지를 거부한다.

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: verify-image-signature
spec:
  validationFailureAction: Enforce
  rules:
    - name: verify-signature
      match:
        any:
          - resources:
              kinds: [Pod]
      verifyImages:
        - imageReferences: ["registry.example.com/*"]
          attestors:
            - entries:
                - keyless:
                    subject: "https://github.com/myorg/*"
                    issuer: "https://token.actions.githubusercontent.com"
```

**Sigstore Policy Controller**나 **Connaisseur**도 같은 역할을 한다.

## 18.6 정책 엔진

### 왜 필요한가

PSA는 Pod 보안만 다룬다. 조직에는 더 많은 규칙이 있다.

- 모든 리소스에 `team` 라벨이 있어야 한다
- `latest` 태그 금지
- Ingress 호스트는 승인된 도메인만
- 프로덕션 네임스페이스의 Deployment는 replicas ≥ 2
- PDB가 없는 Deployment 금지

**ValidatingAdmissionPolicy(CEL)** 로 단순한 것은 처리할 수 있지만(17.5절), 복잡한 정책이나 리소스 생성·변형은 정책 엔진이 낫다.

### Kyverno

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: require-labels
spec:
  validationFailureAction: Enforce
  background: true                    # 기존 리소스도 검사
  rules:
    # ① 검증
    - name: check-team-label
      match:
        any:
          - resources:
              kinds: [Deployment, StatefulSet, DaemonSet]
      exclude:
        any:
          - resources:
              namespaces: [kube-system, kyverno]
      validate:
        message: "team 라벨이 필요합니다"
        pattern:
          metadata:
            labels:
              team: "?*"

    # ② 변형 — 기본값 주입
    - name: add-default-securityContext
      match:
        any: [{ resources: { kinds: [Pod] } }]
      mutate:
        patchStrategicMerge:
          spec:
            securityContext:
              +(runAsNonRoot): true
              +(seccompProfile):
                type: RuntimeDefault

    # ③ 생성 — 관련 리소스 자동 생성
    - name: create-default-netpol
      match:
        any: [{ resources: { kinds: [Namespace] } }]
      generate:
        apiVersion: networking.k8s.io/v1
        kind: NetworkPolicy
        name: default-deny-ingress
        namespace: "{{request.object.metadata.name}}"
        synchronize: true
        data:
          spec:
            podSelector: {}
            policyTypes: [Ingress]
```

**Kyverno의 강점은 세 가지 동작(validate/mutate/generate)을 모두 YAML로 표현한다**는 것이다. 새 네임스페이스가 만들어질 때 기본 NetworkPolicy를 자동 생성하는 것 같은 일을 쉽게 할 수 있다.

### OPA Gatekeeper

Rego 언어를 쓴다. 표현력이 높지만 학습 곡선이 있다.

```yaml
apiVersion: templates.gatekeeper.sh/v1
kind: ConstraintTemplate
metadata:
  name: k8srequiredlabels
spec:
  crd:
    spec:
      names: { kind: K8sRequiredLabels }
      validation:
        openAPIV3Schema:
          properties:
            labels: { type: array, items: { type: string } }
  targets:
    - target: admission.k8s.gatekeeper.sh
      rego: |
        package k8srequiredlabels
        violation[{"msg": msg}] {
          required := input.parameters.labels[_]
          not input.review.object.metadata.labels[required]
          msg := sprintf("라벨 '%v'가 필요합니다", [required])
        }
---
apiVersion: constraints.gatekeeper.sh/v1beta1
kind: K8sRequiredLabels
metadata:
  name: require-team-label
spec:
  match:
    kinds: [{ apiGroups: ["apps"], kinds: ["Deployment"] }]
  parameters:
    labels: ["team", "cost-center"]
```

### 선택과 도입

| | Kyverno | OPA Gatekeeper | ValidatingAdmissionPolicy |
|---|---|---|---|
| 언어 | YAML | Rego | CEL |
| 학습 곡선 | 낮음 | 높음 | 중간 |
| 변형(mutate) | ✅ | ✅ (v3.10+) | 알파 |
| 생성(generate) | ✅ | ❌ | ❌ |
| 외부 데이터 조회 | ✅ | ✅ | ❌ |
| 별도 서버 | 필요 | 필요 | **불필요** |

**도입 순서 권장**
1. 단순한 규칙은 **ValidatingAdmissionPolicy**로 (서버 불필요)
2. 변형·생성이 필요하면 **Kyverno**
3. 이미 Rego 자산이 있거나 매우 복잡한 정책은 **Gatekeeper**

**모든 정책 엔진은 `Audit`/`Warn` 모드로 먼저 도입한다.** 17.5절에서 말한 웹훅 가용성 위험도 잊지 말자.

## 18.7 런타임 보안과 감사

### 감사 로그

API 서버의 모든 요청을 기록한다.

```yaml
# audit-policy.yaml
apiVersion: audit.k8s.io/v1
kind: Policy
omitStages: ["RequestReceived"]
rules:
  # 시크릿은 메타데이터만 (내용 노출 방지)
  - level: Metadata
    resources:
      - group: ""
        resources: ["secrets", "configmaps"]

  # exec, attach는 전체 기록
  - level: RequestResponse
    resources:
      - group: ""
        resources: ["pods/exec", "pods/attach", "pods/portforward"]

  # RBAC 변경은 전체 기록
  - level: RequestResponse
    resources:
      - group: "rbac.authorization.k8s.io"

  # 읽기는 무시 (양이 너무 많다)
  - level: None
    verbs: ["get", "list", "watch"]

  - level: Metadata
```

```yaml
# kube-apiserver 플래그
--audit-policy-file=/etc/kubernetes/audit-policy.yaml
--audit-log-path=/var/log/kubernetes/audit.log
--audit-log-maxage=30
--audit-log-maxbackup=10
--audit-log-maxsize=100
```

**31장에서 이 로그를 중앙 시스템으로 보내 분석한다.**

### 런타임 위협 탐지 — Falco

eBPF로 시스템콜을 관찰해 이상 행위를 탐지한다.

```yaml
- rule: Terminal shell in container
  desc: 컨테이너에서 셸이 실행됨
  condition: >
    spawned_process and container
    and shell_procs and proc.tty != 0
  output: >
    Shell spawned in container
    (user=%user.name container=%container.name
     shell=%proc.name parent=%proc.pname)
  priority: WARNING

- rule: Write below etc
  desc: /etc 아래 파일 쓰기
  condition: >
    open_write and container and fd.name startswith /etc
  output: "File below /etc opened for writing (file=%fd.name)"
  priority: ERROR
```

**탐지 예시**
- 컨테이너에서 셸 실행
- 민감한 파일 읽기 (`/etc/shadow`)
- 예상치 못한 아웃바운드 연결
- 특권 컨테이너 시작
- 패키지 매니저 실행

**Tetragon**(Cilium)도 eBPF 기반으로 유사한 기능을 제공하며, 탐지뿐 아니라 **차단**도 가능하다.

## 실습 과제

**과제 1 — 노드 탈출 재현**
`privileged: true`와 `hostPath: /`를 쓰는 Pod를 만들어 노드의 파일 시스템에 접근하고, `chroot`로 노드 루트 셸을 얻어 본다. (**실습 클러스터에서만**) 그다음 PSA `baseline`을 적용해 이 Pod가 거부되는 것을 확인한다.

**과제 2 — restricted 프로파일 통과시키기**
평범한 nginx Deployment를 `restricted` 네임스페이스에 배포하고, 에러 메시지를 하나씩 해결해 가며 통과시킨다. 어떤 필드가 필요한지, 왜 비루트 이미지가 필요한지 체험한다.

**과제 3 — NetworkPolicy AND/OR 검증**
`podSelector`와 `namespaceSelector`를 ① 별도 항목(OR)과 ② 한 항목(AND)으로 각각 구성하고, 세 개의 네임스페이스에서 통신을 시도해 차이를 확인한다.

**과제 4 — 메타데이터 서비스 차단**
클라우드 클러스터가 있다면 Pod에서 IMDS에 접근되는 것을 확인하고, NetworkPolicy로 차단한 뒤 다시 시도한다. (없다면 임의의 외부 IP로 대체해 실험한다.)

**과제 5 — 이미지 서명 파이프라인**
로컬 이미지를 cosign으로 서명하고, Kyverno 정책으로 미서명 이미지를 차단한다. 서명된 이미지와 서명되지 않은 이미지를 각각 배포해 결과를 비교한다.

## 요약

- 보안 설계의 질문은 "뚫리지 않게"가 아니라 **"침해되면 어디까지 번지는가"**(블래스트 레이디어스)다. 컨테이너 → Pod → 노드 → 네트워크 → API → 클라우드 각 층에서 반경을 좁힌다.
- **클라우드 메타데이터 서비스(169.254.169.254)** 는 잊기 쉬운 탈출 경로다. IMDSv2 + hop limit 1, 워크로드 아이덴티티, NetworkPolicy로 막는다.
- `securityContext`의 핵심 다섯 가지: **`runAsNonRoot`, `allowPrivilegeEscalation: false`, `readOnlyRootFilesystem`, `capabilities.drop: ALL`, `seccompProfile: RuntimeDefault`**. `privileged: true`는 사실상 노드 root다.
- **Pod Security Admission**은 네임스페이스 라벨로 `privileged`/`baseline`/`restricted` 프로파일을 적용한다. `warn`/`audit`으로 먼저 관찰하고 `enforce`로 넘어가는 **점진 도입이 필수**다.
- **NetworkPolicy는 CNI가 지원해야 동작한다.** kindnet과 Flannel은 지원하지 않는다. 정책이 하나라도 적용되면 그 Pod는 기본 거부가 되며, **DNS 예외를 빠뜨리면 모든 것이 깨진다.**
- `podSelector`와 `namespaceSelector`가 **별도 항목이면 OR, 한 항목이면 AND**다. 하이픈 위치가 의미를 바꾼다.
- 공급망 보안은 **스캐닝(Trivy) → 서명(Cosign 키리스) → 검증(어드미션)** 세 단계다. SBOM을 남겨 두면 새 CVE 공개 시 영향 범위를 즉시 답할 수 있다.
- 정책 엔진은 단순한 규칙에는 **ValidatingAdmissionPolicy**(서버 불필요), 변형·생성이 필요하면 **Kyverno**, 복잡한 로직은 **Gatekeeper**를 쓴다. 모두 `Audit`/`Warn`으로 먼저 도입한다.

**4부를 마치며** — 이제 여러 팀이 하나의 클러스터를 안전하고 효율적으로 나눠 쓸 수 있다. 5부에서는 지금까지 "이렇게 동작한다"고 설명한 것들의 **내부를 직접 열어 본다.** Pod를 리눅스 프리미티브로 밑바닥부터 만들고, kubelet과 컨트롤 플레인의 코드 경로를 따라가고, etcd와 CNI를 해부한다.
