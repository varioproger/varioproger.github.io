# 32장. 클러스터 라이프사이클과 장애 대응

> **학습목표**
> - 고가용성 컨트롤 플레인을 설계하고 장애 도메인을 분산할 수 있다.
> - 버전 스큐 정책을 이해하고 무중단 업그레이드를 수행할 수 있다.
> - PodDisruptionBudget으로 노드 유지보수를 안전하게 만들 수 있다.
> - 백업과 재해 복구 절차를 수립하고 RTO/RPO를 산정할 수 있다.
> - 증상에서 원인으로 좁혀 가는 트러블슈팅 플레이북을 사용할 수 있다.
> - 비용을 측정하고 최적화할 수 있다.

이 책의 마지막 장이다.

## 32.1 고가용성 설계

### 장애 도메인 분리

```
리전 (Region)
 ├── 가용 영역 A (AZ)
 │    ├── 컨트롤 플레인 1
 │    └── 워커 노드들
 ├── 가용 영역 B
 │    ├── 컨트롤 플레인 2
 │    └── 워커 노드들
 └── 가용 영역 C
      ├── 컨트롤 플레인 3
      └── 워커 노드들
```

**22.4절에서 본 대로 etcd 멤버는 3개 AZ에 하나씩** 배치한다. AZ 하나가 죽어도 쿼럼(2/3)이 유지된다.

### 컨트롤 플레인 구성

```
                    로드밸런서 (API 서버 앞단)
                            │
        ┌───────────────────┼───────────────────┐
        ▼                   ▼                   ▼
   ┌─────────┐        ┌─────────┐         ┌─────────┐
   │ CP-1    │        │ CP-2    │         │ CP-3    │
   │ apiserver│       │ apiserver│        │ apiserver│  ← 모두 활성
   │ scheduler│       │ scheduler│        │ scheduler│  ← 리더 선출 (21.4절)
   │ ctrl-mgr │       │ ctrl-mgr │        │ ctrl-mgr │  ← 리더 선출
   │ etcd     │       │ etcd     │        │ etcd     │  ← Raft (22.2절)
   └─────────┘        └─────────┘         └─────────┘
```

**API 서버는 무상태**이므로 모두 활성이다. **scheduler와 controller-manager는 리더 선출**로 하나만 활성이다.

**적층형(stacked) vs 외부(external) etcd**

| | 적층형 | 외부 |
|---|---|---|
| 배치 | 컨트롤 플레인 노드에 etcd 함께 | etcd 전용 노드 |
| 노드 수 | 3 | 3(CP) + 3(etcd) = 6 |
| 장애 영향 | 노드 하나가 죽으면 CP + etcd 멤버 동시 상실 | 독립적 |
| 운영 복잡도 | 낮음 | 높음 |
| 권장 | 대부분 | 대규모, 엄격한 격리 요구 |

**매니지드 서비스는 이것을 신경 쓸 필요가 없다**(29장). 자체 구축 시에만 결정한다.

### 워커 노드 분산

15.5절의 토폴로지 분산 제약을 프로덕션 워크로드에 반드시 적용한다.

```yaml
spec:
  replicas: 6
  template:
    spec:
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: ScheduleAnyway
          labelSelector:
            matchLabels: { app: web }
          matchLabelKeys: [pod-template-hash]
        - maxSkew: 2
          topologyKey: kubernetes.io/hostname
          whenUnsatisfiable: ScheduleAnyway
          labelSelector:
            matchLabels: { app: web }
```

**AZ 간 균등 + 노드 간 분산.** AZ 하나가 죽어도 2/3의 용량이 남는다.

### 용량 계획

```
정상 운영에 필요한 용량 = C
AZ 하나 장애 시 남는 용량 = C × 2/3

→ AZ 장애를 견디려면 전체 용량을 1.5C 이상으로

노드 하나 장애도 고려하면
→ N+1 또는 N+2 여유
```

**Cluster Autoscaler가 있어도 즉시 반응하지 않는다**(16.6절의 2~7분 지연). 오버프로비저닝 Pod로 여유 노드를 확보해 두는 것이 안전하다.

## 32.2 버전 스큐와 업그레이드

### 버전 스큐 정책

```
kube-apiserver          n           ← 기준
kube-controller-manager n, n-1      (HA에서는 n-1까지)
kube-scheduler          n, n-1
kubelet                 n ~ n-3     ★ 3 마이너 버전까지 뒤처져도 됨
kube-proxy              kubelet과 같은 규칙
kubectl                 n+1 ~ n-1
```

**핵심 규칙**

- **컨트롤 플레인을 먼저, 노드를 나중에** 올린다
- **kubelet이 API 서버보다 앞설 수 없다**
- **마이너 버전을 건너뛰지 않는다**: 1.29 → 1.30 → 1.31 (1.29 → 1.31 불가)

```bash
kubectl version
kubectl get nodes -o wide      # KERNEL-VERSION, KUBELET-VERSION 열
```

### 업그레이드 전 점검

```bash
# ① 폐기 예정 API 사용 확인 (4.1절)
kubectl get --raw /metrics | grep apiserver_requested_deprecated_apis

# ② 매니페스트 정적 검사
pluto detect-files -d ./manifests/
pluto detect-helm --target-versions k8s=v1.31.0

# ③ 클러스터의 실제 리소스 검사
kubectl get --raw '/apis/apiregistration.k8s.io/v1/apiservices' | jq -r '.items[] | select(.status.conditions[]?.status=="False") | .metadata.name'

# ④ 릴리스 노트 확인 — CHANGELOG의 "Urgent Upgrade Notes"
```

> **⚠️ 반드시 릴리스 노트를 읽어라**
> 각 릴리스의 **"Urgent Upgrade Notes"** 섹션에 파괴적 변경이 정리되어 있다. v1.24의 dockershim 제거(2.5절), v1.25의 PodSecurityPolicy 제거(18.3절) 같은 것이 여기 있었다.

### 업그레이드 순서

```
① 백업 (22.7절)
   · etcd 스냅샷
   · Velero로 오브젝트 + 볼륨 (12.6절)
        ↓
② 컨트롤 플레인 (한 노드씩)
   · CP-1 업그레이드 → 검증
   · CP-2 업그레이드 → 검증
   · CP-3 업그레이드 → 검증
        ↓
③ 애드온
   · CNI, CoreDNS, kube-proxy, CSI 드라이버
   · 버전 호환성 매트릭스 확인
        ↓
④ 워커 노드 (배치 단위로)
   · cordon → drain → 업그레이드 → uncordon
        ↓
⑤ 검증
   · 모든 워크로드 정상 동작
   · 관측성 대시보드 확인 (31장)
```

### kubeadm 업그레이드

```bash
# ── 첫 번째 컨트롤 플레인 노드 ──
apt-mark unhold kubeadm && apt-get update
apt-get install -y kubeadm=1.31.0-1.1
apt-mark hold kubeadm

kubeadm upgrade plan               # 계획 확인
kubeadm upgrade apply v1.31.0

# kubelet과 kubectl
apt-mark unhold kubelet kubectl
apt-get install -y kubelet=1.31.0-1.1 kubectl=1.31.0-1.1
apt-mark hold kubelet kubectl
systemctl daemon-reload && systemctl restart kubelet

# ── 나머지 컨트롤 플레인 노드 ──
kubeadm upgrade node              # apply가 아니라 node

# ── 워커 노드 ──
kubectl drain <node> --ignore-daemonsets --delete-emptydir-data --timeout=300s
# 노드에서:
kubeadm upgrade node
apt-get install -y kubelet=1.31.0-1.1
systemctl daemon-reload && systemctl restart kubelet
# 다시:
kubectl uncordon <node>
```

**인증서 갱신**(21.6절)이 `kubeadm upgrade apply` 시 자동으로 이루어진다. 이것이 **1년에 한 번 이상 업그레이드해야 하는 이유**다.

### 매니지드 업그레이드

```bash
# GKE — 릴리스 채널에 맡기거나 수동
gcloud container clusters upgrade prod --master --cluster-version 1.31.1
gcloud container clusters upgrade prod --node-pool general

# EKS
eksctl upgrade cluster --name prod --version 1.31 --approve
eksctl upgrade nodegroup --cluster prod --name general
# 애드온도 별도로
eksctl update addon --cluster prod --name vpc-cni --version latest

# AKS
az aks upgrade -g prod-rg -n prod --kubernetes-version 1.31.1
az aks nodepool upgrade -g prod-rg --cluster-name prod -n general
```

**노드 업그레이드 전략**

| 전략 | 동작 | 특징 |
|---|---|---|
| **서지(surge)** | 새 노드를 먼저 추가하고 옮긴 뒤 옛 노드 제거 | 용량 유지. **권장** |
| **인플레이스** | 드레인 후 그 자리에서 업그레이드 | 용량 일시 감소 |
| **블루-그린 노드 풀** | 새 노드 풀 생성 → 워크로드 이동 → 옛 풀 삭제 | 가장 안전. 롤백 쉬움 |

```bash
# GKE 서지 업그레이드 설정
gcloud container node-pools update general --cluster prod \
  --max-surge-upgrade 2 --max-unavailable-upgrade 0
```

**`max-unavailable-upgrade 0`이 8.2절의 `maxUnavailable: 0`과 같은 원리다.**

### 업그레이드 테스트

```
① 개발 클러스터에서 먼저
② 스테이징에서 실제 워크로드로
③ 프로덕션 (가능하면 카나리 노드 풀부터)
```

**환경을 클러스터로 분리한 이유**(13.5절)가 여기서 드러난다. 같은 클러스터에 dev와 prod가 있으면 업그레이드를 먼저 시험할 곳이 없다.

## 32.3 노드 유지보수와 PDB

### drain의 동작

```bash
kubectl cordon <node>       # 새 Pod 스케줄 금지 (테인트 추가, 15.4절)
kubectl drain <node> \
  --ignore-daemonsets \     # DaemonSet Pod는 축출 불가 (8.4절)
  --delete-emptydir-data \  # emptyDir 데이터 손실 감수 (12.1절)
  --timeout=300s \
  --grace-period=30
kubectl uncordon <node>
```

**drain이 하는 일**

```
① 노드에 unschedulable 테인트 추가
② 각 Pod에 대해 Eviction API 호출
        ↓
③ API 서버가 PDB를 확인
   · 허용 → Pod 삭제 (graceful termination, 6.4절)
   · 위반 → 429 반환, kubectl이 재시도
        ↓
④ 모든 Pod가 축출될 때까지 반복
```

### PodDisruptionBudget

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-pdb
spec:
  maxUnavailable: 1          # 또는 minAvailable
  selector:
    matchLabels: { app: web }
  unhealthyPodEvictionPolicy: AlwaysAllow    # v1.27+
```

> **⚠️ `minAvailable`과 `maxUnavailable` 중 무엇을 쓸 것인가**
>
> ```yaml
> replicas: 3
> minAvailable: 3        # ❌ 하나도 축출할 수 없다 → drain이 영원히 멈춘다
> minAvailable: 2        # ✅
> maxUnavailable: 1      # ✅ replicas가 변해도 안전
> ```
>
> **HPA와 함께 쓴다면 `maxUnavailable`이 낫다.** replicas가 오르내려도 의미가 유지된다.

> **⚠️ PDB는 kubelet의 축출을 막지 못한다**
> 14.4절에서 말한 대로, PDB는 **자발적 중단**(drain, 오토스케일러의 노드 제거)만 제어한다. 노드 자원 부족으로 kubelet이 축출하는 것은 **비자발적 중단**이라 PDB를 무시한다.

**`unhealthyPodEvictionPolicy`** (v1.27+)가 중요한 개선이다.

```
IfHealthyBudget (기본)
  → Ready가 아닌 Pod도 PDB 예산을 소비한다
  → 이미 깨진 Pod 때문에 drain이 막히는 문제

AlwaysAllow
  → Ready가 아닌 Pod는 언제든 축출 가능
  → 장애 상황에서 drain이 진행된다
```

**대부분의 경우 `AlwaysAllow`가 낫다.**

### drain이 멈출 때

```bash
kubectl drain <node> --ignore-daemonsets
# error: cannot evict pod as it would violate the pod's disruption budget
```

**진단**

```bash
# PDB 상태 확인
kubectl get pdb -A
```
```
NAME      MIN AVAILABLE   MAX UNAVAILABLE   ALLOWED DISRUPTIONS   AGE
web-pdb   2               N/A               0                     5d
```

**`ALLOWED DISRUPTIONS: 0`이면 막힌 것이다.**

**원인별 대응**

| 원인 | 대응 |
|---|---|
| replicas가 minAvailable과 같다 | replicas를 늘리거나 PDB 조정 |
| Pod가 Ready가 아니다 | `unhealthyPodEvictionPolicy: AlwaysAllow` |
| 다른 노드에 배치할 곳이 없다 | 노드 추가, 어피니티 완화 |
| 컨트롤러 없는 Pod (kind: Pod) | 수동 삭제 필요 |
| StatefulSet의 마지막 replica | 계획된 다운타임 필요 |

**최후의 수단**

```bash
kubectl drain <node> --ignore-daemonsets --disable-eviction    # PDB 무시
kubectl delete pod <pod> --force --grace-period=0              # 강제
```

**StatefulSet에는 `--force`를 쓰지 마라**(5.7절). 같은 ID의 Pod가 둘 실행되는 스플릿 브레인이 생길 수 있다.

### 안전한 유지보수 절차

```
① 사전 확인
   □ PDB가 모든 중요 워크로드에 있는가
   □ ALLOWED DISRUPTIONS > 0 인가
   □ 다른 노드에 여유 용량이 있는가
   □ StatefulSet의 상태 (프라이머리 위치)
        ↓
② cordon (즉시 반영)
        ↓
③ drain (--timeout 설정)
        ↓
④ 유지보수 작업
        ↓
⑤ uncordon
        ↓
⑥ 워크로드가 돌아왔는지 확인
   kubectl get pods -o wide | grep <node>
```

## 32.4 백업과 재해 복구

### 무엇을 백업하는가

```
① etcd (22.7절)
   · 모든 쿠버네티스 오브젝트
   · 클러스터 재구축 시 필요
   · 볼륨 데이터는 포함되지 않는다 ★

② 오브젝트 + 볼륨 (Velero, 12.6절)
   · 네임스페이스 단위 복원
   · 클러스터 간 마이그레이션
   · 볼륨 스냅샷 포함

③ 애플리케이션 데이터
   · DB 논리 백업 (pg_dump 등)
   · 오브젝트 스토리지
   · 가장 신뢰할 수 있는 마지막 방어선

④ 클러스터 정의
   · Terraform/Crossplane 상태 (29.7절)
   · GitOps 저장소 (30.4절)
   · 이것이 있으면 클러스터를 재구축할 수 있다 ★
```

> **GitOps가 최고의 백업이다**
> 30.4절의 config-repo에 모든 매니페스트가 있으면, **클러스터를 새로 만들고 Argo CD를 심으면 전체가 복원된다.** etcd 복원보다 깨끗하고 검증 가능하다.
>
> etcd 백업은 GitOps로 관리되지 않는 것(사람이 만든 리소스, 오퍼레이터가 생성한 상태)을 위한 보완재로 본다.

### RTO와 RPO

```
RPO (Recovery Point Objective)  얼마나 오래된 데이터까지 잃어도 되나
RTO (Recovery Time Objective)   얼마 만에 복구해야 하나
```

| 시나리오 | RPO | RTO | 방법 |
|---|---|---|---|
| Pod 장애 | 0 | 초 | 컨트롤러 자동 복구 (8장) |
| 노드 장애 | 0 | 분 | 스케줄러 재배치 (15장) |
| AZ 장애 | 0 | 분 | 멀티 AZ 분산 (32.1절) |
| 네임스페이스 실수 삭제 | 백업 주기 | 10~30분 | Velero 복원 |
| 클러스터 손상 | 백업 주기 | 1~4시간 | 재구축 + GitOps |
| 리전 장애 | 복제 지연 | 수 시간 | DR 리전 |

**백업 주기가 곧 RPO다.** 6시간마다 백업하면 최대 6시간의 데이터를 잃을 수 있다.

### DR 전략

| 전략 | 준비 | 비용 | RTO |
|---|---|---|---|
| **백업 & 복원** | 백업만 | 최저 | 수 시간 |
| **파일럿 라이트** | 최소 규모 DR 클러스터 상시 | 낮음 | 30분~1시간 |
| **웜 스탠바이** | 축소 규모로 상시 운영 | 중간 | 10~30분 |
| **핫 스탠바이 (액티브-액티브)** | 동일 규모 양쪽 운영 | 최고 | 분 |

**대부분의 조직에는 파일럿 라이트가 현실적이다.**

```
· DR 리전에 최소 노드로 클러스터 유지
· GitOps로 매니페스트는 동기화 (배포는 안 함)
· DB는 크로스 리전 복제
· 장애 시: 노드 스케일 업 → Argo CD sync → DNS 전환

## 32.5 트러블슈팅 플레이북

이 책 전체의 진단 지식을 하나로 모은다.

### 진단의 기본 순서

```
① 무엇이 잘못됐는가 — 증상 확인
   kubectl get pods -A --field-selector status.phase!=Running
   kubectl get nodes
   kubectl get events -A --sort-by=.lastTimestamp | tail -30

② 언제부터인가 — 변경 사항 확인
   kubectl rollout history deployment/<name>
   git log --oneline -10          (config-repo, 30.4절)
   Grafana 대시보드의 배포 주석 (31.7절)

③ 어디까지 정상인가 — 계층별로 좁힌다
   앱 → Pod → Service → DNS → Ingress → 외부

④ 왜 그런가 — 원인 특정
   로그, 이벤트, 메트릭, 트레이스 (31장)
```

### 증상별 진입점

| 증상 | 시작 지점 | 관련 장 |
|---|---|---|
| Pod가 `Pending` | 스케줄링 진단 | 15.9절 |
| Pod가 `CrashLoopBackOff` | `logs --previous` | 6.3절 |
| Pod가 `ImagePullBackOff` | 이미지 이름, 인증 | 6.5절 |
| Pod가 `0/1 Running` | readiness 프로브 | 6.2절 |
| Pod가 `Terminating`에서 멈춤 | 파이널라이저, SIGTERM | 4.2절, 6.4절 |
| Pod가 `OOMKilled` | 메모리 limits | 14.3절 |
| 서비스 연결 안 됨 | 엔드포인트 확인 | 9.7절 |
| DNS 해석 안 됨 | CoreDNS 진단 | 10.6절 |
| 인그레스 404/502/503 | 컨트롤러 로그 | 11.7절 |
| 볼륨 마운트 실패 | PVC/PV 상태 | 12.7절 |
| 노드 `NotReady` | kubelet 로그 | 20.8절 |
| `kubectl`이 느림 | etcd 지연 | 21.6절, 22.9절 |
| 노드 간 통신 안 됨 | CNI, MTU | 23.6절 |

| 정책 적용 후 전부 안 됨 | **NetworkPolicy의 DNS 예외** | 18.4절 |

### 계층별 격리 기법

**"어디까지 정상인가"를 빠르게 좁히는 방법이다.**

```bash
# ① 컨테이너 안에서 앱이 응답하는가
kubectl exec <pod> -- curl -sS --max-time 3 localhost:8080/healthz

# ② Pod IP로 직접 (다른 Pod에서)
POD_IP=$(kubectl get pod <pod> -o jsonpath='{.status.podIP}')
kubectl run t --rm -it --image=nicolaka/netshoot --restart=Never -- \
  curl -sS --max-time 3 $POD_IP:8080/healthz

# ③ ClusterIP로
SVC_IP=$(kubectl get svc <svc> -o jsonpath='{.spec.clusterIP}')
kubectl run t --rm -it --image=nicolaka/netshoot --restart=Never -- \
  curl -sS --max-time 3 $SVC_IP:80

# ④ DNS 이름으로
kubectl run t --rm -it --image=nicolaka/netshoot --restart=Never -- \
  curl -sS --max-time 3 http://<svc>.<ns>.svc.cluster.local

# ⑤ 인그레스를 통해
curl -sS -H "Host: app.example.com" http://<ingress-ip>/

# ⑥ 외부에서
curl -sS https://app.example.com/
```

**어느 단계에서 실패하는지가 원인의 위치를 알려 준다.**

```
①만 실패      → 앱 문제
①✓ ②✗        → CNI, NetworkPolicy
②✓ ③✗        → kube-proxy, 엔드포인트
③✓ ④✗        → DNS (CoreDNS)
④✓ ⑤✗        → 인그레스 컨트롤러
⑤✓ ⑥✗        → 외부 LB, DNS, 방화벽
```

### 장애 대응 체크리스트

```
■ 즉시 (0~5분)
  □ 영향 범위 파악 — 어떤 서비스, 몇 %의 사용자
  □ 최근 배포가 있었나 → 롤백 검토 (8.2절)
  □ 상태 페이지 업데이트
  □ 온콜 채널에 공유

■ 안정화 (5~30분)
  □ 롤백 또는 스케일 아웃으로 임시 완화
  □ 근본 원인은 나중에 — 먼저 서비스 복구
  □ 필요하면 트래픽 차단 (라벨 변경으로 Pod 격리, 4.3절)

■ 진단 (병렬로)
  □ 위의 계층별 격리
  □ 메트릭·로그·트레이스 확인 (31장)
  □ 최근 변경 이력 (Git, 배포 주석)

■ 사후 (24~72시간)
  □ 무비난 사후 분석(blameless postmortem)
  □ 타임라인 정리
  □ 액션 아이템 (모니터링 추가, 알림 개선, 자동화)
  □ 런북 갱신
```

## 32.6 비용 최적화

### 어디에 돈이 새는가

```
① 과대 requests (14장)
   가장 큰 낭비. 노드가 텅 비어 있는데 스케줄이 안 된다

② 유휴 노드
   스케일 인이 안 되는 노드 (16.5절의 CA 제약)

③ 불필요한 LoadBalancer (9.2절)
   Service마다 클라우드 LB. 인그레스로 통합

④ AZ 간 트래픽
   AZ를 넘는 통신은 유료. 토폴로지 인식 라우팅(9.3절)

⑤ 미사용 볼륨 (12.3절)
   삭제된 워크로드의 PVC/PV, 오래된 스냅샷

⑥ 과도한 로그·메트릭 (31장)
   보관 기간과 카디널리티

⑦ 온디맨드 인스턴스
   스팟으로 옮길 수 있는 워크로드
```

### 측정

13.7절에서 언급한 도구들이다.

```bash
# OpenCost
kubectl cost namespace --window 7d
kubectl cost deployment --window 30d --show-efficiency
```

**효율 지표**

```promql
# CPU 효율 = 실제 사용 / requests
sum(rate(container_cpu_usage_seconds_total{container!=""}[7d])) by (namespace)
  / sum(kube_pod_container_resource_requests{resource="cpu"}) by (namespace)

# 노드 할당률
sum(kube_pod_container_resource_requests{resource="cpu"}) by (node)
  / sum(kube_node_status_allocatable{resource="cpu"}) by (node)
```

**효율이 20% 미만이면 requests가 과대하다.**

### 최적화 실행

**① 리소스 라이트사이징** — 가장 효과가 크다

```
14.5절의 방법론 적용
  · VPA 권고 모드로 추천값 수집
  · P50~P70(CPU), P95(메모리) 기준으로 조정
  · 목표: 노드 할당률 70~80%
```

**② 스팟 인스턴스**

```yaml
# 중단 가능한 워크로드만
spec:
  tolerations:
    - key: spot
      operator: Equal
      value: "true"
      effect: NoSchedule
  terminationGracePeriodSeconds: 120     # 중단 알림 후 여유
```

**적합**: 배치, CI 러너, 개발 환경, 스테이트리스 워커
**부적합**: 데이터베이스, 상태 저장 앱, 중단이 치명적인 것

**Karpenter는 스팟 중단을 자동 처리한다**(16.5절). 중단 알림을 받으면 미리 새 노드를 준비한다.

**③ 노드 통합(consolidation)**

```yaml
# Karpenter
disruption:
  consolidationPolicy: WhenEmptyOrUnderutilized
  consolidateAfter: 1m
```

**주의**: 노드 교체가 잦아지므로 PDB와 graceful shutdown이 제대로 되어 있어야 한다.

**④ 밀집 배치 스케줄러 프로파일** (15.8절)

```yaml
profiles:
  - schedulerName: bin-packing
    pluginConfig:
      - name: NodeResourcesFit
        args:
          scoringStrategy:
            type: MostAllocated
```

빈 노드를 만들어 CA가 제거할 수 있게 한다.

**⑤ 개발 환경 자동 종료**

```yaml
# 야간·주말에 dev 네임스페이스 스케일 다운
apiVersion: batch/v1
kind: CronJob
metadata:
  name: scale-down-dev
spec:
  schedule: "0 20 * * 1-5"
  timeZone: "Asia/Seoul"
  jobTemplate:
    spec:
      template:
        spec:
          serviceAccountName: scaler
          restartPolicy: OnFailure
          containers:
            - name: kubectl
              image: bitnami/kubectl
              command:
                - sh
                - -c
                - kubectl scale deployment --all --replicas=0 -n dev
```

**또는 KEDA의 cron 스케일러**(16.3절)로 더 우아하게 처리한다.

**⑥ 스토리지 정리**

```bash
# 바인딩되지 않은 PV
kubectl get pv --field-selector status.phase=Released

# 사용되지 않는 PVC
kubectl get pvc -A -o json | jq -r '.items[] | select(.status.phase=="Bound") | "\(.metadata.namespace)/\(.metadata.name)"' > all-pvcs.txt

## 32.7 프로덕션 준비 체크리스트

```

## 실습 과제

**과제 1 — 업그레이드 리허설**
kind로 구버전 클러스터(예: v1.29)를 만들고, 워크로드를 배포한 뒤 v1.30 → v1.31로 단계적 업그레이드한다. 각 단계에서 워크로드가 정상 동작하는지 확인하고, 소요 시간을 기록한다.

**과제 2 — PDB 데드락 재현과 해결**
`replicas: 3`, `minAvailable: 3`인 PDB를 만들고 노드를 drain해 멈추는 것을 확인한다. 세 가지 방법(replicas 증가, PDB 조정, `--disable-eviction`)으로 각각 해결하고 차이를 비교한다.

**과제 3 — 전체 복구 시나리오**
1. 워크로드를 배포하고 Velero로 백업
2. 네임스페이스를 삭제
3. 복원하고 RTO 측정
4. etcd 스냅샷으로도 같은 시나리오를 수행해 두 방법의 차이(속도, 범위, 볼륨 데이터)를 비교

**과제 4 — 장애 시뮬레이션**
다음 장애를 각각 일으키고 32.5절의 플레이북으로 진단한다. 진단에 걸린 시간을 기록한다.
- Service 셀렉터 오타
- CoreDNS 스케일을 0으로
- NetworkPolicy에서 DNS 예외 누락
- 노드에 메모리 압박 유발

**과제 5 — 비용 분석**
클러스터의 리소스 효율을 측정하고, 상위 5개 워크로드의 requests를 실측 기반으로 조정한다. 조정 전후의 노드 할당률과 필요 노드 수를 비교한다.

## 요약

- **고가용성은 장애 도메인 분리**다. etcd 멤버와 워커 노드를 3개 AZ에 분산하고, `topologySpreadConstraints`로 워크로드를 균등 배치한다. AZ 장애를 견디려면 **1.5배의 용량 여유**가 필요하다.
- **버전 스큐**: 컨트롤 플레인을 먼저, 노드를 나중에. kubelet은 API 서버보다 최대 3 마이너 버전까지 뒤처질 수 있지만 **앞설 수는 없다.** 마이너 버전을 건너뛰지 않는다.
- **업그레이드 전에 폐기 예정 API를 반드시 확인**하고(`pluto`, 메트릭), 릴리스 노트의 "Urgent Upgrade Notes"를 읽는다. **인증서가 자동 갱신되므로 연 1회 이상 업그레이드해야 한다.**
- **PDB는 자발적 중단만 제어한다.** `minAvailable`을 replicas와 같게 하면 drain이 영원히 멈춘다. **`maxUnavailable`이 HPA와 함께 쓸 때 안전**하고, `unhealthyPodEvictionPolicy: AlwaysAllow`가 장애 상황의 drain을 가능하게 한다.
- **GitOps가 최고의 백업이다.** 클러스터를 새로 만들고 Argo CD를 심으면 전체가 복원된다. etcd 백업은 GitOps로 관리되지 않는 것을 위한 보완재다. **백업 주기가 곧 RPO**이며, **테스트하지 않은 백업은 백업이 아니다.**
- 진단은 **증상 → 최근 변경 → 계층별 격리 → 원인**의 순서다. 계층별 격리(컨테이너 안 → Pod IP → ClusterIP → DNS → 인그레스 → 외부)에서 **어느 단계가 실패하는지가 원인의 위치**를 알려 준다.
- 장애 시 **근본 원인보다 서비스 복구가 먼저**다. 롤백이나 스케일 아웃으로 안정화한 뒤 진단한다. 사후에는 **무비난 분석**과 런북 갱신으로 마무리한다.
- 비용의 가장 큰 낭비는 **과대 requests**다. 리소스 효율을 측정해 라이트사이징하고, 스팟·통합·밀집 배치·개발 환경 자동 종료로 최적화한다.

## 이 책을 마치며

1장에서 "인프라 드리프트를 어떻게 없앨 것인가"로 시작했다. 32장을 지나며 그 답은 이렇게 확장됐다.

```
① 선언적 상태와 조정 루프          (1장)
   원하는 것을 적으면 시스템이 유지한다

② 컨테이너와 Pod                  (2~8장)
   리눅스 프리미티브 위에서 워크로드를 실행한다

③ 연결과 데이터                   (9~12장)
   서비스를 노출하고 상태를 보관한다

④ 공유와 통제                     (13~18장)
   여러 팀이 안전하고 효율적으로 나눠 쓴다

⑤ 내부 이해                       (19~23장)
   추상화 아래에서 실제로 무슨 일이 일어나는지 안다

⑥ 확장                           (24~28장)
   우리의 운영 지식을 조정 루프로 옮긴다

⑦ 운영                           (29~32장)
   프로덕션에서 이 모든 것을 지속 가능하게 만든다
```

**쿠버네티스의 본질은 처음부터 끝까지 하나였다.**

> **원하는 상태를 선언하고, 조정 루프가 그것을 유지한다.**

Deployment도, 오퍼레이터도, GitOps도 같은 패턴의 다른 층위일 뿐이다. 이 패턴을 이해하면 처음 보는 리소스도, 새로 나온 도구도 같은 방식으로 읽을 수 있다.

**여기서부터는 실전이다.** 3장에서 만든 kind 클러스터로 실습했다면, 이제 실제 워크로드를 올려 보자. 이 책의 체크리스트를 하나씩 채워 가면서.
