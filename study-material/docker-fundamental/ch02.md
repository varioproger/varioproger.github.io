# 2장. 격리의 기초 — Linux Namespaces 완전 정복

1장에서 runc가 컨테이너 프로세스를 실행하기 직전에 "네임스페이스를 구성한다"는 표현을 여러 번 사용했습니다.
사실 컨테이너라는 개념 자체가 특별한 커널 객체가 아니라, 일반 프로세스에 여러 개의 네임스페이스를 조합해서
씌운 것에 지나지 않습니다. 이 장에서는 그 네임스페이스가 정확히 무엇을 격리하는지, 커널에 언제 어떤 형태로
도입되었는지, 그리고 Docker가 컨테이너를 만들 때 이들을 어떻게 조합하는지를 하나씩 살펴봅니다.

## 2.1 네임스페이스란 무엇인가

리눅스 네임스페이스는 커널이 관리하는 전역 자원(프로세스 ID, 네트워크 인터페이스, 마운트 테이블 등)을
프로세스 그룹별로 서로 다르게 "보이게" 만드는 커널 기능입니다. 중요한 것은 네임스페이스가 가상 머신처럼
자원을 실제로 복제하거나 물리적으로 분할하는 것이 아니라는 점입니다. 같은 물리 서버 위에서 실행되는 컨테이너
10개는 여전히 같은 커널, 같은 CPU, 같은 물리 네트워크 인터페이스를 공유합니다. 다만 각 컨테이너에 속한
프로세스가 `ps`를 실행했을 때 자신이 속한 네임스페이스 안의 프로세스만 보이고, `ip addr`을 실행했을 때 자신의
네트워크 네임스페이스 안의 인터페이스만 보일 뿐입니다.

이 접근 방식은 하드웨어 가상화(KVM 같은)나 반가상화와는 근본적으로 다릅니다. 컨테이너는 커널을 공유하는
"보통 프로세스"이고, 네임스페이스는 그 프로세스가 커널에 질의할 때 결과를 필터링/치환해주는 렌즈에 가깝습니다.
이 때문에 컨테이너는 VM보다 훨씬 가볍게 뜨지만, 동시에 커널 자체는 공유하므로 네임스페이스만으로는 완전한
보안 경계가 되지 못한다는 한계도 갖습니다. 이 한계는 이 장의 마지막 절에서 다시 짚습니다.

리눅스는 현재 8가지 네임스페이스 종류를 제공합니다. `clone()`, `unshare()`, `setns()` 시스템 콜에 각
네임스페이스에 대응하는 플래그(`CLONE_NEWPID`, `CLONE_NEWNET` 등)를 넘기면 새 네임스페이스를 만들거나
기존 네임스페이스에 합류할 수 있습니다. 아래에서 각각을 도입 시점과 함께 살펴봅니다.

## 2.2 여덟 가지 네임스페이스

### PID 네임스페이스 (`CLONE_NEWPID`, 커널 2.6.24)

PID 네임스페이스는 프로세스 ID 공간을 분리합니다. 새 PID 네임스페이스 안에서 처음 실행되는 프로세스는 그
네임스페이스 안에서 PID 1을 부여받습니다. 컨테이너 안에서 `ps -ef`를 실행하면 컨테이너의 엔트리포인트
프로세스가 PID 1로 보이는 이유가 이것입니다. 하지만 호스트 쪽에서 보면 그 프로세스는 여전히 호스트의 PID
공간에서 임의의(보통 두 자릿수~네 자릿수의) PID를 가지고 있습니다. 즉 PID는 네임스페이스마다 다르게 매핑된
"뷰"이지, 프로세스에 실제로 여러 개의 ID가 물리적으로 부여되는 것이 아니라 각 네임스페이스 계층에서 별도의
번호가 할당되는 구조입니다.

PID 네임스페이스는 중첩(nested)될 수 있습니다. 호스트의 PID 네임스페이스가 최상위이고, 그 안에 컨테이너의
PID 네임스페이스가 자식으로 존재하며, 컨테이너 안에서 다시 `unshare --pid`를 실행하면 손자 네임스페이스가
생길 수 있습니다. 프로세스는 자신이 속한 네임스페이스와 그 조상 네임스페이스들에서는 보이지만, 형제나
자식 네임스페이스에서는 보이지 않습니다.

PID 1이라는 위치는 리눅스에서 특별한 책임을 갖습니다. 좀비 프로세스를 회수(reap)하는 역할, 그리고 시그널
처리의 기본 동작이 다르다는 점(PID 1은 핸들러를 명시적으로 등록하지 않은 시그널에 대해 커널 기본 동작을
따르지 않고 무시하는 경우가 많습니다)이 대표적입니다. 그래서 컨테이너의 엔트리포인트가 다른 자식 프로세스를
여럿 fork하는 애플리케이션(셸 스크립트로 여러 데몬을 띄우는 경우 등)이라면, PID 1 역할을 제대로 하지 못해
좀비 프로세스가 쌓이는 문제가 흔히 발생합니다. 이런 이유로 `tini`처럼 최소한의 init 역할만 하는 바이너리를
PID 1로 앞세우는 패턴이 널리 쓰이며, Docker는 `docker run --init` 옵션으로 이를 간편하게 활성화할 수 있게
지원합니다.

### 네트워크 네임스페이스 (`CLONE_NEWNET`, 커널 2.6.29 전후로 점진적 완성)

네트워크 네임스페이스는 네트워크 인터페이스, 라우팅 테이블, iptables/nftables 규칙, 포트 바인딩 공간을
분리합니다. 각 컨테이너는 기본적으로 자신만의 loopback(`lo`)과 가상 이더넷 인터페이스(veth pair의 한쪽 끝)를
가지며, 이것이 컨테이너마다 독립적으로 `0.0.0.0:80` 같은 포트를 바인딩할 수 있는 이유입니다. 네트워크
네임스페이스는 8개 네임스페이스 중에서도 구현이 가장 복잡한 축에 속하는데, 라우팅 테이블뿐 아니라 방화벽
규칙, 소켓, `/proc/net` 하위의 각종 통계까지 네임스페이스별로 독립적으로 유지되어야 하기 때문입니다. 이
네임스페이스는 11~16장에서 다루는 브리지/오버레이/nftables 논의의 근간이 됩니다.

### 마운트 네임스페이스 (`CLONE_NEWNS`, 커널 2.4.19 — 가장 먼저 도입됨)

마운트 네임스페이스는 사실 리눅스에 가장 먼저 들어온 네임스페이스로, 플래그 이름도 `CLONE_NEWNS`("new
namespace"라는 일반적인 이름을 그대로 가져다 썼는데, 이후 다른 네임스페이스들이 추가되면서 상대적으로
어색한 이름이 되었습니다)입니다. 마운트 네임스페이스는 프로세스별로 독립적인 마운트 테이블(어떤 디바이스나
디렉터리가 어떤 경로에 마운트되어 있는지에 대한 뷰)을 제공합니다. 컨테이너의 루트 파일시스템 격리, 즉
컨테이너 안에서 `/`를 봤을 때 호스트의 실제 루트가 아니라 이미지 레이어를 합성한 overlay 파일시스템이
보이는 것은 이 네임스페이스와 `pivot_root`(또는 구형 방식의 `chroot`) 시스템 콜의 조합으로 만들어집니다.

### UTS 네임스페이스 (`CLONE_NEWUTS`, 커널 2.6.19)

UTS는 "UNIX Time-sharing System"의 약자로, 호스트 이름(hostname)과 NIS 도메인 이름을 격리합니다. 컨테이너
안에서 `hostname`을 실행하면 호스트의 실제 호스트 이름이 아니라 컨테이너에 할당된 이름(기본적으로 컨테이너
ID의 앞자리, 또는 `--hostname`으로 지정한 값)이 보이는 것이 이 네임스페이스 덕분입니다. 8개 네임스페이스
중 가장 단순한 축에 속합니다.

### IPC 네임스페이스 (`CLONE_NEWIPC`, 커널 2.6.19)

IPC 네임스페이스는 System V IPC 객체(공유 메모리 세그먼트, 세마포어, 메시지 큐)와 POSIX 메시지 큐를
격리합니다. 서로 다른 컨테이너에서 동일한 IPC 키를 사용해도 충돌하지 않는 이유가 이것입니다. 데이터베이스나
일부 레거시 애플리케이션처럼 System V 공유 메모리에 의존하는 워크로드를 여러 컨테이너로 나눌 때 이 네임스페이스의
격리 여부가 중요한 변수가 될 수 있습니다.

### 사용자 네임스페이스 (`CLONE_NEWUSER`, 커널 3.8)

사용자 네임스페이스는 UID/GID 공간을 격리합니다. 즉 컨테이너 안에서 UID 0(root)으로 보이는 프로세스가
호스트에서는 UID 0이 아닌 임의의 비특권 UID(예: 100000)로 매핑되도록 할 수 있습니다. 이 매핑은
`/proc/[pid]/uid_map`, `/proc/[pid]/gid_map` 파일에 `<네임스페이스 내부 시작 ID> <호스트 시작 ID> <범위>`
형식으로 기록됩니다. 사용자 네임스페이스는 8개 네임스페이스 중 보안적으로 가장 파급력이 크면서도, 다른
네임스페이스와 달리 비특권 사용자가 스스로 생성할 수 있다는 특징이 있습니다(다른 네임스페이스들은 보통
`CAP_SYS_ADMIN` 등의 권한이 필요하지만, 사용자 네임스페이스 생성 자체는 일반 사용자도 가능하도록 설계되어
있습니다. 이는 rootless 컨테이너 실행의 기반이 됩니다).

Docker에서 사용자 네임스페이스는 `userns-remap`(데몬 전역 설정)이나 Docker 특정 최신 버전들이 지원하는
컨테이너별 `--userns=` 옵션을 통해 활성화할 수 있습니다. 활성화하면 컨테이너 안에서 root로 보이는 프로세스가
호스트에서는 비특권 UID로 매핑되므로, 컨테이너 탈출(escape) 취약점이 발생하더라도 호스트에서 실제 root
권한을 획득하지는 못하게 되는 추가 방어선이 생깁니다. 이 주제와 rootless Docker 전반의 네트워킹 구조는
17장에서 RootlessKit, gvisor-tap-vsock과 함께 심화해서 다룹니다. 이 장에서는 사용자 네임스페이스가 "UID를
가상화하는 네임스페이스"라는 개념만 확실히 잡고 넘어가면 충분합니다.

### cgroup 네임스페이스 (`CLONE_NEWCGROUP`, 커널 4.6)

cgroup 네임스페이스는 프로세스가 자신이 속한 cgroup 계층 구조를 볼 때, 실제 호스트 전체의 cgroup 트리가
아니라 자신이 속한 하위 트리를 마치 루트인 것처럼 보게 만듭니다. 이 네임스페이스가 없다면 컨테이너 안에서
`/proc/self/cgroup`이나 `/sys/fs/cgroup`을 들여다봤을 때 호스트의 전체 cgroup 경로 구조가 그대로 노출되어
정보가 새어나가거나, 일부 cgroup-aware 소프트웨어가 오작동할 수 있습니다. cgroup 자체(자원 제한 메커니즘)는
3장에서 자세히 다루며, 이 네임스페이스는 그 cgroup을 "보는 방식"을 격리하는 역할이라는 점에서 구분됩니다.

### 타임 네임스페이스 (`CLONE_NEWTIME`, 커널 5.6 — 가장 최근에 안정화)

타임 네임스페이스는 8개 중 가장 나중에(2020년, 커널 5.6) 안정화된 네임스페이스로, 시스템 부팅 이후 경과
시간을 나타내는 monotonic 클록과 boot-time 클록의 오프셋을 네임스페이스별로 다르게 설정할 수 있게 해줍니다.
직관적으로 이해하면, 컨테이너를 체크포인트/복원(CRIU를 통한 라이브 마이그레이션 등)하거나 특정 시점의
시스템 uptime을 시뮬레이션해야 하는 테스트 시나리오에서 유용합니다. 다만 벽시계 시각(wall clock, `CLOCK_REALTIME`)
자체를 컨테이너별로 다르게 설정해주는 기능은 아니라는 점에 유의해야 합니다. 타임 네임스페이스는 실무에서
가장 존재감이 적은 네임스페이스이지만, "네임스페이스는 pid/net/mnt 세 가지뿐"이라고 알고 있는 독자가 많으므로
전체 목록에 반드시 포함해 이해해 둘 필요가 있습니다.

## 2.3 네임스페이스 도입 시점 정리

아래 표는 위 내용을 시간 순으로 정리한 것입니다. 커널 버전은 해당 기능이 처음 병합되거나 안정화된 시점을
기준으로 하며, 배포판에 따라 백포트 여부가 다를 수 있으므로 실제 사용 가능 여부는 각 배포판의 커널 설정을
확인하는 것이 정확합니다.

| 네임스페이스 | 플래그 | 커널 버전 | 격리 대상 |
|---|---|---|---|
| Mount | `CLONE_NEWNS` | 2.4.19 | 마운트 테이블 |
| UTS | `CLONE_NEWUTS` | 2.6.19 | 호스트 이름, NIS 도메인 |
| IPC | `CLONE_NEWIPC` | 2.6.19 | System V IPC, POSIX 메시지 큐 |
| PID | `CLONE_NEWPID` | 2.6.24 | 프로세스 ID 공간 |
| Network | `CLONE_NEWNET` | 2.6.29 전후 | 네트워크 인터페이스, 라우팅, 방화벽 |
| User | `CLONE_NEWUSER` | 3.8 | UID/GID 매핑 |
| cgroup | `CLONE_NEWCGROUP` | 4.6 | cgroup 계층 뷰 |
| Time | `CLONE_NEWTIME` | 5.6 | 부팅 이후 경과 시각 클록 |

## 2.4 `/proc/[pid]/ns/`로 네임스페이스 확인하기

리눅스는 프로세스가 속한 각 네임스페이스를 `/proc/[pid]/ns/` 아래의 심볼릭 링크로 노출합니다.

```bash
ls -l /proc/$$/ns/
```

전형적인 출력은 다음과 같습니다(현재 셸 프로세스 기준).

```
lrwxrwxrwx 1 root root 0 ... cgroup -> 'cgroup:[4026531835]'
lrwxrwxrwx 1 root root 0 ... ipc -> 'ipc:[4026531839]'
lrwxrwxrwx 1 root root 0 ... mnt -> 'mnt:[4026531840]'
lrwxrwxrwx 1 root root 0 ... net -> 'net:[4026531992]'
lrwxrwxrwx 1 root root 0 ... pid -> 'pid:[4026531836]'
lrwxrwxrwx 1 root root 0 ... pid_for_children -> 'pid:[4026531836]'
lrwxrwxrwx 1 root root 0 ... time -> 'time:[4026531834]'
lrwxrwxrwx 1 root root 0 ... time_for_children -> 'time:[4026531834]'
lrwxrwxrwx 1 root root 0 ... user -> 'user:[4026531837]'
lrwxrwxrwx 1 root root 0 ... uts -> 'uts:[4026531838]'
```

대괄호 안의 숫자는 네임스페이스의 고유 식별자(inode 번호)입니다. 두 프로세스가 같은 네임스페이스에
속해 있는지 확인하려면 이 번호를 비교하면 됩니다. 예를 들어 컨테이너 안의 프로세스와 호스트의 프로세스가
네트워크 네임스페이스를 공유하고 있는지(`--net=host`로 실행한 경우) 확인하려면 두 프로세스의
`net -> net:[...]` 번호가 같은지 보면 됩니다.

이 심볼릭 링크는 단순히 "읽기용" 정보가 아니라, 실제로 열 수 있는 파일 디스크립터이기도 합니다.
`setns()` 시스템 콜에 이 경로를 열어서 얻은 파일 디스크립터를 넘기면, 호출한 프로세스가 그 네임스페이스에
합류(join)할 수 있습니다. `nsenter`는 바로 이 메커니즘을 CLI로 감싼 도구입니다.

### `unshare`, `nsenter`, `ip netns` 실습

```bash
# 새로운 mount + PID 네임스페이스에서 셸을 하나 띄우기
sudo unshare --mount --pid --fork --mount-proc bash

# 새 네임스페이스 안에서 ps를 실행하면 자기 자신과 극소수의 프로세스만 보임
ps -ef
# 확인 포인트: 위에서 fork한 bash가 PID 1로 보임(--mount-proc 덕분에 /proc가 새 PID 네임스페이스
# 기준으로 다시 마운트되어 ps가 정확한 결과를 보여줌)
```

```bash
# 실행 중인 컨테이너의 네임스페이스에 호스트에서 진입하기
docker run -d --name web nginx:latest
PID=$(docker inspect -f '{{.State.Pid}}' web)

# 해당 컨테이너의 네트워크 네임스페이스에 들어가서 인터페이스 확인
sudo nsenter --target $PID --net -- ip addr

# 해당 컨테이너의 마운트 네임스페이스만 공유해서 파일시스템 확인
sudo nsenter --target $PID --mount -- ls /
```

`nsenter`는 컨테이너 디버깅에서 대단히 실용적인 도구입니다. 컨테이너 이미지 안에 셸이나 디버깅 도구가
전혀 설치되어 있지 않은 "distroless" 이미지라 하더라도, 호스트에 설치된 도구를 사용해 그 컨테이너의
네임스페이스 안으로 진입해서 네트워크나 마운트 상태를 확인할 수 있기 때문입니다.

```bash
# ip netns를 이용한 네트워크 네임스페이스 관리(컨테이너와 무관하게 독립적으로 생성 가능)
sudo ip netns add testns
sudo ip netns exec testns ip addr
sudo ip netns list
sudo ip netns delete testns
```

`ip netns`는 Docker와 무관하게 네트워크 네임스페이스만 독립적으로 다룰 때 쓰는 도구이며, 리눅스 네트워크
관리자에게는 컨테이너보다 먼저 익숙한 도구입니다. 다만 `ip netns`가 만드는 네임스페이스는 기본적으로
`/var/run/netns/` 아래에 이름이 붙은 형태로 등록되는 반면, Docker가 만드는 네트워크 네임스페이스는
`/var/run/docker/netns/`(또는 유사 경로) 아래에 별도로 관리되므로 두 네임스페이스 등록 체계가 완전히
같지는 않다는 점도 참고해 둘 만합니다.

## 2.5 Docker가 네임스페이스를 조합하는 방식

`docker run`으로 컨테이너를 실행하면 기본적으로 PID, 마운트, UTS, IPC, 네트워크(그리고 조건부로 cgroup)
네임스페이스가 새로 생성됩니다. 사용자 네임스페이스는 기본적으로는 새로 생성되지 않고 호스트의 사용자
네임스페이스를 그대로 사용하지만, `userns-remap`이 설정되어 있거나 `--userns=`를 명시하면 새로 생성됩니다.
타임 네임스페이스는 기본적으로 새로 생성하지 않고 호스트와 공유합니다.

Docker의 여러 CLI 옵션은 사실 "이 네임스페이스는 새로 만들지 말고 다른 대상과 공유하라"는 지시로
이해하면 명확해집니다.

```bash
# 네트워크 네임스페이스를 호스트와 공유 (새 net 네임스페이스를 만들지 않음)
docker run --rm --net=host nginx:latest

# 네트워크 네임스페이스를 다른 컨테이너 X와 공유 (사이드카 패턴의 기반)
docker run -d --name app myapp:latest
docker run --rm --net=container:app busybox ip addr

# PID 네임스페이스를 호스트와 공유 (호스트의 모든 프로세스가 컨테이너 안에서 보임 — 디버깅용)
docker run --rm --pid=host busybox ps -ef

# IPC 네임스페이스를 호스트 또는 다른 컨테이너와 공유
docker run --rm --ipc=host busybox ipcs

# 사용자 네임스페이스 매핑을 활성화(데몬 전역 userns-remap 설정이 선행되어야 하는 경우가 많음)
docker run --userns=host busybox id   # 리매핑을 우회하고 호스트 사용자 네임스페이스 사용
```

`--net=container:app` 패턴은 Kubernetes의 파드(Pod) 안에서 여러 컨테이너가 네트워크 네임스페이스를
공유하는 구조와 정확히 같은 원리입니다. Kubernetes의 파드는 실제로 "pause 컨테이너"라는 것을 먼저 만들어
네트워크 네임스페이스를 생성해두고, 같은 파드에 속한 나머지 컨테이너들이 모두 그 네임스페이스에
합류(`--net=container:pause`와 동등한 방식)하는 구조로 동작합니다. 이 장에서 다룬 네임스페이스 공유
메커니즘을 이해하면 Kubernetes 파드 네트워킹의 근본 원리도 자연스럽게 이해할 수 있습니다.

`--userns=`는 Docker 버전과 데몬 설정에 따라 사용 가능한 값과 기본 동작이 달라질 수 있는 옵션이므로,
실제 운영에 적용하기 전에는 반드시 사용 중인 Docker Engine 버전의 공식 문서에서 정확한 동작을 확인하는
것이 안전합니다. 이 옵션과 rootless 모드, `userns-remap` 데몬 설정 사이의 관계는 17장에서 심화해서
다룹니다. 여기서는 "사용자 네임스페이스도 결국 네트워크/PID 네임스페이스와 마찬가지로 새로 만들거나
호스트와 공유하거나 선택할 수 있는 대상"이라는 개념만 잡아두면 충분합니다.

## 2.6 네임스페이스만으로는 부족하다

여기까지 살펴본 8가지 네임스페이스는 컨테이너가 "다른 프로세스, 다른 네트워크, 다른 파일시스템을 보게"
만들어주지만, 이것이 곧 보안 격리를 의미하지는 않습니다. 몇 가지 이유가 있습니다.

첫째, 네임스페이스는 커널 자체를 분리하지 않습니다. 호스트와 모든 컨테이너는 여전히 같은 커널 코드를
실행하므로, 커널의 취약점(예: 네임스페이스 처리 로직 자체의 버그)이 있다면 네임스페이스 경계를 그대로
넘어갈 수 있습니다.

둘째, 네임스페이스는 "무엇을 할 수 있는지"를 제한하지 않고 "무엇이 보이는지"만 제한합니다. 예를 들어
사용자 네임스페이스 없이 컨테이너 안에서 진짜 UID 0(root)으로 실행되고 있다면, 컨테이너 안에서 커널
모듈을 로드하거나(관련 capability가 있다면) 커널 파라미터를 조정하는 것과 같은 위험한 행위를 막는
것은 네임스페이스가 아니라 **capabilities**(리눅스가 root의 권한을 잘게 쪼갠 단위)와 **seccomp**(허용된
시스템 콜만 호출할 수 있게 제한하는 필터)의 몫입니다.

셋째, 자원 사용량 자체를 제한하는 것은 네임스페이스의 역할이 아닙니다. 한 컨테이너가 호스트의 메모리나
CPU를 독점해서 다른 컨테이너에 영향을 주는 것("noisy neighbor" 문제)을 막는 것은 다음 장에서 다룰
**cgroups**의 역할입니다.

정리하면, 네임스페이스는 컨테이너 격리를 구성하는 여러 축 중 "가시성(visibility)"을 담당하는 축이고,
capabilities/seccomp는 "권한(privilege)"을, cgroups는 "자원(resource)"을 담당하는 축입니다. 실무에서
"컨테이너가 격리되어 있다"고 말할 때는 이 세 축이 함께 작동하고 있다는 것을 의미하며, 그중 하나라도
느슨하게 설정되면(예: `--privileged`로 capabilities와 seccomp를 사실상 무력화하는 경우) 나머지 축이
아무리 엄격해도 전체 격리 수준은 가장 약한 축을 따라갑니다. 이 세 축의 관계와 실전 보안 하드닝은 4장(OCI
런타임 스펙에서 capabilities/seccomp가 어떻게 명세되는지)에서 더 자세히 다룹니다.

## 핵심 요약

- 네임스페이스는 커널 자원을 실제로 나누는 것이 아니라, 프로세스마다 다른 "뷰"를 제공하는 커널 기능이다.
- 리눅스는 mount(2.4), uts/ipc(2.6.19), pid(2.6.24), net(2.6.29), user(3.8), cgroup(4.6), time(5.6) 총
  8가지 네임스페이스를 제공하며, time 네임스페이스가 가장 최근에 안정화되었다.
- 각 프로세스가 속한 네임스페이스는 `/proc/[pid]/ns/` 아래의 심볼릭 링크(대괄호 안 inode 번호)로 확인할
  수 있고, `setns()`로 재진입할 수 있다.
- `unshare`는 새 네임스페이스를 만들고, `nsenter`는 기존 프로세스의 네임스페이스에 진입하며, `ip netns`는
  네트워크 네임스페이스를 독립적으로 관리하는 도구다.
- Docker의 `--net=host`, `--net=container:X`, `--pid=host`, `--ipc=host`, `--userns=` 옵션은 모두
  "이 네임스페이스는 새로 만들지 말고 지정한 대상과 공유하라"는 의미로 이해할 수 있다.
- 사용자 네임스페이스(UID/GID 매핑)는 rootless 컨테이너 실행의 기반이 되며, 세부 내용은 17장에서
  다시 다룬다.
- 네임스페이스는 격리의 "가시성" 축일 뿐이며, "권한" 축은 capabilities/seccomp가, "자원" 축은 cgroups가
  담당한다. 이 세 축이 함께 작동해야 실질적인 컨테이너 격리가 완성된다.

## 실습

아래 실습은 root 권한이 필요하며, `util-linux` 패키지(`unshare`, `nsenter` 포함)와 `iproute2` 패키지
(`ip netns` 포함)가 설치되어 있어야 합니다.

```bash
# 1) 현재 셸의 네임스페이스 목록과 각 inode 번호 확인
ls -l /proc/$$/ns/
# 확인 포인트: mnt, net, pid, uts, ipc, user, cgroup, time 8개 항목이 모두 보이는지 확인합니다.

# 2) 컨테이너를 하나 띄우고 호스트와 네임스페이스 inode 번호를 비교
docker run -d --name web nginx:latest
CPID=$(docker inspect -f '{{.State.Pid}}' web)
sudo ls -l /proc/$CPID/ns/net /proc/self/ns/net
# 확인 포인트: 두 net 네임스페이스의 inode 번호(대괄호 안 숫자)가 서로 다르면 독립된 네트워크
# 네임스페이스를 쓰고 있다는 뜻입니다.

# 3) --net=host로 실행한 컨테이너는 호스트와 번호가 같은지 비교
docker run -d --name web-host --net=host nginx:latest
HPID=$(docker inspect -f '{{.State.Pid}}' web-host)
sudo ls -l /proc/$HPID/ns/net /proc/self/ns/net
# 확인 포인트: 이번에는 두 번호가 동일하게 나오는지 확인합니다.

# 4) nsenter로 컨테이너의 네트워크 네임스페이스에 직접 진입
sudo nsenter --target $CPID --net -- ip addr show
# 확인 포인트: 호스트의 물리 인터페이스가 아니라 컨테이너 전용 veth 인터페이스(eth0 등)와 lo만
# 보이는지 확인합니다.

# 5) unshare로 새 PID 네임스페이스를 만들고 PID 1 확인
sudo unshare --pid --fork --mount-proc readlink /proc/self
# 확인 포인트: 결과가 1로 나오는지 확인합니다(새 네임스페이스 안에서 PID 1을 부여받았다는 의미).

# 6) 정리
docker rm -f web web-host
```

다음 장에서는 네임스페이스가 만들어내는 "보이는 세계"의 경계를 넘어, 실제로 CPU와 메모리, I/O 사용량을
얼마나 쓸 수 있는지를 결정하는 cgroups로 넘어갑니다. cgroups v1의 한계와 v2가 이를 어떻게 재설계했는지를
다룹니다.
