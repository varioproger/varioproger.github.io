# 14장. macvlan, ipvlan, host/none 네트워크 모드

11장에서는 CNM(Container Network Model)이 네트워크, 엔드포인트, 샌드박스라는 세 가지 추상을 통해 컨테이너의
네트워킹을 어떻게 모델링하는지 살펴보았고, 12장과 13장에서는 그중 가장 널리 쓰이는 두 드라이버, 즉 단일
호스트에서 동작하는 브리지 네트워크와 여러 호스트를 VXLAN으로 엮는 오버레이 네트워크를 각각 심층적으로
다루었습니다. 이 두 드라이버는 공통점이 하나 있습니다. 컨테이너가 어떤 방식으로든 NAT(주소 변환)를 거쳐
외부와 통신한다는 점입니다. 브리지 네트워크의 컨테이너는 사설 대역(예: `172.17.0.0/16`)의 IP를 받고, 외부로
나가는 트래픽은 호스트의 IP로 매스커레이딩되며, 외부에서 들어오는 트래픽은 포트 매핑을 통한 DNAT로 컨테이너에
도달합니다. 이 구조는 대부분의 상황에서 충분히 잘 동작하지만, 컨테이너가 물리 네트워크에서 마치 하나의
독립된 물리 장비처럼 보여야 하는 요구사항 앞에서는 한계를 드러냅니다. 이 장에서는 NAT를 우회하고 컨테이너를
물리 네트워크에 직접 노출시키는 macvlan과 ipvlan 드라이버, 그리고 네트워크 네임스페이스 자체를 다루는 방식이
근본적으로 다른 host/none 모드를 다룹니다.

## 14.1 왜 NAT를 우회해야 하는가

브리지 네트워크와 포트 매핑 조합이 널리 쓰이는 이유는 명확합니다. 호스트 하나의 IP만으로 수십, 수백 개의
컨테이너를 구분 없이 실행할 수 있고, 컨테이너가 재시작되어 IP가 바뀌어도 외부에는 호스트의 IP와 포트만
노출되므로 영향이 없습니다. 하지만 이 편리함은 몇 가지 대가를 치릅니다.

첫째, 레거시 애플리케이션 중에는 자기 자신의 IP 주소나 MAC 주소를 라이선스 검증, 클러스터 멤버십 판단,
멀티캐스트 기반 디스커버리 등의 근거로 사용하는 소프트웨어가 있습니다. 이런 애플리케이션을 NAT 뒤에
두면 컨테이너 내부에서 확인하는 IP와 외부에서 실제로 도달하는 경로의 IP가 일치하지 않아 오동작하는
경우가 있습니다. 물리 네트워크나 가상 네트워크 어플라이언스를 그대로 컨테이너로 옮기는 마이그레이션
프로젝트에서 특히 자주 마주치는 문제입니다.

둘째, 포트 매핑 방식은 컨테이너마다 별도의 호스트 포트를 할당해야 하므로, 여러 컨테이너가 동일한 기본
포트(예: 모두 80번 포트를 쓰는 웹 서버 여러 개)를 그대로 노출하려면 호스트 쪽에서 포트를 구분해 매핑해야
합니다. 이 자체는 큰 문제가 아니지만, 네트워크 장비나 방화벽 정책이 "각 서비스는 자신의 IP를 가지고 표준
포트로 응답한다"는 전제를 두고 설계된 환경에서는 컨테이너마다 고유한 IP를 할당하는 편이 운영이 단순해집니다.

셋째, DNAT/SNAT 자체가 커널의 conntrack 서브시스템을 거치는 추가 처리 단계이므로, 초당 연결 수가 매우 많은
고성능 네트워킹 워크로드에서는 이 오버헤드가 무시할 수 없는 수준이 되기도 합니다. 물론 대부분의 웹 애플리케이션
수준에서는 체감되지 않지만, NFV(Network Function Virtualization)나 패킷 처리량이 핵심인 워크로드에서는
NAT 계층 자체를 걷어내고 싶어지는 상황이 생깁니다.

macvlan과 ipvlan은 이런 요구에 대한 답으로, 컨테이너의 네트워크 인터페이스를 호스트의 물리 인터페이스에
직접 연결해 컨테이너가 물리 네트워크상에서 "보통의 호스트"처럼 보이도록 만드는 드라이버입니다.

## 14.2 macvlan 드라이버의 동작 원리

macvlan은 리눅스 커널의 `macvlan` 디바이스 드라이버를 그대로 활용하는 네트워크 드라이버입니다. 이 드라이버의
핵심 아이디어는 하나의 물리 네트워크 인터페이스(parent interface) 위에, 각자 고유한 MAC 주소를 가진 여러 개의
가상 서브인터페이스를 만들어내는 것입니다. 예를 들어 호스트의 `eth0`를 부모 인터페이스로 지정하면, 컨테이너마다
`eth0`를 기반으로 한 별도의 macvlan 서브인터페이스가 생성되고, 이 서브인터페이스는 커널이 새로 발급한 고유
MAC 주소를 가지고 컨테이너의 네트워크 네임스페이스 안으로 이동합니다.

여기서 중요한 점은, 이 트래픽이 브리지 네트워크에서처럼 veth 페어와 리눅스 브리지(docker0)를 거치는 것이
아니라, `eth0`가 직접 수신하는 이더넷 프레임 레벨에서 MAC 주소를 기준으로 각 서브인터페이스에 프레임을
분배한다는 것입니다. 즉 컨테이너의 트래픽은 호스트의 IP 스택(라우팅 테이블, iptables/nftables 체인)을 거치지
않고 물리 네트워크로 직접 나갑니다. 스위치 입장에서는 이 컨테이너가 같은 물리 포트 뒤에 있는 또 다른 독립
장비로 보이며, DHCP를 통해 외부 네트워크에서 정상적으로 IP를 할당받거나, 고정 IP를 그대로 사용할 수 있습니다.

### macvlan의 네 가지 모드

macvlan 드라이버는 서브인터페이스 간 트래픽을 어떻게 처리할지에 따라 네 가지 모드를 지원하며, Docker에서는
`-o macvlan_mode` 옵션으로 지정합니다. 기본값은 `bridge` 모드입니다.

| 모드 | 동작 | 주요 용도 |
|---|---|---|
| `bridge` (기본값) | 같은 부모 인터페이스를 공유하는 서브인터페이스끼리는 커널 내부에서 직접 스위칭되어 물리 스위치를 거치지 않고 서로 통신 | 대부분의 컨테이너 간 통신 요구에 적합, 가장 널리 쓰임 |
| `vepa` (Virtual Ethernet Port Aggregator) | 같은 부모를 공유하는 서브인터페이스 간 트래픽도 반드시 외부 스위치로 내보낸 뒤 되돌아오도록 강제 | 802.1Qbg를 지원하는 스위치에서 모든 트래픽에 대해 중앙 집중적인 정책/모니터링을 적용하고 싶을 때 |
| `private` | 같은 부모를 공유하는 서브인터페이스끼리 상호 통신 자체를 차단 | 컨테이너 간 격리가 보안상 반드시 필요한 멀티테넌시 환경 |
| `passthru` | 부모 인터페이스 하나를 컨테이너 하나에 통째로 전달(서브인터페이스를 여러 개 만들지 않음) | 컨테이너가 물리 NIC를 배타적으로 점유해야 하는 특수한 경우 |

실무에서 압도적으로 많이 쓰이는 것은 `bridge` 모드입니다. `vepa`라는 이름 때문에 이 모드가 "802.1Q 트렁크"
자체를 의미한다고 오해하기 쉬운데, 정확히는 vepa는 스위치가 반사(reflective relay) 기능을 지원해야 동작하는
표준화된 프로토콜 확장이고, 802.1Q VLAN 트렁킹은 이와는 별개로 부모 인터페이스 자체를 VLAN 서브인터페이스로
구성하는 방식입니다. 즉 "802.1Q 트렁크 모드"라는 별도의 macvlan 모드가 있는 것이 아니라, 아래에서 설명할
서브인터페이스 구성 방식과 macvlan 모드는 서로 독립적인 축입니다.

### 부모 인터페이스와 802.1Q 서브인터페이스

macvlan 네트워크를 만들 때는 반드시 어떤 물리(또는 물리에 준하는) 인터페이스를 부모로 쓸지 지정해야 합니다.

```bash
docker network create -d macvlan \
  --subnet=192.168.10.0/24 \
  --gateway=192.168.10.1 \
  -o parent=eth0 \
  mv-net
```

호스트의 물리 스위치 포트가 트렁크(trunk)로 설정되어 여러 VLAN의 태그된 프레임을 함께 실어 나르는 환경이라면,
부모 인터페이스로 물리 인터페이스 자체가 아니라 VLAN 서브인터페이스를 지정해야 합니다. 이때 부모 인터페이스
이름에 `.`과 VLAN ID를 붙여 지정합니다(예: `eth0.20`). Docker는 이 이름 규칙을 인식해 해당 VLAN 서브인터페이스가
아직 없으면 자동으로 생성해 줍니다.

```bash
docker network create -d macvlan \
  --subnet=192.168.20.0/24 \
  --gateway=192.168.20.1 \
  -o parent=eth0.20 \
  mv-net-vlan20
```

이렇게 하면 하나의 물리 인터페이스 위에 VLAN별로 별도의 macvlan 네트워크를 여러 개 만들 수 있고, 각 네트워크에
연결된 컨테이너는 해당 VLAN 안에서만 보이게 됩니다. 물리 스위치의 트렁크 설정과 Docker 네트워크의 VLAN ID가
반드시 일치해야 하며, 이 부분이 어긋나면 컨테이너가 아예 통신하지 못하는데도 Docker 쪽에서는 별다른 오류를
내지 않는 경우가 많아 트러블슈팅 시 스위치 쪽 설정부터 확인하는 습관이 필요합니다.

### 실무에서 반드시 챙겨야 할 promiscuous mode 주의점

macvlan은 하나의 물리 인터페이스로 서로 다른 여러 MAC 주소를 가진 트래픽을 송수신해야 합니다. 그런데 일부
물리 NIC나 가상화 환경(특히 퍼블릭 클라우드의 가상 NIC, 일부 하이퍼바이저의 vSwitch)은 기본적으로 자신에게
할당된 MAC 주소로 온 프레임만 통과시키고 나머지는 버리도록 설정되어 있습니다. macvlan이 정상 동작하려면
NIC가 promiscuous mode로 동작하며 자신의 MAC 주소가 아닌 프레임도 상위로 전달해야 하고, 경우에 따라 물리
스위치 포트 자체도 "포트당 여러 MAC 주소 학습을 허용"하도록 설정되어 있어야 합니다.

이는 특히 클라우드 인스턴스에서 macvlan을 쓰려 할 때 자주 발목을 잡습니다. AWS EC2, GCP Compute Engine 등
주요 퍼블릭 클라우드는 보안상의 이유로 인스턴스의 가상 NIC에 대해 소스/목적지 MAC 검사를 엄격히 적용하며,
인스턴스 콘솔에서 별도로 "소스/목적지 확인 비활성화"나 이와 동등한 설정을 거치지 않으면 macvlan으로 만든
컨테이너의 트래픽이 클라우드 네트워크 계층에서 조용히 드롭됩니다. 온프레미스 환경이라면 물리 스위치 포트가
포트 보안(port security)이나 802.1X 같은 기능으로 MAC 주소 개수를 제한하고 있지 않은지 사전에 네트워크 팀과
확인해야 합니다. 이 제약은 다음 절에서 다룰 ipvlan이 대안이 되는 핵심적인 이유이기도 합니다.

## 14.3 ipvlan 드라이버 — MAC 주소를 공유하는 대안

ipvlan은 macvlan과 목적은 같지만 접근 방식이 다른 드라이버입니다. macvlan이 컨테이너마다 새로운 MAC 주소를
발급하는 것과 달리, ipvlan에 연결된 모든 컨테이너는 부모 인터페이스의 MAC 주소를 그대로 공유합니다. 대신
IP 주소를 기준으로 커널이 각 서브인터페이스로 패킷을 분배합니다. 이 특성 때문에 ipvlan은 스위치 입장에서
"MAC 주소 하나 뒤에 여러 IP를 쓰는 하나의 장비"로 보이며, 앞서 설명한 promiscuous mode나 포트당 MAC 주소
개수 제한 문제에서 자유롭습니다. 물리 스위치가 포트 보안 기능으로 인터페이스당 학습 가능한 MAC 주소 개수를
엄격히 제한하는 환경, 또는 클라우드 인스턴스처럼 가상 NIC 자체가 원천적으로 자신에게 할당된 MAC 주소
이외의 트래픽을 통과시키지 않는 환경에서는 ipvlan이 macvlan보다 훨씬 안정적으로 동작합니다.

### L2 모드와 L3 모드

ipvlan은 부모 인터페이스와 컨테이너 사이에서 패킷을 어떤 계층에서 처리할지에 따라 두 가지 모드를 제공합니다.

**L2 모드(기본값)** 는 macvlan의 bridge 모드와 유사하게 동작합니다. 같은 부모 인터페이스를 공유하는
컨테이너들은 같은 브로드캐스트 도메인(같은 서브넷)에 속한 것처럼 취급되며, ARP나 브로드캐스트/멀티캐스트
트래픽이 정상적으로 오갑니다. 다른 서브넷에 있는 대상과 통신하려면 물리 네트워크의 게이트웨이(라우터)를
거쳐야 하는 것도 일반적인 L2 네트워크와 동일합니다.

**L3 모드** 는 이름 그대로 부모 인터페이스가 사실상 라우터처럼 동작하도록 만듭니다. L3 모드에서는 브로드캐스트와
멀티캐스트 트래픽이 전달되지 않으며, 커널이 각 서브인터페이스로 향하는 패킷을 IP 주소 기준으로 직접
라우팅합니다. 흥미로운 점은, 같은 부모 인터페이스를 공유하는 ipvlan L3 컨테이너들은 서로 다른 서브넷에
속해 있어도 외부 라우터의 개입 없이 커널 내부에서 곧바로 통신할 수 있다는 것입니다. 대신 이 모드는 브로드캐스트
기반 프로토콜(DHCP 클라이언트가 브로드캐스트로 서버를 찾는 것 등)에 의존하는 워크로드에는 맞지 않으므로,
컨테이너에 고정 IP를 명시적으로 할당하는 것이 일반적입니다.

```bash
# L2 모드(기본값)
docker network create -d ipvlan \
  --subnet=192.168.30.0/24 \
  --gateway=192.168.30.1 \
  -o parent=eth0 \
  -o ipvlan_mode=l2 \
  ipv-l2-net

# L3 모드
docker network create -d ipvlan \
  --subnet=192.168.40.0/24 \
  -o parent=eth0 \
  -o ipvlan_mode=l3 \
  ipv-l3-net
```

L3 모드에서는 게이트웨이를 지정하지 않는 경우가 많다는 점도 특징입니다. 부모 인터페이스 자체가 이미 라우팅
역할을 하기 때문에, 전통적인 의미의 "이 서브넷의 게이트웨이 IP"라는 개념이 L2 모드에서와는 다르게 적용됩니다.

### macvlan과 ipvlan, 언제 무엇을 고를 것인가

두 드라이버는 겉보기 사용법이 비슷하지만 선택 기준은 비교적 명확합니다. 컨테이너가 물리 네트워크에서 완전히
독립된 장비처럼 보여야 하고(자체 MAC 주소가 필요한 레거시 소프트웨어, 네트워크 장비 에뮬레이션 등) 스위치
환경에 MAC 주소 개수 제한이 없다면 macvlan이 더 직관적입니다. 반대로 스위치나 클라우드 환경이 인터페이스당
MAC 주소 개수를 제한하거나, 애초에 대규모로 수백~수천 개의 컨테이너에 각각 물리망 IP를 부여해야 해서 MAC
주소 테이블(CAM 테이블) 부담을 줄이고 싶다면 ipvlan이 유리합니다. 두 드라이버 모두 Docker Engine 29에서도
libnetwork의 기존 드라이버 구조를 그대로 유지하고 있으며, 16장에서 다룰 nftables 방화벽 백엔드 전환의 직접적인
영향권 밖에 있습니다. nftables 백엔드 전환은 주로 브리지 네트워크의 포트 게시 경로에 관련된 변경이고,
macvlan/ipvlan은 애초에 호스트의 NAT/포트 매핑 계층 자체를 거치지 않으므로 이 전환과 사실상 무관하게 동작합니다.

## 14.4 공통 제약 — 호스트와 컨테이너가 직접 통신하지 못하는 이유

macvlan과 ipvlan을 처음 써본 사람들이 거의 예외 없이 마주치는 문제가 하나 있습니다. 컨테이너는 물리
네트워크의 다른 장비들과는 잘 통신하는데, 정작 컨테이너를 실행하고 있는 호스트 자신과는 ping조차 되지
않는 현상입니다. 이는 설정 실수가 아니라 리눅스 커널의 구조적인 제약입니다.

macvlan/ipvlan 서브인터페이스는 부모 인터페이스를 통해 들어오고 나가는 트래픽을 MAC(macvlan) 또는
IP(ipvlan) 기준으로 분배하는 방식으로 동작하는데, 호스트 자신의 IP 스택과 부모 인터페이스에 붙어 있는
서브인터페이스들 사이에는 이런 분배 경로가 존재하지 않습니다. 조금 더 정확히 말하면, macvlan/ipvlan
서브인터페이스에서 나간 패킷이 같은 물리 인터페이스로 다시 돌아 들어오는 경로 자체가 커널 레벨에서 만들어지지
않습니다. 호스트의 `eth0`과 그 위에 만들어진 macvlan 서브인터페이스는 부모-자식 관계에 있지만, 이 관계는
"하나의 물리 매체를 공유한다"는 의미이지 "서로 자유롭게 통신할 수 있는 논리적 링크로 연결되어 있다"는 의미가
아닙니다. 이 제약은 macvlan bridge 모드든 ipvlan L2 모드든 동일하게 적용되는, 커널 드라이버 자체의 설계상
한계입니다.

### macvlan bridge 트릭으로 우회하기

이 문제를 해결하는 가장 널리 알려진 방법은 호스트에도 컨테이너와 같은 부모 인터페이스를 사용하는 macvlan
서브인터페이스를 하나 더 만들어, 호스트가 "물리 네트워크 관점에서 또 다른 macvlan 장비"인 것처럼 위장하는
것입니다.

```bash
# 호스트에 macvlan 서브인터페이스를 하나 만들어 컨테이너와 같은 대역에 배치
sudo ip link add mv-shim link eth0 type macvlan mode bridge
sudo ip addr add 192.168.10.200/24 dev mv-shim
sudo ip link set mv-shim up

# 이제 호스트의 mv-shim을 통해 macvlan 네트워크의 컨테이너와 통신 가능
ping 192.168.10.101
```

이 방식이 동작하는 이유는, 호스트의 `eth0` 자체가 아니라 `eth0`을 부모로 하는 또 다른 macvlan
서브인터페이스(`mv-shim`)를 통해 통신하기 때문입니다. 즉 호스트조차 "부모 인터페이스에 매달린 또 하나의
macvlan 자식"이 되어야 앞서 설명한 제약을 피해갈 수 있습니다. Docker는 이 패턴을 편의를 위해 문서화하고
있지만, 사용자가 직접 `ip link`로 구성해야 하는 다소 수동적인 절차이며 Docker CLI가 자동으로 만들어 주지는
않습니다. ipvlan에서도 동일한 원리로 부모 인터페이스 위에 호스트용 ipvlan 서브인터페이스를 하나 추가해
문제를 우회할 수 있습니다.

이런 제약이 있다는 사실 자체가 실무적으로 중요한 이유는, macvlan/ipvlan 네트워크에 올린 컨테이너에 대해
호스트에서 헬스체크를 수행하거나 모니터링 에이전트가 호스트에서 직접 컨테이너 IP로 접속해 상태를 확인하려는
설계를 세울 때 이 제약을 미리 감안해야 하기 때문입니다. 그렇지 않으면 "물리 네트워크의 다른 서버에서는
컨테이너에 접속되는데 정작 컨테이너를 실행 중인 호스트 자신에서는 안 된다"는, 처음 겪으면 매우 당혹스러운
증상으로 나타납니다.

## 14.5 host 네트워크 모드 — 네임스페이스 분리를 포기하다

지금까지 다룬 브리지, 오버레이, macvlan, ipvlan은 모두 컨테이너마다 독립된 네트워크 네임스페이스를 만들고,
그 네임스페이스 안에 어떤 방식으로든 네트워크 인터페이스를 구성해 넣는다는 공통점이 있었습니다. host
네트워크 모드는 이 전제 자체를 뒤집습니다. 2장에서 다룬 것처럼 리눅스는 `clone()`이나 `unshare()`에
`CLONE_NEWNET` 플래그를 주어 새로운 네트워크 네임스페이스를 만드는데, `--network host`로 실행한 컨테이너는
애초에 이 플래그를 사용하지 않습니다. 즉 컨테이너의 프로세스는 호스트의 초기 네트워크 네임스페이스를 그대로
공유하며, 호스트가 보는 모든 인터페이스, 라우팅 테이블, iptables/nftables 규칙, 포트를 그대로 봅니다.

```bash
docker run -d --network host --name web-host nginx:latest
```

이 컨테이너 안의 nginx는 컨테이너 전용 IP를 갖지 않고, 호스트의 IP로 직접 80번 포트를 리슨합니다. 별도의
포트 매핑(`-p`)이 필요 없으며, 애초에 `-p` 옵션을 지정해도 무시됩니다(네트워크 네임스페이스가 분리되어 있지
않으므로 매핑할 대상 네임스페이스 자체가 없습니다).

### 성능 이점

host 모드의 가장 큰 장점은 네트워크 경로에서 veth 페어, 브리지, conntrack을 거치는 NAT 단계가 완전히
사라진다는 것입니다. 브리지 네트워크에서 패킷이 컨테이너에 도달하려면 물리 NIC → 커널 네트워크 스택 →
docker0 브리지 → veth 페어 → 컨테이너 네트워크 네임스페이스라는 여러 단계를 거쳐야 하지만, host 모드에서는
이 모든 중간 단계가 사라지고 애플리케이션이 호스트의 소켓 계층에 사실상 직접 접근합니다. 초당 수만~수십만
연결을 처리해야 하는 고성능 프록시, 로드밸런서, 패킷 캡처 도구처럼 네트워크 지연과 처리량이 민감한
워크로드에서 host 모드가 선호되는 이유입니다.

### 트레이드오프

이 이점은 명확한 대가를 동반합니다. 네트워크 네임스페이스가 분리되지 않는다는 것은 곧 포트 네임스페이스도
공유한다는 뜻이므로, 같은 호스트에서 host 모드로 실행되는 컨테이너 두 개가 같은 포트를 리슨하려 하면
평범한 리눅스 프로세스 두 개가 같은 포트를 두고 충돌하는 것과 똑같은 방식으로 실패합니다. 브리지 네트워크에서
누리던 "컨테이너마다 격리된 네트워크 스택 덕분에 포트 번호가 서로 겹쳐도 무방하다"는 편의는 host 모드에서
사라집니다.

보안 관점에서도 host 모드는 격리를 포기하는 선택입니다. 컨테이너 프로세스가 호스트의 모든 네트워크
인터페이스와 라우팅 정보에 접근할 수 있으므로, 컨테이너가 침해당했을 때 공격자가 볼 수 있는 네트워크
표면적이 넓어집니다. 또한 컨테이너 안에서 `iptables`나 `nft` 같은 도구로 실제 호스트의 방화벽 규칙에 영향을
줄 수 있는 권한(`NET_ADMIN` capability와 결합될 경우)을 가지면, 호스트 자체의 방화벽 정책을 컨테이너에서
직접 조작하는 것도 가능해집니다. 따라서 host 모드는 신뢰할 수 있는 워크로드이면서 성능이 명확한 우선순위인
경우로 한정해서 쓰는 것이 일반적인 권고입니다.

## 14.6 none 네트워크 모드 — 완전한 격리와 수동 구성의 자유

none 네트워크 모드는 host 모드와 정반대의 극단입니다. `--network none`으로 실행한 컨테이너는 독립된 네트워크
네임스페이스를 가지지만, 그 안에 루프백(`lo`) 인터페이스 외에는 아무것도 없습니다. veth 페어도, 브리지 연결도,
IP 주소도 할당되지 않습니다.

```bash
docker run -it --network none alpine:latest ip addr
```

이 명령을 실행해 보면 `lo` 인터페이스 하나만 보이고, 그마저도 기본적으로 UP 상태가 아닌 경우가 많습니다.
이 컨테이너는 사실상 외부 세계와 어떤 방식으로도 패킷을 주고받을 수 없는 상태입니다.

none 모드가 실무에서 쓰이는 대표적인 상황은 두 가지입니다. 첫째, 애초에 네트워크가 필요 없는 순수 배치
작업(파일 변환, 로컬 데이터 처리 등)에서 공격 표면을 최소화하기 위해 의도적으로 네트워크 접근 자체를
차단하는 경우입니다. 둘째, Docker의 기본 네트워킹 드라이버가 아닌 다른 네트워킹 솔루션(예: 별도의 CNI
플러그인, SR-IOV 기반 직접 연결, 특수한 하드웨어 오프로드 경로)을 컨테이너에 수동으로 연결하고 싶을 때,
Docker가 자체적으로 아무 인터페이스도 만들지 않도록 none 모드로 컨테이너를 띄운 뒤 컨테이너의 네트워크
네임스페이스(`/var/run/docker/netns/` 아래 또는 `nsenter`로 접근 가능한 네임스페이스)에 외부 도구가 직접
개입해 인터페이스를 붙이는 패턴입니다. Kubernetes와 무관하게 Docker를 직접 오케스트레이션 레이어의 하위
컴포넌트로 쓰는 일부 플랫폼이나, 컨테이너 네트워킹을 실험하는 개발 환경에서 이런 패턴을 볼 수 있습니다.
이때 Docker는 컨테이너의 네임스페이스만 만들어주는 역할을 하고, 실제 네트워킹 구성의 책임은 완전히 외부
도구로 넘어갑니다.

## 14.7 다섯 가지 모드 한눈에 비교

지금까지 다룬 드라이버들, 그리고 12~13장에서 다룬 브리지/오버레이까지 포함해 핵심 특성을 정리하면 다음과
같습니다.

| 모드 | 네트워크 네임스페이스 | 컨테이너 IP | NAT 필요 여부 | 호스트-컨테이너 통신 | 주 용도 |
|---|---|---|---|---|---|
| bridge(사용자 정의) | 분리 | 사설 대역, docker0 등 경유 | 필요(포트 매핑) | 가능 | 범용 단일 호스트 |
| overlay | 분리 | VXLAN 오버레이 대역 | 필요(ingress 등) | 가능(호스트도 참여 시) | Swarm 멀티호스트 |
| macvlan | 분리 | 물리망 대역, 고유 MAC | 불필요 | 기본 불가(우회 필요) | 레거시 IP/MAC 요구 |
| ipvlan | 분리 | 물리망 대역, MAC 공유 | 불필요 | 기본 불가(우회 필요) | MAC 제한 환경 |
| host | 미분리(호스트 공유) | 호스트 IP 그대로 | 불필요 | 구분 자체가 없음 | 고성능, 신뢰 워크로드 |
| none | 분리(루프백만) | 없음 | 해당 없음 | 불가 | 완전 격리, 수동 구성 |

## 핵심 요약

- macvlan은 컨테이너마다 고유한 MAC 주소를 부여해 물리 네트워크에서 독립된 장비처럼 보이게 하며,
  bridge(기본값)/vepa/private/passthru 네 가지 모드를 제공한다. 부모 인터페이스는 물리 인터페이스뿐 아니라
  `eth0.20`처럼 802.1Q VLAN 서브인터페이스로도 지정할 수 있다.
- macvlan은 물리 NIC나 스위치가 promiscuous mode 및 포트당 다중 MAC 주소 학습을 지원해야 하며, 퍼블릭
  클라우드의 가상 NIC 환경에서는 이 조건이 충족되지 않아 별도 설정 없이는 동작하지 않는 경우가 많다.
- ipvlan은 부모 인터페이스의 MAC 주소를 컨테이너들이 공유하고 IP 기준으로 트래픽을 분배하므로, MAC 주소
  개수를 제한하는 스위치/클라우드 환경에서 macvlan의 대안이 된다. L2 모드는 같은 브로드캐스트 도메인에서
  동작하고, L3 모드는 브로드캐스트를 버리는 대신 외부 라우터 없이 서로 다른 서브넷 간 통신을 가능하게 한다.
- macvlan/ipvlan 모두 커널 구조상 호스트와 컨테이너 간 직접 통신이 기본적으로 불가능하며, 호스트에 같은
  부모를 쓰는 별도의 서브인터페이스를 만들어 우회하는 것이 일반적인 해결책이다.
- host 모드는 네트워크 네임스페이스 자체를 분리하지 않아 NAT 오버헤드가 사라지고 성능이 좋아지지만,
  포트 네임스페이스도 공유되므로 포트 충돌과 격리 약화라는 트레이드오프를 동반한다.
- none 모드는 루프백만 남기고 완전히 격리하며, 네트워크가 불필요한 워크로드나 외부 도구가 네트워크
  네임스페이스를 수동으로 구성하는 특수한 통합 시나리오에 쓰인다.
- macvlan/ipvlan은 Docker Engine 29에서도 기존 libnetwork 드라이버 구조를 그대로 유지하며, 16장에서 다룰
  nftables 방화벽 백엔드 전환의 영향권 밖에 있다(이 전환은 주로 브리지 네트워크의 포트 게시 경로에 관련된다).

## 실습

다음 실습은 물리 스위치에 접근할 수 있는 온프레미스 리눅스 호스트를 전제로 합니다. 클라우드 인스턴스에서는
가상 NIC의 MAC 필터링 때문에 macvlan 부분이 그대로 동작하지 않을 수 있습니다.

```bash
# 1) 부모로 쓸 물리 인터페이스 확인
ip -br link show
# 확인 포인트: eth0(또는 enpXsY) 인터페이스 이름을 확인합니다. 이후 명령에서 이 이름을 그대로 사용합니다.

# 2) macvlan 네트워크 생성 및 컨테이너 두 개 연결
docker network create -d macvlan \
  --subnet=192.168.10.0/24 --gateway=192.168.10.1 \
  -o parent=eth0 mv-net

docker run -d --name mv-a --network mv-net --ip 192.168.10.101 alpine:latest sleep infinity
docker run -d --name mv-b --network mv-net --ip 192.168.10.102 alpine:latest sleep infinity

# 3) 컨테이너 간 통신 확인 (같은 macvlan 네트워크, bridge 모드)
docker exec mv-a ping -c 3 192.168.10.102
# 확인 포인트: 정상적으로 응답이 오면 커널 macvlan bridge 모드가 정상 동작 중임을 의미합니다.

# 4) 호스트에서 컨테이너로 ping (기본적으로 실패해야 정상)
ping -c 2 192.168.10.101
# 확인 포인트: 응답 없음(Destination Host Unreachable 또는 타임아웃)이 정상입니다.
# 이것이 14.4절에서 설명한 커널 제약입니다.

# 5) macvlan bridge 트릭으로 호스트-컨테이너 통신 우회
sudo ip link add mv-shim link eth0 type macvlan mode bridge
sudo ip addr add 192.168.10.200/24 dev mv-shim
sudo ip link set mv-shim up
ping -c 3 192.168.10.101
# 확인 포인트: 이번에는 정상적으로 응답이 옵니다. mv-shim을 삭제하려면
# sudo ip link delete mv-shim 을 실행합니다.

# 6) host 네트워크 모드 비교
docker run -d --network host --name web-host nginx:latest
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:80
# 확인 포인트: 호스트의 80번 포트로 바로 접속되며, docker ps로 봐도 PORTS 칼럼이 비어 있는(포트 매핑이
# 표시되지 않는) 것을 확인합니다.

# 7) none 네트워크 모드 확인
docker run --rm --network none alpine:latest ip addr
# 확인 포인트: lo 인터페이스 외에 아무것도 없는 것을 확인합니다.

# 8) 정리
docker rm -f mv-a mv-b web-host 2>/dev/null
docker network rm mv-net
sudo ip link delete mv-shim 2>/dev/null
```

다음 장에서는 지금까지 IP 레벨에서 다룬 통신을 한 단계 위, 즉 이름으로 서로를 찾는 DNS와 서비스
디스커버리, 그리고 포트 매핑이 실제로 어떤 커널 경로를 거쳐 패킷을 전달하는지를 다룹니다.
