# 13장. 오버레이 네트워크와 VXLAN — Swarm 멀티호스트 네트워킹

12장에서는 단일 호스트 안에서 브리지와 veth pair가 컨테이너를 연결하는 방식을 자세히 살펴봤습니다. 이
장에서는 그 범위를 호스트 한 대 밖으로 확장합니다. 여러 대의 서버에 흩어져 떠 있는 컨테이너들이 마치
같은 스위치에 꽂혀 있는 것처럼 통신하려면 어떤 기술이 필요한지, 그리고 Docker Swarm 모드가 이 기술을
바탕으로 어떻게 멀티호스트 서비스 네트워킹을 구성하는지가 이 장의 주제입니다. CNM 관점에서 보면 오버레이
네트워크는 결국 11장에서 설명한 Network 객체를 VXLAN이라는 기술로 구현한 드라이버일 뿐이며, Sandbox와
Endpoint의 개념적 역할은 브리지 드라이버와 다르지 않습니다. 달라지는 것은 오직 "같은 Network에 속한다"는
멤버십을 물리적으로 다른 호스트 사이에서 어떻게 실현하느냐입니다.

## 13.1 단일 호스트 브리지의 한계

12장에서 다룬 리눅스 브리지는 근본적으로 L2 스위치를 소프트웨어로 구현한 것입니다. 브리지에 연결된
인터페이스들은 물리적으로 같은 스위치에 꽂혀 있는 것과 동일하게 취급되고, 이더넷 프레임이 MAC 주소를
기준으로 전달됩니다. 그런데 이 전제 자체가 브리지의 한계를 만듭니다. 브리지는 하나의 리눅스 커널 안에
존재하는 디바이스이므로, 다른 물리 호스트에 있는 브리지와 자동으로 이어지지 않습니다. 호스트 A의
`docker0`에 연결된 컨테이너와 호스트 B의 `docker0`에 연결된 컨테이너는, 아무 조치도 하지 않으면 서로
완전히 다른 사설 IP 대역에 속한 채 서로의 존재조차 알지 못하는 상태로 남습니다.

물론 호스트 간 라우팅을 수동으로 구성하거나, 각 호스트의 브리지 대역이 겹치지 않게 관리하면서 정적
라우트를 깔아주는 식으로 억지로 연결할 수는 있습니다. 하지만 이런 방식은 호스트 수가 늘어날수록 설정
복잡도가 기하급수적으로 늘어나고, 컨테이너가 재스케줄링되어 다른 호스트로 옮겨갈 때마다 라우팅 정보를
다시 갱신해야 하는 근본적인 확장성 문제를 가지고 있습니다. 여러 호스트에 걸쳐 컨테이너를 자유롭게
배치하고 이동시키는 오케스트레이션(Swarm, 그리고 넓게는 Kubernetes)을 실현하려면, 물리적인 네트워크
토폴로지를 신경 쓰지 않고도 논리적으로 같은 L2 네트워크에 속한 것처럼 통신할 수 있는 방법이 필요합니다.

이 문제를 푸는 접근이 오버레이 네트워크입니다. 오버레이 네트워크는 이미 존재하는 L3(IP) 연결성 위에,
캡슐화(encapsulation)라는 기법으로 가상의 L2 네트워크를 하나 더 얹는 방식입니다. 물리적으로는 호스트
A와 호스트 B가 평범한 IP 라우팅으로만 연결되어 있어도, 그 위에 캡슐화된 터널을 통해 마치 같은 스위치에
연결된 것처럼 이더넷 프레임을 주고받을 수 있게 만드는 것이 오버레이의 핵심 아이디어입니다. "L3 위에
가상 L2를 얹는다"는 표현이 바로 이 구조를 가리킵니다.

## 13.2 VXLAN의 원리

Docker의 오버레이 드라이버가 이 캡슐화를 구현하는 데 사용하는 기술이 VXLAN(Virtual eXtensible Local
Area Network)입니다. VXLAN은 RFC 7348로 표준화된 캡슐화 프로토콜로, 원래 대규모 데이터센터에서 가상
머신들을 위한 멀티테넌트 L2 네트워크를 대량으로 만들어야 하는 요구에서 출발했습니다. 컨테이너
오버레이는 이 기술을 그대로 가져다 쓰고 있습니다.

VXLAN의 동작 원리는 세 가지 요소로 이해할 수 있습니다.

**VNI(VXLAN Network Identifier)**: VXLAN은 24비트 크기의 식별자인 VNI로 논리적인 L2 네트워크를
구분합니다. 24비트이므로 이론적으로 약 1,600만 개에 달하는 서로 다른 오버레이 네트워크를 동시에
운용할 수 있습니다. `docker network create -d overlay`로 오버레이 네트워크를 하나 만들면, 그 네트워크
전체가 하나의 VNI에 대응됩니다. 같은 VNI를 공유하는 Endpoint들끼리는 서로 같은 논리 L2 네트워크에
속한 것으로 취급되어 이더넷 프레임 수준에서 통신할 수 있고, 다른 VNI에 속한 트래픽과는 완전히
격리됩니다.

**UDP 캡슐화**: VXLAN은 원본 이더넷 프레임 전체(그 안에 담긴 IP 패킷까지 포함)를 UDP 데이터그램의
페이로드로 감싸서 전송합니다. 이 UDP 패킷의 목적지 포트로 IANA가 VXLAN 전용으로 할당해 둔
**4789번 포트**를 사용하는 것이 표준 동작입니다(과거 일부 벤더 구현이 다른 포트를 기본값으로 쓰던 시절이
있었지만, RFC 7348 이후로는 4789번이 사실상의 표준 목적지 포트로 정착했습니다). 이 캡슐화 덕분에
오버레이 네트워크의 패킷은 물리 네트워크 입장에서 보면 그냥 평범한 UDP 트래픽일 뿐이며, 물리 네트워크
장비는 그 안에 어떤 논리적인 L2 프레임이 들어 있는지 전혀 알 필요가 없습니다. VXLAN을 종단하는 지점을
VTEP(VXLAN Tunnel Endpoint)이라고 부르는데, Swarm 환경에서는 각 호스트(정확히는 각 노드의 커널)가
VTEP 역할을 수행합니다.

**MTU 오버헤드**: 원본 프레임을 통째로 UDP로 한 번 더 감싸는 구조이다 보니, VXLAN 캡슐화에는 추가
헤더만큼의 오버헤드가 붙습니다. 외부 IP 헤더, UDP 헤더, VXLAN 헤더가 차례로 덧붙기 때문에, 일반적으로
VXLAN 캡슐화는 원본 프레임에 50바이트 안팎의 오버헤드를 추가하는 것으로 알려져 있습니다. 이 때문에
물리 네트워크의 MTU가 일반적인 이더넷 표준값인 1500바이트로 고정되어 있는 환경에서, 컨테이너 내부의
MTU도 똑같이 1500바이트로 두면 캡슐화 과정에서 오버헤드를 더한 실제 패킷 크기가 물리 MTU를 초과해
버립니다. 그 결과로 패킷이 단편화(fragmentation)되거나, 단편화가 허용되지 않는 조건에서는 아예 폐기되어
버리는 문제가 생길 수 있습니다. 이런 이유로 오버레이 네트워크를 사용할 때는 컨테이너 쪽 인터페이스의
MTU를 물리 MTU보다 오버헤드만큼 낮게(일반적으로 1450바이트 안팎으로) 설정해 캡슐화 이후에도 물리
MTU 한도 안에 들어오도록 관리하는 것이 권장됩니다. Docker의 오버레이 드라이버는 대체로 이런 MTU 조정을
자동으로 처리하지만, 물리 네트워크 자체의 MTU가 표준보다 작게 설정된 환경(일부 클라우드 VPC, 특정
터널링 구간 등)에서는 수동으로 재확인해야 하는 경우도 있습니다.

## 13.3 Swarm 모드의 오버레이 — 컨트롤 플레인과 데이터 플레인의 분리

Swarm 모드에서 오버레이 네트워크가 실제로 동작하려면 두 가지가 함께 갖춰져야 합니다. 하나는 "어떤
컨테이너가 어느 호스트에 있고, 그 호스트의 VTEP 주소가 무엇인지"를 클러스터 전체가 알아야 한다는 것이고,
다른 하나는 그 정보를 바탕으로 실제 패킷을 VXLAN으로 캡슐화해서 주고받는 것입니다. 이 둘은 Swarm
아키텍처에서 컨트롤 플레인과 데이터 플레인이라는 서로 다른 계층으로 명확히 분리되어 있습니다.

컨트롤 플레인은 클러스터 멤버십과 네트워크 상태를 동기화하는 역할을 합니다. Swarm 노드들은 gossip
프로토콜 기반의 분산 상태 전파 메커니즘으로 서로의 존재와 상태를 알립니다. 이 계열의 기술적 뿌리는
HashiCorp의 Serf 프로젝트와 그 안에 구현된 memberlist 알고리즘(SWIM 프로토콜 계열)에 닿아 있습니다.
gossip 프로토콜의 핵심 아이디어는 중앙 조정자 없이 노드들이 서로 임의로 정보를 주고받으며 점진적으로
클러스터 전체가 같은 상태로 수렴하도록 만드는 것입니다. Swarm에서는 이 메커니즘을 통해 어떤 서비스의
어떤 태스크(컨테이너)가 어느 노드에서 실행 중인지, 그리고 오버레이 네트워크에 속한 각 Endpoint의 IP와
MAC 주소, 그 Endpoint가 있는 노드의 실제 IP(VTEP 주소)가 무엇인지 같은 정보가 클러스터 전체에 전파됩니다.
이 정보가 있어야 각 노드의 커널이 "이 MAC 주소로 가는 프레임은 저 물리 IP의 노드로 캡슐화해서 보내야
한다"는 판단을 내릴 수 있습니다.

데이터 플레인은 이렇게 컨트롤 플레인이 동기화해 둔 정보를 바탕으로 실제 애플리케이션 트래픽을 처리하는
계층입니다. 컨테이너 A가 다른 노드에 있는 컨테이너 B로 패킷을 보내면, 그 패킷은 먼저 로컬 호스트의
오버레이 네트워크 인터페이스로 들어가고, 컨트롤 플레인이 전파해 둔 정보를 참고해 목적지가 있는 노드의
IP로 VXLAN 캡슐화되어 UDP 4789 포트를 통해 물리 네트워크로 나갑니다. 상대 노드는 이 패킷을 받아
캡슐을 벗기고, 원본 이더넷 프레임을 그 노드의 오버레이 브리지를 통해 컨테이너 B의 veth로 전달합니다.
이 과정에서 실제 애플리케이션 데이터는 gossip 메시지와는 완전히 분리된 경로(VXLAN UDP 캡슐)로
전달되며, 컨트롤 플레인 트래픽 양이 데이터 플레인의 처리량에 직접적인 영향을 주지 않도록 설계되어
있습니다. 이 분리 덕분에 클러스터의 멤버십 정보량이 늘어나더라도(노드나 서비스 수가 증가하더라도)
실제 패킷 전달 성능 자체는 별도로 확장될 수 있습니다.

## 13.4 ingress 네트워크와 라우팅 메시

Swarm 모드에서 서비스를 만들고 포트를 게시하면(`docker service create --publish` 또는 `docker
service create -p`), 그 포트는 단순히 서비스의 태스크가 실제로 떠 있는 노드에서만 열리는 것이 아니라
**클러스터의 모든 노드**에서 동시에 리스닝됩니다. 이 동작을 라우팅 메시(routing mesh)라고 부르고, 이를
구현하는 특수한 오버레이 네트워크가 `ingress`라는 이름으로 Swarm 초기화 시 자동으로 만들어집니다.

라우팅 메시가 제공하는 사용자 경험은 단순합니다. 서비스의 태스크가 세 개 노드 중 한 곳에서만 실제로
실행 중이더라도, 클러스터의 어느 노드로 요청을 보내든 결과적으로 그 서비스에 도달합니다. 이 동작의
핵심은 각 노드의 커널에 구성된 IPVS(IP Virtual Server)입니다. IPVS는 리눅스 커널에 내장된 L4
로드밸런서로, 원래 리눅스 방화벽/로드밸런싱 스택의 일부로 오랫동안 존재해 온 기술입니다. Swarm은 각
노드에 IPVS 규칙을 구성해서, 게시된 포트로 들어온 요청을 실제로 서비스를 실행 중인 노드들의 ingress
네트워크 상의 컨테이너 IP로 로드밸런싱하도록 만듭니다.

구체적인 흐름은 다음과 같습니다. 클라이언트가 노드 X의 8080번 포트(게시된 포트)로 요청을 보냈는데,
정작 그 서비스의 태스크는 노드 Y에서만 실행 중이라고 가정하겠습니다. 노드 X는 자신이 그 서비스를
직접 실행하고 있지 않더라도, IPVS 규칙에 따라 이 요청을 ingress 오버레이 네트워크를 통해 노드 Y의
컨테이너로 전달합니다. 이 전달 과정에서 출발지 주소는 ingress 네트워크 내부의 주소로 SNAT되므로,
서비스 컨테이너 입장에서는 요청이 어느 노드를 거쳐왔든 ingress 네트워크의 주소에서 온 것으로
보입니다. 이 특성 때문에 클라이언트의 실제 원본 IP를 서비스 컨테이너에서 그대로 보존하기가 어렵다는
점은 라우팅 메시의 잘 알려진 제약 중 하나입니다. 원본 클라이언트 IP 보존이 중요한 서비스라면 이 제약을
반드시 감안해서 설계해야 합니다.

## 13.5 2026년 현재 Swarm의 위치

Swarm 모드는 한때 Kubernetes에 밀려 개발이 멈추는 것 아니냐는 이야기가 여러 차례 나왔지만, 2026년
현재 시점에서 Docker Swarm 모드는 deprecated 상태가 아니며 여전히 유지보수되고 있습니다. 공식 문서
어디에도 폐지 예정이라는 표시는 없고, Docker Engine의 릴리스마다 Swarm 관련 기능도 함께 다뤄지고
있습니다. 특히 Docker Swarm의 상용 지원을 이어받은 Mirantis는 엔터프라이즈 고객을 대상으로 Swarm에
대한 장기 지원을 2030년까지 약속한 상태입니다. Kubernetes만큼의 생태계 규모나 화제성은 아니지만,
운영 복잡도를 낮게 유지하고 싶은 중소규모 환경이나 단순한 오케스트레이션으로 충분한 워크로드에서는
Swarm이 여전히 실용적인 선택지로 남아 있습니다.

다만 최신 변화와 관련해서 한 가지 분명히 짚어야 할 제약이 있습니다. 12장에서 예고했던 Docker Engine
29의 실험적 nftables 방화벽 백엔드(`--firewall-backend=nftables`)는, 2026년 9월 현재 기준으로 Swarm
모드의 오버레이 네트워크가 필요로 하는 방화벽 규칙 세트가 아직 nftables로 완전히 마이그레이션되지
않았습니다. 그 결과 Swarm 모드가 활성화된 노드에서는 이 nftables 백엔드를 켤 수 없다는 제약이 현재
존재합니다. 즉 nftables 전환은 아직 브리지/일반 네트워킹 경로부터 단계적으로 진행 중이며, Swarm
오버레이까지 이 전환이 완료되는 것은 이후 릴리스의 과제로 남아 있습니다. 이 nftables 전환의 전체적인
배경과 구조, 그리고 왜 오버레이 네트워크 쪽 마이그레이션이 더 시간이 걸리는지는 16장(방화벽 백엔드의
전환)에서 자세히 다룹니다. 지금 시점에서는 "Swarm을 쓰는 노드는 당분간 기존 iptables 기반 방화벽
경로를 그대로 사용해야 한다"는 제약 사항만 기억해 두면 충분합니다.

## 13.6 Swarm 없이 오버레이 드라이버만 실습하기

오버레이 네트워크는 Swarm 모드의 전유물이 아닙니다. libnetwork의 overlay 드라이버 자체는 Swarm
클러스터 상태 관리와는 별개의 계층이므로, Swarm을 초기화하지 않고도 단일 데몬에서 순수하게 오버레이
드라이버의 캡슐화 동작만 확인하는 것이 가능합니다. 다만 오버레이 네트워크는 원래 여러 호스트에 걸친
멤버십 조율을 전제로 설계되었기 때문에, Swarm의 컨트롤 플레인(gossip 기반 상태 동기화) 없이는 그
멤버십 정보를 어디선가 대신 제공해야 합니다. `docker network create`에 `--attachable` 옵션을 붙이면,
Swarm 서비스가 아닌 일반 `docker run` 컨테이너도 그 오버레이 네트워크에 직접 연결할 수 있게 됩니다.

```bash
docker network create -d overlay --attachable demo-overlay
```

단일 호스트에서 이 명령을 실행하면 Swarm이 초기화되어 있지 않아도(또는 Swarm이 초기화된 상태에서도)
overlay 드라이버로 네트워크가 만들어지고, 그 네트워크에 일반 컨테이너를 연결해 VXLAN 인터페이스가
실제로 생성되는 것을 확인할 수 있습니다. 다만 이 상태에서는 노드가 하나뿐이므로 VXLAN 캡슐화가 실제로
다른 호스트로 나가는 모습까지는 관찰할 수 없습니다. 여러 호스트에 걸친 진짜 멀티호스트 오버레이
통신을 확인하려면 Swarm을 초기화해서 최소 두 개 이상의 노드를 조인시킨 뒤, `--attachable` 오버레이
네트워크에 각 호스트에서 컨테이너를 붙여 서로 핑을 주고받아 보는 방식이 가장 확실합니다. 이 실습은
아래 실습 섹션에서 안내합니다.

## 핵심 요약

- 단일 호스트의 리눅스 브리지는 커널 하나의 범위를 벗어나지 못하므로, 여러 호스트에 걸친 컨테이너
  통신에는 L3 연결 위에 가상 L2를 얹는 오버레이 네트워크가 필요하다.
- VXLAN은 24비트 VNI로 논리적 L2 네트워크를 구분하고, 원본 이더넷 프레임을 UDP(목적지 포트 4789,
  RFC 7348 표준)로 캡슐화해 전달한다. 캡슐화 오버헤드 때문에 오버레이 네트워크에서는 컨테이너 쪽 MTU를
  물리 MTU보다 낮춰 설정해야 단편화 문제를 피할 수 있다.
- Swarm 모드의 오버레이는 컨트롤 플레인(gossip/Serf·memberlist 계열 기술로 클러스터 멤버십과 네트워크
  상태를 동기화)과 데이터 플레인(VXLAN 캡슐화로 실제 패킷을 전달)이 명확히 분리되어 있다.
- ingress 네트워크는 Swarm의 라우팅 메시를 구현하는 특수한 오버레이 네트워크로, 게시된 포트를 모든
  노드에서 리스닝하게 하고 IPVS 기반 로드밸런싱으로 실제 태스크가 없는 노드로 들어온 요청도 올바른
  노드로 전달한다. 이 과정에서 SNAT이 일어나 원본 클라이언트 IP 보존이 어렵다는 제약이 있다.
- 2026년 현재 Docker Swarm 모드는 deprecated가 아니며, Mirantis가 엔터프라이즈 지원을 2030년까지
  약속했다. 다만 Docker Engine 29의 실험적 nftables 방화벽 백엔드는 Swarm 오버레이 네트워크 규칙
  마이그레이션이 아직 완료되지 않아 Swarm 모드에서는 활성화할 수 없다.
- `docker network create -d overlay --attachable`을 사용하면 Swarm 서비스 없이도 일반 컨테이너를
  오버레이 네트워크에 연결해 동작을 실습해볼 수 있다.

## 실습

다음 실습은 서로 통신 가능한 리눅스 호스트 두 대(Swarm 노드 두 개)를 전제로 합니다. 한 대만 있다면
1~2단계까지만 진행해도 오버레이 네트워크와 VXLAN 인터페이스가 생성되는 것은 확인할 수 있습니다.

```bash
# --- 노드 1(매니저) ---

# 1) Swarm 초기화
docker swarm init --advertise-addr <노드1의 IP>
# 확인 포인트: 출력되는 "docker swarm join --token ..." 명령을 기록해 둡니다.

# 2) attachable 오버레이 네트워크 생성
docker network create -d overlay --attachable demo-overlay
docker network inspect demo-overlay --format '{{.Driver}} {{.Scope}}'
# 확인 포인트: Driver가 overlay, Scope가 swarm으로 출력되는지 확인합니다.

# 3) 노드 1에서 컨테이너 실행
docker run -d --name c1 --network demo-overlay alpine sleep 3600

# --- 노드 2(워커) ---

# 4) 클러스터에 조인 (1번에서 출력된 토큰 사용)
docker swarm join --token <토큰> <노드1의 IP>:2377

# 5) 노드 2에서도 같은 오버레이 네트워크에 컨테이너 연결
docker run -d --name c2 --network demo-overlay alpine sleep 3600

# --- 다시 노드 1 또는 노드 2 아무 곳에서나 ---

# 6) 서로 다른 호스트의 컨테이너 사이 통신 확인
docker exec c1 ping -c 3 c2
# 확인 포인트: 내장 DNS로 c2의 이름이 해석되고, ping 응답이 정상적으로 오는지 확인합니다.

# 7) VXLAN 인터페이스 확인 (각 노드에서)
ip -d link show type vxlan
# 확인 포인트: vxlan 타입 인터페이스가 존재하고, 목적지 포트가 4789로 설정되어 있는지
# "dstport 4789" 항목으로 확인합니다.

# 8) 실제 VXLAN 캡슐화 트래픽 관찰 (선택, 물리 인터페이스 이름은 환경에 맞게 교체)
sudo tcpdump -i eth0 udp port 4789 -n -c 10
# 확인 포인트: c1에서 c2로 ping을 보내는 동안 4789번 포트로 UDP 패킷이 오가는지 확인합니다.

# 9) 정리
docker rm -f c1   # 노드 1에서
docker rm -f c2   # 노드 2에서
docker network rm demo-overlay
docker swarm leave --force   # 각 노드에서 (실습 클러스터를 계속 쓸 계획이 없다면)
```

다음 장에서는 오버레이와는 또 다른 방향으로, 컨테이너에 물리 네트워크 인터페이스와 동급의 주소를
직접 부여하는 macvlan과 ipvlan, 그리고 격리 자체를 최소화하는 host/none 네트워크 모드를 다룹니다.
