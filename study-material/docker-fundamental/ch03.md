# 3장. 자원 제어의 진화 — cgroups v1에서 v2로

2장에서 살펴본 네임스페이스는 컨테이너에게 "무엇이 보이는가"를 결정했습니다. 하지만 보이는 것과 실제로
쓸 수 있는 자원의 양은 별개의 문제입니다. 네임스페이스만 적용된 프로세스는 자신이 마치 독립된 시스템에
있는 것처럼 느끼지만, 여전히 호스트의 CPU와 메모리를 제한 없이 가져다 쓸 수 있습니다. 여러 컨테이너가
같은 호스트에서 실행되는 환경에서 이는 곧바로 문제가 됩니다. 컨테이너 하나가 메모리 누수를 일으키면
호스트 전체가 스와핑에 빠지거나 OOM 상황에 몰릴 수 있고, CPU를 많이 쓰는 컨테이너 하나가 나머지 컨테이너의
응답 속도를 떨어뜨릴 수 있습니다. 이 문제를 해결하는 커널 메커니즘이 **cgroups(control groups)**이며, 이
장에서는 cgroups의 구조가 v1에서 v2로 어떻게 재설계되었는지, 그리고 Docker/containerd/runc가 이를 어떻게
다루는지를 살펴봅니다.

## 3.1 cgroups v1의 구조와 그 한계

cgroups는 2007년 커널 2.6.24 무렵 처음 도입되었고, 이후 오랫동안 지금 우리가 "v1"이라고 부르는 형태로
자리 잡았습니다. cgroups v1의 핵심 개념은 **컨트롤러(controller, 리소스 종류별로 자원을 관리하는 서브시스템.
cpu, memory, blkio, pids 등)마다 독립적인 계층(hierarchy)을 가질 수 있다**는 것이었습니다. 즉 `cpu` 컨트롤러를
위한 트리 구조와 `memory` 컨트롤러를 위한 트리 구조를 완전히 다르게 구성할 수 있었고, 심지어 프로세스가
`cpu` 계층에서는 그룹 A에 속하면서 `memory` 계층에서는 그룹 B에 속하는 것도 가능했습니다.

이 유연함은 동시에 v1의 가장 큰 구조적 문제이기도 했습니다. 컨트롤러별로 계층이 따로 놀다 보니, 특정
프로세스 그룹에 대해 "CPU도 이만큼, 메모리도 이만큼" 식으로 일관되게 정책을 적용하려면 여러 계층에 걸쳐
같은 그룹 구조를 수작업으로 동기화해서 유지해야 했습니다. 실무에서는 대부분의 도구가 편의상 모든 컨트롤러를
동일한 트리 구조로 마운트해서 사용했지만(이것이 systemd나 Docker가 실제로 택한 방식이었습니다), 이는
어디까지나 관례였을 뿐 커널이 강제하는 규칙은 아니었습니다. 그 결과 컨트롤러 간 계층이 어긋난 환경에서는
디버깅이 매우 어려워졌고, 특히 하나의 프로세스가 여러 cgroup에 걸쳐 있을 수 있다는 점은 "이 프로세스가
정확히 어떤 자원 제한을 받고 있는가"를 파악하기 어렵게 만드는 근본 원인이었습니다.

또한 v1은 컨트롤러마다 설계 시점이 다르다 보니 인터페이스 파일 이름과 동작 방식에 일관성이 부족했고,
비특권 사용자에게 위임(delegation)하는 모델도 명확하지 않았습니다. 이런 문제들을 근본적으로 재설계하기
위해 커널 커뮤니티는 **cgroups v2(unified hierarchy)**를 새로 설계했고, 커널 4.5(2016년)부터 이를 사용할
수 있게 되었습니다.

## 3.2 cgroups v2의 unified hierarchy

cgroups v2의 핵심 아이디어는 단순합니다. **모든 컨트롤러가 하나의 동일한 계층 구조를 공유한다**는 것입니다.
프로세스는 이제 단 하나의 cgroup 경로에만 속하며, 그 경로에 어떤 컨트롤러들을 활성화할지는 상위 cgroup의
`cgroup.subtree_control` 파일을 통해 명시적으로 제어합니다. 이 구조 덕분에 "이 컨테이너에 대해 CPU, 메모리,
I/O 제한을 함께 건다"는 작업이 하나의 디렉터리 트리 안에서 일관되게 이루어집니다.

또한 v2는 계층 위임(delegation) 모델을 명확히 정의해서, 상위 프로세스가 하위 cgroup 서브트리의 관리
권한을 안전하게 위임할 수 있게 했습니다. 이는 rootless 컨테이너 런타임이나 systemd의 사용자 세션이 각자
자신의 cgroup 서브트리를 독립적으로 관리하는 것을 가능하게 하는 기반입니다. v1에서는 이런 위임 모델이
사실상 없었기 때문에, 비특권 프로세스가 자신의 자원 제한을 스스로 세밀하게 관리하는 것이 훨씬 어려웠습니다.

v2는 또한 프로세스 식별 및 정책 일관성을 높이기 위해, 하나의 cgroup 안에 프로세스와 하위 cgroup이 섞여
있을 수 없다는 "no internal process" 규칙 같은 제약을 도입했습니다. 이런 제약들은 개발자 입장에서는 다소
엄격하게 느껴질 수 있지만, 결과적으로 자원 제한 정책이 트리 구조 전체에서 예측 가능한 방식으로 적용되도록
보장합니다.

2026년 현재, 주요 리눅스 배포판(Ubuntu, Debian, Fedora, RHEL 계열, Arch 등) 대부분이 systemd 245 이상 및
최신 릴리스 기준으로 cgroup v2 unified hierarchy를 기본값으로 전환을 마친 상태입니다. 다만 오래전에 구축되어
업그레이드 없이 유지되고 있는 일부 legacy 환경이나, 특정 컨테이너 런타임/모니터링 스택이 아직 v1 전용
기능에 의존하고 있는 경우에는 v1 또는 v1/v2가 공존하는 하이브리드 모드(`systemd.unified_cgroup_hierarchy=0`
커널 부팅 파라미터로 강제 전환하거나, 일부 컨트롤러만 v1 방식으로 마운트하는 구성)를 여전히 볼 수 있습니다.
새로운 환경을 구축한다면 v2를 기본으로 삼는 것이 사실상 표준이지만, 기존 인프라를 다룰 때는 어떤 모드로
동작 중인지 먼저 확인하는 습관이 필요합니다.

## 3.3 Docker/containerd/runc가 cgroup을 다루는 방식

runc는 컨테이너를 실행할 때 지정된 cgroup 경로 아래에 컨테이너 프로세스를 배치하고, OCI Runtime Spec의
`linux.resources` 필드에 명시된 제한(CPU, 메모리, I/O, PID 수 등)을 해당 cgroup의 제어 파일에 기록합니다.
이 과정에서 실제로 cgroup 디렉터리를 만들고 관리하는 방식에는 크게 두 가지 드라이버가 있습니다.

**cgroupfs 드라이버**는 runc(그리고 상위의 containerd, dockerd)가 `/sys/fs/cgroup` 아래에 직접 디렉터리를
만들고 파일을 써서 cgroup을 관리하는 방식입니다. 단순하고 직접적이지만, systemd가 관리하는 시스템에서는
systemd가 자신의 관점에서 cgroup 트리를 관리하려고 하기 때문에 두 관리 주체가 충돌할 여지가 있습니다.

**systemd 드라이버**는 runc가 cgroup을 직접 조작하는 대신, systemd에게 D-Bus API를 통해 "이런 자원 제한을
가진 scope/slice 유닛을 만들어 달라"고 요청하는 방식입니다. systemd가 init 시스템으로 cgroup 트리 전체의
소유권을 가지고 있는 대부분의 현대 리눅스 배포판에서는 이 방식이 권장됩니다. 두 관리 주체가 같은 트리를
서로 다른 방식으로 건드리는 상황을 피할 수 있기 때문입니다. 특히 cgroup v2 환경에서 systemd가 init으로
동작 중이라면 systemd 드라이버를 사용하는 것이 사실상 표준적인 권장 사항이며, 최신 Docker Engine/containerd
기본 설정도 systemd가 감지되는 환경에서는 systemd 드라이버를 기본값으로 채택하는 방향으로 정리되어 있습니다.
다만 정확한 기본값과 자동 감지 로직은 Docker Engine 버전에 따라 달라질 수 있으므로, 실제 운영 환경에서는
아래 명령으로 직접 확인하는 것이 가장 확실합니다.

```bash
docker info --format 'Cgroup Version: {{.CgroupVersion}}, Cgroup Driver: {{.CgroupDriver}}'
```

dockerd의 설정 파일(`/etc/docker/daemon.json`)에서 드라이버를 명시적으로 지정할 수도 있습니다.

```json
{
  "exec-opts": ["native.cgroupdriver=systemd"]
}
```

Kubernetes 환경에서는 kubelet과 컨테이너 런타임의 cgroup 드라이버가 서로 일치하지 않으면 자원 제한이
제대로 걸리지 않거나 파드가 예상치 못하게 실패하는 문제가 잘 알려져 있습니다. 이는 Docker 단독 사용
환경보다 Kubernetes와 함께 쓸 때 훨씬 자주 부딪히는 문제이므로, kubelet 설정과 컨테이너 런타임 설정의
cgroup 드라이버가 항상 일치해야 한다는 점을 기억해 둘 필요가 있습니다.

## 3.4 주요 컨트롤러와 Docker 옵션의 매핑

cgroups는 여러 컨트롤러로 나뉘어 있고, Docker의 자원 제한 관련 CLI 옵션들은 결국 이 컨트롤러들의 제어
파일에 값을 쓰는 것으로 귀결됩니다. 이 절에서는 실무에서 가장 자주 쓰이는 네 가지 컨트롤러를 Docker
옵션과 짝지어 설명합니다.

### cpu 컨트롤러

CPU 컨트롤러는 프로세스 그룹이 사용할 수 있는 CPU 시간을 제한하거나 상대적 비중을 조정합니다. Docker의
대표적인 옵션은 다음과 같습니다.

- `--cpus`: 컨테이너가 사용할 수 있는 CPU 코어 수를 소수점 단위로 제한합니다(예: `--cpus=1.5`는 코어
  1.5개 분량). 내부적으로는 cgroup v2의 `cpu.max`(v1에서는 `cpu.cfs_quota_us`/`cpu.cfs_period_us`
  조합)를 이용한 CFS(Completely Fair Scheduler) 대역폭 제어로 구현됩니다.
- `--cpu-shares`: 여러 컨테이너가 CPU를 두고 경쟁할 때의 상대적 가중치를 지정합니다(절대적인 상한이
  아니라 유휴 자원이 있을 때의 배분 비율을 조정하는 값이며, cgroup v2에서는 `cpu.weight`에 대응합니다).
- `--cpuset-cpus`: 컨테이너가 실행될 수 있는 물리 CPU 코어를 특정 번호로 고정합니다(`cpuset` 컨트롤러 사용).

```bash
docker run -d --name limited --cpus="1.5" --cpu-shares=512 nginx:latest
cat /sys/fs/cgroup/system.slice/docker-*.scope/cpu.max   # cgroup v2 예시 경로
```

### memory 컨트롤러

메모리 컨트롤러는 프로세스 그룹의 메모리 사용 상한을 강제합니다.

- `--memory`: 컨테이너가 사용할 수 있는 최대 메모리 양(예: `--memory=512m`)을 지정합니다. cgroup v2의
  `memory.max`에 대응합니다.
- `--memory-swap`: 메모리와 스왑을 합친 총 상한을 지정합니다. `--memory`와 같은 값으로 지정하면 스왑을
  아예 사용하지 못하게 막는 효과가 있고, `-1`로 지정하면 스왑 사용에 제한을 두지 않는 식의 특수한 동작을
  갖습니다(정확한 동작은 Docker 버전별 문서를 확인하는 것이 안전합니다).
- `--memory-swappiness`: 커널이 해당 cgroup의 페이지를 얼마나 적극적으로 스왑 아웃할지의 성향(0~100)을
  조정합니다.

```bash
docker run -d --name memlimited --memory=512m --memory-swap=512m nginx:latest
cat /sys/fs/cgroup/system.slice/docker-*.scope/memory.max
```

### io 컨트롤러

I/O 컨트롤러(cgroup v1에서는 `blkio`, v2에서는 `io`)는 블록 디바이스에 대한 읽기/쓰기 대역폭이나 IOPS를
제한합니다.

- `--blkio-weight`: 여러 컨테이너가 디스크 I/O를 두고 경쟁할 때의 상대적 가중치를 지정합니다.
- `--device-read-bps`, `--device-write-bps`: 특정 블록 디바이스에 대한 초당 읽기/쓰기 바이트 수 상한을
  지정합니다.
- `--device-read-iops`, `--device-write-iops`: 초당 I/O 작업 횟수 상한을 지정합니다.

이 옵션들은 특히 여러 컨테이너가 같은 물리 디스크나 네트워크 스토리지를 공유하는 환경에서, 특정 컨테이너의
디스크 집약적 작업(대규모 로그 쓰기, 백업 작업 등)이 다른 컨테이너의 I/O 지연 시간에 영향을 주지 않도록
격리하는 데 유용합니다.

### pids 컨트롤러

pids 컨트롤러는 cgroup 안에서 생성될 수 있는 프로세스/스레드 수의 총합을 제한합니다.

- `--pids-limit`: 컨테이너 안에서 fork/clone으로 생성 가능한 프로세스 수의 상한을 지정합니다.

이 옵션은 "포크 폭탄(fork bomb)"과 같이 프로세스를 무한히 생성해서 호스트의 PID 공간이나 메모리를
고갈시키는 공격/버그로부터 호스트 전체를 보호하는 데 중요한 역할을 합니다. 네임스페이스만으로는 컨테이너
안에서 프로세스를 무한정 생성하는 것 자체를 막을 수 없으므로, pids 컨트롤러는 2장에서 언급한 "네임스페이스만으로는
격리가 완전하지 않다"는 논점을 자원 관점에서 보여주는 대표적인 사례입니다.

```bash
docker run -d --name pidlimited --pids-limit=100 nginx:latest
cat /sys/fs/cgroup/system.slice/docker-*.scope/pids.max
```

## 3.5 OOM Killer와 cgroup 메모리 한도

`--memory`로 메모리 상한을 건 컨테이너가 그 한도를 초과하면 어떤 일이 벌어질까요. 커널은 해당 cgroup
안에서 자체적으로 **cgroup-aware OOM killer**를 동작시킵니다. 이는 시스템 전체의 메모리가 부족할 때
발동하는 전역 OOM killer와는 별개로, 특정 cgroup의 메모리 사용량이 그 cgroup에 설정된 `memory.max`(v1의
`memory.limit_in_bytes`)를 초과했을 때 그 cgroup 안의 프로세스 중 하나(보통 메모리 사용량이 가장 크거나
`oom_score_adj` 값이 높은 프로세스)를 골라 `SIGKILL`로 종료시키는 방식으로 동작합니다.

컨테이너가 이렇게 종료되면 `docker inspect`의 `State.OOMKilled` 필드가 `true`로 표시되며, 애플리케이션
로그에는 대개 아무 흔적도 남지 않고 프로세스가 갑자기 사라진 것처럼 보입니다. 컨테이너가 "이유 없이" 재시작
정책에 의해 계속 재기동되고 있다면, 가장 먼저 확인해야 할 것이 바로 이 필드입니다.

```bash
docker inspect --format '{{.State.OOMKilled}}' <container-id-or-name>
```

Docker는 이 동작과 관련된 두 가지 세부 옵션을 제공합니다.

- `--oom-kill-disable`: 컨테이너 cgroup에 대해 OOM killer 발동 자체를 비활성화합니다. 다만 이 옵션을
  단독으로 쓰면 메모리 한도를 초과한 프로세스가 커널에 의해 즉시 종료되는 대신 메모리 회수를 위해 계속
  대기(hang)하게 될 수 있으므로, 반드시 `--memory`로 명확한 상한을 함께 지정하는 것이 권장되며 상한 없이
  이 옵션만 켜는 것은 호스트 전체의 메모리 고갈로 이어질 수 있어 위험합니다.
- `--oom-score-adj`(호스트 프로세스 레벨의 개념을 컨테이너 단위로 반영하는 옵션): 전역 OOM killer가 여러
  프로세스 중 누구를 먼저 죽일지 판단할 때 참고하는 가중치를 조정합니다.

## 3.6 cgroup v1의 잔존과 하이브리드 모드

앞서 언급했듯 2026년 현재 대부분의 주류 배포판은 cgroup v2를 기본값으로 사용합니다. 하지만 실무에서는
여전히 v1 환경을 마주칠 수 있는 몇 가지 시나리오가 남아 있습니다.

- 오랫동안 OS 업그레이드 없이 운영되어 온 legacy 서버(오래된 커널 버전을 사용 중인 경우, v2 자체가 아예
  지원되지 않거나 기능이 불완전할 수 있습니다).
- 특정 레거시 모니터링 에이전트나 자원 관리 도구가 v1 전용 인터페이스(`memory.limit_in_bytes`, `blkio.weight`
  같은 v1 고유 파일명)에 하드코딩되어 있어, v2로 전환 시 해당 도구가 오작동하는 경우.
- 컨테이너 오케스트레이션 스택의 일부 구성 요소가 과거 버전에 고정되어 있어 v2 전환이 검증되지 않은 채로
  남아 있는 경우.

이런 상황에서 흔히 쓰이는 것이 **하이브리드 모드**입니다. 하이브리드 모드에서는 대부분의 컨트롤러가
cgroup v2 unified hierarchy로 동작하면서, 일부 레거시 컨트롤러만 v1 방식으로 별도 마운트되어 공존합니다.
어떤 모드로 동작 중인지는 `/sys/fs/cgroup` 마운트 구조를 살펴보면 확인할 수 있습니다.

```bash
mount | grep cgroup
# v2 unified hierarchy만 사용 중이라면 cgroup2 타입의 마운트 하나만 /sys/fs/cgroup에 보임
# v1 또는 하이브리드라면 컨트롤러별 cgroup 타입 마운트가 여러 개 보임(/sys/fs/cgroup/cpu,
# /sys/fs/cgroup/memory 등)
```

새로운 인프라를 설계한다면 v2를 전제로 하는 것이 합리적이지만, 기존 레거시 환경을 다룰 때는 이런 혼재
가능성을 염두에 두고 `docker info`의 `Cgroup Version` 필드를 먼저 확인하는 습관을 들이는 것이 문제 해결
시간을 크게 줄여줍니다.

## 핵심 요약

- cgroups v1은 컨트롤러마다 독립적인 계층을 가질 수 있어 유연했지만, 계층 간 불일치와 관리 복잡성이라는
  구조적 문제를 안고 있었다.
- cgroups v2는 unified hierarchy로 모든 컨트롤러가 하나의 트리를 공유하게 재설계했고, 명확한 위임
  모델을 통해 rootless 환경 등에서의 자원 관리도 개선했다.
- runc는 cgroupfs 드라이버(직접 조작) 또는 systemd 드라이버(systemd에 위임) 중 하나로 cgroup을 관리하며,
  systemd가 init인 현대 배포판에서는 systemd 드라이버가 권장된다. `docker info`로 현재 드라이버와
  cgroup 버전을 확인할 수 있다.
- `--cpus`/`--cpu-shares`/`--cpuset-cpus`(cpu), `--memory`/`--memory-swap`/`--memory-swappiness`(memory),
  `--blkio-weight`/`--device-*-bps`/`--device-*-iops`(io), `--pids-limit`(pids)은 각각 대응하는 cgroup
  컨트롤러의 제어 파일에 값을 기록하는 것으로 구현된다.
- 메모리 상한을 초과한 컨테이너는 cgroup-aware OOM killer에 의해 SIGKILL로 종료되며, `docker inspect`의
  `State.OOMKilled` 필드로 이를 확인할 수 있다. `--oom-kill-disable`은 반드시 `--memory` 상한과 함께
  사용해야 안전하다.
- 2026년 현재 주류 배포판은 cgroup v2가 기본값이지만, legacy 환경이나 구형 도구와의 호환을 위해 v1 또는
  v1/v2 하이브리드 모드가 여전히 일부 남아 있다.

## 실습

아래 실습은 cgroup v2가 활성화된 systemd 기반 Linux 환경(Docker Engine 29.x)을 전제로 합니다.

```bash
# 1) 현재 시스템의 cgroup 버전과 드라이버 확인
docker info --format 'Cgroup Version: {{.CgroupVersion}}, Cgroup Driver: {{.CgroupDriver}}'
mount | grep cgroup
# 확인 포인트: CgroupVersion이 2로 나오고, mount 결과에 cgroup2 타입 마운트가 /sys/fs/cgroup에
# 하나만 보이는지 확인합니다.

# 2) CPU와 메모리를 제한한 컨테이너 실행
docker run -d --name resourcetest --cpus="0.5" --memory="256m" --pids-limit=50 \
  polinux/stress stress --vm 1 --vm-bytes 200M --timeout 60s

# 3) 실제 cgroup 제어 파일 값 확인
CID=$(docker inspect -f '{{.Id}}' resourcetest)
cat /sys/fs/cgroup/system.slice/docker-${CID}.scope/cpu.max
cat /sys/fs/cgroup/system.slice/docker-${CID}.scope/memory.max
cat /sys/fs/cgroup/system.slice/docker-${CID}.scope/pids.max
# 확인 포인트: cpu.max의 첫 번째 값과 두 번째 값(quota/period)의 비율이 0.5에 해당하는지,
# memory.max가 268435456(256MiB)로 설정되어 있는지 확인합니다. 경로는 cgroup 드라이버 설정에
# 따라 달라질 수 있으므로 다르다면 `find /sys/fs/cgroup -name "*${CID:0:12}*"`로 탐색합니다.

# 4) 의도적으로 메모리 한도를 초과시켜 OOM killer 동작 확인
docker run --name oomtest --memory=50m polinux/stress stress --vm 1 --vm-bytes 150M --timeout 20s
docker inspect --format '{{.State.OOMKilled}}' oomtest
# 확인 포인트: 결과가 true로 나오는지 확인합니다.

# 5) 정리
docker rm -f resourcetest oomtest
```

지금까지 2장과 3장을 통해 컨테이너 격리의 두 축인 네임스페이스(가시성)와 cgroups(자원)를 살펴봤습니다.
다음 장에서는 이 두 메커니즘을 커널이 아니라 표준의 관점에서 다시 바라봅니다. runc가 정확히 어떤 형식의
명세(config.json)를 받아 지금까지 설명한 네임스페이스와 cgroup 설정을 만들어내는지, 그리고 runc 외에
crun, gVisor, Kata Containers 같은 다른 런타임 구현체들이 같은 표준 위에서 어떻게 서로 다른 트레이드오프를
택하고 있는지를 OCI Runtime/Image Spec을 중심으로 다룹니다.
