# 4장. 컨테이너 런타임 표준 — OCI Runtime/Image Spec과 런타임 생태계

2장과 3장에서는 컨테이너를 감싸는 커널 메커니즘, 즉 namespaces와 cgroups를 다뤘습니다. 그런데 이 두 메커니즘을
"어떤 순서로, 어떤 설정으로 조합해서 프로세스 하나를 컨테이너로 만들 것인가"는 커널이 정해주지 않습니다.
그 조합 방식을 표준화한 것이 이 장에서 다룰 OCI(Open Container Initiative) 스펙이고, 그 표준을 실제로
구현해 커널 API를 호출하는 프로그램이 runc를 비롯한 런타임들입니다. 1장에서 살펴본 dockerd → containerd →
runc 실행 경로에서 맨 끝에 있던 그 runc가 정확히 무엇을 어떤 규칙으로 실행하는지, 그리고 runc가 유일한
선택지가 아니라는 사실을 이번 장에서 다룹니다.

## 4.1 OCI는 왜 만들어졌는가

Docker는 2013년 공개 이후 빠르게 컨테이너의 사실상 표준(de facto standard)이 되었습니다. 하지만 표준이
단일 기업의 오픈소스 프로젝트에 종속되어 있다는 점은 생태계 전체에 불안 요소였습니다. 이미지 포맷이나
실행 방식이 Docker의 내부 구현에 종속된다면, 다른 벤더가 호환 도구를 만들거나 Kubernetes 같은 오케스트레이터가
여러 런타임을 자유롭게 선택하기 어려워집니다.

이 문제의식은 실제 경쟁 구도로도 나타났습니다. 2014년 CoreOS는 Docker의 데몬 중심 아키텍처와 이미지 배포
방식에 문제를 제기하며 `rkt`라는 대안 컨테이너 엔진을 내놓았고, 이를 뒷받침하는 이미지·실행 표준으로
App Container Specification(줄여서 appc)을 제안했습니다. appc는 이미지 포맷(ACI), 실행 환경, 검증 방식을
독자적으로 정의했고, 한동안 Docker의 이미지 포맷과 appc는 서로 다른 진영으로 갈라설 조짐을 보였습니다.

이 분열을 막기 위해 2015년 6월, 리눅스 파운데이션 산하에 OCI가 결성되었습니다. 창립 멤버에는 Docker와
CoreOS가 함께 이름을 올렸고, Docker는 당시 자사 컨테이너 실행 엔진의 핵심이었던 `libcontainer` 프로젝트를
Docker 자체 코드와 분리해 독립 실행 파일로 만든 뒤 OCI에 기부했습니다. 이것이 오늘날까지 이어지는 `runc`입니다.
appc 진영 역시 이후 OCI 표준화 작업에 합류했고, 별도의 이미지 포맷으로서 appc/ACI는 2016년 이후 사실상
개발이 종료되었습니다. 결과적으로 "컨테이너를 어떻게 실행할 것인가"와 "컨테이너 이미지를 어떻게 표현할 것인가"라는
두 가지 질문에 대해 벤더 중립적인 단일 답이 남게 된 것이 OCI의 역사적 의미입니다.

OCI는 크게 세 개의 스펙을 관리합니다.

- **Runtime Specification**: 컨테이너를 생성·실행·종료하는 방법을 정의합니다.
- **Image Specification**: 컨테이너 이미지의 구조(레이어, 설정, 매니페스트)를 정의합니다.
- **Distribution Specification**: 이미지를 레지스트리에 올리고 받아오는 API(push/pull 프로토콜)를 정의합니다.

세 스펙 모두 "구현을 하나로 강제하지 않고, 서로 다른 구현이 상호운용되도록 인터페이스와 포맷만 규정한다"는
철학을 공유합니다. 그래서 runc 대신 crun을 써도, Docker Hub 대신 사설 레지스트리를 써도, containerd 대신
CRI-O를 써도 이미지와 실행 방식의 근본 구조는 동일하게 유지됩니다.

## 4.2 OCI Runtime Specification — 번들과 config.json

Runtime Spec은 "번들(bundle)"이라는 단위를 실행의 기본 입력으로 정의합니다. 번들은 디스크 상의 디렉터리로,
최소한 다음 두 가지를 포함해야 합니다.

- `config.json`: 컨테이너의 설정을 담은 JSON 파일
- 루트 파일시스템(보통 `rootfs/`라는 이름의 디렉터리): 컨테이너 안에서 `/`로 보일 파일시스템 트리

runc를 포함한 대부분의 저수준 런타임은 이미지를 이해하지 못합니다. containerd가 이미지를 받아와 레이어를
풀고, 그 결과물을 rootfs로 배치하고, 설정값을 config.json으로 직렬화한 뒤에야 runc를 호출합니다. 즉
"이미지 → 번들" 변환은 상위 계층(containerd, 그리고 그 위의 dockerd)의 책임이고, runc는 오직 번들만 압니다.
이 역할 분리 덕분에 이미지 포맷이 바뀌어도 runc 자체는 손댈 필요가 없습니다.

### config.json의 주요 구조

config.json은 플랫폼 공통 필드와 리눅스 전용 필드(`linux` 객체 아래)로 나뉩니다. 실무에서 자주 마주치는
핵심 필드는 다음과 같습니다.

| 필드 | 설명 |
|---|---|
| `ociVersion` | 이 config.json이 따르는 Runtime Spec 버전 |
| `root.path` | rootfs 경로, `root.readonly`로 읽기 전용 여부 지정 |
| `mounts` | 컨테이너 내부에 추가로 마운트할 항목 목록(`/proc`, `/dev`, `/sys` 등 포함) |
| `process` | 실행할 프로그램(`args`), 환경 변수(`env`), 작업 디렉터리(`cwd`), 실행 사용자(`user`), capabilities 등 |
| `hostname` | 컨테이너의 UTS 네임스페이스에 설정될 호스트명 |
| `linux.namespaces` | 이 컨테이너가 새로 만들거나 공유할 네임스페이스 목록과 종류(`pid`, `network`, `mount`, `uts`, `ipc`, `user`, `cgroup` 등) |
| `linux.resources` | cgroup으로 제어할 자원 한도(`memory`, `cpu`, `pids`, `blockIO` 등) |
| `linux.cgroupsPath` | 이 컨테이너가 속할 cgroup 경로 |
| `hooks` | 라이프사이클 특정 시점(`prestart`, `createRuntime`, `poststart`, `poststop` 등)에 실행할 외부 프로그램 |

`linux.namespaces` 항목은 2장에서 다룬 네임스페이스 종류를 그대로 나열하는 자리라는 점을 눈여겨볼 필요가
있습니다. 즉 config.json은 "namespace 여덟 종류 중 무엇을 새로 만들지"를 선언적으로 명시하고, runc는 이
선언을 읽어 `clone()`/`unshare()`/`setns()` 계열 시스템 콜을 실제로 호출하는 실행자 역할을 합니다.
`linux.resources` 역시 3장에서 다룬 cgroup v2 컨트롤러 설정값을 JSON으로 옮겨 놓은 것에 지나지 않습니다.
결국 runc의 본질은 "config.json에 적힌 네임스페이스·cgroup 설정을 커널 API 호출로 번역하는 얇은 계층"이라고
정리할 수 있습니다.

### 라이프사이클: state, create, start, kill, delete

Runtime Spec은 런타임이 지원해야 할 표준 동작과 컨테이너가 거치는 상태를 정의합니다. 상태는 네 가지입니다.

- **creating**: 런타임이 컨테이너 환경을 구성하는 중
- **created**: 환경 구성은 끝났지만 사용자 프로그램(`process.args`)은 아직 실행되지 않은 상태
- **running**: 사용자 프로그램이 실행 중인 상태
- **stopped**: 컨테이너 프로세스가 종료된 상태

이에 대응하는 표준 동작은 다음과 같습니다.

```bash
# 번들로부터 컨테이너를 생성한다. 이 시점에는 네임스페이스/마운트/cgroup까지 준비되지만
# process.args로 지정한 프로그램은 아직 실행되지 않는다.
runc create --bundle /path/to/bundle mycontainer

# created 상태의 컨테이너에서 실제로 사용자 프로그램을 실행한다.
runc start mycontainer

# 실행 중이거나 생성된 컨테이너에 시그널을 보낸다.
runc kill mycontainer SIGTERM

# stopped 상태의 컨테이너가 점유하던 자원(cgroup, 네임스페이스 등)을 정리한다.
runc delete mycontainer

# 컨테이너의 현재 상태를 JSON으로 조회한다.
runc state mycontainer
```

`create`와 `start`를 분리해 둔 것이 이 스펙에서 특히 중요한 설계 결정입니다. create 단계에서 네임스페이스
격리와 마운트, cgroup 배치가 전부 끝나 있으므로, 이 시점에 상위 계층(containerd의 shim)이 관찰용 프로세스를
붙이거나 네트워크 인터페이스를 컨테이너 네임스페이스 안으로 옮기는 등의 후처리를 안전하게 끼워 넣을 수
있습니다. 사용자 프로그램이 실제로 뜨는 시점을 start로 미뤄 둠으로써, "컨테이너는 만들어졌지만 애플리케이션은
아직 세상과 통신할 준비가 안 된" 중간 상태를 표준적으로 활용할 수 있게 되는 것입니다. `hooks`에 등록하는
`createRuntime`, `createContainer`, `prestart`, `poststart` 같은 훅들이 바로 이 틈새에서 실행됩니다.

runc는 이 스펙의 참조 구현(reference implementation)입니다. "참조 구현"이라는 표현이 중요한데, 이는 runc가
유일하게 허용된 구현체가 아니라 스펙 준수 여부를 판단하는 기준점 역할을 한다는 뜻입니다. 뒤에서 살펴볼
crun, gVisor, Kata Containers, youki는 모두 이 config.json 포맷과 create/start/kill/delete 인터페이스를
동일하게 구현하면서도, 내부적으로는 전혀 다른 방식으로 격리를 구현합니다.

## 4.3 OCI Image Specification과 배포 스펙

Runtime Spec이 "이미 준비된 rootfs를 어떻게 실행하는가"를 다룬다면, Image Spec은 "그 rootfs를 어떻게
내려받고 조립하는가"를 다룹니다. OCI 이미지는 크게 세 종류의 객체로 구성됩니다.

- **이미지 매니페스트(Image Manifest)**: 이미지 config에 대한 참조와, 그 이미지를 구성하는 레이어들의
  다이제스트 목록을 담은 JSON 문서
- **이미지 config**: 컨테이너 실행 시 기본으로 사용할 `Cmd`, `Entrypoint`, `Env`, `WorkingDir`, 노출 포트 등
  런타임 설정과, 이 이미지가 어떤 레이어들을 어떤 순서로 쌓아 만들어졌는지에 대한 `rootfs.diff_ids` 정보
- **레이어(layer, diff)**: 파일시스템 변경분을 담은 tar 아카이브. 레이어는 단독으로는 완전한 파일시스템이
  아니며, 반드시 순서대로 겹쳐 쌓아야 완전한 rootfs가 만들어집니다

여러 아키텍처(amd64, arm64 등)를 하나의 이미지 이름으로 배포하고 싶을 때는 **이미지 인덱스(Image Index)**를
사용합니다. 인덱스는 매니페스트들의 목록을 가리키는 상위 문서로, 흔히 "멀티 아키텍처 이미지" 또는
"매니페스트 리스트"라고 부르는 것이 바로 이 구조입니다. `docker buildx build --platform linux/amd64,linux/arm64`로
빌드한 이미지를 레지스트리에서 내려받으면, 클라이언트는 먼저 인덱스를 읽고 자신의 아키텍처에 맞는
매니페스트를 골라 그 매니페스트가 가리키는 레이어들만 내려받습니다.

각 객체는 미디어 타입(media type) 문자열로 종류가 구분됩니다. 대표적인 값은 다음과 같습니다.

| 객체 | 미디어 타입 |
|---|---|
| 이미지 매니페스트 | `application/vnd.oci.image.manifest.v1+json` |
| 이미지 인덱스 | `application/vnd.oci.image.index.v1+json` |
| 이미지 config | `application/vnd.oci.image.config.v1+json` |
| 레이어(비압축 tar) | `application/vnd.oci.image.layer.v1.tar` |
| 레이어(gzip 압축) | `application/vnd.oci.image.layer.v1.tar+gzip` |
| 레이어(zstd 압축) | `application/vnd.oci.image.layer.v1.tar+zstd` |

### Docker 이미지 포맷과의 관계

역사적으로 Docker는 자체적으로 "Docker Image Manifest V2, Schema 2"라는 포맷을 사용해 왔습니다
(미디어 타입 `application/vnd.docker.distribution.manifest.v2+json`). OCI Image Spec은 이 Docker v2
포맷을 기반으로 설계되었기 때문에, 구조적으로는 거의 동일합니다. 매니페스트 안에 config에 대한 참조 하나와
레이어 목록이 들어간다는 뼈대, 콘텐츠를 다이제스트로 식별한다는 원칙이 그대로 이어졌습니다. 차이는 주로
미디어 타입 문자열과 일부 확장 필드(예: OCI 쪽의 `annotations`)에 있으며, 대부분의 최신 레지스트리와
빌드 도구는 두 포맷을 사실상 동등하게 취급합니다. BuildKit은 기본적으로 OCI 포맷으로 이미지를 만들고,
Docker Hub를 포함한 주요 레지스트리들은 두 미디어 타입을 모두 받아들입니다. 다만 아주 오래된 레지스트리나
도구 체인 중 일부는 OCI 미디어 타입을 인식하지 못하는 경우가 있어, 상호운용성 문제가 발생하면 이 미디어
타입 차이를 가장 먼저 의심해 볼 만합니다.

### Distribution Spec — 레지스트리 API

이미지를 "어떻게 표현하는가"를 정의한 Image Spec과 짝을 이루는 것이 "그 표현물을 어떻게 주고받는가"를
정의한 Distribution Spec입니다. 이 스펙은 HTTP 기반 API로, `/v2/` 아래에 다음과 같은 엔드포인트들을
표준화합니다.

```text
GET  /v2/                              # API 버전 확인, 인증 필요 여부 프로브
GET  /v2/<name>/manifests/<reference>  # 매니페스트 조회 (reference는 태그 또는 다이제스트)
GET  /v2/<name>/blobs/<digest>         # 레이어·config 등 블롭 다운로드
POST /v2/<name>/blobs/uploads/         # 블롭 업로드 시작 (push)
PUT  /v2/<name>/manifests/<reference>  # 매니페스트 업로드 (push 마무리)
```

`docker pull`, `docker push`, `ctr images pull` 등 어떤 클라이언트를 쓰더라도 내부적으로는 이 API를
호출합니다. 이 스펙이 표준화되어 있기 때문에 Docker Hub, GitHub Container Registry, 사설 Harbor 인스턴스,
클라우드 벤더의 관리형 레지스트리가 모두 같은 클라이언트로 다뤄질 수 있는 것입니다.

## 4.4 runc와 대체 런타임 생태계

runc가 Runtime Spec의 참조 구현이라는 지위를 갖고 있지만, 실무에서는 격리 강도나 시작 속도, 신뢰 모델이
다른 여러 런타임을 상황에 맞게 골라 쓰는 경우가 늘고 있습니다. 이들은 모두 config.json을 입력으로 받고
create/start/kill/delete 인터페이스를 구현한다는 점에서 상위 계층(containerd)에서 보면 서로 교체 가능한
부품입니다.

### runc — 기준점

runc는 Go로 작성되었고, 내부적으로 `libcontainer` 패키지를 통해 네임스페이스 생성, cgroup 배치, capability
설정, seccomp 필터 적용 같은 작업을 직접 수행합니다. 별도의 커널 모듈이나 특수한 하드웨어 기능 없이,
2~3장에서 다룬 표준 리눅스 커널 기능만으로 격리를 구성한다는 점이 특징입니다. 격리 수준은 "리눅스 커널이
프로세스에게 제공하는 것과 동일한 커널"을 컨테이너와 공유하는 정도이며, 이는 곧 커널 자체에 존재하는
취약점이 있다면 컨테이너 격리도 그 영향을 받는다는 뜻이기도 합니다.

### crun — C로 재구현된 저오버헤드 런타임

crun은 Red Hat 주도로 C 언어로 처음부터 다시 작성된 OCI 런타임입니다. Go 런타임이 갖는 가비지 컬렉션이나
멀티스레드 런타임 초기화 비용 없이 `fork`/`exec` 모델에 가깝게 동작하기 때문에 바이너리 크기와 메모리
사용량이 runc보다 작고, 컨테이너 시작 지연(cold start)이 짧습니다. 정확한 수치는 벤치마크 환경에 따라
달라지지만, 대체로 crun의 시작 시간이 runc보다 눈에 띄게 빠르다는 결과가 여러 벤치마크에서 반복적으로
보고됩니다. 안정 상태(steady state)에서의 CPU·메모리 사용량 차이는 미미한 편이라, crun의 이점은 특히
"컨테이너가 자주, 그리고 짧게 뜨고 사라지는" 워크로드에서 두드러집니다. Red Hat OpenShift는 crun을
기본 런타임으로 채택하고 있습니다.

### gVisor(runsc) — 유저스페이스 커널 기반 샌드박싱

gVisor는 격리 모델 자체가 runc·crun과 다릅니다. `runsc`라는 이름의 OCI 런타임 바이너리로 동작하지만,
내부에는 Go로 작성된 "Sentry"라는 유저스페이스 커널이 있습니다. 컨테이너 프로세스가 발생시키는 시스템
콜은 호스트 커널로 직접 전달되지 않고, 플랫폼 계층(ptrace 기반의 systrap, 또는 KVM 기반 플랫폼)이
가로채 Sentry로 넘깁니다. Sentry는 리눅스 시스템 콜 ABI를 유저스페이스에서 스스로 구현하고 있어서,
파일시스템 접근은 "Gofer"라는 별도 프로세스에 9P 유사 프로토콜로 위임하는 방식으로 처리합니다. 결과적으로
컨테이너 프로세스가 실제 호스트 커널에 열어 두는 시스템 콜 표면적은 seccomp로 걸러진 극히 일부로 좁아집니다.

이 구조는 "커널 취약점 하나로 컨테이너를 탈출한다"는 공격 시나리오에 대한 방어층을 하나 더 추가하지만,
대가도 있습니다. 시스템 콜마다 트랩을 거치는 구조이므로 시스템 콜이 잦은 워크로드에서는 성능 저하가
발생할 수 있고, `io_uring`처럼 최신 커널 기능에 의존하는 애플리케이션(최신 PostgreSQL, 일부 Node.js
libuv 경로, Rust 비동기 런타임 등)이 Sentry가 아직 완전히 구현하지 못한 시스템 콜이나 기능에 걸려
기동 시점에 실패하는 사례도 보고되고 있습니다. 따라서 gVisor를 도입할 때는 대상 워크로드가 실제로
정상 동작하는지 사전 검증이 필요합니다.

### Kata Containers — 경량 VM 기반 격리

Kata Containers는 아예 다른 접근을 취합니다. 컨테이너 프로세스를 호스트 커널 위에서 직접 실행하는 대신,
컨테이너 하나(또는 파드 하나)마다 커널까지 별도로 구동되는 경량 가상 머신을 띄우고 그 안에서 워크로드를
실행합니다. 하이퍼바이저로는 Cloud Hypervisor(기본값, 클라우드 환경에서 성능이 좋음), Firecracker(부팅이
빠르고 디바이스 모델이 최소화됨), QEMU(하드웨어 호환성이 가장 넓음) 중에서 선택할 수 있습니다. 이 방식의
핵심 이점은 게스트 커널 자체가 호스트 커널과 분리되어 있어, 커널 수준의 취약점이 있더라도 다른 테넌트의
VM으로 전이되기 어렵다는 점입니다. 대신 VM 부팅에 따르는 지연과 메모리 오버헤드는 runc/crun보다 커집니다.

Kata는 뒤에서 다룰 containerd의 shim v2 아키텍처를 활용해, 파드 하나에 여러 컨테이너가 있어도 VM(및 shim)을
파드당 하나만 띄우는 구조를 지원합니다. 과거처럼 컨테이너 개수만큼 VM을 중복해서 띄우지 않아도 되도록
설계되어 있다는 뜻입니다.

### youki — Rust로 작성된 실험적·차세대 구현

youki는 Rust로 작성된 OCI 런타임으로, 이름은 일본어로 "그릇/용기"를 뜻하는 단어에서 따왔습니다. Rust의
메모리 안전성을 살려 C/Go 구현에서 발생할 수 있는 특정 클래스의 메모리 버그를 원천적으로 줄이는 것을
목표로 하며, cgroup v1/v2, rootless 실행, seccomp 필터링 등 runc의 주요 기능을 동등하게 구현하는 것을
지향합니다. containerd의 통합 테스트 스위트를 통과할 정도로 성숙도가 올라와 있고 일부 환경에서 프로덕션
채택 사례도 보고되고 있지만, 여전히 runc·crun에 비해 생태계 검증 기간이 짧은 편이므로 도입 전 자체 검증이
권장됩니다.

## 4.5 언제 runc가 아닌 다른 런타임을 쓰는가

런타임 선택은 "보안이 필요하면 무조건 gVisor/Kata"라는 단순한 규칙보다는, 신뢰 경계와 성능 요구사항을
함께 고려해 정해야 합니다. 실무에서 자주 나오는 판단 기준을 정리하면 다음과 같습니다.

- **신뢰할 수 있는 내부 워크로드, 컨테이너 수가 많고 자주 뜨고 내려감(CI 러너, 서버리스 스케일-투-제로)**:
  runc의 표준 격리로 충분하며, crun으로 바꾸면 시작 지연을 더 줄일 수 있습니다.
- **멀티테넌시 SaaS에서 서로 신뢰하지 않는 고객 코드를 실행**: 커널 공유 자체가 위험 요소이므로 gVisor나
  Kata Containers처럼 격리 경계를 커널 아래(Kata) 또는 커널 인터페이스 앞단(gVisor)으로 밀어내는 런타임을
  검토합니다.
- **신뢰할 수 없는 임의 코드 실행(예: 사용자가 업로드한 스크립트를 그대로 실행하는 온라인 코드 실행기)**:
  전형적으로 gVisor 또는 Kata가 요구되는 시나리오입니다.
- **레거시 애플리케이션이 io_uring 등 최신 커널 기능에 의존**: gVisor 도입 전 해당 기능의 Sentry 지원
  여부를 반드시 확인해야 합니다.
- **하드웨어 수준 격리가 컴플라이언스 요구사항인 경우**: Kata Containers가 제공하는 VM 경계가 감사 관점에서
  설명하기 쉬운 경우가 많습니다.

## 4.6 런타임을 선택하는 실제 설정 방법

같은 호스트, 같은 containerd 위에서 워크로드별로 다른 런타임을 쓰는 것은 드문 일이 아닙니다. Kubernetes
환경에서는 containerd의 CRI 플러그인 설정에서 여러 런타임을 등록해 두고 `RuntimeClass`로 파드마다 골라
씁니다. `/etc/containerd/config.toml`에 다음과 같이 등록합니다.

```toml
[plugins."io.containerd.grpc.v1.cri".containerd]
  default_runtime_name = "runc"

[plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc]
  runtime_type = "io.containerd.runc.v2"

[plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runsc]
  runtime_type = "io.containerd.runsc.v1"

[plugins."io.containerd.grpc.v1.cri".containerd.runtimes.kata]
  runtime_type = "io.containerd.kata.v2"
```

각 런타임 이름(`runc`, `runsc`, `kata`)은 Kubernetes 쪽 `RuntimeClass` 리소스의 `handler` 필드와 이어집니다.

```yaml
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: gvisor
handler: runsc
---
apiVersion: v1
kind: Pod
metadata:
  name: untrusted-workload
spec:
  runtimeClassName: gvisor
  containers:
  - name: app
    image: myregistry/app:latest
```

Docker Engine 단에서 dockerd가 containerd를 통해 직접 컨테이너를 띄우는 경우에는 `daemon.json`의 `runtimes`
항목이나 `--add-runtime` 플래그로 등록합니다.

```json
{
  "default-runtime": "runc",
  "runtimes": {
    "runsc": {
      "path": "/usr/local/bin/runsc"
    }
  }
}
```

```bash
docker run --runtime=runsc -it --rm alpine sh
```

두 경로 모두 결국 containerd 설정의 `runtime_type`이 실제로 어떤 shim(`io.containerd.runc.v2`,
`io.containerd.runsc.v1`, `io.containerd.kata.v2` 등)을 통해 컨테이너를 실행할지 결정한다는 점은 동일합니다.
이 shim이라는 개념, 그리고 containerd가 이 여러 런타임 구현체들을 어떻게 통일된 방식으로 관리하는지는
다음 5장에서 containerd 아키텍처를 깊이 파고들며 다시 다룹니다.

## 핵심 요약

- OCI는 Docker의 사실상 표준을 벤더 중립 표준으로 재정립하기 위해 2015년 결성되었고, Docker의 libcontainer가
  runc로 기부되며 실행 표준의 기준점이 되었습니다. 경쟁 관계에 있던 appc(CoreOS rkt)는 이후 개발이
  종료되었습니다.
- OCI Runtime Spec은 번들(config.json + rootfs)을 입력으로 받아 create/start/kill/delete/state라는 표준
  라이프사이클을 정의합니다. config.json의 `linux.namespaces`, `linux.resources`는 각각 2장·3장에서 다룬
  네임스페이스와 cgroup 설정을 JSON으로 표현한 것입니다.
- OCI Image Spec은 매니페스트, 이미지 config, 레이어(diff)의 3단 구조로 이미지를 표현하며, 여러 아키텍처를
  묶는 이미지 인덱스도 정의합니다. Docker v2 이미지 포맷과 구조적으로 거의 동일하며 대부분의 도구가 상호
  호환됩니다.
- Distribution Spec은 `/v2/` 아래의 표준 HTTP API로 이미지 push/pull을 정의하여, 서로 다른 레지스트리
  구현체 간 상호운용성을 보장합니다.
- runc는 참조 구현일 뿐 유일한 선택지가 아닙니다. crun(저오버헤드), gVisor/runsc(유저스페이스 커널
  기반 syscall 가로채기), Kata Containers(경량 VM), youki(Rust)는 모두 같은 스펙을 구현하면서 격리 모델과
  성능 특성이 다릅니다.
- 런타임 선택은 containerd의 `config.toml`에 등록한 `runtime_type`과 Kubernetes의 `RuntimeClass`,
  또는 dockerd의 `daemon.json`의 `runtimes`/`--add-runtime`을 통해 워크로드 단위로 다르게 지정할 수 있습니다.

## 실습

아래 실습은 runc 설치가 되어 있는 리눅스 환경(커널 5.15+ 권장)에서 진행합니다. `oci-image-tool`이나
`skopeo`가 없다면 우선 `docker export`로 간단한 rootfs를 만들어 실습할 수 있습니다.

```bash
# 1. runc가 설치되어 있는지, 버전이 무엇인지 확인합니다.
runc --version
# 출력 예: runc version 1.5.1, spec: 1.3.0 -- Runtime Spec 버전까지 함께 표시됩니다.

# 2. 최소한의 번들을 만들어 봅니다.
mkdir -p /tmp/mybundle/rootfs
cd /tmp/mybundle
docker export "$(docker create alpine)" | tar -C rootfs -xf -

# 3. runc spec으로 기본 config.json 템플릿을 생성합니다.
runc spec
cat config.json | head -30
# process.args가 기본값으로 ["sh"]인지, linux.namespaces에 pid/network/ipc/uts/mount가
# 나열되어 있는지 확인해 봅니다.

# 4. 컨테이너를 create 상태까지만 만들어 봅니다(아직 프로세스는 실행되지 않습니다).
sudo runc create --bundle /tmp/mybundle demo1
sudo runc state demo1
# "status": "created" 로 표시되는지 확인합니다.

# 5. start로 실제 프로세스를 실행합니다.
sudo runc start demo1
sudo runc state demo1
# "status": "running" 으로 바뀐 것을 확인합니다. (config.json의 process.args가
# 대화형 셸이 아니라면 곧바로 stopped로 넘어갈 수 있습니다.)

# 6. 정리합니다.
sudo runc kill demo1 SIGKILL 2>/dev/null
sudo runc delete demo1

# 7. 같은 번들을 crun으로도 실행해 config.json 포맷이 그대로 호환되는지 확인합니다.
# (crun이 설치되어 있어야 합니다: apt-get install crun 또는 배포판 패키지 매니저 사용)
sudo crun run --bundle /tmp/mybundle demo2
```

4단계와 5단계에서 `runc state`의 출력이 `creating → created → running`으로 바뀌는 것을 직접 눈으로
확인하는 것이 이번 실습의 핵심입니다. 7단계까지 진행하면, 동일한 config.json 하나로 서로 다른 두 런타임을
그대로 구동할 수 있다는 사실, 즉 OCI Runtime Spec이 실제로 상호운용 가능한 표준으로 동작한다는 점을
체감할 수 있습니다.
