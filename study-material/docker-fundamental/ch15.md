# 15장. DNS와 서비스 디스커버리, 포트 매핑의 내부 동작

14장에서는 macvlan/ipvlan으로 컨테이너를 물리 네트워크에 직접 노출시키는 방법과, host/none 모드로 네트워크
네임스페이스 자체를 다루는 두 극단을 살펴보았습니다. 하지만 실무에서 가장 자주 마주치는 상황은 이런 특수한
모드가 아니라, 12장에서 다룬 평범한 사용자 정의 브리지 네트워크 위에서 컨테이너들이 서로의 이름을 어떻게
찾아내고, 외부에서 들어오는 요청이 어떤 경로로 정확한 컨테이너까지 도달하는가 하는 문제입니다. `docker run
--name api ...`로 띄운 컨테이너를 다른 컨테이너에서 `http://api:3000`으로 호출할 수 있다는 것은 이제 너무
당연하게 받아들여지지만, 이 뒤에는 Docker가 각 컨테이너 안에 심어 넣는 작은 DNS 리졸버와, 그 리졸버가
질의를 처리하는 정교한 경로가 있습니다. 이 장에서는 이 내장 DNS의 동작 원리, Swarm 환경에서의 서비스
디스커버리 방식, 그리고 포트 매핑이 실제로 패킷 레벨에서 어떻게 처리되는지를 순서대로 다룹니다.

## 15.1 내장 DNS 서버 — 127.0.0.11의 정체

사용자 정의 브리지 네트워크(또는 오버레이 네트워크)에 연결된 컨테이너 내부에서 `/etc/resolv.conf`를 열어보면
낯선 주소 하나를 발견하게 됩니다.

```bash
docker network create mynet
docker run --rm --network mynet alpine:latest cat /etc/resolv.conf
```

```
nameserver 127.0.0.11
options ndots:0
```

`127.0.0.11`은 루프백 대역(`127.0.0.0/8`) 안의 한 주소이지만, 이것이 가리키는 것은 컨테이너 자신의 로컬
프로세스가 아니라 dockerd가 각 컨테이너의 네트워크 네임스페이스 안에 심어 놓은 가상의 DNS 리스너입니다.
정확히 말하면, dockerd는 컨테이너의 네트워크 네임스페이스 안에서 127.0.0.11:53(UDP/TCP)으로 들어오는
쿼리를 가로채도록 iptables/nftables DNAT 규칙을 컨테이너 네임스페이스 내부에 심어두고, 실제 쿼리 처리는
dockerd(정확히는 libnetwork) 프로세스 안에서 컨테이너별 네트워크 컨텍스트를 알고 있는 내장 리졸버가
담당합니다. 이 리졸버를 흔히 embedded DNS server라고 부릅니다.

이 구조 덕분에 컨테이너 입장에서는 마치 자기 자신의 루프백 인터페이스에 DNS 서버가 떠 있는 것처럼 보이지만,
실제로 쿼리에 응답하는 로직은 호스트에서 실행되는 dockerd가 그 네트워크에 속한 컨테이너들의 이름-IP 매핑
테이블(각 네트워크 드라이버가 컨테이너 연결/해제 시점마다 갱신하는 내부 서비스 디스커버리 데이터베이스)을
조회해서 만들어냅니다. 즉 `mynet`에 연결된 컨테이너가 다른 컨테이너 이름으로 질의를 보내면, 127.0.0.11이
그 이름을 같은 네트워크 안에서 검색해 해당 컨테이너의 IP로 응답합니다. 컨테이너 이름뿐 아니라 `docker run
--network-alias`로 지정한 별칭, Compose의 서비스 이름, 그리고 Compose가 자동으로 붙여주는 별칭들도 동일한
방식으로 조회됩니다.

### 외부 도메인에 대한 포워딩

컨테이너 안의 애플리케이션이 조회하는 이름이 항상 같은 네트워크의 다른 컨테이너인 것은 아닙니다.
`api.example.com`처럼 외부 인터넷 도메인을 조회하는 경우, 127.0.0.11은 자신의 내부 테이블에서 이름을 찾지
못하면 이 쿼리를 실패시키는 대신 호스트에 설정된 업스트림 DNS 서버로 그대로 포워딩합니다. 이때 참조하는
업스트림 서버 목록은 기본적으로 호스트의 `/etc/resolv.conf`에 설정된 네임서버(또는 `--dns` 옵션으로 명시적으로
지정한 서버)입니다. 결과적으로 컨테이너 입장에서는 사내 서비스 이름과 외부 인터넷 도메인을 구분할 필요 없이
동일한 네임서버(127.0.0.11) 하나에만 쿼리를 보내면 되고, 그 뒤에서 로컬 우선 조회와 외부 포워딩이 투명하게
처리됩니다. 사용자 정의 네트워크에서는 이 내장 DNS가 업스트림 서버들에 순서대로 질의해 성공적인 응답이나
NXDOMAIN 응답을 받는 즉시 중단하는 방식으로 동작하며, 이는 여러 서버에 무작위로 흩어 쿼리하던 예전 방식보다
더 예측 가능한 동작을 제공합니다.

## 15.2 기본 브리지에는 없는 이유, 그리고 `--link`의 역사

12장에서 이미 짚었듯, Docker가 설치 직후 기본으로 제공하는 브리지 네트워크(`docker0`, `docker network ls`에서
`bridge`라는 이름으로 보이는 그 네트워크)에 연결된 컨테이너들 사이에는 지금 설명한 내장 DNS 기반의 이름 해석이
동작하지 않습니다. 이 네트워크에 연결된 컨테이너의 `/etc/resolv.conf`를 보면 127.0.0.11 대신 호스트의
네임서버 설정이 그대로 복사되어 있는 것을 볼 수 있습니다.

이는 설계상의 누락이 아니라 역사적인 이유가 있습니다. 기본 브리지 네트워크는 Docker 초창기부터 존재해 온
"컨테이너가 명시적으로 네트워크를 지정하지 않았을 때 붙는 기본값"이며, 이 네트워크가 설계되던 시점에는
지금과 같은 서비스 디스커버리 개념 자체가 없었습니다. 당시 컨테이너 간 이름 기반 통신을 지원하기 위해
Docker가 제공한 기능이 `--link`였습니다. `docker run --link api:api-alias`처럼 지정하면 Docker가 대상
컨테이너의 IP를 확인해 새 컨테이너의 `/etc/hosts`에 정적으로 한 줄 추가해 주는 방식으로 동작했습니다. 이
방식은 몇 가지 근본적인 한계가 있었습니다. 컨테이너가 재시작되어 IP가 바뀌면 `/etc/hosts`를 갱신할 방법이
마땅치 않았고, 링크는 생성 시점에 한 번 정적으로 기록되는 관계라 동적으로 늘어나는 서비스 그룹(예: 같은
역할의 컨테이너 여러 개를 로드밸런싱 대상으로 묶는 것)을 표현할 수 없었습니다.

사용자 정의 브리지 네트워크(`docker network create`로 만든 네트워크)가 도입되면서 이 문제가 근본적으로
해결되었습니다. 사용자 정의 네트워크에 연결된 컨테이너는 자동으로 내장 DNS를 통한 이름 해석 대상이 되고,
컨테이너가 재시작되어 IP가 바뀌어도 내장 DNS의 매핑 테이블이 함께 갱신되므로 이름으로 조회하는 한 문제가
없습니다. 이 때문에 오늘날 실무에서는 기본 브리지 네트워크를 그대로 쓰기보다 컨테이너를 위한 전용 사용자
정의 브리지 네트워크를 만들어 사용하는 것이 사실상 표준 관행으로 자리 잡았고, `--link` 옵션은 레거시로
간주되어 새로운 구성에서는 쓰지 않는 것이 권장됩니다. Docker Compose가 별도 설정 없이도 프로젝트별로
전용 네트워크를 자동 생성하고 서비스 이름으로 서로를 찾게 해주는 것도 바로 이 사용자 정의 브리지 + 내장
DNS 조합 위에서 동작하는 것입니다.

## 15.3 Swarm 서비스 디스커버리 — VIP와 DNSRR

지금까지 설명한 내용은 컨테이너 하나하나를 이름으로 찾는 경우였습니다. Swarm 모드에서 서비스를 스케일링해
같은 역할의 태스크(컨테이너)가 여러 개 떠 있는 경우, "서비스 이름으로 조회했을 때 어떤 태스크로 연결되는가"라는
질문에 답하는 방식이 두 가지로 나뉩니다. 13장에서 다룬 것처럼 Swarm 오버레이 네트워크는 gossip 프로토콜로
멤버십과 라우팅 정보를 전파하는데, 서비스 디스커버리는 이 정보를 바탕으로 클라이언트에게 어떤 주소를
돌려줄지를 결정합니다.

**VIP(Virtual IP) 모드** 는 `docker service create`의 기본값입니다. 서비스를 만들면 Swarm은 그 서비스에
고정된 가상 IP를 하나 할당하고, 서비스 이름으로 DNS 질의를 하면 항상 이 VIP 하나만 응답으로 돌아옵니다.
실제로 여러 태스크 중 어느 것으로 트래픽이 가는지는 이 VIP를 대상으로 하는 IPVS(IP Virtual Server) 기반의
로드밸런싱 규칙이 커널 레벨에서 처리합니다. 클라이언트 애플리케이션 입장에서는 단일 IP만 알면 되고, 태스크가
늘어나거나 줄어들어도 이 IP 자체는 바뀌지 않으므로 애플리케이션이 캐시한 DNS 응답이 오래돼서 생기는 문제가
거의 없습니다.

**DNSRR(DNS Round Robin) 모드** 는 이와 달리 VIP를 두지 않고, 서비스 이름을 조회할 때마다 그 시점에 살아있는
모든 태스크의 IP 목록을 그대로 응답으로 돌려줍니다. 클라이언트가 여러 IP 중 하나를 라운드로빈으로 선택해
접속하는 방식이며, 로드밸런싱의 책임이 커널의 IPVS가 아니라 클라이언트(또는 클라이언트가 사용하는 DNS
캐싱 계층)로 넘어갑니다. `endpoint_mode: dnsrr`으로 명시적으로 지정해야 활성화되며, Swarm의 라우팅 메시
(routing mesh, 13장에서 다룬 ingress 모드의 핵심 기능)와는 함께 쓸 수 없다는 제약이 있습니다. 라우팅 메시
자체가 VIP를 전제로 각 노드에서 들어온 트래픽을 올바른 태스크로 전달하는 방식으로 동작하기 때문입니다.

```yaml
# Compose 파일에서 DNSRR 모드를 지정하는 예
services:
  worker:
    image: myapp:latest
    deploy:
      endpoint_mode: dnsrr
```

실무에서는 대부분 기본값인 VIP 모드를 그대로 사용합니다. DNSRR은 클라이언트가 자체적으로 정교한 로드밸런싱
로직(특정 IP에만 우선 접속, 커넥션 풀링 전략 등)을 이미 갖추고 있어서 IPVS 기반의 단순 로드밸런싱보다
애플리케이션 레벨의 제어가 필요한 특수한 경우, 또는 UDP 기반 프로토콜처럼 IPVS의 연결 추적 방식과 궁합이
맞지 않는 워크로드에서 선택적으로 고려되는 옵션입니다.

## 15.4 포트 매핑의 내부 경로 — `-p`가 실제로 하는 일

`docker run -p 8080:80 nginx`처럼 포트를 매핑하면 호스트의 8080번 포트로 들어온 트래픽이 컨테이너의 80번
포트로 전달됩니다. 12장에서 이미 브리지 네트워크의 veth 페어와 iptables 규칙을 다뤘으므로, 여기서는 포트
매핑 하나에 한정해서 그 경로를 처음부터 끝까지 다시 추적해 보겠습니다.

dockerd는 컨테이너를 시작할 때 두 가지 준비를 동시에 합니다. 첫째, iptables(또는 16장에서 다룰 nftables
백엔드가 활성화된 경우 nftables)의 `nat` 테이블에 DNAT 규칙을 추가합니다. 이 규칙은 "호스트의 8080번 포트로
들어오는 트래픽의 목적지 주소를 컨테이너의 IP:80으로 바꿔라"는 내용입니다. 정확히는 Docker가 자체적으로
만드는 `DOCKER` 체인에 규칙이 추가되고, 호스트의 `PREROUTING`/`OUTPUT` 체인에서 이 `DOCKER` 체인으로
점프하도록 연결되어 있습니다.

```
(외부에서 온 패킷, dst=host_ip:8080)
        │
        ▼
PREROUTING (nat 테이블) ── DOCKER 체인으로 점프
        │
        ▼
DNAT: dst를 container_ip:80 으로 변경
        │
        ▼
라우팅 결정 (목적지가 이제 컨테이너 IP이므로 docker0 브리지 방향으로)
        │
        ▼
FORWARD 체인 (filter 테이블) ── 정책에 따라 ACCEPT/DROP 판단
        │
        ▼
docker0 브리지 → veth(호스트 쪽) → veth(컨테이너 쪽)
        │
        ▼
컨테이너 네트워크 네임스페이스 안의 eth0:80 (nginx 프로세스가 accept)
```

이 경로에서 중요한 것은 DNAT가 이루어지는 시점이 라우팅 결정보다 앞선 `PREROUTING` 단계라는 점입니다.
즉 커널은 목적지 주소를 컨테이너 IP로 바꾼 뒤에 "이 패킷을 어디로 보낼지"를 다시 판단하며, 그 결과 패킷이
docker0 브리지 쪽으로 라우팅되어 최종적으로 veth 페어를 거쳐 컨테이너 네임스페이스 안으로 들어갑니다. 응답
패킷은 conntrack이 기억하고 있는 연결 정보를 바탕으로 반대 방향으로 자동으로 주소가 되돌려지므로(un-DNAT),
클라이언트는 항상 자신이 접속한 host_ip:8080이라는 주소만 보게 됩니다.

과거 버전의 Docker에서는 이 경로 중 일부(특히 바인딩 주소가 `0.0.0.0`이 아니거나 hairpin NAT가 필요한
특수한 경우)를 커널 레벨 DNAT 대신 `docker-proxy`라는 사용자 공간 프로세스가 대신 중계하기도 했습니다.
이 부분은 12장에서 `docker-proxy`와 `userland-proxy` 옵션을 다룰 때 이미 설명했으므로, 여기서는 기본 경로가
iptables/nftables 기반의 커널 DNAT라는 사실만 다시 짚고 넘어갑니다.

### 컨테이너가 자기 자신의 게시된 포트로 접속할 때 — hairpin NAT

포트 매핑에서 자주 간과되는 경계 사례가 하나 있습니다. 컨테이너 A가 자기 자신이 게시한 포트를, 호스트의
공인 IP나 게시 주소를 통해 되돌아 들어오는 경로로 접속하려는 경우입니다. 예를 들어 컨테이너 안의 스크립트가
설정 파일에 적힌 `http://<호스트의_외부_IP>:18080`이라는 주소를 그대로 사용해 자기 자신에게 요청을 보내는
상황을 생각해 볼 수 있습니다. 이 요청은 컨테이너의 veth를 통해 나가서 docker0 브리지를 거쳐 DNAT를 받고,
다시 같은 컨테이너로 돌아 들어와야 하는데, 이런 식으로 패킷이 나갔던 인터페이스로 되돌아 들어오는 경로를
가리켜 hairpin(헤어핀) NAT라고 부릅니다. 리눅스 브리지와 conntrack 조합은 이 시나리오를 항상 매끄럽게
처리하지는 못했고, 과거에는 이런 경우를 위해 `docker-proxy`가 커널 DNAT를 우회해 사용자 공간에서 직접
루프백 트래픽을 중계하는 방식으로 문제를 해결하기도 했습니다. 오늘날에는 커널의 브리지 netfilter 훅과
conntrack이 개선되어 대부분의 최신 배포판에서 hairpin 트래픽도 커널 DNAT만으로 정상 처리되지만, 아주 오래된
커널이거나 브리지 netfilter가 비활성화된 환경에서는 여전히 이 경계 사례가 어긋날 수 있습니다. 실무에서는
컨테이너가 자기 자신을 호출해야 하는 상황 자체를 피하고, 대신 컨테이너 이름이나 `localhost`로 접근하도록
설계를 바꾸는 것이 가장 간단하고 확실한 회피책입니다.

## 15.5 라우팅 메시 vs 단일 호스트 포트 매핑

지금까지 설명한 경로는 컨테이너를 단일 호스트에서 직접 `-p`로 실행했을 때의 이야기입니다. Swarm에서
`docker service create --publish published=8080,target=80`으로 서비스를 게시하면 겉보기 명령은 비슷하지만
내부 동작은 상당히 다릅니다. 13장에서 다룬 ingress 오버레이 네트워크와 라우팅 메시가 여기 관여하기
때문입니다.

| 구분 | 단일 컨테이너 포트 매핑 (`docker run -p`) | Swarm ingress 라우팅 메시 (`docker service --publish`) |
|---|---|---|
| 요청을 받을 수 있는 노드 | 해당 컨테이너가 실제로 떠 있는 호스트뿐 | Swarm 클러스터의 모든 노드(태스크가 그 노드에 없어도 가능) |
| DNAT 대상 결정 | 항상 그 호스트의 특정 컨테이너 IP로 고정 | 어느 노드로 요청이 들어오든 ingress 네트워크를 통해 실제 태스크가 떠 있는 노드로 재전달 |
| 로드밸런싱 | 없음(컨테이너가 하나면 그 컨테이너로만 감) | IPVS 기반 VIP 로드밸런싱으로 여러 태스크에 분산 |
| 사용되는 네트워크 | 로컬 브리지(docker0 또는 사용자 정의 브리지) | 특수한 `ingress` 오버레이 네트워크(VXLAN 캡슐화) |
| 노드 장애/스케일 변화 대응 | 컨테이너가 죽으면 포트도 함께 사라짐 | 태스크가 다른 노드로 재스케줄되어도 게시된 포트는 클러스터 전체에서 계속 유효 |

핵심적인 차이는 "포트가 게시된 곳"과 "실제로 요청을 처리하는 곳"이 분리되어 있는지 여부입니다. 단일 호스트
포트 매핑에서는 이 둘이 항상 같은 물리 호스트입니다. 반면 Swarm의 라우팅 메시는 클러스터의 어느 노드로
요청이 들어오더라도, 그 노드에 실제 태스크가 없다면 ingress 네트워크를 통해 태스크가 실제로 떠 있는 노드로
트래픽을 한 번 더 전달합니다. 이 재전달 경로 자체가 VXLAN으로 캡슐화된 오버레이 트래픽이라는 점은 13장에서
이미 다룬 내용과 정확히 맞닿아 있습니다. 즉 라우팅 메시는 "포트 매핑 + 오버레이 네트워크 라우팅"을 합친
상위 개념이라고 볼 수 있습니다.

## 15.6 DNS 관련 런타임 옵션과 파일 반영

마지막으로, 컨테이너를 실행할 때 DNS 동작 자체를 직접 제어하는 옵션들을 정리합니다. 이 옵션들은 모두
컨테이너 내부의 `/etc/resolv.conf` 또는 `/etc/hosts`에 직접 반영되는 방식으로 동작하므로, 컨테이너 안에서
해당 파일을 열어보면 옵션이 어떻게 적용되었는지 그대로 확인할 수 있습니다.

- **`--dns`**: 컨테이너가 사용할 네임서버를 명시적으로 지정합니다. 지정한 IP가 `/etc/resolv.conf`의
  `nameserver` 항목으로 추가됩니다. 사용자 정의 네트워크에서는 기본적으로 127.0.0.11(내장 DNS)이 이미
  들어가 있으므로, `--dns`를 추가로 지정하면 내장 DNS가 외부 이름을 포워딩할 때 참조하는 업스트림 서버
  목록에 영향을 주는 방식으로 동작합니다.
- **`--dns-search`**: DNS 검색 도메인을 지정하며 `/etc/resolv.conf`의 `search` 항목으로 반영됩니다. 이름
  해석 시 짧은 이름(FQDN이 아닌 이름)에 이 도메인을 자동으로 덧붙여 조회하게 합니다.
- **`--dns-option`**: `ndots`, `timeout`, `attempts` 같은 resolver의 세부 옵션을 `/etc/resolv.conf`의
  `options` 항목으로 그대로 반영합니다. 사용자 정의 네트워크의 컨테이너는 기본적으로 `ndots:0`이 설정되어
  있어, 짧은 이름을 검색 도메인 없이도 우선 그대로 조회하도록 되어 있습니다.
- **`--add-host`**: `host:ip` 형식으로 정적인 이름-IP 매핑을 `/etc/hosts`에 직접 추가합니다. 오래된
  `--link`가 하던 일을 훨씬 명시적이고 예측 가능한 방식으로 대신하는 옵션이며, DNS 질의 자체를 거치지 않고
  파일 조회만으로 해석되므로 내장 DNS나 외부 네임서버 상태와 무관하게 항상 즉시 해석됩니다. `host-gateway`라는
  특수한 값을 IP 자리에 지정하면 호스트 자신을 가리키는 내부 IP로 자동 치환되며, 컨테이너 안에서 호스트로
  접근해야 하는 개발 환경 등에서 유용하게 쓰입니다.

```bash
docker run --rm \
  --dns=1.1.1.1 \
  --dns-search=example.internal \
  --add-host=host.docker.internal:host-gateway \
  alpine:latest sh -c "cat /etc/resolv.conf; echo ---; cat /etc/hosts"
```

이 옵션들은 모두 컨테이너 생성 시점에 파일에 한 번 기록되는 정적인 설정이라는 공통점이 있습니다. 즉
컨테이너가 실행되는 도중에 호스트의 DNS 설정이 바뀌어도 이미 떠 있는 컨테이너의 `/etc/resolv.conf`가
자동으로 갱신되지는 않으며(일부 예외적으로 dockerd가 특정 조건에서 관리하는 파일을 갱신하는 경우가 있지만
일반적으로는 정적입니다), 변경 사항을 반영하려면 컨테이너를 재생성해야 한다는 점을 기억해 둘 필요가 있습니다.

## 15.7 DNS 관련 문제를 진단할 때 확인할 것들

내장 DNS와 관련된 장애는 대부분 몇 가지 정형화된 원인으로 좁혀집니다. 실제로 트러블슈팅할 때 다음 순서로
확인하면 원인을 빠르게 좁힐 수 있습니다.

첫째, 이름을 조회하는 컨테이너와 조회 대상 컨테이너가 정말 같은 사용자 정의 네트워크에 연결되어 있는지
확인합니다. 내장 DNS의 이름 해석 범위는 네트워크 단위입니다. 두 컨테이너가 서로 다른 브리지 네트워크에
각각 연결되어 있다면, 둘 다 127.0.0.11을 네임서버로 갖고 있더라도 서로를 찾을 수 없습니다. 이는 별도의
DNS 서버 인스턴스가 아니라, 같은 dockerd가 네트워크별로 분리해서 관리하는 조회 테이블이기 때문입니다.

둘째, 컨테이너가 기본 브리지 네트워크에 붙어 있지는 않은지 확인합니다. `docker run`에서 `--network`를
지정하지 않으면 여전히 기본 브리지로 붙는 경우가 있고, 이 경우 15.2절에서 설명한 대로 내장 DNS 자체가
적용되지 않습니다.

셋째, `ndots` 설정과 검색 도메인 조합이 예상과 다른 이름으로 조회를 시도하게 만드는 경우가 있습니다.
쿠버네티스 환경에서 넘어온 설정을 그대로 가져와 `ndots:5`처럼 큰 값을 지정하면, 짧은 이름 하나를 조회할
때마다 검색 도메인을 하나씩 덧붙여 가며 여러 번 질의를 시도하게 되고, 그 과정에서 불필요한 지연이나
예상치 못한 외부 도메인 매칭이 발생할 수 있습니다. 사용자 정의 브리지의 기본값인 `ndots:0`에서 이 값을
바꿀 때는 그 의미를 정확히 이해하고 바꾸는 것이 안전합니다.

넷째, 컨테이너 안에서 `nslookup`이나 `dig` 대신 애플리케이션이 자체적으로 구현한 DNS 캐싱 라이브러리를
쓰는 경우, 그 라이브러리가 TTL을 얼마나 신뢰하는지도 확인 대상입니다. 일부 언어 런타임(특히 JVM 계열)은
기본적으로 DNS 응답을 매우 길게 캐싱하는 설정을 갖고 있어서, 컨테이너가 재시작되어 IP가 바뀌었는데도
애플리케이션이 예전 IP로 계속 접속을 시도하는 문제가 발생할 수 있습니다. 이는 Docker의 내장 DNS 문제가
아니라 애플리케이션 레벨의 캐싱 정책 문제이므로, 원인을 dockerd 쪽에서만 찾다가 시간을 허비하지 않도록
주의해야 합니다.

## 핵심 요약

- 사용자 정의 브리지/오버레이 네트워크의 컨테이너는 `/etc/resolv.conf`에 127.0.0.11을 네임서버로 갖게
  되며, 이는 dockerd가 관리하는 내장 DNS 리졸버로 컨테이너 이름/별칭을 조회하고 실패 시 호스트의 업스트림
  DNS로 쿼리를 포워딩한다.
- 기본 브리지 네트워크(docker0)는 이 내장 DNS 해석 대상이 아니며, 과거에는 정적인 `--link`로 이름 해석을
  대신했다. 사용자 정의 브리지를 쓰는 것이 이 문제를 근본적으로 해결하며, 오늘날 사실상 표준 관행이다.
- Swarm 서비스 디스커버리는 기본값인 VIP 모드(고정 가상 IP + IPVS 로드밸런싱)와, 조회 시마다 모든 태스크
  IP를 반환하는 DNSRR 모드로 나뉘며, DNSRR은 라우팅 메시와 함께 쓸 수 없다.
- 포트 매핑(`-p`)은 iptables/nftables의 `nat` 테이블 DNAT 규칙(PREROUTING → DOCKER 체인)이 목적지 주소를
  컨테이너 IP로 바꾼 뒤, 라우팅을 거쳐 브리지와 veth 페어를 지나 컨테이너 네트워크 네임스페이스에 도달하는
  경로로 동작한다.
- 단일 컨테이너 포트 매핑은 그 컨테이너가 실제로 떠 있는 호스트에서만 유효하지만, Swarm의 ingress 라우팅
  메시는 클러스터의 모든 노드에서 게시된 포트로 접근할 수 있게 하고, 필요하면 ingress 오버레이 네트워크를
  통해 실제 태스크가 있는 노드로 트래픽을 재전달한다.
- `--dns`, `--dns-search`, `--dns-option`, `--add-host`는 각각 `/etc/resolv.conf`와 `/etc/hosts`에 정적으로
  반영되는 컨테이너 생성 시점의 설정이며, 실행 중 갱신하려면 일반적으로 컨테이너 재생성이 필요하다.

## 실습

```bash
# 1) 사용자 정의 네트워크에서 내장 DNS 확인
docker network create dns-lab
docker run -d --name svc-a --network dns-lab alpine:latest sleep infinity
docker run --rm --network dns-lab alpine:latest cat /etc/resolv.conf
# 확인 포인트: nameserver 127.0.0.11 이 보이는지 확인합니다.

# 2) 이름으로 다른 컨테이너 조회
docker run --rm --network dns-lab alpine:latest sh -c "nslookup svc-a || getent hosts svc-a"
# 확인 포인트: svc-a라는 이름이 실제 컨테이너 IP로 해석되는지 확인합니다.
# (alpine 이미지에 nslookup이 없다면 apk add --no-cache bind-tools 로 설치하거나 getent를 사용합니다.)

# 3) 기본 브리지와 비교
docker run --rm alpine:latest cat /etc/resolv.conf
# 확인 포인트: 127.0.0.11이 아니라 호스트의 실제 네임서버 설정이 그대로 보이는 것을 확인합니다.
# (기본 bridge 네트워크에는 내장 DNS 기반 컨테이너 이름 해석이 적용되지 않습니다.)

# 4) 포트 매핑의 iptables 규칙 확인
docker run -d -p 18080:80 --name web-port nginx:latest
sudo iptables -t nat -L DOCKER -n --line-numbers
# 확인 포인트: 18080 포트에 대한 DNAT 규칙이 컨테이너의 실제 IP:80을 가리키고 있는지 확인합니다.

curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:18080
# 확인 포인트: 200이 출력되면 DNAT 경로가 정상 동작하는 것입니다.

# 5) DNS 런타임 옵션 확인
docker run --rm \
  --dns=1.1.1.1 --dns-search=example.internal \
  --add-host=host.docker.internal:host-gateway \
  alpine:latest sh -c "cat /etc/resolv.conf; echo ---; cat /etc/hosts"
# 확인 포인트: resolv.conf에 nameserver 1.1.1.1과 search example.internal이,
# hosts 파일에 host.docker.internal 항목이 호스트 게이트웨이 IP로 추가되어 있는지 확인합니다.

# 6) 정리
docker rm -f svc-a web-port
docker network rm dns-lab
```

다음 장에서는 지금까지 여러 차례 등장한 iptables 기반 DNAT/필터링 규칙이 Docker Engine 29부터 어떻게
nftables 네이티브 백엔드로 재설계되고 있는지, 그리고 Docker Engine 28의 인바운드 하드닝이 어떤 문제를
해결하기 위한 것이었는지를 자세히 다룹니다.
