# 8장. 시그널

시그널은 리눅스에서 가장 오래되고 가장 다루기 까다로운 메커니즘이다. 하지만 피할 수 없다. `Ctrl+C`, `kill`, `docker stop`, OOM killer, 세그폴트, 자식 종료 통지, 끊긴 소켓에 쓰기가 모두 시그널로 도착한다. 이 장의 목표는 "시그널을 잘 쓰는 것"이 아니라 **"시그널에 당하지 않는 것"**이다.

## 8.1 시그널이란

시그널은 커널이 프로세스에 보내는 **번호 하나짜리 비동기 통지**다. 도착하면 프로세스가 무엇을 하고 있었든 중단되고 미리 정해진 동작이 실행된다.

시그널마다 **기본 동작(default action)**이 있다.

| 기본 동작 | 시그널 |
|---|---|
| **종료(Term)** | `SIGTERM`(15), `SIGINT`(2, Ctrl+C), `SIGHUP`(1), `SIGPIPE`(13), `SIGALRM`(14), `SIGUSR1/2` |
| **종료 + 코어 덤프(Core)** | `SIGSEGV`(11), `SIGABRT`(6), `SIGBUS`(7), `SIGFPE`(8), `SIGILL`(4), `SIGQUIT`(3, Ctrl+\) |
| **무시(Ign)** | `SIGCHLD`(17), `SIGURG`, `SIGWINCH` |
| **정지(Stop)** | `SIGSTOP`(19), `SIGTSTP`(20, Ctrl+Z), `SIGTTIN/TTOU` |
| **재개(Cont)** | `SIGCONT`(18) |

프로세스는 대부분의 시그널에 대해 동작을 바꿀 수 있다. **핸들러를 등록**하거나, **무시**하거나, **블록**(나중에 받기)할 수 있다. 예외는 두 개다. **`SIGKILL`(9)과 `SIGSTOP`은 잡을 수도 무시할 수도 없다.** 그래서 `kill -9`는 최후의 수단이고, 그래서 `kill -9`로 죽인 프로세스는 정리 코드를 실행할 기회가 없다(임시 파일, 락 파일, 절반 쓴 데이터가 남는다).

### 종료 코드로 시그널 읽기

시그널로 죽은 프로세스의 종료 상태는 셸에서 `128 + 시그널 번호`로 보인다.

| 종료 코드 | 의미 |
|---|---|
| 130 | SIGINT (Ctrl+C) |
| 137 | SIGKILL — **OOM killer** 또는 `kill -9`, `docker stop` 타임아웃 |
| 139 | SIGSEGV — 세그폴트 |
| 143 | SIGTERM — 정상 종료 요청 |
| 134 | SIGABRT — `abort()`, assert 실패, glibc가 힙 손상 감지 |

쿠버네티스 파드의 `Exit Code: 137`을 보면 첫 의심은 메모리 제한이다 ([5장](05_메모리.md)).

## 8.2 시그널의 출처

- **커널 → 하드웨어 예외**: 잘못된 메모리 접근(`SIGSEGV`, `SIGBUS`), 0으로 나누기(`SIGFPE`). 동기적이다. 그 명령을 실행한 바로 그 스레드에 간다.
- **커널 → 이벤트**: 자식 종료(`SIGCHLD`), 닫힌 파이프에 쓰기(`SIGPIPE`), 터미널 끊김(`SIGHUP`), 타이머(`SIGALRM`), 윈도우 크기 변경(`SIGWINCH`).
- **다른 프로세스**: `kill(pid, sig)`. 같은 UID거나 root여야 한다. `kill` 명령, `docker stop`(SIGTERM 후 10초 뒤 SIGKILL), systemd(`KillSignal=`), 쿠버네티스(SIGTERM 후 `terminationGracePeriodSeconds`).
- **터미널**: Ctrl+C → SIGINT, Ctrl+\ → SIGQUIT, Ctrl+Z → SIGTSTP를 **전경 프로세스 그룹 전체**에.
- **자기 자신**: `raise`, `abort`, `alarm`.

## 8.3 핸들러 등록: signal()이 아니라 sigaction()

```c
#include <signal.h>

static volatile sig_atomic_t got_term = 0;

static void on_term(int sig) {
    got_term = 1;                  // 플래그만 세운다. 다른 일은 메인 루프가
}

struct sigaction sa = {0};
sa.sa_handler = on_term;
sigemptyset(&sa.sa_mask);
sa.sa_flags = SA_RESTART;          // 중단된 시스템 콜을 자동 재시작
sigaction(SIGTERM, &sa, NULL);
sigaction(SIGINT,  &sa, NULL);

// 메인 루프
while (!got_term) {
    do_work();
}
cleanup_and_exit();
```

`signal()`은 역사적 이유로 플랫폼마다 동작이 다르다(핸들러가 한 번 실행되면 기본으로 되돌아가는 구현도 있었다). 항상 `sigaction`을 써라.

### 핸들러 안에서 할 수 있는 일은 거의 없다

시그널 핸들러는 프로그램의 **임의의 지점**에서 실행된다. `malloc` 도중일 수도, `printf`가 버퍼를 조작하는 도중일 수도 있다. 핸들러가 다시 `malloc`이나 `printf`를 부르면 내부 자료구조가 깨지거나 데드락된다(`malloc`은 락을 잡는다. 락을 잡은 채 시그널이 오고 핸들러가 다시 `malloc`을 부르면 자기 자신을 기다린다).

핸들러에서 부를 수 있는 함수는 **async-signal-safe** 목록(`man 7 signal-safety`)에 있는 것만이다. `write`, `_exit`, `kill`, `sigaction`, `waitpid` 등 시스템 콜 대부분은 안전하다. **`printf`, `malloc`, `free`, `syslog`, 뮤텍스 잠금, C++ 예외, 대부분의 라이브러리 함수는 안전하지 않다.** 로그를 남기고 싶어도 `write(2, "got signal\n", 11)`처럼 직접 써야 한다.

그래서 표준 패턴은 위 코드처럼 **핸들러는 `volatile sig_atomic_t` 플래그 하나만 세우고 즉시 반환**하고, 실제 처리는 메인 루프에서 한다. `errno`도 핸들러가 바꿀 수 있으므로 핸들러 진입 시 저장하고 나갈 때 복원한다.

## 8.4 EINTR: 시그널이 시스템 콜을 끊는다

블로킹 시스템 콜(`read`, `accept`, `wait`, `nanosleep`...) 중에 시그널 핸들러가 실행되면, 시스템 콜은 `-1`과 `errno = EINTR`로 반환된다. 이걸 처리하지 않은 코드는 "가끔 이유 없이" 읽기 실패를 낸다.

```c
// 방법 1: 재시도 루프
ssize_t n;
do {
    n = read(fd, buf, sz);
} while (n == -1 && errno == EINTR);

// 방법 2: SA_RESTART 플래그 — 커널이 대부분의 시스템 콜을 자동 재시작
```

`SA_RESTART`가 있어도 재시작되지 않는 것들이 있다. `sleep`류, `epoll_wait`/`poll`/`select`, 타임아웃이 설정된 소켓 연산. 이벤트 루프의 `epoll_wait`는 반드시 `EINTR`를 처리해야 한다. 자기 시그널이 아니어도 `SIGCHLD`, `SIGWINCH` 등이 언제든 올 수 있다.

## 8.5 실무에서 반드시 처리할 시그널

### SIGTERM: 우아한 종료

`docker stop`, `kubectl delete pod`, `systemctl stop`이 보내는 것. 받으면 새 요청 수락을 멈추고, 진행 중인 요청을 마치고, 연결을 닫고, 상태를 저장하고, 종료해야 한다. 기본 동작(즉시 종료)에 맡기면 진행 중인 요청이 끊긴다. 유예 시간(도커 10초, 쿠버네티스 30초 기본) 안에 못 끝내면 `SIGKILL`이다.

**PID 1 함정**: 컨테이너에서 PID 1인 프로세스는 핸들러가 없는 시그널을 **커널이 무시한다.** 기본 동작이 "종료"인 `SIGTERM`도 무시된다. 그래서 핸들러 없는 서버는 `docker stop`에 10초 동안 반응하지 않다가 SIGKILL로 죽는다. 해결은 핸들러를 등록하거나 `tini`를 PID 1로 두는 것 ([3장](03_프로세스.md)).

**셸 스크립트 함정**: `CMD ["sh", "-c", "node server.js"]`처럼 셸이 PID 1이면 셸은 자식에게 시그널을 **전달하지 않는다.** `exec node server.js`로 셸을 교체하거나 exec 형식 `CMD ["node", "server.js"]`를 써라.

### SIGPIPE: 소리 없는 죽음

상대가 닫은 소켓이나 파이프에 `write`하면 `SIGPIPE`가 오고 기본 동작은 종료다. 클라이언트가 연결을 끊는 순간 서버가 죽는다. 로그도 없다. **모든 네트워크 서버는 시작 시 `signal(SIGPIPE, SIG_IGN)`을 해야 한다.** 그러면 `write`가 `EPIPE`를 반환하고 정상적으로 처리할 수 있다. 소켓 단위로는 `send(..., MSG_NOSIGNAL)`. 많은 런타임(Go, Node.js, Python)이 이를 대신 해주지만, C/C++ 서버나 일부 라이브러리는 아니다.

반면 `cat bigfile | head -1`처럼 파이프라인의 앞 명령이 `SIGPIPE`로 조용히 죽는 것은 **의도된 동작**이다. CLI 도구를 만들 때는 `SIGPIPE`를 무시하지 않는 것이 관례다(무시하면 `EPIPE` 에러 메시지를 뿜으며 죽는다).

### SIGCHLD: 좀비 방지

자식이 종료하면 온다. 기본 동작은 무시지만, 무시된다고 좀비가 회수되는 것은 아니다. `waitpid(-1, ..., WNOHANG)` 루프로 회수하거나, 종료 코드가 필요 없으면 `SIG_IGN`으로 **명시적으로** 설정해 커널이 자동 회수하게 한다 ([3장](03_프로세스.md)).

### SIGHUP: 설정 리로드 관례

터미널이 끊길 때 오는 시그널이지만, 데몬은 터미널이 없으므로 **"설정 다시 읽어라"**는 의미로 재정의하는 것이 관례다(nginx, sshd, rsyslog). `kill -HUP <pid>`.

### SIGSEGV, SIGABRT: 크래시

잡을 수는 있지만 **잡아서 계속 실행하면 안 된다.** 메모리가 이미 손상된 상태다. 잡는 정당한 용도는 스택 트레이스를 덤프하고 죽는 것(크래시 리포터)뿐이다. 그것도 async-signal-safe하게 해야 하니 `backtrace_symbols_fd`처럼 제한적이다. 대신 **코어 덤프**를 켜두는 것이 낫다: `ulimit -c unlimited`, `/proc/sys/kernel/core_pattern` 확인, 컨테이너라면 호스트의 core_pattern이 적용된다는 점 주의 ([9장](09_디버깅과_도구.md)).

## 8.6 시그널 마스크와 블로킹

시그널을 **블록**하면 도착해도 전달되지 않고 pending 상태로 대기한다. 언블록하면 그때 전달된다. 임계 영역에서 시그널을 잠시 막는 데 쓴다.

```c
sigset_t set, old;
sigemptyset(&set);
sigaddset(&set, SIGTERM);
pthread_sigmask(SIG_BLOCK, &set, &old);   // 스레드의 마스크 변경 (sigprocmask는 단일 스레드용)
/* SIGTERM 없이 처리할 구간 */
pthread_sigmask(SIG_SETMASK, &old, NULL);
```

**표준 시그널은 큐잉되지 않는다.** 블록된 동안 `SIGCHLD`가 다섯 번 와도 언블록 시 한 번만 전달된다. SIGCHLD 핸들러가 `while (waitpid(...) > 0)` 루프여야 하는 이유다. 실시간 시그널(`SIGRTMIN`~`SIGRTMAX`)은 큐잉되고 값도 전달할 수 있지만 잘 쓰이지 않는다.

## 8.7 멀티스레드와 시그널: 전용 스레드 패턴

프로세스에 온 시그널은 **그 시그널을 블록하지 않은 스레드 중 임의의 하나**에 전달된다. 어느 스레드에서 핸들러가 실행될지 모른다. 그래서 멀티스레드 프로그램의 정석은:

1. `main`에서 스레드를 만들기 **전에** 관심 있는 시그널을 모두 블록한다(새 스레드는 마스크를 상속한다).
2. 시그널 전용 스레드 하나가 `sigwait`으로 **동기적으로** 받는다. 핸들러가 아니므로 async-signal-safe 제약이 없다. 마음껏 `printf`, 락, 채널 전송을 할 수 있다.

```c
void *signal_thread(void *arg) {
    sigset_t *set = arg;
    int sig;
    for (;;) {
        sigwait(set, &sig);
        if (sig == SIGTERM) { request_shutdown(); return NULL; }
        if (sig == SIGHUP)  { reload_config(); }
    }
}
```

Go 런타임의 `signal.Notify`, Rust의 `signal-hook`, Java의 `sun.misc.Signal`이 내부적으로 이 패턴이다.

## 8.8 signalfd: 시그널을 이벤트 루프로

시그널을 블록한 뒤 `signalfd`로 fd를 만들면, 시그널이 `read`할 수 있는 데이터가 된다. 그 fd를 epoll에 등록하면 **소켓 이벤트와 시그널을 하나의 `epoll_wait`로** 처리할 수 있다. 핸들러도, 전용 스레드도, `EINTR`도 없다. 이벤트 루프 기반 서버(systemd가 이 방식이다)에 가장 깔끔한 방법이다.

```c
sigset_t mask; sigemptyset(&mask); sigaddset(&mask, SIGTERM); sigaddset(&mask, SIGCHLD);
sigprocmask(SIG_BLOCK, &mask, NULL);
int sfd = signalfd(-1, &mask, SFD_NONBLOCK | SFD_CLOEXEC);
// sfd를 epoll에 EPOLLIN으로 등록. 이벤트가 오면 read(sfd, &struct signalfd_siginfo, ...)
```

같은 철학의 `pidfd`(자식 종료를 poll로 대기), `timerfd`(타이머를 fd로)와 함께 쓰면 시그널 핸들러가 전혀 없는 서버를 만들 수 있다.

## 8.9 직접 확인해보기

```bash
kill -l                                   # 시그널 번호 목록
grep -E 'Sig(Pnd|Blk|Ign|Cgt)' /proc/<pid>/status   # pending/blocked/ignored/caught 마스크 (16진)
kill -TERM <pid>; echo $?                 # 종료 코드 확인 (128+N)
strace -e trace=signal -p <pid>           # 시그널 전달과 sigaction 호출 관찰
strace -e trace=rt_sigaction ./prog       # 프로그램이 어떤 핸들러를 등록하는지
timeout 5 ./prog                          # 5초 후 SIGTERM 보내기
```

`/proc/<pid>/status`의 `SigCgt`(caught)가 0이면 그 프로세스는 아무 핸들러도 등록하지 않은 것이다. PID 1인 컨테이너 프로세스라면 `docker stop`이 안 먹을 것이라 예측할 수 있다.

## 8.10 실전 체크리스트

- [ ] `SIGTERM`(과 `SIGINT`)에 우아한 종료 핸들러가 있는가? 유예 시간 안에 끝나는가?
- [ ] 네트워크 서버라면 `SIGPIPE`를 무시하는가?
- [ ] 자식을 만든다면 `SIGCHLD`를 처리하거나 명시적으로 `SIG_IGN`하는가?
- [ ] 핸들러 안에서 `printf`, `malloc`, 락, 로깅 라이브러리를 부르지 않는가? 플래그만 세우는가?
- [ ] 블로킹 시스템 콜과 `epoll_wait`의 `EINTR`를 처리하는가?
- [ ] 컨테이너에서 셸이 PID 1이 되어 시그널을 삼키고 있지 않은가? (`exec` 사용, exec 형식 CMD)
- [ ] 멀티스레드라면 시그널을 전용 스레드나 `signalfd`로 받는가?
- [ ] 코어 덤프가 활성화되어 있고 어디에 쓰이는지 아는가?

## 8.11 다른 OS에서는

Windows에는 시그널에 직접 대응하는 것이 없다. 역할별로 흩어져 있다.

| 역할 | Linux | Windows |
|---|---|---|
| 종료 요청 | `SIGTERM` | `WM_CLOSE`(GUI), 콘솔 컨트롤 핸들러 `CTRL_CLOSE_EVENT`, 서비스 `SERVICE_CONTROL_STOP` |
| Ctrl+C | `SIGINT` | `SetConsoleCtrlHandler`, `CTRL_C_EVENT` |
| 강제 종료 | `SIGKILL` | `TerminateProcess` |
| 하드웨어 예외 | `SIGSEGV`, `SIGFPE` | SEH (`__try/__except`), `AddVectoredExceptionHandler` |
| 자식 종료 통지 | `SIGCHLD` | 프로세스 핸들 대기 (`WaitForSingleObject`) |
| 닫힌 파이프 쓰기 | `SIGPIPE` | `ERROR_NO_DATA`/`ERROR_BROKEN_PIPE` 반환 (시그널 없음) |
| 타이머 | `SIGALRM`, `timerfd` | Waitable Timer, `SetTimer` |

**더 깊이**: TLPI 20~22장(시그널 기본, 핸들러, 고급 기능. 특히 21.1절 async-signal-safe, 21.5절 EINTR), 26장(SIGCHLD), 33.2절(스레드와 시그널), 23장(타이머). `man 7 signal`, `man 7 signal-safety`.

다음 장에서는 이 책에서 다룬 모든 것을 실제로 관찰하는 도구를 정리한다.
