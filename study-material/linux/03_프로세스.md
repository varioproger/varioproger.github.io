# 3장. 프로세스

## 3.1 프로세스란 무엇인가

프로세스는 "실행 중인 프로그램 하나에 대한 커널의 관리 단위"다. 실제로는 다음의 묶음이다.

- **가상 주소 공간**: 이 프로세스만 보는 독립된 메모리 뷰 ([5장](05_메모리.md))
- **파일 디스크립터 테이블**: 열린 파일, 소켓, 파이프 등에 대한 참조 ([7장](07_파일시스템과_IO.md))
- **최소 1개의 스레드(태스크)**: 실제로 코드를 실행하는 주체 ([4장](04_스레드와_동시성.md))
- **자격 증명**: 실제/유효 UID·GID, capabilities
- **환경**: 인자, 환경변수, 현재 디렉터리, umask, 시그널 처리 방식, 자원 한도(`ulimit`)
- **`task_struct`**: 커널이 이것들을 관리하기 위해 들고 있는 구조체

핵심은: **프로세스는 "그릇"이고, 실제 실행은 스레드가 한다.** 프로세스 자체는 코드를 실행하지 않는다.

## 3.2 프로세스의 메모리 레이아웃

```
높은 주소  ┌──────────────────────┐ 0x7fff...
          │ 스택 (main 스레드)      │ ↓ 아래로 자람. 지역 변수, 리턴 주소
          │  ...                 │
          │ 메모리 매핑 영역        │ 공유 라이브러리(libc.so), mmap()한 파일/익명 메모리,
          │  (mmap)              │ 다른 스레드들의 스택
          │  ...                 │
          │ 힙 (brk)              │ ↑ 위로 자람. malloc이 관리
          ├──────────────────────┤
          │ .bss  (초기화 안 된 전역) │ 0으로 채워짐, 실행 파일에는 크기만 기록
          │ .data (초기화된 전역)    │
          │ .text (코드)           │ 읽기 전용, 실행 가능. 같은 프로그램 여러 개가 물리 페이지 공유
낮은 주소  └──────────────────────┘ 0x400000 (또는 PIE면 랜덤)
```

직접 확인: `cat /proc/self/maps` 또는 `pmap -x <pid>`. 각 줄이 하나의 매핑이고 권한(`r-xp`, `rw-p`)이 표시된다. `p`는 private(COW), `s`는 shared.

## 3.3 프로세스 생성: fork와 exec

리눅스는 "새 프로그램 실행"을 두 단계로 나눈다.

```c
pid_t pid = fork();              // 1. 현재 프로세스를 복제
if (pid == -1) { perror("fork"); }
else if (pid == 0) {             // 자식
    execve("/bin/ls", argv, envp);   // 2. 자신을 다른 프로그램으로 교체
    _exit(127);                      //    exec이 반환했다면 실패
} else {                         // 부모
    int status;
    waitpid(pid, &status, 0);        // 3. 자식 종료 대기 + 종료 코드 회수
}
```

### fork()가 저렴한 이유: Copy-on-Write

`fork`는 부모의 주소 공간 전체를 "복제"하지만 실제로 페이지를 복사하지는 않는다. 페이지 테이블만 복사하고 모든 페이지를 **읽기 전용**으로 표시한다. 부모나 자식 중 한쪽이 **쓰기**를 시도하는 순간 페이지 폴트가 나고, 커널이 그 페이지 하나만 복사한다. 이것이 **Copy-on-Write(COW)**다.

그래서 `fork` 직후 `exec`하는 흔한 패턴은 거의 아무것도 복사하지 않는다. 하지만 함정이 있다.

- **큰 프로세스의 fork는 여전히 비싸다.** 페이지 테이블 복사 자체가 주소 공간 크기에 비례한다. 10GB 힙을 가진 프로세스가 `fork`하면 수십 ms가 걸릴 수 있다. Redis가 백그라운드 저장(BGSAVE)에 fork를 쓰면서 겪는 지연이 이것이다.
- **fork 후 부모가 계속 쓰기를 하면** COW 복사가 계속 일어나 메모리가 두 배 가까이 늘 수 있다.
- **멀티스레드 프로세스의 fork**는 위험하다. 자식에는 `fork`를 호출한 스레드 하나만 복제된다. 다른 스레드가 잡고 있던 뮤텍스는 영원히 잠긴 채 남는다(malloc 내부 락 포함). **멀티스레드 프로그램에서는 fork 직후 exec만 하라.** 그 사이에 `malloc`이나 `printf`도 부르지 마라.
- 자식으로 다른 프로그램을 띄우는 것이 목적이면 **`posix_spawn`**을 쓰는 것이 안전하고 빠르다. 최신 glibc는 내부적으로 `CLONE_VM|CLONE_VFORK`를 써서 주소 공간 복제를 건너뛴다.

### exec(): 프로세스 안의 프로그램을 통째로 교체

`execve`는 현재 프로세스의 코드, 데이터, 힙, 스택을 모두 버리고 새 실행 파일을 적재한다. **PID는 그대로**이고, 열린 파일 디스크립터도 기본적으로 그대로 유지된다. 이것이 셸 리다이렉션 `ls > out.txt`의 원리다. fork 후 자식에서 fd 1을 `out.txt`로 바꾸고 exec하면 된다.

fd가 exec을 넘어 상속되는 게 싫으면 `O_CLOEXEC` 플래그로 열어라. 서버 소켓이 자식 프로세스에 새어 나가면 부모가 소켓을 닫아도 포트가 안 풀리는 버그가 생긴다.

## 3.4 프로세스 종료와 좀비, 고아

**정상 종료 경로**: `exit()` → atexit 핸들러 실행, stdio 버퍼 플러시 → `_exit()` 시스템 콜 → 커널이 fd 닫기, 메모리 해제 → 종료 코드를 `task_struct`에 보관하고 **부모에게 `SIGCHLD` 전송**.

이 시점에서 프로세스는 **좀비(Z)**가 된다. 메모리도 fd도 없지만, 종료 코드를 담은 `task_struct`와 PID만 남아 있다. 부모가 `wait()`/`waitpid()`로 종료 코드를 회수하면 그제야 완전히 사라진다.

- **좀비가 쌓이면**: PID를 낭비한다(`pid_max` 기본 32768 또는 4194304). 결국 `fork: Resource temporarily unavailable`. 좀비는 `kill -9`로 죽일 수 없다. 이미 죽었기 때문이다. **부모를 고쳐야 한다.**
- **고아(Orphan)**: 부모가 먼저 죽은 자식. **PID 1(init/systemd)** 또는 "subreaper"로 지정된 프로세스에 재입양된다. init은 주기적으로 `wait`하여 고아가 좀비로 남지 않게 한다.

### 컨테이너의 PID 1 문제

도커 컨테이너 안에서는 **내 서버 프로세스가 PID 1**이 되는 경우가 많다. 그러면:

1. 컨테이너 내 모든 고아 프로세스가 내 서버에 재입양되는데, 내 서버는 `wait`할 줄 모른다 → 좀비 누적.
2. PID 1은 시그널 처리가 특별하다. 핸들러를 등록하지 않은 시그널은 **커널이 무시**한다. 그래서 `docker stop`(SIGTERM)에 반응하지 않고 10초 뒤 SIGKILL로 강제 종료된다.

해결: `tini`나 `dumb-init`을 ENTRYPOINT로 쓰거나(`docker run --init`), 직접 SIGTERM 핸들러와 SIGCHLD 회수 로직을 구현한다 ([8장](08_시그널.md)).

### 자식 회수의 올바른 패턴

```c
// SIGCHLD 핸들러: 여러 자식이 동시에 죽어도 시그널은 한 번만 올 수 있으므로 루프
void on_sigchld(int sig) {
    int saved = errno;
    while (waitpid(-1, NULL, WNOHANG) > 0) { }
    errno = saved;
}
```

자식 종료 코드에 관심이 없다면 `signal(SIGCHLD, SIG_IGN)`으로 커널이 자동 회수하게 할 수 있다.

## 3.5 PID, PPID, 프로세스 그룹, 세션

```
세션(SID=100) ── 로그인 셸 bash(PID 100)
   ├─ 프로세스 그룹(PGID=200): cat file | grep x | sort
   │     ├─ cat  (PID 200)
   │     ├─ grep (PID 201)
   │     └─ sort (PID 202)
   └─ 프로세스 그룹(PGID=300): ./server &
         └─ server (PID 300)
```

- **프로세스 그룹**: 파이프라인 하나가 한 그룹이다. `Ctrl+C`는 전경 그룹 전체에 `SIGINT`를 보낸다. `kill -TERM -300`(음수 PID)으로 그룹 전체에 시그널을 보낼 수 있다.
- **세션**: 터미널 하나에 연결된 그룹들의 묶음. 터미널이 끊기면(SSH 끊김) 세션 리더에게 `SIGHUP`이 가고, 이것이 전파되어 백그라운드 서버까지 죽는다.

`nohup`, `setsid`, systemd 서비스가 이 문제를 푸는 방법이다. 직접 데몬을 만들 때의 고전적 절차: `fork` → 자식에서 `setsid()`로 새 세션 생성(터미널과 분리) → 다시 `fork`(세션 리더가 아니게 하여 터미널 재획득 방지) → `chdir("/")`, `umask(0)`, stdin/out/err을 `/dev/null`로. 요즘은 systemd가 이걸 대신 해주므로 **포그라운드로 실행하고 stdout에 로그를 쓰는** 것이 권장된다. 컨테이너도 같은 원칙이다.

## 3.6 자격 증명과 권한

프로세스에는 **실제 UID(real)**, **유효 UID(effective)**, **저장된 set-UID(saved)**가 있다. 권한 검사는 **유효 UID**로 한다.

- `passwd` 같은 set-UID 프로그램은 실행 시 유효 UID가 파일 소유자(root)가 된다.
- 서버가 80번 포트를 바인딩하려면 root(또는 `CAP_NET_BIND_SERVICE`)가 필요하다. root로 시작해 포트를 열고 `setuid`로 권한을 내리는 고전 방식보다, **capabilities**(`setcap cap_net_bind_service=+ep ./server`)나 systemd의 `AmbientCapabilities`로 필요한 권한만 주는 것이 현재 표준이다.
- 컨테이너 안의 root는 기본적으로 capabilities가 제한된 root다. `docker run --user 1000` 등으로 애초에 root를 쓰지 않는 것이 좋다.

## 3.7 자원 한도: ulimit과 RLIMIT

프로세스별로 커널이 강제하는 한도가 있다. `ulimit -a`로 보고, 코드에서는 `getrlimit`/`setrlimit`.

| 한도 | 기본값(일반) | 초과 시 |
|---|---|---|
| `RLIMIT_NOFILE` (fd 수) | 1024 soft | `EMFILE`. 서버는 반드시 올려야 한다 |
| `RLIMIT_STACK` | 8MB | 스택 오버플로 → `SIGSEGV` |
| `RLIMIT_NPROC` (프로세스/스레드 수) | 수만 | `fork`/`pthread_create` 실패 `EAGAIN` |
| `RLIMIT_CORE` | 0 (코어 덤프 없음) | 디버깅 위해 `unlimited`로 |
| `RLIMIT_AS` (가상 메모리) | unlimited | `mmap` 실패 `ENOMEM` |

systemd 서비스는 `LimitNOFILE=65536` 식으로 지정한다. 컨테이너는 도커 데몬의 기본값을 상속한다.

## 3.8 프로세스 간 통신(IPC)

프로세스는 주소 공간이 격리되어 있으므로, 데이터를 주고받으려면 커널이 중재하는 명시적 메커니즘이 필요하다.

| 방식 | 특징 | 용도 |
|---|---|---|
| 파이프 (`pipe`), FIFO | 단방향 바이트 스트림. 64KB 커널 버퍼. 꽉 차면 writer 블로킹 | 부모-자식, 셸 파이프라인 |
| Unix 도메인 소켓 | 양방향, 스트림/데이터그램, **fd 전달 가능**(`SCM_RIGHTS`) | 로컬 서비스 간 (Docker 데몬, systemd, DB 로컬 접속) |
| 공유 메모리 (`shm_open`+`mmap`, `memfd_create`) | 커널 개입 없이 직접 접근. 가장 빠름. 동기화는 직접 | 대용량·저지연 데이터 (DB 버퍼 풀, 멀티프로세스 캐시) |
| 시그널 | 정수 하나만 전달 | 종료·재시작 통지 ([8장](08_시그널.md)) |
| POSIX 메시지 큐, 세마포어 | 구조화된 메시지, 프로세스 간 동기화 | 잘 안 쓰인다. 대부분 소켓으로 대체 |
| eventfd | 카운터 하나. epoll에 붙일 수 있음 | 스레드/프로세스 간 이벤트 알림 |

공유 메모리가 가장 빠른 이유: 파이프/소켓은 데이터를 유저 버퍼 → 커널 버퍼 → 상대 유저 버퍼로 두 번 복사하지만, 공유 메모리는 **같은 물리 페이지를 두 프로세스의 가상 주소 공간에 매핑**만 해두면 복사 없이 접근한다 ([5장](05_메모리.md)).

**파이프의 함정**: 자식의 stdout과 stderr을 둘 다 파이프로 받는 부모가 stdout만 읽고 있으면, 자식이 stderr을 64KB 이상 쓰는 순간 자식이 블로킹되어 **데드락**이 된다. Python의 `subprocess.communicate()` 같은 API가 존재하는 이유다.

## 3.9 프로세스 vs 스레드, 언제 무엇을 쓰나

| 기준 | 여러 프로세스 | 여러 스레드 |
|---|---|---|
| 격리/안정성 | 하나가 죽어도 다른 것에 영향 없음 | 하나가 크래시하면 전체가 죽음 |
| 통신 비용 | IPC 필요, 상대적으로 비쌈 | 메모리 공유, 저렴하지만 동기화 필요 |
| 생성 비용 | 비쌈 (페이지 테이블 복사, 수십~수백 µs) | 저렴 (수 µs) |
| 대표 사례 | nginx worker, PostgreSQL 백엔드, Chrome 탭, gunicorn 워커 | 웹 서버 요청 처리 풀, DB 커넥션 풀 |
| GIL 있는 언어(CPython) | 진짜 병렬 CPU 활용 가능 | CPU 바운드는 병렬 안 됨 |

## 3.10 직접 확인해보기

```bash
ps -eo pid,ppid,pgid,sid,stat,cmd --forest     # 프로세스 트리와 그룹/세션
cat /proc/$$/status | grep -E 'State|Threads|VmRSS|Uid'
ls -l /proc/$$/fd                              # 셸이 열고 있는 fd
strace -f -e trace=process ./myprog            # fork/exec/wait/exit만 추적
ps -eo stat,pid,cmd | awk '$1 ~ /Z/'           # 좀비 찾기
```

## 3.12 다른 OS에서는

| 개념 | Linux | Windows |
|---|---|---|
| 생성 | `fork` + `exec` (복제 후 교체), `posix_spawn` | `CreateProcess` (즉시 새 이미지) |
| 관리 구조체 | `task_struct` | EPROCESS |
| 종료 회수 | `wait`/`waitpid`, 좀비 | 핸들 닫기, 프로세스 객체 참조 카운트 |
| 부모 사망 시 | init/subreaper에 재입양 | 독립적으로 계속 실행 |
| 그룹 제어 | 프로세스 그룹, 세션, cgroup | Job Object |
