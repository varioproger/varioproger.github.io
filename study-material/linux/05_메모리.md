# 5장. 메모리

이 책에서 가장 오해가 많은 주제다. "메모리 사용량"이라는 숫자 하나에 최소 4가지 다른 의미가 섞여 있고, `free`가 보여주는 "사용 가능 메모리"도 직관과 다르다.

## 5.1 가상 메모리: 모든 것의 시작

프로세스가 보는 주소(예: `0x7f3a1c200000`)는 **실제 물리 메모리 주소가 아니다.** CPU의 MMU가 **페이지 테이블**을 통해 가상 주소를 물리 주소로 변환한다. 단위는 **페이지**, 기본 4KB다.

```
가상 주소 공간 (프로세스별 독립, x86-64: 128TB)    물리 메모리 (전체 시스템 공유)
┌──────────────┐                               ┌──────────────┐
│ 페이지 0x1000  │ ──────────────────────────────▶│ 물리 프레임 A   │
│ 페이지 0x2000  │ ──────────────────────────────▶│ 물리 프레임 B   │
│ 페이지 0x3000  │ ─(매핑 없음: 접근 시 페이지 폴트)   │  ...          │
│ 페이지 0x4000  │ ──(디스크/스왑에 있음)             │               │
└──────────────┘                               └──────────────┘
```

왜 이렇게 하는가:

1. **격리**: 각 프로세스가 독립된 주소 공간을 갖는다. 다른 프로세스의 메모리는 페이지 테이블에 없으니 접근 자체가 불가능하다.
2. **지연 할당**: 실제로 접근할 때까지 물리 메모리를 배정하지 않는다(demand paging). 그래서 물리 메모리보다 큰 주소 공간을 쓸 수 있다.
3. **공유**: 같은 물리 페이지를 여러 프로세스가 매핑할 수 있다. libc 코드는 시스템에 한 번만 있다. COW도 이 원리.
4. **파일 매핑**: 파일을 메모리처럼 접근할 수 있다(`mmap`).

**페이지 폴트**: 매핑이 없는 가상 주소에 접근하면 CPU가 예외를 던지고 커널이 처리한다.

- **Minor fault**: 물리 페이지를 새로 배정하거나(첫 접근), 이미 페이지 캐시에 있는 것을 매핑만 하면 됨. 수 µs.
- **Major fault**: 디스크에서 읽어와야 함(스왑인, 파일 첫 읽기). 수 ms. **100배 이상 느리다.**
- **잘못된 접근**: 매핑도 없고 정당한 이유도 없음 → `SIGSEGV`. 이것이 "Segmentation fault"다.

`ps -o min_flt,maj_flt <pid>` 또는 `/proc/<pid>/stat`로 볼 수 있다. major fault가 계속 늘면 메모리가 부족해 스왑을 치고 있다는 뜻이다.

## 5.2 "할당했다"와 "실제로 쓴다"는 다르다

```c
char *p = malloc(1 << 30);        // 1GB. 성공. 그런데 RSS는 거의 안 늘어남
memset(p, 0, 1 << 30);            // 이제야 물리 페이지 262,144개가 실제로 배정됨
```

`malloc`은 큰 요청을 `mmap(MAP_ANONYMOUS)`로 처리하고, 이것은 **가상 주소 공간에 예약만** 한다. 물리 페이지는 처음 쓰기가 일어나는 페이지마다 하나씩 폴트를 통해 배정된다. 그래서:

- **VSZ(가상 크기)**는 "예약한 주소 공간". 의미 없는 숫자인 경우가 많다(JVM, Go 런타임은 수 GB를 예약한다).
- **RSS(Resident Set Size)**는 "현재 물리 메모리에 있는 페이지". 실제 사용량에 가깝지만, **공유 라이브러리 페이지도 포함**되어 프로세스별로 더하면 실제 총량보다 크다.
- **PSS(Proportional Set Size)**는 공유 페이지를 공유하는 프로세스 수로 나눠 배분한 것. 여러 프로세스의 합이 실제 총량과 일치한다. `/proc/<pid>/smaps_rollup`에서 볼 수 있다.
- **USS(Unique Set Size)**는 이 프로세스만 쓰는 페이지. "이 프로세스를 죽이면 돌아오는 메모리".

| 상황 | 볼 숫자 |
|---|---|
| 이 프로세스가 얼마나 먹나 (대략) | RSS (`top`의 RES) |
| 여러 워커 프로세스의 합계 | PSS 합 |
| 컨테이너 메모리 제한에 걸리나 | cgroup `memory.current` (RSS + 페이지 캐시 + 커널 메모리) |
| 메모리 누수인가 | RSS 또는 USS의 **시간에 따른 추세** |

## 5.3 malloc은 시스템 콜이 아니다: 할당자의 내부

`malloc`/`free`는 glibc의 **ptmalloc2** 할당자다. 커널에 메모리를 요청하는 두 시스템 콜 위에서 돈다.

- `brk`/`sbrk`: 힙의 끝(program break)을 늘린다. 128KB 미만 작은 할당의 기본 공급원.
- `mmap`: 128KB 이상(`M_MMAP_THRESHOLD`, 동적 조정됨) 큰 할당은 별도 매핑. `free`하면 `munmap`으로 즉시 반환.

할당자는 요청받은 작은 조각들을 자기가 관리하는 큰 블록(아레나) 안에서 잘라 준다. 그래서:

**`free()`해도 RSS가 안 줄어든다.** 할당자가 재사용을 위해 들고 있기 때문이다. 힙 꼭대기가 비어야만 `brk`로 반환하는데, 중간에 살아 있는 조각 하나가 있으면 그 아래 전부가 갇힌다. 이것이 **단편화(fragmentation)**다. 장기 실행 서버가 "누수는 없는데 RSS가 서서히 늘어나는" 흔한 원인이다.

**멀티스레드와 아레나**: 락 경합을 피하기 위해 ptmalloc은 스레드마다 별도 아레나를 만든다(최대 코어 수 × 8). 스레드가 많은 서버에서 아레나마다 조각이 남아 RSS가 부풀어 오르는 것이 잘 알려진 문제다. 대응:

- `MALLOC_ARENA_MAX=2` 환경변수 (Java 컨테이너에서 흔한 설정)
- `jemalloc`, `tcmalloc`, `mimalloc`으로 교체 (`LD_PRELOAD=libjemalloc.so`). 단편화가 덜하고 메모리 반환이 적극적이다. Redis, Rust 프로젝트 다수가 jemalloc을 쓴다.
- `malloc_trim(0)`으로 강제 반환 시도

**`calloc`의 비밀**: `calloc`은 `malloc` + `memset(0)`이 아니다. 새 `mmap` 페이지는 커널이 이미 0으로 준다는 것을 알기 때문에 memset을 건너뛴다. 큰 배열을 0으로 초기화할 때 `calloc`이 훨씬 빠른 이유.

## 5.4 오버커밋과 OOM Killer: ENOMEM이 안 나오는 이유

리눅스는 기본적으로 **오버커밋**한다. `malloc(100GB)`가 물리 메모리 16GB 머신에서 성공할 수 있다. 실제로 쓰기 시작해야 문제가 된다. `vm.overcommit_memory`:

- `0` (기본, heuristic): 명백히 터무니없는 요청만 거절
- `1`: 항상 성공
- `2`: 엄격. 스왑 + RAM × `overcommit_ratio`까지만 허용. `ENOMEM`이 실제로 나옴

물리 메모리가 진짜로 바닥나면 커널은 **OOM killer**를 발동한다. `oom_score`가 가장 높은(대략 RSS가 가장 큰) 프로세스를 `SIGKILL`로 죽인다. **당신의 프로그램에는 아무 경고도 없다.** `dmesg | grep -i 'killed process'`에만 흔적이 남는다.

- `/proc/<pid>/oom_score_adj`(-1000 ~ 1000)로 우선순위를 조정할 수 있다. -1000은 절대 안 죽임.
- 컨테이너에서는 cgroup 메모리 제한(`memory.max`)에 닿으면 **그 컨테이너 안에서** OOM kill이 일어난다. 도커는 `OOMKilled: true`, 쿠버네티스는 exit code 137로 보고한다. 이것이 **"137"의 의미**다(128 + SIGKILL 9).

메모리를 실제로 확보해두고 싶다면 `mlock`/`MAP_POPULATE`로 페이지를 미리 배정한다. DB나 지연에 민감한 서버가 쓴다.

## 5.5 페이지 캐시: "free 메모리가 없다"는 착각

```
$ free -h
               total   used   free   shared  buff/cache  available
Mem:            31Gi   8.0Gi  1.2Gi   0.5Gi    22Gi       22Gi
```

`free`가 1.2GB뿐이지만 문제없다. 22GB는 **페이지 캐시**다. 커널은 디스크에서 읽은 파일 내용과 쓸 예정인 내용을 남는 RAM에 최대한 캐시한다. 프로세스가 메모리를 필요로 하면 캐시를 버리고 내준다. **봐야 할 숫자는 `available`**이다.

- 파일을 `read()`하면 디스크 → 페이지 캐시 → 유저 버퍼로 복사된다. 두 번째 읽기는 캐시에서 나와 100배 빠르다.
- `write()`는 페이지 캐시에 쓰고 **즉시 반환**한다. 디스크에는 나중에(수 초 내, `dirty_expire_centisecs`) 커널 스레드가 쓴다. 그래서 `write` 성공 ≠ 디스크 기록. 정전이면 사라진다. `fsync`가 필요한 이유 ([7장](07_파일시스템과_IO.md)).
- 컨테이너 cgroup의 `memory.current`에는 **그 컨테이너가 만든 페이지 캐시도 포함**된다. 큰 파일을 읽기만 해도 컨테이너 메모리가 한도에 가까워지는 것처럼 보이지만, 압박이 오면 회수되므로 대부분 OOM까지는 안 간다. 로그를 많이 쓰는 컨테이너에서 "메모리 사용량"이 높게 보이는 원인.

`echo 3 > /proc/sys/vm/drop_caches`로 캐시를 비울 수 있지만 벤치마크용이다. 운영에서 할 이유가 없다.

## 5.6 mmap: 파일을 메모리처럼

```c
int fd = open("data.bin", O_RDONLY);
char *p = mmap(NULL, size, PROT_READ, MAP_PRIVATE, fd, 0);
// 이제 p[i]로 파일 내용에 접근. read() 호출 없음
```

- 페이지 캐시의 물리 페이지를 **그대로 내 주소 공간에 매핑**한다. `read`처럼 커널 버퍼 → 유저 버퍼 복사가 없다(zero-copy).
- 접근할 때마다 필요한 페이지만 폴트로 들어온다. 100GB 파일을 매핑해도 접근한 부분만 메모리를 쓴다.
- `MAP_SHARED`로 매핑하고 쓰면 파일에 반영된다. 같은 파일을 매핑한 다른 프로세스에도 보이므로 공유 메모리 IPC가 된다. `msync`로 디스크 반영을 강제.
- 단점: 무작위 접근이 많으면 페이지 폴트 비용이 `read`보다 클 수 있고, 매핑된 파일이 I/O 에러를 내면 `SIGBUS`가 온다. 매핑을 만들고 지우는 것 자체가 비싸다(TLB 플러시).

DB(SQLite, LMDB), 검색 엔진(Lucene)이 mmap을 핵심으로 쓴다. 실행 파일과 공유 라이브러리를 적재하는 방법도 mmap이다.

## 5.7 스왑

물리 메모리가 부족하면 커널은 익명 페이지(힙, 스택)를 스왑 공간에 내보낸다. 파일 페이지는 그냥 버린다(디스크에 원본이 있으니). 나중에 접근하면 major fault로 다시 읽어온다.

- 스왑이 조금 쓰이는 것은 정상이다(오래 안 쓴 페이지). **스왑 in/out이 계속 일어나는 것**(`vmstat`의 `si`/`so`)이 문제다. 이 상태가 **thrashing**이고, 시스템이 "멈춘 듯" 느려진다.
- `vm.swappiness`(0~200, 기본 60)로 스왑 경향을 조절한다. DB 서버는 낮게(1~10) 두는 것이 관례.
- 쿠버네티스는 전통적으로 스왑을 끈다. 스왑이 있으면 메모리 제한과 스케줄링 예측이 어려워지기 때문.
- 지연에 민감한 코드는 `mlock`으로 스왑을 막을 수 있다(`RLIMIT_MEMLOCK` 한도 내).

## 5.8 캐시와 TLB: 왜 접근 패턴이 성능을 좌우하는가

CPU 캐시(L1: ~1ns, L2: ~4ns, L3: ~15ns, 메모리: ~80ns)는 자릿수 차이다. 데이터가 캐시에 있느냐가 알고리즘의 big-O보다 중요한 경우가 흔하다.

```c
// 캐시 친화적: 행 우선 순회 (연속 메모리)
for (i = 0; i < N; i++) for (j = 0; j < N; j++) sum += m[i][j];

// 캐시 비친화적: 열 우선 순회 (매번 다른 캐시 라인) — 같은 연산, 5~10배 느림
for (j = 0; j < N; j++) for (i = 0; i < N; i++) sum += m[i][j];
```

**TLB(Translation Lookaside Buffer)**는 가상→물리 변환 결과를 캐시한다. 4KB 페이지에서 TLB 엔트리 수천 개면 커버 범위가 수 MB밖에 안 된다. 수 GB의 힙을 무작위로 접근하는 프로그램(DB, 인메모리 캐시, JVM 큰 힙)은 TLB 미스가 병목이 된다.

**Huge Page(2MB)**를 쓰면 엔트리 하나가 512배 넓은 범위를 커버한다.

- **Transparent Huge Pages(THP)**: 커널이 자동으로 합친다(`/sys/kernel/mm/transparent_hugepage/enabled`). 대부분 이득이지만 `khugepaged`의 압축 작업이 지연 스파이크를 만들어 Redis, MongoDB, PostgreSQL은 `madvise` 또는 `never`를 권한다.
- **명시적 hugetlbfs**: 미리 예약하고 `mmap(MAP_HUGETLB)`. DB 버퍼 풀, DPDK.

## 5.9 NUMA 한 줄

소켓이 2개 이상인 서버에서는 메모리가 CPU 소켓별로 나뉜다. 다른 소켓의 메모리 접근은 1.5~2배 느리다. 기본 정책은 "처음 접근한 스레드가 있는 노드에 배정"이다. 스레드가 소켓 사이를 이사하면 원격 접근이 늘어난다. `numactl --cpunodebind=0 --membind=0`으로 고정하거나, 큰 DB는 노드마다 프로세스를 하나씩 띄운다. 클라우드 VM 대부분은 단일 노드이므로 걱정할 일이 적다.

## 5.10 메모리 누수 찾기

메모리 누수는 세 가지 다른 현상이다.

1. **진짜 누수**: 참조를 잃어 다시는 `free`할 수 없는 메모리. C/C++의 고전 문제. Valgrind(`memcheck`), AddressSanitizer(`-fsanitize=address`, LeakSanitizer 포함), heaptrack으로 잡는다.
2. **논리적 누수**: 참조는 살아 있지만 다시는 안 쓰는 것. 만료 없는 캐시, 계속 자라는 리스트, 닫지 않은 리스너. GC 언어에서의 "누수"는 전부 이것이다. 힙 덤프 분석이 필요하다.
3. **할당자 단편화**: 누수가 아닌데 RSS가 는다. 5.3절. `malloc_info`나 jemalloc 통계로 구분한다.

첫 번째 조치는 항상 같다. **`/proc/<pid>/status`의 VmRSS를 시간에 따라 기록**하고, 일정하게 증가하는지 계단식으로 증가 후 안정되는지(단편화나 캐시 워밍업) 본다.

## 5.11 직접 확인해보기

```bash
cat /proc/<pid>/status | grep -E 'Vm(Size|RSS|Swap)|RssAnon|RssFile'
cat /proc/<pid>/smaps_rollup                 # PSS, USS, 공유/사적 페이지
pmap -x <pid> | sort -k3 -n | tail           # 가장 큰 매핑
free -h; cat /proc/meminfo
vmstat 1                                     # si/so (스왑), free, cache
ps -o pid,min_flt,maj_flt,rss,vsz,cmd -p <pid>
dmesg -T | grep -i -E 'oom|killed process'   # OOM 이력
cat /sys/fs/cgroup/memory.current /sys/fs/cgroup/memory.max   # 컨테이너 메모리 (cgroup v2)
```

## 5.13 다른 OS에서는

| 개념 | Linux | Windows |
|---|---|---|
| 예약/커밋 | `mmap` (예약+커밋 동시, 지연 배정) | `VirtualAlloc(MEM_RESERVE)` / `MEM_COMMIT` 구분 |
| 오버커밋 | 기본 허용, OOM killer | 커밋 한도 엄격 (커밋 실패 시 할당 실패) |
| 상주 메모리 | RSS | Working Set |
| 페이지 캐시 | Page cache (`buff/cache`) | System cache, Standby list |
| 파일 매핑 | `mmap` | `CreateFileMapping` + `MapViewOfFile` |
| 힙 할당자 | ptmalloc2 (glibc), jemalloc 등 | Heap Manager (LFH), mimalloc |
| 스왑 | 스왑 파티션/파일 | pagefile.sys |

**더 깊이**: TLPI 6.3~6.4절(메모리 레이아웃, 가상 메모리), 7장(malloc), 49~50장(mmap, 가상 메모리 연산), 48·54장(공유 메모리). *How Linux Works* 8장. 커널 내부는 *Understanding the Linux Virtual Memory Manager*(Mel Gorman, 무료 공개).
