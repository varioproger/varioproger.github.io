# 10장. 마무리

## 10.1 이 책에서 반복된 하나의 패턴

돌이켜보면 모든 장에서 같은 구조가 반복됐다.

> **"프로그래머에게는 단순한 추상화로 보이지만, 그 아래에서 커널은 훨씬 복잡한 일을 하고 있으며, 그 복잡함이 새어나오는 지점(leaky abstraction)이 바로 버그와 성능 문제가 생기는 곳이다."**

- **프로세스**: "그냥 프로그램 하나 실행"처럼 보이지만 → COW 페이지 테이블 복사, 좀비 회수, PID 1의 특별 취급, fd 상속
- **스레드**: "그냥 동시에 실행"처럼 보이지만 → futex 경합, 메모리 가시성, 거짓 공유, 시그널이 어느 스레드로 가는지
- **메모리**: "그냥 할당"처럼 보이지만 → 가상/물리 분리, 지연 배정, 할당자 단편화, 오버커밋과 OOM killer, 페이지 캐시
- **네트워크**: "그냥 send/recv"처럼 보이지만 → 스트림에 경계 없음, TIME_WAIT, 블로킹의 확장성 한계, 준비/완료 모델
- **파일**: "그냥 write"처럼 보이지만 → stdio 버퍼, 페이지 캐시, fsync, 디렉터리 fsync, rename 원자성
- **시그널**: "그냥 kill"처럼 보이지만 → async-signal-safe, EINTR, 큐잉 안 됨, PID 1은 무시

그리고 리눅스 고유의 패턴 하나가 더 있었다. **"모든 것은 fd다."** 소켓, 파이프, 타이머, 시그널, 프로세스, 익명 메모리까지 fd로 만들 수 있고, `epoll` 하나로 전부 기다릴 수 있다. 이 통일성을 알면 리눅스 위의 모든 비동기 런타임(libuv, tokio, Go netpoller, asyncio)의 구조가 한 번에 보인다.

## 10.2 핵심 개념 한 장 요약

| 장 | 한 문장 요약 |
|---|---|
| 2. OS 큰 그림 | 유저 코드는 시스템 콜·인터럽트·예외로만 커널에 들어가고, 스케줄러는 vruntime으로 공정하게 CPU를 나누며, cgroup 쿼터가 컨테이너의 스로틀링을 만든다 |
| 3. 프로세스 | 프로세스는 격리된 주소 공간 + fd 테이블의 그릇이고, fork는 COW로 싸지만 큰 프로세스와 멀티스레드에서는 위험하며, 자식은 반드시 wait로 회수해야 한다 |
| 4. 스레드/동시성 | 커널에게 스레드는 주소 공간을 공유하는 태스크일 뿐이며, 락은 싸지만 경합은 비싸고, 동기화 없는 공유 변수 접근은 정의되지 않은 동작이다 |
| 5. 메모리 | 프로세스가 보는 주소는 가상이고 물리 페이지는 첫 접근 때 배정되며, free는 OS에 반환이 아니고, 137은 OOM kill이며, free 메모리가 적은 것은 페이지 캐시 때문이다 |
| 6. 네트워크 | TCP는 경계 없는 스트림이고, TIME_WAIT은 정상이며, 수만 커넥션은 스레드가 아니라 epoll로 기다리고, SIGPIPE를 무시하지 않은 서버는 조용히 죽는다 |
| 7. 파일/IO | write 성공은 디스크 기록이 아니고, 크래시 안전성은 fsync + rename으로 만들며, 열린 파일은 rm해도 공간이 안 돌아오고, 파일 락은 권고일 뿐이다 |
| 8. 시그널 | 핸들러에서는 플래그만 세우고, EINTR를 재시도하고, SIGTERM·SIGPIPE·SIGCHLD를 처리하고, 컨테이너에서 셸이 PID 1이 되지 않게 한다 |
| 9. 도구 | 가설은 strace/perf/gdb/eBPF로 검증하며, CPU를 쓰는 곳(perf)과 CPU를 안 쓰고 기다리는 이유(off-CPU)는 다른 도구로 본다 |

## 10.3 서버 코드 출시 전 통합 체크리스트

각 장의 체크리스트에서 가장 자주 사고를 내는 항목만 모았다.

**프로세스/시그널**
- [ ] SIGTERM에 우아한 종료. 컨테이너에서 PID 1 문제(`tini` 또는 핸들러) 해결
- [ ] SIGPIPE 무시. 자식 프로세스 wait 회수
- [ ] 멀티스레드에서 fork 후 exec 외의 일 안 함

**스레드**
- [ ] TSan을 통과. 락 순서 규칙 문서화. 스레드 풀 크기 = 실제 CPU 쿼터 기준
- [ ] 스레드에 이름 부여

**메모리**
- [ ] RSS 추세 모니터링. 컨테이너 메모리 제한과 런타임 힙 설정 일치
- [ ] 멀티스레드 C/C++ 서버라면 `MALLOC_ARENA_MAX` 또는 jemalloc 검토

**네트워크**
- [ ] `SO_REUSEADDR`. 부분 read/write 처리. 메시지 경계 프로토콜
- [ ] 모든 블로킹 네트워크 호출에 타임아웃. 장기 연결에 keepalive
- [ ] 이벤트 루프 안에 블로킹 호출(DNS, 파일, 동기 DB) 없음
- [ ] `RLIMIT_NOFILE`, `somaxconn` 상향

**파일**
- [ ] 잃으면 안 되는 데이터는 fsync. 덮어쓰기는 임시 파일 + rename
- [ ] 에러 경로에서 fd 닫기. 컨테이너에서 stdout 버퍼링 해제

**관측**
- [ ] 코어 덤프 활성화 및 저장 위치 확인. 심볼 포함 빌드
- [ ] 장애 첫 60초 명령 스크립트화

## 10.4 더 공부하고 싶다면

이 폴더에 이미 있는 두 참고서로 더 깊이 들어갈 수 있다.

- **The Linux Programming Interface** (Michael Kerrisk) — 이 책에서 한 문단으로 넘긴 모든 API를 시스템 콜 하나하나 수준에서 정밀하게 다룬다. 1,500페이지지만 레퍼런스로 두고 필요한 장만 찾아 읽으면 된다. 각 장 끝의 "더 깊이"에 해당 장 번호를 적어 두었다. 특히 추천하는 장: 6·24~27(프로세스), 29~33(스레드), 49(mmap), 56~61(소켓), 63(대안 I/O 모델), 20~22(시그널).
- **How Linux Works, 3rd Edition** (Brian Ward) — 부팅, systemd, 네트워크 설정, 디스크와 파일시스템 같은 "시스템 전체가 어떻게 조립되어 있나"를 다룬다. 이 책이 프로세스 관점이라면 그 책은 운영자 관점이다. 두 관점이 만나는 곳이 컨테이너다.

플랫폼 무관하게, 또는 더 깊게:

- *Operating Systems: Three Easy Pieces* (Arpaci-Dusseau, 무료 온라인) — 가상화·동시성·영속성이라는 이 책과 거의 같은 3축으로 학술적 배경을 채워준다.
- *Systems Performance, 2nd Edition* (Brendan Gregg) — 9장의 도구들을 방법론으로 묶어준다. USE 메서드, off-CPU 분석, Flame Graph의 원저자.
- *Understanding the Linux Kernel* (Bovet & Cesati), *Linux Kernel Development* (Robert Love) — 커널 소스 수준으로 내려가고 싶을 때.
- *TCP/IP Illustrated, Volume 1* (Stevens/Fall) — 6장에서 다루지 않은 프로토콜 자체.
- *C++ Concurrency in Action* (Anthony Williams) — 4장에서 "메모리 배리어"라고만 부른 메모리 모델의 정확한 정의.

같은 구조의 Windows 편이 `../window os/book/`에 있다. 두 편을 나란히 읽으면 "OS가 다르면 무엇이 다르고 무엇이 같은가"가 보인다. 같은 것이 훨씬 많다.

## 10.5 마지막으로

이 책의 목표는 "커널 전문가"를 만드는 게 아니라, **평소에 쓰는 API 뒤에서 벌어지는 일에 대한 정확한 멘탈 모델**을 갖추는 것이었다. 다음에 이상한 성능 문제나 동시성 버그, 설명할 수 없는 137 종료를 만나면, "감"이 아니라 이 책에서 다룬 메커니즘(가상 메모리, 스케줄러, futex, 페이지 캐시, epoll, 시그널) 중 어디가 관련 있는지부터 짚어보길 바란다. 그리고 가설이 섰다면 9장의 도구로 확인하라. 리눅스는 그 확인을 허락하는 OS다.
