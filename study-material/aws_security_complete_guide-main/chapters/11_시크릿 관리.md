# 11장. 시크릿 관리

> **이 장에서 다루는 것**
> - 시크릿의 정의 — **시스템이 시스템에게 자기를 증명하는 자격 증명** — 과 원서의 6가지 원칙, 절대 두면 안 되는 7곳
> - **Parameter Store** 🧪 — `SecureString`, 고객 관리형 KMS 키, 계층 경로와 경로 단위 IAM 통제
> - **Secrets Manager** 🧪 — RDS 자격 증명, 자동 순환, 리소스 정책·크로스 계정, 복구 기간
> - 두 서비스의 선택 기준과 결정 트리
> - **무중단 순환 설계** 🔴 — 단일 사용자 vs 다중 사용자 교대, 순환 실패 3중 탐지, 캐시 무효화
> - 안전하게 읽는 패턴 — SDK 캐싱, Lambda 확장, ECS `secrets` 필드, CloudTrail 감사, 서드파티 시크릿 서버 연동
>
> **선행 지식**: 6장(자격 증명의 종류), 7장(IAM 정책 평가), 8장(역할과 임시 자격 증명)
> **난이도**: ★★☆

---

2부는 "누가 무엇을 할 수 있는가"를 다뤘습니다. 6~9장은 **사람**의 신원을, 10장은 **고객**의 신원을 다뤘습니다. 남은 것은 **앱 서버가 데이터베이스에게 자기를 증명하는 방법**이고, 여기에는 사람이 쓰던 도구가 하나도 통하지 않습니다.

> 📖 *Practical Cloud Security* 2판 4장 「Secrets Management」는 이렇게 시작합니다. **"애플리케이션 서버가 데이터베이스 서버와 통신해야 하는 경우를 보자. 여기서는 분명히 다중 인증을 쓸 수 없다 — 애플리케이션 서버는 하드웨어 보안 키도 지문도 없다! 즉 시스템 간 연결의 인증 자격 증명은 매우 신중하게 다루어야 한다. 그것이 당신의 유일한 인증 방어선일 수 있기 때문이다."** 그리고 범위를 정의합니다. **"시스템 간 인증 자격 증명은 비밀번호, API 키, 암호 토큰, 공개/사설 키 쌍일 수 있다. (…) 우리는 이 모든 것을 그냥 시크릿이라 부르고, 시크릿 관리란 그것을 필요로 하는 주체에게 — 그리고 오직 그 주체에게만 — 제공하는 일이다."**

8장에서 절반은 이미 해결했습니다. EC2 인스턴스 프로파일, ECS 태스크 역할, Lambda 실행 역할은 **AWS 서비스를 호출할 때는 시크릿이 아예 필요 없게** 만듭니다(원서도 이것을 가장 성숙한 형태로 꼽습니다 — 11.7).

문제는 나머지 절반입니다. ShopMini 앱 컨테이너는 RDS MySQL에 접속해야 하는데 MySQL은 IAM을 이해하지 못하고(16.2의 IAM 데이터베이스 인증은 예외이자 목표점), 결제 PG API 키와 세션 서명 키도 마찬가지입니다. **AWS로 대체할 수 없는 시크릿이 남고, 이 장은 그것을 어디에 두고 어떻게 꺼내 쓸지를 다룹니다.**

## 11.1 시크릿이란 무엇이고 어디에 두면 안 되는가 ⚠️

### 사고 시나리오

ShopMini 팀의 신규 개발자가 `.env`에 운영 RDS 비밀번호와 결제 PG 라이브 키를 적고 `git add -f`로 강제 추가했습니다. 리뷰 지적을 받고 다음 커밋에서 삭제했고, **PR은 "시크릿 제거" 커밋과 함께 병합되었습니다.**

11주 뒤, 결제 PG로부터 "귀사 라이브 키로 새벽 3시에 해외 IP에서 환불 API가 호출되었다"는 연락을 받습니다. 저장소는 3주 전 퍼블릭으로 전환되었고, 크롤러가 **Git 히스토리**에서 키를 찾아낸 것이었습니다.

### 원인

**첫째, Git은 파일을 지워도 히스토리를 지우지 않습니다.** "시크릿 제거" 커밋은 최신 트리에서만 파일을 제거하고, 이전 커밋 객체는 `git log -p`로 누구나 볼 수 있습니다. 퍼블릭 전환은 11주 전 커밋도 함께 공개합니다.

**둘째, 애초에 소스 저장소가 시크릿을 담을 곳이 아니었습니다.** 원서는 그 이유를 두 개로 정리합니다.

> 📖 *Practical Cloud Security* 2판 4장은 **"AWS API 키 같은 시크릿을 소스 코드에 실수로 저장한 결과로 발생한 침해가 아주 많았다"** 고 전제하고, 이유를 두 가지로 못 박습니다. **"① 소스 코드 저장소는 애초에 정보를 비밀로 유지하도록 설계된 것이 아니다. 그것의 주된 기능은 소스 코드의 무결성을 지키는 것이다. (…) ② 소스 코드 저장소가 완벽하게 안전하다 해도, 소스 코드에 접근할 수 있는 모든 사람이 운영 환경에서 사용되는 시크릿까지 볼 권한을 가져야 할 가능성은 매우 낮다."**
>
> 각주는 문제의 규모를 보여줍니다. **"퍼블릭 GitHub 저장소에서 발견되는 시크릿에는 실제로 통용되는 이름이 있다: 'GitHub dorks.' 이것이 워낙 광범위한 문제였기 때문에 GitHub은 이제 시크릿이 포함된 코드 푸시를 차단하는 방법을 제공한다."** 1판 4장은 같은 대목에서 사례를 들었습니다. **"2016년 Uber는 일부 시크릿(이 경우 AWS 자격 증명)이 소스 코드에 있었기 때문에 5,700만 명의 드라이버와 고객이 연루된 데이터 침해를 겪었다."**

두 번째 이유가 더 중요합니다. 프라이빗 저장소에서도 문제는 남습니다. **ShopMini 저장소 읽기 권한자는 20명이지만, 운영 DB 비밀번호를 알아야 하는 사람은 0명입니다.** 두 권한은 다른 축인데, 시크릿을 코드에 넣으면 강제로 하나가 됩니다.

> 📖 *Practical Cloud Security* 1판·2판 4장: **"대부분의 경우 애플리케이션의 배포는 함께 모이는 세 조각으로 구성된다 — 애플리케이션 코드, 이 특정 배포를 위한 구성, 이 특정 배포에 필요한 시크릿. 이 세 가지를 함께 저장하는 것은 정말로 나쁜 생각이다. 구성과 시크릿을 함께 두는 것도 종종 나쁜 생각인데, 구성 데이터를 담도록 설계된 시스템은 그 데이터를 비밀로 유지하도록 적절히 설계되지 않았을 수 있기 때문이다."**

마지막 문장에 주의하십시오. **코드에서 시크릿을 빼내 "설정 저장소"에 넣는 것으로는 절반만 해결됩니다.** 11.2에서 `String`과 `SecureString`을 구분하는 이유입니다.

### 시크릿을 두면 안 되는 7곳

| # | 두면 안 되는 곳 | 왜 위험한가 | 노출 경로 |
|---|---|---|---|
| 1 | **소스 코드 / Git 히스토리** | 삭제 커밋이 히스토리를 지우지 않는다. 코드 접근자 ≠ 시크릿 접근자 | 저장소 퍼블릭 전환, 포크, 로컬 클론 유출, 크롤러 |
| 2 | **환경 변수(플랫폼 콘솔에 평문 입력)** | 프로세스 목록·크래시 덤프·에러 리포트·`/proc/<pid>/environ`에 함께 실린다 | APM/에러 추적 SaaS로 전송, 코어 덤프, 컨테이너 `inspect` |
| 3 | **EC2 User Data** | IMDS `latest/user-data`에서 **평문**으로 조회된다. SSRF 하나면 끝 | SSRF, 인스턴스 로그인한 누구나, `DescribeInstanceAttribute` 권한자 |
| 4 | **AMI / 컨테이너 이미지 레이어** | 레이어는 불변이다. 다음 레이어에서 `rm` 해도 앞 레이어에 남는다 | AMI 공유·스냅샷 공개, 레지스트리 pull, `docker history` |
| 5 | **CI/CD 빌드 로그** | `set -x`, `curl -v`, 실패 시 덤프가 값을 그대로 출력한다 | 빌드 로그 보관·아티팩트, 로그 전달 SaaS |
| 6 | **티켓 / 위키 / 채팅** | 검색 인덱스에 영구 보존, 접근 통제가 넓고 순환이 불가능하다 | 퇴사자 계정, 외부 협력사 초대된 채널, 검색 |
| 7 | **일반 설정 저장소(암호화 없는 파라미터·ConfigMap)** | 원서 지적대로 **기밀 유지용으로 설계되지 않았다** | 넓은 읽기 권한, 백업 사본, IaC 상태 파일 |

3번은 22.4와, 4번은 24.2와 이어집니다. 하나만 강조합니다. **1~7 전부의 공통점은 "순환할 수 없다"는 것입니다.** 이미지 레이어의 비밀번호를 바꾸려면 이미지를 다시 만들어 전 노드에 재배포해야 하고, 위키의 키는 누가 언제 복사했는지 알 수 없습니다.

### 올바른 구성: 원서의 6가지 원칙 → AWS 구현

> 📖 *Practical Cloud Security* 1판·2판 4장은 **"시크릿은 조심스럽게 다루어야 하는 위험한 것들이다"** 라며 6개 원칙을 제시합니다.

| 원서의 원칙 (요약 인용) | AWS 구현 |
|---|---|
| **"시크릿은 정기적으로, 그리고 유출되었다고 생각할 이유가 있을 때마다 쉽게 바꿀 수 있어야 한다. 시크릿을 바꾸려면 애플리케이션을 내리고 여러 곳에서 수동으로 바꿔야 한다면 그것은 문제다."** | Secrets Manager 자동 순환 + 애플리케이션의 **참조만 배포**(값은 배포하지 않음) → 11.5 |
| **"시크릿은 항상 저장 시와 전송 시 암호화되어야 하며, 적절한 인증과 인가를 거친 뒤에만 시스템에 배포되어야 한다."** | KMS 고객 관리형 키로 봉투 암호화 + TLS API 엔드포인트 + IAM/키 정책 이중 평가 → 11.2, 11.3 |
| **"가능하다면 어떤 사람도 시크릿을 알아서는 안 된다 — 코드를 쓰는 개발자도, 실행 중인 시스템을 볼 수 있는 운영자도, 아무도."** | Secrets Manager가 비밀번호를 **생성**하고(`get-random-password`), 사람은 `GetSecretValue` 권한을 갖지 않는다 → 11.6 |
| **"시크릿을 저장하고 나눠주는 시스템은 잘 보호되어야 한다. 시크릿을 전부 금고에 넣고 그 금고 열쇠를 수십 명에게 나눠준다면 그것은 문제다."** | KMS 키 정책을 별도 통제선으로 유지(13.4), `secretsmanager:GetSecretValue`는 워크로드 역할에만 |
| **"시크릿은 시스템이 동작하는 데 지장이 없는 한 공격자에게 최대한 쓸모없어야 한다. (…) 모든 시스템에 루트 접근을 주는 것 같은 '왕국의 열쇠'를 두지 말고, 특정 데이터베이스에 읽기 전용 접근만 허용하는 시크릿처럼 제한된 시크릿을 두라."** | DB 사용자를 앱별·읽기/쓰기별로 분리하고 시크릿도 그만큼 쪼갠다 → 11.3 |
| **"시크릿에 대한 모든 접근과 변경은 로깅되어야 한다."** | CloudTrail 관리 이벤트로 `GetSecretValue`/`GetParameter` 기록 + 이상 조회 알람 → 11.6 |

원서는 이 원칙들이 흔히 무시된다고 덧붙입니다.

> 📖 *Practical Cloud Security* 2판 4장: **"인증과 인가를 훌륭하게 해내는 조직조차 시크릿 관리는 종종 간과한다. 예를 들어, 데이터베이스에 접근할 수 있는 개인 ID를 가진 사람이 누구인지는 아주 잘 관리하고 있을지 모른다 — 그런데 애플리케이션 서버가 데이터베이스와 통신할 때 쓰는 비밀번호를 아는 사람은 몇 명인가? 그것은 정기적으로 바뀌는가, 그리고 누군가 팀을 떠나면 즉시 바뀌는가?"**

**이 두 질문에 답할 수 없다면 9장의 아이덴티티 라이프사이클에 구멍이 있는 것입니다.** 퇴사자의 IAM 사용자를 지워도 그가 아는 DB 비밀번호는 그대로 살아 있습니다.

## 11.2 Systems Manager Parameter Store 🧪

Parameter Store는 원래 **구성 데이터** 저장소였고, KMS 암호화 타입(`SecureString`)이 붙어 시크릿에도 쓰입니다.

> 📖 *AWS Security Cookbook* 6장 「Storing sensitive data with the Systems Manager Parameter Store」: **"우리는 Systems Manager Parameter Store를 이용해 데이터를 암호화하거나 암호화하지 않고 저장할 수 있고, 그 뒤 어느 곳에도 데이터를 하드코딩하지 않은 채 여러 서비스에서 그것을 참조할 수 있다."**
>
> 원서 실습은 이름 `MySecureParameter`, 티어 `Standard`, 타입 `SecureString`, **KMS Key ID `alias/aws/ssm`** 으로 파라미터를 만들고, EC2에 SSM용 역할을 붙인 뒤 `aws ssm get-parameters --names MySecureParameter --with-decryption` 으로 값을 읽습니다. 옵션 기본값도 명시합니다. **"아무것도 지정하지 않으면 기본값은 `--no-with-decryption`이고 값을 복호화하지 않는다."** 그리고 **"타입을 `SecureString` 대신 `String`으로 설정하면 암호화 없이 파라미터를 만들 수도 있다"** 고 덧붙입니다.

이를 운영 기준으로 바꾸려면 세 곳을 고쳐야 합니다. **① 이름을 계층 경로로, ② KMS 키를 고객 관리형으로, ③ 접근 권한을 경로 단위로.**

### ① 계층 경로 설계

파라미터 이름은 `/`로 시작하는 경로가 될 수 있고, 이 경로가 곧 **IAM 권한 경계**입니다. 이름 규칙이 곧 보안 설계입니다.

```
/shopmini/<환경>/<컴포넌트>/<항목>

/shopmini/prod/db/host              String        (구성 — 비밀 아님)
/shopmini/prod/db/port              String        (구성)
/shopmini/prod/db/username          String        (구성)
/shopmini/prod/app/feature-flags    StringList    (구성)
/shopmini/prod/pg/api-key           SecureString  (시크릿)
/shopmini/prod/app/session-key      SecureString  (시크릿)
/shopmini/dev/pg/api-key            SecureString  (시크릿 — 별도 계정 555555555555)
```

**환경을 두 번째 세그먼트에 두는 것이 핵심입니다.** `/shopmini/prod/*`와 `/shopmini/dev/*`를 IAM에서 완전히 분리할 수 있습니다. `/db/prod/password`처럼 환경을 뒤에 두면 와일드카드로 분리할 수 없습니다.

구성과 시크릿이 같은 트리에 있어도 됩니다. **타입이 다르기 때문입니다.** 11.1의 "구성과 시크릿을 함께 두는 것도 나쁜 생각"이라는 경고는 *암호화 없는* 저장소를 가리킵니다. `SecureString`은 KMS 봉투 암호화를 거치고 별도의 `kms:Decrypt` 권한을 요구하므로 통제선이 다릅니다.

### ② 고객 관리형 KMS 키로 만들기

```bash
# 고객 관리형 키(CANON: alias/shopmini/app)로 SecureString 생성
aws ssm put-parameter \
  --name "/shopmini/prod/pg/api-key" \
  --description "ShopMini prod payment gateway live API key" \
  --value "REPLACE_WITH_REAL_VALUE" \
  --type SecureString \
  --key-id "alias/shopmini/app" \
  --tier Standard \
  --tags "Key=Project,Value=awssec-lab" "Key=Chapter,Value=ch11" "Key=AutoDelete,Value=true" \
  --region ap-northeast-2 \
  --profile awssec-lab

# 값 갱신 (--overwrite 필요. 태그는 이때 함께 지정할 수 없음)
aws ssm put-parameter \
  --name "/shopmini/prod/pg/api-key" \
  --value "NEW_VALUE" \
  --type SecureString \
  --key-id "alias/shopmini/app" \
  --overwrite \
  --region ap-northeast-2 --profile awssec-lab

# 단건 조회 (원서의 get-parameters 대신 get-parameter 사용)
aws ssm get-parameter \
  --name "/shopmini/prod/pg/api-key" \
  --with-decryption \
  --query "Parameter.Value" --output text \
  --region ap-northeast-2 --profile awssec-lab

# 경로 단위 일괄 조회 — 앱 부팅 시 1회 호출로 트리 전체를 받는다
# 주의: get-parameters-by-path 는 개별 파라미터가 아니라 --path 프리픽스에 대한
#       ssm:GetParametersByPath 권한을 요구한다 (아래 IAM 정책의 Resource 와일드카드가 그것)
aws ssm get-parameters-by-path \
  --path "/shopmini/prod/" \
  --recursive \
  --with-decryption \
  --region ap-northeast-2 --profile awssec-lab
```

**왜 고객 관리형 키인가.** 원서의 AWS 관리형 키는 학습에는 충분하지만 운영에서는 세 가지를 잃습니다.

| 항목 | `alias/aws/ssm` (AWS 관리형) | `alias/shopmini/app` (고객 관리형) |
|---|---|---|
| 키 정책 편집 | 불가 — 계정 내 SSM 권한자면 사실상 복호화 가능 | 가능 — **키 정책이 독립적인 2차 관문**(13.4) |
| 크로스 계정 사용 | 불가 | 가능 |
| 키 순환·삭제 통제 | AWS가 관리 | 조직 정책대로 |

두 번째 열의 첫 줄이 결정적입니다. 심층 방어(1.2) 관점에서 **IAM 정책이 잘못 넓어지는 사고를 KMS 키 정책이 한 번 더 막는 구조**에는 고객 관리형 키가 필요합니다.

```json
{
  "Sid": "AllowSSMSecureStringDecryptForAppRoleOnly",
  "Effect": "Allow",
  "Principal": {
    "AWS": "arn:aws:iam::111122223333:role/shopmini-app-task-role"
  },
  "Action": [
    "kms:Decrypt",
    "kms:DescribeKey"
  ],
  "Resource": "*",
  "Condition": {
    "StringEquals": {
      "kms:ViaService": "ssm.ap-northeast-2.amazonaws.com"
    }
  }
}
```

`kms:ViaService`는 **SSM 경유 호출만 허용**해, 앱 역할이 KMS를 직접 호출해 임의 암호문을 복호화하는 경로를 막습니다(13.8).

### ③ 경로 단위 IAM 정책

파라미터 `/shopmini/prod/pg/api-key`의 ARN은 `arn:aws:ssm:ap-northeast-2:111122223333:parameter/shopmini/prod/pg/api-key`입니다. 이름의 선행 `/`가 ARN에서 중복되지 않는 점에 주의하십시오.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadProdShopMiniParametersOnly",
      "Effect": "Allow",
      "Action": [
        "ssm:GetParameter",
        "ssm:GetParameters",
        "ssm:GetParametersByPath"
      ],
      "Resource": "arn:aws:ssm:ap-northeast-2:111122223333:parameter/shopmini/prod/*"
    },
    {
      "Sid": "DecryptOnlyViaSSM",
      "Effect": "Allow",
      "Action": "kms:Decrypt",
      "Resource": "arn:aws:kms:ap-northeast-2:111122223333:key/EXAMPLE-KEY-ID",
      "Condition": {
        "StringEquals": {
          "kms:ViaService": "ssm.ap-northeast-2.amazonaws.com"
        }
      }
    },
    {
      "Sid": "DenyWriteToProdParameters",
      "Effect": "Deny",
      "Action": [
        "ssm:PutParameter",
        "ssm:DeleteParameter",
        "ssm:DeleteParameters"
      ],
      "Resource": "arn:aws:ssm:ap-northeast-2:111122223333:parameter/shopmini/prod/*"
    }
  ]
}
```

첫 문장이 **읽기 범위를 경로로 제한**, 둘째가 **복호화를 SSM 경유로 제한**, 셋째가 **앱 역할의 쓰기를 명시적으로 거부**합니다. 셋째가 없으면 앱 침해가 곧 시크릿 변조로 이어집니다.

> ⚠️ `ssm:DescribeParameters`는 리소스 수준 권한을 지원하지 않아 계정 전체 파라미터 **이름 목록**이 노출됩니다. 이름 자체가 정보(`/shopmini/prod/partner-x/api-key`)이므로 앱 역할에 주지 마십시오.

### 티어 선택

| 항목 | Standard | Advanced |
|---|---|---|
| 값 크기 | 4KB | 8KB |
| 계정·리전당 개수 | 10,000 | 100,000 |
| 파라미터 정책(만료·미변경 알림) | 없음 | 있음 |
| 비용 | 저장 무료 | 파라미터당 월 과금 |

Advanced 티어의 **파라미터 정책**이 쓸모가 있습니다. `Expiration`으로 만료일을 걸고, `NoChangeNotification`으로 "N일 동안 값이 바뀌지 않았다"는 EventBridge 이벤트를 받아 **순환 누락을 탐지**할 수 있습니다. Parameter Store에 자동 순환이 없으므로 순환을 강제하는 유일한 내장 수단입니다.

## 11.3 AWS Secrets Manager 🧪

Secrets Manager는 처음부터 시크릿 전용입니다. 차이는 한 줄로 요약됩니다. **Parameter Store는 값을 보관하고, Secrets Manager는 값의 수명주기를 관리합니다.**

> 📖 *AWS Security Cookbook* 10장 「Using AWS Secrets Manager to manage RDS credentials」: **"이 레시피에서 우리는 AWS Secrets Manager로 RDS 자격 증명을 관리하는 법을 배운다. 이것은 RDS 자격 증명을 수동으로 관리하고 순환시키는 것보다 더 안전한 대안이다."** 원서 실습은 콘솔에서 시크릿 유형 **Credentials for RDS database**를 고르고 **Enable automatic rotation → 30일 → Create a new Lambda function to perform rotation**을 설정합니다.
>
> 저장 후 나타나는 경고를 원서는 특히 강조합니다. **"이 시크릿을 저장하면 첫 순환이 즉시 일어난다는 경고를 보았다. 따라서 우리 애플리케이션 중 하나라도 여전히 하드코딩된 자격 증명을 쓰고 있고 최신 자격 증명을 가져오는 API를 사용하도록 업데이트되지 않았다면, 그 애플리케이션들은 실패할 것이다."**
>
> 선택지도 나열합니다. 다른 시크릿 유형은 **"Credentials for Redshift cluster, Credentials for DocumentDB database, Credentials for other database, Other type of secrets (예: API key)"** 이고, 순환 주기는 **"30일, 60일, 90일 또는 최대 365일까지 임의 기간"** 입니다. 삭제는 **"시크릿이 삭제되기 전 7일에서 30일 사이의 대기 기간을 반드시 지정해야 한다"** 고 명시합니다.

"첫 순환이 즉시 일어난다"는 경고가 이 장 전체의 축입니다. **순환은 저장소 기능이 아니라 애플리케이션 계약입니다.** 앱이 값을 캐시한 채 재조회하지 않으면 순환을 켜는 행위 자체가 장애입니다. 11.5와 11.6이 이 계약을 다룹니다.

### CLI로 만들기

```bash
# 1) 사람이 비밀번호를 보지 않고 생성하게 한다 (원서 원칙 3)
NEWPW=$(aws secretsmanager get-random-password \
  --password-length 32 \
  --exclude-characters '"@/\' \
  --require-each-included-type \
  --query RandomPassword --output text \
  --region ap-northeast-2 --profile awssec-lab)

# 2) RDS 자격 증명 시크릿 생성 (CANON: 이름 rds/shopmini)
aws secretsmanager create-secret \
  --name "rds/shopmini" \
  --description "ShopMini prod RDS MySQL app credentials" \
  --kms-key-id "alias/shopmini/app" \
  --secret-string "{\"engine\":\"mysql\",\"host\":\"shopmini-prod.abc123.ap-northeast-2.rds.amazonaws.com\",\"port\":3306,\"username\":\"shopmini_app\",\"password\":\"${NEWPW}\",\"dbname\":\"shopmini\"}" \
  --tags "Key=Project,Value=awssec-lab" "Key=Chapter,Value=ch11" "Key=AutoDelete,Value=true" \
  --region ap-northeast-2 --profile awssec-lab
unset NEWPW

# 3) 자동 순환 설정 — 30일 주기, 순환 창은 UTC 18시(KST 03시) 시작 2시간
aws secretsmanager rotate-secret \
  --secret-id "rds/shopmini" \
  --rotation-lambda-arn "arn:aws:lambda:ap-northeast-2:111122223333:function:SecretsManagerRDSMySQLRotationSingleUser" \
  --rotation-rules '{"ScheduleExpression":"rate(30 days)","Duration":"2h"}' \
  --region ap-northeast-2 --profile awssec-lab

# 4) 읽기
aws secretsmanager get-secret-value \
  --secret-id "rds/shopmini" \
  --query SecretString --output text \
  --region ap-northeast-2 --profile awssec-lab
```

RDS 유형 시크릿은 `engine`, `host`, `port`, `username`, `password`, `dbname` 키를 쓰고, AWS 순환 Lambda 템플릿이 이 스키마를 기대합니다. **`host`·`port`를 함께 담으면** 순환 시 엔드포인트까지 갱신되고 앱은 조회를 한 번만 하면 됩니다.

> 💡 **원서 이후 변경** — 원서 집필 시점에는 순환에 항상 사용자 Lambda가 필요했습니다. 이후 RDS·Redshift·DocumentDB 등에 대해 **관리형 순환(managed rotation)** 이 추가되어 Lambda 없이 순환할 수 있게 되었고, RDS 쪽에도 `modify-db-instance --manage-master-user-password`로 **마스터 자격 증명을 RDS가 Secrets Manager에 직접 만들어 관리**하게 하는 경로가 생겼습니다. DB 마스터 사용자에는 이 경로를, 애플리케이션 DB 사용자에는 이 절의 방식을 쓰는 조합이 실무 기본값입니다.

### 리소스 정책과 크로스 계정

Parameter Store와 갈라지는 차이가 **리소스 정책**입니다. 보안 도구 계정(`444455556666`)의 스캐너가 운영 시크릿 메타데이터를 읽어야 할 때 필요합니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowSecurityAccountReadOnlyMetadata",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::444455556666:role/security-secret-auditor"
      },
      "Action": [
        "secretsmanager:DescribeSecret",
        "secretsmanager:ListSecretVersionIds"
      ],
      "Resource": "*"
    },
    {
      "Sid": "DenyValueReadFromOutsideOrg",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "secretsmanager:GetSecretValue",
      "Resource": "*",
      "Condition": {
        "StringNotEquals": {
          "aws:PrincipalOrgID": "o-exampleorgid"
        }
      }
    }
  ]
}
```

```bash
# --block-public-policy 는 "광범위한 접근을 허용(Allow)하는" 정책만 거부한다.
# 위 정책의 두 번째 문장처럼 Principal "*" 를 쓰는 Deny 는 차단 대상이 아니다.
aws secretsmanager put-resource-policy \
  --secret-id "rds/shopmini" \
  --resource-policy file://secret-policy.json \
  --block-public-policy \
  --region ap-northeast-2 --profile awssec-lab

# 적용된 정책 확인
aws secretsmanager get-resource-policy --secret-id "rds/shopmini" \
  --region ap-northeast-2 --profile awssec-lab
```

🔴 **`--block-public-policy`를 항상 붙이십시오.** 없으면 `"Principal": "*"` Allow 정책이 통과됩니다. 시크릿 저장소를 퍼블릭으로 만드는 실수는 S3 버킷 공개와 같은 급입니다.

크로스 계정 접근에는 **3중 확인**이 필요합니다(13.10과 같은 구조).

| # | 확인 대상 | 필요 설정 |
|---|---|---|
| 1 | 시크릿 리소스 정책 | 상대 계정 프린시펄에 `GetSecretValue` Allow |
| 2 | 상대 계정 IAM 정책 | 해당 역할에 `secretsmanager:GetSecretValue` + 시크릿 ARN |
| 3 | **KMS 키 정책** | 상대 계정 프린시펄에 `kms:Decrypt` Allow |

3번 누락이 가장 흔한 실패입니다. 그리고 **AWS 관리형 키(`aws/secretsmanager`)로 암호화된 시크릿은 크로스 계정 공유가 불가능합니다** — 키 정책을 편집할 수 없기 때문입니다. 크로스 계정 계획이 있다면 생성 시점에 고객 관리형 키를 지정하십시오.

### 복구 기간과 삭제

```bash
# 기본 30일, 최소 7일 대기 삭제
aws secretsmanager delete-secret \
  --secret-id "rds/shopmini" \
  --recovery-window-in-days 30 \
  --region ap-northeast-2 --profile awssec-lab

# 대기 중 복구
aws secretsmanager restore-secret --secret-id "rds/shopmini" \
  --region ap-northeast-2 --profile awssec-lab
```

복구 기간은 **양날의 칼**입니다. 실수 삭제를 되돌릴 수 있게 하지만 대기 중에도 과금은 계속되고 순환은 멈춥니다. `--force-delete-without-recovery`는 즉시 영구 삭제하므로 — 공격자가 쓰면 복구 경로가 없습니다 — SCP나 권한 경계에서 막습니다.

```json
{
  "Sid": "DenyForceDeleteOfSecrets",
  "Effect": "Deny",
  "Action": "secretsmanager:DeleteSecret",
  "Resource": "*",
  "Condition": {
    "BoolIfExists": {
      "secretsmanager:ForceDeleteWithoutRecovery": "true"
    }
  }
}
```

`BoolIfExists`를 쓰는 이유는 4.2와 같습니다. 플래그를 지정하지 않은 요청에서 조건이 매칭되지 않아 Deny가 통과되는 것을 막습니다.

### 리전 복제

```bash
aws secretsmanager replicate-secret-to-regions \
  --secret-id "rds/shopmini" \
  --add-replica-regions "Region=ap-northeast-1,KmsKeyId=alias/shopmini/app" \
  --region ap-northeast-2 --profile awssec-lab
```

복제본은 **읽기 전용**이고 주 리전의 순환이 자동 전파됩니다. DR 리전 앱이 리전 간 호출 없이 시크릿을 읽게 하는 표준입니다. 단 KMS 키는 리전 종속이므로 대상 리전에 **동일 별칭의 키가 있어야** 합니다(13.11).

## 11.4 Parameter Store vs Secrets Manager 선택 기준

원서도 이 비교를 명시적으로 합니다.

> 📖 *AWS Security Cookbook* 10장은 **"AWS Secrets Manager는 AWS Systems Manager Parameter Store와 비슷해 보일 수 있다"** 며 다음과 같이 정리합니다.
>
> - **"Secrets Manager는 주로 데이터베이스 자격 증명, API 키, SSH 키를 저장하는 데 쓰인다. Parameter Store는 주로 라이선스 코드, 구성 데이터, 사용자 정의 파라미터, 데이터베이스 문자열을 저장하는 데 쓰이고, 비밀번호에도 덜 흔하게 쓰인다."**
> - **"Secrets Manager는 RDS 데이터베이스와의 내장 통합이 있다."**
> - **"Secrets Manager는 RDS에 대한 시크릿의 내장 순환을 지원한다. 커스텀 Lambda를 이용해 비(非)RDS 데이터베이스의 순환도 지원한다."**
> - **"AWS Secrets Manager는 시크릿당 월 단위로, 그리고 API 호출당 과금된다. AWS Systems Manager Parameter Store는 standard 파라미터에 대해서는 과금하지 않지만, advanced 파라미터에 대해서는 저장된 advanced 파라미터 수와 API 상호작용당 과금한다."**

이 네 항목을 실무 결정 축으로 확장하면 다음과 같습니다.

| 축 | Parameter Store | Secrets Manager |
|---|---|---|
| **비용** | Standard 저장 무료, API 호출도 기본 무료 / Advanced는 파라미터당 월 과금 | **시크릿당 월 과금 + API 호출당 과금** |
| **자동 순환** | **없음** (직접 EventBridge+Lambda 구현, Advanced 정책으로 미변경 탐지만 가능) | **내장** — RDS/Redshift/DocumentDB 관리형 순환, 그 외 커스텀 Lambda |
| **비밀번호 생성** | 없음 | `get-random-password` 내장 |
| **값 크기** | Standard 4KB / Advanced 8KB | 64KB |
| **리소스 정책** | **없음** — 크로스 계정은 역할 위임(AssumeRole)으로 우회 | 있음 (`put-resource-policy` + `--block-public-policy`) |
| **리전 복제** | 없음 (직접 복제 파이프라인 구현) | **내장** (`replicate-secret-to-regions`) |
| **버전 관리** | 버전 번호 + 레이블(`LabelParameterVersion`), 이력 조회 가능 | 버전 ID + **스테이징 라벨**(`AWSCURRENT`/`AWSPENDING`/`AWSPREVIOUS`) — 순환 프로토콜의 기반 |
| **계층 조회** | **`GetParametersByPath --recursive`** — 트리 일괄 조회가 강점 | `BatchGetSecretValue`(필터 기반), 경로 개념 없음 |
| **감사 로깅** | CloudTrail 관리 이벤트(`GetParameter` 등, 값은 기록되지 않음) | CloudTrail 관리 이벤트(`GetSecretValue` 등) + 순환 이벤트 |
| **KMS** | `SecureString`에만 적용, 타입 실수 시 평문 저장 위험 | **항상 암호화** — 평문 저장 옵션이 없음 |

마지막 행이 중요합니다. **Parameter Store에서 `--type String`으로 잘못 만들면 시크릿이 평문 저장되고 아무 오류도 나지 않습니다.** Secrets Manager에는 이 실수의 가능성 자체가 없습니다 — 비용 차이를 정당화하는 첫 번째 이유입니다.

> 💡 **원서 이후 변경** — Parameter Store에도 advanced 티어 파라미터를 AWS Resource Access Manager로 다른 계정에 공유하는 경로가 생겼습니다. 다만 Secrets Manager의 리소스 정책만큼 조건·액션 단위로 세밀하지 않으므로, 크로스 계정 요구가 확정적이라면 Secrets Manager가 단순합니다.

### 결정 트리

```
① 값이 유출되면 즉시 바꿔야 하는가?
   NO  → Parameter Store (String/StringList).  구성 데이터다. 여기서 끝.
   YES → ②

② 자동 순환이 필요한가? (DB 자격 증명 / 규정상 90일 순환 의무 등)
   YES → Secrets Manager.  여기서 끝.
   NO  → ③

③ 크로스 계정 또는 크로스 리전에서 이 값을 읽어야 하는가?
   YES → Secrets Manager (리소스 정책 + 리전 복제).  여기서 끝.
   NO  → ④

④ 값이 4KB(Standard) 또는 8KB(Advanced)를 넘는가? (인증서 체인·서비스 계정 JSON 등)
   YES → Secrets Manager (64KB).  여기서 끝.
   NO  → ⑤

⑤ 이 값을 읽는 주체가 초당 수십~수백 회 호출하며, 캐싱을 넣을 수 없는가?
   YES → Parameter Store SecureString (호출 과금 없음).  단 순환 미지원을 문서화.
   NO  → 시크릿 수가 적다면 Secrets Manager로 통일하는 것이 운영상 단순하다.
```

**ShopMini의 배치**:

| 값 | 저장소 | 이유 |
|---|---|---|
| `rds/shopmini` (DB 자격 증명) | **Secrets Manager** | 자동 순환 필수, RDS 내장 통합 |
| PG 라이브 API 키 | **Secrets Manager** | 유출 시 즉시 교체, 순환 절차 필요(수동 트리거) |
| 세션 서명 키 | **Secrets Manager** | 순환 시 이전 키 병행 검증 필요 → `AWSPREVIOUS` 활용 |
| DB 호스트·포트·DB명 | Parameter Store `String` | 비밀이 아니다. 순환 대상도 아니다 |
| 기능 플래그·튜닝 값 | Parameter Store `StringList` | 구성 데이터, 경로 일괄 조회가 편하다 |
| 서드파티 웹훅 서명 시크릿 | Parameter Store `SecureString` | 상대가 순환을 지원하지 않아 순환 불가 — 대신 Advanced 정책으로 미변경 알림 |

**"모든 시크릿을 한 곳에"가 목표가 아닙니다.** 순환 가능성이 저장소를, 비밀 여부가 타입을 정합니다.

## 11.5 시크릿 순환(Rotation) 설계 🔴

순환은 시크릿 관리에서 유일하게 **애플리케이션을 고장낼 수 있는** 부분이라, 이 절은 명령형으로 씁니다.

### 🔴 반드시 이렇게 구성하라

**1. 애플리케이션이 순환을 견딜 수 있음을 먼저 증명하고, 그 다음에 순환을 켜라.**

원서 경고대로 "첫 순환은 저장 즉시" 일어납니다. 순서를 반대로 하면 순환 활성화가 곧 운영 장애입니다.

- ① 앱이 시크릿을 **참조(ARN/이름)** 로만 배포받고 값은 런타임에 조회하는가
- ② 개발 계정(`555555555555`)에서 `rotate-secret --rotate-immediately`로 무중단이 확인되었는가
- ③ 인증 실패 시 **캐시를 무효화하고 1회 재시도**하는 코드가 있는가 (11.6)

**2. 순환 주기를 시크릿 유형별로 정하고 문서화하라.** 전 시크릿 일괄 30일에는 근거가 없습니다.

| 시크릿 유형 | 권장 주기 | 근거 |
|---|---|---|
| 애플리케이션 DB 자격 증명 | 30일 | 순환 자동화가 완전. 짧게 해도 비용이 낮다 |
| DB 마스터 자격 증명 | 90일 + 인원 변동 시 즉시 | 사용 빈도 낮음, 순환 실패 영향이 크다 |
| 서드파티 API 키 | 90일 또는 제공자 최대 허용 | 상대 시스템 제약을 따른다 |
| 세션·토큰 서명 키 | 90일, 이전 키 검증 유예 7일 | 유예 없이 바꾸면 전 사용자 로그아웃 |
| 침해 의심 시 | **즉시** | 주기와 무관. 원서 원칙 1 |

**3. 순환 방식을 단일 사용자와 다중 사용자 교대 중에서 의식적으로 선택하라.** 기본값을 그대로 받아들이는 것이 가장 흔한 실수입니다.

### 순환 Lambda의 4단계

순환 프로토콜은 스테이징 라벨과 4개 단계로 정의됩니다. 이 구조를 알면 두 방식의 차이가 분명해집니다.

| 단계 | 하는 일 | 라벨 상태 |
|---|---|---|
| `createSecret` | 새 비밀번호를 생성해 **새 버전**으로 저장 | 새 버전에 `AWSPENDING` 부여 |
| `setSecret` | 데이터베이스에 새 자격 증명을 **실제로 반영** | 변화 없음 |
| `testSecret` | `AWSPENDING` 값으로 DB에 **접속 테스트** | 변화 없음 |
| `finishSecret` | 라벨 이동 — 새 버전을 현재로 승격 | `AWSPENDING` → `AWSCURRENT`, 기존 → `AWSPREVIOUS` |

버전 스테이지를 지정하지 않은 `GetSecretValue`는 항상 `AWSCURRENT`를 받습니다. **즉 `finishSecret` 실행 순간이 앱에 보이는 값이 바뀌는 유일한 지점입니다.**

### 단일 사용자 방식 (Single user)

DB 사용자 하나(`shopmini_app`)의 비밀번호만 바꿉니다. `SecretsManagerRDSMySQLRotationSingleUser` 템플릿이 이 방식입니다.

```
시각 →
[setSecret]  DB의 shopmini_app 비밀번호가 새 값으로 변경됨
             ↓
             ★ 이 구간에서 캐시에 옛 비밀번호를 들고 있는 앱은 인증 실패
             ↓
[finishSecret] AWSCURRENT가 새 값으로 이동 → 앱이 재조회하면 정상
```

★ 구간이 **취약 창(vulnerability window)** 입니다. 보통 수 초지만, 앱이 1시간 캐시한다면 최악의 경우 **1시간 동안 인증 실패**입니다. 그래서 단일 사용자 방식은 **"인증 실패 시 캐시 무효화 + 재시도" 코드가 전제**입니다.

| 항목 | 평가 |
|---|---|
| 설정 복잡도 | 낮음 — 시크릿 1개, DB 사용자 1개 |
| 무중단 | **조건부** — 앱의 재시도 로직에 의존 |
| DB 권한 요구 | 자기 비밀번호 변경 권한 |
| 적합 | 재시도 로직이 확실한 단일 앱, 개발/스테이징 |

### 다중 사용자 교대 방식 (Alternating users) 🔴

DB 사용자 **두 개**(`shopmini_app`, `shopmini_app_clone`)를 두고 순환할 때마다 번갈아 씁니다. `SecretsManagerRDSMySQLRotationMultiUser` 템플릿이 이 방식이며, **DB 마스터 자격 증명을 담은 별도 시크릿(superuser secret)** 을 참조해 사용자를 관리합니다.

```
순환 N회차 상태:  AWSCURRENT = shopmini_app        (사용 중)
                  AWSPREVIOUS = shopmini_app_clone  (유효하지만 미사용)

[createSecret] 다음 차례인 shopmini_app_clone 용 새 비밀번호 생성 → AWSPENDING
[setSecret]    DB에서 shopmini_app_clone 의 비밀번호만 변경
               ↓
               ★ 이 구간에도 앱은 여전히 shopmini_app 으로 정상 접속 중 — 영향 0
               ↓
[testSecret]   shopmini_app_clone 으로 접속 테스트 통과
[finishSecret] AWSCURRENT = shopmini_app_clone 으로 이동
               shopmini_app 은 AWSPREVIOUS 로 밀려나되 **비밀번호는 유효**
               → 캐시가 남은 앱도 다음 갱신까지 정상 동작
```

**핵심은 마지막 두 줄입니다.** 라벨 이동 뒤에도 이전 자격 증명이 살아 있어 캐시를 든 인스턴스도 실패하지 않습니다. 취약 창이 **사라집니다**.

| 항목 | 평가 |
|---|---|
| 설정 복잡도 | 높음 — DB 사용자 2개 + 마스터 시크릿 + 두 사용자 권한 동일 유지 |
| 무중단 | **구조적으로 보장** — 재시도 로직 없이도 안전 |
| DB 권한 요구 | 마스터 권한(사용자 생성·권한 부여) |
| 적합 | **운영 환경, 다중 인스턴스 오토스케일링, 무중단이 요구되는 모든 경우** |

🔴 **운영 환경의 DB 자격 증명은 다중 사용자 교대 방식을 쓰십시오.** 그렇지 않으면 순환은 예정된 정기 장애가 됩니다. 인스턴스가 20개까지 늘어나는 오토스케일링 환경에서는 캐시 만료 시점이 제각각이라 순환 직후 **일부 인스턴스만 5xx를 반환하는 간헐적 장애**가 발생하고, 재현이 어려워 원인 규명에 며칠이 걸립니다.

⚠️ 교대 방식의 함정: **두 사용자의 DB 권한이 항상 동일해야 합니다.** `shopmini_app`에만 새 권한을 부여하면 다음 순환에서 특정 기능만 권한 오류로 실패합니다. 권한 부여는 **역할 또는 스크립트로 두 사용자에게 동시에** 적용하십시오.

### 순환 실패 알람 🔴

**순환은 조용히 실패합니다.** `testSecret`이 실패하면 라벨이 이동하지 않고 순환이 중단됩니다 — 앱은 정상 동작하므로 아무도 모릅니다. 그러다 90일 뒤 감사에서 "마지막 순환이 언제입니까"라는 질문을 받습니다.

```json
{
  "Name": "shopmini-secret-rotation-failed",
  "EventPattern": {
    "source": ["aws.secretsmanager"],
    "detail-type": ["AWS Service Event via CloudTrail"],
    "detail": {
      "eventName": ["RotationFailed", "RotationAbandoned"]
    }
  }
}
```

```bash
aws events put-rule \
  --name "shopmini-secret-rotation-failed" \
  --event-pattern file://rotation-failed-pattern.json \
  --region ap-northeast-2 --profile awssec-lab

aws events put-targets \
  --rule "shopmini-secret-rotation-failed" \
  --targets "Id=1,Arn=arn:aws:sns:ap-northeast-2:111122223333:shopmini-security-alerts" \
  --region ap-northeast-2 --profile awssec-lab
```

한 겹으로는 부족합니다. **3중 탐지**를 씁니다.

| 겹 | 탐지 대상 | 구현 |
|---|---|---|
| 1 | 순환 시도가 실패했다 | 위 EventBridge 규칙 → SNS |
| 2 | 순환 Lambda가 예외로 죽었다 | 순환 Lambda의 CloudWatch `Errors` 지표 알람 (임계값 ≥ 1) |
| 3 | **순환이 아예 시도되지 않았다** | `DescribeSecret`의 `LastRotatedDate`를 주기적으로 검사해 주기 초과 시 경보 |

3번이 가장 중요합니다. 1·2번은 "실패한 순환"을 잡지만 **순환 설정이 비활성화된 경우**는 아무 이벤트도 발생하지 않습니다. AWS Config 규칙(`secretsmanager-rotation-enabled-check`, `secretsmanager-scheduled-rotation-success-check`)이나 `DescribeSecret` 순회 Lambda로 채웁니다.

## 11.6 애플리케이션에서 시크릿을 안전하게 읽는 패턴

옳은 곳에 두고도 읽는 방식이 틀리면 원점입니다. 축은 **캐싱·주입·최소 권한·감사** 넷입니다.

### 1) 캐싱: 매 요청 조회는 답이 아니다

Secrets Manager는 API 호출당 과금되고 스로틀 한도가 있습니다. 요청마다 호출하면 비용·지연이 오르고 한도에 걸리면 서비스가 멈춥니다. 반대로 무기한 캐시하면 순환에 죽습니다. 정답은 **TTL 캐시 + 실패 시 강제 갱신**이고, AWS는 언어별 캐싱 클라이언트를 제공합니다.

```python
import boto3
import pymysql
from aws_secretsmanager_caching import SecretCache, SecretCacheConfig

client = boto3.client("secretsmanager", region_name="ap-northeast-2")

# secret_refresh_interval 기본값은 3600초(1시간). 순환 주기보다 충분히 짧게 둔다.
cache = SecretCache(
    config=SecretCacheConfig(secret_refresh_interval=600),
    client=client,
)

SECRET_ID = "rds/shopmini"


def _connect():
    import json
    s = json.loads(cache.get_secret_string(SECRET_ID))
    return pymysql.connect(
        host=s["host"], port=int(s["port"]),
        user=s["username"], password=s["password"],
        database=s["dbname"],
        ssl={"ca": "/etc/pki/tls/certs/rds-combined-ca-bundle.pem"},  # 전송 중 암호화 (16.2)
        connect_timeout=3,
    )


def get_connection():
    try:
        return _connect()
    except pymysql.err.OperationalError as e:
        # 1045 = Access denied. 순환 직후일 수 있으므로 캐시를 버리고 1회만 재시도한다.
        if e.args and e.args[0] == 1045:
            cache._cache.clear()          # 캐시 무효화
            return _connect()
        raise
```

세 가지가 이 코드의 요점입니다.

- **TTL을 순환 주기가 아니라 취약 창 기준으로 정한다.** 30일 순환에 TTL 10분이면 단일 사용자 방식에서도 최악 노출이 10분입니다.
- **인증 실패를 캐시 무효화 신호로 해석한다.** 이 다섯 줄이 11.5의 "증명 절차 ③"입니다.
- **재시도는 1회만 한다.** 무한 재시도는 Secrets Manager와 DB를 동시에 두드리는 폭주가 됩니다.

⚠️ `except Exception` 으로 뭉뚱그려 잡고 캐시를 비우지 마십시오. 네트워크 오류나 DB 다운에도 캐시가 비워져 **스로틀링 폭풍**이 발생합니다.

### 2) 주입: 런타임별 표준 경로

**Lambda — AWS Parameters and Secrets Lambda Extension.** 레이어를 붙이면 함수 옆에 로컬 HTTP 캐시가 떠 `localhost`로 조회합니다.

```python
import os, json, urllib.request

PORT = os.environ.get("PARAMETERS_SECRETS_EXTENSION_HTTP_PORT", "2773")
TOKEN = os.environ["AWS_SESSION_TOKEN"]  # 확장 인증용


def get_secret(secret_id: str) -> dict:
    url = f"http://localhost:{PORT}/secretsmanager/get?secretId={secret_id}"
    req = urllib.request.Request(url)
    req.add_header("X-Aws-Parameters-Secrets-Token", TOKEN)
    with urllib.request.urlopen(req, timeout=2) as r:
        return json.loads(json.loads(r.read())["SecretString"])
```

캐시는 `SECRETS_MANAGER_TTL`, `SSM_PARAMETER_STORE_TTL`, `PARAMETERS_SECRETS_EXTENSION_CACHE_ENABLED` 환경 변수로 조정합니다. **콜드 스타트 이후 여러 호출이 같은 값을 재사용**하므로 API 호출 수가 크게 줄어듭니다.

**ECS — 태스크 정의 `secrets` 필드.** ShopMini 앱 컨테이너의 표준 경로입니다.

```json
{
  "family": "shopmini-app",
  "taskRoleArn": "arn:aws:iam::111122223333:role/shopmini-app-task-role",
  "executionRoleArn": "arn:aws:iam::111122223333:role/shopmini-app-execution-role",
  "networkMode": "awsvpc",
  "containerDefinitions": [
    {
      "name": "app",
      "image": "111122223333.dkr.ecr.ap-northeast-2.amazonaws.com/shopmini-app:1.42.0",
      "portMappings": [{ "containerPort": 8443, "protocol": "tcp" }],
      "environment": [
        { "name": "APP_ENV", "value": "prod" },
        { "name": "DB_SECRET_ID", "value": "rds/shopmini" }
      ],
      "secrets": [
        {
          "name": "PG_API_KEY",
          "valueFrom": "arn:aws:ssm:ap-northeast-2:111122223333:parameter/shopmini/prod/pg/api-key"
        }
      ]
    }
  ]
}
```

`DB_SECRET_ID`는 값이 아니라 **참조**이므로 `environment`에 있어도 안전하고, 앱은 이 이름으로 앞의 캐싱 클라이언트를 호출합니다. `PG_API_KEY`는 `secrets`로 주입되어, 실행 역할이 부팅 시 값을 가져와 환경 변수로 넣어줍니다.

⚠️ **`secrets` 필드의 한계**: 주입된 값은 컨테이너 안에서 **평문 환경 변수**이고(11.1의 2번), **태스크 재시작 때만 갱신**되어 순환이 반영되지 않습니다. 그래서 ShopMini는 **순환 대상(DB 자격 증명)은 SDK 캐싱으로, 순환하지 않는 값은 `secrets` 필드로** 나눕니다 — 이 절의 실무적 결론입니다.

또한 `secrets` 필드는 태스크 역할이 아니라 **실행 역할(execution role)** 의 권한을 요구합니다. 혼동하면 태스크가 `AccessDenied`로 기동하지 않습니다(24.3).

**EKS** — 파드에 시크릿을 넣는 표준은 Secrets Store CSI Driver의 AWS 프로바이더 또는 External Secrets Operator이며, 인증은 IRSA/Pod Identity로 합니다. ⚠️ Kubernetes `Secret`은 etcd에 **base64 인코딩**으로만 저장되므로 그 자체가 시크릿 저장소가 아닙니다(24.4).

### 3) 최소 권한: 시크릿 하나 단위로

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadOnlyItsOwnSecret",
      "Effect": "Allow",
      "Action": "secretsmanager:GetSecretValue",
      "Resource": "arn:aws:secretsmanager:ap-northeast-2:111122223333:secret:rds/shopmini-??????",
      "Condition": {
        "StringEquals": {
          "secretsmanager:VersionStage": "AWSCURRENT"
        }
      }
    },
    {
      "Sid": "DecryptOnlyViaSecretsManager",
      "Effect": "Allow",
      "Action": "kms:Decrypt",
      "Resource": "arn:aws:kms:ap-northeast-2:111122223333:key/EXAMPLE-KEY-ID",
      "Condition": {
        "StringEquals": {
          "kms:ViaService": "secretsmanager.ap-northeast-2.amazonaws.com"
        }
      }
    }
  ]
}
```

세 가지 기법이 들어 있습니다.

- **시크릿 ARN 뒤의 `-??????`**: Secrets Manager는 이름 뒤에 6자 임의 접미사를 붙입니다. `rds/shopmini*`로 쓰면 `rds/shopmini-backup` 같은 다른 시크릿까지 포함되므로, `?` 6개로 접미사만 매칭합니다.
- **`secretsmanager:VersionStage`**: `AWSCURRENT`만 읽게 제한해, 침해된 앱이 `AWSPREVIOUS`로 이전 비밀번호를 수집하는 것을 막습니다.
- **`kms:ViaService`**: 11.2와 같은 이유입니다.

그리고 **사람에게는 `GetSecretValue`를 주지 않습니다.** 원서 원칙 3의 구현입니다. 사람에게 필요한 것은 시크릿의 **존재와 상태**(`DescribeSecret`)뿐이고, 값을 봐야 하는 예외는 32.4의 브레이크 글래스 절차로 처리하며 **즉시 알람**을 겁니다.

### 4) 감사: 접근을 로그로 남기고 이상을 알린다

원서 원칙 6은 AWS에서 절반이 자동 충족됩니다. `GetSecretValue`, `PutSecretValue`, `GetParameter`, `PutParameter`가 CloudTrail **관리 이벤트**로 기록되기 때문입니다(값 자체는 기록되지 않습니다). 남은 절반은 **무엇을 알람으로 걸 것인가**이고, 원서 7장이 목록을 줍니다.

> 📖 *Practical Cloud Security* 2판 7장 「Secrets Server」: **"시크릿 서버를 운영한다면 시크릿에 대한 모든 접근을 로깅해야 한다. 알람을 걸고 조사하고 싶을 만한 비정상 활동의 예를 들면 다음과 같다 — 공격을 시사할 수 있는 시크릿 서버에서의 인증 또는 인가 실패, 비정상적인 양의 시크릿 조회 활동, 관리자 자격 증명의 사용."**

AWS로 번역하면 이렇습니다.

| 원서 항목 | 탐지 대상 이벤트 | 임계 예시 |
|---|---|---|
| 인증/인가 실패 | `errorCode`가 `AccessDenied*`인 `GetSecretValue`/`GetParameter` | 5분간 3회 이상 |
| 비정상적인 조회량 | 동일 프린시펄의 `GetSecretValue` 급증, 또는 **다수 시크릿을 순회 조회** | 5분간 서로 다른 시크릿 10개 이상 |
| 관리자 자격 증명 사용 | 워크로드 역할이 아닌 **사람 프린시펄**의 `GetSecretValue` | 1회라도 즉시 |

세 번째가 실무에서 값어치가 가장 큽니다. 앱 역할만 시크릿을 읽는 것이 정상이라면 **사람이 읽는 순간이 곧 조사 대상**입니다. 두 번째의 "다수 시크릿 순회"는 자격 증명 탈취 후의 전형적 수집 행위이며, GuardDuty 탐지와 함께 보면 신뢰도가 올라갑니다(31.1).

### 5) 시크릿을 로그에 남기지 않는 코딩 습관

가장 자주 무너집니다. 저장소를 완벽히 구성해도 예외 처리 한 줄이 시크릿을 CloudWatch Logs로 쏟아냅니다. **로그는 순환할 수 없습니다** — 보존 기간 내내 남고, 로그 계정으로 복제되고, SIEM으로 전달됩니다.

📋 코드 리뷰에서 확인할 항목

- [ ] 시크릿을 담은 객체 전체를 로깅하는 코드가 없다 (`logger.debug(config)`)
- [ ] 예외 메시지에 접속 문자열이 없다 — DB 드라이버가 DSN을 예외에 포함하는 경우가 많다
- [ ] 시크릿 클래스의 `__repr__`/`toString`이 값을 마스킹한다
- [ ] `set -x` 구간에서 시크릿을 변수로 다루지 않고, `curl -v`·HTTP 디버그 로깅이 운영에서 꺼져 있다
- [ ] APM·에러 추적 SaaS의 자동 컨텍스트 수집에서 환경 변수·요청 헤더가 제외되어 있다
- [ ] 로그 그룹에 대해 Macie 또는 지표 필터로 **시크릿 패턴 유출을 상시 탐지**한다 (12.4)

마지막 항목이 안전망입니다. 앞의 항목들을 사람이 100% 지킬 수는 없으므로 **로그에 시크릿이 들어갔음을 탐지하는 통제**가 따로 필요합니다.

## 11.7 서드파티 시크릿 서버 연동

외부 시크릿 서버를 AWS와 함께 쓰는 조직은 많습니다. 온프레미스에서 이미 쓰고 있었거나 멀티 클라우드인 경우입니다.

> 📖 *Practical Cloud Security* 1판·2판 4장은 시크릿 관리 접근법을 네 단계로 제시합니다. **두 번째 접근법**이 시크릿 서버입니다. **"별도의 시크릿 서버를 두면 구성 데이터에는 시크릿에 대한 참조와 시크릿 서버와 통신할 능력만 있으면 된다. (…) 그런데 문제가 보이지 않는가? 이제 걱정해야 할 또 하나의 시크릿(시크릿 서버의 비밀번호)이 생긴 것이다."** 그럼에도 요청을 로깅할 수 있고, IP 범위 같은 **"유용한 2차 통제"** 를 더할 수 있으며, **"나중에 시크릿을 쉽게 갱신할 수 있고, 시크릿을 가져오는 모든 시스템이 자동으로 새 것을 받게 된다"** 는 가치가 있다고 말합니다.
>
> **네 번째 접근법**이 이 장의 결론과 맞닿습니다. **"가능하다면 클라우드 플랫폼이 제공자에 의해 내장한 기능을 활용해 '거북이가 끝없이 내려가는' 문제를 피하는 것이다. 일부 클라우드 제공자는 클라우드에 프로비저닝된 시스템에 인스턴스 메타데이터나 신원 문서를 제공한다."** 2판은 여기에 한 문장을 더 붙입니다. **"앞으로는 신원 문서를 대부분의 클라우드 서비스에 직접 사용해 시크릿 서버가 아예 필요 없게 될지도 모른다."** 도구로는 **"HashiCorp Vault와 Keywhiz"** 같은 독립 제품과 **"서비스형 모델로 제공되는 AWS Secrets Manager"** 를 듭니다.

"거북이가 끝없이 내려간다(turtles all the way down)"가 이 절의 전부입니다. **시크릿 서버에 접근하기 위한 시크릿을 어떻게 관리할 것인가.** 검토 항목은 넷입니다.

### ① 인증 경로 — 부트스트랩 시크릿을 없애라

🔴 **Vault의 AWS 인증 방법(auth method)을 사용해 IAM 역할을 신원으로 쓰십시오.** Vault 토큰이나 AppRole Secret ID를 AMI·User Data·이미지 레이어에 심는 구성은 11.1의 3·4번을 그대로 재현합니다. AWS 인증 방법은 원서가 말한 네 번째 접근법의 실물이고, 두 방식이 있습니다.

| 방식 | 동작 | 특징 |
|---|---|---|
| `iam` | 클라이언트가 서명한 `sts:GetCallerIdentity` 요청을 Vault에 제출 → Vault가 STS에 확인 | EC2·ECS·EKS·Lambda 어디서나 동작. **권장** |
| `ec2` | EC2 인스턴스 아이덴티티 문서(PKCS#7 서명)를 제출 | EC2 전용. 원서가 묘사한 "서명된 신원 문서"에 정확히 해당 |

`iam` 방식이면 **AWS 밖으로 나가는 정적 시크릿이 없습니다.** Vault가 IAM 역할 ARN을 정책에 매핑하므로 인스턴스 프로파일/태스크 역할이 곧 신원입니다.

⚠️ 반대 방향인 Vault **AWS 시크릿 엔진**(단기 IAM 자격 증명 동적 발급)은 편리하지만, **Vault에 IAM 사용자 생성 권한을 가진 장기 자격 증명을 주게 됩니다.** 8장에서 없애기로 한 것을 다시 만드는 셈이므로, Vault는 인스턴스 역할로 실행하고 그 역할의 권한 경계를 좁히십시오.

### ② 가용성 — 시크릿 서버가 곧 단일 장애점

Secrets Manager는 AWS가 리전 규모로 운영합니다. 자체 운영 Vault는 **여러분의 SLA**가 되고, 시크릿 서버 장애 = 전체 배포 불가입니다.

📋 자체 운영 시 확인 항목

- [ ] 다중 AZ(`ap-northeast-2a`/`2c`)에 배치되어 있다
- [ ] 봉인 해제가 KMS 기반 auto-unseal로 자동화되어 있다 — 수동 언실 키 배포는 그 자체가 시크릿 배포 문제다
- [ ] 재해 복구 절차와 백업 복호화 키 보관 위치가 문서화되고 **복구 테스트를 통과했다**(17.6)
- [ ] 앱이 장애 시 **캐시된 값으로 계속 동작**한다 (11.6의 TTL 캐시)
- [ ] 접근 경로가 프라이빗이다 — VPC 내부 또는 PrivateLink(20.2)

두 번째 항목이 결정적입니다. **KMS auto-unseal은 "Vault를 쓰더라도 신뢰의 뿌리는 결국 KMS"** 임을 보여줍니다 — "거북이"의 끝은 대개 클라우드 제공자의 하드웨어 신뢰 근원입니다.

### ③ 감사 이중화 — 로그가 두 곳으로 갈라진다

가장 자주 간과됩니다. 외부 시크릿 서버를 도입하면 **시크릿 접근 감사 추적이 두 시스템으로 쪼개집니다.**

| 시크릿 위치 | 접근 감사 로그 | 조사 시 |
|---|---|---|
| Secrets Manager / Parameter Store | CloudTrail | Athena로 즉시 질의 (30.6) |
| Vault | Vault audit device (파일/syslog/socket) | **별도 수집·보관·질의 경로 필요** |

🔴 **Vault audit device를 중앙 로그 계정(`777788889999`)으로 전달하고, CloudTrail과 동일한 보존 기간·무결성 통제를 적용하십시오.** 그렇지 않으면 "이 자격 증명을 누가 언제 가져갔는가"에 답할 수 없는 구간이 생기고, 그 구간이 하필 침해 구간일 가능성이 높습니다. 29장의 로깅 아키텍처에 **시크릿 서버 로그를 처음부터 포함**시키십시오.

⚠️ Vault audit device는 기본적으로 꺼져 있어 **활성 device가 없으면 요청이 그냥 처리됩니다.** 반대로 유일한 device가 쓰기 실패하면 Vault가 요청을 거부하므로, 로그 장애가 서비스 장애로 번지지 않게 **2개 이상**을 구성하십시오.

### ④ 이중 관리 비용 — 통합의 현실적 지점

두 저장소를 병행하면 순환 자동화·정책 동기화·감사 증거 수집이 전부 두 벌이 됩니다. 실무에서 정착하는 패턴은 둘입니다.

| 패턴 | 구성 | 적합 |
|---|---|---|
| **경계 분리** | 멀티 클라우드/온프렘 공용 시크릿은 Vault, AWS 전용 시크릿(RDS·AWS 서비스 통합)은 Secrets Manager | 대부분의 조직. AWS 내장 순환·`secrets` 필드 통합을 잃지 않는다 |
| **단방향 동기화** | Vault를 단일 원본(source of truth)으로 두고 AWS 저장소로 동기화, 앱은 AWS만 읽는다 | 조직 정책상 시크릿 원본이 한 곳이어야 할 때. ⚠️ 동기화 지연·역방향 변경 충돌 관리가 필수 |

두 패턴 모두 원칙은 하나입니다. **애플리케이션이 두 저장소를 동시에 읽지 않게 하십시오.** 양쪽에 의존하면 가용성이 두 시스템의 곱이 되고 장애 원인 분리가 어려워집니다.

2판이 예고한 방향 — "앞으로는 신원 문서를 대부분의 클라우드 서비스에 직접 사용해 시크릿 서버가 아예 필요 없게 될지도 모른다" — 은 AWS에 이미 부분적으로 도착했습니다. **IAM 역할(8장), RDS의 IAM 데이터베이스 인증(16.2), IAM Roles Anywhere(6.4)가 각각 시크릿을 하나씩 없앱니다.** 시크릿 관리의 최종 목표는 시크릿을 잘 보관하는 것이 아니라 **보관할 시크릿을 줄이는 것**입니다.

| Secrets Manager | 항상 암호화, 리소스 정책, 리전 복제, **내장 순환**. 시크릿당 월 과금 |
| 선택 기준 | **순환 필요 여부가 저장소를, 비밀 여부가 타입을 결정한다** |
| 순환 설계 | 앱의 무중단을 먼저 증명 → 유형별 주기 → 운영은 **다중 사용자 교대 방식** |
| 순환 실패 | 조용히 실패한다. EventBridge + Lambda Errors + `LastRotatedDate` **3중 탐지** |
| 읽는 패턴 | TTL 캐시(순환 주기보다 짧게) + 인증 실패 시 캐시 무효화 1회 재시도 |
| ECS `secrets` 필드 | 재시작 시에만 갱신 → **순환 대상 값에는 쓰지 않는다** |
| 감사 | CloudTrail 관리 이벤트 + 원서 7장의 3가지 이상 징후(인가 실패·조회 급증·사람의 조회) |
| 외부 시크릿 서버 | `iam` 인증 방법으로 부트스트랩 시크릿 제거, KMS auto-unseal, **audit 로그를 중앙 로그 계정으로** |
| 최종 목표 | 시크릿을 잘 보관하는 것이 아니라 **보관할 시크릿을 줄이는 것** |

## 🔴 필수 구성 체크리스트

- [ ] Git 전체 히스토리에 **시크릿 스캐닝**이 돌고, 푸시 차단(push protection)이 활성이다
- [ ] 과거에 커밋된 시크릿은 **삭제가 아니라 순환**으로 처리되었다
- [ ] User Data와 AMI/이미지 레이어에 시크릿이 없음이 확인되었다
- [ ] 모든 시크릿이 Secrets Manager 또는 Parameter Store **`SecureString`** 에 있다 (`String` 오지정 없음)
- [ ] Parameter Store 시크릿이 **고객 관리형 KMS 키**(`alias/shopmini/app`)로 암호화되어 있다
- [ ] 파라미터 경로가 `/shopmini/<환경>/<컴포넌트>/<항목>` 규칙을 따르고 **환경이 두 번째 세그먼트**다
- [ ] IAM 정책이 **경로/시크릿 ARN 단위**로 좁혀져 있고, 앱 역할에 쓰기는 명시적 Deny다
- [ ] `kms:Decrypt`에 **`kms:ViaService` 조건**이 걸려 있다
- [ ] 앱 역할에 `ssm:DescribeParameters`·`secretsmanager:ListSecrets`가 없다
- [ ] 시크릿 ARN에 `-??????` 매칭을 써서 **인접 시크릿이 포함되지 않는다**
- [ ] `secretsmanager:VersionStage`를 `AWSCURRENT`로 제한하고, 리소스 정책에 **`--block-public-policy`** 를 썼다
- [ ] 크로스 계정 접근 시 **리소스 정책 · 상대 IAM · KMS 키 정책 3중 확인**을 완료했다
- [ ] `secretsmanager:ForceDeleteWithoutRecovery`를 `BoolIfExists`로 거부한다
- [ ] DB 자격 증명에 **자동 순환이 활성**이고, 운영은 **다중 사용자 교대 방식**이다
- [ ] 교대 방식의 두 DB 사용자가 **항상 동일한 권한**을 갖도록 자동화되어 있다
- [ ] 순환을 켜기 **전에** 개발 계정에서 `--rotate-immediately`로 무중단이 검증되었다
- [ ] 순환 실패 3중 탐지(`RotationFailed` · Lambda `Errors` · `LastRotatedDate` 초과)가 모두 있다
- [ ] 앱이 **TTL 캐시**를 쓰고, 인증 실패 시 **캐시 무효화 + 1회 재시도** 로직이 있다
- [ ] ECS `secrets` 필드에 **순환 대상 시크릿을 넣지 않았다**
- [ ] 사람 프린시펄에게 `GetSecretValue`가 없고, 예외는 브레이크 글래스 + 즉시 알람이다
- [ ] `GetSecretValue`/`GetParameter`가 CloudTrail에 기록되고 **사람의 조회는 1회라도 경보**된다
- [ ] 로그에 시크릿이 들어갔는지 **탐지하는 통제**가 별도로 있다
- [ ] 외부 시크릿 서버를 쓴다면 **audit device 2개 이상**이 중앙 로그 계정으로 전달된다

## ⚠️ 자주 하는 실수

| 실수 | 결과 | 올바른 구성 |
|---|---|---|
| 커밋된 시크릿을 다음 커밋에서 삭제하고 끝낸다 | 히스토리에 그대로 남아 저장소 공개·포크 시 유출 (11.1 시나리오) | 삭제가 아니라 **순환**. 그 값은 이미 유출된 것으로 취급 |
| 시크릿을 콘솔에서 환경 변수로 평문 입력한다 | 크래시 덤프·APM·`docker inspect`로 새어나감 | 참조만 환경 변수로, 값은 런타임 조회 (11.6) |
| User Data에 DB 비밀번호를 넣는다 | IMDS `latest/user-data`로 평문 노출 — SSRF 한 번이면 끝 | Parameter Store `SecureString` + 인스턴스 역할 (22.4) |
| Parameter Store에 `--type String`으로 시크릿을 넣는다 | 평문 저장. 오류가 나지 않아 아무도 모른다 | `SecureString` 강제. Config 규칙으로 상시 점검 |
| `alias/aws/ssm` / `aws/secretsmanager`를 그대로 쓴다 | 키 정책 2차 관문 없음, 크로스 계정 공유 불가 | 고객 관리형 키(`alias/shopmini/app`) (11.2, 11.3) |
| `/db/prod/password`처럼 환경을 경로 뒤에 둔다 | 와일드카드로 환경을 분리할 수 없어 dev 역할에 prod 권한이 샌다 | 환경을 두 번째 세그먼트로 (11.2) |
| 앱 역할에 `ssm:PutParameter`를 남겨둔다 | 앱 침해가 곧 시크릿 변조 → 서비스 거부 | 쓰기는 명시적 Deny (11.2) |
| 시크릿 ARN을 `rds/shopmini*`로 쓴다 | `rds/shopmini-backup` 등 인접 시크릿까지 읽힌다 | `rds/shopmini-??????` (11.6) |
| 리소스 정책에 `--block-public-policy` 없이 적용한다 | `Principal: "*"` Allow가 통과 — 시크릿 저장소 공개 | 항상 플래그 사용 (11.3) |
| 크로스 계정 설정에서 KMS 키 정책을 빼먹는다 | `AccessDeniedException` — 원인 파악에 시간 소모 | 3중 확인표대로 (11.3) |
| 앱 검증 없이 자동 순환을 먼저 켠다 | 원서 경고대로 **첫 순환이 즉시** 일어나 하드코딩 앱이 즉사 | 개발 계정 검증 → 운영 활성화 (11.5) |
| 운영에서 단일 사용자 순환 방식을 쓴다 | 캐시 TTL만큼의 취약 창 — 순환마다 간헐적 5xx | 다중 사용자 교대 방식 (11.5) |
| 교대 방식에서 한 사용자에게만 권한을 추가한다 | 다음 순환 후 특정 기능만 권한 오류로 실패 | 두 사용자 권한을 스크립트로 동시 적용 (11.5) |
| 순환 실패 알람을 걸지 않는다 | 조용히 멈춘 채 90일 뒤 감사에서 발견 | EventBridge + Lambda Errors + `LastRotatedDate` 3중 (11.5) |
| 매 요청마다 `GetSecretValue`를 호출한다 | API 비용 증가 + 스로틀 시 서비스 전체 정지 | TTL 캐시 (11.6) |
| 시크릿을 무기한 캐시한다 | 순환 시점에 전 인스턴스가 인증 실패 | TTL + 인증 실패 시 무효화 (11.6) |
| `except Exception`으로 잡고 캐시를 비운다 | DB 장애 시 매 요청이 조회 → 스로틀링 폭풍 | 인증 오류 코드만 좁혀서 처리 (11.6) |
| 순환하는 DB 자격 증명을 ECS `secrets` 필드로 주입한다 | 태스크 재시작까지 옛 값 사용 → 순환 후 접속 실패 | 순환 대상은 SDK 캐싱으로 조회 (11.6) |
| `secrets` 필드 권한을 태스크 역할에 준다 | 태스크가 기동조차 하지 않는다 | **실행 역할**에 부여 (11.6, 24.3) |
| Kubernetes `Secret`을 시크릿 저장소로 쓴다 | etcd에 base64 인코딩만 — 암호화가 아니다 | CSI Driver / External Secrets + IRSA (11.6, 24.4) |
| 담당자에게 `GetSecretValue`를 상시 부여한다 | 원서 원칙 3 위반. 퇴사 시 순환 누락으로 값이 계속 유효 | 사람은 `DescribeSecret`까지. 예외는 브레이크 글래스 (32.4) |
| 예외 로그에 접속 문자열을 남긴다 | 로그는 순환 불가 — 보존 기간 내내 남고 SIEM까지 복제 | 마스킹 + 로그 시크릿 탐지 통제 (11.6) |
| Vault 토큰을 AMI/User Data에 심는다 | 11.1의 3·4번을 그대로 재현 | `iam` 인증 방법으로 IAM 역할을 신원으로 (11.7) |
| Vault audit device를 켜지 않는다 | 시크릿 접근 감사 구간이 통째로 비어 조사 불가 | 2개 이상 구성 + 중앙 로그 계정 전달 (11.7, 29장) |
| 앱이 Vault와 Secrets Manager를 동시에 읽는다 | 가용성이 두 시스템의 곱, 장애 원인 분리 불가 | 경계 분리 또는 단방향 동기화 (11.7) |
