# 3장. 위협 모델링과 신뢰 경계

> **이 장에서 다루는 것**
> - 원서가 제시하는 네 부류의 위협 행위자와, 그 분류를 AWS 계정 환경에서 어떻게 다시 읽어야 하는가
> - ShopMini의 데이터 흐름도(DFD)를 직접 그리고 신뢰 경계(trust boundary)를 긋는 6단계 절차 — 이 장에서 정의한 **DF1~DF8·A1~A3·L1~L2 흐름 번호는 이후 모든 장에서 그대로 참조**됩니다
> - STRIDE 6개 위협 유형을 AWS 통제로 옮기는 매핑표
> - 클라우드에만 있는 여섯 개의 공격 경로 — 노출된 액세스 키, 퍼블릭 버킷, IAM 권한 상승 체인, IMDS·SSRF, 크로스 계정 신뢰 오설정, 퍼블릭 스냅샷/AMI
> - 공개된 클라우드 침해 "유형"별 근본 원인 역추적: 어떤 통제 하나가 있었으면 그 사고는 일어나지 않았는가
>
> **선행 지식**: 0장(예제 애플리케이션 ShopMini), 1장(최소 권한·심층 방어·폭발 반경), 2장(공동 책임 모델)
> **난이도**: ★☆☆

2장에서 "무엇이 내 책임인가"의 목록을 만들었습니다. 이제 그 목록을 어디부터 손댈지 정해야 합니다. 예산도 시간도 유한하기 때문에, **모든 것을 똑같이 지키겠다는 계획은 아무것도 지키지 못하는 계획**입니다.

원서는 이 우선순위 문제를 아주 간결한 방법으로 풉니다. 누가 나를 공격하는지 정하고(3.1), 내 시스템이 무엇과 무엇을 신뢰하는지 그림으로 그리고(3.2), 그 신뢰가 깨지는 지점에 통제를 놓는(3.3~3.4) 것입니다.

> 📖 *Practical Cloud Security* 2판 1장은 위협 모델링을 이렇게 정의합니다. **"위협 모델링은 누가 당신의 시스템을 공격할 가능성이 높고 왜 그런지를 이해하는 것, 그리고 시스템의 구성요소들이 어떻게 함께 동작하는지를 이해하는 과정이다."** 그리고 두 가지를 알고 나면 "잠재적 공격자의 눈으로 시스템을 볼 수 있게 되고, 공격자가 바람직하지 않은 무언가를 할 수 있는 영역을 찾아낼 수 있다"고 이어갑니다. 결론은 이 장 전체의 요지이기도 합니다. **"일반적으로 완화 조치를 놓기에 가장 효과적인 위치는 신뢰 경계다. 신뢰 경계란 시스템의 한 부분이 다른 부분을 신뢰해야 하는 지점이다."**

같은 장의 다이어그램 절은 더 짧게 못을 박습니다.

> 📖 *Practical Cloud Security* 1판·2판 1장은 다이어그램 그리기 절차를 마무리하며 이렇게 씁니다. **"선이 신뢰 경계를 가로지르는 지점을 모두 보라. 이곳이 우리가 가장 먼저 보안에 집중해야 할 곳이다."**

이 장은 그 "선이 경계를 가로지르는 지점"을 ShopMini에서 실제로 세어보는 장입니다.

## 3.1 위협 행위자 분류

### 원서의 네 부류

> 📖 *Practical Cloud Security* 1판·2판 1장은 리스크를 생각하는 여러 방식 중 **"자산 중심(asset-oriented) 접근"** 을 선호한다고 밝히면서, 동시에 "누가 당신에게 문제를 일으킬 가능성이 가장 높은지를 염두에 두는 것도 좋은 생각"이라고 말합니다. 그리고 이 책에서 고려할 **네 가지 주요 위협 행위자 유형**을 다음과 같이 열거합니다.
> - **조직범죄 또는 독립 범죄자(organized crime or independent criminals)** — 주로 **돈을 버는 데** 관심이 있음
> - **핵티비스트(hacktivists)** — 주로 훔친 데이터를 공개하거나, 반달리즘 행위를 하거나, 비즈니스를 방해해 **당신의 신뢰를 떨어뜨리는 데** 관심이 있음
> - **내부 공격자(inside attackers)** — 대개 **신뢰를 떨어뜨리거나 돈을 버는 데** 관심이 있음
> - **국가 행위자(state actors)** — **비밀을 훔치거나** 외국 정부의 정치적 임무·목적을 진전시키기 위해 **비즈니스를 방해하는 데** 관심이 있을 수 있음
>
> 저자는 예시로 이렇게 씁니다. "당신은 자금이 풍부한 국가 행위자를 방어할 필요가 없을지도 모른다. 하지만 사이버 범죄자가 당신의 데이터를 훔쳐 돈을 벌 수 있는 업종에 있거나, 핵티비스트가 정치적·사회적 이유로 당신의 웹사이트를 훼손하고 싶어 하는 업종에 있을 수는 있다."

여기서 중요한 것은 목록 자체가 아니라 **"당신은 국가 행위자를 방어할 필요가 없을지도 모른다"** 는 문장입니다. 위협 행위자 분류의 목적은 백과사전을 만드는 것이 아니라 **어떤 행위자는 방어 대상에서 제외하겠다고 명시적으로 결정하는 것**입니다. 그 결정을 하지 않으면 모든 통제가 "있으면 좋은 것" 목록에 남아 아무 순위도 생기지 않습니다.

원서는 이 결정을 구체적으로 만드는 실무 기법도 하나 제시합니다.

> 📖 같은 절에서 저자는 **사용자 경험 디자인의 기법을 빌려오라**고 권합니다. "해당되는 각 그룹의 구성원 한 명을 상상하고, 이름을 붙이고, 그 '페르소나'에 대해 카드에 조금 적어두고, 방어를 설계할 때 그 카드들을 눈에 보이는 곳에 두라."

이 기법을 실제로 써보면 추상적 분류가 설계 결정으로 바뀝니다. ShopMini의 페르소나 카드 한 장은 예컨대 이렇게 씁니다.

```
┌─ 페르소나 #1 ─────────────────────────────────────────────┐
│ 이름   : "스캐너 봇" (기회주의적 범죄자)                    │
│ 동기   : 컴퓨트 자원 탈취 → 암호화폐 채굴 수익             │
│ 표적성 : 없음. ShopMini가 뭐 하는 회사인지 모름            │
│ 도구   : 퍼블릭 리포지토리 크롤러, 전 IPv4 포트 스캔,      │
│          버킷 이름 사전 대입                               │
│ 이 페르소나가 이길 조건 :                                  │
│   "액세스 키가 코드에 한 번이라도 커밋되면"                │
│ 이 페르소나가 지는 조건 :                                  │
│   "장기 키가 애초에 발급 불가능하면"                       │
│ → 설계 결정 : 6.4의 장기 키 금지 SCP를 Day 1에 적용        │
└───────────────────────────────────────────────────────────┘
```

카드에서 중요한 것은 마지막 두 줄입니다. **"이 페르소나가 이기는 조건"과 "지는 조건"을 한 문장씩 적으면, 그 자리에서 통제 하나가 결정됩니다.** 조건을 쓸 수 없다면 그 페르소나를 아직 충분히 이해하지 못한 것입니다.

### AWS 문맥으로 다시 읽기

원서의 네 부류는 온프레미스·클라우드 공통의 분류입니다. AWS 환경에서는 여기에 **"기회주의적 자동화"** 라는 축이 하나 더 필요합니다. 클라우드에서는 공격자가 당신을 표적으로 삼지 않아도 당신이 피해자가 될 수 있기 때문입니다. 퍼블릭 GitHub에 커밋된 액세스 키를 긁어가는 봇, 전체 IPv4 대역을 스캔해 열린 3306 포트를 찾는 스캐너, 이름 사전(dictionary)으로 S3 버킷 이름을 무작위 대입하는 도구는 **당신이 누구인지 모른 채** 당신의 계정에 도달합니다.

그래서 실무에서는 원서의 4분류를 **동기(왜) × 표적성(누구를)** 2축으로 다시 배치하는 것이 유용합니다.

| 행위자 | 원서 분류 | 주 동기 | 표적성 | AWS에서의 전형적 행동 | ShopMini 관련성 |
|---|---|---|---|---|---|
| **기회주의적 범죄자** | 조직범죄/독립 범죄자 | 금전 | **무차별** — 자동화된 스캐닝 | 노출된 액세스 키 수집 → EC2 대량 기동(암호화폐 채굴), 열린 RDS 무차별 대입, 퍼블릭 버킷 크롤링 | **매우 높음** — 규모와 무관하게 즉시 노출 |
| **표적형 범죄자** | 조직범죄 | 금전(랜섬·갈취) | **표적** | 정찰 → 초기 침투 → 권한 상승 → 백업·스냅샷 삭제 후 데이터 암호화·유출 협박 | **높음** — 회원 개인정보·주문 데이터 보유 |
| **핵티비스트** | 핵티비스트 | 평판 훼손 | 표적(업종·이슈 기반) | 정적 자산 변조(웹사이트 훼손), 고객 데이터 공개, DDoS | 중간 — 업종·브랜드에 따라 변동 |
| **악의적 내부자** | 내부 공격자 | 금전·보복 | 표적(자신의 소속 조직) | 정당한 자격 증명으로 데이터 대량 조회·반출, 퇴사 직전 스냅샷 개인 계정 공유 | **높음** — 통제 대부분을 우회함 |
| **과실 내부자** | (원서 4분류에는 없음) | 없음(실수) | — | 퍼블릭 액세스 차단 해제, `0.0.0.0/0` 개방, 키를 리포지토리에 커밋 | **매우 높음** — 실제 사고의 최대 원인 |
| **탈취된 내부자 계정** | 조직범죄 ↔ 내부자 경계 | 금전 | 표적 | 피싱으로 얻은 SSO 세션·MFA 우회로 정당한 권한 사용 | **높음** |
| **국가 행위자** | 국가 행위자 | 첩보·교란 | 표적(전략적 가치) | 공급망 침투, 장기 잠복, 로그 조작 | **낮음** — ShopMini 규모에서는 명시적 제외 |

> 💡 **원서 이후 보충** — "과실 내부자"는 원서의 4분류에 별도 항목으로 등장하지 않습니다. 원서의 내부 공격자(inside attackers)는 **악의(신뢰 훼손·금전)** 를 전제한 분류입니다. 그러나 클라우드에서는 악의 없는 설정 실수 하나가 악의적 내부자와 **동일한 결과**를 만들기 때문에(퍼블릭 버킷, 열린 보안 그룹), 이 책에서는 별도 행위자로 분리해 다룹니다. 2장에서 인용한 원서의 S3 사고 목록도 대부분 이 유형에서 비롯된 것입니다.

### 방어 수준을 결정하는 법

행위자를 나열했으면 각각에 대해 **"막을 것인가, 탐지만 할 것인가, 받아들일 것인가"** 를 정합니다. 1장의 심층 방어는 무한한 층을 쌓으라는 뜻이 아닙니다.

> 📖 *Practical Cloud Security* 2판 1장 결론부는 심층 방어의 한계를 수치로 설명합니다. "95% 효과적인 두 개의 겹치지만 독립적인 통제가 있다면, 둘의 조합은 **99.75% 효과적**이다." 그러나 곧바로 덧붙입니다. **"다만 이 접근에는 수확 체감이 있어서, 같은 영역에 다섯 겹 여섯 겹을 쌓는 것은 아마도 자원을 잘 쓰는 방법이 아닐 것이다."**

ShopMini의 판정은 다음과 같이 문서로 남깁니다. 이 표가 이후 모든 통제 투자 논쟁의 기준선이 됩니다.

| 행위자 | 판정 | 근거 | 이 책에서 대응하는 곳 |
|---|---|---|---|
| 기회주의적 범죄자 | **예방(Prevent)** | 비용이 거의 들지 않고 자동화 가능 | 5장(Day 1), 15.2, 19.3, 3.4 |
| 과실 내부자 | **예방** — 가드레일로 실수 자체를 불가능하게 | 사고 최대 원인 | 37.1(SCP), 28.3(정책 게이트) |
| 표적형 범죄자 | **탐지 + 복구** | 완전 예방은 비현실적 → 폭발 반경과 복구력에 투자 | 17장(백업), 31장(GuardDuty), 33장 |
| 악의적 내부자 | **탐지 + 억제** | 정당한 권한을 쓰므로 예방 곤란 → 최소 권한·직무 분리·감사 | 9.5(PAM), 29.9(로그 분리) |
| 탈취된 내부자 계정 | **예방(피싱 저항 MFA)** | 패스키로 상당 부분 차단 가능 | 9.4 |
| 핵티비스트 | **탐지 + 완화** | WAF·Shield로 상당 부분 흡수 | 23.8~23.10 |
| 국가 행위자 | **명시적 제외** | ShopMini 규모·데이터 가치 대비 비용 과다 | — (제외 결정을 리스크 대장에 기록: 4.1) |

**"명시적 제외"를 반드시 문서로 남기십시오.** 제외 결정이 문서에 없으면 나중에 감사에서 "왜 이 통제가 없느냐"는 질문에 답할 수 없고, 반대로 문서가 있으면 그것은 결함이 아니라 **의사결정**이 됩니다.

## 3.2 데이터 흐름도와 신뢰 경계 그리기 🧪

### 원서의 6단계 절차

> 📖 *Practical Cloud Security* 1판·2판 1장은 "무엇이 무엇과 대화해야 하는지를 파악하는 가장 쉬운 방법은 그림을 그려서 취약할 것 같은 지점을 찾아내는 것"이라고 하면서, 아주 단순한 애플리케이션 구성요소 다이어그램을 위한 절차를 제시합니다.
> 1. 졸라맨을 하나 그리고 **"사용자"**, 또 하나 그리고 **"관리자"** 라고 이름 붙인다. 나중에 여러 유형의 사용자·관리자나 다른 역할이 있음을 발견할 수 있지만 이것이 좋은 출발점이다.
> 2. **사용자가 가장 먼저 대화하는 구성요소**(예: 웹 서버)를 상자로 그리고, 사용자에서 그 상자로 선을 긋고, **어떻게 대화하는지를 선에 라벨로 적는다.** 이 시점에서 그 구성요소는 서버리스 함수일 수도, 컨테이너일 수도, 가상 머신일 수도 있다. "이것은 누구나 대화할 수 있게 하므로 **아마도 가장 먼저 공격받을 것**이다. 우리는 다른 구성요소들이 이것을 필요 이상으로 신뢰하는 것을 정말 원하지 않는다."
> 3. 그 첫 시스템이 대화해야 하는 **다른 모든 구성요소**를 뒤에 상자로 그리고 선을 긋는다. 실제로 데이터를 저장하는 시스템에 도달할 때마다 **작은 기호(저자는 원통을 쓴다)를 옆에 그리고 거기에 어떤 데이터가 있는지 적는다.**
> 4. **관리자(및 정의한 다른 역할)가 애플리케이션에 접근하는 방법**을 그린다. 저자는 관리자가 여러 경로를 가질 수 있다고 명시합니다 — "클라우드 제공자의 포털이나 API를 통해서, 또는 운영체제를 통해서, 또는 사용자가 접근하는 것과 비슷한 방식으로."
> 5. **상자들 주위에 점선으로 신뢰 경계를 그린다.** 저자의 정의는 이렇습니다. **"신뢰 경계란, 그 경계 안에 있는 모든 것은 경계 안의 다른 모든 것의 의도를 적어도 어느 정도 확신할 수 있지만, 경계 바깥의 무언가를 신뢰하기 전에는 검증을 요구한다는 뜻이다."** 그리고 핵심 가정을 덧붙입니다. **"공격자가 신뢰 경계의 한 부분에 들어오면 결국 그 안의 모든 것을 완전히 장악하게 된다고 가정하는 것이 합리적이므로, 각 신뢰 경계를 통과하는 데는 어느 정도 노력이 들어야 한다."**
> 6. **모든 상자를(관리자는 포함하되 사용자는 제외하고) 감싸는 점선을 하나 더 그린다.** 저자는 "신뢰 경계 안에 신뢰 경계가 있다는 사실이 서로 다른 신뢰 수준을 보여준다"고 설명합니다. 그리고 관리자가 여럿이면 — 웹 서버 관리자와 데이터베이스 관리자처럼 — **서로 다른 신뢰 경계에 있을 수 있다**고 명시합니다.
>
> 2판은 5단계에 제로 트러스트를 접목한 문장을 추가했습니다. **"이 맥락에서 제로 트러스트 원칙은 이러한 신뢰 경계를 합리적으로 가능한 가장 작은 크기로 — 예를 들면 단일 구성요소로 — 줄이도록 이끈다."**

원서는 마지막에 이렇게 못을 박습니다. **"선이 신뢰 경계를 가로지르는 지점을 모두 보라. 이곳이 우리가 가장 먼저 보안에 집중해야 할 곳이다."**

### 흐름 정의 — DF1~DF8 · A1~A3 · L1~L2

**이 번호는 이후 장에서 계속 참조됩니다.** DF1~DF8은 0장의 ①~⑧과 동일한 흐름입니다. 여기에 원서 4단계가 요구하는 **관리자 접근 경로(A1~A3)** 와, 6부에서 쓸 **로그 흐름(L1~L2)** 을 추가했습니다.

| 번호 | 흐름 | 프로토콜/포트 | 가로지르는 경계 | 이 경계에서의 인증 수단 | 데이터 민감도 |

| **DF4** | ALB → 앱 | HTTPS 8443 | TB3 → TB4 | SG 참조 체인 + TLS | 기밀 |
| **DF5** | 앱 → RDS | TCP 3306 (TLS) | TB4 → TB5 | DB 자격 증명(또는 IAM DB 인증) | **기밀** |

### 경계별 통제 배치

원서 5단계의 정의 — *"공격자가 경계의 한 부분에 들어오면 결국 그 안의 모든 것을 장악한다고 가정하는 것이 합리적"* — 를 그대로 적용하면, 각 경계에 놓을 통제는 **"이 경계 안이 전부 털렸다고 가정할 때, 다음 경계로 넘어가는 것을 무엇이 막는가"** 라는 질문의 답이어야 합니다.

| 경계 | 안쪽이 전부 침해되면 공격자가 얻는 것 | 다음 경계로 넘어가는 것을 막을 통제 | 다루는 절 |
|---|---|---|---|
| **TB0 → TB1** (인터넷 → 계정) | — | 계정 수준 퍼블릭 액세스 차단, `aws:PrincipalOrgID` 제한, 리소스 정책에 와일드카드 Principal 금지, IAM Access Analyzer 상시 감시 | 15.2, 7.5, 7.7 |
| **TB0 → TB2** (사용자 → 엣지) | 없음(설계상 익명 허용) | AWS WAF 관리형 규칙 + 속도 기반 규칙, Shield, TLS 정책, ACM 인증서 만료 알람 | 23.6~23.10 |
| **TB2 → TB3** (엣지 → ALB) | WAF **우회** — 오리진 직접 타격 | ALB SG를 CloudFront 관리형 프리픽스 리스트로 한정 + 커스텀 헤더 검증 | 23.9 |
| **TB3 → TB4** (ALB → 앱) | 앱 계층 진입 | SG 참조 체인(ALB SG만 8443 허용), 대상 그룹 상태 검사, 앱 컨테이너 읽기 전용 루트 | 19.2, 24.5 |
| **TB4 → TB5** (앱 → RDS) | **회원 개인정보 전량** | DB SG는 App SG 참조만 허용, 격리 서브넷 라우팅에 IGW/NAT 부재, TLS 강제, IAM DB 인증, 저장 암호화 | 16.2, 18.3 |
| **TB4 → TB0** (앱 → 인터넷, DF6) | **데이터 반출·C2 통신** | 이그레스 필터링, Network Firewall 도메인 허용 목록, NAT 트래픽 급증 알람 | 19.6, 30.3 |
| **TB4 → (D3)** (앱 → S3) | 업로드 파일 전량 | 게이트웨이 엔드포인트 + 엔드포인트 정책(`aws:PrincipalOrgID`), 버킷 정책의 `aws:SourceVpce` 제한, 역할 권한을 접두사 단위로 | 20.1, 20.3, 15.4 |
| **TB4 → (D4)(D5)** (앱 → KMS·시크릿) | **복호화 능력 자체** | 키 정책 + `kms:ViaService` + 암호화 컨텍스트, 시크릿 접근 로깅, 자동 순환 | 13.4, 13.8, 11.5 |
| **TB4 내부** (IMDS) | 역할 자격 증명 | **IMDSv2 강제 + 홉 제한 1**, 컨테이너에서 IMDS 도달 차단 | 8.3, 3.4 |
| **TB0 → TB6** (관리 평면) | **모든 것** | 피싱 저항 MFA, 상시 관리자 권한 제거(JIT), SCP 가드레일, 브레이크 글래스 알람 | 9.4, 9.5, 37.1, 32.4 |
| **TB1 → 777788889999** (L1) | 흔적 삭제 능력 | 운영 계정에 **쓰기만** 허용, 객체 잠금, 버킷 정책에서 삭제 Deny | 29.3, 29.9 |

> 📖 원서 4단계는 관리자가 **"클라우드 제공자의 포털이나 API를 통해서, 또는 운영체제를 통해서, 또는 사용자가 접근하는 것과 비슷한 방식으로"** 여러 경로를 가질 수 있다고 명시합니다. TB6을 별도 경계로 분리한 이유가 여기에 있습니다. 온프레미스에서는 관리 접근이 데이터 흐름과 대체로 같은 네트워크를 탔지만, **AWS에서는 관리 평면이 네트워크와 완전히 분리된 별개의 인터넷 노출 표면**입니다. VPC를 아무리 잘 격리해도 A1 경로 하나가 뚫리면 TB1 전체가 무의미해집니다.

### 관리자는 한 명이 아니다 — TB6을 다시 쪼개기

원서 6단계에는 실무에서 자주 놓치는 문장이 하나 더 있습니다.

> 📖 *Practical Cloud Security* 1판·2판 1장 6단계는 이렇게 명시합니다. **"관리자가 여럿이라면, 예컨대 웹 서버 관리자와 데이터베이스 관리자처럼, 그들은 서로 다른 신뢰 경계에 있을 수 있다."**

TB6을 하나의 상자로 두면 "AWS 계정에 로그인할 수 있는 사람" 전체가 한 덩어리가 됩니다. 그러면 3.1에서 분리했던 악의적 내부자·과실 내부자·탈취된 계정이 모두 같은 취급을 받게 되고, 직무 분리(Segregation of Duties)를 설계할 근거가 사라집니다. ShopMini에서는 TB6을 다음과 같이 네 개로 쪼갭니다.

| 하위 경계 | 주체 | 접근할 수 있어야 하는 것 | 접근하면 **안 되는** 것 | 강제 수단 |
|---|---|---|---|---|
| **TB6-a** 앱 운영 | 서비스 운영자 | ECS/EC2 배포·롤백, 앱 로그, 대시보드 | RDS 데이터 직접 조회, KMS 키 정책 변경 | 권한 경계 + 키 정책에서 제외 |
| **TB6-b** 데이터 관리 | DBA | RDS 파라미터·스키마, 스냅샷 | 스냅샷 공유 설정 변경, 로그 삭제 | SCP(퍼블릭 공유 금지) |
| **TB6-c** 보안 운영 | 보안팀(`444455556666`) | 탐지 결과 조회, 포렌식 스냅샷 생성 | 운영 데이터 변경·삭제 | 읽기 중심 역할 + 별도 계정 |
| **TB6-d** 감사·로그 | 아무도 상시 보유하지 않음 | (로그 조회만) | **로그 삭제·변조 — 누구도 불가** | 로그 아카이브 계정 분리 + 객체 잠금 |

> 🔴 **TB6-d의 "아무도"에 주목하십시오.** 운영 계정의 관리자가 로그를 지울 수 있다면, 악의적 내부자와 계정을 장악한 외부 공격자 모두에게 **완전 범죄의 경로**가 열립니다. 이 구조를 만드는 방법이 29.9(중앙 로그 계정)와 17.4(백업 계정 분리)이고, 그것이 0장에서 계정을 다섯 개로 나눈 근본 이유입니다.

**① TB0 → TB1: 계정 밖에서 접근 가능한 리소스가 있는가**

```bash
# 계정 수준 퍼블릭 액세스 차단이 4개 항목 모두 true인지
```

**④ TB4 내부: IMDS가 자격 증명 발급기로 노출되어 있는가**

```bash
aws ec2 describe-instances \

           Tokens:MetadataOptions.HttpTokens,
           Hop:MetadataOptions.HttpPutResponseHopLimit,
           Role:IamInstanceProfile.Arn}' \

```

`Tokens`가 `optional`인 인스턴스는 IMDSv1이 열려 있어 **SSRF 한 번으로 `Role` 열의 자격 증명이 유출됩니다**(3.4 참조).

**⑤ DF7/DF8: 엔드포인트 정책이 조직 밖을 막고 있는가**

```bash
aws ec2 describe-vpc-endpoints \
  --filters "Name=vpc-id,Values=$VPC_ID" \
```

정책이 `{"Statement":[{"Effect":"Allow","Principal":"*","Action":"*","Resource":"*"}]}`(기본 완전 개방)이면 DF7은 **우리 조직 버킷이 아닌 임의의 버킷으로도 데이터를 내보낼 수 있는 통로**입니다.

## 3.3 STRIDE를 AWS 아키텍처에 적용하기

3.2에서 **어디를** 지킬지 정했다면, STRIDE는 각 지점에서 **무엇을** 걱정해야 하는지 빠짐없이 세는 체크리스트입니다.

> 📖 *Practical Cloud Security* 1판·2판 1장은 다이어그램 그리기를 설명하면서 각주로 **"이 주제에 관한 책이 통째로 있다"** 고 밝히고, **Adam Shostack의 *Threat Modeling: Designing for Security* (Wiley, 2014)** 를 추천합니다. 또 "높은 위험 환경에 있다면 졸라맨을 그리는 대신 적절한 도구로 정식 다이어그램을 만들어야 할 것"이라고 덧붙입니다.
>
> 💡 **보충** — STRIDE 자체는 원서 3권 어디에도 이름으로 등장하지 않습니다. STRIDE는 Microsoft에서 정립된 위협 분류 체계로, 위에서 원서가 추천한 Shostack의 책이 이를 상세히 다룹니다. 이 절은 원서의 신뢰 경계 개념 위에 STRIDE를 얹어 AWS 통제로 번역한 것으로, 원서 저자의 서술이 아닙니다.

### 6개 위협 유형과 AWS 통제 매핑

| 약자 | 위협 | 위반되는 보안 속성 | ShopMini에서의 구체적 질문 | 예방 통제(AWS) | 탐지 통제(AWS) |
|---|---|---|---|---|---|
| **S** — Spoofing | 신원 위장 | 인증(Authentication) | "이 요청이 정말 우리 CloudFront에서 왔는가?" "이 토큰이 정말 우리 사용자인가?" | SigV4, IAM 역할, Cognito, ACM/TLS, OAC, 커스텀 헤더, MFA·패스키, ExternalId | CloudTrail의 이상 주체, GuardDuty `UnauthorizedAccess:IAMUser/InstanceCredentialExfiltration.OutsideAWS` |
| **T** — Tampering | 변조 | 무결성(Integrity) | "정적 자산이 바꿔치기되었는가?" "로그가 지워졌는가?" | S3 버전 관리, 객체 잠금, KMS 암호화 컨텍스트, 코드 서명, ECR 태그 불변성, CloudTrail 로그 파일 검증 | AWS Config 구성 이력, CloudTrail Insights, S3 이벤트 알림 |
| **R** — Repudiation | 부인 | 부인 방지(Non-repudiation) | "누가 이 보안 그룹을 열었는지 증명할 수 있는가?" | 조직 CloudTrail(전 리전), S3 데이터 이벤트, 로그 아카이브 계정 분리, 객체 잠금 | Athena 기반 사후 조회, Detective 그래프 |
| **I** — Information Disclosure | 정보 노출 | 기밀성(Confidentiality) | "이 데이터가 경계 밖에서 읽히는가?" | 퍼블릭 액세스 차단, 버킷/키 정책, SSE-KMS, TLS 강제, VPC 엔드포인트 정책, Macie | GuardDuty `Exfiltration:S3/AnomalousBehavior`, IAM Access Analyzer, VPC 플로우 로그 |
| **D** — Denial of Service | 서비스 거부 | 가용성(Availability) | "이 계층이 멈추면 무엇이 멈추는가?" | Shield, WAF 속도 기반 규칙, Auto Scaling, Multi-AZ, API Gateway 스로틀링, 서비스 쿼터 | CloudWatch 지표 알람, Shield Advanced 이벤트 |
| **E** — Elevation of Privilege | 권한 상승 | 인가(Authorization) | "이 역할에서 관리자로 갈 수 있는 경로가 있는가?" | 최소 권한 정책, `iam:PassRole` 조건 제한, 권한 경계, SCP, IMDSv2 + 홉 제한 | GuardDuty `PrivilegeEscalation:IAMUser/AnomalousBehavior`, Access Analyzer 미사용 액세스 |

> 📖 *AWS Security Cookbook* 1장은 기밀성·무결성·가용성의 CIA 3요소를 소개하면서 **"이 외에도 보안을 다룰 때 부인 방지(non-repudiation)를 고려해야 한다"** 고 명시하고, "부인 방지란 사용자가 어떤 활동을 부인하지 못하게 하는 것"이며 **"암호학이 이를 달성하는 데 도움을 준다"** 고 설명합니다. STRIDE의 R(부인)이 다루는 것이 정확히 이 속성이며, AWS에서는 CloudTrail 로그 파일 검증(다이제스트 파일의 서명)이 그 구현입니다.

### 흐름 단위로 STRIDE 적용하기 — 세 가지 예

STRIDE는 요소(element)마다 적용할 수도 있고 상호작용(interaction)마다 적용할 수도 있습니다. **신뢰 경계를 가로지르는 흐름마다** 적용하는 것이 3.2의 결과와 가장 잘 맞습니다.

**DF4 (ALB → 앱, TB3 → TB4)**

| | 이 흐름에서의 위협 | 배치할 통제 |
|---|---|---|
| S | 공격자가 ALB를 우회해 앱 8443에 직접 접속 | App SG는 **ALB SG 참조만** 허용(CIDR 금지) |
| T | 요청 헤더 변조로 내부 라우팅 조작 | ALB에서 신뢰할 수 없는 헤더 제거, 앱에서 `X-Forwarded-For` 맹신 금지 |
| R | 어느 인스턴스가 요청을 처리했는지 불명 | ALB 액세스 로그 + 앱 로그 상관 키(trace ID) |
| I | 8443 구간 평문 전송 | 종단 간 TLS(23.5), 대상 그룹 프로토콜 HTTPS |
| D | 단일 AZ 대상 그룹 | 2a/2c 양쪽 등록 + 상태 검사 |
| E | 앱 컨테이너 탈출 → 호스트 권한 | 읽기 전용 루트 파일시스템, `privileged` 금지 |

**DF7 (앱 → S3 `shopmini-uploads`, TB4 → 데이터 저장소)**

| | 이 흐름에서의 위협 | 배치할 통제 |
|---|---|---|
| S | 탈취된 역할 자격 증명을 AWS 밖에서 사용 | IMDSv2, 버킷 정책의 `aws:SourceVpce` 제한 |
| T | 업로드 객체 덮어쓰기·삭제 | 버전 관리, 삭제에 MFA 요구, 객체 잠금(필요 시) |
| R | 누가 어떤 객체를 읽었는지 모름 | **CloudTrail 데이터 이벤트**(기본 비활성) |
| I | 다른 사용자의 업로드 파일 열람 | 역할 권한을 `${aws:PrincipalTag/tenant}` 접두사로 한정, SSE-KMS |
| D | 대량 삭제 | 버전 관리 + 라이프사이클 + 교차 계정 백업 |
| E | 버킷 정책 자체를 수정할 권한 보유 | 앱 역할에서 `s3:PutBucketPolicy` 제거, SCP로 이중 차단 |

**A2 (배포 파이프라인 → AWS API, TB0 → TB6)**

| | 이 흐름에서의 위협 | 배치할 통제 |
|---|---|---|
| S | 다른 리포지토리가 우리 역할을 가로챔 | OIDC 신뢰 정책에서 `sub` 클레임을 **리포지토리·브랜치까지** 고정 |
| T | 빌드 산출물 변조 후 배포 | 아티팩트 서명·검증, 재현 가능 빌드 |
| R | 누가 배포를 트리거했는지 불명 | 파이프라인 실행 ID를 세션 이름으로 |
| I | 빌드 로그에 시크릿 출력 | 로그 마스킹, 시크릿을 환경 변수로 노출 금지 |
| D | 파이프라인 잠금으로 배포 불가 | 브레이크 글래스 배포 경로 문서화 |
| E | **파이프라인 역할이 관리자 권한 보유** | 환경별 역할 분리 + 권한 경계(27.6) |

> ⚠️ STRIDE를 돌리면 위협이 수십 개 쏟아집니다. **전부 처리하려 하지 마십시오.** 3.1에서 정한 행위자 판정표와 교차해서, "명시적 제외"한 행위자만 수행할 수 있는 위협은 리스크 대장에 기록만 하고 넘어갑니다. 이 교차 작업이 4장의 리스크 관리로 이어집니다.

## 3.4 클라우드 특유의 공격 경로 ⚠️

온프레미스 위협 모델을 그대로 들고 오면 놓치는 경로들이 있습니다. 공통점은 **네트워크를 전혀 뚫지 않고도 데이터에 도달한다**는 것입니다. 방화벽 뒤에 있느냐가 아니라 **누가 API를 호출할 수 있느냐**가 경계이기 때문입니다.

각 경로를 "사고 시나리오 → 원인 → 올바른 구성" 3단으로, 그리고 공격 단계 · 탐지 지점 · 차단 통제를 표로 정리합니다.

### ① 노출된 장기 액세스 키

**사고 시나리오** — 개발자가 로컬 테스트 편의를 위해 IAM 사용자 액세스 키를 만들어 `config.py`에 넣었습니다. 실수로 퍼블릭 리포지토리에 푸시했고, 수 분 뒤 여러 리전에서 대형 GPU 인스턴스가 기동되기 시작합니다. 다음 날 아침 청구서 알림이 먼저 도착합니다.

**원인** — 만료되지 않는 자격 증명이 존재했다는 것. 키를 커밋한 것은 방아쇠일 뿐, **근본 원인은 장기 키가 발급 가능한 상태였다**는 점입니다.

> 📖 *Practical Cloud Security* 2판 4장은 이 문제를 정면으로 다룹니다. **"소스 코드에 시크릿, 예컨대 AWS API 키를 우발적으로 저장한 데서 비롯된 침해가 많이 있었다."** 저자는 코드에 시크릿을 넣으면 안 되는 이유를 두 가지로 정리합니다. ① **"소스 코드 리포지토리는 애초에 정보를 비밀로 유지하기 위해 설계된 것이 아니다."** 그 주된 기능은 소스 코드의 무결성 보호 — 백도어 삽입 같은 무단 수정 방지 — 이며, "많은 경우 소셜 코딩의 일환으로 기본적으로 모두에게 소스 코드를 보여준다"는 것입니다. ② **"설령 소스 코드 리포지토리가 완벽하게 안전하더라도, 소스 코드에 접근할 수 있는 모든 사람이 운영 환경에서 쓰이는 시크릿을 볼 권한까지 있어야 할 가능성은 매우 낮다."** 각주에서는 퍼블릭 GitHub 리포지토리에서 발견되는 시크릿을 가리키는 **"GitHub dorks"** 라는 용어가 있을 정도로 이 문제가 광범위했고, 그래서 GitHub이 시크릿이 포함된 푸시를 차단하는 방법을 제공하게 되었다고 설명합니다.

**🔴 올바른 구성** — 장기 액세스 키를 **발급 자체가 불가능하도록** 만듭니다. 사람은 IAM Identity Center, 워크로드는 IAM 역할, CI/CD는 OIDC를 씁니다(6.4, 8.2, 27.6). 조직 차원에서는 SCP로 봉인합니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyLongTermAccessKeyCreation",
      "Effect": "Deny",
      "Action": [
        "iam:CreateAccessKey",
        "iam:CreateUser",
        "iam:CreateLoginProfile"
      ],
      "Resource": "*",
      "Condition": {
        "ArnNotLike": {
          "aws:PrincipalArn": "arn:aws:iam::*:role/shopmini-break-glass"
        }
      }
    }
  ]
}
```

| 공격 단계 | 공격자가 하는 일 | 탐지 지점 | 차단 통제 |
|---|---|---|---|
| 수집 | 퍼블릭 리포지토리·페이스트빈 자동 스캔 | (외부) — 탐지 불가 | 시크릿 스캐닝을 **커밋 훅과 파이프라인 양쪽**에 |
| 검증 | `sts:GetCallerIdentity`, `iam:GetUser` 호출 | CloudTrail — **낯선 IP/UA의 최초 호출** | 조건 키로 소스 IP·VPC 제한 |
| 정찰 | `iam:List*`, `s3:ListAllMyBuckets`, `ec2:Describe*` 폭주 | GuardDuty `Recon:IAMUser/*`, CloudTrail Insights | 최소 권한 |
| 실행 | 여러 리전에서 `ec2:RunInstances` | **결제 알람(가장 빠른 신호)**, GuardDuty `CryptoCurrency:EC2/BitcoinTool.B!DNS` | 미승인 리전 차단 SCP, 서비스 쿼터 |
| 지속 | 새 IAM 사용자·키 생성 | CloudTrail `CreateUser`/`CreateAccessKey` 알람 | 위 SCP |

> ⚠️ AWS는 퍼블릭에 노출된 키를 탐지하면 `AWSCompromisedKeyQuarantineV3` 같은 격리 정책을 자동 부착하고 지원 케이스를 엽니다. **이것을 통제로 계산하지 마십시오.** 탐지되지 않는 노출 경로(비공개 유출, 개인 노트북 탈취)가 훨씬 많습니다.

### ② 퍼블릭 S3 버킷

**사고 시나리오** — 마케팅팀 요청으로 캠페인 이미지를 임시 공개하려고 `shopmini-uploads`의 퍼블릭 액세스 차단을 잠깐 껐습니다. 캠페인이 끝난 뒤 되돌리는 것을 잊었고, 그 사이 버킷 이름 사전 대입 스캐너가 사용자 업로드 파일 전체를 인덱싱했습니다.

**원인** — 공개해야 하는 자산과 공개하면 안 되는 자산이 **같은 버킷**에 있었고, 예외 처리가 버킷 전체 스위치를 끄는 방식이었다는 것.

**🔴 올바른 구성** — ShopMini가 버킷을 `shopmini-assets`(공개 자산)와 `shopmini-uploads`(사용자 업로드)로 분리한 이유가 정확히 이것입니다. 공개가 필요한 자산은 **버킷을 공개하는 것이 아니라 CloudFront OAC로 배포**합니다(DF3). 계정 수준 퍼블릭 액세스 차단은 절대 끄지 않고, 버킷 정책으로 이중 잠급니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyPrincipalsOutsideOrganization",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::shopmini-uploads",
        "arn:aws:s3:::shopmini-uploads/*"
      ],
      "Condition": {
        "StringNotEquals": {
          "aws:PrincipalOrgID": "o-exampleorgid"
        },
        "Bool": {
          "aws:PrincipalIsAWSService": "false"
        }
      }
    },
    {
      "Sid": "DenyInsecureTransport",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::shopmini-uploads",
        "arn:aws:s3:::shopmini-uploads/*"
      ],
      "Condition": {
        "Bool": {
          "aws:SecureTransport": "false"
        }
      }
    }
  ]
}
```

> ⚠️ `aws:PrincipalOrgID`로 조직 밖을 막을 때 **`aws:PrincipalIsAWSService` 가드를 빠뜨리면** 로그 전달, 복제, 일부 서비스 통합이 조용히 깨집니다. AWS 서비스 주체는 조직 ID를 갖지 않기 때문입니다. 이 한 줄이 "정책을 적용했더니 CloudTrail 로그가 끊겼다"는 사고를 막습니다.

| 공격 단계 | 공격자가 하는 일 | 탐지 지점 | 차단 통제 |
|---|---|---|---|
| 발견 | 버킷 이름 사전 대입, 인터넷 인덱싱 서비스 조회 | (외부) | 예측 가능한 버킷 이름 회피 — **부차적 통제일 뿐** |
| 확인 | 익명 `s3:ListBucket` | S3 서버 액세스 로그, GuardDuty `Policy:S3/BucketAnonymousAccessGranted` | 계정 수준 퍼블릭 액세스 차단 |
| 반출 | 익명 `s3:GetObject` 대량 | CloudTrail **데이터 이벤트**, GuardDuty `Exfiltration:S3/AnomalousBehavior` | 위 버킷 정책 |
| 지속 | — (일회성 반출로 충분) | — | Macie로 어떤 민감 데이터가 있었는지 사후 산정 |

### ③ 과도한 IAM 권한과 권한 상승 체인

**사고 시나리오** — 앱 역할 `shopmini-app-role`에 개발 편의상 `iam:PassRole`이 `Resource: "*"`로 붙어 있었고, `lambda:CreateFunction`과 `lambda:InvokeFunction`도 있었습니다. 앱을 장악한 공격자는 관리자 역할을 붙인 Lambda 함수를 만들고 호출해 **관리자 권한을 획득**합니다. 네트워크는 한 번도 뚫리지 않았습니다.

**원인** — 개별 권한은 각각 "합리적"으로 보였지만, **조합이 관리자와 등가**였다는 것.

> 📖 *Practical Cloud Security* 2판 1장 결론부는 최소 권한을 이렇게 정리합니다. "최소 권한은 기본적으로, 무엇에든 누구에게든 특권 접근을 주는 것은 리스크이며 필요 이상의 리스크를 지고 싶지 않다는 것을 인정하는 것이다." 그리고 결정적인 한 문장을 덧붙입니다. **"이것은 자동화에 대해 종종 간과되지만, 많은 실제 공격이 시스템이나 자동화를 속여 예상치 못한 행동을 하게 만드는 데 달려 있기 때문에 자동화에서 오히려 더 중요하다."**

**🔴 올바른 구성** — `iam:PassRole`은 **어떤 역할을, 어떤 서비스에** 넘길 수 있는지까지 못 박습니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "PassOnlyAppRoleToECSTasks",
      "Effect": "Allow",
      "Action": "iam:PassRole",
      "Resource": "arn:aws:iam::111122223333:role/shopmini-app-role",
      "Condition": {
        "StringEquals": {
          "iam:PassedToService": "ecs-tasks.amazonaws.com"
        }
      }
    }
  ]
}
```

권한 상승으로 이어지는 대표적 조합은 알아둘 가치가 있습니다.

| 상승 체인 | 필요한 권한 조합 | 결과 |
|---|---|---|
| 정책 버전 교체 | `iam:CreatePolicyVersion` (+ `SetDefaultPolicyVersion`) | 자기 정책을 관리자 정책으로 덮어씀 |
| 정책 부착 | `iam:AttachRolePolicy` / `AttachUserPolicy` | `AdministratorAccess` 자가 부착 |
| 인라인 정책 주입 | `iam:PutRolePolicy` / `PutUserPolicy` | 동일 |
| 컴퓨트 경유 | `iam:PassRole` + `lambda:CreateFunction` + `lambda:InvokeFunction` | 관리자 역할로 임의 코드 실행 |
| 컴퓨트 경유(2) | `iam:PassRole` + `ec2:RunInstances` | 관리자 역할이 붙은 인스턴스 기동 후 IMDS에서 자격 증명 획득 |
| 신뢰 정책 조작 | `iam:UpdateAssumeRolePolicy` + `sts:AssumeRole` | 자신을 임의 역할의 신뢰 주체로 추가 |
| 자격 증명 재발급 | `iam:CreateAccessKey` (타 사용자 대상) | 더 강한 사용자의 키 탈취 |
| 로그인 프로파일 | `iam:UpdateLoginProfile` | 타 사용자 콘솔 비밀번호 변경 |

| 공격 단계 | 공격자가 하는 일 | 탐지 지점 | 차단 통제 |
|---|---|---|---|
| 정찰 | `iam:GetRolePolicy`, `iam:SimulatePrincipalPolicy`로 자기 권한 열거 | CloudTrail — 워크로드 역할의 **IAM 읽기 호출은 정상 동작이 아님** | 앱 역할에서 `iam:*` 전면 제거 |
| 상승 | 위 표의 조합 실행 | GuardDuty `PrivilegeEscalation:IAMUser/AnomalousBehavior`, `CreateFunction`/`AttachRolePolicy` 알람 | `iam:PassRole` 조건 제한, 권한 경계, SCP |
| 지속 | 새 역할·신뢰 관계 생성 | Config 규칙 `iam-policy-no-statements-with-admin-access` | SCP로 보안 역할 수정 금지 |

> 🔴 **반드시 이렇게 구성하라** — 워크로드 역할(`shopmini-app-role`)에는 **`iam:` 로 시작하는 액션을 단 하나도 넣지 마십시오.** 앱이 IAM을 호출할 정당한 이유는 거의 없습니다. 예외가 필요하다면 그것은 별도 역할로 분리되어야 할 기능입니다. 이것을 지키지 않으면 SSRF 하나, 라이브러리 취약점 하나가 곧바로 계정 장악으로 연결됩니다.

### ④ IMDS 악용과 SSRF

**사고 시나리오** — ShopMini의 상품 이미지 미리보기 기능은 사용자가 준 URL을 서버가 가져와 썸네일을 만듭니다. 공격자가 `http://169.254.169.254/latest/meta-data/iam/security-credentials/shopmini-app-role`을 입력합니다. 서버는 성실하게 그 URL을 가져와 응답 본문에 **임시 자격 증명(AccessKeyId·SecretAccessKey·Token)** 을 담아 돌려줍니다. 공격자는 그 자격 증명을 자기 노트북에 넣고 `shopmini-uploads`를 통째로 내려받습니다.

**원인** — 두 개입니다. ① 애플리케이션이 사용자 입력 URL을 검증 없이 가져왔다(SSRF). ② **인스턴스 메타데이터 서비스가 단순 GET 요청 하나에 자격 증명을 내주는 상태(IMDSv1)였다.**

> 📖 *Practical Cloud Security* 1판·2판 4장은 메타데이터 기반 신원 문서의 구조적 한계를 이렇게 지적합니다. **"이것은 확실한 방법이 아니다. 시스템의 어떤 프로세스든, 시스템 상의 권한 수준과 무관하게 이 메타데이터를 요청할 수 있기 때문이다."** 그래서 "동일한 신뢰 수준의 프로세스만 그 시스템에 올리거나, 낮은 권한의 프로세스가 시스템 전체의 신원을 도용하지 못하도록 조치를 취해야 한다"고 말합니다. 이어서 컨테이너 환경을 특별히 경고합니다. **"이것은 컨테이너 환경에서 특히 우려되는데, 호스트 시스템의 어떤 컨테이너든 메타데이터를 요청해 그 호스트 시스템인 척할 수 있기 때문이다. 이런 경우에는 컨테이너가 메타데이터 서비스에 도달하지 못하도록 차단해야 한다."**

원서의 이 문장은 2019년과 2023년 판이 사실상 동일합니다. **AWS는 그 사이에 이 문제에 대한 구조적 답을 내놨습니다.**

> 💡 **원서 이후 변경** — IMDSv2는 **세션 지향 방식**입니다. 먼저 `PUT` 요청으로 토큰을 발급받고, 이후 모든 조회에 `X-aws-ec2-metadata-token` 헤더로 그 토큰을 실어야 합니다. 대부분의 SSRF는 공격자가 임의의 HTTP 메서드와 헤더를 지정할 수 없기 때문에(단순 GET만 가능), **IMDSv2 강제만으로 이 경로가 사실상 닫힙니다.** 여기에 `HttpPutResponseHopLimit`을 1로 두면 컨테이너(호스트로부터 1홉 더 떨어져 있음)에서 IMDS에 도달하는 것도 막혀, 원서가 말한 "컨테이너가 메타데이터 서비스에 도달하지 못하도록 차단하라"가 설정 한 줄로 달성됩니다.

**🔴 올바른 구성** — 계정에서 IMDSv1을 없앱니다. 기존 인스턴스는 `ec2:ModifyInstanceMetadataOptions`로 전환하고, 신규 생성은 SCP로 봉인합니다.

```bash
# 기존 인스턴스: IMDSv2 강제 + 홉 제한 1
aws ec2 modify-instance-metadata-options \
  --instance-id i-0abc123def4567890 \
  --http-tokens required \
  --http-put-response-hop-limit 1 \
  --http-endpoint enabled
```

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyRunInstancesWithoutIMDSv2",
      "Effect": "Deny",
      "Action": "ec2:RunInstances",
      "Resource": "arn:aws:ec2:*:*:instance/*",
      "Condition": {
        "StringNotEquals": {
          "ec2:MetadataHttpTokens": "required"
        }
      }
    },
    {
      "Sid": "DenyRunInstancesWithHighHopLimit",
      "Effect": "Deny",
      "Action": "ec2:RunInstances",
      "Resource": "arn:aws:ec2:*:*:instance/*",
      "Condition": {
        "NumericGreaterThan": {
          "ec2:MetadataHttpPutResponseHopLimit": "1"
        }
      }
    }
  ]
}
```

| 공격 단계 | 공격자가 하는 일 | 탐지 지점 | 차단 통제 |
|---|---|---|---|
| 초기 접근 | SSRF 가능한 기능(URL 가져오기, 웹훅, PDF 렌더링) 탐색 | WAF SSRF 규칙, 앱 로그의 `169.254.169.254` 패턴 | 입력 URL 허용 목록, 링크-로컬 대역 차단 |
| 자격 증명 접근 | IMDS에서 역할 자격 증명 조회 | (인스턴스 내부라 CloudTrail에 안 남음) ⚠️ | **IMDSv2 강제 + 홉 제한 1** |
| 반출 후 사용 | 외부에서 그 자격 증명으로 API 호출 | **GuardDuty `UnauthorizedAccess:IAMUser/InstanceCredentialExfiltration.OutsideAWS`** | 역할 신뢰 정책·리소스 정책에 `aws:SourceVpce`·`aws:VpcSourceIp` 조건 |
| 반출 | S3 대량 다운로드 | GuardDuty `Exfiltration:S3/AnomalousBehavior`, CloudTrail 데이터 이벤트 | 앱 역할 권한을 접두사·액션 단위로 축소 |

> ⚠️ **탐지 지점 열의 두 번째 행에 주목하십시오.** IMDS 조회는 CloudTrail에 남지 않습니다. 인스턴스 안에서 링크-로컬 주소로 일어나는 일이기 때문입니다. 즉 **이 단계는 사후에 로그로 재구성할 수 없습니다.** 반출 이후에야 탐지가 가능하다는 것이 이 경로를 특별히 위험하게 만드는 이유이고, 그래서 예방(IMDSv2)이 유일하게 신뢰할 수 있는 통제입니다.

### ⑤ 크로스 계정 신뢰 정책 오설정

**사고 시나리오** — 비용 분석 SaaS를 도입하면서 벤더 안내대로 읽기 역할을 만들었습니다. 신뢰 정책의 Principal에 벤더 계정을 넣고 `sts:ExternalId` 조건은 "선택 사항"이라기에 생략했습니다. 몇 달 뒤, 같은 벤더를 쓰는 다른 고객이 벤더 콘솔에서 우리 계정 ARN을 입력해 **우리 계정 데이터를 조회**할 수 있었다는 사실이 드러납니다.

**원인** — **혼동된 대리자(Confused Deputy)** 문제입니다. 벤더의 서비스 역할은 "고객이 시킨 대로" 우리 역할을 맡습니다. 우리 신뢰 정책이 "벤더 계정이면 누구든"이라고만 쓰여 있으면, 벤더 시스템은 **누가 시켰는지 구분해줄 의무가 없습니다.**

**🔴 올바른 구성** — 서드파티에 역할을 줄 때는 **ExternalId를 필수 조건으로** 넣습니다. ExternalId는 우리와 벤더만 아는 추측 불가능한 값이어야 하며, **고객마다 달라야** 합니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowVendorAssumeWithExternalId",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::999988887777:root"
      },
      "Action": "sts:AssumeRole",
      "Condition": {
        "StringEquals": {
          "sts:ExternalId": "shopmini-2f6c1a9e7b4d40c8"
        }
      }
    }
  ]
}
```

AWS 서비스가 우리를 대신해 리소스에 접근하는 경우에는 ExternalId 대신 `aws:SourceArn`·`aws:SourceAccount`를 씁니다. 두 경우를 혼동하지 마십시오.

| 신뢰 대상 | 사용할 조건 키 | 이유 |
|---|---|---|
| 서드파티 SaaS 계정 | `sts:ExternalId` | 벤더가 여러 고객을 대신해 호출하므로 고객 구분자가 필요 |
| AWS 서비스 주체(예: CloudTrail이 S3에 쓰기) | `aws:SourceArn` + `aws:SourceAccount` | 서비스가 어느 리소스·계정을 대신해 호출하는지 검증 |
| 우리 조직 내 다른 계정 | `aws:PrincipalOrgID` | 조직 밖 계정 전체를 배제 |
| 사람 관리자 | `aws:MultiFactorAuthPresent` | 세션 탈취 시 피해 축소 |

| 공격 단계 | 공격자가 하는 일 | 탐지 지점 | 차단 통제 |
|---|---|---|---|
| 발견 | 계정 ID·역할 이름 추측 또는 유출 문서에서 확보 | — | 역할 이름을 추측하기 어렵게 — **부차적** |
| 접근 | 벤더 경로로 `sts:AssumeRole` | CloudTrail `AssumeRole`의 **낯선 `sourceIdentity`/외부 계정** | ExternalId 필수화 |
| 정찰·반출 | 위임된 읽기 권한으로 데이터 조회 | GuardDuty, Access Analyzer의 크로스 계정 접근 결과 | 위임 권한을 읽기·특정 리소스로 한정 |

> ⚠️ 더 흔하고 더 위험한 변형은 신뢰 정책에 **`"Principal": {"AWS": "*"}`** 를 쓰는 것입니다. 이것은 "AWS 계정을 가진 전 세계 누구나"를 뜻합니다. IAM Access Analyzer가 이 패턴을 잡아내므로, 3.2의 실습 ①을 반드시 돌리십시오.

### ⑥ 퍼블릭 스냅샷과 AMI

**사고 시나리오** — 성능 문제를 재현하려고 운영 RDS 스냅샷을 만들어 벤더 엔지니어와 공유했습니다. 공유 설정에서 계정 지정 대신 "퍼블릭"을 골랐습니다. 스냅샷에는 회원 테이블 전체가 들어 있고, 누구나 자기 계정으로 복원할 수 있습니다. **네트워크·IAM·버킷 정책 어느 것도 이 경로에 관여하지 않습니다.**

**원인** — 데이터의 **사본**이 원본과 다른 통제 체계 아래 있었다는 것. 3.2의 다이어그램에 스냅샷이 그려져 있지 않았다는 사실 자체가 이 사고의 전조입니다.

> 📖 *AWS Security Cookbook* 10장은 Trusted Advisor의 **기본(Basic) 플랜에서도 제공되는 보안 권고 항목**을 열거하는데, 세 개 중 두 개가 바로 이것입니다 — **`Amazon EBS Public Snapshots`** 와 **`Amazon RDS Public Snapshots`**(나머지 하나는 `Specific Ports Unrestricted`). AWS가 지원 플랜과 무관하게 모든 고객에게 이 두 항목을 보여준다는 사실 자체가, 이 실수가 얼마나 흔하고 얼마나 치명적인지를 말해줍니다.
>
> 같은 책 10장은 AMI에 대해서도 **"우리는 신뢰하는 퍼블릭 AMI만 사용해야 한다"** 고 경고합니다. 반대 방향의 위험 — **우리 AMI가 퍼블릭이 되는 것** — 도 같은 무게로 다뤄야 합니다. AMI에는 애플리케이션 코드, 설정 파일, 때로는 하드코딩된 자격 증명이 들어 있습니다.

**🔴 올바른 구성** — 공유는 **계정 지정 공유만** 허용하고, 퍼블릭 공유는 SCP로 차단합니다. 그리고 사본이 만들어지는 모든 지점 — 스냅샷, AMI, RDS 스냅샷, 백업 볼트 — 을 3.2의 다이어그램에 **명시적으로 추가**하십시오.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyPublicSnapshotAndImageSharing",
      "Effect": "Deny",
      "Action": [
        "ec2:ModifySnapshotAttribute",
        "ec2:ModifyImageAttribute",
        "rds:ModifyDBSnapshotAttribute",
        "rds:ModifyDBClusterSnapshotAttribute"
      ],
      "Resource": "*"
    }
  ]
}
```

> ⚠️ 위 SCP는 **모든** 공유 변경을 막는 강한 형태입니다. 크로스 계정 백업(17.3)처럼 정당한 공유가 필요한 계정에는 이 SCP를 적용하지 말고, 대신 AWS Config 규칙 `ebs-snapshot-public-restorable-check`·`rds-snapshots-public-prohibited`로 탐지 후 자동 교정(35.3)하는 조합을 쓰십시오. SCP를 넓게 걸어 정상 백업이 멈추는 것은 1.6에서 다룬 전형적인 원칙 충돌입니다.

| 공격 단계 | 공격자가 하는 일 | 탐지 지점 | 차단 통제 |
|---|---|---|---|
| 발견 | 퍼블릭 스냅샷/AMI 목록을 리전별로 조회 | (외부) | — |
| 접근 | 자기 계정으로 스냅샷 복원 / AMI 기동 | **우리 계정 CloudTrail에는 남지 않음** ⚠️ | 애초에 퍼블릭이 되지 않게 |
| 수집 | 복원한 볼륨에서 데이터·자격 증명 추출 | — | 스냅샷 KMS 암호화(퍼블릭 공유 자체가 불가) |

> 🔴 **암호화가 이 경로의 최종 방어선입니다.** 고객 관리형 KMS 키로 암호화된 EBS 스냅샷·RDS 스냅샷은 **퍼블릭으로 공유하는 것이 API 수준에서 거부**됩니다. 키를 공유하지 않으면 계정 지정 공유를 받은 상대도 복원할 수 없습니다. 2장에서 "암호화는 항상 고객 책임"이라고 한 이유가 여기서도 나타납니다.

### 여섯 경로 종합

| 경로 | 네트워크 통제로 막히는가 | 로그에 남는가 | 유일하게 확실한 통제 | 다루는 절 |
|---|---|---|---|---|
| ① 노출된 장기 키 | **아니오** | 사용 시점부터 남음 | 장기 키 발급 자체 금지 | 6.4, 27.6 |
| ② 퍼블릭 버킷 | **아니오** | 데이터 이벤트 켜야 남음 | 계정 수준 퍼블릭 액세스 차단 | 15.2 |
| ③ IAM 권한 상승 | **아니오** | 남음 | 최소 권한 + `PassRole` 조건 | 7.5, 8장 |

**여섯 개 중 다섯 개가 네트워크 통제로 막히지 않습니다.** 이것이 1장에서 "클라우드에서 IAM은 곧 네트워크 경계"라고 한 말의 실증입니다. 방화벽 규칙을 아무리 정교하게 짜도 이 표의 대부분은 그대로 남습니다.

## 3.5 실제 클라우드 침해 사례 해부

> ⚠️ **이 절의 서술 원칙** — 여기서는 특정 기업의 사고를 지목하지 않습니다. 공개된 사고 보고서와 원서가 언급한 사례들에서 **반복적으로 나타나는 패턴**을 유형으로 일반화했습니다. 미확인 세부사항을 사실처럼 쓰지 않기 위한 선택입니다. 실무에서 사례를 학습할 때도 같은 태도를 권합니다 — 중요한 것은 "누가 당했나"가 아니라 **"어떤 통제 하나가 있었으면 안 일어났나"** 입니다.

원서도 사고 사례를 유형으로 다룹니다.

> 📖 *Practical Cloud Security* 1판·2판 1장은 공동 책임 모델을 잘못 이해해서 생긴 실제 사고들이 **"열려 있는 Amazon S3 버킷"에서 많이 나온다**고 하면서, 그로 인해 유실된 데이터를 열거합니다 — 1억 9,800만 명의 미국 유권자 데이터, 차량 추적 회사 기록, 무선 통신 고객 기록, 300만 건이 넘는 인구통계 설문 기록, 5만 명이 넘는 인도 시민의 신용 보고서. 2판은 여기에 10만 명이 넘는 학생의 성적·개인정보와, 사적인 대화가 담긴 수천 시간 분량의 음성·영상 녹음을 추가했습니다. 저자는 **"예는 훨씬 더 많다"** 고 덧붙입니다. 저자가 이 목록에 붙인 진단은 한 문장입니다. **"물론 S3 스토리지는 안전하고 암호화되어 있다. 하지만 접근 통제를 제대로 설정하지 않으면 그중 어느 것도 도움이 되지 않는다."**
>
> 같은 책 4장은 침해의 다른 축을 지목합니다. **"웹 애플리케이션이 연루된 침해에서, 분실되거나 도난당한 자격 증명은 여러 해 연속으로 공격자가 가장 많이 사용한 도구였다."** 그리고 이렇게 결론짓습니다. **"공격자가 당신의 시스템에 로그인할 유효한 자격 증명을 갖고 있다면, 세상의 모든 패치와 방화벽도 그들을 막지 못한다."**

두 인용을 합치면 클라우드 침해의 두 축이 나옵니다 — **잘못 설정된 접근 통제**와 **탈취된 자격 증명**. 아래 여섯 유형은 이 두 축의 조합입니다.

### 유형 A — 공개 리포지토리에 커밋된 자격 증명 → 자원 남용

| 항목 | 내용 |
|---|---|
| **전형적 전개** | 개발자가 편의상 만든 장기 액세스 키가 코드에 포함되어 퍼블릭 리포지토리에 푸시됨 → 자동 스캐너가 수 분 내 수집 → 다수 리전에서 컴퓨트 대량 기동 → 요금 폭증 |
| **근본 원인** | 만료되지 않는 자격 증명의 존재 자체 |
| **킬 체인 단계** | 자격 증명 접근 → 초기 접근 → 실행 → 영향(비용) |
| **놓친 탐지 지점** | 미승인 리전의 `RunInstances`, 결제 이상 |
| **있었으면 막았을 단 하나의 통제** | **장기 액세스 키 발급 금지 SCP** — 키가 없으면 커밋할 것도 없음 |
| **차선의 통제** | 리전 제한 SCP, 예산 알림, 파이프라인 시크릿 스캐닝 |
| **다루는 절** | 3.4①, 5.4, 6.4, 37.2 |

### 유형 B — 오설정된 스토리지의 대량 노출

| 항목 | 내용 |
|---|---|
| **전형적 전개** | 임시 공개 요청 또는 기본 설정 오해로 버킷/컨테이너가 인터넷에 노출 → 스캐너가 인덱싱 → 제3자가 발견해 언론·연구자에게 제보 → 규제 신고 의무 발생 |
| **근본 원인** | 공개 자산과 비공개 자산이 같은 버킷에 있고, 예외 처리가 **버킷 전체 스위치**를 끄는 방식 |

| **놓친 탐지 지점** | 퍼블릭 액세스 차단 해제 이벤트, 익명 접근 급증 |

| **다루는 절** | 3.4②, 15.2, 12.4, 37.2 |

### 유형 C — 애플리케이션 취약점 → 메타데이터 → 데이터 반출

| 항목 | 내용 |

| **전형적 전개** | 웹 계층의 SSRF 또는 원격 코드 실행 → 인스턴스 메타데이터에서 역할 자격 증명 획득 → 그 역할의 광범위한 스토리지 권한으로 대량 반출 |

| **다루는 절** | 3.4③④, 8.3, 15.4, 19.6, 31.1 |

| 항목 | 내용 |
|---|---|
| **전형적 전개** | 디버깅·이관 목적으로 만든 스냅샷/AMI를 퍼블릭 또는 넓은 범위로 공유 → 원본에 걸린 모든 통제를 우회해 데이터가 복제됨 |
| **근본 원인** | **데이터 사본이 위협 모델 다이어그램에 없었다** — 통제 대상 목록에 애초에 포함되지 않음 |
| **킬 체인 단계** | 정찰 → 수집 (우리 계정에서는 어떤 로그도 남지 않음) |
| **놓친 탐지 지점** | `ModifySnapshotAttribute`/`ModifyImageAttribute` 호출 |
| **있었으면 막았을 단 하나의 통제** | **고객 관리형 KMS 키로 암호화** — 암호화된 스냅샷은 퍼블릭 공유가 API에서 거부됨 |
| **차선의 통제** | 퍼블릭 공유 차단 SCP, Trusted Advisor 퍼블릭 스냅샷 점검, Config 자동 교정 |
| **다루는 절** | 3.4⑥, 16.1, 16.7, 26.7, 35.3 |

### 역추적이 말해주는 것

여섯 유형의 "있었으면 막았을 단 하나의 통제" 열을 모아보면 공통점이 보입니다.

| 유형 | 결정적 통제 | 성격 | 비용 |
|---|---|---|---|
| A | 장기 키 발급 금지 | 예방(가드레일) | 거의 0 |
| B | 계정 수준 퍼블릭 액세스 차단 | 예방(가드레일) | 0 |
| C | IMDSv2 강제 | 예방(설정) | 0 |
| D | ExternalId 필수화 | 예방(설정) | 0 |
| E | IdP 중앙화 | 예방(구조) | 중간 |
| F | KMS 암호화 | 예방(설정) | 낮음 |

**여섯 개 모두 예방 통제이고, 다섯 개는 사실상 무료입니다.** 탐지 도구를 사는 것보다 이 여섯 개를 켜는 것이 먼저입니다. 3.1에서 "기회주의적 범죄자와 과실 내부자는 예방으로 대응한다"고 판정한 근거가 여기에 있습니다 — 예방 비용이 압도적으로 싸기 때문입니다.

동시에 이 표는 한계도 보여줍니다. **표적형 공격자와 악의적 내부자에 대해서는 "단 하나의 통제"가 존재하지 않습니다.** 그래서 6부 전체가 탐지와 대응에 할애됩니다.

## 🔴 필수 구성 체크리스트

- [ ] ShopMini의 **위협 행위자 판정표**가 문서로 존재하고, "명시적 제외"한 행위자와 그 근거가 기록되어 있다
- [ ] 데이터 흐름도에 **DF1~DF8 · A1~A3 · L1~L2 전부**가 그려져 있고, 각 선이 어느 경계를 가로지르는지 표시되어 있다
- [ ] 다이어그램에 **데이터 저장소마다 어떤 데이터가 있는지**(원서 3단계) 적혀 있다 — RDS(회원·주문), uploads(업로드), 시크릿, 로그
- [ ] 다이어그램에 **스냅샷·백업·AMI 등 데이터 사본**이 별도 요소로 그려져 있다
- [ ] 관리자 접근 경로(A1~A3)가 **데이터 흐름과 분리된 경계(TB6)** 로 그려져 있다
- [ ] TB6이 **앱 운영·데이터 관리·보안 운영·감사**로 쪼개져 있고, **로그를 삭제할 수 있는 주체가 아무도 없다**
- [ ] 경계를 가로지르는 13개 흐름 각각에 **인증 수단이 명시**되어 있다("네트워크 위치"는 인증 수단이 아니다)
- [ ] IAM Access Analyzer 외부 접근 분석기가 **켜져 있고 결과가 0건**(의도된 것 제외)이다
- [ ] 계정 수준 **S3 퍼블릭 액세스 차단 4개 항목이 모두 활성**이다
- [ ] 모든 EC2 인스턴스의 `HttpTokens`가 **`required`** 이고 `HttpPutResponseHopLimit`이 **1**이다
- [ ] 워크로드 역할(`shopmini-app-role`)에 **`iam:` 로 시작하는 액션이 하나도 없다**
- [ ] `iam:PassRole` 권한에 **`iam:PassedToService` 조건과 구체적 역할 ARN**이 지정되어 있다
- [ ] 서드파티에 준 모든 크로스 계정 역할의 신뢰 정책에 **`sts:ExternalId` 조건**이 있다
- [ ] 신뢰 정책·리소스 정책에 **`"Principal": {"AWS": "*"}`** 가 하나도 없다
- [ ] Isolated-Data 서브넷 라우팅 테이블에 **IGW·NAT 경로가 없다**
- [ ] 모든 EBS·RDS 스냅샷이 **고객 관리형 KMS 키로 암호화**되어 있다(퍼블릭 공유 자체를 불가능하게)
- [ ] 3.2의 검증 명령 5종이 **분기마다 실행**되거나 Config 규칙으로 자동화되어 있다

## 다음 장 예고

이제 누가 공격하는지(3.1), 어디가 약한지(3.2~3.3), 어떤 경로가 실제로 쓰이는지(3.4~3.5)를 알게 됐습니다. 남은 질문은 **"그래서 어느 것부터, 얼마나 돈을 써서 막을 것인가"** 입니다.

4장에서는 **리스크 = 가능성 × 영향** 이라는 기본식으로 이 장에서 뽑은 위협들에 값을 매기고, 리스크를 수용·전가·완화·회피 중 무엇으로 처리할지 결정합니다. 그리고 통제의 강도를 결정하는 또 하나의 축 — **데이터 분류 체계** — 를 4단계(공개/내부/기밀/극비)로 세웁니다. 3.2의 다이어그램에 적어둔 "이 저장소에는 어떤 데이터가 있는가"가 여기서 등급으로 바뀌고, 등급마다 필수 통제가 정해집니다. 마지막으로 PCI DSS·GDPR·ISMS-P 같은 규제 요구사항을 **아키텍처 요구사항으로 번역하는 법**과, 컴플라이언스를 통과했는데도 뚫리는 체크박스 함정을 다룹니다.
