# 21장. 하이브리드 연결과 경계

> **이 장에서 다루는 것**
> - **Site-to-Site VPN** — 가상 프라이빗 게이트웨이/Transit Gateway + 고객 게이트웨이, 이중 터널, BGP vs 정적 라우팅, IKEv2와 터널 옵션 강화
> - **Direct Connect** ⚠️ — 전용 회선의 장점과 **기본적으로 암호화되지 않는다**는 사실, MACsec과 IPsec 오버레이, VIF 유형과 이중화 설계
> - **Transit Gateway 아키텍처** — 허브앤스포크, 라우팅 테이블 분리로 운영↔개발 격리 유지, 검사 VPC 삽입과 어플라이언스 모드
> - **VPC 피어링의 한계** ⚠️ — 전이적 라우팅 불가, 연결 수 폭증, CIDR 중복 불가. Transit Gateway 전환 판단 기준
> - **관리 접근(Administrative Access) 설계** 🔴 — 배스천 호스트 vs Session Manager. 왜 SSH/RDP 포트를 열지 않는 것이 정답인가
> - **Session Manager 구성** 🧪 — 인스턴스 프로파일, VPC 엔드포인트, 세션 로깅과 KMS 암호화, 포트 포워딩, 태그 기반 접근 제한
>
> **선행 지식**: 18장(VPC 설계·CIDR 계획), 19장(보안 그룹·이그레스 통제), 20장(엔드포인트·프라이빗 연결), 8장(역할과 인스턴스 프로파일)
> **난이도**: ★★★

18~20장에서 우리는 주소를 계획하고, 서브넷을 나누고, 규칙으로 트래픽을 통제하고, 엔드포인트로 인터넷 경로를 없앴습니다. 그 결과가 **닫힌 상자**입니다. 문제는 어떤 시스템도 완전히 닫힌 채로 운영되지 않는다는 점입니다. 온프레미스 결제 시스템이 ShopMini의 주문 API를 호출해야 하고, 무엇보다 **사람이 그 상자 안으로 들어가야 하는 순간**이 옵니다.

이 장은 그 "들어가는 구멍"을 다룹니다. **네트워크 대 네트워크**(21.1~21.4)와 **사람 대 시스템**(21.5~21.6), 두 종류입니다. 결론을 미리 말하면 이렇습니다. **첫 번째 구멍은 잘 설계해서 뚫되, 두 번째 구멍은 아예 뚫지 않는 것이 현재의 정답입니다.**

> 📖 *Practical Cloud Security* 2판 6장은 이 장의 주제를 정확히 같은 순서로 배치합니다. 애플리케이션 주위에 벽을 세우고 내부 감지 장치를 놓은 다음, "다른 시스템이나 관리자가 애플리케이션을 유지보수하기 위해 경계를 통과할 방법이 필요해진다"며 관리 접근(Allowing Administrative Access) 절을 시작합니다. 저자는 공격자가 할 수 있는 최악의 일 중 하나로 **관리 인터페이스에 대한 접근 — 예를 들어 데이터베이스 관리 인터페이스에 직접 접근해 뒷문으로 고객 데이터를 전부 빼내는 것** — 을 꼽습니다.

## 21.1 Site-to-Site VPN

### 구성 요소: 무엇과 무엇을 잇는가

AWS Site-to-Site VPN은 인터넷 위에 IPsec 터널을 만들어 온프레미스와 AWS를 잇습니다. 구성 요소는 네 개뿐입니다.

| 구성 요소 | 위치 | 역할 |
|---|---|---|
| 고객 게이트웨이(Customer Gateway, CGW) | 온프레미스 | 실제 라우터/방화벽을 AWS에 등록한 **논리적 표현**. 공인 IP 또는 인증서로 식별 |
| 가상 프라이빗 게이트웨이(Virtual Private Gateway, VGW) | AWS | VPC 하나에 붙는 VPN 종단점 |
| Transit Gateway(TGW) | AWS | 여러 VPC + 여러 VPN을 함께 수용하는 허브형 종단점 |
| VPN 연결(VPN Connection) | AWS | CGW ↔ (VGW 또는 TGW) 사이의 **터널 2개 묶음** |

**VGW를 쓸 것인가, TGW를 쓸 것인가.** VGW는 VPC 하나에만 붙으므로 VPC가 열 개면 VPN 연결도 온프레미스 라우터 설정도 열 벌입니다. TGW는 VPN 연결 하나로 TGW에 붙은 모든 VPC에 도달합니다. 판단 기준은 단순합니다. **온프레미스와 연결할 VPC가 하나뿐이고 앞으로도 하나일 것이 확실하면 VGW, 그 외에는 모두 TGW입니다.** VGW로 시작했다가 나중에 TGW로 옮기려면 온프레미스 라우터를 다시 손봐야 하므로, 처음부터 TGW가 대개 낫습니다.

### 터널이 두 개인 이유

AWS는 VPN 연결 하나에 **반드시 터널 두 개**를 제공합니다. 각 터널은 서로 다른 AZ의 서로 다른 AWS 종단 장비에 붙고 서로 다른 공인 IP를 가집니다. AWS가 그 종단 장비를 정기적으로 교체·업데이트하는 동안 해당 터널은 내려가므로, 터널 하나만 설정해 두면 그 순간이 곧 단절입니다. **터널 2개를 다 설정하는 것은 이중화의 최소 조건이지 추가 옵션이 아닙니다.**

흔한 오해가 하나 있습니다. 터널 2개는 **AWS 쪽 이중화**일 뿐입니다. 온프레미스 라우터가 한 대면 그 라우터나 회선이 죽는 순간 터널 2개가 함께 내려갑니다. 진짜 이중화는 **온프레미스 라우터 2대 × 터널 2개 = 총 4개 터널**입니다.

```
                        [ AWS ap-northeast-2 ]
온프레미스 라우터 A ──터널1──▶ ┐
                  └─터널2──▶ ├── Transit Gateway ──▶ VPC들
온프레미스 라우터 B ──터널3──▶ │
                  └─터널4──▶ ┘
   (라우터 A/B는 서로 다른 회선사업자·서로 다른 전원계통이어야 의미가 있다)
```

### BGP vs 정적 라우팅

| 항목 | 동적(BGP) | 정적 |
|---|---|---|
| 경로 학습 | 양쪽이 서로 광고 | 손으로 등록 |
| 장애 전환 | BGP 세션 끊기면 자동으로 다른 터널로 | **자동 전환 안 됨**(경로가 그대로 남음) |
| 온프레미스 요구사항 | BGP 지원 라우터, ASN 필요 | 없음 |
| 네트워크 추가 시 | 광고만 하면 반영 | 양쪽 라우팅 테이블 수정 |
| TGW ECMP | 가능 | 불가 |

**정적 라우팅은 이중화를 무력화합니다.** 정적 경로는 "이 대역은 이 VPN 연결로"라고만 말할 뿐, 특정 터널이 죽었다는 사실을 라우팅에 반영하지 못합니다. 터널 2개를 만들어 놓고도 장애 시 수동 개입이 필요해집니다. **가능하면 BGP를 쓰고**, 저가 장비 때문에 정적을 택할 수밖에 없다면 그 사실을 리스크 등록부에 올리십시오.

BGP를 쓸 때 실무에서 챙길 것은 셋입니다.

| 항목 | 내용 |
|---|---|
| 경로 요약(summarization) | 광고 경로 수에는 한도가 있다. `/24` 200개 대신 묶어서 광고. 한도 초과 시 BGP 세션이 내려가고 이는 전체 단절 |
| AS_PATH 프리펜딩 · MED | 터널 4개 중 주 경로를 온프레미스에서 결정 |
| 광고 대역 최소화 | AWS와 통신해야 하는 대역만 광고. 라우팅은 그 자체로 접근 통제(18.4) |

TGW에서는 **VPN ECMP**를 켤 수 있습니다. 터널당 대역폭이 약 1.25Gbps로 제한되므로 그 이상이 필요하면 VPN 연결을 여러 개 만들어 분산합니다. BGP가 전제이며 VGW에서는 불가능합니다.

### 🧪 터널 옵션 강화

기본값으로 만든 VPN은 구버전 IKE와 약한 DH 그룹까지 협상 가능한 상태로 열려 있을 수 있습니다. AWS는 협상 가능한 알고리즘 목록을 지정하게 해 주므로, **약한 것을 목록에서 제거하는 것**이 강화의 실체입니다. 먼저 고객 게이트웨이를 등록합니다.

```bash
aws ec2 create-customer-gateway \
  --profile awssec-lab --region ap-northeast-2 \
  --type ipsec.1 \
  --ip-address 203.0.113.10 \
  --bgp-asn 65010 \
  --device-name onprem-edge-rtr-a \
  --tag-specifications 'ResourceType=customer-gateway,Tags=[{Key=Project,Value=awssec-lab},{Key=Chapter,Value=ch21},{Key=AutoDelete,Value=true}]'
```

터널 옵션을 파일로 정의합니다. 두 터널 모두 동일한 강화 정책을 적용합니다.

```bash
aws ec2 create-vpn-connection \
  --profile awssec-lab --region ap-northeast-2 \
  --type ipsec.1 \
  --customer-gateway-id cgw-0123456789abcdef0 \
  --transit-gateway-id tgw-0123456789abcdef0 \
  --options file://vpn-options.json \
```

읽을 점 세 가지입니다.

- **`IKEVersions`를 `ikev2`만 남깁니다.** IKEv2는 재협상 시 세션 유지, MOBIKE, 더 나은 DoS 저항성을 제공합니다.
- **DH 그룹에서 14 미만을 제거합니다.** 위 예제는 ECP 384/521(그룹 20/21)만 허용했습니다. 온프레미스 장비가 지원하지 않으면 협상이 실패하므로, 상대 장비 지원 목록을 먼저 확인하고 교집합에서 가장 강한 것을 고르십시오.
- **`PreSharedKey`를 명시하지 않았습니다.** 지정하지 않으면 AWS가 생성합니다. IaC 저장소에 PSK를 하드코딩하는 것은 11.1에서 다룬 시크릿 사고의 전형입니다. 가능하면 **인증서 기반 인증**(`create-customer-gateway --certificate-arn`)이 더 낫습니다.

> 📖 *Practical Cloud Security* 2판 6장은 클라우드 제공자별 VPN 기능을 정리하면서, **"일부 산업 또는 규제 인증에서는 VPN 연결 생성을 로깅하도록 요구할 수 있으니, VPN 솔루션에서 연결 로그를 꺼낼 수 있는지 확인하라"** 고 못 박습니다. 위 예제의 `LogOptions`가 그 요구에 대한 AWS 측 대응입니다. VPN 연결 생성·수정 자체는 CloudTrail 관리 이벤트(`CreateVpnConnection`, `ModifyVpnTunnelOptions`)로 남습니다(29.2).

### VPN에 대한 원서의 경고

> 📖 *Practical Cloud Security* 1·2판 6장은 사이트 간 통신용 VPN을 두고 **"사이트 간 모든 통신이 TLS를 사용하고 가능한 곳에 IP 허용 목록이 적용된다면, 더 이상 사이트 간 VPN 사용을 권하지 않는다"** 고 밝히며 세 가지 이유를 듭니다. ① 사이트 간 VPN 설정은 TLS를 쓰는 것보다 일이 많다(보통 이중화된 방화벽 4대를 파라미터·자격 증명·라우팅까지 맞춰야 한다). ② **VPN은 터널에 들어가기 전 양 끝단에서는 데이터를 보호하지 못하므로**, 경계 안으로 들어온 공격자가 그 구간을 엿들을 수 있고, VPN이 있다는 이유로 안전하지 않은 프로토콜을 쓰게 되면 오히려 덜 안전해진다. ③ 사이트 간 VPN은 **입도가 너무 거칠다** — 한 네트워크(대개 거대한 사내망) 전체에 다른 네트워크(예: 관리 인터페이스) 접근을 허용해 버린다. 접근 통제는 네트워크 수준이 아니라 **관리 사용자 수준**에서 하는 편이 낫다.

세 번째 지적이 이 장 전체를 관통합니다. VPN을 뚫는 순간 "사내망에 있는 사람"과 "AWS 리소스에 접근할 자격이 있는 사람"이 같은 뜻이 되어 버립니다. 그것은 제로 트러스트의 정반대입니다(1.3).

실무의 결론은 이렇습니다. **하이브리드 연결(VPN/DX)은 애플리케이션 대 애플리케이션 트래픽을 위해 만들되, 그 위에서도 TLS를 종단 간으로 유지하고(23.5), 관리 접근은 별도의 신원 기반 경로로 처리합니다(21.5).** VPN이 열려 있다는 사실이 어떤 보안 그룹 규칙도 느슨하게 만들어서는 안 됩니다.

## 21.2 Direct Connect ⚠️

### 전용 회선이 주는 것과 주지 않는 것

Direct Connect(DX)는 DX 로케이션(통신사 데이터센터)에서 고객 라우터와 AWS 라우터를 **물리적 크로스커넥트**로 직접 연결합니다. 인터넷을 거치지 않으므로 다음을 얻습니다.

| 얻는 것 | 설명 |
|---|---|
| 일관된 지연 시간 | 인터넷 경로 변동에 좌우되지 않음 |
| 높고 예측 가능한 대역폭 | 1/10/100Gbps 급 전용 연결. VPN의 터널당 1.25Gbps 한계 없음 |
| 데이터 전송 비용 절감 | 대량 아웃바운드에서 인터넷 대비 단가 이점 |
| 인터넷 노출 감소 | 트래픽이 공중망을 통과하지 않음 |

그리고 **얻지 못하는 것이 하나 있습니다. 암호화입니다.**

### ⚠️ 사고 시나리오: "전용선이니까 평문으로 보내도 됩니다"

**사고.** 온프레미스 결제 시스템과 ShopMini 백엔드를 10Gbps DX로 연결한 뒤, 두 시스템 사이의 내부 API를 HTTP(평문)로, 배치 작업의 DB 연결을 TLS 없이 3306으로 구성했습니다. "전용 회선이라 외부에 노출되지 않는다"는 것이 근거였습니다. 이후 보안 심사에서 이 구간의 트래픽 보호 수단을 제시하지 못해 지적을 받았고, 카드 데이터가 이 경로를 지나고 있었기 때문에 컴플라이언스 범위 전체가 흔들렸습니다.

**원인.** "전용(dedicated)"을 "격리(isolated)"로, 다시 "암호화(encrypted)"로 잘못 등치한 것입니다. DX는 **레이어 2 전용 경로**일 뿐이며 AWS는 기본 암호화를 제공하지 않습니다. 그 경로에는 최소한 ① 고객 라우터 ↔ DX 로케이션 크로스커넥트 배선(통신사 시설, 공용 랙·패치 패널) ② 파트너 호스팅 연결을 쓰는 경우 파트너 사업자의 전송망 ③ VIF·VLAN 태그 오설정으로 인한 오라우팅 가능성이 존재합니다. 이 구간들은 "인터넷이 아니다"일 뿐 "내가 통제한다"가 아닙니다.

> 📖 *Practical Cloud Security* 2판 6장 "Encryption in Motion"이 이 논점을 정면으로 다룹니다. 저자는 **"내가 통제하는 네트워크를 지나는 트래픽을 암호화하는 것이 좋은 생각인지에 대해 일각에서 논쟁이 있다"** 고 소개하며, 그 논쟁의 암묵적 전제는 "공격자가 경계를 뚫고 들어와 트래픽을 볼 가능성이 낮다"는 것인데 **현실에서 침해의 최상위 원인 중 하나가 웹 애플리케이션 공격이며 그 결과 공격자는 이미 경계 안쪽의 애플리케이션 서버에 있다**고 반박합니다. 결론은 **"공개되면 피해가 되는 정보를 담은 모든 네트워크 트래픽을 암호화하라"** 이며, 나아가 클라우드에서는 프론트엔드뿐 아니라 **물리적·가상 네트워크 스위치를 건너는 모든 통신에 TLS를 쓰라**고 권합니다. DX 회선은 정의상 물리 스위치를 건너는 통신입니다.

**올바른 구성.** 세 가지 층을 순서대로 적용합니다.

| 순위 | 수단 | 보호 범위 | 비고 |
|---|---|---|---|
| 1 | **애플리케이션 TLS** | 종단 간(앱 ↔ 앱) | 원서가 최우선으로 권하는 것. 다른 두 수단으로 대체 불가 |
| 2 | **MACsec (IEEE 802.1AE)** | 고객 라우터 ↔ AWS DX 라우터 **물리 링크 구간만** | 지원 로케이션의 전용(Dedicated) 연결에서만. 양쪽 장비 모두 지원 필요 |
| 3 | **DX 위 IPsec VPN 오버레이** | 고객 게이트웨이 ↔ AWS VPN 종단점 | 터널당 약 1.25Gbps 한계가 다시 생김. 필요 시 다중 터널 + TGW ECMP |

**MACsec의 한계를 정확히 이해하십시오.** MACsec은 **점대점 링크 암호화**로, 고객 라우터와 AWS DX 장비 사이의 그 한 구간만 보호합니다. 그 지점을 지난 AWS 내부 경로도, 고객 라우터 이전의 사내망 구간도 보호하지 않습니다. **MACsec은 종단 간 암호화가 아니며, "이제 평문 프로토콜을 써도 된다"는 근거가 될 수 없습니다.**

```bash
# MACsec CKN/CAK를 Secrets Manager에 저장한 뒤 연결에 연동
aws directconnect associate-mac-sec-key \
  --profile awssec-lab --region ap-northeast-2 \
  --connection-id dxcon-fgexample \
  --secret-arn arn:aws:secretsmanager:ap-northeast-2:111122223333:secret:dx/macsec-shopmini

# 암호화되지 않은 트래픽 자체를 거부하도록 전환 (점검 후 적용)
aws directconnect update-connection \
  --profile awssec-lab --region ap-northeast-2 \
  --connection-id dxcon-fgexample \
  --encryption-mode must_encrypt
```

⚠️ `must_encrypt`로 전환하면 MACsec 세션이 성립하지 않는 동안 링크가 **통신 불가**가 됩니다. `should_encrypt`로 검증한 뒤 유지보수 시간에 전환하십시오.

### 가상 인터페이스(VIF) 유형

물리 연결 위에 논리 인터페이스(VIF)를 얹어야 통신이 시작됩니다. 세 종류이고 **보안 관점의 성격이 완전히 다릅니다.**

| VIF 유형 | 도달 대상 | 종단점 | 보안 관점 |
|---|---|---|---|
| 프라이빗(Private) VIF | VPC의 사설 IP | VGW 또는 DX 게이트웨이 | VIF 하나당 VGW 하나. VPC가 늘면 VIF도 늘어남 |
| 퍼블릭(Public) VIF | AWS **퍼블릭 IP 범위**(S3, DynamoDB 등 공개 엔드포인트) | 없음(BGP로 AWS 공인 대역 수신) | ⚠️ **AWS의 모든 퍼블릭 서비스 대역을 수신**. 사실상 "인터넷 없는 인터넷 경로". 프리픽스 필터 필수 |
| 전송(Transit) VIF | DX 게이트웨이를 통해 **Transit Gateway** | DX 게이트웨이 → TGW | 다중 VPC·다중 리전 확장의 표준. 21.3과 결합 |

**⚠️ 퍼블릭 VIF의 함정.** 퍼블릭 VIF는 BGP로 AWS의 공인 IP 프리픽스를 대량 수신합니다. 온프레미스 라우터가 이를 그대로 사내망에 재배포하면 사내 어디서든 AWS 퍼블릭 서비스로 나가는 새 경로가 생기고, 기존의 인터넷 프록시·이그레스 필터(19.6)를 우회하게 됩니다. **수신 프리픽스를 필터링하고 재배포 범위를 명시적으로 제한하십시오.**

VPC가 둘 이상이거나 늘어날 가능성이 있으면 **전송 VIF + DX 게이트웨이 + TGW**가 표준입니다. DX 게이트웨이는 여러 리전의 VGW/TGW를 하나의 DX 연결에 묶어 주므로, 서울과 도쿄 리전을 같은 회선으로 커버할 수 있습니다.

```bash
aws directconnect create-transit-virtual-interface \
  --profile awssec-lab --region ap-northeast-2 \
  --connection-id dxcon-fgexample \
  --new-transit-virtual-interface \
    'virtualInterfaceName=shopmini-transit-vif,vlan=101,asn=65010,mtu=9001,directConnectGatewayId=<dxgw-id>,addressFamily=ipv4,customerAddress=192.168.100.2/30,amazonAddress=192.168.100.1/30'
```

### 🔴 이중화 설계 — 회선 하나는 회선이 아니다

DX는 물리 회선입니다. 굴착기 한 대가 케이블을 끊으면 끝입니다. AWS는 복원력 모델을 세 단계로 제시합니다.

| 모델 | 구성 | 감당 가능한 장애 |
|---|---|---|
| 개발/테스트 | 단일 로케이션, 단일 디바이스에 2개 연결 | 회선(포트) 장애만 |
| 고복원력(High Resiliency) | **2개 로케이션**, 각 1개 연결 | 로케이션 전체 장애 |
| 최대 복원력(Maximum Resiliency) | **2개 로케이션 × 각 2개 디바이스** | 로케이션 + 디바이스 동시 장애 |

여기에 더해 **Site-to-Site VPN을 백업 경로로 항상 함께 구성하십시오.** DX와 VPN이 같은 VGW/TGW에 붙어 동일 프리픽스를 광고하면 DX 경로가 우선되고, DX가 끊어지면 VPN으로 자동 전환됩니다. 비용은 VPN 시간당 요금 수준이고, 얻는 것은 "전용선이 끊긴 날에도 서비스가 산다"는 결과입니다.

⚠️ 단, 백업 VPN의 대역폭은 DX의 몇 분의 일입니다. **전환 시 어떤 트래픽을 살리고 어떤 트래픽을 죽일지**(예: 배치 복제는 중단, 결제 API만 유지)를 미리 정해 두지 않으면, 전환된 순간 좁아진 관을 모두가 나눠 쓰다가 전부 느려집니다.

## 21.3 Transit Gateway 아키텍처

### 허브앤스포크가 해결하는 것

Transit Gateway는 리전 단위의 라우팅 허브입니다. VPC, VPN 연결, DX 게이트웨이, 다른 리전의 TGW(피어링)를 **연결(Attachment)** 로 붙이고, TGW의 **라우팅 테이블**이 그들 사이의 통신 가능 여부를 결정합니다. 핵심은 뒷문장입니다. **TGW는 "다 붙였으니 다 통한다"가 아닙니다.** 라우팅 테이블을 어떻게 나누느냐가 곧 격리 설계이고, 이 점이 VPC 피어링과의 결정적 차이입니다(21.4).

### 연결(Association)과 전파(Propagation)

- **연결(Association)**: "이 어태치먼트에서 나가는 트래픽은 **어느 라우팅 테이블을 참조해** 목적지를 찾는가." 어태치먼트 하나는 라우팅 테이블 **하나에만** 연결됩니다.
- **전파(Propagation)**: "이 어태치먼트가 가진 대역을 **어느 라우팅 테이블에 광고하는가.**" 하나의 어태치먼트를 여러 테이블에 전파할 수 있습니다.

이 비대칭이 격리의 도구입니다. 운영·개발 VPC는 각각 자기 라우팅 테이블에 연결하고, 온프레미스 대역은 두 테이블 모두에 전파합니다. 반대로 운영 VPC 대역은 개발 라우팅 테이블에 전파하지 않습니다. 그러면 **개발은 온프레미스와 통신할 수 있지만 운영과는 통신할 수 없습니다.**

### 🔴 라우팅 도메인 분리 설계

ShopMini 조직의 목표 구성입니다.

```
                              [ 온프레미스 DC 172.16.0.0/16 ]
                                    │ DX(전송 VIF) + 백업 VPN
                                    ▼
   ┌──────────────────────────── Transit Gateway (네트워크 계정, RAM 공유) ────────────────────────────┐
   │                                                                                                  │
   │   RT-PROD                    RT-DEV                     RT-SHARED             RT-INSPECTION       │
   │   ├ assoc: prod-vpc          ├ assoc: dev-vpc           ├ assoc: shared-vpc   ├ assoc: insp-vpc   │
   │   ├ prop:  onprem            ├ prop:  onprem            ├ prop:  prod,dev,    ├ prop:  전체        │
   │   ├ prop:  shared            ├ prop:  shared            │        onprem       │                   │
   │   └ prop:  dev 전파 안 함     └ prop:  prod 전파 안 함    └                     └                   │
   │                                                                                                  │
   └───┬──────────────────┬──────────────────────┬───────────────────────┬─────────────────────────────┘
       │                  │                      │                       │
  prod-vpc            dev-vpc              shared-vpc              inspection-vpc
  10.20.0.0/16       10.30.0.0/16          10.40.0.0/16            10.10.0.0/16
  (111122223333)     (555555555555)        (공유 서비스)            (Network Firewall / GWLB)
```

**설계 원칙 네 가지입니다.**

**1. 기본 라우팅 테이블 자동 연결·전파를 끄십시오.** `DefaultRouteTableAssociation`과 `DefaultRouteTablePropagation`을 `disable`로 두지 않으면, 나중에 누군가 VPC를 붙이는 순간 **자동으로 기본 라우팅 테이블에 연결·전파되어 모든 것과 통신 가능해집니다.** 격리 설계가 새 어태치먼트 하나로 무너집니다.

```bash
aws ec2 create-transit-gateway \
  --profile awssec-lab --region ap-northeast-2 \
  --description "ShopMini hub" \
  --options 'AmazonSideAsn=64512,AutoAcceptSharedAttachments=disable,DefaultRouteTableAssociation=disable,DefaultRouteTablePropagation=disable,DnsSupport=enable,VpnEcmpSupport=enable,MulticastSupport=disable' \
  --tag-specifications 'ResourceType=transit-gateway,Tags=[{Key=Project,Value=awssec-lab},{Key=Chapter,Value=ch21},{Key=AutoDelete,Value=true}]'
```

`AutoAcceptSharedAttachments=disable`도 함께 보십시오. `enable`이면 TGW를 공유받은 계정이 **네트워크 팀 승인 없이** 자기 VPC를 붙일 수 있습니다. 수동 수락이 변경 통제의 한 지점입니다.

**2. 환경별 라우팅 테이블을 만들고 명시적으로 연결·전파하십시오.**

```bash
# 운영용 라우팅 테이블 생성
aws ec2 create-transit-gateway-route-table \
  --profile awssec-lab --region ap-northeast-2 \
  --transit-gateway-id tgw-0123456789abcdef0 \
  --tag-specifications 'ResourceType=transit-gateway-route-table,Tags=[{Key=Name,Value=RT-PROD},{Key=Project,Value=awssec-lab}]'

# 운영 VPC 어태치먼트를 RT-PROD에 연결(association)
aws ec2 associate-transit-gateway-route-table \
  --profile awssec-lab --region ap-northeast-2 \
  --transit-gateway-route-table-id tgw-rtb-prod0000000000000 \
  --transit-gateway-attachment-id tgw-attach-prod000000000000

# 온프레미스(VPN/DX) 어태치먼트 대역을 RT-PROD에 전파(propagation)
aws ec2 enable-transit-gateway-route-table-propagation \
  --profile awssec-lab --region ap-northeast-2 \
  --transit-gateway-route-table-id tgw-rtb-prod0000000000000 \
  --transit-gateway-attachment-id tgw-attach-onprem00000000

# 개발 대역으로 향하는 트래픽은 블랙홀로 명시 차단
aws ec2 create-transit-gateway-route \
  --profile awssec-lab --region ap-northeast-2 \
  --transit-gateway-route-table-id tgw-rtb-prod0000000000000 \
  --destination-cidr-block 10.30.0.0/16 \
  --blackhole
```

마지막 명령이 중요합니다. 전파하지 않으면 경로가 없어 통신이 안 되는 것은 맞지만, **블랙홀 경로를 명시하면 "이 통신은 의도적으로 금지되었다"는 사실이 라우팅 테이블에 문서로 남습니다.** 누군가 나중에 실수로 전파를 켜도 더 구체적인 블랙홀 경로가 차단을 유지합니다.

**3. 운영↔개발 직접 통신 차단이 이 구조의 존재 이유입니다.** 개발 계정은 통제가 느슨하고 실험적 코드가 돌며 개발자 다수가 넓은 권한을 가집니다(28.6). 그 환경에서 침해가 나도 **네트워크 경로가 없으면 폭발 반경이 개발 계정에서 멈춥니다**(1.4). 공유가 필요한 DNS·아티팩트 저장소·CI 러너는 `shared-vpc`를 경유하면 됩니다.

**4. TGW는 네트워크 계정에 두고 RAM으로 공유하십시오.** 운영 계정에 두면 운영 계정 관리자가 라우팅 도메인 전체를 바꿀 수 있습니다. 네트워크 계정에 두면 각 계정은 **자기 VPC를 붙일 수만 있고 라우팅 테이블은 건드릴 수 없습니다.**

```bash
aws ram create-resource-share \
  --profile awssec-lab --region ap-northeast-2 \
  --name shopmini-tgw-share \
  --resource-arns arn:aws:ec2:ap-northeast-2:111122223333:transit-gateway/tgw-0123456789abcdef0 \
  --principals arn:aws:organizations::123456789012:organization/o-exampleorgid \
  --no-allow-external-principals
```

`--no-allow-external-principals`로 조직 외부 계정 공유를 원천 차단합니다.

### 검사 VPC 삽입 패턴과 어플라이언스 모드

19.5에서 다룬 AWS Network Firewall이나 서드파티 IPS 어플라이언스를 **모든 VPC 간·온프레미스 간 트래픽 경로에 강제로 통과시키는** 패턴이 검사 VPC(inspection VPC)입니다. 각 스포크 라우팅 테이블의 기본 경로(`0.0.0.0/0`)를 검사 VPC 어태치먼트로 보내고, 방화벽을 거친 트래픽이 다시 TGW로 돌아와 최종 목적지로 향합니다.

```
prod-vpc ──▶ TGW(RT-PROD: 0.0.0.0/0 → insp-attach) ──▶ inspection-vpc
                                                          │ Network Firewall 엔드포인트
                                                          ▼ (검사 통과)
                                                       TGW(RT-INSPECTION) ──▶ dev/shared/onprem
```

⚠️ **여기서 반드시 어플라이언스 모드를 켜야 합니다.** 검사 VPC처럼 트래픽이 들어왔다 나가는 구조에서는 **왕복 패킷이 서로 다른 AZ의 방화벽 엔드포인트로 갈 수 있습니다.** 상태 저장 방화벽은 요청만 보고 응답을 못 보거나 그 반대가 되어 정상 트래픽을 비대칭 흐름으로 판단해 폐기합니다. 증상은 "가끔 연결이 끊긴다"이고 원인 파악에 며칠이 걸립니다.

```bash
aws ec2 create-transit-gateway-vpc-attachment \
  --profile awssec-lab --region ap-northeast-2 \
  --transit-gateway-id tgw-0123456789abcdef0 \
  --vpc-id vpc-inspection0000000 \
  --subnet-ids subnet-insp2a00000000 subnet-insp2c00000000 \
  --options ApplianceModeSupport=enable,DnsSupport=enable,Ipv6Support=disable
```

`ApplianceModeSupport=enable`은 **검사 VPC 어태치먼트에** 설정합니다. TGW가 흐름 해시를 기준으로 동일 흐름의 양방향 패킷을 같은 AZ로 고정해 줍니다.

한 가지 더. **TGW 어태치먼트용 서브넷은 작게, 전용으로 만드십시오.** `/28` 정도를 AZ마다 두고 다른 리소스를 배치하지 않습니다. 워크로드와 섞으면 그 서브넷의 라우팅 테이블을 바꿀 때 TGW 경로까지 영향을 받습니다.

## 21.4 VPC 피어링의 한계 ⚠️

### ⚠️ 사고 시나리오: 개발 서버 하나가 운영 DB에 닿았다

**사고.** 조직이 성장하며 VPC가 7개가 되었고, 필요할 때마다 피어링을 추가해 총 15개 연결이 운영 중이었습니다. 어느 날 개발 VPC의 EC2 인스턴스가 취약한 의존성을 통해 침해되었고, 공격자는 내부 스캔으로 운영 VPC 데이터 서브넷의 RDS 3306 포트에 도달했습니다. 조사 결과 두 가지가 겹쳐 있었습니다. ① 개발-운영 사이에 **1년 전 일회성 데이터 마이그레이션을 위해 만든 피어링**과 라우팅 경로가 그대로 살아 있었고 ② RDS 보안 그룹이 SG 참조가 아니라 `10.0.0.0/8` 광역 CIDR을 허용하고 있었습니다(19.2의 안티패턴).

**원인.** VPC 피어링은 **"연결되었다"와 "격리되었다" 사이에 중간 단계가 없습니다.** 라우팅 테이블에 경로를 넣는 순간 두 VPC는 같은 네트워크가 되고, 그 위에서 격리를 표현할 수 있는 계층은 보안 그룹뿐입니다. 보안 그룹은 리소스 수만큼 존재하고 각각이 실수 가능한 지점이므로, **의도를 한곳에 표현할 방법이 없다는 것**이 근본 문제입니다. 게다가 15개가 되면 15곳의 라우팅 항목을 사람이 추적해야 하고, "이 피어링은 왜 있는가"를 아무도 답하지 못하는 상태가 됩니다.

**올바른 구성.** 21.3의 TGW 라우팅 도메인 분리입니다. 격리 의도가 **네트워크 계정의 라우팅 테이블 한 곳**에 블랙홀 경로로 표현되고, 변경은 네트워크 팀만 할 수 있습니다.

### 피어링의 네 가지 구조적 한계

**1. 전이적 라우팅이 되지 않는다.**

> 📖 *AWS Security Cookbook* 5장은 VPC 피어링을 설명하며 **"AWS VPC에서 전이적 피어링(transitive peering)은 현재 지원되지 않는다. 모든 VPC는 필요한 다른 모든 VPC와 스타 토폴로지처럼 각각 피어링되어야 한다"** 고 명시하고, 이어서 **"VPC 피어링으로 다수의 점대점 연결을 관리하는 오버헤드를 피하기 위해 AWS Transit Gateway를 사용해 모든 VPC와 온프레미스 네트워크를 단일 게이트웨이에 연결할 수 있다"** 고 대안을 제시합니다. 이 장의 21.3이 정확히 그 대안의 구현입니다.

A–B와 B–C가 피어링되어도 A는 C에 도달할 수 없습니다. "B에 프록시를 두자"는 발상이 나오는데, 그 프록시는 **라우팅 통제를 우회하는 애플리케이션 계층 구멍**입니다. 같은 이유로 **엣지 투 엣지 라우팅**도 불가능해, 상대 VPC의 인터넷 게이트웨이·NAT 게이트웨이·VPC 엔드포인트(20장)·VPN을 빌려 쓸 수 없습니다. "중앙 NAT VPC를 공유하자"는 설계는 TGW가 필요합니다.

**2. 연결 수가 제곱으로 늘어난다.** 완전 연결이 필요한 VPC가 n개면 피어링 연결은 **n(n-1)/2** 개입니다.

| VPC 수 | 피어링 연결 수 | 관리할 라우팅 항목(대략) |
|---|---|---|
| 4 | 6 | 12 |
| 7 | 21 | 42 |
| 10 | 45 | 90 |
| 15 | 105 | 210 |
| 20 | 190 | 380 |

TGW에서는 어태치먼트가 n개이고 라우팅 테이블은 도메인 수만큼입니다. VPC 20개면 피어링은 190개 연결, TGW는 20개 어태치먼트입니다.

**3. CIDR이 겹치면 아예 불가능하다.** 피어링은 중복 CIDR을 지원하지 않고, TGW도 중복 대역을 라우팅할 수 없습니다(NAT나 PrivateLink 같은 우회 수단이 필요합니다). 18.2에서 조직 전체 IP 계획을 먼저 그리라고 강조한 이유가 여기서 청구서로 돌아옵니다. **인수합병으로 두 조직의 `10.0.0.0/16`이 만나면 해결책은 재주소화(re-addressing)뿐입니다.**

**4. 보안 그룹 참조에 제약이 있다.** 19.2에서 "CIDR 대신 SG를 참조하라"고 했지만 그 참조가 언제나 되는 것은 아닙니다.

| 경로 | 보안 그룹 참조 |
|---|---|
| 동일 VPC 내 | 가능 |
| 동일 리전 VPC 피어링 | 가능 |
| **리전 간(inter-region) VPC 피어링** | **불가** — CIDR로 쓸 수밖에 없음 |
| Transit Gateway 경유 | 리전·구성에 따라 다름. 설계 시점에 확인 필요 |

> 💡 **원서 이후 변경** — 전통적으로 보안 그룹 참조는 동일 리전 VPC 피어링에서만 동작했고, TGW 경유 통신에서는 CIDR 기반 규칙을 쓸 수밖에 없었습니다. 이후 동일 리전 TGW 연결에 대한 보안 그룹 참조 지원이 추가되었으므로, 설계 시점에 해당 리전·구성에서의 지원 여부를 최신 문서로 반드시 확인하십시오. 지원되지 않는 구간에서는 **CIDR 규칙을 쓰되 `/8`이 아니라 해당 티어 서브넷 단위(`10.30.10.0/24`)까지 좁히는 것**이 차선입니다.

### Transit Gateway 전환 판단 기준

피어링이 언제나 나쁜 것은 아닙니다.

| 조건 | 권장 |
|---|---|
| VPC 2~3개, 완전 연결 불필요, 향후 확장 계획 없음 | **피어링** — 단순하고 시간당 요금 없음 |
| 초저지연·초고대역폭이 필요한 특정 두 VPC 간 경로 | **피어링** — TGW는 홉이 하나 늘고 어태치먼트 처리 한도가 있음 |
| VPC 4개 이상 또는 매년 증가 | **TGW** |
| 온프레미스(VPN/DX) 연결이 필요 | **TGW** |
| **환경 간 격리를 라우팅으로 강제해야 함** | **TGW** — 피어링으로는 표현 불가 |
| 중앙 검사(방화벽/IPS) 삽입 필요 | **TGW** |
| 다계정 구조에서 네트워크 통제를 중앙화해야 함 | **TGW** + RAM |

비용도 정직하게 봅시다. 피어링은 시간당 요금 없이 데이터 전송 비용만 드는 반면 TGW는 **어태치먼트당 시간 요금 + GB당 데이터 처리 요금**이 붙어, 트래픽이 많으면 더 비쌉니다. 그러나 **"라우팅 도메인으로 격리를 표현할 수 있다"는 통제 가치**가 대개 그 비용을 정당화합니다. 15개 피어링을 추적하다 하나를 놓치는 비용이 훨씬 큽니다.

절충안도 유효합니다. **환경 간 통신은 TGW로 통제하고, 동일 환경 내 대용량 경로만 피어링으로 직결**하는 방식입니다. 단, 그 피어링마다 "왜 존재하는가"를 태그와 문서로 남기고 정기 검토 대상에 넣으십시오.

## 21.5 관리 접근(Administrative Access) 설계 🔴

### 원서가 그린 문제

지금까지 만든 것은 애플리케이션 트래픽을 위한 경로입니다. 이제 **사람**이 들어갈 차례인데, 원서는 이 장면에서 먼저 단서를 하나 답니다.

> 📖 *Practical Cloud Security* 1·2판 6장은 배스천과 VPN 논의를 시작하기 직전에 이런 단서를 답니다. **"서버에서 명령을 실행할 방법(예: AWS Systems Manager Run Command나 `kubectl exec`)이 있거나, 나오는 로그로 항상 문제를 진단하고 이상이 있는 컴포넌트를 새 버전으로 교체할 수 있다면, 관리자는 경계 안으로 들어갈 필요가 없을지도 모른다. 경계 뒤로 들어가지 않고 일상 운영을 할 수 있다면 그것이 이상적이지만, 많은 애플리케이션이 그렇게 설계되어 있지 않다."**

이 문단이 21.5의 전부라고 해도 과언이 아닙니다. **최선의 관리 접근 경로는 존재하지 않는 경로입니다.** 22.8에서 다룰 불변 인프라 — 로그로 진단하고 문제가 있으면 인스턴스를 교체한다 — 가 궁극의 답입니다. 하지만 원서 자신이 인정하듯 많은 애플리케이션이 그렇게 설계되어 있지 않고, 그래서 남는 선택지가 배스천과 VPN이었습니다.

### 원서의 배스천 호스트 서술

> 📖 *Practical Cloud Security* 2판 6장은 배스천 호스트(점프 호스트)를 **"덜 신뢰되는 네트워크(예: 인터넷)에서 접근 가능한 관리 접근용 시스템으로, 내부 네트워크로의 모든 통신이 배스천 호스트를 통과하도록 네트워크를 구성한다"** 고 정의하고 세 가지 보안 속성을 듭니다. ① **공격 표면을 줄인다** — 다른 머신들이 뒤에 숨는 단일 목적의 강화된 호스트이므로. ② **세션 기록이 가능하다** — 내부자 공격, 탈취된 자격 증명 사용, 공격자가 원격 접근 트로이목마(RAT)로 관리자 워크스테이션을 조종하는 것을 잡아내기 위해 기록을 표본 점검할 수 있음. ③ **프로토콜 전환(protocol shift)** — RDP로 들어와 HTTPS로 나가는 구조는 공격자가 배스천과 목적지 애플리케이션 **양쪽 모두를 침해해야** 하도록 만든다.
>
> 저자의 최종 권고는 이렇습니다. **"세션 기록이나 프로토콜 전환의 고급 기능이 환경에 유용하거나 클라이언트-사이트 VPN이 어떤 이유로 적합하지 않다면 배스천 호스트를 권한다. 그렇지 않다면, 관리 접근에는 서비스로 제공되는 클라이언트-사이트 VPN을 권한다. 관리할 것이 하나 줄어들기 때문이다."** 2판은 여기에 **특권 접근 관리(PAM) 도구의 "인라인 모드"** — 세션 기록·모니터링·종료·특정 명령 차단 — 가 배스천과 유사한 기능을 한다는 서술을 추가했습니다(9.5).

원서의 논지는 세 가지 요구사항으로 압축됩니다. **① 공격 표면 축소 ② 세션 기록 ③ 관리 경로의 자격 증명을 일반 사용자 경로와 분리.** 배스천과 VPN은 이 요구를 부분적으로 만족시키는 **당시의 수단**이었습니다.

### 💡 그런데 AWS에서는 셋 다 인프라 없이 얻을 수 있습니다

> 💡 **원서 이후 변경** — 원서 3권은 배스천/VPN 서술을 유지하며, 2판은 Run Command를 "경계 안으로 들어가지 않는 방법"의 예로 언급하는 데 그칩니다. **현재 AWS 환경에서 관리 접근의 표준 답은 배스천 호스트도 클라이언트-사이트 VPN도 아닌 SSM Session Manager입니다.** 원서가 요구한 세 가지(공격 표면 축소·세션 기록·관리 경로 분리)를 Session Manager가 **더 강하게** 만족시키기 때문입니다.

| 비교 항목 | 배스천 호스트 | SSM Session Manager |
|---|---|---|
| **인바운드 포트** | 22/3389를 인터넷 또는 사내망에 개방 | **0개.** 인바운드 규칙 자체가 필요 없음 |
| **퍼블릭 IP** | 대개 필요 | 불필요. 인터넷 게이트웨이 없어도 동작(VPC 엔드포인트) |
| **연결 방향** | 외부 → 내부 (인바운드) | **에이전트가 내부 → SSM으로 아웃바운드 연결** |
| **인증** | SSH 키 / 로컬 계정 / AD | **IAM.** 역할·세션·조건 키 전부 적용 |
| **MFA 연계** | 별도 구축(PAM, SSH CA 등) | `aws:MultiFactorAuthPresent` 조건 키 한 줄 |
| **자격 증명 관리** | 키 페어 배포·회수(22.2의 난제) | **키 자체가 없음.** 임시 자격 증명만 |
| **감사** | 배스천 OS 로그를 직접 수집·보존 | **CloudTrail에 `StartSession` 기록** + 세션 내용 S3/CloudWatch Logs 스트리밍 |
| **세션 기록** | 별도 도구(PAM 인라인 모드 등) 필요 | 내장. KMS 암호화 지원 |
| **가용성** | 인스턴스 장애 = 접근 불가 | AWS 관리형 서비스 |
| **패치·강화 책임** | 배스천 OS를 직접 패치·강화·모니터링 | 에이전트만 최신 유지(Patch Manager로 자동화) |
| **대상 제한** | SG/서브넷 수준 | **IAM 정책 + 인스턴스 태그**(`ssm:resourceTag/*`) |
| **접근 즉시 회수** | 키 회수 어려움, 세션은 계속 살아 있음 | IAM 정책 변경으로 즉시 차단, `TerminateSession`으로 강제 종료 |
| **비용** | 인스턴스 + 패치 + 모니터링 상시 비용 | 세션 로깅 저장 비용 외 추가 요금 없음 |

원서가 배스천의 장점으로 꼽은 **프로토콜 전환**은 Session Manager에서 더 극적으로 일어납니다. 관리자는 SSH 프로토콜을 쓰지 않습니다. **HTTPS로 AWS API를 호출하고, 인증은 SigV4로, 인가는 IAM으로 이뤄지며, 그 결과 WebSocket 데이터 채널이 열립니다.** 네트워크 계층에서 보면 SSH 트래픽이라는 것이 존재하지 않습니다. **공격 표면 축소**도 한 걸음 더 나갑니다. 배스천은 표면을 하나로 줄인 것이지 없앤 것이 아니고, 그 하나는 여전히 도달 가능한 22번 포트이며 스캐너가 몇 분 안에 찾아냅니다(19.3). Session Manager는 **그 하나마저 없앱니다.**

### 🔴 반드시 이렇게 구성하라

| # | 반드시 이렇게 하라 | 안 하면 |
|---|---|---|
| 1 | **어떤 보안 그룹에도 22/3389 인바운드 규칙을 두지 마라** | 개방된 SSH는 노출 즉시 자격 증명 대입 공격의 표적. 침해되면 인스턴스 IAM 역할이 공격자의 것이 되고 역할 권한 범위 전체가 폭발 반경이 된다(8.2). 사내망에만 열어도 "사이트 간 VPN은 입도가 너무 거칠다"는 21.1의 지적이 그대로 적용된다 |
| 2 | **관리 인터페이스 보호에 사이트 간 VPN을 쓰지 마라** (원서 1판 "쓰여서는 안 된다" / 2판 "보통은 쓰이지 않아야 한다") | 네트워크 위치 = 권한이 되어, 침해된 사내 PC 한 대가 곧바로 운영 DB 관리 인터페이스에 도달한다 |
| 3 | **접근을 IAM으로, 대상을 태그로 제한하라** — "누가 어느 인스턴스에"를 정책 한 곳에서 표현 | 인스턴스 100대는 곧 100개의 접근 통제 지점이고, 어느 하나에서 실수가 난다 |
| 4 | **모든 세션을 기록하고 로그 아카이브 계정(`777788889999`)에 보존하라**(29.9) | 내부자 행위, 탈취된 자격 증명 사용, RAT로 조종되는 관리자 워크스테이션을 사후에도 판별할 수 없다 |
| 5 | **남는 예외를 브레이크 글래스 절차로 정의·문서화하라**(32.4) | 에이전트가 죽거나 부팅이 멈춘 순간 누군가 임시 배스천을 열고, 그것이 영구 구성이 된다 |

5번은 특히 실무적입니다. Session Manager로 해결되지 않는 상황 — SSM 에이전트 중단, 부팅 실패 — 은 반드시 생깁니다. EC2 Instance Connect Endpoint를 쓰든 승인된 배스천을 한시적으로 기동하든, **그 사용이 즉시 알람으로 이어지고 사후 검토 대상이 되어야 합니다.**

> 💡 **배스천이 여전히 정답인 경우** — 원서가 배스천을 권하는 조건(세션 기록과 프로토콜 전환이 절실한 고보안 환경)에서 배스천이 완전히 사라지지는 않습니다. 다만 오늘날의 구현은 "인터넷에 22번 포트를 연 EC2"가 아니라 **Session Manager로 접근하는 관리 전용 인스턴스** 또는 PAM 제품의 인라인 모드입니다. 배스천의 *기능*은 남고 *네트워크 노출*은 사라집니다.

## 21.6 Session Manager 구성 🧪

### 준비물 네 가지

| 요소 | 내용 | 확인 방법 |

### 🧪 2단계 — VPC 엔드포인트

완전 격리 서브넷(20.4)에는 NAT 게이트웨이도 인터넷 게이트웨이도 없습니다. 그럼에도 Session Manager가 동작하려면 인터페이스 엔드포인트가 필요합니다.

| 엔드포인트 서비스 이름 | 용도 | 필수 여부 |
|---|---|---|
| `com.amazonaws.ap-northeast-2.ssmmessages` | **세션 데이터 채널**(WebSocket) | 🔴 필수 |
| `com.amazonaws.ap-northeast-2.ssm` | SSM API(등록·인벤토리·문서 조회) | 🔴 사실상 필수 |
| `com.amazonaws.ap-northeast-2.ec2messages` | Run Command 등 메시지 채널 | 권장(Run Command·Patch Manager 사용 시 필수) |
| `com.amazonaws.ap-northeast-2.s3` (게이트웨이) | 세션 로그 S3 업로드, 에이전트/플러그인 다운로드 | 로깅 시 필요 |
| `com.amazonaws.ap-northeast-2.logs` | CloudWatch Logs 스트리밍 | CW 로깅 시 필요 |
| `com.amazonaws.ap-northeast-2.kms` | 세션 데이터 KMS 암호화 | KMS 사용 시 필요 |

```bash
for SVC in ssm ssmmessages ec2messages logs kms; do
  aws ec2 create-vpc-endpoint \
    --profile awssec-lab --region ap-northeast-2 \
    --vpc-id vpc-shopminiprod00000 \
    --vpc-endpoint-type Interface \
    --service-name com.amazonaws.ap-northeast-2.$SVC \
    --subnet-ids subnet-app2a0000000000 subnet-app2c0000000000 \
    --security-group-ids sg-vpce00000000000000 \
    --private-dns-enabled \
    --tag-specifications "ResourceType=vpc-endpoint,Tags=[{Key=Name,Value=vpce-$SVC},{Key=Project,Value=awssec-lab},{Key=Chapter,Value=ch21}]"
done
```

⚠️ 엔드포인트용 보안 그룹(`sg-vpce...`)은 **앱 인스턴스 SG로부터의 443만** 허용해야 합니다. `0.0.0.0/0` 443을 열면 VPC 안의 모든 리소스가 SSM API에 도달합니다(19.2의 SG 참조 패턴).

### 🧪 3단계 — 세션 로깅과 KMS 암호화

세션 기본 설정은 `SSM-SessionManagerRunShell`이라는 **세션 문서**로 리전마다 관리됩니다.

```json
{
  "schemaVersion": "1.0",
  "description": "ShopMini prod session preferences",
  "sessionType": "Standard_Stream",
  "inputs": {
    "s3BucketName": "shopmini-session-logs",
    "s3KeyPrefix": "prod/",
    "s3EncryptionEnabled": true,
    "cloudWatchLogGroupName": "/aws/ssm/shopmini-sessions",
    "cloudWatchEncryptionEnabled": true,
    "cloudWatchStreamingEnabled": true,
    "kmsKeyId": "arn:aws:kms:ap-northeast-2:111122223333:key/1234abcd-12ab-34cd-56ef-1234567890ab",
    "runAsEnabled": true,
    "runAsDefaultUser": "ssm-ops",
    "idleSessionTimeout": "15",
    "maxSessionDuration": "60",
    "shellProfile": {
      "linux": "cd /var/log && export PS1='[shopmini-prod \\u@\\h \\W]\\$ '",
      "windows": ""
    }
  }
}
```

```bash
aws ssm update-document \
  --profile awssec-lab --region ap-northeast-2 \
  --name SSM-SessionManagerRunShell \
  --content file://session-prefs.json \
  --document-version '$LATEST'
```

| 항목 | 하는 일 |
|---|---|
| `kmsKeyId` | 세션 데이터를 TLS에 더해 **KMS 키로 한 번 더 암호화**. 키 정책에서 관리자·인스턴스 역할 양쪽에 `kms:GenerateDataKey`/`kms:Decrypt` 허용 필요(13.4) |
| `s3EncryptionEnabled` / `cloudWatchEncryptionEnabled` | `true`면 **암호화되지 않은 대상에는 로그를 쓰지 않는다.** 로깅 실패가 조용히 넘어가지 않고 암호화가 강제된다. 반드시 `true` |
| `cloudWatchStreamingEnabled` | `true`면 세션 진행 중 실시간 스트리밍. `false`는 종료 시 일괄 전송이라 비정상 종료 시 기록 유실 |
| `runAsEnabled` / `runAsDefaultUser` | 기본값에서 세션은 `ssm-user`로 실행되며 여기에 sudo를 주면 사실상 무제한. 최소 권한 전용 OS 계정 지정 |
| `idleSessionTimeout` / `maxSessionDuration` | 방치·장시간 세션 강제 종료. 잊혀진 터미널이 곧 취약점 |

로그 버킷은 로그 아카이브 계정(`777788889999`)에 두고 객체 잠금과 버전 관리를 적용합니다(15.8, 15.9, 29.9).

### 🧪 4단계 — IAM으로 대상과 조건 제한

Session Manager의 진짜 힘은 여기 있습니다. **"누가, 어떤 태그를 가진 인스턴스에, 어떤 세션 문서로, MFA를 거쳤을 때만"** 을 정책 하나로 표현합니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "StartSessionOnlyOnTaggedProdInstances",
      "Effect": "Allow",
      "Action": "ssm:StartSession",
      "Resource": "arn:aws:ec2:ap-northeast-2:111122223333:instance/*",
      "Condition": {
        "StringEquals": {
          "ssm:resourceTag/Project": "shopmini",
          "ssm:resourceTag/Environment": "prod"
        },
        "Bool": { "aws:MultiFactorAuthPresent": "true" },
        "BoolIfExists": { "ssm:SessionDocumentAccessCheck": "true" }
      }
    },
    {
      "Sid": "AllowOnlyApprovedSessionDocuments",
      "Effect": "Allow",
      "Action": "ssm:StartSession",
      "Resource": [
        "arn:aws:ssm:ap-northeast-2::document/AWS-StartPortForwardingSession",
        "arn:aws:ssm:ap-northeast-2::document/AWS-StartPortForwardingSessionToRemoteHost",
        "arn:aws:ssm:ap-northeast-2:111122223333:document/ShopMini-ReadOnlyShell"
      ]
    },
    {
      "Sid": "ManageOwnSessionsOnly",
      "Effect": "Allow",
      "Action": [
        "ssm:TerminateSession",
        "ssm:ResumeSession"
      ],
      "Resource": "arn:aws:ssm:ap-northeast-2:111122223333:session/${aws:username}-*"
    },
    {
      "Sid": "ReadOnlyDiscovery",
      "Effect": "Allow",
      "Action": [
        "ssm:DescribeSessions",
        "ssm:DescribeInstanceInformation",
        "ssm:GetConnectionStatus",
        "ssm:GetDocument"
      ],
      "Resource": "*"
    }
  ]
}
```

| 요소 | 의미 |
|---|---|
| `ssm:resourceTag/Environment` | 태그 기반 접근 제어(8.7의 ABAC). 이 정책만 가진 사람은 `Environment=dev` 인스턴스에 접근할 수 없다. ⚠️ **태그를 바꿀 수 있는 사람은 접근 통제를 바꿀 수 있으므로** `ec2:CreateTags`를 조건 키·SCP로 보호할 것(12.3, 37.2) |
| `ssm:SessionDocumentAccessCheck` | `true`면 세션 시작 시 **사용자가 해당 세션 문서 권한도 갖는지** 함께 검사. 없으면 두 번째 Statement의 문서 제한이 우회될 수 있다 |
| `session/${aws:username}-*` | 남의 세션을 끊지 못하게 한다. 보안 대응팀에는 전체 세션에 대한 `ssm:TerminateSession`을 별도 역할로 부여해 사고 시 강제 종료 가능하게 할 것(33.3) |

### 🧪 5단계 — 셸 제한과 포트 포워딩

**전체 셸을 줄 이유가 없는 경우가 많습니다.** 로그 확인만 필요한 온콜 담당자에게는 제한된 명령만 실행되는 세션 문서를 주십시오.

```bash
aws ssm start-session \
  --profile awssec-lab --region ap-northeast-2 \
  --target i-0abcd1234efgh5678 \
  --document-name AWS-StartInteractiveCommand \
  --parameters '{"command":["tail -n 200 -f /var/log/shopmini/app.log"]}'
```

**포트 포워딩**은 배스천의 마지막 용도 — "터널을 뚫어 내부 서비스에 붙는 것" — 을 대체합니다.

```bash
# 앱 인스턴스의 8443 포트를 로컬 18443으로
aws ssm start-session \
  --profile awssec-lab --region ap-northeast-2 \
  --target i-0abcd1234efgh5678 \
  --document-name AWS-StartPortForwardingSession \
  --parameters '{"portNumber":["8443"],"localPortNumber":["18443"]}'

# 인스턴스를 경유해 격리 서브넷의 RDS(3306)에 접속
aws ssm start-session \
  --profile awssec-lab --region ap-northeast-2 \
  --target i-0abcd1234efgh5678 \
  --document-name AWS-StartPortForwardingSessionToRemoteHost \
  --parameters '{"host":["shopmini-prod.cluster-abc123.ap-northeast-2.rds.amazonaws.com"],"portNumber":["3306"],"localPortNumber":["13306"]}'
```

두 번째 명령의 의미가 큽니다. **DBA는 이제 배스천에 SSH로 들어가 `mysql`을 실행할 필요가 없습니다.** 자기 노트북의 DB 클라이언트를 `localhost:13306`에 붙이면 되고, 그 트래픽은 IAM으로 인가되고 CloudTrail에 기록된 채널을 지납니다. RDS 보안 그룹의 인바운드 규칙은 하나도 늘지 않습니다.

⚠️ 다만 **포트 포워딩 세션의 내용은 셸 세션처럼 로깅되지 않습니다.** 터널을 지나간 SQL 쿼리는 세션 로그에 남지 않으므로, DB 접근 감사가 필요하면 RDS 감사 로그·IAM 데이터베이스 인증(16.2)을 함께 켜야 합니다. 포트 포워딩 문서 권한은 별도 역할로 분리하고 사용 시 알람을 거십시오.

### 검증

```bash
# 인스턴스가 SSM에 등록되었는지
aws ssm describe-instance-information \
  --profile awssec-lab --region ap-northeast-2 \
  --filters "Key=tag:Project,Values=shopmini" \
  --query 'InstanceInformationList[].{Id:InstanceId,Ping:PingStatus,Agent:AgentVersion}' \
  --output table

# 진행 중인 세션 확인
aws ssm describe-sessions \
  --profile awssec-lab --region ap-northeast-2 \
  --state Active \
  --query 'Sessions[].{Id:SessionId,Target:Target,Owner:Owner,Start:StartDate}' \
  --output table

# SSH/RDP 인바운드가 남아 있는 보안 그룹 색출
aws ec2 describe-security-groups \
  --profile awssec-lab --region ap-northeast-2 \
  --filters Name=ip-permission.from-port,Values=22 \
  --query 'SecurityGroups[].{Id:GroupId,Name:GroupName,Vpc:VpcId}' \
  --output table
```

마지막 명령의 결과가 **비어 있어야** 이 장의 목표가 달성된 것입니다. 결과가 있다면 각각에 대해 "왜 필요한가"를 답할 수 있어야 하고, 답할 수 없다면 지우십시오. 이 점검은 AWS Config 관리형 규칙 `restricted-ssh`와 EventBridge로 상시화할 수 있습니다(19.3, 35.2).

|---|---|
| Site-to-Site VPN | 터널 2개는 **AWS 쪽 이중화일 뿐**. 진짜 이중화는 온프레미스 라우터 2대 × 4터널. BGP 없이는 자동 전환도 없다 |
| 터널 옵션 | IKEv2만, DH 그룹 14 미만 제거, PSK 하드코딩 금지, 터널 로그를 CloudWatch Logs로 |
| VPN에 대한 원서 입장 | 사이트 간 VPN은 **입도가 너무 거칠다**. TLS를 먼저 하고, 관리 접근에는 쓰지 말 것 |
| Direct Connect | ⚠️ **기본 암호화 없음.** 순서는 ① 앱 TLS ② MACsec(링크 구간만) ③ DX 위 IPsec |
| VIF 유형 | 프라이빗(VPC) / 퍼블릭(⚠️ AWS 공인 대역 수신, 프리픽스 필터 필수) / 전송(DX GW → TGW) |
| DX 이중화 | 2 로케이션 × 2 디바이스 + VPN 백업. 전환 시 살릴 트래픽을 미리 정할 것 |
| Transit Gateway | **연결(association)과 전파(propagation)의 비대칭**이 격리의 도구. 기본 연결·전파는 반드시 `disable` |
| 라우팅 도메인 분리 | 운영↔개발 직접 통신 차단. 전파 안 함 + **블랙홀 경로로 의도를 문서화** |
| 검사 VPC | 스포크 기본 경로를 검사 VPC로. ⚠️ **어플라이언스 모드 필수**(비대칭 흐름 폐기 방지) |
| VPC 피어링 한계 | 전이 라우팅 불가 · n(n-1)/2 · CIDR 중복 불가 · 리전 간 SG 참조 불가 · 엣지 투 엣지 불가 |
| TGW 전환 기준 | VPC 4개 이상 / 온프레미스 연결 / **환경 격리를 라우팅으로 강제** / 중앙 검사 |
| 관리 접근의 원칙 | 최선의 경로는 **존재하지 않는 경로**(원서: Run Command가 있으면 경계 안에 들어갈 필요가 없다) |
| 배스천 vs Session Manager | 원서가 요구한 3가지(공격 표면 축소·세션 기록·경로 분리)를 Session Manager가 **인바운드 포트 0개로** 달성 |
| Session Manager 필수 4종 | 에이전트 · `AmazonSSMManagedInstanceCore` · VPC 엔드포인트(ssm/ssmmessages/ec2messages) · 로깅 설정 |
| 세션 로깅 | `s3EncryptionEnabled`/`cloudWatchEncryptionEnabled`를 `true`로 → 암호화 강제. 로그는 로그 아카이브 계정에 |
| IAM 제한 | `ssm:resourceTag/*` + `aws:MultiFactorAuthPresent` + `ssm:SessionDocumentAccessCheck` |
| 포트 포워딩 | 배스천 터널의 대체. ⚠️ 터널 내용은 세션 로그에 남지 않음 → DB 감사 로그 병행 |

## 🔴 필수 구성 체크리스트

- [ ] **어떤 보안 그룹에도 `0.0.0.0/0` 또는 사내망 대역의 22/3389 인바운드가 없다**
- [ ] 관리 접근은 SSM Session Manager로 통일되어 있고, 예외는 브레이크 글래스 절차로 문서화되어 있다
- [ ] 모든 세션이 S3 + CloudWatch Logs에 기록되고 KMS로 암호화되며, 로그는 로그 아카이브 계정에 있다
- [ ] `idleSessionTimeout`과 `maxSessionDuration`이 설정되어 있다
- [ ] Session Manager 시작 권한이 인스턴스 태그와 MFA 조건으로 제한되어 있다
- [ ] `ssm:SessionDocumentAccessCheck`가 켜져 있고 허용 세션 문서 목록이 명시되어 있다
- [ ] 사용자는 자기 세션만 종료할 수 있고, 대응팀만 모든 세션을 종료할 수 있다
- [ ] VPN 연결마다 터널이 2개 모두 설정되어 있고, 온프레미스 라우터도 2대 이상이다
- [ ] VPN이 BGP 동적 라우팅을 쓴다(정적이라면 리스크 등록부에 있다)
- [ ] VPN 터널 옵션에서 IKEv1과 DH 그룹 14 미만이 제거되어 있다
- [ ] PSK가 IaC 저장소나 코드에 하드코딩되어 있지 않다
- [ ] Direct Connect 구간의 트래픽이 애플리케이션 계층 TLS로 보호된다(MACsec 유무와 무관하게)
- [ ] DX에 백업 VPN 경로가 구성되어 있고, 전환 시 트래픽 우선순위가 정의되어 있다
- [ ] 퍼블릭 VIF를 쓴다면 수신 프리픽스 필터와 사내 재배포 제한이 적용되어 있다
- [ ] TGW의 `DefaultRouteTableAssociation`과 `DefaultRouteTablePropagation`이 `disable`이다
- [ ] `AutoAcceptSharedAttachments`가 `disable`이고 어태치먼트 수락이 수동 절차다
- [ ] 운영과 개발 라우팅 도메인이 분리되어 있고, 상호 대역에 블랙홀 경로가 있다
- [ ] TGW는 네트워크 계정에 있고 RAM 공유는 조직 내부로 제한(`--no-allow-external-principals`)되어 있다
- [ ] 검사 VPC 어태치먼트에 `ApplianceModeSupport=enable`이 설정되어 있다
- [ ] 존재하는 모든 VPC 피어링에 "왜 존재하는가"가 태그·문서로 남아 있고 정기 검토 대상이다

## ⚠️ 자주 하는 실수

| 실수 | 결과 | 올바른 구성 |
|---|---|---|
| VPN 터널을 1개만 설정 | AWS 유지보수마다 단절. "간헐적 장애"로 몇 달 방치 | 터널 2개 + 온프레미스 라우터 2대(총 4터널) |
| 정적 라우팅으로 VPN 구성 | 터널 장애 시 자동 전환 안 됨 — 이중화가 무의미 | BGP 동적 라우팅 (21.1) |
| PSK를 Terraform 코드에 하드코딩 | Git 히스토리에 영구 잔존, 저장소 유출 시 터널 침해 | AWS 생성 PSK 또는 인증서 기반 인증 (11.1) |
| "DX는 전용선이라 안전"하다고 평문 프로토콜 사용 | 회선 구간 노출, 컴플라이언스 범위 붕괴 | 앱 TLS 우선 + MACsec/IPsec 보조 (21.2) |
| MACsec을 종단 간 암호화로 착각 | 링크 구간 밖은 무방비인데 안전하다고 오판 | MACsec은 점대점 링크 전용. TLS를 대체하지 않음 |
| 퍼블릭 VIF 수신 경로를 사내망에 그대로 재배포 | 기존 이그레스 프록시·필터를 우회하는 새 경로 생성 | 프리픽스 필터 + 재배포 범위 제한 (19.6) |
| TGW 기본 라우팅 테이블 자동 연결·전파를 켜 둠 | 새 VPC 하나 붙는 순간 격리 설계 붕괴 | 생성 시 둘 다 `disable` (21.3) |
| 검사 VPC에 어플라이언스 모드 미설정 | 왕복 패킷이 다른 AZ 방화벽으로 → 비대칭 흐름 폐기 → 간헐 단절 | `ApplianceModeSupport=enable` |
| 필요할 때마다 피어링 추가 | 연결 수 폭증, 오래된 피어링이 잊혀진 채 잔존 → 개발→운영 침투 경로 | TGW 라우팅 도메인 분리 (21.3, 21.4) |
| 리전 간 피어링에서 SG 참조가 될 거라 가정 | 구성 실패 후 급하게 `10.0.0.0/8` 허용으로 우회 | 티어 서브넷 CIDR까지 좁혀서 사용 |
| 배스천을 인터넷에 열고 "IP 제한했으니 안전" | 사내 PC 한 대 침해로 관리 인터페이스 전체 도달 | Session Manager. 인바운드 규칙 0개 (21.5) |
| 사이트 간 VPN으로 관리 접근 허용 | 사내망 전체 = 관리 권한. 원서가 명시적으로 반대 | 관리 사용자 수준 접근 통제(IAM) |
| Session Manager를 켜고 세션 로깅은 미설정 | 누가 무엇을 했는지 사후 확인 불가 — 배스천보다 감사가 약해짐 | S3+CW Logs 로깅 + KMS 암호화 필수 |
| `ssm-user`에 무제한 sudo 부여 | IAM으로 인가한 의미가 OS 계층에서 사라짐 | `runAsDefaultUser`로 전용 계정 + 최소 sudo |
| 인스턴스 태그로 접근을 제한하면서 `ec2:CreateTags`는 방치 | 사용자가 자기 대상 인스턴스에 태그를 붙여 권한 확대 | 태그 변경 권한을 SCP·조건 키로 통제 (12.3, 37.2) |

## 다음 장 예고

21장은 "인스턴스에 들어가는 문"을 IAM 뒤로 옮겼습니다. 하지만 문을 잘 만드는 것과 애초에 들어갈 일이 없게 만드는 것은 다른 이야기입니다.

22장은 EC2 인스턴스 자체의 보안을 다룹니다. 서브넷 배치, 키 페어 관리의 난제(⚠️ 배포한 키는 회수할 수 없습니다), IAM 역할 부착, 사용자 데이터에 시크릿을 넣으면 안 되는 이유, 골든 AMI 파이프라인과 Patch Manager. 마지막 절은 21.5의 원서 인용으로 되돌아옵니다 — **"경계 뒤로 들어가지 않고 일상 운영을 할 수 있다면 그것이 이상적이다."** 불변 인프라가 그 이상을 실현하는 방법이고, Session Manager 세션 수가 0에 수렴하는 것이 그 성숙도의 지표입니다.
