## 0.1 이 책이 다루는 것과 다루지 않는 것

AWS 보안을 다룬 자료는 크게 두 갈래로 나뉩니다. 하나는 "왜 이렇게 해야 하는가"를 설명하는 원칙서이고, 다른 하나는 "이 버튼을 누르면 된다"를 알려주는 실습서입니다. 두 갈래가 따로 놀면 곤란한 일이 생깁니다. 원칙만 아는 사람은 KMS 키 정책 한 줄을 못 쓰고, 실습만 아는 사람은 자신이 방금 켠 통제가 어떤 위협을 막는지 설명하지 못합니다.

이 책은 두 갈래를 하나의 흐름으로 잇는 것을 목표로 합니다. **원칙(Why) → 아키텍처(What) → 서비스 구현(How) → 운영·규모화(Scale)** 라는 Top-Down 순서로, 매 장마다 "이 통제는 무슨 위협을 막는가"를 먼저 세운 뒤 실제 CLI 명령과 JSON 정책으로 내려갑니다.

> 📖 *Practical Cloud Security* 2판 서문에서 저자는, 이 책이 특정 클라우드의 통제를 어떻게 구현하는지 알려주는 쿡북 형식의 안내서가 **아니라고** 분명히 밝힙니다. 이유는 두 가지로, 클라우드 제공자가 구현을 계속 개선하기 때문에 그런 안내서는 금방 낡고, 어차피 제공자 자신이 쓴 how-to 문서가 더 정확하기 때문입니다. 대신 저자가 제공하려는 것은 "**언제 그런 안내서를 찾아 읽어야 하는지**에 대한 이해"라고 말합니다.

> 📖 반대편에 있는 *AWS Security Cookbook* 서문은 대상 독자를 IT 보안 전문가, 클라우드 보안 아키텍트, 보안 역할을 맡은 클라우드 애플리케이션 개발자로 규정하고, **AWS와 클라우드 컴퓨팅에 대한 사전 지식이 필요하다**고 못 박습니다. 또한 AWS Certified Security – Specialty 자격증을 준비하는 독자에게도 도움이 된다고 밝히고 있습니다.

이 책은 두 원서 사이의 빈칸을 메웁니다. 원칙서가 "언제 찾아 읽어야 하는지"까지만 알려주고 멈춘 지점에서 AWS의 실제 설정으로 이어가고, 실습서가 "이 버튼을 누르라"고만 말한 지점에서 그 버튼이 막는 위협을 되짚습니다.

### 이 책이 다루지 않는 것

| 다루지 않는 것 | 이유 | 대신 어디서 보나 |

| 애플리케이션 시큐어 코딩 자체 (SQL 인젝션 방어 코드, XSS 이스케이핑 등) | 언어·프레임워크 종속적이며 AWS 아키텍처와 독립적 | OWASP Top 10, 언어별 시큐어 코딩 가이드. 단, **SAST/DAST/SCA를 파이프라인에 배치하는 방법은 26장에서 다룸** |

| 물리 보안·데이터센터 통제 | AWS 책임 영역 | 2장 공동 책임 모델에서 경계선만 다룸 |
| 특정 침해 사고의 미공개 세부사항 | 확인되지 않은 내용을 지어내지 않는다는 원칙 | 3.5는 "공개된 유형" 수준으로 일반화해 서술 |

### 이 책의 표기 규칙

본문에서 절 제목 옆에 붙는 기호는 그 절을 어떻게 읽어야 하는지를 알려줍니다.

| 기호 | 의미 | 읽는 법 |
|---|---|---|
| 🔴 | **필수(Must)** | 빠지면 설계 결함으로 취급합니다. "이렇게 구성하라"는 명령형과, 하지 않았을 때의 결과가 함께 제시됩니다 |
| ⚠️ | **주의(Caution)** | 흔히 잘못 설정하는 함정입니다. 사고 시나리오 → 원인 → 올바른 구성 3단으로 서술됩니다 |
| 🧪 | **실습(Lab)** | 콘솔/CLI/IaC 핸즈온. 명령을 직접 쳐야 넘어갈 수 있습니다 |
| 📋 | **체크리스트** | 설계 리뷰·감사 대응에 그대로 복사해 쓰는 점검 목록입니다 |
| 📖 | **원서 인용** | 근거 원서 3권의 실제 서술을 옮긴 부분입니다 |
| 💡 | **원서 이후 변경** | 원서 집필 시점 이후 AWS가 바꾼 내용으로, 원서에는 없는 서술입니다 |

계정 ID는 전부 AWS 문서 관례의 더미값(`111122223333`, `444455556666`, `777788889999` 등)이며, 리전 예시는 별도 언급이 없으면 `ap-northeast-2`(서울)입니다.

## 0.2 독자별 학습 경로

40개 장을 1장부터 순서대로 읽는 것이 가장 안전하지만, 대부분의 독자는 그럴 시간이 없습니다. 아래 4개 트랙 중 자신에게 맞는 것을 골라 읽되, **1부(1~5장)는 어느 트랙이든 건너뛰지 마세요.** 뒤의 모든 장이 1부에서 세운 다섯 가지 원칙으로 되돌아옵니다.

| 트랙 | 대상 | 필독 장(순서대로) | 선택 장 | 예상 분량 |
|---|---|---|---|---|
| **A. 입문자** | AWS는 써봤지만 보안 설계는 처음 | 1 → 2 → 3 → 5 → 6 → 7 → 8 → 15 → 18 → 19 → 22 → 23 | 4, 9, 13, 29, 30 | 약 12장 |
| **B. 아키텍트** | 시스템 설계를 책임지는 역할 | 1 → 2 → 3 → 4 → 18 → 19 → 20 → 21 → 22 → 23 → 24 → 36 → 37 → 40 | 8, 13, 17, 28 | 약 14장 |
| **C. 보안 담당자** | 탐지·대응·거버넌스 운영 담당 | 1 → 3 → 25 → 26 → 27 → 29 → 30 → 31 → 32 → 33 → 34 → 35 → 37 → 38 → 39 | 7, 12, 15, 17 | 약 15장 |
| **D. 자격증 준비 (SCS-C02)** | AWS Certified Security – Specialty | 전 범위 1 → 40장 + 부록 A·E·H | — | 전권 |

**트랙 A — 입문자 (1부 → 2부 → 4부)**
가장 흔한 실수는 IAM을 대충 넘기고 네트워크부터 파는 것입니다. 클라우드에서는 IAM이 곧 경계이므로 6~8장을 확실히 소화한 뒤 15장(S3)에서 "가장 많은 사고가 나는 곳"을 먼저 만져보고, 그다음 18~19장으로 네트워크를 잡으세요. 13장(KMS)은 어렵게 느껴지면 15.7(S3 암호화)을 먼저 읽고 되돌아와도 됩니다.

**트랙 B — 아키텍트 (1부 → 4부 → 7부)**
설계 리뷰에서 지적당하는 항목은 대부분 네트워크 격리(4부)와 계정 경계(7부)입니다. 4부에서 단일 워크로드의 격리를 완성한 뒤, 36~37장에서 그 격리를 조직 전체에 SCP로 강제하는 방법으로 확장하고, 40장의 레퍼런스 아키텍처 3종으로 마무리하는 흐름이 가장 효율적입니다.

**트랙 C — 보안 담당자 (5부 → 6부 → 7부)**
"뚫린 뒤에 알기"를 없애는 것이 목표입니다. 5부에서 배포 전 차단, 6부에서 탐지·대응, 7부에서 조직 전체 강제로 이어집니다. 단 29장(로깅 아키텍처)은 다른 모든 장의 전제이므로 6부에서 가장 먼저 읽으세요. 로그가 없으면 나머지 장은 전부 실행 불가능합니다.

**트랙 D — 자격증 준비**
시험 도메인 매핑은 부록 H에 있습니다. 실습(🧪) 표시 절은 반드시 직접 손으로 따라 하세요. 시험 문제의 상당수가 "여러 정책이 충돌할 때 결과는?" 형태이므로 **7.3(정책 평가 순서)**과 **13.4(키 정책과 IAM의 결합 평가)**, **15.1(S3 4중 구조)** 세 절은 암기 수준으로 반복하기를 권합니다.

> 📖 *Practical Cloud Security* 2판 서문은 4~6장을 "가장 먼저 고려해야 할 보안 통제를 **우선순위 순서대로**" 배치했다고 밝히며, 그 순서를 ① 아이덴티티·접근 관리 ② 취약점 관리 ③ 네트워크 통제로 제시합니다. 이 책도 **아이덴티티를 가장 앞(2부)에 두는 판단**은 그대로 따릅니다. 다만 AWS에서는 네트워크 설계가 컴퓨트 배치와 한 덩어리로 움직이므로 네트워크를 4부로 앞당기고 취약점·공급망을 5부로 옮겼습니다. 읽는 순서를 원서 우선순위 그대로 맞추고 싶다면 **2부 → 5부 → 4부** 로 읽어도 무리가 없습니다.

## 0.3 실습 환경 구성 🧪

### 1단계: 실습 전용 AWS 계정 만들기

**회사 운영 계정에서 이 책의 실습을 하지 마세요.** 실습은 정의상 잘못 설정하는 과정을 포함하며, 이 책에는 퍼블릭 버킷을 일부러 만들어 보는 실습도 있습니다.

- 조직(AWS Organizations)이 이미 있다면 → `Sandbox` OU 아래에 신규 계정을 만듭니다(36.3 참조).
- 개인 학습이라면 → 새 이메일 주소(대부분의 메일 서비스는 `you+awssec@example.com` 형태의 별칭을 지원합니다)로 계정을 새로 만듭니다.

계정을 만든 직후 해야 할 일은 5장 「AWS 계정 첫날(Day 1) 필수 보안」에 정리되어 있습니다. 최소한 아래 세 가지는 **CLI를 설치하기 전에** 콘솔에서 끝내세요.

- 루트 사용자에 MFA 등록
- 루트 사용자의 액세스 키가 존재한다면 삭제
- 결제 알림 수신 설정(Billing preferences)

> 📖 *AWS Security Cookbook* 1장의 첫 레시피도 같은 순서를 따릅니다. IAM 대시보드의 체크리스트 항목을 전부 초록색으로 유지하는 것이 좋은 습관이라고 설명하면서, 첫 항목이 **루트 계정에 프로그래밍 방식 접근용 액세스 키가 살아 있는지**를 검사하는 것이라고 짚습니다. 루트는 다른 사용자를 만드는 데만 쓰고 일상 작업은 그 사용자로 하라는 것이 이 레시피의 결론입니다.

### 2단계: AWS CLI v2 설치

이 책의 모든 명령은 **AWS CLI v2** 기준입니다. v1에는 `aws configure sso` 서브커맨드 자체가 없고, `--cli-binary-format` 같은 옵션도 지원하지 않습니다. 이미 v1이 깔려 있다면 제거하거나 PATH에서 v2가 먼저 잡히도록 하세요.

```bash
# Linux (x86_64)
curl "https://awscli.amazonaws.com/awscli-exe-linux-x86_64.zip" -o "awscliv2.zip"
unzip awscliv2.zip
sudo ./aws/install

# macOS
curl "https://awscli.amazonaws.com/AWSCLIV2.pkg" -o "AWSCLIV2.pkg"
sudo installer -pkg AWSCLIV2.pkg -target /

# Windows (PowerShell, 관리자)
msiexec.exe /i https://awscli.amazonaws.com/AWSCLIV2.msi
```

```bash
# 반드시 2.x 가 나와야 합니다
aws --version
```

### 3단계: 프로파일 설정

이 책의 모든 명령 예제는 `--profile awssec-lab` 을 붙인다고 가정합니다. 기본 프로파일(`default`)을 실습 계정으로 두면, 나중에 업무 계정에서 명령을 실행할 때 **어느 계정에 명령이 나가는지 모르는 상태**가 됩니다. 프로파일을 반드시 명명하세요.

방법 A — IAM Identity Center(권장, 9.2 참조):

```bash
aws configure sso --profile awssec-lab
```

`~/.aws/config` 에 다음과 같이 기록됩니다.

```ini
[sso-session awssec]
sso_start_url = https://d-1234567890.awsapps.com/start
sso_region = ap-northeast-2
sso_registration_scopes = sso:account:access

[profile awssec-lab]
sso_session = awssec
sso_account_id = 111122223333
sso_role_name = LabAdministrator
region = ap-northeast-2
output = json
```

방법 B — IAM 사용자 액세스 키(개인 학습 계정에서만, 90일 내 회수 전제):

```bash
aws configure --profile awssec-lab
# AWS Access Key ID     : AKIA...
# AWS Secret Access Key : ...
# Default region name   : ap-northeast-2
# Default output format : json
```

설정을 확인합니다. **여기서 나오는 계정 ID가 실습 계정인지 매번 눈으로 확인하는 습관**이 이 책 전체에서 가장 값싼 안전장치입니다.

```bash
aws sts get-caller-identity --profile awssec-lab
```

```json
{
    "UserId": "AROAEXAMPLEID:lab-session",
    "Account": "111122223333",
    "Arn": "arn:aws:sts::111122223333:assumed-role/LabAdministrator/lab-session"
}
```

### 4단계: 예산 알림 설정

침해의 첫 신호가 요금 폭증인 경우가 많습니다(5.4에서 상세히 다룹니다). 실습 계정에는 반드시 예산을 겁니다.

`budget.json`:

```json
{
    "BudgetName": "awssec-lab-monthly",
    "BudgetLimit": {
        "Amount": "20",
        "Unit": "USD"
    },
    "TimeUnit": "MONTHLY",
    "BudgetType": "COST"
}
```

`notifications.json`:

```json
[
    {
        "Notification": {
            "NotificationType": "ACTUAL",
            "ComparisonOperator": "GREATER_THAN",
            "Threshold": 50,
            "ThresholdType": "PERCENTAGE"
        },
        "Subscribers": [
            {
                "SubscriptionType": "EMAIL",
                "Address": "you@example.com"
            }
```

### 5단계: 실습 리소스에 태그 붙이기와 정리 스크립트

이 책의 모든 실습 리소스에는 다음 태그를 붙입니다. 태그가 없으면 나중에 무엇을 지워야 할지 알 수 없습니다.

| 태그 키 | 값 | 용도 |
|---|---|---|
| `Project` | `awssec-lab` | 정리 대상 식별 |
| `Chapter` | `ch15` 등 | 어느 장 실습인지 |
| `AutoDelete` | `true` | 삭제해도 되는 리소스 표시 |

태그가 붙은 잔여 리소스를 찾는 명령입니다.

```bash
aws resourcegroupstaggingapi get-resources \
  --tag-filters Key=Project,Values=awssec-lab \
  --region ap-northeast-2 \
  --profile awssec-lab \
  --query 'ResourceTagMappingList[].ResourceARN' \
  --output table
```

과금이 큰 리소스는 태그를 놓쳤을 수 있으므로, 실습을 마칠 때마다 아래 스크립트로 **삭제가 아니라 조회**부터 합니다.

```bash
#!/usr/bin/env bash
# lab-sweep.sh — 실습 계정에 남아 있는 과금 리소스를 조회한다 (삭제하지 않음)
set -euo pipefail
PROFILE="${1:-awssec-lab}"
REGION="${2:-ap-northeast-2}"
A=(--profile "$PROFILE" --region "$REGION" --output text)

echo "== 실행 중인 EC2 인스턴스 =="
aws ec2 describe-instances "${A[@]}" \
  --filters Name=instance-state-name,Values=running,pending \
  --query 'Reservations[].Instances[].[InstanceId,InstanceType]'

echo "== NAT 게이트웨이 (시간당 + 데이터 처리량 과금) =="
aws ec2 describe-nat-gateways "${A[@]}" \
  --filter Name=state,Values=available \
  --query 'NatGateways[].[NatGatewayId,VpcId]'

echo "== 미연결 탄력적 IP =="
aws ec2 describe-addresses "${A[@]}" \
  --query 'Addresses[?AssociationId==`null`].[PublicIp,AllocationId]'

echo "== 로드 밸런서 =="
aws elbv2 describe-load-balancers "${A[@]}" \
  --query 'LoadBalancers[].[LoadBalancerName,Type]'

echo "== RDS 인스턴스 =="
aws rds describe-db-instances "${A[@]}" \
  --query 'DBInstances[].[DBInstanceIdentifier,DBInstanceClass]'

echo "== 인터페이스 VPC 엔드포인트 (시간당 과금) =="
aws ec2 describe-vpc-endpoints "${A[@]}" \
  --filters Name=vpc-endpoint-type,Values=Interface \
  --query 'VpcEndpoints[].[VpcEndpointId,ServiceName]'

echo "== 이번 달 누적 비용 =="
aws ce get-cost-and-usage \
  --profile "$PROFILE" --region us-east-1 \
  --time-period Start="$(date -u +%Y-%m-01)",End="$(date -u +%Y-%m-%d)" \
  --granularity MONTHLY --metrics UnblendedCost \
  --query 'ResultsByTime[].Total.UnblendedCost.Amount' --output text
```

> 💡 **원서 이후 변경** — Cost Explorer(`ce`) API는 계정 단위 글로벌 엔드포인트를 사용하므로 위 스크립트에서 이 명령만 `us-east-1`로 호출합니다. 세 가지를 유의하세요. ① Cost Explorer는 최초 활성화 후 데이터가 채워지기까지 시간이 걸려 계정 생성 직후에는 결과가 비어 있을 수 있습니다. ② `--time-period` 의 `End` 는 **미포함(exclusive)** 이므로 매월 1일에는 `Start` 와 `End` 가 같아져 오류가 납니다. 그날은 `End` 를 다음 날짜로 직접 지정하세요. ③ Cost Explorer API는 요청당 과금되는 유료 API입니다. 스크립트를 루프에서 돌리지 마세요.

각 실습의 예상 소요 시간과 정리 스크립트는 **부록 D(실습 랩 인덱스)** 에 장별로 모아 두었습니다. 비용이 큰 실습을 시작하기 전에 부록 D에서 해당 항목을 먼저 확인하세요.

## 0.4 ⚠️ 실습 시 과금·유출 사고 방지 수칙

실습 중에 실제로 일어나는 사고는 몇 가지 유형으로 압축됩니다. 각각을 **사고 시나리오 → 원인 → 올바른 구성** 순서로 봅니다.

### 시나리오 1 — 액세스 키를 커밋했더니 몇 시간 만에 요금이 폭증했다

**사고**: 실습용 코드를 GitHub 퍼블릭 저장소에 올렸다. 몇 시간 뒤 여러 리전에서 대형 GPU 인스턴스가 실행되고, 다음 날 청구서에 수백 달러가 찍혔다.

**원인**: 소스 코드(또는 설정 파일)에 장기 액세스 키가 들어 있었다. 퍼블릭 저장소는 자동 스캐너의 상시 표적이며, 노출된 키는 사람이 아니라 봇이 즉시 사용한다.

> 📖 *Practical Cloud Security* 2판 4장은 AWS API 키 같은 시크릿을 소스 코드에 저장해 발생한 침해가 **많이 있었다**고 서술하며, 소스 코드 저장소에 시크릿을 넣으면 안 되는 이유 두 가지를 듭니다. ① 저장소의 주된 기능은 비밀 유지가 아니라 소스 코드의 무결성 보호이며, 많은 경우 기본적으로 모두에게 코드를 공개한다는 점. ② 저장소가 완벽히 안전하더라도, 코드에 접근 가능한 모든 사람이 운영 환경의 시크릿까지 볼 자격이 있을 가능성은 매우 낮다는 점.

**올바른 구성**
- 장기 액세스 키를 아예 만들지 않습니다. IAM Identity Center(SSO)로 단기 자격 증명을 쓰세요(9.2).
- 키가 필요한 경우에도 `~/.aws/credentials`에만 두고, 저장소에는 절대 두지 않습니다. `.gitignore`에 `.env`, `*.pem`, `credentials`를 넣습니다.
- 커밋 전 시크릿 스캐너를 pre-commit 훅으로 붙입니다(27.6).
- EC2에서는 키 대신 인스턴스 프로파일을 씁니다(8.2).

### 시나리오 2 — 실습을 끝냈는데 요금이 계속 나온다

**사고**: 실습 인스턴스는 종료했는데 다음 달에도 요금이 나온다.

**원인**: 인스턴스만 지우면 끝난다고 생각했다. NAT 게이트웨이, 미연결 탄력적 IP, 인터페이스 VPC 엔드포인트, 로드 밸런서, CloudHSM은 **인스턴스와 무관하게 시간 단위로 과금**됩니다.

> 📖 *AWS Security Cookbook* 4장의 CloudHSM 레시피는 이 함정을 반복해서 경고합니다. CloudHSM은 KMS보다 비싸고 **프리 티어가 없으며**, 프로비저닝된 HSM은 실행되는 시간마다 과금되므로, 학습이나 실험 목적이라면 다음 레시피를 최대한 빨리 끝내고 생성한 리소스를 전부 정리하라고 명시합니다.

**올바른 구성**
- 실습 세션을 마칠 때마다 0.3의 `lab-sweep.sh` 를 실행합니다.
- 삭제 순서를 지킵니다: 인스턴스/태스크 → 로드 밸런서 → NAT 게이트웨이 → 탄력적 IP 해제 → 엔드포인트 → 서브넷/VPC. 의존 리소스가 남아 있으면 VPC 삭제가 실패합니다.
- CloudHSM, EKS 클러스터, Redshift처럼 프리 티어가 없고 단가가 높은 실습은 **한 자리에서 끝까지 마치고 즉시 정리**합니다.

### 시나리오 3 — 실습용 퍼블릭 버킷에 실제 데이터를 올렸다

**사고**: 15장에서 퍼블릭 접근을 실험하려고 버킷을 열었는데, 테스트 파일로 회사 문서 샘플을 올렸다.

**원인**: 실습 데이터와 실제 데이터를 구분하지 않았다.

**올바른 구성**
- 실습에는 반드시 무의미한 더미 파일만 씁니다(`echo "lab dummy" > sample.txt`).
- 퍼블릭으로 여는 실습이 끝나면 **같은 세션 안에서** 계정 수준 퍼블릭 액세스 차단을 다시 켭니다(15.2).
- 실습 계정과 업무 계정에서 CLI 프로파일 이름을 확실히 다르게 둡니다.

### 시나리오 4 — 리전을 섞어 써서 리소스를 놓쳤다

**사고**: 정리했다고 생각했는데 `us-east-1`에 만들어둔 리소스가 몇 달째 살아 있었다.

**원인**: 콘솔 리전 드롭다운을 무심코 바꿨거나, 리전 지정 없이 명령을 실행해 기본 리전으로 나갔다.

**올바른 구성**
- 이 책의 실습 리전은 **`ap-northeast-2`(서울)로 고정**합니다. 예외는 두 가지뿐입니다. ① CloudFront에 붙일 ACM 인증서는 `us-east-1`에서 발급해야 합니다(23.7). ② Cost Explorer·IAM·Organizations 등 글로벌 서비스 API.
- 프로파일 `region` 을 명시적으로 설정하고, 스크립트에서도 `--region` 을 생략하지 않습니다.
- 미사용 리전 차단은 SCP로 강제할 수 있습니다(5.5, 37.2).

### 📋 실습 전 매번 확인할 6개 수칙

- [ ] **루트 액세스 키를 만들지 않는다.** 루트로는 CLI를 쓰지 않는다.
- [ ] **장기 액세스 키를 퍼블릭 저장소에 올리지 않는다.** 커밋 전 스캔한다.
- [ ] **실습 계정과 업무 계정을 분리하고**, `aws sts get-caller-identity` 로 계정 ID를 확인한 뒤 실습을 시작한다.
- [ ] **실습 리전을 `ap-northeast-2`로 고정한다.**
- [ ] **예산 알림(ACTUAL 50% + FORECASTED 100%)을 걸어둔다.**
- [ ] **실습 종료 절차를 실습의 일부로 취급한다.** 정리하지 않은 실습은 끝난 실습이 아니다.

| ⑥ | 앱 → 인터넷(아웃바운드) | HTTPS 443 | 이그레스 필터링, Network Firewall 도메인 허용 목록 | 19.6 |
| ⑦ | 앱 → S3 | HTTPS (VPC 내부) | 게이트웨이 엔드포인트 + 엔드포인트 정책(`aws:PrincipalOrgID`) | 20.1, 20.3 |
| ⑧ | 앱 → KMS/Secrets Manager | HTTPS (VPC 내부) | 인터페이스 엔드포인트, 키 정책, 시크릿 자동 순환 | 11.3, 13.4, 20.2 |

### 데이터 자산과 분류

| 자산 | 저장 위치 | 분류 등급 | 필수 통제 |
|---|---|---|---|
| 회원 개인정보, 주문 내역 | RDS `shopmini` | 기밀 | KMS 저장 암호화, 전송 TLS 강제, 격리 서브넷, 감사 로깅 |
| 사용자 업로드 파일 | S3 `shopmini-uploads` | 기밀 | SSE-KMS, 퍼블릭 차단, 버전 관리, Macie 스캔 |
| 상품 이미지·정적 자산 | S3 `shopmini-assets` | 공개 | 무결성 보호 우선(버전 관리), CloudFront OAC로만 제공 |
| DB 자격 증명 | Secrets Manager | 극비 | 자동 순환, 최소 권한, 접근 로깅 |
| 감사 로그 | 로그 계정 S3 | 기밀 | 객체 잠금, 크로스 계정 쓰기 전용, 삭제 불가 |

### 이 아키텍처가 각 부에서 어떻게 확장되는가

| 부 | ShopMini에 무슨 일이 일어나는가 |
|---|---|
| 1부 | 이 아키텍처의 신뢰 경계를 긋고 STRIDE로 위협을 뽑는다 (3.2, 3.3) |
| 2부 | 앱 역할·배포 역할·운영자 역할을 최소 권한으로 설계한다 |
| 3부 | RDS·S3·시크릿을 KMS로 암호화하고, 백업을 별도 계정으로 뺀다 |
| 4부 | 위 그림의 서브넷·SG·엔드포인트를 실제로 만든다 |
| 5부 | 컨테이너 이미지에 SBOM을 붙이고 배포 전 정책 게이트를 건다 |
| 6부 | 위 8개 흐름 전부에 로그를 걸고, 침해 시나리오로 대응을 훈련한다 |
| 7부 | 같은 구조를 SCP와 Control Tower로 조직 전체에 강제한다 |

각 장의 실습은 이 그림의 한 조각을 만드는 작업입니다. 40장을 마치면 그림 전체가 완성됩니다.
