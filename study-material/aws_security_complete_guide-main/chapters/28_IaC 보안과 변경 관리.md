# 28장. IaC 보안과 변경 관리

> **이 장에서 다루는 것**
> - **IaC가 보안에 주는 네 가지** — 리뷰 가능성, 재현성, 드리프트 판정 기준, 감사 증적. 22.8 불변 인프라의 전제 조건
> - **IaC 정적 분석** 🧪 — CloudFormation Guard 규칙 작성, Terraform 플랜 기반 검사, OPA/Rego 정책 as code, CI 통합 스크립트
> - **배포 전 정책 게이트** 🔴 — 위험한 구성을 **머지 전에** 차단하는 게이트 규칙 10개와 각 규칙이 대응하는 장, 예방 vs 탐지 역할 분담
> - **드리프트와 ClickOps** ⚠️ — 콘솔 수동 변경이 만드는 세 가지 손실, `detect-stack-drift`, CloudTrail 콘솔 변경 탐지, 운영 계정 읽기 전용화
> - **변경 관리 프로세스** — 표준/일반/긴급 3분류, 긴급 변경의 사후 승인, 롤백 설계
> - **환경 분리** 🔴 — 개발/스테이징/운영을 **계정 단위**로 나누는 이유와 ⚠️ 운영 데이터 반입 금지
>

> **난이도**: ★★★

25장부터 27장까지는 "무엇이 취약한가"와 "그것이 어떻게 코드 안으로 들어오는가"를 다뤘습니다. 남은 질문이 하나 있습니다. **취약한 것은 코드만이 아닙니다.** 인프라 구성 자체가 취약할 수 있고, 이 책이 지금까지 설명한 통제의 대부분은 "어떤 API를 어떤 파라미터로 호출했는가"의 결과물입니다.

`BlockPublicAcls`를 `false`로 둔 S3 버킷, `0.0.0.0/0`에서 22번을 받는 보안 그룹, `HttpTokens`가 `optional`인 시작 템플릿 — 이것들은 CVE 번호가 붙지 않습니다. 스캐너가 "취약점"으로 세지도 않습니다. 그러나 지금까지 이 책이 다룬 사고 시나리오의 절대다수가 여기서 출발했습니다.

**5부의 마지막 장은 이 구성이 만들어지는 경로 자체를 통제 대상으로 삼습니다.** 인프라를 코드로 정의하고, 그 코드를 머지 전에 검사하고, 코드 밖에서 일어난 변경을 탐지하고, 변경 자체에 절차를 붙이는 일입니다.

> 📖 *Practical Cloud Security* 2판 5장 「Vulnerability Management」: **"클라우드 서비스와 Infrastructure as Code는 환경의 정의를 코드의 일부로 만들 수 있게 해 준다. 덕분에 새 환경과 새 코드를 함께 테스트할 수 있고, 기존 머신에 설치하는 마지막 단계에서 환경과 코드를 결합하지 않아도 된다."**

> 💡 **원서 범위 밖 보강** — 근거 원서 3권은 IaC를 **개념 수준**에서만 다룹니다. *Practical Cloud Security*는 5장에서 IaC를 "가용성 리스크를 낮춰 보안 변경을 빠르게 밀어낼 수 있게 하는 수단"으로, 6장에서 "네트워크 구성은 스크립트를 직접 짜지 말고 Terraform이나 CloudFormation 같은 IaC 도구를 쓰라"는 권고로 언급합니다. **IaC 정적 분석 도구·정책 게이트·드리프트 탐지 API는 원서 범위 밖의 보강**이며, 아래에서 📖 인용이 붙지 않은 부분은 모두 그렇습니다.

## 28.1 Infrastructure as Code가 보안에 주는 것

### 콘솔 클릭이 남기지 않는 것

ShopMini의 격리 데이터 서브넷 라우팅을 누군가 콘솔에서 바꿨다고 해 봅시다. CloudTrail에는 `CreateRoute` 한 줄이 남습니다. 그런데 이 한 줄로는 답할 수 없는 질문이 넷 있습니다.

| 질문 | 콘솔 변경 | IaC 변경 |
|---|---|---|
| 이 변경을 배포 전에 누가 검토했는가 | 기록 없음 | PR 리뷰어와 승인 이력 |
| 다른 리전·다른 계정에 똑같이 재현할 수 있는가 | 사람이 다시 클릭 | 같은 템플릿 재적용 |
| 지금 상태가 "의도한 상태"인지 어떻게 아는가 | 비교 대상이 없음 | 코드가 곧 기준선 |
| 왜 이렇게 바꿨는가 | 담당자 기억 | 커밋 메시지·티켓 링크 |

네 번째가 특히 중요합니다. 감사에서 "이 보안 그룹은 왜 이 포트를 열고 있습니까"라는 질문을 받았을 때, 콘솔 환경의 정답은 대개 "예전에 누가 열었는데 무서워서 못 닫고 있습니다"입니다. **의도가 기록되지 않은 구성은 시간이 지나면 아무도 건드릴 수 없는 화석이 됩니다.**

### IaC가 만드는 네 가지 보안 속성

**① 리뷰 가능성 — 코드 리뷰가 곧 인프라 리뷰**
보안 그룹 변경이 diff로 보이면, 애플리케이션 코드 리뷰와 같은 절차를 태울 수 있습니다. `-  CidrIp: 10.20.10.0/24` / `+  CidrIp: 0.0.0.0/0` 이 두 줄은 리뷰어가 놓치기 어렵습니다. 27.6에서 파이프라인 권한을 좁혔던 것과 같은 맥락입니다. 사람을 믿는 대신 **변경을 눈에 보이게** 만듭니다.

**② 재현성 — 스테이징에서 검증한 것이 운영에 그대로 간다**
"스테이징에서는 됐는데요"의 절반은 환경 차이에서 옵니다. 환경 정의가 코드에 있으면 그 차이가 파라미터 파일 diff로 드러납니다(28.6).

**③ 드리프트 판정 기준 — "달라졌다"를 말할 수 있게 된다**
드리프트는 IaC가 **만든** 문제가 아니라 IaC가 **보이게 만든** 문제입니다. 기준선이 없으면 그냥 "현재 상태"일 뿐입니다.

**④ 감사 증적 — 변경 티켓을 따로 만들지 않아도 된다**
누가 언제 무엇을 왜 바꿨고 누가 승인했는지가 Git에 이미 있습니다. 28.5에서 이것을 변경 관리 증적으로 쓰는 방법을 다룹니다.

### 22.8과의 연결 — 불변 인프라의 전제 조건

22.8에서 "SSH로 접속할 일이 없는 상태"를 목표로 잡았습니다. 그 목표가 성립하려면 **인스턴스를 고치는 대신 교체할 수 있어야** 하고, 교체하려면 교체 대상이 코드로 정의되어 있어야 합니다. IaC 없는 불변 인프라는 존재하지 않습니다.

> 📖 *Practical Cloud Security* 2판 5장 결론부: **"불변 인프라와 지속적 전달의 철학은 클라우드와 함께 채택되는 경우가 많고, 이는 변경으로 인한 장애 위험을 상당히 줄여 준다. 이것이 운영 리스크와 보안 리스크 사이의 균형을 바꾼다."** — 보안 수정도 변경이고, 변경을 안전하게 할 수 있게 되면 보안 수정을 더 빨리 밀어낼 수 있다는 논지입니다.

### ⚠️ IaC는 그 자체로 보안이 아니다

여기서 흔한 착각을 끊어 둡니다. **IaC는 옳은 구성을 만들어 주지 않습니다. 구성을 일관되고 빠르게 복제해 줄 뿐입니다.** 퍼블릭 버킷을 만드는 모듈을 사내 공용 모듈로 등록하면, 그 결함이 조직의 모든 계정에 정확히 같은 형태로 배포됩니다. 콘솔에서 실수했다면 버킷 하나로 끝났을 일입니다.

그래서 28.2와 28.3이 필요합니다. **코드가 되었으니 검사할 수 있다** — 이것이 IaC의 진짜 보안 이득입니다.

## 28.2 IaC 정적 분석 🧪

### 세 가지 검사 범주

| 범주 | 검사 대상 | 실행 시점 | 대표 도구 |
|---|---|---|---|
| **템플릿 규칙 검사** | 템플릿 파일 자체 | 커밋·PR | CloudFormation Guard, cfn_nag, cdk-nag |
| **플랜 기반 검사** | 적용 후 예상 상태 | PR·배포 직전 | `terraform plan` JSON + 정책 엔진 |
| **정책 as code** | 위 둘의 판정 규칙 자체를 코드로 | 규칙 저장소 | OPA/Rego, Conftest |

세 번째가 개념적으로 가장 중요합니다. **"무엇을 금지하는가"를 도구 설정 화면이 아니라 버전 관리되는 파일에 둔다**는 뜻입니다. 규칙 변경도 PR을 거치고, 규칙을 누가 언제 완화했는지가 기록에 남습니다.

⚠️ **검사 대상은 사람이 쓴 파일이 아니라 실제로 배포될 산출물이어야 합니다.** AWS CDK나 CloudFormation 매크로, Terraform 모듈처럼 한 단계 변환을 거치는 환경에서 소스만 검사하면, 변환 결과에서 생긴 구성은 그대로 통과합니다. CDK라면 `cdk synth`가 만든 템플릿을, Terraform이라면 플랜 JSON을 검사 대상으로 삼습니다. CDK 자체에는 합성 시점에 규칙을 평가하는 `cdk-nag` 같은 애스펙트 라이브러리도 있어 앞단 피드백으로 함께 쓰면 좋습니다.

### CloudFormation Guard로 규칙 쓰기

`cfn-guard`는 AWS가 공개한 오픈소스 정책 평가 도구로, CloudFormation 템플릿(및 임의의 JSON/YAML)을 자체 DSL 규칙으로 검사합니다.

```text
# rules/shopmini.guard

# ---- ① S3: 퍼블릭 액세스 차단 4종 (본문 15.2) ----
let s3_buckets = Resources.*[ Type == 'AWS::S3::Bucket' ]

rule S3_BLOCK_PUBLIC_ACCESS when %s3_buckets !empty {
    %s3_buckets.Properties.PublicAccessBlockConfiguration {
        BlockPublicAcls        == true
        BlockPublicPolicy      == true
        IgnorePublicAcls       == true
        RestrictPublicBuckets  == true
    }
    <<
      violation: S3 버킷에 퍼블릭 액세스 차단 4종이 모두 켜져 있어야 합니다. 본문 15.2 참고.
    >>
}

# ---- ② 보안 그룹: 관리 포트 전체 개방 금지 (본문 19.3) ----
let security_groups = Resources.*[ Type == 'AWS::EC2::SecurityGroup' ]

rule NO_OPEN_ADMIN_PORTS when %security_groups !empty {
    %security_groups.Properties.SecurityGroupIngress[
        CidrIp == '0.0.0.0/0'
        FromPort IN [22, 3389, 3306, 5432]
    ] empty
    <<
      violation: 0.0.0.0/0 에서 관리·DB 포트를 받는 인바운드 규칙은 허용되지 않습니다. 본문 19.3 참고.
    >>
}

# ---- ③ EBS: 고객 관리 키로 암호화 (본문 16.1) ----
let volumes = Resources.*[ Type == 'AWS::EC2::Volume' ]

rule EBS_ENCRYPTED when %volumes !empty {
    %volumes.Properties.Encrypted == true
    %volumes.Properties.KmsKeyId exists
    <<
      violation: EBS 볼륨은 암호화하고 고객 관리 KMS 키를 지정해야 합니다. 본문 16.1 참고.
    >>
}

# ---- ④ 시작 템플릿: IMDSv2 강제 + 홉 제한 (본문 8.3, 22장) ----
let launch_templates = Resources.*[ Type == 'AWS::EC2::LaunchTemplate' ]

rule IMDSV2_REQUIRED when %launch_templates !empty {
    %launch_templates.Properties.LaunchTemplateData.MetadataOptions {
        HttpTokens               == 'required'
        HttpPutResponseHopLimit  <= 2
    }
    <<
      violation: IMDSv2 를 required 로 강제하고 홉 제한을 2 이하로 두어야 합니다. 본문 8.3 참고.
    >>
}

# ---- ⑤ RDS: 퍼블릭 접근 금지 + 저장 암호화 (본문 16.2) ----
let db_instances = Resources.*[ Type == 'AWS::RDS::DBInstance' ]

rule RDS_PRIVATE_AND_ENCRYPTED when %db_instances !empty {
    %db_instances.Properties.PubliclyAccessible == false
    %db_instances.Properties.StorageEncrypted   == true
    <<
      violation: RDS 인스턴스는 PubliclyAccessible=false, StorageEncrypted=true 여야 합니다. 본문 16.2 참고.
    >>
}
```

실행과 회귀 테스트:

```bash
# 템플릿 검사 — 실패한 규칙만 요약 출력, 실패 시 0이 아닌 종료 코드
cfn-guard validate \
  --rules rules/shopmini.guard \
  --data templates/network.yaml \
  --show-summary fail

# 규칙 자체의 회귀 테스트 — "이 입력은 PASS, 저 입력은 FAIL" 을 고정한다
cfn-guard test \
  --rules-file rules/shopmini.guard \
  --test-data tests/shopmini_tests.yaml
```

**규칙에도 테스트를 붙이는 습관이 중요합니다.** 규칙을 고치다가 조용히 아무것도 잡지 못하게 되는 사고가 실제로 자주 일어납니다. `cfn-guard test`는 "이 템플릿 조각은 반드시 걸려야 한다"를 고정해 줍니다.

### Terraform: 플랜을 검사한다

Terraform은 HCL 소스를 그대로 검사하는 것보다 **플랜 결과를 JSON으로 뽑아서 검사**하는 쪽이 정확합니다. 변수·모듈·`for_each`가 모두 해석된 뒤의 최종 상태를 보기 때문입니다.

```bash
terraform init -backend=false
terraform validate

terraform plan -out=tfplan.binary
terraform show -json tfplan.binary > tfplan.json

# 정책 엔진으로 플랜 JSON 검사
conftest test --policy policy/ tfplan.json
```

Rego 정책 예시입니다.

```rego
# policy/s3.rego
package main

# 참고: OPA 1.0 이상에서는 `deny contains msg if { ... }` 문법을 씁니다.
deny[msg] {
    rc := input.resource_changes[_]
    rc.type == "aws_s3_bucket_public_access_block"
    rc.change.after.block_public_policy == false
    msg := sprintf("%s: block_public_policy 가 false 입니다 (본문 15.2)", [rc.address])
}

deny[msg] {
    rc := input.resource_changes[_]
    rc.type == "aws_security_group_rule"
    rc.change.after.type == "ingress"
    rc.change.after.cidr_blocks[_] == "0.0.0.0/0"
    rc.change.after.from_port == 22
    msg := sprintf("%s: 0.0.0.0/0 에서 SSH 인바운드 (본문 19.3)", [rc.address])
}

deny[msg] {
    rc := input.resource_changes[_]
    rc.type == "aws_db_instance"
    rc.change.after.publicly_accessible == true
    msg := sprintf("%s: RDS 퍼블릭 접근이 켜져 있습니다 (본문 16.2)", [rc.address])
}
```

이 밖에 Terraform·CloudFormation·Kubernetes 매니페스트를 공통으로 스캔하는 오픈소스 도구군(Checkov, tfsec, Terrascan, KICS, Trivy의 설정 스캔 모드 등)과 상용 CSPM 제품의 IaC 스캔 기능이 있습니다. **도구 선택보다 중요한 것은 두 가지입니다.** ① 규칙 세트가 사내 표준(이 책의 🔴 항목들)과 매핑되어 있을 것 ② 억제(suppression)가 코드에 남고 만료될 것.

### CI에 붙이기

```bash
#!/usr/bin/env bash
# ci/iac-gate.sh — PR 체크로 실행. 하나라도 실패하면 머지 불가.
set -euo pipefail

FAILED=0

echo "== 1) 템플릿 문법 검증 =="
for t in templates/*.yaml; do
  aws cloudformation validate-template --template-body "file://$t" >/dev/null \
    || { echo "  FAIL: $t"; FAILED=1; }
done

echo "== 2) 정책 규칙 검사 (cfn-guard) =="
cfn-guard validate --rules rules/ --data templates/ --show-summary fail || FAILED=1

echo "== 3) IAM 정책 검증 (Access Analyzer) =="
for p in policies/*.json; do
  aws accessanalyzer validate-policy \
    --policy-type IDENTITY_POLICY \
    --policy-document "file://$p" \
    --query "findings[?findingType=='ERROR' || findingType=='SECURITY_WARNING']" \
    --output json | grep -q '^\[\]$' || { echo "  FAIL: $p"; FAILED=1; }
done

exit $FAILED
```

3번은 7.7에서 다룬 **IAM Access Analyzer 정책 검증**입니다. 문법 오류뿐 아니라 `iam:PassRole`을 리소스 제한 없이 허용하는 것 같은 보안 경고를 잡아 줍니다. IaC 게이트의 IAM 부분은 이 API에 맡기는 편이 자체 규칙을 쓰는 것보다 정확합니다.

### 정적 분석이 못 잡는 것

과신을 막기 위해 한계를 분명히 해 둡니다.

- **다른 스택이 만든 리소스와의 조합** — 이 템플릿의 보안 그룹은 정상인데, 참조하는 상위 스택의 SG가 열려 있는 경우
- **런타임에 결정되는 값** — SSM 파라미터, 데이터 소스 조회 결과, 배포 시 입력 파라미터
- **콘솔에서 나중에 바뀐 것** — 28.4의 영역입니다
- **의도 자체가 잘못된 경우** — 문법적으로 완벽한 "전 세계에 공개된 버킷"

그래서 정적 분석은 **예방 통제의 1층**이지, 유일한 층이 아닙니다.

## 28.3 배포 전 정책 게이트 🔴

### 게이트를 놓는 네 지점

게이트는 하나가 아니라 층입니다. 앞쪽일수록 싸고 빠르며, 뒤쪽일수록 우회가 어렵습니다.

| 층 | 위치 | 강제력 | 우회 가능성 |
|---|---|---|---|
| **1. 로컬** | pre-commit 훅 | 없음(권고) | 훅을 끄면 통과 |
| **2. PR** | 필수 상태 체크 + 리뷰 승인 | 브랜치 보호로 강제 | 리포지토리 관리자가 우회 가능 |
| **3. 파이프라인** | 배포 직전 잡 | 파이프라인이 유일한 배포 경로면 강제 | 파이프라인을 안 쓰면 우회 |
| **4. 계정** | SCP, AWS Config 프로액티브 규칙, CloudFormation Hooks | **어떤 경로로 와도 강제** | 조직 관리 계정만 예외(37.3) |

🔴 **1~3층만으로 "차단했다"고 말하지 마십시오.** 파이프라인 밖에서 API를 직접 호출하면 전부 무력화됩니다. 4층(SCP·프로액티브 규칙)이 최종 방어선이고, 이것은 37장에서 조직 전체 가드레일로 다룹니다. 28장의 게이트는 **개발자에게 빠르고 친절한 피드백을 주는 층**입니다 — 실패가 배포 30분 뒤가 아니라 PR 3분 뒤에 오게 하는 것이 목적입니다.

### 🔴 게이트 규칙 10개

머지 전에 **차단(fail)** 해야 하는 최소 집합입니다. 경고가 아니라 차단입니다.

| # | 게이트 규칙 | 걸러 내는 구성 | 본문 |
|---|---|---|---|
| 1 | S3 퍼블릭 액세스 차단 4종이 모두 `true` | BPA 미설정·부분 설정 버킷 | 15.1, 15.2 |
| 2 | 버킷 정책·리소스 정책에 `"Principal": "*"` 금지(조건 없는 것) | 익명 접근 허용 | 15.4, 7.5 |
| 3 | `0.0.0.0/0` → 22/3389/3306/5432 인바운드 금지 | 관리·DB 포트 전체 개방 | 19.3 |
| 4 | EBS·RDS·EFS·S3에 암호화 속성 필수(+고객 관리 키) | 비암호화 스토리지 | 13.3, 16.1, 16.2 |
| 5 | 시작 템플릿 `HttpTokens: required`, 홉 제한 ≤ 2 | IMDSv1 허용 인스턴스 | 8.3, 24.4 |
| 6 | IAM 정책에 `Action: "*"` + `Resource: "*"` 동시 금지, 무제한 `iam:PassRole` 금지 | 사실상 관리자 권한 역할 | 7.5, 7.6 |
| 7 | RDS `PubliclyAccessible: false` 강제 | 인터넷에 노출된 DB | 16.2 |
| 8 | CloudTrail·VPC 플로우 로그·ALB 액세스 로그·S3 서버 액세스 로깅 설정 필수 | 로깅 없는 리소스 | 29장 |
| 9 | ALB/CloudFront에 TLS 1.2 이상 보안 정책, HTTP 리스너 리다이렉트 강제 | 평문·구버전 TLS | 23.5, 23.6 |
| 10 | 필수 태그(`Owner`, `DataClass`, `Environment`) 누락 금지 | 주인 없는 리소스 | 12.3 |

**안 하면 어떻게 되는가.** 이 10개는 이 책 전체에서 사고 시나리오로 등장했던 구성들입니다. 게이트가 없으면 각각을 26.6의 CSPM이 **배포된 뒤에** 발견하고, 발견에서 조치까지 평균 며칠이 걸립니다. 그 며칠이 노출 창(window)입니다. 게이트는 이 창을 0으로 만듭니다.

### 예방(shift-left)과 탐지(런타임)의 역할 분담

같은 위험을 두 곳에서 봅니다. 어느 쪽이 무엇을 맡는지 명확히 나눠야 중복 알람과 사각지대를 둘 다 피합니다.

| 구분 | 예방 게이트 (28.3) | 탐지 통제 (26.6, 29~31장) |
|---|---|---|
| 시점 | 리소스가 생기기 **전** | 리소스가 생긴 **후** |
| 대상 | IaC로 만들어지는 것 | 계정 안의 **모든** 리소스 |
| 실패 시 | 머지·배포 실패 | 발견 항목 생성, 알림, 자동 조치 |
| 강점 | 노출 창 0, 개발자에게 즉시 피드백 | 경로 무관, 기존 리소스도 커버 |
| 사각지대 | 콘솔·CLI 직접 생성, 기존 리소스 | 발견~조치 사이의 시간 |
| 대표 구현 | cfn-guard, OPA, PR 체크 | AWS Config 규칙, Security Hub, GuardDuty |

🔴 **원칙: 예방으로 막을 수 있는 것을 탐지에 맡기지 말고, 예방이 못 보는 것을 탐지가 반드시 보게 하라.** 위 10개 규칙은 예방 게이트와 AWS Config 규칙 **양쪽에 같은 이름으로** 존재해야 합니다. 그래야 "게이트를 통과했는데 왜 Config가 걸었나"를 규칙 이름 하나로 추적할 수 있습니다.

37.4에서 이 두 축에 **대응(Responsive)** 가드레일을 더해 3분류로 확장하고, 조직 전체에 배포하는 방법을 다룹니다.

### 🔴 반드시 이렇게 구성하라

1. **게이트 실패는 머지 불가로 만든다.** 브랜치 보호 규칙에서 게이트 잡을 필수 상태 체크로 지정합니다. "경고만 띄우고 통과"는 3주 안에 아무도 보지 않는 로그가 됩니다.
2. **억제는 코드에 남기고 만료일을 붙인다.** 예외가 필요하면 규칙을 끄지 말고, 해당 리소스에 억제 주석을 달되 `suppress-until: 2026-03-31`과 `owner:`를 함께 씁니다. 만료된 억제는 게이트가 다시 실패시킵니다.
3. **예외 승인자는 리소스 소유자가 아니어야 한다.** 자기 PR의 예외를 자기가 승인하면 게이트가 아닙니다.
4. **규칙 저장소를 별도 리포지토리로 분리하고 쓰기 권한을 보안팀에 둔다.** 애플리케이션 리포지토리에 규칙이 있으면 개발자가 규칙을 고쳐서 통과시킬 수 있습니다.
5. **파이프라인 역할이 게이트를 건너뛸 수 없게 한다.** 27.6에서 좁힌 파이프라인 역할에 "게이트 잡 없이 배포 잡만 실행"이 가능한 경로가 남아 있는지 확인합니다.

## 28.4 드리프트 탐지와 수동 변경 금지 ⚠️

### 사고 시나리오

**새벽 2시.** ShopMini 앱 티어에서 RDS 연결 실패가 쏟아집니다. 온콜 엔지니어가 콘솔에서 DB 보안 그룹을 열어 보니 앱 SG 참조 규칙 하나가 의심스럽습니다. 급한 마음에 임시로 `10.20.0.0/16` 전체에서 3306을 허용하는 규칙을 추가합니다. 장애가 멎습니다. 아침에 원인은 다른 데 있었던 것으로 밝혀지지만, 추가한 규칙은 지워지지 않습니다.

**6주 뒤.** 네트워크 스택을 업데이트합니다. CloudFormation은 템플릿에서 바뀐 속성만 반영하므로 손으로 추가한 그 규칙은 **그대로 남습니다.** 아무도 모릅니다.

**3개월 뒤.** 다른 팀이 같은 템플릿으로 재해 복구 리전에 환경을 재구축합니다. 그 규칙은 코드에 없으므로 **재현되지 않습니다.** DR 환경에서만 동작이 다릅니다. 왜 다른지 아무도 설명하지 못합니다.

**6개월 뒤.** 감사에서 "격리 데이터 서브넷의 3306 인바운드 소스가 왜 VPC 전체입니까"라는 질문이 나옵니다. Git에는 근거가 없고, CloudTrail 보존 기간은 지났고, 그날 새벽의 온콜 엔지니어는 퇴사했습니다.

### 원인 — ClickOps가 끊는 세 가지

| 끊기는 것 | 구체적 결과 |
|---|---|
| **재현성** | 코드에 없는 구성은 다른 리전·계정·DR 환경에서 재현되지 않는다 |
| **감사 추적** | "왜"가 없다. CloudTrail의 API 한 줄은 사실이지 이유가 아니다 |
| **수렴성** | 다음 배포가 되돌릴지 그대로 둘지 예측할 수 없다. 되돌리면 장애 재발, 안 되돌리면 유령 규칙 잔존 |

세 번째가 가장 고약합니다. **CloudFormation은 "관리하지 않는 속성"을 자동으로 되돌리지 않습니다.** 손으로 추가한 인바운드 규칙은 스택 업데이트를 몇 번 해도 살아남을 수 있고, 반대로 템플릿이 그 속성을 명시적으로 관리하고 있었다면 다음 배포에서 조용히 사라집니다. **어느 쪽인지 예측할 수 없다는 것 자체가 결함입니다.**

### 올바른 구성 ① — 드리프트를 탐지한다

CloudFormation 스택 단위 드리프트 탐지입니다.

```bash
# 탐지 시작 — 비동기 작업이므로 ID를 받아 상태를 조회한다
DRIFT_ID=$(aws cloudformation detect-stack-drift \
  --stack-name shopmini-prod-network \
  --query StackDriftDetectionId --output text)

aws cloudformation describe-stack-drift-detection-status \
  --stack-drift-detection-id "$DRIFT_ID" \
  --query "{Status:DetectionStatus,Drift:StackDriftStatus,Drifted:DriftedStackResourceCount}"

# 어떤 리소스가 어떻게 달라졌는지 — 실제 값과 기대 값의 차이가 나온다
aws cloudformation describe-stack-resource-drifts \
  --stack-name shopmini-prod-network \
  --stack-resource-drift-status-filters MODIFIED DELETED \
  --query "StackResourceDrifts[].{Res:LogicalResourceId,Type:ResourceType,Status:StackResourceDriftStatus}" \
  --output table
```

조직 전체에 강제하려면 AWS Config 관리형 규칙 `cloudformation-stack-drift-detection-check`를 씁니다. 이 규칙은 스택이 `IN_SYNC`가 아니면 비준수로 표시하므로, 29.8·31장의 Security Hub 집계에 그대로 올라옵니다. Terraform 환경이라면 정기적으로 `terraform plan -detailed-exitcode`를 돌려 종료 코드 `2`(변경 있음)를 드리프트 신호로 씁니다.

⚠️ **드리프트 탐지가 커버하지 못하는 범위를 알아 두십시오.** 스택으로 관리되지 않는 리소스, 스택에 있지만 드리프트 탐지를 지원하지 않는 리소스 타입, 그리고 태그·정책 문서 내부의 미세한 변경은 놓칠 수 있습니다. **드리프트 탐지는 AWS Config의 구성 이력(29.8)과 함께 써야 완결됩니다.**

### 올바른 구성 ② — 수동 변경을 CloudTrail로 찾는다

드리프트 탐지가 "무엇이 달라졌나"라면, CloudTrail은 "누가 파이프라인 밖에서 만졌나"에 답합니다. 30.6에서 만든 Athena 테이블에 다음 쿼리를 상시 리포트로 걸어 둡니다.

```sql
-- 운영 계정에서 배포 역할이 아닌 주체가 일으킨 '쓰기' API 호출
SELECT
    eventtime,
    useridentity.arn        AS principal,
    eventname,
    sourceipaddress,
    useragent
FROM cloudtrail_logs
WHERE recipientaccountid = '111122223333'
  AND readonly = 'false'
  AND eventname NOT IN ('AssumeRole', 'GetSessionToken')
  -- 승인된 배포 경로 제외
  AND useridentity.arn NOT LIKE '%:assumed-role/shopmini-cfn-exec/%'
  AND useridentity.arn NOT LIKE '%:assumed-role/shopmini-deploy/%'
  AND useridentity.invokedby IS NULL          -- AWS 서비스가 대신 호출한 것 제외
ORDER BY eventtime DESC;
```

콘솔 경유 여부를 더 좁히려면 `useragent`가 `console.amazonaws.com`, `signin.amazonaws.com`, 또는 브라우저 UA 문자열로 시작하는 건을 추려 냅니다. ⚠️ **다만 `useragent`는 클라이언트가 임의로 설정할 수 있으므로 통제의 근거로 삼지 말고 조사 보조 지표로만 쓰십시오.** 통제는 아래 ③의 주체 기반 제한으로 겁니다.

이 쿼리의 결과가 **0건인 것이 정상 상태**입니다. 0건이 아니면 그 각각에 티켓이 있어야 합니다. 30.5의 EventBridge 규칙으로 실시간 알림까지 연결하면 새벽 2시의 그 변경이 아침 회의 전에 안건이 됩니다.

### 올바른 구성 ③ — 운영 계정 콘솔을 읽기 전용으로

탐지만으로는 반복을 못 막습니다. **운영 계정에서 사람의 손이 인프라를 바꿀 수 없게** 만듭니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyInfraChangesOutsideDeployRole",
      "Effect": "Deny",
      "Action": [
        "ec2:AuthorizeSecurityGroupIngress",
        "ec2:AuthorizeSecurityGroupEgress",
        "ec2:RevokeSecurityGroupIngress",
        "ec2:CreateRoute",
        "ec2:ReplaceRoute",
        "ec2:ModifyVpcEndpoint",
        "ec2:ModifyInstanceMetadataOptions",
        "rds:ModifyDBInstance",
        "s3:PutBucketPolicy",
        "s3:DeleteBucketPolicy",
        "s3:PutBucketPublicAccessBlock",
        "iam:CreatePolicy",
        "iam:PutRolePolicy",
        "iam:AttachRolePolicy",
        "kms:PutKeyPolicy",
        "lambda:AddPermission"
      ],
      "Resource": "*",
      "Condition": {
        "ArnNotLike": {
          "aws:PrincipalArn": [
            "arn:aws:iam::*:role/shopmini-cfn-exec",
            "arn:aws:iam::*:role/shopmini-deploy",
            "arn:aws:iam::*:role/break-glass-admin"
          ]
        }
      }
    }
  ]
}
```

- 운영 계정 사용자에게는 기본적으로 **읽기 권한 + Session Manager 접근**(21.6)만 줍니다. 조사·디버깅은 얼마든지 하되 상태를 바꾸지 못합니다.
- 배포는 `shopmini-cfn-exec`(CloudFormation 서비스 역할)와 `shopmini-deploy`(파이프라인 역할)만 할 수 있습니다. 두 역할의 신뢰 정책은 사람이 직접 맡을 수 없도록 씁니다.
- `break-glass-admin`은 **브레이크글래스** 역할입니다. 아래 절차를 붙입니다.

**브레이크글래스 절차**
- [ ] 역할 전환에 MFA 필수(`aws:MultiFactorAuthPresent`)와 최대 세션 1시간
- [ ] 전환 즉시 보안 채널로 자동 알림(EventBridge → SNS, 30.5)
- [ ] 세션 중 모든 API 호출이 별도 대시보드에 표시
- [ ] 사용 후 24시간 내 사후 티켓 작성 — 28.5의 긴급 변경 절차로 연결
- [ ] 월 1회 사용 이력 검토, 사용이 잦으면 그것은 예외가 아니라 **설계 결함 신호**

⚠️ **SCP는 조직 관리 계정에 적용되지 않고, SCP 자체가 권한을 부여하지도 않습니다.** 이 함정은 37.3에서 자세히 다룹니다.

## 28.5 변경 관리 프로세스

### 원서가 말하는 변경 관리

> 📖 *Practical Cloud Security* 2판 5장 「Change Management」: **"가장 단순한 형태에서 변경 관리는 변경이 승인된 뒤에만 이루어지도록 보장하고, 변경의 위험이 어느 정도 평가되도록 보장해야 한다."** 저자는 이어서 **"잘못 운영되면 변경 관리는 오히려 취약점 관리를 방해하고, 취약점 해결에 필요한 변경을 늦춰 전체 리스크를 높인다"** 고 경고합니다.

이 균형이 이 절의 전부입니다. 변경 관리는 **변경을 늦추는 장치가 아니라 위험한 변경만 늦추는 장치**여야 합니다. 보안 패치를 3주짜리 승인 큐에 넣는 변경 관리는 보안을 해칩니다.

> 📖 같은 절: **"예를 들어, 보안 수정과 함께 새 코드를 운영에 밀어 넣는 일은, 좋은 상태로 빠르게 되돌아가는 절차가 입증되어 있다면 변경 관리 위원회가 자동 승인하는 통상 업무(business-as-usual)가 될 수 있다."** 그리고 **"애플리케이션 설계 변경 같은 더 큰 변경은 여전히 수동 변경 관리 절차를 거쳐야 할 수 있다"** 고 구분합니다.

여기서 **"좋은 상태로 빠르게 되돌아가는 절차가 입증되어 있다면"** 이라는 조건이 핵심입니다. 저자는 그 수단으로 다시 배포하기, 이전 버전으로 롤백하기, 새 버전으로 가는 트래픽을 끄기를 예로 듭니다. **자동 승인의 자격은 "위험이 없다"가 아니라 "되돌릴 수 있다"입니다.**

> 📖 같은 절: **"이상적으로는 변경 통제 절차에 최소 한 명의 보안 실무자가 변경 통제 위원회 위원이나 자문으로 참여해야 한다."** 또한 **"문서화된 변경 관리 절차는 SOC 2, ISO 27001, PCI DSS를 포함한 여러 산업·규제 인증에서 요구된다"** 고 명시합니다(38장 연결).

### 변경 3분류

| 유형 | 정의 | 승인 | ShopMini 예시 |
|---|---|---|---|
| **표준(Standard)** | 사전 승인된 반복 변경. 절차와 롤백이 문서화됨 | 자동 승인. PR 리뷰 1인 + 게이트 통과로 충분 | 골든 AMI 갱신 후 ASG 인스턴스 리프레시(22.8), 애플리케이션 배포, 패치 베이스라인 적용(22.6) |
| **일반(Normal)** | 설계·경계·권한을 바꾸는 변경 | 변경 위원회 또는 지정 승인자. 보안 리뷰 필수 | VPC 라우팅 변경, 새 크로스 계정 신뢰 관계(8.5), SCP 추가(37장), KMS 키 정책 변경(13.4) |
| **긴급(Emergency)** | 장애·보안 사고 대응. 지연 자체가 손해 | **사후 승인** | 침해 대응 중 키 비활성화(13.11), 유출 시 접근 차단 |

🔴 **표준 변경 목록을 명시적으로 만드십시오.** 목록이 없으면 모든 변경이 일반 변경이 되고, 그러면 사람들이 변경 관리를 우회합니다. 표준 변경으로 승격할 자격 요건은 세 가지입니다.

- [ ] **자동화되어 있는가** — 사람이 콘솔에서 하는 변경은 표준 변경이 될 수 없습니다
- [ ] **롤백이 입증되었는가** — 최근에 실제로 롤백해 본 적이 있어야 합니다
- [ ] **게이트가 검사하는가** — 28.3의 규칙이 이 변경 유형을 커버해야 합니다

### 긴급 변경의 사후 승인 절차

긴급 변경은 "승인을 건너뛰는 것"이 아니라 **"승인을 뒤로 미루는 것"** 입니다. 미룬 승인을 실제로 받아 내는 절차가 없으면 그냥 통제 부재입니다.

| 시점 | 해야 할 일 | 책임 |
|---|---|---|
| **T+0** | 브레이크글래스 역할 전환. 전환 사실이 자동 알림 | 실행자 |
| **T+0** | 변경 내용을 대응 채널에 실시간 기록(무엇을, 왜) | 실행자 |
| **T+1h** | 조치 완료 후 브레이크글래스 세션 종료 | 실행자 |
| **T+24h** | 사후 티켓 작성 — 근거, 실행 명령, 영향 범위, 원상 복구 계획 | 실행자 |
| **T+72h** | 변경 위원회 사후 승인 또는 반려. 반려 시 원상 복구 기한 지정 | 승인자 |
| **T+5d** | **IaC 코드에 반영하거나 되돌린다.** 둘 중 하나여야 한다 | 실행자 |
| **T+5d** | 드리프트 탐지에서 해당 스택이 `IN_SYNC`로 돌아왔는지 확인 | 보안팀 |

⚠️ **마지막 두 줄이 없으면 앞의 전부가 형식입니다.** 28.4의 사고 시나리오는 정확히 이 두 단계가 빠져서 발생했습니다. 긴급 변경 티켓은 **코드에 반영되었거나 원상 복구되었을 때에만** 닫힙니다.

### 롤백을 설계한다

원서가 자동 승인의 조건으로 든 "입증된 복구 절차"를 AWS에서 구현하는 방법입니다.

| 수단 | 동작 | 주의 |
|---|---|---|
| **CloudFormation 자동 롤백** | 스택 업데이트 실패 시 이전 상태로 되돌림 | 롤백 자체가 실패해 `UPDATE_ROLLBACK_FAILED`가 되면 수동 개입 필요 |
| **변경 세트(Change Set)** | 적용 전에 "무엇이 교체(Replacement)되는지" 확인 | 운영 스택은 변경 세트 검토를 필수 절차로 |
| **스택 정책** | RDS·KMS 키 등 특정 리소스의 교체·삭제를 스택 수준에서 거부 | 상태를 가진 리소스에 반드시 적용 |
| **삭제 방지 속성** | `DeletionPolicy: Retain`, RDS 삭제 방지 | 스택을 지워도 데이터는 남음 |
| **트래픽 전환** | 블루/그린, 가중 라우팅 | 📖 2판 5장이 예로 든 "새 버전으로 가는 트래픽 끄기" |

⚠️ **Terraform에는 "롤백"이 없습니다.** 이전 커밋을 다시 `apply`하는 것이 롤백이고, 그 사이에 상태를 가진 리소스가 파괴되었다면 되돌아오지 않습니다. `prevent_destroy` 수명 주기 설정과 상태 파일 백업(⚠️ 상태 파일에는 시크릿이 평문으로 들어갈 수 있으므로 암호화된 원격 백엔드 + 접근 제한 필수, 11.1)이 그 자리를 대신합니다.

### PR을 변경 티켓으로 쓰기

별도 변경 관리 시스템을 유지하는 조직이 많지만, IaC 환경에서는 **PR 자체가 대부분의 증적을 이미 담고 있습니다.**

| 변경 관리 요구사항 | PR에서 자동으로 확보되는 것 |
|---|---|
| 변경 내용 | diff |
| 변경 사유 | 커밋 메시지·PR 본문·이슈 링크 |
| 위험 평가 | 게이트 결과(28.3), 변경 세트 요약 |
| 승인자 | 리뷰 승인 이력 |
| 실행 시각·실행자 | 파이프라인 실행 로그 + CloudTrail |
| 롤백 계획 | PR 템플릿의 필수 항목으로 강제 |

38.5의 감사 대응에서 "지난 분기 운영 환경 변경 전건과 승인 증적"을 요구받았을 때, 이 구조라면 리포지토리 질의 한 번으로 답이 나옵니다.

## 28.6 환경 분리 🔴

### 🔴 개발/스테이징/운영은 계정 단위로 나눈다

VPC로 나누거나 태그로 나누는 것으로는 부족합니다. **계정이 AWS에서 가장 강한 격리 경계**이기 때문입니다.

| 격리 수준 | 권한 격리 | 실수 격리 | 데이터 격리 | 서비스 한도 |
|---|---|---|---|---|
| 태그 | 조건 키로 부분 가능, 실수 시 무력 | 없음 | 없음 | 공유 |
| VPC | 없음(IAM은 계정 범위) | 네트워크만 | 네트워크만 | 공유 |
| **계정** | **완전** | **완전** | **완전** | **분리** |

네 가지 이유를 구체적으로 봅니다.

**① 권한 격리** — IAM 정책의 `Resource: "*"`는 **계정 전체**를 뜻합니다. 같은 계정에 개발과 운영이 있으면, 개발자에게 준 `s3:GetObject` 와일드카드 권한이 운영 버킷에도 그대로 닿습니다. 태그 기반 접근 제어(8.7)로 막을 수 있지만, 태그 하나만 잘못 붙어도 뚫립니다. **계정이 다르면 애초에 도달할 수 없습니다.**

**② 실수 격리(폭발 반경)** — 1.4에서 말한 폭발 반경입니다. 개발 계정에서 `terraform destroy`를 잘못 실행해도 운영 자원은 손끝 하나 닿지 않습니다.

**③ 데이터 격리** — 개발 계정의 침해가 운영 데이터로 이어지지 않습니다. 특히 KMS 키가 계정 경계를 넘지 않도록 두면(13.10), 운영 스냅샷이 실수로 개발 계정에 복사되어도 **복호화되지 않습니다.**

**④ 서비스 한도와 과금** — 개발 계정의 부하 테스트가 운영의 API 호출 한도(13.11의 KMS 스로틀링 같은)를 잡아먹지 않습니다. 비용도 계정별로 자연스럽게 분리됩니다.

> 📖 *Practical Cloud Security* 2판 7장은 같은 논리를 백업에 적용합니다: **"백업이 별도의 클라우드 계정에, 운영 데이터와 분리된 관리자 자격 증명으로 보관되도록 하십시오. 공격자가 운영 데이터뿐 아니라 운영 계정에서 접근 가능한 백업까지 모두 지운 사례가 문서로 남아 있습니다."** — 계정 경계를 격리 수단으로 쓰는 사고방식 자체는 원서의 것입니다.

**36장에서 심화합니다.** AWS Organizations 구성, OU 설계, 필수 코어 계정(로그 아카이브·보안 도구·백업), 계정 팩토리로 신규 계정을 자동 생성하는 방법은 36장의 주제입니다. 이 절은 **"5부의 파이프라인 관점에서 왜 계정을 나눠야 하는가"** 만 다룹니다.

### 환경별 IaC 파라미터 분리

계정을 나눴으면 **템플릿은 하나, 파라미터는 환경별로** 유지합니다. 환경마다 템플릿을 복사하면 두 파일이 서서히 갈라져서 "스테이징에서는 됐는데"가 돌아옵니다.

```text
infra/
├── templates/
│   ├── network.yaml          # 환경 무관. 모든 환경이 같은 파일을 쓴다
│   ├── data.yaml
│   └── compute.yaml
├── params/
│   ├── dev.json              # 555555555555
│   ├── staging.json
│   └── prod.json             # 111122223333
└── ci/
    └── iac-gate.sh
```

```bash
# 운영 배포 — 실행 역할, 파라미터, 태그가 모두 환경별로 다르다
aws cloudformation deploy \
  --template-file templates/network.yaml \
  --stack-name shopmini-prod-network \
  --parameter-overrides \
      Environment=prod \
      VpcCidr=10.20.0.0/16 \
      EnableFlowLogs=true \
      RetentionDays=400 \
  --role-arn arn:aws:iam::111122223333:role/shopmini-cfn-exec \
  --tags Project=shopmini Environment=prod Owner=platform \
  --profile awssec-lab
```

| 파라미터로 뺄 것 | 코드에 고정할 것 |
|---|---|
| CIDR, AZ, 인스턴스 크기, 용량 | 암호화 사용 여부 |
| 로그 보존 기간, 알람 임계값 | 퍼블릭 액세스 차단 설정 |
| 도메인, 인증서 ARN | IMDSv2 강제 |
| 계정 ID, KMS 키 ARN | 보안 그룹의 소스(SG 참조 구조) |

🔴 **오른쪽 열은 절대 파라미터로 만들지 마십시오.** `EnableEncryption` 같은 파라미터가 존재하는 순간, 어느 환경에선가 `false`가 됩니다. 그리고 그 환경이 어느 날 운영 데이터를 받습니다. **보안 기본값은 선택지가 아니라 상수여야 합니다.**

⚠️ 개발 환경이라고 통제를 다 풀어도 되는 것은 아닙니다. 개발 계정도 실제 AWS 계정이고, 유출된 개발 계정 액세스 키는 공격자에게 **조직 내부의 발판**입니다. 개발 계정에서 완화해도 되는 것은 **비용·가용성 관련 설정**(다중 AZ, 인스턴스 크기, 백업 주기)이지 **암호화·퍼블릭 차단·로깅**이 아닙니다.

### ⚠️ 운영 데이터를 개발 계정에 반입하지 마라

**사고 시나리오.** 재현이 안 되는 결제 버그를 잡기 위해, 개발자가 운영 RDS 스냅샷을 공유받아 개발 계정에 복원합니다. "일주일만 쓰고 지우겠다"고 합니다. 개발 계정의 보안 그룹은 사내 IP 대역 전체에 3306을 열어 두고 있고, 스냅샷 복원 인스턴스에는 태그가 없어 Macie 스캔 대상에서도 빠집니다. 2년 뒤 그 인스턴스는 여전히 살아 있고, 그 안에는 실명·연락처·주문 이력이 들어 있습니다.

**원인.**
- 개발 계정은 **의도적으로 통제가 느슨한** 환경입니다. 개발자 수가 많고, 권한이 넓고, 실험적 리소스가 많습니다
- 데이터가 계정을 넘어가는 순간, 그 데이터의 보호 수준은 **도착지 계정의 수준으로 떨어집니다**
- "일주일"은 지켜지지 않습니다. 사람은 지운 것을 기억하지만 안 지운 것은 잊습니다

**올바른 구성.**

- [ ] 🔴 **기본은 합성 데이터** — 개발·테스트는 생성된 데이터로 한다. 스키마와 볼륨만 운영과 맞춘다
- [ ] 실 데이터가 꼭 필요하면 **마스킹·토큰화 후 반입**한다(16.6). 원본 식별자는 절대 넘기지 않는다
- [ ] 운영 계정에서 **스냅샷 공유 API를 SCP로 차단**한다 — `rds:ModifyDBSnapshotAttribute`, `ec2:ModifySnapshotAttribute`, `ec2:ModifyImageAttribute`를 배포 역할 외에는 거부(28.4의 SCP 패턴과 동일)
- [ ] 운영 KMS 키의 키 정책에서 **개발 계정 주체를 허용하지 않는다**(13.4, 13.10). 암호화된 스냅샷은 키 없이는 무용지물이므로 이것이 가장 강력한 기술적 차단이다
- [ ] 개발 계정에도 **Macie를 켜서**(12.4) 개인정보가 발견되면 알람이 울리게 한다. 반입은 결국 일어나므로 탐지 층을 둔다
- [ ] 데이터 분류 태그(`DataClass`, 12.3)를 게이트 규칙 10번으로 강제하고, 개발 계정에 `Confidential` 이상 태그가 생기면 즉시 조사한다

⚠️ **반대 방향도 막아야 합니다.** 개발 계정에서 만든 AMI·컨테이너 이미지·Lambda 레이어가 검증 없이 운영으로 넘어가는 경로 역시 공급망 위험입니다(27.5의 아티팩트 서명·검증). **데이터는 운영→개발로, 아티팩트는 개발→운영으로 흐르며, 둘 다 게이트가 필요합니다.**

## 🔴 필수 구성 체크리스트

**IaC 기본**
- [ ] 운영 환경의 모든 인프라가 IaC로 정의되어 있고, 정의되지 않은 리소스 목록을 알고 있다
- [ ] IaC 리포지토리에 브랜치 보호가 걸려 있고 직접 푸시가 금지되어 있다
- [ ] Terraform 상태 파일이 암호화된 원격 백엔드에 있고 접근 주체가 제한되어 있다
- [ ] 사내 공용 모듈에도 게이트가 적용된다(결함이 조직 전체로 복제되므로)

**정적 분석·게이트**
- [ ] 게이트 규칙 10개가 모두 구현되어 있고 **경고가 아니라 차단**이다
- [ ] 게이트 잡이 브랜치 보호의 필수 상태 체크로 등록되어 있다
- [ ] 규칙 파일에 회귀 테스트(`cfn-guard test` 등)가 있다
- [ ] 규칙 저장소의 쓰기 권한이 애플리케이션 팀과 분리되어 있다
- [ ] 억제(suppression)에 소유자와 만료일이 있고, 만료 시 게이트가 다시 실패한다
- [ ] IAM 정책은 Access Analyzer 정책 검증을 거친다(7.7)
- [ ] 같은 10개 규칙이 AWS Config 규칙으로도 존재한다(예방+탐지 이중화)

**드리프트·수동 변경**
- [ ] 운영 스택에 드리프트 탐지가 주기적으로 실행되고 결과가 Security Hub에 모인다
- [ ] "배포 역할 외 주체의 쓰기 API" 쿼리가 상시 리포트로 존재하고 결과가 0건이다
- [ ] 운영 계정 사용자는 기본적으로 읽기 권한 + Session Manager만 갖는다
- [ ] 인프라 변경 API가 배포 역할·브레이크글래스 역할 외에는 SCP로 거부된다
- [ ] 브레이크글래스 역할에 MFA·세션 시간 제한·실시간 알림·사후 티켓 절차가 있다

**변경 관리**
- [ ] 표준 변경 목록이 문서화되어 있고, 각 항목의 롤백을 실제로 실행해 본 적이 있다
- [ ] 일반 변경에 보안 리뷰어가 참여한다(📖 원서 권고)
- [ ] 긴급 변경 티켓은 **코드 반영 또는 원상 복구**를 확인해야 닫힌다
- [ ] 운영 스택 업데이트는 변경 세트 검토를 거친다
- [ ] 상태를 가진 리소스에 스택 정책·삭제 방지가 걸려 있다

**환경 분리**
- [ ] 개발/스테이징/운영이 **별도 AWS 계정**이다
- [ ] 템플릿은 공유하고 파라미터 파일만 환경별로 분리되어 있다
- [ ] 암호화·퍼블릭 차단·IMDSv2·로깅은 파라미터가 아니라 코드에 고정되어 있다
- [ ] 운영 계정에서 스냅샷·AMI 공유 API가 SCP로 차단되어 있다
- [ ] 운영 KMS 키 정책에 개발 계정 주체가 없다
- [ ] 개발 계정에 Macie가 켜져 있고 개인정보 발견 시 알람이 간다
