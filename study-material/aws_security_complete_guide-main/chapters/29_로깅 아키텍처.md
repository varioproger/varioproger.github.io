# 29장. 로깅 아키텍처

> **이 장에서 다루는 것**
> - **무엇을 감시해야 하는가** 🔴 — 원서의 감시 대상 7종을 AWS 로그 소스로 매핑, 켜지 않으면 되살릴 수 없는 로그
> - **CloudTrail 심화** 🧪 — 관리/데이터/인사이트 이벤트, 조직 트레일 + 다중 리전, 고급 이벤트 선택기, 약 15분 전달 지연
> - **로그 무결성 보장** 🔴⚠️ — `validate-logs`, 객체 잠금, 계정 격리. **공격자가 가장 먼저 하는 일은 트레일을 끄는 것**
> - **VPC 플로우 로그** 🧪 — 사용자 지정 형식, 집계 간격, ⚠️ 플로우 로그가 **기록하지 않는 것**
> - **로그 그룹 설계와 보존 기간** 🧪🔴 — KMS·구독/지표 필터, "최소 1년" 권고와 ⚠️ 개인정보 규제의 충돌 조율
> - **Config와 중앙 로그 계정** 🧪🔴 — "언제 누가 이 SG를 열었나", 운영 계정 관리자가 로그를 지울 수 없는 구조
>
> **선행 지식**: 12장(계정 분리), 15장(S3·객체 잠금), 19장(SG/NACL), 20장(엔드포인트), 28장(변경 관리)
> **난이도**: ★★★

---

5부까지의 모든 장은 **예방**에 관한 것이었습니다. 6부는 전제를 바꿉니다. **예방은 언젠가 뚫립니다.** 뚫린 다음에 무슨 일이 벌어졌는지 알 수 없다면, 앞의 28개 장은 사고 발생 시점에 아무 도움이 되지 않습니다.

> 📖 *Practical Cloud Security* 1·2판 7장: **"클라우드 제공자의 책임 영역에서 나오는 로그는 대부분 볼 수 없다. 그러나 클라우드 환경에는 중요한 특권 사용자 로그 원천이 새로 생긴다 — 제공자의 포털, API, 명령줄 인터페이스를 통해 팀이 한 일을 추적할 수 있다."**

클라우드에서는 **"누가 어떤 API를 호출했는가"라는 단일 축**이 생기고, 그 축 위에 인프라 변경·권한 변경·데이터 접근이 모두 올라옵니다. 대신 새로운 문제가 생깁니다. 그 축을 **끄는 것도 API 호출 한 번**이라는 것입니다.

이 장은 사고 조사에 필요한 증거를 **사고가 나기 전에** 만들어 두는 방법을 다룹니다. 30장의 알람도, 31장의 위협 탐지도, 33장의 사고 대응도 전부 이 장에서 남긴 로그 위에서 동작합니다.

## 29.1 무엇을 감시해야 하는가 🔴

### 데이터에 파묻히지 않기

> 📖 *Practical Cloud Security* 1·2판 7장: **"적당한 규모의 시스템이라면 어떤 것이든 너무 많은 로그와 지표를 내놓기 때문에, 보안에 쓸모없는 데이터에 파묻히기 쉽다. 무엇을 감시할지 고르는 것이 매우 중요하다!"**

원서는 무엇을 감시할지가 **환경과 애플리케이션에 따라 달라진다**고 못 박고 위협 모델에서 출발하라고 말합니다. 수 테라바이트의 데이터를 가졌다면 트래픽 양과 연결 지속 시간이 유용하지만, 백도어 삽입을 걱정하는 배포자에게는 양·목적지·세션 길이가 그대로이고 **내용만 오염**되므로 같은 지표가 쓸모없다는 예를 듭니다. 이어서 로그 레코드의 최소 기준을 제시합니다.

> 📖 *Practical Cloud Security* 1·2판 7장: **"최소한 이것은 보통 when, what, who를 의미한다 — 이벤트가 언제 일어났고, 무엇이 일어났으며, 누가 그 이벤트를 유발했는가."**

여기에 중요한 금지 조항이 붙습니다.

> 📖 *Practical Cloud Security* 1·2판 7장: **"한 가지 예외를 제외하면, 비밀번호·API 키·민감한 개인정보·보호 대상 건강정보나 그 밖의 민감 데이터를 로그에 절대 넣어서는 안 된다. (…) 로그에 접근할 수 있는 모든 사람이 그 정보를 볼 권한을 가진 것은 아니다."** 프라이버시를 위해 **"개인 식별 데이터를 직접 로깅하지 말고 GUID 같은 비식별 고유 ID를 쓰고, 그 ID를 실제 주체와 연결하는 표는 다른 곳에 두라"** 고 권고합니다.

원서가 인정하는 유일한 예외는 **특권 사용자 감시를 위한 세션 레코딩**입니다. 비밀번호가 남을 수 있지만 "감사할 수 있다는 이익이 위험보다 큰 경우가 많다"고 보되, **그 기록에 대한 접근은 매우 엄격히 통제**해야 합니다.

### 원서의 감시 대상 7종 → AWS 로그 소스 매핑

원서 7장은 감시 대상을 우선순위 순으로 7개 범주로 나눕니다. 각각을 AWS에서 무엇이 채우는지 정리하면 다음과 같습니다.

| # | 원서의 감시 대상 | 원서가 말하는 핵심 | AWS 로그 소스 | 기본 상태 |
|---|---|---|---|---|
| 1 | **Privileged User Access** (특권 사용자 접근) | 관리자를 못 믿어서가 아니라 **관리자를 사칭하는 사람**을 잡기 위해 | **CloudTrail 관리 이벤트**, IAM Identity Center 로그인 이벤트, SSM Session Manager 세션 로그 | 이벤트 기록 90일만. **트레일은 직접 생성** |
| 2 | **Logs from Defensive Tooling** (방어 도구 로그) | 도구가 100% 막지 못한다. 초기 경보의 이점을 버리지 말 것 | GuardDuty, Security Hub, WAF 로그, Network Firewall alert/flow 로그, Shield Advanced, Inspector, Macie | 대부분 **명시적 활성화 필요** |
| 3 | **Cloud Service Logs and Metrics** (클라우드 서비스 로그·지표) | CPU·네트워크·I/O·플랫폼 서비스 지표가 공격 중 요동친다 | **VPC 플로우 로그**, ALB/CloudFront 액세스 로그, **S3 서버 액세스 로그**, Route 53 Resolver 쿼리 로그, **EKS 컨트롤 플레인 로그**, CloudWatch 지표 | **전부 기본 비활성** |
| 4 | **Operating System Logs and Metrics** (OS 로그·지표) | VM을 쓴다면 OS 보안은 사용자 책임 | **CloudWatch 에이전트**(`/var/log/secure`, `auditd`, Windows 이벤트 로그), SSM 인벤토리 | 에이전트 설치·구성 필요 |
| 5 | **Middleware Logs** (미들웨어 로그) | 직접 운영하는 DB·큐·앱 서버의 로깅을 켜야 함 | **RDS 로그**(error·general·slowquery·audit) → CloudWatch Logs 내보내기, Amazon MQ, MSK 로그 | 파라미터 그룹에서 활성화 |
| 6 | **Secrets Server** (시크릿 서버) | 시크릿 접근을 **전부** 기록. 인증 실패·비정상 조회량·관리자 자격 증명 사용에 경보 | **Secrets Manager `GetSecretValue`**(CloudTrail 관리 이벤트), SSM Parameter Store `GetParameter`, KMS `Decrypt`/`GenerateDataKey` | CloudTrail이 있으면 기록됨 |
| 7 | **Your Application** (애플리케이션) | 자체 앱의 업무 이벤트(예: 임계액 초과 이체) | 애플리케이션 → CloudWatch Logs, Lambda 로그, X-Ray | 앱이 직접 기록 |

2판은 여기에 **Cloud provider monitoring tools** 항목을 추가합니다(1판에는 없습니다).

> 📖 *Practical Cloud Security* 2판 7장: **"AWS CloudTrail, Azure Monitor, IBM Cloud Activity Tracker 같은 클라우드 제공자 모니터링 도구는 클라우드 계정 안의 여러 주체가 무엇을 하고 있는지에 대한 중요한 통찰을 제공한다. 이는 특권 사용자나 고권한 서비스 계정에 특히 중요하다."** 그리고 **"절대 일어나서는 안 되거나, 드물어서 다른 사용자에게 알릴 만한 행위"** 의 예로 **"계정 내에서 특권 역할을 맡는 것, 계정이나 핵심 서비스의 보안 파라미터를 변경하는 것"** 을 듭니다. 30.3의 경보 목록이 이 문장의 구현입니다.

### 🔴 반드시 이렇게 구성하라 — "나중에 켤 수 없는 로그"부터

로그는 **소급 생성이 불가능**합니다. 오늘 켜면 오늘부터 남습니다. 따라서 우선순위는 "가치 ÷ 비용"이 아니라 **"없을 때 답할 수 없게 되는 질문의 무게"** 로 정합니다.

| 순위 | 켤 것 | 없으면 답할 수 없는 질문 |
|---|---|---|
| 1 | **조직 CloudTrail 트레일(다중 리전)** | "누가 언제 이 권한을 만들었나" |
| 2 | **VPC 플로우 로그** | "침해된 인스턴스가 어디로 연결을 시도했나" |
| 3 | **AWS Config 레코더** | "이 보안 그룹이 언제부터 열려 있었나" |
| 4 | **S3 데이터 이벤트(민감 버킷)** | "무엇이 몇 건 나갔나"(15.11) |
| 5 | **ALB/CloudFront 액세스 로그** | "공격 요청이 어떤 URL로 들어왔나" |
| 6 | **Route 53 Resolver 쿼리 로그** | "이 인스턴스가 어떤 도메인을 조회했나 — C2 여부" |
| 7 | **EKS 컨트롤 플레인 감사 로그** | "누가 이 파드에 `exec` 했나" |

**하지 않으면**: 사고 대응의 첫 30분이 "로그를 지금부터 켜자"로 소모되고, **들어온 경로를 특정할 방법이 영구히 사라집니다.** 경로를 모르면 봉쇄도 할 수 없어 같은 방식으로 다시 들어옵니다.

### ⚠️ 로그에 개인정보를 넣지 않기 — ShopMini의 경우

ShopMini 앱이 `logger.error("order failed: " + order)` 로 주문 객체 전체(이름·주소·전화번호)를 남기는 순간 **로그 그룹 전체가 개인정보 처리 시스템이 됩니다.** 접근 통제 등급이 올라가고, 보존 기간이 규제 대상이 되며, 개발자가 트러블슈팅으로 로그를 보는 행위가 개인정보 열람이 됩니다.

원서의 권고대로 **주문 ID(비식별 UUID)만 로깅**하고, 실제 주체와의 연결은 데이터베이스에서 하십시오. 이 원칙이 29.7의 보존 기간 충돌을 **미리 해소**해 줍니다.

## 29.2 CloudTrail 심화 🧪

### 세 가지 이벤트 유형

> 📖 *AWS Security Cookbook* 8장: **"별도 구성 없이도 CloudTrail은 계정의 API 활동 이벤트를 로깅하며, CloudTrail 콘솔을 통해 90일간 제공된다."** 그리고 트레일이 필요한 이유를 셋으로 정리합니다. **"로그를 90일 넘게 보관하려면, S3나 Lambda의 데이터 이벤트 로깅을 활성화하려면, 그리고 로그 검색에 추가적인 유연성을 얻으려면 트레일을 만들어 S3 버킷에 데이터를 기록할 수 있다."**

즉 **이벤트 기록(Event history)** 은 공짜로 90일간 조회되지만, **트레일(Trail)** 은 직접 만들어야 합니다.

| 이벤트 유형 | 무엇을 기록하나 | ShopMini 예 | 비용 |
|---|---|---|---|
| **관리 이벤트**(Management) | 제어 평면 API — 리소스 생성·변경·삭제·권한 조작 | `RunInstances`, `AttachRolePolicy`, `AuthorizeSecurityGroupIngress`, `GetSecretValue` | 리전별 **첫 번째 트레일의 사본은 무료**, 두 번째부터 과금 |
| **데이터 이벤트**(Data) | 데이터 평면 API — 객체·함수·테이블 수준 접근 | `GetObject`(`shopmini-uploads`), `PutObject`, Lambda `Invoke`, DynamoDB 항목 조작 | **이벤트 건당 과금.** 대량 버킷은 비쌈 |
| **인사이트 이벤트**(Insights) | 쓰기 관리 API의 **비정상 호출량·오류율**을 기준선 대비 탐지 | 평소 시간당 3건이던 `DeleteObject`가 4,000건 | **별도 과금** |

> 📖 *AWS Security Cookbook* 8장: **"인사이트 이벤트는 쓰기 관리 API의 비정상적인 호출량을 포착한다. 인사이트 이벤트에는 추가 요금이 발생한다."** 데이터 이벤트도 **"S3 버킷 내부나 Lambda 함수에서 수행되는 리소스 작업(데이터 이벤트)을 기록한다. 데이터 이벤트에는 추가 비용이 든다."**

### 🔴 조직 트레일 + 다중 리전

> 📖 *AWS Security Cookbook* 8장: **"기본적으로 트레일은 한 리전의 이벤트만 기록한다. 그러나 트레일을 다중 리전 트레일로 구성할 수 있다."** 그리고 Organizations 관리 계정에서는 **"조직에 트레일 적용(Apply trail to my organization)"** 옵션이 보이며, **"조직 트레일은 모든 멤버 계정에 생성되므로, 이 레시피에서 본 것처럼 버킷 정책을 수정하지 않아도 된다"**.

이 둘을 반드시 함께 켜십시오. **공격자는 로그가 없는 리전을 고릅니다.** 서울 리전만 트레일을 걸어 두면, 훔친 자격 증명으로 `sa-east-1`에 채굴 인스턴스를 띄우는 활동이 어떤 트레일에도 남지 않습니다. 신규 계정에 트레일 붙이기를 사람이 기억해야 하는 구조도 마찬가지로 실패합니다.

```bash
# 관리 계정(123456789012)에서 조직 트레일 생성
# 로그는 로그 아카이브 계정(777788889999)의 버킷으로 간다
aws cloudtrail create-trail \
  --name shopmini-org-trail \
  --s3-bucket-name shopmini-org-cloudtrail-logs \
  --is-organization-trail \
  --is-multi-region-trail \
  --include-global-service-events \
  --enable-log-file-validation \
  --kms-key-id arn:aws:kms:ap-northeast-2:777788889999:key/EXAMPLE-KEY-ID \
  --region ap-northeast-2 \
  --profile awssec-lab

aws cloudtrail start-logging \
  --name shopmini-org-trail \
  --profile awssec-lab
```

플래그 하나하나가 통제입니다.

| 플래그 | 안 켜면 |
|---|---|
| `--is-organization-trail` | 신규 계정이 로깅 없이 만들어짐 |
| `--is-multi-region-trail` | 다른 리전의 활동이 안 남음 |
| `--include-global-service-events` | **IAM·STS·CloudFront 같은 글로벌 서비스 이벤트가 빠짐** |
| `--enable-log-file-validation` | 로그 변조를 증명할 수 없음(29.3) |
| `--kms-key-id` | 로그 버킷 읽기 권한만으로 전문 열람 가능 |

> 💡 **원서 이후 변경** — 현재는 조직 트레일 관리를 로그 아카이브 계정이나 보안 계정에 **위임 관리자(delegated administrator)** 로 넘길 수 있습니다. 관리 계정에 상시 로그인하지 않고도 트레일을 운영하기 위한 구조이며, 29.9에서 다룹니다.

### 고급 이벤트 선택기로 데이터 이벤트 좁히기

데이터 이벤트를 전부 켜면 로깅 비용이 워크로드 비용을 넘어설 수 있습니다. **고급 이벤트 선택기(advanced event selectors)** 로 범위를 좁힙니다. 15.11에서 S3 예제를 다뤘으므로, 여기서는 **잡음 제거** 관점의 패턴을 봅니다.

```bash
# 민감 버킷만 데이터 이벤트로 / 관리 이벤트는 전부 유지
aws cloudtrail put-event-selectors \
  --trail-name shopmini-org-trail \
  --advanced-event-selectors '[
    {
      "Name": "SensitiveBucketObjectEvents",
      "FieldSelectors": [
        { "Field": "eventCategory", "Equals": ["Data"] },
        { "Field": "resources.type", "Equals": ["AWS::S3::Object"] },
        { "Field": "resources.ARN", "StartsWith": ["arn:aws:s3:::shopmini-uploads/"] }
      ]
    },
    {
      "Name": "ManagementEventsAll",
      "FieldSelectors": [
        { "Field": "eventCategory", "Equals": ["Management"] }
      ]
    }
  ]' \
  --profile awssec-lab
```

**한 선택기 안에서 같은 `Field`를 두 번 쓸 수 없습니다.** 버킷을 더 넣으려면 `StartsWith` 배열에 값을 추가하거나 선택기를 하나 더 만드십시오. **로그 버킷 자체를 데이터 이벤트 대상에 넣지 마십시오** — 로그를 쓰는 행위가 다시 로그를 만드는 자기 증식이 일어납니다.

**주의**: `put-event-selectors`는 기존 선택기를 **덮어씁니다.** 관리 이벤트 선택기를 함께 넣지 않으면 관리 이벤트 로깅이 꺼집니다. 인사이트 이벤트는 별도 API로 켭니다.

```bash
aws cloudtrail put-insight-selectors \
  --trail-name shopmini-org-trail \
  --insight-selectors '[
    { "InsightType": "ApiCallRateInsight" },
    { "InsightType": "ApiErrorRateInsight" }
  ]' \
  --profile awssec-lab
```

`ApiErrorRateInsight`가 특히 유용합니다. **권한 열거(enumeration)를 하는 공격자는 대량의 `AccessDenied`를 만들어 냅니다.** 정상 운영에서 오류율은 안정적이므로 기준선 이탈이 선명하게 보입니다.

### ⚠️ 약 15분의 지연이 만드는 제약

CloudTrail은 API 호출 후 **평균 약 15분** 안에 로그 파일을 전달합니다. 이 숫자가 아키텍처 설계를 바꿉니다.

| 하려는 것 | 15분 지연의 영향 | 대안 |
|---|---|---|
| 사후 조사·감사 | 문제없음 | 트레일 → S3 → Athena(30.6) |
| "위험한 API 호출 시 즉시 차단" | **불가능.** 15분이면 공격은 끝나 있음 | **예방 통제(SCP·IAM, 37장)** 로 애초에 막을 것 |
| 준실시간 알림 | 트레일 → CloudWatch Logs 경로도 같은 지연을 상속 | **EventBridge**(30.5)는 대부분의 이벤트를 수 초~수 분 내 전달 |

**로그 기반 대응은 늘 사후입니다.** "CloudTrail로 탐지해서 자동 차단하겠다"는 설계는 이미 벌어진 일을 되돌리는 것이지 막는 것이 아니고, 데이터 유출은 되돌릴 수 없습니다. **막아야 하는 것은 SCP로 막고, CloudTrail은 "막았는데도 뚫린 것"을 남기는 데 씁니다.**

## 29.3 로그 무결성 보장 🔴

### ⚠️ 사고 시나리오 — 트레일이 꺼져 있던 3일

**시나리오**: 유출된 장기 액세스 키로 운영 계정(`111122223333`)에 접근한 공격자가 첫 API 호출 3분 만에 `StopLogging`을 실행했습니다. 3일 뒤 이상 청구액으로 사고를 인지했지만 **그 3일간의 CloudTrail 로그는 존재하지 않습니다.** 어떤 데이터에 접근했는지, 백도어가 남아 있는지 알 수 없어 결국 계정 전체를 폐기하고 재구축했습니다.

**원인**: 세 가지가 겹쳤습니다.
1. 트레일 조작을 막는 **SCP가 없었다** — 운영 계정 관리자 권한이면 `StopLogging`이 가능했다.
2. 로그가 **같은 계정의 버킷**에 있었다 — 계정 권한 하나로 트레일과 로그를 모두 통제할 수 있었다.
3. **트레일 중지 경보가 없었다** — 로그가 끊긴 것을 3일간 아무도 몰랐다.

> 📖 *Practical Cloud Security* 1·2판 7장은 세 번째 항목을 명시적으로 요구합니다. **"로그가 흐르지 않을 때에도 경보가 필요하다는 것을 잊지 마라. 그것도 보안 문제다! 많은 경우 단순히 무언가 오작동하고 있다는 뜻이고, 그러면 미래의 문제를 보지 못하게 된다. 그러나 어떤 경우에는 실제로 진행 중인 공격의 지표일 수도 있다."**

### 올바른 구성 — 4중 방어

**① 로그 파일 무결성 검증**

> 📖 *AWS Security Cookbook* 8장은 트레일 생성 시 고급 옵션으로 이 기능을 소개합니다. **"로그 파일 검증을 활성화하면 CloudTrail이 로그를 전달한 이후에 로그 파일이 수정·삭제되었는지, 변경되지 않았는지 확인할 수 있다."**

CloudTrail은 로그 파일마다 SHA-256 해시를 계산하고, 이를 모은 **다이제스트 파일**을 시간당 하나씩 별도 프리픽스에 씁니다. 다이제스트는 서명되고 **직전 다이제스트를 참조하는 체인**을 이룹니다. 로그 파일을 지우면 다이제스트와 불일치하고, 다이제스트까지 지우면 체인이 끊깁니다.

```bash
aws cloudtrail validate-logs \
  --trail-arn arn:aws:cloudtrail:ap-northeast-2:123456789012:trail/shopmini-org-trail \
  --start-time 2026-09-01T00:00:00Z \
  --end-time 2026-09-06T00:00:00Z \
  --profile awssec-lab
```

정상이면 검증한 파일 수와 유효 요약이 나오고, 변조·삭제가 있으면 해당 파일이 무효(invalid) 또는 누락(missing)으로 보고됩니다. **주기적으로(예: 일 1회) 자동 실행하고 결과를 경보로 연결**하십시오. 사고가 난 뒤 처음 돌려 보는 명령이면 늦습니다.

**② S3 객체 잠금 — 지울 수 없게 만들기**

15.9의 객체 잠금을 로그 버킷에 겁니다. **로그 아카이브 버킷은 컴플라이언스 모드**입니다. 루트 사용자도 AWS 지원팀도 보존 기간 내에는 삭제할 수 없습니다.

```bash
# 로그 아카이브 계정(777788889999)에서
aws s3api put-object-lock-configuration \
  --bucket shopmini-org-cloudtrail-logs \
  --object-lock-configuration '{
    "ObjectLockEnabled": "Enabled",
    "Rule": { "DefaultRetention": { "Mode": "COMPLIANCE", "Years": 1 } }
  }' \
  --profile awssec-lab
```

**⚠️ 보존 기간을 신중하게 정하십시오.** 컴플라이언스 모드는 되돌릴 수 없고, 조직 트레일 로그는 계정 수가 늘수록 빠르게 커집니다. 1년으로 시작해 규제 요구가 명확해지면 연장하십시오(연장은 언제나 가능합니다).

**③ 별도 계정 격리** — 29.9의 주제입니다. 원칙만 확인하면, **트레일을 통제하는 권한과 로그를 삭제할 수 있는 권한이 같은 사람 손에 있으면 안 됩니다.**

**④ SCP + 경보**

트레일 조작 API를 조직 전체에서 금지합니다. 상세는 37.2에서 다루므로 핵심 액션만 제시합니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyLoggingTampering",
      "Effect": "Deny",
      "Action": [
        "cloudtrail:StopLogging",
        "cloudtrail:DeleteTrail",
        "cloudtrail:UpdateTrail",
        "cloudtrail:PutEventSelectors",
        "config:DeleteConfigurationRecorder",
        "config:StopConfigurationRecorder",
        "config:DeleteDeliveryChannel",
        "ec2:DeleteFlowLogs",
        "logs:DeleteLogGroup",
        "logs:PutRetentionPolicy"
      ],
      "Resource": "*",
      "Condition": {
        "ArnNotLike": {
          "aws:PrincipalARN": "arn:aws:iam::*:role/OrgLoggingAdminRole"
        }
      }
    }
  ]
}
```

`ArnNotLike` 예외는 **정당한 운영 경로 하나만** 남깁니다. 이 역할은 로그 아카이브 계정에서만 맡을 수 있게 하고, 사용 자체를 경보 대상으로 만듭니다. 동시에 **탐지 알람**을 겁니다(30.3에서 15가지로 확장).

- `StopLogging`, `DeleteTrail`, `UpdateTrail`, `PutEventSelectors` 호출
- `DeleteFlowLogs`, `StopConfigurationRecorder`, `DeleteConfigurationRecorder` 호출
- **로그 유입 중단 자체** — 로그 그룹 `IncomingLogEvents` 지표가 N분간 0이면 경보. 원서가 요구한 "로그가 흐르지 않을 때의 경보"가 이것입니다.

**⚠️ SCP만으로 충분하다고 생각하지 마십시오.** 관리 계정 루트에는 SCP가 적용되지 않고, SCP 자체를 바꿀 수 있는 주체도 존재합니다. 예방(SCP) + 불변성(객체 잠금) + 탐지(경보) + 증명(무결성 검증) 네 층을 모두 두는 이유입니다.

## 29.4 크로스 계정 CloudTrail 로깅 🧪

### 왜 계정을 나누는가

> 📖 *AWS Security Cookbook* 8장: **"로그를 별도 계정에 저장함으로써 우리는 소스 계정으로부터 로그를 격리하며, 이는 소스 계정에 접근 권한을 가진 누구도 로그를 변조하지 못하게 한다. 로그 계정에 대한 계정 수준 접근은 제한된 소수에게만 부여할 수 있다. 여러 계정에서 하나의 계정으로 로그를 보내는 것은 로그를 질의할 중앙 지점도 제공한다."**

원서는 **격리**와 **중앙화**라는 두 이익을 함께 얻는다고 정리합니다. 이것이 29.9 전체의 근거입니다.

### 실습 — 로그 아카이브 계정의 버킷 정책

**로그 아카이브 계정 `777788889999`** 의 버킷 `shopmini-org-cloudtrail-logs`에, 관리 계정 `123456789012`가 만든 조직 트레일이 로그를 씁니다.

원서가 보여 주는 기본 버킷 정책은 두 개의 문(statement)입니다. `AWSCloudTrailAclCheck`가 `s3:GetBucketAcl`을, `AWSCloudTrailWrite`가 `s3:PutObject`를 허용하되 `s3:x-amz-acl`이 `bucket-owner-full-control`인지 검사합니다. 크로스 계정 확장은 **`Resource`를 리스트로 바꾸고 상대 계정의 로그 폴더 경로를 추가**하는 방식입니다.

> 💡 **원서 이후 변경 — 혼동된 대리인 방어가 필수입니다.** 원서 시점의 정책에는 `s3:x-amz-acl` 조건만 있었지만, 현재 AWS가 생성하는 정책은 **`aws:SourceArn`(트레일 ARN)** 과 **`aws:SourceAccount`** 를 포함합니다. 없으면 CloudTrail 서비스 주체를 통해 **다른 사람의 트레일이 우리 버킷에 쓰도록 유도하는 혼동된 대리인(confused deputy)** 공격이 가능합니다. ACL이 비활성(`BucketOwnerEnforced`)인 버킷에서는 `s3:x-amz-acl` 조건이 의미를 잃으므로 `SourceArn`이 유일한 방어입니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AWSCloudTrailAclCheck",
      "Effect": "Allow",
      "Principal": { "Service": "cloudtrail.amazonaws.com" },
      "Action": "s3:GetBucketAcl",
      "Resource": "arn:aws:s3:::shopmini-org-cloudtrail-logs",
      "Condition": {
        "StringEquals": {
          "aws:SourceArn": "arn:aws:cloudtrail:ap-northeast-2:123456789012:trail/shopmini-org-trail"
        }
      }
    },
    {
      "Sid": "AWSCloudTrailOrganizationWrite",
      "Effect": "Allow",
      "Principal": { "Service": "cloudtrail.amazonaws.com" },
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::shopmini-org-cloudtrail-logs/AWSLogs/o-exampleorgid/*",
      "Condition": {
        "StringEquals": {
          "s3:x-amz-acl": "bucket-owner-full-control",
          "aws:SourceAccount": "123456789012",
          "aws:SourceArn": "arn:aws:cloudtrail:ap-northeast-2:123456789012:trail/shopmini-org-trail"
        }
      }
    },
    {
      "Sid": "DenyUnencryptedAndInsecureTransport",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::shopmini-org-cloudtrail-logs",
        "arn:aws:s3:::shopmini-org-cloudtrail-logs/*"
      ],
      "Condition": { "Bool": { "aws:SecureTransport": "false" } }
    }
  ]
}
```

**조직 트레일의 경로는 계정 ID가 아니라 조직 ID(`o-exampleorgid`)로 시작합니다.** 실제 객체 키는 `AWSLogs/o-exampleorgid/111122223333/CloudTrail/ap-northeast-2/2026/09/06/...` 형태로, 원서가 **"CloudTrail은 각 계정의 로그를 그 계정에 특정한 폴더에 기록한다"** 고 설명한 구조가 조직 단위로 한 겹 감싸진 것입니다.

**독립 계정(비 Organizations) 방식**이라면 원서대로 `Resource`를 배열로 만들고 각 계정 폴더를 나열합니다.

```text
"Resource": [
  "arn:aws:s3:::shopmini-org-cloudtrail-logs/AWSLogs/111122223333/*",
  "arn:aws:s3:::shopmini-org-cloudtrail-logs/AWSLogs/555555555555/*"
]
```

이 방식은 **계정이 늘 때마다 사람이 정책을 고쳐야** 하므로 조직 트레일이 훨씬 낫습니다. 다만 원서의 경고는 유효합니다.

> 📖 *AWS Security Cookbook* 8장: **"멤버 계정이 이미 트레일을 가지고 있다면 이 옵션을 활성화할 때 추가 요금이 발생할 수 있다. 리전 내 첫 번째 트레일만 무료이기 때문이다."**

조직 트레일을 켜기 전에 **멤버 계정의 기존 개별 트레일을 정리**하십시오. 그대로 두면 같은 이벤트를 두 번 저장하며 두 배로 냅니다.

## 29.5 VPC 플로우 로그 🧪

### 무엇을 남기나

> 📖 *AWS Security Cookbook* 5장: **"VPC 플로우 로그는 VPC를 드나드는 IP 트래픽을 포착하는 데 도움을 준다. VPC 플로우 로그 데이터는 CloudWatch Logs나 S3 버킷으로 게시할 수 있다. 허용된 트래픽만, 거부된 트래픽만, 또는 둘 다를 로깅하도록 선택할 수 있다. VPC 플로우 로그는 VPC 수준, 서브넷 수준, 네트워크 인터페이스 수준 등 서로 다른 수준에서 만들 수 있다."**

19장에서 확인했듯 **보안 그룹과 NACL은 자체 로그를 남기지 않습니다.** 플로우 로그는 그 공백을 메우는 유일한 수단이고, 특히 **REJECT 레코드**가 보안 신호입니다.

### 기본 형식 vs 사용자 지정 형식

기본 형식은 `version account-id interface-id srcaddr dstaddr srcport dstport protocol packets bytes start end action log-status` 14개 필드입니다. 조사에는 부족합니다 — **어느 서브넷인지, 어느 인스턴스인지, 방향이 무엇인지가 없습니다.**

| 추가할 필드 | 왜 필요한가 |
|---|---|
| `vpc-id`, `subnet-id`, `instance-id` | ENI ID를 사람이 아는 리소스로 환원 |
| `flow-direction` | ingress/egress 구분 — 유출 탐지의 핵심 |
| `traffic-path` | egress가 IGW·NAT·VPC 피어링·Transit Gateway 중 어디로 갔는지 |
| `pkt-srcaddr`, `pkt-dstaddr` | NAT·로드밸런서 뒤의 **진짜** 주소 |
| `tcp-flags` | SYN만 있고 SYN-ACK가 없는 포트 스캔 패턴 식별 |
| `pkt-src-aws-service`, `pkt-dst-aws-service` | S3·DynamoDB 등 AWS 서비스 대상 트래픽 식별(20장의 유출 경로) |
| `az-id`, `region` | 다중 리전 상관 분석 |

```bash
aws ec2 create-flow-logs \
  --resource-type VPC \
  --resource-ids vpc-0shopminiprodEXAMPLE \
  --traffic-type ALL \
  --log-destination-type s3 \
  --log-destination arn:aws:s3:::shopmini-org-flowlogs \
  --max-aggregation-interval 60 \
  --destination-options FileFormat=parquet,HiveCompatiblePartitions=true,PerHourPartition=true \
  --log-format '${version} ${account-id} ${vpc-id} ${subnet-id} ${instance-id} ${interface-id} ${srcaddr} ${dstaddr} ${srcport} ${dstport} ${protocol} ${packets} ${bytes} ${start} ${end} ${action} ${log-status} ${tcp-flags} ${flow-direction} ${traffic-path} ${pkt-srcaddr} ${pkt-dstaddr} ${pkt-src-aws-service} ${pkt-dst-aws-service}' \
  --tag-specifications 'ResourceType=vpc-flow-log,Tags=[{Key=Project,Value=awssec-lab},{Key=Chapter,Value=ch29}]' \
  --profile awssec-lab
```

**`--max-aggregation-interval`** 은 60초 또는 600초(기본)입니다. 60초는 탐지가 빠른 대신 레코드 수와 비용이 늘어납니다. **운영 VPC는 60초, 개발 VPC는 600초** 정도가 실용적 절충입니다. **`FileFormat=parquet` + 하이브 호환 파티션**은 30.6의 Athena 분석에서 스캔 비용을 크게 낮춥니다.

### S3 vs CloudWatch Logs — 어디로 보낼 것인가

| 항목 | S3 | CloudWatch Logs |
|---|---|---|
| 저장 비용 | **낮음**(수명 주기로 Glacier 이전 가능) | 높음(수집 요금 + 저장 요금) |
| 대량 분석 | **Athena로 우수**(Parquet + 파티션) | Logs Insights, 대량 스캔은 비쌈 |
| 준실시간 경보 | 어려움(객체 도착 이벤트 기반) | **지표 필터로 즉시 경보 가능** |
| 보존 | 무제한, 객체 잠금 가능 | 최대 10년, 잠금 불가 |
| 원서 대응 | — | 원서 5장 실습은 CloudWatch Logs 대상 |

**둘 다 쓰는 것이 정답에 가깝습니다.** 한 리소스에 플로우 로그를 여러 개 붙일 수 있으므로, 전수 보존·대량 분석은 S3로, **REJECT만 골라 보는 경보용 소량 스트림**은 CloudWatch Logs로 보냅니다.

```bash
# 경보용: 거부 트래픽만 CloudWatch Logs로
aws ec2 create-flow-logs \
  --resource-type VPC \
  --resource-ids vpc-0shopminiprodEXAMPLE \
  --traffic-type REJECT \
  --log-destination-type cloud-watch-logs \
  --log-group-name /shopmini/prod/vpc-flowlogs-reject \
  --deliver-logs-permission-arn arn:aws:iam::111122223333:role/FlowLogsToCloudWatchRole \
  --max-aggregation-interval 60 \
  --profile awssec-lab
```

19.7에서 정한 원칙 — **"내부 출발지의 REJECT는 잡음이 아니라 신호"** — 를 실행하는 구성이 이것입니다.

### ⚠️ 플로우 로그가 기록하지 않는 것

플로우 로그를 켜 두면 네트워크에서 벌어진 일을 다 안다고 믿게 되는데, 사실이 아닙니다.

**첫째, 페이로드가 없습니다.** 플로우 로그는 **연결의 메타데이터**(누가 누구에게, 몇 바이트, 허용/거부)만 남깁니다. 어떤 SQL이 실행됐고 어떤 파일이 나갔는지는 알 수 없어, 패킷 내용이 필요하면 **VPC 트래픽 미러링**이 별도로 필요합니다.

**둘째, 원서가 명시한 미기록 트래픽이 있습니다.**

> 📖 *AWS Security Cookbook* 5장: **"다음을 포함한 일부 IP 트래픽은 플로우 로그가 모니터링하지 않는다. 기본 VPC 라우터의 예약 IP 주소로 가는 트래픽, DHCP 트래픽, 인스턴스 메타데이터 조회를 위한 169.254.169.254로 가는 트래픽, 인스턴스가 Amazon DNS 서버로 보내는 트래픽(단, 자체 DNS 서버로 가는 트래픽은 기록된다), Windows 라이선스 활성화 트래픽."**

이 중 **IMDS**와 **Amazon DNS** 가 보안상 치명적입니다.

| 미기록 항목 | 보안상 함의 | 보완 수단 |
|---|---|---|
| **169.254.169.254 (IMDS)** | 22장의 SSRF → 자격 증명 탈취 시도가 **플로우 로그에 전혀 안 남음** | IMDSv2 강제(예방), OS 수준 감사, 자격 증명 사용처를 CloudTrail `sourceIPAddress`로 역추적 |
| **Amazon DNS 조회** | **C2 도메인 조회, DNS 터널링 유출이 안 보임** | **Route 53 Resolver 쿼리 로깅**을 별도로 활성화 |
| DHCP, 라이선스 활성화 | 실무상 영향 적음 | — |

**Route 53 Resolver 쿼리 로그는 플로우 로그와 별개의 서비스입니다.** 켜지 않으면 "이 인스턴스가 어떤 도메인을 물어봤는가"에 답할 수 없습니다. 29.1 표에서 6순위로 둔 이유입니다.

**셋째, 구성 변경이 어렵습니다.** 원서는 **"현재는 플로우 로그 구성을 생성한 뒤에 연결된 IAM 역할 같은 설정을 변경할 수 없다"** 고 적었고, 지금도 로그 형식을 포함한 대부분은 변경 불가여서 **삭제 후 재생성**이 실무 절차입니다. 필드를 빠뜨린 채 6개월을 쌓으면 그 6개월치는 영영 그 형식이므로 **처음부터 넉넉히 잡으십시오.** Athena 분석 쿼리는 **30.6**에서 다룹니다.

## 29.6 CloudWatch 로그 그룹 설계 🧪

### 로그 그룹과 로그 스트림

> 📖 *AWS Security Cookbook* 8장: **"로그 그룹은 로그 스트림의 그룹이다. 로그 스트림은 같은 소스에서 나온 로그 이벤트의 시퀀스다. 로그 그룹 내의 로그 스트림들은 같은 보존, 모니터링, 접근 제어 설정을 공유한다."**

이 한 문장이 설계 원칙을 결정합니다. **보존 기간과 접근 통제는 로그 그룹 단위로만 걸립니다.** 따라서 **보존 요구나 접근 주체가 다른 로그는 반드시 다른 로그 그룹으로 나눠야 합니다.**

| 로그 그룹 | 내용 | 보존 | 누가 읽나 |
|---|---|---|---|
| `/shopmini/prod/app` | 앱 애플리케이션 로그 | 30일 | 개발팀 + 보안팀 |
| `/shopmini/prod/nginx-access` | 웹 액세스 로그 | 90일 | 개발팀 + 보안팀 |
| `/shopmini/prod/os-audit` | `auditd`, `/var/log/secure` | 400일 | **보안팀만** |
| `/shopmini/prod/vpc-flowlogs-reject` | 거부 트래픽 | 90일 | 보안팀 + 네트워크팀 |
| `/aws/rds/instance/shopmini/audit` | RDS 감사 로그 | 400일 | **보안팀만** |
| `/shopmini/prod/session-manager` | SSM 세션 기록(특권 세션) | 400일 | **보안팀 소수만** |

마지막 항목이 29.1의 "toxic log"입니다. **세션 기록에는 비밀이 섞일 수 있으므로 별도 그룹 + 별도 KMS 키 + 최소 인원 접근**이 원칙이고, **접근 자체가 알림을 발생**시켜야 합니다.

### 보존 기간과 KMS 암호화

**로그 그룹의 기본 보존 기간은 "만료 없음(Never expire)"** 입니다. 안전해 보이지만 실제로는 **비용 사고와 규제 위반의 원인**입니다. 반드시 명시하십시오.

```bash
aws logs create-log-group \
  --log-group-name /shopmini/prod/os-audit \
  --tags Project=awssec-lab,Chapter=ch29 \
  --profile awssec-lab

# 보존 기간은 정해진 값만 허용된다(1,3,5,7,14,30,60,90,120,150,180,365,400,545,731,1096,1827,2192,2557,2922,3288,3653)
aws logs put-retention-policy \
  --log-group-name /shopmini/prod/os-audit \
  --retention-in-days 400 \
  --profile awssec-lab

# 고객 관리형 KMS 키로 암호화
aws logs associate-kms-key \
  --log-group-name /shopmini/prod/os-audit \
  --kms-key-id arn:aws:kms:ap-northeast-2:111122223333:key/EXAMPLE-KEY-ID \
  --profile awssec-lab
```

KMS 키 정책에는 `logs.ap-northeast-2.amazonaws.com` 서비스 주체에 `kms:Encrypt*`, `kms:Decrypt*`, `kms:ReEncrypt*`, `kms:GenerateDataKey*`, `kms:Describe*` 를 허용하고, 14장의 원칙대로 `kms:EncryptionContext:aws:logs:arn` 조건으로 **해당 로그 그룹에만** 한정하십시오.

> 💡 **원서 이후 변경** — 현재 CloudWatch Logs는 **로그 클래스**를 제공합니다. `STANDARD`는 모든 기능을 쓸 수 있고, `INFREQUENT_ACCESS`는 수집 비용이 낮은 대신 지표 필터·구독 필터 등이 제한됩니다. **경보를 걸 로그 그룹은 반드시 `STANDARD`** 로 두십시오.

### 지표 필터 — 로그를 숫자로 바꾸기

> 📖 *Practical Cloud Security* 1·2판 7장: **"로그의 주된 장점은 무슨 일이 있었는지에 대해 훨씬 많은 정보를 준다는 것이지만, 로그를 저장하고 검색하는 비용은 활동이 늘어나면 빠르게 증가할 수 있다. (…) 반면 지표가 각 기간에 보고하는 숫자는 활동이 늘어도 저장·처리 비용이 늘지 않는다. (…) 다뤄야 할 로그 항목이 너무 많을 때는 지표가 경보에 더 나은 선택일 수 있다."**

**지표 필터는 로그를 지표로 바꾸는 장치**입니다. 로그 원문은 그대로 두고, 특정 패턴의 발생 횟수만 CloudWatch 지표로 뽑아 경보를 겁니다.

```bash
# CloudTrail을 CloudWatch Logs로도 보내는 경우: 루트 사용자 사용 탐지
aws logs put-metric-filter \
  --log-group-name /shopmini/org/cloudtrail \
  --filter-name RootAccountUsage \
  --filter-pattern '{ $.userIdentity.type = "Root" && $.userIdentity.invokedBy NOT EXISTS && $.eventType != "AwsServiceEvent" }' \
  --metric-transformations \
      metricName=RootAccountUsageCount,metricNamespace=ShopMini/Security,metricValue=1,defaultValue=0 \
  --profile awssec-lab
```

`defaultValue=0`이 중요합니다. 이것이 없으면 **이벤트가 없는 기간에 데이터 포인트가 생기지 않아** 경보가 `INSUFFICIENT_DATA` 상태를 오갑니다. 30.2에서 이 지표에 알람을 붙입니다.

> 📖 *AWS Security Cookbook* 8장은 CloudTrail-CloudWatch 통합 시 부여되는 권한을 짚습니다. **"다음 권한이 부여되었다. 지정한 로그 그룹에 로그 스트림을 만들기 위한 `CreateLogStream`, CloudTrail 이벤트를 로그 스트림에 전달하기 위한 `PutLogEvents`."** 이어서 AWS가 제공하는 **"보안 및 네트워크 관련 API 활동에 대한 CloudWatch 알람"** CloudFormation 템플릿으로 알람 세트를 한 번에 만드는 방법도 소개합니다(30.3의 출발점).

### 구독 필터 — 중앙으로 흘려보내기

지표 필터가 "숫자만 뽑는다"면, **구독 필터는 로그 이벤트 자체를 실시간 스트리밍**합니다. 계정마다 흩어진 CloudWatch Logs를 로그 아카이브 계정으로 모으는 경로입니다.

```bash
# 운영 계정(111122223333)의 로그를 로그 계정의 Firehose로 스트리밍
aws logs put-subscription-filter \
  --log-group-name /shopmini/prod/os-audit \
  --filter-name ToCentralLogAccount \
  --filter-pattern "" \
  --destination-arn arn:aws:logs:ap-northeast-2:777788889999:destination:CentralLogDestination \
  --role-arn arn:aws:iam::111122223333:role/CWLtoCentralLogDestinationRole \
  --profile awssec-lab
```

`--filter-pattern ""`(빈 문자열)은 **전체 전달**입니다. 비용이 걱정되면 패턴으로 좁히되, **좁힌 것은 중앙에서 볼 수 없습니다.** OS 감사 로그처럼 조사의 핵심이 되는 것은 전량 보내십시오.

| 방식 | 용도 | 지연 |
|---|---|---|
| **구독 필터 → Firehose → S3(로그 계정)** | 전량 중앙 집계, 장기 보존 | 수십 초~수 분 |
| **구독 필터 → Lambda** | 변환·마스킹 후 전달 | 수 초 |
| **지표 필터 → CloudWatch 알람** | 즉시 경보(30.2) | 수 초~1분 |
| **`create-export-task` → S3** | 배치 아카이빙(수동·비실시간) | 수 시간 |

## 29.7 로그 보존 기간 정하기 🔴

### 원서의 권고

> 📖 *Practical Cloud Security* **1판** 7장: **"대부분의 로그는 최소 1년간 보존해야 하지만, 더 긴 보존 기간이 보안 사고 조사에 도움이 될 때도 있다. 산업 표준이나 규제 표준의 적용을 받는다면 해당 로그에 대한 구체적인 보존 요건을 확인하되, 보통은 1년이면 충분하다."**

2판은 같은 자리에 **한 문장을 추가**합니다. 이 차이가 이 절의 전부입니다.

> 📖 *Practical Cloud Security* **2판** 7장: **"대부분의 로그는 최소 1년간 보존해야 한다. 더 긴 보존 기간이 보안 사고 조사에 도움이 될 때도 있지만, 더 긴 보존 기간은 때때로 프라이버시 규제와 충돌할 수 있다. 산업 표준이나 규제 표준의 적용을 받는다면 해당 로그에 대한 구체적인 보존 요건을 확인하라. 다만 집필 시점 기준으로 1년은 대체로 안전한 선택이다."**

1판의 "1년이면 충분하다"가 2판에서 **"1년은 대체로 안전한 선택"** 으로 완화되고, **프라이버시 규제와의 충돌**이 명시적으로 들어왔습니다.

### ⚠️ 두 요구가 정면으로 충돌할 때

**보안**은 "오래 남겨라"라고 하고, **개인정보 보호**는 "목적 달성 후 지체 없이 파기하라"고 합니다. 둘 다 법적 요구인 경우가 많습니다. 이 충돌은 **"로그를 얼마나 오래 두느냐"로는 풀리지 않고, "로그에 무엇이 들어 있느냐"로 풉니다.**

| 로그 유형 | 개인정보 포함 여부 | 권장 보존 | 근거 |
|---|---|---|---|
| CloudTrail 관리 이벤트 | 거의 없음(IAM 주체명은 있음) | **최소 1년, 권장 2년+** | 침해 체류 기간이 길다 |
| CloudTrail 데이터 이벤트 | 객체 키에 포함될 수 있음 | 1년 | 키에 개인 식별자 넣지 말 것 |
| VPC 플로우 로그 | IP 주소 = 준식별자 | 90일~1년 | IP만으로는 특정 곤란 |
| AWS Config 구성 이력 | 없음 | **최소 1년** | 구성 드리프트 추적 |
| ALB/CloudFront 액세스 로그 | **IP + User-Agent + URL** | 90일 | 개인정보 성격 강함 |
| 애플리케이션 로그 | **설계에 따라 있음** | **30~90일** | 29.1의 비식별 ID 원칙 적용 |
| OS 감사·특권 세션 로그 | 계정명 | **400일+** | 내부자 조사용 |

**핵심 전략은 셋입니다.**

1. **29.1의 비식별화를 설계 단계에서 적용한다.** 개인정보가 없는 로그는 보존 기간 논쟁 자체가 없습니다. 가장 싸고 확실한 해법입니다.
2. **로그 그룹·버킷 프리픽스를 개인정보 포함 여부로 분리한다.** 섞어 두면 **가장 긴 요구와 가장 짧은 요구를 동시에 만족시킬 수 없습니다.**
3. **파기를 자동화하고 증명한다.** S3 수명 주기 규칙과 CloudWatch Logs 보존 정책이 파기 증적입니다. 수동 삭제는 증명할 수 없습니다.

### 계층형 보존 — 핫·웜·콜드

1년치 로그를 전부 CloudWatch Logs에 두면 비용이 감당되지 않습니다. **조회 빈도에 따라 저장 위치를 옮깁니다.**

```
[핫]  CloudWatch Logs (0~30일)      즉시 검색, Logs Insights, 실시간 경보
   │   구독 필터 / Firehose
   ▼
[웜]  S3 Standard (30~90일)          Athena 즉시 쿼리, Parquet 파티션
   │   수명 주기 규칙
   ▼
[콜드1] S3 Glacier Instant Retrieval (90~365일)   밀리초 조회, Athena 가능
   │   수명 주기 규칙
   ▼
[콜드2] S3 Glacier Deep Archive (1년~)            복원에 최대 12시간, 규제 대응용
   │   만료 규칙
   ▼
[파기]  삭제 (객체 잠금 보존 기간 경과 후)
```

| 계층 | 상대 저장 비용 | 조회 지연 | 적합한 질문 |
|---|---|---|---|
| CloudWatch Logs | 가장 비쌈 | 초 | "지금 무슨 일이 일어나고 있나" |
| S3 Standard | 기준(1×) | 초(Athena) | "지난주 사고의 경위는" |
| Glacier Instant Retrieval | 약 0.2× | 밀리초(조회 요금 별도) | "6개월 전에도 같은 IP가 있었나" |
| Glacier Deep Archive | 약 0.04× | 최대 12시간 | "3년 전 감사 증적을 제출하라" |

```bash
aws s3api put-bucket-lifecycle-configuration \
  --bucket shopmini-org-cloudtrail-logs \
  --lifecycle-configuration '{
    "Rules": [
      {
        "ID": "CloudTrailTieredRetention",
        "Filter": { "Prefix": "AWSLogs/" },
        "Status": "Enabled",
        "Transitions": [
          { "Days": 90,  "StorageClass": "GLACIER_IR" },
          { "Days": 365, "StorageClass": "DEEP_ARCHIVE" }
        ],
        "Expiration": { "Days": 2555 },
        "NoncurrentVersionExpiration": { "NoncurrentDays": 2555 }
      }
    ]
  }' \
  --profile awssec-lab
```

**⚠️ 객체 잠금과 수명 주기의 상호작용에 주의하십시오.** 컴플라이언스 모드 보존 기간이 남아 있으면 만료 규칙이 있어도 객체는 삭제되지 않습니다. 의도된 동작이지만 "만료시켰다고 생각한 데이터가 계속 과금되는" 상황을 만듭니다. **객체 잠금 보존 기간 ≤ 수명 주기 만료 기간**으로 설계하십시오.

### 🔴 반드시 이렇게 하라

- **CloudTrail 관리 이벤트는 최소 1년, 실무적으로 2년 이상.** 침해 체류 기간은 수개월 단위인 경우가 흔해, 1년치 로그로 "언제 처음 들어왔나"에 답하지 못하는 사고가 실제로 있습니다.
- **모든 로그 그룹과 버킷에 보존 정책을 명시한다.** "만료 없음"과 "규칙 없음"은 결정을 미룬 것이지 안전한 기본값이 아닙니다.
- **보존 기간의 근거(규제 조항 / 보안 판단)를 함께 문서화한다.** 감사의 "왜 90일입니까"와 개인정보 심사의 "왜 400일입니까"에 모두 답할 수 있어야 합니다.

**하지 않으면**: 결정적 시점의 로그가 이미 만료되었거나, 반대로 개인정보를 목적 달성 후에도 보관해 규제 위반이 됩니다. **두 실패는 동시에 일어납니다** — 앱 로그는 3년치 개인정보를 쌓아 두고 CloudTrail은 90일만 남아 있는 조직이 드물지 않습니다.

## 29.8 AWS Config로 구성 이력 추적 🧪

### CloudTrail과 무엇이 다른가

CloudTrail은 **"누가 무엇을 호출했는가"**(행위)를 남기고, Config는 **"그 결과 리소스가 어떤 상태였는가"**(상태)를 남깁니다. 둘은 대체재가 아니라 **짝**입니다.

> 📖 *AWS Security Cookbook* 8장: **"우리는 Config를 사용해 AWS 리소스의 구성을 기록하고 평가할 수 있다. 보안 표준을 정의하는 규칙을 만들고 그 표준을 준수하지 않는 리소스를 찾아낼 수 있다. Config는 문제가 탐지될 때마다 자동 교정(auto-remediation)도 지원한다."** 이 장에서는 **기록(구성 이력)** 만 다루고 **규칙과 준수 평가는 37.7**에 위임합니다.

| 질문 | CloudTrail | AWS Config |
|---|---|---|
| "누가 이 API를 호출했나" | ○ | × |
| "지금 sg-abc의 인바운드 규칙은" | × | ○ |
| "**3주 전 화요일에** sg-abc는 어떤 상태였나" | ×(재구성 필요) | ○ **구성 이력** |
| "이 보안 그룹을 쓰는 ENI는 무엇인가" | × | ○ **관계(relationships)** |
| "0.0.0.0/0을 여는 SG를 **전부** 찾아라" | × | ○ **고급 쿼리** |

### 레코더와 전송 채널 설정

**구성 레코더(configuration recorder)** 가 리소스 변경을 감지해 **구성 항목(configuration item, CI)** 을 만들고, **전송 채널(delivery channel)** 이 이를 S3(와 선택적으로 SNS)로 보냅니다.

원서는 설정 시 **"이 리전에서 지원되는 모든 리소스 기록"과 "글로벌 리소스 포함(예: AWS IAM 리소스)"** 을 모두 선택하라고 합니다. **글로벌 리소스 포함을 빠뜨리면 IAM 역할·정책 변경 이력이 통째로 빠집니다.**

```bash
# 1) 구성 레코더 (서비스 연결 역할 사용)
aws configservice put-configuration-recorder \
  --configuration-recorder '{
    "name": "default",
    "roleARN": "arn:aws:iam::111122223333:role/aws-service-role/config.amazonaws.com/AWSServiceRoleForConfig",
    "recordingGroup": {
      "allSupported": true,
      "includeGlobalResourceTypes": true
    }
  }' \
  --profile awssec-lab

# 2) 전송 채널 — 로그 아카이브 계정의 버킷으로
aws configservice put-delivery-channel \
  --delivery-channel '{
    "name": "default",
    "s3BucketName": "shopmini-org-config-history",
    "s3KeyPrefix": "config",
    "snsTopicARN": "arn:aws:sns:ap-northeast-2:444455556666:security-config-changes",
    "configSnapshotDeliveryProperties": { "deliveryFrequency": "TwentyFour_Hours" }
  }' \
  --profile awssec-lab

# 3) 기록 시작
aws configservice start-configuration-recorder \
  --configuration-recorder-name default \
  --profile awssec-lab
```

**전송 대상 버킷도 로그 아카이브 계정(`777788889999`)에 두십시오.** 구성 이력은 CloudTrail과 똑같이 "공격자가 지우고 싶어 하는" 데이터이고, 29.3의 SCP에 `config:StopConfigurationRecorder`가 들어 있는 이유입니다.

> 📖 *AWS Security Cookbook* 8장: **"AWS Config는 기록되는 규칙 평가 횟수를 기준으로 과금된다."** 여기에 더해 구성 항목 기록 자체에도 과금됩니다. **변경이 잦은 리소스 유형**(Auto Scaling 그룹, ENI 등)이 비용의 대부분인 경우가 있으므로, 비용이 문제라면 `allSupported: false`와 `resourceTypes`로 좁히되 **IAM·S3·EC2 보안 그룹·KMS는 반드시 포함**하십시오.

### "언제 누가 이 보안 그룹을 열었나"에 답하기

Config가 존재하는 가장 실용적인 이유입니다. 3단계로 답합니다.

**1단계 — 지금 열려 있는 보안 그룹을 전부 찾는다(고급 쿼리)**

```bash
aws configservice select-resource-config \
  --expression "
    SELECT
      resourceId,
      resourceName,
      awsRegion,
      configuration.ipPermissions
    WHERE
      resourceType = 'AWS::EC2::SecurityGroup'
      AND configuration.ipPermissions.ipRanges = '0.0.0.0/0'
  " \
  --profile awssec-lab
```

조직 전체를 한 번에 보려면 **애그리게이터(aggregator)** 를 만들고 `select-aggregate-resource-config`를 씁니다. 원서도 **"AWS Config에서 애그리게이터를 만들어 여러 계정과 모든 리전에 걸친 AWS 리소스 인벤토리나 Config 규칙 준수 상태를 볼 수 있다"** 고 합니다.

**2단계 — 그 보안 그룹의 구성 이력을 꺼낸다**

```bash
aws configservice get-resource-config-history \
  --resource-type AWS::EC2::SecurityGroup \
  --resource-id sg-0abcd1234EXAMPLE \
  --later-time 2026-09-06T00:00:00Z \
  --earlier-time 2026-08-01T00:00:00Z \
  --profile awssec-lab
```

각 구성 항목에는 `configurationItemCaptureTime`과 그 시점의 전체 구성 JSON이 들어 있습니다. **두 연속 항목을 비교하면 "무엇이 바뀌었는가"** 가 나오고, `configurationItemCaptureTime`이 **"언제"** 에 대한 답입니다.

**3단계 — 그 시각의 CloudTrail을 조회해 "누가"를 확정한다**

```bash
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=ResourceName,AttributeValue=sg-0abcd1234EXAMPLE \
  --start-time 2026-08-14T09:00:00Z \
  --end-time 2026-08-14T11:00:00Z \
  --profile awssec-lab
```

`AuthorizeSecurityGroupIngress` 이벤트의 `userIdentity`에서 **누가**, `sourceIPAddress`에서 **어디서**, `requestParameters`에서 **정확히 무엇을** 열었는지가 나옵니다.

> 💡 구성 항목에 관련 CloudTrail 이벤트 ID를 담는 필드가 있지만 **항상 채워지지는 않으므로**, 위처럼 **시각으로 좁혀 CloudTrail을 조회하는 절차**를 표준으로 삼는 편이 안정적입니다. 90일이 지난 이벤트는 `lookup-events`로 조회되지 않아 **트레일 로그를 Athena로** 봐야 합니다(30.6).

### 관계(relationships)가 주는 것

구성 항목에는 `relationships` 배열이 있어 **"이 보안 그룹을 참조하는 ENI/인스턴스"** 같은 연결이 기록됩니다. 사고 대응에서 **폭발 반경(blast radius)을 즉시 산정**하는 데 쓰입니다. "이 열린 보안 그룹이 붙어 있는 인스턴스가 몇 대인가"에 API 한 번으로 답하는 것과 콘솔을 뒤지는 것은 대응 속도가 다릅니다.

## 29.9 중앙 로그 계정 아키텍처 🔴

### 원서가 요구하는 구조

> 📖 *Practical Cloud Security* 1·2판 7장: **"개별 시스템 디스크가 가득 차서 로그 손실과 운영 문제를 일으킬 수 있고, 시스템에 침입한 공격자가 자신의 흔적을 지우려고 로그를 삭제할 수 있다. (…) 클라우드에서는 로그 집계 서비스를 다른 관리 자격 증명을 가진 별도의 클라우드 계정에 둠으로써 같은 이익의 상당 부분을 훨씬 쉽게 얻을 수 있다. 그러면 주 시스템에 접근할 수 있는 누군가가 로그를 지워 버릴 수 없다."**

**"다른 관리 자격 증명(different administrative credentials)"** 이 핵심 구절입니다. 같은 계정 안에서 IAM 정책으로 나누는 것으로는 부족하고 **계정 경계**여야 합니다.

### 구조가 만족해야 하는 다섯 가지 불변식

| # | 불변식 | 구현 |
|---|---|---|
| 1 | **운영 계정 관리자는 로그를 읽을 수도, 지울 수도 없다** | 로그 버킷 정책이 `cloudtrail.amazonaws.com` 등 서비스 주체의 `PutObject`만 허용. 운영 계정 IAM 주체에 대한 허용 문 없음 |
| 2 | **로그 계정 관리자도 로그를 지울 수 없다** | 객체 잠금 COMPLIANCE 모드(15.9) |
| 3 | **트레일을 끄면 즉시 알려진다** | SCP Deny + `StopLogging` 경보 + 로그 유입 중단 경보(30.3) |
| 4 | **로그가 변조되면 증명할 수 있다** | 로그 파일 무결성 검증 자동 실행(29.3) |
| 5 | **로그 계정 자체의 접근이 통제·감시된다** | 아래 참조 |

### ⚠️ 로그 계정 자체가 새로운 단일 실패점이 된다

중앙 로그 계정은 조직 전체의 활동 기록을 한곳에 모으므로 **공격자에게 가장 매력적인 표적**이 됩니다. 여기를 뚫으면 전 계정의 IAM 주체 이름, 리소스 구조, 접근 패턴, 그리고 (데이터 이벤트를 켰다면) 어떤 객체가 어디 있는지까지 알 수 있습니다. **로그는 그 자체로 정찰 자료입니다.**

| 위험 | 통제 |
|---|---|
| 로그 계정 자격 증명 탈취 | **일상 접근 계정으로 쓰지 않는다.** 사람은 평소 로그인하지 않고, 조회는 보안 계정에서 크로스 계정 읽기 전용 역할로 |
| 로그 계정 관리자의 내부자 위협 | 객체 잠금으로 삭제 불가. **읽기 행위 자체를 S3 데이터 이벤트로 기록**하고 보안 계정으로 전송 |
| 로그 버킷의 실수 공개 | 계정 수준 퍼블릭 액세스 차단(15.2), `aws:SecureTransport` Deny, VPC 엔드포인트 한정 정책 |
| 로그 계정 KMS 키 삭제 | 키 삭제 예약(`ScheduleKeyDeletion`) 경보 + SCP Deny(14장) |
| 로그 계정 루트 사용자 | MFA 하드웨어 토큰, 자격 증명 물리 보관, **루트 사용 시 즉시 경보**(30.3) |

**분석은 로그 계정에서 하지 않습니다.** 로그 계정은 **저장 전용**으로 두고, 보안 도구 계정(`444455556666`)이 Athena·Security Lake·SIEM으로 **읽기 전용** 접근을 합니다. 저장과 분석을 분리하면 분석 도구가 침해되어도 로그는 남습니다.

### 위임 관리자

> 💡 **원서 이후 변경** — 원서 시점에는 조직 트레일과 Config 집계를 관리 계정에서 운영해야 했지만, 현재는 **위임 관리자**를 지정할 수 있습니다.

```bash
# 관리 계정에서 실행: CloudTrail 위임 관리자를 로그 아카이브 계정으로
aws cloudtrail register-organization-delegated-admin \
  --member-account-id 777788889999 \
  --profile awssec-lab

# AWS Config의 조직 집계·조직 규칙 관리 위임 (보안 도구 계정)
aws organizations register-delegated-administrator \
  --account-id 444455556666 \
  --service-principal config-multiaccountsetup.amazonaws.com \
  --profile awssec-lab
```

위임의 목적은 편의가 아니라 **관리 계정 로그인 빈도를 0에 가깝게 만드는 것**입니다. 12장의 원칙 — 관리 계정에서는 아무 일도 하지 않는다 — 을 로깅 운영에서도 지키는 장치입니다.

**하지 않으면**: 운영 계정 관리자 권한 하나가 **예방·탐지·조사 능력을 동시에** 무력화합니다. 침해의 흔한 패턴은 "권한 상승 → 로깅 무력화 → 목적 수행"이고, 두 번째 단계를 막지 못하면 세 번째 단계를 관측할 수 없습니다. **로그 계정 분리는 이 사슬을 끊는 구조적 조치이며 IAM 정책으로 대체할 수 없습니다.**

## 🔴 필수 구성 체크리스트

- [ ] 조직 트레일을 **다중 리전 + 글로벌 서비스 이벤트 + 로그 파일 검증 + SSE-KMS** 로 생성했다
- [ ] 트레일 로그가 **로그 아카이브 계정(`777788889999`)** 의 버킷으로 간다
- [ ] 로그 버킷에 **버전 관리 + 객체 잠금(COMPLIANCE)** 이 걸려 있다
- [ ] 버킷 정책에 **`aws:SourceArn` + `aws:SourceAccount`** 조건이 있다
- [ ] 멤버 계정의 **중복 개별 트레일을 정리**해 이중 과금을 없앴다
- [ ] 민감 버킷의 **S3 데이터 이벤트**를 고급 이벤트 선택기로 범위를 좁혀 켰다
- [ ] **인사이트 이벤트**(`ApiCallRateInsight`, `ApiErrorRateInsight`)를 켰다
- [ ] `validate-logs`를 **주기 자동 실행**하고 실패를 경보로 연결했다
- [ ] 로깅 조작 API를 **SCP로 Deny** 했고, 예외 역할은 하나뿐이며 사용이 경보된다
- [ ] **로그 유입 중단**(`IncomingLogEvents` = 0)에 경보를 걸었다
- [ ] 모든 운영 VPC에 **플로우 로그**를 켰고 **사용자 지정 형식**에 `flow-direction`·`instance-id`·`pkt-*` 를 포함했다
- [ ] **Route 53 Resolver 쿼리 로깅**을 켰다(플로우 로그가 DNS를 남기지 않으므로)
- [ ] **모든 로그 그룹에 보존 기간을 명시**했다("만료 없음"이 남아 있지 않다)
- [ ] 특권 세션·OS 감사 로그를 **별도 로그 그룹 + 별도 KMS 키 + 최소 인원**으로 격리했다
- [ ] **AWS Config 레코더**가 켜져 있고 **글로벌 리소스 유형을 포함**한다
- [ ] Config 전송 채널의 S3 버킷이 **로그 아카이브 계정**에 있다
- [ ] 로그 계정에 **일상 접근이 없고**, 조회는 보안 계정의 읽기 전용 역할로만 한다
- [ ] 보존 기간마다 **근거(규제 조항 / 보안 판단)를 문서화**했다
