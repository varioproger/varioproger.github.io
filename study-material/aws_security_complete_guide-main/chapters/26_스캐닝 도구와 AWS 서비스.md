# 26장. 스캐닝 도구와 AWS 서비스

> **이 장에서 다루는 것**
> - **도구 지형도** — 원서의 도구 분류 13종 ↔ 25.2의 취약 지점 7계층 매핑. ⚠️ 1판 「Cloud Provider Security Management Tools」가 2판에서 **CWPP**로 바뀐 의미
> - **애플리케이션 보안 테스트 4종 + RASP** — SAST·DAST·SCA·IAST의 사각지대와 **CI/CD 배치 위치**
> - **Amazon Inspector** 🧪 — 조직 단위 활성화, EC2·ECR·Lambda 자동 스캔, SSM 의존성, 억제 규칙. 💡 원서의 Inspector(Classic)와 현재 Inspector는 **다른 서비스**
> - **수동 코드 리뷰와 모의 침투 테스트** — ⚠️ **AWS 침투 테스트 정책**(허용 범위와 금지 행위)
> - **버그 바운티와 제보 창구** — VDP와의 차이, security.txt, 갈취와 제보의 경계
> - **CSPM** 🔴 — 설정 오류를 취약점으로 다루기. Config 규칙, Security Hub 보안 표준
> - **Trusted Advisor** 🧪 — ⚠️ 지원 플랜 의존성, `support` API 조회
>
> **선행 지식**: 22장(패치 관리), 24장(이미지 스캔), 25장(취약점 관리 체계·7계층·지표)
> **난이도**: ★★★

25장에서 세운 것은 **틀**이었습니다. 취약 지점 7계층, 발견→우선순위→조치→검증→보고 프로세스, 커버리지와 MTTR 같은 지표. 그 틀은 "무엇이 그 칸을 채우는가"를 말하지 않습니다. 이 장이 그 칸을 채웁니다 — **25장이 "무엇을 왜"라면 26장은 "무엇으로"입니다.** 다만 도구를 늘리는 것 자체는 성과가 아닙니다.

> 📖 *Practical Cloud Security* 2판 5장 「Vulnerability Management」: **"흔한 함정은 어딘가의 모범 사례 목록에서 체크박스 몇 개를 채우려고 네다섯 벌의 서로 다른 도구와 프로세스를 갖춰 두는 것이다. 그중 어느 것도 실제로는 취약점을 찾고 고치는 데 큰 가치를 주지 못한다."**

저자의 기준은 일관됩니다. **가장 큰 구멍부터 막고, 거기서 가치를 뽑아낸 다음 넘어간다.** 이 장의 목록도 전부 도입하라는 뜻이 아니라 **어느 파이프가 가장 굵게 새는지**를 판별하기 위한 지도입니다.

## 26.1 도구 지형도

### 원서의 분류 체계

2판 5장 「Finding and Fixing Vulnerabilities」는 도구를 아래 범주로 나누면서 곧바로 단서를 답니다 — **"많은 제품이 이 범주 중 여러 개를 동시에 다룬다."** 범주는 제품 분류가 아니라 **탐지 원리의 분류**입니다.

| # | 원서 범주 | 탐지 원리 | 주 커버 계층(25.2) |
|---|---|---|---|
| 1 | Network Vulnerability Scanners | 네트워크 주소에 요청을 던져 응답으로 판단 | 네트워크, 미들웨어 |
| 2 | Agentless Scanners and Configuration Management Systems | 자격 증명으로 로그인해 내부 점검 | OS, 미들웨어 |
| 3 | Agent-Based Scanners and Configuration Management Systems | 각 시스템의 에이전트가 결과를 push | OS, 미들웨어 |
| 4 | **Cloud Workload Protection Platforms (CWPP)** | 위 결과 + 파이프라인 + 클라우드 구성 정보를 한 대시보드로 | 전 계층 집계 |
| 5 | Container Scanners | 이미지 분해 스캔 / 호스트 에이전트가 실행 컨테이너 점검 | 미들웨어, OS, 가상 인프라 |
| 6 | Dynamic Application Scanners (DAST) | 실행 중인 URL·API를 사용자처럼 두드림 | 애플리케이션 |
| 7 | Static Application Scanners (SAST) | 작성한 소스 코드를 직접 분석 | 애플리케이션 |
| 8 | Software Composition Analysis Tools (SCA) | 오픈소스 의존성 목록 ↔ 알려진 취약점 대조 | 애플리케이션 |
| 9 | Interactive Application Scanners (IAST) | 애플리케이션 안에서 실행을 관찰 | 애플리케이션 |
| 10 | Runtime Application Self-Protection (RASP) | 실행 중 공격을 **차단** (탐지 기술 아님) | 애플리케이션 |
| 11 | Manual Code Reviews | 사람이 코드를 읽음 | 애플리케이션, 데이터 접근 |
| 12 | Penetration Tests | 사람이 실제로 침투를 시도 | 전 계층 |
| 13 | User Reports | 사용자·연구자가 제보 | 전 계층 |

7계층 중 **물리 인프라**와 **가상 인프라 대부분**은 AWS 책임이라 우리 도구가 닿지 않습니다(2.1). 위 표는 사실상 **데이터 접근·애플리케이션·미들웨어·OS·네트워크** 다섯 칸의 문제입니다. 그리고 **데이터 접근 계층 — IAM·버킷 정책의 과잉 권한 — 을 덮는 자동 도구는 위 목록에 사실상 없습니다.** 26.6의 CSPM과 IAM Access Analyzer(7.7)가 그 칸을 맡습니다.

### ⚠️ 1판 → 2판: "클라우드 제공자 보안 관리 도구"가 CWPP가 된 이유

같은 자리의 범주 이름이 판을 넘기며 바뀌었습니다. 문장을 나란히 놓으면 보입니다.

> 📖 *Practical Cloud Security* 1판 5장, 「Cloud Provider Security Management Tools」: **"이 범주의 도구들은 일반적으로 특정 클라우드 제공자에 한정된다. 대개 에이전트 또는 에이전트리스 방식으로 구성·취약점 관리 정보를 수집하거나, 서드파티 도구에서 그 정보를 끌어온다."**

> 📖 *Practical Cloud Security* 2판 5장, 「Cloud Workload Protection Platforms」: **"(…) 도구는 클라우드 제공자와 서드파티 양쪽에서 제공된다. 대개 에이전트 또는 에이전트리스 방식으로, 배포 파이프라인을 통해, 또는 서드파티 도구로부터 정보를 수집한다. (…) 개발 및 배포 단계 전반에 걸친 여러 보안 기능의 '원스톱 대시보드'로 마케팅된다. (…) 때로는 클라우드 네이티브 애플리케이션 보호 플랫폼(CNAPP)이라고도 불린다."**

세 군데가 달라졌습니다.

| 축 | 1판 | 2판 | 실무적 함의 |
|---|---|---|---|
| **공급자** | "특정 클라우드 제공자에 한정" | "제공자와 서드파티 **양쪽**" | 제공자 네이티브 도구가 유일한 선택지가 아님. 멀티 클라우드에서는 서드파티가 기본 후보 |
| **수집 경로** | 에이전트/에이전트리스/서드파티 | + **배포 파이프라인** | 런타임에 스캔하는 도구에서 **파이프라인에서 차단하는 도구**로 무게중심 이동(28.3) |
| **범위** | "해당 제공자에서의 여러 보안 기능" | "**개발 및 배포 단계 전반**" | 좌측 이동(shift-left)이 범주 정의 안으로 들어옴 |
| **별칭** | (없음) | **CNAPP** | 벤더 용어의 상위 개념화 |

**이름이 제공자 중심에서 워크로드 중심으로 바뀐 것이 핵심입니다.** 1판의 정의는 "AWS를 쓰니 AWS 콘솔에서 보는 대시보드"였고, 2판은 "워크로드가 어디서 돌든, 어느 단계에 있든 따라가는 플랫폼"입니다. AWS에서는 Security Hub가 1판식 위치에, Inspector + ECR 스캔 + 파이프라인 게이트의 조합이 2판식 위치에 가깝습니다.

> 💡 **원서 이후 용어** — 2판이 쓰는 것은 CWPP와 CNAPP 둘뿐입니다. CSPM·CIEM 등은 원서 이후 정착한 용어이며, 정리는 26.6에 모았습니다.

### 네트워크 스캐너: "격리했으니 필요 없다"는 착각

> 📖 2판 5장: **"격리된 컴포넌트가 있다는 이유만으로 네트워크 취약점 스캔이 불필요하다고 생각하는 실수를 하지 말라. (…) 알려지지 않은 취약점의 위험이, 공격자가 그 방화벽 규칙을 이용해 제한 구역에 들어올 위험보다 훨씬 높다."**

근거는 경험입니다. **경계를 넘어와 내부의 취약한 시스템을 익스플로잇한 사고는 여러 번 봤지만, 공격자가 스캐너를 장악해 그 네트워크 접근을 이용한 사고는 보거나 들은 적이 없다**는 것입니다. ShopMini의 private-app·isolated-data 서브넷도 예외 구역이 아닙니다. 다만 **인터넷 노출 앞단이 1순위, 내부 서브넷이 2순위**이고, 내부 스캔은 VPC 안 릴레이를 두고 아웃바운드로 제어합니다.

네트워크 스캐너는 **자기가 무엇과 대화하는지 모른 채** 열린 포트의 응답만 봅니다.

> 📖 2판 5장: **"도구는 흔히 컴포넌트가 보고한 버전을 사용하는데, 그 버전이 정확하지 않거나 보안 패치 설치를 반영하지 못할 수 있다. 오탐을 마스킹하는 잘 문서화된 효과적인 프로세스가 반드시 있어야 한다. 그렇지 않으면 일부가 틀렸다는 이유로 팀이 스캔 결과 전체를 무시하게 된다."**

25.5의 "오탐 비율" 지표가 필요한 이유가 여기 있습니다. **오탐 마스킹 절차가 없는 스캐너는 결국 아무도 안 보는 리포트가 됩니다.**

### 에이전트 vs 에이전트리스: 원서의 4축과 AWS 매핑

원서는 두 모델을 자격 증명·배포·네트워크·최소 권한 네 축으로 비교합니다. AWS에서는 대부분 **SSM Agent를 쓸 것인가**의 문제로 귀결됩니다.

| 축 | 에이전트리스 | 에이전트 기반 | AWS에서의 형태 |
|---|---|---|---|
| **자격 증명** | 스캔 대상 전체의 (보통 특권) 자격 증명을 스캐너가 보유 → **스캐너가 매력적인 표적** | 최초 배포 시에만 권한 필요. 콘솔은 에이전트가 허용한 만큼만 | SSM Agent + 인스턴스 프로파일. 중앙에 SSH 키를 쌓아 두지 않음 |
| **배포** | 배포할 코드 없음. 대신 대상에 사용자 ID·sudo 구성 필요 | 에이전트를 배포·최신 유지해야 하고, **에이전트 취약점이 전체 인프라를 위협** | 골든 AMI에 SSM Agent 포함(22.5). Amazon Linux·Windows는 기본 포함 |
| **네트워크** | **인바운드 접근 필요** → 경계에 구멍 | **아웃바운드만** | SSM은 인터페이스 엔드포인트 경유 아웃바운드(20.2). 인바운드 22/3389 불필요 |
| **최소 권한** | 스캐너용 ID의 권한을 좁힘. 다만 전체 관리자 권한을 요구하는 제품이 많음 | SELinux/AppArmor 등으로 프로세스 단위 제약이 더 잘 먹힘 | 인스턴스 프로파일에 `AmazonSSMManagedInstanceCore`만 (8.2) |

저자의 결론은 **"보통 에이전트 기반을 선호하지만 양쪽 다 좋은 논거가 있고, 가장 중요한 것은 구성·취약점 관리를 어떤 식으로든 하는 것"** 입니다. 그리고 결정적인 단서를 답니다.

> 📖 2판 5장: **"여러 클라우드 제공자가 자사 클라우드 환경 지원의 일부로 에이전트 기반 스캐너를 제공한다. 이런 도구는 자동 배포가 더 간단하고, 자산 목록을 수동으로 뽑아 스캐너에 넣어 줄 필요도 없다."**

**이것이 26.3의 Amazon Inspector가 앉는 자리입니다.** 자산 목록을 스캐너에 먹여 주는 작업 — 25.1의 "짧은 수명의 자산을 스캐너가 못 따라가는" 문제 — 이 제공자 네이티브 도구에서는 구조적으로 사라집니다.

### 도구 배치 전에: 두 종류의 누수

원서는 3장의 자산 관리 파이프라인을 다시 꺼내 도구 배치를 **누수 막기**로 설명합니다. 두 지점이 샙니다.

| 누수 | 정의 | AWS에서의 전형적 모습 | 지표(25.5) |
|---|---|---|---|
| **도구 누수(tooling leaks)** | 알고 있는 자산인데 도구가 덮지 못함 | Inspector를 켰지만 SSM 에이전트가 없어 EC2 절반이 스캔 안 됨. 특정 리전만 활성화 | 도구 커버리지 |
| **결과 누수(findings leaks)** | 도구는 찾아냈는데 아무도 처리하지 않음 | Security Hub에 4만 건이 쌓여 있고 담당자 미지정 | 미조치 시스템 비율 |

> 📖 2판 5장: **"어느 영역에 도구가 아예 없거나 도구가 자산 상당수를 못 보고 있어서 물이 콸콸 새고 있다는 것을 깨닫게 되는 경우가 있다. 이는 알려지지 않은 리스크로 이어질 수 있다!"**

## 26.2 애플리케이션 보안 테스트 4종

0장 0.1에서 **애플리케이션 시큐어 코딩 자체는 범위 밖이지만 파이프라인 배치는 26장에서 다룬다**고 선언했습니다. 여기가 그 자리입니다. XSS를 어떻게 고치는가는 다루지 않고, **XSS를 언제·어디서 잡을 것인가**를 다룹니다.

### 4종 + 1: RASP는 테스트 도구가 아니다

절 제목의 "4종"은 오타가 아닙니다.

> 📖 2판 5장 「Runtime Application Self-Protection Scanners (RASP)」: **"RASP 도구는 앞서 설명한 스캐너들과 비슷하게 들릴 수 있지만, 이것은 스캐닝 기술이 아니다. (…) RASP 도구는 취약점을 탐지하는 것이 아니라 공격을 차단하도록 설계되었다."**

즉 **테스트(발견) 도구는 SAST·DAST·SCA·IAST 4종**이고 **RASP는 WAF와 같은 계열의 방어 통제**입니다. 원서도 RASP를 WAF와 함께 네트워크 보안 장에서 다룹니다(본서 23.8·23.9).

### 4종 비교

| 축 | **SAST** | **DAST** | **SCA** | **IAST** |
|---|---|---|---|---|
| 보는 대상 | 내가 쓴 소스 코드 | 실행 중인 URL·REST API | 오픈소스 의존성 목록 | 실행 중인 코드 내부 |
| 원리 | 정적 분석 | 사용자처럼 요청을 보냄 | 컴포넌트·버전 ↔ 취약점 DB 대조 | 앱 옆에 로드되어 실행을 관찰 |
| 대표적으로 잡는 것 | 메모리 누수, off-by-one, 인젝션 패턴 | XSS, SQL 인젝션 | Log4j·Struts·Spring 류 의존성 CVE | 정적+동적 결합 결함 |
| 못 잡는 것 | 런타임/구성/의존성 문제 | 코드 내부, 도달 못 한 경로 | 내가 쓴 코드의 결함 | 도구가 지원 안 하는 언어·런타임 |
| 필요 조건 | 언어 지원 | 앱 자격 증명이 필요한 경우 많음 | 의존성 매니페스트 | 언어·런타임 지원 + 앱 옆 배포 |
| 대표 실패 모드 | **높은 오탐 → 개발자 보안 피로** | 인증 뒤 경로 미탐 | 전이 의존성 누락 | 운영 성능 저하 |
| 파이프라인 위치 | **커밋 직후** | 테스트 환경 배포 후 / 정기 | 커밋 + 빌드 + **배포 후 상시 재평가** | 기능 테스트·DAST와 동시 |

각 도구에 붙은 단서 중 배치 판단에 직결되는 것만 옮깁니다.

- **SAST** — **"새 코드가 커밋되자마자 배포 파이프라인의 일부로 실행하기에 아주 좋은 후보"**. 다만 **"가장 큰 문제는 오탐률이 높은 경향이 있어 개발자에게 '보안 피로'를 유발할 수 있다"**. 처방은 **개발자가 오탐을 빠르고 쉽게 마스킹할 수 있게 만들어라**입니다.
- **DAST** — 원서는 WAF와의 관계를 짚습니다. **"동적 스캐너가 찾은 취약점 일부는 WAF로도 차단할 수 있다. 그러면 수정 우선순위를 낮출 수는 있겠지만, 심층 방어를 위해 어차피 꽤 빨리 고쳐야 한다. 제대로 구성되어 있지 않으면 공격자가 WAF를 우회해 직접 공격할 수 있다."** — 23.9의 오리진 직접 접근 차단이 다시 나옵니다.
- **SCA** — 라이선스 점검과 **SBOM 생성**까지 포함되며, 원서는 미 연방정부가 구매 제품에 SBOM을 요구하기 시작했다고 적습니다(27.2).
- **IAST** — **"SAST나 DAST 어느 쪽보다도 문제를 더 효과적으로 찾아내고 오탐을 제거하는 경우가 많다."** 대가는 성능이며, 완화책은 수평 확장 또는 **운영 부하를 모사한 테스트 환경에서 파이프라인이 돌리는 것**입니다.

원서가 반복하는 요구가 하나 더 있습니다 — **결과를 이슈 트래커에 흘려보내라.** **"DAST 도구는 누군가 리포트를 확인해 주기를 기대할 것이 아니라, 결과를 이슈 추적 시스템으로 보내야 한다."** 26.1의 "결과 누수"를 막는 유일한 구조적 방법입니다.

### 파이프라인 배치도

ShopMini의 CI/CD에 얹으면 이렇습니다. 괄호 안은 실패 시 동작입니다.

```text
[커밋]
  ├─ SAST            (High 이상 → PR 블록, 오탐은 인라인 마스킹 + 만료일)
  ├─ SCA             (Critical 의존성 → PR 블록)
  ├─ 시크릿 스캔      (탐지 → 즉시 블록 + 키 폐기 절차, 11.1)
  └─ IaC 정적 분석    (28.2)
        ↓
[빌드]
  └─ 컨테이너 이미지 빌드 → ECR 푸시
        ↓
[레지스트리]
  └─ ECR 향상된 스캔 = Inspector (24.2, 26.3)
        (Critical → 배포 파이프라인 중단)
        ↓
[테스트 환경 배포]
  ├─ DAST            (신규 High → 배포 게이트)
  ├─ IAST            (기능 테스트와 동시 실행)
  └─ 네트워크 취약점 스캔 (원서 권고: 테스트 환경 스캔을 배포 프로세스에 포함)
        ↓
[운영 배포]
  ├─ Inspector 상시 스캔 (EC2·ECR·Lambda, 26.3)
  ├─ AWS WAF / RASP      (차단, 23.8)
  └─ CSPM 상시 평가       (Config·Security Hub, 26.6)
```

> 📖 2판 5장은 네트워크 스캔에도 같은 배치를 권합니다. **"가능하다면 테스트 환경에 대한 네트워크 취약점 스캔을 배포 프로세스에 포함시켜야 한다. 결과는 버그 트래커로 보내고, 오탐으로 표시되지 않은 한 배포를 차단하는 것이 이상적이다."**

**게이트를 세울 때 두 가지.** 첫째, **차단 기준을 처음부터 높게 잡지 마십시오.** 기존 코드베이스에 SAST를 붙이면 첫 실행에서 수천 건이 나옵니다. "오늘 이후 신규 High만 차단"으로 시작해 기준선을 점진적으로 내리는 것이 유일하게 작동합니다. 둘째, **예외에 만료일을 붙이십시오.** 만료 없는 예외는 영구 면제가 되고, 결과는 25.6의 "스캔하지 않으면 취약점이 0으로 보인다"와 같아집니다.

> 💡 **AWS 매니지드 옵션** — AWS는 SAST 성격을 **Inspector의 Lambda 코드 스캔**으로, SCA 성격을 **Inspector의 ECR·Lambda 의존성 스캔**과 **SBOM 내보내기**로 제공합니다(26.3). 일반 애플리케이션 소스의 SAST·DAST·IAST는 여전히 서드파티·오픈소스 영역이며, CodeBuild 단계 실행이 일반적입니다. 원서는 도구 선정에 **OWASP Source Code Analysis Tools** 페이지를 참고 자료로 제시합니다.

## 26.3 Amazon Inspector 🧪

### 💡 원서의 Inspector와 지금의 Inspector는 다른 서비스입니다

> 💡 **원서 이후 변경 — Inspector Classic과 현행 Inspector** — Cookbook 9장의 두 레시피와 *Practical Cloud Security* 1판 도구 목록이 설명하는 Inspector는 현재 **Amazon Inspector Classic**으로 분류되는 이전 세대 서비스입니다. **평가 대상 → 평가 템플릿 → 규칙 패키지 → 주기적 실행** 구조 자체가 현행에는 없고, CLI 네임스페이스도 다릅니다(구 `aws inspector` / 현 `aws inspector2`). 신규 구성에 Classic을 쓰지 마십시오.

두 세대를 나란히 놓으면 무엇이 계승되고 무엇이 사라졌는지 보입니다.

| 축 | 원서가 설명하는 Inspector (Classic) | 현행 Amazon Inspector |
|---|---|---|
| 실행 모델 | 템플릿을 **주기 실행**(레시피에서는 주 1회) | **상시·이벤트 기반** 자동 재스캔 |
| 범위 지정 | 평가 대상 + 태그로 대상 EC2 선택 | 활성화하면 **계정 내 지원 리소스 전체** 자동 포함 |
| 점검 내용 | 규칙 패키지 4종: Network Reachability, Security Best Practices, CVE, CIS OS Benchmarks | CVE + 네트워크 도달성, ECR 이미지, Lambda 의존성·코드 |
| 대상 | EC2 only | **EC2 · ECR 이미지 · Lambda 함수** |
| 에이전트 | 별도 Inspector 에이전트 (SSM Run Command로 설치) | **SSM Agent 재사용**(별도 에이전트 없음) + 에이전트리스 옵션 |
| 결과 전달 | SNS 주제 + 콘솔 리포트(PDF) | 콘솔·API + **Security Hub·EventBridge 자동 연동** |
| 조직 단위 | 계정별 개별 구성 | **Organizations 위임 관리자** |

📖 Cookbook 9장의 정리. **"네트워크 평가에서는 AWS가 네트워크 구성 분석을 수행해 VPC 바깥에서 도달 가능한 포트를 점검한다. (…) 호스트 평가에서는 AWS가 CVE를 점검하고 호스트 하드닝(CIS 벤치마크)과 그 밖의 보안 모범 사례를 수행한다."** 전제 조건도 명시합니다 — **"EC2 머신에 Inspector 에이전트를 설치하려면 SSM Agent가 설치되어 있어야 하고, Run Command를 허용하는 IAM 역할이 있어야 한다."**

**이 SSM 의존성만은 그대로 계승되었습니다.** 별도 Inspector 에이전트가 사라진 대신, 현행 Inspector의 EC2 스캔은 SSM Agent와 SSM 관리형 인스턴스 상태에 직접 의존합니다.

2판의 도구 목록에서 Inspector 설명이 길어진 것도 이 변화를 반영합니다.

> 📖 1판 5장 도구 목록: **"Amazon Inspector는 Linux와 Windows 시스템의 누락된 패치와 부적절한 구성을 스캔할 수 있는 에이전트 기반 스캐너다."**
> 📖 2판 5장 도구 목록: **"Amazon Inspector는 Linux와 Windows 시스템의 누락된 패치와 부적절한 구성을 스캔할 수 있는 에이전트 기반 스캐너이며, 컨테이너 및 서버리스 스캐너이기도 하다."** — 뒷부분(컨테이너·서버리스)이 2판에서 추가된 서술입니다.

### 🧪 활성화 — 계정 단위와 조직 단위

단일 계정에서는 한 줄입니다.

```bash
# 운영 계정(111122223333)에서 3종 스캔 활성화
aws inspector2 enable \
  --resource-types EC2 ECR LAMBDA LAMBDA_CODE \
  --region ap-northeast-2 \
  --profile awssec-lab

# 활성화 상태 확인
aws inspector2 batch-get-account-status \
  --region ap-northeast-2 --profile awssec-lab
```

그러나 **계정별로 켜는 방식은 26.1의 "도구 누수"를 그대로 만듭니다.** 신규 계정이 생기면 아무도 켜지 않고 그 계정은 조용히 사각지대가 됩니다. 조직 단위 구성이 기본값이어야 합니다.

```bash
# 1) 관리 계정(123456789012)에서 보안 도구 계정을 위임 관리자로 지정
aws inspector2 enable-delegated-admin-account \
  --delegated-admin-account-id 444455556666 \
  --region ap-northeast-2

# 2) 위임 관리자(444455556666)에서 신규 계정 자동 활성화 켜기
aws inspector2 update-organization-configuration \
  --auto-enable ec2=true,ecr=true,lambda=true,lambdaCode=true \
  --region ap-northeast-2

# 3) 기존 멤버 계정들 일괄 활성화
aws inspector2 associate-member --account-id 111122223333 --region ap-northeast-2
aws inspector2 enable \
  --account-ids 111122223333 555555555555 \
  --resource-types EC2 ECR LAMBDA LAMBDA_CODE \
  --region ap-northeast-2
```

⚠️ **Inspector는 리전 서비스입니다.** 사용하는 모든 리전에서 활성화하고, 미사용 리전은 37.2의 리전 제한 SCP로 봉인해 두십시오.

### 스캔 대상 3종과 전제 조건

| 대상 | 무엇을 보는가 | 전제 조건 | ⚠️ 흔한 미커버 원인 |
|---|---|---|---|
| **EC2** | OS 패키지 CVE, 프로그래밍 언어 패키지, 네트워크 도달성 | SSM Agent 실행 + 인스턴스 프로파일에 `AmazonSSMManagedInstanceCore` + SSM 관리형 인스턴스로 등록 | 프라이빗 서브넷에서 SSM 엔드포인트 미구성(20.2), 인스턴스 프로파일 미부착, SSM Agent 미실행/구버전 |
| **ECR 이미지** | 이미지 레이어의 OS 패키지 + 애플리케이션 의존성 | 리포지토리 스캔 설정이 **향상된 스캔(enhanced)** | 리포지토리가 기본 스캔에 머물러 있음, 재스캔 기간 만료 |
| **Lambda** | 함수 의존성(표준 스캔) + **함수 코드 자체**(코드 스캔) | 코드 스캔은 `LAMBDA_CODE` 별도 활성화 | 레이어에 든 의존성을 잊음, 코드 스캔 미활성화 |

**커버리지를 지표로 만드십시오.** 25.5의 "도구 커버리지"가 한 줄로 나옵니다.

```bash
# 스캔되지 않고 있는 리소스만 뽑기 (도구 누수 탐지)
aws inspector2 list-coverage \
  --filter-criteria '{"scanStatusCode":[{"comparison":"NOT_EQUALS","value":"ACTIVE"}]}' \
  --region ap-northeast-2 --profile awssec-lab
```

> 💡 **에이전트리스 EC2 스캔** — 현행 Inspector는 SSM 기반 에이전트 스캔 외에 **EBS 스냅샷을 이용한 에이전트리스 스캔**을 제공하며, 둘을 함께 쓰는 하이브리드 모드도 선택할 수 있습니다. SSM Agent를 넣을 수 없는 인스턴스의 커버리지 구멍을 메우는 용도이며, 원서 집필 이후 추가된 기능입니다.

### 심각도와 결과 조회

심각도는 `INFORMATIONAL`·`LOW`·`MEDIUM`·`HIGH`·`CRITICAL`·`UNTRIAGED`로 표기되고, Inspector 점수는 **CVSS 기본 점수에 환경 요인(대표적으로 네트워크 도달성)을 반영**해 조정됩니다. 25.4의 "CVSS만으로는 부족하고 실제 노출 여부를 결합해야 한다"가 서비스에 부분 구현된 셈입니다. **다만 데이터 민감도는 반영되지 않습니다.** 그 축은 12.3의 `DataClass` 태그로 우리가 결합합니다.

```bash
# EC2의 Critical + 공개된 익스플로잇이 존재하는 것만 = 우선순위 큐 최상단
aws inspector2 list-findings \
  --filter-criteria '{
    "severity":[{"comparison":"EQUALS","value":"CRITICAL"}],
    "resourceType":[{"comparison":"EQUALS","value":"AWS_EC2_INSTANCE"}],
    "exploitAvailable":[{"comparison":"EQUALS","value":"YES"}]
  }' \
  --region ap-northeast-2 --profile awssec-lab

# 결과 리포트 내보내기 (SBOM은 별도 명령: create-sbom-export → 27.2)
aws inspector2 create-findings-report \
  --report-format CSV \
  --s3-destination bucketName=shopmini-security-reports,keyPrefix=inspector/,kmsKeyArn=arn:aws:kms:ap-northeast-2:444455556666:key/EXAMPLE-KEY-ID \
  --region ap-northeast-2
```

### 억제 규칙 — 예외를 구조로 관리하기

26.1의 원칙 — **오탐 마스킹 절차가 없으면 팀이 결과 전체를 무시합니다.** Inspector에서 이것은 `SUPPRESS` 액션 필터입니다.

```bash
# 예: Dev 계정의 자동 종료 실습 인스턴스는 Medium 이하 억제
aws inspector2 create-filter \
  --name "suppress-lab-medium-and-below" \
  --description "awssec-lab 태그 리소스의 MEDIUM 이하 억제 (검토일 2026-12-31)" \
  --action SUPPRESS \
  --filter-criteria '{
    "resourceTags":[{"comparison":"EQUALS","key":"Project","value":"awssec-lab"}],
    "severity":[{"comparison":"EQUALS","value":"MEDIUM"}]
  }' \
  --region ap-northeast-2 --profile awssec-lab
```

⚠️ **억제는 조치가 아닙니다.** 설명(description)에 ① 사유 ② 승인자 ③ **재검토 일자**를 남기고 분기마다 `list-filters`로 전수 검토하십시오. 방치하면 대시보드만 깨끗해지고 리스크는 그대로입니다 — 25.6의 지표 함정 그 자체입니다.

### Cookbook의 "커스텀 템플릿"은 무엇으로 계승되었나

📖 Cookbook 9장의 「Creating a custom Inspector template」 레시피는 **`Environment=Prod` 태그가 붙은 EC2만 평가 대상으로 삼는 템플릿**을 만들며 적습니다. **"실무 사례에서는 대부분 운영 시스템 같은 표적 시스템에 대해 평가를 실행하게 된다. 비용이 제약이 아니라면 모든 인스턴스에 대해 평가를 수행하는 것이 계정을 더 안전하게 만든다."**

현행 Inspector에는 **"무엇을 스캔할지 고르는" 개념이 없습니다.** 활성화하면 전부 스캔합니다. 레시피의 의도는 이렇게 계승됩니다.

| Classic의 의도 | 현행에서의 대응 |
|---|---|
| 태그로 **스캔 범위**를 좁힘 | 범위 축소 개념 없음. 대신 **태그로 결과를 분류·필터**하고 우선순위를 나눔 |
| 비용을 통제 | 리소스 단위 과금이므로, 통제 수단은 **불필요한 리소스·이미지의 정리**(ECR 라이프사이클 정책) |
| SNS로 알림 | **EventBridge → SNS/Lambda**(30.5), Security Hub 연동 |
| 규칙 패키지 선택 | 선택 불가. CIS OS 벤치마크 성격의 점검은 **Security Hub 표준**과 SSM 규정 준수로 이동(26.6) |

**"규칙 패키지 선택"이 사라진 것이 가장 큰 변화입니다.** Classic에서 CIS OS 벤치마크를 담당하던 자리는 지금 Security Hub 보안 표준이 메웁니다(26.6).

## 26.4 수동 코드 리뷰와 모의 침투 테스트

### 자동화가 못 잡는 것

> 📖 *Practical Cloud Security* 2판 5장 「Manual Code Reviews」: **"수동 코드 리뷰는 비용과 시간이 많이 들 수 있지만, 여러 유형의 취약점을 찾는 데 있어서는 애플리케이션 테스트 도구보다 나을 수 있다."**

절충안도 제시합니다. **"코드 리뷰는 많은 고보안 환경에서 표준 관행이다. 그 밖의 많은 환경에서는 암호화나 접근 제어를 구현하는 부분처럼 보안상 특별한 의미를 갖는 코드 구간에만 사용될 수 있다."** 전수 리뷰가 불가능하다면 **암호화·인가 로직·시크릿 취급 코드**만이라도 사람이 읽어야 합니다.

자동 도구가 못 잡는 것의 공통점은 **"하나하나는 정상인데 조합이 위험한 경우"** 입니다.

| 자동화가 못 잡는 것 | 왜 못 잡는가 | AWS에서의 구체적 형태 |
|---|---|---|
| **비즈니스 로직 결함** | 도구는 "의도한 동작"을 모름 | 주문 금액을 클라이언트가 보낸 값으로 신뢰. 쿠폰 중복 적용 |
| **인가 우회(IDOR)** | 요청은 문법적으로 정상 | `/api/orders/{id}`에서 소유자 검증 누락 |
| **IAM 권한 상승 체인** | 정책 하나하나는 위험해 보이지 않음 | `iam:PassRole` + `lambda:CreateFunction` 조합으로 관리자 역할 탈취(7.5) |
| **크로스 계정 신뢰 오설정** | 신뢰 정책은 문법적으로 유효 | External ID 없는 서드파티 신뢰(8.6) |
| **경쟁 조건** | 단일 요청 분석으로는 안 보임 | 잔액 차감과 주문 생성 사이의 중복 요청 |
| **설계 수준 결함** | 코드가 아니라 아키텍처의 문제 | WAF를 우회하는 오리진 직접 접근 경로 존재(23.9) |

**IAM 권한 상승 체인은 클라우드 고유의 사각지대입니다.** Access Analyzer(7.7)는 외부 노출과 미사용 권한을 찾지만, "이 역할에서 저 역할로 올라탈 수 있는가"라는 **경로 문제**는 사람 또는 전용 그래프 분석 도구의 영역입니다.

### 모의 침투 테스트

원서의 펜테스트 서술에서 실무 판단에 직결되는 대목은 넷입니다.

| # | 요지 | 원서 근거 |
|---|---|---|
| 1 | **자동 스캔은 펜테스트가 아니다** | 📖 "앞서 논의한 유형의 자동 스캔은 침투 테스트가 아니라는 점을 유념해야 한다. 다만 펜테스터가 그런 스캔을 출발점으로 사용할 수는 있다." / "자동 스캔으로 찾을 수 있었던 결과를 펜테스터가 들고 온다면 돈과 시간을 낭비하고 있는 것이다." |
| 2 | **설계 정보는 주되 자격 증명은 주지 않는다** | 📖 "펜테스터에게 시스템 설계에 대한 정보는 제공하되, 비밀번호나 API 키 같은 비밀 정보는 제공하지 말 것을 권한다." 근거는 "실제 공격자는 보통 펜테스터보다 시간이 더 많다" |
| 3 | **펜테스트는 모든 경로를 찾지 않는다** | 📖 "펜테스터는 보통 시스템에 들어가는 한두 가지 방법을 찾아내지, 모든 방법을 찾아내지는 않는다." → 수용 가능한 결과가 나올 때까지 재테스트 |
| 4 | **결과 우선순위는 최상위** | 📖 2판 "심각도 높은 펜테스트 결과는 **사용자 제보를 제외한** 다른 모든 발견보다 우선해 고쳐야 한다." |

⚠️ 4번은 판이 바뀌며 달라진 지점입니다. **1판은 "다른 발견보다 우선"이었는데 2판에서 사용자 제보가 그 위로 올라갔습니다.** 2번도 마찬가지로, 2판은 1판의 white/gray/black box 용어를 걷어내고 단일 권고로 정리했습니다.

원서는 펜테스트가 **PCI DSS와 FedRAMP moderate/high 표준에서 독립 제3자에 의해 요구된다**고도 적습니다(4.3·38.3). 일정 배치도 함정입니다. 📖 **"펜테스팅은 릴리스 주기 후반에 수행되는 경우가 많은데, 이는 곧 발견된 문제가 릴리스를 지연시킬 가능성이 더 크다는 뜻이다."** 위협 모델링(3장)을 앞단에 배치해야 하는 이유입니다.

### ⚠️ AWS 침투 테스트 정책 — 승인 없이 하면 무슨 일이 일어나는가

> 📖 2판 5장: **"대부분의 클라우드 서비스 제공자는 자사 인프라나 플랫폼에서 호스팅되는 애플리케이션에 대해 침투 테스트를 수행하기 전에 승인을 받도록 요구한다. 승인을 받지 않으면 이용 약관 위반이 될 수 있고, 제공자의 대응에 따라 서비스 중단으로 이어질 수도 있다."**

**사고 시나리오.** 보안팀이 외주 펜테스터를 고용해 ShopMini 운영 환경(`111122223333`)을 테스트합니다. "AWS는 펜테스트를 허용한다"는 말만 듣고 범위 없이 시작합니다. 테스터는 워밍업으로 CloudFront에 초당 수만 건을 던지고 ALB 앞단에 요청 플러딩을 시도합니다. 몇 분 뒤 사용자 트래픽이 저하되고 AWS 남용 대응 절차가 발동합니다.

**원인.** ① 허용 서비스 목록과 금지 행위를 확인하지 않았습니다. ② **DoS 성격의 시험은 별도 절차 대상**이라는 점을 몰랐습니다. ③ 운영 환경에서, 알림 억제 없이 수행했습니다.

**올바른 구성.**

🔴 **① 사전 승인 없이 테스트할 수 있는 서비스 범위를 확인한다.** AWS는 고객이 소유한 리소스에 한해 아래 서비스에 대한 침투 테스트를 사전 승인 없이 허용합니다.

- Amazon EC2 인스턴스, NAT 게이트웨이, Elastic Load Balancer
- Amazon RDS / Amazon Aurora
- Amazon CloudFront
- Amazon API Gateway
- AWS Lambda 및 Lambda@Edge 함수
- Amazon Lightsail 리소스
- AWS Elastic Beanstalk 환경

⚠️ **이 목록은 AWS가 갱신합니다.** 컨테이너·스토리지 등 추가된 항목이 있으므로, 계약 전에 **AWS 침투 테스트 고객 지원 정책 페이지를 원본으로 확인**하십시오. 이 책의 목록을 근거로 삼지 마십시오.

🔴 **② 금지 행위는 승인 여부와 무관하게 하지 않는다.**

| 금지 행위 | 왜 금지인가 |
|---|---|
| **DoS / DDoS / 시뮬레이션 DoS·DDoS** | 공유 인프라 및 다른 고객에 영향 |
| **포트 플러딩 / 프로토콜 플러딩** | 위와 동일 |
| **요청 플러딩**(로그인 요청 플러딩, API 요청 플러딩) | 위와 동일 |
| **Route 53 호스팅 영역에 대한 DNS 존 워킹** | 정보 수집을 넘는 남용 |
| **DNS 하이재킹 · DNS 파밍** | 타 고객 영향 |
| **본인 소유가 아닌 리소스 대상 테스트** | 명백한 무단 접근 |

DoS 내성 시험이 필요하다면 **AWS의 시뮬레이션 이벤트(Simulated Events) 신청 절차**로 사전 승인을 받으십시오. Shield Advanced 사용 조직이라면 DDoS 대응 팀과의 사전 협의도 함께 진행합니다(23.10).

🔴 **③ 계약과 실행 절차에 명시한다.** 대상 계정 ID·리전·ARN 범위와 **범위 밖 리소스의 명시적 제외**, 시작·종료 시각과 트래픽 소스 IP, 양측 24시간 긴급 중단 연락처, 발견 사항의 암호화·보존·파기 방식. 그리고 **블루팀 사전 통지 여부** — 통지하지 않는다면 그것은 레드팀 훈련이며 사고 대응 절차가 실제로 발동한다는 뜻입니다.

> 📖 원서(1·2판 공통)의 별도 박스: **"침투 테스트는 보통 (…) 특정 대상으로 범위가 정해지고, 특정 시점에 수행되도록 일정이 잡힌다. 레드 팀은 펜테스터와 같은 도구를 많이 쓰지만, 네트워크나 조직 전체를 돌아다니며 취약점을 찾도록 더 느슨하게 계약된다. 블루 팀은 방어 팀으로, 레드 팀(그리고 실제 공격자!)을 탐지하려 시도한다. 일부 조직은 퍼플 팀을 두어 (…) 협업하게 한다."**

⚠️ 테스트 중 발생한 GuardDuty 결과(31.1)를 "훈련이었다"며 일괄 무시하면 **실제 공격이 훈련 기간에 섞여 들어왔을 때 놓칩니다.** 태그를 붙여 보존하고, 종료 후 **테스터 활동 로그와 GuardDuty·CloudTrail 기록을 대조**하십시오. 이 대조가 곧 탐지 커버리지 검증(32.5)입니다.

## 26.5 버그 바운티와 사용자 제보 창구

### 원서의 「User Reports」

> 📖 *Practical Cloud Security* 2판 5장 「User Reports」: **"완벽한 세계라면 모든 버그와 취약점은 사용자가 보기 전에 발견되어 고쳐질 것이다. 웃음을 그쳤다면, 이제 사용자나 버그 바운티 프로그램으로부터 받는 보안 취약점 제보를 처리해야 한다. 이는 곧 각 제보가 실제인지 검증하고, 실제라면 수정을 배포하고 사용자에게 알리는, 잘 정의되고 빠른 프로세스가 필요하다는 뜻이다. 버그 바운티의 경우 공개까지 제한된 시간만 주어질 수 있으며, 공개 이후에는 악의적 공격의 위험이 급격히 높아진다."**

2판에는 1판에 없던 문장이 추가되었습니다.

> 📖 2판 5장: **"어떤 경우에는 외부 사용자의 제보가 도움이 되는 신고와 갈취(extortion) 시도 사이의 경계에 걸쳐 있기도 하다!"**

저자는 **커뮤니케이션 전문가와 법률 자문**이 필요할 수 있다고 말하며 세 이해의 충돌을 지적합니다 — **법적 책임을 피하려 최소한만 말하려는 욕구, 홍보 재앙을 피하려 투명하려는 욕구, 고치는 동안 조용히 있으려는 욕구.**

> 📖 2판 5장: **"제보된 취약점이나 침해에 대한 부실한 대응이 최초의 문제 자체보다 조직에 훨씬 더 큰 피해를 준 주목할 만한 사례가 여러 건 있었다."** (원서는 각주에서 침해를 은폐하려다 1억 4,800만 달러 이상의 합의금을 지불한 Uber 사례와, 2022년 8월 보안 사건의 심각성을 축소하려다 평판이 훼손된 LastPass 사례를 듭니다.)

### VDP와 버그 바운티는 다른 것입니다

두 용어가 혼용되지만 **비용 구조도 준비 상태 요구도 다릅니다.**

| 축 | **취약점 공개 정책(VDP)** | **버그 바운티** |
|---|---|---|
| 목적 | "여기로 제보하세요"라는 **창구와 규칙**의 공표 | 발견에 **금전적 보상**을 걸어 적극 유인 |
| 비용 | 창구 운영 인건비 | 보상금 + 트리아지 비용 |
| 유입량 | 자연 발생량 | **의도적으로 크게 늘림** (중복·저품질 포함) |
| 전제 조건 | 접수 창구 + 대응 프로세스 | VDP가 이미 성숙하게 돌고 있을 것 |
| 필수 조항 | 안전 항구(safe harbor), 연락처, 범위, 대응 SLA | + 보상 기준표, 중복 판정 규칙, 공개 시점 합의 |
| 도입 순서 | **1단계** | **2단계** |

🔴 **VDP 없이 버그 바운티를 먼저 열지 마십시오.** 트리아지 능력 없이 유입량만 늘리면 심각한 제보가 저품질 더미에 묻힙니다. 원서가 말한 "제한된 시간" 안에 대응하지 못하는 사태는 대부분 여기서 발생합니다.

### 창구 운영 실무

> 💡 **원서 이후 표준 — security.txt** — 제보 창구를 기계가 읽을 수 있게 공표하는 방식이 **RFC 9116(`security.txt`)** 으로 표준화되었습니다. 원서에 없는 내용이므로 인용이 아닌 보강입니다. 사이트 루트의 `/.well-known/security.txt`에 연락처·정책 URL·언어·만료일을 두면, 연구자가 "누구에게 알려야 할지 몰라서" 공개 게시판에 먼저 올리는 사태를 줄일 수 있습니다.

ShopMini에서는 `shopmini-assets` 버킷의 해당 객체를 CloudFront로 서빙하면 됩니다(23.7).

- `Contact:` — 전용 메일 주소 또는 제보 폼 URL (개인 메일 금지, 팀 별칭 사용)
- `Policy:` — VDP 문서 URL (범위, 금지 행위, 안전 항구, 대응 SLA 명시)
- `Preferred-Languages:` / `Expires:` — ⚠️ **만료된 security.txt는 없느니만 못합니다.** 갱신 알람을 걸어 두십시오(23.2의 인증서 갱신 알람과 같은 발상).

📋 **제보 접수 프로세스 체크리스트**

- [ ] 접수 채널이 **단일화**되어 있고 24시간 안에 접수 확인 회신이 나간다
- [ ] 트리아지 담당자와 백업이 지정되어 있다(휴가·퇴사 시 공백 없음)
- [ ] 심각도 판정 기준이 문서화되어 있다(25.4의 우선순위 기준 재사용)
- [ ] **안전 항구 조항**이 있다 — 정책 범위 안에서 선의로 테스트한 연구자를 추궁하지 않는다는 약속
- [ ] 법무·홍보가 **에스컬레이션 경로에 미리 포함**되어 있다(사건 후 찾지 않는다)
- [ ] 공개 시점을 제보자와 합의하는 절차가 있다
- [ ] AWS 인프라 자체의 취약점은 **AWS 보안 창구**로 보낸다는 구분이 문서화되어 있다
- [ ] 갈취성 연락(금전 요구 + 공개 위협)에 대한 **대응 지침과 신고 절차**가 별도로 있다

### 제보를 지표로 바꾸기

원서는 사용자 제보를 "사고 관리와 겹치는 영역"으로 규정합니다. 여기에 하나를 더하면 도구 평가에 쓸 수 있습니다.

🔴 **"사용자·연구자 제보로 처음 발견된 취약점의 비율"을 지표로 두십시오.** 이 비율이 높다는 것은 **우리 도구가 그만큼 놓치고 있다**는 뜻입니다(25.5 미탐률의 실측 대리 지표). 제보마다 "어느 도구가 잡았어야 하는가"를 한 줄 기록하고, 분기마다 26.1의 지형도를 갱신하십시오.

## 26.6 🔴 클라우드 설정 오류 스캐닝(CSPM)

### 왜 이것이 취약점 관리인가

여기까지의 도구는 대부분 **CVE**를 찾습니다. 그런데 클라우드에서 실제 침해로 이어지는 문제의 큰 축에는 CVE 번호가 붙지 않습니다. 퍼블릭 버킷, `0.0.0.0/0`의 3306, MFA 없는 관리자, 암호화 없는 스냅샷 — **소프트웨어에는 결함이 없고 설정만 틀렸습니다.** 원서가 이를 별도 범주로 떼지 않고 **구성 관리를 취약점 관리 안에 통합**해 서술하는 이유이고, 도구 범주 이름이 전부 "Scanners **and Configuration Management** Systems"인 이유입니다.

> 📖 2판 5장: **"에이전트리스 스캐너는 보안 구성이 올바른지, 정책 요구사항을 충족하는지 점검할 수 있다. 예를 들어 시스템이 Telnet 연결을 허용하도록 구성되어 있다면(정책상 금지되어야 한다), 스캐너는 Telnet이 활성화되어 있음을 탐지하고 경보를 띄워야 한다."**

**클라우드에서 "Telnet이 켜져 있다"의 등가물이 "버킷이 퍼블릭이다"입니다.** CSPM은 별개 분야가 아니라 **취약점 관리의 구성 관리 축**입니다.

> 💡 **용어 정리 — 원서 이후 정착한 시장 용어들** — 2판이 명시적으로 쓰는 것은 **CWPP**와 **CNAPP** 둘뿐입니다. 아래 나머지는 원서 이후 애널리스트·벤더가 정착시킨 구분이며, 원서 인용이 아닙니다.
>
> | 약어 | 무엇을 보는가 | AWS 네이티브 대응 |
> |---|---|---|
> | **CSPM** (Cloud Security Posture Management) | 클라우드 **제어 평면 설정**의 오류·규정 위반 | AWS Config 규칙, Security Hub 보안 표준, Trusted Advisor |
> | **CWPP** (Cloud Workload Protection Platform) | **워크로드 내부** — VM·컨테이너·함수의 취약점과 런타임 | Amazon Inspector, GuardDuty Runtime Monitoring |
> | **CIEM** (Cloud Infrastructure Entitlement Management) | **권한(entitlement)** — 과잉 권한과 권한 상승 경로 | IAM Access Analyzer(미사용 액세스·외부 접근), 마지막 액세스 정보 |
> | **KSPM** | 쿠버네티스 구성 | EKS 관련 Security Hub 컨트롤, 파드 보안 표준(24.4) |
> | **CNAPP** | 위 전체를 하나로 묶은 상위 범주 | 단일 AWS 서비스로는 대응되지 않음(조합으로 구성) |

### 🔴 반드시 이렇게 구성하라

**① AWS Config를 전 계정·전 사용 리전에서 활성화하고 보안 도구 계정에 애그리게이터를 둔다.** 안 하면 설정 변경 이력을 답할 수 없고 규칙 평가가 불가능합니다. Security Hub 컨트롤 상당수가 Config 기록에 의존하므로 **Config가 없으면 Security Hub도 반쪽입니다.**

**② Security Hub를 켜고 최소 두 표준을 활성화한다 — AWS 기초 보안 모범 사례(FSBP)와 CIS AWS Foundations Benchmark.** 카드 결제를 다룬다면 PCI DSS를 추가합니다.

```bash
# 활성화된 표준 확인
aws securityhub get-enabled-standards --region ap-northeast-2 --profile awssec-lab

# 사용 가능한 표준 목록에서 ARN 확인 후 구독
aws securityhub describe-standards --region ap-northeast-2 --profile awssec-lab

aws securityhub batch-enable-standards \
  --standards-subscription-requests \
    StandardsArn=arn:aws:securityhub:ap-northeast-2::standards/aws-foundational-security-best-practices/v/1.0.0 \
  --region ap-northeast-2 --profile awssec-lab
```

⚠️ 표준 ARN에는 **버전 문자열**이 들어갑니다. `describe-standards` 출력의 ARN을 그대로 쓰십시오.

**③ 결과를 단일 큐로 모은다.** Config·Inspector·GuardDuty·Access Analyzer 결과를 각각 다른 콘솔에서 보는 순간 26.1의 "결과 누수"가 시작됩니다. Security Hub가 집계 지점입니다(31.5).

**④ 예외에 만료일을 붙인다.** 컨트롤 비활성화·결과 억제·규칙 제외 모두 사유·승인자·재검토일을 남기고 분기 검토합니다.

**⑤ 신규 계정 베이스라인에 위 전부를 넣는다.** 계정 생성 후 사람이 켜는 방식은 반드시 누락됩니다(37.9).

### 취약점 관리 관점에서의 역할 분담

⚠️ **이 절은 CSPM을 "취약점 관리 도구"로서만 다룹니다.** Security Hub의 운영·집계 아키텍처는 31.5, Config 적합성 팩의 조직 배포와 거버넌스는 37.7입니다. 여기서 필요한 것은 **"어느 도구가 어느 구멍을 보는가"** 하나입니다.

| 도구 | 보는 것 | 보지 못하는 것 | 취약점 관리에서의 역할 |
|---|---|---|---|
| **AWS Config 규칙** | 개별 리소스 설정의 규정 준수 + **변경 이력** | OS·앱 내부 | 설정 오류의 **탐지와 근본 원인 추적** ("언제 누가 열었나") |
| **Security Hub 표준** | 계정 전반의 벤치마크 준수 상태 | 커스텀 정책, 앱 로직 | 설정 오류의 **집계와 점수화**, 표준 대비 갭 |
| **Trusted Advisor** | 계정 수준 고위험 항목 소수 | 대부분의 세부 설정 | 빠른 **1차 훑기**. CSPM 대체 불가(26.7) |
| **Amazon Inspector** | EC2·이미지·함수 **내부의 CVE** | 클라우드 설정 | CVE 축 담당 |
| **IAM Access Analyzer** | 외부 노출 리소스, 미사용 권한 | 권한 상승 경로 자체 | 데이터 접근 계층의 과잉 권한(7.7) |

**대표적인 Config 관리형 규칙**을 계층별로 꼽으면 커버리지 감각이 잡힙니다.

| 25.2 계층 | 관리형 규칙 식별자 | 무엇을 막는가 |
|---|---|---|
| 데이터 접근 | `s3-bucket-public-read-prohibited`, `s3-bucket-server-side-encryption-enabled` | 퍼블릭 버킷, 비암호화 (15.2·15.7) |
| 데이터 접근 | `encrypted-volumes`, `rds-storage-encrypted` | 비암호화 EBS·RDS (16.1·16.2) |
| 데이터 접근 | `iam-password-policy`, `iam-user-mfa-enabled` | 약한 인증 (5.6) |
| 네트워크 | `restricted-ssh`, `vpc-default-security-group-closed` | `0.0.0.0/0` 개방, 기본 SG 사용 (19.3) |
| OS | `ec2-imdsv2-check` | IMDSv1 방치로 인한 SSRF 자격 증명 탈취 (8.3) |
| OS | `ec2-instance-managed-by-systems-manager` | **SSM 미관리 = Inspector 스캔 사각지대**(26.3) |

마지막 줄이 중요합니다. **`ec2-instance-managed-by-systems-manager`는 "취약점 스캔이 안 되는 인스턴스"를 찾아 주는 규칙**이며, 25.6의 "스캔하지 않으면 취약점이 0으로 보인다"를 자동 감시하는 방법입니다.

⚠️ **CSPM 도입에서 반복되는 세 가지 실수**

| 실수 | 결과 | 올바른 구성 |
|---|---|---|
| 규칙·표준만 켜고 담당자·큐를 안 만듦 | 결과 수만 건이 쌓이고 아무도 안 봄 | 결과를 이슈 트래커로 라우팅(26.2와 동일 원칙) |
| 주 사용 리전만 활성화 | 미사용 리전에 만들어진 리소스가 사각지대 | 전 리전 활성화 + 미사용 리전은 SCP로 봉인(37.2) |
| Config 기록 대상을 전체 리소스로 두고 방치 | 변경이 잦은 리소스 때문에 비용 급증 | 기록 대상 유형과 빈도를 설계해서 선택 |

## 26.7 Trusted Advisor 활용 🧪

### 원서가 설명하는 Trusted Advisor

> 📖 *AWS Security Cookbook* 10장 「Using AWS Trusted Advisor for recommendations」: **"Trusted Advisor는 비용 최적화, 성능, 보안, 내결함성, 서비스 한도와 관련된 권장 사항을 제공하는 AWS의 온라인 도구다. (…) 서비스 수준은 두 가지다 — Basic 플랜과 전체(full) Trusted Advisor. Basic 플랜은 무료이며 핵심 점검과 권장 사항을 다룬다. 전체 Trusted Advisor 기능은 Business 및 Enterprise AWS 지원 플랜에서 사용할 수 있다."**

> 📖 1판·2판의 도구 목록도 같은 규정을 합니다. **"(…) AWS 리소스에 대한 구성 관리 영역에서 적절한 IAM 비밀번호 정책이 적용되어 있는지, CloudTrail 로깅이 활성화되어 있는지 같은 일부 고수준(high-level) 점검을 수행할 수 있다."**

**"고수준(high-level) 점검"** 이 핵심입니다. 저자는 Trusted Advisor를 CSPM 대체재로 보지 않습니다. **넓고 얕은 1차 훑기**입니다.

### ⚠️ 지원 플랜에 따라 보이는 항목이 달라집니다

**사고 시나리오.** 신규 팀이 Basic 지원 플랜의 개발 계정에서 Trusted Advisor를 엽니다. 보안 카테고리에 경고가 거의 없습니다. 팀은 "보안 점검을 통과했다"고 판단하고 운영 전환을 진행합니다.

**원인.** Basic 플랜에서는 **애초에 대부분의 점검이 실행되지 않습니다.** 경고가 없는 것이 아니라 **점검 자체가 없는 것**입니다. 📖 Cookbook 10장은 플랜별 항목을 구체적으로 나열합니다.

| 구분 | Cookbook이 나열한 항목 |
|---|---|
| **Basic 플랜의 보안 권장 사항** | Specific Ports Unrestricted (Alert), Amazon EBS Public Snapshots, Amazon RDS Public Snapshots |
| **Basic 플랜의 내결함성 권장 사항** | Auto Scaling Groups, CloudFormation Stacks, DynamoDB Read Capacity |
| **전체 Trusted Advisor의 보안 권장 사항(예)** | Unrestricted Access, IAM Password Policy |
| **전체 Trusted Advisor의 내결함성 권장 사항(예)** | Amazon EBS Snapshots, Amazon EC2 Availability Zone Balance, Load Balancer Optimization, VPN Tunnel Redundancy |

그리고 명시합니다 — **"Basic 플랜은 현재 비용 최적화, 성능, 내결함성 아래에 사용 가능한 권장 사항이 없다."**

**올바른 구성.** 🔴 **Trusted Advisor의 초록불을 보안 판정 근거로 쓰지 마십시오.** 판정 근거는 26.6의 Config 규칙과 Security Hub 표준이고, Trusted Advisor는 **"플랜 등급에 따라 보이는 것이 달라지는 보조 지표"** 입니다. 계정마다 플랜이 다르면 **같은 결과라도 의미가 다르다**는 점을 리뷰 문서에 명기하십시오.

> 💡 **원서 이후 변경** — ① Basic·Developer 플랜에서도 **서비스 할당량 점검과 일부 보안 점검**을 볼 수 있도록 범위가 넓어졌습니다. ② 기존 5개 범주에 **운영 우수성(Operational Excellence)** 범주가 추가되었습니다. ③ Enterprise 플랜에서는 **Trusted Advisor Priority**와 조직 단위 뷰를 쓸 수 있습니다. ④ 결과를 EventBridge 이벤트로 받을 수 있습니다. 세부는 변동되므로 콘솔에서 확인하십시오.

### 🧪 CLI로 결과 조회하기

⚠️ **제약 두 가지를 먼저 확인하십시오.** ① Trusted Advisor를 프로그래밍 방식으로 조회하는 `support` API는 **`us-east-1` 엔드포인트**에서만 동작합니다(서울 리전 리소스를 점검하더라도 마찬가지). ② **Business·Enterprise On-Ramp·Enterprise 지원 플랜**이 필요하며, 미달이면 `SubscriptionRequiredException`이 반환됩니다.

```bash
# 1) 점검 목록과 check-id 확보 (언어 지정 필수)
aws support describe-trusted-advisor-checks \
  --language en \
  --region us-east-1 --profile awssec-lab \
  --query 'checks[?category==`security`].[id,name]' --output table

# 2) 전체 점검의 상태 요약 — 어떤 점검이 error(빨강)인지 한눈에
aws support describe-trusted-advisor-check-summaries \
  --check-ids <CHECK_ID_1> <CHECK_ID_2> \
  --region us-east-1 --profile awssec-lab \
  --query 'summaries[?status==`error`].[checkId,status,resourcesSummary.resourcesFlagged]' \
  --output table

# 3) 특정 점검의 상세 결과 — 어떤 리소스가 걸렸는지
aws support describe-trusted-advisor-check-result \
  --check-id <CHECK_ID> --language en \
  --region us-east-1 --profile awssec-lab \
  --query 'result.flaggedResources[].metadata'

# 4) 결과 갱신 요청 (콘솔의 새로고침 버튼과 동일)
aws support refresh-trusted-advisor-check \
  --check-id <CHECK_ID> \
  --region us-east-1 --profile awssec-lab
```

📖 Cookbook 10장이 콘솔에서 안내하는 **다운로드 버튼(.xls)과 새로고침 버튼**이 위 CLI의 `describe-trusted-advisor-check-result`·`refresh-trusted-advisor-check`에 대응합니다. 콘솔 클릭을 스크립트로 옮기면 주기 실행과 이력 보관이 가능합니다.

**실무 배치.** 위 명령을 보안 도구 계정(`444455556666`)의 Lambda로 주 1회 실행해 결과를 S3에 적재하고 `status`가 `error`인 항목만 SNS로 통지하는 것이 흔한 구성입니다(30.1·30.5). ⚠️ 실행 역할에는 `support:Describe*`와 `support:RefreshTrustedAdvisorCheck`만 부여하십시오 — `support:*`는 지원 케이스 생성·조회까지 포함합니다.

> 💡 **원서 이후 추가 — Trusted Advisor API** — `support`와 별개로 `trustedadvisor` 네임스페이스 API(`list-checks`, `list-recommendations`, `update-recommendation-lifecycle`)가 추가되었습니다. 권장 사항의 **처리 상태를 기록**할 수 있다는 점이 차이이며, 이쪽도 Business 이상 플랜과 `us-east-1`을 요구합니다.

### Trusted Advisor의 자리

**Trusted Advisor는 "계정을 처음 인수받았을 때 30분 만에 큰 구멍을 보는 도구"** 입니다. 인수인계, M&A 실사, 새도우 IT 계정 회수(12.5)에서 값어치가 큽니다. 반대로 **상시 규정 준수 감시를 여기 맡기는 것은 오용**이며, 그 자리는 Config와 Security Hub의 것입니다.

## 🔴 필수 구성 체크리스트

**도구 커버리지**
- [ ] 25.2의 7계층마다 **담당 도구**가 지정되고, 빈칸은 의식적으로 수용된 리스크다
- [ ] "도구 누수"·"결과 누수"의 현재 수치를 안다
- [ ] 프라이빗·격리 서브넷도 스캔 범위에 포함된다
- [ ] 모든 도구에 **오탐 마스킹 절차**가 있고 예외에 만료일이 붙는다

**파이프라인**
- [ ] SAST·SCA·시크릿 스캔이 **커밋 시점**에 돈다
- [ ] 이미지 스캔이 레지스트리 단계에 있고 Critical은 배포를 차단한다
- [ ] 모든 결과가 **이슈 트래커로 자동 유입**된다(사람이 리포트를 여는 구조가 아니다)
- [ ] 차단 기준이 "신규 발생분"부터 단계적으로 강화된다

**Amazon Inspector**
- [ ] Organizations **위임 관리자**로 구성되고 신규 계정 자동 활성화가 켜져 있다
- [ ] EC2·ECR·Lambda·Lambda 코드 **4가지 유형 모두**, **모든 사용 리전**에서 활성화
- [ ] `list-coverage`와 `ec2-instance-managed-by-systems-manager` 규칙으로 미커버 리소스를 감시한다
- [ ] 억제 규칙마다 사유·승인자·재검토일이 기록되고 분기 검토된다

**수동 테스트·제보**
- [ ] 암호화·인가·시크릿 취급 코드는 **사람이 리뷰**한다
- [ ] 펜테스트 계약에 대상 ARN 범위·시각·긴급 연락처·범위 밖 제외가 명시된다
- [ ] **AWS 침투 테스트 정책 원본**을 확인했고 DoS 성격 시험은 별도 승인을 거친다
- [ ] `/.well-known/security.txt`의 `Expires`가 유효하고 갱신 알람이 있다
- [ ] VDP에 안전 항구 조항·대응 SLA가 있고 갈취성 연락 지침이 별도로 있다

**CSPM**
- [ ] AWS Config가 전 계정·전 사용 리전에서 켜지고 보안 도구 계정에 애그리게이터가 있다
- [ ] Security Hub에 **FSBP + CIS**가 켜져 있고(카드 결제 시 PCI DSS 추가) 결과가 단일 큐로 모인다
- [ ] 신규 계정 베이스라인에 Config·Security Hub·Inspector·GuardDuty가 포함된다

## ⚠️ 자주 하는 실수

| 실수 | 결과 | 올바른 구성 |
|---|---|---|
| 체크박스용으로 도구 5종 도입 | 어느 것도 제대로 운영되지 않고 결과는 전부 방치 | 가장 굵은 누수 하나부터 가치를 뽑고 다음으로 (26.1) |
| "격리 서브넷은 스캔 불필요" | 경계 안으로 들어온 공격자가 취약한 내부 시스템을 익스플로잇 | 릴레이·에이전트로 내부도 스캔. 우선순위만 낮춤 |
| 오탐 마스킹 절차 없이 스캐너 도입 | 일부가 틀렸다는 이유로 팀이 **결과 전체를 무시** | 마스킹 절차 문서화 + 오탐률 지표화 (25.5) |
| 스캔 결과를 리포트로만 발행 | 아무도 열어 보지 않음 = 결과 누수 | 이슈 트래커 자동 연동 |
| 기존 코드베이스에 SAST 차단 게이트를 곧바로 적용 | 수천 건 폭발 → 개발자가 게이트를 우회하거나 꺼 버림 | 신규 발생분부터 차단, 기준선 점진 하향 |
| WAF가 막아 주니 앱 취약점 수정을 미룸 | 오리진 직접 접근으로 WAF 우회 시 무방비 | 심층 방어 — 둘 다. 오리진 접근 차단 (23.9) |
| 원서 레시피대로 Inspector 평가 템플릿을 찾음 | Classic 기준이라 현행 콘솔에 없음 | `inspector2` 기반 상시 스캔으로 구성 (26.3) |
| Inspector를 켰는데 EC2 절반이 안 잡힘 | SSM 미관리 인스턴스가 조용히 사각지대 | 인스턴스 프로파일 + SSM 엔드포인트 + `list-coverage` 점검 |
| 억제 규칙으로 대시보드를 정리 | 지표는 개선, 리스크는 그대로 (25.6의 함정) | 억제에 사유·승인자·만료일 필수, 분기 전수 검토 |
| 승인·범위 없이 운영 환경 펜테스트 | 이용 약관 위반 + 실제 서비스 중단 | 허용 서비스 확인, DoS 금지, 범위·시각 계약 명시 |
| 테스트 기간 GuardDuty 결과를 일괄 무시 | 훈련에 섞인 **실제 공격**을 놓침 | 태그 붙여 보존하고 종료 후 활동 로그와 대조 |
| VDP 없이 버그 바운티부터 개설 | 트리아지 붕괴, 심각한 제보가 묻힘 | VDP → 프로세스 검증 → 바운티 순서 |
| security.txt를 만들고 `Expires` 방치 | 만료된 창구 = 없느니만 못함 | 갱신 알람 설정 (23.2와 동일 발상) |
| Trusted Advisor 초록불을 보안 근거로 사용 | Basic 플랜은 **점검 자체가 실행되지 않음** | 판정 근거는 Config·Security Hub. TA는 1차 훑기 |
| `support` API를 서울 리전에서 호출 | 엔드포인트 오류 | `--region us-east-1` 고정 + Business 이상 플랜 확인 |
| Config·Security Hub를 주 사용 리전만 활성화 | 미사용 리전의 리소스가 사각지대 | 전 리전 활성화 + 미사용 리전 SCP 봉인 (37.2) |
