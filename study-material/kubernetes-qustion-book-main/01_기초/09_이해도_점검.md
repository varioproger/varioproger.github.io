# 09. 외우지 않고 구조를 설명하는 연습

> 전체 학습 09/35 · 기초
> [이전: 08. 그림으로 연결하는 Terraform · Docker · Kubernetes · EKS](08_그림으로_연결하기.md) · [전체 목차](../README.md) · [다음: 10. 내 답변에서 출발해 구조 다시 연결하기](10_내_답변_교정과_개념_연결.md)
> 본문을 위에서 아래로 읽고 마지막의 다음 장으로 이동한다. 본문 속 다른 장·출처 링크는 선택 참고용이다.

## 1. 백지 그림 과제

여섯 시작 질문에 대한 개인 답변 교정은 [10](10_내_답변_교정과_개념_연결.md)에 있다. 이 장의 문제와 추가 문제를 먼저 풀고, 다음 장에서 답변 교정을 읽는다.

자료를 덮고 아래 세 그림을 각각 그린다. 상자 이름보다 **화살표에 적은 동사**가 중요하다.

1. **생성·배포 그림:** Terraform, AWS API, VPC, EKS, Node Group, Docker 빌드, ECR, Kubernetes API, kubelet, Pod를 배치한다. ‘생성’, ‘push’, ‘pull’, ‘관찰’, ‘실행’을 연결한다.
2. **실제 요청 그림:** 사용자, DNS, ALB, Pod, DB를 연결한다. IP target 기준으로 그리고 Service가 설정상 어디에 관여하는지 별도로 표시한다.
3. **복구 그림:** ‘Pod 하나가 삭제됨’에서 시작해 원하는 복제 수를 되찾는 과정을 그린다. controller, scheduler, kubelet을 구분한다.

정답의 핵심은 01의 관리 관계, 05의 배포·요청·장애 흐름과 같다. EKS를 Kubernetes 뒤에 있는 별도의 앱 실행 엔진으로 그리거나, Terraform을 HTTP 요청 경로에 넣었다면 다시 그린다.

## 2. 반대로 생각하는 12문제

먼저 스스로 한두 문장으로 답한 후 아래 해설을 읽는다.

| 번호 | 질문 |
|---|---|
| 1 | Terraform CLI를 종료하면 기존 서비스가 멈추는가? |
| 2 | ECR에 새 이미지를 push했는데 왜 앱 버전이 그대로인가? |
| 3 | Node에 Docker Engine이 없어도 Docker 빌드 이미지를 실행할 수 있는가? |
| 4 | Deployment의 `replicas: 3`이면 반드시 서로 다른 AZ에 하나씩 생기는가? |
| 5 | Pod IP가 바뀌면 Service YAML도 매번 수정해야 하는가? |
| 6 | Ingress 객체만 만들면 반드시 외부 접속이 되는가? |
| 7 | ALB IP target 요청이 Service ClusterIP를 반드시 통과하는가? |
| 8 | HPA로 Pod를 10개로 늘리면 EC2도 자동으로 10개가 되는가? |
| 9 | ServiceAccount를 만들면 Pod가 S3를 쓸 수 있는가? |
| 10 | Kubernetes API가 일시적으로 불통이면 기존 HTTP 요청도 즉시 모두 멈추는가? |
| 11 | 컨테이너의 파일을 수정하면 ECR 이미지도 바뀌는가? |
| 12 | EKS를 쓰면 앱·DB 가용성과 백업도 AWS가 자동 보장하는가? |

### 해설

1. **멈추지 않는다.** Terraform이 만든 자원은 외부 서비스에 남는다. Kubernetes의 제어 루프와 AWS의 관리 기능이 각자 작동한다.
2. **이미지 저장과 배포 설정 변경은 별개다.** Deployment의 이미지 참조를 새 digest 등으로 갱신해야 한다. 같은 tag를 덮어썼다고 실행 중인 Pod가 자동 교체되지 않는다.
3. **가능하다.** 호환되는 이미지와 CRI 런타임을 통해 실행한다. 예시 경로는 kubelet → containerd → OCI runtime이다.
4. **아니다.** 수량과 분산 배치 조건은 별개다. topology spread, affinity와 실제 용량 등을 함께 설계한다.
5. **일반적인 selector 기반 Service라면 매번 수정하지 않는다.** controller가 대상 Pod 변화와 상태를 EndpointSlice 등에 반영한다. selector 없는 Service처럼 수동 관리하는 예외도 있다.
6. **아니다.** 이를 처리할 controller와 네트워크·권한·DNS 등 실제 연결 조건이 있어야 한다.
7. **아니다.** Service를 통해 대상을 알아내더라도 실제 요청은 ALB → Pod IP로 갈 수 있다.
8. **아니다.** HPA는 Pod 수를 조정한다. 노드 자동 확장은 별도이며 노드 하나에 여러 Pod가 들어갈 수 있다.
9. **아니다.** AWS API 호출 권한을 Pod Identity나 IRSA 등으로 연결해야 한다. 네트워크 경로도 있어야 한다.
10. **반드시 그렇지는 않다.** 기존 프로세스와 전달 규칙이 계속 작동할 수 있다. 다만 새 배포·스케줄링·주소 변경 반영·복구가 영향을 받고, API 의존적인 앱 기능도 실패할 수 있다.
11. **바뀌지 않는다.** 컨테이너의 쓰기 계층 또는 마운트된 스토리지의 변경이다. 실행 컨테이너만 수동 수정하면 이후 교체 시 사라질 수 있다.
12. **아니다.** 관리 범위가 넓어져도 앱 설계·설정·데이터 보호 책임이 남는다.

## 3. 계층별 장애 추론

### 사례 A: ‘노드 CPU는 넉넉한데 Pod가 시작되지 않는다’

**확인 순서:** Pod에 노드가 배정됐는지 → Events가 가리키는 실패 → requests·배치 조건 또는 이미지·CNI·볼륨 준비 문제로 분리한다.

노드가 배정된 뒤 `FailedCreatePodSandBox`와 IP 할당 오류가 있다면 VPC CNI, subnet 여유 IP, ENI 관련 제약을 확인한다. CPU만 증설하면 해결된다고 단정할 수 없다.

배울 점: 자원은 CPU와 메모리만 있는 것이 아니다. 네트워크 주소와 스토리지도 실행 조건이다.

### 사례 B: ‘Pod는 모두 Ready인데 외부 접속이 안 된다’

**확인 순서:** DNS가 기대한 ALB를 가리키는지 → ALB listener와 rule → target group 등록·health → 보안 그룹·실제 앱 포트.

Kubernetes readiness가 통과해도 ALB의 health check 경로·포트가 다르면 target이 unhealthy일 수 있다. Pod가 정상인 것과 외부 연결 전체가 정상인 것은 다른 상태다.

배울 점: 각 계층의 건강 상태는 독립적으로 확인해야 한다.

### 사례 C: ‘수동으로 복제 수를 바꿨는데 다시 돌아간다’

HPA, GitOps 도구, Terraform 또는 다른 배포 도구 중 누가 같은 필드를 관리하는지 본다. 마지막 명령이 무조건 최종 의도가 되는 구조가 아닐 수 있다.

배울 점: **자원과 필드의 소유자**를 정해야 서로 다른 자동화가 충돌하지 않는다.

### 사례 D: ‘앱 이미지를 롤백했는데 주문 처리가 여전히 깨진다’

새 버전에서 DB 스키마가 바뀌었는지, 이전 이미지가 그 스키마와 호환되는지 확인한다. 이미지 롤백과 데이터 복구는 서로 다른 작업이다.

배울 점: 컨테이너 교체의 편리함이 데이터 변경의 가역성을 만들어 주지는 않는다.

## 4. 코드 실행 없이 하는 배포 추적

아래 상태를 가정하고 빈칸을 채워 본다.

```text
원하는 상태: orders 이미지 B, replicas 3
관찰한 상태: 이미지 A Pod 3개

① __________ controller가 새 버전에 맞는 ReplicaSet을 조정한다.
② __________ controller가 필요한 Pod 객체를 만든다.
③ __________가 새 Pod의 노드를 선택한다.
④ 노드의 __________가 CRI로 실행을 요청한다.
⑤ __________가 ECR에서 이미지를 가져와 실행을 준비한다.
⑥ __________ 신호 등을 보고 요청을 받을 준비를 판단한다.
⑦ ALB를 관리하는 __________가 대상 변경을 AWS에 반영한다.
```

답: ① Deployment ② ReplicaSet ③ Scheduler ④ kubelet ⑤ containerd 같은 runtime ⑥ readiness ⑦ AWS Load Balancer Controller. 실제 rolling update는 이 동작들이 상태를 관찰하며 반복·병행되는 과정이다.

## 5. 개념 쌍을 구분하면 절반은 이해한 것이다

| 쌍 | 구분 문장 |
|---|---|
| 이미지 / 컨테이너 | 저장된 실행 산출물 / 실행 중인 프로세스 환경 |
| Docker / containerd | 빌드·실행 도구 생태계 / 컨테이너 런타임 구현 |
| Kubernetes / EKS | 컨테이너 운영 시스템 / AWS의 관리형 Kubernetes 서비스 |
| Deployment / Service | 실행·교체 의도 / 연결·대상 발견 의도 |
| Ingress / ALB | HTTP 라우팅 API 객체 / 실제 AWS 로드밸런서 |
| Controller / 데이터 경로 | 설정과 상태를 조정 / 실제 요청 전달 |
| Pod / Node | 앱 배치 단위 / 그 앱이 실행되는 머신 |
| Terraform state / etcd / DB | 자원 연결 기록 / Kubernetes 객체 저장 / 업무 데이터 |
| CRI / CNI / CSI | 컨테이너 실행 / 네트워크 구성 / 스토리지 연결 인터페이스 |
| IAM / RBAC | AWS 자원 권한 / Kubernetes 객체에 대한 역할 기반 권한 |
| Kubernetes Namespace / Linux namespace | API 객체 관리 범위 / 프로세스가 보는 OS 자원 범위 |

## 7. 중간 원리를 확인하는 추가 문제

1. kubelet을 종료했을 때 containerd가 ‘kubelet 안에 있으므로 함께 사라진다’는 설명이 맞는가?
2. EKS 노드가 앱 이미지를 실행할 때 원래 Dockerfile을 반드시 다운로드해야 하는가?
3. OCI와 runc 중 실행 가능한 프로그램은 무엇인가? 둘은 어떤 관계인가?
4. Pod IP를 바꾸고 `80 → 8080`만 유지하면 전달 규칙을 갱신하지 않아도 되는가?
5. ALB가 전혀 없어도 클러스터 내부에서 Service를 통해 교체된 Pod로 접속할 수 있는가?
6. 주문 API가 500을 반환하는데 `kubectl get pods`가 성공했다. 모순인가?
7. 백업을 자동화했다면 팀의 데이터 복구 책임도 없어진 것인가?

### 추가 문제 해설

1. 아니다. 별도 프로세스다. kubelet 정지 시 Pod 관리·상태 보고에는 영향이 있지만 프로그램 포함 관계로 설명하지 않는다.
2. 아니다. runtime은 빌드 결과 이미지와 실행 설정을 사용한다. 빌드 입력인 Dockerfile 자체는 실행에 필수 입력이 아니다.
3. runc가 프로그램이고, OCI runtime 규격을 구현한다. OCI는 규격을 정의하는 프로젝트·규격 문맥이다.
4. 아니다. 포트와 주소는 다른 정보다. 새로운 대상 IP를 목록·규칙에 반영해야 한다.
5. 가능하다. 일반 ClusterIP 경로는 EndpointSlice와 노드의 전달 구현으로 동작할 수 있다.
6. 모순이 아니다. 앱 요청과 클러스터 관리 요청은 목적지 프로그램과 경로가 다르다.
7. 아니다. 정책·보존·복구 시점·실제 복구 가능성의 검증 책임은 남는다. 수동 실행 여부와 책임은 다른 문제다.
