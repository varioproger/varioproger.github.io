# 01. 최종 이해도 문제

> 전체 학습 32/35 · 최종 점검
> [이전: 21. 오브젝트 사전과 원문으로 돌아가는 지도](../02_심화/21_오브젝트_사전과_원문_지도.md) · [전체 목차](../README.md) · [다음: 02. 최종 이해도 문제 답안지](02_답안지.md)

답은 [별도 답안지](02_답안지.md)에 쓴다. 괄호의 점수는 배점이다.

## 1부. 개념의 경계 구분 — 20점

각 문제에 1–3문장으로 답한다. 맞다/아니다만 쓰면 부분 점수만 받을 수 있다.

1. Terraform `apply`가 끝난 뒤 Pod 하나가 삭제되었다. Terraform이 새 Pod를 만드는가? 실제 복구 주체를 설명하라. (2)
2. Terraform state, Kubernetes etcd, 애플리케이션 DB가 각각 무엇을 저장하는지 구분하라. (3)
3. Docker image와 container의 차이를 “저장된 것”과 “실행 중인 것” 관점에서 설명하라. (2)
4. Docker로 만든 이미지를 Docker Engine이 없는 EKS 노드에서 실행할 수 있는 이유를 containerd·CRI·OCI를 포함해 설명하라. (3)
5. Kubernetes와 EKS의 관계를 설명하라. EKS를 Kubernetes 다음 단계의 별도 실행 엔진으로 생각하면 왜 틀리는가? (2)
6. Kubernetes API endpoint와 사용자가 접속하는 ALB 주소의 목적과 요청 대상을 구분하라. (2)
7. Deployment 객체와 Deployment controller의 차이는 무엇인가? (2)
8. Node, kubelet, containerd를 각각 장소·에이전트·런타임 관점에서 구분하라. (2)
9. Kubernetes ServiceAccount와 AWS IAM role은 같은 권한 체계인가? 둘을 어떤 경우에 연결하는가? (2)

## 2부. 처음부터 끝까지 흐름 추적 — 20점

10. 다음 항목을 일반적인 작업 순서로 배열하고 각 화살표의 동사를 쓰라. (4)

   `ECR`, `Git push`, `EKS의 Kubernetes API`, `Docker build`, `Deployment`, `containerd`, `Pod`, `CI runner`

11. Terraform으로 VPC·EKS·Managed Node Group을 만들 때 HCL, provider, AWS API, state가 맡는 역할을 설명하라. (3)
12. `kubectl apply -f deployment.yaml`이 성공한 뒤 Pod가 Ready가 되기까지 API Server, Deployment controller, ReplicaSet controller, scheduler, kubelet, containerd의 역할을 순서대로 쓰라. (4)
13. ECR에 `orders:v2`를 push했지만 실행 중인 앱은 계속 v1이다. 정상일 수 있는 이유와 실제 배포에 필요한 변경을 설명하라. (2)
14. 사용자가 `https://orders.example.com/api`로 보낸 요청이 일반 EKS + ALB IP target 구성에서 Pod까지 도착하는 경로를 쓰라. Ingress, Service, AWS Load Balancer Controller가 설정상 어디에 관여하는지도 표시하라. (4)
15. Pod A가 삭제되고 새 IP의 Pod B가 생성되었을 때 Service로 새 연결이 가능해지는 과정을 label, EndpointSlice, 데이터 경로를 포함해 설명하라. (3)

## 3부. Kubernetes 오브젝트 이해 — 20점

16. Deployment → ReplicaSet → Pod의 관계에서 누가 누구를 소유하며, 각 객체가 맡는 의도는 무엇인가? (3)
17. Service가 Pod를 선택하는 관계와 Deployment가 ReplicaSet을 소유하는 관계는 어떻게 다른가? Service를 삭제하면 일반적으로 Pod도 삭제되는가? (2)
18. Deployment, StatefulSet, DaemonSet, Job 중 다음 요구에 맞는 객체를 하나씩 고르고 이유를 쓰라. (4)

   a. 교체 가능한 HTTP API
   b. `db-0`, `db-1` 같은 안정적인 구성원 이름과 개별 저장소
   c. 대상 노드마다 하나씩 실행할 로그 에이전트
   d. 완료 후 종료되는 일회성 데이터 처리

19. readiness, liveness, startup probe가 각각 묻는 질문과 실패 시 대표 동작을 설명하라. (3)
20. ConfigMap을 환경 변수로 사용하는 Pod가 실행 중이다. ConfigMap 값을 수정하면 프로세스의 환경 변수가 즉시 바뀌는가? 안전한 반영 방법을 하나 쓰라. (2)
21. PVC, PV, StorageClass, CSI driver, 실제 디스크의 관계를 소비자 요구에서 실제 mount까지 연결하라. (3)
22. Role, RoleBinding, ClusterRole, ClusterRoleBinding의 범위와 연결 차이를 설명하라. (3)

## 4부. 장애 진단과 자동 확장 — 20점

각 사례에 첫 가설과 확인할 증거를 쓴다. “재시작한다”만 쓰면 점수를 받을 수 없다.

23. 새 Pod가 Pending이며 `nodeName`이 비어 있다. Node CPU의 현재 사용률은 낮다. 가능한 원인 두 가지와 확인할 Kubernetes 증거를 쓰라. (3)
24. Pod에 `nodeName`이 있고 상태가 `ImagePullBackOff`다. CI의 ECR push는 성공했다. 조사할 세 가지를 쓰라. (3)
25. `FailedCreatePodSandBox`와 IP 할당 실패 메시지가 보인다. CPU를 늘리기 전에 EKS에서 확인할 자원을 쓰라. (2)
26. Pod 두 개는 Running이지만 Ready가 아니며 Service의 정상 대상이 없다. 어떤 객체·상태·로그를 순서대로 볼 것인가? (3)
27. Pod는 Ready이고 클러스터 내부 Service 접속도 성공하지만 ALB는 503을 반환한다. 어떤 경계에서 무엇을 확인할 것인가? (3)
28. HPA의 desired replicas는 10인데 실제 Ready Pod는 4개다. HPA에서 시작해 기반 자원까지 조사 순서를 쓰라. (3)
29. HPA와 Cluster Autoscaler의 입력과 출력을 각각 설명하라. HPA가 늘어났다고 노드가 반드시 생기는 것은 왜 아닌가? (2)
30. PDB에 `minAvailable: 2`가 있는데 노드가 갑자기 고장 나 서비스가 중단되었다. 모순이 아닌 이유를 설명하라. (1)

## 5부. 종합 설계 — 20점

다음 요구를 만족하는 구조를 설계한다. 반드시 그림 또는 화살표 흐름과 설명을 함께 쓴다.

> 주문 API를 AWS EKS에서 운영한다. Git에 코드가 merge되면 테스트 후 이미지를 만들고 ECR에 저장한다. 평소 Pod 3개가 여러 노드에 분산되어야 하고, 증가한 요청에 따라 확장해야 한다. 외부 사용자는 HTTPS로 접속한다. 앱은 지정한 S3 경로만 읽을 수 있어야 한다. 주문 데이터는 Pod 교체 후에도 남아야 하고 복구 목표를 가져야 한다. 새 버전 실패 시 사용자 영향을 줄이고 원인을 관찰할 수 있어야 한다.

31. Git부터 사용자의 HTTPS 요청까지 구성요소를 연결한 전체 흐름을 그려라. Terraform이 만드는 영역, CI/CD가 반복하는 영역, Kubernetes가 계속 조정하는 영역을 구분하라. (6)
32. 필요한 Kubernetes 객체를 고르고 각 객체가 해결하는 요구를 쓰라. 최소 Deployment, Service, Ingress 또는 Gateway 계열, ServiceAccount, HPA를 포함한다. (4)
33. HPA가 Pod 수를 늘린 뒤 실행 공간이 부족한 경우의 노드 공급 구조를 설명하라. Cluster Autoscaler 또는 Karpenter 중 하나를 선택해 입력·출력·실패 조건을 쓰라. (3)
34. 앱 권한, 배포자 권한, 노드 권한을 분리해 설명하라. Kubernetes RBAC와 AWS IAM이 각각 어디에 적용되는지도 쓰라. (3)
35. 무중단에 가까운 배포, 관측, 데이터 보호를 위해 필요한 설정·운영 정책을 각각 한 가지 이상 쓰고, Kubernetes/EKS가 자동으로 보장하지 않는 부분을 설명하라. (4)

## 보너스: 설명 능력 확인 — 점수에는 미포함

36. “Kubernetes가 알아서 한다”라는 문장을 사용하지 않고 Pod 복구를 설명하라.
37. `kubectl get pods`가 모두 Running이어도 서비스가 장애일 수 있는 이유를 네 계층으로 설명하라.
38. Terraform, Docker, Kubernetes, EKS 중 하나를 제거한다면 어떤 책임을 다른 도구나 사람이 맡아야 하는지 하나의 사례로 설명하라.
