# 10장. 오퍼레이터 프레임워크

> **학습목표**
> - `Manager`, `Controller`, `Reconciler`로 이어지는 controller-runtime의 계층을 설명할 수 있다.
> - `client.Client`가 캐시에서 읽고 API 서버에 쓰는 이유와 그 함의를 안다.
> - Kubebuilder로 프로젝트를 스캐폴딩하고 마커 기반 코드 생성을 사용할 수 있다.
> - 파이널라이저, Conditions, 재큐 전략 등 조정 로직의 표준 설계 패턴을 적용할 수 있다.
> - `envtest`와 fake client의 차이를 이해하고 상황에 맞는 테스트 전략을 고른다.
> - Operator SDK 등 대안 프레임워크가 controller-runtime과 어떤 관계인지 안다.

---

## 들어가며

8장에서 client-go의 Informer, Lister, 워크큐를 직접 배선해 컨트롤러를 만들었다. 9장에서는 CRD로 커스텀 리소스의 스키마와 버저닝을 정의했다. 이 장은 그 둘을 잇는다. **CRD는 만들었는데, 그것을 조정할 컨트롤러는 어떻게 돌리는가?**

8장에서 직접 짠 코드를 돌이켜 보자. Informer 설정, 워크큐 배선, 캐시 동기화 대기, 이벤트 핸들러 등록, 리더 선출 연결... **도메인 로직(원하는 상태와 실제 상태를 비교해 조치하는 부분)은 전체 코드의 일부에 불과했다.** 나머지는 어떤 컨트롤러를 만들든 반복되는 보일러플레이트다.

**controller-runtime**은 이 반복을 라이브러리로 흡수한다. 8장에서 client-go로 직접 만든 패턴 — Informer, 워크큐, 조정 함수 — 을 controller-runtime이 감싸 주고, 개발자는 `Reconciler` 인터페이스 하나만 구현하면 된다. **Kubebuilder**는 그 위에 스캐폴딩과 코드 생성을 얹은 CLI 도구다.

```
8장: client-go 저수준           10장: controller-runtime
┌─────────────────────┐        ┌─────────────────────┐
│ Informer 수동 설정     │        │  Manager             │
│ 워크큐 수동 배선        │  ───▶  │  ├─ Controller (자동) │
│ 이벤트 핸들러 수동 등록  │        │  │   └─ 워크큐/Informer│
│ 캐시 동기화 대기 코드    │        │  └─ Reconciler (직접) │
│ 리더 선출 별도 연결      │        │      ← 여기만 작성     │
└─────────────────────┘        └─────────────────────┘
```

이 장을 마치면 CRD 하나(9장에서 정의한 `WebApp`을 그대로 쓴다)에 대해 실제로 동작하는 오퍼레이터를 로컬에서 실행하게 된다.

## 10.1 controller-runtime 아키텍처

### 세 개의 계층

controller-runtime은 세 가지 개념으로 이루어진다.

```
┌────────────────────────────────────────────────────────┐
│  Manager                                                │
│    · 공유 캐시(Informer 집합)를 소유하고 시작한다              │
│    · 공유 client.Client를 제공한다                          │
│    · 리더 선출을 관리한다 (5장)                              │
│    · 메트릭·헬스체크 HTTP 서버를 띄운다                        │
│    · 여러 Controller를 등록받아 함께 구동한다                   │
│                                                          │
│    ┌──────────────────────────────────────────┐         │
│    │  Controller                               │         │
│    │    · Source(감시 대상)를 워크큐에 연결한다        │         │
│    │    · 워크큐, 워커 고루틴을 자동으로 배선한다        │         │
│    │    · 재시도·레이트 리밋을 자동 처리한다             │         │
│    │                                            │         │
│    │    ┌──────────────────────────────┐        │         │
│    │    │  Reconciler (직접 구현하는 부분)   │        │         │
│    │    │    Reconcile(ctx, req)        │        │         │
│    │    │      → (Result, error)        │        │         │
│    │    └──────────────────────────────┘        │         │
│    └──────────────────────────────────────────┘         │
└────────────────────────────────────────────────────────┘
```

**Manager**는 프로세스 하나에 해당한다. 캐시, 클라이언트, 리더 선출, 메트릭 서버를 한 번만 만들어 여러 Controller가 공유한다. 오퍼레이터가 CRD 세 개를 조정해야 하면, Controller 세 개가 같은 Manager 아래에서 돈다.

```go
// cmd/main.go
scheme := runtime.NewScheme()
_ = clientgoscheme.AddToScheme(scheme)
_ = demov1.AddToScheme(scheme)

mgr, err := ctrl.NewManager(ctrl.GetConfigOrDie(), ctrl.Options{
    Scheme:                 scheme,
    Metrics:                metricsserver.Options{BindAddress: ":8080"},
    HealthProbeBindAddress: ":8081",
    LeaderElection:         true,
    LeaderElectionID:       "webapp-operator.example.com",
})
if err != nil {
    setupLog.Error(err, "unable to start manager")
    os.Exit(1)
}

if err := (&controller.WebAppReconciler{
    Client: mgr.GetClient(),
    Scheme: mgr.GetScheme(),
}).SetupWithManager(mgr); err != nil {
    setupLog.Error(err, "unable to create controller", "controller", "WebApp")
    os.Exit(1)
}

if err := mgr.Start(ctrl.SetupSignalHandler()); err != nil {
    setupLog.Error(err, "problem running manager")
    os.Exit(1)
}
```

**Controller**는 `SetupWithManager`가 만든다. `For(&demov1.WebApp{})`가 8장에서 손으로 만든 Informer + 이벤트 핸들러 + 워크큐 조합을 한 줄로 대신한다.

```go
func (r *WebAppReconciler) SetupWithManager(mgr ctrl.Manager) error {
    return ctrl.NewControllerManagedBy(mgr).
        For(&demov1.WebApp{}).
        Owns(&appsv1.Deployment{}).      // 소유한 Deployment의 변경도 감시
        WithOptions(controller.Options{MaxConcurrentReconciles: 2}).
        Complete(r)
}
```

내부적으로 무슨 일이 일어나는지는 8장의 그림 그대로다. `For`가 지정한 타입마다 Informer가 만들어지고, 이벤트가 오면 키(namespace/name)가 워크큐에 들어가고, 워커 고루틴이 `Reconciler.Reconcile`을 호출한다. **차이는 이 배선을 개발자가 짤 필요가 없다는 것뿐이다.**

### Reconciler 인터페이스

```go
type Reconciler interface {
    Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error)
}

type Request struct {
    types.NamespacedName   // Namespace, Name 필드만 있다 — 오브젝트 자체가 아니다
}
```

**`Request`에 오브젝트가 아니라 이름만 들어 있는 이유는 8장에서 워크큐에 키만 넣은 이유와 같다.** 이벤트가 발생한 시점과 워커가 처리하는 시점 사이에 오브젝트가 또 바뀌었을 수 있다. 조정 함수는 항상 **그 시점의 최신 상태**를 캐시에서 다시 읽어야 한다.

```go
func (r *WebAppReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
    var app demov1.WebApp
    if err := r.Get(ctx, req.NamespacedName, &app); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err)
    }
    // ... 조정 로직 ...
    return ctrl.Result{}, nil
}
```

### client.Client — 캐시에서 읽고, API 서버에 쓴다

`r.Get`, `r.List`는 API 서버를 직접 호출하지 않는다. **Manager가 소유한 로컬 캐시(Informer의 Store)에서 읽는다.** 반면 `r.Create`, `r.Update`, `r.Delete`, `r.Patch`, `r.Status().Update()`는 캐시를 거치지 않고 **API 서버에 직접 요청한다.**

```
읽기 (Get/List)                 쓰기 (Create/Update/Delete/Patch)
      │                                    │
      ▼                                    ▼
┌──────────────┐                  ┌──────────────────┐
│ 로컬 캐시      │                  │  API 서버 (직접)    │
│ (Informer가   │                  │  → etcd에 반영     │
│  watch로 채움) │                  │  → watch 이벤트 발생│
└──────────────┘                  └──────────────────┘
```

| | 읽기 | 쓰기 |
|---|---|---|
| 경로 | 로컬 캐시 (`Indexer`) | API 서버 직접 |
| 지연 | 거의 없음 | 네트워크 왕복 |
| API 서버 부하 | 없음 (캐시가 이미 있으면) | 있음 |
| 최신성 | **약간 지연될 수 있다** (watch 전파 지연) | 항상 최신 요청 |

**이것이 함의하는 것**: 방금 만든 오브젝트를 즉시 `Get`으로 읽으면 캐시에 아직 반영되지 않아 `NotFound`가 나올 수 있다. **조정 함수 안에서는 이 지연을 전제로 설계해야 한다.** 대부분의 경우 문제가 되지 않는다 — 다음 조정에서 캐시가 따라잡기 때문이다(레벨 트리거, 5장). 정말 최신 상태를 강제로 읽어야 한다면 `mgr.GetAPIReader()`로 캐시를 건너뛸 수 있다(11장에서 웹훅의 클러스터 조회 시 이 문제를 다시 다룬다).

> **캐시 대상 축소하기**
>
> 기본적으로 Manager는 `Scheme`에 등록된 모든 타입, 모든 네임스페이스를 캐시한다. 클러스터가 크면 메모리 부담이 크다. `cache.Options`로 특정 네임스페이스나 라벨셀렉터로 캐시 범위를 좁힐 수 있다.
>
> ```go
> mgr, err := ctrl.NewManager(cfg, ctrl.Options{
>     Cache: cache.Options{
>         ByObject: map[client.Object]cache.ByObject{
>             &corev1.Secret{}: {
>                 Namespaces: map[string]cache.Config{
>                     "webapp-operator-system": {},
>                 },
>             },
>         },
>     },
> })
> ```

### 마커 주석이 코드 생성의 입력이다

Go 주석이 `controller-gen`의 입력이 된다. 9장에서 YAML로 쓴 OpenAPI 스키마 제약을 Go 타입에 마커로 붙인다.

```go
// api/v1/webapp_types.go
package v1

import (
    corev1 "k8s.io/api/core/v1"
    metav1 "k8s.io/apimachinery/pkg/apis/meta/v1"
)

type WebAppSpec struct {
    // +kubebuilder:validation:Required
    // +kubebuilder:validation:MinLength=1
    // +kubebuilder:validation:Pattern=`^[a-z0-9.\-/]+:[a-zA-Z0-9._\-]+$`
    Image string `json:"image"`

    // +kubebuilder:validation:Minimum=0
    // +kubebuilder:validation:Maximum=50
    // +kubebuilder:default=1
    // +optional
    Replicas *int32 `json:"replicas,omitempty"`

    // +kubebuilder:validation:Minimum=1
    // +kubebuilder:validation:Maximum=65535
    // +kubebuilder:default=8080
    // +optional
    Port int32 `json:"port,omitempty"`
}

type WebAppStatus struct {
    // +optional
    Phase string `json:"phase,omitempty"`

    // +optional
    ReadyReplicas int32 `json:"readyReplicas,omitempty"`

    // +optional
    ObservedGeneration int64 `json:"observedGeneration,omitempty"`

    // +optional
    // +listType=map
    // +listMapKey=type
    Conditions []metav1.Condition `json:"conditions,omitempty"`
}

// +kubebuilder:object:root=true
// +kubebuilder:subresource:status
// +kubebuilder:resource:shortName=wa
// +kubebuilder:printcolumn:name="Image",type=string,JSONPath=`.spec.image`
// +kubebuilder:printcolumn:name="Ready",type=integer,JSONPath=`.status.readyReplicas`
// +kubebuilder:printcolumn:name="Phase",type=string,JSONPath=`.status.phase`
type WebApp struct {
    metav1.TypeMeta   `json:",inline"`
    metav1.ObjectMeta `json:"metadata,omitempty"`
    Spec              WebAppSpec   `json:"spec,omitempty"`
    Status            WebAppStatus `json:"status,omitempty"`
}

// +kubebuilder:object:root=true
type WebAppList struct {
    metav1.TypeMeta `json:",inline"`
    metav1.ListMeta `json:"metadata,omitempty"`
    Items           []WebApp `json:"items"`
}

func init() {
    SchemeBuilder.Register(&WebApp{}, &WebAppList{})
}
```

```bash
make manifests generate
```

이 한 명령이 두 가지를 한다.

| 대상 | 마커 | 산출물 |
|---|---|---|
| `generate` | `+kubebuilder:object:root=true` 등 | `zz_generated.deepcopy.go` |
| `manifests` | `+kubebuilder:validation:*`, `+kubebuilder:subresource:*` | `config/crd/bases/*.yaml` |
| `manifests` | `+kubebuilder:rbac:*` (10.4절 컨트롤러 코드에 작성) | `config/rbac/role.yaml` |

**Go 타입이 진실의 원천이 된다.** 9장에서 CRD YAML을 손으로 관리했다면, 여기서는 Go 타입과 CRD YAML을 별도로 동기화할 필요가 없다 — 항상 `make manifests`로 재생성한다.

```bash
cat config/crd/bases/demo.example.com_webapps.yaml | head -30
```

### make의 역할

Kubebuilder Makefile은 자주 쓰는 작업을 캡슐화한다.

| 타겟 | 하는 일 |
|---|---|
| `make manifests` | 마커 → CRD/RBAC/웹훅 YAML |
| `make generate` | 마커 → DeepCopy 코드 |
| `make install` | CRD를 현재 kubeconfig의 클러스터에 등록 |
| `make run` | 매니저를 **로컬에서** 실행 (kubeconfig로 클러스터 접속) |
| `make docker-build` | 컨트롤러 이미지 빌드 |
| `make deploy` | `config/`를 클러스터에 적용 (오퍼레이터를 Pod로 배포) |
| `make test` | envtest 기반 통합 테스트 (10.5절) |

**개발 중에는 `make run`이 압도적으로 편하다.** 이미지를 빌드하지 않고, 컨트롤러 바이너리를 로컬에서 실행하면서 클러스터의 CRD만 조정한다. 로그도 터미널에 바로 찍힌다.

## 10.3 Operator SDK와의 관계

**Operator SDK는 controller-runtime 위에 다른 스캐폴딩을 얹은 것**이지, 경쟁 프레임워크가 아니다. Go 프로젝트를 만들면 내부 구조는 Kubebuilder가 만드는 것과 사실상 동일하다.

```bash
operator-sdk init --domain example.com --plugins go/v4
operator-sdk create api --group demo --version v1 --kind WebApp --resource --controller
```

**차이는 Go가 아닌 언어를 쓰고 싶을 때 드러난다.** Operator SDK는 세 가지 프로젝트 타입을 제공한다.

| 타입 | 조정 로직을 어떻게 작성하는가 | 적합한 경우 |
|---|---|---|
| **Go** | Kubebuilder와 사실상 동일한 controller-runtime 코드 | Go 팀, 복잡한 로직 |
| **Ansible** | CR의 spec을 변수로 받는 Ansible 플레이북 | 기존 Ansible 자동화 자산이 있는 팀 |
| **Helm** | CR의 spec이 Helm values가 되고, 조정이 `helm upgrade`가 된다 | 이미 Helm 차트가 있고 로직이 단순한 경우 |

```bash
operator-sdk init --plugins helm --domain example.com
operator-sdk create api --group demo --version v1 --kind WebApp --helm-chart=./charts/webapp
```

**Helm 오퍼레이터의 조정 로직은 사실상 "CR을 받아서 `helm upgrade --install`을 실행"이다.** Go 코드를 한 줄도 쓰지 않고 기본적인 배포·업그레이드 로직을 가진 오퍼레이터를 만들 수 있다. 다만 페일오버 판단, 외부 시스템 폴링 같은 절차적 로직은 Helm 템플릿으로 표현할 수 없으므로 한계가 뚜렷하다.

또한 Operator SDK는 **OLM(Operator Lifecycle Manager)** 번들 생성을 지원해 OperatorHub 배포를 염두에 둔 프로젝트에 유리하다. 이 책은 Kubebuilder를 기준으로 진행하지만, **여기서 배우는 controller-runtime 지식은 Operator SDK의 Go 프로젝트에도 그대로 적용된다.**

## 10.4 조정 로직 설계 패턴

### 파이널라이저 — 삭제 전 정리

5장에서 본 `ownerReferences` 기반 가비지 컬렉션은 **쿠버네티스 안의** 자식 리소스에만 통한다. 클라우드 리소스, 외부 DB 레코드, 외부 API 등록처럼 **클러스터 밖의 자원**을 정리하려면 파이널라이저가 필요하다.

```go
const finalizerName = "demo.example.com/finalizer"

func (r *WebAppReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
    var app demov1.WebApp
    if err := r.Get(ctx, req.NamespacedName, &app); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err)
    }

    // 삭제 중인가?
    if !app.DeletionTimestamp.IsZero() {
        if controllerutil.ContainsFinalizer(&app, finalizerName) {
            if err := r.cleanupExternalResources(ctx, &app); err != nil {
                return ctrl.Result{}, err   // 정리 실패 → 재시도
            }
            controllerutil.RemoveFinalizer(&app, finalizerName)
            if err := r.Update(ctx, &app); err != nil {
                return ctrl.Result{}, err
            }
        }
        return ctrl.Result{}, nil
    }

    // 삭제 중이 아니면 파이널라이저를 붙인다 (한 번만)
    if !controllerutil.ContainsFinalizer(&app, finalizerName) {
        controllerutil.AddFinalizer(&app, finalizerName)
        if err := r.Update(ctx, &app); err != nil {
            return ctrl.Result{}, err
        }
    }

    // ... 본 조정 로직 ...
    return ctrl.Result{}, nil
}
```

> **⚠️ 파이널라이저는 정말 필요할 때만**
> 컨트롤러가 죽거나 버그로 무한히 실패하면, 파이널라이저를 제거해 줄 주체가 없어 리소스가 영원히 `Terminating` 상태에 남는다. **`ownerReferences`로 처리되는 정리에는 파이널라이저가 필요 없다.** 그리고 정리 로직은 반드시 **멱등**해야 한다 — 이미 지워진 것을 다시 지우려 해도 성공을 반환해야 한다.

### status와 Conditions — 표준 관용구

status는 컨트롤러만 쓰는 서브리소스다(9장). `metav1.Condition`은 쿠버네티스 생태계 전반에서 쓰이는 표준 상태 표현이다.

```go
type Condition struct {
    Type               string             // "Ready", "Progressing" 등
    Status             ConditionStatus    // "True" | "False" | "Unknown"
    ObservedGeneration int64
    LastTransitionTime metav1.Time
    Reason             string             // CamelCase, 기계가 읽는 짧은 코드
    Message            string             // 사람이 읽는 설명
}
```

```go
func (r *WebAppReconciler) setCondition(
    app *demov1.WebApp, condType string, status metav1.ConditionStatus, reason, msg string) {
    meta.SetStatusCondition(&app.Status.Conditions, metav1.Condition{
        Type:               condType,
        Status:             status,
        Reason:             reason,
        Message:            msg,
        ObservedGeneration: app.Generation,
    })
}
```

`meta.SetStatusCondition`(`k8s.io/apimachinery/pkg/api/meta`)은 같은 `Type`의 기존 Condition을 찾아 **`Status`가 실제로 바뀔 때만** `LastTransitionTime`을 갱신한다. 매 조정마다 Condition을 새로 만들면 `LastTransitionTime`이 계속 바뀌어 "언제부터 이 상태였는가"라는 정보가 무의미해진다.

```yaml
status:
  observedGeneration: 3
  readyReplicas: 3
  phase: Running
  conditions:
    - type: Ready
      status: "True"
      reason: AllReplicasReady
      message: "3/3 replicas ready"
      lastTransitionTime: "2026-09-20T10:00:00Z"
      observedGeneration: 3
```

```bash
kubectl get webapp hello -o jsonpath='{.status.conditions[?(@.type=="Ready")].status}'
kubectl wait webapp/hello --for=condition=Ready --timeout=60s
```

**`ObservedGeneration`이 중요한 이유**: `spec.generation`은 spec이 바뀔 때마다 증가한다(9장). status의 `observedGeneration`이 `metadata.generation`보다 낮으면 **"컨트롤러가 아직 최신 spec을 반영하지 못했다"**는 뜻이다. 이 필드가 있어야 사용자가 "내 변경이 적용됐는가"를 정확히 판단할 수 있다.

### 재큐 전략

```go
// ① 성공 — 다음 이벤트(watch)까지 대기, 폴링 없음
return ctrl.Result{}, nil

// ② 에러 — 워크큐가 지수 백오프로 재시도 (8장의 레이트 리미터)
return ctrl.Result{}, err

// ③ 외부 상태를 폴링해야 할 때 — 정해진 시간 후 재조정
return ctrl.Result{RequeueAfter: 30 * time.Second}, nil

// ④ 즉시 재조정 (백오프 적용) — 남용하지 않는다
return ctrl.Result{Requeue: true}, nil
```

**`RequeueAfter`가 실제로 쓰이는 경우**는 클러스터 밖의 상태를 감시해야 할 때다. 예를 들어 클라우드 인증서 발급이 끝나기를 기다리거나, 외부 SaaS API의 프로비저닝 완료를 폴링할 때다.

```go
provisioned, err := checkExternalProvisioning(ctx, app.Spec.ExternalRef)
if err != nil {
    return ctrl.Result{}, err
}
if !provisioned {
    r.setCondition(app, "Ready", metav1.ConditionFalse, "Provisioning", "외부 리소스 프로비저닝 대기 중")
    _ = r.Status().Update(ctx, app)
    return ctrl.Result{RequeueAfter: 15 * time.Second}, nil
}
```

> **`Requeue: true`보다 `Watches()`를 먼저 고려한다**
> 대부분의 "다시 확인해야 할 일"은 사실 **다른 리소스의 변화를 감시**하면 해결된다. `Owns()`나 `Watches()`로 관심 있는 리소스를 등록하면 변화가 생겼을 때 자동으로 조정이 촉발되므로, 폴링(`RequeueAfter`)이 필요한 경우는 **클러스터 API로 관찰할 수 없는 외부 상태**로 좁혀진다.

## 10.5 테스트 전략

8장에서 `client-go`의 fake client로 컨트롤러 로직을 단위 테스트했다. controller-runtime 기반 오퍼레이터에는 두 계층의 테스트가 있다.

│  단위 테스트 — fake client                                │

│    · 메모리 안에서 빠르게 동작                                │

│  통합 테스트 — envtest                                     │

│    · CRD 검증, 웹훅, status 서브리소스가 실제로 동작한다          │

**③ Reconciler 구현** — `internal/controller/webapp_controller.go`에 다음을 작성한다. 핵심은 `spec.replicas`/`spec.image`에 맞는 Deployment를 멱등하게 유지하고, `status.conditions`에 `Ready`를 반영하는 것이다.

```go
func (r *WebAppReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
    var app demov1.WebApp
    if err := r.Get(ctx, req.NamespacedName, &app); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err)
    }

    deploy := &appsv1.Deployment{
        ObjectMeta: metav1.ObjectMeta{Name: app.Name, Namespace: app.Namespace},
    }
    _, err := controllerutil.CreateOrUpdate(ctx, r.Client, deploy, func() error {
        labels := map[string]string{"app": app.Name}
        deploy.Spec.Replicas = app.Spec.Replicas
        deploy.Spec.Selector = &metav1.LabelSelector{MatchLabels: labels}
        deploy.Spec.Template = corev1.PodTemplateSpec{
            ObjectMeta: metav1.ObjectMeta{Labels: labels},
            Spec: corev1.PodSpec{
                Containers: []corev1.Container{{
                    Name:  "app",
                    Image: app.Spec.Image,
                    Ports: []corev1.ContainerPort{{ContainerPort: app.Spec.Port}},
                }},
            },
        }
        return controllerutil.SetControllerReference(&app, deploy, r.Scheme)
    })
    if err != nil {
        return ctrl.Result{}, err
    }

    app.Status.ReadyReplicas = deploy.Status.ReadyReplicas
    app.Status.ObservedGeneration = app.Generation
    desired := ptr.Deref(app.Spec.Replicas, 1)
    if deploy.Status.ReadyReplicas >= desired {
        app.Status.Phase = "Running"
        r.setCondition(&app, "Ready", metav1.ConditionTrue, "AllReplicasReady", "모든 replica가 준비됨")
    } else {
        app.Status.Phase = "Progressing"
        r.setCondition(&app, "Ready", metav1.ConditionFalse, "ReplicasNotReady", "replica 준비 중")
    }
    if err := r.Status().Update(ctx, &app); err != nil {
        return ctrl.Result{}, err
    }
    return ctrl.Result{}, nil
}
```

## 실습 과제

**과제 1 — CreateOrUpdate 없이 구현하고 무한 루프 관찰**

`reconcileService` 함수를 추가해 WebApp마다 ClusterIP Service가 함께 생성되도록 확장한다. `Owns(&corev1.Service{})`도 등록한다.

**과제 4 — fake client 단위 테스트 작성**

**과제 5 — envtest 통합 테스트 작성**

## 요약

- **controller-runtime은 8장에서 손으로 짠 Informer/워크큐/이벤트 핸들러 배선을 라이브러리로 감싼다.** 개발자는 `Reconciler.Reconcile(ctx, req) (Result, error)`만 구현하면 된다.
- **Manager**는 캐시·클라이언트·리더 선출을 소유하고 여러 Controller를 함께 구동한다. **Controller**는 `For`/`Owns`/`Watches`로 감시 대상을 워크큐에 연결한다.
- **`client.Client`는 읽기(Get/List)는 로컬 캐시에서, 쓰기(Create/Update/Delete)는 API 서버에 직접 요청한다.** 이로 인해 방금 쓴 값을 즉시 읽으면 지연이 있을 수 있다는 점을 설계에 반영해야 한다.
- **Kubebuilder**는 마커 주석을 입력으로 `make manifests`/`make generate`가 CRD, RBAC, DeepCopy 코드를 생성한다. **Go 타입이 진실의 원천**이 되어 스키마와 코드가 어긋나지 않는다.
- **Operator SDK는 controller-runtime 위의 다른 스캐폴딩**일 뿐이며, Go 프로젝트라면 사실상 동일하다. Ansible/Helm 옵션은 비Go 팀이나 Level 1~2 오퍼레이터에 적합하다.
- 조정 로직 설계 원칙: **파이널라이저는 클러스터 밖 자원 정리에만**, **Conditions로 상태를 표준화해 노출**, **`RequeueAfter`는 외부 상태 폴링에만 쓰고 가능하면 `Watches()`로 대체**한다.
- 테스트는 두 계층이다. **fake client**는 빠른 로직 단위 테스트에, **envtest**는 실제 apiserver+etcd로 API 상호작용 전체를 검증하는 통합 테스트에 쓴다.

**다음 장에서는** 오퍼레이터가 만든 리소스를 넘어, 클러스터에 들어오는 모든 리소스에 정책을 강제하는 어드미션 웹훅과 CEL 기반 정책 프레임워크를 다룬다.
