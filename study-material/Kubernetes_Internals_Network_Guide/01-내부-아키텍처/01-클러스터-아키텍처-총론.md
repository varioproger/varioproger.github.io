# 1장. 클러스터 아키텍처 총론

> **학습목표**
> - 선언적 상태와 조정 루프를 수렴성·멱등성 관점에서 형식화해 설명할 수 있다.
> - 컨트롤 플레인 5개 컴포넌트 각각의 책임 경계와 "하지 않는 일"을 구분할 수 있다.
> - 노드 컴포넌트(kubelet·kube-proxy·컨테이너 런타임·CNI·CSI/디바이스 플러그인)의 역할 분담을 설명할 수 있다.
> - `kubectl apply` 한 번이 컨테이너 실행까지 이어지는 전체 경로를 컴포넌트 단위로 추적할 수 있다.
> - 고가용성 구성에서 컴포넌트가 어떻게 배치되고 무엇으로 이중화되는지 개략적으로 안다.
> - 이 책 2부·3부가 다루는 영역과 이 장의 연결점을 파악한다.

---

## 들어가며

이 책은 쿠버네티스 오브젝트를 다루는 법을 다시 설명하지 않는다. `kubectl create deployment`가 무엇을 하는지, Pod와 Service가 어떤 관계인지는 이미 알고 있다고 전제한다. 대신 이 책이 답하려는 질문은 이것이다. **`kubectl apply -f deployment.yaml`을 실행한 순간, 그 YAML 한 장이 실제로 동작하는 컨테이너가 되기까지 어떤 컴포넌트들이 무엇을 주고받는가.**

이 질문에 제대로 답하려면 먼저 클러스터를 구성하는 컴포넌트들의 지도를 그려야 한다. 어떤 컴포넌트가 어떤 책임을 지는지, 그리고 — 이 부분이 더 중요한데 — **어떤 책임은 명시적으로 지지 않는지**를 구분해야 한다. 쿠버네티스가 안정적으로 확장되는 이유는 각 컴포넌트의 책임 경계가 매우 좁고 명확하게 그어져 있기 때문이다. 이 경계를 흐리게 이해하면 장애가 났을 때 엉뚱한 컴포넌트의 로그를 뒤지게 된다.

이 장은 1부 전체의 지도 역할을 한다. 1.1절에서 조정 루프를 개념적으로 정식화하고, 1.2~1.3절에서 컴포넌트 지도를 그린 뒤, 1.4절에서 요청 하나가 지도 위를 어떻게 이동하는지 추적한다. 2~6장은 이 지도의 각 칸을 하나씩 확대해서 들여다보는 작업이다.

## 1.1 선언적 상태와 조정 루프

### 명령형과 선언형의 차이를 다시 본다

명령형 시스템에서는 "무엇을 할지"를 지시한다. `docker run`, `scp`, 셸 스크립트가 그렇다. 이 방식의 문제는 **현재 상태를 알지 못한 채 동작을 실행한다**는 데 있다. 이미 실행 중인 컨테이너에 `docker run`을 다시 내리면 중복 컨테이너가 생긴다. 명령의 결과가 현재 상태에 의존하기 때문이다.

쿠버네티스는 선언형이다. "무엇을 원하는가"만 기술하고, "어떻게 그 상태로 만들 것인가"는 시스템이 결정한다. 이 차이를 정확히 형식화하면 다음과 같다.

```
desired state  (spec)     : 사용자가 API 서버에 기록한 "원하는 결과"
observed state (status)   : 클러스터에서 현재 실제로 관찰되는 상태
reconcile(desired, observed) → action
                             : 두 상태의 차이를 관찰해 좁히는 방향의 조치
```

여기서 `action`은 목표 상태를 직접 만들어내지 않는다. **차이를 줄이는 방향의 한 걸음**을 만들 뿐이다. ReplicaSet 컨트롤러가 "Pod가 2개 부족하다"를 관찰하면 2개를 한꺼번에 만들도록 시도하지만, 그 시도가 실패하거나 부분적으로만 성공해도 상관없다. 다음 조정 주기에 다시 관찰하고 다시 시도한다.

### 수렴성(Convergence)

조정 루프가 유효하려면 **유한한 조치의 반복만으로 관찰 상태가 목표 상태에 도달**해야 한다. 이를 수렴성이라 부른다. 수렴성이 성립하려면 다음 조건이 필요하다.

```
① 조치가 항상 "차이를 줄이는 방향"이어야 한다 (발산하지 않음)
② 외부 조건이 고정되면 유한 스텝 안에 오차가 0에 도달해야 한다
③ 조정 도중 desired state가 다시 바뀌면, 새 목표를 향해 다시 수렴을 시작한다
```

실제 쿠버네티스 컨트롤러가 수렴성을 보장하는 방식은 매우 단순하다. **매 조정마다 전체 상태를 다시 계산**하고, 그 차이만큼만 행동한다. "지난번에 무엇을 했는지"를 기억하지 않는다. 이 성질이 다음 절의 레벨 트리거 개념과 직접 연결된다.

### 레벨 트리거 vs 엣지 트리거 — 형식적 정의

이 개념은 입문서에서도 다루지만, 여기서는 왜 이것이 **수렴성의 필요조건**인지를 짚는다.

**엣지 트리거**는 상태 변화 이벤트 자체에 반응한다. `Pod 삭제됨`이라는 이벤트를 조건으로 조치가 실행된다. 이 모델의 문제는 이벤트가 유실될 수 있다는 것이다. 네트워크 단절, 컨트롤러 재시작, 큐 오버플로 등으로 이벤트 하나를 놓치면 그 조치는 **영원히 실행되지 않는다.** 시스템이 목표 상태로 수렴한다는 보장이 사라진다.

**레벨 트리거**는 이벤트가 아니라 **현재 관찰된 상태값(level)**에 반응한다. "Pod가 3개 있어야 하는데 지금 2개다"라는 판단은 과거에 어떤 이벤트가 있었는지와 무관하게, 지금 이 순간 API 서버를 조회하면 언제든 다시 계산할 수 있다. 이벤트를 몇 개 놓쳐도, 다음 조정 주기에 현재 상태를 다시 관찰하면 오차가 그대로 드러나고 즉시 교정된다.

```
엣지 트리거: state_t-1 → event → action        (event 유실 시 action 없음)
레벨 트리거: state_t   → diff(desired, state_t) → action  (항상 재계산 가능)
```

**쿠버네티스의 모든 내장 컨트롤러는 레벨 트리거로 설계되어 있다.** watch 이벤트는 "지금 다시 봐야 할 때가 됐다"는 신호(트리거)로만 쓰이고, 실제 판단은 항상 그 시점의 최신 상태를 다시 읽어서 내린다. 이 설계 원칙은 5장에서 Informer와 워크큐 구조를 다룰 때 코드 수준으로 다시 확인한다.

### 멱등성(Idempotency)

조정 함수가 같은 입력에 대해 여러 번 호출되어도 결과가 달라지지 않아야 한다.

```
reconcile(desired, observed) 를 두 번 연속 실행해도
observed'  = observed'' 이어야 한다
```

이것이 왜 필수인가. 레벨 트리거 모델에서는 **조정이 얼마나 자주, 몇 번 실행될지 예측할 수 없다.** watch 이벤트가 중복 도착할 수도 있고, 컨트롤러가 재시작하며 처음부터 다시 훑을 수도 있고, 주기적 재동기화(resync)가 겹칠 수도 있다. 멱등하지 않은 조정 함수 — 예를 들어 "항상 Pod를 하나 추가로 만든다" — 는 호출 횟수만큼 부작용이 누적되어 시스템을 오히려 발산시킨다.

멱등성을 지키는 실무적 방법은 "절대적 목표 상태와 비교해서 차이만큼만 행동하는 것"이다. "Pod를 하나 더 만들어라"가 아니라 "Pod 개수가 3이어야 하는데 지금 2이니 1개를 만들어라"로 조정 로직을 짜면, 그 조정이 중복 실행되어도 다음 실행 시점엔 이미 3개이므로 아무 일도 일어나지 않는다.

### 세 개념의 관계

```
┌─────────────────────────────────────────────────────┐
│  선언적 API (spec에 원하는 상태 기록)                    │
│         │                                            │
│         ▼                                            │
│  레벨 트리거 (이벤트가 아니라 "현재 상태"로 판단)           │
│         │                                            │
│         ▼                                            │
│  멱등한 조정 함수 (몇 번 실행되어도 같은 결과)              │
│         │                                            │
│         ▼                                            │
│  수렴 (유한 스텝 안에 desired == observed)              │
└─────────────────────────────────────────────────────┘
```

이 네 가지가 한 덩어리로 맞물려야 "컨트롤러가 죽었다 살아나도, 이벤트를 놓쳐도, 네트워크가 잠깐 끊겨도 결국 올바른 상태로 돌아온다"는 쿠버네티스의 핵심 신뢰성 모델이 성립한다. 5장에서 이 원칙이 실제 컨트롤러 코드에서 어떻게 구현되는지 자세히 다룬다.

## 1.2 컨트롤 플레인 컴포넌트 지도

컨트롤 플레인은 클러스터의 "판단"을 담당한다. 다섯 개 컴포넌트로 구성되며, 각각의 책임 경계는 의도적으로 매우 좁다.

```
┌──────────────────────────────────────────────────────────────┐
│                        컨트롤 플레인                             │
│                                                                │
│   kube-apiserver          모든 요청의 단일 관문, 유일한 etcd 접근자  │
│   etcd                    상태 저장소 (진실의 원천)                │
│   kube-scheduler          Pod의 노드 배치 "결정"만                │
│   kube-controller-manager 수십 개 조정 루프의 집합                │
│   cloud-controller-manager 클라우드 API 연동 전용                │
└──────────────────────────────────────────────────────────────┘
```

### kube-apiserver

**책임**: 모든 클러스터 상태 변경의 유일한 진입점. 인증·인가·어드미션·버전 변환·유효성 검증을 거쳐 etcd에 기록하고, watch를 통해 상태 변화를 다른 컴포넌트에 통지한다.

**하지 않는 일**:
- **스케줄링 결정을 내리지 않는다.** Pod를 어느 노드에 배치할지는 스케줄러의 몫이다. API 서버는 Pod가 어떤 노드에도 배정되지 않은 채로 저장되는 것을 허용한다(`spec.nodeName`이 빈 상태).
- **조정을 하지 않는다.** Deployment를 만들면 ReplicaSet과 Pod가 "저절로" 생기는 것처럼 보이지만, API 서버는 그 어떤 종속 오브젝트도 스스로 만들지 않는다. 그 일은 컨트롤러 매니저가 watch를 통해 감지하고 별도로 요청을 보내서 이루어진다.
- **직접 etcd 프로토콜 이외의 저장소 로직을 갖지 않는다.** API 서버는 stateless 프로세스에 가깝다(watch cache라는 메모리 상태는 있지만, 이는 최적화이지 진실의 원천이 아니다). 진짜 상태는 전적으로 etcd에 있다.

이 컴포넌트의 내부 구조(필터 체인, 버전 변환, 어그리게이션, watch cache, APF)는 2장 전체의 주제다.

### etcd

**책임**: 클러스터의 유일한 진실의 원천(source of truth). 모든 오브젝트, 모든 시크릿, 모든 상태가 여기 저장된다. Raft 합의 알고리즘으로 복제되어 일부 노드가 죽어도 데이터가 보존된다.

**하지 않는 일**:
- **쿠버네티스 오브젝트를 이해하지 않는다.** etcd는 범용 키-값 저장소다. Pod가 무엇인지, Deployment가 무엇인지 전혀 모른다. 그저 바이트 배열을 키로 저장하고 조회할 뿐이다. 오브젝트의 의미를 해석하는 계층은 전적으로 API 서버에 있다.
- **어떤 API 서버와도 직접 통신하는 클라이언트를 구분하지 않는다.** 접근 제어는 mTLS 인증서 수준에서 이루어지며, RBAC 같은 쿠버네티스 개념은 etcd에 존재하지 않는다.

etcd의 Raft 합의, 키 구조, MVCC, 압축은 3장에서 자세히 다룬다.

### kube-scheduler

**책임**: 아직 노드가 배정되지 않은 Pod를 감시하다가, 그 Pod가 실행되기에 가장 적합한 노드를 찾아 API 서버에 "이 Pod를 이 노드에 바인딩하라"는 요청을 보낸다.

**하지 않는 일**:
- **Pod를 직접 실행하지 않는다.** 스케줄러의 작업은 `Binding` 오브젝트를 만드는 순간 끝난다. 실제로 컨테이너를 시작하는 것은 해당 노드의 kubelet이다.
- **배치 이후의 상태를 감시하지 않는다.** 노드에 장애가 나서 Pod가 죽어도 스케줄러가 직접 개입하지 않는다(그 Pod가 ReplicaSet 소속이라면 컨트롤러가 새 Pod를 만들고, 그 새 Pod가 다시 스케줄러의 감시 대상이 될 뿐이다).
- **리소스 사용량을 실시간으로 강제하지 않는다.** 스케줄링 시점의 리소스 요청량(requests)을 기준으로 배치를 결정할 뿐, 실행 중 리소스 초과를 감시하고 대응하는 것은 kubelet과 커널의 몫이다.

스케줄링 프레임워크(Filter/Score/Bind, 확장점)는 4장에서 다룬다.

### kube-controller-manager

**책임**: 수십 개의 독립적인 컨트롤러(Deployment, ReplicaSet, Node, GC, ServiceAccount 등)를 하나의 프로세스 안에서 각각 별도 고루틴으로 구동한다. 각 컨트롤러는 1.1절의 조정 루프 패턴을 따른다.

**하지 않는 일**:
- **API 서버 기능을 대체하지 않는다.** 컨트롤러 매니저는 API 서버의 클라이언트일 뿐이다. 오브젝트를 읽고 쓸 때도 반드시 API 서버를 거친다. etcd에 직접 접근하지 않는다.
- **스케줄링을 하지 않는다.** ReplicaSet 컨트롤러는 "Pod가 몇 개 있어야 하는가"만 판단하고 Pod 오브젝트를 만든다. 그 Pod를 어느 노드에 놓을지는 스케줄러의 몫으로 넘긴다.
- **모든 컨트롤러가 서로 알지 못한다.** Deployment 컨트롤러는 ReplicaSet 컨트롤러의 존재를 모른다. 각자 자신이 감시하는 리소스 타입만 보고 독립적으로 조정한다. 연쇄 반응(Deployment → ReplicaSet → Pod)은 각 컨트롤러가 자신의 담당 범위 안에서 반응한 결과가 이어진 것이지, 하나의 통합된 로직이 아니다.

컨트롤러 패턴의 내부 구현(Informer, 워크큐, 리더 선출, GC)은 5장에서 다룬다.

### cloud-controller-manager

**책임**: 클라우드 제공자 API와의 연동만 전담한다. 노드 정보 보강(인스턴스 타입, 가용 영역 라벨), LoadBalancer 타입 Service에 대응하는 실제 클라우드 로드밸런서 생성, 클라우드 라우팅 테이블 설정.

**하지 않는 일**:
- **클라우드 제공자와 무관한 어떤 컨트롤러 로직도 갖지 않는다.** 이 컴포넌트가 분리된 이유 자체가 "클라우드 벤더 고유 코드를 쿠버네티스 본체에서 떼어내기 위함"이었다. 코드 구조상 core 컨트롤러 매니저와 확실히 분리되어 있다.
- **온프레미스/베어메탈 클러스터에는 존재하지 않을 수 있다.** 클라우드 프로바이더가 없는 kind 클러스터 같은 환경에서는 이 컴포넌트가 아예 배포되지 않거나 최소 기능만 수행한다.

## 1.3 노드 컴포넌트 지도

노드 컴포넌트는 클러스터의 "실행"을 담당한다. 컨트롤 플레인이 "무엇을 해야 하는가"를 결정하면, 노드 컴포넌트는 "그것을 실제로 일으키는" 역할이다.

```
┌──────────────────────────────────────────────────────────────┐
│                          워커 노드                              │
│                                                                │
│   kubelet         노드의 에이전트, Pod 생명주기의 총괄자           │
│     │                                                         │
│     ├─ CRI ──→ 컨테이너 런타임(containerd 등) — 컨테이너 실행    │
│     ├─ CNI ──→ 네트워크 플러그인 — Pod 네트워크 연결              │
│     ├─ CSI ──→ 스토리지 플러그인 — 볼륨 attach/mount             │
│     └─ 디바이스 플러그인 ──→ GPU 등 특수 하드웨어 노출              │
│                                                                │
│   kube-proxy      Service 가상 IP → Pod IP 변환 규칙 관리         │
└──────────────────────────────────────────────────────────────┘
```

### kubelet

**책임**: 해당 노드에 배정된 Pod 명세를 API 서버로부터 받아, 그 명세와 실제 실행 중인 컨테이너 상태를 지속적으로 비교하고 조정한다(1.1절의 조정 루프가 노드 수준에서 재현된 것). CRI를 통해 컨테이너 런타임에 지시를 내리고, 노드 및 Pod 상태를 다시 API 서버에 보고한다.

**하지 않는 일**:
- **컨테이너를 직접 실행하지 않는다.** 컨테이너를 생성·시작·중지하는 실제 작업은 CRI 인터페이스 너머의 컨테이너 런타임(containerd, CRI-O 등)이 수행한다. kubelet은 CRI gRPC 호출을 통해 요청만 보낸다.
- **Pod 간 네트워크를 직접 구성하지 않는다.** 네트워크 네임스페이스를 만든 뒤 CNI 플러그인을 호출해 실제 인터페이스 연결과 IP 할당을 위임한다.
- **Service 트래픽 라우팅에 관여하지 않는다.** 그것은 kube-proxy(또는 CNI 데이터플레인)의 몫이다.
- **다른 노드의 상태를 알지 못한다.** kubelet은 철저히 자기 노드 범위 안에서만 동작한다.

### kube-proxy

**책임**: API 서버가 watch로 전달하는 Service/EndpointSlice 정보를 바탕으로, 노드의 iptables/IPVS 규칙(또는 eBPF 프로그램)을 갱신해 ClusterIP로 향하는 트래픽이 실제 Pod로 전달되도록 한다.

**하지 않는 일**:
- **DNS 이름 해석을 하지 않는다.** `myservice.default.svc.cluster.local`을 IP로 바꾸는 것은 CoreDNS의 역할이다(16장). kube-proxy는 이미 IP로 향하는 패킷의 목적지를 바꿀 뿐이다.
- **L7 라우팅을 하지 않는다.** HTTP 경로 기반 라우팅, TLS 종료는 Ingress 컨트롤러나 서비스 메시의 몫이다(17장). kube-proxy는 L3/L4(IP/포트) 수준에서만 동작한다.
- **일부 CNI(예: Cilium의 eBPF 모드)에서는 아예 존재하지 않을 수 있다.** kube-proxy가 하던 일을 CNI 자체가 eBPF로 대체하는 구성이 늘고 있다(15장, 19장에서 상세히 다룬다).

### 컨테이너 런타임 (CRI)

**책임**: CRI(Container Runtime Interface) 규격을 구현하여, 실제 컨테이너 생성·이미지 pull·네임스페이스/cgroup 설정을 수행한다. containerd, CRI-O가 대표적이다.

**하지 않는 일**:
- **쿠버네티스 오브젝트(Pod, Deployment 등)를 전혀 알지 못한다.** CRI가 주고받는 것은 `PodSandbox`, `Container`, `Image` 같은 런타임 수준 개념이다. "이 컨테이너가 어느 Deployment 소속인가"는 런타임의 관심사가 아니다.
- **네트워크를 스스로 구성하지 않는다.** PodSandbox를 만들 때 네트워크 네임스페이스는 준비하지만, 그 안에 실제 인터페이스를 넣는 것은 CNI 플러그인 호출을 통해 이루어진다(런타임이 CNI를 호출하는 경우도, kubelet이 직접 호출하는 경우도 있다).

### CNI 플러그인

**책임**: Pod의 네트워크 네임스페이스에 인터페이스를 만들고 IP를 할당하며, 그 Pod가 클러스터 네트워크 모델의 요구사항(모든 Pod가 NAT 없이 서로 통신 가능해야 한다는 등, 13장에서 다룬다)을 만족하도록 라우팅/오버레이를 설정한다.

**하지 않는 일**:
- **Service 개념을 모른다.** 순수한 CNI 스펙은 Pod 대 Pod 네트워크 연결만 다룬다. ClusterIP 로드밸런싱은 CNI 스펙 밖의 일이며, kube-proxy나 CNI 벤더가 자체적으로 추가한 기능이다(단, Cilium 등 일부 CNI는 이 둘을 통합해서 제공한다).

### CSI 플러그인과 디바이스 플러그인 (개관)

**CSI(Container Storage Interface)**는 외부 스토리지 시스템의 볼륨을 Pod에 attach/mount하는 표준 인터페이스다. kubelet은 볼륨을 "어떻게" 붙일지 알 필요 없이, CSI 드라이버에게 attach/mount를 위임한다. **디바이스 플러그인**은 GPU, FPGA 같은 노드의 특수 하드웨어 자원을 kubelet에게 노출해, 스케줄러가 그 자원을 고려해 Pod를 배치할 수 있게 한다. 두 인터페이스 모두 이 책에서는 깊이 다루지 않지만, "kubelet이 모든 것을 직접 하지 않고 표준 인터페이스 뒤로 위임한다"는 설계 철학의 연장선에 있다는 점만 기억해 두자.

## 1.4 요청 하나의 전체 여정

이제 지도의 각 칸이 실제로 어떻게 연결되는지 하나의 시나리오로 추적한다. `kubectl apply -f deployment.yaml`로 3개 레플리카의 nginx Deployment를 만드는 순간부터 시작한다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels: { app: web }
  template:
    metadata:
      labels: { app: web }
    spec:
      containers:
        - name: nginx
          image: nginx:alpine
```

```
[kubectl]
   │ ① HTTP POST (인증서/토큰 첨부)
   ▼
[kube-apiserver]
   │ ② 인증 → 인가 → 어드미션 → 버전 변환 → 스키마 검증
   │ ③ etcd에 Deployment 오브젝트 기록
   ▼
[etcd] ── Raft 합의 → 커밋 완료 응답 ──▶ [kube-apiserver] ──▶ [kubectl] "created"

   (이 시점에서 apply 명령은 이미 반환된다. 아래는 비동기로 이어진다)

[kube-controller-manager] Deployment 컨트롤러
   │ ④ watch로 새 Deployment 오브젝트 감지
   │ ⑤ 조정: "ReplicaSet이 없다" → ReplicaSet 오브젝트 생성 요청
   ▼
[kube-apiserver] → [etcd]  (ReplicaSet 저장)

[kube-controller-manager] ReplicaSet 컨트롤러
   │ ⑥ watch로 새 ReplicaSet 감지
   │ ⑦ 조정: "Pod가 0개인데 3개여야 한다" → Pod 3개 생성 요청
   ▼
[kube-apiserver] → [etcd]  (Pod 3개 저장, 아직 spec.nodeName 없음)

[kube-scheduler]
   │ ⑧ watch로 "nodeName이 비어 있는 Pod" 3개 감지
   │ ⑨ 각 Pod에 대해 Filter(배치 불가능한 노드 제외) → Score(순위 매기기)
   │ ⑩ 최적 노드 선정 → Binding 오브젝트 생성 요청
   ▼
[kube-apiserver] → [etcd]  (Pod.spec.nodeName 갱신)

[kubelet] (배정된 노드에서 실행 중)
   │ ⑪ watch로 "내 노드에 배정된 새 Pod" 감지
   │ ⑫ PodSandbox 생성 요청 (CRI)
   ▼
[컨테이너 런타임] (containerd 등)
   │ ⑬ 네트워크 네임스페이스 생성
   ▼
[CNI 플러그인]
   │ ⑭ 인터페이스 생성, IP 할당, 라우팅 설정
   ▼
[컨테이너 런타임]
   │ ⑮ 이미지 pull → 컨테이너 프로세스 시작
   ▼
[kubelet]
   │ ⑯ 컨테이너 상태 확인(readiness/liveness) → Pod.status 갱신
   ▼
[kube-apiserver] → [etcd]  (Pod.status = Running)

[kube-controller-manager] EndpointSlice 컨트롤러 (Service가 있다면)
   │ ⑰ watch로 "Ready 상태가 된 Pod" 감지 → EndpointSlice 갱신
   ▼
[kube-proxy] (모든 노드에서)
   │ ⑱ watch로 EndpointSlice 변경 감지 → iptables/IPVS 규칙 갱신
```

이 여정에서 짚어야 할 점 세 가지가 있다.

**① 모든 화살표는 결국 API 서버를 거친다.** 스케줄러가 컨트롤러 매니저에 직접 말을 걸지 않는다. kubelet이 스케줄러의 결정을 직접 통보받지도 않는다. 모든 컴포넌트는 API 서버를 매개로 한 **watch/write**만으로 통신한다. 이것이 각 컴포넌트를 독립적으로 재시작·교체 가능하게 만드는 핵심 설계다.

**② `kubectl apply`가 반환되는 시점과 Pod가 실제로 Running이 되는 시점 사이에는 상당한 간극이 있다.** 이 간극 동안 최소 4개의 서로 다른 조정 루프(Deployment, ReplicaSet, Scheduler, kubelet)가 순차적으로 개입한다. 각 단계는 독립적으로 실패하고 독립적으로 재시도될 수 있다 — 이것이 1.1절에서 다룬 수렴성이 실전에서 어떻게 조합되는지 보여주는 예다.

**③ 이 여정 어디에도 "Deployment 전체를 이해하는 단일 컴포넌트"는 없다.** Deployment 컨트롤러는 ReplicaSet만 알고, ReplicaSet 컨트롤러는 Pod만 알고, 스케줄러는 배치만 알고, kubelet은 자기 노드의 컨테이너만 안다. 전체 그림은 이 좁은 책임들의 합성으로만 존재한다.

## 1.5 고가용성 구성에서 컴포넌트 배치

프로덕션 클러스터는 컨트롤 플레인을 단일 장애점으로 두지 않는다. 이 절은 개념만 짚고, 세부 메커니즘은 각 장에서 깊이 다룬다.

### 리더 선출 — 활성/대기 이중화

`kube-scheduler`와 `kube-controller-manager`는 여러 인스턴스(보통 3개)를 동시에 띄우되, **한 번에 하나만 활성(active)이고 나머지는 대기(standby)** 상태로 둔다. 활성 인스턴스가 죽으면 대기 인스턴스 중 하나가 Lease 오브젝트를 획득해 활성으로 전환된다.

```
kube-scheduler #1 (active)   ── Lease 보유 중, 15초마다 갱신
kube-scheduler #2 (standby)  ── Lease 감시 중
kube-scheduler #3 (standby)  ── Lease 감시 중
```

`kube-apiserver`는 다르다. 여러 인스턴스가 **모두 동시에 활성 상태로 요청을 처리한다**(active-active). API 서버는 자체적으로 상태를 갖지 않고 etcd에 위임하므로, 여러 인스턴스가 동시에 요청을 처리해도 충돌하지 않는다. 앞단에 로드밸런서를 두어 여러 API 서버 인스턴스에 트래픽을 분산한다. 리더 선출의 정확한 동작 방식(Lease, 낙관적 동시성 제어, 갱신 주기)은 5장에서 다룬다.

### etcd 클러스터 사이징과 쿼럼

etcd는 Raft 합의를 쓰므로, 클러스터를 구성하는 노드 수가 홀수여야 한다. 전체 노드 수를 N이라 하면 과반수(quorum)는 `(N/2)+1`이며, 클러스터는 `(N-1)/2`개 노드가 죽어도 살아남는다.

| 노드 수 | 쿼럼 | 허용 장애 수 |
|---|---|---|
| 1 | 1 | 0 |
| 3 | 2 | 1 |
| 5 | 3 | 2 |
| 7 | 4 | 3 |

**노드를 짝수로 늘리는 것은 무의미하다.** 4노드는 3노드보다 쓰기 지연이 늘어나는데 허용 장애 수는 여전히 1이다(쿼럼이 3으로 늘기 때문). 실무에서는 3노드 또는 5노드가 표준이다. 이 계산의 근거(Raft 합의 자체의 동작)는 3장에서 자세히 다룬다.

### stacked vs external etcd 토폴로지

컨트롤 플레인을 배치하는 방식은 크게 두 가지다.

```
[stacked etcd]                      [external etcd]
control-plane-1                     control-plane-1        etcd-1
  ├─ kube-apiserver                   ├─ kube-apiserver ───┐
  ├─ etcd                             ├─ kube-scheduler    │
  ├─ kube-scheduler                   └─ kube-ctrl-manager │
  └─ kube-ctrl-manager                                     │
                                     control-plane-2        etcd-2
control-plane-2                       ├─ kube-apiserver ───┤
  ├─ kube-apiserver                   ├─ kube-scheduler    │
  ├─ etcd                             └─ kube-ctrl-manager │
  ├─ kube-scheduler                                        │
  └─ kube-ctrl-manager                control-plane-3       etcd-3
                                       ├─ kube-apiserver ───┘
control-plane-3                       ├─ kube-scheduler
  ├─ etcd                             └─ kube-ctrl-manager
  ├─ kube-apiserver
  ├─ kube-scheduler
  └─ kube-ctrl-manager
```

**stacked**(적층형)는 etcd를 각 컨트롤 플레인 노드에 함께 배치한다. 구성이 단순하고 노드 수가 적게 든다. kubeadm의 기본 구성이며, 이 책이 전제하는 `kind` 클러스터도 이 방식이다.

**external**(분리형)은 etcd를 별도의 노드 집합으로 완전히 분리한다. 컨트롤 플레인 노드의 장애가 etcd 쿼럼에 영향을 주지 않으며, etcd에 더 특화된 하드웨어(빠른 로컬 디스크)를 독립적으로 할당할 수 있다. 대규모 프로덕션 환경에서 선호되는 방식이다.

두 방식 모두 "etcd 쿼럼이 유지되는 한 클러스터 상태는 안전하다"는 원칙은 동일하다. stacked 구성에서는 컨트롤 플레인 노드 장애가 곧 etcd 노드 장애이므로, 노드 수와 쿼럼 계산이 그대로 맞물린다는 점만 유의하면 된다.

## 1.6 이 책의 로드맵

여기까지가 1부의 출발점이다. 2장부터 6장까지는 이 절에서 그린 지도의 각 칸 — kube-apiserver, etcd, kube-scheduler, 컨트롤러 매니저, 그리고 노드 삼각편대(kubelet·런타임·kube-proxy) — 을 하나씩 소스 레벨 메커니즘까지 파고든다.

1부를 마치면 **2부(프레임워크)**로 넘어간다. 여기까지 배운 내부 동작 지식은 "쿠버네티스를 어떻게 확장하는가"를 이해하기 위한 토대다. 7장(확장 지점 지도)이 그 전체 그림을 열고, client-go, CRD, 오퍼레이터, 어드미션 웹훅, 커스텀 스케줄러/API 서버까지 이어진다.

**3부(네트워크)**는 1부에서 개관만 했던 CNI·kube-proxy·서비스 디스커버리를 프로토콜과 데이터플레인 수준으로 완전히 해부한다. 13장(네트워킹 모델과 CNI 스펙)이 그 시작점이며, Service·EndpointSlice·kube-proxy 내부·DNS·Ingress/메시·NetworkPolicy·eBPF 데이터플레인까지 이어진다.

세 부 모두 결국 이 1장에서 그린 지도 위의 화살표들을 확대경으로 들여다보는 작업이라는 점을 기억하면, 어느 장에서 길을 잃어도 다시 여기로 돌아와 위치를 확인할 수 있다.

## 실습: 컴포넌트 실체 확인하기

이 실습은 `kind`로 만든 3노드 클러스터(`k8s-guide`, 컨트롤 플레인 노드명 `k8s-guide-control-plane`)를 전제로 한다.

**① 컨트롤 플레인 컴포넌트 상태 확인**

```bash
kubectl get componentstatuses
```

`ComponentStatus`는 레거시 API로 최신 버전에서는 사용을 권장하지 않는다. 대신 각 컴포넌트의 헬스 엔드포인트를 직접 조회한다.

```bash
kubectl get --raw /healthz
kubectl get --raw /readyz?verbose
```

**② static Pod로 실행 중인 컨트롤 플레인 컴포넌트 확인**

kubeadm 기반 클러스터에서 컨트롤 플레인 컴포넌트는 kubelet이 직접 관리하는 static Pod로 실행된다.

```bash
kubectl get pods -n kube-system -o wide | grep k8s-guide-control-plane
```

```
etcd-k8s-guide-control-plane                      1/1   Running
kube-apiserver-k8s-guide-control-plane             1/1   Running
kube-controller-manager-k8s-guide-control-plane    1/1   Running
kube-scheduler-k8s-guide-control-plane             1/1   Running
```

static Pod의 정의 파일은 노드의 파일시스템에 직접 존재한다.

```bash
docker exec k8s-guide-control-plane ls /etc/kubernetes/manifests/
```

```
etcd.yaml
kube-apiserver.yaml
kube-controller-manager.yaml
kube-scheduler.yaml
```

**③ 노드에서 크리(CRI) 레벨로 컨테이너 확인**

kubelet이 아니라 컨테이너 런타임의 시각에서 같은 컴포넌트를 확인한다.

```bash
docker exec k8s-guide-control-plane crictl ps --name kube-apiserver
docker exec k8s-guide-control-plane crictl ps --name etcd
```

`kubectl get pods`는 API 서버를 거친 시각이고, `crictl ps`는 그 노드의 런타임이 실제로 관리 중인 컨테이너의 시각이다. 두 관점이 늘 일치해야 정상이다.

**④ 각 컴포넌트의 헬스 엔드포인트 직접 호출**

```bash
# API 서버 (kubectl 자체가 이미 이 엔드포인트를 거친다)
kubectl get --raw /livez

# etcd 헬스 확인 (컨트롤 플레인 노드 내부에서)
docker exec k8s-guide-control-plane sh -c \
  "ETCDCTL_API=3 etcdctl --cacert=/etc/kubernetes/pki/etcd/ca.crt \
   --cert=/etc/kubernetes/pki/etcd/server.crt \
   --key=/etc/kubernetes/pki/etcd/server.key \
   endpoint health"

# kubelet의 헬스 엔드포인트 (각 노드에서 10248 포트)
docker exec k8s-guide-control-plane curl -sk http://localhost:10248/healthz
```

**⑤ 노드 컴포넌트를 워커 노드에서 확인**

```bash
kubectl get nodes
docker exec k8s-guide-worker crictl ps
docker exec k8s-guide-worker ps aux | grep -E 'kubelet|kube-proxy'
```

kube-proxy는 워커 노드에서 DaemonSet Pod로 실행되므로 static Pod가 아니라 일반 Pod로 조회된다.

```bash
kubectl get pods -n kube-system -o wide | grep kube-proxy
```

## 실습 과제

**과제 1 — 컴포넌트 경계 확인**
`kubectl get pods -n kube-system`으로 컨트롤 플레인·노드 컴포넌트 전체 목록을 뽑고, 각각이 1.2절/1.3절의 어느 컴포넌트에 해당하는지, static Pod인지 DaemonSet Pod인지 분류표를 만들어 본다.

**과제 2 — 조정 루프 관찰**
`kubectl scale deployment <name> --replicas=5`를 실행한 직후 `kubectl get pods -w`로 Pod가 하나씩 늘어나는 과정을 관찰한다. 모든 Pod가 동시에 생기지 않는 이유를 1.4절의 여정과 연결해 설명해 본다.

**과제 3 — 컴포넌트 재시작 실험**
`docker exec k8s-guide-control-plane crictl stop <kube-scheduler 컨테이너ID>`로 스케줄러를 잠시 중지시키고, 그 사이 새 Pod를 만들어 `Pending` 상태로 머무는 것을 확인한다. 스케줄러를 되살리면(static Pod이므로 kubelet이 자동 재기동한다) 대기 중이던 Pod가 즉시 배치되는 것을 관찰한다.

**과제 4 — etcd 단일 장애점 확인**
`kind` 클러스터가 컨트롤 플레인 노드 1개(stacked etcd, 단일 노드)로 구성되어 있다면, 이 구성에서 etcd 노드 장애가 곧 전체 클러스터 장애로 이어지는 이유를 1.5절의 쿼럼 계산으로 설명해 본다.

**과제 5 — 헬스 엔드포인트 비교**
`/livez`, `/readyz`, `/healthz` 세 엔드포인트를 각각 `?verbose`를 붙여 호출하고 출력 차이를 비교한다. 이 차이가 왜 존재하는지(재시작 판단 vs 트래픽 수신 판단) 정리해 본다.

## 요약

- 쿠버네티스의 신뢰성은 **선언적 상태 + 레벨 트리거 + 멱등한 조정 함수**의 조합에서 나온다. 이벤트를 놓쳐도 다음 조정에서 현재 상태를 다시 관찰해 교정하기 때문에 유한 스텝 안에 목표 상태로 수렴한다.
- 컨트롤 플레인 다섯 컴포넌트(**kube-apiserver, etcd, kube-scheduler, kube-controller-manager, cloud-controller-manager**)는 각각 좁은 책임만 진다. API 서버는 스케줄링도 조정도 하지 않고, 스케줄러는 배치 결정만 내리고 실행하지 않으며, 컨트롤러 매니저는 조정만 하고 배치·실행에 관여하지 않는다.
- 노드 컴포넌트(**kubelet, kube-proxy, 컨테이너 런타임, CNI, CSI/디바이스 플러그인**)도 마찬가지로 각자의 인터페이스(CRI/CNI/CSI) 뒤에 명확히 분리되어 있다. kubelet은 컨테이너를 직접 실행하지 않고 런타임에 위임하며, 네트워크를 직접 구성하지 않고 CNI에 위임한다.
- **모든 컴포넌트 간 통신은 API 서버를 거친다.** 컴포넌트끼리 직접 통신하지 않고, watch와 write만으로 느슨하게 결합되어 있다는 점이 각 컴포넌트를 독립적으로 재시작·교체할 수 있게 하는 근본 이유다.
- `kubectl apply` 한 번은 최소 네 개의 독립적인 조정 루프(Deployment → ReplicaSet → 스케줄러 → kubelet)를 순차적으로 거쳐야 실제 컨테이너 실행에 도달한다.
- 고가용성 구성에서 **kube-scheduler/kube-controller-manager**는 리더 선출로 active-standby를 이루고, **kube-apiserver**는 active-active로 동작하며, **etcd**는 Raft 쿼럼(`(N/2)+1`)으로 장애를 흡수한다. 배치는 stacked(단순) 또는 external(분리, 대규모 환경 선호) 토폴로지 중 하나를 택한다.

**다음 장에서는** 이 지도의 첫 번째 칸, 모든 요청의 유일한 관문인 kube-apiserver 내부로 들어간다. 필터 체인부터 버전 변환, 어그리게이션, watch cache, API 우선순위·공정성까지 — 이 책의 "내부 동작" 축을 여는 기술적 닻이 되는 장이다.
