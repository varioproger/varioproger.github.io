# 50장. 병렬 프로그래밍

> **이 장의 위치** — Part IX「동시성과 비동기」의 여섯 번째 장이다. 45장부터 49장까지는 스레드·태스크·동기화·신호라는 **원자재**를 다뤘다. 이 장은 그 위에 얹힌 **구조화된 병렬성(structured parallelism)** — 작업을 쪼개고, 여러 코어에 뿌리고, 결과를 다시 모으는 일을 라이브러리에 맡기는 층 — 을 다룬다. 46장에서 "`Task`는 있지만 작업을 어떻게 나눌지는 네 몫"이라고 남겨 둔 부분, 48장에서 "잠금을 잘 거는 것보다 잠금이 필요 없게 설계하라"고만 말한 부분이 여기서 구체적인 API로 채워진다.
>
> **선수 지식** — 45장(스레드의 기초), 46장(스레드 풀과 태스크), 48장(동기화와 잠금), 29장(LINQ 쿼리), 24장(컬렉션)
>
> **이 장에서 다루지 않는 것** — LINQ 쿼리 구문과 개별 연산자의 의미론은 29장과 30장에서 이미 끝냈다. `Task`의 생성·합성·취소 프로토콜과 `TaskScheduler`·`TaskFactory`는 46장, `async`/`await`의 상태 기계는 47장, `lock`·`Interlocked`·`SpinLock`·메모리 모델은 48장, `Barrier`와 스레드 로컬 저장소는 49장에 있다. `AggregateException`의 API 자체(`Flatten`·`Handle`·`GetBaseException`)는 32.13절에서 전수했으므로 여기서는 **병렬 맥락에서만** 다시 짚는다. `System.Threading.Channels.Channel<T>`는 51.1절, 캐시 계층의 하드웨어 원리는 61.4절, BenchmarkDotNet 사용법은 67.3절이다.

## 50.1 동시성 vs 병렬성 — 용어 정리

### 두 단어는 같은 뜻이 아니다

실무에서 가장 흔하게 뒤섞이는 두 단어부터 갈라 놓자.

- **동시성(concurrency)** 은 **여러 일을 다루는 구조**에 관한 말이다. 진행 중인 작업이 여럿이면 동시성이 있다. 코어가 하나뿐이어도 성립한다. 스케줄러가 작업 사이를 오가며 조금씩 진척시키면 관찰자에게는 여러 일이 함께 진행되는 것처럼 보인다.
- **병렬성(parallelism)** 은 **여러 일을 물리적으로 같은 순간에 실행하는 것**에 관한 말이다. 코어가 둘 이상이어야 성립한다.

동시성은 **설계 속성**이고 병렬성은 **실행 속성**이다. 동시적으로 설계된 프로그램은 코어가 늘어나면 병렬로 실행될 수 있지만, 동시성 없이 병렬성만 얻을 수는 없다.

```text
  단일 코어에서의 동시성 (인터리빙)
  Core 0: [A₁][B₁][A₂][C₁][B₂][A₃][C₂][B₃]  ─── 시간 →
          A, B, C 셋이 "진행 중"이지만 어느 순간에도 하나만 실행된다

  멀티코어에서의 병렬성
  Core 0: [A₁][A₂][A₃][A₄]  ─── 시간 →
  Core 1: [B₁][B₂][B₃][B₄]
  Core 2: [C₁][C₂][C₃][C₄]
          같은 순간에 셋이 실제로 돈다
```

45.2절에서 본 스레드는 동시성의 **메커니즘**이지 병렬성의 보장이 아니다. 스레드 100개를 만들어도 코어가 하나면 병렬 실행량은 1이다.

| 축 | 동시성 | 병렬성 | 비동기 |
|---|---|---|---|
| **묻는 질문** | 여러 일을 어떻게 **다루는가** | 여러 일을 어떻게 **동시에 실행하는가** | 기다리는 동안 스레드를 어떻게 **놓아주는가** |
| **필요 하드웨어** | 코어 1개로 충분 | 코어 2개 이상 | 코어 1개로 충분 |
| **주 목적** | 구조·응답성 | 처리량(throughput)·지연 시간 단축 | 자원 효율(스레드 절약) |
| **대표 도구** | 스레드, 태스크, 이벤트 루프 | PLINQ, `Parallel` (이 장) | `async`/`await` (47장) |
| **바운드 유형** | 무관 | **CPU 바운드** | **I/O 바운드** |

> **⚠️ `async`/`await`는 병렬화 도구가 아니다**
>
> 47.2절에서 본 것처럼 `async`/`await`의 본질은 "대기하는 동안 스레드를 반납하는 것"이다. CPU가 실제로 계산해야 하는 100밀리초는 `await`를 붙인다고 줄지 않는다. 반대로 `Parallel.For`는 CPU 계산을 여러 코어에 뿌리지만, 네트워크 응답을 기다리는 시간은 전혀 줄이지 못하면서 스레드만 붙들고 있는다.
>
> **CPU 바운드 병목에는 이 장을, I/O 바운드 병목에는 47장을 펴라.** 둘을 바꿔 쓰면 성능은 나아지지 않고 자원만 낭비된다. 두 성격이 섞여 있다면 50.7절의 `Parallel.ForEachAsync`가 정답인 경우가 많다.

### 데이터 병렬성과 태스크 병렬성

작업을 스레드에 나누는 전략은 크게 둘이다.

**데이터 병렬성(data parallelism)** — 많은 데이터 값에 같은 작업 집합을 수행해야 할 때, 각 스레드가 값의 부분집합에 대해 **같은 작업**을 수행하도록 병렬화한다. 데이터를 스레드 사이에 나누므로 데이터 병렬성이다.

**태스크 병렬성(task parallelism)** — 태스크 자체를 나눈다. 각 스레드가 **서로 다른 작업**을 수행한다.

일반적으로 데이터 병렬성이 더 쉽고 고도로 병렬적인 하드웨어에 더 잘 확장된다. 공유 데이터를 줄이거나 없애기 때문에 경합과 스레드 안전성 문제가 줄어들고, 보통 별개의 태스크보다 데이터 값이 훨씬 많아서 병렬화 잠재력이 커진다.

데이터 병렬성은 **구조적 병렬성(structured parallelism)** 에도 잘 맞는다. 병렬 작업 단위가 프로그램의 같은 지점에서 시작하고 끝난다는 뜻이다. 반면 태스크 병렬성은 비구조적인 경향이 있어서, 병렬 작업 단위가 프로그램 여기저기 흩어진 곳에서 시작하고 끝난다. 구조적 병렬성이 더 단순하고 오류가 적으며, 파티셔닝·스레드 조율·결과 병합이라는 어려운 일을 라이브러리에 위임할 수 있다.

| 구분 | 데이터 병렬성 | 태스크 병렬성 |
|---|---|---|
| 나누는 대상 | 데이터 | 작업 |
| 각 스레드가 하는 일 | 같은 일, 다른 데이터 | 다른 일 |
| 공유 상태 | 적거나 없음 | 많은 경향 |
| 구조 | 구조적 | 비구조적 |
| 코어 수 확장성 | 좋음 | 태스크 개수에 묶임 |
| 대표 API | PLINQ(50.3절), `Parallel.For`/`ForEach`(50.6절) | `Parallel.Invoke`(50.6절), `Task`(50.8절) |

> **📌 "당황스러울 만큼 병렬적인" 문제**
>
> 가장 쉬운 이득은 **embarrassingly parallel** 문제에서 나온다. 작업을 각자 독립적으로 효율적으로 실행되는 태스크로 쉽게 나눌 수 있는 경우다. 이미지 처리, 광선 추적(ray tracing), 수학이나 암호학의 무차별 대입 접근이 대표적이다.
>
> 반례는 최적화된 퀵정렬 구현이다. 좋은 결과를 얻으려면 생각이 필요하고 비구조적 병렬성이 필요할 수 있다(50.8절).

### 암달의 법칙 — 왜 코어를 늘려도 한계가 있는가

병렬 프로그래밍의 첫 번째 벽은 **암달의 법칙(Amdahl's law)** 이다. 병렬화로 얻을 수 있는 최대 성능 개선은 **순차적으로 실행되어야 하는 코드의 비율**이 지배한다.

알고리즘 실행 시간의 3분의 2만 병렬화 가능하다면, 코어가 무한히 많아도 **3배를 넘는 이득은 결코 얻을 수 없다.**

직렬 비율을 `α`, 코어 수를 `N`이라 할 때 최대 배속은 다음과 같다.

```text
             1
S(N) = ───────────────
        α + (1 - α)/N

  N → ∞ 이면  S → 1/α
```

| 직렬 비율 α | 코어 4개 | 코어 16개 | 코어 64개 | 코어 무한 |
|---|---|---|---|---|
| 0% | 4.00× | 16.00× | 64.00× | ∞ |
| 5% | 3.48× | 9.14× | 15.42× | 20.00× |
| 10% | 3.08× | 6.40× | 8.77× | 10.00× |
| 25% | 2.29× | 3.37× | 3.82× | 4.00× |
| 50% | 1.60× | 1.88× | 1.97× | 2.00× |

(표의 값은 위 공식으로 계산한 이론값이다. 실제로는 조정 비용이 더해져 이보다 낮다.)

이 표가 주는 실무적 교훈은 하나다. **병렬화에 손대기 전에 병목이 병렬화 가능한 코드 안에 있는지부터 확인하라.** 그리고 애초에 그 코드가 계산 집약적일 필요가 있는지 따져 보라 — 최적화가 종종 가장 쉽고 효과적인 접근이다. 다만 절충이 있다. 어떤 최적화 기법은 코드를 병렬화하기 더 어렵게 만든다.

### 구스타프슨의 법칙 — 반대편에서 본 같은 현실

암달의 법칙은 **문제 크기가 고정되어 있다**고 가정한다. 현실의 서버·과학 계산은 종종 다르다. 코어가 늘면 사람들은 같은 문제를 더 빨리 푸는 대신 **더 큰 문제**를 푼다. 이 관점을 정식화한 것이 **구스타프슨의 법칙(Gustafson's law)** 이다.

병렬 실행 시간을 기준으로 놓고, 그중 직렬 부분의 비율을 `α`라 하면 확장된 배속은 다음과 같다.

```text
S(N) = N - α·(N - 1)
```

같은 α = 5%, N = 64에서 암달은 15.42배를 말하지만 구스타프슨은 60.85배를 말한다. 모순이 아니다. **두 법칙은 다른 질문에 답한다.**

| | 암달의 법칙 | 구스타프슨의 법칙 |
|---|---|---|
| 고정하는 것 | 문제 크기 | 실행 시간 |
| 묻는 것 | "같은 일을 얼마나 빨리?" | "같은 시간에 얼마나 많이?" |
| 결론 | 직렬 부분이 상한을 정한다 | 문제를 키우면 확장된다 |
| 맞는 상황 | 지연 시간(latency) 최적화 | 처리량(throughput) 최적화 |

> **💡 어느 법칙을 볼지는 요구사항이 정한다**
>
> "이 보고서 생성이 30초 걸리는데 5초로 줄이고 싶다"는 암달의 세계다. 직렬 구간을 찾아 없애지 않으면 코어를 아무리 늘려도 목표에 못 간다.
>
> "동시 요청을 지금의 4배로 받고 싶다"는 구스타프슨의 세계다. 요청마다 독립적이므로 코어를 늘리면 거의 선형으로 확장된다 — **단, 요청들이 공유 자원(DB 커넥션, 잠금, 메모리 대역폭)에서 만나지 않는 한.**

### "병렬화하면 항상 빨라진다"는 오해

이 오해가 이 장에서 가장 비싼 오해다. 병렬화에는 최소한 세 가지 비용이 붙는다.

**1. 조정 비용(coordination cost).** 태스크를 만들고, 스레드 풀에 큐잉하고, 델리게이트를 호출하고, 완료를 기다리고, 예외를 취합한다. 작업 항목이 몇 개뿐이거나 항목당 처리가 아주 빠르면 이 비용이 이득을 삼킨다. 델리게이트 객체가 할당되어야 하고 그 델리게이트가 **작업 항목마다 한 번씩** 호출된다.

**2. 파티셔닝 비용(partitioning cost).** 입력을 나누는 일 자체가 공짜가 아니다. 해시 파티셔닝(50.3절)은 모든 원소의 해시 코드를 미리 계산한다. 청크 파티셔닝은 공유 입력 시퀀스에서 원소를 꺼낼 때마다 잠금을 잡는다.

**3. 메모리 대역폭 한계.** 코어를 늘려도 메모리 버스는 하나다. 계산 밀도가 낮고 메모리를 많이 훑는 작업(예: 큰 배열 합계)은 코어 2~4개 지점에서 대역폭에 막혀 더 이상 빨라지지 않는다. 여기에 거짓 공유(50.12절)까지 겹치면 **코어를 늘릴수록 느려지는** 그래프가 나온다.

원천 자료의 벤치마크가 이 점을 그대로 보여 준다. 배열의 원소를 콘솔에 출력하는 루프를 `foreach`와 `Parallel.ForEach`로 각각 측정했더니 **평범한 `foreach`가 더 빨랐다.** 반대로 여러 URL을 내려받는 작업에서는 병렬 버전이 훨씬 빨랐다.

> **⚠️ `Console.WriteLine`을 병렬 루프 본문에 넣지 마라**
>
> `Console` 클래스는 내부적으로 스레드를 동기화해서 한 번에 하나만 콘솔 창에 접근하게 한다. 여러 스레드의 텍스트가 뒤섞여 읽을 수 없게 되는 것을 막기 위해서다.
>
> 그래서 병렬 루프 본문이 `Console.WriteLine`뿐이면 **모든 스레드가 그 잠금 하나에 줄을 선다.** 병렬화 이득은 0이고 조정 비용만 남는다. 위 벤치마크에서 `foreach`가 이긴 이유가 정확히 이것이다. 병렬 코드를 측정할 때 본문에 로그 출력을 넣으면 측정 자체가 무의미해진다.

> **💡 병렬화 전에 던져야 할 네 가지 질문**
>
> 1. **병목이 정말 여기인가?** 프로파일러로 확인했는가(67.6절), 아니면 짐작인가.
> 2. **CPU 바운드인가?** 스레드가 계산 중인가, 아니면 무언가를 기다리는 중인가.
> 3. **항목당 작업이 충분히 큰가?** 마이크로초 단위 미만이면 조정 비용이 이긴다.
> 4. **항목들이 독립적인가?** 공유 상태를 잠금으로 보호해야 한다면 병렬화 잠재력은 그 잠금이 정한다.
>
> 네 질문에 모두 "그렇다"가 나오지 않으면, 병렬화보다 알고리즘 개선·할당 제거(69장)·자료구조 교체(72.6절)가 먼저다.

## 50.2 PFX 개념과 구성 요소, 언제 쓰는가

### PFX라는 이름

멀티코어 프로세서를 활용하기 위한 .NET의 멀티스레딩 API와 구조를 통틀어 느슨하게 **PFX(Parallel Framework)** 라고 부른다. 그 안에서 `Parallel` 클래스와 태스크 병렬성 구조를 묶어 **TPL(Task Parallel Library, 태스크 병렬 라이브러리)** 이라고 부른다.

PFX는 두 계층으로 되어 있다.

```text
┌─────────────────────────────────────────────────────────┐
│  상위 계층 — 구조적 데이터 병렬성                        │
│                                                          │
│   ┌────────────────┐        ┌──────────────────────┐    │
│   │  PLINQ         │        │  Parallel 클래스     │    │
│   │  (선언적)      │        │  (명령형)            │    │
│   │  50.3~50.5절   │        │  50.6~50.7절         │    │
│   └────────────────┘        └──────────────────────┘    │
└─────────────────────────────────────────────────────────┘
                          ↓ 위에서 아래를 쓴다
┌─────────────────────────────────────────────────────────┐
│  하위 계층 — 태스크 병렬성과 보조 구조                   │
│                                                          │
│   ┌──────────────┐ ┌───────────────┐ ┌───────────────┐  │
│   │ Task /       │ │ 동시성 컬렉션 │ │ SpinLock /    │  │
│   │ TaskFactory /│ │ 50.10~50.11절 │ │ SpinWait      │  │
│   │ TaskScheduler│ │               │ │ (48.12절)     │  │
│   │ 46장, 50.8절 │ │               │ │               │  │
│   └──────────────┘ └───────────────┘ └───────────────┘  │
└─────────────────────────────────────────────────────────┘
```

상위 계층의 두 API는 성격이 다르다. PLINQ는 **선언적(declarative)** 이다 — 병렬화하고 싶다고 선언하기만 하면(작업을 LINQ 쿼리로 구조화한 뒤) 런타임이 구현 세부를 처리한다. 나머지는 **명령형(imperative)** 이다 — 나누거나 모으는 코드를 직접 써야 한다.

| API | 작업을 나눠 주는가 | 결과를 모아 주는가 |
|---|---|---|
| PLINQ | **예** | **예** |
| `Parallel` 클래스 | **예** | 아니오 |
| PFX의 태스크 병렬성 | 아니오 | 아니오 |

동시성 컬렉션과 스피닝 프리미티브는 더 낮은 수준의 병렬 프로그래밍 활동을 돕는다. 이들이 중요한 이유는 PFX가 오늘의 하드웨어뿐 아니라 **훨씬 많은 코어를 가진 미래 세대의 프로세서**까지 염두에 두고 설계되었기 때문이다.

> **📌 장작 더미 비유**
>
> 잘라 놓은 장작 더미를 옮겨야 하고 일꾼이 32명 있다고 하자. 가장 큰 문제는 장작을 옮기는 일 자체가 아니라 **일꾼들이 서로 방해하지 않게 하는 것**이다. 알고리즘을 32개 코어에 나누는 일도 똑같다. 공통 자원을 평범한 잠금으로 보호하면, 그로 인한 블로킹 때문에 그 코어들 중 일부만 실제로 바쁠 수 있다.
>
> 동시성 컬렉션은 고도의 동시 접근에 맞춰 튜닝되어 있고, 블로킹을 최소화하거나 제거하는 데 초점이 있다. PLINQ와 `Parallel` 클래스 자체도 작업을 효율적으로 관리하기 위해 동시성 컬렉션과 스피닝 프리미티브에 의존한다.

### PFX의 다른 용도

병렬 프로그래밍 구조는 멀티코어 활용 말고도 쓰인다.

- **동시성 컬렉션**은 그냥 스레드 안전한 큐·스택·딕셔너리가 필요할 때 적절할 수 있다.
- **`BlockingCollection`** 은 프로듀서/컨슈머 구조를 구현하는 쉬운 수단이자 **동시성을 제한하는** 좋은 방법이다.
- **`Task`** 는 46장에서 본 것처럼 비동기 프로그래밍의 기반이다.

### 언제 PFX를 쓰는가

PFX의 주 사용 사례는 하나다. **계산 집약적 코드를 멀티코어 프로세서로 빠르게 만드는 것.**

세 조건이 모두 성립해야 이득이 난다.

**1. CPU 바운드여야 한다.** 스레드가 계산 중이어야지 무언가를 기다리는 중이면 안 된다.

**2. 작업 단위가 충분히 커야 한다.** PLINQ가 유용하려면 워커 스레드에 넘길 만한 **합리적인 양의 계산 집약적 작업**이 있어야 한다. 대부분의 LINQ to Objects 쿼리는 아주 빨리 실행되므로 병렬화가 불필요할 뿐 아니라, 파티셔닝·병합·추가 스레드 조율의 오버헤드가 오히려 느리게 만들 수 있다.

**3. 항목이 독립적이어야 한다.** 병렬 메서드를 호출할 때는 **작업 항목이 동시에 수행되어도 괜찮다는 가정**이 깔려 있다. 순차 순서로 처리되어야 하는 작업에는 쓰지 마라. 공유 데이터를 수정하는 작업 항목도 피하라 — 여러 스레드가 동시에 조작하면 데이터가 깨질 수 있다. 보통은 데이터 접근 주위에 동기화 잠금을 추가해 고치지만, 그러면 한 번에 한 스레드만 접근하므로 **여러 항목을 병렬로 처리하는 이득을 잃는다.**

> **💡 항목당 몇 마이크로초부터 이득인가**
>
> 정확한 손익분기점은 하드웨어·JIT·본문 내용에 따라 달라지므로 숫자를 외울 것이 아니라 측정해야 한다. 다만 실무적 감각으로는 **항목당 작업이 수십 마이크로초 미만이면 병렬화를 의심하고, 밀리초 단위면 대체로 이득**이라고 생각하면 크게 틀리지 않는다.
>
> 항목당 작업이 작은데 항목 수가 아주 많다면, 항목을 **묶어서**(50.6절의 `Partitioner.Create(from, to, rangeSize)`) 작업 단위를 인위적으로 키우는 것이 정답이다. 항목을 그대로 두고 병렬도만 올리면 델리게이트 호출 비용만 늘어난다.

> **⚠️ I/O 바운드 작업에 `Parallel.For`를 쓰면 안 되는 이유**
>
> `Parallel.*` 메서드와 PLINQ는 **컴퓨트 바운드에 최적화되어 있지 I/O 바운드에 최적화되어 있지 않다.** 그런데도 이 실수가 흔한 이유는, 동기 I/O를 `Parallel.ForEach`로 감싸면 실제로 "빨라 보이기" 때문이다.
>
> 무슨 일이 벌어지는지 보자. 워커가 동기 I/O에서 블로킹되면 그 스레드는 **아무 일도 안 하면서 스레드 풀 슬롯을 점유한다.** 스레드 풀은 큐가 밀리는 것을 보고 hill-climbing 알고리즘에 따라 스레드를 더 주입하는데(46.2절), 주입 속도는 초당 한두 개 수준이다. 그동안 애플리케이션의 다른 모든 스레드 풀 작업 — ASP.NET 요청 처리, 타이머 콜백, `Task` 연속 — 이 굶는다. 이것이 스레드 풀 기아(starvation)다.
>
> 특히 PLINQ는 **`Task`와 달리 스레드를 블로킹하지 않고는 I/O 바운드 작업을 수행할 수 없다.** 그것도 하필 풀 스레드를 블로킹한다.
>
> 정답은 셋 중 하나다. **`Parallel.ForEachAsync`**(50.7절), **`SemaphoreSlim`으로 동시성을 제한한 `Task.WhenAll`**(48.11절), 또는 **`Channel`** 기반 파이프라인(51.1절). 셋 다 블로킹 없이 동시 실행 개수를 제어한다.

> **📌 PLINQ는 로컬 컬렉션 전용이다**
>
> PLINQ는 로컬 컬렉션에만 동작한다. 예를 들어 Entity Framework에는 쓸 수 없다 — 그 경우 LINQ가 SQL로 번역되어 데이터베이스 서버에서 실행되기 때문이다. 다만 데이터베이스 쿼리로 얻은 결과 집합에 대해 **추가적인 로컬 쿼리**를 PLINQ로 수행하는 것은 가능하다. 식 트리와 `IQueryable<T>`의 동작은 31장에 있다.

## 50.3 PLINQ — 병렬 실행 원리, 순서, 한계

### 문법 — `AsParallel()` 하나

PLINQ는 로컬 LINQ 쿼리를 자동으로 병렬화한다. 작업 파티셔닝과 결과 병합의 부담을 모두 .NET에 넘긴다는 점에서 쓰기 쉽다.

쓰는 법은 입력 시퀀스에 `AsParallel()`을 호출하고 나머지는 평소대로 쓰는 것이 전부다. 다음 쿼리는 3부터 100,000 사이의 소수를 계산하며 대상 머신의 모든 코어를 사용한다.

```csharp
// 단순한(최적화되지 않은) 알고리즘으로 소수를 계산한다.
IEnumerable<int> numbers = Enumerable.Range (3, 100000 - 3);

var parallelQuery =
    from n in numbers.AsParallel()
    where Enumerable.Range (2, (int) Math.Sqrt (n)).All (i => n % i > 0)
    select n;

int[] primes = parallelQuery.ToArray();
```

### 컴파일 결과 — 확장 메서드 바인딩이 바뀐다

`AsParallel`이 하는 일을 정확히 말하면 이렇다. `AsParallel`은 `System.Linq.ParallelEnumerable`에 정의된 확장 메서드로, 입력을 `ParallelQuery<TSource>` 기반 시퀀스로 감싼다. 그 결과 **뒤이어 호출하는 LINQ 쿼리 연산자들이 `ParallelEnumerable`에 정의된 다른 확장 메서드 집합에 바인딩된다.** 이 메서드들이 표준 쿼리 연산자 각각의 병렬 구현을 제공한다.

```csharp
namespace System.Linq
{
    public static class ParallelEnumerable
    {
        public static ParallelQuery<TSource> AsParallel<TSource> (
            this IEnumerable<TSource> source);

        public static ParallelQuery AsParallel (this IEnumerable source);

        // Where, Select, SelectMany, GroupBy, Join, OrderBy, Skip, Take ...
        // 표준 연산자의 병렬 버전이 전부 여기 있다
    }
}
```

핵심은 **컴파일 시점에 오버로드 해석이 달라진다**는 것이다. 런타임에 "이 쿼리를 병렬로 돌릴까?"를 판단하는 마법이 있는 것이 아니라, `AsParallel()`이 반환하는 정적 타입이 `ParallelQuery<T>`이기 때문에 C# 컴파일러가 `Enumerable.Where` 대신 `ParallelEnumerable.Where`를 고른다. IL을 열어 보면 그냥 다른 정적 메서드 호출일 뿐이다.

```csharp
IEnumerable<int> src = ...;

var a = src.Where (x => x > 0);                 // Enumerable.Where  → IEnumerable<int>
var b = src.AsParallel().Where (x => x > 0);    // ParallelEnumerable.Where → ParallelQuery<int>
```

`ParallelQuery<T>`는 `IEnumerable<T>`를 구현하므로 `foreach`로 열거하거나 `IEnumerable<T>`를 받는 API에 넘길 수 있다. 다만 **`IEnumerable<T>` 타입 변수에 담는 순간 이후 연산자는 다시 순차 버전에 바인딩된다.**

```csharp
IEnumerable<int> q = src.AsParallel().Where (x => x > 0);   // 여기까지는 병렬
var r = q.Select (x => x * 2);                              // ⚠ 순차 Select 에 바인딩됨
```

> **⚠️ `var`를 버리면 병렬성이 조용히 사라진다**
>
> 위 예제처럼 중간 결과를 `IEnumerable<T>`로 선언하면 컴파일 오류도 경고도 나지 않고 **뒤쪽 연산자만 순차로 돌아간다.** 성능은 떨어지지만 결과는 맞으므로 발견이 늦다.
>
> 반대 방향의 실수도 있다. 이미 `ParallelQuery<T>`인 시퀀스에 `AsParallel()`을 다시 부르는 것이다.
>
> ```csharp
> mySequence.AsParallel()       // 시퀀스를 ParallelQuery<int>로 감싼다
>           .Where (n => n > 100)   // 또 다른 ParallelQuery<int>를 출력한다
>           .AsParallel()           // 불필요하고 — 비효율적이다!
>           .Select (n => n * n)
> ```
>
> 쿼리 연산자가 이미 다른 `ParallelQuery` 시퀀스를 출력하므로 `AsParallel`을 계속 붙일 필요가 없다. 실제로 `AsParallel`을 다시 호출하면 **쿼리의 병합과 재파티셔닝을 강제**해서 비효율을 만든다.

`AsSequential()`을 호출하면 `ParallelQuery` 시퀀스의 포장이 풀려 이후 쿼리 연산자가 표준 쿼리 연산자에 바인딩되고 순차적으로 실행된다. 부작용이 있거나 스레드 안전하지 않은 메서드를 호출하기 전에 필요하다.

```csharp
public static IEnumerable<TSource> AsSequential<TSource> (
    this ParallelQuery<TSource> source);
```

> **⚠️ 두 입력 시퀀스를 받는 연산자는 양쪽 모두에 `AsParallel()`이 필요하다**
>
> `Join`, `GroupJoin`, `Concat`, `Union`, `Intersect`, `Except`, `Zip` — 두 개의 입력 시퀀스를 받는 연산자들은 **두 입력 시퀀스 모두에 `AsParallel()`을 적용해야 한다.** 그러지 않으면 예외가 던져진다.

### 런타임 동작 — 파티션 · 워커 · 병합

일반 LINQ 쿼리처럼 PLINQ 쿼리도 지연 평가된다. 즉 결과를 소비하기 시작할 때만 실행이 트리거된다 — 보통 `foreach` 루프를 통해서지만 `ToArray` 같은 변환 연산자나 단일 요소·값을 반환하는 연산자를 통해서도 트리거된다.

하지만 결과를 열거할 때의 실행 방식은 일반 순차 쿼리와 상당히 다르다.

```text
              입력 시퀀스
                   │
          ┌────────┴────────┐
          │   파티셔너      │   ← 청크 / 범위 / 해시 / 스트라이프
          └────────┬────────┘
       ┌───────┬───┴───┬───────┐
       ▼       ▼       ▼       ▼
   ┌───────┬───────┬───────┬───────┐
   │워커 1 │워커 2 │워커 3 │워커 4 │   ← 각자 쿼리 체인 전체를 실행
   └───┬───┴───┬───┴───┬───┴───┬───┘
       └───────┴───┬───┴───────┘
          ┌────────┴────────┐
          │   병합기        │   ← 버퍼링 (WithMergeOptions)
          └────────┬────────┘
                   ▼
              출력 시퀀스  →  소비자(foreach)
```

순차 쿼리는 전적으로 소비자가 "당기는(pull)" 방식으로 구동된다. 입력 시퀀스의 각 원소는 소비자가 요구하는 바로 그때 정확히 가져와진다.

병렬 쿼리는 보통 **독립적인 스레드들이 소비자가 필요로 하기 조금 전에 입력 시퀀스에서 원소를 미리 가져온다**(뉴스 진행자의 텔레프롬프터와 비슷하다). 그런 다음 쿼리 체인을 통해 원소들을 병렬로 처리하고, 소비자가 요구하면 바로 줄 수 있도록 결과를 작은 버퍼에 담아 둔다. 소비자가 일시 정지하거나 열거에서 일찍 빠져나오면, CPU 시간과 메모리를 낭비하지 않도록 쿼리 처리기도 일시 정지하거나 멈춘다.

이 "미리 가져오기" 때문에 **첫 `MoveNext()` 호출이 상당량의 결과를 만들어 낼 수 있다.** 원천 자료의 실험이 이를 잘 보여 준다. 300개 원소에 대한 순차 LINQ 쿼리는 `MoveNext()`를 부를 때마다 다음 결과 하나를 만들 만큼만 입력을 소비하지만, 같은 쿼리를 PLINQ로 돌리면 첫 `MoveNext()` 호출이 여러 스레드를 모두 시작시켜 (그 실험에서는 거의 전부인) 결과 객체 상당수를 생성했다. 이후 `MoveNext()` 호출들은 이미 만들어진 것 중 다음 항목을 가져올 뿐이다.

### PLINQ가 쓰는 세 가지 실행 알고리즘

| 알고리즘 | 언제 | 특징 |
|---|---|---|
| **파이프라이닝(pipelining)** | 기본. `foreach`로 결과를 열거할 때 | 한 스레드가 열거를 담당하고 나머지 스레드가 쿼리를 처리한다. 보통 스레드 수 = 코어 수 + 1 |
| **Stop & Go** | `ToList()`·`ToArray()`, 정렬·집계처럼 전체 결과가 필요할 때 | 열거를 시작한 스레드가 쿼리 스레드들에 조인한다. 성능이 조금 더 좋은 대신 메모리 사용량이 크다 |
| **역열거(inverted enumeration)** | `ForAll()`을 호출할 때 | 결과 시퀀스를 만들지 않고 각 결과에 액션을 수행한다. Stop & Go보다 메모리 사용량이 적다 |

> **📌 파이프라이닝이 코어 수 + 1인 이유**
>
> 열거를 담당하는 스레드가 따로 있기 때문이다. 그 스레드는 대부분의 시간을 대기하며 보내므로 하나를 더 만드는 것이 합리적이다.

### 파티셔닝 전략 네 가지

PLINQ는 입력 소스와 쿼리 종류에 따라 네 가지 파티셔닝 알고리즘 중 하나를 고른다. 파티셔닝은 시간을 많이 쓸 수 없다 — 그러면 PLINQ가 파티셔닝에 너무 많은 시간을, 실제 데이터 처리에 너무 적은 시간을 쓰게 된다.

| 전략 | 원소 할당 | 상대 성능 | 언제 쓰이는가 |
|---|---|---|---|
| **청크(chunk) 파티셔닝** | 동적 | 평균 | 인덱싱 불가 시퀀스의 기본값 |
| **범위(range) 파티셔닝** | 정적 | 나쁨 ~ 아주 좋음 | 배열·`IList<T>` 등 인덱싱 가능 시퀀스의 기본값 |
| **해시(hash) 파티셔닝** | 정적 | 나쁨 | 원소 비교가 필요한 연산자에서 강제 |
| **스트라이프(stripe) 파티셔닝** | 정적 | 시작 구간에 유리 | `TakeWhile`/`SkipWhile` 최적화 |

**범위 파티셔닝**이 가장 단순하다. 입력 시퀀스를 태스크 수로 나누어 각 태스크에 한 묶음씩 준다. 원소 1,000개를 쿼드 코어 머신에서 처리하면 250개씩 네 범위를 만든다. **쿼리 소스가 시퀀스 인덱싱을 지원하고 원소 개수를 보고할 때만** 쓰인다. 즉 `List<T>`, 배열, `IList<T>`를 구현하는 시퀀스로 제한된다. 정상적인 입력 측 열거를 우회하고 각 워커에 동일한 개수의 원소를 미리 할당하므로 입력 시퀀스에서의 경합을 피한다. 하지만 일부 스레드가 "쉬운" 원소를 받아 일찍 끝나면, 나머지 스레드가 작업하는 동안 놀게 된다.

**청크 파티셔닝**은 각 워커 스레드가 주기적으로 입력 시퀀스에서 작은 "청크"의 원소를 가져와 처리한다. PLINQ는 아주 작은 청크(한 번에 한두 개)를 할당하는 것으로 시작해, 쿼리가 진행됨에 따라 청크 크기를 늘린다. 이렇게 하면 작은 시퀀스도 효과적으로 병렬화되고 큰 시퀀스에서 과도한 왕복이 생기지 않는다. 워커가 우연히 "쉬운" 원소를 받으면 결국 더 많은 청크를 받게 된다. 이 시스템은 모든 스레드를 균등하게 바쁘게 유지한다. 유일한 단점은 공유 입력 시퀀스에서 원소를 가져올 때 **동기화(보통 배타적 잠금)** 가 필요하다는 것이며, 이것이 약간의 오버헤드와 경합을 만들 수 있다.

**해시 파티셔닝**은 `Join`, `GroupJoin`, `GroupBy`, `Distinct`, `Except`, `Union`, `Intersect` 연산을 위한 특수 목적 알고리즘이다. 같은 해시 코드를 만드는 모든 항목이 같은 태스크에서 처리되도록 보장해 태스크 간 통신을 최소화한다. 대신 **모든 원소의 해시 코드를 미리 계산해야** 하므로 상대적으로 비효율적이다. 너무 느리다고 판단되면 유일한 선택지는 `AsSequential`을 호출해 병렬화를 끄는 것이다.

**스트라이프 파티셔닝**은 범위 파티셔닝의 특수한 경우로, 시퀀스의 앞쪽 원소 처리를 최적화한다. 각 워커 스레드가 N개 항목을 건너뛴 다음 M개를 처리하고, 다시 N개를 건너뛴다. 스트라이프 크기가 1이고 워커 태스크가 넷이면, 한 태스크가 인덱스 0, 4, 8, 12…를 받고 두 번째 태스크가 1, 5, 9, 13…을 받는다. 스트라이프 파티션은 쿼리 전체에 대해 `TakeWhile()`과 `SkipWhile()`을 구현할 때 스레드 간 동기화를 피하게 해 준다. 각 워커 스레드는 단순 산술로 다음에 처리할 항목으로 이동할 수 있다.

**파티셔닝을 강제하는 방법**은 다음과 같다.

```csharp
// 범위 파티셔닝 강제 — Enumerable.Range 대신 ParallelEnumerable.Range
ParallelEnumerable.Range (1, 10_000_000).Sum (i => Math.Sqrt (i));

// 범위 파티셔닝 강제 — 입력을 인덱싱 가능하게 만든다 (비용을 감안할 것)
someSequence.ToArray().AsParallel().Where (...);

// 청크(부하 분산) 파티셔닝 강제
int[] numbers = { 3, 4, 5, 6, 7, 8, 9 };
var parallelQuery = Partitioner.Create (numbers, loadBalance: true)
                               .AsParallel()
                               .Where (n => n % 2 == 1);
```

> **⚠️ `ParallelEnumerable.Range`는 `Enumerable.Range(…).AsParallel()`의 축약이 아니다**
>
> 두 표현은 같은 값을 만들지만 **성능이 다르다.** `ParallelEnumerable.Range`는 **범위 파티셔닝을 활성화**한다. 모든 숫자가 같은 시간이 걸리는 계산(제곱근 합 같은)에서는 이 차이가 크다.
>
> `ParallelEnumerable.Range`는 `ParallelQuery<T>`를 반환하므로 뒤에 `AsParallel`을 또 부를 필요가 없다.
>
> 반대로 소수 판정처럼 원소마다 처리 시간이 크게 다른 계산에서는 범위 파티셔닝이 오히려 나쁘다. 앞쪽 작은 수를 받은 워커가 일찍 끝나고 논다. 이럴 때는 청크 파티셔닝이 맞다.

`Partitioner.Create`의 두 번째 인자는 **쿼리를 부하 분산(load balance)하고 싶다는 뜻**이며, 이는 청크 파티셔닝을 원한다는 말과 같다. `Partitioner` 타입은 `System.Collections.Concurrent` 네임스페이스에 있다.

> **📌 범위 파티셔닝이 항상 연속 블록은 아니다**
>
> 범위 파티셔닝이 반드시 원소 범위를 연속된 블록으로 할당하는 것은 아니다. 대신 "스트라이핑" 전략을 택할 수도 있다. 워커가 둘이면 한 워커는 홀수 번째 원소를, 다른 워커는 짝수 번째 원소를 처리할 수 있다. `TakeWhile` 연산자는 시퀀스 뒤쪽의 원소를 불필요하게 처리하지 않기 위해 거의 확실히 스트라이핑 전략을 유발한다.

### 순서 보존 — 기본은 보장하지 않는다

쿼리 연산자를 병렬화한 부작용으로, 결과가 병합될 때 **제출된 것과 같은 순서라는 보장이 없다.** LINQ의 통상적인 순서 보존 보장이 더 이상 성립하지 않는다.

순서 보존이 필요하면 `AsParallel()` 뒤에 `AsOrdered()`를 호출해 강제할 수 있다.

```csharp
myCollection.AsParallel().AsOrdered()...
```

`AsOrdered`를 호출하면 **원소 수가 많을 때 성능이 떨어진다.** PLINQ가 각 원소의 원래 위치를 추적해야 하기 때문이다. 스레드들이 항목을 그룹으로 처리한 뒤 그룹들을 순서를 보존하며 다시 병합한다.

쿼리 뒤쪽에서 `AsUnordered`를 호출해 `AsOrdered`의 효과를 무효화할 수 있다. 이는 "무작위 셔플 지점"을 도입해 그 지점부터 쿼리가 더 효율적으로 실행되게 한다.

```csharp
inputSequence.AsParallel().AsOrdered()
    .QueryOperator1()
    .QueryOperator2()
    .AsUnordered()          // 여기서부터는 순서가 중요하지 않다
    .QueryOperator3()
    ...
```

`AsOrdered`가 기본이 아닌 이유는 대부분의 쿼리에서 원래 입력 순서가 중요하지 않기 때문이다. `AsOrdered`가 기본이었다면 최고 성능을 얻기 위해 대다수 병렬 쿼리에 `AsUnordered`를 붙여야 했을 것이고, 그건 부담스럽다.

연산자에 따라 순서에 미치는 영향이 다르다.

| 연산자 | 순서에 대한 효과 |
|---|---|
| `Distinct`, `Except`, `Intersect`, `Union`, `Join`, `GroupBy`, `GroupJoin`, `ToLookup` | **순서 없는** 연산을 만든다. 이후 순서를 강제하려면 `AsOrdered` 호출 |
| `OrderBy`, `OrderByDescending`, `ThenBy`, `ThenByDescending` | **순서 있는** 연산을 만든다. 이후 성능을 위해 순서를 풀려면 `AsUnordered` 호출 |

### `ForAll` — 병합 없이 실행하기

PLINQ의 장점 중 하나는 병렬화된 작업의 결과를 하나의 출력 시퀀스로 편리하게 병합해 준다는 것이다. 그런데 때로는 그 시퀀스로 하는 일이 **원소마다 함수를 한 번 실행하는 것**뿐이다.

```csharp
foreach (int n in parallelQuery)
    DoSomething (n);
```

이 경우이고 원소가 처리되는 순서를 신경 쓰지 않는다면, PLINQ의 `ForAll` 메서드로 효율을 개선할 수 있다.

```csharp
public static void ForAll<TSource> (
    this ParallelQuery<TSource> source, Action<TSource> action);
```

`ForAll`은 `ParallelQuery`의 모든 출력 원소에 대해 델리게이트를 실행한다. **PLINQ의 내부에 직접 연결되어 결과를 모으고 열거하는 단계를 우회한다.**

```csharp
"abcdef".AsParallel().Select (c => char.ToUpper (c)).ForAll (Console.Write);
```

결과를 모으고 열거하는 것이 엄청나게 비싼 연산은 아니므로, `ForAll` 최적화는 **빠르게 실행되는 입력 원소가 아주 많을 때** 가장 큰 이득을 낸다.

> **⚠️ `ForAll(Console.WriteLine)`은 함정이다**
>
> 여러 스레드가 동시에 `Console.WriteLine`을 호출하면 실제로는 성능이 나빠진다. `Console` 클래스가 내부적으로 스레드를 동기화해서 한 번에 하나만 콘솔 창에 접근하게 하기 때문이다(50.1절). `ForAll`은 **각 결과에 계산을 수행하려 할 때** 써라.
>
> 이미지 처리도 비슷한 이유로 PLINQ와 궁합이 나쁘다. 수백만 픽셀을 출력 시퀀스로 모으는 것 자체가 병목이 된다. 그럴 때는 픽셀을 배열이나 비관리 메모리 블록에 직접 쓰고 `Parallel` 클래스나 태스크 병렬성으로 멀티스레딩을 관리하는 편이 낫다. (알고리즘이 자연스럽게 LINQ에 맞는다면 `ForAll`로 결과 병합을 무력화하는 방법도 있다.)

### PLINQ의 한계 — 무엇을 못 하는가

PLINQ가 병렬화할 수 있는 것에는 실질적인 한계가 있다.

**1. 인덱스 기반 오버로드.** 다음 쿼리 연산자들은 **소스 원소가 원래 인덱싱 위치에 있지 않은 한** 기본적으로 병렬화를 막는다.

- `Select`, `SelectMany`, `ElementAt`의 인덱스 버전

대부분의 쿼리 연산자가 원소의 인덱싱 위치를 바꾸므로(`Where`처럼 원소를 제거하는 연산자 포함), 이 연산자들을 쓰려면 보통 **쿼리 맨 앞**에 있어야 한다.

**2. 비싼 파티셔닝 전략을 쓰는 연산자.** 다음은 병렬화 가능하지만 비싼 파티셔닝 전략(해시 파티셔닝)을 써서 때로는 순차 처리보다 느릴 수 있다.

- `Join`, `GroupBy`, `GroupJoin`, `Distinct`, `Union`, `Intersect`, `Except`

**3. 시드가 있는 `Aggregate`.** `Aggregate` 연산자의 시드 오버로드는 표준 형태로는 병렬화되지 않는다. PLINQ는 이를 다루기 위한 특수 오버로드를 제공한다(50.5절).

**4. 순서 의존적 연산자.** `Concat`, `ElementAt(OrDefault)`, `First(OrDefault)`, `Last(OrDefault)`, `Skip(While)`, `Take(While)`, `Zip`을 쓰면 순차 처리가 더 나은 성능을 내는 경우가 많다. PLINQ는 이를 알고 있어서 자주 순차 알고리즘을 고른다.

원천 자료의 실험이 이 마지막 항목을 잘 보여 준다. 병렬 쿼리 뒤에 `Skip(20).Take(20)`을 붙이면, PLINQ가 300개 전부가 아니라 20개만 만드는 것이 더 빠르다고 판단해 **출력이 순차 LINQ와 동일해진다.** 그런데 그 사이에 `orderby`를 하나 끼워 넣으면 — 정렬하려면 모든 원소를 만들어야 하므로 — PLINQ는 다시 여러 스레드를 띄운다.

**5. 작은 컬렉션.** PLINQ는 큰 데이터셋에 최적화되어 있다. 작은 컬렉션에서는 오히려 성능이 떨어질 수 있다.

**6. 이미 I/O로 막힌 쿼리.** 50.2절에서 본 이유로, 동기 I/O가 섞인 쿼리는 PLINQ의 대상이 아니다.

### 조용한 순차 폴백과 `WithExecutionMode`

위 목록에 없는 나머지 연산자는 모두 병렬화 가능하다. **하지만 그 연산자를 쓴다고 해서 쿼리가 병렬화된다는 보장은 없다.** PLINQ는 병렬화 오버헤드가 그 쿼리를 느리게 만들 것으로 의심하면 **조용히 순차로 실행한다.**

이 동작을 재정의하고 병렬성을 강제하려면 `AsParallel()` 뒤에 다음을 호출한다.

```csharp
.WithExecutionMode (ParallelExecutionMode.ForceParallelism)
```

```csharp
public enum ParallelExecutionMode
{
    Default         = 0,   // PLINQ가 최선의 처리 방법을 결정하게 한다
    ForceParallelism = 1   // 쿼리를 병렬로 처리하도록 강제한다
}
```

> **⚠️ 순차 폴백은 진단하기 어렵다**
>
> "`AsParallel()`을 붙였는데 코어가 하나만 돈다"는 상황의 원인은 대개 셋 중 하나다.
>
> 1. **PLINQ가 순차 실행을 선택했다.** `WithExecutionMode(ForceParallelism)`으로 확인해 보라 — 이걸 붙였더니 코어가 다 도는데 더 느려졌다면, PLINQ의 판단이 옳았던 것이다.
> 2. **중간에 `IEnumerable<T>` 변수를 거쳤다.** 위의 `var` 함정이다.
> 3. **본문이 잠금이나 `Console` 같은 직렬화 지점에서 만난다.** 코어는 다 깨어 있지만 대부분 대기 중이다. Concurrency Visualizer(50.13절)로 확인할 수 있다.
>
> `WithExecutionMode`는 진단 도구이지 상시 설정이 아니다. 프로덕션 코드에 붙여 두면 PLINQ가 옳게 내린 판단까지 무력화한다.

## 50.4 함수적 순수성과 병렬 안전성

### 왜 부작용 없는 람다여야 하는가

PLINQ는 쿼리를 병렬 스레드에서 실행하므로 **스레드 안전하지 않은 연산을 수행하지 않도록 조심해야 한다.** 특히 변수에 쓰는 것은 부작용이며 따라서 스레드 안전하지 않다.

```csharp
// 다음 쿼리는 각 원소에 그 위치를 곱한다.
// Enumerable.Range(0,999)를 입력으로 주면 제곱을 출력해야 한다.
int i = 0;
var query = from n in Enumerable.Range (0, 999).AsParallel() select n * i++;
```

이 코드는 세 가지가 동시에 잘못됐다.

**1. `i++`는 원자적이 아니다.** 48.2절에서 본 것처럼 `i++`는 읽기·증가·쓰기 세 연산이다. 여러 스레드가 동시에 실행하면 증가가 유실된다.

**2. 잠금으로 고쳐도 문제가 남는다.** 잠금을 써서 `i`의 증가를 스레드 안전하게 만들 수 있지만, **`i`가 입력 원소의 위치에 반드시 대응하지는 않는다**는 문제는 그대로다.

**3. `AsOrdered`로도 안 고쳐진다.** 쿼리에 `AsOrdered`를 추가해도 후자의 문제는 해결되지 않는다. `AsOrdered`는 원소들이 **순차적으로 처리된 것과 일관된 순서로 출력되도록** 보장할 뿐, 실제로 순차적으로 처리하지는 않기 때문이다.

올바른 해법은 인덱스 버전의 `Select`를 쓰도록 쿼리를 다시 쓰는 것이다.

```csharp
var query = Enumerable.Range (0, 999).AsParallel().Select ((n, i) => n * i);
```

> **⚠️ `AsOrdered`는 "순차 실행"이 아니라 "순차 순서의 출력"이다**
>
> 이 구분이 흐릿하면 위의 세 번째 실수를 반복하게 된다. `AsOrdered`는 **결과의 나열 순서**를 보장하지 최종적으로 몇 번째 스레드가 몇 번째 원소를 언제 처리했는지는 전혀 통제하지 않는다.
>
> 처리 순서 자체가 필요하면 병렬화를 포기하거나(`AsSequential`), 인덱스를 원소와 함께 **명시적으로 들고 다녀야** 한다.

최고의 성능을 위해서는, 쿼리 연산자에서 호출되는 어떤 메서드든 **필드나 속성에 쓰지 않음으로써**(부작용 없음, 즉 함수적으로 순수함) 스레드 안전해야 한다. 잠금 덕분에 스레드 안전한 경우라면, 쿼리의 병렬성 잠재력은 경합의 영향으로 제한된다.

### 공유 변수 갱신이 왜 깨지는지 — 세 층위

| 층위 | 무엇이 깨지는가 | 예 | 해법 |
|---|---|---|---|
| **원자성** | 읽기-수정-쓰기가 쪼개진다 | `total += x`, `i++` | `Interlocked`(48.4절) 또는 스레드 로컬 누적 |
| **가시성/재배치** | 한 스레드가 쓴 값을 다른 스레드가 못 본다 | 플래그 폴링 | `volatile`/`Volatile`(48.3절), 잠금 |
| **불변식** | 개별 연산은 원자적인데 조합이 깨진다 | `if (!dict.ContainsKey(k)) dict.Add(k, v)` | 복합 원자 연산(`GetOrAdd`, 50.10절) 또는 잠금 |

병렬 루프에서 가장 흔한 실수는 첫 번째 층위지만, 가장 찾기 어려운 것은 세 번째다. 세 번째는 동시성 컬렉션을 써도 남는다.

### 잠금은 병렬화를 무력화한다

숫자 1부터 10,000,000까지의 제곱근을 합산한다고 하자. 1,000만 개의 제곱근을 계산하는 것은 병렬화가 쉽지만, 값을 합산하는 것은 골치 아프다 — 합계를 갱신할 때 잠금을 걸어야 하기 때문이다.

```csharp
object locker = new object();
double total = 0;
Parallel.For (1, 10000000,
              i => { lock (locker) total += Math.Sqrt (i); });
```

병렬화로 얻는 이득이 **1,000만 번의 잠금 획득 비용과 그로 인한 블로킹**으로 상쇄되고도 남는다. 48.9절에서 본 것처럼 무경합 잠금 획득은 수십 나노초지만, 경합 상태에서는 그 수백 배가 된다. 그리고 여기서는 항상 경합한다.

### 스레드 로컬 누적 후 병합 — 이 장의 중심 패턴

현실적으로는 1,000만 번의 잠금이 필요하지 않다. 자원봉사자 팀이 대량의 쓰레기를 줍는 상황을 상상해 보자. 모든 작업자가 쓰레기통 하나를 공유하면 이동과 경합 때문에 과정이 극히 비효율적이다. 명백한 해법은 **각 작업자가 개인 쓰레기통을 갖고, 가끔씩 그것을 메인 쓰레기통에 비우는 것**이다.

이 패턴이 병렬 프로그래밍 전체에서 가장 중요한 관용구다. .NET은 세 가지 형태로 제공한다.

**형태 1 — `Parallel.For`/`ForEach`의 `localInit`/`localFinally`.**

```csharp
object locker = new object();
double grandTotal = 0;

Parallel.For (1, 10000000,

    () => 0.0,                         // localInit: 지역 값을 초기화한다

    (i, state, localTotal) =>          // body: 새 지역 합계를 반환한다
        localTotal + Math.Sqrt (i),

    localTotal =>                      // localFinally: 지역 값을
    { lock (locker) grandTotal += localTotal; }   // 마스터 값에 더한다
);
```

여전히 잠금을 걸어야 하지만 **지역 값을 총합에 집계할 때만** 건다. 잠금 횟수가 1,000만 번에서 참여 태스크 수(보통 코어 수 언저리)로 줄어든다. 이것이 과정을 극적으로 효율적으로 만든다.

**형태 2 — PLINQ `Aggregate`의 4인자 오버로드.** 50.5절에서 다룬다.

**형태 3 — `ThreadLocal<T>`로 스레드마다 별도 인스턴스.** 49.8절의 `ThreadLocal<T>`를 병렬 쿼리 안에서 쓰는 것이다.

### `ThreadLocal<T>`로 스레드 안전하지 않은 객체 다루기

병렬 쿼리 안에서 `Random`을 쓰는 흔한 예를 보자. 100만 개의 무작위 단어 목록을 만드는 순차 버전이다.

```csharp
string[] wordsToTest = Enumerable.Range (0, 1000000)
    .Select (i => wordList [random.Next (0, wordList.Length)])
    .ToArray();
```

불행히도 `random.Next` 호출은 스레드 안전하지 않으므로 `AsParallel()`을 끼워 넣는 것만으로는 안 된다. `random.Next` 주위에 잠금을 거는 함수를 쓸 수도 있지만 동시성이 제한된다. 더 나은 선택은 `ThreadLocal<Random>`을 써서 **스레드마다 별도의 `Random` 객체**를 만드는 것이다.

```csharp
var localRandom = new ThreadLocal<Random>
    ( () => new Random (Guid.NewGuid().GetHashCode()) );

string[] wordsToTest = Enumerable.Range (0, 1000000).AsParallel()
    .Select (i => wordList [localRandom.Value.Next (0, wordList.Length)])
    .ToArray();
```

`Random` 객체를 인스턴스화하는 팩토리 함수에서 `Guid`의 해시 코드를 넘긴다. 짧은 시간 안에 `Random` 객체 두 개가 만들어져도 서로 다른 난수 시퀀스를 만들도록 보장하기 위해서다.

> **📌 ※.NET 6 이후에는 `Random.Shared`가 있다**
>
> .NET 6부터 `Random.Shared` 정적 속성이 추가됐고 **이 인스턴스는 스레드 안전하다.** 위 예제는 다음처럼 줄어든다.
>
> ```csharp
> string[] wordsToTest = Enumerable.Range (0, 1000000).AsParallel()
>     .Select (i => wordList [Random.Shared.Next (0, wordList.Length)])
>     .ToArray();
> ```
>
> 다만 `Random.Shared`는 내부적으로 스레드별 상태를 쓰기 때문에 **재현 가능한 시드**를 줄 수 없다. 시드가 필요한 테스트에서는 여전히 `ThreadLocal<Random>` 패턴이 필요하다.
>
> `ThreadLocal<T>` 패턴 자체는 `Random`에만 쓰이는 것이 아니다. `StringBuilder`, `MemoryStream`, `HashAlgorithm`, EF Core의 `DbContext` 등 **상태를 가진 비스레드안전 객체 전부**가 같은 대상이다.

### 스레드 안전하지 않은 BCL 타입 카탈로그

| 타입 | 병렬 람다에서 공유하면 | 대안 |
|---|---|---|
| `Random` | 결과가 0으로 몰리거나 시퀀스가 깨진다 | `Random.Shared` ※.NET 6 / `ThreadLocal<Random>` |
| `StringBuilder` | 문자열이 뒤섞이거나 예외 | 지역 인스턴스 + `localFinally`에서 병합 |
| `List<T>` / `Dictionary<K,V>` | 내부 배열이 깨진다. 예외가 안 날 수도 있다 | `ConcurrentBag`·`ConcurrentDictionary`(50.10절) |
| `MemoryStream` | 위치가 엉킨다 | 스레드마다 하나씩 |
| EF Core `DbContext` | `InvalidOperationException` 또는 상태 손상 | 작업 단위마다 새 인스턴스 |
| `HttpClient` | **안전하다** — 재사용이 권장된다 | 그대로 공유 |

> **⚠️ "예외가 안 났으니 괜찮다"는 가장 위험한 결론이다**
>
> `List<T>.Add`를 여러 스레드에서 동시에 호출하면 운이 좋으면 `IndexOutOfRangeException`이나 `ArgumentException`이 난다. 운이 나쁘면 **아무 일도 없이 항목 몇 개가 사라진다.** 내부 배열 확장 중에 다른 스레드가 인덱스를 쓴 결과다.
>
> 병렬 코드의 버그는 "터지는 버그"보다 "조용히 틀리는 버그"가 압도적으로 많다. 테스트가 통과했다는 것은 그날 그 머신에서 그 타이밍으로는 안 터졌다는 뜻일 뿐이다(50.13절).

### 캡처된 변수와 클로저의 함정

26장에서 본 것처럼 람다가 바깥 변수를 캡처하면 컴파일러는 그 변수를 **클로저 클래스의 필드**로 승격시킨다. 병렬 맥락에서는 이 승격이 곧 "공유 필드가 생긴다"는 뜻이다.

```csharp
var results = new List<int>();
Parallel.For (0, 1000, i =>
{
    results.Add (i * i);      // ⚠ results 는 캡처된 공유 변수 — 스레드 안전하지 않다
});
```

`results`는 클로저 필드가 되어 모든 워커가 같은 `List<int>`를 만진다. 위 표의 두 번째 함정이다.

`for` 루프 변수를 캡처하는 고전적 함정도 병렬 코드에서 더 나빠진다.

```csharp
var tasks = new List<Task>();
for (int i = 0; i < 5; i++)
    tasks.Add (Task.Run (() => Console.Write (i)));    // ⚠ i 하나를 다섯 태스크가 공유
Task.WaitAll (tasks.ToArray());
```

`for` 문의 반복 변수는 **루프 전체에서 하나**다. 다섯 태스크가 같은 변수를 보므로 출력은 `55555`가 될 수도, 무엇이든 될 수도 있다. 고치려면 반복마다 새 변수를 만든다.

```csharp
for (int i = 0; i < 5; i++)
{
    int copy = i;                                      // 반복마다 새 변수
    tasks.Add (Task.Run (() => Console.Write (copy)));
}
```

> **📌 `foreach` 변수는 C# 5부터 반복마다 새로 만들어진다**
>
> C# 5 이전에는 `foreach`의 반복 변수도 루프 전체에서 하나였고 같은 버그를 만들었다. C# 5에서 언어 명세가 바뀌어 `foreach` 변수는 **반복마다 새 변수**가 되었다. 반면 **`for` 문의 반복 변수는 지금도 하나다.** 이 비대칭을 기억해 두면 위 코드를 보자마자 문제를 알아챌 수 있다.
>
> 클로저와 변수 캡처의 컴파일 결과는 26.10절에, 지연 실행과 캡처의 상호작용은 29.7절에 있다.

> **💡 병렬 람다를 쓰기 전 체크리스트**
>
> 1. 람다가 **캡처하는 변수**를 모두 나열하라. 그중 쓰는 것이 있으면 그것이 문제다.
> 2. 람다가 호출하는 메서드가 **필드나 정적 상태에 쓰는가**. 문서에 "스레드 안전"이라고 쓰여 있지 않으면 안전하지 않다고 가정하라.
> 3. 누적이 필요하면 **`localInit`/`localFinally` 또는 `Aggregate` 4인자 오버로드**를 먼저 떠올려라. `lock`이 본문 안에 들어가면 설계를 다시 보라.
> 4. 결과를 모아야 하면 **동시성 컬렉션**(50.10절)을 쓰되, 그것도 "빠른 잠금"이지 공짜가 아님을 기억하라.

## 50.5 병렬도 설정, 취소, PLINQ 최적화

### `WithDegreeOfParallelism`

기본적으로 PLINQ는 사용 중인 프로세서에 대해 최적의 병렬도를 고른다. `AsParallel` 뒤에 `WithDegreeOfParallelism`을 호출해 이를 재정의할 수 있다.

```csharp
...AsParallel().WithDegreeOfParallelism (4)...
```

이 메서드는 **쿼리를 처리하도록 허용되는 최대 스레드 수**를 지정한다. 필요하지 않은 스레드까지 강제로 만들지는 않는다. 보통은 이 메서드를 호출하지 않고, 기본적으로 쿼리는 코어당 스레드 하나로 실행된다.

코어 수보다 **작은** 값을 넘기는 경우는 명확하다. 다른 작업을 위해 코어를 남겨 두고 싶을 때다.

코어 수보다 **큰** 값을 넘기는 경우는 I/O 바운드 작업이 섞여 있을 때다(웹 페이지를 한꺼번에 많이 내려받는 경우 등). 쿼리가 동기 I/O 연산을 수행하면 스레드가 그 동안 블로킹되므로, 스레드를 더 낭비하는 대신 최종 결과를 더 짧은 시간에 만들 수 있다.

> **⚠️ 코어 수보다 큰 병렬도는 "잘못된 도구를 참고 쓰는 것"이다**
>
> 이 기법이 동작하는 것은 사실이다. 하지만 **애초에 도구 선택이 틀렸다는 신호**로 읽어야 한다.
>
> - 태스크 합성기와 비동기 함수가 비슷하게 쉬우면서 **더 효율적인** 해법을 제공한다(46.9절).
> - `Task`와 달리 PLINQ는 스레드를 블로킹하지 않고는 I/O 바운드 작업을 수행할 수 없다. 그것도 **풀 스레드**를 블로킹한다.
> - 클라이언트 애플리케이션에서는 고려해 볼 수 있다. **서버 애플리케이션에서 동기 I/O를 수행하는 것은 강력히 권장되지 않는다.** 스레드 풀 기아로 애플리케이션 전체가 마비된다.
>
> .NET 6 이후에는 이 상황의 정답이 `Parallel.ForEachAsync`(50.7절)로 확정됐다. 코어 수보다 큰 `WithDegreeOfParallelism`을 쓰고 싶어졌다면 그쪽으로 가라.

### 쿼리 도중에 병렬도 바꾸기

PLINQ 쿼리 하나 안에서 `WithDegreeOfParallelism`은 **한 번만 호출할 수 있다.** 다시 호출해야 한다면 쿼리 안에서 `AsParallel()`을 다시 호출해 병합과 재파티셔닝을 강제해야 한다.

```csharp
"The Quick Brown Fox"
    .AsParallel().WithDegreeOfParallelism (2)
    .Where (c => !char.IsWhiteSpace (c))
    .AsParallel().WithDegreeOfParallelism (3)   // 병합 + 파티션을 강제한다
    .Select (c => char.ToUpper (c))
```

### 취소

결과를 `foreach` 루프에서 소비하는 PLINQ 쿼리를 취소하는 것은 쉽다. **`foreach`에서 빠져나오면 열거자가 암묵적으로 해제되면서 쿼리가 자동으로 취소된다.**

변환·요소·집계 연산자로 끝나는 쿼리는 다른 스레드에서 취소 토큰으로 취소할 수 있다. 토큰을 넣으려면 `AsParallel` 뒤에 `WithCancellation`을 호출하고 `CancellationTokenSource` 객체의 `Token` 속성을 넘긴다. 그러면 다른 스레드가 토큰 소스에서 `Cancel`을 호출할 수 있다(직접 지연 후 호출할 수도 있다). 이는 쿼리 소비자에게 `OperationCanceledException`을 던진다.

```csharp
IEnumerable<int> tenMillion = Enumerable.Range (3, 10_000_000);

var cancelSource = new CancellationTokenSource();
cancelSource.CancelAfter (100);      // 100밀리초 후 쿼리를 취소한다

var primeNumberQuery =
    from n in tenMillion.AsParallel().WithCancellation (cancelSource.Token)
    where Enumerable.Range (2, (int) Math.Sqrt (n)).All (i => n % i > 0)
    select n;

try
{
    // 쿼리 실행을 시작한다.
    int[] primes = primeNumberQuery.ToArray();
    // 다른 스레드가 우리를 취소할 것이므로 여기 도달하지 않는다.
}
catch (OperationCanceledException)
{
    Console.WriteLine ("쿼리가 취소되었다");
}
```

> **⚠️ 취소는 "즉시 멈춤"이 아니다**
>
> 취소 시 PLINQ는 **각 워커 스레드가 현재 원소 처리를 끝낼 때까지 기다린 뒤** 쿼리를 종료한다. 이는 쿼리가 호출하는 외부 메서드가 **끝까지 실행된다**는 뜻이다.
>
> 원소 하나의 처리가 30초 걸린다면 `Cancel()` 후 최대 30초를 더 기다려야 한다. 취소 응답성이 필요하면 본문 안에서도 토큰을 관찰해야 한다(46.8절의 협력적 취소 프로토콜).

취소 토큰은 다른 API에서도 인식되므로 구조 사이로 자연스럽게 전파된다.

```csharp
var cancelSource = new CancellationTokenSource();
CancellationToken token = cancelSource.Token;

Task task = Task.Factory.StartNew (() =>
{
    // 취소 토큰을 PLINQ 쿼리에 넘긴다:
    var query = someSequence.AsParallel().WithCancellation (token)...
    // ... 쿼리를 열거한다 ...
});
```

이 예제에서 `cancelSource`의 `Cancel`을 호출하면 PLINQ 쿼리가 취소되고, 그것이 태스크 본문에서 `OperationCanceledException`을 던지며, 그것이 다시 태스크를 취소한다.

### `WithMergeOptions` — 지연 시간과 처리량의 절충

PLINQ는 여러 스레드가 항목을 처리한 뒤 결과를 다시 병합해야 한다. `WithMergeOptions`로 항목이 버퍼링되고 병합되는 방식을 제어할 수 있다.

```csharp
public enum ParallelMergeOptions
{
    Default       = 0,   // 현재는 AutoBuffered와 같다 (미래에 바뀔 수 있다)
    NotBuffered   = 1,   // 결과가 준비되는 대로 처리한다
    AutoBuffered  = 2,   // 각 스레드가 처리 전에 일부 결과를 버퍼링한다
    FullyBuffered = 3    // 각 스레드가 처리 전에 모든 결과를 버퍼링한다
}
```

| 옵션 | 첫 결과까지의 지연 시간 | 전체 처리량 | 메모리 | 쓰는 상황 |
|---|---|---|---|---|
| `NotBuffered` | **가장 짧다** | 가장 낮다 | 가장 적다 | 결과를 가능한 한 빨리 보고 싶을 때(스트리밍 UI) |
| `AutoBuffered` (기본) | 중간 | 중간 | 중간 | 대부분의 쿼리 |
| `FullyBuffered` | **가장 길다** | 가장 높다 | 가장 많다 | 전체 결과가 어차피 필요할 때 |

기본값 `AutoBuffered`가 일반적으로 전반적으로 가장 좋은 결과를 낸다. `NotBuffered`는 버퍼를 비활성화하며 결과를 가능한 한 빨리 보고 싶을 때 유용하다. `FullyBuffered`는 소비자에게 제시하기 전에 전체 결과 집합을 캐시한다.

> **📌 어떤 연산자는 자연스럽게 `FullyBuffered`로 동작한다**
>
> `OrderBy`와 `Reverse` 연산자는 본질적으로 전체 결과가 있어야 동작하므로 자연스럽게 이렇게 동작한다. 요소·집계·변환 연산자도 마찬가지다.
>
> 그리고 **버퍼링은 힌트이지 명령이 아니다.** PLINQ는 요청을 무시할 수 있다.

> **💡 어떤 병합 옵션이 최선인지는 알 수 없다**
>
> 원천 자료의 조언이 정직하다 — "어떤 쿼리에 어느 것을 고를지 아는 유일한 방법은 전부 시도해 성능 결과를 비교하거나, 그냥 기본값을 받아들이는 것이다. 기본값이 많은 쿼리에서 꽤 잘 동작한다."
>
> 여러 대상 머신에서 실험할 수 없다면 **기본값을 쓰라.** 이 설정은 알고리즘에 크게 의존한다.

### 사용자 정의 집계 — `Aggregate`의 4인자 오버로드

PLINQ는 `Sum`, `Average`, `Min`, `Max` 연산자를 추가 개입 없이 효율적으로 병렬화한다. 그러나 `Aggregate` 연산자는 특별한 도전을 제기한다.

30.10절에서 본 것처럼 `Aggregate`는 사용자 정의 집계를 수행한다.

```csharp
int[] numbers = { 1, 2, 3 };
int sum = numbers.Aggregate (0, (total, n) => total + n);   // 6
```

시드 없는 집계에서는 제공하는 델리게이트가 **결합적(associative)이고 교환적(commutative)** 이어야 한다. 이 규칙을 어기면 PLINQ가 틀린 결과를 낸다. 시퀀스의 여러 파티션을 동시에 집계하기 위해 **입력 시퀀스에서 여러 개의 시드를 뽑기** 때문이다.

명시적으로 시드가 있는 집계는 PLINQ에서 안전해 보이지만, 불행히도 이것들은 **단일 시드에 의존하기 때문에 보통 순차적으로 실행된다.** 이를 완화하기 위해 PLINQ는 여러 시드를 — 정확히는 **시드 팩토리 함수**를 — 지정할 수 있는 `Aggregate`의 다른 오버로드를 제공한다. 각 스레드에 대해 이 함수를 실행해 별도의 시드를 생성하고, 이것이 원소를 지역적으로 집계할 **스레드 로컬 누산기**가 된다.

지역 누산기와 메인 누산기를 어떻게 결합할지 나타내는 함수도 제공해야 한다. 마지막으로 이 `Aggregate` 오버로드는 결과에 최종 변환을 수행할 델리게이트를 기대한다(이건 나중에 직접 함수를 실행해도 똑같이 달성할 수 있다).

전달 순서대로 네 델리게이트는 다음과 같다.

| 매개변수 | 역할 |
|---|---|
| `seedFactory` | 새 지역 누산기를 반환한다 |
| `updateAccumulatorFunc` | 원소를 지역 누산기에 집계한다 |
| `combineAccumulatorFunc` | 지역 누산기를 메인 누산기와 결합한다 |
| `resultSelector` | 최종 결과에 마지막 변환을 적용한다 |

아주 단순한 예로, 다음은 `numbers` 배열의 값을 합산한다.

```csharp
numbers.AsParallel().Aggregate (
    () => 0,                                    // seedFactory
    (localTotal, n) => localTotal + n,          // updateAccumulatorFunc
    (mainTot, localTot) => mainTot + localTot,  // combineAccumulatorFunc
    finalResult => finalResult)                 // resultSelector
```

> **⚠️ 시드 값 대신 시드 팩토리를 쓰는 이유**
>
> 단순한 시나리오에서는 시드 팩토리 대신 시드 **값**을 지정할 수 있다. **이 전술은 시드가 변경하려는 참조 타입일 때 실패한다.** 같은 인스턴스가 각 스레드에 공유되기 때문이다.
>
> 즉 배열이나 `List<T>`를 누산기로 쓰려면 반드시 팩토리 오버로드를 써야 한다. 값을 넘기면 모든 스레드가 같은 배열을 갱신해 조용히 틀린 결과가 나온다.

더 현실적인 예를 보자. 주어진 문자열에서 영어 알파벳 각 글자의 빈도를 계산한다고 하자. 단순한 순차 해법은 이렇다.

```csharp
string text = "Let's suppose this is a really long string";
var letterFrequencies = new int[26];
foreach (char c in text)
{
    int index = char.ToUpper (c) - 'A';
    if (index >= 0 && index < 26) letterFrequencies [index]++;
}
```

이를 병렬화하려고 `foreach`를 `Parallel.ForEach`로 바꾸면 공유 배열의 동시성 문제를 다뤄야 한다. 그리고 그 배열 접근에 잠금을 걸면 병렬화 잠재력이 거의 사라진다. `Aggregate`가 깔끔한 해법을 제공한다.

```csharp
int[] result =
    text.AsParallel().Aggregate (

        () => new int[26],               // 새 지역 누산기를 만든다

        (localFrequencies, c) =>         // 지역 누산기에 집계한다
        {
            int index = char.ToUpper (c) - 'A';
            if (index >= 0 && index < 26) localFrequencies [index]++;
            return localFrequencies;
        },

        (mainFreq, localFreq) =>         // 지역 → 메인 누산기 집계
            mainFreq.Zip (localFreq, (f1, f2) => f1 + f2).ToArray(),

        finalResult => finalResult       // 최종 결과에 대한 변환
    );
```

지역 집계 함수가 `localFrequencies` 배열을 **변경(mutate)** 한다는 점에 주목하라. 이 최적화를 수행할 수 있다는 것이 중요하며, `localFrequencies`가 각 스레드에 지역적이므로 정당하다.

> **📌 유전자 서열 분석이 이 예제의 실제 용도다**
>
> 입력 텍스트가 아주 길 수 있는 예가 유전자 서열 분석이다. 그때 "알파벳"은 a, c, g, t 네 글자가 된다.

> **💡 `Aggregate` 4인자 오버로드와 `Parallel.For`의 `localInit`/`localFinally`는 같은 패턴이다**
>
> 둘 다 "지역 쓰레기통 → 메인 쓰레기통" 패턴의 구현이다. 차이는 **결과 병합을 누가 하느냐**다.
>
> | | PLINQ `Aggregate` | `Parallel.For`/`ForEach` |
> |---|---|---|
> | 지역 값 초기화 | `seedFactory` | `localInit` |
> | 원소 처리 | `updateAccumulatorFunc` | `body` (새 지역 값을 반환) |
> | 병합 | `combineAccumulatorFunc` (**PLINQ가 스레드 안전하게 처리**) | `localFinally` (**직접 잠금하거나 `Interlocked`**) |
> | 최종 변환 | `resultSelector` | 없음 |
>
> 병합의 스레드 안전성을 PLINQ가 대신 처리해 준다는 것이 `Aggregate` 쪽의 이점이다. 반대로 `Parallel` 쪽은 인덱스 접근이나 조기 탈출(`Break`/`Stop`)이 필요할 때 유리하다.

## 50.6 `Parallel.Invoke` / `For` / `ForEach`와 파티셔닝 전략

PFX는 `Parallel` 클래스의 세 정적 메서드를 통해 기본 형태의 구조적 병렬성을 제공한다.

| 메서드 | 역할 |
|---|---|
| `Parallel.Invoke` | `Action` 델리게이트 배열을 병렬로 실행한다 |
| `Parallel.For` | C# `for` 루프의 병렬 등가물을 수행한다 |
| `Parallel.ForEach` | C# `foreach` 루프의 병렬 등가물을 수행한다 |

세 메서드 모두 **모든 작업이 완료될 때까지 블로킹된다.** PLINQ와 마찬가지로, 처리되지 않은 예외 이후에는 남은 워커들이 현재 반복을 마친 뒤 중단되고, 예외(들)가 `AggregateException`으로 감싸져 호출자에게 던져진다(50.9절).

> **📌 호출 스레드도 작업에 참여한다**
>
> `Parallel`의 모든 메서드는 **호출 스레드가 작업 처리에 참여하게** 한다. 호출 스레드가 스레드 풀 스레드들이 모든 작업을 하는 동안 그냥 자기 자신을 정지시키는 것은 자원 사용 측면에서 낭비이기 때문이다.
>
> 호출 스레드가 스레드 풀 스레드들보다 자기 몫을 먼저 끝내면, 그때는 모든 작업이 끝날 때까지 자기 자신을 정지시킨다. 이 역시 `for`나 `foreach` 루프와 같은 의미론을 준다는 점에서 바람직하다 — **모든 작업이 끝나기 전에는 스레드가 계속 진행하지 않는다.**

### `Parallel.Invoke`

`Parallel.Invoke`는 `Action` 델리게이트 배열을 병렬로 실행하고 완료를 기다린다. 가장 단순한 버전의 정의는 다음과 같다.

```csharp
public static void Invoke (params Action[] actions);
```

```csharp
// 하나의 스레드가 모든 메서드를 순차적으로 실행한다
Method1();
Method2();
Method3();

// 스레드 풀의 스레드들이 메서드들을 병렬로 실행한다
Parallel.Invoke (
    () => Method1(),
    () => Method2(),
    () => Method3());
```

표면적으로는 스레드 바인딩된 `Task` 객체 두 개를 만들고 기다리는 편리한 축약처럼 보인다. 하지만 중요한 차이가 있다. **`Parallel.Invoke`는 백만 개의 델리게이트 배열을 넘겨도 여전히 효율적으로 동작한다.** 델리게이트마다 별도의 `Task`를 만드는 대신, 많은 수의 원소를 **배치로 나누어 소수의 하위 `Task`에 할당하기** 때문이다.

`Parallel`의 모든 메서드와 마찬가지로 **결과를 모으는 것은 스스로 해야 한다.** 스레드 안전성을 염두에 두어야 한다는 뜻이다. 다음은 스레드 안전하지 않다.

```csharp
var data = new List<string>();
Parallel.Invoke (
    () => data.Add (Download ("http://www.foo.com")),
    () => data.Add (Download ("http://www.far.com")));
```

리스트에 추가하는 부분에 잠금을 걸면 해결되지만, 빠르게 실행되는 델리게이트의 배열이 훨씬 크면 잠금이 병목을 만든다. 더 나은 해법은 스레드 안전한 컬렉션을 쓰는 것이며 이 경우 `ConcurrentBag`이 이상적이다(50.10절).

`Parallel.Invoke`는 `ParallelOptions` 객체를 받는 오버로드도 있다.

```csharp
public static void Invoke (ParallelOptions options, params Action[] actions);
```

> **📌 취소 시 아직 시작되지 않은 델리게이트만 버려진다**
>
> `ParallelOptions`로 취소 토큰을 넣고 최대 동시성을 제한하고 커스텀 태스크 스케줄러를 지정할 수 있다. **취소 토큰은 코어 수보다 (대략) 더 많은 태스크를 실행할 때 의미가 있다.** 취소 시 아직 시작되지 않은 델리게이트는 버려진다. 그러나 **이미 실행 중인 델리게이트는 완료까지 계속된다.**

### `Parallel.For`와 `Parallel.ForEach`

가장 단순한 시그니처는 다음과 같다.

```csharp
public static ParallelLoopResult For (
    int fromInclusive, int toExclusive, Action<int> body);

public static ParallelLoopResult ForEach<TSource> (
    IEnumerable<TSource> source, Action<TSource> body);
```

순차 루프를 병렬화하는 방법은 기계적이다.

```csharp
for (int i = 0; i < 100; i++)     →   Parallel.For (0, 100, i => Foo (i));
    Foo (i);                          Parallel.For (0, 100, Foo);   // 더 간단히

foreach (char c in "Hello, world") →   Parallel.ForEach ("Hello, world", Foo);
    Foo (c);
```

실무적인 예로, `System.Security.Cryptography` 네임스페이스를 임포트하면 공개/개인 키 쌍 문자열 여섯 개를 병렬로 생성할 수 있다.

```csharp
var keyPairs = new string[6];
Parallel.For (0, keyPairs.Length,
              i => keyPairs[i] = RSA.Create().ToXmlString (true));
```

`Parallel.Invoke`와 마찬가지로 많은 수의 작업 항목을 넘기면 소수의 태스크에 효율적으로 분할된다.

> **💡 `For`와 `ForEach` 중 고를 수 있다면 `For`를 써라**
>
> 코드에서 `For`와 `ForEach` 중 어느 것이든 쓸 수 있다면 **`For`를 쓰는 것이 권장된다. 더 빠르게 실행되기 때문이다.** `ForEach`는 열거자를 통해 원소를 꺼내야 하고 그 과정에 동기화가 필요하지만, `For`는 인덱스를 산술로 계산할 수 있다.
>
> 다만 `ForEach`에 `Partitioner.Create`로 만든 범위 파티셔너를 넘기면 `For`에 가까운 특성을 얻을 수 있다(이 절 마지막 참조).

### 바깥 루프 대 안쪽 루프

`Parallel.For`와 `Parallel.ForEach`는 보통 안쪽 루프보다 **바깥 루프**에서 가장 잘 동작한다. 전자에서는 병렬화할 더 큰 작업 덩어리를 제공하므로 관리 오버헤드가 희석되기 때문이다. 안쪽과 바깥 루프를 모두 병렬화하는 것은 보통 불필요하다.

```csharp
Parallel.For (0, 100, i =>
{
    Parallel.For (0, 50, j => Foo (i, j));   // 안쪽 루프는 순차가 낫다
});
```

이 예제에서 안쪽 병렬화로 이득을 보려면 보통 코어가 100개보다 많아야 한다.

### 인덱스가 있는 `Parallel.ForEach`

루프 반복 인덱스를 알아야 할 때가 있다. 순차 `foreach`에서는 쉽다.

```csharp
int i = 0;
foreach (char c in "Hello, world")
    Console.WriteLine (c.ToString() + i++);
```

하지만 공유 변수를 증가시키는 것은 병렬 맥락에서 스레드 안전하지 않다(50.4절). 대신 다음 버전의 `ForEach`를 써야 한다.

```csharp
public static ParallelLoopResult ForEach<TSource> (
    IEnumerable<TSource> source,
    Action<TSource, ParallelLoopState, long> body);
```

`Action`의 세 번째 타입 매개변수 `long`이 루프 인덱스다.

```csharp
Parallel.ForEach ("Hello, world", (c, state, i) =>
{
    Console.WriteLine (c.ToString() + i);
});
```

실용적인 맥락으로, 백만 개 단어 배열에 대한 철자 검사를 인덱스 버전으로 수행해 보자.

```csharp
var misspellings = new ConcurrentBag<(int Index, string Word)>();

Parallel.ForEach (wordsToTest, (word, state, i) =>
{
    if (!wordLookup.Contains (word))
        misspellings.Add (((int) i, word));
});
```

결과를 **스레드 안전한 컬렉션에 모아야 했다**는 점에 주목하라. 이것이 PLINQ에 비한 단점이다. PLINQ에 비한 장점은 인덱스 `Select` 쿼리 연산자를 적용하는 비용을 피한다는 것이다 — 인덱스 `ForEach`보다 인덱스 `Select`가 덜 효율적이다.

### `ParallelLoopState` — 루프에서 일찍 빠져나오기

병렬 `For`나 `ForEach`의 루프 본문은 델리게이트이므로 `break` 문으로 루프를 일찍 빠져나올 수 없다. 대신 `ParallelLoopState` 객체의 `Break`나 `Stop`을 호출해야 한다.

```csharp
public class ParallelLoopState
{
    public void Break();
    public void Stop();

    public bool IsExceptional { get; }
    public bool IsStopped { get; }
    public long? LowestBreakIteration { get; }
    public bool ShouldExitCurrentIteration { get; }
}
```

`ParallelLoopState`를 얻는 것은 쉽다. `For`와 `ForEach`의 모든 버전이 `Action<TSource, ParallelLoopState>` 타입의 루프 본문을 받도록 오버로드되어 있다.

```csharp
foreach (char c in "Hello, world")     Parallel.ForEach ("Hello, world", (c, loopState) =>
    if (c == ',')                →     {
        break;                             if (c == ',')
    else                                       loopState.Break();
        Console.Write (c);                 else
                                               Console.Write (c);
                                       });
                                       // 출력 예: Hlloe
```

출력에서 보듯 루프 본문은 **무작위 순서로 완료될 수 있다.** 이 차이를 제외하면 `Break` 호출은 최소한 순차 실행과 같은 원소들을 산출한다. 위 예제는 항상 H, e, l, l, o를 (어떤 순서로든) 최소한 출력한다.

`Break` 대신 `Stop`을 호출하면 **모든 스레드가 현재 반복 직후 즉시 종료된다.** 위 예제에서 `Stop`을 호출하면 다른 스레드가 뒤처져 있을 경우 H, e, l, l, o의 부분집합만 얻을 수도 있다.

| | `Break()` | `Stop()` |
|---|---|---|
| 의미 | "현재 항목보다 뒤의 항목은 처리하지 마라" | "지금 당장 전부 멈춰라" |
| 보장 | 순차 루프가 처리했을 원소는 **모두** 처리된다 | 보장 없음 |
| 추가 처리 | 그보다 뒤의 항목이 이미 처리됐을 수 있다 | 현재 반복만 끝난다 |
| `LowestBreakIteration` | `Break`를 호출한 가장 낮은 항목 번호 | `null` |
| 쓰는 상황 | "N번째까지는 확실히 필요하다" | 찾던 것을 찾았거나 오류가 났고 결과를 보지 않을 때 |

`ForEach`가 항목 100개를 처리하도록 지시받았고 다섯 번째 항목을 처리하는 중에 `Break`가 호출되면, 루프는 `ForEach`가 반환하기 전에 **처음 다섯 항목이 처리되도록 보장한다.** 다만 추가 항목들이 처리됐을 수도 있다.

### `ShouldExitCurrentIteration`과 `IsExceptional`

루프 본문이 길다면, 이른 `Break`나 `Stop`이 있을 때 다른 스레드들도 메서드 본문 중간에서 빠져나오게 하고 싶을 수 있다. 코드 여러 곳에서 `ShouldExitCurrentIteration` 속성을 폴링하면 된다. 이 속성은 `Stop` 직후에, 또는 `Break` 직후 곧 `true`가 된다.

`ShouldExitCurrentIteration`은 다음 경우에도 `true`가 된다.

- `Stop`이 호출되었다
- `Break`가 호출되었다
- `ParallelOptions.CancellationToken`이 참조하는 `CancellationTokenSource`가 취소되었다
- 어떤 항목의 처리가 처리되지 않은 예외를 냈다

`IsExceptional`은 다른 스레드에서 예외가 발생했는지 알려 준다. 처리되지 않은 예외는 **각 스레드의 현재 반복 이후 루프를 멈추게 한다.** 이를 피하려면 코드에서 예외를 명시적으로 처리해야 한다.

### `ParallelLoopResult`

`Parallel.For`와 `Parallel.ForEach`는 `ParallelLoopResult` 구조체를 반환한다.

```csharp
public struct ParallelLoopResult
{
    // 연산이 조기 종료되었으면 false를 반환한다
    public bool IsCompleted { get; }
    public long? LowestBreakIteration { get; }
}
```

| `IsCompleted` | `LowestBreakIteration` | 의미 |
|---|---|---|
| `true` | `null` | 루프가 완주했고 모든 항목이 처리되었다 |
| `false` | `null` | 어떤 스레드가 `Stop`을 호출했다 |
| `false` | 값이 있음 | 어떤 스레드가 `Break`를 호출했고, 그 값은 **처리가 보장된 가장 낮은 항목의 인덱스**다 |

예외가 던져지면 `AggregateException`을 잡아 우아하게 복구해야 한다.

### `ParallelOptions`

```csharp
public class ParallelOptions
{
    public ParallelOptions();

    // 연산의 취소를 허용한다
    public CancellationToken CancellationToken { get; set; }   // 기본값 = CancellationToken.None

    // 동시에 처리될 수 있는 작업 항목의 최대 개수를 지정한다
    public int MaxDegreeOfParallelism { get; set; }            // 기본값 = -1 (사용 가능한 CPU 수)

    // 어느 TaskScheduler를 쓸지 지정한다
    public TaskScheduler TaskScheduler { get; set; }           // 기본값 = TaskScheduler.Default
}
```

취소를 결합한 실제 코드는 이렇게 생겼다.

```csharp
private void ProcessFiles()
{
    // ParallelOptions 인스턴스에 CancellationToken을 담는다.
    ParallelOptions parOpts = new ParallelOptions();
    parOpts.CancellationToken = _cancelToken.Token;
    parOpts.MaxDegreeOfParallelism = Environment.ProcessorCount;

    string[] files = Directory.GetFiles (@".\TestPictures", "*.jpg",
                                         SearchOption.AllDirectories);
    string outputDirectory = @".\ModifiedPictures";
    Directory.CreateDirectory (outputDirectory);

    try
    {
        Parallel.ForEach (files, parOpts, currentFile =>
        {
            parOpts.CancellationToken.ThrowIfCancellationRequested();
            // ... 파일을 처리한다 ...
        });
    }
    catch (OperationCanceledException ex)
    {
        Console.WriteLine (ex.Message);
    }
}
```

> **⚠️ 취소 토큰은 두 곳에서 각각 역할이 다르다**
>
> `ParallelOptions.CancellationToken`에 토큰을 넣으면 **`Parallel`이 아직 시작하지 않은 작업 항목을 배정하지 않는다.** 하지만 **이미 실행 중인 본문은 스스로 토큰을 관찰하지 않으면 끝까지 실행된다.**
>
> 그래서 본문 안에서 `ThrowIfCancellationRequested()`를 호출해야 응답성 있는 취소가 된다. 두 가지를 다 해야 한다는 것이 핵심이다.
>
> 그리고 취소로 루프가 끝나면 `Parallel.ForEach`는 `AggregateException`이 아니라 **`OperationCanceledException`을 던진다.** 취소는 예외가 아니라 정상적인 종료 경로로 취급되기 때문이다(50.9절).

### 지역 값 최적화 — `localInit` / `body` / `localFinally`

`Parallel.For`와 `Parallel.ForEach`는 각각 `TLocal`이라는 제네릭 타입 인자를 가진 오버로드 집합을 제공한다. 반복 집약적 루프에서 데이터 병합을 최적화하도록 설계되었다. 가장 단순한 형태는 다음과 같다.

```csharp
public static ParallelLoopResult For <TLocal> (
    int fromInclusive,
    int toExclusive,
    Func <TLocal> localInit,
    Func <int, ParallelLoopState, TLocal, TLocal> body,
    Action <TLocal> localFinally);
```

세 델리게이트가 하는 일은 이렇다.

- **`localInit`** — 작업에 참여하는 **각 태스크마다 한 번** 호출된다. 태스크가 작업 항목을 처리하도록 요청받기 전에 호출된다.
- **`body`** — 작업에 참여하는 여러 스레드가 처리하는 **각 항목마다 한 번** 호출된다.
- **`localFinally`** — 참여하는 **각 태스크마다 한 번** 호출된다. 태스크가 자신에게 배정된 모든 작업 항목을 처리한 뒤 호출된다. **본문 델리게이트 코드가 처리되지 않은 예외를 겪어도 호출된다.**

디렉터리 안 모든 파일의 바이트 수를 더하는 예제다.

```csharp
private static long DirectoryBytes (string path, string searchPattern,
                                    SearchOption searchOption)
{
    var files = Directory.EnumerateFiles (path, searchPattern, searchOption);
    long masterTotal = 0;

    ParallelLoopResult result = Parallel.ForEach<string, long> (
        files,

        () => 0,                        // localInit: 시작 시 태스크당 한 번 호출
                                        // 이 태스크가 본 바이트 수를 0으로 초기화

        (file, loopState, index, taskLocalTotal) =>   // body: 작업 항목당 한 번
        {
            // 이 파일의 크기를 얻어 이 태스크의 누적 합계에 더한다
            long fileLength = 0;
            FileStream fs = null;
            try
            {
                fs = File.OpenRead (file);
                fileLength = fs.Length;
            }
            catch (IOException) { /* 접근할 수 없는 파일은 무시한다 */ }
            finally { if (fs != null) fs.Dispose(); }

            return taskLocalTotal + fileLength;
        },

        taskLocalTotal =>               // localFinally: 종료 시 태스크당 한 번
        {
            // 이 태스크의 합계를 "마스터" 합계에 원자적으로 더한다
            Interlocked.Add (ref masterTotal, taskLocalTotal);
        });

    return masterTotal;
}
```

각 태스크는 자신에게 주어진 파일들에 대한 자체 누적 합계(`taskLocalTotal` 변수)를 유지한다. 각 태스크가 작업을 완료하면 `Interlocked.Add` 메서드를 호출해 마스터 합계를 스레드 안전하게 갱신한다(48.4절). 각 태스크가 자체 누적 합계를 가지므로 **항목 처리 중에는 스레드 동기화가 전혀 필요 없다.** 스레드 동기화는 성능을 해치므로 이는 좋은 일이다. `Interlocked.Add` 호출 비용은 **작업 항목당 한 번이 아니라 태스크당 한 번**만 발생한다.

> **💡 `TLocal` 오버로드는 실무에서 자주 필요하지 않다**
>
> 원천 자료의 평가가 정직하다 — "이 메서드들은 실무에서 거의 필요하지 않다. 대상 시나리오 대부분이 PLINQ로 커버되기 때문이다(다행이다, 이 오버로드들은 다소 위압적이니까)."
>
> 위 제곱근 합 예제는 PLINQ로 이렇게 쓸 수 있다.
>
> ```csharp
> ParallelEnumerable.Range (1, 10000000).Sum (i => Math.Sqrt (i))
> ```
>
> (`ParallelEnumerable`을 써서 범위 파티셔닝을 강제했다. 모든 숫자가 똑같이 오래 걸리므로 이 경우 성능이 개선된다.) 더 복잡한 시나리오에서는 `Sum` 대신 `Aggregate`를 쓸 수 있고, 지역 시드 팩토리를 제공하면 상황이 `Parallel.For`에 지역 값 함수를 제공하는 것과 다소 유사해진다.

### 파티셔닝 전략 — 짧은 본문이 문제인 이유

`Parallel.For`는 기본적으로 **범위 파티셔너**를 쓴다. 반복 공간을 워커 태스크들에 청크 단위로 나눠 준다. 이 청크 크기는 런타임이 정하며, 워커가 청크를 다 처리하면 다음 청크를 가져온다.

문제는 **본문이 아주 짧을 때** 드러난다. 청크를 가져오는 조율 비용과 델리게이트 호출 비용이 본문 자체보다 커진다.

```csharp
double[] data = new double[100_000_000];
// 본문이 한 줄뿐 — 델리게이트 호출 비용이 본문보다 크다
Parallel.For (0, data.Length, i => data[i] = Math.Sqrt (i));
```

해법은 **수동 청킹**이다. `Partitioner.Create(from, to, rangeSize)`가 인덱스 범위를 `Tuple<int,int>`(또는 `Tuple<long,long>`) 시퀀스로 잘라 주고, 각 워커는 그 범위를 **평범한 `for` 루프로** 돈다.

```csharp
using System.Collections.Concurrent;

double[] data = new double[100_000_000];

Parallel.ForEach (
    Partitioner.Create (0, data.Length, rangeSize: 10_000),
    range =>
    {
        for (int i = range.Item1; i < range.Item2; i++)
            data[i] = Math.Sqrt (i);        // 델리게이트 호출은 청크당 한 번
    });
```

델리게이트 호출 횟수가 1억 번에서 1만 번으로 줄고, 안쪽 루프는 JIT이 최적화하기 좋은 평범한 `for` 루프가 된다.

| 상황 | 권장 |
|---|---|
| 본문이 밀리초 단위 | 기본 `Parallel.For` |
| 본문이 마이크로초 미만, 항목이 아주 많음 | `Partitioner.Create(from, to, rangeSize)`로 수동 청킹 |
| 항목마다 처리 시간이 크게 다름 | 청크(부하 분산) 파티셔닝 — `Partitioner.Create(source, loadBalance: true)` |
| 원소가 열거자에서만 나옴(파일 스트림 등) | `Parallel.ForEach`의 기본 동작 |

> **⚠️ `rangeSize`를 너무 크게 잡으면 부하 불균형이 난다**
>
> 청크가 크면 델리게이트 호출은 줄지만, 마지막에 한 워커만 큰 청크를 붙들고 나머지가 노는 **꼬리 지연(tail latency)** 이 생긴다. 실무적 시작점은 **`전체 항목 수 / (코어 수 × 4~16)`** 정도이고, 거기서부터 측정하며 조정하는 것이 안전하다.
>
> 그리고 이 수치는 반드시 **BenchmarkDotNet으로 측정**해야 한다(67.3절). 청킹은 캐시 지역성에도 영향을 주므로 직관이 잘 맞지 않는다.

## 50.7 `Parallel.ForEachAsync`

### I/O 바운드 병렬 처리의 올바른 도구

※.NET 6 / C# 10에서 `Parallel` 클래스에 `ForEachAsync` 메서드가 추가되었다. 이름이 시사하듯 메서드 자체가 비동기이며 **본문도 비동기 메서드**로 받는다.

이 메서드는 이 장에서 반복해 경고한 문제 — "I/O 바운드 작업을 `Parallel.ForEach`로 병렬화하지 마라" — 에 대한 **정식 해답**이다.

```csharp
public static Task ForEachAsync<TSource> (
    IEnumerable<TSource> source,
    Func<TSource, CancellationToken, ValueTask> body);

public static Task ForEachAsync<TSource> (
    IEnumerable<TSource> source,
    ParallelOptions parallelOptions,
    Func<TSource, CancellationToken, ValueTask> body);

// IAsyncEnumerable<T> 오버로드도 있다
public static Task ForEachAsync<TSource> (
    IAsyncEnumerable<TSource> source,
    ParallelOptions parallelOptions,
    Func<TSource, CancellationToken, ValueTask> body);
```

가장 단순한 사용 형태다.

```csharp
using var http = new HttpClient();
string[] urls = { "https://a.example", "https://b.example", /* ... */ };

await Parallel.ForEachAsync (urls, async (url, token) =>
{
    string content = await http.GetStringAsync (url, token);
    await File.WriteAllTextAsync (ToLocalPath (url), content, token);
});
```

`Parallel.ForEach`에서 옮겨 오는 것은 기계적이다. 처음 두 매개변수는 같고, 본문이 **두 매개변수(현재 항목과 취소 토큰)** 를 받는 비동기 람다로 바뀐다.

```csharp
// 이전 코드:
// Parallel.ForEach (files, parOpts, currentFile =>

// 새 코드:
await Parallel.ForEachAsync (files, parOpts, async (currentFile, token) =>
```

본문에 전달되는 취소 토큰은 `ParallelOptions` 인스턴스에 있는 것과 **같은 토큰**이다. 따라서 `ParallelOptions` 쪽이 아니라 매개변수 쪽 토큰을 확인하면 된다.

```csharp
// 이전 코드:
// parOpts.CancellationToken.ThrowIfCancellationRequested();

// 새 코드:
token.ThrowIfCancellationRequested();
```

### `MaxDegreeOfParallelism`의 의미가 다르다

여기가 이 절에서 가장 중요한 지점이다.

> **⚠️ `ForEachAsync`의 `MaxDegreeOfParallelism`은 스레드 개수가 아니라 동시 실행 개수다**
>
> `Parallel.ForEach`에서 `MaxDegreeOfParallelism = 8`은 "최대 8개의 워커 태스크가 동시에 본문을 실행한다"는 뜻이고, 본문이 동기 블로킹을 하면 실제로 **스레드 8개가 묶인다.**
>
> `Parallel.ForEachAsync`에서 `MaxDegreeOfParallelism = 8`은 "**진행 중인(in-flight) 비동기 연산이 최대 8개**"라는 뜻이다. 그 8개가 전부 `await` 상태로 네트워크 응답을 기다리는 동안 **스레드는 0개가 묶인다.** 완료 콜백이 도착할 때만 풀 스레드를 잠깐 쓴다.
>
> 이 차이 때문에 `ForEachAsync`에서는 `MaxDegreeOfParallelism`을 코어 수보다 훨씬 크게 — 예컨대 50이나 100으로 — 잡는 것이 **정상이고 권장된다.** 이때의 상한은 CPU가 아니라 **상대 서버의 수용량, 커넥션 풀 크기, 레이트 리밋**이 정한다.

```csharp
var options = new ParallelOptions
{
    MaxDegreeOfParallelism = 32,       // 동시 요청 32개. 스레드 32개가 아니다
    CancellationToken = cts.Token
};

await Parallel.ForEachAsync (urls, options, async (url, ct) =>
{
    using var response = await http.GetAsync (url, ct);
    response.EnsureSuccessStatusCode();
});
```

> **📌 기본값은 `Environment.ProcessorCount`다**
>
> `MaxDegreeOfParallelism`을 지정하지 않으면 `ForEachAsync`도 프로세서 수를 기본값으로 쓴다. I/O 바운드 작업에서는 이 기본값이 **너무 작은** 경우가 많으므로, 이 메서드를 쓸 때는 값을 명시적으로 정하는 습관을 들이는 편이 낫다.

### `IAsyncEnumerable<T>` 지원

`ForEachAsync`는 `IEnumerable<T>`뿐 아니라 **`IAsyncEnumerable<T>`** 도 소스로 받는다. 비동기 스트림에서 항목이 나오는 대로 병렬로 처리할 수 있다는 뜻이다.

```csharp
async IAsyncEnumerable<int> GenerateSequence()
{
    for (int i = 0; i < 20; i++)
    {
        await Task.Delay (100);
        yield return i;
    }
}

await Parallel.ForEachAsync (GenerateSequence(), options, async (n, ct) =>
{
    await ProcessAsync (n, ct);
});
```

이는 `Parallel.ForEach`로는 불가능한 일이다. `Parallel.ForEach`는 동기 열거자만 받으므로, 비동기 스트림을 넘기려면 먼저 전부 메모리에 모아야 한다.

> **📌 비동기 스트림 자체는 47.11절에 있다**
>
> `IAsyncEnumerable<T>`와 `await foreach`의 문법, `async` 반복자가 만드는 상태 기계는 47장에서 다뤘다. 여기서 중요한 것은 **비동기 소스를 그대로 병렬 처리할 수 있는 유일한 `Parallel` 메서드**라는 사실이다.

### 취소와 예외

`ForEachAsync`는 `Task`를 반환하므로 `await`한다. 예외 처리 의미론은 `await`의 규칙을 따른다.

- 본문에서 예외가 나면 **남은 항목의 처리가 중단된다.**
- 여러 항목이 동시에 실패할 수 있으므로 예외는 내부적으로 **취합되어 `AggregateException`** 에 담긴다.
- 그런데 `await`는 32.13절에서 본 것처럼 **첫 내부 예외만 다시 던진다.** 전부를 보려면 반환된 `Task`의 `Exception` 속성을 봐야 한다.

```csharp
Task t = Parallel.ForEachAsync (urls, options, BodyAsync);
try
{
    await t;
}
catch (Exception)
{
    // await 는 첫 내부 예외만 던진다.
    // 전부 보려면 Task 의 Exception 을 본다.
    foreach (var e in t.Exception!.Flatten().InnerExceptions)
        Log (e);
}
```

취소는 `ParallelOptions.CancellationToken`으로 넣는다. 취소되면 반환 태스크가 **취소 상태**가 되고 `await` 시 `OperationCanceledException`(또는 그 하위 타입인 `TaskCanceledException`)이 던져진다.

### `ForEach`와 `ForEachAsync` 비교

| | `Parallel.ForEach` | `Parallel.ForEachAsync` |
|---|---|---|
| 도입 | .NET Framework 4.0 | ※.NET 6 |
| 대상 | **CPU 바운드** | **I/O 바운드** (CPU 바운드에도 쓸 수 있으나 이점 없음) |
| 반환 | `ParallelLoopResult` (블로킹) | `Task` (`await` 대상) |
| 본문 | `Action<T>` 계열 | `Func<T, CancellationToken, ValueTask>` |
| 비동기 람다 | **불가** (`async void`가 되어 예외가 유실된다) | 가능 |
| `MaxDegreeOfParallelism` | 워커 태스크 수 ≈ 스레드 수 | **동시 진행 연산 수** |
| 소스 | `IEnumerable<T>` | `IEnumerable<T>` + **`IAsyncEnumerable<T>`** |
| 조기 탈출 | `ParallelLoopState.Break`/`Stop` | **없음** — 취소 토큰으로 처리 |
| 지역 값 최적화 | `localInit`/`localFinally` 있음 | **없음** |
| 예외 | `AggregateException` 즉시 던짐 | `Task`에 취합, `await`는 첫 예외만 |

> **⚠️ `Parallel.ForEach`에 비동기 람다를 넘기는 것은 조용한 재앙이다**
>
> ```csharp
> Parallel.ForEach (urls, async url =>        // ⚠ async void 람다가 된다
> {
>     await http.GetStringAsync (url);
> });
> ```
>
> `Parallel.ForEach`의 본문은 `Action<T>`다. 여기에 `async` 람다를 넘기면 컴파일러가 **`async void`** 로 해석한다(47.14절). 결과는 셋이다.
>
> 1. `Parallel.ForEach`는 첫 `await`에서 본문이 "끝났다"고 판단하고 즉시 다음 항목으로 넘어간다 — **동시성 제한이 전혀 걸리지 않는다.**
> 2. `Parallel.ForEach`가 반환되어도 **작업은 아직 진행 중**이다.
> 3. 본문에서 난 예외는 `AggregateException`에 취합되지 않고 **`async void`의 규칙에 따라 스레드 풀 스레드에서 다시 던져져 프로세스를 죽인다.**
>
> 컴파일 오류도 경고도 나지 않는다. .NET 6 이상이면 `ForEachAsync`로, 그 이하면 `SemaphoreSlim` + `Task.WhenAll`로 써야 한다.

> **💡 세 가지 동시성 제한 관용구 중 무엇을 고를 것인가**
>
> | 도구 | 언제 |
> |---|---|
> | `Parallel.ForEachAsync` | 컬렉션의 각 항목에 같은 비동기 작업을 하고, 결과를 모을 필요가 적을 때 — **가장 단순** |
> | `SemaphoreSlim` + `Task.WhenAll` | 각 작업의 **결과가 필요**하거나 항목마다 다른 작업을 할 때(48.11절) |
> | `Channel<T>` 파이프라인 | 생산과 소비의 속도가 다르고 **백프레셔**가 필요할 때(51.1절, 51.2절) |
>
> 세 번째로 갈수록 유연하지만 코드가 길어진다. 위에서부터 시도해서 부족할 때 아래로 내려가라.

## 50.8 태스크 병렬성 — 생성·대기·취소·연속

태스크 병렬성은 PFX에서 **가장 낮은 수준**의 병렬화 접근이다. 이 수준에서 다루는 클래스들은 `System.Threading.Tasks` 네임스페이스에 정의되어 있다.

| 클래스 | 목적 |
|---|---|
| `Task` | 작업 단위를 관리 |
| `Task<TResult>` | 반환값이 있는 작업 단위를 관리 |
| `TaskFactory` | 태스크를 생성 |
| `TaskFactory<TResult>` | 같은 반환 타입의 태스크와 연속을 생성 |
| `TaskScheduler` | 태스크의 스케줄링을 관리 |
| `TaskCompletionSource` | 태스크의 워크플로를 수동으로 제어 |

이 타입들의 기본 사용법 — `Task.Run`, `Task.Factory.StartNew`, `TaskCreationOptions`, `ContinueWith`, `TaskContinuationOptions`, `TaskScheduler`, `TaskCompletionSource`, 협력적 취소 — 은 **46장에서 전수했다.** 여기서는 반복하지 않고 **병렬 맥락에서만 의미가 있는 세 가지**에 집중한다.

- 부모/자식 태스크 관계
- 연속 체이닝으로 의존 그래프 만들기
- 분할 정복(divide and conquer) 패턴

> **⚠️ 태스크를 수백만 개 만들지 마라**
>
> TPL은 수백(심지어 수천) 개의 태스크를 최소한의 오버헤드로 만들 수 있게 해 준다. **하지만 수백만 개의 태스크를 만들고 싶다면 효율을 유지하기 위해 그 태스크들을 더 큰 작업 단위로 분할해야 한다.** `Parallel` 클래스와 PLINQ는 이 일을 자동으로 한다.
>
> 이것이 50.6절에서 본 수동 청킹과 같은 원리다. 태스크 하나의 생성·스케줄링 비용은 작지만 0은 아니고, 본문이 그보다 작으면 전부 오버헤드가 된다.

### 부모/자식 태스크 — `AttachedToParent`

한 태스크가 다른 태스크를 시작할 때 선택적으로 부모-자식 관계를 맺을 수 있다.

```csharp
Task parent = Task.Factory.StartNew (() =>
{
    Console.WriteLine ("나는 부모다");

    Task.Factory.StartNew (() =>              // 분리된(detached) 태스크
    {
        Console.WriteLine ("나는 분리되었다");
    });

    Task.Factory.StartNew (() =>              // 자식 태스크
    {
        Console.WriteLine ("나는 자식이다");
    }, TaskCreationOptions.AttachedToParent);
});
```

자식 태스크가 특별한 이유는 **부모 태스크의 완료를 기다릴 때 자식들도 함께 기다린다**는 점이다. 그 시점에 자식의 예외들이 위로 전파된다.

```csharp
TaskCreationOptions atp = TaskCreationOptions.AttachedToParent;

var parent = Task.Factory.StartNew (() =>
{
    Task.Factory.StartNew (() =>              // 자식
    {
        Task.Factory.StartNew (() => { throw null; }, atp);   // 손자
    }, atp);
});

// 다음 호출은 (중첩된 AggregateException으로 감싸진)
// NullReferenceException 을 던진다:
parent.Wait();
```

이 중첩이 `AggregateException.Flatten()`이 필요한 이유다(32.13절, 50.9절).

> **📌 `Task.Run`은 자식 붙이기를 거부한다**
>
> 46.3절에서 본 것처럼 `Task.Run`은 `TaskCreationOptions.DenyChildAttach`를 적용하지만 `Task.Factory.StartNew`는 적용하지 않는다. 그래서 부모/자식 관계를 만들려면 **`StartNew`를 써야 한다.**
>
> 반대로 말하면, `Task.Run`으로 만든 태스크 안에서 누군가 `AttachedToParent`로 태스크를 만들어도 **붙지 않는다.** 라이브러리 코드를 호출할 때 완료 시점이 예측 가능해지는 장점이 있다.

연속과 결합하면 강력해진다. **연속은 모든 자식 태스크가 완료된 뒤에야 실행되며**, 그 시점에 자식들이 던진 예외가 연속으로 마셜링된다.

```csharp
TaskCreationOptions atp = TaskCreationOptions.AttachedToParent;

Task.Factory.StartNew (() =>
{
    Task.Factory.StartNew (() => { throw null; }, atp);
    Task.Factory.StartNew (() => { throw null; }, atp);
    Task.Factory.StartNew (() => { throw null; }, atp);
})
.ContinueWith (p => Console.WriteLine (p.Exception),
               TaskContinuationOptions.OnlyOnFaulted);
```

자식 태스크 셋이 각각 `NullReferenceException`을 던지고, 부모에 대한 연속 하나로 셋을 한꺼번에 잡는다.

### 연속으로 의존 그래프 만들기

`Parallel.Invoke`가 표현할 수 있는 것은 "이것들을 전부 병렬로 실행하고 기다려라"뿐이다. 실제 작업에는 **의존 관계**가 있다.

```text
        ┌───────┐
        │ Load  │
        └───┬───┘
      ┌─────┴─────┐
      ▼           ▼
  ┌───────┐   ┌───────┐
  │Parse A│   │Parse B│      ← 서로 독립. 병렬 실행 가능
  └───┬───┘   └───┬───┘
      └─────┬─────┘
            ▼
        ┌───────┐
        │ Merge │            ← 둘 다 끝나야 시작
        └───┬───┘
            ▼
        ┌───────┐
        │ Write │
        └───────┘
```

이 그래프를 연속으로 표현한다.

```csharp
Task<Raw> load = Task.Run (() => LoadRaw (path));

Task<Parsed> parseA = load.ContinueWith (t => ParseA (t.Result));
Task<Parsed> parseB = load.ContinueWith (t => ParseB (t.Result));

Task<Merged> merge = Task.Factory.ContinueWhenAll (
    new[] { parseA, parseB },
    tasks => Merge (tasks[0].Result, tasks[1].Result));

Task write = merge.ContinueWith (t => Write (t.Result));
write.Wait();
```

`TaskFactory`의 `ContinueWhenAll`과 `ContinueWhenAny`는 여러 선행 태스크의 완료에 기반해 연속을 스케줄한다. 다만 46.9절의 태스크 합성기(`WhenAll`, `WhenAny`)가 도입되면서 **이 메서드들은 사실상 불필요해졌다.**

```csharp
// 같은 결과를 WhenAll 로:
Task<Merged> merge = Task.WhenAll (parseA, parseB)
    .ContinueWith (t => Merge (parseA.Result, parseB.Result));
```

> **💡 오늘날 이 그래프의 가장 좋은 표현은 `async` 메서드다**
>
> ```csharp
> async Task RunPipelineAsync (string path)
> {
>     Raw raw = await Task.Run (() => LoadRaw (path));
>
>     Task<Parsed> a = Task.Run (() => ParseA (raw));
>     Task<Parsed> b = Task.Run (() => ParseB (raw));
>     await Task.WhenAll (a, b);
>
>     Merged merged = Merge (a.Result, b.Result);
>     await Task.Run (() => Write (merged));
> }
> ```
>
> 의존 그래프가 **코드의 제어 흐름 그대로** 읽힌다. 연속 체이닝은 (1) `async`를 쓸 수 없는 곳, (2) 조건부 연속(`OnlyOnFaulted` 등)이 필요한 곳, (3) 스케줄러를 태스크마다 다르게 지정해야 하는 곳에서만 쓸 이유가 있다.
>
> 연속의 조건부 플래그와 그 함정(연속이 실행되지 않으면 "취소"된다는 것)은 46.4절에서 다뤘다.

### 분할 정복 패턴

병렬화하기 어려운 문제의 대표가 정렬이다. 원천 자료가 든 예 그대로 — "당황스러울 만큼 병렬적이지 않은 문제의 예는 최적화된 퀵정렬 구현이다. 좋은 결과를 얻으려면 생각이 좀 필요하고 비구조적 병렬성이 필요할 수 있다."

분할 정복 알고리즘은 문제를 재귀적으로 쪼갠다. 쪼개진 하위 문제들이 서로 독립적이므로 **재귀 호출을 병렬화**할 수 있다.

```csharp
static void ParallelQuickSort (int[] a, int lo, int hi, int depth)
{
    if (hi - lo < SequentialThreshold || depth <= 0)
    {
        SequentialQuickSort (a, lo, hi);      // 임계 크기 아래에서는 순차로
        return;
    }

    int p = Partition (a, lo, hi);

    Parallel.Invoke (
        () => ParallelQuickSort (a, lo, p - 1, depth - 1),
        () => ParallelQuickSort (a, p + 1, hi, depth - 1));
}
```

이 코드의 핵심은 세 가지다.

**1. 임계 크기 아래에서 순차로 전환한다.** `SequentialThreshold`(예: 원소 2,048개)보다 작은 조각은 태스크를 만들지 않고 그냥 순차 정렬한다. 조각이 작아질수록 태스크 생성 비용이 정렬 비용을 압도하기 때문이다. **이 전환이 없으면 병렬 퀵정렬은 순차 퀵정렬보다 훨씬 느리다.**

**2. 재귀 깊이를 제한한다.** `depth` 매개변수로 병렬 분기 깊이를 제한한다. 초기값은 보통 `log2(Environment.ProcessorCount)` 언저리로 잡는다. 코어가 8개인데 깊이 20까지 분기하면 태스크 100만 개가 만들어진다.

**3. 두 하위 문제가 배열의 겹치지 않는 구간을 만진다.** 그래서 잠금이 없다. 분할 정복이 병렬화에 잘 맞는 이유가 정확히 이것이다.

> **⚠️ 재귀적 `Parallel.Invoke`에서 임계값을 빼먹는 것이 이 패턴의 1번 실수다**
>
> "재귀 호출을 `Parallel.Invoke`로 감쌌더니 오히려 느려졌다"는 보고의 거의 전부가 임계값 부재다. 원소 두 개짜리 조각을 정렬하려고 태스크를 두 개 만드는 코드를 상상해 보라.
>
> 임계값의 적정 크기는 원소 하나 처리 비용에 반비례한다. 정수 비교처럼 싼 작업이면 수천 개, 객체 비교처럼 비싼 작업이면 수십 개가 될 수도 있다. **측정으로 정하라.**

> **📌 병합 정렬은 왜 다른가**
>
> 병합 정렬도 분할 정복이지만 **병합 단계에서 여분의 배열이 필요**하다. 분할은 병렬화되지만 병합은 순차적이거나 별도의 병렬 병합 알고리즘이 필요하다. 암달의 법칙(50.1절)이 여기서 직접 작동한다 — 병합 단계가 직렬 비율이 된다.
>
> 실무에서는 정렬을 직접 병렬화하기 전에 `Array.Sort`(내부적으로 잘 최적화된 인트로소트)와 PLINQ의 `OrderBy`를 먼저 벤치마크하라. 대부분의 경우 직접 짠 병렬 정렬이 지지 않으면 다행인 수준이다.

## 50.9 병렬 코드의 예외 처리와 `AggregateException`

### 왜 예외를 감싸야 하는가

PLINQ, `Parallel` 클래스, `Task`는 예외를 자동으로 소비자에게 마셜링한다. 왜 이것이 필수인지 보려면 다음 LINQ 쿼리를 생각해 보자. 첫 반복에서 `DivideByZeroException`을 던진다.

```csharp
try
{
    var query = from i in Enumerable.Range (0, 1000000)
                select 100 / i;
    // ...
}
catch (DivideByZeroException)
{
    // ...
}
```

PLINQ에 이 쿼리를 병렬화하도록 요청했는데 예외 처리를 무시했다면, `DivideByZeroException`은 **별도의 스레드에서 던져져 `catch` 블록을 우회하고 애플리케이션을 죽였을 것이다.**

그래서 예외는 자동으로 잡혀 호출자에게 다시 던져진다. 그런데 단순히 `DivideByZeroException`을 잡는 것만큼 간단하지 않다. 이 라이브러리들은 많은 스레드를 쓰므로 **둘 이상의 예외가 동시에 던져지는 것이 실제로 가능하다.** 모든 예외가 보고되도록 예외들은 `AggregateException` 컨테이너에 감싸지고, 이 컨테이너는 잡힌 예외 각각을 담는 `InnerExceptions` 속성을 노출한다.

```csharp
try
{
    var query = from i in ParallelEnumerable.Range (0, 1000000)
                select 100 / i;
    // 쿼리를 열거한다
    // ...
}
catch (AggregateException aex)
{
    foreach (Exception ex in aex.InnerExceptions)
        Console.WriteLine (ex.Message);
}
```

`AggregateException`의 API 자체 — `InnerExceptions` vs `InnerException`, `Flatten()`, `Handle()`, `GetBaseException()` — 는 **32.13절에서 전수했다.** 여기서는 병렬 맥락에서만 나타나는 동작을 본다.

### 예외가 나면 나머지 반복은 어떻게 되는가

이것이 실무에서 가장 자주 묻는 질문이다.

**PLINQ와 `Parallel` 클래스 모두 첫 예외를 만나면 쿼리나 루프 실행을 종료한다** — 더 이상의 원소나 루프 본문을 처리하지 않음으로써. **그러나 현재 사이클이 완료되기 전에 더 많은 예외가 던져질 수 있다.**

정확히 표현하면 이렇다.

| 시점 | 동작 |
|---|---|
| 스레드 A의 반복 #17에서 예외 발생 | 그 예외가 내부에 기록된다 |
| 다른 스레드들 | **현재 실행 중인 반복은 끝까지 실행된다** |
| 그 사이에 스레드 B의 반복 #23에서도 예외 발생 | 이 예외도 함께 기록된다 |
| 아직 시작하지 않은 반복 | **배정되지 않는다** |
| `Parallel.ForEach` 반환 시 | 기록된 예외 전부를 담은 `AggregateException`을 던진다 |

그래서 다음 세 가지가 모두 참이다.

1. 예외가 나도 **일부 반복은 추가로 실행된다.**
2. `InnerExceptions`에 **여러 개**가 들어 있을 수 있다.
3. `AggregateException`의 **`InnerException`(단수)은 첫 예외**를 가리킨다.

> **⚠️ 부분 실행 상태를 정리하는 것은 전적으로 당신 몫이다**
>
> `Parallel.ForEach`가 항목 1,000개 중 300개를 처리하다 예외로 중단되면, **이미 처리된 300개의 부작용은 그대로 남는다.** 파일을 썼다면 파일이 남고, DB에 넣었다면 행이 남는다.
>
> 병렬 알고리즘이 문제 발생 시 롤백을 지원해야 한다면, 어떤 부작용이 발생했고 그 오류로부터 어떻게 복구할지 이해하기 위해 **더 많은 작업을 해야 한다.** 모든 알고리즘은 요구사항이 다르므로 병렬 환경의 예외 처리에 보편적인 답은 없다.
>
> 실무적으로는 (1) 본문을 멱등(idempotent)하게 만들거나, (2) 결과를 즉시 커밋하지 않고 모았다가 전부 성공했을 때만 반영하거나, (3) `ParallelLoopState.IsExceptional`을 폴링해 조기에 정리 경로로 빠지는 세 가지 중 하나를 택한다.

`ParallelLoopState`를 쓰면 다른 스레드의 실패를 감지할 수 있다(50.6절).

```csharp
Parallel.ForEach (items, (item, state) =>
{
    if (state.IsExceptional) return;          // 다른 스레드가 이미 실패했다
    if (state.ShouldExitCurrentIteration) return;

    Process (item);
});
```

### PLINQ의 예외 취합과 그 함정

PLINQ에는 순차 LINQ와 결정적으로 다른 점이 하나 더 있다.

일반적인 LINQ 쿼리에서는 **쿼리 결과를 사용하는 코드**에만 `try`/`catch`를 두면 된다. 쿼리 식을 정의하는 코드 주위에는 필요 없다 — 지연 실행이기 때문이다.

```csharp
var nums = from n in data
           where n < 150
           select Factorial (n);
try
{
    foreach (var item in nums)           // 여기서 실제로 실행된다
        Console.WriteLine (item);
}
catch (InvalidOperationException inv) { /* ... */ }
```

**PLINQ가 관련되면 쿼리 정의도 `try`/`catch` 블록 안에 넣어야 한다.** 백그라운드 스레드들이 스케줄러가 허락하는 즉시 결과를 만들기 시작하기 때문이다. 즉시는 아니지만 아주 곧이다.

그리고 물론, PLINQ를 쓰면 **원래 기대하던 예외 대신 `AggregateException`을 잡아야 한다.** 이는 파이프라이닝·Stop & Go·역열거 어느 알고리즘을 쓰든 마찬가지다.

> **⚠️ `catch (InvalidOperationException)`이 `AsParallel()` 하나로 죽는다**
>
> 순차 LINQ에서 잘 동작하던 예외 처리 코드에 `AsParallel()`을 추가하면, **`catch` 블록이 더 이상 잡지 못한다.** 실제 예외가 `AggregateException` 안에 들어가기 때문이다.
>
> 컴파일 오류도 경고도 나지 않는다. 예외가 발생하기 전까지는 아무 문제도 보이지 않는다. **`AsParallel()`을 추가할 때는 그 주변의 모든 `catch` 절을 반드시 다시 읽어라.**

### 취소와 예외의 구분

병렬 코드에서 "실패"와 "취소"는 다른 사건이며 다르게 표현된다.

| 사건 | 결과 |
|---|---|
| 본문에서 임의의 예외 | `AggregateException` (내부에 실제 예외) |
| 본문에서 `token.ThrowIfCancellationRequested()` — 토큰이 `ParallelOptions`/`WithCancellation`의 것과 **일치** | **`OperationCanceledException`** (감싸지지 않음) |
| 본문에서 `OperationCanceledException`을 직접 던짐 — 토큰이 **불일치** | `AggregateException` (실패로 취급) |
| `Task`가 일치하는 토큰으로 취소 | `Task.Status == Canceled`, `Wait()`는 `AggregateException`에 담긴 `TaskCanceledException` |

46.8절에서 본 협력적 취소 프로토콜의 핵심 규칙이 여기서 다시 나온다. **던지는 `OperationCanceledException`의 `CancellationToken` 속성이 API에 넘긴 토큰과 일치해야만 "취소"로 인정된다.** 일치하지 않으면 그냥 실패한 것이다.

```csharp
// 올바른 방법 — 토큰이 자동으로 붙는다
token.ThrowIfCancellationRequested();

// 직접 던질 때는 토큰을 생성자에 반드시 넘겨야 한다
throw new OperationCanceledException (token);

// ⚠ 이렇게 하면 취소가 아니라 실패로 취급된다
throw new OperationCanceledException();
```

`TaskCanceledException`은 `OperationCanceledException`의 하위 클래스다. 토큰을 넘기지 않으면 태스크가 `TaskStatus.Canceled` 상태로 끝나지 않고 `OnlyOnCanceled` 연속도 트리거되지 않는다.

### `Flatten`과 `Handle` — 병렬 맥락에서

부모/자식 태스크(50.8절)나 중첩된 병렬 연산은 `AggregateException` 안에 `AggregateException`을 만든다. 병렬 연산이 많을수록 이 중첩이 깊어질 수 있다. 게다가 병렬 연산들이 서로 합성되는 방식 때문에 **최종 예외 컬렉션에 원래 예외의 복사본이 여러 개** 들어갈 수도 있다.

`Flatten()`을 먼저 부르는 것이 사실상 필수다.

```csharp
catch (AggregateException aex)
{
    foreach (Exception ex in aex.Flatten().InnerExceptions)
        myLogWriter.LogException (ex);
}
```

`Handle`은 특정 예외 타입만 잡고 나머지는 다시 던지고 싶을 때 쓴다. 모든 내부 예외에 대해 실행되는 예외 술어를 받는다.

```csharp
var parent = Task.Factory.StartNew (() =>
{
    // 자식 태스크 셋으로 예외 셋을 한 번에 던진다:
    int[] numbers = { 0 };
    var childFactory = new TaskFactory (
        TaskCreationOptions.AttachedToParent, TaskContinuationOptions.None);

    childFactory.StartNew (() => 5 / numbers[0]);   // 0으로 나누기
    childFactory.StartNew (() => numbers [1]);      // 인덱스 범위 초과
    childFactory.StartNew (() => { throw null; });  // 널 참조
});

try { parent.Wait(); }
catch (AggregateException aex)
{
    aex.Flatten().Handle (ex =>          // Flatten 호출이 여전히 필요하다
    {
        if (ex is DivideByZeroException)
        {
            Console.WriteLine ("0으로 나누기");
            return true;                 // 이 예외는 "처리됨"
        }
        if (ex is IndexOutOfRangeException)
        {
            Console.WriteLine ("인덱스 범위 초과");
            return true;                 // 이 예외는 "처리됨"
        }
        return false;                    // 나머지는 모두 다시 던져진다
    });
}
```

술어가 모든 예외에 대해 `true`를 반환했다면 예외는 다시 던져지지 않는다. `false`가 하나라도 있으면 그 예외들을 담은 **새 `AggregateException`이 만들어져 다시 던져진다.**

> **💡 하나만 골라 던지지 마라**
>
> 처리되지 않은 예외 하나만 던지는 대신 원래 `AggregateException`을 다시 던지는 이유가 있다. 컬렉션에서 예외 하나만 뽑아 던지면 **중요한 정보를 잃을 수 있다.** `InnerExceptions`에는 임의 개수의 예외가 있을 수 있고, 그중 둘 이상이 예상하지 못한 타입일 수 있다.
>
> 많은 경우 `InnerExceptions`에 예외가 하나뿐일 것이다. **그렇다고 그렇게 가정하고 코드를 쓰면 안 된다.** 그 추가 정보가 정말 필요한 날, 거기 없을 것이기 때문이다.

> **💡 가장 좋은 계획은 예외가 병렬 태스크를 빠져나가지 못하게 하는 것이다**
>
> 원천 자료의 결론이다. 백그라운드 작업을 실행하는 코드를 고쳐 **예외가 백그라운드 태스크를 빠져나갈 수 없게** 만드는 것이 거의 모든 경우에 낫다.
>
> 단, 모든 예외를 잡으라는 뜻은 아니다. **복구할 수 있는 예외만 잡아야 한다.** 다운로드 예제라면 원격 호스트가 응답하지 않는다는 `HttpRequestException`은 합리적으로 복구 가능하지만, 다른 예외 타입은 더 심각한 문제를 뜻하므로 계속 예외를 발생시켜 모든 처리를 중단해야 한다.
>
> 그래도 `AggregateException`이 던져질 때 무슨 일이 일어나는지는 여전히 처리해야 한다. 그것을 치명적 오류로 취급하는 것만으로 충분할 수도 있다.

### 어느 API가 무엇을 던지는가

| API | 성공 실패 시 던지는 것 |
|---|---|
| `Parallel.For` / `ForEach` / `Invoke` | `AggregateException` |
| `Parallel.ForEachAsync` (`await` 시) | **첫 내부 예외** (`Task.Exception`에는 `AggregateException`) |
| PLINQ 쿼리 (열거 시) | `AggregateException` |
| `task.Wait()` / `task.Result` | `AggregateException` |
| `Task.WaitAll(...)` | `AggregateException` (모든 태스크를 끝까지 기다린 뒤) |
| `await task` | **첫 내부 예외** (감싸지 않음) |
| 취소 (일치하는 토큰) | `OperationCanceledException` |

> **📌 `WaitAll`은 감싸지만 끝까지 기다린다**
>
> `Task.WaitAll`은 각 태스크를 차례로 기다리는 것과 비슷하지만, 컨텍스트 스위치가 (최대) 한 번만 필요해서 더 효율적이다. 또한 태스크 하나 이상이 처리되지 않은 예외를 던져도 **`WaitAll`은 여전히 모든 태스크를 끝까지 기다린다.** 그런 다음 실패한 각 태스크의 예외를 누적한 `AggregateException`을 다시 던진다. 이것이 `AggregateException`이 진정으로 유용한 지점이다.

## 50.10 동시성 컬렉션 — `IProducerConsumerCollection<T>`, `ConcurrentBag<T>`

.NET은 `System.Collections.Concurrent` 네임스페이스에 스레드 안전한 컬렉션을 제공한다.

| 동시성 컬렉션 | 비동시성 대응물 |
|---|---|
| `ConcurrentStack<T>` | `Stack<T>` |
| `ConcurrentQueue<T>` | `Queue<T>` |
| `ConcurrentBag<T>` | (없음) |
| `ConcurrentDictionary<TKey,TValue>` | `Dictionary<TKey,TValue>` |

24.12절에서 이 타입들의 **선택 기준**을 다뤘다. 여기서는 **내부 구조와 계약**을 판다.

### 다섯 가지 주의사항

동시성 컬렉션은 고도의 동시성 시나리오에 최적화되어 있지만, 평범한 컬렉션에 잠금을 거는 대안으로도 유용하다. 다만 다음을 알아야 한다.

**1. 고도의 동시성 시나리오가 아닌 모든 경우에 전통적 컬렉션이 동시성 컬렉션을 능가한다.**

**2. 스레드 안전한 컬렉션이 그것을 쓰는 코드가 스레드 안전함을 보장하지는 않는다.**

**3. 다른 스레드가 수정하는 동안 동시성 컬렉션을 열거해도 예외가 던져지지 않는다.** 대신 옛 내용과 새 내용이 섞인 결과를 얻는다.

**4. `List<T>`의 동시성 버전은 없다.**

**5. 동시성 스택·큐·백 클래스는 내부적으로 연결 리스트로 구현되어 있다.** 이는 비동시성 `Stack`과 `Queue`보다 메모리 효율이 떨어지게 만들지만, 연결 리스트가 잠금 없는(lock-free) 또는 낮은 잠금(low-lock) 구현에 유리하므로 동시 접근에는 더 낫다. (연결 리스트에 노드를 삽입하는 것은 참조 몇 개만 갱신하면 되지만, `List<T>` 같은 구조에 원소를 삽입하는 것은 기존 원소 수천 개를 옮겨야 할 수 있기 때문이다.)

즉 이 컬렉션들은 **단순히 평범한 컬렉션에 잠금을 건 축약이 아니다.** 이를 보여 주기 위해 원천 자료가 든 실측이 있다. 다음 코드를 단일 스레드에서 실행하면

```csharp
var d = new ConcurrentDictionary<int,int>();
for (int i = 0; i < 1000000; i++) d[i] = 123;
```

다음보다 **세 배 느리게** 실행된다.

```csharp
var d = new Dictionary<int,int>();
for (int i = 0; i < 1000000; i++) lock (d) d[i] = 123;
```

(다만 `ConcurrentDictionary`에서 **읽는 것**은 빠르다. 읽기가 잠금 없이 수행되기 때문이다.)

> **⚠️ 확장 메서드와 명시적 인터페이스 구현은 스레드 안전이 보장되지 않는다**
>
> 동시성 컬렉션의 **확장 메서드**와 **명시적 인터페이스 구현**은 스레드 안전이 보장되지 않는다. 이 경우 스레드 안전성을 보장하려면 동기화가 필요할 수 있다.
>
> 구체적으로 말하면 `ConcurrentDictionary`에 LINQ의 `Count()`, `ToList()`, `Where()`를 거는 것은 클래스가 보장하는 원자성 밖의 일이다. 개별 원소 읽기는 안전하지만 **전체를 훑는 동안의 일관성은 보장되지 않는다.**

### `IProducerConsumerCollection<T>` 계약

동시성 컬렉션은 전통적 컬렉션과 또 다른 점이 있다. **원자적 test-and-act 연산을 수행하는 특수 메서드**를 노출한다는 것이다. `TryPop` 같은 것들이다. 이 메서드 대부분이 `IProducerConsumerCollection<T>` 인터페이스로 통일되어 있다.

프로듀서/컨슈머 컬렉션은 두 가지 주 사용 사례를 갖는 컬렉션이다.

- **원소를 추가한다**("생산")
- **원소를 제거하면서 가져온다**("소비")

고전적인 예가 스택과 큐다. 프로듀서/컨슈머 컬렉션은 **효율적인 잠금 없는 구현에 유리**하기 때문에 병렬 프로그래밍에서 중요하다.

```csharp
public interface IProducerConsumerCollection<T> : IEnumerable<T>, ICollection, IEnumerable
{
    void CopyTo (T[] array, int index);
    T[] ToArray();
    bool TryAdd (T item);
    bool TryTake (out T item);
}
```

이 인터페이스를 구현하는 클래스는 셋이다. `ConcurrentStack<T>`, `ConcurrentQueue<T>`, `ConcurrentBag<T>`. **`ConcurrentDictionary`는 구현하지 않는다.**

`TryAdd`와 `TryTake`는 추가/제거 연산이 수행될 수 있는지 검사하고, 가능하면 수행한다. **검사와 실행이 원자적으로 수행되므로**, 전통적 컬렉션에서 하던 것처럼 잠금을 걸 필요가 없어진다.

```csharp
// 전통적 컬렉션에서 필요했던 것:
int result;
lock (myStack) if (myStack.Count > 0) result = myStack.Pop();
```

`TryTake`는 컬렉션이 비어 있으면 `false`를 반환한다. `TryAdd`는 제공된 세 구현에서 **항상 성공하고 `true`를 반환한다.** 다만 중복을 금지하는 자체 동시성 컬렉션을 작성한다면(동시성 집합 같은), 원소가 이미 존재할 때 `TryAdd`가 `false`를 반환하게 만들 것이다.

`TryTake`가 제거하는 특정 원소는 하위 클래스가 정의한다.

| 컬렉션 | `TryTake`가 제거하는 것 | 공개 메서드 이름 |
|---|---|---|
| `ConcurrentStack<T>` | 가장 최근에 추가된 원소 (LIFO) | `Push` / `TryPop` |
| `ConcurrentQueue<T>` | 가장 오래전에 추가된 원소 (FIFO) | `Enqueue` / `TryDequeue` |
| `ConcurrentBag<T>` | **가장 효율적으로 제거할 수 있는 원소** | `Add` / `TryTake` |

세 구체 클래스는 대부분 `TryTake`와 `TryAdd`를 **명시적으로 구현하고**, 같은 기능을 `TryDequeue`·`TryPop` 같은 더 구체적인 이름의 공개 메서드로 노출한다.

### 내부 구현 — 무엇이 잠금 없는가

| 클래스 | 내부 동기화 |
|---|---|
| `ConcurrentQueue<T>` | **잠금 없음.** `Interlocked` 메서드로 컬렉션을 조작한다 |
| `ConcurrentStack<T>` | **잠금 없음.** `Interlocked` 메서드로 컬렉션을 조작한다 |
| `ConcurrentBag<T>` | 스레드별 미니 컬렉션 + `Interlocked`. **훔칠 때만** `Monitor` |
| `ConcurrentDictionary<K,V>` | `Monitor`를 쓰지만 **잠금을 아주 짧게** 유지한다. 읽기는 잠금 없음 |

이 컬렉션들은 모두 **비블로킹(non-blocking)** 이다. 즉 어떤 스레드가 존재하지 않는 원소를 꺼내려 하면 즉시 반환한다. 원소가 나타날 때까지 블로킹하지 않는다. 그래서 `TryDequeue`, `TryPop`, `TryTake`, `TryGetValue` 같은 메서드가 항목을 얻었으면 `true`, 아니면 `false`를 반환하는 것이다.

**비블로킹이 잠금 없음을 뜻하지는 않는다는 점**에 주의하라. `ConcurrentDictionary`는 내부적으로 `Monitor`를 쓴다.

> **📌 블로킹이 필요하면 `BlockingCollection<T>`로 감싼다**
>
> "원소가 없으면 나타날 때까지 기다린다"는 동작이 필요할 때 `TryTake` 메서드들에 그 기능을 오버로드로 얹을 수도 있었다(취소 토큰과 타임아웃까지 고려하면 멤버가 폭발했겠지만). PFX 설계자들은 대신 그 기능을 **`BlockingCollection<T>`라는 래퍼 클래스로 캡슐화했다.** 50.11절에서 다룬다.

### `ConcurrentBag<T>` — 스레드별 로컬 목록과 훔치기

`ConcurrentBag<T>`는 **순서 없는** 객체 컬렉션을 저장한다(중복 허용). `Take`나 `TryTake`를 호출할 때 어떤 원소를 얻든 상관없는 상황에 적합하다.

동시성 큐나 스택 대비 백의 이점은 **여러 스레드가 동시에 `Add`를 호출할 때 경합이 거의 없다는 것**이다. 반면 큐나 스택에서 `Add`를 병렬로 호출하면 어느 정도 경합이 생긴다(비동시성 컬렉션에 잠금을 거는 것보다는 훨씬 적지만). `Take` 호출도 아주 효율적이다 — **각 스레드가 `Add`한 것보다 더 많은 원소를 `Take`하지 않는 한.**

내부 구조가 이 특성을 만든다.

```text
 ConcurrentBag<T>
 ┌─────────────────────────────────────────────────────────┐
 │  스레드 1의 로컬 목록: [d]→[c]→[b]→[a]                  │
 │  스레드 2의 로컬 목록: [g]→[f]→[e]                      │
 │  스레드 3의 로컬 목록: (비어 있음)                      │
 └─────────────────────────────────────────────────────────┘

   스레드 1이 Add    → 자기 목록 머리에 추가. 경합 없음 (Interlocked)
   스레드 1이 Take   → 자기 목록 머리에서 제거. 경합 없음 (d를 얻는다)
   스레드 3이 Take   → 자기 목록이 비었다 → 다른 스레드 목록의 꼬리에서
                        "훔친다"(steal). 여기서 Monitor 를 잡는다 (a를 얻는다)
```

동시성 백 안에서 **각 스레드는 자기만의 전용 연결 리스트를 갖는다.** 원소는 `Add`를 호출하는 스레드에 속한 전용 리스트에 추가되므로 경합이 제거된다. 백을 열거하면 열거자가 각 스레드의 전용 리스트를 순회하며 각각의 원소를 차례로 내놓는다.

`Take`를 호출하면 백은 먼저 **현재 스레드의 전용 리스트**를 본다. 원소가 최소 하나 있으면 경합 없이 쉽게 작업을 완료할 수 있다. 리스트가 비어 있으면 **다른 스레드의 전용 리스트에서 원소를 "훔쳐야" 하고**, 경합 가능성을 감수한다.

정확히 말하면 `Take`는 **그 스레드에서 가장 최근에 추가된 원소**를 준다. 그 스레드에 원소가 없으면 무작위로 선택된 다른 스레드에서 가장 최근에 추가된 원소를 준다.

> **📌 완전한 무경합에는 원소가 최소 두 개 필요하다**
>
> 구현 세부 때문에 경합을 완전히 피하려면 실제로는 로컬 리스트에 **원소가 최소 두 개** 있어야 한다.

동시성 백은 **컬렉션에 대한 병렬 연산이 주로 원소 `Add`로 구성될 때**, 또는 **`Add`와 `Take`가 스레드 단위로 균형을 이룰 때** 이상적이다. 전자의 예를 50.6절에서 봤다. `Parallel.ForEach`로 병렬 철자 검사기를 구현할 때다.

```csharp
var misspellings = new ConcurrentBag<(int Index, string Word)>();
Parallel.ForEach (wordsToTest, (word, state, i) =>
{
    if (!wordLookup.Contains (word))
        misspellings.Add (((int) i, word));
});
```

> **⚠️ 동시성 백은 프로듀서/컨슈머 큐로는 나쁜 선택이다**
>
> 원소가 **서로 다른 스레드에 의해** 추가되고 제거되기 때문이다. 프로듀서 스레드가 자기 로컬 리스트에 쌓고, 컨슈머 스레드는 자기 리스트가 항상 비어 있어서 **매번 훔쳐야 한다.** 훔치기마다 `Monitor`를 잡으므로 경합이 상시화된다.
>
> 프로듀서/컨슈머에는 `ConcurrentQueue<T>`(FIFO 의미론까지 얻는다) 또는 `Channel<T>`(51.1절)를 쓴다.

### `ConcurrentDictionary<TKey,TValue>` — 잠금 샤딩

`ConcurrentDictionary`는 `IProducerConsumerCollection<T>`를 구현하지 않는다. 프로듀서/컨슈머 컬렉션이 아니기 때문이다.

```csharp
public class ConcurrentDictionary<TKey, TValue> : IDictionary<TKey, TValue>, /* ... */
{
    public bool TryAdd (TKey key, TValue value);
    public bool TryGetValue (TKey key, out TValue value);
    public TValue this[TKey key] { get; set; }
    public bool TryUpdate (TKey key, TValue newValue, TValue comparisonValue);
    public bool TryRemove (TKey key, out TValue value);

    public TValue AddOrUpdate (TKey key, TValue addValue,
                               Func<TKey, TValue, TValue> updateValueFactory);
    public TValue GetOrAdd (TKey key, TValue value);
    public TValue GetOrAdd (TKey key, Func<TKey, TValue> valueFactory);

    public int Count { get; }
    public IEnumerator<KeyValuePair<TKey, TValue>> GetEnumerator();
}
```

내부적으로는 **버킷 배열을 여러 개의 잠금으로 나눈다(잠금 샤딩, lock sharding).** 키의 해시 코드가 어느 잠금에 속하는지 결정하므로, 서로 다른 잠금에 속하는 키를 갱신하는 스레드들은 서로를 막지 않는다. **읽기는 잠금을 전혀 잡지 않는다.**

`TryUpdate`는 세 인자를 받는 비교 후 교체(compare-and-swap) 연산이다.

```csharp
// 현재 값이 comparisonValue와 같을 때만 newValue로 바꾼다
bool changed = dict.TryUpdate (key, newValue: 10, comparisonValue: 9);
```

48.4절의 `Interlocked.CompareExchange`와 같은 발상이며, 낙관적 갱신 루프를 만들 때 쓴다.

> **⚠️ `GetOrAdd`·`AddOrUpdate`의 팩터리 델리게이트는 잠금 밖에서, 여러 번 호출될 수 있다**
>
> 이것이 `ConcurrentDictionary`의 가장 결정적인 함정이다.
>
> `GetOrAdd(key, valueFactory)`의 팩터리는 **잠금을 잡지 않은 상태에서 호출된다.** 두 스레드가 동시에 없는 키를 요청하면 **팩터리가 두 번 실행되고, 그중 하나의 결과만 딕셔너리에 남는다.** 이는 잠금 보유 시간을 최소화하기 위한 의도적인 설계다 — 팩터리가 얼마나 오래 걸릴지 딕셔너리는 알 수 없기 때문이다.
>
> 반환값은 **실제로 저장된 값**이므로 "저장된 것과 다른 값을 받는" 일은 없다. 그러나 **버려진 쪽의 부작용은 되돌려지지 않는다.**
>
> ```csharp
> // ⚠ 커넥션이 두 개 열리고 하나는 영원히 Dispose 되지 않는다
> var conn = pool.GetOrAdd (key, k => OpenConnection (k));
>
> // ⚠ 파일이 두 번 만들어진다
> var handle = cache.GetOrAdd (key, k => File.Create (Path (k)));
> ```
>
> 값 생성이 비싸거나 부작용이 있으면 **`Lazy<T>`를 값 타입으로 저장하는 관용구**를 쓴다.
>
> ```csharp
> var cache = new ConcurrentDictionary<string, Lazy<byte[]>>();
> byte[] data = cache.GetOrAdd (key,
>     k => new Lazy<byte[]>(() => LoadFromDisk (k),
>                           LazyThreadSafetyMode.ExecutionAndPublication)).Value;
> ```
>
> `Lazy<T>` 객체는 두 개 만들어질 수 있지만 **가볍고**, 실제 팩터리는 살아남은 `Lazy<T>` 하나에서만 — `ExecutionAndPublication` 모드 덕에 정확히 한 번만 — 실행된다.
>
> `AddOrUpdate`의 `updateValueFactory`도 마찬가지다. 갱신 경합이 나면 **재시도되면서 여러 번 호출된다.** 그래서 이 델리게이트는 반드시 **순수 함수**여야 한다.

### `Count`와 열거의 의미론

`Count` 속성은 **조회하는 그 순간** 컬렉션에 있는 원소 개수를 반환한다. 다른 스레드가 동시에 원소를 추가하거나 제거하고 있으면 그 값은 **즉시 부정확해질 수 있다.**

열거의 의미론은 클래스마다 다르다.

| 클래스 | `GetEnumerator` 동작 |
|---|---|
| `ConcurrentStack<T>` | 컬렉션 내용의 **스냅숏**을 찍고 그 스냅숏에서 원소를 반환한다 |
| `ConcurrentQueue<T>` | **스냅숏** |
| `ConcurrentBag<T>` | **스냅숏** |
| `ConcurrentDictionary<K,V>` | **스냅숏을 찍지 않는다.** 열거 중에 내용이 바뀔 수 있다 |

스냅숏을 찍는 세 컬렉션에서는 열거 중에 실제 컬렉션 내용이 바뀌어도 열거자가 보는 것은 고정되어 있다. `ConcurrentDictionary`는 다르므로 **주의해야 한다.**

세 컬렉션 어느 쪽이든 공통점이 하나 있다. **다른 스레드가 수정하는 동안 열거해도 예외가 던져지지 않는다.** `Dictionary<K,V>`나 `List<T>`가 던지는 `InvalidOperationException("Collection was modified")`이 없다는 뜻이다. 이것이 편리하기도 하고 위험하기도 하다 — **버그가 예외로 드러나지 않는다.**

### 조합 연산은 여전히 원자적이 아니다

48.7절과 24.12절에서 이미 본 규칙이 여기서도 유효하다. **"스레드 안전"은 각 메서드 호출이 원자적이라는 뜻이지 호출들의 조합이 원자적이라는 뜻이 아니다.**

```csharp
// ⚠ 여전히 경합한다 — 두 호출 사이에 다른 스레드가 끼어들 수 있다
if (!dict.ContainsKey (k))
    dict.TryAdd (k, v);

// ⚠ 이것도 경합한다
if (bag.Count > 0)
    bag.TryTake (out var item);

// ⚠ 두 컬렉션을 함께 갱신하는 불변식은 동시성 컬렉션 둘로 해결되지 않는다
index.TryAdd (id, record);
byName.TryAdd (record.Name, record);   // 그 사이에 다른 스레드가 둘 사이의 불일치를 본다
```

세 번째가 가장 흔하고 가장 발견이 어렵다. **불변식이 두 컬렉션에 걸쳐 있으면 동시성 컬렉션이 아니라 잠금이 필요하다** — 또는 두 컬렉션을 하나의 불변 객체로 묶고 참조를 교체하는 설계(48.14절)가 필요하다.

> **💡 동시성 컬렉션 선택 결정표**
>
> | 필요한 것 | 답 |
> |---|---|
> | 여러 스레드가 결과를 모으기만 한다 | `ConcurrentBag<T>` |
> | FIFO 순서가 필요하다 | `ConcurrentQueue<T>` |
> | LIFO 순서가 필요하다 | `ConcurrentStack<T>` |
> | 키로 조회하는 캐시 | `ConcurrentDictionary<K,V>` (+ `Lazy<T>` 관용구) |
> | 비어 있으면 대기해야 한다 | `BlockingCollection<T>` (50.11절) |
> | 비동기로 대기해야 한다 | `Channel<T>` (51.1절) |
> | 읽기가 압도적이고 쓰기가 드물다 | 불변 컬렉션 + 참조 교체 (24.10절) |
> | 스레드가 하나뿐이다 | **평범한 컬렉션** (24장) |

## 50.11 `BlockingCollection<T>`로 프로듀서/컨슈머 큐 만들기

### 무엇을 얹어 주는가

앞 절의 프로듀서/컨슈머 컬렉션 — `ConcurrentStack<T>`, `ConcurrentQueue<T>`, `ConcurrentBag<T>` — 에서 `TryTake`를 호출했는데 컬렉션이 비어 있으면 메서드는 `false`를 반환한다. 이 상황에서 **원소가 사용 가능해질 때까지 기다리는 것**이 더 유용한 경우가 있다.

`BlockingCollection<T>`는 `IProducerConsumerCollection<T>`를 구현하는 **아무 컬렉션이나 감싸서** 두 가지를 더한다.

1. **블로킹** — 원소가 없으면 `Take`가 대기한다.
2. **경계 용량(bounded capacity)** — 컬렉션의 전체 크기를 제한하고, 그 크기를 초과하면 **프로듀서를 블로킹**한다. 이렇게 제한된 컬렉션을 **경계 블로킹 컬렉션(bounded blocking collection)** 이라 부른다.

```csharp
public class BlockingCollection<T> : IEnumerable<T>, ICollection, IEnumerable, IDisposable
{
    public BlockingCollection();
    public BlockingCollection (int boundedCapacity);
    public BlockingCollection (IProducerConsumerCollection<T> collection);
    public BlockingCollection (IProducerConsumerCollection<T> collection,
                               int boundedCapacity);

    public void Add (T item);
    public bool TryAdd (T item, int msTimeout, CancellationToken cancellationToken);
    public void CompleteAdding();

    public T Take();
    public bool TryTake (out T item, int msTimeout, CancellationToken cancellationToken);

    public int  BoundedCapacity    { get; }
    public int  Count              { get; }
    public bool IsAddingCompleted  { get; }   // CompleteAdding 이 호출되었으면 true
    public bool IsCompleted        { get; }   // IsAddingCompleted 이고 Count == 0 이면 true

    public IEnumerable<T> GetConsumingEnumerable();
    public IEnumerable<T> GetConsumingEnumerable (CancellationToken cancellationToken);
    public void CopyTo (T[] array, int index);
    public T[] ToArray();
    public void Dispose();
}
```

사용 절차는 세 단계다.

1. 클래스를 인스턴스화한다. 선택적으로 감쌀 `IProducerConsumerCollection<T>`와 최대 크기(경계)를 지정한다.
2. `Add`나 `TryAdd`를 호출해 하위 컬렉션에 원소를 추가한다.
3. `Take`나 `TryTake`를 호출해 하위 컬렉션에서 원소를 제거(소비)한다.

**생성자에 컬렉션을 넘기지 않으면 클래스가 자동으로 `ConcurrentQueue<T>`를 인스턴스화한다.** `ConcurrentStack`을 넘기면 프로듀서/컨슈머 **스택**이 된다.

생산·소비 메서드는 취소 토큰과 타임아웃을 지정할 수 있다. 컬렉션 크기가 제한되어 있으면 `Add`와 `TryAdd`가 블로킹할 수 있고, `Take`와 `TryTake`는 컬렉션이 비어 있는 동안 블로킹한다.

| 상황 | `Add` | `Take` |
|---|---|---|
| 여유 있음 / 원소 있음 | 즉시 반환 | 즉시 반환 |
| 용량 초과 | **블로킹** | — |
| 비어 있음 | — | **블로킹** |
| `CompleteAdding` 호출 후 | **`InvalidOperationException`** | 남은 원소를 다 꺼내면 `InvalidOperationException` |

### `GetConsumingEnumerable`과 `CompleteAdding`

원소를 소비하는 다른 방법은 `GetConsumingEnumerable`을 호출하는 것이다. 이것은 **원소가 사용 가능해지는 대로 내놓는 (잠재적으로) 무한한 시퀀스**를 반환한다. `CompleteAdding`을 호출하면 시퀀스를 강제로 끝낼 수 있다. 이 메서드는 **더 이상의 원소가 큐에 들어가는 것도 막는다.**

```csharp
public static void Main()
{
    var bl = new BlockingCollection<int> (new ConcurrentQueue<int>());

    // 스레드 풀 스레드가 소비를 담당한다
    ThreadPool.QueueUserWorkItem (ConsumeItems, bl);

    // 컬렉션에 항목 5개를 추가한다
    for (int item = 0; item < 5; item++)
    {
        Console.WriteLine ("생산: " + item);
        bl.Add (item);
    }

    // 더 이상 항목이 추가되지 않음을 소비 스레드(들)에게 알린다
    bl.CompleteAdding();

    Console.ReadLine();       // 테스트 목적
}

private static void ConsumeItems (object o)
{
    var bl = (BlockingCollection<int>) o;

    // 항목이 나타날 때까지 블로킹한 다음 처리한다
    foreach (var item in bl.GetConsumingEnumerable())
        Console.WriteLine ("소비: " + item);

    // 컬렉션이 비었고 더 들어올 것이 없다
    Console.WriteLine ("모든 항목이 소비되었다");
}
```

출력에서 "생산"과 "소비" 줄은 뒤섞일 수 있지만, **"모든 항목이 소비되었다"는 항상 마지막**이다.

> **⚠️ `CompleteAdding`을 안 부르면 컨슈머가 영원히 대기한다**
>
> `GetConsumingEnumerable`의 `foreach`는 `IsCompleted`가 `true`가 되어야만 종료된다. 즉 **`CompleteAdding`이 호출되고 큐가 비어야** 한다.
>
> 프로듀서가 예외로 중단되어 `CompleteAdding`에 도달하지 못하면 모든 컨슈머 스레드가 영원히 블로킹된다. **`CompleteAdding`은 반드시 `finally`나 `Dispose`에서 호출하라.**
>
> 반대 방향의 실수도 있다. `CompleteAdding` 이후에 `Add`를 부르면 **`InvalidOperationException`** 이 던져진다. 프로듀서가 여럿이면 "마지막 프로듀서만 `CompleteAdding`을 부른다"는 조율이 필요하고, 그 조율에는 `CountdownEvent`(49.3절)가 잘 맞는다.

### `AddToAny`와 `TakeFromAny`

`BlockingCollection`은 여러 블로킹 컬렉션을 지정하면서 원소를 추가하거나 가져올 수 있는 **정적 메서드**도 제공한다. `AddToAny`, `TryAddToAny`, `TakeFromAny`, `TryTakeFromAny`다. 모두 `BlockingCollection<T>[]`와 항목·타임아웃·취소 토큰을 받는다.

- `(Try)AddToAny` — 배열의 모든 컬렉션을 순회하며 **용량에 여유가 있어 항목을 받을 수 있는 컬렉션**을 찾을 때까지 돈다.
- `(Try)TakeFromAny` — 배열의 모든 컬렉션을 순회하며 **항목을 제거할 수 있는 컬렉션**을 찾을 때까지 돈다.

즉 그 요청을 처리할 수 있는 첫 번째 컬렉션이 그 동작을 수행한다. 우선순위 큐를 여러 개 두고 어느 쪽이든 먼저 준비되는 쪽에서 꺼내는 패턴에 쓴다.

### 프로듀서/컨슈머 큐 구현

프로듀서/컨슈머 큐는 병렬 프로그래밍과 일반 동시성 시나리오 양쪽에서 유용한 구조다. 동작 방식은 이렇다.

- 작업 항목 — 또는 작업이 수행될 데이터 — 을 기술하는 큐를 마련한다.
- 태스크를 실행해야 할 때 큐에 넣고, 호출자는 다른 일을 계속한다.
- 하나 이상의 워커 스레드가 백그라운드에서 큐에 든 항목을 꺼내 실행한다.

프로듀서/컨슈머 큐는 **한 번에 몇 개의 워커 스레드가 실행되는지 정밀하게 제어**할 수 있게 해 준다. 이는 CPU 소비를 제한하는 데뿐 아니라 다른 자원에도 유용하다. 태스크가 집약적인 디스크 I/O를 수행한다면, 운영체제와 다른 애플리케이션을 굶기지 않도록 동시성을 제한할 수 있다. 큐의 생애 동안 워커를 동적으로 추가·제거할 수도 있다.

> **📌 CLR의 스레드 풀 자체가 프로듀서/컨슈머 큐다**
>
> 짧게 실행되는 컴퓨트 바운드 작업에 최적화된 형태다(46.1절). 그러므로 직접 만드는 프로듀서/컨슈머 큐는 **스레드 풀과 다른 정책이 필요할 때만** 의미가 있다.

프로듀서/컨슈머 큐는 보통 (같은) 태스크가 수행될 데이터 항목을 담는다. 예를 들어 데이터 항목이 파일명이고 태스크가 그 파일들을 암호화하는 것일 수 있다. 그러나 **항목을 델리게이트로 만들면** 각 항목이 무엇이든 할 수 있는 더 범용적인 프로듀서/컨슈머 큐를 쓸 수 있다.

```csharp
public class PCQueue : IDisposable
{
    BlockingCollection<Action> _taskQ = new BlockingCollection<Action>();

    public PCQueue (int workerCount)
    {
        // 컨슈머마다 별도의 Task를 만들어 시작한다:
        for (int i = 0; i < workerCount; i++)
            Task.Factory.StartNew (Consume);
    }

    public void Enqueue (Action action) { _taskQ.Add (action); }

    void Consume()
    {
        // 열거하는 이 시퀀스는 원소가 없으면 블로킹하고
        // CompleteAdding이 호출되면 끝난다.
        foreach (Action action in _taskQ.GetConsumingEnumerable())
            action();                          // 작업을 수행한다.
    }

    public void Dispose() { _taskQ.CompleteAdding(); }
}
```

`BlockingCollection`의 생성자에 아무것도 넘기지 않았으므로 동시성 큐가 자동으로 인스턴스화되었다. `ConcurrentStack`을 넘겼다면 프로듀서/컨슈머 **스택**이 되었을 것이다.

### `Task`를 담는 버전

방금 만든 프로듀서/컨슈머는 작업 항목이 큐에 들어간 뒤에는 추적할 수 없다는 점에서 유연하지 않다. 다음이 가능하면 좋겠다.

- 작업 항목이 완료되었는지 안다(그리고 `await`한다)
- 작업 항목을 취소한다
- 작업 항목이 던진 예외를 우아하게 처리한다

이상적인 해법은 `Enqueue` 메서드가 방금 말한 기능을 주는 객체를 반환하는 것이다. **바로 그 일을 하는 클래스가 이미 존재한다 — `Task` 클래스다.** `TaskCompletionSource`로 만들거나 직접 인스턴스화해서(시작되지 않은, 즉 "차가운" 태스크를 만들어서) 얻을 수 있다.

```csharp
public class PCQueue : IDisposable
{
    BlockingCollection<Task> _taskQ = new BlockingCollection<Task>();

    public PCQueue (int workerCount)
    {
        for (int i = 0; i < workerCount; i++)
            Task.Factory.StartNew (Consume);
    }

    public Task Enqueue (Action action,
                         CancellationToken cancelToken = default (CancellationToken))
    {
        var task = new Task (action, cancelToken);
        _taskQ.Add (task);
        return task;
    }

    public Task<TResult> Enqueue<TResult> (Func<TResult> func,
                         CancellationToken cancelToken = default (CancellationToken))
    {
        var task = new Task<TResult> (func, cancelToken);
        _taskQ.Add (task);
        return task;
    }

    void Consume()
    {
        foreach (var task in _taskQ.GetConsumingEnumerable())
            try
            {
                if (!task.IsCanceled) task.RunSynchronously();
            }
            catch (InvalidOperationException) { }   // 경합 조건
    }

    public void Dispose() { _taskQ.CompleteAdding(); }
}
```

`Enqueue`에서는 만들었지만 시작하지 않은 태스크를 큐에 넣고 호출자에게 반환한다. `Consume`에서는 컨슈머의 스레드에서 태스크를 동기적으로 실행한다. 태스크가 취소되었는지 확인하는 것과 실행하는 것 사이에 취소되는 드문 경우를 처리하기 위해 `InvalidOperationException`을 잡는다.

사용법은 다음과 같다.

```csharp
var pcQ = new PCQueue (2);        // 최대 동시성 2
string result = await pcQ.Enqueue (() => "쉬웠다!");
```

예외 전파, 반환값, 취소 등 태스크의 모든 이점을 누리면서 **스케줄링을 완전히 통제**하게 된다.

### 한계 — 왜 `Channel`로 가야 하는가

`BlockingCollection<T>`의 근본적 한계는 이름에 있다. **블로킹한다.**

- `Take()`는 **스레드를 블로킹한다.** 컨슈머가 서버 애플리케이션의 스레드 풀 스레드라면 이는 스레드 풀 기아의 직행 티켓이다(50.2절).
- `TakeAsync()` 같은 메서드가 **없다.** `async` 메서드 안에서 쓰려면 `Task.Run`으로 감싸 스레드를 하나 태워야 한다.
- 컨슈머 하나가 스레드 하나를 전용으로 붙든다. 45.9절이 하지 말라고 한 바로 그것이다.

그래서 .NET Core 3에서 **`System.Threading.Channels.Channel<T>`** 이 도입되었다. 고성능 **비동기** 프로듀서/컨슈머 큐이며, `BlockingCollection<T>`가 하는 일 전부를 스레드를 블로킹하지 않고 한다.

| | `BlockingCollection<T>` | `Channel<T>` (51.1절) |
|---|---|---|
| 도입 | .NET Framework 4.0 | .NET Core 3 |
| 대기 방식 | **스레드 블로킹** | **`await`** |
| 경계 용량 | `boundedCapacity` | `BoundedChannelOptions` |
| 가득 찼을 때 | 프로듀서 블로킹 | 대기 / 가장 오래된 것 버림 / 최신 것 버림 / 실패 |
| 완료 신호 | `CompleteAdding()` | `Writer.Complete()` |
| 소비 열거 | `GetConsumingEnumerable()` | `Reader.ReadAllAsync()` (`IAsyncEnumerable<T>`) |
| 하위 컬렉션 교체 | 가능 (`IProducerConsumerCollection<T>`) | 불가 (전용 구현) |
| 단일 리더/라이터 최적화 | 없음 | `SingleReader`/`SingleWriter` 옵션 |
| 할당 | 항목당 대기 시 커널 대기 가능 | 대기가 `ValueTask` 기반, 할당 최소 |

> **💡 새 코드에서 `BlockingCollection<T>`을 골라야 하는 경우**
>
> 딱 세 가지다.
>
> 1. **.NET Framework 대상**이라 `System.Threading.Channels`를 쓸 수 없다(NuGet 패키지로는 가능하다).
> 2. **컨슈머가 진짜 전용 스레드**여야 한다 — 예컨대 STA 스레드나 특정 스레드 친화성이 필요한 네이티브 라이브러리를 다룰 때.
> 3. **큐 자료구조를 바꿔야 한다** — 스택 의미론이나 자체 `IProducerConsumerCollection<T>` 구현을 감싸야 할 때.
>
> 그 밖에는 `Channel<T>`가 낫다. 특히 ASP.NET Core 같은 서버 환경에서는 예외 없이 그렇다. 백프레셔 설계는 51.2절에서 다룬다.

## 50.12 false sharing과 캐시 라인

### 원리 — 코드에 없는 공유가 하드웨어에 있다

61.4절에서 다루듯, RAM과 CPU 캐시 사이의 데이터는 **캐시 라인(cache line)** 이라는 고정 크기 블록 단위로 전송된다. 오늘날 압도적 다수의 컴퓨터에서 이 크기는 **64바이트**다. 1비트만 읽고 싶어도 64바이트 캐시 라인 전체가 채워진다.

멀티코어에서는 각 코어가 자기만의 L1·L2 캐시를 갖고 L3를 공유한다. 코어마다 같은 메모리의 사본을 갖게 되므로 **캐시 일관성(cache coherency)** 문제가 생기고, MESI 같은 캐시 일관성 프로토콜이 이를 해결한다. 이름은 캐시 라인이 가질 수 있는 네 상태 — Modified, Exclusive, Shared, Invalid — 에서 왔다. 로컬 캐시의 데이터가 수정되면 그 정보가 다른 코어들에 브로드캐스트되어야 한다.

여기서 **거짓 공유(false sharing)** 가 나온다.

> **거짓 공유** — 이론적으로는 수정되지 않는 공유 데이터가, 다른 스레드가 변경하는 캐시 라인 안에 위치해서 그 라인이 계속 무효화되는 불운한 데이터 접근 패턴.

논리적으로는 서로 다른 데이터를 만지는 스레드들이 물리적으로 같은 64바이트 안에 있으면, 각 코어는 매 수정마다 다른 코어의 사본을 무효화한다. **코드에는 공유가 없는데 하드웨어에는 공유가 있는 것이다.**

```text
  64바이트 캐시 라인 하나
  ┌────┬────┬────┬────┬────┬────┬────┬─── ... ───┐
  │ 4B │ 4B │ 4B │ 4B │    │    │    │           │
  └─┬──┴─┬──┴─┬──┴─┬──┴────┴────┴────┴───────────┘
    │    │    │    │
  코어1 코어2 코어3 코어4    ← 넷이 각자 "자기" 4바이트만 증가시킨다

  코어1이 쓴다 → 라인이 Modified
              → 코어2·3·4의 사본이 Invalid 가 된다
  코어2가 쓴다 → 라인을 다시 가져와야 한다 (코어1에서 전송)
              → 코어1·3·4의 사본이 Invalid 가 된다
  ... 무한 반복. 이것이 캐시 라인 핑퐁(ping-pong)이다
```

### 전형적 사례 — 배열 요소별 카운터

가장 흔한 형태가 "스레드마다 배열의 한 칸을 쓰는" 코드다. 원천 자료의 벤치마크가 정확히 이것이다.

```csharp
const int offset = 1;
const int gap = 0;
public static int[] sharedData = new int[4 * offset + gap * offset];

public static long DoFalseSharingTest (int threadsCount, int size = 100_000_000)
{
    Thread[] workers = new Thread[threadsCount];
    for (int i = 0; i < threadsCount; ++i)
    {
        workers[i] = new Thread (new ParameterizedThreadStart (idx =>
        {
            int index = (int) idx + gap;
            for (int j = 0; j < size; ++j)
            {
                sharedData[index * offset] = sharedData[index * offset] + 1;
            }
        }));
    }
    for (int i = 0; i < threadsCount; ++i) workers[i].Start (i);
    for (int i = 0; i < threadsCount; ++i) workers[i].Join();
    return 0;
}
```

각 스레드가 "이론적으로는 다른 스레드에 영향을 주지 않으면서" 배열 원소 하나만 증가시킨다. `offset`과 `gap` 두 매개변수가 원소들이 공유 배열 안에 어떻게 배치되는지를 결정한다.

원천 자료가 네 코어 머신에서 `threadsCount = 4`로 측정한 결과다.

| 버전 | PC | 노트북 | Raspberry Pi 2 |
|---|---|---|---|
| #1 (offset=1, gap=0) | 5.0초 | 6.7초 | 29.0초 |
| #2 (offset=16, gap=0) | 2.4초 | 2.6초 | 13.8초 |
| #3 (offset=16, gap=16) | **0.7초** | **0.8초** | 12.1초 |

**버전 #1**은 가장 흔한 경우다. 네 개의 `int`(4바이트씩)가 같은 64바이트 캐시 라인 안에 나란히 있다. 각 스레드(코어)가 같은 메모리 영역의 자체 로컬 사본을 갖게 되고, 증가할 때마다 다른 코어의 로컬 사본을 무효화해야 한다. 코어들이 계속 캐시를 무효화하도록 강제된다.

**버전 #2**는 명백한 해법이다. 훨씬 큰 배열을 만들고 **16번째 원소만** 사용한다(16 × 4바이트 = 64바이트). 성능이 훨씬 좋아지지만 **여전히 개선의 여지가 있다.**

**버전 #3**이 나머지를 설명한다. 첫눈에는 명백하지 않지만 **여전히 무효화되는 캐시 라인이 하나 남아 있다.** .NET의 모든 타입은 시작 부분에 추가 헤더를 갖는다(62장). 배열의 경우 **객체 시작 부분에 길이(length)가 저장된다.** 게다가 인덱스 연산자로 배열 원소에 접근할 때 생성되는 코드는 **범위를 벗어나지 않았는지 검사한다.** 이는 어떤 배열 원소에 접근하든 매번 **배열 객체의 앞부분을 읽어 길이를 확인한다**는 뜻이다.

따라서 첫 번째 코어는 배열 객체의 앞부분을 다른 코어들과 공유하며 해당 캐시 라인을 계속 무효화한다. 이를 고치려면 원소들을 **캐시 라인 하나만큼 뒤로 밀어야** 한다. 그것이 `offset`은 여전히 16이지만 `gap`도 16인 버전이다. 이 경우 각 코어는 첫 캐시 라인의 자체 로컬 사본을 **읽기 전용으로** 갖고, 데이터가 있는 자기 캐시 라인만 수정한다. 캐시 일관성 프로토콜 오버헤드가 전혀 추가되지 않는다. **거짓 공유가 있을 때보다 일곱 배 빠르다.**

> **⚠️ 배열 헤더도 캐시 라인 하나를 잡아먹는다**
>
> 이 두 번째 효과는 C#에서만 나타나는 함정이라 특히 놓치기 쉽다. 패딩을 넣었는데도 기대만큼 안 빨라졌다면 **배열의 첫 캐시 라인을 비워 두었는지** 확인하라.
>
> 배열 대신 **스레드마다 별도의 객체**를 쓰면 이 문제는 자연히 사라진다. 다만 그 객체들이 힙에서 연달아 할당되면(GC가 그럴 가능성이 높다) **다시 같은 캐시 라인에 들어갈 수 있다.**

### 진단 — 성능이 스레드 수에 반비례한다

거짓 공유의 특징적 증상은 명확하다.

| 증상 | 해석 |
|---|---|
| 스레드를 늘릴수록 **느려진다** | 거짓 공유 또는 잠금 경합의 강한 신호 |
| CPU 사용률은 100%인데 처리량이 안 는다 | 코어들이 캐시 라인을 주고받느라 바쁘다 |
| 단일 스레드 버전이 4스레드 버전보다 빠르다 | 거의 확실히 거짓 공유 |
| 데이터 배치만 바꿨는데 몇 배 빨라진다 | 확인 사살 |

잠금 경합과 구분하는 방법은 **`dotnet-counters`로 `monitor-lock-contention-count`를 보는 것**이다(48.9절). 잠금 경합이 없는데도 확장이 안 되면 거짓 공유를 의심한다.

> **📌 관리 코드에서는 프로파일러로 직접 보기 어렵다**
>
> 원천 자료의 지적처럼, 거짓 공유 같은 문제를 명확히 짚어 주는 것은 **저수준 도구뿐**이다. Windows에서는 Intel VTune이나 Concurrency Visualizer(50.13절), Linux에서는 `perf c2c` 같은 도구가 캐시 라인 경합을 직접 보여 준다.
>
> 관리 코드만 보는 프로파일러로는 "이 루프가 느리다"까지만 알 수 있고 **왜** 느린지는 알 수 없다. 그래서 실무에서 가장 빠른 진단법은 **패딩을 넣어 보고 빨라지는지 확인하는 것**이다.

### 해결책 셋

**1. 스레드 로컬 누적 후 병합 — 가장 좋은 해법.**

50.4절과 50.6절의 패턴이 거짓 공유도 함께 해결한다. 각 워커가 **자기 스택이나 자기 지역 변수**에 누적하면 애초에 공유 캐시 라인이 없다.

```csharp
long masterTotal = 0;
Parallel.For (0, N,
    () => 0L,                                        // localInit
    (i, state, local) => local + Compute (i),        // body — 지역 변수만 만진다
    local => Interlocked.Add (ref masterTotal, local) // localFinally — 태스크당 한 번
);
```

`local`은 JIT이 레지스터에 올릴 수 있는 지역 값이므로 캐시 라인 문제가 아예 발생하지 않는다. **거짓 공유를 고치는 첫 번째 시도는 항상 이것이어야 한다.**

**2. 패딩 — 배열/필드 배치를 강제로 벌린다.**

구조체를 `[StructLayout]`의 `Size`로 캐시 라인 크기까지 부풀린다.

```csharp
using System.Runtime.InteropServices;

[StructLayout (LayoutKind.Explicit, Size = 128)]
struct PaddedCounter
{
    [FieldOffset (0)] public long Value;
    // 나머지 120바이트는 패딩. 각 원소가 자기 캐시 라인을 독점한다
}

var counters = new PaddedCounter[Environment.ProcessorCount];
```

`LayoutKind.Sequential`에 `Size`를 지정해도 된다.

```csharp
[StructLayout (LayoutKind.Sequential, Size = 128)]
struct PaddedLong { public long Value; }
```

참조 타입 필드를 패딩할 때는 **필드 순서를 명시적으로 고정해야** 한다는 점에 주의하라. 참조 타입의 기본값은 `LayoutKind.Auto`라서 CLR이 필드를 재배열한다(16.1절, 상세한 계산은 54.4절).

**3. 배열 앞뒤에 여백을 둔다.**

위 벤치마크의 버전 #3처럼, 배열 헤더가 있는 첫 캐시 라인과 실제 데이터를 분리한다.

```csharp
const int Pad = 16;                                   // 16 × 4바이트 = 64바이트
var data = new int[Pad + threads * Pad];
int MyIndex (int threadId) => Pad + threadId * Pad;
```

> **⚠️ 캐시 라인 크기는 플랫폼마다 다르고, BCL은 그 값을 노출하지 않는다**
>
> x86/x64에서는 64바이트가 사실상 표준이지만 **보편적이지 않다.**
>
> - Apple Silicon(M 시리즈)의 성능 코어는 **128바이트** 캐시 라인을 쓴다.
> - 일부 프로세서는 인접 두 라인을 함께 프리페치하므로, 실효 간격이 128바이트인 것처럼 동작한다.
> - .NET에는 캐시 라인 크기를 알려 주는 **공개 API가 없다.**
>
> 그래서 패딩 값으로 **128바이트를 쓰는 것이 안전한 기본값**이다. 64로 잡으면 Apple Silicon과 일부 서버 CPU에서 거짓 공유가 남는다. 메모리를 두 배 쓰지만, 이 패턴을 쓰는 대상은 애초에 스레드 수만큼의 카운터뿐이므로 절대량이 무시할 만하다.
>
> 그리고 반드시 **대상 하드웨어에서 측정하라.** 위 표에서 Raspberry Pi 2의 결과가 PC와 전혀 다른 모양인 것을 보라 — 버전 #2와 #3의 차이가 거의 없다. 캐시 구조가 다르기 때문이다.

> **💡 패딩은 최후의 수단이다**
>
> 패딩은 (1) 메모리를 낭비하고, (2) 캐시 라인 활용률을 떨어뜨리며, (3) 코드의 의도를 흐린다. **거짓 공유가 측정으로 확인된 뒤에만** 넣어라.
>
> 실무에서 이 패턴이 정당한 곳은 좁다. 코어마다 하나씩 두는 카운터·통계·샤딩된 잠금 정도다. 데이터 구조 전체에 패딩을 뿌리면 캐시 미스가 늘어 오히려 느려진다(61.5절, 70장).

## 50.13 병렬 디버깅·프로파일링 — Parallel Stacks, Tasks 창, Concurrency Visualizer

### 병렬 버그는 왜 재현이 어려운가

병렬 코드의 버그는 세 가지 성질 때문에 일반 버그와 다르게 다뤄야 한다.

1. **타이밍 의존적이다.** 같은 입력, 같은 빌드, 같은 머신에서 100번 돌려도 안 나다가 101번째에 난다.
2. **디버거를 붙이면 사라진다.** 중단점이 스레드를 멈추면 경합 창이 닫힌다. 이른바 하이젠버그(heisenbug)다.
3. **머신마다 다르다.** 코어 수, 캐시 구조, 메모리 순서 모델(x64 vs ARM64, 48.2절)이 결과를 바꾼다.

그래서 병렬 코드의 검증은 **디버거보다 스트레스 테스트에 의존한다.**

> **💡 병렬 코드를 위한 스트레스 테스트 설계**
>
> | 축 | 무엇을 바꾸는가 |
> |---|---|
> | 반복 | 같은 시나리오를 수만~수십만 회 반복한다. 경합 창은 좁다 |
> | 병렬도 | 스레드 수를 1, 2, 코어 수, 코어 수 × 4로 바꿔 본다 |
> | 코어 수 | `MaxDegreeOfParallelism`을 1로 놓고도 통과하는지 확인한다(결과 정확성 기준선) |
> | 지연 삽입 | 의심 지점 앞뒤에 `Thread.Yield()`나 무작위 `Thread.SpinWait`를 넣어 경합 창을 벌린다 |
> | 아키텍처 | x64와 **ARM64** 양쪽에서 돌린다. 재배치 버그는 x64에서 숨는다 |
> | 빌드 | **반드시 Release 빌드**로. Debug 빌드는 JIT 최적화가 꺼져 있어 재배치가 덜 일어난다 |
>
> 그리고 **결과 정확성 검증을 순차 버전과 비교**하는 형태로 짜라. "예외가 안 났다"는 통과 기준이 아니다(50.4절).

### Parallel Stacks 창

Visual Studio에서 `Debug ▸ Windows ▸ Parallel Stacks`를 열면 **여러 스레드의 호출 스택을 하나의 그래프로** 볼 수 있다. 프로그램이 디버거에서 멈춘 상태여야 한다.

이 창의 값어치는 스레드가 많을 때 나온다. `Threads` 창은 스레드를 목록으로 나열하지만, Parallel Stacks는 **같은 스택 프레임을 공유하는 스레드들을 묶어서** 보여 준다. "지금 스레드 20개 중 18개가 `AcquireLock`에서 멈춰 있다"가 한눈에 보인다.

- 메서드 그룹 위에 마우스를 올리면 **스레드와 스택 프레임의 표**가 뜬다. 메서드 이름과 줄 번호가 나온다.
- 현재 스레드의 활성 스택 프레임은 **노란 화살표**로 표시된다.
- 스택 프레임 위에서 오른쪽 클릭하면 표시할 세부 정보를 고를 수 있다. **매개변수 값**도 포함된다.

드롭다운에서 `Threads`와 `Tasks`를 전환할 수 있다. `Tasks` 뷰는 스레드 대신 **비동기 논리 스택(async logical stack)** 을 보여 준다. `await` 경계를 넘어가는 논리적 흐름을 따라가므로 `async` 코드 디버깅에 특히 유용하다(47장).

### Tasks 창

`Debug ▸ Windows ▸ Tasks`를 열면 `Threads` 창과 등가이되 **태스크에 대한** 창이 뜬다. 각 태스크와 그 상태, 그 밖의 정보를 보여 준다.

- 열 머리글에서 오른쪽 클릭하면 보고 싶은 열을 고를 수 있다.
- 줄을 클릭하면 해당 소스 위치로 이동한다.

| 열 | 보여 주는 것 |
|---|---|
| ID | `Task.Id` |
| Status | `Scheduled` / `Running` / `Awaiting` / `Blocked` / `Deadlocked` 등 |
| Location | 태스크가 현재 실행 중인 위치 |
| Task | 태스크가 시작된 델리게이트 |
| Thread Assignment | 어느 스레드에 배정되었는가 |
| **AsyncState** | `Task.AsyncState` 값 |

> **💡 태스크에 이름을 붙여 디버깅을 쉽게 만들어라**
>
> `Task.Factory.StartNew`는 대상에 전달되는 **상태 객체**를 지정할 수 있다. 이는 원래 람다 클로저 비용을 피하기 위한 마이크로 최적화지만, 실무에서 더 유용한 용도는 **태스크에 의미 있는 이름을 부여하는 것**이다.
>
> ```csharp
> var task = Task.Factory.StartNew (state => Greet ("Hello"), "Greeting");
> Console.WriteLine (task.AsyncState);       // Greeting
> ```
>
> **Visual Studio는 Parallel Tasks 창에 각 태스크의 `AsyncState`를 표시한다.** 여기에 의미 있는 이름을 넣어 두면 디버깅이 상당히 수월해진다. 태스크가 수십 개일 때 ID 숫자만 보고 무엇이 무엇인지 알아내는 것과 비교해 보라.

### Concurrency Visualizer

Concurrency Visualizer는 Visual Studio 확장이자 **명령줄 유틸리티**다. 명령줄에서 트레이스를 수집할 수 있고, 수집한 트레이스는 Visual Studio 확장에서 열어 본다 — **Visual Studio가 설치되지 않은 컴퓨터에서도 수집이 가능**하다는 뜻이다.

```bash
CVCollectionCmd.exe /launch <실행파일 경로> /outdir <출력 디렉터리>
```

`CVCollectionCmd.exe`는 기본적으로 Visual Studio 설치 경로의 `Common7\IDE\Extensions` 아래에 설치된다. 이 도구는 `.etl`과 `.cvtrace` 확장자의 파일 여러 개를 생성한다. Visual Studio 메뉴에서 `Analyze ▸ Concurrency Visualizer ▸ Open Trace`로 열 수 있다.

세 개의 탭이 있다.

| 탭 | 보여 주는 것 |
|---|---|
| **Utilization** | 추적한 프로그램이 사용하는 **논리 코어 수**. "코어 16개 중 12개만 쓰고 있다"를 확인하는 곳 |
| **Threads** | 사용된 스레드들의 상세 내역, 각 스레드의 역할, 실행에 걸린 시간 |
| **Cores** | 논리 코어와 그 사용률. 스레드 ID, 이름, **크로스 코어 컨텍스트 스위치 수**, 총 컨텍스트 스위치 수, 컨텍스트 스위치 비율 |

> **⚠️ Concurrency Visualizer는 Windows 전용이고 웹 프로젝트를 지원하지 않는다**
>
> **Windows 이벤트 추적(ETW)에 의존**하기 때문이다. 리눅스 컨테이너에서 도는 서비스나 ASP.NET Core 웹 프로젝트에는 쓸 수 없다.
>
> 크로스 플랫폼 대안은 `dotnet-trace`(73.9절)로 EventPipe 트레이스를 뜬 뒤 PerfView나 SpeedScope로 보는 것이다.

Threads 탭의 크로스 코어 컨텍스트 스위치 수는 **거짓 공유(50.12절)와 NUMA 문제(61.7절)를 의심할 근거**를 준다. 스레드가 코어를 자주 옮겨 다니면 캐시가 매번 무효화된다.

### `dotnet-counters`의 스레드 풀 카운터

프로덕션에서 병렬 코드를 관찰하는 가장 가벼운 도구가 `dotnet-counters`다(73.9절).

```bash
dotnet-counters monitor --process-id <PID> --counters System.Runtime
```

병렬 프로그래밍과 직결되는 카운터는 다음이다.

| 카운터 | 읽는 법 |
|---|---|
| `threadpool-thread-count` | 풀 스레드 수. **계속 증가하면 스레드 풀 기아**를 의심한다(50.2절) |
| `threadpool-queue-length` | 대기 중인 작업 항목 수. **0에서 안 내려오면** 작업이 스레드를 붙들고 있다 |
| `threadpool-completed-items-count` | 완료된 작업 항목 수. 증가율이 처리량이다 |
| `monitor-lock-contention-count` | 잠금 경합 횟수. 확장이 안 되는데 이 값이 낮으면 **거짓 공유**를 의심한다 |
| `cpu-usage` | 프로세스 CPU 사용률. 100%인데 처리량이 안 늘면 캐시 문제 |
| `gc-heap-size` / `alloc-rate` | 병렬 루프가 항목마다 할당하고 있는지 확인(69장) |

> **⚠️ 스레드 풀 기아의 서명**
>
> `threadpool-thread-count`가 **초당 한두 개씩 천천히, 그러나 끝없이 증가**하고 `threadpool-queue-length`가 0으로 돌아오지 않는다면, 거의 확실히 누군가 풀 스레드를 블로킹하고 있다.
>
> 흔한 범인은 셋이다. (1) I/O 바운드 작업에 `Parallel.ForEach`(50.2절), (2) `.Result`/`.Wait()`로 sync-over-async(47.14절), (3) `BlockingCollection.Take()`를 풀 스레드에서 호출(50.11절).

### BenchmarkDotNet으로 병렬 이득 측정하기

이 장의 모든 주장은 **측정으로 확인해야 한다.** 병렬화에는 초기 비용이 있으므로 때로는 병렬 코드가 최선이 아니다.

```csharp
[MemoryDiagnoser]
public class ParallelBenchmarks
{
    private int[] _data;

    [GlobalSetup]
    public void Setup() => _data = Enumerable.Range (0, 1_000_000).ToArray();

    [Params (1, 2, 4, 8, 16)]
    public int Dop { get; set; }         // 병렬도를 축으로 잡는다

    [Benchmark (Baseline = true)]
    public double Sequential()
    {
        double total = 0;
        for (int i = 0; i < _data.Length; i++) total += Math.Sqrt (_data[i]);
        return total;
    }

    [Benchmark]
    public double Plinq() =>
        _data.AsParallel().WithDegreeOfParallelism (Dop).Sum (x => Math.Sqrt (x));

    [Benchmark]
    public double ParallelForLocal()
    {
        double grand = 0;
        object locker = new object();
        Parallel.For (0, _data.Length,
            new ParallelOptions { MaxDegreeOfParallelism = Dop },
            () => 0.0,
            (i, s, local) => local + Math.Sqrt (_data[i]),
            local => { lock (locker) grand += local; });
        return grand;
    }
}
```

`[Params]`로 병렬도를 축으로 잡는 것이 핵심이다. **배속이 코어 수에 비례하는지, 어디서 꺾이는지**를 봐야 암달의 법칙(50.1절)과 거짓 공유(50.12절) 중 무엇이 한계인지 알 수 있다.

> **⚠️ 병렬 벤치마크가 거짓말하는 지점**
>
> - **본문에 `Console.WriteLine`을 넣었다.** 콘솔 잠금이 측정을 지배한다(50.1절).
> - **Debug 빌드로 측정했다.** BenchmarkDotNet은 경고하지만 무시하기 쉽다.
> - **다른 프로세스가 코어를 쓰고 있다.** 병렬 벤치마크는 순차 벤치마크보다 배경 부하에 훨씬 민감하다.
> - **계층형 컴파일 워밍업이 부족하다.** 병렬 코드는 여러 스레드가 각자 워밍업을 지나야 한다(67.4절).
> - **입력이 프로덕션 규모가 아니다.** 프로덕션 크기의 데이터셋으로 개발하고 테스트해야 성능 문제가 늦게가 아니라 일찍 드러난다.
>
> BenchmarkDotNet의 올바른 사용법과 함정 목록은 67.3절과 67.4절에 있다.

> **📌 진단 도구의 상세는 Vol3에 있다**
>
> `dotnet-counters`·`dotnet-trace`·`dotnet-dump`의 전체 사용법은 73.9절, 덤프 기반 사후 분석은 74.5절, 병렬·비동기 코드 디버깅 실전은 74.4절, BenchmarkDotNet은 67.3절에서 다룬다. 이 절은 **병렬 코드에서 무엇을 보아야 하는지**만 짚었다.

## 이 장의 요약

- **동시성은 구조이고 병렬성은 실행이다.** 동시성은 코어 하나로도 성립하지만 병렬성은 코어가 둘 이상이어야 한다. CPU 바운드 병목에는 이 장을, I/O 바운드 병목에는 47장을 펴라. 둘을 바꿔 쓰면 성능은 나아지지 않고 자원만 낭비된다.
- **암달의 법칙은 직렬 비율이 상한을 정한다고 말한다.** 실행 시간의 3분의 2만 병렬화 가능하면 코어가 무한해도 3배를 넘지 못한다. 여기에 조정 비용·파티셔닝 비용·메모리 대역폭 한계가 더해지므로, "병렬화하면 항상 빨라진다"는 명제는 틀렸다.
- **PFX는 두 계층이다.** 상위의 PLINQ(선언적)와 `Parallel` 클래스(명령형), 하위의 태스크 병렬성·동시성 컬렉션·스피닝 프리미티브. PLINQ만이 파티셔닝과 결과 병합을 **둘 다** 대신해 준다.
- **`AsParallel()`은 오버로드 해석을 바꾸는 장치다.** 입력을 `ParallelQuery<T>`로 감싸 이후 연산자가 `ParallelEnumerable`에 바인딩되게 한다. 중간에 `IEnumerable<T>` 변수를 거치면 병렬성이 조용히 사라지고, `AsParallel`을 두 번 부르면 병합과 재파티셔닝을 강제한다.
- **파티셔닝 전략은 넷이고 각각 쓰이는 자리가 다르다.** 인덱싱 가능하면 범위, 아니면 청크가 기본이고, 비교가 필요한 연산자는 해시가 강제되며, `TakeWhile`/`SkipWhile`은 스트라이프를 유발한다. `ParallelEnumerable.Range`는 `Enumerable.Range().AsParallel()`의 축약이 아니라 **범위 파티셔닝 활성화 장치**다.
- **PLINQ는 기본적으로 순서를 보장하지 않는다.** `AsOrdered()`가 순서를 되살리지만 각 원소의 원래 위치를 추적하는 비용을 문다. 그리고 `AsOrdered`는 "순차 실행"이 아니라 "순차 순서의 출력"이므로, 공유 카운터 문제를 고치지 못한다.
- **병렬 람다는 함수적으로 순수해야 한다.** 공유 변수 갱신은 원자성·가시성·불변식 세 층위에서 깨지고, 잠금으로 고치면 병렬화 이득이 사라진다. 정답은 **스레드 로컬 누적 후 병합** — `Aggregate`의 4인자 오버로드이거나 `Parallel.For`의 `localInit`/`localFinally`다.
- **`Parallel.For`에서 `Break`와 `Stop`은 다르다.** `Break`는 순차 루프가 처리했을 원소를 모두 처리하도록 보장하지만 `Stop`은 아무것도 보장하지 않는다. `ParallelLoopResult.LowestBreakIteration`이 `null`이면 `Stop`이 호출된 것이다.
- **본문이 짧으면 델리게이트 호출 비용이 본문을 압도한다.** `Partitioner.Create(from, to, rangeSize)`로 수동 청킹해서 안쪽을 평범한 `for` 루프로 만들면 호출 횟수가 몇 자릿수 줄어든다. `rangeSize`는 `항목 수 / (코어 수 × 4~16)`에서 시작해 측정으로 조정한다.
- **I/O 바운드 병렬 처리의 정답은 `Parallel.ForEachAsync`다** ※.NET 6. 여기서 `MaxDegreeOfParallelism`은 스레드 수가 아니라 **진행 중인 비동기 연산 수**이므로 코어 수보다 훨씬 크게 잡는 것이 정상이다. `Parallel.ForEach`에 `async` 람다를 넘기면 `async void`가 되어 동시성 제한이 사라지고 예외가 프로세스를 죽인다.
- **병렬 API는 예외를 `AggregateException`으로 취합한다.** 첫 예외 이후 새 반복은 배정되지 않지만 **실행 중인 반복은 끝까지 실행되고 그 사이 예외가 더 쌓일 수 있다.** 부분 실행의 부작용을 되돌리는 것은 전적으로 당신 몫이며, `AsParallel()`을 추가할 때는 주변의 모든 `catch` 절을 다시 읽어야 한다.
- **동시성 컬렉션은 잠금을 건 평범한 컬렉션의 축약이 아니다.** 단일 스레드에서는 오히려 느리다(원천 실측 3배). `ConcurrentBag`은 스레드별 로컬 목록 + 훔치기 구조라 같은 스레드가 넣고 빼는 패턴에 최적이고 프로듀서/컨슈머에는 나쁘다. 열거 시 `Dictionary`만 스냅숏을 찍지 않는다.
- **`ConcurrentDictionary`의 팩터리 델리게이트는 잠금 밖에서 여러 번 호출될 수 있다.** 반환값은 실제로 저장된 값이지만 **버려진 쪽의 부작용은 되돌려지지 않는다.** 값 생성이 비싸거나 부작용이 있으면 `Lazy<T>`를 값 타입으로 저장하라. 그리고 개별 연산이 원자적이어도 **조합은 여전히 원자적이 아니다.**
- **`BlockingCollection<T>`은 스레드를 블로킹한다.** 그것이 정체성이고 동시에 한계다. `TakeAsync`가 없으므로 서버 코드에서는 스레드 풀 기아를 부른다. .NET Core 3 이후의 새 코드는 `Channel<T>`(51.1절)를 써야 한다.
- **거짓 공유는 코드에 없는 공유가 하드웨어에 있는 것이다.** 스레드마다 배열 한 칸을 쓰는 코드가 전형적 사례이고, C#에서는 **배열 헤더의 길이 검사**까지 첫 캐시 라인을 오염시킨다. 진단 신호는 "스레드를 늘릴수록 느려진다"이며, 첫 번째 해법은 패딩이 아니라 **스레드 로컬 누적**이다.
- **병렬 버그는 디버거보다 스트레스 테스트로 잡는다.** 반복 횟수·병렬도·아키텍처(x64와 ARM64)를 축으로 흔들고, 결과 정확성은 순차 버전과 비교하라. Parallel Stacks/Tasks 창은 멈춘 순간을, Concurrency Visualizer와 `dotnet-counters`는 흐르는 동안을 보여 준다.

## 연습 문제

1. **암달의 법칙 확인.** 전체 작업의 일정 비율만 병렬화되는 벤치마크를 작성하라(예: 순차 구간에서 `Thread.SpinWait`, 병렬 구간에서 `Parallel.For`). 직렬 비율을 0%·10%·25%·50%로 바꾸고 `MaxDegreeOfParallelism`을 1부터 코어 수까지 올리며 배속을 표로 기록하라. 50.1절의 이론값 표와 얼마나 벌어지는지, 그 차이가 어디서 오는지 설명하라.

2. **PLINQ 순차 폴백 관찰.** `Enumerable.Range(0, 100).AsParallel().Select(n => Work(n))` 형태의 쿼리를 만들고 본문에서 `Thread.CurrentThread.ManagedThreadId`를 수집하라. `Work`가 아주 빠를 때와 밀리초 단위일 때 관찰되는 서로 다른 스레드 ID 개수를 비교하고, `WithExecutionMode(ParallelExecutionMode.ForceParallelism)`을 붙였을 때 실행 시간이 어떻게 변하는지 측정하라.

3. **파티셔닝 전략 비교.** 소수 판정(원소마다 비용이 크게 다름)과 제곱근 합(원소마다 비용이 같음) 두 작업에 대해 `Enumerable.Range(...).AsParallel()`, `ParallelEnumerable.Range(...)`, `Partitioner.Create(source, loadBalance: true).AsParallel()` 세 버전을 BenchmarkDotNet으로 측정하라. 어느 조합에서 순위가 뒤집히는지 확인하고 이유를 50.3절의 표로 설명하라.

4. **`Break` vs `Stop`.** 0부터 999까지의 `Parallel.For`에서 값이 500일 때 각각 `Break()`와 `Stop()`을 호출하는 두 버전을 만들고, 실제로 실행된 인덱스를 `ConcurrentBag<int>`에 모아라. 두 버전에서 "500 미만인데 처리되지 않은 인덱스"의 개수와 `ParallelLoopResult.LowestBreakIteration` 값을 비교하라.

5. **비동기 람다 함정 재현.** 같은 URL 목록에 대해 (a) `Parallel.ForEach`에 `async` 람다를 넘기는 버전, (b) `Parallel.ForEachAsync` 버전을 작성하라. 진행 중인 요청 수를 `Interlocked`로 세어 최댓값을 출력하고, `MaxDegreeOfParallelism = 4`가 (a)에서는 지켜지지 않고 (b)에서는 지켜지는 것을 확인하라. (a)의 본문에서 예외를 던지면 무슨 일이 일어나는지도 관찰하라.

6. **`GetOrAdd` 팩터리 중복 호출 재현.** `ConcurrentDictionary<int, string>`에 대해 여러 스레드가 동시에 같은 키로 `GetOrAdd(key, k => { Interlocked.Increment(ref _factoryCalls); Thread.Sleep(50); return Build(k); })`를 호출하게 하라. `_factoryCalls`가 1보다 큰 것을 확인한 뒤 `Lazy<T>` 관용구로 바꿔 정확히 한 번만 호출되는지 검증하라.

7. **거짓 공유 재현과 제거.** 50.12절의 벤치마크를 그대로 작성해 `(offset, gap)`을 `(1,0)`·`(16,0)`·`(16,16)`으로 바꿔 가며 실행 시간을 측정하라. 그다음 `[StructLayout(LayoutKind.Explicit, Size = 128)]` 구조체 배열 버전과 `Parallel.For`의 `localInit`/`localFinally` 버전을 추가해 네 가지를 비교하고, ARM64 머신(Apple Silicon 등)이 있다면 같은 실험을 반복해 패딩 128바이트의 효과를 확인하라.
