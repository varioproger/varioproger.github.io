# 64장. GC 알고리즘 완전 해부

> **이 장의 위치** — Part XI「메모리와 가비지 컬렉션」의 심장이다. 62장에서 힙이 어떻게 나뉘어 있는지 보았고, 63장에서 객체가 어떻게 태어나는지 보았다. 이 장은 **객체가 어떻게 죽는지**, 정확히는 **런타임이 죽은 객체를 어떻게 알아내고 그 자리를 어떻게 되찾는지**를 끝까지 판다. 61.9절에서 "표시-쓸기-압축"이라는 이름만 붙여 두고 미룬 것, 62.7절에서 카드 테이블이 "Mark 단계에서 쓰인다"고만 말하고 넘어간 것, 63.6절에서 "예산이 소진되면 GC가 트리거된다"로 끝낸 것이 전부 여기서 만난다.
>
> **선수 지식** — 61장(메모리의 기초, 특히 61.9절), 62장(.NET 힙의 구조, 특히 62.4·62.6·62.7절), 63장(할당, 특히 63.1·63.2·63.6절), 34장(객체 수명과 파이널라이제이션)
>
> **이 장에서 다루지 않는 것** — 동시(백그라운드) GC와 워크스테이션/서버 모드의 차이는 65장에서, GC 문제를 실제로 진단하는 도구 워크플로는 66장에서, 파이널라이제이션 큐의 의미론은 34장에서 다룬다. 이 장은 **비동시 워크스테이션 GC 한 사이클**을 현미경으로 본다.

---

이 장은 다른 장보다 길다. 그럴 만한 이유가 있다. GC의 한 사이클은 서로 맞물린 다섯 단계로 이루어져 있고, 각 단계를 따로 떼어 설명하면 **왜 그렇게 되어 있는지**가 사라진다. plug와 gap이 왜 있는지는 압축 결정을 봐야 알고, 압축 결정이 왜 어려운지는 고정(pinning)을 봐야 알고, 고정이 왜 문제인지는 다시 plug 구조를 봐야 안다. 그래서 하나로 묶었다.

한 가지 약속을 하고 시작한다. **이 장의 기본 무대는 비동시(non-concurrent) 워크스테이션 GC다.** 힙이 하나이고, GC가 도는 동안 관리 스레드가 전부 멈춰 있는 가장 단순한 경우다. 이 경우를 완전히 이해하면 나머지 세 조합(서버, 백그라운드, 둘 다)은 65장에서 차이만 얹으면 된다.

## 64.1 GC 한 사이클의 전체 흐름 — 예제로 따라가기

### 여덟 단계

높은 곳에서 내려다보면 가비지 컬렉션 한 번은 여덟 단계다.

```text
┌───────────────────────────────────────────────────────────────────┐
│ 1. 트리거          무언가가 GC의 필요를 발생시킨다                    │
│                    (할당 예산 소진 / GC.Collect / 저메모리 알림 / 내부) │
└───────────────────────────────┬───────────────────────────────────┘
                                ↓
┌───────────────────────────────────────────────────────────────────┐
│ 2. EE 일시 중단     실행 엔진에 관리 스레드 전부를 멈추라고 요청한다     │
│                    (비동시 GC에서는 GC 전 구간 동안 멈춘 상태 유지)     │
└───────────────────────────────┬───────────────────────────────────┘
                                ↓
┌───────────────────────────────────────────────────────────────────┐
│ 3. GC 코드 실행     GC를 촉발한 그 사용자 스레드가 GC 코드를 실행한다   │
│                    (비동시 워크스테이션 모드 한정. 전용 GC 스레드 없음) │
└───────────────────────────────┬───────────────────────────────────┘
                                ↓
┌───────────────────────────────────────────────────────────────────┐
│ 4. 대상 세대 결정   condemned generation을 고른다                    │
│                    (요청받은 세대보다 더 늙은 세대가 될 수 있다)        │
└───────────────────────────────┬───────────────────────────────────┘
                                ↓
┌───────────────────────────────────────────────────────────────────┐
│ 5. Mark            루트에서 출발해 도달 가능한 객체를 표시한다         │
│                    (대상 세대와 그보다 젊은 세대만)                   │
└───────────────────────────────┬───────────────────────────────────┘
                                ↓
┌───────────────────────────────────────────────────────────────────┐
│ 6. Plan            압축한다면 각 객체가 어디로 갈지 계산한다.          │
│                    그 결과로 Sweep과 Compact 중 무엇을 할지 정한다     │
└───────────────────────────────┬───────────────────────────────────┘
                                ↓
┌───────────────────────────────────────────────────────────────────┐
│ 7. Sweep 또는 Compact                                              │
│      Sweep   : gap을 프리 리스트 항목으로 만든다                     │
│      Compact : (a) Relocate — 모든 참조를 새 주소로 갱신             │
│                (b) Compact  — 객체를 실제로 옮긴다                   │
└───────────────────────────────┬───────────────────────────────────┘
                                ↓
┌───────────────────────────────────────────────────────────────────┐
│ 8. EE 재개         실행 엔진에 관리 스레드를 다시 돌리라고 요청한다     │
└───────────────────────────────────────────────────────────────────┘
```

이 그림이 이 장의 지도다. 64.2~64.5절이 5단계를, 64.6~64.8절이 6단계를, 64.9~64.10절이 7단계를, 64.12절이 2·8단계를 판다. 나머지(1·4단계)는 이 절에서 끝낸다.

> **📌 "GC 스레드"가 없다**
>
> 비동시 워크스테이션 GC에서는 **전용 GC 스레드가 존재하지 않는다.** 할당하다가 예산을 넘긴 바로 그 사용자 스레드가 실행 엔진에 중단을 요청하고, 자기가 GC 코드를 실행하고, 끝나면 재개를 요청하고 원래 하던 할당을 계속한다. 서버 GC와 백그라운드 GC에서는 전용 스레드가 생기며, 그 차이가 진단할 때 스택 트레이스의 모양을 바꾼다(65장).

### 대상 세대 — 무엇을 수집하는가

가비지 컬렉션은 언제나 **특정 세대의 맥락에서** 일어난다. 이 세대를 **대상 세대(condemned generation)** 라고 부른다. 세대별 GC의 이득은 힙의 일부만 수집해도 된다는 데서 나온다. 62.4절에서 본 것처럼 .NET은 **대상 세대보다 젊은 세대도 함께** 수집하기로 설계했다. LOH와 POH의 객체는 논리적으로 세대 2에 속한다.

| 대상 세대 | 실제로 수집되는 것 | 통칭 |
|---|---|---|
| 세대 0 | 세대 0만 | ephemeral GC |
| 세대 1 | 세대 0, 1 | ephemeral GC |
| 세대 2 | 세대 0, 1, 2 + LOH + POH | **전체 GC(full GC)** |

Mark 단계는 **대상 세대와 그보다 젊은 세대의 객체에 대해서만** 도달 가능성을 검사한다. 그다음 GC는 Sweep과 Compact 중 무엇을 할지 정한다.

### 세그먼트 구현에서의 세 가지 시나리오

62.6절에서 본 세그먼트 구조를 놓고 보자. ephemeral 세그먼트 하나가 세대 0·1·2를 담고 있고, LOH 세그먼트가 따로 있다.

```text
[초기 상태 — 세그먼트 구현]

ephemeral 세그먼트
┌──────────────┬──────────────┬──────────────┬────────────┐
│    세대 2     │    세대 1     │    세대 0     │   미사용    │
│ ▨▨ ▨▨▨ ▨    │ ▨▨▨ ▨ ▨▨    │ ▨ ▨▨ ▨▨     │            │
└──────────────┴──────────────┴──────────────┴────────────┘
LOH 세그먼트
┌───────────────────────────────────┬──────────────────────┐
│ ▨▨▨▨▨▨    ▨▨▨▨▨▨▨▨▨              │        미사용         │
└───────────────────────────────────┴──────────────────────┘

  ▨ = 객체
```

**세대 0이 대상일 때.** Mark는 세대 0의 객체만 도달 가능성을 검사한다. 세대 1과 2와 LOH는 **카드 테이블을 통해 세대 0을 가리키는 참조를 찾기 위해서만** 스캔된다(62.7절).

```text
[세대 0 대상 — Sweep 결과]
┌──────────────┬──────────────┬────┬─────────┬──────────────┐
│    세대 2     │        세대 1        │  세대 0  │   미사용    │
│ ▨▨ ▨▨▨ ▨    │ ▨▨▨ ▨ ▨▨   ░░░ ▩    │  (비어짐) │            │
└──────────────┴─────────────────────┴─────────┴────────────┘
                              └─ 큰 구멍 (단편화)

[세대 0 대상 — Compact 결과]
┌──────────────┬────────────────┬───────┬────────────────────┐
│    세대 2     │      세대 1     │ 세대 0 │       미사용        │
│ ▨▨ ▨▨▨ ▨    │ ▨▨▨ ▨ ▨▨ ▩   │ (비어짐)│                    │
└──────────────┴────────────────┴───────┴────────────────────┘

  ▩ = 세대 0에서 승격된 객체,  ░ = 빈 공간
```

세대 0 수집이 끝나면 이렇게 된다.

- 세대 0의 객체만 도달 가능성이 검사되었다.
- **세대 0은 비었다.** 젊은 세대의 객체는 수집되거나 승격되거나 둘 중 하나다(예외는 곧 나올 강등이다).
- 살아남은 세대 0 객체는 세대 1로 승격되었다.
- 세대 1이 커졌다. Sweep이면 단편화 때문에 더 크게, Compact면 덜 크게.
- 세대 2와 LOH는 변하지 않았다. 다만 자기 안에서 세대 0을 가리키는 참조를 찾느라 **스캔은 되었다.**

**세대 1이 대상일 때.** 세대 0과 1을 마킹한다. 세대 0 생존자는 세대 1로, 세대 1 생존자는 세대 2로 승격된다. 재미있는 사실 하나 — **세대 1을 수집했는데 세대 1이 커질 수 있다.** Sweep을 선택하면 단편화가 그대로 세대 1 안에 남기 때문이다. 물론 그런 상황이면 GC가 Sweep을 고르지 않을 가능성이 높지만, 이론적으로도 기술적으로도 가능하다.

**세대 2가 대상일 때(전체 GC).** 세대 0·1·2와 LOH·POH 전부를 마킹한다. 훨씬 많은 객체를 봐야 한다. Sweep을 고르면 세대 2·1과 LOH에 대량의 단편화가 생긴다. Compact를 고르면 SOH 전체가 압축된다 — **LOH는 자동으로 압축되지 않고, POH는 절대 압축되지 않는다.**

> **⚠️ 전체 GC의 비용은 세대 0 GC보다 "몇 배"가 아니라 "몇 자릿수" 더 비쌀 수 있다**
>
> 전체 GC는 모든 세대와 LOH를 통틀어 마킹한다. 이들은 여러 세그먼트/리전에 걸쳐 있고, 살아남는 양이 많으면 그 자체로 대단히 비싸다. 게다가 이 과정에서 세대 2 세그먼트가 재사용되거나 새 세그먼트가 만들어질 수 있다. 반면 세대 0·1 GC는 **ephemeral 세그먼트 하나** 안에서 끝나고, 그 세그먼트는 CPU 캐시에 부분적으로 올라와 있을 가능성이 높다. 그래서 오버헤드 차이가 **수 자릿수**까지 벌어진다. 전체 GC는 가능한 한 피해야 한다.

### 세대 2가 계속 자라면 — 새 ephemeral 세그먼트

세대 1이나 2를 대상으로 하는 GC가 반복되면 세대 2가 세그먼트 안에서 계속 자란다. 오래 사는 객체가 많은 애플리케이션에서는 결국 세대 0·1에 남는 공간이 부족해지는 순간이 온다. 이때 단순 Sweep이나 Compact로는 부족하다. GC는 대개 이렇게 한다.

1. 현재 ephemeral 세그먼트를 **세대 2 전용 세그먼트로 전환한다.** 세대 1과 2의 생존 객체를 여기에 압축한다.
2. **새 ephemeral 세그먼트를 만든다.** 세대 0의 생존 객체를 여기에 (세대 1 객체로서) 압축한다.
3. LOH는 평소대로 Sweep한다.

즉 **세대 2는 "끝없이" 자랄 수 있다.** 새 ephemeral 세그먼트에서 같은 상황이 반복되면 다시 세대 2 전용 세그먼트가 되고, 새 ephemeral 세그먼트는 다음 셋 중 하나로 마련된다.

| 방법 | 조건 |
|---|---|
| 메모리를 예약·커밋해 **새 세그먼트를 만든다** | 언제나 가능 |
| **세그먼트 대기 목록(standby list)** 에서 하나 꺼내 쓴다 | VM hoarding이 켜져 있어야 한다(62.8절) |
| 세대 2가 작은 **기존 세대 2 전용 세그먼트를 ephemeral로 전환**한다 | VM hoarding 없이도 가능 |

> **⚠️ 과도한 고정이 세그먼트 전체를 세대 2로 밀어 올린다**
>
> ephemeral 세그먼트를 세대 2 전용으로 전환하는 일은 **과도한 고정(pinning)** 때문에도 일어난다. 고정된 객체가 ephemeral 세그먼트에 많으면 그 세그먼트를 쓰기가 어려워진다 — 단편화 때문에 할당 컨텍스트를 잡기조차 힘들어진다. 그러면 세그먼트 전체가 세대 2로 승격된다. 고정 요구 자체는 이래도 문제없다(고정 객체의 주소가 바뀌지 않으므로). 그러나 **원래 세대 0에서 죽었어야 할 객체들이 통째로 세대 2로 올라간다.** 이것이 고정이 만드는 가장 조용하고 비싼 사고다. 64.7절과 Rule 22에서 다시 본다.

### 리전 구현에서는 무엇이 달라지는가

.NET 7부터 기본이 된 리전 구현(62.6절)에서는 GC의 일이 더 균질해진다. 세대 0·1·2를 한 세그먼트에 담는 ephemeral 세그먼트 같은 것이 없다. **리전 하나는 한 세대의 객체만 담는다.** Sweep과 Compact는 여전히 있지만 몇 가지가 다르다.

```text
[리전 — Sweep]
(a) 수집 전                        (b) 리전 자체가 승격된다
┌──────────┐                      ┌──────────┐
│ gen0 리전 │  생존 객체가 많다     │ gen1 리전 │   ← 같은 리전, 세대 번호만 바뀜
│ ▨ ▨ ▨ ▨ │  ─────────────→      │ ▨ ▨ ▨ ▨ │      (객체 복사 없음!)
└──────────┘                      └──────────┘
                                  (c) 새 gen0 리전을 만든다
                                  ┌──────────┐
                                  │ gen0 리전 │
                                  │  (비어짐)  │
                                  └──────────┘

[리전 — Compact]
(a) 수집 전                        (b) 늙은 리전으로 "할당"된다
┌──────────┐  ┌──────────┐        ┌──────────┐  ┌──────────┐
│ gen0 리전 │  │ gen1 리전 │        │ gen0 리전 │  │ gen1 리전 │
│ ▨ ░ ░ ▨ │  │ ▨▨ ░░   │  ───→   │ (비어짐)  │  │ ▨▨ ▨▨   │
└──────────┘  └──────────┘        └──────────┘  └──────────┘
                                   프리 리스트로     프리 리스트나
                                     들어간다        끝에 배치
```

**Sweep일 때**, 젊은 대상 세대의 표시된 객체를 늙은 세대로 복사하는 대신 **젊은 리전 전체를 승격할 수 있다.** 메모리 복사가 아예 없다. GC가 끝날 때 모든 세대 0 리전이 세대 1로 승격되었다면, 앞으로의 할당을 위해 새 세대 0 리전을 만든다.

**Compact일 때**, 젊은 세대의 표시된 객체를 늙은 세대 리전에 "할당"한다 — 그 리전의 프리 리스트나 리전 끝에다, 세대 0에서 새 객체를 할당할 때와 똑같은 방식으로. 그러면 젊은 리전은 비게 되고 **그대로 같은 세대에 남는다.**

| 항목 | 세그먼트 (~.NET 6) | 리전 (.NET 7+) |
|---|---|---|
| 한 단위가 담는 세대 | ephemeral 세그먼트가 세대 0·1(·2)을 함께 담는다 | **한 리전 = 한 세대** |
| 세대 경계 | 세그먼트 내부의 주소 경계로 관리한다 | 개념 자체가 없다 |
| Sweep 시 승격 | 객체를 옮기거나 경계를 이동한다 | **리전 통째로 승격**(복사 0) |
| 새 ephemeral 세그먼트 확보 | 필요할 때 만들거나 전환한다 | 해당 없음 |
| "Expand Heap" 대상 세대 사유 | 있다 | **없다** |
| 강등(demotion) | 고정 plug에 한해 일어난다 | 리전 단위로 세대가 배정된다 (런타임에는 여전히 강등·승격 판단 코드가 있다) |

> **⚠️ 이 장의 다이어그램 대부분은 세그먼트 구현을 그린다**
>
> plug·gap·brick table·세대 경계·강등 같은 개념은 세그먼트 구현에서 가장 선명하게 드러나고, **리전 구현에서도 plug/gap/brick table은 그대로 쓰인다.** 달라지는 것은 세대 경계 관리와 승격 방식이다. 그림에 `[세그먼트 구현]` 표시가 붙은 것은 리전에서는 그대로 적용되지 않는다는 뜻이다. 매 절에서 차이를 명시한다.

### 단계별 비용 — 실측

각 단계가 실제로 얼마나 비싼지 감을 잡아 두자. 워크스테이션 GC로 도는 애플리케이션에 ETW CPU 프로파일링을 걸어 부하 테스트를 한 결과다. 테스트 동안 **627번의 GC**가 일어났고 **평균 일시 정지 4.33밀리초**였다.

| 관찰 | 내용 |
|---|---|
| Mark와 Plan | 비용이 서로 비슷하다 |
| `plan_phase` 메서드 | GC 코드 구조상 **compact와 relocate를 모두 포함한다** |
| Relocate vs Compact | **주소를 갱신하는 relocate가 객체를 옮기는 compact보다 오래 걸린다** |

마지막 줄이 직관에 반한다. 메모리를 실제로 복사하는 것보다 참조를 고쳐 쓰는 쪽이 더 비싸다. 이유는 64.10절에서 본다.

객체 수가 비용에 미치는 영향은 두 갈래로 갈린다.

- **객체가 많으면** → **Plan 단계**가 일을 많이 한다. 관리 힙을 객체 단위로 훑기 때문이다. 다만 이 접근은 **엄격하게 선형**(객체 다음 객체)이라 캐시가 상당 부분 완화해 준다.
- **생존 객체가 많으면** → **Mark 단계**가 일을 많이 한다. 힙을 **비선형으로**(캐시에 불친절하게) 헤집는다. 객체 간 참조가 많을수록 더 나빠진다. 게다가 Compact까지 하면 대량의 메모리 트래픽과 참조 갱신이 따라온다. **Plan은 생존 객체 수에 덜 민감하다** — plug(생존 객체 묶음) 단위로 일하기 때문이다.

> **💡 이 표에서 끌어낼 실무 결론**
>
> 결론은 단순하다. **객체를 적게 만들수록 좋다.** 예를 들어 작은 배열 여러 개를 만드는 것보다 LOH에 큰 배열 하나를 만들고 `Span<T>`로 조각내 재사용하는 편이 GC 관점에서 낫다(63.10절의 `ArrayPool<T>` 논의와 같은 방향이다).
>
> 다만 이 수치들에 너무 매달리지 마라. 생존 객체 비율, 객체 간 참조 개수, 총 객체 수에 따라 크게 달라진다. 자기 애플리케이션에서 직접 재는 것이 옳다 — PerfView에서 CPU Samples를 켜고 수집한 뒤 CPU Stacks 뷰에서 `coreclr!`(또는 .NET Framework면 `clr!`) 행에 Lookup Symbols를 걸고 `garbage_collect`를 찾아 "Goto Item in Callees"로 내려가면 된다.

### 무엇이 GC를 촉발하는가

GC 설계의 대전제부터 보자. Book of the Runtime에 명시된 것들이다.

- 관리 힙에 **쓰이지 않는데 할당된 객체(쓰레기)** 가 비율로든 절대량으로든 유의미하게 쌓이지 않도록 GC가 충분히 자주 일어나야 한다.
- 그러면서도 **가능한 한 드물게** 일어나야 한다. 메모리 사용량은 낮아지겠지만 CPU 시간을 낭비하기 때문이다.
- GC는 **생산적**이어야 한다. 되찾은 메모리가 적으면 그 GC(와 그 CPU 사이클)는 낭비다.
- 각 GC는 **빨라야** 한다. 많은 워크로드에 저지연 요구가 있다.
- 관리 코드 개발자는 **GC를 잘 몰라도** 자기 워크로드에 맞는 메모리 활용을 얻어야 한다. GC가 스스로 튜닝해야 한다.

이 다섯을 합치면 답이 나온다 — **가능한 한 드물게, 가능한 한 좋은 결과로.** 그래서 "몇 밀리초마다 한 번" 같은 주기적 호출은 (몇 가지 예외를 빼면) 쓰지 않는다. 그냥 돌려 보고 결과를 확인하는 방식은 생산적이지 않다.

#### 1. 할당 트리거

63장에서 본 것처럼 SOH와 UOH 할당자 모두 적당한 자리를 찾지 못하면 GC를 촉발할 수 있다. **압도적으로 가장 흔한 사유다.** 네 갈래로 갈린다(괄호 안은 PerfView 리포트에 표시되는 이름).

| 사유 | 내용 |
|---|---|
| 작은 객체 할당 (`AllocSmall`) | 가장 흔하다. 객체 할당 중 **세대 0 할당 예산 초과** |
| 큰 객체 할당 (`AllocLarge`) | 대형 객체 할당 중 **LOH 예산 소진** |
| SOH 느린 경로 (`OutOfSpaceSOH`) | 느린 경로 할당 중 SOH 공간 부족. 세그먼트 재조직과 GC를 이미 몇 번 한 뒤에도 자리가 없다. 64비트에서는 드물어야 하지만 워크스테이션 GC에서는 일어난다 |
| LOH 느린 경로 (`OutOfSpaceLOH`) | UOH 느린 경로 할당 중 공간 부족. 마찬가지로 드물어야 한다 |

**할당이 없으면 이 유형의 트리거는 아예 없다. 할당이 없으면 GC도 없다.** 63장 전체가 이 한 문장을 위해 존재한다.

#### 2. 명시적 트리거

`GC.Collect` 계열로 직접 요청하는 것이다. 이렇게 발생한 GC를 **유도된(induced) GC**라 부른다.

```csharp
GC.Collect();                          // 전체 GC. 블로킹이지만 압축을 강제하지는 않는다
GC.Collect(int generation);            // 세대 지정. 블로킹, 압축 강제 없음
GC.Collect(int generation, GCCollectionMode mode);
GC.Collect(int generation, GCCollectionMode mode, bool blocking);
GC.Collect(int generation, GCCollectionMode mode, bool blocking, bool compacting);
```

`GCCollectionMode`는 세 가지다.

| 값 | 의미 |
|---|---|
| `Forced` | 무조건 수집한다 |
| `Optimized` | 판단을 GC에 맡긴다 |
| `Aggressive` | **압축 GC를 강제하고 메모리를 공격적으로 decommit 한다.** `generation` 인자가 반드시 2여야 한다 |

> **⚠️ `GC.Collect(2, Forced, blocking: false, compacting: true)` 는 모순된 요청이다**
>
> 65장에서 보겠지만 **비블로킹(동시) 전체 GC는 압축하지 않는다.** 그래서 이 인자 조합은 자기모순이다. 이런 경우 실제로 실행되는 GC는 **비블로킹·비압축이거나 블로킹·압축이거나 둘 중 하나**이며, 어느 쪽인지는 GC가 정한다. 프로그래머의 의도대로 되지 않는다.

> **⚠️ 어느 세대를 지정하든 전체 GC가 될 수 있다**
>
> GC는 어느 세대를 수집하는 것이 가장 생산적인지 판단하는 단계(4단계)를 거친다. 그래서 `GC.Collect(0)`을 호출해도 세대 2가 대상이 될 수 있다 — 예컨대 늙은 세대가 이미 자기 할당 예산을 넘겼다면. **`GC.Collect(0)`은 "가벼운 GC"의 보증이 아니다.**

`GC.Collect` 호출이 정당화되는 경우는 드물다. Rule 20에서 정리하겠지만 근거를 미리 밝혀 둔다. 어떤 객체가 수집되지 않는다는 것은 **무언가가 아직 그 객체에 대한 참조를 붙들고 있다는 뜻**이다. `GC.Collect`는 여기에 아무 도움이 되지 않는다. 그리고 GC는 생산적이지 않을 GC를 트리거하지 않는다. 따라서 명시적 `GC.Collect` 호출은 **비생산적일 확률이 높다.**

그럼에도 정당한 몇 안 되는 경우가 있다.

- **GC가 이해할 수 없는 간헐적 동작을 당신은 알고 있을 때.** 예를 들어 가끔 도는 배치 처리가 대량의 객체를 세대 2까지 밀어 올렸는데 처리 후 전부 참조가 끊기는 경우다. 이런 할당 폭증이 드물면 GC는 한참 동안 세대 2를 수집하지 않는다. GC 오버헤드가 늘지는 않지만 프로세스가 필요 이상으로 메모리를 쓴다.
- **대량 할당이 예상되는 처리 직전의 정리.** 게임에서 새 레벨을 로드하기 직전 같은 경우. 저지연 모드로 전환하기 직전에도 유용하다.
- **시작 시 대량의 데이터를 프리로드하는 웹 애플리케이션이 서비스에 투입되기 직전.** 압축 GC를 한 번 강제해서 캐시 데이터를 세대 2에 깔끔하게 눌러 담으면, 그 비정상적 할당이 첫 요청들에 미치는 영향을 제한할 수 있다.
- **제3자 라이브러리의 메모리 사용 패턴이 나쁠 때** 사용 전후로 정리하는 것.
- **벤치마킹 직전의 정리.** 측정마다 동일한 출발 상태를 만들려면 전체 GC를 먼저 돌리는 것이 관례다. BenchmarkDotNet이 그렇게 한다.
- **`WeakReference`를 쓰거나 누수가 의심되는 코드를 검증하는 단위·통합 테스트.** 테스트 전후로 명시 호출해 결과를 재현 가능하게 만든다.

반대로 **요청 수가 안정적인 웹 애플리케이션이 정상 운영 중일 때**는 정확히 반대다. GC가 당신보다 할당·생존 특성을 훨씬 잘 안다.

> **⚠️ 주기적 `GC.Collect`는 문제를 양탄자 밑에 쓸어 넣는 것이다**
>
> 어떤 문제를 우회하려고 `GC.Collect`를 타이머로 돌리고 있다면 십중팔구 진짜 문제는 따로 있다. 전형적인 진짜 문제는 **중년기 위기(mid-life crisis)** 이거나 **영원히 붙들고 있는 루트**다(66.12절, 66.11절). 둘 다 명시적 GC로 해결되지 않는다.

거의 명시적인 또 하나의 경로가 `GC.AddMemoryPressure(long size)` 다(65.8절). 관리 객체가 비관리 메모리를 얼마나 붙들고 있는지 GC에게 알려 주는 API다. 비관리 데이터는 GC 힙에서 추적되지 않으므로 GC가 판단에 반영할 수 없다. `AddMemoryPressure`로 누적된 총량이 동적으로 조정되는 임계값을 넘으면 **내부 휴리스틱이 정한 세대의 비블로킹 GC가 트리거된다.**

#### 3. 저메모리 시스템 트리거

Windows에서는 "외부 원인"으로 GC가 일어날 수 있다. OS가 메모리 부족을 감지하면 "low-memory" 알림을 브로드캐스트한다. .NET 런타임은 이 알림을 듣고 있다가 받으면 **세대 0 GC를 트리거한다**(높은 메모리 압박 상황에서는 전체 GC로 승격될 수 있다).

> **📌 저메모리 알림의 내부**
>
> 이 메커니즘은 **Windows에서만** 지원된다. 내부적으로 `CreateMemoryResourceNotification` API로 Windows 메모리 리소스 알림 객체를 만들고, 이를 **파이널라이저 스레드**가 감시한다. 파이널라이저 스레드를 고른 이유는 애플리케이션의 전 수명 동안 살아 있는 것이 보장되기 때문이다. 알림이 세트되면 파이널라이저 스레드에서 GC가 트리거된다.
>
> 내부 `System.Runtime.Caching.PhysicalMemoryMonitor` 클래스의 주석(그리고 그것이 근거로 삼는 Windows 구현의 주석)에 따르면, 저메모리 이벤트는 **물리 메모리의 97~99%가 점유되었을 때** 발신된다(설치된 RAM 총량에 따라 다르다).

확인하려면 PerfView나 `dotnet-trace`로 세션을 기록한 뒤 `Microsoft-Windows-DotNETRuntime/GC/Start` 이벤트에서 사유가 `LowMemory` 또는 `InducedLowMemory`인 GC를 찾으면 된다.

> **⚠️ CLR은 저메모리 알림을 무시할 수 있다**
>
> 가치가 없다고 판단하면 GC를 아예 트리거하지 않는다. 다만 일반적으로 **시스템 전역의 메모리 압박은 GC를 더 공격적으로 만든다** — 여유 공간을 만들 가능성이 있다면.

#### 4. 각종 내부 트리거

런타임과 표준 라이브러리 여기저기서 내부적으로 GC를 요청한다. 대부분 유도된(induced) GC로 표시된다 — GC 관점에서는 사용자 코드에서 왔든 런타임에서 왔든 차이가 없기 때문이다.

| 트리거 | 동작 | 비고 |
|---|---|---|
| **AppDomain 언로드** | 블로킹 전체 GC | **.NET Framework 전용** |
| **죽은 스레드 `Thread` 객체 정리** | 비블로킹 GC | 아래 설명 |
| **`GC.TryStartNoGCRegion` 호출 중** | 블로킹 전체 GC | `disallowFullBlockingGC: true`를 넘기면 생략 |

죽은 스레드 정리는 조건이 구체적이다. 스레드마다 관리 객체가 있고, 관리 스레드가 정리되기 전에는 네이티브 스레드 핸들이 닫히지 않는다. 대체로 유휴 상태이면서 가끔 스레드를 만드는 애플리케이션에서 핸들이 누적된다. 이를 막으려고 **죽은 스레드가 75개를 넘고, 마지막 전체 GC로부터 30분 이상 지났으면** 비블로킹 수집이 트리거된다. 그 GC는 **죽은 스레드를 37개 이상 가진 가장 높은 세대**를 수집한다(스레드는 대체로 수명이 길어 세대 2가 되는 경우가 많다).

> **📌 GC stress**
>
> .NET 팀이 쓰는 내부 메커니즘으로, 진단 목적으로 GC를 훨씬 자주 트리거한다. 주로 **GC hole** — GC에 보고되어야 하는데 보고되지 않는 것들 — 을 찾아내기 위한 것이다.

### 대상 세대를 고르는 조정 규칙

요청받은 세대와 실제 대상 세대는 다를 수 있다. **여기서 결정의 순서가 중요하다.** 각 후속 판단은 보통 대상 세대를 **올린다**. 어떤 검사가 세대 2를 고르고 그다음 검사가 세대 1을 고르면, 결국 **더 늙은 쪽이 선택된다.**

아래는 대상 세대를 바꿀 수 있는 판단의 전체 목록이다. 괄호 안은 PerfView의 "Condemned reasons for GCs" 표에 나타나는 이름이다. 이 표가 이 단계를 분석하는 가장 좋은 곳이다.

| 사유 (PerfView 이름) | 내용 |
|---|---|
| **Generation Budget Exceeded** | 할당 예산을 넘긴 **가장 늙은 세대**가 대상이 된다. LOH를 넘겼으면 세대 2(전체 GC)가 되지만, 백그라운드 GC가 이미 돌고 있으면 예외다 |
| **Time Tuning** | 시간·횟수 기준. **워크스테이션 모드에서만**, 그리고 Interactive 또는 SustainedLowLatency 지연 모드에서만 |
| **Internal Tuning** | 카드 테이블 효율이 낮다. 세대 1을 대상으로 올린다 |
| **Ephemeral Low** | ephemeral 세그먼트 공간 부족. 세대 1이 대상이 된다 |
| **Low Ephemeral Fragmented Gen2** | 위에 더해, 세대 2의 단편화가 (압축 후) 세대 1을 담을 만큼 크면 세대 2가 대상이 된다 |
| **Fragmented Ephemeral** | ephemeral 세대의 단편화 임계값 초과. 세대 0 또는 1이 대상 |
| **Expand Heap** | 세그먼트를 확장하지 않고는 커지는 ephemeral 세대를 담을 수 없다. 세대 2(블로킹 전체 GC). **리전에는 적용되지 않는다** |
| **Compacting Full GC** | `OutOfMemoryException`을 던지기 직전 최후 수단. 전체·블로킹·압축 GC |
| **High Memory** | "높은 메모리 부하"이거나 OS 저메모리 알림이 왔고 세대 2가 심하게 단편화되어 있다 |
| **Max Generation Budget** | 위 상황에 더해 세대 2 예산이 거의 소진되었다. 더 공격적으로 전체 GC |
| **Fragmented Gen2** | 세대 2의 단편화 임계값 초과 |
| **Small Heap** | 세대 2·LOH·POH가 백그라운드 GC를 하기에 너무 작다. 블로킹 전체 GC |
| **Avoid Unproductive Full GC** | 압축 전체 GC가 비생산적일 것으로 판단되면 세대 1 GC로 **낮춘다** |
| **Provisional Mode Induced / Provisional Mode LOH alloc / Provision Mode** | 임시 모드 관련. 아래 참조 |
| **Compacting Full under HardLimit / LOH Frag HardLimit / LOH Reclaim HardLimit** | 하드 메모리 리밋 관련. 아래 참조 |
| **Ephemeral Before BGC** | 백그라운드 전체 GC의 초기 단계로 ephemeral GC를 시작한다(65장) |
| **저지연 모드** | 세대 0 또는 1만 대상이 될 수 있다. **앞선 모든 판단을 덮어쓴다** |

`Ephemeral Low` 조건을 더 구체적으로 보면, 세그먼트의 남은 예약 메모리가 **세대 0 최소 크기의 두 배보다 작을 때** 발동한다.

시간 기반 조정의 구체적 임계값은 이렇다.

- **세대 1**은 **10초 그리고 10번의 GC** 동안 수집되지 않았으면 대상이 될 수 있다.
- **세대 2**는 **100초 그리고 100번의 GC** 동안 수집되지 않았으면 대상이 될 수 있다(전체 GC 트리거).

> **⚠️ "GC 황금률 1:10:100"은 워크스테이션 GC에만 해당하고, 지금은 일반적으로 유효하지 않다**
>
> 건강한 애플리케이션에서 세대별 수집 횟수 비율이 1:10:100이어야 한다는 말을 종종 듣는다. 이 비율은 위의 시간 기반 조정에서 곧바로 유도된 것이다. 그런데 시간 기반 조정은 **워크스테이션 모드에서만, 특정 지연 모드에서만** 동작한다. 서버 GC에는 아예 적용되지 않는다. 실제 "건강한" 비율은 이런 단순한 비보다 훨씬 복잡하고 동적이다. **이 비율을 건강 지표로 삼지 마라.**

카드 테이블 효율(Internal Tuning)은 62.7절의 카드 테이블 이야기와 이어진다. 카드 하나가 연속된 메모리 영역을 대표하고 그 안에 여러 객체가 있다. 각 객체가 다른 객체를 참조하지만 그중 일부만이 진짜 세대 간 참조다. **전체 참조 대비 "유의미한" 참조의 비율이 카드 테이블 효율**이다. 효율이 낮으면 쓸데없이 많은 객체를 훑는다는 뜻이다. 그래서 임계값 아래로 떨어지면 세대 1을 대상으로 올린다 — 오래 사는 객체를 세대 2로 모아 세대 간 참조를 없애려는 것이다.

### 단편화 임계값

위 판단들 중 여럿에서 단편화 임계값이 쓰인다. 세대마다 자기 임계값을 두 값으로 가진다.

**총 단편화 크기**(사용 불가능한 단편화). 여기에는 두 가지가 들어간다.

- **세대 할당자가 관리하지 않는 미사용 여유 공간** — Sweep 중 생긴 작은 gap들, 그리고 ephemeral 세대에서 맞춰 넣기에 실패한 뒤 버려진 공간(62장에서 본 대로 이 세대들의 프리 리스트 항목은 한 번만 검사되고 버려진다).
- **할당자 효율 기대치** — 지금까지 프리 리스트 항목을 얼마나 잘 재사용했는가.

**단편화 비율.** 위 총 단편화 크기를 세대 전체 크기로 나눈 값이다.

여기서 **아주 중요한 함정**이 있다. 이 임계값은 **두 곳에서 서로 다른 값으로** 쓰인다.

| 세대 | 대상 세대 결정용 크기 | 대상 세대 결정용 비율 | 압축 결정용 크기 | 압축 결정용 비율 |
|---|---|---|---|---|
| 세대 0 | 40,000 | 75% | 40,000 | 50% |
| 세대 1 | 80,000 | 75% | 80,000 | 50% |
| 세대 2 | 200,000 | 50% | 200,000 | 25% |

> **⚠️ 같은 "단편화 임계값"이라도 쓰이는 곳에 따라 비율이 다르다**
>
> 대상 세대를 고를 때(64.1절)의 비율은 정적 데이터의 `fragmentation_burden_limit`을 **2배 하되 75%를 넘지 않게** 만든 값이다. 반면 압축 여부를 정할 때(64.8절)의 비율은 `fragmentation_burden_limit` **그 자체**다. 그래서 세대 2 기준으로 "너무 단편화되었다"가 대상 세대 결정에서는 50%, 압축 결정에서는 25%다. **두 표를 혼동하면 관측 결과를 잘못 해석하게 된다.**
>
> 예를 들어 세대 2는 **사용 불가능한 단편화가 200,000바이트를 넘고 동시에 세대 전체 크기의 50%를 넘을 때** "너무 단편화되었다"고 판단되어 대상 세대가 되고, **200,000바이트를 넘고 25%를 넘을 때** 압축 대상이 된다.

### 하드 메모리 리밋

`GCHeapHardLimit` 또는 `GCHeapHardLimitPercent` 설정으로 GC 힙 크기의 하드 리밋을 지정할 수 있다. 절대값 또는 총 물리 메모리 대비 백분율로 **최대 커밋 크기**를 정한다.

64비트 런타임에서 프로세스가 **제한된 환경**(Windows의 job, Docker 컨테이너)에서 메모리 제한을 갖고 돌면, GC 하드 메모리 리밋은 **그 제한의 75%**(단 20 MB 미만은 되지 않음)로 자동 설정된다. 컨테이너 메모리 제한이 1 GB면 GC 하드 리밋은 **750 MB**다.

> **⚠️ 하드 리밋을 낮추면 고메모리 부하 시나리오에 더 쉽게 진입한다**
>
> 이것은 의도된 설계다. GC를 더 공격적으로 만들어 빡빡한 메모리 요구 하에서 `OutOfMemoryException`을 막으려는 것이다. 다만 그 대가로 **전체 GC가 잦아지고 일시 정지가 늘어난다.** 컨테이너 메모리 제한을 낮추면 CPU 사용량이 올라가는 현상은 대개 여기서 온다.

하드 리밋이 존재하면(설정이든 컨테이너든) 대상 세대 사유가 세 개 추가된다. **셋 다 LOH 압축을 트리거해서** 단편화 때문에 메모리 한계에 부딪히는 것을 막는다.

| 사유 | 조건 |
|---|---|
| `Compacting Full under HardLimit` | `OutOfMemoryException` 직전의 마지막 GC |
| `LOH Frag HardLimit` | **LOH 단편화가 하드 리밋의 1/8을 넘을 때** |
| `LOH Reclaim HardLimit` | Plan 후, **LOH에서 하드 리밋의 1/8보다 많이 되찾을 수 있다고 판단될 때** |

### 고메모리 부하

여러 판단이 "높은 메모리 부하"를 조건으로 삼는다. 정의는 이렇다.

- 시스템의 **물리 메모리 부하가 주어진 임계값을 넘을 때** — 대개 **90%**.
- 논리 코어가 많고 **RAM이 80 GB를 넘는** 강력한 머신에서는 임계값이 더 클 수 있다 — **최대 97%**.
- **"매우 높은" 메모리 부하** 임계값이 따로 있고, 기본값보다 **7% 위**다 — 보통 **97%**.
- `GCHighMemPercent` 구성 변수로 기본값을 덮어쓸 수 있다.

고메모리 부하는 GC 동작 여러 측면을 공격적으로 바꾼다.

- **블로킹·압축**을 선택할 가능성이 높아진다(특히 "매우 높은" 임계값에서).
- 메모리 리전을 **decommit** 한다.
- **LOH 압축**을 트리거할 수 있다.
- **임시 모드(Provisional mode)** 발동의 필수 조건이다.

### 임시 모드(Provisional Mode)

자동으로 켜지고 GC의 판단을 여러 방향으로 바꾸는 모드가 하나 있다. Maoni Stephens의 표현으로 "GC가 시작된 뒤에도 자기가 하는 GC의 종류에 대해 마음을 바꿀 수 있다". 판단이 임시적이라서 이 이름이 붙었다. 개발자는 이 모드를 제어할 수 없고, 완전히 투명하게 동작한다.

.NET 8 시점 기준으로 임시 모드가 다루는 시나리오는 하나뿐이다.

| 항목 | 내용 |
|---|---|
| **언제** | 블로킹 전체 GC의 끝(`PMFullGC` 포함) |
| **조건** | 고메모리 부하 상황이고, 세대 2 단편화가 문제적이다 — 구체적으로 **세대 2가 전체 관리 힙의 50%를 넘고, 그 단편화가 10%를 넘을 때** |
| **결과** | 전체 GC 대신 **압축 세대 1 GC로 전환한다** — 비생산적이고 비싼 압축 전체 GC 대신 세대 2의 빈틈을 메운다 |
| **언제까지** | 세대 1 GC 도중 세대 2 크기가 늘어났다면(세대 1 생존자가 세대 2의 여유 공간에 더는 들어가지 않는다는 신호) 그 직후에 `PMFullGC` 사유의 압축 전체 GC를 실행한다. 이때 임시 모드가 끝날 수도 있고 계속될 수도 있다 |

임시 모드 중에는 세 가지 대상 세대 사유를 볼 수 있다.

- `Provisional Mode Induced` — 전체 GC가 블로킹으로 전환되었다.
- `Provisional Mode LOH alloc` — LOH 할당으로 트리거된 GC가 블로킹으로 전환되었다.
- `Provision Mode` — 전체 GC가 압축 세대 1 GC로 전환되었다.

앞의 두 사유는 이렇게 설명된다. 임시 모드에서 전체 GC를 하면 **항상 블로킹**이다. 포어그라운드 GC가 압축 전체 GC를 요청했는데 못 받는 상황에 빠지는 것을 피하기 위해서다.

> **⚠️ `PMFullGC`가 반복적으로 보인다면 진짜 문제는 다른 곳에 있다**
>
> "세대 0 GC 몇 번 → 세대 1로 승격 → 즉시 `PMFullGC` 전체 GC" 패턴이 끝없이 반복된다면, 임시 모드가 나쁜 것이 아니라 **세대 2가 단편화와 함께 계속 자라고 있다**는 뜻이다. 원인은 대개 누수이거나 중년기 위기다. 임시 모드는 증상 완화 장치이지 해결책이 아니다.

### 서보 튜닝

.NET 8 시점에 **BGC servo tuning**이라는 실험적 기능이 있고 기본으로 꺼져 있다. `BGCFLTuningEnabled`와 `BGCMemGoal` 설정으로 켤 수 있다. 이름은 "서보 모터 튜닝"에서 왔을 것으로 보이며, 특정 메모리 사용 목표에 맞추는 **폐루프 피드백**을 구현하는 것이 목적이다. 켜면 대상 세대 사유가 넷 늘어난다 — `Servo Initial`, `Servo Blocking gc`, `Servo BGC`, `Servo Gen0`. 앞으로를 위한 참고로만 알아 두면 된다.

### 실제 GC 다섯 번을 따라가기

추상적인 설명을 실측으로 못박아 두자. 아래 프로그램은 25,000바이트짜리 `byte[]`를 백만 개 만들면서 전부 배열에 담아 살려 둔다. 각 배열의 실제 크기는 **25,024바이트**다(데이터 25,000 + 배열 길이 8 + 객체 메타데이터 16).

```csharp
GC.Collect();
const int LEN = 1_000_000;
byte[][] list = new byte[LEN][];
for (int i = 0; i < LEN; ++i)
{
    list[i] = new byte[25000];
    if (i % 100 == 0)
    {
        Console.WriteLine("Allocated 100 arrays");
        if (GC.CollectionCount(0) >= 20)
        {
            Console.WriteLine($"Leaving at i = {i}");
            break;
        }
    }
}
```

PerfView의 GCStats 리포트에서 `PerHeapHistory` 이벤트를 보면 GC마다 이런 값들을 얻을 수 있다.

| 관심 데이터 | 이벤트 속성 |
|---|---|
| GC 시작 시점의 세대 크기 (Begin size) | `SizeBefore` |
| 할당 예산 (Allocation budget) | `NewAllocation` (TraceEvent 페이로드에서는 `Budget`) |
| 승격된 객체 크기 (Promoted size) | `PinnedSurv` + `NonePinnedSurv` |
| GC 종료 시점의 세대 크기 (Final size) | `SizeAfter` |

**GC #1 — 명시적 `GC.Collect()`.** `2NI`(비동시 전체 GC, Induced)로 기록된다.

| | Gen0 | Gen1 | Gen2 | LOH | POH |
|---|---|---|---|---|---|
| 남은 예산 | 15,859,696 | 262,144 | 262,144 | 3,145,728 | 3,113,016 |
| 시작 크기 | 776,560 | 0 | 0 | 0 | 32,712 |
| 승격 크기 | 298,880 | 0 | 0 | 0 | 32,712 |
| 새 할당 예산 | 16,777,216 | 262,144 | 262,144 | 3,145,728 | 3,145,728 |
| 종료 크기 | 584 | 302,352 | 0 | 0 | 32,712 |

세대 0에서 총 776,560바이트 중 298,880바이트가 도달 가능해서 승격되었다 — **생존율 약 38%**다. 세대 1과 2는 생존율이 0이었으므로 예산이 다시 최소값으로 설정되었다.

**GC #2 — 할당에 의한 트리거.** `2N`. 지난 GC 이후 세대 0에 **16.78 MB**(루프의 배열들), LOH에 **8 MB**(백만 개 8바이트 참조를 담는 큰 배열)가 할당되었다.

| | Gen0 | Gen1 | Gen2 | LOH | POH |
|---|---|---|---|---|---|
| 남은 예산 | **–13,168** | **–112,144** | 262,144 | **–4,854,328** | 3,145,728 |
| 시작 크기 | 16,790,848 | 302,352 | 0 | 8,000,056 | 32,712 |
| 승격 크기 | 16,766,472 | 276,536 | 0 | 8,000,024 | 32,712 |
| 새 할당 예산 | 134,217,728 | 1,935,752 | 262,144 | 28,000,088 | 3,145,728 |
| 종료 크기 | 0 | 16,790,848 | 302,352 | 8,000,056 | 32,712 |

세대 0 예산과 LOH 예산이 **동시에** 음수다. 세대 1 예산도 이전 GC의 승격 때문에 소진되었다. LOH 예산 초과 때문에 이 GC는 전체 GC가 되었다. 생존율이 100%에 가까우니 세대 0 예산이 **128 MB로 대폭 증가**했고, LOH 예산은 거의 9배가 되었다.

> **📌 SOH와 LOH는 다른 락을 쓴다**
>
> SOH에 할당하는 스레드와 LOH에 할당하는 스레드가 동시에 각자의 세대 예산 초과를 관측하고 둘 다 GC를 트리거할 수 있다. `SuspendEE`는 하나만 이기지만, 실제 가비지 컬렉션 시점에는 **두 세대의 예산이 모두 초과된 상태**가 된다.

**GC #3, #4 — 계속 전체 GC.** 세대 0에 128 MB 정도가 할당되어 예산을 소진하지만, 승격 때문에 세대 1·2 예산도 함께 음수가 되어 전체 GC가 반복된다. GC #4가 끝나면 예산은 이렇게 된다.

| | Gen0 | Gen1 | Gen2 | LOH | POH |
|---|---|---|---|---|---|
| 새 할당 예산 | 134,217,728 | 134,217,728 | 120,917,056 | 28,000,088 | 3,145,728 |
| 종료 크기 | 0 | 134,239,664 | 151,332,864 | 8,000,056 | 32,712 |

세대 0 예산은 이미 **최대 크기에 도달해서** 생존율이 높은데도 더 오르지 않는다.

**GC #5 — 드디어 세대 0 GC.** `0N`.

| | Gen0 | Gen1 | Gen2 | LOH | POH |
|---|---|---|---|---|---|
| 남은 예산 | **–22,728** | 114,112 | **–13,126,136** | 120,977,480 | 120,977,480 |

세대 0(할당 때문)과 세대 2(직전 GC의 승격 때문) 예산이 모두 초과되었다. 그런데도 전체 GC가 되지 않았다. **예산 검사 로직이 세대 0부터 시작해서 초과되지 않은 첫 세대에서 멈추기 때문**이다. 세대 1 예산이 초과되지 않았으므로 세대 2 예산은 보지도 않는다. 결과는 세대 0 GC다. 물론 다음 GC들 중 하나에서 세대 1 예산이 초과되는 순간 곧바로 전체 GC가 된다.

> **⚠️ "세대 크기의 기본값"이라는 질문 자체가 성립하지 않는다**
>
> 세대는 그냥 **비어 있는 상태로 만들어진다.** 기본 크기 같은 것은 없다. 객체가 할당되고 승격되면서 할당 예산에 따라 자란다. 런타임 초기화 시점에 각 세대의 할당 예산이 정적 데이터의 **최소 예산**으로 설정되는 것이 전부다.
>
> 그리고 **할당 예산은 세대 크기가 아니다.** 할당 예산은 "그 세대의 다음 GC까지 허용할 할당량"이라는 논리적 값이다(내부 필드 이름이 `desired_allocation`인 이유다). 실제 세대 크기보다 작을 수도 있다 — GC #2 직후의 세대 1이 정확히 그 경우다(예산 1,935,752 vs 크기 16,790,848).

세대 크기와 예산의 관계는 .NET 소스의 이 메서드가 가장 간결하게 말해 준다.

```cpp
size_t gc_heap::current_generation_size (int gen_number)
{
    dynamic_data* dd = dynamic_data_of (gen_number);
    size_t gen_size = (dd_current_size (dd) + dd_desired_allocation (dd)
                        - dd_new_allocation (dd));
    return gen_size;
}
```

임의의 시점에서 세대의 대략적 데이터 크기(단편화 제외)는 **현재 데이터 크기 + (할당 예산 − 남은 예산)** 이다. GC가 끝나면 수집된 세대의 남은 예산이 할당 예산 값으로 설정된다. 그 후 할당이 일어나면서 남은 예산이 줄어든다. 두 값의 차이가 곧 지난 GC 이후의 할당량이다.

> **📌 `new_allocation`은 객체마다 갱신되지 않는다**
>
> 63.1절의 빠른 경로에는 예산을 차감하는 코드가 없었다. 그럴 만하다. **`new_allocation`은 할당 컨텍스트가 새로 만들어지거나 커질 때만 줄어든다.** 할당 컨텍스트가 GC가 나눠 주는 메모리 블록의 단위이기 때문이다. 객체 하나하나가 아니라 8 kB짜리 덩어리 단위로 예산이 소비된다.

이 실험의 교훈을 압축하면 이렇다. **세대 크기는 할당 예산이 만드는 동적 값이고, 할당 예산은 생존율이 만든다.** GC는 현재의 할당·생존 패턴에 맞추어 세대 크기를 끊임없이 조율하고 있다.

## 64.2 Mark 단계 — 객체 순회와 마킹

Mark 단계 시작 시점에는 모든 관리 스레드가 멈춰 있다. 애플리케이션이 관리 힙을 갱신하지 않는 것이 보장된다. 힙은 온전히 GC의 소유이고, 이제 도달 가능한 객체를 찾아 안전하게 돌아다닐 수 있다.

61.9절에서 본 대로 CLR은 **추적 수집기(tracing collector)** 를 구현한다. 여러 종류의 루트에서 출발해 현재 프로그램 상태의 객체 그래프 전체를 재귀적으로 순회한다. **어떤 루트에서도 도달할 수 없는 객체는 죽은 것으로 간주된다.**

### 순회 루틴 — 루트 주소 하나가 주어졌을 때

루트의 종류는 많지만 도달 가능한 객체를 찾는 메커니즘은 공통이다. 특정 루트 주소가 주어지면 순회 루틴은 다음을 수행한다.

**1단계 — 내부 포인터를 객체 시작 주소로 변환한다.**

**내부 포인터(interior pointer)** 란 관리 객체의 시작이 아니라 **중간 어딘가**를 가리키는 포인터다. 전형적으로 배열의 원소이거나 클래스에 중첩된 구조체에 대한 참조다. GC는 이것을 먼저 진짜 객체 주소로 바꿔야 한다.

**2단계 — 고정 플래그를 세트한다.**

객체가 고정되어 있으면 **객체 헤더의 특정 비트 하나**를 세트한다. GC는 고정 여부를 **고정 핸들 테이블**을 보거나 **스택 스캐닝 중 보고된 플래그**로 안다. POH의 객체에는 이 과정이 적용되지 않는다 — 언제나 고정된 것으로 취급되기 때문이다.

**3단계 — 객체의 참조를 따라 순회를 시작한다.**

`MethodTable`에 저장된 타입 정보(54장) 덕분에 GC는 **어느 오프셋(필드)이 나가는 참조인지** 안다. 방문할 객체 컬렉션을 유지하면서 **깊이 우선(depth-first)** 으로 방문한다. 이 컬렉션을 **마크 스택(mark stack)** 이라 부른다 — push와 pop 연산을 갖는 스택 자료 구조이기 때문이다. 객체를 방문할 때는 이렇게 한다.

- 이미 방문했거나 **더 늙은 세대에 속하면** 그냥 건너뛴다.
- 아직 방문하지 않았으면 **표시(mark)** 한다 — **`MethodTable` 포인터에 비트 하나를 세트하는 것**으로 한다.
- 그 객체가 나가는 참조들을 마크 스택에 넣는다.

마크 스택이 비면 순회가 끝난다.

> **📌 왜 MethodTable 포인터에 비트를 세우는가**
>
> `MethodTable` 데이터의 주소는 워드 정렬되어 있다 — 4 또는 8의 배수다. 따라서 **최소한 하위 2비트는 언제나 0이고 쓰이지 않는다.** 여기에 표시 비트를 넣어도 MT 포인터가 망가지지 않는다. 제대로 된 MT 포인터가 필요하면 하위 2비트를 0으로 만들면 그만이다(.NET 코드의 `GetMethodTable` 메서드를 보라). 객체마다 별도의 표시 비트맵을 두지 않아도 되는, 공짜에 가까운 트릭이다.

> **📌 재귀 대신 반복**
>
> 깊이 우선 그래프 순회의 전형적 구현은 재귀 호출이다. 그러나 스택 오버플로가 나지 않는다는 보장을 하기가 어렵다. **힙에 할당된 스택 형태의 컬렉션**을 쓰는 반복적 기법이 더 쉽고 안전하다 — 필요하면 늘릴 수 있기 때문이다. CLR의 마크 스택이 정확히 그것이다.

> **⚠️ 표시 비트와 고정 비트는 GC 밖에서는 존재하지 않는다**
>
> 표시(marked)와 고정(pinned) 플래그는 **Mark 단계에서 세트되고 Plan 단계에서 해제된다.** 관리 스레드가 도는 정상적인 객체 수명 동안에는 헤더나 MT 포인터를 봐도 그 객체가 고정되었는지 표시되었는지 알 방법이 없다. 이 사실이 진단을 어렵게 만든다 — 메모리 덤프를 떠도 GC 한복판을 잡을 확률은 극히 낮으므로, **덤프에서는 아무것도 고정되어 있지 않은 것처럼 보인다.** 64.7절에서 이 문제의 우회 방법을 다룬다.

### 단계별로 따라가기

작은 객체 그래프로 순회를 눈으로 따라가 보자. 루트가 둘 있고 객체가 여덟 개인 힙이다. 각 단계에서 마크 스택의 내용을 함께 표시했다.

```text
[초기 상태] R1, R2는 루트. 화살표는 참조.

    R1 ──→ (A) ──→ (B) ──→ (C)
                    │
                    └────→ (D)
    R2 ──→ (E) ──→ (F)

           (G) ──→ (H)          ← 어떤 루트에서도 닿지 않는다

 마크 스택: [ ]
 표시된 것: 없음
```

```text
[1단계] R1을 처리한다. A를 표시하고 A의 나가는 참조를 push.

    R1 ──→ [A]★ ──→ (B) ──→ (C)
                     │
                     └────→ (D)
    R2 ──→ (E) ──→ (F)
           (G) ──→ (H)

 마크 스택: [ B ]
 표시된 것: A
```

```text
[2단계] B를 pop. 표시하고 참조 두 개를 push.

    R1 ──→ [A]★ ──→ [B]★ ──→ (C)
                     │
                     └─────→ (D)
    R2 ──→ (E) ──→ (F)
           (G) ──→ (H)

 마크 스택: [ C, D ]
 표시된 것: A, B
```

```text
[3단계] D를 pop(깊이 우선이므로 top부터). 표시. 나가는 참조 없음.
[4단계] C를 pop. 표시. 나가는 참조 없음. 마크 스택이 비었다.

    R1 ──→ [A]★ ──→ [B]★ ──→ [C]★
                     │
                     └─────→ [D]★
    R2 ──→ (E) ──→ (F)
           (G) ──→ (H)

 마크 스택: [ ]
 표시된 것: A, B, C, D      ← R1 하나에서 시작한 순회가 여기서 끝난다
```

```text
[5~6단계] 다음 루트 R2로 넘어간다. E, F를 같은 방식으로 표시.

    R1 ──→ [A]★ ──→ [B]★ ──→ [C]★
                     │
                     └─────→ [D]★
    R2 ──→ [E]★ ──→ [F]★
           (G) ──→ (H)          ← 끝까지 방문되지 않는다

 마크 스택: [ ]
 표시된 것: A, B, C, D, E, F
```

**G와 H는 죽었다.** 서로를 참조하고 있어도 상관없다. 순환 참조가 참조 카운팅에서는 치명적이지만 추적 수집기에서는 아무 문제도 아닌 이유가 정확히 이 그림에 있다(61.9절).

> **⚠️ "이미 표시되었거나 더 늙은 세대면 건너뛴다"가 조용한 함정을 만든다**
>
> 세대 0 GC에서 세대 2에 있는 객체를 만나면 순회는 거기서 멈춘다. 그 객체의 필드가 세대 0의 객체를 가리키고 있어도 **이 경로로는 발견되지 않는다.** 그것을 발견하는 것은 완전히 별개의 메커니즘 — 카드 테이블(62.7절, 그리고 이 장 64.3절의 "내부 루트") — 의 일이다. 두 메커니즘이 합쳐져야 정확성이 성립한다.

### 루트 종류마다 순회를 다시 하는데도 비용이 폭발하지 않는 이유

이 장의 뒤에서 보겠지만 GC는 스택 루트, 파이널라이제이션 루트, 핸들 루트, 내부 루트를 **각각 따로** 스캔한다. 그런데 표시 플래그는 객체 안에 저장되고 종류를 가리지 않는다. 그래서 **같은 객체의 나가는 참조(그리고 그 아래 서브그래프 전체)를 반복해서 방문하지 않는다.** 다른 종류의 루트는 결과 그래프를 넓힐 뿐이다.

이 성질은 진단에서 실제로 관측할 수 있다. `MarkWithType` ETW 이벤트는 각 GC에서 **어느 종류의 루트 때문에 몇 바이트가 표시되었는지** 알려 준다. 값은 대체로 **누적적**이다 — 파이널라이제이션 루트로 인한 승격 바이트에는 이미 스택 루트로 표시된 객체가 포함되지 않는다. 핸들 루트 이벤트에는 스택이나 파이널라이제이션으로 이미 승격된 것이 포함되지 않는다. 이하 마찬가지다.

> **💡 순서가 곧 귀속이다**
>
> 이 누적적 성질 때문에 `MarkWithType` 데이터를 읽을 때 "어느 루트가 이 객체를 살렸는가"는 **스캔 순서**에 달려 있다. 스택 루트로도 핸들로도 도달 가능한 객체는 언제나 스택 루트 몫으로 계산된다. 이 데이터로 "핸들 누수"를 판정하려 들면 안 되는 이유다. 66.5절의 지배자 분석이 그 목적에는 훨씬 적합하다.

### Mark 단계에서 비용이 나오는 지점

| 요인 | 영향 |
|---|---|
| **생존 객체 수** | 직접적. 살아 있는 객체가 많을수록 순회할 것이 많다 |
| **객체 간 참조 수** | 직접적. 나가는 참조마다 마크 스택 push/pop이 발생한다 |
| **메모리 접근 패턴** | **비선형이라 캐시에 불친절하다.** 이것이 Mark를 비싸게 만드는 진짜 이유다 |
| **대상 세대** | 전체 GC면 LOH·POH를 포함한 힙 전체 |
| **카드 테이블 효율** | 낮으면 세대 간 참조를 찾느라 헛돌이가 늘어난다 |

Plan 단계가 힙을 **객체 순서대로 선형 순회**하는 것과 대비된다(64.6절). 같은 객체 수에서도 Mark가 캐시를 훨씬 많이 놓친다.

> **⚠️ 메모리 누수는 마킹의 버그가 아니다**
>
> 애플리케이션의 메모리 사용량이 시간에 따라 자란다고 해서 도달 가능성 판정에 오류가 있다고 가정하지 마라. 이 판정은 틀리지 않는다. 누수가 있다면 십중팔구 **무언가가 계속해서 다른 무언가에 대한 참조를 붙들고 있는 것**이다. .NET 메모리 관리 전체를 통틀어 가장 전형적인 문제는 "그 루트가 무엇인가"를 찾는 일이다.
>
> 그리고 **관리 메모리 누수가 확실하다고 말할 수 있는 유일한 조건**은 이렇다. **압축하는 전체 세대 2 GC가 실제로 일어나고 있는데도 메모리 사용량이 계속 자랄 때.** 그렇지 않다면 그냥 GC가 아직 전체 힙을 수집할 때가 아니라고 판단한 것일 수 있고(여유 메모리가 충분하면 그렇다), 비압축 백그라운드 전체 GC만 일어나서 단편화로 메모리가 자란 것일 수도 있다.

> **📌 압축 전체 GC를 강제로 한 번 일으키는 법**
>
> 다음 압축 전체 GC를 기다리기 싫다면 PerfView나 `dotnet-trace`로 `Microsoft-Windows-DotNETRuntime` 공급자를 키워드 `0x800000`(`CLR_MANAGEDHEAPCOLLECT_KEYWORD`)으로 구독하면 된다. 이 키워드는 정확히 이 목적으로 추가되었고, **새 리스너가 구독하면 런타임이 GC를 강제한다.**
>
> ```text
> dotnet-trace collect -p <pid> --providers Microsoft-Windows-DotNETRuntime:800000
> ```

## 64.3 루트의 종류 — 스택 루트, GC 핸들, 파이널라이제이션 루트, 내부 루트

34.1절에서 "객체가 살아 있다"의 정의가 루트라고 했다. 이제 그 루트가 실제로 네 종류라는 것과, 각각이 어떻게 스캔되는지 본다.

| 루트 종류 | 어디에 저장되는가 | 스캔 방법 | 대표적 사고 유형 |
|---|---|---|---|
| **스택 루트** | 스레드 스택 슬롯 또는 **CPU 레지스터** | GC Info를 보고 스택 워커가 프레임별로 훑는다 | 예상보다 짧은 생존(64.5절), 지역 변수 고정 |
| **파이널라이제이션 루트** | 파이널라이제이션 큐 / F-reachable 큐 | 큐를 하나씩 훑는다 | 파이널라이저 큐 적체, 세대 승격 |
| **GC 핸들 루트** | 전역 **핸들 테이블**(비관리 메모리) | 핸들 테이블을 종류별로 훑는다 | 정적·인터닝 문자열, 해제되지 않은 `GCHandle` |
| **GC 내부 루트** | 카드 테이블(기억 집합) | 세트된 카드 영역의 객체를 훑는다 | 세대 간 참조 과다, 카드 효율 저하 |

각각을 차례로 본다.

### 스택 루트

지역 변수가 가장 흔한 루트다. 어떤 것은 지극히 짧게 산다.

```csharp
public static void Delete(string path)
{
    string fullPath = Path.GetFullPath(path);
    FileSystem.Current.DeleteFile(fullPath);
}
```

어떤 것은 애플리케이션 전 수명을 산다.

```csharp
public static void Main(string[] args)
{
    var host = BuildWebHost(args);
    host.Run();
}
```

명시적으로 만들지 않아도 만들어진다. 아래 코드는 위 코드와 **정확히 같다.**

```csharp
public static void Main(string[] args)
{
    BuildWebHost(args).Run();
}
```

지역 변수는 값 타입일 수도 있고 참조 타입 값에 대한 참조일 수도 있다. 여기서 관심 있는 것은 **참조를 담은 지역 변수**다(참조 타입이든 박싱된 값 타입이든).

.NET Guide 문서는 스택 루트를 "JIT 컴파일러와 스택 워커가 제공하는 스택 변수"라고 설명하는데, 이 표현은 다소 혼란스럽다. 정확히는 **현재 실행 중인 메서드의 지역 변수와, 현재 호출 스택에 있는 모든 메서드의 지역 변수**다. "스택 루트"의 "스택"은 **호출 스택**을 가리킨다.

> **⚠️ 스택 루트는 스택에 없을 수 있다**
>
> 몇 번을 반복해도 지나치지 않은 사실이다. **지역 변수로 표현되는 루트는 스택에 있을 수도, CPU 레지스터에 있을 수도 있다.** JIT 컴파일러는 레지스터와 스택 슬롯을 최대한 효율적으로 배분한다. 그래서 `!gcroot` 출력에 `rbx:` 같은 레지스터 이름이 나온다. 스택 메모리를 아무리 뒤져도 그 루트는 없다.
>
> 특히 x64 런타임의 JIT은 레지스터를 더 적극적으로 쓴다 — x64가 범용 레지스터 여덟 개(`r8`~`r15`)를 추가했기 때문이다.

EE 중단이 완료되면 모든 관리 스레드의 호출 스택을 워킹해서 지역 변수를 전부 찾아야 한다. 이것이 스택 워커의 일이다. 현재 호출 스택의 어떤 메서드에 관리 객체 참조를 담은 지역 변수가 있으면 그 객체는 살아 있는 것으로 간주되고, 객체 그래프 순회의 출발점이 된다.

문제는 **"주어진 명령 주소에 지역 변수가 있는가, 그것이 객체 참조인가"에 답하기가 자명하지 않다는 것**이다. 그 답을 저장한 것이 **GC Info**이고, 64.4절 전체가 이 주제다.

### 파이널라이제이션 루트

파이널라이제이션은 객체가 수집될 때 어떤 로직을 실행하는 메커니즘이다. 대개 관리 객체가 붙들고 있는 비관리 리소스를 놓아 주는 데 쓴다. 자세한 의미론은 34장에서 다룬다.

여기서는 이 정도면 충분하다 — **"파이널라이즈되어야 하는" 객체를 추적하기 위해 GC가 특별한 큐들을 유지한다.** 이 큐들은 "파이널라이즈 준비된" 객체에 대한 참조를 담고 있으므로, **당연히 스캔되어야 할 루트다.**

파이널라이제이션 큐 스캔은 단순하다. GC가 큐의 객체를 하나씩 훑으면서 각각에서 마킹 순회를 시작한다.

> **⚠️ 파이널라이저가 있는 객체는 GC를 한 번 더 살아남는다**
>
> 이것이 34.2절의 핵심이자 Rule 18의 각주이기도 하다. 파이널라이저가 있으면 원래 세대 1에서 죽었을 객체가 **세대 2로 승격된다.** 파이널라이저를 무심코 붙이는 것이 중년기 위기를 만드는 흔한 경로다.

### GC 내부 루트 — 카드 테이블을 통한 스캔

세대 0이나 1 GC에서는 **늙은 객체 → 젊은 객체 참조**를 포함해야 한다(62.7절). 이 단계는 세대 간 기억 집합에 저장된 객체 안의 참조를 훑는 것이다. 카드 워드와 카드 번들이 그런 참조가 있는 메모리 영역을 빠르게 식별해 준다. **사용자 코드에서 온 것이 아니라서 GC 내부 루트라고 부른다.**

카드 스캐닝의 단계는 이렇다.

```text
바깥 루프: 세트된 카드의 연속 영역을 찾는다
   │
   └─→ 그런 영역마다:
         ├─ 첫 객체를 찾는다
         │    · SOH: 브릭(64.6절)의 도움을 받는다
         │    · UOH: 브릭이 없으므로 객체 단위로 훑는다
         └─ 영역 안의 객체를 하나씩 스캔한다
              참조를 가진 객체마다 그 참조가 정말 세대 간인지 확인
              그렇다면 루트로 취급하고 마킹 순회를 시작
```

이 처리 중에 GC는 **카드 효율 비율**도 계산한다 — 실제 세대 0 영역을 가리키는 카드가 몇 개인지 대비 ephemeral 영역을 가리키는 카드가 몇 개인지. 이 비율은 어느 세대를 수집할지 정할 때 쓰인다. **너무 낮으면 세대 0 대신 세대 1을 대상으로 삼는다.** 기본 임계값은 **30%**이며 `DOTNET_GCLowSkipRatio` 환경 변수로 바꿀 수 있다.

카드 루트 스캐닝은 **스택 루트 스캐닝 다음에** 수행된다. 그래서 많은 객체가 이미 방문(표시)되어 있고 다시 방문할 필요가 없다.

> **📌 낮은 카드 효율은 대개 걱정할 일이 아니다**
>
> 정기적인 internal tuning은 자연스러운 현상이다. 사용자 관점에서의 유일한 효과는 **세대 0 GC 대신 세대 1 GC를 하는 것**이고, 큰 차이가 아니다. PerfView의 "Condemned reasons for GCs" 표에서 `Internal Tuning` 열을 보면 어느 세대를 대상으로 삼으려 했는지 알 수 있다.

### GC 핸들 루트

마지막 종류는 각종 GC 핸들이다. 종류가 여럿이지만 전부 **하나의 전역 핸들 테이블 맵**에 저장된다. 특정 핸들 종류들에 대해 이 테이블이 스캔되고, 그 대상이 루트로 취급된다. 가장 중요한 두 종류는 이렇다.

| 핸들 종류 | 설명 |
|---|---|
| **강한 핸들(strong handle)** | 일반 참조와 같다. `GCHandle.Alloc` 호출로 명시적으로 만들 수 있다. CLR 자신도 내부적으로 쓴다 — 예를 들어 미리 할당해 둔 예외(`Exception`, `OutOfMemoryException`, `ExecutionEngineException`)를 담는 데 쓴다 |
| **고정 핸들(pinned handle)** | 강한 핸들의 하위 범주. `GCHandle.Alloc(obj, GCHandleType.Pinned)`로 객체를 고정하면 그 객체를 대상으로 하는 "pinned" 종류의 핸들이 만들어진다. Mark 단계에서 이 핸들들이 루트로 취급되고, 대상 객체는 **객체 헤더의 고정 비트가 세트된다.** 이 비트는 Plan 단계에서 쓰이고 GC 종료 전에 해제된다 |

고정 핸들에는 중요한 변종이 하나 더 있다 — **비동기 고정 핸들(async pinned handle)** 이다. 의미는 일반 고정 핸들과 같지만(객체를 이동 불가로 만든다), CLR이 **비동기 I/O**(파일이나 소켓 읽기·쓰기)에 내부적으로 쓴다. 이 핸들에는 추가 기능이 있다 — **비동기 I/O 작업이 완료되는 즉시 내부적으로 고정을 해제한다.** 사용자 코드의 명시적 해제를 기다리지 않는다. 덕분에 이런 흔한 연산에서의 고정이 최대한 짧아진다.

> **⚠️ `fixed` 키워드에 의한 고정과 `GCHandle`에 의한 고정은 루트가 다르다**
>
> 결과는 같다 — 힙 압축 중 객체가 이동하지 않는다. 차이는 **그 객체의 루트가 무엇인가**다. `GCHandle`은 **핸들 테이블**이 루트이고, `fixed` 키워드는 **스택**이 루트다. 진단 도구가 보여 주는 것이 달라진다. WinDbg의 SOS는 **핸들 기반 고정만** 나열할 수 있고, 스택 기반 고정은 나열하지 못한다. `\.NET CLR Memory\# of Pinned Objects` 카운터는 **둘 다** 센다. 그래서 카운터 값과 `!gchandles` 출력이 맞지 않는 것이 정상이다.

### 핸들 루트는 생각보다 훨씬 중요하다

핸들 루트는 첫눈에 보이는 것보다 현재 런타임 구현에서 훨씬 큰 역할을 한다. **고정 객체 힙에 저장되는(AppDomain당) 두 개의 결정적인 배열**이 있다.

- **인터닝된 문자열에 대한 참조를 담은 배열**
- **정적 객체에 대한 참조를 담은 배열**

이 배열들은 런타임 자신이 POH에 직접 만든다. 유용한 이유는 각종 CLR 내부 데이터가 이 배열 원소의 주소를 담기 때문이다 — 주소가 절대 바뀌지 않아야 한다.

```text
┌──────────────────────────┐
│  핸들 테이블 (비관리 메모리) │
│                          │
│  [pinned handle] ────────┼──┐
│  [strong handle] ────────┼──┼──┐
│  [strong handle] ────────┼──┼──┼──→ (사용자가 만든 임의 객체)
│  [pinned handle] ────────┼──┼──┼──→ (사용자가 고정한 객체)
└──────────────────────────┘  │  │
                              ↓  ↓
     POH (고정 객체 힙)  ┌───────────────────┐  ┌───────────────────┐
                        │ Object[]          │  │ Object[]          │
                        │ 인터닝 문자열 참조   │  │ 정적 객체 참조      │
                        │  [0] ──┐          │  │  [0] ──┐          │
                        │  [1] ──┼──┐       │  │  [1] ──┼──┐       │
                        └────────┼──┼───────┘  └────────┼──┼───────┘
                                 ↓  ↓                   ↓  ↓
     SOH / NGCH        ┌──────────────────────────────────────────┐
                       │  "Hello"   "World"    Static1   Static2   │
                       └──────────────────────────────────────────┘
                          ↑
      ┌──────────────────┴───────────────────┐
      │ 문자열 리터럴 맵 (보조 자료 구조)          │
      │  ※ 이것은 루트가 아니다. 빠른 검색용일 뿐   │
      └──────────────────────────────────────┘
```

> **⚠️ 문자열 리터럴 맵은 루트가 아니다**
>
> 위 그림에서 문자열 리터럴 맵을 굳이 그린 이유가 이것이다. 인터닝된 문자열을 살리는 것은 리터럴 맵이 아니라 **POH의 `Object[]` 배열**이고, 그 배열을 살리는 것은 **핸들 테이블의 핸들**이다. 맵은 빠른 검색을 위한 보조 자료 구조로서 그 배열의 원소를 참조할 뿐이다. `!gcroot`가 인터닝된 문자열의 루트로 리터럴 맵을 보여 주지 않는 이유다.
>
> 표기에 주의하라. 아래 실습에서 `!gcroot`는 이 배열의 루트를 `(strong handle)`로 찍지만, 같은 핸들 주소(`...015f8`)를 `!gchandles`는 `Pinned`로 나열한다. **고정 핸들은 강한 핸들의 하위 범주**이므로 둘 다 틀린 말이 아니다. 핸들의 정확한 종류가 필요하면 `!gchandles` 쪽을 믿어라.

### 실습 — WinDbg로 루트 네 종류를 확인하기

아래 프로그램으로 각기 다른 루트가 어떻게 보고되는지 본다.

```csharp
public int Run()
{
    Normal normal = new Normal();
    Pinned onlyPinned = new Pinned();
    GCHandle handle = GCHandle.Alloc(onlyPinned, GCHandleType.Pinned);
    ObjectWithStatic obj = new ObjectWithStatic();
    Console.WriteLine(ObjectWithStatic.StaticField);
    Marked strong = new Marked();
    GCHandle strongHandle = GCHandle.Alloc(strong, GCHandleType.Normal);
    string literal = "Hello world!";
    GCHandle literalHandle = GCHandle.Alloc(literal, GCHandleType.Normal);
    Console.ReadLine();
    GC.KeepAlive(obj);
    // ... 핸들 해제
    return 0;
}

public class Normal            { public long F1 = 101; }

[StructLayout(LayoutKind.Sequential)]
public class Pinned            { public long F1 = 301; }

public class Marked            { public long F1 = 401; }

public class ObjectWithStatic  { public static Static StaticField = new Static(); }

public class Static            { public long F1 = 501; }
```

`Console.ReadLine` 시점에 WinDbg를 붙이고 `!gcroot`로 하나씩 본다.

### 루트 종류별 통계 얻기

메모리 누수를 추적할 때 "어떤 종류의 루트가 지배적인가"를 아는 것이 힌트가 된다. `MarkWithType` 이벤트가 GC마다 **루트 종류별로 몇 바이트가 표시(승격)되었는지** 알려 준다. 종류는 숫자로 표현되며 `_GC_ROOT_KIND` 열거형에서 온다.

```cpp
namespace ETW
{
typedef  enum _GC_ROOT_KIND {
        GC_ROOT_STACK       = 0,
        GC_ROOT_FQ          = 1,   // 파이널라이제이션 큐
        GC_ROOT_HANDLES     = 2,
        GC_ROOT_OLDER       = 3,   // 늙은→젊은 참조
        GC_ROOT_SIZEDREF    = 4,
        GC_ROOT_OVERFLOW    = 5,
        GC_ROOT_DH_HANDLES  = 6,   // 의존 핸들
        GC_ROOT_NEW_FQ      = 7,
        GC_ROOT_STEAL       = 8,
        GC_ROOT_BGC         = 9
      } GC_ROOT_KIND;
};
```

PerfView의 Collect 대화상자에서 **GC Collect Only** 옵션만 켜도 기록된다. Events 뷰에서 프로세스로 필터링해 나열할 수 있고, CSV로 내보내 Excel 등에서 분석할 수 있다(현재 PerfView에는 이 데이터의 요약이나 그래프 표현이 없다).

> **⚠️ `MarkWithType`의 값은 누적적이고, 순서에 의존한다**
>
> `GC_ROOT_SIZEDREF`(드문 경우)를 제외하면 값들은 위 열거형의 **순서대로 누적적**이다. 각 이벤트는 "해당 루트 종류 때문에 **추가로** 승격된 바이트 수"를 말한다. 스택 루트로 이미 표시된 객체는 파이널라이제이션 루트 몫에 포함되지 않는다. 이 성질을 모르고 비율을 계산하면 완전히 틀린 결론이 나온다.

`GC_ROOT_OLDER`(값 3)가 유독 크게 나오는 애플리케이션이라면 세대 간 참조가 지배적이라는 뜻이다. 그때 **정확히 무엇이 승격되는지** 알고 싶다면 런타임의 **세대별 인식 분석(generational aware analysis)** 을 쓸 수 있다.

```text
DOTNET_GCGenAnalysisGen=<관심 있는 최소 세대>
DOTNET_GCGenAnalysisBytes=<승격 임계값, 16진수>
DOTNET_GCGenAnalysisIndex=<앞쪽 GC 몇 개를 건너뛸지>
```

`GCGenAnalysisBytes`는 **16진수**여야 한다. 16 MB 넘게 승격하는 GC를 기다리려면 `1000000`으로 설정한다. 이 변수들을 설정하고 애플리케이션을 평소대로 실행하면 작업 디렉터리에 `gcgenaware.PID.nettrace`라는 빈 파일이 생기고, 조건에 맞는 GC가 오면 데이터가 쓰인 뒤 `gcgenaware.PID.nettrace.completed` 파일이 만들어져 완료를 알린다. **일회성 분석**이므로 그 뒤로는 더 기록되지 않는다. PerfView로 열면 **Gen 0 / Gen 1 Walkable Objects Stacks** 뷰가 생기고, 이것이 정확히 "늙은 세대에서 도달 가능했던 젊은 세대 객체는 무엇인가"를 보여 준다. 자세한 워크플로는 66.13절에서 다룬다.

## 64.4 GC Info와 스택 루트 스캐닝, 어휘 범위 vs 실제 생존 범위

이 절이 이 장에서 가장 실무적 파급이 큰 절이다. "Debug에서는 되는데 Release에서는 안 된다"는 부류의 버그 대부분이 여기서 설명된다.

### 문제 설정

64.3절에서 남긴 질문은 이것이었다. **주어진 명령 주소에서, 어떤 스택 슬롯과 레지스터가 관리 객체 참조를 담고 있는가?**

64.12절에서 볼 것을 미리 당겨 쓰면, 스레드는 **안전 지점(safe point)** 에서만 멈출 수 있다. 안전 지점은 메서드가 어떻게 JIT되었느냐에 따라 거의 모든 명령이거나(완전 인터럽트 가능) 다른 메서드 호출 지점뿐이다(부분 인터럽트 가능). 어느 쪽이든 GC는 **메서드의 모든 안전 지점마다 살아 있는 스택 루트 정보**를 어떻게든 저장해 두어야 한다. 그것이 **GC Info**다.

### 어휘 범위

C#에서 지역 변수는 **어휘 범위(lexical scope)** 에 묶인다. 그 변수가 보이는 코드 영역을 정의한다. 예제를 보자.

```csharp
 1 private int LexicalScopeExample(int value)
 2 {
 3     ClassOne c1 = new ClassOne();
 4     if (c1.Check())
 5     {
 6         ClassTwo c2 = new ClassTwo();
 7         int data = c2.CalculateSomething(value);
 8         DoSomeLongRunningCall(data);
 9         return 1;
10     }
11     return 0;
12 }
```

- `c1` — `ClassOne` 객체 참조. 어휘 범위는 **메서드 전체**(3~11행). 가장 바깥 블록에 선언되었으므로.
- `c2` — `ClassTwo` 객체 참조. 어휘 범위는 **조건 블록 안**(6~9행).
- `data` — 원시 정수 값. 참조가 아니므로 GC의 관심 밖이다.

### 어휘 범위를 그대로 따르는 GC Info

가장 직관적인 접근은 도달 가능성을 어휘 범위에 맞추는 것이다. 그러면 GC Info는 이렇게 된다(완전 인터럽트 가능 코드 기준. 실제 단위는 어셈블리 명령이지만 간결하게 C# 행으로 표현한다).

```text
 1     살아 있는 슬롯 없음
 2     살아 있는 슬롯 없음
 3     c1 슬롯
 4     c1 슬롯
 5     c1 슬롯
 6     c1 슬롯, c2 슬롯
 7     c1 슬롯, c2 슬롯
 8     c1 슬롯, c2 슬롯
 9     c1 슬롯, c2 슬롯
10     c1 슬롯
11     c1 슬롯
12     살아 있는 슬롯 없음
```

부분 인터럽트 가능이라면 메서드 호출이 있는 행에만 저장된다.

```text
 3     c1 슬롯
 4     c1 슬롯
 6     c1 슬롯, c2 슬롯
 7     c1 슬롯, c2 슬롯
 8     c1 슬롯, c2 슬롯
```

물론 GC Info는 C# 변수 이름이 아니라 **스택 슬롯이나 CPU 레지스터 슬롯**으로 표현된다. JIT이 `c1`에 `rax`를, `c2`에 `rbx`를 배정했다고 하면 이렇게 된다.

```text
 1     살아 있는 슬롯: 없음
 2     살아 있는 슬롯: 없음
 3     살아 있는 슬롯: rax
 4     살아 있는 슬롯: rax
 5     살아 있는 슬롯: rax
 6     살아 있는 슬롯: rax, rbx
 7     살아 있는 슬롯: rax, rbx
 8     살아 있는 슬롯: rax, rbx
 9     살아 있는 슬롯: rax, rbx
10     살아 있는 슬롯: rax
11     살아 있는 슬롯: rax
12     살아 있는 슬롯: 없음
```

7행에서 스레드가 멈췄다면 GC는 `rax`와 `rbx`에 살아 있는 스택 루트가 있음을 즉시 안다. 그 주소에서 마킹을 시작하면 된다.

**이 접근은 완전히 유효하고 올바른 결과를 낸다.** 그리고 **Debug 모드로 컴파일하면 실제로 이렇게 동작한다.** JIT 컴파일러가 모든 지역 변수의 도달 가능성을 어휘 범위 끝까지 연장한다. 디버깅에는 대단히 유용하다 — 코드에서 더는 참조되지 않는 변수의 값도 들여다볼 수 있다.

그러나 Release 모드에서는 메모리 사용을 위해 더 할 수 있는 일이 있다.

### 즉시 루트 수집을 적용한 GC Info

같은 코드를 다시 보자. **어휘 범위가 사용을 허용한다는 것이 실제로 사용된다는 뜻은 아니다.**

- `ClassOne` 인스턴스는 **5행 이후로 쓰이지 않는다.** `c1`의 어휘 범위는 11행까지지만, 살아 있는 스택 루트인 것은 **3~4행뿐**이다.
- `ClassTwo` 인스턴스는 **6행과 7행에서만** 쓰인다.

C# 컴파일러가 각 객체의 실제 사용을 파악해서 이 정보를 저장하고, JIT 컴파일러가 슬롯 배정(수명이 짧으면 값비싼 CPU 레지스터를 재사용할 수 있다)과 GC Info 방출에 쓴다. 훨씬 효율적인 GC Info가 나온다.

```text
 1     살아 있는 슬롯: 없음
 2     살아 있는 슬롯: 없음
 3     살아 있는 슬롯: rax
 4     살아 있는 슬롯: rax
 5     살아 있는 슬롯: 없음      ← c1은 여기서 이미 죽었다
 6     살아 있는 슬롯: rax        ← rax가 c2에 재사용되었다
 7     살아 있는 슬롯: rax
 8     살아 있는 슬롯: 없음      ← c2도 여기서 이미 죽었다
 9     살아 있는 슬롯: 없음
10     살아 있는 슬롯: 없음
11     살아 있는 슬롯: 없음
12     살아 있는 슬롯: 없음
```

두 그림을 나란히 놓으면 차이가 선명하다.

```text
                    3    4    5    6    7    8    9   10   11
어휘 범위(Debug)
  c1 (ClassOne)     ████████████████████████████████████████   ← 11행까지
  c2 (ClassTwo)                    ███████████████             ← 9행까지

실제 생존 범위(Release, 즉시 루트 수집)
  c1 (ClassOne)     ██████████                                  ← 4행까지!
  c2 (ClassTwo)                    ██████████                   ← 7행까지!
                              ↑                    ↑
                       여기서 이미 수집 가능    여기서 이미 수집 가능
                       (아직 블록 안인데도)     (아직 블록 안인데도)
```

메서드 실행 시간의 대부분 동안 **살아 있는 스택 루트가 하나도 없다.** 각 객체는 더 필요하지 않게 되는 즉시 지역 변수로부터 도달 불가능한 것으로 취급된다. 이런 적극성을 **즉시 루트 수집(eager root collection)** 이라 부른다. 메모리 사용 관점에서 더 효율적이고, CPU 레지스터를 더 조밀하게 쓸 수 있다.

> **📌 스택 슬롯이 쓰이는 경우**
>
> 위 예제들은 전부 CPU 레지스터 슬롯만 썼다. 전형적인 시나리오다 — JIT은 느린 스택 슬롯 대신 빠른 레지스터를 쓰려고 최선을 다한다. 특정 상황에서는 스택 슬롯을 쓰기로 할 수 있지만 메커니즘은 같다. 스택 슬롯은 **`rsp`나 `rbp` 주소에 대한 오프셋**으로 표현되고(메서드가 어느 쪽을 쓰느냐에 따라), 그래서 GC Info는 각 안전 지점의 **현재 `rsp`·`rbp` 값도 함께 저장한다.**

### 진짜 GC Info를 보는 법

지금까지의 GC Info 표현은 전부 단순화다. 실제 GC Info는 **아주 조밀하게 압축된 이진 데이터**다. 저장 방식의 구현 세부는 흥미롭지만 우리 목적에는 무관하다. 개념은 지금까지 본 그대로다.

진단 목적으로 진짜 GC Info를 얻는 것은 아쉽게도 간단하지 않다. 편하게 해 주는 도구가 없다. 두 가지 방법이 있다.

1. **WinDbg + SOS 확장.** 주된 방법이며 아래에서 쓴다.
2. **런타임의 JIT 로그 기능.** 적절한 플래그를 켜면 GC Info까지 방출한다. 다만 **.NET 런타임의 로컬 Debug 빌드가 필요**해서 복잡하다. .NET 팀의 JIT 개발자가 만든 **Disasmo** 도구를 쓰면 편해진다.

> **⚠️ 계층 컴파일 때문에 실험이 재현되지 않는다**
>
> 계층 컴파일(tiered compilation)은 .NET Core 3.0부터 기본으로 켜져 있다. **Tier0 최적화는 즉시 루트 수집을 제공하지 않는다.** 그래서 이 절과 다음 절의 코드 조각들을 그대로 실행해도 같은 결과가 나오지 않는다. 완전히 최적화된 JIT 코드를 보려면 둘 중 하나를 해야 한다.
>
> ```xml
> <TieredCompilation>false</TieredCompilation>
> ```
>
> ```csharp
> [MethodImpl(MethodImplOptions.AggressiveOptimization)]  // 즉시 최상위 계층으로
> ```
>
> 또는 해당 메서드를 충분히 여러 번 호출해서 Tier1으로 승격시키면 된다. **즉시 루트 수집은 Release 모드이면서 Tier1으로 승격된 메서드에서만 동작한다.**

> **📌 GC Info의 내부 저장 방식**
>
> 완전 인터럽트 가능 메서드의 GC Info는 **코드 자체 크기에 맞먹는 저장 공간**을 요구할 수 있다. 디코딩 시간과 저장 효율의 타협으로, GC Info의 주된 부분은 **대응 코드 영역에 걸친 스택 루트 생존 변화(liveness change)를 나타내는 비트 덩어리**로 저장된다. 더해서 각 덩어리마다 **초기 생존 상태**를 기억한다. 특정 코드 오프셋의 스택 루트 생존을 디코딩하려면, 해당 덩어리를 초기 생존 상태부터 시작해 관심 오프셋까지 변화를 하나씩 적용하면 된다. SOS의 `gcinfo` 확장 명령은 이 작업을 메서드의 모든 유효 명령 오프셋에 대해 반복해서 위와 같은 요약을 만든다.

**안전 지점이 메서드 호출 지점에만 세트되었다.** 런타임 내부 메서드(할당자)를 부르는 곳과 다른 관리 메서드(생성자 포함)를 부르는 곳 둘 다다.

그런데 주의 깊은 독자라면 놀랐을 것이다. 앞에서 예상한 GC Info(부분 인터럽트 가능 + 즉시 루트 수집)와 정확히 일치하지 않는다. 안전 지점 다섯 개가 방출된 것은 맞지만 **어느 것도 살아 있는 루트를 보고하지 않는다.** 왜인가?

**스레드 중단은 메서드가 호출될 때가 아니라 메서드가 반환할 때 일어나기 때문이다**(64.12절). `ClassOne.Check` 호출 지점의 안전 지점 관점에서는 정말로 살아 있는 루트가 필요 없다. 메서드가 곧 호출될 것이고, `this` 인자는 `rcx` 레지스터로 전달된다. 그 시점에 EE 중단이 필요해지면 **인자를 살려 두는 것은 `Check` 메서드의 책임**이다(필요한 동안). 호출자(`LexicalScopeExample`) 관점에서는 `Check`가 끝난 뒤 `ClassOne` 인스턴스가 더는 필요 없다. 그래서 살아 있는 루트가 보고되지 않는다. 나머지 안전 지점도 같은 이야기다.

> **⚠️ 안전 지점에 루트가 없다고 "이 시점에 아무것도 살아 있지 않다"고 읽으면 안 된다**
>
> 호출된 메서드가 자기 프레임에서 인자를 살려 두고 있다. 스택 워커는 **프레임을 하나씩 거슬러 올라가며** 각 프레임의 GC Info를 적용한다. 어느 한 프레임의 GC Info만 보고 판단할 수 없다. `!gcroot`가 보여 주는 것도 이 전체 워킹의 결과다.

### 완전 인터럽트 가능 코드는 어떻게 보이는가

완전 인터럽트 가능 코드를 보려면 그런 메서드를 직접 써야 한다. 완전/부분 인터럽트 가능 중 무엇을 방출할지는 **전적으로 JIT의 판단**이다. 다만 **반복 횟수가 동적인 비자명한 루프**를 쓰면 완전 인터럽트 가능 버전이 나올 가능성이 높아진다.

```csharp
private int RegisterMap(int value)
{
    int total = 0;
    SomeClass local = new SomeClass(value);
    for (int i = 0; i < value; ++i)
    {
        total += local.DoSomeStuff(i);
    }
    return total;
}

public int DoSomeStuff(int value)
{
    return value * value;
}
```

### 추적되지 않는 루트(untracked root)

`!gcinfo`나 `!u -gcinfo` 출력에서 **untracked**라고 표시된 루트를 만날 수 있다. 참조를 담고 있지만 **수명 정보가 런타임에 없는** 인자나 지역 변수를 뜻한다. GC는 이런 위치를 **메서드 본문 전체에 걸쳐 살아 있는 것으로 가정한다**(값이 0이 아닌 한).

> **💡 `null` 대입이 의미 있는 유일한 경우**
>
> 다음 절에서 보겠지만 "GC에게 알려 주려고" 지역 변수에 `null`을 넣는 것은 대개 불필요하다. **추적되지 않는 변수가 그 예외다.** 이들은 메서드 전체에 걸쳐 살아 있는 것으로 간주되므로, 정말로 중요한 리소스라면 `null`을 넣어 JIT을 도울 여지가 있다. 다만 어떤 변수가 추적되지 않는지는 GC Info를 봐야만 알 수 있고, 실무에서 이 최적화가 정당화되는 경우는 극히 드물다.

### 고정된 지역 변수

고정된 지역 변수는 특별한 종류의 지역 변수다. C#과 F#에서 `fixed` 키워드를 쓸 때 **암묵적으로** 만들어진다(60.8절). VB.NET에는 포인터가 아예 없어서 이 키워드도 없다.

```csharp
static unsafe void TestPinning()
{
    var array = new byte[50];
    var weakRef = new WeakReference(array);
    fixed (byte* b = &array[26])
    {
        *b = 0x55;
    }
    DoCheck(weakRef);
}
```

이 메서드의 CIL을 보면(sharplab.io 등으로) 특별한 **고정 지역 변수**가 보인다 — 여기서는 인덱스 1번이다.

```il
.method private hidebysig static
void TestPinning () cil managed noinlining flag(0200)
{
  // Method begins at RVA 0x2050
  // Code size 37 (0x25)
  .maxstack 2
  .locals init (
        [0] class [System.Runtime]System.WeakReference weakRef,
        [1] uint8& pinned
  )
  // ...
}
```

`pinned` 키워드는 이름 그대로다 — **이 지역 변수의 내용은 GC가 이동시켜서는 안 된다.** 타입은 `uint8&`, 즉 `byte`에 대한 주소다.

이 정보를 JIT 컴파일러가 소비해서 적절한 GC Info를 만든다. 이번에는 루트 정보와 함께 **그것이 고정되었다는 정보도** 보존된다.


한 줄씩 보자. 메서드 시작에서 `sp+30`과 `sp+28` 스택 위치가 0으로 채워진다. 몇 줄 뒤 새로 할당된 `byte[]` 배열의 참조가 `rbx`에 저장된다. 다시 몇 명령 뒤 `rbx`가 증가해서 배열 객체 **안쪽** 데이터의 주소가 된다. 그 주소가 `sp+30` 위치에 저장된다. **이 줄 이후에 스레드가 중단되면 GC는 이 주소를 보고 객체 전체를 고정된 것으로 취급한다.** 그래서 `sp+30` 루트에 **interior** 표시도 붙어 있다 — 그 주소가 배열 객체 내부를 가리키기 때문이고, GC가 이를 적절히 해석한다.

`fixed` 블록이 끝나면 `sp+30`에 0이 쓰인다. **0이면 살아 있는 루트가 아니다.** 이것이 `fixed` 블록의 종료를 GC에 알리는 방식이다.

> **⚠️ 지역 변수에 의한 고정은 메모리 덤프에서 거의 보이지 않는다**
>
> 이런 고정 루트는 **아주 짧은 시간 동안만** 존재한다 — 감싸는 메서드가 실행되는 동안뿐이다. 그리고 실제로 "고정됨"으로 표시되는 것은 **GC 실행 중, 스택 루트 스캐닝 단계에서**뿐이다. Plan 단계에서 고정 비트는 지워진다. 그래서 **메모리 덤프를 뜨면 이들은 아예 고정되어 있지 않다.** 이런 고정의 출처를 찾는 것이 자명하지 않은 이유다.
>
> 어떤 도구는 이런 고정 출처를 나열해 준다. 현재 스레드에서 실행 중인 모든 메서드의 GC Info와 지역 변수 상태를 알면 "지금 GC가 일어난다면 어떤 변수가 고정될까"를 계산할 수 있다. 물론 근사치다 — 실제 GC라면 스레드가 안전 지점에서 멈출 것이고 지금 있는 자리가 아닐 것이다. 게다가 덤프는 한 시점의 스냅숏일 뿐이다.
>
> **다행히 `PinObjectAtGCTime`이라는 ETW 이벤트가 객체가 고정될 때마다 방출된다.** 지역 고정 변수를 포함해 고정되는 모든 객체를 알 수 있는 훌륭한 정보원이다. 64.7절에서 실제로 쓴다.

> **📌 `goto`는 이 메커니즘을 깨뜨리지 않는다**
>
> `goto`가 프로그램 제어를 레이블로 무조건 점프시키니, 스택 루트 메커니즘을 망가뜨릴 수 있지 않을까? 갑자기 완전히 다른 코드 블록에서 완전히 다른 데이터 집합을 쓰게 될 테니까.
>
> 다행히 `goto`는 그렇게 강력하지 않다. C# 언어 명세는 레이블(=`goto` 대상)에 대해 이렇게 말한다. "레이블은 그 레이블의 범위 안에 있는 `goto` 문에서 참조될 수 있다. 이는 `goto` 문이 블록 안에서 그리고 블록 밖으로 제어를 옮길 수 있지만 **블록 안으로는 결코 옮길 수 없다**는 뜻이다." 따라서 `goto`는 메서드 밖의 다른 메서드로 뛸 수 없고, 중간 코드를 건너뛰어 중첩 블록 안으로 뛸 수도 없다. 즉 **`goto`는 안전하게 설계되었다.** 실행되는 `goto`는 메서드 안의 적절한 코드 블록으로 명령 포인터를 바꾸는 것 이상이 아니다.

## 64.5 즉시 루트 수집(eager root collection)

64.4절에서 메커니즘을 보았다. 이 절은 그 **결과**를 본다. 즉시 루트 수집은 놀랍고 때로는 오해를 부르는 동작을 만든다. "Debug에서는 X인데 Release에서는 Y다"로 시작하는 질문 대부분이 여기 뿌리를 둔다.

### `null` 대입은 거의 언제나 불필요하다

"이제 이 객체 안 쓴다"고 GC에게 알리려고 지역 변수에 `null`을 넣는 것은 대부분 필요 없다.

```csharp
private int LexicalScopeExample(int value)
{
    ClassOne c1 = new ClassOne();
    if (c1.Check())
    {
        c1 = null;                                  // 불필요
        ClassTwo c2 = new ClassTwo();
        int data = c2.CalculateSomething(value);
        c2 = null;                                  // 불필요
        DoSomeLongRunningCall(data);
        return 1;
    }
    return 0;
}
```

긴 호출 직전이라도 마찬가지다. 즉시 루트 수집 덕분에 컴파일러와 JIT이 변수의 실제 사용 범위를 완벽히 파악한다. 명시적으로 알려 줄 필요가 없다. **위 코드와 64.4절의 원본 코드는 그 점에서 완전히 동일하다.** 같은 GC Info와 같은 어셈블리 코드를 만든다(JIT이 저 불필요한 `null` 대입을 애초에 최적화로 제거한다).

예외는 앞 절에서 말한 **추적되지 않는 변수**뿐이다.

### 부작용이 있는 객체에서 이상한 일이 생긴다

즉시 루트 수집이 문제가 되는 것은 **객체의 수명 자체에 부작용이 묶여 있을 때**다. 어휘 범위에 맞춰 부작용이 지속되기를 기대하지만 실제 수명은 어휘 범위를 따르지 않는다. 전형적인 시나리오는 각종 **타이머**, **동기화 프리미티브**(`Mutex` 등), **시스템 전역 리소스 접근**(파일 등)이다.

```csharp
 1 static void Main(string[] args)
 2 {
 3     Timer timer = new Timer((obj) => Console.WriteLine(DateTime.Now.ToString()),
                               null, 0, 100);
 4     Console.WriteLine("Hello World!");
 5     GC.Collect(); // 여기서 GC가 일어난다고 가정
 6     Console.ReadLine();
 7 }
```

직관적으로는 `timer`의 어휘 범위에 맞춰 `Timer` 객체가 살아 있어야 한다. 키를 누를 때까지 현재 시각이 끝없이 출력되어야 한다. **Debug 빌드에서는 실제로 그렇게 동작한다.**

Release 빌드에서는 즉시 루트 수집이 개입한다. `Timer` 객체는 3행 이후 쓰이지 않으므로 JIT이 GC Info에 그렇게 반영한다. **3행 이후 `Timer` 객체는 도달 불가능이다!** `Main`이 그 줄 이후를 실행하는 동안 GC가 일어나면 수집된다 — 타이머가 멈추고 시각이 더는 출력되지 않는다.

```text
프로그램 출력:
Hello World!
12/18/2023 7:49:52 PM
```

한 번 찍고 끝이다.

> **⚠️ 이 예제에서 `GC.Collect()`는 재현성을 위한 것이다**
>
> 실제 상황에서는 **다른 스레드의 할당 때문에** GC가 일어난다. 그래서 이 버그는 부하가 걸릴 때만, 프로덕션에서만 나타난다. 개발 머신에서는 GC가 그 짧은 창에 걸리지 않아 재현되지 않는다.

### 메서드가 실행 중인데도 객체가 죽는다

즉시 루트 수집은 여기서 멈추지 않는다. **객체의 메서드가 아직 실행 중인데도 그 객체가 도달 불가능으로 취급될 수 있다** — 그 메서드가 `this`를 참조하지 않는다면.

```csharp
static void Main(string[] args)
{
    SomeClass sc = new SomeClass();
    sc.DoSomething("Hello world!");
    Console.ReadKey();
}

class SomeClass
{
    public void DoSomething(string msg)
    {
        GC.Collect();
        Console.WriteLine(msg);
    }

    ~SomeClass()
    {
        Console.WriteLine("Killing...");
    }
}
```

```text
프로그램 출력:
Killing...
Hello world!
```

**메서드 전체가 실행되기 전에 객체가 죽었다.** `DoSomething`이 `this`를 참조하지 않으므로 사실 자기 객체 인스턴스가 필요 없기 때문이다.

더 나아간다. 특정 상황에서는 **메서드가 `this`를 참조하는데도** 객체가 즉시 수집될 수 있다.

```csharp
static void Main(string[] args)
{
    SomeClass sc = new SomeClass() { Field = new Random().Next() };
    sc.DoSomethingElse();
    Console.ReadKey();
}

class SomeClass
{
    public int Field;

    public void DoSomethingElse()
    {
        Console.WriteLine(this.Field.ToString());
        GC.Collect();
        Console.WriteLine("Am I dead?");
    }

    ~SomeClass()
    {
        Console.WriteLine("Killing...");
    }
}
```

```text
프로그램 출력:
615323
Killing...
Am I dead?
```

`this.Field`를 읽고 나면 그 이후로 `this`가 쓰이지 않는다. 즉시 루트 수집에는 그것으로 충분하다.

> **⚠️ 이것이 파이널라이저를 위험하게 만든다**
>
> 34장에서 다루겠지만 여기서 한 번 못박아 둔다. 파이널라이저는 **객체의 다른 메서드가 아직 실행 중일 때 실행될 수 있다.** 파이널라이저가 필드를 해제하고, 그 필드를 실행 중인 메서드가 쓰고 있으면 조용히 깨진다. 이것이 `GC.KeepAlive`와 `SafeHandle`이 존재하는 근본 이유다.

> **📌 겁먹을 필요는 없다**
>
> 이런 최적화는 아주 흔하다. JIT은 지역 변수 수명을 최대한 짧게 만들려고 매우 공격적이다. 그러나 **대부분의 경우 이 기법은 프로그램 논리를 바꾸지 않으므로 안전하다.** 여기서 나오는 예상 밖의 동작은 매우 드물고, **수명에 부작용이 묶인 객체**에만 해당한다. `String` 객체가 메모리에 있다고 해서 무언가가 일어나지는 않는다 — 그냥 거기 있을 뿐이다. `Timer`는 다르다. 힙에 `Timer` 객체가 존재한다는 사실 자체가 스레드 풀 스레드로 하여금 메서드를 주기적으로 호출하게 만든다. 이런 타입은 흔치 않다.

### `GC.KeepAlive`

객체 수명을 더 잘 제어해야 할 때가 있다. 앞의 `Timer` 예제에서 정말로 애플리케이션 전 수명 동안 타이머가 돌아야 한다면. 이를 위한 것이 `GC.KeepAlive`다.

```csharp
static void Main(string[] args)
{
    Timer timer = new Timer((obj) => Console.WriteLine(DateTime.Now.ToString()),
                            null, 0, 100);
    Console.WriteLine("Hello World!");
    GC.Collect(); // 여기서 GC가 일어난다고 가정
    Console.ReadLine();
    GC.KeepAlive(timer);
}
```

`GC.KeepAlive`는 정말 단순한 트릭이다. 구현에 **코드가 하나도 없다.**

```csharp
[MethodImplAttribute(MethodImplOptions.NoInlining)] // 최적화 방지
[Intrinsic]
public static void KeepAlive(Object obj)
{
}
```

`[MethodImpl(MethodImplOptions.NoInlining)]`이 인라이닝을 막고, 그것이 컴파일러로 하여금 **전달된 인자를 사용된 것(따라서 도달 가능한 것)으로 취급하게** 만든다. 그래서 `GC.KeepAlive`를 쓰면 GC Info가 대상 객체의 수명을 **그 호출 지점까지** 연장한다.

> **📌 빈 메서드도 비용이 있다 — 그래서 intrinsic이 되었다**
>
> JIT이 최적화로 제거할 수 없는 빈 메서드는 그 자체로 오버헤드다. 이를 해결하려고 **.NET 5부터 `KeepAlive`는 JIT intrinsic이 되어 특별 취급을 받는다.** 위 소스의 `[Intrinsic]` 특성이 그것이다.

> **💡 대부분의 경우 `Dispose`가 더 나은 답이다**
>
> `Mutex`나 `Timer`처럼 이런 부작용을 갖는 객체는 대개 `IDisposable`을 구현한다. `Main` 끝에서(또는 `using` 절로) `timer.Dispose()`를 호출하면 **수명이 적절히 연장되면서 리소스도 제대로 해제된다.** `GC.KeepAlive`를 부를 필요가 없다.
>
> 아이러니한 지점이 여기 있다. **타이머를 어디서 폐기할지 명시함으로써 그 지점까지 살아 있게 만드는 것이다.** `Dispose` 인스턴스 메서드를 호출하려면 `timer`의 값이 `this` 인자로 전달되어야 하고, 그러려면 살아 있어야 하기 때문이다.
>
> 그렇다고 즉시 수집의 함정을 잊어도 된다는 뜻은 아니다. `Dispose`가 없는 타입, 또는 `Dispose`를 부르는 시점보다 앞에서 부작용이 필요한 경우가 여전히 있다. 34.8절에서 `GC.KeepAlive`가 반드시 필요한 경우를 따로 다룬다.

### 정리

| 상황 | Debug 빌드 | Release 빌드 + Tier1 |
|---|---|---|
| 지역 변수 수명 | **어휘 범위 끝까지** 인위적으로 연장 | 마지막 실제 사용 지점까지 |
| `Timer` 예제 | 계속 틱한다 | **한 번 찍고 멈춘다** |
| `this`를 안 쓰는 메서드 실행 중 | 객체가 산다 | **파이널라이저가 먼저 돈다** |
| CPU 레지스터 재사용 | 제한적 | 적극적 |
| 디버거에서 변수 조사 | 가능 | 이미 죽어서 못 볼 수 있다 |

> **⚠️ 계층 컴파일 때문에 Release 빌드에서도 재현되지 않을 수 있다**
>
> 다시 강조한다. **Tier0 최적화는 즉시 루트 수집을 제공하지 않는다.** 위 예제들을 Release로 빌드해서 그냥 실행하면 "정상" 동작할 수 있다. 그리고 그 메서드가 충분히 여러 번 호출되어 Tier1으로 승격되는 순간 **프로덕션에서 갑자기 동작이 바뀐다.** 이것이 이 부류의 버그를 가장 악랄하게 만드는 요소다. 재현하려면 `<TieredCompilation>false</TieredCompilation>`을 넣거나 `[MethodImpl(MethodImplOptions.AggressiveOptimization)]`을 붙여라.

## 64.6 Plan 단계 — plug와 gap, 브릭 테이블, 세대 경계, 강등

Mark 단계가 끝나면 모든 객체는 도달 가능한지 아닌지가 판별되어 있다. 도달 가능한 것은 전용 비트로 마킹되었고, 그중 일부는 또 다른 비트로 **고정됨(pinned)** 표시가 추가로 붙어 있다. 이제 GC는 일을 계속할 정보를 다 갖췄다. 그런데 질문이 하나 남는다.

**Sweep으로 갈 것인가, Compact로 갈 것인가?**

이전 수집의 결과를 보고 추측할 수도 있다. 하지만 GC는 더 나은 방법을 쓴다 — **현재 조건에서 결과가 어떻게 될지 직접 계산한다.** 예측되는 단편화 같은 요소를 보고 압축할 가치가 있는지 판단한다.

여기에 역설이 있다. **압축 결과를 정확히 예측하려면 실제로 압축을 해봐야 한다.** 특히 고정 때문에 정확한 예측이 쉽지 않다.

Plan 단계가 하는 일이 바로 이것이다. **객체를 실제로 옮기지 않으면서 압축을 시뮬레이션한다.** 이렇게 해서 압축 결과에 대한 정밀한 정보를 얻고, 그 데이터로 결정을 내린다.

게다가 이렇게 준비한 정보는 이후 Compact 단계와 Sweep 단계가 **그대로 소비한다.** 압축 결과가 유망하면 수집한 정보를 직접 써서 압축하고, Sweep으로 충분하면 그 정보를 그대로 스윕에 쓴다. 시뮬레이션 결과가 버려지는 일은 드물다 — 가장 잦은 수집인 gen0·gen1이 대체로 압축이기 때문이다.

> **📌 Plan 단계가 GC의 진짜 엔진이다**
>
> 어떤 의미에서 Plan 단계는 GC 전체 과정의 **주력 마력**이다. 무겁고 필요한 계산을 전부 여기서 한다. Sweep이나 Compact 단계는 그 계산 결과를 꽤 단순하게 소비할 뿐이다.
>
> GC를 "Mark-Sweep-Compact"로 설명하는 문헌이 많고, Plan 단계는 흔히 빠진다. 이 절을 읽고 나면 왜 그것이 부당한 생략인지 알게 된다.

이 장에서 설명하는 과정은 SOH(gen 0/1/2)와 UOH(LOH·POH)에서 조금 다르다. 더 복잡한 SOH부터 본다.

### plug와 gap

GC 시작 시점의 관리 힙 한 조각을 상상해보자. 객체들이 서로 붙어 있다. 각 객체는 헤더, 메서드 테이블 포인터, 그리고 최소 포인터 크기 필드 하나로 구성된다(54.3절). 어떤 것은 크고 어떤 것은 작다.

```text
GC 시작 시점의 힙 조각
┌────┬────┬─────────┬────┬────┬──────┬────┬────┬───────────┬────┬────┬────┐
│ H  │ MT │ 필드들   │ H  │ MT │ 필드 │ H  │ MT │  필드들    │ H  │ MT │필드│
└────┴────┴─────────┴────┴────┴──────┴────┴────┴───────────┴────┴────┴────┘
   객체 A (48B)        객체 B (32B)      객체 C (56B)         객체 D (24B)
```

Mark 단계가 끝나면 도달 가능한 객체가 마킹된다.

```text
Mark 이후 (■ = 마킹됨, □ = 마킹 안 됨)
┌──────────────┬────────────┬─────────────────┬──────────┐
│   ■ 객체 A    │  □ 객체 B   │    ■ 객체 C      │ ■ 객체 D  │
└──────────────┴────────────┴─────────────────┴──────────┘
```

Plan 단계에서는 **수집 대상 세대와 그보다 젊은 세대를 객체 단위로 스캔한다.** 객체 크기는 메서드 테이블 정보로 계산한다. 배열이라면 기본 크기 + 원소 크기 × 원소 개수다. 스캔 중에는 전용 포인터를 현재 객체 크기만큼 전진시켜 다음 객체로 점프한다.

**어떤 의미에서 힙은 거대한 연결 리스트다.** 각 객체의 크기가 다음 객체의 주소를 계산하는 데 쓰이기 때문이다.

그런데 이건 객체 사이에 빈 공간이 없을 때만 동작한다. 힙은 거의 항상 단편화되어 있는데, 빈 공간을 만나면 다음 객체를 어떻게 찾나?

답은 63.2절에서 이미 봤다. **힙에 빈 공간이 생기면 GC가 그것을 더미 "Free" 객체로 채운다.** 전용 메서드 테이블 항목을 가진 배열처럼 동작하고, 원소는 각 1바이트다. 이 가짜 배열의 원소 개수가 빈 영역 전체를 덮도록 조정된다. 이렇게 하면 힙을 걸을 때 GC(그리고 같은 기법을 쓰는 디버거)가 빈 공간을 **실제 객체처럼 "점프"할 수 있다.**

Plan 단계의 핵심 원리는 객체 단위 스캔 중에 **마킹된 객체와 마킹 안 된 객체를 그룹으로 묶는 것**이다. 두 종류의 그룹이 만들어진다.

| 그룹 | 정의 |
|---|---|
| **plug** | 인접한 마킹된(도달 가능한) 객체들의 묶음 |
| **gap** | 인접한 마킹 안 된(도달 불가능한) 객체들의 묶음 |

```text
힙을 plug와 gap으로 분할
┌──────────────┬────────────┬─────────────────────────────┐
│    plug 1     │   gap 1     │          plug 2              │
│  ■■■■■■■■     │  □□□□□□     │       ■■■■■■■■■■■■           │
└──────────────┴────────────┴─────────────────────────────┘
     48 B          32 B                   80 B
```

힙 전체를 plug와 gap의 연속으로 쪼개면 필요한 정보를 효율적으로 계산할 수 있다.

- **각 gap의 크기와 위치** — Sweep 수집이 선택되면 대부분의 gap이 프리 리스트가 관리하는 빈 공간이 된다.
- **각 plug의 재배치 오프셋(relocation offset)과 위치** — Compact 수집이 선택되면 각 plug가 그 오프셋만큼 이동한다.

### 재배치 오프셋은 어떻게 계산되는가

가장 단순한 시나리오라면 **이전 gap들의 크기 누적**으로 계산할 수 있다. 하지만 실제 구현은 훨씬 복잡하다. **자체 내부 할당자**를 써서 각 plug가 재배치될 적절한 주소를 찾고, 실제로 옮기는 대신 그 주소를 기록한다.

plug가 고정되지 않아 이동 가능한 단순한 경우, 범프 포인터 할당자가 각 plug를 나란히 배치한다. 다음은 내부 할당자 관점에서 본 "가상 공간" — 압축 후 힙이 어떻게 보일지의 표현이다.

```text
(a) 할당 포인터를 세대 시작으로 리셋
    할당 포인터 ↓
    ├──────────────────────────────────────────────

(b) 첫 plug(객체 1개)를 만남 → 할당 포인터 위치에 공간 예약, 포인터 전진
    ┌──────┐  할당 포인터 ↓
    │plug 1│
    └──────┘
    ← reloc offset 1 →  (새 위치와 옛 위치의 차이를 기억)

(c) 다음 plug(객체 3개) → 직전 "할당된" plug 바로 뒤에 공간 예약
    ┌──────┬────────────────┐  할당 포인터 ↓
    │plug 1│     plug 2      │
    └──────┴────────────────┘

(d) 마지막 plug도 같은 로직
    ┌──────┬────────────────┬──────────┐  할당 포인터 ↓
    │plug 1│     plug 2      │  plug 3  │
    └──────┴────────────────┴──────────┘
```

모든 재배치 오프셋이 계산되었으므로, GC는 **압축이 일어난다면 할당 포인터의 최종값이 얼마인지 정확히 안다.** 이 정보로 **압축 효율(compaction efficiency)** 을 계산하고, 나중에 압축 여부 결정에 쓴다.

> **📌 압축이 얼마나 이득인가는 뺄셈 한 번이다**
>
> 위 예에서 압축 후 모든 객체가 차지하는 공간은 **할당 포인터의 초기값과 최종값의 차이**만큼 줄어든다. 그게 전부다.

정리하면, 객체를 plug와 gap으로 조직함으로써 완전한 정보 집합을 매우 효율적으로 얻는다.

- 압축 효율은 얼마인가?
- Sweep 수집이라면 프리 리스트 항목을 **어디에** 만들어야 하는가(gap)?
- Compact 수집이라면 도달 가능한 객체를 **어디로** 옮겨야 하는가(plug)?

> **📌 .NET 소스를 직접 보고 싶다면**
>
> 이 모든 것이 `gc_heap::plan_phase` 메서드에서 일어난다. 이 메서드 안에서 연속된 객체를 스캔하며 plug와 gap을 발견한다. 각 plug의 새 위치는 `allocate_in_condemned_generations` 또는 `allocate_in_older_generations`를 호출해 계산한다. 여기서 시작하면 된다(83.2절).

### plug 정보는 어디에 저장되는가

다음 질문 — plug와 gap 관련 데이터를 어디에 저장할까? GC가 전용 메모리 영역을 쓸 수도 있다. 하지만 작은 gap과 plug가 많이 교차하는 시나리오에서는 그 영역이 메모리를 엄청나게 잡아먹는다. 게다가 관리 힙과 별도 메모리 영역을 번갈아 접근하는 것은 **CPU 캐시 사용 관점에서 최악**이다(61.4절).

GC는 이미 관리 힙 메모리 영역을 집중적으로 쓰고 있다. 그렇다면 그것을 재사용하면 되지 않을까? Microsoft .NET이 택한 접근이 정확히 이것이다.

gap과 plug가 적절히 구성되면 **각 plug 앞에는 대응하는 gap이 온다.** GC가 객체를 교차하는 plug/gap으로 묶는 이유가 여기 있다 — 이렇게 하면 **각 plug 앞, 즉 직전 gap의 끝에** 관심 있는 정보를 저장할 수 있다. gap의 내용은 안전하게 덮어써도 된다. 더 이상 쓰이지 않을 도달 불가능한 객체만 들어 있기 때문이다.

```text
        gap 1                         plug 2
┌──────────────────────┬──────────────────────────────┐
│  □□□□□□□  │plug info│ │  ■■■■■■■■■■■■■■■■■■         │
└──────────────────────┴──────────────────────────────┘
                ↑
        24바이트(64비트) / 12바이트(32비트)
        · 대응 gap 크기
        · plug 재배치 오프셋 (하위 2비트는 별도 용도)
        · left / right 오프셋 (BST 자식 위치)
```

plug 정보는 64비트 런타임에서 정확히 **24바이트**, 32비트에서 **12바이트**를 차지한다. 대응 gap 크기, plug 재배치 오프셋, 그리고 나중에 설명할 추가 데이터(재배치 오프셋의 일부인 2비트와 left/right 오프셋)를 담는다.

> **⚠️ 최소 객체 크기 24바이트의 진짜 이유가 여기 있다**
>
> 54.3절에서 "빈 객체도 64비트에서 24바이트여야 한다"고 했다. GC 설계 요구라고만 말하고 넘어갔는데, **진짜 이유가 이것이다.**
>
> plug 앞의 gap에는 최소한 객체 하나가 들어 있고, 따라서 최소 24바이트다. plug 정보를 저장할 공간이 **항상 충분함을 보장하는 우아한 방법**인 것이다. 최소 객체 크기와 plug 정보 크기가 같은 24바이트인 것은 우연이 아니다.

### 왜 이진 탐색 트리인가

GC가 압축을 결정하면 이 plug 정보를 아주 많이 쓴다. 특히 **"GC가 끝난 뒤 이 객체의 새 주소는 무엇인가?"** 에 답하는 데 필요하다.

답하는 방법은 이렇다. 주소 X가 어떤 plug에 속하는지 확인하고, 속한다면 X에서 그 plug의 재배치 오프셋을 뺀다.

이 질문은 **정말, 정말 자주** 나온다. 그래서 이 계산을 최대한 효율적으로 만드는 데 어떤 노력도 아끼지 않는다. plug를 **이진 탐색 트리(BST)** 로 조직하는 이유가 이것이다.

각 plug 정보는 앞서 본 것처럼 left/right 오프셋을 담는다. 이 오프셋은 각각 왼쪽·오른쪽 자식 plug 정보의 위치를 가리키고, 자식이 없으면 0이다. 이것이 모든 plug 주소를 담는 **이진 plug 트리**의 기반 구조다. 이 트리는 균형 잡히게 만들어져, 어떤 노드든 왼쪽 자식들은 더 작은 주소에, 오른쪽 자식들은 더 큰 주소에 있다.

> **📌 트리의 주소는 plug의 첫 객체를 가리킨다**
>
> plug 트리의 주소는 plug 안 첫 객체의 주소(CLR에서 늘 그렇듯 MT 필드)를 가리킨다. GC는 그것과 연관된 상수 오프셋으로 plug 정보를 어디서 찾을지 안다.

> **⚠️ Plan 단계 중에 캡처한 메모리 덤프는 못 쓴다**
>
> 문제 조사 중에 전체 메모리 덤프를 떴는데 데이터 구조가 무효라 쓸 수 없는 경우가 있다. 대부분의 SOS 명령에서 이런 메시지가 나온다.
>
> ```text
> > !dumpheap -stat
> The garbage collector data structures are not in a valid state for traversal.
> It is either in the "plan phase," where objects are being moved around, or we are at
> the initialization or shutdown of the gc heap. Commands related to displaying, finding
> or traversing objects as well as gc heap segments may not work properly. !dumpheap and
> !verifyheap may incorrectly complain of heap consistency errors.
> ```
>
> 덤프가 **GC 계획 단계 중에** 캡처되었을 수 있다는 뜻이다. 그 순간 객체가 "정상 상태"라는 보장이 없다 — 힙을 정상적인 방법(리전 시작에서 객체 크기만큼 전진)으로 걸을 수 없기 때문이다. .NET 코드에는 Plan 단계 주위에 이런 가드가 있다.
>
> ```text
> GCScan::GcRuntimeStructuresValid (FALSE);
> plan_phase (n);
> GCScan::GcRuntimeStructuresValid (TRUE);
> ```
>
> **런타임에서 이런 보호가 걸린 유일한 곳이다.** GC 관련 코드를 실행 중인 스레드를 찾아 확인할 수 있다.
>
> | 심볼 조합 | 환경 |
> |---|---|
> | `coreclr!wks` | .NET, 워크스테이션 GC |
> | `coreclr!srv` | .NET, 서버 GC |
> | `clr!wks` | .NET Framework, 워크스테이션 GC |
> | `clr!srv` | .NET Framework, 서버 GC |
>
> ```text
> > !findstack coreclr!wks
> Thread 000, 6 frame(s) match
>   * 00 000000a963b7cd30 CoreCLR!WKS::gc_heap::plan_phase+0xa9
>   * 01 000000a963b7ce40 CoreCLR!WKS::gc_heap::gc1+0x178
>   * 02 000000a963b7ceb0 CoreCLR!WKS::gc_heap::garbage_collect+0x5ca
>   * 03 000000a963b7cf20 CoreCLR!WKS::GCHeap::GarbageCollectGeneration+0x191
> ```
>
> `gc_heap::plan_phase`를 실행 중인 스레드가 있으면 Plan 단계 한복판인 게 명백하다.
>
> **단, 같은 메시지가 다른 이유로도 나온다.** 저자들의 경험상 SOS 버전이 런타임과 맞지 않을 때(예: .NET 4.0 런타임에 2.0용 SOS)도 이 메시지가 뜬다. 덤프를 의심하기 전에 SOS 버전부터 확인하라.

### 브릭 테이블

plug 트리의 루트는 어딘가에 저장되어야 한다. 관리 힙 전체에 대해 **거대한 plug 트리 하나**를 만드는 것은 비현실적이다.

- 연속된 gap과 plug를 조사하면서 트리에 새 항목을 추가할 때마다 **재균형**이 필요할 수 있다. 모든 plug를 덮는 거대한 트리라면 이게 매우 비싸다.
- 조회 시 그런 트리를 순회하는 것도 비싸다 — 트리 레벨을 여러 층 건너뛰어야 하기 때문이다.

훨씬 실용적인 접근은 **연속된 주소 범위마다 plug 트리를 만드는 것**이다. CLR에서 그런 범위를 **브릭(brick)** 이라 부른다.

| 항목 | 32비트 | 64비트 |
|---|---|---|
| 브릭 크기 | **2,048 B** | **4,096 B** |
| 브릭 테이블 항목 크기 | 16비트 정수 | 16비트 정수 |
| 표현 가능 오프셋 범위 | −32,767 ~ 32,767 | −32,767 ~ 32,767 |

즉 관리 힙의 매 2 kB(또는 4 kB)가 브릭 하나로 표현되고, 그 브릭이 자기 plug 트리 정보를 담는다. 브릭들은 관리 힙 전체를 덮는 **브릭 테이블**에 저장된다.

각 브릭 테이블 항목은 16비트 정수이고 논리적으로 세 가지 값을 가진다.

| 값 | 의미 |
|---|---|
| **0** | 이 브릭에 배정된 plug 정보가 없다(해당 주소 범위에 plug가 없다) |
| **> 0** | 대응 메모리 영역 안에서 plug 트리 루트의 **오프셋**. 0이 "정보 없음"을 뜻할 수 있도록 값에 1을 더해 저장한다 |
| **< 0** | 이 브릭이 **이전 브릭들의 연속**이다(여러 브릭에 걸친 큰 plug가 있다). 주어진 브릭 수만큼 되돌아가야 한다 |

```text
브릭 테이블
┌───────┬───────┬───────┬───────┬───────┬───────┐
│   0   │ 0x6f1 │  -1   │  -2   │ 0x0a3 │   0   │  ← 16비트 항목들
└───────┴───────┴───────┴───────┴───────┴───────┘
 0x0000  0x1000  0x2000  0x3000  0x4000  0x5000     ← 각 브릭이 덮는 주소(64비트, 4 kB)
            │       └───┬───┘
            │           └─ 큰 plug가 3개 브릭에 걸침 → 되돌아가기
            ↓
   plug 트리 루트 = 0x1000 + (0x6f1 - 1) = 0x16f0
```

예를 들어 브릭 테이블 항목이 `0x6f1`이라면 대응 메모리 영역 안 plug 트리 루트의 오프셋이다. 두 번째 항목이므로 `0x1000`(4 kB)과 `0x2000`(8 kB) 사이 영역을 나타낸다. 루트는 `0x6f0`(양수 값은 1을 빼야 한다) + `0x1000` = **`0x16f0`** 에 있다. 이 주소에서 시작해 plug 정보의 오프셋을 따라가면 이 브릭의 plug 트리 전체를 순회할 수 있다.

**"주소 X의 객체의 새 주소는 무엇인가?"** 에 답하는 절차는 이렇다.

1. 주소 X를 브릭 크기로 나눠 브릭 테이블 항목의 인덱스를 계산한다.
2. 항목 값이 **0보다 작으면** — 지정된 브릭 테이블 항목으로 점프해 반복한다.
3. 항목 값이 **0보다 크면** — plug 트리를 순회해 적절한 plug를 찾는다.
4. plug에서 재배치 오프셋을 얻어 X에서 뺀다.

> **💡 왜 16비트로 충분한가**
>
> 브릭 테이블 항목과 left/right 오프셋이 모두 short 정수(16비트)인 이유는 단순하다. 저장하는 값이 −32,767~32,767 범위이고, 이것이면 **4 kB 주소 범위 안의 오프셋을 표현하기에 충분**하기 때문이다. 자료구조 하나하나가 캐시 라인을 아끼려고 설계되어 있다는 것을 다시 확인할 수 있다.

### 세대 경계

임시(ephemeral) 세그먼트 안에서 세대 경계는 스윕이나 압축 후에 바뀐다. 고정된 객체가 없는 시나리오라면 꽤 단순하다. **세대 경계는 승격된 객체를 모두 포함하도록 조정된다.**

전체 수집(Full GC) 중 세 세대가 모두 있고 각 세대에 마킹된 객체가 있다고 하자. Plan 단계에서 내부 할당자가 plug의 새 주소를 계산하는 동시에 **새 세대 경계도 계산한다.** 객체를 실제로 옮기지 않고 전부 가상으로 진행한다.

> **📌 리전에서는 세대 경계라는 개념이 없다**
>
> 62.6절에서 봤듯이 각 리전은 **단일 세대**를 담는다(여러 세대를 담는 임시 세그먼트와 대조된다). 그래서 리전에서는 세대 경계 개념이 적용되지 않는다. 압축 중에 생존 객체는 더 오래된 세대에 할당되고, 스윕 중에는 **리전 자체가 오래된 세대로 승격된다.**

> **📌 모든 세대는 빈 객체 하나로 시작한다**
>
> 세그먼트에는 작은 특이점이 하나 더 있다. **각 세대는(비어 있는 세대라도) 최소 객체 크기의 빈 공간 하나로 시작한다.** 이 빈 공간은 그 세대의 첫 plug에 대한 plug 정보를 저장하는 데 쓰인다. 덕분에 두 세대에 걸치는 문제를 걱정하지 않고 plug를 일관되게 다룰 수 있다.
>
> 메모리 덤프를 분석하다 **각 세대가 3-포인터 길이 빈 공간으로 시작하는 것**을 발견해도 놀라지 마라. 정상이다.

### 강등(demotion)

고정된 plug 주변에서 내부 할당자가 어떻게 동작하고 세대가 어디서 시작할지는 아직 명확하지 않다.

구현 관점에서 가장 단순한 해법은 **고정된 plug 뒤에서 누적 재배치 오프셋을 리셋하는 것**이다. 그러면 이후 plug들이 그 뒤에 할당되고, 세대 경계는 생존 객체를 모두 덮도록 설정된다.

이건 **단편화 관점에서 매우 비효율적**이다. 때때로 큰 빈 메모리 영역을 만들어내기 때문이다. 대신 내부 할당자는 **고정된 plug 사이의 gap을 일반 plug로 채우려 한다.**

```text
(a) 할당 포인터를 세대 시작으로 리셋
(b) 첫 plug의 자리를 찾음
(c) 두 번째 plug의 자리를 찾음
(d) 고정된 plug를 "원래 주소 그대로" 할당
(e) 고정된 plug 앞의 마지막 plug 자리를 찾음 — 공간이 충분하다
(f) 세대 경계 결정
```

임시 세그먼트라고 하자. 처음에 모든 객체는 세대 0에 있었다. 생존 객체가 전부 예상대로 세대 1로 승격된다면, 고정된 객체를 포함해 **세대 0은 고정된 plug 바로 뒤에서 시작해야** 한다. 고정된 객체도 다른 객체처럼 세대 0에서 1로 승격되어야 하니까.

그런데 그러면 **세대 1에 큰 단편화가 생긴다.** 더 나은 결정은 기존 gap을 재사용하고 **세대 1을 더 일찍 끝내는 것**이다. 세대 0은 고정된 객체 **앞에서** 시작하도록 계획된다.

그 결정 때문에 **고정된 객체는 세대 0에 남았다** — 평소처럼 세대 0에서 1로 승격되지 않았다.

이런 사건을 **강등(demotion)** 이라 부른다(승격의 반대). 객체가 있어야 할 세대보다 **낮은 세대에 놓이는 것**이다. 강등은 "승격되지 않았다"는 뜻일 수도 있고, "더 낮은 세대에 떨어졌다"는 뜻일 수도 있다.

고정 때문에 객체 승격에 세 가지 가능성이 모두 생긴다. 세대 1의 고정된 plug(뒤의 객체 하나로 확장된) 관점에서 보면 이렇다.

| 앞선 gap의 상태 | 결과 |
|---|---|
| 일반 plug들을 할당하기에 **충분히 큰** gap이 앞에 있다 | 고정된 plug가 **세대 1 → 0으로 강등** |
| 일반 plug들 + 세대 1 시작점까지 넣을 만큼 gap이 크다 | 고정된 plug가 강등되되 **세대 1에 머문다** |
| 앞에 일반 plug를 넣을 공간이 **부족하다** | 고정된 plug와 일반 plug가(큰 빈 gap 포함) **오래된 세대로 승격** — 원치 않는 단편화 발생 |

> **⚠️ 내부 할당자는 plug를 쪼갤 수 없다**
>
> 내부 할당자는 개별 객체가 아니라 **plug 단위로** 동작한다. 고정된 객체 앞의 gap을 채우려고 plug를 더 작은 조각으로 나눌 수 없다. 이것은 **할당자의 복잡도와 단편화 오버헤드 사이의 타협**이다.
>
> 일반적으로 이 오버헤드는 무시할 만하다. 전형적인 고정은 수명이 아주 짧거나 아주 길기 때문이다.
>
> - **짧은 경우** — 세대 0에서 죽는다. 세대 0은 작고 동적이라 그 오버헤드를 흡수하고 단편화를 남기지 않는다.
> - **긴 경우** — 고정된 객체가 세대 2에 산다. gen2 압축이 일어나지 않는 한 대부분의 시간 영향이 미미하다.
>
> **문제는 그 중간이다.** 오래 살아서 오래된 세대로 승격될 만큼은 살지만 영원하지는 않은 고정된 객체 — 이것이 가장 골치 아프다(Rule 22).

> **📌 세그먼트에서 강등되는 것은 고정된 plug뿐이다**
>
> 세그먼트 구현에서는 **고정된 plug만 강등될 수 있다.** 즉 고정된 객체와, 있다면 그 뒤에 붙은 고정되지 않은 객체 하나까지다.
>
> 고정된 plug가 여럿이면 그중 일부만 강등될 수도 있다. 전적으로 현재 plug/gap 배치에 달렸다.
>
> gen2 전용 세그먼트가 임시 세그먼트로 전환될 수 있다고 62장에서 언급했다. 그런 일이 일어나면 **고정된 plug가 세대 2에서 세대 1과 0으로 강등된다.**

> **💡 강등을 진단할 필요는 없다**
>
> 강등은 gap을 최대한 재사용하기 위한 **최적화**다. 남은 빈 공간은 충분히 크면 프리 리스트 항목이 되어 재사용 기회를 얻는다.
>
> 아마 그래서 강등에 대한 진단 데이터가 제공되지 않는 것이다. 철저한 메모리 덤프 분석으로 관찰할 수는 있지만 그럴 일은 없을 것이다. **신경 써야 할 것은 고정된 plug가 유발하는 단편화 수준이지 강등 자체가 아니다.**

> **📌 `!DumpGCData` — 문서화되지 않은 SOS 명령**
>
> SOS에는 문서화되지 않은 `!DumpGCData` 명령이 있다. 압축 이유나 GC 종류별 횟수처럼 다른 방법으로도 얻을 수 있는 데이터 외에, **다른 어디서도 못 얻는** "interesting data points"를 담고 있다.
>
> ```text
> Interesting data points
>         pre short: 0
>        post short: 0
>       merged pins: 0
>    converted pins: 0
>           pre pin: 0
>          post pin: 0
>  pre and post pin: 0
>  pre short padded: 0
> post short padded: 0
> ```
>
> | 항목 | 의미 |
> |---|---|
> | pre and post pin | pre-plug와 post-plug 정보를 **둘 다** 가진 고정된 plug |
> | pre pin | pre-plug 정보만 가진 고정된 plug |
> | post pin | post-plug 정보만 가진 고정된 plug |
> | converted pin | 고정된 plug 확장 때문에 **고정으로 전환된** 객체 |
>
> 이 명령은 GC 개발자용이고 .NET 개발자에게 실용적 쓸모는 없다. **미래 SOS 버전에 이 명령이 존재하리라는 보장도 없다.** 더 파고 싶으면 .NET 소스의 `gc_heap::record_interesting_data_point` 메서드를 찾아라.

## 64.7 고정(pinning)이 계획 단계에 미치는 영향

객체가 고정되었다면 십중팔구 그 주소를 비관리 코드에 넘기기 위해서다(60.8절).

**고정된 객체는 압축 중에 단순히 옮길 수 없다.** 비관리 코드가 그것을 쓰고 있을지 모르기 때문이다. 그 코드는 여전히 같은 주소를 참조할 것이고, 옮겼다면 그 주소는 이제 **완전히 다른 데이터**를 가리킨다.

```text
고정된 객체를 옮기면 벌어지는 일

이동 전                          이동 후
┌─────────────┐                 ┌─────────────┐
│ 고정된 객체   │ ← 비관리 코드    │ 다른 객체    │ ← 비관리 코드
│  (버퍼)      │   포인터        │ (엉뚱한 데이터)│   포인터 (그대로!)
└─────────────┘                 └─────────────┘
                                      ↑
                              정의되지 않은 동작 / AV / 데이터 손상
```

고정은 앞 절에서 설명한 기법을 **상당히 복잡하게** 만든다. 내부 할당자와 plug 트리 구축에서 고정된 객체를 특별히 고려해야 한다.

고정 때문에 객체 그룹이 실제로는 **세 종류**가 된다.

| 그룹 | 정의 |
|---|---|
| **plug** | 마킹된(도달 가능한) 객체 묶음 |
| **고정된 plug(pinned plug)** | 고정된(따라서 마킹된) 객체 묶음 |
| **gap** | 마킹 안 된(도달 불가능한) 객체 묶음 |

### 경우 1 — 고정된 plug가 gap 바로 뒤에 있을 때

가장 단순한 시나리오다. 이전과 크게 달라지지 않는다. plug 정보는 평소처럼 대응 gap의 끝에 저장할 수 있고, plug 트리 구축 시 적절한 left/right 오프셋이 저장된다.

**주된 차이는 이런 plug의 재배치 오프셋이 0이어야 한다는 것이다.**

추가로, **압축 시 해제될 공간의 크기**가 각 고정된 plug 앞에 저장된다.

그래서 압축 중에 일반 plug는 이동하고 고정된 plug는 이동하지 않는다. 앞서 설명한 내부 할당자가 **고정된 plug를 옮기지 않기 때문**이다(정확히 있던 자리에 공간을 "할당"한다).

> **⚠️ 일반 plug와 고정된 plug 사이에 큰 빈 공간이 생길 수 있다**
>
> 이 경우 압축 결과로 일반 plug와 고정된 plug 사이에 **큰 빈 gap**이 생길 수 있다. 이 시나리오가 앞 절의 강등으로 이어진다.

모든 고정된 plug 관련 데이터는 **고정 plug 큐(pinned plug queue)** 에도 기억된다. GC는 표준 plug 정보에 들어가지 않는 추가 정보를 자주 저장해야 하고, 그래서 별도 큐가 필요하다.

> **📌 `mark_stack_array`라는 이름에 속지 마라**
>
> 흥미롭게도 고정 plug 데이터를 저장하는 데 **이미 알고 있는 `mark_stack_array`가 재사용된다.** 다만 이때는 객체 주소 대신 전용 `mark` 클래스 인스턴스에 대한 포인터를 저장한다.
>
> 그래서 .NET 코드를 분석하다 보면 **고정 plug 처리와 관련된 코드에서** `mark_stack_array`(그리고 대응하는 `mark_stack_tos`·`mark_stack_bos` 포인터)를 아주 자주 만나게 된다. 이름만 보고 Mark 단계 코드라고 오해하기 쉽다.

### 경우 2 — 고정된 plug가 일반 plug 바로 뒤에 있을 때 (pre-plug)

여기에 문제가 있다. 고정된 plug 정보는 평소처럼 그것이 시작하기 직전에 저장되어야 하는데, 그 자리에 빈 공간 대신 **일반적이고 도달 가능한 객체**가 있다.

GC는 고정 plug 정보를 다른 데 저장할 수도 있었다. 그런데 흥미롭게도 — **실제로는 고정된 plug 앞의 객체를 덮어쓴다.**

이게 가능한 이유는 **Plan 단계가 모든 관리 스레드가 중단된 상태에서 실행됨이 보장되기 때문**이다. 그래서 나중에 "복원"되기 전에 어떤 .NET 코드도 그 "파괴된" 객체에 접근할 가능성이 없다.

잘려나간 마지막 객체의 끝부분(64비트에서 3-포인터 크기, **24바이트**)은 다른 고정 plug 데이터와 함께 **새 고정 plug 큐 항목**에 저장된다. 이런 객체 끝부분을 **pre-plug**라 부른다(고정된 plug에 선행하기 때문). 나중에 압축이나 스윕 실행 중에 쓰인다.

```text
(a) 원래 배치
┌──────────────┬──────────────────┐
│  일반 plug    │   고정된 plug     │
│  ■■■■■■■     │   ▓▓▓▓▓▓▓        │
└──────────────┴──────────────────┘

(b) plug 정보를 위해 앞 객체의 끝 24바이트를 덮어씀
┌────────┬─────────┬──────────────────┐
│ 일반    │plug info│   고정된 plug     │
│ ■■■    │(24 B)   │   ▓▓▓▓▓▓▓        │
└────────┴─────────┴──────────────────┘
             ↑
   덮어쓴 24바이트 = pre-plug → 고정 plug 큐에 보관
```

> **📌 24바이트 최소 크기가 또 한 번 구한다**
>
> 객체가 최소 24바이트여야 한다는 요구가 여기서도 크게 도움이 된다. **가장 작은 선행 객체 안에도 plug 정보를 넣을 공간이 확보된다는 것을 보장**하기 때문이다.

이 접근 덕분에 GC는 고정된 plug를 **일반적인 방식으로** 다룰 수 있다. 재배치 오프셋은 0, gap 크기는 인위적으로 24바이트로 설정되고(실제 gap은 없지만 통계 목적으로 계산해야 한다), plug 정보는 평소처럼 plug 트리에 편입된다.

### 경우 3 — 고정된 plug가 일반 plug 바로 앞에 있을 때 (확장)

또 다른 문제가 생긴다. 일반 plug는 자기 정보를 시작 직전, 즉 **고정된 객체가 끝나는 자리**에 저장하고 싶어 한다. 그런데 고정된 객체는 **GC 중에도 중단되지 않는 비관리 스레드가 접근할 수 있다.** 따라서 고정된 객체는 **항상 건드려지지 않음이 보장되어야 한다.**

해법은 간단하다. 새 plug를 만드는 대신, **고정된 객체 바로 뒤의 객체를 고정된 plug에 편입시킨다.**

```text
(a) 원래 배치
┌──────────────┬──────────────┐
│  고정된 plug  │  일반 plug    │
│  ▓▓▓▓▓▓      │  ■■■■■■      │
└──────────────┴──────────────┘

(b) 일반 plug의 첫 객체를 고정된 plug에 병합
┌──────────────────────────────┐
│    확장된 고정 plug            │
│  ▓▓▓▓▓▓  +  ■(객체 하나)      │  ← 이 객체도 고정 취급된다
└──────────────────────────────┘
```

> **⚠️ GC가 고정하지 않아도 될 객체를 고정한다**
>
> 이건 일종의 타협이다. 고정된 객체와 인접한 일반 객체가 **확장된 고정 plug**로 취급되므로, 그 일반 객체도 고정의 모든 단점을 떠안는다.
>
> 고정은 피해야 한다고 계속 말해왔는데, 여기서 GC가 하는 일은 **정반대 — 추가 일반 객체를 고정하는 것**이다. plug를 일반적으로 취급하는 이점이 단점을 앞선다고 본 것이다. 고정된 객체 뒤의 일반 객체가 작다면 발생하는 교란은 무시할 만하다.

그런데 고정된 객체 뒤에 **마킹된 객체의 큰 블록**이 온다면 문제가 될 수 있다. 그것들을 전부 확장된 고정 plug에 넣어야 할까(이론적으로 메가바이트, 심지어 기가바이트 크기의 고정 plug가 가능해진다)? 당연히 아니다.

**고정 plug의 확장은 첫 번째 객체 하나로만 이루어진다.**

고정된 객체 뒤에 마킹된 객체가 최소 둘 있다고 하자. 고정 plug는 앞서 설명한 대로 확장되어 둘 중 첫 번째를 포함한다. 그러면 이제 나머지 마킹된 객체들로 일반 plug를 만들 수 있다 — 고정 plug에 포함된 그 일반 객체를 덮어써도 안전하기 때문이다. 그렇게 "파괴된" 객체의 끝부분은 pre-plug 데이터처럼 다른 곳에 저장해야 하고, 이런 객체 끝부분을 **post-plug**라 부른다.

### 경우 4 — 고정된 객체가 큰 블록 한복판에 있을 때 (전형적)

가장 전형적인 시나리오는 고정된 객체가 **더 큰 마킹된 객체 블록 안에** 놓인 경우다. 이 경우 **pre-plug와 post-plug를 둘 다 저장해야 하고, 세 개의 별도 plug**(그중 하나는 고정되고 확장된)가 만들어진다.

```text
(a) 원래 배치 — 마킹된 큰 블록 한복판에 고정된 객체 하나
┌────────────────┬──────────┬────────────────────┐
│   ■■■■■■■■     │  ▓▓▓▓    │   ■■■■■■■■■■       │
└────────────────┴──────────┴────────────────────┘

(b) 결과 — 3개의 plug
┌──────────┬─────┬───────────────────┬─────┬──────────┐
│ 일반 plug │pre- │ 확장된 고정 plug    │post-│ 일반 plug │
│  ■■■■    │plug │  ▓▓▓▓ + ■(하나)    │plug │  ■■■■■   │
└──────────┴─────┴───────────────────┴─────┴──────────┘
                  ↑ 잘린 24B는 고정 plug 큐에 보관 ↑
```

### 고정의 실제 비용

이 모든 것이 함의하는 바는 셋이다.

| 함의 | 내용 |
|---|---|
| **추가 메모리 트래픽** | pre-plug와 post-plug를 복사하는 것 자체가 비용이다. **고정된 객체가 많을수록 오버헤드가 커진다** |
| **필요 이상의 고정** | 고정 plug가 객체 하나만큼 확장되므로 **의도한 것보다 많은 메모리가 고정된다.** 그 일반 객체가 크면 상당한 메모리 영역이 이동 불가능해진다 |
| **힙을 걸을 수 없다** | Plan 단계 중 힙의 일부 객체가 pre-plug/post-plug 정보로 부분적으로 덮어써져 정상적인 방법으로 **"걸을 수 없게(not walkable)"** 된다. 그 단계에서 메모리 덤프를 뜨면 문제가 된다(64.6절의 ⚠️ 박스) |

### 고정의 두 가지 출처와 진단

고정을 조사하려면 먼저 **출처가 둘**이라는 것을 알아야 한다.

| 출처 | 특징 | 덤프에서 보이는가 |
|---|---|---|
| **지역 고정 변수** | `fixed` 키워드로 암묵적으로 만들어지는 지역 변수. 수명이 **둘러싼 메서드 실행 동안**으로 제한된다 | **거의 안 보인다.** 현재 실행 중인 것에 기반한 작은 조각만 보인다 |
| **고정 핸들** | `GCHandle.Alloc(obj, GCHandleType.Pinned)` 등으로 **명시적으로** 고정. CLR 자신이 잡는 내부 객체도 포함 | **잘 보인다.** 핸들 테이블이 애플리케이션 수명 내내 메모리에 있다 |

두 종류 모두에 대해 **`PinObjectAtGCTime` ETW 이벤트가 방출된다.** Mark 단계 중 고정된 객체마다 하나씩이다. 다만 고정 핸들 쪽은 **그 GC가 수집하는 세대의 것만** 기록된다 — 핸들 테이블이 세대를 인식하기 때문이다. 세대 0 GC만 잔뜩 기록해 놓고 "고정이 없다"고 결론 내리면 안 된다.

> **⚠️ `# of Pinned Objects` 성능 카운터는 .NET Framework 전용이다**
>
> `\.NET CLR Memory\# of Pinned Objects` 성능 카운터는 두 종류를 모두 센다. 그러나 이 카운터는 **.NET Framework에서만 제공되며 .NET / .NET Core에는 대응 카운터가 없다.** .NET Core에서는 PerfView의 GCStats 리포트 **`Pinned Obj` 열**에서 시작해야 한다. 각 GC가 승격한 고정 객체 수를 보여준다.

진단 절차는 이렇다.

1. **PerfView로 ETW 세션 기록.** `.NET` 체크박스만 켜면 된다(`GC Collect Only`는 끈다).
2. **GCStats 리포트**(Memory 그룹)를 열어 `Pinned Obj` 열로 고정이 눈에 띄는 수준인지 확인한다.
3. **`Pinning At GC Time Stacks` 뷰**(Advanced 그룹)로 넘어간다. 이게 핵심이다.

> **⚠️ `PinObjectAtGCTime` 이벤트에 스택 트레이스는 쓸모없다**
>
> 이 이벤트에는 스택 트레이스가 붙어 있지 않다. `@StacksEnabled=true` 옵션으로 켤 수는 있지만 **전혀 도움이 안 된다.** 그 이벤트의 스택 트레이스는 항상 **GC 코드 안**이지 고정된 객체가 쓰이는 자리가 아니기 때문이다.
>
> 대신 전용 `Pinning At GC Time Stacks` 뷰를 써라. 추가 분석과 그룹핑을 해서 요약 데이터를 준다. 기본 `By Name` 뷰가 고정된 타입의 주된 기여자를 보여준다. 우클릭 → `Goto Item in Callers`(F10)로 더 파고들면 `StackPinned` 여부까지 확인된다.

핸들로 고정된 객체를 분석하는 다른 방법은 WinDbg의 **`!GCHandles` 명령**이다.

```text
> !GCHandles Pinned
  Handle Type          Object     Size          Data Type
007f1374 Pinned      04988078   131084          System.Byte[]
007f1378 Pinned      04968058   131084          System.Byte[]
007f1398 Pinned      0490f058    32780          System.Object[]
007f13c0 Pinned      0403dbac       12          Bid+BindingCookie
...
Statistics:
      MT    Count    TotalSize Class Name
720dffe4       18       417536 System.Object[]
720e419c        4       524336 System.Byte[]
Total 24 objects
```

문자열 인터닝 풀이나 정적 필드처럼(54.5절, 35.5절) CLR 내부 배열, Kestrel 서버가 쓰는 각종 버퍼 등이 보인다.

> **⚠️ SOS는 스택 기반 고정을 못 본다**
>
> 현재 **스택 기반 고정 출처를 나열해주는 WinDbg 확장은 없다.** SOS 확장은 **핸들 관련 고정 출처만** 나열한다.
>
> 정리하면 — 고정 전반을 제대로 보려면 **두 출처를 모두 고려하는 `PinObjectAtGCTime` 이벤트**를 봐야 한다.

`.gcdump` 힙 스냅샷을 PerfView로 여는 것도 유용하다. `[.NET Roots]` 행을 찾아 `Goto Item in CallTree`(Alt+T)를 선택하고, `Fold%` 필드를 비워 폴딩을 제거하면 **고정된 지역 변수를 포함한 모든 루트 종류**를 나열할 수 있다. 다만 정적 스냅샷이므로 스택 기반 고정 출처가 전부 나오지는 않는다.

> **💡 `GroupPats`와 `FoldPats`를 비워라**
>
> `GroupPats` 필드의 그룹핑과 `FoldPats` 필드의 폴딩을 모두 제거하면 더 세밀하고 서술적인 결과가 나온다. 고정 출처를 추적할 때는 이렇게 보는 편이 낫다.

출처를 식별한 뒤에는 피할 수 있는지 판단한다. 단편화를 크게 유발하지 않는다면 그대로 둬도 된다. 문제가 된다면 해법을 찾아야 하고, 과도한 고정을 피하는 접근은 60.8절과 69장에서 다룬다.

### LOH의 Plan 단계

LOH의 Plan 단계는 **압축할 때만 필요하다.** 기본값은 항상 스윕이고, 스윕은 plug와 gap을 쓰지 않는다. LOH 압축은 드물고, 보통 개발자가 명시적으로 요청하거나 `ConserveMemory`가 켜졌을 때만 일어난다(65.5절). **대다수 .NET 애플리케이션에서 LOH는 한 번도 압축되지 않는다.**

그래도 압축은 가능하므로 LOH는 단순화된 형태로 plug와 gap 개념을 지원한다. LOH는 큰 객체만 산다는 것이 보장되므로 단순화가 가능하다.

| 단순화 | 이유 |
|---|---|
| **각 도달 가능 객체를 별도 plug로 취급** | 개별 객체가 이미 충분히 크다. LOH의 객체 밀도가 SOH보다 훨씬 낮아 이것으로도 주소 변환 효율이 충분하다. 게다가 여러 큰 객체로 이루어진 거대한 plug를 재배치하는 것이 훨씬 어려우므로 **단편화 방지에도 도움이 된다** |
| **객체 사이에 패딩** | plug 정보 저장 오버헤드(pre-plug/post-plug 처리 포함)를 없애려고, LOH 객체들은 사이에 작은 패딩을 두고 할당된다. 이 패딩은 **4-포인터 크기(64비트에서 32바이트)** 이고 정상 free 객체로 만들어진다 |

패딩 덕분에 plug 정보가 다른 객체를 덮어쓸 가능성이 없으므로 **pre-plug와 post-plug 데이터를 유지할 필요가 없다.**

객체 수가 상대적으로 적고 크기가 크기 때문에 **plug 트리를 관리할 필요도 없다.** 새 주소는 plug 정보에서 재배치 오프셋을 가져와 객체 주소에서 빼기만 하면 된다. 따라서 **LOH에는 브릭과 브릭 테이블도 없다.**

LOH 안에는 세대가 없으므로 세대 경계를 다시 계산할 필요도 없고, **강등도 불가능하다.**

> **⚠️ LOH의 고정도 SOH와 똑같이 단편화를 만든다**
>
> 중요한 부기 사항 — LOH에서의 고정은 SOH와 **같은 방식으로 단편화를 유발할 수 있다.** LOH가 애초에 압축되지 않으니 상관없다고 생각하기 쉽지만, 프리 리스트 재사용을 방해한다는 점은 동일하다.
>
> LOH 계획 코드는 `gc_heap::plan_loh` 메서드에 있다.

## 64.8 압축(compaction) 결정 로직

Plan 단계에서 복잡한 계산을 마친 뒤, GC는 **압축할 가치가 있는지** 결정해야 한다. 압축을 강제하는 이유가 여럿 있지만 대부분의 경우 결정은 **단편화 수준**에 기반한다.

### 압축을 결정하는 이유들

| 이유 | 설명 |
|---|---|
| **OOM 직전 마지막 full GC** | `OutOfMemoryException`을 던지기 전 마지막 전체 GC — GC는 메모리를 되찾기 위해 최선을 다해야 한다 |
| **명시적으로 유도됨** | 예를 들어 적절한 `GC.Collect` 매개변수를 제공한 경우(65.8절) |
| **임시 세그먼트 공간 부족** | GC는 기존 임시 세그먼트를 확장하거나 새로 만들기 전에 공격적으로 메모리를 회수하려 한다 |
| **리전에서 여유 리전 부족** | 다음 수집 전 gen 0에 예측되는 할당량을 담을 만큼 **비어 있는(또는 비게 될) 리전이 부족할 때** |
| **세대 단편화가 높음** | 어떤 세대의 단편화가 높다면 그 세대를 압축하며 수집하는 것이 생산적일 가능성이 크다 |
| **시스템 물리 메모리 부하가 높음** | 가능하다면, 압축으로 회수되는 메모리가 특정 임계값을 넘을 때 |

### 단편화 임계값

위 결정 중 여럿에서 **단편화 임계값**이 중요한 역할을 한다. 각 세대는 자기 임계값을 유지하며, 정적 세대 데이터에서 온 두 값으로 구성된다.

- **총 단편화(total fragmentation)** — Plan 단계에서 모은 정보로 특정 세대의 단편화를 계산하기는 쉽다. 개별 세그먼트의 계획된 종료 할당 주소와 고정으로 인해 생길 빈 공간을 고려하면 된다. 내부적으로 `fragmentation_limit`으로 표현된다.
- **단편화 비율(fragmentation ratio)** — 위 총 단편화 크기를 수집 대상 세대 전체 크기로 나눈 비율. 내부적으로 `fragmentation_burden_limit`으로 표현된다.

| 세대 | 단편화 크기 임계값 | 단편화 비율 임계값 |
|---|---|---|
| **Gen0** | 40,000 | **50%** |
| **Gen1** | 80,000 | **50%** |
| **Gen2** | 200,000 | **25%** |

예를 들어 **세대 2는 전체 단편화 크기가 200,000바이트를 넘으면서 동시에 세대 전체 크기의 25%를 넘을 때** 너무 단편화되었다고 판단된다.

> **📌 두 조건은 AND다**
>
> 크기와 비율 중 하나만 넘어서는 안 된다. **둘 다** 넘어야 한다. 작은 세대에서 절대 크기가 커 보이거나, 거대한 세대에서 비율이 커 보이는 오판을 막는 설계다.
>
> 압축 결정은 `gc_heap::decide_on_compacting` 메서드에 있다.

### 특수 리전 (실험적)

**특수 리전(special regions)** 은 `DOTNET_GCEnableSpecialRegions=1`로 켜는 실험적 기능이다. 이름 그대로 **리전에서만** 동작한다. 리전이 도입되기 전에는 불가능했던 것 중 하나라, 실험적 상태임에도 연구할 가치가 있다.

**SIP(swept-in-plan).** 보통은 GC가 압축을 시뮬레이션하고 그 결과로 실제 압축 여부를 결정한다. 특수 리전이 켜지면 GC가 먼저 **각 리전의 생존 객체 비율**을 확인한다. 90%를 넘으면(즉 10% 미만만 수집 가능하면) 그 리전은 스윕한다. 리전 안 객체 중 죽은 것이 적다면, 압축이 생산적이지 않을 것을 알기 위해 시뮬레이션조차 할 필요가 없다는 논리다. 스윕이 **Plan 단계 중에 바로** 이루어지기 때문에 "계획 중에 스윕됨"이라는 이름이 붙었다.

**동적 승격(dynamic promotion).** 리전의 생존자 비율이 90%를 넘는다는 것을 확인한 뒤, GC는 그 객체들을 살려두는 **루트가 어디서 오는지** 확인한다. 세대 2의 루트가 리전 객체의 90% 이상을 살려두고 있다면, GC는 그 리전을 **곧바로 세대 2로 승격한다.** gen 1 리전에는 변화가 없지만, **gen 0 리전이 세대 2로 직행할 수 있다는 뜻이다.**

논리는 이렇다. 세대 2에서 참조되는 객체는 **최소한 다음 gen 2 수집 전에는 죽을 수 없다.** 그 루트가 그때까지 수집되지 않기 때문이다. 그러니 리전을 세대 1로만 승격하는 것은 비생산적이다 — 다음 gen 1 수집에서 같은 객체들이 여전히 참조되고 있을 테니까.

> **⚠️ 좋기만 한 게 아니라서 아직 실험적이다**
>
> 늘 그렇듯 최적화는 타협의 문제다. 이 규칙들을 적용하면 GC는 **CPU 오버헤드를 줄이는 대신 메모리를 낭비한다.**
>
> 동적 승격에서는 90%의 객체가 다음 gen 1 수집에서 생존하더라도, **수집될 수 있었던 최대 10%의 객체가 남는다.** 그것들은 다음 gen 2 수집까지 살아 있게 된다. GC 팀의 현재 초점은 메모리 사용량 감소이므로 이 타협은 아직 받아들여지지 않았다.
>
> 그래도 **리전이 어떤 종류의 시나리오를 가능하게 했는지** 보여준다는 점에서 흥미롭다. 세그먼트에서는 작은 메모리 덩어리를 개별적으로 관리하고 특화된 전략을 적용할 수 없었다.

## 64.9 Sweep 단계와 프리 리스트 구성

GC가 압축하지 않기로 하면 Sweep 단계로 간다. 61.9절에서 봤듯 Sweep 수집은 쉽다. **더 이상 도달할 수 없는 객체를 전부 빈 공간으로 바꾸면 된다.** .NET GC 용어로는 **모든(또는 일부) gap을 프리 리스트 항목으로 바꾸는 것**이다.

> **📌 Sweep과 Compact가 이 책에서 짧은 이유**
>
> 문헌에서 GC를 설명할 때 그렇게 자주 등장하는 Sweep과 Compact 단계가 이 장에서 이렇게 작은 부분을 차지하는 것이 의외일 수 있다. **무거운 계산이 전부 Plan 단계에서 이미 끝났기 때문이다.** 두 단계는 Plan이 모은 정보를 단순히 소비할 뿐이다.
>
> 그렇다고 가벼운 것은 아니다. **성능 관점에서는 오히려 가장 큰 기여자다.** plug를 수정하고 옮기면서 메모리에 접근하는 비용이 가장 비싸기 때문이다. 구현 관점에서는 이전 단계들보다 덜 복잡하지만, **성능 관점에서는 가장 영향이 크다.**

> **⚠️ 가장 전형적인 조합은 "LOH 스윕 + SOH 압축"이다**
>
> 그리고 **순서가 중요하다.** LOH 스윕이 SOH 압축보다 **먼저** 일어난다. 이유는 64.10절의 참조 재배치 단계에서 밝혀진다.

### SOH 스윕

SOH 스윕에서는 다음 단계를 밟는다.

| 단계 | 내용 |
|---|---|
| **gap에서 프리 리스트 항목 생성** | **최소 객체 두 개보다 큰** 모든 gap에서 새 프리 리스트 항목을 만들어 프리 리스트에 편입한다(63.2절). 더 작은 gap은 그냥 사용되지 않는 빈 공간으로 취급된다(단편화 통계에는 포함된다) |
| **저장된 pre-plug·post-plug 복원** | "파괴된" 객체를 전부 되돌려 쓴다 |
| **부기 작업** | 파이널라이제이션 큐를 새 세대 경계에 맞게 갱신하고, 적절한 종류의 생존 핸들을 노화(또는 회춘)시킨다 |
| **세그먼트·리전 재배치** | 더 이상 필요 없는 것을 제거하거나, VM 호딩이 켜져 있으면 재사용 리스트에 보관한다(62.8절) |

```text
Sweep 결과 (Plan 단계 정보 기반)

Plan 이후:
┌──────────┬────────┬──────────────┬──────┬────────────┐
│  plug 1  │ gap 1  │    plug 2     │gap 2 │   plug 3   │
└──────────┴────────┴──────────────┴──────┴────────────┘

Sweep 이후 (객체는 이동하지 않는다):
┌──────────┬────────┬──────────────┬──────┬────────────┐
│  plug 1  │ FREE   │    plug 2     │ FREE │   plug 3   │
│          │→프리리스트│              │→너무 │            │
│          │        │              │ 작음 │            │
└──────────┴────────┴──────────────┴──────┴────────────┘
```

> **📌 .NET 소스에서 SOH 스윕 찾기**
>
> `gc_heap::plan_phase` 메서드에서 시작한다. `should_compact` 조건 검사의 `else` 블록 안에서 가장 중요한 두 메서드가 호출된다 — **`gc_heap::make_free_lists`** 가 gap에서 프리 리스트 항목을 만들고, **`gc_heap::recover_saved_pinned_info`** 가 pre-plug와 post-plug로 파괴된 객체를 복원한다.

### LOH와 POH 스윕

UOH(User Old Heap, 즉 LOH·POH) 스윕에는 **Plan 단계가 전혀 개입하지 않는다.** 스윕은 SOH의 Plan 단계처럼 힙을 객체 단위로 스캔하면서 **마킹된 객체 사이에 프리 리스트 항목을 만드는 것**으로 구현된다. 추가로 더 이상 필요 없는 UOH 세그먼트·리전이 삭제된다(VM 호딩이 켜져 있으면 세그먼트 재사용 리스트에 보관).

> **⚠️ 단순하고 효율적인 대신 단편화가 남는다**
>
> UOH 스윕 구현은 단순하고 효율적이다. 단점은 하나뿐이다 — **단편화.** 필요하면 사용자가 LOH 압축을 명시적으로 요청할 수 있다(65.8절의 `GCSettings.LargeObjectHeapCompactionMode`).

## 64.10 Compact 단계 — 참조 재배치, 객체 이동, 세대 경계 수정

GC가 압축하기로 하면(또는 명시적으로 지시받으면) Compact 단계로 간다. Plan 단계에서 모은 정보에 의존한다.

Compact 단계는 두 개의 주요 국면으로 나뉜다.

1. **객체를 옮기기(복사)**
2. **옮겨진 객체에 대한 모든 참조를 갱신하기**

이 때문에 Compact 단계는 Sweep보다 **상당히 복잡하다.**

### 필요하면 새 임시 세그먼트 얻기

계획 단계에서 임시 세그먼트 확장이 필요하다고 나왔다면(압축 후 세대 0·1을 담을 공간이 부족하다면) 이 단계가 실행된다. 현재 임시 세그먼트를 확장하거나, 다른 것을 재사용하거나(62.8절), 새로 만든다.

> **📌 리전에서는 이 단계가 없다**
>
> 리전 구현에는 임시 세그먼트라는 개념이 없으므로 이 단계가 적용되지 않는다.

### 참조 재배치 (Relocate References)

이 단계는 **나중에 옮겨질 객체 주소의 모든 출현을 갱신한다.**

여기서 순서가 반직관적이다. Plan 단계에서 모든 것이 계산되었으므로 최종 주소가 이미 알려져 있고, 따라서 **객체를 실제로 옮기기 전에 참조를 먼저 갱신할 수 있다.**

관리 힙 전체에 그런 참조가 흩어져 있으므로 일이 많다. 재배치는 현재 주소를 새 주소로 빠르게 변환하기 위해 **브릭과 plug 트리를 집중적으로 사용한다.**

이 단계에서 스캔되는 메모리 영역은 다음과 같다.

| 스캔 대상 | 설명 |
|---|---|
| **스택 위 참조** | 모든 관리 스레드의 스택 프레임을 스캔해 관리 객체에 대한 참조를 찾아 갱신한다 |
| **세대 간 기억 집합 안 객체의 참조** | 전체 GC가 아닌 경우, 카드로 저장된 모든 세대 간 참조(62.7절)를 새 주소로 갱신해야 한다. SOH와 LOH의 세대 간 참조 모두 포함 |
| **SOH·UOH 객체 안 참조** | 다른 객체를 참조하는 생존 객체는 참조를 갱신해야 한다. SOH에서는 브릭과 plug 트리로 생존 객체를 빠르게 찾는다. LOH·POH에서는 **UOH 스윕이 SOH 압축보다 먼저 끝났기 때문에** 이 시점에 보통 생존 객체만 남아 있고, 따라서 브릭 지원 없이도 하나씩 효율적으로 스캔할 수 있다 |
| **pre-plug·post-plug 안 참조** | 일부 객체의 끝부분이 plug 정보로 덮어써져 손상되었고 원본은 고정 plug 큐 항목에 저장되어 있다. 거기에 참조가 있다면 그것도 갱신해야 한다 |
| **파이널라이제이션 큐 객체의 참조** | 파이널라이제이션 큐(34.2절)에 있는 객체 주소도 갱신이 필요하다 |
| **핸들 테이블의 참조** | 핸들이 자기 포인터를 갱신해야 한다 |

> **⚠️ 이제 "LOH 먼저 스윕"의 이유가 밝혀졌다**
>
> UOH 스윕이 SOH 압축보다 먼저 실행되기 때문에, 참조 재배치 시점에 LOH·POH에는 **생존 객체만** 남아 있다. 그래서 브릭·plug 트리 없이 순차 스캔만으로 충분하다. 순서 하나가 자료구조 하나를 통째로 없앤 것이다.

> **⚠️ 참조 필드가 많을수록 GC가 느려진다**
>
> **객체가 필드로 담는 참조가 많을수록 이 단계에서 GC가 하는 일이 많아진다.** 전형적인 애플리케이션에서는 문제가 아닐 수 있다. 하지만 **성능이 중요한 핫 패스에서 매우 복잡한 데이터 구조를 쓴다면 직접적인 객체 참조를 피하는 것을 고려할 가치가 있다.**
>
> 이것이 70장(데이터 지향 설계)에서 다루는 AoS → SoA 전환과 값 타입 선호가 GC 관점에서도 이득인 이유다. 참조가 없는 구조체 배열은 이 단계에서 **스캔 대상이 아예 아니다.**
>
> 재배치 단계 코드는 `gc_heap::relocate_phase`에서 시작한다. 내부적으로 가장 중요한 메서드는 브릭과 plug 트리로 주소를 새 값으로 변환하는 **`gc_heap::relocate_address`** 이고, `GCScan::GcScanRoots`, `gc_heap::relocate_in_uoh_objects`, `gc_heap::relocate_survivors` 등이 이것을 쓴다.

### 객체 압축 (Compact Objects)

필요한 참조가 모두 갱신되었으니, 이제 생존 객체를 실제로 옮길 차례다.

| 단계 | 내용 |
|---|---|
| **객체 복사** | 계산된 재배치 오프셋을 써서 **plug 단위로** 이루어진다 |
| **pre-plug·post-plug 정보 복원** | 손상된 객체 부분을 고정 plug 큐 항목의 사본으로 되돌린다 |

설명은 짧고 단순하지만 **여기서 무거운 일이 많이 일어난다.** 전체 GC라면 관리 힙 전체에 걸쳐 모든 plug를 복사하는 것이 상당한 메모리 트래픽을 만든다. **압축 GC에서 대부분의 시간이 소비되는 곳이 바로 여기다.**

### 겹치는 영역을 어떻게 덮어쓰지 않는가

객체 복사는 어떻게 구현될까? plug는 꽤 크기 때문에 **최종 위치가 현재 위치와 겹칠 수 있다.** 자기 자신을 덮어쓰지 않으려면 어떻게 해야 할까?

```text
문제: 제자리 복사 시 자기 자신을 덮어쓸 수 있다

     원본 위치        목적 위치
        ↓                ↓
  ┌─────────────────────────┐
  │███████████│             │
  └─────┬───────────────────┘
        └──── 이동 ────→
        ↑ 겹침 구간 ↑
```

**순진한 해법**은 중간 버퍼를 쓰는 것이다. 하지만 그러면 메모리 트래픽이 두 배가 된다 — 모든 객체를 두 번 복사해야 한다. 명백히 받아들일 수 없다.

우리는 객체를 통째로 복사해야 하는 일관된 레고 블록처럼 생각하는 경향이 있다. 그러나 **낮은 수준에서 이것들은 더 작은 조각으로 복사할 수 있는 연속된 메모리 영역일 뿐이다.**

CLR이 택한 접근이 정확히 그것이다. **슬라이딩 압축(sliding compaction)** 의 요점은 **항상 더 앞선 주소를 먼저 복사하고, 겹침이 자연스럽게 불가능해질 만큼 작은 양씩 복사하는 것**이다(.NET에서 최소 재배치 주소 차이는 최소 포인터 크기다).

따라서 객체 복사는 메모리를 포인터 단위로 복사하는 `memcopy` 함수로 실현된다. 코드를 더 효율적으로 만들기 위해 복사 루프는 **한 번에 4개의 포인터 크기 영역을 처리하도록 언롤링**되고, 나머지는 2개 또는 1개씩 묶는다.

```c
void memcopy (uint8_t* dmem, uint8_t* smem, size_t size)
{
   const size_t sz4ptr = sizeof(PTR_PTR)*4;
   // ...
   // 한 번에 포인터 크기 4개씩 복사
   if (size >= sz4ptr)
   {
      do
      {
         ((PTR_PTR)dmem)[0] = ((PTR_PTR)smem)[0];
         ((PTR_PTR)dmem)[1] = ((PTR_PTR)smem)[1];
         ((PTR_PTR)dmem)[2] = ((PTR_PTR)smem)[2];
         ((PTR_PTR)dmem)[3] = ((PTR_PTR)smem)[3];
         dmem += sz4ptr;
         smem += sz4ptr;
      }
      while ((size -= sz4ptr) >= sz4ptr);
   }
   // 남은 16바이트 / 8바이트 복사
}
```

이 복사 라인들은 여러 개의 `mov` 어셈블리 명령으로 컴파일되어 극도로 효율적이다.

> **📌 리전에서도 같은 메커니즘이다**
>
> 압축 단계 코드는 `gc_heap::compact_phase`에서 시작한다. 활성 브릭마다 `gc_heap::compact_in_brick`을 호출하고, 그것이 내부적으로 `gc_heap::compact_plug`를 호출한다.
>
> **리전에서 객체가 젊은 리전에서 오래된 리전으로 옮겨질 때도 정확히 같은 메커니즘이 쓰인다.** 다만 모든 오프셋 계산에 쓰는 할당자가 오래된 리전의 할당자라는 점만 다르다.

### 세대 경계 수정

Compact 단계 후에 호출되어 모든 세대 경계를 고친다. 내부 할당 포인터를 리셋하고, 계획된 할당 컨텍스트를 위한 빈 공간을 만들고(63.1절), 기타 필요한 보정을 한다.

> **📌 리전에서 세대가 비면**
>
> 리전에서는 어떤 세대에 리전이 하나도 남지 않으면 **리전 프리 리스트에서 하나를 가져온다.** 사용 가능한 것이 없으면 새로 만든다(62.8절).

### 세그먼트·리전 삭제·커밋 해제

더 이상 필요 없는 세그먼트와 리전을 제거하거나(VM 호딩이 켜져 있으면 재사용 리스트에 보관) 재배치한다.

### 프리 리스트 항목 생성

**각 고정된 plug 앞에** 새 free 객체를 만들어, 충분히 크면 프리 리스트에 추가한다. 그 길이는 Plan 단계에서 이미 계산되어 고정 plug 큐 항목에 저장되어 있다.

```text
압축 후 — 고정된 plug 앞의 빈 공간을 프리 리스트로

┌──────────┬──────────┬───────────┬──────────────────┐
│  plug 1  │  plug 2  │   FREE    │  고정된 plug      │
│  (이동)   │  (이동)   │ →프리리스트 │  (제자리)         │
└──────────┴──────────┴───────────┴──────────────────┘
                       ↑
              Plan에서 계산된 크기
```

### 루트 노화 (Age Roots)

파이널라이제이션 큐를 새 세대 경계에 맞게 갱신하고, 적절한 종류의 생존 핸들을 노화(또는 회춘)시키는 추가 보정을 한다. **핸들의 나이는 그것이 가리키는 객체의 세대를 반영하므로, GC는 어느 핸들을 수집 중에 스캔해야 할지 안다.**

### LOH 압축

LOH 압축은 SOH와 유사한 기법에 기반한다. 다만 **세대, 복잡한 plug, 브릭, plug 트리가 없어서** 구현이 훨씬 단순하다.

활성화되면 **LOH 압축은 SOH 압축보다 먼저 실행된다.** LOH에서 마킹된 객체를 스캔하는 단일 루프로 구성되고, LOH 계획 단계에서 계산된 재배치 오프셋을 써서 하나씩 목적지로 복사한다. 추가로 고정된 객체에 대해서는 그 앞에 대응하는 빈 공간이 만들어져 프리 리스트에 연결된다. **객체 사이의 패딩은 남는다** — 다음 GC 실행에서 필요할 수 있기 때문이다.

## 64.11 쓰기 장벽(write barrier)의 비용

62.7절에서 카드 테이블의 구조를 봤다. 여기서는 **그것을 유지하는 비용이 어디에 나타나는가**를 본다.

### 쓰기 장벽이 필요한 이유

세대별 GC의 핵심 전제는 **젊은 세대만 수집할 때 오래된 세대 전체를 스캔하지 않는 것**이다. 그런데 오래된 세대의 객체가 젊은 세대의 객체를 참조할 수 있다. 그 참조를 놓치면 살아 있는 객체를 수집하게 된다.

해법이 카드 테이블이고, 카드 테이블을 최신으로 유지하는 것이 **쓰기 장벽**이다. **참조 타입 필드에 참조를 쓸 때마다** 런타임이 대응하는 카드를 표시한다.

```csharp
class Node { public Node Next; }

node.Next = other;   // ← 이 한 줄이 단순한 store가 아니다
```

JIT이 만드는 코드는 대략 이렇다.

```asm
; node.Next = other;
mov     rcx, [rsp+20h]      ; rcx = node
mov     rdx, [rsp+28h]      ; rdx = other
call    CORINFO_HELP_ASSIGN_REF   ; ← 쓰기 장벽 헬퍼
```

헬퍼 안에서 실제 저장과 카드 표시가 함께 일어난다.

```asm
mov     [rcx], rdx          ; 실제 저장 (본래의 일)
; --- 여기부터가 쓰기 장벽 비용 ---
mov     rax, <ephemeral 하한>
cmp     rdx, rax
jb      Exit                ; 저장한 참조가 ephemeral보다 아래면 끝
mov     r8,  <ephemeral 상한>
cmp     rdx, r8
jae     Exit                ; 위면 끝 — 카드를 건드리지 않는다
mov     rax, <카드 테이블 주소>
shr     rcx, 0Bh            ; 대상 주소 / 2048 → 카드 바이트 인덱스
cmp     byte ptr [rcx+rax], 0FFh
jne     UpdateCardTable     ; 이미 표시되어 있으면 건너뛴다
REPRET
UpdateCardTable:
mov     byte ptr [rcx+rax], 0FFh   ; 카드 표시
Exit:
```

**모든 참조 저장이 카드를 더럽히는 것은 아니다.** 저장하는 **값**(`rdx`)이 ephemeral 세대(세대 0·1) 범위 안에 있을 때만 카드가 표시된다. 늙은 객체를 가리키는 참조를 쓰는 것은 검사 두 번으로 끝난다. 전체 어셈블리와 줄별 해설은 62.7절에 있다.

### 비용이 어디에 나타나는가

| 비용 | 내용 |
|---|---|
| **CPU — 명령어 추가** | 참조 저장 하나가 단순 `mov` 하나가 아니라 시프트·비교·조건 분기·저장으로 늘어난다 |
| **CPU — 캐시 오염** | 카드 테이블은 관리 힙과 **다른 메모리 영역**이다. 참조를 쓸 때마다 카드 테이블 캐시 라인도 건드린다(61.4절) |
| **CPU — 젊은 GC의 스캔** | 표시된 카드가 덮는 영역(64비트에서 카드 바이트 하나 = **2,048바이트**)을 젊은 GC마다 전부 스캔해야 한다 |
| **메모리** | 카드 테이블과 카드 번들 자체가 메모리를 차지한다. **관리 힙 밖**이라 GC 통계에는 안 잡힌다 |

> **⚠️ 실제 세분성은 카드가 아니라 2,048바이트다**
>
> 62.7절에서 카드 하나가 64비트에서 **256바이트**를 덮는다고 했다. 그런데 위 어셈블리를 보면 `shr rcx, 0Bh` — 즉 **2,048로 나눈 뒤 바이트 전체를 `0FFh`로 set**한다.
>
> 성능 관점에서 실제 세분성은 **2,048바이트**다. 그 안의 어느 한 곳에 참조를 쓰면 2 kB 전체가 "더러움"으로 표시되고, 다음 젊은 GC에서 그 2 kB를 전부 스캔한다.

> **⚠️ 서버 GC는 ephemeral 범위 검사를 생략한다**
>
> 위 어셈블리는 워크스테이션 GC용 `JIT_WriteBarrier_PreGrow64`/`PostGrow64`의 형태다. **서버 GC에서는 힙이 여럿이라 세대 0·1도 여럿**이고, 참조가 그중 어디에 속하는지 검사하는 것이 너무 느리다. 그래서 `JIT_WriteBarrier_SVR64`는 **ephemeral 범위 검사를 빼고 조건 없이 카드를 set 한다**(62.7절).
>
> 결과적으로 서버 GC에서는 늙은 객체를 가리키는 참조를 써도 카드가 더러워진다. 젊은 GC가 훑어야 할 영역이 그만큼 넓어진다.

> **⚠️ 쓰기 장벽은 대상이 늙은 세대인지 보지 않는다**
>
> 검사되는 것은 **저장하는 값**(`rdx`)뿐이고, **대상 주소**(`rcx`)가 늙은 세대인지는 확인하지 않는다. 그래서 젊은→젊은 참조도 카드를 더럽힌다. 허용되는 이유는 Mark 단계가 카드 테이블을 **늙은 세대 주소에 대해서만** 조회하기 때문이다 — 나머지 표시는 그냥 무시된다.

### 쓰기 장벽을 피하는 방법

**값 타입 필드에는 쓰기 장벽이 없다.**

```csharp
struct Point { public int X, Y; }        // 참조 없음
class Holder { public Point P; }

holder.P.X = 5;   // 쓰기 장벽 없음 — 단순 mov
```

참조가 없는 구조체는 GC가 추적할 것이 없으므로 쓰기 장벽이 생성되지 않는다. 이것이 69.1절에서 "구조체로 바꿀 때의 손익"을 계산할 때 계상해야 할 **숨은 이득**이다.

| 코드 | 쓰기 장벽 |
|---|---|
| `obj.RefField = other;` | **있다** |
| `obj.IntField = 5;` | 없다 |
| `structVar.RefField = other;` (스택 위 구조체) | 없다 — 스택은 카드 테이블 대상이 아니다 |
| `array[i] = refValue;` (참조 타입 배열) | **있다** (+ 배열 공변성 검사, 9.2절) |
| `array[i] = intValue;` (값 타입 배열) | 없다 |
| `Span<T>`를 통한 저장 (T에 참조 없음) | 없다 |

> **💡 참조가 없는 데이터 구조가 두 번 이득이다**
>
> 참조 필드를 없애면 두 곳에서 이득이 난다.
>
> 1. **쓰기 시점** — 쓰기 장벽이 사라진다(이 절)
> 2. **GC 시점** — 참조 재배치 단계의 스캔 대상에서 빠진다(64.10절)
>
> 70장의 AoS → SoA 전환과 63.9절의 "구조체를 고려하라"가 GC 관점에서 왜 효과적인지가 여기서 합쳐진다. 단순히 힙 할당을 줄이는 것 이상이다.

> **⚠️ 그렇다고 참조를 없애려고 코드를 비틀지 마라**
>
> 쓰기 장벽은 나노초 단위 비용이다. **핫 패스에서 초당 수백만 번 참조를 쓰는 자료구조**가 아니라면 측정 가능한 차이를 만들지 못한다. 67장의 원칙 그대로 — **측정하고 나서 판단하라.**

## 64.12 EE 일시 중단(suspension)과 안전 지점(safe point)

GC의 어떤 단계에서는 애플리케이션 코드를 실행하는 스레드가 돌아서는 안 된다. 그 스레드가 접근하려는 객체를 **GC 자신이 조작하고 있기 때문**이다. GC 모드에 따라 그 순간은 짧거나 길다. 비동시(non-concurrent) 모드에서는 GC 전체가 사용자 스레드 중단 상태에서 실행된다. 동시(concurrent) 모드(65.2절)에서도 **일부 구간은 반드시 중단이 필요하다.**

사용자 코드를 실행하는 모든 스레드를 중단하는 과정을 **EE 일시 중단(EE suspension, Execution Engine suspension)** 이라 한다. 애플리케이션 관점에서는 GC 기간 동안 온 세상이 멈추므로 흔히 **"stop the world"** 기법이라 부른다.

> **📌 Book of the Runtime의 정의**
>
> "CLR은 모든 관리 객체를 안전하고 신뢰성 있게 찾기 위해, 모든 관리 스레드가 멈춰 있음을(그래서 힙을 수정하지 않음을) 보장해야 한다. **레지스터와 스택 위치를 살아 있는 참조에 대해 검사할 수 있는 안전 지점(safe point)에서만** 멈춘다."
>
> 즉 **안전 지점이란 레지스터와 스택 위치를 살아 있는 참조에 대해 검사할 수 있는 코드 위치**다.

### 협조 모드와 선점 모드

GC 관점에서 각 관리 스레드는 두 가지 모드 중 하나에 있다.

| 모드 | 의미 |
|---|---|
| **협조(cooperative)** | .NET Core 소스의 표현으로 — "스레드가 협조 모드에 있다는 것은 기본적으로 **GC 참조를 수정하고 있을 가능성이 있다**고 말하는 것이며, 따라서 런타임은 GC 참조를 열거할 수 있는 'GC 안전' 위치에 도달하도록 그 스레드와 **협조해야** 한다." 관리 코드를 실행 중일 때 대부분의 시간 이 모드에 있다 |
| **선점(preemptive)** | 중단 서비스가 이 스레드를 신경 쓸 필요가 없다는 뜻이다. GC 참조에 접근하거나 조작하지 않는 코드를 실행 중이므로 **GC가 일어나도 되는 자리에 있음이 보장된다.** 대부분의 경우 P/Invoke 호출로 비관리 코드를 실행 중이라는 뜻이다(60.1절). 네이티브 호출에서 돌아올 때, GC가 진행 중이면 스레드가 스스로 중단한다 |

이렇게 보면 **EE 일시 중단은 모든 관리 스레드가 선점 모드에 있는 상황을 강제하는 것**으로 정의할 수 있다.

협조 → 선점 전환은 **안전 지점에서만** 일어날 수 있다. 모든 안전 지점에서 스레드 상태의 스냅샷이 기억된다 — 스택과 레지스터의 레이아웃을 서술하는 것인데, 그것들이 객체에 대한 참조(객체 트리의 루트를 이루는)를 담을 수 있기 때문이다. 이 데이터가 **GC info**다(64.4절).

### 부분 중단 가능 vs 완전 중단 가능

애플리케이션의 모든 명령을 안전 지점으로 취급하면(모든 명령에서 스레드를 선점할 수 있게 하려면) **모든 명령마다 GC info를 저장해야 한다.** 엄청난 메모리를 소비한다.

늘 그렇듯 타협이 이루어졌다. 관리 코드는 두 종류로 JIT될 수 있다.

| 종류 | 안전 지점 | 특징 |
|---|---|---|
| **부분 중단 가능(partially interruptible)** | **다른 메서드 호출 지점만**(GC가 대기 중인지 확인하는 명시적 GC 폴 호출 포함) | 평균적인 .NET 메서드에서 메서드 호출 사이 명령 수는 꽤 적다. 따라서 합리적인 GC info 저장 오버헤드로 좋은 안전 지점 밀도를 제공한다. **JIT 컴파일러가 선호하는 선택** |
| **완전 중단 가능(fully interruptible)** | 메서드의 **모든 명령**(프롤로그·에필로그 제외) | JIT이 모든 명령에 대해 GC info를 저장해야 하지만, 코드를 빠르게 중단 가능하게 만든다. 저장 오버헤드 때문에 JIT은 이 방식을 피하려 한다 |

> **📌 JIT이 완전 중단 가능을 선택하는 전형적 경우**
>
> **반복 횟수를 알 수 없고 안에 메서드 호출이 없는 루프**다. 빨리 끝난다는 보장이 없으므로 GC를 임의의 시간 동안 막을 수 있기 때문이다.
>
> JIT이 이 문제를 푸는 또 다른 방법은 **루프의 각 반복에 GC 폴 호출을 주입하는 것**이다. .NET Core 코드에서 `FC_GC_POLL`과 `FC_GC_POLL_RET` 매크로를 찾아보면 GC 폴 호출 구현을 볼 수 있다.
>
> 다만 GC 폴은 효율적인 접근이 아니라서 드물다. 대부분의 메서드에서는 **첫 메서드 호출을 기다리는 것으로 충분**하다. 그 호출 자체가 안전 지점이기 때문이다.
>
> Book of the Runtime의 표현으로 — "JIT은 **코드 품질, GC info 크기, GC 중단 지연 시간 사이의 최선의 타협**을 찾는 휴리스틱에 기반해 완전 중단 가능 코드를 낼지 부분 중단 가능 코드를 낼지 선택한다."

### 중단 절차와 하이재킹

중단 중에 실행 엔진은 현재 협조 모드로 돌고 있는 모든 스레드를 **안전 지점에서 선점 모드로 옮기도록** 조율한다. 먼저 OS API를 호출해 하부 네이티브 스레드를 중단시킨다(Windows에서는 `SuspendThread`). 그다음,

- **완전 중단 가능 코드** — 쉽다. 스레드가 항상 안전 지점에 있으므로 그냥 중단된 채로 둔다.
- **부분 중단 가능 코드** — 스레드가 안전 지점 밖에서 중단되었다면, 실행 엔진이 스택에 저장된 **스레드의 반환 주소를 수정해** 특별한 스텁을 가리키게 한다. 그 스텁이 스레드를 안전 지점에 "주차"시킨다. 그다음 스레드를 재개하면, 현재 메서드에서 돌아올 때 그 스텁을 실행한다.

> **⚠️ 이론과 현실 — 하이재킹**
>
> 위의 첫 번째 항목("완전 중단 가능 코드는 그냥 중단된 채로 둔다")에는 각주가 붙어 있다. 현실은 더 복잡하다. **"각종 역사적 OS 버그가 이 방식이 그대로 동작하는 것을 막는다."** 그래서 런타임은 중단되는 스레드를 **하이재킹(hijack)** 한다 — 명령 포인터를 특별한 "리디렉트 루틴"으로 덮어쓰는 것이다. 그다음 스레드를 재개하면 그 루틴이 정확한 스레드 컨텍스트를 얻고 GC 완료를 기다린다.

**스레드 재개는 중단보다 훨씬 단순한 작업이다.** GC가 끝나면 중단 종료를 알리는 이벤트가 시그널되어 중단된 스레드들이 전부 깨어나고 실행을 재개한다.

### 측정하기

GC 중단과 스레드 재개는 CLR 이벤트 쌍으로 모니터링할 수 있다.

| 이벤트 쌍 | 측정 대상 |
|---|---|
| `GCSuspendEEBegin_V1` / `GCSuspendEEEnd_V1` | 중단에 걸린 시간 |
| `GCRestartEEBegin_V1` / `GCRestartEEEnd_V1` | 재개에 걸린 시간 |

.NET 애플리케이션에서 가장 쉬운 방법은 `dotnet-gcmon`을 `-c`로 실행하고 **suspension time (ms) 열**을 선택한 뒤 `-p`로 프로세스 ID를 주는 것이다. .NET Framework이거나 `dotnet-trace`로 기록한 세션을 분석하려면 **PerfView의 GCStats 리포트**를 쓴다. `GC Events by Time` 표에 각 GC의 **`Suspend Msec`** 과 **`Pause MSec`** 열이 있다.

> **📌 중단 시간은 일시 정지 시간보다 훨씬 짧다**
>
> 스레드가 중단되기를 기다리는 시간은 **일시 정지 자체보다 훨씬 짧다.** 이것이 정상이다.
>
> **Rule 17 — 런타임 중단을 지켜보라.** 스레드를 멈추고 재개하는 과정은 최적화가 잘 되어 있어서 **모든 스레드를 중단하는 데 밀리초의 몇 분의 일이 걸린다.** 중단이 일관되게 그보다 오래 걸린다면 뭔가 잘못된 것이니 조사해야 한다. **1밀리초를 넘는 중단 시간은 주목해야 한다.**
>
> 그런 일이 생기면 중단 기간에 네이티브 프로파일러를 돌려보라. 코드의 무언가가(높은 우선순위 스레드를 실행하거나, 아주 긴 I/O를 동기적으로 실행해서) 스레드 중단을 방해하고 있는 것을 발견할 수 있다.

> **📌 과거의 실제 버그**
>
> 일반적으로 애플리케이션 실행 중 눈에 띄는 중단 시간을 관찰해서는 안 된다. 관찰된다면 **십중팔구 런타임 버그**다. 실제로 .NET 2.0에는 특정 시나리오(안전 지점에 닿지 않고 같은 코드를 실행하는 빡빡한 CPU 바운드 루프)에서 중단 시간이 **수 초까지 늘어나는 버그**가 있었다. .NET 4.0에서 고쳐졌다.
>
> 일반적인 애플리케이션에서 긴 중단(1 ms 초과)을 볼 수 있는 경우는 **긴 I/O 작업**이나 **엉망이 된 스레드 우선순위** 정도다.

### 모드 전환의 숨은 비용 — 스택 스필

스레드를 협조에서 선점으로 전환하는 데는 비용이 있다. 부기 작업도 있지만, 오버헤드의 큰 부분은 **음험한 문제**에서 온다. 이해하려면 먼저 호출 규약 이야기를 해야 한다.

함수를 호출할 때 호출자와 피호출자는 인수와 반환값을 어디에 저장할지 정하는 **호출 규약**을 쓴다. 호출 규약은 **호출 끝에 레지스터 값을 복원할 책임이 누구에게 있는지**도 정의한다. 호출자 정리(caller cleanup), 피호출자 정리(callee cleanup), 또는 둘의 혼합일 수 있다.

**피호출자 정리 규약**으로 함수가 호출되면, 호출 기간 동안 레지스터에 저장된 값에 무슨 일이 일어날지 알 수 없다. 메서드가 값을 다른 레지스터로 복사하거나, 스택에 푸시했다가 팝하거나 할 수 있다. **유일한 보장은 반환 전에 원래 값을 복원한다는 것뿐이다.**

여기서 문제가 생긴다. **그런 메서드 실행 중에 가비지 컬렉션이 일어나면?** 객체가 옮겨지면 GC는 그것을 가리키는 모든 값을 갱신해야 한다. 그런데 그 값 중 하나가 네이티브 피호출자 정리 메서드 호출 중에 레지스터에 저장되어 있다면, **GC는 그 값이 현재 어디 저장되어 있는지 알 방법이 없고**, 메서드는 반환 시 옛 값을 복원해버린다.

결국 **런타임은 선점 모드로 전환하기 전에 어떤 값도 레지스터에 남겨둘 수 없다.** 그래서 JIT은 **스택 스필(stack spill)** 이라 부르는 것을 낸다 — 선점 모드 전환 전에 모든 레지스터 값을 스택에 저장하는 일련의 `push` 명령과, 협조 모드로 돌아올 때 다시 읽어들이는 일련의 `pop` 명령이다. 이렇게 하면 스레드가 선점 모드인 동안 GC가 일어나도 런타임이 **스택 위 값을 직접 갱신할 수 있다.** 네이티브 메서드가 레지스터로 무엇을 하든 신경 쓸 필요가 없다.

> **⚠️ 스택 스필의 비용과 `SuppressGCTransition`**
>
> 스택 스필에는 비용이 있다. P/Invoke 호출 시간에 **여러 나노초**를 더한다. 메서드가 밀리초, 심지어 수백 마이크로초 걸린다면 무시할 만하지만, **거의 즉시 반환하는 사소한 메서드를 호출할 때는 엄청나게 비싸질 수 있다.**
>
> 그런 경우를 위해 **`SuppressGCTransition` 특성**이 .NET 5에 도입되었다(60.10절). P/Invoke를 할 메서드에 적용하면 이른바 "GC 전환"을 제거하고, 스레드는 네이티브 호출 기간 동안 **협조 모드에 머문다.** 실무적으로는 그 네이티브 호출 중에 **가비지 컬렉션이 일어날 수 없다는 뜻이다**(실행 엔진이 스레드를 중단하려 하지만 네이티브 코드 안에는 안전 지점이 없으므로 메서드가 반환할 때까지 아무 일도 일어나지 않는다). 덕분에 JIT이 스택 스필을 낼 필요가 없어 네이티브 호출 오버헤드의 일부가 사라진다.
>
> **그러나 양날의 검이다.** 네이티브 호출 중에 가비지 컬렉션이 트리거되면, 실행 엔진은 **다른 모든 스레드를 중단시킨 뒤** 그 마지막 스레드가 호출에서 나오기를 기다린다. 즉 **네이티브 스레드만 계속 일하는 동안 애플리케이션이 사실상 얼어붙는다.** 상황이 오히려 나빠지는 것이다.
>
> 그래서 `SuppressGCTransition`은 **사소한 시간(수 나노초) 안에 완료됨이 절대적으로 보장되는 메서드에만** 써야 한다. **I/O나 동기화에 의존하는 메서드에는 절대 쓰지 마라.** 단점이 이점을 크게 초과한다.

## 이 장의 요약

- **GC 한 사이클은 EE 일시 중단 → Mark → Plan → Sweep 또는 Compact → 재개** 순서다. 문헌이 흔히 "Mark-Sweep-Compact"로 줄여 부르지만 **Plan이 실제 엔진**이다.
- **Mark 단계**는 루트에서 객체 그래프를 순회하며 도달 가능한 객체에 비트를 세운다. 루트는 스택 루트, GC 핸들, 파이널라이제이션 루트, GC 내부 루트 네 종류다.
- **GC Info와 즉시 루트 수집** 때문에 **어휘 범위와 실제 생존 범위가 다르다.** Release 빌드 + Tier1에서 지역 변수는 마지막 실제 사용 지점에서 죽는다. `GC.KeepAlive`가 필요한 이유이고, 계층형 컴파일 때문에 프로덕션에서만 재현되는 버그의 원인이다.
- **Plan 단계는 객체를 옮기지 않고 압축을 시뮬레이션한다.** 힙을 plug(생존 묶음)와 gap(사망 묶음)으로 쪼개고, 각 plug의 재배치 오프셋을 내부 할당자로 계산한다. plug 정보는 **직전 gap의 끝, 24바이트(64비트)** 에 저장된다 — 최소 객체 크기가 24바이트인 진짜 이유다.
- **브릭 테이블**은 4 kB(64비트) 단위로 plug 트리 루트를 가리켜 "이 객체의 새 주소는?"에 빠르게 답한다.
- **고정은 Plan 단계를 크게 복잡하게 만든다.** pre-plug/post-plug 복사 비용, 고정 plug가 일반 객체 하나만큼 확장되는 문제, 힙을 걸을 수 없게 되는 문제. **가장 나쁜 것은 중간 수명의 고정이다.**
- **강등(demotion)** 은 고정된 plug 주변 gap을 재사용하기 위한 최적화다. 진단할 필요는 없고, **고정이 유발하는 단편화**만 신경 쓰면 된다.
- **압축 결정**은 세대별 단편화 크기와 비율 **둘 다** 임계값을 넘을 때 내려진다(gen0 40,000/50%, gen1 80,000/50%, gen2 200,000/25%).
- **Sweep은 gap을 프리 리스트 항목으로 바꾸는 것이 전부**고, **Compact는 참조를 먼저 갱신한 뒤 plug를 슬라이딩 복사한다.** 전형적 조합은 **LOH 스윕 + SOH 압축**이며 순서가 자료구조를 하나 없앤다.
- **쓰기 장벽**은 참조 저장마다 붙고 실제 세분성은 2,048바이트다. **참조 없는 자료구조는 쓰기 시점과 GC 시점 양쪽에서 이득**이다.
- **EE 일시 중단**은 모든 관리 스레드를 안전 지점에서 선점 모드로 옮기는 것이다. 정상이면 밀리초의 몇 분의 일이고, **1 ms를 넘으면 조사 대상**이다(Rule 17).

### 이 장이 소개한 규칙

| 규칙 | 요지 |
|---|---|
| **Rule 17 — 런타임 중단을 지켜보라** | 중단은 밀리초의 몇 분의 일이어야 한다. 1 ms 초과는 조사 대상 |

## 연습 문제

1. `GC.Collect()` 전후로 `GC.CollectionCount(0)`, `(1)`, `(2)`를 출력하는 프로그램을 만들고, 세대 인자를 바꿔가며 실제로 어느 세대가 수집되는지 확인하라. 요청한 세대와 다른 결과가 나오는 경우를 찾아보라.
2. `fixed`로 큰 배열을 고정한 채 다른 객체를 대량 할당하는 프로그램을 만들고, PerfView로 `Pinned Obj` 열과 `Pinning At GC Time Stacks` 뷰를 확인하라. 고정을 제거한 버전과 단편화 수치를 비교하라.
3. `GCHandle.Alloc(obj, GCHandleType.Pinned)`로 고정한 뒤 WinDbg에서 `!GCHandles Pinned`로 확인하라. `fixed`로 고정한 것은 왜 이 목록에 안 나오는지 설명하라.
4. `dotnet-gcmon -c -p <pid>`로 suspension time 열을 켜고, 긴 동기 I/O를 하는 스레드가 있을 때와 없을 때의 중단 시간을 비교하라.
5. 참조 필드가 많은 클래스 배열과, 같은 데이터를 담은 값 타입(참조 없음) 구조체 배열을 만들어 GC 시간을 BenchmarkDotNet으로 비교하라. 차이의 원인을 64.10절과 64.11절로 설명하라.
6. `DOTNET_GCEnableSpecialRegions=1`을 켜고 끈 상태로 같은 워크로드를 돌려 gen0→gen2 직행 승격이 관찰되는지 `dotnet-trace`로 확인하라. (실험적 기능이므로 런타임 버전에 따라 동작하지 않을 수 있다.)
7. `!DumpGCData`를 실행해 "interesting data points"의 `converted pins` 값을 확인하고, 고정을 늘렸을 때 그 값이 어떻게 변하는지 관찰하라.
