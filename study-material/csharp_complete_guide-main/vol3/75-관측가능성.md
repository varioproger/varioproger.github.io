# 75장. 관측 가능성

> **이 장의 위치** — Part XIII의 마지막 장이다. 73장은 `Debug`/`Trace`/성능 카운터라는 **1세대 진단 API**를, 74장은 디버거를 붙일 수 있는 상황의 **디버깅 워크플로**를 다뤘다. 그런데 프로덕션에서 벌어지는 문제 대부분은 디버거를 붙일 수 없다. 재현되지 않고, 특정 인스턴스에서만 나고, 서비스 열 개를 거쳐가는 요청 하나에서 난다. 그런 문제를 다루는 유일한 방법은 **애플리케이션이 스스로 자기 상태를 말하게 만드는 것** — 관측 가능성(observability)이다.
>
> **선수 지식** — 73장(진단 API), 74장(디버깅 기법), 49.9절(`AsyncLocal<T>`), 32장(예외)
>
> **이 장에서 다루지 않는 것** — `Debug`/`Trace`/`TraceListener`/성능 카운터는 73장에서 다뤘다. 메모리 문제 진단 절차는 66장, 벤치마킹은 67장, ASP.NET Core 파이프라인 통합은 81.3절이다.

## 관측 가능성이란 무엇인가

**모니터링(monitoring)** 과 **관측 가능성(observability)** 은 다르다. 이 차이를 먼저 잡고 가야 나머지가 말이 된다.

| | 모니터링 | 관측 가능성 |
|---|---|---|
| 질문의 성격 | **미리 아는 질문**에 답한다 | **미리 몰랐던 질문**에 답할 수 있다 |
| 예 | "CPU가 80%를 넘었나?" | "왜 어제 오후 3시 12분에 특정 고객의 결제만 느렸나?" |
| 설계 방식 | 알람 대상을 먼저 정하고 그것만 잰다 | 나중에 쪼갤 수 있도록 **맥락을 함께** 남긴다 |
| 실패 모드 | 대시보드는 전부 초록인데 사용자는 불평한다 | 데이터가 너무 많아 비용이 폭발한다 |

관측 가능성은 **시스템의 외부 출력만 보고 내부 상태를 얼마나 추론할 수 있는가**의 척도다. 제어 이론에서 온 말이고, 소프트웨어에서는 실무적으로 이렇게 읽힌다 — **코드를 고치거나 재배포하지 않고, 이미 나온 신호만으로 새 질문에 답할 수 있는가.**

> **⚠️ "로그를 많이 찍으면 관측 가능하다"는 오해**
>
> 로그 양과 관측 가능성은 비례하지 않는다. `Console.WriteLine("여기 도착")`을 천 군데 박아도, 그 로그에 **요청 ID가 없으면** 동시 요청 100개가 섞인 텍스트 더미일 뿐이다.
>
> 관측 가능성을 만드는 것은 양이 아니라 **상관관계(correlation)** 다. 이 장의 대부분은 결국 "어떻게 신호에 맥락을 붙일 것인가"에 대한 이야기다.

### 세 가지 신호

관측 가능성은 세 종류의 신호로 이루어진다. 흔히 "세 기둥(three pillars)"이라 부른다.

```text
                    ┌─────────────────────────────┐
                    │      하나의 요청/작업          │
                    └──────────────┬──────────────┘
                                   │
        ┌──────────────────────────┼──────────────────────────┐
        ↓                          ↓                          ↓
┌───────────────┐         ┌───────────────┐         ┌───────────────┐
│     로그       │         │    메트릭      │         │     추적       │
│    (Logs)     │         │   (Metrics)   │         │   (Traces)    │
├───────────────┤         ├───────────────┤         ├───────────────┤
│ 개별 사건의    │         │ 집계된 수치의  │         │ 하나의 요청이  │
│ 상세 기록      │         │ 시계열         │         │ 지나간 경로    │
│               │         │               │         │               │
│ "무슨 일이     │         │ "얼마나 자주,  │         │ "어디서 시간을 │
│  있었나"       │         │  얼마나 나쁜가"│         │  썼나"         │
│               │         │               │         │               │
│ 고카디널리티   │         │ 저카디널리티   │         │ 고카디널리티   │
│ 비쌈           │         │ 쌈             │         │ 샘플링 필요    │
└───────────────┘         └───────────────┘         └───────────────┘
        │                          │                          │
        └──────────────────────────┴──────────────────────────┘
                                   ↓
                    TraceId / SpanId 로 서로 연결된다
                    ← 이것이 "세 기둥"의 실제 가치다
```

세 신호가 각각 유용한 것이 아니다. **서로 연결될 때** 유용하다. 메트릭에서 p99 지연이 튄 것을 보고 → 그 시간대의 느린 추적을 찾고 → 그 추적의 특정 스팬으로 좁히고 → 그 스팬에 붙은 로그를 읽는다. 이 흐름이 끊기면 세 기둥은 세 개의 고립된 도구일 뿐이다.

### .NET의 API 지형

.NET에서 세 신호에 대응하는 API는 각각 다른 네임스페이스에 있고, 도입 시기도 다르다.

| 신호 | API | 네임스페이스 | 패키지 | 도입 |
|---|---|---|---|---|
| 로그 | `ILogger<T>` | `Microsoft.Extensions.Logging` | `Microsoft.Extensions.Logging.Abstractions` | .NET Core 1.0 |
| 로그(소스 생성) | `[LoggerMessage]` | 위와 같음 | 위와 같음 | ※.NET 6 |
| 메트릭 | `Meter`, `Counter<T>` 등 | `System.Diagnostics.Metrics` | BCL 내장 (`System.Diagnostics.DiagnosticSource`) | ※.NET 6 |
| 추적 | `ActivitySource`, `Activity` | `System.Diagnostics` | 위와 같음 | `Activity`는 .NET Core 2.1, `ActivitySource`는 .NET 5 |
| 상태 점검 | `IHealthCheck` | `Microsoft.Extensions.Diagnostics.HealthChecks` | 동명 패키지 | .NET Core 2.2 |

> **📌 왜 BCL 안에 있는 것과 패키지로 나온 것이 갈리는가**
>
> `Meter`와 `ActivitySource`는 **BCL에 있다.** 라이브러리 저자가 계측을 넣을 때 외부 의존성을 추가하지 않아도 되게 하려는 의도적 설계다. 그래서 `System.Net.Http`, `Microsoft.EntityFrameworkCore`, ASP.NET Core가 전부 이 API로 자기 자신을 계측하고 있고, 당신은 **그것을 켜기만 하면 된다**(75.5절).
>
> 반면 `ILogger`는 `Microsoft.Extensions.*` 계열이라 패키지가 필요하다. 다만 `Microsoft.Extensions.Logging.Abstractions`는 인터페이스만 담은 초경량 패키지라, 라이브러리가 참조해도 부담이 적다.

## 75.1 로깅과 구조적 로그 — `ILogger`, 로그 수준, 스코프

### 73장의 `Trace`에서 무엇이 달라졌나

73.2절에서 `Debug`와 `Trace`를 봤다. `Trace.WriteLine`은 문자열 하나를 리스너에 흘려보낸다. 그것으로 충분했던 시절이 있었지만, 지금의 요구는 다르다.

| 요구 | `Trace` | `ILogger` |
|---|---|---|
| 여러 대상에 동시 출력 | `TraceListener` 추가 | 공급자(provider) 추가 |
| 수준별 필터링 | `TraceSwitch` (전역) | **카테고리별** 최소 수준 |
| 구조화된 데이터 | 없음 (문자열만) | **메시지 템플릿 + 이름 있는 값** |
| 의존성 주입 | 정적 클래스 | `ILogger<T>` 생성자 주입 |
| 요청 단위 맥락 | 없음 | `BeginScope` |
| 비활성 시 비용 | `[Conditional]`로 호출 제거 | `IsEnabled` 게이트 |

> **💡 새 코드에서는 `ILogger`를 써라**
>
> `Trace`/`TraceSource`는 여전히 동작하고, 프레임워크에 깊이 박힌 레거시 코드에서는 그것이 유일한 선택일 수 있다. 그러나 **새로 쓰는 코드에서는 `ILogger`가 정답이다.** 이유는 위 표의 마지막 세 줄 — 구조화, 의존성 주입, 스코프 — 이고, 이 셋이 없으면 분산 시스템에서 로그를 쓸 수 없기 때문이다.

### 로그 수준 7종

`LogLevel` 열거형은 값 7개를 가진다. 값이 클수록 심각하다.

| 수준 | 값 | 실무 기준 | 프로덕션 기본 활성 |
|---|---|---|---|
| `Trace` | 0 | 변수 값, 루프 반복 — **민감 정보가 섞이기 쉬움** | 아니오 |
| `Debug` | 1 | 개발 중 흐름 추적, 분기 선택 이유 | 아니오 |
| `Information` | 2 | **비즈니스적으로 의미 있는 사건.** "주문 생성됨", "사용자 로그인" | 예 |
| `Warning` | 3 | 비정상이지만 처리는 계속됨. 재시도, 폴백 발동, 캐시 미스율 급증 | 예 |
| `Error` | 4 | **현재 작업이 실패했다.** 요청 하나가 죽었지만 프로세스는 산다 | 예 |
| `Critical` | 5 | **프로세스나 시스템이 위태롭다.** 시작 실패, 데이터 손상, 디스크 고갈 | 예 |
| `None` | 6 | 로깅 안 함 (필터 설정용, 로그 호출용이 아님) | — |

> **⚠️ `Trace` 수준에는 민감 정보를 찍지 마라**
>
> `LogLevel.Trace`가 "개발용이니 아무거나 찍어도 된다"는 뜻이 아니다. 누군가 프로덕션에서 문제를 잡으려고 임시로 `Trace`를 켜는 순간, 그동안 안전하다고 믿었던 비밀번호·토큰·개인정보가 전부 로그 저장소로 흘러간다.
>
> ASP.NET Core 자체가 이 문제를 갖고 있다 — `Microsoft.AspNetCore` 카테고리를 `Trace`로 켜면 **요청 헤더 전체**가 찍히고 거기에는 `Authorization` 헤더가 들어 있다. 그래서 프레임워크는 `Debug`/`Trace`를 켤 때 경고를 문서에 명시한다.
>
> 원칙 — **어떤 수준이든 로그에 찍는 순간 그것은 영구 기록이라고 가정하라.**

> **⚠️ `Error`와 `Critical`을 구별하지 않으면 알람이 무의미해진다**
>
> 흔한 실패 패턴이 있다. 모든 예외를 `LogError`로 찍으면, 사용자가 잘못된 입력을 보낸 것(정상적인 400)과 데이터베이스가 죽은 것(비정상적인 500)이 같은 수준으로 쌓인다. 그러면 `Error` 개수 기반 알람은 노이즈에 묻혀 아무도 안 본다.
>
> 기준 — **`Error`는 "이 요청이 실패했다", `Critical`은 "다음 요청도 실패할 것이다".** 사용자 입력 오류는 `Warning`이거나 아예 로그가 아니다.

### 기본 사용

```csharp
using Microsoft.Extensions.Logging;

public class OrderService
{
    readonly ILogger<OrderService> _logger;

    // 생성자 주입 — 카테고리 이름이 자동으로 "MyApp.OrderService"가 된다
    public OrderService(ILogger<OrderService> logger) => _logger = logger;

    public async Task<Order> CreateAsync(int customerId, decimal amount)
    {
        _logger.LogInformation(
            "주문 생성 시작. 고객 {CustomerId}, 금액 {Amount}", customerId, amount);

        try
        {
            var order = await _repository.InsertAsync(customerId, amount);
            _logger.LogInformation("주문 {OrderId} 생성됨", order.Id);
            return order;
        }
        catch (DbException ex)
        {
            _logger.LogError(ex,
                "주문 생성 실패. 고객 {CustomerId}, 금액 {Amount}", customerId, amount);
            throw;
        }
    }
}
```

호스트가 없는 콘솔 앱에서 직접 팩터리를 만들려면 이렇게 한다.

```csharp
using ILoggerFactory factory = LoggerFactory.Create(builder =>
{
    builder
        .AddConsole()
        .SetMinimumLevel(LogLevel.Information);
});

ILogger<Program> logger = factory.CreateLogger<Program>();
logger.LogInformation("시작");
```

> **⚠️ `ILoggerFactory`는 반드시 폐기해야 한다**
>
> `LoggerFactory.Create`가 반환하는 팩터리는 `IDisposable`이다. 폐기하지 않으면 **버퍼링하는 공급자의 로그가 유실된다** — 73.3절에서 본 `TraceListener` 플러시 문제와 정확히 같은 함정이다.
>
> 호스트(`Host.CreateApplicationBuilder`)를 쓰면 DI 컨테이너가 수명을 관리하므로 신경 쓸 필요가 없다. 직접 만들 때만 문제가 된다.

### 구조적 로그 — 왜 문자열 보간이 아닌가

이것이 이 절에서 가장 중요한 내용이다.

```csharp
// ❌ 하지 마라
_logger.LogInformation($"주문 {orderId} 생성됨, 금액 {amount}");

// ✅ 이렇게 하라
_logger.LogInformation("주문 {OrderId} 생성됨, 금액 {Amount}", orderId, amount);
```

겉보기에는 같은 문자열이 나온다. 그러나 **완전히 다른 일이 일어난다.**

| | 문자열 보간 | 메시지 템플릿 |
|---|---|---|
| 로거가 받는 것 | 이미 조립된 문자열 하나 | **템플릿 + 이름-값 쌍 배열** |
| 로그 저장소에 저장되는 것 | 문자열 | 템플릿 + `{OrderId: 4711, Amount: 29.9}` |
| `OrderId = 4711`로 검색 | 정규식으로 문자열 파싱 (사실상 불가) | **필드 조회. 인덱스가 걸린다** |
| 같은 종류의 로그 그룹핑 | 불가 (매번 문자열이 다름) | 템플릿이 같으므로 **자동 그룹핑** |
| 비활성 수준일 때 비용 | **문자열이 이미 만들어졌다** | 조립 안 함 |

마지막 행이 결정적이다. 문자열 보간을 쓰면 `LogTrace`를 껐어도 **문자열은 이미 힙에 만들어진 뒤**에 로거에게 전달되고, 로거는 그것을 버린다. 63.9절에서 본 "숨은 할당"의 교과서적 사례다.

> **📌 자리표시자 이름은 위치로 매칭된다**
>
> `{OrderId}`와 `orderId` 인자가 이름으로 연결된다고 생각하기 쉽지만 **아니다. 순서로 매칭된다.** 다음 코드는 컴파일되고 실행되며, 값이 뒤바뀐 채 기록된다.
>
> ```csharp
> _logger.LogInformation("주문 {OrderId} 금액 {Amount}", amount, orderId);  // 뒤바뀜
> ```
>
> 이 실수를 컴파일 타임에 잡는 방법이 75.2절의 소스 생성 로깅이다.

> **⚠️ 자리표시자 이름은 `PascalCase`로**
>
> 관례상 자리표시자는 `{OrderId}`처럼 파스칼 케이스를 쓴다. 저장소에서 필드명이 되기 때문이고, 대소문자를 섞어 쓰면 같은 개념이 `orderId`/`OrderId`/`order_id`로 흩어져 검색이 깨진다.
>
> 그리고 **같은 개념에는 프로젝트 전체에서 같은 이름을 써라.** `UserId`와 `AccountId`와 `CustomerId`가 같은 것을 가리킨다면 관측 가능성은 이미 절반 망가진 것이다.

### `@`와 `$` 접두사

일부 로깅 공급자(대표적으로 Serilog)는 자리표시자에 접두사를 붙여 직렬화 방식을 지정할 수 있다.

```csharp
_logger.LogInformation("주문 상세 {@Order}", order);   // 객체를 구조 분해해서 저장
_logger.LogInformation("상태 {$Status}", statusObj);   // ToString() 결과를 문자열로
```

> **⚠️ `{@Object}`는 공급자 의존적이고 위험하다**
>
> 두 가지 문제가 있다.
>
> 1. **`Microsoft.Extensions.Logging`의 기본 공급자는 `@`를 특별 취급하지 않는다.** Serilog 등 일부 공급자만 해석한다. 즉 이식성이 없다.
> 2. **객체를 통째로 직렬화하면 그 안의 모든 필드가 로그에 들어간다.** 엔티티를 그대로 넘기면 비밀번호 해시, 개인정보, 내부 ID가 전부 나간다. 게다가 순환 참조나 지연 로딩 프로퍼티를 건드려 **로깅이 데이터베이스 쿼리를 유발**하는 사고도 난다.
>
> 필요한 필드만 명시적으로 넘겨라.

### 로그 수준 필터링과 그 비용

수준 필터링은 `appsettings.json`에서 **카테고리별로** 설정한다.

```json
{
  "Logging": {
    "LogLevel": {
      "Default": "Information",
      "Microsoft.AspNetCore": "Warning",
      "Microsoft.EntityFrameworkCore.Database.Command": "Warning",
      "MyApp.OrderService": "Debug"
    },
    "Console": {
      "LogLevel": {
        "Default": "Warning"
      }
    }
  }
}
```

규칙은 이렇다.

- 카테고리 이름은 **접두사 매칭**이다. `Microsoft.AspNetCore`는 `Microsoft.AspNetCore.Mvc.Routing`에도 적용된다.
- **가장 긴 접두사가 이긴다.** 위 설정에서 `Microsoft.EntityFrameworkCore.Database.Command`는 `Warning`이고, 다른 EF Core 카테고리는 `Default`인 `Information`이다.
- 공급자별 섹션(`"Console"`)이 전역 섹션보다 우선한다.

> **⚠️ `Microsoft.EntityFrameworkCore.Database.Command`를 `Information`으로 두면 SQL이 전부 찍힌다**
>
> 개발에서는 유용하지만 프로덕션에서는 재앙이다. 쿼리 하나당 로그 한 줄이 나가고, 파라미터 값까지 찍히도록 설정했다면(`EnableSensitiveDataLogging`) **모든 사용자 데이터가 로그에 남는다.**
>
> 이것이 "로그 비용이 애플리케이션 비용보다 큰" 상황을 만드는 가장 흔한 원인이다.

#### `IsEnabled` 게이트

로그 인자를 만드는 데 비용이 들면 게이트를 걸어야 한다.

```csharp
// 인자 계산이 비쌀 때
if (_logger.IsEnabled(LogLevel.Debug))
{
    _logger.LogDebug("캐시 상태: {Snapshot}", BuildExpensiveSnapshot());
}
```

> **📌 대부분의 경우 게이트는 필요 없다**
>
> `LogDebug("값 {X}", x)`처럼 인자가 이미 있는 값이라면 게이트가 오히려 코드를 더럽힌다. 로거 내부에서 어차피 수준 검사를 먼저 한다.
>
> 게이트가 필요한 경우는 셋뿐이다 — (1) 인자 계산이 비쌀 때, (2) 인자가 값 타입이라 **박싱**되는데 호출 빈도가 매우 높을 때(54.6절), (3) `params object?[]` 배열이 매번 할당될 때. 그리고 (2)와 (3)은 75.2절의 소스 생성 로깅이 근본적으로 해결한다.

### 스코프 — 맥락을 붙이는 법

`BeginScope`는 **그 범위 안에서 발생하는 모든 로그에 공통 속성을 붙인다.**

```csharp
public async Task ProcessOrderAsync(int orderId, string correlationId)
{
    using (_logger.BeginScope(new Dictionary<string, object>
    {
        ["OrderId"] = orderId,
        ["CorrelationId"] = correlationId
    }))
    {
        _logger.LogInformation("검증 시작");     // OrderId, CorrelationId 자동 포함
        await ValidateAsync();
        _logger.LogInformation("결제 요청");     // 여기도 포함
        await ChargeAsync();
    }
    _logger.LogInformation("범위 밖");          // 포함 안 됨
}
```

스코프는 중첩되고, 안쪽 스코프가 바깥 스코프의 속성을 상속한다.

> **📌 스코프는 `AsyncLocal<T>`로 구현된다**
>
> 그래서 `await`를 넘어가도 유지되고, `Task.Run`으로 띄운 작업에도 흘러간다(49.9절). 대신 그 대가로 **비동기 흐름마다 컨텍스트 복사 비용**이 붙는다.

> **⚠️ 콘솔 공급자는 스코프를 기본으로 출력하지 않는다**
>
> `BeginScope`를 썼는데 출력에 안 보인다면 공급자 설정 문제다.
>
> ```json
> { "Logging": { "Console": { "IncludeScopes": true } } }
> ```
>
> 구조적 로그 저장소(Seq, Elasticsearch, Application Insights 등)로 보낼 때는 대개 자동으로 필드가 된다.

> **⚠️ 스코프를 상관관계 ID의 유일한 수단으로 삼지 마라**
>
> 요청을 서비스 경계 너머로 따라가려면 스코프로는 부족하다. 그것이 75.4절의 분산 추적이 하는 일이고, `Activity.Current.TraceId`가 있으면 스코프에 상관관계 ID를 수동으로 넣을 필요 자체가 없어진다. **스코프는 프로세스 안에서만 유효한 도구다.**

### 예외 로깅

예외는 **첫 번째 인자**로 넘긴다.

```csharp
catch (DbException ex)
{
    // ✅ 예외 객체를 전용 매개변수로
    _logger.LogError(ex, "주문 {OrderId} 저장 실패", orderId);

    // ❌ 메시지에 문자열로 끼워 넣지 마라
    _logger.LogError("주문 {OrderId} 저장 실패: {Error}", orderId, ex.ToString());
}
```

전용 매개변수로 넘겨야 저장소가 예외를 **별도 필드**로 저장하고, 스택 트레이스 파싱·예외 타입별 그룹핑·내부 예외 전개가 동작한다. 문자열로 끼워 넣으면 전부 사라진다.

> **⚠️ 삼키고 로그만 찍는 것은 대부분 잘못이다**
>
> ```csharp
> catch (Exception ex) { _logger.LogError(ex, "실패"); }   // 그리고 계속 진행
> ```
>
> 이 패턴은 32장에서 다룬 "예외를 삼키는" 문제를 로그로 위장한 것이다. 로그를 찍었다고 해서 실패가 처리된 것이 아니다. **호출자는 성공했다고 믿고 잘못된 데이터로 계속 간다.**
>
> 로그를 찍고 다시 던지려면 `throw;`를 쓴다(`throw ex;`가 아니다 — 32.5절).

> **⚠️ 같은 예외를 계층마다 로그하면 하나의 사고가 다섯 줄이 된다**
>
> 리포지터리에서 찍고, 서비스에서 찍고, 컨트롤러에서 찍고, 전역 핸들러에서 또 찍는다. 그러면 알람 개수가 부풀고 근본 원인이 어디인지 알 수 없다.
>
> 원칙 — **예외를 처리하는 곳에서 한 번만 로그한다.** 다시 던진다면 로그하지 않는다. 맥락을 추가하고 싶다면 로그가 아니라 예외를 감싸라.

## 75.2 소스 생성 로깅 (`[LoggerMessage]`)

### 확장 메서드 로깅의 숨은 비용

`_logger.LogInformation("주문 {OrderId} 금액 {Amount}", orderId, amount)`는 편하지만, 호출마다 다음이 일어난다.

```csharp
// LoggerExtensions의 실제 시그니처
public static void LogInformation(
    this ILogger logger, string? message, params object?[] args);
```

| 비용 | 내용 |
|---|---|
| **`object?[]` 배열 할당** | `params`이므로 인자가 있으면 배열이 매번 만들어진다(63.9절) |
| **값 타입 박싱** | `orderId`(`int`)와 `amount`(`decimal`)가 `object`로 박싱된다(54.6절) |
| **템플릿 파싱** | 메시지 템플릿을 매 호출 파싱한다(캐시가 있지만 조회 비용은 남는다) |
| **수준 검사가 나중** | 배열과 박싱이 **먼저** 일어나고, 로거 안에서 수준을 검사해 버린다 |

마지막 항목이 핵심이다. **`LogDebug`를 껐어도 배열 할당과 박싱은 이미 발생했다.**

핫 패스에서 초당 수만 번 로그를 호출하는 서버라면 이것이 측정 가능한 비용이 된다.

### `[LoggerMessage]` 소스 생성기

.NET 6부터 컴파일 타임에 최적화된 로깅 메서드를 생성해준다.

```csharp
using Microsoft.Extensions.Logging;

public static partial class OrderLog
{
    [LoggerMessage(
        EventId = 1001,
        Level = LogLevel.Information,
        Message = "주문 {orderId} 생성됨. 고객 {customerId}, 금액 {amount}")]
    public static partial void OrderCreated(
        this ILogger logger, int orderId, int customerId, decimal amount);

    [LoggerMessage(
        EventId = 1002,
        Level = LogLevel.Error,
        Message = "주문 {orderId} 저장 실패")]
    public static partial void OrderSaveFailed(
        this ILogger logger, Exception ex, int orderId);
}
```

호출은 이렇게 된다.

```csharp
_logger.OrderCreated(order.Id, customerId, amount);
_logger.OrderSaveFailed(ex, orderId);
```

생성기가 만드는 코드는 대략 이런 모양이다.

```csharp
// 컴파일러가 생성 (개념적 형태)
static readonly Action<ILogger, int, int, decimal, Exception?> __OrderCreatedCallback =
    LoggerMessage.Define<int, int, decimal>(
        LogLevel.Information,
        new EventId(1001, nameof(OrderCreated)),
        "주문 {orderId} 생성됨. 고객 {customerId}, 금액 {amount}",
        new LogDefineOptions { SkipEnabledCheck = true });

public static partial void OrderCreated(
    this ILogger logger, int orderId, int customerId, decimal amount)
{
    if (logger.IsEnabled(LogLevel.Information))   // ← 수준 검사가 맨 앞
    {
        __OrderCreatedCallback(logger, orderId, customerId, amount, null);
    }
}
```

바뀐 것을 정리하면 이렇다.

| | 확장 메서드 | 소스 생성 |
|---|---|---|
| 수준 검사 시점 | 인자 준비 **후** | **맨 처음** |
| `object?[]` 할당 | 매 호출 | **없음** (강타입 제네릭 델리게이트) |
| 값 타입 박싱 | 매 호출 | **없음** |
| 템플릿 파싱 | 런타임 | **컴파일 타임 1회** |
| 자리표시자와 인자 불일치 | 런타임에 조용히 잘못됨 | **컴파일 오류** |
| `EventId` | 지정 안 하면 0 | 명시 강제 가능 |

> **💡 성능보다 큰 이득은 컴파일 타임 검사다**
>
> 할당 제거는 핫 패스에서만 의미가 있다. 그러나 **자리표시자 개수·순서·타입이 컴파일 타임에 검증된다**는 것은 모든 코드에서 이득이다. 75.1절에서 본 "값이 뒤바뀌어 기록되는" 버그가 원천적으로 불가능해진다.
>
> 그리고 `EventId`를 강제하면 로그를 **문자열이 아니라 ID로 알람 걸 수 있다.** 메시지 문구를 고쳐도 알람이 안 깨진다.

### 규칙과 함정

`[LoggerMessage]`가 붙은 메서드는 다음을 지켜야 한다.

| 규칙 | 이유 |
|---|---|
| `partial`이어야 한다 | 생성기가 본문을 채운다 |
| 본문이 없어야 한다 | 위와 같음 |
| 담는 클래스도 `partial` | 위와 같음 |
| `static`이면 첫 인자가 `ILogger` | 확장 메서드 형태 |
| 인스턴스 메서드면 클래스에 `ILogger` 필드 | 생성기가 찾아 쓴다 |
| 반환 타입 `void` | 로깅은 값을 반환하지 않는다 |
| 제네릭 메서드 불가 | 강타입 델리게이트를 만들 수 없다 |

> **⚠️ `Level`을 생략하면 첫 인자가 `LogLevel`이어야 한다**
>
> ```csharp
> [LoggerMessage(EventId = 1003, Message = "상태 변경 {state}")]
> public static partial void StateChanged(
>     this ILogger logger, LogLevel level, string state);   // level이 필수
> ```
>
> 런타임에 수준을 정해야 하는 경우에 쓴다. 둘 다 지정하지 않으면 컴파일 오류다.

> **⚠️ 예외 인자는 이름이 아니라 타입으로 인식된다**
>
> 매개변수 타입이 `Exception`(또는 파생)이면 생성기가 자동으로 예외 슬롯에 넣는다. 이름이 `ex`든 `error`든 상관없다. 반대로 **`Exception`을 자리표시자로도 쓰고 싶다면** 별도 매개변수가 필요하다.

> **⚠️ `SkipEnabledCheck = true`를 함부로 쓰지 마라**
>
> `[LoggerMessage(..., SkipEnabledCheck = true)]`로 `IsEnabled` 검사를 생략할 수 있다. 이미 호출부에서 검사했을 때만 의미가 있고, 그렇지 않으면 **꺼진 로그도 전부 공급자까지 간다.** 기본값(`false`)을 유지하는 것이 옳다.

> **📌 `LoggerMessage.Define`은 여전히 유효하다**
>
> 소스 생성기 이전에는 `LoggerMessage.Define<T1, T2>`를 손으로 써서 같은 효과를 냈다. .NET Standard 2.0을 대상으로 하거나 생성기를 쓸 수 없는 환경에서는 지금도 이 방법이 유효하다. 생성기는 결국 이 API를 호출하는 코드를 만들 뿐이다.

### `EventId` 설계

`EventId`는 정수와 선택적 이름으로 이루어진다. 프로젝트 전체에서 **의미 있게 배분**하면 운영이 편해진다.

```csharp
public static class LogEvents
{
    // 1000번대: 주문
    public const int OrderCreated       = 1001;
    public const int OrderSaveFailed    = 1002;
    public const int OrderCancelled     = 1003;

    // 2000번대: 결제
    public const int PaymentAuthorized  = 2001;
    public const int PaymentDeclined    = 2002;

    // 9000번대: 인프라
    public const int DatabaseUnavailable = 9001;
}
```

> **💡 `EventId`는 알람의 안정적 식별자다**
>
> 메시지 문구는 바뀐다. 번역되고, 오타가 고쳐지고, 필드가 추가된다. 그때마다 알람 규칙이 깨지면 안 된다. **`EventId`로 알람을 걸면 문구를 자유롭게 고칠 수 있다.**
>
> 그리고 번호 대역을 나눠두면 "9000번대가 뜨면 즉시 호출"처럼 **대역 단위 정책**을 세울 수 있다.

## 75.3 메트릭 — `System.Diagnostics.Metrics`, `Meter`, 계측기 종류

### 73장의 성능 카운터에서 무엇이 달라졌나

73.7절에서 `PerformanceCounter`를 봤다. Windows 전용이고, 범주 생성에 관리자 권한이 필요하고, 문자열 기반이고, 차원(dimension)이 없다.

`System.Diagnostics.Metrics`는 ※.NET 6에서 도입된 3세대 API이며, **OpenTelemetry 메트릭 사양에 맞춰 설계되었다.** `Counter<T>`·`Histogram<T>`·`ObservableCounter<T>`·`ObservableGauge<T>`가 .NET 6에 들어왔고, `UpDownCounter<T>`와 `ObservableUpDownCounter<T>`는 ※.NET 7에 추가되었다.

| 세대 | API | 플랫폼 | 차원 지원 | 상태 |
|---|---|---|---|---|
| 1세대 | `PerformanceCounter` | **Windows 전용** | 인스턴스 이름 하나 | 레거시 |
| 2세대 | `EventCounter` | 크로스 플랫폼 | 없음 | 유지되나 신규 권장 아님 |
| 3세대 | `Meter` / `Counter<T>` 등 | 크로스 플랫폼 | **임의 태그** | **권장** |

> **📌 `System.Runtime` 미터 ※.NET 9**
>
> .NET 9부터 런타임 자체가 `System.Runtime` 이름의 `Meter`로 GC·JIT·스레드 풀·예외 지표를 노출한다. 기존 `EventCounter` 이름 체계와 **이름이 다르므로** 대시보드를 그대로 옮길 수 없다. 66.8절에서 본 `dotnet-counters` 이름과도 다르다.

### `Meter` 만들기

`Meter`는 계측기(instrument)를 담는 그릇이다. 보통 **라이브러리/컴포넌트당 하나**를 만든다.

```csharp
using System.Diagnostics.Metrics;

public class OrderMetrics
{
    public const string MeterName = "MyApp.Orders";

    readonly Counter<long> _ordersCreated;
    readonly Counter<long> _ordersFailed;
    readonly Histogram<double> _orderDuration;
    readonly UpDownCounter<long> _ordersInFlight;

    public OrderMetrics(IMeterFactory meterFactory)   // ※.NET 8
    {
        Meter meter = meterFactory.Create(MeterName);

        _ordersCreated = meter.CreateCounter<long>(
            "orders.created",
            unit: "{order}",
            description: "생성된 주문 수");

        _ordersFailed = meter.CreateCounter<long>(
            "orders.failed", unit: "{order}");

        _orderDuration = meter.CreateHistogram<double>(
            "orders.duration",
            unit: "s",
            description: "주문 처리 소요 시간");

        _ordersInFlight = meter.CreateUpDownCounter<long>(
            "orders.in_flight", unit: "{order}");
    }

    public void OrderCreated(string channel) =>
        _ordersCreated.Add(1, new KeyValuePair<string, object?>("channel", channel));

    public void OrderFailed(string channel, string reason) =>
        _ordersFailed.Add(1,
            new KeyValuePair<string, object?>("channel", channel),
            new KeyValuePair<string, object?>("reason", reason));

    public void RecordDuration(double seconds, string channel) =>
        _orderDuration.Record(seconds,
            new KeyValuePair<string, object?>("channel", channel));

    public IDisposable TrackInFlight()
    {
        _ordersInFlight.Add(1);
        return new Decrementer(_ordersInFlight);
    }

    sealed class Decrementer(UpDownCounter<long> counter) : IDisposable
    {
        public void Dispose() => counter.Add(-1);
    }
}
```

> **📌 `IMeterFactory` ※.NET 8을 써라**
>
> `new Meter("MyApp.Orders")`로 직접 만들 수도 있지만, `IMeterFactory`를 쓰면 DI 컨테이너가 수명을 관리하고 **테스트에서 미터를 격리**할 수 있다. 직접 만든 `Meter`는 정적으로 살아남아 테스트 간에 상태가 새는 원인이 된다.
>
> ASP.NET Core에서는 `builder.Services.AddMetrics()`로 등록된다.

### 계측기 6종

| 계측기 | 값의 성격 | 호출 방식 | 예 |
|---|---|---|---|
| `Counter<T>` | **단조 증가**하는 누적값 | `Add(양수)` — 능동 | 처리한 요청 수, 전송 바이트 |
| `UpDownCounter<T>` ※.NET 7 | 증가·감소하는 누적값 | `Add(±)` — 능동 | 진행 중 요청 수, 큐 길이, 활성 커넥션 |
| `Histogram<T>` | **분포**를 재는 개별 측정값 | `Record(값)` — 능동 | 요청 지연, 응답 크기 |
| `ObservableCounter<T>` | 단조 증가 누적값 | 콜백 — **수동(관측 시점에 조회)** | 프로세스 총 CPU 시간 |
| `ObservableUpDownCounter<T>` ※.NET 7 | 증감 누적값 | 콜백 | 힙 크기, 스레드 수 |
| `ObservableGauge<T>` | **현재 순간의 값** (누적 아님) | 콜백 | 온도, 캐시 적중률, 남은 디스크 |

능동(synchronous)과 수동(observable)의 차이가 핵심이다.

- **능동 계측기** — 사건이 일어날 때 코드가 직접 호출한다. 사건 하나도 놓치지 않는다.
- **수동 계측기** — 수집기가 주기적으로 콜백을 부른다. **현재 값만** 알 수 있고 그 사이의 변화는 모른다.

```csharp
// 수동 계측기 — 콜백이 수집 주기마다 호출된다
meter.CreateObservableGauge<long>(
    "process.memory.working_set",
    () => Environment.WorkingSet,
    unit: "By");

meter.CreateObservableUpDownCounter<int>(
    "threadpool.threads",
    () => { ThreadPool.GetAvailableThreads(out int w, out _); return w; });
```

> **⚠️ `ObservableGauge` 콜백에서 무거운 일을 하지 마라**
>
> 콜백은 수집 주기마다(보통 5~60초) 호출되고, **수집 스레드를 블록한다.** 데이터베이스 조회나 락 획득을 넣으면 수집 전체가 지연되거나 교착한다.
>
> 이미 계산되어 있는 값을 읽어 반환하는 것만 하라. 계산이 필요하면 별도 백그라운드 작업이 미리 계산해 필드에 넣어두고, 콜백은 그 필드를 읽는다.

> **⚠️ `Counter<T>`에 음수를 넣으면 안 된다**
>
> `Counter<T>.Add`는 **단조 증가**를 전제로 한다. 음수를 넣으면 예외는 안 나지만 수집기 쪽에서 "카운터가 리셋되었다"고 해석해 rate 계산이 망가진다. 감소가 필요하면 `UpDownCounter<T>`다.

### 태그(차원)와 카디널리티

메트릭의 힘은 **태그로 쪼갤 수 있다**는 데서 온다.

```csharp
_ordersCreated.Add(1,
    new KeyValuePair<string, object?>("channel", "web"),
    new KeyValuePair<string, object?>("region", "kr"));
```

이러면 `orders.created`를 채널별·지역별로 쪼개 볼 수 있다. 그런데 여기에 이 장 전체에서 가장 비싼 함정이 있다.

> **⚠️ 카디널리티 폭발 — 관측 가능성 비용의 1번 원인**
>
> 메트릭 시계열의 개수는 **태그 값 조합의 곱**이다.
>
> | 태그 구성 | 시계열 개수 |
> |---|---|
> | `channel`(3) | 3 |
> | `channel`(3) × `region`(5) | 15 |
> | `channel`(3) × `region`(5) × `status`(6) | 90 |
> | 위 + `customer_id`(100만) | **9천만** |
>
> 마지막 줄이 사고다. 저장소는 시계열마다 메모리를 잡고, 쿼리는 느려지고, 청구서가 폭발한다. 어떤 관리형 저장소는 그냥 거부한다.
>
> **절대 태그로 넣으면 안 되는 것** — 사용자 ID, 주문 ID, 요청 ID, 세션 ID, 원본 URL 경로, 예외 메시지, 타임스탬프.
>
> 그런 것은 **로그나 추적에 넣어라.** 메트릭은 "얼마나 자주, 얼마나 나쁜가"를 저카디널리티로 재고, 개별 사건의 정체는 추적에서 찾는다. 이것이 세 신호를 나누는 이유다.

> **⚠️ URL 경로는 반드시 템플릿으로 정규화하라**
>
> `/orders/4711`을 태그로 쓰면 주문 수만큼 시계열이 생긴다. `/orders/{id}`로 정규화해야 한다. ASP.NET Core의 내장 메트릭은 라우트 템플릿을 쓰므로 안전하지만, **직접 계측할 때는 실수하기 쉽다.**

> **💡 태그 개수가 3개를 넘으면 재검토하라**
>
> 절대 규칙은 아니지만 실무 감각으로 그렇다. 태그가 늘어날수록 조합이 곱으로 늘고, 대시보드에서 실제로 그 축을 쓰는 일은 드물다. **"이 태그로 실제로 필터링하거나 그룹핑할 것인가?"** 에 답할 수 없으면 빼라.

### `MeterListener`로 직접 수집하기

수집기를 붙이지 않고 프로세스 안에서 값을 읽을 수도 있다. 자체 진단 엔드포인트나 테스트에 쓴다.

```csharp
using var listener = new MeterListener();

listener.InstrumentPublished = (instrument, l) =>
{
    if (instrument.Meter.Name == OrderMetrics.MeterName)
        l.EnableMeasurementEvents(instrument);
};

listener.SetMeasurementEventCallback<long>((instrument, measurement, tags, state) =>
{
    Console.Write($"{instrument.Name} = {measurement}");
    foreach (var tag in tags)
        Console.Write($" [{tag.Key}={tag.Value}]");
    Console.WriteLine();
});

listener.Start();

// 수동 계측기 콜백을 강제로 한 번 호출
listener.RecordObservableInstruments();
```

> **⚠️ 타입마다 콜백을 따로 등록해야 한다**
>
> `SetMeasurementEventCallback<T>`는 제네릭이고 **타입별로 따로 등록**된다. `long` 콜백만 등록하고 `Histogram<double>`을 쓰면 그 측정값은 조용히 사라진다. 쓰는 타입 전부(`byte`, `short`, `int`, `long`, `float`, `double`, `decimal`) 등록해야 한다.

### 이름 규칙

OpenTelemetry 사양의 관례를 따르는 것이 좋다.

| 규칙 | 예 |
|---|---|
| 소문자, 점으로 계층 구분 | `http.server.request.duration` |
| 단수형 명사 | `orders.created` (`orders_created_total` 아님) |
| 단위는 `unit` 매개변수로 | `unit: "s"`, `unit: "By"`, `unit: "{request}"` |
| 이름에 단위를 넣지 않는다 | `request.duration` (`request.duration.seconds` 아님) |

> **📌 단위 표기는 UCUM 규약을 쓴다**
>
> `s`(초), `ms`(밀리초), `By`(바이트), `%`(퍼센트), `1`(무차원 비율). 개수처럼 단위가 없는 것은 중괄호로 감싼다 — `{request}`, `{order}`. 중괄호 표기는 **주석 성격**이라 계산에는 쓰이지 않는다.

## 75.4 분산 추적 — `ActivitySource`, `Activity`, 컨텍스트 전파

### 문제 정의

서비스 다섯 개를 거치는 요청이 3초 걸렸다. 어디서 걸렸나?

각 서비스의 로그를 따로 보면 알 수 없다. 로그에 요청 ID가 있어도, 그것이 서비스 경계를 넘어 전파되지 않으면 소용이 없다. **분산 추적(distributed tracing)** 이 푸는 문제가 정확히 이것이다.

```text
클라이언트 요청 (TraceId = 4bf92f...)
│
├─ [API Gateway] ────────────────────────────────── 3,012 ms
│  └─ [OrderService] ──────────────────────────── 2,980 ms
│     ├─ [Auth] ──── 12 ms
│     ├─ [Inventory] ─────── 45 ms
│     └─ [PaymentService] ──────────────────── 2,890 ms  ← 여기다
│        ├─ DB 조회 ── 8 ms
│        └─ 외부 PG 호출 ──────────────────── 2,870 ms  ← 진짜 원인
│
└─ 각 막대 = 스팬(span) = Activity 하나
   전부 같은 TraceId를 공유하고, 부모-자식 관계를 SpanId로 잇는다
```

### 용어

| 용어 | .NET 타입 | 의미 |
|---|---|---|
| 추적(trace) | — | 하나의 요청 전체. `TraceId`로 식별 |
| 스팬(span) | `Activity` | 추적 안의 작업 단위 하나. `SpanId`로 식별 |
| 추적 컨텍스트 | `ActivityContext` | `TraceId` + `SpanId` + 플래그 + 상태 |
| 스팬 생성기 | `ActivitySource` | 스팬을 만드는 이름 있는 공장 |
| 구독자 | `ActivityListener` | 어떤 스팬을 만들지·수집할지 결정 |

> **📌 .NET은 "스팬"을 `Activity`라고 부른다**
>
> OpenTelemetry 용어로 span인 것이 .NET에서는 `Activity`다. `ActivitySource`가 `Tracer`에, `ActivityKind`가 `SpanKind`에 대응한다. .NET의 `Activity`가 OpenTelemetry보다 먼저 있었기 때문에 생긴 이름 차이이고, **OpenTelemetry .NET SDK는 `Activity`를 그대로 쓴다.** 별도 래핑이 없다.

### `ActivitySource` 만들고 쓰기

```csharp
using System.Diagnostics;

public static class Telemetry
{
    public const string ServiceName = "MyApp.Orders";

    // 정적 하나. 어셈블리 버전을 함께 주는 것이 관례
    public static readonly ActivitySource Source =
        new(ServiceName, typeof(Telemetry).Assembly.GetName().Version?.ToString());
}
```

```csharp
public async Task<Order> CreateAsync(int customerId, decimal amount)
{
    using Activity? activity = Telemetry.Source.StartActivity(
        "CreateOrder", ActivityKind.Internal);

    // ⚠️ activity는 null일 수 있다 — 아무도 듣지 않으면 만들어지지 않는다
    activity?.SetTag("customer.id", customerId);
    activity?.SetTag("order.amount", amount);

    try
    {
        var order = await _repository.InsertAsync(customerId, amount);

        activity?.SetTag("order.id", order.Id);
        activity?.SetStatus(ActivityStatusCode.Ok);
        return order;
    }
    catch (Exception ex)
    {
        activity?.SetStatus(ActivityStatusCode.Error, ex.Message);
        activity?.AddEvent(new ActivityEvent("order.failed"));
        throw;
    }
}
```

> **⚠️ `StartActivity`는 `null`을 반환할 수 있다 — 이것이 설계다**
>
> 등록된 `ActivityListener` 중 이 소스를 켠 것이 없으면 `StartActivity`는 **`null`을 반환하고 아무것도 할당하지 않는다.** 계측 코드가 프로덕션에서 꺼져 있을 때 비용이 0에 수렴하도록 만든 설계다.
>
> 그래서 **모든 접근에 `?.`를 붙여야 한다.** `activity.SetTag(...)`라고 쓰면 추적이 꺼진 환경에서 `NullReferenceException`이 난다. 이것이 이 API의 가장 흔한 버그다.
>
> 태그 계산이 비싸다면 아예 감싸라.
>
> ```csharp
> if (activity is not null)
> {
>     activity.SetTag("payload.summary", BuildExpensiveSummary());
> }
> ```

> **⚠️ `using`을 빠뜨리면 부모-자식 관계가 망가진다**
>
> `Activity`는 `Dispose`될 때 종료 시각이 기록되고 `Activity.Current`가 부모로 복원된다. `using`을 빠뜨리면 **이후에 만들어지는 모든 스팬이 이 스팬의 자식이 되어버린다.** 추적 트리가 끝없이 깊어진다.

### `ActivityKind`

스팬이 무엇을 나타내는지 알린다. 수집기와 UI가 이것으로 서비스 맵을 그린다.

| 값 | 의미 | 예 |
|---|---|---|
| `Internal` | 프로세스 내부 작업 (기본값) | 비즈니스 로직 메서드 |
| `Server` | **수신한** 동기 요청 처리 | HTTP 요청 핸들러, gRPC 서비스 |
| `Client` | **송신하는** 동기 요청 | `HttpClient` 호출, DB 쿼리 |
| `Producer` | 비동기 메시지 **발행** | 큐에 메시지 넣기 |
| `Consumer` | 비동기 메시지 **소비** | 큐에서 메시지 꺼내 처리 |

> **⚠️ `Server`/`Client`를 잘못 쓰면 서비스 맵이 뒤집힌다**
>
> 관측 도구는 `Client` 스팬과 그 자식인 `Server` 스팬을 이어 "A가 B를 호출한다"를 그린다. 내부 메서드에 `Server`를 붙이면 존재하지 않는 서비스 경계가 그려지고, 반대로 HTTP 핸들러를 `Internal`로 두면 진입점이 사라진다.
>
> 판단 기준 — **네트워크 경계를 넘는가?** 넘지 않으면 `Internal`이다.

### 태그, 이벤트, 링크

```csharp
// 태그 — 스팬 전체에 대한 속성 (키-값)
activity?.SetTag("db.system", "postgresql");
activity?.SetTag("db.statement", "SELECT ...");   // ⚠️ 아래 경고 참조

// 이벤트 — 스팬 안의 특정 시점에 일어난 일 (타임스탬프 포함)
activity?.AddEvent(new ActivityEvent(
    "cache.miss",
    tags: new ActivityTagsCollection { ["key"] = cacheKey }));

// 상태
activity?.SetStatus(ActivityStatusCode.Error, "결제 게이트웨이 타임아웃");
```

> **⚠️ 추적 태그에도 개인정보를 넣지 마라**
>
> 메트릭보다 카디널리티 제약은 훨씬 느슨하지만(추적은 개별 사건 저장소다), **개인정보 규제는 똑같이 적용된다.** SQL 문을 통째로 태그에 넣으면 파라미터에 개인정보가 딸려간다.
>
> OpenTelemetry 시맨틱 규약도 `db.statement`에 파라미터를 넣지 말라고 권고한다. 파라미터화된 문장만 넣어라.

> **📌 태그 이름은 시맨틱 규약을 따라라**
>
> OpenTelemetry는 흔한 개념에 표준 이름을 정해뒀다 — `http.request.method`, `http.response.status_code`, `server.address`, `db.system`, `error.type`. 표준 이름을 쓰면 도구가 알아보고 전용 UI를 그려준다. 자체 태그는 `myapp.` 같은 접두사로 구분하라.

### 컨텍스트 전파 — W3C Trace Context

서비스 경계를 넘어 `TraceId`가 이어지는 것은 **HTTP 헤더** 덕분이다.

```text
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  │                                │                │
             │  │                                │                └─ 플래그(01=샘플됨)
             │  │                                └─ 부모 SpanId (8바이트)
             │  └─ TraceId (16바이트)
             └─ 버전

tracestate: vendor1=value1,vendor2=value2      (벤더별 추가 정보, 선택)
```

```text
[서비스 A]                              [서비스 B]
Activity 생성                      
TraceId=4bf92f..., SpanId=00f067..
      │
      │ HttpClient 호출
      │  traceparent: 00-4bf92f..-00f067..-01
      ↓                                  ↓
                                   헤더에서 파싱
                                   Activity 생성
                                   TraceId=4bf92f.. (동일!)
                                   ParentSpanId=00f067..
                                   SpanId=b7ad6b71.. (새로 생성)
```

> **📌 `HttpClient`와 ASP.NET Core는 이걸 자동으로 한다**
>
> `HttpClient`가 요청을 보낼 때 `Activity.Current`가 있으면 `traceparent` 헤더를 **자동으로 붙인다.** ASP.NET Core는 들어온 요청의 `traceparent`를 **자동으로 파싱해** 부모 컨텍스트로 삼는다.
>
> 즉 HTTP만 쓴다면 **전파를 위해 아무 코드도 쓸 필요가 없다.** 이것이 `Activity`가 BCL에 있는 이유다.

> **⚠️ 큐·메시지 브로커는 자동이 아니다**
>
> RabbitMQ, Kafka, Azure Service Bus 등으로 넘어갈 때는 **직접 전파해야 한다.** 발행 측에서 컨텍스트를 메시지 헤더에 넣고, 소비 측에서 꺼내 부모로 지정한다.
>
> ```csharp
> // 발행
> var activity = Telemetry.Source.StartActivity("publish", ActivityKind.Producer);
> if (activity is not null)
>     message.Headers["traceparent"] =
>         $"00-{activity.TraceId}-{activity.SpanId}-{(activity.Recorded ? "01" : "00")}";
>
> // 소비
> ActivityContext parent = default;
> if (message.Headers.TryGetValue("traceparent", out var tp))
>     ActivityContext.TryParse(tp, null, out parent);
>
> using var activity = Telemetry.Source.StartActivity(
>     "consume", ActivityKind.Consumer, parent);
> ```
>
> OpenTelemetry SDK를 쓰면 `Propagators.DefaultTextMapPropagator`로 이 코드를 대신할 수 있다.

> **⚠️ .NET Framework와 초기 .NET Core는 W3C 형식이 기본이 아니다**
>
> `Activity.DefaultIdFormat`이 예전에는 계층적 ID(`|abc.1.2.`) 형식이었다. .NET 5부터 W3C가 기본이지만, 레거시와 통신한다면 명시하는 편이 안전하다.
>
> ```csharp
> Activity.DefaultIdFormat = ActivityIdFormat.W3C;
> Activity.ForceDefaultIdFormat = true;
> ```

### `Baggage` — 추적을 따라 흐르는 임의 데이터

배기지(baggage)는 `TraceId`처럼 전파되지만 **애플리케이션이 정의하는** 키-값이다. W3C `baggage` 헤더로 실려 나간다.

API가 두 곳에 있다는 점을 먼저 짚어야 한다. **BCL의 `Activity`**에 `AddBaggage`/`GetBaggageItem`/`Baggage` 멤버가 있고, **OpenTelemetry API 패키지**에는 앰비언트 정적 타입 `OpenTelemetry.Baggage`가 따로 있다. 헤더로의 전파를 실제로 수행하는 것은 OpenTelemetry SDK의 전파기(propagator)다.

```csharp
using System.Diagnostics;

// BCL — 현재 Activity에 붙인다
Activity.Current?.AddBaggage("tenant.id", tenantId);
string? tenant = Activity.Current?.GetBaggageItem("tenant.id");
```

```csharp
using OpenTelemetry;   // OpenTelemetry API 패키지

// OpenTelemetry — Activity가 없어도 앰비언트로 유지된다
Baggage.SetBaggage("tenant.id", tenantId);
string? t2 = Baggage.GetBaggage("tenant.id");
```

> **⚠️ `Baggage`는 신중하게 — 모든 하위 호출의 헤더에 실린다**
>
> 세 가지 문제가 있다.
>
> 1. **크기.** 모든 아웃바운드 요청 헤더에 실려 나간다. 크면 대역폭과 지연에 영향을 준다.
> 2. **보안.** 신뢰하지 않는 서비스로도 나간다. 민감 정보를 넣으면 유출이다.
> 3. **신뢰성.** 외부에서 들어온 baggage는 **공격자가 조작할 수 있다.** 인가 결정에 쓰면 안 된다.
>
> 테넌트 ID나 실험 그룹처럼 작고 민감하지 않은 값에만 써라.

### 샘플링

모든 요청을 추적하면 저장 비용이 감당되지 않는다. `ActivityListener`의 `Sample` 콜백이 결정한다.

```csharp
var listener = new ActivityListener
{
    ShouldListenTo = source => source.Name.StartsWith("MyApp."),

    Sample = (ref ActivityCreationOptions<ActivityContext> options) =>
    {
        // 부모가 이미 샘플됨 → 따라간다 (추적이 끊기지 않게)
        if (options.Parent.TraceFlags.HasFlag(ActivityTraceFlags.Recorded))
            return ActivitySamplingResult.AllDataAndRecorded;

        // 루트 스팬은 10%만
        return Random.Shared.NextDouble() < 0.1
            ? ActivitySamplingResult.AllDataAndRecorded
            : ActivitySamplingResult.None;
    }
};

ActivitySource.AddActivityListener(listener);
```

| `ActivitySamplingResult` | 결과 |
|---|---|
| `None` | `Activity`를 **만들지 않는다**. `StartActivity`가 `null` 반환 |
| `PropagationData` | ID만 있는 `Activity`. 태그 미수집. 전파는 유지 |
| `AllData` | 전부 수집하되 `Recorded` 플래그 없음 |
| `AllDataAndRecorded` | 전부 수집하고 하위 서비스에도 "기록하라"고 전파 |

> **⚠️ 부모 결정을 존중하지 않으면 추적이 조각난다**
>
> 각 서비스가 독립적으로 10% 샘플링하면, 5단계 호출 체인이 완전히 남을 확률은 0.1⁵ = **0.001%** 다. 사실상 완전한 추적을 볼 수 없다.
>
> **루트에서만 결정하고 하위는 부모를 따라가야 한다.** 위 코드의 첫 분기가 그것이다. OpenTelemetry의 `ParentBasedSampler`가 기본으로 이 동작을 한다.

> **💡 오류는 항상 샘플링하고 싶겠지만, 그건 어렵다**
>
> 샘플링 결정은 스팬 **시작 시점**에 내려진다. 그때는 아직 실패할지 모른다. "실패한 것만 저장"하려면 스팬이 끝난 뒤 결정하는 **꼬리 샘플링(tail sampling)** 이 필요하고, 이는 애플리케이션이 아니라 수집기(OpenTelemetry Collector 등)에서 한다.

## 75.5 OpenTelemetry 연동

### 왜 필요한가

지금까지 본 `ILogger`, `Meter`, `ActivitySource`는 **신호를 만드는 API**다. 그것을 **어딘가로 보내는** 것은 별개의 문제다.

OpenTelemetry는 그 "보내는" 부분의 벤더 중립 표준이다. 애플리케이션은 표준 형식(OTLP)으로 내보내고, 백엔드는 무엇이든 바꿔 끼울 수 있다.

```text
  애플리케이션                 SDK                    백엔드
┌──────────────┐      ┌────────────────┐      ┌────────────────┐
│ ILogger      │─────→│                │      │ Prometheus     │
│ Meter        │─────→│ OpenTelemetry  │─OTLP→│ Jaeger / Tempo │
│ ActivitySource│────→│     SDK        │      │ Seq / Loki     │
└──────────────┘      │                │      │ Azure Monitor  │
   BCL / MEL          │ 샘플링·배치·변환 │      │ Datadog ...    │
   (벤더 중립)         └────────────────┘      └────────────────┘
                       (여기만 바꾸면 됨)
```

> **📌 계측 코드는 SDK에 의존하지 않는다**
>
> 이것이 이 설계의 핵심이다. 라이브러리가 `ActivitySource`와 `Meter`로 계측하면, **OpenTelemetry를 쓰든 안 쓰든 상관없다.** SDK를 붙이지 않으면 리스너가 없어 비용이 0이고, 붙이면 자동으로 수집된다.
>
> 그래서 `System.Net.Http`, `Microsoft.EntityFrameworkCore`, `Npgsql`, ASP.NET Core가 이미 계측되어 있고, **당신은 켜기만 하면 된다.**

### 구성

호스트 기반 애플리케이션의 전형적인 구성은 이런 모양이다.

```csharp
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddOpenTelemetry()
    .ConfigureResource(resource => resource
        .AddService(serviceName: "MyApp.Orders", serviceVersion: "1.4.2"))

    .WithTracing(tracing => tracing
        .AddSource(Telemetry.ServiceName)        // 내 ActivitySource
        .AddAspNetCoreInstrumentation()          // 수신 HTTP
        .AddHttpClientInstrumentation()          // 송신 HTTP
        .AddOtlpExporter())

    .WithMetrics(metrics => metrics
        .AddMeter(OrderMetrics.MeterName)        // 내 Meter
        .AddAspNetCoreInstrumentation()
        .AddRuntimeInstrumentation()             // GC·JIT·스레드 풀
        .AddOtlpExporter());

builder.Logging.AddOpenTelemetry(logging =>
{
    logging.IncludeScopes = true;
    logging.AddOtlpExporter();
});
```

> **⚠️ `AddSource`/`AddMeter`를 빠뜨리면 아무것도 안 나온다**
>
> 가장 흔한 "왜 데이터가 안 보이지" 원인이다. `ActivitySource`와 `Meter`는 **명시적으로 등록한 이름만** 수집된다. 이름에 오타가 있어도 오류가 나지 않고 조용히 비어 있다.
>
> 와일드카드를 쓸 수도 있다 — `.AddSource("MyApp.*")`. 다만 의도치 않은 소스까지 켜지 않도록 주의하라.

> **⚠️ 패키지 이름과 API는 버전에 따라 달라진다**
>
> OpenTelemetry .NET은 계측 패키지마다 안정화 시점이 다르고, 프리릴리스 단계에서 API가 바뀐 이력이 있다. 위 코드는 **개념을 보여주는 형태**로 이해하고, **실제 패키지 이름과 확장 메서드는 사용하는 버전의 공식 문서를 확인하라.** 이 책이 특정 버전의 API를 단정하면 그것이 곧 낡은 정보가 된다.

### 리소스 속성

`ConfigureResource`로 지정하는 것은 **이 프로세스가 무엇인가**를 설명하는 속성이다. 모든 신호에 공통으로 붙는다.

| 속성 | 예 | 왜 필요한가 |
|---|---|---|
| `service.name` | `MyApp.Orders` | **필수.** 없으면 `unknown_service` |
| `service.version` | `1.4.2` | 배포 전후 비교 |
| `service.instance.id` | 파드 이름 | 인스턴스별 이상 탐지 |
| `deployment.environment` | `production` | 환경 분리 |

> **💡 `service.version`을 배포 파이프라인에서 주입하라**
>
> 하드코딩하면 잊는다. 릴리스 v1.4.3의 p99가 나빠졌다는 것을 보려면 버전이 신호에 붙어 있어야 한다. `AssemblyInformationalVersion`(52.6절)을 그대로 쓰면 커밋 해시까지 따라온다.

### 수집기(Collector)를 둘 것인가

애플리케이션이 백엔드로 직접 보낼 수도 있고, 중간에 OpenTelemetry Collector를 둘 수도 있다.

| | 직접 전송 | Collector 경유 |
|---|---|---|
| 구성 변경 | **애플리케이션 재배포** | Collector만 재시작 |
| 백엔드 교체 | 애플리케이션 코드 수정 | Collector 설정만 |
| 꼬리 샘플링 | 불가 | **가능** |
| 민감 정보 마스킹 | 애플리케이션에서 | **중앙에서 일괄** |
| 운영 부담 | 없음 | Collector 자체를 운영해야 함 |
| 백엔드 장애 시 | 애플리케이션이 버퍼링 | Collector가 흡수 |

> **💡 서비스가 몇 개를 넘으면 Collector를 둬라**
>
> 서비스 하나짜리 프로젝트에 Collector는 과잉이다. 그러나 서비스가 늘어나면 "샘플링 비율을 바꾸려고 전 서비스를 재배포"하는 상황이 온다. 그 시점이 Collector를 도입할 때다.

## 75.6 상태 점검(health check)과 준비성

### liveness와 readiness는 다른 질문이다

컨테이너 오케스트레이터는 두 가지를 묻는다. **이 둘을 구분하지 않으면 운영 사고가 난다.**

| | Liveness (활성) | Readiness (준비성) |
|---|---|---|
| 질문 | "이 프로세스가 살아 있나?" | "지금 트래픽을 받아도 되나?" |
| 실패 시 조치 | **컨테이너 재시작** | **로드밸런서에서 제외** (재시작 안 함) |
| 의존성 검사 | **포함하면 안 됨** | 포함 |
| 예 | 이벤트 루프가 돌고 있다 | DB 커넥션 확보, 캐시 예열 완료 |

> **⚠️ liveness에 데이터베이스 검사를 넣으면 연쇄 장애가 난다**
>
> 이것이 이 절에서 가장 중요한 경고다.
>
> 데이터베이스가 잠깐 느려진다 → 모든 파드의 liveness가 실패한다 → 오케스트레이터가 **전부 재시작한다** → 재시작한 파드가 동시에 커넥션을 요청한다 → 데이터베이스가 더 죽는다 → 무한 재시작.
>
> DB가 죽었을 때 애플리케이션 프로세스를 재시작해서 좋아지는 것은 없다. **liveness는 "프로세스 자체가 망가졌는가"만 물어야 한다** — 교착, 힙 고갈, 이벤트 루프 정지처럼 재시작이 실제로 해결책인 경우.

### 구현

```csharp
builder.Services.AddHealthChecks()
    .AddCheck("self", () => HealthCheckResult.Healthy(), tags: ["live"])
    .AddCheck<DatabaseHealthCheck>("database", tags: ["ready"])
    .AddCheck<CacheHealthCheck>("cache", tags: ["ready"]);

var app = builder.Build();

app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("live")
});

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("ready")
});
```

사용자 정의 검사는 `IHealthCheck`를 구현한다.

```csharp
public sealed class DatabaseHealthCheck(IDbConnectionFactory factory) : IHealthCheck
{
    public async Task<HealthCheckResult> CheckHealthAsync(
        HealthCheckContext context, CancellationToken cancellationToken = default)
    {
        try
        {
            using var cts = CancellationTokenSource.CreateLinkedTokenSource(cancellationToken);
            cts.CancelAfter(TimeSpan.FromSeconds(2));   // ← 반드시 타임아웃

            await using var conn = await factory.OpenAsync(cts.Token);
            await conn.ExecuteScalarAsync("SELECT 1", cancellationToken: cts.Token);

            return HealthCheckResult.Healthy();
        }
        catch (Exception ex)
        {
            return HealthCheckResult.Unhealthy("데이터베이스 연결 실패", ex);
        }
    }
}
```

`HealthStatus`는 세 값을 가진다.

| 값 | 의미 | 기본 HTTP 상태 |
|---|---|---|
| `Healthy` | 정상 | 200 |
| `Degraded` | 동작하지만 성능·기능이 저하됨 | 200 |
| `Unhealthy` | 동작 불가 | 503 |

> **⚠️ 상태 점검에 반드시 타임아웃을 걸어라**
>
> 검사가 응답하지 않으면 상태 점검 엔드포인트 자체가 멈추고, 오케스트레이터는 타임아웃으로 간주해 파드를 죽인다. **검사 내부의 지연이 곧 파드의 죽음이 된다.**
>
> 위 코드처럼 `CancelAfter`로 자체 타임아웃을 걸고, 프로브의 `timeoutSeconds`보다 짧게 잡아라.

> **⚠️ `Degraded`가 200을 반환한다는 것을 기억하라**
>
> `Degraded`를 반환했는데 파드가 트래픽에서 빠지길 기대했다면 실망한다. 기본 매핑은 200이다. 바꾸려면 명시해야 한다.
>
> ```csharp
> new HealthCheckOptions
> {
>     ResultStatusCodes =
>     {
>         [HealthStatus.Healthy]   = StatusCodes.Status200OK,
>         [HealthStatus.Degraded]  = StatusCodes.Status503ServiceUnavailable,
>         [HealthStatus.Unhealthy] = StatusCodes.Status503ServiceUnavailable
>     }
> }
> ```

> **⚠️ 상태 점검 엔드포인트를 인터넷에 노출하지 마라**
>
> 상세 응답에는 내부 컴포넌트 이름, 예외 메시지, 때로는 연결 문자열 조각이 들어간다. 공격자에게 내부 구조 지도를 주는 셈이다.
>
> 별도 포트에 바인딩하거나, 인증을 걸거나, 최소한 상세 응답을 끄고 상태 코드만 반환하라.

> **💡 시작 프로브(startup probe)를 잊지 마라**
>
> 시작이 느린 애플리케이션(EF Core 마이그레이션, 캐시 예열, JIT 워밍업 — 72.7절)은 liveness 프로브가 먼저 발동해 무한 재시작에 빠질 수 있다. 오케스트레이터의 **startup probe**를 써서 "시작이 끝날 때까지 liveness를 미루는" 구성이 필요하다.

## 75.7 무엇을 계측할 것인가 — 신호 설계

도구는 다 봤다. 남은 질문은 **무엇을 잴 것인가**다. 이것이 실제로 어려운 부분이다.

### RED — 요청 기반 서비스

사용자 요청을 처리하는 서비스라면 세 가지를 재라.

| | 지표 | .NET 계측기 |
|---|---|---|
| **R**ate | 초당 요청 수 | `Counter<long>` |
| **E**rrors | 실패한 요청 수(또는 비율) | 같은 `Counter`에 `error.type` 태그 |
| **D**uration | 요청 처리 시간 **분포** | `Histogram<double>` |

```csharp
_requestCount.Add(1,
    new("http.route", route),
    new("http.response.status_code", statusCode));

_requestDuration.Record(elapsed.TotalSeconds,
    new("http.route", route));
```

> **💡 오류를 별도 카운터로 만들지 말고 태그로 쪼개라**
>
> `requests.total`과 `requests.failed`를 따로 두면 "실패율"을 구하려고 두 시계열을 나눠야 하고, 두 카운터의 태그가 어긋나면 계산이 틀린다.
>
> **하나의 카운터에 `status` 태그**를 붙이면 합계도 실패율도 같은 시계열에서 나온다.

### USE — 리소스

리소스(CPU, 메모리, 커넥션 풀, 스레드 풀)라면 다른 세 가지를 재라.

| | 지표 | 예 |
|---|---|---|
| **U**tilization | 사용 중인 비율 | 커넥션 풀 사용률, CPU 사용률 |
| **S**aturation | 대기열 길이 | 스레드 풀 대기 작업, 커넥션 대기 시간 |
| **E**rrors | 리소스 오류 | 커넥션 획득 실패, `OutOfMemoryException` |

> **💡 포화도(saturation)가 가장 먼저 움직인다**
>
> 사용률이 100%에 닿기 **전에** 대기열이 자라기 시작한다. 그래서 포화도가 조기 경보 신호다.
>
> .NET에서 대표적인 것이 **스레드 풀 큐 길이**다. `ThreadPool.PendingWorkItemCount`(※.NET Core 3.0)가 계속 증가하면 sync-over-async나 스레드 풀 기아를 의심해야 한다(47.14절).

### 히스토그램과 백분위

지연 시간은 **평균으로 보면 안 된다.** 67.1절에서 본 이유가 여기서도 그대로다.

```text
1000개 요청의 지연 분포

  개수
   │
   │ ████
   │ ████
   │ ████                                    ▌  ← p99: 2,400 ms
   │ ████▄▄▄                                 ▌
   └─┴────┴────┴────┴────┴────┴────┴────┴────┴──→ 지연
     10   50   100  ...                    2400

  평균 = 68 ms   ← "괜찮네"
  p50  = 42 ms
  p95  = 180 ms
  p99  = 2,400 ms  ← 100명 중 1명은 2.4초를 기다린다
```

> **⚠️ 백분위는 평균낼 수 없다**
>
> 인스턴스 세 대의 p99가 각각 100ms, 200ms, 300ms일 때 전체 p99는 200ms가 **아니다.** 백분위의 평균은 수학적으로 의미가 없다.
>
> 올바른 방법은 **히스토그램 버킷을 합산한 뒤 백분위를 계산**하는 것이다. 그래서 `Histogram<T>`가 값 하나가 아니라 분포를 보내는 것이고, 수집 백엔드가 버킷 단위로 집계하는 것이다.

### 카디널리티 예산

75.3절의 경고를 설계 원칙으로 바꾸면 이렇다.

| 신호 | 카디널리티 | 개별 식별자 | 보존 |
|---|---|---|---|
| 메트릭 | **낮게 유지** (수백~수천 시계열) | **금지** | 길게 (수개월) |

> **💡 "이 태그로 알람을 걸거나 그래프를 쪼갤 것인가?"**
>
> 메트릭 태그를 추가하기 전에 이 질문에 답하라. 답이 "아니오"거나 "혹시 몰라서"라면 빼고, 대신 **추적 태그나 로그 필드로** 넣어라. 거기서는 비용이 훨씬 싸다.

### 계측 오버헤드

| 신호 | 꺼져 있을 때 | 켜져 있을 때 |
|---|---|---|

>

>

### 시작 지점 — 실용적 체크리스트

전부 한 번에 할 필요는 없다. 순서가 있다.

| 단계 | 무엇을 | 왜 이 순서인가 |
|---|---|---|
| 1 | **구조적 로그 + 상관관계 ID** | 이것 없이는 아무것도 조사할 수 없다 |
| 2 | **RED 메트릭 3종** | 문제가 있는지 없는지를 알려준다 |
| 3 | **분산 추적 (샘플링)** | 문제가 어디인지 좁혀준다 |
| 4 | **상태 점검** | 오케스트레이터가 올바르게 동작하게 한다 |
| 5 | **런타임 메트릭** (GC, 스레드 풀) | 65·66장의 진단과 연결된다 |
| 6 | 비즈니스 메트릭 | 기술 지표가 안정된 다음 |

>
> 66장의 메모리 진단이 "덤프를 뜰 수 있을 때"의 이야기라면, 이 장은 **"덤프를 뜰 수 없을 때"** 를 위한 준비다. 준비는 사고 전에만 할 수 있다.

## 이 장의 요약

- **관측 가능성은 로그 양이 아니라 상관관계다.** 신호가 `TraceId`로 이어지지 않으면 세 기둥은 고립된 세 도구일 뿐이다.
- **구조적 로그를 써라.** 문자열 보간이 아니라 메시지 템플릿 — 검색 가능해지고, 그룹핑되고, 비활성 수준에서 문자열이 만들어지지 않는다.
- **`[LoggerMessage]` 소스 생성 로깅**은 배열 할당과 박싱을 없애지만, 더 큰 이득은 **자리표시자 불일치를 컴파일 타임에 잡는 것**이다.
- **메트릭은 저카디널리티**로. 사용자 ID·요청 ID를 태그로 넣는 순간 시계열이 폭발하고 비용이 감당되지 않는다. 개별 식별자는 추적과 로그에 넣어라.
- **`StartActivity`는 `null`을 반환할 수 있다.** 그것이 "꺼져 있을 때 비용 0" 설계이고, 그래서 모든 접근에 `?.`가 필요하다.
- **HTTP 컨텍스트 전파는 자동, 메시지 큐는 수동.** `traceparent` 헤더를 직접 넣고 꺼내야 한다.
- **샘플링은 루트에서 결정하고 하위는 부모를 따른다.** 각자 결정하면 5단계 체인의 완전한 추적을 볼 확률이 0.001%가 된다.
- **`ActivitySource`와 `Meter`는 BCL에 있다.** 라이브러리가 외부 의존성 없이 계측할 수 있게 한 설계이고, 그래서 BCL과 ASP.NET Core가 이미 계측되어 있다.
- **liveness에 의존성 검사를 넣지 마라.** DB가 느려지면 모든 파드가 재시작해 연쇄 장애가 된다.
- **RED(요청)와 USE(리소스)** 로 시작하고, 백분위는 히스토그램 버킷을 합산해 계산하라 — 백분위의 평균은 의미가 없다.

7. liveness 검사에 데이터베이스 조회를 넣은 버전과 넣지 않은 버전을 만들고, DB를 중지시켰을 때 각각 어떤 일이 벌어지는지 관찰하라(로컬 컨테이너로 충분하다).
8. `Histogram<double>`로 지연을 기록하는 코드를 작성하고, 인스턴스 3개의 p99를 각각 구한 뒤 "p99의 평균"과 "전체 데이터의 p99"를 비교해 얼마나 다른지 확인하라.
