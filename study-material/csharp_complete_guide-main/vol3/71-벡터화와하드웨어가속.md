# 71장. 벡터화와 하드웨어 가속

> **이 장의 위치** — Part XII「고성능 C#」의 다섯 번째 장이다. 70장까지는 "데이터를 어떤 모양으로 놓을 것인가"였다. 이 장은 그 데이터를 **한 번에 몇 개씩 처리할 것인가**를 다룬다. 지금까지 본 모든 루프는 원소를 하나씩 만졌다. CPU에는 원소 8개, 16개, 64개를 명령 하나로 처리하는 실행 유닛이 따로 달려 있고, .NET은 그것을 `System.Numerics.Vector<T>`와 `System.Runtime.Intrinsics`로 노출한다. 70장의 SoA 레이아웃이 여기서 값을 한다 — 같은 필드가 연속으로 늘어서 있어야 벡터 하나에 통째로 실린다.
>
> **선수 지식** — 55장(JIT 컴파일과 코드 생성), 61장(메모리의 기초), 67장(측정 없이 최적화 없다), 68장(`Span<T>`와 `Memory<T>`), 70장(데이터 지향 설계)
>
> **이 장에서 다루지 않는 것** — 멀티코어 병렬화(`Parallel`, PLINQ)는 50장에서, 캐시 계층과 비일시적 접근의 하드웨어 배경은 61.4~61.6절에서, `SearchValues<T>`의 내부 선택 로직은 69.6절에서 이미 다뤘다. GPU 오프로딩과 `System.Numerics.Tensors`의 텐서 API 전반은 이 책의 범위 밖이다.

---

**시작하기 전에 한 가지 경고.** 이 장의 기법은 이 책에서 **가장 좁은 적용 범위**를 가진다. 67장의 측정이 "이 루프가 전체 시간의 40%를 먹는다"고 말해주기 전까지, 이 장의 어떤 코드도 쓸 이유가 없다. 벡터화는 코드를 서너 배 길게 만들고, 읽기 어렵게 만들고, 플랫폼별 분기를 도입하고, 잘못 쓰면 스칼라 코드보다 느려진다. 71.6절은 그 손해 목록에 통째로 할애했다. 먼저 읽어도 좋다.

그럼에도 이 장이 필요한 이유는, 어떤 코드에서는 벡터화가 **다른 어떤 최적화로도 얻을 수 없는 배수**를 주기 때문이다. 알고리즘 개선도 캐시 튜닝도 이미 끝났고 여전히 루프가 병목일 때, 남은 카드는 이것 하나다.

## 71.1 `Vector<T>`와 `Vector128` / `Vector256` / `Vector512`

### SIMD란 무엇인가

**SIMD(Single Instruction, Multiple Data)** 는 명령 하나로 여러 데이터에 같은 연산을 적용하는 실행 방식이다. 이름 그대로 "명령 하나, 데이터 여럿"이다.

일반적인 스칼라 덧셈은 이렇게 동작한다.

```text
스칼라 루프 — int 8개를 더하려면 명령 8개

  a[0] + b[0] → c[0]      add
  a[1] + b[1] → c[1]      add
  a[2] + b[2] → c[2]      add
  a[3] + b[3] → c[3]      add
  a[4] + b[4] → c[4]      add
  a[5] + b[5] → c[5]      add
  a[6] + b[6] → c[6]      add
  a[7] + b[7] → c[7]      add
                          ────
                          8 회
```

SIMD 덧셈은 이렇게 동작한다.

```text
벡터 루프 — 같은 일을 명령 1개로

        ┌────┬────┬────┬────┬────┬────┬────┬────┐
   a →  │a[0]│a[1]│a[2]│a[3]│a[4]│a[5]│a[6]│a[7]│   256비트 레지스터 (YMM)
        └────┴────┴────┴────┴────┴────┴────┴────┘
           +    +    +    +    +    +    +    +
        ┌────┬────┬────┬────┬────┬────┬────┬────┐
   b →  │b[0]│b[1]│b[2]│b[3]│b[4]│b[5]│b[6]│b[7]│
        └────┴────┴────┴────┴────┴────┴────┴────┘
           ↓    ↓    ↓    ↓    ↓    ↓    ↓    ↓
        ┌────┬────┬────┬────┬────┬────┬────┬────┐
   c →  │c[0]│c[1]│c[2]│c[3]│c[4]│c[5]│c[6]│c[7]│   vpaddd  ← 명령 1개
        └────┴────┴────┴────┴────┴────┴────┴────┘
```

CPU 안에는 범용 레지스터(`rax`, `rbx` 등)와 별개로 **넓은 벡터 레지스터**가 따로 있다. x86-64에서는 SSE의 128비트 `xmm0~xmm15`, AVX의 256비트 `ymm0~ymm15`, AVX-512의 512비트 `zmm0~zmm31`이다. ARM64에서는 NEON의 128비트 `v0~v31`이다. 이 레지스터 하나에 같은 타입의 값을 여러 개 채워 넣고, 전용 실행 유닛이 그것을 한 사이클에 처리한다.

### 벡터 폭과 동시 처리 개수

레지스터 폭을 원소 크기로 나눈 것이 **한 번에 처리되는 개수(lane 수)** 다.

| 타입 | 크기 | SSE/NEON (128비트) | AVX2 (256비트) | AVX-512 (512비트) |
|---|---|---|---|---|
| `byte` / `sbyte` | 1바이트 | 16개 | 32개 | 64개 |
| `short` / `ushort` | 2바이트 | 8개 | 16개 | 32개 |
| `int` / `uint` / `float` | 4바이트 | 4개 | 8개 | 16개 |
| `long` / `ulong` / `double` | 8바이트 | 2개 | 4개 | 8개 |

이 표가 곧 **이론상 최대 배수**다. AVX2에서 `int` 배열을 더하면 이론상 8배, `byte` 배열을 훑으면 이론상 32배다.

> **⚠️ 표의 배수는 상한이지 예측값이 아니다**
>
> "AVX2로 `int` 8개를 동시에 → 8배 빨라진다"는 명령 개수만 세었을 때의 이야기다. 실측은 거의 언제나 그보다 낮게 나오며, 그 이유는 대체로 **메모리 대역폭**이다. 배열 합계처럼 원소당 연산이 덧셈 하나뿐인 루프는 스칼라 코드에서도 이미 메모리를 기다리며 놀고 있다. 계산을 8배 빠르게 해도 데이터가 8배 빨리 도착하지 않으면 아무 일도 일어나지 않는다.
>
> 이 장의 어떤 수치도 "당신의 하드웨어에서 이만큼 나온다"는 뜻이 아니다. **67장의 방법으로 직접 재라.** 특히 배열 길이를 바꿔가며 재라 — 배열이 L1/L2/L3/DRAM 어디에 있느냐에 따라 배수가 통째로 달라진다.

### 두 갈래의 API

.NET은 SIMD를 **두 가지 계층**으로 노출한다. 이 장 전체가 사실상 이 둘의 선택 문제다.

```text
                     ┌─────────────────────────────────────┐
                     │  BCL이 이미 벡터화한 API (71.5절)   │  ← 0순위
                     │  string.IndexOf, SequenceEqual,     │
                     │  SearchValues<T>, TensorPrimitives  │
                     └─────────────────────────────────────┘
                                     ↓ 없으면
                     ┌─────────────────────────────────────┐
                     │  System.Numerics.Vector<T>          │  ← 1순위
                     │  가변 폭. 한 벌만 쓰면 모든 CPU     │
                     └─────────────────────────────────────┘
                                     ↓ 부족하면
                     ┌─────────────────────────────────────┐
                     │  Vector128/256/512<T>               │  ← 2순위
                     │  고정 폭 + 크로스 플랫폼 연산       │
                     └─────────────────────────────────────┘
                                     ↓ 그래도 부족하면
                     ┌─────────────────────────────────────┐
                     │  Sse2 / Avx2 / AdvSimd ... (71.2절) │  ← 최후
                     │  CPU 명령 1:1 대응                  │
                     └─────────────────────────────────────┘
```

아래로 내려갈수록 성능 상한은 올라가고, 코드량·플랫폼 분기·유지보수 비용도 함께 올라간다.

### `Vector<T>` — 폭이 런타임에 정해지는 벡터

`System.Numerics.Vector<T>`는 **크기가 컴파일 타임에 정해지지 않는** 값 타입이다. JIT이 실행 중인 CPU를 보고 결정한다.

```csharp
using System.Numerics;

Console.WriteLine(Vector.IsHardwareAccelerated);   // 예: True
Console.WriteLine(Vector<byte>.Count);             // AVX2 머신이면 32
Console.WriteLine(Vector<int>.Count);              // AVX2 머신이면 8
Console.WriteLine(Vector<double>.Count);           // AVX2 머신이면 4
```

기본 사용법은 배열이나 스팬에서 벡터를 만들고, 산술 연산자를 그대로 쓰고, 다시 써넣는 것이다.

```csharp
using System.Numerics;

// a[i] = a[i] * 2 + b[i] 를 벡터로
static void FusedScale(float[] a, float[] b)
{
    int step = Vector<float>.Count;
    int i = 0;

    var two = new Vector<float>(2.0f);

    for (; i <= a.Length - step; i += step)
    {
        var va = new Vector<float>(a, i);
        var vb = new Vector<float>(b, i);
        var vr = va * two + vb;      // 연산자 오버로드가 SIMD 명령으로 간다
        vr.CopyTo(a, i);
    }

    for (; i < a.Length; i++)        // 잔여 처리
        a[i] = a[i] * 2.0f + b[i];
}
```

여기서 눈여겨볼 것이 세 가지다.

1. **`Vector<float>.Count`가 상수가 아니다.** 소스에는 프로퍼티 접근으로 보이지만 JIT이 상수로 접어버린다(55.6절). 그래서 `i += step`은 `i += 8` 같은 즉시값 덧셈이 된다.
2. **연산자가 명령이 된다.** `va * two + vb`는 메서드 호출 세 번처럼 보이지만 JIT은 이것을 `vmulps` + `vaddps` 두 명령으로 만든다. `Vector<T>`의 모든 연산은 **JIT 내장 함수(intrinsic)** 다.
3. **잔여 루프가 반드시 있어야 한다.** 배열 길이가 `Count`의 배수라는 보장이 없다.

> **📌 `Vector<T>`의 역사**
>
> `System.Numerics.Vector<T>`는 .NET Framework 4.6과 함께 `System.Numerics.Vectors` NuGet 패키지로 처음 나왔다. 당시에는 **RyuJIT이 활성화된 64비트 프로세스**에서만 가속되었고, 그 외에는 소프트웨어 폴백으로 동작했다 — 즉 느렸다.
>
> 실용적인 물건이 된 것은 **.NET Core 3.0**부터다. 이때 하드웨어 내장 함수 기반 구현이 들어가면서 BCL 자신이 `Vector<T>`를 쓰기 시작했다. ※.NET 7에서 `Load`/`Store` 계열 정적 메서드가 추가되어 배열이 아닌 임의의 `ref T`에서 직접 로드할 수 있게 되었고, 이것이 지금 쓰는 표준 형태다.

`Vector<T>`가 지원하는 `T`는 원시 수치 타입으로 한정된다.

| 지원 | `sbyte` `byte` `short` `ushort` `int` `uint` `long` `ulong` `nint` `nuint` `float` `double` |
|---|---|
| **미지원** | `bool` `char` `decimal` `Half` 사용자 정의 구조체, 참조 타입 |

지원 여부는 `Vector<T>.IsSupported` ※.NET 8로 확인할 수 있고, 지원하지 않는 `T`로 인스턴스를 만들려 하면 런타임에 실패한다. 제네릭 코드에서 `Vector<T>`를 쓸 때는 이 프로퍼티로 먼저 걸러야 한다.

> **⚠️ `char`는 지원되지 않는다 — `ushort`로 재해석하라**
>
> 문자열을 벡터로 다루려는 시도가 `Vector<char>`에서 막힌다. `char`는 `Vector<T>`의 지원 타입이 아니다. 해법은 `MemoryMarshal.Cast<char, ushort>(span)`으로 스팬 자체를 `ushort` 스팬으로 재해석하는 것이다. `char`와 `ushort`는 메모리 표현이 동일하므로 복사도 변환도 일어나지 않는다.
>
> ```csharp
> ReadOnlySpan<char> text = "hello";
> ReadOnlySpan<ushort> raw = MemoryMarshal.Cast<char, ushort>(text);
> ```
>
> 고정 폭 API에서는 `Vector128<ushort>`를 쓰면 되고, 필요하면 `AsUInt16()` / `AsInt16()` 같은 재해석 확장 메서드로 lane 타입만 바꿀 수 있다. 재해석은 비트를 그대로 두고 타입만 바꾸는 무비용 연산이다.

### `Vector128<T>` / `Vector256<T>` / `Vector512<T>` — 고정 폭 벡터

`System.Runtime.Intrinsics` 네임스페이스의 `Vector128<T>`, `Vector256<T>`, `Vector512<T>`는 이름 그대로 **폭이 고정**된 벡터다. `Vector64<T>`도 있다(ARM NEON의 D 레지스터에 대응).

이 타입들 자체는 .NET Core 3.0부터 있었지만, 그때는 하드웨어 내장 함수에 넘기는 **불투명한 상자**에 가까웠다. 연산을 하려면 `Sse2.Add(...)` 같은 플랫폼 전용 클래스를 거쳐야 했다.

**※.NET 7에서 이 상황이 정리됐다.** `Vector128`, `Vector256` 정적 클래스 자체는 .NET Core 3.0부터 `Create`·`AsByte` 같은 생성·재해석 메서드를 갖고 있었지만, .NET 7에서 **플랫폼을 가리지 않는 연산 집합**(산술 연산자, `Add`·`Sum`·`Equals`·`Shuffle`·`LoadUnsafe`·`ExtractMostSignificantBits` 등)이 통째로 들어왔다.

```csharp
using System.Runtime.Intrinsics;

var a = Vector128.Create(1, 2, 3, 4);          // Vector128<int>
var b = Vector128.Create(10);                   // 모든 lane이 10
var c = a + b;                                  // Vector128.Add와 동일
int total = Vector128.Sum(c);                   // 46 — 수평 합
```

이 코드에는 `Sse2`도 `AdvSimd`도 나오지 않는다. JIT이 x64에서는 `paddd`로, ARM64에서는 `add v0.4s`로 각각 번역한다. **고정 폭이면서 플랫폼 독립적**이라는 것이 .NET 7이 만든 새로운 지점이다.

**※.NET 8에서 `Vector512<T>`가 추가됐다.** AVX-512를 가진 CPU에서 512비트 레지스터를 직접 쓸 수 있다.

```csharp
Console.WriteLine(Vector128.IsHardwareAccelerated);  // 거의 모든 현대 CPU에서 True
Console.WriteLine(Vector256.IsHardwareAccelerated);  // AVX2 있으면 True
Console.WriteLine(Vector512.IsHardwareAccelerated);  // AVX-512 있으면 True
```

> **⚠️ `Vector512.IsHardwareAccelerated`가 `true`여도 `Vector<T>`는 512비트가 되지 않는다**
>
> ※.NET 8 기준으로, AVX-512를 지원하는 머신에서도 `Vector<T>`의 폭은 기본적으로 **256비트에 머무른다.** `Vector<int>.Count`는 16이 아니라 8이다.
>
> 이유는 안정성이다. 일부 인텔 세대에서 512비트 명령을 많이 쓰면 코어 주파수가 내려가는 현상이 있었고, 512비트가 항상 이득이라고 단정할 수 없다. 그래서 런타임은 보수적인 기본값을 택했다.
>
> 이 기본값은 `DOTNET_PreferredVectorBitWidth=512` 환경 변수로 바꿀 수 있지만, **켜기 전에 반드시 측정하라.** 이것은 진단·실험용 노브이고, 제품 환경에서 켤 이유가 있다면 그 근거는 벤치마크여야 한다.

### 둘 중 무엇을 쓸 것인가

| 판단 기준 | `Vector<T>` | `Vector128/256/512<T>` |
|---|---|---|
| 폭 | 런타임 결정 (플랫폼별로 다름) | 컴파일 타임 고정 |
| 코드 벌수 | **한 벌** | 폭마다 한 벌 (또는 제네릭 헬퍼) |
| CPU 활용도 | JIT이 고른 폭까지만 | **가능한 최대 폭까지** |
| lane 위치를 아는가 | 모른다 — `Count`가 가변 | **안다** — 셔플·마스크·상수 테이블 가능 |
| ReadyToRun 사전 컴파일 | **불가** (크기가 가변이라 crossgen2가 건너뜀, 55.7절) | 가능 |
| 폴백 코드 | `Vector.IsHardwareAccelerated` 하나 | 폭마다 분기 필요 |
| 적합한 작업 | 원소별 산술, 단순 누적·비교 | 셔플, 마스크 추출, 테이블 조회, 비대칭 알고리즘 |
| 읽기 난이도 | 낮음 | 중간~높음 |

실무 규칙은 단순하다.

- **원소별로 같은 산술만 반복한다면 `Vector<T>`.** 합계, 스케일링, 원소별 비교, 최댓값 — 코드 한 벌로 끝나고 미래의 더 넓은 CPU도 자동으로 활용한다.
- **lane 사이를 넘나드는 조작이 필요하면 고정 폭.** 셔플(`Shuffle`), 마스크를 비트로 추출(`ExtractMostSignificantBits`), 상수 룩업 테이블, 인접 lane 결합 — 이런 것은 폭을 알아야 쓸 수 있다.
- **BCL 수준의 최고 성능이 필요하고 유지보수 인력이 있다면** 고정 폭으로 512/256/128 세 경로를 쓴다. `System.Private.CoreLib`이 실제로 이렇게 되어 있다.

> **💡 `Vector<T>`로 시작하고, 측정이 요구할 때만 내려가라**
>
> 벡터화의 이득 대부분은 "스칼라 → SIMD"라는 첫 단계에서 나온다. `Vector<T>`로 얻는 것이 6배인데 고정 폭 손코딩으로 7배가 된다면, 그 1배 차이에 코드 세 벌과 플랫폼 분기를 지불할 가치가 있는지는 별개의 판단이다.
>
> 반대의 경우도 있다. `Vector<T>`로는 애초에 표현할 수 없는 알고리즘(셔플 기반 파싱, 비트마스크 조기 탈출)이라면 처음부터 고정 폭으로 가는 것이 맞다. 71.3절의 `IndexOf` 예제가 그 경계선에 있다.

### 컴파일 결과 — IL에는 아무것도 없다

`Vector<T>` 연산이 IL에서 어떻게 보이는지 확인해두면 이후 논의가 편하다.

```csharp
static Vector<int> AddTwo(Vector<int> a, Vector<int> b) => a + b;
```

IL은 평범한 정적 메서드 호출이다.

```il
.method private hidebysig static valuetype [System.Runtime]System.Numerics.Vector`1<int32>
        AddTwo(valuetype [System.Runtime]System.Numerics.Vector`1<int32> a,
               valuetype [System.Runtime]System.Numerics.Vector`1<int32> b) cil managed
{
  .maxstack  8
  IL_0000:  ldarg.0
  IL_0001:  ldarg.1
  IL_0002:  call       valuetype [System.Runtime]System.Numerics.Vector`1<!0>
                       valuetype [System.Runtime]System.Numerics.Vector`1<int32>::op_Addition(
                           valuetype [System.Runtime]System.Numerics.Vector`1<!0>,
                           valuetype [System.Runtime]System.Numerics.Vector`1<!0>)
  IL_0007:  ret
}
```

**IL 수준에는 SIMD가 없다.** `op_Addition` 호출 하나뿐이다. C# 컴파일러는 `Vector<T>`를 특별 취급하지 않는다.

마법은 전부 JIT에서 일어난다. JIT은 `System.Numerics.Vector`1::op_Addition`이라는 시그니처를 **내장 함수로 인식**하고, 호출을 생성하는 대신 대상 CPU의 벡터 덧셈 명령을 직접 뿜는다. 55장에서 본 `Math.Abs`나 `Unsafe.Add`와 같은 메커니즘이다.

이 사실에서 두 가지 실무적 귀결이 나온다.

- **인터프리터나 내장 함수를 끈 환경에서는 소프트웨어 폴백이 돈다.** `Vector<T>`는 여전히 **동작은 한다.** 다만 lane마다 루프를 도는 관리 코드로 떨어지고, 스칼라 코드보다 느리다. `Vector.IsHardwareAccelerated`가 `false`일 때 벡터 경로를 타면 안 되는 이유다.
- **`Vector<T>`를 쓰는 메서드는 ReadyToRun 이미지에 들어가지 않는다.** 벡터 크기가 실행 시점에야 정해지므로 crossgen2가 사전 컴파일을 포기한다(55.7절의 R2R 체크리스트 3번). 시작 시간이 중요한 애플리케이션에서 SIMD 코드가 많으면 R2R 커버리지가 눈에 띄게 낮아진다. 고정 폭 API에는 이 문제가 없다.

### 주요 연산 대응표

`Vector<T>`와 고정 폭 API의 연산 이름은 대체로 대응한다. 자주 쓰는 것만 정리한다.

| 하는 일 | `Vector<T>` | `Vector128/256/512<T>` |
|---|---|---|
| 모든 lane을 같은 값으로 | `new Vector<T>(value)` | `Vector128.Create(value)` |
| 메모리에서 로드 (`ref` 기준) | `Vector.LoadUnsafe(ref x, offset)` | `Vector128.LoadUnsafe(ref x, offset)` |
| 메모리로 저장 | `v.StoreUnsafe(ref y, offset)` | `v.StoreUnsafe(ref y, offset)` |
| 원소별 사칙연산 | `+` `-` `*` `/` | `+` `-` `*` `/` |
| 원소별 비교 (마스크 반환) | `Vector.Equals`, `Vector.GreaterThan`, `Vector.LessThan` | `Vector128.Equals`, `Vector128.GreaterThan`, ... |
| 하나라도 일치하는가 | `Vector.EqualsAny` | `Vector128.EqualsAny` |
| 전부 일치하는가 | `Vector.EqualsAll` | `Vector128.EqualsAll` |
| 마스크로 선택 | `Vector.ConditionalSelect` | `Vector128.ConditionalSelect` |
| 수평 합 (lane 전부 더하기) | `Vector.Sum` ※.NET 6 | `Vector128.Sum` |
| 원소별 최소/최대 | `Vector.Min` / `Vector.Max` | `Vector128.Min` / `Vector128.Max` |
| 절댓값·제곱근 | `Vector.Abs` / `Vector.SquareRoot` | `Vector128.Abs` / `Vector128.Sqrt` |
| 비트 연산 | `&` `\|` `^` `~` | `&` `\|` `^` `~` |
| 폭 좁히기 / 넓히기 | `Vector.Narrow` / `Vector.Widen` | `Vector128.Narrow` / `Vector128.Widen` |
| lane 타입 재해석 | `Vector.AsVectorByte` 등 | `.AsByte()`, `.AsInt32()` 등 |
| 마스크를 정수 비트로 | (없음) | `Vector128.ExtractMostSignificantBits` |
| lane 재배치 | (없음) | `Vector128.Shuffle` |

마지막 두 줄이 앞의 결정표에서 말한 "lane 위치를 아는가"의 실체다. 가변 폭에는 원리상 존재할 수 없는 연산이다.

> **⚠️ `Vector.Create<T>`는 ※.NET 9부터다**
>
> `Vector128.Create`, `Vector256.Create`는 .NET Core 3.0부터 있었지만, 가변 폭 쪽의 `Vector.Create<T>`는 **.NET 8에는 없다.** .NET 8을 대상으로 한다면 생성자를 써야 한다.
>
> ```csharp
> var v = new Vector<int>(42);        // .NET 8에서도 동작
> ```
>
> 고정 폭과 가변 폭 API가 대칭으로 보이지만 세부는 버전마다 다르다. 이 장의 코드는 **.NET 8을 기준선**으로 삼는다.

## 71.2 하드웨어 내장 함수(`System.Runtime.Intrinsics`)

### 무엇이 노출되어 있는가

**하드웨어 내장 함수(hardware intrinsics)** 는 CPU 명령 하나에 정적 메서드 하나를 1:1로 대응시킨 API다. .NET Core 3.0에 도입됐고, 이후 버전마다 대응 명령이 늘었다.

네임스페이스는 아키텍처별로 갈린다.

| 네임스페이스 | 대상 | 주요 클래스 |
|---|---|---|
| `System.Runtime.Intrinsics.X86` | x86 / x86-64 | `Sse`, `Sse2`, `Sse3`, `Ssse3`, `Sse41`, `Sse42`, `Avx`, `Avx2`, `Avx512F`, `Avx512BW`, `Bmi1`, `Bmi2`, `Popcnt`, `Lzcnt`, `Fma`, `Aes`, `Pclmulqdq`, `X86Base` |
| `System.Runtime.Intrinsics.Arm` | ARM32 / ARM64 | `AdvSimd`, `ArmBase`, `Crc32`, `Aes`, `Sha1`, `Sha256`, `Dp`, `Rdm` |
| `System.Runtime.Intrinsics.Wasm` | WebAssembly | `PackedSimd` |

x86 클래스들은 **명령어 집합의 포함 관계를 상속으로 표현**한다.

```text
  X86Base
     ├── Bmi1
     ├── Bmi2
     ├── Lzcnt
     └── Sse ── Sse2 ── Sse3 ── Ssse3 ── Sse41 ── Sse42 ── Avx ── Avx2 ── Avx512F
                  │                                   │       │            ├── Avx512BW ── Avx512Vbmi
                  ├── Aes                             └─ Popcnt└─ Fma      ├── Avx512CD
                  └── Pclmulqdq                                            └── Avx512DQ
```

이 상속에는 의미가 있다. **`Avx2.IsSupported`가 `true`라면 그 조상들(`Avx`, `Sse42`, ... `Sse`)의 `IsSupported`도 `true`다.** CPU가 AVX2를 지원한다는 것은 그 아래 세대 명령을 전부 지원한다는 뜻이기 때문이다. 그래서 AVX2 경로 안에서 SSE2 명령을 마음 놓고 섞어 쓸 수 있다.

각 클래스에는 64비트 전용 명령을 담은 중첩 클래스 `X64`(ARM에서는 `Arm64`)가 있다.

```csharp
using System.Runtime.Intrinsics.X86;

if (Popcnt.X64.IsSupported)
    return Popcnt.X64.PopCount(value);   // 64비트 popcnt
```

### `IsSupported`를 건너뛰면 무슨 일이 생기는가

내장 함수 클래스의 메서드는 **CPU가 그 명령을 지원할 때만 호출할 수 있다.** 지원하지 않는 CPU에서 호출하면 `PlatformNotSupportedException`이 발생한다.

```csharp
// 위험 — AVX2 없는 CPU에서 던진다
static Vector256<int> Bad(Vector256<int> a, Vector256<int> b)
    => Avx2.Add(a, b);

// 올바름
static Vector256<int> Good(Vector256<int> a, Vector256<int> b)
{
    if (Avx2.IsSupported)
        return Avx2.Add(a, b);
    return a + b;                   // 크로스 플랫폼 폴백
}
```

`IsSupported` 검사를 넣는 비용은 **0**이다. 그 이유는 71.4절에서 자세히 본다.

> **⚠️ `IsSupported`를 변수에 담지 마라**
>
> ```csharp
> // 이렇게 하면 JIT의 상수 폴딩이 깨질 수 있다
> bool useAvx = Avx2.IsSupported;
> // ... 수십 줄 뒤 ...
> if (useAvx) { /* ... */ }
> ```
>
> `Avx2.IsSupported`를 **`if` 조건에 직접** 쓰면 JIT은 그 자리에서 상수로 접고 죽은 분기를 통째로 지운다. 지역 변수를 한 번 거치면 대부분의 경우 여전히 접히지만, 그 변수가 루프를 넘나들거나 클로저에 잡히거나 `out` 인자로 전달되면 보장이 사라진다.
>
> 그리고 접히지 않는 순간 문제는 성능이 아니다. **접히지 않은 분기 안의 `Avx2.Add` 호출은 그 CPU에서 실제로 실행될 수 있고, 그러면 예외가 난다.** 습관적으로 `if (Avx2.IsSupported)`를 직접 쓰라.

### 명명 규약

내장 함수 메서드 이름은 어셈블리 니모닉을 그대로 쓰지 않고 **서술적인 영어 이름**을 쓴다. 대응을 익혀두면 인텔/ARM 문서를 참조하기 쉬워진다.

| .NET 메서드 | x86 명령 | 하는 일 |
|---|---|---|
| `Sse2.LoadVector128(int*)` | `movdqu` | 정렬 없이 128비트 로드 |
| `Sse2.LoadAlignedVector128(int*)` | `movdqa` | **정렬된** 128비트 로드 |
| `Sse2.Store(int*, v)` | `movdqu` | 정렬 없이 저장 |
| `Sse2.StoreAligned(int*, v)` | `movdqa` | 정렬된 저장 |
| `Sse2.StoreAlignedNonTemporal(int*, v)` | `movntdq` | 캐시를 거치지 않는 저장 (61.6절) |
| `Sse2.CompareEqual(v1, v2)` | `pcmpeqd` 등 | lane별 같음 비교 → 마스크 |
| `Sse2.MoveMask(Vector128<byte>)` | `pmovmskb` | lane별 최상위 비트를 정수 하나로 |
| `Avx.LoadVector256(float*)` | `vmovups` | 256비트 로드 |
| `Avx2.MoveMask(Vector256<byte>)` | `vpmovmskb` | 32비트 마스크 |
| `Avx2.Min(Vector256<byte>, ...)` | `vpminub` | 부호 없는 바이트 최솟값 |
| `Popcnt.PopCount(uint)` | `popcnt` | 1인 비트 개수 |
| `Lzcnt.LeadingZeroCount(uint)` | `lzcnt` | 선행 0 개수 |
| `Bmi1.TrailingZeroCount(uint)` | `tzcnt` | 후행 0 개수 |

ARM 쪽도 같은 방식이다.

| .NET 메서드 | 하는 일 |
|---|---|
| `AdvSimd.LoadVector128(int*)` | 128비트 로드 |
| `AdvSimd.Add(v1, v2)` | lane별 덧셈 |
| `AdvSimd.CompareEqual(v1, v2)` | lane별 같음 비교 |
| `AdvSimd.Arm64.AddAcross(Vector128<int>)` | 수평 합 → `Vector64<int>` |
| `ArmBase.LeadingZeroCount(uint)` | 선행 0 개수 |
| `Crc32.ComputeCrc32C(uint, uint)` | CRC-32C 누적 |

> **📌 ARM에는 `MoveMask`가 없다**
>
> x86의 `pmovmskb`는 "각 바이트 lane의 최상위 비트를 모아 32비트 정수로"라는 아주 편리한 연산이고, 벡터 검색 알고리즘의 핵심 도구다. **NEON에는 이에 직접 대응하는 명령이 없다.**
>
> 그래서 .NET 7이 추가한 `Vector128.ExtractMostSignificantBits`는 x86에서는 명령 하나로, ARM64에서는 **여러 명령의 조합**으로 구현된다. 동작은 같지만 비용은 다르다. 크로스 플랫폼 API가 "어디서나 같은 속도"를 뜻하지는 않는다는 예다.
>
> ARM에서 "일치하는 lane이 있는가"만 알면 되는 경우라면 `Vector128.EqualsAny`나 최댓값 비교가 더 싸게 먹힐 수 있다. 71.3절의 `IndexOf` 예제에서 이 차이가 드러난다.

### 상수를 요구하는 인자

일부 명령은 인자 중 하나가 **명령 인코딩에 박히는 즉시값**이다. 셔플 패턴이나 벡터 인덱스가 그렇다. 이런 파라미터에는 `[ConstantExpected]` 특성 ※.NET 7이 붙어 있다.

```csharp
// 두 번째 인자는 반드시 컴파일 타임 상수여야 한다
Vector128<int> lower = Avx.ExtractVector128(v256, 0);
Vector128<int> upper = Avx.ExtractVector128(v256, 1);
```

변수를 넘기면 컴파일은 되더라도 JIT이 명령에 즉시값을 박지 못해 **훨씬 느린 우회 경로**를 생성한다. 분석기가 경고를 내주지만 경고는 경고일 뿐이다.

> **⚠️ 상수 인자에 루프 변수를 넘기지 마라**
>
> ```csharp
> for (int lane = 0; lane < 2; lane++)
>     sum += Avx.ExtractVector128(v, (byte)lane);   // 나쁘다
> ```
>
> `lane`은 JIT이 상수로 접을 수 있을 때만 제대로 컴파일된다. 루프를 풀지 못하면 그렇지 못하다. 이런 코드는 **손으로 펼쳐 쓰는 것이 정답이다.**
>
> ```csharp
> sum += Avx.ExtractVector128(v, 0);
> sum += Avx.ExtractVector128(v, 1);
> ```

### ARM64와 WebAssembly

x86만 대상으로 하던 시절은 끝났다. Apple Silicon 개발 머신, AWS Graviton과 Ampere 기반 서버, Android 디바이스 — ARM64는 이제 예외가 아니라 일급 대상이다.

`System.Runtime.Intrinsics.Arm`의 클래스 구성은 x86과 대칭적이다.

| 클래스 | 대응하는 것 |
|---|---|
| `ArmBase` | 기본 명령. `LeadingZeroCount`, `ReverseElementBits`, `Yield` |
| `AdvSimd` | NEON 전체. 이 장에서 말하는 "ARM SIMD"는 대부분 이것 |
| `AdvSimd.Arm64` | ARM64에서만 쓸 수 있는 NEON 명령 (`AddAcross`, `MaxAcross` 등) |
| `Crc32` | CRC-32 / CRC-32C 누적 |
| `Dp` | 도트 프로덕트 확장 |
| `Rdm` | 반올림 2배 곱셈 누산 확장(`SQRDMLAH`/`SQRDMLSH`) |
| `Aes`, `Sha1`, `Sha256` | 암호 확장 |

x86과 ARM의 가장 큰 구조적 차이는 **벡터 폭**이다. NEON은 128비트가 전부다. 256비트도 512비트도 없다. ARM의 확장 벡터 명령 집합인 SVE/SVE2는 폭이 가변이지만, .NET의 내장 함수로는 아직 노출되지 않았다.

이 사실이 실무에 주는 함의는 분명하다. **ARM64를 대상에 포함한다면 128비트 경로가 주 경로다.** 256비트 경로를 열심히 최적화해도 ARM 서버에서는 실행되지 않는다. `Vector128.IsHardwareAccelerated` 경로에 가장 많은 주의를 쏟는 것이 맞다.

WebAssembly 쪽은 `System.Runtime.Intrinsics.Wasm.PackedSimd`가 WASM SIMD 명령을 노출한다. Blazor WebAssembly에서 의미가 있지만, 브라우저와 런타임 설정에 따라 가용성이 달라지므로 폴백 경로가 특히 중요하다.

> **📌 AVX-512의 진짜 이점은 폭이 아니라 마스크 레지스터다**
>
> AVX-512를 "AVX2의 두 배 폭"으로만 이해하면 절반만 아는 것이다. AVX-512는 **전용 마스크 레지스터(`k0`~`k7`)** 를 도입했고, 거의 모든 명령이 마스크를 인자로 받는다. 즉 "이 lane들만 연산하고 나머지는 건드리지 않기"가 명령 수준에서 지원된다.
>
> 이것이 잔여 처리를 근본적으로 바꾼다. 71.3절에서 본 스칼라 꼬리나 겹치기 대신, **마지막 벡터에 마스크를 씌워 한 번에 끝낼 수 있다.** 게더/스캐터도 마스크와 결합해 훨씬 쓸 만해진다.
>
> ※.NET 8의 `Avx512F` 계열 클래스는 이 명령들 중 상당수를 노출하지만, **크로스 플랫폼 `Vector512` API에는 마스크 개념이 없다.** `Vector512.LoadUnsafe`는 전체 폭을 로드할 뿐이다. 마스크를 쓰려면 `Avx512F` 클래스를 직접 부르고, 그만큼 x86 전용 코드가 된다.

### 내장 함수의 문서를 읽는 법

내장 함수를 쓰다 보면 결국 CPU 벤더 문서를 봐야 한다. 이름 대응만 알면 어렵지 않다.

.NET의 메서드는 대응하는 명령의 **니모닉을 XML 문서 주석에 그대로 적어둔다.** IDE에서 `Avx2.MoveMask`에 마우스를 올리면 다음과 같은 것이 보인다.

```text
int _mm256_movemask_epi8 (__m256i a)
VPMOVMSKB reg, ymm
```

첫 줄은 인텔 C/C++ 내장 함수(intrinsic) 이름, 둘째 줄은 어셈블리 니모닉이다. 이 이름으로 인텔 Intrinsics Guide나 ARM Intrinsics Reference를 검색하면 정확한 의미론과 지연 시간(latency)·처리량(throughput) 표를 찾을 수 있다.

거꾸로도 쓸 수 있다. C/C++ SIMD 코드를 .NET으로 옮길 때, `_mm256_add_epi32` 같은 이름으로 .NET 소스나 문서를 검색하면 대응 메서드(`Avx2.Add`)가 나온다.

> **⚠️ C/C++ 내장 함수와 1:1이 아닌 경우가 있다**
>
> 대부분은 1:1이지만 예외가 있다. .NET은 명령의 **타입 안전성**을 위해 하나의 C 내장 함수를 여러 오버로드로 쪼개거나, 반대로 여러 명령을 하나의 이름으로 묶는다.
>
> `Sse2.MoveMask`가 좋은 예다. C에는 `_mm_movemask_epi8`(정수)과 `_mm_movemask_pd`(double)가 별개 이름으로 있지만, .NET에서는 인자 타입으로 구분되는 `MoveMask` 오버로드 셋이다. `Vector128<byte>`, `Vector128<sbyte>`, `Vector128<double>`만 받는다 — **`Vector128<int>`를 넘길 수 없다.** `int` 벡터의 마스크가 필요하면 `.AsByte()`로 재해석하거나 `Sse.MoveMask(v.AsSingle())`을 쓴다.
>
> 이런 세부는 문서를 읽지 않으면 알 수 없고, 컴파일 오류로 나타나므로 그나마 다행이다. 조용히 다른 명령이 나가는 경우는 없다.

### 스칼라 내장 함수 — `Popcnt`, `Lzcnt`, `Bmi1`, `Bmi2`

내장 함수가 벡터만 다루는 것은 아니다. 비트 조작 명령도 그대로 노출된다.

```csharp
using System.Runtime.Intrinsics.X86;

if (Popcnt.IsSupported)
    return (int)Popcnt.PopCount(x);
```

**그런데 이 코드는 대부분의 경우 쓸 이유가 없다.** `System.Numerics.BitOperations`가 같은 일을 하면서 플랫폼 분기를 알아서 처리한다.

```csharp
using System.Numerics;

int bits = BitOperations.PopCount(x);           // x86이면 popcnt, ARM이면 대응 명령
int lz   = BitOperations.LeadingZeroCount(x);
int tz   = BitOperations.TrailingZeroCount(x);
uint p2  = BitOperations.RoundUpToPowerOf2(x);
int log  = BitOperations.Log2(x);
```

`BitOperations`의 메서드는 전부 JIT 내장 함수이고, 지원하지 않는 CPU에서는 소프트웨어 구현으로 폴백한다. **직접 `Popcnt`를 부를 이유는 사실상 없다.**

> **💡 내장 함수를 쓰기 전에 세 번 물어라**
>
> 1. **BCL에 이미 있는가?** (71.5절) — `IndexOf`, `SequenceEqual`, `BitOperations`, `TensorPrimitives`.
> 2. **`Vector<T>`로 표현되는가?** (71.1절) — 원소별 산술이면 거의 그렇다.
> 3. **`Vector128/256`의 크로스 플랫폼 연산으로 표현되는가?** — 셔플·마스크까지도 대부분 그렇다.
>
> 세 번 다 "아니오"일 때만 `Sse2`/`Avx2`/`AdvSimd`를 직접 부른다. 그 시점에서 당신은 **x86 경로와 ARM 경로와 폴백 경로를 각각 작성하고 각각 테스트할 책임**을 지게 된다.

## 71.3 SIMD로 다시 쓰는 루프 — 합계, 검색, 변환

이 절은 세 가지 흔한 루프를 각각 **스칼라 → `Vector<T>` → 고정 폭 내장 함수** 세 단계로 다시 쓴다. 세 예제 모두 그대로 컴파일해서 돌려볼 수 있다.

### 예제 1 — 배열 합계

#### 1단계: 스칼라

```csharp
static long SumScalar(ReadOnlySpan<int> source)
{
    long total = 0;
    for (int i = 0; i < source.Length; i++)
        total += source[i];
    return total;
}
```

누적을 `long`으로 받는 것에 주목하라. `int` 100만 개의 합은 `int` 범위를 쉽게 넘긴다.

#### 2단계: `Vector<T>`

```csharp
using System.Numerics;
using System.Runtime.InteropServices;

static long SumVector(ReadOnlySpan<int> source)
{
    if (!Vector.IsHardwareAccelerated || source.Length < Vector<int>.Count)
        return SumScalar(source);

    ref int start = ref MemoryMarshal.GetReference(source);
    int step = Vector<int>.Count;
    int i = 0;

    var acc = Vector<int>.Zero;

    // 벡터 본체
    for (; i <= source.Length - step; i += step)
    {
        var v = Vector.LoadUnsafe(ref start, (nuint)i);
        acc += v;
    }

    // 수평 합 — 루프 밖에서 딱 한 번
    long total = Vector.Sum(acc);

    // 잔여 처리
    for (; i < source.Length; i++)
        total += source[i];

    return total;
}
```

네 가지가 중요하다.

**첫째, 누적 벡터를 루프 밖에 둔다.** `acc`는 lane마다 부분합을 들고 있는 벡터다. AVX2라면 8개의 독립적인 부분합이 동시에 자란다.

**둘째, 수평 합은 루프 밖에서 한 번만 한다.** `Vector.Sum`은 lane들을 서로 더하는 **수평(horizontal) 연산**이고, 이것은 SIMD에서 가장 비싼 연산 부류에 속한다. lane 사이를 셔플로 옮겨가며 로그 단계로 접어야 하기 때문이다. 루프 안에서 매번 `Vector.Sum`을 부르면 벡터화의 이득이 통째로 날아간다.

**셋째, `LoadUnsafe`를 쓴다.** `new Vector<int>(source.Slice(i))`도 동작하지만 슬라이스마다 경계 검사가 들어간다. `MemoryMarshal.GetReference`로 첫 원소의 관리 포인터를 얻고 `LoadUnsafe`로 오프셋을 주면 검사가 사라진다. 대신 **범위를 벗어나지 않을 책임이 전적으로 코드에 있다** — 루프 조건 `i <= source.Length - step`이 그 계약이다.

**넷째, `Vector.Sum(acc)`의 반환 타입은 `int`다.** `long total = Vector.Sum(acc)`는 `int` 결과를 `long`으로 넓히는 것이지, `long`으로 누적한 것이 아니다.

> **⚠️ 벡터 누적은 스칼라 누적보다 먼저 넘친다**
>
> 위 코드에는 **오버플로 함정**이 있다. `acc`는 `Vector<int>`이므로 각 lane은 32비트다. 원소가 크고 배열이 길면 lane 하나가 `int.MaxValue`를 넘기고, C#의 기본 산술은 unchecked이므로 **조용히 감싸 돈다.**
>
> 스칼라 버전은 `long total`로 누적하므로 이 문제가 없다. 즉 **벡터화가 결과를 바꿔버린다.** 이것은 성능 문제가 아니라 정확성 문제다.
>
> 안전한 방법은 두 가지다.
>
> 1. **넓혀서 누적한다.** `Vector.Widen(v, out var lo, out var hi)`로 `Vector<long>` 두 개를 얻어 각각 누적한다. 처리량은 절반이 되지만 오버플로가 없다.
> 2. **블록으로 나눈다.** 안전한 개수마다 `Vector.Sum`으로 걷어내 `long`에 옮기고 `acc`를 리셋한다.
>
> 입력 범위를 안다면(예: 픽셀 값 0~255) 그냥 두어도 된다. **모른다면 반드시 처리하라.** 71.6절에서 다시 다룬다.

넓혀서 누적하는 버전은 이렇다.

```csharp
static long SumVectorWidened(ReadOnlySpan<int> source)
{
    if (!Vector.IsHardwareAccelerated || source.Length < Vector<int>.Count)
        return SumScalar(source);

    ref int start = ref MemoryMarshal.GetReference(source);
    int step = Vector<int>.Count;
    int i = 0;

    var accLo = Vector<long>.Zero;
    var accHi = Vector<long>.Zero;

    for (; i <= source.Length - step; i += step)
    {
        var v = Vector.LoadUnsafe(ref start, (nuint)i);
        Vector.Widen(v, out Vector<long> lo, out Vector<long> hi);
        accLo += lo;
        accHi += hi;
    }

    long total = Vector.Sum(accLo) + Vector.Sum(accHi);

    for (; i < source.Length; i++)
        total += source[i];

    return total;
}
```

`Vector.Widen`은 `Vector<int>` 하나를 `Vector<long>` 둘로 쪼갠다. 벡터 하나당 명령이 늘지만 정확성을 얻는다.

#### 3단계: 고정 폭 내장 함수

이제 폭별 경로를 명시적으로 쓴다. 여기서는 `int`를 그대로 누적하는(오버플로 없다고 가정하는) 버전을 보인다.

```csharp
using System.Runtime.InteropServices;
using System.Runtime.Intrinsics;
using System.Runtime.Intrinsics.X86;

static int SumIntrinsics(ReadOnlySpan<int> source)
{
    ref int start = ref MemoryMarshal.GetReference(source);
    int length = source.Length;
    int i = 0;
    int total = 0;

    if (Avx2.IsSupported && length >= Vector256<int>.Count)
    {
        var acc = Vector256<int>.Zero;
        int step = Vector256<int>.Count;               // 8

        for (; i <= length - step; i += step)
        {
            Vector256<int> v = Vector256.LoadUnsafe(ref start, (nuint)i);
            acc = Avx2.Add(acc, v);
        }

        total = Vector256.Sum(acc);
    }
    else if (Vector128.IsHardwareAccelerated && length >= Vector128<int>.Count)
    {
        var acc = Vector128<int>.Zero;
        int step = Vector128<int>.Count;               // 4

        for (; i <= length - step; i += step)
        {
            Vector128<int> v = Vector128.LoadUnsafe(ref start, (nuint)i);
            acc += v;                                  // 크로스 플랫폼 — x64/ARM64 모두
        }

        total = Vector128.Sum(acc);
    }

    for (; i < length; i++)
        total += source[i];

    return total;
}
```

`Avx2.Add`는 x86 전용이지만 `acc += v`(즉 `Vector128.Add`)는 크로스 플랫폼이다. 실무에서는 **양쪽 다 크로스 플랫폼 연산으로 쓰고 폭만 분기하는 것**이 보통이다. 위 코드에서 `Avx2.Add(acc, v)`를 `acc + v`로 바꾸고 가드도 `Avx2.IsSupported` 대신 `Vector256.IsHardwareAccelerated`로 바꾸면, 그 경로가 x64와 ARM64 양쪽에서 컴파일된다. 다만 ARM64에서 `Vector256.IsHardwareAccelerated`는 `false`이므로(NEON은 128비트가 전부다) 실제로는 128비트 경로가 선택된다.

> **📌 `Avx2.Add` 대신 `Vector256.Add`를 쓰면 무엇이 달라지나**
>
> 거의 아무것도 달라지지 않는다. x64에서 두 코드는 **같은 `vpaddd` 명령**으로 컴파일된다. 차이는 이식성뿐이다.
>
> 플랫폼 전용 클래스를 직접 부를 이유는 **크로스 플랫폼 API에 대응물이 없을 때뿐이다.** `Avx2.MoveMask`, `Ssse3.Shuffle`처럼 특정 아키텍처에만 있는 연산, 혹은 `Sse2.StoreAlignedNonTemporal` 같은 캐시 제어 명령이 그렇다.

### 예제 2 — 값 검색(`IndexOf`)

합계와 검색은 성격이 완전히 다르다. 합계는 **모든 원소를 처리해야 하지만**, 검색은 **찾는 순간 멈춘다.** 이 조기 탈출이 벡터화를 까다롭게 만든다.

#### 1단계: 스칼라

```csharp
static int IndexOfScalar(ReadOnlySpan<int> source, int value)
{
    for (int i = 0; i < source.Length; i++)
        if (source[i] == value)
            return i;
    return -1;
}
```

#### 2단계: `Vector<T>`

벡터 비교의 결과는 **마스크 벡터**다. 일치하는 lane은 전체 비트가 1(`AllBitsSet`), 아닌 lane은 0이 된다.

```csharp
using System.Numerics;
using System.Runtime.InteropServices;

static int IndexOfVector(ReadOnlySpan<int> source, int value)
{
    if (!Vector.IsHardwareAccelerated || source.Length < Vector<int>.Count)
        return IndexOfScalar(source, value);

    ref int start = ref MemoryMarshal.GetReference(source);
    int step = Vector<int>.Count;
    var target = new Vector<int>(value);
    int i = 0;

    for (; i <= source.Length - step; i += step)
    {
        var v = Vector.LoadUnsafe(ref start, (nuint)i);

        if (Vector.EqualsAny(v, target))
        {
            // 이 블록 안에 있다 — 어느 lane인지는 스칼라로 찾는다
            var mask = Vector.Equals(v, target);
            for (int lane = 0; lane < step; lane++)
                if (mask[lane] != 0)
                    return i + lane;
        }
    }

    for (; i < source.Length; i++)
        if (source[i] == value)
            return i;

    return -1;
}
```

핵심은 **두 단계 구조**다.

1. `Vector.EqualsAny`로 "이 블록에 있는가"만 빠르게 판정한다. 대부분의 블록에서 `false`이므로 이 경로가 거의 전부를 처리한다.
2. `true`인 블록에서만 lane을 하나씩 뒤진다. 이 스칼라 루프는 전체 실행에서 **최대 한 번** 돈다.

`Vector<T>`에서는 이것이 최선이다. 마스크를 정수 비트로 뽑는 연산이 없으므로 lane을 인덱서로 훑을 수밖에 없다.

> **⚠️ `mask[lane] != 0`은 타입에 의존한다**
>
> `Vector.Equals(v, target)`가 반환하는 마스크의 lane 값은 `T`의 "전체 비트 1"이다. `int`라면 `-1`, `uint`라면 `uint.MaxValue`다. **`== 1`이나 `== true`로 비교하면 안 된다.** `!= 0`이나 `!= default`로 비교하라.
>
> 부동소수점은 더 미묘하다. `Vector<float>`의 마스크 lane은 전체 비트가 1인 비트 패턴이고, 이것을 `float`로 해석하면 NaN이다. **`float` 마스크를 값으로 비교하지 마라.** `Vector.AsVectorInt32(mask)`로 정수로 재해석한 뒤 비교하는 것이 안전하다.

#### 3단계: 고정 폭 내장 함수 + 마스크 비트 추출

바이트 검색이라면 훨씬 좋은 방법이 있다. `MoveMask`로 32개 lane의 결과를 **32비트 정수 하나**로 압축하고, `TrailingZeroCount`로 첫 일치 위치를 즉시 얻는 것이다.

```csharp
using System.Numerics;
using System.Runtime.InteropServices;
using System.Runtime.Intrinsics;
using System.Runtime.Intrinsics.X86;

static int IndexOfByteIntrinsics(ReadOnlySpan<byte> source, byte value)
{
    ref byte start = ref MemoryMarshal.GetReference(source);
    int length = source.Length;
    int i = 0;

    if (Avx2.IsSupported && length >= Vector256<byte>.Count)
    {
        var target = Vector256.Create(value);
        int step = Vector256<byte>.Count;              // 32

        for (; i <= length - step; i += step)
        {
            Vector256<byte> v = Vector256.LoadUnsafe(ref start, (nuint)i);
            Vector256<byte> eq = Avx2.CompareEqual(v, target);

            int mask = Avx2.MoveMask(eq);              // lane 32개 → 비트 32개
            if (mask != 0)
                return i + BitOperations.TrailingZeroCount(mask);
        }
    }
    else if (Vector128.IsHardwareAccelerated && length >= Vector128<byte>.Count)
    {
        var target = Vector128.Create(value);
        int step = Vector128<byte>.Count;              // 16

        for (; i <= length - step; i += step)
        {
            Vector128<byte> v = Vector128.LoadUnsafe(ref start, (nuint)i);
            Vector128<byte> eq = Vector128.Equals(v, target);

            uint mask = eq.ExtractMostSignificantBits();   // 크로스 플랫폼
            if (mask != 0)
                return i + BitOperations.TrailingZeroCount(mask);
        }
    }

    for (; i < length; i++)
        if (source[i] == value)
            return i;

    return -1;
}
```

이것이 BCL의 `MemoryExtensions.IndexOf`가 실제로 하는 일의 골자다. `mask != 0` 하나로 32바이트를 판정하고, 일치하면 `tzcnt` 하나로 정확한 오프셋을 얻는다. **lane 루프가 없다.**

`Avx2.MoveMask`는 `int`를, `ExtractMostSignificantBits`는 `uint`를 반환한다. `BitOperations.TrailingZeroCount`는 두 타입 모두에 오버로드가 있다.

> **💡 검색 루프에서 조기 탈출을 미루면 더 빨라질 때가 있다**
>
> 위 코드는 벡터마다 `mask != 0`을 검사한다. 분기가 벡터당 하나씩 생기고, 분기 예측이 거의 항상 "찾지 못함"으로 맞으므로 비용은 낮다.
>
> 그러나 "찾을 확률이 극히 낮은" 검색(예: 검증 코드에서 잘못된 바이트 찾기)이라면, **여러 벡터의 마스크를 OR로 누적해두었다가 한 번에 검사**하는 방식이 더 빠를 수 있다. 분기 개수가 1/4로 줄기 때문이다. 대신 발견 후 위치를 다시 좁히는 코드가 필요하고, 첫 일치가 앞쪽에 있을 때는 손해다.
>
> 어느 쪽이 이기는지는 **데이터의 통계에 달렸다.** 이런 선택은 반드시 실제 입력 분포로 측정해야 한다.

### 예제 3 — 바이트 변환(ASCII 대문자화)

세 번째 예제는 **조건부 변환**이다. 각 바이트가 `'a'`~`'z'`이면 32를 빼고, 아니면 그대로 둔다.

#### 1단계: 스칼라

```csharp
static void ToUpperScalar(Span<byte> buffer)
{
    for (int i = 0; i < buffer.Length; i++)
    {
        byte b = buffer[i];
        if (b >= (byte)'a' && b <= (byte)'z')
            buffer[i] = (byte)(b - 32);
    }
}
```

이 루프에는 **분기**가 있다. 입력이 뒤섞여 있으면 분기 예측이 계속 실패한다. 벡터화의 가장 큰 이득이 여기서 나온다 — SIMD는 분기 대신 **마스크로 선택**하므로 예측 실패가 원리적으로 없다.

#### 2단계: `Vector<T>`

범위 비교를 두 번 하는 대신, **뺄셈 후 부호 없는 비교** 한 번으로 줄이는 고전적 기법을 쓴다.

`b - 'a'`를 바이트 산술(모듈로 256)로 계산하면,

- `b`가 `'a'`(97)~`'z'`(122)이면 결과는 0~25
- `b`가 97보다 작으면 결과는 감싸 돌아 큰 값(예: `0 - 97 = 159`)
- `b`가 122보다 크면 결과는 26~158

따라서 **부호 없는 비교로 "26 미만"이면 정확히 소문자다.** 비교 한 번으로 끝난다.

```csharp
using System.Numerics;
using System.Runtime.InteropServices;

static void ToUpperVector(Span<byte> buffer)
{
    if (!Vector.IsHardwareAccelerated || buffer.Length < Vector<byte>.Count)
    {
        ToUpperScalar(buffer);
        return;
    }

    ref byte start = ref MemoryMarshal.GetReference(buffer);
    int step = Vector<byte>.Count;
    int i = 0;

    var lowerA   = new Vector<byte>((byte)'a');
    var range26  = new Vector<byte>(26);
    var caseBit  = new Vector<byte>(32);

    for (; i <= buffer.Length - step; i += step)
    {
        var v = Vector.LoadUnsafe(ref start, (nuint)i);

        var shifted = v - lowerA;                            // 감싸 도는 뺄셈
        var isLower = Vector.LessThan(shifted, range26);     // byte는 부호 없는 비교

        var upper = v - caseBit;
        var result = Vector.ConditionalSelect(isLower, upper, v);

        result.StoreUnsafe(ref start, (nuint)i);
    }

    for (; i < buffer.Length; i++)
    {
        byte b = buffer[i];
        if (b >= (byte)'a' && b <= (byte)'z')
            buffer[i] = (byte)(b - 32);
    }
}
```

`Vector.ConditionalSelect(condition, left, right)`는 마스크가 1인 lane에서는 `left`를, 0인 lane에서는 `right`를 고른다. **양쪽 값을 모두 계산한 뒤 고르는 것**이 SIMD의 조건부 처리 방식이다. `upper`는 소문자가 아닌 lane에서도 계산되지만 그 결과는 버려진다.

> **⚠️ 양쪽을 모두 계산해도 안전할 때만 `ConditionalSelect`를 쓸 수 있다**
>
> 위 예제에서 `v - caseBit`는 어떤 바이트에 대해서도 안전하다(감싸 돌 뿐이다). 그러나 다음 같은 코드는 벡터로 그대로 옮길 수 없다.
>
> ```csharp
> if (divisor[i] != 0) result[i] = a[i] / divisor[i];
> ```
>
> 벡터 나눗셈은 **모든 lane을 나눈다.** 0인 lane에서 정수 나눗셈은 하드웨어 예외를, 부동소수점 나눗셈은 무한대나 NaN을 만든다. 부동소수점이라면 결과를 버리므로 대체로 무해하지만, **부동소수점 예외 플래그를 켜둔 환경**이거나 정수 나눗셈이라면 사고가 난다.
>
> 대응은 "안전한 값으로 미리 치환"이다. 0인 lane의 제수를 1로 바꾼 뒤 나누고, 나중에 마스크로 결과를 버린다. 이런 우회가 필요한 시점이 곧 **"이 루프는 벡터화에 적합하지 않다"는 신호**이기도 하다(71.6절).

#### 3단계: 고정 폭 내장 함수

AVX2에는 **부호 없는 바이트 "작다" 비교 명령이 없다.** `vpcmpgtb`는 부호 있는 비교다. 표준 우회는 `vpminub`(부호 없는 최솟값)와 `vpcmpeqb`(같음)를 조합하는 것이다.

`min(x, 25) == x`는 곧 `x <= 25`와 같다. 이것으로 부호 없는 비교를 만든다.

```csharp
using System.Runtime.InteropServices;
using System.Runtime.Intrinsics;
using System.Runtime.Intrinsics.X86;

static void ToUpperIntrinsics(Span<byte> buffer)
{
    ref byte start = ref MemoryMarshal.GetReference(buffer);
    int length = buffer.Length;
    int i = 0;

    if (Avx2.IsSupported && length >= Vector256<byte>.Count)
    {
        var lowerA  = Vector256.Create((byte)'a');
        var max25   = Vector256.Create((byte)25);
        var caseBit = Vector256.Create((byte)32);
        int step    = Vector256<byte>.Count;           // 32

        for (; i <= length - step; i += step)
        {
            Vector256<byte> v = Vector256.LoadUnsafe(ref start, (nuint)i);

            Vector256<byte> shifted = Avx2.Subtract(v, lowerA);
            // min(shifted, 25) == shifted  ⟺  shifted <= 25
            Vector256<byte> isLower =
                Avx2.CompareEqual(Avx2.Min(shifted, max25), shifted);

            // 마스크가 1인 lane에서만 32를 뺀다
            Vector256<byte> delta = Avx2.And(isLower, caseBit);
            Vector256<byte> result = Avx2.Subtract(v, delta);

            result.StoreUnsafe(ref start, (nuint)i);
        }
    }
    else if (Vector128.IsHardwareAccelerated && length >= Vector128<byte>.Count)
    {
        var lowerA  = Vector128.Create((byte)'a');
        var max25   = Vector128.Create((byte)25);
        var caseBit = Vector128.Create((byte)32);
        int step    = Vector128<byte>.Count;           // 16

        for (; i <= length - step; i += step)
        {
            Vector128<byte> v = Vector128.LoadUnsafe(ref start, (nuint)i);

            Vector128<byte> shifted = v - lowerA;
            Vector128<byte> isLower = Vector128.LessThanOrEqual(shifted, max25);

            Vector128<byte> result = v - (isLower & caseBit);
            result.StoreUnsafe(ref start, (nuint)i);
        }
    }

    for (; i < length; i++)
    {
        byte b = buffer[i];
        if (b >= (byte)'a' && b <= (byte)'z')
            buffer[i] = (byte)(b - 32);
    }
}
```

두 경로의 차이를 보라. **AVX2 경로는 `Min` + `CompareEqual` 우회가 필요했지만, `Vector128`의 크로스 플랫폼 `LessThanOrEqual`은 그냥 쓰면 된다.** 크로스 플랫폼 API는 이런 아키텍처별 우회를 내부에서 처리해준다. 이것이 71.2절에서 "크로스 플랫폼 API를 먼저 보라"고 한 이유다.

또한 `Avx2.And(isLower, caseBit)` 대신 `isLower & caseBit`를 쓴 것도 같은 이야기다. 마스크(전체 1 또는 전체 0)와 상수를 AND하면 **선택된 lane에서만 32가, 나머지에서는 0이** 남는다. `ConditionalSelect`보다 명령 하나 적다.

> **📌 이 예제는 실무에서 쓸 일이 없다 — ※.NET 8에 `Ascii`가 있다**
>
> ```csharp
> using System.Text;
>
> Span<byte> buffer = ...;
> Ascii.ToUpperInPlace(buffer, out int written);
> ```
>
> `System.Text.Ascii`는 .NET 8에 추가된 클래스이고, `ToUpper`, `ToLower`, `ToUpperInPlace`, `ToLowerInPlace`, `Equals`, `EqualsIgnoreCase`, `IsValid`, `FromUtf16`, `ToUtf16`을 제공한다. 전부 벡터화되어 있고, ASCII 범위를 벗어난 입력을 `OperationStatus`로 정확히 보고한다.
>
> 그럼에도 이 예제를 셋째로 고른 이유는, **조건부 변환의 벡터화 패턴**이 여기에 다 들어 있기 때문이다. 범위 비교를 뺄셈으로 접기, 마스크 만들기, 마스크로 선택하기 — 이 세 가지가 대부분의 변환 루프에 그대로 적용된다.

### 잔여 처리(remainder handling)

세 예제 모두 마지막에 스칼라 루프가 붙어 있었다. 배열 길이가 벡터 폭의 배수라는 보장이 없기 때문이다. 이 **잔여(tail)** 를 다루는 방법은 세 가지다.

```text
길이 100, 벡터 폭 32인 경우

  [0 ─────── 31][32 ────── 63][64 ────── 95][96 97 98 99]
   ↑ 벡터 1      ↑ 벡터 2      ↑ 벡터 3      ↑ 잔여 4개

  (a) 스칼라 꼬리   :  벡터 3개 + 스칼라 루프 4회
  (b) 겹치는 마지막 :  벡터 3개 + [68 ────── 99] 한 번 더  ← 28개 중복 처리
  (c) 마스크        :  벡터 3개 + 마스크 적용 벡터 1개
```

| 방식 | 장점 | 단점 | 쓸 수 있는 조건 |
|---|---|---|---|
| **(a) 스칼라 꼬리** | 언제나 옳다. 구현이 자명 | 최대 `Count-1`회의 스칼라 반복 | 제한 없음 |
| **(b) 겹치는 마지막 벡터** | 분기 하나, 벡터 하나로 끝 | 일부 원소를 두 번 처리 | **연산이 멱등(idempotent)** 하고, 길이 ≥ 벡터 폭 |
| **(c) 마스크 로드/스토어** | 중복도 스칼라도 없음 | AVX-512 이상 필요, 코드 복잡 | 마스크 명령이 있는 CPU |

**(b) 겹치는 마지막 벡터**가 실무에서 가장 자주 쓰인다. BCL 내부에서도 흔한 패턴이다.

```csharp
using System.Numerics;
using System.Runtime.InteropServices;
using System.Runtime.Intrinsics;

static int CountZeroScalar(ReadOnlySpan<byte> source)
{
    int n = 0;
    for (int i = 0; i < source.Length; i++)
        if (source[i] == 0) n++;
    return n;
}

static int CountZeroBytes(ReadOnlySpan<byte> source)
{
    if (!Vector128.IsHardwareAccelerated || source.Length < Vector128<byte>.Count)
        return CountZeroScalar(source);

    ref byte start = ref MemoryMarshal.GetReference(source);
    int step = Vector128<byte>.Count;
    var zero = Vector128<byte>.Zero;

    int count = 0;
    int i = 0;

    for (; i <= source.Length - step; i += step)
    {
        var v = Vector128.LoadUnsafe(ref start, (nuint)i);
        count += BitOperations.PopCount(
            Vector128.Equals(v, zero).ExtractMostSignificantBits());
    }

    // 잔여가 있으면 마지막 벡터를 끝에 맞춰 다시 한 번
    if (i != source.Length)
    {
        // 겹쳐서 세면 중복 계수가 되므로, 여기서는 겹치지 않는 꼬리만 센다
        for (; i < source.Length; i++)
            if (source[i] == 0) count++;
    }

    return count;
}
```

주석이 말하듯, **계수(count)는 멱등이 아니므로 겹치기를 쓸 수 없다.** 같은 바이트를 두 번 세면 결과가 틀린다.

겹치기가 정당한 것은 다음 같은 경우다.

- **제자리 변환** — 대문자화나 비트 마스킹(AND/OR)처럼 **두 번 적용해도 같은 결과가 나오는 것.** 대문자화는 이미 대문자인 바이트를 건드리지 않으므로 멱등이다. **반면 "32를 무조건 빼기"도, XOR도 멱등이 아니다** — XOR은 두 번 적용하면 원래 값으로 돌아간다.
- **최댓값/최솟값 누적** — 같은 값을 두 번 넣어도 결과가 같다.
- **"존재하는가" 판정** — OR 누적.
- **첫 일치 위치 찾기** — 앞에서부터 찾으므로 중복 검사는 결과를 바꾸지 않는다.

겹치기 버전의 대문자화는 이렇게 쓴다.

```csharp
// 벡터 본체 루프가 끝난 뒤
if (i != buffer.Length)
{
    // 마지막 벡터를 배열 끝에 맞춘다 — 앞부분이 이미 처리된 영역과 겹친다
    nuint tailOffset = (nuint)(buffer.Length - step);

    Vector128<byte> v = Vector128.LoadUnsafe(ref start, tailOffset);
    Vector128<byte> shifted = v - lowerA;
    Vector128<byte> isLower = Vector128.LessThanOrEqual(shifted, max25);
    Vector128<byte> result = v - (isLower & caseBit);
    result.StoreUnsafe(ref start, tailOffset);
}
```

이미 대문자로 바뀐 앞부분을 다시 처리해도, 대문자는 `'a'`~`'z'` 범위 밖이므로 마스크가 0이 되어 그대로 남는다. **멱등이므로 안전하다.**

> **⚠️ 겹치기는 길이가 벡터 폭 이상일 때만 성립한다**
>
> `buffer.Length - step`이 음수가 되면 `LoadUnsafe`가 배열 앞을 읽는다. **관리 힙에서 이것은 임의 메모리 접근이고, 조용히 잘못된 값을 읽거나 프로세스를 죽인다.** 경계 검사가 없는 API를 쓰는 대가다.
>
> 그래서 모든 벡터 경로는 반드시 `length >= step` 가드로 시작해야 한다. 이 장의 모든 예제가 그 검사로 시작하는 이유다. 잊기 쉽고, 잊으면 **짧은 입력에서만 재현되는 메모리 손상**이 된다.

> **💡 잔여 처리를 없애는 가장 좋은 방법은 데이터 크기를 맞추는 것이다**
>
> 버퍼를 직접 할당한다면 길이를 벡터 폭의 배수로 올려두고, 남는 자리를 연산에 영향이 없는 값(합계라면 0, 최솟값이라면 `T.MaxValue`)으로 채워라. 잔여 루프가 통째로 사라진다.
>
> 70장의 SoA 배열이 이 기법과 궁합이 좋다. 배열 하나를 `Count`의 배수로 잡아두면, 그 위를 도는 모든 커널이 잔여 처리 없이 돌아간다. 패딩 원소 몇 개의 메모리는 그만한 가치가 있다.

### 정렬과 `LoadAligned` / `StoreAligned`

61.5절에서 본 대로, 대부분의 SIMD 로드/스토어 명령에는 **정렬을 요구하는 변종**과 그렇지 않은 변종이 있다.

| API | 정렬 요구 | 위반 시 |
|---|---|---|
| `Vector128.Load` / `LoadUnsafe` | 없음 | — |
| `Sse2.LoadVector128` | 없음 | — |
| `Vector128.LoadAligned` | 16바이트 | **하드웨어 폴트** |
| `Vector256.LoadAligned` | 32바이트 | **하드웨어 폴트** |
| `Sse2.LoadAlignedVector128` | 16바이트 | **하드웨어 폴트** |
| `Avx.LoadAlignedVector256` | 32바이트 | **하드웨어 폴트** |
| `Vector128.StoreAlignedNonTemporal` | 16바이트 | **하드웨어 폴트** |

요구되는 정렬은 **캐시 라인 크기가 아니라 벡터 폭**이다. 128비트 벡터는 16바이트, 256비트는 32바이트, 512비트는 64바이트다.

> **⚠️ 정렬 위반은 잡을 수 있는 예외가 아니다**
>
> 정렬된 로드를 정렬되지 않은 주소에 쓰면 CPU가 일반 보호 폴트를 낸다. .NET에서 이것이 어떻게 나타나는지는 플랫폼과 실행 환경에 따라 다르다 — 프로세스가 즉시 죽을 수도 있고, 액세스 위반 계열 예외로 보일 수도 있다. **어느 쪽이든 `try`/`catch`로 대응할 성질의 것이 아니다.**
>
> 그리고 이 버그는 **재현이 산발적이다.** 관리 배열의 시작 주소는 GC의 상태에 따라 달라지고, 같은 코드가 어제는 돌고 오늘은 죽을 수 있다. 정렬 API를 쓴다면 정렬을 **보장하는 방법**으로 메모리를 얻어야 한다.

관리 배열은 정렬을 보장하지 않는다. 방법은 세 가지다.

```csharp
// 1) 네이티브 정렬 할당 ※.NET 6
unsafe
{
    float* p = (float*)NativeMemory.AlignedAlloc(
        byteCount: (nuint)(count * sizeof(float)),
        alignment: 32);
    try
    {
        var span = new Span<float>(p, count);
        // ... p는 32바이트 정렬이 보장된다
    }
    finally { NativeMemory.AlignedFree(p); }
}
```

```csharp
// 2) 배열을 고정하고 첫 정렬 주소를 찾아 거기서부터
unsafe
{
    fixed (float* basePtr = array)
    {
        nuint addr = (nuint)basePtr;
        int misalign = (int)(addr % 32);
        int skip = misalign == 0 ? 0 : (32 - misalign) / sizeof(float);

        // [0, skip) 은 스칼라로 처리
        // [skip, ...) 부터 LoadAligned 사용 가능
    }
}
```

```csharp
// 3) 고정 힙(POH)에 할당 — 주소가 안정적이지만 정렬 자체는 보장되지 않는다
float[] pinned = GC.AllocateUninitializedArray<float>(count, pinned: true);
```

세 번째는 오해하기 쉽다. `pinned: true`는 **객체가 움직이지 않는다**는 보장이지 **특정 경계에 정렬된다**는 보장이 아니다. 정렬이 필요하면 여전히 (2)의 오프셋 계산이 필요하다.

> **💡 대부분의 경우 정렬 API를 쓸 이유가 없다**
>
> Nehalem 이후의 x86 CPU에서 **정렬된 주소에 대한 비정렬 로드(`movdqu`)는 정렬 로드(`movdqa`)와 같은 속도**다. 성능 차이는 명령의 종류가 아니라 **접근이 캐시 라인을 걸치는가**에서 나온다.
>
> 즉 `LoadAligned`를 쓴다고 빨라지는 것이 아니다. **정렬된 데이터**가 빠른 것이고, 그 데이터에는 `LoadUnsafe`를 써도 똑같이 빠르다. `LoadAligned`가 주는 것은 속도가 아니라 **정렬 위반을 즉시 폭발시켜 알려주는 진단 효과**다.
>
> 정렬 API가 실제로 필요한 경우는 좁다. `StoreAlignedNonTemporal`처럼 **정렬을 요구하는 것 말고는 대안이 없는 명령**을 쓸 때다(61.6절). 그 외에는 `LoadUnsafe`/`StoreUnsafe`를 쓰고, 정렬은 데이터 배치로 확보하라.

## 71.4 폴백 경로 설계와 `IsHardwareAccelerated` 검사

### 세 가지 검사와 그 의미

.NET에는 "이 하드웨어가 무엇을 할 수 있는가"를 묻는 API가 층층이 있다. 각각 묻는 것이 다르다.

| 검사 | 묻는 것 | `false`일 때 |
|---|---|---|
| `Vector.IsHardwareAccelerated` | `Vector<T>` 연산이 SIMD 명령으로 컴파일되는가 | 소프트웨어 폴백 — **스칼라보다 느리다** |
| `Vector128.IsHardwareAccelerated` | 128비트 벡터가 가속되는가 | 128비트 경로를 쓰면 안 된다 |
| `Vector256.IsHardwareAccelerated` | 256비트 벡터가 가속되는가 | 128비트로 내려가라 |
| `Vector512.IsHardwareAccelerated` | 512비트 벡터가 가속되는가 | 256비트로 내려가라 |
| `Vector<T>.IsSupported` | 이 `T`로 `Vector<T>`를 만들 수 있는가 | 그 타입으로는 벡터화 불가 |
| `Avx2.IsSupported` 등 | 그 명령어 집합이 있는가 | 그 클래스의 메서드를 부르면 예외 |

**`IsHardwareAccelerated`와 `IsSupported`는 다른 질문이다.** `Vector<double>.IsSupported`는 어디서나 `true`지만, `Vector.IsHardwareAccelerated`는 SIMD가 없는 환경에서 `false`다. 전자는 "이 타입이 유효한가", 후자는 "빠른가"를 묻는다.

### 이 검사들이 공짜인 이유

55.6절에서 상수 폴딩을 봤다. 그 표에 이 검사들이 전부 들어 있었다. 다시 확인해두자.

```csharp
static int Process(ReadOnlySpan<int> data)
{
    if (Vector512.IsHardwareAccelerated && data.Length >= Vector512<int>.Count)
        return Process512(data);
    if (Vector256.IsHardwareAccelerated && data.Length >= Vector256<int>.Count)
        return Process256(data);
    if (Vector128.IsHardwareAccelerated && data.Length >= Vector128<int>.Count)
        return Process128(data);
    return ProcessScalar(data);
}
```

이 메서드는 네 개의 경로를 담고 있지만, **JIT이 만드는 네이티브 코드에는 하나만 남는다.**

JIT은 컴파일 시점에 이미 실행 중인 CPU가 무엇을 지원하는지 안다. AVX2는 있고 AVX-512는 없는 머신이라면,

1. `Vector512.IsHardwareAccelerated` → 상수 `false`
2. `false && ...` → 상수 `false`
3. 첫 `if` 전체가 죽은 코드 → 제거
4. `Vector256.IsHardwareAccelerated` → 상수 `true`
5. `true && data.Length >= 8` → `data.Length >= 8`만 남음
6. 아래 두 `if`는 도달 불가 → 제거 (`Process512`, `Process128`, `ProcessScalar` 호출도 사라진다)

최종 코드는 `if (data.Length >= 8) return Process256(data);` 하나에 폴백 하나다. **분기 검사도, 죽은 경로의 코드도 남지 않는다.**

같은 일이 `Avx2.IsSupported`, `Sse2.IsSupported`, `AdvSimd.IsSupported`에서도 일어난다. 이 폴딩이 없었다면 SIMD 코드를 쓸 때마다 런타임 검사 비용을 냈을 것이고, 짧은 루프에서는 그 비용만으로 이득이 사라졌을 것이다.

> **📌 죽은 경로는 JIT되지도 않는다**
>
> 제거되는 것은 코드만이 아니다. `Process512`가 도달 불가로 판정되면 **그 메서드는 JIT 컴파일 대상에서도 빠진다.** 호출이 없으므로 컴파일할 이유가 없다.
>
> 이것은 시작 시간에도 영향을 준다. 폭별로 세 벌의 커널을 써두어도, 실제 CPU에서 컴파일되는 것은 한 벌뿐이다. **경로를 여러 개 두는 것의 런타임 비용은 사실상 0이다** — 비용은 전부 유지보수 쪽에 있다.

### R2R과 Native AOT에서는 다르다

55.7절에서 본 대로 **ReadyToRun 코드에는 이 폴딩이 적용되지 않는다.** R2R은 게시 시점에 컴파일되므로 실행 CPU를 알 수 없고, 따라서 보수적인 **기준 명령어 집합**을 가정한다.

| | JIT (Tier-1) | ReadyToRun | Native AOT |
|---|---|---|---|
| `Avx2.IsSupported` | 상수로 접힘 | **접히지 않음** | 기본 기준선 기준으로 접힘 |
| 실제 실행되는 경로 | 최적 경로 | 런타임 검사 후 분기 | 지정한 명령어 집합 경로 |
| 개선 방법 | — | 뜨거워지면 Tier-1로 재컴파일 | `IlcInstructionSet` 지정 |

R2R에서는 검사가 실제 분기로 남지만, 그 메서드가 뜨거워지면 Tier-1으로 재컴파일되면서 폴딩이 적용된다. **일시적인 손해**다.

Native AOT는 다르다. 재컴파일이 없으므로 게시 시점에 정한 기준선이 끝까지 간다. 기본 기준선은 보수적이므로, AVX2를 확실히 쓸 수 있는 배포 환경이라면 명시적으로 올려야 한다.

```xml
<PropertyGroup>
  <PublishAot>true</PublishAot>
  <!-- 이 실행 파일은 AVX2 없는 CPU에서 동작하지 않는다 -->
  <IlcInstructionSet>x86-x64-v3</IlcInstructionSet>
</PropertyGroup>
```

> **⚠️ 기준선을 올리면 그 아래 CPU에서는 실행 자체가 안 된다**
>
> `x86-x64-v3`는 AVX2, BMI1/2, FMA, LZCNT, MOVBE를 포함하는 마이크로아키텍처 레벨이다. 이것을 지정하면 컴파일러가 **검사 없이** 그 명령들을 쓴다. 지원하지 않는 CPU에서 실행하면 시작하자마자 잘못된 명령 예외로 죽는다.
>
> 컨테이너 이미지 하나로 여러 세대의 서버에 배포하는 환경이라면 이 설정은 지뢰다. **배포 대상 하드웨어 집합을 통제할 수 있을 때만** 올려라. 그렇지 않다면 기본값을 두고, JIT 기반 배포(R2R 포함)를 쓰는 것이 안전하다.

### 경로 설계 패턴

폭별 경로를 쓸 때의 표준 골격은 다음과 같다.

```csharp
public static int Compute(ReadOnlySpan<byte> source)
{
    // 1. 가장 넓은 것부터. 각 경로는 "폭이 가속되는가" + "길이가 충분한가"를 함께 본다
    if (Vector512.IsHardwareAccelerated && source.Length >= Vector512<byte>.Count)
        return ComputeCore512(source);

    if (Vector256.IsHardwareAccelerated && source.Length >= Vector256<byte>.Count)
        return ComputeCore256(source);

    if (Vector128.IsHardwareAccelerated && source.Length >= Vector128<byte>.Count)
        return ComputeCore128(source);

    // 2. 마지막은 언제나 스칼라. 이것이 정답의 정의다
    return ComputeScalar(source);
}
```

여기서 두 가지 원칙이 나온다.

**원칙 1 — 스칼라 경로는 지우지 마라.** 벡터 경로가 세 개든 다섯 개든, 스칼라 구현은 반드시 남긴다. 이유는 셋이다.

- 짧은 입력에서 실제로 실행된다.
- SIMD가 없는 환경(일부 컨테이너 설정, 오래된 CPU, WASM)에서 유일한 경로다.
- **정답의 기준**이 된다. 벡터 경로를 테스트할 때 무엇과 비교할 것인가.

**원칙 2 — 길이 검사를 폭 검사와 함께 하라.** `Vector512.IsHardwareAccelerated`가 `true`여도 입력이 30바이트면 512비트 경로는 벡터를 한 번도 돌리지 못하고 전부 잔여 처리로 간다. 그럴 바에는 256비트 경로가 낫다.

### 모든 경로를 실제로 테스트하기

폭별 경로를 쓰는 코드의 진짜 위험은 성능이 아니라 **정확성**이다. 개발 머신에서는 AVX2 경로만 돌고, AVX-512 경로는 프로덕션에서 처음 실행된다.

.NET은 JIT 설정 노브로 명령어 집합을 **인위적으로 꺼서** 다른 경로를 강제할 수 있다.

| 환경 변수 | 효과 |
|---|---|
| `DOTNET_EnableAVX512F=0` | AVX-512 경로를 끈다 → 256비트 경로 실행 |
| `DOTNET_EnableAVX2=0` | AVX2 이상을 끈다 → 128비트 경로 실행 |
| `DOTNET_EnableSSE42=0` | SSE4.2 이상을 끈다 |
| `DOTNET_EnableHWIntrinsic=0` | 내장 함수 전체를 끈다 → 스칼라/소프트웨어 폴백 |
| `DOTNET_PreferredVectorBitWidth=128` | `Vector<T>`와 암묵적 벡터화의 폭 상한 |

```bash
# 같은 테스트를 네 가지 구성으로 돌린다
dotnet test
DOTNET_EnableAVX512F=0 dotnet test
DOTNET_EnableAVX2=0 dotnet test
DOTNET_EnableHWIntrinsic=0 dotnet test
```

> **💡 CI에 이 매트릭스를 넣어라**
>
> 벡터 코드의 버그는 거의 전부 **경계에서** 난다 — 길이가 폭보다 1 작을 때, 정확히 폭일 때, 폭+1일 때, 잔여가 없을 때. 그리고 그 경계는 폭마다 다르다.
>
> 실무에서 효과가 좋은 테스트는 이렇게 생겼다.
>
> ```csharp
> [Theory]
> [InlineData(0)] [InlineData(1)] [InlineData(15)] [InlineData(16)] [InlineData(17)]
> [InlineData(31)] [InlineData(32)] [InlineData(33)]
> [InlineData(63)] [InlineData(64)] [InlineData(65)]
> [InlineData(1000)] [InlineData(1023)]
> public void VectorMatchesScalar(int length)
> {
>     var data = CreateRandomData(length);
>     Assert.Equal(ComputeScalar(data), Compute(data));
> }
> ```
>
> 이 테스트를 위의 네 가지 환경 변수 구성으로 각각 돌리면, 폭별 경로 × 경계 길이의 조합이 전부 덮인다. 벡터 코드를 쓰기로 했다면 **이 매트릭스는 선택이 아니다.**

> **⚠️ `DOTNET_EnableHWIntrinsic=0`은 성능 측정용이 아니다**
>
> 이 노브들은 **진단·테스트용**이다. 제품 환경에서 켜두면 BCL 자신의 벡터화된 구현까지 전부 스칼라로 떨어진다 — `string.IndexOf`도, `SequenceEqual`도, `Encoding.UTF8`도. 애플리케이션 전체가 느려진다.
>
> "SIMD를 끄면 얼마나 느려지나"를 재려고 이 변수를 쓰면, 당신 코드의 벡터화 이득이 아니라 **BCL 전체의 벡터화 이득**을 재게 된다. 자기 코드의 스칼라 대비 이득을 재려면 스칼라 메서드를 직접 부르는 벤치마크를 따로 만들어라(67장).

### 계층형 컴파일과의 상호작용

한 가지 더. **Tier-0 코드에서도 `IsSupported`는 상수로 접힌다.** 하드웨어 지원 여부는 최적화가 아니라 정확성의 문제이므로(지원하지 않는 명령을 부르면 예외다) JIT은 계층과 무관하게 이 폴딩을 한다.

그러나 Tier-0에서는 **다른 최적화가 거의 없다.** 인라이닝이 제한적이고, 경계 검사 제거도 약하다. 그래서 벡터 코드도 Tier-0에서는 기대만큼 빠르지 않다.

이것이 67.4절에서 본 "워밍업 부족" 문제가 벡터 코드에서 특히 심한 이유다. 벤치마크가 Tier-0 코드를 재고 있으면 SIMD의 이득이 절반쯤으로 보인다. BenchmarkDotNet은 이것을 알아서 처리하지만, `Stopwatch`로 재는 임시 측정은 그렇지 않다.

`[MethodImpl(MethodImplOptions.AggressiveOptimization)]`을 붙이면 그 메서드는 계층형 컴파일을 건너뛰고 처음부터 최적화된 코드로 컴파일된다.

```csharp
[MethodImpl(MethodImplOptions.AggressiveOptimization)]
static int HotVectorKernel(ReadOnlySpan<byte> source) { /* ... */ }
```

> **⚠️ `AggressiveOptimization`은 대가가 있다**
>
> 이 특성이 붙은 메서드는 **ReadyToRun 이미지에서 제외되고**(55.7절 체크리스트 4번), **동적 PGO의 대상에서도 빠진다.** 첫 호출에서 전체 최적화 컴파일을 하므로 그 호출만 느려진다.
>
> 쓸 만한 곳은 좁다 — **프로세스 수명 동안 몇 번 호출되지 않지만 한 번 호출되면 오래 도는 커널**이다. 호출 계수가 승격 임계에 도달하지 못해 영영 Tier-0에 머무는 경우가 그렇다. 초당 수천 번 호출되는 메서드라면 어차피 곧 Tier-1이 되므로 이 특성은 손해다.

## 71.5 BCL이 이미 벡터화한 것들 — 바퀴를 다시 만들지 않기

### 원칙

이 절의 내용은 문장 하나로 요약된다. **당신이 벡터화하려는 그 루프는 이미 BCL 안에 있을 가능성이 높다.**

.NET Core 3.0 이후 런타임 팀은 BCL의 뜨거운 경로를 체계적으로 벡터화해왔다. 문자열 검색, 스팬 비교, 인코딩 변환, Base64, 비트 연산 — 이런 것들은 이미 폭별 경로와 잔여 처리와 플랫폼 분기를 갖춘 코드로 되어 있고, 그 코드는 당신이 쓸 수 있는 것보다 시간을 훨씬 많이 들인 것이다.

### 이미 벡터화된 API 목록

| 영역 | API | 비고 |
|---|---|---|
| 스팬 검색 | `MemoryExtensions.IndexOf`, `LastIndexOf`, `Contains` | 원시 타입에 대해 벡터 경로 |
| 스팬 검색 | `IndexOfAny`, `IndexOfAnyExcept`, `LastIndexOfAny` | 값 2~3개까지 전용 경로 |
| 스팬 검색 | `IndexOfAnyInRange`, `ContainsAnyInRange` ※.NET 8 | 범위 비교 벡터화 |
| 스팬 검색 | `MemoryExtensions.Count` ※.NET 8 | 일치 개수 세기 |
| 스팬 비교 | `SequenceEqual`, `SequenceCompareTo`, `StartsWith`, `EndsWith` | |
| 스팬 변형 | `Span.Fill`, `Span.Clear`, `Span.Reverse`, `Span.Replace` ※.NET 8 | |
| 검색 집합 | `SearchValues<T>` ※.NET 8, `SearchValues<string>` ※.NET 9 | 69.6절 |
| 문자열 | `string.IndexOf(char)`, `string.Contains`, 서수 `Equals` | 서수(ordinal) 비교만 |
| ASCII | `System.Text.Ascii` 전체 ※.NET 8 | `ToUpper`, `ToLower`, `Equals`, `EqualsIgnoreCase`, `IsValid`, ... |
| 인코딩 | `Encoding.UTF8` 변환, `Encoding.ASCII` | |
| 인코딩 | `Convert.ToHexString` / `FromHexString`, `Convert.ToBase64String` | |
| 인코딩 | `System.Buffers.Text.Base64` | |
| 비트 | `System.Numerics.BitOperations` 전체 | 스칼라 내장 함수로 매핑 |
| 비트 | `BitArray`의 `And`/`Or`/`Xor`/`Not` | |
| 정규식 | `Regex` — 리터럴 접두사/문자 클래스 스캔 | 내부적으로 `SearchValues` 활용 |
| JSON | `Utf8JsonReader`의 구분자 스캔 | |
| 수치 배열 | `TensorPrimitives` ※.NET 8 | `System.Numerics.Tensors` 패키지 |
| LINQ | `Enumerable.Sum` 등 일부 경로 ※.NET 9 | 원시 타입 배열/리스트 한정 |

> **⚠️ 이 표는 "구현 세부"이지 계약이 아니다**
>
> 어떤 API가 벡터화되어 있는지는 **버전마다 바뀐다.** 새 버전에서 추가되기도 하고, 특정 입력 크기 아래에서는 스칼라 경로를 타기도 한다. 문서화된 계약이 아니라 구현 선택이다.
>
> 그래서 이 표를 "이건 빠르니까 마음껏 써도 된다"는 보증으로 읽으면 안 된다. **"직접 벡터화하기 전에 여기 있는지 먼저 확인하라"** 는 목록으로 읽어라. 있다면 쓰고, 그래도 느리면 그때 재라.

### `TensorPrimitives` — 수치 배열 연산의 벡터화된 창구

`System.Numerics.Tensors` 패키지 ※.NET 8의 `TensorPrimitives` 클래스는 **스팬 대 스팬 수치 연산**을 벡터화된 구현으로 제공한다.

```csharp
using System.Numerics.Tensors;

ReadOnlySpan<float> a = ..., b = ...;
Span<float> result = ...;

TensorPrimitives.Add(a, b, result);           // result[i] = a[i] + b[i]
TensorPrimitives.Multiply(a, b, result);
TensorPrimitives.MultiplyAdd(a, b, c, result);

float dot = TensorPrimitives.Dot(a, b);
float sum = TensorPrimitives.Sum(a);
float norm = TensorPrimitives.Norm(a);
float sim = TensorPrimitives.CosineSimilarity(a, b);

int argmax = TensorPrimitives.IndexOfMax(a);
```

이 밖에도 `Abs`, `Divide`, `Subtract`, `Negate`, `Min`, `Max`, `Exp`, `Log`, `Log2`, `Sigmoid`, `SoftMax`, `Tanh`, `Distance`, `SumOfSquares` 등이 있다.

**이 목록에 있는 연산을 직접 벡터화하는 것은 순수한 낭비다.** 임베딩 벡터의 코사인 유사도를 계산하는 코드를 손으로 쓰는 팀이 여전히 많은데, `TensorPrimitives.CosineSimilarity` 한 줄이 그것을 대체한다.

> **📌 `TensorPrimitives`는 out-of-band 패키지다**
>
> `System.Numerics.Tensors`는 런타임에 내장된 것이 아니라 **NuGet 패키지**다.
>
> ```xml
> <PackageReference Include="System.Numerics.Tensors" Version="8.0.0" />
> ```
>
> 그래서 런타임 버전과 독립적으로 갱신되고, 버전에 따라 메서드 집합이 다르다. 이름이 비슷하지만 `System.Numerics.Vector<T>`(런타임 내장)와는 별개의 물건이다.

### 손으로 쓴 루프를 BCL 호출로 되돌리기

실무에서 만나는 코드는 대개 이 방향의 리팩터링이 필요하다. 아래는 흔한 형태다.

```csharp
// 손으로 쓴 검증 — 헤더 값에 제어 문자가 섞여 있는가
static bool HasControlCharOld(string value)
{
    for (int i = 0; i < value.Length; i++)
    {
        char c = value[i];
        if (c < ' ' || c == (char)127)
            return true;
    }
    return false;
}
```

이 루프는 문자 하나씩 읽고 비교를 두 번 한다. 헤더 값이 짧으면 문제없지만, 요청마다 헤더 수십 개에 대해 돌면 누적된다. 벡터화하고 싶어진다 — 그러나 그럴 필요가 없다.

```csharp
using System.Buffers;

// 0x00~0x1F 와 0x7F 를 모두 담은 집합을 한 번만 만든다
private static readonly SearchValues<char> ControlChars = SearchValues.Create(
    BuildControlChars());

private static string BuildControlChars()
{
    var chars = new char[33];
    for (int i = 0; i < 32; i++) chars[i] = (char)i;
    chars[32] = (char)127;
    return new string(chars);
}

static bool HasControlCharNew(string value)
    => value.AsSpan().ContainsAny(ControlChars);
```

`SearchValues<char>`는 이 집합이 전부 ASCII 범위임을 생성 시점에 분석하고, 비트맵과 SIMD 셔플을 쓰는 구현을 고른다(69.6절). 코드는 짧아졌고, 벡터화의 이득은 그대로 받는다. 그리고 이 코드에는 **잔여 처리도, 폭별 분기도, 정렬 고민도 없다.**

같은 종류의 치환이 계속 나온다.

| 손으로 쓴 것 | 바꿀 대상 |
|---|---|
| 루프로 두 시퀀스 비교 | `span.SequenceEqual(other)` |
| 루프로 특정 값 찾기 | `span.IndexOf(value)` |
| 루프로 여러 값 중 하나 찾기 | `span.IndexOfAny(a, b, c)` 또는 `SearchValues<T>` |
| 루프로 범위 밖 값 찾기 | `span.IndexOfAnyExceptInRange(lo, hi)` ※.NET 8 |
| 루프로 개수 세기 | `span.Count(value)` ※.NET 8 |
| 루프로 배열 채우기 | `span.Fill(value)` |
| 수동 헥사 변환 루프 | `Convert.ToHexString` / `Convert.FromHexString` |
| 수동 ASCII 대소문자 비교 | `Ascii.EqualsIgnoreCase` ※.NET 8 |

> **⚠️ `string.IndexOf(string)`의 기본값은 문화권 인식이고, 그 경로는 벡터화되지 않는다**
>
> ```csharp
> int i = text.IndexOf("abc");                              // 문화권 인식 — 느리다
> int j = text.IndexOf("abc", StringComparison.Ordinal);    // 서수 — 벡터화된다
> ```
>
> `string.IndexOf(char)`는 언제나 서수 비교지만, **`string.IndexOf(string)`의 인자 하나짜리 오버로드는 기본이 `StringComparison.CurrentCulture`다.** 이 경로는 문화권 콜레이션을 거치며, 벡터화된 서수 검색과는 비교가 안 되게 느리다.
>
> 더 나쁜 것은 **결과 자체가 다를 수 있다는 점**이다. 문화권 인식 비교에서는 결합 문자나 무시 가능 문자 때문에 직관과 어긋나는 위치가 나온다. 검색 대상이 식별자·프로토콜 토큰·파일 확장자처럼 언어와 무관한 문자열이라면 **반드시 `StringComparison.Ordinal`을 명시하라.**
>
> `StartsWith`, `EndsWith`, `Contains(string)`, `Compare`도 사정이 같다. `CA1307`·`CA1309` 분석기 규칙을 켜두면 놓친 자리를 잡아준다.

> **💡 "벡터화했는데 BCL보다 느리다"면 BCL이 무엇을 더 하는지 보라**
>
> 손으로 쓴 벡터 코드가 BCL보다 느릴 때, 원인은 대개 셋 중 하나다.
>
> 1. **BCL은 폭별 경로를 전부 갖고 있다.** 당신 코드가 128비트만 쓰는데 BCL은 256비트를 쓰고 있다.
> 2. **BCL은 짧은 입력용 특수 경로를 갖고 있다.** 아주 짧은 입력은 벡터를 아예 쓰지 않고 펼친 스칼라 코드로 처리한다.
> 3. **BCL은 경계 검사를 완전히 제거했다.** `MemoryMarshal.GetReference`와 `Unsafe` 조합 중 JIT이 인식하는 형태를 정확히 쓴다.
>
> 세 가지 모두 흉내 낼 수는 있다. 그러나 그러고 나면 당신 코드는 BCL 코드와 거의 같아지고, 유지보수 부담만 남는다.

### 직접 쓰기 전의 체크리스트

| 질문 | "예"라면 |
|---|---|
| 스팬 안에서 값이나 값 집합을 찾는 일인가 | `IndexOf`, `IndexOfAny`, `SearchValues<T>` |
| 두 스팬이 같은지 비교하는 일인가 | `SequenceEqual` |
| 스팬을 특정 값으로 채우거나 비우는 일인가 | `Fill`, `Clear` |
| ASCII 대소문자 변환·검증인가 | `System.Text.Ascii` |
| 헥사/Base64 변환인가 | `Convert`, `System.Buffers.Text.Base64` |
| 비트 개수·최상위 비트 위치인가 | `BitOperations` |
| `float`/`double` 배열의 원소별 산술·집계인가 | `TensorPrimitives` |
| 위 어느 것도 아닌가 | **그때 71.3절로 간다** |

> **💡 BCL 구현을 이기려면 무엇을 더 알아야 하는지 물어라**
>
> 가끔은 직접 쓴 코드가 BCL을 이긴다. 그러나 그것은 **BCL이 모르는 무언가를 당신이 알 때**만 가능하다.
>
> - 입력 길이가 항상 특정 범위임을 안다 (→ 폭 분기와 잔여 처리를 생략)
> - 데이터가 항상 정렬되어 있음을 안다 (→ 정렬 명령, 비일시적 스토어)
> - 여러 연산을 한 패스로 합칠 수 있다 (→ 메모리를 한 번만 읽음)
> - 입력에 특정 불변식이 있다 (예: 항상 ASCII, 항상 양수)
>
> 마지막 것 — **여러 연산의 융합(fusion)** — 이 실무에서 가장 큰 이득을 준다. `TensorPrimitives.Add` 다음에 `TensorPrimitives.Multiply`를 부르면 배열을 두 번 읽는다. 두 연산을 한 루프에 합치면 한 번만 읽는다. 메모리 바운드 코드에서는 이것이 배수 차이를 만든다.
>
> **"BCL보다 SIMD를 잘 쓸 수 있어서" 직접 쓰는 것은 거의 언제나 오판이다. "BCL이 모르는 제약을 알아서" 쓰는 것이 옳은 이유다.**

## 71.6 언제 SIMD가 오히려 손해인가

이 절은 이 장에서 가장 중요하다. 앞의 다섯 절이 "어떻게"였다면 이 절은 "하지 마라"다.

### 손해 유형 1 — 짧은 데이터

벡터 루프에는 고정 비용이 있다.

```text
스칼라 루프 비용:  N × (원소당 비용)

벡터 루프 비용:    (진입 검사) + (상수 벡터 준비)
                 + ⌊N/W⌋ × (벡터당 비용)
                 + (수평 축약)
                 + (N mod W) × (원소당 비용)
```

`N`이 작으면 고정 비용이 전부를 지배한다. `N < W`(벡터 폭)이면 벡터 루프는 **한 번도 돌지 않고** 잔여 처리만 실행되므로, 스칼라보다 순수하게 느리다 — 진입 검사만큼.

| 배열 길이 (`int`, AVX2에서 `W=8`) | 벡터 반복 | 잔여 반복 | 판단 |
|---|---|---|---|
| 4 | 0 | 4 | 벡터화 순손해 |
| 8 | 1 | 0 | 대략 본전 |
| 16 | 2 | 0 | 미미한 이득 |
| 64 | 8 | 0 | 이득 |
| 10,000 | 1,250 | 0 | 명확한 이득 |

> **⚠️ "평균 길이"로 판단하지 마라 — 분포로 판단하라**
>
> 실무에서 가장 흔한 오판이 이것이다. "평균 입력이 200바이트니까 벡터화하면 이득"이라고 결론 내리지만, 실제 분포는 **10바이트가 95%, 10KB가 5%**여서 평균이 200인 경우가 많다.
>
> 이 경우 호출의 95%는 진입 검사만 하고 잔여 루프로 떨어진다. 벡터화는 그 95%를 미세하게 느리게 만들고, 5%만 빠르게 만든다. 전체로는 이득일 수도 손해일 수도 있고, **평균값으로는 알 수 없다.**
>
> 로그를 걸어 실제 길이 히스토그램을 뽑아라. 그게 없으면 벡터화 결정은 추측이다.

### 손해 유형 2 — 분기가 많은 로직

SIMD는 분기하지 않는다. **양쪽을 모두 계산하고 마스크로 고른다.** 그래서 원소마다 하는 일이 다른 로직은 벡터화하면 오히려 일이 늘어난다.

```csharp
// 이런 루프는 벡터화 후보가 아니다
for (int i = 0; i < items.Length; i++)
{
    if (items[i].Kind == Kind.A)      ProcessA(ref items[i]);
    else if (items[i].Kind == Kind.B) ProcessB(ref items[i]);
    else                              ProcessC(ref items[i]);
}
```

벡터로 옮기려면 `ProcessA`, `ProcessB`, `ProcessC`를 **모든 원소에 대해 전부** 계산한 뒤 마스크 세 개로 골라야 한다. 스칼라는 원소당 하나만 하는데, 벡터는 원소당 셋을 한다. 벡터 폭이 8이라도 일이 3배로 늘면 실질 배수는 2.7배로 떨어지고, 각 `Process`가 무거우면 그마저 사라진다.

**해법은 벡터화가 아니라 데이터 재배치다.** 70.4절의 ECS 사고방식이 정확히 이 문제를 푼다. 종류별로 배열을 나누면 각 배열 안에서는 분기가 없어지고, 그때 비로소 벡터화가 성립한다.

> **💡 "벡터화가 어렵다"는 대개 "데이터 배치가 잘못됐다"는 신호다**
>
> 벡터화를 시도하다 마스크가 세 겹으로 중첩되기 시작하면, 코드를 더 짜기 전에 **데이터 쪽을 보라.** 70장의 AoS→SoA 전환이나 종류별 분리를 먼저 하면, 남는 루프는 대체로 자명하게 벡터화된다.
>
> 순서가 중요하다. **데이터 설계(70장) → 벡터화(71장)** 이지 그 반대가 아니다.

### 손해 유형 3 — 메모리 대역폭 한계

이것이 실측 배수가 이론 배수에 못 미치는 **가장 흔한 이유**다.

**산술 강도(arithmetic intensity)** — 메모리에서 읽은 바이트당 수행하는 연산 수 — 가 낮으면, 계산을 아무리 빠르게 해도 데이터가 도착하기를 기다린다.

| 커널 | 원소당 메모리 | 원소당 연산 | 벡터화 효과 |
|---|---|---|---|
| `c[i] = a[i] + b[i]` | 12바이트 (읽기 8, 쓰기 4) | 1 | **낮다** — 대역폭 한계 |
| `sum += a[i]` | 4바이트 | 1 | 낮다 |
| `sum += a[i] * b[i]` | 8바이트 | 2 | 중간 |
| 8차 다항식 평가 | 4바이트 | 16 | **높다** — 계산 한계 |
| ASCII 대문자화 (제자리) | 2바이트 | 3 | 중간~높음 |

L1 캐시에 들어가는 작은 배열이면 대역폭이 넉넉하므로 이론 배수에 가깝게 나온다. 같은 코드가 DRAM에서 오는 큰 배열에서는 배수가 크게 떨어진다. **같은 코드, 같은 CPU인데 배열 크기만으로 결과가 달라진다.**

> **⚠️ 벤치마크 배열 크기를 하나만 쓰면 잘못된 결론을 얻는다**
>
> 1,000개짜리 배열로 벤치마크해서 "7배 빨라졌다"는 결과를 얻고, 프로덕션의 1,000만 개 배열에서 1.3배밖에 안 나오는 것 — 흔한 시나리오다. 1,000개는 L1에 들어가고 1,000만 개는 DRAM에서 온다.
>
> 67장의 규칙대로 **실제 데이터 크기로** 재라. 그리고 여러 크기로 재서 곡선을 보라. L1/L2/L3 경계에서 꺾이는 지점이 보일 것이고, 그 그래프가 "내 데이터는 어디에 있는가"를 말해준다.

### 손해 유형 4 — 데이터 배치가 SIMD에 맞지 않을 때

SIMD 로드는 **연속된 메모리**를 한 덩어리로 읽는다. 데이터가 흩어져 있으면 벡터를 채우는 것 자체가 비싸다.

```csharp
// 이것은 벡터 로드 한 번
float[] xs = ...;
var v = Vector.LoadUnsafe(ref xs[0]);

// 이것은 벡터 로드가 아니다 — 원소마다 따로 읽어 조립해야 한다
Particle[] ps = ...;   // struct Particle { float X, Y, Z; float Mass; }
// ps[0].X, ps[1].X, ps[2].X, ... 를 모으려면?
```

두 번째 경우 `X` 필드들은 16바이트 간격으로 떨어져 있다. 이것을 벡터에 모으려면 **게더(gather)** 가 필요한데, x86의 게더 명령은 존재하지만 느리고, ARM NEON에는 없다. .NET의 크로스 플랫폼 벡터 API에도 게더는 노출되지 않는다.

**해법은 70.3절의 AoS→SoA 전환이다.**

```csharp
// AoS — 벡터화 불가
struct Particle { public float X, Y, Z, Mass; }
Particle[] particles;

// SoA — 각 배열이 그대로 벡터 로드 대상
float[] xs, ys, zs, masses;
```

> **📌 SoA는 벡터화의 전제 조건이지 최적화 옵션이 아니다**
>
> 70장에서 SoA를 "캐시 라인 활용률"의 관점에서 봤다. 여기서는 더 강한 이유가 붙는다. **SoA가 아니면 벡터 로드 자체가 불가능하다.**
>
> 게임 엔진과 물리 시뮬레이터가 SoA를 쓰는 진짜 이유가 이것이다. 캐시 효율은 부수 효과이고, 본질은 "위치 배열 전체에 같은 변환을 벡터로 적용할 수 있다"는 것이다.

### 손해 유형 5 — 부동소수점 결과가 달라진다

배열 합계를 벡터화하면 **결과 값이 바뀔 수 있다.**

스칼라 합계는 `((((a[0]+a[1])+a[2])+a[3])+...)` 순서로 더한다. 벡터 합계는 lane별로 부분합을 만든 뒤 마지막에 합친다 — **덧셈 순서가 다르다.**

부동소수점 덧셈은 결합법칙이 성립하지 않는다. 순서가 다르면 반올림이 다르고, 결과가 다르다.

```csharp
// 스칼라와 벡터의 결과가 마지막 비트에서 다를 수 있다
float sumScalar = SumScalar(data);
float sumVector = SumVector(data);
// sumScalar == sumVector 가 보장되지 않는다
```

> **⚠️ 이것은 버그가 아니지만 사고가 될 수 있다**
>
> 차이는 보통 극히 작다(마지막 몇 비트). 그러나 다음 상황에서는 문제가 된다.
>
> - **회귀 테스트가 정확한 값을 기대할 때.** 벡터화 후 테스트가 깨진다. 테스트가 틀린 것이 아니라 결과가 실제로 바뀐 것이다.
> - **결과가 임계값 비교에 쓰일 때.** `if (total > threshold)`의 판정이 뒤집힐 수 있다.
> - **재현성이 계약일 때.** 금융 계산이나 과학 시뮬레이션에서 "같은 입력 → 같은 출력"이 요구되면, 벡터 폭이 CPU마다 다른 `Vector<T>`는 **머신마다 다른 답**을 낸다.
>
> 마지막 항목이 특히 위험하다. AVX2 서버와 AVX-512 서버가 섞인 클러스터에서 `Vector<T>` 기반 합계는 **서버마다 다른 값**을 낼 수 있다. 재현성이 필요하면 고정 폭을 쓰거나, 아예 벡터화하지 마라.
>
> 정수 연산에는 이 문제가 없다. 정수 덧셈은 결합법칙이 성립한다(오버플로가 없다면).

### 손해 유형 6 — 수평 연산이 루프 안에 있을 때

lane 사이를 넘나드는 연산 — 수평 합, 마스크 추출, 셔플, `ExtractVector128` — 은 lane 독립적인 연산보다 훨씬 비싸다. 데이터가 벡터 레지스터 안에서 옆으로 움직여야 하기 때문이다.

```csharp
// 나쁨 — 벡터마다 수평 합
for (...)
{
    var v = Vector256.LoadUnsafe(ref start, (nuint)i);
    total += Vector256.Sum(v);          // ← 매 반복마다 로그 단계 셔플
}

// 좋음 — 벡터 누적, 마지막에 한 번
var acc = Vector256<int>.Zero;
for (...)
{
    var v = Vector256.LoadUnsafe(ref start, (nuint)i);
    acc += v;                            // ← 명령 하나
}
total = Vector256.Sum(acc);              // ← 루프 밖에서 한 번
```

이 실수는 벡터화 초심자가 가장 자주 저지르는 것이고, 증상은 "벡터화했는데 더 느려졌다"이다.

### 손해 유형 7 — 코드 복잡도

숫자로 재기 어렵지만 실제로 가장 비싼 비용이다.

| 항목 | 스칼라 | `Vector<T>` | 폭별 내장 함수 |
|---|---|---|---|
| 대략적인 줄 수 | 5 | 20 | 60~100 |
| 이해에 필요한 배경 | 없음 | SIMD 기초 | ISA 문서 |
| 테스트 조합 | 1 | 2 (가속/비가속) | 4 이상 (폭별 × 경계) |
| 리뷰 가능한 사람 | 전원 | 일부 | 소수 |
| 새 플랫폼 대응 | 자동 | 자동 | **수동** |

> **💡 벡터화 코드에는 스칼라 참조 구현을 남겨라**
>
> 벡터 커널 옆에 스칼라 구현을 `private static`으로 남기고, 테스트에서 두 결과를 비교하라. 71.4절의 폴백 경로가 그 역할을 겸한다. 이것은 성능 비용이 0이면서(도달 불가 코드는 JIT되지 않는다) 다음을 준다.
>
> - **정답의 정의** — 벡터 코드가 뭘 해야 하는지 문서보다 정확히 말해준다.
> - **디버깅 진입점** — 벡터 경로에서 값이 이상하면 스칼라와 대조한다.
> - **폐기 경로** — 벡터 코드에 심각한 버그가 발견되면 조건 하나로 끌 수 있다.

>

## 이 장의 요약

- **SIMD는 명령 하나로 여러 원소를 처리하는 실행 방식이고, 이론상 배수는 벡터 폭 ÷ 원소 크기다.** AVX2에서 `int` 8개, `byte` 32개다. 실측은 거의 언제나 그보다 낮으며, 가장 흔한 이유는 메모리 대역폭이다.

- **`Vector<T>`는 폭이 런타임에 정해지고, `Vector128/256/512<T>`는 고정이다.** 원소별 산술만 반복한다면 `Vector<T>`로 코드 한 벌이면 되고, 셔플·마스크 추출처럼 lane 위치를 알아야 하는 연산이 필요하면 고정 폭으로 내려간다. `Vector<T>`를 쓰는 메서드는 ReadyToRun 사전 컴파일에서 제외된다.

- **※.NET 7이 `Vector128`/`Vector256` 크로스 플랫폼 API를 정리했고, ※.NET 8이 `Vector512`를 추가했다.** 이제 고정 폭을 쓰면서도 `Sse2`/`AdvSimd`를 직접 부르지 않을 수 있다. 플랫폼 전용 클래스는 크로스 플랫폼 대응물이 없을 때만 쓴다.

- **`Avx2.IsSupported` 같은 검사는 JIT이 상수로 접어 죽은 경로를 통째로 제거한다.** 도달 불가가 된 메서드는 JIT 컴파일 대상에서도 빠진다. 그래서 폭별 경로를 여러 개 두는 런타임 비용은 사실상 0이고, 비용은 전부 유지보수 쪽에 있다. 단 ReadyToRun 코드에서는 이 폴딩이 적용되지 않는다.

- **잔여 처리는 스칼라 꼬리·겹치는 마지막 벡터·마스크 셋 중 하나다.** 겹치기는 연산이 멱등일 때만 쓸 수 있고, 길이가 벡터 폭 이상이라는 가드가 없으면 배열 앞을 읽는 메모리 손상이 된다.

- **정렬 API는 속도가 아니라 진단 효과를 준다.** 현대 x86에서 정렬된 주소에 대한 비정렬 로드는 정렬 로드와 같은 속도다. `LoadAligned`가 필요한 경우는 `StoreAlignedNonTemporal`처럼 대안이 없는 명령을 쓸 때뿐이고, 위반하면 잡을 수 없는 하드웨어 폴트가 난다.

- **BCL은 이미 대부분을 벡터화해두었다.** `IndexOf`, `SequenceEqual`, `SearchValues<T>`, `Ascii`, `BitOperations`, `TensorPrimitives`. 직접 쓰기 전에 이 목록을 먼저 확인하라. BCL을 이길 수 있는 것은 "SIMD를 더 잘 써서"가 아니라 **"BCL이 모르는 제약을 알아서"** 일 때뿐이다.

- **벡터화가 손해인 경우가 이득인 경우보다 흔하다.** 짧은 입력, 원소별로 다른 분기, 낮은 산술 강도, 불연속 데이터, 부동소수점 재현성 요구, 그리고 유지보수 인력 부재. 이 중 하나라도 해당되면 다시 생각하라.

- **순서가 중요하다 — 측정(67장) → 데이터 설계(70장) → 벡터화(71장).** 벡터화가 어렵게 느껴진다면 대개 앞 단계가 덜 된 것이다. SoA로 뒤집고 나면 남는 루프는 자명하게 벡터화되는 경우가 많다.

## 연습 문제

1. 자신의 머신에서 `Vector.IsHardwareAccelerated`, `Vector<byte>.Count`, `Vector<int>.Count`, `Vector<double>.Count`, `Vector128/256/512.IsHardwareAccelerated`를 전부 출력하는 프로그램을 작성하라. 그 다음 `DOTNET_EnableAVX2=0`, `DOTNET_EnableHWIntrinsic=0`, `DOTNET_PreferredVectorBitWidth=128`을 각각 걸고 같은 프로그램을 돌려 출력이 어떻게 달라지는지 표로 정리하라. AVX-512를 지원하는 머신이라면 `DOTNET_PreferredVectorBitWidth=512`도 시도해 `Vector<int>.Count`가 16이 되는지 확인하라.

2. 71.3절의 `SumScalar`, `SumVector`, `SumVectorWidened`, `SumIntrinsics`를 BenchmarkDotNet으로 측정하되, 배열 길이를 8, 64, 1_000, 100_000, 10_000_000의 다섯 가지로 파라미터화하라. 길이별 배수 곡선을 그리고, 꺾이는 지점을 자신의 CPU 캐시 크기(L1/L2/L3)와 대조하라. 어느 길이부터 벡터화가 이득이 되는지 손익분기점을 찾아라.

3. `SumVector`에 오버플로를 실제로 일으켜라. `int.MaxValue / 4` 정도의 값으로 채운 배열을 만들어 `SumScalar`와 `SumVector`의 결과가 갈라지는 지점을 찾고, `SumVectorWidened`가 올바른 값을 내는지 확인하라. 이어서 "블록으로 나눠 주기적으로 걷어내는" 세 번째 방식을 직접 구현해 세 방식의 속도를 비교하라.

4. 71.3절의 `IndexOfByteIntrinsics`를 완성하고, `MemoryExtensions.IndexOf`와 성능을 비교하라. 찾는 값의 위치를 배열 앞(0%), 중간(50%), 끝(100%), 없음의 네 가지로 파라미터화하라. 그 다음 "마스크를 4벡터씩 OR로 누적했다가 한 번에 검사하는" 변형을 구현해, 어느 위치 분포에서 그 변형이 이기는지 찾아라.

5. `ToUpperVector`를 겹치는 마지막 벡터 방식으로 다시 쓰고, 길이 0~64의 모든 값에 대해 스칼라 버전과 결과가 같은지 검증하는 테스트를 작성하라. 이어서 이 잔여 처리 방식을 "32를 무조건 빼기"라는 비멱등 연산에 적용했을 때 어떤 값이 나오는지 직접 관찰하고, 왜 틀리는지 설명하라. 마지막으로 이 테스트를 `DOTNET_EnableAVX512F=0`, `DOTNET_EnableAVX2=0`, `DOTNET_EnableHWIntrinsic=0`의 세 구성으로 각각 다시 돌리는 CI 스크립트를 작성하고, 잔여 처리 가드(`length >= step`)를 일부러 제거했을 때 어느 구성에서 실패가 잡히는지 확인하라.

6. `struct Particle { public float X, Y, Z, Mass; }` 배열 100만 개에 대해 "모든 입자의 X를 1.5배" 하는 루프를 세 가지로 구현하라 — (a) AoS 배열에 스칼라 루프, (b) AoS 배열에 벡터화 시도, (c) SoA로 전환한 뒤 `Vector<float>`. (b)를 실제로 시도해보고 어디서 막히는지 기록하라. 세 방식의 속도를 비교하고, (c)의 배수가 이론값 8배(AVX2)에 얼마나 못 미치는지, 그 이유가 무엇인지 산술 강도로 설명하라.

7. `TensorPrimitives.CosineSimilarity`를 직접 구현한 버전(`Vector<float>` 사용)과 비교 측정하라. 길이 384, 768, 1536(흔한 임베딩 차원)에 대해 재라. 그 다음 "정규화된 벡터만 들어온다"는 제약을 이용해 분모 계산을 생략한 특화 버전을 만들고, 그것이 `TensorPrimitives`를 이기는지 확인하라. 이기지 못한다면 왜인지 조사하라.
