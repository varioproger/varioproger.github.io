# 79장. 코드 관용구

> **이 장의 위치** — Part XV「설계와 관용구」의 두 번째 장이다. 78장이 **남에게 내보내는 계약**을 다뤘다면, 이 장은 그 계약 안쪽 — **내가 코드를 실제로 써 내려가는 방식**을 다룬다. 앞의 여러 장에서 문법과 IL과 런타임 동작을 하나씩 뜯어봤지만, "그래서 이 두 가지 문법 중 무엇을 쓸 것인가"라는 질문에는 매번 답을 미뤘다. 여기서 그 답들을 모아 끝낸다.
>
> **선수 지식** — 13장(클래스와 캡슐화), 14장(상속과 다형성), 15장(`object`와 박싱), 26장(델리게이트와 람다), 28장(열거와 반복자), 78장(API 설계)
>
> **이 장에서 다루지 않는 것** — 공개 API의 형태(가시성, 오버로드, 이벤트 계약, 버전 관리)는 78장에서 끝냈다. 각 문법의 상세 규칙은 해당 장으로 돌린다 — `is` 패턴의 전체 문법은 77장, 보간 문자열의 컴파일 결과는 35.7절, 박싱의 IL과 힙 레이아웃은 54.6절, 숨은 할당의 전수 카탈로그는 63.9절, `IDisposable` 구현 패턴은 33장, 성능 관점의 분석기 규칙은 67.7절이다. 테스트 가능성을 위한 코드 습관은 80장에서 다룬다.

---

관용구(idiom)는 규칙이 아니다. 규칙은 "하라/하지 마라"로 끝나지만 관용구는 **왜 그것이 기본값이어야 하는가**와 **언제 기본값을 벗어나야 하는가**를 함께 갖는다. 이 장의 각 절은 예외 없이 같은 순서로 간다. 나쁜 예를 보이고, 그 코드가 무엇으로 컴파일되어 어떻게 조용히 틀리는지 보이고, 좋은 예를 보인다. 규칙만 나열한 목록이라면 이 장은 실패다.

그리고 마지막 절에서 이 장 전체를 뒤집는 이야기를 한다. **관용구는 코드 리뷰로 강제할 수 없다.** 사람의 주의력은 확장되지 않고, 같은 논쟁은 신입이 들어올 때마다 반복되며, 리뷰어가 피곤한 금요일 저녁의 PR은 그냥 통과된다. 관용구를 팀에 정착시키는 유일한 방법은 **빌드가 실패하게 만드는 것**이다. 79.13절이 그 방법이다. 앞의 열두 절은 그 도구에 무엇을 켤지 정하기 위한 근거다.

## 79.1 `var`를 쓸 자리와 쓰지 말 자리

### `var`는 동적 타이핑이 아니다

먼저 오해부터 없앤다. `var`로 선언한 지역 변수는 **정적으로 타입이 정해진다.** 컴파일러가 초기화 식의 컴파일 타임 타입을 그대로 변수의 타입으로 삼는다. `dynamic`과는 아무 관계가 없다.

```csharp
var s = "hello";
s = 42;              // CS0029: 'int'를 'string'으로 암시적 변환할 수 없다
```

IL에는 `var`의 흔적이 전혀 남지 않는다. 지역 변수 시그니처에는 추론된 실제 타입이 박힌다.

```csharp
var count = 3;
var name = "Widget";
```

```il
.locals init ([0] int32 count,
              [1] string name)
IL_0000:  ldc.i4.3
IL_0001:  stloc.0
IL_0002:  ldstr      "Widget"
IL_0007:  stloc.1
```

즉 **`var`는 런타임 성능에 아무 영향이 없다.** 타이핑 분량과 가독성만의 문제다 — 라고 말하고 싶지만, 그렇지 않은 경우가 정확히 두 가지 있다. 그 둘이 이 절의 본론이다.

### 나쁜 예 1 — 숫자 타입에 `var`를 쓰면 정밀도가 조용히 바뀐다

```csharp
var f = GetMagicNumber();
var total = 100 * f / 6;
Console.WriteLine($"Declared Type: {total.GetType().Name}, Value: {total}");
```

`total`은 무슨 타입인가? 이 코드만 봐서는 알 수 없다. `GetMagicNumber()`의 반환 타입에 따라 다섯 가지 결과가 나온다.

```text
Declared Type: Double,  Value: 166.666666666667
Declared Type: Single,  Value: 166.6667
Declared Type: Decimal, Value: 166.66666666666666666666666667
Declared Type: Int32,   Value: 166
Declared Type: Int64,   Value: 166
```

**왜 나쁜가.** 컴파일러는 `f`에 `GetMagicNumber()`의 선언된 반환 타입을 준다. 계산식의 리터럴 `100`과 `6`은 `f`의 타입으로 변환되고, 그 타입의 산술 규칙으로 계산된다. `int`라면 정수 나눗셈이 일어나 소수점이 사라진다. 코드를 읽는 사람은 `GetMagicNumber()`의 시그니처를 찾아가기 전까지 어느 규칙이 적용되는지 알 수 없다. 게다가 나중에 누군가 `GetMagicNumber()`의 반환 타입을 `int`에서 `double`로 바꾸면 **이 호출 지점은 컴파일 오류 하나 없이 결과가 달라진다.**

`total`만 명시해도 완전히 낫지는 않다.

```csharp
double total = 100 * GetMagicNumber() / 6;   // 여전히 위험하다
```

`GetMagicNumber()`가 `int`를 반환하면 곱셈과 나눗셈이 전부 정수 연산으로 끝난 뒤 그 결과가 `double`로 넓혀진다. 반올림은 이미 일어난 뒤다.

### 좋은 예 — 숫자 변수는 타입을 적는다

```csharp
decimal f = GetMagicNumber();      // 암시적 변환이 없으면 여기서 컴파일 오류가 난다
decimal total = 100 * f / 6;
```

핵심은 **컴파일러가 내 가정을 검사하게 만드는 것**이다. `GetMagicNumber()`가 `decimal`로 암시적 변환되지 않는 타입을 반환한다면 이 줄에서 오류가 난다. 그때 코드를 들여다보고 어떤 변환이 개입해야 하는지 결정하면 된다. `var`를 쓰면 그 기회 자체가 사라진다.

> **⚠️ 넓히기 변환은 조용하고 좁히기 변환은 시끄럽다 — 그러나 `var`는 둘 다 조용하게 만든다**
>
> `float`→`double` 같은 넓히기(widening) 변환은 안전하고, `long`→`int` 같은 좁히기(narrowing) 변환은 명시적 캐스트를 요구한다. 이 안전장치는 **대입 대상의 타입을 내가 적었을 때만** 작동한다. `var`는 대입 대상의 타입을 오른쪽에서 가져오므로 변환 자체가 일어나지 않고, 따라서 검사할 것도 없어진다.

### 나쁜 예 2 — 명시적 타입이 오히려 성능을 망가뜨리는 경우

방향이 반대인 사례도 있다. 이번에는 타입을 적은 쪽이 틀렸다.

```csharp
public IEnumerable<string> FindCustomersStartingWith1(string start)
{
    IEnumerable<string> q =
        from c in db.Customers
        select c.ContactName;

    var q2 = q.Where(s => s.StartsWith(start));
    return q2;
}
```

**왜 나쁜가.** 데이터베이스에 대한 쿼리이므로 `from c in db.Customers select c.ContactName`의 실제 타입은 `IQueryable<string>`이다. 그런데 개발자가 `IEnumerable<string>`으로 받아버렸다. `IQueryable<T>`는 `IEnumerable<T>`를 상속하므로 컴파일러는 경고 하나 없이 이 대입을 허용한다.

문제는 다음 줄이다. **확장 메서드는 가상이 아니고, 오버로드 해석은 컴파일 타임 타입으로만 결정된다.** `q`의 컴파일 타임 타입이 `IEnumerable<string>`이므로 `q.Where(...)`는 `Queryable.Where`가 아니라 `Enumerable.Where`로 해석된다. 그 결과:

- `where` 절이 식 트리에 합성되지 않는다.
- 첫 부분만 서버에서 실행된다. **모든 고객의 이름이 네트워크를 건너온다.**
- 필터링은 로컬 메모리에서 일어난다.

### 좋은 예 — 컴파일러가 나보다 더 나은 타입을 고르게 둔다

```csharp
public IEnumerable<string> FindCustomersStartingWith(string start)
{
    var q =
        from c in db.Customers
        select c.ContactName;

    var q2 = q.Where(s => s.StartsWith(start));
    return q2;
}
```

이제 `q`는 `IQueryable<string>`이다. `q.Where(...)`는 `Queryable.Where`로 해석되고, 필터가 식 트리에 합성되어 서버로 넘어간다. 반환 타입은 여전히 `IEnumerable<string>`이므로 호출자가 보는 계약은 같다 — 바뀐 것은 내부 파이프라인의 효율뿐이다.

> **⚠️ 이 함정은 `IQueryable`에서만 나오는 것이 아니다**
>
> 인터페이스로 받아 확장 메서드를 이어 붙이는 모든 코드가 같은 위험을 갖는다. `List<T>`를 `IEnumerable<T>`로 받아 `Count()`를 부르면 `ICollection<T>` 최적화 경로를 타긴 하지만, `Last()`나 `ElementAt()`처럼 구현별 최적화가 있는 연산자는 **컴파일 타임 타입이 아니라 런타임 타입을 검사해서** 분기한다. 즉 어떤 연산자는 런타임 타입을 보고 어떤 연산자는 안 본다. 이 비일관성을 외우려 하지 말고, **소스에서 나온 타입을 그대로 유지하라**는 원칙으로 대신하라.

### `var` 판단표

원서의 결론은 "숫자 타입은 명시하고, 나머지는 `var`"다. 실무에서는 조금 더 결이 필요하다.

| 상황 | 판단 | 이유 |
|---|---|---|
| `var x = new Widget();` | **`var`** | 타입이 오른쪽에 그대로 적혀 있다. 두 번 적을 이유가 없다 |
| `var q = from c in db.Customers ...` | **`var`** | 컴파일러가 `IQueryable<T>`를 고른다. 내가 고르면 망가진다 |
| `var p = new { X = 5, Y = 7 };` | **`var` 필수** | 익명 타입은 이름이 없다(79.10절) |
| `var d = dict.GetValueOrDefault(k);` | **`var`** | 반환 타입이 컨테이너 선언에서 명백하다 |
| `int count = list.Count;` | **명시** | 숫자 타입 |
| `double ratio = a / b;` | **명시** | 숫자 타입 — 정수 나눗셈 사고의 진원지 |
| `var r = obj.DoSomeWork(x);` | **명시** | 메서드 이름이 반환 타입을 말해 주지 않는다 |
| `IReadOnlyList<T> x = BuildList();` | **명시** | 반환 타입을 **좁히려는 의도**가 있는 경우. `var`면 `List<T>`가 새어 나온다 |
| `foreach (var item in nonGenericList)` | **명시** | 아래 박스 참조 |

> **⚠️ 비제네릭 컬렉션의 `foreach (var ...)`는 `object`가 된다**
>
> ```csharp
> ArrayList list = GetLegacyList();
> foreach (var item in list)      // item은 object다
>     Console.WriteLine(item.Length);   // CS1061: object에 Length가 없다
> ```
>
> 비제네릭 `IEnumerable`의 `Current`는 `object`를 반환하므로 `var`는 `object`로 추론된다. 반면 타입을 명시하면 `foreach`가 **캐스트를 삽입한다**(79.3절). 즉 이 두 줄은 같은 코드가 아니다. 하나는 컴파일 오류이고 하나는 런타임에 `InvalidCastException`이 날 수 있는 코드다.

> **⚠️ `var`와 대상 타입 `new()`는 정확히 반대 방향이다**
>
> ```csharp
> var widget = new Widget();       // 오른쪽에 타입이 있다
> Widget widget = new();           // 왼쪽에 타입이 있다 ※C# 9
> var widget = new();              // 컴파일되지 않는다 — 어느 쪽에도 타입이 없다
> ```
>
> 둘 중 **어느 쪽이든 타입은 정확히 한 번 나타난다.** 팀 규칙을 정할 때 이 둘을 섞어 쓰지 않기로 하는 편이 diff가 깨끗하다. 대상 타입 `new()`는 필드 선언(`private readonly List<int> _items = new();`)처럼 왼쪽 타입이 이미 필수인 자리에서 가장 잘 어울린다.

### 팀 규칙을 정하는 법

`var` 논쟁은 코드 리뷰에서 가장 많은 시간을 낭비하는 주제다. 논쟁을 끝내는 방법은 **한 번 정하고 도구에 넣는 것**이다. `.editorconfig`에는 이 결정을 세 조각으로 나눠 표현할 수 있다.

```ini
[*.cs]
# 내장 타입(int, string, bool ...)에는 var를 쓰지 않는다
csharp_style_var_for_built_in_types = false:warning

# 오른쪽에 타입이 드러나면(new, 캐스트, 팩토리) var를 쓴다
csharp_style_var_when_type_is_apparent = true:suggestion

# 그 밖의 경우는 강제하지 않는다
csharp_style_var_elsewhere = true:silent
```

세 옵션은 각각 진단 **IDE0007**(`var` 사용)과 **IDE0008**(명시적 타입 사용)으로 보고된다. 위 설정은 이 장에서 정리한 결론과 정확히 일치한다 — 숫자를 포함한 내장 타입은 경고로 막고, 타입이 명백한 자리는 제안으로 권하고, 나머지는 개인의 판단에 맡긴다.

> **💡 규칙보다 중요한 것은 "왜"를 남기는 것이다**
>
> `.editorconfig`는 주석을 지원한다. 각 옵션 위에 한 줄씩 이유를 적어라. 6개월 뒤 누군가 "왜 여기서만 명시적 타입이지?"라고 물을 때 답이 파일 안에 있으면 논쟁이 다시 시작되지 않는다. 규칙 자체보다 **규칙이 재논의되지 않는 것**이 팀의 생산성에 더 크게 기여한다.

> **📌 `var`는 타입 안전성과 무관하다**
>
> "타입을 적어야 타입 안전하다"는 것은 오해다. 타입 검사는 컴파일러가 하고, 컴파일러는 `var`든 아니든 똑같이 검사한다. 키를 더 두드리는 것이 안전성을 만들지는 않는다. `var`의 논점은 오직 **읽는 사람이 타입을 알아야 하는가**이다.

## 79.2 `const`보다 `readonly`

### C#에는 상수가 두 종류 있다

```csharp
public class UsefulValues
{
    public const int EndValue = 10;                 // 컴파일 타임 상수
    public static readonly int StartValue = 5;      // 런타임 상수
}
```

둘 다 "바뀌지 않는 값"이지만 **언제 값이 결정되는가**가 다르고, 그 차이가 버전 관리 전체를 좌우한다.

| | `const` | `static readonly` |
|---|---|---|
| 값이 정해지는 시점 | **컴파일 타임** | **런타임**(정적 생성자 또는 초기화자) |
| 허용 타입 | 정수형·부동소수·`enum`·`string`·`null` | **모든 타입** |
| `new` 사용 | 불가 | 가능 |
| 인스턴스별 값 | 불가 (항상 `static`) | 가능 (`readonly` 인스턴스 필드) |
| 메서드 지역 선언 | 가능 (`const int x = 3;`) | 불가 |
| 특성 인수·`case` 레이블·`enum` 정의 | **가능** | 불가 |
| 소비자 어셈블리에서 | **값이 인라인된다** | 필드를 참조한다 |
| 값을 바꾸면 | 소비자 **재컴파일 필요** | 재배포만으로 반영 |
| 성능 | 약간 빠르다 | 필드 로드 한 번 |

### IL 수준에서 무슨 일이 벌어지는가

이 표의 모든 항목은 결국 한 줄의 IL 차이에서 나온다. 먼저 필드 정의부터 보자.

```il
.field public static literal int32 EndValue = int32(0x0000000A)
.field public static initonly int32 StartValue
```

`const`는 `literal` 플래그를 달고 **값 자체가 메타데이터에 들어간다**(Constant 테이블). 실제 저장 공간은 존재하지 않는다. `static readonly`는 `initonly` 플래그를 단 평범한 정적 필드다 — 저장 공간이 있고, 선언 타입의 생성자 밖에서는 쓸 수 없다.

이제 다른 어셈블리에서 이 둘을 읽는 코드를 보자.

```csharp
for (int i = UsefulValues.StartValue; i < UsefulValues.EndValue; i++)
    Console.WriteLine($"value is {i}");
```

```il
IL_0000:  ldsfld     int32 Infrastructure.UsefulValues::StartValue   // 필드를 읽는다
IL_0005:  stloc.0
IL_0006:  br.s       IL_001A
          // ...
IL_001A:  ldloc.0
IL_001B:  ldc.i4.s   10                                              // 값이 박혀 있다
IL_001D:  blt.s      IL_0008
```

**`EndValue`라는 이름은 컴파일된 코드 어디에도 남지 않는다.** 상수 `10`이 호출 지점에 그대로 복사되어 들어갔다. `UsefulValues` 타입에 대한 참조조차 남지 않는다.

### 그래서 이런 사고가 난다

시간이 흘러 Infrastructure 어셈블리를 이렇게 고쳤다고 하자.

```csharp
public class UsefulValues
{
    public static readonly int StartValue = 105;
    public const int EndValue = 120;
}
```

Application 어셈블리는 **재컴파일하지 않고** 새 Infrastructure DLL만 덮어썼다. 기대한 출력은 105부터 119까지다. 실제 출력은 **아무것도 없다.**

```text
시작값 = 105   ← ldsfld 가 새 필드 값을 읽어 왔다
종료값 = 10    ← ldc.i4.s 10 이 옛 어셈블리에 박제되어 있다
105 < 10 이 거짓이므로 루프가 한 번도 돌지 않는다
```

> **⚠️ `public const`의 값을 바꾸는 것은 인터페이스 변경이다**
>
> `readonly` 값을 바꾸는 것은 **구현 변경**이다 — 바이너리 호환이며 DLL만 교체하면 반영된다. `const` 값을 바꾸는 것은 **인터페이스 변경**이다 — 그 상수를 참조하는 모든 코드를 다시 컴파일해야 한다. 78.13절의 호환성 표에서 `const` 값 변경이 "소스 안전 / 바이너리 안전 / **동작 파괴**"로 분류된 이유가 이것이다. 컴파일도 되고 실행도 되는데 답만 틀린, 가장 찾기 어려운 종류의 파괴다.
>
> 필드의 **종류**를 바꾸는 것도 파괴적 변경이다. `static readonly`를 `const`로 바꾸면, 그 필드를 `ldsfld`로 읽던 기존 컴파일 코드가 이제 저장 공간이 없는 `literal` 필드를 찾게 되어 `MissingFieldException`을 맞는다. 반대로 `const`를 `static readonly`로 바꾸면 이미 컴파일된 소비자는 인라인된 **옛 값**을 계속 쓰고, 재컴파일하면 특성 인수나 `case` 레이블처럼 컴파일 타임 상수가 필요한 자리에서 소스가 깨진다. **어느 방향이든 파괴적 변경으로 다뤄라**(78.13절).

### `const`를 반드시 써야 하는 자리

`readonly`를 기본값으로 삼되, 다음 자리에서는 선택의 여지가 없다. **컴파일 타임에 값이 필요한 문맥**이기 때문이다.

```csharp
[Obsolete(DeprecationMessages.UseNewApi)]              // ① 특성 인수
public void OldApi() { }

switch (code) { case StatusCodes.NotFound: break; }    // ② case 레이블·상수 패턴

public enum Level { Low = Thresholds.LowValue }        // ③ enum 멤버 정의

public void Retry(int times = DefaultRetryCount) { }   // ④ 선택적 매개변수 기본값

public const int Doubled = Base * 2;                   // ⑤ 다른 const의 초기화
```

이 밖에 고정 크기 버퍼처럼 컴파일 타임 크기가 필요한 문맥도 마찬가지다.

> **⚠️ `string.Empty`는 `const`가 아니다**
>
> `string.Empty`는 `String` 클래스의 **정적 읽기 전용 필드**이지 컴파일 타임 상수가 아니다. 그래서 선택적 매개변수의 기본값으로 쓸 수 없다.
>
> ```csharp
> public MyClass(string name = string.Empty) { }   // CS1736: 컴파일되지 않는다
> public MyClass(string name = "") { }             // 이렇게 써야 한다
> ```
>
> 같은 이유로 `case string.Empty:`도 안 된다. 코드베이스에서 `string.Empty`와 `""`가 섞여 있는 것을 보면 대개 이 제약 때문이다.

### `readonly`가 아니면 표현할 수 없는 것

```csharp
public class Config
{
    // const 불가 — DateTime은 컴파일 타임 상수가 될 수 없다
    public static readonly DateTime Epoch = new DateTime(2000, 1, 1, 0, 0, 0, DateTimeKind.Utc);

    // const 불가 — 참조 타입 인스턴스
    public static readonly TimeSpan DefaultTimeout = TimeSpan.FromSeconds(30);

    // 인스턴스별로 다른 "상수"
    private readonly Guid _instanceId = Guid.NewGuid();
}
```

`const DateTime`은 컴파일되지 않는다. `new` 연산자로는 컴파일 타임 상수를 만들 수 없기 때문이다 — 값 타입이라도 마찬가지다.

> **⚠️ `static readonly` 배열은 상수가 아니다**
>
> ```csharp
> public static readonly int[] Primes = { 2, 3, 5, 7, 11 };
> // 다른 곳에서
> Config.Primes[0] = 99;      // 컴파일된다. 그리고 모두에게 영향을 준다
> ```
>
> `readonly`가 막는 것은 **필드 자체에 대한 재대입**뿐이다. 참조가 가리키는 객체의 내용은 얼마든지 바뀔 수 있다. 공개하려면 `ImmutableArray<T>`나 `ReadOnlyCollection<T>`를 쓰거나(78.5절), 바이트 상수라면 `ReadOnlySpan<byte>` 프로퍼티로 UTF-8 리터럴을 노출하는 편이 낫다(※C# 11).
>
> ```csharp
> // 이 형태는 배열을 아예 할당하지 않는다 — 데이터가 어셈블리 메타데이터에서 직접 참조된다
> public static ReadOnlySpan<byte> Header => "MZ\0\0"u8;
> ```

> **⚠️ `readonly` 필드가 구조체이면 읽을 때마다 복사본이 만들어질 수 있다**
>
> `readonly` 필드에 담긴 구조체의 멤버를 호출하면, 그 멤버가 필드를 변경할 가능성을 컴파일러가 배제하지 못하는 한 **방어적 복사(defensive copy)** 가 삽입된다. 구조체가 `readonly struct`로 선언되어 있으면 이 복사가 사라진다. 큰 구조체를 `static readonly` 필드로 두고 반복 접근하는 코드에서 실제로 측정되는 비용이다. 자세한 규칙은 16.5절에서 다룬다.

### 분석기 규칙이 반대 방향을 가리키는 문제

`CA1802`("Use literals where appropriate")는 컴파일 타임 상수로 초기화된 `static readonly` 필드를 발견하면 `const`로 바꾸라고 권한다. 성능 관점에서는 맞는 말이다 — 필드 로드 한 번이 사라진다. 그러나 이 절의 논지와 정면으로 충돌한다.

> **💡 `CA1802`는 어셈블리 경계를 기준으로 갈라 적용하라**
>
> - **`internal`·`private` 상수** — `CA1802`를 켜라. 어셈블리 밖으로 나가지 않으므로 인라인되어도 버전 문제가 없다.
> - **`public`·`protected` 상수** — `CA1802`를 꺼라. 값이 소비자에게 박제된다. 유연성이 필드 로드 한 번보다 비싸다.
>
> `.editorconfig`는 경로 단위로 적용되므로 공개 상수를 모아둔 파일이나 폴더에서만 `dotnet_diagnostic.CA1802.severity = none`으로 두면 된다. 성능 차이가 실제로 문제인지는 측정해서 확인하라(67장) — 대부분의 코드에서 `ldsfld` 한 번은 측정되지 않는다.

> **📌 선택적 매개변수의 기본값도 `const`와 같은 방식으로 인라인된다**
>
> `public void Retry(int times = 3)`에서 `3`은 호출 지점에 복사된다. 즉 기본값을 바꾸면 **재컴파일하지 않은 호출자는 옛 값을 계속 보낸다.** `const`와 완전히 같은 함정이고, 78.13절의 표에서 "선택적 매개변수 기본값 변경 = 동작 파괴"로 분류된 이유다. 상수를 다룰 때 배운 조심성을 기본값에도 그대로 적용하라.

## 79.3 캐스트보다 `is` / `as`

### 세 가지 변환 수단

런타임 타입 검사가 불가피한 자리가 있다. 프레임워크가 `object` 매개변수를 정해 놓았거나, 비제네릭 인터페이스를 구현해야 하거나, 이종 컬렉션을 다뤄야 할 때다. C#은 세 가지 수단을 준다.

```csharp
object o = Factory.GetObject();

MyType a = (MyType)o;             // 캐스트 — 실패하면 InvalidCastException
MyType b = o as MyType;           // as   — 실패하면 null
if (o is MyType c) { /* ... */ }  // is 패턴 — 검사와 변환을 한 번에 ※C# 7
```

| | 실패 시 | 사용자 정의 변환 | 값 타입 대상 | IL |
|---|---|---|---|---|
| `(T)x` 캐스트 | `InvalidCastException` | **수행한다**(컴파일 타임 타입 기준) | 가능 | `castclass` / `unbox.any` / `call op_Explicit` |
| `x as T` | `null` | 하지 않는다 | 널 가능 타입만 | `isinst` |
| `x is T t` | `false` | 하지 않는다 | 가능 | `isinst` (+ `unbox.any`) |
| `x.GetType() == typeof(T)` | — | — | — | `callvirt GetType` + 참조 비교 |

### 나쁜 예 — 예외로 흐름을 제어한다

```csharp
object o = Factory.GetObject();
try
{
    MyType t = (MyType)o;
    // t로 작업한다
}
catch (InvalidCastException)
{
    // 변환 실패를 보고한다
}
```

**왜 나쁜가.** 세 가지다.

1. **예외는 비싸다.** 스택 언와인딩과 예외 객체 할당이 일어난다. 실패가 정상 흐름의 일부라면 예외로 표현하면 안 된다.
2. **`null`을 따로 처리해야 한다.** `null`은 어떤 참조 타입으로도 캐스트되고 예외를 던지지 않는다. 즉 `catch`를 써도 `t`가 `null`인 경우는 여전히 남는다. 검사가 두 겹이 된다.
3. **사용자 정의 변환이 개입할 수 있다.** 이게 가장 위험하다. 아래에서 따로 본다.

### 좋은 예

```csharp
object o = Factory.GetObject();
if (o is MyType t)
{
    // t로 작업한다. null이 아님이 보장된다
}
else
{
    // 변환 실패를 보고한다
}
```

한 줄에서 검사·변환·널 배제가 동시에 끝난다. IL은 `isinst` 하나에 분기 하나다.

```il
IL_0001:  isinst     MyType
IL_0006:  dup
IL_0007:  stloc.0
IL_0008:  brfalse.s  IL_0015
```

`isinst`는 **런타임 타입이 대상 타입이거나 그로부터 파생되면 참조를, 아니면 `null`을 푸시한다.** 예외를 던지지 않는다.

### 사용자 정의 변환이 만드는 함정

```csharp
public class SecondType
{
    private MyType _value;
    public static implicit operator MyType(SecondType t) => t._value;   // 암시적 변환
}

object o = Factory.GetObject();   // 실제로는 SecondType 인스턴스다
MyType t1 = o as MyType;          // null — 실패한다
MyType t2 = (MyType)o;            // InvalidCastException — 역시 실패한다
```

**둘 다 실패한다.** 캐스트가 사용자 정의 변환을 수행한다고 배웠는데 왜 실패하는가?

컴파일러는 **컴파일 타임 타입만 본다.** `o`의 컴파일 타임 타입은 `object`이고, `object`에서 `MyType`으로 가는 사용자 정의 변환은 없다. 따라서 컴파일러는 사용자 정의 변환 코드를 아예 생성하지 않고, 대신 런타임 타입이 `MyType`인지 검사하는 `castclass`를 생성한다. `o`의 런타임 타입은 `SecondType`이므로 검사에 실패한다.

같은 식이 정적 타입에 따라 다르게 컴파일된다.

```csharp
SecondType st = o as SecondType;
MyType t = (MyType)st;            // 성공한다 — op_Implicit 호출로 컴파일된다
```

```il
IL_0009:  call       MyType SecondType::op_Implicit(SecondType)
```

> **⚠️ `t = (MyType)st;`의 의미는 `st`의 선언 타입에 따라 달라진다**
>
> `st`가 `SecondType`이면 사용자 정의 변환이 호출되고, `object`이면 런타임 타입 검사가 일어난다. **소스는 한 글자도 다르지 않은데 하는 일이 완전히 다르다.** 반면 `st as MyType`은 `st`의 선언 타입과 무관하게 언제나 런타임 타입 검사다 — 그래서 `as`가 더 예측 가능하다.
>
> 덧붙여, 두 타입이 상속으로 연결되어 있지 않고 사용자 정의 변환만 있다면 `st as MyType`은 **컴파일 오류**가 난다(CS0039). 컴파일러가 "이 변환은 `as`로 표현할 수 없다"고 미리 알려 주는 것이므로, 이 오류를 만나면 캐스트로 바꾸지 말고 **변환 자체가 정말 필요한지** 다시 보라(78.6절).

### 값 타입에 `as`를 쓸 수 없는 이유와 우회

```csharp
object o = Factory.GetValue();
int i = o as int;                 // CS0077: 컴파일되지 않는다
```

`as`는 실패하면 `null`을 반환해야 하는데 `int`는 `null`을 가질 수 없다. 어떤 값을 골라도 그것이 유효한 `int`일 수 있으므로 "실패"를 표현할 방법이 없다. 두 가지 우회가 있다.

```csharp
// 방법 1 — 널 가능 값 타입으로 받는다
var i = o as int?;
if (i != null)
    Console.WriteLine(i.Value);

// 방법 2 — is 패턴 (권장)
if (o is int n)
    Console.WriteLine(n);
```

방법 1은 `System.Nullable<int32>`에 대한 `isinst` 뒤에 언박싱이 붙고, 방법 2는 `isinst System.Int32` 뒤에 `unbox.any`가 붙는다. 방법 2가 널 가능 구조체 하나를 덜 만든다. **값 타입이든 참조 타입이든 `is` 패턴 하나로 통일할 수 있다는 점이 `is` 패턴을 기본 관용구로 삼는 결정적 이유다.**

### `foreach`가 쓰는 것은 캐스트다

```csharp
public void UseCollection(IEnumerable theCollection)
{
    foreach (MyType t in theCollection)
        t.DoStuff();
}
```

이 코드는 대략 다음과 같이 전개된다.

```csharp
IEnumerator it = theCollection.GetEnumerator();
while (it.MoveNext())
{
    MyType t = (MyType)it.Current;      // 캐스트다. as가 아니다
    t.DoStuff();
}
```

**`foreach`의 반복 변수 변환은 캐스트다.** 값 타입과 참조 타입을 동일하게 다뤄야 하므로 언어가 그렇게 정했다. 결과적으로 원소 하나가 잘못된 타입이면 `InvalidCastException`이 난다. 그리고 `IEnumerator.Current`가 `object`를 반환하므로 **사용자 정의 변환은 절대 개입하지 않는다** — 컴파일러가 보는 것은 `object`에서 `MyType`으로 가는 변환뿐이고, 그런 것은 없기 때문이다.

```csharp
// 안전한 대안: 타입이 맞는 원소만 걸러낸다
foreach (MyType t in theCollection.OfType<MyType>())
    t.DoStuff();
```

> **⚠️ `Cast<T>()`와 `OfType<T>()`는 다르다**
>
> - `Enumerable.Cast<T>()`는 **구식 캐스트**를 쓴다. 맞지 않는 원소를 만나면 `InvalidCastException`을 던진다. `class` 제약을 두지 않기 위해 BCL 팀이 의도적으로 캐스트를 택했다.
> - `Enumerable.OfType<T>()`는 **`isinst` 의미론**이다. 맞지 않는 원소는 조용히 건너뛴다.
>
> 그리고 **제네릭 안의 캐스트는 사용자 정의 변환을 쓰지 않는다.** 그래서 `int` 시퀀스에 `Cast<double>()`을 걸면 `int`→`double` 암시적 변환이 있음에도 실패한다. 이걸 하려면 `Select(n => (double)n)`을 써야 한다. 실무에서 꽤 자주 물리는 함정이다.

### `is`와 `GetType()`은 다른 질문이다

```csharp
fido is Animal          // true — Dog는 Animal이다. 다형성 규칙을 따른다
fido.GetType() == typeof(Animal)   // false — 정확한 타입이 아니다
```

`is`는 "이 타입으로 취급해도 되는가"를 묻고, `GetType()` 비교는 "정확히 이 타입인가"를 묻는다. **정확한 타입이 중요한 거의 유일한 자리는 동등성 판정이다.**

```csharp
public override bool Equals(object? obj)
{
    // 파생 타입과 기반 타입이 서로 같다고 판정하면 대칭성이 깨진다
    if (obj is null || obj.GetType() != GetType())
        return false;
    // ...
}
```

그 밖의 비교에서는 `is`/`as`가 제공하는 `isinst` 의미론이 의미상 옳다.

> **💡 `is`/`as`가 필요하다는 것은 설계를 다시 볼 신호일 수 있다**
>
> 좋은 객체지향 설계에서는 타입 변환이 드물다. `is` 검사가 `switch`처럼 늘어서기 시작하면 대개 다형성으로 표현했어야 할 것을 조건문으로 표현하고 있다는 뜻이다. 다만 프레임워크가 `object` 시그니처를 강제하거나, 외부 데이터를 파싱하거나, 방문자 패턴 대신 패턴 매칭을 쓰기로 결정한 경우처럼 **정당한 자리도 분명히 있다**. 그런 자리에서는 주저 없이 `is` 패턴을 쓰되, `switch` 식으로 완전성을 표현할 수 있는지 먼저 보라(77.14절).

> **📌 분석기가 이 변환을 대신 고쳐 준다**
>
> **IDE0019**는 `as` 뒤에 `null` 검사가 오는 형태를 `is` 패턴으로 바꾸라고 제안한다. `is` 검사 뒤에 캐스트가 오는 형태에 대해서는 **IDE0020**과 **IDE0038**이 짝으로 존재한다(패턴 변수를 도입하는 경우와 아닌 경우). 셋 다 자동 코드 픽스가 있으므로, 레거시 코드베이스에 적용하면 `dotnet format`으로 한 번에 정리된다(79.13절).

## 79.4 `string.Format` 대신 보간 문자열, 문화권 의존 문자열은 `FormattableString`

### 나쁜 예 — 위치 인덱스는 컴파일러가 검사하지 않는다

```csharp
var msg = string.Format("{0}님의 주문 {1}건이 {2}에 처리되었습니다.",
                        user.Name, orderCount);
```

**왜 나쁜가.** 자리 표시자는 셋인데 인수는 둘이다. 컴파일러는 이것을 잡지 못한다 — `string.Format`의 시그니처는 `params object[]`이고, 형식 문자열의 내용은 컴파일러에게 그저 문자열일 뿐이다. 실행 시점에 `FormatException`이 난다.

더 나쁜 것은 개수가 맞는데 **순서가 틀린** 경우다.

```csharp
var msg = string.Format("{0}건이 {1}님 앞으로 {2}에 처리되었습니다.",
                        user.Name, orderCount, timestamp);
```

컴파일도 되고 실행도 된다. 출력만 틀린다. 이걸 발견하려면 코드를 돌려서 생성된 문자열을 눈으로 읽어야 한다. 인수 목록과 형식 문자열이 물리적으로 떨어져 있으므로 검토로 잡기도 어렵다.

### 좋은 예

```csharp
var msg = $"{user.Name}님의 주문 {orderCount}건이 {timestamp}에 처리되었습니다.";
```

식이 그것이 나타날 자리에 그대로 있다. 개수가 틀릴 수 없고, 순서가 틀릴 수 없다. 그리고 `{}` 안에는 **임의의 C# 식**이 들어간다.

```csharp
Console.WriteLine($"고객 이름: {c?.Name ?? "이름 없음"}");   // null 조건·병합 연산자
Console.WriteLine($"원주율은 {Math.PI:F2}");                 // 형식 문자열은 ':' 뒤에
Console.WriteLine($"레코드: {(records.TryGetValue(index, out var r)
                              ? r : $"인덱스 {index}에 레코드 없음")}");   // 중첩도 된다
```

> **⚠️ 삼항 연산자의 `:`는 형식 문자열의 `:`와 충돌한다**
>
> ```csharp
> // 컴파일 오류 — 컴파일러가 ':' 를 형식 문자열의 시작으로 읽는다
> Console.WriteLine($"원주율은 {round ? Math.PI.ToString() : Math.PI.ToString("F2")}");
>
> // 식 전체를 괄호로 묶으면 해결된다
> Console.WriteLine($"원주율은 {(round ? Math.PI.ToString() : Math.PI.ToString("F2"))}");
> ```
>
> `?:`뿐 아니라 딕셔너리 인덱서에 콜론이 들어간 문자열 키를 쓸 때도 같은 문제가 나온다. **보간 구멍 안에 `:`가 나타나면 괄호를 씌운다**는 것만 기억하면 된다.

### 제어 흐름은 넣을 수 없다

`{}` 안에 들어가는 것은 **식**이다. `if`/`while` 같은 문장은 넣을 수 없다. 필요하면 메서드나 지역 함수로 빼서 호출하라. `?:`, 스위치 식, LINQ 쿼리는 전부 식이므로 들어간다.

### 컴파일 결과 — 세 갈래로 갈린다

보간 문자열이 무엇으로 컴파일되는지는 **C# 버전과 대상 타입**에 따라 달라진다. 자세한 내부는 35.7절에서 다루고, 여기서는 관용구 판단에 필요한 만큼만 본다.

| 조건 | 컴파일 결과 |
|---|---|
| 구멍이 하나도 없다 | 그냥 문자열 리터럴 |
| 모든 조각이 상수 문자열 ※C# 10 | **컴파일 타임에 결합된 상수** — `const string`에도 쓸 수 있다 |
| 대상 타입이 `string`, ※C# 10 이상 | `DefaultInterpolatedStringHandler`를 스택에 만들고 `AppendLiteral`/`AppendFormatted<T>` 호출 |
| 대상 타입이 `string`, C# 9 이하 | `string.Concat` 또는 `string.Format(string, object[])` |
| 대상 타입이 `FormattableString`/`IFormattable` | `FormattableStringFactory.Create(format, args)` |
| 사용자 정의 보간 핸들러를 받는 매개변수 | 그 핸들러 타입으로 |

핵심 차이는 **박싱**이다. `string.Format(string, params object[])` 경로에서는 값 타입 인수가 전부 `object`로 박싱된다. 반면 `DefaultInterpolatedStringHandler.AppendFormatted<T>(T value)`는 제네릭이므로 값 타입이 박싱되지 않는다.

```csharp
int a = 1, b = 2, c = 3;

// C# 9 이하 / string.Format 직접 호출 — 박싱 3회 + object[] 할당 1회
Console.WriteLine(string.Format("숫자: {0}, {1}, {2}", a, b, c));

// C# 10 이상의 보간 — 핸들러 경로. 박싱 없음
Console.WriteLine($"숫자: {a}, {b}, {c}");
```

> **⚠️ `.ToString()`을 붙이라는 옛 조언은 이제 조건부다**
>
> 원서(2016년)는 보간 구멍 안의 값 타입에 `.ToString()`을 명시적으로 붙여 박싱을 피하라고 권한다. **C# 10 / .NET 6 이후로는 대부분 불필요하다** — 핸들러의 제네릭 오버로드가 박싱을 없앴기 때문이다. 오히려 `.ToString()`을 붙이면 문자열 인스턴스가 하나 더 생겨 손해일 수 있다.
>
> 다만 다음 경우에는 옛 조언이 여전히 유효하다.
>
> - `string.Format`을 **직접** 호출하는 코드
> - `Console.WriteLine(object)`처럼 매개변수 타입이 `object`인 오버로드로 해석되는 호출
> - .NET Framework 대상 프로젝트 — 핸들러 타입 자체가 없다
>
> 판단 기준은 하나다. **호출되는 메서드의 매개변수 타입이 `object`인가**를 보라. 자세히는 63.9절의 숨은 할당 카탈로그에 있다.

### 문화권이 개입하는 지점

보간 문자열로 만들어진 `string`은 **실행 시점의 현재 문화권**으로 포맷된다. 미국에서는 소수점이 `.`이고 독일에서는 `,`다. 로그·직렬화·파일 이름·SQL처럼 **기계가 다시 읽을 문자열**에서 이것은 사고다.

`FormattableString`이 그 해법이다. 보간 문자열 리터럴은 **`string`으로도, `FormattableString`으로도 암시적 변환된다.** 어느 쪽이 되는지는 **대상 타입**이 결정한다.

```csharp
// string — 현재 문화권으로 즉시 포맷된다
string first = $"오늘은 {DateTime.Now.Month}월 {DateTime.Now.Day}일";

// FormattableString — 형식 문자열과 인수가 분리 보관된다. 아직 포맷되지 않았다
FormattableString second = $"오늘은 {DateTime.Now.Month}월 {DateTime.Now.Day}일";

// var — string으로 추론된다
var third = $"오늘은 {DateTime.Now.Month}월 {DateTime.Now.Day}일";
```

`FormattableString`은 `Format` 속성(`"오늘은 {0}월 {1}일"`)과 `GetArguments()`를 갖고 있다. 즉 **포맷을 나중에, 원하는 문화권으로 수행할 수 있다.**

```csharp
public static string ToGerman(FormattableString src) =>
    string.Format(System.Globalization.CultureInfo.CreateSpecificCulture("de-DE"),
                  src.Format, src.GetArguments());

// 호출
var text = ToGerman($"값은 {3.14}입니다");
```

불변 문화권이 필요하면 BCL이 준비해 둔 것을 쓴다. 둘 다 현재 문화권을 보지 않는다.

```csharp
string a = FormattableString.Invariant($"값은 {3.14}");
string b = string.Create(CultureInfo.InvariantCulture, $"값은 {3.14}");   // ※.NET 6
```

두 번째의 `string.Create(IFormatProvider, ref DefaultInterpolatedStringHandler)` 오버로드는 핸들러 경로를 그대로 쓰면서 문화권만 지정하므로 `FormattableString` 객체와 인수 배열을 만들지 않는다. **.NET 6 이상이라면 이쪽이 낫다.**

> **⚠️ `FormattableString`을 받는 메서드를 확장 메서드로 만들면 안 된다**
>
> ```csharp
> // 이렇게 만들면 절대 호출되지 않는다
> public static string ToGerman(this FormattableString src) { /* ... */ }
>
> $"값은 {3.14}".ToGerman();     // src는 이미 string으로 포맷된 뒤다
> ```
>
> 보간 문자열 리터럴이 `.` 연산자의 **왼쪽**에 오면 컴파일러는 그것을 `string`으로 만든다. 확장 메서드를 부르려면 인스턴스가 있어야 하고, 인스턴스를 만들려면 타입을 정해야 하는데, 그 자리에서 컴파일러가 고르는 타입은 `string`이다. **반드시 일반 정적 메서드로 만들어 인수로 넘겨라.**

> **⚠️ `string` 오버로드와 `FormattableString` 오버로드를 함께 두지 마라**
>
> 둘 다 적용 가능하면 컴파일러는 **언제나 `string` 쪽을 고른다.** `FormattableString` 오버로드는 죽은 코드가 되고, 문화권 처리는 조용히 사라진다. 오버로드 대신 이름을 다르게 하라.

> **⚠️ 보간 문자열로 SQL을 만들지 마라**
>
> 보간의 결과는 **모든 값이 이미 박힌 하나의 문자열**이다. 매개변수화된 쿼리가 아니다. `$"SELECT * FROM Users WHERE Name = '{name}'"`은 교과서적인 SQL 인젝션이다.
>
> 그런데 여기에 `FormattableString`의 가장 좋은 실무 용례가 있다. EF Core의 `FromSqlInterpolated`/`ExecuteSqlInterpolated`는 매개변수 타입이 `FormattableString`이다. 즉 **형식 문자열과 인수가 분리된 채로 전달되고, 각 인수가 `DbParameter`로 변환된다.**
>
> ```csharp
> // 안전하다 — name이 매개변수로 바인딩된다
> var users = context.Users.FromSqlInterpolated($"SELECT * FROM Users WHERE Name = {name}");
> ```
>
> 같은 문법이 어느 API에 들어가느냐에 따라 인젝션이 되기도 하고 매개변수화가 되기도 한다. **매개변수 타입이 `string`인지 `FormattableString`인지가 유일한 차이다.**

### 문자열로 타입을 대신하지 마라

같은 뿌리를 가진 문제가 하나 더 있다. **심벌의 이름을 문자열 리터럴로 적는 것**이다. 리팩터링 도구도, 컴파일러도, 분석기도 문자열 안은 보지 않는다.

```csharp
// 나쁜 예 — 프로퍼티 이름을 바꾸면 조용히 깨진다
PropertyChanged?.Invoke(this, new PropertyChangedEventArgs("Name"));
throw new ArgumentNullException("thisCantBeNull", "이 값은 null일 수 없다");

// 좋은 예
PropertyChanged?.Invoke(this, new PropertyChangedEventArgs(nameof(Name)));
throw new ArgumentNullException(nameof(thisCantBeNull), "이 값은 null일 수 없다");
```

`nameof`는 심벌을 그 **로컬 이름 문자열**로 바꾼다. 타입·변수·멤버·네임스페이스에 쓸 수 있고, 완전 한정 이름을 넣어도 마지막 조각만 나온다(`nameof(System.Int32.MaxValue)`는 `"MaxValue"`다). 특성 인수, 라우트 정의에도 쓸 수 있다.

`nameof`를 쓰면 이름 변경이 자동으로 따라오는 것 말고도 이득이 하나 더 있다. **`ArgumentNullException(string paramName, string message)`처럼 문자열 매개변수가 둘인 API에서 순서를 바꿔 넣는 실수를 분석기가 잡을 수 있게 된다.** 문자열 리터럴만 있으면 도구는 아무것도 판단할 수 없다.

문자열 기반 API를 벗어나는 더 근본적인 처방은 35.10절에서 다룬다.

> **📌 이 절과 관련된 분석기 규칙**
>
> | 규칙 | 내용 |
> |---|---|
> | `CA2241` | 형식 메서드에 올바른 개수·형태의 인수를 전달하라 — `string.Format`의 자리 표시자 불일치를 잡는다 |
> | `CA1507` | 문자열 리터럴 대신 `nameof`를 사용하라 |
> | `CA1305` | `IFormatProvider`를 지정하라 |
> | `CA1304` | `CultureInfo`를 지정하라 |
> | `CA1307` | 명확성을 위해 `StringComparison`을 지정하라 |
> | `CA1310` | 정확성을 위해 `StringComparison`을 지정하라 |
> | `CA1848` | 로깅에 `LoggerMessage` 델리게이트를 사용하라 |
> | `CA2254` | 로깅 메시지 템플릿은 정적 식이어야 한다 |
>
> 마지막 두 개는 특히 중요하다. **로거 호출에 보간 문자열을 쓰면 안 된다.**
>
> ```csharp
> // 나쁜 예 — 로그 레벨이 꺼져 있어도 문자열이 만들어진다. 구조화 로깅도 깨진다
> logger.LogInformation($"사용자 {userId}가 {itemCount}건을 주문했다");
>
> // 좋은 예 — 템플릿은 상수, 값은 인수로
> logger.LogInformation("사용자 {UserId}가 {ItemCount}건을 주문했다", userId, itemCount);
> ```
>
> 여기서는 **원래의 위치 기반 형식 문자열이 옳다.** 로깅 프레임워크가 템플릿과 값을 분리해 저장해야 하기 때문이다. 이 절의 결론이 "보간 문자열이 언제나 낫다"가 아니라 **"기계가 다시 읽을 문자열이면 형식과 값을 분리해 둬라"**인 이유다.

## 79.5 멤버 초기화자 vs 생성자 할당, 정적 멤버의 올바른 초기화

### 초기화자를 기본값으로 삼는 이유

```csharp
public class MyClass
{
    private List<string> _labels = new List<string>();
}
```

생성자를 몇 개 추가하든 `_labels`는 초기화된다. 컴파일러가 **모든 생성자의 앞부분에 초기화자 코드를 복사해 넣기** 때문이다. 명시적 생성자를 하나도 만들지 않았다면 컴파일러가 만들어 주는 기본 생성자에도 들어간다.

반대 방향으로도 이득이다. 새 필드를 추가할 때 **모든 생성자를 찾아다니며 초기화 줄을 추가할 필요가 없다.** 선언 자리에서 한 번 초기화하면 끝이다. 생성자와 필드 목록이 시간이 지나며 어긋나는 흔한 버그가 이 관용구 하나로 사라진다.

초기화자 코드가 놓이는 위치도 중요하다. **초기화자는 기반 클래스 생성자가 실행되기 *전에* 실행되고, 선언 순서대로 실행된다.** 이 사실이 79.6절의 가상 함수 문제와 직접 연결된다.

### 초기화자를 쓰면 안 되는 세 경우

**1. 0이나 `null`로 초기화할 때**

```csharp
private int _count = 0;              // 셋 다 불필요하다
private string? _name = null;
private List<int>? _items = default;
```

CLR은 객체 메모리 전체를 **0으로 채운 뒤** 생성자에 들어간다. CPU 명령 수준에서 블록 단위로 처리되는 아주 싼 연산이다. 여기에 다시 0을 대입하는 코드를 붙이면 컴파일러는 그 명령을 성실하게 추가한다. 틀린 코드는 아니지만 불필요하고, "이 값은 명시적으로 0으로 초기화해야 한다"는 잘못된 인상을 준다. 분석기 규칙 **`CA1805`**("불필요하게 초기화하지 마라")가 이것을 잡는다.

값 타입에서는 비용이 더 눈에 띈다.

```csharp
MyValType v1;                     // 0으로 초기화된다
MyValType v2 = new MyValType();   // 역시 0이지만 initobj 명령이 추가로 나간다
```

**2. 생성자마다 다른 값으로 초기화할 때**

```csharp
public class MyClass2
{
    private List<string> _labels = new List<string>();

    MyClass2() { }

    MyClass2(int size)
    {
        _labels = new List<string>(size);     // 앞의 리스트는 즉시 쓰레기가 된다
    }
}
```

컴파일러가 실제로 만드는 코드는 이렇다.

```csharp
public class MyClass2
{
    private List<string> _labels;

    MyClass2()
    {
        _labels = new List<string>();
    }

    MyClass2(int size)
    {
        _labels = new List<string>();         // 초기화자가 복사되어 들어왔다
        _labels = new List<string>(size);     // 그리고 곧바로 버려진다
    }
}
```

`new MyClass2(100)` 한 번에 `List<string>` 두 개가 만들어지고 하나는 즉시 가비지가 된다. **초기화자는 모든 생성자가 같은 방식으로 초기화하는 필드에만 쓴다.** 생성자마다 다르다면 79.6절의 생성자 체이닝으로 해결한다.

**3. 예외 처리가 필요할 때**

초기화자는 `try` 블록으로 감쌀 수 없다. 초기화 중 예외가 나면 그대로 객체 밖으로 전파되고 타입 안에서 복구할 방법이 없다. 복구가 필요하면 생성자 본문으로 옮겨라.

### 초기화 순서 다이어그램

이 순서를 외우지 못하면 79.6절의 함정을 이해할 수 없다. 어떤 타입의 **첫 번째 인스턴스**를 만들 때 실행되는 순서는 이렇다.

```text
    new Derived(args)  가 실행될 때

  ┌──────────────────────────── 타입 초기화 (타입당 한 번만) ─────┐
  │                                                              │
  │  ① 정적 변수 저장소를 0으로 채운다                            │
  │             ↓                                                │
  │  ② 정적 변수 초기화자를 선언 순서대로 실행                    │
  │             ↓                                                │
  │  ③ 기반 클래스 정적 생성자는 여기서 돌지 않는다 → ⑦           │
  │             ↓                                                │
  │  ④ 이 클래스의 정적 생성자 실행                               │
  │                                                              │
  └──────────────────────────────────────────────────────────────┘
                            ↓
  ┌──────────────────────── 인스턴스 초기화 (인스턴스마다) ───────┐
  │                                                              │
  │  ⑤ 인스턴스 변수 저장소를 0으로 채운다                        │
  │             ↓                                                │
  │  ⑥ 인스턴스 변수 초기화자를 선언 순서대로 실행                │
  │       ※ Derived의 초기화자가 여기서 실행된다                  │
  │             ↓                                                │
  │  ⑦ 해당하는 기반 클래스 인스턴스 생성자 실행                  │
  │       ※ Base의 ⑤⑥⑦⑧이 여기서 재귀적으로 일어난다             │
  │             ↓                                                │
  │  ⑧ 이 클래스의 인스턴스 생성자 본문 실행                      │
  │                                                              │
  └──────────────────────────────────────────────────────────────┘

  · 같은 타입의 두 번째 인스턴스부터는 ⑤에서 시작한다
  · ⑥과 ⑦은 생성자 체이닝(: this(...))이 있으면 중복이 제거된다(79.6절)
  · 기반 클래스의 타입 초기화(①~④)는 ⑦에서 기반 생성자가 처음 호출될 때 비로소 일어난다
```

여기서 **⑥이 ⑦보다 먼저**라는 것이 C#의 결정적 선택이다. C++은 반대다. 이 순서 때문에 파생 클래스의 필드 초기화자는 기반 클래스 생성자가 돌기 전에 이미 실행되어 있고, 따라서 기반 클래스 생성자에서 호출한 가상 함수가 **파생 클래스의 초기화자 값은 보지만 파생 클래스 생성자 본문의 값은 보지 못하는** 어중간한 상태가 만들어진다.

### 순서를 직접 확인하기

```csharp
class Base
{
    private static readonly string s_baseStatic = Trace("Base 정적 초기화자");
    private readonly string _baseField = Trace("Base 인스턴스 초기화자");

    static Base() => Trace("Base 정적 생성자");
    public Base() => Trace("Base 인스턴스 생성자");

    protected static string Trace(string m) { Console.WriteLine(m); return m; }
}

class Derived : Base
{
    private static readonly string s_derivedStatic = Trace("Derived 정적 초기화자");
    private readonly string _derivedField = Trace("Derived 인스턴스 초기화자");

    static Derived() => Trace("Derived 정적 생성자");
    public Derived() => Trace("Derived 인스턴스 생성자");
}

// 실행
new Derived();
Console.WriteLine("---");
new Derived();
```

```text
Derived 정적 초기화자
Derived 정적 생성자
Derived 인스턴스 초기화자
Base 정적 초기화자
Base 정적 생성자
Base 인스턴스 초기화자
Base 인스턴스 생성자
Derived 인스턴스 생성자
---
Derived 인스턴스 초기화자
Base 인스턴스 초기화자
Base 인스턴스 생성자
Derived 인스턴스 생성자
```

두 번째 생성에서는 정적 초기화가 전부 사라졌다. 그리고 `Base`의 타입 초기화가 `Derived`의 인스턴스 초기화자 **뒤에** 일어난 것에 주목하라 — 타입 초기화는 "그 타입이 처음 필요해지는 순간"에 일어나고, `Base`가 처음 필요해지는 순간은 `Base` 생성자 호출 시점이기 때문이다.

> **⚠️ 정적 초기화 시점은 `beforefieldinit`에 따라 달라진다**
>
> 위 출력은 **정적 생성자를 명시적으로 선언했을 때**의 결과다. 정적 생성자 없이 정적 초기화자만 있으면 컴파일러는 타입에 **`beforefieldinit`** 플래그를 붙이고, CLR은 "정적 필드에 처음 접근하기 *전 어느 시점*"이라는 느슨한 보장만 한다. 즉 **위 출력의 순서가 달라질 수 있다.**
>
> 정확한 시점 보장이 필요하면 정적 생성자를 명시하고, 필요 없다면 명시하지 마라 — `beforefieldinit`이 사라지면 JIT이 정적 필드 접근마다 초기화 검사를 삽입할 수 있어 비용이 생긴다. 분석기 규칙 **`CA1810`**("참조 형식의 정적 필드를 인라인으로 초기화하라")이 불필요한 정적 생성자를 지적하는 이유가 이것이다. 자세한 규칙은 13.12절에 있다.

### 정적 멤버 초기화 — 초기화자와 정적 생성자의 분업

```csharp
// 단순 할당이면 초기화자로 충분하다
public class MySingleton
{
    private static readonly MySingleton s_instance = new MySingleton();
    public static MySingleton Instance => s_instance;
    private MySingleton() { }
}

// 복잡한 로직이나 예외 처리가 필요하면 정적 생성자를 쓴다
public class MySingleton2
{
    private static readonly MySingleton2 s_instance;
    static MySingleton2()
    {
        try { s_instance = new MySingleton2(); }
        catch (IOException) { /* 복구를 시도한다 */ }
    }
    public static MySingleton2 Instance => s_instance;
    private MySingleton2() { }
}
```

**인스턴스 생성자나 별도의 초기화 헬퍼로 정적 필드를 초기화하지 마라.** "첫 인스턴스가 만들어질 때 초기화한다"는 것은 정적 멤버를 인스턴스 없이 쓰는 코드에서 곧바로 깨진다. C#은 이 목적으로 정적 생성자를 언어에 넣었다.

> **⚠️ 정적 생성자에서 예외가 새어 나가면 타입이 영구히 죽는다**
>
> CLR은 정적 생성자를 자동으로, 정확히 한 번 호출한다. 예외가 밖으로 나가면 **`TypeInitializationException`** 으로 감싸져 던져진다. 더 나쁜 것은 그다음이다. **CLR은 다시 시도하지 않는다.** 그 타입(과 파생 타입)의 인스턴스를 만들려는 모든 시도가 같은 예외로 실패한다. 프로세스가 죽을 때까지 계속된다.
>
> 호출자가 그 예외를 잡아서 계속 실행하면 상황이 더 나빠진다 — 초기화되지 않은 타입이 남아 있고, 그 타입을 쓰는 모든 코드가 이해할 수 없는 지점에서 실패한다. **정적 생성자 안에서는 예외를 던질 수 있는 일을 하지 마라.** 설정 읽기, 파일 접근, 네트워크 호출은 전부 여기에 해당한다.

> **⚠️ 정적 생성자끼리 서로를 참조하면 순환이 생긴다**
>
> `A`의 정적 생성자가 `B.Something`을 읽고, `B`의 정적 생성자가 `A.Other`를 읽으면 어느 한쪽은 **초기화가 끝나지 않은 상태의 값(즉 0이나 `null`)** 을 보게 된다. CLR은 교착 상태를 피하려고 이 상황을 허용하며, 예외도 경고도 없다. 어느 쪽이 0을 보게 되는지는 어느 타입이 먼저 접근되었는가에 달려 있으므로 **실행마다 달라질 수 있다.** 정적 상태 사이의 의존성을 그림으로 그려 순환이 없는지 확인하라.

### 비싸거나 드물게 쓰이는 정적 상태는 `Lazy<T>`

```csharp
private static readonly Lazy<MetadataCache> s_lazy =
    new Lazy<MetadataCache>(() => new MetadataCache(), LazyThreadSafetyMode.ExecutionAndPublication);

public static MetadataCache Instance => s_lazy.Value;
```

`Lazy<T>`는 첫 접근 시점까지 초기화를 미루고, 스레드 안전성 모드를 명시적으로 선택하게 해 준다. 정적 생성자로 같은 것을 흉내 내면 **타입에 처음 접근하는 모든 경로**가 그 비용을 물게 되지만, `Lazy<T>`는 **그 필드를 실제로 읽는 경로**만 물게 된다.

### 초기화 수단 선택표

| 하고 싶은 것 | 쓸 것 |
|---|---|
| 모든 생성자에서 같은 값 | **필드 초기화자** |
| 0 / `null` / `default` | **아무것도 쓰지 않는다** (`CA1805`) |
| 생성자 인수에 따라 다른 값 | 생성자 본문 + 생성자 체이닝(79.6절) |
| 초기화 중 예외 복구 | 생성자 본문의 `try` |
| 단순한 정적 값 | **정적 필드 초기화자** |
| 복잡한 정적 초기화 / 예외 처리 | **정적 생성자** (`beforefieldinit` 상실을 감수) |
| 비싸고 드물게 쓰이는 정적 값 | **`Lazy<T>`** |
| 생성 후 절대 안 바뀌는 인스턴스 상태 | `readonly` 필드 또는 `init` 프로퍼티 |
| 호출자가 반드시 채워야 하는 값 | `required` 멤버 ※C# 11 (13.13절) |

> **💡 `readonly`는 최대한 붙여라 — 도구가 대신 붙여 준다**
>
> 생성자 밖에서 대입되지 않는 필드에는 `readonly`를 붙인다. 컴파일러가 실수로 인한 재대입을 막아 주고, 읽는 사람에게 "이 값은 객체 수명 동안 고정"이라는 정보를 준다. 코드 스타일 규칙 **IDE0044**("`readonly` 한정자 추가")가 후보를 전부 찾아 주며 자동 수정도 지원한다. 레거시 코드베이스에 처음 적용하면 놀랄 만큼 많이 걸린다.

## 79.6 중복 초기화 로직 제거

### 나쁜 예 — 공용 헬퍼 메서드

여러 생성자가 같은 일을 할 때 C++ 출신 개발자가 흔히 쓰는 방법이다.

```csharp
public class MyClass
{
    private List<ImportantData> _coll;
    private string _name;

    public MyClass() => CommonConstructor(0, "");
    public MyClass(int initialCount) => CommonConstructor(initialCount, "");
    public MyClass(int initialCount, string name) => CommonConstructor(initialCount, name);

    private void CommonConstructor(int count, string name)
    {
        _coll = (count > 0) ? new List<ImportantData>(count) : new List<ImportantData>();
        _name = name;
    }
}
```

**왜 나쁜가.** 소스는 중복이 없어 보이지만 **컴파일 결과에는 중복이 그대로 남는다.** 컴파일러는 모든 생성자 앞에 두 가지를 자동으로 삽입한다.

1. 모든 인스턴스 필드 초기화자
2. 기반 클래스 생성자 호출

즉 세 생성자 각각의 IL 앞부분에 **초기화자 코드 한 벌과 `base..ctor()` 호출이 따로따로** 들어간다. 생성자가 다섯 개면 다섯 벌이다. 그리고 결정적인 문제가 하나 더 있다.

```csharp
private readonly string _name;          // readonly로 바꾸면

private void CommonConstructor(int count, string name)
{
    _name = name;      // CS0191: readonly 필드는 생성자에서만 대입할 수 있다
}
```

**`readonly` 필드는 헬퍼 메서드에서 대입할 수 없다.** 컴파일러가 "생성자 본문"과 "생성자가 부른 메서드"를 구별하기 때문이다. 불변성을 포기하든지 헬퍼를 포기하든지 골라야 하는 상황이 된다.

### 좋은 예 — 생성자 체이닝

```csharp
public class MyClass
{
    private readonly List<ImportantData> _coll;
    private readonly string _name;

    public MyClass() : this(0, "") { }

    public MyClass(int initialCount) : this(initialCount, "") { }

    public MyClass(int initialCount, string name)
    {
        _coll = (initialCount > 0)
            ? new List<ImportantData>(initialCount)
            : new List<ImportantData>();
        _name = name;
    }
}
```

컴파일러는 `: this(...)`를 **특별한 문법으로 인식하고** 중복을 제거한다. 앞의 두 생성자는 IL에서 `this..ctor(...)` 호출 한 줄로 끝나고, **초기화자도 `base..ctor()` 호출도 체인의 마지막 생성자에만 들어간다.** 그리고 `readonly` 필드 대입이 정상적으로 허용된다 — 체인의 끝은 진짜 생성자이기 때문이다.

> **⚠️ `this(...)`와 `base(...)`는 함께 쓸 수 없다**
>
> 생성자 이니셜라이저는 생성자당 하나뿐이다. 같은 클래스의 다른 생성자로 위임하거나(`this`), 기반 클래스 생성자를 고르거나(`base`) 둘 중 하나다. 둘 다 하고 싶다면 체인의 **마지막** 생성자에서 `base(...)`를 지정하면 된다 — 어차피 기반 생성자는 거기서만 호출된다.

### 선택적 매개변수로 대신할 수 있는가

```csharp
public class MyClass
{
    private readonly List<ImportantData> _coll;
    private readonly string _name;

    // 제네릭 new() 제약을 만족시키기 위해 필요하다
    public MyClass() : this(0, "") { }

    public MyClass(int initialCount = 0, string name = "")
    {
        _coll = (initialCount > 0)
            ? new List<ImportantData>(initialCount)
            : new List<ImportantData>();
        _name = name;
    }
}
```

생성자 두 개로 네 가지 조합을 전부 표현한다. 매개변수가 늘어나면 오버로드는 조합 폭발을 일으키지만 기본값은 그렇지 않다. 다만 대가가 있다.

| | 오버로드 | 선택적 매개변수 |
|---|---|---|
| 조합 수 | 매개변수 수에 지수적으로 증가 | 생성자 하나 |
| 매개변수 **이름**이 계약인가 | 아니다 | **그렇다** (명명된 인수) |
| 기본값 변경 | 자유 | **호출자를 재컴파일해야 반영된다**(79.2절) |
| 리플렉션 기반 활성화 | 무매개변수 생성자가 있어야 함 | 기본값이 다 있어도 **무매개변수 생성자로 치지 않는다** |
| 제네릭 `new()` 제약 | 무매개변수 생성자가 있어야 함 | 위와 같음 |

> **⚠️ "모든 매개변수에 기본값이 있는 생성자"는 무매개변수 생성자가 아니다**
>
> `new MyClass()`라고 쓸 수는 있다 — 컴파일러가 호출 지점에 기본값을 채워 넣기 때문이다. 하지만 메타데이터에는 **매개변수 두 개짜리 생성자 하나**만 있다. 따라서 `Activator.CreateInstance<T>()`나 `where T : new()` 제약, 대부분의 DI 컨테이너와 직렬화기는 이 타입을 인스턴스화하지 못한다. 그래서 위 예제에 명시적 무매개변수 생성자를 남겨 뒀다. 자세한 트레이드오프는 78.4절에 있다.

> **📌 ※C# 12 기본 생성자는 이 문제의 지형을 바꾼다**
>
> ```csharp
> public class MyClass(int initialCount = 0, string name = "")
> {
>     private readonly List<ImportantData> _coll =
>         initialCount > 0 ? new List<ImportantData>(initialCount) : new();
>     private readonly string _name = name;
>
>     public MyClass() : this(0, "") { }
> }
> ```
>
> 기본 생성자의 매개변수는 **필드 초기화자에서 직접 쓸 수 있다.** 즉 "생성자 인수에 따라 다른 초기화"가 초기화자로 표현 가능해지므로 79.5절의 예외 2번이 상당 부분 사라진다. 다만 클래스에서는 기본 생성자 매개변수가 **캡처되어 숨은 필드가 될 수 있다**는 점에 주의하라 — 초기화자에서만 쓰면 필드가 생기지 않지만, 메서드 본문에서 쓰면 컴파일러가 필드를 만든다. 자세히는 13.10절에서 다룬다.

### 생성자에서 가상 함수를 호출하면 안 되는 이유

초기화 로직을 정리하다 보면 "공통 초기화를 가상 메서드로 빼서 파생 클래스가 확장하게 하자"는 발상이 자연스럽게 나온다. **하지 마라.** 이유를 실행 순서로 추적한다.

```csharp
class B
{
    protected B()
    {
        VFunc();
    }

    protected virtual void VFunc() => Console.WriteLine("VFunc in B");
}

class Derived : B
{
    private readonly string _msg = "초기화자가 설정한 값";

    public Derived(string msg)
    {
        _msg = msg;
    }

    protected override void VFunc() => Console.WriteLine(_msg);

    public static void Main()
    {
        var d = new Derived("Main에서 설정한 값");
    }
}
```

무엇이 출력되는가? 후보는 셋이다 — `"Main에서 설정한 값"`, `"VFunc in B"`, `"초기화자가 설정한 값"`. C++ 경험자는 두 번째를, C# 초심자는 첫 번째를 고른다. **정답은 세 번째다.**

79.5절의 순서표를 그대로 따라가 보자.

| 단계 | 실행되는 것 | 이 시점의 `_msg` |
|---|---|---|
| ⑤ | `Derived` 인스턴스 저장소를 0으로 채움 | `null` |
| ⑥ | `Derived`의 인스턴스 초기화자 실행 | **`"초기화자가 설정한 값"`** |
| ⑦ | `B()` 생성자 진입 | `"초기화자가 설정한 값"` |
| ⑦ 안 | `VFunc()` 호출 → **런타임 타입이 `Derived`이므로 `Derived.VFunc`가 실행된다** | `"초기화자가 설정한 값"` ← **여기서 출력** |
| ⑧ | `Derived(string)` 본문 실행 | `"Main에서 설정한 값"` |

**가상 디스패치는 객체가 완전히 만들어지기 전부터 작동한다.** C# 명세는 "모든 필드 초기화자가 실행되었으므로 객체를 사용 가능한 것으로 본다"고 결정했다. 그러나 실제로 초기화된 것은 **초기화자가 설정한 값뿐이고, 생성자 본문이 설정하는 값은 아직 아니다.**

여기서 `_msg`가 `readonly`라는 점이 특히 고약하다. 불변이어야 할 값이 객체 수명 중 **두 개의 서로 다른 값을 가진 순간**이 존재한다.

### 왜 C#은 이 규칙을 택했나

C++은 반대로 동작한다 — 생성자가 실행되는 동안 객체의 런타임 타입은 그 생성자가 속한 클래스이므로, `B`의 생성자에서 부른 `VFunc()`는 `B::VFunc`로 간다. 얼핏 더 안전해 보인다. 그러나 `B`가 추상 클래스이고 `VFunc`가 추상 멤버라면 C++에서는 **구현이 없는 함수를 부르게 되어 런타임에 크래시한다.** C#의 규칙(런타임 타입 기준 디스패치)에서는 언제나 파생 클래스의 구현이 존재하므로 최소한 크래시는 나지 않는다.

**어느 쪽을 골라도 생성 중 가상 호출은 일관성 없는 상태를 만든다.** 언어 설계자들은 "덜 나쁜 쪽"을 골랐을 뿐이다. 결론은 언어와 무관하게 같다 — **생성자에서 가상 함수를 부르지 마라.**

### 그럼에도 확장점이 필요하다면

1. **클래스를 `sealed`로 만든다.** 오버라이드가 불가능하면 문제도 없다.
2. **초기화 메서드를 비가상으로 만든다.** 확장점을 열지 않으면 된다.
3. **생성과 초기화를 분리하고 팩토리로 감싼다.**

```csharp
public class Widget
{
    protected Widget() { }
    protected virtual void OnInitialized() { }

    public static T Create<T>() where T : Widget, new()
    {
        var w = new T();
        w.OnInitialized();      // 생성이 완전히 끝난 뒤에 호출된다
        return w;
    }
}
```

방법 3이 가장 유연하지만 "생성자만 호출하면 객체가 완성된다"는 계약을 깨므로, 그 사실을 문서화하고 가능하면 생성자를 `protected`로 막아 팩토리를 통하게 강제하라.

> **⚠️ `required`와 `init`은 이 문제를 해결하지 못한다 — 오히려 악화시킨다**
>
> ```csharp
> class Derived : B
> {
>     public required string Msg { get; init; }
>     protected override void VFunc() => Console.WriteLine(Msg);   // null이다
> }
>
> var d = new Derived { Msg = "설정한 값" };
> ```
>
> 객체 초기화자 문법은 **생성자가 완전히 끝난 다음에** 실행된다. 즉 `init` 접근자가 값을 넣는 시점은 생성자보다도 늦다. 생성자 안에서 호출된 가상 함수가 보는 것은 여전히 `null`이다. `required`가 보장하는 것은 "호출자가 값을 넣도록 컴파일러가 강제한다"일 뿐, **언제 넣는지에 대한 보장이 아니다.**

> **📌 이 함정은 분석기가 잡아 준다**
>
> **`CA2214`**("생성자에서 재정의 가능한 메서드를 호출하지 마라")가 정확히 이 패턴을 보고한다. 가상 메서드뿐 아니라 가상 프로퍼티 접근과 가상 이벤트 접근자도 포함된다. 이 규칙은 켜 두는 것이 좋다 — 오탐이 거의 없고, 걸리는 코드는 대개 실제로 위험하다. 자세한 배경은 14.10절에 있다.

## 79.7 불필요한 객체 생성 회피

### 세 가지 기법

GC는 훌륭하지만, **할당하지 않은 객체를 수거하는 것보다 싼 일은 없다.** 이 절은 성능 최적화 장(69장)이 아니라 **코딩 습관** 장이다. 프로파일러를 켜기 전에 몸에 붙여 둘 만한 세 가지를 본다.

### 기법 1 — 자주 호출되는 메서드의 지역 참조 타입을 필드로 승격

```csharp
// 나쁜 예 — 다시 그릴 때마다 Font를 새로 만든다
protected override void OnPaint(PaintEventArgs e)
{
    using (Font myFont = new Font("Arial", 10.0f))
        e.Graphics.DrawString(DateTime.Now.ToString(), myFont, Brushes.Black, new PointF(0, 0));
    base.OnPaint(e);
}
```

**왜 나쁜가.** `OnPaint`는 초당 수십 번 호출된다. 매번 동일한 설정의 `Font` 객체가 만들어지고 곧바로 버려진다. GC가 실행 시점을 결정하는 기준 중 하나가 **할당량과 할당 빈도**이므로, 이런 코드는 GC를 필요 이상으로 자주 부른다.

```csharp
private readonly Font _font = new Font("Arial", 10.0f);      // 한 번만 만든다

protected override void OnPaint(PaintEventArgs e)
{
    e.Graphics.DrawString(DateTime.Now.ToString(), _font, Brushes.Black, new PointF(0, 0));
    base.OnPaint(e);
}
```

승격 조건은 두 가지다. **참조 타입일 것**(값 타입 지역 변수는 애초에 힙을 쓰지 않는다), 그리고 **자주 호출되는 경로일 것.** 1분에 한 번 호출되는 메서드의 지역 변수를 필드로 올리는 것은 이득 없이 클래스만 복잡하게 만든다.

> **⚠️ `IDisposable`을 필드로 올리면 클래스도 `IDisposable`이 되어야 한다**
>
> 위 예제의 `Font`는 `IDisposable`이다. 지역 변수일 때는 `using`이 정리해 줬지만 필드가 되면 그 책임이 클래스로 넘어온다. 정리하지 않으면 비관리 리소스(GDI 핸들)가 파이널라이저가 돌 때까지 살아 있다. 표준 Dispose 패턴 구현은 33.3절에서 다룬다. 분석기 규칙 **`CA1001`**("삭제 가능한 필드를 소유한 타입은 삭제 가능해야 한다")과 **`CA2213`**("삭제 가능한 필드는 삭제되어야 한다")이 이 실수를 잡는다.

### 기법 2 — 흔히 쓰는 인스턴스를 정적으로 공유

`Brushes.Black`이 정확히 이 기법이다. BCL은 색깔별 브러시를 정적 프로퍼티로 제공하고, 내부적으로는 **처음 요청될 때 만들어 캐시한다.** 프로그램 전체에서 검정 브러시는 하나만 만들어지고, 쓰이지 않는 색의 브러시는 아예 만들어지지 않는다.

BCL에는 이 목적의 준비된 인스턴스가 여럿 있다. **빈 컬렉션을 매번 새로 만드는 코드는 특히 흔한 낭비다.**

```csharp
public int[] GetResults() => new int[0];            // 호출마다 길이 0 배열을 할당한다
public int[] GetResults() => Array.Empty<int>();    // 타입마다 하나뿐인 캐시된 인스턴스
public IEnumerable<int> GetSequence() => Enumerable.Empty<int>();
```

분석기 규칙 **`CA1825`**("길이가 0인 배열 할당을 피하라")가 첫 번째 형태를 잡는다.

> **⚠️ 캐싱은 공짜가 아니다**
>
> 정적 캐시에 담긴 객체는 프로세스가 끝날 때까지 살아 있다. 즉 **Gen 2로 승격되어 영구히 GC의 검사 대상이 된다.** 그리고 비관리 리소스를 쥔 객체라면 `Dispose`를 부를 시점이 영영 오지 않는다. 캐시는 다음 조건을 만족할 때만 이득이다.
>
> - 객체가 **불변이거나 스레드 안전**하다 (공유되므로)
> - 객체가 **작다** (영구히 메모리를 점유하므로)
> - 재사용 빈도가 **높다**
>
> 셋 중 하나라도 어긋나면 매번 만드는 편이 낫다. 특히 **가변 객체를 정적 필드로 공유하는 것은 캐싱이 아니라 전역 변수**이며, 멀티스레드에서 재현 불가능한 버그의 원천이 된다.

### 기법 3 — 불변 타입에는 빌더를 붙인다

```csharp
// 나쁜 예 — 임시 문자열 세 개가 쓰레기가 된다
string msg = "안녕하세요, ";
msg += user.Name;
msg += ". 오늘은 ";
msg += DateTime.Now.ToString();
```

`string`은 불변이다. `+=`는 기존 문자열을 고치는 것이 아니라 **새 문자열을 만들고 옛것을 버린다.** 위 네 줄은 문자열 객체를 넷 만들고 그중 셋을 즉시 쓰레기로 버린다.

간단한 경우라면 보간 문자열이 답이다 — 조각 수를 컴파일러가 미리 알고 한 번에 만든다.

```csharp
string msg = $"안녕하세요, {user.Name}. 오늘은 {DateTime.Now}";
```

조립 로직이 복잡해서(반복문, 조건 분기) 보간으로 표현할 수 없다면 `StringBuilder`를 쓴다.

```csharp
var sb = new StringBuilder("안녕하세요, ");
sb.Append(user.Name).Append(". 오늘은 ").Append(DateTime.Now.ToString());
string finalMsg = sb.ToString();
```

여기서 배울 것은 `StringBuilder`라는 특정 클래스가 아니라 **설계 관용구**다. **불변 타입을 설계했다면 그것을 여러 단계에 걸쳐 조립할 가변 빌더도 함께 제공하라.** `ImmutableArray<T>.Builder`, `ImmutableDictionary<K,V>.Builder`가 BCL의 같은 패턴이다.

### 박싱 최소화 체크리스트

박싱은 "불필요한 객체 생성"의 가장 은밀한 형태다. `new`가 어디에도 보이지 않는데 힙 할당과 복사가 일어난다. 박싱의 IL과 힙 레이아웃은 54.6절에서, 할당 관점의 전수 목록은 63.9절에서 다뤘다. 여기서는 **코드를 쓰면서 눈으로 잡을 수 있는 형태**만 모은다.

| # | 이런 코드를 보면 | 왜 | 대신 |
|---|---|---|---|
| 1 | 값 타입을 `object` 매개변수에 넘긴다 | `object`로의 변환 = 박싱 | 제네릭 오버로드를 찾거나 `.ToString()`으로 미리 변환 |
| 2 | 값 타입을 비제네릭 컬렉션에 넣는다 (`ArrayList`, `Hashtable`) | 원소가 전부 `object` | `List<T>`, `Dictionary<K,V>` |
| 3 | 값 타입을 인터페이스 참조로 받는다 (`IComparable x = 3;`) | 인터페이스는 참조 타입 | 제네릭 + `where T : IComparable<T>` 제약 |
| 4 | 구조체에 `Equals`/`GetHashCode`를 재정의하지 않았다 | `ValueType.Equals`의 기본 구현이 박싱과 리플렉션을 쓸 수 있다 | `IEquatable<T>` 구현 + `Equals`/`GetHashCode` 재정의 (`CA1815`) |
| 5 | 구조체에 `ToString()`을 재정의하지 않았다 | `ValueType.ToString()` 호출 시 박싱된다 | 재정의하면 `constrained` 접두사로 박싱 없이 호출된다 |
| 6 | `params object[]`를 받는 메서드에 값 타입을 넘긴다 | 배열 할당 + 원소마다 박싱 | 제네릭 오버로드, 보간 핸들러 |
| 7 | 구조체 컬렉션을 `IEnumerable<T>`로 받아 `foreach` | 값 타입 열거자가 인터페이스로 박싱된다 | 구체 타입(`List<T>`)으로 받아 구조체 열거자를 그대로 쓴다 |
| 8 | `object`에 `null` 가능 값 타입을 대입한다 | `Nullable<T>`는 박싱 시 **내부 값만** 박싱되거나 `null`이 된다 | 의미를 알고 쓰거나 제네릭 유지 |
| 9 | `string.Format`이나 `Console.WriteLine(object)` | 매개변수 타입이 `object` | 보간 문자열(C# 10 이상) 또는 명시적 `.ToString()` |
| 10 | 열거형을 `object`로 다룬다 (딕셔너리 키, 로그 인수) | 열거형도 값 타입 | 제네릭 유지, 또는 기본 정수형으로 변환 |

> **⚠️ `Enum.HasFlag`의 박싱은 .NET Framework 전용 이야기다**
>
> 오래된 자료들이 `flags.HasFlag(MyEnum.A)` 대신 `(flags & MyEnum.A) != 0`을 쓰라고 권한다. **.NET Framework에서는 맞는 조언이다** — `HasFlag`의 시그니처가 `bool HasFlag(Enum value)`이므로 인수와 수신자가 모두 박싱된다.
>
> **.NET Core 2.1 이후로는 틀린 조언이다.** JIT이 `HasFlag` 호출을 인식해 비트 연산으로 직접 치환하며(인트린식), 박싱이 남지 않는다. 두 런타임을 함께 대상으로 하는 라이브러리라면 비트 연산을 쓰고, .NET만 대상으로 한다면 가독성이 좋은 `HasFlag`를 써도 된다. **성능 조언에는 유효 기간이 있다.**

> **💡 "불필요한"의 판단 기준은 언제나 측정이다**
>
> 이 절의 기법들은 **습관으로 붙여 둘 가치가 있는 것들**이다 — 비용이 없거나 거의 없기 때문이다. `Array.Empty<T>()`를 쓰는 것이 `new int[0]`보다 어렵지 않고, `readonly` 필드로 폰트를 올리는 것이 코드를 복잡하게 만들지 않는다.
>
> 그러나 여기서 한 발짝만 더 나가면 — 객체 풀, 구조체로의 전환, `stackalloc` — 코드의 복잡도가 급격히 오른다. **그 선을 넘기 전에는 반드시 프로파일러가 그 코드를 지목해야 한다**(67장). 할당을 줄이는 본격적인 기법은 69장에서 다룬다.

## 79.8 `new` 한정자는 기반 클래스 변경에 반응할 때만

### 나쁜 예

```csharp
public class MyClass
{
    public void MagicMethod() => Console.WriteLine("MyClass");
}

public class MyOtherClass : MyClass
{
    public new void MagicMethod() => Console.WriteLine("MyOtherClass");
}
```

```csharp
object c = MakeObject();                        // 실제 런타임 타입은 MyOtherClass
((MyClass)c).MagicMethod();                     // "MyClass"
((MyOtherClass)c).MagicMethod();                // "MyOtherClass"
```

**같은 객체에 같은 이름의 메서드를 불렀는데 결과가 다르다.**

**왜 나쁜가.** `new` 한정자는 **비가상 메서드를 가상으로 만들지 않는다.** 하는 일은 단 하나 — 파생 클래스의 이름 범위에 **별개의 메서드를 하나 더 추가하는 것**이다. 비가상 메서드는 정적으로 바인딩되므로, 어느 것이 호출될지는 **참조 변수의 컴파일 타임 타입**이 결정한다.

| 참조 변수의 선언 타입 | 실행되는 메서드 | IL |
|---|---|---|
| `MyClass` | `MyClass.MagicMethod` | `callvirt MyClass::MagicMethod` |
| `MyOtherClass` | `MyOtherClass.MagicMethod` | `callvirt MyOtherClass::MagicMethod` |
| `object` (캐스트 없이) | 컴파일 오류 | — |

객체의 정체가 아니라 **그 객체를 부르는 이름표**가 동작을 바꾼다. 이것은 다형성의 기본 기대를 정면으로 위반한다. 코드를 읽는 사람은 두 호출이 같은 일을 한다고 가정하고, 그 가정은 조용히 틀린다.

> **⚠️ `new`가 없어도 숨기기는 일어난다 — 경고만 나올 뿐이다**
>
> 파생 클래스에서 기반 클래스 멤버와 같은 이름·시그니처의 멤버를 선언하면, `new`를 쓰지 않아도 **숨기기는 일어나고** 컴파일러가 **CS0108** 경고를 낸다.
>
> ```text
> warning CS0108: 'MyOtherClass.MagicMethod()' hides inherited member
>                 'MyClass.MagicMethod()'. Use the new keyword if hiding was intended.
> ```
>
> 즉 `new`는 기능을 켜는 키워드가 아니라 **"의도한 것이다"라고 선언해 경고를 없애는 키워드**다. 이 경고를 `new`를 붙여 없애는 것이 습관이 되면, 진짜 사고인 경우와 의도한 경우를 구별할 수 없게 된다. **CS0108을 만나면 먼저 이름을 바꿀 수 있는지 검토하라.**

### `new`가 정당한 유일한 상황

당신이 라이브러리를 만들고 있다. 다른 회사의 `BaseWidget`을 상속했다.

```csharp
public class MyWidget : BaseWidget
{
    public void NormalizeValues() { /* ... */ }
}
```

출시했고 고객들이 쓰고 있다. 그런데 `BaseWidget`의 새 버전이 나왔고, 거기에 **같은 이름의 메서드가 추가되었다.**

```csharp
public class BaseWidget
{
    public void NormalizeValues() { /* ... */ }     // 새로 추가됨
}
```

이제 당신의 빌드에 CS0108 경고가 뜬다. 선택지는 둘이다.

```csharp
// 선택 1 — 이름을 바꾼다. 의미가 같다면 기반 구현도 호출한다
public class MyWidget : BaseWidget
{
    public void NormalizeAllValues() => base.NormalizeValues();
}

// 선택 2 — new를 붙여 "의도한 숨기기"임을 선언한다
public class MyWidget : BaseWidget
{
    public new void NormalizeValues() => base.NormalizeValues();
}
```

**모든 클라이언트 코드에 접근할 수 있다면 선택 1이 낫다.** 장기적으로 이름 충돌 자체가 사라지기 때문이다. 그러나 이미 세상에 배포한 API라면 이름을 바꾸는 순간 **모든 사용자의 코드가 깨진다**(78.13절의 소스 호환성 파괴). 이럴 때가 `new`를 쓸 자리다. 사용자들은 `MyWidget.NormalizeValues()`를 그대로 계속 쓰고, `BaseWidget.NormalizeValues()`는 애초에 존재하지 않았으므로 아무도 그것을 부르고 있지 않다.

**이것이 `new` 한정자를 써도 되는 유일한 상황이다.** 다른 모든 경우에는 설계 실수를 감추는 도구일 뿐이다.

> **⚠️ 시간이 지나면 이 해법도 문제로 돌아온다**
>
> 사용자들이 언젠가 `BaseWidget.NormalizeValues()`의 동작을 원하게 되면, 이름은 같은데 의미가 다른 두 메서드가 계층에 공존하는 원래의 문제로 돌아간다. `new`는 **이름을 바꿀 시간을 버는 도구**이지 영구적 해법이 아니다. 다음 메이저 버전에서 이름을 정리할 계획을 함께 세워라.

> **⚠️ `new virtual`은 새 가상 슬롯을 연다**
>
> ```csharp
> public class Base { public virtual void M() { } }
> public class Derived : Base { public new virtual void M() { } }
> public class Leaf : Derived { public override void M() { } }
> ```
>
> `Derived.M`은 IL 메타데이터에 **`newslot virtual`** 로 나타난다. 즉 `Base.M`과 완전히 별개의 가상 슬롯이 만들어지고, `Leaf.M`은 `Derived.M`만 재정의한다. `Base` 참조로 `Leaf` 인스턴스의 `M()`을 부르면 **`Base.M`이 실행된다.** 이 구조는 거의 언제나 사고이며, 의도적으로 쓸 이유가 실무에 사실상 없다.

> **📌 확장 메서드도 같은 방식으로 숨겨진다**
>
> 인스턴스 메서드는 언제나 확장 메서드보다 우선한다. 라이브러리가 나중에 당신의 확장 메서드와 같은 이름·시그니처의 인스턴스 메서드를 추가하면, **당신의 확장 메서드는 조용히 호출되지 않게 된다.** 경고조차 없다 — 컴파일러 입장에서는 그저 더 나은 후보를 찾은 것뿐이기 때문이다. `new`로 표시할 방법도 없다. 확장 메서드 이름을 지을 때 이 위험을 감안하라.

### 그렇다고 전부 `virtual`로 만들지는 마라

이 절의 결론이 "숨기지 말고 재정의하라"로 읽히면 곤란하다. 메서드를 `virtual`로 만드는 것은 **"파생 클래스가 이 동작을 바꿔도 된다"는 계약을 맺는 일**이다. 계약을 맺으면 되돌릴 수 없다(78.13절: `virtual` 제거는 파괴적 변경).

"기본적으로 전부 가상"이라는 설계는 유연해 보이지만 실제로는 **어떤 동작이 확장점인지 생각하지 않았다는 뜻**이다. C#이 `virtual`을 기본값으로 하지 않고 명시하게 만든 것은 의도적인 설계 결정이며, 그 배경은 78.14절에서 다룬다. **확장점은 많이가 아니라 정확히 열어야 한다.**

## 79.9 프로퍼티는 데이터처럼 동작해야 한다

### 프로퍼티는 두 개의 삶을 산다

밖에서 보면 수동적인 데이터 요소지만, 안에서는 메서드다. 이 이중성 때문에 **사용자는 데이터의 기대를 갖고 접근하는데 저자는 메서드의 자유를 행사하는** 불일치가 생긴다.

사용자가 프로퍼티에 대해 갖는 기대는 넷이다.

1. **연속해서 읽으면 같은 값이 나온다.** 중간에 아무것도 하지 않았다면.
2. **빠르다.** 루프 조건에 넣어도 된다.
3. **getter는 예외를 던지지 않는다.**
4. **getter는 관찰 가능한 부작용이 없다.**

이 기대는 근거가 있다. 배열을 순회하는 모든 `for` 루프가 `myArray.Length`를 매 반복 읽는다. 만약 `Length`가 원소를 세는 연산이었다면 모든 루프가 2차 시간이 되었을 것이고, 아무도 루프를 쓰지 않았을 것이다.

### 나쁜 예 — getter가 원격 호출을 한다

```csharp
public class MyType
{
    public string ObjectName => RetrieveNameFromRemoteDatabase();
}
```

**왜 나쁜가.**

- 루프 안에서 읽으면 반복마다 데이터베이스 왕복이 일어난다. 두 번 읽으면 다른 값이 나올 수도 있다.
- 네트워크 오류가 프로퍼티 접근 지점에서 예외로 터진다. 아무도 `x = obj.ObjectName;` 줄에 `try`를 감싸지 않는다.
- **디버거가 이 getter를 자동으로 호출한다.** 중단점에서 객체를 펼치기만 해도 데이터베이스에 접속하며, 서버가 죽어 있으면 디버깅 세션 자체가 이상해진다.

### 좋은 예 — 연산은 메서드 이름으로 드러낸다

```csharp
public class MyType
{
    public string ObjectName { get; set; }

    public void LoadFromDatabase() => ObjectName = RetrieveNameFromRemoteDatabase();
    public void SaveToDatabase()   => SaveNameToRemoteDatabase(ObjectName);
}
```

이제 프로퍼티는 객체 상태를 들여다보는 창일 뿐이고, 비싼 연산은 **동사로 된 메서드 이름**을 갖는다. 사용자는 `LoadFromDatabase()`가 시간이 걸리고 실패할 수 있다는 것을 이름에서 안다.

값을 캐시하고 싶다면 `Lazy<T>`가 그 목적으로 만들어져 있다.

```csharp
private readonly Lazy<string> _lazyObjectName;

public MyType() =>
    _lazyObjectName = new Lazy<string>(() => RetrieveNameFromRemoteDatabase());

public string ObjectName => _lazyObjectName.Value;
```

단 이것은 **첫 호출자만 대가를 치르고, 값이 바뀌지 않을 때** 타당하다. 다른 프로세스가 원격 저장소를 바꾸는 상황이라면 이 설계는 틀렸다.

### 계산은 얼마나 해도 되는가

간단한 계산은 기대를 깨지 않는다.

```csharp
public class Point
{
    public int X { get; set; }
    public int Y { get; set; }
    public double Distance => Math.Sqrt(X * X + Y * Y);
}
```

제곱근 하나는 "데이터 접근처럼 빠르다"는 기대 범위 안이다. 만약 이것이 병목으로 측정된다면 캐시할 수 있지만, **캐시를 넣는 순간 무효화 책임이 생긴다.**

```csharp
private int _x;
public int X
{
    get => _x;
    set { _x = value; _distance = null; }      // 값이 바뀌면 캐시를 버린다
}
// Y도 동일하게

private double? _distance;
public double Distance
{
    get { _distance ??= Math.Sqrt(X * X + Y * Y); return _distance.Value; }
}
```

무효화를 하나라도 빠뜨리면 조용히 틀린 값을 반환한다. **더 나은 답은 대개 `Point`를 불변으로 만드는 것이다** — 값이 바뀌지 않으면 무효화도 필요 없다.

### setter에도 같은 기대가 있다

```csharp
// 나쁜 예 — 대입 한 줄이 데이터베이스에 쓴다
public string ObjectName
{
    get { /* ... */ }
    set { _objectName = value; SaveNameToRemoteDatabase(_objectName); }
}
```

setter가 상태를 바꾸는 것은 당연하지만, **원격 호출을 하고 실패할 수 있다는 것은 아무도 예상하지 않는다.** 검증은 괜찮다 — 빠르고, 객체의 유효성을 지키며, 사용자가 기대하는 종류의 동작이다.

```csharp
public string LastName
{
    get => _lastName;
    set => _lastName = string.IsNullOrEmpty(value)
        ? throw new ArgumentException("성은 비어 있을 수 없다", nameof(value))
        : value;
}
```

### 자동 구현 프로퍼티를 기본값으로

```csharp
public string Name { get; set; }
```

컴파일러가 백킹 필드와 두 접근자를 만든다. 접근자가 대입 한 줄뿐이므로 **JIT이 거의 항상 인라인한다** — 필드 접근과 성능이 같아진다. 그리고 나중에 검증을 넣어야 할 때 **바이너리 호환을 유지한 채** 명시적 프로퍼티로 바꿀 수 있다.

**이것이 처음부터 공개 필드를 쓰지 말아야 할 이유다.** 필드를 프로퍼티로 바꾸는 것은 소스 호환이지만 **바이너리 파괴**다 — 필드 읽기는 `ldfld`이고 프로퍼티 읽기는 `call get_Name()`이라는 완전히 다른 명령이기 때문이다(78.13절). 나중에 바꾸면 되겠지 하는 전략은 통하지 않는다.

접근자별로 접근성을 다르게 줄 수 있다는 점도 자동 구현 프로퍼티의 이득이다.

```csharp
public string Name { get; protected set; }  // 파생 클래스만 설정
public string Kind { get; }                 // 생성자에서만 설정
public string Tag { get; init; }            // 객체 초기화자까지 설정 ※C# 9
```

> **⚠️ 자동 구현 프로퍼티의 백킹 필드 이름은 계약이 아니다**
>
> 컴파일러가 만드는 이름(`<Name>k__BackingField`)은 **버전 간 안정성이 보장되지 않는다.** 그래서 필드 이름에 의존하는 직렬화 방식 — 대표적으로 `[Serializable]` + `BinaryFormatter` — 과 자동 구현 프로퍼티는 함께 쓸 수 없다. 클래스를 조금만 고쳐도 저장된 데이터를 읽지 못하게 될 수 있다. 이런 타입에서는 명시적 백킹 필드를 두거나, 애초에 이름 기반 직렬화기(`System.Text.Json` 등)를 쓰라.

> **⚠️ 배열을 반환하는 프로퍼티는 둘 중 하나로 틀린다**
>
> ```csharp
> public int[] Values => _values;              // 내부 배열을 그대로 넘긴다 — 호출자가 고칠 수 있다
> public int[] Values => _values.ToArray();    // 읽을 때마다 배열을 복사한다 — 데이터처럼 싸지 않다
> ```
>
> 분석기 규칙 **`CA1819`**("프로퍼티는 배열을 반환하지 않아야 한다")가 이 형태를 지적한다. `IReadOnlyList<T>`, `ImmutableArray<T>`를 반환하거나, 복사가 필요하다는 사실을 드러내는 메서드(`ToArray()`)로 바꿔라. 내부 참조 노출 문제 전반은 78.5절에서 다뤘다.

> **⚠️ getter에서 예외를 던지지 마라**
>
> **`CA1065`**("예기치 않은 위치에서 예외를 발생시키지 마라")는 프로퍼티 getter, `Equals`, `GetHashCode`, `ToString`, 정적 생성자, `Dispose`, 같음 연산자, 암시적 변환 연산자에서 예외를 금지한다. 프로퍼티 getter의 예외는 두 가지 이유로 특히 나쁘다 — 호출자가 `try`를 감쌀 생각을 하지 않고, 디버거가 자동 호출하기 때문이다. 예외가 불가피하다면 그것은 프로퍼티가 아니라 메서드여야 한다는 신호다.

### 프로퍼티인가 메서드인가

| 이런 성질이면 | |
|---|---|
| 논리적으로 객체의 **속성**이다 | 프로퍼티 |
| 읽어도 상태가 안 바뀐다 | 프로퍼티 |
| 매번 같은 값을 준다 | 프로퍼티 |
| 필드 접근에 준하게 빠르다 | 프로퍼티 |
| 실패할 수 있다 | **메서드** |
| I/O·네트워크·파일 접근을 한다 | **메서드** |
| 호출할 때마다 다른 객체를 반환한다 | **메서드** |
| 매개변수가 필요하다 | 메서드 또는 인덱서 |
| 시간이 오래 걸린다 | **메서드** (비동기라면 반드시) |

> **📌 관련 분석기 규칙과 ※C# 14의 `field` 키워드**
>
> **`CA1024`**는 매개변수 없이 값만 반환하는 `GetXxx()` 메서드를 프로퍼티로 바꾸라고 권하고, **`CA1721`**은 `Name` 프로퍼티와 `GetName()` 메서드가 공존하는 혼란을 지적한다. **`CA2011`**은 setter 안에서 자기 프로퍼티에 대입하는 무한 재귀를, **`IDE0032`**는 수동으로 쓴 단순 프로퍼티를 자동 구현 프로퍼티로 바꿀 수 있음을 알려 준다.
>
> ※C# 14의 `field` 키워드는 백킹 필드를 선언하지 않고도 접근자 안에서 참조할 수 있게 해 준다(C# 13에서는 프리뷰였다 — 76.12절). 검증 하나 때문에 필드를 손으로 선언하던 관행이 줄어든다.
>
> ```csharp
> public string Name
> {
>     get => field;
>     set => field = value ?? throw new ArgumentNullException(nameof(value));
> }
> ```
>
> 자세한 문법은 13.8절에 있다.

## 79.10 익명 타입으로 타입 범위 제한하기

### 익명 타입의 정체

```csharp
var aPoint = new { X = 5, Y = 67 };
```

이 한 줄로 컴파일러에게 다음을 요구한 것이다 — **`internal sealed` 참조 타입**을 하나 만들고, **불변**으로 하고, 읽기 전용 프로퍼티 둘과 그 백킹 필드를 두라고.

컴파일러가 만드는 것은 대략 이런 모양이다.

```csharp
internal sealed class <>f__AnonymousType0<TX, TY>
{
    private readonly TX _x;   public TX X => _x;
    private readonly TY _y;   public TY Y => _y;

    public <>f__AnonymousType0(TX x, TY y) { _x = x; _y = y; }

    public override bool Equals(object obj) { /* 필드별 비교 */ }
    public override int GetHashCode() { /* 필드 기반 */ }
    public override string ToString() => $"{{ X = {_x}, Y = {_y} }}";
}
```

손으로 쓰는 것보다 컴파일러가 쓰는 편이 낫다. 더 빠르고, 매번 같은 코드를 생성하고, 유지보수할 코드가 줄어들며, 다른 개발자가 읽고 "이건 뭐지"를 고민할 대상이 하나 줄어든다.

객체 초기화자 문법을 쓰지만 실제 컴파일 결과는 생성자 호출이다.

```csharp
var aPoint = new { X = 5, Y = 67 };
// 실제로는
var aPoint = new <>f__AnonymousType0<int, int>(5, 67);
```

**이것은 익명 타입만의 특권이다.** 손으로 만든 불변 타입은 접근 가능한 setter가 없으므로 객체 초기화자 문법을 쓸 수 없다.

### 같은 타입으로 취급되는 조건

컴파일러는 익명 타입을 무한정 만들지 않는다. 다음을 모두 만족하면 **같은 타입을 재사용한다.**

- 같은 어셈블리 안이다
- 프로퍼티 **이름**이 같다
- 프로퍼티 **타입**이 같다
- 프로퍼티 **순서**가 같다

```csharp
var a = new { X = 5, Y = 67 };
var b = new { X = 16, Y = 12 };    // a와 같은 타입
var c = new { Y = 12, X = 16 };    // 다른 타입이다 — 순서가 다르다
```

같은 개념을 나타내는 익명 타입이라면 **프로퍼티 순서를 항상 같게 유지하라.** 그러지 않으면 타입이 늘어나고, 두 시퀀스를 `Union`이나 `Concat`으로 합치려 할 때 컴파일 오류를 만난다.

### 값 의미론 덕분에 복합 키가 된다

익명 타입은 `Equals`와 `GetHashCode`를 필드 기준으로 구현하므로 **딕셔너리 키와 그룹 키로 쓸 수 있다.**

```csharp
var query = from c in customers
            group c by new { c.SalesRep, c.ZipCode };
```

키가 "영업 담당자 + 우편번호" 쌍인 그룹이 만들어진다. 이 목적으로 전용 타입을 선언하고 `Equals`/`GetHashCode`를 구현하는 것에 비하면 압도적으로 간결하다.

### 한계 — 이름이 없다는 것의 대가

익명 타입은 **이름이 없으므로 메서드 매개변수 타입이나 반환 타입으로 쓸 수 없다.** 스코프가 선언된 메서드 안으로 제한된다. 이것이 단점이자 **동시에 이 관용구의 요점**이다 — 중간 결과를 담기 위해 애플리케이션의 네임스페이스를 오염시키지 않는다.

그 안에서 조작이 필요하면 **제네릭 메서드 + 람다**로 우회한다.

```csharp
static T Transform<T>(T element, Func<T, T> transformFunc) => transformFunc(element);

var aPoint = new { X = 5, Y = 67 };
var doubled = Transform(aPoint, p => new { X = p.X * 2, Y = p.Y * 2 });
```

`T`가 익명 타입으로 추론되므로 이름을 적지 않고도 함수를 적용할 수 있다.

### 익명 타입 · 튜플 · 레코드

| | 익명 타입 | `ValueTuple` | `record` / `record struct` |
|---|---|---|---|
| 종류 | 참조 타입 (`class`) | **값 타입** (`struct`) | 선택 가능 |
| 가변성 | **불변** | **가변** (public 필드) | 기본 불변(`init`) |
| 이름 | 없음 | 없음 (모양으로 식별) | **있다** |
| 타입 동일성 | **명목적** (이름 기준) | **구조적** (모양 기준) | 명목적 |
| 메서드 매개변수·반환 | **불가** | 가능 | 가능 |
| 어셈블리 경계 통과 | **불가** | 가능 | 가능 |
| 동등성 | 값 기준 (`Equals` 생성) | 값 기준 | 값 기준 |
| 딕셔너리 키 적합성 | **좋다** (불변) | 가능하나 가변이라 위험 | 좋다 |
| 할당 | 힙 | 스택 (또는 인라인) | 힙 / 스택 |
| 멤버 이름의 런타임 존재 | 프로퍼티로 실재 | **컴파일러가 추적** (`Item1`, `Item2`가 실체) | 실재 |

> **⚠️ 튜플의 요소 이름은 런타임에 존재하지 않는다**
>
> `(X: 5, Y: 67)`은 `System.ValueTuple<int, int>`의 인스턴스이고, 실제 필드 이름은 `Item1`, `Item2`다. `X`와 `Y`는 컴파일러가 추적하는 메타데이터일 뿐이며, 리플렉션으로 튜플 인스턴스를 들여다보면 나오지 않는다. **어떤 두 정수 튜플도 같은 타입이다** — 구조적 타이핑이기 때문이다. 자세한 것은 77.2절에 있다.

> **⚠️ 익명 타입은 어셈블리 경계를 넘지 못한다**
>
> 익명 타입은 `internal`이므로 다른 어셈블리에서 볼 수 없다. 그리고 `dynamic`으로 받아 넘기더라도 접근성 때문에 멤버를 읽을 수 없다. ASP.NET 계열에서 익명 타입을 뷰 모델로 넘기던 옛 코드가 곤란해지는 이유가 이것이다. **어셈블리를 넘어야 하면 익명 타입이 아니라 튜플이나 레코드다.**

> **💡 셋 중 무엇을 고를 것인가**
>
> - **메서드 안에서만 쓰는 중간 결과, 특히 LINQ 프로젝션** → 익명 타입
> - **딕셔너리·그룹의 복합 키** → 익명 타입 (불변이라 키로 안전하다)
> - **메서드에서 값 두세 개를 돌려주고 싶다** → 튜플
> - **이 개념에 이름을 붙일 만하고, 여러 곳에서 쓰인다** → 레코드
>
> 판단이 갈리는 지점은 "이 묶음에 이름이 필요한가"이다. 이름을 붙이려고 30초 이상 고민했다면 그것은 대개 이름이 필요한 개념이고, 레코드로 승격할 때다.

> **📌 프로젝션에서 이름을 생략할 수 있다**
>
> ```csharp
> var q = customers.Select(c => new { c.Name, c.City });     // X = c.Name 이라고 안 써도 된다
> ```
>
> 멤버 접근식이나 변수 이름을 그대로 쓰면 프로퍼티 이름이 추론된다. 코드 스타일 규칙 **IDE0037**("추론된 멤버 이름 사용")이 중복 표기를 지적한다. 익명 타입은 언제나 힙에 할당되므로, 아주 뜨거운 루프에서 프로젝션을 반복한다면 그 자체가 할당의 원천임을 기억하라(63.9절).

## 79.11 반복자 메서드 · 쿼리 구문 · 지연 평가 선호

### 나쁜 예 — 컬렉션을 만들어 반환한다

```csharp
static IList<int> CreateSequence(int numberOfElements, int startAt, int stepBy)
{
    var collection = new List<int>(numberOfElements);
    for (int i = 0; i < numberOfElements; i++)
        collection.Add(startAt + i * stepBy);
    return collection;
}
```

**왜 나쁜가.** 네 가지다.

1. **저장 구조를 강요한다.** 호출자가 `BindingList<int>`를 원하면 다시 옮겨 담아야 한다.
2. **중단할 수 없다.** 호출자가 앞의 10개만 필요해도 `numberOfElements`개를 전부 만든다.
3. **파이프라인의 병목이 된다.** 뒤 단계가 시작되기 전에 모든 원소가 만들어져야 한다.
4. **전체를 저장할 메모리가 필요하다.** 원소가 많으면 그대로 비용이다.

### 좋은 예 — 반복자 메서드

```csharp
static IEnumerable<int> CreateSequence(int numberOfElements, int startAt, int stepBy)
{
    for (int i = 0; i < numberOfElements; i++)
        yield return startAt + i * stepBy;
}
```

핵심 로직은 같지만 실행 방식이 완전히 달라졌다. 컴파일러는 `yield return`을 만나면 **`IEnumerable<T>`와 `IEnumerator<T>`를 구현하는 상태 기계 클래스**를 생성한다(28.4절). 메서드를 호출하면 그 객체가 만들어질 뿐 **본문은 한 줄도 실행되지 않는다.** 실제 코드는 `MoveNext()`가 불릴 때마다 조금씩 실행된다.

그 결과 위의 네 문제가 전부 사라진다.

```csharp
var list  = new List<int>(CreateSequence(100, 0, 5));          // 호출자가 저장 구조를 고른다
var array = CreateSequence(100, 0, 5).ToArray();
var bound = new BindingList<int>(CreateSequence(100, 0, 5).ToList());

var seq = CreateSequence(10000, 0, 7).TakeWhile(n => n < 1000); // 1000을 넘으면 생성이 멈춘다
```

**저장할지 말지는 호출자가 결정하게 하라.** 시퀀스를 반환하면 두 경우를 모두 지원하지만, 컬렉션을 반환하면 지연 생성 시나리오는 영원히 불가능해진다. 내부적으로 캐시가 이득이라고 **측정되면** 그때 내부에서만 캐시하면 된다.

`Enumerable.Range(0, int.MaxValue)`가 즉시 반환되는 것도 같은 원리다. 21억 개의 정수를 저장하지 않는다.

### 지연 평가의 다른 얼굴 — 두 번 열거하면 두 번 실행된다

```csharp
static IEnumerable<T> Generate<T>(int n, Func<T> gen)
{
    for (int i = 0; i < n; i++) yield return gen();
}

var sequence = Generate(10, () => DateTime.Now);
foreach (var v in sequence) Console.WriteLine($"{v:T}");
Console.ReadLine();                                      // 잠시 기다린다
foreach (var v in sequence) Console.WriteLine($"{v:T}");
```

두 루프의 출력 시각이 **다르다.** `sequence` 변수가 담고 있는 것은 원소가 아니라 **원소를 만드는 방법**이기 때문이다. 이것이 지연 평가(lazy evaluation)이고, 대개 원하는 동작이다 — 매번 새로운 결과를 얻는다.

원하지 않는다면 그 시점의 스냅숏을 명시적으로 만든다.

```csharp
var snapshot = sequence.ToList();     // 지금 전부 실행하고 저장한다
```

> **⚠️ 두 번 열거는 두 배의 비용이다 — 데이터베이스라면 왕복도 두 번이다**
>
> ```csharp
> var orders = db.Orders.Where(o => o.Total > 1000);
>
> if (orders.Any())                      // 쿼리 1회
>     foreach (var o in orders) { }      // 쿼리 2회
> ```
>
> 지연 평가의 함정 중 실무에서 가장 자주 물리는 형태다. `IEnumerable<T>` 매개변수를 받는 메서드가 그것을 두 번 순회하는 것도 같은 문제이며, 소스가 한 번만 열거 가능한 시퀀스(네트워크 스트림 등)라면 두 번째 순회는 **예외 또는 빈 결과**가 된다. 여러 번 쓸 것이 확실하면 메서드 진입부에서 `ToList()`로 고정하라.

### 어떤 연산자가 전체 시퀀스를 요구하는가

```csharp
// 무한 시퀀스여도 즉시 끝난다 — Take는 앞의 10개만 요구한다
var answers = AllNumbers().Take(10);

// 영원히 끝나지 않는다 — where는 전체를 검사해야 한다
var answers = from n in AllNumbers() where n < 10 select n;
```

| 스트리밍 (원소 단위로 흘려보낸다) | 버퍼링 (전체를 봐야 한다) |
|---|---|
| `Where`, `Select`, `SelectMany` | `OrderBy`, `OrderByDescending`, `ThenBy` |
| `Take`, `TakeWhile`, `Skip`, `SkipWhile` | `Reverse`, `GroupBy`, `Join`, `GroupJoin` |
| `Concat`, `Zip`, `Cast`, `OfType` | `ToList`, `ToArray`, `ToDictionary`, `ToHashSet` |
| `Distinct`\*, `Union`\* | `Count`, `Sum`, `Max`, `Min`, `Average`, `Aggregate` |
| `First`, `FirstOrDefault`, `Any` | `Last`, `LastOrDefault`, `All`, `Single` |

\* `Distinct`와 `Union`은 결과를 하나씩 내보내지만 이미 본 원소를 전부 기억하므로 메모리는 누적된다.

`Where`가 양쪽에 걸쳐 있는 것처럼 보이는 이유가 있다. **결과를 하나씩 내보낸다는 점에서는 스트리밍이지만, "조건에 맞는 것이 더 있는가"를 알려면 남은 원소를 계속 검사해야 하므로** 무한 시퀀스에서 끝나지 않는다. 무한 시퀀스에 안전한 것은 **개수를 스스로 정하는** 연산자(`Take`, `First`, `Any`)뿐이다.

### 필터를 앞으로 옮겨라

```csharp
// 느리다 — 전부 정렬한 다음 대부분을 버린다
var slow = from p in products
           orderby p.UnitsInStock descending
           where p.UnitsInStock > 100
           select p;

// 빠르다 — 걸러낸 다음 남은 것만 정렬한다
var fast = from p in products
           where p.UnitsInStock > 100
           orderby p.UnitsInStock descending
           select p;
```

LINQ to Objects(`System.Linq.Enumerable`)는 쿼리를 재배치하지 않는다. 적힌 순서대로 실행한다. **버퍼링 연산자는 가능한 한 뒤로, 필터는 앞으로.** 반면 데이터베이스 공급자는 식 트리를 받아 자체 최적화기를 돌리므로 둘의 성능이 같을 수 있다 — 그러나 순서를 바로잡아 손해 볼 일은 없다.

### 인수 검증은 즉시, 생성은 지연

지연 실행에는 대가가 있다. **반복자 메서드의 본문은 첫 `MoveNext()`까지 실행되지 않으므로, 인수 검증도 그때까지 미뤄진다.**

```csharp
// 나쁜 예 — 예외가 호출 지점이 아니라 열거 지점에서 난다
public static IEnumerable<char> GenerateSubset(char first, char last)
{
    if (first < 'a') throw new ArgumentException("...", nameof(first));
    for (var c = first; c <= last; c++) yield return c;
}
```

`GenerateSubset('Z', 'a')`를 불러도 예외가 나지 않는다. 반환된 시퀀스를 처음 순회하는 **다른 곳**에서 난다. 스택 추적이 실수한 지점을 가리키지 않는다.

```csharp
// 좋은 예 — 검사하는 메서드와 생성하는 메서드를 분리한다
public static IEnumerable<char> GenerateSubset(char first, char last)
{
    if (first < 'a') throw new ArgumentException("...", nameof(first));
    if (last < first) throw new ArgumentException("...", nameof(last));

    return Impl(first, last);

    static IEnumerable<char> Impl(char first, char last)
    {
        for (var c = first; c <= last; c++)
            yield return c;
    }
}
```

바깥 메서드에는 `yield`가 없으므로 **평범한 메서드로 컴파일되어 즉시 실행된다.** 반복자 부분만 지역 함수로 분리했다. 비동기 메서드도 같은 구조가 필요하며, 자세한 것은 78.12절에 있다.

> **⚠️ 반복자 메서드에는 `ref`/`out`/`in` 매개변수를 쓸 수 없다**
>
> 상태 기계 클래스가 매개변수를 필드로 복사해 보관해야 하는데, 참조 매개변수는 필드가 될 수 없기 때문이다. 같은 이유로 `ref struct` 타입 매개변수도 쓸 수 없다. 반복자로 바꾸려던 메서드가 컴파일되지 않는다면 시그니처부터 확인하라.

> **⚠️ 지연 평가 + 가변 소스 = 예측 불가**
>
> 쿼리를 정의한 뒤 소스 컬렉션을 수정하고 나서 열거하면, **수정된 내용이 반영된다.** 그리고 열거 도중에 소스를 수정하면 대부분의 BCL 컬렉션이 `InvalidOperationException`("컬렉션이 수정되었습니다")을 던진다. 쿼리를 변수에 담아 여기저기 넘기는 코드에서는 소스가 그동안 무엇을 겪는지 알 수 없다. 경계를 넘겨야 한다면 `ToList()`로 고정해서 넘기는 편이 안전하다.

> **💡 쿼리 구문과 메서드 구문은 취향 문제가 아니다**
>
> 쿼리 구문(`from ... where ... select`)이 확실히 유리한 경우가 있다.
>
> - `join`, `group by`, `let`, 다중 `from` — 메서드 구문으로 쓰면 중첩 람다와 임시 익명 타입 때문에 읽기 어려워진다.
>
> 반대로 메서드 구문만 가능한 것도 있다.
>
> - `Take`, `Skip`, `Aggregate`, `Distinct`, `First`, `Any` 등 — 쿼리 구문에 대응 키워드가 없다.
>
> 실무의 결론은 **섞어 쓰는 것**이다. 쿼리 구문으로 뼈대를 잡고 괄호로 감싼 뒤 메서드를 이어 붙이면 된다. "무조건 하나만"이라는 팀 규칙은 대개 코드를 나쁘게 만든다.

## 79.12 비싼 리소스를 클로저에 가두지 말 것

### 캡처된 변수의 수명은 스코프를 따르지 않는다

지역 변수는 블록이 끝나면 수집 대상이 된다 — 우리가 자원 수명을 관리할 때 쓰는 기본 가정이다. **클로저는 이 가정을 깬다.**

```csharp
// Generate 는 79.11절의 것과 같은 사용자 정의 생성기 메서드다
var counter = 0;
var numbers = Extensions.Generate(30, () => counter++);
```

컴파일러는 `counter`를 필드로 갖는 **디스플레이 클래스**를 만들고, 람다를 그 클래스의 인스턴스 메서드로 바꾼다(26.10절).

```csharp
private sealed class Closure
{
    public int generatedCounter;
    public int generatorFunc() => generatedCounter++;
}
```

`counter`는 더 이상 지역 변수가 아니라 **힙에 있는 객체의 필드**다. 이 시퀀스를 메서드 밖으로 반환하면 델리게이트가 살아 있는 한 `Closure` 인스턴스도 살아 있고, 그 안의 모든 필드도 살아 있다. **캡처된 변수가 메모리만 붙들고 있다면 문제가 없다.** 문제는 그것이 파일 핸들이나 데이터베이스 연결일 때다.

### 나쁜 예 — `using`으로 감쌌는데 예외가 난다

```csharp
// ReadLines()와 DefaultParse()는 이 예제를 위해 직접 만든 확장 메서드다
public static IEnumerable<IEnumerable<int>> ReadNumbersFromStream(TextReader t)
{
    var allLines = from line in t.ReadLines() select line.Split(',');
    var matrix   = from line in allLines select from item in line select item.DefaultParse(0);
    return matrix;
}
```

리소스를 닫으라는 코드 리뷰 지적을 받고 이렇게 고쳤다.

```csharp
IEnumerable<IEnumerable<int>> rows;
using (TextReader t = new StreamReader(File.OpenRead("TestFile.txt")))
    rows = ReadNumbersFromStream(t);

foreach (var line in rows)                     // ObjectDisposedException
    foreach (int num in line)
        Console.Write($"{num}, ");
```

**왜 나쁜가.** `using` 블록 안에서는 **아무 파일도 읽지 않았다.** 쿼리는 "무엇을 할지"만 기술했을 뿐이고, `TextReader`는 클로저에 캡처된 채로 대기 중이다. `using`을 빠져나가며 스트림이 닫히고, 그다음 `foreach`가 실제로 읽으려는 순간 이미 닫힌 스트림에 접근한다.

### 세 가지 해법

**해법 1 — 리소스가 살아 있는 동안 소비한다.**

```csharp
using (TextReader t = new StreamReader(File.OpenRead("TestFile.txt")))
    foreach (var line in ReadNumbersFromStream(t))
        foreach (var num in line) Console.Write($"{num}, ");
```

단순하지만 이 코드가 여러 곳에 필요하면 중복이 생긴다. 그리고 `using (...) return ReadNumbersFromStream(t);` 형태로 이미 배포된 API라면 **닫을 자리가 아예 없다.**

**해법 2 — 획득과 해제를 반복자 안으로 넣는다.**

```csharp
public static IEnumerable<string> ParseFile(string path)
{
    using var r = new StreamReader(File.OpenRead(path));
    var line = r.ReadLine();
    while (line != null)
    {
        yield return line;
        line = r.ReadLine();
    }
}
```

상태 기계의 `Dispose()`가 `finally` 블록을 실행하므로, **열거가 끝나거나 중간에 중단되어도** 스트림이 닫힌다(28.5절). 호출자는 리소스의 존재조차 몰라도 된다.

**해법 3 — 알고리즘을 델리게이트로 주입한다.**

```csharp
public static TResult ProcessFile<TResult>(string path, Func<IEnumerable<string>, TResult> action)
{
    using (TextReader t = new StreamReader(File.OpenRead(path)))
        return action(t.ReadLines());
}

// 사용
var maximum = ProcessFile("testFile.txt", lines => lines.Select(l => l.Length).Max());
```

리소스가 메서드 안에서 열리고 닫히므로 클로저에 실려 나갈 것이 없다. 같은 파일을 여러 방식으로 처리해야 할 때 가장 잘 맞는다.

> **⚠️ 해법 2는 두 번 열거하면 두 번 Dispose된다**
>
> ```csharp
> var query = ParseFile("data.txt").Take(5);
> foreach (var s in query) { }      // 여기서 파일이 닫힌다
> foreach (var s in query) { }      // 다시 열린다 — ParseFile 이 처음부터 다시 실행된다
> ```
>
> `ParseFile` 자체는 매번 새 `StreamReader`를 만들므로 이 경우는 동작한다. 그러나 **이미 열린 스트림을 캡처한 형태**(나쁜 예의 `ReadNumbersFromStream`)라면 두 번째 열거가 `ObjectDisposedException`으로 죽는다. 여러 번 열거할 계획이 있다면 해법 3을 쓰거나 결과를 `ToList()`로 고정하라.

### 클로저는 스코프 단위로 뭉친다

더 은밀한 문제가 있다.

```csharp
private static IEnumerable<int> LeakingClosure()
{
    var filter  = new ResourceHogFilter();          // 비싼 리소스
    var source  = new CheapNumberGenerator();
    var results = new CheapNumberGenerator();

    var stat = (from num in source.GetNumbers(50)
                where filter.PassesFilter(num)
                select num).Average();

    return from num in results.GetNumbers(100)
           where num > stat
           select num;
}
```

`filter`는 메서드 지역 변수이고 메서드가 끝나면 사라질 것처럼 보인다. **아니다.**

컴파일러는 **하나의 스코프에서 캡처된 모든 변수를 하나의 디스플레이 클래스에 모은다.** `filter`(첫 쿼리의 `where`가 캡처)와 `stat`(둘째 쿼리의 `where`가 캡처)이 같은 메서드 본문 스코프에 있으므로 **같은 클래스의 필드**가 된다. 반환된 시퀀스는 둘째 `where` 델리게이트를 붙들고 있고, 그 델리게이트는 디스플레이 클래스 인스턴스를 붙들고 있으며, 그 안에는 `filter`도 들어 있다.

**해법은 스코프를 나누는 것이다** — 즉 메서드를 쪼갠다.

```csharp
private static IEnumerable<int> NotLeakingClosure()
{
    var stat = GenerateStatistic();                 // filter는 이 메서드 안에서 끝난다
    var results = new CheapNumberGenerator();

    return from num in results.GetNumbers(100)
           where num > stat
           select num;
}

private static double GenerateStatistic()
{
    var filter = new ResourceHogFilter();
    var source = new CheapNumberGenerator();

    return (from num in source.GetNumbers(50)
            where filter.PassesFilter(num)
            select num).Average();
}
```

`Average()`는 전체 시퀀스를 요구하는 버퍼링 연산자이므로(79.11절) **열거가 `GenerateStatistic` 안에서 완료된다.** 반환되는 것은 `double` 값 하나이고, `filter`를 담은 디스플레이 클래스는 메서드가 끝나는 즉시 도달 불가능해진다.

> **💡 캡처 자체를 금지하는 방법이 있다**
>
> ※C# 9의 `static` 람다는 **바깥 변수를 캡처하려 하면 컴파일 오류를 낸다.**
>
> ```csharp
> var results = source.Where(static n => n > 0);      // 지역 변수를 캡처하면 컴파일 오류
> ```
>
> 뜨거운 경로의 람다에 `static`을 붙여 두면 나중에 누군가 실수로 지역 변수를 참조했을 때 **컴파일 단계에서 막힌다.** 성능뿐 아니라 수명 관리 측면에서도 가치가 있다.

### 관련 관용구 — 콜백과 이벤트 호출

클로저와 델리게이트를 다루는 김에, 같은 뿌리를 가진 두 관용구를 정리한다.

**콜백은 델리게이트로 표현한다.** 인터페이스보다 결합이 느슨하고, 대상을 런타임에 구성할 수 있으며, 람다라는 간결한 문법이 준비되어 있다. `Predicate<T>`, `Func<>`, `Action<>`이 표준 형태다. 다만 **모든 델리게이트는 멀티캐스트**라는 사실에서 두 가지 함정이 나온다 — **예외가 나면 체인이 거기서 끊겨** 뒤의 대상이 호출되지 않고, **반환값은 마지막 대상의 것만 남는다.** 둘 다 중요하면 직접 순회한다.

```csharp
bool keepGoing = true;
foreach (Func<bool> pr in shouldContinue.GetInvocationList())
    keepGoing &= pr();          // 모든 대상의 반환값을 합산한다
```

**이벤트 호출은 `?.Invoke`로 한다.** 예전에는 `var handler = Updated;`로 얕은 복사를 뜬 뒤 `null`을 검사하는 관용구를 썼다. 동작은 하지만 왜 스레드 안전한지가 코드에 드러나지 않고, 이벤트를 발생시키는 모든 자리에 복제해야 했다.

```csharp
Updated?.Invoke(this, counter);
```

`?.`는 **왼쪽을 정확히 한 번만 평가하고** `null`이 아닐 때만 오른쪽을 실행하므로, 옛 관용구와 의미가 같으면서 한 줄이다. 괄호를 `?.` 바로 뒤에 쓸 수 없어 `Invoke`를 명시해야 하는데, 이것은 컴파일러가 델리게이트마다 생성하는 타입 안전한 메서드이므로 직접 호출과 완전히 같은 코드다. 자세한 것은 27.5절에 있다.

> **⚠️ 이벤트 구독은 게시자가 구독자를 붙드는 관계다**
>
> 클로저가 리소스를 붙드는 것과 정확히 같은 구조로, **이벤트에 핸들러를 등록하면 게시자가 구독자에 대한 참조를 갖게 된다.** 게시자가 오래 사는 객체(정적 이벤트, 애플리케이션 수명 서비스)이고 구독자가 짧게 살아야 할 객체(화면, 뷰 모델)라면 구독자는 절대 수집되지 않는다. 구독한 곳에서 반드시 해제하거나 약한 이벤트 패턴을 쓴다(27.6절, 27.7절).

## 79.13 코드 분석기와 `.editorconfig`로 관용구 강제하기

### 왜 코드 리뷰로는 안 되는가

앞의 열두 절은 전부 "이렇게 쓰는 편이 낫다"는 판단이다. 판단을 팀 전체의 습관으로 만드는 방법은 두 가지뿐이다 — 사람이 리뷰에서 지적하거나, 도구가 빌드를 실패시키거나.

리뷰는 다음 이유로 실패한다.

- **확장되지 않는다.** 리뷰어의 주의력을 `var` 사용법 같은 기계적 사항에 쓰는 것은 낭비다.
- **일관성이 없다.** 같은 코드가 리뷰어에 따라, 요일에 따라 다르게 통과한다.
- **늦게 도착하고 논쟁이 반복된다.** 코드를 다 쓴 뒤에 듣는 지적은 편집기의 밑줄보다 훨씬 비싸고, 새 사람이 올 때마다 같은 토론이 처음부터 시작된다.

도구는 이 넷을 전부 해결한다. **관용구에 대한 합의는 한 번 하고, 그 합의를 `.editorconfig`에 적고, 그 파일을 리뷰한다.** 그 뒤로 개별 PR에서는 아무도 그 이야기를 하지 않는다.

### 분석기의 정체와 규칙 계열

.NET 분석기는 **Roslyn 컴파일 파이프라인 안에서 실행되는 코드**다. 컴파일러가 만든 구문 트리와 의미 모델을 그대로 받아 검사하고, 진단(ID·범주·심각도·위치)을 내놓는다. 일부는 코드 수정(code fix)까지 제공한다. 별도 실행 단계가 아니라 컴파일의 일부이므로 **IDE에서 타이핑하는 동안과 CI에서 빌드하는 동안 똑같이 작동한다.**

| 접두사 | 무엇 | 어디서 오는가 |
|---|---|---|
| `CS` | 컴파일러 자체의 오류·경고 | Roslyn 컴파일러 |
| `CA` | **코드 품질** 규칙 | .NET SDK 내장 (`Microsoft.CodeAnalysis.NetAnalyzers`) |
| `IDE` | **코드 스타일** 규칙 | .NET SDK 내장 |
| `RS` | 분석기 개발·공개 API 추적 | `Roslyn.Analyzers`, `PublicApiAnalyzers`(78.13절) |
| `SA` / `SX` | 서식·명명 규칙 | StyleCop.Analyzers (서드파티) |

이 장의 관용구는 대부분 `CA`와 `IDE`로 표현할 수 있다.

### 심각도 네 단계

`.editorconfig`에서 규칙 하나에 줄 수 있는 값은 여섯 개이고, 그중 **실제로 무언가를 표시하는 단계는 넷**이다.

| 값 | 빌드 | 편집기 | 쓰는 자리 |
|---|---|---|---|
| `error` | **실패한다** | 빨간 물결선 | 절대 어기면 안 되는 규칙 |
| `warning` | 경고 (`TreatWarningsAsErrors`면 실패) | 초록 물결선 | 대부분의 규칙의 기본 자리 |
| `suggestion` | 아무 일 없음 | 회색 점선 + 전구 | 권장하지만 강제하지 않는 것 |
| `silent` | 아무 일 없음 | 표시 없음 (리팩터링 메뉴에는 나타남) | 자동 수정만 제공하고 싶을 때 |
| `none` | 규칙을 **끈다** | 표시 없음 | 이 팀에 맞지 않는 규칙 |
| `default` | 규칙 저자가 정한 기본값 | | 명시적으로 기본으로 되돌릴 때 |

`silent`와 `none`의 차이가 헷갈리기 쉽다. **`silent`는 규칙이 돌아가되 표시하지 않는 것**이라 "빠른 작업" 메뉴에서 수정을 고를 수 있고, **`none`은 아예 실행되지 않는다.**

### `.editorconfig` 실전 예제

솔루션 루트에 하나를 두고 필요한 하위 디렉터리에서 덮어쓴다.

```ini
# 이 파일이 최상위다. 위로 더 올라가지 않는다
root = true

# ─────────────────────────────────────────────
[*]
indent_style = space
insert_final_newline = true
charset = utf-8-bom
trim_trailing_whitespace = true

# ─────────────────────────────────────────────
[*.{cs,csx}]
indent_size = 4
end_of_line = crlf

#### 언어 스타일 — 79.1절 ####
csharp_style_var_for_built_in_types = false:warning
csharp_style_var_when_type_is_apparent = true:suggestion
csharp_style_var_elsewhere = true:silent

#### 언어 스타일 — 79.3절, 패턴 매칭 ####
csharp_style_pattern_matching_over_as_with_null_check = true:warning
csharp_style_pattern_matching_over_is_with_cast_check = true:warning
csharp_style_prefer_not_pattern = true:suggestion

#### 언어 스타일 — null 관련 ####
dotnet_style_null_propagation = true:warning
dotnet_style_coalesce_expression = true:warning

#### 언어 스타일 — 79.5절 ####
dotnet_style_readonly_field = true:warning
dotnet_style_object_initializer = true:suggestion
csharp_style_prefer_primary_constructors = true:suggestion

#### 언어 스타일 — 기타 ####
csharp_style_namespace_declarations = file_scoped:warning
csharp_style_expression_bodied_properties = when_on_single_line:suggestion
dotnet_style_prefer_inferred_tuple_names = true:suggestion
dotnet_style_prefer_inferred_anonymous_type_member_names = true:suggestion

#### 코드 품질 규칙 — 이 장의 각 절에 대응 ####
dotnet_diagnostic.CA1805.severity = warning   # 79.5 기본값으로 초기화하지 마라
dotnet_diagnostic.CA1810.severity = warning   # 79.5 정적 필드를 인라인으로 초기화하라
dotnet_diagnostic.CA2214.severity = error     # 79.6 생성자에서 가상 호출 금지
dotnet_diagnostic.CA1825.severity = warning   # 79.7 길이 0 배열 할당 금지
dotnet_diagnostic.CA1815.severity = warning   # 79.7 구조체의 Equals/== 재정의
dotnet_diagnostic.CA1065.severity = warning   # 79.9 getter에서 예외 금지
dotnet_diagnostic.CA1819.severity = warning   # 79.9 프로퍼티가 배열을 반환하지 않게
dotnet_diagnostic.CA2211.severity = error     # 비상수 정적 필드는 public 금지
dotnet_diagnostic.CA2241.severity = error     # 79.4 형식 문자열 인수 불일치
dotnet_diagnostic.CA1507.severity = warning   # 79.4 문자열 리터럴 대신 nameof
dotnet_diagnostic.CA1305.severity = warning   # 79.4 IFormatProvider 지정
dotnet_diagnostic.CA1001.severity = error     # 79.7 disposable 필드를 가진 타입
dotnet_diagnostic.CA2213.severity = warning   # 79.7 disposable 필드를 dispose 하라
dotnet_diagnostic.CA1822.severity = suggestion  # 인스턴스 상태를 안 쓰면 static 으로
dotnet_diagnostic.CA1852.severity = warning     # 상속되지 않는 internal 타입은 sealed
dotnet_diagnostic.CA2016.severity = warning     # CancellationToken 을 전달하라
dotnet_diagnostic.IDE0090.severity = suggestion # new() 로 단순화

# 공개 상수가 모인 파일에서는 CA1802 를 끈다 (79.2절)
[src/**/PublicConstants.cs]
dotnet_diagnostic.CA1802.severity = none

# 생성된 코드에는 스타일 규칙을 적용하지 않는다
[**/{obj,bin,Generated}/**.cs]
generated_code = true

# 테스트 프로젝트는 규칙을 느슨하게 둔다
[tests/**/*.cs]
dotnet_diagnostic.CA1062.severity = none      # 테스트에서 인수 검증까지 요구하지 않는다
dotnet_diagnostic.CA2007.severity = none      # 테스트에는 ConfigureAwait 가 필요 없다
```

`.editorconfig`는 **디렉터리 계층을 따라 병합**된다. 파일이 있는 디렉터리에서 시작해 `root = true`를 만날 때까지 위로 올라가며, **더 가까운 파일과 더 구체적인 섹션이 이긴다.** 즉 위의 `[tests/**/*.cs]` 섹션은 앞의 `[*.{cs,csx}]` 설정을 상속한 뒤 두 규칙만 덮어쓴다.

### 프로젝트 속성 — 무엇이 실제로 켜지는가

`.editorconfig`가 "어느 규칙을 어떤 심각도로"를 정한다면, `.csproj`(또는 `Directory.Build.props`)의 속성은 **"어느 규칙 집합을 아예 실행할 것인가"** 를 정한다.

| 속성 | 하는 일 | 부작용 |
|---|---|---|
| `EnableNETAnalyzers` | `CA` 규칙 실행. .NET 5 이상 SDK 프로젝트에서 기본 `true` | 빌드 시간이 늘어난다 |
| `AnalysisLevel` | **어느 세대의 규칙 집합**을 쓸지 (`latest`, `9.0`, `preview`, `none`) | `latest`로 두면 **SDK를 올릴 때마다 새 경고가 쏟아진다** |
| `AnalysisMode` | 그 세대에서 **몇 개를 켤지** (`Default`, `Minimum`, `Recommended`, `All`, `None`) | `All`은 실무에서 감당하기 어렵다 |
| `EnforceCodeStyleInBuild` | `IDE` 규칙을 **빌드에서도** 실행 (기본 `false`) | 빌드가 느려지고, IDE에서만 보이던 것이 **CI 실패로 승격**된다 |
| `TreatWarningsAsErrors` | 모든 경고를 오류로 | **가장 위험한 스위치**. 아래 참조 |
| `WarningsAsErrors` | **지정한 ID만** 오류로 | 위의 안전한 대안 |
| `WarningsNotAsErrors` | `TreatWarningsAsErrors` 중 예외로 둘 ID | 단계적 도입에 쓴다 |
| `NoWarn` | 지정한 ID를 완전히 무시 | 이유를 주석으로 남겨라 |

> **⚠️ `AnalysisLevel`을 `latest`로 두면 SDK 업그레이드가 빌드 파괴가 된다**
>
> `latest`는 "설치된 SDK가 아는 가장 최신 규칙 집합"을 뜻한다. 새 .NET SDK가 나오면 규칙이 추가되고, **어제까지 빌드되던 코드가 오늘 경고를 쏟아낸다.** `TreatWarningsAsErrors`가 함께 켜져 있으면 그대로 CI 실패다. 더 나쁜 것은 이 실패가 **개발자마다 다른 시점에** 발생한다는 점이다 — 각자 설치한 SDK 버전이 다르기 때문이다.
>
> 해법은 두 가지를 함께 쓰는 것이다. `global.json`으로 SDK 버전을 고정하고, `AnalysisLevel`에 **구체적인 버전 번호**(`9.0` 같은)를 적는다. 규칙 집합을 올리는 것은 그 자체로 하나의 작업 항목이 되어야 한다.

> **⚠️ `TreatWarningsAsErrors`는 서드파티와 생성 코드까지 잡는다**
>
> 이 속성은 **모든 경고**를 오류로 만든다. 여기에는 다음이 포함된다.
>
> - NuGet 패키지가 함께 배포한 분석기의 경고
> - 소스 생성기가 만든 코드의 경고 (`generated_code = true`로 걸러야 한다)
> - `[Obsolete]` 사용 경고(CS0618) — 의존성 하나가 API를 폐기하면 빌드가 멈춘다
> - 널 허용 경고(CS86xx) — 라이브러리가 주석을 추가하면 빌드가 멈춘다
>
> 즉 **내가 코드를 한 줄도 고치지 않았는데 빌드가 실패하는 경로가 여럿 열린다.** 신규 프로젝트라면 처음부터 켜도 좋지만, 기존 코드베이스에는 `WarningsAsErrors`로 **오류로 승격할 ID를 명시적으로 나열하는 편**이 관리 가능하다.
>
> ```xml
> <!-- 전부 오류로 만들지 않고, 절대 어기면 안 되는 것만 지목한다 -->
> <WarningsAsErrors>CA2214;CA2211;CA1001;CS8600;CS8602</WarningsAsErrors>
> ```

### `Directory.Build.props`로 솔루션 전체에 강제하기

`.csproj` 스무 개에 같은 속성을 복사해 넣으면 곧 어긋난다. MSBuild는 **프로젝트 파일을 읽기 전에 상위 디렉터리를 훑어 `Directory.Build.props`를 찾아 자동으로 가져온다.** 솔루션 루트에 하나만 두면 모든 프로젝트가 상속한다.

```xml
<!-- 솔루션 루트/Directory.Build.props -->
<Project>
  <PropertyGroup>
    <LangVersion>latest</LangVersion>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>

    <!-- 분석기: 버전을 고정해 SDK 업그레이드와 분리한다 -->
    <EnableNETAnalyzers>true</EnableNETAnalyzers>
    <AnalysisLevel>9.0</AnalysisLevel>
    <AnalysisMode>Recommended</AnalysisMode>
    <EnforceCodeStyleInBuild>true</EnforceCodeStyleInBuild>

    <!-- 전부가 아니라 지목한 것만 오류로 -->
    <WarningsAsErrors>CA2214;CA2211;CA1001;CA2241</WarningsAsErrors>

    <!-- 문서 주석 누락 경고는 끈다 -->
    <NoWarn>$(NoWarn);CS1591</NoWarn>
  </PropertyGroup>
</Project>
```

> **⚠️ `Directory.Build.props`는 가장 가까운 것 하나만 자동으로 읽힌다**
>
> MSBuild는 프로젝트에서 위로 올라가다 **첫 번째로 만난 `Directory.Build.props`에서 탐색을 멈춘다.** `.editorconfig`처럼 계층 전체를 병합하지 않는다. 그래서 `tests/` 아래에 별도의 `Directory.Build.props`를 두려면 그 파일 첫머리에서 상위 파일을 **직접 가져와야** 한다. 이 줄을 빠뜨리면 그 아래 프로젝트들만 조용히 아무 분석기도 없이 빌드된다.
>
> ```xml
> <Import Project="$([MSBuild]::GetPathOfFileAbove('Directory.Build.props', '$(MSBuildThisFileDirectory)../'))" />
> ```

### `dotnet format`과 CI 구성

`dotnet format`은 SDK에 포함된 도구로, 분석기가 지적한 것 중 **자동 수정이 있는 것을 실제로 적용한다.**

```bash
dotnet format whitespace   # 공백·들여쓰기만    dotnet format style     # IDE 규칙
dotnet format analyzers    # CA 규칙 중 수정 가능한 것    dotnet format   # 위 셋 전부

dotnet format --verify-no-changes --severity warn   # 고칠 것이 있으면 종료 코드 2. 파일은 안 고친다
```

마지막 스위치가 CI용이다. 파이프라인은 이렇게 구성한다.

```yaml
# GitHub Actions 예시
- name: Restore
  run: dotnet restore

- name: 서식·스타일 검사 (고치지 않고 확인만)
  run: dotnet format --verify-no-changes --severity warn

- name: 빌드 (분석기 경고를 오류로)
  run: dotnet build --no-restore -warnaserror

- name: 테스트
  run: dotnet test --no-build
```

`-warnaserror`를 프로젝트 파일이 아니라 **CI 명령줄에 두는 것**에 주목하라. 이렇게 하면 개발자의 로컬 빌드는 경고만 보고 계속 진행되고, CI에서만 차단된다. 작업 중인 코드가 경고 하나 때문에 실행조차 안 되는 상황을 피할 수 있다.

### 기존 코드베이스에 도입하는 순서

한 번에 다 켜면 경고 수천 개가 나오고, 팀은 그것을 `NoWarn`으로 덮은 뒤 다시는 보지 않는다. 순서가 중요하다.

1. **`.editorconfig`를 만들고 전부 `suggestion`으로 시작한다.** 편집기에 회색 점선만 뜬다. 누구의 빌드도 깨지지 않는다.
2. **`dotnet format`을 한 번 돌려 자동 수정 가능한 것을 전부 정리한다.** 이 커밋은 로직 변경이 없으므로 리뷰가 쉽고, `.git-blame-ignore-revs`에 등록해 `git blame`을 오염시키지 않게 한다.
3. **남은 위반이 적은 규칙부터 `warning`으로 올린다.** 위반이 5건이면 지금 고치고 올린다.
4. **위반이 많이 남은 규칙은 신규 코드에만 적용한다.** 디렉터리 단위로 `.editorconfig`를 두어 새로 만드는 프로젝트에서만 `warning`으로 둔다.
5. **절대 어기면 안 되는 소수만 `error`로 승격한다.** `CA2214`(생성자 가상 호출), `CA1001`(정리되지 않는 리소스)처럼 **버그가 확실한 것**만이다.
6. **CI에 `--verify-no-changes`와 `-warnaserror`를 넣는다.**

> **⚠️ 규칙을 억제할 때는 범위를 최소로 하고 이유를 남겨라**
>
> ```csharp
> // 나쁜 예 — 왜 껐는지 6개월 뒤에 아무도 모른다
> #pragma warning disable CA1822
>
> // 좋은 예 — 억제 범위와 이유가 명시된다
> [SuppressMessage("Performance", "CA1822:Mark members as static",
>     Justification = "리플렉션 기반 바인딩이 인스턴스 메서드를 요구한다")]
> public string FormatValue() => "...";
> ```
>
> `#pragma`가 코드 곳곳에 흩뿌려지면 **진짜 예외인 곳과 습관적으로 끈 곳을 구별할 수 없게 된다.** 특정 파일이나 디렉터리 전체에 적용되는 정책이라면 `#pragma`가 아니라 `.editorconfig`에 쓰는 것이 옳다 — 그래야 정책이 리뷰의 대상이 된다.

> **⚠️ 분석기는 공짜가 아니다**
>
> 분석기는 컴파일과 같은 프로세스에서 돌므로 **빌드 시간을 직접적으로 늘린다.** `AnalysisMode`를 `All`로 두면 큰 솔루션에서 빌드가 눈에 띄게 느려지고, 그러면 사람들은 분석기를 끄고 싶어진다. `Recommended`에서 시작해 필요한 것만 개별로 추가하는 편이 오래간다. 어느 분석기가 느린지는 `dotnet build /p:ReportAnalyzer=true`로 확인할 수 있다.

## 이 장의 요약

- **`var`의 논점은 타입 안전성이 아니라 가독성이다.** 숫자 타입에는 타입을 적어 컴파일러가 변환을 검사하게 하고, 쿼리 결과에는 `var`를 써서 컴파일러가 `IQueryable<T>`를 고르게 하라. 확장 메서드 해석은 컴파일 타임 타입으로만 결정된다.
- **`const`는 값이 소비자 어셈블리에 박제된다.** `ldc.i4` 대 `ldsfld` 한 줄의 차이가 버전 관리 전체를 좌우한다. 특성 인수·`case` 레이블·`enum` 정의·기본값처럼 컴파일 타임 값이 필요한 자리에만 `const`를 쓰고, 나머지는 `static readonly`다.
- **`is` 패턴이 기본 관용구다.** 캐스트는 사용자 정의 변환을 **컴파일 타임 타입 기준으로만** 수행하므로 `object`를 거치면 조용히 실패한다. `foreach`와 `Cast<T>()`는 캐스트를 쓰고 `OfType<T>()`는 `isinst`를 쓴다.
- **보간 문자열은 인수 개수와 순서를 컴파일러가 보장한다.** 문화권을 통제해야 하면 `FormattableString`으로 받아 나중에 포맷하고, 로깅처럼 기계가 다시 읽을 문자열에서는 오히려 템플릿과 값을 분리해 둬라.
- **초기화 순서는 정적 저장소 0 → 정적 초기화자 → 정적 생성자 → 인스턴스 저장소 0 → 인스턴스 초기화자 → 기반 생성자 → 인스턴스 생성자다.** 파생 클래스의 초기화자가 기반 생성자보다 먼저 실행된다는 것이 C#의 결정적 선택이다.
- **생성자 체이닝은 문법 설탕이 아니다.** 컴파일러가 초기화자와 기반 생성자 호출의 중복을 실제로 제거하며, `readonly` 필드 대입을 가능하게 하는 유일한 방법이다.
- **생성자에서 가상 함수를 부르면 파생 클래스의 초기화자 값만 보인다.** 생성자 본문이 설정할 값은 아직 없다. `required`와 `init`은 이 문제를 더 악화시킨다.
- **`new` 한정자는 비가상 메서드를 가상으로 만들지 않는다.** 참조 변수의 선언 타입이 동작을 결정하게 될 뿐이다. 정당한 용도는 배포된 API의 이름을 바꿀 수 없는데 기반 클래스가 같은 이름을 추가한 경우, 그 하나뿐이다.
- **프로퍼티는 데이터의 기대를 갖는다** — 같은 값, 빠름, 예외 없음, 부작용 없음. 그 밖의 일은 동사로 된 메서드 이름을 가져야 한다. 디버거가 getter를 자동 호출한다는 사실을 잊지 마라.
- **익명 타입은 메서드 안에 갇힌 불변 참조 타입이다.** 어셈블리 경계를 넘어야 하면 튜플이나 레코드이고, 복합 키가 필요하면 익명 타입이다.
- **시퀀스를 반환하고 저장 여부는 호출자가 정하게 하라.** 지연 평가는 두 번 열거하면 두 번 실행된다는 뜻이기도 하다. 인수 검증은 지역 함수로 분리해 즉시 보고하라.
- **클로저는 스코프 단위로 뭉치며 캡처된 변수의 수명을 연장한다.** 비싼 리소스가 반환된 시퀀스에 실려 나가지 않게 하려면 메서드를 쪼개거나, 리소스 관리를 메서드 안으로 넣거나, 알고리즘을 델리게이트로 주입하라.
- **관용구는 리뷰가 아니라 도구로 강제한다.** `.editorconfig`에 합의를 적고, `Directory.Build.props`로 솔루션 전체에 상속시키고, CI에서 `dotnet format --verify-no-changes`와 `-warnaserror`로 차단하라. 도입은 `suggestion`에서 시작해 단계적으로 올린다.

## 연습 문제

1. `int`, `long`, `float`, `double`, `decimal`을 반환하는 `GetMagicNumber()` 다섯 벌을 만들고 `var total = 100 * GetMagicNumber() / 6;`의 결과를 각각 출력하라. 그다음 `double total = ...`로 바꿔도 정수 나눗셈이 살아남는 것을 확인하라.
2. 클래스 라이브러리에 `public const int End = 10;`과 `public static readonly int Start = 5;`를 두고 콘솔 앱에서 루프를 돌려라. 라이브러리만 `End = 120`, `Start = 105`로 고쳐 **콘솔 앱을 재컴파일하지 말고** DLL만 교체한 뒤 실행하라. 출력이 사라지는 이유를 `ildasm`으로 콘솔 앱의 IL을 열어 확인하라.
3. `MyType`으로 암시적 변환되는 `SecondType`을 만들고, `object`로 받은 `SecondType` 인스턴스에 `(MyType)o`, `o as MyType`, `o is MyType t`를 각각 시도하라. 그다음 `SecondType st = (SecondType)o;`를 먼저 하고 `(MyType)st`를 시도해 결과가 달라지는 것을 확인하라.
4. 79.5절의 `Base`/`Derived` 추적 예제를 실행해 출력 순서를 확인하라. 그다음 `Base`와 `Derived`의 정적 생성자를 지우고(초기화자만 남기고) 출력이 어떻게 달라지는지 관찰하라. `ildasm`으로 두 경우의 타입 플래그에서 `beforefieldinit`의 유무를 확인하라.
5. 79.6절의 가상 함수 예제를 실행해 `"초기화자가 설정한 값"`이 출력되는 것을 확인하라. `_msg`를 `required string Msg { get; init; }`로 바꾸고 객체 초기화자로 값을 넣었을 때 `null`이 출력되는 것도 확인하라. 그다음 `CA2214`를 `error`로 켜고 빌드가 실패하는지 보라.
6. 파일을 여는 `using` 블록 안에서 LINQ 쿼리를 만들어 반환하는 메서드를 작성하고, 블록 밖에서 열거해 `ObjectDisposedException`을 재현하라. 그다음 `using`을 반복자 메서드 안으로 옮겨 해결하고, **같은 쿼리를 두 번 열거**했을 때 어떤 일이 일어나는지 확인하라.
7. 빈 프로젝트에 이 장의 `.editorconfig`와 `Directory.Build.props`를 넣고 각 규칙을 일부러 위반하는 코드를 작성하라. `dotnet build`, `dotnet format --verify-no-changes`, `dotnet build -warnaserror`가 각각 어떻게 반응하는지 비교하고, `dotnet build /p:ReportAnalyzer=true`로 어느 분석기가 시간을 많이 쓰는지 확인하라.
