# 81장. 애플리케이션 유형별 지도

> **이 장의 위치** — Part XVI「실전 적용」의 첫 장이다. 3권은 여기까지 CLR 내부, 메모리와 GC, 고성능 기법, 진단, 설계 관용구를 순서대로 팠다. 전부 **런타임과 언어의 이야기**였다. 이 장은 그 지식이 **어떤 애플리케이션 유형에서 어떻게 현금화되는가**를 그리는 지도다. ASP.NET Core가 요청마다 스코프를 만든다는 사실은 63장(할당)과 65장(GC 모드)을 만나야 의미가 생기고, Blazor WebAssembly가 트리밍에 의존한다는 사실은 57.14절을 만나야 위험이 보인다.
>
> **선수 지식** — 52장(어셈블리), 63장(할당), 65장(GC 모드와 튜닝), 72장(시스템 레벨 성능), 78장(API 설계), 80장(테스트 가능한 코드)
>
> **이 장에서 다루지 않는 것** — 개별 프레임워크의 튜토리얼은 다루지 않는다. EF Core의 성능 함정은 72.4절에, 데이터 접근 벤치마크는 72.3절에, 시작 시간 최적화는 72.7절에, 컨테이너 GC 설정은 65.7절과 72.8절에 있다. 이 장은 **선택 기준과 연결 관계**만 다룬다.

## 81.1 콘솔 앱과 워커 서비스

### 이 장을 읽는 법

이 장은 열 개의 애플리케이션 유형을 훑는다. 각 유형마다 세 가지를 묻는다.

1. **무엇에 적합하고 무엇에 부적합한가**
2. **런타임이 그 유형에서 무엇을 다르게 하는가** — 호스트 수명, 스레딩 모델, 할당 패턴
3. **3권의 어느 장이 이 유형에서 가장 자주 필요해지는가**

세 번째가 이 장의 존재 이유다. 프레임워크 문서는 첫 번째와 두 번째까지만 알려준다.

>

>
> 생성된 암시적 `using` 목록은 `obj/Debug/net8.0/<프로젝트명>.GlobalUsings.g.cs`에서 직접 볼 수 있다.

### 콘솔 앱 — 가장 얇은 호스트

콘솔 앱은 `Main`이 반환하면 프로세스가 끝난다. 그게 전부다. 이 단순함이 장점이자 한계다.

```csharp
// Program.cs — 최상위 문(top-level statements)
Console.WriteLine("I can run everywhere!");
Console.WriteLine($"OS Version is {Environment.OSVersion}.");

if (OperatingSystem.IsMacOS())
{
    Console.WriteLine("I am macOS.");
}
else if (OperatingSystem.IsWindowsVersionAtLeast(major: 10, build: 22000))
{
    Console.WriteLine("I am Windows 11.");
}
else if (OperatingSystem.IsWindowsVersionAtLeast(major: 10))
{
    Console.WriteLine("I am Windows 10.");
}
else
{
    Console.WriteLine("I am some other mysterious OS.");
}
```

`OperatingSystem` 정적 메서드들은 **플랫폼 호환성 분석기**가 이해하는 가드다. `[SupportedOSPlatform]`으로 표시된 API를 이 조건문 안에서 호출하면 CA1416 경고가 사라진다.

콘솔 앱이 3권 지식과 만나는 지점은 셋이다.

| 만나는 지점 | 무슨 일이 일어나는가 | 참조 |
|---|---|---|
| **시작 시간** | 프로세스가 짧게 살수록 JIT 비용의 비중이 커진다. 1초 도는 CLI 도구는 시작 시간이 전체의 절반일 수 있다 | 55.2절(계층형 컴파일), 72.7절 |
| **Native AOT** | 콘솔 앱은 AOT 제약(동적 로딩·`Reflection.Emit` 금지)을 지키기 가장 쉬운 유형이다 | 55.7절, 57.14절 |
| **GC 모드** | 기본은 워크스테이션 GC다. 짧게 사는 프로세스에서는 GC가 한 번도 안 돌 수도 있다 | 65.1절 |

> **💡 CLI 도구는 AOT의 최적 후보다**
>
> `dotnet tool`로 배포하는 CLI 도구는 사용자가 하루에 수십 번 실행한다. 매번 런타임 초기화 + JIT을 반복한다. 이 유형이야말로 Native AOT의 이득이 가장 크게 체감되는 자리다. 시작 시간이 수십 밀리초에서 한 자릿수 밀리초로 떨어진다. 반대로 하루 한 번 도는 야간 배치는 AOT로 얻을 게 거의 없다 — 20분 도는 프로세스에서 시작 시간 30ms는 반올림 오차다.

> **⚠️ `Console.ReadKey`는 컨테이너에서 즉시 던진다**
>
> 콘솔 앱 템플릿의 관용구인 `Console.ReadKey(intercept: true)`를 그대로 두고 컨테이너에 배포하면, 표준 입력이 리다이렉트된 환경에서 `InvalidOperationException`이 난다("Cannot read keys when either application does not have a console or when console input has been redirected"). 배포 전에 제거하거나, `Console.IsInputRedirected`로 가드하라.
>
> ```csharp
> if (!Console.IsInputRedirected)
> {
>     Console.ReadKey(intercept: true);
> }
> ```

### 워커 서비스 — 상시 실행되는 것들

콘솔 앱과 워커 서비스의 차이는 **호스트(Host)** 의 유무다. 호스트는 DI 컨테이너, 구성 시스템, 로깅, 수명 관리, 정상 종료를 한 묶음으로 제공한다.

```csharp
// Program.cs — 워커 서비스 ※.NET 8 (HostApplicationBuilder)
using Microsoft.Extensions.DependencyInjection;
using Microsoft.Extensions.Hosting;

HostApplicationBuilder builder = Host.CreateApplicationBuilder(args);
builder.Services.AddHostedService<QueueConsumer>();

IHost host = builder.Build();
host.Run();   // 스레드를 막는 호출. 종료 신호가 올 때까지 반환하지 않는다.
```

`Host.CreateApplicationBuilder`는 .NET 8에서 도입된 간소화된 빌더다. 그 이전에는 `Host.CreateDefaultBuilder(args).ConfigureServices(...)` 형태를 썼고 지금도 동작한다. 작업 자체는 `BackgroundService`를 상속해 구현한다.

```csharp
using Microsoft.Extensions.Hosting;
using Microsoft.Extensions.Logging;

public sealed class QueueConsumer : BackgroundService
{
    private readonly ILogger<QueueConsumer> _logger;
    private readonly IServiceScopeFactory _scopeFactory;

    public QueueConsumer(ILogger<QueueConsumer> logger, IServiceScopeFactory scopeFactory)
    {
        _logger = logger;
        _scopeFactory = scopeFactory;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            // 메시지 하나를 처리할 때마다 스코프를 직접 연다.
            using IServiceScope scope = _scopeFactory.CreateScope();
            var handler = scope.ServiceProvider.GetRequiredService<IMessageHandler>();

            await handler.HandleNextAsync(stoppingToken);
        }

        _logger.LogInformation("정상 종료 신호를 받아 루프를 빠져나간다.");
    }
}
```

여기 두 가지가 이 장 전체를 관통한다.

**첫째, 스코프를 누가 만드는가.** ASP.NET Core는 요청마다 프레임워크가 스코프를 만들어준다(81.3절). 워커 서비스에는 요청이 없으므로 **개발자가 직접 `IServiceScopeFactory.CreateScope()`를 호출해야 한다.** 이걸 빼먹고 싱글턴인 `BackgroundService`의 생성자에서 `DbContext`를 받으면 81.3절에서 다룰 포획 의존성(captive dependency) 사고가 난다.

**둘째, `CancellationToken`이 정상 종료의 전부다.** `host.Run()`은 SIGTERM(리눅스), Ctrl+C, Windows 서비스 중지 요청을 받으면 `stoppingToken`을 취소하고, 기본 5초 동안 `ExecuteAsync`가 반환하기를 기다린다. 이 시간은 조정할 수 있다.

```csharp
builder.Services.Configure<HostOptions>(options =>
{
    options.ShutdownTimeout = TimeSpan.FromSeconds(30);
});
```

> **⚠️ `ExecuteAsync`에서 새는 예외는 기본적으로 호스트를 죽인다 ※.NET 6+**
>
> .NET 5까지는 `BackgroundService`에서 처리되지 않은 예외가 나면 **조용히 그 서비스만 멈추고 호스트는 계속 돌았다.** 로그에도 남지 않았다. 큐 소비자가 죽었는데 프로세스는 살아 있고 헬스체크도 통과하는, 최악의 실패 모드였다.
>
> .NET 6부터 기본값이 `BackgroundServiceExceptionBehavior.StopHost`로 바뀌었다. 예외가 새면 호스트 전체가 내려간다. 오케스트레이터가 재시작해주므로 이쪽이 훨씬 낫다. 옛 동작이 필요하면 명시적으로 되돌릴 수 있지만, **되돌리기 전에 왜 필요한지 두 번 생각하라.**
>
> ```csharp
> builder.Services.Configure<HostOptions>(options =>
> {
>     options.BackgroundServiceExceptionBehavior =
>         BackgroundServiceExceptionBehavior.Ignore;   // 권장하지 않는다
> });
> ```

> **⚠️ `ExecuteAsync`의 첫 `await` 이전 코드는 호스트 시작을 막는다**
>
> `BackgroundService.StartAsync`는 `ExecuteAsync`를 호출하고, **첫 번째 미완료 `await`를 만날 때까지 동기적으로 실행된다.** `ExecuteAsync` 첫머리에 동기 초기화 코드를 잔뜩 넣으면 호스트 시작 전체가 그만큼 지연된다. 다른 호스티드 서비스도, 웹 앱이라면 요청 수신 시작도 함께 밀린다.
>
> 무거운 초기화는 `await Task.Yield();`를 먼저 두어 즉시 반환하게 만들거나, `IHostedLifecycleService`(※.NET 8)의 `StartedAsync`로 옮긴다.

### 서비스로 등록하기

워커를 OS 서비스로 돌리려면 패키지 하나와 호출 한 줄이 필요하다.

| 플랫폼 | NuGet 패키지 | 등록 호출 |
|---|---|---|
| Windows 서비스 | `Microsoft.Extensions.Hosting.WindowsServices` | `builder.Services.AddWindowsService();` |
| systemd (리눅스) | `Microsoft.Extensions.Hosting.Systemd` | `builder.Services.AddSystemd();` |

이 호출은 수명 관리자(`IHostLifetime`)를 교체한다. `AddSystemd`는 systemd에 `READY=1`을 통지하고 로그를 저널 형식으로 접두사 처리한다. `AddWindowsService`는 SCM(Service Control Manager)과 통신한다. **둘 다 해당 환경이 아니면 아무 일도 하지 않는다** — 개발 머신에서 그냥 콘솔로 실행해도 깨지지 않는다.

### 워커 서비스와 3권

상시 실행되는 프로세스는 짧게 사는 프로세스와 **완전히 다른 메모리 프로파일**을 갖는다.

| 특성 | 콘솔 앱 (짧게 산다) | 워커 서비스 (오래 산다) |
|---|---|---|
| GC 세대 도달 | gen0에서 끝나는 경우가 많다 | gen2·LOH까지 간다. 단편화가 문제가 된다 |
| 누수의 의미 | 무해하다 — 프로세스가 곧 죽는다 | **치명적이다.** 며칠 뒤 OOM으로 나타난다 |
| 진단 방법 | 없어도 된다 | 스냅샷 비교, 지배자 분석이 필수 |
| 중요한 장 | 55장(JIT), 72.7절 | 63장, 64장, 65장, **66장** |

> **💡 워커 서비스에서 가장 자주 필요해지는 장은 66장이다**
>
> 3권의 어느 장이 실무에서 가장 자주 열리는가를 유형별로 묻는다면, 워커 서비스의 답은 66장(메모리 문제 진단)이다. 특히 66.11절의 대표 시나리오 여섯 가지 — 이벤트 누수, 정적 캐시, 타이머, LOH 단편화, 파이널라이저 큐 적체, 어셈블리 누적 — 중 **타이머와 정적 캐시**는 워커 서비스에서 압도적으로 흔하다. `while(true)` 루프 안에서 정적 딕셔너리에 무언가를 계속 넣는 코드는 리뷰에서 잡아야 한다.

## 81.2 클래스 라이브러리 설계와 NuGet 패키징

### 라이브러리는 애플리케이션이 아니다

클래스 라이브러리를 애플리케이션처럼 만드는 것이 가장 흔한 실수다. 차이는 세 가지다.

| 축 | 애플리케이션 | 라이브러리 |
|---|---|---|
| **대상 프레임워크** | 하나로 고정해도 된다 | 소비자가 누구인지 모른다. 다중 대상이 필요할 수 있다 |
| **의존성** | 마음대로 추가한다 | 추가하는 순간 **모든 소비자에게 전염된다** |
| **깨지는 변경** | 내가 고치면 끝 | 내가 모르는 코드가 깨진다 (78장) |
| **트리밍·AOT** | 내가 결정한다 | **소비자가 결정한다.** 내 라이브러리가 트림 안전하지 않으면 소비자의 AOT가 깨진다 |

마지막 줄이 3권을 읽은 사람에게 가장 중요한 항목이다. 자세히는 이 절 뒤쪽에서 본다.

### 대상 프레임워크 고르기

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>net8.0</TargetFramework>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
  </PropertyGroup>
</Project>
```

| 대상 | 쓸 수 있는 소비자 | 언제 고르나 |
|---|---|---|
| `net8.0` | .NET 8 이상 | 기본값. 사내 라이브러리, 최신 API가 필요한 경우 |
| `net8.0-windows` | Windows의 .NET 8 이상 | WinForms/WPF 관련 타입을 쓸 때 |
| `netstandard2.0` | .NET Framework 4.6.1+, .NET Core 2.0+, Mono, Xamarin, Unity 전부 | .NET Framework 소비자를 버릴 수 없을 때 |
| `net8.0;netstandard2.0` (다중 대상) | 둘 다 | 넓은 호환성 + 최신 API 활용을 동시에 원할 때 |

`netstandard2.0`을 대상으로 하면 공개 NuGet 피드의 사실상 모든 .NET 플랫폼이 참조할 수 있다. 대가는 크다 — `Span<T>`의 상당 부분, `System.Text.Json`의 최신 기능, 정적 추상 인터페이스 멤버(※C# 11) 같은 것을 쓸 수 없거나 별도 패키지를 끌어와야 한다.

> **⚠️ `netstandard2.0`은 기본적으로 C# 7.3 컴파일러를 쓴다**
>
> `netstandard2.0`을 대상으로 하는 프로젝트는 언어 버전이 자동으로 7.3으로 잡힌다. 파일 범위 네임스페이스도, 레코드도, `required` 멤버도 못 쓴다. 최신 문법을 쓰려면 명시해야 한다.
>
> ```xml
> <PropertyGroup>
>   <TargetFramework>netstandard2.0</TargetFramework>
>   <LangVersion>12</LangVersion>
> </PropertyGroup>
> ```
>
> 다만 **언어 버전을 올린다고 없는 런타임 API가 생기지는 않는다.** 컴파일러가 런타임 타입을 요구하는 기능(레코드의 `IsExternalInit`, `required`의 `RequiredMemberAttribute` 등)은 그 타입을 직접 정의해 넣거나 `PolySharp` 같은 폴리필 패키지를 써야 한다.

### 다중 대상과 조건부 컴파일

```xml
<PropertyGroup>
  <TargetFrameworks>net8.0;netstandard2.0</TargetFrameworks>
</PropertyGroup>

<ItemGroup Condition="'$(TargetFramework)' == 'netstandard2.0'">
  <PackageReference Include="System.Memory" Version="4.5.5" />
</ItemGroup>
```

```csharp
#if NET8_0_OR_GREATER
// SearchValues는 .NET 8에서 도입되었다 (68장).
private static readonly System.Buffers.SearchValues<char> Vowels =
    System.Buffers.SearchValues.Create("aeiou");
#endif

public static bool ContainsVowel(ReadOnlySpan<char> text)
{
#if NET8_0_OR_GREATER
    return text.ContainsAny(Vowels);
#else
    foreach (char c in text)
    {
        if (c is 'a' or 'e' or 'i' or 'o' or 'u') return true;
    }
    return false;
#endif
}
```

`NET8_0_OR_GREATER`, `NETSTANDARD2_0` 같은 심볼은 SDK가 자동으로 정의한다. 직접 `<DefineConstants>`에 넣을 필요가 없다.

> **⚠️ 다중 대상은 테스트도 다중이어야 한다**
>
> `#if`로 갈라진 두 구현은 **서로 다른 코드**다. 테스트 프로젝트도 같은 대상들로 다중 대상 지정하지 않으면, `net8.0` 경로만 테스트하고 `netstandard2.0` 경로는 컴파일만 확인한 채로 배포하게 된다. 위 예제에서 폴백 구현의 모음 판정이 틀렸다면 .NET Framework 소비자만 조용히 잘못된 값을 받는다.

### 패키지 메타데이터

`dotnet pack`이 만드는 `.nupkg`의 내용은 `.csproj`의 속성들이 결정한다.

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>netstandard2.0</TargetFramework>
    <LangVersion>12</LangVersion>

    <GeneratePackageOnBuild>true</GeneratePackageOnBuild>
    <PackageId>Contoso.Text.Validation</PackageId>
    <PackageVersion>8.0.0</PackageVersion>
    <Title>Contoso Text Validation</Title>
    <Authors>Contoso Engineering</Authors>
    <Description>문자열 값을 검증하는 확장 메서드 모음.</Description>
    <PackageLicenseExpression>MIT</PackageLicenseExpression>
    <PackageProjectUrl>https://github.com/contoso/text-validation</PackageProjectUrl>
    <PackageReadmeFile>readme.md</PackageReadmeFile>
    <PackageIcon>icon.png</PackageIcon>
    <PackageRequireLicenseAcceptance>false</PackageRequireLicenseAcceptance>
    <PackageReleaseNotes>정규식 기반 검증 메서드 세 개 추가.</PackageReleaseNotes>
    <Copyright>Copyright © 2026 Contoso</Copyright>
    <PackageTags>string;validation;regex</PackageTags>
  </PropertyGroup>

  <ItemGroup>
    <None Include="icon.png" PackagePath="\" Pack="true" />
    <None Include="readme.md" PackagePath="\" Pack="true" />
  </ItemGroup>
</Project>
```

몇 가지 규칙이 있다.

- `PackageId`는 **공개 피드 전체에서 유일해야 한다.** nuget.org에 올릴 생각이 조금이라도 있다면 회사·조직 접두사를 붙여라.
- `PackageLicenseExpression`은 [SPDX 라이선스 식별자](https://spdx.org/licenses/) 목록의 값이어야 한다(`MIT`, `Apache-2.0`, `MS-PL` 등). 커스텀 라이선스는 `PackageLicenseFile`을 쓴다.
- `<None ... Pack="true">`의 `None`은 **빌드에 참여하지 않는 파일**을 뜻한다. `PackagePath`가 패키지 안에서의 위치다.
- 불리언 값 속성에는 **공백이 들어가면 안 된다.** `<PackageRequireLicenseAcceptance>` 안에 줄바꿈과 들여쓰기를 넣으면 값이 `true`로 파싱되지 않는다.

`GeneratePackageOnBuild`를 켜지 않았다면 명시적으로 팩한다.

```text
dotnet pack -c Release
```

> **📌 IntelliSense가 폐기된 태그를 권할 수 있다**
>
> `.csproj` 편집 중 자동 완성이 `<PackageIconUrl>`을 제안하는 경우가 있는데, 이것은 폐기된 이름이고 현재는 `<PackageIcon>`을 쓴다. 자동화 도구를 항상 믿을 수는 없다. 정확한 이름은 NuGet의 `msbuild-targets` 문서 표에 있는 **MSBuild Property** 열이 기준이다.

### 의존성 버전 고정

```xml
<!-- 나쁜 예 -->
<PackageReference Include="Newtonsoft.Json" Version="13.0.2-beta1" />
<PackageReference Include="Microsoft.EntityFrameworkCore.Sqlite" Version="8.0-*" />

<!-- 좋은 예 -->
<PackageReference Include="Newtonsoft.Json" Version="13.0.3" />
<PackageReference Include="Microsoft.EntityFrameworkCore.Sqlite" Version="8.0.0" />
```

와일드카드는 항상 최신 릴리스를 가리키므로 편하지만, **미래의 호환되지 않는 패키지가 조용히 들어와 코드를 깬다.** 프리릴리스 한정자(`beta1`, `rc4`)도 마찬가지다.

Microsoft는 특정 .NET 버전과 함께 출하된 패키지 버전들(예: 전부 `8.0.0`)로 고정하면 서로 호환됨을 보증한다. **프로덕션 배포에서는 거의 항상 고정하라.**

> **💡 중앙 패키지 관리로 버전 드리프트를 막는다 ※NuGet 6.2+**
>
> 솔루션에 프로젝트가 열 개쯤 되면 같은 패키지의 버전이 프로젝트마다 어긋나기 시작한다. 솔루션 루트에 `Directory.Packages.props`를 두면 버전을 한 곳에서 관리할 수 있다.
>
> ```xml
> <Project>
>   <PropertyGroup>
>     <ManagePackageVersionsCentrally>true</ManagePackageVersionsCentrally>
>   </PropertyGroup>
>   <ItemGroup>
>     <PackageVersion Include="Microsoft.EntityFrameworkCore.Sqlite" Version="8.0.0" />
>     <PackageVersion Include="Newtonsoft.Json" Version="13.0.3" />
>   </ItemGroup>
> </Project>
> ```
>
> 개별 프로젝트는 버전 없이 참조만 쓴다.
>
> ```xml
> <PackageReference Include="Newtonsoft.Json" />
> ```

### 라이브러리를 트림 안전하게 만들기

이 절에서 3권 지식이 가장 직접적으로 쓰이는 부분이다. 소비자가 Native AOT나 트리밍을 켤 계획이면, **라이브러리가 협조하지 않으면 소비자는 못 켠다.**

```xml
<PropertyGroup>
  <TargetFramework>net8.0</TargetFramework>
  <IsTrimmable>true</IsTrimmable>        <!-- 이 어셈블리는 트림 대상이다 -->
  <IsAotCompatible>true</IsAotCompatible> <!-- ※.NET 8: 트림+AOT 분석기를 켠다 -->
</PropertyGroup>
```

`<IsAotCompatible>true</IsAotCompatible>`는 .NET 8에서 도입된 편의 속성으로, `IsTrimmable`과 함께 `EnableTrimAnalyzer`, `EnableAotAnalyzer`, `EnableSingleFileAnalyzer`를 모두 켠다. 그 결과 **빌드 시점에** 문제 코드가 경고로 잡힌다.

| 경고 접두사 | 무엇을 잡는가 |
|---|---|
| `IL2xxx` | 트리밍 안전성 — 리플렉션으로만 접근하는 멤버가 잘려나갈 수 있는 지점 |
| `IL3xxx` | AOT 안전성 — 런타임 코드 생성이 필요한 지점 (`IL3050`이 대표) |

분석기를 만족시키는 방법은 두 가지다.

**첫째, 리플렉션 대상을 명시한다.**

```csharp
using System.Diagnostics.CodeAnalysis;

public static object CreateInstance(
    [DynamicallyAccessedMembers(DynamicallyAccessedMemberTypes.PublicConstructors)]
    Type type)
{
    return Activator.CreateInstance(type)!;
}
```

`[DynamicallyAccessedMembers]`는 트리머에게 "이 `Type`이 가리키는 타입의 public 생성자는 자르지 마라"고 알린다. 57.14절에서 이 특성의 전체 목록과 흐름 분석 규칙을 다뤘다.

**둘째, 안 되는 API는 안 된다고 표시한다.**

```csharp
using System.Diagnostics.CodeAnalysis;

[RequiresDynamicCode("동적 프록시 생성은 Native AOT에서 동작하지 않는다.")]
public static T CreateProxy<T>() where T : class
{
    // System.Reflection.Emit 사용 (58장)
    // ...
}
```

`[RequiresDynamicCode]`와 `[RequiresUnreferencedCode]`는 **경고를 없애는 것이 아니라 호출자에게 전파한다.** 소비자가 이 메서드를 AOT 앱에서 부르면 그쪽에서 경고가 난다. 이것이 올바른 동작이다 — 문제를 숨기는 대신 계약으로 만든다.

> **⚠️ 소스 생성기는 트리밍 문제의 근본 해법이다**
>
> 리플렉션을 `[DynamicallyAccessedMembers]`로 감싸는 것은 대증 요법이다. 트리머가 자르지 않게 막을 뿐, 리플렉션의 런타임 비용(57.12절)은 그대로 남는다.
>
> **컴파일 타임에 코드를 생성하면 두 문제가 동시에 사라진다.** `System.Text.Json`의 소스 생성 컨텍스트(`JsonSerializerContext`)나 `[LoggerMessage]`(75.2절)가 이 접근의 대표다. 새 라이브러리를 만든다면 리플렉션 기반 API를 공개 표면에 넣기 전에 소스 생성기로 대체할 수 있는지 먼저 검토하라. 자세히는 57.15절에 있다.

### 어셈블리 경계와 테스트

`internal` 타입을 테스트 프로젝트에 노출하는 관용구는 52장에서 본 그대로다.

```csharp
using System.Runtime.CompilerServices;

[assembly: InternalsVisibleTo("Contoso.Text.Validation.Tests")]
```

라이브러리가 강력한 이름으로 서명되어 있다면 테스트 어셈블리도 서명되어야 하고, 위 인자에 공개 키 전체를 붙여야 한다. .NET 5 이후 강력한 이름의 중요도는 크게 떨어졌지만(52.6절), `InternalsVisibleTo`는 여전히 이 규칙을 따른다.

> **💡 `internal`을 테스트하려고 노출하기 전에 설계를 의심하라**
>
> `InternalsVisibleTo`는 유용한 도구지만 남용의 신호이기도 하다. 테스트하고 싶은 `internal` 타입이 많다면, 그것은 보통 **그 타입들이 별도 라이브러리여야 한다는 뜻**이다. 80.2절에서 본 경계 설계의 관점으로 다시 보라.

## 81.3 ASP.NET Core — 미들웨어 파이프라인, DI, 구성, 최소 API

### ASP.NET Core 앱은 콘솔 앱이다

이것이 출발점이다. ASP.NET Core 애플리케이션은 **`IHost`를 만들어 구성하는 콘솔 애플리케이션**이다. .NET Framework 시대의 ASP.NET처럼 IIS가 호스팅하는 별종이 아니다. `Main`이 있고, 프로세스가 있고, 그 프로세스 안에서 Kestrel이라는 웹 서버가 돈다.

```csharp
// Program.cs
var builder = WebApplication.CreateBuilder(args);

// ── 1단계: 서비스 등록 (DI 컨테이너 구성) ──
builder.Services.AddRazorPages();
builder.Services.AddNorthwindContext();

var app = builder.Build();   // 여기서 컨테이너가 봉인된다

// ── 2단계: HTTP 파이프라인 구성 ──
if (!app.Environment.IsDevelopment())
{
    app.UseHsts();
}
app.UseHttpsRedirection();
app.UseDefaultFiles();       // index.html, default.html 등
app.UseStaticFiles();        // wwwroot 아래 정적 파일
app.MapRazorPages();
app.MapGet("/", () => $"Environment is {app.Environment.EnvironmentName}");

// ── 3단계: 실행 ──
app.Run();   // 스레드를 막는 호출
Console.WriteLine("이 줄은 웹 서버가 멈춘 뒤에 실행된다!");
```

`builder.Build()`가 경계선이다. **그 위는 등록, 아래는 파이프라인.** 이 두 구간을 섞으면 안 된다.

> **📌 `Startup.cs`는 어디 갔나**
>
> .NET 5까지는 `Program.cs`에서 `WebHost`를 만들고 `Startup.cs`의 `ConfigureServices`(등록)와 `Configure`(파이프라인) 두 메서드로 나눠 설정했다. .NET 6부터 최상위 문 하나로 합쳐졌다. 위 코드의 `builder.Build()` 위쪽이 옛 `ConfigureServices`, 아래쪽이 옛 `Configure`에 해당한다. `Startup.cs` 방식도 여전히 동작하므로 레거시 코드를 만나도 당황할 필요는 없다.

### 미들웨어 파이프라인

파이프라인은 **연결된 델리게이트의 시퀀스**다. 각 델리게이트는 요청을 보고, 처리하거나, 다음 델리게이트에게 넘긴다. 응답은 역순으로 되돌아온다.

델리게이트의 시그니처는 놀랄 만큼 단순하다.

```csharp
public delegate Task RequestDelegate(HttpContext context);
```

`HttpContext` 하나에 URL 경로, 쿼리 문자열, 쿠키, 헤더, 사용자 에이전트, 응답 스트림이 전부 들어 있다.

```text
ASP.NET Core 요청 파이프라인 — 요청 두 건의 여정

  브라우저
    │
    │ ① http://localhost:5130/index.html   (평문 HTTP)
    ▼
  ┌──────────────────────────┐
  │ UseHttpsRedirection      │──① 307 + https URL ──▶ 브라우저 (재요청)
  └───────────┬──────────────┘
              │ ② https://localhost:5131/index   ▲
              ▼                                   │ 응답이 역순으로
  ┌──────────────────────────┐                    │ 되돌아오며
  │ UseDefaultFiles          │                    │ 각 미들웨어가
  │ UseStaticFiles           │──② wwwroot에 없음──┤ 응답을 수정할
  └───────────┬──────────────┘                    │ 기회를 갖는다
              │                                   │
              ▼                                   │
  ┌──────────────────────────┐                    │
  │ MapRazorPages            │                    │
  │  /index → Pages/Index    │────── HTML ────────┘
  │           .cshtml 실행    │
  └──────────────────────────┘

  ★ 파이프라인은 등록한 순서대로 실행된다. 순서가 곧 의미다.
```

미들웨어를 파이프라인에 넣는 방법은 세 가지다.

| 메서드 | 동작 | 언제 쓰나 |
|---|---|---|
| `Use` | 다음 델리게이트를 호출할지 스스로 결정한다. 호출 전후로 요청·응답을 수정할 수 있다 | 대부분의 경우 |
| `Run` | **종단(terminal)** 델리게이트. 다음을 호출하지 않고 즉시 응답한다 | 파이프라인 끝 |
| `Map` | URL 경로 등이 일치하면 파이프라인을 **분기**한다 | 경로별로 다른 파이프라인이 필요할 때 |

인라인 익명 메서드로 직접 하나 끼워 넣어 보자. 엔드포인트 라우팅 결정 이후의 위치에서 어떤 엔드포인트가 선택되었는지 출력하고, `/bonjour`는 직접 처리한다.

```csharp
app.Use(async (HttpContext context, Func<Task> next) =>
{
    RouteEndpoint? rep = context.GetEndpoint() as RouteEndpoint;
    if (rep is not null)
    {
        Console.WriteLine($"Endpoint name: {rep.DisplayName}");
        Console.WriteLine($"Endpoint route pattern: {rep.RoutePattern.RawText}");
    }

    if (context.Request.Path == "/bonjour")
    {
        // 일치하면 여기서 종료한다. next를 부르지 않으므로 종단 델리게이트가 된다.
        await context.Response.WriteAsync("Bonjour Monde!");
        return;
    }

    // 다음 델리게이트 호출 전에 요청을 수정할 수 있다.
    await next();
    // 호출 후에 응답을 수정할 수 있다.
});
```

이 코드를 `UseHttpsRedirection` 앞에 두고 실행하면 관찰할 수 있는 것들이 있다.

| 요청 경로 | 콘솔 출력 | 왜 |
|---|---|---|
| `/` | `Endpoint name: /index` | 라우팅이 `/`를 `/index` 엔드포인트로 매칭했다 |
| `/suppliers` | `Endpoint name: /Suppliers` | Razor Page 파일명으로 매칭 |
| `/index.html` | (없음) | 엔드포인트 매칭 실패. 정적 파일 미들웨어가 처리했다 |
| `/bonjour` | (없음) | 엔드포인트 매칭 실패. 우리 델리게이트가 직접 응답했다 |

**정적 파일은 엔드포인트가 아니다.** 이 차이가 인증·권한 부여 미들웨어의 위치를 결정한다.

### 클래스로 만드는 미들웨어

인라인이 아니라 재사용 가능한 미들웨어를 만들려면 `UseMiddleware<T>` 규약을 따른다. `T`는 다음 둘을 가져야 한다.

- 다음 파이프라인 구성 요소를 받는 `RequestDelegate` 매개변수를 가진 생성자
- `HttpContext` 매개변수를 받고 `Task`를 반환하는 `Invoke` 메서드

```csharp
public sealed class RequestTimingMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<RequestTimingMiddleware> _logger;

    public RequestTimingMiddleware(RequestDelegate next,
                                   ILogger<RequestTimingMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task Invoke(HttpContext context)
    {
        long start = Stopwatch.GetTimestamp();
        try
        {
            await _next(context);
        }
        finally
        {
            TimeSpan elapsed = Stopwatch.GetElapsedTime(start);   // ※.NET 7
            _logger.LogInformation("{Path} took {Elapsed} ms",
                context.Request.Path, elapsed.TotalMilliseconds);
        }
    }
}
```

```csharp
app.UseMiddleware<RequestTimingMiddleware>();
```

> **⚠️ 미들웨어 클래스는 싱글턴이다 — 생성자로 스코프 서비스를 받지 마라**
>
> `UseMiddleware<T>`는 인스턴스를 **애플리케이션 수명 동안 딱 한 번** 만든다. 생성자에 `DbContext`나 다른 스코프 서비스를 받으면, 첫 요청의 인스턴스가 영원히 붙잡힌다. 이것이 다음에 볼 포획 의존성이다.
>
> 미들웨어에서 스코프 서비스가 필요하면 **`Invoke`의 매개변수로 받아라.** ASP.NET Core가 요청마다 주입한다.
>
> ```csharp
> public async Task Invoke(HttpContext context, IOrderService orders)
> {
>     // orders는 이 요청의 스코프에서 온다
>     await _next(context);
> }
> ```

> **⚠️ 미들웨어 순서는 문서가 아니라 코드다**
>
> `UseAuthentication` → `UseAuthorization` → `MapControllers` 순서를 뒤집으면 인증이 적용되지 않은 채로 엔드포인트가 실행된다. **예외도, 경고도 나지 않는다.** 조용히 열린 API가 된다.
>
> 지켜야 할 기본 골격은 다음과 같다.
>
> ```text
> UseExceptionHandler / UseDeveloperExceptionPage
>   → UseHsts → UseHttpsRedirection
>   → UseStaticFiles
>   → UseRouting
>   → UseCors
>   → UseAuthentication → UseAuthorization
>   → Map*  (엔드포인트 실행)
> ```
>
> `UseStaticFiles`가 `UseAuthorization`보다 **앞에** 있다는 점을 특히 보라. `wwwroot`의 파일은 권한 검사를 거치지 않는다. 비공개 파일을 `wwwroot`에 두면 안 되는 이유다.

`UseRouting`과 `UseEndpoints`를 명시적으로 나누는 형태도 있다.

- `UseRouting` — **라우팅 결정이 내려지는 지점**을 표시한다.
- `UseEndpoints` — **선택된 엔드포인트가 실행되는 지점**을 표시한다.

지역화나 권한 부여처럼 이 둘 사이에서 도는 미들웨어는 `context.GetEndpoint()`로 선택된 엔드포인트를 볼 수 있고, 필요하면 다른 엔드포인트로 바꿀 수도 있다. 엔드포인트 라우팅이라는 이름은 **라우트 테이블을 엔드포인트의 컴파일된 트리로 표현하기 때문에** 붙었다. 이 트리를 걷는 것이 옛 방식보다 빠르다.

> **📌 라우트 단락(short-circuit) ※ASP.NET Core 8**
>
> 라우팅이 엔드포인트를 매칭한 뒤에도 나머지 미들웨어 파이프라인이 전부 돌고 나서야 엔드포인트 로직이 호출된다. 그 시간이 아깝다면 즉시 호출하고 응답하게 만들 수 있다.
>
> ```csharp
> app.MapGet("/", () => "Hello World").ShortCircuit();
> app.MapShortCircuit(404, "robots.txt", "favicon.ico");
> ```
>
> 두 번째 형태는 더 처리할 필요 없는 리소스에 404(또는 지정한 상태 코드)로 즉답한다.

### 의존성 주입 — 세 가지 수명

`builder.Services`는 `IServiceCollection`이다. 여기 등록한 것을 프레임워크와 애플리케이션 코드가 생성자 주입으로 받는다. 수명은 셋뿐이다.

| 수명 | 등록 메서드 | 인스턴스 생성 시점 | 폐기 시점 | 대표 용도 |
|---|---|---|---|---|
| **Transient** | `AddTransient<T>` | **요청될 때마다** 새로 | 자신을 만든 스코프가 끝날 때 | 가볍고 상태 없는 것 |
| **Scoped** | `AddScoped<T>` | **클라이언트 요청당 한 번** | 응답이 클라이언트로 반환될 때 | `DbContext`, 요청 컨텍스트, 리포지터리 |
| **Singleton** | `AddSingleton<T>` | 최초 요청 시 한 번 (또는 등록 시 인스턴스 제공) | 애플리케이션 종료 시 | 캐시, 구성, 스레드 안전한 상태 없는 서비스 |

ASP.NET Core에서 **"스코프"는 곧 HTTP 요청**이다. 프레임워크가 요청 시작 시 `IServiceScope`를 만들고, 응답을 다 쓴 뒤 `Dispose`한다.

```text
요청 하나의 수명과 서비스 수명

  요청 도착
    │
    ├─▶ IServiceScope 생성 ────────────────────────────┐
    │                                                  │
    │   미들웨어 파이프라인 실행                          │
    │     ├── Singleton 서비스: 앱 시작 때부터 있던 것 재사용
    │     ├── Scoped   서비스: 이 스코프에서 최초 1회 생성 ──┐
    │     └── Transient 서비스: 요청될 때마다 새로 생성      │
    │                                                  │  │
    │   엔드포인트 실행 (컨트롤러 / Razor Page / 델리게이트) │  │ 같은
    │     └── 같은 Scoped 인스턴스를 받는다  ◀─────────────┘  │ 인스턴스
    │                                                  │
    │   응답 전송                                        │
    │                                                  │
    └─▶ scope.Dispose() ───────────────────────────────┘
          · Scoped·Transient 중 IDisposable인 것 전부 Dispose
          · 여기서 DbContext의 커넥션이 풀로 반환된다
```

주요 등록 확장 메서드는 다음과 같다. 상위 메서드가 하위 메서드를 호출하는 구조다.

| 메서드 | 등록하는 서비스 |
|---|---|
| `AddMvcCore` | 요청 라우팅과 컨트롤러 호출에 필요한 최소 집합 |
| `AddAuthorization` | 인증·권한 부여 서비스 |
| `AddDataAnnotations` | MVC 데이터 주석 서비스 |
| `AddCacheTagHelper` | MVC 캐시 태그 도우미 서비스 |
| `AddApiExplorer` | 웹 API 탐색기 서비스 (OpenAPI 문서 생성의 기반) |
| `AddCors` | 교차 출처 리소스 공유(CORS) 지원 |
| `AddFormatterMappings` | URL 형식과 미디어 타입 간 매핑 |
| `AddViews` | 기본 규약을 포함한 `.cshtml` 뷰 지원 |
| `AddRazorViewEngine` | Razor 뷰 엔진 지원 (`@` 기호 처리 포함) |
| `AddRazorPages` | `AddMvcCore` + `AddAuthorization` + `AddDataAnnotations` + `AddCacheTagHelper` + Razor 뷰 엔진 |
| `AddControllers` | `AddMvcCore` + `AddAuthorization` + `AddDataAnnotations` + `AddCacheTagHelper` + `AddApiExplorer` + `AddCors` + `AddFormatterMappings`. **뷰·페이지 서비스는 없다** — 웹 API용 |
| `AddControllersWithViews` | `AddControllers`의 전부 + `AddViews` + `AddRazorViewEngine`. MVC 웹사이트용 |
| `AddMvc` | `AddControllersWithViews`와 유사하지만 **하위 호환용으로만** 써야 한다 |
| `AddDbContext<T>` | `DbContext` 파생 타입과 선택적 `DbContextOptions<TContext>` |

> **📌 키 지정 서비스 ※.NET 8**
>
> 같은 인터페이스의 구현을 여러 개 등록하고 키로 구분해 꺼낼 수 있다.
>
> ```csharp
> builder.Services.AddKeyedSingleton<IMemoryCache, BigCache>("big");
> builder.Services.AddKeyedSingleton<IMemoryCache, SmallCache>("small");
>
> class BigCacheConsumer([FromKeyedServices("big")] IMemoryCache cache)
> {
>     public object? GetData() => cache.Get("data");
> }
>
> class SmallCacheConsumer(IKeyedServiceProvider keyedServiceProvider)
> {
>     public object? GetData() =>
>         keyedServiceProvider.GetRequiredKeyedService<IMemoryCache>("small");
> }
> ```
>
> 이전에는 팩토리를 직접 만들거나 서드파티 컨테이너로 갈아타야 했던 시나리오다.

### 포획 의존성 — 이 절의 핵심 함정

**긴 수명의 서비스가 짧은 수명의 서비스를 붙잡는 것**을 포획 의존성(captive dependency)이라 한다.

```csharp
// 등록
builder.Services.AddSingleton<OrderProcessor>();   // 싱글턴!
builder.Services.AddDbContext<ShopContext>();      // 기본은 Scoped

// 구현
public sealed class OrderProcessor
{
    private readonly ShopContext _db;   // 문제 지점: 스코프 서비스를 싱글턴이 붙잡았다

    public OrderProcessor(ShopContext db) => _db = db;
}
```

무슨 일이 일어나는가.

1. 첫 요청에서 `OrderProcessor`가 만들어지면서 그 요청의 `ShopContext`를 받는다.
2. 요청이 끝나고 스코프가 `Dispose`되면서 `ShopContext`도 `Dispose`된다.
3. `OrderProcessor`는 싱글턴이므로 살아남는다. **폐기된 `ShopContext`를 든 채로.**
4. 두 번째 요청부터는 `ObjectDisposedException`이 나거나, 더 나쁘게는 여러 스레드가 하나의 `DbContext`를 동시에 두들긴다.

3권의 언어로 번역하면 이렇다. **싱글턴은 GC 루트다.** 63장에서 본 대로 정적 필드와 싱글턴이 붙잡은 객체 그래프는 절대 수집되지 않는다. 스코프 서비스를 붙잡은 싱글턴은 그 서비스가 참조하는 모든 것 — 변경 추적기에 있는 엔티티 전부, 그 엔티티가 참조하는 관련 엔티티 전부 — 을 gen2에 영구히 고정시킨다. 66.11절의 "정적 캐시" 누수 시나리오와 정확히 같은 형태다.

> **⚠️ 개발 환경에서만 잡아준다 — 프로덕션에서는 조용하다**
>
> ASP.NET Core는 **개발 환경에서** 기본적으로 스코프 검증을 켠다. 위 코드는 시작 시 `InvalidOperationException`으로 터진다.
>
> ```text
> Cannot consume scoped service 'ShopContext' from singleton 'OrderProcessor'.
> ```
>
> 문제는 **이 검증이 프로덕션(`ASPNETCORE_ENVIRONMENT=Production`)에서는 기본으로 꺼져 있다는 것**이다. 개발 환경에서 시작조차 못 하던 앱이 프로덕션에서는 멀쩡히 뜨고, 부하가 걸린 뒤에야 이상하게 죽는다.
>
> **모든 환경에서 켜라.** 시작 시 한 번 도는 검증이고, 프로덕션에서 조용히 죽는 것보다 시작 시 터지는 게 백 배 낫다.
>
> ```csharp
> builder.Host.UseDefaultServiceProvider((context, options) =>
> {
>     options.ValidateScopes = true;
>     options.ValidateOnBuild = true;   // 등록 시점에 그래프 전체를 검증
> });
> ```

> **⚠️ 검증이 잡지 못하는 포획도 있다**
>
> 스코프 검증은 **생성자 주입 그래프**만 본다. 다음은 검증을 통과하고 런타임에 깨진다.
>
> ```csharp
> public sealed class BadCache
> {
>     private readonly IServiceProvider _root;   // 루트 provider!
>     private ShopContext? _cached;
>
>     public BadCache(IServiceProvider root) => _root = root;
>
>     public ShopContext Get() =>
>         _cached ??= _root.GetRequiredService<ShopContext>();  // 처음 것을 영원히 캐시
> }
> ```
>
> 서비스 로케이터 패턴으로 스코프를 우회하면 컨테이너는 아무것도 알 수 없다. 싱글턴 안에서 스코프 서비스가 필요하면 **반드시 `IServiceScopeFactory`로 스코프를 열고 `using`으로 닫아라**(81.1절의 `QueueConsumer` 예제 참조).

수명 선택의 기준을 정리하면 이렇다.

| 질문 | 답이 예면 |
|---|---|
| 요청별 상태(사용자, 트랜잭션, 추적 중인 엔티티)를 갖는가 | **Scoped** |
| 스레드 안전하지 않은가 | **Scoped** 또는 **Transient** |
| 만드는 비용이 큰데 상태가 없고 스레드 안전한가 | **Singleton** |
| 만드는 비용이 작고 상태를 갖는가 | **Transient** |
| `DbContext`인가 | **Scoped** (예외는 81.6절) |

### 구성 — 환경별 계층

ASP.NET Core의 구성은 JSON 파일 기반이며 **환경 이름으로 계층화**된다.

```text
로드 순서 (뒤가 앞을 덮어쓴다)

  appsettings.json
    → appsettings.{환경이름}.json      (Development / Staging / Production)
      → 사용자 비밀(Development 한정)
        → 환경 변수
          → 명령줄 인자
```

환경 이름은 `ASPNETCORE_ENVIRONMENT` 환경 변수(또는 `launchSettings.json`의 프로필)로 정한다.

```csharp
if (app.Environment.IsDevelopment())
{
    app.UseDeveloperExceptionPage();   // 스택 추적, 상세 예외 정보
}
else
{
    app.UseExceptionHandler("/Error"); // 단순한 오류 페이지
    app.UseHsts();
}
```

`IHostEnvironment`에는 `IsDevelopment()`, `IsStaging()`, `IsProduction()`, 그리고 임의 문자열과 비교하는 `IsEnvironment(string)`이 있다. **전부 대소문자를 구분하지 않는다.**

구성 값은 `IConfiguration`으로 읽는다.

```csharp
var config = builder.Configuration;                    // 빌드 전
string? cs = config.GetConnectionString("Northwind");
// var config = app.Configuration;                     // 빌드 후에도 접근 가능
```

문자열 키로 읽는 대신 **옵션 패턴**으로 강력한 타입을 주입받는 것이 낫다.

```csharp
public sealed class DealerInfo
{
    public string Name { get; set; } = string.Empty;
    public string City { get; set; } = string.Empty;
}
```

```csharp
builder.Services.Configure<DealerInfo>(
    builder.Configuration.GetSection(nameof(DealerInfo)));
```

```csharp
public IActionResult Index([FromServices] IOptionsMonitor<DealerInfo> dealerMonitor)
{
    DealerInfo dealer = dealerMonitor.CurrentValue;
    return View(dealer);
}
```

`IOptions<T>` 계열은 네 가지가 있고 차이가 중요하다.

| 인터페이스 | 값을 읽는 법 | 변경 감지 | 수명 | 언제 쓰나 |
|---|---|---|---|---|
| `IOptions<T>` | `.Value` | **없다.** 앱 시작 시 한 번 계산 | Singleton | 절대 안 바뀌는 설정. 하위 호환용 루트 인터페이스 |
| `IOptionsSnapshot<T>` | `.Value` | 요청마다 다시 계산 | **Scoped** | 요청 단위로 일관된 값이 필요할 때 |
| `IOptionsMonitor<T>` | `.CurrentValue`, `.Get(name)` | **있다.** `OnChange` 콜백, 구성 리로드, 명명된 옵션, 선택적 무효화 | Singleton | 싱글턴 서비스에서 변경을 반영해야 할 때 |
| `IOptionsFactory<T>` | — | — | Singleton | `T`의 새 인스턴스를 만드는 확장 지점 |

여기에 `IOptionsMonitorCache<T>`가 캐싱과 전체·부분 무효화를 담당한다.

> **⚠️ 싱글턴에 `IOptionsSnapshot<T>`을 주입하면 포획 의존성이다**
>
> `IOptionsSnapshot<T>`은 **스코프 서비스**다. 싱글턴 서비스의 생성자에서 받으면 앞에서 본 그 함정에 그대로 빠진다. 싱글턴에서는 `IOptionsMonitor<T>`를 써라. 스코프 검증을 켜 두었다면 시작 시 잡힌다.

### 최소 API vs 컨트롤러

같은 HTTP 엔드포인트를 두 가지로 쓸 수 있다.

```csharp
// 최소 API
app.MapGet("/products/{id:int}", async (int id, ShopContext db) =>
    await db.Products.FindAsync(id) is Product p
        ? Results.Ok(p)
        : Results.NotFound());
```

```csharp
// 컨트롤러
[ApiController]
[Route("api/[controller]")]
public sealed class ProductsController : ControllerBase
{
    private readonly ShopContext _db;
    public ProductsController(ShopContext db) => _db = db;

    [HttpGet("{id:int}")]
    [ProducesResponseType(StatusCodes.Status200OK, Type = typeof(Product))]
    [ProducesResponseType(StatusCodes.Status404NotFound)]
    public async Task<IActionResult> Get(int id)
        => await _db.Products.FindAsync(id) is Product p ? Ok(p) : NotFound();
}
```

| 축 | 최소 API | 컨트롤러 |
|---|---|---|
| **Native AOT** | **지원한다** (.NET 8의 `webapiaot` 템플릿) | .NET 8 기준 **지원하지 않는다** — 런타임 코드 생성에 의존한다 |
| **시작 시간·메모리** | 더 작다. 리플렉션 기반 탐색이 적다 | 컨트롤러 탐색·모델 바인딩 메타데이터 구축 비용이 있다 |
| **필터 파이프라인** | 엔드포인트 필터(`AddEndpointFilter`) | 액션 필터, 리소스 필터, 예외 필터, 결과 필터 전부 |
| **모델 바인딩** | 매개변수 기반. 규칙이 단순하고 명시적 | 규약 기반. `[FromBody]`·`[FromQuery]` 등 풍부하지만 암묵적 |
| **규약** | 없다. 라우트를 직접 다 쓴다 | `[Route("api/[controller]")]` 같은 규약으로 일관성 확보 |
| **코드 조직** | 엔드포인트가 늘면 `Program.cs`가 비대해진다 (그룹으로 분리 가능) | 파일·클래스 단위로 자연스럽게 나뉜다 |
| **단위 테스트** | 델리게이트를 직접 부르기 애매하다. 통합 테스트 위주 | 컨트롤러 클래스를 그냥 인스턴스화해 테스트할 수 있다 |
| **적합** | 엔드포인트 수 개~수십, 마이크로서비스, AOT 대상 | 수십~수백 엔드포인트, 버저닝·필터·복잡한 바인딩 |

최소 API가 커질 때는 라우트 그룹으로 나눈다.

```csharp
RouteGroupBuilder products = app.MapGroup("/products")
                                .WithTags("Products")
                                .RequireAuthorization();

products.MapGet("/", GetAllProducts);
products.MapGet("/{id:int}", GetProductById);
products.MapPost("/", CreateProduct);
```

> **💡 "최소 API가 더 빠르다"는 절반만 맞다**
>
> 최소 API의 이점은 대부분 **시작 시간과 메모리 풋프린트**에서 온다. 요청 하나를 처리하는 정상 상태 처리량은 두 방식이 크게 다르지 않다 — 둘 다 같은 Kestrel, 같은 라우팅 트리, 같은 직렬화기를 쓴다.
>
> 그래서 최소 API를 고르는 진짜 이유는 성능이 아니라 **AOT 가능 여부**다. 짧게 살고 자주 뜨는 서버리스 함수나 스케일 투 제로 컨테이너라면 시작 시간이 곧 비용이고(81.10절), 이때 AOT를 켤 수 있느냐가 판을 가른다. 24시간 도는 서비스라면 컨트롤러의 구조적 이점을 포기할 이유가 별로 없다. 72.7절의 시작 시간 논의를 함께 보라.

### 요청 수명과 3권

ASP.NET Core에서 요청 하나는 **할당의 단위**다. 이것이 63장·65장과 만나는 지점이다.

| 요청마다 할당되는 것 | 어디로 가는가 |
|---|---|
| `HttpContext` 및 부속 객체 (풀링되지만 완전히는 아니다) | gen0 |
| `IServiceScope`와 그 안의 모든 스코프 서비스 | gen0 |
| `DbContext`와 변경 추적기가 물고 있는 엔티티 | 크기에 따라 gen0~LOH |
| 모델 바인딩 결과, 역직렬화된 DTO | gen0 |
| 응답 직렬화 버퍼 | 풀링(`ArrayPool`) 또는 gen0/LOH |

이상적으로는 **요청 하나가 만든 것 전부가 gen0에서 죽는다.** gen0 컬렉션은 싸다(64장). 문제는 요청이 gen0 컬렉션 하나보다 오래 살 때 생긴다 — 느린 외부 호출을 기다리는 동안 그 요청의 객체들이 gen1로, 다시 gen2로 승격된다. 66.12절이 다루는 **중년기 위기(mid-life crisis)** 패턴이 웹 애플리케이션에서 나타나는 전형적 형태다.

| 웹 앱에서 자주 필요해지는 3권 항목 | 왜 |
|---|---|
| **65.1절** 서버 GC | 웹 앱의 기본값이 서버 GC인 이유와, 컨테이너에서 그게 왜 문제가 되는지 |
| **65.7절** DATAS ※.NET 8+ | 코어 수 대비 작은 서비스의 힙 낭비를 자동으로 줄인다 |
| **63.9절** 숨은 할당 | 요청당 수백 바이트가 초당 수천 요청에서 무엇이 되는지 |
| **72.5절** 캐싱 계층 | 요청당 작업을 줄이는 가장 큰 지렛대 |
| **75장** 관측 가능성 | 요청 하나를 추적으로 따라가는 것이 웹 앱 디버깅의 기본기 |

## 81.4 Razor Pages와 MVC

### 서버 렌더링이라는 선택

Razor Pages와 MVC는 **HTML을 서버에서 만들어 보내는** 방식이다. 클라이언트는 브라우저의 기본 능력만 쓴다. 자바스크립트 프레임워크도, WebAssembly도, 상시 연결도 없다.

이 방식이 여전히 옳은 경우가 많다. 초기 로딩이 빠르고, 검색 엔진이 잘 읽고, 클라이언트 상태가 없으므로 서버를 마음대로 늘릴 수 있고, 비즈니스 로직이 전부 서버에 있으므로 자격 증명 없이 데이터베이스에 접근한다.

### 파일 종류를 먼저 정리한다

ASP.NET Core의 파일 형식들은 비슷해 보이지만 다르다. 이 차이를 모르면 자기 프로젝트를 구현하다 크게 헷갈린다.

| 기술 | 특별한 파일명 | 확장자 | 지시문 |
|---|---|---|---|
| Razor 컴포넌트 (Blazor) | — | `.razor` | — |
| Razor 컴포넌트 (페이지 라우팅 포함) | — | `.razor` | `@page` |
| Razor Page | — | `.cshtml` | `@page` |
| Razor 뷰 (MVC) | — | `.cshtml` | — |
| Razor 레이아웃 | — | `.cshtml` | — |
| Razor 뷰 시작 | `_ViewStart` | `.cshtml` | — |
| Razor 뷰 가져오기 | `_ViewImports` | `.cshtml` | — |

지시문(`@page` 같은 것)은 파일 내용 **맨 위**에 온다. 특별한 파일명이 없는 형식은 아무 이름이나 붙일 수 있다.

레이아웃 파일이 레이아웃인 이유는 파일 이름이나 확장자가 아니다. **다른 Razor 파일의 `Layout` 속성으로 지정되었기 때문**이다.

```razor
@{
    Layout = "_MyCustomLayout";  // 확장자는 쓰지 않는다
}
```

공유되는 Razor 파일(레이아웃, 부분 뷰)은 **밑줄로 시작하는 이름**을 쓰는 것이 관례다. `_ViewStart.cshtml`, `_Layout.cshtml`, `_Product.cshtml` 같은 식이다.

> **⚠️ 확장자와 지시문을 틀리면 예상 못 한 동작이 나온다**
>
> `.cshtml` 파일에 `@page`를 빠뜨리면 Razor Page가 아니라 MVC 뷰가 된다. 라우팅되지 않으므로 URL로 접근하면 404가 난다. 반대로 MVC 뷰에 `@page`를 넣으면 컨트롤러를 거치지 않고 직접 라우팅되면서, 컨트롤러가 넣어줄 뷰 모델이 없어 `NullReferenceException`이 날 수 있다. **컴파일 오류는 나지 않는다.**

### Razor Pages — 페이지가 단위다

Razor Page는 `@page` 지시문으로 시작하고, 파일 경로가 곧 URL이다. `Pages/Suppliers.cshtml`은 `/suppliers`로 접근된다.

로직은 코드 비하인드 파일(`.cshtml.cs`)의 `PageModel` 파생 클래스에 넣는다.

```csharp
// Pages/Suppliers.cshtml.cs
using Microsoft.AspNetCore.Mvc.RazorPages;
using Northwind.EntityModels;

public class SuppliersModel : PageModel
{
    private readonly NorthwindContext _db;

    public SuppliersModel(NorthwindContext db) => _db = db;

    public IEnumerable<string> Suppliers { get; set; } = Enumerable.Empty<string>();

    [BindProperty]
    public Supplier? Supplier { get; set; }

    public void OnGet()
    {
        ViewData["Title"] = "공급자 목록";
        Suppliers = _db.Suppliers.Select(s => s.CompanyName).OrderBy(n => n);
    }

    public IActionResult OnPost()
    {
        if (Supplier is not null && ModelState.IsValid)
        {
            _db.Suppliers.Add(Supplier);
            _db.SaveChanges();
            return RedirectToPage("/Suppliers");
        }
        OnGet();
        return Page();
    }
}
```

```razor
@page
@model SuppliersModel
<h1>@ViewData["Title"]</h1>
<table class="table">
  @foreach (string name in Model.Suppliers)
  {
    <tr><td>@name</td></tr>
  }
</table>
```

핵심 규약 세 가지가 있다.

- **핸들러 메서드 이름이 HTTP 메서드를 결정한다.** `OnGet`/`OnGetAsync`, `OnPost`/`OnPostAsync`, `OnPut`, `OnDelete`.
- **`[BindProperty]`** 는 폼 값을 그 속성에 바인딩한다. 기본적으로 GET에는 바인딩하지 않는다(`SupportsGet = true`로 바꿀 수 있다).
- **`RedirectToPage`** 로 POST 후 리다이렉트한다. 새로고침 시 재전송을 막는 Post-Redirect-Get 패턴이다.

### MVC — 컨트롤러가 단위다

MVC에서는 컨트롤러 클래스가 여러 액션 메서드를 갖고, 각 액션이 뷰를 고른다. 라우트 `/home/index`는 `HomeController`의 `Index` 액션을 뜻한다.

Razor Pages 대비 이득은 **한 컨트롤러가 여러 뷰를 지휘할 때** 나온다. `CarsController` 하나가 `Index`, `Details`, `Create`(GET/POST), `Edit`(GET/POST), `Delete`(GET/POST)를 갖는 CRUD는 MVC의 전형이다.

### 뷰에 데이터를 전달하는 방법

강력한 타입 뷰 모델이 기본이자 최선이다. 그 외에 세 가지가 더 있다.

| 전달 수단 | 타입 | 수명 | 언제 쓰나 |
|---|---|---|---|
| 뷰 모델 | 임의 클래스 | 요청 | **기본으로 이것을 써라.** 컴파일 타임에 검증된다 |
| `TempData` | 딕셔너리 (세션 기반) | **다음 요청까지** | 다른 액션 메서드로 리다이렉트할 때 값 전달 |
| `ViewData` | `ViewDataDictionary` (문자열 키) | 요청 | 뷰 제목처럼 작은 부수 데이터 |
| `ViewBag` | `dynamic` | 요청 | `ViewData`와 같은 저장소를 동적으로 접근 |

> **⚠️ `ViewBag`은 오타가 컴파일되지 않는다**
>
> `ViewBag`은 `dynamic`이므로 `ViewBag.Titel = "..."`이라고 써도 컴파일된다. 뷰에서 `@ViewBag.Title`을 읽으면 `null`이 나오고 제목이 빈칸으로 렌더링된다. 예외도 안 난다. **`ViewData`와 `ViewBag`은 같은 저장소를 공유**하므로 한쪽에서 쓰고 다른 쪽에서 읽어도 되지만, 그만큼 오타 사고가 잦다.
>
> 그리고 `TempData`는 **세션을 요구한다.** 세션 미들웨어를 등록하지 않았거나 분산 환경에서 세션이 스티키하지 않으면 조용히 사라진다.

### 태그 도우미

태그 도우미는 서버 측 코드가 HTML 요소를 생성·수정하게 해준다. 옛 HTML 도우미(`Html.ActionLink` 등)를 대체한다.

| 태그 도우미 | 대체하는 HTML 도우미 |
|---|---|
| Form | `Html.BeginForm`, `Html.BeginRouteForm`, `Html.AntiForgeryToken` |
| Anchor | `Html.ActionLink` |
| Input | `Html.TextBox`/`TextBoxFor`, `Html.Editor`/`EditorFor` |
| TextArea | `Html.TextAreaFor` |

```razor
<a asp-controller="Cars" asp-action="Details" asp-route-id="@car.Id">자세히</a>

<form asp-controller="Cars" asp-action="Create" method="post">
  <input asp-for="Car.Name" class="form-control" />
  <span asp-validation-for="Car.Name" class="text-danger"></span>
  <button type="submit" class="btn btn-primary">저장</button>
</form>
```

태그 도우미가 HTML 도우미보다 나은 점은 **HTML처럼 보인다는 것**이다. 프런트엔드 담당자가 읽고 수정할 수 있다. `<form>` 태그 도우미는 위조 방지 토큰(`__RequestVerificationToken`)도 자동으로 넣는다.

### Razor Pages vs MVC 선택 기준

| 상황 | Razor Pages | MVC |
|---|---|---|
| 화면 하나 = 진입점 하나 (목록, 상세, 폼) | **적합** | 보일러플레이트가 많다 |
| 화면 하나에 여러 컨트롤러의 데이터가 얽힌다 | 어색해진다 | **적합** |
| 액션 단위 단위 테스트 비중이 크다 | `PageModel`도 테스트 가능하지만 덜 관례적 | **적합** |
| 팀에 MVC 경험이 많다 | 학습 곡선이 있다 | **적합** |
| 코드 조직의 응집도 | 페이지와 로직이 나란히 있다 | 컨트롤러·뷰·모델이 흩어진다 |
| 라우팅 | 파일 경로 = URL. 예측 가능 | 라우트 템플릿. 유연하지만 복잡 |

**한 프로젝트에서 둘을 섞어 써도 된다.** `AddControllersWithViews()`와 `AddRazorPages()`를 함께 호출하고 `MapControllerRoute()`와 `MapRazorPages()`를 함께 등록하면 된다. 실제로 ASP.NET Core Identity의 기본 UI는 Razor Pages로 되어 있어서, MVC 프로젝트에도 Razor Pages가 딸려 들어온다.

### 서버 렌더링과 3권

| 만나는 지점 | 무슨 일이 일어나는가 | 참조 |
|---|---|---|
| **문자열 할당** | 뷰 렌더링은 본질적으로 대량의 문자열 조립이다. Razor는 `TextWriter`에 직접 쓰지만 `@Model.Name` 같은 표현식마다 `ToString()` 호출과 박싱이 숨어 있다 | 63.9절 |
| **LOH** | 큰 테이블을 렌더링한 HTML 응답이 85,000바이트를 넘으면 응답 버퍼가 LOH로 간다 | 62장, 63.4절 |
| **캐싱** | `[ResponseCache]`, 출력 캐싱(`AddOutputCache` ※.NET 7), 캐시 태그 도우미 — 렌더링 자체를 건너뛰는 것이 가장 큰 최적화다 | 72.5절 |
| **N+1** | 뷰 안에서 `@foreach`를 돌며 지연 로딩된 탐색 속성에 접근하면 렌더링 도중에 쿼리가 나간다 | **72.4절** |

> **⚠️ 뷰 안에서 데이터베이스에 접근하지 마라**
>
> Razor 뷰에서 `@Model.Orders.Count()`를 쓰는 순간, 그것이 지연 로딩되는 탐색 속성이면 **HTML을 스트리밍하는 도중에 SQL이 나간다.** 응답 헤더는 이미 나갔으므로 예외가 나도 오류 페이지를 보여줄 수 없다. 브라우저는 잘린 HTML을 받는다.
>
> 데이터는 `OnGet`/액션 메서드에서 전부 확정해 뷰 모델에 담아 넘겨라. 이것이 지연 로딩을 웹 앱에서 끄는 것을 권하는 가장 큰 이유다(81.6절).

## 81.5 웹 서비스 만들기와 소비하기 — REST, 문서화, 테스트

### 웹 API는 뷰를 반환하지 않는다

MVC 컨트롤러가 Razor 뷰를 호출해 HTML을 만드는 반면, 웹 API 컨트롤러는 **콘텐츠 협상(content negotiation)** 으로 클라이언트가 원하는 형식의 데이터를 반환한다. JSON, XML, 또는 `X-WWW-FORM-URLENCODED` 같은 형식이다.

```text
firstName=Mark&lastName=Price&jobtitle=Author
```

현대 웹 서비스에서 가장 많이 쓰는 형식은 **JSON**이다. 간결하고 브라우저의 자바스크립트에서 네이티브로 동작한다.

ASP.NET Core 웹 API 프로젝트의 기본 출력 포맷터는 넷이다.

```text
Default output formatters:
  HttpNoContentOutputFormatter
  StringOutputFormatter, Media types: text/plain
  StreamOutputFormatter
  SystemTextJsonOutputFormatter, Media types: application/json, text/json, application/*+json
```

XML이 필요하면 명시적으로 추가한다.

```csharp
builder.Services.AddControllers()
    .AddXmlDataContractSerializerFormatters()
    .AddXmlSerializerFormatters();
```

> **⚠️ XML 직렬화는 순환 참조에서 터진다**
>
> EF Core 엔티티를 그대로 반환하면 `Customer.Orders` → `Order.Customer` 같은 순환이 생긴다. `System.Text.Json`은 `ReferenceHandler` 설정으로 다룰 수 있지만, `XmlSerializer`는 컬렉션 탐색 속성을 만나면 초기화 단계에서 예외를 던진다.
>
> ```text
> An error occurred while trying to create an XmlSerializer for the type
> 'Northwind.EntityModels.Customer'. ... 'Orders' of type
> 'System.Collections.Generic.ICollection`1[...]'
> ```
>
> 근본 해법은 하나다. **엔티티를 API 표면에 노출하지 말고 DTO를 반환하라.** 78장의 API 설계 원칙 그대로다. 엔티티는 데이터베이스 스키마의 모양이고 DTO는 계약의 모양인데, 이 둘을 하나로 묶으면 스키마 변경이 곧 API 파괴적 변경이 된다.

### HTTP 메서드와 상태 코드

REST 스타일 서비스는 HTTP 의미론을 그대로 쓴다. 컨트롤러 메서드에 특성을 붙여 어떤 메서드에 응답할지 정한다.

| 특성 | 응답하는 요청 | 의미 |
|---|---|---|
| `[HttpGet]`, `[HttpHead]` | GET, HEAD | 리소스 조회. HEAD는 헤더만 |
| `[HttpPost]` | POST | 새 리소스 생성, 또는 서비스가 정의한 동작 수행 |
| `[HttpPut]`, `[HttpPatch]` | PUT, PATCH | 기존 리소스 갱신. PUT은 전체 교체, PATCH는 부분 갱신 |
| `[HttpDelete]` | DELETE | 리소스 제거 |
| `[HttpOptions]` | OPTIONS | 지원하는 동작 안내 |

응답을 만드는 `ControllerBase` 도우미 메서드는 다음과 같다.

| 메서드 | 상태 코드 | 흔히 쓰는 자리 |
|---|---|---|
| `Ok` | 200 | GET 응답. 리소스를 클라이언트가 선호하는 형식으로 변환해 반환 |
| `CreatedAtRoute` | 201 | POST로 리소스를 빠르게 생성했을 때. 새 리소스 경로를 함께 반환 |
| `Accepted` | 202 | POST/PUT/PATCH/DELETE가 오래 걸리는 백그라운드 처리를 촉발했을 때 |
| `NoContent` | 204 | PUT/PATCH/DELETE 응답에 본문이 필요 없을 때 |
| `BadRequest` | 400 | 선택적으로 상세 메시지 문자열을 함께 |
| `NotFound` | 404 | `ProblemDetails` 본문이 자동으로 채워진다 |

반환 타입은 상황에 따라 셋 중 하나를 고른다.

| 선언 | 언제 |
|---|---|
| 구체 타입 (`Product`, `IEnumerable<Product>`) | 항상 성공하고 항상 같은 타입을 반환할 때 |
| `ActionResult<T>` | **단일 타입**을 반환하지만 상태 코드가 여러 가지일 때 |
| `IActionResult` | 입력이나 상태에 따라 **서로 다른 타입**을 반환할 수 있을 때 |

```csharp
[HttpGet("{id}")]
[ProducesResponseType(StatusCodes.Status200OK, Type = typeof(Customer))]
[ProducesResponseType(StatusCodes.Status404NotFound)]
public async Task<IActionResult> GetCustomer(string id)
{
    Customer? c = await _repo.RetrieveAsync(id);
    if (c is null) return NotFound();   // 404
    return Ok(c);                        // 200 + 직렬화된 본문
}
```

> **💡 `[ProducesResponseType]`은 주석이 아니라 계약이다**
>
> 이 특성은 OpenAPI 문서 생성기가 읽어서 "이 엔드포인트는 200과 404를 낼 수 있다"고 공개 문서에 적는다. 클라이언트 코드 생성기는 그 문서를 보고 강력한 타입 클라이언트를 만든다. **즉 이 특성을 빠뜨리면 소비자가 잘못된 클라이언트를 생성한다.**
>
> API 분석기 패키지를 참조하면 특성을 빠뜨린 액션 메서드에 경고를 준다. 이것을 형식 문서의 일부로 취급하라.

### 라우트 제약 조건

라우트 매개변수에 콜론으로 제약을 붙이면 데이터 타입과 검증 규칙을 라우팅 단계에서 강제할 수 있다.

| 제약 | 예 | 설명 |
|---|---|---|
| `required` | `{id:required}` | 매개변수가 제공되었다 |
| `int`, `long` | `{id:int}` | 해당 크기의 정수 |
| `decimal`, `double`, `float` | `{unitprice:decimal}` | 해당 크기의 실수 |
| `bool` | `{discontinued:bool}` | `true`/`false` 대소문자 무시 매칭 |
| `datetime` | `{hired:datetime}` | 인바리언트 문화권 날짜·시각 |
| `guid` | `{id:guid}` | GUID 값 |
| `minlength(n)`, `maxlength(n)`, `length(n)`, `length(n, m)` | `{title:length(5, 25)}` | 정의된 최소·최대 길이 |
| `min(n)`, `max(n)`, `range(n, m)` | `{age:range(18, 65)}` | 정의된 최소·최대 범위의 정수 |
| `alpha`, `regex` | `{firstname:alpha}`, `{id:regex(^[A-Z]{{5}}$)}` | 알파벳 문자, 또는 정규식 매칭 |

여러 제약은 콜론으로 이어 붙인다.

```csharp
[Route("employees/{years:int:minlength(3)}")]
public Employees[] GetLoyalEmployees(int years)
```

정규식 제약에는 `RegexOptions.IgnoreCase | RegexOptions.Compiled | RegexOptions.CultureInvariant`가 자동으로 적용된다. 그리고 **정규식 토큰은 이스케이프해야 한다** — `\`는 `\\`로, `{`는 `{{`로, `}`는 `}}`로. 또는 축자 문자열 리터럴을 쓴다.

`IRouteConstraint`를 구현해 커스텀 제약을 만들 수도 있다.

> **⚠️ 라우트 제약은 유효성 검사가 아니다**
>
> `{id:int}`가 매칭에 실패하면 400이 아니라 **404**가 난다. 라우팅 입장에서는 "그런 엔드포인트가 없다"이기 때문이다. 클라이언트에게 "id는 정수여야 한다"는 오류를 돌려주고 싶다면 제약 대신 모델 유효성 검사(`ModelState`)를 써야 한다.
>
> 라우트 제약의 진짜 용도는 **오버로드 구분**이다. `/products/{id:int}`와 `/products/{name:alpha}`를 나란히 둘 수 있게 해준다.

### 문제 상세 — 오류의 표준 형식

`[ApiController]` 특성이 붙은 컨트롤러는 4xx 응답 본문을 자동으로 `ProblemDetails` JSON 문서로 채운다. RFC 7807이 정의하는 형식이다.

```csharp
return BadRequest(new ProblemDetails
{
    Status = StatusCodes.Status400BadRequest,
    Title = "고객을 삭제하지 못했다.",
    Detail = $"ID {id}의 고객은 존재하지만 삭제에 실패했다.",
    Instance = HttpContext.Request.Path
});
```

`AddProblemDetails()`(※.NET 7)를 등록하면 처리되지 않은 예외와 상태 코드 페이지도 같은 형식으로 통일된다.

### 문서화 — OpenAPI

**OpenAPI 명세**는 REST 스타일 API의 계약을 사람과 기계가 모두 읽을 수 있는 형식으로 기술한다. 개발자는 이 명세로부터 선호하는 언어의 강력한 타입 클라이언트 코드를 자동 생성할 수 있다.

.NET 8 기준 웹 API 템플릿은 Swashbuckle을 쓴다.

```xml
<PackageReference Include="Swashbuckle.AspNetCore" Version="6.4.0" />
```

```csharp
using Swashbuckle.AspNetCore.SwaggerUI;   // SubmitMethod를 쓰기 위해

builder.Services.AddEndpointsApiExplorer();
builder.Services.AddSwaggerGen();

// ...

if (app.Environment.IsDevelopment())
{
    app.UseSwagger();
    app.UseSwaggerUI(c =>
    {
        c.SwaggerEndpoint("/swagger/v1/swagger.json", "Northwind Service API Version 1");
        c.SupportedSubmitMethods(new[] {
            SubmitMethod.Get, SubmitMethod.Post,
            SubmitMethod.Put, SubmitMethod.Delete });
    });
}
```

Swagger UI는 명세로부터 **시각적 테스트 기능이 딸린 문서 페이지**를 자동 생성한다. `/swagger`로 접근해 엔드포인트를 펼치고 Try it out을 눌러 실제 요청을 보낼 수 있다.

> **📌 .NET 9에서 템플릿이 Swashbuckle을 버렸다 ※.NET 9**
>
> .NET 9의 웹 API 템플릿은 Swashbuckle 대신 Microsoft가 직접 제공하는 `Microsoft.AspNetCore.OpenApi`를 쓴다.
>
> ```csharp
> builder.Services.AddOpenApi();
> // ...
> if (app.Environment.IsDevelopment())
> {
>     app.MapOpenApi();   // /openapi/v1.json
> }
> ```
>
> 이것은 **명세 문서 생성만** 한다. Swagger UI 같은 대화형 UI는 포함하지 않으므로, 필요하면 Scalar나 Swagger UI를 별도로 붙여야 한다. .NET 8 프로젝트를 .NET 9로 올릴 때 흔히 놀라는 지점이다.

> **⚠️ Swagger UI를 프로덕션에 노출할지는 비즈니스 결정이다**
>
> 템플릿은 개발 환경에서만 Swagger를 켠다. 내부 API라면 프로덕션에도 켜 두는 것이 편리하다. 하지만 공개 API라면 **엔드포인트 목록, 매개변수, 스키마가 전부 공격 표면의 지도**가 된다. 기본값을 무심코 바꾸지 마라.

### HTTP 로깅

요청·응답을 통째로 로그로 남기는 미들웨어가 있다. 테스트에 유용하다.

```csharp
using Microsoft.AspNetCore.HttpLogging;

builder.Services.AddHttpLogging(options =>
{
    options.LoggingFields = HttpLoggingFields.All;
    options.RequestBodyLogLimit = 4096;    // 기본값은 32K
    options.ResponseBodyLogLimit = 4096;
});

// ...
app.UseHttpLogging();
```

W3C 표준 형식으로 남기는 `AddW3CLogging`도 있다. ASP.NET Core 7 이상에서는 기록할 추가 요청 헤더를 지정할 수 있다.
```csharp
services.AddW3CLogging(options =>
{
    options.AdditionalRequestHeaders.Add("x-forwarded-for");
    options.AdditionalRequestHeaders.Add("x-client-ssl-protocol");
});
```

> **⚠️ HTTP 로깅은 성능을 떨어뜨리고 비밀을 흘린다**
>
> `HttpLoggingFields.All`은 본문까지 전부 로그로 쓴다. 요청마다 문자열을 만들어 I/O를 하므로 처리량이 크게 떨어지고(63.9절의 문자열 할당이 요청당 수 KB로 늘어난다), **로그인 요청의 비밀번호와 토큰이 그대로 로그에 남는다.** 프로덕션에서 켜려면 `LoggingFields`를 좁히고 민감한 헤더를 반드시 제외하라. 상시 계측이 목적이라면 75장의 구조적 로그와 분산 추적이 올바른 도구다.

### 소비하기 — `HttpClient`와 팩토리

`HttpClient`는 웹 서비스를 소비하는 가장 쉬운 방법이지만 **가장 많이 잘못 쓰이는 타입**이기도 하다.

`IDisposable`을 구현하니 `using` 문에 넣는 것이 보통의 직관이다. **`HttpClient`는 다르다.** 공유되고, 재진입 가능하고, 부분적으로 스레드 안전하다. 문제는 그 아래의 네트워크 소켓 관리 방식에 있다. 매 요청마다 만들고 버리면 소켓이 `TIME_WAIT` 상태로 쌓여 결국 포트가 고갈된다.

**결론: 소비하는 HTTP 엔드포인트마다 인스턴스 하나를 애플리케이션 수명 동안 쓴다.** 이렇게 하면 각 인스턴스가 자기 엔드포인트에 맞는 기본값(기본 주소, 헤더, 타임아웃)을 갖고, 소켓은 효율적으로 재사용된다.

이 관행을 강제하기 위해 ASP.NET Core 2.1에서 `IHttpClientFactory`가 도입되었다.

```csharp
using System.Net.Http.Headers;   // MediaTypeWithQualityHeaderValue

builder.Services.AddHttpClient(name: "Northwind.WebApi",
    configureClient: options =>
    {
        options.BaseAddress = new Uri("https://localhost:5151/");
        options.DefaultRequestHeaders.Accept.Add(
            new MediaTypeWithQualityHeaderValue(
                mediaType: "application/json", quality: 1.0));
    });
```

```csharp
public class HomeController : Controller
{
    private readonly IHttpClientFactory _clientFactory;

    public HomeController(IHttpClientFactory httpClientFactory)
        => _clientFactory = httpClientFactory;

    public async Task<IActionResult> Customers()
    {
        HttpClient client = _clientFactory.CreateClient("Northwind.WebApi");

        // System.Net.Http.Json 확장 메서드
        IEnumerable<Customer>? model =
            await client.GetFromJsonAsync<IEnumerable<Customer>>("api/customers");

        return View(model);
    }
}
```

> **⚠️ 싱글턴 `HttpClient`는 DNS 변경을 영원히 못 본다**
>
> "인스턴스 하나를 애플리케이션 수명 동안 쓴다"를 순진하게 `static readonly HttpClient`로 구현하면, 그 인스턴스가 붙잡은 커넥션은 DNS 레코드가 바뀌어도 갱신되지 않는다. 블루-그린 배포나 페일오버 뒤에 트래픽이 죽은 인스턴스로 계속 흘러간다.
>
> `IHttpClientFactory`는 이 문제를 **핸들러 풀링**으로 푼다. `CreateClient()`가 돌려주는 `HttpClient`는 매번 새 객체지만, 그 아래의 `HttpMessageHandler`는 풀에서 재사용되고 기본 2분마다 순환한다. 소켓 고갈과 DNS 정체를 동시에 푼다.
>
> 팩토리를 쓸 수 없는 환경(콘솔 앱 등)이라면 `SocketsHttpHandler.PooledConnectionLifetime`을 직접 설정한다.
>
> ```csharp
> var handler = new SocketsHttpHandler
> {
>     PooledConnectionLifetime = TimeSpan.FromMinutes(2)
> };
> var client = new HttpClient(handler);   // 이 인스턴스는 static으로 공유해도 안전하다
> ```

## 81.6 EF Core — 모델 정의, 쿼리, 추적, 변경 저장, 마이그레이션

이 절은 **모델링 관점**만 다룬다. N+1, 추적 오버헤드, 지연 로딩 비용, 컴파일된 쿼리 같은 성능 함정은 72.4절에서 이미 끝냈다. 여기서는 "무엇이 어떻게 매핑되고, `DbContext`가 언제 살고 죽으며, 스키마를 어떻게 진화시키는가"에 집중한다.

### 공급자 선택

EF Core는 데이터 저장소마다 별도의 공급자 패키지를 요구한다.

| 관리할 데이터 저장소 | 참조할 NuGet 패키지 |
|---|---|
| SQL Server 2012 이상 | `Microsoft.EntityFrameworkCore.SqlServer` |
| SQLite 3.7 이상 | `Microsoft.EntityFrameworkCore.Sqlite` |
| 인메모리 | `Microsoft.EntityFrameworkCore.InMemory` |
| Azure Cosmos DB SQL API | `Microsoft.EntityFrameworkCore.Cosmos` |
| MySQL | `MySQL.EntityFrameworkCore` |
| Oracle DB 11.2 | `Oracle.EntityFrameworkCore` |
| PostgreSQL | `Npgsql.EntityFrameworkCore.PostgreSQL` |

> **⚠️ 인메모리 공급자는 테스트용 데이터베이스가 아니다**
>
> `Microsoft.EntityFrameworkCore.InMemory`는 관계형 데이터베이스가 **아니다.** 참조 무결성을 강제하지 않고, 고유 제약을 검사하지 않으며, `FromSqlRaw` 같은 관계형 전용 기능을 지원하지 않고, 무엇보다 **트랜잭션 의미론이 다르다.** 인메모리로 통과한 테스트가 SQL Server에서 실패하는 일은 흔하다.
>
> 통합 테스트에는 SQLite 인메모리 모드나 컨테이너에 띄운 실제 데이터베이스를 써라. 80.5절이 이 주제를 다룬다.

### 모델을 정의하는 세 가지 층위

같은 매핑을 세 방법으로 표현할 수 있고, 뒤쪽이 앞쪽을 이긴다.

| 층위 | 어떻게 | 장점 | 한계 |
|---|---|---|---|
| **규약(convention)** | 이름 규칙을 따르기만 한다 | 코드가 없다 | 표현력이 낮다 |
| **주석 특성(annotation)** | 엔티티 클래스에 특성을 붙인다 | 모델 바로 옆에 보인다 | 엔티티가 EF Core에 의존하게 된다 |
| **Fluent API** | `OnModelCreating`에서 설정한다 | **엔티티 클래스가 깨끗하게 유지된다.** 표현력이 가장 높다 | 매핑이 엔티티에서 멀어진다 |

규약의 예를 보면 감이 온다. `Id` 또는 `<타입명>Id`라는 이름의 속성은 기본 키로 간주되고, 그 타입이 정수라면 데이터베이스가 값을 자동 생성하는 열이 된다. `string` 속성은 SQL Server에서 `nvarchar`로, `int` 속성은 `int`로 매핑된다.

주석 특성은 매핑과 유효성 검사를 겸한다.

| 특성 | 하는 일 |
|---|---|
| `[Required]` | 값이 `null`이 아님을 보장한다. ※.NET 8에서 값 타입의 기본값도 막는 `DisallowAllDefaultValues` 매개변수가 추가되었다 |
| `[StringLength(50)]` | 값의 길이를 최대 50자로 |
| `[Column]` | 열 타입과 열 이름을 지정 |
| `[RegularExpression]` | 지정한 정규식과 일치하는지 |
| `[Range]` | `double`·`int`·`string` 값이 범위 안인지. ※.NET 8에서 `MinimumIsExclusive`·`MaximumIsExclusive` 추가 |
| `[AllowedValues]` / `[DeniedValues]` | 값이 `params` 배열 안에 있는지 / 없는지 |

Fluent API는 `DbContext`에서 설정한다.

```csharp
using Microsoft.EntityFrameworkCore;

public class NorthwindContext : DbContext
{
    public DbSet<Category> Categories { get; set; } = null!;
    public DbSet<Product> Products { get; set; } = null!;

    public NorthwindContext(DbContextOptions<NorthwindContext> options)
        : base(options) { }

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Product>()
            .Property(p => p.ProductName)
            .IsRequired()
            .HasMaxLength(40);

        modelBuilder.Entity<Product>()
            .Property(p => p.UnitPrice)
            .HasColumnType("money");

        // 시드 데이터
        modelBuilder.Entity<Category>().HasData(
            new Category { CategoryId = 1, CategoryName = "Beverages" });
    }
}
```

`HasData` 호출은 `dotnet ef database update`로 실행되는 데이터 마이그레이션이나 `EnsureCreated` 시점에 반영된다.

> **💡 실무에서는 Fluent API로 통일하는 편이 낫다**
>
> 주석 특성과 Fluent API를 섞으면 "이 열의 길이가 왜 이렇지"를 두 곳에서 찾아야 한다. 엔티티 클래스는 **POCO(plain old CLR object)** 로 두고 모든 매핑을 `IEntityTypeConfiguration<T>` 구현체로 분리하는 것이 규모가 커질 때 유지보수하기 쉽다.
>
> ```csharp
> public sealed class ProductConfiguration : IEntityTypeConfiguration<Product>
> {
>     public void Configure(EntityTypeBuilder<Product> builder)
>     {
>         builder.Property(p => p.ProductName).IsRequired().HasMaxLength(40);
>     }
> }
> // OnModelCreating에서:
> modelBuilder.ApplyConfigurationsFromAssembly(typeof(NorthwindContext).Assembly);
> ```
>
> 이렇게 하면 엔티티 어셈블리가 EF Core에 의존하지 않아도 되고, 엔티티 모델을 서버와 클라이언트가 공유할 때(Blazor WebAssembly 등) 특히 유리하다.

### `DbContext`의 수명

**`DbContext`는 스레드 안전하지 않다.** 이것이 이 절에서 가장 중요한 문장이다.

기본적으로 `AddDbContext<T>`는 **Scoped** 수명으로 등록한다. 즉 여러 스레드가 같은 인스턴스를 공유할 수 있는 구조다. 두 스레드가 같은 인스턴스를 동시에 쓰면 런타임 예외가 난다.

```text
A second operation started on this context before a previous operation completed.
This is usually caused by different threads using the same instance of a DbContext,
however instance members are not guaranteed to be thread safe.
```

| 등록 메서드 | 수명 | 언제 |
|---|---|---|
| `AddDbContext<T>()` | Scoped (기본) | ASP.NET Core MVC / Razor Pages / 웹 API |
| `AddDbContext<T>(..., contextLifetime: ServiceLifetime.Transient)` | Transient | Blazor 서버 측 컴포넌트처럼 동시성 문제가 있는 곳 |
| `AddDbContextPool<T>()` | Scoped + 인스턴스 풀 | 처리량이 중요한 웹 API |
| `AddDbContextFactory<T>()` | Singleton 팩토리 | **Blazor 권장 방식.** 필요할 때마다 인스턴스를 만들어 즉시 폐기 |

> **⚠️ Blazor 서버 측 컴포넌트는 Scoped `DbContext`를 깨뜨린다**
>
> 클라이언트 측에서 상호작용이 일어날 때마다 SignalR 호출이 서버로 되돌아온다. 이때 **데이터베이스 컨텍스트의 단일 인스턴스가 여러 클라이언트 사이에서 공유되는 상황**이 만들어진다. 위의 "A second operation started..." 예외가 바로 이 자리에서 나온다.
>
> 컴포넌트가 클라이언트 측에서 실행되도록 설정되어 있다면 이 문제는 생기지 않는다.
>
> 회피책은 두 가지다. 하나는 등록 시 수명을 Transient로 내리는 것이다.
>
> ```csharp
> services.AddDbContext<NorthwindContext>(options =>
> {
>     options.UseSqlite($"Data Source={path}");
> },
> // Blazor 서버 측 프로젝트의 동시성 문제를 피하기 위해 Transient로 등록한다.
> contextLifetime: ServiceLifetime.Transient,
> optionsLifetime: ServiceLifetime.Transient);
> ```
>
> 다른 하나는 `AddDbContextFactory<T>()`로 팩토리를 등록하고 컴포넌트가 필요할 때마다 `await using var db = await factory.CreateDbContextAsync();`로 짧게 쓰는 것이다. **후자가 권장 방식이다.**

`AddDbContextPool`은 인스턴스 풀을 만들어 요청 사이에 상태를 초기화한 뒤 재사용한다. 컨텍스트 생성 비용이 사라져 성능이 올라간다. 단, EF Core 6에서 도입된 축약형 등록(`AddSqlServer<T>(connectionString)`)은 풀링을 지원하지 않는다.

> **⚠️ 풀링된 `DbContext`에 상태를 두지 마라**
>
> `AddDbContextPool`은 인스턴스를 **재사용**한다. `DbContext` 파생 클래스에 사용자 ID나 테넌트 ID 같은 필드를 두고 생성자에서 채우면, 그 값이 다음 요청으로 새어 들어간다. 풀이 초기화하는 것은 EF Core가 아는 상태(변경 추적기 등)뿐이고, **당신이 추가한 필드는 초기화되지 않는다.**
>
> 멀티테넌시처럼 컨텍스트별 상태가 필요하면 풀링을 쓰지 말거나, `IDbContextFactory<T>`로 매번 새로 만들어라.

### 변경 추적기

EF Core는 각 엔티티 인스턴스를 **기본 키 값으로 식별**한다. 이것을 엔티티 아이덴티티 해석(identity resolution)이라 한다. 같은 컨텍스트에서 같은 키의 행을 두 번 쿼리하면 두 번째는 새 객체를 만들지 않고 이미 추적 중인 인스턴스를 돌려준다.

기본적으로 EF Core는 로컬 메모리에서 엔티티를 추적한다고 가정한다. 추가·수정·삭제를 하고 `SaveChanges`를 부르면 그 변경들이 데이터 저장소에 반영된다.

```csharp
using Microsoft.EntityFrameworkCore.ChangeTracking;   // EntityEntry<T>

private static (int affected, int productId) AddProduct(
    int categoryId, string productName, decimal? price, short? stock)
{
    using NorthwindDb db = new();

    Product p = new()
    {
        CategoryId = categoryId,
        ProductName = productName,
        Cost = price,
        Stock = stock
    };

    // 변경 추적기에서 추가됨 상태로 표시한다.
    EntityEntry<Product> entity = db.Products.Add(p);
    Console.WriteLine($"State: {entity.State}, ProductId: {p.ProductId}");
    // State: Added, ProductId: 0

    int affected = db.SaveChanges();
    Console.WriteLine($"State: {entity.State}, ProductId: {p.ProductId}");
    // State: Unchanged, ProductId: 78   ← 데이터베이스가 할당한 값

    return (affected, p.ProductId);
}
```

새 객체가 메모리에 만들어져 추적되기 시작하면 상태는 `Added`이고 ID는 0이다. `SaveChanges` 후에는 상태가 `Unchanged`가 되고 ID는 데이터베이스가 할당한 값으로 채워진다. **`SaveChanges`는 삽입 후 생성된 키를 다시 읽어와 객체에 써 넣는다.**

> **📌 키 없는 엔티티는 절대 추적되지 않는다**
>
> EF Core는 키가 있는 엔티티만 추적할 수 있다. 키로 데이터베이스에서 유일하게 식별하기 때문이다. 뷰가 반환하는 것 같은 키 없는(keyless) 엔티티는 **어떤 시나리오에서도 추적되지 않는다.**

### 추적을 제어하는 세 가지 선택

| 설정 | 추적 | 아이덴티티 해석 | 결과 |
|---|---|---|---|
| 기본 (`TrackAll`) | 한다 | 한다 | 로컬에 사본 하나. 데이터베이스의 변경은 반영되지 않는다. `SaveChanges`가 동작한다 |
| `AsNoTracking()` | 안 한다 | **안 한다** | 쿼리마다 최신 값을 새 인스턴스로 받는다. **중복 인스턴스가 생긴다** |
| `AsNoTrackingWithIdentityResolution()` | 안 한다 | 한다 | 최신 값을 받으면서 중복은 없앤다. 대신 해석 비용이 든다 |

```csharp
// 쿼리 단위
var products = db.Products
    .AsNoTracking()
    .Where(p => p.UnitPrice > price)
    .Select(p => new { p.ProductId, p.ProductName, p.UnitPrice });

// 컨텍스트 인스턴스 단위
db.ChangeTracker.QueryTrackingBehavior = QueryTrackingBehavior.NoTracking;
db.ChangeTracker.QueryTrackingBehavior = QueryTrackingBehavior.NoTrackingWithIdentityResolution;

// 모든 새 인스턴스의 기본값
protected override void OnConfiguring(DbContextOptionsBuilder optionsBuilder)
{
    optionsBuilder.UseSqlServer(connectionString)
        .UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking);
}
```

> **⚠️ "`AsNoTracking`을 부르면 빨라진다"는 항상 참이 아니다**
>
> 이 조언은 블로그와 링크드인 게시물의 단골 소재다. 절반만 맞다.
>
> 수천 개의 엔티티를 반환하는 쿼리를 같은 컨텍스트 안에서 **두 번** 실행한다고 하자. 추적을 끄면 아이덴티티 해석도 함께 꺼지므로 **수천 개의 중복 인스턴스가 생긴다.** 메모리를 낭비하고 성능을 해친다. 3권의 언어로는, 중복 인스턴스 수천 개가 gen0 예산을 빠르게 소진시켜 GC를 유발하고, 요청이 길면 그것들이 gen1로 승격된다(63.6절, 66.12절).
>
> 세 가지 선택의 동작을 이해하고 **컨텍스트나 개별 쿼리마다 맞는 것을 고르는 것**이 답이다. 읽고 버리는 단발 조회에는 `AsNoTracking`이 맞고, 같은 데이터를 여러 번 훑는다면 `AsNoTrackingWithIdentityResolution`이나 기본 추적이 낫다.

### 관련 데이터를 불러오는 세 가지 패턴

| 패턴 | 어떻게 | 왕복 횟수 | 위험 |
|---|---|---|---|
| **즉시 로딩(eager)** | `Include(c => c.Products)` | 1회 (조인) | 카티전 폭발 — 조인 결과가 곱해진다 |
| **지연 로딩(lazy)** | 프록시 + `virtual` 탐색 속성 | **접근할 때마다** | **N+1 (72.4절)** |
| **명시적 로딩(explicit)** | `db.Entry(c).Collection(x => x.Products).Load()` | 필요할 때만 1회 | 없음. 다만 코드가 길어진다 |

지연 로딩을 켜려면 `Microsoft.EntityFrameworkCore.Proxies` 패키지를 참조하고, 탐색 속성을 `virtual`로 표시하고, `UseLazyLoadingProxies()`를 호출해야 한다. EF Core는 엔티티를 상속해 속성을 재정의한 프록시 타입을 런타임에 만들어 쓴다.

```csharp
db.ChangeTracker.LazyLoadingEnabled = false;   // 런타임에 끄기
```

명시적 로딩은 지연 로딩과 비슷하게 동작하되 **개발자가 언제 로드할지 결정한다**는 점이 다르다.

```csharp
using Microsoft.EntityFrameworkCore.ChangeTracking;

CollectionEntry<Category, Product> products = db.Entry(c).Collection(c2 => c2.Products);
if (!products.IsLoaded) products.Load();
```

> **📌 EF Core 8은 추적하지 않는 엔티티의 지연 로딩을 지원한다 ※EF Core 8**
>
> EF Core 7 이하에서 `AsNoTracking`을 켜면 지연 로딩을 쓸 수 없었다. 시도하면 다음 예외가 났다.
>
> ```text
> An attempt was made to lazy-load navigation 'Category' on a detached entity
> of type 'ProductProxy'. Lazy loading is not supported for detached entities
> or entities that are loaded with 'AsNoTracking'.
> ```
>
> EF Core 8부터는 추적되지 않는 엔티티도 지연 로딩할 수 있다. 편해졌지만 **N+1의 사각지대가 하나 늘어난 것이기도 하다.**

> **💡 웹 애플리케이션에서는 지연 로딩을 끄는 것이 기본값이어야 한다**
>
> 지연 로딩의 편리함은 데스크톱 앱이나 스크립트에서 온다. 웹에서는 렌더링 도중에 SQL이 나가는 사고(81.4절)와 N+1(72.4절)의 원인이 된다. **즉시 로딩과 프로젝션(`Select`로 DTO 만들기)을 기본으로 하고, 지연 로딩은 켜지 마라.**

### 마이그레이션

EF Core CLI 도구는 전역 도구로 설치한다.

```text
dotnet tool install --global dotnet-ef
```

대상 프로젝트는 `Microsoft.EntityFrameworkCore.Design` 패키지를 참조해야 한다.

| 명령 | 하는 일 | 하위 명령 |
|---|---|---|
| `dotnet ef database` | 데이터베이스를 관리한다 | `drop`, `update` |
| `dotnet ef dbcontext` | `DbContext` 타입을 관리한다 | `scaffold`, `list`, `info` |
| `dotnet ef migrations` | 마이그레이션을 관리한다 | `add`, `list`, `remove`, `script` |

```text
dotnet ef migrations add Initial -o Migrations -c NorthwindContext
dotnet ef database update
dotnet ef migrations script --idempotent -o migrate.sql
```

프로젝트에 `DbContext` 파생 클래스가 하나뿐이면 자동으로 선택된다. 여럿이면 `-c`로 지정해야 한다.

> **⚠️ 설계 시점 인스턴스화가 실패하는 이유**
>
> CLI 명령은 `DbContext` 인스턴스를 **설계 시점에** 만들어야 한다. 순서는 이렇다.
>
> 1. `IDesignTimeDbContextFactory<TContext>` 구현이 있으면 그것을 쓴다.
> 2. 없으면 **매개변수 없는 생성자**로 인스턴스화한다.
> 3. 둘 다 없으면 명령이 실패한다.
>
> 2번은 `OnConfiguring` 재정의에 커넥션 문자열이 하드코딩되어 있어야 동작하는데, 그것은 좋은 관행이 아니다. **`DbContext`마다 `IDesignTimeDbContextFactory<TContext>`를 항상 만들어라.** 사실상 유일한 올바른 선택지다.
>
> ```csharp
> public sealed class NorthwindContextFactory
>     : IDesignTimeDbContextFactory<NorthwindContext>
> {
>     public NorthwindContext CreateDbContext(string[] args)
>     {
>         var options = new DbContextOptionsBuilder<NorthwindContext>()
>             .UseSqlServer("Server=(localdb)\\mssqllocaldb;Database=Northwind;")
>             .Options;
>         return new NorthwindContext(options);
>     }
> }
> ```

> **⚠️ 코드 우선과 데이터베이스 우선은 사실상 되돌릴 수 없는 약속이다**
>
> **코드 우선(code first)** 은 엔티티와 컨텍스트를 코드로 작성하고 마이그레이션으로 데이터베이스를 갱신한다. 신규 프로젝트의 표준이다. **데이터베이스 우선(database first)** 은 기존 데이터베이스에서 클래스를 스캐폴딩하고, 스키마가 바뀌면 다시 스캐폴딩한다.
>
> 어느 쪽을 고르든 그것은 **약속(commitment)** 이다. 코드 우선이면 모든 변경은 코드에서 시작해 마이그레이션으로 흘러간다. 데이터베이스 우선이면 모든 변경은 데이터베이스에서 시작해 재스캐폴딩으로 흘러간다. **코드와 데이터베이스를 동시에 손으로 고치기 시작하면 두 진실이 갈라진다.**
>
> 재스캐폴딩이 커스텀 코드를 지우지 않도록 스캐폴딩 도구는 partial 클래스를 생성한다. 커스텀 코드는 반드시 별도 partial 파일에 두어라.

> **📌 여러 `DbContext`가 한 엔티티를 공유할 때 ※EF Core 5+**
>
> 두 컨텍스트가 같은 엔티티를 알고 있으면 양쪽 마이그레이션이 모두 그 테이블 생성 코드를 만든다. 두 번째 스크립트는 "이미 존재한다"로 실패한다. 한쪽에서 제외하면 된다.
>
> ```csharp
> modelBuilder.Entity<LogEntry>().ToTable("Logs", t => t.ExcludeFromMigrations());
> ```

## 81.7 데이터 접근 계층 설계 — ADO.NET / Dapper / EF Core 선택 기준

### 세 층위

| 축 | ADO.NET | Dapper | EF Core |
|---|---|---|---|
| **추상화 수준** | 없다. 커넥션·명령·리더를 직접 다룬다 | 얇다. SQL은 직접 쓰고 결과 매핑만 맡긴다 | 두껍다. SQL도 생성해준다 |
| **SQL 작성** | 전부 직접 | 전부 직접 | LINQ에서 번역 (원시 SQL도 가능) |
| **변경 추적** | 없다 | 없다 | **있다** |
| **마이그레이션** | 없다 | 없다 | **있다** |
| **관계 탐색** | 직접 조인 | 직접 조인 + 멀티 매핑 | 탐색 속성 |
| **Native AOT** | 지원 (공급자에 따라) | 리플렉션 기반 매핑이라 주의 필요 | .NET 8 기준 **미지원** |
| **학습 곡선** | 낮다 (SQL을 안다면) | 낮다 | **높다** — 함정을 알아야 안전하다 |
| **생산성** | 낮다 | 중간 | **높다** |

### 선택 결정표

| 상황 | 권장 | 왜 |
|---|---|---|
| 도메인이 복잡하고 엔티티 관계가 많다 | **EF Core** | 탐색 속성과 변경 추적이 그대로 이득이다 |
| 스키마가 코드와 함께 진화한다 (그린필드) | **EF Core** | 마이그레이션이 스키마를 코드와 동기화한다 |
| 읽기 전용 보고서·대시보드 쿼리 | **Dapper** | 복잡한 SQL을 직접 쓰고 DTO로 바로 받는다 |
| 핫 패스의 단일 값 조회 | **Dapper / ADO.NET** | 72.3절 벤치마크에서 두 방식이 사실상 동률로 1·2위 |
| 대량 삽입·대량 갱신 | **ADO.NET** (`SqlBulkCopy`) 또는 EF Core `ExecuteUpdate` | 행마다 왕복하지 않는다 |
| 저장 프로시저가 이미 다 있다 | **ADO.NET / Dapper** | EF Core로 프로시저를 부르는 조합은 72.3절에서 최악의 숫자를 냈다 |
| Native AOT가 필수인 서비스 | **ADO.NET** | EF Core는 .NET 8 기준 AOT 불가 |
| 팀에 SQL 숙련자가 없다 | **EF Core** | LINQ가 부정확한 SQL을 막아준다 |

> **💡 하나로 통일하지 않아도 된다**
>
> 72.3절의 결론은 "EF Core는 느리다"가 아니라 **"연산 종류마다 이기는 프레임워크가 다르다"** 였다. 실무의 좋은 답은 대개 하이브리드다.
>
> - **쓰기 경로와 도메인 로직** — EF Core. 변경 추적과 트랜잭션 관리의 이득이 크다.
> - **읽기 경로의 복잡한 조회** — Dapper. `Select`로 DTO를 만드는 LINQ가 읽기 어려워지는 지점이 넘어가면 SQL이 더 정직하다.
> - **배치·마이그레이션·벌크** — ADO.NET.
>
> 이것은 81.10절에서 볼 CQRS의 가장 실용적인 형태이기도 하다. 쓰기 모델과 읽기 모델을 **서로 다른 데이터 접근 기술로** 구현하는 것. 별도의 데이터베이스나 이벤트 버스 없이도 CQRS의 이득 절반을 가져간다.

### 리포지터리 패턴을 씌울 것인가

데이터 리포지터리를 정의해 CRUD를 제공하는 것은 널리 권장되는 관행이다. 캐싱을 얹기도 좋다.

```csharp
public sealed class CustomerRepository : ICustomerRepository
{
    private readonly NorthwindContext _db;
    private readonly IMemoryCache _cache;

    public CustomerRepository(NorthwindContext db, IMemoryCache memoryCache)
    {
        _db = db;
        _cache = memoryCache;
    }

    public async Task<Customer?> RetrieveAsync(string id, CancellationToken ct = default)
    {
        if (_cache.TryGetValue(id, out Customer? cached)) return cached;

        Customer? c = await _db.Customers.FindAsync(new object?[] { id }, ct);
        if (c is not null)
        {
            _cache.Set(id, c, TimeSpan.FromMinutes(5));
        }
        return c;
    }
}
```

> **⚠️ `DbContext` 위에 리포지터리를 또 씌우는 것은 공짜가 아니다**
>
> `DbSet<T>`는 이미 리포지터리이고 `DbContext`는 이미 작업 단위(unit of work)다. 그 위에 얇은 리포지터리를 하나 더 얹으면 다음을 잃는다.
>
> - `Include`, `AsNoTracking`, 프로젝션 같은 **쿼리 조합 능력**. `IEnumerable<T>`를 반환하는 리포지터리 메서드는 필터링을 메모리로 끌어와 N+1보다 나쁜 일을 한다.
> - 트랜잭션 경계. 리포지터리마다 `SaveChanges`를 부르면 원자성이 깨진다.
>
> 그럼에도 리포지터리가 정당한 경우가 있다. **데이터 접근 기술을 바꿀 여지를 남기고 싶을 때**(하이브리드 접근의 전제), 그리고 **캐싱·재시도·감사 같은 횡단 관심사를 한곳에 모으고 싶을 때**다. 위 예제가 후자다. 목적 없이 관례로만 씌우지 마라.

> **⚠️ 프로덕션에서는 `IMemoryCache`가 인스턴스마다 따로 논다**
>
> `IMemoryCache`는 **프로세스 메모리**다. 웹 서버를 두 대로 늘리는 순간 캐시가 둘로 갈라지고, 한쪽에서 무효화한 항목이 다른 쪽에는 남는다. 사용자는 새로고침할 때마다 다른 데이터를 본다.
>
> 실제 서비스에서는 Redis 같은 분산 캐시(`IDistributedCache`)를 써라. 캐시 계층 설계 전반은 72.5절에 있다.

## 81.8 Blazor / MAUI / WPF / WinUI 3 개요와 선택 기준

### Blazor — C#으로 만드는 UI 컴포넌트

전통적으로 브라우저에서 실행되는 코드는 자바스크립트이거나 자바스크립트로 트랜스파일되는 무언가여야 했다. 20년 넘게 모든 브라우저가 지원해온 최소 공통분모이기 때문이다.

Microsoft는 2008년 Silverlight 2로 플러그인을 통해 이 벽을 넘으려 했지만, 2011년 Silverlight 5 무렵 iPhone과 iPad에서 플러그인이 금지되면서 포기했다. 두 번째 기회는 **WebAssembly(Wasm)** 가 만들었다. 2017년 WebAssembly 합의가 완료되었고 지금은 Chromium 계열(Chrome, Edge, Opera, Brave), Firefox, WebKit(Safari)이 모두 지원한다. Wasm은 가상 머신을 위한 이진 명령 형식으로, 여러 언어로 작성한 코드를 웹에서 네이티브에 가까운 속도로 돌리는 방법이며 C# 같은 고수준 언어의 이식 가능한 컴파일 대상으로 설계되었다.

Blazor의 단위는 **컴포넌트**다. `.razor` 파일이고, UI를 어떻게 렌더링할지와 사용자 이벤트에 어떻게 반응할지를 정의하며, 중첩·합성이 가능하고 Razor 클래스 라이브러리로 패키징할 수 있다.

```razor
@* Rating.razor *@
<div>
    @for (int i = 0; i < Maximum; i++)
    {
        if (i < Value)
        {
            <span class="oi oi-star-filled" />
        }
        else
        {
            <span class="oi oi-star-empty" />
        }
    }
</div>

@code {
    [Parameter]
    public byte Maximum { get; set; }

    [Parameter]
    public byte Value { get; set; }
}
```

```razor
<h1>Review</h1>
<Rating id="rating" Maximum="5" Value="3" />
<textarea id="comment" />
```

컴포넌트 인스턴스를 만드는 마크업은 HTML 태그처럼 생겼고 태그 이름이 곧 컴포넌트 타입이다. `@code` 블록 대신 `Rating.razor.cs`라는 코드 비하인드 파일에 `partial` 클래스로 분리할 수도 있다(클래스 이름은 컴포넌트와 같아야 한다).

### 렌더 모드 — .NET 8의 통합 호스팅 모델

.NET 7 이하에서는 **프로젝트마다** 호스팅 모델을 하나 골라야 했다.

| 옛 호스팅 모델 | 실행 위치 | 특징 |
|---|---|---|
| Blazor Server (ASP.NET Core 3, 2019년 9월) | 서버 | C# 코드가 서버 자원에 자격 증명 없이 접근한다. SignalR로 UI 갱신을 전달하고 **모든 클라이언트의 상태를 서버가 추적한다.** 클라이언트가 많으면 확장이 어렵다 |
| Blazor WebAssembly (3.2, 2020년 5월) | 브라우저 | C# 코드가 브라우저 자원만 볼 수 있다. 서버 자원은 HTTP 호출로만 접근 |
| .NET MAUI Blazor (Blazor Hybrid) | 네이티브 앱 내 웹 뷰 | 로컬 인터롭 채널로 웹 UI를 렌더링한다. 개념적으로 Electron 앱과 비슷하다 |

.NET 8부터는 **컴포넌트 하나하나가 서로 다른 렌더 모드로 실행**될 수 있다.

| 렌더 모드 | 어디서 도는가 | 특징 | 적합 |
|---|---|---|---|
| **정적 서버 렌더링(SSR)** | 서버 | Razor Pages·MVC처럼 완성된 응답을 보내고 끝. 이후 상호작용 없음 | 콘텐츠 페이지 |
| **스트리밍 렌더링** | 서버 | HTML을 먼저 보내 표시하고, 연결을 연 채로 비동기 작업을 계속한 뒤 최종 마크업으로 갱신 | 느린 데이터 조회가 있는 페이지("Loading…"을 먼저 보여준다) |
| **대화형 서버(Interactive Server)** | 서버 | SignalR로 상호작용. 서버 자원에 완전하고 쉬운 접근. **영구 연결이 필요해 확장성이 제한된다** | 클라이언트 수가 제한적이고 대역폭이 넉넉한 인트라넷 |
| **대화형 WebAssembly** | 브라우저 | 브라우저 자원만 접근. 새 데이터가 필요할 때마다 서버 콜백 | 클라이언트가 많고 일부는 저대역폭인 공개 웹사이트 |
| **대화형 자동(Auto)** | 서버 → 브라우저 | 초기 표시는 서버에서 빠르게, 백그라운드로 WebAssembly를 내려받은 뒤 이후 상호작용은 클라이언트에서 | 둘의 장점을 모두 원할 때 |

계획을 잘 세우면 **컴포넌트를 한 번 작성하고 실행 위치를 나중에 고를 수 있다.** 다만 .NET 8에서 Blazor WebAssembly 컴포넌트는 여전히 별도 프로젝트에 있어야 한다.

> **⚠️ 대화형 서버 렌더링은 클라이언트당 서버 메모리를 소비한다**
>
> 대화형 서버 모드에서 각 클라이언트는 **회로(circuit)** 를 갖는다. 회로는 그 클라이언트의 컴포넌트 트리, 렌더 트리, 상태를 서버 메모리에 유지한다. 클라이언트 1,000명이면 1,000개의 객체 그래프가 **요청 하나보다 훨씬 오래** 서버에 살아 있다.
>
> 3권의 언어로 번역하면 이것은 gen2 압박이다. 웹 API에서는 gen0에서 죽었을 객체들이 여기서는 사용자가 탭을 닫을 때까지 산다. 서버 GC의 힙 개수와 메모리 한계(65.5절), 컨테이너에서의 DATAS 동작(65.7절)이 곧바로 관심사가 된다. 그리고 회로가 붙잡은 것을 세는 도구는 66.5절의 지배자 분석이다.
>
> 확장성 계획 없이 대화형 서버 모드를 공개 웹에 쓰지 마라.

> **⚠️ Blazor WebAssembly는 트리밍에 목숨을 건다**
>
> WebAssembly 모드는 **모든 .NET 라이브러리를 브라우저로 내려받아야 한다.** 초기 다운로드 크기를 줄이는 것이 이 유형에서 가장 큰 성능 과제이고, 그 수단이 트리밍이다.
>
> 그런데 트리밍은 리플렉션을 쓰는 코드를 조용히 깨뜨린다(57.14절). 개발 중에는 트리밍이 꺼져 있어 멀쩡하다가, 게시한 뒤 브라우저에서만 `MissingMethodException`이나 `NullReferenceException`이 나는 전형적 시나리오다. **게시 빌드를 실제로 브라우저에서 테스트하기 전까지 동작한다고 믿지 마라.**
>
> 라이브러리를 고를 때 `IsTrimmable` 표시가 있는지 확인하고(81.2절), 자기 코드의 리플렉션은 소스 생성기로 대체하라.

### 데스크톱 — WPF, WinForms, WinUI 3, MAUI

| 프레임워크 | 대상 플랫폼 | UI 정의 | 특징 |
|---|---|---|---|
| **WinForms** | Windows | 디자이너 + 코드 | 가장 오래되고 가장 안정적. 고DPI 인식과 긴 경로 인식을 명시적으로 켜야 한다 |
| **WPF** | Windows | XAML | 데이터 바인딩·템플릿·스타일이 강력하다. 성숙한 서드파티 생태계 |
| **WinUI 3** | Windows (Windows App SDK) | XAML | 최신 Windows 룩앤필. `ProgressRing` 같은 현대적 컨트롤 |
| **.NET MAUI** | iOS, Android, macOS, Windows | XAML | Xamarin.Forms의 후신. **Android·iOS·macOS 프로젝트가 하나로 통합**되었다. Windows 코드는 여전히 별도 프로젝트에 있지만 통합 작업이 진행 중이다 |

MAUI의 주요 변화 몇 가지를 짚어둔다.

- **레이아웃** — Xamarin.Forms의 옛 레이아웃은 `Microsoft.Maui.Controls.Compatibility` 네임스페이스로 이동했다. 기본 레이아웃은 성능·일관성·유지보수성을 위해 새로 작성된 `LayoutManager` 기반의 `Grid`, `FlexLayout`, `StackLayout`(`HorizontalStackLayout`, `VerticalStackLayout`)이다. **새 레이아웃의 기본 간격 값은 전부 0**이므로 전역 스타일에서 직접 지정하는 것을 전제로 한다.
- **접근성** — `TabIndex`와 `IsTabStop`은 혼란스럽고 접근성 요구를 충족하지 못해 제거되었다. 읽기 순서 제어에는 `SemanticOrderView`를 쓴다. `SemanticExtensions`의 `SetSemanticFocus()`로 스크린 리더 포커스를 옮기고, `SemanticScreenReader.Announce(...)`로 안내를 읽게 할 수 있다.
- **글꼴 크기 조절** — 모든 컴포넌트에서 자동 글꼴 크기 조절이 기본으로 켜져 있다. 끄려면 `FontAutoScalingEnabled="False"`.
- **`BlazorWebView`** — MAUI 앱 안에 Blazor 웹사이트를 호스팅한다. 웹 UI가 네이티브 플랫폼 기능과 사용자 컨트롤을 쓸 수 있게 된다.

```xml
<BlazorWebView HostPage="wwwroot/index.html"
               Services="{StaticResource Services}">
  <BlazorWebView.RootComponent>
    <RootComponent Selector="#app" ComponentType="{x:Type local:Main}" />
  </BlazorWebView.RootComponent>
</BlazorWebView>
```

> **⚠️ .NET MAUI는 Linux를 지원하지 않는다**
>
> MAUI 팀은 Linux 지원을 오픈소스 커뮤니티에 맡겼다. 진짜 크로스 플랫폼 그래픽 앱이 필요하다면 **Avalonia**나 **Uno Platform** 같은 대안을 검토해야 한다.

### UI 애플리케이션의 공통 제약 — UI 스레드

WinForms, WPF, WinUI 3, MAUI가 공유하는 규칙이 하나 있다. **UI 요소는 자신을 만든 스레드에서만 갱신할 수 있다.** 백그라운드 작업에서 진행률을 보고하려면 디스패처를 거쳐야 한다.

```csharp
// WPF
Application.Current.Dispatcher.Invoke(() => StatusLabel.Content = "처리 중...");
```

이 제약 때문에 데스크톱 앱의 응답성 문제는 거의 항상 **긴 작업이 UI 스레드를 붙잡는 것**으로 귀결된다. 해법은 셋이다.

1. `async`/`await`로 I/O를 비동기화한다.
2. CPU 바운드 작업은 `Task.Run`으로 스레드 풀에 넘긴다.
3. 진행률 보고에는 `IProgress<T>` 또는 `BackgroundWorker`의 `ProgressChanged` 이벤트를 쓴다.

자세한 패턴과 측정 방법은 72.9절에 있다.

> **💡 데스크톱 앱에서 가장 자주 열리는 3권 장은 66장과 74장이다**
>
> 데스크톱 앱은 사용자가 몇 시간, 며칠씩 켜 둔다. 이벤트 핸들러를 해제하지 않아 생기는 누수(66.11절)가 가장 흔한 사고 유형이고, 사용자 머신에서만 재현되는 문제를 원격으로 진단하는 기술(74장, 73장의 진단 API)이 두 번째다. 성능보다 **오래 켜 두어도 안 죽는 것**이 이 유형의 핵심 품질이다.

## 81.9 배포 — 프레임워크 종속 vs 자체 포함, 단일 파일, 트리밍, Native AOT

### 세 가지 배포 형태

.NET 애플리케이션을 게시·배포하는 방법은 근본적으로 셋이다.

| 형태 | 약어 | 산출물 | .NET 런타임 설치 필요 | 실행 방법 |
|---|---|---|---|---|
| **프레임워크 종속 배포** | FDD | `.dll` | **필요** | `dotnet MyApp.dll` |
| **프레임워크 종속 실행 파일** | FDE | `.exe` (+ `.dll`) | **필요** | 직접 실행 |
| **자체 포함** | — | `.exe` + 런타임 전체 | 불필요 | 직접 실행 |

애플리케이션과 패키지 의존성만 배포하고 .NET 자체는 배포하지 않는 방식은 **웹 서버에 잘 맞는다.** 그 서버에는 이미 .NET과 다른 웹 애플리케이션들이 있을 가능성이 높기 때문이다. 반대로 USB 스틱에 담아 건네고도 상대 컴퓨터에서 돌아가야 한다면 자체 포함이 답이다. 파일 크기는 훨씬 커지지만 확실히 동작한다.

자체 포함으로 게시하려면 **런타임 식별자(RID)** 를 지정해야 한다.

```xml
<PropertyGroup>
  <OutputType>Exe</OutputType>
  <TargetFramework>net8.0</TargetFramework>
  <RuntimeIdentifiers>
    win-x64;osx-x64;osx-arm64;linux-x64;linux-arm64
  </RuntimeIdentifiers>
</PropertyGroup>
```

`linux-arm`은 32비트 Raspberry Pi OS용, `linux-arm64`는 64비트 Ubuntu를 돌리는 Raspberry Pi용이다.

> **⚠️ `RuntimeIdentifier`와 `RuntimeIdentifiers`는 한 글자 차이다**
>
> 하나만 지정하려면 `<RuntimeIdentifier>`(단수), 여럿을 지정하려면 `<RuntimeIdentifiers>`(복수)를 쓴다. 잘못 쓰면 컴파일러가 오류를 내는데, **한 글자 차이라 원인을 알아채기 어렵다.**

### 게시 명령과 옵션 조합

```text
dotnet publish -c Release -r win-x64 --self-contained
```

| 옵션 | 의미 |
|---|---|
| `--self-contained` | .NET 런타임을 함께 게시한다. **RID를 지정하면 기본값이 `true`** |
| `--no-self-contained` | 런타임 없이 프레임워크 종속으로 게시 |
| `-r <RID>` | 대상 런타임 |
| `-c` | 구성 — `Debug` 또는 `Release` |

> **⚠️ `dotnet publish`의 기본 구성이 .NET 8에서 바뀌었다 ※.NET 8**
>
> .NET 7 이하에서 `dotnet publish`는 **Debug** 구성을 기본으로 게시했다. .NET 8부터는 **Release**가 기본이다. 반대로 `dotnet build`의 기본은 여전히 Debug다.
>
> CI 스크립트에 `-c Release`를 명시하고 있었다면 아무 일도 없다. 명시하지 않은 채로 .NET 8로 올렸다면, 그동안 실수로 Debug 바이너리를 배포하고 있었다는 사실을 이제야 알게 될 수도 있다.

### 크기를 줄이는 세 단계

Hello World 콘솔 앱 하나를 놓고 옵션을 하나씩 더해 보면 효과가 보인다. 아래 숫자는 원천 도서의 실측값이며 프로젝트·버전·플랫폼에 따라 달라진다.

| 게시 방식 | 파일 수 | 크기 |
|---|---|---|
| 자체 포함 (Windows x64) | 200개 이상 | 폴더 전체 약 68 MB |
| + 단일 파일 (`PublishSingleFile`) | 2개 (`.exe`, `.pdb`) | `.exe` 약 60~63 MB |
| + 압축 + 트리밍 + R2R | 2개 | 약 11 MB |
| **Native AOT** | 2개 | **약 1.2 MB** |

```text
dotnet publish -c Release -r win-x64 -p:PublishSingleFile=true -p:DebugType=embedded ^
  -p:EnableCompressionInSingleFile=true -p:PublishTrimmed=true -p:PublishReadyToRun=true
```

`<DebugType>embedded</DebugType>`는 `.pdb`를 실행 파일 안에 넣어 진짜 단일 파일로 만든다.

**앱 트리밍**은 .NET Core 3에서 쓰이지 않는 어셈블리를 제거하는 기능(`copyused`)으로 시작해, .NET 5에서 개별 타입과 멤버까지 제거하는 수준(`link`)으로 발전했다. Hello World 콘솔 앱에서 `System.Console.dll`이 61.5 KB에서 31.5 KB로 줄어드는 정도다. .NET 6에서 Microsoft가 자사 라이브러리에 트리밍 안전성 주석을 달면서 타입·멤버 수준 트리밍이 기본값이 되었고, .NET 7에서 `link`는 `full`로, `copyused`는 `partial`로 이름이 바뀌었다.

```xml
<PublishTrimmed>true</PublishTrimmed>              <!-- 기본: full (타입·멤버 수준) -->
<TrimMode>partial</TrimMode>                       <!-- 어셈블리 수준으로 낮추기 -->
```

### Native AOT

Native AOT로 게시한 어셈블리는 두 가지 성질을 갖는다.

- **자체 포함이다** — .NET 런타임이 설치되지 않은 시스템에서 돈다.
- **AOT 컴파일되었다** — IL이 아니라 네이티브 코드다. 시작이 빠르고 메모리 풋프린트가 작을 수 있다.

```xml
<PropertyGroup>
  <TargetFramework>net8.0</TargetFramework>
  <PublishAot>true</PublishAot>
  <InvariantGlobalization>true</InvariantGlobalization>
</PropertyGroup>
```

`InvariantGlobalization`을 `true`로 두는 것은 .NET 8 템플릿들이 새로 채택한 기본값이다(웹 API 템플릿, 그리고 AOT를 켠 콘솔 앱 템플릿). 문화권에 의존하지 않게 만들어 전 세계 어디에 배포해도 같은 동작을 하게 한다. `false`이거나 요소가 없으면 호스트 컴퓨터의 문화권을 따른다.

**Native AOT의 제약**은 다음과 같다.

| 제약 | 내용 |
|---|---|
| 동적 어셈블리 로딩 불가 | 52장의 `AssemblyLoadContext` 플러그인 시스템이 동작하지 않는다 |
| 런타임 코드 생성 불가 | `System.Reflection.Emit`(58장), 식 트리 컴파일 |
| 트리밍 필수 | 트리밍의 모든 제약을 함께 진다 |
| 자체 포함 필수 | 호출하는 라이브러리를 전부 임베드하므로 크기가 커진다 |

자기 코드가 이 기능들을 안 쓴다고 안심할 수 없다. **.NET 자체의 큰 부분이 쓴다.** ASP.NET Core MVC(컨트롤러를 쓰는 웹 API 포함)와 EF Core는 기능 구현에 런타임 코드 생성을 사용한다. .NET 8은 **최소 API를 쓸 경우에만 ASP.NET Core를 기본 수준으로 지원하고, EF Core는 지원하지 않는다.**

AOT 비호환을 표시하는 가장 흔한 특성은 `[RequiresDynamicCode]`다. 게시 시 분석기가 경고를 낸다.

```text
warning IL3050: Using member 'System.Reflection.Emit.AssemblyBuilder.DefineDynamicAssembly(
AssemblyName, AssemblyBuilderAccess)' which has 'RequiresDynamicCodeAttribute' can break
functionality when AOT compiling. Defining a dynamic assembly requires dynamic code.
```

> **⚠️ 개발 중에는 AOT가 아니다 — 게시해봐야 안다**
>
> 프로젝트에 `<PublishAot>true</PublishAot>`를 켜 두어도, 코드 편집기에서 디버깅하고 실행하는 동안에는 **여전히 런타임 JIT 컴파일러가 쓰인다.** AOT는 게시 시점에만 일어난다.
>
> 즉 개발 중에 잘 돌던 앱이 게시 후에 깨질 수 있다. 트리밍되고 AOT 컴파일된 코드는 **다른 코드**이고 동작도 다르기 때문이다. **배포 전에 반드시 게시해서 실행해보라.** 게시 시 AOT 경고가 하나도 없다면 그때 비로소 동작을 신뢰할 수 있다.
>
> 리플렉션이 필요한 멤버는 `[DynamicallyAccessedMembers]`로 표시해 트리밍에서 제외시켜야 한다(57.14절).

> **⚠️ 크로스 플랫폼 AOT 게시는 지원하지 않는다**
>
> **배포할 운영체제에서 게시를 실행해야 한다.** Linux에서 Windows용 Native AOT 프로젝트를 게시할 수 없고 그 반대도 마찬가지다. 네이티브 링커가 필요하기 때문이다.
>
> 추가 요구사항도 있다. Windows에서는 Visual Studio 2022의 "C++를 사용한 데스크톱 개발" 워크로드를 기본 구성 요소 전부와 함께 설치해야 하고, Linux(Ubuntu 18.04 이상)에서는 `sudo apt-get install clang zlib1g-dev`가 필요하다.
>
> 결과적으로 **CI 파이프라인이 대상 OS별로 갈라진다.** 단일 빌드 머신에서 다섯 개 RID를 게시하던 스크립트는 AOT로 넘어가는 순간 다시 써야 한다.

### 배포 형태와 3권의 연결

| 배포 결정 | 3권의 어느 절이 답을 갖고 있나 |
|---|---|
| R2R과 Native AOT 중 무엇을 쓰나 | **55.7절** — 두 방식의 코드 생성 차이와 트레이드오프 |
| 트리밍이 리플렉션을 깨는 지점 | **57.14절** — `[DynamicallyAccessedMembers]`와 경고 코드 해석 |
| 시작 시간을 실제로 재고 줄이기 | **72.7절** — 무엇이 시작 시간을 먹는지 측정하는 법 |
| 컨테이너에서 메모리 한계와 GC | **65.7절**(DATAS), **72.8절**(힙 하드 리밋) |
| 플러그인 아키텍처와 AOT의 충돌 | **52.14절** — ALC 기반 플러그인은 AOT와 양립하지 않는다 |
| 트리밍 대신 소스 생성기 | 57.15절 |

> **💡 컨테이너에서는 배포 형태보다 GC 설정이 먼저다**
>
> 컨테이너 이미지 크기를 줄이려고 트리밍과 AOT에 매달리기 전에, **GC가 컨테이너의 메모리 한계를 제대로 인식하고 있는지부터 확인하라.** 서버 GC는 CPU 코어마다 힙을 만드는데(65.1절), 64코어 호스트에서 CPU 0.5개를 할당받은 컨테이너가 힙 64개를 만들면 메모리 한계에 부딪혀 OOMKilled된다.
>
> DATAS는 힙 개수를 워크로드에 맞춰 동적으로 조정한다. .NET 8에서는 **옵트인**(`DOTNET_GCDynamicAdaptationMode=1`)이고 .NET 9부터 서버 GC에서 기본으로 켜진다(65.7절). 켤 수 없는 버전이라면 `DOTNET_GCHeapHardLimit`나 `DOTNET_GCHeapCount`를 명시해야 한다. 이미지 20 MB를 아끼는 것보다 이쪽의 효과가 훨씬 크다.

## 81.10 분산 시스템 관점 — CQRS, 이벤트 소싱, 서버리스, 컨테이너

이 절의 목적은 각 패턴을 가르치는 것이 아니라 **각 패턴이 도입하는 실제 비용**을 밝히는 것이다. 분산 패턴은 대부분 "복잡도를 지불하고 어떤 속성을 산다." 무엇을 사는지 모르고 지불하면 남는 것은 복잡도뿐이다.

### CQRS — 명령과 질의를 나눈다

**명령 질의 책임 분리(Command Query Responsibility Segregation, CQRS)** 를 가장 단순하게 말하면 이렇다. **명령은 동작을 수행하는 메서드이고, 질의는 데이터를 반환하는 메서드다. 명령은 질의하지 않고, 질의는 명령하지 않는다.**

```csharp
public sealed class CommandClass
{
    public void Sleep(int milliseconds) => Thread.Sleep(milliseconds);   // 값을 반환하지 않는다
}

public sealed class QueryClass
{
    public DateTime Now() => DateTime.Now;   // 아무것도 바꾸지 않는다
}
```

데이터베이스 연산으로 옮기면 추가·편집·삭제·갱신이 명령이고 조회가 질의다. 이렇게 보면 지나치게 단순해 보이지만, CQRS는 그 자체로 대단한 것이 아니라 **다른 것들을 가능하게 하는 enabling 패턴**이다. 메시지 브로커, 메시지 버스, 도메인 모델링, 도메인 이벤트, 이벤트 소싱, 최종 일관성, 읽기·쓰기 모델 분리, 도메인 주도 설계(DDD)가 CQRS 위에서 서로 맞물린다. 사람들이 길을 잃는 지점이 여기다 — **패턴 자체는 아주 단순하고, 복잡한 것은 그 위에 얹는 것들이다.**

| CQRS가 사는 것 | 지불하는 비용 |
|---|---|
| 읽기와 쓰기를 **독립적으로 최적화·확장**할 수 있다 | 모델이 둘이 된다. 같은 개념을 두 번 표현한다 |
| 읽기 모델을 비정규화해 조인을 없앨 수 있다 | 두 모델의 동기화 책임이 생긴다 |
| 읽기와 쓰기에 **다른 기술**을 쓸 수 있다 (81.7절의 하이브리드) | 최종 일관성 — 쓰고 나서 바로 읽으면 옛 값이 나올 수 있다 |

> **💡 CQRS의 가장 저렴한 형태부터 시작하라**
>
> 별도 데이터베이스도, 이벤트 버스도, 최종 일관성도 없이 **같은 데이터베이스에 대해 쓰기 경로는 EF Core로, 읽기 경로는 Dapper로** 구현하는 것만으로 CQRS의 실용적 이득 대부분을 얻는다. 읽기 모델을 별도 저장소로 분리하는 것은 그 다음 문제이고, **최종 일관성이 비즈니스적으로 허용될 때만** 넘어가라. "3초 전 잔액"을 보여줘도 되는 화면과 안 되는 화면은 개발자가 아니라 도메인이 결정한다.

### 이벤트 소싱 — 상태 대신 사실을 저장한다

보통 데이터베이스의 레코드나 문서 저장소의 문서가 비즈니스의 진실이다. **그 상태가 진실의 원천**이다. 이벤트 소싱은 이것을 뒤집는다. **기록된 이벤트가 진실의 원천이 된다.**

예전에는 이것을 감사 추적(audit trail)이라고 불렀다. 데이터베이스 트리거가 추가·갱신·삭제·읽기마다 발화해 어떤 데이터 수정이 있었고, 누가 했고, 왜 했고, 언제 했는지를 감사 테이블에 기록했다.

은행 명세서가 가장 좋은 비유다. 전월 이월 잔액에서 시작해, 기간 중의 거래 목록이 이어진다. 입금, 출금, 자동이체, 이자, 정기 이체, 수수료, 급여. **각 거래가 이벤트다.** 데이터베이스 관점에서 현재 잔액만 보면 어떻게 그 상태에 도달했는지 알 수 없다. 여러 테이블을 조인하는 쿼리를 써야 사실이 드러나고, 그래도 **왜** 그 변경이 일어났는지의 맥락은 알 수 없다.

이벤트는 **추가 전용(append-only) 형태의 애그리게이트(aggregate)** 로 저장된다. 애그리게이트는 일관성의 수호자다. 이벤트를 앞뒤로 재생하면 특정 시점의 마지막 일관된 상태로 되돌릴 수 있다. 계좌마다 스트림과 고유 식별자가 있고 그 계좌에 대한 모든 이벤트가 그 스트림에 기록된다 — **애그리게이트당 스트림 하나**다.

| 이벤트 소싱이 사는 것 | 지불하는 비용 |
|---|---|
| 완전한 감사 추적. **왜** 상태가 바뀌었는지까지 남는다 | 현재 상태를 알려면 이벤트를 재생해야 한다. 스냅샷 메커니즘이 별도로 필요하다 |
| 시점 복원 — 과거 어느 순간의 상태로 되돌릴 수 있다 | 저장 용량이 계속 늘어난다. 삭제가 어렵다(GDPR 삭제권과 충돌한다) |
| 이벤트 로그 자체가 경영·마케팅·재무에 가치 있는 정보다 | **이벤트 스키마 버저닝**이 영구 과제가 된다. 3년 전 이벤트도 읽을 수 있어야 한다 |

> **⚠️ 이벤트 소싱은 되돌리기가 가장 어려운 결정이다**
>
> CQRS는 나중에 걷어낼 수 있다. 이벤트 소싱은 다르다. 이벤트 스토어가 진실의 원천이 되는 순간, **모든 과거 이벤트를 영원히 읽을 수 있어야 한다.** 이벤트 클래스에 속성 하나를 추가하거나 이름을 바꾸는 것이 마이그레이션 프로젝트가 된다.
>
> 감사 추적이 필요한 것과 이벤트 소싱이 필요한 것은 다르다. **감사 테이블이면 충분한지 먼저 물어라.** 대부분의 시스템에서는 충분하다.

### 서버리스와 컨테이너

컨테이너와 서버리스 기술은 모두 마이크로서비스 생태계에서 정당한 자리를 갖는다. 핵심은 강점과 약점을 알고 필요에 맞는 쪽을 고르는 것이다.

| | 컨테이너 | 서버리스 |
|---|---|---|
| **강점** | 레거시 코드를 **다시 쓰지 않고** 현대적 플랫폼으로 옮길 수 있다. 웹 서비스와 배치 프로세스를 컨테이너에 넣어 클라우드에 배포하고, 시간·예산·인력이 생겼을 때 재작성을 계획하면 된다 | 이벤트 기반 접근을 장려한다. 코드가 쉽게 확장되고, 비즈니스가 바뀌면 쉽게 다시 쓰거나 버릴 수 있다 |
| **비용 모델** | **항상 켜져 있는 클러스터 노드**가 최소 몇 개 필요하다. 그 비용이 계속 나간다 | **스케일 투 제로.** 함수는 필요할 때만 돌고 안 쓰면 안 돈다. 실행 시간만큼만 지불한다 |
| **개발 편의** | Docker Compose 파일로 여러 마이크로서비스를 로컬에서 한꺼번에 띄운다. Docker Hub에서 서드파티 의존성 컨테이너를 바로 받아 쓴다 | 프로그래밍 모델이 단순해 빠른 개발이 가능하다 |
| **보안** | Kubernetes의 인그레스 컨트롤러로 노출할 서비스만 노출한다. 공격 표면이 작아진다 | 함수가 보안 위험이 될 수 있어 별도 조치가 필요하다 |
| **약점** | 더 무겁고 컴퓨팅 파워를 더 요구하는 옛 개발 기법을 조장할 수 있다. 컴퓨팅 비용이 올라간다 | 콜드 스타트. 상태를 함수 밖에 두어야 한다 |

Azure Functions에는 상태를 런타임이 관리해주는 **Durable Functions**가 있고, 널리 쓰이는 패턴이 정리되어 있다.

| 패턴 | 무엇을 푸나 |
|---|---|
| 애그리게이터(상태 있는 엔티티) | 여러 소스에서 시간에 걸쳐 도착하는 이벤트 데이터를 하나의 주소 지정 가능한 엔티티에 모으고, 집계 결과를 외부 클라이언트가 질의하게 한다. **단일 프로세스/VM에서 실행해야 한다** — 상태 없는 일반 함수로는 동시성 제어가 복잡해지기 때문 |
| 비동기 HTTP API | 오래 걸리는 함수 실행을 처리하는 내장 메커니즘. 런타임이 상태를 관리한다 |
| 팬아웃/팬인 | 함수들을 병렬로 실행하고 그 결과를 모은다 |
| 함수 체이닝 | 함수 순서를 한 곳에서 정하고, 스토리지 큐를 런타임이 자동 관리하며, 활동에서 난 오류가 오케스트레이션 함수로 전파된다 |
| 사람 개입 | 합의된 기한 안에 사람의 상호작용이 없으면 프로세스를 에스컬레이션한다 |
| 모니터링(액터) | 시스템 자원 해제 같은 반복 작업. 반복 간격 관리, 오케스트레이션 하나로 여러 모니터 프로세스 관리, 작업 수명 관리 |

> **⚠️ 콜드 스타트는 3권의 시작 시간 문제 그 자체다**
>
> 서버리스의 스케일 투 제로는 비용을 아껴주지만, 그 대가로 **호출이 없다가 처음 들어올 때 프로세스를 새로 띄운다.** 여기에 런타임 초기화, 어셈블리 로드, JIT 컴파일이 전부 들어간다.
>
> 즉 서버리스 함수는 **72.7절(시작 시간 최적화)과 55.7절(R2R·Native AOT)이 곧바로 돈으로 환산되는 유일한 배포 형태**다. 그리고 81.3절에서 본 대로, .NET 8에서 AOT를 쓰려면 컨트롤러가 아니라 **최소 API**여야 하고 EF Core를 쓸 수 없다. 함수의 프레임워크 선택과 데이터 접근 기술 선택(81.7절)이 배포 형태에 의해 역방향으로 제약되는 것이다.
>
> 72.3절 끝의 계산 — 같은 논리적 작업이 월 5만 달러 차이를 만든다 — 이 나온 곳도 정확히 이 자리다.

### 확장과 성능

워크로드가 현재 시스템의 처리 능력을 넘으면 선택지는 둘이다. **수직 확장(scale up)** 은 물리적 컴퓨팅 용량을 늘리는 것이고, **수평 확장(scale out)** 은 서버를 더 붙이는 것이다. 현재 많은 회사가 택하는 길은 서버 VM과 컨테이너를 Docker·Kubernetes 같은 컨테이너 관리 소프트웨어로 클라우드 플랫폼(Azure, AWS, Google Cloud 등)에서 돌리는 것이다. 큰 라이브러리와 실행 파일은 Azure Functions 같은 마이크로서비스로 코드를 옮겨 작게 만들 수 있다 — 필요할 때만 실행되고 확장·축소되므로 전기와 장비 비용을 아낀다.

분산 환경에서 성능 문제를 진단할 때 자주 나오는 원인들은 다음과 같다.

- **네트워크** — TCP 충돌(같은 IP를 쓰는 컴퓨터가 둘 이상일 때 흔하다)로 패킷이 유실되어 연결이 타임아웃된다. DNS 설정 오류로 리소스 접근이 예상보다 오래 걸린다. 분산 방화벽 설정 오류로 리소스가 거부되거나 보이지 않는다.
- **데이터베이스** — 같은 결과를 내는 쿼리도 작성 방식에 따라 성능이 크게 다르다. 특히 조인이 많은 큰 결과 집합에서 그렇다. 동적 SQL도 느릴 수 있다. 실행 계획을 검토해 병목을 찾고, 누락된 인덱스를 추가하고, 잘못된 인덱스를 고치고, 미리 컴파일된 저장 프로시저를 쓴다.
- **연결 수** — 리소스 서버가 특정 임계치에 도달하면 클라이언트를 대체 서버로 보내는 로드 밸런싱을 도입한다.
- **보안 소프트웨어** — 방화벽과 백신이 네트워크 트래픽을 크게 느리게 하고 프로그램을 아예 막을 수 있다. 인증 기관이 승인한 코드 서명 인증서로 서명하지 않은 DLL과 실행 파일은 유해 소프트웨어로 오탐되어 격리될 수 있다(52.7절).
- **리소스 크기** — 크기가 클수록 요청·수신 시간이 길어진다. 이미지·비디오·오디오는 압축하고, 애플리케이션 시작 시점처럼 미리 전송할 수 있는 것은 미리 보내고, 한 번 받은 것은 로컬 캐시에 둔다.

분산 시스템의 성능 고려사항 전반은 72.10절에 있다.

## 이 장의 요약

- **애플리케이션 유형은 SDK가 결정한다.** `.csproj`의 `Sdk` 특성이 암시적 `using`, 기본 빌드 동작, 사용 가능한 호스팅 모델을 정한다. 유형 선택은 이 장 첫 표의 "부적합한 경우" 열을 먼저 읽고 하는 것이 빠르다.
- **호스트의 유무가 콘솔 앱과 워커 서비스를 가른다.** 워커에는 요청이 없으므로 스코프를 개발자가 직접 열어야 하고, `ExecuteAsync`에서 새는 예외는 .NET 6부터 호스트를 내린다.
- **라이브러리는 애플리케이션이 아니다.** 의존성은 전염되고, 트림 안전성은 소비자가 아니라 라이브러리가 결정한다. `<IsAotCompatible>`(※.NET 8)로 분석기를 켜고 `[DynamicallyAccessedMembers]`·`[RequiresDynamicCode]`로 계약을 명시하라.
- **ASP.NET Core 앱은 콘솔 앱이다.** `builder.Build()`가 등록 구간과 파이프라인 구간을 가른다. 미들웨어 순서는 문서가 아니라 코드이고, 순서를 틀리면 예외 없이 조용히 보안이 열린다.
- **DI 수명 셋 중 스코프가 HTTP 요청이다.** 싱글턴이 스코프 서비스를 붙잡는 포획 의존성은 3권의 언어로 GC 루트가 gen2를 고정하는 문제이며, `ValidateScopes`·`ValidateOnBuild`를 **모든 환경에서** 켜야 프로덕션에서 조용히 죽지 않는다.
- **최소 API를 고르는 진짜 이유는 처리량이 아니라 AOT 가능 여부다.** .NET 8 기준 컨트롤러와 EF Core는 Native AOT를 지원하지 않는다.
- **`DbContext`는 스레드 안전하지 않다.** 기본 Scoped 수명은 Blazor 서버 측에서 깨지고, 해법은 Transient 등록이나 `AddDbContextFactory<T>`다. `AsNoTracking`은 항상 빠르지 않다 — 아이덴티티 해석까지 꺼져 중복 인스턴스를 만든다.
- **데이터 접근 기술은 하나로 통일하지 않아도 된다.** 쓰기는 EF Core, 복잡한 읽기는 Dapper, 벌크는 ADO.NET이 CQRS의 가장 저렴하고 실용적인 형태다.
- **배포 형태의 모든 선택은 3권 어딘가에 대응하는 절이 있다.** 트리밍은 57.14절, AOT는 55.7절, 시작 시간은 72.7절, 컨테이너 GC는 65.7절과 72.8절이다. 그리고 컨테이너에서는 이미지 크기보다 GC 설정이 먼저다.
- **분산 패턴은 복잡도를 지불하고 속성을 산다.** CQRS는 되돌릴 수 있고 이벤트 소싱은 사실상 되돌릴 수 없다. 서버리스의 콜드 스타트는 시작 시간 최적화가 곧 요금이 되는 유일한 자리다.

## 연습 문제

1. 워커 서비스 프로젝트를 만들고 `BackgroundService.ExecuteAsync`에서 5초 후 `InvalidOperationException`을 던지게 하라. 프로세스가 종료되는지 확인하고, `HostOptions.BackgroundServiceExceptionBehavior`를 `Ignore`로 바꾼 뒤 다시 실행해 차이를 관찰하라. 어느 쪽이 운영에서 발견하기 쉬운가?
2. ASP.NET Core 웹 API를 만들고 싱글턴 서비스의 생성자에서 `DbContext`를 받도록 하라. `ASPNETCORE_ENVIRONMENT=Development`로 실행했을 때와 `Production`으로 실행했을 때의 동작 차이를 확인하고, `ValidateScopes = true`를 명시적으로 켠 뒤 다시 비교하라.
3. 81.3절의 인라인 미들웨어 델리게이트를 파이프라인에 넣고 `/`, `/index`, `/index.html`, 존재하지 않는 경로를 각각 요청하라. 콘솔 출력이 나오는 경우와 나오지 않는 경우를 정리하고, 그 델리게이트를 `UseStaticFiles` **뒤로** 옮겼을 때 결과가 어떻게 달라지는지 설명하라.
4. 같은 조회를 세 가지 추적 설정(기본, `AsNoTracking`, `AsNoTrackingWithIdentityResolution`)으로 한 컨텍스트 안에서 두 번씩 실행하고, `db.ChangeTracker.Entries().Count()`와 반환된 인스턴스의 참조 동일성(`ReferenceEquals`)을 비교하라. `dotnet-counters`로 할당량 차이도 함께 측정하라(66.8절).
5. 콘솔 앱 하나를 다섯 가지로 게시하라 — FDD, 자체 포함, 단일 파일, 단일 파일+트리밍+R2R, Native AOT. 각각의 파일 수, 총 크기, 첫 실행 시간을 표로 정리하라. 그다음 코드에 `AssemblyBuilder.DefineDynamicAssembly` 호출을 추가하고 AOT 게시를 다시 시도해 어떤 경고가 나오는지 확인하라.
6. 최소 API와 컨트롤러로 같은 엔드포인트 하나씩을 구현한 프로젝트를 각각 만들고, `<PublishAot>true</PublishAot>`로 게시해보라. 어느 쪽이 성공하고 어느 쪽이 어떤 경고·오류를 내는가? 컨트롤러 프로젝트에 EF Core를 추가하면 결과가 어떻게 달라지는가?
7. Blazor Web App 프로젝트를 만들어 같은 컴포넌트를 대화형 서버 모드와 대화형 WebAssembly 모드로 각각 렌더링하라. 브라우저 탭을 열 때마다 서버 프로세스의 관리 힙 크기가 어떻게 변하는지 `dotnet-counters`로 관찰하고, 탭을 전부 닫은 뒤 힙이 회수되기까지 걸리는 시간을 재라.
