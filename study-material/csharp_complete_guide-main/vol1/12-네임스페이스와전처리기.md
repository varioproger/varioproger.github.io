# 12장. 네임스페이스와 전처리기

> **이 장의 위치** — 6장부터 11장까지는 "타입 하나, 메서드 하나 안에서 무엇을 쓸 수 있는가"였다. 이 장은 시선을 한 단계 올려 **그 코드 조각들을 파일과 프로젝트 안에 어떻게 배치하는가**를 다룬다. 이름을 어느 영역에 두고, 다른 영역의 이름을 어떻게 끌어오고, 같은 이름이 둘일 때 컴파일러가 무엇을 고르는지가 앞의 절반이다. 뒤의 절반은 컴파일러가 소스를 읽기 **전에** 소스의 어느 부분을 볼지 결정하는 전처리기 지시문, 그리고 소스에 적어 두면 IDE와 NuGet 패키지까지 따라가는 XML 문서 주석이다. Part II의 마지막 장이며, 여기까지 오면 "혼자 돌아가는 C# 파일"이 아니라 "여럿이 나눠 쓰는 프로젝트"를 쓸 준비가 된다.
>
> **선수 지식** — 3장(첫 프로그램이 실행되기까지), 특히 3.7절(최상위 문과 암시적 `using`). 4장(프로젝트, 대상 프레임워크, 배포 형태), 특히 4.1절(`.csproj` 해부)과 4.6절(`Nullable`, `ImplicitUsings`). 6장(구문과 타입 기초).
>
> **이 장에서 다루지 않는 것** — **네임스페이스와 어셈블리는 다른 것**이며, 어셈블리가 무엇을 담고 런타임이 타입 참조를 어떻게 해석하는지는 52.1절과 52.8절이다. `internal`을 다른 어셈블리에 열어 주는 `InternalsVisibleTo`는 17.2절이고, 접근 제한자 전체는 17.1절이다. `[Conditional]` 특성의 정의와 동작은 20.10절, 진단 코드 관점에서 조건부 컴파일·정적 플래그·`[Conditional]`을 끝까지 비교하는 것은 73.1절이다(이 장의 12.8절은 그 비교의 요약본이다). 널 가능 참조 타입의 의미론 전체는 21.6절이며 여기서는 `#nullable` 지시문의 문법만 다룬다. 튜플 별칭의 세부는 77.4절, NuGet 패키징 실무는 81.2절이다.

## 12.1 네임스페이스 선언과 파일 범위 네임스페이스 ※C# 10

### 네임스페이스는 타입 이름의 영역이다

**네임스페이스**(namespace)는 타입 이름이 사는 영역이다. 타입을 계층적으로 정리해 찾기 쉽게 만들고, 이름 충돌을 피하게 해 준다. 공개 키 암호화를 담당하는 `RSA` 타입은 다음 네임스페이스 안에 정의되어 있다.

```text
System.Security.Cryptography
```

여기서 중요한 것은 네임스페이스가 타입 이름을 **꾸미는 장식이 아니라 이름의 일부**라는 사실이다. 다음 코드는 `RSA`의 `Create` 메서드를 호출한다.

```csharp
System.Security.Cryptography.RSA rsa =
    System.Security.Cryptography.RSA.Create();
```

이 긴 이름이 이 타입의 **완전 정규화된 이름**(fully qualified name)이다. `using` 지시문(12.2절)은 이 이름을 짧게 쓰게 해 주는 편의 장치일 뿐, 타입의 진짜 이름을 바꾸지 않는다.

> **⚠️ 네임스페이스와 어셈블리는 아무 관계가 없다**
>
> `System.Security.Cryptography` 네임스페이스의 타입들이 반드시 `System.Security.Cryptography.dll` 하나에 들어 있는 것이 아니다. 하나의 네임스페이스가 여러 어셈블리에 흩어질 수 있고, 하나의 어셈블리가 여러 네임스페이스를 담을 수 있다. 네임스페이스는 **컴파일러가 이름을 찾을 때 쓰는 논리적 영역**이고, 어셈블리는 **배포 단위인 `.dll` 파일**이다.
>
> 이 둘을 혼동하면 "`using`을 썼는데 타입을 못 찾는다"는 상황에서 영영 헤매게 된다. `using`은 이름을 짧게 해 줄 뿐 어셈블리를 참조 목록에 추가하지 않는다. 그 타입이 사는 어셈블리를 참조하지 않았다면 `using`을 백 번 써도 컴파일되지 않는다(3.4절). 어셈블리의 실체와 런타임 타입 참조 해석은 52.1절과 52.8절에서 다룬다.

> **📌 네임스페이스는 가시성에 영향을 주지 않는다**
>
> `public`, `internal`, `private` 같은 접근 제한자는 네임스페이스와 무관하게 동작한다. 같은 네임스페이스에 있다고 해서 서로의 `private` 멤버가 보이지 않고, 다른 네임스페이스에 있다고 해서 `public` 타입이 안 보이지도 않는다. `internal`의 경계는 네임스페이스가 아니라 **어셈블리**다. 접근 제한자 전체는 17.1절에서 다룬다.

### 블록 네임스페이스와 점 표기

`namespace` 키워드는 블록 안의 타입들이 속할 네임스페이스를 정한다.

```csharp
namespace Outer.Middle.Inner
{
    class Class1 { }
    class Class2 { }
}
```

네임스페이스 이름의 점은 **중첩 계층**을 뜻한다. 위 코드는 `namespace Outer { namespace Middle { namespace Inner { ... } } }`로 세 겹을 직접 중첩한 것과 의미가 완전히 같다. `Class1`의 완전 정규화된 이름은 `Outer.Middle.Inner.Class1`이다.

어느 네임스페이스에도 속하지 않은 타입은 **전역 네임스페이스**(global namespace)에 산다고 말한다. 전역 네임스페이스는 최상위 네임스페이스들(위 예에서 `Outer`)도 포함한다.

### 파일 범위 네임스페이스 ※C# 10

한 파일의 타입 전부를 하나의 네임스페이스에 넣는 것이 압도적으로 흔한 경우다. 그런데 블록 문법은 그 흔한 경우에 항상 중괄호 한 쌍과 **들여쓰기 한 단계**를 요구한다. ※C# 10부터는 **파일 범위 네임스페이스**(file-scoped namespace)로 같은 일을 중괄호 없이 할 수 있다.

```csharp
namespace MyNamespace;    // 이 파일에서 뒤따르는 모든 것에 적용된다

class Class1 { }
class Class2 { }
```

중괄호 대신 세미콜론 하나다. 선언 이후 파일 끝까지가 전부 그 네임스페이스에 들어간다.

> **💡 들여쓰기 한 단계가 왜 중요한가**
>
> "중괄호 두 개와 공백 네 칸"이 뭐가 대수인가 싶지만, 이것은 파일마다 반복되는 고정 비용이다.
>
> - **가로 공간**은 유한하다. 팀 컨벤션이 120칼럼이면 네임스페이스 들여쓰기 4칸은 실제 코드에 쓸 수 있는 폭의 3%를 상시 잡아먹는다. 여기에 클래스 들여쓰기 4칸, 메서드 4칸이 더해지면 메서드 본문은 이미 12칼럼에서 시작한다. 긴 제네릭 타입 이름 하나에 줄바꿈이 생기는 경계선이 바로 이 근처다.
> - **diff 노이즈**가 준다. 네임스페이스를 바꾸면 블록 문법에서는 파일 전체가 다시 들여쓰기되어 한 줄짜리 변경이 200줄짜리 diff가 된다. 파일 범위 문법에서는 한 줄만 바뀐다.
> - **의도가 드러난다.** 세미콜론 문법은 "이 파일에는 네임스페이스가 하나뿐"임을 문법 수준에서 못 박는다. 블록 문법에서는 파일 끝까지 읽어야 두 번째 `namespace` 블록이 없다는 걸 알 수 있다.
>
> 새 코드는 파일 범위 네임스페이스로 쓰는 편이 낫다. 기존 코드 전체를 일괄 변환할 때는 `.editorconfig`의 `csharp_style_namespace_declarations = file_scoped:warning` 규칙을 켜고 IDE의 일괄 수정을 쓰면 된다.

파일 범위 네임스페이스에는 규칙이 셋 붙는다. 한 파일에 파일 범위 선언은 **하나만** 올 수 있고, 파일 범위 선언과 블록 선언을 **같은 파일에서 혼용할 수 없으며**, 파일 범위 선언은 타입 선언보다 **앞**에 와야 한다. 그 앞에 올 수 있는 것은 `extern alias`, `using`, 특성뿐이며, 셋 중 하나라도 어기면 컴파일 오류다.

다만 파일 범위 선언 **안에서** 다시 블록 네임스페이스를 여는 것은 허용되며, 이 방식으로 중첩을 표현할 수 있다.

```csharp
namespace CustomNamespaces;

namespace MyShapes            // 실제 네임스페이스는 CustomNamespaces.MyShapes
{
    public class Circle { }
}
```

하지만 실무에서 중첩을 표현하는 방법으로 압도적으로 흔한 것은 점 표기(`namespace CustomNamespaces.MyShapes;`)다.

> **⚠️ 최상위 문이 있는 파일에는 네임스페이스를 쓸 수 없다**
>
> 최상위 문(3.7절)으로 시작하는 파일, 즉 프로젝트의 `Program.cs`에는 `namespace` 선언을 넣을 수 없다. 최상위 문이 컴파일러가 만드는 숨은 `Program` 클래스의 본문이 되기 때문이다.
>
> 최상위 문 파일 안에 타입을 선언하는 것은 가능하지만(파일 끝에 붙여야 한다), 그렇게 선언한 타입은 **전역 네임스페이스**에 놓인다. 나중에 그 타입을 다른 파일에서 쓰려 하면 네임스페이스가 안 맞아 혼란스러워지므로, 타입은 별도 파일로 빼는 편이 낫다.

### 같은 네임스페이스를 여러 번 선언해도 된다

네임스페이스 선언은 반복할 수 있다. 그 안의 타입 이름만 충돌하지 않으면 된다.

```csharp
// 파일 A                          // 파일 B
namespace Outer.Middle.Inner       namespace Outer.Middle.Inner
{                                  {
    class Class1 { }                   class Class2 { }
}                                  }
```

두 파일이 서로 다른 **어셈블리**로 컴파일되어도 상관없다. 그 결과 `Outer.Middle.Inner`라는 하나의 네임스페이스가 두 어셈블리에 걸쳐 존재하게 된다. `System` 네임스페이스가 정확히 그렇게 되어 있다.

한 파일 안에서 블록 문법을 쓴다면 여러 네임스페이스를 나란히 둘 수도 있다 — `namespace Sales { ... }`와 `namespace Billing { ... }`을 한 파일에 두는 식이다.

> **💡 파일 하나에 타입 하나, 폴더 구조는 네임스페이스와 일치시켜라**
>
> C# 컴파일러는 파일 이름과 타입 이름의 일치도, 폴더 구조와 네임스페이스의 일치도 요구하지 않는다. 하지만 팀 작업에서는 둘 다 맞추는 것이 사실상 표준이다.
>
> 이유는 병합 충돌이다. 한 파일에 `Circle`, `Square`, `Hexagon`이 다 들어 있으면 세 사람이 각자 다른 클래스를 고쳐도 같은 파일을 건드려 충돌이 난다. 클래스마다 파일을 나누면 충돌 자체가 생기지 않는다. 폴더 구조 일치는 도구가 거들어 준다 — IDE가 `Shapes/` 폴더의 새 클래스에 `RootNamespace.Shapes`를 자동으로 붙여 주고, 불일치는 Roslyn 분석기 규칙 IDE0130이 경고한다.

### 명명 규칙

관례적인 네임스페이스 이름은 다음 모양이다.

```text
회사명.제품명.어셈블리명.경로
```

예를 들어 `Newtonsoft.Json.Linq`, `Microsoft.Extensions.DependencyInjection.Abstractions` 같은 식이다. 회사명으로 시작하는 이유는 단순하다 — 전 세계의 NuGet 패키지가 한 프로젝트에 섞여도 최상위 이름이 충돌하지 않게 하기 위해서다.

`RootNamespace`는 `.csproj`에서 바꾼다. 기본값은 프로젝트 이름이다.

```xml
<PropertyGroup>
  <RootNamespace>MyCompany.Shapes</RootNamespace>
</PropertyGroup>
```

> **📌 `RootNamespace`는 컴파일러 옵션이 아니다**
>
> `RootNamespace`는 C# 컴파일러에게 전달되지 않는다. IDE와 SDK가 **새 파일을 만들 때 어떤 `namespace` 줄을 적어 넣을지** 결정하는 데 쓰는 값이고, 그 외에는 리소스 파일의 매니페스트 이름(53장)을 만드는 데 쓰인다. 이미 존재하는 파일의 `namespace` 선언에는 아무 영향이 없다. `RootNamespace`를 바꿔도 기존 코드는 그대로다.

### 컴파일 결과 — IL에 네임스페이스는 없다

여기가 이 절의 핵심이다. **네임스페이스는 순수한 컴파일 타임 개념이다.**

메타데이터의 `TypeDef` 테이블에는 타입마다 두 개의 문자열 열이 있다 — `TypeNamespace`와 `TypeName`. 컴파일러는 소스의 네임스페이스 계층을 평평하게 눌러 점으로 이은 문자열 하나로 이 열에 적는다.

```text
소스                                     메타데이터 TypeDef 행
┌────────────────────────────┐          ┌────────────────┬───────────┐
│ namespace Outer            │          │ TypeNamespace  │ TypeName  │
│ {                          │   ───▶   ├────────────────┼───────────┤
│   namespace Middle         │          │ Outer.Middle   │ Class1    │
│   { class Class1 { } }     │          └────────────────┴───────────┘
│ }                          │
└────────────────────────────┘          중첩 계층은 사라지고 문자열 하나만 남는다
```

이 사실에서 몇 가지가 따라 나온다.

- **런타임에는 "네임스페이스"라는 개체가 없다.** 리플렉션의 `Type.Namespace`는 저 문자열 열을 그대로 읽어 돌려주는 프로퍼티다. `Namespace` 클래스 같은 것은 존재하지 않는다.
- **IL에는 짧은 이름이나 부분 정규화 이름이 나타나지 않는다.** 모든 타입 참조는 완전 정규화된 이름이다. 그러므로 `using`을 쓰든 안 쓰든 결과 IL은 한 바이트도 다르지 않다.
- **네임스페이스를 깊게 파도 런타임 비용이 없다.** `A.B.C.D.E.F.Thing`이 `Thing`보다 느리지 않다. 다만 메타데이터의 문자열 힙에 조금 더 긴 문자열이 들어갈 뿐이며, 어셈블리 크기에 바이트 단위로 영향을 준다.

> **📌 중첩 타입은 다르다**
>
> 네임스페이스 중첩과 **타입 중첩**은 메타데이터에서 완전히 다르게 표현된다. `namespace A { class B { } }`는 `TypeNamespace = "A"`, `TypeName = "B"`가 되지만, `class A { class B { } }`는 `TypeNamespace = ""`, `TypeName = "B"`에 `NestedClass` 테이블 항목이 하나 더 생긴다. 완전 정규화된 이름을 문자열로 적을 때도 다르다 — 중첩 타입은 점이 아니라 `+`를 쓴다(`A+B`). `Type.GetType("A+B")`처럼 리플렉션에서 타입을 이름으로 찾을 때 이 차이가 드러난다(57장). 중첩 타입 자체는 17.5절에서 다룬다.

## 12.2 `using` 지시문과 이름 해석 규칙

### 문법

`using` 지시문은 네임스페이스를 **가져온다**(import). 그러면 그 안의 타입을 짧은 이름으로 쓸 수 있다.

```csharp
using Outer.Middle.Inner;

Class1 c;      // 완전 정규화된 이름이 필요 없다
```

`using`이 하는 일은 그것뿐이다. 코드를 삽입하지도, 어셈블리를 참조하지도, 실행 시점에 무언가를 로드하지도 않는다. **컴파일러가 짧은 이름을 만났을 때 어디를 찾아볼지 후보 목록에 한 줄 추가하는 것**이 전부다.

> **⚠️ `using`은 재귀적이지 않다**
>
> `using System;`을 썼다고 `System.Collections.Generic`의 타입이 보이지는 않는다. 네임스페이스 계층은 이름의 구조일 뿐 포함 관계가 아니며, `using`은 **정확히 그 네임스페이스에 직접 들어 있는 타입만** 가져온다.
>
> 초보자가 `using System;` 하나로 `List<T>`를 쓰려다 실패하는 이유가 이것이다. 지금은 암시적 `using`이 `System.Collections.Generic`도 넣어 주기 때문에 이 실수를 겪을 일이 줄었지만(12.3절), 원리는 알아 둬야 한다.

### 이름 해석 순서

같은 짧은 이름을 여러 곳에서 찾을 수 있을 때 컴파일러가 무엇을 고르는지가 이 절의 본론이다. 규칙은 **가까운 것이 이긴다**로 요약된다.

식별자 `Foo`를 만났을 때 컴파일러가 보는 순서는 다음과 같다.

```text
  1. 지역 범위 — 지역 변수, 매개변수, 타입 매개변수
        ↓ 못 찾으면
  2. 현재 타입의 멤버 (그리고 기반 타입의 멤버)
        ↓ 못 찾으면
  3. 현재 타입을 감싼 타입들 (중첩 타입인 경우, 안쪽부터 바깥쪽으로)
        ↓ 못 찾으면
  4. 현재 네임스페이스에 직접 선언된 타입
        ↓ 못 찾으면
  5. 현재 네임스페이스에 적용된 using 지시문들   ── 여기서 여러 개면 CS0104
        ↓ 못 찾으면
  6. 한 단계 바깥 네임스페이스로 올라가 4~5를 반복
        ↓ 계속 올라가 전역 네임스페이스까지
  7. 전역 범위의 using 지시문 (파일 최상단 + global using)
        ↓ 못 찾으면
  8. CS0246 — 형식 또는 네임스페이스 이름을 찾지 못함
```

핵심은 **4번이 5번보다 먼저**라는 점이다. 즉 **직접 선언된 타입은 언제나 `using`으로 가져온 타입을 이긴다.** 그리고 이 우선이 조용하다 — 경고조차 나지 않는다.

### 바깥 네임스페이스의 이름은 안쪽에서 그냥 보인다

바깥 네임스페이스에 선언된 이름은 안쪽 네임스페이스에서 한정 없이 쓸 수 있다.

```csharp
namespace Outer
{
    class Class1 { }

    namespace Inner
    {
        class Class2 : Class1 { }     // Outer.Class1 — 한정이 필요 없다
    }
}
```

네임스페이스 계층의 다른 가지에 있는 타입은 **부분 정규화된 이름**으로 참조할 수 있다.

```csharp
namespace MyTradingCompany
{
    namespace Common
    {
        class ReportBase { }
    }

    namespace ManagementReporting
    {
        class SalesReport : Common.ReportBase { }    // 부분 정규화
    }
}
```

`ManagementReporting` 안에서 `Common`을 찾을 때 컴파일러는 한 단계 바깥인 `MyTradingCompany`로 올라가 `MyTradingCompany.Common`을 찾아낸다.

### 이름 숨김 — 안쪽이 이긴다

같은 타입 이름이 안쪽과 바깥쪽 네임스페이스에 모두 있으면 **안쪽이 이긴다.** 바깥의 것을 쓰려면 한정해야 한다.

```csharp
namespace Outer
{
    class Foo { }

    namespace Inner
    {
        class Foo { }

        class Test
        {
            Foo f1;          // = Outer.Inner.Foo
            Outer.Foo f2;    // = Outer.Foo
        }
    }
}
```

> **⚠️ 이름 숨김은 조용하다 — 리팩터링의 함정**
>
> 위 코드에서 `Outer.Inner.Foo`를 나중에 삭제하면 `Foo f1;`이 갑자기 `Outer.Foo`를 가리키게 된다. **컴파일은 성공한다.** 타입이 우연히 호환된다면 동작까지 바뀐 채로 넘어간다.
>
> 반대 방향도 있다. 잘 돌아가던 코드에 누군가 안쪽 네임스페이스에 `Foo`라는 클래스를 새로 추가하면, 그 네임스페이스 안의 모든 `Foo` 참조가 조용히 새 타입으로 갈아탄다. 새 타입에 같은 이름의 멤버가 있으면 컴파일 오류조차 나지 않는다.
>
> 이것이 흔한 짧은 이름(`Task`, `Timer`, `Path`, `File`, `Console`, `Environment`, `Buffer`, `Log`, `Settings`, `Configuration`)을 자기 코드의 타입 이름으로 쓰면 안 되는 이유다. 특히 `Task`는 최악이다 — 업무 도메인의 "작업"을 `Task`라고 이름 붙이는 순간 그 네임스페이스 안에서는 `System.Threading.Tasks.Task`를 쓸 때마다 완전 정규화해야 한다.

### 모호할 때 — CS0104

두 개의 `using`이 같은 짧은 이름을 제공하고, 그 이름이 직접 선언된 타입으로도 없다면 컴파일러는 **고르지 않는다.** 오류를 낸다.

```csharp
using CustomNamespaces.MyShapes;      // Circle, Square, Hexagon
using CustomNamespaces.My3DShapes;    // Circle, Square, Hexagon

Hexagon h = new Hexagon();    // 오류!
Circle c = new Circle();      // 오류!
Square s = new Square();      // 오류!
```

```text
error CS0104: 'Hexagon' is an ambiguous reference between
'CustomNamespaces.MyShapes.Hexagon' and 'CustomNamespaces.My3DShapes.Hexagon'
```

해결책은 세 가지다.

```csharp
// (1) 완전 정규화 — 쓰는 자리마다
CustomNamespaces.My3DShapes.Hexagon h = new CustomNamespaces.My3DShapes.Hexagon();

// (2) 별칭 — 12.5절
using ThreeD = CustomNamespaces.My3DShapes;
ThreeD.Hexagon h2 = new ThreeD.Hexagon();

// (3) 문제가 되는 using 하나를 빼고, 그쪽만 완전 정규화
using CustomNamespaces.MyShapes;
var h3 = new CustomNamespaces.My3DShapes.Hexagon();
```

> **💡 같은 이름을 다른 네임스페이스에 두는 것 자체는 죄가 아니다**
>
> 오히려 흔하고 바람직하다. 다만 조건이 있다 — **소비자가 두 네임스페이스를 동시에 가져올 일이 없어야 한다.** 좋은 예가 `TextBox`다. `System.Windows.Controls.TextBox`(WPF)와 `System.Windows.Forms.TextBox`(Windows Forms)가 같이 있지만, 한 파일에서 둘을 동시에 쓰는 사람은 거의 없다.
>
> 나쁜 예는 같은 제품의 `Models`와 `Dtos`에 `Customer`를 둘 다 두는 경우다. 매핑 코드에서 반드시 둘을 동시에 가져오게 되고, 그때부터 매 줄이 완전 정규화이거나 별칭이다. 그럴 바에는 `CustomerDto`라고 이름을 다르게 짓는 편이 낫다.

### `using`을 네임스페이스 안에 넣기

`using` 지시문은 네임스페이스 선언 **안**에 넣을 수 있다. 그러면 효력이 그 네임스페이스 안으로 제한된다.

```csharp
namespace N1
{
    class Class1 { }
}

namespace N2
{
    using N1;

    class Class3 : Class1 { }    // OK
}

class Class2 : Class1 { }        // 컴파일 오류 — 여기서는 N1이 안 보인다
```

이 기능은 실무에서 두 가지 용도로 쓰인다.

| 용도 | 설명 |
|---|---|
| 충돌 국지화 | 문제가 되는 `using`을 필요한 네임스페이스 블록 안에만 넣어, 파일의 나머지 부분을 모호함에서 지킨다 |
| 별칭 국지화 | `using X = ...` 별칭을 특정 네임스페이스에만 적용한다 |

> **⚠️ 파일 범위 네임스페이스에서는 국지화가 불가능하다**
>
> 파일 범위 네임스페이스(`namespace N;`)를 쓰면 그 아래 모든 `using`은 자동으로 그 네임스페이스 범위가 되지만, "파일의 이 부분만"이라는 국지화는 할 수 없다. 애초에 파일 안에 블록이 하나뿐이기 때문이다.
>
> 실무에서는 문제가 되지 않는다. 애초에 `using` 국지화가 필요할 만큼 복잡한 파일이면, 그 파일을 쪼개는 것이 옳은 해결이다.

### `using`의 위치 규칙

한 파일 안에서 지시문의 순서는 고정되어 있다.

```csharp
extern alias W1;                  // 1. extern alias (12.6절)
global using System.Text;         // 2. global using (12.3절)
using System;                     // 3. 일반 using
using static System.Math;
using Json = System.Text.Json;
[assembly: CLSCompliant(true)]    // 4. 어셈블리 특성
namespace MyApp;                  // 5. 네임스페이스 선언
using System.Linq;                // 6. 네임스페이스 범위 using
class Program { }                 // 7. 타입 선언
```

이 순서를 어기면 컴파일 오류다. 특히 `using`을 타입 선언 뒤에 쓸 수 없다는 점, `global using`이 일반 `using`보다 앞에 와야 한다는 점이 자주 걸린다.

### 컴파일 결과와 성능

**`using` 지시문은 IL에 아무 흔적도 남기지 않는다.** 12.1절에서 본 대로 IL의 모든 타입 참조는 완전 정규화된 이름이므로, 소스에서 `using`을 썼는지 완전 정규화된 이름을 적었는지는 컴파일 후 구분할 수 없다.

```csharp
// 이 두 메서드는 완전히 동일한 IL을 만든다
using System;
static void A() => Console.WriteLine("hi");

static void B() => System.Console.WriteLine("hi");
```

따라서 다음이 모두 참이다.

| 질문 | 답 |
|---|---|
| 쓰지 않는 `using`이 어셈블리 크기를 늘리는가 | 아니다. 0바이트다 |
| 쓰지 않는 `using`이 시작 시간을 늘리는가 | 아니다. 어셈블리 로드를 유발하지 않는다 |
| 쓰지 않는 `using`이 컴파일 시간을 늘리는가 | 이름 조회 후보가 늘어나므로 **아주 조금** 늘린다. 측정 가능한 수준은 아니다 |
| 그러면 왜 IDE가 회색으로 표시하고 지우라고 하는가 | 가독성과 이름 충돌 위험 때문이다 |

> **💡 그래도 쓰지 않는 `using`은 지워라 — 성능이 아니라 충돌 때문이다**
>
> 쓰지 않는 `using` 하나가 6개월 뒤 다른 사람이 추가한 타입과 CS0104를 일으킬 수 있다. IDE0005("불필요한 using 지시문") 규칙을 경고로 켜 두고 CI에서 `dotnet format --verify-no-changes`로 검사하면 자동으로 관리된다. 다만 IDE0005를 빌드에서 잡으려면 `.csproj`에 `<GenerateDocumentationFile>true</GenerateDocumentationFile>`이 필요한 알려진 제약이 있다 — 이 규칙이 정확히 동작하려면 컴파일러가 문서 주석까지 분석해야 하기 때문이다(12.9절).

> **⚠️ 확장 메서드는 `using`이 있어야 보인다**
>
> `using`이 순수한 편의 장치라는 말에는 예외가 하나 있다. **확장 메서드는 그 메서드를 담은 정적 클래스의 네임스페이스를 `using`으로 가져와야만 확장 형태로 호출할 수 있다.** 완전 정규화된 이름으로는 확장 형태를 쓸 수 없다.
>
> ```csharp
> using System.Linq;                       // 이게 없으면
> var evens = numbers.Where(n => n % 2 == 0);   // 이 호출이 안 된다
> ```
>
> `using System.Linq;`를 지우면 위 코드는 CS1061("`int[]`에 `Where` 정의가 없다")로 실패한다. `Enumerable.Where(numbers, n => ...)`라고 완전 정규화해서 부를 수는 있지만 점 문법은 `using` 없이 불가능하다. 확장 메서드의 해석 규칙은 20.5절에서 다룬다.

## 12.3 `global using`과 암시적 using ※C# 10

### 문법

`using` 지시문 앞에 `global` 키워드를 붙이면, 그 지시문은 **프로젝트(정확히는 컴파일 단위) 전체의 모든 파일**에 적용된다. ※C# 10부터다.

```csharp
global using System;
global using System.Collections.Generic;
```

이 두 줄을 프로젝트의 아무 `.cs` 파일에나 한 번 써 두면, 프로젝트의 모든 파일에서 `using System;`을 쓴 것과 같아진다.

규칙은 세 가지다.

| 규칙 | 이유 |
|---|---|
| `global using`은 일반 `using`보다 **앞**에 와야 한다 | 파싱 순서를 단순하게 유지하기 위해 |
| `namespace` 선언 **안**에는 쓸 수 없다 | 프로젝트 전체 범위인데 네임스페이스 안에 두면 의미가 모순된다 |
| `using static`, 별칭과 조합 가능하다 | `global using static System.Math;`, `global using Json = System.Text.Json;` 모두 유효 |

> **💡 `global using`은 한 파일에 모아라**
>
> 문법적으로는 아무 파일에나 써도 되지만, 흩어 놓으면 "이 프로젝트에서 무엇이 자동으로 가져와지는가"를 아무도 모르게 된다. 관례는 프로젝트 루트에 `GlobalUsings.cs`라는 파일을 하나 만들고 거기에만 쓰는 것이다.
>
> ```csharp
> // GlobalUsings.cs — 이 프로젝트의 전역 import 목록
> global using System.Text.Json;
> global using System.Diagnostics.CodeAnalysis;
> global using static MyCompany.Logging.Log;
> ```
>
> 이렇게 해 두면 "왜 이 파일에는 `using`이 없는데 컴파일되지?"라는 질문에 답할 곳이 한 군데로 정해진다.

### 암시적 using ※.NET 6

`.csproj`의 `<ImplicitUsings>` 속성이 `enable`이면(새 프로젝트 템플릿의 기본값) SDK가 다음 네임스페이스를 자동으로 가져온다.

```text
System
System.Collections.Generic
System.IO
System.Linq
System.Net.Http
System.Threading
System.Threading.Tasks
```

이것이 `Microsoft.NET.Sdk`(콘솔·클래스 라이브러리)의 목록이며, 프로젝트 SDK에 따라 여기에 더 붙는다.

| SDK / 속성 | 추가되는 네임스페이스(대표) |
|---|---|
| `Microsoft.NET.Sdk` | 위의 7개 |
| `Microsoft.NET.Sdk.Web` | `System.Net.Http.Json`, `Microsoft.AspNetCore.Builder`, `Microsoft.AspNetCore.Hosting`, `Microsoft.AspNetCore.Http`, `Microsoft.AspNetCore.Routing`, `Microsoft.Extensions.Configuration`, `Microsoft.Extensions.DependencyInjection`, `Microsoft.Extensions.Hosting`, `Microsoft.Extensions.Logging` |
| `Microsoft.NET.Sdk.Worker` | `Microsoft.Extensions.Configuration`, `Microsoft.Extensions.DependencyInjection`, `Microsoft.Extensions.Hosting`, `Microsoft.Extensions.Logging` |
| `<UseWindowsForms>true</UseWindowsForms>` | `System.Drawing`, `System.Windows.Forms` |

> **⚠️ 이 표를 외우지 말고 생성된 파일을 열어라**
>
> 위 목록은 SDK 버전에 따라 바뀔 수 있다. 확실한 방법은 하나뿐이다 — 빌드한 뒤 `obj/Debug/net8.0/<프로젝트명>.GlobalUsings.g.cs`를 여는 것이다. 거기에 **정확히 무엇이 들어갔는지**가 `global using` 목록으로 적혀 있다.
>
> ```csharp
> // <auto-generated/>
> global using global::System;
> global using global::System.Collections.Generic;
> // ... 나머지도 같은 모양
> ```
>
> 3.7절에서 이 파일을 이미 열어 봤다. 여기서 확인할 것은 **암시적 using이 언어 기능이 아니라는 사실**이다. SDK가 소스 파일을 하나 더 끼워 넣는 빌드 기능일 뿐이며, 컴파일러는 사람이 쓴 `global using`과 구분하지 못한다. `global::` 접두사가 붙어 있는 것도 눈여겨봐라 — 생성 코드는 사용자가 만든 이름과 절대 충돌하지 않아야 하므로 언제나 전역 한정자를 쓴다(12.6절).

### 켜고 끄고 다듬기

암시적 using은 `.csproj`에서 세밀하게 조절된다.

```xml
<PropertyGroup>
  <ImplicitUsings>disable</ImplicitUsings>   <!-- 전부 끈다 -->
</PropertyGroup>
```

전부 끄지 않고 **개별 조정**하려면 `Using` 항목을 쓴다.

```xml
<ItemGroup>
  <Using Remove="System.Net.Http" />                              <!-- 기본 목록에서 빼기 -->
  <Using Include="System.Text.Json" />                            <!-- 더하기 -->
  <Using Include="System.Math" Static="true" />                   <!-- using static -->
  <Using Include="System.Text.Json.JsonSerializer" Alias="Json" /><!-- 별칭 -->
</ItemGroup>
```

이 항목들은 그대로 `GlobalUsings.g.cs`에 반영된다. 즉 `.csproj`로 `global using`을 쓰는 셈이다.

> **💡 `.csproj`의 `Using` 항목 vs `GlobalUsings.cs` 파일 — 어느 쪽인가**
>
> 둘 다 결과는 같다. 솔루션의 모든 프로젝트에 공통으로 걸 것은 `Directory.Build.props`의 `<Using>` 항목(4.8절), 이 프로젝트만의 도메인 네임스페이스는 `GlobalUsings.cs` 파일이 읽기 좋다.
>
> 다만 **SDK 기본 목록에서 무언가를 빼는 것은 `.csproj`에서만 가능하다.** `global using`으로 들어온 것을 `.cs` 파일에서 취소할 방법은 없다.

### 함정 — 전역 import는 이름 충돌 위험을 프로젝트 전체로 키운다

`using`의 범위가 넓어진다는 것은, 12.2절에서 본 CS0104의 사정거리도 넓어진다는 뜻이다.

```csharp
// GlobalUsings.cs
global using MyCompany.Shapes;      // 여기에 Timer 클래스가 있다고 하자
global using System.Threading;      // 여기에도 Timer가 있다
```

이제 프로젝트의 **어느 파일에서든** `Timer`라고 쓰면 CS0104다. 그 파일이 도형과 아무 상관이 없어도 마찬가지다.

> **⚠️ 도메인 네임스페이스를 `global using`에 넣기 전에 두 번 생각하라**
>
> `System.Text.Json` 같은 프레임워크 네임스페이스는 이름이 얌전해서 전역으로 가져와도 대체로 안전하다. 반면 `MyCompany.Domain.Models` 같은 도메인 네임스페이스는 `Order`, `Task`, `Result`, `Error` 같은 흔한 이름을 잔뜩 담고 있어, 전역으로 가져오면 프로젝트가 커질수록 충돌이 쌓인다.
>
> 판단 기준은 하나다 — **거의 모든 파일에서 쓰는가.** 열 파일 중 아홉이면 전역으로, 절반 이하면 파일마다 쓰는 것이 낫다.

> **📌 `global using`은 어셈블리 경계를 넘지 않는다**
>
> 라이브러리 프로젝트에 `global using MyStuff;`를 써도, 그 라이브러리를 참조하는 애플리케이션에는 아무 영향이 없다. `global using`의 범위는 **컴파일 단위**, 즉 하나의 어셈블리를 만드는 컴파일 작업이다.
>
> 이것은 의도된 설계다. 라이브러리가 소비자의 이름 공간을 오염시킬 수 있다면 재앙일 것이다. 참조 어셈블리와 컴파일 단위의 관계는 4.4절과 52.1절에서 다룬다.

## 12.4 `using static`

### 문법

`using static`은 네임스페이스가 아니라 **타입**을 가져온다. 그러면 그 타입의 모든 접근 가능한 정적 멤버를 한정 없이 쓸 수 있다.

```csharp
using static System.Console;

WriteLine("Hello");     // Console.WriteLine 대신
```

가져오는 것은 정적 메서드만이 아니다. **정적 필드, 정적 프로퍼티, 상수, 중첩 타입**이 모두 들어온다.

```csharp
using static System.Math;

double r = 2.0;
double area = PI * Pow(r, 2);        // Math.PI, Math.Pow
double big  = Max(area, E);          // Math.Max, Math.E
```

### 열거형 멤버 가져오기

`using static`을 열거형 타입에 적용하면 그 멤버들이 한정 없이 들어온다.

```csharp
using static System.Windows.Visibility;

var textBox = new TextBox { Visibility = Hidden };    // XAML 스타일
```

`Visibility.Hidden` 대신 `Hidden`만 써도 된다. 열거형의 실체와 변환 규칙은 20.1절에서 다룬다.

> **📌 `using static`은 ※C# 6에서 들어왔다**
>
> 이 기능이 없던 시절 수치 코드는 `Math.`로 뒤덮여 읽기 어려웠다. 다른 언어(파이썬의 `from math import *`, C++의 `using namespace std`)에는 오래 있던 기능이며, C#은 뒤늦게, 그리고 **네임스페이스가 아니라 타입 단위로만** 받아들였다. 이 제한이 오히려 안전 장치가 되었다 — 한 번에 들어오는 이름이 타입 하나의 정적 멤버로 제한되기 때문이다.

### 확장 메서드는 특별하게 처리된다

`using static`으로 정적 클래스를 가져오면, 그 클래스에 정의된 **확장 메서드는 확장 형태로 사용 가능해진다.** 정적 메서드로 한정 없이 부를 수 있게 되는 것과는 별개다.

```csharp
using static System.Linq.Enumerable;

// Enumerable의 정적 메서드를 한정 없이
var nums = Range(1, 10);                  // Enumerable.Range(1, 10)

// 그리고 Enumerable의 확장 메서드는 확장 형태로도 쓸 수 있다
var evens = nums.Where(n => n % 2 == 0);
```

이 조합은 "LINQ의 특정 확장 메서드만 가져오고 싶다"는 요구에 답이 될 수 있다. `using System.Linq;`는 `Enumerable`, `Queryable`, `ParallelEnumerable` 등을 모두 열지만, `using static System.Linq.Enumerable;`은 딱 한 타입만 연다.

### 모호할 때

두 개의 `using static`이 같은 이름의 정적 멤버를 제공하면 어떻게 될까.

```csharp
using static System.Math;      // Max(int, int), Max(double, double), ...
using static MyMath;           // Max(int, int)

int m = Max(3, 5);             // 오류
```

**컴파일러는 문맥에서 올바른 타입을 추론할 만큼 똑똑하지 않다.** 오류를 낸다. 12.2절의 CS0104와 같은 원리다.

> **⚠️ `using static`의 모호함은 오버로드 해석보다 먼저 일어난다**
>
> 위 예에서 `MyMath.Max`가 `int` 오버로드만 갖고 있고 `Math.Max`가 `double` 오버로드도 갖고 있어도, 컴파일러가 "`int` 인수니까 `MyMath` 쪽이겠지"라고 골라 주지 않는다. 이름 조회 단계에서 이미 모호하기 때문이다. 오버로드 해석(13.2절)은 후보 집합이 정해진 **다음** 단계이며, 여기서는 후보 집합을 만드는 단계에서 실패한다.

### 언제 쓸 만한가

`using static`은 남용하면 코드를 읽기 어렵게 만든다. `WriteLine("hi")`만 보고 그것이 `Console.WriteLine`인지, `Debug.WriteLine`인지, 자기 팀의 `Log.WriteLine`인지 알 수 없기 때문이다. 파일 상단까지 스크롤해서 확인해야 한다.

| 판단 | 경우 | 이유 |
|---|---|---|
| 쓸 만하다 | `using static System.Math` / `System.MathF` | 수식이 수학 표기에 가까워진다. `PI`, `Sqrt`를 헷갈릴 사람은 없다 |
| 쓸 만하다 | `using static` + 열거형 | XAML·설정 코드에서 `Visibility.Hidden` 반복을 줄인다 |
| 쓸 만하다 | 테스트의 단언 헬퍼 (`using static Xunit.Assert;`) | 테스트 DSL을 만든다 |
| 쓸 만하다 | 팩터리 메서드·상수 모음 | `Circle(3)`, `Square(4)`처럼 읽힌다 |
| 쓸 만하다 | 작은 스크립트·샘플 | `WriteLine` 반복을 없앤다 |
| 피하라 | 대형 코드베이스의 일반 클래스 | 이름의 출처를 추적하기 어렵다 |
| 피하라 | 이름이 흔한 정적 클래스(`Log`, `Config`, `Helper`) | 충돌 폭탄이다 |
| 피하라 | `global using static`으로 도메인 헬퍼 열기 | 프로젝트 전체에서 이름 출처가 사라진다 |

> **💡 정적 멤버 이름이 스스로 말하지 않으면 `using static`을 쓰지 마라**
>
> 판단 기준은 간단하다. **한정자를 뗀 이름만 보고 무슨 일이 일어나는지 알 수 있는가?** `Sqrt(x)`와 `PI`는 안다 — 좋다. `Create(x)`, `Parse(s)`, `Empty`는 모른다(`string.Empty`인가 `Array.Empty`인가) — 나쁘다. 이 테스트를 통과하지 못하면 타입 이름을 남겨 두는 편이 언제나 낫다.

### 컴파일 결과

`using`과 마찬가지로 **IL에는 흔적이 없다.** `WriteLine("hi")`는 `call void [System.Console]System.Console::WriteLine(string)`이 되고, `Console.WriteLine("hi")`도 똑같은 IL이 된다. 성능 차이는 0이다.

## 12.5 타입·네임스페이스 별칭과 "모든 타입 별칭" ※C# 12

### 타입 별칭

네임스페이스를 통째로 가져오면 이름 충돌이 생길 수 있다. 필요한 타입만, 그것도 다른 이름으로 가져오는 방법이 **별칭**(alias)이다.

```csharp
using PropertyInfo2 = System.Reflection.PropertyInfo;

class Program { PropertyInfo2 p; }
```

`PropertyInfo2`는 새 타입이 아니다. **컴파일 시점에 `System.Reflection.PropertyInfo`로 치환되는 이름**일 뿐이다. `typeof(PropertyInfo2) == typeof(PropertyInfo)`는 `true`이고, IL에는 `PropertyInfo2`라는 문자열이 나타나지 않는다.

### 네임스페이스 별칭

네임스페이스 전체에 짧은 이름을 붙일 수도 있다. 실무에서 더 흔히 쓰이는 형태다.

```csharp
using R = System.Reflection;

class Program { R.PropertyInfo p; }
```

12.2절의 충돌 상황을 이 방식으로 푼다.

```csharp
using ThreeD = CustomNamespaces.My3DShapes;
using Flat   = CustomNamespaces.MyShapes;

ThreeD.Hexagon h3 = new ThreeD.Hexagon();
Flat.Hexagon   h2 = new Flat.Hexagon();
```

두 `Hexagon`이 코드에서 시각적으로 구분된다. 완전 정규화보다 짧고, `using` 두 개보다 안전하다.

> **📌 별칭 이름은 파일 밖으로 나가지 않는다**
>
> `using X = ...`로 만든 별칭은 그 **파일 안에서만** 유효하다(네임스페이스 안에 썼다면 그 네임스페이스 안에서만). 다른 파일에서 `X`를 쓰려면 그 파일에도 같은 별칭 선언이 필요하다. 프로젝트 전체에 걸고 싶으면 `global using X = ...`를 쓴다(12.3절).
>
> 이것은 별칭이 **타입 시스템의 일부가 아니기** 때문이다. 별칭은 컴파일러의 이름 조회 표에 든 항목이지 메타데이터에 기록되는 무언가가 아니다. C의 `typedef`와 같은 층위다.

> **⚠️ 별칭 남용은 코드베이스를 낯설게 만든다**
>
> 별칭은 강력한 만큼 위험하다. 팀의 다른 사람이 `The3DHexagon`이라는 타입을 코드베이스에서 검색하면 **아무것도 나오지 않는다.** 그런 타입은 실제로 존재하지 않기 때문이다. 별칭 선언 한 줄을 못 보면 그 타입이 어디 있는지 영영 못 찾는다.
>
> 별칭은 두 경우에만 써라 — **진짜 충돌을 풀 때**, 그리고 **길고 반복되는 제네릭 타입을 줄일 때**(`using Cache = ConcurrentDictionary<string, List<int>>;`). "타자가 귀찮아서"는 이유가 되지 않는다.

### 모든 타입 별칭 ※C# 12

C# 11까지 별칭의 대상은 **명명된 타입**과 네임스페이스뿐이었다. 배열, 튜플, 포인터처럼 이름이 없는 타입에는 별칭을 붙일 수 없었다.

※C# 12부터는 **거의 모든 타입**에 별칭을 붙일 수 있다.

```csharp
using NumberList = double[];

NumberList numbers = { 2.5, 3.5 };
```

가능해진 것들을 정리하면 다음과 같다.

| 별칭 대상 | 예시 | C# 11 이하 | C# 12 |
|---|---|---|---|
| 명명된 타입 | `using P = System.Reflection.PropertyInfo;` | 가능 | 가능 |
| 네임스페이스 | `using R = System.Reflection;` | 가능 | 가능 |
| 닫힌 제네릭 | `using Dict = Dictionary<string, int>;` | 가능 | 가능 |
| 배열 | `using Buffer = byte[];` | 불가 | **가능** |
| 다차원 배열 | `using Grid = int[,];` | 불가 | **가능** |
| 튜플 | `using Point = (int X, int Y);` | 불가 | **가능** |
| 널 가능 **값** 타입 | `using MaybeInt = int?;` | 불가 | **가능** |
| 포인터 | `using unsafe PInt = int*;` | 불가 | **가능** (`unsafe` 필요) |
| 열린 제네릭 | `using L = List<>;` | 불가 | 불가 |
| 널 가능 **참조** 타입 | `using S = string?;` | 불가 | **불가** |

마지막 두 줄이 중요하다.

> **⚠️ 별칭에 `string?`은 못 쓴다 — `int?`는 된다**
>
> 이 비대칭에는 이유가 있다. `int?`는 `Nullable<int>`라는 **실재하는 구조체 타입**이지만(21.1절), `string?`은 타입이 아니라 **컴파일러가 붙이는 주석**이다. 런타임에 `string`과 `string?`은 완전히 같은 타입이고, 차이는 컴파일러의 흐름 분석에만 존재한다(21.6절).
>
> 별칭은 타입을 가리키는 이름이므로, 타입이 아닌 것에는 붙을 수 없다. `using S = string?;`은 컴파일 오류다. 대신 `using S = string;`을 만들어 두고 쓰는 자리에서 `S?`를 쓰면 된다.

포인터 별칭에는 `unsafe` 키워드가 `using` 뒤에 붙는다. 이 문법 자체가 ※C# 12에서 새로 생긴 것이다.

```csharp
using unsafe ByteP = byte*;      // .csproj에 <AllowUnsafeBlocks>true</AllowUnsafeBlocks> 필요
```

튜플 별칭은 익명 튜플에 이름을 주는 가장 가벼운 방법이다.

```csharp
using Point = (int X, int Y);

Point Move(Point p, int dx, int dy) => (p.X + dx, p.Y + dy);
```

`Point`는 별개의 타입이 아니라 `ValueTuple<int, int>`의 다른 이름이므로, 다른 곳에서 `(int, int)`를 쓰는 코드와 자유롭게 호환된다. 이것이 장점이자 함정이며, 튜플 별칭의 세부는 77.4절에서 다룬다.

> **💡 "모든 타입 별칭"이 실제로 유용한 자리**
>
> 이 기능이 가장 빛나는 곳은 **의미 없는 튜플과 배열이 시그니처에 반복해서 나타나는 코드**다.
>
> ```csharp
> // 전 — (double Lat, double Lon)이 시그니처마다 반복된다
> Dictionary<string, (double Lat, double Lon)> LoadCities();
> (double Lat, double Lon) Center((double Lat, double Lon)[] pts);
>
> // 후
> using GeoPoint = (double Lat, double Lon);
> Dictionary<string, GeoPoint> LoadCities();
> GeoPoint Center(GeoPoint[] pts);
> ```
>
> 다만 이 정도로 반복된다면 애초에 `readonly record struct GeoPoint(double Lat, double Lon)`을 정의하는 편이 나은 경우가 많다(19장). 별칭은 **타입을 만들 만큼은 아닌데 반복이 거슬리는** 중간 지대를 위한 도구다.

### 별칭과 조건부 컴파일의 조합

별칭이 정적 플래그 변수로는 흉내 낼 수 없는 일을 하는 대표적인 자리가 여기다.

```csharp
using TestType =
#if V2
    MyCompany.Widgets.GadgetV2;
#else
    MyCompany.Widgets.Gadget;
#endif
```

심볼 하나로 프로젝트 전체가 참조하는 타입을 바꿔치기할 수 있다. 이 기법의 함의는 12.8절과 73.1절에서 다룬다.

### `global::` — 전역 네임스페이스 한정자

이름 숨김(12.2절)은 완전 정규화된 이름으로도 못 푸는 경우가 있다.

```csharp
namespace N
{
    class A
    {
        static void Main() => new A.B();    // 어느 B인가?
        public class B { }                  // 중첩 타입
    }
}

namespace A
{
    class B { }
}
```

`A.B`는 중첩 클래스 `N.A.B`일 수도 있고 네임스페이스 `A`의 클래스 `B`일 수도 있다. **컴파일러는 언제나 현재 네임스페이스의 식별자에 더 높은 우선순위를 준다** — 이 경우 중첩된 `B`가 이긴다. `A.B`라고 아무리 정확히 적어도 네임스페이스 `A`의 `B`에는 닿을 수 없다.

이럴 때 쓰는 것이 **네임스페이스 별칭 한정자** `::`다. `::`의 왼쪽에 올 수 있는 것은 딱 두 가지다.

1. `global` — 모든 네임스페이스의 뿌리인 전역 네임스페이스 (문맥 키워드)
2. `extern alias`로 정의한 별칭 (12.6절)

```csharp
namespace N
{
    class A
    {
        static void Main()
        {
            System.Console.WriteLine (new A.B());            // N.A.B
            System.Console.WriteLine (new global::A.B());    // A.B
        }

        public class B { }
    }
}

namespace A
{
    class B { }
}
```

`global::A.B`는 "전역 네임스페이스에서 시작해서 `A`, 그 안의 `B`"라는 뜻이므로 중첩 타입에 가려지지 않는다.

> **📌 생성 코드가 `global::`을 도배하는 이유**
>
> 소스 생성기, `GlobalUsings.g.cs`, `*.Designer.cs`, EF Core 마이그레이션 같은 자동 생성 코드는 타입 이름마다 `global::`을 붙인다.
>
> ```csharp
> global::System.Collections.Generic.List<global::MyApp.Order> orders;
> ```
>
> 읽기에는 끔찍하지만 이유가 있다. 생성기는 **사용자가 어떤 이름을 쓸지 모른다.** 사용자가 `MyApp` 안에 `System`이라는 클래스를 만들어 두었다면 `System.Collections...`가 그것에 가려질 수 있다. `global::`을 붙이면 사용자가 무슨 짓을 해도 안전하다. 자동 생성 코드는 사람이 읽을 것을 전제하지 않으므로 안전을 택한 것이다.
>
> 소스 생성기를 직접 만든다면 이 관례를 따라야 한다(13.14절).

> **⚠️ `.`과 `::`은 바꿔 쓸 수 없다**
>
> `global.A.B`는 오류다. `global`은 타입도 네임스페이스도 아니므로 점 연산자의 피연산자가 될 수 없다. `::` 왼쪽에만 올 수 있는 문맥 키워드다.
>
> 반대로 `global`이라는 이름의 클래스나 변수를 만드는 것은 (권장되지 않지만) 가능하다. 문맥 키워드이기 때문이다. 그런 코드가 있으면 `global::`의 해석이 헷갈리기 시작하므로 절대 하지 마라.

## 12.6 `extern alias`와 이름 충돌 해결

### 문제 — 완전 정규화된 이름조차 같을 때

지금까지 본 충돌은 전부 **짧은 이름**의 충돌이었고, 완전 정규화된 이름을 쓰면 풀렸다. 그런데 **완전 정규화된 이름까지 같은** 두 타입이 있을 수 있다. 조건은 하나다 — 두 타입이 **서로 다른 어셈블리**에 있어야 한다.

라이브러리 1, `Widgets1.dll`로 컴파일된다.

```csharp
namespace Widgets
{
    public class Widget { }
}
```

라이브러리 2, `Widgets2.dll`로 컴파일된다.

```csharp
namespace Widgets
{
    public class Widget { }
}
```

두 DLL을 모두 참조하는 애플리케이션.

```csharp
using Widgets;

Widget w = new Widget();     // 오류 — Widget이 모호하다
```

`Widgets.Widget`이라고 완전 정규화해도 소용없다. 두 어셈블리의 타입 이름이 글자 하나까지 같기 때문이다. C#의 타입 이름 문법에는 어셈블리를 지정할 자리가 없다.

### 해결 — 어셈블리에 별칭을 부여한다

**외부 별칭**(extern alias)은 이 문제를 위해 존재한다. 두 단계로 이뤄진다.

**1단계.** `.csproj`에서 각 참조에 고유한 별칭을 준다.

```xml
<ItemGroup>
  <Reference Include="Widgets1">
    <Aliases>W1</Aliases>
  </Reference>
  <Reference Include="Widgets2">
    <Aliases>W2</Aliases>
  </Reference>
</ItemGroup>
```

프로젝트 참조나 NuGet 패키지 참조에도 같은 메타데이터를 붙일 수 있다 — `<ProjectReference Include="..\Widgets1\Widgets1.csproj" Aliases="W1" />` 형태다.

**2단계.** 소스 파일 최상단에 `extern alias` 지시문을 쓴다.

```csharp
extern alias W1;
extern alias W2;

W1.Widgets.Widget  w1 = new W1.Widgets.Widget();      // 점 표기
W2::Widgets.Widget w2 = new W2::Widgets.Widget();     // :: 한정자 — 더 명시적이다
```

`extern alias`가 하는 일은 이렇게 그릴 수 있다.

```text
기본 상태 — 모든 참조 어셈블리가 하나의 전역 네임스페이스로 합쳐진다

   Widgets1.dll ─┐
                 ├──▶  global::  ──▶  Widgets.Widget  ◀── 충돌!
   Widgets2.dll ─┘

extern alias 적용 — 어셈블리마다 별도의 루트가 생긴다

   Widgets1.dll ──▶  W1::  ──▶  Widgets.Widget
   Widgets2.dll ──▶  W2::  ──▶  Widgets.Widget
```

즉 `extern alias`는 **어셈블리마다 별도의 전역 네임스페이스 루트를 만드는 장치**다. 별칭을 준 어셈블리의 타입은 `global::`에서 더 이상 보이지 않고, 오직 그 별칭을 통해서만 접근된다.

> **⚠️ `Aliases`를 지정하면 `global::`에서 사라진다**
>
> `<Aliases>W1</Aliases>`를 붙이는 순간, `Widgets1.dll`의 타입은 `using Widgets;`로도 `Widgets.Widget`으로도 접근할 수 없게 된다. 그 어셈블리를 쓰는 **모든 파일**에 `extern alias W1;`을 써야 한다.
>
> 그래서 실무에서는 **두 어셈블리 중 하나에만** 별칭을 주는 방법을 쓰기도 한다. `Widgets1`은 평소대로 `global::`에서 보이게 두고, 드물게 필요한 `Widgets2`에만 `Aliases="W2"`를 붙여 그것을 쓰는 파일에서만 `extern alias W2;`를 선언하는 식이다. 수정해야 할 파일 수가 최소가 된다.
>
> 별칭 여러 개를 세미콜론으로 붙여 `<Aliases>W1;global</Aliases>`처럼 쓰면 전역에서도 보이고 별칭으로도 보이게 할 수 있다.

> **📌 `extern alias`는 `using`보다도 앞에 온다**
>
> 파일 안에서 `extern alias` 지시문은 **어떤 `using`보다도 앞**, 심지어 `global using`보다도 앞에 와야 한다. 파일에서 가장 먼저 나올 수 있는 것은 주석과 `#` 전처리기 지시문뿐이다.
>
> 이유는 의존 관계다. `global using W1::Something;`처럼 `using`이 별칭을 참조할 수 있으므로, 별칭이 먼저 선언되어야 한다.

### 실전에서 `extern alias`가 필요해지는 상황

이 기능은 드물게 쓰인다. 원래 그렇게 설계되었다. 그래도 다음 상황에서는 다른 방법이 없다.

| 상황 | 설명 |
|---|---|
| 같은 라이브러리의 두 버전 동시 사용 | 마이그레이션 중 v1 어댑터와 v2 어댑터를 나란히 두어야 할 때 |
| 벤더가 다른데 이름이 겹치는 SDK | 두 결제 게이트웨이가 모두 `Payments.Transaction`을 정의한 경우 |
| 병합 산출물(ILMerge·ILRepack)과 원본 패키지의 공존 | 이름이 그대로 남는다 |
| 참조 어셈블리와 구현 어셈블리를 동시에 참조 | 도구 개발에서 드물게 발생 (4.4절) |

> **💡 해결 순서 — 위에서부터 시도하라**
>
> 이름 충돌을 만나면 다음 순서로 해결책을 찾아라. 아래로 갈수록 비용이 크다.
>
> | 순위 | 방법 | 비용 |
> |---|---|---|
> | 1 | **자기 타입의 이름을 바꾼다** | 리팩터링 한 번. 이후 영원히 무료 |
> | 2 | 문제 되는 `using`을 지우고 그쪽만 완전 정규화 | 몇 줄이 길어진다 |
> | 3 | 네임스페이스 별칭(`using X = ...`) | 파일마다 선언이 필요 |
> | 4 | `using`을 네임스페이스 블록 안으로 국지화 | 파일 구조 제약 |
> | 5 | `extern alias` | `.csproj` + 모든 사용처 수정 |
>
> **1번이 압도적으로 낫다.** 자기 코드가 `System.Timers.Timer`와 충돌하는 `Timer`를 갖고 있다면, 그것을 `PollingTimer`나 `JobScheduler`로 바꾸는 데 드는 30분이 앞으로 5년간의 혼란을 없앤다. `extern alias`는 **자기 코드를 고칠 수 없을 때만** 쓰는 마지막 수단이다.

### 중첩 네임스페이스 이름 충돌 — 실전 사례

이름 충돌은 외부 라이브러리 때문만 생기는 것이 아니다. 자기 코드 안에서 훨씬 자주 생긴다.

**사례 1 — 회사 이름과 같은 최상위 네임스페이스**

`namespace Contoso.Billing;` 안에서 `Contoso.Reporting.Report`를 참조하는 것은 잘 동작한다. 그런데 누군가 `Contoso.Billing` 안에 `Contoso`라는 클래스를 만들면 무너진다.

```csharp
namespace Contoso.Billing;

class Contoso { }                        // 회사를 나타내는 도메인 클래스라 치자

class Invoice
{
    Contoso.Reporting.Report r;          // 오류 — Contoso는 이제 클래스다
    global::Contoso.Reporting.Report r2; // 이렇게 해야 한다
}
```

이름 조회는 타입을 먼저 찾고 네임스페이스는 나중에 찾는다(12.2절). 클래스 `Contoso`가 네임스페이스 `Contoso`를 완전히 가려 버린다.

**사례 2 — 자기 프로젝트에 `System`이라는 네임스페이스 조각을 만든 경우**

```csharp
namespace MyApp.System.Diagnostics;      // 절대 하지 마라

class Tracer { }
```

`MyApp` 안의 어떤 파일에서 `System.Console`을 쓰려 하면, 이름 조회가 바깥으로 올라가다가 `MyApp.System`을 먼저 만나고 거기서 멈춘다. `System.Console`은 `MyApp.System.Console`로 해석되고, 그런 것은 없으므로 오류다. 전부 `global::System.Console`로 써야 한다.

**사례 3 — 서비스마다 같은 이름의 `Models`**

`using Orders.Models;`와 `using Shipping.Models;`가 각각 `Customer`를 갖고 있으면 DTO 매핑 코드에서 반드시 CS0104가 난다. 여기서 `extern alias`는 필요 없다 — 네임스페이스 별칭으로 충분하다.

```csharp
using OrderModels = Orders.Models;
using ShipModels  = Shipping.Models;

OrderModels.Customer src = ...;
ShipModels.Customer  dst = Map(src);
```

> **⚠️ 네임스페이스 이름에 클래스 이름과 같은 단어를 쓰지 마라**
>
> .NET 프레임워크 설계 지침의 오래된 규칙이다. `Contoso.Order` 네임스페이스와 `Order` 클래스가 함께 있으면 반드시 사고가 난다. 네임스페이스는 **복수형이나 추상적인 그룹 이름**(`Orders`, `Ordering`, `Sales`), 타입은 **단수 명사**(`Order`)로 짓는 관례가 여기서 나왔다.
>
> BCL 자체가 이 규칙을 지킨다 — `System.Collections` 네임스페이스에 `Collections`라는 타입은 없고, `System.Text`에 `Text`라는 타입은 없다.

## 12.7 전처리기 지시문 — `#if`, `#define`, `#region`, `#pragma`, `#nullable`, `#line`

### C#의 전처리기는 C/C++의 전처리기가 아니다

이 절을 C나 C++ 경험을 갖고 읽는다면 먼저 지워야 할 것이 있다. 이름이 같고 문법이 비슷해 보이지만, **C#에는 전처리기라는 별도의 단계가 존재하지 않는다.**

| | C/C++ 전처리기 | C# "전처리기" |
|---|---|---|
| 별도 실행 단계 | 있다 (`cpp`가 먼저 돌아 `.i` 파일을 만든다) | 없다. 컴파일러의 어휘 분석 단계에서 함께 처리된다 |
| 매크로 | 있다 (`#define MAX(a,b) ((a)>(b)?(a):(b))`) | **없다** |
| 텍스트 치환 | 한다 | **하지 않는다** |
| 파일 포함 | `#include` | **없다** |
| 조건부 컴파일 | 있다 | 있다 |
| 심볼의 값 | 임의의 토큰 열을 가질 수 있다 | 값이 없다. 정의됨/안 됨 두 상태뿐 |
| 심볼 정의 위치 | 파일 어디든 | 파일 **최상단**만 |

C#의 `#define`은 이름 하나를 "정의됨" 상태로 만드는 것이 전부다. `#define DEBUG_LOG`는 되지만 `#define MAX 100`은 오류다 — C#에는 값이 있는 심볼이 없다.

> **⚠️ C#에 매크로가 없는 것은 결함이 아니라 설계다**
>
> C의 매크로는 디버거가 볼 수 없고, 타입 검사를 받지 않으며, 이름 충돌을 막을 수 없고, 인수를 여러 번 평가하는 함정을 만든다(`MAX(i++, j)`). C#은 이 문제 전부를 언어 기능으로 대체했다.
>
> | C 매크로의 용도 | C#의 대안 |
> |---|---|
> | 상수 정의 | `const` 필드 (10.11절) |
> | 짧은 인라인 함수 | 일반 메서드 + JIT 인라이닝 (55장) |
> | 타입 이름 줄이기 | `using` 별칭 (12.5절) |
> | 조건부 코드 | `#if` / `[Conditional]` (12.8절) |
> | 문자열화(`#x`) | `nameof` (13.15절), `CallerArgumentExpression` (20.11절) |
> | 파일 포함 | 어셈블리 참조 + `using` |
>
> 대안이 전부 **타입 검사를 받고 디버거에서 보인다**는 점이 핵심이다. C#에서 매크로를 흉내 내고 싶어질 때는 거의 항상 언어가 제공하는 다른 답이 있다.

그렇다면 "전처리기"라는 이름은 왜 남았는가. 두 가지 때문이다. 첫째, 문법이 C에서 왔다. 둘째, **논리적으로는 본 컴파일 이전에 처리된다.** `#if`로 배제된 코드는 파싱조차 되지 않고, 결과적으로 어셈블리에 아예 존재하지 않는다.

### 전처리기 지시문 전체 목록

| 지시문 | 하는 일 |
|---|---|
| `#define 심볼` | 심볼을 정의한다 |
| `#undef 심볼` | 심볼 정의를 해제한다 |
| `#if 심볼 [연산자 심볼2]...` | 심볼을 검사한다. 연산자는 `==`, `!=`, `&&`, `\|\|`이며 `#else`, `#elif`, `#endif`가 뒤따른다 |
| `#else` | 뒤따르는 `#endif`까지의 코드를 실행(컴파일)한다 |
| `#elif 심볼 [연산자 심볼2]` | `#else` 분기와 `#if` 검사를 합친다 |
| `#endif` | 조건부 지시문을 끝낸다 |
| `#warning 텍스트` | 컴파일러 출력에 나타날 경고 텍스트 |
| `#error 텍스트` | 컴파일러 출력에 나타날 오류 텍스트 |
| `#error version` | 컴파일러 버전을 보고하고 종료한다 |
| `#pragma warning [disable \| restore]` | 컴파일러 경고를 끄거나 복원한다 |
| `#line [번호 ["파일"] \| hidden]` | 번호는 소스 코드의 줄 번호(※C# 10부터 열도 지정 가능), 파일은 컴파일러 출력에 나타날 파일명, `hidden`은 다음 `#line` 지시문까지 디버거가 건너뛰게 한다 |
| `#region 이름` | 코드 접기 영역의 시작 |
| `#endregion` | 접기 영역의 끝 |
| `#nullable 옵션` | 널 허용 컨텍스트를 제어한다 (21.6절) |

모든 지시문에는 공통 규칙이 있다.

- **반드시 줄 전체를 차지한다.** 앞에 공백은 올 수 있지만 다른 코드는 올 수 없다.
- **줄 끝에 세미콜론이 없다.**
- 뒤에 한 줄 주석(`//`)은 올 수 있지만 여러 줄 주석(`/* */`)은 올 수 없다.

### `#define`, `#undef`, `#if`

가장 흔하게 쓰이는 것이 조건부 지시문이다.

```csharp
#define DEBUG

class MyClass
{
    int x;

    void Foo()
    {
#if DEBUG
        Console.WriteLine ("Testing: x = {0}", x);
#endif
    }
    // ...
}
```

`DEBUG` 심볼이 없으면 `Console.WriteLine` 문은 **컴파일되지 않는다.** 주석 처리된 것과 결과가 같다.

`#define`과 `#undef`는 **파일 최상단**, `using`보다도 앞에만 올 수 있고 효력은 **그 파일 안으로 제한된다.** `using System;` 뒤에 `#define`을 쓰면 CS1032다.

`#if`와 `#elif`에서는 `||`, `&&`, `!` 연산자로 여러 심볼을 조합할 수 있고, 괄호로 묶을 수도 있다.

```csharp
#if TESTMODE && !DEBUG
    // TESTMODE는 정의되어 있고 DEBUG는 정의되어 있지 않을 때만 컴파일된다
#endif

#if (NET8_0_OR_GREATER || NETSTANDARD2_1) && !BROWSER
    // ...
#endif
```

`==`와 `!=`는 `true`/`false` 리터럴과의 비교에만 쓸 수 있다. `#if DEBUG == true`는 `#if DEBUG`와 같다.

> **⚠️ 전처리기 심볼은 변수가 아니다**
>
> `#if`가 평가하는 것은 일반적인 C# 식이 **아니다.** 여기 등장하는 이름은 정적 필드든 지역 변수든 상수든 **어떤 변수와도 아무 연관이 없다.**
>
> ```csharp
> const bool DEBUG = false;
>
> #if DEBUG                 // 이 DEBUG는 위의 const와 완전히 무관하다
>     Console.WriteLine("이 줄은 .csproj가 DEBUG를 정의했으면 컴파일된다");
> #endif
> ```
>
> 같은 이름의 `bool` 필드가 있어도 무관하다. 심볼에는 값이 없고 "정의되었나/아닌가" 두 상태만 있다. 반대로 `#if` 안에서 변수를 쓸 수도 없다 — `#if x > 5`는 오류다.

> **⚠️ 배제된 코드는 문법 검사를 받지 않는다**
>
> `#if false` 블록 안의 코드는 파싱되지 않으므로, 문법이 완전히 망가져 있어도 컴파일이 성공한다.
>
> ```csharp
> #if NEVER_DEFINED
>     이건 C# 코드가 아니지만 컴파일은 통과한다 @#$%
> #endif
> ```
>
> 이것이 조건부 컴파일의 가장 위험한 성질이다. **어느 심볼 조합에서만 컴파일되고 다른 조합에서는 깨지는 코드**를 만들기 쉽다. CI가 Debug 구성만 빌드한다면 `#if !DEBUG` 블록 안의 오타는 Release 빌드 때까지 발견되지 않는다.
>
> 단, 지시문 자체의 짝(`#if`/`#endif`)은 배제된 영역 안에서도 검사된다. 배제된 블록 안에 짝 없는 `#if`가 있으면 오류다.
>
> **대응** — 멀티 타깃 프로젝트나 조건부 컴파일이 많은 프로젝트는 CI에서 **모든 구성과 모든 TFM을 빌드**해야 한다. `dotnet build -c Release`와 `dotnet build -c Debug`를 둘 다 돌리는 것이 최소한이다.

### 프로젝트 수준에서 심볼 정의하기

어셈블리 전체에 적용할 심볼은 `.csproj`에 정의한다.

```xml
<PropertyGroup>
  <DefineConstants>$(DefineConstants);TESTMODE;ANOTHERSYMBOL</DefineConstants>
</PropertyGroup>
```

`$(DefineConstants);` 접두사를 반드시 붙여라. MSBuild 속성은 덮어쓰기 방식이므로 이것을 빠뜨리면 SDK가 넣어 둔 `DEBUG`와 `TRACE`가 사라진다. 그 결과 `#if DEBUG` 블록이 통째로 사라지고 빌드는 성공한다 — 4.1절에서 다룬 조용한 사고의 전형이다.

구성별로 다른 심볼을 정의하려면 `<PropertyGroup Condition="'$(Configuration)' == 'Release'">` 안에 넣으면 된다.

프로젝트 수준에서 정의된 심볼을 **특정 파일에서만** 무효화하려면 그 파일 최상단에 `#undef TESTMODE`를 쓴다.

### SDK가 자동으로 정의하는 심볼

`.csproj`에 아무것도 쓰지 않아도 이미 여러 심볼이 정의되어 있다. 이것을 알아야 멀티 타깃 라이브러리를 쓸 수 있다.

| 심볼 | 언제 정의되는가 |
|---|---|
| `DEBUG` | `Configuration`이 `Debug`일 때 |
| `TRACE` | Debug·Release 양쪽 기본값 |
| `NET` | .NET Core 계열(.NET 5 이상)을 대상으로 할 때 |
| `NET8_0` | `TargetFramework`가 정확히 `net8.0`일 때 |
| `NET8_0_OR_GREATER` | `net8.0` 이상을 대상으로 할 때 (`net9.0`에서도 정의된다) |
| `NET6_0_OR_GREATER`, `NET7_0_OR_GREATER`, ... | 위와 같은 규칙으로 하위 버전 것들이 **모두** 정의된다 |
| `NETSTANDARD2_0`, `NETSTANDARD2_0_OR_GREATER` | .NET Standard를 대상으로 할 때 (4.3절) |
| `NETFRAMEWORK`, `NET48`, `NET48_OR_GREATER` | .NET Framework를 대상으로 할 때 |
| `WINDOWS`, `WINDOWS10_0_19041_0` 등 | TFM에 플랫폼이 붙었을 때 (`net8.0-windows10.0.19041.0`) |
| `ANDROID`, `IOS`, `MACCATALYST`, `BROWSER` | 해당 플랫폼 TFM일 때 |

핵심은 **`_OR_GREATER` 심볼이 누적된다**는 점이다. `net8.0`을 대상으로 빌드하면 `NET5_0_OR_GREATER`부터 `NET8_0_OR_GREATER`까지가 전부 정의된다. 그래서 "이 API는 .NET 6 이상에 있다"를 표현할 때 `#if NET6_0_OR_GREATER` 한 줄이면 되고, .NET 9가 나와도 코드를 고칠 필요가 없다.

```csharp
public static string Describe(ReadOnlySpan<char> s)
{
#if NET8_0_OR_GREATER
    return string.Concat("len=", s.Length.ToString());
#else
    return "len=" + s.Length.ToString();
#endif
}
```

> **💡 심볼 목록을 확인하는 가장 빠른 방법**
>
> 어떤 심볼이 정의되어 있는지 확신이 안 서면 `#if NET8_0_OR_GREATER` / `#error 정의됨` / `#endif`를 잠깐 넣고 빌드해 보면 된다. 더 정석적인 방법은 `dotnet build -v:diagnostic`의 출력에서 컴파일러 명령줄의 `/define:` 인수를 찾는 것이다. 거기에 최종 목록이 그대로 있다.

> **⚠️ `TRACE`는 Release에서도 정의되어 있다**
>
> `DEBUG`는 Debug 구성에서만 정의되지만 `TRACE`는 **양쪽 모두에서** 정의된다. 이것이 `Debug.WriteLine`은 Release 빌드에서 사라지지만 `Trace.WriteLine`은 남는 이유다(73.2절). 릴리스 바이너리에서 진단 출력을 완전히 없애고 싶다면 `<DefineTrace>false</DefineTrace>`로 꺼야 한다.

### `#error`와 `#warning`

`#error`와 `#warning`은 잘못된 심볼 조합이 조용히 넘어가는 것을 막는다.

```csharp
#if TESTMODE && RELEASE_BUILD
#error TESTMODE와 RELEASE_BUILD를 동시에 정의할 수 없다
#endif

#if !NET8_0_OR_GREATER
#warning 이 라이브러리는 .NET 8 이상에서 최적 성능을 낸다
#endif
```

`#error`는 빌드를 실패시키고, `#warning`은 경고만 낸다. `#error version`이라는 특수 형태도 있는데, 이것은 컴파일러 버전과 언어 버전을 오류 메시지로 보고하고 종료한다 — 버그 리포트를 쓸 때 쓴다.

> **💡 조건부 컴파일에는 반드시 `#else #error`를 달아라**
>
> 이 관용구는 조건부 컴파일의 가장 흔한 사고를 막아 준다.
>
> ```csharp
> #if NET8_0_OR_GREATER
>     // .NET 8 경로
> #elif NETSTANDARD2_0
>     // .NET Standard 경로
> #else
> #error 지원하지 않는 대상 프레임워크다. TargetFrameworks를 확인하라
> #endif
> ```
>
> `#else` 없이 두면, 나중에 누군가 `TargetFrameworks`에 새 TFM을 추가했을 때 **아무 경로도 컴파일되지 않은 채로 빌드가 성공한다.** 메서드 본문이 통째로 비어 버려도 반환 타입이 `void`면 오류조차 나지 않는다.

### `#region`과 `#endregion`

`#region`은 IDE에게 "여기서부터 여기까지를 접을 수 있게 하라"고 알린다.

```csharp
public class Order
{
    #region 필드
    private int _id;
    private DateTime _created;
    #endregion

    #region IComparable<Order> 구현
    public int CompareTo(Order? other) => _id.CompareTo(other?._id ?? 0);
    #endregion
}
```

**컴파일에는 아무 영향이 없다.** 컴파일러는 `#region`/`#endregion`을 읽고 짝이 맞는지만 확인한 뒤 버린다. IL에도, 메타데이터에도, PDB에도 남지 않는다.

`#region`은 중첩할 수 있고, 짝만 맞으면 클래스 경계나 메서드 경계를 가로질러도 된다.

> **⚠️ `#region`은 대개 나쁜 코드의 증상이다**
>
> 이것은 저자의 판단이지만 널리 공유되는 판단이다. `#region`을 접어야만 읽을 수 있는 클래스는 **너무 큰 클래스**다. 리전으로 접는 것은 문제를 숨기는 것이지 푸는 것이 아니다.
>
> 특히 나쁜 패턴이 셋 있다 — 멤버 종류로 나누는 `#region 필드`/`#region 메서드`(IDE의 개요 창이 이미 해 준다), 접힌 리전 안에 숨겨진 200줄짜리 메서드, 그리고 내용과 어긋난 채 방치된 리전 이름(컴파일러가 검사하지 않으므로 언제든 거짓말이 된다).
>
> 그래도 정당한 용도가 둘 있다. **자동 생성 코드 구획**(디자이너 코드를 사람 코드와 분리)과 **인터페이스 구현 구획**(`#region IDisposable`)이다. 후자도 부분 클래스나 명시적 구현으로 대체할 수 있다.

### `#pragma warning`

컴파일러 경고는 버그를 잡는 데 매우 유용하다. 그런데 **틀린 경고**가 섞이면 그 가치가 무너진다. 큰 애플리케이션에서는 신호 대 잡음비를 유지하는 것이 결정적이다 — 진짜 경고가 눈에 띄려면 가짜 경고가 없어야 한다.

`#pragma warning`은 경고를 **선택적으로** 억제한다.

```csharp
public class Foo
{
    static void Main() { }

#pragma warning disable 414
    static string Message = "Hello";
#pragma warning restore 414
}
```

여기서는 "필드 `Message`가 할당되었지만 사용되지 않았다"는 경고 414를 껐다. 숫자 대신 `CS0414`처럼 전체 ID를 써도 된다. 숫자만 쓰는 것은 옛 관례이고, 최근에는 ID를 쓰는 편이 읽기 좋다.

```csharp
#pragma warning disable CS0414    // 할당되었으나 사용되지 않음
#pragma warning restore CS0414
```

여러 개를 쉼표로 나열할 수 있고(`#pragma warning disable CS0414, CS0169, IDE0051`), 번호를 생략하면 **모든** 경고에 적용된다 — 거의 언제나 잘못된 선택이다. `restore`는 억제를 되돌리는데, 되돌아가는 곳은 **프로젝트 설정**이지 "이전 `#pragma`"가 아니다.

> **⚠️ `disable`만 쓰고 `restore`를 안 쓰면 파일 끝까지 꺼진다**
>
> `#pragma warning disable`의 범위는 파일이다. `restore`를 빠뜨리면 그 아래 코드 전부에서 그 경고가 사라진다. 나중에 그 파일에 추가되는 코드에도 적용된다.
>
> 반드시 **최소 범위**로 감싸라.
>
> ```csharp
> #pragma warning disable CS0618      // 사용되지 않는 API에 대한 경고
>     legacyApi.OldMethod();          // 정확히 이 한 줄만
> #pragma warning restore CS0618
> ```
>
> 그리고 억제할 때는 **왜 억제하는지 주석을 반드시 남겨라.** 6개월 뒤에 이 `#pragma`를 지워도 되는지 판단할 근거가 그것뿐이다.

경고를 프로젝트 전체에서 끄고 싶다면 `.csproj`를 쓴다.

```xml
<PropertyGroup>
  <NoWarn>$(NoWarn);CS1591;CA1416</NoWarn>
</PropertyGroup>
```

반대로 경고를 오류로 승격시킬 수도 있다.

```xml
<PropertyGroup>
  <TreatWarningsAsErrors>true</TreatWarningsAsErrors>          <!-- 전부 -->
  <WarningsAsErrors>CS8600;CS8602;CS8618</WarningsAsErrors>    <!-- 골라서 -->
</PropertyGroup>
```

> **💡 `#pragma`를 철저히 쓰면 `TreatWarningsAsErrors`를 켤 수 있다**
>
> 이것이 `#pragma warning`의 진짜 가치다. 정당하게 무시해도 되는 경고를 그 자리에서 이유와 함께 억제해 두면, 남은 경고는 전부 진짜 문제다. 그 상태에서 `TreatWarningsAsErrors`를 켜면 **경고가 쌓이는 것 자체가 불가능해진다.**
>
> 실무 순서는 이렇다 — 현재 경고를 세고, 고칠 수 있는 것을 고치고, 남은 것을 `#pragma`로 이유 주석과 함께 억제하고, 그다음 `TreatWarningsAsErrors`를 켠다. 이후로 새 경고는 빌드를 실패시킨다.
>
> 세 번째 단계를 `<NoWarn>`으로 뭉뚱그리지 마라. 프로젝트 전역 `NoWarn`은 앞으로 생길 진짜 문제까지 가려 버린다.

> **📌 `#pragma checksum`**
>
> `#pragma`의 또 다른 형태로 `#pragma checksum "파일" "{GUID}" "체크섬"`이 있다. 소스 생성기와 Razor 같은 도구가 만든 코드에서, 원본 파일의 체크섬을 PDB에 기록해 디버거가 올바른 원본을 찾게 하는 용도다. 손으로 쓸 일은 없다. 생성 코드를 읽다가 만나면 "이건 생성된 파일이구나"라는 표지로 읽으면 된다.

### `#nullable`

`#nullable` 지시문은 널 허용 컨텍스트를 파일 안에서 켜고 끈다.

```csharp
#nullable enable      // 여기서부터 널 가능 참조 타입 활성화
#nullable disable     // 여기서부터 비활성화
#nullable restore     // 프로젝트 설정값으로 복원
```

프로젝트 전체 설정은 `.csproj`다.

```xml
<PropertyGroup>
  <Nullable>enable</Nullable>
</PropertyGroup>
```

`enable`은 두 가지를 동시에 켠다. **주석 컨텍스트**(annotation context)는 모든 참조 타입 선언을 `?`가 없으면 널 불가로 취급하게 하고, **경고 컨텍스트**(warning context)는 `NullReferenceException` 위험이 있는 코드에 경고를 낸다.

이 둘을 따로 켤 수도 있다 — `#nullable enable annotations`는 주석 컨텍스트만, `#nullable enable warnings`는 경고 컨텍스트만 켠다. `disable`과 `restore`에도 같은 방식이 적용되며, `.csproj`에서도 `<Nullable>annotations</Nullable>` 또는 `<Nullable>warnings</Nullable>`로 쓸 수 있다.

> **💡 레거시 코드베이스에 널 안정성을 도입하는 첫걸음**
>
> 수십만 줄짜리 코드베이스에 `<Nullable>enable</Nullable>`을 켜면 경고가 수만 개 쏟아진다. 아무도 그것을 고치지 못하고 결국 설정을 되돌린다.
>
> 현실적인 경로는 `<Nullable>annotations</Nullable>`로 **주석 컨텍스트만 먼저 켜는 것**이다. 자기 코드에서는 경고가 하나도 안 나오지만, 공개 멤버에 `?`를 제대로 붙여 두면 **이 어셈블리를 참조하는 다른 프로젝트는 널 안정성의 혜택을 온전히 받는다.** 자기 집을 치우지 않고도 이웃에게 좋은 시민이 되는 셈이다.
>
> 그다음 단계는 파일 단위 전환이다. 새로 만드는 파일과 손대는 파일에만 `#nullable enable`을 붙여 나가면, 몇 달에 걸쳐 자연스럽게 코드베이스 전체가 전환된다. 널 가능 참조 타입의 의미론과 마이그레이션 전략 전체는 21.6절과 21.7절에서 다룬다.

> **⚠️ `#nullable`은 런타임에 아무 일도 하지 않는다**
>
> 널 가능 참조 타입은 **순수한 컴파일 타임 구조물**이다. `string`과 `string?`은 런타임에 완전히 같은 타입이며, `#nullable enable`을 켜도 널 검사 코드가 삽입되지 않는다. 성능 영향은 정확히 0이다.
>
> 반대로 값 타입의 `int?`는 `Nullable<int>`라는 실재하는 구조체이므로 런타임 표현이 다르다(21.1절). 이 비대칭이 12.5절에서 본 "`string?`에는 별칭을 못 붙인다"의 원인이기도 하다.

### `#line`

`#line`은 컴파일러가 진단 메시지와 디버그 정보에 기록할 **줄 번호와 파일 이름을 바꿔친다.**

```csharp
#line 200 "Original.template"
    ThisWillReportAsLine200OfOriginalTemplate();
#line default
    ThisReportsNormally();
```

용도는 하나뿐이라고 해도 좋다 — **코드 생성기**다. Razor 뷰, T4 템플릿, 소스 생성기가 만든 `.cs` 파일에서 오류가 나면, 사용자에게 생성된 파일의 줄 번호를 보여 줘 봐야 소용이 없다. `#line`으로 원본 `.cshtml`의 줄 번호를 심어 두면 오류 메시지와 디버거 중단점이 원본 파일을 가리킨다.

`#line hidden`은 디버거에게 "다음 `#line`까지는 중단점을 걸지 말고 한 줄씩 실행할 때 건너뛰어라"고 지시한다. 생성 코드의 배관 부분을 디버깅 중에 감추는 데 쓴다.

※C# 10부터는 열 위치까지 지정하는 **범위 형태**가 추가되었다 — `#line (1, 12) - (1, 45) 5 "Source.razor"`. 보간 문자열 안의 식처럼 한 줄의 일부만 원본에 대응할 때 쓰인다.

> **📌 손으로 `#line`을 쓸 일은 없다**
>
> 이 지시문은 사람이 쓰라고 만든 것이 아니다. 디컴파일된 코드나 `obj/` 안의 생성 파일에서 `#line`을 보면 "이 파일은 다른 무언가에서 생성되었고, 원본은 저기에 있다"는 정보로 읽으면 된다. 스택 트레이스에 존재하지 않는 파일 이름이 찍히는 이유가 대개 이것이다(73.4절).

### 전처리기 지시문이 처리되는 위치

컴파일 과정에서 이 모든 것이 어디쯤에서 일어나는지 정리하면 다음과 같다.

```text
   소스 텍스트
       │
       ↓
 ┌───────────────────────────────────────────────┐
 │ 어휘 분석 (lexing)                             │
 │  · 토큰으로 쪼갠다                              │
 │  · #define / #undef 로 심볼 표를 갱신           │
 │  · #if / #elif / #else 를 평가해                │
 │    배제된 영역의 토큰을 아예 버린다  ◀── 여기!   │
 │  · #region / #endregion 은 짝만 확인하고 버린다 │
 │  · #pragma / #nullable / #line 은 표시로 남긴다 │
 └───────────────────────────────────────────────┘
       │  살아남은 토큰만
       ↓
   구문 분석 (parsing) → 의미 분석 → IL 생성 → 어셈블리
```

배제된 코드가 **구문 분석 이전에** 버려진다는 점이 결정적이다. 그래서 문법 오류가 있어도 통과하고, 그래서 IL에 흔적이 없고, 그래서 리팩터링 도구가 그 코드를 보지 못한다.

> **⚠️ `#if` 안의 코드는 IDE의 눈에도 반쯤만 보인다**
>
> 조건부 컴파일의 실무 비용은 여기서 나온다. **이름 바꾸기가 미친다** — IDE는 현재 활성화된 분기만 고치고, 비활성 분기의 호출은 옛 이름으로 남아 그 심볼로 빌드하는 날 깨진다. **테스트되지 않는다** — CI가 한 조합만 빌드하면 나머지는 컴파일조차 되지 않는다. **커버리지에도 분석기에도 잡히지 않는다** — 존재하지 않는 코드는 도구가 볼 수 없다.
>
> 그래서 **`#if` 블록은 짧을수록 좋다.** 100줄짜리 메서드를 통째로 두 벌 만드는 대신, 실제로 다른 몇 줄만 작은 메서드로 뽑아 그 메서드 하나만 두 버전으로 두어라.
>
> ```csharp
> public void Process()
> {
>     /* 공통 로직 */
>     var hash = ComputeHash(data);      // 다른 것은 이 한 줄의 구현뿐
>     /* 공통 로직 */
> }
>
> #if NET8_0_OR_GREATER
> private static byte[] ComputeHash(byte[] d) => SHA256.HashData(d);
> #else
> private static byte[] ComputeHash(byte[] d)
> {
>     using var sha = SHA256.Create();
>     return sha.ComputeHash(d);
> }
> #endif
> ```

## 12.8 조건부 컴파일 vs 정적 플래그 vs `[Conditional]`

"개발 중에는 있어야 하고 배포본에는 없어야 하는 코드"를 다루는 방법이 C#에는 세 가지 있다. 이 절은 셋의 차이를 문법 관점에서 정리한다. 진단 코드라는 구체적 용도에 맞춘 깊은 비교, 즉 어느 것을 언제 고르고 각각이 어떤 IL을 만드는지는 **73.1절**에서 끝까지 다룬다.

### 세 가지 방법

**(1) 조건부 컴파일** — 코드가 어셈블리에 존재하지 않게 된다.

```csharp
#if DEBUG
    Console.WriteLine($"x = {x}");
#endif
```

**(2) 정적 플래그 변수** — 코드는 남고 런타임에 분기한다.

```csharp
internal static bool TestMode = true;

if (TestMode) Console.WriteLine($"x = {x}");
```

**(3) `[Conditional]` 특성** — 메서드는 남지만 **호출하는 쪽이** 사라진다.

```csharp
using System.Diagnostics;

[Conditional("DEBUG")]
static void Log(string msg) => Console.WriteLine(msg);

Log($"x = {x}");    // DEBUG가 없으면 이 줄 전체가 컴파일되지 않는다
```

### 비교

| 기준 | 조건부 컴파일 | 정적 플래그 | `[Conditional]` |
|---|---|---|---|
| 배포본에 코드가 남는가 | 아니다 | 남는다 | 메서드는 남고 호출은 사라진다 |
| 런타임에 켜고 끌 수 있는가 | 아니다 | **가능하다** | 아니다 |
| 인수 계산 비용이 사라지는가 | 그렇다 | 아니다 | **그렇다** |
| 문법 오류가 컴파일에서 잡히는가 | **아니다**(배제된 분기) | 그렇다 | 그렇다 |
| 특성을 조건부로 붙일 수 있는가 | **가능하다** | 불가능 | 해당 없음 |
| 변수의 선언 타입을 바꿀 수 있는가 | **가능하다** | 불가능 | 해당 없음 |
| `using` 별칭을 전환할 수 있는가 | **가능하다** | 불가능 | 해당 없음 |
| 호출부가 지저분해지는가 | 그렇다(`#if`가 흩어진다) | 조금 | **아니다** |
| 사용 제약 | 없음 | 없음 | 반환 타입이 `void`여야 하고 `out` 매개변수 불가 |

### 조건부 컴파일만이 갈 수 있는 곳

정적 플래그로는 절대 흉내 낼 수 없는 세 가지가 있다. 표에서 굵게 표시한 항목이다.

```csharp
// (1) 특성을 조건부로
#if DEBUG
[Obsolete("디버그 빌드 전용 진입점")]
#endif
public static void DevOnlyEntry() { }

// (2) 선언 타입 바꾸기 — 정밀도 실험
#if HIGH_PRECISION
    using Real = System.Double;
#else
    using Real = System.Single;
#endif

// (3) 대규모 리팩터링을 통째로 넣어 두기
#if NEW_ENGINE
    // 새 구현 전체
#else
    // 옛 구현 전체
#endif
```

여러 런타임 버전을 대상으로 컴파일하면서 가능한 곳에서만 최신 API를 쓰는 라이브러리를 만들 때, `NET8_0_OR_GREATER` 같은 SDK 자동 심볼이 정확히 이 용도로 쓰인다(12.7절).

> **⚠️ `[Conditional]`이 사라뜨리는 것은 호출뿐이 아니다 — 인수도 사라진다**
>
> ```csharp
> Log($"결과: {ComputeExpensiveReport()}");
> ```
>
> `DEBUG`가 없으면 이 줄 전체가 컴파일되지 않으므로 `ComputeExpensiveReport()`도 **호출되지 않는다.** 이것이 `[Conditional]`의 최대 장점이자 최대 함정이다 — 진단용 인수 계산 비용이 릴리스에서 완전히 0이 되지만, 인수에 **부작용**을 넣으면 그 부작용도 사라진다.
>
> ```csharp
> Log($"카운터: {++_counter}");    // 릴리스에서 _counter가 증가하지 않는다!
> ```
>
> `[Conditional]` 메서드의 인수에는 절대 부작용을 넣지 마라. 세부는 20.10절과 73.1절에서 다룬다.

> **📌 `[Conditional]`은 특성 클래스에도 붙일 수 있다**
>
> `[Conditional]`을 특성 클래스 자체에 붙이면, 그 특성은 지정한 심볼이 정의된 파일에서만 메타데이터에 기록된다.
>
> ```csharp
> [Conditional("DEBUG")]
> public class TestAttribute : Attribute { }
>
> [Test] class Foo { [Test] string s; }   // DEBUG가 정의된 파일에서만 실제로 붙는다
> ```
>
> 심볼이 그 파일에서 유효하지 않으면 `[Test]`는 조용히 무시된다 — 오류도 경고도 없다. 리플렉션으로 특성을 찾는 코드(20.9절)가 릴리스에서 아무것도 못 찾는 원인이 될 수 있다.

## 12.9 XML 문서 주석 — 표준 태그, 사용자 정의 태그, 크로스 레퍼런스

### 문법

**문서 주석**(documentation comment)은 타입이나 멤버를 설명하는, 소스에 삽입된 XML 조각이다. 선언 바로 앞에 오며 슬래시 세 개로 시작한다.

```csharp
/// <summary>실행 중인 쿼리를 취소한다.</summary>
public void Cancel() { ... }
```

여러 줄로 쓸 수도 있다.

```csharp
/// <summary>
/// 실행 중인 쿼리를 취소한다.
/// </summary>
public void Cancel() { ... }
```

`/** <summary>...</summary> */` 형태도 지원된다(시작 별표가 하나 더 붙는다). 실무에서는 `///`만 쓴다. IDE가 `///`를 입력하는 순간 시그니처를 읽어 `<summary>`, `<param>`, `<returns>` 골격을 자동 생성해 주기 때문이다.

### 문서 파일 생성

`.csproj`에 다음 속성을 넣으면 컴파일러가 문서 주석을 뽑아 XML 파일 하나로 모은다.

```xml
<PropertyGroup>
  <GenerateDocumentationFile>true</GenerateDocumentationFile>
</PropertyGroup>
```

출력 경로를 직접 지정하려면 `<DocumentationFile>bin\MyLib.xml</DocumentationFile>`을 쓴다. 다만 `GenerateDocumentationFile`이 어셈블리 이름과 같은 `.xml`을 어셈블리 옆에 만들어 주므로 요즘은 이쪽이 표준이다.

이 XML 파일의 용도는 두 가지다. **IntelliSense** — 컴파일된 어셈블리와 **같은 폴더에** 두면 Visual Studio·Rider·LINQPad가 자동으로 읽어 소비자에게 멤버 설명을 띄운다. **문서 생성** — DocFX, Sandcastle 같은 도구가 XML을 HTML 도움말로 변환한다.

> **⚠️ IntelliSense는 파일 이름과 위치로만 XML을 찾는다**
>
> 도구는 `MyLib.dll` 옆의 `MyLib.xml`을 찾는다. 그것이 전부다. 어셈블리 안에 문서를 심는 메커니즘은 없고, 매니페스트에 문서 파일 경로가 기록되지도 않는다.
>
> 그래서 `.dll`만 복사했거나, 배포 스크립트가 `.xml`을 "불필요한 파일"로 지웠거나, 단일 파일 게시(4.9절)로 묻혔거나, 애초에 `GenerateDocumentationFile`을 켜지 않았으면 IntelliSense 설명이 조용히 사라진다.
>
> 참조하는 라이브러리에서 갑자기 툴팁이 비어 보인다면, `.dll` 옆에 `.xml`이 있는지부터 확인하라.

> **📌 NuGet 패키지에는 XML이 자동으로 들어간다**
>
> `GenerateDocumentationFile`이 켜져 있으면 `dotnet pack`이 만드는 `.nupkg`의 `lib/net8.0/` 폴더에 `MyLib.dll`과 함께 `MyLib.xml`이 담긴다. 복원 시 둘 다 나란히 풀리므로 소비자의 IntelliSense가 자동으로 동작한다.
>
> 널리 쓰이는 패키지가 좋은 IntelliSense 설명을 갖는 것은 이 한 줄의 설정 덕분이다. **라이브러리를 NuGet에 올릴 계획이라면 `GenerateDocumentationFile`은 선택이 아니라 필수다.** 패키징 실무 전반은 81.2절에서 다룬다.

> **⚠️ `GenerateDocumentationFile`을 켜면 CS1591이 쏟아진다**
>
> 이 속성을 켜는 순간, 문서 주석이 없는 모든 `public` 멤버마다 경고가 하나씩 나온다.
>
> ```text
> warning CS1591: Missing XML comment for publicly visible type or member 'Foo.Bar'
> ```
>
> 기존 프로젝트에 켜면 경고 수천 개를 만나게 된다. 대응은 `<NoWarn>$(NoWarn);CS1591</NoWarn>`으로 전역에서 끄거나, 파일 단위 `#pragma warning disable CS1591`로 억제하며 점진적으로 문서화하는 것이다.
>
> **공개 API 라이브러리라면 전역 억제를 임시로 쓰되 목표는 제거다.** 문서 없는 공개 API는 사용자에게 소스를 읽으라고 요구하는 것과 같다. 반대로 애플리케이션 프로젝트에서 IDE0005(불필요한 `using`)를 쓰려고 `GenerateDocumentationFile`을 켠 것뿐이라면(12.2절), CS1591은 그냥 꺼 두는 것이 맞다.

### 표준 XML 태그

Visual Studio와 문서 생성기가 인식하는 표준 태그는 다음과 같다.

| 태그 | 형태 | 하는 일 |
|---|---|---|
| `<summary>` | `<summary>...</summary>` | IntelliSense가 표시할 툴팁. 보통 한 문장 |
| `<remarks>` | `<remarks>...</remarks>` | 타입·멤버에 대한 추가 설명. 문서 생성기가 본문에 병합한다 |
| `<param>` | `<param name="name">...</param>` | 메서드 매개변수 설명 |
| `<returns>` | `<returns>...</returns>` | 반환값 설명 |
| `<exception>` | `<exception cref="type">...</exception>` | 메서드가 던질 수 있는 예외 (`cref`가 예외 타입을 가리킨다) |
| `<example>` | `<example>...</example>` | 예제. 보통 설명 텍스트와 `<c>`/`<code>`를 함께 담는다 |
| `<c>` | `<c>...</c>` | 인라인 코드 조각 |
| `<code>` | `<code>...</code>` | 여러 줄 코드 샘플 |
| `<see>` | `<see cref="member"/>` | 본문 안의 크로스 레퍼런스. HTML 생성기가 하이퍼링크로 바꾼다 |
| `<seealso>` | `<seealso cref="member"/>` | 페이지 하단의 "참고" 절에 들어가는 크로스 레퍼런스 |
| `<paramref>` | `<paramref name="name"/>` | `<summary>`나 `<remarks>` 안에서 매개변수를 참조한다 |
| `<typeparam>` | `<typeparam name="T">...</typeparam>` | 제네릭 타입 매개변수 설명 |
| `<typeparamref>` | `<typeparamref name="T"/>` | 본문 안에서 타입 매개변수를 참조한다 |
| `<value>` | `<value>...</value>` | 프로퍼티가 나타내는 값의 설명 |
| `<list>` | `<list type="bullet\|number\|table">` | 글머리 기호·번호·표 형태의 목록 |
| `<para>` | `<para>...</para>` | 내용을 별도 문단으로 만든다 |
| `<include>` | `<include file='f' path='xpath'/>` | 외부 XML 파일의 문서를 병합한다. `path`는 XPath 질의다 |
| `<inheritdoc>` | `<inheritdoc/>` | 기반 타입·인터페이스의 문서를 상속한다 |

`<list>`의 전체 형태는 `<listheader>` 하나와 `<item>` 여럿으로 이루어지고, 각 항목은 `<term>`(제목)과 `<description>`(내용) 쌍이다.

```csharp
/// <remarks>
/// <list type="table">
///   <listheader><term>모드</term><description>동작</description></listheader>
///   <item><term>Fast</term><description>검증을 생략한다.</description></item>
///   <item><term>Safe</term><description>모든 입력을 검증한다.</description></item>
/// </list>
/// </remarks>
```

### 실제로 쓰이는 조합

```csharp
/// <summary><paramref name="source"/>에서 조건을 만족하는 첫 요소를 찾는다.</summary>
/// <typeparam name="T">요소 타입.</typeparam>
/// <param name="source">검색할 시퀀스. null일 수 없다.</param>
/// <param name="predicate">각 요소에 적용할 조건.</param>
/// <returns>조건을 만족하는 첫 요소. 없으면 <c>default(T)</c>.</returns>
/// <exception cref="ArgumentNullException">
/// <paramref name="source"/> 또는 <paramref name="predicate"/>가 <c>null</c>일 때.
/// </exception>
/// <example><code>var first = items.FindFirst(x => x.Id > 100);</code></example>
/// <seealso cref="Enumerable.FirstOrDefault{TSource}(IEnumerable{TSource})"/>
public static T? FindFirst<T>(this IEnumerable<T> source, Func<T, bool> predicate)
{
    ArgumentNullException.ThrowIfNull(source);
    ArgumentNullException.ThrowIfNull(predicate);
    foreach (var item in source)
        if (predicate(item)) return item;
    return default;
}
```

마지막 `<seealso>`에서 제네릭 타입을 참조할 때 **중괄호**를 쓴 것에 주목하라. XML 안에서 꺾쇠는 태그로 해석되므로 `cref="Foo{T,U}"`처럼 쓴다.

### `cref`는 컴파일러가 검증한다

여기가 XML 문서 주석이 단순한 주석과 결정적으로 다른 지점이다.

컴파일러가 문서 주석에 대해 하는 특별 처리는 딱 두 가지다.

1. **`<param>` 태그** — 매개변수 이름이 실제로 존재하는지, 그리고 모든 매개변수가 문서화되었는지 검증한다.
2. **`cref` 속성** — 가리키는 타입이나 멤버가 실재하는지 검증하고, **완전 정규화된 ID로 확장한다.**

```csharp
/// <exception cref="ArgumentNullExcepton">오타가 있다</exception>
public void Foo(object o) { }
```

```text
warning CS1574: XML comment has cref attribute 'ArgumentNullExcepton'
that could not be resolved
```

이름을 바꾸는 리팩터링을 하면 IDE가 `cref` 안의 이름도 함께 바꿔 준다. 일반 주석에서는 절대 일어나지 않는 일이다.

> **💡 예외 타입은 `<exception cref>`로만 써라 — 문장으로 쓰지 마라**
>
> ```csharp
> /// <summary>source가 null이면 ArgumentNullException을 던진다.</summary>   // 나쁨
> ```
>
> 이렇게 쓰면 나중에 예외 타입을 바꿔도 아무도 모른다. `cref`로 쓰면 존재하지 않는 타입일 때 경고가 나고, 이름을 바꾸면 자동으로 따라온다.
>
> `<param>` 이름도 같은 이유로 `<paramref name="source"/>`를 써라. 매개변수 이름을 바꾸면 IDE가 함께 고쳐 준다.

### `<inheritdoc>`

인터페이스나 기반 클래스에 이미 쓴 문서를 구현체에서 반복하는 것은 낭비이고, 두 벌이 어긋나는 순간 거짓말이 된다. `<inheritdoc/>`이 이 문제를 푼다.

```csharp
public interface IRepository<T>
{
    /// <summary>주어진 키로 엔티티를 조회한다.</summary>
    /// <param name="id">엔티티 키.</param>
    /// <returns>찾은 엔티티. 없으면 <c>null</c>.</returns>
    T? Get(int id);
}

public class SqlRepository<T> : IRepository<T>
{
    /// <inheritdoc/>
    public T? Get(int id) { ... }
}
```

특정 멤버의 문서를 골라 오거나, 일부만 가져올 수도 있다.

```csharp
/// <inheritdoc cref="IRepository{T}.Get(int)"/>
public T? Get(int id) { ... }

/// <inheritdoc path="/summary"/>
/// <returns>캐시에 있으면 캐시된 인스턴스를 반환한다.</returns>
public T? Get(int id) { ... }
```

두 번째 예처럼 `<summary>`만 상속하고 `<returns>`는 새로 쓰는 것이 실무에서 유용하다.

> **⚠️ `<inheritdoc>`은 컴파일러가 풀어 주지 않는다**
>
> 이것이 가장 자주 오해되는 지점이다. 컴파일러는 `<inheritdoc/>` 태그를 **그대로** XML 파일에 적어 넣는다. 상속 관계를 따라가 실제 문서를 채워 넣지 않는다.
>
> ```xml
> <member name="M:MyApp.SqlRepository`1.Get(System.Int32)">
>     <inheritdoc/>
> </member>
> ```
>
> 태그를 해석하는 것은 **소비하는 도구**다. Visual Studio와 Rider의 IntelliSense, DocFX, Sandcastle은 모두 `<inheritdoc/>`을 이해하고 풀어 준다. 그러나 이것을 이해하지 못하는 옛 도구나 자체 제작 스크립트에서는 **설명이 텅 빈 채로 나온다.**
>
> 판단 기준 — 사내에서 IDE로만 소비되는 라이브러리라면 `<inheritdoc/>`을 마음껏 써라. 공개 NuGet 패키지에서 문서 품질이 중요하다면, 최소한 `<summary>`만이라도 직접 쓰는 편이 안전하다.

### 사용자 정의 태그

컴파일러가 특별 취급하는 것은 `<param>`과 `cref`뿐이다. 나머지 태그는 컴파일러에게 아무 의미가 없으므로, **자기만의 태그를 자유롭게 정의해도 된다.**

```csharp
/// <summary>주문을 확정한다.</summary>
/// <threadsafety>이 메서드는 스레드 안전하지 않다.</threadsafety>
/// <sinceversion>2.3</sinceversion>
/// <jira cref="System.String">PROJ-1841</jira>
public void Confirm() { ... }
```

`cref` 속성은 사용자 정의 태그 안에서도 똑같이 검증되고 확장된다. `<exception>`, `<permission>`, `<see>`, `<seealso>`에서와 다르지 않다.

만든 태그를 실제 문서에 보이게 하려면 문서 생성기 쪽에 변환 규칙을 추가해야 한다. 그 노력이 아깝다면, 태그를 새로 만들지 말고 `<remarks>` 안에 쓰는 편이 낫다.

### 타입·멤버 크로스 레퍼런스 ID

타입 이름과 크로스 레퍼런스는 타입이나 멤버를 유일하게 식별하는 **ID 문자열**로 번역되어 XML에 기록된다. ID는 무엇을 가리키는지 나타내는 접두사와 시그니처로 구성된다.

| 접두사 | 가리키는 것 |
|---|---|
| `N` | 네임스페이스 |
| `T` | 타입 (클래스, 구조체, 열거형, 인터페이스, 델리게이트) |
| `F` | 필드 |
| `P` | 프로퍼티 (인덱서 포함) |
| `M` | 메서드 (특수 메서드 포함) |
| `E` | 이벤트 |
| `!` | 오류 |

시그니처 생성 규칙은 잘 문서화되어 있지만 꽤 복잡하다. 다음은 타입 하나와 그로부터 생성되는 ID들이다.

```csharp
// 네임스페이스는 독립적인 시그니처를 갖지 않는다
namespace NS
{
    /// T:NS.MyClass
    class MyClass
    {
        /// F:NS.MyClass.aField
        string aField;

        /// P:NS.MyClass.aProperty
        short aProperty { get { ... } set { ... } }

        /// T:NS.MyClass.NestedType
        class NestedType { ... }

        /// M:NS.MyClass.X()
        void X() { ... }

        /// M:NS.MyClass.Y(System.Int32,System.Double@,System.Decimal@)
        void Y(int p1, ref double p2, out decimal p3) { ... }

        /// M:NS.MyClass.Z(System.Char[],System.Single[0:,0:])
        void Z(char[] p1, float[,] p2) { ... }

        /// M:NS.MyClass.op_Addition(NS.MyClass,NS.MyClass)
        public static MyClass operator+ (MyClass c1, MyClass c2) { ... }

        /// M:NS.MyClass.op_Implicit(NS.MyClass)~System.Int32
        public static implicit operator int (MyClass c) { ... }

        /// M:NS.MyClass.#ctor
        MyClass() { ... }

        /// M:NS.MyClass.Finalize
        ~MyClass() { ... }

        /// M:NS.MyClass.#cctor
        static MyClass() { ... }
    }
}
```

이 표기법에서 읽어 낼 것이 여럿 있다.

| 소스 | ID 표기 | 관찰 |
|---|---|---|
| `ref double` / `out decimal` | `System.Double@` / `System.Decimal@` | `ref`와 `out`이 **구분되지 않는다**. 둘 다 `@`다 |
| `char[]` | `System.Char[]` | 1차원 배열 |
| `float[,]` | `System.Single[0:,0:]` | 다차원 배열은 차원마다 하한:개수 표기 |
| `operator+` | `op_Addition` | 연산자는 특수 메서드 이름으로 (22장) |
| `implicit operator int` | `op_Implicit(...)~System.Int32` | 변환 연산자는 반환 타입까지 `~` 뒤에 붙는다 |
| 인스턴스 생성자 | `#ctor` | |
| 정적 생성자 | `#cctor` | 13.12절 |
| 파이널라이저 | `Finalize` | 소스의 `~MyClass`가 아니라 CLR 이름 |
| 네임스페이스 | 시그니처 없음 | `N:NS`뿐 |

> **📌 이 ID는 XML 문서만의 것이 아니다**
>
> 같은 ID 형식이 Roslyn API(`ISymbol.GetDocumentationCommentId()`), DocFX의 링크, `[Obsolete]` 진단 도구, 그리고 각종 API 호환성 검사 도구에서 쓰인다. 두 버전의 어셈블리를 비교해 "사라진 공개 API"를 찾는 도구가 비교하는 것이 정확히 이 ID 문자열이다(78.13절).
>
> `ref`와 `out`이 ID에서 구분되지 않는다는 사실도 여기서 의미를 갖는다 — 메서드의 `ref`를 `out`으로 바꾸는 것은 소스 호환성을 깨지만 문서 ID는 그대로다.

### 컴파일 결과와 성능

정리하면 다음과 같다.

| 질문 | 답 |
|---|---|
| 문서 주석이 IL에 들어가는가 | **아니다.** 별도의 `.xml` 파일로만 나간다 |
| 어셈블리 크기를 늘리는가 | 아니다. 0바이트다 |
| 런타임 성능에 영향이 있는가 | 없다 |
| 컴파일 시간에 영향이 있는가 | 늘어난다. `cref` 검증과 XML 생성이 추가 작업이다 |
| 소비자가 문서를 런타임에 읽을 수 있는가 | 어셈블리에서는 불가능. `.xml` 파일을 직접 파싱해야 한다 |

마지막 항목이 종종 놀라움을 준다. **리플렉션으로 문서 주석을 읽는 방법은 없다.** `MethodInfo`에는 `Summary` 같은 프로퍼티가 없다. 런타임에 설명이 필요하다면 문서 주석이 아니라 특성을 써야 한다.

```csharp
[Description("실행 중인 쿼리를 취소한다.")]   // System.ComponentModel
public void Cancel() { ... }
```

> **💡 문서 주석은 "왜"를 쓰는 자리다**
>
> 나쁜 문서 주석의 전형은 시그니처를 그대로 반복하는 것이다.
>
> ```csharp
> /// <summary>Id를 가져오거나 설정한다.</summary>
> public int Id { get; set; }
> ```
>
> 이 줄은 정보를 0비트 추가하고 CS1591 경고 하나를 없앤 대가로 모든 독자의 시간을 조금씩 훔친다.
>
> 문서 주석이 값을 만드는 자리는 시그니처가 말하지 못하는 것을 쓸 때다 — **계약**(null을 허용하는가, 없을 때 빈 컬렉션인가 null인가), **예외 조건**, **스레드 안전성**, **비용**(I/O를 하는가, 캐시하는가), **수명**(호출자가 `Dispose`해야 하는가), 그리고 **이상해 보이는 시그니처의 이유**. BCL의 좋은 문서는 전부 이 항목들을 다룬다. API 설계 관점의 문서화 원칙은 78장에서 다룬다.

## 이 장의 요약

- **네임스페이스는 순수한 컴파일 타임 개념이다.** 메타데이터에는 `TypeNamespace` 문자열 하나로 눌려 들어가고, IL의 모든 타입 참조는 완전 정규화된 이름이다. 그래서 네임스페이스를 깊게 파도, `using`을 쓰든 완전 정규화된 이름을 적든 결과 IL은 한 바이트도 다르지 않다. 네임스페이스는 어셈블리와 무관하고 가시성에도 영향을 주지 않는다.

- **파일 범위 네임스페이스는 들여쓰기 한 단계를 돌려준다.** ※C# 10의 `namespace N;` 문법은 가로 공간을 아끼고, 네임스페이스 변경 시 diff를 한 줄로 줄이며, "이 파일에는 네임스페이스가 하나뿐"임을 문법으로 못 박는다. 한 파일에 하나만 올 수 있고 블록 문법과 섞을 수 없다.

- **이름 해석은 가까운 것이 이긴다.** 지역 → 현재 타입의 멤버 → 감싼 타입 → 현재 네임스페이스의 타입 → 그 네임스페이스의 `using` → 바깥 네임스페이스로 반복 → 전역 `using` 순이다. **직접 선언된 타입은 언제나 `using`으로 가져온 타입을 이기며, 이 우선은 조용하다.** 여러 `using`이 같은 이름을 주면 컴파일러는 고르지 않고 CS0104를 낸다.

- **`global using`은 편의와 위험을 함께 넓힌다.** 프로젝트 전체에 적용되므로 이름 충돌의 사정거리도 프로젝트 전체가 된다. 암시적 using은 언어 기능이 아니라 SDK가 `GlobalUsings.g.cs`를 끼워 넣는 빌드 기능이며, `.csproj`의 `<Using Include/Remove>`로 다듬는다. `using static`은 `Sqrt(x)`처럼 이름이 스스로 말할 때만 쓰고 `Create(x)` 같은 것에는 쓰지 마라.

- **별칭은 컴파일러의 이름 조회 표에만 존재한다.** 파일 밖으로 나가지 않고 IL에도 남지 않는다. ※C# 12부터 배열·다차원 배열·튜플·`int?`·포인터(`using unsafe`)까지 별칭을 붙일 수 있지만, `string?`은 타입이 아니라 컴파일러 주석이므로 여전히 불가능하다.

- **이름 충돌은 위에서부터 풀어라.** 자기 타입 이름 바꾸기 → 완전 정규화 → 별칭 → `using` 국지화 → `extern alias` 순이며, 아래로 갈수록 비싸다. `extern alias`는 완전 정규화된 이름까지 같은 두 어셈블리를 다룰 때만 쓰는 마지막 수단이고, 어셈블리마다 별도의 루트 네임스페이스를 만들어 준다. `global::`은 중첩 타입에 가려진 네임스페이스에 닿는 유일한 방법이다.

- **C#의 전처리기는 매크로가 없고 텍스트 치환을 하지 않는다.** 별도 실행 단계도 없이 어휘 분석 단계에서 처리되며, 심볼에는 값이 없고 정의됨/안 됨 두 상태뿐이다. C 매크로의 용도는 `const`, `nameof`, `using` 별칭, `[Conditional]`이 각각 나눠 가졌고, 그 대안들은 전부 타입 검사를 받고 디버거에서 보인다.

- **`#if`로 배제된 코드는 파싱조차 되지 않는다.** 그래서 문법 오류가 있어도 빌드가 성공하고, IDE의 이름 바꾸기가 그 코드를 고치지 못하며, 커버리지에도 분석기에도 잡히지 않는다. `#if` 블록은 짧게 유지하고, `#else #error`로 빠진 조합을 막고, CI에서 모든 구성·모든 TFM을 빌드해야 한다.

- **SDK가 자동으로 정의하는 심볼을 알면 멀티 타깃이 쉬워진다.** `DEBUG`(Debug 구성), `TRACE`(양쪽 모두), `NET8_0`, 그리고 누적되는 `NET8_0_OR_GREATER` 계열이다. `DefineConstants`에 자기 심볼을 더할 때는 반드시 `$(DefineConstants);` 접두사를 붙여라 — 빠뜨리면 `DEBUG`가 조용히 사라진다.
- **`#pragma warning`을 철저히 쓰면 `TreatWarningsAsErrors`를 켤 수 있다.** 정당하게 무시할 경고를 그 자리에서 이유와 함께 억제하면 남은 경고는 전부 진짜다. `restore`를 빠뜨리면 파일 끝까지 꺼지므로 최소 범위로 감싸고, 전역 `NoWarn`은 앞으로 생길 문제까지 가린다는 것을 기억하라.

- **XML 문서 주석은 컴파일러가 검증하는 유일한 주석이다.** `<param>`의 이름과 `cref`가 실재하는지 검사되고 리팩터링을 따라온다. 예외 타입과 매개변수는 반드시 `cref`·`<paramref>`로 써라. `<inheritdoc/>`은 컴파일러가 풀어 주지 않고 XML에 그대로 실리며, 해석은 소비하는 도구의 몫이다.

- **문서 파일은 어셈블리 옆의 `.xml` 하나가 전부다.** 이름과 위치로만 찾으므로 `.dll`만 복사하면 IntelliSense가 조용히 사라진다. `GenerateDocumentationFile`을 켜면 `dotnet pack`이 자동으로 패키지에 넣어 주므로, NuGet에 올릴 라이브러리에는 필수다. 리플렉션으로는 읽을 수 없으니 런타임에 필요한 설명은 특성으로 써야 한다.

## 연습 문제

1. **이름 해석 순서를 직접 재현하라.** `Outer` 네임스페이스에 `class Foo`를, `Outer.Inner`에도 `class Foo`를 만들고, `Outer.Inner` 안의 클래스에서 `Foo f1; Outer.Foo f2;`를 선언하라. 각각이 어떤 타입인지 `Console.WriteLine(typeof(Foo).FullName)`로 확인하라. 이어서 `Outer.Inner.Foo`를 삭제했을 때 컴파일이 성공하는지, `f1`이 무엇을 가리키게 되는지 확인하라.

2. **CS0104를 만들고 네 가지 방법으로 풀어라.** 같은 프로젝트 안에 `Shapes2D.Circle`과 `Shapes3D.Circle`을 만들고 두 네임스페이스를 모두 `using`한 뒤 `Circle c;`를 선언해 오류를 확인하라. 그다음 (a) 완전 정규화, (b) 네임스페이스 별칭, (c) 타입 별칭, (d) `using`을 네임스페이스 블록 안으로 옮기기 — 네 가지로 각각 해결하고, 어느 것이 가장 읽기 좋은지 판단하라.

3. **암시적 using의 실제 목록을 확인하라.** 콘솔 프로젝트를 만들어 빌드한 뒤 `obj/Debug/net8.0/*.GlobalUsings.g.cs`를 열어라. 다음으로 `<Using Remove="System.Linq" />`를 `.csproj`에 추가하고 다시 빌드해 파일이 어떻게 바뀌는지, 그리고 LINQ를 쓰는 코드가 어떤 오류로 실패하는지 기록하라. 마지막으로 `<Using Include="System.Math" Static="true" />`를 추가해 `Sqrt(2)`가 컴파일되는지 확인하라.

4. **`using`이 IL에 영향을 주지 않음을 확인하라.** SharpLab(sharplab.io)에서 `Console.WriteLine("hi")`(with `using System;`), `System.Console.WriteLine("hi")`, 그리고 `using static System.Console;` + `WriteLine("hi")` 세 가지의 IL을 비교하라. 세 IL이 같은가? 그다음 쓰지 않는 `using`을 열 개 추가하고 IL과 어셈블리 크기가 변하는지 확인하라.

5. **`#if`로 배제된 코드가 검사되지 않음을 확인하라.** `#if NEVER` 블록 안에 문법적으로 완전히 망가진 텍스트를 넣고 빌드가 성공하는지 확인하라. 그다음 그 블록 안에 짝 없는 `#if`를 하나 더 넣고 무슨 일이 일어나는지 보라. 마지막으로 `DefineConstants`에 `NEVER`를 추가해 빌드가 어떻게 실패하는지 확인하라.

6. **자동 정의 심볼을 조사하라.** `<TargetFrameworks>net8.0;netstandard2.0</TargetFrameworks>`로 멀티 타깃 라이브러리를 만들고, `#if` / `#elif` / `#else #error` 사슬로 어떤 심볼이 각 TFM에서 정의되는지 조사하라. `NET6_0_OR_GREATER`가 `net8.0` 빌드에서 정의되는지, `netstandard2.0` 빌드에서 정의되는지 각각 확인하라. 그다음 `<DefineConstants>MY_FLAG</DefineConstants>`(접두사 없이)를 넣고 `#if DEBUG` 블록이 사라지는 것을 관찰하라.

7. **`[Conditional]`의 인수 소멸을 관찰하라.** `[Conditional("DEBUG")] static void Log(string s)`를 만들고 `Log($"count={++counter}")`를 호출하라. Debug 빌드와 Release 빌드에서 `counter`의 최종 값을 각각 출력해 비교하고, Release 빌드의 IL에서 `Log` 호출과 문자열 보간 코드가 모두 사라졌는지 확인하라.

8. **XML 문서 파일을 만들어 IntelliSense를 확인하라.** 클래스 라이브러리에 `<GenerateDocumentationFile>true</GenerateDocumentationFile>`을 켜고 `<summary>`, `<param>`, `<exception cref>`를 갖춘 공개 메서드를 쓰라. 생성된 `.xml`에서 ID 문자열(`M:...`)과 `cref`가 완전 정규화로 확장된 것을 확인하고, 별도 콘솔 프로젝트에서 참조해 툴팁이 뜨는지 본 뒤 `bin`에서 `.xml`만 지우고 다시 확인하라. 마지막으로 인터페이스 문서를 `/// <inheritdoc/>`으로 상속한 구현체를 추가해, 생성된 `.xml`에 태그가 **그대로** 남는지 확인하라.
