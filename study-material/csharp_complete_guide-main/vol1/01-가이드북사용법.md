# 1장. 가이드북 사용법

> **이 장의 위치** — 책 전체의 첫 장이자 Part 0의 유일한 장이다. C# 문법은 한 줄도 가르치지 않는다. 대신 이 책이 무엇을 다르게 하는지, 84개 장이 어떤 순서로 무엇을 답하는지, 그리고 지금 무엇을 설치하고 무엇을 건너뛰어야 하는지를 정한다. 10분 안에 "이 책이 나에게 맞는가"와 "나는 몇 장부터 읽어야 하는가"에 답이 나오면 이 장은 제 역할을 한 것이다.
>
> **선수 지식** — 없다. 이 장은 아무것도 전제하지 않는다.
>
> **이 장에서 다루지 않는 것** — C#과 .NET이 무엇인지는 2장에서, 프로그램이 실행되는 전체 경로는 3장에서, 프로젝트 파일과 배포 형태는 4장에서 다룬다. 이 장은 지도이지 목적지가 아니다.

## 1.1 대상 독자와 선수 지식

### 이 책이 무엇을 다르게 하는가

C# 책은 이미 많다. 그런데 시중의 책은 대체로 두 부류로 갈린다.

**첫째 부류는 문법을 가르친다.** `foreach`를 어떻게 쓰는지, `async`를 어디에 붙이는지, LINQ 연산자가 몇 개인지를 알려준다. 이 책들을 다 읽으면 코드는 짜진다. 그런데 프로덕션에서 메모리가 계속 오르는 이유는 모른다. 왜 이 API가 저 API보다 느린지 설명하지 못한다. 코드 리뷰에서 "이건 왜 이렇게 쓰면 안 되나요"라는 질문에 "그렇게 배웠는데요"라고 답하게 된다.

**둘째 부류는 내부를 가르친다.** GC 알고리즘, 메서드 테이블 레이아웃, JIT 최적화 패스를 판다. 훌륭한 책들이다. 그런데 이 책들은 독자가 이미 C#을 5년 썼다고 가정한다. 문법과 내부 사이의 다리가 없다. 그래서 "`gen0` 예산이 소진되면 GC가 트리거된다"는 문장은 이해했는데, 정작 자기 코드의 어느 줄이 `gen0` 예산을 갉아먹고 있는지는 못 찾는다.

**이 책의 목표는 이 두 사람을 한 사람으로 합치는 것이다.**

문법을 배우는 그 자리에서 컴파일 결과를 보고, 컴파일 결과를 보는 그 자리에서 런타임이 무엇을 하는지 보고, 런타임 동작을 아는 그 자리에서 그게 성능에 어떤 값을 만드는지 본다. `foreach`를 배우는 11장에서 이미 열거자가 무엇인지 알고, 28장에서 그 열거자가 구조체인지 클래스인지가 왜 중요한지 알고, 63장에서 그 차이가 힙에 몇 바이트를 남기는지 안다. 순서가 뒤집히지 않는다.

이 접근을 이 책에서는 **4단 원칙**이라고 부른다. 문법 → 컴파일 결과 → 런타임 동작 → 성능 영향. 1.3절에서 실제 코드와 IL로 이 원칙이 어떻게 작동하는지 보여준다. 그 절 하나만 읽어도 이 책이 어떤 책인지 판단할 수 있을 것이다.

> **💡 이 책의 한 문장 요약**
>
> "이 코드가 무엇으로 바뀌는지 모르면, 이 코드가 왜 느린지도 모른다."
>
> 이 책은 그 "무엇으로 바뀌는지"를 84장 내내 보여준다.

자신이 어디에 해당하는지 먼저 찾아라. 그다음 오른쪽 열의 안내를 따르면 된다.

가장 많은 독자는 **C**다. 이 책의 서술 밀도는 C를 기준으로 맞춰져 있다. D는 앞부분이 지루할 수 있고, A는 뒷부분이 벽처럼 느껴질 수 있다. 둘 다 정상이다.

### "프로그래밍 자체가 처음"이어도 되는가

**된다. 다만 조건이 있다.**

이 책은 입문서로 설계되지 않았다. 6장은 "변수란 값을 담는 상자입니다"에서 시작하지 않고, 미리 정의된 타입의 분류(taxonomy)에서 시작한다. 그런데도 입문자가 이 책을 완주하는 것이 불가능하지는 않다. 세 가지 조건을 지키면 된다.

**조건 1 — Part II(6~12장)를 두 번 읽어라.** 한 번은 4단 원칙의 1단(문법)만 읽는다. IL 블록과 "컴파일 결과" 소제목은 통째로 건너뛴다. 그렇게 12장까지 끝내고 Part III로 넘어간 뒤, Part III를 반쯤 읽었을 때 다시 6장으로 돌아와 건너뛴 부분을 읽는다. 이 시점이면 "컴파일러가 코드를 바꾼다"는 개념 자체가 낯설지 않다.

**조건 2 — 손으로 타이핑하라.** 이 책의 코드는 전부 실행 가능하다(1.7절). 복사·붙여넣기로는 안 된다. 입문자에게 이 책의 가장 큰 위험은 "읽으면 이해되는데 쓰면 안 되는" 상태에 빠지는 것이다. 장마다 있는 연습 문제는 "설명하라"가 아니라 "실행해서 확인하라"로 되어 있다. 그 이유가 이것이다.

**조건 3 — ⚫ 표시가 붙은 Part를 만나면 멈추고 되돌아가라.** 1.2절의 4단계 학습 경로에서 ⚫는 마스터 단계다. 입문자가 첫 회독에 Part X(52장)를 읽는 것은 시간 낭비다. 34장까지 끝내고 나서 실무 코드를 6개월 쓰고 돌아와라.

> **📌 입문자가 이 책 대신 먼저 볼 것**
>
> 프로그래밍이 처음이고 위 조건 세 개가 버겁게 느껴진다면, 마이크로소프트가 무료로 제공하는 대화형 튜토리얼(`learn.microsoft.com`의 C# 입문 경로)을 4~6시간 먼저 하는 편이 낫다. "변수에 값을 넣고, 조건에 따라 분기하고, 반복문으로 배열을 돌린다"까지만 해보면 된다. 그 상태로 이 책 2장을 펴면 훨씬 수월하다.

### 선수 지식 — 무엇이 필요하고 무엇이 필요 없는가

| 항목 | 필요한가 | 없다면 |
|---|---|---|
| 프로그래밍 경험(언어 무관) | **있으면 크게 유리** | 위 "조건" 3개를 지키면 가능 |
| C# 문법 | 불필요 | Part II에서 처음부터 쌓는다 |
| 객체지향 개념(클래스·상속·인터페이스) | 불필요 | Part III 전체가 이것이다 |
| 컴퓨터 구조(스택·힙·캐시) | 불필요 | 6.8절에서 시작해 61장에서 끝까지 판다 |
| 어셈블리어 | **불필요** | IL은 어셈블리어가 아니다. 56장에서 처음부터 가르친다 |
| 자료구조·알고리즘 | 있으면 유리 | Big-O 표기는 24.15절에서 최소한만 쓴다 |
| 영어 | 문서 검색 정도 | 도구 출력과 예외 메시지는 영어다. 이 책이 번역해준다 |
| Windows | **불필요** | Linux·macOS 전부 다룬다. Windows 전용 항목은 명시한다 |

정리하면 **필수 선수 지식은 없다.** 다만 "다른 언어를 1년 써봤다"는 조건이 있으면 완주 기간이 절반으로 줄어든다.

> **⚠️ 이 책은 API 레퍼런스가 아니다**
>
> `System.String`의 메서드 90개를 알파벳 순으로 나열하는 책이 아니다. 35.3절에 문자열 조작 메서드가 정리되어 있지만, 목적은 "무엇이 있는지 감을 잡는 것"이지 "찾아보는 것"이 아니다. 시그니처와 오버로드 전체 목록이 필요하면 공식 API 문서를 봐라. 이 책이 답하는 질문은 다르다 — **"왜 이 메서드는 이런 모양인가"**, **"이 메서드를 호출하면 힙에 무엇이 생기는가"**.
>
> 반대로 공식 문서가 답하지 못하는 질문이 이 책의 영역이다. 공식 문서에는 `List<T>.GetEnumerator()`가 `List<T>.Enumerator`를 반환한다고 적혀 있다. 그것이 왜 구조체이고 그 사실이 당신 코드의 할당량을 어떻게 바꾸는지는 적혀 있지 않다.

## 1.2 4단계 학습 경로 — 입문 / 중급 / 심화 / 마스터

### 왜 단계를 나누는가

C#을 "안다"는 말은 최소 네 가지 서로 다른 상태를 뭉뚱그린다.

1. 문법을 보고 코드를 짤 수 있다.
2. 남의 코드를 읽고 설계 의도를 파악할 수 있다.
3. 이 코드가 무엇으로 컴파일되고 런타임이 무엇을 하는지 설명할 수 있다.
4. 프로덕션 장애 앞에서 도구를 열고 원인을 찾아 고칠 수 있다.

1번에서 4번으로 가는 길은 연속적이지 않다. 각 단계마다 **필요한 도구가 다르고, 읽어야 하는 것이 다르고, 실패하는 방식이 다르다.** 그래서 이 책은 모든 Part에 단계 표시를 붙였다.

| 표시 | 단계 | 도달점 — 이 단계를 끝내면 무엇을 할 수 있는가 |
|---|---|---|
| 🟢 | **입문** | C#으로 콘솔 프로그램을 처음부터 끝까지 짤 수 있다. 컴파일 오류 메시지를 읽고 스스로 고친다. `dotnet build`가 무엇을 하는지 설명한다 |
| 🔵 | **중급** | 타입을 설계한다. 클래스와 구조체 중 무엇을 쓸지 근거를 대고 고른다. LINQ 쿼리가 언제 실행되는지 안다. 남의 라이브러리 API를 보고 의도를 읽는다 |
| 🟣 | **심화** | 비동기 코드를 데드락 없이 짠다. 예외·리소스·객체 수명을 통제한다. 프로파일러 출력을 읽고 병목을 짚는다 |
| ⚫ | **마스터** | IL과 JIT 출력을 읽는다. GC 로그와 힙 덤프로 메모리 문제를 진단한다. 할당 0인 핫 패스를 설계한다. 런타임 소스를 열어 답을 확인한다 |

### 🟢 입문 — "돌아가는 코드"

**도달점을 구체적으로 쓰면 이렇다.**

- 빈 폴더에서 `dotnet new console`로 프로젝트를 만들고, 파일을 하나 더 추가하고, NuGet 패키지를 하나 참조해 빌드할 수 있다.
- `int`와 `long`, `float`와 `decimal`을 언제 쓰는지 근거를 댈 수 있다(7.7절).
- `string`이 불변이라는 사실과 그 결과를 설명할 수 있다(8.2절).
- 배열의 경계 검사가 무엇이고 왜 존재하는지 안다(9.5절).
- `foreach`가 컴파일되면 무엇이 되는지 대략 안다(11.5절). **여기서 이미 IL 이야기가 나온다.** 입문 단계라고 4단 원칙을 미루지 않는다.

**해당 Part**: Part 0(1장), Part I(2~5장), Part II(6~12장). 총 12개 장.

**흔한 실패** — 문법을 다 외웠는데 프로그램이 안 짜진다. 이건 문법 문제가 아니라 "타입을 설계해본 적이 없다"는 문제다. 그럴 때는 Part II를 다시 읽지 말고 Part III로 진행하라.

### 🔵 중급 — "설계할 수 있는 코드"

**도달점.**

- `class`와 `struct` 중 무엇을 쓸지 손익을 계산해서 고른다(16.8절).
- 인터페이스와 기반 클래스 중 무엇을 쓸지 결정표를 근거로 고른다(18.12절).
- `Equals`와 `GetHashCode`를 계약에 맞게 재정의한다(25.3절, 25.4절).
- 제네릭 제약을 "최소이면서 충분하게" 건다(23.13절).
- LINQ 쿼리가 **언제** 실행되는지 안다. 지연 실행이 만드는 재평가 함정을 피한다(29.6절, 29.7절).
- 델리게이트 캡처가 만드는 숨은 할당을 인지한다(26.11절).

**해당 Part**: Part III(13~22장), Part IV(23~25장), Part V의 전반부(26~29장), Part VII(35~39장), Part XIV(76~77장), Part XVI(81~82장).

**흔한 실패** — 설계 원칙을 외워서 기계적으로 적용한다. "상속보다 조합"을 외우고 모든 곳에 조합을 쓴다. 이 책이 14.12절과 78.2절에서 **판단 기준**을 제시하는 이유가 이것이다.

### 🟣 심화 — "통제할 수 있는 코드"

**도달점.**

- `async void`가 왜 금지인지, sync-over-async가 왜 데드락을 만드는지 **메커니즘 수준에서** 설명한다(47.14절).
- `ConfigureAwait(false)`가 정확히 무엇을 바꾸는지 안다(47.12절).
- 예외 처리가 2단계(필터 패스 → 언와인딩 패스)로 동작한다는 것을 알고, 예외 필터를 로깅에 활용한다(32.6절, 32.8절).
- `IDisposable`과 파이널라이저의 관계를 알고 `SafeHandle`을 쓴다(33.7절).
- 이벤트 구독이 만드는 메모리 누수를 구조적으로 막는다(27.6절, 27.7절).
- 프로파일러를 붙여 병목 위치를 찾는다(67.6절).

### 예제 — `foreach` 한 줄

#### 1단. 문법

`foreach`는 C#에서 가장 먼저 배우는 반복문이다. 아래 두 메서드는 **본문이 글자 하나까지 똑같다.** 다른 것은 매개변수의 정적 타입뿐이다.

```csharp
using System.Collections.Generic;

public class Sum
{
    // (A) 구체 타입으로 받는다
    public int Direct(List<int> numbers)
    {
        int total = 0;
        foreach (int n in numbers)
            total += n;
        return total;
    }

    // (B) 인터페이스로 받는다
    public int ViaInterface(IEnumerable<int> numbers)
    {
        int total = 0;
        foreach (int n in numbers)
            total += n;
        return total;
    }
}
```

문법 책은 여기서 끝난다. "`foreach`는 컬렉션의 모든 요소를 순회한다. `IEnumerable<T>`로 받으면 더 유연하다." 실제로 대부분의 코딩 규약이 "매개변수는 가장 일반적인 타입으로 받아라"라고 권한다. 틀린 말은 아니다.

**그런데 (A)와 (B)는 같은 프로그램이 아니다.**

#### 2단. 컴파일 결과 — IL을 보면 다르다

C# 컴파일러(Roslyn)에게 `foreach`는 키워드가 아니라 **패턴**이다. 컴파일러는 대상 타입에서 `GetEnumerator()`라는 이름의 접근 가능한 메서드를 찾고, 그 반환 타입에서 `MoveNext()`와 `Current`를 찾는다. 인터페이스를 구현했는지는 **두 번째로** 본다. 이 덕 타이핑(duck typing) 규칙은 11.5절과 28.1절에서 자세히 다룬다.

`List<int>`에는 두 종류의 `GetEnumerator()`가 있다.

```csharp
// List<T>가 가진 것 (개념적으로)
public Enumerator GetEnumerator();                       // public, 구조체를 반환
IEnumerator<T> IEnumerable<T>.GetEnumerator();           // 명시적 인터페이스 구현
IEnumerator IEnumerable.GetEnumerator();                 // 명시적 인터페이스 구현
```

`List<T>.Enumerator`는 **구조체**다. `class`가 아니다. 이 사실 하나가 아래 모든 것을 결정한다.

**(A) `List<int>`로 받았을 때의 IL** — 컴파일러는 public `GetEnumerator()`를 골라 잡는다.

```il
.method public hidebysig instance int32 Direct(class [System.Collections]System.Collections.Generic.List`1<int32> numbers) cil managed
{
  .maxstack  2
  .locals init (int32 V_0,
                valuetype [System.Collections]System.Collections.Generic.List`1/Enumerator<int32> V_1,
                int32 V_2)
  IL_0000:  ldc.i4.0
  IL_0001:  stloc.0                       // total = 0
  IL_0002:  ldarg.1
  IL_0003:  callvirt   instance valuetype [System.Collections]System.Collections.Generic.List`1/Enumerator<!0>
                       class [System.Collections]System.Collections.Generic.List`1<int32>::GetEnumerator()
  IL_0008:  stloc.1                       // 열거자 "구조체"를 지역 슬롯에 복사
  .try
  {
    IL_0009:  br.s       IL_0017
    IL_000b:  ldloca.s   V_1              // 주소만 싣는다 — 힙 접근 없음
    IL_000d:  call       instance !0 valuetype [System.Collections]System.Collections.Generic.List`1/Enumerator<int32>::get_Current()
    IL_0012:  stloc.2
    IL_0013:  ldloc.0
    IL_0014:  ldloc.2
    IL_0015:  add
    IL_0016:  stloc.0
    IL_0017:  ldloca.s   V_1
    IL_0019:  call       instance bool valuetype [System.Collections]System.Collections.Generic.List`1/Enumerator<int32>::MoveNext()
    IL_001e:  brtrue.s   IL_000b
    IL_0020:  leave.s    IL_0030
  }
  finally
  {
    IL_0022:  ldloca.s   V_1
    IL_0024:  constrained. valuetype [System.Collections]System.Collections.Generic.List`1/Enumerator<int32>
    IL_002a:  callvirt   instance void [System.Runtime]System.IDisposable::Dispose()
    IL_002f:  endfinally
  }
  IL_0030:  ldloc.0
  IL_0031:  ret
}
```

읽을 지점 네 곳을 짚자.

- **`.locals init`에 `valuetype ... Enumerator<int32> V_1`이 있다.** 열거자가 지역 변수 슬롯에 그대로 놓인다. 스택 프레임 안이다. 힙에는 아무것도 안 생긴다.
- **`ldloca.s V_1`** — `ldloc`(값 싣기)이 아니라 `ldloca`(주소 싣기)다. 구조체를 복사하지 않고 관리 포인터로 다룬다.
- **`call`이지 `callvirt`가 아니다.** `MoveNext()`와 `get_Current()`가 정적으로 결정됐다. 가상 디스패치가 없다.
- **`constrained.` 접두사.** 구조체가 `IDisposable`을 구현할 때 컴파일러가 박싱 없이 `Dispose()`를 호출하는 장치다. 이 옵코드는 56.3절에서 다룬다.

**(B) `IEnumerable<int>`로 받았을 때의 IL** — 컴파일러가 고를 수 있는 것은 인터페이스 메서드뿐이다.

```il
.method public hidebysig instance int32 ViaInterface(class [System.Runtime]System.Collections.Generic.IEnumerable`1<int32> numbers) cil managed
{
  .maxstack  2
  .locals init (int32 V_0,
                class [System.Runtime]System.Collections.Generic.IEnumerator`1<int32> V_1,
                int32 V_2)
  IL_0000:  ldc.i4.0
  IL_0001:  stloc.0
  IL_0002:  ldarg.1
  IL_0003:  callvirt   instance class [System.Runtime]System.Collections.Generic.IEnumerator`1<!0>
                       class [System.Runtime]System.Collections.Generic.IEnumerable`1<int32>::GetEnumerator()
  IL_0008:  stloc.1                       // 열거자 "참조"를 지역 슬롯에 저장
  .try
  {
    IL_0009:  br.s       IL_0017
    IL_000b:  ldloc.1                     // 참조를 싣는다 — 힙 객체를 따라간다
    IL_000c:  callvirt   instance !0 class [System.Runtime]System.Collections.Generic.IEnumerator`1<int32>::get_Current()
    IL_0011:  stloc.2
    IL_0012:  ldloc.0
    IL_0013:  ldloc.2
    IL_0014:  add
    IL_0015:  stloc.0
    IL_0017:  ldloc.1
    IL_0018:  callvirt   instance bool [System.Runtime]System.Collections.IEnumerator::MoveNext()

    IL_001f:  leave.s    IL_002e

    IL_0021:  ldloc.1
```

같은 한 줄인데 IL이 다르다.

| 지점 | (A) `List<int>` | (B) `IEnumerable<int>` |
|---|---|---|
| 지역 변수 타입 | `valuetype ...Enumerator<int32>` — 구조체 | `class ...IEnumerator<int32>` — 참조 |
| 열거자 접근 | `ldloca` — 주소 | `ldloc` — 참조 역참조 |
| `MoveNext` 호출 | `call` (정적 바인딩) | `callvirt` (인터페이스 디스패치) |
| `Current` 호출 | `call` | `callvirt` |
| `finally`의 null 검사 | 없음 (구조체는 null일 수 없다) | `brfalse.s` 있음 |
| `Dispose` 호출 | `constrained. callvirt` — 박싱 없음 | `callvirt` |

> **📌 (A)에는 할당이 안 보이는데 (B)에도 안 보인다**
>
> (B)의 IL 어디에도 `newobj`가 없다. 그런데 할당은 분명히 일어난다. 어디서?
>
> **`List<T>` 안에서다.** `IEnumerable<T>.GetEnumerator()`의 명시적 구현은 개념적으로 이렇게 생겼다.
>
> ```csharp
> IEnumerator<T> IEnumerable<T>.GetEnumerator() => new Enumerator(this);
> ```
>
> `Enumerator`는 구조체인데 반환 타입은 인터페이스다. 여기서 **암시적 박싱 변환**이 일어난다. 즉 호출한 쪽의 IL이 아니라 호출당한 쪽의 IL에 `box` 명령이 있다. 자기 코드만 봐서는 절대 안 보이는 할당이다. 63.9절의 「숨은 할당 카탈로그」가 존재하는 이유다.

#### 3단. 런타임 동작 — CLR이 무엇을 하는가

이제 실행 시점으로 내려간다.

**(A)의 경우.** `List<int>.Enumerator`는 필드 네 개를 가진 구조체다 — 리스트 참조, 인덱스, 버전 스냅샷, 현재 값. 이 20여 바이트가 `Direct` 메서드의 **스택 프레임 안에** 그대로 놓인다. 힙에 손대지 않으므로 GC가 알아야 할 것이 하나도 늘지 않는다.

그리고 결정적인 것은 **JIT이 이 루프를 통째로 인라인할 수 있다는 점**이다. `MoveNext()`와 `get_Current()`가 `call`(정적 바인딩)이고, 대상 타입이 봉인된 구조체이고, 메서드 본문이 작다. JIT의 인라이닝 휴리스틱(55.4절)이 통과시키기 좋은 모든 조건을 갖췄다. 실제로 Tier-1로 승격된 코드(55.2절)에서는 `foreach` 루프가 배열을 도는 `for` 루프와 거의 같은 기계어가 된다. 경계 검사까지 제거되는 경우가 많다(55.6절).

**(B)의 경우.** 세 가지가 추가된다.

1. **힙 할당.** 박싱된 열거자 객체가 gen0에 하나 생긴다. 범프 포인터 할당이므로 할당 자체는 싸다(63.1절). 문제는 이 객체가 나중에 GC가 훑어야 할 대상이 된다는 것이다.
2. **인터페이스 디스패치.** `callvirt`가 요소마다 두 번(`MoveNext`, `get_Current`) 실행된다. 인터페이스 호출은 가상 메서드 호출보다 한 단계 더 비싸다 — 메서드 테이블의 인터페이스 맵을 거치거나 디스패치 스텁을 타야 한다(18.9절, 54.1절).
3. **인라이닝 실패.** 호출 대상이 런타임에 정해지므로 JIT이 본문을 펼쳐 넣지 못한다. JIT의 가드된 역가상화(GDV, 55.5절)가 "이 호출 지점은 십중팔구 `List<int>.Enumerator`더라"라고 추측해 빠른 경로를 만들어주기도 하지만, 추측이 빗나가면 폴백 경로로 떨어지고 **박싱된 객체 자체는 어차피 이미 할당된 뒤다.**

이걸 그림으로 보면 차이가 분명해진다.

```text
(A) List<int>로 받았을 때            (B) IEnumerable<int>로 받았을 때

  스택                                 스택                힙(gen0)
 ┌──────────────┐                    ┌──────────────┐    ┌──────────────────┐
 │ total        │                    │ total        │    │ 객체 헤더  8B     │
 ├──────────────┤                    ├──────────────┤    │ MT 포인터  8B     │
 │ Enumerator   │ ← 구조체 그대로     │ IEnumerator  │───→│ _list      8B     │
 │  _list       │   (약 24B)         │  (참조 8B)   │    │ _index     4B     │
 │  _index      │                    └──────────────┘    │ _version   4B     │
 │  _version    │                                        │ _current   4B     │
 │  _current    │                     힙 할당: 40B        │ (정렬 패딩 4B)    │
 └──────────────┘                     GC 대상: 1개        └──────────────────┘
   힙 할당: 0B                                              합계 40B
   GC 대상: 없음
```

박싱된 객체 크기가 40바이트인 계산은 이렇다. 64비트에서 참조 타입 인스턴스는 **객체 헤더(싱크 블록 인덱스) 8바이트 + 메서드 테이블 포인터 8바이트**를 항상 달고 다닌다(54.2절). 여기에 필드 20바이트가 붙고, 8바이트 정렬로 올림하면 40바이트다. 최소 객체 크기와 필드 레이아웃 규칙은 54.3절과 54.4절에서 다룬다.

#### 4단. 성능 영향 — 그래서 얼마나 다른가

`int` 10,000개를 담은 `List<int>`를 각각 순회하는 벤치마크다. BenchmarkDotNet으로 측정했고, 코드는 예제 저장소 `ch01/ForeachFourWays`에 있다(1.7절).

| 방식 | 평균 | 상대 | 할당 / 호출 | Gen0 수집 |
|---|---|---|---|---|
| `int[]`를 `for`로 순회 | 2.9 µs | 1.00 | 0 B | 0 |
| `List<int>`를 `foreach` (A) | 4.1 µs | 1.41 | **0 B** | 0 |
| `IEnumerable<int>`를 `foreach` (B) | 26.4 µs | 9.10 | **40 B** | 있음 |
| `IEnumerable<int>`에 `.Sum()` (LINQ) | 31.7 µs | 10.9 | 40 B | 있음 |

> **⚠️ 이 숫자를 그대로 인용하지 마라**
>
> 위 표는 **필자의 특정 머신·특정 런타임 버전에서 나온 한 번의 측정**이다. 절대값은 CPU, 런타임 버전, 계층형 컴파일 상태에 따라 얼마든지 달라진다.
>
> 이 표에서 가져갈 것은 두 가지뿐이다. **(1) 할당 열의 0 B와 40 B는 구조적인 차이라서 머신이 바뀌어도 안 바뀐다. (2) 인터페이스를 거치는 순간 한 자릿수 배가 아니라 자릿수가 바뀔 수 있다.** 벤치마크가 거짓말하는 방식은 67.4절에 정리해 두었다. 이 책의 모든 성능 표는 같은 태도로 읽어야 한다.

**40바이트가 왜 문제인가.** 호출 한 번에 40바이트면 아무것도 아니다. 그런데 이 메서드가 초당 10만 번 호출되는 웹 API 핸들러 안에 있다면 초당 4 MB다. gen0 예산(63.6절)을 훨씬 빠르게 소진시키고, gen0 GC 빈도가 올라가고, 살아남은 객체는 gen1로 승격되고, 그중 일부는 gen2까지 간다. 이것이 66.12절에서 다루는 **mid-life crisis** 패턴의 전형적인 시작점이다.

**그래서 무엇을 하라는 말인가.** "항상 구체 타입으로 받아라"가 아니다. 판단 기준은 이렇다.

- **공개 API의 경계**에서는 `IEnumerable<T>`가 맞다. 유연성이 40바이트보다 값지다.
- **초당 수만 번 도는 내부 핫 패스**에서는 구체 타입이나 제네릭 제약(`where TCollection : IEnumerable<T>`)을 쓴다. 구조체 열거자가 박싱되지 않고 그대로 살아남는다.
- **어느 쪽인지 모르겠으면 측정한다.** 이 순서를 뒤집지 않는 것이 67장 전체의 주제다.

같은 논리가 24.16절(인터페이스로 받을 것인가 구체 클래스로 받을 것인가), 68.7절(전방 전용 열거자 패턴), 78.3절(메서드 그룹 설계)에서 각각 다른 각도로 반복된다.

### 왜 이 예제를 골랐는가

`foreach`는 C#을 배우는 첫 주에 나오는 문법이다. 그런데 이 한 줄 안에 이 책이 다루는 것이 거의 다 들어 있다.

| 4단 원칙 | `foreach` 예제에서 | 자세히 다루는 곳 |
|---|---|---|
| 문법 | 덕 타이핑된 열거자 패턴, 대상 타입에 따른 오버로드 선택 | 11.5절, 28.1절 |
| 컴파일 결과 | `call` vs `callvirt`, `ldloca` vs `ldloc`, `constrained.` | 56.3절, 56.6절 |
| 런타임 동작 | 구조체 vs 박싱, 인터페이스 디스패치, JIT 인라이닝 | 15.2절, 18.9절, 55.4절 |
| 성능 영향 | 0 B vs 40 B, gen0 압박, 승격, mid-life crisis | 63.9절, 66.12절 |

**핵심은 이것이다. 소스 코드는 프로그램이 아니다.** 소스는 컴파일러에 대한 요청이고, IL은 런타임에 대한 요청이고, 실제로 실행되는 것은 JIT이 만든 기계어다. 이 세 층을 각각 볼 줄 알아야 "왜 느린가"에 답할 수 있다.

> **⚠️ IL을 외우려 들지 마라**
>
> 이 책은 IL을 자주 보여주지만, **옵코드 목록을 암기하라는 뜻이 아니다.** 실무에서 필요한 것은 200개 옵코드가 아니라 스무 개 남짓이다.
>
> 필요한 능력은 이것뿐이다 — IL 덤프를 봤을 때 (1) `newobj` / `box` / `newarr`가 있으면 할당이 있다는 것을 알아채고, (2) `call`과 `callvirt`를 구분하고, (3) 컴파일러가 만든 이상한 이름(`<>c__DisplayClass0_0`, `<Sum>d__1` 같은)이 무엇인지 짐작하는 것. 56장은 이 세 가지에 집중한다.

> **⚠️ Debug 빌드의 IL로 성능을 논하지 마라**
>
> SharpLab 같은 도구는 기본이 Debug 구성인 경우가 있다. Debug IL에는 최적화가 전혀 들어가지 않고, 지역 변수가 불필요하게 늘고, `nop`이 섞이고, 무엇보다 **JIT이 인라이닝을 거의 하지 않는다.**
>
> 컴파일러가 무엇을 만드는지 **구조**를 볼 때는 Debug가 오히려 읽기 쉽다. 하지만 "이게 빠른가"를 판단할 때는 반드시 Release 구성으로 바꾸고, 최종 판단은 IL이 아니라 **측정**으로 내려야 한다. 55.8절에서 `DOTNET_JitDisasm`으로 실제 기계어를 보는 방법을 다룬다.

### 4단 원칙이 항상 4단은 아니다

모든 절이 네 단계를 다 밟지는 않는다. 주제에 따라 무게가 다르다.

| 주제 유형 | 1단 문법 | 2단 컴파일 | 3단 런타임 | 4단 성능 | 예 |
|---|---|---|---|---|---|
| 컴파일러가 크게 바꾸는 문법 | 중 | **강** | **강** | 중 | `async`(47.7절), 반복자(28.4절), 클로저(26.10절) |
| 런타임이 직접 지원하는 것 | 중 | 중 | **강** | **강** | 박싱(15.2절), 제네릭(23.11절), 배열(9.5절) |
| 순수 라이브러리 기능 | **강** | 약 | 중 | 중 | 정규식(36장), 날짜/시간(37장) |
| 설계·관용구 | **강** | 약 | 약 | 중 | API 설계(78장), 코드 관용구(79장) |
| 순수 런타임 주제 | — | — | **강** | **강** | GC 알고리즘(64장), 힙 구조(62장) |

"이 절에는 IL이 없는데?"라고 느껴진다면 그건 누락이 아니라 해당 주제에서 2단이 할 말이 없기 때문이다. 반대로 **컴파일러가 코드를 크게 다시 쓰는 문법**(비동기, 반복자, 클로저, 패턴 매칭, 보간 문자열)에서는 2단이 절 하나를 통째로 차지한다.

## 1.5 실습 환경 구축

이 책의 기준 환경은 **.NET 8(LTS) 또는 .NET 9 SDK**, 언어는 **C# 12 / C# 13**이다. 그보다 새로운 런타임에서도 이 책의 코드는 거의 그대로 돌아간다. 특정 버전 이상에서만 되는 기능에는 `※C# 12`, `※.NET 8` 같은 표시를 붙였다(1.7절).

### SDK 설치와 확인

설치는 `dotnet.microsoft.com/download`에서 자기 OS용 **SDK**를 받으면 된다. 리눅스는 배포판 패키지 관리자로도 설치할 수 있고, macOS는 Homebrew로도 된다. Windows는 Visual Studio 2022를 설치하면 SDK가 함께 들어온다.

설치했으면 터미널에서 확인한다.

```text
dotnet --version
```

```text
9.0.100
```

여기서 나오는 것은 **SDK 버전**이다. 더 자세히 보려면 이렇게 한다.

```text
dotnet --info
```

```text
.NET SDK:
 Version:   9.0.100
 Commit:    (해시)

런타임 환경:
 OS Name:     ubuntu
 OS Version:  24.04
 OS Platform: Linux
 RID:         linux-x64
 Base Path:   /usr/share/dotnet/sdk/9.0.100/

.NET SDKs installed:
  8.0.404 [/usr/share/dotnet/sdk]
  9.0.100 [/usr/share/dotnet/sdk]

.NET runtimes installed:
  Microsoft.AspNetCore.App 8.0.11 [/usr/share/dotnet/shared/Microsoft.AspNetCore.App]
  Microsoft.NETCore.App 8.0.11 [/usr/share/dotnet/shared/Microsoft.NETCore.App]
  Microsoft.NETCore.App 9.0.0 [/usr/share/dotnet/shared/Microsoft.NETCore.App]
```

이 출력에서 확인할 것은 세 가지다.

1. **`.NET SDKs installed`에 8.0 또는 9.0 계열이 하나 이상 있다.**
2. **`.NET runtimes installed`에 `Microsoft.NETCore.App`이 있다.** 이게 없으면 빌드는 되는데 실행이 안 된다.
3. **`RID`**(런타임 식별자, runtime identifier)가 자기 플랫폼과 맞다. 자체 포함 배포와 네이티브 AOT를 다룰 때 이 값이 필요하다(4.9절, 81.9절).

> **⚠️ SDK와 런타임은 다르다**
>
> 가장 흔한 설치 사고가 **런타임만 설치하고 SDK라고 착각하는 것**이다.
>
> - **런타임**(`Microsoft.NETCore.App`) — 이미 빌드된 .NET 앱을 **실행**만 한다. 서버에 배포할 때 필요한 것.
> - **SDK** — 컴파일러, MSBuild, `dotnet` CLI, 그리고 런타임까지 전부 포함한다. **개발하려면 이쪽이다.**
>
> `dotnet --version`이 동작해도 안심하면 안 된다. 런타임만 있어도 그 명령은 실행된다. **`dotnet --list-sdks`가 빈 줄을 뱉으면 SDK가 없는 것이다.** 그 상태에서 `dotnet new console`을 하면 "명령을 찾을 수 없다"는 메시지를 만난다.

여러 SDK가 깔려 있을 때 특정 버전으로 고정하려면 솔루션 루트에 `global.json`을 둔다.

```json
{
  "sdk": {
    "version": "9.0.100",
    "rollForward": "latestFeature"
  }
}
```

`rollForward` 정책과 SDK·런타임·언어 버전의 관계는 4.5절과 76.13절에서 다룬다.

> **⚠️ .NET Framework와 .NET을 섞지 마라**
>
> 검색하면 `.NET Framework 4.8` 기준 자료가 아직도 대량으로 나온다. 이름이 비슷해서 헷갈리지만 **다른 제품**이다.
>
> - **.NET Framework** — Windows 전용. 4.8이 사실상 마지막. `mscorlib`, GAC, AppDomain, `app.config`가 있는 세계.
> - **.NET** (5부터 번호가 이어진다) — 크로스 플랫폼. GAC 없음, AppDomain 없음(`AssemblyLoadContext`로 대체), `runtimeconfig.json`.
>
> 이 책은 **.NET 기준**으로 쓴다. .NET Framework에서만 다르게 동작하는 항목은 그때마다 명시한다. 두 갈래가 갈라진 역사는 2.3절에 있다. 오래된 블로그 글을 참고할 때는 반드시 대상이 어느 쪽인지 먼저 확인하라. 이게 실무에서 가장 흔한 사고 원인이다.

```xml
  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net9.0</TargetFramework>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
  </PropertyGroup>

</Project>
```

네 줄짜리 `PropertyGroup`인데 이 안에 이 책의 여러 장이 들어 있다. `TargetFramework`는 4.2절, `ImplicitUsings`는 12.3절, `Nullable`은 21.6절이다. `Program.cs`가 `class`도 `Main`도 없이 한 줄인 이유(최상위 문)는 3.7절에 있다.

> **📌 `.exe`가 있는데 왜 `.dll`이 "진짜"인가**
>
> .NET에서 애플리케이션을 빌드하면 파일이 두 개 나온다. **`.dll`이 IL과 메타데이터를 담은 어셈블리**이고, `.exe`는 그 `.dll`을 런타임에 얹어 실행시키는 얇은 네이티브 런처다.
>
> 그래서 나중에 ILSpy로 자기 앱을 열어볼 때 `.exe`를 열면 아무것도 안 나온다. **열어야 할 것은 `.dll`이다.** .NET Framework은 반대였다 — `.exe` 하나가 어셈블리와 런처 역할을 동시에 했다. 자세히는 52.1절에서 다룬다.

### Release 구성으로 빌드하기

이 책에서 성능을 다루는 모든 실습은 **Release 구성**이 전제다.

```text
dotnet build -c Release
dotnet run -c Release
```

Debug 구성은 최적화가 꺼져 있고, JIT이 인라이닝을 거의 하지 않고, 디버거를 위해 지역 변수를 살려 둔다. Debug 빌드로 측정한 숫자는 아무 의미가 없다. 이 규칙을 어기는 것이 성능 측정에서 가장 흔한 실수이고, 67.4절에서 다시 짚는다.

## 1.6 이 책이 계속 쓰는 8가지 도구

1.3절의 4단 원칙은 도구 없이는 구호에 그친다. "컴파일러가 무엇으로 바꾸는지 봐라"는 말은 **볼 수단이 있을 때만** 의미가 있다.

이 책은 여덟 개 도구를 반복해서 쓴다. 여덟 개를 지금 다 설치할 필요는 없다. 아래 표의 "첫 등장" 열이 각 도구가 처음 필요해지는 지점이다.

| 도구 | 무엇을 보는가 | 설치 | 첫 등장 | 본격 사용 |
|---|---|---|---|---|
| **SharpLab** | C# → IL / 디컴파일된 C# / JIT 어셈블리 | 불필요(웹) | **3.8절** | 전 장 |
| **ILSpy** | 이미 빌드된 `.dll`의 IL과 메타데이터 | 앱 또는 `dotnet tool` | 3.3절 | 56.8절 |
| **BenchmarkDotNet** | 처리량·지연·할당량을 통계적으로 | NuGet 패키지 | 15.2절(결과 인용) | **67.3절** |
| **PerfView** | ETW 이벤트, GC 통계, 힙 스냅샷 | Windows 단일 실행 파일 | 66.6절 | **66.7절** |
| **dotnet-counters** | 살아 있는 프로세스의 실시간 카운터 | `dotnet tool` | **66.8절** | 73.9절 |
| **dotnet-dump** | 프로세스 덤프 수집과 사후 분석 | `dotnet tool` | **66.8절** | 74.5절 |
| **WinDbg + SOS** | 힙·객체 레이아웃·루트 경로를 바닥까지 | Windows(Store) | **54.10절** | 66.9절 |
| **코드 분석기** | 컴파일 시점에 규약 위반과 함정 검출 | SDK 내장 | 4.6절 | 79.13절 |

### 1. SharpLab — 이 책의 기본 습관

브라우저에서 `sharplab.io`를 열고 왼쪽에 C# 코드를 붙이면 오른쪽에 결과가 나온다. 출력 형식을 골라야 한다.

| 출력 모드 | 보여주는 것 | 언제 쓰나 |
|---|---|---|
| **IL** | 컴파일러가 만든 IL 그대로 | 4단 원칙의 2단. 이 책에서 가장 자주 |
| **C#** | IL을 다시 C#으로 디컴파일 | 컴파일러가 생성한 클래스 구조를 보고 싶을 때 |
| **JIT Asm** | JIT이 만든 x64 기계어 | 인라이닝·경계 검사 제거 확인(55.8절) |
| **Syntax Tree** | Roslyn 구문 트리 | 소스 생성기를 만들 때(57.15절) |

**출력 모드 옆의 구성(Debug / Release)을 반드시 확인하라.** 1.3절의 ⚠️ 박스에서 짚은 그 함정이다.

SharpLab의 가장 큰 가치는 **C# 디컴파일 모드**다. 예를 들어 `yield return`이 들어간 메서드를 붙이면, 컴파일러가 만든 `<GetNumbers>d__0`이라는 상태 기계 클래스가 C# 코드로 나온다. 28.4절이 그 실물을 다룬다. 람다를 붙이면 `<>c__DisplayClass0_0` 디스플레이 클래스가 나온다(26.10절). `async` 메서드를 붙이면 `MoveNext()`가 통째로 나온다(47.7절).

> **💡 이 책을 읽는 가장 좋은 자세**
>
> **브라우저 탭 하나에 SharpLab을 띄워 놓고 읽어라.** 이 책에 IL이 실려 있어도 직접 붙여보는 것과는 다르다. 코드를 한 글자 바꿨을 때 IL이 어떻게 달라지는지가 진짜 학습이다.
>
> 1.3절의 예제를 지금 붙여보는 것을 권한다. `List<int>`를 `IEnumerable<int>`로 바꾸는 순간 `call`이 `callvirt`로 바뀌는 것을 눈으로 보면, 이 책이 무슨 이야기를 하려는지 5초 만에 이해된다.

> **⚠️ SharpLab이 보여주지 못하는 것**
>
> SharpLab은 **컴파일 결과**(2단)를 보여준다. 런타임 동작(3단)의 일부(JIT 어셈블리)까지는 보여주지만, **할당량·GC 압박·실제 처리량(4단)은 절대 보여주지 못한다.** 힙에 무엇이 얼마나 생기는지는 BenchmarkDotNet과 프로파일러의 영역이다.
>
> SharpLab의 IL을 보고 "이게 더 짧으니 더 빠르겠군"이라고 판단하는 것은 이 책이 가르치려는 것과 정반대다. IL 명령 수와 실행 속도는 상관관계가 약하다.

### 2. ILSpy — 이미 빌드된 것을 열어본다

SharpLab은 자기가 지금 쓴 코드를 본다. **ILSpy는 남이 만든 `.dll`을 본다.** NuGet 패키지 안에서 무슨 일이 벌어지는지, BCL의 `List<T>.Enumerator`가 정확히 어떻게 구현되어 있는지 확인할 때 쓴다.

```text
dotnet tool install --global ilspycmd
ilspycmd -il bin/Release/net9.0/HelloGuide.dll
```

GUI 버전(ILSpy)과 명령줄 버전(`ilspycmd`)이 있고, JetBrains dotPeek도 같은 역할을 한다. 56.8절에서 비교한다. Windows에서는 .NET SDK와 함께 배포되던 고전 도구 `ildasm`도 여전히 유효하고, 이 책은 IL을 인용할 때 `ildasm` 출력 형식을 따른다(52.2절, 56.7절).

### 3. BenchmarkDotNet — 측정 없이 최적화 없다

C#/.NET 마이크로벤치마킹의 사실상 표준이다. 워밍업, 계층형 컴파일 안정화, 이상치 제거, 통계 처리를 전부 대신 해준다.

```text
dotnet new console -o Bench
cd Bench
dotnet add package BenchmarkDotNet
```

```csharp
using BenchmarkDotNet.Attributes;
using BenchmarkDotNet.Running;

[MemoryDiagnoser]                        // 할당량을 같이 잰다
public class ForeachBench
{
    private readonly List<int> _list = Enumerable.Range(0, 10_000).ToList();

    [Benchmark(Baseline = true)]
    public int Direct()
    {
        int total = 0;
        foreach (int n in _list) total += n;
        return total;
    }

    [Benchmark]
    public int ViaInterface() => Sum((IEnumerable<int>)_list);

    private static int Sum(IEnumerable<int> numbers)
    {
        int total = 0;
        foreach (int n in numbers) total += n;
        return total;
    }
}

BenchmarkRunner.Run<ForeachBench>();
```

```text
dotnet run -c Release
```

`[MemoryDiagnoser]`가 붙으면 결과표에 `Allocated` 열이 생긴다. 1.3절의 40 B가 바로 그 열이다. 67.5절에서 자세히 다룬다.

> **⚠️ BenchmarkDotNet은 Release에서만 돌아간다**
>
> Debug 구성으로 실행하면 BenchmarkDotNet이 **경고를 띄우고 결과를 신뢰하지 말라고 알려준다.** 그 경고를 무시하고 숫자만 읽는 사람이 많다.
>
> 그리고 벤치마크 메서드의 반환값을 반드시 쓰라(위 예제가 `total`을 `return`하는 이유다). 반환하지 않으면 JIT이 계산 자체를 **죽은 코드로 판정해 제거**할 수 있고, 그러면 "0.2 ns"라는 말이 안 되는 숫자가 나온다. 이 함정을 포함해 벤치마크가 거짓말하는 다섯 가지 방식이 67.4절에 있다.

### 4. PerfView — 프로세스 전체에서 무슨 일이 있었나

Microsoft가 배포하는 Windows용 단일 실행 파일이다. ETW(Windows용 이벤트 추적) 이벤트를 수집해 CPU 샘플, GC 통계, 할당 스택, 힙 스냅샷을 보여준다.

이 책에서 PerfView를 쓰는 지점은 명확하다. **"GC가 얼마나 자주 돌았고, 각 GC가 얼마나 오래 멈췄고, 무엇이 살아남았나"** — 이 세 질문의 답은 GCStats 뷰에 있다(66.7절). 크로스 플랫폼 환경에서는 같은 데이터를 `dotnet-trace`와 EventPipe로 수집한다(66.6절).

### 5·6. dotnet-counters와 dotnet-dump — CLI 진단 도구

.NET 진단 도구는 전부 `dotnet tool`로 설치하는 크로스 플랫폼 CLI다. Windows·Linux·macOS·컨테이너에서 동일하게 동작한다.

```text
dotnet tool install --global dotnet-counters
dotnet tool install --global dotnet-dump
dotnet tool install --global dotnet-trace
dotnet tool install --global dotnet-gcdump
```

**`dotnet-counters`** — 살아 있는 프로세스의 카운터를 실시간으로 본다. 재시작도, 코드 수정도 필요 없다.

```text
dotnet-counters monitor --process-id 1234 --counters System.Runtime
```

```text
[System.Runtime]
    GC Heap Size (MB)                              412
    Gen 0 GC Count (Count / 1 sec)                  23
    Gen 1 GC Count (Count / 1 sec)                   4
    Gen 2 GC Count (Count / 1 sec)                   0
    Allocation Rate (B / 1 sec)                1.42e+08
    % Time in GC since last GC (%)                  11
    ThreadPool Thread Count                         16
    ThreadPool Queue Length                        142
```

이 여덟 줄만 읽을 줄 알아도 프로덕션 문제의 절반은 방향을 잡는다. `ThreadPool Queue Length`가 계속 쌓이면 스레드 풀 기아이고(46.1절), `Allocation Rate`가 높은데 `Gen 2 GC Count`가 0이면 gen0에서 다 죽고 있다는 뜻이다(62.4절).

**`dotnet-dump`** — 프로세스 덤프를 뜨고, 그 덤프를 CLI에서 분석한다.

```text
dotnet-dump collect --process-id 1234
dotnet-dump analyze core_20260905_120000
```

`analyze`에 들어가면 SOS 명령을 그대로 쓸 수 있다. `dumpheap -stat`, `gcroot`, `eeheap` 같은 것들이다(66.9절). **Windows가 아니어도 SOS를 쓸 수 있다는 것이 이 도구의 핵심 가치다.**

### 7. WinDbg + SOS — 바닥까지 내려간다

WinDbg는 Windows 커널 시절부터 있던 디버거이고, SOS는 그 위에 얹는 .NET 전용 확장이다. 배우는 비용이 가장 크고, 대신 볼 수 있는 것이 가장 많다.

이 책에서 WinDbg가 처음 등장하는 곳은 **54.10절**이다. "객체 하나가 힙에서 몇 바이트인가"를 계산으로 배운 다음, 그 계산이 맞는지 실제 프로세스를 열어 확인한다. 계산과 실물이 일치하는 것을 한 번 보면 54장 전체가 추상이 아니게 된다.

```text
!dumpheap -stat          현재 힙의 타입별 개수와 총 바이트
!gcroot <주소>            이 객체를 살려 두고 있는 참조 경로
!objsize <주소>           이 객체가 붙들고 있는 그래프 전체 크기
!eeheap -gc              세대·세그먼트·리전 구조
!finalizequeue           파이널라이저 대기열 상태
```

66.9절이 이 다섯 명령으로 실전 시나리오를 푼다.

> **💡 WinDbg를 지금 설치할 필요는 없다**
>
> 여덟 도구 중 학습 곡선이 가장 가파르다. **Part XI(61~66장)에 들어가기 전까지는 필요 없다.** 그전까지는 SharpLab과 BenchmarkDotNet 둘이면 충분하다.
>
> Windows가 아니라면 `dotnet-dump analyze`가 SOS 명령의 대부분을 대체한다. 이 책은 두 경로를 모두 안내한다.

### 8. 코드 분석기 — 컴파일 시점에 잡는다

Roslyn 분석기(analyzer)는 별도 도구가 아니라 **컴파일러 안에서 도는 규칙 집합**이다. .NET SDK에 이미 수백 개가 들어 있고, `.csproj`에서 켜기만 하면 된다.

```xml
<PropertyGroup>
  <EnableNETAnalyzers>true</EnableNETAnalyzers>
  <AnalysisLevel>latest</AnalysisLevel>
  <AnalysisMode>Recommended</AnalysisMode>
  <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
</PropertyGroup>
```

분석기가 잡아주는 것 중에는 이 책의 여러 장에서 다루는 함정이 그대로 들어 있다. 문화권 인식 문자열 비교(35.4절), `IDisposable` 미해제(33.4절), `async void`(47.14절), 불필요한 할당(63.9절) 같은 것들이다. **책에서 배운 규칙을 팀 전체에 강제하는 수단**이 분석기와 `.editorconfig`이고, 79.13절이 그 방법을 다룬다.

## 1.7 예제 코드 저장소와 실행 방법

### 예제는 세 종류다

이 책의 코드는 성격이 달라서 다루는 방법도 다르다. 어느 종류인지 알아야 헛수고를 피한다.

| 종류 | 표시 | 실행 방법 | 예 |
|---|---|---|---|
| **완전한 예제** | 별도 표시 없음 | 그대로 복사해 `Program.cs`에 붙여 실행 | 대부분의 코드 |
| **조각(fragment)** | `// ...` 로 생략 표시 | 맥락 안에 넣어야 컴파일된다 | 메서드 본문만 보여줄 때 |
| **개념 코드** | 📌 박스에 "개념적 형태"로 명시 | **컴파일되지 않는다.** 읽기용 | 컴파일러가 생성하는 코드, 런타임 내부 C++ |

> **⚠️ "개념적 형태"라고 적힌 코드를 붙여넣지 마라**
>
> 컴파일러가 생성하는 상태 기계(47.7절), `Reflection.Emit`이 만드는 IL의 C# 등가물(58.1절), CoreCLR의 C++ 조각(64.10절, 83.2절) 같은 것은 **동작을 설명하기 위해 재구성한 것**이다. 실제 생성 코드는 이름이 다르고(`<>c__DisplayClass0_0` 같은 것), 최적화되어 있고, 버전마다 바뀐다.
>
> 진짜를 보고 싶다면 그 코드를 SharpLab에 붙여 넣어라(1.6절). 그것이 이 책이 SharpLab을 첫 번째 도구로 꼽는 이유다.

### 최소 실행 환경

대부분의 예제는 콘솔 프로젝트 하나면 된다.

```bash
dotnet new console -n Playground
cd Playground
dotnet run
```

이 책의 코드는 **.NET 8 이상**을 전제한다. `※.NET 9`, `※C# 13` 같은 표시가 붙은 것만 그보다 높은 버전이 필요하다.

`.csproj`는 다음 정도면 이 책 전체를 소화한다.

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
```
