# ch07 — 스트림

7장 「스트림」에서 가장 자주 사고로 이어지는 세 가지 주제를 실행 결과로 확인한다.

| 파일 | 무엇을 보여주는가 | 대응 절 |
|---|---|---|
| `backpressure.js` | `write()` 반환값을 무시할 때와 존중할 때의 버퍼·RSS 차이 | 7.4 |
| `pipeline-errors.js` | `pipe()` 의 파일 디스크립터 누수와 `pipeline()` 의 자동 정리 | 7.7 |
| `transform-parallel.js` | 순서를 보장하는 병렬 Transform 스트림 구현 | 7.8 |

## 실행

```bash
node backpressure.js
node --expose-gc backpressure.js   # GC 잡음을 줄여 RSS 비교를 선명하게
node pipeline-errors.js
node transform-parallel.js
```

## 관찰 포인트

### backpressure.js

62.5MB(16KB × 4000청크)를 느린 소비자에게 쓴다. `highWaterMark` 는 64KB다.

- **무시 버전**: 내부 버퍼에 62.5MB 가 그대로 쌓인다. RSS 도 그만큼 늘어난다
- **존중 버전**: 버퍼가 0.1MB 를 넘지 않는다. 약 1000배 차이다
- 핵심: `highWaterMark` 는 **상한이 아니라 신호선**이다.
  "여기까지 찼다"고 알려 줄 뿐, 더 쓰는 것을 막지 않는다. 막는 것은 호출자 책임이다
- 동기 루프는 이벤트 루프를 놓지 않으므로 `'drain'` 이 발생할 기회조차 없다

이 버그는 소비자가 느릴 때만 나타난다. 부하 테스트에서도 잘 안 잡힌다.

### pipeline-errors.js

파이프 20개를 만들고 각각의 목적지를 도중에 실패시킨다.

- **`pipe()`**: 소스 20개가 전부 살아남고 파일 디스크립터가 **+20** 늘어난다.
  `dest.on('error')` 를 달아 둔 것은 프로세스가 죽지 않게 했을 뿐, 소스를 닫지 않는다
- **`pipeline()`**: 살아남은 소스 0개, FD 증가 **+0**
- 리눅스라면 `ls /proc/<pid>/fd | wc -l` 로 운영 중에도 같은 것을 확인할 수 있다

요청마다 이런 파이프를 만드는 서버는 결국 `EMFILE` 로 죽는다.
서버 코드에서는 `pipe()` 대신 `stream/promises` 의 `pipeline()` 을 쓴다.

### transform-parallel.js

처리 시간이 제각각인 12개 항목(합 495ms)을 네 가지 방식으로 처리한다.

| 방식 | 소요 | 순서 |
|---|---|---|
| 순차 Transform (기본) | 약 500ms | 유지 |
| 병렬 4 · 순서 안 지킴 | 약 140ms | **깨짐** |
| 병렬 4 · 순서 보장 | 약 140ms | 유지 |
| 병렬 12 · 순서 보장 | 약 90ms | 유지 |

- 기본 `Transform` 은 콜백을 부르기 전까지 다음 청크를 받지 않는다 → 항상 순차다
- 콜백을 먼저 부르면 병렬이 되지만 출력이 완료 순으로 섞인다
- 인덱스를 붙여 `Map` 에 보관했다가 차례대로 내보내면 둘 다 얻는다
- 동시성을 전체로 올려도 **가장 느린 항목(90ms)보다 빨라지지 않는다**
- 순서 보장의 대가: 첫 항목이 느리면 뒤의 결과들이 메모리에 쌓인다. 버퍼 상한이 필요하다
