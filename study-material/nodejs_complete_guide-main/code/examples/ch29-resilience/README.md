# ch29 — 복원력

29장 「복원력 있는 서비스 만들기」의 세 가지 패턴을 시뮬레이션으로 확인한다.
모두 가상 시계나 결정적 난수를 쓰므로 **실제로 기다리지 않고 매번 같은 결과**가 나온다.

| 파일 | 무엇을 보여주는가 | 대응 절 |
|---|---|---|
| `circuit-breaker.js` | 서킷 브레이커 구현과 CLOSED/OPEN/HALF_OPEN 상태 전이 | 29.6 |
| `retry-backoff.js` | 지터 없는 백오프와 있는 백오프의 재시도 몰림 비교 | 29.6 |
| `chaos.js` | 확률적 실패 주입 래퍼와 이벤트 루프 정지 주입기 | 29.7 |

## 실행

```bash
node circuit-breaker.js
node retry-backoff.js
node chaos.js
CHAOS_CRASH=1 node chaos.js    # 크래시 주입까지 켠다 (종료 코드 1)
```

## 관찰 포인트

### circuit-breaker.js

가상 시계 위에서 정상 → 장애 → 회복 시나리오를 20건의 요청으로 재현한다.
요청마다 "상태 전이 경로"와 "실제로 원격을 호출했는가"를 함께 출력한다.

- 연속 5회 실패 후 `CLOSED → OPEN`. 이후 요청은 **원격을 호출조차 하지 않는다**
- 유예 시간이 지난 뒤 탐색 요청이 실패하면 `OPEN → HALF_OPEN → OPEN` 이 한 요청 안에서 일어난다
- 회복 후에는 연속 2회 성공해야 `CLOSED` 로 돌아간다.
  한 번의 우연한 성공으로 복귀하면 곧바로 다시 열리는 진동(flapping)이 생긴다
- 20건 중 7건을 차단해 약 3500ms 의 타임아웃 대기와 커넥션 점유를 아꼈다

서킷 브레이커의 목적은 두 가지다. **우리 자원을 지키는 것**과
**회복하려는 상대를 방해하지 않는 것**.

### retry-backoff.js

500개 클라이언트가 동시에 실패한 뒤 재시도가 서버에 언제 도착하는지 히스토그램으로 그린다.

| 전략 | 최대 순간 부하 | 부하가 퍼진 구간 |
|---|---|---|
| 고정 간격 | 500건/200ms | 6/40 버킷 |
| 지수 (지터 없음) | 500건/200ms | 4/40 버킷 |
| 지수 + Full jitter | 약 250건 | 40/40 버킷 |
| 지수 + Equal jitter | 약 310건 | 33/40 버킷 |
| 지수 + Decorrelated | 약 120건 | 38/40 버킷 |

- 지수 백오프만으로는 몰림이 해결되지 않는다. **모두가 똑같이 간격을 벌리기 때문**이다
- 지터를 넣으면 총 재시도 횟수는 그대로인데 최대 순간 부하만 4배 낮아진다. 공짜로 얻는 이득이다
- ASCII 히스토그램에서 지터 없는 전략이 몇 개의 기둥(`█`)으로만 서 있는 모습을 확인하라

### chaos.js

두 종류의 주입기를 보여준다.

1. **실패 주입 래퍼** — 즉시 실패 15% / 지연 20% / 무응답 5%.
   호출부 코드는 전혀 바뀌지 않는다. 함수를 감싸기만 한다
2. **이벤트 루프 정지 주입** — p50 은 그대로 두고 p99·max 만 10ms → 125ms 로 밀어 올린다.
   "평균은 멀쩡한데 일부 사용자만 느리다"는 신고를 재현하는 가장 빠른 방법이다

주입할 장애는 **세 종류를 모두** 다뤄야 한다.

| 유형 | 난이도 |
|---|---|
| 즉시 실패 | 가장 쉽다. 오류가 바로 온다 |
| 느린 응답 | 커넥션 풀을 조용히 고갈시킨다 |
| **무응답** | 가장 위험하다. 타임아웃이 없으면 영원히 기다린다 |

많은 팀이 첫 번째만 테스트하고 나머지 둘에서 무너진다.

## 카오스 테스트의 규칙

- **재현 가능해야 한다.** 난수 시드를 고정하고 로그에 남긴다.
  재현되지 않는 장애는 고쳤는지 확인할 방법도 없다
- **폭발 반경을 정한다.** 트래픽 1%, 특정 사용자군, 특정 인스턴스부터
- **즉시 끌 수 있어야 한다.** `maybeCrash` 는 `CHAOS_CRASH=1` 이면서
  `NODE_ENV !== production` 일 때만 동작한다. 안전장치는 이중으로 둔다
- **가설을 먼저 세운다.** "recipe-api 가 20% 실패해도 web-api 는 캐시로 200 을 준다"
  같은 검증할 문장을 정하고, 어긋나면 그것이 발견한 결함이다
- **관측이 먼저다.** 메트릭과 추적이 없으면 무엇이 깨졌는지도 알 수 없다 (30·31장)

## 세 패턴은 함께 써야 한다

```
타임아웃  →  재시도(+지터)  →  서킷 브레이커  →  폴백
```

- 타임아웃이 없으면 실패로 판정되기까지 무한정 기다린다
- 재시도에 지터가 없으면 회복 중인 서버를 다시 넘어뜨린다
- 서킷 브레이커가 없으면 죽은 서비스에 계속 재시도한다
- 폴백이 없으면 결국 사용자에게 오류가 간다
