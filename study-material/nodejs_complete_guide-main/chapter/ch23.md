# 23장. 메시징과 통합 패턴

분산 시스템에서 어려운 부분은 각각의 서비스를 만드는 일이 아니라 그것들을 잇는 일이다. HTTP 호출 한 줄이면 두 서비스가 이어지는 것처럼 보이지만, 그 한 줄은 호출자의 가용성을 피호출자의 가용성에 묶어 버린다. 서비스가 셋을 넘어가는 순간 이 묶음은 사슬이 되고, 사슬의 어느 한 고리가 끊기면 전체가 멈춘다.

메시징(messaging)은 이 사슬을 끊는 방법이다. 호출자는 메시지를 남기고 즉시 돌아오며, 수신자는 준비가 되었을 때 그것을 가져간다. 대신 새로운 문제가 따라온다. 메시지는 중복될 수 있고, 순서가 뒤바뀔 수 있으며, 응답이 영영 오지 않을 수도 있다.

이 장은 메시징의 개념 모델부터 시작해 Redis Pub/Sub, RabbitMQ(AMQP), Redis Streams를 차례로 다루고, 그 위에 작업 분배와 요청/응답을 얹는다. 장 전체를 관통하는 주장은 하나다. **정확히 한 번(exactly-once) 전달은 없다. 최소 한 번(at-least-once) 전달에 멱등성(idempotency)을 얹는 것이 현실적인 정답이다**(29장 참조).

## 23.1 메시징 시스템의 기본: 단방향 vs 요청/응답

### 왜 필요한가

주문 서비스가 결제 서비스를 HTTP로 직접 호출한다고 하자.

```js
// 동기 호출: 주문 서비스가 결제 서비스에 직결된다
const res = await fetch('http://payments.internal/charge', {
  method: 'POST',
  headers: { 'content-type': 'application/json' },
  body: JSON.stringify({ orderId, amount })
})
if (!res.ok) throw new Error('PAYMENT_FAILED')
```

이 코드에는 세 가지 결합(coupling)이 숨어 있다.

- **시간적 결합(temporal coupling)**: 결제 서비스가 지금 이 순간 살아 있어야 한다. 배포 중이거나 과부하 상태면 주문도 실패한다.
- **공간적 결합(spatial coupling)**: 주문 서비스가 결제 서비스의 주소와 인터페이스를 알아야 한다. 수신자가 둘로 늘면 호출 코드를 고쳐야 한다.
- **가용성 곱셈**: 두 서비스가 각각 99.9% 가용성이면 이 경로의 가용성은 99.8%다. 서비스가 다섯이면 99.5%로 떨어진다.

메시징은 중간에 브로커(broker)를 두어 이 결합을 끊는다. 주문 서비스는 "결제해라"라는 메시지를 브로커에 넣고 곧바로 응답을 반환한다. 결제 서비스가 30초 뒤에 살아나도 메시지는 큐에 남아 있다.

결합을 끊는 대가는 복잡성이다. 브로커를 운영해야 하고, 메시지가 언제 처리될지 보장되지 않으며, 흐름을 눈으로 좇기 어려워진다. 그래서 판단 기준은 "지금 답이 필요한가"와 "실패를 나중에 만회할 수 있는가" 두 가지다. 사용자가 결제 버튼을 누르고 결과 화면을 기다리는 동안에는 답이 지금 필요하므로 동기가 맞다. 반면 결제가 확정된 뒤 영수증 이메일을 보내고, 적립금을 적립하고, 배송 시스템에 알리는 후속 작업은 몇 초 늦어도 되고 실패하면 재시도하면 되므로 메시징이 맞다. 하나의 주문 흐름 안에서도 앞단은 동기, 뒷단은 비동기로 나누는 것이 실무의 전형이다.


### 어떻게 동작하는가

메시징 패턴은 통신 방향에 따라 크게 둘로 나뉜다.

**단방향(one-way, fire-and-forget)**은 발신자가 메시지를 보내고 응답을 기다리지 않는다. 발신자는 수신자가 누구인지, 몇 명인지조차 몰라도 된다. 이벤트 알림, 로그 수집, 감사 기록이 여기에 속한다.

**요청/응답(request/reply)**은 발신자가 응답을 기대한다. 메시징 위에서도 구현할 수 있지만(23.8 참조), 상관 식별자와 반환 주소라는 추가 기계 장치가 필요하다.

이 둘의 차이는 코드의 모양보다 실패 처리에서 드러난다. 단방향에서 실패는 "브로커가 메시지를 받았는가"만 확인하면 되지만, 요청/응답에서는 "응답이 오지 않았을 때 요청은 처리되었는가, 아닌가"를 알 수 없다. 이 불확실성이 분산 시스템 설계의 대부분을 지배한다.

| 축 | 동기 호출(HTTP/RPC) | 비동기 메시징 |
| --- | --- | --- |
| 시간적 결합 | 강함(둘 다 살아 있어야 함) | 없음(브로커가 완충) |
| 공간적 결합 | 강함(주소를 알아야 함) | 약함(토픽/익스체인지만 알면 됨) |
| 지연 시간 | 낮음(왕복 1회) | 높음(브로커 경유) |
| 부하 스파이크 | 그대로 전파됨 | 큐에 쌓여 평탄화됨 |
| 실패 처리 | 호출자가 재시도 | 브로커가 보관, 소비자가 재처리 |
| 디버깅 | 스택 트레이스로 추적 | 분산 추적 필요(31장 참조) |
| 백프레셔 | 호출자를 블로킹 | 큐 길이로 관측 |

### 실무 함정

메시징을 도입하면 "느슨해졌다"는 느낌이 들지만, 결합은 사라진 것이 아니라 **메시지 스키마로 이동**했을 뿐이다. 발행자가 페이로드 필드 이름을 바꾸면 소비자가 조용히 깨진다. HTTP였다면 400 응답이 즉시 났을 오류가, 메시징에서는 데드 레터 큐에 조용히 쌓인다. 스키마 버전을 메시지에 명시하고 소비자를 관대하게(tolerant reader) 작성하는 것이 이 함정을 피하는 유일한 방법이다.

또 하나. 모든 것을 비동기로 만들면 안 된다. 사용자가 화면 앞에서 결과를 기다리는 흐름은 동기가 맞다. 메시징은 "지금 답이 필요 없는 일"과 "실패해도 나중에 다시 하면 되는 일"에 쓴다.

마지막으로, 메시징은 관측(observability)의 성격을 바꾼다. 동기 호출은 실패가 그 자리에서 예외로 드러나지만, 비동기 메시징의 실패는 큐 깊이, 데드 레터 큐 크기, 소비 지연 같은 간접 신호로만 나타난다. 하나의 요청이 여러 서비스를 메시지로 통과하면 스택 트레이스로는 흐름을 재구성할 수 없고, 봉투에 심은 상관 식별자를 축으로 로그를 이어 붙이는 분산 추적이 필수가 된다(31장 참조). 메시징을 도입하는 순간 관측 체계도 함께 설계해야 하며, 이를 나중으로 미루면 장애 상황에서 아무것도 볼 수 없게 된다.


## 23.2 메시지 타입: 커맨드, 이벤트, 문서

### 왜 필요한가

메시지를 무작정 JSON 덩어리로 던지면 시스템이 커질수록 누가 무엇을 책임지는지 알 수 없게 된다. 메시지에 의도(intent)를 담는 세 가지 표준 분류가 있다.

**커맨드(command)**는 "이것을 해라"다. 수신자가 정확히 하나이고, 발신자는 그 일이 수행되기를 기대한다. 이름은 명령형 현재 시제를 쓴다: `ChargePayment`, `SendEmail`.

**이벤트(event)**는 "이런 일이 있었다"다. 이미 벌어진 사실이므로 거부할 수 없고, 수신자는 0명일 수도 100명일 수도 있다. 이름은 과거 시제를 쓴다: `OrderPlaced`, `PaymentCaptured`.

**문서(document)**는 그냥 데이터다. 의도가 없고, 수신자가 무엇을 하든 발신자는 상관하지 않는다. 배치 파일 전송이나 상태 스냅숏 동기화가 여기에 해당한다.

이 구분이 중요한 이유는 결합의 방향이 반대이기 때문이다. 커맨드는 발신자가 수신자를 안다(발신자 → 수신자 결합). 이벤트는 수신자가 발신자를 안다(수신자 → 발신자 결합). 새 기능을 붙일 때 기존 코드를 고치지 않아도 되는 쪽은 이벤트다.

| 타입 | 의도 | 시제 | 수신자 수 | 거부 가능 | 결합 방향 |
| --- | --- | --- | --- | --- | --- |
| 커맨드 | 하라 | 명령형 | 정확히 1 | 가능 | 발신자가 수신자를 앎 |
| 이벤트 | 일어났다 | 과거형 | 0..N | 불가능 | 수신자가 발신자를 앎 |
| 문서 | 받아라 | 명사 | 0..N | 무의미 | 스키마로만 결합 |

### 어떻게 동작하는가

어떤 타입이든 메시지는 봉투(envelope)와 페이로드(payload)로 나눈다. 봉투는 인프라가 쓰는 메타데이터이고, 페이로드는 도메인 데이터다. 이 둘을 섞으면 나중에 라우팅 규칙을 바꾸기 어려워진다.

```js
// messaging/envelope.mjs
import { randomUUID } from 'node:crypto'

/**
 * 봉투는 인프라의 것이고 payload는 도메인의 것이다.
 * causationId: 이 메시지를 유발한 직전 메시지의 id
 * correlationId: 하나의 비즈니스 흐름 전체를 묶는 id (31장 참조)
 */
export function createMessage({ type, payload, correlationId, causationId, kind = 'event' }) {
  return {
    id: randomUUID(),
    type,                                   // 'OrderPlaced', 'ChargePayment'
    kind,                                   // 'command' | 'event' | 'document'
    schemaVersion: 1,                       // 소비자가 분기할 근거
    occurredAt: new Date().toISOString(),
    correlationId: correlationId ?? randomUUID(),
    causationId: causationId ?? null,
    payload
  }
}

// 이벤트를 받아 후속 커맨드를 만들 때 흐름 id를 이어붙인다
export function follow(source, { type, payload, kind = 'command' }) {
  return createMessage({
    type,
    payload,
    kind,
    correlationId: source.correlationId,    // 흐름은 유지
    causationId: source.id                  // 인과는 직전 메시지를 가리킴
  })
}
```

`id`가 봉투에 있는 것이 결정적으로 중요하다. 최소 한 번 전달에서 같은 메시지가 두 번 도착할 수 있으므로, 소비자는 이 `id`를 멱등성 키(idempotency key)로 써서 중복을 걸러낸다.

```js
// messaging/idempotency.mjs
// 처리 결과와 메시지 id를 같은 트랜잭션에 기록해야 진짜 멱등이다(19장 참조)
export async function handleOnce(pool, message, handler) {
  const client = await pool.connect()
  try {
    await client.query('BEGIN')
    const { rowCount } = await client.query(
      'INSERT INTO processed_messages (id, consumer) VALUES ($1, $2) ON CONFLICT DO NOTHING',
      [message.id, 'billing-worker']
    )
    if (rowCount === 0) {
      await client.query('ROLLBACK')
      return { skipped: true }               // 이미 처리한 메시지
    }
    const result = await handler(client, message)   // 같은 트랜잭션에서 도메인 변경
    await client.query('COMMIT')
    return { skipped: false, result }
  } catch (err) {
    try { await client.query('ROLLBACK') } catch { /* 연결이 이미 끊긴 경우 */ }
    throw err
  } finally {
    client.release()
  }
}
```

멱등성 처리를 별도 Redis 조회로 구현하는 코드를 자주 보는데, 그것은 멱등이 아니다. "Redis에 기록했지만 DB 커밋 전에 죽는" 창이 열려 있기 때문이다. 중복 판정과 도메인 변경은 같은 원자 단위 안에 있어야 한다.

멱등성 키를 무엇으로 삼을지도 설계 판단이다. 봉투의 `id`는 "같은 메시지의 재전달"은 막지만, "논리적으로 같은 요청이 서로 다른 메시지로 두 번 발행된 경우"는 막지 못한다. 예를 들어 사용자가 결제 버튼을 두 번 누르면 서로 다른 `id`를 가진 두 커맨드가 생긴다. 이때는 봉투 id가 아니라 도메인 수준의 키(예: `orderId`)를 멱등성 키로 써야 한다. 인프라 수준 중복은 봉투 id로, 도메인 수준 중복은 도메인 키로 막는 이중 방어가 견고한 시스템의 모습이다.


### 실무 함정

커맨드를 이벤트처럼 이름 붙이는 실수가 흔하다. `OrderPlaced`를 발행해 놓고 결제 서비스만 그것을 듣게 만들면, 이름은 이벤트지만 실체는 커맨드다. 나중에 다른 서비스가 같은 이벤트를 구독하는 순간 결제가 두 번 일어난다. 이벤트에는 "누가 들어도 안전한 사실"만 담고, 특정 서비스가 반드시 해야 할 일은 커맨드로 명시한다.

## 23.3 큐, 스트림, 그리고 브로커

### 왜 필요한가

메시지를 옮기는 방법은 크게 둘이다. 피어 투 피어(peer-to-peer)로 직접 연결하거나, 중간에 브로커를 두거나.

P2P는 브로커라는 단일 장애점이 없고, 홉이 하나뿐이라 지연이 낮다. ZeroMQ가 대표적이다. 대신 참여자들이 서로를 찾아야 하고(서비스 디스커버리), 메시지 저장 책임이 애플리케이션에 남으며, 노드가 N개면 연결이 N²로 늘어난다.

브로커 기반은 반대다. 발행자와 소비자가 서로를 몰라도 되고, 브로커가 메시지를 보관하므로 소비자가 죽어 있어도 손실이 없다. 대신 브로커 자체를 운영해야 하고 모든 메시지가 홉을 하나 더 거친다.

| 축 | P2P (예: ZeroMQ) | 브로커 (예: RabbitMQ, Kafka) |
| --- | --- | --- |
| 지연 | 낮음(홉 1) | 높음(홉 2 이상) |
| 단일 장애점 | 없음 | 브로커(클러스터로 완화) |
| 메시지 보관 | 애플리케이션 책임 | 브로커가 책임 |
| 디스커버리 | 직접 구현 필요 | 브로커 주소만 알면 됨 |
| 연결 수 | O(N²) | O(N) |
| 운영 부담 | 코드에 몰림 | 인프라에 몰림 |

실무에서는 대부분 브로커를 쓴다. P2P가 유리한 경우는 초저지연이 절대적이거나(고빈도 트레이딩), 브로커를 둘 수 없는 환경(엣지, 온프레미스 제약)이다.

### 어떻게 동작하는가

브로커를 골랐다면 다음 질문은 "큐인가 스트림인가"다. 이것이 이 절의 핵심이다.

**큐(queue)**는 메시지를 소비하면 사라지는 구조다. 브로커가 커서(cursor)를 관리하고, 소비자가 ack를 보내면 브로커가 메시지를 삭제한다. 작업 분배에 적합하다.

**스트림(stream)**은 추가만 되는 로그(append-only log)다. 메시지를 읽어도 로그에 남고, 각 소비자가 자기 오프셋(offset)을 들고 있다. 같은 메시지를 여러 소비자가 각자 다른 속도로 읽을 수 있고, 오프셋을 되감아 재생(replay)할 수 있다.

| 축 | 큐 | 스트림 |
| --- | --- | --- |
| 소비 후 | 삭제됨 | 로그에 남음 |
| 커서 소유 | 브로커 | 소비자(오프셋) |
| 다중 소비자 | 경쟁(하나만 받음) | 각자 전량 수신 가능 |
| 재생 | 불가(DLQ 재투입은 별개) | 가능(오프셋 되감기) |
| 순서 보장 | 큐 단위, 소비자 늘리면 깨짐 | 파티션/키 단위로 보장 |
| 보존 정책 | 소비될 때까지 | 시간/크기 기준 |
| 대표 구현 | RabbitMQ, SQS | Kafka, Redis Streams |
| 적합한 일 | 작업 분배, 커맨드 | 이벤트 소싱, 감사 로그, 다중 구독 |

두 모델의 차이는 "누가 진도를 기억하는가"로 요약된다. 큐는 브로커가 기억하므로 소비자가 단순해지고, 스트림은 소비자가 기억하므로 유연해진다.

전달 보장(delivery guarantee)은 세 가지로 이야기하지만, 실제로 존재하는 것은 둘이다.

- **최대 한 번(at-most-once)**: 처리 전에 ack. 죽으면 유실된다. 메트릭 수집처럼 손실을 감내할 수 있을 때만.
- **최소 한 번(at-least-once)**: 처리 후 ack. ack 직전에 죽으면 재전달되어 중복이 생긴다. 실무의 기본값이다.
- **정확히 한 번(exactly-once)**: 브로커와 소비자의 상태 변경을 하나의 원자적 커밋으로 묶어야 성립한다. 브로커와 데이터베이스가 서로 다른 시스템인 한, 네트워크 위에서 이것은 불가능하다. Kafka의 "exactly-once semantics"도 Kafka 안에서 읽고 Kafka 안에 쓰는 닫힌 경로에 한정된다.

따라서 설계 규칙은 단순하다. **최소 한 번을 전제하고, 소비자를 멱등하게 만든다.** 23.2의 `handleOnce`가 그 구현이다. 이 원칙은 이후 모든 절에 반복해서 등장한다.

순서 보장(ordering)도 모델에 따라 달라진다. 큐는 단일 소비자일 때만 발행 순서를 지키고, 처리량을 위해 소비자를 늘리는 순간 순서가 깨진다. 두 소비자가 각자 다른 속도로 처리하면 나중에 발행된 메시지가 먼저 완료될 수 있기 때문이다. 스트림은 파티션(또는 키) 단위로 순서를 보장하므로, 같은 키의 메시지를 같은 파티션에 보내면 그 키에 대해서는 순서가 유지된다. "사용자별로는 순서가 중요하지만 사용자 간에는 무관한" 흔한 요구는 사용자 ID를 파티션 키로 삼으면 해결된다. 순서가 정말로 전역에서 필요하다면 병렬성을 포기해야 하며, 이는 처리량과의 직접적인 맞교환이다.


### 실무 함정

브로커를 도입하면 큐 길이가 새로운 관측 지표가 된다. 큐가 계속 자라면 소비 속도가 생산 속도를 못 따라가는 것이고, 이때 큐는 완충 장치가 아니라 지연 폭탄이다. 큐 길이와 가장 오래된 메시지의 나이(age of oldest message)를 반드시 알람으로 걸어야 한다(31장 참조). 큐 길이만 보면 소비가 완전히 멈춘 상태에서 생산도 멈춘 경우를 놓친다.

브로커를 고르는 실무 판단은 대개 "이미 무엇을 운영하고 있는가"에서 출발한다. 새 인프라를 하나 더 들이는 비용은 코드로 드러나지 않지만 조직에 실재한다. 이미 Redis가 있다면 가벼운 작업에는 Redis의 리스트나 스트림으로 충분하고, 신뢰성과 라우팅이 중요해지는 시점에 RabbitMQ를, 로그가 시스템의 중추가 되는 시점에 Kafka를 도입하는 단계적 접근이 현실적이다. 처음부터 Kafka를 세우는 것은 대부분의 팀에게 과잉 설계이며, 반대로 결제 이벤트를 Redis Pub/Sub으로 나르는 것은 명백한 과소 설계다. 브로커 선택은 기술 비교표가 아니라 요구되는 신뢰성 수준과 운영 여력의 교차점에서 결정된다.


## 23.4 발행/구독 패턴

### 왜 필요한가

발행/구독(publish/subscribe)은 발행자가 특정 토픽에 메시지를 보내면 그 토픽을 구독한 모든 소비자가 사본을 받는 패턴이다. 발행자는 구독자가 몇 명인지, 누구인지 모른다.

이 패턴이 가장 직관적으로 드러나는 예제는 실시간 채팅이다. 단일 프로세스라면 WebSocket 연결 목록을 메모리에 들고 순회하면 끝난다.

```js
// chat/server-single.mjs
import { createServer } from 'node:http'
import { WebSocketServer } from 'ws'

const server = createServer()
const wss = new WebSocketServer({ server })

wss.on('connection', (ws) => {
  ws.on('message', (raw) => {
    const text = raw.toString()
    // 자기 자신을 포함한 모든 열린 연결에 브로드캐스트
    for (const client of wss.clients) {
      if (client.readyState === client.OPEN) client.send(text)
    }
  })
})

server.listen(process.env.PORT ?? 8080)
```

이 코드는 인스턴스가 하나일 때만 옳다. 로드 밸런서 뒤에 프로세스를 셋으로 늘리는 순간(18장 참조), 인스턴스 A에 붙은 사용자의 메시지는 인스턴스 B, C에 붙은 사용자에게 도달하지 않는다. `wss.clients`는 그 프로세스가 아는 연결만 담고 있기 때문이다. 클러스터 모듈이든 컨테이너 복제든 마찬가지다. 상태가 프로세스 메모리에 있는 한 수평 확장은 기능을 깨뜨린다.

### 어떻게 동작하는가

해결책은 인스턴스들 사이에 메시지 버스를 두는 것이다. Redis Pub/Sub이 가장 가벼운 선택지다.

```bash
docker run -d --name redis7 -p 6379:6379 redis:7-alpine
```

핵심은 **구독용 연결과 발행용 연결을 분리**하는 것이다. Redis 프로토콜에서 `SUBSCRIBE`를 실행한 연결은 구독 모드로 들어가 일반 명령을 받지 않는다. `node-redis`에서는 `duplicate()`로 두 번째 연결을 만든다.

```js
// chat/server-pubsub.mjs
import { createServer } from 'node:http'
import { WebSocketServer } from 'ws'
import { createClient } from 'redis'
import { randomUUID } from 'node:crypto'

const CHANNEL = 'chat:room:general'
const instanceId = randomUUID()          // 자기가 보낸 메시지를 구분하기 위한 식별자

const publisher = createClient({ url: process.env.REDIS_URL })
const subscriber = publisher.duplicate() // 구독 전용 연결
await Promise.all([publisher.connect(), subscriber.connect()])

const server = createServer()
const wss = new WebSocketServer({ server })

// 로컬 연결에만 뿌리는 함수
function broadcastLocal(payload) {
  const text = JSON.stringify(payload)
  for (const client of wss.clients) {
    if (client.readyState === client.OPEN) client.send(text)
  }
}

// 다른 인스턴스(그리고 자기 자신)가 발행한 메시지를 받는다
await subscriber.subscribe(CHANNEL, (raw) => {
  const msg = JSON.parse(raw)
  broadcastLocal(msg)
})

wss.on('connection', (ws) => {
  ws.on('message', (raw) => {
    const msg = {
      id: randomUUID(),
      origin: instanceId,
      text: raw.toString(),
      at: Date.now()
    }
    // 로컬에 직접 뿌리지 않는다. Redis를 한 바퀴 돌아 자기에게 되돌아온다.
    // 이렇게 해야 모든 인스턴스에서 메시지 순서가 동일해진다.
    publisher.publish(CHANNEL, JSON.stringify(msg))
  })
})

server.listen(process.env.PORT ?? 8080)
```

발행자가 로컬 브로드캐스트를 먼저 하고 Redis에도 보내는 구현을 흔히 보는데, 그렇게 하면 자기 인스턴스에 붙은 사용자만 다른 순서로 메시지를 보게 된다. 위 코드처럼 **모든 메시지가 예외 없이 브로커를 경유**하게 만들면 순서가 브로커 하나에서 결정되어 일관해진다. 지연은 1ms 남짓 늘어나지만 그 값어치를 한다.

이 구조에서 인스턴스를 몇 개로 늘리든 동작은 동일하다. 새 인스턴스는 뜨자마자 채널을 구독하고, 죽으면 조용히 빠진다. 발행자 코드는 전혀 바뀌지 않는다. 이것이 발행/구독의 이점이다.

한 가지 더 짚을 것은 채널 분리의 이유다. Redis 프로토콜에서 `SUBSCRIBE`를 실행한 연결은 구독 모드로 전환되어 그 위에서 일반 명령을 실행할 수 없다. 발행과 구독을 같은 연결에서 하려다 이 제약에 부딪히는 실수가 흔하다. `duplicate()`로 연결을 하나 더 만드는 것은 낭비가 아니라 프로토콜의 요구다. 두 연결은 같은 Redis 서버를 가리키지만 역할이 분리되어, 하나는 계속 구독 대기하고 다른 하나는 발행과 일반 명령을 처리한다. 다중 방을 지원하려면 방마다 채널을 두는 대신 패턴 구독(`PSUBSCRIBE chat:room:*`)을 쓰거나, 방 이름을 페이로드에 담아 단일 채널로 흘리고 소비 측에서 필터링하는 편이 연결 수 관리에 유리하다.


### 실무 함정

Redis Pub/Sub은 **메시지를 저장하지 않는다.** 이것은 구현 결함이 아니라 설계 자체다. `PUBLISH`는 그 순간 연결되어 있는 구독자에게 전달을 시도하고 끝난다. 구체적으로 다음 상황에서 메시지가 사라진다.

- 구독자가 0명이면 메시지는 그대로 버려진다. `PUBLISH`는 전달된 구독자 수를 반환할 뿐 에러가 아니다.
- 인스턴스가 재시작하는 3초 동안 발행된 메시지는 그 인스턴스에서 영영 볼 수 없다.
- 구독자의 소켓 출력 버퍼가 `client-output-buffer-limit pubsub` 한도를 넘으면 Redis가 **구독자 연결을 끊어 버린다.** 느린 소비자는 조용히 탈락한다.
- Redis 자체가 재시작하면 진행 중이던 모든 것이 사라진다. AOF/RDB는 Pub/Sub과 무관하다.

따라서 Redis Pub/Sub은 "놓쳐도 되는 실시간 알림"에만 쓴다. 채팅 메시지를 유실하면 안 된다면, 메시지를 데이터베이스에 먼저 쓰고 Pub/Sub은 "새 메시지가 있다"는 신호로만 쓰거나, 아예 23.6의 Redis Streams로 옮겨야 한다. 여기서도 원칙은 같다. 전달 보장이 필요하면 저장하는 매체를 써야 하고, 저장하는 매체를 쓰면 중복이 따라오므로 멱등성이 필요하다.

Pub/Sub이 상태를 갖지 않는다는 성질은 접속 관리에도 영향을 준다. "지금 누가 접속해 있는가" 같은 프레즌스(presence) 정보는 Pub/Sub만으로는 유지할 수 없고, 각 인스턴스가 자신에게 붙은 연결 집합을 Redis의 셋(set)이나 만료 키로 따로 기록해야 한다. 인스턴스가 죽으면 그 기록도 정리되어야 하므로 TTL과 하트비트를 조합한다. 이처럼 실시간 시스템은 "메시지 전달"과 "상태 유지"라는 두 축을 별개로 설계해야 하며, Pub/Sub은 앞의 축만 담당한다.


## 23.5 신뢰성 있는 메시지 전달: AMQP와 RabbitMQ

### 왜 필요한가

유실을 허용할 수 없는 메시지, 예를 들어 결제 요청이나 이메일 발송은 브로커가 디스크에 보관하고 소비자가 처리를 완료했다고 확인할 때까지 지워지지 않아야 한다. AMQP 0-9-1과 그 대표 구현인 RabbitMQ가 이 요구를 정면으로 다룬다.

```bash
docker run -d --name rabbit \
  -p 5672:5672 -p 15672:15672 \
  -e RABBITMQ_DEFAULT_USER=app \
  -e RABBITMQ_DEFAULT_PASS=devpass \
  rabbitmq:3.13-management-alpine

# 관리 UI: http://localhost:15672 (app / devpass)
```

### 어떻게 동작하는가

AMQP의 모델은 네 가지 개념으로 이루어진다.

- **익스체인지(exchange)**: 발행자가 메시지를 보내는 곳. 메시지를 저장하지 않고 라우팅만 한다.
- **큐(queue)**: 메시지가 실제로 쌓이는 곳. 소비자는 큐에서만 읽는다.
- **바인딩(binding)**: 익스체인지와 큐를 잇는 규칙.
- **라우팅 키(routing key)**: 발행 시 메시지에 붙는 문자열. 바인딩 규칙과 대조된다.

발행자는 큐를 모르고 익스체인지에만 보낸다. 소비자는 익스체인지를 모르고 큐에서만 읽는다. 이 간접층이 있기 때문에 새 소비자를 추가할 때 발행자를 건드리지 않아도 된다.

이 간접층의 실질적 이득은 배포 유연성이다. 새로운 서비스가 기존 이벤트를 소비하고 싶으면, 자기 큐를 만들어 익스체인지에 원하는 라우팅 키로 바인딩하기만 하면 된다. 발행 측 코드도, 이미 돌고 있는 다른 소비자도 전혀 영향을 받지 않는다. `topic` 익스체인지를 쓰면 이 확장이 특히 매끄럽다. `order.#` 패턴으로 주문 관련 모든 이벤트를 받다가, 나중에 취소 이벤트만 별도 처리하고 싶어지면 `order.cancelled`에 바인딩된 큐를 새로 붙이면 그만이다. 라우팅 키를 계층적으로 설계해 두는 초기 투자가 이후의 모든 확장을 코드 수정 없이 만든다.


| 익스체인지 종류 | 라우팅 규칙 | 쓰임새 |
| --- | --- | --- |
| `direct` | 라우팅 키가 바인딩 키와 정확히 일치 | 작업 유형별 분배 |
| `topic` | 점으로 구분된 패턴 매칭(`*`=한 단어, `#`=0개 이상) | `order.created.kr` 같은 계층적 이벤트 |
| `fanout` | 키를 무시하고 바인딩된 모든 큐에 복사 | 브로드캐스트, 다중 구독 |
| `headers` | 헤더 값으로 매칭 | 드묾. 라우팅 키로 표현이 어려울 때 |

먼저 지속성 있는 구독자(durable subscriber)를 만든다. 23.4의 Redis Pub/Sub과 달리, 소비자가 꺼져 있는 동안 발행된 메시지도 살아난 뒤에 받는다.

```js
// amqp/connection.mjs
import amqp from 'amqplib'

export async function connect() {
  const conn = await amqp.connect(process.env.AMQP_URL ?? 'amqp://app:devpass@localhost:5672')
  // 연결이 끊기면 프로세스를 죽이고 오케스트레이터가 재시작하게 둔다(29장 참조)
  conn.on('error', (err) => { console.error('amqp error', err); process.exit(1) })
  conn.on('close', () => { console.error('amqp closed'); process.exit(1) })
  return conn
}
```

```js
// amqp/durable-subscriber.mjs
import { connect } from './connection.mjs'

const EXCHANGE = 'events'          // topic 익스체인지
const QUEUE = 'billing-service'    // 이 서비스 전용 지속 큐

const conn = await connect()
const ch = await conn.createChannel()

// durable: true → 브로커 재시작 후에도 정의가 살아남는다
await ch.assertExchange(EXCHANGE, 'topic', { durable: true })
await ch.assertQueue(QUEUE, {
  durable: true,                   // 큐 정의가 디스크에 남는다
  arguments: {
    'x-queue-type': 'quorum',      // 클러스터에서 복제되는 큐 타입(권장)
    'x-dead-letter-exchange': 'events.dlx'
  }
})
// order.* 아래 모든 이벤트를 이 큐로
await ch.bindQueue(QUEUE, EXCHANGE, 'order.#')
```

발행 측은 메시지 자체도 지속성으로 표시해야 한다. 큐가 durable이어도 메시지가 non-persistent면 브로커 재시작 시 사라진다. 여기에 발행자 확인(publisher confirm)을 붙이면 "브로커가 정말 받았는가"까지 보장된다.

```js
// amqp/publisher.mjs
import { connect } from './connection.mjs'
import { createMessage } from '../messaging/envelope.mjs'

const conn = await connect()
const ch = await conn.createConfirmChannel()   // 발행 확인 채널
await ch.assertExchange('events', 'topic', { durable: true })

export async function publishEvent(type, payload, opts = {}) {
  const msg = createMessage({ type, payload, kind: 'event', ...opts })
  const routingKey = type.toLowerCase().replaceAll(/([a-z])([A-Z])/g, '$1.$2') // OrderPlaced → order.placed

  await ch.publish(
    'events',
    routingKey,
    Buffer.from(JSON.stringify(msg)),
    {
      persistent: true,            // 디스크에 기록
      messageId: msg.id,
      correlationId: msg.correlationId,
      contentType: 'application/json',
      timestamp: Date.now()
    }
  )
  await ch.waitForConfirms()       // 브로커의 ack를 기다린다. 실패 시 throw.
  return msg.id
}
```

`waitForConfirms()`를 생략하면 `publish()`는 로컬 소켓 버퍼에 쓰고 즉시 반환하므로, 브로커가 받기 전에 프로세스가 죽으면 메시지가 사라진다. 유실이 문제 되는 경로에서는 반드시 확인을 기다린다.

소비 측에서는 ack/nack와 prefetch가 핵심이다.

```js
// amqp/consumer.mjs
import { connect } from './connection.mjs'
import { pool } from '../db/pool.mjs'
import { handleOnce } from '../messaging/idempotency.mjs'

const QUEUE = 'billing-service'
const conn = await connect()
const ch = await conn.createChannel()

// prefetch: 미확인 메시지를 최대 N개까지만 받는다.
// 이것이 없으면 브로커가 큐 전체를 이 소비자에게 밀어넣어 메모리를 채운다.
await ch.prefetch(20)

await ch.consume(QUEUE, async (raw) => {
  if (raw === null) return                    // 소비자가 취소됨
  let msg
  try {
    msg = JSON.parse(raw.content.toString())
  } catch {
    ch.nack(raw, false, false)                // 파싱 불가 → 재시도 무의미, DLQ로
    return
  }

  try {
    // 최소 한 번 전달이므로 같은 메시지가 다시 올 수 있다. 멱등 처리로 흡수한다.
    await handleOnce(pool, msg, async (client, m) => {
      await client.query(
        'INSERT INTO invoices (order_id, amount) VALUES ($1, $2)',
        [m.payload.orderId, m.payload.amount]
      )
    })
    ch.ack(raw)                               // 처리 완료 후에만 ack
  } catch (err) {
    const redelivered = raw.fields.redelivered
    // 이미 한 번 재전달된 것이 또 실패하면 무한 루프를 막기 위해 DLQ로 보낸다
    ch.nack(raw, false, !redelivered)         // requeue = !redelivered
  }
}, { noAck: false })                          // 수동 ack 모드
```

`noAck: true`로 두면 브로커는 메시지를 보내는 즉시 지웠다고 간주한다. 이것이 최대 한 번 전달이며, 소비자가 처리 중 죽으면 메시지는 사라진다. 신뢰성이 필요하면 언제나 수동 ack다.

`prefetch`는 흐름 제어(flow control)의 전부다. 값이 1이면 처리량이 낮지만 워커 간 부하가 완벽히 균등해지고, 값이 크면 처리량은 오르지만 느린 워커가 메시지를 붙들고 있게 된다. 처리 시간이 짧고 균일하면 50~100, 처리 시간이 길고 편차가 크면 1~5가 출발점이다.

마지막으로 데드 레터 큐(dead letter queue, DLQ)다. 위 `assertQueue`에서 `x-dead-letter-exchange`를 지정했으므로, `nack(..., requeue=false)`된 메시지와 TTL이 만료된 메시지가 그 익스체인지로 흘러간다.

```js
// amqp/dlq-setup.mjs
import { connect } from './connection.mjs'

const conn = await connect()
const ch = await conn.createChannel()

await ch.assertExchange('events.dlx', 'fanout', { durable: true })
await ch.assertQueue('events.dead', {
  durable: true,
  arguments: {
    'x-message-ttl': 14 * 24 * 60 * 60 * 1000   // 14일 뒤 자동 삭제
  }
})
await ch.bindQueue('events.dead', 'events.dlx', '')
```

DLQ는 만들어 두는 것으로 끝이 아니다. **DLQ 길이가 0보다 크면 알람이 울려야 한다.** 아무도 보지 않는 DLQ는 메시지를 조용히 버리는 것과 같다.

### 실무 함정

큐 타입 선택도 신뢰성에 직결된다. RabbitMQ의 전통적인 클래식 큐(classic queue)는 단일 노드에 데이터를 두므로 그 노드가 죽으면 큐 내용이 사라진다. 위 예제에서 쓴 쿼럼 큐(quorum queue)는 라프트(Raft) 합의로 여러 노드에 복제하므로, 과반이 살아 있는 한 메시지가 보존된다. 신뢰성이 목적이라면 클러스터 환경에서는 쿼럼 큐가 사실상 기본값이다. 다만 복제 비용이 있으므로 초당 수십만 건의 초고처리량 경로에는 맞지 않고, 그런 경우는 애초에 Kafka 계열이 어울린다.

`amqplib`의 채널은 스레드 세이프하지 않으며, 하나의 채널에서 에러가 나면 채널 전체가 닫힌다. 존재하지 않는 큐에 `checkQueue`를 하는 것만으로 채널이 죽는다. 발행용과 소비용 채널을 분리하고, 채널 `error` 이벤트에서 재생성 로직을 두거나 프로세스를 죽여 재시작에 맡긴다.

또한 `ack`를 잊은 코드는 즉시 티가 나지 않는다. prefetch만큼 메시지를 받고 나면 그 소비자는 조용히 멈춘다. 로그도 에러도 없다. 큐의 "unacked" 카운트가 prefetch 값에 붙어 움직이지 않으면 이 상황이다.

트랜잭션 안에서 메시지를 발행하지 않는다. DB 커밋은 성공했는데 발행이 실패하거나 그 반대인 경우가 반드시 생긴다. 이 문제의 표준 해법은 아웃박스 패턴(transactional outbox)이다. 도메인 변경과 같은 트랜잭션에서 `outbox` 테이블에 메시지를 INSERT하고, 별도 워커가 그 테이블을 폴링해 발행한 뒤 표시한다. 이 경우에도 "발행 후 표시 전 사망"이 있으므로 중복이 생기고, 다시 멱등성으로 돌아온다.

## 23.6 스트림 기반 메시징: Redis Streams

### 왜 필요한가

RabbitMQ의 큐는 메시지를 소비하면 사라진다. 그런데 "새로 붙는 소비자가 과거 메시지를 처음부터 다시 읽어야" 하거나, "같은 이벤트를 여러 팀이 각자의 속도로 소비"해야 하거나, "장애를 겪은 워커가 자기가 어디까지 처리했는지 알아야" 한다면 스트림이 맞다. Redis Streams는 이미 운영 중인 Redis 위에서 이 모델을 제공한다.

23.4의 채팅을 다시 구현하되, 이번에는 메시지가 로그에 남아 늦게 접속한 사용자도 최근 이력을 받을 수 있게 한다.

### 어떻게 동작하는가

기본 명령은 `XADD`(추가)와 `XREAD`(읽기)다. 각 엔트리는 `1526919030474-0` 형태의 시간 기반 ID를 자동으로 받고, 이 ID가 곧 오프셋이다.

```js
// chat/stream-basic.mjs
import { createClient } from 'redis'

const client = createClient({ url: process.env.REDIS_URL })
await client.connect()
const STREAM = 'chat:general'

// 메시지 추가. MAXLEN으로 로그가 무한히 자라지 않게 근사 트리밍한다.
export async function postMessage(user, text) {
  return client.xAdd(
    STREAM,
    '*',                                  // ID 자동 생성
    { user, text },
    { TRIM: { strategy: 'MAXLEN', strategyModifier: '~', threshold: 10_000 } }
  )
}

// 마지막으로 본 ID 이후만 블로킹으로 읽는다. 늦게 접속하면 '0'부터 읽어 이력을 받는다.
export async function* readFrom(lastId = '$') {
  let cursor = lastId
  while (true) {
    const res = await client.xRead(
      { key: STREAM, id: cursor },
      { BLOCK: 5000, COUNT: 100 }         // 5초 롱폴링
    )
    if (!res) continue                    // 타임아웃, 다시 대기
    for (const { id, message } of res[0].messages) {
      yield { id, ...message }
      cursor = id                         // 오프셋을 앞으로 민다
    }
  }
}
```

여기서 `$`는 "지금 이후의 새 메시지만", `0`은 "처음부터"를 뜻한다. 오프셋을 소비자가 들고 있다는 스트림의 성질이 그대로 드러난다. 하지만 이 방식은 소비자가 죽으면 어디까지 읽었는지 스스로 기억해야 하고, 여러 워커에게 작업을 나눠 줄 수도 없다. 그래서 소비자 그룹(consumer group)이 필요하다.

소비자 그룹은 하나의 스트림을 여러 소비자가 **나눠서** 읽게 하되(경쟁 소비자), 그룹 단위로는 모든 메시지를 소비하도록 브로커가 보장하는 구조다. 그룹은 각 메시지를 정확히 한 소비자에게 배정하고, 배정된 메시지는 소비자가 `XACK`할 때까지 펜딩 목록(Pending Entries List, PEL)에 남는다.

```js
// chat/stream-group.mjs
import { createClient } from 'redis'
import { randomUUID } from 'node:crypto'

const client = createClient({ url: process.env.REDIS_URL })
await client.connect()
const STREAM = 'chat:general'
const GROUP = 'persisters'                          // DB에 저장하는 워커 그룹
const consumer = `worker-${randomUUID().slice(0, 8)}`

// 그룹 생성(이미 있으면 무시). MKSTREAM은 스트림이 없을 때 만든다.
try {
  await client.xGroupCreate(STREAM, GROUP, '0', { MKSTREAM: true })
} catch (err) {
  if (!String(err.message).includes('BUSYGROUP')) throw err
}

async function processBatch() {
  // '>' 는 아직 아무에게도 배정되지 않은 새 메시지를 뜻한다
  const res = await client.xReadGroup(
    GROUP, consumer,
    { key: STREAM, id: '>' },
    { BLOCK: 5000, COUNT: 10 }
  )
  if (!res) return
  for (const { id, message } of res[0].messages) {
    try {
      await saveToDb(message)                       // 실제 처리
      await client.xAck(STREAM, GROUP, id)          // 처리 성공 후에만 ack
    } catch (err) {
      // ack하지 않으면 PEL에 남아 나중에 복구된다. 여기서는 그냥 넘어간다.
      console.error('처리 실패, PEL에 보존됨', id, err)
    }
  }
}

async function saveToDb(message) { /* 19장의 리포지토리 */ }

while (true) await processBatch()
```

`XACK`하지 않은 메시지는 PEL에 남는다. 소비자가 처리 도중 죽으면 그 메시지는 여전히 죽은 소비자 앞으로 배정된 상태로 남아 있다. 다른 소비자가 이를 구제하려면 펜딩 목록을 조회하고 소유권을 넘겨받아야 한다.

```js
// chat/stream-recover.mjs
// 유휴 시간이 임계값을 넘은 펜딩 메시지를 이 소비자가 넘겨받는다
export async function recoverStale(client, STREAM, GROUP, consumer, minIdleMs = 30_000) {
  // XAUTOCLAIM: 오래 방치된 펜딩 메시지를 자동으로 소유권 이전
  let cursor = '0-0'
  do {
    const res = await client.xAutoClaim(
      STREAM, GROUP, consumer, minIdleMs, cursor, { COUNT: 50 }
    )
    cursor = res.nextId
    for (const { id, message } of res.messages) {
      if (message === null) {                        // 원본이 트리밍으로 사라진 경우
        await client.xAck(STREAM, GROUP, id)         // PEL에서만 제거
        continue
      }
      try {
        await saveToDb(message)
        await client.xAck(STREAM, GROUP, id)
      } catch { /* 다음 주기에 다시 시도된다 */ }
    }
  } while (cursor !== '0-0')
}

async function saveToDb(message) { /* ... */ }
```

`XAUTOCLAIM`은 유휴 시간이 임계값을 넘은 펜딩 메시지를 찾아 현재 소비자로 소유권을 옮기고 함께 반환한다. 워커마다 이 복구 루틴을 주기적으로 돌리면, 어떤 워커가 죽어도 그가 붙들고 있던 메시지가 30초 뒤 다른 워커에게 넘어가 재처리된다. 재처리이므로 당연히 중복이 생기고, `saveToDb`는 멱등해야 한다. 원칙은 또 반복된다.

`XADD`의 `MAXLEN ~` 근사 트리밍은 성능을 위해 정확한 개수 대신 매크로 노드 경계에서 자른다. 그래서 아직 소비되지 않은(PEL에 있는) 메시지가 트리밍으로 사라질 수 있고, 위 복구 코드가 `message === null`을 다루는 이유가 그것이다.

여기서 소비자 그룹이 Pub/Sub의 팬아웃과 다르다는 점을 분명히 해야 한다. 하나의 스트림에 서로 다른 이름의 그룹을 여러 개 만들면, 각 그룹은 모든 메시지를 독립적으로 전량 수신한다(팬아웃). 반면 하나의 그룹 안에 소비자를 여러 명 두면 그 메시지들은 소비자들에게 나뉘어 분배된다(경쟁 소비). 즉 "그룹 간에는 브로드캐스트, 그룹 안에서는 분배"라는 두 층위가 한 스트림 위에 공존한다. `persisters` 그룹은 DB에 저장하고 `analytics` 그룹은 통계를 집계하도록 팀별로 그룹을 나누되, 각 그룹 내부는 부하에 맞춰 소비자 수를 조절하는 식이다. 이 조합이 큐 모델과 Pub/Sub 모델을 하나의 저장소에서 모두 표현할 수 있게 하는 스트림의 힘이다.


### Kafka와의 관계

Redis Streams의 모델은 Apache Kafka에서 그대로 가져온 것이다. 추가 전용 로그, 소비자 그룹, 오프셋, 파티션에 대응하는 개념이 모두 있다. 차이는 규모와 운영에 있다. Kafka는 파티션을 여러 브로커에 분산해 초당 수백만 메시지와 수 TB 보존을 감당하도록 설계되었고, 디스크가 진실의 원천이다. Redis Streams는 메모리 우선이라 지연이 극히 낮고 운영이 단순하지만, 데이터가 메모리에 들어가는 규모까지가 현실적인 한계다. 이미 Redis를 쓰고 있고 초당 수만 건 수준이면 Redis Streams가, 로그가 시스템의 중추이고 장기 보존과 대규모 재처리가 필요하면 Kafka가 맞다. 애플리케이션 코드의 소비자 그룹 로직은 두 시스템에서 놀랄 만큼 비슷하다.

### 실무 함정

소비자 그룹을 만들 때 시작 ID를 `$`로 주면 그룹 생성 시점 **이후** 메시지만 소비한다. 이미 쌓여 있던 메시지를 처리해야 한다면 `0`으로 만들어야 한다. 이 실수는 조용히 데이터를 건너뛰므로 발견이 늦다.

또한 PEL은 무한정 자란다. `XACK`을 빠뜨린 코드나 복구 루틴이 없는 그룹은 펜딩 목록이 계속 커져 메모리를 잠식한다. `XPENDING`으로 그룹별 펜딩 개수와 가장 오래된 펜딩의 나이를 주기적으로 관측한다.

## 23.7 작업 분배 패턴: Fanout/Fanin, 경쟁 소비자, 파이프라인

### 왜 필요한가

CPU를 오래 쓰는 작업을 이벤트 루프에서 직접 돌리면 그동안 다른 모든 요청이 막힌다(11장 참조). 이런 작업은 큐에 넣고 별도 워커 여러 대가 나눠 처리해야 한다. 예제로 해시 크래커(hash cracker)를 만든다. 주어진 MD5 해시에 대응하는 문자열을, 정해진 문자 공간을 완전 탐색해 찾는 작업이다. 순수하게 CPU 바운드이고 잘게 나눌 수 있어 작업 분배의 교과서적 예다.

### 어떻게 동작하는가

전체 탐색 공간을 접두사(prefix)별로 쪼개 각각을 하나의 작업 메시지로 만든다. 이것이 **작업 분할(fanout)**이다. 여러 워커가 같은 큐에서 작업을 꺼내 처리하는 것이 **경쟁 소비자(competing consumers)**이고, 각 워커의 결과를 한곳에 모으는 것이 **결과 취합(fanin)**이다.

RabbitMQ의 워크 큐를 쓴다. 하나의 큐에 여러 소비자를 붙이면 브로커가 메시지를 라운드로빈에 가깝게 나눠 주는데, prefetch를 1로 두면 실제로는 "먼저 손이 빈 워커가 다음 작업을 가져가는" 부하 기반 분배가 된다.

```js
// cracker/dispatch.mjs — 작업 분할(fanout)
import { connect } from '../amqp/connection.mjs'
import { randomUUID } from 'node:crypto'

const TASKS = 'crack.tasks'
const RESULTS = 'crack.results'
const CHARSET = 'abcdefghijklmnopqrstuvwxyz'

export async function dispatch(targetHash, length) {
  const conn = await connect()
  const ch = await conn.createConfirmChannel()
  await ch.assertQueue(TASKS, { durable: true })
  await ch.assertQueue(RESULTS, { durable: true })

  const jobId = randomUUID()
  // 첫 글자별로 26개의 작업으로 분할한다. 각 워커는 자기 접두사의 공간만 탐색한다.
  for (const prefix of CHARSET) {
    const task = { jobId, targetHash, length, prefix }
    ch.sendToQueue(TASKS, Buffer.from(JSON.stringify(task)), { persistent: true })
  }
  await ch.waitForConfirms()
  return { jobId, partitions: CHARSET.length }
}
```

```js
// cracker/worker.mjs — 경쟁 소비자
import { createHash } from 'node:crypto'
import { connect } from '../amqp/connection.mjs'

const TASKS = 'crack.tasks'
const RESULTS = 'crack.results'
const CHARSET = 'abcdefghijklmnopqrstuvwxyz'

const conn = await connect()
const ch = await conn.createChannel()
await ch.assertQueue(TASKS, { durable: true })
await ch.assertQueue(RESULTS, { durable: true })
await ch.prefetch(1)                  // 한 번에 작업 하나. 부하 기반 분배의 핵심.

// prefix로 시작하는 length 길이 문자열을 완전 탐색
function crack({ targetHash, length, prefix }) {
  const rest = length - prefix.length
  const total = CHARSET.length ** rest
  const buf = new Array(rest)
  for (let n = 0; n < total; n++) {
    let x = n
    for (let i = rest - 1; i >= 0; i--) { buf[i] = CHARSET[x % CHARSET.length]; x = (x / CHARSET.length) | 0 }
    const candidate = prefix + buf.join('')
    if (createHash('md5').update(candidate).digest('hex') === targetHash) return candidate
  }
  return null
}

await ch.consume(TASKS, (raw) => {
  if (raw === null) return
  const task = JSON.parse(raw.content.toString())
  const found = crack(task)
  // 결과 취합 큐로 보낸다. 못 찾았어도 "이 파티션은 끝났다"를 보고한다.
  ch.sendToQueue(RESULTS, Buffer.from(JSON.stringify({
    jobId: task.jobId, prefix: task.prefix, found
  })), { persistent: true })
  ch.ack(raw)                          // 결과를 보낸 뒤 ack. 워커가 죽으면 재분배된다.
}, { noAck: false })
```

```js
// cracker/collector.mjs — 결과 취합(fanin)
import { connect } from '../amqp/connection.mjs'

const RESULTS = 'crack.results'
const conn = await connect()
const ch = await conn.createChannel()
await ch.assertQueue(RESULTS, { durable: true })

const jobs = new Map()   // jobId → { done, total, answer }

export function trackJob(jobId, total) {
  return new Promise((resolve) => {
    jobs.set(jobId, { done: 0, total, answer: null, resolve })
  })
}

await ch.consume(RESULTS, (raw) => {
  if (raw === null) return
  const { jobId, found } = JSON.parse(raw.content.toString())
  const job = jobs.get(jobId)
  ch.ack(raw)
  if (!job) return
  job.done += 1
  if (found) job.answer = found
  // 모든 파티션이 보고했거나 답을 찾으면 완료
  if (job.answer || job.done >= job.total) {
    jobs.delete(jobId)
    job.resolve(job.answer)
  }
}, { noAck: false })
```

경쟁 소비자에서 prefetch를 1로 두는 것이 왜 중요한지 짚을 필요가 있다. prefetch가 크면 빠른 워커든 느린 워커든 똑같이 여러 작업을 미리 받아 쥔다. 그 결과 느린 워커 앞에 작업이 쌓여 대기하는 동안 빠른 워커는 일찍 손을 비운다. prefetch를 1로 두면 워커는 현재 작업을 끝내야 다음을 받으므로, 빠른 워커가 자연스럽게 더 많은 작업을 처리하는 부하 기반 분배가 성립한다. 작업 처리 시간의 편차가 클수록 이 효과가 크다.

이 구조에서 워커를 늘리는 것은 프로세스를 더 띄우는 것뿐이다. `worker.mjs`를 그대로 여러 개 실행하면 같은 큐에서 경쟁하며 작업을 나눠 가진다. 발행자도 취합기도 바뀌지 않는다.

**확장 곡선**을 보자. 작업이 순수 CPU 바운드이고 파티션이 워커 수보다 충분히 많으면, 워커를 2배로 늘릴 때 처리 시간은 대략 절반이 된다. 이 선형성은 코어 수까지만 유지된다. 8코어 머신에서 워커를 8개까지 늘리는 동안은 거의 선형이지만, 9개째부터는 코어를 두고 경쟁해 개선이 급격히 꺾인다. 여러 머신으로 워커를 흩뿌리면 다시 선형으로 돌아가는데, 이때 병목은 CPU에서 브로커 처리량과 결과 취합 지점으로 옮겨 간다. 확장의 규칙은 늘 같다. 병목은 사라지지 않고 이동한다.

파티션 수도 확장에 영향을 준다. 26개 파티션에 워커가 30개면 4개는 논다. 반대로 파티션이 워커보다 훨씬 많으면 분배가 고르고 낙오자(straggler) 문제가 줄어든다. 가장 오래 걸리는 파티션 하나가 전체 완료를 늦추므로(꼬리 지연, tail latency), 작업은 워커 수보다 넉넉하게 잘게 쪼개는 편이 좋다.

**파이프라인(pipeline)**은 작업 분배의 또 다른 형태다. 처리가 여러 단계로 나뉘고 각 단계의 특성이 다를 때, 단계마다 큐를 두고 서로 다른 수의 워커를 배치한다. 예를 들어 이미지 처리에서 다운로드(I/O 바운드) → 리사이즈(CPU 바운드) → 업로드(I/O 바운드)를 세 큐로 나누면, CPU 단계에만 워커를 많이 배치해 각 단계를 독립적으로 확장할 수 있다. 한 단계의 큐가 길어지면 그 단계가 병목임이 큐 길이로 즉시 드러난다.

파이프라인의 또 다른 장점은 부분 재시도다. 리사이즈 단계에서 실패한 작업은 다운로드를 다시 하지 않고 리사이즈 큐에서만 재처리하면 된다. 단계 사이에 큐가 있으므로 각 단계의 산출물이 다음 큐에 남아 있고, 실패는 그 지점에서 국소화된다. 반대로 한 워커가 세 단계를 통째로 처리하는 구조라면 마지막 단계의 실패가 앞의 모든 작업을 무효로 만든다. 큐 경계는 곧 재시도 경계이며, 이 성질이 긴 처리 흐름을 여러 큐로 쪼개는 강력한 근거가 된다.


### 실무 함정

취합기가 메모리에 진행 상태를 들고 있으면 취합기가 죽는 순간 그 정보가 사라진다. 위 `collector.mjs`는 예제라 `Map`을 썼지만, 실무에서는 진행 상태를 Redis나 DB에 두어야 취합기를 재시작하거나 여러 대로 늘릴 수 있다.

또한 작업이 멱등하지 않으면 경쟁 소비자 패턴이 위험하다. 워커가 결과를 보내고 ack하기 직전에 죽으면 그 작업은 다른 워커에게 재분배되어 두 번 실행된다. 해시 크래킹처럼 부작용이 없는(pure) 작업은 안전하지만, "이메일 발송"이 작업이라면 두 번 발송된다. 부작용이 있는 작업은 반드시 멱등 키로 보호한다.

또한 독약 메시지(poison message)를 조심한다. 특정 작업이 항상 워커를 죽이는 예외를 일으키면, 그 작업은 재분배될 때마다 다음 워커를 또 죽인다. 워커 풀이 이 하나의 메시지에 연쇄적으로 쓰러질 수 있다. 재시도 횟수를 메시지에 기록해 임계값을 넘으면 DLQ로 보내는 방어를 두어야 하며, 이는 신뢰성 있는 큐에서만이 아니라 작업 분배에서도 똑같이 필요하다.


## 23.8 요청/응답 패턴: 상관 식별자와 반환 주소

### 왜 필요한가

지금까지의 패턴은 모두 단방향이었다. 그런데 때로는 비동기 메시징의 이점(시간적 결합 해소, 부하 평탄화)을 누리면서도 응답을 받아야 한다. 예를 들어 API 게이트웨이가 재고 서비스에 "이 상품의 재고는?"을 묻고 답을 기다려야 하는 경우다. 이것을 브로커 위에서 구현하려면 두 가지 기계 장치가 필요하다.

- **반환 주소(reply-to)**: 요청자가 "응답은 이 큐로 보내라"를 요청 메시지에 담는다. 응답자는 이 큐가 어디인지 미리 알 필요가 없다.
- **상관 식별자(correlation ID)**: 요청자가 여러 요청을 동시에 보내면 돌아온 응답이 어느 요청의 것인지 알아야 한다. 요청마다 고유 ID를 붙이고, 응답자가 그 ID를 그대로 돌려준다.

### 어떻게 동작하는가

요청자는 자기 전용 응답 큐를 하나 만들고, 그 큐로 오는 메시지를 상관 식별자로 진행 중인 요청과 짝지어 준다. 이 로직을 재사용 가능한 클래스로 추상화한다.

```js
// messaging/request-reply.mjs
import { randomUUID } from 'node:crypto'

// 비동기 메시징 위에 요청/응답을 얹는 요청자 측 추상화
export class Requestor {
  constructor(channel) {
    this.ch = channel
    this.pending = new Map()   // correlationId → { resolve, reject, timer }
    this.replyQueue = null
  }

  async init() {
    // exclusive+autoDelete: 이 연결 전용의 익명 응답 큐. 연결이 끊기면 사라진다.
    const q = await this.ch.assertQueue('', { exclusive: true, autoDelete: true })
    this.replyQueue = q.queue

    await this.ch.consume(this.replyQueue, (raw) => {
      if (raw === null) return
      const correlationId = raw.properties.correlationId
      const entry = this.pending.get(correlationId)
      if (!entry) return                       // 이미 타임아웃된 응답. 조용히 버린다.
      clearTimeout(entry.timer)
      this.pending.delete(correlationId)
      try {
        entry.resolve(JSON.parse(raw.content.toString()))
      } catch (err) {
        entry.reject(err)
      }
    }, { noAck: true })                        // 응답은 유실돼도 요청자가 타임아웃으로 처리
  }

  request(targetQueue, payload, { timeoutMs = 5000 } = {}) {
    const correlationId = randomUUID()
    return new Promise((resolve, reject) => {
      // 응답이 영영 오지 않을 때를 대비한 타임아웃. 이것이 없으면 pending이 영원히 샌다.
      const timer = setTimeout(() => {
        this.pending.delete(correlationId)     // 반드시 정리한다
        reject(new Error(`request timeout: ${targetQueue} ${correlationId}`))
      }, timeoutMs)

      this.pending.set(correlationId, { resolve, reject, timer })

      this.ch.sendToQueue(targetQueue, Buffer.from(JSON.stringify(payload)), {
        correlationId,
        replyTo: this.replyQueue               // 반환 주소를 봉투에 담는다
      })
    })
  }
}
```

응답자 측은 요청을 처리하고, 봉투에 담긴 `replyTo`로 결과를 보내면서 `correlationId`를 그대로 돌려준다.

```js
// messaging/replier.mjs
export async function serve(channel, requestQueue, handler) {
  await channel.assertQueue(requestQueue, { durable: false })
  await channel.prefetch(10)

  await channel.consume(requestQueue, async (raw) => {
    if (raw === null) return
    const { replyTo, correlationId } = raw.properties
    let response
    try {
      const payload = JSON.parse(raw.content.toString())
      response = { ok: true, data: await handler(payload) }
    } catch (err) {
      response = { ok: false, error: err.message }   // 에러도 응답으로 되돌린다
    }
    // 반환 주소가 없으면 응답할 곳이 없다. 요청자가 이미 떠난 경우.
    if (replyTo) {
      channel.sendToQueue(replyTo, Buffer.from(JSON.stringify(response)), { correlationId })
    }
    channel.ack(raw)
  }, { noAck: false })
}
```

사용하는 쪽은 마치 평범한 함수 호출처럼 보인다.

```js
// messaging/usage.mjs
import { connect } from '../amqp/connection.mjs'
import { Requestor } from './request-reply.mjs'

const conn = await connect()
const ch = await conn.createChannel()
const requestor = new Requestor(ch)
await requestor.init()

try {
  const res = await requestor.request('inventory.query', { sku: 'A-1024' }, { timeoutMs: 3000 })
  console.log('재고:', res.data.quantity)
} catch (err) {
  console.error('재고 조회 실패, 캐시 값으로 대체', err.message)  // 타임아웃 시 폴백
}
```

### 응답이 오지 않을 때

요청/응답에서 가장 중요한 것은 **응답이 영영 오지 않는 경우의 정리**다. 응답자가 죽었거나, 응답 메시지가 유실됐거나, 처리가 타임아웃보다 오래 걸릴 수 있다. 위 코드에서 타임아웃 타이머가 두 가지 일을 한다. 요청자에게 에러를 반환하고, `pending` 맵에서 항목을 제거한다. 이 제거가 없으면 응답 없는 요청이 쌓일 때마다 맵이 커져 메모리가 샌다. 응답 큐를 `exclusive`로 만든 것도 같은 맥락이다. 요청자 연결이 끊기면 큐가 자동 삭제되어, 아무도 읽지 않는 큐에 응답이 쌓이는 것을 막는다.

여기서 근본적인 한계를 직시해야 한다. 타임아웃은 "요청이 처리되지 않았다"를 뜻하지 않는다. 요청은 성공했는데 응답만 유실됐을 수도 있다. 따라서 요청/응답 위에서 부작용이 있는 작업(예: 결제)을 할 때는, 타임아웃 후 재시도가 중복 실행을 일으키지 않도록 요청 자체에 멱등 키를 담아야 한다. 응답 유무와 무관하게 서버가 같은 키의 요청을 한 번만 반영하게 만드는 것이다. 요청/응답조차 최소 한 번 전달의 규칙에서 벗어나지 못한다.

요청/응답을 확장하면 스캐터-개더(scatter-gather)가 된다. 하나의 요청을 여러 응답자에게 뿌리고 도착하는 여러 응답을 모으는 패턴이다. 예를 들어 여러 공급사에 동시에 견적을 묻고 가장 싼 값을 고르는 경우다. 이때는 상관 식별자 하나에 여러 응답이 매핑되므로, `pending` 항목이 단일 `resolve`가 아니라 응답 수집기를 들고 있어야 한다. 그리고 모든 응답자가 답하기를 기다리면 가장 느린 응답자가 전체를 지배하므로, "N개 중 먼저 온 K개" 또는 "타임아웃 시점까지 도착한 것만"으로 완료 조건을 정한다. 느린 응답자를 기다리지 않고 부분 결과로 진행하는 결정이 스캐터-개더 설계의 핵심이다.


### 실무 함정

요청/응답을 메시징 위에 얹는 것은 가능하지만, 대부분의 동기적 요청/응답에는 그냥 HTTP나 gRPC가 낫다. 메시징 요청/응답은 지연이 브로커 왕복만큼 늘고, 디버깅이 어렵다. 이 패턴이 정당한 경우는 요청량이 폭발적이어서 큐로 완충해야 하거나, 응답자 풀을 동적으로 늘리고 줄여야 하거나, 이미 모든 통신이 브로커를 지나는 아키텍처일 때다. 그 외에는 동기 호출이 단순하고 옳다. 도구를 위해 문제를 만들지 않는다.

## 요약

- 메시징은 서비스 간 시간적·공간적 결합을 끊지만, 결합을 없애는 것이 아니라 메시지 스키마로 옮긴다. 관대한 소비자와 명시적 스키마 버전이 이 대가를 관리하는 방법이다.
- 메시지는 커맨드(하라, 수신자 1), 이벤트(일어났다, 수신자 N), 문서(데이터)로 나뉘며, 이 구분이 결합의 방향과 확장성을 결정한다.
- 큐는 소비하면 사라지고 브로커가 커서를 쥐며(작업 분배에 적합), 스트림은 로그에 남고 소비자가 오프셋을 쥔다(다중 구독·재생에 적합). 이 차이가 브로커 선택의 첫 갈림길이다.
- Redis Pub/Sub은 가볍지만 메시지를 저장하지 않아 구독자가 없으면 유실된다. 유실이 문제라면 RabbitMQ의 지속 큐나 Redis Streams처럼 저장하는 매체를 써야 한다.
- RabbitMQ는 익스체인지·큐·바인딩·라우팅 키 모델에 지속성, 발행자 확인, 수동 ack, prefetch 흐름 제어, 데드 레터 큐를 더해 신뢰성 있는 전달을 제공하고, Redis Streams는 소비자 그룹·펜딩 목록·XAUTOCLAIM으로 경쟁 소비와 장애 복구를 지원하며 Kafka와 같은 로그 모델을 더 가벼운 운영으로 제공한다.
- 작업 분배(fanout/경쟁 소비자/fanin/파이프라인)의 확장은 코어 수까지 선형이며, 병목은 사라지지 않고 CPU에서 브로커·취합 지점으로 이동한다.
- 모든 패턴을 관통하는 원칙: 정확히 한 번 전달은 없다. 최소 한 번 전달을 전제하고 소비자를 멱등하게 만드는 것이 유일하게 현실적인 정답이다(29장 참조).

## 연습문제

1. 23.4의 Redis Pub/Sub 채팅에서 특정 순간 구독자가 0명이면 메시지가 유실된다. 이 유실을 방지하도록, 메시지를 먼저 데이터베이스에 저장하고 Pub/Sub은 "새 메시지 도착" 신호로만 쓰도록 서버를 개조하라. 늦게 접속한 클라이언트가 최근 50개 메시지를 받도록 조회 엔드포인트도 추가하라.

2. 23.5의 RabbitMQ 소비자에 재시도 정책을 추가하라. 처리에 실패한 메시지를 즉시 DLQ로 보내는 대신, 지수 백오프(1초, 4초, 16초)로 최대 3회 재시도한 뒤에야 DLQ로 보내도록 만들어라. 힌트: TTL이 설정된 지연 큐(delay queue)와 데드 레터를 조합한다. 재시도 횟수는 메시지 헤더에 담아 추적하라.

3. 23.7의 해시 크래커를 계측하라. 워커를 1, 2, 4, 8개로 실행하며 동일한 6자리 해시를 크래킹하는 데 걸리는 시간을 측정하고, 워커 수 대비 처리 시간을 표로 정리하라. 실행 머신의 코어 수를 넘어설 때 곡선이 어떻게 꺾이는지, 그리고 파티션 수(현재 26)를 늘리거나 줄일 때 낙오자 문제가 어떻게 달라지는지 관찰해 설명하라.
