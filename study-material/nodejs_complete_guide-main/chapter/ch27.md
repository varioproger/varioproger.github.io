# 27장. 마이크로서비스 아키텍처

마이크로서비스는 지난 10년간 가장 많이 이야기되고 가장 자주 오용된 아키텍처다. Node.js는 프로세스가 가볍고 기동이 빠르며 HTTP 서버를 몇 줄로 띄울 수 있어 서비스를 쪼개기에 유리한 런타임이고, 그래서 필요 이상으로 쪼갠 시스템도 많이 만들어냈다.

이 장은 마이크로서비스를 권하는 장이 아니다. 모놀리스가 무엇을 잘하는지에서 시작해, 그것이 무너지는 구체적 징후를 확인하고, 분해의 기준과 통합 패턴, 데이터 소유권 문제를 차례로 다룬 뒤, 마지막에 "아직 나누지 말라"는 신호들로 끝낸다. 결론을 먼저 말하면, 분리는 조직이 감당할 수 있는 운영 역량을 이미 갖춘 뒤에 하는 선택이지 그 역량을 얻기 위한 수단이 아니다.

## 27.1 모놀리식 아키텍처의 장단점

### 모놀리스가 실제로 잘하는 것

먼저 모놀리스를 옹호하는 데서 출발하자. 하나의 배포 단위 안에 모든 기능이 들어 있는 구조는 다음 네 가지를 사실상 공짜로 제공한다.

**단일 배포.** 빌드 산출물이 하나이므로 배포 파이프라인도 하나다. 버전 조합을 고민할 필요가 없고, "어느 서비스가 어느 버전과 호환되는가"라는 질문 자체가 존재하지 않는다. 롤백은 이전 이미지로 되돌리는 한 번의 조작이다. 서비스가 여덟 개인 시스템에서 롤백은 여덟 개의 버전 조합 중 어느 지점으로 되돌릴 것인가라는 문제로 바뀐다.

**트랜잭션 일관성.** 주문을 만들고 재고를 차감하고 포인트를 적립하는 세 가지 쓰기가 하나의 데이터베이스 트랜잭션 안에 들어간다. 중간에 실패하면 전부 없던 일이 된다.

```js
// 모놀리스: 세 개의 쓰기가 하나의 트랜잭션이다
async function placeOrder(db, userId, items) {
  return db.transaction(async (tx) => {
    const order = await tx.orders.insert({ userId, items })
    await tx.inventory.decrement(items)      // 재고 부족이면 여기서 예외
    await tx.points.accrue(userId, order.total)
    return order
  })
  // 어느 단계에서 실패하든 세 테이블 모두 원래 상태로 되돌아간다
}
```

이 코드가 서비스 세 개로 갈라지면 데이터베이스가 대신 해주던 원자성이 사라진다. 27.5에서 다룰 사가(saga)와 보상 트랜잭션은 이 상실을 애플리케이션 코드로 메우려는 시도이고, 그 코드는 위 예제보다 최소 한 자릿수 이상 복잡하다.

**리팩터링 용이성.** 함수 시그니처를 바꾸면 컴파일러나 타입 체커, 최소한 전역 검색이 모든 호출 지점을 찾아준다. 변경은 하나의 커밋, 하나의 PR, 하나의 배포로 끝난다. 같은 변경이 서비스 경계를 넘으면 API 버저닝, 호환성 유지 기간, 배포 순서 조율이 필요한 몇 주짜리 과제가 된다. 경계를 넘는 리팩터링 비용은 마이크로서비스가 부과하는 가장 과소평가된 세금이다.

**디버깅 단순성.** 스택 트레이스 하나가 요청의 전체 경로를 담는다. 로컬에서 디버거를 붙이면 흐름을 끝까지 따라갈 수 있다. 분산 시스템에서 같은 일을 하려면 분산 추적(distributed tracing)과 상관관계 ID, 로그 수집 파이프라인을 먼저 구축해야 한다(31장 참조).

### 모놀리스가 무너지는 지점

그럼에도 모놀리스는 특정 규모를 넘으면 무너진다. 중요한 것은 "코드가 크다"가 아니라 아래의 구체적 징후들이다. 이 중 서너 개가 동시에 관찰될 때가 분해를 검토할 시점이다.

- **빌드와 테스트 시간의 초선형 증가.** 전체 테스트가 40분이 되면 개발자는 로컬에서 테스트를 돌리지 않는다. 피드백 루프가 끊기고 품질이 함께 내려간다.
- **배포 결합.** 한 줄짜리 문구 수정을 배포하려면 다른 팀이 머지한 검증되지 않은 변경 열 개가 함께 나간다. 배포 실패의 원인 규명이 어려워지고, 그 결과 배포 주기가 길어지며, 주기가 길어질수록 한 번에 나가는 변경량이 늘어 위험이 다시 커지는 악순환이 생긴다.
- **팀 간 충돌.** 같은 파일을 여러 팀이 고쳐 머지 충돌이 상시화된다. 릴리스 브랜치 관리에 사람을 배정하기 시작한다면 이미 늦은 신호다.
- **부분 확장 불가.** 전체 트래픽의 2%인 이미지 변환 작업이 CPU의 70%를 쓴다. 그것 때문에 인스턴스를 늘리면 나머지 코드 전부의 메모리 사본도 함께 늘어난다. 특히 Node.js에서는 이 징후가 다른 형태로도 드러나는데, CPU 집약적 작업 하나가 이벤트 루프를 막아 무관한 요청의 지연까지 끌어올린다(3장 참조).
- **장애 전파.** 부가 기능의 메모리 누수가 전체 프로세스를 재시작시킨다. 격리 단위가 프로세스뿐이므로 어떤 코드의 결함이든 모든 기능을 함께 죽인다.

### 모듈러 모놀리스라는 중간 지점

여기서 곧바로 마이크로서비스로 건너뛰는 것이 흔한 실수다. 위 다섯 징후 중 팀 간 충돌과 리팩터링 어려움은 대부분 배포 단위가 하나여서가 아니라 내부 경계가 없어서 생긴다. 모듈러 모놀리스(modular monolith)는 배포는 하나로 유지하면서 코드 안에 서비스 경계에 준하는 규율을 세우는 방식이다.

핵심 규칙은 세 가지다. 첫째, 각 모듈은 공개 인터페이스를 하나만 노출하고 다른 모듈은 그 인터페이스로만 접근한다. 둘째, 모듈은 다른 모듈의 테이블을 직접 읽거나 쓰지 않는다. 셋째, 모듈 간 호출은 동기 함수 호출이지만 인터페이스는 나중에 네트워크로 바뀌어도 견딜 형태여야 한다. 즉 인자와 반환값이 직렬화 가능해야 하고 트랜잭션 객체를 넘기지 않는다.

```js
// modules/inventory/index.js — 이 파일만이 재고 모듈의 공개 면이다
export { reserve, release, getAvailability } from './service.js'
// 내부 구현(repository, 스키마, 도메인 객체)은 절대 export 하지 않는다

// modules/orders/service.js
import * as inventory from '../inventory/index.js'

export async function placeOrder(userId, items) {
  // 재고 테이블을 직접 조회하지 않는다. 나중에 이 호출만 HTTP로 바꾸면 된다
  const reservation = await inventory.reserve(items)
  ...
}
```

경계는 도구로 강제해야 유지된다. `package.json`의 `imports` 필드나 ESLint의 임포트 제한 규칙, 또는 워크스페이스 패키지 분리로 "orders에서 inventory 내부 파일 임포트 금지"를 CI에서 실패로 만들어야 한다. 규율을 문서로만 두면 마감 직전에 무너진다.

모듈러 모놀리스의 실질적 가치는 경계를 싸게 실험할 수 있다는 데 있다. 잘못 그은 경계는 리팩터링 한 번으로 옮길 수 있다. 같은 실수를 서비스로 저지르면 두 서비스를 다시 합치거나 데이터를 이전하는 몇 달짜리 작업이 된다. 경계가 6개월간 안정적으로 유지되었다는 증거를 얻은 뒤에 그 선을 따라 프로세스를 분리하는 순서가 안전하다.

## 27.2 복잡한 애플리케이션 분해하기

### 모듈 철학의 연장선

Node.js 생태계는 처음부터 작은 모듈을 조합하는 문화 위에 있었다(1장 참조). 하나의 모듈은 하나의 일을 하고, 공개 면은 좁으며, 내부 구현은 감춘다. 서비스 분해는 이 원칙을 프로세스 경계로 끌어올린 것에 가깝다.

다만 결정적 차이가 하나 있다. 모듈 경계를 넘는 호출은 나노초 단위이고 절대 실패하지 않는다. 서비스 경계를 넘는 호출은 밀리초 단위이고 언제든 실패하며, 더 나쁘게는 성공했는지 실패했는지 알 수 없는 상태(부분 실패)가 존재한다(21장 참조). 그래서 좋은 모듈 경계가 반드시 좋은 서비스 경계인 것은 아니다. 서비스 경계는 추가로 "이 선을 넘는 호출이 드물고, 느려도 괜찮고, 실패해도 상대가 대응할 수 있는가"를 만족해야 한다.

### 분해의 네 가지 기준

**비즈니스 능력(business capability).** 가장 신뢰할 만한 1차 기준이다. 조직이 하는 일을 명사가 아니라 능력 단위로 나눈다. "사용자 테이블"이 아니라 "인증", "결제", "배송 추적", "상품 검색"이다. 기술 계층(컨트롤러 서비스, 데이터 서비스)으로 나누는 것은 거의 항상 잘못된 분해다. 그렇게 나누면 기능 하나를 바꿀 때마다 모든 서비스를 함께 고쳐야 해서, 분산의 비용은 전부 내고 독립 배포라는 이득은 하나도 얻지 못한다.

**변경 빈도.** 코드베이스에서 매주 바뀌는 부분과 2년간 손대지 않은 부분이 같은 배포 단위에 있으면, 안정적인 부분이 불안정한 부분의 배포 위험을 함께 진다. 저장소 로그로 파일별 커밋 빈도를 뽑아보면 경계 후보가 데이터로 드러난다.

```bash
# 최근 1년간 파일별 변경 횟수 — 변경 밀도가 다른 영역을 찾는다
git log --since='1 year ago' --name-only --pretty=format: \
  | grep -v '^$' | sort | uniq -c | sort -rn | head -40
```

여기에 더해 "함께 바뀌는 파일"(temporal coupling)을 보는 것이 더 유용하다. 같은 커밋에 항상 함께 등장하는 두 파일은 다른 서비스로 갈라놓으면 안 되는 후보다. 갈라놓으면 모든 변경이 두 번의 배포와 순서 조율을 요구하게 된다.

**확장 요구.** 트래픽 프로필과 자원 프로필이 근본적으로 다른 부분은 분리 가치가 크다. 초당 5만 건의 읽기를 받는 상품 조회와 하루 200건이지만 건당 30초 CPU를 쓰는 정산 배치는 같은 프로세스에 있을 이유가 없다. Node.js에서는 특히 CPU 바운드 작업이 이벤트 루프를 점유하므로 분리 효과가 크다. 다만 이 경우 서비스로 나누기 전에 워커 스레드나 별도 워커 프로세스 + 작업 큐로 해결되는지를 먼저 확인해야 한다(23장 참조). 큐로 충분한 문제를 서비스로 푸는 것은 과잉이다.

**팀 구조(콘웨이의 법칙).** "시스템을 설계하는 조직은 그 조직의 의사소통 구조를 그대로 닮은 설계를 만든다." 이 법칙은 관찰이지 권고가 아니지만, 역으로 활용할 수 있다. 원하는 아키텍처가 있다면 그에 맞게 조직을 먼저 배치하는 것이다(역 콘웨이 전략). 실무적 함의는 단순하다. 하나의 서비스는 하나의 팀이 온전히 소유해야 한다. 두 팀이 한 서비스를 공유하면 배포 조율 비용이 그대로 남고, 한 팀이 여덟 개 서비스를 운영하면 운영 부담만 여덟 배가 된다.

### 분해의 실행 순서

경계를 정했다면 한 번에 다 쪼개지 않는다. 실전에서 가장 성공률이 높은 순서는 다음과 같다.

1. 모놀리스 안에서 모듈 경계를 먼저 세우고 내부 직접 접근을 CI로 차단한다.
2. 가장 바깥쪽 잎 노드(다른 모듈에 거의 의존하지 않고, 실패해도 핵심 흐름이 유지되는 것)를 하나 고른다. 알림 발송, 리포트 생성, 이미지 처리가 전형적이다.
3. 그 하나를 분리하고 배포·모니터링·온콜까지 실제로 운영해본다. 이 과정에서 조직에 없는 역량이 드러난다.
4. 드러난 역량 공백을 메운 뒤 다음 후보로 넘어간다.

핵심 도메인(주문, 결제)부터 쪼개려는 시도는 대개 실패한다. 가장 복잡하고, 가장 많은 것과 얽혀 있으며, 실패했을 때 되돌리기가 가장 어렵기 때문이다.

## 27.3 마이크로서비스의 장점과 대가

### 얻는 것

**독립 배포.** 가장 큰 이득이자 사실상 유일하게 대체 불가능한 이득이다. 한 팀이 다른 팀의 릴리스 일정을 기다리지 않고 하루에 여러 번 배포할 수 있다. 변경 단위가 작아지므로 장애 시 원인 범위도 좁다. 다만 이 이득은 조건부다. 서비스 A를 배포할 때 서비스 B도 함께 배포해야 한다면 독립 배포는 존재하지 않고, 그것이 27.6에서 경고할 분산 모놀리스다.

**기술 이질성.** 서비스마다 다른 언어와 저장소를 고를 수 있다. 이미지 처리는 Rust로, 추천 모델 서빙은 Python으로, API 게이트웨이는 Node.js로 하는 식이다. 하지만 이 이득은 실무에서 가장 자주 과대평가된다. 언어가 늘어날 때마다 빌드 파이프라인, 보안 패치 추적, 관측성 계측 라이브러리, 채용과 온콜 로테이션이 각각 늘어난다. 명확한 성능·생태계 근거 없이 언어를 늘리는 것은 이득이 아니라 부채다.

**부분 확장.** 병목 서비스만 인스턴스를 늘린다. 자원 효율이 좋아지고, 자원 프로필이 다른 워크로드를 서로 다른 인스턴스 타입에 배치할 수 있다.

**장애 격리.** 추천 서비스가 죽어도 상품 페이지는 추천 영역만 비운 채 응답한다. 단 이 격리는 자동으로 오지 않는다. 호출 측이 타임아웃, 서킷 브레이커, 폴백을 구현했을 때만 성립한다(21장 참조). 그 구현이 없으면 격리는커녕 장애가 호출 체인을 타고 더 넓게 퍼진다.

### 잃는 것

**분산 트랜잭션의 부재.** 27.1의 `placeOrder` 예제가 세 서비스로 흩어지면 원자성이 사라진다. 2단계 커밋(2PC)은 이론적 대안이지만 코디네이터가 단일 장애점이 되고 참여자를 잠금 상태로 붙잡아 두므로 현대 서비스 아키텍처에서는 사실상 쓰이지 않는다. 남는 선택지는 결과적 일관성(eventual consistency)을 받아들이고 사가로 보상하는 것뿐이며, 그 순간 "결제는 됐는데 재고 확보는 실패한 주문"이라는 상태가 시스템에 실재하게 된다. 비즈니스가 그 상태를 정의하고 처리 절차를 갖고 있어야 한다.

**네트워크 지연과 부분 실패.** 함수 호출이 네트워크 호출이 되면 지연은 나노초에서 밀리초로 여섯 자릿수 커지고, 무엇보다 실패 양상이 달라진다. 응답이 오지 않았을 때 요청이 도달하지 못한 것인지, 처리는 됐는데 응답만 유실된 것인지 구분할 수 없다. 따라서 모든 재시도는 멱등성 키를 요구한다(21장 참조). 지연은 누적되기도 한다. p99가 50ms인 서비스 다섯 개를 순차 호출하면 전체 p99는 250ms가 아니라 그보다 나쁘다. 하나라도 느리면 전체가 느려지기 때문이다. 호출 팬아웃이 커질수록 꼬리 지연(tail latency)이 지배한다.

**관측성 비용.** 모놀리스에서 스택 트레이스 하나로 끝나던 일이 상관관계 ID 전파, 분산 추적 수집기, 중앙 로그 집계, 서비스별 대시보드와 알람으로 바뀐다(31장 참조). 이 인프라 없이 서비스를 나누면 장애가 났을 때 어느 서비스가 원인인지 특정하는 데만 몇 시간이 걸린다.

**운영 복잡도.** 서비스 개수만큼 CI 파이프라인, 배포 설정, 시크릿, 인증서, 헬스 체크, 온콜 문서가 곱해진다. 서비스 간 호출에는 인증과 인가가 필요하고(네트워크 내부라고 신뢰하면 안 된다), 스키마 변경에는 하위 호환 규약이 필요하다.

**로컬 개발 환경.** 개발자가 기능 하나를 만들려고 노트북에서 서비스 열두 개를 띄워야 한다면 생산성은 무너진다. 현실적 대안은 세 가지다. 의존 서비스를 계약 기반 스텁으로 대체하기, 개발자별 원격 네임스페이스에 배포하고 로컬에서는 담당 서비스만 트래픽 인터셉트로 연결하기, 그리고 계약 테스트(consumer-driven contract test)로 통합 테스트 의존을 줄이기다. 이 중 어느 것도 공짜가 아니며, 서비스 개수가 늘기 전에 준비되어 있어야 한다.

정리하면 마이크로서비스는 **기술적 문제가 아니라 조직적 문제의 해법**이다. 팀이 서로를 기다리느라 못 나가는 상황이 실재할 때만 그 대가가 정당화된다. 성능을 위해 서비스를 나누는 것은 대부분 잘못된 판단이다. 네트워크 왕복이 추가되므로 단일 요청의 지연은 거의 항상 나빠진다.

## 27.4 통합 패턴: API 프록시, API 오케스트레이션, 메시지 브로커

서비스를 나누면 곧바로 "클라이언트는 이 여러 서비스를 어떻게 부르는가"라는 문제가 생긴다. 세 가지 대표 패턴을 결합도와 실패 모드 관점에서 비교한다.

### API 프록시

가장 단순한 형태다. 게이트웨이가 경로를 보고 적절한 백엔드로 요청을 넘긴다. 응답을 조합하지 않고 그대로 흘려보낸다.

```js
// gateway/proxy.js — 경로 기반 라우팅 프록시
import { createServer } from 'node:http'

const routes = [
  { prefix: '/api/orders', target: 'http://orders:3000' },
  { prefix: '/api/catalog', target: 'http://catalog:3000' },
]

createServer(async (req, res) => {
  const route = routes.find((r) => req.url.startsWith(r.prefix))
  if (!route) return res.writeHead(404).end()

  const upstream = new URL(req.url, route.target)
  const controller = new AbortController()
  // 업스트림이 늦으면 게이트웨이 소켓이 무한정 쌓인다. 타임아웃은 선택이 아니다
  const timer = setTimeout(() => controller.abort(), 3000)

  try {
    const upstreamRes = await fetch(upstream, {
      method: req.method,
      // 홉 단위 헤더(connection, transfer-encoding 등)는 그대로 넘기면 안 된다
      headers: sanitize(req.headers),
      body: req.method === 'GET' || req.method === 'HEAD' ? undefined : req,
      duplex: 'half',        // 요청 본문을 스트림으로 넘길 때 필수
      signal: controller.signal,
    })
    res.writeHead(upstreamRes.status, Object.fromEntries(upstreamRes.headers))
    // 본문을 메모리에 모으지 않고 그대로 흘려보낸다 — 메모리 사용이 상수로 유지된다
    await upstreamRes.body?.pipeTo(
      new WritableStream({ write: (c) => void res.write(c), close: () => res.end() })
    )
  } catch (err) {
    // 업스트림 장애를 게이트웨이 5xx로 바꾸지 말고 502/504로 정확히 구분한다
    res.writeHead(err.name === 'AbortError' ? 504 : 502).end()
  } finally {
    clearTimeout(timer)
  }
}).listen(8080)
```

결합도는 가장 낮다. 게이트웨이는 백엔드의 응답 스키마를 알 필요가 없고, 백엔드가 스키마를 바꿔도 게이트웨이는 수정하지 않는다. 실패 모드도 단순해서 백엔드 하나의 장애는 그 경로의 요청에만 영향을 준다.

대가는 클라이언트에 전가된다. 화면 하나를 그리는 데 서비스 다섯 개를 호출해야 한다면, 그 다섯 번의 왕복을 모바일 네트워크에서 클라이언트가 감당한다. 게다가 클라이언트가 서비스 분해 구조를 알게 되므로 백엔드를 재분할할 때 클라이언트도 함께 바꿔야 한다.

### API 오케스트레이션과 BFF

오케스트레이터는 여러 서비스를 호출해 하나의 응답으로 조합한다. 이를 클라이언트 종류별로 두는 것이 BFF(Backend For Frontend) 패턴이다. 모바일 앱과 웹은 필요한 필드와 화면 구성이 다르므로 각자의 BFF를 갖는다.

```js
// bff/product-page.js — 상품 상세 화면 하나에 필요한 데이터를 조합한다
async function get(url, { timeout, signal }) {
  const ctl = new AbortController()
  const onAbort = () => ctl.abort()
  signal?.addEventListener('abort', onAbort, { once: true })
  const timer = setTimeout(() => ctl.abort(), timeout)
  try {
    const res = await fetch(url, { signal: ctl.signal })
    if (!res.ok) throw new Error(`upstream ${res.status}`)
    return await res.json()
  } finally {
    clearTimeout(timer)
    signal?.removeEventListener('abort', onAbort)
  }
}

export async function productPage(productId, { signal }) {
  // 필수 데이터와 선택 데이터를 구분하는 것이 이 패턴의 핵심이다
  const [product, reviews, recommendations] = await Promise.all([
    get(`http://catalog:3000/products/${productId}`, { timeout: 300, signal }),
    get(`http://reviews:3000/summary/${productId}`, { timeout: 200, signal })
      .catch(() => null),
    get(`http://reco:3000/for/${productId}`, { timeout: 150, signal })
      .catch(() => []),
  ])
  // product 호출이 실패하면 예외가 그대로 전파되어 502가 된다 — 의도한 동작이다
  return {
    ...product,
    reviewSummary: reviews,              // null이면 화면에서 영역을 숨긴다
    recommendations,                     // 빈 배열이면 캐러셀을 그리지 않는다
  }
}
```

여기서 중요한 설계 결정은 두 가지다. 첫째, `Promise.all`로 병렬 호출해 지연이 합이 아니라 최댓값이 되게 한다. 서비스 A의 결과가 B의 입력이 아니라면 순차 호출할 이유가 없다. 둘째, 모든 업스트림을 동등하게 다루지 않는다. 상품 정보 없이는 화면이 성립하지 않지만 추천이 없어도 화면은 그려진다. 선택적 호출에 `.catch()`로 폴백을 주는 것이 27.3에서 말한 장애 격리를 실제로 구현하는 지점이다. 폴백 없이 `Promise.all`만 쓰면 추천 서비스 하나가 죽을 때 상품 페이지 전체가 죽는다.

결합도는 중간이다. BFF는 업스트림들의 응답 스키마를 알아야 하므로 업스트림 변경이 BFF 수정을 유발한다. 대신 클라이언트는 서비스 구조로부터 완전히 격리되어, 백엔드를 다시 쪼개도 BFF 안에서만 흡수된다. 실패 모드는 팬아웃 특유의 문제를 갖는다. 업스트림 하나가 느려지면 BFF의 소켓과 메모리가 그 요청들에 묶이므로, 타임아웃과 서킷 브레이커, 동시 호출 상한(bulkhead)이 반드시 함께 있어야 한다. BFF가 조직의 새로운 병목이 되지 않으려면 소유권도 명확해야 한다. BFF는 그것을 쓰는 프런트엔드 팀이 소유하는 것이 원칙이다.

### 메시지 브로커를 통한 이벤트 기반 통합

앞의 두 패턴은 모두 동기 요청/응답이다. 호출자는 피호출자의 주소, 인터페이스, 가용성에 의존한다. 브로커를 두면 이 의존이 사라진다(23장 참조). 서비스는 "무슨 일이 일어났다"는 사실만 발행하고, 누가 그것을 소비하는지 알지 못한다.

```js
// orders/service.js — 발행 측은 소비자를 전혀 모른다
async function completeOrder(db, orderId) {
  await db.transaction(async (tx) => {
    await tx.orders.update(orderId, { status: 'completed' })
    // 아웃박스 테이블에 이벤트를 같은 트랜잭션으로 기록한다
    await tx.outbox.insert({
      type: 'order.completed',
      key: orderId,                       // 파티션 키 — 같은 주문의 순서를 보장한다
      payload: { orderId, completedAt: new Date().toISOString() },
    })
  })
  // 별도 릴레이 프로세스가 outbox를 읽어 브로커에 발행한다
}
```

여기서 아웃박스(transactional outbox) 패턴이 핵심이다. 상태 변경을 DB에 커밋하고 그다음 줄에서 브로커에 발행하면, 두 작업 사이에 프로세스가 죽었을 때 상태는 바뀌었는데 이벤트는 없는 상황이 생긴다. 반대로 발행을 먼저 하면 커밋되지 않은 사실이 세상에 알려진다. 같은 트랜잭션 안에 이벤트를 테이블로 적고 별도 릴레이가 그것을 발행하면 이 간극이 사라진다. 대신 릴레이가 발행 후 삭제 전에 죽으면 같은 이벤트가 두 번 나가므로, 소비자는 **반드시** 멱등해야 한다. 최소 1회 전달(at-least-once)은 예외가 아니라 기본 전제다.

```js
// notifications/consumer.js — 소비 측은 발행자를 모르고, 중복 수신을 전제한다
export async function onOrderCompleted(msg, { db }) {
  const { orderId } = msg.payload
  // 처리 기록을 유니크 제약으로 남겨 중복 수신을 흡수한다
  const inserted = await db.processed.insertIfAbsent({
    consumer: 'notifications',
    messageId: msg.id,
  })
  if (!inserted) return                   // 이미 처리한 메시지 — 조용히 성공 처리
  await sendEmail(orderId)
}
```

결합도는 가장 낮다. 새 소비자(예: 정산, 데이터 웨어하우스 적재)를 추가할 때 발행 측은 한 줄도 바뀌지 않는다. 소비자가 다운되어도 발행 측은 정상 동작하고, 소비자가 복구되면 밀린 메시지를 처리한다.

대가는 다른 곳에서 나타난다. 인과 관계가 코드에 드러나지 않아 "이 이메일은 왜 발송됐는가"를 추적하려면 로그와 추적에 의존해야 한다. 결과적 일관성이 사용자에게 노출되어, 주문 직후 조회하면 아직 반영 전인 상태가 보일 수 있다. 그리고 브로커 자체가 새로운 운영 대상이 된다. 컨슈머 랙(consumer lag) 모니터링, 데드 레터 큐 처리 절차, 재처리 도구가 없으면 조용히 쌓이다가 한꺼번에 터진다.

### 세 패턴의 비교

| 관점 | API 프록시 | 오케스트레이션(BFF) | 메시지 브로커 |
| --- | --- | --- | --- |
| 결합도 | 가장 낮음(주소만) | 중간(스키마 의존) | 가장 낮음(이벤트 계약만) |
| 지연 | 1홉 추가 | 최대 업스트림 지연 | 비동기(즉시 응답) |
| 주요 실패 모드 | 업스트림 5xx 전달 | 팬아웃 꼬리 지연, 부분 실패 | 중복 전달, 컨슈머 랙 |
| 필수 대비책 | 타임아웃 | 폴백·서킷 브레이커·동시성 상한 | 멱등 소비·아웃박스·DLQ |
| 적합한 용도 | 단순 라우팅, 인증·레이트 리밋 | 화면 단위 데이터 조합 | 부수 효과, 비동기 워크플로 |

실제 시스템은 셋을 함께 쓴다. 사용자 요청 경로의 읽기는 BFF로 조합하고, 쓰기 이후의 부수 효과(알림, 정산, 검색 색인 갱신)는 이벤트로 흘리며, 그 앞단에 프록시가 인증과 레이트 리밋을 담당하는 조합이 가장 흔하다. 판단 기준은 단순하다. **호출자가 결과를 지금 필요로 하면 동기, 그렇지 않으면 비동기다.** 응답에 필요 없는 작업을 동기로 호출하면 그만큼 사용자 지연과 장애 결합이 늘어난다.

## 27.5 서비스 경계 설정과 데이터 소유권

### "서비스마다 자기 DB"의 의미와 대가

마이크로서비스에서 가장 자주 인용되면서 가장 자주 지켜지지 않는 원칙이 데이터 소유권이다. 각 데이터에는 소유 서비스가 정확히 하나 있고, 다른 서비스는 소유자의 API나 소유자가 발행한 이벤트를 통해서만 그 데이터에 접근한다.

이 원칙이 필요한 이유는 캡슐화 때문이다. 스키마가 서비스 내부에 감춰져 있으면 소유 팀은 컬럼을 나누고 인덱스를 바꾸고 저장소를 통째로 교체해도 다른 팀에 영향을 주지 않는다. 스키마가 공유되는 순간 그것은 사실상 공개 API가 되고, 변경하려면 그 테이블을 읽는 모든 서비스를 찾아 함께 배포해야 한다.

공유 데이터베이스가 만드는 결합은 스키마에만 있지 않다. 한 서비스가 실행한 무거운 질의가 다른 서비스의 응답 시간을 끌어내리고, 커넥션 풀은 공유 자원이라 한쪽의 누수가 다른 쪽의 커넥션 고갈이 된다. 한쪽이 건 긴 트랜잭션의 잠금이 다른 쪽을 대기시키고, DB 장애는 모든 서비스를 동시에 중단시켜 장애 격리라는 이득을 완전히 지운다. 서비스는 나뉘었는데 데이터베이스가 하나라면 얻은 것은 배포 파이프라인 개수뿐이다.

대가도 분명하다. 저장소가 늘어나면 백업·복구 절차, 스키마 마이그레이션 도구, 커넥션 관리, 용량 계획이 서비스 수만큼 늘어난다. 무엇보다 조인이 사라진다.

### 조인이 불가능해질 때

`orders`와 `users`가 다른 서비스에 속하면 "지난달 주문 목록에 사용자 이름 붙여 보여주기"라는 평범한 요구가 갑자기 설계 문제가 된다. 선택지는 셋이다.

**API 조합.** 주문 서비스에서 주문 목록을 받고, 거기 등장한 사용자 ID를 모아 사용자 서비스에 한 번에 조회한다. 가장 단순하고 데이터가 항상 최신이다.

```js
// N+1 호출을 피한다 — 사용자 조회는 반드시 배치로 한 번만
const orders = await get('http://orders:3000/orders?month=2026-08')
const ids = [...new Set(orders.map((o) => o.userId))]
const users = await post('http://users:3000/users/batch', { ids })
const byId = new Map(users.map((u) => [u.id, u]))
const view = orders.map((o) => ({ ...o, userName: byId.get(o.userId)?.name ?? '(알 수 없음)' }))
```

한계는 명확하다. 사용자 이름으로 정렬하거나 필터링할 수 없다. 그런 질의를 하려면 사용자 서비스의 전체 데이터를 가져와야 하기 때문이다. 결과 집합이 커지면 배치 조회 자체가 무거워지고, 페이지네이션과 결합하면 정확한 총 개수를 구하기도 어려워진다.

**데이터 복제.** 주문 서비스가 사용자 이벤트를 구독해 필요한 필드(ID, 표시 이름)만 자기 저장소에 복제해 둔다. 조인이 로컬에서 가능해지고 사용자 서비스가 다운되어도 주문 조회가 동작한다. 대가는 결과적 일관성이다. 이름을 바꾼 직후의 주문 목록은 옛 이름을 보여줄 수 있다. 여기서 중요한 구분이 하나 있다. 복제한 값을 **참조용 스냅숏**으로 볼 것인가, **당시의 사실**로 볼 것인가다. 주문서에 찍힌 배송 주소는 나중에 사용자가 주소를 바꿔도 갱신되면 안 된다. 그것은 캐시가 아니라 주문 서비스가 소유한 자기 데이터다. 이 구분을 흐리면 "왜 과거 영수증의 금액이 바뀌었는가" 같은 사고가 난다.

**CQRS.** 읽기 모델을 별도로 두는 방식이다. 여러 서비스의 이벤트를 구독해 화면에 맞게 비정규화한 조회 전용 저장소를 만들고, 복잡한 조회는 거기에만 던진다. 쓰기 모델은 각 서비스가 자기 형태로 유지한다. 강력하지만 비싸다. 읽기 모델의 재구축 절차, 이벤트 누락 시의 정합성 검증, 지연 모니터링이 모두 필요하다. 검색·리포팅처럼 조회 패턴이 쓰기 패턴과 근본적으로 다른 영역에 한정해 쓰는 것이 안전하다.

### 사가와 보상 트랜잭션

분산 트랜잭션이 불가능할 때 여러 서비스에 걸친 작업의 일관성을 확보하는 방법이 사가다. 사가는 로컬 트랜잭션들의 순서 있는 나열이며, 각 단계는 자기 서비스 안에서 원자적으로 커밋된다. 어떤 단계가 실패하면 이미 커밋된 앞 단계들을 **보상 트랜잭션(compensating transaction)**으로 되돌린다.

여기서 반드시 이해해야 할 점은 보상이 롤백이 아니라는 것이다. 롤백은 그 일이 없던 것으로 만들지만, 보상은 반대 효과를 갖는 새로운 트랜잭션을 추가로 실행한다. 결제 승인의 보상은 환불이고, 그 사이의 중간 상태는 다른 관찰자에게 실제로 보였다. 즉 사가는 원자성(A)을 흉내 내되 격리성(I)은 제공하지 않는다. 이 때문에 "결제는 됐지만 재고 확보 실패로 곧 환불될 주문"이 잠시 조회되는 것을 시스템과 비즈니스가 모두 수용할 수 있어야 한다.

사가의 조율 방식은 두 가지다. **코레오그래피(choreography)**는 각 서비스가 이벤트를 듣고 다음 단계를 스스로 실행한다. 중앙 조정자가 없어 결합도가 낮지만, 전체 흐름이 어디에도 적혀 있지 않아 단계가 넷을 넘으면 추적이 어려워진다. **오케스트레이션(orchestration)**은 사가 조정자가 각 단계를 명시적으로 호출하고 실패 시 보상을 역순으로 실행한다. 흐름이 한곳에 드러나 디버깅과 상태 조회가 쉽고, 대신 조정자가 각 참여자를 알아야 한다.

```js
// 오케스트레이션 방식 사가의 골격 — 성공한 단계만 역순으로 보상한다
const steps = [
  { name: 'payment',   run: (c) => payments.authorize(c),  compensate: (c) => payments.refund(c) },
  { name: 'inventory', run: (c) => inventory.reserve(c),   compensate: (c) => inventory.release(c) },
  { name: 'shipping',  run: (c) => shipping.schedule(c),   compensate: (c) => shipping.cancel(c) },
]

async function runSaga(ctx, store) {
  const done = []
  try {
    for (const step of steps) {
      // 각 단계 실행 전후를 영속화한다. 조정자가 죽어도 재개할 수 있어야 한다
      await store.mark(ctx.sagaId, step.name, 'started')
      await step.run(ctx)                 // 요청에는 sagaId를 멱등성 키로 함께 보낸다
      await store.mark(ctx.sagaId, step.name, 'done')
      done.push(step)
    }
  } catch (err) {
    for (const step of done.reverse()) {
      // 보상 자체도 실패할 수 있다. 무한 재시도하지 말고 상한을 두고 사람에게 넘긴다
      await retryWithBackoff(() => step.compensate(ctx), { attempts: 5 })
        .catch(() => store.escalate(ctx.sagaId, step.name))
    }
    throw err
  }
}
```

이 골격에서 실무적으로 중요한 것은 세 가지다. 첫째, 사가 상태는 반드시 영속화한다. 조정자 프로세스가 2단계와 3단계 사이에서 죽으면 재기동 후 어디까지 진행됐는지 알아야 한다. 둘째, 모든 단계와 모든 보상은 멱등해야 한다. 재개와 재시도가 같은 호출을 반복하기 때문이다. 셋째, 보상이 최종적으로 실패하는 경우를 설계에 포함해야 한다. 이미 발송된 상품은 취소할 수 없다. 그런 단계는 사가의 뒤쪽에 배치하거나(되돌릴 수 없는 일은 마지막에), 사람이 개입하는 예외 처리 경로를 만들어야 한다.

## 27.6 언제 분리하지 말아야 하는가

이 장의 결론이다. 아래 신호 중 하나라도 해당하면 분리를 미루는 편이 거의 항상 낫다.

**도메인 경계가 아직 불확실하다.** 제품이 6개월 안에 방향을 바꿀 수 있다면 경계는 아직 발견되지 않은 것이다. 잘못 그은 경계는 서비스 간 수다스러운 호출로 나타나고, 그것을 고치려면 데이터 이전과 API 재설계가 동시에 필요하다. 이 시기에는 모듈러 모놀리스로 경계를 싸게 실험하는 것이 옳다.

**팀이 하나다.** 마이크로서비스가 해결하는 문제는 팀 간 조율 비용이다. 조율할 다른 팀이 없다면 얻는 것 없이 비용만 낸다. 대략적인 기준으로, 팀이 셋 미만이거나 개발자가 15명 미만이라면 배포 결합이 실제 병목일 가능성은 낮다.

**배포 자동화가 없다.** 배포에 수동 단계가 있다면 서비스 개수만큼 수동 작업이 곱해진다. 원클릭 배포, 자동 롤백, 무중단 배포가 서비스 하나에서 이미 동작하고 있어야 한다.

**관측성이 없다.** 상관관계 ID 전파, 중앙 로그, 분산 추적, 서비스별 SLO와 알람이 없는 상태에서 서비스를 나누면 장애 시 원인 서비스를 찾는 데만 몇 시간이 걸린다(31장 참조). 첫 서비스를 분리하기 전에 계측 표준을 정하고 공용 라이브러리로 만들어 두어야 한다.

**분산의 기초 대비가 없다.** 타임아웃, 재시도와 백오프, 멱등성 키, 서킷 브레이커가 코드에 없다면 서비스 간 호출은 장애 증폭기가 된다(21장 참조).

### 분산 모놀리스라는 최악의 결과

가장 나쁜 결과는 모놀리스도 마이크로서비스도 아닌 상태다. 다음 증상들이 분산 모놀리스의 진단 기준이다.

- 기능 하나를 배포하려면 여러 서비스를 정해진 순서로 함께 배포해야 한다.
- 서비스들이 같은 데이터베이스를 공유하거나 남의 테이블을 직접 읽는다.
- 한 서비스가 다운되면 다른 서비스도 전부 사용 불가가 된다.
- 서비스들이 항상 같은 커밋에서 함께 바뀐다.
- 통합 테스트를 하려면 모든 서비스를 띄워야 한다.

이 상태는 모놀리스의 결합도를 그대로 유지한 채 네트워크 지연, 부분 실패, 운영 복잡도라는 비용만 추가로 낸다. 모놀리스보다 명백히 나쁘다. 원인은 대부분 하나다. 경계가 비즈니스 능력이 아니라 기술 계층이나 기존 코드 구조를 따라 그어졌기 때문이다.

진행 중인 분해가 이 방향으로 가고 있다면 되돌리는 것이 옳은 판단이다. 서비스를 다시 합치는 것은 실패가 아니라 정보를 얻은 뒤의 정상적인 설계 수정이다. 실제로 규모 있는 조직들이 과분해된 서비스를 다시 통합한 사례는 드물지 않다. 아키텍처 결정은 한 방향으로만 흐르지 않는다.

마이크로서비스는 도착지가 아니라 특정 조건에서 선택하는 트레이드오프다. 조건은 명확하다. 여러 팀이 서로를 기다리고 있고, 도메인 경계가 안정적으로 검증되었으며, 배포 자동화와 관측성이 이미 갖춰져 있을 때다. 그 조건이 아니라면 좋은 모듈 경계를 가진 모놀리스가 더 나은 선택이다.

## 요약

- 모놀리스는 단일 배포, 트랜잭션 일관성, 저렴한 리팩터링, 단순한 디버깅을 공짜로 제공한다. 이 이득들은 분리하는 순간 전부 대가를 치르고 다시 사야 한다.
- 분해를 검토할 시점은 코드 크기가 아니라 구체적 징후로 판단한다. 빌드 시간 폭증, 배포 결합, 팀 간 충돌 상시화, 부분 확장 불가, 장애 전파가 동시에 관찰될 때다.
- 모듈러 모놀리스는 배포를 하나로 유지한 채 경계를 세우는 중간 지점이며, 잘못 그은 경계를 리팩터링 한 번으로 고칠 수 있다는 점에서 경계 실험 비용이 가장 싸다.
- 분해 기준은 비즈니스 능력, 변경 빈도, 확장 요구, 팀 구조다. 기술 계층으로 나누는 분해는 비용만 내고 독립 배포를 얻지 못한다.
- 마이크로서비스는 기술적 문제가 아니라 조직적 문제의 해법이다. 성능 향상을 이유로 나누는 것은 대개 잘못이며, 네트워크 왕복 때문에 단일 요청 지연은 오히려 나빠진다.
- 통합 패턴은 결합도와 실패 모드로 고른다. 프록시는 단순 라우팅, BFF는 화면 단위 조합(폴백과 동시성 상한 필수), 브로커는 부수 효과와 비동기 워크플로(아웃박스와 멱등 소비 필수)에 맞는다.
- 데이터 소유자는 서비스 하나여야 한다. 공유 DB는 스키마·성능·장애를 동시에 결합시켜 분리의 이득을 지운다. 조인 상실은 API 조합·데이터 복제·CQRS로 메우되 각각의 일관성 대가를 인지해야 한다.
- 사가는 원자성을 흉내 내지만 격리성은 제공하지 않는다. 보상은 롤백이 아니라 반대 효과를 내는 새 트랜잭션이며, 중간 상태는 실제로 관찰된다.
- 도메인 경계가 불확실하거나, 팀이 하나이거나, 배포 자동화나 관측성이 없다면 분리를 미룬다. 그 상태에서 나누면 모놀리스보다 나쁜 분산 모놀리스가 된다.

## 연습문제

1. 담당 중인 코드베이스에서 최근 1년치 커밋 로그를 분석해 (a) 파일별 변경 빈도와 (b) 같은 커밋에 함께 등장하는 파일 쌍의 상위 20개를 뽑아라. 이 두 지표를 근거로 서비스 경계 후보를 세 개 제안하고, 각 후보에 대해 "이 선을 넘는 호출이 드문가, 느려도 괜찮은가, 실패해도 상대가 대응 가능한가"를 검증하라. 함께 변경되는 쌍이 경계를 가로지르는 후보는 왜 위험한지 서술하라.

2. 27.4의 BFF 예제를 확장해 세 업스트림을 실제로 띄우고, 추천 서비스에만 인위적으로 2초 지연과 50% 실패율을 주입하라. (a) 폴백 없이 `Promise.all`만 쓴 버전, (b) 예제처럼 `.catch()` 폴백을 준 버전, (c) 여기에 서킷 브레이커와 동시 호출 상한을 추가한 버전 셋을 같은 부하로 비교하고, BFF의 p99 지연과 열린 소켓 수, 성공률의 차이를 측정해 각 대비책이 어느 지표를 개선했는지 설명하라.

3. 결제·재고·배송 세 단계를 갖는 사가를 오케스트레이션 방식으로 구현하되, 상태를 데이터베이스에 영속화하고 모든 단계와 보상에 멱등성 키를 적용하라. 그다음 (a) 2단계 실행 직후, (b) 보상 실행 중간 두 지점에서 조정자 프로세스를 강제 종료하고 재기동시켜, 중복 결제나 중복 환불 없이 사가가 올바른 종단 상태에 도달함을 보여라. 보상이 5회 재시도 후에도 실패하는 경우를 재현하고 그때 시스템이 남기는 기록이 사람의 개입에 충분한지 평가하라.
