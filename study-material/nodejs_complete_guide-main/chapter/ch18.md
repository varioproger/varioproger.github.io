# 18장. 실시간 애플리케이션

웹은 원래 요청과 응답의 세계다. 브라우저가 묻고 서버가 답하면 관계는 끝난다. 그러나 채팅, 알림, 대시보드, 공동 편집기, 주문 현황판처럼 "서버가 먼저 말을 거는" 요구는 끊이지 않았고, 지난 20년간의 실시간 기법은 결국 이 단방향 구조를 어떻게 우회하거나 갈아엎을 것인가에 대한 답들의 역사였다.

이 장은 그 답들을 계보 순으로 훑되, 오래된 기법은 맥락으로만 짚고 현대 Node.js(v20 LTS 이상)에서 실제로 선택지가 되는 세 가지 — Server-Sent Events, WebSocket, 그리고 그 위의 Socket.IO — 에 집중한다. 이어서 실시간의 가장 어려운 사례인 공동 편집을 다루고, 마지막으로 인스턴스가 여러 개가 되는 순간 무너지는 것들을 정리한다.

실시간 기능은 만들기는 쉽고 운영하기는 어렵다. 이 장의 절반은 그 어려운 쪽에 할애한다.

## 18.1 폴링에서 푸시로: 실시간 기법의 계보

### 왜 계보를 봐야 하는가

실시간 기법의 선택은 취향 문제가 아니라 비용 배분 문제다. 어떤 기법을 고르든 서버는 (1) 동시에 열어 둘 연결 수, (2) 메시지 한 건당 낭비되는 바이트, (3) 이벤트 발생부터 화면 갱신까지의 지연, (4) 인프라(프록시, 로드밸런서, 방화벽)의 호환성이라는 네 가지 비용을 어딘가에 지불한다. 계보를 이해한다는 것은 각 기법이 이 네 항목을 어떻게 나눠 냈는지를 이해한다는 뜻이다.

가장 먼저 나온 기법은 짧은 폴링(short polling)이다. 클라이언트가 n초마다 `GET /messages?since=...`를 던지는 방식이다. 구현이 자명하고 어떤 인프라에서도 동작하지만 대가가 크다. 폴링 간격이 곧 지연의 하한이 되고, 아무 일도 일어나지 않는 대부분의 요청이 순수한 낭비가 된다. 사용자 1만 명이 5초 간격으로 폴링하면 초당 2,000 요청이 발생하는데, 그중 유의미한 응답은 몇 건 되지 않는다. 게다가 HTTP 요청마다 쿠키와 헤더가 통째로 실려 나가므로, 페이로드가 20바이트인 이벤트를 받기 위해 1KB 남짓의 헤더를 왕복시키는 일이 흔했다.

롱 폴링(long polling), 흔히 코멧(Comet)이라 불린 기법은 이 낭비를 지연 쪽으로 옮겼다. 서버가 요청을 즉시 응답하지 않고 이벤트가 생길 때까지 붙들고 있다가 응답한 뒤, 클라이언트가 곧바로 다음 요청을 건다. 지연은 거의 0에 가까워지지만 연결은 사실상 계속 열려 있게 되고, 이벤트마다 요청-응답 사이클이 새로 발생하므로 헤더 오버헤드는 남는다. 무엇보다 "응답이 언제 올지 모르는 요청"은 중간 프록시와 로드밸런서 입장에서 타임아웃 대상이라, 60초·120초 같은 상한선과 싸우는 코드를 늘 곁들여야 했다. 롱 폴링은 오늘날 주력이 아니라 폴백(fallback) 수단으로만 의미가 있다.

Server-Sent Events(SSE)는 롱 폴링의 반복을 없앤 표준이다. 하나의 HTTP 응답을 끝내지 않고 열어 둔 채 텍스트 이벤트를 흘려보낸다. 요청은 한 번뿐이므로 헤더 오버헤드는 최초 1회로 끝나고, 이벤트 하나의 오버헤드는 `data: `라는 여섯 글자와 줄바꿈 정도다. 브라우저의 `EventSource`가 자동 재연결과 이벤트 ID 기반 이어받기를 표준으로 제공한다는 점이 결정적이다. 대신 방향은 서버→클라이언트 단방향이다.

WebSocket은 아예 HTTP를 벗어난다. HTTP 업그레이드 핸드셰이크를 한 번 거친 뒤 TCP 위에 프레임 기반 양방향 채널을 만든다. 프레임 헤더는 2~14바이트에 불과하고 지연은 TCP 왕복에 수렴한다. 대신 HTTP의 편의(캐시, 표준 인증 헤더, 압축 협상, 재연결)를 전부 잃고 직접 구현해야 한다.

### 비교표

| 기법 | 방향 | 연결 유지 | 이벤트당 오버헤드 | 지연 | 재연결 | 인프라 호환성 |
|---|---|---|---|---|---|---|
| 짧은 폴링 | C→S 요청 | 없음 | 요청+응답 헤더 전체(≈1KB+) | 폴링 간격의 절반~1배 | 자동(다음 요청) | 완전 |
| 롱 폴링 | C→S 요청 | 요청 단위 | 이벤트당 헤더 전체 | 거의 0 | 자동(다음 요청) | 대체로 양호, 타임아웃 주의 |
| SSE | S→C 단방향 | 지속 | 수 바이트 | 거의 0 | 브라우저 내장 + Last-Event-ID | 양호, 버퍼링 주의 |
| WebSocket | 양방향 | 지속 | 2~14바이트 | 거의 0 | 직접 구현 | 업그레이드 차단 환경 존재 |
| HTTP/2 서버 푸시 | — | — | — | — | — | 사실상 폐기, 사용하지 말 것 |

### 무엇을 골라야 하는가

판단 기준은 단순하다. **클라이언트가 서버로 초당 여러 번 데이터를 보내야 하는가?** 그렇지 않다면 SSE로 충분하다. 알림, 진행률 표시, 대시보드 갱신, 로그 스트리밍, LLM 토큰 스트리밍, 주문 상태 변화 — 실무에서 마주치는 실시간 요구의 대다수가 이 범주에 속한다. 클라이언트가 서버로 무언가 보낼 일은 어차피 일반 `fetch` 한 번이면 되고, 그 결과는 다시 SSE 스트림으로 흘러오면 된다.

SSE를 기본값으로 두라고 권하는 근거는 세 가지다. 첫째, 프로토콜이 텍스트 HTTP이므로 `curl`로 디버깅되고 기존 인증·미들웨어·관측 도구가 그대로 적용된다. 둘째, 재연결과 유실 복구가 브라우저 표준으로 들어 있어 직접 만들 코드가 없다. 셋째, 로드밸런서와 프록시가 그냥 HTTP 응답으로 취급하므로 배포 지형에 대한 요구가 적다.

반대로 WebSocket이 정당한 경우는 명확하다. 커서 위치나 게임 입력처럼 클라이언트→서버 방향의 고빈도 메시지가 있을 때, 바이너리 프레임이 필요할 때, 요청-응답이 아니라 진짜 대칭적 대화가 필요할 때다. 공동 편집(18.5)과 실시간 게임이 대표적이다.

한 가지 더. 계보의 다음 항목으로 WebTransport가 자주 언급된다. HTTP/3(QUIC) 위에서 신뢰성 있는 스트림과 신뢰성 없는 데이터그램을 함께 제공하며, TCP 대기열 선두 차단(head-of-line blocking)이 없다는 점이 매력이다. 다만 2026년 현재 브라우저 지원과 인프라 성숙도가 고르지 않아 실서비스의 기본 선택지는 아니다. 지연에 극도로 민감한 게임이나 미디어가 아니라면 SSE와 WebSocket 두 축으로 판단해도 충분하다.

HTTP/2 서버 푸시는 브라우저에서 제거되었으므로 후보에서 제외한다. 참고로 SSE는 HTTP/1.1에서 도메인당 6개 연결 제한에 걸리지만, HTTP/2 이상에서는 하나의 연결에 다중화되므로 이 제약이 사라진다. 오늘날 SSE를 재평가해야 하는 가장 큰 이유가 이것이다.

## 18.2 Server-Sent Events와 `EventSource` 프로토콜

### 와이어 포맷부터 본다

SSE는 놀랄 만큼 단순한 텍스트 프로토콜이다. `Content-Type: text/event-stream` 응답 본문에 UTF-8 텍스트를 흘려보내되, 빈 줄(`\n\n`)이 이벤트 하나의 끝을 표시한다. 필드는 네 개뿐이다.

```text
event: price
id: 1042
data: {"symbol":"AAPL","price":231.4}

data: 여러 줄 데이터는
data: data 필드를 반복하면 된다

retry: 5000

: 이 줄은 주석이며 하트비트로 자주 쓰인다
```

`data:`는 페이로드이고 여러 번 나오면 줄바꿈으로 이어 붙여진다. `event:`는 이벤트 이름으로, 생략하면 `message`가 된다. 클라이언트는 `es.addEventListener('price', ...)`로 이름별 구독이 가능하다. `id:`는 이벤트 식별자이고, 브라우저는 마지막으로 수신한 id를 기억해 두었다가 재연결 시 `Last-Event-ID` 요청 헤더로 되돌려 보낸다. `retry:`는 재연결 대기 시간을 밀리초로 지시한다. 콜론으로 시작하는 줄은 주석이며 아무 이벤트도 발생시키지 않는다 — 연결을 살아 있게 유지하는 하트비트로 쓰기 좋다.

이 포맷이 중요한 이유는, 서버 쪽에 라이브러리가 전혀 필요 없다는 사실을 알려 주기 때문이다. SSE 서버는 문자열을 규칙대로 쓰는 일이 전부다.

### 서버 구현

Node.js 내장 `http` 모듈만으로 구현한다. 핵심은 응답을 끝내지 않는 것, 그리고 클라이언트가 사라졌을 때 정리하는 것이다.

```js
// sse-server.mjs
import { createServer } from 'node:http'
import { randomUUID } from 'node:crypto'

// 최근 이벤트를 링 버퍼에 보관해 Last-Event-ID 복구에 사용한다
const HISTORY_LIMIT = 500
const history = []
let lastId = 0

const clients = new Set()

function publish (eventName, payload) {
  const event = { id: ++lastId, name: eventName, data: payload }
  history.push(event)
  if (history.length > HISTORY_LIMIT) history.shift()
  for (const client of clients) client.send(event)
}

function serialize ({ id, name, data }) {
  // data에 줄바꿈이 있으면 각 줄마다 data: 접두사를 붙여야 한다
  const lines = JSON.stringify(data).split('\n')
    .map((line) => `data: ${line}`).join('\n')
  return `id: ${id}\nevent: ${name}\n${lines}\n\n`
}

const server = createServer((req, res) => {
  if (req.url !== '/events') {
    res.writeHead(404).end()
    return
  }

  res.writeHead(200, {
    'Content-Type': 'text/event-stream; charset=utf-8',
    'Cache-Control': 'no-cache, no-transform',
    Connection: 'keep-alive',
    // 리버스 프록시(nginx)의 응답 버퍼링을 끈다. 18.2의 함정 참조
    'X-Accel-Buffering': 'no'
  })

  // 재연결 간격을 3초로 지시하고, 즉시 한 번 flush 한다
  res.write('retry: 3000\n\n')

  const client = {
    id: randomUUID(),
    send (event) { res.write(serialize(event)) }
  }
  clients.add(client)

  // 끊긴 구간을 이어받는다
  const since = Number(req.headers['last-event-id'] ?? 0)
  if (since > 0) {
    for (const event of history) {
      if (event.id > since) client.send(event)
    }
  }

  // 30초마다 주석 하트비트. 유휴 타임아웃과 죽은 소켓 감지를 겸한다
  const beat = setInterval(() => res.write(': keep-alive\n\n'), 30_000)

  req.on('close', () => {
    clearInterval(beat)
    clients.delete(client)
  })
})

// 데모용 이벤트 소스
setInterval(() => publish('tick', { at: Date.now(), clients: clients.size }), 1000)

server.listen(3000)
```

클라이언트는 다섯 줄이면 끝난다.

```html
<script>
  const es = new EventSource('/events')

  es.addEventListener('tick', (e) => {
    const { at, clients } = JSON.parse(e.data)
    document.querySelector('#status').textContent =
      `${new Date(at).toLocaleTimeString()} · 접속자 ${clients}명`
  })

  // onerror는 "끊겼다"는 알림일 뿐이다. 브라우저가 알아서 재연결하므로
  // 여기서 new EventSource를 다시 만들면 연결이 이중으로 생긴다
  es.onerror = () => console.warn('연결 끊김, 자동 재연결 대기 중')
</script>
```

### 유실 없이 이어받기

`EventSource`는 연결이 끊기면 `retry`로 지정된 간격 뒤 자동으로 재접속하며, 그때 마지막으로 받은 `id`를 `Last-Event-ID` 헤더에 담는다. 서버가 위 예제처럼 그 값 이후의 이벤트를 재전송하면, 사용자 입장에서 끊김은 존재하지 않은 일이 된다. 이 복구 능력이 SSE의 진짜 가치이며, WebSocket으로는 같은 것을 손으로 만들어야 한다.

다만 히스토리를 프로세스 메모리에 두면 인스턴스가 재시작되거나 다른 인스턴스로 재연결될 때 무너진다. 실서비스에서는 Redis Stream이나 이벤트 테이블처럼 공유 저장소에 커서 기반으로 보관하는 편이 낫다(18.6, 23장 참조).

### 실무 함정

가장 자주 겪는 사고는 "로컬에서는 되는데 배포하면 이벤트가 안 온다"는 증상이다. 원인은 거의 항상 중간 계층의 버퍼링이다. nginx는 기본적으로 업스트림 응답을 버퍼에 모았다가 내보내므로, 스트림이 몇 KB 쌓이기 전까지 브라우저에 아무것도 도착하지 않는다. 응답 헤더에 `X-Accel-Buffering: no`를 넣거나 location 블록에 `proxy_buffering off;`를 지정해야 한다. 압축도 같은 문제를 만든다. `compression` 미들웨어가 gzip으로 감싸면 압축 버퍼가 찰 때까지 출력이 지연되므로, `text/event-stream`은 압축 대상에서 제외하고 `Cache-Control`에 `no-transform`을 명시해 중간 CDN의 재압축도 막아야 한다.

두 번째 함정은 연결 수다. HTTP/1.1에서 브라우저는 도메인당 동시 연결을 6개로 제한하므로, 사용자가 탭 여섯 개를 열면 여섯 번째부터 아무 요청도 나가지 않는다. HTTP/2를 켜면 해결되고, 그럴 수 없다면 `BroadcastChannel`이나 `SharedWorker`로 탭 하나만 스트림을 열고 나머지에 중계하는 구조를 쓴다.

세 번째는 프록시와 로드밸런서의 유휴 타임아웃이다. 아무 데이터도 흐르지 않는 스트림은 60초쯤 뒤 조용히 끊긴다. 위 예제의 주석 하트비트가 이 문제를 막으며, 동시에 클라이언트가 사라졌을 때 `write`가 실패하도록 만들어 정리 로직을 깨운다.

마지막으로 `EventSource`는 커스텀 헤더를 지원하지 않는다. `Authorization` 헤더를 붙일 수 없으므로 인증은 쿠키에 의존해야 하며, 크로스 오리진이면 `withCredentials: true`와 서버의 `Access-Control-Allow-Credentials`가 함께 필요하다. 토큰을 쿼리스트링에 넣는 방식은 접근 로그에 그대로 남으므로 최후의 수단으로만 쓰고, 쓴다면 수명이 짧은 일회용 티켓으로 발급한다(17장 참조).

## 18.3 WebSocket API 직접 다루기

### 핸드셰이크는 HTTP다

WebSocket 연결은 평범한 HTTP GET 요청으로 시작한다. 클라이언트가 `Connection: Upgrade`, `Upgrade: websocket`, 그리고 무작위 16바이트를 base64로 인코딩한 `Sec-WebSocket-Key`를 보내면, 서버는 그 키에 고정 GUID를 이어 붙여 SHA-1 해시한 값을 `Sec-WebSocket-Accept`로 되돌려 주며 `101 Switching Protocols`로 응답한다. 그 순간부터 그 TCP 소켓 위에서는 HTTP가 아니라 WebSocket 프레임이 오간다.

이 사실이 실무에 주는 함의는 두 가지다. 첫째, 핸드셰이크 시점까지는 쿠키, `Origin`, 쿼리스트링 같은 HTTP의 모든 것을 쓸 수 있다. 인증을 붙일 자리가 바로 여기다. 둘째, 그 이후로는 HTTP가 아니므로 로드밸런서·프록시·API 게이트웨이가 명시적으로 업그레이드를 허용하도록 설정되어 있어야 한다. nginx라면 `proxy_http_version 1.1`과 `Upgrade`/`Connection` 헤더 전달이 필수다. 이 설정을 빠뜨렸을 때의 증상은 "연결이 계속 400이나 502로 실패한다"이다.

Node.js에는 WebSocket 서버가 내장되어 있지 않다. 사실상의 표준은 `ws`이며, 클라이언트 측은 Node 22부터 전역 `WebSocket`이 안정화되어 브라우저와 동일한 API를 쓸 수 있다.

### ws로 서버 만들기

기존 HTTP 서버에 얹는 형태가 실무에서 가장 흔하다. 인증 검사를 업그레이드 단계에서 수행하려면 `noServer` 모드를 쓴다.

```js
// ws-server.mjs
import { createServer } from 'node:http'
import { WebSocketServer } from 'ws'
import { verifySessionCookie } from './auth.mjs'

const server = createServer((req, res) => res.writeHead(404).end())

const wss = new WebSocketServer({
  noServer: true,
  maxPayload: 64 * 1024,          // 프레임 크기 상한. 기본값은 100MB로 너무 크다
  perMessageDeflate: false        // 텍스트가 작으면 압축이 오히려 CPU 낭비다
})

server.on('upgrade', async (req, socket, head) => {
  // 여기는 아직 HTTP다. 쿠키와 Origin을 검사할 수 있는 마지막 지점이다
  if (req.headers.origin !== 'https://app.example.com') {
    socket.write('HTTP/1.1 403 Forbidden\r\n\r\n')
    socket.destroy()
    return
  }

  const user = await verifySessionCookie(req.headers.cookie)
  if (!user) {
    socket.write('HTTP/1.1 401 Unauthorized\r\n\r\n')
    socket.destroy()
    return
  }

  wss.handleUpgrade(req, socket, head, (ws) => {
    ws.user = user
    wss.emit('connection', ws, req)
  })
})

wss.on('connection', (ws) => {
  ws.isAlive = true
  ws.on('pong', () => { ws.isAlive = true })

  ws.on('message', (raw, isBinary) => {
    if (isBinary) return ws.close(1003, 'binary not supported')

    let msg
    try {
      msg = JSON.parse(raw)
    } catch {
      return ws.close(1007, 'invalid json')   // 잘못된 페이로드
    }
    handle(ws, msg)
  })

  ws.on('error', (err) => console.error('ws error', err))
})

server.listen(3000)
```

`maxPayload`를 명시하는 것은 선택이 아니라 필수다. 기본값을 그대로 두면 악의적인 클라이언트가 거대한 프레임 하나로 프로세스 메모리를 고갈시킬 수 있다. `perMessageDeflate`도 마찬가지다. 켜면 연결마다 zlib 컨텍스트가 잡히므로, 수천 연결에서는 압축 이득보다 메모리 압박이 크다. 큰 JSON을 자주 보내는 경우에만 선택적으로 켠다.

### 하트비트로 죽은 연결 감지하기

TCP는 상대가 사라진 것을 알려 주지 않는다. 노트북 뚜껑을 덮거나 모바일 네트워크가 전환되면 FIN도 RST도 오지 않고, 서버 쪽 소켓은 몇 시간이고 "열려 있는" 상태로 남는다. 이 좀비 연결은 메모리와 구독 목록을 갉아먹으며, 사용자 한 명이 여러 번 접속한 것처럼 보이는 통계 오류를 만든다. 해결책은 프로토콜 레벨 ping/pong이다.

```js
// 30초마다 살아 있는지 확인하고, 두 주기 연속 응답이 없으면 끊는다
const interval = setInterval(() => {
  for (const ws of wss.clients) {
    if (ws.isAlive === false) {
      ws.terminate()   // close()가 아니라 terminate() — 응답을 기다리지 않는다
      continue
    }
    ws.isAlive = false
    ws.ping()
  }
}, 30_000)

wss.on('close', () => clearInterval(interval))
```

`close()`는 종료 핸드셰이크를 시도하며 상대의 응답을 기다리지만, 죽은 연결은 애초에 응답하지 않는다. 그래서 좀비를 치울 때는 `terminate()`를 써야 한다.

### 백프레셔: 느린 클라이언트가 서버를 죽인다

`ws.send()`는 동기적으로 보이지만 실제로는 커널 버퍼가 찰 때까지만 즉시 나가고, 나머지는 프로세스 메모리에 쌓인다. 초당 100건을 브로드캐스트하는데 모바일 클라이언트 한 명이 초당 10건밖에 받지 못하면, 그 차이만큼 힙이 계속 증가한다. 지표는 `ws.bufferedAmount`다.

```js
const HIGH_WATER_MARK = 1 << 20   // 1MB

function broadcast (payload) {
  const data = JSON.stringify(payload)
  for (const ws of wss.clients) {
    if (ws.readyState !== ws.OPEN) continue

    if (ws.bufferedAmount > HIGH_WATER_MARK) {
      // 따라오지 못하는 클라이언트는 끊는다. 재연결 후 스냅숏으로 복구시킨다
      ws.close(1013, 'too slow')
      continue
    }
    ws.send(data)
  }
}
```

실시간 시스템에서 느린 소비자를 다루는 전략은 세 가지뿐이다. 끊거나(위 예제), 버리거나(최신 값만 유지하는 병합 큐), 늦추거나(발행 자체를 스로틀). 무한정 버퍼링하는 네 번째 선택지는 존재하지 않는다. 주가나 커서 위치처럼 최신 값만 의미 있는 데이터라면 클라이언트별로 "보류 중인 최신 상태" 하나만 들고 있다가 버퍼가 비었을 때 보내는 병합 방식이 가장 효율적이다.

### 종료 코드와 오류 처리

WebSocket을 오래 운영해 보면 연결이 끊기는 이유를 구분해야 할 일이 반드시 생긴다. 사용자가 탭을 닫은 것인지, 네트워크가 잠깐 끊긴 것인지, 서버가 정책 위반으로 끊은 것인지에 따라 클라이언트의 재연결 정책이 달라져야 하기 때문이다. 이때 쓰는 것이 종료 코드(close code)다. 1000은 정상 종료, 1001은 페이지 이탈, 1006은 종료 프레임 없이 끊긴 비정상 종료를 뜻하며, 애플리케이션은 4000~4999 구간을 자유롭게 쓸 수 있다. 인증 만료를 4001, 다른 기기 로그인으로 인한 강제 종료를 4002처럼 정해 두면, 클라이언트는 4001에서 토큰을 갱신하고 4002에서는 재연결을 아예 포기하는 식으로 정확히 반응할 수 있다.

반대로 서버 쪽에서 반드시 지켜야 할 규칙은 모든 소켓에 `error` 리스너를 다는 것이다. `ws`의 소켓은 `EventEmitter`이므로 리스너 없는 `error` 이벤트는 프로세스를 통째로 종료시킨다. 연결 하나의 TCP 리셋이 서버 전체를 내리는 사고가 실제로 흔하다. 또한 `send()`의 완료 콜백에서 발생하는 오류, 이미 닫힌 소켓에 쓰는 경우도 같은 경로로 들어오므로 `readyState` 확인과 `error` 리스너는 세트로 다뤄야 한다.

### 인증을 어디에 붙일까

브라우저의 `WebSocket` 생성자는 커스텀 헤더를 허용하지 않는다. `Authorization: Bearer ...`를 붙일 방법이 없으므로 선택지는 셋이다.

**쿠키 방식**은 위 예제처럼 업그레이드 요청의 `Cookie` 헤더를 검증한다. 기존 세션 인프라를 그대로 쓸 수 있고 토큰이 URL에 노출되지 않는다는 점에서 동일 오리진 서비스의 기본값으로 적합하다. 단, CSRF에 해당하는 공격(CSWSH)이 성립하므로 `Origin` 헤더 검증을 반드시 함께 해야 한다. WebSocket에는 동일 출처 정책이 적용되지 않기 때문에, 이 검사를 빠뜨리면 임의의 사이트가 사용자 쿠키로 연결을 열 수 있다.

**첫 메시지 토큰 방식**은 연결은 열어 주되 인증 전에는 아무 동작도 허용하지 않고, 클라이언트가 보내는 첫 메시지의 토큰을 검증한다. 크로스 오리진이나 모바일 클라이언트에 유리하고 토큰 갱신도 자연스럽다. 대가는 "인증되지 않은 열린 소켓"이 잠시 존재한다는 점이므로, 5초 안에 인증 메시지가 오지 않으면 끊는 타이머가 필수다.

**티켓 방식**은 둘의 절충이다. 일반 HTTP API로 수명 30초짜리 일회용 티켓을 발급받아 쿼리스트링에 실어 연결하고, 서버는 티켓을 즉시 소각한다. URL에 남는 값이 곧 만료되는 일회용이라 로그 노출 위험이 낮다. 어느 방식이든 인증은 연결 시점의 스냅숏이라는 점을 기억해야 한다. 권한이 취소되어도 이미 열린 소켓은 살아 있으므로, 민감한 시스템이라면 주기적으로 세션 유효성을 재검사하고 만료 시 서버가 먼저 끊어야 한다.

## 18.4 Socket.IO: 방, 네임스페이스, 재연결

### Socket.IO는 WebSocket이 아니다

가장 흔한 오해부터 정리한다. Socket.IO는 WebSocket 구현체가 아니라 WebSocket(그리고 HTTP 롱 폴링)을 전송 수단으로 쓰는 별도의 프로토콜이다. 자체 핸드셰이크, 자체 패킷 인코딩, 자체 하트비트를 가지므로 브라우저의 `new WebSocket('wss://...')`으로는 Socket.IO 서버에 접속할 수 없다. 반드시 짝이 맞는 클라이언트 라이브러리를 써야 하며, 이것이 이 선택의 가장 큰 대가다.

그럼에도 널리 쓰이는 이유는 raw WebSocket으로 가면 반드시 직접 만들어야 하는 것들을 이미 갖고 있기 때문이다.

### 무엇을 얹어 주는가

**재연결.** 연결이 끊기면 지수 백오프에 지터를 섞어 자동으로 재시도하고, 큐에 쌓인 메시지를 복구 후 흘려보낸다. 18.3에서 손으로 만들어야 했던 코드가 설정 몇 줄로 대체된다.

**방(room)과 네임스페이스(namespace).** 방은 서버 측 논리적 그룹이다. 소켓을 `join('doc:42')` 하면 `io.to('doc:42').emit(...)`으로 그 그룹에만 보낼 수 있고, 연결이 끊기면 자동으로 빠진다. raw WebSocket에서 `Map<roomId, Set<ws>>`를 직접 관리하며 정리 누락 버그를 만드는 일을 없애 준다. 네임스페이스는 `/chat`, `/admin`처럼 하나의 연결을 논리적으로 다중화하는 채널로, 미들웨어와 인증을 채널별로 분리할 수 있다.

**확인 응답(acknowledgement).** 이벤트에 콜백을 붙이면 요청-응답 패턴을 쓸 수 있다. 상관관계 ID를 직접 붙이는 수고가 사라진다.

**폴백.** WebSocket이 차단된 환경에서 HTTP 롱 폴링으로 내려앉는다. 기업 프록시가 남아 있는 환경에서는 여전히 의미가 있지만, 이 폴백이야말로 18.6에서 스티키 세션을 강제하는 원인이기도 하다.

```js
// socketio-server.mjs
import { createServer } from 'node:http'
import { Server } from 'socket.io'
import { verifyToken } from './auth.mjs'

const httpServer = createServer()
const io = new Server(httpServer, {
  cors: { origin: 'https://app.example.com', credentials: true },
  // 폴링 폴백이 필요 없다면 꺼서 스티키 세션 요구를 줄인다
  transports: ['websocket'],
  connectionStateRecovery: {
    // 짧은 단절 동안 놓친 이벤트를 재전송하고 방 소속을 복원한다
    maxDisconnectionDuration: 2 * 60 * 1000
  }
})

const chat = io.of('/chat')

// 네임스페이스 단위 인증 미들웨어
chat.use(async (socket, next) => {
  const user = await verifyToken(socket.handshake.auth.token)
  if (!user) return next(new Error('unauthorized'))
  socket.data.user = user
  next()
})

chat.on('connection', (socket) => {
  socket.on('room:join', async (roomId, ack) => {
    if (!(await canRead(socket.data.user, roomId))) {
      return ack?.({ ok: false, error: 'forbidden' })
    }
    socket.join(`room:${roomId}`)
    ack?.({ ok: true })          // 확인 응답
  })

  socket.on('message:send', async ({ roomId, text }, ack) => {
    if (!socket.rooms.has(`room:${roomId}`)) return ack?.({ ok: false })
    const saved = await saveMessage(socket.data.user.id, roomId, text)
    // 보낸 사람을 제외한 같은 방 구성원에게 전파
    socket.to(`room:${roomId}`).emit('message:new', saved)
    ack?.({ ok: true, id: saved.id })
  })
})

httpServer.listen(3000)
```

### 대가와 판단 기준

Socket.IO를 고를 때 치르는 비용은 분명하다. 프로토콜 종속 때문에 다른 언어 클라이언트나 표준 WebSocket 도구를 붙이기 어렵고, 메시지마다 패킷 타입과 네임스페이스 식별자가 붙어 오버헤드가 커진다. 클라이언트 번들도 수십 KB 늘어난다. 메이저 버전 간 프로토콜 호환이 깨진 전례가 있어 서버와 클라이언트를 함께 올려야 하는 제약도 있다.

한 가지 더 짚어 둘 것은 `connectionStateRecovery`다. 예전의 Socket.IO는 재연결이 곧 새로운 세션이었기 때문에, 끊긴 사이의 이벤트는 사라지고 방 소속도 초기화되어 애플리케이션이 직접 재구독과 상태 복구를 해야 했다. 최근 버전이 제공하는 이 옵션은 짧은 단절 구간의 이벤트를 버퍼에 보관했다가 재전송하고 방 소속을 복원해 준다. SSE의 `Last-Event-ID`가 표준으로 제공하던 능력을 뒤늦게 따라온 셈인데, 지정한 시간을 넘긴 단절에서는 여전히 복구되지 않으므로 "복구되지 않았을 때 스냅숏을 다시 받아 가는 경로"는 어차피 만들어 두어야 한다. 실시간 애플리케이션에서 재연결 시 상태를 어떻게 되맞출 것인가는 라이브러리가 아니라 도메인이 답해야 하는 질문이다.

정리하면 이렇다. 방과 브로드캐스트가 도메인의 중심이고 팀이 재연결·그룹 관리 코드를 직접 유지보수하고 싶지 않다면 Socket.IO가 합리적이다. 반대로 공개 API로 노출할 프로토콜이거나, 다양한 언어의 클라이언트가 붙거나, 연결당 메모리를 극한까지 아껴야 한다면 `ws` 위에 필요한 만큼만 얹는 편이 낫다. 그리고 애초에 단방향이면 SSE를 다시 검토한다.

## 18.5 협업 애플리케이션 만들기: 공동 편집 예제

### 마지막 쓰기 우선이 무너지는 지점

두 사람이 같은 문서를 동시에 편집한다고 하자. 가장 단순한 구현은 편집할 때마다 문서 전체를 서버에 보내고 서버가 그대로 덮어쓰는 것이다. 이 마지막 쓰기 우선(last-write-wins) 방식은 문서 단위 잠금이 있거나 동시 편집이 사실상 없는 환경에서는 문제가 없다. 그러나 진짜 동시 편집에서는 조용히 데이터를 잃는다. A가 첫 문단을 고치고 B가 마지막 문단을 고쳤을 뿐인데, 나중에 저장한 쪽의 스냅숏이 상대의 편집을 통째로 지워 버린다. 더 나쁜 것은 아무도 오류를 보지 못한다는 점이다.

버전 번호를 붙여 충돌을 감지하는 낙관적 잠금(optimistic locking)은 데이터 손실은 막지만 사용자 경험을 망친다. 초당 여러 번 키를 누르는 편집기에서 "다른 사람이 먼저 저장했습니다. 새로고침하세요"는 답이 아니다. 문서 전체가 아니라 편집 조작(operation) 단위로 주고받아야 한다.

여기서 근본 문제가 드러난다. 편집 조작은 위치에 의존한다. A가 위치 0에 "Hello"를 삽입하는 사이 B가 위치 5의 문자를 지웠다면, B의 조작을 A의 문서에 그대로 적용할 수 없다. B가 의도한 위치 5는 A의 문서에서 이미 위치 10이기 때문이다.

### OT와 CRDT

이 문제의 해법은 크게 둘이다.

**운영 변환(Operational Transformation, OT)** 은 도착한 조작을 그동안 적용된 다른 조작들에 맞춰 변환한다. 위 예에서 B의 "위치 5 삭제"는 A 쪽에서 "위치 10 삭제"로 변환되어 적용된다. Google Docs가 쓰는 접근이며, 조작 자체는 작고 문서 크기에 비례하는 메타데이터가 없어 효율적이다. 대신 대부분의 OT 구현은 모든 조작의 순서를 정해 주는 중앙 서버를 전제하고, 변환 함수들이 만족해야 할 성질(TP1, TP2)을 모든 조작 쌍에 대해 증명해야 한다. 구현 난도가 극도로 높고, 상용 시스템에서도 미묘한 순서 조합에서 문서가 갈라지는 버그가 오래 남았다.

**충돌 없는 복제 데이터 타입(Conflict-free Replicated Data Type, CRDT)** 은 접근이 다르다. 각 문자에 전역적으로 유일하고 순서 비교가 가능한 식별자를 부여해, 조작이 어떤 순서로 도착하든 병합 결과가 같아지도록 자료구조 자체를 설계한다. 변환이 필요 없으므로 중앙 서버 없이 P2P로도 수렴하고, 오프라인 편집 후 재접속 병합이 자연스럽다. 대가는 메타데이터다. 삭제된 문자도 묘비(tombstone)로 남고 문자마다 식별자가 붙으므로 문서보다 큰 상태를 다루게 될 수 있다. 다만 Yjs 같은 현대 구현은 연속 삽입을 블록으로 묶고 가비지 컬렉션을 수행해 이 오버헤드를 실용적인 수준까지 낮췄다.

**직접 구현하지 말 것.** 이 조언은 과장이 아니다. OT의 변환 함수든 CRDT의 식별자 순서 규칙이든, 정확성이 실패하는 방식은 "예외가 던져진다"가 아니라 "두 사용자의 화면이 조용히 달라진다"이다. 검증된 라이브러리를 쓴다. 실무의 사실상 표준은 Yjs이며, Automerge가 대안이다.

### Yjs로 만드는 최소 공동 편집기

Yjs의 구조는 명료하다. `Y.Doc`이 CRDT 상태를 들고 있고, 프로바이더(provider)가 문서 간 동기화를 담당하며, 바인딩(binding)이 에디터 UI와 연결한다. 서버가 할 일은 놀랍게도 "문서 내용을 이해하는 것"이 아니라 바이너리 업데이트를 같은 방의 다른 참여자에게 중계하고 보존하는 것뿐이다.

```js
// collab-server.mjs — Yjs 업데이트를 중계하고 스냅숏을 보존한다
import { createServer } from 'node:http'
import { WebSocketServer } from 'ws'
import * as Y from 'yjs'
import { loadSnapshot, saveSnapshot } from './storage.mjs'

const wss = new WebSocketServer({ noServer: true, maxPayload: 1 << 20 })
const rooms = new Map()   // docId -> { doc, sockets:Set, dirty:boolean }

async function getRoom (docId) {
  let room = rooms.get(docId)
  if (room) return room

  const doc = new Y.Doc()
  const snapshot = await loadSnapshot(docId)
  if (snapshot) Y.applyUpdate(doc, snapshot)   // 저장된 상태 복원

  room = { doc, sockets: new Set(), dirty: false }
  doc.on('update', () => { room.dirty = true })
  rooms.set(docId, room)
  return room
}

wss.on('connection', async (ws, req) => {
  const docId = new URL(req.url, 'http://x').searchParams.get('doc')
  const room = await getRoom(docId)
  room.sockets.add(ws)

  // 신규 참여자에게 현재 상태 전체를 한 번 보낸다
  ws.send(Y.encodeStateAsUpdate(room.doc))

  ws.on('message', (data) => {
    const update = new Uint8Array(data)
    // 서버도 문서를 유지해 늦게 들어온 참여자에게 스냅숏을 줄 수 있게 한다
    Y.applyUpdate(room.doc, update)
    for (const peer of room.sockets) {
      if (peer !== ws && peer.readyState === peer.OPEN) peer.send(update)
    }
  })

  ws.on('close', () => {
    room.sockets.delete(ws)
    if (room.sockets.size === 0) {
      // 마지막 참여자가 나가면 저장하고 메모리에서 내린다
      if (room.dirty) saveSnapshot(docId, Y.encodeStateAsUpdate(room.doc))
      room.doc.destroy()
      rooms.delete(docId)
    }
  })
})

// 편집 중에도 주기적으로 저장한다. 프로세스가 죽어도 잃는 구간을 제한
setInterval(() => {
  for (const [docId, room] of rooms) {
    if (!room.dirty) continue
    room.dirty = false
    saveSnapshot(docId, Y.encodeStateAsUpdate(room.doc))
  }
}, 10_000)

const server = createServer()
server.on('upgrade', (req, socket, head) => {
  wss.handleUpgrade(req, socket, head, (ws) => wss.emit('connection', ws, req))
})
server.listen(3000)
```

클라이언트는 프로바이더와 바인딩만 연결하면 된다.

```js
// 클라이언트 — y-websocket 프로바이더 사용
import * as Y from 'yjs'
import { WebsocketProvider } from 'y-websocket'

const doc = new Y.Doc()
const provider = new WebsocketProvider('wss://api.example.com', 'doc-42', doc)
const text = doc.getText('body')

// awareness는 문서에 저장되지 않는 휘발성 상태(커서, 선택 영역, 이름)를 다룬다
provider.awareness.setLocalStateField('user', { name: '민지', color: '#e11d48' })

// 편집은 로컬 자료구조를 바꾸는 것으로 끝난다. 동기화는 프로바이더가 처리한다
text.insert(0, '안녕하세요')

text.observe(() => render(text.toString()))
```

여기서 중요한 설계 관점 하나. 커서 위치나 참여자 이름 같은 정보는 문서의 일부가 아니다. 이런 휘발성 상태를 문서 CRDT에 넣으면 편집 히스토리가 커서 이동으로 오염된다. Yjs가 awareness라는 별도 채널을 두는 이유이며, 직접 만든 프로토콜에서도 "지속되는 문서 상태"와 "현재 접속자의 순간 상태"는 반드시 분리해야 한다.

### 실무 함정

첫째, 권한 검사는 여전히 서버의 몫이다. 위 예제는 중계에 집중했지만 실제로는 업그레이드 시점에 문서 읽기·쓰기 권한을 확인해야 하고, 읽기 전용 참여자의 업데이트는 적용하지 말고 버려야 한다. CRDT는 충돌을 해결할 뿐 권한을 알지 못한다.

둘째, 보존 전략을 정해야 한다. 업데이트를 append-only 로그로 계속 쌓으면 로딩이 점점 느려지므로, 주기적으로 병합해 스냅숏 하나로 압축하는 과정이 필요하다. 셋째, 인스턴스가 여러 개면 같은 문서의 참여자가 서로 다른 서버에 붙는다. 이때 문서 단위로 인스턴스를 고정하거나 Pub/Sub으로 업데이트를 중계해야 하며, 이는 바로 다음 절의 주제다.

## 18.6 실시간 애플리케이션의 수평 확장과 스티키 세션

### 인스턴스가 둘이 되는 순간 깨지는 것

지금까지의 예제는 모두 "연결 목록이 프로세스 메모리에 있다"는 전제 위에 서 있다. 인스턴스가 하나일 때는 아무 문제가 없다. 그런데 트래픽이 늘어 인스턴스를 두 개로 늘리는 순간, 같은 방에 있는 두 사용자가 서로 다른 프로세스에 연결될 수 있다. 인스턴스 A의 `wss.clients`에는 B에 붙은 사용자가 없으므로, A가 아무리 브로드캐스트해도 그 메시지는 절반의 사용자에게만 도달한다. 증상은 "가끔 메시지가 안 온다" 또는 "새로고침하면 보인다"로 나타나며, 로컬 개발 환경에서는 절대 재현되지 않는다.

해법의 방향은 하나다. 인스턴스 간에 이벤트를 공유하는 백플레인(backplane)을 두는 것. 각 인스턴스는 자신이 발행할 메시지를 공유 버스에 던지고, 버스에서 오는 메시지를 자기 소켓들에 뿌린다. 가장 흔한 구현이 Redis Pub/Sub이며, Socket.IO는 이를 어댑터로 제공한다(23장 참조).

```js
// Socket.IO + Redis 어댑터
import { createAdapter } from '@socket.io/redis-adapter'
import { createClient } from 'redis'

const pub = createClient({ url: process.env.REDIS_URL })
const sub = pub.duplicate()   // 구독 전용 연결이 반드시 별도로 필요하다
await Promise.all([pub.connect(), sub.connect()])

io.adapter(createAdapter(pub, sub))
// 이제 io.to('room:42').emit(...)이 모든 인스턴스의 구성원에게 도달한다
```

raw `ws`를 쓴다면 같은 일을 직접 한다.

```js
// ws + Redis 백플레인
const channel = 'realtime:broadcast'
const INSTANCE_ID = process.env.HOSTNAME ?? randomUUID()

await sub.subscribe(channel, (raw) => {
  const { from, room, payload } = JSON.parse(raw)
  if (from === INSTANCE_ID) return          // 자기 발행분 반향 방지
  deliverLocally(room, payload)
})

function publish (room, payload) {
  deliverLocally(room, payload)             // 로컬은 즉시
  pub.publish(channel, JSON.stringify({ from: INSTANCE_ID, room, payload }))
}
```

Redis Pub/Sub은 fire-and-forget이라는 점을 기억해야 한다. 구독자가 잠시 끊긴 사이의 메시지는 사라진다. 유실이 허용되지 않는 도메인이라면 Redis Streams나 정식 메시지 브로커를 쓰고, 클라이언트가 재연결할 때 마지막 커서 이후를 다시 받아 가는 경로를 만들어야 한다(18.2의 `Last-Event-ID`가 정확히 이 역할이다).

### 스티키 세션이 필요한 이유와 필요 없는 경우

스티키 세션(sticky session)은 같은 클라이언트의 요청을 항상 같은 인스턴스로 보내는 로드밸런서 설정이다. WebSocket에서 이것이 필요한 이유는 흔히 오해되는 것과 다르다. 일단 연결이 수립되면 그 TCP 소켓은 특정 인스턴스에 고정되므로, 연결 유지 자체에는 스티키 설정이 필요 없다.

문제는 핸드셰이크가 여러 HTTP 요청으로 이뤄지는 경우다. Socket.IO의 기본 설정은 HTTP 롱 폴링으로 세션을 시작한 뒤 WebSocket으로 업그레이드하는데, 이 과정의 요청들이 서로 다른 인스턴스로 흩어지면 "Session ID unknown" 오류가 나며 연결이 계속 실패한다. 따라서 **폴링 폴백을 켜 두었다면 스티키 세션이 필수**이고, `transports: ['websocket']`으로 WebSocket만 쓴다면 필요 없다. 18.4의 예제가 전송 방식을 명시한 이유가 이것이다.

nginx라면 `ip_hash` 또는 `hash $cookie_sid consistent`로, 클라우드 로드밸런서라면 쿠키 기반 어피니티로 설정한다. 다만 `ip_hash`는 모바일 캐리어 NAT 뒤의 대량 사용자를 한 인스턴스에 몰아넣을 수 있어 분포가 나빠지기 쉽다. 가능하면 쿠키 기반을 쓴다.

주의할 점은 스티키가 상태 공유의 대체재가 아니라는 것이다. 스티키 세션이 있어도 A의 사용자와 B의 사용자는 여전히 다른 프로세스에 있으므로, 백플레인은 별개로 필요하다.

### 배포할 때 모든 연결이 끊긴다

무상태 HTTP 서비스의 롤링 배포는 조용하다. 진행 중인 요청 몇 개만 마무리하면 되기 때문이다. 그러나 장수 연결(long-lived connection)에서는 인스턴스 하나를 내릴 때마다 거기 붙은 수천 개의 소켓이 동시에 끊긴다. 클라이언트가 모두 즉시 재연결을 시도하면 남은 인스턴스에 순간적인 연결 폭주가 몰리고, 그 부하로 또 다른 인스턴스가 흔들리면 재연결 폭풍(thundering herd)이 연쇄한다.

대응은 세 겹이다. 첫째, 클라이언트의 재연결에 반드시 지수 백오프와 **지터(jitter)** 를 넣는다. 모두가 정확히 1초 뒤 재시도하면 폭주는 그대로 반복된다. 둘째, 서버는 종료 시 즉시 끊지 말고 점진적으로 드레이닝(draining)한다. 셋째, 종료 중임을 클라이언트에 먼저 알려 "곧 옮겨 가라"고 유도한다.

```js
// graceful-shutdown.mjs
let shuttingDown = false

process.on('SIGTERM', async () => {
  shuttingDown = true

  // 1) 로드밸런서가 신규 트래픽을 끊도록 헬스체크를 먼저 실패시킨다
  //    LB가 인지할 시간을 준 뒤에야 소켓을 건드린다
  await delay(5_000)

  // 2) 기존 연결을 초당 일정 수만 끊어 재연결을 시간축으로 분산시킨다
  const sockets = [...wss.clients]
  const BATCH = 50
  for (let i = 0; i < sockets.length; i += BATCH) {
    for (const ws of sockets.slice(i, i + BATCH)) {
      // 1012 = Service Restart. 클라이언트가 의도된 재연결로 해석한다
      ws.close(1012, 'server restarting')
    }
    await delay(1_000)
  }

  server.close(() => process.exit(0))
})

// 종료 중에는 신규 업그레이드를 거절한다
server.on('upgrade', (req, socket, head) => {
  if (shuttingDown) {
    socket.write('HTTP/1.1 503 Service Unavailable\r\n\r\n')
    return socket.destroy()
  }
  // ...
})
```

여기서 자주 놓치는 지점이 첫 단계의 지연이다. `SIGTERM`을 받자마자 소켓을 끊으면, 로드밸런서가 아직 이 인스턴스를 정상으로 알고 있어서 재연결한 클라이언트를 죽어 가는 인스턴스로 다시 보낸다. 헬스체크를 먼저 실패시키고 LB의 확인 주기만큼 기다린 뒤 끊어야 한다. 쿠버네티스라면 `preStop` 훅과 `terminationGracePeriodSeconds`를 드레이닝 시간보다 넉넉히 잡아야 하며, 그러지 않으면 드레이닝 도중 `SIGKILL`을 맞는다.

마지막으로 용량 계획의 관점 하나. 연결 하나는 요청 하나보다 훨씬 오래 살고 메모리를 상주시킨다. `ws` 기준으로 연결당 수십 KB 수준이지만, `perMessageDeflate`를 켜면 배 이상으로 뛴다. 인스턴스당 최대 연결 수를 측정해 두고, 파일 디스크립터 한계(`ulimit -n`)와 함께 오토스케일 지표를 CPU가 아니라 **동시 연결 수**로 잡아야 한다. 실시간 서비스에서 CPU 기반 오토스케일링은 거의 언제나 잘못된 신호를 준다.

## 요약

- 실시간 기법의 선택은 연결 수, 이벤트당 오버헤드, 지연, 인프라 호환성이라는 네 가지 비용의 배분 문제다. 짧은 폴링과 롱 폴링은 역사적 맥락과 폴백으로만 의미가 있다.
- 클라이언트→서버 고빈도 메시지가 없다면 SSE가 기본값이다. 표준 HTTP이므로 기존 인증·관측 도구가 그대로 쓰이고, 자동 재연결과 `Last-Event-ID` 기반 유실 복구가 브라우저에 내장되어 있다.
- SSE의 대표적 실패는 프록시 버퍼링과 압축이다. `X-Accel-Buffering: no`, `proxy_buffering off`, `text/event-stream` 압축 제외, 주기적 주석 하트비트를 기본 세트로 적용한다.
- WebSocket을 직접 다룰 때는 `maxPayload` 제한, ping/pong 하트비트와 `terminate()`, `bufferedAmount` 기반 백프레셔 처리가 필수다. 무한정 버퍼링이라는 선택지는 없다 — 끊거나, 병합해 버리거나, 스로틀한다.
- WebSocket 인증은 업그레이드 시점의 쿠키 검증(+ `Origin` 검사로 CSWSH 방어), 첫 메시지 토큰, 단명 티켓 중 하나를 고른다. 인증은 연결 시점의 스냅숏이므로 장수 연결은 주기적 재검증이 필요하다.
- 공동 편집에서 마지막 쓰기 우선은 조용히 데이터를 잃는다. OT와 CRDT의 차이를 이해하되 직접 구현하지 말고 Yjs 같은 검증된 라이브러리를 쓰며, 지속 상태와 커서 같은 휘발성 상태(awareness)를 분리한다.
- 인스턴스가 둘 이상이면 Redis Pub/Sub 같은 백플레인이 필요하다. 스티키 세션은 폴링 폴백을 쓸 때만 필수이며 백플레인의 대체재가 아니다. 배포 시에는 헬스체크 선행 실패 → 점진적 드레이닝 → 지터 있는 재연결로 재연결 폭풍을 막는다.

## 연습문제

1. 18.2의 SSE 서버는 히스토리를 프로세스 메모리에 보관한다. 인스턴스가 재시작되거나 다른 인스턴스로 재연결되어도 `Last-Event-ID` 복구가 동작하도록 Redis Streams(또는 단조 증가 ID를 가진 이벤트 테이블)를 사용하도록 고쳐 보라. 이벤트 ID의 유일성과 순서를 어떻게 보장할 것인지, 그리고 히스토리 보존 기간을 넘어선 재연결 요청에 서버가 어떻게 응답해야 하는지를 함께 설계하라.

2. 18.3의 브로드캐스트는 느린 클라이언트를 끊어 버린다. 이를 병합(coalescing) 방식으로 바꿔 보라. 클라이언트마다 "아직 보내지 못한 최신 상태" 하나만 유지하다가 `bufferedAmount`가 0이 되면 전송하는 구조를 만들고, 대시보드처럼 최신 값만 의미 있는 데이터와 채팅처럼 모든 메시지가 의미 있는 데이터에서 각각 어떤 전략이 옳은지 설명하라.

3. 18.5의 Yjs 중계 서버를 인스턴스 두 개로 확장하라. 같은 문서의 참여자가 서로 다른 인스턴스에 연결되어도 편집이 수렴해야 한다. Redis Pub/Sub으로 바이너리 업데이트를 중계하는 방식과, 문서 ID를 해시해 특정 인스턴스로 라우팅하는 방식(문서 단위 어피니티)을 각각 구현하고, 스냅숏 저장 중복·업데이트 유실·인스턴스 추가 시 재배치라는 세 가지 관점에서 두 방식을 비교하라.
