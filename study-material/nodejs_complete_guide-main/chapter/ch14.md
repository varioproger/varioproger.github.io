# 14장. 행위 패턴

구조 패턴(13장 참조)이 객체를 어떻게 조립하느냐를 다뤘다면, 행위 패턴(behavioral pattern)은 조립된 객체들이 어떻게 협력하고 어떤 순서로 일을 처리하느냐를 다룬다. 알고리즘을 갈아 끼우고, 상태에 따라 행동을 바꾸고, 컬렉션을 순회하고, 요청을 파이프라인에 흘려보내고, 작업 자체를 객체로 만드는 다섯 가지 관심사가 여기에 모인다.

이 장이 다른 언어의 패턴 카탈로그와 갈라지는 지점은 JavaScript가 이 패턴들 중 상당수를 **언어 차원에서 이미 흡수했다**는 사실이다. 이터레이터는 프로토콜이 되었고, 제너레이터는 이터레이터를 문법으로 대체했으며, 일급 함수는 전략 패턴에서 클래스 계층을 지워버렸다. 그래서 이 장은 패턴의 이름을 외우는 장이 아니라, 언어가 제공하는 것과 직접 만들어야 하는 것의 경계를 긋는 장이다.

특히 14.6~14.7의 비동기 이터레이터는 Node.js v20 이후 실무에서 가장 자주 쓰이는 도구이며, 14.8의 미들웨어는 Express와 Koa를 포함한 거의 모든 Node.js 프레임워크의 뼈대다.

## 14.1 전략(Strategy): 다중 포맷 설정 객체

### 문제 상황

설정 파일을 읽고 쓰는 `Config` 클래스를 만든다고 하자. 처음에는 JSON만 지원하면 충분했다. 그런데 레거시 서비스가 INI를 쓰고, 쿠버네티스 매니페스트와 CI 설정은 YAML이며, 어떤 팀은 `.env` 형식을 요구한다. 순진하게 확장하면 이렇게 된다.

```js
class Config {
  async load(filePath) {
    const data = await readFile(filePath, 'utf8')
    const ext = extname(filePath)
    if (ext === '.json') {
      this.data = JSON.parse(data)
    } else if (ext === '.ini') {
      this.data = parseIni(data)
    } else if (ext === '.yaml' || ext === '.yml') {
      this.data = parseYaml(data)
    } else {
      throw new Error(`지원하지 않는 형식: ${ext}`)
    }
  }
  // save()에도 똑같은 분기가 한 벌 더 생긴다
}
```

문제는 세 가지다. 첫째, 포맷을 추가할 때마다 `Config` 자체를 수정해야 한다(개방-폐쇄 원칙 위반). 둘째, `load`와 `save`에 동일한 분기가 중복된다. 셋째, JSON만 쓰는 애플리케이션도 YAML 파서를 함께 로드해야 한다.

### 패턴의 정의

**전략 패턴**은 알고리즘군(family of algorithms)을 각각 별도의 객체로 캡슐화하고, 이들을 런타임에 교체할 수 있게 만든다. 등장인물은 둘이다.

- **컨텍스트(context)**: 공통 로직을 담당하는 객체. 여기서는 `Config`. 파일을 읽고 쓰고, 키를 조회하고 설정하는 일은 포맷과 무관하다.
- **전략(strategy)**: 가변적인 부분만 구현하는 객체. 여기서는 `{ parse, stringify }` 인터페이스를 만족하는 직렬화기(serializer).

컨텍스트는 전략을 **합성(composition)**으로 보유한다. 이것이 상속으로 문제를 푸는 템플릿 패턴(14.3)과의 결정적 차이다.

### 구현 코드

먼저 전략들을 정의한다. 각 전략은 `parse(text) → object`와 `stringify(object) → text` 두 함수만 제공하면 된다.

```js
// strategies.js
import ini from 'ini'
import { parse as parseYaml, stringify as stringifyYaml } from 'yaml'

export const jsonStrategy = {
  parse: (text) => JSON.parse(text),
  stringify: (obj) => JSON.stringify(obj, null, 2)
}

export const iniStrategy = {
  parse: (text) => ini.parse(text),
  stringify: (obj) => ini.stringify(obj)
}

export const yamlStrategy = {
  parse: (text) => parseYaml(text),
  stringify: (obj) => stringifyYaml(obj)
}
```

컨텍스트는 전략을 생성자 주입으로 받는다.

```js
// config.js
import { readFile, writeFile } from 'node:fs/promises'

export class Config {
  #data = {}
  #strategy

  constructor(strategy) {
    if (typeof strategy?.parse !== 'function' ||
        typeof strategy?.stringify !== 'function') {
      throw new TypeError('전략은 parse와 stringify를 모두 제공해야 한다')
    }
    this.#strategy = strategy
  }

  get(path) {
    // 'server.port' 같은 점 표기 경로를 지원한다
    return path.split('.').reduce((acc, key) => acc?.[key], this.#data)
  }

  set(path, value) {
    const keys = path.split('.')
    const last = keys.pop()
    const target = keys.reduce((acc, key) => (acc[key] ??= {}), this.#data)
    target[last] = value
    return this
  }

  async load(filePath) {
    const text = await readFile(filePath, 'utf8')
    this.#data = this.#strategy.parse(text)   // 가변 지점 1
    return this
  }

  async save(filePath) {
    const text = this.#strategy.stringify(this.#data)  // 가변 지점 2
    await writeFile(filePath, text)
    return this
  }
}
```

사용하는 쪽은 이렇다.

```js
const jsonCfg = await new Config(jsonStrategy).load('./config.json')
console.log(jsonCfg.get('server.port'))

// 같은 데이터를 다른 포맷으로 내보내는 일이 거저 된다
const yamlCfg = new Config(yamlStrategy)
yamlCfg.set('server.port', 8080).set('server.host', '0.0.0.0')
await yamlCfg.save('./config.yaml')
```

포맷 변환기가 공짜로 따라온다는 점에 주목하자. `Config`는 코드 한 줄도 바뀌지 않았는데 JSON을 읽어 YAML로 저장할 수 있다.

### JavaScript다운 방식: 객체 맵으로 등록하기

고전 카탈로그에서는 전략마다 클래스를 만들고 인터페이스를 상속시킨다. JavaScript에서는 그럴 이유가 없다. 전략은 그냥 **객체이거나 함수**이며, 전략의 집합은 그냥 **객체 맵**이다.

```js
// registry.js
const strategies = new Map([
  ['.json', jsonStrategy],
  ['.ini', iniStrategy],
  ['.yaml', yamlStrategy],
  ['.yml', yamlStrategy]
])

export function registerStrategy(ext, strategy) {
  strategies.set(ext, strategy)   // 외부에서 확장 가능하다
}

export function createConfig(filePath) {
  const ext = extname(filePath).toLowerCase()
  const strategy = strategies.get(ext)
  if (!strategy) {
    throw new Error(`지원하지 않는 형식: ${ext} (등록된 형식: ${[...strategies.keys()].join(', ')})`)
  }
  return new Config(strategy)
}
```

이제 서드파티가 TOML 지원을 추가하려면 `Config`를 건드릴 필요 없이 `registerStrategy('.toml', tomlStrategy)`만 호출하면 된다. `if/else` 사슬이 데이터로 바뀌었고, 데이터는 런타임에 확장할 수 있다.

전략의 인터페이스가 메서드 하나뿐이라면 객체조차 필요 없다. 함수 자체가 전략이다. 정렬 비교자, 재시도 백오프 계산기, 로드 밸런서의 노드 선택 알고리즘이 모두 이 형태이며, 이때 전략 맵은 `{ fixed: (n) => 1000, exponential: (n) => 2 ** n * 100 }` 같은 평범한 객체가 된다.

`Array.prototype.sort(comparator)`, `array.map(fn)`은 언어에 내장된 전략 패턴이다. 우리가 매일 쓰면서 패턴이라고 부르지 않을 뿐이다.

### 실전 사례

- **Passport**: 인증 방식(로컬, OAuth, JWT, SAML)을 전략으로 캡슐화한 대표 사례다. `passport.use(new LocalStrategy(...))`라는 API 자체가 패턴 이름을 그대로 쓴다.
- **HTTP 압축 협상**: `Accept-Encoding` 헤더를 보고 gzip/brotli/deflate 중 하나를 고르는 코드는 전략 맵으로 쓰는 것이 자연스럽다.
- **데이터베이스 드라이버 추상화**: 동일한 리포지토리 인터페이스 아래에 PostgreSQL 전략과 인메모리 전략을 두면, 테스트에서 DB 없이 도는 스위트를 만들 수 있다.
- **직렬화 포맷 협상**: JSON, MessagePack, Protobuf를 콘텐츠 협상 결과에 따라 교체한다.

### 언제 쓰지 말아야 하는가

- **전략이 사실상 하나이고 늘어날 계획이 없을 때.** 미래의 확장을 상상해 만든 전략 인터페이스는 대개 실제 두 번째 전략이 등장하는 순간 맞지 않아 다시 설계된다. 두 번째 구현이 나타난 뒤에 추출하는 편이 낫다.
- **전략이 컨텍스트의 내부 상태에 깊이 의존할 때.** 전략에 컨텍스트 전체를 넘겨야 한다면(`strategy.run(this)`) 캡슐화가 이미 깨진 것이고, 그것은 전략이 아니라 잘못 분리된 메서드다.
- **분기가 알고리즘이 아니라 데이터 차이일 때.** 세 포맷의 차이가 구분자 문자 하나뿐이라면 전략 객체 셋보다 설정값 하나가 옳다.

## 14.2 상태(State): 페일세이프 소켓 구현

### 문제 상황

원격 로그 수집기로 TCP 소켓을 통해 메시지를 보내는 클라이언트를 만든다. 수집기는 배포 중이거나 네트워크 사정으로 종종 끊긴다. 요구사항은 이렇다. 연결이 살아 있으면 즉시 전송하고, 끊겨 있으면 메시지를 버리지 말고 큐에 쌓았다가 재연결되면 순서대로 흘려보낸다. 호출하는 쪽은 `socket.send(msg)` 한 줄만 알면 된다.

플래그로 구현하면 이런 코드가 된다.

```js
send(data) {
  if (this.connected && !this.connecting && !this.closing) {
    this.socket.write(data)
  } else if (!this.closing) {
    this.queue.push(data)
    if (!this.connecting) this.connect()
  }
}
```

불리언 플래그 세 개는 여덟 가지 조합을 만들지만 유효한 조합은 셋뿐이다. 나머지 다섯은 언젠가 실제로 발생하는 버그다.

### 패턴의 정의

**상태 패턴**은 전략 패턴의 특수한 형태다. 전략을 외부에서 주입받는 대신, **컨텍스트가 자신의 상태 변화에 따라 스스로 전략을 교체한다**. 유효한 상태 집합이 코드에 명시되고, 상태 전이가 한곳에 모이며, 각 상태에서의 행동이 서로 격리된다.

전이 다이어그램을 먼저 그리면 구현이 자명해진다.

```text
                    connect() 호출
   ┌──────────┐    ─────────────▶   ┌────────────┐
   │ OFFLINE  │                     │ CONNECTING │
   │ (큐잉)   │  ◀─────────────      │            │
   └──────────┘   'error'/'close'   └────────────┘
        ▲                                  │
        │                                  │ 'connect'
        │ 'close' / 'error'                ▼
        │                            ┌──────────┐
        └────────────────────────────│  ONLINE  │
                                     │ (즉시 전송)│
                                     └──────────┘
                                          │ end()
                                          ▼
                                     ┌──────────┐
                                     │  CLOSED  │ (종단 상태)
                                     └──────────┘

상태별 send() 동작
  OFFLINE   : 큐에 적재 + 재연결 시도
  CONNECTING: 큐에 적재 (중복 연결 금지)
  ONLINE    : socket.write() 즉시 전송
  CLOSED    : 예외 발생
```

### 구현 코드

각 상태를 `send`와 `activate`를 가진 객체로 만든다. `activate`는 그 상태에 진입할 때 한 번 실행되는 훅이다.

```js
// failsafe-socket.js
import { EventEmitter } from 'node:events'
import net from 'node:net'

class OfflineState {
  constructor(socket) { this.socket = socket }

  send(data) {
    this.socket.queue.push(data)   // 버리지 않고 쌓는다
  }

  activate() {
    const reconnect = () => {
      this.socket.emit('reconnecting')
      this.socket.changeState('connecting')
    }
    // 지수 백오프로 재연결한다. unref()로 이 타이머가 프로세스를 붙잡지 않게 한다
    this.timer = setTimeout(reconnect, this.socket.nextDelay()).unref()
  }

  deactivate() { clearTimeout(this.timer) }
}

class ConnectingState {
  constructor(socket) { this.socket = socket }

  send(data) {
    this.socket.queue.push(data)   // 연결 중에도 잃지 않는다
  }

  activate() {
    const conn = net.createConnection(this.socket.options)
    this.conn = conn

    conn.once('connect', () => {
      this.socket.connection = conn
      this.socket.resetDelay()
      this.socket.changeState('online')
    })
    conn.once('error', (err) => {
      this.socket.emit('warning', err)      // 실패는 치명적이지 않다
      this.socket.changeState('offline')
    })
  }

  deactivate() {
    this.conn.removeAllListeners('connect')
  }
}

class OnlineState {
  constructor(socket) { this.socket = socket }

  send(data) {
    this.socket.connection.write(data)
  }

  activate() {
    const conn = this.socket.connection
    // 진입 즉시 밀린 큐를 순서대로 비운다
    while (this.socket.queue.length > 0) {
      conn.write(this.socket.queue.shift())
    }
    const fail = (err) => {
      if (err) this.socket.emit('warning', err)
      this.socket.connection = null
      this.socket.changeState('offline')
    }
    conn.once('error', fail)
    conn.once('close', () => fail())
    this.socket.emit('online')
  }

  deactivate() {
    this.socket.connection?.removeAllListeners()
  }
}

class ClosedState {
  send() { throw new Error('닫힌 소켓에는 전송할 수 없다') }
  activate() {}
  deactivate() {}
}
```

컨텍스트는 놀랄 만큼 단순해진다. 조건문이 하나도 없다.

```js
export class FailsafeSocket extends EventEmitter {
  #states
  #current

  constructor(options) {
    super()
    this.options = options
    this.queue = []
    this.connection = null
    this.attempt = 0
    this.#states = {
      offline: new OfflineState(this),
      connecting: new ConnectingState(this),
      online: new OnlineState(this),
      closed: new ClosedState(this)
    }
    this.changeState('connecting')
  }

  changeState(name) {
    const next = this.#states[name]
    if (!next) throw new Error(`알 수 없는 상태: ${name}`)
    this.#current?.deactivate()
    this.#current = next
    this.state = name
    this.emit('state', name)
    next.activate()
  }

  send(data) {
    this.#current.send(data)
    return this
  }

  nextDelay() {
    // 1초에서 시작해 최대 30초까지 지수적으로 늘린다
    return Math.min(1000 * 2 ** this.attempt++, 30_000)
  }

  resetDelay() { this.attempt = 0 }

  end() {
    this.connection?.end()
    this.changeState('closed')
  }
}
```

사용하는 쪽은 소켓의 상태를 전혀 신경 쓰지 않는다.

```js
const sock = new FailsafeSocket({ port: 5000, host: '127.0.0.1' })
sock.on('state', (s) => console.log('상태 전이:', s))
sock.on('warning', (e) => console.warn('일시적 오류:', e.message))

setInterval(() => {
  sock.send(JSON.stringify({ ts: Date.now(), level: 'info' }) + '\n')
}, 1000)
```

수집기를 껐다 켜도 애플리케이션은 죽지 않고, 재연결되는 순간 밀린 메시지가 순서대로 흘러간다.

### 실전 사례

- **서킷 브레이커(circuit breaker)**: `CLOSED → OPEN → HALF_OPEN`은 상태 패턴의 교과서적 예이며, 각 상태의 `call()` 동작이 완전히 다르다(29장 참조).
- **WebSocket 클라이언트**: `CONNECTING/OPEN/CLOSING/CLOSED`라는 `readyState`는 명세 차원의 상태 기계다.
- **결제·주문 워크플로**: `PENDING → PAID → SHIPPED → REFUNDED` 같은 도메인 상태에서 허용되는 연산이 상태마다 다르다. 상태 객체는 "배송 완료된 주문은 취소할 수 없다" 같은 규칙을 한곳에 담는다.

### 언제 쓰지 말아야 하는가

- **상태가 둘이고 전이가 자명할 때.** `isOpen` 불리언 하나로 끝날 일에 클래스 두 개를 만들면 읽는 사람만 손해다.
- **상태별 행동 차이가 없을 때.** 모든 상태가 같은 `send`를 하고 로그 문자열만 다르다면 그것은 상태 값(enum)이지 상태 패턴이 아니다.
- **전이 규칙이 외부 워크플로 엔진에 있을 때.** 복잡한 도메인 상태 기계는 XState 같은 선언적 라이브러리로 명세를 분리하는 편이 검증과 시각화에 유리하다.

## 14.3 템플릿(Template)

### 문제 상황

14.1의 `Config`를 다시 보자. 골격은 동일하고 두 지점(`parse`, `stringify`)만 다르다. 전략은 이 가변 지점을 **외부 객체에 위임**했다. 템플릿 메서드는 같은 문제를 **상속**으로 푼다. 알고리즘의 뼈대를 상위 클래스에 두고, 구멍은 하위 클래스가 메우게 하는 것이다.

### 패턴의 정의

**템플릿 메서드 패턴**은 상위 클래스가 알고리즘의 순서(템플릿 메서드)를 확정하고, 그중 일부 단계를 추상 메서드로 남겨 하위 클래스가 구현하게 한다. JavaScript에는 `abstract` 키워드가 없으므로, 구현되지 않은 단계는 호출 시 예외를 던지도록 만드는 것이 관례다.

### 구현 코드

```js
// config-template.js
import { readFile, writeFile } from 'node:fs/promises'

export class ConfigTemplate {
  #data = {}

  // 템플릿 메서드: 순서가 여기 고정된다
  async load(filePath) {
    const text = await readFile(filePath, 'utf8')
    this.#data = this._parse(text)
    this._afterLoad(this.#data)   // 훅(hook): 기본 구현은 아무것도 안 한다
    return this
  }

  async save(filePath) {
    await writeFile(filePath, this._stringify(this.#data))
    return this
  }

  get(path) {
    return path.split('.').reduce((acc, k) => acc?.[k], this.#data)
  }

  // 추상 단계 — 하위 클래스가 반드시 구현한다
  _parse(text) { throw new Error('_parse()를 구현해야 한다') }
  _stringify(obj) { throw new Error('_stringify()를 구현해야 한다') }

  // 선택 훅 — 필요할 때만 재정의한다
  _afterLoad(data) {}
}

export class JsonConfig extends ConfigTemplate {
  _parse(text) { return JSON.parse(text) }
  _stringify(obj) { return JSON.stringify(obj, null, 2) }
}

export class YamlConfig extends ConfigTemplate {
  _parse(text) { return parseYaml(text) }
  _stringify(obj) { return stringifyYaml(obj) }
  _afterLoad(data) {
    // YAML은 타입 추론이 관대하다. 'on'이 true가 되는 문제를 여기서 보정한다
    if (typeof data.mode === 'boolean') data.mode = data.mode ? 'on' : 'off'
  }
}
```

### 전략과 템플릿의 차이

같은 문제를 두 방식으로 풀었으니 차이가 선명하다.

| 관점 | 전략(합성) | 템플릿(상속) |
|---|---|---|
| 결합 방식 | `new Config(yamlStrategy)` | `class YamlConfig extends ConfigTemplate` |
| 교체 시점 | 런타임. 인스턴스 생성 후에도 교체 가능 | 컴파일 시점. 클래스가 곧 선택이다 |
| 조합 가능성 | 전략끼리 자유롭게 조합·중첩 | 다중 상속 불가, 조합하려면 믹스인 필요 |
| 재사용 | 전략을 다른 컨텍스트에서도 재사용 | 상위 클래스에 묶여 재사용 어려움 |
| 테스트 | 전략을 단독으로 테스트 | 상위 클래스를 함께 끌고 와야 함 |
| 가변 지점이 많을 때 | 인터페이스가 비대해짐 | 훅을 늘리기 쉬움 |

핵심은 한 문장으로 정리된다. **템플릿은 "무엇을 채울지"를 클래스 정의 시점에 고정하고, 전략은 객체 생성 시점(또는 그 이후)까지 미룬다.**

### JavaScript에서 템플릿 패턴을 덜 쓰게 되는 이유

1. **함수가 일급이다.** 가변 지점을 채우려고 클래스를 파생시킬 필요가 없다. 함수를 인자로 넘기면 끝이다. `ConfigTemplate`을 상속한 `JsonConfig`는 결국 함수 두 개를 전달하는 일을 클래스 선언으로 포장한 것에 지나지 않는다.
2. **상속은 조합이 안 된다.** JSON을 읽으면서 암호화도 하고 싶다면 전략에서는 데코레이터로 감싸면(13장 참조) 되지만, 상속에서는 `EncryptedJsonConfig`, `EncryptedYamlConfig`처럼 클래스가 곱셈으로 늘어난다.
3. **`_` 접두사는 강제력이 없다.** 보호된 멤버가 언어에 없으므로 템플릿의 계약은 관례일 뿐이다. `#private`을 쓰면 하위 클래스에서 접근조차 안 되어 템플릿과 충돌한다.
4. **깊은 계층은 디버깅을 어렵게 한다.** 실행 흐름이 클래스 세 개를 오르내리면 스택 트레이스만으로는 어떤 `_parse`가 불렸는지 알기 어렵다.

그럼에도 템플릿이 옳은 경우가 있다. **프레임워크가 확장점을 정의할 때**다. Node.js 코어 스트림이 정확히 이 형태다.

```js
import { Transform } from 'node:stream'

// _transform()이 추상 단계, 나머지 흐름(백프레셔, 버퍼링, 이벤트)은 상위가 전담한다
class UpperCaseTransform extends Transform {
  _transform(chunk, encoding, callback) {
    callback(null, chunk.toString().toUpperCase())
  }
  _flush(callback) { callback() }   // 선택 훅
}
```

`Readable._read`, `Writable._write`, `Transform._transform`은 모두 템플릿 메서드다(7장 참조). 백프레셔 제어처럼 틀리기 쉬운 골격을 코어가 쥐고, 사용자에게는 정말 달라지는 한 단계만 열어주는 것이 이 패턴의 정당한 용도다.

### 실전 사례

- **커스텀 스트림 구현**: 위에서 본 대로다.
- **테스트 프레임워크의 훅**: `beforeEach → test → afterEach`라는 실행 순서는 프레임워크가 고정하고, 각 단계의 내용만 사용자가 채운다.

### 언제 쓰지 말아야 하는가

- **가변 지점이 하나뿐일 때.** 콜백 하나를 받으면 될 일이다.
- **동일한 골격을 여러 축으로 확장해야 할 때.** 클래스 폭발이 예정되어 있다면 처음부터 전략과 데코레이터로 간다.
- **라이브러리 사용자가 상속을 강요받는 것이 부담일 때.** 공개 API에서 "우리 클래스를 상속하라"는 요구는 사용자의 상속 슬롯 하나를 영구히 점유한다.

## 14.4 이터레이터와 이터러블 프로토콜

### 문제 상황

컬렉션을 순회하는 코드는 컬렉션의 내부 구조에 묶이기 쉽다. 배열은 인덱스로, 연결 리스트는 `next` 포인터로, 트리는 재귀로, 데이터베이스 커서는 `fetchNext()`로 순회한다. 순회 방식이 자료구조마다 다르면 이들을 다루는 유틸리티(필터링, 매핑, 앞의 N개 취하기)도 자료구조마다 다시 써야 한다.

### 패턴의 정의

**이터레이터 패턴**은 컬렉션의 내부 표현을 노출하지 않고 원소를 순차적으로 접근하는 방법을 제공한다. JavaScript는 이것을 라이브러리가 아니라 **언어 프로토콜**로 못박았고, 그 결과 `for...of`, 전개 연산자, 구조 분해, `Promise.all`, `Array.from`, `Map`/`Set` 생성자가 전부 같은 약속 위에서 동작한다.

프로토콜은 두 개다.

- **이터레이터 프로토콜(iterator protocol)**: `next()` 메서드를 가진 객체. 호출하면 `{ value, done }` 형태의 결과를 돌려준다. 선택적으로 `return(value)`과 `throw(err)`를 가질 수 있다.
- **이터러블 프로토콜(iterable protocol)**: `[Symbol.iterator]()` 메서드를 가진 객체. 호출하면 이터레이터를 돌려준다.

`for...of`는 이터러블만 받는다. 이터레이터 자체는 `for...of`에 넣을 수 없다는 점이 초심자가 가장 자주 걸리는 지점이다.

### 구현 코드

먼저 이터레이터를 손으로 만든다. 알파벳 시퀀스를 도는 이터레이터다.

```js
function createAlphabetIterator() {
  const end = 'z'.codePointAt(0)
  let code = 'a'.codePointAt(0)

  return {
    next() {
      if (code > end) return { value: undefined, done: true }
      return { value: String.fromCodePoint(code++), done: false }
    }
  }
}

const it = createAlphabetIterator()
console.log(it.next())  // { value: 'a', done: false }
console.log(it.next())  // { value: 'b', done: false }
```

`done: true`가 나온 뒤에도 `next()`를 호출할 수 있어야 하며, 계속 `{ done: true }`를 반환해야 한다. 이것을 지키지 않으면 소비자가 무한 루프에 빠질 수 있다.

이제 이터러블을 만든다. 실전에 가까운 예로, 2차원 행렬을 행 우선으로 순회하는 클래스를 보자.

```js
class Matrix {
  constructor(rows, cols, fill = 0) {
    this.rows = rows
    this.cols = cols
    this.data = new Array(rows * cols).fill(fill)
  }

  at(r, c) { return this.data[r * this.cols + c] }
  set(r, c, v) { this.data[r * this.cols + c] = v; return this }

  // 기본 순회: 행 우선으로 모든 원소
  [Symbol.iterator]() {
    let r = 0, c = 0
    return {
      next: () => {
        if (r >= this.rows) return { done: true, value: undefined }
        const value = this.at(r, c)
        if (++c >= this.cols) { c = 0; r++ }
        return { done: false, value }
      },
      // 소비자가 중간에 멈추면(break, return, throw) 호출된다. 자원 정리 지점이다
      return: () => {
        r = this.rows
        return { done: true, value: undefined }
      },
      // 이터레이터를 스스로도 이터러블로 만든다
      [Symbol.iterator]() { return this }
    }
  }

  // 대체 순회 전략은 별도 메서드로 제공한다
  *columnMajor() {
    for (let c = 0; c < this.cols; c++) {
      for (let r = 0; r < this.rows; r++) yield this.at(r, c)
    }
  }
}
```

프로토콜을 지키는 순간 언어의 모든 도구가 열린다.

```js
const m = new Matrix(2, 3)
m.set(0, 0, 1).set(0, 1, 2).set(0, 2, 3).set(1, 0, 4).set(1, 1, 5).set(1, 2, 6)

for (const v of m) process.stdout.write(v + ' ')  // 1 2 3 4 5 6
console.log([...m])                                // [1,2,3,4,5,6]
const [first, second] = m                          // 구조 분해
console.log(Math.max(...m))                        // 6
console.log(new Set(m).size)                       // 6
console.log([...m.columnMajor()])                  // [1,4,2,5,3,6]
```

이터레이터에 `[Symbol.iterator]() { return this }`를 넣은 것을 **이터러블 이터레이터(iterable iterator)**라고 부른다. 부분 순회 후 나머지를 이어서 도는 패턴이 이것 덕분에 가능하다.

```js
const iter = m[Symbol.iterator]()
iter.next()                      // 첫 원소 소비
console.log([...iter])           // [2,3,4,5,6] — 남은 것부터 이어서 돈다
```

### 실전 사례

Node.js와 브라우저 API는 이미 이터러블로 가득하다. `Map`, `Set`, `URLSearchParams`, `Headers`, `FormData`, `NodeList`, 그리고 문자열도 이터러블이다. 문자열 이터레이터는 UTF-16 코드 유닛이 아니라 **코드 포인트** 단위로 돈다는 점이 실용적으로 중요하다.

```js
const s = '한글🇰🇷'
console.log(s.length)      // 6 — 코드 유닛 개수
console.log([...s].length) // 3 — 이터레이터는 서로게이트 쌍을 올바르게 다룬다
```

`URLSearchParams`는 엔트리 이터러블이라 그대로 `Object.fromEntries`에 넣을 수 있다.

```js
const params = new URLSearchParams('page=2&limit=50')
console.log(Object.fromEntries(params))  // { page: '2', limit: '50' }
```

### 언제 쓰지 말아야 하는가

- **손으로 `next()`를 구현하는 것 자체가 대개 불필요하다.** 14.5에서 보듯 제너레이터가 같은 일을 1/5 분량으로 해낸다. 손 구현이 정당한 경우는 이터레이터에 `peek()`나 `reset()` 같은 추가 메서드를 붙이거나, 극단적인 성능 요구로 제너레이터의 프레임 비용을 피해야 할 때뿐이다.
- **인덱스가 필요한 단순 배열 순회.** `for (let i = 0; ...)`는 여전히 가장 빠르고 명확하다.
- **랜덤 접근이 필요한 자료구조.** 이터레이터는 순차 접근만 표현한다.

## 14.5 제너레이터: 이론, 제어, 이터레이터 대체

### 문제 상황

14.4의 `Matrix[Symbol.iterator]`는 클로저 변수 `r`, `c`를 손으로 관리했다. 트리처럼 재귀적인 구조로 가면 손 구현은 급격히 어려워진다. 재귀 호출의 위치를 명시적 스택으로 바꿔야 하기 때문이다. 순회 로직을 **평범한 제어 흐름으로 쓰되, 실행을 중간에 멈췄다가 재개**할 수 있다면 이 문제가 사라진다.

### 패턴의 정의

**제너레이터(generator)**는 실행 도중 스스로를 일시 중단하고 나중에 그 지점에서 재개할 수 있는 함수다. `function*`로 선언하고 `yield`로 중단한다. 제너레이터 함수를 호출하면 본문이 실행되지 않고 **제너레이터 객체**가 반환되는데, 이 객체는 이터레이터이자 이터러블이다. 즉 제너레이터는 이터레이터 프로토콜의 문법적 구현체다.

### 구현 코드

14.4의 알파벳 이터레이터가 세 줄로 줄어든다.

```js
function* alphabet() {
  for (let c = 'a'.codePointAt(0); c <= 'z'.codePointAt(0); c++) {
    yield String.fromCodePoint(c)
  }
}
console.log([...alphabet()].join(''))  // abcdefghijklmnopqrstuvwxyz
```

재귀 순회에서 진가가 드러난다. 파일 시스템 트리를 도는 코드를 보자.

```js
import { readdirSync } from 'node:fs'
import { join } from 'node:path'

function* walkSync(dir) {
  for (const entry of readdirSync(dir, { withFileTypes: true })) {
    const full = join(dir, entry.name)
    if (entry.isDirectory()) {
      yield* walkSync(full)   // 하위 제너레이터에 순회를 위임한다
    } else {
      yield full
    }
  }
}

// 지연 평가이므로 첫 결과가 즉시 나온다. 전체 트리를 메모리에 담지 않는다
for (const file of walkSync('./src')) {
  if (file.endsWith('.js')) console.log(file)
}
```

`yield*` 하나가 재귀 순회 전체를 처리한다. 손으로 만든 이터레이터로 같은 일을 하려면 디렉터리 스택을 직접 유지해야 한다.

### 양방향 통신: `next()`에 값 넘기기

제너레이터는 값을 내보내기만 하는 것이 아니라 **받을 수도** 있다. `yield` 표현식의 평가값은 다음번 `next(v)`에 전달된 `v`다.

```js
function* accumulator() {
  let total = 0
  while (true) {
    // 바깥에서 next(x)로 넘긴 값이 여기 들어온다
    const delta = yield total
    if (typeof delta === 'number') total += delta
  }
}

const acc = accumulator()
console.log(acc.next().value)    // 0 — 첫 next()는 첫 yield까지 달리기만 한다
console.log(acc.next(10).value)  // 10
console.log(acc.next(5).value)   // 15
```

첫 `next()`에 넘긴 인자는 버려진다는 점이 중요하다. 첫 호출 시점에는 값을 받을 `yield`가 아직 없기 때문이다. 이 양방향성이 있었기에 `async/await` 이전 시대에 co 같은 라이브러리가 제너레이터로 비동기 흐름을 구현할 수 있었다. 오늘날 async 함수는 사실상 프로미스를 자동으로 `next()`에 되먹이는 제너레이터다(6장 참조).

### `return()`과 `throw()`: 바깥에서 제어하기

```js
function* resourceReader(name) {
  console.log(`${name} 열기`)
  try {
    let i = 0
    while (true) yield `${name}:${i++}`
  } catch (err) {
    console.log('제너레이터 내부에서 오류 수신:', err.message)
    yield `${name}:recovered`
  } finally {
    console.log(`${name} 닫기`)   // 조기 종료에도 반드시 실행된다
  }
}

const r = resourceReader('db')
r.next()                              // 'db 열기', { value: 'db:0' }
r.throw(new Error('연결 끊김'))        // 내부 catch로 들어간다
r.return('중단')                       // finally 실행 → 'db 닫기'
```

`for...of`가 `break`나 예외로 조기 종료되면 런타임이 자동으로 `return()`을 호출한다. 따라서 제너레이터의 `finally` 블록은 **자원 정리를 위한 신뢰할 수 있는 지점**이다. 파일 핸들이나 DB 커서를 여는 제너레이터라면 반드시 `try/finally`로 감싼다.

### 무한 시퀀스와 지연 평가

제너레이터는 값을 요청받을 때만 계산하므로 무한 시퀀스를 자연스럽게 표현한다.

```js
function* naturals(start = 0) {
  for (let n = start; ; n++) yield n
}

function* map(iterable, fn) {
  for (const v of iterable) yield fn(v)
}

function* filter(iterable, pred) {
  for (const v of iterable) if (pred(v)) yield v
}

function* take(iterable, n) {
  if (n <= 0) return
  let i = 0
  for (const v of iterable) {
    yield v
    if (++i >= n) return   // 여기서 상위 이터레이터의 return()이 연쇄 호출된다
  }
}

// 무한 수열에서 짝수의 제곱 5개
const result = [...take(map(filter(naturals(1), n => n % 2 === 0), n => n * n), 5)]
console.log(result)  // [4, 16, 36, 64, 100]
```

배열 메서드 체인이었다면 `naturals()`에서 이미 멈춰 있었을 것이다. 제너레이터 파이프라인은 **각 단계가 원소 하나씩 당겨오는(pull) 구조**라 중간 배열을 만들지 않는다. 원소가 수백만 개인 로그 파일을 처리할 때 이 차이가 메모리 사용량을 결정한다.

### 실전 사례

- **ID·시퀀스 생성기**: `function* idGen() { let i = 0; while (true) yield `req-${++i}` }`
- **페이지네이션 커서**: 동기 버전은 드물지만, 이 구조가 14.6의 비동기 제너레이터로 그대로 이어진다.
- **`stream.Readable.from()`**: 제너레이터를 그대로 읽기 스트림으로 바꾼다(14.7).

### 언제 쓰지 말아야 하는가

- **결과가 어차피 작은 배열일 때.** `[...gen()]`로 즉시 펼칠 거라면 그냥 배열을 반환하는 함수가 읽기 쉽다.
- **성능이 극단적으로 중요한 내부 루프.** 제너레이터는 호출마다 재개 프레임을 다루므로 단순 `for` 루프보다 느리다. 수천만 회 도는 수치 계산 루프에서는 측정 후 판단한다.
- **제너레이터를 코루틴처럼 쓰려는 시도.** `next()`에 값을 되먹이는 비동기 제어 흐름은 async/await가 이미 대체했다. 새 코드에서 co 스타일을 재발명할 이유가 없다.
- **여러 소비자가 같은 제너레이터를 공유할 때.** 제너레이터 객체는 일회용이며 상태를 공유한다. 두 곳에서 순회하면 원소가 나뉘어 버린다. 재순회가 필요하면 제너레이터 함수를 감싼 이터러블 객체를 반환한다.

```js
// 매번 새 순회를 만드는 재사용 가능 이터러블
const reusable = { *[Symbol.iterator]() { yield* [1, 2, 3] } }
console.log([...reusable], [...reusable])  // 두 번 모두 [1,2,3]
```

## 14.6 비동기 이터레이터와 비동기 제너레이터

### 문제 상황

원소를 얻는 데 I/O가 필요한 시퀀스가 있다. REST API의 페이지네이션 결과, 데이터베이스 커서, 메시지 큐의 스트림, 디렉터리 재귀 순회가 전부 그렇다. 동기 이터레이터로는 표현할 수 없고, 결과를 전부 배열에 모아 반환하면 지연 평가와 메모리 이점을 잃는다.

전통적으로는 이렇게 썼다.

```js
// 페이지를 전부 모아 반환한다 — 결과가 10만 건이면 메모리가 터진다
async function fetchAllUsers() {
  const all = []
  let cursor = null
  do {
    const res = await fetch(`/api/users?cursor=${cursor ?? ''}`)
    const page = await res.json()
    all.push(...page.items)
    cursor = page.nextCursor
  } while (cursor)
  return all
}
```

### 패턴의 정의

**비동기 이터레이터(async iterator)**는 `next()`가 값 대신 `Promise<{value, done}>`을 반환하는 이터레이터다. **비동기 이터러블(async iterable)**은 `[Symbol.asyncIterator]()`를 가진 객체이며, `for await...of`로 순회한다.

`Symbol.iterator`와 `Symbol.asyncIterator`는 별개의 심벌이다. `for await...of`는 `Symbol.asyncIterator`를 먼저 찾고, 없으면 `Symbol.iterator`로 대체(fallback)한 뒤 각 값을 `await`한다. 그래서 `for await (const v of [p1, p2])`처럼 프로미스 배열도 순회할 수 있다.

**비동기 제너레이터(async generator)**는 `async function*`로 선언하며, 내부에서 `await`와 `yield`를 함께 쓸 수 있다. 반환되는 객체가 곧 비동기 이터러블이다.

### 구현 코드

앞의 페이지네이션을 비동기 제너레이터로 다시 쓴다.

```js
// 페이지 단위로 당겨오되, 소비자에게는 사용자 하나씩 흘려보낸다
async function* fetchUsers(baseUrl, { signal, pageSize = 100 } = {}) {
  let cursor = null
  do {
    const url = new URL('/api/users', baseUrl)
    url.searchParams.set('limit', String(pageSize))
    if (cursor) url.searchParams.set('cursor', cursor)

    const res = await fetch(url, { signal })
    if (!res.ok) throw new Error(`HTTP ${res.status} — ${url.pathname}`)
    const page = await res.json()

    yield* page.items          // 페이지의 원소들을 하나씩 방출한다
    cursor = page.nextCursor
  } while (cursor)
}
```

소비하는 쪽은 페이지네이션의 존재조차 모른다.

```js
const ac = new AbortController()

let count = 0
for await (const user of fetchUsers('https://api.example.com', { signal: ac.signal })) {
  if (user.status === 'deleted') continue
  await archive(user)
  if (++count >= 500) break   // 조기 종료 — 남은 페이지는 애초에 요청되지 않는다
}
```

`break`가 이 예제의 핵심이다. 500명을 처리하고 멈추면 6번째 페이지 요청은 발생하지 않는다. 전부 모아서 반환하는 버전과 비교하면 네트워크 왕복과 메모리 모두 절약된다.

### 조기 종료와 자원 정리

`for await...of`가 `break`, `return`, 예외로 빠져나오면 런타임이 비동기 이터레이터의 `return()`을 호출하고 그 결과를 `await`한다. 따라서 `finally`에서 비동기 정리도 안전하게 할 수 있다.

```js
async function* queryRows(pool, sql) {
  const conn = await pool.acquire()
  try {
    const cursor = conn.cursor(sql)
    let rows
    while ((rows = await cursor.read(200)).length > 0) {
      yield* rows
    }
  } finally {
    // break로 중단되든 예외가 나든 커넥션은 반드시 반납된다
    await pool.release(conn)
  }
}
```

이 성질 덕분에 커넥션 누수를 구조적으로 막을 수 있다. 다만 소비자가 순회를 시작만 하고 스코프를 떠나면(예: 이터레이터를 변수에 담아두고 잊으면) `return()`이 호출되지 않으니, 반드시 `for await...of`로 소비하도록 API를 설계한다.

### 직접 구현하는 비동기 이터러블

클래스에 붙일 때는 `[Symbol.asyncIterator]`를 비동기 제너레이터 메서드로 정의하면 그만이다. 손으로 구현할 필요가 생기는 경우는 **푸시 기반 소스를 풀 기반 소비로 바꿀 때**뿐이다. 이벤트는 언제 도착할지 모르므로, 값이 아직 없으면 `next()`가 프로미스를 보류해두었다가 이벤트가 도착하는 순간 그 프로미스를 이행시켜야 한다. 대기 중인 `resolve` 함수들의 큐와 아직 소비되지 않은 값들의 큐, 두 개를 유지하는 것이 전부다.

Node.js는 이 어댑터를 `events.on(emitter, eventName)` 헬퍼로 이미 제공한다.

```js
import { on, EventEmitter } from 'node:events'

const emitter = new EventEmitter()
setInterval(() => emitter.emit('tick', Date.now()), 1000).unref()

for await (const [ts] of on(emitter, 'tick')) {  // 인자 배열로 전달된다
  console.log('틱', ts)
  if (Date.now() - ts > 5000) break
}
```

주의할 점이 있다. `events.on`은 소비자가 느리면 이벤트를 **무한히 버퍼링**한다. 백프레셔이 없는 것이다. 고빈도 이벤트에는 `highWaterMark` 옵션을 주거나 스트림으로 다루어야 한다.

### 순차 실행이라는 함정

`for await...of`는 **한 번에 하나씩** 처리한다. 각 반복이 끝나야 다음 `next()`가 불린다. 이는 순서 보장과 백프레셔 측면에서 장점이지만, 독립적인 작업을 병렬로 돌리고 싶을 때는 심각한 성능 저하가 된다.

```js
// 나쁨: 1000개 항목을 100ms씩 순차 처리 → 100초
for await (const item of source) await process(item)

// 좋음: 동시성 상한을 두고 병렬 처리
async function forEachConcurrent(asyncIterable, limit, fn) {
  const workers = Array.from({ length: limit }, async () => {
    // 여러 워커가 같은 이터레이터를 공유해 하나씩 당겨간다
    for await (const item of asyncIterable) await fn(item)
  })
  await Promise.all(workers)
}

const iter = source[Symbol.asyncIterator]()
await forEachConcurrent({ [Symbol.asyncIterator]: () => iter }, 8, process)
```

여러 워커가 하나의 이터레이터를 공유하는 것이 요령이다. 각 워커가 `for await`로 순회하되 이터레이터 객체는 동일하므로, 원소가 중복 없이 분배된다.

### 실전 사례

- **AWS SDK v3의 `paginateXxx()`**: 모든 페이지네이션 API가 비동기 이터러블로 제공된다.
- **MongoDB 드라이버의 `find()` 커서**: `for await (const doc of collection.find(q))`가 표준 사용법이다.
- **`fs.promises.opendir()`**: 디렉터리 핸들이 비동기 이터러블이라 대용량 디렉터리를 메모리 폭발 없이 순회한다.

### 언제 쓰지 말아야 하는가

- **원소가 몇 개뿐이고 전부 필요할 때.** `await Promise.all(...)` 한 줄이 더 빠르고 명확하다.
- **완전 병렬 처리가 목적일 때.** 위에서 봤듯 `for await`는 기본이 순차다. 동시성이 본질이라면 세마포어나 작업 풀(6장 참조)이 옳은 도구다.
- **소비자가 값을 밀어 넣기만 하면 되는 순수 이벤트 시나리오.** 버퍼가 무한히 커질 위험이 있다면 그냥 이벤트 리스너를 쓴다.

## 14.7 비동기 이터레이터와 스트림의 만남

### 문제 상황

Node.js 스트림은 강력하지만 API가 이벤트 기반이라 흐름을 눈으로 좇기 어렵다. `data`, `end`, `error` 리스너를 붙이고, 백프레셔(backpressure)을 위해 `pause()`/`resume()`을 관리하고, 오류 발생 시 모든 스트림을 파괴해야 한다(7장 참조).

```js
// 전통적 방식: 오류 처리와 백프레셔가 손으로 얽힌다
let lineCount = 0
rl.on('line', (line) => {
  if (isInteresting(line)) {
    const ok = out.write(transform(line))
    if (!ok) { rl.pause(); out.once('drain', () => rl.resume()) }
  }
  lineCount++
})
rl.on('error', reject)
rl.on('close', () => resolve(lineCount))
```

### 패턴의 정의

Node.js v10 이후 **모든 `stream.Readable`은 비동기 이터러블**이다. 즉 `Symbol.asyncIterator`를 구현하고 있다. 이 한 가지 사실이 스트림과 14.6의 세계를 하나로 잇는다. 스트림은 비동기 이터러블이고, 비동기 제너레이터는 비동기 이터러블을 만든다. 따라서 둘은 자유롭게 상호 변환된다.

세 방향의 다리가 있다.

1. **스트림 → 이터레이터**: `for await (const chunk of readable)`
2. **이터레이터 → 스트림**: `Readable.from(asyncIterable)`
3. **파이프라인 중간 단계**: `pipeline(src, asyncGeneratorFn, dst)`

### 구현 코드: 스트림을 순회하기

읽기 스트림을 그대로 `for await`에 넣는다. 백프레셔은 자동으로 처리된다. 루프 본문이 오래 걸리면 `next()`가 늦게 불리고, 스트림은 알아서 내부 버퍼가 찰 때까지만 읽는다.

```js
import { createReadStream } from 'node:fs'
import { createInterface } from 'node:readline'

const rl = createInterface({
  input: createReadStream('access.log'),
  crlfDelay: Infinity
})

let errors = 0
// readline 인터페이스도 비동기 이터러블이다
for await (const line of rl) {
  if (line.includes(' 500 ')) errors++
}
console.log('5xx 응답 수:', errors)
```

`try/catch`가 스트림 오류를 잡고, `break`가 스트림을 파괴하며, 함수의 `return`이 자원을 정리한다. 이벤트 리스너 다섯 개가 언어 구문 셋으로 대체됐다.

### 구현 코드: 이터러블을 스트림으로

`Readable.from()`은 (비동기) 이터러블을 읽기 스트림으로 감싼다. 데이터 소스를 제너레이터로 쓰고, 소비는 스트림 생태계에 맡기는 조합이 강력하다.

```js
import { Readable } from 'node:stream'
import { createWriteStream } from 'node:fs'
import { pipeline } from 'node:stream/promises'

async function* csvRows(baseUrl) {
  yield 'id,name,email\n'
  for await (const user of fetchUsers(baseUrl)) {   // 14.6의 제너레이터를 재사용한다
    yield `${user.id},${escapeCsv(user.name)},${user.email}\n`
  }
}

// objectMode를 끄면 문자열을 그대로 바이트로 흘린다
await pipeline(
  Readable.from(csvRows('https://api.example.com')),
  createWriteStream('users.csv')
)
```

API 응답 10만 건을 CSV로 내보내면서 메모리에 담기는 것은 한 번에 한 페이지뿐이다.

### 구현 코드: 비동기 제너레이터를 변환 단계로

가장 실용적인 지점이다. `pipeline()`은 중간 인자로 **비동기 제너레이터 함수**를 받는다. `Transform` 클래스를 만들 필요 없이, 입력 이터러블을 받아 출력을 `yield`하는 함수만 쓰면 된다.

```js
import { pipeline } from 'node:stream/promises'
import { createReadStream, createWriteStream } from 'node:fs'
import { createGunzip, createGzip } from 'node:zlib'

// 각 단계는 (source) => AsyncIterable 형태의 평범한 함수다
async function* splitLines(source) {
  let buffer = ''
  for await (const chunk of source) {
    buffer += chunk
    const lines = buffer.split('\n')
    buffer = lines.pop()          // 마지막 조각은 다음 청크와 이어붙인다
    yield* lines
  }
  if (buffer) yield buffer
}

async function* parseJson(source) {
  for await (const line of source) {
    if (!line.trim()) continue
    try {
      yield JSON.parse(line)
    } catch {
      // 손상된 줄은 건너뛰되 파이프라인 전체를 죽이지 않는다
    }
  }
}

async function* enrich(source) {
  for await (const record of source) {
    // 각 레코드마다 비동기 조회를 해도 백프레셔가 유지된다
    record.geo = await geoLookup(record.ip)
    yield record
  }
}

async function* toNdjson(source) {
  for await (const record of source) yield JSON.stringify(record) + '\n'
}

await pipeline(
  createReadStream('events.ndjson.gz'),
  createGunzip(),
  splitLines,
  parseJson,
  enrich,
  toNdjson,
  createGzip(),
  createWriteStream('enriched.ndjson.gz')
)
```

이 파이프라인의 성질을 짚어보자.

- **백프레셔이 끝에서 앞으로 전파된다.** `enrich`의 `await geoLookup()`이 느려지면 그 위 단계들이 자연히 느려지고, 파일 읽기도 멈춘다. 손으로 아무것도 하지 않았다.
- **오류가 한곳에서 잡힌다.** 어느 단계에서 예외가 나든 `pipeline`이 모든 스트림을 파괴하고 프로미스를 거부한다.
- **각 단계를 단독 테스트할 수 있다.** `splitLines`는 스트림을 몰라도 되고, 배열을 넣어도 동작한다. `expect(await collect(splitLines(['a\nb', 'c\n']))).toEqual(['a', 'bc'])`.

`AbortSignal`도 그대로 통한다.

```js
const ac = new AbortController()
setTimeout(() => ac.abort(), 30_000)
await pipeline(src, splitLines, parseJson, dst, { signal: ac.signal })
```

### 실전 사례

- **대용량 로그 ETL**: 위 예제가 그대로 실무 코드다. GB 단위 로그를 상수 메모리로 처리한다.
- **HTTP 응답 스트리밍**: `Readable.from(asyncGen())`을 `res`에 파이프하면 서버가 전체 결과를 만들기 전에 첫 바이트를 내보낸다(16장 참조).
- **웹 표준 스트림 상호 운용**: `Readable.fromWeb()`/`Readable.toWeb()`으로 `fetch` 응답 본문과 Node 스트림을 오간다.

### 언제 쓰지 말아야 하는가

- **데이터가 작을 때.** 몇 KB짜리 JSON을 스트림 파이프라인으로 처리하는 것은 순수한 오버헤드다. `await readFile()` 한 줄이 낫다.
- **`objectMode` 성능이 문제일 때.** 레코드 하나마다 제너레이터 프레임과 스트림 이벤트가 생긴다. 초당 수십만 레코드를 처리해야 한다면 청크 단위(배열 묶음)로 `yield`해 오버헤드를 분산한다.
- **스트림을 두 번 순회하려 할 때.** `for await`는 스트림을 소비한다. 두 소비자가 필요하면 `PassThrough`로 티(tee)를 만들어야 한다.
- **`for await` 중에 `readable.on('data')`를 함께 쓸 때.** 두 방식은 섞이지 않는다. 하나만 골라야 한다.

## 14.8 미들웨어: 패턴으로서의 미들웨어와 프레임워크 만들기

### 문제 상황

HTTP 요청 하나를 처리하려면 인증, 로깅, 본문 파싱, 압축, 오류 변환, CORS 헤더 부착 같은 횡단 관심사(cross-cutting concern)를 거쳐야 한다. 이들을 핸들러마다 호출하면 중복이 생기고, 순서를 잘못 두면 미묘한 버그가 난다.

### 패턴의 정의

**미들웨어(middleware)**는 원래 시스템 사이를 잇는 접착 소프트웨어를 뜻했지만, Node.js 생태계에서는 **처리 단위 함수들의 파이프라인**을 가리키는 말로 굳었다. 각 함수는 공유 컨텍스트를 받아 그것을 가공하고, 다음 함수로 제어를 넘긴다.

핵심 성질 셋이다.

1. 각 미들웨어는 컨텍스트를 **읽고 변형**할 수 있다.
2. 각 미들웨어는 다음으로 넘길지, 여기서 끊을지 **스스로 결정**한다.
3. 미들웨어는 **런타임에 등록**되며 순서가 곧 의미다.

이것은 사실 책임 연쇄(Chain of Responsibility) 패턴에 "함수 하나가 다음 함수를 호출한다"는 규약을 얹은 것이다. Express의 `(req, res, next) => {}`는 이 패턴의 가장 유명한 구현일 뿐, 미들웨어는 HTTP 전용 개념이 아니다.

### 구현 코드: 범용 미들웨어 매니저

HTTP와 무관한 매니저를 만들어보자. 메시지 브로커 클라이언트가 보내고 받는 데이터를 미들웨어로 가공한다.

```js
export class MiddlewareManager {
  #inbound = []
  #outbound = []

  use(middleware) {
    if (middleware.inbound) this.#inbound.push(middleware.inbound)
    if (middleware.outbound) this.#outbound.unshift(middleware.outbound)  // 역순 등록
    return this
  }

  async #run(chain, payload) {
    let value = payload
    for (const fn of chain) {
      value = await fn(value)
      if (value === undefined) {
        throw new Error('미들웨어는 반드시 값을 반환해야 한다')
      }
    }
    return value
  }

  runInbound(raw) { return this.#run(this.#inbound, raw) }
  runOutbound(msg) { return this.#run(this.#outbound, msg) }
}
```

미들웨어는 `{ inbound, outbound }` 쌍으로 정의한다. 대칭적인 관심사(직렬화/역직렬화, 압축/해제, 암호화/복호화)를 한 모듈에 담을 수 있다.

```js
import { gzip, gunzip } from 'node:zlib'
import { promisify } from 'node:util'
const gzipAsync = promisify(gzip)
const gunzipAsync = promisify(gunzip)

const jsonMiddleware = {
  inbound: (buf) => JSON.parse(buf.toString('utf8')),
  outbound: (obj) => Buffer.from(JSON.stringify(obj), 'utf8')
}

const zipMiddleware = {
  inbound: (buf) => gunzipAsync(buf),
  outbound: (buf) => gzipAsync(buf)
}

const mm = new MiddlewareManager()
mm.use(zipMiddleware)    // 수신: 압축 해제 먼저
mm.use(jsonMiddleware)   // 수신: 그 다음 JSON 파싱

// 송신은 outbound가 unshift로 등록되므로 자동으로 역순: JSON 직렬화 → 압축
const wire = await mm.runOutbound({ type: 'ping', ts: Date.now() })
const back = await mm.runInbound(wire)
```

`unshift`로 outbound를 역순 등록한 것이 설계의 요점이다. 사용자는 등록 순서 하나만 생각하면 되고, 반대 방향은 매니저가 뒤집어준다.

### 선형 모델과 양파 모델

미들웨어 실행 구조에는 두 가지 계보가 있다.

**선형 모델(Express 스타일)**: 각 미들웨어가 `next()`를 호출하면 다음으로 넘어간다. 제어는 앞으로만 흐르며, 응답 후 처리를 하려면 `res.on('finish')` 같은 우회가 필요하다.

```js
function createLinearApp() {
  const stack = []
  const use = (fn) => (stack.push(fn), api)

  function handle(ctx) {
    let i = 0
    function next(err) {
      const fn = stack[i++]
      if (!fn) return
      try {
        // 오류 미들웨어는 인자가 4개라는 관례로 구분한다
        if (err) {
          if (fn.length === 4) fn(err, ctx.req, ctx.res, next)
          else next(err)
        } else {
          if (fn.length === 4) next()
          else fn(ctx.req, ctx.res, next)
        }
      } catch (e) { next(e) }
    }
    next()
  }

  const api = { use, handle }
  return api
}
```

이 구현이 드러내는 Express의 정체는 명확하다. **Express 미들웨어는 배열에 담긴 함수들과, 인덱스를 하나 올리며 다음을 호출하는 `next` 클로저가 전부다.** 라우팅조차 "경로가 맞을 때만 실행되는 미들웨어"에 지나지 않는다.

선형 모델의 약점도 위 코드에 보인다. `try/catch`가 동기 예외만 잡으므로, `async` 미들웨어가 거부(reject)하면 오류가 사라진다. Express 4에서 async 핸들러를 쓸 때 반드시 래퍼가 필요한 이유다.

```js
const asyncHandler = (fn) => (req, res, next) =>
  Promise.resolve(fn(req, res, next)).catch(next)

app.get('/users', asyncHandler(async (req, res) => {
  res.json(await findUsers())   // 여기서 던진 오류가 next로 전달된다
}))
```

**양파 모델(Koa 스타일)**: 각 미들웨어가 `await next()`를 호출하고, 그 아래 전체가 끝난 뒤 제어가 돌아온다. 요청은 양파 껍질을 안쪽으로 뚫고 들어갔다가 다시 바깥으로 나온다.

```text
요청 →  [logger  [auth  [router  ● 핸들러 ]  auth]  logger] → 응답
         ↓내려감                                    ↑올라옴
```

```js
export function compose(middlewares) {
  return function run(ctx, last) {
    let index = -1
    function dispatch(i) {
      if (i <= index) return Promise.reject(new Error('next()가 두 번 호출됐다'))
      index = i
      const fn = middlewares[i] ?? last
      if (!fn) return Promise.resolve()
      // 동기 예외도 거부된 프로미스로 변환한다
      try {
        return Promise.resolve(fn(ctx, () => dispatch(i + 1)))
      } catch (err) {
        return Promise.reject(err)
      }
    }
    return dispatch(0)
  }
}
```

40줄이 채 안 되는 이 함수가 Koa의 심장이며, 이것 하나로 앞뒤 처리가 모두 가능해진다.

```js
const app = compose([
  // 응답 시간 측정: 내려갈 때 시작, 올라올 때 기록
  async (ctx, next) => {
    const start = process.hrtime.bigint()
    await next()
    const ms = Number(process.hrtime.bigint() - start) / 1e6
    ctx.res.setHeader('X-Response-Time', `${ms.toFixed(1)}ms`)
    console.log(`${ctx.req.method} ${ctx.req.url} ${ctx.status} ${ms.toFixed(1)}ms`)
  },

  // 오류 경계: 하위 전체를 감싸는 try/catch가 성립한다
  async (ctx, next) => {
    try {
      await next()
    } catch (err) {
      ctx.status = err.statusCode ?? 500
      ctx.body = { error: err.expose ? err.message : '내부 서버 오류' }
      if (ctx.status >= 500) console.error(err)
    }
  },

  // 핸들러
  async (ctx) => {
    ctx.body = await findUsers()
    ctx.status = 200
  }
])

await app(ctx)
```

두 모델의 차이를 표로 정리한다.

| 관점 | 선형(Express) | 양파(Koa) |
|---|---|---|
| 제어 흐름 | 단방향, `next()`는 반환값 없음 | 왕복, `await next()`가 하위 완료를 기다림 |
| 오류 처리 | 4-인자 미들웨어 관례, async는 래퍼 필요 | `try { await next() }`가 자연스럽게 성립 |
| 응답 후 처리 | `res.on('finish')` 등 우회 | 올라오는 길에 그냥 코드를 쓴다 |
| 구현 난도 | 매우 단순 | `compose` 함수 하나 필요 |
| 생태계 | 압도적으로 큼 | 작지만 현대적 |

Fastify는 세 번째 길을 택했다. 미들웨어 대신 **훅(hook)**을 생명주기 단계별로(`onRequest`, `preValidation`, `preHandler`, `onSend`) 명시적으로 등록하게 하고, 각 훅은 async 함수를 그대로 지원한다. 양파 모델의 앞뒤 처리 능력을 얻으면서 실행 순서를 이름으로 드러낸 셈이다(16장 참조).

### 실전 사례

- **Express/Koa/Fastify**: 웹 프레임워크 전체가 이 패턴 위에 서 있다.
- **Redux 미들웨어**: `store => next => action => {}`는 양파 모델의 커링 버전이다.
- **ØMQ/브로커 클라이언트**: 위에서 만든 매니저처럼 직렬화·압축·암호화 계층을 조립한다.

### 언제 쓰지 말아야 하는가

- **관심사가 하나뿐일 때.** 함수 하나를 호출하면 될 일에 파이프라인 인프라를 만들 이유가 없다.
- **순서 의존이 암묵적일 때가 위험하다.** "인증 미들웨어는 반드시 본문 파서 뒤"처럼 순서가 정확성에 직결되는데 코드에 드러나지 않으면, 등록 순서 한 줄이 보안 사고가 된다. 이런 경우 Fastify식 명명된 단계가 낫다.
- **컨텍스트가 자유 형식 객체일 때.** 모든 미들웨어가 `ctx`에 아무 속성이나 붙일 수 있으면 타입도 추적도 불가능해진다. 큰 애플리케이션에서는 컨텍스트 스키마를 정하거나 `AsyncLocalStorage`로 범위를 나눈다.
- **성능이 극도로 중요한 경로.** 미들웨어 하나마다 클로저와 프로미스가 생긴다. 요청당 40개의 미들웨어는 측정 가능한 비용이다.

## 14.9 커맨드(Command)와 태스크 패턴

### 문제 상황

`await sendEmail(user, template)`처럼 함수를 직접 호출하면 그 호출은 **즉시, 한 번, 되돌릴 수 없게** 일어난다. 그런데 실무 요구는 대개 이렇다. 지금 말고 나중에 실행하고, 실패하면 재시도하고, 동시 실행 수를 제한하고, 누가 언제 무엇을 실행했는지 감사 로그를 남기고, 사용자가 취소를 누르면 중단하고, 경우에 따라 되돌리고 싶다. 호출이 코드에 박혀 있으면 이 중 무엇도 할 수 없다.

### 패턴의 정의

**커맨드 패턴**은 "무엇을 할 것인가"를 객체로 만든다. 호출을 데이터로 승격시키면 그 데이터를 저장하고, 전달하고, 검사하고, 지연시키고, 반복할 수 있다. 구성 요소는 넷이다.

- **커맨드(command)**: 실행할 작업을 담은 객체
- **클라이언트**: 커맨드를 생성하는 쪽
- **인보커(invoker)**: 커맨드를 언제 실행할지 결정하는 쪽 (큐, 스케줄러)
- **타깃(target)**: 실제 작업이 수행되는 대상

JavaScript에서 가장 가벼운 커맨드는 **클로저**다. 이것을 흔히 **태스크(task) 패턴**이라 부른다.

```js
// 가장 단순한 커맨드: 인자를 묶은 함수 하나
function createSendTask(mailer, to, subject) {
  return () => mailer.send(to, subject)
}

const task = createSendTask(mailer, 'a@example.com', '환영합니다')
await queue.push(task)   // 실행 시점을 인보커가 결정한다
```

이 형태로 지연 실행과 큐잉은 이미 해결된다. 취소·재시도·감사·실행 취소가 필요할 때만 객체로 승격한다.

### 구현 코드

```js
// task.js
import { randomUUID } from 'node:crypto'

export class Task {
  constructor({ type, payload, run, undo = null, maxAttempts = 3 }) {
    this.id = randomUUID()
    this.type = type
    this.payload = payload      // 직렬화 가능한 순수 데이터
    this.createdAt = new Date()
    this.status = 'pending'     // pending | running | done | failed | cancelled
    this.attempts = 0
    this.maxAttempts = maxAttempts
    this.result = undefined
    this.error = null
    this.#run = run
    this.#undo = undo
    this.#controller = new AbortController()
  }

  #run; #undo; #controller

  get signal() { return this.#controller.signal }
  get canUndo() { return this.status === 'done' && typeof this.#undo === 'function' }

  cancel(reason = '사용자 취소') {
    if (this.status === 'done') return false
    this.status = 'cancelled'
    this.#controller.abort(new Error(reason))   // 실행 중인 I/O에 전파된다
    return true
  }

  async execute() {
    if (this.status === 'cancelled') throw this.#controller.signal.reason
    this.status = 'running'
    this.attempts++
    try {
      this.result = await this.#run(this.payload, { signal: this.signal })
      this.status = 'done'
      return this.result
    } catch (err) {
      this.error = err
      this.status = this.status === 'cancelled' ? 'cancelled' : 'failed'
      throw err
    }
  }

  async undo() {
    if (!this.canUndo) throw new Error(`되돌릴 수 없는 작업: ${this.type}`)
    await this.#undo(this.payload, this.result)
    this.status = 'undone'
  }

  // 감사 로그와 영속화를 위한 표현
  toJSON() {
    return {
      id: this.id, type: this.type, payload: this.payload,
      status: this.status, attempts: this.attempts,
      createdAt: this.createdAt.toISOString(),
      error: this.error ? { message: this.error.message, name: this.error.name } : null
    }
  }
}
```

인보커는 동시성 제한, 재시도, 감사를 담당한다. 커맨드는 이 정책들을 전혀 모른다.

```js
// runner.js
import { EventEmitter } from 'node:events'
import { setTimeout as delay } from 'node:timers/promises'

export class TaskRunner extends EventEmitter {
  #queue = []
  #running = 0

  constructor({ concurrency = 4, auditLog = console.log } = {}) {
    super()
    this.concurrency = concurrency
    this.auditLog = auditLog
  }

  submit(task) {
    this.#queue.push(task)
    this.auditLog('task.queued', task.toJSON())
    queueMicrotask(() => this.#pump())
    return task    // 호출자는 이 핸들로 취소·상태 조회를 한다
  }

  #pump() {
    while (this.#running < this.concurrency && this.#queue.length > 0) {
      const task = this.#queue.shift()
      if (task.status === 'cancelled') { this.auditLog('task.cancelled', task.toJSON()); continue }
      this.#running++
      this.#execute(task).finally(() => { this.#running--; this.#pump() })
    }
    if (this.#running === 0 && this.#queue.length === 0) this.emit('drain')
  }

  async #execute(task) {
    while (true) {
      try {
        const result = await task.execute()
        this.auditLog('task.succeeded', task.toJSON())
        this.emit('success', task, result)
        return
      } catch (err) {
        if (task.status === 'cancelled' || task.attempts >= task.maxAttempts) {
          this.auditLog('task.failed', task.toJSON())
          this.emit('failure', task, err)
          return
        }
        const backoff = 2 ** task.attempts * 100
        this.auditLog('task.retrying', { ...task.toJSON(), nextDelayMs: backoff })
        await delay(backoff)
      }
    }
  }
}
```

사용 예를 보면 커맨드를 객체로 만들어 얻은 것들이 한눈에 들어온다.

```js
const runner = new TaskRunner({ concurrency: 2, auditLog: (evt, data) =>
  logger.info({ evt, ...data }, '태스크 이벤트') })

const provision = new Task({
  type: 'provisionAccount',
  payload: { userId: 42, plan: 'pro' },
  run: async ({ userId, plan }, { signal }) => {
    const res = await fetch(`/internal/accounts/${userId}`, {
      method: 'POST', body: JSON.stringify({ plan }), signal
    })
    if (!res.ok) throw new Error(`프로비저닝 실패: ${res.status}`)
    return res.json()
  },
  undo: async ({ userId }, result) => {
    await fetch(`/internal/accounts/${userId}/rollback`, {
      method: 'POST', body: JSON.stringify({ txId: result.txId })
    })
  }
})

runner.submit(provision)

// 어디서든 취소할 수 있다 — 실행 중이면 AbortSignal이 fetch를 끊는다
setTimeout(() => provision.cancel('요청 타임아웃'), 5000)

// 후속 단계가 실패하면 되돌린다 (보상 트랜잭션)
runner.on('failure', async (failed) => {
  if (failed.type === 'chargeCard' && provision.canUndo) await provision.undo()
})
```

`payload`를 순수 데이터로 유지한 것이 결정적이다. 그 덕분에 `toJSON()`이 성립하고, 태스크를 Redis나 데이터베이스에 넣었다가 프로세스 재시작 후 복원할 수 있다. 실행 로직(`run`)은 `{ provisionAccount: provisionRun, chargeCard: chargeRun }` 같은 타입 → 핸들러 레지스트리에 두고, 복원 시 `type`으로 찾아 다시 결합하면 된다.

이 순간 커맨드 패턴은 **분산 작업 큐**가 된다. BullMQ와 Celery가 하는 일이 정확히 이것이며, 차이는 저장소와 워커 프로토콜의 성숙도뿐이다.

### 실전 사례

- **작업 큐**: BullMQ, Agenda, pg-boss의 잡(job)은 영속화된 커맨드 객체다.
- **에디터의 실행 취소 스택**: 각 편집을 `undo()`를 가진 커맨드로 만들고 스택에 쌓는다.
- **사가(saga)와 보상 트랜잭션**: 분산 트랜잭션의 각 단계를 커맨드로 만들고, 실패 시 역순으로 `undo()`를 호출한다.
- **CQRS의 커맨드 버스**: 명령을 객체로 표현해 검증·권한 검사·감사를 버스 계층에서 일괄 처리한다.

### 언제 쓰지 말아야 하는가

- **즉시 실행하고 결과만 쓰면 될 때.** 함수를 호출하라. 커맨드 객체는 지연·큐잉·취소·감사 중 최소 하나가 실제로 필요할 때만 값을 한다.
- **필요한 것이 지연 실행뿐일 때.** 클로저 하나면 충분하다. `Task` 클래스는 상태 기계와 직렬화가 필요할 때 꺼낸다.
- **영속화 요구가 진짜일 때 직접 만들려는 시도.** 프로세스 재시작을 견디고, 중복 실행을 막고, 죽은 워커의 잡을 회수해야 한다면 검증된 큐 라이브러리를 쓴다. 자체 구현은 정확히 이 지점에서 무너진다.
- **`undo()`가 실제로 불가능한 도메인.** 이미 발송된 이메일이나 승인된 결제는 되돌릴 수 없다. 이때 필요한 것은 실행 취소가 아니라 **보상 작업**이며, 이름을 정확히 붙이지 않으면 잘못된 기대를 만든다.

## 요약

- **전략은 합성으로, 템플릿은 상속으로** 같은 문제를 푼다. JavaScript에서는 함수가 일급이므로 대개 전략이 이기며, 전략의 집합은 클래스 계층이 아니라 객체 맵으로 표현하는 것이 이 언어다운 방식이다.
- **상태 패턴은 스스로 전략을 교체하는 전략 패턴**이다. 불리언 플래그 세 개가 만드는 여덟 조합 대신 유효한 상태 넷을 코드에 명시하면, 컨텍스트에서 조건문이 사라진다.
- **이터레이터는 JavaScript에서 패턴이 아니라 프로토콜**이다. `[Symbol.iterator]`를 구현하는 순간 `for...of`, 전개, 구조 분해, `Map`/`Set` 생성자가 전부 열린다.
- **제너레이터는 이터레이터의 문법적 대체재**이며, `yield*`로 재귀 순회를, 무한 시퀀스와 지연 평가로 상수 메모리 파이프라인을 가능하게 한다. `finally`는 조기 종료에도 실행되는 신뢰할 수 있는 정리 지점이다. `for await...of`는 여기에 I/O를 더해 페이지네이션·커서·큐를 하나의 순회 문법으로 통일하며, 기본이 순차 실행이라 백프레셔에는 유리하고 병렬 처리에는 불리하다.
- **모든 `Readable`은 비동기 이터러블이고, 비동기 제너레이터는 `pipeline()`의 변환 단계가 된다.** `Transform` 클래스 없이 평범한 함수로 스트림 처리를 조립할 수 있으며 백프레셔과 오류 전파는 그대로 유지된다.
- **미들웨어는 함수 파이프라인이다.** Express의 선형 모델은 배열과 인덱스 클로저가 전부이고, Koa의 양파 모델은 `compose` 함수 하나로 앞뒤 처리와 자연스러운 오류 경계를 얻는다.
- **커맨드는 호출을 데이터로 승격시킨다.** 지연·큐잉·재시도·취소·감사·실행 취소 중 최소 하나가 실제로 필요할 때만 값을 하며, 그렇지 않다면 함수를 그냥 호출하는 것이 옳다.

## 연습문제

1. **전략과 상태의 결합.** 14.1의 `Config`에 `.env`와 `.toml` 전략을 추가하고, 파일 확장자를 보고 전략을 자동 선택하는 `createConfig()`를 완성하라. 그 위에 "파일이 변경되면 자동으로 다시 로드하되, 파싱에 실패하면 직전의 유효한 설정을 유지한다"는 요구를 상태 패턴(`VALID`/`RELOADING`/`STALE`)으로 구현하고, `STALE` 상태에서 `get()`이 경고 이벤트를 발생시키도록 만들어라.

2. **비동기 제너레이터 파이프라인.** 대용량 NDJSON 로그 파일(gzip 압축)을 입력받아 다음을 수행하는 `pipeline()`을 작성하라. (a) 줄 단위 분할, (b) JSON 파싱 실패 줄을 별도 파일로 분리, (c) `status >= 500`인 레코드만 통과, (d) 1분 단위로 집계해 분당 오류 수를 CSV로 출력. 각 변환 단계를 배열 입력만으로 테스트할 수 있는 순수 비동기 제너레이터로 작성하고, 100MB 파일 처리 시 RSS가 일정하게 유지되는지 `process.memoryUsage()`로 검증하라(9장 참조).

3. **양파 모델 프레임워크와 태스크 러너의 통합.** 14.8의 `compose()`를 사용해 최소 HTTP 프레임워크를 만들고, 요청 ID 부착·응답 시간 측정·오류 경계·라우팅 미들웨어를 구현하라. 그 위에 `POST /jobs` 엔드포인트를 두어 요청 본문을 14.9의 `Task`로 변환해 `TaskRunner`에 제출하고, `GET /jobs/:id`로 상태를 조회하며 `DELETE /jobs/:id`로 취소할 수 있게 하라. 취소 시 실행 중인 `fetch`가 실제로 중단되는지 `AbortSignal`로 확인하고, 프로세스가 SIGTERM을 받으면 큐에 남은 태스크를 영속화한 뒤 종료하도록 만들어라(9장 참조).
