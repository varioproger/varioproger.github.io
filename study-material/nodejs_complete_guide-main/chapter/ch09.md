# 9장. 프로세스, 버퍼, 그리고 OS 리소스

Node.js 애플리케이션은 결국 운영체제(OS) 위에서 도는 하나의 프로세스다. 이벤트 루프와 스트림 같은 상위 추상화(7장 참조)에 익숙해지면 이 사실을 잊기 쉽지만, 프로덕션에서 터지는 문제의 상당수는 추상화 아래층에서 발생한다. 컨테이너가 보낸 SIGTERM을 무시해 배포마다 요청이 끊기고, `process.exit()`가 로그를 잘라먹고, UTF-8 한글이 버퍼 경계에서 깨지고, `os.cpus()`를 믿고 워커를 32개 띄웠다가 CPU 0.5코어짜리 파드에서 컨텍스트 스위칭에 죽는다.

이 장은 그 아래층을 다룬다. `process` 객체로 자신의 자원 사용을 관측하는 법, 인자와 환경 변수와 표준 스트림으로 외부와 소통하는 법, 시그널을 받아 우아하게 종료하는 법, `Buffer`로 바이너리를 다루는 법, 인코딩 변환의 함정, 그리고 `os`·`path`·`url` 모듈로 실행 환경을 정확히 파악하는 법을 차례로 살펴본다. 특히 9.3의 우아한 종료(graceful shutdown)는 이 장의 핵심이며, 무중단 배포를 지탱하는 실질적인 기반이다.

## 9.1 `process` 객체 완전 정복

### 왜 필요한가

`process`는 실행 중인 Node.js 프로세스 자신을 나타내는 전역 객체다. `require`나 `import` 없이 어디서나 접근할 수 있으며, 프로세스의 정체(pid, 버전, 실행 인자), 자원 사용량(메모리, CPU), 외부와의 접점(환경 변수, 표준 스트림, 시그널), 생명주기(종료 코드, 종료 훅)를 모두 이 하나의 객체가 노출한다. 관측 가능성(observability)의 출발점이자 종료 처리의 출발점이 여기다.

ESM에서도 `process`는 전역이지만, 명시적으로 `import process from 'node:process'`라고 적는 편을 권한다. 어떤 모듈이 프로세스 상태에 의존하는지 임포트 목록만 보고 알 수 있고, 테스트에서 모킹하기도 쉽다.

### 어떻게 동작하는가

프로세스의 정체부터 보자. `process.pid`는 자신의 프로세스 ID, `process.ppid`는 부모 프로세스 ID다. 컨테이너 안에서 `pid`가 1이면 자신이 init 프로세스라는 뜻이고, 이는 9.3에서 다룰 시그널 문제와 직결된다.

```js
import process from 'node:process'

console.log('pid', process.pid, 'ppid', process.ppid)
console.log('node', process.version)          // 'v22.11.0'
console.log('플랫폼', process.platform, process.arch) // 'linux' 'x64'
console.log('실행 파일', process.execPath)
console.log('실행 인자', process.execArgv)    // ['--max-old-space-size=512'] 같은 노드 옵션
console.log('가동 시간(초)', process.uptime().toFixed(2))
```

가장 자주 쓰이는 것은 `process.memoryUsage()`다. 반환되는 다섯 필드는 각각 의미가 다르며, 이를 구분하지 못하면 메모리 누수 진단이 불가능하다.

```js
const m = process.memoryUsage()
console.log(m)
// {
//   rss: 51200000,        // 상주 집합 크기(Resident Set Size)
//   heapTotal: 20971520,  // V8이 OS로부터 확보한 힙 총량
//   heapUsed: 15728640,   // 그중 실제로 객체가 점유한 양
//   external: 1638400,    // V8이 관리하는 C++ 객체의 메모리
//   arrayBuffers: 819200  // ArrayBuffer/Buffer가 점유한 외부 메모리(external의 부분집합)
// }
```

- **rss**: 프로세스가 물리 메모리에 올려둔 전체 크기다. 힙, 스택, 코드 세그먼트, 네이티브 할당을 모두 포함한다. 컨테이너의 OOM 킬러가 보는 값이 사실상 이것이므로, 메모리 상한 대비 여유를 볼 때 기준으로 삼아야 할 값이다.
- **heapTotal / heapUsed**: V8 자바스크립트 힙이다. `heapUsed`가 계단식으로 증가하고 GC 후에도 내려오지 않으면 자바스크립트 객체 누수다. 반대로 `heapUsed`는 평평한데 `rss`만 오른다면 누수는 네이티브 쪽에 있다.
- **external**: V8이 관리하는 C++ 객체가 붙잡고 있는 메모리다. `Buffer`, zlib 스트림, TLS 세션 등이 여기 잡힌다.
- **arrayBuffers**: `ArrayBuffer`와 그 위에 얹힌 `Buffer`가 쓰는 양이다. 스트림 처리 중 백프레셔가 깨져 버퍼가 쌓이면 이 값이 먼저 튄다.

`process.memoryUsage()`는 시스템 콜을 동반해 그리 싸지 않다. 초당 수천 번 호출하는 코드는 그 자체가 병목이 된다. `rss`만 필요하다면 훨씬 가벼운 `process.memoryUsage.rss()`가 있다.

CPU와 I/O 사용량은 `process.cpuUsage()`와 `process.resourceUsage()`로 얻는다.

```js
const start = process.cpuUsage()
crunchNumbers()
const diff = process.cpuUsage(start)   // 인자를 주면 델타를 반환한다
console.log('user μs', diff.user, 'system μs', diff.system)

const r = process.resourceUsage()
console.log('최대 RSS(KB)', r.maxRSS)
console.log('자발적 컨텍스트 스위치', r.voluntaryContextSwitches)
console.log('비자발적 컨텍스트 스위치', r.involuntaryContextSwitches)
```

`involuntaryContextSwitches`가 급증한다면 CPU 할당량(quota)에 눌리고 있다는 신호이며, 워커 수를 줄여야 한다는 근거가 된다(9.6 참조).

시간 측정에는 `Date.now()` 대신 `process.hrtime.bigint()`를 쓴다. 나노초 단위 단조 증가(monotonic) 시계라서 NTP 보정이나 시스템 시간 변경의 영향을 받지 않는다.

```js
const t0 = process.hrtime.bigint()
await doWork()
const elapsedMs = Number(process.hrtime.bigint() - t0) / 1e6
console.log(`소요 ${elapsedMs.toFixed(3)}ms`)
```

작업 디렉터리는 `process.cwd()`로 읽고 `process.chdir()`로 바꾼다. 다만 `chdir()`은 프로세스 전역 상태를 바꾸므로 라이브러리 코드에서는 절대 호출하면 안 된다. 동시에 실행되는 다른 비동기 작업의 상대 경로 해석을 조용히 망가뜨린다. 경로는 `chdir` 대신 `path.resolve()`로 명시적으로 조합하는 편이 안전하다(9.6 참조).

### 코드: `process.exit()`가 출력을 잘라먹는 문제

종료 코드를 정하는 방법은 둘이다. `process.exitCode = 1`처럼 값을 대입해 두면 이벤트 루프가 자연스럽게 비었을 때 그 코드로 종료한다. 반면 `process.exit(1)`은 **즉시** 종료하며 대기 중인 비동기 작업을 모두 버린다. 문제는 파일이나 파이프로 리다이렉트된 `stdout`이 비동기라는 점이다.

```js
// exit-truncation.mjs
import process from 'node:process'

for (let i = 0; i < 20000; i++) {
  console.log(`line ${i}`)
}
process.exit(0)   // 위험: 아직 커널에 넘기지 못한 출력이 버려진다
```

터미널에 그냥 실행하면 멀쩡해 보인다. TTY로 나가는 `stdout`은 동기 쓰기이기 때문이다. 그러나 파이프로 넘기면 결과가 달라진다.

```bash
$ node exit-truncation.mjs | wc -l
8192          # 20000이 아니다. 잘렸다.
```

같은 코드를 `exitCode`로 바꾸면 온전히 나온다.

```js
for (let i = 0; i < 20000; i++) {
  console.log(`line ${i}`)
}
process.exitCode = 0   // 이벤트 루프가 비면 그때 종료한다. 출력이 온전하다.
```

이 차이는 로그를 파일이나 사이드카 수집기로 흘리는 컨테이너 환경에서 그대로 재현된다. "에러가 났는데 로그의 마지막 몇 줄이 항상 없다"는 증상의 범인은 대개 `process.exit()`다.

### 실무 함정

- **`process.exit()`는 최후의 수단으로만**: 정상 경로에서는 `exitCode` 대입 후 자연 종료를 택한다. `exit()`는 우아한 종료가 타임아웃됐을 때의 강제 탈출용으로 남겨둔다(9.3 참조).
- **`beforeExit`는 `exit()`에서 안 불린다**: `process.on('exit')` 핸들러 안에서는 동기 코드만 실행된다. 비동기 정리 로직을 `exit` 훅에 넣으면 절대 완료되지 않는다.
- **`unhandledRejection`과 `uncaughtException`**: Node 15부터 처리되지 않은 프로미스 거부는 기본적으로 프로세스를 종료시킨다. 핸들러를 달아 "무시"하면 애플리케이션이 손상된 상태로 계속 도는 최악의 상황이 된다. 로깅 후 종료가 원칙이다.
- **`memoryUsage()`를 헬스체크 엔드포인트마다 호출하지 않는다**: 주기적 샘플링(예: 10초)으로 충분하며, 그 값을 메트릭으로 내보내는 편이 낫다.

## 9.2 명령행 인자, 환경 변수, 표준 스트림

### 왜 필요한가

프로세스는 세 가지 통로로 외부 세계와 연결된다. 시작할 때 한 번 주어지는 **명령행 인자(command-line arguments)**, 실행 환경이 상속시키는 **환경 변수(environment variable)**, 그리고 실행 내내 열려 있는 **표준 스트림(standard streams)** 이다. 12요소 앱(Twelve-Factor App) 원칙이 설정을 환경 변수로 주입하라고 말하는 이유도, CLI 도구가 파이프로 조립되는 이유도 모두 이 세 통로 위에 있다.

과거에는 인자 파싱에 `yargs`나 `commander` 같은 외부 의존성이 필수였다. Node 18.11부터 `util.parseArgs()`가 내장되어 Node 20 LTS 기준으로는 대부분의 CLI가 의존성 없이 만들어진다.

### 어떻게 동작하는가

`process.argv`는 문자열 배열이며 첫 두 요소가 고정되어 있다. `argv[0]`은 노드 실행 파일 경로, `argv[1]`은 실행된 스크립트의 절대 경로, 그 뒤부터가 사용자 인자다. 그래서 실제 인자는 `process.argv.slice(2)`다.

`util.parseArgs()`는 이 배열을 옵션 스키마에 따라 해석한다.

```js
// cli.mjs
import { parseArgs } from 'node:util'
import process from 'node:process'

const { values, positionals } = parseArgs({
  args: process.argv.slice(2),
  options: {
    output:  { type: 'string',  short: 'o', default: 'out.json' },
    verbose: { type: 'boolean', short: 'v', default: false },
    // multiple: true 이면 반복 지정한 값을 배열로 모은다
    include: { type: 'string',  short: 'i', multiple: true, default: [] },
    help:    { type: 'boolean', short: 'h', default: false }
  },
  allowPositionals: true,   // 기본값은 false다. 켜지 않으면 위치 인자에서 에러가 난다
  strict: true              // 정의하지 않은 옵션이 오면 예외를 던진다
})

if (values.help) {
  console.log('사용법: cli [옵션] <입력파일...>')
  process.exitCode = 0
} else {
  console.log('옵션', values)
  console.log('입력', positionals)
}
```

```bash
$ node cli.mjs -v -o result.json -i a.txt -i b.txt src/
# 옵션 { output: 'result.json', verbose: true, include: [ 'a.txt', 'b.txt' ], help: false }
# 입력 [ 'src/' ]
```

`strict: true`(기본값)는 오타 난 옵션을 조용히 무시하는 대신 즉시 실패시킨다. 배포 스크립트에서 `--dry-run`을 `--dryrun`으로 잘못 적어 실제로 실행돼 버리는 사고를 막아준다.

환경 변수는 `process.env`로 읽는다. 값은 **항상 문자열**이며, 존재하지 않으면 `undefined`다. 여기서 두 가지 실수가 반복된다. 하나는 `process.env.DEBUG`가 `'false'`일 때 문자열 `'false'`는 참(truthy)이라는 점이고, 다른 하나는 숫자 변환을 빼먹는 것이다. 설정은 한곳에서 검증하고 타입을 확정한 뒤 그 결과만 애플리케이션에 노출하는 편이 좋다.

```js
// config.mjs — 설정을 한곳에서 검증하고 동결한다
import process from 'node:process'

function required(name) {
  const v = process.env[name]
  if (v === undefined || v === '') throw new Error(`환경 변수 ${name}이(가) 필요하다`)
  return v
}

function int(name, fallback) {
  const raw = process.env[name]
  if (raw === undefined) return fallback
  const n = Number.parseInt(raw, 10)
  if (Number.isNaN(n)) throw new Error(`환경 변수 ${name}은(는) 정수여야 한다: ${raw}`)
  return n
}

function bool(name, fallback = false) {
  const raw = process.env[name]?.toLowerCase()
  if (raw === undefined) return fallback
  return raw === '1' || raw === 'true' || raw === 'yes'
}

export const config = Object.freeze({
  nodeEnv:      process.env.NODE_ENV ?? 'development',
  port:         int('PORT', 3000),
  databaseUrl:  required('DATABASE_URL'),
  shutdownMs:   int('SHUTDOWN_TIMEOUT_MS', 10_000),
  tracing:      bool('ENABLE_TRACING')
})
```

`.env` 파일을 읽기 위해 `dotenv`를 설치할 필요도 이제는 없다. Node 20.6부터 `--env-file` 플래그가, Node 20.12부터 `process.loadEnvFile()`이 제공된다.

```bash
$ node --env-file=.env --env-file=.env.local server.mjs   # 뒤쪽 파일이 앞을 덮어쓴다
```

```js
import process from 'node:process'

// 파일이 없으면 예외를 던지므로 선택적 로딩은 try로 감싼다
try { process.loadEnvFile('.env.local') } catch { /* 없으면 무시 */ }
```

표준 스트림은 `process.stdin`, `process.stdout`, `process.stderr` 세 개다. 셋 다 스트림이지만 성질이 미묘하게 다르다. 파일이나 TTY로 연결됐을 때는 동기 쓰기, 파이프로 연결됐을 때는 비동기 쓰기가 된다. 이 차이가 9.1에서 본 출력 잘림의 원인이다.

stdin을 읽을 때는 비동기 이터레이터가 가장 간결하다.

```js
// filter.mjs — 표준 입력에서 줄을 읽어 패턴에 맞는 줄만 출력한다
import { createInterface } from 'node:readline'
import process from 'node:process'

const pattern = new RegExp(process.argv[2] ?? '.')

// TTY라면 사람이 직접 실행한 것이므로 사용법을 안내한다
if (process.stdin.isTTY) {
  console.error('사용법: cat file.log | node filter.mjs "ERROR"')
  process.exitCode = 1
} else {
  const rl = createInterface({ input: process.stdin, crlfDelay: Infinity })
  for await (const line of rl) {
    if (pattern.test(line)) process.stdout.write(line + '\n')
  }
}
```

`isTTY` 판별은 CLI 도구의 품질을 가른다. 컬러 출력, 진행 막대, 대화형 프롬프트는 TTY일 때만 켜야 한다. 파이프로 연결된 상태에서 ANSI 이스케이프 코드를 뿌리면 다운스트림 도구가 파싱에 실패한다.

### 실무 함정

- **로그는 stdout, 진단은 stderr**: 데이터 출력과 진단 메시지를 같은 스트림에 섞으면 파이프라인이 오염된다. `console.log`는 stdout, `console.error`는 stderr로 간다.
- **`process.env`에 비밀 값을 넣은 채 덤프하지 않는다**: 예외 리포터가 `process.env` 전체를 직렬화해 외부로 보내면 그대로 자격 증명 유출이다.
- **`--env-file`은 프로덕션 설정 주입 수단이 아니다**: 로컬 개발과 CI 편의용이며, 프로덕션에서는 오케스트레이터의 시크릿 주입을 쓴다.
- **`process.stdout.write()`의 반환값**: 대량 출력 시 `false`를 반환하면 백프레셔가 걸린 것이다. `drain` 이벤트를 기다리지 않으면 메모리가 부푼다(7장 참조).

## 9.3 시그널 처리와 우아한 종료(graceful shutdown)

### 왜 필요한가

배포는 프로세스를 죽이고 새로 띄우는 일이다. 오토스케일링도, 노드 교체도, 스팟 인스턴스 회수도 마찬가지다. 즉 프로세스가 죽는 것은 예외 상황이 아니라 **일상**이다. 그런데 종료 처리를 하지 않은 서버는 죽는 순간 처리 중이던 요청을 그대로 끊는다. 사용자에게는 502가 보이고, 결제 트랜잭션은 절반만 커밋되며, 큐에서 꺼낸 메시지는 처리도 완료도 되지 않은 채 사라진다. 하루에 열 번 배포하는 팀이라면 이 손실은 매일 누적된다.

우아한 종료는 "죽으라는 신호를 받은 뒤, 새 일은 받지 않되 하던 일은 끝내고 죽는" 규율이다. 이를 구현하려면 먼저 시그널(signal)을 이해해야 한다.

### 어떻게 동작하는가

POSIX 시그널 중 Node.js 서버가 신경 써야 할 것은 셋이다.

- **SIGTERM (15)**: "정리하고 종료하라"는 정중한 요청이다. `kill`의 기본값이며, 쿠버네티스가 파드를 내릴 때, 도커가 `docker stop`을 실행할 때, systemd가 서비스를 멈출 때 보내는 시그널이다. 가로챌 수 있으며, **우아한 종료의 진입점**이다.
- **SIGINT (2)**: 터미널에서 Ctrl+C를 눌렀을 때 포그라운드 프로세스 그룹에 전달된다. 개발 중에 만나는 종료 신호이며, 역시 가로챌 수 있다.
- **SIGHUP (1)**: 원래는 제어 터미널이 끊겼음을 알리는 시그널이다. 관례적으로 데몬에서는 "설정을 다시 읽으라"는 의미로 재해석해 쓴다. Node의 기본 동작은 종료다.

**SIGKILL (9)** 과 **SIGSTOP (19)** 은 가로챌 수 없다. 오케스트레이터는 SIGTERM 후 유예 기간(쿠버네티스의 `terminationGracePeriodSeconds`, 기본 30초)이 지나면 SIGKILL을 보낸다. 우리의 종료 시퀀스는 반드시 이 유예 기간보다 짧게 끝나야 한다.

여기서 컨테이너 환경 특유의 함정이 나온다. Dockerfile에 다음처럼 적었다고 하자.

```dockerfile
CMD npm start        # 셸 형식(shell form) — 위험하다
```

셸 형식은 `/bin/sh -c "npm start"`로 실행되므로 PID 1은 셸이고 Node는 그 자식이다. 그런데 `sh`는 시그널을 자식에게 전달하지 않는다. 결과적으로 SIGTERM은 셸이 삼키고, Node는 아무것도 모른 채 30초 뒤 SIGKILL로 즉사한다. 종료 코드를 아무리 잘 짜도 호출조차 되지 않는다. 게다가 `npm`을 거치면 npm이 PID 1이 되어 같은 문제가 반복된다.

해결은 **exec 형식**으로 노드를 직접 PID 1로 띄우는 것이다.

```dockerfile
CMD ["node", "server.mjs"]     # exec 형식 — Node가 PID 1이 되어 시그널을 직접 받는다
```

PID 1에는 또 하나의 특성이 있다. 리눅스 커널은 PID 1에 대해 **핸들러가 등록되지 않은 시그널의 기본 동작을 적용하지 않는다.** 즉 SIGTERM 핸들러를 등록하지 않은 상태로 PID 1이 되면, SIGTERM을 받아도 프로세스가 죽지 않는다. "`docker stop`이 항상 10초를 기다린다"는 증상이 이것이다. 핸들러를 등록하면 해결되며, 좀비 프로세스 수확까지 필요하다면 `--init` 플래그나 `tini` 같은 최소 init을 PID 1로 둔다.

### 코드: 완전한 우아한 종료 시퀀스

종료 시퀀스는 순서가 전부다. (1) 새 연결 거부와 헬스체크 실패 전환, (2) 진행 중 요청 완료 대기, (3) 유휴 커넥션 정리, (4) 커넥션 풀·큐·타이머 등 외부 자원 해제, (5) 타임아웃 시 강제 종료.

```js
// server.mjs
import http from 'node:http'
import process from 'node:process'
import { setTimeout as delay } from 'node:timers/promises'
import { config } from './config.mjs'
import { pool } from './db.mjs'          // 예: pg.Pool
import { consumer } from './queue.mjs'   // 예: 메시지 큐 컨슈머

let shuttingDown = false

const server = http.createServer(async (req, res) => {
  // (1) 헬스체크는 종료가 시작되면 즉시 실패로 전환한다.
  //     로드밸런서가 이 파드를 라우팅 대상에서 빼도록 유도하는 것이 목적이다.
  if (req.url === '/healthz') {
    res.writeHead(shuttingDown ? 503 : 200, { 'content-type': 'text/plain' })
    return res.end(shuttingDown ? 'shutting down' : 'ok')
  }

  // 종료 중에는 keep-alive 재사용을 막아 클라이언트가 새 대상으로 붙게 한다
  if (shuttingDown) res.setHeader('Connection', 'close')

  await handleRequest(req, res)
})

// keep-alive 타임아웃은 로드밸런서의 유휴 타임아웃보다 길게 잡는다(경쟁 조건 방지)
server.keepAliveTimeout = 72_000
server.headersTimeout = 75_000

server.listen(config.port, () => {
  console.log(`listening on ${config.port} (pid ${process.pid})`)
})

async function shutdown(signal) {
  if (shuttingDown) return       // 재진입 방지: Ctrl+C 연타에도 시퀀스는 한 번만 돈다
  shuttingDown = true
  console.log(`[shutdown] ${signal} 수신, 종료 시퀀스 시작`)

  // (5) 안전망: 정해진 시간 안에 끝나지 않으면 강제 종료한다.
  //     unref()로 이 타이머 자체가 이벤트 루프를 붙잡지 않게 한다.
  const forceTimer = setTimeout(() => {
    console.error('[shutdown] 타임아웃, 강제 종료한다')
    process.exit(1)
  }, config.shutdownMs).unref()

  try {
    // (1) 라우팅에서 빠지기까지의 유예. LB의 헬스체크 주기를 고려한 값이다.
    await delay(config.drainDelayMs ?? 5_000)

    // (2) 새 연결을 거부하고, 진행 중인 요청이 끝나기를 기다린다.
    //     close()는 즉시 반환하지 않으며, 모든 연결이 닫혀야 콜백이 불린다.
    const closed = new Promise((resolve, reject) =>
      server.close(err => (err ? reject(err) : resolve()))
    )

    // (3) 요청을 처리 중이지 않은 keep-alive 연결을 즉시 끊는다.
    //     이것이 없으면 유휴 커넥션 때문에 close()가 keepAliveTimeout만큼 지연된다.
    server.closeIdleConnections()

    // 유예 시간의 절반이 지나도 남아 있으면 처리 중인 연결까지 끊는다
    const hardCut = setTimeout(() => {
      console.warn('[shutdown] 남은 연결을 강제로 끊는다')
      server.closeAllConnections()
    }, config.shutdownMs / 2).unref()

    await closed
    clearTimeout(hardCut)
    console.log('[shutdown] HTTP 서버 종료 완료')

    // (4) 외부 자원 정리: 컨슈머를 먼저 멈추고, 그다음 DB 풀을 닫는다.
    //     순서를 뒤집으면 처리 중인 메시지가 닫힌 풀에 질의해 실패한다.
    await consumer.stop()
    await pool.end()
    console.log('[shutdown] 자원 정리 완료')

    clearTimeout(forceTimer)
    process.exitCode = 0        // exit()가 아니라 exitCode로 자연 종료한다
  } catch (err) {
    console.error('[shutdown] 종료 중 오류', err)
    process.exitCode = 1
  }
}

for (const signal of ['SIGTERM', 'SIGINT']) {
  process.on(signal, () => { void shutdown(signal) })
}

// 복구 불가능한 오류: 로깅 후 같은 시퀀스로 종료한다. 무시하지 않는다.
process.on('uncaughtException', err => {
  console.error('[fatal] uncaughtException', err)
  process.exitCode = 1
  void shutdown('uncaughtException')
})
process.on('unhandledRejection', reason => {
  console.error('[fatal] unhandledRejection', reason)
  process.exitCode = 1
  void shutdown('unhandledRejection')
})
```

`server.closeIdleConnections()`와 `server.closeAllConnections()`는 Node 18.2에서 추가된 메서드로, 그 이전에는 소켓을 직접 추적해야 했던 문제를 해결한다. HTTP keep-alive가 켜진 상태에서 `server.close()`만 호출하면 유휴 커넥션이 살아 있는 한 콜백이 불리지 않아 종료가 `keepAliveTimeout`만큼 지연된다. 두 메서드의 역할 분담은 명확하다. `closeIdleConnections()`는 요청을 처리하고 있지 **않은** 소켓만 끊으므로 진행 중인 작업에 안전하고, `closeAllConnections()`는 처리 중인 것까지 끊으므로 최후 수단이다.

`await delay(...)`로 라우팅 제외를 기다리는 단계가 의아할 수 있지만 반드시 필요하다. 쿠버네티스에서 SIGTERM 전달과 엔드포인트 제거는 **병렬로** 일어나며 순서가 보장되지 않는다. 이 유예가 없으면 서버가 이미 닫힌 뒤에 로드밸런서가 보낸 요청이 도착해 연결 거부가 발생한다.

### 실무 함정

- **핸들러 안에서 `process.exit()`을 바로 부르는 것**: 우아한 종료를 쓰겠다면서 첫 줄에 `exit()`를 부르는 코드가 흔하다. 강제 종료는 타임아웃 경로에만 둔다.
- **워커 프로세스를 잊는 것**: 클러스터나 워커 스레드를 쓴다면 프라이머리가 시그널을 받아 워커들에게 전파하고, 워커의 종료를 기다린 뒤 자신이 종료해야 한다(25장 참조).
- **`terminationGracePeriodSeconds`보다 긴 타임아웃**: 애플리케이션 타임아웃이 오케스트레이터 유예보다 길면 SIGKILL이 먼저 온다. 유예 30초라면 애플리케이션은 20초 안에 끝내도록 잡는다.
- **비동기 시그널 핸들러의 예외**: `shutdown()`이 던진 예외는 아무도 잡지 않는다. 위 코드처럼 내부를 `try/catch`로 감싼다.
- **`SIGHUP`으로 설정 리로드를 구현할 때**: 재시작 없이 설정만 갈아끼우려면 리로드가 원자적이어야 한다. 새 설정 검증에 실패하면 기존 설정을 유지하고 로그만 남긴다.

## 9.4 `Buffer`와 `TypedArray`: 바이너리 데이터 다루기

### 왜 필요한가

네트워크에서 오는 것도, 디스크에서 읽는 것도 본질은 바이트 열이다. 문자열은 그 바이트를 특정 인코딩으로 해석한 결과일 뿐이다. 이미지 썸네일 생성, 커스텀 바이너리 프로토콜 구현, 암호화, 압축, 파일 시그니처 판별 같은 작업은 바이트를 바이트로 다뤄야 한다. Node.js에서 그 도구가 `Buffer`다.

`Buffer`는 자바스크립트에 `TypedArray`가 없던 시절에 만들어진 Node 고유 타입이지만, 지금은 **`Uint8Array`의 서브클래스**다. 이 사실이 중요한 이유는 상호 운용성 때문이다. `Buffer`는 `Uint8Array`를 받는 모든 웹 표준 API(`TextDecoder`, `crypto.subtle`, `fetch`의 본문 등)에 그대로 전달할 수 있다. 반대 방향으로는 `Buffer.from(uint8array)`가 복사를 하고, `Buffer.from(u8.buffer, u8.byteOffset, u8.byteLength)`는 메모리를 공유한다.

### 어떻게 동작하는가

버퍼를 만드는 방법은 셋이며, 그중 둘은 보안적으로 성격이 다르다.

```js
import { Buffer } from 'node:buffer'

const a = Buffer.alloc(8)          // 0으로 초기화된 8바이트. 안전하다.
const b = Buffer.allocUnsafe(8)    // 초기화하지 않는다. 이전 메모리 내용이 그대로 남아 있다.
const c = Buffer.from('안녕', 'utf8')   // 문자열을 인코딩해 새 버퍼를 만든다

console.log(a) // <Buffer 00 00 00 00 00 00 00 00>
console.log(b) // <Buffer 68 74 74 70 2f 31 2e 31>  ← 이전에 쓰이던 데이터의 잔재일 수 있다
console.log(c.length) // 6 — '안녕'은 UTF-8로 6바이트다
```

`allocUnsafe()`가 빠른 이유는 0으로 채우는 비용을 생략하기 때문이다. 대신 반환된 메모리에는 **직전에 해제된 다른 버퍼의 내용**이 남아 있을 수 있다. 그 버퍼가 세션 토큰이나 비밀번호를 담고 있었다면, 초기화 없이 그대로 응답에 실려 나가는 정보 유출이 된다. 실제로 Node 생태계에서 이 문제로 CVE가 발행된 적이 있다. 규칙은 단순하다. **할당 직후 전 영역을 반드시 덮어쓴다고 스스로 증명할 수 없다면 `alloc()`을 쓴다.**

`allocUnsafe()`는 성능을 위해 **버퍼 풀(buffer pool)** 을 쓴다. `Buffer.poolSize`(기본 8KiB)보다 작은 요청은 미리 잡아둔 큰 `ArrayBuffer`의 한 조각을 잘라 반환한다.

```js
const small = Buffer.allocUnsafe(1024)
const big   = Buffer.allocUnsafe(16 * 1024)

console.log(Buffer.poolSize)        // 8192
console.log(small.buffer.byteLength) // 8192 — 풀을 공유한다
console.log(big.buffer.byteLength)   // 16384 — 풀 크기를 넘어 단독 할당됐다
console.log(small.byteOffset)        // 0이 아닐 수 있다
```

여기서 함정이 나온다. 풀에서 잘라낸 버퍼의 `.buffer` 속성은 **풀 전체**를 가리킨다. `small.buffer`를 그대로 다른 API에 넘기면 자기 것이 아닌 8KiB 전체를 넘기는 셈이다. `Buffer`를 `ArrayBuffer`로 변환할 때는 항상 `byteOffset`과 `byteLength`를 함께 써야 한다.

```js
// 잘못된 변환: 풀 전체가 노출된다
const wrong = small.buffer
// 올바른 변환: 자기 영역만 잘라 복사한다
const right = small.buffer.slice(small.byteOffset, small.byteOffset + small.byteLength)
```

버퍼를 이어붙이고 자르는 연산에서도 복사 여부를 구분해야 한다.

```js
const chunks = []
for await (const chunk of stream) chunks.push(chunk)
const body = Buffer.concat(chunks)          // 새 메모리에 복사한다(총 길이를 주면 더 빠르다)

const header = body.subarray(0, 16)         // 복사하지 않는다. 같은 메모리를 본다.
header[0] = 0xff
console.log(body[0])                        // 255 — 원본이 함께 바뀌었다
```

`Buffer.prototype.slice()`는 이름과 달리 `Array.prototype.slice()`처럼 복사하지 않는다. `subarray()`와 동일하게 **뷰(view)** 를 반환한다. 이 비직관성 때문에 `slice()`는 Node 문서에서 비권장으로 표시되었으며, 뷰가 필요하면 `subarray()`를, 복사가 필요하면 `Buffer.from(source.subarray(a, b))`를 쓰는 것이 명확하다. 뷰의 또 다른 부작용은 메모리 유지다. 10MiB 응답에서 16바이트 헤더만 `subarray`로 떼어 캐시에 보관하면, 그 16바이트가 10MiB 전체의 해제를 막는다.

### 코드: `DataView`로 바이너리 프로토콜 파싱하기

고정 레이아웃의 바이너리 메시지를 다룰 때는 `DataView`가 가장 명확하다. 엔디언(endianness)을 호출마다 명시하기 때문이다.

```js
// 프로토콜: [magic:u32 BE][version:u8][flags:u8][length:u16 BE][payload:length bytes]
const MAGIC = 0x4e4f4445   // 'NODE'
const HEADER_SIZE = 8

export function encodeFrame(version, flags, payload) {
  const frame = Buffer.alloc(HEADER_SIZE + payload.length)
  const view = new DataView(frame.buffer, frame.byteOffset, frame.byteLength)
  view.setUint32(0, MAGIC, false)   // false = 빅엔디언. 네트워크 바이트 순서다.
  view.setUint8(4, version)
  view.setUint8(5, flags)
  view.setUint16(6, payload.length, false)
  payload.copy(frame, HEADER_SIZE)
  return frame
}

export function decodeFrame(buf) {
  // 부분 수신 가능성을 항상 먼저 확인한다. TCP는 메시지 경계를 보장하지 않는다.
  if (buf.length < HEADER_SIZE) return null
  const view = new DataView(buf.buffer, buf.byteOffset, buf.byteLength)
  if (view.getUint32(0, false) !== MAGIC) throw new Error('매직 넘버 불일치')
  const length = view.getUint16(6, false)
  if (buf.length < HEADER_SIZE + length) return null   // 아직 페이로드가 덜 왔다
  return {
    version: view.getUint8(4),
    flags:   view.getUint8(5),
    payload: Buffer.from(buf.subarray(HEADER_SIZE, HEADER_SIZE + length)), // 복사해 소유권 분리
    consumed: HEADER_SIZE + length
  }
}
```

`Buffer`에도 `readUInt32BE()` 같은 메서드가 있어 같은 일을 할 수 있다. 차이는 취향과 이식성이다. `DataView`는 브라우저에서도 동작하므로 클라이언트와 코드를 공유할 때 유리하고, `Buffer` 메서드는 Node 전용이지만 더 짧다.

### 실무 함정

- **`allocUnsafe()`를 습관적으로 쓰지 않는다**: 이득은 마이크로초 단위이고 손실은 정보 유출이다.
- **버퍼를 문자열로 바꿔 비교하지 않는다**: 비밀 값 비교는 `crypto.timingSafeEqual()`로 한다. `===` 비교는 타이밍 공격에 취약하다.
- **`buf.toString()`의 기본 인코딩은 UTF-8이다**: 바이너리 데이터를 무심코 문자열로 바꾸면 잘못된 바이트가 U+FFFD로 치환되어 **되돌릴 수 없다**.
- **최대 크기 한계**: `buffer.constants.MAX_LENGTH`를 넘는 버퍼는 만들 수 없다. 큰 데이터는 스트림으로 다룬다(7장 참조).

## 9.5 인코딩과 문자열 변환의 함정

### 왜 필요한가

한국어 개발자에게 인코딩 문제는 남의 일이 아니다. ASCII만 쓰는 환경에서는 "1문자 = 1바이트"라는 착각이 끝까지 들키지 않지만, 한글이 섞이는 순간 모든 가정이 무너진다. 스트림에서 받은 청크를 그때그때 문자열로 바꾸면 한글이 깨지고, 길이 제한을 문자 수로 검사한 API가 DB의 바이트 제한을 넘겨 실패하며, 이모지가 들어오면 `length`가 예상의 두 배로 나온다. 이 절은 그 각각의 원인과 처방을 다룬다.

### 어떻게 동작하는가

UTF-8은 가변 길이 인코딩이다. ASCII 문자는 1바이트, 대부분의 라틴·그리스·키릴 문자는 2바이트, 한글과 한자를 포함한 기본 다국어 평면(BMP)의 문자는 3바이트, 이모지 같은 보충 평면 문자는 4바이트를 쓴다.

```js
console.log('a'.length, Buffer.byteLength('a'))        // 1 1
console.log('한'.length, Buffer.byteLength('한'))       // 1 3
console.log('🙂'.length, Buffer.byteLength('🙂'))       // 2 4
console.log('안녕하세요'.length, Buffer.byteLength('안녕하세요')) // 5 15
```

`String.prototype.length`는 **UTF-16 코드 유닛의 개수**다. 자바스크립트 문자열의 내부 표현이 UTF-16이기 때문이며, BMP를 벗어난 문자는 서로게이트 페어(surrogate pair) 두 개로 표현되어 `length`가 2로 센다. 반면 `Buffer.byteLength(str)`는 지정한 인코딩(기본 UTF-8)으로 변환했을 때의 바이트 수다. `Content-Length` 헤더를 직접 계산하거나 `VARCHAR(n)` 제한을 검사할 때는 반드시 후자를 써야 한다.

문자 단위로 순회해야 한다면 인덱스 접근 대신 이터레이터를 쓴다. 문자열 이터레이터는 코드 포인트 단위로 동작한다.

```js
const s = '가족: 👨‍👩‍👧'
console.log(s.length)               // 12 — UTF-16 코드 유닛 수
console.log([...s].length)          // 8  — 코드 포인트 수(ZWJ 포함)
console.log([...new Intl.Segmenter('ko', { granularity: 'grapheme' }).segment(s)].length) // 5
```

사용자가 "글자 수"라고 부르는 것은 대개 마지막 값, 즉 자소 클러스터(grapheme cluster)다. 가족 이모지는 세 개의 이모지가 폭 없는 결합자(ZWJ)로 이어진 하나의 자소이며, `slice()`로 아무 데나 자르면 완전히 다른 그림이 된다. 표시용 말줄임 처리에는 `Intl.Segmenter`를 쓴다.

### 코드: 버퍼 경계에서 잘리는 멀티바이트 문자

스트림은 청크 경계를 문자 경계에 맞춰주지 않는다. 3바이트 문자가 두 청크에 걸쳐 도착하는 상황은 흔하다.

```js
import { Buffer } from 'node:buffer'
import { StringDecoder } from 'node:string_decoder'

const full = Buffer.from('한글 테스트', 'utf8')
const c1 = full.subarray(0, 4)   // '한'의 3바이트 + '글'의 첫 1바이트
const c2 = full.subarray(4)

// 잘못된 방법: 청크마다 독립적으로 문자열 변환
console.log(c1.toString('utf8') + c2.toString('utf8'))
// '한�\ufffd글 테스트'처럼 깨진다. 불완전한 시퀀스가 U+FFFD로 치환됐다.

// 올바른 방법: StringDecoder가 불완전한 바이트를 내부에 보관했다가 다음 청크와 합친다
const decoder = new StringDecoder('utf8')
let out = decoder.write(c1)      // '한' — '글'의 첫 바이트는 보관된다
out += decoder.write(c2)         // '글 테스트'
out += decoder.end()             // 남은 불완전 바이트가 있으면 여기서 방출된다
console.log(out)                 // '한글 테스트'
```

한 번 U+FFFD(치환 문자)로 바뀐 바이트는 원래 값을 복구할 수 없다는 점이 핵심이다. 그래서 "깨진 문자열을 나중에 고친다"는 접근은 불가능하고, 애초에 깨지지 않게 디코딩해야 한다.

같은 문제를 스트림 레벨에서는 인코딩을 지정해 해결한다. `stream.setEncoding('utf8')`이나 `createReadStream(path, { encoding: 'utf8' })`은 내부적으로 `StringDecoder`를 쓴다. 다만 인코딩을 지정한 스트림은 청크를 문자열로 내보내므로, 바이너리 처리 파이프라인에서는 절대 켜지 말아야 한다.

인코딩 간 변환도 자주 쓴다.

```js
const buf = Buffer.from('Node.js 안녕', 'utf8')

console.log(buf.toString('base64'))        // 바이너리를 텍스트 채널로 나를 때
console.log(buf.toString('base64url'))     // URL/JWT용. +/ 대신 -_ 를 쓰고 패딩이 없다
console.log(buf.toString('hex'))           // 해시·체크섬 표기
console.log(buf.toString('latin1'))        // 바이트 ↔ 문자 1:1 매핑

// latin1은 무손실 왕복이 보장되는 유일한 1:1 인코딩이다
const round = Buffer.from(buf.toString('latin1'), 'latin1')
console.log(round.equals(buf))             // true

// utf8은 그렇지 않다: 유효하지 않은 바이트가 있으면 왕복이 깨진다
const invalid = Buffer.from([0xff, 0xfe, 0x41])
console.log(Buffer.from(invalid.toString('utf8'), 'utf8').equals(invalid)) // false
```

`base64` 디코딩은 관대해서 잘못된 문자를 조용히 무시한다. 입력 검증이 필요하다면 디코딩 후 다시 인코딩해 원본과 비교하거나, `TextDecoder`의 `fatal: true` 옵션처럼 엄격 모드를 제공하는 API를 쓴다.

```js
const decoder = new TextDecoder('utf8', { fatal: true })
try {
  decoder.decode(Buffer.from([0xff]))
} catch (err) {
  console.error('유효하지 않은 UTF-8이다:', err.message)
}
```

### 실무 함정

- **`slice()`로 문자열 자르기**: `str.slice(0, 100)`은 서로게이트 페어 중간이나 자소 클러스터 중간을 자를 수 있다. 표시용이면 `Intl.Segmenter`, 저장 제한이면 바이트 기준으로 자른 뒤 `StringDecoder`로 불완전 바이트를 버린다.
- **DB 컬럼 길이와 문자 길이의 혼동**: MySQL의 `utf8mb4`에서 한글 한 글자는 3바이트, 이모지는 4바이트다. 검증은 `Buffer.byteLength()` 기준으로 한다.
- **`JSON.parse`에 넘기기 전 인코딩**: 스트림으로 받은 JSON은 반드시 전체를 모은 뒤 한 번에 디코딩하거나 스트리밍 파서를 쓴다. 청크마다 `toString()` 후 이어붙이면 위와 같은 이유로 깨진다.
- **정규화(normalization) 차이**: macOS 파일 시스템은 한글을 NFD(자모 분리)로 저장한다. 리눅스에서 만든 NFC 문자열과 바이트 비교하면 다르다. 비교 전 `str.normalize('NFC')`로 맞춘다.

## 9.6 `os`, `path`, `url` 모듈 활용

### 왜 필요한가

애플리케이션은 자신이 도는 환경을 알아야 한다. CPU가 몇 개인지에 따라 워커 수가 정해지고, 메모리 상한에 따라 캐시 크기가 정해지며, 경로 구분자에 따라 파일 접근이 성공하거나 실패한다. 문제는 컨테이너 시대에 이 "환경 정보"의 상당수가 **거짓말**이라는 점이다.

### 어떻게 동작하는가

`os` 모듈은 호스트의 정보를 준다. 강조점은 "호스트"다.

```js
import os from 'node:os'

console.log(os.cpus().length)        // 호스트의 논리 코어 수
console.log(os.availableParallelism()) // 권장 병렬도(Node 19.4+)
console.log(os.totalmem(), os.freemem())
console.log(os.hostname(), os.type(), os.release())
console.log(os.tmpdir(), os.homedir(), os.userInfo().username)
console.log(os.loadavg())            // [1분, 5분, 15분] — 윈도우에서는 항상 [0,0,0]
```

컨테이너 안에서 `os.cpus().length`는 파드의 CPU 제한이 아니라 **노드 전체의 코어 수**를 반환한다. 64코어 머신의 `cpu: "500m"` 파드에서도 64가 나온다. 이 값으로 워커를 띄우면 0.5코어를 64개 프로세스가 나눠 쓰며 컨텍스트 스위칭으로 자멸한다. `os.freemem()`과 `os.totalmem()`도 마찬가지로 호스트 값이며, 메모리 상한 512MiB 파드에서 `totalmem()`이 256GiB로 보고된다.

`os.availableParallelism()`은 CPU 어피니티(affinity)를 반영하므로 `cpus().length`보다는 낫지만, cgroup의 CPU 쿼터는 여전히 보지 못한다. 정확한 값을 원한다면 cgroup 파일을 직접 읽어야 한다.

```js
// detect-cpu.mjs — cgroup v2/v1 제한을 읽어 실제 사용 가능한 CPU 수를 추정한다
import { readFile } from 'node:fs/promises'
import os from 'node:os'

async function readOrNull(p) {
  try { return (await readFile(p, 'utf8')).trim() } catch { return null }
}

export async function detectCpuLimit() {
  // cgroup v2: "max 100000" 또는 "50000 100000" 형식(quota period)
  const v2 = await readOrNull('/sys/fs/cgroup/cpu.max')
  if (v2) {
    const [quota, period] = v2.split(/\s+/)
    if (quota !== 'max') return Math.max(1, Math.floor(Number(quota) / Number(period)))
  }
  // cgroup v1: 두 파일에 나뉘어 있다
  const q = await readOrNull('/sys/fs/cgroup/cpu/cpu.cfs_quota_us')
  const p = await readOrNull('/sys/fs/cgroup/cpu/cpu.cfs_period_us')
  if (q && p && Number(q) > 0) return Math.max(1, Math.floor(Number(q) / Number(p)))

  return os.availableParallelism()   // 제한이 없으면 호스트 기준값을 쓴다
}

// 명시적 설정이 최우선이다. 자동 감지는 어디까지나 기본값일 뿐이다.
export const workerCount = Number(process.env.WEB_CONCURRENCY) || await detectCpuLimit()
```

메모리도 같은 방식으로 `/sys/fs/cgroup/memory.max`를 읽을 수 있지만, 실무에서는 오케스트레이터가 주입한 환경 변수를 쓰고 V8 힙 상한을 `--max-old-space-size`로 명시하는 편이 단순하고 확실하다.

경로 처리는 `path` 모듈로 한다. 문자열 연결로 경로를 만들면 윈도우에서 깨지고, 사용자 입력을 그대로 붙이면 경로 순회(path traversal) 취약점이 된다.

```js
import path from 'node:path'

const base = '/srv/uploads'
const userInput = '../../etc/passwd'

const unsafe = base + '/' + userInput             // 위험하다
const resolved = path.resolve(base, userInput)     // '/etc/passwd' — 여전히 위험하다

// 검증: 정규화 결과가 기지 디렉터리 안에 있는지 확인한다
function safeJoin(base, input) {
  const target = path.resolve(base, input)
  const rel = path.relative(base, target)
  if (rel.startsWith('..') || path.isAbsolute(rel)) throw new Error('경로 이탈')
  return target
}
```

`path.posix`와 `path.win32`로 플랫폼별 구현을 명시적으로 선택할 수 있다. URL 경로나 S3 키처럼 항상 슬래시를 쓰는 대상에는 `path.posix.join()`을 쓴다. 실행 중인 OS와 무관하게 동작하기 때문이다.

ESM에는 `__dirname`과 `__filename`이 없다. 대신 `import.meta.dirname`과 `import.meta.filename`(Node 20.11+)이 있으며, 구버전 호환이 필요하면 `url` 모듈로 변환한다.

```js
import { fileURLToPath, pathToFileURL, URL } from 'node:url'

const here = import.meta.dirname                       // Node 20.11+
const legacy = path.dirname(fileURLToPath(import.meta.url))  // 모든 버전

// 동적 import에는 파일 경로가 아니라 file:// URL을 넘겨야 한다.
// 윈도우 경로('C:\...')를 문자열로 넘기면 'C:'가 프로토콜로 해석되어 실패한다.
const plugin = await import(pathToFileURL(path.join(here, 'plugins', 'auth.mjs')).href)
```

URL 조작에는 전역 `URL`과 `URLSearchParams`를 쓴다. 문자열 템플릿으로 쿼리를 만들면 인코딩 누락으로 깨진다.

```js
const url = new URL('/search', 'https://api.example.com')
url.searchParams.set('q', '노드 & 스트림')   // 자동으로 퍼센트 인코딩된다
url.searchParams.append('tag', 'a')
url.searchParams.append('tag', 'b')          // 같은 키를 여러 번 허용한다
console.log(url.href)
// https://api.example.com/search?q=%EB%85%B8%EB%93%9C+%26+%EC%8A%A4%ED%8A%B8%EB%A6%BC&tag=a&tag=b
```

### 실무 함정

- **`os.cpus().length`로 워커 수를 정하는 것**: 컨테이너에서 거의 항상 틀린다. 환경 변수로 명시하고 cgroup을 폴백으로 둔다.
- **`os.freemem()`으로 캐시 크기를 정하는 것**: 파드가 아니라 노드의 여유 메모리다. LRU 캐시는 항목 수나 바이트 상한으로 직접 제한한다.
- **`path.join()`으로 URL을 만드는 것**: 윈도우에서 역슬래시가 들어간다. URL은 `new URL()`로 조립한다.
- **`os.tmpdir()`이 컨테이너에서 tmpfs가 아닐 수 있다**: 큰 임시 파일을 쓰면 컨테이너 레이어를 채워 디스크 압박으로 이어진다.

## 요약

- `process` 객체는 프로세스의 정체와 자원 사용을 관측하는 창구다. `memoryUsage()`의 `rss`는 OOM 킬러가 보는 값, `heapUsed`는 자바스크립트 객체 누수의 지표, `external`/`arrayBuffers`는 네이티브·버퍼 누수의 지표로 구분해 읽는다.
- `process.exit()`는 대기 중인 비동기 출력을 잘라먹는다. 정상 종료는 `process.exitCode` 대입으로 처리하고, `exit()`는 타임아웃 시 강제 탈출에만 쓴다.
- `util.parseArgs()`와 `--env-file`/`process.loadEnvFile()` 덕분에 CLI 인자 파싱과 `.env` 로딩에 외부 의존성이 더는 필요 없다. 환경 변수는 한곳에서 타입 변환과 검증을 거쳐 동결된 설정 객체로 노출한다.
- 우아한 종료의 순서는 헬스체크 실패 전환 → 라우팅 제외 대기 → `server.close()` + `closeIdleConnections()` → 외부 자원 정리 → 타임아웃 시 강제 종료다. 컨테이너에서는 Dockerfile을 exec 형식으로 작성해 Node가 시그널을 직접 받게 해야 한다.
- `Buffer`는 `Uint8Array`의 서브클래스이며, `allocUnsafe()`는 초기화되지 않은 메모리를 반환해 정보 유출 위험이 있다. `slice()`와 `subarray()`는 복사하지 않는 뷰를 반환하므로 원본 수정과 메모리 유지에 주의한다.
- 문자열 길이(`length`)는 UTF-16 코드 유닛 수, 바이트 길이는 `Buffer.byteLength()`, 사람이 세는 글자 수는 `Intl.Segmenter`다. 스트림 청크를 문자열로 바꿀 때는 `StringDecoder`를 써서 멀티바이트 문자가 경계에서 깨지지 않게 한다.
- `os.cpus()`, `os.freemem()`, `os.totalmem()`은 컨테이너 안에서도 호스트 값을 보고한다. 워커 수와 메모리 예산은 명시적 설정을 우선하고 cgroup 값을 폴백으로 쓴다.

## 연습문제

1. `process.exit()`가 출력을 잘라먹는 현상을 재현하는 스크립트를 작성하라. 20,000줄을 출력한 뒤 `process.exit(0)`를 호출하고 `| wc -l`로 줄 수를 세어 확인한다. 그다음 `exitCode` 방식으로 바꿔 차이를 측정하고, `process.stdout.write()`의 반환값과 `drain` 이벤트를 이용해 `exit()`를 쓰면서도 출력을 보존하는 세 번째 방법을 구현하라.

2. HTTP 서버에 우아한 종료를 구현하고 동작을 검증하라. 3초 걸리는 엔드포인트를 만들고, 요청을 보낸 직후 다른 터미널에서 `kill -TERM <pid>`를 실행해 (a) 진행 중이던 요청이 정상 응답으로 완료되는지, (b) 종료 시작 후 도착한 새 요청이 거부되는지, (c) `/healthz`가 503으로 바뀌는지를 확인하라. 이어서 `closeIdleConnections()` 호출을 주석 처리한 뒤 keep-alive 클라이언트를 붙여두고 종료 시간이 얼마나 늘어나는지 측정하라.

3. TCP 소켓에서 9.4의 프레임 프로토콜을 파싱하는 누적 파서(accumulating parser)를 구현하라. 소켓은 프레임 경계를 보장하지 않으므로, 남은 바이트를 보관했다가 다음 청크와 합쳐 가능한 만큼의 완결 프레임을 방출해야 한다. 페이로드가 UTF-8 텍스트일 때 `StringDecoder` 없이 청크마다 `toString()`을 호출하면 어떤 입력에서 깨지는지 한글 문자열로 재현하고, 올바른 구현과 비교하라.
