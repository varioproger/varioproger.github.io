# 32장. 컨테이너와 오케스트레이션

지금까지 recipe-api와 web-api는 개발자의 노트북이나 한 대의 서버에서 `node server.js`로 실행됐다. 25장에서 클러스터로 복제했고, 26장에서 서비스 레지스트리로 서로를 찾았고, 29장에서 재시도와 서킷 브레이커를 붙였고, 31장에서 지표와 추적을 심었다. 이제 남은 질문은 하나다. **이 두 서비스를 어떻게 여러 머신 위에 올리고, 실패하면 다시 띄우고, 트래픽이 늘면 늘리고, 새 버전을 무중단으로 갈아끼울 것인가.**

이 장은 그 질문에 컨테이너(container)와 오케스트레이터(orchestrator)로 답한다. Docker로 두 서비스를 이미지로 만들고, Compose로 로컬에서 데이터베이스까지 묶어 띄우고, 같은 이미지를 Kubernetes에 배포한다. 마지막 절은 이 장 전체에서 가장 실무적이다. 컨테이너 안의 Node.js는 밖에서와 다르게 동작하며, 그 차이를 모르면 "배포는 성공했는데 파드가 계속 죽는" 상태에 갇힌다.

## 32.1 Docker 입문

### 이미지와 컨테이너는 다른 것이다

혼동이 가장 잦은 지점부터 정리한다. **이미지(image)는 파일 시스템의 스냅숏과 실행 메타데이터를 담은 읽기 전용 아티팩트**다. **컨테이너(container)는 그 이미지를 기반으로 만들어진 실행 중인 프로세스**다. 클래스와 인스턴스의 관계와 같다. 이미지 하나로 컨테이너를 100개 띄울 수 있고, 컨테이너를 지워도 이미지는 남는다.

컨테이너는 가상 머신(virtual machine)이 아니다. 게스트 커널이 없고, 부팅 과정도 없다. 호스트 커널 위에서 돌아가는 평범한 리눅스 프로세스이되, 네임스페이스(namespace)로 시야가 제한되고 cgroup으로 자원이 제한된 프로세스다. 네임스페이스는 "무엇을 볼 수 있는가"를 정한다. PID 네임스페이스 덕에 컨테이너 안의 첫 프로세스는 자기 PID를 1로 본다. 마운트 네임스페이스 덕에 자기만의 루트 파일 시스템을 본다. cgroup은 "얼마나 쓸 수 있는가"를 정한다. CPU 쿼터와 메모리 상한이 여기서 걸린다.

이 두 메커니즘이 32.10의 모든 함정의 뿌리다. Node.js는 PID 1이 되면 시그널 처리가 달라지고, cgroup 한도를 기본적으로 읽지 못해 자원 계산을 틀린다.

### 레이어와 유니온 파일 시스템

이미지는 통짜 파일이 아니라 **레이어(layer)의 스택**이다. Dockerfile의 각 명령이 파일 시스템에 변화를 만들면 그 차이(diff)가 레이어 하나로 저장되고, 각 레이어는 내용 해시로 식별된다. 실행 시점에는 유니온 파일 시스템(union filesystem, 요즘은 대개 overlayfs)이 레이어들을 겹쳐 하나의 뷰로 합쳐 준다. 위 레이어의 파일이 아래 레이어의 같은 경로를 가린다.

여기서 실무적으로 중요한 성질이 두 가지 나온다.

첫째, **레이어는 공유된다.** recipe-api와 web-api가 같은 `node:20-alpine`을 베이스로 쓰면 그 베이스 레이어는 디스크에도 한 벌, 레지스트리에서 내려받을 때도 한 번만 전송된다. 같은 조직의 모든 서비스가 베이스 이미지를 통일해야 하는 이유다.

둘째, **레이어는 지워지지 않는다.** 어떤 레이어에서 파일을 만들고 다음 레이어에서 `rm`하면, 위 레이어에는 삭제 마커만 생기고 아래 레이어의 파일은 그대로 남는다. 이미지 크기도 줄지 않고, 그 파일을 꺼내 볼 수도 있다. `.npmrc`에 토큰을 넣고 `npm install` 후 지우는 패턴이 위험한 이유가 이것이다. 비밀은 레이어에 영원히 박힌다. 해결책은 32.2의 멀티 스테이지 빌드이거나 BuildKit의 `--mount=type=secret`이다.

셋째, **캐시는 순서를 따른다.** 어떤 레이어가 무효화되면 그 아래(뒤)의 모든 레이어가 함께 무효화된다. 자주 바뀌는 것을 뒤에 두는 것이 Dockerfile 설계의 제1원칙이다.

```bash
# 레이어 구성과 각 레이어의 크기를 확인한다
docker history recipe-api:local

# 이미지의 최종 크기 목록
docker image ls recipe-api
```

## 32.2 Node.js 서비스 컨테이너화: 멀티 스테이지 빌드

### 베이스 이미지 고르기: alpine이냐 slim이냐

먼저 크기 감각을 잡는다. 압축 해제 기준 대략적인 수치는 다음과 같다.

| 베이스 이미지 | 크기 | 특징 |
|---|---|---|
| `node:20` | 약 1.1 GB | Debian 전체. 빌드 도구, git, curl 포함 |
| `node:20-slim` | 약 220 MB | Debian 최소 구성. glibc |
| `node:20-alpine` | 약 135 MB | Alpine. musl libc |
| `gcr.io/distroless/nodejs20` | 약 110 MB | 셸조차 없음 |

크기만 보면 alpine이 이긴다. 하지만 alpine은 glibc가 아니라 **musl libc**를 쓴다. 이것이 Node.js에서 만드는 문제는 구체적이다.

- **네이티브 애드온(native addon)의 prebuilt 바이너리가 안 맞는다.** `sharp`, `better-sqlite3`, `node-canvas` 같은 패키지는 glibc용으로 빌드된 바이너리를 내려받는데, alpine에서는 이것이 실패하거나 `Error loading shared library ld-linux-x86-64.so.2`로 런타임에 터진다. 결국 `apk add --no-cache python3 make g++`을 넣어 소스에서 빌드하게 되고, 그 순간 절약한 크기가 사라진다(부록 A 참조).
- **DNS 해석 동작이 다르다.** musl의 리졸버는 `search` 도메인 처리와 TCP 폴백에서 glibc와 다르게 동작한 이력이 있다. Kubernetes의 `ndots:5` 기본값과 겹치면 서비스 디스커버리가 간헐적으로 느려지는 형태로 나타난다(32.8 참조).
- **성능 차이가 있다.** musl의 malloc은 멀티스레드 부하에서 glibc보다 느린 경우가 보고된다. libuv 스레드 풀을 많이 쓰는 워크로드에서 체감될 수 있다.

**기본 선택은 `node:20-slim`이다.** 220MB와 135MB의 차이 85MB는 레지스트리와 노드 사이에서 한 번 전송되고 캐시되는 비용일 뿐, 디버깅 하루치보다 싸다. 순수 JavaScript 의존성만 쓰고 이미지 크기가 정말 중요한 경우에만 alpine을 고르고, 고를 때는 CI에서 alpine 이미지로 테스트를 돌려야 한다.

### .dockerignore 먼저

Dockerfile을 쓰기 전에 `.dockerignore`부터 만든다. 이것이 없으면 `COPY . .`가 로컬 `node_modules`를 통째로 넣는다. 로컬에서 macOS용으로 빌드된 네이티브 모듈이 리눅스 컨테이너에 들어가 런타임에 터지는 사고가 여기서 나온다. 빌드 컨텍스트 전송 시간도 몇 초에서 몇 분으로 늘어난다.

```text
# .dockerignore
node_modules
npm-debug.log
.git
.gitignore
.env
.env.*
coverage
.nyc_output
test
**/*.test.js
Dockerfile
docker-compose.yml
README.md
.github
```

### Dockerfile: 의존성 스테이지와 릴리스 스테이지

recipe-api의 Dockerfile이다. 각 줄에 이유가 있다.

```dockerfile
# syntax=docker/dockerfile:1.7

# ---------- 1단계: 의존성 설치 (빌드 도구가 필요한 구간) ----------
FROM node:20-slim AS deps
WORKDIR /app

# package.json과 lockfile만 먼저 복사한다.
# 소스 코드가 바뀌어도 이 레이어는 재사용되므로 npm ci를 다시 돌리지 않는다.
COPY package.json package-lock.json ./

# npm ci는 lockfile을 정확히 재현한다. npm install과 달리 lockfile을 수정하지 않고,
# lockfile과 package.json이 어긋나면 실패한다 — CI에서 원하는 동작이다.
# --omit=dev로 devDependencies를 제외한다.
RUN --mount=type=cache,target=/root/.npm \
    npm ci --omit=dev --ignore-scripts

# ---------- 2단계: 빌드 (트랜스파일·번들이 필요한 경우) ----------
FROM node:20-slim AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci
COPY . .
RUN npm run build --if-present

# ---------- 3단계: 릴리스 ----------
FROM node:20-slim AS release
ENV NODE_ENV=production

# tini: PID 1 문제를 해결하는 최소 init (32.10에서 자세히 다룬다)
RUN apt-get update \
 && apt-get install -y --no-install-recommends tini \
 && rm -rf /var/lib/apt/lists/*

WORKDIR /app

# node:20-slim 이미지에는 uid/gid 1000의 node 사용자가 이미 있다.
# 소유권을 미리 지정해 복사하면 별도의 chown 레이어가 생기지 않는다.
COPY --from=deps --chown=node:node /app/node_modules ./node_modules
COPY --from=build --chown=node:node /app/dist ./dist
COPY --chown=node:node package.json ./
COPY --chown=node:node server.js ./

# 비루트로 실행한다. 컨테이너 탈출 취약점의 영향 범위를 줄이는 가장 값싼 조치다.
USER node

EXPOSE 4000

# exec 형식 CMD. 셸을 거치지 않으므로 node가 직접 PID 1의 자식이 되고 시그널을 받는다.
ENTRYPOINT ["/usr/bin/tini", "--"]
CMD ["node", "--max-old-space-size=384", "server.js"]
```

각 선택의 근거를 정리한다.

**COPY 순서.** `package.json`과 lockfile을 먼저 복사하고 `npm ci`를 돌린 뒤에 소스를 복사한다. 이 순서를 지키면 소스 한 줄 고쳐 재빌드할 때 의존성 설치 레이어가 캐시에서 그대로 나온다. 의존성 500개짜리 프로젝트에서 `npm ci`는 40~90초, 캐시 히트는 0초다. 반대로 `COPY . .`을 먼저 하면 매 커밋마다 전체 재설치가 일어난다.

**`--omit=dev`.** devDependencies에는 테스트 러너, 린터, 타입 정의가 들어 있다. 프로덕션 이미지에 있을 이유가 없고, 있으면 공격 표면만 넓어진다(34장 참조). 전형적인 프로젝트에서 `node_modules`가 320MB에서 140MB로 줄어든다.

**`--ignore-scripts`.** 의존성의 `postinstall` 스크립트는 공급망 공격의 주요 통로다(34.3 참조). 네이티브 모듈 빌드가 필요해 스크립트가 꼭 필요하다면 이 플래그를 빼되, 그때는 lockfile 감사가 더 중요해진다.

**멀티 스테이지의 효과.** 단일 스테이지로 `node:20`에 빌드 도구까지 넣으면 최종 이미지가 1.3GB 근처가 된다. 위 구성의 최종 이미지는 **약 280MB**다(slim 220MB + node_modules 55MB + 앱 코드). 빌드 캐시, npm 캐시, devDependencies, 소스 트리가 릴리스 스테이지로 넘어오지 않기 때문이다. 이 차이는 노드에 이미지를 처음 내려받는 시간, 즉 스케일 아웃 지연에 직접 나타난다.

**비루트 실행.** 기본값은 root다. 컨테이너의 root는 호스트의 root와 같은 uid 0이며, 커널 취약점이나 잘못된 볼륨 마운트와 겹치면 실질적 권한 상승이 된다. `USER node` 한 줄로 대부분의 시나리오가 막힌다. 단, 1024 미만 포트를 바인딩할 수 없으므로 애플리케이션은 3000/4000번대를 쓴다. 우리 두 서비스는 21장부터 그렇게 해 왔다.

```bash
# 빌드하고 크기를 확인한다
docker build -t recipe-api:local ./recipe-api
docker image ls recipe-api:local

# 로컬 실행. --init 없이 tini를 이미 넣었으므로 그대로 띄운다
docker run --rm -p 4000:4000 -e NODE_ENV=production recipe-api:local

# 비루트로 도는지 확인
docker run --rm recipe-api:local id
# → uid=1000(node) gid=1000(node)
```

## 32.3 이미지 재빌드와 버저닝

### `latest`는 태그가 아니라 거짓말이다

`recipe-api:latest`를 배포하면 두 가지가 동시에 깨진다. 첫째, **무엇이 배포됐는지 알 수 없다.** 장애가 났을 때 "지금 도는 게 어느 커밋인가"에 답할 방법이 없다. 둘째, **롤백할 대상이 없다.** 이전 `latest`는 덮어써졌다.

더 교묘한 문제도 있다. 쿠버네티스의 기본 `imagePullPolicy`는 태그가 `latest`이면 `Always`, 아니면 `IfNotPresent`다. 즉 `latest`를 쓰면 파드가 재시작될 때마다 다른 이미지가 뜰 수 있고, 같은 Deployment의 세 레플리카가 서로 다른 코드를 돌리는 상태가 실제로 만들어진다.

**규칙: 배포 가능한 태그는 불변(immutable)이어야 한다.**

```bash
# CI에서 생성하는 태그들
SHA=$(git rev-parse --short=12 HEAD)      # 예: 9f3c1a7b20de
VERSION=$(node -p "require('./package.json').version")

docker build \
  -t registry.internal:5000/recipe-api:${SHA} \
  -t registry.internal:5000/recipe-api:${VERSION} \
  -t registry.internal:5000/recipe-api:latest \
  ./recipe-api

docker push registry.internal:5000/recipe-api:${SHA}
docker push registry.internal:5000/recipe-api:${VERSION}
docker push registry.internal:5000/recipe-api:latest
```

`latest`를 밀어 두는 것 자체는 사람이 `docker pull`로 최신을 받아 보는 편의를 위해 무방하다. **매니페스트에 쓰지 않으면 된다.** 매니페스트에는 커밋 SHA 태그를 쓴다. SemVer 태그는 라이브러리에 어울리고 서비스에는 SHA가 어울린다. 서비스의 버전 번호는 사람이 올리는 것을 잊지만 커밋 SHA는 항상 정확하기 때문이다(33.3 참조).

### 다이제스트로 못 박기

태그조차도 완전히 불변은 아니다. 레지스트리에 쓰기 권한이 있는 누구든 같은 태그를 다른 이미지에 다시 붙일 수 있다. 진짜 불변 식별자는 **다이제스트(digest)**, 즉 이미지 매니페스트의 SHA-256 해시다.

```bash
# 푸시된 이미지의 다이제스트를 얻는다
docker buildx imagetools inspect registry.internal:5000/recipe-api:9f3c1a7b20de \
  --format '{{.Manifest.Digest}}'
# → sha256:6b1f...c9

# 매니페스트에서 다이제스트로 고정한다
image: registry.internal:5000/recipe-api@sha256:6b1f...c9
```

베이스 이미지도 마찬가지다. `FROM node:20-slim`은 오늘과 다음 달에 다른 이미지를 의미한다. 재현 가능한 빌드가 필요하면 `FROM node:20-slim@sha256:...`으로 고정하고, Renovate 같은 도구로 그 해시를 주기적으로 갱신하는 PR을 자동 생성한다(34.5 참조). 고정하지 않으면 "코드는 그대로인데 어제 되던 빌드가 오늘 실패한다"를 반복해서 겪는다.

### CI에서 빌드 캐시 재사용하기

CI 러너는 매번 깨끗한 상태로 시작하므로 로컬 레이어 캐시가 없다. 그대로 두면 모든 빌드가 `npm ci` 전체를 다시 돈다. BuildKit의 캐시 익스포트로 이를 해결한다.

```bash
docker buildx build \
  --cache-from type=registry,ref=registry.internal:5000/recipe-api:buildcache \
  --cache-to   type=registry,ref=registry.internal:5000/recipe-api:buildcache,mode=max \
  -t registry.internal:5000/recipe-api:${SHA} \
  --push \
  ./recipe-api
```

`mode=max`는 중간 스테이지의 레이어까지 캐시에 넣는다. 최종 스테이지만 캐시하는 `mode=min`보다 캐시 이미지가 크지만, 멀티 스테이지 빌드에서는 `deps` 스테이지가 재사용되는 것이 이득의 대부분이므로 `max`가 맞다. 의존성이 바뀌지 않은 전형적인 커밋에서 빌드 시간이 2분에서 25초로 줄어드는 정도를 기대할 수 있다.

주의할 점 하나. `npm ci`는 lockfile이 조금이라도 다르면 레이어 캐시를 무효화한다. 이것은 정상이며 바람직하다. 캐시가 자주 깨진다면 원인은 대개 `.dockerignore` 누락이나, 빌드마다 값이 바뀌는 `ARG`/`LABEL`을 Dockerfile 앞쪽에 둔 것이다. 빌드 시각이나 커밋 SHA를 라벨로 넣을 때는 반드시 **마지막 스테이지의 마지막 부분**에 둔다.

## 32.4 Docker Compose로 하는 기본 오케스트레이션

쿠버네티스로 가기 전에 Compose를 거치는 이유는 두 가지다. 개발자 노트북에서 전체 스택을 한 명령으로 띄우는 것이 실제로 유용하고, 통합 테스트 환경으로도 충분하다(30장 참조). Compose는 한 대의 머신 안에서만 동작하므로 프로덕션 오케스트레이터는 아니지만, 그 한계를 알고 쓰면 낭비가 없다.

```yaml
# docker-compose.yml — 앱 2개 + PostgreSQL + Redis
services:
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: devpassword
      POSTGRES_DB: recipes
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      # 포트가 아니라 "쿼리를 받을 준비가 됐는가"를 본다
      test: ["CMD-SHELL", "pg_isready -U postgres -d recipes"]
      interval: 5s
      timeout: 3s
      retries: 10
      start_period: 10s

  redis:
    image: redis:7-alpine
    command: ["redis-server", "--save", "", "--appendonly", "no"]
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      retries: 10

  recipe-api:
    build:
      context: ./recipe-api
      target: release
    environment:
      NODE_ENV: production
      PORT: "4000"
      DATABASE_URL: postgres://postgres:devpassword@postgres:5432/recipes
      REDIS_URL: redis://redis:6379
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_healthy
    # 컨테이너가 죽으면 다시 띄운다. 재시작 루프는 로그로 드러난다
    restart: unless-stopped

  web-api:
    build:
      context: ./web-api
      target: release
    environment:
      NODE_ENV: production
      PORT: "3000"
      # 서비스 이름이 곧 호스트 이름이다. Compose의 내장 DNS가 해석한다
      RECIPE_API: http://recipe-api:4000
      UPSTREAM_TIMEOUT_MS: "1000"
    ports:
      - "3000:3000"   # 외부에 노출되는 유일한 서비스
    depends_on:
      - recipe-api
    restart: unless-stopped

volumes:
  pgdata:
```

```bash
docker compose up --build          # 빌드 후 전부 기동
docker compose ps                  # 상태와 헬스 확인
docker compose logs -f web-api     # 특정 서비스 로그
docker compose down -v             # 볼륨까지 정리
```

주목할 점은 **web-api만 `ports`를 갖는다**는 것이다. recipe-api와 데이터베이스는 Compose가 만든 내부 네트워크에만 있고 호스트에서 접근할 수 없다. 21장에서 정한 "프로듀서는 외부에 노출하지 않는다"는 원칙이 여기서 인프라로 강제된다. 개발 중 recipe-api를 직접 찔러 보고 싶다면 `docker compose exec web-api node -e "..."`나 임시 `ports` 추가로 처리하고, 기본 상태를 오염시키지 않는다.

### depends_on의 한계를 정확히 이해하기

`depends_on`은 기본적으로 **기동 순서만** 보장한다. `condition: service_healthy`를 붙이면 헬스 체크 통과까지 기다리지만, 그래도 다음 두 가지는 해결되지 않는다.

첫째, **헬스 체크가 통과했다는 것은 그 순간의 상태일 뿐이다.** PostgreSQL은 recipe-api가 뜬 뒤 언제든 재시작될 수 있다. 컨테이너 이미지 교체, 호스트 재부팅, OOM 킬 모두 흔한 일이다. 그때 recipe-api는 이미 기동을 마친 상태이므로 `depends_on`은 아무 도움이 되지 않는다.

둘째, **포트가 열린 것과 준비된 것은 다르다.** `pg_isready` 대신 `nc -z postgres 5432`로 헬스 체크를 짰다고 하자. PostgreSQL은 리스닝은 시작했지만 크래시 복구 중일 수 있고, 이 상태에서 오는 연결은 거부된다. 애플리케이션 관점의 준비 상태를 검사하지 않는 헬스 체크는 거짓 안심을 준다.

**정답은 애플리케이션 측 재시도다**(29장 참조). 기동 시점의 의존성 연결에 지수 백오프와 지터를 적용하고, 실패해도 프로세스가 즉시 죽지 않게 한다.

```js
// db.js — 기동 시 연결 재시도. Compose에서도 쿠버네티스에서도 똑같이 동작한다
import pg from 'pg';
import { setTimeout as sleep } from 'node:timers/promises';

export async function connectWithRetry({ url, attempts = 12, baseMs = 250, maxMs = 5000 }) {
  const pool = new pg.Pool({ connectionString: url, max: 10 });
  for (let i = 1; i <= attempts; i++) {
    try {
      await pool.query('SELECT 1');           // 리스닝이 아니라 쿼리 가능 여부를 본다
      return pool;
    } catch (err) {
      if (i === attempts) throw err;
      // 지수 백오프 + 풀 지터. 여러 레플리카가 동시에 재시도해 DB를 때리는 것을 막는다
      const backoff = Math.min(maxMs, baseMs * 2 ** (i - 1));
      const delay = Math.random() * backoff;
      console.warn(JSON.stringify({
        level: 'warn', msg: 'db connect failed, retrying',
        attempt: i, delayMs: Math.round(delay), code: err.code,
      }));
      await sleep(delay);
    }
  }
}
```

이 코드가 있으면 `depends_on`은 있으면 좋은 최적화이지 정확성의 근거가 아니게 된다. 그리고 이것이 쿠버네티스에서 유일하게 통하는 방식이다. 쿠버네티스에는 `depends_on`에 해당하는 기능이 아예 없고, 파드는 임의의 순서로 임의의 시점에 재시작된다. 순서에 의존하지 않는 애플리케이션을 만드는 것이 이 장 전체를 관통하는 요구 사항이다.

## 32.5 내부 Docker 레지스트리 운영

이미지는 만든 곳에서만 쓰이지 않는다. CI가 빌드한 이미지를 쿠버네티스 노드들이 내려받아야 하고, 그러려면 공용 저장소가 필요하다. 외부 SaaS 레지스트리를 쓸 수도 있지만, 내부 네트워크에 두면 전송이 빠르고 이미지가 조직 밖으로 나가지 않는다.

```bash
# 데이터가 유지되는 레지스트리를 띄운다
docker run -d --name registry \
  -p 5000:5000 \
  -v registry-data:/var/lib/registry \
  --restart=always \
  registry:2

# 로컬 이미지를 레지스트리 주소로 태깅한 뒤 푸시한다
docker tag recipe-api:local localhost:5000/recipe-api:9f3c1a7b20de
docker push localhost:5000/recipe-api:9f3c1a7b20de

# 다른 머신에서 확인
curl -s http://registry.internal:5000/v2/_catalog | jq
curl -s http://registry.internal:5000/v2/recipe-api/tags/list | jq
```

주의할 것이 하나 있다. Docker 데몬은 **HTTPS가 아닌 레지스트리를 기본적으로 거부한다.** `localhost`만 예외다. 다른 호스트의 평문 레지스트리를 쓰려면 각 노드의 `/etc/docker/daemon.json`에 `insecure-registries`를 추가하고 데몬을 재시작해야 한다.

```json
{ "insecure-registries": ["registry.internal:5000"] }
```

이 설정은 실습과 폐쇄망 한정이다. 프로덕션이라면 리버스 프록시(nginx, Traefik) 뒤에 두고 TLS를 종단하며, `REGISTRY_AUTH=htpasswd`로 기본 인증을 켜거나 Harbor 같은 제품을 쓴다. Harbor는 취약점 스캐닝, 이미지 서명, 프로젝트 단위 권한, 보존 정책을 함께 준다. 마지막 항목이 특히 중요하다. **커밋마다 이미지를 푸시하면 저장소가 순식간에 찬다.** 서비스당 하루 20개 이미지 × 280MB면 한 달에 168GB다. "태그 최근 30개 + 프로덕션에서 참조 중인 태그는 무조건 보존" 같은 정책을 처음부터 걸어 둔다.

쿠버네티스에서 사설 레지스트리를 쓰려면 자격 증명을 시크릿으로 만들어 서비스 어카운트에 붙인다.

```bash
kubectl create secret docker-registry regcred \
  --docker-server=registry.internal:5000 \
  --docker-username=ci \
  --docker-password="$REGISTRY_PASSWORD"
# 매니페스트의 spec.imagePullSecrets 에 name: regcred 로 참조한다
```

## 32.6 Kubernetes 개념과 시작하기

### 최소한의 개념 지도

쿠버네티스의 개념은 많지만, 서비스 두 개를 배포하는 데 필요한 것은 여섯 개뿐이다.

- **파드(Pod)**: 배포의 최소 단위. 네트워크 네임스페이스와 볼륨을 공유하는 컨테이너 하나 이상의 묶음. IP를 하나 갖는다. 우리 서비스는 컨테이너 하나짜리 파드다. 파드는 **일회용(ephemeral)** 이며 IP는 재생성될 때마다 바뀐다.
- **레플리카셋(ReplicaSet)**: "이 파드 템플릿의 복제본을 N개 유지하라"를 책임진다. 파드가 죽으면 새로 만든다. 직접 다루는 일은 거의 없다.
- **디플로이먼트(Deployment)**: 레플리카셋을 세대별로 관리하며 롤링 업데이트와 롤백을 제공한다. 무상태 서비스는 사실상 항상 이것으로 배포한다.
- **서비스(Service)**: 바뀌는 파드 IP들 앞에 붙는 고정된 이름과 가상 IP. 로드 밸런싱도 여기서 일어난다.
- **컨피그맵(ConfigMap)**: 비밀이 아닌 설정. 환경 변수나 파일로 주입한다.
- **시크릿(Secret)**: 비밀. 기본 상태에서는 base64 인코딩일 뿐 암호화가 아니다. etcd 저장 시 암호화(encryption at rest)를 켜거나 외부 시크릿 관리자를 쓰는 것이 실무의 최소선이다(34.1 참조).

관통하는 원리는 **선언적 조정 루프(declarative reconciliation)** 다. 사용자는 "무엇을 원하는가"를 선언하고, 컨트롤러가 현재 상태와 원하는 상태의 차이를 계속 좁힌다. `kubectl apply`는 명령이 아니라 원하는 상태의 갱신이다. 그래서 파드를 손으로 지워도 잠시 후 다시 생기고, 그것이 버그가 아니라 설계다.

## 32.7 애플리케이션 배포: kubectl과 설정 파일

### 설정과 비밀 분리

먼저 설정부터 만든다. 이미지에는 코드만 들어 있고 환경별 값은 밖에서 주입한다는 원칙이다(34.4 참조).

```yaml
# k8s/config.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: web-api-config
data:
  NODE_ENV: "production"
  PORT: "3000"
  # 클러스터 DNS 이름. 32.8에서 자세히 본다
  RECIPE_API: "http://recipe-api:4000"
  UPSTREAM_TIMEOUT_MS: "1000"
---
apiVersion: v1
kind: Secret
metadata:
  name: recipe-api-secret
type: Opaque
stringData:                      # stringData는 평문으로 쓰면 API 서버가 인코딩한다
  DATABASE_URL: "postgres://app:s3cret@postgres:5432/recipes"
```

### Deployment

```yaml
# k8s/recipe-api.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: recipe-api
  labels: { app: recipe-api }
spec:
  replicas: 3
  selector:
    matchLabels: { app: recipe-api }
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1          # 목표 개수보다 최대 1개 더 띄운다
      maxUnavailable: 0    # 준비된 파드가 3개 밑으로 내려가지 않는다
  template:
    metadata:
      labels: { app: recipe-api }
    spec:
      # SIGTERM 후 강제 종료(SIGKILL)까지의 유예. 32.10에서 계산 근거를 다룬다
      terminationGracePeriodSeconds: 45
      imagePullSecrets:
        - name: regcred
      containers:
        - name: recipe-api
          image: registry.internal:5000/recipe-api:9f3c1a7b20de   # latest 금지
          imagePullPolicy: IfNotPresent
          ports:
            - name: http
              containerPort: 4000
          envFrom:
            - secretRef: { name: recipe-api-secret }
          env:
            - name: NODE_ENV
              value: "production"
            - name: PORT
              value: "4000"
            # 파드 이름을 로그와 추적에 넣으면 어느 인스턴스인지 즉시 보인다(31장 참조)
            - name: POD_NAME
              valueFrom:
                fieldRef: { fieldPath: metadata.name }
          resources:
            requests: { cpu: "250m", memory: "256Mi" }   # 스케줄링 기준
            limits:   { cpu: "1000m", memory: "512Mi" }  # 강제 상한
          # 기동이 느릴 수 있는 구간을 startupProbe가 흡수한다. 통과 전에는 다른 프로브가 돌지 않는다
          startupProbe:
            httpGet: { path: /health/live, port: http }
            periodSeconds: 2
            failureThreshold: 30          # 최대 60초까지 기동을 기다린다
          livenessProbe:                  # 실패하면 컨테이너를 재시작한다
            httpGet: { path: /health/live, port: http }
            periodSeconds: 10
            failureThreshold: 3
          readinessProbe:                 # 실패하면 서비스 엔드포인트에서 뺀다
            httpGet: { path: /health/ready, port: http }
            periodSeconds: 5
            failureThreshold: 2
          securityContext:
            runAsNonRoot: true
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities: { drop: ["ALL"] }
          volumeMounts:
            - name: tmp
              mountPath: /tmp           # 읽기 전용 루트에서 쓰기가 필요한 곳만 연다
      volumes:
        - name: tmp
          emptyDir: {}
---
apiVersion: v1
kind: Service
metadata:
  name: recipe-api
spec:
  type: ClusterIP            # 클러스터 내부에서만 접근 가능
  selector: { app: recipe-api }
  ports:
    - port: 4000
      targetPort: http
```

프로브 세 종류의 구분이 핵심이다. **liveness는 "재시작이 답인가"** 를 묻고, **readiness는 "지금 트래픽을 받아도 되는가"** 를 묻는다(31장 참조). 이 둘을 같은 엔드포인트로 두면 사고가 난다. 예를 들어 데이터베이스가 잠시 끊겼을 때 readiness는 실패해야 하지만 liveness는 성공해야 한다. 둘 다 DB를 검사하면 모든 파드가 동시에 재시작되고, 재기동 폭풍이 DB 복구를 더 늦춘다.

```bash
kubectl apply -f k8s/config.yaml
kubectl apply -f k8s/recipe-api.yaml
kubectl apply -f k8s/web-api.yaml

kubectl get pods -l app=recipe-api -o wide
kubectl describe pod recipe-api-7d9c8f6b45-x2k9p     # 이벤트가 문제의 90%를 말해 준다
kubectl logs -f deploy/recipe-api --all-containers
kubectl port-forward svc/web-api 3000:3000           # 로컬에서 테스트
curl -s localhost:3000/recipes/42 | jq
```

`kubectl describe`의 Events 섹션을 먼저 보는 습관이 중요하다. `ImagePullBackOff`(태그 오타나 자격 증명 문제), `CrashLoopBackOff`(기동 직후 종료), `OOMKilled`(메모리 한도 초과), `FailedScheduling`(요청한 자원을 줄 노드가 없음)이 대부분의 배포 실패를 설명한다.

## 32.8 서비스 디스커버리

### 클러스터 DNS

26장에서 우리는 서비스 레지스트리를 직접 구현하거나 Consul 같은 도구를 붙였다. 쿠버네티스에서는 그 대부분이 사라진다. 서비스를 만드는 순간 CoreDNS에 이름이 등록되고, 클라이언트는 그냥 이름으로 연결한다.

```js
// web-api: 주소는 환경 변수로 주입되고, 값은 그저 서비스 이름이다
const RECIPE_API = process.env.RECIPE_API ?? 'http://recipe-api:4000';
```

이름의 정식 형태는 `<service>.<namespace>.svc.cluster.local`이다. 같은 네임스페이스라면 `recipe-api`만으로 충분하고, 다른 네임스페이스의 서비스는 `recipe-api.production`처럼 네임스페이스를 붙인다. 이름 해석은 파드의 `/etc/resolv.conf`에 심어진 `search` 목록과 `options ndots:5`로 이뤄진다.

`ndots:5`는 알아 둘 가치가 있다. **점이 5개 미만인 이름은 먼저 search 도메인들을 차례로 붙여서 질의한다**는 뜻이다. `recipe-api`를 찾을 때 실제로는 `recipe-api.default.svc.cluster.local`, `recipe-api.svc.cluster.local`, `recipe-api.cluster.local` 순으로 시도된다. 내부 이름은 첫 시도에 맞으니 문제가 없지만, **외부 도메인**은 다르다. `api.stripe.com`은 점이 2개이므로 search 접미사 3~4개를 모두 실패한 뒤에야 절대 이름으로 질의된다. 요청마다 DNS 왕복이 4~5회 늘어나고, p99 지연에 수십 밀리초가 얹힌다. 해결책은 외부 호스트명 끝에 점을 찍어 절대 이름으로 만들거나(`api.stripe.com.`), 파드 스펙에 `dnsConfig.options`로 `ndots: 1`을 주는 것이다.

Node.js 쪽에서도 할 일이 있다. 기본 DNS 해석 결과는 캐시되지 않으므로, 요청량이 많으면 CoreDNS가 병목이 된다. 커넥션 재사용(keep-alive)을 켜면 해석 횟수 자체가 줄어든다.

```js
import { Agent, setGlobalDispatcher } from 'undici';

setGlobalDispatcher(new Agent({
  keepAliveTimeout: 30_000,      // 커넥션 재사용으로 DNS·TCP·TLS 비용을 상각한다
  keepAliveMaxTimeout: 60_000,
  connections: 64,               // 호스트당 커넥션 상한
}));
```

한 가지 함정이 있다. keep-alive는 **커넥션을 유지하므로 로드 밸런싱을 고정시킨다.** ClusterIP 서비스는 커넥션 단위로 백엔드를 고른다. 커넥션이 오래 살아 있으면 web-api 각 인스턴스는 특정 recipe-api 파드에만 계속 요청을 보낸다. 레플리카가 3개인데 커넥션이 3개면 운이 나쁠 때 한 파드에 두 개가 몰린다. 스케일 아웃 후에도 새 파드로 트래픽이 안 가는 현상도 같은 원인이다. 커넥션 최대 수명(`keepAliveMaxTimeout`)을 유한하게 두는 것이 그래서 중요하다.

### ClusterIP, NodePort, LoadBalancer, Ingress

서비스 타입 네 가지는 계층 관계다.

**ClusterIP**(기본값)는 클러스터 내부에서만 유효한 가상 IP를 준다. 실제 패킷 전달은 각 노드의 kube-proxy가 iptables나 IPVS 규칙으로 처리하며, 프록시 프로세스를 거치지 않는다. recipe-api처럼 외부에 노출되면 안 되는 서비스의 정답이다.

**NodePort**는 ClusterIP에 더해 모든 노드의 같은 포트(기본 30000~32767)를 연다. 어느 노드로 들어와도 서비스로 전달된다. 로컬 실습이나 외부 로드 밸런서를 직접 운영할 때 쓴다. 포트 번호가 예쁘지 않고 노드 IP를 알아야 해서 프로덕션에서 직접 쓰기에는 불편하다.

**LoadBalancer**는 NodePort에 더해 클라우드 제공자의 로드 밸런서를 프로비저닝하고 외부 IP를 붙인다. 편하지만 **서비스마다 로드 밸런서가 하나씩 생기고 각각 과금된다.** 서비스가 20개면 로드 밸런서도 20개다.

**Ingress**가 그 문제의 답이다. L7 라우터 하나(ingress-nginx, Traefik 등)가 로드 밸런서 하나 뒤에 서서, 호스트와 경로를 보고 여러 ClusterIP 서비스로 분배한다. TLS 종단, 경로 재작성, 속도 제한도 여기서 처리한다.

```yaml
# k8s/ingress.yaml — 외부 진입점은 오직 web-api 하나
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: public
  annotations:
    nginx.ingress.kubernetes.io/proxy-body-size: "2m"
    nginx.ingress.kubernetes.io/proxy-read-timeout: "30"
spec:
  ingressClassName: nginx
  tls:
    - hosts: [ "api.example.com" ]
      secretName: api-example-tls
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-api
                port: { number: 3000 }
```

여기서 21장의 토폴로지가 그대로 재현된다. 외부 → Ingress → web-api(ClusterIP) → recipe-api(ClusterIP) → PostgreSQL. recipe-api에는 Ingress 규칙이 없으므로 클러스터 밖에서 도달할 방법 자체가 없다. 네트워크 정책(NetworkPolicy)을 추가하면 "recipe-api의 4000 포트는 `app=web-api` 라벨이 붙은 파드에서 오는 트래픽만 받는다"까지 강제할 수 있고, 이것이 클러스터 안에서의 최소 권한 원칙이다.

## 32.9 스케일링, 롤링 업데이트, 롤백

### 수동 스케일링

```bash
kubectl scale deployment/web-api --replicas=6
kubectl get deploy web-api -w        # 진행 상황을 지켜본다
```

레플리카를 늘릴 때 반드시 함께 계산해야 하는 것이 **하류 자원**이다. recipe-api 파드 하나가 PostgreSQL 커넥션을 10개 잡는다면 레플리카 3개는 30개, 20개는 200개다. `max_connections`가 100인 데이터베이스는 여기서 무너진다. 25장에서 프로세스를 복제할 때 했던 계산이 그대로 반복되며, 오케스트레이터가 자동으로 늘려 줄수록 이 계산을 놓치기 쉽다. 파드당 풀 크기를 작게 잡고 PgBouncer 같은 커넥션 풀러를 앞에 두는 것이 규모가 커졌을 때의 정석이다.

### 롤링 업데이트

새 이미지를 배포하는 것은 결국 Deployment의 이미지 필드를 바꾸는 일이다.

```bash
# 선언적 방식(권장): 매니페스트의 태그를 고치고 apply
kubectl apply -f k8s/recipe-api.yaml

# 명령형 방식: 긴급 상황에 쓸 수 있다
kubectl set image deployment/recipe-api recipe-api=registry.internal:5000/recipe-api:a71bd4e9c012

kubectl rollout status deployment/recipe-api --timeout=180s
kubectl rollout history deployment/recipe-api
```

`maxSurge`와 `maxUnavailable`이 교체 속도와 안전성의 다이얼이다. `replicas: 3, maxSurge: 1, maxUnavailable: 0`이면 컨트롤러는 새 파드 1개를 먼저 띄우고, **그 파드의 readiness가 통과한 뒤에** 옛 파드 1개를 종료한다. 준비된 파드 수가 3 밑으로 내려가지 않으므로 용량 손실이 없다. 대신 배포 중 잠시 4개가 되므로 자원 여유가 필요하고, 교체가 순차적이라 느리다. 반대로 `maxUnavailable: 1, maxSurge: 1`은 빠르지만 배포 중 용량이 2/3로 떨어진다. **트래픽이 많은 서비스는 `maxUnavailable: 0`이 기본값이어야 한다.**

### 무중단은 프로브와 우아한 종료가 함께 있어야 성립한다

이 절에서 가장 중요한 문장이다. **롤링 업데이트 자체는 무중단을 보장하지 않는다.** 두 가지가 모두 갖춰져야 한다.

**readiness 프로브가 없으면 새 파드가 준비되기 전에 트래픽을 받는다.** 컨테이너가 시작되고 `node server.js`가 실행됐지만 아직 데이터베이스 풀이 워밍업되지 않았고 리스닝조차 시작하지 않은 그 1~3초 동안, 쿠버네티스는 readiness 프로브가 없으면 컨테이너 시작을 곧 준비 완료로 간주한다. 그 파드에 라우팅된 요청은 커넥션 거부로 실패한다. 배포할 때마다 5xx가 잠깐 튀는 그래프의 정체가 대개 이것이다(31장 참조).

**우아한 종료가 없으면 옛 파드가 처리 중인 요청을 잘라 버린다.** SIGTERM을 받고 즉시 `process.exit()`하면 진행 중인 응답이 커넥션 리셋으로 끝난다. 9장에서 만든 종료 절차가 여기서 값을 한다.

```js
// server.js — 우아한 종료. 9장의 패턴을 컨테이너 환경에 맞춰 정리한 것
let shuttingDown = false;

app.get('/health/ready', async (req, reply) => {
  // 종료가 시작되면 즉시 not-ready를 반환해 엔드포인트에서 빠진다
  if (shuttingDown) return reply.code(503).send({ status: 'shutting_down' });
  const ok = await db.ping().then(() => true, () => false);
  return reply.code(ok ? 200 : 503).send({ status: ok ? 'ready' : 'degraded' });
});

async function shutdown(signal) {
  if (shuttingDown) return;              // 중복 시그널 방어
  shuttingDown = true;
  console.log(JSON.stringify({ level: 'info', msg: 'shutdown started', signal }));

  // 1) 엔드포인트 목록에서 빠질 시간을 번다. preStop 훅이 이 역할을 대신할 수도 있다
  await sleep(5_000);
  // 2) 새 커넥션을 받지 않고, 진행 중인 요청은 끝까지 처리한다
  await app.close();
  // 3) 하류 자원을 정리한다
  await db.end();

  console.log(JSON.stringify({ level: 'info', msg: 'shutdown complete' }));
  process.exit(0);
}

for (const sig of ['SIGTERM', 'SIGINT']) process.on(sig, () => shutdown(sig));
```

`await sleep(5000)`이 이상해 보이지만 필수다. 파드가 Terminating으로 바뀔 때 **두 가지 일이 병렬로 일어난다.** 컨테이너로 SIGTERM이 전달되는 것과, 엔드포인트 컨트롤러가 파드를 서비스 엔드포인트에서 제거하고 그 변경이 모든 노드의 kube-proxy 규칙에 반영되는 것이다. 후자는 클러스터 크기에 따라 수백 밀리초에서 수 초가 걸린다. 그 사이에 도착하는 요청은 이미 서버를 닫아 버린 파드로 향한다. 그래서 SIGTERM을 받고도 잠시 요청을 계속 받아야 한다. 이 지연은 32.10의 `preStop` 훅으로도 구현할 수 있다.

### 롤백

```bash
kubectl rollout undo deployment/recipe-api                    # 직전 리비전으로
kubectl rollout undo deployment/recipe-api --to-revision=7    # 특정 리비전으로
kubectl rollout pause deployment/recipe-api                   # 배포 도중 멈춘다
kubectl rollout resume deployment/recipe-api
```

`kubectl rollout undo`는 훌륭하지만 만능이 아니다. **데이터베이스 스키마 변경은 롤백되지 않는다.** 컬럼을 삭제하는 마이그레이션을 배포한 뒤 애플리케이션을 롤백하면 옛 코드가 없는 컬럼을 찾는다. 그래서 마이그레이션은 항상 하위 호환으로 쪼갠다. 컬럼 추가 → 새 코드 배포 → 안정화 확인 → 옛 컬럼 제거를 별도 배포로. 33.7의 배포 전략이 이 문제를 정면으로 다룬다.

### HPA

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-api
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-api
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 65     # requests 대비 비율이다. limits가 아니다
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300   # 축소는 천천히. 플래핑을 막는다
    scaleUp:
      stabilizationWindowSeconds: 0     # 확장은 즉시
```

`averageUtilization: 65`는 **`resources.requests.cpu` 대비 사용률**이다. requests를 250m으로 잡았다면 파드 평균 사용량이 162m을 넘을 때 확장된다. requests를 실제보다 크게 잡아 두면 HPA는 영원히 확장하지 않는다. requests 설정과 HPA 설정은 반드시 함께 검토해야 한다.

CPU 기반 HPA에는 근본적 한계도 있다. **Node.js의 전형적인 병목은 CPU가 아니라 이벤트 루프 지연이나 하류 응답 시간이다**(28장 참조). I/O 대기 중인 파드는 CPU 사용률이 낮지만 이미 포화 상태일 수 있다. 이 경우 Prometheus Adapter나 KEDA로 커스텀 지표(이벤트 루프 지연 p99, 큐 길이, 초당 요청 수)를 HPA에 물리는 편이 훨씬 정확하다(31장 참조).

## 32.10 컨테이너 안의 Node.js: 시그널, PID 1, 리소스 제한

### PID 1은 특별하다

리눅스 커널은 PID 1인 프로세스를 다르게 취급한다. **PID 1에는 시그널의 기본 동작(default disposition)이 적용되지 않는다.** 일반 프로세스라면 SIGTERM에 핸들러가 없을 때 커널이 알아서 종료시키지만, PID 1은 명시적 핸들러가 없으면 시그널이 그냥 무시된다.

Node.js는 SIGTERM 핸들러를 기본으로 등록하지 않는다. 따라서 `node server.js`가 PID 1인 컨테이너는 **SIGTERM을 받아도 죽지 않는다.** 결과는 이렇게 나타난다.

```bash
docker stop mycontainer     # 즉시 끝날 줄 알았는데 10초를 기다린 뒤 종료된다
```

`docker stop`은 SIGTERM을 보내고 10초 뒤 SIGKILL한다. 쿠버네티스는 `terminationGracePeriodSeconds`(기본 30초)만큼 기다린 뒤 SIGKILL한다. 즉 **모든 파드 종료가 30초씩 걸리고, 그동안 진행 중이던 요청은 결국 강제로 끊긴다.** 레플리카 10개짜리 롤링 업데이트가 5분 걸리는 이유가 이것이다.

해결책은 세 가지다.

**첫째, 애플리케이션에 SIGTERM 핸들러를 등록한다.** 32.9의 `shutdown` 코드가 그것이다. 핸들러가 있으면 PID 1이어도 정상 동작한다. 이것이 가장 근본적인 해결이다.

**둘째, exec 형식 CMD를 쓴다.** 이것이 조용한 함정이다.

```dockerfile
# 나쁨: 셸 형식. /bin/sh -c "node server.js" 로 실행되어 sh가 PID 1이 된다.
# sh는 시그널을 자식에게 전달하지 않으므로 node는 SIGTERM을 아예 받지 못한다.
CMD node server.js

# 좋음: exec 형식. node가 직접 실행된다.
CMD ["node", "server.js"]
```

`npm start`도 같은 문제를 만든다. npm이 중간에 끼어 시그널 전달이 불완전해지고, 종료 코드도 왜곡된다. **컨테이너에서는 `npm start`를 쓰지 않고 `node`를 직접 호출한다.**

**셋째, init을 넣는다.** `tini`는 PID 1로 실행되어 시그널을 자식에게 전달하고 좀비 프로세스를 회수한다. 애플리케이션이 자식 프로세스를 만들거나(11장 참조) 서드파티 코드가 시그널을 가로챌 가능성이 있을 때 안전망이 된다.

```dockerfile
ENTRYPOINT ["/usr/bin/tini", "--"]
CMD ["node", "server.js"]
```

Docker에서는 `docker run --init`, 쿠버네티스에서는 이미지에 tini를 넣거나 `shareProcessNamespace`를 쓴다. tini는 핸들러의 대체재가 아니라 보완재다. tini가 SIGTERM을 전달해도 Node.js에 핸들러가 없으면 여전히 안 죽는다.

### preStop 훅과 유예 시간 계산

32.9에서 본 5초 지연을 애플리케이션 코드 대신 매니페스트로 구현할 수 있다.

```yaml
lifecycle:
  preStop:
    exec:
      # SIGTERM 전송 전에 실행된다. 엔드포인트 전파가 끝날 시간을 번다
      command: ["sleep", "5"]
terminationGracePeriodSeconds: 45
```

순서를 정확히 기억한다. **preStop 훅이 먼저 완료되고, 그다음에 SIGTERM이 전달되며, `terminationGracePeriodSeconds`는 preStop 시작 시점부터 카운트된다.** 따라서 유예 시간은 다음처럼 계산한다.

```text
terminationGracePeriodSeconds
  >= preStop 지연(5초)
   + 진행 중 요청의 최대 처리 시간(우리 서비스는 타임아웃 30초)
   + 커넥션 정리 여유(5초)
  = 40초  →  안전하게 45초
```

기본값 30초를 그대로 두면 30초 걸리는 요청이 반드시 잘린다. 반대로 300초처럼 크게 잡으면 노드 드레이닝과 배포가 하염없이 느려진다. 서비스의 최대 요청 시간을 근거로 정하는 것이 맞다. `readOnlyRootFilesystem: true`를 쓴다면 `sleep`이 있는 이미지인지도 확인해야 한다. distroless에는 셸도 `sleep`도 없으므로 그때는 애플리케이션 코드 안의 지연을 써야 한다.

### CPU 제한과 os.cpus()의 불일치

컨테이너에 `limits.cpu: 1000m`을 걸어도 `os.cpus()`는 **호스트의 코어 수**를 반환한다. 64코어 노드에서 CPU 1개만 쓸 수 있는 컨테이너의 Node.js가 자기에게 코어가 64개 있다고 믿는 것이다. 결과는 두 곳에서 나타난다.

**클러스터 워커 수.** `cluster.fork()`를 `os.cpus().length`만큼 돌리는 코드(25장 참조)는 워커를 64개 만든다. 1코어 분량의 CPU 쿼터를 워커 64개가 나눠 쓰며 컨텍스트 스위칭만 하고, 메모리는 프로세스당 40MB씩 2.5GB를 요구해 즉시 OOM으로 죽는다.

**libuv 스레드 풀.** 기본 크기는 4로 고정이지만, 코어 수에 맞춰 늘리는 코드를 넣어 뒀다면 같은 문제가 생긴다.

Node.js 20에는 이를 위한 API가 있다.

```js
import os from 'node:os';

// os.cpus().length         → 호스트의 물리 코어 수 (컨테이너 한도와 무관)
// os.availableParallelism() → cgroup CPU 쿼터와 CPU 어피니티를 반영한 값
const workers = os.availableParallelism();
console.log({ hostCpus: os.cpus().length, usable: workers });
// 64코어 노드, limits.cpu=1000m 인 컨테이너에서 → { hostCpus: 64, usable: 1 }
```

**컨테이너에서 `os.cpus().length`를 병렬도 계산에 쓰지 않는다.** `os.availableParallelism()`을 쓰거나, 더 명시적으로 환경 변수(`WORKER_COUNT`)로 주입한다. 사실 쿠버네티스 환경에서는 클러스터 모듈 자체가 대개 불필요하다. 파드 하나에 프로세스 하나를 두고 레플리카 수로 스케일하는 편이 스케줄링, 자원 회계, 장애 격리 모두에서 낫다. **컨테이너 안에서의 수평 확장은 오케스트레이터의 일이다.**

### 메모리 제한과 OOM Killer

가장 자주 겪는 사고다. `limits.memory: 512Mi`인 컨테이너에서 `--max-old-space-size` 없이 Node.js를 실행하면, V8은 자기 힙 상한을 호스트 메모리에서 유도한다. 64GB 노드라면 V8은 힙을 4GB까지 키워도 된다고 판단한다. 힙이 512MB를 넘는 순간 커널의 OOM Killer가 프로세스를 SIGKILL한다.

이 죽음의 특징은 **로그가 없다는 것**이다. `FATAL ERROR: Reached heap limit`도 없고, `process.on('exit')`도 실행되지 않는다. 파드 상태에 `OOMKilled`와 종료 코드 137만 남는다.

```bash
kubectl get pod recipe-api-7d9c8f6b45-x2k9p -o jsonpath='{.status.containerStatuses[0].lastState.terminated}' | jq
# → { "exitCode": 137, "reason": "OOMKilled", ... }
```

**규칙: `--max-old-space-size`를 컨테이너 메모리 한도의 70~80%로 명시한다.** 나머지는 힙이 아닌 영역이 쓴다. V8 힙 외부(Buffer, 스트림 백프레셔 버퍼, TLS 세션), Node.js 런타임 자체, 네이티브 애드온, 스택, 그리고 glibc 할당자의 단편화가 모두 여기서 나온다. 여유가 없으면 힙은 한도 안에 있는데 RSS가 한도를 넘어 죽는 일이 생긴다.

| `limits.memory` | `--max-old-space-size` | 비힙 여유 |
|---|---|---|
| 256Mi | 192 | 64Mi |
| 512Mi | 384 | 128Mi |
| 1Gi | 768 | 256Mi |
| 2Gi | 1536 | 512Mi |

```dockerfile
# Dockerfile에 기본값을 두되, 매니페스트에서 덮어쓸 수 있게 한다
ENV NODE_OPTIONS="--max-old-space-size=384"
CMD ["node", "server.js"]
```

```yaml
# 매니페스트에서 한도와 함께 관리하는 편이 더 낫다. 둘이 항상 같이 보인다
env:
  - name: NODE_OPTIONS
    value: "--max-old-space-size=384"
resources:
  limits: { memory: "512Mi" }
```

값을 하드코딩하지 않고 Downward API로 한도를 읽어 계산할 수도 있지만, 표를 보고 명시하는 쪽이 읽기 쉽고 사고도 적다. 어느 쪽이든 **한도를 바꾸면 반드시 `--max-old-space-size`도 함께 바꾼다**는 규칙을 팀에 남겨야 한다. 메모리 한도만 512Mi에서 256Mi로 줄이고 힙 설정을 잊는 것이 이 부류 장애의 가장 흔한 시작이다.

마지막으로 `requests`와 `limits`의 관계를 정리한다. 메모리는 압축 불가능한 자원이라 한도를 넘으면 곧바로 죽는다. CPU는 압축 가능해서 한도를 넘으면 죽는 대신 스로틀링(throttling)된다. 스로틀링은 조용히 p99를 망가뜨리므로, `container_cpu_cfs_throttled_seconds_total` 지표를 반드시 대시보드에 올려 둔다(31장 참조). CPU limits를 아예 생략하고 requests만 두는 운영 방식도 널리 쓰이는데, 이는 CFS 쿼터의 버스트 억제로 인한 지연 스파이크를 피하기 위한 선택이다. 노드가 과밀해질 위험과 맞바꾸는 결정이므로, 클러스터의 노드 여유와 함께 판단한다.

## 요약

- 이미지는 읽기 전용 아티팩트이고 컨테이너는 그 실행 인스턴스다. 이미지는 레이어의 스택이며 레이어에서 지운 파일은 하위 레이어에 그대로 남으므로, 비밀은 절대 중간 레이어에 넣지 않는다.
- 멀티 스테이지 빌드로 의존성 설치와 릴리스를 분리하고, `package.json`을 먼저 복사해 레이어 캐시를 살리고, `npm ci --omit=dev`와 `USER node`를 쓴다. 기본 베이스는 `node:20-slim`이며 alpine은 musl 문제를 감수할 때만 고른다.
- 배포 태그는 불변이어야 한다. `latest`는 매니페스트에 쓰지 않고 커밋 SHA나 다이제스트로 고정하며, CI에서는 BuildKit 레지스트리 캐시로 `npm ci` 레이어를 재사용한다.
- `depends_on`은 기동 순서만 보장한다. 포트가 열린 것과 준비된 것은 다르며, 진짜 해법은 애플리케이션 측의 지수 백오프 재시도다.
- 쿠버네티스는 선언적 조정 루프로 동작한다. Deployment로 배포하고 ClusterIP Service로 내부 이름을 얻으며, 외부 노출은 Ingress 하나로 모아 recipe-api를 클러스터 안에 가둔다.
- 롤링 업데이트가 무중단이 되려면 readiness 프로브와 우아한 종료가 **둘 다** 필요하다. 하나만 있으면 배포마다 5xx가 튄다. `maxUnavailable: 0`이 트래픽 많은 서비스의 기본값이다.
- 컨테이너 안의 Node.js는 PID 1 문제(exec 형식 CMD, SIGTERM 핸들러, tini), `os.cpus()` 대신 `os.availableParallelism()`, 메모리 한도의 70~80%로 설정한 `--max-old-space-size`라는 세 가지 조치를 요구한다. 종료 코드 137은 OOM Killer의 서명이다.

## 연습문제

1. **이미지 다이어트와 캐시 측정.** recipe-api를 두 가지로 빌드하라. (a) `node:20` 단일 스테이지에 `COPY . .` 후 `npm install`, (b) 32.2의 멀티 스테이지 버전. 두 이미지의 크기를 `docker image ls`로, 레이어 구성을 `docker history`로 비교하라. 그다음 `server.js`의 주석 한 줄만 고쳐 각각을 재빌드하고 걸린 시간을 측정하라. 캐시가 어느 레이어에서 깨졌는지 설명하고, `.dockerignore`를 지웠을 때 빌드 컨텍스트 전송 크기가 어떻게 변하는지 확인하라.

2. **무중단 배포의 조건 분리 실험.** kind 클러스터에 recipe-api를 레플리카 4개로 배포하고, `autocannon`으로 초당 200건의 부하를 주는 동안 새 이미지로 롤링 업데이트를 실행하라. 다음 네 가지 구성에서 실패 응답(5xx, 커넥션 리셋) 수를 각각 기록하라. (a) readiness 프로브와 SIGTERM 핸들러 모두 없음, (b) readiness만 있음, (c) SIGTERM 핸들러만 있음, (d) 둘 다 + `preStop: sleep 5`. 각 조합에서 실패가 발생하는 **정확한 메커니즘**을 서술하라.

3. **OOM과 CPU 한도 재현.** `limits.memory: 256Mi`인 파드에서 `--max-old-space-size` 없이 recipe-api를 실행하고, 응답 객체를 계속 배열에 쌓아 힙을 키우는 엔드포인트를 호출하라. 파드가 죽는 방식(종료 코드, `reason`, 남은 로그)을 기록한 뒤 `--max-old-space-size=192`를 주고 같은 실험을 반복해 무엇이 달라지는지 비교하라. 이어서 같은 파드 안에서 `os.cpus().length`와 `os.availableParallelism()`을 출력하고, `limits.cpu`를 `500m`으로 바꿨을 때 두 값이 각각 어떻게 변하는지 확인하라.
