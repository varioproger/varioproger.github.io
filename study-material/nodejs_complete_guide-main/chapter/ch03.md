# 3장. 이벤트 루프 깊이 보기

1장에서 Node.js가 논블로킹 I/O와 리액터 패턴(reactor pattern) 위에 서 있다는 것을 확인했다. 이 장은 그 심장부인 이벤트 루프(event loop)를 한 단계 더 파고든다. 이벤트 루프는 "비동기 코드가 마법처럼 나중에 실행된다"는 추상을 걷어내면 결국 정해진 순서로 큐를 비우는 하나의 while 루프다. 그 순서를 정확히 아는 개발자와 모르는 개발자의 코드는 프로덕션에서 전혀 다르게 동작한다. 여기서는 여섯 단계의 실행 순서, `process.nextTick`과 마이크로태스크의 우선순위, 타이머 API들의 미묘한 차이, 루프가 막혔을 때 그것을 측정하고 진단하는 방법을 다룬다.

## 3.1 JavaScript의 단일 스레드 특성

### 왜 단일 스레드인가

멀티 스레드 서버 모델에서 가장 큰 비용은 문맥 전환(context switch)이 아니라 개발자의 인지 비용이다. 두 스레드가 같은 객체를 동시에 만지는 순간 뮤텍스(mutex), 데드락(deadlock), 데이터 경쟁(data race)이라는 문제군이 따라붙고, 이 문제들은 재현이 어렵고 테스트로 잡히지 않는다. Node.js는 이 문제 전체를 회피하는 쪽을 택했다. JavaScript 코드를 실행하는 스레드를 하나로 고정하면, 어떤 함수가 실행되는 동안 다른 JavaScript 코드가 그 변수를 바꾸는 일은 절대 일어나지 않는다. 이 성질을 실행-완료 시맨틱(run-to-completion semantics)이라고 부른다. 함수가 시작되면 `return` 하거나 `await`에서 양보(yield)할 때까지 그 함수는 CPU를 독점한다.

이 보장 덕분에 Node.js 코드에서는 락을 걸 필요가 거의 없다. 예를 들어 요청 카운터를 증가시키는 `counter += 1`은 여러 언어에서 원자적이지 않지만, Node.js에서는 다른 JavaScript가 그 사이에 끼어들 수 없으므로 안전하다. 대신 다른 종류의 위험이 생긴다. `await` 한 줄이 함수의 중간을 갈라 놓기 때문에, `await` 전후의 상태가 같다고 가정하면 논리적 경쟁 상태가 발생한다. 물리적 데이터 경쟁 대신 논리적 경쟁 상태를 다루는 것이 Node.js의 동시성 모델이다.

### 프로세스는 단일 스레드가 아니다

"Node.js는 싱글 스레드다"라는 문장은 절반만 맞다. 정확히는 **JavaScript를 실행하는 스레드가 하나**일 뿐이며, Node.js 프로세스 자체는 항상 여러 스레드로 구성된다. 리눅스에서 아무 일도 하지 않는 Node 프로세스의 스레드 수를 세어 보면 대개 일곱 개 안팎이 나온다.

- **메인 스레드**: 이벤트 루프를 돌리며 JavaScript를 실행한다.
- **libuv 스레드 풀**: 기본 4개. 파일 시스템 호출, DNS 조회(`dns.lookup`), `zlib` 압축, `crypto`의 일부 비동기 함수가 여기서 실행된다. `UV_THREADPOOL_SIZE` 환경 변수로 조정한다.
- **V8 워커 스레드**: 백그라운드 GC 표시(marking), 최적화 컴파일(TurboFan)을 담당한다.
- **인스펙터 스레드**: `--inspect`를 켰을 때 디버거 프로토콜을 처리한다.

즉 CPU를 여러 개 쓰는 일이 전혀 없는 것이 아니라, **개발자가 작성한 JavaScript만** 한 줄로 세워져 실행된다. 그래서 파일을 100개 동시에 읽으면 스레드 풀이 알아서 병렬로 처리하지만, 배열 100만 개를 정렬하면 그 시간 동안 서버 전체가 멈춘다.

```js
import { setTimeout as delay } from 'node:timers/promises';

const start = performance.now();

setTimeout(() => {
  // 100ms 후 실행되기를 기대하지만, 아래 동기 루프가 끝나야 실행된다
  console.log('타이머 지연:', Math.round(performance.now() - start), 'ms');
}, 100);

// 이벤트 루프를 붙잡는 동기 연산
const until = Date.now() + 1000;
while (Date.now() < until) { /* 1초간 CPU 점유 */ }

console.log('동기 블록 종료');
```

출력은 `동기 블록 종료`가 먼저, 그다음 `타이머 지연: 1000ms`다. 타이머는 100ms 뒤에 "실행 자격"을 얻었을 뿐, 실행 스레드가 비어야 실제로 호출된다. 이벤트 루프의 모든 논의는 이 한 가지 사실의 변주다.

### 실무 조언

단일 스레드 모델을 다룰 때 지켜야 할 원칙은 단순하다. **하나의 콜백이 붙잡는 시간을 짧게 유지한다.** 경험적으로 개별 태스크가 10ms를 넘기기 시작하면 p99 지연이 눈에 띄게 흔들리고, 100ms를 넘으면 헬스 체크가 실패하기 시작한다. CPU를 오래 쓰는 작업이 불가피하다면 워커 스레드나 별도 프로세스로 옮긴다(11장 참조). 그리고 "이 코드는 얼마나 걸리는가"를 감으로 판단하지 말고 3.6절의 방법으로 측정한다.

## 3.2 이벤트 루프의 여섯 단계

### 루프의 뼈대

libuv의 이벤트 루프는 매 회전(tick)마다 정해진 순서로 여섯 개의 단계(phase)를 지난다. 각 단계는 자신만의 콜백 큐를 가지며, 그 단계에 진입하면 큐가 비거나 시스템이 정한 최대 개수에 도달할 때까지 콜백을 하나씩 꺼내 실행한다. 단계가 끝나면 다음 단계로 넘어가고, 마지막 단계가 끝나면 루프가 아직 살아 있는지 확인한 뒤 다시 첫 단계로 돌아간다.

```text
   ┌───────────────────────────┐
┌─>│         timers            │  만료된 setTimeout / setInterval
│  ├───────────────────────────┤
│  │    pending callbacks      │  지연된 시스템 콜백(주로 TCP 오류)
│  ├───────────────────────────┤
│  │     idle, prepare         │  libuv 내부 전용
│  ├───────────────────────────┤     ┌──────────────┐
│  │          poll             │<────│  I/O 이벤트   │
│  ├───────────────────────────┤     └──────────────┘
│  │          check            │  setImmediate
│  ├───────────────────────────┤
└──│      close callbacks      │  'close' 이벤트
   └───────────────────────────┘
```

### 각 단계에서 실제로 무엇이 실행되는가

**1. timers.** 만료 시각이 지난 `setTimeout`과 `setInterval` 콜백을 실행한다. libuv는 타이머를 최소 힙(min-heap)으로 관리하므로 가장 이른 타이머부터 꺼낸다. 여기서 실행되는 것은 **만료된** 타이머이지 "정확히 지정한 시각의" 타이머가 아니다. 100ms로 등록한 타이머가 137ms에 실행되는 것은 버그가 아니라 설계다.

**2. pending callbacks.** 직전 루프 회전에서 처리되지 못하고 미뤄진 시스템 레벨 콜백을 실행한다. 대표적으로 TCP 소켓이 `ECONNREFUSED` 같은 오류를 반환했을 때, 일부 운영체제에서는 오류 알림을 다음 회전으로 미룬다. 애플리케이션 코드가 이 단계를 직접 겨냥하는 경우는 사실상 없다.

**3. idle, prepare.** libuv가 내부적으로 쓰는 단계다. Node.js는 여기서 poll 진입 준비 작업을 한다. 사용자 코드가 여기에 콜백을 넣을 방법은 없다.

**4. poll.** 이벤트 루프의 실질적인 중심이다. 두 가지 일을 한다. 첫째, 완료된 I/O 이벤트의 콜백을 실행한다. 파일 읽기 완료, 소켓 수신, HTTP 요청 도착 같은 것 대부분이 이 단계에서 처리된다. 둘째, **필요하다면 여기서 블로킹한다.** 커널의 `epoll_wait`(리눅스), `kqueue`(macOS), IOCP(윈도우)를 호출해 새 이벤트가 올 때까지 스레드를 재운다.

**5. check.** `setImmediate`로 등록된 콜백만 실행한다. poll 단계 직후라는 위치가 이 API의 존재 이유다. I/O 콜백 처리를 마친 직후, 하지만 다음 타이머 단계로 넘어가기 전에 실행할 코드를 넣는 자리다.

**6. close callbacks.** `socket.destroy()`처럼 핸들이 갑자기 닫혔을 때 `'close'` 이벤트 콜백을 실행한다. 리소스 정리 코드가 도는 곳이다.

### poll 단계는 언제 블로킹하는가

이 부분이 이벤트 루프에서 가장 자주 오해되는 지점이다. poll 큐가 비었을 때 루프는 다음 규칙에 따라 대기 시간(timeout)을 계산한다.

1. **check 큐에 `setImmediate` 콜백이 있으면 타임아웃 0.** 블로킹하지 않고 즉시 poll을 빠져나가 check 단계로 간다.
2. **`setImmediate`가 없고 만료 예정 타이머가 있으면, 가장 가까운 타이머까지 남은 시간만큼 블로킹한다.** 그 시간 안에 I/O가 도착하면 깨어나 콜백을 처리하고, 아니면 타임아웃되어 timers 단계로 넘어간다.
3. **타이머도 `setImmediate`도 없으면 무기한 블로킹한다.** 이것이 유휴 상태의 Node 서버가 CPU를 0%만 쓰는 이유다. 커널이 소켓에 데이터를 넣어 줄 때까지 프로세스는 잠들어 있다.

여기서 중요한 결론이 나온다. **CPU 사용률이 0%인데 응답이 느린 서버**는 이벤트 루프가 아니라 외부 의존성(데이터베이스, 다운스트림 서비스)이 느린 것이다. 반대로 **CPU가 100%에 붙어 있는데 처리량이 낮은 서버**는 poll 단계에 도달하지 못하고 어딘가에서 동기 연산에 붙잡혀 있다. 진단의 첫 갈림길로 이 구분을 사용한다.

```js
import { readFile } from 'node:fs/promises';

console.log('1: 동기 코드');

setTimeout(() => console.log('4: timers 단계'), 0);
setImmediate(() => console.log('3: check 단계'));

readFile(new URL(import.meta.url), 'utf8').then(() => {
  // 이 콜백은 poll 단계에서 실행된다
  console.log('5: poll 단계 (파일 읽기 완료)');
  setTimeout(() => console.log('7: I/O 이후 timers'), 0);
  setImmediate(() => console.log('6: I/O 이후 check'));
});

queueMicrotask(() => console.log('2: 마이크로태스크'));
```

앞의 세 줄(1, 2)은 확정적이고, 3과 4의 순서는 3.4절에서 설명할 이유로 실행 환경에 따라 뒤바뀔 수 있다. 하지만 파일 읽기 콜백 안에서 등록한 6과 7의 순서는 **항상** `setImmediate`가 먼저다. poll 단계에서 등록했으니 바로 다음 단계인 check가 먼저 오기 때문이다.

### 실무 함정

이벤트 루프 단계를 외운 지식으로 코드 실행 순서를 조작하려 들면 유지보수 불가능한 코드가 된다. 단계 지식의 목적은 **순서를 설계하는 것이 아니라 관찰된 동작을 설명하는 것**이다. "왜 이 로그가 저 로그보다 늦게 찍히는가", "왜 부하가 걸리면 타이머가 200ms씩 밀리는가"를 해석할 수 있으면 충분하다. 실행 순서에 의존하는 로직이 필요하다면 Promise 체인이나 명시적인 큐로 표현한다(6장 참조).

## 3.3 `process.nextTick`과 마이크로태스크 큐

### 여섯 단계 밖의 두 큐

여섯 단계는 이야기의 절반이다. Node.js에는 어느 단계에도 속하지 않는 두 개의 큐가 더 있고, 이들은 **단계 사이가 아니라 개별 콜백 사이마다** 비워진다.

- **nextTick 큐**: `process.nextTick(fn)`으로 등록한다.
- **마이크로태스크 큐(microtask queue)**: Promise의 `then`/`catch`/`finally` 콜백, `await` 이후의 재개 지점, `queueMicrotask(fn)`이 여기 들어간다.

규칙은 두 줄로 요약된다. 첫째, **JavaScript 콜백 하나가 끝날 때마다** 두 큐를 모두 비운다. 둘째, **nextTick 큐를 완전히 비운 뒤에 마이크로태스크 큐를 비운다.** 그리고 마이크로태스크를 처리하는 도중 새 nextTick이 등록되면 다시 nextTick 큐로 돌아간다. 두 큐가 모두 빌 때까지 루프는 다음 콜백으로 넘어가지 않는다.

### 순서를 눈으로 확인하기

```js
console.log('A: 동기 시작');

setTimeout(() => {
  console.log('F: timers');
  process.nextTick(() => console.log('G: timers 콜백 뒤의 nextTick'));
  Promise.resolve().then(() => console.log('H: timers 콜백 뒤의 promise'));
}, 0);

setImmediate(() => {
  console.log('I: check');
  process.nextTick(() => console.log('J: check 콜백 뒤의 nextTick'));
});

process.nextTick(() => {
  console.log('C: nextTick 1');
  process.nextTick(() => console.log('D: nextTick 안에서 등록한 nextTick'));
});

Promise.resolve().then(() => console.log('E: promise'));

console.log('B: 동기 끝');
```

출력은 다음과 같다.

```text
A: 동기 시작
B: 동기 끝
C: nextTick 1
D: nextTick 안에서 등록한 nextTick
E: promise
F: timers
G: timers 콜백 뒤의 nextTick
H: timers 콜백 뒤의 promise
I: check
J: check 콜백 뒤의 nextTick
```

이 출력이 증명하는 것은 세 가지다. (1) 동기 코드가 전부 끝난 뒤에야 어떤 큐도 처리되지 않는다 — A, B가 먼저다. (2) nextTick 큐가 마이크로태스크보다 먼저다 — C, D가 E보다 앞선다. 그리고 nextTick 안에서 등록한 nextTick(D)조차 Promise(E)를 앞지른다. (3) 각 단계의 각 콜백이 끝날 때마다 두 큐가 다시 비워진다 — F 다음에 곧바로 G, H가 오고, 그 뒤에야 check 단계의 I로 넘어간다.

### 재귀 nextTick으로 루프 굶기기

nextTick 큐를 "완전히" 비운다는 규칙에는 대가가 따른다. nextTick 콜백이 또 nextTick을 등록하면 큐가 영원히 비지 않고, 이벤트 루프는 다음 단계로 진행하지 못한다. 이것을 이벤트 루프 기아(event loop starvation)라고 한다.

```js
import { createServer } from 'node:http';

const server = createServer((req, res) => res.end('ok'));
server.listen(3000);

setInterval(() => console.log('이 로그는 한 번도 찍히지 않는다'), 100);

let n = 0;
function starve() {
  n += 1;
  process.nextTick(starve); // 큐가 절대 비지 않는다
}
starve();
```

이 프로세스는 CPU 100%를 쓰면서 살아 있지만, 타이머도 실행되지 않고 HTTP 요청도 받지 못한다. poll 단계에 도달할 수 없기 때문이다. 같은 코드를 `setImmediate(starve)`로 바꾸면 매 회전마다 check 단계에서 한 번씩만 실행되므로, 서버는 요청을 정상적으로 처리하고 타이머도 동작한다. **재귀적으로 자신을 다시 예약해야 한다면 `setImmediate`를 쓴다**는 규칙은 여기서 나온다.

Promise 체인으로도 같은 기아를 만들 수 있다. `Promise.resolve().then(loop)` 형태의 무한 재귀는 마이크로태스크 큐를 비우지 못하게 만들어 동일한 결과를 낳는다. `await` 루프 안에 진짜 I/O나 타이머가 하나도 없으면 이 함정에 빠진다.

### 실무 조언

애플리케이션 코드에서 `process.nextTick`을 쓸 이유는 거의 없다. 표준 API인 `queueMicrotask`가 있고, 대부분의 "다음 틱에 실행" 요구는 Promise로 더 명확하게 표현된다. `nextTick`이 정당한 경우는 라이브러리를 만들 때다. 생성자에서 이벤트를 발생시켜야 하는데 호출자가 아직 리스너를 붙일 기회가 없었을 때, 혹은 API가 동기와 비동기 양쪽으로 동작해 Zalgo 문제를 일으키는 것을 막을 때 사용한다(4장 참조). 그 밖의 상황에서 `nextTick`은 우선순위를 몰래 높이는 도구일 뿐이고, 남용하면 위와 같은 기아를 만든다.

## 3.4 `setTimeout` / `setInterval` / `setImmediate`의 차이

### 세 API의 정체

이름만 보면 `setImmediate`가 가장 빠르고 `setTimeout(fn, 0)`이 그다음일 것 같지만, 실제 관계는 이벤트 루프의 단계 구조에서 결정된다. 세 API는 서로 다른 큐에 콜백을 넣는다.

- `setTimeout(fn, ms)` — timers 단계. 지정한 밀리초 **이후** 첫 timers 단계에서 한 번 실행된다.
- `setInterval(fn, ms)` — timers 단계. 실행 후 자신을 다시 예약해 반복된다.
- `setImmediate(fn)` — check 단계. 현재 poll 단계가 끝난 직후 실행된다.

여기에 하나 더 알아야 할 사실이 있다. Node.js는 `setTimeout`의 지연 값을 1 이상으로 강제 보정한다. `setTimeout(fn, 0)`은 내부적으로 `setTimeout(fn, 1)`이 된다. 2,147,483,647(약 24.8일)을 넘는 값도 1로 보정되므로, "한 달 뒤 실행"을 타이머로 구현하면 즉시 실행되는 버그가 된다.

### 메인 모듈에서의 비결정성

다음 코드의 출력 순서는 실행할 때마다 달라질 수 있다.

```js
setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));
```

이유는 1ms 보정에 있다. 프로세스가 부팅되어 첫 이벤트 루프 회전의 timers 단계에 도달하기까지 걸리는 시간이 1ms를 넘느냐 넘지 않느냐가 순서를 가른다. 머신이 느리거나 모듈 로딩이 무거워 준비 시간이 1.2ms 걸렸다면 타이머는 이미 만료되어 있으므로 `timeout`이 먼저 출력된다. 반대로 0.4ms만에 도달했다면 타이머는 아직 만료되지 않았고, 루프는 poll을 지나 check 단계에서 `immediate`를 먼저 실행한 뒤 다음 회전에서 타이머를 처리한다. 같은 코드를 100번 돌리면 두 결과가 섞여 나온다.

### I/O 콜백 안에서는 항상 `setImmediate`가 먼저다

반면 I/O 콜백 내부에서는 순서가 결정적이다.

```js
import { readFile } from 'node:fs';

readFile(new URL(import.meta.url), () => {
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate'));
});
// 항상: immediate → timeout
```

이 콜백은 poll 단계에서 실행 중이다. 콜백이 끝나면 루프는 poll 단계를 마무리하고 **바로 다음 단계인 check**로 넘어가므로 `setImmediate`가 먼저 실행된다. timers 단계는 루프가 한 바퀴를 다 돌고 다음 회전을 시작해야 나온다. 그래서 실무 규칙이 나온다. **I/O 콜백 안에서 "지금 하던 일을 끝내고 곧바로" 실행할 코드는 `setTimeout(fn, 0)`이 아니라 `setImmediate(fn)`으로 예약한다.** 전자는 다음 루프 회전까지 기다려야 하고, 그사이에 다른 I/O가 몰리면 예측 불가능하게 지연된다.

### `setInterval`의 두 가지 함정

첫째, **드리프트(drift)**. `setInterval(fn, 1000)`은 "1초마다"가 아니라 "직전 실행이 끝난 뒤 최소 1초 후"에 가깝게 동작한다. 콜백이 300ms를 쓰면 실제 주기는 1초보다 길어지고, 이벤트 루프가 막히면 더 밀린다. 오차가 누적되므로 정확한 시각에 무언가를 해야 한다면 매번 `Date.now()`와 목표 시각의 차이를 계산해 `setTimeout`을 다시 거는 방식을 쓴다.

둘째, **중첩 실행(overlap)**. 콜백이 비동기 작업을 수행하고 그 작업이 주기보다 오래 걸리면, 이전 작업이 끝나기 전에 다음 실행이 시작된다. 폴링 작업에서 이것은 데이터베이스 커넥션 고갈이나 중복 처리로 이어진다. 안전한 형태는 `setInterval` 대신 자기 자신을 다시 예약하는 재귀 `setTimeout`이다.

```js
import { setTimeout as delay } from 'node:timers/promises';

// 위험: 작업이 5초 걸리면 실행이 중첩된다
setInterval(async () => { await syncFromUpstream(); }, 1000);

// 안전: 이전 작업이 끝난 뒤에만 다음 주기를 예약한다
async function pollLoop(signal) {
  while (!signal.aborted) {
    try {
      await syncFromUpstream();
    } catch (err) {
      console.error('동기화 실패', err);
    }
    await delay(1000, undefined, { signal }); // 취소 가능한 대기
  }
}

const controller = new AbortController();
pollLoop(controller.signal).catch((err) => {
  if (err.name !== 'AbortError') throw err;
});
// 종료 시: controller.abort()
```

`node:timers/promises`의 `setTimeout`과 `setImmediate`는 Promise를 반환하고 `AbortSignal`을 받는다. 콜백 대신 `await`으로 쓸 수 있어 반복 작업 코드가 훨씬 읽기 쉬워지며, 종료 시 대기 중인 타이머를 깔끔하게 취소할 수 있다(6.9절, 29장 참조). 새로 쓰는 코드에서는 콜백형 타이머보다 이쪽을 기본으로 삼는다.

### 실무 함정

`setTimeout`으로 타임아웃을 구현할 때 성공 경로에서 `clearTimeout`을 호출하지 않으면, 이미 끝난 요청의 타이머가 계속 살아 있으면서 프로세스 종료를 막고 메모리를 붙잡는다. 요청당 타이머를 만드는 코드에서는 반드시 `finally` 블록에서 정리한다. 그리고 부하 테스트 중 타이머 콜백이 지정한 시간보다 훨씬 늦게 실행된다면 그것은 타이머의 문제가 아니라 이벤트 루프 지연의 증상이다. 3.6절의 계측이 필요하다는 신호다.

## 3.5 `ref` / `unref`와 프로세스 종료 조건

### Node.js 프로세스는 언제 종료되는가

Node.js 프로세스가 종료되는 조건은 명료하다. **이벤트 루프에 참조된(ref'd) 활성 핸들(handle)이나 요청(request)이 하나도 남지 않으면** 루프가 끝나고 프로세스가 정상 종료된다. 여기서 핸들은 서버, 소켓, 타이머처럼 오래 사는 리소스이고, 요청은 파일 읽기처럼 일회성 작업이다.

이 규칙이 두 방향의 흔한 문제를 설명한다. 첫째, **스크립트가 끝났는데 프로세스가 종료되지 않는 경우.** 어딘가에 `setInterval`이 남아 있거나, 데이터베이스 커넥션 풀이 닫히지 않았거나, HTTP 서버가 리스닝 중이다. 둘째, **끝나기 전에 프로세스가 죽는 경우.** 모든 핸들이 unref 되어 있어서 루프가 할 일이 없다고 판단한 것이다.

### `unref()`의 의미

핸들에 `unref()`를 호출하면 "이 핸들은 살아 있지만, 이것 때문에 프로세스를 붙잡아 두지는 말라"는 뜻이 된다. 반대로 `ref()`는 다시 붙잡게 만든다.

```js
// 5분마다 메트릭을 보내는 타이머 — 이것 때문에 프로세스가 안 죽으면 곤란하다
const metricsTimer = setInterval(flushMetrics, 5 * 60_000);
metricsTimer.unref();

// 디버그용 진단 서버 — 메인 서버가 닫히면 같이 끝나야 한다
const diagServer = createServer(handler);
diagServer.listen(9229);
diagServer.unref();
```

전형적인 용도는 두 가지다. 하나는 **백그라운드 유지보수 타이머**(메트릭 플러시, 캐시 만료 정리, 커넥션 keep-alive 체크)로, 애플리케이션의 본질적 작업이 아니므로 종료를 막아서는 안 된다. 다른 하나는 **부수적 리스너**로, 진단 엔드포인트나 임시 소켓처럼 주 작업이 끝나면 함께 사라져야 하는 것들이다.

주의할 점은 `unref()`가 리소스를 닫지 않는다는 것이다. 타이머는 여전히 등록되어 있고, 다른 이유로 루프가 살아 있으면 정상적으로 실행된다. 단지 "혼자 남았을 때 프로세스를 붙잡지 않을" 뿐이다. 정리가 목적이라면 `clearInterval`이나 `close()`를 써야 한다.

### 무엇이 프로세스를 붙잡고 있는지 알아내기

배포 파이프라인에서 CI 잡이 끝나지 않거나, 컨테이너가 `SIGTERM` 이후에도 살아 있는 문제는 대부분 남은 핸들 때문이다. Node.js는 이를 확인할 내장 수단을 제공한다.

```js
process.on('beforeExit', () => {
  // 종료 직전이지만 아직 루프가 살아 있을 수 있는 시점
  console.log('활성 리소스:', process.getActiveResourcesInfo());
});

// 강제 진단: 5초 뒤에도 살아 있으면 무엇이 남았는지 출력
const watchdog = setTimeout(() => {
  console.error('종료 지연. 남은 리소스:', process.getActiveResourcesInfo());
}, 5000);
watchdog.unref(); // 감시자 자신이 프로세스를 붙잡으면 안 된다
```

`process.getActiveResourcesInfo()`는 `[ 'TCPSERVERWRAP', 'Timeout', 'Timeout' ]` 같은 문자열 배열을 돌려준다. 타입만 알려 주므로 위치까지는 알 수 없지만, "타이머가 셋 남아 있다"는 정보만으로도 범위를 좁히기에 충분한 경우가 많다. 더 자세한 스택 추적이 필요하면 `--trace-exit` 플래그나 `why-is-node-running` 같은 도구를 쓴다.

### `process.exit()`을 함부로 쓰지 말 것

프로세스를 확실히 끝내려고 `process.exit(0)`을 부르는 코드를 자주 보게 되는데, 이것은 대개 잘못된 처방이다. `process.exit()`은 진행 중인 비동기 작업을 기다리지 않고 즉시 종료한다. 버퍼링된 stdout 쓰기가 잘리고, 커밋 중이던 트랜잭션이 끊기고, 아직 응답을 보내지 못한 요청이 사라진다. 올바른 순서는 서버의 신규 연결을 닫고(`server.close()`), 진행 중인 요청이 끝나기를 기다리고, 커넥션 풀과 브로커 연결을 정리한 뒤, 자연스럽게 루프가 비어 종료되게 하는 것이다. 강제 종료는 그 과정에 타임아웃을 건 최후 수단으로만 남긴다(9.3절, 29장 참조).

### 실무 함정

`unref()`한 타이머에 의존해 반드시 실행되어야 할 로직(예: 마지막 메트릭 플러시)을 넣으면, 프로세스가 그 전에 종료되어 데이터가 유실된다. unref는 "실행되면 좋고 아니어도 그만"인 작업에만 쓴다. 또한 `unref()`는 핸들 종류에 따라 존재하지 않을 수 있다. `worker_threads`의 워커, `child_process`의 자식 프로세스에도 `unref()`가 있지만 의미가 조금씩 다르므로 문서를 확인하고 쓴다.

## 3.6 이벤트 루프를 막는 코드 진단하기

### 지연을 숫자로 만들기

"서버가 가끔 느리다"는 보고는 조치로 이어지지 않는다. 필요한 것은 **이벤트 루프 지연(event loop delay)** 이라는 하나의 숫자다. 정의는 간단하다. 타이머를 특정 간격으로 예약했을 때 실제 실행 시각이 예정 시각보다 얼마나 늦었는가. 이 값이 평상시 1ms 미만이다가 특정 요청에서 300ms로 튄다면, 그 요청이 이벤트 루프를 300ms 붙잡았다는 뜻이다.

Node.js는 이 계측을 내장으로 제공한다. `perf_hooks`의 `monitorEventLoopDelay()`는 libuv 수준에서 고해상도 히스토그램을 수집하므로, JavaScript로 직접 구현한 계측기보다 정확하고 오버헤드도 낮다.

```js
import { monitorEventLoopDelay } from 'node:perf_hooks';

const histogram = monitorEventLoopDelay({ resolution: 10 }); // 10ms 샘플링
histogram.enable();

setInterval(() => {
  // 나노초 단위이므로 1e6으로 나눠 밀리초로 변환
  const toMs = (ns) => Math.round(ns / 1e6 * 100) / 100;
  console.log({
    mean: toMs(histogram.mean),
    p50: toMs(histogram.percentile(50)),
    p99: toMs(histogram.percentile(99)),
    max: toMs(histogram.max),
  });
  histogram.reset(); // 다음 구간을 위해 초기화
}, 10_000).unref();
```

여기서 봐야 할 값은 평균이 아니라 **p99와 max**다. 평균은 대부분의 요청이 빠르면 낮게 유지되지만, 사용자가 체감하는 것은 꼬리 지연이다. 실무 기준선으로는 p99가 10ms 이하면 건강, 50ms를 넘으면 조사, 100ms를 넘으면 즉시 조치가 필요한 상태로 본다.

`performance.eventLoopUtilization()`도 함께 쓸 만하다. 이 함수는 루프가 대기하지 않고 실제로 일한 시간의 비율(0~1)을 알려 준다. 지연 히스토그램이 "얼마나 밀렸는가"를 본다면, 이 값은 "얼마나 포화되었는가"를 본다. 두 값을 함께 보면 여유가 있는데 특정 요청만 튀는 것인지, 전반적으로 CPU가 포화된 것인지 구분할 수 있다.

### 부하 차단(load shedding)

루프가 이미 막혀 있는데 요청을 계속 받아들이면 큐가 쌓여 상황이 악화된다. 어차피 타임아웃될 요청이라면 빨리 거절하는 편이 전체 지연을 낮춘다. 예전에는 `toobusy-js` 같은 패키지를 썼지만, 지금은 내장 히스토그램만으로 같은 동작을 만들 수 있다.

```js
import { monitorEventLoopDelay } from 'node:perf_hooks';

const lag = monitorEventLoopDelay({ resolution: 20 });
lag.enable();

const THRESHOLD_MS = 70;

export function shedLoad(req, res, next) {
  const p99 = lag.percentile(99) / 1e6;
  if (p99 > THRESHOLD_MS) {
    res.statusCode = 503;
    res.setHeader('Retry-After', '1');
    res.end('서버 과부하');
    return;
  }
  next();
}

// 히스토그램이 과거에 갇히지 않도록 주기적으로 리셋
setInterval(() => lag.reset(), 5_000).unref();
```

임계값을 너무 낮게 잡으면 정상 트래픽을 거절하고, 너무 높게 잡으면 차단의 의미가 없다. 부하 테스트로 실제 p99 분포를 측정한 뒤(28장 참조) 정상 상태 p99의 5~10배 정도로 잡는 것이 출발점이다. 그리고 헬스 체크 엔드포인트는 이 미들웨어보다 앞에 두어야 한다. 그러지 않으면 과부하 시 헬스 체크까지 503을 받아 오케스트레이터가 인스턴스를 죽이고, 남은 인스턴스에 부하가 몰리는 연쇄 붕괴가 일어난다(31.5절 참조).

### 원인 지점 찾기: 프로파일링

지연이 있다는 것을 알았다면 다음은 어느 코드가 원인인지 찾는 단계다.

**`--cpu-prof`** 가 가장 손쉽다. 프로세스가 종료될 때 `.cpuprofile` 파일이 생성되고, 이것을 Chrome DevTools의 Performance 탭이나 VS Code에 끌어다 놓으면 함수별 자기 시간(self time)이 정렬된 표와 불꽃 그래프(flame graph)로 보인다.

```bash
node --cpu-prof --cpu-prof-dir=./profiles server.js
# 부하를 준 뒤 SIGINT로 종료하면 CPU.<pid>.<tid>.cpuprofile 생성
```

**`--prof`** 는 V8의 저수준 틱 로그를 남긴다. 원시 로그는 읽기 어렵지만 `node --prof-process isolate-*.log`로 요약하면 JavaScript/C++/GC별 시간 분포가 나온다. GC 비중이 비정상적으로 높다면 이벤트 루프 지연의 원인이 애플리케이션 로직이 아니라 메모리 압박일 수 있다.

실행 중인 프로세스를 건드려야 한다면 `--inspect`로 인스펙터를 붙여 DevTools에서 프로파일을 시작·중지할 수 있고, 프로그램 안에서 `node:inspector` 모듈의 세션을 열어 원하는 시점에만 프로파일을 뜨는 것도 가능하다. 프로덕션에서는 상시 프로파일링 대신 지연 p99가 임계값을 넘을 때만 짧게 프로파일을 뜨고 저장하는 방식이 실용적이다.

### 메트릭으로 내보내기

일회성 진단이 아니라 지속적인 관측이 목표라면, 이벤트 루프 지연은 반드시 메트릭 시스템으로 나가야 한다. Prometheus를 쓴다면 게이지(gauge) 또는 요약(summary)으로, StatsD 계열이라면 주기적 게이지 전송으로 내보낸다.

```js
import { monitorEventLoopDelay, performance } from 'node:perf_hooks';

const h = monitorEventLoopDelay({ resolution: 10 });
h.enable();
let lastELU = performance.eventLoopUtilization();

setInterval(() => {
  const elu = performance.eventLoopUtilization(lastELU);
  lastELU = performance.eventLoopUtilization();

  metrics.gauge('node.eventloop.delay.p50', h.percentile(50) / 1e6);
  metrics.gauge('node.eventloop.delay.p99', h.percentile(99) / 1e6);
  metrics.gauge('node.eventloop.delay.max', h.max / 1e6);
  metrics.gauge('node.eventloop.utilization', elu.utilization);
  metrics.gauge('node.heap.used', process.memoryUsage().heapUsed);
  h.reset();
}, 10_000).unref();
```

이 네 개 지표(p50, p99, max, utilization)와 힙 사용량은 모든 Node.js 서비스가 기본으로 내보내야 할 최소 집합이다. 대시보드에서 요청 지연 그래프와 이벤트 루프 지연 그래프를 나란히 놓으면, 느려진 원인이 우리 프로세스 내부인지 외부 의존성인지 한눈에 구분된다(31.3절 참조).

### 실무 함정

멀티 프로세스로 운영할 때(25장 참조) 각 워커의 지연은 독립적이다. 집계된 평균만 보면 워커 하나가 막혀 있는 상황을 놓친다. 메트릭에 워커 식별자나 PID를 라벨로 붙여 워커별로 볼 수 있게 한다. 또한 개발 환경에서 측정한 지연은 프로덕션과 무관하다. 실제 데이터 크기와 동시성 수준이 다르면 병목 지점 자체가 달라지므로, 판단은 프로덕션에 준하는 부하에서 내린다.

## 3.7 실무 지침: 무엇을 이벤트 루프에서 하면 안 되는가

이벤트 루프를 막는 코드는 대개 다섯 가지 유형 중 하나다. 각각에 대해 증상과 대안을 정리한다.

### 1. 거대한 `JSON.parse` / `JSON.stringify`

JSON 직렬화는 완전히 동기적이며 취소할 수 없다. 10MB짜리 JSON을 파싱하면 대략 수십에서 수백 밀리초 동안 루프가 멈추고, 그 사이 도착한 모든 요청이 대기한다. 게다가 파싱 결과 객체는 원본 문자열보다 훨씬 큰 힙을 차지해 GC 압박까지 유발한다.

대안은 순서대로 세 가지다. 첫째, **애초에 큰 페이로드를 받지 않는다.** 요청 본문 크기 제한을 걸고, 페이지네이션을 강제한다. 대부분의 거대 JSON은 API 설계 실수의 결과다. 둘째, **스트리밍 파서를 쓴다.** 대용량 데이터를 처리해야 한다면 JSONL(줄 단위 JSON) 포맷으로 바꾸고 스트림으로 한 줄씩 처리한다(7장 참조). 셋째, **워커 스레드로 옮긴다.** 파싱 자체가 불가피하게 크다면 워커에서 파싱하고 결과만 전달한다. 다만 구조화된 복제(structured clone) 비용이 있으므로 워커가 결과를 그대로 소비하도록 설계하는 편이 낫다.

응답 직렬화 쪽에서는 Fastify가 쓰는 **스키마 기반 직렬화**가 효과적이다. 응답 스키마를 미리 알려 주면 범용 `JSON.stringify` 대신 최적화된 직렬화 함수를 생성해 두세 배 빠르게 처리한다(16.4절 참조).

### 2. 동기 파일 시스템 호출

`readFileSync`, `writeFileSync`, `existsSync`, `readdirSync`는 디스크 I/O가 끝날 때까지 스레드를 완전히 정지시킨다. 로컬 SSD에서는 1ms 미만이라 개발 중에는 문제를 느끼지 못하지만, 네트워크 파일 시스템이나 컨테이너의 오버레이 파일 시스템, 혹은 디스크 경합 상황에서는 수백 밀리초가 걸릴 수 있다.

원칙은 명확하다. **동기 fs 호출은 프로세스 시작 시점(설정 파일 로딩, 인증서 읽기)에만 허용한다.** 요청 처리 경로에서는 예외 없이 `node:fs/promises`를 쓴다. 로깅 라이브러리가 파일에 동기로 쓰는지도 확인할 대상이다. 파일을 통째로 읽어 응답하는 코드는 스트림으로 바꾸면 메모리와 지연이 동시에 개선된다(8.3절 참조).

### 3. 정규식 백트래킹(ReDoS)

JavaScript의 정규식 엔진은 백트래킹(backtracking) 방식이라 특정 패턴에서 입력 길이에 지수적으로 비례하는 시간을 쓴다. `/^(a+)+$/` 같은 중첩 수량자가 대표적이고, `(\s*\w+\s*)+$` 처럼 이메일이나 URL 검증에 흔히 쓰이는 패턴에도 같은 위험이 숨어 있다. 공격자가 40자짜리 문자열 하나로 서버 프로세스를 몇 초씩 멈출 수 있으므로 이것은 성능 문제가 아니라 보안 취약점이다(34.2절 참조).

대응은 네 가지다. **입력 길이를 먼저 제한한다** — 정규식을 적용하기 전에 길이 상한을 검사하는 것만으로 대부분의 실전 공격이 막힌다. **중첩 수량자를 제거한다** — `(x+)+`, `(x|x)*` 형태를 발견하면 다시 쓴다. **선형 시간이 보장되는 엔진을 쓴다** — 사용자 입력에 복잡한 패턴을 적용해야 한다면 RE2 바인딩처럼 백트래킹이 없는 엔진을 고려한다. **정적 분석을 CI에 넣는다** — `eslint-plugin-security`나 전용 ReDoS 검사 도구로 위험 패턴을 자동 검출한다.

### 4. 동기 암호화 연산

비밀번호 해싱은 의도적으로 느리게 설계된 연산이다. `crypto.pbkdf2Sync`를 100,000회 반복 설정으로 호출하면 50~100ms 동안 루프가 멈춘다. 로그인 요청 20개가 동시에 오면 2초 가까이 서버 전체가 정지한다. bcrypt 라이브러리의 동기 API도 마찬가지다.

대안은 단순하다. **비동기 버전을 쓴다.** `crypto.pbkdf2`, `crypto.scrypt`, `crypto.randomBytes`, `crypto.generateKeyPair`의 콜백/Promise 버전은 libuv 스레드 풀에서 실행되므로 메인 스레드를 막지 않는다. bcrypt와 argon2 네이티브 모듈도 비동기 API를 제공하며 내부적으로 같은 방식으로 동작한다.

여기서 주의할 점이 하나 있다. 스레드 풀의 기본 크기는 4다. 해싱 요청이 동시에 여러 개 오면 스레드 풀이 포화되고, 같은 풀을 쓰는 파일 읽기와 DNS 조회까지 함께 밀린다. 인증이 잦은 서비스라면 `UV_THREADPOOL_SIZE`를 CPU 코어 수에 맞춰 늘리거나, 해싱을 전담 워커 풀로 분리한다(11.6절 참조).

### 5. 거대한 배열 정렬과 순회

100만 개 객체를 `sort()` 하거나 `map().filter().reduce()` 체인으로 여러 번 순회하는 코드는 수백 밀리초를 쓴다. 이 유형의 문제는 보통 "데이터베이스에서 전부 가져와 애플리케이션에서 처리한다"는 설계에서 나온다.

대안의 우선순위는 이렇다. 첫째, **데이터를 옮기지 말고 연산을 옮긴다.** 정렬, 집계, 필터링은 데이터베이스가 인덱스를 써서 훨씬 잘한다. `ORDER BY`와 `LIMIT`으로 해결되는 문제를 애플리케이션에서 풀지 않는다. 둘째, **작업을 쪼개 양보한다.** 어쩔 수 없이 큰 배열을 순회해야 한다면 청크 단위로 나누고 사이사이에 `setImmediate`로 루프에 제어를 돌려준다.

```js
// 큰 배열을 청크로 나눠 처리하며 이벤트 루프에 숨 쉴 틈을 준다
import { setImmediate as yieldToLoop } from 'node:timers/promises';

async function processInChunks(items, fn, chunkSize = 1000) {
  const out = [];
  for (let i = 0; i < items.length; i += chunkSize) {
    for (const item of items.slice(i, i + chunkSize)) out.push(fn(item));
    await yieldToLoop(); // check 단계로 양보 → 대기 중인 I/O 처리
  }
  return out;
}
```

이 기법은 총 처리 시간을 늘리는 대신 다른 요청의 지연을 줄인다. 전체 처리량이 중요한 배치 작업이라면 오히려 손해이므로, 응답성이 중요한 서버 프로세스에서만 쓴다. 셋째, **워커 스레드로 완전히 분리한다.** 정렬 대상 데이터를 `SharedArrayBuffer`나 전송 가능(transferable) 객체로 넘기면 복제 비용 없이 병렬 처리할 수 있다(11.5절 참조).

### 판단 기준

새 코드를 리뷰할 때 던질 질문은 하나다. **"이 함수는 최악의 입력에서 몇 밀리초를 쓰는가?"** 답이 "입력 크기에 비례한다"이고 그 입력이 외부에서 온다면, 상한을 걸거나 다른 스레드로 옮겨야 한다. 답이 "항상 상수 시간이고 1ms 미만"이라면 이벤트 루프에서 실행해도 안전하다. 이 질문에 답하지 못하는 코드가 프로덕션 장애의 재료가 된다.

## 요약

- Node.js에서 단일 스레드인 것은 **JavaScript 실행 스레드**뿐이다. libuv 스레드 풀, V8 GC 스레드 등이 함께 돌아가므로 프로세스 자체는 멀티 스레드다.
- 이벤트 루프는 timers → pending callbacks → idle/prepare → poll → check → close callbacks 여섯 단계를 반복한다. poll 단계는 `setImmediate`가 대기 중이면 즉시 빠져나가고, 아니면 가장 가까운 타이머까지 혹은 무기한 블로킹한다.
- `process.nextTick` 큐는 마이크로태스크(Promise) 큐보다 먼저 비워지며, 두 큐 모두 **각 콜백이 끝날 때마다** 완전히 비워진다. 재귀 `nextTick`은 이벤트 루프를 굶기므로 반복 예약에는 `setImmediate`를 쓴다.
- 메인 모듈에서 `setTimeout(fn, 0)`과 `setImmediate`의 순서는 1ms 보정과 프로세스 준비 시간 때문에 비결정적이지만, I/O 콜백 안에서는 poll 다음이 check이므로 `setImmediate`가 항상 먼저다.
- 프로세스는 참조된 활성 핸들이 하나도 없을 때 종료된다. 배경 타이머는 `unref()`로 종료를 막지 않게 하고, 남은 핸들은 `process.getActiveResourcesInfo()`로 확인한다.
- `monitorEventLoopDelay()`의 p99와 `eventLoopUtilization()`을 메트릭으로 상시 내보내고, 원인 추적에는 `--cpu-prof`를 쓴다. 과부하 시에는 헬스 체크를 제외한 요청을 503으로 빠르게 거절한다.
- 이벤트 루프에서 금지할 것: 거대한 JSON 직렬화, 요청 경로의 동기 fs 호출, 백트래킹 정규식, 동기 암호화, 대용량 배열 연산. 각각 크기 제한·스트리밍·비동기 API·워커 스레드로 대체한다.

## 연습문제

1. 다음 코드의 출력 순서를 실행 전에 예측하고, 그 근거를 이벤트 루프 단계와 두 개의 큐(nextTick, 마이크로태스크)로 설명하라. 그런 다음 실제로 실행해 예측을 검증하라.
   ```js
   import { readFile } from 'node:fs/promises';
   setImmediate(() => { console.log(1); process.nextTick(() => console.log(2)); });
   setTimeout(() => { console.log(3); Promise.resolve().then(() => console.log(4)); }, 0);
   readFile(new URL(import.meta.url)).then(() => console.log(5));
   process.nextTick(() => console.log(6));
   Promise.resolve().then(() => console.log(7));
   console.log(8);
   ```

HTTP 서버를 만들고 두 개의 엔드포인트를 제공하라. `/fast`는 즉시 응답하고, `/slow`는 `crypto.pbkdf2Sync`로 200,000회 반복 해싱을 수행한 뒤 응답한다. `monitorEventLoopDelay()`로 지연 히스토그램을 수집하면서, 부하 도구로 `/fast`에 초당 100요청을 보내는 동안 `/slow`를 10회 호출하라. `/fast`의 p99 지연과 이벤트 루프 지연 p99가 어떻게 변하는지 기록한 뒤, `/slow`를 비동기 `crypto.pbkdf2`로 바꾸고 같은 실험을 반복해 두 결과를 비교하라.
