# 11장. 멀티 프로세스와 멀티 스레드

Node.js는 "단일 스레드 플랫폼"이라는 문장으로 요약되곤 하지만, 이 요약은 절반만 맞고 절반은 틀렸다. 사용자가 작성한 JavaScript는 한 번에 하나의 스레드에서만 실행되지만, 그 코드를 떠받치는 프로세스는 처음부터 여러 개의 스레드로 이루어져 있다. 이 사실을 모르면 왜 파일 여섯 개를 동시에 읽었는데 네 개씩 끊어서 끝나는지, 왜 DNS 조회가 느려지자 관계없는 압축 작업까지 지연되는지 설명할 수 없다.

이 장에서는 먼저 Node.js 프로세스의 실제 스레드 구조를 실측으로 확인하고, CPU를 더 쓰기 위한 두 가지 도구인 자식 프로세스(child process)와 워커 스레드(worker thread)를 차례로 다룬다. 이어 공유 메모리와 원자적 연산으로 스레드 사이의 상태를 다루는 방법을 살펴본 뒤, 하나의 CPU 바운드 문제를 네 가지 전략으로 구현해 실행 시간과 이벤트 루프 지연을 직접 비교한다. 마지막으로 프로덕션에서 쓸 수 있는 워커 풀을 만들고, 언제 워커 대신 별도 서비스로 분리해야 하는지를 판단하는 기준을 세운다.

## 11.1 단일 스레드 모델의 이점과 한계

### 왜 필요한가

"Node.js는 단일 스레드다"라는 말은 성능 문제를 진단할 때 거의 항상 잘못된 결론으로 이어진다. 실제로는 두 가지 서로 다른 층위가 섞여 있다. **JavaScript 실행은 단일 스레드**다. 즉 어느 순간에도 사용자 코드는 한 줄만 실행된다. 그러나 **Node.js 프로세스는 멀티 스레드**다. `node -e "setInterval(()=>{},1000)"` 하나만 띄워 놓고 스레드 수를 세어 보면 최소 7개 안팎이 나온다.

```bash
# Linux에서 실행 중인 Node.js 프로세스의 스레드 수를 센다
$ node -e 'setInterval(() => {}, 1000)' &
$ ls /proc/$!/task | wc -l
7
```

이 스레드들의 정체는 대략 다음과 같다.

| 스레드 | 개수 | 역할 |
|---|---|---|
| 메인 스레드 | 1 | 이벤트 루프와 JavaScript 실행 |
| libuv 스레드풀 | 기본 4 | 논블로킹 API가 없는 작업을 대신 수행 |
| V8 헬퍼 | 2~4 | 백그라운드 GC, JIT 컴파일, 최적화 |
| 인스펙터 | 0~1 | `--inspect` 사용 시 디버깅 프로토콜 처리 |

### 어떻게 동작하는가

핵심은 **libuv 스레드풀(thread pool)** 이다. 운영체제가 논블로킹 인터페이스를 제공하는 작업 — TCP/UDP 소켓, 파이프, 시그널 — 은 epoll(Linux), kqueue(macOS), IOCP(Windows) 같은 이벤트 디멀티플렉서에 등록되므로 스레드가 필요 없다(3장 참조). 하지만 다음 네 부류는 그런 인터페이스가 없거나 순수 계산이어서, libuv가 스레드풀에 던져 처리한다.

- **파일 시스템**: `fs` 모듈의 거의 모든 비동기 API (Linux의 `io_uring` 경로를 제외하면)
- **압축**: `zlib`의 비동기 함수 (`gzip`, `deflate`, `brotliCompress` 등)
- **암호**: `crypto.pbkdf2`, `scrypt`, `randomBytes`, `generateKeyPair`, `sign`/`verify`의 비동기 형태
- **DNS**: `dns.lookup` (내부적으로 블로킹 함수인 `getaddrinfo`를 호출한다). 반면 `dns.resolve` 계열은 c-ares를 통해 네트워크로 직접 질의하므로 스레드풀을 쓰지 않는다

스레드풀 크기가 기본 4라는 사실은 실측으로 바로 드러난다.

```js
// threadpool-saturation.mjs — 스레드풀 크기를 눈으로 확인한다
import { pbkdf2 } from 'node:crypto'
import { promisify } from 'node:util'

const pbkdf2Async = promisify(pbkdf2)
const start = process.hrtime.bigint()

const elapsed = () => Number(process.hrtime.bigint() - start) / 1e6

// 각각 약 400ms가 걸리는 작업 6개를 "동시에" 시작한다
for (let i = 0; i < 6; i++) {
  pbkdf2Async('password', 'salt', 500_000, 64, 'sha512')
    .then(() => console.log(`작업 ${i} 완료: ${elapsed().toFixed(0)}ms`))
}
```

```text
작업 0 완료: 412ms
작업 1 완료: 415ms
작업 2 완료: 418ms
작업 3 완료: 421ms
작업 4 완료: 828ms   ← 두 번째 배치
작업 5 완료: 831ms
```

여섯 개를 동시에 던졌지만 네 개가 먼저 끝나고 나머지 둘은 두 배의 시간이 걸렸다. 스레드가 네 개뿐이기 때문이다. 환경 변수로 크기를 바꿔 보면 결과가 달라진다.

```bash
$ UV_THREADPOOL_SIZE=6 node threadpool-saturation.mjs
작업 0 완료: 445ms
...
작업 5 완료: 452ms   ← 모두 한 배치에 끝난다
```

더 위험한 것은 **스레드풀 고갈(thread pool starvation)** 이 서로 무관해 보이는 작업들 사이에 지연을 전파한다는 점이다. 아래 코드는 `pbkdf2` 네 개가 스레드풀을 점유한 동안 아주 작은 파일 읽기가 어떻게 밀리는지 보여준다.

```js
// starvation.mjs — 암호 연산이 파일 읽기를 막는다
import { pbkdf2 } from 'node:crypto'
import { readFile } from 'node:fs/promises'

const t0 = Date.now()

// 스레드풀 4칸을 모두 점유하는 무거운 작업
for (let i = 0; i < 4; i++) {
  pbkdf2('password', 'salt', 1_000_000, 64, 'sha512', () => {})
}

// 몇 마이크로초면 끝날 파일 읽기
readFile('/etc/hostname').then(() => {
  console.log(`파일 읽기 대기 시간: ${Date.now() - t0}ms`)  // 800ms 이상
})
```

이벤트 루프는 전혀 막히지 않았다. `setInterval`로 심어 둔 타이머는 정확히 돈다. 그런데도 파일 읽기 응답 시간은 1초 가까이 늘어난다. "이벤트 루프 지연은 0인데 p99 레이턴시가 튄다"는 현상의 흔한 원인이 바로 이것이다.

### 실무 함정

**첫째, `UV_THREADPOOL_SIZE`는 스레드풀이 처음 사용되기 전에 설정해야 한다.** 스레드풀은 지연 초기화되며 한 번 만들어지면 크기를 바꿀 수 없다. 코드 첫 줄에서 `process.env.UV_THREADPOOL_SIZE = '16'`을 실행해도, 그보다 앞서 어떤 모듈이 `fs` 비동기 호출을 했다면 무시된다. 반드시 프로세스 바깥(셸, `Dockerfile`의 `ENV`, 오케스트레이터의 환경 변수)에서 지정한다. 상한은 1024다.

**둘째, 스레드풀을 무작정 키우는 것은 해법이 아니다.** 스레드가 코어 수를 크게 넘어가면 컨텍스트 스위칭과 캐시 오염 때문에 전체 처리량이 오히려 떨어진다. 실용적인 출발점은 `os.availableParallelism()` 값 정도이며, 그 이상이 필요하다면 문제는 스레드풀이 아니라 설계에 있다.

**셋째, `dns.lookup`을 조심한다.** HTTP 클라이언트가 호스트 이름으로 요청을 보낼 때마다 내부적으로 `dns.lookup`이 호출된다. DNS 서버 응답이 느려지면 스레드풀이 그대로 잠기고, 그 프로세스의 모든 파일 I/O와 압축이 함께 멈춘다. 외부 API 호출량이 많은 서비스라면 DNS 결과 캐싱이 필수다.

정리하면 단일 스레드 모델의 이점은 명확하다. 락(lock)이 없고, 데이터 경쟁(data race)이 없으며, 컨텍스트 스위칭 비용 없이 수만 개의 동시 연결을 처리한다. 대신 두 가지를 잃는다. 하나는 **한 조각의 CPU 바운드 코드가 모든 요청을 정지시킨다**는 것이고, 다른 하나는 **기본적으로 코어를 하나만 쓴다**는 것이다. 이 장의 나머지는 이 두 가지 한계를 넘는 방법에 관한 것이다.

## 11.2 자식 프로세스: `spawn`, `exec`, `fork`

### 왜 필요한가

멀티 코어를 쓰는 가장 오래되고 가장 견고한 방법은 프로세스를 여러 개 띄우는 것이다. 프로세스는 메모리 공간이 완전히 분리되어 있어서 하나가 죽어도 나머지는 멀쩡하고, 메모리 누수도 격리된다. `node:child_process` 모듈은 자식 프로세스를 만드는 네 가지 함수를 제공하는데, 이름이 비슷해서 자주 혼동된다.

### 어떻게 동작하는가

네 함수의 차이는 다음 표로 정리된다.

| 함수 | 셸 경유 | 결과 전달 | IPC 채널 | 주 용도 |
|---|---|---|---|---|
| `spawn(cmd, args)` | 아니오(기본) | 스트림 | 옵션으로 가능 | 출력이 크거나 오래 도는 명령 |
| `exec(cmdString)` | **예** | 버퍼(콜백) | 없음 | 짧은 셸 명령, 파이프라인 |
| `execFile(file, args)` | 아니오 | 버퍼(콜백) | 없음 | 짧은 출력의 실행 파일 호출 |
| `fork(modulePath)` | 아니오 | 스트림 | **항상 생성** | 또 다른 Node.js 프로세스 |

`spawn`이 근본이고 나머지 셋은 그 위의 편의 함수다. `exec`는 `/bin/sh -c "명령 문자열"`을 실행하고 표준 출력 전체를 버퍼에 모아 콜백에 넘긴다. `execFile`은 셸을 거치지 않고 실행 파일을 직접 호출하되 결과는 마찬가지로 버퍼링한다. `fork`는 현재와 같은 Node.js 실행 파일로 지정한 모듈을 실행하며, 부모와 자식 사이에 IPC 채널을 자동으로 만든다.

```js
// spawn-stream.mjs — 출력이 큰 명령은 스트림으로 받는다
import { spawn } from 'node:child_process'
import { createWriteStream } from 'node:fs'
import { pipeline } from 'node:stream/promises'

const child = spawn('find', ['/usr', '-type', 'f'], { stdio: ['ignore', 'pipe', 'pipe'] })

// 표준 출력을 파일로 흘려보낸다. 메모리에 쌓이지 않는다
await pipeline(child.stdout, createWriteStream('files.txt'))

const code = await new Promise(resolve => child.on('close', resolve))
console.log(`종료 코드: ${code}`)
```

### 셸 주입: `exec`를 쓰면 안 되는 이유

`exec`의 인자는 **셸이 해석하는 문자열**이다. 사용자 입력이 그 문자열에 섞이는 순간 임의 명령 실행 취약점이 된다.

```js
// 절대 이렇게 쓰지 않는다
import { exec } from 'node:child_process'

function convertImage (filename) {
  // filename이 "a.png; rm -rf /var/data" 라면?
  exec(`convert ${filename} out.png`, (err, stdout) => { /* ... */ })
}
```

`filename`에 세미콜론, 백틱, `$(...)`, 파이프 중 무엇이라도 들어오면 공격자의 명령이 그대로 실행된다. 따옴표로 감싸는 것도 근본적인 해결이 아니다. 작은따옴표 자체를 이스케이프하는 로직은 셸마다 다르고, 실수하기 쉽다.

**해결책은 인자를 배열로 넘기는 `execFile` 또는 `spawn`이다.**

```js
// 안전한 버전 — 셸이 개입하지 않으므로 메타 문자가 데이터로만 취급된다
import { execFile } from 'node:child_process'
import { promisify } from 'node:util'

const execFileAsync = promisify(execFile)

async function convertImage (filename) {
  const { stdout } = await execFileAsync('convert', [filename, 'out.png'], {
    timeout: 10_000,        // 10초 넘으면 SIGTERM
    maxBuffer: 4 * 1024 * 1024
  })
  return stdout
}
```

배열로 넘긴 인자는 `execve` 시스템 콜에 그대로 전달되므로 셸 파싱 단계 자체가 존재하지 않는다. 규칙은 단순하다. **셸 기능(파이프, 리다이렉션, 글로브)이 반드시 필요한 경우가 아니면 `exec`와 `shell: true`를 쓰지 않는다.** 필요하다면 입력을 화이트리스트로 검증한 뒤에만 쓴다(34장 참조).

### stdio 옵션과 백프레셔

`stdio` 옵션은 자식의 파일 디스크립터 0, 1, 2(및 그 이상)를 어디에 연결할지 정한다.

```js
spawn('cmd', [], { stdio: 'pipe' })                 // ['pipe','pipe','pipe']와 동일
spawn('cmd', [], { stdio: 'inherit' })              // 부모의 터미널을 그대로 물려준다
spawn('cmd', [], { stdio: 'ignore' })               // /dev/null로 버린다
spawn('cmd', [], { stdio: ['ignore', logFd, logFd] }) // 정수 fd를 직접 지정
spawn('cmd', [], { stdio: ['pipe', 'pipe', 'pipe', 'ipc'] }) // IPC 채널 추가
```

`'pipe'`를 쓰면 자식의 출력은 OS 파이프 버퍼(리눅스 기본 64KiB)에 쌓인다. 부모가 `child.stdout`을 읽지 않으면 버퍼가 차고, **자식의 `write()`가 블로킹되어 자식 프로세스가 멈춘다.** 데드락처럼 보이는 이 현상은 "자식이 응답하지 않는다"는 버그 리포트의 단골 원인이다. 출력에 관심이 없다면 `'ignore'`를 쓰고, 관심이 있다면 반드시 소비한다.

`exec`와 `execFile`의 `maxBuffer`(기본 1MiB)도 같은 맥락이다. 출력이 이 값을 넘으면 자식은 `SIGTERM`을 받고 죽으며 `ERR_CHILD_PROCESS_STDIO_MAXBUFFER` 오류가 난다. 출력 크기를 예측할 수 없다면 `exec` 계열 대신 `spawn` + 스트림을 쓴다.

### 좀비와 고아 방지

자식이 종료되면 커널은 종료 코드를 보관한 채 프로세스 테이블 항목을 남긴다. 부모가 이를 수거(reap)해야 항목이 사라지는데, Node.js는 `exit` 이벤트를 처리하면서 자동으로 수거하므로 보통은 문제가 없다. 진짜 문제는 반대 방향, 즉 **부모가 먼저 죽고 자식이 살아남는 고아(orphan) 프로세스**다.

```js
import { spawn } from 'node:child_process'

const ac = new AbortController()
const child = spawn('long-running-task', [], {
  signal: ac.signal,        // abort 시 자식에게 SIGTERM
  killSignal: 'SIGTERM',
  detached: false           // 부모의 프로세스 그룹에 남긴다
})

child.on('error', err => {
  if (err.name === 'AbortError') console.log('요청 취소로 자식 종료')
})

// 부모가 종료될 때 자식도 정리한다
const cleanup = () => { if (!child.killed) child.kill('SIGTERM') }
process.once('SIGTERM', cleanup)
process.once('SIGINT', cleanup)
process.once('exit', cleanup)

// 필요할 때 취소
setTimeout(() => ac.abort(), 5_000)
```

`child.kill()`은 자식 **하나**에만 시그널을 보낸다. 자식이 다시 손자 프로세스를 띄웠다면 손자는 살아남는다. 프로세스 트리 전체를 죽이려면 `detached: true`로 새 프로세스 그룹을 만든 뒤 그룹 전체에 시그널을 보낸다.

```js
const child = spawn('sh', ['-c', 'sleep 1000 & wait'], { detached: true })
// 음수 PID는 "프로세스 그룹 전체"를 의미한다
process.kill(-child.pid, 'SIGTERM')
```

반대로 자식을 부모와 무관하게 계속 살려 두고 싶다면 `detached: true` + `child.unref()` + `stdio: 'ignore'` 세 가지를 함께 쓴다. 셋 중 하나라도 빠지면 부모가 종료되지 않거나 자식이 함께 죽는다. 컨테이너 환경에서 PID 1이 시그널을 자식에게 전파하지 않아 생기는 문제는 32장에서 따로 다룬다.

## 11.3 프로세스 간 메시지 통신(IPC)

### 왜 필요한가

프로세스를 나누면 메모리가 분리되므로 안전하지만, 동시에 아무것도 공유할 수 없게 된다. 부모가 자식에게 작업을 시키고 결과를 돌려받으려면 통신 수단이 필요하다. 표준 입출력을 직접 파싱해도 되지만, `fork`로 만든 자식과는 훨씬 편한 길이 있다. `fork`는 부모와 자식 사이에 **IPC 채널(inter-process communication channel)** 을 자동으로 열어 준다.

### 어떻게 동작하는가

IPC 채널은 유닉스 도메인 소켓(윈도우에서는 네임드 파이프) 위에 구현된 메시지 지향 통로다. 부모는 `child.send()`, 자식은 `process.send()`로 보내고, 반대편에서 `message` 이벤트로 받는다.

```js
// parent.mjs
import { fork } from 'node:child_process'

const child = fork(new URL('./worker.mjs', import.meta.url))

child.on('message', msg => {
  console.log('자식으로부터:', msg)
})

child.send({ type: 'sum', values: [1, 2, 3, 4, 5] })

// 통신이 끝나면 명시적으로 채널을 닫고 종료를 기다린다
child.on('exit', code => console.log('자식 종료:', code))
setTimeout(() => child.disconnect(), 1000)
```

```js
// worker.mjs
process.on('message', msg => {
  if (msg.type === 'sum') {
    const total = msg.values.reduce((a, b) => a + b, 0)
    process.send({ type: 'result', total })
  }
})

// 채널이 닫히면 정리 후 종료한다
process.on('disconnect', () => process.exit(0))
```

### 직렬화: 구조화 복제와 JSON

메시지는 프로세스 경계를 넘기 위해 반드시 직렬화(serialization)된다. Node.js는 두 가지 방식을 제공한다.

```js
fork('./worker.mjs', [], { serialization: 'json' })      // 기본값
fork('./worker.mjs', [], { serialization: 'advanced' })  // 구조화 복제
```

기본값인 `'json'`은 `JSON.stringify`/`JSON.parse`와 사실상 같다. 빠르고 단순하지만 표현력이 좁다. `Date`는 문자열이 되고, `Map`·`Set`·`BigInt`·`TypedArray`·순환 참조는 모두 잃거나 예외를 낸다. `undefined`인 프로퍼티는 사라진다.

`'advanced'`는 V8의 **구조화 복제 알고리즘(structured clone algorithm)** 을 직접 쓴다. `Map`, `Set`, `Date`, `RegExp`, `ArrayBuffer`, `TypedArray`, `BigInt`, 순환 참조를 모두 보존하며, 이진 데이터는 base64 인코딩 없이 바이트 그대로 전송되므로 큰 `Buffer`를 보낼 때 훨씬 빠르다. 대신 문자열 위주의 작은 메시지에서는 JSON이 근소하게 빠를 수 있다.

```js
// serialization-bench.mjs — 1MiB 버퍼를 1000번 보낼 때의 차이
import { fork } from 'node:child_process'

async function bench (mode) {
  const child = fork(new URL('./echo.mjs', import.meta.url), [], { serialization: mode })
  const payload = { data: Buffer.alloc(1024 * 1024, 7) }
  const t0 = performance.now()
  for (let i = 0; i < 1000; i++) {
    child.send(payload)
    await new Promise(res => child.once('message', res))
  }
  const ms = performance.now() - t0
  child.kill()
  return ms
}

console.log('json    :', (await bench('json')).toFixed(0), 'ms')      // 예: 9800ms
console.log('advanced:', (await bench('advanced')).toFixed(0), 'ms')  // 예: 2100ms
```

`'json'` 모드에서 `Buffer`는 `{ type: 'Buffer', data: [7, 7, ...] }` 형태의 거대한 숫자 배열로 변환된다. 1MiB가 수 MiB의 텍스트가 되는 셈이니 느릴 수밖에 없다.

어느 쪽이든 기억할 원칙은 하나다. **IPC 메시지의 비용은 크기에 비례하며, 그 비용은 메인 스레드에서 지불된다.** 직렬화와 역직렬화는 동기 작업이므로 1MiB 메시지 하나가 양쪽 프로세스의 이벤트 루프를 각각 수 밀리초씩 멈춘다. 작업 단위를 크게 잡고 메시지 수를 줄이는 편이, 잘게 쪼개 자주 보내는 것보다 거의 항상 낫다.

### 핸들 전달: `cluster`의 원리

IPC 채널의 가장 강력한 기능은 데이터가 아니라 **핸들(handle)** 을 넘길 수 있다는 점이다. `send`의 두 번째 인자로 `net.Server`, `net.Socket`, `dgram.Socket`을 넘기면, 운영체제 수준에서 파일 디스크립터가 자식에게 복제된다.

```js
// handle-parent.mjs — 서버 소켓 자체를 자식에게 넘긴다
import { fork } from 'node:child_process'
import { createServer } from 'node:net'

const server = createServer()
server.listen(3000, () => console.log('부모가 3000 포트를 열었다'))

const children = []
for (let i = 0; i < 4; i++) {
  const child = fork(new URL('./handle-child.mjs', import.meta.url))
  child.send({ type: 'server' }, server)   // 두 번째 인자가 핸들
  children.push(child)
}

// 부모는 더 이상 연결을 받지 않는다. 커널이 자식들에게 분배한다
server.close()
```

```js
// handle-child.mjs
process.on('message', (msg, handle) => {
  if (msg.type !== 'server') return
  handle.on('connection', socket => {
    socket.end(`처리 프로세스: ${process.pid}\n`)
  })
})
```

이것이 `cluster` 모듈의 심장이다. `cluster`는 마스터가 포트를 열고 그 리스닝 소켓을 워커들에게 나눠 주거나(라운드로빈 모드에서는 마스터가 연결을 받아 개별 소켓 핸들을 넘긴다), 워커가 직접 `SO_REUSEPORT` 유사 동작으로 accept하도록 조율한다. 요청 분배 정책과 무중단 재시작 같은 운영 관점의 논의는 25장에서 이어진다.

### 실무 함정

**`send()`는 비동기이며 백프레셔가 있다.** 반환값이 `false`면 커널 버퍼가 찼다는 뜻이므로, 대량 전송 시에는 반환값을 확인하거나 완료 콜백(`send(msg, cb)`)을 기다려야 한다. 무시하고 계속 보내면 메모리에 큐가 무한히 쌓인다.

**채널은 프로세스를 살려 둔다.** `fork`한 자식은 IPC 채널이 열려 있는 한 이벤트 루프에 참조가 남아 종료하지 않는다. 작업이 끝나면 부모가 `child.disconnect()`를 호출하거나, 자식이 `process.channel.unref()`로 참조를 해제해야 한다.

**메시지 순서는 보장되지만 도착은 보장되지 않는다.** 자식이 `process.send()` 직후 `process.exit()`을 호출하면 메시지가 채널에 실리기 전에 프로세스가 사라져 부모는 아무것도 받지 못한다. 전송 콜백이 호출된 뒤에 종료하거나, 부모의 `disconnect` 신호를 기다렸다가 종료한다.

## 11.4 `worker_threads`: 스레드 모델과 공유 메모리

### 왜 필요한가

자식 프로세스는 격리가 강력한 대신 비싸다. 프로세스 하나를 새로 띄우면 새 V8 인스턴스, 새 힙, 새 이벤트 루프가 만들어지고 30~60MiB의 상주 메모리를 먹는다. 게다가 모든 데이터 교환이 직렬화를 거친다. **같은 프로세스 안에서 JavaScript를 병렬로 실행하되 메모리 일부를 진짜로 공유하고 싶을 때** 쓰는 것이 `node:worker_threads`다.

### 어떻게 동작하는가

`Worker`는 새 스레드에 **독립된 V8 아이솔레이트(isolate)와 독립된 힙, 독립된 이벤트 루프**를 만든다. 여기서 반드시 짚어야 할 점이 있다. **워커는 스레드지만 힙은 분리되어 있다.** 전역 변수는 공유되지 않고, 같은 모듈을 임포트해도 각 워커에서 새로 평가되며, 싱글턴 캐시는 워커마다 따로 존재한다. Java나 C++의 스레드를 떠올리면 안 된다. 기본 모델은 프로세스에 가깝고, 다른 점은 주소 공간을 물리적으로 공유할 **수단이 있다**는 것뿐이다.

```js
// main.mjs
import { Worker } from 'node:worker_threads'

function runWorker (data) {
  return new Promise((resolve, reject) => {
    const worker = new Worker(new URL('./hash-worker.mjs', import.meta.url), {
      workerData: data,                  // 생성 시 1회 전달 (구조화 복제)
      resourceLimits: {
        maxOldGenerationSizeMb: 256,     // 워커 힙 상한
        maxYoungGenerationSizeMb: 16
      }
    })
    worker.once('message', resolve)
    worker.once('error', reject)
    worker.once('exit', code => {
      if (code !== 0) reject(new Error(`워커가 코드 ${code}로 종료`))
    })
  })
}

console.log(await runWorker({ text: 'hello', rounds: 200_000 }))
```

```js
// hash-worker.mjs
import { workerData, parentPort } from 'node:worker_threads'
import { pbkdf2Sync } from 'node:crypto'

// 워커 안에서는 동기 API를 써도 된다. 메인 이벤트 루프는 영향받지 않는다
const digest = pbkdf2Sync(workerData.text, 'salt', workerData.rounds, 64, 'sha512')
parentPort.postMessage(digest.toString('hex'))
```

`workerData`는 생성 시점에 한 번 전달되는 초기 데이터이며 구조화 복제로 복사된다. 이후의 양방향 통신은 `parentPort`를 통한다.

### 생성 비용

워커 하나를 만드는 데는 새 아이솔레이트 초기화, 부트스트랩 코드 실행, 모듈 로딩이 필요하다. 실측하면 대략 다음과 같다.

| 항목 | 대략적인 비용 |
|---|---|
| `new Worker()` 부터 첫 `message` 까지 | 15~50ms |
| 워커 1개의 기본 상주 메모리 | 5~10MiB |
| `child_process.fork()` 프로세스 1개 | 40~80ms / 30~60MiB |

밀리초 단위 작업 하나를 처리하려고 매번 워커를 만드는 것은 배보다 배꼽이 크다. **워커는 만들어 두고 재사용한다**는 것이 기본 원칙이며, 그 구현이 11.7의 워커 풀이다.

### `MessagePort`와 전송 가능 객체

`parentPort` 외에 임의의 채널을 만들 수 있다. `MessageChannel`은 서로 연결된 두 개의 `MessagePort`를 만들고, 포트는 워커 사이로 전달할 수 있다. 워커 A와 워커 B가 메인 스레드를 거치지 않고 직접 통신하게 만들 때 쓴다.

```js
import { Worker, MessageChannel } from 'node:worker_threads'

const { port1, port2 } = new MessageChannel()
const a = new Worker('./a.mjs')
const b = new Worker('./b.mjs')

// 포트는 전송 가능 객체이므로 transferList에 넣어 넘긴다
a.postMessage({ peer: port1 }, [port1])
b.postMessage({ peer: port2 }, [port2])
```

`postMessage`의 두 번째 인자인 **transferList**는 "복사하지 말고 소유권을 넘겨라"는 지시다. `ArrayBuffer`, `MessagePort`, `ReadableStream` 등이 대상이다. 전송된 `ArrayBuffer`는 보낸 쪽에서 **분리(detached)** 되어 `byteLength`가 0이 되고 접근이 불가능해진다. 대신 아무리 커도 비용은 상수다.

```js
// transfer.mjs — 64MiB를 복사 없이 넘긴다
const buf = new ArrayBuffer(64 * 1024 * 1024)
new Uint8Array(buf).fill(1)

const t0 = performance.now()
worker.postMessage({ buf }, [buf])          // 전송: 0.05ms 수준
console.log('전송 후 크기:', buf.byteLength) // 0 — 분리되었다
console.log((performance.now() - t0).toFixed(2), 'ms')

// 비교: transferList 없이 보내면 64MiB 전체가 복사된다 (수십 ms + 메모리 2배)
```

### 종료와 오류 처리

워커의 생애 주기 이벤트는 세 가지다.

- `'message'`: 워커가 `parentPort.postMessage()`를 호출했을 때
- `'error'`: 워커 안에서 처리되지 않은 예외가 발생했을 때. 워커는 이후 종료된다
- `'exit'`: 워커 스레드가 끝났을 때. 종료 코드가 함께 온다

```js
const worker = new Worker('./task.mjs')

worker.on('error', err => {
  // 워커 내부의 throw가 여기로 온다. 반드시 처리한다
  console.error('워커 오류:', err)
})

worker.on('exit', code => {
  console.log('워커 종료 코드:', code)   // terminate()로 죽이면 1
})

// 강제 종료: 진행 중인 JavaScript를 중단하고 스레드를 끝낸다
const exitCode = await worker.terminate()
```

`worker.terminate()`는 무한 루프에 빠진 워커도 확실히 죽일 수 있다는 점에서 중요하다. 메인 스레드에서는 불가능한 일이다. 이것이 신뢰할 수 없는 코드나 사용자 제공 코드를 워커에서 실행하는 이유 중 하나다.

### 실무 함정

**워커에서 발생한 오류를 처리하지 않으면 프로세스 전체가 죽는다.** `'error'` 리스너가 없으면 처리되지 않은 예외로 간주되어 메인 프로세스가 종료된다. 워커를 만드는 코드에는 항상 `'error'`와 `'exit'` 핸들러를 함께 붙인다.

**모듈 부작용이 워커마다 반복된다.** DB 커넥션 풀을 모듈 최상위에서 만드는 코드가 있다면, 워커 8개는 커넥션 풀 8개를 만든다. 워커에서 로드되는 모듈은 최상위 부작용을 최소화하고, 필요한 자원은 명시적으로 초기화한다.

**`process.exit()`을 워커 안에서 호출하면 그 워커만 끝난다.** 반면 워커 안에서 `process.chdir()`이나 일부 프로세스 전역 설정 변경은 아예 지원되지 않는다. 워커는 프로세스가 아니라는 사실이 여기서 드러난다.

**모든 네이티브 애드온(native addon)이 스레드 안전하지는 않다.** 컨텍스트 인식(context-aware)으로 빌드되지 않은 애드온을 워커에서 로드하면 프로세스가 크래시한다. `node-api`(N-API) 기반 애드온을 쓰는 것이 안전하다.

## 11.5 `SharedArrayBuffer`와 `Atomics`

### 왜 필요한가

`transferList`는 소유권을 넘길 뿐이어서 한쪽만 데이터를 볼 수 있다. 여러 워커가 **동시에 같은 메모리를 읽고 써야** 한다면 `SharedArrayBuffer`(SAB)가 유일한 수단이다. 큰 행렬을 여러 워커가 구역별로 나눠 계산하거나, 워커들이 공유 카운터로 진행률을 보고하거나, 락 없는 큐를 만드는 경우가 대표적이다.

### 어떻게 동작하는가

SAB는 `postMessage`로 그냥 보내면 된다. transferList에 넣지 않으며, 넣어서도 안 된다. 보내는 쪽과 받는 쪽이 **같은 물리 메모리를 가리키는 뷰**를 각각 갖게 된다.

```js
// sab-main.mjs
import { Worker } from 'node:worker_threads'

const sab = new SharedArrayBuffer(4 * 8)   // Int32 8칸
const counter = new Int32Array(sab)

for (let i = 0; i < 4; i++) {
  new Worker(new URL('./sab-worker.mjs', import.meta.url), { workerData: { sab } })
}

setInterval(() => {
  // 원자적으로 읽는다. 찢어진 값(torn read)을 방지한다
  console.log('현재 카운트:', Atomics.load(counter, 0))
}, 200)
```

```js
// sab-worker.mjs
import { workerData } from 'node:worker_threads'

const counter = new Int32Array(workerData.sab)

for (let i = 0; i < 1_000_000; i++) {
  Atomics.add(counter, 0, 1)   // 읽기-수정-쓰기가 하나의 원자적 연산
}
```

`counter[0]++`로 쓰면 결과는 반드시 틀린다. 이 표현식은 "읽고, 더하고, 쓴다"는 세 단계로 컴파일되며, 그 사이에 다른 스레드가 끼어들어 갱신을 잃는 **경쟁 상태(race condition)** 가 발생한다. `Atomics.add`는 CPU의 원자적 명령(x86의 `lock xadd`)으로 컴파일되어 이 문제를 없앤다.

조건부 갱신에는 `Atomics.compareExchange`를 쓴다. "값이 여전히 기대한 값이면 바꾼다"는 CAS(compare-and-swap) 연산이며, 락 없는 자료구조의 기본 블록이다.

```js
// 최댓값을 경쟁 없이 갱신한다
function updateMax (arr, index, candidate) {
  let current = Atomics.load(arr, index)
  while (candidate > current) {
    const witness = Atomics.compareExchange(arr, index, current, candidate)
    if (witness === current) return true   // 성공
    current = witness                       // 다른 스레드가 먼저 바꿨다. 재시도
  }
  return false
}
```

`Atomics.wait`와 `Atomics.notify`는 바쁜 대기(busy wait) 없이 스레드를 재우고 깨운다. `wait`는 지정한 인덱스의 값이 예상값과 같으면 스레드를 블로킹하고, 다른 스레드가 `notify`를 호출하면 깨어난다.

```js
// 워커: 신호가 올 때까지 대기 (CPU를 쓰지 않는다)
Atomics.wait(flags, 0, 0)          // flags[0]이 0인 동안 잠든다
// 메인: 값을 바꾸고 깨운다
Atomics.store(flags, 0, 1)
Atomics.notify(flags, 0, 1)        // 대기 중인 스레드 1개를 깨운다
```

SAB를 여러 워커에 나눠 줄 때는 **구역을 겹치지 않게 분할**하는 방식이 가장 안전하다. 예를 들어 길이 N의 `Float64Array`를 워커 k개가 처리한다면, 워커 i는 `[i*N/k, (i+1)*N/k)` 구간만 읽고 쓰도록 정한다. 이렇게 하면 원자적 연산 없이도 경쟁이 발생하지 않으며, 각 워커가 자기 캐시 라인만 건드리므로 코어 간 캐시 무효화(false sharing)도 줄어든다. `Atomics`가 필요한 곳은 여러 워커가 같은 칸을 만지는 지점 — 공유 카운터, 작업 인덱스 분배, 완료 신호 — 로 한정하는 것이 원칙이다.

### 실무 함정

**`Atomics.wait`를 메인 스레드에서 호출하지 않는다.** Node.js는 브라우저와 달리 메인 스레드에서의 호출을 막지 않지만, 호출하는 순간 이벤트 루프가 완전히 멈춘다. 타이머도, 네트워크도, 시그널 처리도 정지한다. 메인 스레드에서 기다려야 한다면 프로미스를 돌려주는 `Atomics.waitAsync`를 쓴다.

**`wait`/`notify`는 `Int32Array`와 `BigInt64Array`에서만 동작한다.** 다른 타입의 뷰에서는 `TypeError`가 난다. 또한 SAB에는 숫자만 담을 수 있다. 문자열이나 객체를 공유하려면 직접 인코딩하거나 별도 채널을 써야 한다.

**공유 메모리를 도입하는 순간 단일 스레드 모델의 가장 큰 이점을 잃는다.** 데드락, ABA 문제, 메모리 가시성 같은 고전적 동시성 버그가 모두 돌아온다. 진짜로 필요한 경우 — 대용량 이진 데이터를 여러 워커가 나눠 처리할 때 — 로 한정하고, 그 외에는 메시지 전달을 쓴다.

## 11.6 CPU 바운드 작업 처리 전략 비교

### 왜 필요한가

이론적인 논의는 여기까지다. 이제 하나의 CPU 바운드 문제를 정하고 네 가지 전략으로 구현해 **실행 시간**과 **이벤트 루프 지연**을 함께 측정한다. 이 두 값을 같이 봐야 하는 이유는, 어떤 전략은 빠르지만 서버를 마비시키고 어떤 전략은 서버를 살리지만 느리기 때문이다.

문제는 **부분집합 합(subset sum)** 이다. 주어진 정수 집합의 부분집합 중 합이 목표값과 같은 것의 개수를 센다. 원소가 n개면 부분집합은 2^n개이므로 n=24면 약 1,600만 번의 반복이 필요한 전형적인 지수 시간 문제다.

```js
// subset-sum.mjs — 공통 알고리즘
export function countSubsets (set, target) {
  const n = set.length
  let count = 0
  for (let mask = 0; mask < (1 << n); mask++) {
    let sum = 0
    for (let i = 0; i < n; i++) {
      if (mask & (1 << i)) sum += set[i]
    }
    if (sum === target) count++
  }
  return count
}
```

측정에는 `perf_hooks`의 이벤트 루프 지연 모니터를 쓴다.

```js
// measure.mjs
import { monitorEventLoopDelay } from 'node:perf_hooks'

export function startMonitor () {
  const h = monitorEventLoopDelay({ resolution: 10 })
  h.enable()
  return {
    stop () {
      h.disable()
      return { mean: h.mean / 1e6, max: h.max / 1e6, p99: h.percentile(99) / 1e6 }
    }
  }
}
```

### 전략 1: 동기 실행

```js
import { countSubsets } from './subset-sum.mjs'

app.get('/solve', (req, res) => {
  const count = countSubsets(SET, TARGET)   // 이 줄이 도는 동안 서버는 죽어 있다
  res.json({ count })
})
```

가장 빠르고 가장 위험하다. 계산이 도는 동안 이벤트 루프는 한 틱도 진행하지 못한다. 다른 요청은 큐에 쌓이고, 헬스 체크는 타임아웃되며, 오케스트레이터는 이 인스턴스를 죽은 것으로 판단해 재시작한다(32장 참조). 단일 요청 지연이 아니라 **가용성 사고**가 된다.

### 전략 2: `setImmediate` 인터리빙

계산을 조각으로 쪼개 매 조각 사이에 이벤트 루프에 제어권을 돌려준다.

```js
export async function countSubsetsInterleaved (set, target, chunk = 4096) {
  const n = set.length
  let count = 0
  for (let mask = 0; mask < (1 << n); mask++) {
    let sum = 0
    for (let i = 0; i < n; i++) if (mask & (1 << i)) sum += set[i]
    if (sum === target) count++
    // 일정 주기마다 제어권을 양보한다
    if ((mask & (chunk - 1)) === 0) await new Promise(res => setImmediate(res))
  }
  return count
}
```

이벤트 루프는 살아난다. 그러나 대가가 크다. 조각마다 프로미스 생성, 마이크로태스크 큐 처리, 이벤트 루프 한 바퀴가 추가되므로 총 실행 시간이 크게 늘어난다. `chunk`를 키우면 오버헤드는 줄지만 그만큼 이벤트 루프 지연이 커진다. 무엇보다 **여전히 코어를 하나만 쓴다.** 계산 중 서버의 처리량은 정상 상태의 일부에 불과하다. 이 전략은 "가끔 실행되는 중간 크기 작업"에나 쓸 만하다.

### 전략 3: 외부 프로세스 위임

`fork`로 워커 프로세스를 띄우고 결과만 받는다.

```js
// delegate.mjs
import { fork } from 'node:child_process'

export function solveInProcess (set, target) {
  return new Promise((resolve, reject) => {
    const child = fork(new URL('./proc-worker.mjs', import.meta.url))
    child.send({ set, target })
    child.once('message', msg => { resolve(msg.count); child.disconnect() })
    child.once('error', reject)
    child.once('exit', code => { if (code !== 0) reject(new Error(`exit ${code}`)) })
  })
}
```

메인 이벤트 루프는 거의 완벽하게 깨끗하다. 여러 코어를 동시에 쓸 수도 있다. 비용은 프로세스 기동 시간(수십 ms)과 메모리, 그리고 입출력 데이터의 직렬화다. 데이터가 작고 계산이 길면 훌륭한 선택이다.

### 전략 4: 워커 스레드 풀

미리 만들어 둔 워커 스레드에 작업을 큐잉한다. 기동 비용이 없고 직렬화도 프로세스 IPC보다 싸며, `SharedArrayBuffer`로 대용량 데이터를 복사 없이 다룰 수 있다.

```js
import { WorkerPool } from './pool.mjs'   // 11.7에서 구현한다

const pool = new WorkerPool(new URL('./thread-worker.mjs', import.meta.url), 4)

app.get('/solve', async (req, res) => {
  const count = await pool.run({ set: SET, target: TARGET })
  res.json({ count })
})
```

### 측정 결과

n=24, 목표값 고정, 8코어 장비에서 계산 중 초당 100회의 헬스 체크 요청을 보내며 측정한 값이다(값은 환경에 따라 달라지지만 **상대적 크기**가 요점이다).

| 전략 | 총 실행 시간 | 루프 지연 평균 | 루프 지연 최대 | 계산 중 처리량 | 코어 활용 |
|---|---|---|---|---|---|
| 1. 동기 | 2,050ms | 2,040ms | 2,050ms | 0 req/s | 1 |
| 2. `setImmediate` | 9,700ms | 0.9ms | 14ms | 약 45 req/s | 1 |
| 3. 외부 프로세스 | 2,120ms | 0.4ms | 6ms | 약 98 req/s | 2 |
| 4. 워커 풀(4) | 590ms | 0.3ms | 4ms | 약 99 req/s | 4 |

읽어야 할 것은 세 가지다. **동기 실행은 실행 시간만 보면 최선이지만 처리량을 0으로 만든다.** **인터리빙은 이벤트 루프를 살리는 대신 실행 시간을 4~5배로 늘리고 코어는 여전히 하나만 쓴다.** **워커 풀은 실행 시간과 이벤트 루프 건강을 동시에 얻는다** — 병렬화 가능한 문제라면 4배 가까운 단축까지 가져간다. 다만 워커 수를 코어 수보다 크게 잡으면 컨텍스트 스위칭 때문에 이득이 사라지고 메모리만 늘어난다.

## 11.7 프로덕션에서의 CPU 바운드 작업

### 왜 필요한가

`new Worker()`를 요청마다 호출하는 코드는 부하가 오르는 순간 스레드 수백 개를 만들고 메모리를 소진하며 죽는다. 프로덕션에서 필요한 것은 **고정 크기 풀, 큐잉, 실패한 워커의 자동 재시작, 타임아웃**을 갖춘 구조다.

### 어떻게 동작하는가

```js
// pool.mjs — 고정 크기 워커 풀
import { Worker } from 'node:worker_threads'
import { EventEmitter } from 'node:events'

export class WorkerPool extends EventEmitter {
  #url; #size; #idle = []; #queue = []; #busy = new Map(); #closed = false

  constructor (url, size = 4) {
    super()
    this.#url = url
    this.#size = size
    for (let i = 0; i < size; i++) this.#spawn()
  }

  #spawn () {
    const worker = new Worker(this.#url)

    worker.on('message', result => this.#settle(worker, null, result))
    worker.on('error', err => this.#settle(worker, err))
    worker.on('exit', code => {
      // 진행 중이던 작업이 있으면 실패시키고, 풀 크기를 유지하기 위해 다시 띄운다
      if (this.#busy.has(worker)) {
        this.#settle(worker, new Error(`워커가 코드 ${code}로 종료`))
      }
      this.#idle = this.#idle.filter(w => w !== worker)
      if (!this.#closed) this.#spawn()
    })

    this.#idle.push(worker)
    this.#dispatch()
  }

  #settle (worker, err, result) {
    const task = this.#busy.get(worker)
    if (!task) return
    this.#busy.delete(worker)
    clearTimeout(task.timer)
    err ? task.reject(err) : task.resolve(result)

    // 오류로 끝난 워커는 상태를 신뢰할 수 없으므로 폐기한다
    if (err) worker.terminate().catch(() => {})
    else { this.#idle.push(worker); this.#dispatch() }
  }

  #dispatch () {
    while (this.#idle.length > 0 && this.#queue.length > 0) {
      const worker = this.#idle.pop()
      const task = this.#queue.shift()
      this.#busy.set(worker, task)
      task.timer = setTimeout(() => {
        // 무한 루프에 빠진 워커도 확실히 죽일 수 있다
        worker.terminate().catch(() => {})
      }, task.timeoutMs)
      worker.postMessage(task.payload, task.transferList)
    }
  }

  run (payload, { timeoutMs = 30_000, transferList = [], maxQueue = 1000 } = {}) {
    if (this.#closed) return Promise.reject(new Error('풀이 종료되었다'))
    // 큐가 무한히 자라면 메모리로 죽는다. 빨리 거절하는 편이 낫다
    if (this.#queue.length >= maxQueue) {
      return Promise.reject(Object.assign(new Error('풀 과부하'), { status: 503 }))
    }
    return new Promise((resolve, reject) => {
      this.#queue.push({ payload, transferList, timeoutMs, resolve, reject })
      this.#dispatch()
    })
  }

  async close () {
    this.#closed = true
    const all = [...this.#idle, ...this.#busy.keys()]
    await Promise.all(all.map(w => w.terminate()))
  }
}
```

```js
// thread-worker.mjs — 풀이 재사용하는 워커
import { parentPort } from 'node:worker_threads'
import { countSubsets } from './subset-sum.mjs'

parentPort.on('message', ({ set, target }) => {
  parentPort.postMessage({ count: countSubsets(set, target) })
})
```

이 구현에는 프로덕션에서 반드시 필요한 네 가지가 들어 있다. 워커 수가 고정이므로 **부하가 올라도 자원 사용량이 상한을 넘지 않는다.** 큐에 상한이 있어 **과부하 시 무한 대기 대신 빠르게 503으로 거절한다.** 작업마다 타임아웃이 있어 **폭주한 워커를 강제 종료한다.** `exit` 핸들러가 **죽은 워커를 자동으로 되살린다.**

### 워커 대신 별도 서비스로 분리해야 할 때

워커 풀은 만능이 아니다. 다음 신호 중 둘 이상에 해당하면 CPU 바운드 작업을 별도 서비스로 떼어 내는 것이 옳다.

- **작업 시간이 수 초를 넘는다.** HTTP 요청-응답 주기 안에서 처리할 수 없으므로 작업 큐와 폴링/웹훅 기반의 비동기 API가 필요하다(23장 참조).
- **작업 부하와 요청 부하의 패턴이 다르다.** API 트래픽은 평탄한데 배치 작업이 하루 두 번 몰린다면, 두 축을 독립적으로 스케일링해야 비용이 맞는다.
- **작업이 메모리를 많이 쓴다.** 워커의 힙은 프로세스 힙 상한을 공유하므로 큰 작업 하나가 API 응답 경로까지 OOM으로 끌고 들어간다.
- **JavaScript가 그 작업에 적합하지 않다.** 이미지 처리, 영상 트랜스코딩, 수치 연산은 전용 도구나 다른 언어의 서비스가 훨씬 빠르다.
- **작업이 실패해도 요청은 성공해야 한다.** 내구성 있는 큐에 넣고 재시도하는 편이 안전하다.

경계는 결국 이것이다. **지연 시간이 수십~수백 밀리초이고 요청 경로 안에서 답을 줘야 하면 워커 풀, 그보다 길거나 독립적으로 확장해야 하면 별도 서비스와 큐.**

### 컨테이너 CPU 제한과 워커 수 결정

컨테이너에서 워커 수를 정할 때 가장 흔한 실수는 `os.cpus().length`를 그대로 쓰는 것이다. 이 값은 **호스트의 물리 코어 수**를 반환하며, cgroup의 CPU 할당량(`--cpus=2`)을 반영하지 않는다. 64코어 노드에서 0.5코어만 할당받은 파드가 워커 64개를 만드는 사태가 이렇게 생긴다.

Node.js 18.14 이후에는 `os.availableParallelism()`이 있다. 이 함수는 스케줄러 어피니티까지 고려하므로 `os.cpus().length`보다 낫지만, **cgroup v2의 `cpu.max` 할당량은 여전히 반영하지 못한다.** 따라서 컨테이너에서는 명시적으로 지정하는 것이 유일하게 확실한 방법이다.

```js
import os from 'node:os'
import { readFileSync } from 'node:fs'

function cpuQuota () {
  try {
    // cgroup v2: "<quota> <period>" 또는 "max <period>"
    const [quota, period] = readFileSync('/sys/fs/cgroup/cpu.max', 'utf8').trim().split(' ')
    if (quota !== 'max') return Number(quota) / Number(period)
  } catch { /* cgroup이 없는 환경 */ }
  return os.availableParallelism()
}

// 환경 변수가 있으면 그것을 우선한다. 최소 1개는 보장한다
const poolSize = Number(process.env.WORKER_POOL_SIZE) || Math.max(1, Math.floor(cpuQuota()))
```

여기에 한 가지를 더 계산에 넣어야 한다. **스레드 예산은 워커 스레드만의 것이 아니다.** 하나의 컨테이너 안에서 메인 스레드 1개, libuv 스레드풀 기본 4개, V8 헬퍼 몇 개, 그리고 워커 스레드가 모두 같은 CPU 할당량을 나눠 쓴다. CPU 1.0을 할당받은 컨테이너에서 워커 8개를 띄우면 스레드들이 서로의 타임 슬라이스를 갉아먹으며 전체 레이턴시가 나빠진다. 실용적인 출발점은 다음과 같다.

- 워커 수 = `max(1, floor(CPU 할당량) - 1)` — 메인 스레드용으로 하나를 남긴다
- `UV_THREADPOOL_SIZE`는 파일/압축/암호 사용량에 맞춰 별도로 조정하되, 워커 수와 합쳐서 CPU 할당량의 2~3배를 넘기지 않는다
- CPU 할당량이 1 미만이면 워커를 쓰지 않는다. 프로세스 수준의 수평 확장이 낫다(25장 참조)

마지막으로, 수치를 추측하지 말고 측정한다. 워커 풀 크기, 큐 길이, 작업 대기 시간, 이벤트 루프 지연을 메트릭으로 내보내면(31장 참조) 적정 크기는 부하 테스트 몇 번으로 드러난다.

## 요약

- Node.js는 단일 스레드가 아니다. JavaScript 실행만 단일 스레드이며, libuv 스레드풀(기본 4, `UV_THREADPOOL_SIZE`)이 `fs`·`zlib`·`crypto`·`dns.lookup`을 처리한다. 스레드풀 고갈은 이벤트 루프 지연 없이도 p99 레이턴시를 망가뜨린다.
- 자식 프로세스 생성 함수는 용도가 다르다. 출력이 크면 `spawn`, 짧은 실행 파일 호출은 `execFile`, 또 다른 Node.js 프로세스는 `fork`를 쓴다. `exec`는 셸을 거치므로 사용자 입력이 섞이면 명령 주입 취약점이 된다.
- `fork`가 만드는 IPC 채널은 메시지뿐 아니라 서버 소켓 같은 **핸들**도 전달할 수 있으며, 이것이 `cluster` 모듈의 동작 원리다. `serialization: 'advanced'`는 이진 데이터에서 기본 JSON 모드보다 훨씬 빠르다.
- 워커 스레드는 같은 프로세스에서 돌지만 힙은 분리되어 있다. 전역 변수는 공유되지 않으며, 데이터는 구조화 복제로 복사되거나 `transferList`로 소유권이 이전된다. 생성 비용이 있으므로 만들어 두고 재사용한다.
- 진짜 메모리 공유는 `SharedArrayBuffer`로만 가능하고, 갱신은 반드시 `Atomics`로 한다. `Atomics.wait`는 메인 스레드에서 호출하면 이벤트 루프를 완전히 정지시키므로 `Atomics.waitAsync`를 쓴다.
- CPU 바운드 작업의 네 전략 중, 동기 실행은 처리량을 0으로 만들고 `setImmediate` 인터리빙은 실행 시간을 몇 배로 늘리면서도 코어를 하나만 쓴다. 워커 풀만이 실행 시간과 이벤트 루프 건강을 동시에 얻는다.
- 프로덕션 워커 풀에는 고정 크기, 큐 상한, 작업 타임아웃, 워커 자동 재시작이 모두 필요하다. 컨테이너에서는 `os.cpus().length`가 cgroup 할당량을 반영하지 않으므로 워커 수를 명시적으로 지정한다.

## 연습문제

1. **스레드풀 고갈 진단**: HTTP 서버 하나에 `/hash` 엔드포인트(`crypto.pbkdf2`로 100만 회 반복)와 `/file` 엔드포인트(작은 파일 읽기)를 만든다. `/hash`에 동시 요청 8개를 보내는 동안 `/file`의 응답 시간과 `monitorEventLoopDelay`로 측정한 이벤트 루프 지연을 함께 기록하라. 이벤트 루프 지연은 낮은데 `/file`이 느려지는 이유를 설명하고, `UV_THREADPOOL_SIZE`를 8, 16으로 바꿔 가며 결과가 어떻게 달라지는지 표로 정리하라.

2. **핸들 전달로 만드는 미니 클러스터**: `cluster` 모듈을 쓰지 않고, 부모 프로세스가 `net.Server`를 열어 `fork`한 자식 4개에게 핸들로 넘기는 HTTP 서버를 구현하라. 각 응답에 `process.pid`를 포함시켜 요청이 실제로 분배되는지 확인하고, 자식 하나를 `kill`했을 때 부모가 이를 감지해 새 자식을 띄우고 핸들을 다시 넘기도록 확장하라.

3. **워커 풀 강화**: 11.7의 `WorkerPool`에 다음 세 기능을 추가하라. (a) 큐 대기 시간과 실행 시간을 각각 기록해 `stats()`로 노출한다. (b) 같은 워커가 연속으로 3회 오류로 종료되면 지수 백오프를 적용해 재생성 간격을 늘린다. (c) `SharedArrayBuffer`를 사용해 진행률을 워커가 보고하고 메인 스레드가 `Atomics.load`로 읽는 경로를 추가한다. 완성한 뒤 워커 수를 1, 2, 4, 8로 바꿔 가며 총 처리 시간을 측정하고, 코어 수를 넘어서면 왜 이득이 사라지는지 설명하라.
