# 9장. 크로스 플랫폼 설계 전략

## 9.1 문제의 재정의

앞 장들에서 본 차이를 모아 보면, 두 OS 사이에 코드를 이식할 때 부딪히는 것은 수백 개의 API 이름 차이가 아니다. 이름 차이는 매크로와 래퍼로 하루면 해결된다. 진짜 문제는 **의미 모델이 다른 소수의 지점**이고, 그 지점에서는 한쪽 모델을 기준으로 삼아 다른 쪽을 흉내 내는 결정을 내려야 한다.

그 지점은 다음 여섯 개로 압축된다.

| # | 갈림길 | 리눅스 모델 | Windows 모델 | 해당 장 |
|---|---|---|---|---|
| 1 | 비동기 I/O 알림 | readiness (epoll) | completion (IOCP) | 6 |
| 2 | 프로세스 생성 | fork + exec (상속 후 정리) | CreateProcess (명시 전달) | 4 |
| 3 | 외부 알림/제어 | 시그널 (비동기 가로채기) | 커널 오브젝트 대기 (동기 확인) | 4, 5 |
| 4 | 이질적 대기 | 모든 것을 fd로 → epoll | 모든 오브젝트가 대기 가능 → WaitForMultipleObjects | 2, 5 |
| 5 | 메모리 커밋 | 오버커밋 (실패는 나중, OOM Killer) | 커밋 차지 (실패는 즉시) | 3 |
| 6 | 열린 파일의 이름 | 이름과 내용 분리 (삭제/교체 자유) | 공유 모드 (열려 있으면 거부) | 7 |

이 장은 각 갈림길에서 어떤 기준을 택할지, 추상화 계층을 어디에 둘지, 그리고 기존 크로스 플랫폼 런타임들이 어떤 선택을 했는지를 다룬다.

## 9.2 추상화 계층을 어디에 둘 것인가

크로스 플랫폼 코드의 구조는 크게 세 가지다.

**(a) 소스 레벨 조건 컴파일 (`#ifdef _WIN32`)**

```c
#ifdef _WIN32
    HANDLE h = CreateFileW(wpath, ...);
#else
    int fd = open(path, ...);
#endif
```

가장 단순하고, 작은 유틸리티나 함수 하나짜리 차이에 적합하다. 하지만 코드 전체에 퍼지면 두 OS 로직이 뒤섞여 어느 쪽도 읽기 어려워지고, 타입 자체가 다른 것(`HANDLE` vs `int`)은 감추기 어렵다. 경험 법칙: **`#ifdef`가 함수 본문 안에 들어가면 그 함수를 OS별 파일로 나눌 때다.**

**(b) OS별 구현 파일 + 공통 헤더 (플랫폼 추상화 계층, PAL)**

```
src/
  io/
    file.h            // 공통 인터페이스: pal_file_open, pal_file_read, ...
    file_posix.c      // 리눅스/macOS 구현
    file_win32.c      // Windows 구현
```

빌드 시스템이 OS에 따라 하나만 컴파일한다. 헤더에는 OS 타입이 노출되지 않도록 불투명 핸들(`typedef struct pal_file pal_file_t;`)을 쓴다. SQLite의 VFS, Chromium의 `base/`, .NET 런타임의 PAL, Python의 `posixmodule.c`/`_winapi.c` 등 대규모 프로젝트가 이 구조다. 각 OS 구현이 독립적으로 읽히고, 새 OS 추가가 파일 추가로 끝난다.

핵심 설계 질문은 **인터페이스의 의미를 어느 OS 기준으로 정하는가**다. 인터페이스가 "리눅스 API를 조금 추상화한 것"이면 Windows 구현이 온갖 우회를 하게 되고, 반대도 마찬가지다. 좋은 PAL은 **양쪽에서 자연스럽게 구현 가능한 최소 공통 의미**를 정의한다. 예: "파일을 연다"가 아니라 "파일을 열되, 다른 프로세스의 삭제를 허용한다/허용하지 않는다를 명시한다". 리눅스에서는 후자를 무시하고, Windows에서는 공유 모드로 옮긴다.

**(c) 기존 크로스 플랫폼 라이브러리 채택**

libuv(C), Boost.Asio/Boost.Filesystem(C++), Qt(C++), SDL(게임), APR(Apache), GLib. 또는 언어 런타임 자체(Go, Rust std, .NET, JVM, Node.js, Python)가 PAL 역할을 한다. 대부분의 애플리케이션 코드는 이 층 위에 있으면 되고, 직접 PAL을 짜는 것은 런타임을 만들거나 런타임이 노출하지 않는 OS 기능이 필요할 때만이다.

**권장 조합**: 애플리케이션은 (c) 위에 짓고, 런타임이 감추지 못하는 지점(9.4절)만 (b)로 격리하고, (a)는 한 줄짜리 차이에만 쓴다.

## 9.3 여섯 갈림길의 기준 선택

각 갈림길에서 "어느 모델을 기준으로 삼고 다른 쪽을 흉내 낼 것인가"의 트레이드오프.

**갈림길 1: 비동기 I/O**

- **readiness 기준, Windows에서 흉내**: 0바이트 `WSARecv`를 걸어 두거나 `AFD` 드라이버에 폴을 걸어 "준비됨"을 얻고, 그 다음 동기 `recv`. 장점: 버퍼를 미리 붙이지 않아 연결당 메모리가 작다. 리눅스 코드 구조를 그대로 유지. 단점: Windows에서 시스템 콜이 두 배(폴 + recv), 디스크 파일 비동기 불가, `AFD` 직접 접근은 비공개 인터페이스. Go netpoll, mio(wepoll), 초기 libuv, Nginx Windows 포트가 이 방식.
- **completion 기준, 리눅스에서 흉내**: readiness 통지 후 라이브러리가 `read`를 호출해 사용자 버퍼를 채우고 완료 콜백. 장점: Windows에서 IOCP를 네이티브로 쓰고 디스크 파일도 통일. `async/await`와 자연스럽게 맞음. `io_uring`으로 전환하면 리눅스에서도 네이티브가 된다. 단점: 리눅스에서 연결마다 대기 버퍼를 붙여야 하므로 메모리가 늘고, 리눅스 개발자에게 낯설다. 현재 libuv, Boost.Asio, .NET Sockets, compio, Python `ProactorEventLoop`이 이 방식.
- **판단**: 2020년대에 새로 설계한다면 **completion 기준**이 유리하다. `io_uring`이 리눅스의 미래 방향이고, `async/await`가 주류 언어의 비동기 표현이며, 디스크 I/O까지 한 모델로 다룰 수 있다. readiness 기준은 기존 리눅스 서버를 Windows로 최소 비용으로 가져갈 때의 선택이다.

**갈림길 2: 프로세스 생성**

- **spawn 기준 (CreateProcess/posix_spawn 의미)**: "실행 파일, 인자, 환경, 상속할 핸들 목록, 작업 디렉터리"를 명시적으로 넘기는 API로 통일한다. 리눅스 구현은 `posix_spawn` 또는 `fork` + 즉시 `exec`. 자식이 부모 상태를 상속받는 것에 의존하지 않는다. **거의 모든 크로스 플랫폼 런타임이 이 기준**이다(Go `os/exec`, Rust `Command`, .NET `Process`, Node `child_process`, Python `subprocess`).
- **fork 기준**: Windows에서 구현 불가. Cygwin 수준의 에뮬레이션은 애플리케이션 라이브러리가 할 일이 아니다.
- **판단**: spawn 기준 외에 선택지가 없다. `fork`에 의존하는 설계(프리포크 워커, COW 스냅샷)는 **워커를 스레드로, 스냅샷을 애플리케이션 레벨 COW나 파일 매핑으로** 재설계한다. 워커 프로세스가 꼭 필요하면(격리, 크래시 내성) spawn한 자식에게 상태를 IPC로 넘기고 리스닝 소켓은 핸들 상속/`SCM_RIGHTS`/`WSADuplicateSocket`으로 전달한다.

**갈림길 3: 외부 알림과 제어**

- **오브젝트/이벤트 기준**: "종료 요청", "설정 리로드", "자식 종료" 같은 외부 사건을 모두 **애플리케이션 내부의 이벤트 채널**(큐, 채널, 조건 변수, `eventfd`)로 변환한다. 리눅스 구현은 시그널 핸들러가 `eventfd`에 쓰거나 `signalfd`로 받아 채널에 밀어 넣고, Windows 구현은 콘솔 핸들러/SCM 콜백/이름 있는 이벤트가 같은 채널에 밀어 넣는다. 애플리케이션 로직은 시그널을 모른다.
- **시그널 기준**: Windows에서 `SIGTERM`, `SIGHUP`, `SIGUSR1`을 흉내 낼 수단이 없다. CRT `signal()`은 `SIGINT`만 실질적으로 동작.
- **판단**: 이벤트 채널 기준. 이것은 리눅스에서도 더 좋은 설계다(시그널 핸들러의 async-signal-safe 제약에서 벗어남). 추가로 **"죽이는 쪽" 프로토콜을 정의**해야 한다: 슈퍼바이저가 리눅스에서는 `SIGTERM`, Windows에서는 `GenerateConsoleCtrlEvent(CTRL_BREAK)`(콘솔 프로세스 그룹) 또는 앱이 공개한 이름 있는 이벤트를 시그널한다. Windows 컨테이너에서 `docker stop`은 `CTRL_SHUTDOWN_EVENT`를 보낸다.

**갈림길 4: 이질적 대기**

- **단일 이벤트 루프 기준**: 소켓, 타이머, 자식 종료, 사용자 정의 이벤트를 모두 하나의 다중화기로 모은다. 리눅스는 epoll + `timerfd`/`pidfd`/`eventfd`, Windows는 IOCP + `PostQueuedCompletionStatus` + 타이머 큐/스레드 풀 대기(`RegisterWaitForSingleObject`가 핸들 시그널을 IOCP 패킷으로 변환). 결과적으로 갈림길 1의 선택에 따라 자연히 따라온다.
- **`WaitForMultipleObjects` 기준**: 리눅스에서 뮤텍스/조건 변수를 대기 목록에 넣을 수 없어 흉내가 불완전하고 64개 한계도 있다.
- **판단**: 단일 이벤트 루프(다중화기) 기준. 스레드 간 동기화(뮤텍스, 조건 변수)는 대기 목록에 넣지 않고, 이벤트 루프에 알릴 일이 있으면 `eventfd`/`PostQueuedCompletionStatus`로 "루프를 깨우는" 패턴으로 통일한다.

**갈림길 5: 메모리 커밋**

- **명시적 예약/커밋 기준 (Windows 의미)**: 큰 영역은 "예약"하고 실제 쓸 부분만 "커밋"하는 2단계 API를 PAL에 둔다. Windows는 `VirtualAlloc(MEM_RESERVE/MEM_COMMIT)`, 리눅스는 `mmap(PROT_NONE)` + `mprotect(PROT_READ|PROT_WRITE)` (또는 `MAP_NORESERVE` 후 그냥 접근). 반납은 `VirtualFree(MEM_DECOMMIT)` / `madvise(MADV_DONTNEED)`.
- **암묵적 커밋 기준 (리눅스 의미)**: `malloc`하고 쓴다. Windows에서 커밋 차지 폭발.
- **판단**: 자체 메모리 관리(아레나, GC 힙, 대형 버퍼 풀)를 하는 코드는 명시적 예약/커밋 기준. 이것은 리눅스에서도 `overcommit_memory=2` 환경과 cgroup 한도에서 더 예측 가능하게 동작한다. 일반 애플리케이션 코드는 언어 런타임의 할당자에 맡기고, **할당 실패를 치명 오류로 처리하는 경로 하나**는 반드시 둔다.

**갈림길 6: 열린 파일과 이름**

- **관대한 공유 기준 (리눅스 의미)**: PAL의 파일 열기는 Windows에서 항상 `FILE_SHARE_READ|WRITE|DELETE`를 지정한다. 삭제는 POSIX 삭제 의미(Win10 RS1+)를 시도하고 실패 시 폴백. 이렇게 하면 **자기 프로그램이 연 파일**에 대해서는 리눅스와 같은 동작을 얻는다. 하지만 **다른 프로그램**(백신, 에디터, 탐색기)이 관대하지 않게 연 파일에는 여전히 공유 위반이 난다.
- **엄격한 공유 기준 (Windows 의미)**: 리눅스에서 `flock`으로 흉내(.NET 6+의 `FileShare` 에뮬레이션). 협력 프로세스 사이에서만 유효.
- **판단**: 관대한 공유 기준 + **공유 위반에 대한 짧은 재시도**(수십 ms 간격, 수 초까지) + **실행 파일 자기 교체는 rename 체인**. 로그 로테이션은 "이름 바꾸기" 대신 **"쓰는 쪽이 새 파일을 열도록 신호"**(copytruncate 또는 앱 내부 로테이션)로 설계하면 두 OS에서 같다.

## 9.4 런타임이 감추지 못하는 것

Go, Rust, .NET, JVM, Node.js, Python을 쓰면 위 여섯 갈림길의 대부분이 런타임 안에 숨는다. 그래도 새어 나오는 것이 있다. 앞 장들의 "런타임에서는" 절을 종합하면 다음이 반복된다.

| 새는 지점 | 증상 | 대응 |
|---|---|---|
| `fork` 기반 기능 | Python `multiprocessing` fork 모드, `os.fork`, Node `cluster`의 소켓 공유 방식, Ruby/Perl `fork` | spawn 모드로 통일하고 `__main__` 가드. 상태를 명시적으로 전달 |
| 시그널 API | `process.on('SIGTERM')`, `signal.signal(SIGTERM)`, Go `signal.Notify(SIGTERM)`이 Windows에서 등록은 되지만 발생하지 않음 | 런타임의 크로스 플랫폼 종료 훅(.NET `IHostApplicationLifetime`, Go `os.Interrupt` + Windows 서비스 래퍼, Node `SIGINT`/`SIGBREAK`) 사용. 슈퍼바이저 측 프로토콜 정의 |
| 커맨드라인 이스케이프 | 인자에 따옴표/백슬래시가 있을 때 Windows에서만 깨짐. `shell: true`/`cmd.exe` 경유 시 `^ % & |` | 배열 인자 API만 사용, 셸 경유 금지, 런타임의 이스케이프 신뢰(직접 문자열 조립 금지) |
| 열린 파일 삭제 | 테스트에서 임시 파일 정리 실패(`EBUSY`, `PermissionError`), `NamedTemporaryFile` 이름 공유 실패 | 핸들을 먼저 닫고 삭제. 재시도. `delete_on_close=False`(Python 3.12+) |
| 대소문자와 경로 | `strcmp` 비교, 하드코딩 `/`, 260자 한계, 예약 이름(`aux.js`!) | `path` 모듈, 정규화 후 비교, 긴 경로 매니페스트 |
| 파일 감시 | 이벤트 개수/순서 차이, 재귀 감시 지원 여부 | 디바운스 + 전체 재스캔 폴백 |
| 파일 잠금 의미 | `FileChannel.lock`이 리눅스 권고, Windows 강제 | 협력 프로세스 간에만 의존. 다른 프로세스가 무시할 수 있다고 가정 |
| 스레드 우선순위 | JVM/.NET에서 리눅스는 무시, Windows는 강하게 반영 | 우선순위에 의존하는 설계 회피. 필요하면 OS별 명시 설정 |
| 스택 크기 | Windows 1MB, 재귀 깊이 차이 | 스레드 생성 시 명시, 재귀를 반복으로 |
| 타이머 해상도 | Windows 기본 15.6ms 틱. `sleep(1ms)`가 15ms | 런타임이 고해상도 요청(Go, .NET 6+, Node)하는지 확인. `timeBeginPeriod` 부작용 인지 |
| 콘솔 I/O | Windows 콘솔의 코드 페이지, ANSI 이스케이프(Win10 1511+ VT 지원), stdin 리디렉션 감지 | UTF-8 출력 설정(`chcp 65001`, `SetConsoleOutputCP`), VT 모드 활성화, `isatty` 확인 |
| 이벤트 루프 종류 | Python `ProactorEventLoop`(IOCP) vs `SelectorEventLoop`, `add_reader` 미지원 | 라이브러리가 요구하는 루프 종류 확인. 3.8+ Windows 기본이 Proactor |
| 시스템 프록시/인증서 | 사내망에서 Windows만 TLS 실패 | 런타임 옵션(.NET 기본 지원, Node `--use-system-ca`(22+), Python `truststore`, Go는 Windows 인증서 저장소 자동 사용) |
| `select` 한계 | Windows 64 소켓 | 런타임이 `select`를 쓰는 경로(`socket.select`, 옛 JDK Selector) 회피 |
| 네이티브 확장 빌드 | `node-gyp`, `pip install`이 Windows에서 컴파일러 요구 | 미리 빌드된 바이너리(휠, prebuild) 제공 |

## 9.5 기존 런타임들의 선택 요약

| 런타임 | I/O 모델 기준 | 프로세스 | 종료 알림 | 파일 공유 모드 (Windows) | 특기 사항 |
|---|---|---|---|---|---|
| **libuv (Node.js)** | completion 콜백 API. 리눅스 epoll 위에 흉내, Windows IOCP 네이티브 | spawn. 이스케이프 내장 | `SIGINT`/`SIGBREAK`/`SIGHUP`(콘솔 닫힘)만 Windows 지원 | READ|WRITE|DELETE | 파일 I/O는 두 OS 모두 워커 풀. `uv_pipe_t`가 UNIX 소켓과 Named Pipe 통일 |
| **Go** | readiness 기준. Windows IOCP 완료를 준비됨으로 변환 | spawn (`clone(VFORK)` / `CreateProcess`) | `os.Interrupt`만. 서비스는 `x/sys/windows/svc` | READ|WRITE|DELETE | cgo 없이 syscall 직접. 크로스 컴파일 용이. 고루틴이 스레드 차이 대부분 은폐 |
| **Rust std + Tokio/mio** | readiness (mio, Windows는 AFD 폴). completion 대안: tokio-uring, compio | spawn. `Command` 이스케이프 | `ctrlc`, `signal-hook`(유닉스), `windows-service` 크레이트 | READ|WRITE|DELETE | `OsString`으로 비UTF-8 경로 타입 강제. MSVC/GNU 두 타깃 |
| **.NET** | completion 기준. Windows IOCP 네이티브, 리눅스 epoll 위에 흉내 | spawn. `ArgumentList` 권장 | `IHostApplicationLifetime`, `Console.CancelKeyPress`, `AppDomain.ProcessExit` | 기본 `FileShare.Read` (Windows 관습). 리눅스에서 `flock` 에뮬레이션 | `SafeHandle`로 fd/HANDLE 통일. Windows 서비스 호스팅 내장 |
| **JVM** | NIO `Selector`는 readiness(epoll/wepoll). `Asynchronous*Channel`은 completion(IOCP/스레드 풀) | spawn. `ProcessBuilder` | `Runtime.addShutdownHook` (리눅스 SIGTERM, Windows 콘솔/로그오프) | READ|WRITE (DELETE는 `ExtendedOpenOption.NOSHARE_*`로 반대 방향 제어) | 가상 스레드로 스레드 차이 은폐. 우선순위 리눅스 무시 |
| **Python** | asyncio: 리눅스 Selector(epoll), Windows Proactor(IOCP). 기능 차이 있음 | spawn(`subprocess`). `multiprocessing`은 OS별 기본 다름 | `signal`은 Windows에서 `SIGINT`/`SIGBREAK` 실질 지원 | CRT 기본 (`FILE_SHARE_READ`만). `os.open`은 READ|WRITE | `os.fork` 부재가 가장 큰 차이. `pathlib`이 경로 은폐 |
| **Boost.Asio (C++)** | completion (Proactor). 리눅스 epoll/io_uring, Windows IOCP | `boost::process` 별도 | `signal_set` (Windows는 CRT signal 수준) | 사용자 지정 | C++ 비동기의 사실상 표준. Networking TS의 기반 |
| **SDL / Qt** | 이벤트 루프 (GUI 중심), 네트워크는 Qt `QAbstractSocket`이 readiness 스타일 | `QProcess` spawn | 이벤트 루프 통합 | 사용자 지정 | GUI 앱의 전통적 PAL |

두 개의 패턴이 보인다. **시스템 프로그래밍에 가까운 런타임(Go, Rust/mio)은 readiness를 기준**으로 삼아 리눅스 성능과 단순성을 지켰고, **애플리케이션 프레임워크에 가까운 런타임(.NET, libuv, Asio)은 completion을 기준**으로 삼아 `async/await`와 디스크 I/O 통합을 얻었다. 둘 다 성공한 선택이며, 어느 쪽이 맞는지는 "누가 이 런타임 위에 무엇을 짓는가"에 달렸다.

## 9.6 테스트 전략

크로스 플랫폼 코드는 **두 OS에서 CI를 돌리지 않으면 반드시 깨진다.** 경험적으로 다음이 두 OS에서 다르게 동작하는 테스트의 주요 원인이다.

1. **임시 파일 정리**: 테스트가 파일을 열어 둔 채 삭제. Windows에서 실패. 픽스처에서 핸들을 먼저 닫는다.
2. **경로 비교**: `assert path == "/tmp/x"`. 구분자, 대소문자, 8.3 짧은 이름(`C:\PROGRA~1`), 심볼릭 링크 해석(`%TEMP%`가 짧은 이름으로 오는 경우). `realpath`/`GetFinalPathNameByHandle`로 정규화 후 비교.
3. **줄 끝**: 텍스트 파일 비교에서 `\r\n`. 바이너리 모드로 열거나 정규화.
4. **시각 해상도와 타임스탬프**: mtime 비교, FAT32 2초, NTFS 100ns vs ext4 ns. `sleep` 기반 테스트는 Windows 15.6ms 틱.
5. **포트 재사용**: 테스트 서버를 빠르게 재시작할 때 리눅스 `SO_REUSEADDR` 필요, Windows 불필요/위험.
6. **프로세스 종료**: `SIGTERM` 보내는 테스트. Windows에서 `TerminateProcess`가 되어 정리 로직이 실행되지 않음.
7. **동시성 타이밍**: 스케줄러 차이로 경합 조건이 한쪽에서만 드러남. TSan은 리눅스에서만.
8. **파일 권한 테스트**: `chmod 000` 후 읽기 실패 기대. Windows에서 읽기 전용 속성만 바뀌어 읽기는 성공.
9. **환경 변수 대소문자**: `os.environ["path"]` vs `PATH`. Windows는 무시, 리눅스는 구분.
10. **홈 디렉터리와 XDG 경로**: `~/.config/app` vs `%APPDATA%\App`. 테스트가 경로를 하드코딩.
11. **대소문자 충돌**: 테스트 픽스처에 `Readme.md`와 `README.md`가 함께 있으면 Windows에서 체크아웃 실패.
12. **예약 파일 이름**: `aux`, `con`, `nul`, `com1` 같은 이름의 테스트 파일이나 모듈(`aux.js`가 실제로 npm 패키지를 깨뜨린 사례).

**CI 구성**: GitHub Actions의 `runs-on: [ubuntu-latest, windows-latest]` 매트릭스가 최소. Windows 러너는 느리고(파일 I/O, Defender), 셸이 PowerShell이므로 스크립트를 두 벌 두거나 `shell: bash`(Git Bash)를 명시한다. Windows 컨테이너나 Windows Server Core 러너도 있지만 클라이언트 SKU와 다르게 동작하는 것(콘솔, 세션 0)이 있다.

## 9.7 WSL, Cygwin, MinGW, 그리고 "Windows에서 리눅스처럼"

Windows에서 리눅스 코드를 돌리는 계층들은 각기 다른 지점에서 번역한다.

| 계층 | 번역 지점 | fork | 시그널 | 파일 시스템 | 성능 | 용도 |
|---|---|---|---|---|---|---|
| **WSL2** | 진짜 리눅스 커널 (경량 VM) | 네이티브 | 네이티브 | ext4 (VM 내), Windows 파일은 9P로 느림 | 리눅스 네이티브 (VM 경계 I/O 제외) | 개발 환경, 리눅스 서버 코드 실행 |
| **WSL1** | 시스템 콜 (NT 커널이 리눅스 ABI 구현) | 에뮬레이션 (느림) | 에뮬레이션 | NTFS 직접 (Windows 파일 접근 빠름) | fork/파일 I/O 느림 | 폐기 방향 |
| **Cygwin** | libc (POSIX API를 Win32로 구현하는 `cygwin1.dll`) | 에뮬레이션 (매우 느림, 불안정) | 에뮬레이션 | Windows 경로를 `/cygdrive/c`로 매핑 | Win32 네이티브 수준 (fork 제외) | POSIX 도구 이식 (bash, git 초기) |
| **MSYS2** | Cygwin 포크 + 경로 변환 | Cygwin과 같음 | Cygwin과 같음 | 인자의 POSIX 경로를 Windows 경로로 자동 변환 | Cygwin과 같음 | MinGW 툴체인 호스팅 (Git for Windows) |
| **MinGW-w64** | 없음 (gcc가 Win32 네이티브 코드 생성, MS CRT 사용) | 없음 | CRT 수준만 | Windows 네이티브 | 네이티브 | gcc로 Win32 프로그램 빌드. POSIX 에뮬레이션 없음 |
| **Git Bash** | MSYS2 기반 bash | (bash 자체는 fork 사용) | | | | Windows에서 bash 스크립트 실행 |

혼동이 잦은 지점: **MinGW로 빌드한 프로그램은 Windows 프로그램**이다. `fork`, `pthread`(winpthreads가 pthread API를 Win32 스레드로 구현하지만 `fork`는 없음), `epoll`이 없다. Cygwin으로 빌드한 프로그램은 `cygwin1.dll`에 의존하는 "Cygwin 프로그램"이고 POSIX API 대부분이 동작하지만 순수 Windows 환경에 배포하려면 DLL을 함께 줘야 한다. WSL2 프로그램은 리눅스 프로그램이고 Windows 프로세스가 아니다(`ps`로 안 보이고 Windows API를 호출할 수 없다. 단 `interop`으로 `.exe`를 실행할 수는 있다).

**개발 환경으로서의 WSL2**: 리눅스 서버 코드를 Windows 노트북에서 개발하는 표준 방법이 되었다. 주의점은 파일 위치다. 프로젝트를 Windows 파일 시스템(`/mnt/c/...`)에 두면 9P 프로토콜 경유로 `git status`, `npm install`이 수 배 느리고, inotify가 동작하지 않는다. WSL 파일 시스템(`~/projects`)에 두고 Windows 쪽에서는 `\\wsl$\`로 접근한다. VS Code Remote-WSL이 이 구조를 전제한다.

**반대 방향**: 리눅스에서 Windows 프로그램을 돌리는 Wine은 Win32 API를 리눅스 위에 구현한 계층(Cygwin의 거울상)이고, Proton(Steam)이 게임용으로 확장했다. 개발 관점에서는 Windows 바이너리를 리눅스 CI에서 테스트할 때 쓸 수 있지만 완전하지 않다.

## 9.8 설계 체크리스트: 새 프로젝트를 시작할 때

1. **런타임 선택**이 첫 결정이다. 런타임이 여섯 갈림길 중 몇 개를 어떻게 감추는지 9.5절 표로 확인한다. 네이티브 C/C++라면 libuv 또는 Asio 채택 여부를 결정한다.
2. **I/O 모델 기준**을 정한다. 새 코드면 completion, 기존 리눅스 서버 이식이면 readiness. 어느 쪽이든 직접 epoll/IOCP를 다루는 코드는 PAL 파일 하나에 격리한다.
3. **프로세스 모델**에서 `fork` 의존을 제거한다. 워커는 스레드 또는 spawn.
4. **종료 프로토콜**을 정의한다. 앱이 받는 방법과 슈퍼바이저가 보내는 방법을 두 OS 각각 문서화한다.
5. **파일 열기 정책**: Windows 공유 모드 기본값과 공유 위반 재시도 정책을 PAL에 박는다.
6. **메모리 정책**: 대형 버퍼/아레나는 예약-커밋 2단계. 할당 실패 경로 하나.
7. **문자열과 경로**: 내부는 UTF-8, Windows API 경계에서 UTF-16 변환. 경로 비교는 정규화 후. 260자 한계 매니페스트.
8. **빌드**: 두 컴파일러, 두 OS CI. 고정 폭 정수. 심볼 export 매크로. CRT 옵션 통일.
9. **관측**: 두 OS의 크래시 덤프 수집과 심볼 보관. 프로파일링 절차.
10. **배포**: 서비스 등록(systemd 유닛 + Windows 서비스 래퍼), 런타임 의존(glibc 버전, VC++ 재배포), 코드 서명.
