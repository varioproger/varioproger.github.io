# 1장. 시작하며: 왜 비교해서 배워야 하는가

## 1.1 같은 코드, 다른 결과

다음은 실무에서 실제로 반복되는 장면들이다.

- 리눅스에서 잘 돌던 Python `multiprocessing` 코드를 Windows에서 실행했더니 `if __name__ == "__main__":`이 없다는 이유로 프로세스가 무한 증식한다.
- 리눅스에서는 `malloc(64GB)`가 성공하고 나중에 OOM killer에 죽는데, Windows에서는 같은 호출이 즉시 `NULL`을 반환한다.
- 로그 로테이션 스크립트가 리눅스에서는 열린 파일을 `rename`으로 잘 돌리는데, Windows에서는 "다른 프로세스가 사용 중"이라며 실패한다.
- Node.js 서버가 리눅스에서는 `epoll`로, Windows에서는 IOCP로 돌아서 같은 코드인데 성능 특성이 다르게 나온다.
- 리눅스 데몬은 `SIGTERM`을 받아 정리하고 죽지만, Windows 서비스는 시그널이 없어서 `SERVICE_CONTROL_STOP`을 따로 처리해야 한다.
- 리눅스에서 `/tmp/a.txt`와 `/tmp/A.txt`는 다른 파일인데, Windows에서는 같은 파일이라 테스트가 깨진다.

이 문제들의 공통점은 **언어나 라이브러리의 버그가 아니다**라는 점이다. 두 OS가 프로세스, 메모리, 파일, I/O를 서로 다른 세계관으로 설계했고, 그 차이가 런타임을 뚫고 올라와 내 코드에 도달한 것이다.

## 1.2 한쪽만 알면 생기는 착각

한 OS만 오래 쓰면 그 OS의 방식이 "OS의 당연한 동작"이라고 믿게 된다.

리눅스만 쓴 개발자는 이렇게 믿는다.

- 프로세스는 당연히 `fork`로 복제해서 만든다.
- 소켓은 당연히 파일 디스크립터다. `read`/`write`/`close`가 통한다.
- 프로세스에 무언가를 알리려면 당연히 시그널을 보낸다.
- 파일이 열려 있어도 당연히 지울 수 있다.
- 메모리는 당연히 요청하면 성공하고, 실제 할당은 나중에 일어난다.

Windows만 쓴 개발자는 반대로 이렇게 믿는다.

- 프로세스는 당연히 실행 파일 경로를 주고 한 번에 만든다.
- 뮤텍스, 이벤트, 프로세스, 파일을 당연히 한 함수(`WaitForMultipleObjects`)로 동시에 기다릴 수 있다.
- 비동기 I/O는 당연히 "요청해 놓고 완료 통지를 받는" 것이다.
- 파일을 열 때 당연히 다른 프로세스가 지우거나 쓸 수 있는지 공유 모드로 지정한다.
- 메모리 커밋이 실패할 수 있으니 당연히 반환값을 확인한다.

둘 다 자기 OS 안에서는 옳다. 문제는 이 "당연함"이 다른 OS에서는 성립하지 않는다는 것이고, 더 큰 문제는 **어느 것이 당연함이고 어느 것이 보편 원리인지 구분하지 못한다**는 것이다. 비교해서 배우는 이유가 여기 있다. 두 OS를 나란히 놓으면 "OS라면 반드시 해야 하는 일"(가상 메모리, 스케줄링, 격리)과 "그 OS가 선택한 방식"(fork, 시그널, 핸들)이 분리되어 보인다.

## 1.3 네 개의 갈림길

이 책 전체를 관통하는 차이는 크게 네 가지다. 각 장은 이 네 갈림길이 해당 주제에서 어떻게 드러나는지를 다룬다.

**갈림길 1: 자원을 무엇으로 추상화하는가**

리눅스는 "모든 것은 파일"이다. 파일, 소켓, 파이프, 디바이스, 심지어 타이머(`timerfd`)와 시그널(`signalfd`)까지 정수 하나(파일 디스크립터)로 다룬다. 같은 `read`, `write`, `close`, `poll`이 전부에 통한다.

Windows는 "모든 것은 오브젝트"다. 파일, 이벤트, 뮤텍스, 프로세스, 스레드, 세마포어가 각각 커널 오브젝트이고, 핸들(`HANDLE`)로 참조한다. 오브젝트마다 전용 API가 있지만, 모두 "시그널 상태"라는 공통 속성을 가져서 한 함수로 동시에 기다릴 수 있다.

**갈림길 2: 비동기 알림을 어떻게 전달하는가**

리눅스는 readiness(준비됨) 모델이다. 커널이 "이 fd는 지금 읽을 수 있다"고 알려주고, 실제 읽기는 내가 한다. `select`, `poll`, `epoll`이 모두 이 모델이다.

Windows는 completion(완료) 모델이다. "이 버퍼에 읽어 달라"고 요청을 던져 놓으면 커널이 나중에 "끝났다"고 알려준다. Overlapped I/O와 IOCP가 이 모델이다.

이 차이는 네트워크 서버의 구조를 근본부터 바꾼다. 최근 리눅스의 `io_uring`이 completion 모델을 들여오면서 두 진영이 가까워지고 있지만, 기존 코드 대부분은 여전히 갈라져 있다.

**갈림길 3: 프로세스를 어떻게 만들고 제어하는가**

리눅스는 `fork`로 자기 자신을 복제한 뒤 `exec`로 다른 프로그램으로 바꿔 끼운다. 부모-자식 관계가 엄격하고, 프로세스 제어는 시그널로 한다.

Windows는 `CreateProcess`로 실행 파일을 지정해 한 번에 만든다. 복제 개념이 없고, 부모-자식 관계가 느슨하며, 시그널 대신 커널 오브젝트와 메시지로 제어한다.

**갈림길 4: 안정된 경계가 어디인가**

리눅스는 커널 시스템 콜 자체가 안정된 공개 인터페이스다. libc를 쓰지 않고 어셈블리로 직접 `syscall` 명령을 호출해도 동작이 보장된다.

Windows는 시스템 콜이 비공개이고 빌드마다 바뀐다. 안정된 경계는 `kernel32.dll`, `ntdll.dll` 같은 사용자 모드 DLL이 노출하는 Win32 API다. 이 차이 때문에 정적 링크, 컨테이너, 하위 호환 정책이 완전히 달라진다.

## 1.4 이 책의 관점: "왜 그렇게 만들었는가"

차이를 외우는 것은 의미가 없다. 각 차이 뒤에는 설계 당시의 목표와 제약이 있다.

- 리눅스(그리고 UNIX)는 1970년대 시분할 미니컴퓨터에서 출발했다. 단순한 인터페이스, 텍스트 파이프라인, 소스 호환성이 최우선이었다. `fork`는 주소 공간이 작고 프로세스 생성이 잦은 환경에서 자연스러운 선택이었다.
- Windows NT는 1990년대 초 데이비드 커틀러가 VMS 경험을 바탕으로 설계했다. 목표는 여러 API 서브시스템(Win32, POSIX, OS/2)을 하나의 커널 위에 올리는 것, 바이너리 하위 호환, 오브젝트 기반 보안 모델이었다. 그래서 커널은 특정 API에 종속되지 않는 중립적 오브젝트 관리자로 만들어졌고, `fork`처럼 UNIX 고유 의미가 강한 기능은 배제되었다.

이 배경을 알면 "Windows에 fork가 없는 것은 결함"이 아니라 "다른 목표를 위한 다른 선택"임이 보이고, 그 선택이 어디까지 영향을 미치는지 예측할 수 있게 된다.

## 1.5 각 장의 구성

3장부터 7장까지는 같은 뼈대를 따른다.

1. **개념 정의**: OS라면 반드시 해결해야 하는 문제가 무엇인가
2. **리눅스 방식**: 어떤 API와 커널 구조로 해결하는가
3. **Windows 방식**: 같은 문제를 어떻게 다르게 해결하는가
4. **왜 다른가**: 설계 배경과 트레이드오프
5. **이식할 때 부딪히는 문제**: 실제 코드가 깨지는 지점과 해결 패턴
6. **런타임에서는**: Go, Rust, .NET, Node.js, Python, JVM이 이 차이를 어떻게 감추거나 노출하는가
7. **실전 체크리스트**

8장은 툴체인과 ABI, 9장은 크로스 플랫폼 코드를 설계하는 전략, 10장은 전체를 한 장으로 압축한 표다.
