# 8장. 개발 환경: 툴체인, ABI, 디버깅

## 8.1 이 장의 범위

앞 장들은 커널이 제공하는 것의 차이를 다뤘다. 이 장은 그 위에서 코드를 컴파일하고, 링크하고, 실행하고, 고치는 도구의 차이를 다룬다. 커널 차이만큼 근본적이지는 않지만, 하루 종일 마주치는 것은 오히려 이쪽이다.

## 8.2 컴파일러와 빌드 도구

| 항목 | 리눅스 | Windows |
|---|---|---|
| 기본 C/C++ 컴파일러 | gcc, clang | MSVC (`cl.exe`), clang-cl(MSVC 호환 clang), MinGW-w64 gcc |
| 링커 | GNU ld, gold, lld, mold | `link.exe`, lld-link |
| 표준 라이브러리 | glibc (또는 musl), libstdc++ (또는 libc++) | UCRT(Universal CRT, Win10+) + vcruntime + MSVC STL |
| 빌드 시스템 | Make, CMake, Meson, Ninja, autotools | MSBuild (`.sln`/`.vcxproj`), CMake, Ninja |
| 패키지 관리 | 시스템 패키지(apt, dnf, pacman) 또는 vcpkg/Conan | vcpkg, Conan, NuGet(C++ 패키지는 소수) |
| 헤더/라이브러리 위치 | `/usr/include`, `/usr/lib`, `pkg-config`로 탐색 | Windows SDK(`C:\Program Files (x86)\Windows Kits\10\`), Visual Studio 설치 경로. 환경 변수 `INCLUDE`, `LIB`를 `vcvarsall.bat`가 설정 |
| 컴파일러 호출 환경 | 셸에서 그냥 `gcc` | "개발자 명령 프롬프트" 또는 `vcvarsall.bat x64` 실행 후. 아키텍처별로 다른 환경 |
| 디버그 정보 | DWARF, 실행 파일에 내장 (`-g`), 분리는 `objcopy --only-keep-debug` | PDB 파일 분리 (`/Zi`, `/DEBUG`). 실행 파일에는 PDB 경로와 GUID만 |
| 최적화 플래그 | `-O2`, `-O3`, `-march=native`, `-flto` | `/O2`, `/Ox`, `/arch:AVX2`, `/GL` + `/LTCG` |
| 경고 | `-Wall -Wextra -Werror` | `/W4 /WX`. 경고 번호 체계(C4996 등) |
| 정의 | `-DFOO=1` | `/DFOO=1` |
| 위치 독립 코드 | `-fPIC` (`.so` 필수), `-fPIE` (기본) | 불필요 (PE 재배치 테이블) |
| 런타임 링크 방식 | 기본 동적 (libc.so), `-static`으로 정적 | `/MD`(동적 CRT DLL), `/MT`(정적 CRT). **모든 모듈이 같아야 함** |
| 디버그/릴리스 런타임 | 같은 libc | `/MDd`, `/MTd` 별도 디버그 CRT. 디버그와 릴리스 모듈 혼용 불가 |
| 컴파일러 확장 | `__attribute__((...))`, `__builtin_*`, 문장식(statement expression), 가변 길이 배열 | `__declspec(...)`, `__forceinline`, `__int64`, `#pragma comment(lib, ...)`, SEH `__try` |
| 인라인 어셈블리 | AT&T 문법 `asm()`, x86/ARM 모두 | 64비트에서 인라인 어셈블리 **불가**. 별도 `.asm` 파일(MASM) 또는 intrinsic |
| 심볼 가시성 기본 | 공개 | 비공개 |

**`/MD`와 `/MT`, 그리고 CRT 혼용 문제**: MSVC에서 CRT를 정적 링크(`/MT`)한 두 DLL은 각각 자기 힙, 자기 `errno`, 자기 `FILE*` 테이블, 자기 로캘을 가진다. A.dll이 `malloc`한 것을 B.dll이 `free`하면 다른 힙이라 크래시. A가 만든 `FILE*`를 B가 `fclose`하면 다른 테이블이라 크래시. 동적 CRT(`/MD`)를 쓰면 프로세스 안의 모든 모듈이 하나의 `ucrtbase.dll`을 공유해 이 문제가 없지만, VS 버전별 `vcruntime140.dll` 재배포가 필요하다. 리눅스는 항상 `libc.so.6` 하나라 이 문제가 없다(정적 링크한 `.so`는 극히 드물다).

**Windows SDK 버전과 `_WIN32_WINNT`**: Windows 헤더는 `_WIN32_WINNT` 매크로(예: `0x0A00` = Windows 10)로 어느 버전의 API까지 노출할지 정한다. 낮게 설정하면 새 API가 컴파일되지 않고, 높게 설정하면 오래된 Windows에서 로드 실패(`GetProcAddress`로 런타임 탐지해야). 리눅스에서는 glibc 심볼 버전이 이 역할을 하는데, 컴파일한 glibc보다 오래된 시스템에서 `GLIBC_2.34 not found`로 실패한다. 두 OS 모두 "오래된 환경에서 빌드하면 새 환경에서도 돈다"가 원칙이다(리눅스는 manylinux 컨테이너, Windows는 낮은 `_WIN32_WINNT`).

## 8.3 ABI: 호출 규약, 이름 맹글링, 예외

같은 x86-64 CPU지만 **ABI가 다르다**. 리눅스는 System V AMD64 ABI, Windows는 Microsoft x64 ABI. 그래서 컴파일된 오브젝트 파일은 서로 호환되지 않고, 어셈블리 코드는 두 벌이 필요하다.

**x86-64 호출 규약**

| 항목 | System V (리눅스) | Microsoft x64 (Windows) |
|---|---|---|
| 정수/포인터 인자 레지스터 | `rdi, rsi, rdx, rcx, r8, r9` (6개) | `rcx, rdx, r8, r9` (4개) |
| 부동소수점 인자 | `xmm0~xmm7` (8개), 정수와 별도 카운트 | `xmm0~xmm3` (4개), **정수와 같은 슬롯 공유** (`f(int, double)`은 `rcx`, `xmm1`) |
| 그 이후 인자 | 스택 | 스택 |
| 섀도 스페이스 | 없음 | 호출자가 32바이트(4 레지스터 분) 스택 공간을 **항상** 예약 |
| 반환 | `rax`(+`rdx`), `xmm0`(+`xmm1`) | `rax`, `xmm0` |
| 호출자 보존(volatile) | `rax, rcx, rdx, rsi, rdi, r8~r11, xmm0~15` | `rax, rcx, rdx, r8~r11, xmm0~5` |
| 피호출자 보존 | `rbx, rbp, r12~r15` | `rbx, rbp, rdi, rsi, r12~r15, xmm6~15` |
| 레드 존 | `rsp` 아래 128바이트를 리프 함수가 자유 사용 | 없음 |
| 구조체 전달 | 16바이트 이하는 레지스터에 분해(분류 알고리즘 복잡) | 1, 2, 4, 8바이트만 레지스터. 그 외 포인터로 |
| 가변 인자 | `al`에 벡터 레지스터 수 | 부동소수점 인자를 정수 레지스터에도 복제 |
| 스택 정렬 | 호출 시 16바이트 | 호출 시 16바이트 |
| 언와인드 정보 | `.eh_frame` (DWARF CFI) | `.pdata`/`.xdata` (컴파일러가 생성, 모든 비리프 함수가 프롤로그 규칙 준수 필수) |

Microsoft ABI는 인자 레지스터가 4개라 인자가 많은 함수는 리눅스보다 스택을 더 쓴다. 대신 섀도 스페이스와 엄격한 프롤로그 규칙 덕분에 **스택 워킹이 디버그 정보 없이도 항상 가능**하다(`RtlVirtualUnwind`). 이것이 Windows에서 크래시 덤프의 스택 추적이 릴리스 빌드에서도 잘 나오는 이유고, SEH가 프레임 포인터 없이 동작하는 기반이다. 리눅스는 `-fomit-frame-pointer`(x86-64 기본)에서 `.eh_frame`이 없으면 스택 추적이 깨진다(최근 배포판이 프레임 포인터를 다시 켜는 추세인 이유).

**ARM64**: 두 OS 모두 AAPCS64를 기반으로 하고 차이가 작다. Windows on ARM64는 `x18`을 TEB 포인터로 예약하는 등 소소한 차이만 있다.

**32비트 x86**: 리눅스는 `cdecl` 하나. Windows는 `__cdecl`(기본), `__stdcall`(Win32 API 전체, 피호출자가 스택 정리), `__fastcall`, `__thiscall`(C++ 멤버), `__vectorcall`. 32비트 Windows 코드에는 `WINAPI`(= `__stdcall`) 매크로가 붙어 있다. 64비트에서는 모두 무시되고 하나로 통일되었다.

**C++ 이름 맹글링**

| | Itanium C++ ABI (gcc, clang 리눅스) | MSVC ABI |
|---|---|---|
| `void foo(int, double)` | `_Z3fooid` | `?foo@@YAXHN@Z` |
| 문서화 | 공개 표준 | 비공개(리버스 엔지니어링으로 알려짐) |
| 복호화 도구 | `c++filt`, `__cxa_demangle` | `undname.exe`, `UnDecorateSymbolName` |
| 컴파일러 간 호환 | gcc ↔ clang 호환 | MSVC ↔ clang-cl 호환. MinGW gcc는 Itanium이라 MSVC와 **비호환** |

맹글링뿐 아니라 **클래스 레이아웃**(가상 함수 테이블 위치, 다중 상속 조정자, 빈 기반 클래스 최적화 규칙), **예외 처리**, **RTTI 형식**, **표준 라이브러리 구현**(`std::string`의 내부 구조)이 모두 다르다. 그래서 C++ 라이브러리는 **컴파일러와 버전과 런타임 종류(`/MD`, `/MDd`)가 완전히 같은 조합**으로만 링크할 수 있다. Windows에서 C++ DLL을 배포할 때 MSVC 버전별로 빌드를 따로 제공하거나, DLL 경계를 C API로 만드는 이유다. 리눅스는 gcc가 사실상 표준이고 libstdc++가 ABI 안정성(dual ABI 사건인 `_GLIBCXX_USE_CXX11_ABI` 제외)을 지켜 온 덕분에 이 문제가 훨씬 덜하다.

**예외 처리**

- 리눅스(Itanium ABI): 제로 코스트 모델. `.eh_frame`과 `.gcc_except_table`에 언와인드 정보와 랜딩 패드를 두고, `throw` 시 `_Unwind_RaiseException`이 두 단계(검색, 정리)로 스택을 푼다. 예외가 없으면 실행 비용 0. C 코드를 거쳐 예외가 통과하려면 C도 `-fexceptions`로 컴파일해야 한다.
- Windows x64(SEH 기반): C++ 예외는 SEH 위에 구현된다(`RaiseException`으로 `0xE06D7363` 코드). `.pdata`/`.xdata`로 언와인드하고 각 함수의 `__C_specific_handler` 또는 `__CxxFrameHandler`가 스코프 테이블을 보고 처리. 역시 제로 코스트에 가깝다(32비트 x86은 프레임 기반이라 비용이 있었다). **하드웨어 예외(액세스 위반, 0 나누기)와 C++ 예외가 같은 메커니즘**이다. `/EHa`로 컴파일하면 `catch(...)`가 액세스 위반까지 잡는다(권장하지 않음). `__try/__except/__finally`는 C에서도 쓸 수 있다.
- 리눅스에서 세그폴트는 시그널이고 C++ 예외와 무관하다. 스택 언와인딩을 시그널 핸들러에서 하는 것은 정의되지 않은 동작에 가깝다.

**결과**: 두 OS 사이에 바이너리 호환은 원래 없지만, **같은 OS 안에서도** Windows는 컴파일러 조합 제약이 훨씬 강하다. C ABI만이 안전한 경계다.

## 8.4 동적 링킹 실무

4.6절에서 ELF와 PE의 구조 차이를 다뤘다. 여기서는 개발 흐름에서 마주치는 차이만 보충한다.

**임포트 라이브러리**: Windows에서 DLL을 링크하려면 `.dll` 자체가 아니라 `.lib`(임포트 라이브러리)를 링커에 준다. `.lib`는 "이 심볼은 foo.dll에 있다"는 스텁 모음이다. 같은 확장자 `.lib`가 정적 라이브러리에도 쓰여 혼란스럽다. 리눅스는 `.so`를 링커에 직접 준다(`-lfoo`가 `libfoo.so`를 찾음).

**심볼 내보내기 매크로 관용구**:

```c
#if defined(_WIN32)
  #ifdef MYLIB_BUILDING
    #define MYLIB_API __declspec(dllexport)
  #else
    #define MYLIB_API __declspec(dllimport)
  #endif
#else
  #define MYLIB_API __attribute__((visibility("default")))
#endif
MYLIB_API int mylib_init(void);
```

거의 모든 크로스 플랫폼 C/C++ 라이브러리에 이 패턴이 있다. CMake의 `GenerateExportHeader`가 자동 생성한다.

**데이터 심볼 내보내기**: 함수는 위 매크로로 충분하지만 전역 변수는 Windows에서 `dllimport` 없이 참조하면 링크 오류 또는 잘못된 주소를 읽는다. 라이브러리 경계에서 전역 변수를 노출하지 않는 것이 최선이다.

**런타임 로딩**: `dlopen`/`dlsym` ↔ `LoadLibraryW`/`GetProcAddress`. `dlsym(RTLD_DEFAULT, "name")`(어느 라이브러리든 찾기)에 해당하는 것이 Windows에 없다. 모듈을 지정해야 한다. `dladdr`(주소 → 심볼) ↔ `SymFromAddr`(DbgHelp, PDB 필요).

**의존성 확인**: `ldd a.out`, `readelf -d`, `objdump -p` ↔ `dumpbin /dependents`, `dumpbin /imports`, Dependencies(오픈소스 GUI). 로더 문제 디버깅: `LD_DEBUG=libs` ↔ `gflags +sls`(로더 스냅) 또는 Process Monitor로 어느 경로에서 DLL을 찾다 실패했는지 관찰.

**버전 충돌 양상**: 리눅스는 전역 네임스페이스라 두 라이브러리가 서로 다른 버전의 OpenSSL을 요구하면 심볼이 충돌한다(심볼 버전과 `RTLD_LOCAL`/`-Bsymbolic`으로 완화). Windows는 모듈별 네임스페이스라 `libssl-1_1.dll`과 `libssl-3.dll`이 한 프로세스에 공존한다. 대신 같은 이름의 DLL이 검색 경로에 여러 버전 있을 때 어느 것이 로드되는지가 문제다(DLL 지옥, SxS로 완화).

## 8.5 디버거

| 기능 | gdb / lldb (리눅스) | WinDbg / Visual Studio 디버거 (Windows) |
|---|---|---|
| 심볼 | DWARF, 바이너리 내장 또는 `.debug` 파일, debuginfod 서버 | PDB, 심볼 서버(`_NT_SYMBOL_PATH=srv*C:\sym*https://msdl.microsoft.com/download/symbols`). MS가 모든 OS 바이너리의 공개 PDB 제공 |
| 시스템 라이브러리 내부 추적 | 배포판 debuginfo 패키지 설치 | 심볼 서버에서 자동 다운로드. `ntdll!NtCreateFile` 같은 곳에 바로 중단점 |
| 프로세스 붙이기 | `gdb -p PID` (ptrace, `ptrace_scope` 제한) | `windbg -p PID`, `DebugActiveProcess` (`SeDebugPrivilege`로 타 사용자 프로세스도) |
| 크래시 시 자동 실행 | `core_pattern`으로 코어 덤프. 디버거 자동 실행은 `core_pattern`에 파이프 스크립트 | JIT 디버거 (`AeDebug` 레지스트리). 크래시 시 디버거가 뜨거나 WER이 덤프 저장 |
| 덤프 형식 | 코어 덤프 (ELF, 전체 메모리 이미지, 크기 큼) | 미니덤프 (`.dmp`, 스택+모듈 목록만 수 MB) 또는 전체 덤프. `MiniDumpWriteDump` API로 프로그램이 직접 |
| 덤프 사후 분석 | `gdb prog core`, `coredumpctl` | `windbg -z dump.dmp`, `!analyze -v`가 크래시 원인 자동 추정 |
| 커널 디버깅 | kgdb, kdb, crash 유틸리티 (사용률 낮음) | WinDbg 커널 모드 (네트워크/USB/직렬), 매우 성숙. 드라이버 개발의 기본 |
| 스크립팅 | Python (gdb, lldb) | JavaScript (WinDbg Preview), 옛 `.dbg` 스크립트, `!` 확장 DLL |
| GUI | VS Code, CLion, gdb TUI | Visual Studio (통합 최고), WinDbg Preview |
| 시간 여행 디버깅 | rr (record & replay, x86 전용) | WinDbg TTD (Time Travel Debugging) |
| 조건부 중단점, 데이터 중단점 | 소프트웨어/하드웨어 워치포인트 | 동일 (`ba` 명령) |
| 릴리스 빌드 스택 추적 | `.eh_frame` 또는 프레임 포인터 필요, 없으면 깨짐 | `.pdata`로 항상 가능 |

**WinDbg의 강점**은 OS 내부까지 심볼이 있다는 것이다. `!handle`(프로세스 핸들 테이블 덤프), `!heap`(NT 힙 상태), `!locks`(크리티컬 섹션 소유자), `!runaway`(스레드별 CPU 시간), `~*k`(모든 스레드 스택), `!analyze -v`. 리눅스 gdb에서 같은 정보를 얻으려면 glibc 내부 구조체를 직접 캐거나 `/proc`을 봐야 한다.

**gdb의 강점**은 어디서나 있고, 스크립팅이 쉽고, 커널 소스와 함께 보면 시스템 콜 아래까지 이해할 수 있다는 것이다.

**크래시 덤프 수집 파이프라인**: 리눅스는 `systemd-coredump`가 코어를 저장하고 `coredumpctl`로 조회, 또는 Breakpad/Crashpad로 미니덤프 형식을 만들어 서버로 전송. Windows는 WER(Windows Error Reporting)이 `LocalDumps` 레지스트리 설정으로 덤프를 저장하고, 개발자는 Microsoft 파트너 센터로 수집할 수 있다. Crashpad는 두 OS 모두 지원해 크로스 플랫폼 표준이 되었다.

## 8.6 시스템 콜 추적과 프로파일링

**시스템 콜 추적**

- 리눅스: `strace` (ptrace 기반, 모든 시스템 콜과 인자, 반환값, 소요 시간. `-f`로 자식까지, `-e trace=file`로 필터, `-c`로 통계). `ltrace`(라이브러리 호출). eBPF 기반 `bpftrace`, BCC 도구(`opensnoop`, `execsnoop`, `tcpconnect`)는 오버헤드가 낮아 프로덕션에서도 쓴다.
- Windows: **`strace`에 정확히 해당하는 것이 없다.** `NtTrace`(서드파티, ptrace 유사)나 `drstrace`(DynamoRIO)가 있지만 널리 쓰이지 않는다. 대신 **Process Monitor**(파일, 레지스트리, 프로세스, 네트워크 이벤트를 필터 드라이버와 ETW로 수집, GUI)가 그 자리를 차지한다. 시스템 콜 전체가 아니라 "의미 있는 이벤트"를 보여 주고, 스택 추적을 함께 준다. API 레벨 추적은 API Monitor(서드파티).

**프로파일링**

| 항목 | 리눅스 | Windows |
|---|---|---|
| CPU 샘플링 | `perf record` / `perf report`, 하드웨어 PMU 카운터(`perf stat`) | WPR/WPA(Windows Performance Recorder/Analyzer, ETW 기반), Visual Studio 프로파일러, Intel VTune, `xperf` |
| 플레임 그래프 | `perf script` + FlameGraph 스크립트, `hotspot` GUI | WPA 플레임 그래프 뷰, `PerfView`(.NET 중심이나 네이티브도) |
| 시스템 전체 추적 | `perf`, `ftrace`, `trace-cmd`, `LTTng`, eBPF | ETW (커널 공급자: 컨텍스트 스위치, 디스크 I/O, 파일 I/O, 네트워크, 페이지 폴트, 스택 워크) |
| 오프 CPU 분석 (왜 기다리나) | `perf sched`, eBPF `offcputime` | WPA "CPU Usage (Precise)" + "Wait analysis": 스레드가 무엇을 기다렸고 누가 깨웠는지(ReadyThread) 완전 추적 |
| 메모리 프로파일링 | Valgrind massif, heaptrack, jemalloc 프로파일, `perf mem` | WPA Heap 추적, VMMap, UMDH(스택별 할당 비교), Visual Studio 메모리 스냅샷 |
| 힙 오류 검출 | Valgrind memcheck, ASan(`-fsanitize=address`) | ASan(MSVC 16.9+), Application Verifier, PageHeap(`gflags /p`), Dr. Memory |
| 데이터 경합 | TSan (`-fsanitize=thread`) | 없음 (MSVC TSan 미지원). clang-cl로도 Windows TSan 미지원 |
| 미정의 동작 | UBSan | 제한적 (`/RTC`, `/sdl`) |
| 캐시 미스, 분기 예측 | `perf stat -e cache-misses`, `perf c2c` | VTune, AMD uProf, WPA는 PMU 일부 |
| 사용자 정의 추적점 | USDT (`DTRACE_PROBE`), eBPF uprobes | `TraceLogging` / `EventWrite` (ETW 공급자, 코드에 삽입), 오버헤드 매우 낮음 |
| GPU | 벤더 도구 (Nsight, RGP) | PIX, GPUView(ETW 기반), Nsight |

**ETW의 위치**: Windows 성능 분석의 중심은 ETW다. 커널, 드라이버, .NET 런타임, 브라우저, 사무용 앱까지 모두 ETW 이벤트를 낸다. WPA는 이 이벤트들을 하나의 타임라인에서 상관 분석한다. "이 스레드가 200ms 멈춘 이유는 다른 프로세스의 디스크 I/O가 페이지 폴트를 지연시켰기 때문"을 클릭 몇 번으로 찾을 수 있다. 리눅스에서 같은 분석은 `perf`, `ftrace`, eBPF 도구를 조합해야 하고, 사용자 공간 런타임 이벤트(JVM, .NET)와 커널 이벤트의 상관은 도구가 흩어져 있다. 반대로 eBPF의 프로그래밍 가능성(커널 안에서 필터하고 집계)은 ETW에 없다.

**Sysinternals**: Process Explorer(작업 관리자 강화판, 핸들/DLL/스레드/스택), Process Monitor, VMMap, RAMMap, Handle, ListDLLs, TCPView, Autoruns, DebugView(`OutputDebugString` 수신). 마크 러시노비치가 만들고 MS가 인수. 리눅스에서 `htop`, `lsof`, `ss`, `/proc` 셸 스크립트로 나눠 하던 것을 GUI로 묶어 놓았다.

## 8.7 셸과 스크립팅

| 항목 | bash/zsh + coreutils | PowerShell (5.1 내장, 7.x 크로스 플랫폼) / cmd.exe |
|---|---|---|
| 파이프라인 | 바이트 스트림 (텍스트) | 오브젝트 (`Get-Process | Where-Object CPU -gt 100 | Select-Object Name`) |
| 텍스트 처리 | `grep`, `sed`, `awk`, `cut`, `sort`, `uniq` | `Select-String`, `-replace`, `ForEach-Object`, `Sort-Object`, `Group-Object`. 오브젝트라 파싱 불필요 |
| 변수 | `$VAR`, 환경 변수와 셸 변수 구분 | `$var`, `$env:VAR` |
| 종료 코드 | `$?` (0 = 성공) | `$?`(bool), `$LASTEXITCODE`(네이티브 exe) |
| 조건 실행 | `a && b`, `a || b` | PowerShell 7+: 동일. 5.1: `a; if ($?) { b }` |
| 인용 | `'literal'`, `"$expand"` | `'literal'`, `"$expand"`, 백틱 이스케이프 |
| 글로빙 | 셸이 확장해 `argv`로 전달 | 프로그램이 직접 처리 (CRT `setargv.obj` 링크 시 확장). cmd.exe는 확장 안 함 |
| 스크립트 실행 | `#!` + 실행 비트 | `.ps1`은 기본 실행 정책 `Restricted`(실행 불가). `Set-ExecutionPolicy RemoteSigned` 필요 |
| 대소문자 | 명령, 파일, 변수 모두 구분 | 명령, 변수 무시. 파일은 FS 따라 |
| 경로 구분 | `/`, `:`(PATH) | `\` (`/`도 대체로 허용), `;`(PATH) |
| 원격 실행 | ssh | PowerShell Remoting (WinRM), OpenSSH (Win10 1809+ 내장) |
| 관리 API 접근 | `/proc`, `/sys`, 명령줄 도구 | WMI/CIM (`Get-CimInstance Win32_Process`), .NET 클래스 직접 호출, COM |
| 크로스 플랫폼 | bash는 Windows에 Git Bash, MSYS2, WSL로 | PowerShell 7은 리눅스/macOS에서 동작 |

**cmd.exe**는 여전히 `.bat` 스크립트와 `CreateProcess`의 `shell=True` 경로로 남아 있다. 인용 규칙(`^` 이스케이프, `%VAR%`, `!VAR!` 지연 확장, `"` 처리)이 일관되지 않아 사용자 입력을 넘길 때 인젝션 위험이 크다. 가능하면 피한다.

**줄 끝과 인코딩**: 스크립트를 git으로 공유할 때 `core.autocrlf`가 `\n` ↔ `\r\n`을 변환한다. bash 스크립트에 `\r`이 섞이면 `$'\r': command not found`. PowerShell 5.1은 BOM 없는 UTF-8 스크립트를 ANSI로 읽어 한글이 깨진다(7.x는 UTF-8 기본). `.gitattributes`로 `*.sh text eol=lf`, `*.ps1 text eol=crlf` 지정이 관례.

**VC++ 재배포 가능 패키지 문제**: `/MD`로 빌드한 프로그램은 대상 PC에 `vcruntime140.dll`, `msvcp140.dll`이 있어야 한다. 없으면 "VCRUNTIME140.dll을 찾을 수 없습니다". 해결은 재배포 패키지 설치(인스톨러에 포함), DLL 동봉(라이선스상 허용), 또는 `/MT` 정적 링크(CRT 혼용 문제 감수). UCRT(`ucrtbase.dll`)는 Windows 10부터 OS의 일부라 배포 부담이 줄었다.

**리눅스의 glibc 문제**: 새 glibc에서 빌드한 바이너리는 옛 glibc에서 `GLIBC_2.xx not found`로 실패한다. 반대는 대체로 동작. 그래서 배포용 빌드는 지원할 가장 오래된 배포판(또는 manylinux 컨테이너)에서 하고, 또는 musl로 완전 정적 링크한다. Windows의 "낮은 `_WIN32_WINNT`로 빌드"와 같은 원칙이다.

## 8.9 이식할 때 부딪히는 문제

1. **컴파일러 확장 의존**: gcc 문장식, 가변 길이 배열(C99 VLA는 MSVC 미지원), `__attribute__`, 지정 초기화자 순서 위반(MSVC C++는 순서 엄격), `typeof`(MSVC C23 이전 미지원), 빈 구조체, 0 길이 배열. MSVC 쪽: `__declspec`, SEH, `#pragma comment(lib)`, 익명 구조체 확장. 해결: `-std=c11 -pedantic`과 `/permissive- /Za`로 표준 준수 검사, 또는 두 컴파일러에서 CI 빌드.
2. **`long`의 크기**: 리눅스 x86-64에서 64비트(LP64), Windows x64에서 **32비트**(LLP64). `long`으로 포인터나 64비트 값을 담는 코드가 깨진다. `int64_t`, `intptr_t`, `size_t`를 쓴다.
3. **`wchar_t`**: 리눅스 32비트(UTF-32), Windows 16비트(UTF-16). `wchar_t` 기반 문자열 처리는 이식 불가. `char16_t`/`char32_t` 또는 UTF-8 `char`로 통일.
4. **헤더**: `<unistd.h>`, `<sys/time.h>`, `<pthread.h>`, `<dirent.h>`, `<sys/mman.h>`는 MSVC에 없다. `<io.h>`, `<direct.h>`, `<process.h>`가 일부 대응. 함수 이름도 다르다: `getcwd`↔`_getcwd`, `access`↔`_access`, `snprintf`(2015 이전 MSVC는 비표준), `strdup`↔`_strdup`, `fileno`↔`_fileno`, `isatty`↔`_isatty`. MSVC는 POSIX 이름을 "deprecated" 경고(C4996)로 취급하고 `_CRT_NONSTDC_NO_DEPRECATE`로 억제.
5. **`min`/`max` 매크로**: `<windows.h>`가 `min`, `max` 매크로를 정의해 `std::min`을 깨뜨린다. `#define NOMINMAX` 먼저.
6. **인라인 어셈블리**: 64비트 MSVC에서 불가. intrinsic(`_mm_*`, `__rdtsc`, `_InterlockedCompareExchange`)으로 바꾸거나 별도 `.asm`.
7. **`#pragma once` vs 인클루드 가드**: 둘 다 양쪽에서 동작. 문제없음.
8. **경고 수준 차이**: MSVC `/W4`가 gcc `-Wall -Wextra`와 다른 것을 잡는다. 두 컴파일러 CI가 서로 다른 버그를 발견한다는 점에서 이식은 품질 향상 기회다.
9. **PDB와 심볼 관리**: 릴리스 빌드마다 PDB를 보관하고 심볼 서버에 올려야 크래시 덤프를 분석할 수 있다. 리눅스 debuginfo 분리(`objcopy`)와 debuginfod에 해당.
10. **빌드 환경 설정**: `vcvarsall.bat` 없이 `cl.exe`를 부르면 헤더를 못 찾는다. CI에서는 `ilammy/msvc-dev-cmd` 액션이나 CMake의 Visual Studio 제너레이터로 우회.
11. **TSan 부재**: Windows에서 데이터 경합 검출은 clang-cl로도 안 된다. 리눅스 CI에서 TSan을 돌려 두 OS 공통 코드의 경합을 잡는다.
12. **`strace` 부재**: "이 프로그램이 뭘 하다 멈추나"를 Windows에서 알아내려면 Process Monitor(파일/레지스트리/네트워크)와 Process Explorer(스레드 스택), WPA(대기 분석)를 조합해야 한다. 습관이 되기까지 시간이 걸린다.

## 8.10 런타임에서는

이 장의 주제는 네이티브 코드 중심이지만, 관리 런타임 사용자도 다음을 만난다.

- **Go**: `cgo`를 쓰면 위의 모든 문제가 돌아온다(Windows에서 MinGW gcc 필요, MSVC 불가). `cgo` 없이 `syscall`/`golang.org/x/sys/windows`로 Win32 API를 직접 호출하는 것이 Go 관례. `go build`는 크로스 컴파일이 쉬워(`GOOS=windows`) 빌드 환경 문제가 적다. 디버깅은 delve가 두 OS 지원. 프로파일링은 `pprof`로 OS 무관.
- **Rust**: Windows 타깃이 두 개다. `x86_64-pc-windows-msvc`(MSVC 링커, PDB, Windows 표준)와 `x86_64-pc-windows-gnu`(MinGW, DWARF). C 라이브러리와 링크하려면 그쪽 컴파일러 ABI에 맞아야 한다. `cargo build`는 `link.exe`를 찾기 위해 VS Build Tools 필요(`-msvc`). `windows` 크레이트(MS 공식)로 Win32 API 전체를 안전하게 호출. 디버거는 VS Code + CodeLLDB 또는 WinDbg(PDB 지원).
- **.NET**: 관리 코드는 ABI 무관. P/Invoke(`[DllImport]`)가 네이티브 경계이고 `long`이 항상 64비트인 C#과 Windows `LONG`(32비트)의 불일치가 흔한 버그. `CsWin32` 소스 생성기가 정확한 시그니처 제공. 디버깅은 VS/`dotnet-dump`/WinDbg + SOS 확장. 프로파일링은 `dotnet-trace`(EventPipe, 두 OS)와 PerfView(Windows ETW 통합).
- **Node.js**: 네이티브 애드온(`node-gyp`)이 Windows에서 VS Build Tools + Python 요구로 악명 높다. `prebuild`/`node-pre-gyp`로 미리 빌드한 바이너리 배포가 해결. N-API가 ABI 안정성 제공.
- **Python**: C 확장이 Windows에서 "Python을 빌드한 MSVC 버전"과 맞아야 했다(3.5+부터 UCRT 덕분에 완화, "stable ABI" `abi3` 휠로 더 완화). `pip install`이 휠이 없으면 컴파일러를 요구해 실패하는 것이 Windows 사용자의 흔한 경험. `ctypes`/`cffi`로 Win32 호출. 프로파일링은 `cProfile`, `py-spy`(두 OS), `scalene`.
- **JVM**: JNI가 네이티브 경계. `System.loadLibrary("foo")`가 `libfoo.so`/`foo.dll`을 `java.library.path`에서 찾는다. JVM 자체의 크래시(`hs_err_pid.log`)는 두 OS에서 같은 형식. 프로파일링은 JFR(Java Flight Recorder), async-profiler(리눅스 `perf_events` 기반, Windows는 제한적).
