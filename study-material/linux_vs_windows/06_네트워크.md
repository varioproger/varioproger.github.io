# 6장. 네트워크

## 6.1 OS가 풀어야 하는 문제

네트워크에서 OS는 다음을 제공한다.

1. **프로토콜 스택**: TCP/IP, UDP, 라우팅, ARP를 커널이 구현한다. 두 OS 모두 커널 모드 스택이고, 프로그래머가 보는 것은 소켓 API다.
2. **소켓 추상화**: 연결 하나를 나타내는 핸들과, 그것으로 데이터를 보내고 받는 API.
3. **다중화(multiplexing)**: 수천, 수만 개의 연결을 적은 수의 스레드로 처리하는 방법. 이것이 두 OS가 가장 크게 갈라지는 지점이다.
4. **버퍼 관리**: 커널 송수신 버퍼와 사용자 버퍼 사이의 복사, 그리고 복사를 피하는 방법.
5. **로컬 IPC**: 같은 머신의 프로세스 사이에 네트워크 소켓과 같은 API로 통신하는 방법.

TCP 프로토콜 자체의 동작(3-way handshake, 혼잡 제어, TIME_WAIT)은 같은 RFC를 따르므로 두 OS에서 개념이 같다. 다만 기본값과 튜닝 방법이 다르다.

## 6.2 소켓 API: BSD 소켓 vs Winsock

**리눅스: BSD 소켓, 소켓은 fd다**

```c
int s = socket(AF_INET, SOCK_STREAM, 0);
struct sockaddr_in addr = { .sin_family = AF_INET, .sin_port = htons(8080) };
inet_pton(AF_INET, "127.0.0.1", &addr.sin_addr);
connect(s, (struct sockaddr*)&addr, sizeof addr);
write(s, "hello", 5);          // send(s, "hello", 5, 0)과 같다
char buf[1024];
ssize_t n = read(s, buf, sizeof buf);
close(s);
```

소켓은 `int` fd다. `read`, `write`, `close`, `fcntl(O_NONBLOCK)`, `dup`, `poll`이 모두 통한다. 소켓 전용 함수(`send`, `recv`, `sendmsg`, `recvmsg`)는 플래그(`MSG_NOSIGNAL`, `MSG_PEEK`, `MSG_DONTWAIT`)와 보조 데이터(`SCM_RIGHTS`로 fd 전달)가 필요할 때만 쓴다. 소켓을 stdin으로 리디렉션해서(`dup2(s, 0)`) 아무 프로그램이든 네트워크 서버로 만드는 `inetd` 방식이 가능한 이유다.

초기화가 없다. 헤더는 `<sys/socket.h>`, `<netinet/in.h>`, `<arpa/inet.h>`, `<netdb.h>`.

**Windows: Winsock2, 소켓은 SOCKET이다**

```c
WSADATA wsa;
WSAStartup(MAKEWORD(2, 2), &wsa);              // 프로세스당 한 번 (참조 카운트)

SOCKET s = socket(AF_INET, SOCK_STREAM, 0);    // INVALID_SOCKET 확인 (-1이 아님)
struct sockaddr_in addr = { .sin_family = AF_INET, .sin_port = htons(8080) };
inet_pton(AF_INET, "127.0.0.1", &addr.sin_addr);
connect(s, (struct sockaddr*)&addr, sizeof addr);   // SOCKET_ERROR 확인
send(s, "hello", 5, 0);                        // write()는 안 됨
char buf[1024];
int n = recv(s, buf, sizeof buf, 0);           // read()는 안 됨
closesocket(s);                                // close()는 안 됨
WSACleanup();
```

Winsock은 원래 Windows 3.1용 서드파티 스택들을 위한 공통 API로 시작했다(WinSock 1.1, 1993). 그래서 초기화(`WSAStartup`)와 정리(`WSACleanup`)가 있고, 여러 프로토콜 제공자를 계층으로 쌓는 SPI(Service Provider Interface, LSP)가 있다. Winsock2(1996)에서 오버랩드 I/O, 이벤트 기반 알림, 다중 프로토콜이 추가되었다.

`SOCKET`은 `UINT_PTR`(포인터 크기 무부호 정수)이고 내부적으로는 커널 파일 오브젝트를 가리키는 핸들이다. 그래서 `ReadFile`/`WriteFile`이 기술적으로 통하고, IOCP에 등록할 수 있다. 하지만 공식적으로는 Winsock 함수만 쓰라고 한다. 유효하지 않은 값은 `INVALID_SOCKET`(`~0`)이고 `-1`과 비교하면 안 된다(부호 문제).

에러는 `WSAGetLastError()`. 코드 이름은 BSD 이름에 `WSA` 접두사가 붙는다: `WSAEWOULDBLOCK`, `WSAECONNRESET`, `WSAEADDRINUSE`. 헤더는 `<winsock2.h>`, `<ws2tcpip.h>`. `<windows.h>`보다 먼저 포함해야 한다(`<windows.h>`가 구 `<winsock.h>`를 끌어들여 재정의 오류를 내기 때문. `WIN32_LEAN_AND_MEAN`으로 방지).

**대응표**

| 개념 | 리눅스 | Windows |
|---|---|---|
| 소켓 타입 | `int` | `SOCKET` (`UINT_PTR`) |
| 무효 값 | `-1` | `INVALID_SOCKET` |
| 에러 반환 | `-1` + `errno` | `SOCKET_ERROR` + `WSAGetLastError()` |
| 닫기 | `close` | `closesocket` |
| 논블로킹 | `fcntl(s, F_SETFL, O_NONBLOCK)` 또는 `SOCK_NONBLOCK` | `ioctlsocket(s, FIONBIO, &one)` |
| 읽기/쓰기 | `read`/`write`/`send`/`recv`/`readv`/`writev`/`sendmsg`/`recvmsg` | `send`/`recv`/`WSASend`/`WSARecv`(scatter-gather는 `WSABUF` 배열) |
| 셧다운 | `shutdown(s, SHUT_RD/WR/RDWR)` | `shutdown(s, SD_RECEIVE/SEND/BOTH)` |
| exec 시 닫기 | `SOCK_CLOEXEC` | 핸들 상속 플래그 (`WSA_FLAG_NO_HANDLE_INHERIT`) |
| 다른 프로세스로 전달 | `sendmsg` + `SCM_RIGHTS` | `WSADuplicateSocket` + 프로토콜 정보 구조체 전달 |
| 주소 변환 | `getaddrinfo`, `inet_pton` | 동일 (Winsock2가 표준을 따름) |
| 초기화 | 없음 | `WSAStartup` / `WSACleanup` |
| 프로토콜 계층 | 커널 내부 | LSP(폐기됨), WFP 콜아웃 |
| `SIGPIPE` | 닫힌 소켓에 쓰면 발생 (`MSG_NOSIGNAL`로 억제) | 없음. `WSAECONNRESET`/`WSAECONNABORTED` 반환 |

## 6.3 I/O 모델: readiness vs completion

이 절이 네트워크 장, 나아가 이 책 전체의 핵심 갈림길이다.

**공통 배경: 블로킹 I/O의 한계**

가장 단순한 서버는 연결마다 스레드를 하나씩 두고 블로킹 `recv`를 부른다. 연결이 1만 개면 스레드가 1만 개다. 스택 메모리(리눅스 8MB × 1만 = 80GB 가상, Windows 1MB × 1만 = 10GB 커밋)와 컨텍스트 스위칭 비용이 감당되지 않는다. 이것이 1999년의 "C10K 문제"다. 해결책은 **적은 스레드로 많은 연결을 다루는 것**이고, 그 방법에서 두 OS가 갈라진다.

**리눅스: readiness (준비됨 통지)**

"이 소켓들 중 지금 읽을 수 있는(recv가 블로킹되지 않을) 것이 있으면 알려 달라"고 커널에 묻는다. 커널은 준비된 소켓 목록을 돌려주고, **실제 읽기는 애플리케이션이 그 다음에 한다.**

```c
// epoll: 등록은 한 번, 대기는 반복
int ep = epoll_create1(0);
struct epoll_event ev = { .events = EPOLLIN, .data.fd = listen_fd };
epoll_ctl(ep, EPOLL_CTL_ADD, listen_fd, &ev);

for (;;) {
    struct epoll_event evs[64];
    int n = epoll_wait(ep, evs, 64, -1);           // 준비된 fd만 돌려받음
    for (int i = 0; i < n; i++) {
        int fd = evs[i].data.fd;
        if (fd == listen_fd) {
            int c = accept4(listen_fd, NULL, NULL, SOCK_NONBLOCK);
            struct epoll_event cev = { .events = EPOLLIN | EPOLLET, .data.fd = c };
            epoll_ctl(ep, EPOLL_CTL_ADD, c, &cev);
        } else {
            char buf[4096];
            ssize_t r;
            while ((r = read(fd, buf, sizeof buf)) > 0)   // 준비됐으니 내가 읽는다
                handle(fd, buf, r);
            if (r == 0 || (r < 0 && errno != EAGAIN)) { close(fd); }
            // EAGAIN이면 다 읽은 것. 다음 epoll_wait으로
        }
    }
}
```

역사적 계보:

- `select` (1983, BSD): fd 비트마스크. `FD_SETSIZE`(1024) 한계. 매 호출마다 전체 집합을 커널에 복사하고, 반환 후 전체를 스캔. O(n).
- `poll` (1986, SVR3): 배열로 한계 제거. 여전히 매 호출 O(n).
- `epoll` (2002, 리눅스 2.5.44): 관심 집합을 커널에 **등록**해 두고(`epoll_ctl`), 대기(`epoll_wait`)는 준비된 것만 돌려받는다. O(준비된 수). 커널이 소켓 콜백에 epoll 항목을 걸어 두고, 데이터가 오면 ready list에 넣는다.

`epoll`의 두 모드:

- **Level-triggered (기본)**: 소켓이 준비 상태인 동안 `epoll_wait`마다 계속 알려준다. 데이터를 다 안 읽어도 다음에 또 뜬다. 안전하지만 다 읽지 않으면 매번 깨어난다.
- **Edge-triggered (`EPOLLET`)**: 상태가 **변할 때**만 알려준다. 알림을 받으면 `EAGAIN`이 나올 때까지 다 읽어야 한다. 안 그러면 남은 데이터를 영영 통지받지 못한다. 시스템 콜 횟수가 줄어 고성능 서버가 선호하지만, 버그가 나기 쉽다.

readiness 모델의 성질:

- 애플리케이션이 버퍼를 **읽는 시점에** 준비하면 된다. 연결 1만 개에 각각 버퍼를 미리 붙여 둘 필요가 없다. 준비된 소켓 몇 개만 작은 버퍼 하나로 순서대로 처리할 수 있다.
- **일반 파일에는 의미가 없다.** 디스크 파일은 항상 "준비됨"으로 보고되고 `read`는 디스크 I/O 동안 블로킹된다. 그래서 리눅스에서 비동기 파일 I/O는 오랫동안 스레드 풀로 흉내 냈다(libuv, glibc `aio_*`). `io_uring`이 이것을 해결했다(6.5절).
- 스레드 여러 개가 같은 epoll을 기다리면 thundering herd(모두 깨어나 하나만 처리)가 생긴다. `EPOLLEXCLUSIVE`(4.5+), 또는 `SO_REUSEPORT`로 스레드마다 별도 리스닝 소켓을 쓰는 방식으로 해결한다.

**Windows: completion (완료 통지)**

"이 버퍼에 데이터를 읽어 달라"고 커널에 **미리 요청**한다. 요청은 즉시 반환되고, 커널이 데이터를 버퍼에 채운 뒤 "완료됐다"고 알린다. **실제 읽기는 커널이 한다.**

```c
// IOCP: 소켓을 완료 포트에 연결하고, 요청을 걸어 두고, 완료를 기다린다
HANDLE iocp = CreateIoCompletionPort(INVALID_HANDLE_VALUE, NULL, 0, 0);

typedef struct { OVERLAPPED ov; SOCKET s; char buf[4096]; WSABUF wbuf; int op; } Ctx;

void post_recv(Ctx *c) {
    memset(&c->ov, 0, sizeof c->ov);
    c->wbuf.buf = c->buf; c->wbuf.len = sizeof c->buf; c->op = OP_RECV;
    DWORD flags = 0;
    WSARecv(c->s, &c->wbuf, 1, NULL, &flags, &c->ov, NULL);   // 즉시 반환. 버퍼는 커널이 소유
    // 반환값 SOCKET_ERROR + WSA_IO_PENDING이 정상
}

// accept된 소켓마다:
CreateIoCompletionPort((HANDLE)c->s, iocp, (ULONG_PTR)c, 0);   // 소켓을 포트에 연결
post_recv(c);

// 워커 스레드 (여러 개 가능):
for (;;) {
    DWORD bytes; ULONG_PTR key; OVERLAPPED *ov;
    BOOL ok = GetQueuedCompletionStatus(iocp, &bytes, &key, &ov, INFINITE);
    Ctx *c = (Ctx*)key;                                      // 어느 연결인가
    if (!ok || bytes == 0) { closesocket(c->s); free(c); continue; }
    if (c->op == OP_RECV) {
        handle(c->s, c->buf, bytes);                         // 데이터는 이미 버퍼에 있다
        post_recv(c);                                        // 다음 요청을 다시 건다
    }
}
```

역사적 계보:

- Winsock 1.1 `select`: BSD와 유사하나 `fd_set`이 배열이라 `FD_SETSIZE`(64) 한계. 소켓 전용.
- `WSAAsyncSelect` (Win 3.1): 소켓 이벤트를 윈도우 메시지로. GUI 앱용.
- `WSAEventSelect` (Winsock2): 소켓 이벤트를 이벤트 오브젝트로. `WSAWaitForMultipleEvents`(64개 한계).
- **Overlapped I/O + IOCP** (NT 3.5, 1994): NT 커널의 I/O 모델 자체가 비동기다. 모든 I/O 요청은 IRP(I/O Request Packet)로 드라이버에 내려가고, 동기 I/O는 커널이 완료를 기다려 주는 것일 뿐이다. `FILE_FLAG_OVERLAPPED`로 열면 그 기다림을 생략하고 완료를 따로 통지받는다. 통지 방법은 (a) `OVERLAPPED.hEvent` 시그널, (b) APC 완료 루틴, (c) **IOCP 큐**. IOCP는 완료 패킷을 큐에 넣고 여러 워커 스레드가 `GetQueuedCompletionStatus`로 꺼내는 구조다.

IOCP의 성질:

- **버퍼를 요청 시점에 제공**해야 하고, 완료까지 그 버퍼를 건드리면 안 된다. 연결 1만 개면 대기 중인 요청 1만 개, 버퍼 1만 개가 살아 있다. 메모리를 더 쓰지만, 데이터가 도착하는 즉시 사용자 버퍼로 복사되어 커널 버퍼 체류 시간이 짧다. 큰 버퍼를 미리 걸면 커널이 잠근(locked) 페이지가 늘어나 부담이 되므로, "0바이트 recv를 걸어 놓고 완료되면 그때 실제 버퍼로 recv"하는 기법도 있다(사실상 readiness 흉내).
- **파일, 파이프, 소켓, 디바이스가 모두 같은 방식**이다. 커널 I/O 모델이 원래 비동기이므로 디스크 파일도 진짜 비동기로 읽는다. 리눅스가 `io_uring` 전까지 못 했던 것이다.
- **스레드 풀과 통합**된다. IOCP는 "동시 실행 스레드 수"를 지정할 수 있고(`NumberOfConcurrentThreads`), 한 워커가 블로킹되면 다른 워커를 깨우는 식으로 활성 스레드 수를 코어 수에 맞춘다. 완료 패킷은 LIFO로 스레드에 배분되어 캐시 친화적이다.
- **취소가 명시적**이다. `CancelIoEx(h, &ov)`로 대기 중인 요청을 취소하면 완료 패킷이 `ERROR_OPERATION_ABORTED`로 도착한다. 취소된 요청의 버퍼는 그 패킷을 받은 뒤에야 해제할 수 있다. 소켓을 닫으면 모든 대기 요청이 취소 완료로 온다. 이 수명 관리가 IOCP 프로그래밍의 가장 어려운 부분이다.
- `AcceptEx`, `ConnectEx`, `TransmitFile`, `DisconnectEx` 같은 확장 함수가 accept/connect/sendfile을 오버랩드로 한다(함수 포인터를 `WSAIoctl(SIO_GET_EXTENSION_FUNCTION_POINTER)`로 얻어야 하는 이상한 관례가 있다). `AcceptEx`는 소켓을 **미리 만들어서** 넘겨야 한다(accept가 새 소켓을 반환하는 BSD와 반대).
- 사용자 정의 패킷을 `PostQueuedCompletionStatus`로 큐에 넣을 수 있다. 워커 스레드에 임의의 작업을 배분하는 데 쓴다. 리눅스 `eventfd`에 해당하지만 페이로드를 담을 수 있다.

**두 모델의 비교**

| 관점 | readiness (epoll) | completion (IOCP) |
|---|---|---|
| 질문 | "누가 준비됐나?" | "무엇이 끝났나?" |
| 읽기 주체 | 애플리케이션 (통지 후 `read`) | 커널 (요청 시 버퍼 제공, 완료 후 데이터 있음) |
| 버퍼 수명 | 읽는 순간만 | 요청~완료 사이 내내 |
| 연결당 메모리 | 작음 (fd 하나 + epoll 항목) | 큼 (대기 요청 + 버퍼) |
| 시스템 콜 수 | 통지 1 + read N | 요청 N + 완료 수신 1 (배치 가능) |
| 디스크 파일 | 지원 안 함 (항상 ready) | 지원 |
| 취소 | 필요 없음 (요청이 없으므로) | `CancelIoEx` + 취소 완료 대기 |
| 멀티스레드 | thundering herd 주의, `EPOLLEXCLUSIVE`/`SO_REUSEPORT` | 설계에 내재 (완료 큐 + 워커 풀) |
| 에러 발견 | `read` 반환값 | 완료 패킷의 상태 |
| 부분 읽기 | ET 모드에서 `EAGAIN`까지 반복 | 완료 바이트 수로 알 수 있음, 다음 요청 다시 걸어야 함 |
| 자연스러운 추상화 | 이벤트 루프 + 콜백/코루틴 (Node.js, Nginx, Tokio) | 비동기 요청 + 완료 콜백 (Windows 비동기, .NET `async`, Go netpoll의 Windows 구현) |

이 차이 때문에 크로스 플랫폼 네트워크 라이브러리는 두 모델 중 하나를 골라 다른 쪽을 흉내 내야 한다.

- **readiness를 기준으로 IOCP를 흉내**: 0바이트 recv를 걸어 "데이터 도착"을 readiness처럼 받는다. Windows에서 IOCP의 장점(커널 직접 복사)을 일부 포기한다. 초기 libuv, mio(`wepoll` 사용)가 이 방식.
- **completion을 기준으로 epoll을 흉내**: readiness 통지를 받은 뒤 라이브러리가 `read`를 호출해 사용자 버퍼를 채우고 완료 콜백을 부른다. 리눅스에서 대기 버퍼 메모리가 IOCP처럼 늘어난다. 현재 libuv, Boost.Asio(Proactor 패턴), .NET Sockets가 이 방식.

## 6.4 스레딩 모델과 이벤트 루프 구조

I/O 모델은 서버의 스레드 구조를 결정한다.

**리눅스 전형: 이벤트 루프 스레드 N개**

Nginx, Node.js(단일), Envoy, Redis(단일), Tokio(멀티): 코어 수만큼 스레드를 만들고 각 스레드가 자기 epoll 루프를 돈다. 연결은 한 스레드에 고정된다(또는 work-stealing으로 태스크 단위 이동). 루프는 "epoll_wait → 준비된 것들 처리 → 다시 대기". 블로킹 호출을 루프 안에서 하면 그 스레드의 모든 연결이 멈추므로, 디스크 I/O나 DNS 조회는 별도 스레드 풀로 보낸다(libuv의 워커 풀, Tokio의 `spawn_blocking`).

**Windows 전형: IOCP + 워커 풀**

IIS, SQL Server, 초기 Windows 게임 서버: 소켓을 전부 하나의 IOCP에 연결하고, 워커 스레드 N개(보통 코어 수 × 1~2)가 `GetQueuedCompletionStatus`를 부른다. 어느 연결의 완료가 어느 스레드에 갈지는 정해져 있지 않다. 연결별 상태는 `OVERLAPPED`를 확장한 컨텍스트 구조체에 담고, 같은 연결에 대한 두 완료가 두 스레드에서 동시에 처리될 수 있으므로 연결 단위 동기화가 필요하다. IOCP가 활성 스레드 수를 제어하므로, 워커에서 잠시 블로킹해도 다른 워커가 깨어나 처리량이 유지된다.

Windows에는 "연결을 스레드에 고정"하는 개념이 없어서, 코어 캐시 지역성은 IOCP의 LIFO 배분에 의존한다. Windows 8부터 `SetFileCompletionNotificationModes(FILE_SKIP_COMPLETION_PORT_ON_SUCCESS)`로 즉시 완료된 요청은 큐를 거치지 않게 해 시스템 콜을 아낀다. RIO(Registered I/O, Windows 8+)는 버퍼를 미리 등록하고 요청/완료 큐를 사용자 공간에 두어 시스템 콜 없이 I/O를 처리하는 초저지연 API인데, 설계가 `io_uring`과 매우 비슷하다.

## 6.5 `io_uring`: 리눅스가 completion 모델을 들여오다

2019년 리눅스 5.1에서 들어온 `io_uring`은 두 진영의 차이를 크게 줄였다.

- 사용자 공간과 커널이 공유하는 두 개의 링 버퍼: **제출 큐(SQ)**와 **완료 큐(CQ)**. 애플리케이션이 SQ에 요청(SQE)을 쓰고 `io_uring_enter`로 알리거나(또는 `SQPOLL`로 커널 스레드가 폴링해 시스템 콜 없이), 커널이 완료(CQE)를 CQ에 쓴다.
- 요청 종류: read/write, send/recv, accept, connect, openat, fsync, timeout, poll, 심지어 다른 요청과의 연결(`IOSQE_IO_LINK`). **파일과 소켓이 같은 인터페이스**다.
- 버퍼 미리 등록(`IORING_REGISTER_BUFFERS`), fd 미리 등록, 멀티샷 accept/recv(요청 하나로 여러 완료).
- 즉 IOCP + RIO에 해당하는 것이 리눅스에 생겼다. 디스크 파일의 진짜 비동기 I/O가 리눅스에서 가능해진 것이 가장 큰 의미다.

다만 아직 epoll을 대체하지는 못했다. 커널 버전 요구(실용적으로 5.10+, 많은 기능은 6.x), 보안 문제로 일부 배포판(예: 초기 컨테이너 런타임의 seccomp 기본 프로필)이 차단, 라이브러리 지원이 진행 중(Tokio `tokio-uring`, libuv 파일 I/O에만 사용, .NET 검토 중). 네트워크에서는 epoll 대비 이득이 상황에 따라 다르고, 파일 I/O에서는 이득이 확실하다.

`io_uring`의 등장으로 "리눅스는 readiness, Windows는 completion"이라는 구분이 "리눅스는 둘 다 가능, Windows는 completion"으로 바뀌고 있다. 크로스 플랫폼 라이브러리가 completion을 기준 모델로 삼는 추세가 강해지는 이유다.

## 6.6 커널 스택의 기본값과 튜닝

| 항목 | 리눅스 | Windows |
|---|---|---|
| 튜닝 위치 | `sysctl net.*`, `/proc/sys/net/`, 소켓 옵션 | 레지스트리 `HKLM\SYSTEM\CurrentControlSet\Services\Tcpip\Parameters`, `netsh int tcp set global`, 소켓 옵션 |
| 리스닝 백로그 | `listen(s, n)`, `net.core.somaxconn`(기본 4096)으로 상한 | `listen(s, SOMAXCONN)`, 실제 값은 200 근처에서 동적 조절. `SOMAXCONN_HINT(n)` |
| TIME_WAIT 지속 | 60초 고정 (`tcp_fin_timeout`은 FIN_WAIT2용) | 기본 120초. `TcpTimedWaitDelay` 레지스트리로 30~300초 |
| 임시 포트 범위 | `ip_local_port_range` 기본 32768~60999 | 기본 49152~65535. `netsh int ipv4 set dynamicport` |
| TIME_WAIT 재사용 | `tcp_tw_reuse`(클라이언트 측), `SO_REUSEADDR`는 리스닝 소켓의 TIME_WAIT 무시 | `SO_REUSEADDR`의 의미가 다름(아래) |
| 혼잡 제어 | 기본 CUBIC, `tcp_congestion_control`로 BBR 등 교체 | 기본 CUBIC (Win10+), `netsh int tcp set supplemental` |
| 수신 버퍼 자동 조절 | `tcp_rmem` 범위 내 자동 | Receive Window Auto-Tuning (`netsh int tcp set global autotuninglevel`) |
| Nagle 끄기 | `TCP_NODELAY` | `TCP_NODELAY` (동일) |
| Keep-alive | `SO_KEEPALIVE` + `TCP_KEEPIDLE/INTVL/CNT` | `SO_KEEPALIVE` + `SIO_KEEPALIVE_VALS` (`WSAIoctl`), Win10 1709+에서 `TCP_KEEPIDLE/INTVL` |
| Fast Open | `TCP_FASTOPEN` | `TCP_FASTOPEN` (Win10+) |
| 지연 accept | `TCP_DEFER_ACCEPT` | 없음 (`AcceptEx`의 초기 수신 버퍼가 유사 효과) |
| 연결 수 상한 | fd 한도(`ulimit -n`, `fs.file-max`) | 사실상 커널 메모리(비페이지드 풀). 클라이언트 SKU에는 동시 연결 제한이 있었으나 현재는 없음 |

**`SO_REUSEADDR`의 의미 차이**는 유명한 함정이다.

- 리눅스(BSD 의미): 리스닝 소켓을 bind할 때 같은 포트에 TIME_WAIT 상태 연결이 남아 있어도 허용한다. 서버 재시작 시 `Address already in use`를 피하는 표준 옵션. **이미 리스닝 중인 소켓과 같은 포트에 또 bind하는 것은 여전히 거부**한다. 이걸 허용하는 것은 `SO_REUSEPORT`(3.9+)다.
- Windows: `SO_REUSEADDR`이 **이미 리스닝 중인 소켓과 같은 포트에 bind를 허용**한다. 즉 리눅스의 `SO_REUSEPORT`에 가까운 위험한 동작이다(포트 하이재킹 가능). Windows의 TIME_WAIT 회피는 별도 옵션이 필요 없고 기본 동작이다. 대신 `SO_EXCLUSIVEADDRUSE`가 "아무도 이 포트를 재사용 못 하게"를 보장한다. 서버는 Windows에서 `SO_EXCLUSIVEADDRUSE`를 켜야 안전하다.

## 6.8 로컬 IPC: UNIX 도메인 소켓 vs Named Pipe

**리눅스: UNIX 도메인 소켓(`AF_UNIX`)**

파일 시스템 경로(`/var/run/docker.sock`) 또는 추상 이름(`@name`, 리눅스 전용)으로 식별한다. TCP 소켓과 API가 완전히 같으므로(`socket`, `bind`, `listen`, `accept`, `connect`, `read`, `write`), 서버를 TCP와 UNIX 소켓 양쪽으로 여는 것이 코드 몇 줄이다. 파일 권한으로 접근 제어한다. `SOCK_STREAM`, `SOCK_DGRAM`, `SOCK_SEQPACKET` 모두 지원. 특수 기능: `SCM_RIGHTS`로 **fd 전달**(다른 프로세스에게 열린 소켓/파일을 넘김), `SCM_CREDENTIALS`/`SO_PEERCRED`로 상대 pid/uid/gid 확인. TCP 루프백보다 빠르다(프로토콜 처리 없음).

그 외: 익명 파이프(`pipe`, 부모-자식), FIFO(`mkfifo`, 경로 있는 파이프), POSIX 메시지 큐(`mq_open`), D-Bus(데스크톱/시스템 버스, UNIX 소켓 위).

**Windows: Named Pipe**

```c
// 서버
HANDLE hPipe = CreateNamedPipeW(L"\\\\.\\pipe\\myapp",
    PIPE_ACCESS_DUPLEX | FILE_FLAG_OVERLAPPED,
    PIPE_TYPE_MESSAGE | PIPE_READMODE_MESSAGE | PIPE_WAIT,
    PIPE_UNLIMITED_INSTANCES, 4096, 4096, 0, NULL /* 보안 기술자 */);
ConnectNamedPipe(hPipe, &ov);     // 클라이언트 연결 대기 (accept에 해당)
// 클라이언트
HANDLE h = CreateFileW(L"\\\\.\\pipe\\myapp", GENERIC_READ | GENERIC_WRITE, 0, NULL, OPEN_EXISTING, FILE_FLAG_OVERLAPPED, NULL);
```

- 이름은 `\\.\pipe\name` (로컬) 또는 `\\server\pipe\name`(원격, SMB 위로 전달). 네트워크 투과성이 UNIX 소켓과 다른 점이다.
- 바이트 모드와 **메시지 모드**가 있다. 메시지 모드는 `SOCK_SEQPACKET`처럼 경계를 유지한다.
- **연결마다 인스턴스를 서버가 미리 만든다.** `accept`가 새 핸들을 돌려주는 방식이 아니라, 서버가 같은 이름으로 `CreateNamedPipe`를 여러 번 불러 인스턴스를 만들고 각 인스턴스에 `ConnectNamedPipe`를 걸어 둔다. `AcceptEx`처럼 "미리 만들기" 패턴이다.
- 보안 기술자로 접근 제어. `ImpersonateNamedPipeClient`로 서버가 클라이언트 토큰으로 가장할 수 있다. `GetNamedPipeClientProcessId`로 상대 pid 확인.
- 핸들 전달은 `DuplicateHandle`로 한다(파이프 자체 기능이 아니라 커널 오브젝트 일반 기능).
- 일반 파일 API(`ReadFile`, `WriteFile`, IOCP)를 쓴다. Winsock이 아니다.
- **AF_UNIX 지원**: Windows 10 1803부터 Winsock에 `AF_UNIX` `SOCK_STREAM`이 추가되었다. 리눅스와 호환되는 경로 기반 소켓이다. 단 `SOCK_DGRAM`, 추상 이름, `SCM_RIGHTS`는 지원하지 않는다. 크로스 플랫폼 코드가 이걸 쓰면 두 OS에서 같은 API로 로컬 IPC가 된다(Docker Desktop, .NET이 사용).

그 외: 익명 파이프(`CreatePipe`, 오버랩드 불가라는 큰 제약), 메일슬롯(브로드캐스트 데이터그램, 거의 안 씀), 윈도우 메시지(`WM_COPYDATA`), COM/DCOM, RPC(MS-RPC, `ncalrpc` 로컬 전송), ALPC(커널 내부 IPC, 비공개), 공유 메모리 + 이벤트.

| 항목 | UNIX 도메인 소켓 | Named Pipe |
|---|---|---|
| API | 소켓 API (TCP와 동일) | 파일 API (`ReadFile`/`WriteFile`) |
| 이름 공간 | 파일 시스템 경로, 추상 이름 | `\\.\pipe\` 오브젝트 네임스페이스 |
| 원격 접근 | 불가 | 가능 (SMB 경유) |
| 메시지 경계 | `SOCK_SEQPACKET`/`SOCK_DGRAM` | 메시지 모드 |
| 연결 수락 | `accept` → 새 fd | 인스턴스 미리 생성 + `ConnectNamedPipe` |
| 접근 제어 | 파일 권한 | 보안 기술자 (ACL) |
| 상대 신원 | `SO_PEERCRED` | `GetNamedPipeClientProcessId`, 가장 |
| fd/핸들 전달 | `SCM_RIGHTS` (소켓 기능) | `DuplicateHandle` (일반 기능) |
| 이벤트 루프 통합 | epoll | IOCP |
| 상호 호환 경로 | `AF_UNIX` (Windows 10 1803+) | 해당 없음 |

## 6.9 이름 풀이와 네트워크 구성 조회

| 항목 | 리눅스 | Windows |
|---|---|---|
| DNS 조회 | `getaddrinfo` (glibc resolver, `/etc/resolv.conf`, `/etc/hosts`, `/etc/nsswitch.conf`). 시스템 리졸버 데몬은 systemd-resolved 등 선택 | `getaddrinfo` (DNS Client 서비스가 캐시, `hosts` 파일, NetBIOS/LLMNR/mDNS 폴백) |
| 비동기 DNS | 표준 없음. `getaddrinfo_a`(glibc 전용), c-ares, 스레드 풀 | `GetAddrInfoExW` with `OVERLAPPED` (Win8+) |
| 인터페이스 목록 | `getifaddrs`, netlink(`RTM_GETLINK`), `/sys/class/net` | `GetAdaptersAddresses` (IP Helper API) |
| 라우팅 테이블 | netlink `RTM_GETROUTE`, `/proc/net/route` | `GetIpForwardTable2` |
| 연결 상태 목록 | `/proc/net/tcp`, netlink `sock_diag` (`ss` 명령) | `GetExtendedTcpTable` (`netstat`) |
| 변경 감시 | netlink 소켓 구독 | `NotifyAddrChange`, `NotifyIpInterfaceChange`, `NotifyRouteChange2` |
| 프록시 설정 | 환경 변수 `http_proxy`, 관례일 뿐 | WinHTTP/WinINet 설정, 레지스트리, PAC 스크립트 (`WinHttpGetIEProxyConfigForCurrentUser`) |
| 인증서 저장소 | 파일 (`/etc/ssl/certs`), OpenSSL | 시스템 인증서 저장소 (CryptoAPI, `certmgr`), Schannel |

마지막 두 행은 "네트워크 클라이언트"를 만들 때 자주 놓친다. Windows에서는 사용자가 설정한 시스템 프록시와 기업 인증서가 레지스트리와 인증서 저장소에 있고, 이를 무시하면 사내망에서 동작하지 않는다. .NET `HttpClient`, Chromium, curl(`--ssl-revoke-best-effort`, `CURLSSLOPT_NATIVE_CA`)이 이것을 처리한다.

| 소켓 상태 | `ss -tnp`, `netstat` | `netstat -ano`, `Get-NetTCPConnection` |
| 패킷 캡처 | `tcpdump`, Wireshark | Wireshark + Npcap, `pktmon` (내장), `netsh trace` |
| 시스템 콜 추적 | `strace -e trace=network` | Process Monitor (네트워크 이벤트는 요약만), ETW `Microsoft-Windows-Winsock-AFD` |

## 6.11 이식할 때 부딪히는 문제

1. **소켓을 fd로 다루는 코드**: `int s`, `close(s)`, `read/write`, `fcntl`, `errno`. 매크로 계층으로 감싼다(대부분의 크로스 플랫폼 C 라이브러리가 `sock_t`, `sock_close()`, `sock_errno()`를 정의한다).
2. **`select`의 `FD_SETSIZE`**: 리눅스 1024, Windows 64. Windows에서 `FD_SETSIZE`를 `winsock2.h` 포함 전에 재정의할 수 있지만 근본 해결은 IOCP/`WSAPoll`로 옮기는 것. `WSAPoll`(Vista+)은 `poll`과 호환되지만 초기 버전에 연결 실패를 보고하지 않는 버그가 있었다(Windows 10 2004에서 수정).
3. **`SIGPIPE`**: 리눅스에서 `signal(SIGPIPE, SIG_IGN)` 또는 `MSG_NOSIGNAL`. Windows에는 없으므로 `#ifdef`.
4. **`SO_REUSEADDR` 의미**: 리눅스에서는 서버 재시작용으로 켜고, Windows에서는 `SO_EXCLUSIVEADDRUSE`를 켜야 한다. 반대로 하면 Windows에서 포트 탈취 가능.
5. **epoll → IOCP**: 이벤트 루프의 핵심 구조가 바뀐다. 직접 구현하지 말고 libuv, Boost.Asio, libevent(Windows IOCP 지원은 제한적), mio를 쓴다. 직접 해야 한다면 completion을 기준 모델로 삼고 리눅스에서 흉내 내는 것이 덜 고통스럽다(io_uring이 그쪽으로 가고 있기도 하다).
6. **소켓 fd 전달 (`SCM_RIGHTS`)**: 프리포크 서버가 리스닝 소켓을 워커에 넘기는 패턴. Windows에서는 `WSADuplicateSocket`으로 `WSAPROTOCOL_INFO`를 얻어 IPC로 넘기고 상대가 `WSASocket`으로 복원. 또는 핸들 상속.
7. **`SO_REUSEPORT` 부하 분산**: Windows에 없다. IOCP 워커 풀로 같은 효과.
8. **UNIX 도메인 소켓**: Windows 10 1803+에서 `AF_UNIX`로 대체 가능. 그 이전 또는 데이터그램/fd 전달이 필요하면 Named Pipe로 재작성.
9. **DNS 설정 읽기**: `/etc/resolv.conf`를 파싱하던 코드(자체 리졸버)는 Windows에서 `GetNetworkParams`/`GetAdaptersAddresses`로.
10. **시스템 프록시와 인증서**: 리눅스에서는 환경 변수와 CA 번들 파일. Windows에서는 WinHTTP 프록시 설정과 시스템 인증서 저장소를 읽어야 사내망에서 동작.
11. **TIME_WAIT과 임시 포트 고갈**: 리눅스 60초 × 28,000포트, Windows 120초 × 16,000포트. 짧은 연결을 다량 만드는 클라이언트는 Windows에서 먼저 포트가 고갈된다. 연결 재사용(keep-alive, 커넥션 풀)이 해답이고, 임시 조치로 Windows에서 `TcpTimedWaitDelay` 축소와 포트 범위 확대.
12. **`accept` 소켓 속성 상속**: 리눅스에서 리스닝 소켓의 `O_NONBLOCK`은 accept된 소켓에 **상속되지 않는다**(BSD는 상속). Windows에서 오버랩드 속성은 `AcceptEx`로 미리 만든 소켓의 속성을 따른다. 두 OS 모두 accept 후 명시적으로 설정하는 것이 안전하다.

## 6.12 런타임에서는

- **Go**: `net` 패키지의 netpoller가 리눅스 epoll, Windows IOCP를 감싼다. Go는 **readiness 모델을 기준**으로 삼아 Windows에서는 IOCP 완료를 "준비됨"으로 변환한다(`runtime/netpoll_windows.go`). 고루틴이 `conn.Read`를 부르면 `WSARecv`를 걸고 파킹, 완료 시 깨운다. 결과적으로 Windows에서도 대기 버퍼는 고루틴이 제공한 것 하나만 있어 IOCP의 메모리 부담이 없다. 파일 I/O는 리눅스에서 블로킹(스레드 늘림), Windows에서 오버랩드 가능.
- **Rust (Tokio/mio)**: mio는 readiness 추상화. Windows에서 `wepoll` 스타일로 `AFD` 드라이버에 직접 `IOCTL_AFD_POLL`을 걸어(비공개 인터페이스!) readiness를 얻는다. 리눅스 epoll과 의미가 거의 같아지지만 비공개 인터페이스 의존이 약점이다. `tokio-uring`은 completion 기반 별도 런타임. `compio`는 completion 기준으로 두 OS를 통일하는 대안 런타임.
- **.NET**: `Socket`은 Windows에서 IOCP 네이티브, 리눅스에서는 `SocketAsyncEngine`이 epoll 위에 completion을 흉내 낸다. `async`/`await`가 completion 모델과 자연스럽게 맞는다. `SocketAsyncEventArgs`가 사실상 `OVERLAPPED` 확장의 관리 버전. `Socket.Select`는 두 OS에서 `select`/`poll`. `UnixDomainSocketEndPoint`가 Windows 1803+ `AF_UNIX`를 사용.
- **Node.js (libuv)**: libuv는 completion 스타일 콜백 API(`uv_read_start`가 라이브러리 소유 버퍼로 읽어 콜백)를 제공하고, 리눅스에서는 epoll + 자체 `read`, Windows에서는 IOCP 네이티브. 파일 I/O는 리눅스에서 워커 풀(io_uring은 1.45부터 일부), Windows에서도 워커 풀(오버랩드 파일 I/O를 쓰지 않는다. 디렉터리와 일부 파일 시스템의 비동기 미지원 때문). Named Pipe와 UNIX 소켓을 `uv_pipe_t`로 통일한다.
- **Python (asyncio)**: 리눅스 기본 `SelectorEventLoop`(epoll), Windows 기본 `ProactorEventLoop`(IOCP, 3.8부터). 두 루프의 기능이 다르다. `ProactorEventLoop`는 서브프로세스 파이프를 지원하지만 `add_reader`/`add_writer`(readiness API)를 지원하지 않는다. `SelectorEventLoop`를 Windows에서 쓰면 `select` 기반이라 64소켓 한계와 파이프 미지원. 이 차이로 Windows에서 asyncio 라이브러리 호환성 문제가 반복된다.
- **JVM (NIO)**: `Selector`는 리눅스 `EPollSelectorImpl`, Windows `WEPollSelectorImpl`(JDK 16+, 이전엔 `select` 기반 `WindowsSelectorImpl`로 1024 한계와 성능 문제). `AsynchronousSocketChannel`은 Windows에서 IOCP 네이티브, 리눅스에서 epoll + 스레드 풀. Netty는 리눅스 `epoll` 네이티브 전송과 `io_uring` 전송(4.2+)을 별도로 제공하고 Windows는 NIO만.
