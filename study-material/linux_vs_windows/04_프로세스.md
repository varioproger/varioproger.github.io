# 4장. 프로세스

## 4.1 OS가 풀어야 하는 문제

프로세스는 "실행 중인 프로그램에 대한 OS의 관리 단위"다. 두 OS 모두 프로세스는 다음의 묶음이다.

- 독립된 가상 주소 공간
- 열린 자원의 테이블(fd 테이블 / 핸들 테이블)
- 하나 이상의 실행 스레드
- 보안 컨텍스트(uid/gid / 액세스 토큰)
- 환경(인자, 환경 변수, 작업 디렉터리)
- 커널이 관리용으로 들고 있는 구조체(`task_struct` / `EPROCESS`)

이 그릇을 **어떻게 만들고, 어떻게 종료를 알아채고, 어떻게 외부에서 제어하며, 어떻게 묶어서 관리하는가**에서 두 OS가 갈라진다.

## 4.2 생성: `fork` + `exec` vs `CreateProcess`

**리눅스: 복제한 뒤 갈아 끼운다**

```c
pid_t pid = fork();
if (pid < 0) {
    perror("fork");
} else if (pid == 0) {
    // 자식: 부모의 완전한 복사본으로 시작한다
    // fd, 시그널 마스크, 환경, 작업 디렉터리, 메모리 내용까지 전부 같다
    dup2(logfd, STDOUT_FILENO);          // 여기서 자식만의 설정을 한다
    close(logfd);
    execvp("ls", (char*[]){"ls", "-l", NULL});  // 성공하면 돌아오지 않는다
    _exit(127);                          // exec 실패 시에만 도달
} else {
    // 부모
    int status;
    waitpid(pid, &status, 0);
    if (WIFEXITED(status)) printf("exit code %d\n", WEXITSTATUS(status));
}
```

`fork()`는 호출한 프로세스를 통째로 복제한다. 주소 공간은 COW(copy-on-write)로 공유되어 실제 복사는 일어나지 않고, 페이지 테이블만 복사된다. 반환값이 두 번 온다: 부모에게는 자식 PID, 자식에게는 0.

`exec` 계열(`execve`가 진짜 시스템 콜, 나머지는 libc 래퍼)은 현재 프로세스의 주소 공간을 버리고 새 실행 파일을 로드한다. PID는 유지되고, fd는 `O_CLOEXEC`가 없으면 유지되고, 시그널 핸들러는 기본값으로 리셋되지만 시그널 마스크는 유지된다.

이 2단계 설계의 힘은 **`fork`와 `exec` 사이**에 있다. 자식 프로세스만의 환경을 꾸미는 코드를 그 사이에 넣으면 된다. 리디렉션, 파이프 연결, `chdir`, `setuid`, `chroot`, 리소스 제한, 시그널 마스크 변경. 셸이 `ls | grep foo > out.txt`를 구현하는 방법이 정확히 이것이다. 부모가 "자식에게 이렇게 해 달라"고 옵션 구조체에 담아 넘기는 것이 아니라, **자식이 스스로 자기를 설정한다**.

대가는 두 가지다.

1. **큰 프로세스의 fork는 느리다.** 페이지 테이블 복사 비용이 주소 공간 크기에 비례한다. 10GB JVM이 `fork`하면 수십 ms가 걸린다. `vfork`(주소 공간 공유, exec 전까지 부모 정지)와 `posix_spawn`(내부적으로 `clone(CLONE_VM|CLONE_VFORK)`)이 이 문제의 우회로다.
2. **멀티스레드 프로세스에서 fork는 위험하다.** `fork`는 호출한 스레드 하나만 복제한다. 다른 스레드가 잡고 있던 뮤텍스(예: malloc의 아레나 락)는 자식에서 영원히 잠긴 채 남는다. 그래서 멀티스레드 프로그램에서 `fork` 후에는 async-signal-safe 함수만 호출하고 즉시 `exec`해야 한다. `pthread_atfork`가 완화책이지만 완전하지 않다.

**Windows: 한 번에 만든다**

```c
STARTUPINFOW si = { .cb = sizeof(si) };
PROCESS_INFORMATION pi;
wchar_t cmd[] = L"cmd.exe /c dir";   // 수정 가능한 버퍼여야 한다 (CreateProcessW가 수정할 수 있음)

si.dwFlags = STARTF_USESTDHANDLES;
si.hStdOutput = hLogFile;             // 리디렉션은 구조체 필드로 지정
si.hStdError  = GetStdHandle(STD_ERROR_HANDLE);
si.hStdInput  = GetStdHandle(STD_INPUT_HANDLE);

BOOL ok = CreateProcessW(
    NULL,           // 실행 파일 경로 (NULL이면 cmd의 첫 토큰)
    cmd,            // 커맨드라인 (하나의 문자열!)
    NULL, NULL,     // 프로세스/스레드 보안 속성
    TRUE,           // 상속 가능 핸들을 상속
    CREATE_NO_WINDOW,
    NULL,           // 환경 블록 (NULL이면 부모 것)
    NULL,           // 작업 디렉터리
    &si, &pi);

WaitForSingleObject(pi.hProcess, INFINITE);
DWORD code; GetExitCodeProcess(pi.hProcess, &code);
CloseHandle(pi.hThread);
CloseHandle(pi.hProcess);
```

`CreateProcess`는 실행 파일 로드, 주소 공간 생성, 첫 스레드 생성, 환경 설정을 한 번에 한다. "자식이 스스로 설정하는 구간"이 없으므로, 자식에게 적용할 모든 것을 인자로 미리 넘겨야 한다. 그래서 `STARTUPINFO`, `STARTUPINFOEX`의 속성 리스트(`PROC_THREAD_ATTRIBUTE_HANDLE_LIST`, `PROC_THREAD_ATTRIBUTE_PARENT_PROCESS`, 완화 정책 등)가 계속 자라 왔다. `posix_spawn`의 `posix_spawnattr_t`와 같은 접근이다.

세부 차이도 크다.

| 항목 | fork/exec | CreateProcess |
|---|---|---|
| 인자 전달 | `argv[]` 배열. 셸 파싱은 호출자 책임이고 커널은 배열을 그대로 전달 | 커맨드라인 문자열 하나. 파싱은 **자식 프로세스의 CRT**가 한다(`CommandLineToArgvW`). 인용 규칙이 복잡하고 프로그램마다 다를 수 있다 |
| 환경 | `envp[]` 배열, 대소문자 구분 | NUL로 구분된 블록, 이름은 대소문자 무시(`PATH` = `Path`) |
| 자원 상속 | 모든 fd가 상속(`O_CLOEXEC` 제외) | `bInheritHandles=TRUE`면 상속 플래그가 켜진 핸들 전부. `STARTUPINFOEX`로 특정 핸들만 지정 가능 |
| 실행 파일 찾기 | `execvp`는 `PATH` 검색, `execv`는 안 함 | 현재 디렉터리 → 시스템 디렉터리 → `PATH`. 확장자 `.exe` 자동 보충 |
| 스크립트 실행 | `#!` 셔뱅을 커널이 해석 | 커널은 PE만 실행. `.bat`는 `cmd.exe /c`로, `.py`는 파일 연결로 `ShellExecute`가 처리 |
| 반환 | PID 하나 | 프로세스 핸들, 스레드 핸들, PID, TID |
| 실패 시점 | `fork`는 자원 부족에서만 실패. `exec`가 실패하면 자식이 이미 만들어진 뒤 | `CreateProcess` 한 번에 성공/실패 |

**커맨드라인 파싱 문제**는 Windows 이식에서 가장 자주 마주치는 함정이다. 리눅스에서 `argv = ["prog", "a b", "c"]`는 그대로 전달되지만, Windows에서는 `L"prog \"a b\" c"`로 직렬화하고 자식이 다시 파싱한다. 인용 규칙에 `\"`, `\\"`, 연속 백슬래시 처리가 얽혀 있어, 인자에 백슬래시와 따옴표가 섞이면 정확한 이스케이프가 필요하다. Python의 `subprocess.list2cmdline`, Rust의 `std::process::Command`가 이 규칙을 구현하고 있다.

## 4.3 왜 Windows에는 fork가 없는가

기술적으로 NT 커널은 주소 공간 복제를 할 수 있다. 원래 NT의 POSIX 서브시스템과 이후 SUA(Subsystem for UNIX-based Applications)가 `fork`를 구현했고, `NtCreateProcess`에 부모 프로세스 핸들을 넘겨 주소 공간을 복제하는 경로가 실제로 존재한다. 그런데도 Win32에 `fork`가 없는 이유는 설계 목표와 맞지 않았기 때문이다.

1. **Win32 서브시스템은 프로세스 생성에 참여한다.** `CreateProcess`는 커널만이 아니라 `csrss.exe`(Client/Server Runtime Subsystem)에 새 프로세스를 등록해야 한다. 콘솔, 윈도우 스테이션, 데스크톱 연결이 여기서 이루어진다. 복제된 프로세스를 csrss에 어떻게 등록할지가 정의되어 있지 않다.
2. **DLL 초기화 모델과 충돌한다.** 모든 DLL은 `DllMain(DLL_PROCESS_ATTACH)`에서 프로세스별 상태를 초기화한다. `fork`로 복제된 프로세스는 이 초기화를 거치지 않았으므로, DLL이 잡고 있던 핸들, 스레드, 서버 연결이 깨진 상태로 남는다. 리눅스에서도 멀티스레드 fork가 위험한 것과 같은 문제인데, Windows는 이 상태를 "지원하지 않음"으로 정리했다.
3. **핸들은 fd보다 복잡하다.** 핸들은 오브젝트 관리자의 참조 카운트, 접근 마스크, 감사 정책과 연결되어 있다. 모든 핸들을 복제하는 것은 fd 테이블 복사보다 비용이 크고 의미가 모호하다(뮤텍스 소유권은 복제되는가?).
4. **철학**: NT 설계자들은 "프로세스 생성은 명시적이어야 한다"는 입장이었다. `fork`는 부모 상태를 암묵적으로 전부 넘기고 자식이 필요 없는 것을 닫는 방식이라, 보안 관점에서 바람직하지 않다고 봤다(실수로 상속된 fd는 UNIX에서 실제 보안 문제 사례가 많다).

**흉내 내는 방법들**

- **Cygwin**: 부모가 `CreateProcess(CREATE_SUSPENDED)`로 자기 자신을 다시 실행하고, 자기 주소 공간의 데이터를 자식에게 `WriteProcessMemory`로 복사한 뒤 재개한다. DLL이 같은 주소에 로드되지 않으면 실패한다. 느리고 불안정하다.
- **WSL1**: NT 커널에 리눅스 시스템 콜을 번역하는 계층(lxcore)을 넣어 `fork`를 커널 레벨에서 구현했다. 그래도 리눅스보다 느렸다.
- **WSL2**: 진짜 리눅스 커널을 경량 VM에서 돌린다. `fork`가 네이티브 속도지만, 그건 Windows가 아니라 리눅스다.
- **Windows 10 1903+의 Process Snapshotting / `RtlCloneUserProcess`**: 비공개 API로 주소 공간 복제가 가능하다. 연구 논문("A fork() in the road")에서 마이크로소프트 리서치조차 "fork는 현대 OS에 맞지 않는 유물"이라고 주장한 바 있다.

## 4.4 종료와 회수: 좀비 vs 핸들

**리눅스: 부모가 회수할 때까지 좀비**

프로세스가 `exit`하면 주소 공간과 fd는 즉시 해제되지만, `task_struct`와 종료 상태는 부모가 `wait`/`waitpid`/`waitid`로 읽어 갈 때까지 남는다. 이 상태가 **좀비**(`Z` 상태)다. 좀비는 메모리를 거의 안 쓰지만 PID 하나를 점유하고, 시스템 PID 한도(`/proc/sys/kernel/pid_max`, 기본 32768 또는 4194304)를 채우면 새 프로세스를 못 만든다.

부모가 먼저 죽으면 자식은 **고아**가 되어 PID 1(init/systemd) 또는 서브리퍼(`prctl(PR_SET_CHILD_SUBREAPER)`)에게 재입양되고, 그쪽이 `wait`해 준다. 컨테이너에서 애플리케이션이 PID 1로 뜨면 이 역할을 스스로 해야 하는데 대부분 안 하므로 좀비가 쌓인다. `tini`, `dumb-init`이 존재하는 이유다.

자식 종료 알림은 `SIGCHLD` 시그널로 온다. 핸들러에서 `waitpid(-1, &st, WNOHANG)`을 루프로 돌려 모두 회수하는 것이 관례다. `SIGCHLD`를 `SIG_IGN`으로 설정하면 커널이 자동 회수해 좀비가 생기지 않는다(단, 종료 코드를 잃는다).

```c
// 이벤트 루프 친화적 방법 (리눅스 5.3+)
int pfd = pidfd_open(pid, 0);
// epoll에 pfd 등록 → 자식이 종료하면 readable
// 이후 waitid(P_PIDFD, pfd, &info, WEXITED, NULL)
```

**Windows: 프로세스 오브젝트의 참조 카운트**

프로세스가 종료하면 주소 공간, 핸들 테이블, 스레드가 정리되고 프로세스 오브젝트는 **시그널 상태**가 된다. 종료 코드는 오브젝트에 저장된다. 오브젝트 자체는 참조 카운트가 0이 될 때, 즉 **이 프로세스를 가리키는 모든 핸들이 닫힐 때** 해제된다.

좀비 개념이 없다. 부모가 `CreateProcess`에서 받은 `pi.hProcess`를 `CloseHandle`하지 않으면 종료된 프로세스의 오브젝트가 남아 있지만, 이것은 "부모의 핸들 누수"이고 PID는 즉시 재사용될 수 있다(그래서 PID로 프로세스를 식별하는 것이 Windows에서는 더 위험하다). 부모가 죽어도 자식에게 아무 일도 일어나지 않고, 재입양도 없다.

종료 대기는 프로세스 핸들에 `WaitForSingleObject`하면 된다. 종료 코드는 `GetExitCodeProcess`. 여러 자식을 기다리려면 `WaitForMultipleObjects`에 핸들을 나열하거나, IOCP에 `RegisterWaitForSingleObject`로 등록한다.

| 항목 | 리눅스 | Windows |
|---|---|---|
| 종료 상태 보관 | 부모가 `wait`할 때까지 좀비로 | 프로세스 오브젝트에, 마지막 핸들이 닫힐 때까지 |
| 회수 안 하면 | 좀비 누적, PID 고갈 | 핸들 누수, 커널 메모리 소모 |
| 부모 사망 시 | init에 재입양 | 아무 일 없음 |
| 알림 | `SIGCHLD` | 핸들이 시그널 상태로 (대기 함수) |
| 종료 코드 범위 | 0~255 (8비트) | 32비트 `DWORD` |
| 강제 종료 | `kill(pid, SIGKILL)` | `TerminateProcess(h, code)` |
| 정상 종료 요청 | `kill(pid, SIGTERM)`, 프로세스가 핸들러로 처리 | 표준 없음. GUI는 `WM_CLOSE`, 콘솔은 `GenerateConsoleCtrlEvent`, 서비스는 `SERVICE_CONTROL_STOP`, 그 외는 애플리케이션 정의 IPC |

마지막 행이 실무에서 큰 차이다. 리눅스에서는 어떤 프로세스든 `SIGTERM`으로 "정리하고 끝내라"고 요청할 수 있는 **보편 프로토콜**이 있다. Windows에는 그것이 없다. `TerminateProcess`는 `SIGKILL`에 해당하는 즉사이고, 정상 종료를 요청하는 방법은 프로세스 종류마다 다르다. 크로스 플랫폼 서버를 만들 때 "Windows에서 graceful shutdown을 어떻게 트리거할 것인가"는 별도 설계가 필요하다(이름 있는 이벤트 오브젝트를 시그널하는 방식이 흔하다).

## 4.5 시그널의 부재

리눅스 프로세스 제어의 절반은 시그널이다. Windows에는 시그널이 사실상 없다. 이 차이는 프로세스 장을 넘어 스레드, 네트워크, 파일 I/O에도 영향을 미치므로 여기서 정리한다.

**리눅스에서 시그널이 하는 일과 Windows 대응물**

| 시그널 | 용도 | Windows에서는 |
|---|---|---|
| `SIGTERM`, `SIGINT` | 종료 요청 | 콘솔: `SetConsoleCtrlHandler`(Ctrl+C, 콘솔 닫힘). GUI: `WM_CLOSE`/`WM_QUERYENDSESSION`. 서비스: SCM 제어 코드 |
| `SIGKILL` | 강제 종료 | `TerminateProcess` |
| `SIGCHLD` | 자식 종료 알림 | 프로세스 핸들 대기 |
| `SIGSEGV`, `SIGFPE`, `SIGILL` | 하드웨어 예외 | SEH(Structured Exception Handling), `__try/__except`, 벡터 예외 핸들러 |
| `SIGPIPE` | 닫힌 파이프/소켓에 쓰기 | 없음. `WriteFile`이 `ERROR_NO_DATA`/`ERROR_BROKEN_PIPE` 반환, 소켓은 `WSAECONNRESET` |
| `SIGALRM`, 타이머 시그널 | 타이머 | 대기 가능 타이머 오브젝트, 타이머 큐, `SetTimer`(메시지) |
| `SIGHUP` | 설정 리로드 관례 | 없음. 애플리케이션 정의 IPC |
| `SIGUSR1/2` | 사용자 정의 | 이름 있는 이벤트 오브젝트 |
| `SIGSTOP`, `SIGCONT` | 정지/재개 | 프로세스 단위 없음. 스레드별 `SuspendThread`/`ResumeThread`, 또는 `NtSuspendProcess`(비공개) |
| `SIGWINCH` | 터미널 크기 변경 | 콘솔 입력 이벤트 `WINDOW_BUFFER_SIZE_EVENT` |

**설계 관점의 차이**

시그널은 "임의의 시점에 프로세스의 실행을 가로채서 핸들러를 실행한다"는 비동기 모델이다. 그래서 핸들러 안에서는 async-signal-safe 함수만 쓸 수 있고, `errno`가 덮어쓰이며, 블로킹 시스템 콜이 `EINTR`로 중단된다. 이것이 UNIX 프로그래밍의 악명 높은 함정들의 원천이다. 현대 리눅스는 `signalfd`, `pidfd`, `timerfd`로 시그널을 fd로 바꿔 동기적으로 처리하는 길을 열었다.

Windows는 처음부터 이 비동기 가로채기 모델을 거부했다. 대신:

- **하드웨어 예외**는 SEH로, 스레드 컨텍스트 안에서 동기적으로 처리한다. 스택 언와인딩과 통합되어 C++ 예외와 같은 메커니즘(`RaiseException`)을 쓴다.
- **외부 알림**은 커널 오브젝트를 시그널 상태로 만들고, 프로세스가 원할 때 대기 함수로 확인한다.
- **콘솔 Ctrl+C**만 예외적으로 비동기다. `SetConsoleCtrlHandler`로 등록한 핸들러는 **새 스레드에서** 실행된다. 리눅스 시그널 핸들러와 달리 어떤 함수든 호출할 수 있지만, 메인 스레드와의 동기화는 스스로 해야 한다.

결과적으로 Windows 코드에는 `EINTR` 처리, 시그널 마스크, async-signal-safety가 없다. 대신 "모든 대기를 핸들 대기로 바꾸고, 취소는 이벤트로 알린다"는 패턴이 있다.

**CRT의 `signal()` 함수**: MSVC CRT는 `signal(SIGINT, handler)`를 제공하지만 `SIGINT`, `SIGSEGV`, `SIGFPE`, `SIGILL`, `SIGABRT`, `SIGTERM`(CRT 내부 용도만)뿐이고, 내부적으로 SEH와 콘솔 핸들러를 감싼 것이다. `kill()`은 없다. 이식성 코드에서 `signal()`을 쓸 수는 있지만 `SIGCHLD`, `SIGPIPE`, `SIGUSR1`, `sigaction`, `sigprocmask`는 컴파일되지 않는다.

## 4.6 실행 파일과 동적 링킹: ELF vs PE

**ELF (리눅스)**

- 섹션(`.text`, `.data`, `.bss`, `.rodata`, `.dynamic`, `.got`, `.plt`)과 프로그램 헤더(로드 세그먼트).
- 동적 링커는 `ld-linux-x86-64.so.2`이고 커널이 `PT_INTERP`로 지정된 이것을 먼저 로드한 뒤 제어를 넘긴다.
- 공유 라이브러리(`.so`)는 기본적으로 **모든 심볼을 내보낸다**. `-fvisibility=hidden`으로 줄일 수 있다.
- 심볼 해석은 **전역 네임스페이스**에서 일어난다. 실행 파일과 모든 `.so`의 심볼이 하나의 공간에 있고, 먼저 로드된 것이 이긴다(symbol interposition). `LD_PRELOAD`가 `malloc`을 교체할 수 있는 이유다.
- 라이브러리 검색: `DT_RPATH` → `LD_LIBRARY_PATH` → `DT_RUNPATH` → `/etc/ld.so.cache` → `/lib`, `/usr/lib`. 실행 파일 위치는 기본 검색 경로가 **아니다**. `$ORIGIN` rpath로 지정해야 한다.
- 버전 관리: `libfoo.so.1.2.3` → `libfoo.so.1`(soname) → `libfoo.so` 심볼릭 링크 체인. 심볼 버전(`GLIBC_2.34`)으로 한 파일 안에 여러 ABI 버전이 공존한다.
- PIE(Position Independent Executable)가 기본이고, `.so`는 항상 PIC다. 재배치는 GOT/PLT를 통한 간접 호출로 처리되어 코드 페이지가 공유된다.

**PE (Windows)**

- 섹션(`.text`, `.data`, `.rdata`, `.idata`(임포트), `.edata`(익스포트), `.reloc`, `.rsrc`(리소스)).
- 로더는 `ntdll.dll` 안의 `Ldr*` 함수들이다. 별도 인터프리터 파일이 없다.
- DLL은 기본적으로 **아무것도 내보내지 않는다**. `__declspec(dllexport)` 또는 `.def` 파일로 명시해야 한다. 임포트도 `__declspec(dllimport)`로 명시하는 것이 정석(안 해도 되지만 간접 호출 최적화를 놓친다).
- 심볼 해석은 **모듈별**이다. `A.dll`이 `foo`를 임포트할 때 어느 DLL에서 가져올지가 임포트 테이블에 DLL 이름과 함께 박혀 있다. 전역 네임스페이스가 없으므로 interposition이 불가능하고, 같은 이름의 함수가 두 DLL에 있어도 충돌하지 않는다. `malloc` 교체가 어려운 이유이고, 동시에 "DLL 지옥"이 "심볼 충돌"이 아니라 "버전 불일치"의 문제인 이유다.
- 라이브러리 검색(기본 SafeDllSearchMode): 실행 파일 디렉터리 → 시스템 디렉터리 → 16비트 시스템 디렉터리 → Windows 디렉터리 → 현재 디렉터리 → `PATH`. **실행 파일 옆이 최우선**이므로 앱과 함께 DLL을 배포하는 것이 자연스럽다. `SetDefaultDllDirectories`, `AddDllDirectory`, 매니페스트의 `probing`으로 제어한다.
- 버전 관리: 파일 이름에 버전을 넣거나(`msvcr120.dll`), Side-by-Side 어셈블리(WinSxS)와 매니페스트를 쓴다. 심볼 버전 개념은 없다.
- 재배치: 64비트에서는 RIP 상대 주소로 대부분 해결되지만, 절대 주소가 필요한 곳은 `.reloc`으로 로드 시 패치한다. 패치된 페이지는 COW로 사적 복사본이 된다. ASLR로 시스템 DLL은 부팅 시 한 번 무작위 배치되고 모든 프로세스가 같은 주소를 쓴다.
- **`DllMain`**: DLL이 로드/언로드되거나 스레드가 생성/종료될 때 호출된다. 로더 락을 잡은 상태에서 호출되므로 안에서 다른 DLL 로드, 스레드 생성 후 대기, 동기화 대기를 하면 데드락이 난다. ELF의 `__attribute__((constructor))`에 대응하지만 제약이 훨씬 엄격하다.

| 항목 | ELF `.so` | PE `.dll` |
|---|---|---|
| 심볼 기본 가시성 | 전부 공개 | 전부 비공개 |
| 심볼 네임스페이스 | 전역, interposition 가능 | 모듈별, 충돌 없음 |
| 검색 우선순위 | 시스템 경로 우선, 실행 파일 옆은 rpath 필요 | 실행 파일 옆 우선 |
| 순환 의존 | 허용 | 허용하나 `DllMain` 순서 문제 |
| 로드 시 콜백 | constructor/destructor | `DllMain` (로더 락 제약) |
| 스레드 생성 알림 | 없음 | `DLL_THREAD_ATTACH/DETACH` |
| 런타임 로드 | `dlopen`, `dlsym`, `dlclose` | `LoadLibrary`, `GetProcAddress`, `FreeLibrary` |
| 언로드 안전성 | `RTLD_NODELETE`로 방지 | `GET_MODULE_HANDLE_EX_FLAG_PIN` |
| 실행 파일이 내보내는 심볼을 라이브러리가 참조 | 자연스럽게 가능 (플러그인이 호스트 함수 호출) | 실행 파일에서 `dllexport`하고 임포트 라이브러리를 만들어야 함 |

## 4.7 보안 컨텍스트: uid/gid vs 토큰과 ACL

**리눅스**

프로세스의 자격은 real/effective/saved uid와 gid, 보조 그룹 목록이다. 파일 접근은 파일의 소유자/그룹/기타 모드 비트(rwx)와 비교한다. 이 모델은 단순하지만 표현력이 낮아 다음이 추가되었다.

- **capabilities**: root 권한을 40여 개 조각(`CAP_NET_BIND_SERVICE`, `CAP_SYS_ADMIN` 등)으로 나눠 프로세스에 부분 부여. 컨테이너가 이것으로 권한을 깎는다.
- **POSIX ACL**: 파일에 `setfacl`로 사용자별 권한 추가. 널리 쓰이지는 않는다.
- **LSM**(SELinux, AppArmor): 강제 접근 제어. 정책 파일로 프로세스가 접근 가능한 자원을 제한.
- **setuid 비트**: 실행 파일을 소유자 권한으로 실행. `sudo`, `passwd`의 원리.

권한 상승은 `setuid` 바이너리 또는 `sudo`를 통한 **새 프로세스**로 이루어진다. 실행 중인 프로세스가 권한을 얻는 일반적 방법은 없고, 반대로 root가 권한을 버리는(`setuid(1000)`) 것은 쉽다. "root로 시작해 80번 포트를 열고 권한을 떨어뜨린다"는 데몬 패턴이 여기서 온다.

**Windows**

프로세스는 **액세스 토큰**을 가진다. 토큰에는 사용자 SID, 그룹 SID 목록, 권한(privilege) 목록(`SeDebugPrivilege`, `SeShutdownPrivilege` 등 약 35개), 무결성 수준(Low/Medium/High/System), 기본 DACL이 들어 있다. 모든 커널 오브젝트(파일, 레지스트리 키, 프로세스, 뮤텍스, 파이프)는 **보안 기술자**(security descriptor)를 가지고, 그 안의 DACL(Discretionary ACL)이 "어느 SID에게 어떤 접근 마스크를 허용/거부하는가"를 나열한다. 오브젝트를 열 때 보안 참조 모니터(SRM)가 토큰과 DACL을 비교해 **요청한 접근 마스크 전체**를 허용할지 결정하고, 결과는 핸들에 박힌다. 이후 그 핸들로 하는 연산은 핸들의 접근 마스크만 확인한다.

즉 리눅스는 "파일을 열 때 uid를 본다"이고 Windows는 "모든 오브젝트를 열 때 토큰을 본다"다. 뮤텍스나 공유 메모리에도 ACL이 붙는 것이 자연스러운 이유다.

- **UAC(User Account Control)**: 관리자 계정으로 로그인해도 프로세스는 기본적으로 **필터된 토큰**(관리자 그룹이 거부 전용으로 표시된)으로 실행된다. 상승이 필요한 작업은 "관리자 권한으로 실행"으로 **새 프로세스**를 완전한 토큰으로 띄운다. 이 점은 리눅스 `sudo`와 같다. 매니페스트의 `requestedExecutionLevel`이 프로세스 시작 시 상승 여부를 정한다.
- **가장(impersonation)**: 서버 스레드가 클라이언트의 토큰을 잠시 빌려 쓸 수 있다(`ImpersonateNamedPipeClient`, `ImpersonateLoggedOnUser`). 스레드 단위로 토큰이 바뀌는 이 기능은 리눅스에 직접 대응물이 없다(스레드별 `setfsuid`가 비슷하지만 제한적).
- **무결성 수준**: 브라우저 렌더러가 Low로 실행되어 Medium 오브젝트에 쓰기를 못 하게 한다. 리눅스에서는 seccomp, 네임스페이스, LSM 조합으로 비슷한 샌드박스를 만든다.
- **권한 부여**: 리눅스 capabilities에 해당하는 것이 Windows privilege다. 큰 페이지(`SeLockMemoryPrivilege`), 다른 프로세스 디버깅(`SeDebugPrivilege`), 심볼릭 링크 생성(`SeCreateSymbolicLinkPrivilege`)이 예다. 토큰에 있어도 기본은 비활성이고 `AdjustTokenPrivileges`로 켜야 한다.

| 항목 | 리눅스 | Windows |
|---|---|---|
| 주체 식별 | uid/gid (정수) | SID (가변 길이 식별자) |
| 프로세스 자격 | uid/gid 집합 + capabilities | 액세스 토큰 (SID들 + privilege들 + 무결성) |
| 오브젝트 권한 | 파일: 모드 비트 (+POSIX ACL). 그 외 오브젝트: 대부분 없음 | 모든 오브젝트: 보안 기술자 (DACL + SACL) |
| 검사 시점 | 열 때 (`open`), 일부 연산마다 | 열 때, 이후 핸들 접근 마스크로 |
| 권한 상승 | setuid 바이너리, sudo → 새 프로세스 | UAC 상승 → 새 프로세스 |
| 권한 하강 | `setuid`, `setgid`, capability drop | 제한 토큰 `CreateRestrictedToken`, 무결성 낮추기 |
| 다른 사용자로 실행 | `su`, `sudo -u`, `setuid` | `CreateProcessAsUser`, `CreateProcessWithLogonW`, `runas` |
| 서비스 계정 | 전용 uid (예: `www-data`), systemd `User=` | `LocalSystem`, `LocalService`, `NetworkService`, 가상 서비스 계정, gMSA |

## 4.8 프로세스 묶음: 그룹/세션/cgroup vs Job Object

**리눅스**

- **프로세스 그룹**: 파이프라인 `a | b | c`가 하나의 그룹. `kill(-pgid, SIGTERM)`으로 그룹 전체에 시그널. 터미널의 포그라운드/백그라운드 작업 제어에 쓰인다.
- **세션**: 로그인 하나. 제어 터미널과 연결. 데몬은 `setsid`로 새 세션을 만들어 터미널에서 분리된다.
- **cgroup v2**: 계층적 자원 제어. CPU(`cpu.max`), 메모리(`memory.max`), I/O, PID 수(`pids.max`)를 트리 노드마다 제한하고, 프로세스는 노드에 속한다. systemd가 모든 서비스를 cgroup에 넣고, 컨테이너 런타임이 컨테이너마다 cgroup을 만든다. `fork`한 자식은 자동으로 같은 cgroup에 속하므로 **자식이 도망칠 수 없다**. `memory.max`를 넘으면 그 cgroup 안에서만 OOM Killer가 동작한다.
- **네임스페이스**: PID, 마운트, 네트워크, UTS, IPC, 사용자, cgroup 네임스페이스. 프로세스가 보는 시스템 뷰를 격리한다. cgroup(자원 제한) + 네임스페이스(가시성 격리) + seccomp(시스템 콜 필터) = 컨테이너.

**Windows: Job Object**

Job Object는 프로세스 집합을 담는 커널 오브젝트다.

```c
HANDLE hJob = CreateJobObjectW(NULL, NULL);
JOBOBJECT_EXTENDED_LIMIT_INFORMATION lim = {0};
lim.BasicLimitInformation.LimitFlags =
    JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE |      // 잡 핸들이 닫히면 전부 종료
    JOB_OBJECT_LIMIT_PROCESS_MEMORY |         // 프로세스별 커밋 상한
    JOB_OBJECT_LIMIT_ACTIVE_PROCESS;          // 프로세스 수 상한
lim.ProcessMemoryLimit = 512ull << 20;
lim.BasicLimitInformation.ActiveProcessLimit = 10;
SetInformationJobObject(hJob, JobObjectExtendedLimitInformation, &lim, sizeof(lim));
AssignProcessToJobObject(hJob, pi.hProcess);
```

- CPU 사용률 제한(`JOB_OBJECT_CPU_RATE_CONTROL`), 메모리, 프로세스 수, UI 제한(클립보드, 데스크톱 접근 금지), 네트워크 대역폭(Windows 10+)을 걸 수 있다.
- 잡에 속한 프로세스가 만든 자식은 자동으로 같은 잡에 속한다(`CREATE_BREAKAWAY_FROM_JOB`으로 탈출 허용 가능). cgroup과 같은 성질이다.
- `TerminateJobObject`로 전체를 한 번에 종료. 리눅스 `kill(-pgid)`나 cgroup의 `cgroup.kill`에 해당.
- Windows 8부터 **중첩 잡**이 가능해 cgroup처럼 계층을 만들 수 있다.
- 잡 알림은 IOCP에 연결해서 받는다(`JobObjectAssociateCompletionPortInformation`). 프로세스 종료, 한도 초과 등이 IOCP 패킷으로 온다.

Windows 컨테이너(Server Silo)는 잡 오브젝트를 확장한 "사일로"로 구현되어 있고, 오브젝트 네임스페이스와 레지스트리를 가상화한다. 리눅스의 네임스페이스에 해당하지만 커널 빌드 종속이 있다(2.2절).

| 기능 | 리눅스 | Windows |
|---|---|---|
| 프로세스 트리 일괄 종료 | 프로세스 그룹 시그널, `cgroup.kill` | `TerminateJobObject`, `KILL_ON_JOB_CLOSE` |
| CPU/메모리 제한 | cgroup | Job Object 한도 |
| 자식 자동 포함 | cgroup 상속 | 잡 상속 |
| 계층 | cgroup 트리 | 중첩 잡 (Win8+) |
| 시스템 뷰 격리 | 네임스페이스 | 사일로 (Windows 컨테이너 전용) |
| 터미널 작업 제어 | 프로세스 그룹 + 세션 | 콘솔 프로세스 그룹 (`CREATE_NEW_PROCESS_GROUP`, Ctrl+Break 전달용) |

## 4.9 데몬 vs 서비스

**리눅스 데몬**: 전통적으로 double-fork(부모 종료 → 자식이 `setsid` → 다시 `fork`해서 세션 리더가 아님을 보장) → `chdir("/")` → fd 0,1,2를 `/dev/null`로 → PID 파일 쓰기. systemd 시대에는 이 절차가 불필요하다. 유닛 파일에 `Type=simple`(그냥 포그라운드로 실행), `Type=notify`(`sd_notify`로 준비 완료 알림)를 쓰고, 로그는 stdout으로 내보내면 journald가 받는다. 종료는 `SIGTERM` 후 `TimeoutStopSec` 뒤 `SIGKILL`.

**Windows 서비스**: SCM(Service Control Manager)에 등록된 프로그램이다. 실행 파일은 시작하자마자 `StartServiceCtrlDispatcherW`를 호출해 SCM에 연결하고, SCM이 `ServiceMain`을 호출한다. 서비스는 `SetServiceStatus`로 상태(`SERVICE_RUNNING`, `SERVICE_STOP_PENDING`)를 보고하고, `HandlerEx` 콜백으로 `SERVICE_CONTROL_STOP`, `PAUSE`, `SHUTDOWN` 같은 제어 코드를 받는다. 30초 안에 `RUNNING`을 보고하지 않으면 시작 실패로 간주된다. 로그는 이벤트 로그(`ReportEvent`) 또는 파일. 콘솔 없이 세션 0에서 실행되므로 GUI를 띄울 수 없다.

같은 프로그램을 두 OS에서 백그라운드 서비스로 돌리려면, 리눅스에서는 그냥 포그라운드 프로그램으로 두고 systemd에 맡기면 되지만, Windows에서는 서비스 프로토콜을 구현하거나 래퍼(NSSM, WinSW, .NET의 `Microsoft.Extensions.Hosting.WindowsServices`)를 써야 한다. 크로스 플랫폼 런타임(Go의 `golang.org/x/sys/windows/svc`, Rust의 `windows-service`)이 이 래핑을 제공한다.

## 4.10 프로세스 정보 조회

| 정보 | 리눅스 | Windows |
|---|---|---|
| 프로세스 목록 | `/proc/*/`, `readdir` | `CreateToolhelp32Snapshot` + `Process32First/Next`, 또는 `EnumProcesses`, 또는 `NtQuerySystemInformation(SystemProcessInformation)` |
| 명령줄 | `/proc/<pid>/cmdline` | `GetCommandLineW`(자기 자신), 다른 프로세스는 PEB를 `ReadProcessMemory`로 읽거나 WMI |
| 실행 파일 경로 | `/proc/<pid>/exe` 심볼릭 링크 | `QueryFullProcessImageNameW` |
| 메모리 사용 | `/proc/<pid>/status`, `statm`, `smaps` | `GetProcessMemoryInfo` (`PROCESS_MEMORY_COUNTERS_EX`) |
| CPU 시간 | `/proc/<pid>/stat`, `getrusage` | `GetProcessTimes` |
| 열린 파일 | `/proc/<pid>/fd/` | 공개 API 없음. `NtQuerySystemInformation(SystemHandleInformation)` + 핸들 복제. Process Explorer, `handle.exe`가 이 방법 |
| 부모 PID | `/proc/<pid>/status`의 PPid | `PROCESSENTRY32.th32ParentProcessID` (부모가 죽었으면 재사용된 PID일 수 있음) |
| 스레드 목록 | `/proc/<pid>/task/` | `Thread32First/Next` |

리눅스는 "모든 것이 파일"이라 `cat`으로 읽으면 된다. Windows는 오브젝트 관리자를 통해 핸들을 열고 API를 호출해야 하고, 다른 프로세스를 조회하려면 그 프로세스에 대한 접근 권한(`PROCESS_QUERY_LIMITED_INFORMATION`)이 필요하다. 보호된 프로세스(PPL)는 관리자도 열 수 없다.

## 4.11 이식할 때 부딪히는 문제

1. **`fork` 기반 워커 풀**: Nginx, Gunicorn, PostgreSQL, Redis BGSAVE, Python `multiprocessing`(fork 모드). Windows에서는 `spawn` 모델로 바꿔야 한다. 부모 상태를 자식이 상속하지 않으므로 초기화 코드를 다시 실행하고, 필요한 상태는 명시적으로 직렬화해 넘긴다. Python이 `if __name__ == "__main__":` 가드를 요구하는 이유가 이것이다(자식이 모듈을 다시 임포트하면서 워커 생성 코드를 재실행하지 않도록).
2. **인자 배열 → 커맨드라인 문자열**: 인용과 이스케이프 규칙을 정확히 구현해야 한다. 특히 `cmd.exe`를 거치면 `^`, `%`, `&`, `|`가 또 다른 의미를 갖는다. 가능하면 `cmd.exe`를 거치지 않고 실행 파일을 직접 실행한다.
3. **`SIGTERM` 핸들러**: Windows에서 graceful shutdown 신호를 어떻게 받을지 결정해야 한다. 콘솔 앱은 `SetConsoleCtrlHandler`, 서비스는 SCM 제어, 그 외는 이름 있는 이벤트. 프로세스를 죽이는 쪽(오케스트레이터, 슈퍼바이저)도 `TerminateProcess` 전에 그 신호를 보내도록 구현해야 한다. `docker stop`은 Windows 컨테이너에서 `CTRL_SHUTDOWN_EVENT`를 보낸다.
4. **`SIGPIPE`**: 리눅스에서는 기본 동작이 프로세스 종료라 `signal(SIGPIPE, SIG_IGN)`을 해야 하고, Windows에서는 애초에 없다. 대신 쓰기 실패 반환값을 반드시 확인해야 한다(두 OS 공통 원칙이지만 Windows에서는 다른 경로가 없다).
5. **PID 재사용**: Windows는 프로세스 종료 직후 PID가 재사용될 수 있다. PID로 "그 프로세스가 아직 살아 있나"를 판단하면 안 되고 핸들을 유지해야 한다. 리눅스도 원리는 같지만(`pidfd`가 나온 이유) 재사용 간격이 길어 문제가 덜 드러났을 뿐이다.
6. **좀비 처리 코드**: `SIGCHLD` 핸들러와 `waitpid` 루프는 Windows에서 불필요하다. 대신 프로세스 핸들을 반드시 `CloseHandle`해야 한다(자식 핸들 두 개, `hProcess`와 `hThread` 모두).
7. **실행 권한 비트**: 파일을 `chmod +x`해서 실행 가능하게 만드는 로직은 Windows에서 의미가 없다. 확장자가 실행 여부를 결정한다. 반대로 Windows에서 리눅스로 갈 때 빌드 산출물의 `x` 비트가 빠지는 문제(git의 `core.fileMode`)가 흔하다.
8. **DLL 심볼 내보내기**: `.so`에서 자동으로 보이던 함수가 `.dll`에서는 `dllexport` 없이 안 보인다. CMake의 `WINDOWS_EXPORT_ALL_SYMBOLS` 또는 명시적 export 매크로가 필요하다. 플러그인이 호스트 실행 파일의 함수를 부르는 구조는 Windows에서 호스트도 export해야 한다.
9. **`DllMain` 제약**: 라이브러리 초기화에서 스레드를 만들고 대기하거나 다른 DLL을 로드하는 코드는 로더 락 데드락을 만든다. 초기화를 명시적 `Init()` 함수로 옮긴다.
10. **권한 검사 로직**: `geteuid() == 0`으로 관리자 여부를 판단하던 코드는 `CheckTokenMembership(BUILTIN\Administrators)` 또는 `IsUserAnAdmin`으로. 파일 모드 비트로 "다른 사용자가 읽을 수 없게" 하던 코드는 DACL 설정으로.

## 4.12 런타임에서는

- **Go**: `os/exec`가 두 OS를 감싼다. 리눅스에서는 `clone(CLONE_VFORK|CLONE_VM)` + `execve`, Windows에서는 `CreateProcess`. `exec.Cmd.SysProcAttr`가 OS별로 완전히 다른 구조체다(`Setpgid` vs `CreationFlags`, `HideWindow`). 시그널은 `os/signal`이 Windows에서 `os.Interrupt`(Ctrl+C)만 지원하고, `syscall.SIGTERM`은 수신할 수 없다(`Process.Signal(SIGTERM)`은 Windows에서 `TerminateProcess`로 동작하지 않고 에러).
- **Rust**: `std::process::Command`가 커맨드라인 이스케이프를 구현한다. `raw_arg`로 우회 가능. `CommandExt::pre_exec`(fork와 exec 사이의 콜백)는 리눅스 전용이고, Windows에는 `creation_flags`가 있다. 종료 시그널 처리는 `ctrlc`, `signal-hook`(리눅스), `windows-service` 크레이트로.
- **.NET**: `Process.Start`는 두 OS 공통이지만 `ProcessStartInfo.ArgumentList`(배열)와 `Arguments`(문자열)가 모두 있어 Windows 이스케이프 문제를 드러낸다. `Process.Kill()`은 `SIGKILL`/`TerminateProcess`. `Process.Kill(entireProcessTree: true)`는 Windows에서 자식 트리를 탐색하고, 리눅스에서는 프로세스 그룹 시그널을 쓴다. `Console.CancelKeyPress`와 `AppDomain.ProcessExit`, `IHostApplicationLifetime`이 graceful shutdown을 추상화한다.
- **Node.js**: `child_process.spawn`은 두 OS 공통이고 libuv가 이스케이프를 처리한다. `shell: true`는 리눅스 `/bin/sh -c`, Windows `cmd.exe /c`. `process.on('SIGTERM')`은 Windows에서 리스너 등록은 되지만 절대 발생하지 않는다. `process.kill(pid, 'SIGTERM')`은 Windows에서 `TerminateProcess`가 된다. `cluster` 모듈은 리눅스에서 fork 후 소켓 공유, Windows에서는 spawn 후 핸들 전달로 구현이 다르다.
- **Python**: `os.fork`는 Windows에 없다(`AttributeError`). `multiprocessing`의 기본 시작 방법이 리눅스 fork(3.14부터 forkserver), Windows spawn. `subprocess`는 두 OS 공통이고 `list2cmdline`으로 이스케이프. `signal.signal`은 Windows에서 `SIGINT`, `SIGBREAK`, `SIGTERM`(발생 안 함), `SIGABRT`, `SIGFPE`, `SIGILL`, `SIGSEGV`만. `os.kill(pid, signal.SIGTERM)`은 `TerminateProcess`, `CTRL_C_EVENT`/`CTRL_BREAK_EVENT`는 콘솔 이벤트를 보낸다.
- **JVM**: `ProcessBuilder`가 커맨드라인 이스케이프를 처리하지만, 역사적으로 이스케이프 버그가 여러 번 있었다(`jdk.lang.Process.allowAmbiguousCommands`). `Runtime.addShutdownHook`이 리눅스 `SIGTERM`/Windows 콘솔 종료 및 `WM_ENDSESSION`을 감싼다. `Process.destroy()`는 리눅스 `SIGTERM`, Windows `TerminateProcess`(즉사)로 의미가 다르다.
