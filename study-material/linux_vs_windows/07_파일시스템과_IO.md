# 7장. 파일 시스템과 I/O

## 7.1 OS가 풀어야 하는 문제

파일 시스템 계층에서 OS는 다음을 제공한다.

1. **이름 공간**: 경로 문자열을 저장 장치의 데이터로 매핑한다.
2. **열린 파일의 상태**: 오프셋, 접근 모드, 공유 규칙.
3. **캐싱과 버퍼링**: 언제 디스크에 실제로 쓰는가, 언제 읽는가.
4. **일관성과 원자성**: 크래시 후에도 파일이 깨지지 않게 하는 수단.
5. **메타데이터**: 권한, 시각, 속성, 확장 속성.
6. **변경 감시**: 파일이 바뀌었을 때 알림.

2장에서 경로와 대소문자를 다뤘으므로 여기서는 열린 파일의 동작, 버퍼링, 원자성, 잠금, 감시를 중심으로 본다.

## 7.2 열린 파일: open file table vs 파일 오브젝트와 공유 모드

**리눅스**

`open`은 세 계층을 연결한다(2.3절). fd → open file description(오프셋, 상태 플래그) → inode. 같은 파일을 두 번 `open`하면 open file description이 두 개 생겨 오프셋이 독립적이다. `dup`이나 `fork`로 복사된 fd는 같은 description을 가리켜 오프셋을 공유한다.

```c
int fd = open("data.bin", O_RDWR | O_CREAT | O_CLOEXEC, 0644);
```

주요 플래그: `O_RDONLY/WRONLY/RDWR`, `O_CREAT`, `O_EXCL`(이미 있으면 실패, 원자적 생성), `O_TRUNC`, `O_APPEND`(모든 write가 원자적으로 끝에), `O_NONBLOCK`, `O_SYNC`/`O_DSYNC`(write마다 디스크 반영), `O_DIRECT`(페이지 캐시 우회), `O_CLOEXEC`, `O_TMPFILE`(이름 없는 임시 파일), `O_PATH`, `O_NOFOLLOW`.

**다른 프로세스가 같은 파일을 열고 있는지는 아무 상관이 없다.** 누가 열고 있어도 열고, 쓰고, 지우고, 이름을 바꿀 수 있다. 조율이 필요하면 별도 잠금(7.6절)을 쓴다.

**Windows**

```c
HANDLE h = CreateFileW(L"data.bin",
    GENERIC_READ | GENERIC_WRITE,                 // 원하는 접근
    FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE,   // 다른 사람에게 허용할 접근
    NULL,                                         // 보안 기술자
    OPEN_ALWAYS,                                  // 생성 규칙
    FILE_ATTRIBUTE_NORMAL | FILE_FLAG_OVERLAPPED, // 속성과 플래그
    NULL);
```

세 번째 인자 **공유 모드**(share mode)가 리눅스에 없는 개념이다. "내가 이 파일을 열어 둔 동안 다른 사람에게 무엇을 허용하는가"를 선언한다. 커널은 새 `CreateFile` 요청의 접근 모드와 **기존에 열려 있는 모든 핸들의 공유 모드**를 비교해 충돌하면 `ERROR_SHARING_VIOLATION`(32)으로 거부한다.

- `FILE_SHARE_READ`가 없으면 다른 사람이 읽기용으로 열 수 없다.
- `FILE_SHARE_WRITE`가 없으면 다른 사람이 쓰기용으로 열 수 없다.
- `FILE_SHARE_DELETE`가 없으면 다른 사람이 지우거나 이름을 바꿀 수 없다.
- 공유 모드 0이면 **배타적 접근**이다.

C 런타임의 `fopen`은 `FILE_SHARE_READ`만 지정한다(`_fsopen`으로 조절). .NET `FileStream` 기본은 `FileShare.Read`. 그래서 Windows 프로그램이 열어 둔 파일을 다른 프로그램이 쓰거나 지우지 못하는 상황이 기본 동작이 된다. 이것이 "파일이 다른 프로세스에서 사용 중입니다"의 원천이고, 로그 뷰어를 열어 둔 채 로그 로테이션이 실패하는 이유다.

생성 규칙 인자도 다르다: `CREATE_NEW`(=`O_CREAT|O_EXCL`), `CREATE_ALWAYS`(=`O_CREAT|O_TRUNC`), `OPEN_EXISTING`(플래그 없음), `OPEN_ALWAYS`(=`O_CREAT`), `TRUNCATE_EXISTING`(=`O_TRUNC`). 이런 정수 상수 조합이 아니라 열거형 하나라서 "존재하면 열고 없으면 만들되 자르지 않는" 같은 조합은 있지만, `O_APPEND`에 해당하는 것은 접근 모드 `FILE_APPEND_DATA`로 표현된다.

핸들에는 **파일 포인터**(오프셋)가 있다. `DuplicateHandle`로 복제하면 같은 파일 오브젝트를 가리켜 오프셋을 공유한다(dup과 같음). 오버랩드 I/O에서는 파일 포인터를 쓰지 않고 `OVERLAPPED.Offset`에 매번 위치를 준다(`pread`/`pwrite`에 해당).

**대응표**

| 개념 | 리눅스 | Windows |
|---|---|---|
| 열기 | `open(path, flags, mode)` | `CreateFileW(path, access, share, sd, disposition, flags, template)` |
| 접근 모드 | `O_RDONLY/WRONLY/RDWR` | `GENERIC_READ/WRITE`, 세부 `FILE_READ_DATA` 등 |
| 공유 제어 | 없음 | 공유 모드 (필수 인자) |
| 원자적 생성 | `O_CREAT | O_EXCL` | `CREATE_NEW` |
| 추가 모드 | `O_APPEND` | `FILE_APPEND_DATA` 접근 |
| 캐시 우회 | `O_DIRECT` (정렬 요구) | `FILE_FLAG_NO_BUFFERING` (섹터 정렬 요구) |
| 쓰기 즉시 반영 | `O_SYNC`, `O_DSYNC` | `FILE_FLAG_WRITE_THROUGH` |
| 위치 지정 읽기 | `pread`/`pwrite` | `ReadFile` + `OVERLAPPED.Offset` (오버랩드 핸들) 또는 `SetFilePointerEx` 후 `ReadFile` |
| 임시 파일 | `O_TMPFILE`, `mkstemp` | `FILE_ATTRIBUTE_TEMPORARY | FILE_FLAG_DELETE_ON_CLOSE`, `GetTempFileNameW` |
| 닫을 때 삭제 | `open` 직후 `unlink` (관용구) | `FILE_FLAG_DELETE_ON_CLOSE` |
| exec 상속 방지 | `O_CLOEXEC` | 보안 속성 `bInheritHandle=FALSE` (기본) |
| 심볼릭 링크 안 따라가기 | `O_NOFOLLOW` | `FILE_FLAG_OPEN_REPARSE_POINT` |
| 디렉터리 열기 | `open(dir, O_DIRECTORY)`, `opendir` | `CreateFileW(dir, ..., FILE_FLAG_BACKUP_SEMANTICS)` |
| 크기 변경 | `ftruncate`, `fallocate` | `SetEndOfFile`, `SetFileValidData`(권한 필요) |

## 7.3 이름과 내용의 분리: unlink와 rename

**리눅스: 이름은 inode에 대한 참조 중 하나일 뿐**

파일의 실체는 inode(메타데이터 + 데이터 블록)다. 디렉터리 엔트리는 이름 → inode 번호 매핑이고, 하드 링크는 같은 inode를 가리키는 여러 이름이다. inode는 **링크 수가 0이고 열린 fd가 0**일 때 해제된다.

```c
int fd = open("/tmp/scratch", O_RDWR | O_CREAT, 0600);
unlink("/tmp/scratch");     // 이름은 사라지지만 fd는 유효. 프로세스 종료 시 자동 해제.
// 이후 fd로 읽고 쓰기 자유
```

이 성질의 결과:

- 실행 중인 프로그램의 바이너리와 라이브러리를 **덮어쓰지 않고 교체**할 수 있다. 패키지 관리자는 새 파일을 옆에 쓰고 `rename`한다. 실행 중인 프로세스는 옛 inode를 계속 쓰고, 새로 시작하는 프로세스는 새 inode를 본다. **재부팅 없는 업데이트**의 원리다. (반대로 열린 파일을 `O_TRUNC`로 덮어쓰면 실행 중인 프로세스가 크래시한다. `ETXTBSY`가 실행 파일을 쓰기용으로 여는 것을 막는 이유다.)
- 로그 파일을 `rm`해도 프로세스가 열고 있으면 디스크 공간이 해제되지 않는다. `df`는 꽉 찼는데 `du`는 비어 있는 상황. `lsof +L1`로 찾는다.
- `rename(old, new)`은 **원자적**이다. `new`가 존재하면 덮어쓰고, 어느 순간에도 `new`는 옛 내용 또는 새 내용 중 하나를 가리킨다. "임시 파일에 쓰고 `fsync`하고 `rename`"이 안전한 파일 갱신의 표준 관용구다.
- 디렉터리를 `rename`할 수 있고, 안에 파일이 열려 있어도 된다. 열려 있는 파일의 절대 경로는 바뀌지만 fd는 그대로다. 현재 작업 디렉터리가 지워질 수도 있다.

**Windows: 파일 오브젝트가 이름을 붙잡는다**

NTFS도 내부적으로는 MFT 레코드(inode에 해당)와 하드 링크를 지원하지만, **열린 핸들이 있는 파일을 지우거나 이름을 바꾸는 것은 기본적으로 거부**된다. 열 때 `FILE_SHARE_DELETE`를 지정한 핸들만이 그것을 허용한다.

- `DeleteFileW`는 삭제를 **예약**한다(`FILE_DELETE_ON_CLOSE` 표시). 마지막 핸들이 닫히면 실제 삭제. 예약된 상태에서 새로 열려고 하면 `ERROR_ACCESS_DENIED`. 이름은 마지막 핸들이 닫힐 때까지 남는다. Windows 10 RS1부터 **POSIX 삭제 의미**(`FILE_DISPOSITION_POSIX_SEMANTICS`)가 추가되어 이름을 즉시 지울 수 있고, Windows 10 1903부터 `DeleteFileW`가 기본으로 이것을 시도한다. 그래도 `FILE_SHARE_DELETE` 없이 열린 핸들이 있으면 거부다.
- 실행 중인 `.exe`와 로드된 `.dll`은 **이미지 섹션이 매핑되어 있어** 삭제와 쓰기가 거부된다(`ERROR_SHARING_VIOLATION` 또는 `ERROR_ACCESS_DENIED`). 이름 바꾸기는 가능하다. 그래서 Windows 업데이트는 재부팅을 요구하고(`MoveFileEx(MOVEFILE_DELAY_UNTIL_REBOOT)`, `PendingFileRenameOperations` 레지스트리), 자기 업데이트 프로그램은 "새 exe를 다른 이름으로 받고, 옛 exe를 `.old`로 rename하고, 새 exe를 원래 이름으로 rename하고, 재시작 후 `.old` 삭제"를 한다.
- `MoveFileExW(old, new, MOVEFILE_REPLACE_EXISTING)`은 NTFS에서 원자적 rename이다. Windows 10 RS1부터 `SetFileInformationByHandle(FileRenameInfoEx)`에 `FILE_RENAME_POSIX_SEMANTICS`로 대상이 열려 있어도(`FILE_SHARE_DELETE`면) 교체 가능. `ReplaceFileW`는 원본 속성과 ACL을 유지하며 교체하지만 원자성이 완전하지 않다(백업 파일 이름을 거친다).
- 디렉터리는 안에 열린 파일이 있으면 rename도 삭제도 안 된다. 현재 작업 디렉터리인 디렉터리도 삭제 불가.

| 동작 | 리눅스 | Windows (기본 공유 모드) | Windows (`FILE_SHARE_DELETE` + POSIX 의미) |
|---|---|---|---|
| 열린 파일 삭제 | 즉시 이름 제거, 내용은 닫힐 때 | 거부 | 즉시 이름 제거 |
| 열린 파일 rename | 가능 | 거부 | 가능 |
| 열린 파일 위로 rename | 가능 (원자적) | 거부 | 가능 |
| 실행 중 exe 삭제 | 가능 | 거부 | 거부 (이미지 섹션) |
| 실행 중 exe rename | 가능 | 가능 | 가능 |
| 실행 중 exe 덮어쓰기 | `ETXTBSY` 거부 | 거부 | 거부 |
| 열린 파일 있는 디렉터리 rename | 가능 | 거부 | 거부 |

## 7.4 버퍼링, 캐시, 그리고 "정말 디스크에 썼는가"

두 OS 모두 세 층의 버퍼가 있다: 애플리케이션(stdio, 언어 런타임) → 커널 페이지 캐시 → 디스크 컨트롤러 캐시.

**리눅스**

- `write()`는 페이지 캐시에 복사하고 반환한다. 디스크 반영은 나중(`dirty_expire_centisecs` 기본 30초, `dirty_writeback_centisecs` 5초 주기, 또는 더티 비율 초과 시).
- **`fsync(fd)`**: 그 파일의 데이터와 메타데이터가 디스크에 도달할 때까지 블로킹. 디스크 캐시 플러시 명령도 보낸다(장치가 지원하면). **`fdatasync`**는 크기 변경 등 필수 메타데이터만.
- **디렉터리도 fsync해야 한다.** 새 파일을 만들고 `fsync(fd)`해도 디렉터리 엔트리가 디스크에 없으면 크래시 후 파일이 사라진다. `open(dir)` → `fsync(dirfd)`가 필요하다. ext4 `auto_da_alloc`이 rename 패턴을 감지해 도와주지만 의존하면 안 된다.
- `sync()`, `syncfs(fd)`: 전체 또는 파일 시스템 단위.
- `O_DIRECT`: 페이지 캐시를 우회해 사용자 버퍼 ↔ 디스크 직접 DMA. 버퍼, 오프셋, 크기가 논리 블록(보통 512B 또는 4KB) 정렬이어야 한다. 데이터베이스가 자기 버퍼 풀을 쓸 때 이중 캐시를 피하기 위해 사용. `fsync`는 여전히 필요(메타데이터).
- `posix_fadvise(SEQUENTIAL/RANDOM/DONTNEED/WILLNEED)`: 캐시 힌트. `DONTNEED`로 백업 프로그램이 읽은 페이지를 즉시 버려 다른 프로세스의 캐시를 밀어내지 않게 한다.
- `fsync` 실패(`EIO`)의 처리가 악명 높다(2018년 PostgreSQL "fsyncgate"). 리눅스는 실패한 더티 페이지를 깨끗한 것으로 표시해 버려서, 다시 `fsync`하면 성공으로 보인다. 데이터베이스는 `fsync` 실패 시 크래시 후 WAL 재생으로 대응한다.

**Windows**

- `WriteFile`도 캐시 매니저에 복사하고 반환한다. Lazy Writer가 약 1초 주기로 더티 페이지의 1/8을 쓴다. 리눅스보다 더 자주, 더 조금씩 쓴다.
- **`FlushFileBuffers(h)`**: `fsync`에 해당. 파일 데이터, 메타데이터, 그리고 볼륨의 디스크 캐시 플러시. NTFS 저널(`$LogFile`) 반영도 포함. **디렉터리 fsync 개념이 없다.** NTFS는 메타데이터 변경을 저널에 기록하고 `FlushFileBuffers`가 저널을 플러시하므로 디렉터리 엔트리 지속성이 함께 보장된다. 이 점은 Windows가 더 단순하다.
- `FILE_FLAG_WRITE_THROUGH`: `O_SYNC`에 해당. 매 `WriteFile`이 디스크 도달까지 대기. 단, 디스크 컨트롤러 캐시까지 플러시하는지는 장치/드라이버 설정("장치에 쓰기 캐싱 사용" + "버퍼 플러시 끄기" 옵션)에 따른다. Windows 8부터 `FILE_FLAG_WRITE_THROUGH`가 FUA(Force Unit Access)를 쓰도록 개선.
- `FILE_FLAG_NO_BUFFERING`: `O_DIRECT`에 해당. 섹터 크기 정렬(물리 섹터가 4KB인 디스크는 4KB). 대체로 `WRITE_THROUGH`와 함께 쓴다.
- `FILE_FLAG_SEQUENTIAL_SCAN`, `FILE_FLAG_RANDOM_ACCESS`: `posix_fadvise` 힌트에 해당. `CreateFile` 시점에 지정.
- 볼륨 전체 플러시: 볼륨 핸들(`\\.\C:`)에 `FlushFileBuffers`. 관리자 권한 필요.
- 시스템 종료 시 Windows는 모든 더티 페이지를 플러시한다. 리눅스도 `sync`를 한다. 두 OS 모두 정전에는 무력하고, 그래서 `fsync`/`FlushFileBuffers`가 필요하다.

**stdio 계층**: 두 OS 모두 C 표준 `FILE*`은 사용자 공간 버퍼(기본 4KB 또는 8KB)를 거친다. `fflush`는 커널로 넘길 뿐 디스크 보장이 아니다. 진짜 보장은 `fflush` → `fsync(fileno(fp))` / `FlushFileBuffers(_get_osfhandle(_fileno(fp)))`. Windows CRT는 텍스트 모드에서 `\n` → `\r\n` 변환을 이 버퍼에서 한다.

**안전한 파일 갱신 관용구**

리눅스:
```c
int fd = open("config.tmp", O_WRONLY | O_CREAT | O_TRUNC, 0644);
write(fd, data, len);
fsync(fd);                           // 데이터 도달
close(fd);
rename("config.tmp", "config.json"); // 원자적 교체
int dfd = open(".", O_RDONLY);
fsync(dfd);                          // 디렉터리 엔트리 도달
close(dfd);
```

Windows:
```c
HANDLE h = CreateFileW(L"config.tmp", GENERIC_WRITE, 0, NULL, CREATE_ALWAYS, FILE_ATTRIBUTE_NORMAL, NULL);
WriteFile(h, data, len, &written, NULL);
FlushFileBuffers(h);                 // 데이터 + 메타데이터 + 저널
CloseHandle(h);
MoveFileExW(L"config.tmp", L"config.json", MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH);
// 대상이 다른 프로세스에 열려 있으면(FILE_SHARE_DELETE 없이) 여기서 실패한다. 재시도 로직 필요.
```

## 7.5 메타데이터: 권한, 시각, 속성

| 항목 | 리눅스 | Windows (NTFS) |
|---|---|---|
| 권한 모델 | 소유자/그룹/기타 rwx + setuid/setgid/sticky (+ POSIX ACL) | 보안 기술자: 소유자 SID + DACL(허용/거부 ACE, 상속 플래그) + SACL(감사) |
| 권한 조회 | `stat` → `st_mode`, `access(path, W_OK)` | `GetFileSecurity`, `AccessCheck`. `_access`는 읽기 전용 속성만 봄 |
| 권한 상속 | 없음 (umask와 기본 ACL) | 부모 디렉터리 ACE의 상속 플래그로 자동 상속 |
| 실행 가능 표시 | `x` 비트 | 없음. 확장자 + `FILE_EXECUTE` 접근 (거의 항상 허용) |
| 읽기 전용 | 쓰기 비트 없음 | `FILE_ATTRIBUTE_READONLY` 속성 (권한과 별개, 소유자도 지울 수 없음, `DeleteFile` 거부) |
| 숨김 | 이름이 `.`으로 시작 (관례) | `FILE_ATTRIBUTE_HIDDEN` |
| 시각 | atime, mtime, ctime(메타데이터 변경 시각), btime(생성, `statx`) | 생성, 마지막 접근, 마지막 쓰기, MFT 변경(`FILE_BASIC_INFO.ChangeTime`) |
| 시각 해상도 | 나노초 (ext4), 파일 시스템별 | 100ns (FILETIME, 1601년 기준) |
| atime 갱신 | 기본 `relatime` (하루 한 번 또는 mtime보다 오래됐을 때) | 기본 **비활성** (Vista+, `NtfsDisableLastAccessUpdate`). Win10 1803부터 시스템 볼륨 크기에 따라 자동 |
| 확장 속성 | `setxattr`/`getxattr` (`user.*`, `security.*`) | 대체 데이터 스트림 (`file.txt:stream`), 확장 속성(`FILE_FULL_EA_INFORMATION`, 거의 안 씀) |
| 인터넷 다운로드 표시 | 없음 | `Zone.Identifier` ADS ("차단 해제") |
| 하드 링크 | `link`, 디렉터리 불가 | `CreateHardLinkW`, 디렉터리 불가 |
| 심볼릭 링크 | `symlink`, 누구나 | `CreateSymbolicLinkW`, 관리자 또는 개발자 모드 필요. 파일/디렉터리 구분 플래그 필수 |
| 디렉터리 정션 | 바인드 마운트 (mount) | 정션 (리파스 포인트, 심볼릭 링크 이전부터 존재, 권한 불필요) |
| 대체 데이터 스트림 | 없음 (macOS 리소스 포크에 해당) | NTFS 고유. `dir /r`로 보임 |
| 압축/암호화 속성 | 파일 시스템별 (btrfs 압축, fscrypt) | `FILE_ATTRIBUTE_COMPRESSED`, `FILE_ATTRIBUTE_ENCRYPTED` (EFS) |
| 희소 파일 | `lseek(SEEK_HOLE/SEEK_DATA)`, `fallocate(PUNCH_HOLE)` | `FSCTL_SET_SPARSE`, `FSCTL_SET_ZERO_DATA`, `FSCTL_QUERY_ALLOCATED_RANGES` |
| 파일 ID | inode 번호 + 디바이스 번호 | 파일 참조 번호(64비트) + 볼륨 시리얼 (`GetFileInformationByHandle`), ReFS는 128비트 |

**`stat`의 비용**: 리눅스 `stat`은 inode 하나를 읽는 저렴한 연산이다. Windows에서 `GetFileAttributesEx`는 파일을 내부적으로 열고 닫는 것과 비슷해 훨씬 비싸다(수 μs vs 수십 μs). 디렉터리 순회 시 파일마다 `stat`하는 코드가 Windows에서 눈에 띄게 느린 이유이고, `FindFirstFile`/`FindNextFile`이 반환하는 `WIN32_FIND_DATA`에 이미 크기와 시각이 들어 있는 이유다. 리눅스 `readdir`은 이름과 타입만 준다(`d_type`).

**Windows Defender와 필터 드라이버**: Windows에서 파일 열기가 리눅스보다 느린 또 하나의 이유다. 모든 `CreateFile`이 필터 관리자를 거쳐 안티바이러스, 검색 인덱서, 백업 소프트웨어의 미니필터를 통과한다. 개발용 디렉터리를 Defender 예외로 설정하면 빌드 시간이 눈에 띄게 줄어든다. 리눅스에는 `fanotify`가 비슷한 후크지만 기본 설치에서는 아무것도 걸려 있지 않다.

## 7.6 파일 잠금

**리눅스: 권고 잠금(advisory)이 기본**

- **`flock(fd, LOCK_SH|LOCK_EX|LOCK_NB)`**: BSD 유래. 파일 전체, open file description 단위(fork/dup으로 복사된 fd는 같은 잠금 공유). NFS에서는 지원이 불완전.
- **`fcntl(fd, F_SETLK/F_SETLKW, &flock)`**: POSIX 레코드 잠금. 바이트 범위, **프로세스 단위**(같은 프로세스가 다른 fd로 열어도 같은 잠금, **어느 fd든 닫으면 그 파일의 모든 잠금 해제**라는 악명 높은 함정). NFS 지원.
- **`F_OFD_SETLK`** (리눅스 3.15+): open file description 단위 바이트 범위 잠금. 위 함정을 고친 것. 스레드 간에도 동작.
- 모두 **권고**다. 잠금을 확인하지 않는 프로세스는 자유롭게 읽고 쓴다. 협력하는 프로세스 사이의 약속이다. 강제 잠금(mandatory locking)은 4.5에서 사실상 제거.
- `lslocks`, `/proc/locks`로 조회.

**Windows: 강제 잠금(mandatory)**

- **공유 모드**(7.2절)가 첫 번째 잠금 수단이다. 파일 전체 단위, 열 때 결정, 커널이 강제.
- **`LockFileEx(h, LOCKFILE_EXCLUSIVE_LOCK | LOCKFILE_FAIL_IMMEDIATELY, 0, lenLow, lenHigh, &ov)`**: 바이트 범위 잠금. **강제**다. 다른 핸들(같은 프로세스의 다른 핸들도 포함)이 잠긴 범위를 읽거나 쓰면 `ERROR_LOCK_VIOLATION`(33). 핸들 단위이므로 `DuplicateHandle`로 복제한 핸들은 잠금을 공유한다.
- 파일 끝을 넘는 범위도 잠글 수 있다(추가 쓰기 조율용).
- 잠금은 핸들이 닫힐 때 해제. 프로세스가 죽으면 커널이 정리.
- 네트워크(SMB)에서도 강제.

| 항목 | 리눅스 `fcntl`/`flock` | Windows `LockFileEx` |
|---|---|---|
| 강제성 | 권고 | 강제 |
| 범위 | 바이트 범위 (`fcntl`), 전체 (`flock`) | 바이트 범위 |
| 소유 단위 | 프로세스 (`fcntl`), OFD (`flock`, `F_OFD_*`) | 핸들 |
| 공유 잠금 | `F_RDLCK`, `LOCK_SH` | 플래그 없음 (기본이 공유) |
| 잠금 승격 | `F_WRLCK`로 재요청 (원자적 아님) | 해제 후 재획득 |
| 데드락 감지 | `fcntl`은 `EDEADLK` 반환 가능 | 없음 |
| 파일 열기 자체를 막는 수단 | 없음 | 공유 모드 |

SQLite가 두 OS에서 다른 잠금 전략(`unix` VFS는 `fcntl`, `win32` VFS는 `LockFileEx` + 공유 모드)을 쓰는 이유가 이 표에 있다.

## 7.7 디렉터리와 변경 감시

**디렉터리 순회**

| 리눅스 | Windows |
|---|---|
| `opendir`/`readdir`/`closedir`, 저수준 `getdents64` | `FindFirstFileW`/`FindNextFileW`/`FindClose`, 저수준 `NtQueryDirectoryFile` |
| 이름 + inode + `d_type` (파일 타입) | 이름 + 속성 + 크기 + 3개 시각 + 짧은 이름 (`WIN32_FIND_DATA`) |
| 순서 미정의 (파일 시스템 의존, ext4는 해시 순) | 순서 미정의 (NTFS는 대체로 이름 순, 보장 아님) |
| `.`과 `..` 포함 | `.`과 `..` 포함 (루트 제외) |
| 와일드카드 없음 (`glob`은 라이브러리) | 패턴 인자 필수 (`L"dir\\*"`). 커널이 매칭, 8.3 짧은 이름도 매칭 대상이라 `*.htm`이 `page.html`에 걸릴 수 있음 |
| 순회 중 변경 | 정의되지 않음, 대체로 안전 | 정의되지 않음 |

**변경 감시**

| 항목 | 리눅스 `inotify` | Windows `ReadDirectoryChangesW` |
|---|---|---|
| 단위 | 디렉터리 또는 파일 하나 (재귀 아님, 하위 디렉터리마다 watch 추가) | 디렉터리 트리 (`bWatchSubtree=TRUE`로 재귀) |
| 이벤트 | `IN_CREATE`, `IN_DELETE`, `IN_MODIFY`, `IN_MOVED_FROM/TO`(쿠키로 쌍), `IN_ATTRIB`, `IN_CLOSE_WRITE` | `FILE_ACTION_ADDED/REMOVED/MODIFIED/RENAMED_OLD_NAME/NEW_NAME` |
| 수신 | inotify fd에서 `read`, epoll 가능 | 오버랩드 I/O, IOCP 가능 |
| 한계 | watch 수 `max_user_watches` (기본 8192, 대형 프로젝트에서 부족), 큐 오버플로 `IN_Q_OVERFLOW` | 버퍼 오버플로 시 `ERROR_NOTIFY_ENUM_DIR` (전체 재스캔 필요), 네트워크 드라이브 불안정 |
| "쓰기 완료" 신호 | `IN_CLOSE_WRITE` (파일이 닫힘) | 없음. `MODIFIED`가 여러 번 옴, 마지막이 언제인지 알 수 없음 |
| 상위 API | `fanotify` (시스템 전체, 권한 필요), `fsnotify` | USN 저널 (`FSCTL_READ_USN_JOURNAL`, 볼륨 전체 변경 로그, 관리자 필요. Everything 검색이 사용) |

크로스 플랫폼 파일 감시(`fs.watch`, Rust `notify`, Java `WatchService`)가 두 OS에서 다른 이벤트 순서와 개수를 내는 것은 이 차이 때문이다. "파일 저장 완료"를 감지하려면 리눅스는 `IN_CLOSE_WRITE`, Windows는 디바운스(마지막 `MODIFIED` 후 일정 시간 대기)를 써야 한다.

## 7.8 특수 파일 시스템과 가상 경로

**리눅스**: `/proc`(프로세스와 커널 상태), `/sys`(디바이스 트리, 커널 파라미터), `/dev`(디바이스 노드), `/dev/shm`(tmpfs 공유 메모리), `/run`(런타임 상태), `/tmp`(대개 tmpfs). 모두 파일 API로 읽는다. `/proc/self/fd/N`으로 fd를 경로처럼 다시 열 수 있고, `/dev/stdin`, `/dev/null`, `/dev/zero`, `/dev/urandom`이 있다.

**Windows**: 사용자 모드에서 보이는 특수 이름은 `NUL`, `CON`, `\\.\PhysicalDrive0`, `\\.\C:`(볼륨), `\\.\pipe\name`, `\\?\` (경로 정규화 우회, 긴 경로), `\\?\GLOBALROOT\`(오브젝트 네임스페이스 접근). 커널 상태는 파일이 아니라 API와 레지스트리로 조회한다. `/proc/self/fd/N`에 해당하는 것은 없고 `DuplicateHandle`이나 `ReOpenFile`을 쓴다. `/dev/urandom`은 `BCryptGenRandom`. 임시 디렉터리는 `%TEMP%`(`GetTempPathW`), 사용자별이고 자동 정리되지 않는다.

**대소문자와 유니코드 정규화**: 리눅스는 바이트 비교. NTFS는 대소문자 무시 비교에 볼륨에 저장된 `$UpCase` 테이블을 쓴다(OS 버전에 따라 다른 유니코드 버전). 유니코드 정규화(NFC/NFD)는 두 OS 모두 하지 않는다(macOS HFS+가 했다). WSL이나 Windows 10 1803+의 `fsutil file setCaseSensitiveInfo`로 디렉터리 단위 대소문자 구분을 켤 수 있다.

## 7.9 이식할 때 부딪히는 문제

1. **열린 파일 삭제/교체**: 로그 로테이션, 캐시 정리, 자기 업데이트, 임시 파일 관용구(`open` 후 즉시 `unlink`). Windows에서는 `FILE_SHARE_DELETE`로 열거나, `FILE_FLAG_DELETE_ON_CLOSE`를 쓰거나, 재시도 루프(다른 프로세스가 곧 닫을 것을 기대)를 넣거나, 삭제를 다음 시작 시점으로 미룬다. 자기 업데이트는 rename 체인.
2. **공유 위반**: Windows에서 파일을 열 때 공유 모드를 가장 관대하게(`READ|WRITE|DELETE`) 지정하는 것이 크로스 플랫폼 코드의 기본이다. 리눅스 의미에 맞추기 위해서다. 다른 프로세스(백신, 인덱서, 에디터)가 잠깐 잡고 있어 `ERROR_SHARING_VIOLATION`이 나는 경우에 대비한 짧은 재시도가 실무에서 필수다.
3. **`fsync` 관용구**: 디렉터리 `fsync`는 Windows에 없으므로 `#ifdef`. Windows `FlushFileBuffers`는 볼륨 캐시까지 플러시해 리눅스보다 훨씬 느릴 수 있다(수십 ms). 호출 빈도를 재검토한다.
4. **`O_DIRECT` 정렬**: 리눅스 512B/4KB 논리 블록, Windows 물리 섹터(4KB Advanced Format). `FILE_FLAG_NO_BUFFERING`은 버퍼 주소, 오프셋, 길이 모두 정렬. `GetFileInformationByHandleEx(FileStorageInfo)`로 조회.
5. **권한 설정**: `chmod(0600)`으로 "나만 읽기"를 만들던 코드는 Windows에서 DACL을 만들어야 한다(`SetSecurityInfo`, 또는 `%LOCALAPPDATA%` 아래에 만들면 기본 상속 ACL이 사용자 전용). `chmod +x`는 무의미. SSH 키 파일 권한 검사처럼 "권한이 너무 열려 있다"를 판단하는 로직은 Windows에서 ACL 해석이 필요하다.
6. **읽기 전용 속성**: Windows에서 `FILE_ATTRIBUTE_READONLY`가 설정된 파일은 소유자도 `DeleteFile`할 수 없다. git이 체크아웃한 파일, CD에서 복사한 파일에서 자주 발생. 삭제 전 `SetFileAttributes(NORMAL)`.
7. **경로 길이**: 260자 한계. 매니페스트 `longPathAware` + 레지스트리 `LongPathsEnabled`(Win10 1607+), 또는 `\\?\` 접두사. 깊은 `node_modules`가 유명한 피해자.
8. **파일 시각**: Unix epoch(1970, 초/나노초) vs FILETIME(1601, 100ns). 변환 상수 `116444736000000000`. 시각 해상도 차이로 "수정 시각이 같으면 변경 없음" 판단이 어긋날 수 있다(FAT32는 2초 단위).
9. **`stat` 남용**: 디렉터리 순회 중 파일마다 `stat`하는 코드는 Windows에서 느리다. `FindNextFile`이 준 정보를 쓴다.
10. **변경 감시 의미**: 이벤트 수와 순서가 다르다. 디바운스와 재스캔 폴백을 항상 둔다.
11. **잠금 의미**: 권고 잠금에 의존하던 협력 프로토콜은 Windows 강제 잠금에서 "잠금 확인 없이 읽던 프로세스"가 갑자기 실패한다. 반대로 Windows 강제 잠금에 의존해 "다른 프로세스가 못 쓸 것"이라고 가정한 코드는 리눅스에서 데이터 경합이 생긴다.
12. **텍스트 모드**: Windows CRT의 `\r\n` 변환과 `Ctrl+Z`(0x1A)를 EOF로 취급하는 동작. 바이너리 파일을 `"r"`로 열면 깨진다. 항상 `"rb"`/`"wb"`, 또는 `_setmode(_O_BINARY)`.
13. **`/tmp` 가정**: Windows에는 시스템 공용 임시 디렉터리가 없다. `GetTempPathW` 결과는 사용자별이고 다른 사용자 프로세스(서비스)와 공유되지 않는다. 프로세스 간 공유 파일은 `%PROGRAMDATA%`.

## 7.10 런타임에서는

- **Go**: `os.Remove`가 Windows에서 읽기 전용 파일에 대해 속성을 지우고 재시도한다. `os.Rename`은 `MoveFileEx(REPLACE_EXISTING)`. `os.Open`은 Windows에서 `FILE_SHARE_READ|WRITE`로 열지만 `FILE_SHARE_DELETE`는 1.x 초기에 없었다가 추가됨. `File.Sync`는 `FlushFileBuffers`. 디렉터리 `Sync`는 Windows에서 no-op.
- **Rust**: `std::fs::File::open`은 Windows에서 `FILE_SHARE_READ|WRITE|DELETE`(가장 관대). `OpenOptions`의 Windows 확장 `share_mode`, `custom_flags`, `attributes`. `fs::remove_file`은 Windows에서 POSIX 삭제 의미를 시도(1.68+). `File::sync_all` = `fsync`/`FlushFileBuffers`, `sync_data` = `fdatasync`/`FlushFileBuffers`(구분 없음).
- **.NET**: `FileStream` 기본 `FileShare.Read`가 Windows 관습. 리눅스에서는 `FileShare`가 무시되다가 .NET 6부터 `flock`으로 **에뮬레이션**한다(`FileShare.None`이 `LOCK_EX`). `File.Delete`는 Windows에서 읽기 전용이면 `UnauthorizedAccessException`. `File.Move(overwrite: true)`는 .NET Core 3.0+. `FileSystemWatcher`가 두 OS에서 다른 이벤트를 낸다.
- **Node.js**: `fs.open`은 libuv가 Windows에서 `FILE_SHARE_READ|WRITE|DELETE`. `fs.unlink`가 Windows에서 열린 파일에 `EBUSY`/`EPERM`. `fs.rename`은 `MoveFileEx(REPLACE_EXISTING)`. `fs.watch`는 리눅스 inotify(재귀 미지원, 20.x부터 `recursive` 지원), Windows `ReadDirectoryChangesW`. `fs.chmod`은 Windows에서 읽기 전용 속성만 조작. `fs.fsync`는 `FlushFileBuffers`.
- **Python**: `os.remove`가 Windows에서 열린 파일에 `PermissionError`. `os.replace`가 원자적 교체(3.3+, Windows `MoveFileEx`). `tempfile.NamedTemporaryFile`은 Windows에서 열려 있는 동안 다른 프로세스가 열 수 없어(`delete=True`일 때 `FILE_SHARE_DELETE` 없이 열림) "이름을 받아 다른 프로그램에 넘기는" 용법이 실패. 3.12에서 `delete_on_close=False` 추가. `os.chmod`은 Windows에서 읽기 전용 비트만. `shutil.rmtree`가 Windows에서 읽기 전용 파일에 실패해 `onerror`/`onexc` 콜백으로 속성을 지우는 관용구가 있다.
- **JVM**: `Files.delete`가 Windows에서 열린 파일에 `FileSystemException`. `Files.move(ATOMIC_MOVE)`는 두 OS 모두 지원. `FileChannel.force(true)` = `fsync`/`FlushFileBuffers`. `FileChannel.lock`이 두 OS 잠금을 감싸지만 리눅스에서는 권고, Windows에서는 강제라 의미가 다르다(Javadoc에 명시). `WatchService`는 리눅스 inotify, Windows `ReadDirectoryChangesW`, macOS는 폴링(!). `File.setExecutable`은 Windows에서 no-op에 가깝다.
