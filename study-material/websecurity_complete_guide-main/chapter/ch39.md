# 39장. GraphQL 정찰과 정보 노출

> **이 장에서 다루는 것**
>
> - GraphQL API가 네트워크에 남기는 지문 — 엔드포인트의 관례, `data`/`errors` 응답 구조, GET 요청에 대한 반응이 어떻게 탐지 신호가 되는가
> - 인트로스펙션이 켜져 있을 때 스키마 전체가 어떻게 한 번의 질의로 넘어오는가, 그리고 InQL이 그것을 어떻게 자동화하는가
> - 인트로스펙션을 껐는데도 스키마가 복원되는 구조 — 필드 제안·필드 스터핑·`__type` 타입 스터핑, 그리고 "기능을 끄는 것"과 "정보를 감추는 것"이 다르다는 이 책의 논지
> - 구현체마다 다른 오류 출력이 곧 지문이 된다는 사실 — 25.6절 서버 핑거프린팅의 GraphQL판
> - GET 기반 질의가 캐시·로그·Referer·브라우저 히스토리에 데이터를 남기는 경로 — 23.3절이 세션 토큰에 대해 말한 것과 같은 구조

정찰은 모든 보안 시험의 첫 단계다. 이 단계의 목표는 대상에 관해 가능한 한 많은 정보를 모으는 것이며, 그 정보가 이후 공격을 어디에 어떻게 겨눌지를 결정한다. GraphQL은 "그저 API 계층"처럼 보이지만, 실험과 전용 도구를 통해 그 뒤에서 돌아가는 애플리케이션과 GraphQL 구현체 자체에 관해 놀랄 만큼 많은 것을 캐낼 수 있다.

이 장이 답하려는 질문은 몇 가지로 압축된다. 이 웹 서버에 GraphQL API가 있기는 한가. 있다면 어느 엔드포인트가 질의를 받는가. 어떤 언어로 쓰인 어떤 구현체인가. 그 구현체가 알려진 취약점을 갖는가. 어떤 방어가 걸려 있고 기본 설정은 무엇인가. 이 물음들에 답하고 나면 대상의 방어에서 빈틈을 찾아 초점 잡힌 공격을 계획할 수 있다.

이 장은 앞 장(38장)이 세운 지형 위에 선다. 38.8절이 인트로스펙션의 **메커니즘**을 이미 다뤘으므로, 이 장은 그것을 정찰에 실제로 쓰는 절차와 도구에서 시작한다. 그리고 30장이 정보 노출을 "노출"의 관점에서 개관했다면(→ 30.10), 이 장은 같은 기법을 **능동적 지도 그리기**의 관점에서 도구와 절차 수준까지 파고든다. 이 장의 절정은 39.5절이다. 인트로스펙션을 껐는데도 스키마가 복원되는 그 절이, 이 책이 반복해 온 하나의 논지 — **기능을 끄는 것과 정보를 감추는 것은 다르다** — 를 GraphQL에서 가장 선명하게 보여준다.

이 장의 실행 예제는 취약 GraphQL 서버 DVGA(Damn Vulnerable GraphQL Application)를 쓴다. 38.4절에서 구축한 랩 그대로다. 서점 맥락이 필요한 곳은 온라인 서점 API로 옮긴다.

## 39.1 GraphQL 탐지 / GraphiQL Explorer·Playground 탐지

정찰의 첫 물음은 단순하다. 이 서버에 GraphQL이 있는가. GraphQL은 네트워크에서 비교적 쉽게 식별된다. 명세가 응답 구조를 규정해 두었기 때문이다.

### 39.1.1 엔드포인트의 관례 — 예측 가능성이 곧 탐지 표면

REST와 GraphQL의 한 차이가 정찰 단계에서 곧바로 쓸모가 된다. GraphQL API의 엔드포인트는 **대개 정적이고, 관례적으로 `/graphql`** 이다(→ 38.1). REST가 자원마다 경로를 흩어 놓는 것과 달리, GraphQL은 단일 엔드포인트에 모든 질의를 받는다. 이 단일성은 공격자에게 유리하다. 찾을 곳이 하나이기 때문이다.

물론 개발자는 이 경로를 임의로 바꿀 수 있다. 그래서 탐지는 몇 가지 흔한 대안을 함께 시험한다.

- 버전 붙은 경로: `/v1/graphql`, `/v2/graphql`, `/v3/graphql`
- IDE 전용 경로: `/graphiql`, `/playground`
- 버전 붙은 IDE 경로: `/v1/graphiql`, `/v2/playground` 등
- 기타 관례: `/gql`, `/query`, `/console`, `/api/graphql`

버전 붙은 엔드포인트는 애플리케이션이 하위 호환을 위해 API 여러 판을 동시에 유지할 때 나타난다. IDE 전용 경로는 GraphiQL Explorer나 GraphQL Playground 같은 통합 개발 인터페이스가 자체 엔드포인트를 쓰기 때문에 생긴다. 여기서 중요한 것은 **각 엔드포인트가 서로 다른 보안 설정을 가질 수 있다**는 점이다. `/graphql`은 엄격하게 잠겨 있어도 `/graphiql`은 느슨할 수 있다. 같은 호스트에서 GraphQL을 받는 엔드포인트를 둘 이상 찾으면 반드시 **각각 따로 시험한다.** 이 관찰은 39.7절에서 다시 결정적이 된다 — DVGA의 `/graphql`은 스택 트레이스를 던지지 않지만 `/graphiql`은 던진다.

경로를 완전히 감춘 경우에는 무차별 대입이 답이다. 디렉터리 워드리스트나 GraphQL 전용 엔드포인트 목록으로 후보 경로를 훑는다. 이 절차 자체는 25.3절이 다룬 "숨겨진 콘텐츠 발견 — 무차별 대입"이 GraphQL 엔드포인트를 대상으로 재현된 것이다. 부록 H가 정찰 체크리스트로, 부록 B가 자동화 절차로 이 무차별 대입을 정리한다.

### 39.1.2 응답 구조로 판별하기 — `data`와 `errors`

경로를 찾았다면, 그 엔드포인트가 정말 GraphQL인지는 **응답의 형태**로 확정한다. 명세는 질의 응답의 구조를 못 박아 두었고, 이것이 곧 판별 규칙이 된다.

- 유효한 질의의 응답은 **항상 `data` 필드**에 결과를 담는다.
- 무효한 질의의 응답은 **항상 `errors` 필드**에 오류 정보를 담는다.

이 두 조건이면 충분하다. 유효하거나 잘못된 질의를 하나 보내고 응답에 `data` 또는 `errors` 키가 있는지 보면 된다. DVGA에 다음 질의를 POST로 보내 보자.

```graphql
query {
  pastes {
    id
  }
}
```

응답은 명세대로 `data` 필드에 결과를 담아 온다.

```json
{
  "data": {
    "pastes": [
      { "id": "1" }
    ]
  }
}
```

이번엔 존재하지 않는 최상위 필드를 물어 무효한 질의를 만든다.

```graphql
query {
  badfield {
    id
  }
}
```

서버는 질의를 처리할 수 없으므로 `errors` 필드를 채워 응답한다.

```json
{
  "errors": [
    {
      "message": "Cannot query field \"badfield\" on type \"Query\".",
      "locations": [ { "line": 2, "column": 3 } ]
    }
  ]
}
```

`message`가 `badfield`라는 필드가 존재하지 않는다고 알려준다. 이 두 응답 형태 자체가 GraphQL의 지문이다. 이 판별 규칙은 자동 스캔에 그대로 쓸 수 있다. UI가 없어 HTML도 HTTP 헤더도 내놓지 않는 순수 API 서버라도, 특정 조건에서 예측 가능한 응답을 돌려주므로 탐지된다. 대표적인 것이 GET 요청에 대한 반응이다.

```
# curl -X GET http://localhost:5013/graphql
{"errors":[{"message":"Must provide query string."}]}
```

`Must provide query string`은 Python·Node.js 기반 구현체가 흔히 내놓는 메시지다. 이런 고정 문자열을 패턴으로 삼아 Nmap의 `http-grep` 같은 NSE 스크립트로 네트워크 전체를 훑을 수 있다. 대량 호스트를 상대로 GraphQL 서버를 골라내는 절차가 이렇게 자동화된다. 다만 GET 기반 질의를 지원하지 않는 서버도 많으므로, 그럴 때는 `__typename`을 이용한 POST 탐지로 넘어간다(39.2에서 다룬다).

### 39.1.3 그래픽 인터페이스 탐지 — GraphiQL Explorer와 Playground

GraphiQL Explorer와 GraphQL Playground는 GraphQL API를 손으로 실험하게 해주는 IDE다. 둘 다 JavaScript 라이브러리 React로 만들어졌다. 여기에 정찰의 사각지대가 있다. cURL이나 Nikto 같은 명령줄 도구는 **JavaScript를 렌더링하지 못하므로** 이 인터페이스들을 놓치기 쉽다.

이런 관리·디버깅·설정 패널은 매력적인 표적이다. 데이터가 풍부하고, 다른 네트워크로 피벗하거나 권한을 상승시키는 발판이 되며, 공개 애플리케이션보다 훨씬 덜 강화되어 있다. 조직은 외부(인터넷)를 내부(사내망)보다 위험하다고 가정하는 경향이 있어, 내부 인터페이스는 패치·설정 검토·취약점 스캔의 관심을 덜 받는다.

JavaScript 렌더링이 필요한 인터페이스를 훑으려면 **헤드리스 브라우저**를 쓴다. EyeWitness 같은 도구는 Selenium 헤드리스 브라우저 엔진으로 대상 페이지의 스크린샷을 찍고 소스와 함께 리포트를 만든다. 스크린샷으로 IDE를 눈으로 확인할 수도 있고, 저장된 소스에서 `graphiql`·`graphql-playground` 같은 문자열을 `grep`으로 찾아 확정할 수도 있다.

그런데 IDE를 찾았다고 해서 API가 질의를 받아준다는 보장은 없다. GraphiQL Explorer와 Playground는 결국 GraphQL 서버에 붙는 **프런트엔드 HTTP 클라이언트**일 뿐이다. 인증·인가 계층, 지리·IP 기반 허용 목록, 클라이언트 측 통제가 질의를 막을 수 있다. 그래서 인터페이스를 찾으면 **어떤 GraphQL API에서나 통하는 무해한 질의** — 이를테면 `{ __typename }` — 하나를 보내 미인증 질의를 받아주는지 확인한다. 이것을 카나리아 질의(canary query)라 부를 수 있다.

DVGA의 `/graphiql`에 접근하면 `400 Bad Request: GraphiQL Access Rejected`가 뜨는 경우가 있다. 겉으로는 접근이 거부된 듯 보이지만, 개발자 도구로 안을 들여다보면 페이지 로드 시 인트로스펙션 질의가 이미 정상적으로 나가고 있다. 거부의 정체는 쿠키에 있다. `env`라는 쿠키가 `graphiql:disable` 값을 갖고, 그 값이 접근 거부를 결정한다. 값을 `graphiql:enable`로 바꾸고 새로고침하면 거부가 사라지고 질의가 통한다. **클라이언트가 직접 통제하는 것은 무엇이든 우회될 수 있다** — 이것은 클라이언트 측 통제의 근본 문제(→ 26장)가 GraphQL IDE 접근 제어에서 그대로 재현된 것이다. 입력 검증이나 파일 업로드 검증을 클라이언트에만 두는 흔한 실수와 같은 계열이다.

> **이 절이 뒷받침하는 것**
>
> - 엔드포인트 무차별 대입 → **25.3** (숨겨진 콘텐츠 발견), **부록 H**(정찰 체크리스트), **부록 B**(자동화)
> - 엔드포인트별 상이한 설정 → **39.7** (스택 트레이스를 던지는 엔드포인트와 그렇지 않은 엔드포인트)
> - 쿠키 기반 IDE 접근 거부의 우회 → **26장** (클라이언트 사이드 통제 우회)

## 39.2 인트로스펙션으로 스키마 질의하기

38.8절에서 인트로스펙션의 메커니즘을 세웠다. **클라이언트가 서버의 스키마 자체를 질의로 물어보는 내장 기능**이며, REST의 Swagger/OpenAPI 정의를 통째로 건네받는 것에 비유된다. 대부분의 구현체가 기본으로 켜 둔다. 이 절은 그 기능을 정찰에 쓰는 절차를 다룬다.

해커가 GraphQL 애플리케이션을 만나 가장 먼저 시험하는 것 중 하나가 인트로스펙션 활성 여부다. 가장 단순한 형태는 모든 타입의 이름을 뽑는 것이다(→ 38.8).

```graphql
query {
  __schema {
    types {
      name
    }
  }
}
```

응답에는 `ID`·`String` 같은 내장 스칼라와 함께 `PasteObject`·`CreatePaste`·`DeletePaste` 같은 개발자 정의 타입이 섞여 나온다. 그러나 이 형태는 스키마의 부분만 보여준다. 질의·뮤테이션 이름, 어떤 질의가 인자를 받는지, 인자의 데이터 타입은 무엇인지가 빠져 있다. 이것들이 중요한 이유는, **인자를 받는 질의가 곧 인젝션·SSRF 같은 취약점의 진입점**이기 때문이다(→ 27.14, 28.10).

그래서 진입점을 정확히 겨눈 인트로스펙션 질의를 쓴다.

```graphql
query IntrospectionQuery {
  __schema {
    queryType { name }
    mutationType { name }
    subscriptionType { name }
    types {
      kind
      name
      fields {
        name
        args {
          name
        }
      }
    }
  }
}
```

이 질의는 애플리케이션의 세 진입점 — 질의(`queryType`)·뮤테이션(`mutationType`)·서브스크립션(`subscriptionType`) — 의 이름을 준다. 이름은 클라이언트 편의를 위해 대개 자기설명적이므로, 이름만으로도 어떤 정보를 받을 수 있는지 짐작된다. 이어 모든 타입을 그 종류(`kind`)와 이름과 함께 얻고, 각 타입의 필드와 필드가 받는 인자까지 캐낸다. 예컨대 새 글을 만드는 뮤테이션이라면 `title`과 `content` 인자를 요구한다는 사실이 여기서 드러난다.

완전한 인트로스펙션 질의는 여기서 더 나아가 디렉티브의 이름·설명, 객체 사이의 관계, 각 필드의 상세 타입까지 뽑는다. 그 응답은 2,000줄에 이를 만큼 방대해서 사람이 손으로 훑기 어렵다. 이 지점에서 시각화 도구가 필요해진다. GraphQL Voyager는 인트로스펙션 응답이나 SDL 파일을 받아 질의·뮤테이션·서브스크립션과 그 사이의 관계를 그림으로 보여준다. 이 시각화에서 **객체 사이의 순환 관계** — `PasteObject`의 `owner` 필드가 `OwnerObject`를 가리키고, `OwnerObject`의 `paste` 필드가 다시 `PasteObject`를 가리키는 것 — 가 눈에 띈다. 이 순환은 40.2절이 다룰 DoS의 씨앗이다.

인트로스펙션의 산출물인 스키마는 이 부의 뒤 장에서 계속 쓰인다. **40.7~40.8절의 인가 테스트가 바로 이 스키마를 입력으로 삼는다.** 어떤 질의·뮤테이션이 있는지 알아야 그것들에 인가가 제대로 걸렸는지 시험할 수 있기 때문이다. 정찰이 뽑은 지도가 곧 공격의 좌표가 된다.

네트워크 규모로 인트로스펙션 활성 여부를 확인할 때는 `graphql-introspection` Nmap NSE 스크립트를 쓴다. 이 스크립트는 `__schema` 메타필드가 가져와지는지를 검사해 대상이 인트로스펙션을 허용하는지를 보고한다. 다만 이것은 첫 단계일 뿐이고, 실제 스키마 추출은 더 견고한 질의로 별도로 해야 한다 — 그 자동화가 39.4절의 InQL이다.

## 39.3 GraphQL 구현체 핑거프린팅

앞에서 GraphQL 구현체가 언어별로 여럿 존재함을 봤다. Apollo(TypeScript), Graphene(Python), graphql-ruby(Ruby), Sangria(Scala), Juniper(Rust), HyperGraphQL(Java) 등이다. 서버에서 도는 것이 어느 구현체인지 알면 그 구현체의 알려진 취약점·기본 설정·보안 통제를 조사해 정확한 공격을 계획할 수 있다. 대상이 어느 구현체인지 알아내는 작업이 **서버 핑거프린팅**이다.

이것은 새로운 문제가 아니다. **25.6절이 다룬 서버 핑거프린팅의 GraphQL판이다.** 25.6절의 원리를 다시 불러오자. 많은 웹 서버가 `Server` 헤더에 버전을 흘리지만, 그 배너는 위조될 수 있다. 그럼에도 서버의 **다른 동작** — 헤더 순서, 비정상 요청에 대한 반응, 오류 응답의 형태 — 으로 소프트웨어를 판별할 수 있다. HTTP 명세에 선택적이거나 구현자 재량에 맡겨진 세부가 많고, 구현체마다 그것을 다르게 처리하기 때문이다. **자기 식별이 사라진 자리를 동작의 불일치가 메운다.**

GraphQL은 이 원리가 극단적으로 들어맞는 표적이다. `HEAD` 요청으로 `Server` 헤더를 읽는 고전 기법은 GraphQL 구현체를 거의 식별하지 못한다. 대신 핑거프린팅은 다음 네 종류의 불일치를 관찰한다.

- 오류 메시지의 불일치
- 잘못된 GraphQL 질의에 대한 응답 출력의 불일치
- 정상 질의에 대한 응답 출력의 불일치
- 명세를 벗어난 질의에 대한 응답 출력의 불일치

이 네 요소를 종합하면 구현체를 유일하게 식별할 수 있다. 구체적으로 보자. 다음은 `query`에 여분의 `y`를 붙여 명세를 위반한 질의다.

```graphql
queryy {
  __typename
}
```

Scala 기반 Sangria는 이렇게 답한다.

```json
{
  "syntaxError": "Syntax error while parsing GraphQL query. Invalid input \"queryy\", expected ExecutableDefinition or TypeSystemDefinition (line 1, column 1):\nqueryy {\n^",
  "locations": [ { "line": 1, "column": 1 } ]
}
```

Java 기반 HyperGraphQL은 같은 질의에 전혀 다르게 답한다.

```json
{
  "extensions": {},
  "errors": [
    {
      "message": "Validation error of type InvalidSyntax: Invalid query syntax.",
      "locations": [ { "line": 0, "column": 0, "sourceName": null } ],
      "validationErrorType": "InvalidSyntax",
      "errorType": "ValidationError"
    }
  ]
}
```

두 응답은 **모든 면에서 다르다.** 최상위 키 이름(`syntaxError` 대 `errors`), 위치 표기 방식(`line 1` 대 `line 0`), 추가 필드의 유무. 이 차이만으로 두 구현체를 구별할 수 있다. DVGA에 같은 질의를 보내면 또 다른 응답이 오는데, DVGA가 Python 기반 Graphene을 쓰기 때문이다.

**표 39-1. 명세 위반 질의에 대한 구현체별 응답 차이 (BHGQL 4장 기준)**

| 구현체 | 언어 | 특징적 응답 |
|---|---|---|
| Sangria | Scala | 최상위 `syntaxError` 키, `expected ExecutableDefinition...` 문구 |
| HyperGraphQL | Java | `errors` 배열 + `validationErrorType`·`errorType` 확장 필드 |
| Graphene | Python | 위 둘과 또 다른 형태 (`Cannot query field ...`) |

손으로 질의를 보내며 차이를 분석하는 것은 규모가 커지지 않는다. 그래서 이 핑거프린팅 능력은 도구에 내장된다. graphw00f가 현재 유일한 GraphQL 서버 핑거프린팅 도구로, 24종 이상의 구현체를 시그니처 데이터베이스와 대조해 식별한다. 탐지(`-d`)와 핑거프린팅(`-f`)을 함께 돌릴 수 있다.

```
# python3 main.py -f -t http://localhost:5013/graphql

  [*] Checking if GraphQL is available at http://localhost:5013/graphql...
  [!] Found GraphQL.
  [*] Attempting to fingerprint...
  [*] Discovered GraphQL Engine: (Graphene)
  [!] Attack Surface Matrix: https://github.com/nicholasaleks/graphql-threat-matrix/...
  [!] Technologies: Python
```

graphw00f는 구현체를 식별한 뒤 **공격 표면 매트릭스** 링크를 준다. 이것은 GraphQL Threat Matrix에 담긴, 각 구현체의 보안 태세 지식이다. 어떤 기능이 기본으로 켜져 있는지, 어떤 보안 통제가 존재하는지가 정리되어 있다. Graphene의 매트릭스에는 다음 같은 항목이 나온다.

- **필드 제안(Field Suggestions)**: 오타 난 질의에 대안을 제안한다. **정보 노출에 악용된다**(→ 39.5).
- **질의 깊이 제한(Query Depth Limit)**: 순환 관계를 악용한 DoS를 막는 보안 통제(→ 40.6).
- **질의 비용 분석(Query Cost Analysis)**: 계산량이 큰 질의로 인한 DoS를 막는 보안 통제(→ 40.6).
- **인트로스펙션(Introspection)**: 스키마 정보를 노출할 수 있다(→ 39.2).
- **디버그 모드(Debug Mode)**: 응답에 추가 정보를 실어 정보 노출을 일으킬 수 있다(→ 39.7).
- **배치 요청(Batch Requests)**: 한 HTTP 요청에 질의를 여럿 담는 기능. DoS의 좋은 벡터(→ 40.4).

핑거프린팅의 요점은 여기서 드러난다. **구현체마다 오류 메시지와 동작이 다르다는 사실 자체가 지문이 되고, 동시에 그 구현체가 어떤 기본값을 갖는지가 곧 다음 공격의 지도가 된다.** 성숙한 구현체일수록 보안 기능이 많고, 오래된 것일수록 빈틈이 많다. 어느 구현체인지 아는 것이 곧 이점이다.

> **이 절이 뒷받침하는 것**
>
> - 동작 불일치 기반 핑거프린팅 → **25.6** (서버 핑거프린팅 — 같은 원리, 자기 식별이 사라진 자리를 동작이 메운다)
> - 식별된 구현체의 기본값 → **39.5**(필드 제안), **39.7**(디버그 모드), **40.6**(깊이·비용 제한)
> - 알려진 취약점 검색 → **40.9** (공개된 취약점 사례 연구)

## 39.4 InQL로 스키마 추출 자동화

인트로스펙션이 켜져 있을 때, 스키마를 손으로 뽑아 정리하는 것은 번거롭다. InQL은 이 과정을 자동화한다. 38.4절에서 설치한 도구다.

InQL은 39.2절에서 본 것과 비슷한 단일 인트로스펙션 질의를 보내고, 그 결과로 HTML·JSON·TSV 여러 형식의 스키마 문서를 생성한다. 이 문서들은 GraphQL Voyager 같은 시각화 도구와 함께 쓰거나, 명령줄에서 후속 자동화의 입력으로 쓴다.

```
# inql -t http://localhost:5013/graphql --generate-tsv

[+] Writing Introspection Schema JSON
[+] DONE
[+] Writing HTML Documentation
[+] DONE
[+] Writing query Templates
```

InQL은 대상 도메인 이름으로 디렉터리를 만들고 그 안에 질의·뮤테이션·서브스크립션별 스키마 파일을 남긴다. TSV(탭 구분) 형식은 명령줄 도구로 다루기 좋다. `awk`로 질의 이름만 뽑을 수 있다.

```
# awk '{print $1}' endpoint_query.tsv | tail -n +2

audits
paste
readAndBurn
pastes
```

인자까지 함께 보려면 탭을 구분자로 지정한다.

```
# awk -F'\t' '{print $1, $2}' endpoint_query.tsv

Operation Name  Args Name
audits
paste           id, title
readAndBurn     id
pastes          filter, limit, public
```

각 질의가 받는 인자가 드러난다. `paste`는 `id`·`title`을, `pastes`는 `filter`·`limit`·`public`을 받는다. 이 인자 목록이 중요한 이유는 39.2절에서 말한 대로다 — 인자를 받는 질의가 인젝션·SSRF·인가 우회의 진입점이다. TSV로 뽑아 두면 퍼징·무차별 대입·민감 정보 검색 같은 후속 작업을 스크립트로 돌리기 쉽다.

InQL의 산출물은 두 방향으로 이어진다. **부록 H**의 정찰 체크리스트가 이 스키마 추출을 정찰의 표준 절차로 정리하고, **부록 B**의 자동화 절차가 추출된 스키마를 입력으로 삼는 퍼징·무차별 대입을 다룬다. 그리고 이렇게 뽑은 스키마는 40.7~40.8절의 인가 테스트로 넘어간다. 도구는 스키마를 자동으로 뽑아 줄 뿐, 그것으로 무엇을 겨눌지는 정찰자가 판단한다.

## 39.5 인트로스펙션이 비활성일 때 — 필드 제안, 필드 스터핑, `__type` 타입 스터핑

여기가 이 장의 절정이다.

언젠가 인트로스펙션이 꺼진 GraphQL API를 만난다. 개발자가 스키마 노출을 막으려 인트로스펙션을 끈 것이다. 상식적으로는 스키마가 감춰졌으니 정찰이 막혀야 한다. 그런데 막히지 않는다. 이 절이 보이는 것은, **인트로스펙션이라는 기능을 껐음에도 스키마 정보가 다른 채널로 계속 새어 나온다**는 사실이다. 그리고 그 채널의 핵심은 필드 제안 — 오타를 교정해 주는 개발 편의 기능이다.

이 구조를 이 책의 논지로 판정하자. **"기능을 끄는 것"과 "정보를 감추는 것"은 다르다.** 인트로스펙션을 끄는 것은 스키마를 물어보는 **한 창구**를 닫는 것이지, 스키마 정보 자체를 감추는 것이 아니다. 정보는 여전히 서버의 동작 곳곳에 배어 있고, 다른 창구로 흘러나온다. 이것은 30.4절이 "정보 누출 방어"에서 말한 원리 — 오류를 **가리는 것**과 결함을 **고치는 것**은 다르다 — 와 정확히 같은 구조다. 그리고 30.3절이 "추론을 통한 정보 수집"에서 말한 것 — 오류 메시지가 없어도 응답의 관찰 가능한 차이가 정보를 준다 — 과도 같은 뿌리다. 인트로스펙션을 끄는 것은 오류 메시지를 커스텀 페이지로 가리는 것에 대응하고, 필드 제안을 통한 스키마 복원은 시간차·상태 코드를 통한 추론에 대응한다.

### 39.5.1 비활성 인트로스펙션 탐지와 `__type` 우회

먼저 인트로스펙션이 정말 꺼졌는지 확인한다. `__schema` 질의를 보내면, 꺼져 있을 때 오류가 온다. 다만 처리 방식은 구현체마다 다르다 — 어떤 것은 오류 메시지 없이 `400 Bad Request`만 주고, 어떤 것은 `200 OK`에 `Introspection is Disabled` 같은 메시지를 담는다. 대개는 후자다. DVGA를 Expert(강화) 모드로 두고 인트로스펙션 질의를 보내면 이렇게 답한다.

```json
{
  "errors": [
    {
      "message": "400 Bad Request: Introspection is Disabled",
      "path": ["__schema"]
    }
  ],
  "data": null
}
```

Apollo Server라면 더 친절하게, 인트로스펙션을 켜는 방법까지 오류에 담아 알려준다. 그런데 여기서 첫 번째 우회가 나온다. 많은 구현체가 인트로스펙션을 막을 때 **`__schema` 키워드만 필터링한다.** 그러나 인트로스펙션 메타필드는 `__schema`만이 아니다. **`__type` 메타필드**도 타입 정보를 뽑을 수 있다.

2022년 5월, AWS AppSync에서 정확히 이 빈틈이 발견됐다. AppSync는 WAF로 보호되고, 그 WAF 룰 중 하나가 `__schema`를 담은 요청을 차단했다. 그러나 룰이 `__schema`만 볼 뿐 다른 인트로스펙션 메타필드는 고려하지 않았다. 룰의 핵심은 이런 형태였다.

```json
{
  "ByteMatchStatement": {
    "FieldToMatch": { "Body": {} },
    "PositionalConstraint": "CONTAINS",
    "SearchString": "__schema"
  }
}
```

본문(`Body`)에 `__schema`가 **포함(CONTAINS)** 되면 차단하는 룰이다. 그러니 `__type`을 쓰면 룰에 걸리지 않고 통과한다. 이 사례가 30.10.3에서 짚은 것 그대로다 — **`__schema` 차단은 "오류를 가리는 것"에 해당하고, `__type` 우회는 그것이 "결함을 고치는 것"이 아님을 증명한다.** 12.11절이 WAF의 한계로 다룬 것 — WAF는 알려진 패턴을 막을 뿐 결함 자체를 없애지 못한다 — 가 GraphQL에서 반복되는 자리다.

인트로스펙션이 허술하게 막혔는지 확인하는 카나리아 질의는 `__type`을 쓴다.

```graphql
{
  __type(name: "Query") {
    name
  }
}
```

질의 루트 타입의 이름은 언제나 `Query`이므로, 인트로스펙션이 제대로 막히지 않았다면 응답은 정확히 이렇게 온다.

```json
{
  "data": {
    "__type": {
      "name": "Query"
    }
  }
}
```

이 예측된 응답이 오면, `__type`으로 스키마를 캐낼 수 있다는 뜻이다. 그리고 비운영 환경도 잊지 말아야 한다. 운영에서 인트로스펙션이 꺼졌어도 `staging`·`dev` 서브도메인에서는 켜져 있을 수 있고, 거기서 얻은 스키마는 운영과 대개 비슷하다.

### 39.5.2 필드 제안 — 개발 편의가 정보 노출 채널이 되는 전형

**필드 제안(field suggestion)** 은 클라이언트가 오타를 보내면 서버가 존재하는 필드를 제안해 주는 기능이다. REST가 잘못된 질의에 `400 Bad Request`로 답하는 것과 달리, GraphQL은 훨씬 친절하게 "혹시 이걸 원했나요?"라고 되묻는다. 이 기능은 **명세의 일부가 아니지만** 오늘날 대다수 구현체가 채택하고 있다.

DVGA에 `title`을 `titlr`로 오타 내 보내면 이렇게 답한다.

```json
{
  "errors": [
    {
      "message": "Cannot query field \"titlr\" on type \"PasteObject\". Did you mean \"title\"?"
    }
  ]
}
```

`Cannot query field ... Did you mean ...?`라는 이 메시지가 스키마의 실제 필드 이름 `title`을 흘린다. 개발자에게는 오타를 잡아 주는 고마운 기능이지만, 공격자에게는 스키마를 한 글자씩 캐내는 창구다. **인트로스펙션이 꺼져 있어도 필드 제안은 스키마를 조금씩 누설한다** — 이것이 이 절의 핵심이다.

필드 제안이 작동하는 방식을 알면 무차별 대입을 최적화할 수 있다. 서버는 **편집 거리(edit-distance)** 알고리즘으로 오타와 유효 필드의 유사도를 잰다. 두 문자열을 맞추는 데 필요한 문자 연산(추가·교체·삭제)의 수가 편집 거리다. `titlr`를 `title`로 맞추려면 `r`을 `e`로 교체하는 한 번의 연산이면 되므로 편집 거리는 1이다.

**표 39-2. 두 문자열 사이의 편집 거리 (BHGQL 표 6-1 기준)**

| 원래 이름 | 오타 | 필요한 연산 | 편집 거리 |
|---|---|---|---|
| `title` | `titl` | `e` 추가 | 1 |
| `content` | `rntent` | `r`→`c` 교체, `o` 추가 | 2 |

구현체는 가변 임계값으로 제안 여부를 결정한다. GraphQL의 참조 구현 GraphQL.js는 이렇게 계산한다.

```
const threshold = Math.floor(input.length * 0.4) + 1;
```

입력 길이에 0.4를 곱하고 내림한 뒤 1을 더한다. 일곱 글자 `content`라면 편집 거리 임계값이 3 이하일 때 제안이 뜬다. 이 공식을 알면 무차별 대입 워드리스트를 임계값 안에 들도록 다듬어 적중률을 높일 수 있다.

필드 제안을 활용하는 두 가지 사실이 더 있다. **첫째, 오타 하나가 여러 필드를 반환할 수 있다.** `owner` 대신 `owne`로 오타 내면, `owne`가 `owner`와 `ownerId` 둘 다의 편집 거리 임계값 안에 들어 둘 다 제안된다.

```json
{
  "errors": [
    {
      "message": "Cannot query field \"owne\" on type \"PasteObject\". Did you mean \"owner\" or \"ownerId\"?"
    }
  ]
}
```

**둘째, 한 요청에 담을 수 있는 오타의 수에 제한이 없다.** 여러 오타 필드를 한 질의에 몰아넣으면, 서버는 각각에 대해 제안을 돌려준다.

```graphql
query {
  pastes {
    tte
    tent
    bli
    urn
  }
}
```

응답은 네 오타 각각에 대한 제안을 담아 온다 — `tte`→`title`, `tent`→`content`, `bli`→`public`, `urn`→`burn`. 한 요청으로 필드 넷을 복원한 것이다. 이 동작이 **대량 정보 수집**을 가능하게 한다. 여기에 배치 질의(→ 40.4)를 겹치면 한 HTTP 요청에 여러 요청을 묶어 더욱 최적화할 수 있다.

이 취약점을 둘러싼 흥미로운 사실이 하나 있다. 2019년 11월 GraphQL.js에 이 문제를 지적하는 이슈가 올라왔고, 공동 창시자 Lee Byron은 "인트로스펙션을 끈 스키마라면 `didYouMean`(필드 제안)도 함께 꺼야 한다"고 논평했다. 그러나 그 의견을 반영해 인트로스펙션이 꺼지면 필드 제안도 끄는 풀 리퀘스트가 올라온 것은 **2년도 더 지난 2022년 1월**이었다. 이것이 알려주는 것 두 가지. 오픈소스·커뮤니티 주도 기술에서 중대한 보안 우려가 빠르게 패치되지는 않는다는 것, 그리고 참조 구현이 고쳐져도 모든 서버 구현과 운영 배포에 퍼지는 데는 오랜 시간이 걸린다는 것. 그래서 지금도 이 채널은 대부분의 배포에서 열려 있다.

### 39.5.3 필드 스터핑 — 필드가 데이터베이스 컬럼에 대응한다는 도박

인트로스펙션과 필드 제안이 **둘 다** 꺼졌다면 어떻게 하는가. **필드 스터핑(field stuffing)** 이 답이다. 필드 목록을 질의에 밀어 넣어, 존재하는 필드가 걸리기를 기대하는 기법이다.

이 기법이 노리는 것은 **GraphQL 객체의 필드가 데이터베이스 컬럼과 가깝게 대응한다**는 경향이다. Burp Suite로 정상 사용자 트래픽을 가로채 다음 같은 질의를 잡았다고 하자.

```graphql
query {
  user {
    name
  }
}
```

`user` 객체의 `name` 필드가 현재 로그인한 계정 이름을 돌려준다. 인트로스펙션이 꺼져 있으니 `user` 객체에 다른 어떤 필드가 있는지 알 수 없다. 그러나 `user` 테이블이 데이터베이스에서 어떤 모습일지는 추측할 수 있다.

**표 39-3. 데이터베이스 스키마와 GraphQL 타입·필드의 대응 (BHGQL 표 6-2 기준)**

| MySQL 스키마 | GraphQL 타입·필드 |
|---|---|
| `id BIGINT(20)` | `User.id (Int)` |
| `name VARCHAR(50)` | `User.name (String)` |
| `email VARCHAR(50)` | `User.email (String)` |
| `password_hash VARCHAR(32)` | `User.password_hash (String)` |
| `api_key VARCHAR(50)` | `User.api_key (String)` |

공격자는 데이터베이스 스키마를 미리 알 수 없지만, 추가 컬럼이 무엇일지 **교육된 추측**을 하고 그 필드 이름들을 질의에 밀어 넣는다.

```graphql
query {
  user {
    name
    username
    address
    password
    ssn
    apiKey
    token
    emailAddress
  }
}
```

운이 좋으면 이 중 하나가 실제로 해석되어 데이터를 반환하거나, 편집 거리 안에서 대안 필드 이름을 제안받는다. 수백 개의 필드 이름을 한 질의에 담는 것은 눈을 가린 채 다트를 던지는 것과 같다 — 그러나 던질 다트가 수백 개다.

필드 이름의 **표기법**에 주의해야 한다. SDL 파일에서 필드는 흔히 `snake_case`(예: `api_key`)로 정의되지만, 클라이언트로 질의할 때는 `camelCase`(예: `apiKey`)로 보일 수 있다. 일부 구현체가 표기법을 자동 변환하기 때문이다. 다만 이 관례는 유지보수자가 바꿀 수 있으므로 두 표기법을 모두 시험한다.

### 39.5.4 `__type` 타입 스터핑

`__type` 메타필드가 막히지 않았다면(39.5.1), 필드 스터핑과 같은 발상을 타입 이름에 적용할 수 있다. **`__type`의 `name` 인자에 타입 이름 후보를 밀어 넣는 것**이다. 알려진 타입 이름 하나로 시작해 그 타입의 필드 목록을 통째로 뽑는다.

```graphql
{
  __type(name: "PasteObject") {
    name
    fields {
      name
    }
  }
}
```

응답은 `PasteObject`의 모든 필드 이름을 준다 — `id`, `title`, `content`, `public`, `userAgent`, `ipAddr`, `ownerId`, `burn`, `owner`. 인트로스펙션 전체는 막혔지만 `__type` 하나로 타입의 내부가 열린 것이다. 이제 필드 스터핑에서처럼 존재할 법한 타입 이름을 하나씩 시험한다. GraphQL의 타입 이름은 대개 `UpperCamelCase`(예: `PrivatePasteProperties`)로 쓰이므로, 그 관례에 맞춰 후보를 만든다.

세 기법 — 필드 제안, 필드 스터핑, 타입 스터핑 — 을 종합하면 인트로스펙션이 꺼진 스키마도 조각조각 복원된다. 손으로 하는 것은 39.6절의 도구가 자동화한다.

> **이 절이 뒷받침하는 것**
>
> - 기능을 끄는 것 ≠ 정보를 감추는 것 → **30.4** (정보 누출 방어 — 가리는 것과 고치는 것은 다르다)
> - 오류 없이도 관찰로 정보를 얻음 → **30.3** (추론을 통한 정보 수집)
> - `__schema`만 막는 WAF 룰의 한계 → **12.11** (WAF의 한계), **30.10.3** (같은 사례를 정보 노출 관점에서)
> - 필드 스터핑의 무차별 대입 발상 → **25.3** (숨겨진 콘텐츠 발견)

> **이 책의 범위를 넘어서**
>
> 필드 제안을 이용한 스키마 복원의 정확한 확률, 편집 거리 임계값을 최적화한 워드리스트 설계, 그리고 자동화 도구의 현재 버전별 옵션은 이 책의 범위 밖이다. 또한 automatic persisted query(질의를 해시로 갈음하는 캐싱·허용목록 메커니즘)는 필드 제안·스터핑과 다른 축의 주제이므로 여기서 다루지 않는다 — 그것의 방어적 활용은 40.6절의 질의 허용목록에서만 짧게 언급한다. 이 절의 목표는 도구 사용법이 아니라, **기능을 껐다는 것이 정보를 감췄다는 뜻이 아니라는 구조**를 보이는 데 있다.

## 39.6 Clairvoyance로 필드 제안·스터핑 자동화

39.5절의 필드 제안과 필드 스터핑을 손으로 하는 것은 규모가 커지지 않는다. Clairvoyance가 이 둘을 자동화해, **인트로스펙션 없이 스키마 전체를 재구성**한다.

Clairvoyance는 워드리스트를 입력으로 받아 그 내용을 여러 GraphQL 질의에 스터핑하고, 유효한 오퍼레이션·필드·인자·입력 타입을 식별한다. 내부적으로는 **정규식으로 오류 메시지의 필드 제안을 파싱**한다 — 즉 39.5.2에서 본 필드 제안 채널을 기계적으로 긁어 모으는 것이다. 워드리스트를 다 훑고 나면 스키마를 출력한다.

```
# python3 -m clairvoyance http://localhost:5013/graphql \
    -w ~/high-frequency-vocabulary/30k.txt -o clairvoyance-dvga-schema.json
```

`-w`가 워드리스트를, `-o`가 출력 스키마 파일을 지정한다. DVGA를 Expert(강화) 모드로 — 즉 인트로스펙션을 끈 채로 — 두고 돌려야 이 도구의 진가가 드러난다. 실행이 끝나면 `clairvoyance-dvga-schema.json`이 생기는데, 이것을 인트로스펙션으로 뽑은 원래 스키마와 GraphQL Voyager에서 나란히 비교하면, **Clairvoyance가 거의 모든 필드와 오퍼레이션을 복원**했음이 드러난다. 인트로스펙션이 꺼진 애플리케이션치고는 놀라운 결과다. 이것이 39.5절의 논지에 대한 실증이다 — 기능은 껐지만 정보는 감춰지지 않았다.

도구는 워드리스트만큼만 강하다. 필드·오퍼레이션·인자 이름을 맞히는 작업이므로 일반 영어 사전 단어 목록이 잘 맞는다(비밀번호·디렉터리용 워드리스트가 아니라). 대상이 영어권이 아니면 그 언어의 워드리스트를 쓴다. 나아가 대상 자체에서 워드리스트를 만드는 것이 가장 효과적이다. CeWL 같은 도구로 애플리케이션 프런트엔드 HTML에서 키워드를 긁어내 30,000단어 목록과 병합하면, 그 애플리케이션 고유의 용어까지 적중 범위에 들어온다.

Clairvoyance와 InQL(39.4)의 관계를 정리하자. 인트로스펙션이 **켜져 있으면** InQL로 스키마를 통째로 자동 추출한다. **꺼져 있으면** Clairvoyance로 필드 제안·스터핑을 자동화해 스키마를 재구성한다. 둘 다 산출물은 스키마이며, 그 스키마는 40.7~40.8절의 인가 테스트로 넘어간다. 이 도구들의 절차적 위치는 **부록 H**(정찰 체크리스트)와 **부록 B**(자동화)가 정리한다.

## 39.7 오류 메시지 남용

30.1~30.2절이 오류 메시지 익스플로잇을, 30.10절이 그 GraphQL판을 정보 노출 관점에서 다뤘다. 이 절은 같은 것을 **정찰 절차**의 관점에서, 즉 오류를 능동적으로 유발해 정보를 캐내는 작업으로 본다.

GraphQL 오류 메시지는 장황하다. 개발자 경험을 위해 GraphQL은 기본적으로 클라이언트에게 많은 것을 알려주도록 설계되었고, 그 친절함이 곧 정찰의 표면이다. 명세에 따르면 GraphQL 오류 응답은 표준 HTTP 상태 코드를 요구하지 않고, 대개 세 필드 — `message`, `location`, `path` — 를 담는다. 필수 title 인자를 빠뜨린 뮤테이션을 DVGA에 보내면 이렇게 답한다.

```json
{
  "errors": [
    {
      "message": "mutate() missing 1 required positional argument: 'title'",
      "locations": [ { "line": 2, "column": 3 } ],
      "path": ["createPaste"]
    }
  ],
  "data": { "createPaste": null }
}
```

각 필드가 무엇을 주는지 보자.

- **`message`**: 오류의 고수준 설명. **대부분의 정보 노출이 이 필드에서 일어난다.** 여기서는 뮤테이션이 `title` 인자를 빠뜨렸다고 알려주는데, 이것 자체가 스키마 정보(필수 인자의 존재)의 누설이다.
- **`location`**: 오류가 GraphQL 문서의 몇 줄 몇 열에서 났는지. 들여쓴 공백도 열 계산에 포함된다.
- **`path`**: 어느 필드에서 오류가 났는지. `null` 결과가 의도된 것인지 런타임 오류인지 구별하는 데 쓰인다.
- **`extensions`**: 구현체·플러그인이 `message`·`location`·`path`를 확장하는 데 쓰는 예약 필드. 오류 코드, 타임스탬프, **스택 트레이스**, 레이트 리밋 정보가 흔히 담긴다.

오류를 능동적으로 유발하면 훨씬 민감한 것이 나온다. 온라인 서점 API에 이미 존재하는 사용자명으로 회원 생성 뮤테이션을 보내면, `message`가 데이터베이스에서 곧장 나온다.

```json
{
  "errors": [
    {
      "message": "(sqlite3.IntegrityError) UNIQUE constraint failed: users.username\n[SQL: INSERT INTO users (username, password) VALUES (?, ?)]\n[parameters: ('tom', 'secret')]",
      "path": ["createUser"]
    }
  ]
}
```

이 한 응답이 과도하게 공유하는 것을 보라. SQLite3 데이터베이스에서 나온 **SQL 문 전체**, `username` 컬럼, 그리고 삽입 시 암호화되지 않는 `password` 컬럼. 이 하나의 오류로 데이터베이스를 핑거프린팅하고(→ 27.3), 유효 계정을 열거할 실마리를 얻으며, SQL 질의 구조를 알아 인젝션을 미세 조정할 수 있다(→ 27.14). 이것은 30.1의 백엔드 DB 메시지 노출과 30.2의 정보성 오류 유도가 GraphQL에서 정확히 재현된 것이다.

정찰의 절차는 **퍼징**이다. 잘못된 형식의 질의를 보내거나, 특수문자를 엉뚱한 자리에 넣거나, GraphQL에 이례적인 HTTP 메서드(`PUT` 같은)로 질의를 보내면, 서버가 예상 못 한 처리 오류를 뱉을 수 있다. 이때 `errors`나 `extensions` 키의 비표준 출력을 노려본다. 여러 시험 케이스를 계속 던져 무언가 걸릴 때까지 시도하는 것이 요령이다.

디버그 모드가 켜지면 오류는 더 많은 것을 준다. 표준 오류 대신 상세 스택 트레이스가 돌아온다. 일부 구현체는 디버그 모드가 기본으로 켜져 있거나, 쿠키·URL 파라미터로 켤 수 있게 열어 둔다 — 예컨대 `?debug=1` 같은 파라미터다. 개발자는 스테이징·개발 환경에서 디버그를 켜 두는 일이 많으므로 비운영 서브도메인을 함께 시험한다.

스택 트레이스는 정찰의 노다지다. 예외가 났을 때 애플리케이션이 실행한 함수 호출의 사슬로, 의존성·소프트웨어 버전·프레임워크·소스 코드 조각·파일시스템 경로·사용자 계정·운영체제까지 드러낸다. 여기서 39.1.1의 관찰 — **엔드포인트마다 설정이 다르다** — 가 결정적이 된다. DVGA의 `/graphql` 엔드포인트는 스택 트레이스를 던지지 않지만, `/graphiql` 엔드포인트는 던진다. 개발자가 그래픽 인터페이스를 디버깅에 쓴다고 가정해 그 엔드포인트에만 상세 오류를 켜 둔 것이다. `env` 쿠키를 `graphiql:enable`로 바꿔(39.1.3) `/graphiql`에서 오타 질의를 보내면 스택 트레이스가 딸려 온다.

```json
{
  "errors": [
    {
      "message": "Cannot query field \"titled\" on type \"PasteObject\". Did you mean \"title\"?",
      "extensions": {
        "exception": {
          "stack": [
            " File \"/Users/dvga-user/Desktop/Damn-Vulnerable-GraphQL-Application/venv/lib/python3.x/site-packages/gevent/baseserver.py\", line 34, ...",
            " File \"/Users/dvga-user/Desktop/Damn-Vulnerable-GraphQL-Application/venv/lib/python3.x/site-packages/flask/app.py\", line 2464, ..."
          ]
        }
      }
    }
  ]
}
```

파일 경로에서 사용자 계정(`dvga-user`), 운영체제, 프로젝트 구조, 프레임워크(gevent·Flask)와 그 버전이 한꺼번에 드러난다. 이 스택 트레이스는 30.1의 스택 트레이스와 똑같은 것 — 다만 REST가 아니라 GraphQL의 `extensions` 필드에 실려 온다. 하나의 서버에서 엔드포인트마다 다른 오류 설정을 갖는다는 사실이, **엔드포인트를 모두 시험해야 한다**는 39.1.1의 원칙을 뒷받침한다.

> **이 절이 뒷받침하는 것**
>
> - 오류 메시지 익스플로잇·유도 → **30.1, 30.2** (같은 기법의 고전판), **30.10** (정보 노출 관점의 개관)
> - SQL 문 노출 → **27.3** (DB 핑거프린팅), **27.14** (GraphQL 경유 SQL 인젝션)
> - 엔드포인트별 상이한 오류 설정 → **39.1.1** (엔드포인트를 각각 시험)

## 39.8 GET 기반 질의로 데이터 누출 — 캐시와 로그에 남는 것

마지막 통로는 HTTP 메서드 자체에 있다. 일부 GraphQL 구현체는 클라이언트가 **GET 메서드로 질의를 실행**하는 것을 허용한다. POST만 받는 구현체도 있지만, Scala 기반 Sangria처럼 GET으로 뮤테이션까지 허용하는 것도 있다.

GET의 문제는 단순하고 근본적이다. **GET은 데이터를 URL 쿼리 파라미터에 실어 나른다.** 다음은 DVGA에 전화번호를 담아 보내는 GET 질의다.

```
http://localhost:5013/graphql?query=query($phone: String)
{ paste(title: $phone) { id title } }&variables={"phone":"555-555-1337"}
```

`variables` 파라미터를 생략하고 값을 질의에 직접 넣을 수도 있다.

```
http://localhost:5013/graphql?query=query{ paste(title: "555-555-1337") { id title } }
```

전화번호는 실제 애플리케이션에서 PII다. 그런데 그것이 URL에 실렸다. **URL은 여러 곳에 남는다.** 이 하나의 사실이 GET 기반 질의를 정보 누출 통로로 만든다. 원서(BHGQL 6장)는 이 조건이 "직접 새로운 정보를 주지는 않지만 침투 테스트에서 반드시 지적해야 할 것"이라고 말한다. 이 책은 여기서 한 걸음 더 나아간다. **이것은 23.3절이 세션 토큰에 대해 말한 것과 완전히 같은 구조다.**

23.3.2절을 다시 불러오자. 애플리케이션이 세션 토큰을 쿠키나 POST 본문이 아니라 URL 쿼리 문자열로 나르면, 그 토큰은 무단 접근이 가능한 여러 곳에 남는다 — 브라우저 히스토리, 웹 서버 로그, 프록시 로그, 그리고 사용자가 외부 링크를 따라갈 때의 Referer 로그. GET 기반 GraphQL 질의에 담긴 PII는 정확히 같은 경로를 밟는다. URL에 놓인 민감 데이터는 그것이 세션 토큰이든 전화번호든 같은 방식으로 샌다. 남는 곳을 하나씩 짚자.

**표 39-4. GET 기반 질의의 URL이 남는 경로와 각 절의 대응**

| 남는 곳 | 무엇이 문제인가 | 이 책의 상세 |
|---|---|---|
| 공유·프록시 캐시 | GET 응답은 캐시 가능하다. 민감 응답이 공유 캐시에 저장되면 다른 사용자에게 새어 나간다 | → **14.8** (공유 캐시의 보안 함의) |
| 웹 서버 접근 로그 | Apache·Nginx 접근 로그가 URL 전체를 기록한다. PII·비밀이 로그에 평문으로 남는다 | → **16.4** (로그가 누출하는 것) |
| Referer 헤더 | 사용자가 외부 링크를 따라가면 현재 URL이 `Referer`에 실려 제3자 서버로 간다 | → **8.6** (헤더의 신뢰성 — Referer) |
| 브라우저 히스토리 | URL이 로컬 브라우저 히스토리에 남아 기기를 쓰는 다른 사람에게 노출된다 | → **36.1** (로컬 프라이버시 공격) |
| 경로상의 프록시 | 정방향·역방향 프록시가 URL을 로깅한다 | → **16.4**, **13장** (중간자) |

**캐시(→ 14.8).** GET은 HTTP에서 안전(safe)하고 캐시 가능한 메서드로 취급된다(→ 8.3.1). 그래서 GET 기반 질의의 응답은 공유 캐시에 저장될 수 있다. 14.8절이 다룬 공유 캐시의 위험 — 민감 응답이 캐싱되어 사용자 간에 응답이 혼동되는 것 — 이 GraphQL 응답에 그대로 적용된다. POST 질의는 기본적으로 캐시되지 않지만 GET 질의는 캐시된다는 이 차이가, 편의를 위해 GET을 켠 대가다.

**로그(→ 16.4).** 웹 서버 접근 로그는 요청 URL을 통째로 기록한다. 16.4절이 "로그가 누출하는 것"에서 다룬 핵심 — `GET` 쿼리 문자열에 담긴 비밀이 로그에 남는다 — 가 GraphQL 질의에서 재현된다. 로그는 도청 위치의 한 사람이 아니라 로그 파일에 접근 가능한 훨씬 넓은 범위에 열려 있다는 점에서(→ 23.3.2), 네트워크 도청보다 결과가 클 수 있다.

**Referer(→ 8.6).** 사용자가 GET 질의로 접근한 페이지에서 외부 링크를 클릭하거나 브라우저가 외부 리소스를 로드하면, 그 URL이 `Referer` 헤더에 실려 제3자에게 간다. 8.6절이 Referer를 "믿을 수 없는 헤더"로 다뤘다면, 여기서는 그 헤더가 **거꾸로 정보를 흘리는 통로**가 된다. 23.3.2절이 URL 세션 토큰의 Referer 누출을 다룬 것과 같은 메커니즘이다.

**브라우저 히스토리(→ 36.1).** URL은 로컬 브라우저 히스토리에 남는다. 36.1절이 "로컬 프라이버시 공격"에서 브라우징 히스토리를 다룬 것 그대로, 공유 기기나 침해된 기기에서 그 URL의 민감 데이터가 노출된다.

이 절의 결론을 이 책의 논지로 못 박자. GET 기반 질의는 GraphQL이 발명한 위험이 아니다. **URL에 민감 데이터를 두는 것**이라는 오래된 실수(→ 23.3.2)가, 클라이언트 편의를 위해 GET을 허용한 GraphQL 서버에서 다시 성립한 것이다. 방어 원리도 같다 — 민감 데이터를 URL에 두지 않고, 상태를 바꾸거나 민감한 질의는 POST로만 받는 것.

그리고 GET 허용은 정보 누출만의 문제가 아니다. **그것은 33.6절(GraphQL CSRF)의 전제이기도 하다.** 33.6절이 보인 대로, GraphQL 서버가 GET 질의를 허용하면 `<a>`·`<img>` 같은 무해해 보이는 HTML 태그가 모두 CSRF 벡터가 된다 — 이미지 태그 하나가 로드되는 것만으로 GET 질의가 발화하기 때문이다. GET을 켜는 한 번의 결정이 정보 누출과 요청 위조라는 두 개의 문을 동시에 연다. 정찰에서 "이 서버가 GET 질의를 받는가"를 확인하는 일이, 정보 노출과 CSRF 양쪽의 전제를 한 번에 확정하는 이유가 여기에 있다.

> **이 절이 뒷받침하는 것**
>
> - URL에 담긴 민감 데이터가 남는 경로 → **23.3.2** (URL 세션 토큰 — 완전히 같은 구조), **14.8**(캐시), **16.4**(로그), **8.6**(Referer), **36.1**(브라우저 히스토리)
> - GET 허용이 여는 또 하나의 문 → **33.6** (GraphQL CSRF의 전제)

## 이 장의 요약

- **GraphQL은 명세가 응답 구조를 규정한 덕에 네트워크에서 쉽게 탐지된다.** 유효 질의는 `data`를, 무효 질의는 `errors`를 담는다는 두 조건, 그리고 GET 요청에 대한 고정 오류 문자열이 자동 스캔의 신호가 된다. 단일 엔드포인트라는 예측 가능성은 찾을 곳을 하나로 줄여 공격자에게 유리하게 작용한다.
- **엔드포인트마다 보안 설정이 다를 수 있다.** `/graphql`이 잠겨 있어도 `/graphiql`은 스택 트레이스를 던진다. 같은 호스트에서 GraphQL을 받는 엔드포인트를 둘 이상 찾으면 반드시 각각 시험한다.
- **인트로스펙션은 스키마 전체를 한 질의로 넘겨준다.** 진입점(질의·뮤테이션·서브스크립션)과 각 필드의 인자까지 캐내면, 그것이 곧 인젝션·인가 테스트의 좌표가 된다(→ 40.7~40.8). InQL이 이 추출을 자동화한다.
- **구현체마다 오류 메시지와 동작이 다르다는 사실 자체가 지문이다.** `Server` 헤더로 못 잡는 GraphQL 서버를, 명세 위반 질의에 대한 서로 다른 오류 출력으로 유일하게 식별한다. 이것은 25.6절 서버 핑거프린팅의 GraphQL판이며, graphw00f가 그 불일치를 데이터베이스화했다.
- **기능을 끄는 것과 정보를 감추는 것은 다르다.** 인트로스펙션을 껐어도 필드 제안이 오타 교정을 빌미로 스키마를 한 필드씩 흘리고, 필드 스터핑·타입 스터핑이 존재할 법한 이름을 밀어 넣어 스키마를 복원한다. Clairvoyance가 이 복원을 자동화한다. 이는 30.4의 "가리는 것과 고치는 것은 다르다", 30.3의 "추론을 통한 정보 수집"과 같은 구조다.
- **`__schema`만 막는 방어는 `__type`으로 우회된다.** 2022년 AWS AppSync의 WAF 룰이 이 빈틈을 드러냈다. 알려진 패턴 하나를 차단하는 것이 결함을 없애는 것이 아니라는 12.11절 WAF의 한계가 GraphQL에서 반복된다.
- **GraphQL 오류는 장황하다.** `message` 필드가 SQL 문 전체를, `extensions` 필드가 스택 트레이스를 넘겨준다. 오류를 능동적으로 유발하는 퍼징이 정찰의 절차이며, 이는 30.1~30.2의 오류 익스플로잇을 정찰 관점에서 다시 쓴 것이다.
- **GET 기반 질의는 URL에 민감 데이터를 남긴다.** 캐시(→ 14.8), 로그(→ 16.4), Referer(→ 8.6), 브라우저 히스토리(→ 36.1)에 남는 그 경로는, 23.3절이 URL 세션 토큰에 대해 말한 것과 완전히 같은 구조다. 그리고 GET 허용은 33.6절 GraphQL CSRF의 전제이기도 하다.

## 이어지는 장

이 장은 대상의 지도를 그렸다. 어떤 엔드포인트가 GraphQL을 받고, 어떤 구현체가 돌며, 스키마에 어떤 질의·뮤테이션·필드·인자가 있는지 — 인트로스펙션이 켜졌든 꺼졌든 — 를 알아냈고, 오류와 GET 질의가 흘리는 것까지 주웠다. 이 지도가 없으면 다음 장의 공격은 눈먼 채 던지는 다트가 된다.

40장은 이 지도 위에서 실제 공격을 실행한다. 이 장이 인트로스펙션으로 뽑고 필드 스터핑으로 복원한 스키마가, 40.7~40.8절의 **인증·인가 테스트**에서 좌표로 쓰인다. 어떤 뮤테이션이 있는지 알아야 그것에 인가가 걸렸는지 시험할 수 있기 때문이다. 그리고 39.2절에서 GraphQL Voyager로 본 객체 사이의 **순환 관계**, 39.3절의 핑거프린팅이 알려준 **깊이·복잡도 제한의 유무**가, 40장이 새로 여는 **서비스 거부(DoS)** 의 전제가 된다. 클라이언트가 질의 구조를 통제한다는 GraphQL의 유일한 새 위험이, 정찰이 확인한 방어의 빈틈과 만나 자원 소모 공격으로 구체화된다.

그리고 이 장이 확인한 GET 허용은 40장을 건너 33.6절 CSRF로도, 39.7절의 SQL 문 노출은 27.14절 인젝션으로도 이어진다. 정찰이 그은 선들이 이 부의 나머지 공격 전부의 출발점이다. 40장은 그중 DoS·인가·공개 취약점 사례를 실습으로 닫고, 부록 H가 이 장과 40장의 절차 전체를 체크리스트로 정리한다.
