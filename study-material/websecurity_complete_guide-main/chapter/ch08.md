# 8장. HTTP 메시지: 메서드, 상태 코드, 헤더

> **이 장에서 다루는 것**
>
> - HTTP 메시지의 세 부분이 각각 어디서 끝나며, 그 끝을 무엇이 표시하는지
> - 메서드가 약속하는 의미와, 그 약속을 강제하는 주체가 프로토콜이 아니라는 사실
> - 서버 설정의 메서드 제한이 왜 애플리케이션의 접근 제어가 되지 못하는지
> - 상태 코드가 판정의 결과이자 동시에 정보 채널이 되는 방식
> - 요청 헤더의 각 값을 누가 쓰고 누가 덮어쓸 수 있는지, 그리고 수신자에게 검증 수단이 있는지
> - CR과 LF 두 문자가 메시지의 구조를 정한다는 사실 하나에서 헤더 인젝션이 어떻게 유도되는지

7장은 **식별자**를 다뤘다. 클라이언트가 무엇을 원하는지 말하는 문자열, 그 문자열의 문법, 그리고 그것이 경로 위에서 여러 번 해석될 때 벌어지는 일들이다. 이 장은 그 식별자를 담는 **그릇**을 연다.

그릇의 구조는 놀라울 만큼 단순하다. 첫 줄 하나, 이름과 값을 콜론으로 이은 줄 여러 개, 빈 줄 하나, 그리고 나머지 전부가 본문이다. 이 단순함이 HTTP가 30년 넘게 살아남은 이유의 상당 부분이고, 동시에 이 장 뒷부분이 다룰 문제 전부의 원인이다. **구조가 문자로만 표시된다는 것은, 문자를 쓸 수 있는 자가 구조를 쓸 수 있다는 뜻이다.**

이 장은 두 개의 무게중심을 갖는다. 앞의 다섯 절(8.1~8.5)은 메시지의 문법과 어휘를 정확히 세운다. 시작줄, 메서드, 상태 코드, 헤더의 분류다. 이 부분은 레퍼런스가 아니라 **뒤의 장들이 인용할 골격**이다. 상태 코드의 상세 목록은 부록 D로, 헤더의 상세 목록은 부록 E로 보냈고, 본문에는 분류와 그 분류가 갖는 결과만 남겼다.

뒤의 두 절(8.6, 8.7)이 이 장의 본론이다. **8.6절은 4.6절이 IP 주소에 대해 확립한 결론 — 주소는 신원이 아니고, 주소에 대한 진술은 더욱 신원이 아니다 — 을 HTTP 헤더 층위에서 받는다.** 6.6절 표 6-9의 여덟 번째 행, "줄 하나를 더하는 일이 줄 하나를 쓰는 것만큼 쉽다"는 경계가 여기서 정확한 형태를 얻는다. **8.7절은 그 반대 방향이다.** 헤더를 읽는 문제가 아니라 헤더를 쓰는 문제이며, 사용자 입력이 응답 헤더에 들어갈 때 메시지의 구조 자체가 사용자 통제 아래 들어가는 과정을 원리 수준에서 세운다.

두 절 모두 여기서 끝나지 않는다. 8.6절은 13.5절(프록시의 `Host` 의존), 15.2절(가상 호스팅), 33.4절(CSRF의 `Referer` 검증)이 각각 다른 방향에서 인용하고, 8.7절은 35.1절이 클라이언트 측 귀결로 상세히 전개한다. 이 장의 역할은 **그 인용들이 딛고 설 원리를 한 번 제대로 세워 두는 것**이다.

## 8.1 메시지의 흐름과 부분들

HTTP가 인터넷의 배달부라면 HTTP 메시지는 그 배달부가 나르는 소포다. 이 절은 소포의 규격을 정한다.

### 방향을 가리키는 네 개의 용어

메시지의 방향을 말하는 어휘가 두 쌍 있다. 두 쌍은 서로 다른 것을 가리키며, 뒤의 장들에서 섞어 쓰이므로 여기서 구별해 둔다.

**인바운드(inbound)와 아웃바운드(outbound)** 는 **오리진 서버를 기준**으로 한다. 요청 메시지는 오리진 서버를 향해 인바운드로 이동하고, 일이 끝나면 응답 메시지가 사용자 에이전트를 향해 아웃바운드로 돌아온다.

**업스트림(upstream)과 다운스트림(downstream)** 은 **송신자와 수신자만을** 기준으로 한다. 모든 메시지는 다운스트림으로 흐른다. 요청이든 응답이든 예외가 없다. 어떤 메시지의 송신자는 그 수신자의 업스트림이다.

```
        인바운드 (서버 방향)  ──────────────────────────────▶
        GET /index.html HTTP/1.1

   클라이언트 ── 프록시 1 ── 프록시 2 ── 프록시 3 ── 오리진 서버

        ◀────────────────────────────  아웃바운드 (에이전트 방향)
                                        HTTP/1.1 200 OK
```

*그림 8-1. 인바운드와 아웃바운드 (HTTP-DG 그림 3-1 기준)*

이 구별이 실무에서 중요한 이유는 하나다. **같은 노드가 요청에 대해서는 프록시 3의 업스트림이고 응답에 대해서는 다운스트림이다.** 프록시 1은 요청 흐름에서 프록시 3보다 업스트림이지만, 응답 흐름에서는 다운스트림이다. 업스트림/다운스트림만으로는 메시지가 서버로 가는지 클라이언트로 가는지 알 수 없다. 로그 분석과 중간자 설정에서 이 혼동이 자주 생긴다(→ 13.1, 16.2).

### 세 부분

모든 HTTP 메시지는 세 부분으로 이뤄진다.

| 부분 | 필수 여부 | 내용 | 무엇이 이 부분의 끝을 표시하는가 |
|---|---|---|---|
| **시작줄(start line)** | 필수 | 요청이면 무엇을 할지, 응답이면 무엇이 일어났는지 | CRLF 하나 |
| **헤더(headers)** | 0개 이상 | 이름/값 쌍의 목록 | **빈 줄** (CRLF 하나가 단독으로) |
| **본문(entity body)** | 선택 | 임의의 텍스트 또는 바이너리 | `Content-Length` 또는 청크 종료 표시 또는 커넥션 종료 |

**표 8-1. HTTP 메시지의 세 부분과 각 부분의 경계 (HTTP-DG 3장 기준)**

이 표의 마지막 열이 이 장의 나머지 전부와 연결된다. **세 부분의 경계는 모두 문자열 안의 약속으로만 표시된다.** 길이 필드가 앞에 붙는 바이너리 프로토콜과 달리, HTTP/1.x는 어디가 끝인지를 데이터 자체에 섞어 놓는다. 그 결과가 두 가지다.

- 헤더 블록의 끝이 **빈 줄**이라는 사실이 8.7절의 응답 분할을 성립시킨다.
- 본문의 끝을 표시하는 방법이 **여럿**이라는 사실이 10.4절의 본문 경계 불일치를 성립시킨다.

시작줄과 헤더는 ASCII 텍스트이고, 줄 단위로 나뉜다. 각 줄은 **두 문자짜리 줄 끝 시퀀스**로 끝난다. 캐리지 리턴(ASCII 13, `0x0d`)과 라인 피드(ASCII 10, `0x0a`)다. 이 쌍을 **CRLF**라 쓴다. 본문은 다르다. 텍스트일 수도 바이너리일 수도 있고, 비어 있을 수도 있다.

### 명세와 관용성 — 두 개의 완화 규칙

HTTP-DG는 여기서 두 가지 예외를 명시한다. 두 예외 모두 **받아들이는 쪽의 관용성**에 관한 것이며, 두 예외 모두 이 장 뒷부분에서 다시 나온다.

**첫째, 줄 끝은 CRLF지만 LF 단독도 받아야 한다.** 명세가 요구하는 종료 시퀀스는 CRLF다. 그러나 오래되거나 잘못 만들어진 HTTP 애플리케이션 중에 CR을 빼고 LF만 보내는 것이 있고, 견고한 구현은 그것도 받아들여야 한다.

**둘째, 헤더 목록은 항상 빈 줄로 끝나야 하지만 그 빈 줄이 없는 메시지도 받아야 한다.** 본문이 없을 때 마지막 CRLF를 빠뜨리는 클라이언트와 서버가 역사적으로 많았고, 그것들과 상호운용하려면 관용이 필요하다.

두 규칙은 실용적이고, 2002년에도 옳았고, 지금도 대체로 옳다. 그리고 **둘 다 파서마다 다른 관용의 정도를 갖게 만든다.** 어떤 파서는 LF 단독을 줄 끝으로 인정하고 어떤 파서는 인정하지 않는다면, 같은 바이트열이 두 파서에게 다른 개수의 헤더로 보인다. 8.7절이 LF 단독 인젝션을 다룰 때, 그리고 13.12절이 중간자별 파싱 불일치 지점을 목록으로 만들 때, 이 관용성이 재료가 된다.

> **관용성 원칙과 그 대가**
>
> 이 두 규칙은 인터넷 프로토콜의 오래된 격언 — "보낼 때는 보수적으로, 받을 때는 관대하게" — 의 적용이다. HTTP-DG는 확장 메서드를 다룰 때 이 격언을 명시적으로 인용한다(→ 8.3.3). 이 원칙이 HTTP의 확장성과 하위 호환성을 만들었다. 그러나 **관대함의 정도가 구현마다 다르면, 관대함 자체가 불일치의 원인이 된다.** 이 책은 이 긴장을 여러 곳에서 다시 만난다: 9.7절(멍청한 프록시), 10.4절(본문 경계), 11.7.1절(바이너리 프레이밍이 왜 모호성을 줄이는가), 13.12절(파싱 불일치 지점 목록).

### 요청과 응답의 일반 형식

두 종류의 메시지는 **시작줄에서만 다르다.** 나머지 구조는 동일하다.

요청 메시지:

```
<메서드> <요청-URL> <버전>
<헤더>

<본문>
```

응답 메시지:

```
<버전> <상태-코드> <이유-구>
<헤더>

<본문>
```

Joe's Hardware Store에서 특가 상품 이미지를 받아 오는 트랜잭션 하나를 실제 문법으로 적으면 다음과 같다. 줄 끝을 명시적으로 표시했다.

```
GET /specials/saw-blade.gif HTTP/1.1\r\n
Host: www.joes-hardware.com\r\n
Accept: image/gif, image/jpeg, */*\r\n
\r\n
```

```
HTTP/1.1 200 OK\r\n
Content-Type: image/gif\r\n
Content-Length: 8572\r\n
\r\n
<8572바이트의 GIF 데이터>
```

요청에는 본문이 없다. 그래도 **빈 줄은 있어야 한다.** 헤더 목록의 끝을 표시하는 것이 그 줄이기 때문이다. 응답에는 본문이 있고, 본문이 어디서 끝나는지는 `Content-Length: 8572`가 말한다. 이 두 문장이 이 절의 핵심이며, 각각 8.7절과 10.2절의 출발점이다.

요청 메시지에 본문이 있는 경우도 같은 구조다.

```
POST /inventory-check.cgi HTTP/1.1\r\n
Host: www.joes-hardware.com\r\n
Content-Type: text/plain\r\n
Content-Length: 18\r\n
\r\n
item=bandsaw 2647
```

`Content-Length: 18`은 `item=bandsaw 2647` 뒤에 개행 하나가 붙어 18바이트라는 뜻이다. 이 값이 실제 본문 길이와 어긋날 때 무슨 일이 일어나는지는 10.2절과 10.4절이 다룬다.

### 메시지를 만든다는 것은 문자열을 만드는 것이다

5.5절에서 브라우저가 요청 메시지를 직렬화하는 과정을 봤다. 그때 지적한 것을 여기서 뒤집어 말한다.

**HTTP 메시지를 만드는 데 필요한 것은 문자열 조작뿐이다.** 특별한 API도, 라이브러리도, 브라우저도 필요 없다. 열린 TCP 소켓에 올바른 순서로 바이트를 쓰면 그것이 HTTP 요청이다. 이것이 6.7절이 확립한 명제 — 사용자는 임의의 입력을 보낼 수 있다 — 의 프로토콜 수준 근거다. **브라우저가 보내지 않을 요청이라는 것은 존재하지 않는다.** 메서드 필드에 무엇을 넣을지, 헤더를 몇 개 넣을지, 같은 헤더를 두 번 넣을지는 전부 요청을 만드는 쪽이 정한다.

그리고 이 명제의 대칭형이 응답 쪽에 있다. **애플리케이션이 응답 헤더를 만드는 방법도 문자열 조작이다.** 프레임워크가 `setHeader("Location", url)`이라는 함수를 제공하더라도, 그 함수가 결국 하는 일은 `"Location: " + url + "\r\n"`이다. `url`에 CR이나 LF가 들어 있으면 그 문자열은 헤더 하나가 아니라 여러 개가 된다. 8.7절 전체가 이 한 문장에서 나온다.

## 8.2 시작줄 — 요청 라인과 응답 라인

모든 HTTP 메시지는 시작줄로 시작한다. 요청의 시작줄은 **무엇을 할지**를 말하고, 응답의 시작줄은 **무엇이 일어났는지**를 말한다.

### 요청 라인

요청 라인은 세 필드를 공백으로 구분한다.

```
GET /test/hi-there.txt HTTP/1.1
 │            │            │
 │            │            └─ 버전
 │            └─ 요청 URL
 └─ 메서드
```

세 필드는 각각 다음과 같다.

**메서드.** 클라이언트가 서버에게 리소스에 대해 수행하기를 원하는 동작이다. `GET`, `HEAD`, `POST` 같은 한 단어다. 8.3절이 상세히 다룬다.

**요청 URL.** 요청하는 리소스를 지정하는 완전한 URL이거나, URL의 경로 부분이다. 서버에 직접 말하고 있다면 경로 부분만으로 충분하다. 그 경로가 리소스의 절대 경로인 한, 서버는 자기 자신을 URL의 호스트/포트로 가정할 수 있기 때문이다. **이 "가정할 수 있다"가 8.6절의 `Host` 헤더 논의로 곧장 이어진다.**

**버전.** `HTTP/<major>.<minor>` 형식이며 major와 minor는 각각 정수다. HTTP/1.0 이전에는 요청 라인에 버전이 없어도 됐다(→ 11.1).

프록시를 통해 보낼 때는 요청 URL의 형태가 달라진다.

```
GET /power-tools.html HTTP/1.1          ← 서버에 직접: 절대 경로
Host: www.joes-hardware.com

GET http://www.joes-hardware.com/power-tools.html HTTP/1.1   ← 프록시에: 절대 URI
Host: www.joes-hardware.com
```

두 번째 형태에서 목적지 정보가 **두 곳에 중복해서** 들어간다는 점에 주목하라. 요청 라인의 절대 URI와 `Host` 헤더가 같은 것을 말한다. 두 값이 다르면 어느 쪽을 따를지가 구현에 달려 있고, 경로에 중간자가 여러 개면 홉마다 다른 선택을 할 수 있다. 13.5절이 이 문제를 정면으로 다룬다.

### 응답 라인

응답 라인도 세 필드를 공백으로 구분한다.

```
HTTP/1.1 200 OK
    │     │   │
    │     │   └─ 이유 구
    │     └─ 상태 코드
    └─ 버전
```

**상태 코드**는 세 자리 숫자로, 요청 처리 중 무슨 일이 일어났는지를 기술한다. 첫 자리가 일반적인 부류를 결정한다. 8.4절이 다룬다.

**이유 구(reason phrase)** 는 숫자 코드를 사람이 읽을 수 있게 옮긴 것이며, 줄 끝까지의 모든 텍스트다. 명세는 이유 구의 정확한 문구에 대해 아무 규칙도 두지 않는다.

여기서 HTTP-DG가 명시적으로 지적하는 사실 하나가 이 책 전체에서 반복해 인용된다.

> **`HTTP/1.0 200 NOT OK`와 `HTTP/1.0 200 OK`는 동등한 성공 표시로 취급되어야 한다.** 이유 구가 반대를 시사하더라도 그렇다.

**이유 구는 사람이 읽으라고 있는 것이고, 처리 판단의 근거가 아니다.** 판단은 숫자로 한다. 이 규칙은 프로토콜 관점에서 옳고, 보안 관점에서 두 가지 결과를 낳는다.

**첫째, 화면과 코드가 갈릴 수 있다.** 사용자에게는 "접근이 거부되었습니다"라고 보이는 응답이 프로토콜 층위에서는 `200 OK`일 수 있다. 그 응답은 캐시될 수 있고(→ 14.8), 모니터링에서 성공으로 집계되며, 자동화 도구는 성공으로 판정한다. 8.4절의 오용 사례 첫 번째가 정확히 이것이다.

**둘째, 이유 구는 자유 텍스트이며 따라서 응답 라인에 임의의 문자열이 들어갈 수 있는 자리다.** 애플리케이션이 이유 구를 사용자 입력으로 채우는 프레임워크가 존재하고, 그 자리는 8.7절이 다룰 인젝션 지점 목록에 포함된다.

### 버전 번호는 소수가 아니다

버전 번호에 관해 한 가지 함정이 있다. **`HTTP/x.y`의 x와 y는 각각 독립적인 정수이며, 전체를 소수로 읽으면 안 된다.** 따라서 `HTTP/2.22`는 `HTTP/2.3`보다 **높은** 버전이다. 22가 3보다 크기 때문이다.

그리고 버전 번호의 의미는 "이 메시지가 그 버전으로 쓰였다"가 아니라 **"이 애플리케이션이 지원하는 가장 높은 버전이 이것이다"** 이다. 이 차이가 실제 혼동을 만들었다. HTTP/1.0 애플리케이션은 응답에 `HTTP/1.1`이 적혀 있으면 그것을 1.1 응답으로 해석하지만, 실제로는 응답하는 쪽이 말할 줄 아는 프로토콜 수준일 뿐이다. 11.13절이 버전 전환기의 운영 함의를 다룰 때 이 지점을 다시 연다.

### 시작줄의 필드는 누구의 통제 아래 있는가

5.5절의 표 5-4를 시작줄에 대해 다시 쓰면 다음과 같다.

| 필드 | 값을 정하는 주체 | 값의 범위 | 서버가 이 값에 의존하는 곳 | 참조 |
|---|---|---|---|---|
| 메서드 | **클라이언트** | 임의의 토큰 (표준 7개에 한정되지 않는다) | 접근 제어 규칙, 라우팅, 캐시 가능성 판정 | 8.3.4, 24.5 |

마지막으로 시작줄의 구조 자체가 갖는 성질 하나. **시작줄은 공백 두 개로 세 조각이 되는 줄이다.** 요청 URL 안에 인코딩되지 않은 공백이 들어가면 그 줄은 네 조각이 되고, 파서는 그것을 문법 오류로 보거나(`400 Bad Request`), 관용적으로 처리하거나, 뒤쪽을 버린다. 세 동작이 서로 다른 결과를 낸다. 7.4절이 URL에서 공백을 반드시 인코딩해야 하는 이유로 이식성을 들었다면, 여기가 그 이유의 프로토콜 층위 근거다.

## 8.3 메서드

메서드는 요청의 시작줄을 여는 토큰이며, 서버에게 무엇을 하라고 말한다. `GET /specials/saw-blade.gif HTTP/1.0`에서 메서드는 `GET`이다.

HTTP 명세는 공통 요청 메서드의 집합을 정의한다. 그 목록은 짧다.

| 메서드 | 하는 일 | 요청 본문 | HTTP/1.1 서버 필수 구현 |
|---|---|---|---|
| `GET` | 서버에서 문서를 가져온다 | 없음 | **필수** |
| `HEAD` | 문서의 헤더만 가져온다 | 없음 | **필수** |
| `POST` | 처리할 데이터를 서버로 보낸다 | 있음 | 선택 |
| `PUT` | 요청 본문을 서버에 저장한다 | 있음 | 선택 |
| `TRACE` | 프록시를 거쳐 서버까지 메시지를 추적한다 | 없음 | 선택 |
| `OPTIONS` | 서버가 어떤 메서드를 지원하는지 알아낸다 | 없음 | 선택 |
| `DELETE` | 서버에서 문서를 제거한다 | 없음 | 선택 |

**표 8-3. 공통 HTTP 메서드 (HTTP-DG 표 3-1 기준, 필수 구현 열은 이 책이 추가)**

이 표에서 곧바로 읽어야 할 것이 두 가지다.

**첫째, HTTP/1.1을 준수하는 데 필요한 것은 `GET`과 `HEAD`뿐이다.** 나머지 다섯은 선택이다. 어떤 서버가 `PUT`이나 `DELETE`를 구현했다 해도, 아무나 자원을 저장하거나 삭제하게 두고 싶지는 않을 것이다. 그래서 이 제한은 **서버 설정**에 들어가고, 사이트마다 서버마다 다르다. 8.3.4절이 다룰 문제의 배경이 이 문장이다. **메서드의 허용 여부가 코드가 아니라 설정에 있다.**

**둘째, 이 일곱 개가 전부가 아니다.** HTTP는 확장 가능하도록 설계됐고, 서버는 자기 나름의 요청 메서드를 구현할 수 있다. 명세에 없는 이런 메서드를 **확장 메서드(extension method)** 라 한다. 8.3.3절이 다룬다.

### 8.3.1 안전한 메서드와 그렇지 않은 메서드

HTTP는 일부 메서드를 **안전한 메서드(safe method)** 로 규정한다. `GET`과 `HEAD`가 그것이다. 안전하다는 말의 뜻은 이렇다. **`GET`이나 `HEAD`를 쓰는 HTTP 요청의 결과로 어떤 동작도 일어나지 않아야 한다.**

"어떤 동작도 일어나지 않는다"는 것은 그 HTTP 요청의 결과로 서버에서 아무 일도 벌어지지 않는다는 뜻이다. Joe's Hardware에서 물건을 사고 "구매 확정" 버튼을 누르면 신용카드 정보와 함께 `POST` 요청이 나가고, 사용자를 대신해 서버에서 동작이 수행된다. 카드에 청구가 일어나는 것이다. 이것이 안전하지 않은 메서드다.

여기서 정확히 읽어야 할 문장이 있다. HTTP-DG는 이렇게 쓴다.

> **안전한 메서드가 동작을 일으키지 않는다는 보장은 없다.** 실제로 그것은 웹 개발자에게 달려 있다.

즉 **안전성은 프로토콜이 강제하는 성질이 아니라 규약이다.** 안전한 메서드라는 개념이 존재하는 이유는, HTTP 애플리케이션 개발자가 사용자에게 "지금 동작을 일으킬 수 있는 안전하지 않은 메서드를 쓰고 있습니다"라고 알릴 수 있게 하기 위해서다. 브라우저가 경고 창을 띄울 수 있게 하는 근거인 것이다.

이 문장이 이 절의 전부다. **규약은 지켜질 때만 규약이고, 규약에 의존하는 설계는 규약이 깨질 때 함께 깨진다.**

**표 8-4. 메서드의 두 가지 성질과 그것에 의존하는 것들**

| 성질 | 해당 메서드 | 누가 강제하는가 | 이 성질을 전제로 동작하는 것 | 깨졌을 때 |
|---|---|---|---|---|
| **안전(safe)** — 상태를 바꾸지 않는다 | `GET`, `HEAD` | 아무도. 개발자의 규약 | 크롤러(→ 16.8), 링크 프리페치, 캐시(→ 14장), 링크 미리보기, 검색 엔진 색인 | 크롤러가 자원을 삭제한다 |
| **멱등(idempotent)** — 여러 번 보내도 결과가 같다 | `GET`, `HEAD`, `PUT`, `DELETE` | 아무도. 서버 구현의 규약 | 커넥션 실패 시 자동 재시도(→ 9.9), 프록시의 재전송 | 재시도가 주문을 두 번 넣는다 |

두 성질 모두 강제 주체가 "아무도"라는 점이 요지다. 그리고 이 표의 네 번째 열이 실제 사고 시나리오의 목록이다.

**안전 규약이 깨졌을 때 벌어지는 일**을 구체적으로 보자. Joe's Hardware의 관리 페이지에 이런 링크가 있다고 하자.

```html
<a href="/admin/delete-product?id=2647">이 상품 삭제</a>
```

이 링크는 `GET` 요청을 만든다. 그리고 이 URL을 아는 자는 이제 다음을 할 수 있다.

- 검색 엔진의 크롤러가 관리자 세션 없이도 이 링크를 따라간다. 인증이 없으면 상품이 지워진다.
- 브라우저의 링크 프리페치가 사용자가 클릭하기도 전에 요청을 보낸다.
- 관리자가 이 페이지를 열어 둔 채로 다른 사이트를 방문하면, 그 사이트가 `<img src="https://www.joes-hardware.com/admin/delete-product?id=2647">` 한 줄로 요청을 발생시킨다. **관리자의 쿠키와 함께.** 이것이 33.2절이 다루는 크로스 사이트 요청 위조(CSRF)이며, **CSRF의 성립 조건 중 하나가 정확히 이 절의 규약 위반이다.**
- 프록시나 브라우저 캐시가 이 응답을 저장한다. `GET`은 캐시 가능한 메서드이기 때문이다(→ 14.6).
- 서버 액세스 로그와 프록시 로그에 삭제 대상 ID가 그대로 남는다(→ 16.4).

여섯 항목 중 어느 것도 "공격"이 아니다. 전부 **안전 규약을 신뢰하고 만들어진 정상 동작**이다. 규약을 어긴 쪽은 애플리케이션이다.

33.4절이 CSRF 방어를 다룰 때 첫 번째 처방이 "상태를 바꾸는 동작에 `GET`을 쓰지 않는다"인 이유가 여기에 있다. 그것은 방어책이라기보다 **깨진 규약을 복구하는 일**이다.

### 8.3.2 GET과 POST의 의미 차이가 만드는 보안 격차

`GET`과 `POST`는 실무에서 마주치는 메서드의 거의 전부다. 두 메서드의 설계 의도는 명확히 다르고, 그 차이가 애플리케이션 보안에 직접적인 결과를 만든다.

**`GET`은 리소스를 가져오도록 설계됐다.** 파라미터를 URL 쿼리 문자열에 담아 보낸다. 그 덕에 사용자는 동적 리소스의 URL을 북마크할 수 있고, 나중에 같은 URL로 같은 결과를 다시 얻을 수 있다. 북마크한 검색 질의가 그런 예다.

**`POST`는 동작을 수행하도록 설계됐다.** 파라미터를 URL 쿼리 문자열에도 담을 수 있지만 메시지 본문에도 담을 수 있다. URL은 여전히 북마크할 수 있지만 본문에 담긴 파라미터는 북마크에서 제외된다.

그리고 이 차이의 핵심은 **URL이 어디에 남는가**에 있다.

**표 8-5. `GET` 파라미터와 `POST` 본문 파라미터의 노출 지점 (WAHH 3장 기준, 참조 열은 이 책이 추가)**

| 노출 지점 | URL 쿼리 문자열 | 본문 파라미터 | 이 책에서 |
|---|---|---|---|
| 브라우저 주소 표시줄 | **노출** | 노출 안 됨 | — |
| 북마크 | **저장됨** | 저장 안 됨 | — |
| 브라우저 방문 기록 | **저장됨** | 저장 안 됨 | 36.1 |
| 웹 서버 액세스 로그 | **기록됨** | 기록 안 됨 | 16.2, 16.4 |
| 프록시·중간자 로그 | **기록됨** | 기록 안 됨 | 16.4 |
| 외부 사이트로 나가는 `Referer` 헤더 | **전송됨** | 전송 안 됨 | 8.6, 26.1 |
| 어깨너머 관찰·화면 캡처 | **노출** | 노출 안 됨 | — |
| 뒤로 가기 시 재전송 | 조용히 재요청 | **경고 후 사용자 확인** | 29.2 |

이 표의 결론은 하나다. **민감한 정보를 쿼리 문자열로 전송해서는 안 된다.** 세션 토큰, 비밀번호, 재설정 토큰, 개인 식별 정보가 URL에 실리면 그 값은 최소 다섯 곳에 사본을 남긴다. 그리고 그중 두 곳 — 프록시 로그와 `Referer` 헤더 — 은 **애플리케이션 운영자의 통제 밖**이다.

이 격차를 이용하는 취약점 유형이 이 책 여러 곳에 흩어져 있다. 20.4절의 fat URL은 URL에 사용자 식별자를 넣는 설계의 결과를 다루고, 23.3절은 세션 토큰이 URL을 통해 노출되는 경로를 다루며, 39.8절은 GraphQL 질의를 `GET`으로 보낼 때 질의 전체가 캐시와 로그에 남는 문제를 다룬다. 셋 다 이 표의 같은 행에서 나온다.

마지막 행 — 뒤로 가기 시의 동작 — 도 규약이다. `POST`가 동작 수행용으로 설계됐으므로, 브라우저는 사용자가 뒤로 가기로 `POST` 페이지에 돌아왔을 때 요청을 자동으로 재전송하지 않고 경고한다. 사용자가 모르는 사이에 같은 동작을 두 번 수행하는 것을 막기 위해서다. **동작을 수행할 때는 항상 `POST`를 써야 하는 이유가 이 브라우저 동작에 있다.**

### 규약이 강제되지 않는다는 사실

지금까지의 논의는 전부 "설계 의도"에 관한 것이었다. 이제 그 의도가 실제로 강제되는지를 묻는다. 답은 명확하다.

**대부분의 애플리케이션 수준 API는 요청 파라미터를 읽을 때 요청 메서드를 구분하지 않는다.**

`request.getParameter("id")`나 그에 해당하는 함수는 쿼리 문자열과 본문 중 어디에 있든 값을 찾아 준다. 이것은 편의 기능이며, 프레임워크 설계자의 합리적 선택이었다. 그리고 그 결과가 이렇다.

- `POST`로 설계된 기능을 `GET`으로 호출할 수 있다. 파라미터를 쿼리 문자열에 넣기만 하면 된다.
- 따라서 표 8-5의 "본문 파라미터" 열이 주는 보호는 **공격자에게는 적용되지 않는다.** 공격자는 자기 요청을 `GET`으로 바꿔서 URL 한 줄로 만들 수 있고, 그 URL을 피해자에게 클릭시킬 수 있다(→ 33.2).
- 그리고 메서드에 기반한 접근 제어 규칙은 이 지점에서 무너진다. 8.3.4절의 주제다.

이 절의 결론을 한 문장으로 적는다. **`GET`과 `POST`의 구별은 의미의 구별이지 메커니즘의 구별이 아니다.** 그 구별에 의존하는 보안 판단 — "이 기능은 `POST`니까 CSRF에 안전하다", "이 값은 본문에 있으니 로그에 안 남는다" — 은 **공격자가 메서드를 바꿀 수 없을 때만** 참이며, 공격자는 바꿀 수 있다.

### 8.3.3 PUT, DELETE, TRACE, OPTIONS, WebDAV 확장 메서드

나머지 다섯 메서드는 실무에서 마주칠 빈도가 낮지만, 마주쳤을 때의 영향은 `GET`·`POST`보다 크다. **자원을 읽는 것이 아니라 쓰거나, 지우거나, 서버의 내부 사정을 드러내기 때문이다.**

#### HEAD

`HEAD`는 `GET`과 정확히 같이 동작하되 서버가 응답에 헤더만 돌려준다. 본문은 절대 반환되지 않는다. 이것으로 클라이언트는 리소스를 실제로 받지 않고 헤더를 검사할 수 있다.

```
HEAD /seasonal/index-fall.html HTTP/1.1
Host: www.joes-hardware.com

```

```
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 617

```

(본문 없음)

용도는 셋이다. 자원을 받지 않고 그 자원에 대해 알아내기(타입 확인 등), 상태 코드만 보고 객체의 존재 확인하기, 헤더를 보고 수정 여부 확인하기. 서버 개발자는 **`GET`이 반환했을 헤더와 정확히 같은 헤더를 반환하도록** 보장해야 한다. `HEAD`도 HTTP/1.1 준수에 필수다.

바로 이 "`GET`과 정확히 같이 동작한다"는 요구사항이 8.3.4절에서 우회 수단이 된다. 대부분의 플랫폼은 `HEAD` 요청을 **해당 `GET` 핸들러를 실행하고 본문만 버리는** 방식으로 처리한다. 명세를 정확히 따른 구현이며, 그 정확함이 문제를 만든다.

#### PUT

`PUT`은 `GET`의 반대 방향이다. `GET`이 서버에서 문서를 읽는다면 `PUT`은 서버에 문서를 쓴다.

```
PUT /product-list.txt HTTP/1.1
Host: www.joes-hardware.com
Content-Type: text/plain
Content-Length: 34

Updated product list coming soon!
```

```
HTTP/1.1 201 Created
Location: http://www.joes-hardware.com/product-list.txt
Content-Type: text/plain
Content-Length: 47

http://www.joes-hardware.com/product-list.txt
```

의미는 이렇다. **서버는 요청 본문을 받아서, 요청 URL이 지정한 이름의 새 문서를 만들거나, 그 URL이 이미 존재하면 본문으로 대체한다.** 일부 발행 시스템은 이 방식으로 웹 페이지를 서버에 직접 설치한다(→ 15.11).

`PUT`은 콘텐츠를 바꿀 수 있으므로 많은 웹 서버가 인증을 요구한다(→ 21장). 그리고 이 문장을 뒤집으면 위험의 정의가 된다. **인증 없이 `PUT`이 열려 있는 경로는 임의의 파일 업로드 지점이다.** 웹 루트 안에 파일을 쓸 수 있으면 첫 번째 표적은 서버 측 모듈이 실행할 백도어 스크립트를 만드는 것이고, 그것이 성공하면 애플리케이션 전체와 대개는 웹 서버 자체까지 공격자의 통제 아래 들어간다. 12.7절이 이 지점을 서버 설정 관점에서 다루고, 28.4절이 실행 경로를 다룬다.

`PUT`이 열려 있는지 확인하는 방법은 단순하다. 무해한 파일을 하나 올려 보면 된다.

```
PUT /public/test.txt HTTP/1.1
Host: www.joes-hardware.com
Content-Length: 4

test
```

```
HTTP/1.1 201 Created
```

권한은 대개 디렉터리별로 설정되므로, 한 경로에서 막힌다고 전체가 막힌 것은 아니다. 재귀적 확인이 필요하다(→ 24.5).

#### DELETE

`DELETE`는 요청 URL이 지정한 자원을 지우라고 요청한다. 여기에 한 가지 성질이 붙는다. **클라이언트는 삭제가 실제로 수행됐다고 보장받지 못한다.** HTTP 명세가 서버로 하여금 클라이언트에게 알리지 않고 요청을 무시하는 것을 허용하기 때문이다.

```
DELETE /product-list.txt HTTP/1.1
Host: www.joes-hardware.com

```

```
HTTP/1.1 200 OK
Content-Type: text/plain
Content-Length: 54

I have your delete request, will take time to process.
```

클라이언트는 자원이 삭제됐다고 생각하고, 서버는 아직 아무것도 하지 않았을 수 있다. **상태 코드가 결과를 말하지 않는 경우**의 첫 번째 예이며, 8.4절이 다룰 오용 사례의 프로토콜적 뿌리 중 하나다.

#### TRACE

`TRACE`는 진단용 메서드다. 클라이언트가 요청을 보내면 그 요청은 방화벽, 프록시, 게이트웨이를 거칠 수 있고, 각 홉이 요청을 수정할 기회를 갖는다. `TRACE`는 **자기 요청이 최종적으로 서버에 도달했을 때 어떤 모습인지**를 클라이언트가 볼 수 있게 한다.

동작은 루프백이다. 마지막 구간의 서버가 자기가 받은 요청 메시지를 **응답 본문에 그대로 담아** 되돌려 보낸다.

```
TRACE /product-list.txt HTTP/1.1
Host: www.joes-hardware.com
Accept: text/html

```

프록시 하나를 통과한 뒤 서버가 받은 것은 이렇다.

```
TRACE /product-list.txt HTTP/1.1
Host: www.joes-hardware.com
Accept: text/html
Via: 1.1 proxy3.company.com

```

그리고 서버의 응답은 이렇다.

```
HTTP/1.1 200 OK
Content-Type: message/http
Content-Length: 96
Via: 1.1 proxy3.company.com

TRACE /product-list.txt HTTP/1.1
Host: www.joes-hardware.com
Accept: text/html
Via: 1.1 proxy3.company.com
```

클라이언트는 이 본문을 보고 **자기가 보내지 않은 `Via` 헤더가 붙었다**는 것을 알 수 있다. 경로상의 애플리케이션들이 자기 메시지를 어떻게 변형했는지 확인하는 도구인 것이다. `Max-Forwards` 헤더로 몇 번째 홉에서 되돌릴지 지정할 수도 있다. `Max-Forwards: 0`을 받은 수신자는 자기가 오리진 서버가 아니더라도 그 자리에서 메시지를 반사해야 한다. 13.6절이 `Via`·`TRACE`·`Max-Forwards`를 메시지 추적이라는 주제로 묶어 다룬다.

`TRACE` 요청에는 본문을 실을 수 없다. 그리고 `TRACE` 응답의 본문은 **서버가 받은 요청 그대로**다.

이 마지막 문장에 보안 함의가 들어 있다. HTTP-DG의 그림 6-23이 보여 주는 실제 `TRACE` 응답 본문에는 다음이 들어 있다.

```
TRACE /index.html HTTP/1.1
Host: www.joes-hardware.com
Accept: text/html
Via: 1.1 proxy.irenes-isp.net, 1.1 p1127.att.net, 1.1 cache.joes-hardware.com
X-Magic-CDN-Thingy: 134-AF-0003
Cookie: access-isp="Irene's ISP, California"
Client-ip: 209.134.49.32
```

**요청에 실려 있던 `Cookie` 헤더와 `Client-ip` 헤더가 응답 본문에 그대로 있다.** 이것이 `TRACE`의 설계 목적이고, 그 목적이 그대로 문제가 된다. 응답 본문은 **문서**다. 브라우저 안에서 어떤 방법으로든 `TRACE` 요청을 발생시키고 그 응답 본문을 읽을 수 있다면, 요청에 자동으로 붙는 모든 헤더 — 쿠키와 인증 자격증명을 포함해서 — 를 문서 내용으로 읽을 수 있다는 뜻이다. 20.6절이 다룰 `HttpOnly` 속성은 "스크립트가 쿠키를 직접 읽지 못하게 한다"는 것인데, `TRACE`는 그 쿠키를 **문서 본문에 실어 되돌려 준다.** 두 메커니즘이 서로 어긋나는 것이다.

그래서 `TRACE`는 오늘날 대부분의 프로덕션 서버에서 꺼져 있다. 진단 가치보다 노출 위험이 크다는 판단이 표준적이다. 25.6절의 서버 핑거프린팅과 24.5절의 메서드 제한 테스트에서 `TRACE`의 활성화 여부는 표준 점검 항목이다.

`TRACE` 자체의 진단 도구로서의 한계도 HTTP-DG가 지적한다. **`TRACE`는 중간 애플리케이션들이 서로 다른 메서드를 같은 방식으로 다룰 것이라고 가정한다.** 그러나 실제로는 많은 HTTP 애플리케이션이 메서드에 따라 다르게 동작한다. 프록시가 `POST`는 서버로 곧장 넘기고 `GET`은 캐시로 보낼 수 있다. `TRACE`에는 메서드를 구분할 수단이 없으므로, `TRACE`로 관찰한 경로가 `POST` 요청의 경로와 같다는 보장이 없다. **진단 결과가 진단 대상과 다른 경로를 측정할 수 있다.**

#### OPTIONS

`OPTIONS`는 서버에게 지원하는 기능을 물어본다. 서버 전체에 대해 물을 수도 있고 특정 리소스에 대해 물을 수도 있다.

```
OPTIONS * HTTP/1.1
Host: www.joes-hardware.com

```

```
HTTP/1.1 200 OK
Allow: GET, POST, PUT, OPTIONS
Content-Length: 0

```

요청 URL 자리의 `*`는 "서버 전체"를 뜻하는 특수한 형태다. 특정 경로에 대해 물으려면 `OPTIONS /public/ HTTP/1.1`처럼 쓴다. 응답의 `Allow` 헤더가 그 리소스에 대해 수행 가능한 메서드를 나열한다.

`OPTIONS`의 가치는 클라이언트가 리소스에 실제로 접근하지 않고도 접근 방법을 알아낼 수 있다는 것이다. 그리고 정찰자에게도 같은 가치가 있다. 25.6절의 서버 핑거프린팅과 24.5절의 메서드 제한 테스트가 `OPTIONS`를 첫 단계로 쓰는 이유다.

여기에 반드시 붙여야 할 단서가 있다. WAHH가 명시하는 것이다.

> **광고된 메서드가 실제로는 쓸 수 없는 경우가 많고, `OPTIONS` 응답에 없는 메서드가 실제로는 쓸 수 있는 경우도 있다.**

`Allow` 헤더는 **서버의 진술**이지 검증된 사실이 아니다. 8.6절이 헤더 전반에 대해 확립할 명제의 응답 헤더판이다. 실무의 결론은 단순하다. **각 메서드를 직접 시도해서 확인해야 한다.**

#### 확장 메서드와 WebDAV

HTTP는 확장 가능하도록 설계됐다. 새 기능이 추가돼도 오래된 소프트웨어가 깨지지 않아야 했다. 그래서 HTTP/1.1 명세에 정의되지 않은 **확장 메서드**를 서버가 구현할 수 있다.

가장 널리 쓰인 확장 메서드 집합은 **WebDAV**(Web-based Distributed Authoring and Versioning)다. HTTP 위에서 웹 콘텐츠를 발행하고 협업 저작하기 위한 확장이며, 1996년부터 널리 사용됐고 최근에는 클라우드 저장소와 협업 애플리케이션에서 채택됐다. 방화벽을 통과하기 쉬운 기존 프로토콜(HTTP) 위에 파일 조작 기능을 얹을 수 있다는 것이 채택 이유였다.

**표 8-6. WebDAV 확장 메서드와 그 위험 (HTTP-DG 표 3-5 + WAHH 18장 기준)**

| 메서드 | 하는 일 | 공격자에게 무엇이 되는가 |
|---|---|---|
| `PUT` | 지정 위치에 첨부 파일을 업로드한다 | 임의 파일 쓰기 → 백도어 스크립트 설치 |
| `DELETE` | 지정 자원을 삭제한다 | 콘텐츠 파괴, 가용성 공격 |
| `COPY` | 자원을 `Destination` 헤더가 지정한 위치로 복사한다 | 확장자 제한 우회 |
| `MOVE` | 자원을 `Destination` 헤더가 지정한 위치로 이동한다 | **`PUT` 확장자 필터 우회** |
| `MKCOL` | 자원(컬렉션/디렉터리)을 생성한다 | 쓰기 가능한 경로 확보 |
| `PROPFIND` | 자원의 정보(작성자, 크기, 콘텐츠 타입)를 조회한다 | 디렉터리 열거, 숨겨진 콘텐츠 발견 |
| `PROPPATCH` | 자원의 속성을 변경한다 | 메타데이터 조작 |
| `SEARCH` | 디렉터리 경로에서 자원을 검색한다 | 콘텐츠 열거 |
| `LOCK` / `UNLOCK` | 편집 중 다른 사용자의 편집을 막기 위해 자원을 잠근다 | 자원 잠금을 통한 서비스 방해 |

이 표에서 실제 공격에 가장 자주 쓰이는 조합은 `PUT` + `MOVE`다. 많은 서버가 `PUT`으로 올릴 수 있는 파일 확장자를 제한한다. `.asp`, `.php`, `.jsp` 같은 서버 측 실행 확장자를 막는 것이다. 그런데 그 제한이 `PUT` 시점에만 적용되고 `MOVE` 시점에는 적용되지 않으면 다음 두 단계로 우회된다.

```
1단계: PUT /public/payload.txt        ← 허용된 확장자로 업로드
2단계: MOVE /public/payload.txt       ← Destination으로 실행 가능한 확장자 지정
       Destination: /public/payload.php
```

DAVTest 같은 도구가 이 절차를 자동화한다. 서버의 모든 디렉터리에 대해 `PUT` 가능 여부와 허용 확장자를 반복 확인하고, 막히면 `PUT` 후 `MOVE`를 시도한다.

WebDAV 인스턴스에서 최종 사용자에게 파일 업로드를 허용하는 경우, 서버 측 스크립트 확장자만 금지하는 것이 흔하다. 그러나 **HTML이나 JAR 파일 업로드가 허용되면 그것만으로 다른 사용자에 대한 공격이 가능하다**(→ 32.6, 36.4). 확장자 필터의 문제는 "실행 가능한 것"의 목록이 서버 설정에만 있는 것이 아니라 브라우저에도 있다는 것이다.

#### 확장 메서드를 다루는 원칙, 그리고 그 원칙의 대가

모든 확장 메서드가 정식 명세로 정의되는 것은 아니다. 자기가 확장 메서드를 정의하면 대부분의 HTTP 애플리케이션은 그것을 이해하지 못할 것이고, 반대로 자기 애플리케이션이 다른 애플리케이션의 이해 못 할 확장 메서드를 만날 수도 있다.

HTTP-DG가 제시하는 처방은 이렇다.

> 이런 경우에는 확장 메서드에 관대한 것이 좋다. 프록시는 종단 간 동작을 깨뜨리지 않고 그렇게 할 수 있다면, 알 수 없는 메서드를 담은 메시지를 다운스트림 서버로 중계하려고 시도해야 한다. 그럴 수 없다면 `501 Not Implemented` 상태 코드로 응답해야 한다. **"보낼 때는 보수적으로, 받을 때는 관대하게."**

이 원칙이 HTTP의 확장성을 만들었다. 그리고 이 원칙이 8.3.4절의 세 번째 우회 유형을 만든다. **"알 수 없는 메서드를 중계한다"는 규칙과 "알 수 없는 메서드를 `GET`처럼 처리한다"는 구현은 한 걸음 차이다.** 그 한 걸음을 실제로 걸은 플랫폼이 존재하고, 그것이 다음 절의 주제다.

### 8.3.4 HTTP 메서드 제한 우회

이 절은 접근 제어의 이야기이면서 동시에 **파싱 계층 불일치의 이야기**다. 24장이 접근 제어를 정면으로 다루고 24.5절이 테스트 방법론을 세우므로, 여기서는 **왜 이 우회가 원리적으로 성립하는가**에 집중한다.

#### 두 층에서 이뤄지는 판단

메서드 기반 접근 제어는 대개 두 층에 나뉘어 존재한다.

```
   요청:  POST /admin/create-user HTTP/1.1
             │
             ▼
   ┌─────────────────────────────────────────┐
   │ ① 플랫폼·서버 층의 규칙                  │
   │    (메서드 + URL 경로 + 사용자 역할)     │   ← 서버 설정 파일, 배포 서술자
   │    "관리자가 아니면 /admin/* 에 POST 금지" │
   └─────────────────────────────────────────┘
             │  통과하면
             ▼
   ┌─────────────────────────────────────────┐
   │ ② 애플리케이션 코드                      │
   │    파라미터를 읽고 동작을 수행한다        │   ← 대개 메서드를 다시 확인하지 않는다
   └─────────────────────────────────────────┘
```

*그림 8-2. 메서드 기반 접근 제어의 두 층 (WAHH 8장 기준)*

①은 규칙 목록이다. 메서드와 경로와 역할의 조합으로 허용/거부를 정한다. ②는 실제 동작을 하는 코드다.

문제는 이 두 층이 **서로 다른 것을 본다**는 데 있다. ①은 요청 라인의 첫 토큰을 문자열로 비교한다. ②는 파라미터를 읽고 동작을 수행하며, 그 파라미터가 쿼리 문자열에서 왔는지 본문에서 왔는지, 요청 메서드가 무엇이었는지에 관심이 없다. 8.3.2절에서 확인한 대로 대부분의 파라미터 조회 API가 메서드에 무관하기 때문이다.

**즉 판단하는 층과 동작하는 층이 다른 정보를 본다.** 8.1절이 세운 명제 — 같은 바이트를 여러 주체가 읽고 다르게 해석할 때 취약점이 생긴다 — 의 메서드판이다.

#### 세 가지 우회 유형

WAHH 8장이 정리한 세 유형을 실패의 구조별로 다시 배열하면 다음과 같다.

**표 8-7. 메서드 제한 우회의 세 유형 (WAHH 8장 기준, "실패의 구조" 열은 이 책이 추가)**

| # | 서버 설정의 규칙 | 우회 방법 | 왜 성립하는가 (실패의 구조) |
|---|---|---|---|
| 1 | `POST`를 거부한다 | 같은 요청을 `GET`으로, 파라미터를 쿼리 문자열에 넣어 보낸다 | 애플리케이션 API가 메서드에 무관하게 파라미터를 읽는다 |
| 2 | `GET`과 `POST`를 모두 거부한다 | `HEAD`로 보낸다 | 플랫폼이 `HEAD`를 **해당 `GET` 핸들러 실행 + 본문 폐기**로 구현한다. 명세를 정확히 따른 결과다 |
| 3 | 특정 메서드 목록을 거부한다 | 목록에 없는 **임의의 무효 메서드**를 쓴다 | 플랫폼이 인식하지 못하는 메서드를 `GET` 핸들러로 넘긴다. 8.3.3절의 관용성 원칙의 구현 |

세 유형을 순서대로 보면 방어의 붕괴 과정이 보인다.

**유형 1**은 가장 직관적이다. 관리자 계정을 생성하는 기능이 `POST`를 쓰고, 플랫폼 규칙이 `POST`를 거부하도록 되어 있다. 그러나 애플리케이션 코드가 "이 요청은 정말 `POST`인가"를 확인하지 않으면, 공격자는 필요한 파라미터를 `GET` 요청의 쿼리 문자열에 넣어 같은 기능을 호출할 수 있다.

**유형 2**는 겉보기에 놀랍다. `GET`과 `POST`를 모두 막았는데도 우회가 된다. 이유는 `HEAD`의 명세에 있다. 명세는 서버가 `HEAD` 요청에 대해 **해당 `GET` 요청에 반환했을 헤더와 같은 헤더를 반환하되 본문은 반환하지 말 것**을 요구한다. 이 요구를 만족시키는 가장 자연스러운 구현은 `GET` 핸들러를 그대로 실행하고 생성된 헤더만 돌려주는 것이다. 대부분의 플랫폼이 그렇게 한다.

그리고 `GET` 요청이 민감한 동작을 수행하는 경우가 많다. 애플리케이션이 명세를 어기고 `GET`으로 동작을 수행하거나(8.3.1절의 규약 위반), `POST`가 쓰였는지 확인하지 않기 때문이다(유형 1). 그러면 이렇게 된다.

> **공격자가 `HEAD` 요청으로 관리자 계정을 추가할 수 있다면, 응답 본문 따위는 없어도 된다.**

동작은 이미 수행됐다. 결과를 볼 필요가 없다.

**유형 3**이 가장 근본적이다. 일부 플랫폼은 인식하지 못하는 HTTP 메서드를 받으면 그것을 그냥 `GET` 요청 핸들러로 넘긴다. 8.3.3절의 관용성 원칙 — 알 수 없는 메서드에 관대하라 — 을 구현에 반영한 결과다. 그러면 **특정 메서드를 거부하는 방식의 플랫폼 통제는 요청 라인 첫 토큰에 아무 문자열이나 넣는 것으로 우회된다.**

```
JOESHARDWARE /admin/create-user?user=attacker&role=admin HTTP/1.1
Host: www.joes-hardware.com

```

`JOESHARDWARE`는 HTTP 메서드가 아니다. 바로 그것이 요점이다. 거부 목록에 `GET`, `POST`, `HEAD`, `PUT`, `DELETE`가 아무리 촘촘하게 들어 있어도, **목록에 없는 문자열은 무한히 많다.**

#### 이것이 말하는 원리

세 유형을 관통하는 원리를 정리한다.

**첫째, 거부 목록(deny list)은 메서드에 대해서도 실패한다.** 유형 3이 그 증명이다. 7.6절이 인코딩에 대해, 32.5절이 XSS 필터에 대해 같은 결론에 도달하는 것과 정확히 같은 구조다. **표현의 집합이 무한하면 차단 목록은 원리적으로 완전할 수 없다.** 메서드 토큰은 임의 문자열이므로 그 집합은 무한하다.

**둘째, 접근 제어의 위치가 잘못됐다.** 세 유형 모두 "서버 설정이 판단하고 애플리케이션이 동작한다"는 분리에서 나온다. 24.6절이 다층 권한 모델을 다룰 때 첫 번째 원칙이 **결정과 집행이 같은 곳에 있어야 한다**는 것인 이유가 여기에 있다.

**셋째, 그리고 이것이 가장 자주 간과된다 — 메서드는 신뢰할 수 없는 입력이다.** 표 8-2가 이미 그렇게 적었다. 요청 라인의 첫 토큰은 클라이언트가 쓴 문자열이다. `Referer`나 `User-Agent`와 다르지 않다. 8.6절이 헤더에 대해 세울 세 개의 질문 — 누가 쓰는가, 누가 덮어쓸 수 있는가, 검증 수단이 있는가 — 을 메서드에 적용하면 답은 각각 "클라이언트", "해당 없음", "없음"이다.

#### 강화

이 절을 부정형으로 끝내지 않기 위해, 원리에서 곧바로 따라 나오는 처방을 적는다. 상세한 방법론은 24.5절과 24.6절에 있다.

**1) 허용 목록으로 뒤집는다.** "이 메서드를 거부한다"가 아니라 "이 경로에서 허용되는 메서드는 이것들뿐이고 나머지는 전부 거부한다"로 쓴다. 유형 3은 이 전환만으로 사라진다.

**2) 애플리케이션 코드가 메서드를 다시 확인한다.** 상태를 바꾸는 핸들러는 진입점에서 요청 메서드가 기대한 것인지 확인하고, 아니면 `405 Method Not Allowed`를 반환한다. `Allow` 헤더를 함께 보내는 것이 명세가 요구하는 동작이다. 이 확인은 서버 설정과 무관하게 코드 안에 있으므로 배포 구성이 바뀌어도 유지된다. 4.6절이 "배포 의존 신뢰"라고 이름 붙인 문제 유형의 회피다.

**3) 메서드를 접근 제어의 축으로 쓰지 않는다.** 가장 근본적인 처방이다. 접근 제어의 축은 **주체(누가)와 자원(무엇을)** 이어야 하고, 메서드는 그 위에 얹히는 부가 조건이지 그 자체가 경계가 아니다. 24.6절이 다층 권한 모델에서 이 원칙을 세운다.

**4) `PUT`·`DELETE`·`TRACE`·WebDAV 메서드를 필요 없으면 끈다.** 이것은 접근 제어가 아니라 공격 표면 축소다. 12.7절과 12.10절이 서버 강화의 항목으로 다룬다.

> **이 절이 뒷받침하는 것**
>
> - 안전·멱등은 프로토콜이 강제하지 않는 규약이다 → **9.9** (커넥션 실패 시 재시도의 조건), **14.6** (캐시 가능성 판정), **33.1** (요청 위조가 성립하는 조건), **33.2** (`GET` 기반 CSRF)
> - `GET`/`POST`의 노출 지점 차이 → **16.4** (로그가 누출하는 것), **20.4** (fat URL), **23.3** (토큰의 네트워크·로그 노출), **39.8** (GET 기반 GraphQL 질의)
> - WebDAV 메서드의 위험 → **12.7** (WebDAV 메서드와 그 위험), **15.11** (발행 시스템), **28.4** (업로드된 파일의 실행)
> - `TRACE`가 요청 헤더를 응답 본문으로 되돌린다 → **13.6** (메시지 추적), **20.6** (`HttpOnly`의 전제), **25.6** (서버 핑거프린팅)
> - 메서드 제한 우회의 세 유형 → **24.4** (메서드 직접 접근 테스트), **24.5** (HTTP 메서드 제한 테스트), **24.6** (다층 권한 모델)
> - 거부 목록이 메서드에 대해서도 실패한다 → **7.6**, **32.5** (같은 결론의 인코딩판·XSS 필터판), **43.6** (거부·정제·안전한 처리의 비교)

## 8.4 상태 코드 분류와 오용 사례

메서드가 서버에게 무엇을 할지 말한다면, 상태 코드는 클라이언트에게 무슨 일이 일어났는지 말한다. 상태 코드는 응답의 시작줄에 있다.

숫자와 사람이 읽을 수 있는 상태가 함께 반환된다. **숫자 코드는 프로그램의 오류 처리를 쉽게 하고, 이유 구는 사람이 이해하기 쉽게 한다.** 8.2절에서 확인한 대로 판단은 숫자로 한다.

### 다섯 개의 분류

상태 코드는 세 자리 숫자의 첫 자리에 따라 다섯 부류로 묶인다.

| 전체 범위 | HTTP/1.1에서 정의된 범위 | 분류 | 뜻 |
|---|---|---|---|
| 100–199 | 100–101 | 정보성(Informational) | 요청의 일부가 수신됐고 계속 진행하라 |
| 200–299 | 200–206 | 성공(Successful) | 요청이 성공했다 |
| 300–399 | 300–305 | 리다이렉션(Redirection) | 자원이 다른 곳에 있거나, 콘텐츠 대신 다른 응답을 준다 |
| 400–499 | 400–417 | 클라이언트 오류(Client error) | 요청에 클라이언트 쪽의 잘못이 있다 |
| 500–599 | 500–505 | 서버 오류(Server error) | 서버 쪽에서 무언가 잘못됐다 |

**표 8-8. 상태 코드의 다섯 분류 (HTTP-DG 표 3-2 기준)**

> HTTP-DG 표 3-2는 클라이언트 오류의 정의 범위를 400–415로 적었으나, 같은 장의 표 3-9는 416 Requested Range Not Satisfiable과 417 Expectation Failed까지 나열한다. 이 책은 표 3-9를 따라 400–417로 적었다. 코드별 상세는 **부록 D**에 있다.

이 표에서 실무적으로 중요한 규칙은 정의 범위 열에 있다. **정의되지 않은 코드를 받으면, 그것이 속한 범위의 일반적인 구성원으로 취급해야 한다.** 예컨대 5xx의 정의 범위를 벗어난 515를 받았다면 그것을 서버 오류로 처리하면 된다. 프로토콜이 진화하면서 새 코드가 추가되고, 누군가 확장으로 정의한 코드일 가능성이 높기 때문이다.

이 규칙이 두 가지 결과를 낳는다.

**첫째, 상태 코드 공간은 사실상 열려 있다.** 서버는 임의의 세 자리 숫자를 보낼 수 있고, 클라이언트는 첫 자리만 보고 처리해야 한다. 8.3.4절이 메서드에 대해 확인한 것 — 값의 집합이 무한하다 — 이 상태 코드에도 적용된다. 상태 코드 목록으로 분기하는 코드는 목록에 없는 값을 만난다.

**둘째, 그럼에도 첫 자리는 의미를 갖는다.** 그리고 그 의미가 캐시, 프록시, 모니터링, 자동화 도구, 브라우저의 동작을 결정한다. 이 절 후반의 오용 사례 전부가 **첫 자리가 실제 결과와 어긋날 때** 생긴다.

### 각 분류에서 짚어야 할 것

부록 D가 코드별 상세를 다루므로, 여기서는 **분류 자체의 성질**과 뒤의 장들이 인용할 몇 개만 짚는다.

**1xx — 정보성.** HTTP/1.1이 도입했고, 복잡성과 실질적 가치에 대해 논란이 있었던 부류다. 두 개뿐이다. `100 Continue`는 클라이언트가 큰 본문을 보내기 전에 서버가 그것을 받을 의사가 있는지 확인하려 할 때 쓰인다. 클라이언트가 `Expect: 100-continue` 요청 헤더를 보내면 서버가 `100 Continue`로 답하거나 오류를 낸다. 이것은 최적화이며, 서버가 처리할 수 없는 큰 엔티티를 보내는 낭비를 피하는 용도로만 써야 한다.

여기에 상호운용성의 주의사항이 세 겹으로 붙는다. 클라이언트는 `100 Continue`를 영원히 기다리면 안 되고 일정 시간 뒤에는 그냥 본문을 보내야 한다. 클라이언트는 자기가 요청하지 않은 `100 Continue` 응답을 받을 수도 있으므로 그것에 대비해야 한다. 서버는 `100-continue` 기대를 표명하지 않은 클라이언트에게 `100 Continue`를 보내면 안 되지만 실제로 그렇게 하는 서버가 있다. **명세와 구현이 어긋나는 지점의 전형적인 예이며, 프록시가 그 사이에 끼면 더 복잡해진다.** 프록시는 다음 홉 서버의 HTTP 버전을 알아야 `Expect` 헤더를 전달할지 `417 Expectation Failed`로 답할지 결정할 수 있다(→ 13.8).

`101 Switching Protocols`는 서버가 클라이언트가 지정한 다른 프로토콜로 전환한다는 표시이며, `Upgrade` 헤더와 함께 쓰인다. 11.12절의 프로토콜 협상과 37.5절의 WebSocket 업그레이드가 이 코드 위에 서 있다.

**2xx — 성공.** `200 OK`가 압도적으로 많다. 몇 개만 짚는다. `201 Created`는 `PUT`처럼 서버 객체를 만드는 요청에 대한 응답이며, **서버는 이 코드를 보내기 전에 객체를 실제로 만들었어야 한다.** `202 Accepted`는 요청이 접수됐지만 서버가 아직 아무 동작도 수행하지 않았다는 뜻이며, **완료를 보장하지 않는다.** `204 No Content`는 헤더와 상태 줄은 있지만 본문이 없는 응답이다. `206 Partial Content`는 범위 요청의 성공이며 10.9절이 다룬다.

`202`의 성질에 주목하라. 8.3.3절에서 `DELETE`가 삭제를 보장하지 않는다고 했다. `202`는 그 성질을 상태 코드로 명시한 것이다. **성공 부류의 코드가 "동작이 수행됐다"를 뜻하지 않는 경우가 프로토콜 안에 이미 존재한다.**

**3xx — 리다이렉션.** 두 가지 서로 다른 일을 한다. 하나는 자원이 다른 위치에 있다고 알리는 것이고(`Location` 헤더와 함께), 다른 하나는 조건부 요청에 대해 "바뀐 것 없다"고 답하는 것이다(`304 Not Modified`). 14.5절이 후자를 다룬다.

`302`, `303`, `307`의 관계가 자주 혼동된다. 뿌리는 HTTP/1.0과 HTTP/1.1이 이 코드들을 다르게 취급한 데 있다. HTTP/1.0 클라이언트가 `POST` 요청에 `302`를 받으면 `Location`의 URL로 **`GET` 요청을** 보낸다. HTTP/1.1은 같은 동작을 위해 `303 See Other`를 도입했고, 임시 리다이렉트에는 `307 Temporary Redirect`를 쓰도록 정했다. **결국 서버는 클라이언트의 HTTP 버전을 확인해서 어느 코드를 쓸지 골라야 한다.**

`305 Use Proxy`에 대해서는 HTTP-DG가 직접 경고한다. 이 응답은 특정 자원에 대해서만 해석되어야 하며, 클라이언트가 그 프록시를 모든 요청에 쓴다고 가정하면 안 된다. **원문의 표현 그대로 "보안 구멍(security hole)을 만든다."** 클라이언트의 트래픽 경로를 응답 하나로 바꿀 수 있다는 뜻이기 때문이다. 13.4절의 프록시 설정과 15.7절의 프록시 리다이렉션이 같은 위험 부류를 다룬다.

**4xx — 클라이언트 오류.** 이 부류에서 보안상 가장 자주 인용되는 세 개는 `401`, `403`, `404`다.

- `401 Unauthorized`는 인증이 필요하다는 뜻이며, `WWW-Authenticate` 헤더와 함께 온다(→ 21.1).
- `403 Forbidden`은 서버가 요청을 거부했다는 뜻이다. HTTP-DG는 이 코드의 용법을 이렇게 설명한다. 서버가 거부 이유를 밝히고 싶으면 본문에 설명을 넣을 수 있지만, **대개 이 코드는 서버가 거부 이유를 밝히고 싶지 않을 때 쓰인다.**
- `404 Not Found`는 요청한 URL에 해당하는 자원을 찾을 수 없다는 뜻이다.
- `405 Method Not Allowed`는 8.3.4절의 강화 항목에서 나온 코드다. **응답에 `Allow` 헤더를 포함해서 어떤 메서드가 허용되는지 알려야 한다.**
- `407 Proxy Authentication Required`는 `401`의 프록시판이다(→ 13.7, 21.9).

**5xx — 서버 오류.** `500 Internal Server Error`는 서버가 요청을 처리하지 못하게 하는 오류를 만났다는 뜻이다. 실무에서 이 코드는 대개 **처리되지 않은 예외**의 결과이며, 그래서 30.1절의 오류 메시지 익스플로잇이 이 코드를 첫 번째 신호로 삼는다. `501 Not Implemented`는 서버의 능력을 벗어난 요청 — 예컨대 지원하지 않는 메서드 — 에 대한 응답이며, 8.3.3절의 확장 메서드 처리 규칙이 지정한 코드다. `502 Bad Gateway`와 `504 Gateway Timeout`은 프록시·게이트웨이가 발행하는 코드이며 그 자체로 배포 구조에 대한 정보를 준다(→ 25.6).

### 오용 사례

여기서부터가 이 절의 본론이다. 상태 코드는 단순한 결과 통보가 아니다. **경로 위의 여러 주체가 그 숫자를 보고 서로 다른 결정을 내린다.**

```
   응답: HTTP/1.1 200 OK
            │
            ├──▶ 브라우저      : 본문을 렌더링한다
            ├──▶ 캐시          : 저장 가능성을 판정한다        (→ 14.4, 14.6)
            ├──▶ 프록시        : 통과·변환 여부를 결정한다     (→ 13.8)
            ├──▶ 모니터링      : 성공률 집계에 넣는다          (→ 16.5)
            ├──▶ 자동화 도구   : "이 요청은 유효하다"고 판정한다 (→ 25.3, 부록 B)
            └──▶ 공격자        : 존재/부재를 추론한다          (→ 30.3)
```

*그림 8-3. 하나의 상태 코드를 읽는 여섯 주체 (신규 작성)*

이 여섯 주체가 같은 숫자를 읽고 각자 다른 결정을 내린다. 그러므로 **상태 코드가 실제 결과와 어긋나면 여섯 개의 결정이 동시에 어긋난다.**

**표 8-9. 상태 코드의 오용 유형 (신규 작성 — WAHH 여러 장의 사례를 이 책이 유형별로 재구성)**

| # | 오용 | 무엇이 잘못되는가 | 이 책에서 |
|---|---|---|---|
| 1 | **오류를 `200`으로 반환한다** — 본문에는 "권한이 없습니다"라고 쓰고 코드는 `200 OK` | 캐시가 오류 페이지를 정상 응답으로 저장한다. 모니터링이 실패를 성공으로 집계한다. 자동화 도구가 유효한 요청으로 판정한다 | 14.8, 16.5, 30.4 |
| 2 | **`401`과 `403`을 존재 여부에 따라 다르게 준다** | "인증하면 볼 수 있는 자원"과 "아예 없는 자원"이 구별된다. 자원의 존재가 인증 없이 새어 나간다 | 25.3, 25.4, **30.3** |
| 3 | **`404`와 `403`의 응답이 미묘하게 다르다** — 코드는 같아도 본문 길이·응답 시간이 다르다 | 숨겨진 콘텐츠를 무차별 대입으로 열거할 수 있다 | **25.3**, 30.3 |
| 4 | **상태 코드가 조건 분기의 관찰 채널이 된다** | 블라인드 인젝션에서 참/거짓을 코드로 읽어 낸다. 사용자명 열거를 로그인 응답 코드로 수행한다 | 22.2, **27.6**, 30.3 |
| 5 | **`3xx` 응답에 원래 콘텐츠가 본문으로 실린다** | 브라우저는 리다이렉트를 따라가므로 사용자에게는 보이지 않지만, 인터셉팅 프록시로 보면 본문이 그대로 있다. 접근 제어가 "화면에 안 보인다"에 의존한 경우 무력화된다 | **24.1**, 26.3 |
| 6 | **인증 실패를 `302`로 처리하고 `Location`에 사용자 입력을 넣는다** | 리다이렉션 목적지가 사용자 통제 아래 들어간다. 오픈 리다이렉션이 되고, `Location` 값이 헤더 인젝션 지점이 된다 | **8.7**, 35.1, 35.3 |
| 7 | **`500`이 스택 트레이스와 함께 온다** | 프레임워크·버전·파일 경로·SQL 문이 노출된다. 정찰의 1차 재료 | **30.1**, 25.6 |
| 8 | **서버 오류를 `200` + 친절한 안내 페이지로 감싼다** | 1번의 반대 방향. 장애가 관측되지 않아 운영 대응이 늦는다. 그리고 오류가 캐시된다 | 14.8, 16.5, 45.2 |
| 9 | **`305 Use Proxy`를 신뢰한다** | 클라이언트의 트래픽 경로가 응답 하나로 바뀐다 | 13.4, 15.7 |

이 표의 1번과 8번이 서로 반대 방향의 같은 실수라는 점을 짚어 둘 만하다. **둘 다 프로토콜 층위의 상태와 애플리케이션 층위의 상태를 어긋나게 만든다.** 8.2절이 이유 구에 대해 말한 것 — 화면과 코드가 갈릴 수 있다 — 이 여기서 상태 코드 전체로 확장된다.

2·3·4번은 하나로 묶인다. **상태 코드는 정보 채널이다.** 공격자가 관찰할 수 있는 것은 응답 본문만이 아니다. 상태 코드, 응답 시간, 응답 길이, 리다이렉션 여부가 모두 채널이며, 그중 상태 코드가 가장 다루기 쉽다. 30.3절이 "추론을 통한 정보 수집"이라는 제목으로 이 채널 전체를 다룬다.

이 사실에서 나오는 방어 원칙은 하나다. **구별되어서는 안 되는 두 경우는 상태 코드도 같아야 한다.** 존재하지 않는 사용자명과 비밀번호가 틀린 사용자명은 같은 코드, 같은 본문, 비슷한 시간으로 답해야 한다(→ 22.2). 접근 권한이 없는 자원과 존재하지 않는 자원도 마찬가지다. 30.4절이 "일반화된 오류 메시지"를 처방하는 이유가 여기에 있으며, 그 처방은 **본문뿐 아니라 상태 코드에도 적용된다.**

마지막으로 5번에 대해 한마디 더. `3xx` 응답에 본문을 넣는 것 자체는 정상이다. HTTP-DG는 오히려 `HEAD` 이외의 요청에 대한 리다이렉션 응답에는 설명과 링크를 담은 엔티티를 포함하는 것이 좋은 관행이라고 권한다. 문제는 그 본문에 **리다이렉트하기 전에 보여 주려던 원래 콘텐츠**가 들어가는 경우다. 이것은 접근 제어를 "브라우저가 화면에 그리지 않을 것"에 위임한 것이며, 24.1절이 "완전히 보호되지 않은 기능"으로 분류하는 유형이다. 브라우저는 리다이렉트를 따라가지만, 인터셉팅 프록시는 따라가지 않는다.

## 8.5 헤더의 다섯 분류 — 일반, 요청, 응답, 엔티티, 확장

시작줄 다음에는 0개 이상의 HTTP 헤더 필드가 온다. 헤더는 요청과 응답 메시지에 부가 정보를 더하며, 기본적으로는 이름/값 쌍의 목록일 뿐이다.

### 문법

각 헤더의 문법은 단순하다.

```
이름 ":" [선택적 공백] 값 CRLF
```

예를 들면 이렇다.

```
Content-length: 19
```

헤더 목록 전체는 **빈 줄(단독 CRLF)** 로 끝나며, 그 빈 줄이 헤더 목록의 끝이자 본문의 시작을 표시한다. HTTP/1.1처럼 특정 헤더의 존재를 요구하는 버전도 있다(`Host`가 그 예다).

여기서 문법상 한 가지를 반드시 짚어야 한다. **헤더 이어쓰기(continuation line)** 다.

긴 헤더 줄은 여러 줄로 나눠 쓸 수 있다. 규칙은 **추가되는 각 줄의 앞에 공백이나 탭을 최소 하나 붙이는 것**이다.

```
HTTP/1.0 200 OK
Content-Type: image/gif
Content-Length: 8572
Server: Test Server
     Version 1.0
```

이 응답에서 `Server` 헤더의 완전한 값은 `Test Server Version 1.0`이다. 다섯 번째 줄은 독립된 헤더가 아니라 네 번째 줄의 연장이다.

이 규칙을 파서의 관점에서 다시 읽으면 다음과 같다.

> **빈 줄이 아니면서 공백이나 탭으로 시작하는 줄은, 앞 헤더의 값에 이어 붙는다.**

즉 헤더 블록을 파싱하려면 각 줄의 **첫 문자**를 봐야 하고, 첫 문자가 무엇이냐에 따라 그 줄은 새 헤더가 되거나, 앞 헤더의 일부가 되거나, 헤더 블록의 끝이 된다. **한 문자가 메시지 구조를 결정하는 또 하나의 지점**이며, 8.7절이 다룰 인젝션의 표면적을 넓히는 요소다. 인젝션된 개행 다음에 공백을 붙이면 그것은 새 헤더가 아니라 앞 헤더의 연장이 되고, 붙이지 않으면 새 헤더가 된다. 공격자는 둘 중 무엇을 원하든 고를 수 있다.

### 다섯 분류

HTTP 헤더는 다섯 부류로 나뉜다. 이 분류는 **헤더가 어떤 메시지에 나타날 수 있고 무엇에 대해 말하는가**에 따른 것이다.

**표 8-10. 헤더의 다섯 분류 (HTTP-DG 3장 기준, 대표 예와 참조 열은 이 책이 구성)**

| 분류 | 나타나는 곳 | 무엇에 대해 말하는가 | 대표 예 | 이 책에서 |
|---|---|---|---|---|
| **일반(General)** | 요청·응답 양쪽 | 메시지 자체의 성질 | `Date`, `Connection`, `Via`, `Transfer-Encoding`, `Upgrade`, `Cache-Control`, `Trailer`, `MIME-Version` | 9.2, 10.3, 13.6, 14.5 |
| **요청(Request)** | 요청만 | 요청의 출처, 클라이언트의 선호와 능력 | `Host`, `Referer`, `User-Agent`, `From`, `Accept*`, `If-*`, `Range`, `Authorization`, `Cookie`, `Expect`, `Max-Forwards`, `Proxy-Authorization` | **8.6**, 10.8, 10.10, 13.6, 21.1 |
| **응답(Response)** | 응답만 | 응답자의 정체와 능력, 응답 처리 지시 | `Server`, `Age`, `Retry-After`, `Warning`, `Vary`, `Accept-Ranges`, `WWW-Authenticate`, `Proxy-Authenticate`, `Set-Cookie` | 14.5, 14.8, 20.5, 21.1, 25.6 |
| **엔티티(Entity)** | 요청·응답 양쪽 | 본문의 크기·타입·내용, 또는 자원 자체 | `Content-Type`, `Content-Length`, `Content-Encoding`, `Content-Language`, `Content-MD5`, `Content-Range`, `Content-Base`, `Location`, `Allow`, `ETag`, `Expires`, `Last-Modified` | **10장 전체**, 8.7 |
| **확장(Extension)** | 어디든 | 명세에 없는 것 | `X-Forwarded-For`, `Client-ip`, `Set-Cookie2`, `X-Cache`, `UA-*` | **4.6**, **8.6**, 20.5 |

이 표에 대해 두 가지를 명확히 해야 한다.

**첫째, 이 분류는 의미의 분류이지 신뢰의 분류가 아니다.** "요청 헤더"라는 딱지는 그 헤더가 요청에만 나타난다는 뜻이지, 그 값이 참이라는 뜻이 아니다. `Host`도 `Referer`도 `User-Agent`도 전부 요청 헤더 부류에 함께 들어 있지만, 세 헤더가 서버에게 주는 신뢰도는 전부 다르고 전부 낮다. 8.6절 전체가 이 지점에 관한 것이다.

**둘째, 확장 헤더의 지위가 중요하다.** 확장 헤더는 애플리케이션 개발자가 만들었지만 아직 공인된 HTTP 명세에 들어가지 않은 비표준 헤더다. 명세는 이렇게 요구한다. **HTTP 프로그램은 확장 헤더를 이해하지 못하더라도 견디고 전달해야 한다.**

이 요구가 확장성을 만들었다. 그리고 그 대가를 4.6절이 이미 청구했다. `X-Forwarded-For`가 확장 요청 헤더라는 사실, 그리고 "이해 못 해도 전달하라"가 명세의 요구라는 사실이 결합하면, **클라이언트가 넣은 확장 헤더가 경로 끝까지 살아서 도착한다.** 4.6절의 첫 번째 문제 — 클라이언트가 XFF를 직접 쓸 수 있다 — 의 프로토콜적 근거가 이 문단이다.

HTTP-DG가 `Client-ip` 헤더에 대해 부록 C에 남긴 주석이 이 지위를 정확히 요약한다.

> **구현자는 이 헤더의 값으로 제공되는 정보가 안전하지 않다는 것을 알아야 한다.**

2002년의 레퍼런스 문서에 이미 적혀 있던 문장이다.

헤더별 상세는 **부록 E**에 정리했다. 알파벳순 목록과 각 헤더의 보안 주석, 그리고 아래에서 다룰 홉 단위/종단 간 구분표가 거기 있다.

### 홉 단위 헤더와 종단 간 헤더

다섯 분류와 **직교하는** 또 하나의 구분이 있다. 이것이 이 절에서 본문에 남겨야 할 두 번째이자 마지막 구분이다.

- **종단 간(end-to-end) 헤더**는 최종 수신자까지 전달되어야 한다. 중간자는 그것을 전달해야 하고, 캐시는 그것을 저장해야 한다.
- **홉 단위(hop-by-hop) 헤더**는 **하나의 커넥션에만** 의미가 있다. 중간자는 그것을 처리하고 **제거한 뒤** 다음 홉으로 넘겨야 한다.

이 구분을 표현하는 메커니즘이 `Connection` 헤더다. `Connection` 헤더의 값은 쉼표로 구분된 **커넥션 토큰**의 목록이며, 세 종류의 토큰이 들어갈 수 있다.

1. **HTTP 헤더 필드 이름** — 이 커넥션에만 관련 있는 헤더를 나열한다
2. **임의의 토큰 값** — 이 커넥션에 대한 비표준 옵션을 기술한다
3. **`close`** — 이 트랜잭션이 끝나면 지속 커넥션을 닫는다

첫 번째가 이 구분의 핵심이다. **커넥션 토큰이 HTTP 헤더 필드의 이름을 담고 있으면, 그 헤더 필드는 커넥션 고유의 정보를 담고 있으므로 전달되어서는 안 된다.** 메시지를 전달하기 전에 그 헤더들을 삭제해야 한다. HTTP-DG는 이 관행을 **"헤더 보호(protecting the header)"** 라 부른다. `Connection` 헤더가 로컬 헤더의 우발적 전달을 막아 주기 때문이다.

```
HTTP/1.1 200 OK
Cache-control: max-age=3600
Connection: meter, close, bill-my-credit-card
Meter: max-uses=3, max-refuses=6, dont-report
```

이 응답을 받은 프록시가 해야 할 일은 셋이다. `meter`라는 토큰이 헤더 이름이므로 `Meter` 헤더를 삭제한다. `close` 토큰에 따라 트랜잭션 후 커넥션을 닫을 준비를 한다. `bill-my-credit-card`라는 비표준 옵션을 처리한다. **그리고 `Connection` 헤더 자체도 삭제한 뒤** 메시지를 다음 홉으로 넘긴다.

여기에 더해, `Connection` 헤더에 나열되지 않아도 **본래 홉 단위인 헤더들**이 있다. 프록시해서는 안 되는 것들이다.

| 헤더 | 왜 홉 단위인가 |
|---|---|
| `Connection` | 자기 자신이 이 커넥션의 옵션을 기술한다 |
| `Proxy-Authenticate` | 특정 프록시가 발행한 챌린지다 (→ 13.7, 21.9) |
| `Proxy-Connection` | HTTP/1.0 프록시와의 커넥션 옵션이다 (→ 9.7) |
| `Transfer-Encoding` | 이 커넥션 구간에서 적용된 전송 인코딩이다 (→ 10.3) |
| `Upgrade` | 이 커넥션을 다른 프로토콜로 전환하자는 제안이다 (→ 11.12, 37.5) |

**표 8-11. `Connection`에 나열되지 않아도 홉 단위인 헤더 (HTTP-DG 4장 기준, 사유 열은 이 책이 추가)**

이 구분이 왜 보안 주제인지는 두 문장으로 정리된다.

**첫째, 규칙을 지키지 않는 중간자가 존재한다.** 홉 단위 헤더를 그대로 전달하는 프록시가 실제로 배포되어 있고, 그것이 9.7절의 "멍청한 프록시" 문제이며 13.8절의 헤더 보존 문제다. `Connection: keep-alive`가 그대로 전달되어 커넥션이 의도치 않게 유지되는 고전적 사례가 여기서 나온다.

**둘째, 그리고 더 중요하게 — 홉 단위 헤더는 "누가 이 값을 소비하는가"를 정하는 규칙이다.** `Transfer-Encoding`이 홉 단위라는 것은 각 홉이 그것을 자기 구간에서만 해석한다는 뜻이고, 따라서 **홉마다 본문의 경계를 다르게 셀 수 있다는 뜻이기도 하다.** 10.4절이 이 지점을 정면으로 다룬다. 8.5절의 이 표는 그 논의의 전제다.

> **이 절이 뒷받침하는 것**
>
> - 상태 코드의 다섯 분류와 정의 범위 밖 코드의 처리 규칙 → **부록 D** (코드별 상세), **14.4** (캐시의 처리 단계)
> - 상태 코드가 여섯 주체의 결정을 동시에 좌우한다 → **14.8** (민감 응답 캐싱), **16.5** (방어자의 로그), **30.3** (추론 채널), **30.4** (일반화된 오류 메시지)
> - 헤더 이어쓰기의 문법 — 공백으로 시작하는 줄은 앞 헤더의 연장이다 → **8.7** (인젝션의 표면), **13.12** (파싱 불일치)
> - 다섯 분류는 의미의 분류이지 신뢰의 분류가 아니다 → **8.6** (헤더의 신뢰성)
> - 확장 헤더는 "이해 못 해도 전달하라"가 명세의 요구다 → **4.6** (XFF가 왜 클라이언트로부터 살아서 도착하는가), **20.5** (`Set-Cookie`도 확장 헤더로 출발했다)
> - 홉 단위와 종단 간의 구분, `Connection` 헤더의 세 가지 토큰 → **9.2** (커넥션 처리와 홉 단위 헤더), **9.7** (멍청한 프록시), **10.3** (`Transfer-Encoding`), **10.4** (본문 경계 불일치), **13.8** (헤더 보존), **부록 E**

## 8.6 헤더의 신뢰성 — Referer, Host, X-Forwarded-For, User-Agent를 믿을 수 있는가

4.6절은 IP 주소에 대해 다음 문장으로 끝났다.

> **주소는 신원이 아니고, 주소에 대한 진술은 더욱 신원이 아니다.**

이 절은 그 문장을 HTTP 헤더 층위에서 일반화한다. 6.6절 표 6-9의 여덟 번째 행이 이 절을 예고했다. **"줄 하나를 더하는 일이 줄 하나를 쓰는 것만큼 쉽다"** 는 구조가 만드는 신뢰 경계다.

### 질문의 형태를 바꾼다

"이 헤더를 믿을 수 있는가"는 잘못 세워진 질문이다. 답이 거의 언제나 "아니오"이기 때문에 유용한 정보를 주지 않는다. 실무에서 필요한 것은 **어떤 종류의 진술이며 누가 그것을 만들었는가**를 아는 것이다.

그래서 이 절은 각 헤더에 대해 세 개의 질문을 던진다.

1. **누가 이 값을 처음 쓰는가?** — 원 작성자
2. **경로 위에서 누가 그것을 덮어쓰거나 덧붙이거나 지울 수 있는가?** — 경로상의 수정자
3. **수신자가 그 값의 진위를 검증할 수단을 갖는가?** — 검증 가능성

세 번째 질문에 "예"라고 답할 수 있는 요청 헤더는 사실상 없다. 그러나 첫 번째와 두 번째의 답은 헤더마다 다르고, **그 차이가 방어를 어디에 놓아야 하는지를 결정한다.**

### 헤더별 작성자·수정자·검증 가능성

**표 8-12. 주요 요청 헤더의 작성자와 경로상 수정 가능성 (신규 작성)**

| 헤더 | 값을 처음 쓰는 주체 | 경로 위에서 수정할 수 있는 주체 | 수신자의 검증 수단 | 이 값에 의존하는 흔한 설계 | 이 책에서 |
|---|---|---|---|---|---|
| `Host` | **클라이언트** (URL에서 복사) | 모든 중간자 | 없음 (허용 목록 대조만 가능) | 가상 호스트 선택, 캐시 키, 절대 URL 생성 | **15.2**, 13.5, 12.4.1 |
| `Referer` | **클라이언트** (브라우저가 자동, 또는 임의 기재) | 모든 중간자, 클라이언트 자신 | 없음 | CSRF 방어, 딥링크 차단, 유입 경로 분석 | **33.4**, 26.1 |
| `User-Agent` | **클라이언트** (자유 기재) | 모든 중간자 | 없음 | 콘텐츠 협상, 봇 차단, WAF 규칙, 기능 게이팅 | 16.9, 25.6, 12.11 |
| `X-Forwarded-For` | **클라이언트 또는 첫 프록시** | 모든 중간자 (덧붙임이 명세된 동작) | 없음 (신뢰 프록시 목록으로 부분적) | 클라이언트 IP 판정, 레이트 리밋, IP 차단 | **4.6**, 20.2, 24.2 |
| `Client-ip` | 클라이언트 또는 프록시 | 모든 중간자 | 없음 — **원서가 명시적으로 "안전하지 않다"고 표기** | XFF와 동일 | 4.6, 20.2 |
| `Via` | 첫 HTTP/1.1 중간자 (필수) | 모든 중간자 (제거 포함) | 없음 | 경로 추적, 루프 탐지 | **13.6**, 13.11 |
| `From` | 클라이언트 (자유 기재) | 모든 중간자 | 없음 | 로봇 운영자 식별 | 16.10 |
| `Cookie` | 브라우저 (**서버가 이전에 발급**) | 모든 중간자, 클라이언트 자신 | **서명·암호화가 있으면 부분적으로 가능** | 세션 식별, 인증 상태, 개인화 | 20.5, 23.2, 26.7 |
| `Authorization` | 클라이언트 | 모든 중간자 | **자격증명 검증으로 가능** | 인증 | 21.1~21.8 |
| `Content-Length` | 요청 작성자 | 모든 중간자 | 실제 바이트 수와 대조 가능 | 본문 경계 결정 | **10.2**, 10.4 |
| `Accept*` | 브라우저 설정 | 모든 중간자 | 없음 | 콘텐츠 협상, 캐시의 `Vary` 키 | 10.10, 14.8 |
| `Connection` | 직전 홉 | **다음 홉이 소비하고 제거해야 한다** | 해당 없음 (홉 단위) | 커넥션 관리 | 9.2, 8.5 |

이 표에서 읽어야 할 것은 네 가지다.

**첫째, "검증 수단" 열에 실질적인 답이 있는 행은 셋뿐이다.** `Content-Length`(실제 길이와 대조), `Authorization`(자격증명 검증), 그리고 서명된 `Cookie`다. 나머지는 전부 "없음"이다. 그리고 이 셋의 공통점은 **값 안에 검증 가능한 것이 들어 있다**는 것이다. 길이는 실물과 비교할 수 있고, 비밀번호는 저장된 것과 비교할 수 있으며, 서명은 키로 확인할 수 있다. 나머지 헤더는 **진술일 뿐이고 진술을 검증할 참조점이 수신자에게 없다.**

**둘째, "경로 위에서 수정할 수 있는 주체" 열이 거의 전부 "모든 중간자"다.** HTTP/1.x에는 헤더의 무결성을 보호하는 메커니즘이 없다. TLS는 채널을 보호하지만 그것은 **홉 단위 보호**다. TLS 종료 지점 뒤에서 헤더는 다시 평문이고, 그 뒤의 모든 중간자가 자유롭게 읽고 쓴다(→ 19.8, 13.8).

**셋째, `Connection` 행만 성질이 다르다.** 그것은 홉 단위 헤더이므로 애초에 "종단까지 전달되는 값"이 아니다. 8.5절의 구분이 여기서 실용적 의미를 갖는다. **홉 단위 헤더에 대해 "누가 썼는가"를 묻는 것은 범주 오류다.** 직전 홉이 썼고, 지금 홉이 소비한다. 그게 전부다.

**넷째, 그리고 이것이 이 표의 핵심 — 다섯 번째 열이 위험의 목록이다.** 각 헤더가 위험한 이유는 그 값이 거짓일 수 있어서가 아니라, **거짓일 수 있는 값에 의존하는 설계가 실제로 존재하기 때문이다.**

이제 네 개의 헤더를 하나씩 본다.

### Referer — 브라우저가 채우고, 브라우저가 채우지 않을 수도 있다

`Referer`는 클라이언트가 이 URL을 어디서 얻었는지 서버에게 알려 주기 위해 요청에 삽입된다. 이름의 철자가 틀린 것은 HTTP 초창기의 유산이며, 전 세계 영어 교열자들의 좌절과 함께 그대로 남았다.

브라우저의 동작은 단순하다. **페이지 A를 받아서 페이지 B로 가는 링크를 클릭하면, 브라우저가 요청에 값 A를 담은 `Referer` 헤더를 넣는다.**

그리고 HTTP-DG 부록 C가 곧바로 붙이는 단서가 이 헤더의 성질 전부를 결정한다.

> **직접 입력한 URL에 대한 요청에는 `Referer` 헤더가 들어가지 않는다.**

즉 **`Referer`는 있을 수도 있고 없을 수도 있는 헤더다.** 그리고 없는 것이 정상인 경우가 여럿이다.

- 사용자가 주소창에 URL을 직접 입력한 경우
- 북마크로 접근한 경우
- 새 탭에서 연 경우
- 프라이버시 설정이나 확장 프로그램이 헤더를 제거한 경우
- 브라우저가 아닌 클라이언트가 요청을 보낸 경우

여기에 원서가 명시하는 또 하나의 성질이 붙는다. **이 헤더는 서버의 편의를 위한 자발적 노력(voluntary effort)이다.** 일부 페이지는 사적인 것이므로 프라이버시 우려가 있고, HTTP/1.1 명세는 **애플리케이션 작성자가 사용자에게 이 헤더의 전송 여부를 선택하게 하라고 권고한다.**

이 두 성질 — 없을 수 있고, 자발적이다 — 에 6.7절의 명제를 더하면 결론이 나온다. **`Referer`는 요청을 만드는 쪽이 완전히 통제하는 값이다.** 브라우저는 정해진 규칙대로 채우지만, 브라우저가 아닌 것은 아무 값이나 채운다. 명령줄 도구로 임의의 `Referer`를 보내는 데 필요한 것은 한 줄이다.

#### 그러므로 Referer 검증은 두 방향으로 실패한다

`Referer`에 의존하는 가장 흔한 설계는 CSRF 방어다. "이 요청의 `Referer`가 우리 사이트인가"를 확인하는 것이다. 33.4절이 이 방어를 정면으로 평가하며, 여기서는 **왜 그것이 원리적으로 부분적인 방어인지**만 세운다.

**표 8-13. `Referer` 검증의 실패 구조 (신규 작성)**

| 검증 방식 | 실패 조건 | 결과 |
|---|---|---|
| 헤더가 없으면 통과시킨다 | 공격자가 헤더를 생략한다 | **우회.** 헤더 생략은 정상 동작이므로 막을 명분도 없다 |
| 헤더가 없으면 거부한다 | 정상 사용자가 북마크·직접 입력·프라이버시 설정으로 접근한다 | **정상 사용자 차단.** 대개 이 규칙은 도입 후 제거된다 |
| 값에 자기 도메인이 포함되는지 본다 | `http://evil.com/www.joes-hardware.com/` | **우회.** 부분 문자열 검사는 7.9절의 표시 문제와 같은 계열 |
| 값이 자기 도메인으로 시작하는지 본다 | `http://www.joes-hardware.com.evil.com/` | **우회.** 접두 검사도 마찬가지다 |
| 값을 URL로 파싱해서 호스트를 비교한다 | 파서가 7.2절의 `@` 문법이나 7.9절의 동형이의 문자를 다르게 읽는다 | 조건부. 그나마 가장 견고하지만 파서 의존 |
| HTTPS→HTTP 전환 시의 동작을 고려하지 않는다 | 브라우저가 헤더를 보내지 않는다 | 정상 요청이 차단되거나, 없음을 허용하다 우회된다 |

이 표의 첫 두 행이 핵심이며, **둘 중 어느 쪽을 골라도 문제가 생긴다**는 것이 `Referer` 검증의 구조적 한계다. 헤더가 없는 것을 허용하면 우회되고, 허용하지 않으면 정상 사용자가 막힌다. 33.4절이 `Referer` 검증을 **일차 방어가 아니라 보조 방어**로만 권하는 이유가 여기에 있다.

세 번째와 네 번째 행은 7장의 결론을 그대로 재활용한다. **부분 문자열 검사는 도메인 검증이 아니다.** 7.9절이 사람과 기계의 판단이 갈리는 지점을 다섯 계층에서 열거했고, 그중 문법 계층의 문제가 여기서 그대로 재현된다.

#### 반대 방향 — Referer가 새는 것

`Referer`는 신뢰의 문제이면서 동시에 **누출**의 문제다. 표 8-5에서 이미 봤다. **URL 쿼리 문자열은 외부 사이트로 나가는 `Referer` 헤더에 실린다.**

Joe's Hardware의 비밀번호 재설정 페이지가 이런 URL이라고 하자.

```
https://www.joes-hardware.com/reset?token=8f3a91c7d2e4b6
```

이 페이지에 외부 광고, 분석 스크립트, 외부 폰트, 또는 그냥 파트너 사이트로 가는 링크가 하나라도 있으면, 그 외부 서버는 요청 헤더에서 다음을 받는다.

```
Referer: https://www.joes-hardware.com/reset?token=8f3a91c7d2e4b6
```

**재설정 토큰이 제3자의 액세스 로그에 기록된다.** 그 로그는 Joe's Hardware의 통제 밖에 있고, 보존 기간도, 접근 권한도, 유출 시의 통보 의무도 다르다. 그리고 이 누출은 어떤 취약점 스캐너도 취약점으로 보고하지 않는다. **정상 동작이기 때문이다.**

원서가 이 헤더에 대해 프라이버시 우려를 언급하며 "웹 서버와 관리자가 당신이 어디서 왔는지 볼 수 있고, 잠재적으로 당신의 서핑을 더 잘 추적할 수 있게 한다"고 쓴 것이 2002년이다. 그 우려의 애플리케이션 보안판이 이것이다. 16.4절(로그가 누출하는 것)과 26.1절(클라이언트를 통해 데이터를 전달할 때)이 이 경로를 다룬다.

이 절이 `Referer`에 대해 남기는 두 문장은 다음과 같다.

> **들어오는 `Referer`는 검증의 근거로 삼기에 너무 약하고, 나가는 `Referer`는 비밀을 담기에 너무 넓다.**

### Host — 값이 아니라 라우팅 입력이다

`Host` 헤더는 클라이언트가 요청을 보내려는 기계의 인터넷 호스트명과 포트 번호를 서버에 제공한다. 그 호스트명과 포트는 **클라이언트가 요청하던 URL에서 온 것**이다.

이 헤더의 존재 이유는 하나다. **서버가 호스트명에 따라 서로 다른 상대 URL을 구별할 수 있게 하고, 그래서 하나의 기계(같은 IP 주소)에서 여러 호스트명을 호스팅할 수 있게 하는 것.** 15.2절이 다룰 가상 호스팅이다.

명세의 요구는 강하다. **HTTP/1.1 클라이언트는 모든 요청에 `Host` 헤더를 넣어야 하고, HTTP/1.1 서버는 `Host` 헤더를 주지 않는 HTTP/1.1 클라이언트에게 `400 Bad Request`로 응답해야 한다.**

여기까지가 프로토콜의 서술이다. 보안 서술은 8.2절에서 이미 시작됐다. 요청 라인은 대개 경로만 담고, 서버는 **자기 자신을 URL의 호스트/포트로 가정할 수 있다.** 그 가정의 근거가 `Host` 헤더다. 그리고 `Host` 헤더는 클라이언트가 쓴 문자열이다.

#### 서버가 이 값으로 하는 일

`Host` 헤더가 다른 요청 헤더와 결정적으로 다른 점은 그것이 **정보가 아니라 입력**이라는 것이다. `User-Agent`는 서버가 무시해도 요청 처리가 진행된다. `Host`는 무시할 수 없다. 서버는 이 값으로 최소 세 가지를 결정한다.

**1) 어느 가상 호스트의 docroot를 쓸 것인가.** 같은 IP, 같은 포트에 여러 사이트가 있을 때, 어느 사이트의 파일 트리를 뒤질지가 이 값으로 정해진다(→ 12.4.1, 15.2).

**2) 캐시 키에 무엇이 들어갈 것인가.** 공유 캐시는 URL과 `Host`를 조합해 캐시 키를 만든다. `Host` 값이 바뀌면 다른 캐시 항목이 된다(→ 14.5, 14.8).

**3) 애플리케이션이 만드는 절대 URL의 호스트 부분.** 이것이 가장 자주 간과된다. 애플리케이션은 자기 자신의 주소를 알아야 할 때가 있다. 리다이렉션의 `Location` 헤더, 비밀번호 재설정 링크, 이메일 본문에 넣을 URL, 페이지 안의 절대 경로 링크가 그렇다. 많은 프레임워크가 이때 **요청의 `Host` 헤더를 읽어서** 자기 주소를 구성한다.

```python
# 흔한 패턴 — 요청 헤더로 자기 주소를 만든다
reset_url = f"https://{request.headers['Host']}/reset?token={token}"
send_email(user.email, reset_url)
```

**사용자가 쓴 문자열이 서버의 자기 이름이 된다.** 그리고 그 이름이 담긴 링크가 이메일로 발송된다. 이 코드가 무엇을 허용하는지는 명백하다.

#### 프록시 경로에서의 중복

8.2절에서 짚은 문제가 여기서 다시 나온다. 프록시로 가는 요청은 요청 라인에 절대 URI를 담고, 그러면서도 `Host` 헤더를 함께 담는다. **같은 정보가 두 곳에 있다.**

```
GET http://www.joes-hardware.com/index.html HTTP/1.1
Host: www.other-site.example
```

이 요청을 받은 중간자는 어느 값을 목적지로 삼아야 하는가. 명세상의 답은 있지만, **경로에 중간자가 여러 개면 각각이 그 답을 다르게 구현할 수 있다.** 하나는 요청 라인을 보고 라우팅하고, 다른 하나는 `Host`를 보고 가상 호스트를 고르면, 요청 하나가 두 개의 서로 다른 목적지 판정을 받는다. 13.5절이 이 문제를 다루고, 13.12절이 그것을 파싱 불일치 지점 목록에 넣는다.

#### 방어

`Host`에 대한 처방은 4.6절이 XFF에 대해 내린 것과 같은 구조다. **값을 검증하려 하지 말고, 값이 통제된 집합에서만 오도록 구조를 바꾼다.**

**1) 허용 호스트 목록을 둔다.** 애플리케이션이 서비스하는 호스트명을 설정으로 명시하고, `Host` 값이 그 목록에 없으면 요청을 거부한다. 이것이 유일하게 실질적인 검증이며, "검증 수단이 없다"는 표 8-12의 판정에 대한 유일한 예외다. **참조점을 수신자 쪽에 두었기 때문에 가능해진다.**

**2) 기본 가상 호스트를 거부로 설정한다.** 어느 가상 호스트에도 매칭되지 않는 `Host` 값이 왔을 때 첫 번째 가상 호스트로 폴백하는 것이 많은 서버의 기본 동작이다. 그 폴백을 명시적 거부로 바꾼다(→ 12.9, 15.2).

**3) 절대 URL을 만들 때 요청 헤더를 쓰지 않는다.** 애플리케이션의 정본 호스트명은 **설정값**이어야 한다. 요청마다 달라질 수 있는 값이 아니다.

```python
# 옳은 패턴 — 자기 주소는 설정에서 온다
reset_url = f"{settings.CANONICAL_BASE_URL}/reset?token={token}"
```

**4) 캐시 앞단에서 `Host`를 정규화한다.** 공유 캐시가 있는 배포에서는 대소문자, 후행 점, 포트 표기의 변형이 서로 다른 캐시 항목을 만들 수 있다. 엣지에서 정본 형태로 정규화하는 것이 14.8절의 캐시 오염을 줄인다.

1번과 3번의 공통 구조를 이름 붙여 두자. **신뢰 경계를 넘는 값 중 자기 정체성에 관한 것은 경계 밖에서 받지 않는다.** 4.6절이 "신뢰 경계의 입구를 유일한 정본 생성 지점으로 만든다"고 표현한 것의 다른 얼굴이며, 44.1절의 도메인 프리미티브가 코드 안에서 같은 일을 한다.

### X-Forwarded-For와 Client-ip — 4.6절이 이미 한 일

이 두 헤더는 4.6절이 상세히 다뤘다. 여기서는 **헤더 분류상의 위치**와 그 위치가 갖는 결과만 확인한다.

`X-Forwarded-For`는 많은 프록시 서버가 요청이 누구를 대신해 전달되었는지 기록하기 위해 쓰는 헤더다. `Client-ip`는 일부 오래된 클라이언트와 프록시가 클라이언트가 실행 중인 기계의 IP 주소를 전송하기 위해 쓰는 헤더다. 둘 다 **확장 요청 헤더**이며, RFC 2616에 정의되어 있지 않다.

표 8-10에서 확인한 확장 헤더의 성질이 여기서 결과를 낸다.

- 확장 헤더이므로 **명세가 정의한 처리 규칙이 없다.** 누가 넣고, 누가 덮어쓰고, 누가 지워야 하는지에 대한 표준이 없다.
- 그럼에도 명세는 **이해하지 못하는 헤더도 전달하라**고 요구한다. 그래서 클라이언트가 넣은 값이 경로 끝까지 살아서 도착한다.
- 그리고 종단 간 헤더로 취급되므로 홉 단위 헤더처럼 각 홉에서 소비되고 사라지지도 않는다.

**세 성질이 결합하면 4.6절의 첫 번째 문제가 된다. 클라이언트가 쓴 값이 프록시가 쓴 값과 같은 헤더 안에 구별 없이 나란히 놓인다.**

HTTP-DG 부록 C가 `Client-ip` 항목에 남긴 주석을 다시 인용한다. **"구현자는 이 헤더의 값으로 제공되는 정보가 안전하지 않다는 것을 알아야 한다."** 같은 문서가 `X-Forwarded-For`에 대해서는 그런 주석을 달지 않았다는 점이 오히려 흥미롭다. 두 헤더의 신뢰 성질은 동일하다.

XFF의 다섯 가지 문제와 여섯 가지 처방은 4.6절에 있다. 이 절이 그 논의에 더하는 것은 하나다. **XFF의 문제는 XFF의 문제가 아니라 헤더 일반의 문제다.** 표 8-12의 어느 행을 봐도 같은 구조가 반복된다. XFF가 유독 자주 문제가 되는 이유는 그것이 **보안 결정에 직접 쓰이기 때문**이지, 그 헤더가 특별히 더 약해서가 아니다.

### User-Agent — 사실을 말하도록 진화하지 않은 문자열

`User-Agent` 헤더는 클라이언트 애플리케이션이 자기를 식별하기 위해 쓰며, 서버 쪽의 `Server` 헤더와 대칭이다. 값은 제품 이름과 클라이언트 애플리케이션을 설명하는 선택적 코멘트다.

원서가 이 헤더에 대해 적은 성질 세 가지가 이 헤더의 신뢰도를 전부 설명한다.

**첫째, 형식이 다소 자유 형식(free-form)이다.** 값은 클라이언트 제품마다, 릴리스마다 다르다.

**둘째, 클라이언트가 실행 중인 기계에 대한 정보까지 담기도 한다.**

**셋째, 오래된 프록시나 게이트웨이가 `Via` 헤더에 해당하는 내용을 `User-Agent` 헤더 안에 끼워 넣어도 놀라지 말라.**

세 번째가 특히 중요하다. **이 필드는 클라이언트만 쓰는 필드가 아니다.** 경로상의 중간자가 자기 정보를 여기에 덧붙이는 구현이 실제로 존재했다. 표 8-12의 "경로 위에서 수정할 수 있는 주체" 열이 `User-Agent`에 대해서도 "모든 중간자"인 이유다.

여기에 WAHH가 지적하는 역사적 사실을 더한다. **대부분의 브라우저가 역사적 이유로 `Mozilla` 접두를 포함한다.** 원래 지배적이던 넷스케이프 브라우저의 `User-Agent` 문자열이 그것이었고, 다른 브라우저들이 자기가 그 표준과 호환된다는 것을 웹사이트에 주장하고 싶어 했기 때문이다. 컴퓨팅 역사의 다른 기벽들처럼, 이것은 너무 굳어져서 그 뒤로도 계속 유지됐다.

이 사실이 말하는 것은 단순하다. **`User-Agent` 문자열은 자기가 무엇인지 정확히 말하기 위해 진화하지 않았다. 서버에게서 원하는 콘텐츠를 얻어내기 위해 진화했다.** 그 문자열의 역사 자체가 "이 값은 사실 주장이 아니라 협상 전술이다"를 증명한다.

#### 이 값에 의존하는 설계들

그럼에도 이 헤더에 의존하는 설계는 흔하다.

| 의존하는 설계 | 우회 방법 | 부작용 | 이 책에서 |
|---|---|---|---|
| 콘텐츠 협상 — 브라우저별로 다른 페이지 | 문자열 위조 | `Vary: User-Agent`가 캐시 항목을 폭발시키고, 오설정 시 사용자 간 응답 혼동 | 14.8, 10.10 |
| 모바일/데스크톱 분기 | 문자열 위조 | 모바일 버전에 다른 보안 통제가 걸린 경우 우회 | 26.3 |
| 봇·크롤러 차단 | 문자열 위조 | 정직한 봇만 차단된다 | **16.9**, 16.10 |
| WAF·IPS의 시그니처 규칙 | 문자열 변형 | 도구 기본값만 차단된다 | **12.11** |
| 기능·라이선스 게이팅 | 문자열 위조 | 클라이언트 측 통제의 전형적 실패 | **26.1** |
| 이상 탐지의 한 특징 | 문자열 위조 | **부작용 없음 — 올바른 용법** | 16.5, 23.6 |

**표 8-14. `User-Agent`에 의존하는 설계와 그 결과 (신규 작성)**

마지막 행이 이 표의 결론이다. **`User-Agent`는 통계이지 판정 근거가 아니다.** 전체 트래픽의 분포를 보는 데는 유용하고, 이상 탐지의 여러 특징 중 하나로 쓰는 것도 정당하다. 그러나 **그 값 하나로 허용/거부를 가르는 순간 그것은 클라이언트가 스스로 발급하는 통행증이 된다.**

원서가 `UA-Color`, `UA-CPU`, `UA-Disp`, `UA-OS`, `UA-Pixels` 같은 확장 헤더들에 대해 남긴 각주도 같은 계열의 판단이다.

> **일부 클라이언트가 구현하기는 하지만, `UA-*` 헤더는 해로운 것으로 간주될 수 있다. 콘텐츠, 특히 HTML은 특정 클라이언트 구성을 겨냥해서는 안 된다.**

2002년의 서술이지만 판단의 근거는 지금도 같다. **클라이언트가 자기 환경에 대해 하는 진술에 서버의 동작을 결부시키면, 그 진술이 서버의 동작을 조종하는 손잡이가 된다.**

### Via — 경로에 대한 진술

`Via` 헤더는 메시지가 프록시와 게이트웨이를 통과하는 것을 추적하는 데 쓰인다. 어떤 애플리케이션이 요청과 응답을 처리하고 있는지 보기 위한 정보성 헤더다.

메시지가 클라이언트나 서버로 가는 길에 HTTP 애플리케이션을 통과할 때, 그 애플리케이션은 `Via` 헤더를 써서 메시지에 "나를 거쳐 갔다"고 표시할 수 있다. 여러 개를 통과하면 각각이 자기 `Via` 문자열을 덧붙인다. **HTTP/1.1 프록시와 게이트웨이는 반드시 `Via` 헤더를 삽입해야 한다.**

형식은 이렇다.

```
Via: 1.1 joes-hardware.com (Joes-Server/1.0)
```

`HTTP-Version 기계-호스트명 (애플리케이션-이름-버전)` 구조다. 위 예는 메시지가 `joes-hardware.com`이라는 기계에서 실행 중인 Joe's Server 1.0 소프트웨어를 거쳤고, 그 서버가 HTTP 1.1을 말했다는 뜻이다.

`Via`는 표 8-12에서 흥미로운 위치에 있다. **경로에 대해 명시적으로 진술하는 유일한 헤더**이기 때문이다. 그리고 정확히 그 이유로 XFF와 같은 성질을 공유한다.

- **클라이언트도 `Via`를 넣을 수 있다.** 첫 홉이 그것을 지우지 않으면 살아남는다.
- **중간자가 `Via`를 제거할 수 있다.** 익명화 프록시의 기능 중 하나가 정확히 이것이다(→ 13.2).
- **서명이 없다.** `Via` 값은 그 중간자가 자기에 대해 한 진술이고, 진술을 검증할 수단은 없다.

그러므로 `Via` 체인은 **경로의 증거가 아니라 경로에 대한 이야기**다. 13.6절이 메시지 추적을 다룰 때, 그리고 13.11절이 잘못 구현된 릴레이를 다룰 때 이 성질이 전제가 된다.

한 가지 실용적 용법은 남는다. **`Via`가 있으면 최소한 하나의 중간자를 거쳤다는 것은 대체로 참이다.** 없다고 해서 거치지 않은 것은 아니지만, 있는 것을 거짓으로 만들 동기는 상대적으로 적다. 응답의 `Age` 헤더가 있으면 그 응답이 중간자(아마도 프록시 캐시)를 통과했다는 것을 시사하는 것과 같은 종류의 약한 신호다.

### 방향이 바뀌면 주체가 바뀐다 — 응답 헤더의 신뢰성

지금까지는 서버가 요청 헤더를 얼마나 믿을 수 있는가를 물었다. 반대 방향도 성립한다. **클라이언트는 응답 헤더를 얼마나 믿을 수 있는가.**

`Server` 헤더가 대표적이다. 이 헤더는 서버가 자기를 클라이언트에게 식별시키는 방법이며, `User-Agent`와 대칭이다. 원서의 서술도 대칭이다. 형식이 자유 형식이고, 값이 제품마다 릴리스마다 다르며, 오래된 프록시나 게이트웨이가 `Via`에 해당하는 내용을 여기에 끼워 넣기도 한다.

```
Server: apache/1.2b6 via proxy gateway CERN-HTTPD/3.0 libwww/2.13
```

WAHH가 이 헤더에 대해 붙이는 단서 한 줄이 전부를 말한다. **"담긴 정보는 정확할 수도 있고 아닐 수도 있다."**

25.6절이 서버 핑거프린팅을 다룰 때 이 헤더는 첫 번째 단서이자 가장 믿을 수 없는 단서다. 서버 운영자는 이 값을 지우거나 위조할 수 있고, 그것이 표준적인 강화 조치 중 하나다(→ 12.10). 그러나 이 조치가 주는 것은 **모호함이지 보호가 아니다.** 실제 소프트웨어와 버전은 응답의 다른 특징 — 헤더 순서, 오류 페이지 형식, 예외적 입력에 대한 반응 — 으로 여전히 추론된다.

여기서 짚어야 할 더 근본적인 사실이 있다. **클라이언트에게도 응답 헤더를 검증할 수단이 없다.** TLS가 무엇을 주는지 정확히 말하면 이렇다. 18.3절이 다룰 인증서 검증은 **"내가 말하고 있는 상대가 이 이름의 소유자다"** 를 확인해 준다. 그것은 채널의 상대에 대한 인증이지, **그 상대가 응답 헤더에 쓴 내용의 진위에 대한 보증이 아니다.** 그리고 그 상대가 오리진 서버라는 보증도 아니다. TLS 종료 지점은 CDN 엣지일 수 있고, 그 뒤의 구간에서 헤더는 평문이며 다시 쓰일 수 있다(→ 13.9, 19.8).

즉 **헤더의 신뢰성 문제는 요청 방향에서만 발생하는 것이 아니다.** 양방향 모두에서, 그리고 같은 이유로 발생한다. HTTP/1.x에는 필드 단위의 무결성 보호가 없다.

### 종합 — 신뢰의 세 등급

이 절의 결론을 하나의 분류로 압축한다. 요청이 가져오는 모든 값은 세 등급 중 하나에 속한다.

**표 8-15. 값의 세 등급 (신규 작성)**

| 등급 | 정의 | 예 | 수신자가 아는 것 | 방어의 방향 |
|---|---|---|---|---|
| **관찰된 값** | 수신자가 자기 계층에서 직접 측정한 것 | 소켓의 피어 주소, 실제 수신 바이트 수, TLS 세션의 상대 | 그 계층에서 참이다 — 단, **직전 홉에 대해서만** | 관찰의 의미를 정확히 좁혀서 쓴다 |
| **진술된 값** | 다른 주체가 보고한 것. 검증 참조점이 없다 | `Host`, `Referer`, `User-Agent`, `X-Forwarded-For`, `Via`, `From`, `Accept*`, `Server` | **아무것도.** 누군가 이 문자열을 보냈다는 사실뿐 | 값을 검증하려 하지 말고, 값이 통제된 집합에서만 오게 한다 |
| **서명된 값** | 수신자가 가진 키로 무결성을 확인할 수 있는 것 | HMAC 서명 쿠키, 검증된 자격증명, 서명 토큰 | 서명 시점 이후 변경되지 않았다 | 키 관리와 재생 방지가 새 과제가 된다 |

세 등급의 관계에서 읽어야 할 것이 두 가지다.

**첫째, 진술된 값을 관찰된 값으로 승격시키는 방법은 없다.** 4.6절이 XFF에 대해 도달한 결론 — 잃어버린 하위 계층 정보를 상위 계층으로 옮기는 것은 정보를 복구하지만 신뢰를 복구하지 않는다 — 이 여기서 일반 명제가 된다. **진술을 아무리 여러 개 모아도 관찰이 되지 않는다.**

**둘째, 진술된 값을 서명된 값으로 만드는 것은 가능하다.** 그러나 그것은 **수신자 쪽에 참조점을 만드는 일**이며, 헤더를 검증하는 것이 아니라 신뢰 경계의 입구에서 정본을 생성하는 것이다. 4.6절의 첫 번째 처방(엣지에서 XFF를 덮어쓴다)과 이 절의 `Host` 처방(허용 목록)이 형태는 달라도 같은 구조인 이유다. **참조점을 어디에 두는가가 방어의 전부다.**

### 안티패턴 목록

마지막으로 실무에서 반복되는 형태들을 모아 둔다.

**표 8-16. 헤더 기반 판정의 안티패턴 (신규 작성)**

| 이 헤더로 이것을 판정한다 | 우회 | 옳은 방향 | 이 책에서 |
|---|---|---|---|
| `X-Forwarded-For`로 "내부 요청"을 판정 | 헤더 한 줄 | 네트워크 계층에서 격리한다. 엣지에서 정본을 생성한다 | **4.6**, 24.2 |
| `Referer`로 CSRF를 막는다 | 헤더 생략 | 요청마다 검증되는 토큰 | **33.4** |
| `Referer`로 딥링크·핫링크를 막는다 | 헤더 위조 | 서명된 URL, 접근 제어 | 24.1 |
| `User-Agent`로 봇을 막는다 | 문자열 위조 | 행위 기반 탐지, 레이트 리밋 | **16.9**, 22.10 |
| `Host`로 절대 URL을 만든다 | 헤더 위조 | 설정의 정본 호스트명 | **15.2** |
| `Host`가 매칭 안 되면 첫 가상 호스트로 폴백 | 임의 `Host` 값 | 명시적 거부 | 12.9, **15.2** |
| `Content-Length`를 검증 없이 신뢰 | 실제 길이와 불일치 | 실제 수신 바이트와 대조, 두 지시자 충돌 시 거부 | **10.2**, 10.4 |
| `Accept-Language`로 접근 지역을 판정 | 헤더 위조 | 지역 판정은 헤더로 할 수 없다 | 10.10 |
| 커스텀 헤더(`X-Admin: true` 등)로 권한 판정 | 헤더 한 줄 | 인증된 주체의 권한을 서버 상태에서 조회 | **24.2**, 26.1 |
| `Origin`이 없으면 동일 출처로 간주 | 비브라우저 클라이언트 | 명시적 허용 목록, 없으면 거부 | **34.7**, 34.11 |

마지막 두 행이 이 표의 요지를 압축한다. `X-Admin: true`로 권한을 판정하는 설계는 우스워 보이지만, **`X-Forwarded-For: 10.0.0.5`로 내부 요청을 판정하는 설계와 구조적으로 동일하다.** 둘 다 클라이언트가 쓴 헤더 한 줄로 권한 경계를 넘는다. 전자가 명백해 보이고 후자가 그렇지 않은 이유는, 후자가 **정당한 인프라도 같은 헤더를 쓰기 때문**이다. 4.6절이 명제 1(위조)과 명제 4(경로상 재작성)를 구별해야 한다고 강조한 이유가 이것이다.

> - `User-Agent`는 통계이지 판정 근거가 아니다 → **16.9** (로봇 배제의 오용), **25.6** (서버·클라이언트 핑거프린팅), **12.11** (WAF의 한계)
> - 확장 헤더의 전달 규칙이 XFF의 성립 조건이다 → **4.6** (XFF의 다섯 문제와 여섯 처방), **20.2** (클라이언트 IP로 식별하기)
> - 값의 세 등급(관찰·진술·서명) → **23.2** (토큰 생성), **26.7** (클라이언트 데이터의 서명·암호화), **44.1** (도메인 프리미티브), **44.7** (테인트 분석)

## 8.7 헤더 인젝션과 응답 분할의 원리 — CR/LF가 메시지 구조를 결정하는 결과

8.6절은 헤더를 **읽는** 문제였다. 이 절은 헤더를 **쓰는** 문제다.

두 문제는 대칭이 아니다. 8.6절의 결론은 "값을 믿지 말라"였다. 이 절의 결론은 그보다 강하다. **값을 검증 없이 헤더에 넣으면 값이 아니라 구조가 사용자 통제 아래 들어간다.**

### 두 개의 전제

이 절 전체가 이미 세워 둔 두 문장에서 유도된다.

**전제 1 (8.1절).** HTTP 메시지의 구조는 문자로만 표시된다. CRLF가 헤더 필드 하나의 끝을 표시하고, CRLF가 단독으로 나타나는 빈 줄이 헤더 블록 전체의 끝을 표시한다. 그 뒤부터가 본문이다.

**전제 2 (7.4.2절).** 구분자와 데이터가 같은 문자 공간을 공유한다. 헤더 값에 쓸 수 있는 문자와 헤더를 구분하는 문자가 같은 바이트 집합에서 나온다.

두 전제를 결합하면 다음이 따라 나온다.

> **헤더 값에 CR과 LF를 넣을 수 있는 자는, 그 지점에서 메시지의 구조를 쓸 수 있다.**

이것이 원리 전체다. 나머지는 그 원리가 어디까지 갈 수 있는지를 세는 일이다.

### 사다리 — 네 단계

인젝션의 위력은 삽입할 수 있는 것에 따라 단계적으로 커진다.

**표 8-17. 헤더 인젝션의 네 단계 (신규 작성)**

| 단계 | 삽입하는 것 | 얻는 것 | 필요한 문자 |
|---|---|---|---|
| **① 값 오염** | 값 안의 구분자 (`;`, `,`, `=`) | 그 헤더의 파라미터를 추가·변경 | 해당 헤더의 문법 문자 |
| **② 헤더 추가** | `CRLF` + `이름: 값` | 응답에 임의의 헤더를 추가 | **CR, LF** |
| **③ 본문 작성** | `CRLF` `CRLF` + 임의의 바이트 | 응답 본문 전체를 작성 | **CR, LF** |
| **④ 응답 분할** | ③ + `HTTP/1.1 200 OK` + 두 번째 헤더 블록 + 두 번째 본문 | 응답 하나를 **두 개의 응답으로** 만든다 | **CR, LF** |

①에서 ②로 올라가는 데 필요한 것이 CR/LF이고, ②부터 ④까지는 **같은 두 문자로 전부 도달한다.** 이것이 이 취약점 유형의 성질이다. **한 번 개행을 넣을 수 있으면 그다음은 정도의 문제일 뿐 종류의 문제가 아니다.**

### 어디서 발생하는가

취약점은 **사용자가 통제하는 데이터가 애플리케이션이 반환하는 HTTP 헤더에 안전하지 않은 방식으로 삽입될 때** 생긴다. 가장 흔한 것은 `Location` 헤더와 `Set-Cookie` 헤더지만, 원리상 어떤 헤더에서도 일어날 수 있다.

Joe's Hardware의 언어 설정 기능을 예로 든다. 사용자가 고른 언어를 쿠키에 저장하는 흔한 기능이다.

```
GET /settings/language?lang=korean HTTP/1.1
Host: www.joes-hardware.com

```

```
HTTP/1.1 200 OK
Set-Cookie: PreferredLanguage=korean
Content-Type: text/html
Content-Length: 1043

<html>...
```

애플리케이션이 하는 일은 `lang` 파라미터의 값을 그대로 `Set-Cookie` 헤더 값에 넣는 것이다. 코드로는 한 줄이다.

```python
response.set_header("Set-Cookie", "PreferredLanguage=" + params["lang"])
```

이제 공격자가 이렇게 요청한다.

```
GET /settings/language?lang=korean%0d%0aX-Injected:+yes HTTP/1.1
Host: www.joes-hardware.com

```

`%0d`는 캐리지 리턴, `%0a`는 라인 피드다. 7.4절이 세운 퍼센트 인코딩의 문법이며, 7.6.1절에서 `%0a`를 개행 문자로 이미 소개했다. 서버는 쿼리 문자열을 디코딩하고, 디코딩된 값을 헤더에 넣는다. 그 결과 응답은 이렇게 된다.

```
HTTP/1.1 200 OK
Set-Cookie: PreferredLanguage=korean
X-Injected: yes
Content-Type: text/html
Content-Length: 1043

<html>...
```

**응답에 헤더가 하나 늘었다.** 사용자가 쓴 것이다.

여기서 정확히 무슨 일이 일어났는지 짚는다. 애플리케이션은 문자열 하나를 값으로 넣었다고 생각했다. 그러나 그 문자열 안에 CRLF가 있었기 때문에, HTTP 파서에게 그것은 **값 하나가 아니라 값 하나 + 새 헤더 하나**였다. **애플리케이션의 데이터 모델과 파서의 데이터 모델이 다르다.** 27장의 SQL 인젝션, 28.1절의 명령 인젝션과 정확히 같은 구조이며, 다른 것은 인젝션 대상 문법이 SQL도 셸도 아닌 **HTTP 메시지 문법**이라는 것뿐이다.

### 왜 이 경로가 열려 있는가 — 디코딩과 삽입 사이

이 취약점이 성립하는 데는 두 개의 조작이 순서대로 일어나야 한다.

```
   URL 쿼리 문자열:  lang=korean%0d%0aX-Injected:+yes
            │
            ▼  ① 퍼센트 디코딩            (7.4절)
   디코딩된 값:      korean\r\nX-Injected: yes
            │
            ▼  ② 헤더 값으로 삽입          (검증 없음)
   응답 바이트열:    Set-Cookie: korean\r\nX-Injected: yes\r\n
            │
            ▼  ③ 수신자의 헤더 파싱        (8.1절, 8.5절)
   파싱 결과:        Set-Cookie: korean
                    X-Injected: yes        ← 헤더 두 개
```

*그림 8-4. 디코딩과 삽입 사이에 검증이 없을 때 (신규 작성)*

**①과 ② 사이에 아무 검증도 없다는 것이 이 취약점의 전부다.** 7.8절이 다단계 검증과 정규화 순서 문제를 다루면서 확립한 명제 — 필터가 정규화보다 앞에 있으면 그 필터는 최종 소비자가 볼 값을 한 번도 보지 못한다 — 의 또 하나의 사례다. 여기서 최종 소비자는 HTTP 파서이고, 그것이 보는 값은 디코딩 **후**의 값이다.

이 그림에서 또 하나 읽을 것이 있다. **③의 파싱 결과가 파서마다 다를 수 있다.** 8.5절에서 헤더 이어쓰기를 다뤘다. 인젝션된 개행 다음에 공백이 오면 그것은 새 헤더가 아니라 앞 헤더의 연장이 된다. 어떤 파서는 공백을 엄격히 요구하고 어떤 파서는 관대하다. 8.1절의 두 완화 규칙도 여기서 작동한다. **CR 없이 LF만 있는 경우, 명세는 그것도 받아들이라고 권했다.** 그 관용이 여기서는 공격자의 편이다. CR이 걸러지고 LF만 통과하는 필터가 있다면, LF만으로 인젝션이 성립하는 파서를 상대로는 무력하다.

### 필터 우회 — 7장의 결론이 그대로 재현된다

애플리케이션이 개행 문자를 차단하거나 정제하기 시작하면, 7.7절과 7.8절이 다룬 우회 기법이 그대로 적용된다. WAHH가 제시하는 시도 목록이 그 증거다.

| 시도 | 노리는 것 | 7장의 대응 절 |
|---|---|---|
| `foo%00%0d%0abar` | 널 바이트로 필터의 문자열 처리를 조기 종료시킨다 | 7.6.1 (`%00`의 성질) |
| `foo%250d%250abar` | 이중 URL 인코딩. 필터는 `%0d`를 보지 못하고, 두 번째 디코딩에서 개행이 된다 | **7.7.1** (`%2527`과 같은 구조) |
| `foo%%0d0d%%0a0abar` | 필터가 `%0d`를 **제거**하면 남은 조각이 다시 `%0d`가 된다 | **7.8.3** (오므라들기) |

**표 8-18. 개행 필터 우회 시도 (WAHH 13장 기준, 대응 절은 이 책이 추가)**

세 시도 모두 **새로운 기법이 아니다.** 7장이 인코딩과 정규화에 대해 확립한 것이 문법만 바꿔 재현된 것이다. 그리고 그 재현이 이 책의 논지를 다시 확인한다. **같은 실패 구조가 다른 문법에서 되풀이된다.**

### 응답 분할 — 사다리의 네 번째 칸

②와 ③이 응답 하나 안에서 벌어지는 일이라면, ④는 응답의 **개수**를 바꾼다.

원리는 이렇다. 인젝션한 내용 안에 **완결된 두 번째 응답 전체**를 쓴다. 첫 번째 응답의 헤더 블록을 닫고(빈 줄), 첫 번째 본문을 쓰고, 그다음에 새 응답 라인(`HTTP/1.1 200 OK`)과 새 헤더 블록과 새 본문을 쓴다.

```
GET /settings/language?lang=ko%0d%0aContent-Length:+22%0d%0a%0d%0a
    <html>%0d%0afoo%0d%0a</html>%0d%0a
    HTTP/1.1+200+OK%0d%0aContent-Length:+2307%0d%0a%0d%0a
    <html><head><title>Administrator+login</title>[...] HTTP/1.1
Host: www.joes-hardware.com
```

(가독성을 위해 줄을 나눠 적었다. 실제로는 한 줄이다.)

서버가 만드는 바이트열은 이렇게 된다.

```
HTTP/1.1 200 OK
Set-Cookie: PreferredLanguage=ko
Content-Length: 22

<html>
foo
</html>
HTTP/1.1 200 OK
Content-Length: 2307

<html><head><title>Administrator login</title>...
```

**하나의 TCP 스트림 위에 두 개의 완전한 HTTP 응답이 있다.** 공격자가 "응답을 쪼갰다(split)"는 것이 이 기법의 이름의 유래다.

#### 왜 이것이 다른 사용자를 공격하는가

두 번째 응답 자체는 공격자에게 아무 이득이 없다. 공격자가 자기 브라우저에서 자기가 만든 HTML을 보는 것뿐이다. 위력은 **경로 위에 응답을 재파싱하는 중간자가 있을 때** 생긴다.

성립 조건이 셋이다.

1. **헤더에 CR/LF를 삽입할 수 있다.** (②~③단계)
2. **경로에 응답을 파싱하고 저장하는 중간자가 있다.** 캐싱 프록시가 대표적이다.
3. **그 중간자가 요청과 응답을 순서로 짝짓는다.** HTTP/1.1의 파이프라이닝이 그것을 허용한다(→ 9.8).

세 조건이 갖춰지면 다음이 일어난다.

```
공격자                     캐싱 프록시                  애플리케이션 서버
   │                            │                            │
   │  요청 1 (인젝션 페이로드)  │                            │
   │  요청 2 (GET /admin/)      │                            │
   ├───────────파이프라인───────▶│                            │
   │                            ├──────두 요청 그대로────────▶│
   │                            │                            │
   │                            │◀─── 응답 1 (실제로는 2개) ──┤
   │                            │◀─── 응답 2 (진짜 /admin/) ──┤
   │                            │                            │
   │           프록시가 세는 방식:                             │
   │             첫 번째 응답  → 요청 1의 응답                 │
   │             두 번째 응답  → 요청 2의 응답로 간주 ★        │
   │                            → /admin/ 의 내용으로 캐시     │
   │             세 번째 응답  → 짝지을 요청이 없다 → 폐기     │
   │                            │                            │
   ▼                            ▼                            ▼

  이후 다른 사용자가 /admin/ 을 요청하면, 프록시가 캐시에서
  공격자가 쓴 본문을 내준다.
```

*그림 8-5. 응답 분할이 캐시를 오염시키는 과정 (WAHH 그림 13-3 기준, ASCII로 재작성)*

★ 표시한 줄이 이 공격의 전부다. **프록시는 응답 세 개를 봤지만 요청은 두 개를 보냈으므로, 두 번째 응답을 두 번째 요청의 것으로 짝짓는다.** 그 두 번째 응답은 공격자가 헤더 안에 써 넣은 것이다.

결과는 이렇다. 그 프록시를 경유하는 모든 사용자가 `/admin/`을 요청하면 **공격자가 만든 페이지를 받는다.** 그것이 가짜 로그인 폼이면 자격증명이 공격자에게 간다. 기업 네트워크의 전 직원이 하나의 캐싱 프록시를 쓰는 배포에서 이 공격의 사정거리는 그 조직 전체다.

#### 이것은 새로운 구조가 아니다

응답 분할을 이 책의 다른 절들과 나란히 놓으면 같은 형태가 보인다.

| 절 | 무엇을 다르게 세는가 | 뿌리 |
|---|---|---|
| **3.1.2** | TCP는 메시지 경계를 주지 않는다 | 바이트 스트림 |
| **8.7** (이 절) | 응답의 **개수**를 두 주체가 다르게 센다 | CRLF가 구조를 정한다 |
| **10.4** | 본문의 **경계**를 두 주체가 다르게 센다 | 길이 지시자가 둘이다 |
| **13.12** | 요청의 여러 속성을 홉마다 다르게 읽는다 | 파서가 여러 개다 |

**표 8-19. 같은 구조의 네 가지 나타남 (신규 작성)**

네 절이 말하는 것은 하나다. **하나의 바이트 스트림 위에서 "메시지 하나"를 세는 방법이 여러 개이고, 그 방법을 여러 주체가 각자 구현한다.** 1.1절이 계층화가 감추는 세 가지 중 세 번째로 "의미의 불일치"를 꼽은 것, 1.3.1절이 "TCP가 자르는 위치는 HTTP의 구조와 아무 관계가 없다"고 한 것이 여기서 회수된다.

### 방어 — 원리 수준

35.1절이 클라이언트 측 귀결과 상세한 탐지·익스플로잇 절차를 다룬다. 여기서는 원리에서 곧바로 따라 나오는 것만 적는다.

**1) 사용자 입력을 헤더에 넣지 않는다.**

가장 효과적인 방법이며, WAHH도 이것을 첫 번째로 든다. 오픈 리다이렉션에서와 마찬가지로, 대개는 더 안전한 대안이 있다. 위의 언어 설정 예를 다시 보자.

```python
# 취약 — 사용자 문자열이 헤더로 간다
response.set_header("Set-Cookie", "PreferredLanguage=" + params["lang"])

# 안전 — 사용자 입력은 인덱스로만 쓰고, 헤더에는 서버가 가진 값이 간다
SUPPORTED = {"ko": "korean", "en": "english", "ja": "japanese"}
lang = SUPPORTED.get(params["lang"])
if lang is None:
    return error_response()
response.set_cookie("PreferredLanguage", lang)
```

**핵심은 간접 참조다.** 사용자가 고르는 것은 목록 안의 항목이고, 헤더에 들어가는 문자열은 애플리케이션이 소유한 상수다. 35.6절이 "간접 참조"라는 이름으로 이 처방을 일반화하고, 44.1절의 도메인 프리미티브가 타입 수준에서 같은 일을 한다.

**2) 넣어야 한다면 값의 형태를 미리 정하고 어긋나면 거부한다.**

입력 검증은 삽입되는 데이터의 컨텍스트에 맞게 최대한 엄격해야 한다. 쿠키 값이 사용자 입력에 따라 설정된다면, 알파벳 문자만 허용하고 최대 길이를 제한하는 것이 적절할 수 있다. 7.8절과 43.6절이 확립한 원칙 — **정화보다 거부가 낫다** — 이 그대로 적용된다. 표 8-18의 세 번째 행이 정화의 위험을 보여 준다.

**3) 출력 시점에도 검사한다 — 0x20 미만의 모든 문자를 의심한다.**

WAHH의 처방을 그대로 옮기면 이렇다. **헤더에 삽입되는 모든 데이터를 필터링해서 잠재적으로 악의적인 문자를 탐지해야 한다. 실무적으로는 ASCII 코드 0x20 미만의 모든 문자를 의심스러운 것으로 간주하고 요청을 거부해야 한다.**

CR(`0x0d`)과 LF(`0x0a`)만 막지 않는 이유가 두 가지다. 첫째, 널 바이트(`0x00`)를 비롯한 다른 제어 문자가 파서마다 다르게 처리된다. 둘째, 입력 검증과 출력 검증을 **모두** 두는 것이 심층 방어이며, 7.8절의 경계 검증 원칙이 요구하는 것이다.

**4) 헤더 설정 API가 개행을 거부하게 만든다.**

이것은 프레임워크 수준의 처방이다. `setHeader(name, value)` 같은 함수가 값 안의 CR/LF를 발견하면 예외를 던지도록 만들면, 애플리케이션 코드의 실수와 무관하게 이 취약점 유형이 사라진다. 현대의 주요 프레임워크 상당수가 이미 그렇게 한다. **취약점을 개발자의 주의력이 아니라 API의 계약으로 막는 것**이며, 43.2절이 "계약으로 빠르게 실패하기"라는 제목으로 다루는 원칙이다.

**5) 같은 문제가 헤더 밖에도 있다.**

CR/LF가 구조를 정하는 곳은 HTTP 헤더만이 아니다.

| 삽입 지점 | 무엇이 되는가 | 이 책에서 |
|---|---|---|
| `Location` 헤더 | 헤더 인젝션 + 오픈 리다이렉션 | **35.1**, 35.3 |
| `Set-Cookie` 헤더 | 헤더 인젝션 + 쿠키 인젝션 | **35.1**, 35.2, 20.9 |
| `Content-Disposition`의 파일명 | 헤더 인젝션 | 35.1 |
| 애플리케이션이 정의한 커스텀 헤더 | 헤더 인젝션 | 35.1 |
| 이유 구 (일부 프레임워크) | 응답 라인 오염 | 8.2 |
| **로그 파일의 한 줄** | 로그 인젝션 — 가짜 로그 항목 생성 | **16.6**, 47.3 |
| **이메일 헤더** | SMTP 헤더 인젝션 — 수신자 추가 | **28.9** |

**표 8-20. CR/LF가 구조를 정하는 다른 지점들 (신규 작성)**

마지막 두 행이 특히 중요하다. **줄 단위로 구조를 갖는 모든 형식이 같은 문제를 갖는다.** 로그 파일은 한 줄이 한 항목이고, SMTP 메시지는 헤더 문법이 HTTP와 거의 같다. 16.6절의 제목이 "로그에 검증되지 않은 문자열을 넣지 말라"인 이유, 28.9절이 메일 서비스 인젝션을 별도로 다루는 이유가 이 표에 있다.

**6) HTTPS는 캐시 오염 경로를 좁힌다 — 그러나 취약점을 없애지는 않는다.**

WAHH가 덧붙이는 조건부 처방이 하나 있다. **애플리케이션의 모든 콘텐츠에 HTTPS를 사용하면 남아 있는 헤더 인젝션 취약점이 프록시 서버 캐시를 오염시키는 데 쓰이는 것을 막을 수 있다. 단, 애플리케이션이 SSL 종료 장치 뒤에 캐싱 리버스 프록시를 두지 않은 경우에 한한다.**

이 단서가 중요하다. **TLS는 중간자를 없애는 것이 아니라 중간자의 위치를 옮긴다.** TLS 종료 지점 뒤에 캐싱 리버스 프록시가 있으면 조건 2와 3이 그대로 성립하고, 공격도 그대로 성립한다. 19.8절과 14.8절이 이 배포 형태를 다룬다.

> **이 책의 범위를 넘어서**
>
> 이 절이 다룬 것은 **응답**의 개수를 두 주체가 다르게 세는 문제다. 같은 구조가 **요청** 방향에서도 성립한다. 프런트엔드 중간자와 백엔드 서버가 하나의 커넥션 위에서 요청의 경계를 다르게 셀 때, 한쪽이 하나로 센 것을 다른 쪽이 둘로 세면서 뒤쪽 요청이 다음 사용자의 요청 앞에 붙는 형태다. 이 계열의 기법들은 2011년 이후 체계적으로 정리되었고 고유한 이름과 분류를 갖게 되었으나, 이 책이 근거로 삼는 다섯 권의 범위 밖이다. 이 책은 그 성립 조건을 이루는 요소들 — 본문 경계를 정하는 두 지시자의 충돌(→ 10.4), 홉 단위 헤더의 처리 불일치(→ 8.5, 9.2), 커넥션 재사용 시 이월되는 것(→ 9.10), 중간자별 파싱 불일치 지점(→ 13.12) — 을 각각의 자리에서 다루며, 그 요소들이 결합했을 때 무엇이 가능한지는 독자의 판단에 맡긴다. 원리는 이 절의 것과 같다. **메시지 하나를 세는 방법이 여럿이고, 그 방법을 여러 주체가 각자 구현한다.**

## 이 장의 요약

- **HTTP 메시지의 세 부분은 모두 문자열 안의 약속으로만 구분된다.** 시작줄은 CRLF로, 헤더 블록은 빈 줄로, 본문은 `Content-Length`나 청크 종료 표시나 커넥션 종료로 끝난다. 길이 필드가 앞에 붙는 바이너리 프로토콜과 달리 경계가 데이터에 섞여 있고, 이 사실 하나가 8.7절의 헤더 인젝션과 10.4절의 본문 경계 불일치를 동시에 성립시킨다.

- **명세의 두 완화 규칙 — LF 단독도 받아라, 마지막 빈 줄이 없어도 받아라 — 은 실용적이며 동시에 파서마다 다른 관용도를 만든다.** "보낼 때는 보수적으로, 받을 때는 관대하게"라는 원칙이 HTTP의 확장성을 만들었고, 관대함의 정도가 구현마다 다르다는 사실이 불일치의 원천이 됐다.

- **요청 라인의 세 필드가 전부 클라이언트 통제 아래 있다.** 7장이 두 번째 필드(요청 URL)에 대해 확립한 것이 메서드와 버전에도 그대로 적용된다. 메서드 토큰은 표준 일곱 개에 한정되지 않는 임의의 문자열이며, 그 사실이 8.3.4절의 세 번째 우회 유형을 성립시킨다.

- **안전(safe)과 멱등(idempotent)은 프로토콜이 강제하는 성질이 아니라 규약이다.** 강제하는 주체가 없다. 그리고 크롤러, 프리페치, 캐시, 커넥션 실패 시의 자동 재시도가 전부 이 규약을 전제로 동작한다. `GET`이 상태를 바꾸는 순간 그 여섯 가지 정상 동작이 전부 공격 경로가 되며, CSRF의 성립 조건 중 하나가 정확히 이 규약 위반이다.

- **`GET`과 `POST`의 차이는 의미의 차이이지 메커니즘의 차이가 아니다.** URL 파라미터는 북마크·방문 기록·액세스 로그·프록시 로그·`Referer`에 사본을 남기고, 그중 둘은 운영자의 통제 밖이다. 그러나 대부분의 파라미터 조회 API가 메서드에 무관하므로, 이 구별에 의존하는 보안 판단은 공격자가 메서드를 바꾸는 순간 무너진다.

- **메서드 기반 접근 제어는 판단하는 층과 동작하는 층이 다른 정보를 보기 때문에 우회된다.** `POST`를 막으면 `GET`으로, `GET`과 `POST`를 막으면 `HEAD`로, 목록을 촘촘히 채우면 목록에 없는 임의의 문자열로 우회된다. 세 번째 우회는 "알 수 없는 메서드에 관대하라"는 명세의 권고를 구현에 반영한 결과이며, **거부 목록이 메서드에 대해서도 원리적으로 실패한다**는 것을 보여 준다.

- **상태 코드는 하나의 응답에 대해 여섯 주체가 서로 다른 결정을 내리는 근거다.** 브라우저, 캐시, 프록시, 모니터링, 자동화 도구, 공격자가 같은 숫자를 읽는다. 그러므로 코드가 실제 결과와 어긋나면 여섯 개의 결정이 동시에 어긋난다. 그리고 상태 코드는 그 자체로 정보 채널이다. **구별되어서는 안 되는 두 경우는 상태 코드도 같아야 한다.**

- **헤더의 다섯 분류는 의미의 분류이지 신뢰의 분류가 아니다.** 이와 직교하는 구분이 홉 단위와 종단 간이며, `Connection` 헤더가 그 경계를 표현한다. `Proxy-Authenticate`, `Proxy-Connection`, `Transfer-Encoding`, `Upgrade`는 나열되지 않아도 홉 단위다. 이 규칙을 지키지 않는 중간자가 9.7절의 멍청한 프록시 문제와 13.8절의 헤더 보존 문제를 만든다.

- **헤더의 신뢰성은 세 개의 질문으로 분해된다: 누가 이 값을 처음 쓰는가, 경로 위에서 누가 그것을 바꿀 수 있는가, 수신자가 검증할 수단을 갖는가.** 주요 요청 헤더 열두 개 중 세 번째 질문에 실질적으로 답할 수 있는 것은 셋뿐이며, 그 셋의 공통점은 값 안에 검증 가능한 것이 들어 있다는 것이다. 나머지는 전부 진술이고, 진술을 검증할 참조점이 수신자에게 없다.

- **`Referer` 검증은 두 방향으로 실패한다.** 헤더가 없는 것을 허용하면 우회되고, 허용하지 않으면 정상 사용자가 막힌다. 헤더가 없는 것은 정상 동작이기 때문이다. 그리고 반대 방향으로, 나가는 `Referer`는 URL 쿼리 문자열 전체를 제3자의 액세스 로그에 넘긴다. **들어오는 `Referer`는 검증의 근거로 삼기에 너무 약하고, 나가는 `Referer`는 비밀을 담기에 너무 넓다.**

- **`Host` 헤더는 정보가 아니라 라우팅 입력이다.** 서버는 이 값으로 가상 호스트의 docroot를 고르고, 캐시 키를 만들고, 자기 자신의 절대 URL을 구성한다. **사용자가 쓴 문자열이 서버의 자기 이름이 된다.** 유일하게 실질적인 방어는 허용 호스트 목록이며, 그것이 가능한 이유는 참조점을 수신자 쪽에 두었기 때문이다.

- **`User-Agent`는 사실을 말하도록 진화하지 않았다.** `Mozilla` 접두의 역사 자체가 그 값이 사실 주장이 아니라 협상 전술임을 증명한다. 통계와 이상 탐지의 한 특징으로는 정당하지만, 그 값 하나로 허용/거부를 가르는 순간 그것은 클라이언트가 스스로 발급하는 통행증이 된다.

- **요청이 가져오는 모든 값은 관찰된 값, 진술된 값, 서명된 값 중 하나다.** 진술된 값을 관찰된 값으로 승격시키는 방법은 없다. 진술을 아무리 여러 개 모아도 관찰이 되지 않는다. 가능한 것은 신뢰 경계의 입구에서 정본을 생성하는 것뿐이며, **참조점을 어디에 두는가가 방어의 전부다.**

- **헤더 값에 CR과 LF를 넣을 수 있는 자는 그 지점에서 메시지의 구조를 쓸 수 있다.** 값 오염에서 헤더 추가로, 본문 작성으로, 응답 분할로 올라가는 사다리에서 ②부터 ④까지는 같은 두 문자로 도달한다. 한 번 개행을 넣을 수 있으면 그다음은 정도의 문제일 뿐 종류의 문제가 아니다.

- **응답 분할은 응답의 개수를 두 주체가 다르게 세는 문제다.** 3.1.2절(TCP는 메시지 경계를 주지 않는다), 10.4절(본문 경계 불일치), 13.12절(중간자 파싱 불일치)과 같은 구조이며, 뿌리는 하나다. **하나의 바이트 스트림 위에서 "메시지 하나"를 세는 방법이 여럿이고, 그 방법을 여러 주체가 각자 구현한다.**

## 이어지는 장

이 장은 **메시지 하나**를 다뤘다. 그 문법, 그 안에 담기는 메서드와 상태 코드와 헤더, 그리고 그 값들을 누가 쓰고 누가 믿을 수 있는가다.

**9장은 그 메시지가 흐르는 통로를 연다.** 3장이 TCP 자체를 다뤘다면, 9장은 **HTTP가 TCP를 어떻게 쓰기로 결정했는가**를 다룬다. 요청 하나당 커넥션 하나였던 시대에서 지속 커넥션으로, 병렬 커넥션에서 파이프라이닝으로 이어지는 결정들이다. 그리고 그 결정 하나하나가 이 장이 남긴 질문을 받는다.

**8.5절의 홉 단위/종단 간 구분을 9.2절이 곧바로 이어받는다.** `Connection` 헤더가 왜 함정인지, 그 헤더를 제거하지 않는 중간자가 무엇을 깨뜨리는지가 9.2절과 9.7절의 주제다. 표 8-11의 다섯 개 헤더가 거기서 각각의 실패 사례를 갖는다.

**8.7절이 성립 조건으로 제시한 파이프라이닝을 9.8절이 정면으로 다룬다.** 응답 분할이 성립하려면 중간자가 요청과 응답을 순서로 짝지어야 하고, 그 짝짓기를 허용한 것이 파이프라이닝이다. 9.8절은 파이프라이닝이 왜 도입됐고 왜 실패했는지를 다루며, 그 실패의 이유 목록에 응답 경계 혼동이 들어간다.

**그리고 9.11절이 이 장과 9장 전체를 이어 묶는다.** 요청 경계 혼동, 프록시 뒤의 커넥션 공유, 커넥션에 걸린 인증 상태 — 세 주제 모두 "커넥션 하나가 무엇을 공유하는 단위인가"라는 질문의 변주이며, 3.9.3절이 처음 던진 질문이다. 8.6절이 헤더에 대해 확립한 것 — 값의 출처를 프로토콜적으로 알 수 없다 — 이 커넥션 층위에서 어떤 모습이 되는지가 그 절의 주제다.

**10장은 다른 방향에서 이 장을 이어받는다.** 이 장은 헤더 블록의 끝까지만 다뤘다. 그 뒤의 본문, 본문의 경계, 본문의 인코딩과 무결성이 10장의 주제이며, **10.4절이 이 장의 8.7절과 정확히 같은 구조의 문제를 본문 층위에서 다룬다.** 표 8-19의 네 행 중 두 번째와 세 번째가 각각 이 장과 그 절이다.

이 장에서 기억해야 할 표는 셋이다. **표 8-12**(헤더별 작성자·수정자·검증 가능성), **표 8-15**(값의 세 등급), **표 8-17**(헤더 인젝션의 네 단계). 뒤의 장들이 이 장을 인용할 때 인용하는 것은 대개 이 셋 중 하나다.

> **표와 그림의 출처.** 표 8-1은 HTTP-DG 3장 "The Parts of a Message"의 서술을 표로 재구성하고 "무엇이 이 부분의 끝을 표시하는가" 열을 이 책이 추가한 것. 표 8-3은 HTTP-DG 표 3-1에 "HTTP/1.1 서버 필수 구현" 열을 추가한 것(그 사실 자체는 원서 "Methods" 절 본문에 있다). 표 8-6은 HTTP-DG 표 3-5의 네 메서드에 WAHH 18장의 여섯 메서드를 합치고 "공격자에게 무엇이 되는가" 열을 이 책이 추가한 것. 표 8-8은 HTTP-DG 표 3-2. 표 8-10은 HTTP-DG 3장 "Headers"의 다섯 분류 정의에 표 3-11~3-22의 헤더들을 분류별로 재배치하고 참조 열을 추가한 것. 표 8-11은 HTTP-DG 4장 "Connection 헤더" 절의 서술을 표로 만들고 "왜 홉 단위인가" 열을 추가한 것. 그림 8-1은 HTTP-DG 그림 3-1을, 그림 8-5는 WAHH 그림 13-3을 각각 ASCII로 재작성한 것. 표 8-18의 세 가지 우회 시도는 WAHH 13장의 목록이며 "7장의 대응 절" 열은 이 책이 추가한 것.

> **이 장에서 신규 작성한 부분.** 표 8-2(시작줄 각 필드의 통제 주체), 표 8-4(안전·멱등과 그것에 의존하는 것들), 표 8-5의 참조 열, 표 8-7의 "실패의 구조" 열, 표 8-9(상태 코드 오용 유형 아홉 가지), **표 8-12(헤더별 작성자·수정자·검증 가능성)**, 표 8-13(`Referer` 검증의 실패 구조), 표 8-14(`User-Agent` 의존 설계), **표 8-15(값의 세 등급)**, 표 8-16(헤더 기반 판정의 안티패턴), **표 8-17(헤더 인젝션의 네 단계)**, 표 8-19(같은 구조의 네 가지 나타남), 표 8-20(CR/LF가 구조를 정하는 다른 지점들), 그림 8-2(메서드 기반 접근 제어의 두 층), 그림 8-3(하나의 상태 코드를 읽는 여섯 주체), 그림 8-4(디코딩과 삽입 사이). 그리고 8.6절의 "세 개의 질문" 틀과 8.7절의 "두 개의 전제에서 사다리를 유도하는" 논증 구조.
>
> **메시지 예시의 문법에 관하여.** 이 장의 모든 HTTP 메시지 예시는 시작줄·헤더·빈 줄·본문의 구조를 실제 문법대로 적었다. 줄 끝 시퀀스를 명시할 필요가 있는 8.1절의 네 예시에는 `\r\n`을 표기했고, 나머지에서는 가독성을 위해 생략했으나 실제 바이트열에는 모든 줄 끝에 CRLF가 있다. 본문이 없는 요청 예시에서도 헤더 목록 끝의 빈 줄을 코드 블록 안에 남겼다. **본문 길이 값에 관하여.** 원서 그림에서 가져온 예시의 `Content-Length` 값은 원서가 제시한 값을 그대로 옮겼다. 원서 그림들의 이 값은 예시 목적의 개략치이며 본문 문자열의 실제 바이트 수와 정확히 일치하지 않는 경우가 있다. 8.1절의 `Content-Length: 18`(그림 3-10, `item=bandsaw 2647`는 17바이트이므로 줄 끝 하나를 포함한 값), 8.3.3절 `PUT` 예시의 34와 47, 같은 절 `TRACE` 응답의 96이 그런 경우다. 반면 **이 책이 새로 구성한 예시의 값은 계산으로 확인했다.** 8.7절 응답 분할 페이로드의 `Content-Length: 22`는 삽입된 본문 `<html>` CRLF `foo` CRLF `</html>` CRLF의 정확한 바이트 수다. 8.7절의 응답 분할 페이로드는 WAHH 13장의 예제를 Joe's Hardware의 언어 설정 기능으로 각색한 것이며, 인코딩된 `%0d%0a`와 디코딩 후의 구조가 대응하도록 확인했다.
>
> **표 8-8의 정의 범위에 관한 주의.** HTTP-DG 표 3-2는 4xx의 정의 범위를 400–415로 적었으나 같은 장의 표 3-9는 416 Requested Range Not Satisfiable과 417 Expectation Failed까지 나열한다. 이 책은 표 3-9를 따라 400–417로 적고 그 사실을 본문에 명시했다. 표 3-2가 쓰인 시점과 표 3-9가 반영한 명세 버전의 차이로 보인다.
>
> **범위에 관한 주의.** 8.7절 말미의 "이 책의 범위를 넘어서" 상자가 언급한 요청 방향의 경계 혼동 기법군은 이 책이 근거로 삼는 다섯 권 중 어디에도 체계적으로 서술되어 있지 않다. WAHH 2판(2011)은 응답 분할까지만 다루며, HTTP-DG(2002)는 홉 단위 헤더 처리와 본문 경계 결정을 각각의 자리에서 다루되 그 결합을 다루지 않는다. 이 책은 그 요소들을 8.5·9.2·9.10·10.4·13.12절에 나눠 세우고, 기법명과 분류는 본문에 도입하지 않았다. 텍스트 프로토콜에서 바이너리 프레이밍으로의 전환이 이 문제 지형을 어떻게 바꾸는지는 11.7.1절이 "파싱 모호성의 감소"라는 제목으로 다루며, 그 절 역시 HPBN 12장의 범위 안에 머문다.
